Middleware Deep Dive Building APIs

What you'll master: the request pipeline as a data structure — how next() actually works, what "downstream" and "upstream" mean, writing middleware that measures or modifies a response, the ordering rules that decide whether your security middleware protects anything, and the standard production stack. Prerequisites: Express Fundamentals.

Part 1 — The Pipeline Is a List and a Cursor

// Middleware is a function (req, res, next) registered in order. Express keeps
// an ordered list and a cursor; next() advances the cursor. That is the model.

app.use((req, res, next) => { console.log("1 in");  next(); console.log("1 out"); });
app.use((req, res, next) => { console.log("2 in");  next(); console.log("2 out"); });
app.get("/x", (req, res)  => { console.log("handler"); res.json({}); });

// GET /x prints:
//   1 in
//   2 in
//   handler
//   2 out          ← control returns as the stack unwinds
//   1 out
//
// So each middleware wraps everything registered after it. "Downstream" is
// the code next() runs; "upstream" is what happens after next() returns.
//
// CRUCIAL CAVEAT: with async handlers, next() returns as soon as the
// downstream handler AWAITS — not when it finishes. So "1 out" can print
// long before the response is sent. Anything that must observe the FINISHED
// response cannot rely on next() returning (see Part 3).

// Three things a middleware may do, and it must do exactly one:
//   1. call next()          → pass control downstream
//   2. respond              → end the request, pipeline stops
//   3. call next(err)       → jump to error middleware, skipping the rest
// Doing none of them hangs the request forever. Doing two produces
// ERR_HTTP_HEADERS_SENT. This is the whole contract.

Part 2 — Where Middleware Attaches

app.use(logger);                            // every request, every method
app.use("/api", apiOnly);                   // path PREFIX — /api, /api/x, /api/x/y
app.get("/admin", requireAuth, handler);    // route-specific, before the handler
app.get("/x", mw1, mw2, handler);           // a chain — arrays work too
router.use(requireAuth);                    // scoped to a mounted router subtree

// Ordering is the entire security model. These two lines are not equivalent:
app.use(rateLimit);  app.use(express.json());   // ✅ reject before parsing bodies
app.use(express.json());  app.use(rateLimit);   // ❌ parse 100KB from every
                                                //    attacker before rate limiting
// The second version does the expensive work first, so the rate limiter
// protects nothing from the cost it was added to prevent. Ask of every
// middleware: what does it protect, and is that thing after it?

// The standard production ordering, outermost first:
//   1. helmet()              security headers — cheap, applies to everything
//   2. request id + logger   so every later log line is correlatable
//   3. cors()                reject cross-origin before doing work
//   4. rate limiting         reject abuse before parsing
//   5. body parsers          express.json({ limit })
//   6. auth                  identify the caller
//   7. routes / routers
//   8. 404 handler
//   9. error handler (4-arg)

Part 3 — Middleware That Observes the Response

// Wrong: with async handlers, next() returns at the first await, so this
// measures the time until the handler SUSPENDS, not until it responds.
app.use((req, res, next) => {
  const t = Date.now();
  next();
  console.log(Date.now() - t);      // ❌ often ~0ms
});

// Right: listen for the response lifecycle event.
app.use((req, res, next) => {
  const start = process.hrtime.bigint();
  res.on("finish", () => {          // headers + body flushed successfully
    const ms = Number(process.hrtime.bigint() - start) / 1e6;
    console.log(req.method, req.originalUrl, res.statusCode, ms.toFixed(1));
  });
  next();
});

// The three events, and the distinction interviewers probe:
//   "finish" — the response was fully written. Success.
//   "close"  — the underlying connection closed. Fires for BOTH a normal
//              completion and a client that disconnected early.
//   "error"  — the response stream failed.
// To detect abandonment specifically: on "close", check res.writableFinished
// — false means the client left before you finished. Counting those as 5xx
// pollutes your error rate with users closing tabs.

// hrtime.bigint() rather than Date.now(): a monotonic clock. Date.now() can
// jump backwards on NTP correction, producing negative durations in your
// latency histograms — rare, real, and confusing when it happens.

Part 4 — Writing Useful Middleware

// Configurable middleware is a FACTORY — a function returning the middleware.
// This is the ubiquitous ecosystem convention (cors(), helmet(), rateLimit()).
export function requireRole(role) {
  return (req, res, next) => {
    if (!req.user) return next(Object.assign(new Error("Unauthenticated"), { status: 401 }));
    if (!req.user.roles.includes(role)) {
      return next(Object.assign(new Error("Forbidden"), { status: 403 }));
    }
    next();
  };
}
app.get("/admin/users", requireRole("admin"), listUsers);
// The factory runs ONCE at startup; the returned function runs per request.
// Expensive setup (compiling a schema, building a regex) belongs in the
// factory body, not inside the returned function where it repeats per request.

// Request-scoped context: attach to req, but namespace it.
app.use((req, res, next) => {
  req.ctx = { id: crypto.randomUUID(), startedAt: Date.now() };
  res.setHeader("x-request-id", req.ctx.id);
  next();
});
// Assigning req.id or req.user directly is common but collides with what
// libraries expect; one namespaced object is safer and greppable.

// Async middleware — same rules as handlers. On Express 5 a rejection is
// forwarded automatically:
export const loadUser = async (req, res, next) => {
  const token = req.headers.authorization?.replace(/^Bearer /, "");
  if (!token) return next();                 // anonymous is not an error here
  req.ctx.user = await users.findByToken(token);   // throws → error middleware
  next();
};
// Note the deliberate split: this middleware IDENTIFIES, requireRole
// AUTHORIZES. Keeping them separate lets public routes run the first
// without the second, instead of duplicating token parsing per route.
The most common middleware bug is a missing return before next(). next() does not stop execution — it invokes the rest of the pipeline and then returns. A guard written as if (!ok) next(err); doWork(); runs doWork() anyway, after the error handler has already responded, and the symptom is ERR_HTTP_HEADERS_SENT pointing at code that looks correct. Always return next(...).

Part 5 — Error Middleware in the Pipeline

// next(err) skips every remaining NORMAL middleware and jumps to the first
// 4-argument handler. You can chain error handlers by calling next(err) again:

app.use((err, req, res, next) => {              // 1. classify
  if (err.name === "ZodError") {
    err.status = 422;
    err.details = err.issues;
  }
  next(err);
});

app.use((err, req, res, next) => {              // 2. log
  const status = err.status ?? 500;
  if (status >= 500) req.log?.error({ err, reqId: req.ctx?.id }, "unhandled");
  next(err);
});

app.use((err, req, res, next) => {              // 3. respond
  if (res.headersSent) return next(err);        // delegate: Express destroys it
  const status = err.status ?? 500;
  res.status(status).json({
    error: status >= 500 ? "Internal error" : err.message,
    details: err.details,
    requestId: req.ctx?.id,                     // ← give the user something to
  });                                           //   quote in a support ticket
});

// Splitting classify/log/respond keeps each piece testable and lets you add
// error TYPES without touching the responder. Returning the request id is a
// small thing that makes production support dramatically easier: the user
// quotes an id, you grep one correlated trace.

Part 6 — The Production Stack, Assembled

import express from "express";
import helmet from "helmet";
import cors from "cors";
import rateLimit from "express-rate-limit";
import pinoHttp from "pino-http";

const app = express();

app.set("trust proxy", 1);        // ← behind a load balancer / reverse proxy
// Without it, req.ip is the PROXY's address: rate limiting then throttles
// every user as one client, and your access logs record one IP forever.
// With it, Express trusts X-Forwarded-For. Set it to the number of proxies
// you actually have — blanket `true` lets clients spoof their own IP by
// sending the header themselves, which defeats IP-based rate limiting.

app.use(helmet());                                   // security headers
app.use(pinoHttp());                                 // structured logs + req.log
app.use(cors({ origin: ["https://app.example.com"] }));  // never reflect *
app.use(rateLimit({ windowMs: 60_000, limit: 100 }));
app.use(express.json({ limit: "100kb" }));
app.use(loadUser);

app.use("/api/orders", ordersRouter);

app.use((req, res) => res.status(404).json({ error: "Not found" }));
app.use(classifyErrors, logErrors, respondToErrors);

// CORS is browser-enforced, not server-enforced. It restricts what BROWSER
// JavaScript on other origins may read — curl and server-to-server calls
// ignore it entirely. It is not authentication, and origin: "*" with
// credentials is a configuration browsers reject outright.

Interview Questions

Beginner: What are the three things a middleware function may do?

Call next() to pass control downstream, send a response itself (ending the pipeline), or call next(err) to skip to error middleware. It must do exactly one: doing none leaves the request hanging until the client times out with nothing logged, and doing two produces ERR_HTTP_HEADERS_SENT.

Beginner: What does app.use("/api", mw) match?

Any request whose path begins with /api — /api, /api/orders, /api/orders/42. Mount paths are prefixes, not exact matches, and the mounted middleware sees the path relative to the mount point in req.url while req.originalUrl keeps the full path — which is why logging middleware should use originalUrl.

Mid: Why does timing middleware that measures around next() report near-zero durations?

Because next() returns as soon as the downstream async handler hits its first await, not when the response is sent. The synchronous portion of the handler is typically microseconds, so the measurement reflects setup time rather than request latency. The fix is to hook the response lifecycle: record a start timestamp, then compute the duration inside res.on("finish"), which fires when the response has actually been flushed. Use process.hrtime.bigint() rather than Date.now() so an NTP adjustment cannot produce a negative duration.

Mid: Why does middleware order matter for security, with a concrete example?

Because middleware only protects what runs after it. Registering express.json() before a rate limiter means every attacker request gets fully parsed — up to the body limit, allocated and deserialized — before the limiter decides to reject it, so the limiter fails to prevent the resource consumption it exists to prevent. The general rule is cheap rejections first: security headers, request identity, CORS, rate limiting, then parsing, then auth, then routes. Ask of each middleware what it protects and confirm that thing is registered after it.

Senior: A service behind an ALB rate-limits at 100 req/min per IP, but in production either everyone is throttled at once or nobody is. Diagnose.

Classic trust proxy misconfiguration, and the two symptoms are the two wrong settings. Unset, req.ip is the load balancer's address, so every user collapses into a single bucket and the whole userbase shares one 100/min budget — everyone throttled together. Set to blanket true while directly reachable, Express trusts the leftmost X-Forwarded-For entry, which the client controls; an attacker rotates that header and gets an unlimited number of buckets — nobody throttled. The correct configuration is the exact number of trusted proxy hops (app.set("trust proxy", 1) for a single ALB) so Express counts inward from the right and derives the real client IP. The transferable principle: any header-derived identity is only as trustworthy as the infrastructure guaranteed to overwrite it, so trust must be configured to match the actual topology rather than turned fully on or off.

Senior: Design request-scoped context (request id, user, timing) available deep in the call stack without threading arguments. Trade-offs?

Two viable designs. The explicit one attaches a namespaced object to req and passes it down as a parameter: simple, obvious, fully testable, but it threads an argument through every layer including code that does not care, and it does not reach into libraries. The implicit one uses AsyncLocalStorage from node:async_hooks: the middleware calls als.run(ctx, next), and any code in that async context calls als.getStore() — no argument threading, and logging libraries can automatically attach request ids to every line, which is its real payoff. Costs: a small performance overhead, and it is action at a distance, so a function's behaviour depends on invisible ambient state that is easy to forget in tests and can be lost if code escapes the async context. My default is explicit passing for business logic where the dependency should be visible, and AsyncLocalStorage specifically for cross-cutting observability — log correlation, tracing — where threading a parameter through every function would be pure noise. Avoid using it as a general dependency-injection mechanism; that is where implicit context turns into untraceable coupling.

1 (easy): Write middleware that logs method, path, and status for every request.
Solution 
app.use((req, res, next) => {
  res.on("finish", () => {
    console.log(req.method, req.originalUrl, res.statusCode);
  });
  next();
});
// originalUrl, not url: inside a mounted router, req.url is relative to the
// mount point, so mounted routes would all log the same short path.
2 (easy): Find the bug: app.use((req,res,next) => { if (!req.headers.authorization) next(new Error("no auth")); req.user = parse(req.headers.authorization); next(); });
Solution 
// Two bugs, one root cause: next() does not stop execution.
// With no auth header, next(err) runs AND THEN parse(undefined) runs and
// next() is called a second time — so the error handler responds, then the
// pipeline continues, producing ERR_HTTP_HEADERS_SENT that points at
// innocent-looking downstream code.
app.use((req, res, next) => {
  if (!req.headers.authorization) return next(new Error("no auth"));
  req.user = parse(req.headers.authorization);
  return next();
});
3 (medium): Write a requireRole(role) factory returning 401 for anonymous and 403 for wrong role.
Solution 
export function requireRole(role) {
  return (req, res, next) => {
    const user = req.ctx?.user;
    if (!user) return next(Object.assign(new Error("Unauthenticated"), { status: 401 }));
    if (!user.roles?.includes(role)) {
      return next(Object.assign(new Error("Forbidden"), { status: 403 }));
    }
    return next();
  };
}
app.get("/admin/users", requireRole("admin"), listUsers);

// 401 vs 403 is a real distinction, not pedantry: 401 tells the client to
// authenticate and retry, 403 tells it retrying is pointless. Returning 403
// to an anonymous user sends clients into a login loop they can never exit.
4 (medium): Add a request id to every request, expose it in a response header, and include it in error responses.
Solution 
import { randomUUID } from "node:crypto";

app.use((req, res, next) => {
  // Honour an upstream id when present so a trace spans services.
  req.ctx = { id: req.headers["x-request-id"] ?? randomUUID() };
  res.setHeader("x-request-id", req.ctx.id);
  next();
});

app.use((err, req, res, next) => {
  if (res.headersSent) return next(err);
  const status = err.status ?? 500;
  console.error({ reqId: req.ctx?.id, err });
  res.status(status).json({
    error: status >= 500 ? "Internal error" : err.message,
    requestId: req.ctx?.id,
  });
});
// Accepting an inbound id is what makes ids useful across a call graph;
// generating a fresh one per hop gives you unlinkable fragments.
5 (hard): Write middleware that rejects requests exceeding a deadline, and explain what it can and cannot cancel.
Solution 
export function deadline(ms) {
  return (req, res, next) => {
    const ac = new AbortController();
    req.ctx = { ...req.ctx, signal: ac.signal };

    const timer = setTimeout(() => {
      ac.abort();                                  // cooperative cancellation
      if (!res.headersSent) {
        res.status(503).json({ error: "Request timeout" });
      }
    }, ms);

    res.on("close", () => clearTimeout(timer));    // fires on finish AND abort
    next();
  };
}
// Handlers must OPT IN by passing req.ctx.signal to fetch, DB drivers, etc.
//
// What it cannot do: interrupt work that ignores the signal. JavaScript has
// no thread to kill — a synchronous CPU-bound loop blocks the event loop and
// the timer itself will not even fire until it finishes. Likewise a DB query
// that does not accept a signal keeps running server-side; you stop WAITING,
// you do not stop the WORK. So this bounds the client's wait and frees the
// socket, but real resource protection also needs query timeouts in the
// database, statement timeouts in the driver, and CPU-bound work moved off
// the event loop (worker threads). Cancellation in Node is cooperative all
// the way down — a signal is a request, never a guarantee.
6 (hard): Two middlewares both need to know the response body size — one for logging, one for a metrics counter. Implement without either breaking streaming.
Solution 
// Naive approach — monkey-patch res.write/res.end to accumulate the body —
// destroys streaming: it buffers the entire response in memory, which for a
// file download reintroduces exactly the OOM that streaming prevents.
// COUNT bytes instead of collecting them.

app.use((req, res, next) => {
  let bytes = 0;
  const write = res.write.bind(res);
  const end = res.end.bind(res);

  res.write = (chunk, ...rest) => {
    if (chunk) bytes += Buffer.byteLength(chunk);
    return write(chunk, ...rest);
  };
  res.end = (chunk, ...rest) => {
    if (chunk && typeof chunk !== "function") bytes += Buffer.byteLength(chunk);
    return end(chunk, ...rest);
  };

  res.ctx = { get bytes() { return bytes; } };   // ONE source of truth
  res.on("finish", () => metrics.observe(bytes));
  next();
});

// Both consumers read res.ctx.bytes in their own res.on("finish") handler.
// Two independent patches of the same methods would work but each layer of
// wrapping adds a call frame to every chunk write and makes ordering bugs
// possible; a single measurement point published on res is cheaper and
// easier to reason about.
//
// Better still when available: skip patching entirely and read the
// content-length response header for buffered responses, falling back to
// counting only for streamed ones. Monkey-patching core methods is a real
// cost — it breaks when the platform changes signatures (res.end's callback
// argument is exactly such a trap, handled above) — so prefer the boring
// route when it exists.

🎯 Key Takeaways

  • Middleware is an ordered list with a cursor; next() advances it and each middleware wraps everything registered after it.
  • Every middleware must do exactly one of: next(), respond, or next(err) — none hangs the request, two throws.
  • next() does not stop execution; return next(...) is the habit that prevents double responses.
  • With async handlers, next() returns at the first await — measure responses in res.on("finish"), not around next().
  • Order is the security model: cheap rejections (headers, CORS, rate limits) before expensive work (body parsing, auth, handlers).
  • trust proxy must match your real topology — unset breaks per-IP rate limiting, blanket true lets clients spoof their IP.
  • Configurable middleware is a factory: setup runs once at startup, the returned function runs per request.
  • Splitting error middleware into classify → log → respond keeps error types addable without touching the responder.
  • Returning a request id to clients turns vague bug reports into a single greppable trace.
  • Cancellation is cooperative: an AbortSignal bounds waiting, it does not stop work that ignores it.
