Caching & Redis Data & Auth

What you'll master: where caches belong, the cache-aside pattern and its invalidation problem, stampede protection, Redis data structures beyond GET/SET, distributed locks and their real guarantees, and HTTP caching that moves work out of your service entirely. Prerequisites: Databases & ORMs, REST API Design. See also the Redis track.

Part 1 — Cache-Aside, and the Two Hard Parts

async function getProduct(id) {
  const key = `product:${id}`;
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);              // 1. try cache

  const product = await db.findProduct(id);     // 2. miss → source of truth
  if (product) {
    await redis.set(key, JSON.stringify(product), "EX", 300);   // 3. populate
  }
  return product;
}
// This is cache-aside (lazy loading): the application owns the cache. It is
// the default pattern and the one worth knowing cold.

// Properties that follow:
//   ✅ only requested data is cached — no wasted memory
//   ✅ a cache outage degrades to slow, not broken (if you handle errors)
//   ❌ every miss pays cache + database latency
//   ❌ data can be stale for up to the TTL

// THE TWO HARD PARTS, and everything else in this lesson descends from them:
//
// 1. INVALIDATION — knowing when cached data became wrong. TTL is the lazy
//    answer: accept staleness up to N seconds. Explicit invalidation on
//    write is more correct but requires knowing every key affected by every
//    write, which is where bugs live.
//
// 2. CONSISTENCY under concurrent writes — two requests can interleave a
//    read, a database write, and a cache write in an order that leaves the
//    cache holding a value the database never had (see Part 3).

// ALWAYS make the cache optional at runtime:
async function getProductSafe(id) {
  try {
    const hit = await redis.get(`product:${id}`);
    if (hit) return JSON.parse(hit);
  } catch (err) {
    log.warn({ err }, "cache read failed");     // degrade, do not fail
  }
  return db.findProduct(id);
}
// A cache that can take the service down when it is unavailable has made
// availability WORSE — you added a dependency to make things faster and
// accidentally made it load-bearing.

Part 2 — TTL, Eviction, and What to Cache

// TTL is a correctness knob disguised as a performance knob: it is the
// maximum time you accept serving wrong data.
//   product catalogue     → minutes (rarely changes, staleness tolerable)
//   user profile          → seconds-to-minutes
//   inventory count       → seconds, or do not cache
//   account balance       → do not cache; read the source of truth
//   permissions/roles     → short, AND invalidate explicitly on change
// "How wrong can this be before someone is harmed?" is the question. Money
// and authorization answers are usually "not at all".

// Eviction policy (redis.conf maxmemory-policy) matters as much as TTL:
//   allkeys-lru     — evict least-recently-used. Right for a pure cache.
//   volatile-lru    — only keys with a TTL. Right when Redis ALSO holds
//                     non-cache data (sessions, queues) that must not vanish.
//   noeviction      — reject writes when full. Right for a queue/store,
//                     catastrophic for a cache (writes start erroring).
// Mixing cache and durable data in one Redis instance with allkeys-lru is a
// classic incident: your sessions get evicted under memory pressure and
// every user is logged out at once.

// Add jitter to TTLs so keys populated together do not expire together:
const ttl = 300 + Math.floor(Math.random() * 60);
await redis.set(key, value, "EX", ttl);
// Without jitter, a deploy that warms 10,000 keys creates a synchronized
// expiry 300 seconds later — a self-inflicted stampede on a timer.

Part 3 — Invalidation Strategies

// On write, you must choose. Each option has a real failure mode.

// A) Delete the key (invalidate) — the safest default:
await db.updateProduct(id, data);
await redis.del(`product:${id}`);
// Next read repopulates from the database. Simple, and a lost delete costs
// you one TTL of staleness rather than permanent corruption.

// B) Write-through (update the cache with the new value):
await db.updateProduct(id, data);
await redis.set(`product:${id}`, JSON.stringify(data), "EX", 300);
// Keeps the cache warm, but it is the RACY one:
//   T1 reads DB (v1) → T2 writes DB (v2) → T2 sets cache (v2)
//                                        → T1 sets cache (v1)  ← stale wins
// The cache now holds v1 while the database holds v2, and no TTL-length
// bound applies to when someone notices. Delete-on-write does not have this
// failure because a delete is idempotent and order-independent.

// ORDER MATTERS: database first, then cache. If you invalidate first, a
// concurrent read can repopulate from the old row before your write lands.

// C) Versioned keys — sidestep invalidation entirely:
const v = await redis.incr(`product:${id}:v`);      // bump on write
const key = `product:${id}:${v}`;
// Old versions simply age out by TTL. No delete needed, no race. Costs more
// memory for a while, and every read needs the version lookup.

// Invalidating GROUPS — never use KEYS in production:
await redis.keys("product:*");       // ❌ O(n) over the entire keyspace,
                                     //    blocks the single-threaded server
for await (const keys of redis.scanIterator({ MATCH: "product:*", COUNT: 100 })) {
  if (keys.length) await redis.del(keys);          // ✅ incremental
}
// Better: maintain a Set of member keys per group, or use versioned
// prefixes so a single counter bump invalidates a whole group at once.
Cache stampede (thundering herd) is the failure that takes services down. A popular key expires; a thousand concurrent requests all miss, and all thousand hit the database simultaneously with the same query. The database saturates, responses slow, more requests pile up, and the cache never repopulates because every attempt times out. The cache made you faster right up until it made you unavailable — and the trigger is a routine expiry, not an attack.

Part 4 — Stampede Protection

// Strategy 1 — single-flight in-process: collapse concurrent identical
// misses within ONE Node process into a single database call.
const inflight = new Map();

async function getWithSingleFlight(key, loader) {
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  if (inflight.has(key)) return inflight.get(key);    // join the existing call

  const promise = loader()
    .then(async (value) => {
      await redis.set(key, JSON.stringify(value), "EX", 300);
      return value;
    })
    .finally(() => inflight.delete(key));             // ← always clean up

  inflight.set(key, promise);
  return promise;
}
// Cheap and effective, but per-process: 20 pods still produce 20 queries
// instead of 1000. Usually that is enough.

// Strategy 2 — distributed lock: exactly one process across the fleet
// recomputes; the others wait briefly and re-read.
const got = await redis.set(`lock:${key}`, id, "NX", "PX", 5000);
if (got) { /* recompute, set, then release */ }
else { await sleep(50); return getFromCacheOrWait(key); }

// Strategy 3 — probabilistic early expiry (XFetch): refresh BEFORE expiry,
// with probability rising as the TTL nears. Avoids a synchronized cliff
// without any coordination at all:
const shouldRefresh = Math.random() < (elapsed / ttl) ** 3;

// Strategy 4 — stale-while-revalidate: serve the stale value immediately and
// refresh in the background. Best latency, and the cache never has a gap:
const entry = JSON.parse(await redis.get(key) ?? "null");
if (entry && entry.expiresAt < Date.now()) {
  refreshInBackground(key).catch((err) => log.warn({ err }, "refresh failed"));
}
return entry?.value;                       // stale but instant
// Store a logical expiry INSIDE the value with a longer physical TTL, so
// "expired" is a property you can read rather than a key that vanished.

Part 5 — Redis Beyond GET/SET

// Redis is a data-structure server. Using it only as a string cache leaves
// most of its value unused.

// Hashes — update one field without rewriting the whole object:
await redis.hSet(`user:${id}`, { name: "Ada", email: "ada@x.com" });
await redis.hIncrBy(`user:${id}`, "loginCount", 1);

// Sorted sets — leaderboards, rate limiting, time-ordered indexes:
await redis.zAdd("leaderboard", { score: 4200, value: "user:42" });
await redis.zRangeWithScores("leaderboard", 0, 9, { REV: true });   // top 10

// A sliding-window rate limiter in three commands:
const now = Date.now();
await redis.zRemRangeByScore(key, 0, now - windowMs);   // drop old entries
const count = await redis.zCard(key);
if (count >= limit) throw new AppError("Rate limited", { status: 429 });
await redis.zAdd(key, { score: now, value: `${now}:${randomUUID()}` });
await redis.expire(key, Math.ceil(windowMs / 1000));
// More accurate than a fixed window, which allows a 2× burst at the boundary
// (limit requests at 0:59 and limit more at 1:01).

// Sets — uniqueness and membership:
await redis.sAdd(`post:${id}:voters`, userId);      // returns 0 if already there

// Atomicity: MULTI batches commands, but for read-then-write logic you need
// a Lua script, which Redis runs atomically:
const script = `
  local current = redis.call("GET", KEYS[1])
  if current and tonumber(current) >= tonumber(ARGV[1]) then return 0 end
  return redis.call("INCR", KEYS[1])`;
await redis.eval(script, { keys: [key], arguments: [String(limit)] });
// The check and the increment cannot interleave with another client's —
// which a GET followed by an INCR from Node cannot guarantee.

// Pipelining — one round trip instead of N (a latency win, not atomicity):
const pipeline = redis.multi();
ids.forEach((id) => pipeline.get(`product:${id}`));
const results = await pipeline.exec();

Part 6 — HTTP Caching: the Cache You Do Not Run

// The cheapest request is the one that never reaches your service.
res.set("cache-control", "public, max-age=300, stale-while-revalidate=60");
res.set("etag", `"${hashOf(body)}"`);

// Conditional requests — the client asks "has it changed?":
if (req.headers["if-none-match"] === currentEtag) {
  return res.status(304).end();      // no body: saves bandwidth, not compute
}

// Cache-Control directives that matter:
//   public        — any cache (CDN, proxy) may store it
//   private       — browser only; NEVER use public for per-user data, or a
//                   shared CDN can serve one user's response to another.
//                   This is a real and severe incident class.
//   max-age=N     — fresh for N seconds
//   s-maxage=N    — overrides max-age for SHARED caches specifically
//   no-store      — never persist (auth responses, personal data)
//   no-cache      — may store, but must revalidate before reuse
//   stale-while-revalidate=N — serve stale up to N seconds while refreshing
//                   in the background: the HTTP version of Part 4's pattern
//   immutable     — content-hashed assets that will never change

// Vary tells caches which request headers change the response:
res.set("vary", "accept-encoding, authorization");
// Omitting `authorization` on a personalized response is exactly how a CDN
// serves user A's data to user B.

// The layered picture, cheapest first:
//   browser cache → CDN → your HTTP cache → Redis → database
// Each layer absorbs load from the next. A correctly cached static asset
// never touches your infrastructure at all.

Interview Questions

Beginner: Describe cache-aside and its trade-offs.

In cache-aside, the application manages the cache itself, beside the database. On a read, it checks the cache first. On a hit, it returns the cached value. On a miss, it reads from the database, writes the result into the cache with a time-to-live, and returns it.

  async function getProduct(id) {
    const hit = await cache.get(`product:${id}`);
    if (hit) return JSON.parse(hit);
    const product = await db.getProduct(id);
    await cache.set(`product:${id}`, JSON.stringify(product), { EX: 300 });
    return product;
  }

Its strengths explain why it is the most common pattern. It is simple and needs no special cache infrastructure. It caches only what is actually read, so memory is spent on hot data rather than everything. And it is resilient: if the cache disappears, the application still works by reading from the database — just more slowly.

The trade-offs are real. The first request for any key is slow, and after a deploy or cache restart every key is cold at once, which can surge load onto the database. Data can be stale for up to the TTL, because the database can change without the cache knowing. And invalidation is the application's responsibility: every code path that writes the data must remember to invalidate the key, and a forgotten path serves stale data until expiry.

The alternatives shift those costs: write-through updates the cache on every write, keeping it fresh at the cost of caching data that may never be read, while read-through moves the loading logic into the cache layer itself.

Beginner: Why should a cache read failure not fail the request?

Because a cache is an optimisation, not a source of truth. The data it holds also exists in the database. If the cache is unavailable, the correct behaviour is to fall through to the database and serve the request slightly more slowly — not to return an error.

Treating a cache failure as fatal turns an optional component into a single point of failure. A Redis restart, a network blip or an eviction storm would then take down every endpoint that reads from the cache, even though the database is perfectly healthy and could serve every one of those requests.

  async function cachedGet(key, load) {
    try {
      const hit = await cache.get(key, { timeout: 50 });
      if (hit) return JSON.parse(hit);
    } catch (err) {
      log.warn({ err, key }, "cache read failed; falling through");
    }
    return load();
  }

The short timeout matters as much as the catch. A cache that is not down but slow is worse than one that fails outright, because every request waits for it. Bounding the call at tens of milliseconds means a degraded cache costs a little latency rather than hanging requests.

There is an important caveat. If the database was sized on the assumption that the cache absorbs most reads, a complete cache outage sends the full read load to the database at once, which may overwhelm it. So the fallback should be protected: a circuit breaker that stops hammering a failing cache, and load shedding or rate limiting if the database cannot take the full traffic. Monitor the cache hit rate so a drop is noticed before it becomes an outage.

Mid: What is a cache stampede and how do you prevent it?

A stampede — also called a thundering herd or dogpile — happens when a popular cache key expires and many requests miss at the same moment. Every one of them goes to the database to recompute the same value simultaneously.

If a key is read a thousand times a second and takes 500ms to compute, its expiry sends around five hundred identical expensive queries to the database before the first one finishes and repopulates the cache. That load spike can slow or knock over the database — and if it does, the recomputation fails, the key stays empty, and the stampede continues.

There are several complementary defences.

Request coalescing, or single-flight: ensure only one request recomputes a given key while the others wait for its result. Within one process this is a map of in-flight promises; across instances it is a short-lived distributed lock.

  const inflight = new Map();
  function load(key, compute) {
    if (!inflight.has(key)) {
      inflight.set(key, compute().finally(() => inflight.delete(key)));
    }
    return inflight.get(key);
  }

Stale-while-revalidate: keep serving the expired value while one background refresh runs, so no request ever waits and the database sees a single recomputation.

Early, probabilistic refresh: recompute a key shortly before it expires, with a probability that rises as expiry approaches, so a refresh usually happens before the herd arrives.

TTL jitter: add randomness to expiry times so that keys cached together — for example after a deploy — do not all expire in the same second.

Mid: Why prefer deleting a cache key on write over updating it?

Because updating the cache on write is vulnerable to race conditions that leave permanently stale data, while deleting is not.

Consider two concurrent writes to the same record. Request A writes value 1 to the database; request B writes value 2. Their cache updates can arrive in the opposite order, because the database write and the cache write are two separate operations with nothing ordering them across requests. B updates the cache to 2, then A — delayed by a GC pause or network jitter — updates it to 1. The database holds 2, the cache holds 1, and the cache now serves the wrong value until the TTL expires, which for long TTLs may be hours.

Deleting sidesteps that. Both writers delete the key; deletes are idempotent and order does not matter. The next read misses and repopulates from the database — the source of truth — so it gets the current value.

Deleting is also simpler: the write path does not need to know how the cached value is built. A cached value is often a derived object — a product with its prices and stock joined together — and reconstructing it correctly in every write path duplicates that logic and invites mistakes.

Deleting is not perfectly race-free either. A read can fetch the old value from the database just before a write, then store it in the cache just after the write's delete — reintroducing stale data. That window is small, and it is mitigated by keeping TTLs bounded, deleting after the database transaction commits rather than before, and, where it matters, a delayed second delete. The cost of deleting is one extra miss after each write, which is almost always worth paying.

Senior: Design caching for a product page: catalogue data, per-user pricing, and live inventory. Justify each decision.

These three have different staleness tolerances, so caching them uniformly is the mistake to avoid. Catalogue data — names, descriptions, images — changes rarely and is identical for everyone, so it gets a long TTL in Redis and is also cacheable at the CDN with public, which removes most traffic from the service entirely. Per-user pricing is personalized, so it must never be in a shared cache: cache it in Redis under a user-scoped key with a short TTL, and mark the HTTP response private with an appropriate Vary so no CDN can store it — getting this wrong means serving one customer's price to another, which is both a correctness and a privacy failure. Live inventory is the one where staleness has real consequences, since showing an item in stock that is not causes failed checkouts; I would either not cache it or cache for a couple of seconds purely as stampede protection, and critically I would treat the displayed count as advisory while enforcing actual availability transactionally at checkout with the condition in the UPDATE, because no cache TTL can make a read-time check authoritative. Composition matters too: rendering these from one cached blob forces the shortest TTL onto everything, so they should be separate cache entries assembled per request. Finally, hot products need stampede protection and jittered TTLs, and every cache read degrades to the source on error.

Senior: A team uses a Redis distributed lock to guarantee a job runs exactly once. What would you tell them?

That a Redis lock gives mutual exclusion most of the time, not a correctness guarantee, and that "exactly once" cannot be built on it. The specific failure: a process acquires the lock with a TTL, stalls — garbage collection pause, network partition, a slow disk — long enough for the TTL to expire, and a second process acquires the same lock. Now both believe they hold it and both run the job. Adding a fencing token helps only if the protected resource can reject stale tokens, which requires support in that resource. Redlock across multiple nodes is also contested and does not remove the timing assumption. What I would recommend instead is designing the job to be idempotent, so a duplicate run is harmless — a unique constraint on a natural key, an upsert, or an idempotency key like the payments pattern — and using the lock purely as an optimization to avoid duplicated work rather than as a correctness mechanism. If exactly-once truly matters, it needs a transactional guarantee where the effect lives: a database transaction, a unique index, or a queue with proper delivery semantics and deduplication. Minimum practical hardening for the lock itself: always set a TTL so a crash cannot hold it forever, release only if you still own it via a Lua compare-and-delete rather than a bare DEL, and keep the critical section much shorter than the TTL. The underlying principle is that distributed locks built on timeouts assume bounded pauses, and that assumption is exactly what fails in the incidents you built the lock for.

2 (easy): Why is KEYS product:* dangerous, and what replaces it?
Solution 
// Redis executes commands on a single thread. KEYS scans the ENTIRE keyspace
// in one blocking operation, so on a few million keys every other client —
// including your session lookups — stalls for the duration.
for await (const keys of redis.scanIterator({ MATCH: "product:*", COUNT: 100 })) {
  if (keys.length) await redis.del(keys);
}
// SCAN returns a cursor and works incrementally, so other commands interleave.

3 (medium): Implement single-flight so concurrent misses for the same key trigger one database call.
Solution 
const inflight = new Map();

export async function cached(key, ttl, loader) {
  const hit = await redis.get(key).catch(() => null);
  if (hit) return JSON.parse(hit);

  if (inflight.has(key)) return inflight.get(key);   // join the in-flight call

  const p = (async () => {
    const value = await loader();
    await redis.set(key, JSON.stringify(value), "EX", ttl + Math.floor(Math.random() * 30))
      .catch(() => {});
    return value;
  })().finally(() => inflight.delete(key));          // cleanup on BOTH paths

  inflight.set(key, p);
  return p;
}
// The .finally is essential: without it a rejected load leaves a permanently
// cached rejected promise, and every later request for that key fails.
// Scope note: this collapses misses within ONE process. Across 20 pods you
// still get up to 20 loads — usually acceptable, and far better than 1000.
4 (medium): Implement a sliding-window rate limiter with a Redis sorted set.
Solution 
async function allow(userId, limit = 100, windowMs = 60_000) {
  const key = `rl:${userId}`;
  const now = Date.now();

  const results = await redis.multi()
    .zRemRangeByScore(key, 0, now - windowMs)      // drop entries out of window
    .zCard(key)                                     // count what remains
    .zAdd(key, { score: now, value: `${now}:${randomUUID()}` })
    .expire(key, Math.ceil(windowMs / 1000))        // reclaim idle keys
    .exec();

  const count = results[1];
  return count < limit;
}
// The member includes a UUID because two requests in the same millisecond
// would otherwise collide on value and count as one (sorted set members are
// unique).
// Sliding beats a fixed window because a fixed window permits a 2x burst
// across the boundary: `limit` requests at 0:59 plus `limit` at 1:01.
// Note this counts the current request before the limit check ordering —
// for strict enforcement, do the check and add atomically in a Lua script.
5 (hard): Implement stale-while-revalidate: serve stale instantly, refresh in the background, exactly one refresher.
Solution 
// Store a LOGICAL expiry inside the value, with a longer PHYSICAL TTL so the
// key still exists after it goes stale.
async function swr(key, logicalTtlMs, physicalTtlSec, loader) {
  const raw = await redis.get(key).catch(() => null);

  if (raw) {
    const entry = JSON.parse(raw);
    if (entry.expiresAt <= Date.now()) {
      // Stale: refresh in the background, but only ONE refresher fleet-wide.
      redis.set(`lock:${key}`, "1", { NX: true, PX: 10_000 })
        .then(async (won) => {
          if (!won) return;
          try {
            const fresh = await loader();
            await redis.set(key, JSON.stringify({
              value: fresh, expiresAt: Date.now() + logicalTtlMs,
            }), "EX", physicalTtlSec);
          } finally {
            await redis.del(`lock:${key}`).catch(() => {});
          }
        })
        .catch((err) => log.warn({ err, key }, "background refresh failed"));
    }
    return entry.value;              // ← stale or fresh, returned IMMEDIATELY
  }

  const value = await loader();      // cold miss: must wait
  await redis.set(key, JSON.stringify({
    value, expiresAt: Date.now() + logicalTtlMs,
  }), "EX", physicalTtlSec).catch(() => {});
  return value;
}
// Why physical > logical TTL: if the key vanished at logical expiry there
// would be nothing stale to serve, and you would be back to a stampede on a
// cold miss. The gap between the two is your protection window.
// The NX lock bounds refresh work to one process; note it is an optimization,
// not a correctness guarantee — a duplicate refresh is harmless here, which
// is exactly when a Redis lock is the right tool.
6 (hard): After adding caching, users intermittently see other users' data. Diagnose the likely causes and the fixes.
Solution 
// This is a severe, reportable class of bug. Three likely causes:

// 1. CACHE KEY MISSING THE USER DIMENSION — the most common.
const key = `dashboard:${orgId}`;              // ❌ same key for every user
const key = `dashboard:${orgId}:${userId}`;    // ✅ every input in the key
// Rule: the key must include EVERY input that affects the output — user,
// role, locale, feature flags, API version. If two requests can produce
// different responses, they must not share a key.

// 2. HTTP CACHE-CONTROL: public ON A PERSONALIZED RESPONSE.
res.set("cache-control", "public, max-age=60");    // ❌ CDN stores it once
res.set("cache-control", "private, max-age=60");   // ✅ browser only
res.set("vary", "authorization");                  // ✅ if it must be shared
// A shared CDN caching a personalized response will serve the first user's
// body to everyone else — and it is invisible in your logs, because the
// requests never reach you.

// 3. A REQUEST-SCOPED VALUE STORED AT MODULE SCOPE.
let currentUser;                     // ❌ shared across concurrent requests
app.use((req) => { currentUser = req.user; });
// Under concurrency, request B overwrites the variable while request A is
// awaiting, and A resumes with B's user. Use req/AsyncLocalStorage instead.

// Response procedure, in order:
//   • purge the affected caches immediately (CDN and Redis) — stop the leak
//     before diagnosing it
//   • determine blast radius from CDN logs: which paths, how many distinct

🎯 Key Takeaways

  • Cache-aside is the default; always make cache failures degrade to the source of truth rather than fail the request.
  • TTL is a correctness decision — it is the maximum time you accept serving wrong data.
  • Delete on write rather than update: deletion is idempotent, so interleaving costs a miss instead of persistent staleness.
  • Write the database first, then invalidate; the reverse order lets a concurrent read repopulate stale data.
  • Stampedes turn a routine expiry into an outage — use single-flight, locks, early refresh, or stale-while-revalidate, and always jitter TTLs.
  • Never run KEYS in production; Redis is single-threaded and it blocks every other client.
  • Read-modify-write against Redis needs a Lua script — separate commands from Node can interleave.
  • Do not mix evictable cache data and durable data in one instance under allkeys-lru.
  • A cache key must contain every input that affects the response, or users will see each other's data.
  • Distributed locks give mutual exclusion, not exactly-once — design idempotent work and use locks as an optimization.
  • Cache-aside caches only what is read, and survives a cache outage.
  • Its costs are cold starts, staleness and application-owned invalidation.
  • A cache is an optimisation, never the source of truth.
  • A slow cache is worse than a failed one, so bound its latency.
  • Plan for the full load reaching the database if the cache disappears.
  • A stampede is many simultaneous misses on one hot key.
  • Coalesce recomputation so only one request does the work.
  • Delete keys on write rather than updating them.
