Performance & Profiling Production Node

What you'll master: measuring before optimizing, event loop lag as the defining Node metric, CPU profiling with flame graphs, finding and fixing memory leaks with heap snapshots, the async pitfalls that quietly serialize your code, and knowing when the answer is architectural rather than micro-optimization. Prerequisites: The Event Loop & libuv, Logging & Observability.

Part 1 — Measure First, Always

// The rule that saves the most time: find the bottleneck before touching
// anything. Intuition about performance is wrong often enough that
// optimizing unmeasured code usually means adding complexity for nothing.

// Establish the ORDER OF MAGNITUDE before you profile — it tells you which
// layer can possibly matter:
//   L1 cache reference            ~1 ns
//   main memory reference       ~100 ns
//   V8 function call             ~2 ns
//   JSON.parse of 1KB            ~2 µs
//   Redis GET (same DC)       ~200 µs
//   Postgres simple query    ~1–5 ms
//   HTTP call to another svc ~5–50 ms
//   Disk seek (spinning)        ~10 ms
//
// A handler doing one database query (2ms) and 500 array operations (~50µs)
// spends 97% of its time waiting on the database. Optimizing the array work
// cannot produce more than a 3% improvement no matter how clever it is —
// this is Amdahl's law, and it is why measurement comes first.

// Where the time actually goes in most Node services, in order:
//   1. waiting on I/O (database, upstreams) — usually dominant
//   2. serialization (JSON.stringify of large payloads)
//   3. blocking the event loop with synchronous work
//   4. garbage collection pressure from excessive allocation
//   5. actual algorithmic cost in your own code — usually last
// Notice that four of the five are not "slow JavaScript".

// Quick local timing before reaching for a profiler:
console.time("query"); await db.query(sql); console.timeEnd("query");
// Structured, keeps working in production:
const t = process.hrtime.bigint();
// ...
metrics.observe(Number(process.hrtime.bigint() - t) / 1e6);

Part 2 — Event Loop Lag: the Defining Metric

// Node runs your JavaScript on ONE thread. Any synchronous work delays
// EVERY pending callback — so one slow function makes every concurrent
// request slower, regardless of what those requests are doing.

import { monitorEventLoopDelay } from "node:perf_hooks";
const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();
setInterval(() => {
  metrics.gauge("event_loop_lag_p99_ms", h.percentile(99) / 1e6);
  h.reset();
}, 10_000);

// Interpretation:
//   < 10ms   healthy
//   10–50ms  something is blocking; investigate
//   > 100ms  users feel it on every request
//
// This is the first metric to check when latency rises with normal CPU:
// high lag means blocking, low lag with high latency means waiting on I/O
// (which points at dependencies or the connection pool instead).

// The usual culprits, all of which look innocent:
JSON.parse(hugeString);              // synchronous, O(size), no yield point
crypto.pbkdf2Sync(...);              // sync crypto — use the async form
fs.readFileSync(path);               // fine at startup, never per request
zlib.gzipSync(buffer);               // same
array.sort()                         // on a very large array
/(a+)+$/.test(userInput);            // ReDoS — can block for minutes
for (const x of millionItems) { ... } // a big synchronous loop

// Yielding inside unavoidable long loops keeps the process responsive:
for (let i = 0; i < items.length; i++) {
  process(items[i]);
  if (i % 1000 === 0) await new Promise((r) => setImmediate(r));  // let I/O run
}
// setImmediate yields to the loop's check phase, so pending I/O callbacks
// get their turn. This makes the total slower but keeps the service alive —
// usually the right trade for a request-serving process.
Throughput and latency are different goals and often conflict. Batching database writes raises throughput while adding latency to each individual write. Yielding to the event loop lowers throughput for one job while protecting latency for everyone else. Decide which one the workload actually needs before optimizing, because a change that improves one usually costs the other — and "faster" without saying which is how teams optimize in the wrong direction.

Part 3 — CPU Profiling and Flame Graphs

// Capture a profile:
node --cpu-prof --cpu-prof-dir=./prof server.js    # writes on exit
// or in production, on demand, without a restart:
//   node --inspect  →  chrome://inspect  →  Performance → Record
// or programmatically, so you can trigger it from an endpoint:
import inspector from "node:inspector/promises";
const session = new inspector.Session();
session.connect();
await session.post("Profiler.enable");
await session.post("Profiler.start");
// ... under load ...
const { profile } = await session.post("Profiler.stop");

// READING A FLAME GRAPH — the skill that matters more than the tooling:
//   • x-axis is NOT time; it is aggregated samples, sorted alphabetically
//   • WIDTH = total time in that function and everything it called
//   • height = stack depth, not cost — a tall narrow tower is cheap
//   • look for WIDE PLATEAUS: a wide frame with no wide children is where
//     time is actually spent (self time). That is your target.
//   • wide frames deep in library code usually mean YOUR code is calling
//     them too often, not that the library is slow

// Common shapes and what they mean:
//   a wide JSON.stringify        → serializing too much; trim the payload
//   wide GC frames               → allocation pressure, not a GC bug
//   wide regex frames            → catastrophic backtracking
//   wide crypto frames           → sync crypto on the request path
//   many thin frames, no plateau → the cost is I/O, not CPU. Stop profiling
//                                  CPU and look at traces and pool metrics.

// Benchmark honestly when comparing implementations:
import { Bench } from "tinybench";
const bench = new Bench({ time: 1000 });
bench.add("map+filter", () => items.map(f).filter(g));
bench.add("single reduce", () => items.reduce(h, []));
await bench.run();
// Microbenchmarks lie readily: V8 can optimize away work whose result is
// unused, and a tight loop over the same data is cache-warm in a way
// production never is. Trust an end-to-end measurement over a microbench
// whenever they disagree.

Part 4 — Memory Leaks

// A leak is memory still REACHABLE that will never be used again — so the
// garbage collector correctly refuses to free it. The signature is a heap
// floor that rises across GC cycles rather than returning to a baseline.

// The four classic Node leaks:
// 1. AN UNBOUNDED CACHE — the most common by far.
const cache = new Map();
cache.set(key, value);                     // ❌ nothing ever removes entries
// Fix: an LRU with a size cap, or a TTL. "It is just a small object" times
// millions of distinct keys is a heap.

// 2. LISTENERS ADDED PER REQUEST TO A LONG-LIVED EMITTER:
app.use((req, res, next) => {
  bus.on("update", () => res.write("..."));   // ❌ never removed
  next();
});
// Every request adds a listener that keeps req/res alive forever. Node's
// "possible EventEmitter memory leak detected" warning at 11 listeners is
// pointing at exactly this. Fix: remove on res.on("close"), or use `once`.

// 3. TIMERS AND INTERVALS THAT ARE NEVER CLEARED — an interval keeps its
//    closure (and everything it captures) alive for the process lifetime.

// 4. CLOSURES CAPTURING MORE THAN INTENDED:
function makeHandler(bigBuffer) {
  const id = bigBuffer.id;                 // only `id` is needed
  return () => console.log(id);            // ✅ captures just id
  // return () => console.log(bigBuffer.id);  ❌ retains the whole buffer
}

// FINDING ONE — compare heap snapshots, do not guess:
//   1. node --inspect, open DevTools → Memory
//   2. take a snapshot at steady state
//   3. apply load, force GC, take a second snapshot
//   4. use "Comparison" view sorted by size delta
//   5. select a suspicious object → RETAINERS pane shows WHAT KEEPS IT
//      ALIVE. That retainer chain is the answer; everything else is noise.
// Programmatic capture for production:
import v8 from "node:v8";
v8.writeHeapSnapshot(`/tmp/heap-${Date.now()}.heapsnapshot`);
// Note this pauses the process and writes a file the size of your heap —
// safe on one instance taken out of rotation, disruptive on all of them.

// Not every rise is a leak: V8 grows the heap lazily and does not return
// memory to the OS eagerly. Judge by the floor AFTER GC over hours, not by
// RSS over minutes.

Part 5 — Async Patterns That Cost Real Time

// SERIAL AWAITS IN A LOOP — the most common accidental slowdown:
for (const id of ids) {
  results.push(await fetchUser(id));       // ❌ 100 ids × 50ms = 5 SECONDS
}
const results = await Promise.all(ids.map(fetchUser));   // ✅ ~50ms
// But unbounded parallelism is its own failure: 10,000 concurrent requests
// exhausts sockets, the connection pool, and upstream rate limits. Bound it:
import pLimit from "p-limit";
const limit = pLimit(10);
const results = await Promise.all(ids.map((id) => limit(() => fetchUser(id))));
// Concurrency is a resource. Unbounded is not "fast", it is "unbounded".

// INDEPENDENT AWAITS RUN SEQUENTIALLY FOR NO REASON:
const user = await getUser(id);            // 50ms
const orders = await getOrders(id);        // 50ms → 100ms total
const [user, orders] = await Promise.all([getUser(id), getOrders(id)]);  // 50ms
// Only serialize when the second call genuinely needs the first's result.

// Promise.all vs allSettled — a correctness choice, not a style one:
//   all        rejects on the FIRST failure; the others still run but their
//              results are discarded. Right when you need everything.
//   allSettled always resolves with per-item status. Right when partial
//              results are useful — the graceful degradation pattern.

// N+1 AT THE APPLICATION LAYER — same shape as the database N+1:
const enriched = await Promise.all(orders.map(async (o) => ({
  ...o, user: await getUser(o.userId),          // ❌ one call per order
})));
const users = await getUsersByIds([...new Set(orders.map((o) => o.userId))]);
// ✅ one batched call, then a Map lookup — the DataLoader pattern.

// STREAM INSTEAD OF BUFFERING for large payloads: memory stays constant and
// time-to-first-byte drops from "after everything" to milliseconds. See the
// streams lesson — it is a performance technique as much as a memory one.

Part 6 — When the Answer Is Not Micro-Optimization

// Ranked by typical payoff, largest first. Note that the first four are not
// code changes at all:
//
// 1. DO LESS WORK. Cache the result. Do not compute what nobody reads.
//    Paginate. Return fewer fields. The fastest code is code not run.
// 2. DO IT LATER. Move non-critical work off the request path into a queue:
//    emails, thumbnails, analytics, webhooks. The user waits for the write,
//    not for everything downstream of it.
// 3. DO IT CLOSER. A CDN, an HTTP cache, or a read replica removes the
//    request from your service entirely.
// 4. FIX THE DATABASE. Missing indexes, N+1 queries, and unbounded result
//    sets dominate real-world latency far more often than JavaScript does.
// 5. SCALE OUT. More instances — cheap, if the service is stateless.
// 6. OPTIMIZE THE CODE. Real, but usually the smallest lever, and the one
//    people reach for first.
//
// Node-specific escape hatches when CPU genuinely is the bottleneck:
//   • WORKER THREADS for CPU-bound work (image processing, compression,
//     large parses) — keeps the main loop free. See the scaling lesson.
//   • CLUSTER / multiple instances to use all cores.
//   • A native addon or a different runtime for a genuinely hot kernel —
//     rare, and worth reaching for only with a profile that justifies it.

// Cheap wins that are usually worth taking:
app.use(compression());                    // gzip/brotli responses
res.set("cache-control", "public, max-age=300");
// Keep-alive on outbound HTTP (undici pools by default) avoids paying a TCP
// handshake per upstream call.
// Choose a faster JSON serializer only after proving serialization is hot —
// fast-json-stringify is a real win for large fixed-schema payloads and
// pure overhead for small ad-hoc ones.

Interview Questions

Beginner: Why does one slow synchronous function affect every request?

Because every request in a Node process shares one JavaScript thread, and a synchronous function holds that thread until it finishes.

Node's concurrency model works because request handlers normally run for tiny slices of time — parse the input, start a database query, return — and spend the rest waiting, during which the thread serves other requests. That only holds if every slice is short.

A synchronous function that takes 200ms — parsing a very large JSON payload, a regular expression with catastrophic backtracking, a readFileSync, a nested loop over a large array, a synchronous crypto call — occupies the thread for all 200ms. During that time nothing else can run: other requests' callbacks wait, responses that are ready cannot be sent, timers fire late, and health checks go unanswered. Every one of the hundreds of connections the process is serving sees an extra 200ms of latency, not just the one that caused it.

That is the key difference from a thread-per-request server, where a slow request slows only itself. In Node, one slow request slows everyone, and under load it compounds: requests queue behind the blocked thread, latency climbs, and health checks can time out, causing the orchestrator to restart a process that was merely busy.

The signal to watch is event-loop delay. The fixes are to make the work asynchronous, split it into chunks that yield between them, move it to a worker thread, or — often best — bound it, since an unbounded input size is usually what turns a fast function into a slow one.

Beginner: What is wrong with for (const id of ids) await fetch(id)?

It runs the requests strictly one after another, even though they are independent. Each iteration waits for the previous request to complete before starting the next, so the total time is the sum of every request's latency.

Twenty requests at 100ms each take two seconds. The thread is not blocked during that time — other requests are still served — but this particular request's latency is twenty times what it needs to be, and the user waits for all of it.

When the requests are independent, start them together and wait for all of them:

  const results = await Promise.all(ids.map(id => fetch(id)));   // ~100ms, not 2s

That takes roughly as long as the slowest single request.

But unbounded parallelism has its own problem on a server, so the complete answer is bounded concurrency. If ids can hold thousands of entries, firing them all at once can exhaust sockets or a connection pool, trip a downstream rate limit, and — multiplied by concurrent incoming requests — overwhelm the dependency. Use a concurrency limit such as p-limit, with a size chosen from what the downstream can handle.

There are legitimate reasons to keep a sequential loop: each step depends on the previous one's result, the order of side effects matters, or a downstream API demands strict serialisation. In those cases the loop is correct — and worth a comment saying so, because it looks like a mistake to the next reader. It is also worth asking whether the work can be one request instead of many: a batch endpoint beats both forms.

Mid: How do you read a flame graph?

A flame graph visualises where a program spends its CPU time, built from many sampled stack traces.

The x-axis is not time. This is the most common misreading. Stacks are sorted alphabetically and merged, and a frame's width represents the proportion of samples in which that function was on the stack. A wide frame means the function was involved in a large share of CPU time; its horizontal position means nothing.

The y-axis is stack depth. Each frame sits on top of the function that called it, so the bottom is the entry point and each tower is a call chain.

The skill is distinguishing total time from self time. A frame's full width is time spent in it and everything it called. The part of a frame with nothing stacked on top of it is self time — time spent executing that function's own code. The most useful places to look are therefore wide plateaus at the top of towers: functions with large self time, which is where CPU is actually being burned.

A wide frame low in the stack is usually just a caller of many things and is not itself the problem; follow its tower upward to find what is genuinely expensive.

To produce one for Node, run with --cpu-prof and open the profile in Chrome DevTools, or use tools such as 0x or Clinic Flame. Profile under realistic load, since a profile of an idle server shows nothing useful, and look for your own code as well as unexpected library hotspots — JSON serialisation, logging and regular expressions are frequent surprises.

Mid: How do you distinguish a memory leak from normal heap growth?

By looking at the baseline after garbage collection over time, not at the heap size at any single moment.

A healthy Node process has a sawtooth heap pattern: memory rises as objects are allocated, then drops sharply when the garbage collector runs. It may also grow for a while after startup as caches warm, code is compiled and pools fill, then level off. Growth alone is not a leak; V8 deliberately lets the heap grow before collecting, because collecting less often is cheaper.

A leak shows up as a rising floor: the low points after each collection climb steadily and never level off. Objects are being retained that should have become unreachable, so each cycle frees a little less, until the process hits its heap limit and crashes, or is killed by the container's memory limit.

To confirm and find it:

Monitor heap-used after GC over hours, under steady load, and look at the trend of the troughs. A plateau is fine; a line trending upwards is a leak.

Take heap snapshots at intervals — through the inspector, --heapsnapshot-signal, or v8.writeHeapSnapshot() — and compare them. The object types whose counts keep growing between snapshots are the suspects.

Follow the retainer path for those objects: it shows exactly what reference is keeping them alive.

The usual culprits in Node are listeners added per request and never removed, unbounded in-memory caches or maps keyed by user or request, closures capturing request objects in long-lived structures, timers never cleared, and global arrays that only grow. Snapshots are expensive and pause the process, so take them carefully in production.

Senior: An endpoint has p50 of 40ms and p99 of 3s. Where do you look?

The gap itself is the clue: the typical path is fast, so the code is not uniformly slow — something intermittent affects a minority of requests, and that pattern points at queueing or variance rather than algorithmic cost. I would work through candidates in order of likelihood. Connection pool saturation produces exactly this shape, since most requests get a connection immediately while a few wait behind others; pool wait time as a metric confirms or eliminates it quickly. Event loop lag is next: periodic blocking work, garbage collection pauses, or a synchronous operation on an uncommon path delays whatever happens to be pending. Then data-dependent cost — a query that is fast for typical users and slow for the one with fifty thousand orders, or a missing index that only matters past a certain row count, which is why breaking latency down by user or tenant is often revealing. Cache misses are another: p50 is a hit and p99 is the miss path, which also means a cache stampede can be hiding here. External dependency variance and retries contribute similarly. Diagnostically, I would sample traces from the slow tail specifically rather than uniformly, since random sampling mostly captures fast requests; tail-based sampling exists for this. I would also check whether the p99 is concentrated in particular instances, which would suggest one unhealthy pod rather than a systemic issue. The general principle is that a wide p50-to-p99 gap is a variance problem, and variance usually means waiting rather than computing.

Senior: A service needs to handle 10× traffic. How do you approach it?

First establish what breaks first rather than optimizing broadly, because scaling is bounded by the earliest constraint and everything else is wasted effort until that one moves. A load test at increasing multiples reveals the actual limit, and it is rarely the thing people expect — usually the database connection pool, the database itself, or a shared dependency rather than Node's CPU. Then I would work through the ladder in payoff order. Do less work: caching at the HTTP layer and in Redis, pagination caps, trimming response payloads. Do it later: move non-critical work off the request path into a queue, since a 10× increase in requests need not mean 10× synchronous work. Do it closer: CDN for anything cacheable, read replicas for read-heavy queries. Fix the database, which at 10× is where most services actually fail — index review, N+1 elimination, and connection pooling through PgBouncer, since naive pool sizing multiplied across ten times the instances will exceed the server's connection limit and turn a capacity problem into an outage. Only then scale out horizontally, which requires the service to be genuinely stateless, and confirm autoscaling responds faster than traffic ramps. Throughout, I would protect the system from the load it cannot serve: rate limiting, bounded concurrency to upstreams, circuit breakers, and load shedding so that exceeding capacity degrades gracefully instead of collapsing. That last part is what separates a system that handles 10× from one that merely does not fall over at 9×.

🏋️ Graded Exercises

1 (easy): Rewrite to run concurrently and explain the latency change.
Solution 
// Before — sequential, latency is the SUM:
const user = await getUser(id);        // 50ms
const orders = await getOrders(id);    // 50ms
const prefs = await getPrefs(id);      // 50ms   → 150ms total

// After — concurrent, latency is the MAX:
const [user, orders, prefs] = await Promise.all([
  getUser(id), getOrders(id), getPrefs(id),
]);                                    // → ~50ms

// Valid only because the three calls are independent. If getOrders needed
// user.accountId, that pair must stay sequential — you can still overlap
// the independent part:
const [user, prefs] = await Promise.all([getUser(id), getPrefs(id)]);
const orders = await getOrders(user.accountId);
2 (easy): Why is Promise.all(ids.map(fetchUser)) risky with 10,000 ids?
Solution 
// It starts 10,000 concurrent operations at once. Consequences:
//   • socket/file-descriptor exhaustion (EMFILE)
//   • the database connection pool is overwhelmed; unrelated requests queue
//   • upstream rate limits trigger, so most calls fail and retry storms form
//   • peak memory holds 10,000 in-flight promises and their responses
import pLimit from "p-limit";
const limit = pLimit(20);
const users = await Promise.all(ids.map((id) => limit(() => fetchUser(id))));
// Bounded concurrency is nearly as fast — throughput saturates well before
// 10,000 — with none of the failure modes. Tune the limit to the slowest
// dependency's capacity, not to the number of items.
3 (medium): Add event loop lag monitoring that alerts when the process is blocked.
Solution 
import { monitorEventLoopDelay } from "node:perf_hooks";

const histogram = monitorEventLoopDelay({ resolution: 10 });
histogram.enable();

setInterval(() => {
  const p99Ms = histogram.percentile(99) / 1e6;      // nanoseconds → ms
  const meanMs = histogram.mean / 1e6;
  metrics.gauge("event_loop_lag_p99_ms", p99Ms);
  metrics.gauge("event_loop_lag_mean_ms", meanMs);

  if (p99Ms > 100) {
    log.warn({ p99Ms, meanMs }, "event loop blocked");
  }
  histogram.reset();                                  // per-window statistics
}, 10_000).unref();      // ← don't keep the process alive for metrics

// p99 rather than mean: blocking is bursty, and a 500ms stall once a minute
// averages away to nothing while being exactly what users feel.
// The alert threshold should be an SLO decision — 100ms of added latency on
// every concurrent request is already user-visible.
4 (medium): Identify and fix the leak.
Solution 
// Leaking version:
const emitter = new EventEmitter();          // module scope: lives forever
app.get("/stream", (req, res) => {
  emitter.on("tick", () => res.write("data\n"));    // ❌ never removed
});
// Each request adds a listener holding a closure over `res`, which retains
// the request, its socket, and its buffers — for the process lifetime.
// Node's "possible EventEmitter memory leak detected (11 listeners)" warning
// is pointing straight at this.

app.get("/stream", (req, res) => {
  const onTick = () => res.write("data\n");
  emitter.on("tick", onTick);
  res.on("close", () => emitter.off("tick", onTick));   // ✅ always cleaned up
});
// res.on("close") fires on both normal completion and client disconnect, so
// it covers every exit path — unlike "finish", which only fires on success.
5 (hard): A CSV export endpoint blocks the server for 8 seconds. Redesign it.
Solution 
// Before — three full materializations plus synchronous CPU work:
const rows = await db.query("SELECT * FROM orders");   // all rows in memory
const csv = rows.map(toCsvLine).join("\n");            // + a second copy
res.send(csv);                                          // + a third

// Two distinct problems: memory scales with rows × concurrency, and the
// map/join is synchronous CPU work that blocks EVERY other request.

// After — stream end to end, constant memory, non-blocking:
import { pipeline } from "node:stream/promises";
import { Transform } from "node:stream";

app.get("/export", async (req, res) => {
  res.writeHead(200, {
    "content-type": "text/csv",
    "content-disposition": 'attachment; filename="orders.csv"',
  });

  const cursor = db.queryStream("SELECT * FROM orders");   // DB cursor
  const toCsv = new Transform({
    objectMode: true,
    transform(row, _enc, cb) { cb(null, toCsvLine(row) + "\n"); },
  });

  try {
    await pipeline(cursor, toCsv, res, { signal: AbortSignal.timeout(300_000) });
  } catch (err) {
    if (err.code !== "ERR_STREAM_PREMATURE_CLOSE") throw err;   // client left
  }
});

// Why this fixes both: the cursor holds a page of rows rather than all of
// them, the transform processes one row per tick so the loop stays
// responsive, and backpressure paces database reads to the client's download
// speed. Time-to-first-byte drops from 8s to milliseconds.
//
// If per-row work were genuinely CPU-heavy, the next step is a worker thread
// or an offline job writing to object storage and emailing a link — at which
// point the endpoint returns 202 with a job id. Streaming is the right answer
// when the work is I/O-shaped; a queue is the right answer when it is not.
6 (hard): Memory grows steadily and pods restart on OOM every few hours. Investigate.
Solution 
// 1. CONFIRM IT IS A LEAK, not lazy heap growth. V8 grows on demand and
//    returns memory to the OS reluctantly, so rising RSS alone proves
//    nothing. Track heapUsed AFTER GC over hours: a leak shows a rising
//    FLOOR, not a rising peak.
setInterval(() => {
  const { heapUsed, heapTotal, rss, external } = process.memoryUsage();
  log.info({ heapUsed, heapTotal, rss, external }, "memory");
}, 60_000).unref();
//    Also check `external` and ArrayBuffers — Buffer leaks live outside the
//    JS heap and are invisible in heapUsed, which misleads people for hours.

// 2. CORRELATE with deploys and traffic. If it started with a release,
//    the diff is the fastest path to the answer. If growth tracks request
//    volume, it is per-request retention; if it grows on idle, it is a
//    timer or subscription.

// 3. SNAPSHOT AND COMPARE — the definitive step:
//    • take one at steady state, apply load, force GC, take another
//    • DevTools → Memory → Comparison, sort by size delta
//    • select the growing constructor, read the RETAINERS pane
//    The retainer chain names the container holding the memory: a Map at
//    module scope, an emitter's listener array, a closure in a pending
//    promise. That chain IS the bug; everything else is inference.
//    In production, do this on ONE instance removed from rotation —
//    writeHeapSnapshot pauses the process and writes a heap-sized file.

// 4. CHECK THE USUAL SUSPECTS while snapshots run: unbounded Map/Set caches,
//    per-request listeners on long-lived emitters, uncleared intervals,
//    accumulating arrays of logs/metrics, promises that never settle (their
//    closures are retained forever), and closures capturing large buffers.

// 5. MITIGATE while fixing: --max-old-space-size to fail fast and predictably
//    rather than being OOM-killed mid-request, and a memory-based alert so

🎯 Key Takeaways

  • Measure before optimizing — Amdahl's law bounds any improvement by the fraction of time you are actually targeting.
  • Event loop lag is the defining Node metric: high lag means blocking, low lag with high latency means waiting on I/O.
  • Any synchronous work on the request path degrades every concurrent request, not just its own.
  • In flame graphs, look for wide plateaus — width is cost, height is only stack depth.
  • Serial awaits over independent work multiply latency; Promise.all with bounded concurrency fixes it without exhausting resources.
  • Unbounded caches and per-request listeners on shared emitters are the two most common Node leaks.
  • Judge leaks by the post-GC heap floor over hours, and locate them through snapshot comparison and retainer chains.
  • Buffer leaks live outside the JS heap — watch external as well as heapUsed.
  • Doing less work, deferring work, and fixing the database almost always beat optimizing JavaScript.
  • Throughput and latency trade against each other — decide which the workload needs before optimizing.
  • One slow synchronous function adds latency to every in-flight request.
  • Unbounded input size is what usually makes a fast function slow.
  • Sequential awaits cost the sum of latencies; parallel costs the maximum.
  • Bound concurrency on the server.
  • A flame graph's width is share of samples, not time.
  • Wide frames at the top of towers are where CPU burns.
  • A leak is a rising post-GC floor, not a large heap.
  • Compare heap snapshots and follow the retainer path.
