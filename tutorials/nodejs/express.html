Express Fundamentals Building APIs

What you'll master: Express as a thin, explicit layer over node:http — the app object, routing with parameters, the request/response helpers, Router for structure, and the Express 5 changes that matter (async errors are finally handled). You'll be able to say precisely which parts are Express and which are still Node underneath. Prerequisites: HTTP Without Frameworks.

Part 1 — What Express Actually Is

import express from "express";
const app = express();

app.get("/health", (req, res) => res.json({ ok: true }));
app.listen(3000);

// `app` is a FUNCTION with the exact signature (req, res) that createServer
// wants. This is the whole trick:
import { createServer } from "node:http";
createServer(app).listen(3000);        // ← app.listen() is shorthand for this
// You need the long form for HTTPS, HTTP/2, or attaching WebSockets to the
// same server — so it is worth knowing it is not magic.

// req and res are the SAME IncomingMessage/ServerResponse from the previous
// lesson, with extra methods mixed in (res.json, res.status, req.params).
// Everything you learned still applies: res is a writable stream, headers
// still lock after the first byte, bodies still arrive in chunks.
//
// So what does Express add over the 200 lines we wrote by hand?
//   1. A ROUTER: path patterns with parameters, method matching, precedence.
//   2. MIDDLEWARE: a composable request pipeline (next lesson).
//   3. ERGONOMICS: res.json, res.status, res.redirect, req.params/query.
//   4. An ERROR-HANDLING convention.
// That is it. It adds no I/O model, no concurrency model, no performance.

Part 2 — Routing & Path Parameters

app.get("/orders", listOrders);                  // method + exact path
app.post("/orders", createOrder);
app.get("/orders/:id", (req, res) => {           // : marks a PARAMETER
  req.params.id;                                 // always a STRING — "42", not 42
});
app.get("/files/:dir/:name", ...);               // multiple params
app.all("/admin/*splat", requireAdmin);          // wildcard (Express 5 syntax)

// ROUTES ARE MATCHED IN REGISTRATION ORDER — first match wins. This is the
// single most common source of "my route never runs":
app.get("/orders/:id", getOrder);                // ← matches "/orders/new" first!
app.get("/orders/new", newOrderForm);            // ← unreachable, always shadowed
// Fix: register the SPECIFIC route before the parametric one. There is no
// specificity ranking like CSS — it is a plain ordered list, top to bottom.

// Params are strings, and validating them is your job:
app.get("/orders/:id", (req, res) => {
  const id = Number(req.params.id);
  if (!Number.isInteger(id) || id <= 0) {
    return res.status(400).json({ error: "id must be a positive integer" });
  }
  // Passing req.params.id straight into a query is how injection happens and
  // how you end up doing a full table scan on a string comparison.
});

// Express 5 note: path patterns changed. "*" alone is no longer valid —
// wildcards must be NAMED ("*splat"), and the old regex-ish forms were
// removed. Code copied from Express 4 tutorials will throw at startup.

Part 3 — The Response Helpers

res.json({ id: 1 });              // sets content-type + content-length, serializes
res.status(201).json(order);      // chainable — status returns res
res.send("hello");                // guesses content-type from the argument type
res.sendStatus(204);              // status + its text as the body
res.redirect(302, "/login");
res.set("cache-control", "no-store");
res.type("text/csv");

// res.json is res.end(JSON.stringify(x)) plus correct headers — including
// Content-Length via Buffer.byteLength, the bug we hit by hand last lesson.
// Prefer it over res.send for APIs: res.send's type guessing means a handler
// returning a string sends text/html, and one returning an object sends JSON,
// so a refactor silently changes the content type.

// res is STILL a stream, so everything from the streams lesson works:
await pipeline(createReadStream("export.csv"), res);
// res.sendFile(path) handles ranges, ETags, and content-type for static files
// and should be preferred when you are literally serving a file from disk.

// The rule that survives from raw Node: ONE response per request. Express
// throws the same ERR_HTTP_HEADERS_SENT, so `return res.json(...)` remains
// the habit that prevents it.

Part 4 — Router: Structure Before It Hurts

// routes/orders.js
import { Router } from "express";
const router = Router();

router.get("/", listOrders);            // paths are RELATIVE to the mount point
router.post("/", createOrder);
router.get("/:id", getOrder);
export default router;

// app.js
app.use("/api/orders", ordersRouter);   // → /api/orders, /api/orders/:id

// A Router is a mini-app: same routing API, mountable, with its own middleware.
// Two properties make it worth using early:
//   • The mount path lives in ONE place, so versioning (/api/v2/orders) or
//     renaming a resource is a one-line change.
//   • Middleware can be scoped to a subtree: router.use(requireAuth) protects
//     every route in the file, and you cannot forget it on a new route —
//     which is exactly how auth gaps get introduced in flat route lists.

// Mount ORDER matters here too, and mount paths are PREFIXES:
app.use("/api", apiRouter);
app.use("/api/admin", adminRouter);     // ← may be shadowed if apiRouter
                                        //   handles /admin/* and responds
Express 5 changed async error handling — this is the upgrade that matters. In Express 4, a rejected promise inside a handler was not caught: the request hung until it timed out, and the process logged an unhandled rejection. Everyone worked around it with express-async-errors or a catchAsync wrapper. In Express 5, a returned promise that rejects is forwarded to your error middleware automatically. If you are reading an older tutorial that insists you must wrap every async handler, check your major version before copying the workaround.

Part 5 — Errors: the Four-Argument Handler

// Express identifies error middleware by ARITY — four parameters, not three.
// Registered LAST, after all routes:
app.use((err, req, res, next) => {
  const status = err.status ?? 500;
  if (status >= 500) req.log?.error({ err }, "request failed");
  res.status(status).json({
    error: status >= 500 ? "Internal error" : err.message,
  });
});
// Note what leaks and what doesn't: a 4xx message is written by you and safe
// to show; a 500 message may contain a stack, a query, or a connection string,
// so it is replaced with a generic string and logged server-side instead.

// Reaching it from a handler:
app.get("/orders/:id", async (req, res) => {
  const order = await db.find(req.params.id);
  if (!order) {
    const err = new Error("Order not found");
    err.status = 404;
    throw err;                    // Express 5: forwarded automatically
    // Express 4 equivalent: next(err)
  }
  res.json(order);
});

// A 404 for UNMATCHED routes is not an error — it is "no route matched", so
// it is a normal middleware registered after your routes but before the
// error handler:
app.use((req, res) => res.status(404).json({ error: "Not found" }));

// The ordering contract for the whole file, and it is not negotiable:
//   1. app-wide middleware (parsers, logging)
//   2. routes / routers
//   3. 404 handler
//   4. error handler (4-arg)
// Anything registered after the error handler is unreachable.

Part 6 — A Complete, Honest Skeleton

import express from "express";
import ordersRouter from "./routes/orders.js";

const app = express();

app.use(express.json({ limit: "100kb" }));   // ← the body cap from last lesson
app.use(express.urlencoded({ extended: true }));

app.get("/health", (req, res) => res.json({ ok: true }));
app.use("/api/orders", ordersRouter);

app.use((req, res) => res.status(404).json({ error: "Not found" }));
app.use((err, req, res, next) => {
  const status = err.status ?? 500;
  res.status(status).json({ error: status >= 500 ? "Internal error" : err.message });
});

const server = app.listen(3000);

// Graceful shutdown is UNCHANGED from raw Node — Express does not do it for
// you, and `server` here is a plain http.Server:
process.on("SIGTERM", () => {
  server.close(() => process.exit(0));
  server.closeIdleConnections();
  setTimeout(() => process.exit(1), 10_000).unref();
});

// express.json() is a body parser with the size cap built in. Its default is
// 100kb — a deliberate default, not an accident. Raising it to "50mb" because
// one endpoint needs large uploads applies that limit to EVERY endpoint;
// scope it per-route instead: app.post("/import", express.json({ limit: "50mb" }), h)

Interview Questions

Beginner: What is the Express app object, really?

A function with the (req, res) signature that http.createServer accepts — which is why createServer(app) works and app.listen() is just shorthand for it. Knowing this matters when you need HTTPS, HTTP/2, or to attach a WebSocket server to the same HTTP server, since all of those require constructing the server yourself and passing app in.

Beginner: Why does /orders/new return the wrong handler when /orders/:id is registered above it?

Express matches routes in registration order and the first match wins — there is no specificity ranking. /orders/:id matches /orders/new with id === "new", so the later, more specific route is unreachable. Register literal paths before parametric ones. The same rule governs mounted routers, whose mount paths act as prefixes.

Mid: How does Express distinguish error middleware from ordinary middleware?

By function arity: four declared parameters (err, req, res, next) marks it as an error handler. This is a genuine footgun, because dropping the unused next to satisfy a linter turns it into ordinary middleware that silently never runs on errors — no warning, errors just fall through to Express's default HTML handler. Error middleware must also be registered last, after routes and the 404 handler, since registration order is execution order.

Mid: What changed about async errors in Express 5, and what should you stop doing?

In Express 4 a handler returning a rejected promise was not caught: the rejection surfaced as an unhandled rejection and the client hung until timeout, because nothing ever responded. That drove the near-universal catchAsync wrapper and the express-async-errors package. Express 5 forwards rejected promises from handlers to error middleware automatically, so those wrappers become redundant. The practical advice: check your major version before copying async-handling patterns from tutorials, since most content online still assumes v4.

Senior: A team argues Express is "too slow" and wants to migrate to Fastify. How do you evaluate that?

First establish whether framework overhead is actually in the critical path. Express adds routing and a middleware chain over node:http; in most services that is single-digit microseconds against database calls, upstream HTTP, and serialization measured in milliseconds. A profile usually shows time in I/O waits, JSON serialization of oversized payloads, N+1 queries, or missing indexes — none of which a framework swap fixes. So the first move is measurement: flame graph under realistic load, and a latency budget attributing time per layer. Fastify is genuinely faster at the routing and serialization layer (schema-based serialization is a real win at high request rates), so if you are serving very high RPS of small JSON responses and have already fixed the application-level costs, it can matter. But weigh migration cost, ecosystem differences, and team familiarity against a benchmark difference that may be invisible behind your p99. The senior answer is not "Express is fine" or "Fastify is faster" — it is insisting the decision come from a profile of this service rather than a benchmark of a hello-world route.

Senior: Design the middleware and router layout for an API with public routes, authenticated user routes, and admin routes. What makes the layout safe rather than merely tidy?

Mount three routers with scoping that makes the insecure case impossible to write by accident: a public router with no auth, a user router whose first line is router.use(requireAuth), and an admin router mounted under it with router.use(requireAdmin). The safety property is that protection attaches to the subtree, not to individual routes, so a developer adding a new endpoint to the admin file inherits authorization without remembering anything. Flat route lists with per-route middleware fail exactly here: the code looks fine, the new route just quietly lacks a guard, and nothing tests for a missing guard because the test suite tests what exists. Reinforce it with an integration test that enumerates registered routes and asserts every non-public path rejects an anonymous request — that turns "we remembered" into "the suite fails if we forget". Order still matters: app-wide parsers first, then routers, then 404, then the error handler.

🏋️ Graded Exercises

1 (easy): Build an app with GET /health returning {ok:true} and a JSON 404 for everything else.
Solution 
import express from "express";
const app = express();

app.get("/health", (req, res) => res.json({ ok: true }));
app.use((req, res) => res.status(404).json({ error: "Not found" }));

app.listen(3000);
// The 404 handler is ordinary middleware with no path, registered after all
// routes: if execution reaches it, nothing matched.
2 (easy): Why does this handler never respond, and what is the minimal fix? app.get("/x", (req,res) => { res.status(200); });
Solution 
// res.status() only SETS the status code and returns res for chaining — it
// never ends the response. The client waits until its own timeout.
app.get("/x", (req, res) => { res.status(200).json({ ok: true }); });
// Or res.sendStatus(200) to send the status with its text as the body.
// General rule: exactly one terminal call per request — json/send/end/
// sendFile/redirect. Setting headers or status is not terminal.
3 (medium): Convert these flat routes to a mounted Router with auth applied to the whole subtree: GET /api/orders, POST /api/orders, GET /api/orders/:id.
Solution 
// routes/orders.js
import { Router } from "express";
const router = Router();

router.use(requireAuth);          // applies to every route below, including
                                  // ones added later — that is the point

router.get("/", listOrders);
router.post("/", createOrder);
router.get("/:id", getOrder);
export default router;

// app.js
app.use("/api/orders", ordersRouter);

// Router paths are relative to the mount point, so the resource name appears
// once. Versioning later is a one-line change: app.use("/api/v2/orders", ...)
4 (medium): Write an error handler that returns a safe JSON body, and a route that triggers a 404 through it.
Solution 
app.get("/orders/:id", async (req, res) => {
  const id = Number(req.params.id);
  if (!Number.isInteger(id)) {
    throw Object.assign(new Error("id must be an integer"), { status: 400 });
  }
  const order = await db.find(id);
  if (!order) throw Object.assign(new Error("Order not found"), { status: 404 });
  res.json(order);
});

// LAST in the file:
app.use((err, req, res, next) => {
  const status = err.status ?? 500;
  if (status >= 500) console.error(err);        // detail stays server-side
  res.status(status).json({
    error: status >= 500 ? "Internal error" : err.message,
  });
});
// Throwing works directly in Express 5. On Express 4 these would need
// next(err) instead, since a rejected promise was not forwarded.
5 (hard): One endpoint must accept 50MB uploads; the rest should stay capped at 100KB. Implement it and explain the risk of the obvious approach.
Solution 
app.use(express.json({ limit: "100kb" }));          // global default stays small

app.post("/import",
  express.json({ limit: "50mb" }),                  // scoped to THIS route
  importHandler);

// The obvious approach — raising the global limit to 50mb — makes EVERY
// endpoint a memory-exhaustion target: an attacker picks any route, posts
// 50MB, and repeats across concurrent connections. The blast radius of a
// limit is every route it covers, so the limit belongs at the narrowest
// scope that needs it.
//
// Better still for genuinely large uploads: do not buffer into memory at
// all. Stream to disk or object storage (busboy for multipart) so peak
// memory is a chunk, not the payload — the constant-memory principle from
// the streams lesson.
6 (hard): A route's async handler throws after the response was already sent. Explain what Express does, why the log is confusing, and how to prevent the class of bug.
Solution 
app.get("/x", async (req, res) => {
  res.json(await load());        // responded
  await audit(req);              // throws → forwarded to error middleware
});

// Express calls the error handler, which tries res.status(500).json(...) on
// an already-sent response → ERR_HTTP_HEADERS_SENT. The log now shows a
// headers-sent error, NOT the audit failure that actually happened, so the
// real cause is masked by its own reporting.

// Defensive error handler — always check before writing:
app.use((err, req, res, next) => {
  if (res.headersSent) return next(err);   // delegate to Express's default,
                                           // which destroys the socket
  res.status(err.status ?? 500).json({ error: "Internal error" });
});

// Preventing the class, not the instance: do all fallible work BEFORE
// responding, and treat responding as the last statement in the handler.
// Post-response work that may fail (audit logs, cache warming, analytics)
// belongs on a queue or in an explicitly-caught fire-and-forget block —
// because after the response, there is no longer any way to tell the client
// something went wrong. Deciding that consciously is the actual lesson:
// once bytes are sent, your error handling options are logging and nothing.

🎯 Key Takeaways

  • Express is a router, a middleware pipeline, and response ergonomics over node:http — app is literally a (req, res) function you can pass to createServer.
  • Routes match in registration order with no specificity ranking, so literal paths must be registered before parametric ones.
  • req.params and req.query are always strings and always untrusted — parse and validate at the boundary.
  • res.status() is not terminal; exactly one of json/send/end/redirect/sendFile ends a request.
  • Error middleware is identified by its four-argument arity and must come last — dropping the unused next silently disables it.
  • Express 5 forwards rejected promises to error middleware; the Express 4 catchAsync wrappers are obsolete there.
  • Routers scope middleware to a subtree, which is what makes auth hard to forget on routes added later.
  • Body-size limits belong at the narrowest scope that needs them — a global 50MB limit makes every route a DoS target.
  • 500 messages go to logs, not to clients; 4xx messages you wrote are safe to return.
  • Express changes none of Node's operational concerns: timeouts, keep-alive, and graceful shutdown remain yours to configure.
