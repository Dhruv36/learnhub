Testing Node Services Production Node

What you'll master: what to test and what not to, the built-in node:test runner, integration tests against real databases with containers, the mocking boundary that keeps tests honest, deterministic tests for time and randomness, and why coverage percentage is a poor goal. Prerequisites: Validation & Error Handling, Databases & ORMs.

Part 1 — The Built-In Runner

// Node has a test runner built in since 18 — no Jest, no config, no
// transpilation for plain JS.
import { test, describe, it, before, after, mock } from "node:test";
import assert from "node:assert/strict";       // ← /strict: === not ==

describe("calculateTotal", () => {
  it("sums line items", () => {
    assert.equal(calculateTotal([{ price: 100, qty: 2 }]), 200);
  });

  it("throws on negative quantity", () => {
    assert.throws(() => calculateTotal([{ price: 100, qty: -1 }]),
                  { message: /quantity/ });
  });
});

// Run:  node --test                     (discovers *.test.js)
//       node --test --watch
//       node --test --experimental-test-coverage
//       node --test --test-name-pattern="sums"

// assert/strict matters: plain `assert.equal` uses ==, so it happily
// accepts "200" for 200 — a test that passes while the code returns the
// wrong type. Always import the strict variant.

// When Jest/Vitest still earn their place: rich mocking of ES modules,
// snapshot testing, jsdom for browser-like environments, or an existing
// suite. For a backend service starting today, node:test is enough and
// removes a large dependency from your build.

Part 2 — The Testing Pyramid, Rebalanced

// The classic pyramid says: many unit, some integration, few end-to-end.
// For a typical Node SERVICE the useful shape is closer to a diamond —
// integration tests carry the most value per line, because most bugs in a
// service live in the WIRING (routing, middleware order, SQL, serialization),
// not in isolated pure functions.
//
//   UNIT        — pure logic: pricing, validation rules, parsers, state
//                 machines. Fast, precise, no I/O. Test these exhaustively,
//                 including edge cases, because they are cheap.
//   INTEGRATION — a real HTTP request through real middleware to a real
//                 database. Catches the bugs that actually occur: wrong
//                 status codes, missing auth, broken queries, N+1s.
//   E2E         — a handful of critical user journeys. Slow and flaky;
//                 keep the set small and stable.
//
// The rule that matters more than the shape: TEST BEHAVIOUR, NOT
// IMPLEMENTATION. A test that asserts "the service calls repository.save()"
// breaks when you refactor while telling you nothing about correctness. A
// test that asserts "after POST /orders, GET /orders/:id returns the order"
// survives refactoring and actually verifies the feature.
//
// Consequence worth internalizing: if a test fails every time you refactor
// without changing behaviour, the test is coupled to implementation and is
// a liability, not an asset.

Part 3 — Integration Tests Against a Real Database

import { test, before, after, beforeEach } from "node:test";
import request from "supertest";
import { PostgreSqlContainer } from "@testcontainers/postgresql";

let container, app;

before(async () => {
  container = await new PostgreSqlContainer("postgres:16").start();
  process.env.DATABASE_URL = container.getConnectionUri();
  await runMigrations();                  // the SAME migrations as production
  app = await buildApp();                 // build AFTER config is set
}, { timeout: 60_000 });                  // pulling an image is slow once

after(async () => { await container.stop(); });

beforeEach(async () => {
  // Truncate between tests so each starts from a known state. Faster than
  // recreating the schema, and order-independent tests are worth the cost.
  await db.query("TRUNCATE orders, users RESTART IDENTITY CASCADE");
});

test("POST /orders creates an order", async () => {
  const user = await createUser({ email: "a@b.c" });

  const res = await request(app)
    .post("/api/orders")
    .set("authorization", `Bearer ${tokenFor(user)}`)
    .send({ items: [{ sku: "ABC-1", qty: 2 }] })
    .expect(201);

  assert.equal(res.body.items.length, 1);
  assert.match(res.headers.location, /^\/orders\/\d+$/);

  // Verify the SIDE EFFECT, not just the response — a handler can return
  // 201 without persisting anything.
  const { rows } = await db.query("SELECT * FROM orders WHERE id = $1", [res.body.id]);
  assert.equal(rows.length, 1);
});

// Why a real database rather than an in-memory fake or SQLite: the whole
// point of these tests is to exercise real SQL, real constraints, real
// transaction semantics, and real migrations. A fake passes on queries
// Postgres would reject and cannot catch a unique-constraint bug, a JSONB
// operator mistake, or a missing index. Testcontainers gives a real,
// disposable instance per run — the fidelity is the value.
Test the auth boundary systematically, not per route. Write one test that enumerates every registered route and asserts that non-public ones reject an anonymous request. Per-route auth tests only cover routes someone remembered to write a test for — which is exactly the same failure mode as forgetting the middleware. A test driven by the route table fails automatically when someone adds an unprotected endpoint.

Part 4 — Mocking: Where to Draw the Line

// Mock at the EDGES of your system. Do not mock your own internals.
//
//   ✅ mock: third-party HTTP APIs, payment providers, email/SMS senders,
//            the clock, randomness, the filesystem when incidental
//   ❌ avoid: your own repositories, services, and modules — mocking those
//            tests your mocks, and couples the test to structure

import { mock } from "node:test";

test("retries the upstream twice before failing", async () => {
  const fetchMock = mock.fn(async () => new Response("", { status: 503 }));
  const client = new UpstreamClient({ fetch: fetchMock, retries: 2 });

  await assert.rejects(() => client.getRates());
  assert.equal(fetchMock.mock.callCount(), 3);      // initial + 2 retries
});
// Note the dependency is INJECTED. Injection is what makes this testable
// without module-level patching, and it is why constructor/parameter
// injection is worth the small ceremony.

// For HTTP, an interceptor is usually better than a hand-written mock
// because it exercises your real client code including URL building,
// headers, and error handling:
import { MockAgent, setGlobalDispatcher } from "undici";
const agent = new MockAgent();
setGlobalDispatcher(agent);
agent.get("https://api.example.com")
     .intercept({ path: "/rates", method: "GET" })
     .reply(200, { usd: 1.1 });

// CONTRACT RISK, and it is the real limitation of all mocking: your mock
// encodes what you BELIEVE the upstream returns. If the provider changes a
// field, every test still passes and production breaks. Mitigations: record
// real responses to build fixtures, verify against the provider's schema,
// or run contract tests against a sandbox on a schedule. A green suite is
// evidence about your code, never about someone else's service.

Part 5 — Determinism: Time, Randomness, Concurrency

// Non-deterministic tests are worse than no tests: a suite that fails 1% of
// the time trains the team to re-run CI instead of reading failures, and
// then a real regression gets re-run away too.

// TIME — never let a test depend on the real clock:
import { mock } from "node:test";
test("expires after 15 minutes", (t) => {
  t.mock.timers.enable({ apis: ["Date", "setTimeout"], now: new Date("2026-07-31T12:00:00Z") });
  const token = issueToken();
  t.mock.timers.tick(16 * 60 * 1000);          // advance instantly
  assert.equal(isExpired(token), true);
});
// Better still, inject the clock so production code has no hidden global:
//   class TokenService { constructor({ now = () => Date.now() } = {}) {} }
// Tests pass a fake `now`; nothing needs patching at all.

// RANDOMNESS — inject the generator:
const service = new Service({ randomId: () => "fixed-id-1" });

// SLEEPS — never sleep to wait for something:
await new Promise((r) => setTimeout(r, 1000));    // ❌ slow AND still racy
await waitFor(() => queue.length === 0, { timeout: 5000 });   // ✅ poll a condition
// A fixed sleep is a bet that the machine is fast enough. CI machines under
// load lose that bet, which is the single most common source of flakiness.

// TEST ISOLATION — shared mutable state between tests creates
// order-dependent failures that only appear when someone adds a test:
//   • truncate the database between tests
//   • reset module-level caches and singletons
//   • use a unique schema/database per worker if running in parallel
//   • never rely on tests running in a particular order
// If a test passes alone but fails in the suite, you have shared state.

Part 6 — Coverage and What It Does Not Tell You

node --test --experimental-test-coverage

// Coverage measures which lines EXECUTED, not whether behaviour is correct.
// This test gives 100% coverage of the function and asserts nothing useful:
test("calculateTotal", () => {
  calculateTotal([{ price: 100, qty: 2 }]);      // no assertion at all
});

// So a coverage TARGET is a poor goal — it is easily satisfied by tests that
// execute code without checking it, and chasing the last few percent drives
// tests for trivial getters and error paths that cannot occur. What coverage
// is genuinely good for is finding what you FORGOT: an uncovered branch is
// a question worth asking, and the report is best read as a map of blind
// spots rather than a score.

// Better signals of suite quality:
//   • Does it catch real regressions? (track escaped bugs, not percentages)
//   • Would a deliberate bug fail a test? (mutation testing measures this
//     directly — Stryker mutates your code and reports which mutations your
//     tests failed to detect)
//   • Are failures actionable — does the message say what broke?
//   • Is it fast enough that people run it locally? A suite nobody runs
//     before pushing has already lost most of its value.

// What to prioritize when time is limited, in order:
//   1. money paths and auth boundaries — highest cost of failure
//   2. bugs you have already shipped once — a regression test each
//   3. complex branching logic — where reasoning fails
//   4. the integration seams — routing, serialization, SQL
// What to skip: framework behaviour, trivial getters, and third-party
// library internals. Testing that Express routes correctly tests Express.

Interview Questions

Beginner: What is the difference between a unit test and an integration test here?

A unit test exercises one function or module in isolation, with its collaborators replaced by fakes. It is fast — milliseconds — precise about where a failure is, and cheap to write in large numbers. A pricing function, a validator or a date calculation is ideal unit-test territory.

An integration test exercises several real components working together through their real boundaries. For a Node service, the most valuable version sends a real HTTP request to the application, which passes through the actual middleware, routing, validation and database layer, and asserts on the response and on the resulting database state.

The trade-off is confidence against cost. Unit tests are fast but can all pass while the system is broken, because the bugs live in the seams: a middleware registered in the wrong order, a query that works against a mock but fails against the real schema, a serialisation mismatch between layers. Integration tests catch those, at the cost of speed and setup.

For HTTP services I weight the suite towards integration tests at the API boundary. They test behaviour the way clients experience it, and they survive refactoring — you can restructure internals completely without rewriting a single test, because the contract did not change. Unit tests then cover genuinely complex pure logic where exhaustive cases are cheap to enumerate.

Tools such as Supertest make the integration style practical by calling the app's handler directly without binding a real port, so these tests remain fast enough to run on every commit.

Beginner: Why use node:assert/strict?

Because the legacy node:assert module uses loose equality in several of its core methods, which lets wrong values pass.

  import assert from "node:assert";
  assert.equal(1, "1");               // passes — uses ==
  assert.deepEqual({ a: 1 }, { a: "1" });   // passes — loose comparison

  import assert from "node:assert/strict";
  assert.equal(1, "1");               // fails — strict mode maps equal to strictEqual

In strict mode, equal behaves as strictEqual (Object.is semantics) and deepEqual behaves as deepStrictEqual, which also compares types and prototypes. So a function that returns the string "42" where the contract says the number 42 — a real bug, often caused by reading from a query string or environment variable — fails the test instead of passing it.

That is the underlying problem with loose assertions: a test that passes wrongly is worse than no test, because it is cited as evidence that the behaviour is correct.

It also has practical advantages: it is built into Node with no dependency, it pairs naturally with the built-in node:test runner, and it produces readable diffs for failed deep comparisons. For floating-point values neither mode is right — compare within a tolerance instead.

Mid: Where should you draw the mocking boundary, and why?

At the boundary of your process — the things you do not own and cannot control: third-party HTTP APIs, payment and email providers, the system clock, randomness, and anything with real-world side effects you must not trigger from a test.

Those are the right things to fake because they are slow, flaky, cost money, or are non-deterministic. A test that charges a real card or depends on a partner API being up is not a test you can run on every commit.

Do not mock your own modules. Mocking the repository layer from the service layer, or one internal function from another, couples the test to the current call graph rather than to behaviour. The result is the worst of both: a refactor that changes nothing observable breaks dozens of tests, while a genuine bug inside the mocked-out module passes, because the mock returns what you told it to rather than what the code does.

Do not mock your own database either, for reasons in the next question.

The structural enabler is dependency injection: pass the clock, the HTTP client and the payment client into the code rather than importing them, so a test supplies fakes by passing a different argument, with no module-mocking machinery. For outbound HTTP, intercept at the network layer — MSW or nock — which exercises your real client code, serialisation and error handling rather than skipping them.

A useful heuristic: if you find yourself mocking many things to test one function, that function is probably reaching out for dependencies it should have been handed.

Mid: Why is a real database preferable to an in-memory substitute?

Because an in-memory substitute tests your code against a different database, and the differences are exactly where production bugs live.

SQLite standing in for PostgreSQL, or a hand-written fake repository, differs in ways that matter: SQL dialect and functions; how constraints such as unique indexes and foreign keys are enforced; transaction isolation and locking behaviour; type coercion, JSON columns, time zones and collation; and how concurrent writes interact. A query can pass every test against the substitute and fail — or silently return different results — against the real engine.

The bugs most worth catching are precisely the ones a fake cannot reproduce: a unique-constraint violation under a race, a migration that fails on real data types, a query that relies on an index behaving a particular way, a deadlock between two transactions.

The historical objection was speed and setup, and it no longer holds. Testcontainers, or a Docker Compose service in CI, starts the real database version you run in production in seconds. Run the real migrations against it, so migrations are tested too.

Speed per test comes from isolation strategy rather than from faking: wrap each test in a transaction that is rolled back afterwards, or truncate tables between tests, so each test starts clean without recreating the database. Tests then run in parallel against separate schemas or databases.

The rule is to fake what you do not own and use the real thing for what you do — and the database is very much something you own.

Senior: A suite of 2,000 tests takes 25 minutes and fails randomly about 5% of runs. How do you fix it?

The flakiness is the more urgent problem, because a suite that fails randomly trains people to re-run CI rather than read failures, and once that habit exists real regressions get re-run away too — so the suite's effective value is already near zero regardless of its size. I would first make flakiness visible by recording per-test pass rates across runs, since teams usually blame "CI being slow" when a handful of tests are responsible. Then fix by cause: fixed sleeps replaced with condition polling, real-clock dependencies replaced with injected or faked time, shared state eliminated with per-test truncation and per-worker database isolation, and order dependencies exposed by randomizing test order. Any test that cannot be made deterministic gets deleted rather than retried, because a test that lies is worse than a missing one. For duration, I would measure where time actually goes before optimizing — usually a small number of tests dominate, often through repeated container startup or full-schema recreation per test rather than truncation. Parallelizing across workers with isolated databases typically gives the largest win, followed by moving slow end-to-end tests out of the pull-request path into a post-merge run so feedback stays fast. Fifteen minutes is roughly the threshold past which people stop waiting and start context-switching, so that is the target I would aim for, and I would keep a fast subset runnable locally in under a minute. The strategic point is that suite speed and reliability are what determine whether tests get run at all, which matters more than how many there are.

Senior: Management wants 100% code coverage. How do you respond?

I would agree with the underlying goal — confidence that changes do not break things — and explain why the metric does not deliver it. Coverage records which lines executed, not whether behaviour was verified, so a test with no assertions at all can produce full coverage; chasing a number therefore reliably produces assertion-free tests written to satisfy the gate. The last stretch is also where cost rises sharply and value falls, since it drives tests for trivial getters and unreachable error branches, and those tests still have to be maintained forever. What I would propose instead: coverage reported but not gated, read as a map of blind spots rather than a score, with a high bar specifically on high-risk code — payment paths, authorization, data migrations — where I would genuinely want near-complete branch coverage. Then better signals alongside it: mutation testing on critical modules, which measures whether tests actually detect deliberately introduced bugs and is the direct measure of what coverage only proxies; tracking escaped defects, since bugs reaching production are the real failure; and requiring a regression test with every bug fix, which targets testing at proven-fragile code. If a number is genuinely required for reporting, I would suggest a floor that prevents backsliding — say 70% with no decrease allowed — rather than a ceiling that distorts behaviour. The principle is that any metric used as a target stops measuring what it measured.

🏋️ Graded Exercises

1 (easy): Write tests for calculateTotal(items) covering the empty case, a normal case, and invalid input.
Solution 
import { test, describe } from "node:test";
import assert from "node:assert/strict";

describe("calculateTotal", () => {
  test("returns 0 for no items", () => {
    assert.equal(calculateTotal([]), 0);
  });

  test("sums price × quantity across items", () => {
    assert.equal(calculateTotal([
      { price: 100, qty: 2 },
      { price: 50, qty: 1 },
    ]), 250);
  });

  test("rejects negative quantities", () => {
    assert.throws(() => calculateTotal([{ price: 100, qty: -1 }]),
                  { message: /quantity/i });
  });
});
// The empty case is the one people skip and the one that breaks in
// production, because reduce without an initial value throws on [].
2 (easy): Why is await new Promise(r => setTimeout(r, 500)) a bad way to wait for a job?
Solution 
// It asserts the machine finishes in under 500ms. On a loaded CI runner it
// does not, so the test fails intermittently — and it wastes 500ms on every
// run even when the work took 5ms.
async function waitFor(predicate, { timeout = 5000, interval = 20 } = {}) {
  const deadline = Date.now() + timeout;
  while (Date.now() < deadline) {
    if (await predicate()) return;
    await new Promise((r) => setTimeout(r, interval));
  }
  throw new Error("Condition not met within timeout");
}

await waitFor(() => jobQueue.isEmpty());
// Returns as soon as the condition holds, and fails with a clear message
// rather than a confusing downstream assertion if it never does.

Solution

5 (hard): Write a test that fails if any non-public route is missing authentication.
Solution 
const PUBLIC = new Set([
  "GET /health", "GET /health/live", "GET /health/ready",
  "POST /api/auth/login", "POST /api/auth/register",
]);

function registeredRoutes(app) {
  // Walk the Express router stack for concrete method+path pairs.
  const out = [];
  for (const layer of app.router.stack) {
    if (layer.route) {
      for (const m of Object.keys(layer.route.methods)) {
        out.push(`${m.toUpperCase()} ${layer.route.path}`);
      }
    }
  }
  return out;
}

test("every non-public route rejects anonymous requests", async () => {
  const routes = registeredRoutes(app);
  assert.ok(routes.length > 0, "no routes discovered — the walker is wrong");

  for (const route of routes) {
    if (PUBLIC.has(route)) continue;
    const [method, path] = route.split(" ");
    const url = path.replace(/:(\w+)/g, "1");        // fill params

    const res = await request(app)[method.toLowerCase()](url).send({});
    assert.ok([401, 403].includes(res.status),
      `${route} returned ${res.status} without auth — expected 401/403`);
  }
});

// Why this beats per-route auth tests: it is driven by the route TABLE, so
// adding an unprotected endpoint fails the suite automatically. Per-route
// tests only cover routes someone remembered — the same failure mode as
// forgetting the middleware in the first place.
// The PUBLIC allowlist is the point of control: making a route public
// becomes an explicit, reviewable edit rather than an omission.
// The non-empty assertion guards against the walker silently breaking on an
// Express upgrade and turning the whole test into a no-op.
6 (hard): A test passes alone but fails in the full suite. Diagnose systematically.
Solution 
// The symptom means SHARED STATE — something a previous test changed that
// this test depends on. Narrow it methodically rather than by guessing.

// 1. CONFIRM it is order dependence, and find the culprit pair:
//    node --test --test-name-pattern="..."   // run subsets
//    Bisect: run the first half of the suite plus the failing test, then
//    the other half. This finds the offending test in log2(n) runs.

// 2. Check the usual sources, most common first:
//    • DATABASE rows left behind → truncate in beforeEach, not afterEach
//      (afterEach does not run if a test crashes, leaving state behind)
//    • MODULE-LEVEL state: caches, singletons, connection pools, memoized
//      config. `import` caches modules, so a mutation persists for the run.
//    • MOCKS not restored → t.mock.restoreAll() / mock.reset()
//    • ENV VARS set by one test and read by another
//    • FAKE TIMERS left enabled, so a later test's real timers never fire
//    • Unawaited promises from a prior test resolving mid-test and writing

// 3. Prove it rather than assuming:
//    Randomize order across runs. If failures move around, it is order
//    dependence; if they are stable, it is a genuine interaction.

// 4. FIX AT THE ROOT, not by reordering. Making the test pass by moving it
//    earlier leaves the shared state, so the next person hits it again:
beforeEach(async () => {
  await db.query("TRUNCATE orders, users RESTART IDENTITY CASCADE");
  cache.clear();
  mock.restoreAll();
});
// And for parallel runs, isolate per worker so tests cannot collide at all:
//   DATABASE_URL pointing at a schema named for process.env.TEST_WORKER_ID

// The principle: tests must be independent by construction, not by
// convention. Any test that depends on another having run is a latent
// failure waiting for someone to add, remove, or parallelize a test.

🎯 Key Takeaways

  • Node has a built-in test runner — node --test with node:assert/strict needs no dependencies.
  • Test behaviour, not implementation: tests that assert on internal calls break on refactors and catch nothing.
  • For services, integration tests carry the most value per line, because most bugs live in the wiring.
  • Use a real database via containers — substitutes cannot exercise real SQL, constraints, or migrations.
  • Mock only at system edges; mocking your own modules tests the mocks and hides wiring bugs.
  • A mock encodes your belief about an upstream, so a green suite is never evidence about someone else's service.
  • Fake or inject the clock and randomness; never wait with fixed sleeps.
  • Order-dependent failures always mean shared state — fix the state, never the ordering.
  • Coverage measures execution, not verification; read it as a blind-spot map rather than a target.
  • A flaky test is worse than no test, because it teaches the team to ignore failures.
  • Unit tests isolate one function; integration tests exercise real components together.
  • Bugs live in the seams, where unit tests with fakes cannot see.
  • API-boundary integration tests survive refactoring.
  • Legacy assert.equal uses ==; the strict module does not.
  • A test that passes wrongly is worse than no test.
  • Mock at process boundaries: third-party APIs, clock, randomness, side effects.
  • Mocking your own modules couples tests to the call graph.
  • Dependency injection lets tests supply fakes without mocking machinery.
  • An in-memory substitute is a different database.
  • Testcontainers makes the real database fast enough for every commit.
