Validation & Error Handling Building APIs

What you'll master: validating untrusted input at the boundary with schemas, the operational-versus-programmer error distinction that decides whether you recover or crash, error taxonomies that survive refactoring, and why uncaughtException should end the process. Prerequisites: REST API Design, Middleware Deep Dive.

Part 1 — Validate at the Boundary, Once

// Every external input is untrusted: request bodies, query strings, path
// params, headers, webhook payloads, env vars, and responses from other
// services. "It's our own internal service" is not a trust argument — it is
// an assumption that fails during an incident.

// ❌ Ad-hoc checks scattered through the handler:
if (!req.body.email) return res.status(400).json({ error: "email required" });
if (typeof req.body.age !== "number") return res.status(400).json(...);
if (req.body.age < 0) ...
// Unmaintainable, easy to forget a field, and the shape lives nowhere.

// ✅ One schema, parsed once, at the edge:
import { z } from "zod";

const CreateOrder = z.object({
  email: z.string().email(),
  items: z.array(z.object({
    sku: z.string().regex(/^[A-Z0-9-]{3,20}$/),
    qty: z.number().int().positive().max(100),
  })).min(1),
  note: z.string().max(500).optional(),
});

// The payoff beyond tidiness: after parse, the rest of your code is dealing
// with a KNOWN shape. Validation is what converts "unknown JSON" into a
// domain type, and it is the only place that conversion should happen.
// In TypeScript you also get the static type for free:
//   type CreateOrder = z.infer<typeof CreateOrder>;
// so the runtime check and the compile-time type cannot drift apart.

Part 2 — A Validation Middleware

export function validate(schemas) {
  return (req, res, next) => {
    for (const key of ["body", "query", "params"]) {
      if (!schemas[key]) continue;
      const result = schemas[key].safeParse(req[key]);
      if (!result.success) {
        return next(Object.assign(new Error("Validation failed"), {
          status: 422,
          code: "validation_failed",
          details: result.error.issues.map((i) => ({
            field: i.path.join("."),
            issue: i.code,
            message: i.message,
          })),
        }));
      }
      req[key] = result.data;     // ← replace with the PARSED value
    }
    next();
  };
}

app.post("/orders", validate({ body: CreateOrder }), createOrder);

// Two details that matter more than they look:
//
// 1. safeParse, not parse. parse throws; safeParse returns a result object.
//    Using the non-throwing form keeps validation failures on the normal
//    control-flow path instead of routing an expected outcome (bad user
//    input) through the exception mechanism meant for the unexpected.
//
// 2. Assigning the parsed value back is the point. Schemas COERCE and STRIP:
//    req.query.limit becomes a real number, unknown keys are removed. If you
//    validate but keep using the raw input, you get the check without the
//    guarantee — and an attacker's extra fields survive into your database.
//    This is the mass-assignment vulnerability, and stripping is its fix.
Query strings are always strings. ?limit=50 gives you "50", and ?active=false gives you the string "false" — which is truthy. Every query-parameter schema needs explicit coercion (z.coerce.number().int().min(1).max(100)), and the maximum is not decoration: an uncapped limit is a client-controlled way to ask your database for everything.

Part 3 — Operational vs Programmer Errors

// The distinction that organizes all error handling in Node:
//
// OPERATIONAL — expected failures in correct programs. The world misbehaved.
//   invalid user input, 404, unauthorized, DB connection lost, upstream
//   timeout, disk full, rate limit exceeded
//   → HANDLE: retry, fail the request, degrade, tell the user
//
// PROGRAMMER — bugs. Your code is wrong.
//   undefined is not a function, forgot to await, wrong argument type,
//   null dereference, unreachable branch reached
//   → DO NOT HANDLE: you cannot recover from a bug whose extent you do not
//     know. Log it with full context and let the process die.
//
// Why the second half is counterintuitive but correct: after a programmer
// error, the process is in an UNKNOWN state — half-applied mutations, a
// released lock that should not have been, a connection returned to the pool
// mid-transaction. Continuing risks corrupting data, which is worse than
// downtime. A crash plus a process manager restart returns you to a known
// good state in milliseconds.

// This is why swallowing errors is the worst option available:
try { await doWork(); } catch (e) { /* ignore */ }        // ❌ never
try { await doWork(); } catch (e) { console.log(e); }     // ❌ barely better
// Both convert a loud failure into a silent wrong answer. If you cannot
// handle it meaningfully, let it propagate to a boundary that can decide.

Part 4 — An Error Taxonomy That Survives Refactoring

// A small base class carries the API contract with the error, so handlers
// never map errors to statuses by inspecting messages.
export class AppError extends Error {
  constructor(message, { status = 500, code = "internal_error", details, cause } = {}) {
    super(message, { cause });          // ← `cause` preserves the original
    this.name = this.constructor.name;
    this.status = status;
    this.code = code;
    this.details = details;
    this.expected = status < 500;       // operational vs programmer, explicitly
    Error.captureStackTrace?.(this, this.constructor);
  }
}

export class NotFound extends AppError {
  constructor(resource) {
    super(`${resource} not found`, { status: 404, code: "not_found" });
  }
}
export class Conflict extends AppError {
  constructor(message, details) {
    super(message, { status: 409, code: "conflict", details });
  }
}

// Usage reads like the domain, not like HTTP plumbing:
const order = await orders.find(id);
if (!order) throw new NotFound("Order");

// `cause` (ES2022) is the underlying feature that makes wrapping honest —
// you add context WITHOUT discarding the original error and its stack:
try {
  await db.query(sql);
} catch (err) {
  throw new AppError("Failed to load orders", { status: 503, cause: err });
}
// Node's console and most loggers print the cause chain automatically, so
// you keep both the domain-level meaning and the driver-level detail. The
// alternative people reach for — `throw new Error(err.message)` — throws
// away the stack that tells you where it actually happened.

Part 5 — The Error Handler, Completed

app.use((err, req, res, next) => {
  if (res.headersSent) return next(err);      // delegate; Express destroys it

  const status = err.status ?? 500;
  const expected = err.expected ?? status < 500;

  // Log level tracks severity: expected failures are info, bugs are errors.
  // Logging 404s at error level is how alerting becomes noise nobody reads.
  req.log?.[expected ? "info" : "error"]({
    err, reqId: req.ctx?.id, path: req.originalUrl, userId: req.ctx?.user?.id,
  }, expected ? "request failed" : "unhandled error");

  res.status(status).json({
    error: err.code ?? "internal_error",
    // NEVER leak an unexpected error's message: it can contain SQL, file
    // paths, connection strings, or internal hostnames.
    message: expected ? err.message : "An unexpected error occurred",
    details: expected ? err.details : undefined,
    requestId: req.ctx?.id,
  });
});

// Known third-party errors get normalized BEFORE this handler (as its own
// middleware), so the responder stays a pure function of the taxonomy:
function normalize(err, req, res, next) {
  if (err.type === "entity.too.large") {
    return next(new AppError("Payload too large", { status: 413, code: "payload_too_large", cause: err }));
  }
  if (err.code === "23505") {                 // Postgres unique violation
    return next(new Conflict("Resource already exists", { constraint: err.constraint }));
  }
  if (err.name === "ZodError") {
    return next(new AppError("Validation failed", {
      status: 422, code: "validation_failed",
      details: err.issues, cause: err,
    }));
  }
  next(err);
}
app.use(normalize, respond);
// Driver-specific codes like "23505" belong in exactly one file. Scattering
// them through handlers couples your business logic to Postgres.

Part 6 — Process-Level Handlers: Crash Correctly

process.on("uncaughtException", (err, origin) => {
  logger.fatal({ err, origin }, "uncaught exception — exiting");
  // Flush logs, then exit NON-ZERO so the supervisor restarts you.
  process.exit(1);
});

process.on("unhandledRejection", (reason) => {
  logger.fatal({ err: reason }, "unhandled rejection — exiting");
  process.exit(1);
});
// Since Node 15 unhandled rejections terminate by default; this handler
// exists to LOG before dying, not to prevent dying.

// The rule people get wrong: these handlers must not resume normal operation.
// Their job is to record why you are crashing, not to keep a process alive in
// an unknown state. "Log and continue" is how a single bug becomes a slow
// corruption of production data.
//
// The full crash sequence in production:
//   1. log with full context (this is your only forensic artifact)
//   2. stop accepting new work (server.close())
//   3. give in-flight requests a brief, BOUNDED grace period
//   4. process.exit(1)
//   5. the supervisor (Kubernetes, systemd, pm2) restarts a clean process
//
// A non-zero exit code matters: exit(0) tells the orchestrator you meant to
// stop, and a crash loop that looks intentional will not alert anyone.

// Graceful degradation is different from crashing, and belongs at the
// request level — not here:
const recommendations = await getRecommendations(userId)
  .catch((err) => { req.log.warn({ err }, "recs unavailable"); return []; });
// A failing non-critical dependency should degrade the response, not the
// process. Deciding which dependencies are load-bearing IS the design work.

Interview Questions

Beginner: Why validate input at the boundary rather than inside business logic?

So the rest of the code can assume a known shape. Boundary validation converts unknown external JSON into a domain type exactly once, which means business logic contains no defensive type checks and cannot be reached with a shape nobody anticipated. Scattering checks through handlers means every new code path is another chance to forget one, and the expected shape is documented nowhere. It also concentrates the security-relevant work — coercion, bounds, and stripping unknown fields — in one reviewable place.

Beginner: What is the difference between 400 and 422?

400 means the request is malformed at the syntax level — unparseable JSON, a missing required field, a wrong content type. 422 means it parsed correctly and is well-formed but semantically invalid: an end date before the start date, a quantity of zero where the domain requires at least one. The practical value is diagnostic: 400 tells a client its serialization is broken, 422 tells it the data is wrong, and those lead a developer to different parts of their code.

Mid: Explain operational vs programmer errors and how each should be handled.

Operational errors are expected failures in a correct program — invalid input, a 404, a dropped database connection, an upstream timeout. They are part of the specification and should be handled: retry, degrade, or return a meaningful status. Programmer errors are bugs — calling undefined, a forgotten await, a null dereference. They should not be handled, because after a bug the process is in an unknown state: mutations may be half-applied, locks held, connections returned mid-transaction. Continuing risks corrupting data, which is strictly worse than downtime. The right response is to log with full context and exit non-zero so a supervisor restarts a clean process. The practical test is whether you can state what recovery means; if you cannot, it is a bug, not a condition.

Mid: Why must the parsed result replace the raw input after validation?

Because schema parsing does two jobs: checking and transforming. It coerces types, applies defaults, and strips unknown keys. If you validate req.body but keep reading the original object, you get the check without the transformation — query params stay strings, defaults are missing, and any extra fields an attacker added survive into whatever you pass downstream. That last one is the mass-assignment vulnerability: a client posts {"email": "...", "role": "admin"}, validation passes because email is valid, and the raw object gets spread into a database update. Assigning the parsed value back is what makes stripping actually protect you.

Senior: Your service logs "Cannot read properties of undefined" thousands of times daily but stays up. Walk through your response.

Staying up while logging that is itself the problem: something is catching programmer errors and continuing, so a bug that should have been a loud crash on day one has become steady-state background noise. First I would find the swallower — usually a broad try/catch around a handler, or an uncaughtException handler that logs and returns instead of exiting — because as long as it exists the process is running in an unknown state after every occurrence, and any of those thousands of requests may have half-applied a mutation. Then I would triage the actual bug with a stack trace and request context, checking whether affected requests returned wrong data rather than failing, since silent wrong answers are the real damage and they will not appear in error-rate dashboards. The fix has three parts: correct the null dereference; remove the swallowing so the class of error crashes loudly in future; and add an alert on fatal exits so the next occurrence pages someone within minutes instead of accruing quietly. I would also check whether this is genuinely a bug or unvalidated input reaching business logic — if an optional upstream field is sometimes absent, the durable fix is boundary validation that rejects it as a 422, converting a programmer error into an operational one.

Senior: Design error handling for a service that calls three upstreams, where one is non-critical. What decisions matter?

The central decision is per-dependency criticality, and it is a product decision as much as a technical one. For each upstream I would establish what the response should be if it is unavailable: fail the request, serve stale data, or omit a section. Critical dependencies propagate their failure as a 502 or 503 with a Retry-After; the non-critical one gets a .catch() at its call site that logs a warning and returns a neutral fallback, so a recommendations outage costs a widget rather than the page. Each call needs its own timeout sized to that dependency's real latency budget, because unbounded waiting is unbounded resource consumption and a slow dependency degrades the whole service even when it is optional. Beyond that, bounded concurrency per upstream so one failing dependency cannot exhaust the connection pool, and a circuit breaker on the non-critical one so that once it is clearly down you stop paying its timeout on every request and fail fast to the fallback instead. Observability has to distinguish degraded from failed — a response served without recommendations is a success with a degradation counter, not an error, or your error rate stops meaning anything. Finally the fallback needs to be explicit in the response contract so clients can tell partial data from complete data rather than silently rendering an empty section as though it were empty by fact.

5 (hard): Normalize a Postgres unique-violation, a body-parser size error, and a Zod error into one response shape.
Solution 
const PG_UNIQUE_VIOLATION = "23505";

export function normalize(err, req, res, next) {
  if (err.name === "ZodError") {
    return next(new AppError("Validation failed", {
      status: 422, code: "validation_failed", cause: err,
      details: err.issues.map((i) => ({ field: i.path.join("."), message: i.message })),
    }));
  }
  if (err.type === "entity.too.large") {          // express.json limit
    return next(new AppError("Payload too large", {
      status: 413, code: "payload_too_large", cause: err,
    }));
  }
  if (err.code === PG_UNIQUE_VIOLATION) {
    return next(new Conflict("Resource already exists", { constraint: err.constraint }));
  }
  return next(err);          // unknown → falls through as a 500
}

app.use(normalize);
app.use(respond);            // the single responder from Part 5

// Why a separate middleware rather than branches inside the responder:
// the responder becomes a pure function of the taxonomy, so adding a new
// third-party error type never risks changing how existing ones are
// rendered. It also keeps Postgres error codes out of business logic
// entirely — swapping databases touches one file.
6 (hard): A handler catches every error and returns 500 with the message. List everything wrong and rewrite it.
Solution 
// ❌ The original
app.get("/orders/:id", async (req, res) => {
  try {
    const order = await db.find(req.params.id);
    res.json(order);
  } catch (err) {
    res.status(500).json({ error: err.message });
  }
});

// Four distinct defects:
// 1. EVERY failure becomes 500 — a missing order is a 404, bad input a 422.
//    Clients cannot distinguish "retry later" from "this will never work".
// 2. err.message is leaked: driver errors carry SQL, table names, hostnames,
//    sometimes credentials from connection strings.
// 3. Programmer errors are caught and converted into a normal response, so
//    real bugs never crash, never alert, and accumulate silently.
// 4. Nothing is logged, so the only record of the failure is a body sent to
//    a client you cannot query.

// ✅ Rewrite: let errors travel to the central handler.
app.get("/orders/:id",
  validate({ params: z.object({ id: z.coerce.number().int().positive() }) }),
  async (req, res) => {
    const order = await db.find(req.params.id);
    if (!order) throw new NotFound("Order");
    res.json(order);
  });

// Nothing is caught here at all, and that is the point: the handler states
// the happy path plus its one domain condition. Invalid input was rejected
// before the handler ran; unexpected failures propagate to the error
// middleware, which logs them at error level, returns a generic 500, and —
// for a genuine programmer error — leaves the crash path intact.
// Catch only where you can add information or make a real decision.

🎯 Key Takeaways

  • Validate every external input at the boundary with a schema, so business logic never sees an unknown shape.
  • Replace the raw input with the parsed value — coercion and stripping are what make validation protective, not just diagnostic.
  • Query parameters are always strings; coerce explicitly and bound every numeric input, especially limit.
  • Operational errors are handled; programmer errors should crash the process, because recovery from an unknown state risks data corruption.
  • Swallowing an error converts a loud failure into a silent wrong answer — the most expensive kind.
  • An error class hierarchy carrying status and a stable code keeps HTTP concerns out of business logic.
  • Use { cause } when wrapping so you add context without discarding the original stack.
  • Normalize third-party and driver errors in one middleware; keep the responder a pure function of your taxonomy.
  • Log level must track expected versus unexpected, or alerting drowns in 404s and nobody reads it.
  • Process-level handlers exist to log and exit non-zero — never to resume normal operation.
