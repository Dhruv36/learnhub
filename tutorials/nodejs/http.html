HTTP Without Frameworks Building APIs

What you'll master: what node:http actually gives you — and therefore what Express is and isn't adding. The request/response objects as streams, reading bodies safely, routing by hand, status codes and headers that matter, keep-alive, and graceful shutdown. Every framework in the ecosystem is a thin layer over this API; knowing it is what lets you debug the layer above. Prerequisites: Streams & Backpressure, EventEmitter.

Part 1 — The Server in Six Lines, and What Each Object Is

import { createServer } from "node:http";

const server = createServer((req, res) => {
  res.writeHead(200, { "content-type": "text/plain" });
  res.end("hello");
});
server.listen(3000);

// The two arguments are the whole API surface, and both are STREAMS:
//   req : http.IncomingMessage — a READABLE stream (the request body)
//         plus metadata: req.method, req.url, req.headers
//   res : http.ServerResponse  — a WRITABLE stream (the response body)
//         plus control: res.statusCode, res.setHeader(), res.end()
//
// That is why the streams lesson came first. `res` being writable is why
// `pipeline(createReadStream(file), res)` works — you are not "using a
// framework feature", you are writing bytes into a socket with flow control.
//
// Note what is NOT here: no routing, no body parsing, no cookies, no static
// files, no error handling. Those are the things Express adds — nothing more
// magical than the code in this lesson.

Part 2 — req.url Is Not a URL

// req.url is the raw request target: a PATH plus query string, never the origin.
//   GET /search?q=node+streams&page=2  →  req.url === "/search?q=node+streams&page=2"
// It is a string. Parsing it by hand (split("?"), indexOf) is where injection
// and normalization bugs are born. Use the WHATWG URL parser:

const url = new URL(req.url, `http://${req.headers.host}`);
url.pathname            // "/search"          — decoded, normalized
url.searchParams.get("q")   // "node streams"  — percent-decoding handled
url.searchParams.getAll("tag")  // repeated params → array

// The base argument is REQUIRED: req.url is relative, and `new URL` on a
// relative string throws. Using the Host header as the base is standard, but
// treat that header as untrusted input — it is client-controlled, so never
// build security decisions (or absolute redirect targets) from it unvalidated.

// Why not just split("?")[0]? Because these are all the same resource, and a
// hand-rolled parser disagrees with the browser about at least one of them:
//   /files/../admin      →  path traversal if you concatenate to a filename
//   /Files               →  case: distinct path, often the same file on macOS/Windows
//   /search?q=a%26b      →  %26 is a literal "&" INSIDE the value, not a separator
// Matching the platform parser is a correctness property, not a style choice.

Part 3 — Reading a Request Body

// The body is not on `req` — it ARRIVES, in chunks, after your handler is
// already running. This is the single biggest surprise coming from PHP/Rails.

// The modern idiom: req is an async iterable of Buffers.
async function readBody(req, limitBytes = 1_000_000) {
  const chunks = [];
  let size = 0;
  for await (const chunk of req) {
    size += chunk.length;
    if (size > limitBytes) {                 // ← NOT optional. See below.
      req.destroy();
      throw Object.assign(new Error("Payload too large"), { status: 413 });
    }
    chunks.push(chunk);
  }
  return Buffer.concat(chunks);
}

const raw = await readBody(req);
const data = JSON.parse(raw.toString("utf8"));   // wrap in try/catch → 400

// THE LIMIT IS A SECURITY CONTROL. Without it, any client can stream gigabytes
// into your heap and take the process down — a one-line denial of service that
// needs no exploit, just a slow upload. Every body parser you will ever use
// (express.json({ limit }), busboy) has this knob; know that it exists and
// that its default is a decision you are making either way.
//
// Two more body facts that bite:
//   1. If you never consume the body, the socket stays busy and keep-alive
//      connections stall. Frameworks drain it for you; here it is on you.
//   2. Content-Type decides the parse. application/json → JSON.parse;
//      application/x-www-form-urlencoded → new URLSearchParams(text);
//      multipart/form-data → do NOT hand-roll it, use a library (busboy).

Part 4 — Status, Headers & Sending a Response

// Headers must be set BEFORE the first byte of body — HTTP sends them first,
// so once any body byte flushes, headers are on the wire and immutable.
res.statusCode = 201;
res.setHeader("content-type", "application/json; charset=utf-8");
res.setHeader("location", "/orders/42");
res.end(JSON.stringify(order));
// Setting a header after end() → ERR_HTTP_HEADERS_SENT. That error nearly
// always means you responded twice: an early return you forgot to `return`.

// The one-shot form (writeHead) is equivalent and atomic:
res.writeHead(201, { "content-type": "application/json" }).end(body);

// Status codes worth being exact about — these carry real client behaviour:
//   200 OK          201 Created (+ Location)     204 No Content (no body!)
//   301 permanent redirect (CACHED BY BROWSERS — hard to undo)  302/307 temporary
//   400 malformed   401 unauthenticated ("who are you?")
//   403 authenticated but forbidden ("I know you; no")
//   404 not found   409 conflict     413 payload too large
//   422 well-formed but semantically invalid    429 rate limited (+ Retry-After)
//   500 our bug     502/504 upstream failed/timed out    503 down (+ Retry-After)
//
// 401 vs 403 and 400 vs 422 are the two pairs interviewers probe, because
// getting them right proves you think about the CLIENT's next action: retry
// with credentials (401) is a different program path than give up (403).

Part 5 — Routing by Hand (and Why Frameworks Exist)

const routes = {
  "GET /health":      (req, res) => json(res, 200, { ok: true }),
  "GET /orders":      listOrders,
  "POST /orders":     createOrder,
};

const server = createServer(async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`);
  const handler = routes[`${req.method} ${url.pathname}`];
  try {
    if (!handler) return json(res, 404, { error: "Not found" });
    await handler(req, res, url);
  } catch (err) {
    // ONE place that turns a thrown error into a response. Without it, an
    // async throw becomes an unhandled rejection and the client just hangs
    // until timeout — the worst possible failure mode.
    json(res, err.status ?? 500, { error: err.status ? err.message : "Internal error" });
  }
});

function json(res, status, body) {
  const payload = JSON.stringify(body);
  res.writeHead(status, {
    "content-type": "application/json; charset=utf-8",
    "content-length": Buffer.byteLength(payload),   // bytes, not characters
  });
  res.end(payload);
}

// This works, and for a small internal service it is genuinely enough.
// It stops scaling the moment you need PARAMETERS (/orders/:id), because an
// exact-match object lookup cannot express them — you need pattern matching,
// which means an ordered list of route patterns, which means precedence rules,
// which is most of what a router library is. That is the honest case for
// Express: not that this is hard, but that everyone writes the same 200 lines.
Content-Length must be byte length. Buffer.byteLength(s), never s.length. A string's .length counts UTF-16 code units, so any non-ASCII character (an emoji, an accented name, a CJK glyph) makes the declared length shorter than the real payload. The client then reads a truncated body and the connection desynchronizes — a bug that only appears once a real user types their own name into your API.

Part 6 — Keep-Alive, Timeouts & Graceful Shutdown

// HTTP/1.1 connections are REUSED by default (keep-alive) — one TCP handshake
// serves many requests. Consequences you must plan for:
//   • Sockets stay open between requests, so "the server is idle" is not the
//     same as "no connections exist".
//   • server.close() stops ACCEPTING new connections but waits for existing
//     ones — with keep-alive, idle clients can hold it open indefinitely.

// Timeouts (defaults are permissive; production should tighten them):
server.requestTimeout = 30_000;      // whole request must arrive within this
server.headersTimeout = 10_000;      // slowloris defence: headers must complete
server.keepAliveTimeout = 5_000;     // idle socket lifetime
// Behind a load balancer, keepAliveTimeout MUST exceed the LB's idle timeout,
// or the LB reuses a socket Node just closed → sporadic 502s that are famously
// hard to reproduce, because they need a race between two idle timers.

// Graceful shutdown — the difference between a clean deploy and dropped requests:
process.on("SIGTERM", () => {
  server.close(() => process.exit(0));   // finish in-flight, then exit
  server.closeIdleConnections();          // don't wait on idle keep-alives
  setTimeout(() => process.exit(1), 10_000).unref();   // hard cap
});
// Orchestrators (Kubernetes, systemd) send SIGTERM and then SIGKILL after a
// grace period. Ignoring SIGTERM means every deploy kills in-flight requests —
// users see errors caused purely by your release process. The .unref() keeps
// that safety timer from itself holding the process open.

Part 7 — Making Outbound Requests

// Use fetch (global since Node 18, backed by undici). It is the right default:
const res = await fetch("https://api.example.com/orders", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({ sku: "A1" }),
  signal: AbortSignal.timeout(5_000),   // fetch has NO default timeout
});
if (!res.ok) throw new Error(`Upstream ${res.status}`);   // ← 4xx/5xx do NOT throw
const data = await res.json();

// The two traps, both of which produce production incidents:
//   1. fetch only rejects on NETWORK failure. A 500 response is a resolved
//      promise — forgetting res.ok means treating an upstream outage as data.
//   2. No timeout by default: a hung upstream holds your handler (and its
//      socket, and its memory) until the OS gives up, minutes later. Under
//      load that exhausts your connection pool and the outage propagates
//      into your own service. AbortSignal.timeout() is not optional.

Interview Questions

Beginner: What are the two objects passed to an http request handler, and what are they really?

req (IncomingMessage) and res (ServerResponse). The key insight is that both are streams: req is Readable — the body arrives in chunks after the handler starts — and res is Writable, which is why you can pipe a file into it. req additionally carries method, url, and headers; res carries statusCode and header methods. Everything else — routing, body parsing, cookies — is application or framework code, not the Node API.

Beginner: Why can't you set a header after calling res.write()?

HTTP transmits the status line and headers before the body, so as soon as the first body byte is flushed the headers are already on the wire and cannot be changed — Node throws ERR_HTTP_HEADERS_SENT. In practice this error is a symptom rather than the disease: it almost always means the handler responded twice, typically an early validation branch that sent a 400 but forgot to return, letting the success path run as well.

Mid: Walk through reading a JSON body safely. What must be enforced and why?

Iterate for await (const chunk of req) collecting Buffers, tracking cumulative size and destroying the request with a 413 past a cap; concat, decode UTF-8, then JSON.parse inside try/catch mapping failures to 400. The size cap is the critical part — it is a security control, not tuning. Without it, any client can stream unbounded data into the heap and kill the process with no exploit at all, just a large slow upload. Also check Content-Type before parsing, and be aware that an unconsumed body leaves a keep-alive socket stuck.

Mid: 401 vs 403, and 400 vs 422 — when is each correct?

401 means unauthenticated: no credentials or invalid ones, and the correct client response is to authenticate and retry. 403 means authenticated but not permitted — retrying with the same identity is pointless, so the client should stop. 400 means the request is malformed at the syntax level (unparseable JSON, missing required field). 422 means it parsed fine but is semantically invalid (an end date before the start date). The distinction matters because status codes are an API for programs: they determine whether a client retries, re-authenticates, or gives up, and the wrong pair sends clients into retry loops against a request that can never succeed.

Senior: After moving to Kubernetes, a service shows a burst of 502s on every deploy and occasional 502s at idle. Diagnose both.

Two distinct causes that share a symptom. The deploy burst is missing graceful shutdown: SIGTERM terminates the process while requests are in flight, so the proxy reports upstream failure. Fix by handling SIGTERM with server.close(), closing idle keep-alive connections so close can actually complete, and an unref'd hard-exit timer as a backstop; ideally also fail the readiness probe first so traffic drains before shutdown begins. The idle 502s are the keep-alive race: if Node's keepAliveTimeout is shorter than the load balancer's idle timeout, the LB can dispatch a request onto a socket Node is simultaneously closing, and the request dies with no server-side log. Fix by raising Node's above the LB's. The general principle: connection lifecycle is a contract between two systems, and mismatched timers surface as rare, unreproducible errors.

Senior: Your service calls three upstreams with fetch. Under partial upstream degradation the whole service becomes unresponsive despite low CPU. Why, and what do you change?

Almost certainly missing timeouts. fetch has no default timeout, so when an upstream stops responding each request holds its handler, socket, and buffers until the OS eventually gives up — minutes. Arrivals keep allocating handlers while none retire, so concurrency climbs until the connection pool and event loop saturate: a slow dependency becomes a full outage. This is why low CPU is diagnostic — the process is waiting, not working. Fixes, in order: AbortSignal.timeout() on every outbound call, sized to the dependency's real latency budget; bound concurrency per upstream so one dependency cannot consume all capacity (bulkhead); a circuit breaker that fails fast once error rates spike, converting slow failures into cheap ones; and deciding per call site whether a degraded upstream should be fatal or produce a partial response. The underlying principle is that unbounded waiting is unbounded resource consumption.

🏋️ Graded Exercises

1 (easy): Write a server that responds 200 with {"ok":true} at /health and 404 JSON everywhere else.
Solution 
import { createServer } from "node:http";

function json(res, status, body) {
  const payload = JSON.stringify(body);
  res.writeHead(status, {
    "content-type": "application/json; charset=utf-8",
    "content-length": Buffer.byteLength(payload),
  });
  res.end(payload);
}

createServer((req, res) => {
  const { pathname } = new URL(req.url, `http://${req.headers.host}`);
  if (req.method === "GET" && pathname === "/health") return json(res, 200, { ok: true });
  json(res, 404, { error: "Not found" });
}).listen(3000);
2 (easy): Given /search?q=a%26b&tag=x&tag=y, extract q and every tag. Why would split("&") get this wrong?
Solution 
const url = new URL(req.url, `http://${req.headers.host}`);
url.searchParams.get("q");        // "a&b"  — %26 decoded to a literal ampersand
url.searchParams.getAll("tag");   // ["x", "y"]

// split("&") splits on the ENCODED %26 only after a naive decode, so a
// hand-rolled parser that decodes first then splits turns the single value
// "a&b" into two parameters. Order matters: split on the raw string, THEN
// percent-decode each piece — which is exactly what URLSearchParams does.
// Repeated keys are also lost by any object-based parse that assigns
// params[key] = value, since the second tag overwrites the first.
3 (medium): Write readJson(req) that enforces a 100KB cap, rejects wrong Content-Type with 415, and malformed JSON with 400.
Solution 
async function readJson(req, limit = 100 * 1024) {
  const type = (req.headers["content-type"] ?? "").split(";")[0].trim();
  if (type !== "application/json") {
    throw Object.assign(new Error("Expected application/json"), { status: 415 });
  }
  const chunks = [];
  let size = 0;
  for await (const chunk of req) {
    size += chunk.length;
    if (size > limit) {
      req.destroy();
      throw Object.assign(new Error("Payload too large"), { status: 413 });
    }
    chunks.push(chunk);
  }
  const text = Buffer.concat(chunks).toString("utf8");
  try {
    return JSON.parse(text);
  } catch {
    throw Object.assign(new Error("Malformed JSON"), { status: 400 });
  }
}
// Content-Type is split on ";" because it legitimately carries parameters
// ("application/json; charset=utf-8") — comparing the whole header fails.
// Note the cap is checked DURING streaming, not after: checking
// Content-Length alone is useless because a client can lie about it.
4 (medium): Stream a large file as a download, correctly handling the client disconnecting halfway.
Solution 
import { pipeline } from "node:stream/promises";
import { createReadStream } from "node:fs";
import { stat } from "node:fs/promises";

async function download(req, res, path) {
  const info = await stat(path);
  res.writeHead(200, {
    "content-type": "application/octet-stream",
    "content-length": info.size,
    "content-disposition": 'attachment; filename="export.csv"',
  });
  try {
    await pipeline(createReadStream(path), res);
  } catch (err) {
    // A client clicking away aborts the response stream. That is a normal
    // event, not a server fault — logging it as an error fills dashboards
    // with noise and hides real failures.
    if (err.code !== "ERR_STREAM_PREMATURE_CLOSE") throw err;
  }
}
// pipeline (not .pipe) guarantees the file descriptor is destroyed when the
// socket dies. With .pipe, the read stream keeps going and leaks the fd.
5 (hard): Add graceful shutdown to a keep-alive server. Explain why server.close() alone can hang.
Solution 
const server = createServer(handler);
server.keepAliveTimeout = 5_000;
server.headersTimeout = 10_000;
server.listen(3000);

let shuttingDown = false;
function shutdown() {
  if (shuttingDown) return;      // SIGTERM can arrive more than once
  shuttingDown = true;
  healthy = false;               // fail readiness first: stop NEW traffic
  server.close(() => process.exit(0));   // waits for in-flight requests
  server.closeIdleConnections();          // release idle keep-alive sockets
  setTimeout(() => process.exit(1), 10_000).unref();
}
process.on("SIGTERM", shutdown);
process.on("SIGINT", shutdown);

// Why close() alone hangs: it stops accepting NEW connections but waits for
// every EXISTING one to end. Keep-alive sockets are idle-but-open by design,
// so a browser that made one request ten seconds ago still holds a connection
// and close()'s callback never fires — until the orchestrator SIGKILLs you,
// which is precisely the ungraceful outcome you were preventing.
// closeIdleConnections() ends exactly those sockets that have no request in
// flight. The unref'd timer bounds the whole thing so a stuck request cannot
// block the deploy; unref keeps that timer from holding the loop open itself.
6 (hard): A handler does const user = await db.find(id); if (!user) res.writeHead(404).end(); res.end(JSON.stringify(user)) and intermittently crashes with ERR_HTTP_HEADERS_SENT. Fix it and generalize the lesson.
Solution 
// The bug: the 404 branch has no `return`, so on a missing user BOTH
// responses run — the second end() throws after headers are sent. It is
// intermittent only because it needs a missing record to trigger.
if (!user) return json(res, 404, { error: "Not found" });
return json(res, 200, user);

// Generalizing: "respond" is a terminal action, and JavaScript gives you no
// type-level help enforcing that a function stops afterwards. Three defences,
// strongest first:
// 1. Make handlers RETURN a result and let one central writer send it —
//    returning twice is impossible, so the bug becomes unrepresentable:
//      const result = await handler(req, url);   // { status, body }
//      json(res, result.status, result.body);
// 2. Throw for error paths and handle them in one error boundary, so early
//    exits use control flow that cannot fall through.
// 3. Failing those, treat every send as `return json(...)` by convention.
// This is the same class of fix as Express's "call next() and return" rule:
// the framework does not remove the hazard, it just renames it.

🎯 Key Takeaways

  • req and res are streams first and HTTP objects second — that is why file downloads, uploads, and backpressure all work the way the streams lesson described.
  • req.url is a raw path+query string, not a URL; parse it with new URL(req.url, base) so your normalization matches the browser's.
  • Request bodies arrive asynchronously and must be size-capped while reading — an uncapped body parser is a one-line denial of service.
  • Headers are immutable once any body byte is sent; ERR_HTTP_HEADERS_SENT almost always means a missing return after an early response.
  • Content-Length is a byte count — Buffer.byteLength(), never string.length.
  • Status codes are an API for programs: 401 vs 403 and 400 vs 422 determine whether the client retries, re-authenticates, or stops.
  • Keep-alive means idle connections outlive requests, so graceful shutdown needs close() plus closeIdleConnections() plus a hard timeout.
  • Node's keepAliveTimeout must exceed your load balancer's idle timeout, or you get sporadic 502s nobody can reproduce.
  • Outbound fetch does not throw on 4xx/5xx and has no default timeout; unbounded waiting is unbounded resource consumption.
  • Frameworks add routing, body parsing, and error boundaries over exactly this API — knowing the layer underneath is what makes the layer above debuggable.
