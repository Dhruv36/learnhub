Logging & Observability Production Node

What you'll master: structured logging that is actually queryable, correlation across services, the three pillars (logs, metrics, traces) and which question each answers, the RED/USE method for dashboards, and why p99 is the number that matters. Prerequisites: Configuration & Secrets, Validation & Error Handling.

Part 1 — Structured Logs, Not Sentences

// ❌ String interpolation produces logs you cannot query:
console.log(`User ${userId} failed login from ${ip} at ${new Date()}`);
// To answer "how many failed logins from this IP last hour?" you now need a
// regex over unstructured text — and it breaks the moment someone reworks
// the wording.

// ✅ Structured: the message is a constant, the variables are FIELDS.
import pino from "pino";
const log = pino({ level: config.LOG_LEVEL });

log.warn({ userId, ip, reason: "bad_password" }, "login failed");
// → {"level":40,"time":1753977600000,"userId":42,"ip":"1.2.3.4",
//    "reason":"bad_password","msg":"login failed"}
//
// Now it is queryable: `reason:"bad_password" AND ip:"1.2.3.4"` — and the
// query keeps working when someone rewords the message, because the message
// is not carrying data.

// Rules that make logs useful rather than voluminous:
// 1. The message is a CONSTANT string — never interpolate values into it.
//    Constant messages group naturally; interpolated ones are all unique.
// 2. Log objects, not strings. `log.info({ orderId }, "order created")`.
// 3. Log at BOUNDARIES: request in/out, external calls, state changes.
//    Logging inside tight loops is how you generate gigabytes of noise.
// 4. Never log secrets. Configure redaction and verify it:
const log = pino({
  redact: ["req.headers.authorization", "req.headers.cookie",
           "*.password", "*.token", "password", "creditCard"],
});
// Redaction that silently does not match your field names is worse than
// none — it creates confidence without protection. Read real output.

// Why pino over console.log: it writes newline-delimited JSON asynchronously
// with very low overhead. console.log is SYNCHRONOUS to a pipe or file,
// so under load it blocks the event loop — logging becomes the bottleneck.

Part 2 — Log Levels That Mean Something

// A level is a decision about who should be woken up. Pick it that way.
log.fatal({ err }, "cannot start");     // process is dying. Page someone.
log.error({ err }, "unhandled error"); // a BUG. Someone must look.
log.warn({ err }, "upstream retry");   // degraded but handled. Watch trends.
log.info({ orderId }, "order created");// business events worth an audit trail.
log.debug({ query }, "executing");     // development detail. Off in prod.
log.trace({ chunk }, "stream chunk");  // firehose. Almost never enabled.

// The discipline that keeps alerting useful: ERROR means a human must act.
// If 404s and validation failures are logged at error level, your error rate
// is dominated by users typing bad URLs, alerts become noise, and the one
// real incident is invisible in the volume. This is the single most common
// reason teams stop trusting their dashboards.
//
// Expected-but-notable → warn. Bugs → error. That maps exactly onto the
// operational/programmer error distinction from the errors lesson.

// Sampling high-volume events keeps cost down without losing signal:
if (Math.random() < 0.01) log.info({ path }, "cache hit");   // 1%
// Always log 100% of errors; sample the successes. Cardinality is what
// makes log storage expensive, and successes are where the volume is.

// Make level runtime-changeable so you can raise verbosity during an
// incident without a deploy:
process.on("SIGUSR2", () => {
  log.level = log.level === "debug" ? config.LOG_LEVEL : "debug";
  log.info({ level: log.level }, "log level changed");
});

Part 3 — Correlation: Following One Request

// A single user action can touch six services. Without a shared id, you have
// six sets of logs and no way to line them up.

import { AsyncLocalStorage } from "node:async_hooks";
const als = new AsyncLocalStorage();

app.use((req, res, next) => {
  const requestId = req.headers["x-request-id"] ?? randomUUID();
  const traceId   = req.headers["x-trace-id"]   ?? requestId;
  res.setHeader("x-request-id", requestId);
  // Every log inside this async context inherits these fields automatically.
  als.run({ requestId, traceId }, () => next());
});

export function logger() {
  const store = als.getStore();
  return store ? log.child(store) : log;      // child() binds the fields
}

logger().info({ orderId }, "order created");
// → includes requestId and traceId with no argument threading at all.

// Propagate the ids on every outbound call, or the chain breaks at the first
// hop and correlation stops exactly where it gets interesting:
await fetch(url, {
  headers: {
    "x-request-id": randomUUID(),                 // new id for THIS hop
    "x-trace-id": als.getStore()?.traceId,        // same trace end to end
  },
});
// requestId identifies one hop; traceId identifies the whole user action.
// Keeping both lets you ask "what happened in this service" and "what
// happened overall" without conflating them.

// AsyncLocalStorage is the right tool specifically here: log correlation is
// cross-cutting, so threading a context parameter through every function
// would be pure noise. For business dependencies, prefer explicit passing —
// implicit context is action at a distance and gets hard to test.
Log the request id back to the client. Returning it in a response header and in error bodies turns "the site was broken this morning" into a single identifier you can search. It costs nothing and is the difference between reproducing a bug from a vague description and reading the exact trace.

Part 4 — The Three Pillars

// Each answers a different question. Using one for another's job is where
// observability budgets get burned.
//
// LOGS    — "what happened in this specific case?"
//           High detail, high cost per event, queryable after the fact.
//           Best for debugging a known incident.
//
// METRICS — "how is the system behaving overall, right now?"
//           Cheap aggregates, retained long, ideal for dashboards and
//           alerts. Cannot explain a single request.
//
// TRACES  — "where did the time go in this request, across services?"
//           A tree of timed spans. Best for latency and dependency problems
//           in distributed systems.
//
// Practical rule: alert on METRICS, diagnose with TRACES, confirm with LOGS.
// Alerting on log patterns is fragile (wording changes break it) and
// expensive (querying raw logs at alert frequency).

import client from "prom-client";
client.collectDefaultMetrics();              // event loop lag, heap, GC, fds

const httpDuration = new client.Histogram({
  name: "http_request_duration_seconds",
  help: "Request duration",
  labelNames: ["method", "route", "status"],
  buckets: [0.01, 0.05, 0.1, 0.5, 1, 2, 5],
});

app.use((req, res, next) => {
  const done = httpDuration.startTimer();
  res.on("finish", () => {
    // req.route.path, NOT req.path — see the cardinality warning below.
    done({ method: req.method, route: req.route?.path ?? "unknown",
           status: res.statusCode });
  });
  next();
});

app.get("/metrics", async (req, res) => {
  res.set("content-type", client.register.contentType);
  res.end(await client.register.metrics());
});

// CARDINALITY IS THE TRAP. A label with unbounded values — user id, order
// id, raw path with parameters — creates a separate time series per value.
// A million users becomes a million series and takes down your metrics
// backend. Use the ROUTE PATTERN ("/orders/:id"), never the concrete path.
// High-cardinality data belongs in logs and traces, never in metric labels.

Part 5 — What to Measure: RED and USE

// RED — for request-driven SERVICES (what your API needs):
//   Rate      — requests per second
//   Errors    — failed requests per second (and as a ratio)
//   Duration  — latency distribution
//
// USE — for RESOURCES (pools, queues, CPU, memory):
//   Utilization — % of time busy
//   Saturation  — queued work waiting
//   Errors      — resource-level failures
// The connection-pool exhaustion from the databases lesson is a saturation
// metric: pool wait time is high while CPU is low.

// PERCENTILES, NOT AVERAGES. This is the most important measurement idea
// here. With 99 requests at 10ms and 1 at 5000ms, the mean is ~60ms — which
// describes NO actual request and hides the outage. p50 tells you the
// typical experience, p99 tells you the worst experience users actually
// have, and p99 is where the queueing, GC pauses, and lock contention show
// up first. Alert on p99, not the mean.
//
// A caveat worth knowing: percentiles do not average across instances. You
// cannot take the p99 of ten pods and average them; you need histograms
// aggregated server-side (which is why Prometheus histograms use buckets).

// The four golden signals (Google SRE) are RED plus saturation, and are a
// good default dashboard:
//   latency · traffic · errors · saturation

// Node-specific metrics that matter and are easy to miss:
//   • EVENT LOOP LAG — the single best health indicator for a Node process.
//     Rising lag means something is blocking the loop, and every request
//     suffers regardless of what it does.
//   • heap used vs total — a steadily rising floor across GC cycles is a leak
//   • active handles/requests — leaked sockets, timers, or fds
//   • GC pause duration — long pauses show up directly in your p99

Part 6 — Alerts Worth Waking Up For

// Alert on SYMPTOMS users feel, not on causes:
//   ✅ "p99 latency > 2s for 5 minutes"          — users are waiting
//   ✅ "error rate > 1% for 5 minutes"           — users see failures
//   ✅ "readiness failing on >30% of pods"       — capacity is going
//   ❌ "CPU > 80%"                               — maybe it is fine
//   ❌ "a single request failed"                 — noise
//
// Cause-based alerts fire when nothing is wrong (high CPU on a batch job)
// and stay silent when something is (a memory leak with low CPU). Symptom
// alerts fire when users are affected, which is the point.

// Every alert needs a DURATION so transients do not page anyone:
//   for: 5m         — sustained, not a blip
// and a RUNBOOK link answering: what does this mean, what do I check first,
// what are the likely causes, how do I mitigate. An alert with no runbook
// is a 3am puzzle.

// SLOs make the trade-off explicit and turn alerting into a budget:
//   "99.9% of requests succeed in under 500ms over 30 days"
//   → an error budget of 0.1% ≈ 43 minutes per month
// Burn-rate alerts fire when you are consuming that budget too fast, which
// scales the urgency to the actual impact: a fast burn pages immediately, a
// slow burn opens a ticket. That is far better than a fixed threshold that
// is either too noisy or too quiet depending on traffic.

// Health endpoints (from the config lesson) feed this:
//   /health/live  → liveness: is the process wedged? (restart)
//   /health/ready → readiness: can it serve? (route around)
// Never put dependency checks in liveness, or a database blip restarts
// every pod simultaneously.

Interview Questions

Beginner: Why is structured logging better than string interpolation?

Because a log line is read by machines far more often than by people, and structured logs are built for machines.

  log.info(`User ${userId} placed order ${orderId} for $${total}`);      // a string
  log.info({ userId, orderId, total, event: "order.placed" }, "order placed");   // fields

With interpolation, every question you later want to ask requires parsing prose with regular expressions — "all orders for this user", "average order value", "errors per endpoint". The regexes are fragile: someone rewords the message and every query and alert built on it silently stops matching.

Structured logs, emitted as JSON with named fields, can be filtered, aggregated and joined directly by a log platform: userId = 42, group by event, percentile of durationMs. The message text can change freely without breaking anything.

It also enables the practices that make logs useful in production. A request or trace ID attached to every line via a child logger lets you pull out everything one request did across services. Redaction can be applied by field name — never log password or authorization — which is impossible with free text. And errors can be serialised with their stack and cause rather than flattened into a string.

Performance matters too: libraries such as pino serialise JSON extremely quickly and can move log processing off the main thread, whereas formatting strings synchronously on every request adds up. Pretty-printing belongs in development tooling, not in production output.

Beginner: What are the three pillars of observability and what does each answer?

Logs answer "what exactly happened?" They are detailed, timestamped records of discrete events — an order placed, an exception with its stack trace, a payment declined with the provider's reason. Logs are the richest in detail and the most expensive to store and query at volume, which makes them best for investigating a specific incident once you know roughly where to look.

Metrics answer "how much, how often, and is it getting worse?" They are numeric measurements aggregated over time — request rate, error rate, latency percentiles, queue depth, memory. They are cheap to store because they are pre-aggregated, and they are what dashboards and alerts are built on. Metrics tell you that something is wrong, quickly, without telling you why.

Traces answer "where did the time go?" A trace follows a single request across every service and operation it touches, as a tree of timed spans — the API handler, the database query, the call to the payment service, the cache lookup. That is the only pillar that shows how a request moved through a distributed system, and it is how you find which of eight downstream calls made a request slow.

The real value comes from correlating them. The usual workflow is: an alert fires on a metric, you open traces around that time to find the slow or failing operation, and you use the trace ID to pull the exact log lines for that request. OpenTelemetry provides one standard for all three, which is what makes that correlation practical.

Mid: What is cardinality and why does it matter for metrics?

Cardinality is the number of unique combinations of label values for a metric. Every distinct combination is stored as a separate time series.

A request-count metric labelled by method (5 values), route (50) and status (10) can produce up to 2,500 series. That is manageable. Add a userId label with a million users and it becomes billions of potential series.

High cardinality causes real failures. Storage and memory in the metrics system grow with every series, so costs explode, often billed per series. Queries slow dramatically because they must scan huge numbers of series. And metrics systems commonly enforce series limits, so a single high-cardinality label can cause metrics to be dropped, or knock over a self-hosted Prometheus — taking your dashboards and alerts down precisely when you need them.

The usual culprits are identifiers that look harmless as labels: user IDs, request IDs, session IDs, email addresses, and raw URLs containing IDs, where /orders/1, /orders/2 and so on each become a separate series. Timestamps and full error messages are similar.

The rules: keep labels to bounded sets of values; use the route template /orders/:id rather than the actual path; bucket status codes if needed. And put high-cardinality detail where it belongs — in logs and traces, which are designed to hold per-request data — rather than in metrics, which are designed for aggregates.

Mid: Why alert on p99 rather than average latency?

Because the average hides exactly the users who are suffering.

Latency distributions are heavily skewed. Most requests are fast — cache hits, simple reads — and a small tail is slow. Suppose 98% of requests take 50ms and 2% take 5 seconds. The average is about 150ms, which looks healthy. Meanwhile one request in fifty is taking five seconds, and the average barely moved.

The p99 is the latency that 99% of requests are faster than, so it looks directly at the tail. In the example it would read around 5 seconds, which is the truth.

The tail matters more than intuition suggests, for two reasons. First, tail latency is common per user, not rare: a single page load may make dozens of requests, so the chance that at least one of them hits the p99 is high — the slow path is something most users experience regularly. Second, the tail is often where real problems appear first: lock contention, a slow query for a particular account shape, garbage-collection pauses, a saturated thread pool.

Averages also mask shifts in the mix. If traffic shifts toward cheap requests, the average improves even as the slow path gets worse.

In practice: alert on p95 or p99 per route, with enough traffic to be statistically meaningful — a p99 over twenty requests is noise. Better still, alert on SLO burn rate, such as "the share of requests over 500ms is consuming the error budget too fast", which ties the alert to user impact and reduces false alarms. And never average percentiles across instances; aggregate histograms instead.

Senior: Users report intermittent slowness; dashboards look normal. How do you investigate?

"Dashboards look normal" is usually a measurement problem, so I would start by questioning the measurements rather than the reports. First, check whether the dashboards show averages — intermittent slowness affecting a minority of requests is exactly what a mean hides, and p99 or p99.9 often tells a completely different story. Second, check aggregation scope: a global view can hide one bad pod, one slow shard, or one region, so I would break the latency down by instance, route, customer, and dependency, since intermittent almost always means "affecting a subset" rather than "randomly distributed". Third, look for periodicity — correlating slow periods with deploys, cron jobs, backups, cache expiry waves, or GC pauses often identifies it immediately. Node-specific candidates: event loop lag spikes from synchronous work, garbage collection pauses, and connection pool saturation, all of which produce user-visible latency with unremarkable CPU. Fourth, if traces exist I would sample slow requests specifically rather than randomly, since uniform sampling mostly captures fast ones; tail-based sampling is designed for this. If none of that resolves it, the gap is instrumentation, and I would add what is missing — per-dependency timings, queue depths, pool wait time — because "we cannot see it" is itself an actionable finding. Throughout, I would treat the user reports as ground truth: if monitoring disagrees with users, monitoring is wrong.

Senior: Design observability for a new service. What do you instrument before launch?

Before launch I want enough to answer "is it healthy" and "why is it not" without shipping a change first. Minimum: RED metrics per route with route-pattern labels and histogram buckets chosen around the latency I expect; structured logs with request and trace ids propagated inbound and outbound; distributed tracing on external calls; and Node runtime metrics, especially event loop lag, heap trend, and GC pause duration. Liveness and readiness endpoints, with dependency checks in readiness only. Then explicit SLOs, because they determine what alerts should exist at all — typically availability and latency objectives with burn-rate alerts, so urgency scales to actual budget consumption rather than to a fixed threshold that is wrong at some traffic level. Every alert gets a runbook before launch, since the alert is useless to whoever is paged without one. On cost, which teams underestimate: sample successful requests aggressively while keeping all errors, set log retention deliberately, and keep high-cardinality data out of metrics. The test I would apply before calling it done is a tabletop exercise — pick three plausible failures such as a slow dependency, a memory leak, and a bad deploy, and confirm that existing signals would both detect each one and localize it. Any failure I cannot see is a gap to close before launch, not after the first incident.

🏋️ Graded Exercises

1 (easy): Convert to structured logging: console.log("Order " + id + " failed for user " + userId)
Solution 
log.error({ orderId: id, userId }, "order failed");
// Constant message, values as fields. Now queryable by orderId or userId,
// and all "order failed" events group together for counting — neither of
// which works when the values are embedded in the string.
2 (easy): Why is user_id a bad metric label but a good log field?
Solution 
// Metrics store one time series per label-value combination. A million
// users means a million series — memory exhaustion in the metrics backend,
// which takes down monitoring exactly when you need it.
httpRequests.inc({ route: "/orders/:id", status: 200 });   // ✅ bounded
httpRequests.inc({ userId: 12345 });                       // ❌ unbounded

// Logs are stored per event and indexed for search, so high-cardinality
// fields are exactly what they are designed for:
log.info({ userId, orderId }, "order created");            // ✅
// Rule: metrics answer "how many / how fast" in aggregate; logs answer
// "which one".
3 (medium): Implement request-id propagation with AsyncLocalStorage so all logs in a request carry it.
Solution 
import { AsyncLocalStorage } from "node:async_hooks";
import { randomUUID } from "node:crypto";

const als = new AsyncLocalStorage();
const base = pino({ level: config.LOG_LEVEL });

export function logger() {
  const store = als.getStore();
  return store ? base.child(store) : base;
}

app.use((req, res, next) => {
  const requestId = req.headers["x-request-id"] ?? randomUUID();
  const traceId = req.headers["x-trace-id"] ?? requestId;
  res.setHeader("x-request-id", requestId);
  als.run({ requestId, traceId }, () => next());
});

// Anywhere, at any depth, with no parameter threading:
logger().info({ orderId }, "order created");

// And on outbound calls, or the trace stops here:
await fetch(url, { headers: { "x-trace-id": als.getStore()?.traceId } });
4 (medium): Add a Prometheus histogram for request duration with correct labels.
Solution 
const httpDuration = new client.Histogram({
  name: "http_request_duration_seconds",
  help: "HTTP request duration in seconds",
  labelNames: ["method", "route", "status"],
  buckets: [0.005, 0.01, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});

app.use((req, res, next) => {
  const end = httpDuration.startTimer();
  res.on("finish", () => {
    end({
      method: req.method,
      route: req.route?.path ?? "unmatched",   // PATTERN, not req.path
      status: res.statusCode,
    });
  });
  next();
});

// Two details that matter:
// • req.route is only populated AFTER routing, which is why it is read
//   inside the finish handler rather than before next().
// • Falling back to "unmatched" rather than req.path keeps 404 scanning
//   traffic from creating a series per probed URL — otherwise an attacker
//   scanning your site can blow up your metrics cardinality deliberately.
// Buckets should bracket your SLO threshold so the percentile near it is
// accurate; histogram precision comes from bucket placement.
5 (hard): Design alerts for an API with a 99.9%/500ms SLO. Explain each choice.
Solution 
// SLO: 99.9% of requests succeed within 500ms over 30 days.
// Error budget: 0.1% ≈ 43 minutes of full unavailability per month.

// 1. FAST BURN — page immediately.
//    Condition: 14.4x burn rate over 1h (and 5m, to confirm it is current)
//    Meaning: at this rate the entire month's budget is gone in ~2 days.
//    Rationale: severe and current, worth waking someone.

// 2. SLOW BURN — ticket, do not page.
//    Condition: 6x burn rate over 6h (and 30m)
//    Meaning: budget exhausted in ~5 days. Real, but not a 3am problem.

// 3. LATENCY SLO burn, measured the same way on the 500ms threshold — with
//    histogram buckets placed so 0.5s is a bucket boundary, or the
//    percentile near the threshold is an interpolation rather than a fact.

// 4. READINESS: >30% of pods failing readiness for 5m → page.
//    A capacity symptom that precedes user-visible errors.

// Why burn rate rather than a static threshold: a fixed "error rate > 1%"
// alert is simultaneously too noisy at low traffic (three failed requests
// out of 200) and too quiet at high traffic (1% of a million requests is a
// major incident that never crosses the line). Burn rate normalizes against
// the budget, so severity tracks actual user impact.
// The dual-window (1h AND 5m) requirement prevents an alert firing on an
// hour-old spike that has already resolved.

// Deliberately NOT alerts: CPU, memory, disk — causes, not symptoms. They
// belong on dashboards for diagnosis, and only become alerts where they
// predict imminent failure with no other signal (disk filling).
// Every alert links a runbook: what it means, first checks, likely causes,
// mitigation.
6 (hard): A service logs 50GB/day, mostly at info level, and the bill is unsustainable. Reduce it without losing debuggability.
Solution 
// Measure before cutting — find the top talkers by message and by service:
//   which constant messages produce the most volume?
// Usually a handful of events dominate, and they are rarely the useful ones.

// 1. SAMPLE SUCCESSES, KEEP ALL ERRORS. The highest-volume events are
//    successful requests, and they are individually the least informative.
if (res.statusCode >= 400 || Math.random() < 0.01) {
  logger().info({ route, status, ms }, "request completed");
}
// Aggregate behaviour is already covered by metrics — that is precisely the
// division of labour between the pillars, and it is what makes this safe.

// 2. REMOVE LOGS THAT DUPLICATE METRICS. "request completed" at 100% is
//    a metric wearing a log's clothing, at ~1000x the storage cost.

// 3. MOVE DEBUG DETAIL BEHIND A RUNTIME SWITCH. Ship at info, expose a
//    SIGUSR2 toggle (or a per-request `x-debug` header for allowlisted
//    callers) so verbosity is available during an incident without paying
//    for it continuously.

// 4. TIERED RETENTION. Errors and audit events: 90 days. Info: 7 days.
//    Debug: 24 hours. Most log spend is retention of data nobody queries
//    after the first day.

// 5. DROP REDUNDANT FIELDS. Full request headers, entire response bodies,
//    and stack traces on expected 4xx errors are large and rarely read.

// 6. TAIL-BASED TRACE SAMPLING for the diagnosis path: keep traces for slow
//    and failed requests, sample the rest at 1%. This preserves the ability
//    to debug the cases that matter while cutting the bulk.

// What NOT to do: raise the global level to warn. It looks like an easy 90%
// saving, but it removes the business-event trail (order created, payment
// captured) that incident reconstruction and audits depend on, and you
// discover the loss only when you need it. Sampling preserves
// representative coverage; blanket level-raising creates blind spots.

🎯 Key Takeaways

  • Structured logs with constant messages and variables as fields are queryable; interpolated strings are not.
  • Use an async logger — console.log blocks the event loop under production load.
  • Log level is a decision about whether a human must act; logging expected failures as errors destroys alerting.
  • Propagate request and trace ids inbound and outbound, and bind them with AsyncLocalStorage so correlation needs no argument threading.
  • Logs, metrics, and traces answer different questions: alert on metrics, diagnose with traces, confirm with logs.
  • Cardinality is the metrics trap — never label with user ids or raw paths; use route patterns.
  • Alert on p99 rather than averages, and remember percentiles cannot be averaged across instances.
  • Alert on user-visible symptoms, not on causes like CPU, and give every alert a duration and a runbook.
  • SLO burn-rate alerts scale urgency to real impact where static thresholds are wrong at some traffic level.
  • Event loop lag is the single best health signal for a Node process.
  • Logs are read by machines far more than people.
  • Structured fields can be filtered and aggregated; interpolated strings need fragile regexes.
  • Attach a request or trace ID to every log line.
  • Redact sensitive fields by name.
  • Logs say what happened; metrics say how much and whether it is worsening; traces say where time went.
  • Metrics detect problems cheaply; traces and logs explain them.
  • Correlation through trace IDs is where the value lies.
  • Every unique label combination is a separate time series.
  • High cardinality raises cost, slows queries and can drop metrics.
  • Keep per-request detail in logs and traces, not metric labels.
  • Averages hide the tail users actually experience.
  • Pages making many requests make p99 latency common per user.
