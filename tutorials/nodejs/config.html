Configuration & Secrets Production Node

What you'll master: configuration as a first-class concern — validating the entire environment at startup so misconfiguration fails immediately, the twelve-factor model and where it stops being enough, secret storage and rotation, and feature flags as a deployment-decoupling tool. Prerequisites: Security, Process, Environment & CLI.

Part 1 — Config Comes From the Environment

// The twelve-factor rule: strict separation of config from code. Anything
// that DIFFERS between environments is config — database URLs, API keys,
// log levels, feature flags, timeouts, port numbers.
//
// The practical test: could this repository be open-sourced right now
// without leaking anything? If not, config and code are entangled.

// ❌ Config selected by branching on the environment name:
const dbUrl = process.env.NODE_ENV === "production"
  ? "postgres://prod-host/app"       // a production hostname in git
  : "postgres://localhost/app";
// Adding a staging environment means editing code and redeploying. Worse,
// the set of environments is now hardcoded, so every new one touches this
// file — and the production URL is committed forever.

// ✅ One variable per setting, supplied by the environment:
const dbUrl = process.env.DATABASE_URL;
// The code is identical everywhere; only the environment differs. That is
// what makes the artifact you tested the artifact you ship.

// NODE_ENV deserves specific care: it is a well-known value that libraries
// (Express, React) branch on for optimizations. Use it ONLY for that, and
// never invent extra values like "staging" — libraries check for exactly
// "production" and a different string silently disables optimizations. Use
// a separate APP_ENV for your own environment naming.

// Precedence, highest first — a predictable order matters more than which:
//   1. explicit CLI flags
//   2. environment variables
//   3. a .env file (local development only, NEVER committed)
//   4. defaults in code (only for non-secret, safe-by-default values)
// Node 20.6+ loads .env natively: `node --env-file=.env server.js`,
// so dotenv is no longer needed for the common case.

Part 2 — Validate the Whole Environment at Startup

// This is the highest-value practice in the lesson: turn every possible
// misconfiguration into a startup crash rather than a runtime surprise.
import { z } from "zod";

const Env = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url(),
  JWT_SECRET: z.string().min(32),          // ← length is a security control
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
  REQUEST_TIMEOUT_MS: z.coerce.number().int().positive().default(30_000),
});

const parsed = Env.safeParse(process.env);
if (!parsed.success) {
  // Print WHICH variables are wrong — a bare "invalid config" wastes an hour.
  console.error("Invalid configuration:");
  for (const issue of parsed.error.issues) {
    console.error(`  ${issue.path.join(".")}: ${issue.message}`);
  }
  process.exit(1);                          // fail FAST and LOUD
}
export const config = Object.freeze(parsed.data);

// Why this pays for itself immediately:
//   • env vars are ALWAYS strings — z.coerce turns PORT into a real number,
//     so you never accidentally compute "3000" + 1 === "30001"
//   • a missing DATABASE_URL kills the process at boot, in the deploy, where
//     someone is watching — instead of on the first request that needs it,
//     at 3am, as a confusing connection error
//   • defaults live in ONE place, not scattered as `?? 3000` across files
//   • the schema documents every setting the service accepts
//   • freezing prevents accidental mutation at runtime
//
// Import `config` everywhere; do not read process.env outside this module.
// That single rule makes the configuration surface greppable and testable.
Fail fast at startup, not lazily at first use. A service that boots with a missing secret and only fails when a specific endpoint is first called will pass its health check, receive traffic, and then break for real users — often long after the deploy that caused it, which makes the connection hard to see. Validating everything before listen() means a bad config never becomes a running instance, and your orchestrator's rollout halts on its own.

Part 3 — Where Secrets Actually Live

// Ranked by how much they protect you:
//
// 1. A SECRET MANAGER (AWS Secrets Manager, Vault, GCP Secret Manager)
//    Encrypted at rest, access-controlled per identity, audit-logged, and
//    rotatable without a deploy. This is the right answer for production.
//
// 2. Platform-injected environment variables (Kubernetes Secrets, ECS task
//    definitions). Good, with caveats: k8s Secrets are base64-ENCODED, not
//    encrypted, unless you enable encryption at rest, and anyone who can
//    read the resource or exec into the pod can read them.
//
// 3. An encrypted file decrypted at boot (SOPS, sealed-secrets). Workable
//    for small teams; the decryption key becomes the thing to protect.
//
// 4. A plain .env file. Local development only. Add it to .gitignore before
//    you create it, not after.
//
// ❌ Never: secrets in the repository, in Docker image layers (they persist
//    in the layer even if a later RUN deletes them — `docker history` shows
//    them), in CI logs, in error messages, or in client-side bundles.

// Loading from a manager at startup, cached for the process lifetime:
async function loadSecrets() {
  const client = new SecretsManagerClient({});
  const res = await client.send(new GetSecretValueCommand({ SecretId: "prod/api" }));
  return JSON.parse(res.SecretString);
}
// Fetch once at boot rather than per request: per-request calls add latency,
// cost money, and make the secret manager a hard dependency of every request
// instead of only of startup.

// ROTATION must be designed for, not bolted on. The requirement is that two
// valid secrets exist simultaneously during the rollover window:
const JWT_SECRETS = [config.JWT_SECRET_CURRENT, config.JWT_SECRET_PREVIOUS];
function verifyToken(token) {
  for (const secret of JWT_SECRETS) {
    try { return jwt.verify(token, secret, { algorithms: ["HS256"] }); }
    catch { /* try the next one */ }
  }
  throw new AppError("Invalid token", { status: 401 });
}
// Sign with CURRENT, accept CURRENT or PREVIOUS. Rotating a single-value
// secret invalidates every live token at once — every user logged out
// simultaneously, which is why teams avoid rotating and then never rotate.
// Supporting two values is what makes rotation routine instead of an event.

Part 4 — Config Shape and Typed Access

// Group flat env vars into a structured object at the boundary, so calling
// code reads domain concepts rather than variable names:
export const config = Object.freeze({
  env: parsed.data.NODE_ENV,
  isProduction: parsed.data.NODE_ENV === "production",
  http: {
    port: parsed.data.PORT,
    requestTimeoutMs: parsed.data.REQUEST_TIMEOUT_MS,
  },
  db: {
    url: parsed.data.DATABASE_URL,
    poolMax: parsed.data.DB_POOL_MAX,
  },
  auth: { jwtSecret: parsed.data.JWT_SECRET },
});
// config.db.poolMax reads better than process.env.DB_POOL_MAX and is typed.

// Make secrets hard to leak accidentally. A config object logged wholesale
// during debugging is a very common leak path:
export function redactedConfig() {
  return { ...config, auth: { jwtSecret: "[redacted]" },
           db: { ...config.db, url: config.db.url.replace(/:[^:@]+@/, ":***@") } };
}
log.info(redactedConfig(), "starting");     // safe to log on boot
// Logging effective configuration at startup is genuinely useful — it tells
// you what the process actually believes — but only in redacted form.

// Per-environment DEFAULTS are fine; per-environment BRANCHES are not:
//   ✅ LOG_LEVEL defaults to "debug" locally and "info" in production,
//      because the default is data
//   ❌ `if (isProduction) { useRealPaymentProvider() }`, because now the
//      code path you test is not the code path you ship
// The distinction: config selects VALUES, not CODE PATHS. Where behaviour
// genuinely must differ, inject the implementation rather than branching
// deep inside business logic.

Part 5 — Feature Flags

// Feature flags decouple DEPLOY from RELEASE: ship code dark, turn it on
// independently, and turn it off without a rollback.
if (await flags.enabled("new-checkout", { userId })) {
  return newCheckout(req);
}
return legacyCheckout(req);

// Four kinds, with genuinely different lifetimes — conflating them is the
// usual source of flag debt:
//   RELEASE     — hide unfinished work. DELETE once shipped. Days to weeks.
//   EXPERIMENT  — A/B tests. Delete when the experiment concludes.
//   OPS         — kill switches for expensive features under load. Permanent
//                 by design, and legitimately so.
//   PERMISSION  — per-plan entitlements. Not really a flag; that is
//                 authorization and belongs in your domain model.

// Costs to be honest about:
//   • every boolean flag doubles the number of code paths, and they
//     multiply: three flags = eight combinations, of which your tests
//     probably cover two
//   • stale flags are permanent complexity — an unremoved release flag is
//     dead code with a runtime cost and a misleading name
//   • flag state is CONFIG, so a flag service outage must fail to a safe,
//     explicit default rather than throwing

const enabled = await flags.enabled("new-checkout", { userId })
  .catch(() => false);      // ← fail closed for new behaviour
// Fail-closed for new features, fail-OPEN for kill switches (a flag service
// outage should not disable a feature that is working). Deciding the
// direction per flag is the actual design work.

// Give every release flag an owner and an expiry date at creation, and
// review them on a schedule. Flags that outlive their purpose are the most
// common form of accumulated complexity in mature services.

Part 6 — Config in Containers and CI

// Build ONE image; configure it per environment. The artifact you tested
// must be bit-for-bit the artifact you promote.
// ❌ docker build --build-arg API_KEY=...    (baked into the image layer)
// ✅ docker run -e API_KEY=...               (supplied at runtime)

// Health checks should reflect config validity:
app.get("/health/live",  (req, res) => res.json({ ok: true }));   // process up
app.get("/health/ready", async (req, res) => {                     // can serve
  const checks = await Promise.allSettled([pingDb(), pingRedis()]);
  const ok = checks.every((c) => c.status === "fulfilled");
  res.status(ok ? 200 : 503).json({ ok });
});
// Liveness = "am I alive" (restart me if not). Readiness = "can I serve
// traffic" (route around me if not). Conflating them is a classic outage:
// if a failing dependency makes LIVENESS fail, the orchestrator restarts
// every pod in a loop, turning a dependency blip into a full outage.

// In CI, keep secrets out of logs and out of forks:
//   • use the platform's secret store, never plaintext in workflow files
//   • never `echo` a secret, even while debugging (CI masks known values,
//     but transformations like base64 defeat the masking)
//   • pull-request builds from forks must not receive production secrets
//   • rotate anything a CI job could have exposed

// Local development should be one command:
//   docker compose up   — with a committed .env.example listing every
//   required variable (names and dummy values, never real ones).
// .env.example doubles as documentation and as the checklist for what a new
// environment needs.

Interview Questions

Beginner: Why should configuration come from the environment rather than committed files?

So one build artifact runs unchanged in every environment — the thing you tested is the thing you ship, with only the environment differing. It also keeps credentials out of version control, where they would be permanently recoverable by anyone with repository access, and it lets a new environment be created without editing and redeploying code. The practical test is whether the repository could be made public right now without leaking anything.

Beginner: Why validate environment variables at startup?

Because otherwise a misconfiguration is discovered at the moment some code path first needs it, which may be hours after the deploy and in front of real users. Validating everything before the server starts listening turns that into an immediate, loud startup failure during the rollout, where someone is already watching and the orchestrator will halt the deployment automatically. Validation also coerces types — environment variables are always strings — and gives one place where every setting and its default is documented.

Mid: How do you rotate a signing secret without invalidating every live session?

Support two secrets simultaneously: sign new tokens with the current secret while accepting either the current or the previous one during verification. Deploy the new secret as current and the old one as previous, wait longer than the maximum token lifetime so every token signed with the old secret has expired naturally, then remove the previous value. Without that overlap, rotation invalidates every outstanding token at once and logs out the entire userbase, which is precisely why teams defer rotation indefinitely and end up with secrets that have never been changed. Designing for two valid values is what makes rotation a routine operation instead of an incident.

Mid: What is wrong with if (process.env.NODE_ENV === "production") inside business logic?

It means the code path exercised by your tests is not the code path that runs in production, so the most important behaviour is the least tested. It also hides environment coupling deep in the call stack where it is hard to find, and it makes adding an environment a code change. The better pattern is to let configuration select values rather than code paths, and where behaviour genuinely must differ — a real payment provider versus a fake — inject the implementation at the composition root so the business logic is identical everywhere and the substitution is visible and testable.

Senior: Design configuration and secret management for a system of a dozen services across three environments.

I would start from a few invariants: one build artifact promoted across environments, no secrets in any repository or image, and every service failing fast on invalid configuration. Each service owns a schema module that validates its entire environment at startup and exports a frozen typed object, so the configuration surface is explicit, greppable, and testable per service rather than shared through a library that couples them. Non-secret configuration lives in the deployment manifests under version control, which gives review and history for things like timeouts and pool sizes. Secrets live in a managed store with per-service identities and least-privilege access, injected at runtime, with rotation supported by dual-value acceptance for anything used to sign or verify. Shared values that genuinely must agree across services — a JWT audience, a queue name — are the risky part, since duplicating them invites drift; I would generate them into manifests from one source rather than copying them by hand. For operations: audit logging on secret access, alerts on unusual retrieval patterns, a documented rotation runbook that has actually been executed at least once, and a committed .env.example per service so a new environment has a checklist. Where I would push back is on a central configuration service in the request path — it adds a runtime dependency for something needed only at startup, and its outage becomes everyone's outage. Fetch at boot, cache for the process lifetime, and let a restart pick up changes.

Senior: A team has accumulated 40 feature flags and is afraid to remove any. How do you address it?

The fear is reasonable — an unknown flag might be load-bearing — so I would replace guessing with data. First, instrument evaluation: log every flag check with its result and caller so that after a representative period you know which flags are still evaluated, which always return the same value, and which are never hit at all. That immediately partitions the set. Flags that always return one value in every environment are dead and can be inlined by deleting the branch, which is the safe majority. Flags never evaluated are dead code paths whose removal is even safer. Then classify what remains by intent: release flags should have been deleted at ship time and can be inlined; experiment flags belong to concluded experiments and follow the winning branch; operational kill switches are legitimately permanent and should be documented as such rather than counted as debt; entitlement checks should be moved out of the flag system into the authorization model where they belong. I would remove them incrementally, a few per release, so any surprise is attributable. Preventing recurrence matters more than the cleanup: every new release flag gets an owner and an expiry date at creation, a scheduled review lists expired ones, and inlining the flag is part of the definition of done for a feature rather than a follow-up ticket nobody picks up. The underlying point is that flags are inventory with a carrying cost — each one multiplies the state space and most are never revisited without a forcing function.

1 (easy): Write a schema validating PORT, DATABASE_URL, and LOG_LEVEL with sensible defaults.
Solution 
import { z } from "zod";

const Env = z.object({
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  DATABASE_URL: z.string().url(),                       // required, no default
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
});

const parsed = Env.safeParse(process.env);
if (!parsed.success) {
  console.error(parsed.error.issues.map((i) => `${i.path}: ${i.message}`).join("\n"));
  process.exit(1);
}
export const config = Object.freeze(parsed.data);
// DATABASE_URL has no default deliberately: a wrong default is worse than a
// missing value, because it fails somewhere far from the cause.
2 (easy): Why does const debug = process.env.DEBUG then if (debug) behave unexpectedly?
Solution 
// Environment variables are ALWAYS strings. DEBUG=false gives the string
// "false", which is truthy — so debug mode turns on when you set it off.
const Env = z.object({
  DEBUG: z.enum(["true", "false"]).default("false").transform((v) => v === "true"),
});
// Now config.DEBUG is a real boolean, and an unrecognized value like
// DEBUG=yes fails loudly at startup rather than silently meaning "on".
3 (medium): Write a redacted config view safe to log at startup.
Solution 
const SECRET_KEYS = /secret|token|password|key|credential/i;

export function redacted(obj) {
  return Object.fromEntries(Object.entries(obj).map(([k, v]) => {
    if (SECRET_KEYS.test(k)) return [k, "[redacted]"];
    if (typeof v === "string" && v.includes("://")) {
      return [k, v.replace(/\/\/[^:]+:[^@]+@/, "//***:***@")];   // strip creds
    }
    if (v && typeof v === "object") return [k, redacted(v)];      // recurse
    return [k, v];
  }));
}
log.info(redacted(config), "effective configuration");

// The URL branch matters: DATABASE_URL does not match the key pattern but
// embeds a password. Pattern-matching key NAMES alone misses credentials
// carried inside values — verify against real output rather than trusting
// the rule.
4 (medium): Implement dual-secret JWT verification supporting rotation.
Solution 
const Env = z.object({
  JWT_SECRET_CURRENT: z.string().min(32),
  JWT_SECRET_PREVIOUS: z.string().min(32).optional(),
});

export function sign(payload) {
  return jwt.sign(payload, config.JWT_SECRET_CURRENT, { expiresIn: "15m" });
}

export function verify(token) {
  const secrets = [config.JWT_SECRET_CURRENT, config.JWT_SECRET_PREVIOUS].filter(Boolean);
  for (const secret of secrets) {
    try {
      return jwt.verify(token, secret, { algorithms: ["HS256"] });
    } catch (err) {
      if (err.name === "TokenExpiredError") throw err;   // don't retry expiry
    }
  }
  throw new AppError("Invalid token", { status: 401 });
}
// Rotation procedure: move CURRENT into PREVIOUS, set a new CURRENT, deploy,
// wait longer than the token lifetime (15m here), then drop PREVIOUS.
// Re-throwing on expiry avoids pointlessly verifying an expired token
// against every secret and returning a misleading "invalid" error.
5 (hard): Design liveness and readiness endpoints, and explain what belongs in each.
Solution 
let ready = false;
let shuttingDown = false;

// LIVENESS: "is this process functioning?" Failing means RESTART ME.
// It must check ONLY the process itself — never dependencies.
app.get("/health/live", (req, res) => res.status(200).json({ ok: true }));

// READINESS: "should traffic be routed here?" Failing means ROUTE AROUND ME.
app.get("/health/ready", async (req, res) => {
  if (shuttingDown || !ready) return res.status(503).json({ ok: false });
  const results = await Promise.allSettled([
    withTimeout(db.query("SELECT 1"), 1000),
    withTimeout(redis.ping(), 500),
  ]);
  const ok = results.every((r) => r.status === "fulfilled");
  res.status(ok ? 200 : 503).json({ ok });
});

await warmUp();                    // migrations checked, pools connected
ready = true;

process.on("SIGTERM", () => { shuttingDown = true; /* then close */ });

// Why dependencies must NOT be in liveness: if the database has a brief
// outage and liveness fails, the orchestrator restarts every pod
// simultaneously. Restarts do not fix the database, but they do drop all
// in-flight requests, empty every cache and connection pool, and produce a
// thundering herd when the database recovers — converting a partial
// degradation into a total outage. Liveness answers "is this process
// wedged", nothing more.
// Failing readiness during shutdown is what drains traffic BEFORE
// server.close(), which is the other half of graceful shutdown.
6 (hard): A secret was committed to a public repository three months ago. Walk through the response.
Solution 
// PREMISE: the secret is compromised. Not "possibly" — public repositories
// are continuously scraped by automated scanners, and three months is
// effectively forever. Treat it as known-leaked.

// 1. ROTATE IMMEDIATELY. This is first, before investigation, before
//    cleanup. Everything else is secondary to invalidating the credential.
//    If rotation requires a deploy, do the deploy now.

// 2. ASSESS BLAST RADIUS. What did the credential grant? Query provider
//    audit logs for use from unknown IPs since the commit date. For a
//    database credential, look for unusual query volume or exports; for a
//    cloud key, for resource creation (crypto-mining is the common one) and
//    IAM changes.

// 3. DO NOT rely on history rewriting as the fix. Rewriting with filter-repo
//    or BFG is worth doing to stop re-leaking, but it does NOT undo the
//    exposure: the repo was cloned, cached by the platform, and indexed.
//    Forks retain the object. Rotation is the only real remedy.

// 4. CHECK FOR SIBLINGS. A commit that leaked one secret usually leaked
//    others, and the same value may be reused elsewhere. Scan the full
//    history with gitleaks or trufflehog rather than only the offending
//    commit.

// 5. TREAT AS AN INCIDENT if the credential touched user data — that carries
//    disclosure obligations, and the decision is not the engineer's alone.

// 6. PREVENT RECURRENCE:
//    • pre-commit secret scanning (gitleaks) so it fails locally
//    • server-side push protection so it cannot land even if bypassed
//    • .gitignore .env before the file is created; commit .env.example only
//    • short-lived, scoped credentials so a leak has a bounded window
//      instead of unlimited standing access — this is the structural fix
//
// The order matters: engineers instinctively start with cleaning history
// because it feels like undoing the mistake. It is the least useful step.
// Rotate first.

🎯 Key Takeaways

  • Configuration is anything that differs between environments — one artifact, many environments.
  • Validate the entire environment against a schema before listen(), so misconfiguration fails during the deploy rather than at 3am.
  • Environment variables are always strings; coerce explicitly or "false" will be truthy.
  • Read process.env in exactly one module and export a frozen typed config object.
  • Config should select values, not code paths — branching on NODE_ENV means shipping untested paths.
  • Secrets belong in a managed store injected at runtime, never in repositories, image layers, or CI logs.
  • Design rotation in from the start by accepting current and previous values — otherwise rotation logs everyone out and never happens.
  • Log effective configuration at startup, but only through an explicit redacted view.
  • Feature flags decouple deploy from release but multiply code paths — give each an owner and an expiry.
  • Liveness checks the process; readiness checks dependencies. Conflating them turns a dependency blip into a restart loop.
