REST API Design Building APIs

What you'll master: designing an HTTP API that clients can use correctly without asking you questions — resource modelling, the method semantics that actually carry guarantees (safety and idempotency), pagination that survives a growing dataset, versioning, and the idempotency-key pattern that makes retries safe for payments. Prerequisites: Express Fundamentals, HTTP Without Frameworks.

Part 1 — Resources, Not Procedures

// REST models NOUNS and uses HTTP methods as the verbs.
// ❌ RPC-over-HTTP wearing a REST costume:
POST /getOrders          POST /createOrder        POST /cancelOrderById
// ✅ resources + methods:
GET    /orders           GET  /orders/42
POST   /orders           PATCH /orders/42        DELETE /orders/42

// Why this is more than aesthetics: with verbs in the URL, every request is
// an opaque POST, so no intermediary can help you. With resources + methods,
// the whole stack understands your API for free:
//   • browsers/proxies/CDNs can CACHE GET responses
//   • load balancers can RETRY safe methods after a network blip
//   • crawlers, monitors, and API gateways can reason about it
//   • clients can guess the next endpoint correctly
// You are borrowing decades of infrastructure behaviour by conforming.

// Nesting expresses ownership, but stop at one level:
GET /orders/42/items          // ✅ items of THIS order
GET /orders/42/items/7/tax    // ❌ deep nesting is brittle and unreadable
GET /order-items/7            // ✅ promote it to a top-level resource

// Plural nouns, kebab-case, no trailing slash, no file extensions:
/order-items                  not /orderItems, /order_items, /orders.json
// Consistency matters more than which convention you pick — but pick one and
// enforce it in review, because clients hard-code these strings forever.

// Some operations genuinely are not CRUD. Model them as sub-resources rather
// than contorting them:
POST /orders/42/cancellation      // creates a cancellation
POST /users/7/password-reset      // creates a reset request
// This keeps the method honest (POST creates something) instead of inventing
// PATCH semantics that mean "run this procedure".

Part 2 — Safety and Idempotency (the Two Real Guarantees)

// SAFE      = does not modify state (so it can be cached and prefetched)
// IDEMPOTENT = doing it N times leaves the same state as doing it once
//              (so it can be RETRIED after a timeout)

// Method    Safe   Idempotent   Notes
// GET       yes    yes          never mutate in a GET — crawlers will find it
// HEAD      yes    yes          GET without a body
// PUT       no     YES          full replacement: same payload = same result
// DELETE    no     YES          deleting twice = still deleted (204 or 404)
// PATCH     no     no*          *depends on your patch semantics
// POST      no     NO           the reason double-submit creates two orders

// This table is not trivia — it decides what a client is ALLOWED to retry.
// A network timeout is ambiguous: the request may have succeeded with the
// response lost. For idempotent methods the client can safely retry. For
// POST it cannot, without help — which is exactly what Part 6 solves.

// PATCH bodies: two competing conventions, and you must document which.
PATCH /orders/42   { "status": "shipped" }          // merge-patch (common)
PATCH /orders/42   [{ "op": "replace", "path": "/status", "value": "shipped" }]
                                                    // JSON Patch (RFC 6902)
// Merge-patch's classic ambiguity: does "field": null mean "set to null" or
// "remove the field"? RFC 7386 says remove. If you do not decide and document
// this, clients will guess differently and you will get bug reports you
// cannot reproduce.

Part 3 — Status Codes That Carry Information

// Creation: return 201 with a Location header pointing at the new resource.
res.status(201).location(`/orders/${order.id}`).json(order);

// Deletion: 204 with NO body (the response must be empty), or 404 if absent.
res.status(204).end();

// Async work: 202 Accepted — "I took this, it is not done yet".
res.status(202).location(`/jobs/${job.id}`).json({ status: "pending" });

// Errors — return a MACHINE-READABLE body, not just a status:
res.status(422).json({
  error: "validation_failed",           // stable code clients can switch on
  message: "Order requires at least one item",   // human-readable, may change
  details: [{ field: "items", issue: "min_length", min: 1 }],
  requestId: req.ctx.id,
});
// The stable `error` code is the contract. If clients must parse `message`
// to branch, you can never reword an error string without breaking them.
// RFC 9457 (problem+json) standardizes this shape if you want an off-the-shelf
// format: type, title, status, detail, instance.

// 207/partial results, and the rule people get wrong: a 200 with
// {"success": false} in the body is an ANTI-PATTERN. It forces every client
// to parse bodies to detect failure, defeats proxy/CDN/monitoring behaviour,
// and silently breaks retry logic that keys on status. Let the status code
// be true.

Part 4 — Pagination, Filtering, Sorting

// Offset pagination — simple, and it degrades badly:
GET /orders?page=3&per_page=50        →  LIMIT 50 OFFSET 100
// Two real problems at scale:
//   1. Cost: OFFSET 1000000 makes the database walk and DISCARD a million
//      rows for every request. Deep pages get linearly slower.
//   2. Correctness: if a row is inserted while a user pages, every later page
//      SHIFTS — items are skipped or duplicated across pages.

// Cursor (keyset) pagination — the production answer:
GET /orders?limit=50&cursor=eyJpZCI6NDIsInRzIjoiMjAyNi0wNy0zMSJ9
// → WHERE (created_at, id) < ($ts, $id) ORDER BY created_at DESC, id DESC LIMIT 50
{
  "data": [ ... ],
  "next_cursor": "eyJpZCI6OTIs...",     // null when exhausted
}
// Constant cost regardless of depth (it seeks an index instead of counting),
// and stable under concurrent inserts because the cursor names a POSITION,
// not a count. The tie-breaker column (id) is mandatory: without it, rows
// sharing a timestamp are ordered nondeterministically and can be skipped.
// Encode the cursor (base64 JSON) to signal it is OPAQUE — clients must not
// construct or decode it, which keeps you free to change the implementation.

// Filtering and sorting — allowlist everything:
GET /orders?status=shipped&created_after=2026-01-01&sort=-created_at
const SORTABLE = new Set(["created_at", "total"]);   // ← never interpolate
// Passing a client string into ORDER BY is SQL injection with extra steps,
// and an unindexed sort column is a full table scan any user can trigger.
Total counts are optional and often expensive. SELECT COUNT(*) over a large filtered set can cost more than the page query itself, and it is the reason many "slow API" incidents trace back to pagination metadata rather than the data. Return has_more (fetch limit + 1 rows and check whether you got an extra) instead of a total, and offer an exact count only where a UI genuinely needs it — or return an estimate.

Part 5 — Versioning & Evolution

// URL versioning — most common, most operable:
/api/v1/orders        /api/v2/orders
// Visible in logs, trivially routable at the gateway, easy to cache
// separately. Purists object that the resource did not change, only its
// representation — but operability usually wins this argument.

// Header versioning — cleaner URLs, harder to debug:
Accept: application/vnd.example.v2+json
// You cannot paste it into a browser, and CDN cache keys must include the
// header or clients get the wrong version served from cache.

// The cheapest strategy is to VERSION LESS by making changes additively:
//   ✅ non-breaking: add a field, add an optional parameter, add an endpoint,
//      add a new enum value IF clients were told to tolerate unknown ones
//   ❌ breaking: remove/rename a field, change a type, tighten validation,
//      change defaults, change error codes, make an optional field required
// Clients must ignore unknown fields (say so in your docs) — that single rule
// is what makes additive evolution possible.

// When you must break: run both versions, instrument v1 usage per client,
// announce a deprecation window, and signal it in-band:
res.set("deprecation", "true");
res.set("sunset", "Wed, 31 Dec 2026 23:59:59 GMT");   // RFC 8594
// Then chase the top remaining callers directly. Removing an endpoint without
// per-client usage data is how you break someone's production on a Friday.

Part 6 — Idempotency Keys: Making POST Retry-Safe

// The problem: a client POSTs /payments, the network drops the RESPONSE.
// The client cannot know whether the charge happened. Retrying risks
// double-charging; not retrying risks losing a legitimate payment.

// The solution: the client generates a unique key and sends it.
POST /payments
Idempotency-Key: 8f14e45f-ea5c-4f2b-9c3a-1d9b2e7a6c50
{ "amount": 5000, "currency": "usd" }

// Server algorithm:
async function withIdempotency(key, requestHash, fn) {
  // 1. Atomically claim the key. The unique constraint is what makes this
  //    safe under CONCURRENT retries, not just sequential ones.
  const claimed = await db.insertIfAbsent("idempotency_keys", {
    key, request_hash: requestHash, status: "in_progress",
  });
  if (!claimed) {
    const existing = await db.get("idempotency_keys", key);
    // 2. Same key, DIFFERENT body = client bug. Fail loudly.
    if (existing.request_hash !== requestHash) {
      throw Object.assign(new Error("Key reused with different payload"), { status: 422 });
    }
    // 3. Still running = concurrent retry. Tell the client to wait.
    if (existing.status === "in_progress") {
      throw Object.assign(new Error("Request in progress"), { status: 409 });
    }
    return existing.response;          // 4. Replay the stored response
  }
  const response = await fn();
  await db.update("idempotency_keys", key, { status: "done", response });
  return response;
}

// The properties that make this correct:
//   • The key is CLIENT-generated, before the first attempt, and reused for
//     every retry of that same logical operation.
//   • Claiming is atomic (unique index), so two simultaneous retries cannot
//     both execute the work.
//   • The stored response is REPLAYED, so the retry sees what the original
//     would have returned.
//   • Keys expire (24h is typical) — this is a retry window, not a permanent
//     audit log.
// This is exactly how Stripe's API works, and it is the standard answer when
// an interviewer asks how to make a payment endpoint safe.

Interview Questions

Beginner: What is the difference between PUT and PATCH?

PUT replaces the entire resource with the representation you send. PATCH applies a partial modification — only the fields you include change.

The difference shows up in what happens to fields you leave out. With PUT, an omitted field is reset to its default or removed, because the body is the new resource. So a client that PUTs { "name": "Ada" } to a user with an email address will, strictly, remove the email. With PATCH, the same body changes only the name and leaves everything else untouched.

That is why PUT requires the client to have the complete current state, typically by fetching first — and why two clients editing different fields with PUT can overwrite each other's changes: each sends its own full copy, and the last write wins.

PUT is idempotent by definition: sending the same complete representation twice leaves the same result. PATCH is not guaranteed to be — an operation such as "append to this list" changes the result each time — though a merge-style patch that sets fields usually is.

PATCH also needs a defined format. JSON Merge Patch (application/merge-patch+json) is the simple one: send the fields to change, and null deletes a field. JSON Patch (application/json-patch+json) is a list of explicit operations — add, remove, replace, move, test — which is more powerful and supports conditional updates. For most APIs, PATCH with merge semantics is what clients actually want.

Beginner: Why should GET never modify state?

Because HTTP defines GET as a safe method, and the entire web infrastructure is built on the assumption that requesting a URL has no side effects.

That assumption is exercised constantly by things you do not control. Search engine crawlers follow every link they find. Browsers prefetch links they predict you will click. Link previews in Slack, email clients and messaging apps fetch URLs as soon as they are pasted. Caches and proxies may serve or replay GET responses. Retry logic in clients and load balancers retries GETs freely, precisely because they are supposed to be harmless.

So a GET /users/42/delete link or a GET /logout endpoint gets triggered by all of them. The classic stories are real: an admin panel whose delete links were all GETs, crawled by a search engine that dutifully deleted every record, and users logged out by their own browser prefetching the logout link.

It is also a security issue. A state-changing GET can be triggered by an attacker simply by embedding the URL in an image tag on any page the victim visits — <img src="https://bank.example/transfer?to=attacker"> — and the browser sends the victim's cookies with it. That is cross-site request forgery with no effort at all, and SameSite cookies only partly help.

The rule is simple: reads are GET; anything that creates, changes or deletes uses POST, PUT, PATCH or DELETE.

Mid: When does offset pagination break, and what replaces it?

Offset pagination — ?limit=20&offset=40, translating to LIMIT 20 OFFSET 40 — breaks in two distinct ways.

It gets slow at depth. The database cannot jump to row 100,000; it must find and discard the first 100,000 rows before returning the next twenty. Cost grows linearly with the offset, so early pages are fast and deep pages — reached by crawlers, exports and "load more" scrolling — become very slow and load the database heavily.

It gives wrong results when data changes. If a new record is inserted at the top while a user is paging through, every record shifts down one position, and the next page repeats the last item of the previous one. If a record is deleted, one is skipped entirely. For feeds, activity logs and anything written to continuously, that produces visible duplicates and silent gaps.

Cursor, or keyset, pagination replaces it. Instead of "skip N rows", the client says "give me the rows after this one", using the sort key of the last item it received:

  SELECT * FROM orders
  WHERE (created_at, id) < ($1, $2)          -- last row seen
  ORDER BY created_at DESC, id DESC
  LIMIT 20;

With an index on those columns, every page is equally fast regardless of depth, and inserts or deletes do not shift anything. Including a unique tiebreaker such as id is essential, or rows with identical timestamps are skipped or duplicated.

The API returns an opaque cursor — encoded, not a raw offset — so the implementation can change. The trade-off is that you lose "jump to page 50", which is rarely genuinely needed.

Mid: How do you evolve an API without versioning every change?

By distinguishing additive changes, which are safe, from breaking changes, which are not — and designing so that the overwhelming majority of changes are additive.

Safe changes include adding a new endpoint, adding an optional request field, adding a new field to a response, and adding a new value to an enum that clients are prepared to handle. None of them affect a client that ignores what it does not recognise.

Breaking changes include removing or renaming a field, changing a field's type or meaning, making an optional field required, changing error formats, and tightening validation on existing inputs.

The techniques that keep changes additive: never remove or rename — add the new field alongside the old, and populate both. Expect tolerant readers: document that clients must ignore unknown fields, so adding fields never breaks them. Deprecate explicitly with documentation and Deprecation and Sunset response headers, and measure actual usage of the old field before removing it. Use feature or capability negotiation for optional new behaviour rather than changing default behaviour.

A new version is then reserved for genuinely unavoidable breaks, and it is a real commitment: every version you publish is one you must maintain, test and eventually migrate clients away from.

The underlying principle is that a published API is a contract with clients you cannot redeploy. Contract tests against real consumer expectations catch accidental breaking changes before they ship.

Senior: Design a payments endpoint that is safe under client retries. Walk through the failure modes.

The core problem is that a timeout is ambiguous — the request may have succeeded with only the response lost — and POST is not idempotent, so a blind retry can double-charge. The solution is client-generated idempotency keys: the client creates a UUID before its first attempt and sends the same key on every retry of that logical operation. The server atomically claims the key with a unique index (atomicity matters because retries can be concurrent, not merely sequential), executes the charge, stores the response, and replays that stored response for any later request with the same key. Failure modes to handle explicitly: same key with a different request body indicates a client bug and should return 422 rather than silently replaying an unrelated response, which is why the request hash is stored; a key still marked in-progress means a concurrent retry, so return 409 and let the client back off; a crash between charging and storing the response leaves a claimed-but-incomplete key, so the record must be written in the same transaction as the charge or reconciled against the payment provider. Keys expire after a retry window such as 24 hours. Beyond the endpoint, the provider call itself should carry its own idempotency key so the same guarantee extends across the trust boundary.

Senior: A mobile client and a web client need very different response shapes from the same resources. How do you handle it without forking the API?

First establish which problem you actually have: over-fetching (mobile wants fewer fields, for bandwidth) or under-fetching (mobile needs several resources per screen, causing request waterfalls on high-latency networks). They have different solutions. For over-fetching, sparse fieldsets (?fields=id,total,status) handle it with one endpoint and an allowlist, at the cost of making caching and response validation more complex. For under-fetching, either expose purpose-built composite endpoints for known screens, or introduce a backend-for-frontend that composes the shared services per client. The BFF is the honest answer when the clients' needs genuinely diverge: each team owns its aggregation layer while the core services stay client-agnostic, at the cost of another deployable. GraphQL solves both directly by letting clients specify shape, but it brings its own operational weight — query cost analysis, depth limiting, caching that no longer works at the HTTP layer. What I would avoid is embedding client-type conditionals in shared handlers, which couples every service to every client and makes changes unreviewable. The decision hinges on how many clients exist and whether their divergence is stable or accidental.

2 (easy): Which of GET, PUT, POST, DELETE, PATCH are idempotent, and why does it matter operationally?
Solution 
// Idempotent: GET, PUT, DELETE (and HEAD).
// Not idempotent: POST, and PATCH in general.
//
// It matters because a network timeout is ambiguous — the request may have
// been applied with the response lost. Idempotency is precisely the property
// that makes a retry safe, so it decides what clients, proxies, and load
// balancers may automatically re-send. DELETE twice yielding 404 the second
// time is still idempotent: the STATE is the same, even though the response
// differs.
3 (medium): Implement cursor pagination for orders sorted by created_at descending.
Solution 
function encodeCursor(row) {
  return Buffer.from(JSON.stringify({ ts: row.created_at, id: row.id })).toString("base64url");
}

app.get("/orders", async (req, res) => {
  const limit = Math.min(Number(req.query.limit) || 50, 100);   // cap it
  const cursor = req.query.cursor
    ? JSON.parse(Buffer.from(req.query.cursor, "base64url").toString())
    : null;

  const rows = await db.query(
    `SELECT * FROM orders
      ${cursor ? "WHERE (created_at, id) < ($1, $2)" : ""}
      ORDER BY created_at DESC, id DESC
      LIMIT ${limit + 1}`,                      // ← fetch one extra
    cursor ? [cursor.ts, cursor.id] : [],
  );

  const hasMore = rows.length > limit;
  const data = rows.slice(0, limit);
  res.json({
    data,
    next_cursor: hasMore ? encodeCursor(data[data.length - 1]) : null,
  });
});
// The (created_at, id) tuple comparison needs a matching composite index.
// limit+1 gives has_more without a COUNT(*). The user-supplied limit is
// capped so a client cannot request a million rows.

5 (hard): Implement idempotency-key handling for POST /payments, including concurrent retries.
Solution 
// Schema: idempotency_keys(key PK, request_hash, status, response, created_at)

app.post("/payments", async (req, res, next) => {
  const key = req.headers["idempotency-key"];
  if (!key) {
    return next(Object.assign(new Error("Idempotency-Key required"), { status: 400 }));
  }
  const hash = createHash("sha256").update(JSON.stringify(req.body)).digest("hex");

  try {
    // Atomic claim: the PRIMARY KEY makes concurrent claims impossible.
    await db.query(
      `INSERT INTO idempotency_keys (key, request_hash, status)
       VALUES ($1, $2, 'in_progress')`, [key, hash]);
  } catch (e) {
    if (e.code !== "23505") throw e;                  // not a unique violation
    const prior = await db.one(`SELECT * FROM idempotency_keys WHERE key = $1`, [key]);
    if (prior.request_hash !== hash) {
      return next(Object.assign(new Error("Key reused with different body"), { status: 422 }));
    }
    if (prior.status === "in_progress") {
      res.set("retry-after", "1");
      return next(Object.assign(new Error("In progress"), { status: 409 }));
    }
    return res.status(200).json(prior.response);      // replay
  }

  // Charge and record the response in ONE transaction, so a crash cannot
  // leave a charge with no stored response (which would replay as a retry
  // of work already done).
  const payment = await db.transaction(async (tx) => {
    const p = await charge(tx, req.body, { idempotencyKey: key });
    await tx.query(
      `UPDATE idempotency_keys SET status='done', response=$2 WHERE key=$1`,
      [key, p]);
    return p;
  });

  res.status(201).location(`/payments/${payment.id}`).json(payment);
});
// Forwarding the key to the payment PROVIDER extends the guarantee across
// the trust boundary — otherwise a crash mid-transaction can still
// double-charge upstream even though your own table is consistent.
6 (hard): You must rename a response field from total to total_cents. Plan the rollout with zero client breakage.
Solution 
// A rename is a REMOVE plus an ADD — the removal is what breaks clients.
// Split it in time so the two never happen together.
//
// Phase 1 — additive (non-breaking): emit BOTH fields.
{ "total": 5000, "total_cents": 5000 }
// Every existing client keeps working; new clients adopt total_cents.
// Document `total` as deprecated in the same release.
//
// Phase 2 — measure. Log per-client whether the response was consumed with
// the old field. Response bodies do not tell you what a client READ, so this
// requires either client instrumentation, a client-version header you already
// collect, or reaching out to known integrators. Never skip this: without
// usage data, removal is a guess.
//
// Phase 3 — signal. On responses to clients still on the old contract:
//   Deprecation: true
//   Sunset: Wed, 31 Dec 2026 23:59:59 GMT
//   Link: <https://docs.example.com/migrations/total-cents>; rel="deprecation"
//
// Phase 4 — remove after the sunset date, having contacted the remaining
// callers directly. If any critical client cannot migrate, keep the field
// behind the /v2 boundary rather than delaying everyone.
//
// The general principle: make the new thing available, migrate readers,
// verify with data, then remove — the same expand/contract pattern used for
// database column renames, and for the same reason. You never need a
// breaking change; you need two non-breaking ones separated by evidence.

🎯 Key Takeaways

  • Model resources and let HTTP methods be the verbs — that is what lets caches, proxies, and retry logic understand your API for free.
  • Safety and idempotency are the two guarantees that decide what may be retried; they are contracts, not conventions.
  • Let the status code carry the outcome — 200 with {"success": false} breaks every intermediary and every retry policy.
  • Error bodies need a stable machine-readable code; if clients branch on prose, you can never reword an error.
  • Offset pagination degrades in both cost and correctness; cursor pagination with a unique tie-breaker is the production default.
  • COUNT(*) for pagination metadata is frequently the most expensive part of a list endpoint — prefer has_more.
  • Allowlist every client-supplied sort and filter field: it is both an injection boundary and a performance boundary.
  • Evolve additively and require clients to ignore unknown fields; that single rule removes most reasons to version.
  • Idempotency keys make POST retry-safe via atomic claim plus response replay — the standard answer for payments.
  • Every rename is expand, migrate, verify, contract — two non-breaking changes separated by usage data.
  • PUT replaces the whole resource; PATCH changes only what you send.
  • PUT is idempotent; PATCH is not guaranteed to be.
  • GET is a safe method, and infrastructure relies on that.
  • A state-changing GET is triggered by crawlers, prefetchers and image tags.
  • Offset pagination slows with depth and misbehaves as data changes.
  • Keyset pagination is equally fast at any depth.
  • Additive changes are safe; removals and renames are breaking.
  • Reserve new versions for genuinely unavoidable breaks.
