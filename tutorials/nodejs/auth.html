Authentication: Sessions & JWT Data & Auth

What you'll master: storing passwords correctly, the real trade-off between server-side sessions and stateless tokens (revocation), cookie flags that decide whether your auth is exploitable, refresh-token rotation, and why "JWT for sessions" is the most over-applied pattern in web development. Prerequisites: Middleware Deep Dive, Databases & ORMs.

Part 1 — Password Storage

import argon2 from "argon2";

// Hash on registration. Never store, log, or email a password.
const hash = await argon2.hash(password, { type: argon2.argon2id });
await db.query("INSERT INTO users (email, password_hash) VALUES ($1, $2)", [email, hash]);

// Verify on login.
const ok = await argon2.verify(user.password_hash, password);

// Why a PASSWORD hash and not SHA-256: general-purpose hashes are designed to
// be FAST, which is exactly wrong here. A GPU computes billions of SHA-256
// hashes per second, so a leaked table of them is cracked offline at scale.
// Password hashes are deliberately SLOW and memory-hard:
//   argon2id  — current recommendation (memory-hard, GPU-resistant)
//   scrypt    — good, available in node:crypto with no dependency
//   bcrypt    — still acceptable; note its 72-byte input truncation
// Each embeds its cost parameters in the output, so you can raise them over
// time and re-hash on next successful login.

// SALT: every password gets a unique random salt, stored with the hash.
// argon2/bcrypt/scrypt do this automatically — that is part of why you use
// them. Salting is what stops one precomputed rainbow table from cracking
// every account at once, and stops identical passwords producing identical
// hashes (which would leak "these users share a password").

// TIMING: comparing secrets must not leak length or content through timing.
import { timingSafeEqual } from "node:crypto";
// argon2.verify already does this. When you compare tokens yourself —
// API keys, reset tokens — use timingSafeEqual on equal-length buffers,
// never ===.

// Login must not reveal whether an account exists:
//   ❌ "No user with that email"  → account enumeration
//   ✅ "Invalid email or password" for both cases
// Also run the hash comparison even when the user is not found (against a
// dummy hash), or response time alone reveals which emails are registered.

Part 2 — Sessions: Server-Side State

// The classic model: the server holds the state, the client holds an opaque id.
import session from "express-session";
import { RedisStore } from "connect-redis";

app.use(session({
  store: new RedisStore({ client: redis }),   // NEVER the default MemoryStore
                                              // in production: it leaks and
                                              // dies with the process
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,        // don't create sessions for anonymous hits
  cookie: {
    httpOnly: true,        // ← JavaScript cannot read it: blunts XSS theft
    secure: true,          // ← HTTPS only: no plaintext interception
    sameSite: "lax",       // ← blunts CSRF (see below)
    maxAge: 1000 * 60 * 60 * 24 * 7,
  },
}));

// The cookie contains a random id; everything else lives in Redis:
//   sess:8f14e45f... → { userId: 42, roles: ["user"], createdAt: ... }
//
// The properties that follow from that, and they are the whole argument:
//   ✅ REVOCATION IS INSTANT — delete the key, the session is dead. Logout,
//      "log out everywhere", ban a user, force re-login after a role change:
//      all one delete.
//   ✅ The client holds no data, so nothing sensitive leaks from the cookie.
//   ✅ You can change what a session means without reissuing anything.
//   ❌ Every authenticated request reads the session store — a dependency in
//      the hot path (fast: Redis is sub-millisecond, but it must be up).

// Session fixation: ALWAYS regenerate the id at the privilege boundary.
req.session.regenerate((err) => {
  req.session.userId = user.id;      // new id, old one invalidated
});
// Without this, an attacker who plants a known session id in a victim's
// browser before login holds a valid authenticated session afterwards.

Part 3 — JWT: Stateless Tokens

import jwt from "jsonwebtoken";

const token = jwt.sign(
  { sub: user.id, roles: user.roles },
  process.env.JWT_SECRET,
  { expiresIn: "15m", issuer: "api.example.com", audience: "app.example.com" },
);
const payload = jwt.verify(token, process.env.JWT_SECRET, {
  issuer: "api.example.com",       // ← verify these, do not just decode
  audience: "app.example.com",
  algorithms: ["HS256"],           // ← PIN the algorithm. See below.
});

// A JWT is three base64url segments: header.payload.signature. The signature
// proves the payload was not altered — it does NOT hide it. The payload is
// readable by anyone holding the token:
//   ❌ never put secrets, PII, or anything you would not print in a log
// "Encoded" is not "encrypted". This is the single most common JWT
// misunderstanding, and it leaks data in real breaches.

// THE ALGORITHM CONFUSION ATTACK — pin `algorithms` or you are vulnerable:
//   • alg: "none" — a token with no signature, accepted by naive verifiers
//   • RS256 → HS256 — if you verify with a public key while allowing HS256,
//     an attacker signs a forged token USING that public key as the HMAC
//     secret, and it verifies. The public key is public.
// Passing an explicit algorithms allowlist closes both.

// THE REAL TRADE-OFF: JWTs cannot be revoked.
// A stateless token is valid until it expires, by definition — that is what
// "stateless" means. So logout does not truly log out, a fired employee keeps
// access, and a stolen token works until expiry. The usual mitigations:
//   • short expiry (5–15 min) + refresh tokens → the standard answer
//   • a denylist of revoked jti values → you are now stateful, having paid
//     JWT's complexity to get sessions' properties back
// If you find yourself building a denylist, that is strong evidence sessions
// were the right choice for your use case.
Do not store JWTs in localStorage. Any XSS on your origin can read localStorage and exfiltrate the token; an httpOnly cookie cannot be read by JavaScript at all. The usual counterargument is CSRF, but that is what sameSite and CSRF tokens are for — and a stolen bearer token is strictly worse than a CSRF-able cookie, because the attacker can use it from anywhere, for its full lifetime. Cookies with httpOnly, secure, and sameSite are the safer default for browser clients regardless of whether the value inside is a session id or a JWT.

Part 4 — Choosing Between Them

// Sessions when (this covers most web applications):
//   • a browser-based app with a first-party API
//   • you need instant revocation (logout, bans, role changes, compromise)
//   • you already run Redis
//   • you want the simplest thing that is correct

// JWTs when:
//   • service-to-service auth where each hop verifies independently
//   • a third-party identity provider issues them (OIDC — you are a consumer,
//     not an issuer, and the format is not your choice)
//   • genuinely stateless horizontal scale where a shared store is a problem
//   • short-lived, single-purpose tokens: email verification, password reset,
//     signed download URLs — these EXPIRE rather than needing revocation,
//     which is exactly what JWTs are good at

// The misconception worth naming: "JWTs scale better." A session lookup is a
// sub-millisecond Redis GET, and Redis handles hundreds of thousands of ops
// per second on modest hardware. For almost every application that is not the
// bottleneck, and you traded instant revocation — a security property — for
// performance you could not measure. Scale is the reason people cite; it is
// rarely the reason that applies.

// Hybrid (what large systems converge on):
//   short-lived access JWT (5–15 min) + long-lived refresh token stored
//   SERVER-SIDE and revocable. You get stateless verification in the hot path
//   and real revocation at refresh time — bounded exposure rather than none.

Part 5 — Refresh Token Rotation

// Access token: short-lived (15 min), sent with every request.
// Refresh token: long-lived (30 days), sent ONLY to /auth/refresh, stored
// hashed server-side, and ROTATED on every use.

async function refresh(req, res) {
  const presented = req.cookies.refresh_token;
  const hash = sha256(presented);                  // store hashes, not tokens —
  const row = await db.one(                        // a DB leak must not yield
    "SELECT * FROM refresh_tokens WHERE token_hash = $1", [hash]);   // usable tokens

  if (!row) throw new AppError("Invalid token", { status: 401 });

  // REUSE DETECTION: this token was already rotated away. Either it was
  // stolen and replayed, or the legitimate client is replaying an old one.
  // Either way you cannot tell which party is the attacker — so revoke the
  // entire family and force re-authentication.
  if (row.used_at) {
    await db.query("UPDATE refresh_tokens SET revoked = true WHERE family_id = $1",
                   [row.family_id]);
    throw new AppError("Token reuse detected", { status: 401 });
  }

  await db.query("UPDATE refresh_tokens SET used_at = now() WHERE id = $1", [row.id]);
  const next = await issueRefreshToken(row.user_id, row.family_id);   // same family
  const access = signAccessToken(row.user_id);

  res.cookie("refresh_token", next, { httpOnly: true, secure: true,
                                      sameSite: "strict", path: "/auth/refresh" });
  res.json({ access_token: access });
}

// Why rotation plus reuse detection is the whole point: without rotation, a
// stolen refresh token works for its full 30-day life, silently, alongside
// the real user. With it, the attacker's use invalidates the victim's token
// (or vice versa) — the theft becomes VISIBLE and self-limiting instead of
// silent. You cannot prevent theft here; you can guarantee it surfaces.
//
// `path` scopes the cookie so the refresh token is not sent with every
// ordinary request — reducing the number of places it can leak.

Part 6 — Cookies, CSRF, and the Flags That Matter

res.cookie("sid", id, {
  httpOnly: true,     // JS cannot read it — an XSS cannot exfiltrate it
  secure: true,       // HTTPS only
  sameSite: "lax",    // sent on top-level navigation, not cross-site POSTs
  path: "/",
  maxAge: 604_800_000,
});

// SameSite values:
//   "strict" — never sent cross-site. Most secure; breaks inbound links
//              (a user arriving from an email lands logged out).
//   "lax"    — sent on top-level GET navigation only. The sensible default,
//              and it blocks the classic cross-site form POST.
//   "none"   — always sent; REQUIRES secure. Only for genuine cross-site
//              needs (an embedded widget on another origin).

// CSRF exists because browsers attach cookies automatically. An attacker's
// page can submit a form to your domain and the browser helpfully includes
// the session cookie. SameSite=lax blocks the common cases; for defence in
// depth on state-changing routes, add a CSRF token:
//   • double-submit: a random value in both a cookie and a header/field;
//     the server compares them. An attacker cannot read your cookie to
//     forge the header (same-origin policy), so they cannot match it.
//   • synchronizer token: server-generated per session, stored server-side.
//
// Bearer tokens in an Authorization header are NOT subject to CSRF, because
// browsers do not attach them automatically — you must run JavaScript to set
// the header, and same-origin policy stops a foreign page reading the token.
// That is the one genuine advantage of header-based auth, and it is why the
// storage question (Part 3's note) is the trade you are actually making.

// Rate limiting login is not optional — it is the difference between a
// password policy and a password suggestion:
app.post("/auth/login", rateLimit({ windowMs: 900_000, limit: 5,
                                     keyGenerator: (req) => req.body.email }),
         login);
// Key on the account, not just the IP: credential-stuffing rotates IPs but
// targets specific accounts. Do both, with different budgets.

Interview Questions

Beginner: Why can't you use SHA-256 for passwords?

Because it is fast by design, and speed is the attacker's advantage in offline cracking. A GPU computes billions of SHA-256 hashes per second, so a leaked table falls quickly to dictionary and brute-force attacks. Password hashes such as argon2id, scrypt, and bcrypt are deliberately slow and memory-hard, with tunable cost parameters, so each guess is expensive and GPU parallelism helps far less. They also handle per-password salting automatically, which prevents one precomputed table from attacking every account at once.

Beginner: What does httpOnly do, and what does it not do?

It prevents JavaScript from reading the cookie via document.cookie, so an XSS payload cannot directly exfiltrate the session id. It does not prevent the cookie from being sent — the browser still attaches it to requests, including cross-site ones unless sameSite restricts that. So httpOnly blunts token theft but not CSRF, and an XSS can still perform actions as the user by making requests from the page; it just cannot steal the credential for use elsewhere.

Mid: What is the fundamental trade-off between sessions and JWTs?

Revocation versus statelessness, and they are two sides of one property. A session id is a pointer to server-held state, so deleting that state instantly invalidates it — logout, bans, and role changes take effect immediately, at the cost of a store lookup on each request. A JWT carries its own claims and is verified by signature alone, so no lookup is needed, but nothing can invalidate it before expiry: that is what stateless means. Every JWT revocation scheme — denylists, short expiry plus refresh — is an attempt to recover the property statelessness gave away, and a denylist in particular means you are paying JWT's complexity to get a session's behaviour.

Mid: Explain the JWT algorithm confusion attack.

Two related forgeries that both come from letting the token's own header choose the verification algorithm. First, alg: "none": a token declaring no algorithm, with an empty signature, which naive verifiers accept as valid. Second, RS256 to HS256 substitution: if a server verifies with an RSA public key but permits HMAC algorithms, an attacker signs a forged token using that public key as the HMAC secret. Since the public key is public, anyone can produce a token that verifies. Both are closed by passing an explicit algorithms allowlist to the verify call, so the token cannot nominate its own verification method. The general principle is never to let untrusted input choose how it is validated.

Senior: Design authentication for a system with a web app, a mobile app, and internal service-to-service calls. Justify each choice.

These are three different threat models and they should not share one mechanism. For the web app I would use server-side sessions in httpOnly, secure, sameSite=lax cookies: the browser is the hostile environment, cookies keep the credential unreadable by JavaScript, and instant revocation matters most where XSS risk is highest. For mobile, there is no cookie jar and no CSRF surface, so short-lived access tokens plus rotating refresh tokens in the platform keystore fit naturally — mobile clients also need long-lived login without re-authentication, which is exactly what refresh rotation with reuse detection provides safely. For service-to-service I would use mTLS where the infrastructure supports it, or short-lived signed tokens from a central issuer with audience restriction per service, so a token minted for one service cannot be replayed against another; the key property is that services verify independently without a shared session store in the request path. Cutting across all three: one identity service issues credentials, authorization decisions live in shared middleware rather than duplicated per client type, and every credential has an expiry and a revocation path. What I would avoid is the common shortcut of issuing the same long-lived JWT to all three and calling it uniform, since it takes the weakest properties of each context and applies them everywhere.

Senior: A user reports their account was accessed from another country. Walk through what your auth design should let you do.

The first question is whether I can terminate access right now, and the answer is a property of the design rather than the incident. With sessions, I delete that user's session keys and every device is logged out immediately. With long-lived JWTs and no denylist, I cannot — access persists until expiry, and the honest answer to the user is that I can only change their password and wait. That single question is the strongest practical argument for sessions or short-token hybrids. Assuming a revocable design: I revoke all sessions and refresh-token families, force a password reset, and invalidate password-reset tokens issued before the compromise. Then I investigate scope using the audit trail — which requires having logged authentication events with request id, IP, user agent, and timestamp, ideally at session creation rather than per request. I check whether the credential was stolen (XSS, phishing, reused password from another breach) or whether reuse detection already fired on a refresh family, since that tells me theft occurred and roughly when. Then I look for lateral movement: what did the session do, were API keys or contact details changed, is the same source IP hitting other accounts, which would indicate credential stuffing rather than a targeted compromise. Long term, this incident is evidence for MFA, for notifying users of new-device logins, and for shortening token lifetimes. The design lesson is that incident response capability has to be built before the incident: revocation, audit logging, and token families are all things you cannot add retroactively to sessions that already exist.

🏋️ Graded Exercises

1 (easy): Write registration and login with argon2, avoiding account enumeration.
Solution 
import argon2 from "argon2";

// A precomputed hash of a random string, used to equalize timing.
const DUMMY_HASH = await argon2.hash(randomUUID());

async function register(email, password) {
  const hash = await argon2.hash(password, { type: argon2.argon2id });
  await db.query("INSERT INTO users (email, password_hash) VALUES ($1,$2)", [email, hash]);
}

async function login(email, password) {
  const user = await db.maybeOne("SELECT * FROM users WHERE email = $1", [email]);
  // Always verify SOMETHING, so response time does not reveal existence.
  const ok = await argon2.verify(user?.password_hash ?? DUMMY_HASH, password);
  if (!user || !ok) {
    throw new AppError("Invalid email or password", { status: 401, code: "invalid_credentials" });
  }
  return user;
}
// One message for both failure modes, and constant-ish timing. Either alone
// is insufficient: identical messages with a fast "user not found" path still
// leak which emails are registered.

3 (medium): Write JWT verification middleware that is not vulnerable to algorithm confusion.
Solution 
import jwt from "jsonwebtoken";

export function requireAuth(req, res, next) {
  const header = req.headers.authorization ?? "";
  const token = header.startsWith("Bearer ") ? header.slice(7) : null;
  if (!token) {
    return next(new AppError("Missing token", { status: 401, code: "unauthenticated" }));
  }
  try {
    req.ctx = {
      ...req.ctx,
      user: jwt.verify(token, process.env.JWT_SECRET, {
        algorithms: ["HS256"],            // ← the critical line
        issuer: "api.example.com",
        audience: "app.example.com",
        clockTolerance: 5,                // small skew allowance
      }),
    };
    return next();
  } catch (err) {
    // Distinguish expiry so clients know to refresh rather than re-login.
    const expired = err.name === "TokenExpiredError";
    return next(new AppError(expired ? "Token expired" : "Invalid token", {
      status: 401, code: expired ? "token_expired" : "invalid_token", cause: err,
    }));
  }
}
// Pinning algorithms blocks alg:none and RS256→HS256. Verifying issuer and
// audience stops a token minted for a different service being replayed here.
4 (medium): Why is jwt.decode() dangerous, and when is it acceptable?
Solution 
// decode() parses the payload WITHOUT checking the signature. Anyone can
// craft {"sub": 1, "roles": ["admin"]} and decode() returns it happily:
const payload = jwt.decode(token);          // ❌ never for authorization
if (payload.roles.includes("admin")) { /* trivially forged */ }

// Acceptable only where the result is not trusted for a security decision:
//   • reading `exp` on the CLIENT to schedule a refresh
//   • logging a token's issuer while debugging
//   • routing to the right key by `kid` before verifying (then verify)
// On the server, in an auth path, use verify() — always.
5 (hard): Implement refresh token rotation with reuse detection. Explain what reuse detection buys.
Solution 
// refresh_tokens(id, user_id, family_id, token_hash, used_at, revoked, expires_at)

async function issue(userId, familyId = randomUUID()) {
  const token = randomBytes(32).toString("base64url");
  await db.query(
    `INSERT INTO refresh_tokens (user_id, family_id, token_hash, expires_at)
     VALUES ($1,$2,$3, now() + interval '30 days')`,
    [userId, familyId, sha256(token)]);
  return token;
}

async function rotate(presented) {
  const row = await db.maybeOne(
    "SELECT * FROM refresh_tokens WHERE token_hash = $1", [sha256(presented)]);

  if (!row || row.revoked || row.expires_at < new Date()) {
    throw new AppError("Invalid refresh token", { status: 401 });
  }

  if (row.used_at) {
    // Already rotated. Two parties hold this token: one is an attacker, and
    // we cannot tell which. Kill the whole family.
    await db.query("UPDATE refresh_tokens SET revoked = true WHERE family_id = $1",
                   [row.family_id]);
    throw new AppError("Token reuse detected — re-authenticate", { status: 401 });
  }

  await db.query("UPDATE refresh_tokens SET used_at = now() WHERE id = $1", [row.id]);
  return {
    refresh: await issue(row.user_id, row.family_id),
    access: signAccessToken(row.user_id),
  };
}

// What reuse detection buys: without it, a stolen refresh token is a silent,
// 30-day parallel session — the victim notices nothing because their own
// token still works. With rotation, only one holder can use a given token
// once, so the attacker's use breaks the victim's session (or vice versa),
// and the mismatch surfaces the theft. You cannot stop the theft; you can
// guarantee it becomes visible and bounded rather than silent and durable.
// Hashes are stored so a database leak does not hand over usable tokens.
6 (hard): A team wants JWTs for a browser app "so we can scale horizontally". Evaluate the argument and propose a design.
Solution 
// Examine the premise first. The claim is that sessions require sticky
// sessions or a shared store that limits scaling. But a shared session store
// is a Redis GET of a few hundred microseconds, and Redis serves hundreds of
// thousands of ops/sec on modest hardware. For nearly every application that
// is not the bottleneck — and it is easy to verify with a load test rather
// than assumed. Sticky sessions are only required for IN-MEMORY session
// state, which nobody should use in production anyway.
//
// Meanwhile the cost is concrete and security-relevant:
//   • no instant logout — "log out everywhere" becomes impossible
//   • a fired employee keeps access until expiry
//   • a compromised account cannot be terminated during an incident
//   • role/permission changes do not take effect until the token expires
// So the trade is a measurable-but-usually-irrelevant performance gain for a
// security capability you need precisely when things go wrong.
//
// Proposal — hybrid, which gets most of both:
//   • access JWT, 10 minutes, verified statelessly in the hot path
//   • refresh token, opaque and revocable, stored hashed server-side,
//     rotated on use with reuse detection
//   • both in httpOnly + secure + sameSite cookies (browser client: keep
//     the credential unreadable by JavaScript)
//   • refresh cookie scoped with path=/auth/refresh
//   • revocation list checked at REFRESH time, not per request
// Worst-case exposure after revocation is one access-token lifetime, which
// is a stated, bounded number rather than "until it expires, whenever that
// is". If the team still wants pure JWT, the question to settle first is:
// what is our incident response when an account is compromised? If the
// answer is "wait for expiry", that needs to be an explicit, accepted
// decision — not a side effect of an architecture chosen for scale.

🎯 Key Takeaways

  • Password hashes must be slow and memory-hard — argon2id, scrypt, or bcrypt, never a general-purpose hash.
  • Identical error messages plus constant-time verification are both required to prevent account enumeration.
  • Regenerate the session id at every privilege change, or session fixation remains possible.
  • A JWT payload is signed, not encrypted — it is readable by anyone holding the token.
  • Always pin algorithms on verify; letting a token choose its own algorithm enables alg:none and RS256→HS256 forgery.
  • The sessions-versus-JWT decision is revocation versus statelessness; every JWT revocation scheme is an attempt to buy back what statelessness gave away.
  • Prefer httpOnly cookies over localStorage for browser clients — a stolen bearer token is worse than a CSRF-able cookie.
  • Refresh tokens must be stored hashed, rotated on every use, and revoked family-wide on reuse — that is what makes theft visible.
  • SameSite blunts CSRF; add explicit CSRF tokens on state-changing routes for defence in depth.
  • Rate limit login by account as well as by IP, because credential stuffing rotates IPs and targets accounts.
