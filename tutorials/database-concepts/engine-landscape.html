The Engine Landscape Design Perspective

What you'll master: the actual architecture of the engines you are most likely to meet — PostgreSQL, MySQL/InnoDB, SQLite, DuckDB and the LSM family — expressed as the specific internal decisions each made and the operational personality that follows, why PostgreSQL's process-per-connection model and in-table MVCC produce the behaviours its users complain about, why InnoDB's clustered index makes primary-key width a first-order concern that Postgres users never think about, why SQLite is the most widely deployed database in the world and where its single-writer model actually binds, how DuckDB became the analytical counterpart to SQLite, and how to read an unfamiliar engine's documentation and predict its behaviour before running a benchmark. Prerequisites: ideally the whole track, since this lesson is where the internals from Sections 1–3 become a comparative framework.

Part 1 — The Six Questions That Characterise Any Engine

-- From lesson 1, now used as a comparative instrument. Answer these six
-- and you can predict most of an engine's behaviour without touching it.

-- 1. STORAGE STRUCTURE       B+tree, LSM, columnar, in-memory?
--    → read/write/space amplification, latency shape
-- 2. DURABILITY              WAL? fsync per commit or grouped? relaxable?
--    → write throughput ceiling, data-loss window
-- 3. CONCURRENCY             MVCC or locking? old versions in-table or
--                            in an undo log?
--    → do readers block writers; bloat versus undo-chain growth
-- 4. LAYOUT                  row or columnar?
--    → OLTP versus analytical suitability
-- 5. INDEXING                clustered primary key, or heap plus
--                            symmetric indexes?
--    → secondary-lookup cost, how much PK width matters
-- 6. PLANNING                cost-based with statistics, or rule-based?
--                            are plans visible and influenceable?
--    → how it fails, and what you can do about it

-- ── AND THREE MORE THAT DECIDE WHETHER YOU CAN OPERATE IT ───────────────
-- 7. PROCESS MODEL           process per connection, thread per
--                            connection, or async? → connection limits
-- 8. EXTENSIBILITY           can you add types, index methods, functions?
-- 9. OPERATIONAL SURFACE     backups, PITR, upgrades, observability
-- ⚠ Question 9 decides more real outcomes than questions 1-6 combined,
--   and it is the one benchmarks never measure.

-- ── THE SUMMARY TABLE ───────────────────────────────────────────────────
--                Postgres   InnoDB     SQLite    DuckDB    RocksDB
--  structure     B+tree     B+tree     B+tree    columnar  LSM
--  MVCC          in-table   undo log   none*     n/a       n/a
--  layout        row        row        row       columnar  KV
--  indexing      heap       clustered  clustered n/a       n/a
--  process       per-conn   thread     in-proc   in-proc   library
--  transactions  full ACID  full ACID  full ACID limited   batch-level
--  * SQLite uses a rollback journal or WAL mode, not MVCC versions.

Part 2 — PostgreSQL

-- ── THE DEFINING DECISIONS ──────────────────────────────────────────────
-- • HEAP storage with symmetric indexes — no clustered primary key
-- • MVCC with old versions IN THE TABLE
-- • PROCESS per connection
-- • extensibility as a first-class design goal
-- Everything characteristic about Postgres follows from those four.

-- ── CONSEQUENCE 1: VACUUM IS THE OPERATIONAL CENTRE ─────────────────────
-- Old row versions live in the table, so they must be reclaimed
-- (lesson 7). This produces the entire family of Postgres-specific
-- operational concerns:
SELECT relname, n_dead_tup, last_autovacuum FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 5;
SELECT age(datfrozenxid) FROM pg_database;   -- wraparound risk
-- ✓ THE UPSIDE, which is rarely stated: ROLLBACK IS FREE. Uncommitted
--   versions are simply invisible, so aborting a transaction costs
--   nothing and crash recovery is redo-only. Oracle and InnoDB pay for
--   rollback by applying undo.
-- ✗ THE DOWNSIDE: bloat, vacuum tuning, and wraparound as a genuine
--   shutdown risk on a badly-run system.

-- ── CONSEQUENCE 2: THE UPDATE PATH IS EXPENSIVE ─────────────────────────
-- Index entries point at physical locations, so a moved row requires
-- updating every index — hence the HOT optimisation and its two
-- conditions (lesson 2). This is why "do not index volatile columns" is
-- much stronger advice on Postgres than elsewhere.

-- ── CONSEQUENCE 3: CONNECTIONS ARE EXPENSIVE ────────────────────────────
-- Each connection is an OS PROCESS with several megabytes of private
-- memory. Past roughly (cores × 2), adding connections REDUCES
-- throughput through context switching and shared-structure contention.
-- ✓ A pooler is not optional at scale — PgBouncer in transaction mode
--   turning 500 application threads into 40 real connections is standard
--   practice, not a workaround.
-- ⚠ And transaction-mode pooling breaks session state: session advisory
--   locks, temp tables and prepared statements do not survive.

-- ── CONSEQUENCE 4: EXTENSIBILITY IS THE REAL DIFFERENTIATOR ─────────────
CREATE EXTENSION postgis;      -- geospatial types, indexes, operators
CREATE EXTENSION pgvector;     -- vector similarity search
CREATE EXTENSION timescaledb;  -- time-series partitioning + compression
CREATE EXTENSION pg_stat_statements, pg_trgm, hstore, citus, ...;
-- Custom types, operators, index access methods (GIN, GiST, BRIN, SP-GiST)
-- and procedural languages are all pluggable.
-- ✓ This is why Postgres keeps absorbing adjacent categories — document
--   storage via JSONB, geospatial via PostGIS, vector search via
--   pgvector, time-series via Timescale. "Just use Postgres" is often
--   correct not because it is best at each, but because ONE system your
--   team already operates beats three they do not.

-- ── WHERE POSTGRES IS GENUINELY WEAK ────────────────────────────────────
-- ✗ very high connection counts without a pooler
-- ✗ update-heavy workloads on wide tables (bloat and index maintenance)
-- ✗ analytical scans over wide tables — a row store (lesson 13)
-- ✗ major-version upgrades: pg_upgrade is fine but requires planning,
--   and statistics do NOT carry over (lesson 6)
-- ✗ multi-master writes: not supported in core

Part 3 — MySQL / InnoDB

-- ── THE DEFINING DECISIONS ──────────────────────────────────────────────
-- • CLUSTERED index: the table IS the primary key's B+tree
-- • MVCC with old versions in an UNDO LOG
-- • THREAD per connection
-- • buffer pool sized large, with O_DIRECT bypassing the OS cache

-- ── CONSEQUENCE 1: THE PRIMARY KEY IS THE TABLE ─────────────────────────
CREATE TABLE orders (id BIGINT AUTO_INCREMENT PRIMARY KEY, ...);
-- Rows are stored in primary-key order inside the PK's B+tree leaves.
-- ✓ a PK lookup is ONE descent that arrives at the row itself
-- ✓ PK range scans are physically sequential — excellent
-- ✗ SECONDARY indexes store the PRIMARY KEY as the row reference, so a
--   secondary lookup needs a SECOND descent through the clustered index
-- ✗ a wide PK is copied into EVERY secondary index
-- ⚠ THIS is why "keep the primary key narrow" is far stronger advice on
--   MySQL, and why a random UUID PK is worse here than on Postgres: it
--   scatters the ACTUAL ROWS, not merely an index, and adds 16 bytes to
--   every entry of every secondary index.
-- ✓ COROLLARY: covering indexes are more valuable in InnoDB, because
--   they avoid the second descent entirely.

-- ── CONSEQUENCE 2: NO VACUUM, BUT UNDO GROWTH INSTEAD ───────────────────
SHOW ENGINE INNODB STATUS;      -- "History list length"
-- Old versions live in the undo log, so tables do not bloat. But a long
-- transaction makes undo chains longer, and READS GET SLOWER as they
-- walk more links. The undo tablespace can also grow without bound.
-- ⚠ Same root cause as Postgres bloat (a long transaction), completely
--   different symptom. Knowing which engine you are on tells you which
--   to look for — and this is the single most useful cross-engine fact
--   in this lesson.

-- ── CONSEQUENCE 3: A DIFFERENT REPEATABLE READ ──────────────────────────
-- At REPEATABLE READ, InnoDB's UPDATE reads the LATEST COMMITTED row
-- rather than the snapshot version, so it silently succeeds and a LOST
-- UPDATE is possible. Postgres aborts with a serialisation failure
-- instead (lesson 7).
-- ⚠ Identical level NAME, opposite safety property. Code correct on one
--   engine can silently corrupt data on the other.
-- InnoDB also uses GAP LOCKS and next-key locking at this level to
-- prevent phantoms, which introduces deadlocks that surprise people
-- coming from Postgres.

-- ── CONSEQUENCE 4: OPERATIONAL DIFFERENCES ──────────────────────────────
-- ✗ DDL IS NOT TRANSACTIONAL. A failed migration leaves a half-changed
--   schema — you cannot wrap ALTER TABLE in a transaction and roll back.
--   (Postgres can, and it materially changes how migrations are written.)
-- ✓ Threads rather than processes → cheaper connections, so the pooling
--   pressure is lower.
-- ✓ Mature, well-understood replication and a large operational
--   ecosystem; Vitess provides battle-tested sharding.
-- • innodb_flush_log_at_trx_commit is the durability dial (the
--   equivalent of synchronous_commit).
🔀 The most useful cross-engine fact: a long transaction hurts every MVCC engine, and each shows it differently. PostgreSQL keeps old versions in the table, so it bloats and vacuum cannot advance. InnoDB and Oracle keep them in an undo log, so tables stay compact but undo chains lengthen and reads slow progressively. Same cause, opposite-looking incident. Knowing which architecture you are operating tells you which symptom to look for first, and that alone shortens most investigations.

Part 4 — SQLite and DuckDB

-- ── SQLITE: THE MOST DEPLOYED DATABASE IN THE WORLD ─────────────────────
-- Billions of instances — every phone, browser, and countless embedded
-- devices. Not a toy, and not "a database for small projects".

-- THE DEFINING DECISIONS:
-- • IN-PROCESS: a library, not a server. No network, no IPC, no
--   authentication layer — a function call reads a B-tree page.
-- • ONE FILE: the entire database, cross-platform, copyable.
-- • SINGLE WRITER, many readers (in WAL mode).
-- • dynamic typing ("type affinity") rather than strict types.

-- ✓ THE PERFORMANCE CONSEQUENCE PEOPLE MISS: no network round trip. A
--   query that costs 0.2 ms in Postgres over a socket can be 5 μs in
--   SQLite. For read-heavy embedded workloads it is FASTER than a
--   client-server database, not a compromise.
PRAGMA journal_mode = WAL;      -- ⚠ essential for concurrency: readers
                                --   no longer block the writer
PRAGMA synchronous = NORMAL;    -- durability dial
PRAGMA foreign_keys = ON;       -- ⚠ OFF by default, for compatibility

-- ── WHERE THE SINGLE WRITER ACTUALLY BINDS ──────────────────────────────
-- One write transaction at a time, database-wide. In WAL mode readers
-- proceed concurrently, so the limit is WRITE concurrency specifically.
-- ✓ Fine to hundreds of writes/sec, which covers a very large share of
--   applications — including many that deploy Postgres reflexively.
-- ✗ Not for: many concurrent writers, or writes from multiple machines
--   (network filesystems break the locking model).
-- ⚠ "SQLite doesn't scale" is usually wrong in the way it is meant. It
--   scales READS extremely well. It does not scale concurrent WRITERS,
--   and it does not do multi-machine. Say which one you mean.
-- (Litestream and rqlite address replication and durability; Turso and
--  D1 build distributed services on the same engine.)

-- ── DUCKDB: "SQLITE FOR ANALYTICS" ──────────────────────────────────────
-- Same in-process, single-file, zero-configuration philosophy —
-- with every internal decision made for the OPPOSITE workload.
-- • COLUMNAR storage
-- • VECTORISED execution (lesson 13)
-- • reads Parquet, CSV and Arrow directly, without loading
SELECT country, sum(revenue) FROM 'data/*.parquet' GROUP BY 1;
SELECT * FROM read_csv_auto('huge.csv') WHERE amount > 1000;
-- ✓ Predicate and projection pushdown into Parquet means it reads only
--   the needed column chunks of the needed row groups — frequently
--   without downloading most of the file.
-- ✓ Hundreds of millions of rows aggregated on a laptop, in seconds.
-- ✗ Not for: concurrent writers, an application backend, transactional
--   workloads. Single-process by design.

-- ── WHY THIS PAIR MATTERS ARCHITECTURALLY ───────────────────────────────
-- Together they cover an enormous amount of ground with NO SERVER:
--   SQLite → embedded OLTP
--   DuckDB → embedded OLAP over files in object storage
-- ✓ A reporting stack of "export Parquet nightly, query with DuckDB" has
--   two moving parts instead of a warehouse plus a streaming pipeline
--   (lesson 13). For many teams that is the right answer and it is
--   routinely overlooked because it does not look like infrastructure.

Part 5 — The LSM Family and Distributed SQL

-- ── ROCKSDB: A LIBRARY, NOT A DATABASE ──────────────────────────────────
-- An embeddable LSM key-value store (lesson 4). It has no query
-- language, no schema and no server — it is the STORAGE LAYER inside
-- other systems: MyRocks (MySQL), CockroachDB, TiKV, Kafka Streams,
-- Flink state, and many more.
-- ✓ Knowing this reframes a lot of "which database" conversations: many
--   apparently different systems share one storage engine, so they share
--   its amplification profile and its compaction behaviour.

-- ── CASSANDRA / SCYLLA ──────────────────────────────────────────────────
-- LSM storage + consistent hashing + tunable consistency. Built for
-- write-heavy, partition-keyed access at scale across many nodes.
-- ✓ excellent ingest, linear scaling, no single point of failure
-- ✗ no joins, limited aggregation, and query patterns must be known at
--   MODELLING time — you design tables per query, not per entity
-- ✗ tombstones make delete-heavy workloads pathological (lesson 4)
-- (Scylla is a C++ rewrite of Cassandra with a shard-per-core
--  architecture; same data model, considerably better efficiency.)

-- ── MONGODB ─────────────────────────────────────────────────────────────
-- Document model over WiredTiger (B+tree with LSM-like write buffering,
-- and MVCC). Modern versions have transactions and a decent query
-- planner.
-- ✓ genuinely good when the data IS document-shaped and access is by
--   document — nested structures avoid joins entirely
-- ✗ the flexible schema is a modelling liability at scale: without a
--   declared shape, five years of drift is invisible until it breaks
-- ⚠ Postgres JSONB covers a large share of the same ground while keeping
--   constraints, joins and full SQL — worth comparing honestly rather
--   than by reputation (lesson 13's "one system beats two" argument).

-- ── DISTRIBUTED SQL: COCKROACHDB, YUGABYTE, SPANNER ─────────────────────
-- SQL interface, distributed storage, consensus (Raft/Paxos) per write.
-- ✓ horizontal scale with strong consistency and survivable node loss
-- ✓ familiar SQL and, for Cockroach/Yugabyte, Postgres wire compatibility
-- ✗ EVERY write pays consensus latency — a cross-region commit costs at
--   least one round trip, which no engineering removes (SQL scaling
--   lesson)
-- ✗ operationally and financially heavier; different failure modes to
--   learn
-- → Justified when you genuinely need global strong consistency or
--   survivable multi-region writes. Frequently adopted when a single
--   well-tuned node plus replicas would have sufficed for years.

-- ── THE PATTERN WORTH NOTICING ──────────────────────────────────────────
-- Every system above is a combination of choices you now recognise:
-- storage structure + durability mechanism + concurrency model +
-- distribution strategy. There is no magic in any of them, and the
-- marketing differences are usually smaller than the architectural ones.

Part 6 — Reading an Unfamiliar Engine

-- ── THE PROCEDURE ───────────────────────────────────────────────────────
-- 1. FIND THE STORAGE STRUCTURE. Usually stated in the first page of the
--    architecture docs, or inferable from the tuning knobs: compaction
--    settings mean LSM; buffer pool and page size mean B+tree;
--    row-group and encoding settings mean columnar.
-- 2. FIND THE DURABILITY DIAL. Every engine has one, and its default
--    tells you what the designers optimised for. If the default is
--    "fsync every N seconds", the system is built for throughput over
--    zero data loss — which may be correct for its intended use.
-- 3. FIND THE CONCURRENCY MODEL. Search the docs for "isolation",
--    "snapshot", "lock". If isolation levels are not discussed at all,
--    that is itself the answer.
-- 4. READ THE LIMITS PAGE. Maximum row size, maximum columns, maximum
--    connections, what cannot be changed after creation. This page is
--    where the real constraints live and it is usually short.
-- 5. READ THE FAILURE DOCUMENTATION. How does it behave when the disk
--    fills, when a node dies mid-write, during a network partition?
--    An engine whose docs do not discuss this has not thought about it.
-- 6. FIND THE BACKUP AND RESTORE STORY. Then actually test a restore.
--    An untested backup is a hypothesis (lesson 6).

-- ── THE QUESTIONS BENCHMARKS DO NOT ANSWER ──────────────────────────────
-- • How do we back it up, and has anyone restored it?
-- • How do we upgrade it without downtime?
-- • What does it expose for observability?
-- • Who on the team can debug it at 3am?
-- • What happens when it runs out of disk?
-- • How large is the community when we hit an unusual bug?
-- ⚠ These decide more real outcomes than throughput numbers, and they
--   are systematically absent from evaluations.

-- ── BENCHMARKING HONESTLY, IF YOU BENCHMARK AT ALL ──────────────────────
-- ✓ Use YOUR data distribution, including the skew. Uniform test data
--   hides the problems that will actually happen (cost-models lesson).
-- ✓ Exceed memory. Almost every database looks excellent when the
--   working set fits in the buffer pool.
-- ✓ Test the corner the architecture did NOT optimise for — that is
--   where you will be surprised in production.
-- ✓ Run long enough for background work — compaction, vacuum,
--   checkpoints — to matter. A five-minute benchmark measures a system
--   that has not yet had to clean up after itself.
-- ✗ Do not trust vendor benchmarks, and do not trust yours either
--   without these controls.

-- ── THE DEFAULT ANSWER, AND WHEN TO LEAVE IT ────────────────────────────
-- Start with PostgreSQL unless you can name the specific property it
-- lacks. Not because it wins every category, but because:
--   • it is competent at nearly everything
--   • extensions cover most adjacent needs (JSONB, PostGIS, pgvector,
--     TimescaleDB, Citus)
--   • the operational knowledge is widely available
--   • ONE system your team can run beats two they cannot
-- ✓ LEAVE IT WHEN you can complete this sentence with evidence: "We need
--   X because our workload has property Y, which Postgres handles at
--   cost Z, and we have measured Z."
-- ✗ Not: "it might not scale", "everyone uses X", or "it feels more
--   modern".

Interview Questions

Beginner: What are the main differences between PostgreSQL and MySQL?

The most consequential difference is how rows are physically stored. InnoDB uses a clustered index, meaning the table is the primary key's B+tree with the full row in the leaves, and every secondary index stores the primary key as its row reference. PostgreSQL stores rows in an unordered heap with all indexes as separate, symmetric structures pointing at physical locations. That single difference explains a lot: primary-key width matters much more in MySQL because it is copied into every secondary index, secondary lookups need a second tree descent, and a random UUID primary key scatters the actual rows rather than just an index.

The second is where old row versions live. PostgreSQL keeps them in the table, so it needs vacuum and can bloat, but rollback is essentially free and crash recovery is redo-only. InnoDB keeps them in an undo log, so tables stay compact and there is no vacuum, but rollback is expensive and long transactions cause undo chains that slow reads progressively. Same problem, opposite symptom.

Then a set of practical differences. PostgreSQL has transactional DDL, so a failed migration rolls back cleanly, which changes how migrations are written. It uses a process per connection, so a pooler is effectively mandatory at scale, whereas MySQL uses threads. And PostgreSQL's extension system — PostGIS, pgvector, TimescaleDB — lets it absorb adjacent workloads in a way MySQL does not.

The one that catches people out is that Repeatable Read means different things: InnoDB permits lost updates at that level while PostgreSQL aborts the transaction instead. Code correct on one can silently corrupt data on the other.

Beginner: When is SQLite the right choice?

More often than its reputation suggests. It is the most widely deployed database in the world — every phone, every browser, enormous numbers of embedded devices — and the reason is that being an in-process library rather than a server removes an entire category of cost. There is no network round trip, no connection handshake, no separate process to operate. A query that costs a couple of hundred microseconds against Postgres over a socket can be a few microseconds in SQLite, so for read-heavy embedded workloads it is genuinely faster, not a compromise.

It suits desktop and mobile applications, embedded systems, test suites, local caches, and as a file format for structured data. It is increasingly viable for small-to-medium web applications too, particularly with WAL mode enabled so readers do not block the writer.

The real limit is concurrent writers: one write transaction at a time, database-wide. That still supports hundreds of writes per second, which covers a large share of applications, but it does not support many simultaneous writers. The other limit is that it expects a local filesystem — network filesystems break its locking assumptions — so multi-machine access is out.

So "SQLite doesn't scale" is usually imprecise. It scales reads very well; it does not scale concurrent writers or span machines. Naming which one you mean is the useful version of the statement, and if neither constraint binds, the operational simplicity is a substantial advantage.

Mid: Why is a random UUID primary key worse in MySQL than in PostgreSQL?

Because of clustering. InnoDB stores the table inside the primary key's B+tree, so the primary key determines the physical order of the rows themselves. A random UUID means each insert belongs at a random position in that tree, so inserts scatter across the whole table rather than appending to one hot page. That causes page splits, poor cache locality, and a working set far larger than the data warrants, because every insert dirties a different page.

There is a second cost specific to clustering. Secondary indexes in InnoDB store the primary key as their row reference rather than a physical pointer, so a sixteen-byte UUID is copied into every entry of every secondary index. A table with four secondary indexes pays that overhead four times over, and each of those indexes becomes correspondingly larger and less cacheable.

In PostgreSQL the same key scatters the primary key's index but not the table, since rows go into the heap wherever there is free space. The damage is real — roughly doubling that index's size because random insertion leaves pages about half full — but it is confined to one structure.

The fix in both cases is a time-ordered identifier such as UUIDv7, ULID or Snowflake, which restores insert locality while keeping global uniqueness. Alternatively keep a narrow internal bigint key and expose a separate opaque public identifier, so joins stay compact and external references stay non-enumerable. What makes this a good question is that the entire answer is derivable from one architectural fact about each engine, without benchmarking anything.

Mid: What is DuckDB and when would you use it?

DuckDB is an in-process analytical database — the columnar counterpart to SQLite. It runs as a library inside your application or notebook, needs no server or configuration, and uses columnar storage with vectorised execution, so it processes batches of a single column with SIMD instructions rather than one row at a time.

Its most useful property in practice is that it queries Parquet, CSV and Arrow files directly, without an import step. You can point it at a glob of Parquet files in object storage and run SQL against them, and it applies predicate and projection pushdown using the files' own statistics — so it reads only the column chunks of the row groups that can match, frequently without downloading most of the data. That makes aggregating hundreds of millions of rows on a laptop entirely routine.

I would reach for it for data analysis and reporting, for ETL and transformation steps, for local exploration of large exports, and as the query engine in a lightweight analytics stack: export Parquet from the transactional database on a schedule and query it with DuckDB. That is two moving parts instead of a warehouse plus a streaming pipeline, and it serves a surprising share of real reporting needs.

It is not for concurrent writers, application backends or transactional workloads — it is single-process by design, exactly like SQLite. The pair is worth thinking of together: SQLite for embedded transactional work, DuckDB for embedded analytical work, and between them they cover a lot of ground with no server at all.

Senior: How would you evaluate an unfamiliar database for a critical system?

I would characterise the architecture before benchmarking, because a benchmark tells you how the system handled your test while the architecture tells you how it will behave on workloads you have not imagined yet.

Six questions cover the core. What is the storage structure — B-tree, LSM, columnar — which predicts the read, write and space amplification profile and the shape of its latency. How is durability achieved: is there a write-ahead log, does it fsync per commit, and can that be relaxed? What is the concurrency model, and if it is MVCC, where do old versions live, since that determines whether I will be fighting bloat or lengthening undo chains. Is it row or columnar. Is the primary key clustered. And is planning cost-based with statistics, which tells me it will fail by mis-estimating.

Then the operational surface, which in my experience decides more outcomes than any of the above: how backups and point-in-time recovery work, how upgrades work, what observability it exposes, how it behaves when the disk fills or a node dies mid-write, and how large the community is when we hit an unusual bug. The limits page in the documentation is short and disproportionately informative, because it lists what cannot be changed after creation.

Only then would I benchmark, and I would design it around the trade-offs the architecture told me to be suspicious of — testing the corner it did not optimise for, with our real data distribution including its skew, at a size exceeding memory, and running long enough for compaction or vacuum to matter. Almost every database looks excellent on uniform data that fits in the buffer pool for five minutes.

Finally I would weight team capability explicitly. A system nobody can debug at three in the morning is a worse choice than a slightly slower one the team already understands, and that consideration is routinely left out of evaluations because it is not measurable in a benchmark.

Senior: A team wants to move from PostgreSQL to a distributed SQL database. How do you respond?

I would ask what specific property they need that Postgres lacks, and require it to be stated as a measurement rather than a concern. The useful form is "we need X because our workload has property Y, which Postgres handles at cost Z, and we have measured Z". If that sentence cannot be completed, the conversation is about anxiety rather than requirements, and the honest thing is to say so.

Then I would establish where the current system actually is. Most databases described as at their limit are running with default cost constants, a poor cache hit rate from bloat, a handful of missing indexes, and no connection pooler. Fixing those routinely yields multiples, and none of it is wasted if we do eventually distribute. I would also check whether the bottleneck is reads, in which case replicas and caching apply, or writes, which is the only case distribution genuinely addresses.

If writes truly saturate a well-tuned primary, I would still propose the cheaper steps first: vertical scaling, which is reversible and needs no code changes, and a functional split moving a self-contained subsystem — events, audit logs, sessions — to its own database. Those are frequently most of the relief for a fraction of the cost.

When distributed SQL is genuinely warranted, I would name what it costs. Every write pays consensus latency, which no engineering removes, so cross-region commits are bounded by the speed of light. The operational surface is heavier, the failure modes are different and less familiar, and even Postgres-compatible systems differ in the details that matter under load. Multi-region writes with strong consistency is the requirement that genuinely justifies it — and if that is the actual requirement, I would say so and support the move.

What I would resist is adopting it pre-emptively for scale that has not arrived, because the cost is paid continuously from day one while the benefit arrives only if the growth does.

-- Given only these settings, infer the architecture.

-- ── ENGINE A ────────────────────────────────────────────────────────────
--   shared_buffers, effective_cache_size, autovacuum_vacuum_scale_factor,
--   max_connections, wal_level, checkpoint_timeout, random_page_cost
-- INFER:
--   "shared_buffers" + "effective_cache_size" → a B+tree page cache AND
--     reliance on the OS page cache (a small pool by design → Postgres)
--   "autovacuum" → MVCC with old versions IN THE TABLE. Bloat is the
--     operational concern; rollback is free.
--   "max_connections" as a tuned limit → process per connection, so a
--     pooler will be needed.
--   "wal_level" → write-ahead logging, which also implies replication
--     and PITR are available from the same mechanism.
--   "random_page_cost" → a COST-BASED planner exposing its constants.
-- → PostgreSQL. And I now know to check vacuum health, connection count
--   and cost constants before anything else.

-- ── ENGINE B ────────────────────────────────────────────────────────────
--   compaction_throughput_mb_per_sec, bloom_filter_fp_chance,
--   memtable_flush_writers, gc_grace_seconds, tombstone_warn_threshold
-- INFER:
--   "compaction" + "memtable" → LSM-TREE (lesson 4).
--   "bloom_filter" → confirms it: bloom filters exist to avoid probing
--     SSTables that lack the key.
--   "gc_grace_seconds" + "tombstone" → deletes are TOMBSTONES, and they
--     must outlive a replica-divergence window → DISTRIBUTED with
--     eventual consistency.
-- → Cassandra/Scylla. I now know: excellent ingest, delete-heavy
--   workloads are pathological, and queries must be modelled per access
--   pattern because there are no joins.

-- ── ENGINE C ────────────────────────────────────────────────────────────
--   innodb_buffer_pool_size, innodb_buffer_pool_instances,
--   innodb_flush_log_at_trx_commit, innodb_flush_method=O_DIRECT,
--   innodb_log_file_size
-- INFER:
--   "buffer_pool" sized large + "O_DIRECT" → BYPASSES the OS cache, so
--     the pool should be ~75% of RAM (the OPPOSITE of engine A).
--   "buffer_pool_instances" → the pool is SHARDED to reduce mutex
--     contention → thread-per-connection with many cores.
--   "flush_log_at_trx_commit" → the durability dial.
-- → MySQL/InnoDB. I now know: size the pool large, keep the primary key
--   narrow (clustered index), and watch History list length rather than
--   dead tuples.

-- ── THE POINT ───────────────────────────────────────────────────────────
-- The tuning surface IS the architecture, made visible. Before reading
-- any marketing, read the configuration reference — it tells you what
-- the designers thought was worth exposing, which is the same as what
-- they thought would need managing.
2 (easy): Predict the same schema's behaviour on Postgres and InnoDB.
Solution 
CREATE TABLE orders (
    id          uuid PRIMARY KEY,              -- random v4
    customer_id bigint NOT NULL,
    status      varchar(20) NOT NULL,
    total       decimal(12,2) NOT NULL,
    created_at  timestamp NOT NULL,
    updated_at  timestamp NOT NULL
);
CREATE INDEX ON orders (customer_id);
CREATE INDEX ON orders (status);
CREATE INDEX ON orders (created_at);
CREATE INDEX ON orders (updated_at);
-- Workload: 5k inserts/sec, 20k status updates/sec.

-- ── PREDICTION: POSTGRESQL ──────────────────────────────────────────────
-- • Random UUID PK scatters INDEX inserts (~50% page density), but rows
--   go into the heap wherever there is room, so the TABLE is unaffected.
-- • The index on `updated_at` is fatal: it changes on every update, so
--   NO update can be HOT. Each update writes a new tuple plus entries in
--   all 5 indexes.
-- • 20k non-HOT updates/sec → 20k dead tuples/sec → 1.7 BILLION/day.
--   Autovacuum at the default 20% scale factor will never keep up.
-- • PREDICTED FAILURE: table and index bloat within days, cache hit rate
--   collapse, and eventually transaction-id wraparound risk.
SELECT n_tup_hot_upd::float/NULLIF(n_tup_upd,0) FROM pg_stat_user_tables;
-- expect ~0.

-- ── PREDICTION: MYSQL/INNODB ────────────────────────────────────────────
-- • Random UUID PK is WORSE here: the table IS the PK's B+tree, so
--   inserts scatter the ACTUAL ROWS, causing page splits throughout.
-- • Every one of the 4 secondary indexes stores the 16-byte UUID as its
--   row pointer → all four are substantially larger and less cacheable.
-- • No vacuum, so no bloat — but 20k updates/sec generate undo, and any
--   long-running reporting transaction makes undo chains grow and reads
--   slow progressively.
-- • PREDICTED FAILURE: insert throughput degrades as the table grows;
--   History list length climbs during reports.
SHOW ENGINE INNODB STATUS;    -- watch "History list length"

-- ── THE SHARED FIXES ────────────────────────────────────────────────────
-- 1. id → bigint (or UUIDv7 if client generation is required).
--    Larger effect on InnoDB, meaningful on both.
-- 2. DROP the index on updated_at. On Postgres it restores HOT updates
--    (the single biggest win). On InnoDB it removes a per-update index
--    write. Serve admin queries from a replica.
-- 3. varchar(20) status → a smallint FK, or an enum.
-- 4. timestamp → timestamptz on Postgres: the original is permanently
--    ambiguous about zone and cannot be fixed later.
-- 5. Postgres only: fillfactor 80 so the new version fits on the page.

-- ── THE LESSON ──────────────────────────────────────────────────────────
-- ONE schema, two engines, DIFFERENT dominant failure modes — bloat
-- versus undo growth and index inflation — from the same root causes.
-- Predicting which symptom you will see requires knowing where the
-- engine puts old versions and whether the table is clustered.
3 (medium): Decide between SQLite and Postgres with actual numbers.
Solution 
-- SITUATION: an internal tool. 200 users, ~50 concurrent. 40 reads/sec,
-- 3 writes/sec. 8 GB of data. Deployed as a single container.
-- The team assumes Postgres. Should they?

-- ── STEP 1: DOES THE WRITE LIMIT BIND? ──────────────────────────────────
-- SQLite: ONE write transaction at a time, database-wide.
-- In WAL mode a write transaction is ~0.1-1 ms.
--   → theoretical ceiling ~1,000-10,000 writes/sec
--   → required: 3/sec.  Headroom: 300-3000×.
-- ✓ The single-writer limit does NOT bind. This is the question people
--   skip, and it is usually the only one that matters.

-- ── STEP 2: DO READS SCALE? ─────────────────────────────────────────────
PRAGMA journal_mode = WAL;    -- readers no longer block the writer
-- Unlimited concurrent readers. 40 reads/sec is nothing.
-- ✓ AND each read avoids a network round trip: ~5 μs in-process versus
--   ~200 μs to a local Postgres socket. The tool will feel FASTER.

-- ── STEP 3: WHAT DO WE GIVE UP? ─────────────────────────────────────────
-- ✗ multi-machine access — the container must own the file; network
--   filesystems break SQLite's locking model
-- ✗ horizontal scaling of writes (not needed here)
-- ✗ some SQL features: no full outer join before 3.39, weaker ALTER
--   TABLE, dynamic typing unless STRICT tables are used
-- ✗ concurrent schema migrations
-- ✓ MITIGATE the dynamic typing, which is the real correctness risk:
CREATE TABLE orders (...) STRICT;     -- 3.37+: enforces declared types
PRAGMA foreign_keys = ON;             -- ⚠ OFF by default

-- ── STEP 4: WHAT DO WE GAIN? ────────────────────────────────────────────
-- • no database server to deploy, monitor, patch or back up separately
-- • backup is copying one file (or `VACUUM INTO` for a consistent copy)
-- • tests run against the real engine with zero setup
-- • no connection pool, no connection limits, no network failure mode
-- • the whole application is one container with one volume

-- ── STEP 5: DURABILITY AND OPERATIONS ───────────────────────────────────
PRAGMA synchronous = FULL;     -- fsync per commit; NORMAL is the usual
                               -- compromise in WAL mode
-- Replication/backup: Litestream streams the WAL to object storage
-- continuously, giving point-in-time recovery — which closes the gap
-- that most people assume is disqualifying.

-- ── THE DECISION ────────────────────────────────────────────────────────
-- ✓ SQLite, with WAL mode, STRICT tables, foreign keys on, and
--   Litestream for backup.
-- REVISIT IF: writes exceed a few hundred per second, the app must run
--   on multiple machines, or online schema migrations become frequent.
--
-- ⚠ THE HONEST CAVEAT: if the team already runs Postgres for other
--   services, using it here may still be right — operational uniformity
--   has real value, and "one system the team already operates" is the
--   same argument that usually favours Postgres. The point of the
--   exercise is that the choice should follow from the numbers, not from
--   the assumption that a server-based database is the serious option.
4 (medium): Explain three engines' behaviour on one workload from architecture alone.
Solution 
-- WORKLOAD: a shopping cart. Read the cart (10 items), add/remove items
-- frequently, cart abandoned after 30 min and deleted. 50k active carts,
-- 5k operations/sec, mostly updates.

-- ── POSTGRESQL ──────────────────────────────────────────────────────────
-- PREDICT from architecture (MVCC in-table, heap, HOT updates):
--   • Every cart update writes a new tuple. 5k/sec = 432M dead
--     tuples/day.
--   • Deletes after 30 min add more dead tuples.
--   • IF no indexed column changes and fillfactor leaves room, HOT
--     updates keep it manageable; otherwise every index is rewritten.
--   • The table is small (50k live rows) but will BLOAT enormously
--     relative to its live size unless autovacuum is tuned aggressively.
-- ✓ VERDICT: workable with fillfactor 70, minimal indexes, and
--   autovacuum_vacuum_scale_factor at 0.01. But this is fighting the
--   architecture — high-churn ephemeral data is exactly what in-table
--   MVCC handles worst.

-- ── REDIS ───────────────────────────────────────────────────────────────
-- PREDICT (in-memory, single-threaded command loop, no MVCC):
--   • Updates modify memory in place. No versions, no vacuum, no bloat.
--   • TTL expiry is built in — the 30-minute abandonment is a native
--     feature rather than a delete + cleanup job.
--   • A hash per cart; 50k carts × 10 items is a few hundred MB.
-- ✓ VERDICT: this workload is precisely what Redis is for. Ephemeral,
--   high-churn, keyed access, natural expiry.
-- ⚠ THE TRADE: durability is weaker (RDB snapshots or AOF), and if a
--   cart must survive a crash you need AOF with fsync — or accept that
--   losing a few seconds of cart edits is acceptable, which for carts it
--   usually is. That is a product decision, and it should be stated.

-- ── MONGODB ─────────────────────────────────────────────────────────────
-- PREDICT (document model, WiredTiger B+tree with MVCC):
--   • The cart IS a document, so updating an item is one document write
--     with no join — a genuinely good model fit.
--   • TTL indexes handle expiry natively.
--   • WiredTiger's MVCC uses an undo-like mechanism, so no Postgres-style
--     table bloat.
-- ✓ VERDICT: a reasonable fit. The document shape matches the access
--   pattern, which is the honest case for a document store.

-- ── WHAT THIS COMPARISON SHOWS ──────────────────────────────────────────
-- The best answer is the one whose ARCHITECTURE matches the data's
-- lifecycle. Cart data is ephemeral, high-churn, keyed, and
-- self-expiring. In-table MVCC is the worst possible match for that, and
-- no amount of tuning changes the underlying mismatch — it only makes it
-- survivable.
-- ✓ THE PRACTICAL ARCHITECTURE: carts in Redis, orders in Postgres. The
--   moment a cart becomes an order it moves to the system with
--   transactions and durability. That boundary follows directly from the
--   data's properties, and it is a better answer than choosing one
--   engine for everything.
5 (hard): Write an evaluation for adopting a new database.
Solution 
-- PROPOSAL: "Move the events pipeline from Postgres to ClickHouse."
-- Write the evaluation a staff engineer should produce.

-- ── 1. WHAT PROBLEM ARE WE SOLVING? (state it as a measurement) ─────────
-- ✓ "Analytical queries over 4.2B events take 40-300s. Product wants
--    sub-5s. Ingest is 80k events/sec and the primary is at 70% CPU."
-- ✗ NOT: "Postgres doesn't scale for analytics."
-- ⚠ If the problem cannot be stated with numbers, the evaluation stops
--   here — and saying so is the valuable contribution.

-- ── 2. HAVE WE EXHAUSTED THE INCUMBENT? ─────────────────────────────────
--   [x] partitioned by time; pruning verified in EXPLAIN
--   [x] covering indexes on the top query shapes
--   [x] materialised views for the 14 KNOWN dashboard queries → 2ms
--   [x] analytics moved to a replica
--   [ ] columnar extension (Hydra/Timescale compression) on old
--       partitions — NOT YET TRIED
-- ⚠ The remaining gap is AD-HOC queries over full history, which
--   pre-aggregation cannot serve by definition. That is the honest case
--   for columnar — and it should be stated as the specific residual,
--   not as a general failure of Postgres.
-- → RECOMMEND trying the columnar extension first: same database, same
--   SQL, no pipeline. Two weeks to prove or disprove.

-- ── 3. WHAT WOULD CLICKHOUSE ACTUALLY BUY? (predict, then verify) ───────
-- From the architecture (lesson 13): 4 of 40 columns, 10-20×
-- compression, zone maps, vectorised execution.
--   PREDICTED: 40-300s → 1-3s. Storage 1.1 TB → ~90 GB.
-- ✓ Then VERIFY on a real subset with real data distribution, at a size
--   exceeding memory, running long enough for merges to matter.

-- ── 4. WHAT DOES IT COST? (the section usually missing) ─────────────────
-- • THE PIPELINE IS A SYSTEM. CDC, schema evolution in two places,
--   backfills, lag monitoring. Frequently harder to operate than either
--   database. It needs a named owner.
-- • EVENTUAL CONSISTENCY. Numbers will disagree with the application.
--   Display the lag or someone will act on stale data.
-- • NO TRANSACTIONS, no FKs, no unique constraints. Integrity must be
--   enforced upstream and validated after load.
-- • MUTATIONS ARE ASYNCHRONOUS. GDPR deletion requests are not a
--   DELETE — they are a background mutation with no completion
--   guarantee at a given time. ⚠ This is a compliance question, not a
--   performance one, and it is routinely discovered late.
-- • A SECOND COPY OF PERSONAL DATA: access control, retention and
--   deletion now apply twice.
-- • TEAM CAPABILITY: who debugs a stuck merge at 3am?

-- ── 5. WHAT ARE THE ALTERNATIVES? ───────────────────────────────────────
-- (a) columnar extension in Postgres — least disruption      ← try first
-- (b) nightly Parquet export + DuckDB — two moving parts, no cluster,
--     serves ad-hoc analysis well if hours-old data is acceptable
-- (c) ClickHouse with CDC — most capable, most operational cost
-- (d) a managed warehouse — trades cost for operational burden

-- ── 6. THE RECOMMENDATION ───────────────────────────────────────────────
-- Phase 1 (2 wks): columnar extension on partitions older than 90 days.
--   Measure against the 14 dashboard queries and 20 sampled ad-hoc ones.
-- Phase 2 (2 wks): if insufficient, nightly Parquet + DuckDB for
--   analysts. Two moving parts, no streaming pipeline.
-- Phase 3: ClickHouse + CDC only if (1) and (2) demonstrably fail, with
--   a named pipeline owner and the compliance question answered first.
-- ✓ Each phase is independently valuable and reversible.

-- ── 7. HOW WE WILL KNOW WE WERE RIGHT ───────────────────────────────────
-- Instrument analyst queries: what percentage complete within the target
-- latency? Review in 90 days. If phase 1 or 2 holds above ~90%, phase 3
-- is not justified — and having the number turns a future architectural
-- argument into an evidence-based decision rather than a preference.
6 (hard): Design a polyglot architecture and justify every boundary.
Solution 
-- SYSTEM: a marketplace. Users, listings, orders, messaging, search,
-- recommendations, analytics, and an audit trail.
-- Design the data layer. Justify each engine by ACCESS PATTERN.

-- ── THE DEFAULT: ONE POSTGRES ───────────────────────────────────────────
-- users, listings, orders, order_items, payments, messages
-- WHY: transactional, relational, needs foreign keys and multi-statement
-- ACID. An order touching inventory, payment and fulfilment must be
-- atomic — that requirement alone rules out most alternatives.
-- ⚠ START HERE FOR EVERYTHING and move things out only with a reason.
--   Every boundary below must justify its existence.

-- ── SEARCH → Elasticsearch/OpenSearch (or Postgres FTS first) ───────────
-- ACCESS PATTERN: full-text relevance ranking, faceting, typo tolerance,
--   synonyms — over listings.
-- WHY NOT POSTGRES: tsvector + GIN handles basic full-text well and
--   should be TRIED FIRST. It does not do relevance tuning, faceted
--   aggregation or fuzzy matching at the quality users now expect.
-- ⚠ THE COST: a sync pipeline, and search results that lag writes. A
--   listing edited and immediately searched may show stale text —
--   acceptable for search, unacceptable for the listing page itself,
--   which reads from Postgres.

-- ── SESSIONS + CART + RATE LIMITS → Redis ───────────────────────────────
-- ACCESS PATTERN: ephemeral, high-churn, keyed, natural TTL expiry.
-- WHY NOT POSTGRES: this is precisely the worst fit for in-table MVCC —
--   every update makes a dead tuple, and 30-minute expiry means constant
--   deletes (exercise 4). Redis expires natively and never bloats.
-- ⚠ THE COST: weaker durability. Fine for sessions and carts; a cart
--   becomes an ORDER in Postgres the moment it is paid for. That
--   boundary is where durability starts mattering, and it should be
--   explicit in the code.

-- ── EVENTS + ANALYTICS → columnar, via CDC ──────────────────────────────
-- ACCESS PATTERN: append-only, billions of rows, few columns per query,
--   ad-hoc exploration, retention by age.
-- WHY NOT POSTGRES: a row store reads all 40 columns to aggregate 3
--   (lesson 13). Pre-aggregation covers the known dashboards; it cannot
--   cover ad-hoc analysis.
-- ✓ TRY IN ORDER: materialised views → columnar extension → Parquet +
--   DuckDB → ClickHouse. Do not start at the end.

-- ── AUDIT LOG → Postgres, partitioned, then archived ────────────────────
-- ACCESS PATTERN: append-only, immutable, rarely read, 7-year retention.
-- WHY POSTGRES: it must be transactionally consistent with the actions
--   it records — writing the audit row in the SAME transaction is the
--   only way to guarantee that. A separate system would be
--   best-effort, which defeats the purpose.
-- ✓ Partition by month; DETACH and export to Parquet after 90 days.

-- ── RECOMMENDATIONS → offline batch + Redis for serving ─────────────────
-- ACCESS PATTERN: expensive batch computation, then microsecond lookups.
-- ✓ Compute nightly in the analytics system, write the results to Redis
--   keyed by user. The serving path never touches the model.

-- ── WHAT I REFUSED TO SPLIT OUT ─────────────────────────────────────────
-- ✗ MESSAGING into its own database: it joins to users and listings, and
--   the volume is unremarkable. A separate store would buy nothing and
--   cost a join across systems.
-- ✗ LISTINGS into a document store because they have variable
--   attributes: JSONB alongside real columns handles that while keeping
--   constraints and joins (SQL schema-design lesson).
-- ✗ A SERVICE-PER-TABLE database split: that is an organisational
--   decision dressed as a technical one, and it makes every cross-entity
--   invariant a distributed-transaction problem.

-- ── THE RULE I APPLIED THROUGHOUT ───────────────────────────────────────
-- Move data out of the primary database ONLY when its access pattern
-- fights the architecture — ephemeral high-churn (Redis), wide-scan
-- analytical (columnar), or relevance search (Elasticsearch). Everything
-- else stays, because every boundary adds a pipeline, an eventual
-- consistency question, and a second place for personal data. Four
-- systems, each with a stated reason and a stated cost — and the
-- reasons are all access patterns, not preferences.

🎯 Key Takeaways

  • Six questions — storage structure, durability, concurrency, layout, indexing, planning — characterise any engine and predict its behaviour before you benchmark.
  • PostgreSQL's heap plus in-table MVCC gives free rollback and redo-only recovery, and bills you in vacuum, bloat and wraparound risk.
  • Its process-per-connection model makes a pooler mandatory at scale, and its extensibility is why it keeps absorbing adjacent categories.
  • InnoDB's clustered index makes primary-key width a first-order concern, since the PK orders the table and is copied into every secondary index.
  • A long transaction hurts every MVCC engine but shows differently: Postgres bloats, InnoDB's undo chains lengthen and reads slow.
  • Isolation level names are not portable — InnoDB's Repeatable Read permits lost updates where Postgres aborts.
  • SQLite is the most deployed database in existence and is often faster in-process; its real limits are concurrent writers and multi-machine access.
  • DuckDB is the analytical counterpart — columnar, vectorised, queries Parquet directly, and makes a two-part reporting stack viable.
  • Many distinct-looking systems share RocksDB as their storage layer, so they share its amplification profile and compaction behaviour.
  • Default to PostgreSQL until you can name the missing property with a measurement — one system a team can operate beats two it cannot.
