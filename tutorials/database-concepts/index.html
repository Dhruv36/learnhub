How a Database Stores Data Foundations

What you'll master: the layered architecture every relational engine shares and why that shape is nearly universal, the single most important number in database performance — the gap between a memory access and a disk access — and how every design decision downstream falls out of it, why databases organise data into fixed-size pages rather than reading rows individually, the read-optimised versus write-optimised split that separates B-trees from LSM-trees, what durability physically requires and why the write-ahead log exists, and how to reason about an engine you have never used by asking which of these trade-offs it made. This track is about what happens underneath the SQL — the design perspective plus the storage-engine internals. Prerequisites: comfort with SQL as a language; the SQL track covers that. Distribution topics — CAP, replication, consensus, sharding — deliberately live in the System Design track and are not repeated here.

--   SQL Server all look like this, because each layer solves a problem
--   created by the one below it. Pages exist because disks are block
--   devices. The buffer pool exists because pages are slow to fetch. The
--   WAL exists because the buffer pool holds changes that are not on
--   disk yet. Recovery exists because the WAL might be all you have.
--
--   Learn the pressure that creates each layer and you can reason about
--   any engine, including ones that do not exist yet.

Part 2 — The Number That Explains Everything

-- Every storage-engine design decision is an answer to ONE fact:
-- storage is slower than memory by an amount most people underestimate.

  L1 cache            ~1 ns
  Main memory (RAM)   ~100 ns          ← the baseline
  NVMe SSD read       ~20,000 ns       (20 μs)     200× slower than RAM
  SATA SSD read       ~100,000 ns      (100 μs)  1,000×
  Spinning disk seek  ~10,000,000 ns   (10 ms)  100,000×

-- ── SCALE IT TO HUMAN TIME (RAM = 1 second) ─────────────────────────────
  RAM              1 second
  NVMe             3.5 minutes
  SATA SSD         17 minutes
  Disk seek        4 MONTHS
--
-- A query that hits RAM answers "instantly". The same query going to a
-- spinning disk waits four months per seek in these terms. THIS is why
-- databases are architected the way they are — everything is an attempt
-- to avoid, batch, or sequence that access.

-- ── THE SECOND FACT: SEQUENTIAL BEATS RANDOM ────────────────────────────
  NVMe sequential read     ~3,000 MB/s
  NVMe random 4KB reads    ~400 MB/s      (~7× worse)
  Disk sequential read       ~150 MB/s
  Disk random 4KB reads        ~1 MB/s    (~150× worse)
--
-- This single ratio explains an enormous amount:
--   • why the planner may prefer a full scan over an index (SQL
--     optimisation lesson) — reading everything sequentially can beat
--     fetching 30% of rows randomly
--   • why the WAL is an APPEND-ONLY sequential file
--   • why LSM-trees exist at all: they convert random writes into
--     sequential ones
--   • why a random-UUID primary key hurts: it scatters inserts across
--     the whole B-tree instead of appending to one hot page

-- ── THE THIRD FACT: WRITES MUST SURVIVE POWER LOSS ──────────────────────
-- A write that reaches the OS is not durable — it sits in a kernel
-- buffer. Durability requires fsync(), forcing the data through to
-- stable storage. fsync is EXPENSIVE (hundreds of microseconds to
-- milliseconds), so it must not happen per row.
-- ✓ The resolution: fsync ONE sequential log file per commit, and write
--   the actual data pages lazily afterwards. That is the write-ahead
--   log, and it is the single most important idea in database
--   durability (lesson 6).
📏 Every engine internal is an answer to the memory/disk gap. Pages exist because you cannot economically fetch one row at a time. The buffer pool exists to avoid fetching the same page twice. B-trees exist to find a row in three or four fetches instead of thousands. LSM-trees exist to turn random writes into sequential ones. The WAL exists so one sequential fsync can make many scattered changes durable. When you meet an unfamiliar mechanism, ask "which access cost is this avoiding?" — the answer is almost always in the table above.

Part 3 — Pages: The Universal Unit

-- Databases never read "a row". They read a PAGE (also called a block):
-- a fixed-size chunk, typically 4KB, 8KB or 16KB.
--
--   Postgres  8KB      MySQL/InnoDB  16KB    SQLite  4KB (default)
--   Oracle    2-32KB   SQL Server    8KB

-- ── WHY A FIXED SIZE, AND WHY THAT SIZE? ────────────────────────────────
-- 1. Storage devices are BLOCK devices — you cannot read 40 bytes from
--    an SSD; the smallest unit is a sector (512B-4KB). Reading less than
--    a block costs the same as reading a block.
-- 2. Fixed size makes memory management tractable: the buffer pool is an
--    array of identical slots, so there is no fragmentation and no
--    variable-size allocator in the hot path.
-- 3. Locality pays off: rows are usually read together with their
--    neighbours, so fetching 8KB to read one 200-byte row is not as
--    wasteful as it sounds — the next query often wants a neighbour.
--
-- THE TRADE-OFF IN THE SIZE ITSELF:
--   Larger pages  → fewer, bigger I/Os; shallower B-trees; better for
--                   scans. But more wasted memory for point lookups, and
--                   more write amplification (a 1-byte change dirties
--                   the whole page).
--   Smaller pages → less waste per random read; more I/O operations and
--                   deeper trees.
-- 8KB is the historical compromise for mixed OLTP workloads. Analytical
-- systems use far larger blocks because they only ever scan.

-- ── WHAT LIVES INSIDE A PAGE ────────────────────────────────────────────
  ┌─────────────────────────────────────────┐
  │ HEADER  checksum, LSN, free-space ptrs  │  ← 24 bytes in Postgres
  ├─────────────────────────────────────────┤
  │ line pointers →→→                       │  ← a small indirection
  ├─────────────────────────────────────────┤
  │              FREE SPACE                 │
  ├─────────────────────────────────────────┤
  │ ←←← row data (grows upward)             │
  └─────────────────────────────────────────┘
-- Pointers grow down from the top, rows grow up from the bottom, and
-- they meet in the middle. The indirection through line pointers means a
-- row can move WITHIN a page (during compaction) without invalidating
-- any index that points at it — indexes reference the slot, not the
-- byte offset. Lesson 2 takes this apart properly.

-- ── THE CONSEQUENCE THAT SHOWS UP IN YOUR SCHEMA ────────────────────────
-- If rows are 200 bytes, an 8KB page holds ~40. Reading 40 rows costs
-- ONE I/O. Widen the row to 2KB and the same page holds 4 — so the same
-- query needs 10× the I/O.
-- ✓ THIS is the real reason SELECT * on a wide table is expensive, and
--   why narrow tables scan faster. Column count is an I/O decision, not
--   a style preference.

Part 4 — The Great Divide: Read-Optimised vs Write-Optimised

-- Almost every storage engine in production is one of two families.
-- Knowing which one you are using predicts its behaviour better than
-- any benchmark.

-- ── B+TREE (Postgres, MySQL/InnoDB, SQLite, Oracle, SQL Server) ─────────
-- Data kept SORTED in a shallow balanced tree, updated IN PLACE.
--   ✓ reads are predictable: ~3-4 page fetches at any table size
--   ✓ range scans and ORDER BY are free — the leaves are already sorted
--   ✗ a random write means: read the page, modify it, write it back —
--     random I/O, and a whole page dirtied for a few bytes
--   → The default choice, and correct for most OLTP workloads.
--     Lesson 3.

-- ── LSM-TREE (RocksDB, Cassandra, ScyllaDB, LevelDB, ClickHouse-ish) ────
-- Writes go to an in-memory table, then get flushed as immutable SORTED
-- FILES, which are merged (compacted) in the background.
--   ✓ writes are SEQUENTIAL and fast — the whole point
--   ✓ excellent compression (immutable sorted files)
--   ✗ a read may check several files → read amplification, mitigated
--     with bloom filters
--   ✗ compaction consumes I/O in the background, forever, and creates
--     latency spikes you must tune for
--   → Chosen for write-heavy workloads: time series, event logs,
--     metrics. Lesson 4.

-- ── THE THREE AMPLIFICATIONS (the vocabulary for this trade-off) ────────
-- READ amplification   pages read per logical read.
--                      B-tree: low (~3-4). LSM: higher (several files).
-- WRITE amplification  bytes written per logical byte.
--                      B-tree: a full page per row change.
--                      LSM: low initially, but compaction rewrites data
--                      repeatedly — often HIGHER overall.
-- SPACE amplification  disk used per logical byte.
--                      B-tree: page fragmentation and MVCC bloat.
--                      LSM: obsolete versions awaiting compaction.
--
-- ⚠ YOU CANNOT MINIMISE ALL THREE. This is the RUM conjecture (Read,
--   Update, Memory), and it is the storage-engine equivalent of CAP:
--   improving two comes at the third's expense. Every engine picks a
--   corner, and its "personality" — what it is good and bad at — follows
--   from that choice rather than from implementation quality.
QuestionB+TreeLSM-Tree
Point lookupExcellent, predictableGood; bloom filters avoid most file checks
Range scan / ORDER BYExcellent — leaves are sorted and linkedGood, but merges across several files
Random write throughputLimited by random page I/OExcellent — appends only
Write amplificationA page per row changeLower up front, higher via compaction
CompressionModest — pages mutate in placeStrong — files are immutable

Part 5 — Durability: What Actually Happens at COMMIT

-- A puzzle that motivates the whole design:
--   Data pages live in the buffer pool (memory). Writing every modified
--   page to disk at COMMIT would mean random I/O across the whole file,
--   which is far too slow. But not writing them means a crash loses the
--   transaction. How can a commit be both fast AND durable?

-- ── THE ANSWER: WRITE-AHEAD LOGGING ─────────────────────────────────────
-- 1. modify the page in the buffer pool          (memory, fast)
-- 2. APPEND a description of the change to the WAL (SEQUENTIAL, fast)
-- 3. fsync the WAL                                ← the durability point
-- 4. COMMIT returns
-- 5. later, a CHECKPOINT writes dirty pages to their real homes
--
-- The trick is that one sequential fsync of a small log record makes
-- many scattered page changes durable. Random work becomes sequential
-- work, which is the recurring theme of this entire subject.
--
-- THE RULE THAT NAMES IT: the log record describing a change must reach
-- durable storage BEFORE the data page it describes. Hence WRITE-AHEAD.

-- ── WHY THIS SURVIVES A CRASH ───────────────────────────────────────────
-- On restart the engine finds the last checkpoint and replays the WAL
-- forward from it:
--   REDO   re-apply committed changes missing from the data pages
--   UNDO   roll back changes from transactions that never committed
-- This is ARIES, the recovery algorithm nearly every engine implements.
-- Lesson 6 covers it in full, including why recovery must itself be
-- crash-safe — the machine can fail again DURING recovery.

-- ── THE SAME LOG, THREE JOBS ────────────────────────────────────────────
-- Once you have a durable, ordered record of every change, you get:
--   • crash recovery      (its original purpose)
--   • REPLICATION         ship the log to another server and replay it
--   • POINT-IN-TIME       replay from a backup to any moment
--   • CHANGE DATA CAPTURE decode it into a stream for other systems
-- One mechanism, four features. This is why the WAL is the piece of a
-- database most worth understanding — and why the SQL track's scaling
-- lesson is really a lesson about the log.

Part 6 — How to Read an Unfamiliar Engine

-- The practical payoff of this track: a checklist that tells you how any
-- database will behave before you benchmark it.

-- 1. WHAT IS THE STORAGE STRUCTURE?  B+tree, LSM, columnar, in-memory?
--    → predicts read/write/space amplification and latency shape.
-- 2. HOW DOES IT ACHIEVE DURABILITY?  WAL? fsync per commit or grouped?
--    Can durability be relaxed?
--    → predicts write throughput and the data-loss window.
-- 3. HOW DOES IT HANDLE CONCURRENCY?  MVCC (readers never block) or
--    locking (readers may block)? Where are old versions kept —
--    in-table like Postgres, or in an undo log like InnoDB and Oracle?
--    → predicts behaviour under mixed read/write load, and whether you
--      will be fighting bloat or fighting long undo chains.
-- 4. ROW-ORIENTED OR COLUMNAR?
--    → predicts OLTP versus analytics suitability (lesson 13).
-- 5. HOW DOES IT INDEX?  Clustered primary key (InnoDB) or heap plus
--    secondary indexes (Postgres)?
--    → predicts whether secondary-index lookups need a second descent,
--      and how much primary-key width costs you.
-- 6. HOW DOES THE PLANNER DECIDE?  Cost-based with statistics, or
--    rule-based? Can you see and influence the plan?
--    → predicts how it fails: cost-based planners fail by mis-estimating
--      (lesson 10).

-- ── APPLYING IT: TWO ENGINES, ONE QUESTION ──────────────────────────────
-- "Why is a UUID primary key worse in MySQL than in Postgres?"
-- InnoDB CLUSTERS the table by the primary key — the rows ARE the PK's
-- B+tree — and every secondary index stores the PK as its row pointer.
-- So a random 16-byte UUID PK scatters inserts across the whole table
-- AND inflates every secondary index by 16 bytes per entry.
-- Postgres keeps rows in a heap with a separate index, so a random PK
-- scatters only the index, not the table.
-- Same schema decision, materially different cost — and you can derive
-- that from question 5 alone, without a benchmark.

Interview Questions

Beginner: Why do databases read pages instead of individual rows?

Because storage devices are block devices. The smallest unit an SSD or disk can transfer is a sector, typically between 512 bytes and 4KB, so reading forty bytes costs the same as reading a whole block. Given that, the database may as well work in fixed-size chunks and get useful neighbouring data for free.

Fixed-size pages also make memory management simple. The buffer pool becomes an array of identical slots, so there is no fragmentation and no variable-size allocation in the hot path. And locality genuinely pays: rows written together are usually read together, so fetching an 8KB page to read one 200-byte row often serves the next several queries too.

The practical consequence is worth stating, because it turns an internal detail into a schema decision. If rows are 200 bytes an 8KB page holds about forty of them, so a scan reads forty rows per I/O. Widen rows to 2KB and the same page holds four, so the identical query needs ten times the I/O. That is the real reason SELECT * on a wide table is expensive and why narrow tables scan faster — it is an I/O consequence, not a style preference.

Beginner: What is a write-ahead log and why does it exist?

It exists to resolve a conflict between speed and durability. Modified pages live in the buffer pool in memory, and writing all of them to their real locations on disk at commit time would mean random I/O scattered across the whole data file — far too slow to do per transaction. But leaving them only in memory means a crash loses committed work.

The write-ahead log resolves it by separating the record of a change from the change itself. The engine modifies the page in memory, appends a compact description of the change to a sequential log file, and fsyncs that one file. Once the log record is durable, the transaction can commit, because the change can always be reconstructed. The actual data pages are written later, in bulk, at a checkpoint. The name comes from the ordering rule: the log record must reach stable storage before the data page it describes.

What makes it elegant is that one sequential fsync makes many scattered changes durable, converting random work into sequential work. And the same log turns out to serve three more purposes almost for free — replication ships and replays it, point-in-time recovery replays it from a backup, and change data capture decodes it into an event stream. One mechanism, four capabilities.

Mid: Compare B-trees and LSM-trees. When would you choose each?

A B+tree keeps data sorted in a shallow balanced tree and updates it in place. Lookups cost three or four page fetches regardless of table size, and because the leaves are sorted and linked, range scans and ORDER BY come essentially free. The weakness is writes: changing a row means reading its page, modifying it, and writing the whole page back, which is random I/O and dirties several kilobytes to change a few bytes.

An LSM-tree inverts that. Writes land in an in-memory structure and are flushed as immutable sorted files, so all write I/O is sequential and therefore fast. Background compaction merges those files to keep read costs bounded. The costs are that a read may have to consult several files — mitigated with bloom filters — and that compaction consumes I/O continuously and produces latency spikes that must be tuned for. Because the files are immutable, compression is much more effective.

I would choose a B-tree for typical OLTP: mixed reads and writes, range queries, and a need for predictable latency — orders, users, ledgers. I would choose an LSM-tree for write-heavy, append-shaped workloads such as time series, metrics and event logs, where write throughput and compression matter more than tail-latency smoothness.

The framing I would offer is the RUM conjecture: you can optimise for read cost, write cost, or space, but improving two comes at the expense of the third. Neither structure is better — each picks a corner, and its strengths and weaknesses follow from that choice rather than from implementation quality.

Mid: Why is a random UUID primary key more damaging in MySQL/InnoDB than in PostgreSQL?

The difference comes from how each engine physically organises rows. InnoDB uses a clustered index: the table is the primary key's B+tree, with the full row stored in the leaf. PostgreSQL stores rows in an unordered heap with indexes as separate structures pointing into it.

With a random UUIDv4 primary key in InnoDB, each insert belongs at a random position in the tree that holds the actual data, so inserts scatter across the whole table. That causes page splits, poor cache locality, and a working set far larger than the data warrants, because every insert dirties a different page. There is a second cost specific to clustering: every secondary index stores the primary key as its row pointer, so a sixteen-byte UUID inflates every secondary index rather than just the primary one. That is why "keep the primary key narrow" is much stronger advice in MySQL.

In PostgreSQL the same key scatters the index but not the table, since new rows are simply appended to the heap wherever there is space. The damage is real but confined to one structure.

The fix in both cases is a time-ordered identifier — UUIDv7, ULID or Snowflake — which restores insert locality while keeping global uniqueness. Alternatively, keep a compact bigint internally and expose an opaque public identifier. What I like about this question is that you can derive the whole answer from one architectural fact about each engine, without benchmarking anything.

Senior: You must evaluate an unfamiliar database. What do you ask, and in what order?

I would characterise the engine before benchmarking it, because a benchmark tells you how it handled your test while the architecture tells you how it will behave on workloads you have not thought of yet. Six questions cover most of it.

First, the storage structure — B-tree, LSM, columnar, or in-memory — because that predicts the read, write and space amplification profile and the shape of its latency. Second, how durability works: is there a write-ahead log, does it fsync per commit or group commits, and can durability be relaxed? That sets the ceiling on write throughput and defines the data-loss window during a crash. Third, the concurrency model: MVCC or locking, and if MVCC, where old versions live — in the table as Postgres does, or in an undo log like InnoDB and Oracle. That determines whether readers block writers, and whether operationally you will be fighting table bloat or long undo chains.

Fourth, row-oriented or columnar, which decides whether it suits transactional or analytical work. Fifth, the indexing model — clustered primary key or heap with separate indexes — which tells me what secondary lookups cost and how much primary-key width matters. Sixth, how the planner decides: cost-based with statistics, or rule-based, and whether plans are visible and influenceable. That predicts its failure mode, since cost-based planners fail by mis-estimating.

Then I would look at the operational surface, which is what actually determines whether a team can run it: what backup and point-in-time recovery look like, how upgrades work, what observability it exposes, and how it behaves when disks fill or a node dies. Only after all that would I benchmark, and I would design the benchmark around the specific trade-offs the architecture told me to be suspicious of — testing the corner it did not optimise for, at a data size exceeding memory, since almost every database looks excellent when everything fits in the buffer pool.

Senior: Explain the relationship between the buffer pool, the WAL, and checkpoints.

They are three parts of one mechanism for making writes both fast and durable, and each exists because of the others.

The buffer pool is the engine's in-memory cache of pages, and all reads and writes go through it. Writes modify pages there and mark them dirty rather than touching disk, which is what makes writes fast — but it means committed changes exist only in volatile memory. The write-ahead log closes that gap: before a transaction commits, a compact record of its changes is appended to a sequential log and fsynced. Since the log is sequential and small, that fsync is cheap, and it is sufficient for durability because the change can be reconstructed from it.

Checkpoints resolve the problem this creates. If dirty pages were never written, the log would grow without bound and recovery would have to replay from the beginning of time. A checkpoint flushes dirty pages to their real locations and records a point in the log before which nothing needs replaying, which lets old WAL segments be recycled and bounds recovery time.

The ordering constraint that ties them together is the write-ahead rule: a page may not be written to disk before the log record describing its change is durable. Otherwise a crash could leave a data page changed with no log record explaining it, and recovery could not tell whether to keep or undo the change.

Operationally this is where several familiar behaviours come from. Checkpoints cause periodic I/O spikes as accumulated dirty pages flush, which is why engines spread them over time. Tuning checkpoint frequency trades recovery time against steady-state I/O: frequent checkpoints mean fast recovery and more constant write load, infrequent ones the reverse. And a large buffer pool improves more than the cache hit rate — it lets a hot page absorb many modifications before being written once, so it reduces total write volume too.

🏋️ Exercises

1 (easy): Compute how many rows fit on a page, and predict the scan cost.
Solution 
-- Postgres: 8192-byte pages, 24-byte page header, 4 bytes per line
-- pointer, 23-24 bytes of row header per tuple.

-- ── TABLE A: NARROW ─────────────────────────────────────────────────────
CREATE TABLE events_narrow (
    id bigint, user_id bigint, kind smallint, created_at timestamptz);
-- payload 8+8+2+8 = 26 → padded to 32; + 24 row header = 56 bytes
-- per-tuple cost = 56 + 4 (line pointer) = 60
-- usable = 8192 - 24 = 8168  →  8168 / 60 ≈ 136 rows/page

-- ── TABLE B: WIDE ───────────────────────────────────────────────────────
CREATE TABLE events_wide (
    id bigint, user_id bigint, kind smallint, created_at timestamptz,
    description text,        -- ~400 bytes average
    metadata jsonb);         -- ~1200 bytes average
-- ≈ 56 + 1600 = 1656; + 4 = 1660  →  8168 / 1660 ≈ 4 rows/page

-- ── THE PREDICTION ──────────────────────────────────────────────────────
-- 10 million rows:
--   narrow  10,000,000 / 136 ≈  73,530 pages ≈  574 MB
--   wide    10,000,000 /   4 ≈ 2,500,000 pages ≈ 19.5 GB
-- A full scan of the wide table costs ~34× the I/O for the SAME ROWS.

-- ── VERIFY IT ───────────────────────────────────────────────────────────
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT * FROM pgstattuple('events_narrow');
SELECT relpages, reltuples, reltuples/NULLIF(relpages,0) AS rows_per_page
FROM pg_class WHERE relname = 'events_narrow';
SELECT pg_size_pretty(pg_relation_size('events_wide'));

-- ── THE TWIST: TOAST ────────────────────────────────────────────────────
-- Postgres moves large values out-of-line into a TOAST table once a row
-- exceeds ~2KB, so the main table's rows shrink back toward narrow.
SELECT pg_size_pretty(pg_relation_size('events_wide')) AS main,
       pg_size_pretty(pg_total_relation_size('events_wide')) AS with_toast;
-- ✓ A scan that does NOT select the toasted columns stays fast.
-- ✗ SELECT * pays a separate fetch PER ROW for the toasted values —
--   which is why SELECT * is worse than it looks on wide tables.

-- ── THE LESSON ──────────────────────────────────────────────────────────
-- Row width is an I/O decision. Splitting rarely-read wide columns into
-- a side table ("vertical partitioning") can make the hot table many
-- times faster to scan, with no change to indexes or queries beyond a
-- join for the cold columns.
2 (easy): Measure the sequential-versus-random gap yourself.
Solution 
-- ── SETUP: a table larger than RAM (or drop caches to simulate) ─────────
CREATE TABLE t AS
SELECT g AS id, repeat('x', 200) AS payload
FROM generate_series(1, 20000000) g;      -- ~5GB
CREATE INDEX ON t (id);
VACUUM ANALYZE t;

-- ── SEQUENTIAL: read everything ─────────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM t;
-- Seq Scan  Buffers: shared read=641026    Time: 4,210 ms
--   → 5GB / 4.2s ≈ 1,200 MB/s

-- ── RANDOM: fetch 100,000 scattered rows ────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS) SELECT count(payload) FROM t
WHERE id = ANY (ARRAY(SELECT (random()*20000000)::int
                      FROM generate_series(1,100000)));
-- Index Scan  Buffers: shared read=98,412  Time: 8,900 ms
--   → 100k random reads in 8.9s ≈ 11,200 reads/s ≈ 90 MB/s

-- ── THE RATIO ───────────────────────────────────────────────────────────
-- Sequential 1,200 MB/s vs random 90 MB/s → ~13× on this NVMe device.
-- On a spinning disk the same test shows 100× or more.

-- ── WHY THE PLANNER'S ARITHMETIC NOW MAKES SENSE ────────────────────────
-- Reading 30% of a table via index = 30% of the rows, each a random
-- fetch. At a 13× penalty, 0.30 x 13 = 3.9 — nearly four times the cost
-- of just reading everything sequentially. That is precisely why the
-- planner switches to a Seq Scan above roughly 5-10% selectivity, and it
-- is not a heuristic: it is this measurement.
SHOW random_page_cost;    -- 4.0 by default = a SPINNING-DISK ratio
-- On SSD the true ratio is far lower, so leaving 4.0 makes the planner
-- over-charge index scans. This experiment is how you justify:
ALTER SYSTEM SET random_page_cost = 1.1;

-- ── CONTROL FOR CACHING, OR THE RESULT IS MEANINGLESS ───────────────────
-- Both runs get faster once pages are in the buffer pool. Compare the
-- `read` (from disk) versus `hit` (from cache) buffer counts, not the
-- wall-clock time, and restart or use a dataset well beyond RAM.
3 (medium): Trace a single-row read from SQL text to returned bytes.
Solution 
SELECT name FROM users WHERE id = 42;

-- 1. WIRE PROTOCOL. The message arrives on a socket; the backend parses
--    the packet and binds parameters. (Postgres: one PROCESS per
--    connection — which is why connection count matters so much and why
--    a pooler is not optional at scale.)

-- 2. PARSER. Text → a parse tree. Syntax errors surface here. The result
--    is checked against the catalog: does `users` exist, does it have
--    `id` and `name`, does this role have SELECT on it?

-- 3. REWRITER. Views are expanded into their definitions, row-level
--    security predicates are injected, rules applied. The query you
--    wrote is often not the query that gets planned.

-- 4. PLANNER. Enumerates access paths — sequential scan versus index
--    scan on users_pkey — costs each using statistics from pg_statistic,
--    and picks the cheapest. Here: Index Scan, estimated cost 0.43..8.45.
--    (Lessons 9-10.)

-- 5. EXECUTOR + ACCESS METHOD. Walks the B+tree:
--      root page   → binary search → child pointer
--      internal    → binary search → leaf pointer
--      leaf        → finds key 42 → row pointer (block 1042, slot 7)
--    3 page requests for a table of any realistic size. (Lesson 3.)

-- 6. BUFFER POOL. Each request is a lookup in the page table:
--      HIT  → return the frame directly (~100 ns)
--      MISS → find a victim frame (clock-sweep), evict it — WRITING IT
--             FIRST if dirty, and only after its WAL record is durable —
--             read the page in (~20 μs), pin it.
--    ⚠ A read can therefore cause a WRITE. That is the write-ahead rule
--      enforced at eviction time. (Lessons 5-6.)

-- 7. VISIBILITY CHECK. The page is in memory, but which VERSION of row
--    42 may this transaction see? Compare the tuple's xmin/xmax against
--    the snapshot; follow the version chain if needed. Under MVCC a
--    "read" is never just a fetch. (Lesson 7.)

-- 8. PROJECTION AND RETURN. Extract the `name` column, convert to the
--    wire format, write to the socket.

-- ── WHERE THE TIME ACTUALLY GOES ────────────────────────────────────────
-- Cached:  planning ~50 μs, execution ~10 μs. PLANNING DOMINATES —
--          which is why prepared statements matter for hot queries.
-- Cold:    3 page faults x 20 μs ≈ 60 μs of I/O dominates instead.
-- ✓ The same query has completely different bottlenecks depending on
--   cache state. This is why one measurement is never enough, and why
--   `hit` versus `read` in EXPLAIN (BUFFERS) is more informative than
--   elapsed time.
4 (medium): Predict how three engines behave on the same workload.
Solution 
-- WORKLOAD: IoT telemetry.
--   50,000 inserts/sec, append-only, keyed (device_id, timestamp)
--   reads: "last 24h for one device" + hourly aggregates
--   retention 90 days; ~130 billion rows total

-- ── POSTGRES (B+tree heap, MVCC in-table) ───────────────────────────────
-- PREDICT: inserts are fine IF the key is time-ordered (append to the
--   rightmost leaf, one hot page). A random key would scatter and
--   collapse throughput.
-- PREDICT: the per-device time-range read is ideal for a composite
--   (device_id, ts) index — a contiguous leaf range.
-- PREDICT: PROBLEMS AT SCALE. 130B rows in one B-tree is unmanageable;
--   vacuum, index maintenance and backups all suffer. Retention by
--   DELETE would be catastrophic.
-- MITIGATION: RANGE partition by time (retention becomes DETACH), and
--   consider TimescaleDB, which is exactly this mitigation packaged.
-- VERDICT: workable with partitioning; not its natural habitat.

-- ── CASSANDRA / SCYLLA (LSM, wide-column) ───────────────────────────────
-- PREDICT: 50k sequential appends/sec is precisely what an LSM is for.
-- PREDICT: partition key device_id, clustering key ts → "last 24h for a
--   device" is one contiguous read within one partition. Ideal.
-- PREDICT: retention is free — TTL per row, reclaimed by compaction.
-- PREDICT: THE COSTS. Aggregates across devices are painful (no joins,
--   limited aggregation); compaction consumes background I/O forever and
--   produces latency spikes; and a hot device could create an oversized
--   partition.
-- VERDICT: excellent for ingest and per-device reads; weak for the
--   analytical half.

-- ── CLICKHOUSE (columnar, LSM-ish merge tree) ───────────────────────────
-- PREDICT: columnar storage compresses telemetry extremely well —
--   10-30× is typical, because a column of similar readings compresses
--   far better than a row of mixed types. 130B rows becomes affordable.
-- PREDICT: hourly aggregates read only the needed columns and are
--   vectorised — this is the workload it is built for.
-- PREDICT: THE COSTS. Single-row lookups are comparatively poor,
--   updates and deletes are awkward, and it prefers batched inserts over
--   many small ones.
-- VERDICT: best for the aggregate half, weakest for point reads.

-- ── THE ANSWER THE QUESTION IS ACTUALLY ASKING ──────────────────────────
-- These are two workloads wearing one name: high-rate ingest with
-- per-device point reads, and analytical aggregation. No single engine
-- is best at both, so the mature answer is usually to split them —
-- ingest into the write-optimised store, stream into the columnar store
-- for analytics — and to be explicit that the second is eventually
-- consistent with the first.
-- ⚠ And say the boring thing too: at 50k/s with partitioning, Postgres
--   plus TimescaleDB may well be sufficient, and ONE system your team
--   already operates beats two they do not.
5 (hard): Design a minimal storage engine and defend each decision.
Solution 
-- REQUIREMENT: an embedded key-value store. Durable, crash-safe,
-- millions of keys, mixed reads and writes, single process.

-- ── DECISION 1: PAGE SIZE = 4KB ─────────────────────────────────────────
-- Matches the OS page and typical SSD sector, so no read is wasted and
-- mmap stays an option. 8KB would suit scans better; for a KV store with
-- point lookups dominating, smaller wins.

-- ── DECISION 2: B+TREE, NOT LSM ─────────────────────────────────────────
-- Mixed read/write with no stated write-throughput crisis. A B+tree
-- gives predictable read latency and needs no compaction thread — and
-- for an EMBEDDED store, background compaction competing with the host
-- application's I/O is a genuine operational problem. LSM would be right
-- if the workload were write-dominated.

-- ── DECISION 3: FILE LAYOUT ─────────────────────────────────────────────
--   page 0        meta: magic, version, page size, root ptr, freelist
--   page 1..n     B+tree internal and leaf pages
--   separate      write-ahead log (append-only)
-- ⚠ TWO meta pages, written alternately with a checksum and a counter.
--   A torn write to the single meta page would destroy the whole
--   database; with two, recovery picks the newest one that checksums.
--   This is exactly what SQLite and LMDB do, and it is the kind of
--   detail that separates a toy from a durable store.

-- ── DECISION 4: WAL, WITH GROUP COMMIT ──────────────────────────────────
-- write: append the record → fsync → apply to the in-memory page
-- ✓ one sequential fsync makes scattered changes durable
-- ✓ GROUP COMMIT: batch concurrent commits into one fsync. Throughput
--   goes from ~200/s (one fsync each on a good SSD) to thousands, and it
--   is nearly free to implement — wait 1ms, fsync everything waiting.
-- CHECKPOINT: when the WAL exceeds N MB, flush dirty pages, fsync the
--   main file, truncate the log.

-- ── DECISION 5: COPY-ON-WRITE PAGES ─────────────────────────────────────
-- Never modify a page in place: write a new copy, update the parent
-- pointer, add the old page to the freelist after no reader needs it.
-- ✓ makes readers lock-free — a reader holding the old root sees a
--   consistent snapshot with no locking whatsoever (this is LMDB's
--   central idea, and it is beautiful)
-- ✓ crash safety comes almost free: the switch is one atomic pointer
--   write in the meta page
-- ✗ write amplification: changing one key rewrites the whole root-to-leaf
--   path. That is the price, and it is a real one.

-- ── DECISION 6: BUFFER POOL WITH CLOCK EVICTION ─────────────────────────
-- Fixed-size frame array; clock-sweep approximates LRU at a fraction of
-- the bookkeeping cost. Pin pages in use; never evict a dirty page
-- before its WAL record is durable — the write-ahead rule, enforced here.

-- ── DECISION 7: SINGLE-WRITER, MANY-READER ──────────────────────────────
-- One write transaction at a time; unlimited concurrent readers via COW
-- snapshots.
-- ✓ eliminates the entire concurrency-control subsystem — no MVCC
--   version chains, no deadlock detection, no lock manager
-- ✗ write throughput is bounded by one thread
-- → For an embedded store this is the RIGHT trade: enormously simpler,
--   and embedded workloads are rarely write-bound. Say the limitation
--   out loud rather than hiding it.

-- ── WHAT I DELIBERATELY LEFT OUT, AND WHY ───────────────────────────────
-- • Compression — adds CPU and complicates page layout; add later if the
--   data proves compressible.
-- • Secondary indexes — a KV store's contract is key lookup; layer them
--   above.
-- • Replication — a separate concern that the WAL already makes possible
--   later, for free.
-- ⚠ THE REAL LESSON: the trade-offs compose. Choosing COW made readers
--   lock-free, which made single-writer acceptable, which removed the
--   need for MVCC and a lock manager entirely. One good decision
--   deleted three subsystems — and that, rather than any individual
--   optimisation, is what good storage-engine design looks like.
6 (hard): Diagnose an engine-level problem from symptoms alone.
Solution 
-- SYMPTOMS: a Postgres OLTP database.
--   • table is 400GB but holds ~90GB of live data
--   • the same query is 8ms sometimes, 4s other times
--   • disk I/O high, CPU low
--   • it degraded gradually over three months
--   • it is fastest right after a restart, then decays

-- ── READ THE SYMPTOMS STRUCTURALLY ──────────────────────────────────────
-- 4.4× size-to-data ratio → BLOAT: dead tuples not reclaimed.
-- High I/O with low CPU  → thrashing the buffer pool, not computing.
-- Gradual decay          → an accumulating problem, not an event.
-- Fast after restart     → cache state matters, so the working set no
--                          longer fits.
-- Bimodal timings        → sometimes cached, sometimes not.
-- These fit ONE story: MVCC bloat has inflated the physical footprint
-- past RAM, so the cache hit rate collapsed.

-- ── CONFIRM ─────────────────────────────────────────────────────────────
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0*n_dead_tup/NULLIF(n_live_tup+n_dead_tup,0),1) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 5;
--  orders | 210,000,000 | 680,000,000 | 76.4 | 2026-05-12   ← 3 months!
SELECT sum(blks_hit)*100/NULLIF(sum(blks_hit+blks_read),0)
FROM pg_stat_database WHERE datname=current_database();   -- 71%

-- ── WHY DID VACUUM STOP? Find the blocker ───────────────────────────────
SELECT pid, now()-xact_start AS age, state, left(query,60)
FROM pg_stat_activity WHERE xact_start IS NOT NULL
ORDER BY xact_start LIMIT 3;
--  4471 | 92 days | idle in transaction | BEGIN
SELECT slot_name, active, now()-... FROM pg_replication_slots;  -- also check
SELECT max(age(datfrozenxid)) FROM pg_database;

-- ⚠ THE MECHANISM, AND IT IS THE WHOLE ANSWER: vacuum cannot remove any
--   row version that might still be visible to the OLDEST RUNNING
--   TRANSACTION. One session that ran BEGIN 92 days ago and never
--   committed froze the snapshot horizon, so for three months EVERY
--   update in the database left permanent garbage. Not just in tables
--   that session touched — DATABASE-WIDE.
--   (An abandoned replication slot or a long-lived prepared transaction
--    does exactly the same thing, and both are worth checking.)

-- ── FIX, IN ORDER ───────────────────────────────────────────────────────
-- 1. Kill the blocker.
SELECT pg_terminate_backend(4471);
-- 2. Reclaim the space. Plain VACUUM marks it reusable but does not
--    shrink the file; the working set stays too big:
VACUUM (VERBOSE, ANALYZE) orders;          -- immediate, non-blocking
--    To actually return 300GB to the OS:
--      VACUUM FULL  — rewrites the table, ACCESS EXCLUSIVE lock, an
--                     outage on a 400GB table. Effective, rarely viable.
--      pg_repack    — same result, ONLINE, needs the free space. ✓ use
--                     this.
-- 3. Prevent recurrence — the part that matters:
ALTER SYSTEM SET idle_in_transaction_session_timeout = '5min';
ALTER SYSTEM SET autovacuum_vacuum_scale_factor = 0.05;   -- 20% default
                                                          -- is too lax
                                                          -- for big tables
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.01);
-- 4. ALERT on the leading indicators, not the outcome:
--      oldest transaction age, dead tuple ratio, replication slot lag,
--      cache hit rate. Every one of these would have caught this in week
--      one instead of month three.

-- ── THE ARCHITECTURAL POINT ─────────────────────────────────────────────
-- This failure is a direct consequence of Postgres keeping old row
-- versions IN THE TABLE. Engines that use an undo log — InnoDB, Oracle —
-- do not bloat tables this way; they suffer a different problem instead,
-- where a long transaction makes reads slower and slower as undo chains
-- grow, and can exhaust undo space. Same root cause, different symptom,
-- because of one architectural choice about where old versions live.
-- Knowing the internals is what turns "the database got slow" into a
-- diagnosis in ten minutes.

🎯 Key Takeaways

  • Every engine is layered the same way — query processor, access methods, buffer pool, transactions, disk manager — because each layer solves a problem the one below it creates.
  • The memory-to-disk gap is the fact all storage design answers: RAM is roughly 200× faster than NVMe and 100,000× faster than a disk seek.
  • Sequential I/O beats random by 7× on NVMe and 150× on disk, which is why logs are append-only, LSM-trees exist, and full scans sometimes beat indexes.
  • Databases read fixed-size pages, not rows — so rows-per-page determines scan cost, and row width is an I/O decision rather than a style choice.
  • B+trees optimise reads and update in place; LSM-trees optimise writes by appending immutable sorted files and paying for compaction.
  • The RUM conjecture bounds the whole field: read cost, update cost, and space — improve two and the third gets worse.
  • COMMIT does not write data pages; it fsyncs one sequential log record, and checkpoints flush pages lazily afterwards.
  • The write-ahead rule — log record durable before the data page — is what makes crash recovery possible, and it is enforced even at page eviction.
  • The same WAL gives you recovery, replication, point-in-time restore, and change data capture: one mechanism, four features.
  • To evaluate an unfamiliar engine, ask about storage structure, durability, concurrency model, row versus columnar, indexing model, and planner — the answers predict its behaviour before you benchmark.
