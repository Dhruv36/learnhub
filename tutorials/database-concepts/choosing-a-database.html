Choosing a Database Design Perspective

What you'll master: a decision procedure that starts from access patterns and constraints rather than from engine categories, how to characterise a workload in the six dimensions that actually determine fit, why "start with PostgreSQL" is a defensible default rather than a lazy one and precisely when to leave it, the operational and organisational costs that decide real outcomes and are systematically absent from evaluations, how to run a proof of concept that can actually fail, how to write a decision record that survives the people who wrote it, and how to recognise the difference between a genuine requirement and anxiety about scale. This is the capstone of the track: every earlier lesson supplies the evidence this one reasons with. Prerequisites: the track, particularly The Engine Landscape and OLTP vs OLAP.

Part 1 — Characterise the Workload First

-- Nearly every bad database decision comes from starting with engines
-- instead of requirements. Characterise the workload in six dimensions
-- and most choices resolve themselves.

-- ── 1. ACCESS PATTERN ───────────────────────────────────────────────────
--   How many ROWS per query?        one / hundreds / millions
--   How many COLUMNS of how many?   all of them / 3 of 40
--   Point lookup, range scan, or full aggregate?
--   Is the query set KNOWN or ad-hoc?
-- → decides row versus columnar, and whether pre-aggregation suffices

-- ── 2. WRITE PATTERN ────────────────────────────────────────────────────
--   Rate: 10/sec, 10k/sec, 1M/sec?
--   Shape: append-only, update-in-place, or delete-heavy?
--   Arrival: single rows or batches?
-- → decides B+tree versus LSM, and whether MVCC bloat will be a problem

-- ── 3. CONSISTENCY REQUIREMENTS ─────────────────────────────────────────
--   Multi-statement transactions? Foreign keys? Uniqueness?
--   Is eventual consistency acceptable, and for WHICH data?
-- → this is usually the hardest constraint, and the least negotiable

-- ── 4. SCALE, HONESTLY ──────────────────────────────────────────────────
--   Data size TODAY and in 24 months — measured, not imagined
--   Query rate, concurrent connections
-- ⚠ Design for 10× current, not 1000×. Designing for scale you do not
--   have costs you continuously and buys nothing until it arrives —
--   and most systems never arrive.

-- ── 5. LATENCY AND AVAILABILITY ─────────────────────────────────────────
--   p50 and p99 targets; is this on the request path?
--   Acceptable downtime; RPO and RTO (WAL lesson)
-- → decides replication topology and whether synchronous commit applies

-- ── 6. OPERATIONAL CONTEXT ──────────────────────────────────────────────
--   What does the team already run and understand?
--   Managed service available? On-call capacity? Compliance constraints?
-- ⚠ This dimension decides more real outcomes than the other five, and
--   it is the one evaluations omit because it is not technical.

-- ── THE OUTPUT ──────────────────────────────────────────────────────────
-- Write these down BEFORE naming any engine. If you cannot fill them in,
-- you are not ready to choose — and saying so is a more valuable
-- contribution than picking something.
📋 The order matters more than the analysis. Teams that start by comparing engines end up justifying a preference. Teams that start by writing down the six dimensions usually find the answer is obvious, and frequently find it is the database they already run. The procedure is not a formality — it is the thing that converts an argument about technology into a conversation about requirements.

Part 2 — Why PostgreSQL Is the Right Default

-- Not because it wins every category. Because of an argument about
-- expected cost across the whole lifetime of a system.

-- ── THE ARGUMENT ────────────────────────────────────────────────────────
-- 1. IT IS COMPETENT AT NEARLY EVERYTHING. Full ACID, a good cost-based
--    planner, JSON, full-text search, geospatial, time-series,
--    vectors — none best-in-class, all good enough for most systems.
-- 2. EXTENSIONS COVER THE ADJACENT NEEDS.
CREATE EXTENSION postgis;      -- geospatial: genuinely best-in-class
CREATE EXTENSION pgvector;     -- vector similarity for RAG
CREATE EXTENSION timescaledb;  -- time-series partitioning + compression
CREATE EXTENSION citus;        -- distributed tables
--    Each removes a reason to add a second system.
-- 3. THE FAILURE MODES ARE DOCUMENTED AND SURVIVABLE. Vacuum, bloat,
--    wraparound, connection limits — all well understood, all with
--    known remedies (this track).
-- 4. THE OPERATIONAL KNOWLEDGE IS WIDELY AVAILABLE. You can hire people
--    who know it; the answer to an obscure problem is findable.
-- 5. IT IS EVERYWHERE AS A MANAGED SERVICE, so the operational burden is
--    optional.

-- ── THE DECISIVE POINT ──────────────────────────────────────────────────
-- ONE system your team can operate beats TWO they cannot. Every
-- additional datastore adds: a deployment, a backup strategy, an upgrade
-- path, monitoring, on-call knowledge, a security surface, and usually a
-- synchronisation pipeline. That cost is paid CONTINUOUSLY; the benefit
-- is usually narrow.
-- ⚠ The most common architectural mistake is not choosing the wrong
--   database — it is choosing THREE when one would have done.

-- ── WHERE POSTGRES GENUINELY LOSES ──────────────────────────────────────
-- ✗ analytical scans over wide tables at scale        → columnar
-- ✗ write rates beyond ~50k/sec sustained on one node → LSM, or shard
-- ✗ multi-region strong-consistency writes            → distributed SQL
-- ✗ ephemeral high-churn data with TTL                → Redis
-- ✗ relevance-ranked full-text search at quality      → Elasticsearch
-- ✗ very high connection counts without a pooler      → (fix with a
--                                                        pooler)
-- ✓ Each of these is a SPECIFIC property, not a general failure. That is
--   the form a justification must take.

-- ── THE SENTENCE THAT JUSTIFIES LEAVING ─────────────────────────────────
-- "We need X because our workload has property Y, which Postgres
--  handles at cost Z, and we have MEASURED Z."
-- ✗ Not: "it might not scale" · "everyone uses X" · "it feels more
--   modern" · "we may need multi-region one day"
-- ⚠ If the sentence cannot be completed with a number in it, the
--   evaluation is not finished.

Part 3 — The Decision Tree

-- ── IS THIS PRIMARY TRANSACTIONAL DATA? ─────────────────────────────────
-- (orders, users, accounts — things with invariants)
--   → RELATIONAL, almost always. Postgres or MySQL.
--   The requirement for multi-statement transactions, foreign keys and
--   uniqueness rules out most alternatives before performance is even
--   discussed. This is the least negotiable constraint there is.

-- ── IS IT ANALYTICAL? ───────────────────────────────────────────────────
--   Query set KNOWN?      → pre-aggregate in the relational database.
--                           Materialised views answer most dashboards in
--                           milliseconds with no second system.
--   Query set AD-HOC over large history?
--                         → columnar. Try in order: a columnar extension
--                           in Postgres, then Parquet + DuckDB, then a
--                           warehouse with CDC.
-- ⚠ Most "we need a warehouse" requests are the first case.

-- ── IS IT EPHEMERAL AND HIGH-CHURN? ─────────────────────────────────────
-- (sessions, carts, rate limits, caches, locks)
--   → REDIS or similar. In-table MVCC is the worst possible fit for data
--     that is written, updated repeatedly and expires in 30 minutes.
--   ⚠ Be explicit about durability: losing a few seconds of cart edits
--     is usually acceptable; losing an order is not. That boundary
--     belongs in the design.

-- ── IS IT APPEND-ONLY AT VERY HIGH RATE? ────────────────────────────────
-- (metrics, telemetry, logs, clickstream)
--   → LSM or time-series. Postgres + TimescaleDB first — it is
--     partitioning plus compression, which is most of what a
--     purpose-built system provides, without a new operational surface.
--   → ClickHouse / Cassandra when volume genuinely exceeds that.

-- ── IS IT SEARCH? ───────────────────────────────────────────────────────
--   Basic full text            → Postgres tsvector + GIN. Try first.
--   Relevance tuning, facets,
--   fuzzy matching, synonyms   → Elasticsearch / OpenSearch
--   ⚠ Accept that search results will lag writes.

-- ── IS IT DOCUMENT-SHAPED? ──────────────────────────────────────────────
--   Variable attributes on a stable core → JSONB columns alongside real
--     columns. Keeps constraints, joins and SQL.
--   Genuinely nested aggregates always read whole → a document store is
--     a fair choice.
--   ⚠ "Flexible schema" is a modelling liability at scale, not a
--     feature: five years of undeclared drift is invisible until it
--     breaks.

-- ── DOES IT NEED MULTI-REGION STRONG CONSISTENCY? ───────────────────────
--   → distributed SQL (Spanner, CockroachDB, Yugabyte).
--   ⚠ Every write pays consensus latency, permanently and by physics.
--     Confirm the requirement is real: most "global" products need a CDN
--     and regional read replicas, not multi-primary writes.

Part 4 — The Costs Evaluations Miss

-- Benchmarks measure throughput. These decide outcomes.

-- ── 1. OPERATIONAL SURFACE ──────────────────────────────────────────────
--   How do we back it up — and has anyone RESTORED it? (WAL lesson: an
--     untested backup is a hypothesis)
--   How do we upgrade without downtime?
--   What does it expose for observability?
--   What happens when the disk fills?
--   How does it behave during a network partition?
-- ⚠ A system with excellent throughput and no restore story is a
--   liability, not an asset.

-- ── 2. TEAM CAPABILITY ──────────────────────────────────────────────────
--   Who can debug this at 3am? What happens when they leave?
--   How long until a new engineer is productive?
-- ✓ A slower database the team understands beats a faster one they do
--   not. This is not a compromise — it is a correct weighting of
--   expected cost.

-- ── 3. THE INTEGRATION, IF THERE ARE TWO SYSTEMS ────────────────────────
--   CDC or ETL pipeline: build, monitor, backfill, evolve
--   Schema changes now happen in two places and can break it silently
--   Eventual consistency: numbers WILL disagree; display the lag
-- ⚠ The pipeline is frequently harder to operate than either database,
--   and it needs a named owner. Treating it as plumbing is the most
--   common way a sound architecture becomes an unreliable one.

-- ── 4. COMPLIANCE AND DATA GOVERNANCE ───────────────────────────────────
--   A second copy of personal data doubles the access-control,
--   retention and deletion surface.
--   ⚠ Deletion requests: in ClickHouse a delete is an ASYNCHRONOUS
--     mutation with no completion guarantee at a given time. That is a
--     GDPR question, and it is routinely discovered after adoption.
--   Where does the data physically live? (residency)

-- ── 5. COST OVER THREE YEARS ────────────────────────────────────────────
--   licence or managed-service fees, storage, egress
--   the ENGINEERING TIME to operate it — usually the largest line and
--   the one never estimated
--   the migration cost if this turns out wrong

-- ── 6. THE EXIT ─────────────────────────────────────────────────────────
--   How hard is it to leave? Proprietary query languages, non-portable
--   types and vendor-specific features raise the exit cost.
-- ⚠ Ask this at ADOPTION time, when you have leverage and no urgency —
--   not during the incident that makes you want to leave.

Part 5 — Running a Proof of Concept That Can Fail

-- A PoC that cannot fail is a procurement exercise with extra steps.
-- Design it to be capable of producing a "no".

-- ── DEFINE THE PASS/FAIL CRITERIA FIRST, IN WRITING ─────────────────────
-- ✓ "p99 under 2s for the 20 sampled analyst queries, at 3× current data
--    volume, while ingest runs at production rate."
-- ✗ "See if it's fast."
-- ⚠ Write the criteria BEFORE running anything. Criteria chosen after
--   seeing results are conclusions, not tests.

-- ── USE REAL DATA, INCLUDING ITS SKEW ───────────────────────────────────
-- Uniform synthetic data hides the problems that will actually happen:
-- the tenant with 40% of the rows, the NULL that dominates a join key,
-- the correlated columns that break estimates (cost-models lesson).
-- ✓ Take a production snapshot, anonymised if needed, at realistic
--   distribution — not just realistic volume.

-- ── EXCEED MEMORY ───────────────────────────────────────────────────────
-- Almost every database looks excellent when the working set fits in the
-- buffer pool. Test at a size where it does not, because that is where
-- the architectural differences appear at all.

-- ── RUN LONG ENOUGH FOR BACKGROUND WORK ─────────────────────────────────
-- Compaction, vacuum, checkpoints and merges only matter after the
-- system has had to clean up after itself. A five-minute benchmark
-- measures a system that has not yet been asked to.
-- ✓ Hours minimum; ideally a sustained multi-day run.

-- ── TEST THE FAILURE PATHS, NOT ONLY THE HAPPY PATH ─────────────────────
--   kill a node mid-write — what is lost, and how long is recovery?
--   fill the disk — does it degrade or wedge?
--   restore from backup — TIME IT. That number is your RTO.
--   run a schema migration under load
--   simulate a network partition if it is distributed
-- ⚠ These reveal more than throughput ever will, and they are what you
--   will actually be doing at 3am.

-- ── TEST THE CORNER THE ARCHITECTURE DID NOT OPTIMISE FOR ───────────────
-- If it is columnar, test point lookups and updates. If it is LSM, test
-- delete-heavy workloads and range scans. You already know from the
-- architecture where it should be weak (engine-landscape lesson) —
-- confirm the weakness is survivable for YOUR workload.

-- ── INCLUDE THE OPERATIONAL DIMENSION ───────────────────────────────────
-- Have someone who has never used it try to: set it up, diagnose a slow
-- query, restore a backup, and perform an upgrade. Time each. That is a
-- direct measurement of the cost you will pay for years.

Part 6 — Writing the Decision Down

-- The deliverable is not the choice. It is a record that lets someone
-- revisit the choice intelligently in two years, when everyone who made
-- it has moved on.

-- ── THE ARCHITECTURE DECISION RECORD ────────────────────────────────────
-- TITLE      "Use PostgreSQL with TimescaleDB for telemetry storage"
-- STATUS     accepted · 2026-08-06
-- CONTEXT
--   The measured requirement, in numbers. What we tried already and what
--   it achieved. The constraints — team size, compliance, budget.
-- DECISION
--   What we chose, and the specific properties that decided it.
-- ALTERNATIVES CONSIDERED
--   Each option, what it would have bought, and why it lost. ⚠ This
--   section is the one that has value later — "we considered
--   ClickHouse and rejected it because X" prevents the same debate
--   annually.
-- CONSEQUENCES
--   What this makes easy. What it makes HARD. What we are accepting.
-- REVISIT WHEN
--   The measurable trigger: "ingest exceeds 200k/sec" or "p99 for
--   analyst queries exceeds 10s". ⚠ Without a trigger, a decision is
--   never revisited until it fails.

-- ── STATE THE TRADE-OFFS EXPLICITLY ─────────────────────────────────────
-- ✓ "We chose Postgres + Timescale. This gives us one operational
--    system, full SQL and transactions with our other data, and
--    compression comparable to a columnar store on older chunks.
--    WE ARE ACCEPTING: ad-hoc analytical queries over the full 3-year
--    history will take 10-60s rather than 1-3s. If analysts find that
--    unworkable, the next step is exporting older chunks to Parquet and
--    querying with DuckDB — a two-week change we have costed."
-- ⚠ A decision without stated costs reads as a claim that there were
--   none, which nobody believes and nobody can build on.

-- ── AND THE ANTI-PATTERNS TO NAME OUT LOUD ──────────────────────────────
-- • RESUME-DRIVEN DEVELOPMENT: choosing for interest rather than fit.
--   Legitimate to want to learn something; not legitimate to spend the
--   company's operational budget on it silently.
-- • CARGO CULTING: "Netflix uses Cassandra." Netflix has hundreds of
--   engineers and a workload unlike yours. Their constraints are not
--   evidence about your constraints.
-- • PREMATURE DISTRIBUTION: adopting distributed systems for scale that
--   has not arrived. The cost is paid from day one; the benefit arrives
--   only if the growth does — and usually it does not.
-- • DEFAULTING TO THE INCUMBENT WITHOUT ANALYSIS: the mirror image, and
--   also wrong. "We always use X" is not a decision either.

-- ── THE HONEST SUMMARY OF THIS WHOLE TRACK ──────────────────────────────
-- Databases are not magic. Each is a specific set of decisions about
-- storage structure, durability, concurrency and distribution, and every
-- decision buys one property by spending another. Once you can name the
-- decisions, marketing categories stop being useful and access patterns
-- start being the only thing that matters — which is what makes the
-- choice tractable.

Interview Questions

Beginner: How would you choose a database for a new project?

I would start by characterising the workload rather than comparing products, because starting from engines tends to produce a justification for whatever someone already preferred.

Six things determine the answer. The access pattern — how many rows and how many columns each query touches, and whether the query set is known or exploratory. The write pattern — the rate, and whether it is append-only, update-heavy or delete-heavy. The consistency requirements — whether multi-statement transactions, foreign keys and uniqueness are needed, which is usually the least negotiable constraint. The realistic scale, measured today and projected over about two years. The latency and availability targets. And the operational context: what the team already runs and can debug.

For most new projects those answers point at a relational database, because primary business data has invariants and needs transactions. I would default to PostgreSQL — not because it wins every category but because it is competent across nearly all of them, its extensions cover most adjacent needs, its failure modes are well documented, and the expertise is widely available.

I would only add or substitute a second system when I could name the specific property PostgreSQL lacks, with a measurement behind it. Every additional datastore costs a deployment, a backup strategy, an upgrade path, monitoring, on-call knowledge and usually a synchronisation pipeline — paid continuously. The most common architectural mistake I see is not picking the wrong database, it is picking three when one would have served.

Beginner: Why is "just use PostgreSQL" reasonable advice?

Because it is an argument about expected cost across a system's whole life, not a claim that it is the fastest at anything.

It is competent at nearly everything: full ACID transactions, a good cost-based planner, JSON documents, full-text search, and via extensions, geospatial with PostGIS, time-series with TimescaleDB, vector search with pgvector, and distribution with Citus. None of those is necessarily best-in-class, but each is good enough for most systems, and each removes a reason to run a second database.

Its failure modes are also well understood. Vacuum, bloat, transaction-id wraparound and connection limits are all documented with known remedies. That predictability matters more than peak throughput, because you will spend far more time operating a database than benchmarking it. And the expertise is widely available, so you can hire people who know it and find answers to obscure problems.

The decisive point is that one system a team can operate beats two it cannot. Every extra datastore adds deployment, backups, upgrades, monitoring, a security surface and usually a pipeline — costs paid continuously against a benefit that is usually narrow.

It is a default, not a dogma. It genuinely loses on analytical scans over wide tables, sustained write rates beyond roughly fifty thousand per second on one node, multi-region strong-consistency writes, ephemeral high-churn data with TTL, and relevance-ranked search. Each of those is a specific property you can name and measure, and that is the form a justification for leaving should take.

Mid: A team says "we need NoSQL because we have a lot of data". How do you respond?

I would treat it as an unfinished requirement rather than a conclusion, and try to find the actual constraint underneath it — usually without disagreeing outright, because there is often a real problem being described badly.

First, how much data and what is the growth rate, measured rather than estimated? A terabyte is unremarkable for PostgreSQL on modern hardware, and I have seen teams reach for distributed systems at a fraction of what one well-tuned node handles. Second, what is actually failing — is it query latency, ingest throughput, storage cost, or something else entirely? Those have completely different remedies, and "a lot of data" describes none of them.

Then I would check whether the incumbent has been given a fair chance. In my experience most databases described as at their limit have default cost constants, a poor cache hit rate from bloat, a handful of missing indexes and no connection pooler. Fixing those routinely yields multiples, and none of that work is wasted if we do eventually move.

I would also separate the workloads, because "a lot of data" usually turns out to be an analytical problem hiding inside a transactional system. If the pain is dashboards, pre-aggregation or a replica solves it without any new technology. If it is genuinely ad-hoc exploration over large history, that is a real case for columnar — and naming it that precisely makes the conversation productive.

Finally I would point out what the move costs: most NoSQL systems give up transactions, foreign keys and joins, and if the data has invariants those must then be enforced in application code, which is where correctness bugs come from. If after all that the answer really is a different engine, I would support it — but the justification needs to be a specific property with a number attached, not volume as a general anxiety.

Mid: What costs do database evaluations typically miss?

Almost everything except throughput, and the omitted items usually dominate.

The operational surface is the biggest. How backups work and whether anyone has actually restored one — an untested backup is a hypothesis, and the restore time is your recovery objective whether you measured it or not. How upgrades happen without downtime. What the system exposes for observability. How it behaves when the disk fills, when a node dies mid-write, or during a network partition. A system with excellent throughput and no restore story is a liability.

Team capability is next, and it is systematically excluded because it is not technical. Who can debug this at three in the morning, what happens when that person leaves, and how long until a new engineer is productive? A slower database the team understands is often the correct choice, and that is a proper weighting of expected cost rather than a compromise.

If the decision introduces a second system, the integration is usually the hardest component. Change data capture, schema evolution in two places, backfills, and lag monitoring — frequently harder to operate than either database, and it needs a named owner rather than being treated as plumbing.

Then compliance, which is discovered late remarkably often. A second copy of personal data doubles the access-control, retention and deletion surface. In some columnar engines a delete is an asynchronous background mutation with no completion guarantee at a given moment, which is a data protection problem rather than a performance one.

And finally the engineering time to operate the thing over three years — usually the largest line item and the one nobody estimates — plus the exit cost, which is worth asking about at adoption when you have leverage rather than during the incident that makes you want to leave.

Senior: Design an evaluation process for a critical database decision.

I would structure it so it can produce a "no", because an evaluation that cannot fail is procurement with extra steps.

It starts with requirements written down before any product is named: the six workload dimensions, and explicit pass/fail criteria with numbers in them. Something like p99 under two seconds for twenty sampled analyst queries at three times current data volume while ingest runs at production rate. Criteria chosen after seeing results are conclusions rather than tests, so the sequencing is not a formality.

Next, exhaust the incumbent honestly and document what was tried and what it achieved. This both frequently resolves the problem and, when it does not, produces the specific residual gap that justifies moving — which is exactly what the decision record needs.

Then a proof of concept designed to expose weakness. Real data with its real skew, because uniform synthetic data hides the tenant with forty percent of the rows and the correlated columns that break estimates. A dataset exceeding memory, because everything looks excellent when it fits in the buffer pool. Running for hours or days so compaction, vacuum and checkpoints actually matter. And deliberately testing the corner the architecture did not optimise for, which you can predict from its design before running anything.

Alongside the performance work, I would test the operational paths: kill a node mid-write and measure what is lost, fill the disk, run a schema migration under load, and time a full restore. Then have someone unfamiliar with the system set it up, diagnose a slow query and perform an upgrade, timing each — that is a direct measurement of a cost you will pay for years.

The output is an architecture decision record with the context in numbers, the alternatives and why each lost, the consequences including what becomes harder, and a measurable trigger for revisiting. The alternatives section is the part with lasting value, because it prevents the same debate recurring annually with no memory of why it was settled.

Senior: When is adding a second database the right call, and how do you do it well?

When a workload's access pattern genuinely fights the incumbent's architecture, and the mismatch has been measured rather than assumed. There are a small number of these. Ephemeral high-churn data with short TTLs is the worst possible fit for in-table MVCC, so sessions and carts belong in something like Redis. Ad-hoc analytical queries over large history cannot be served by pre-aggregation by definition, which is the real case for columnar. Relevance-ranked search with faceting and fuzzy matching exceeds what a general-purpose engine's full-text support provides. And sustained write rates beyond what one tuned node handles point at an LSM design.

The discipline is that each of those is a specific property, and the justification should be a sentence with a number in it. If it cannot be written that way, the answer is usually to keep improving the incumbent.

Doing it well starts with sequencing. I would exhaust the cheap reversible options first — query tuning, pre-aggregation, a read replica, an extension that covers the need inside the existing database — because each is valuable independently and none is wasted if we do eventually move. Then introduce the second system for one clearly bounded workload rather than as a general platform, so the blast radius is small and the boundary is visible in the code.

The integration deserves the most attention, because it is usually the hardest part and the least planned. It needs a named owner, lag monitoring that is visible to users of the data, a backfill story, and a plan for schema changes that now happen in two places. I would also decide up front which system is authoritative for what, and make eventual consistency explicit rather than discovered — displaying data freshness alongside the numbers is a small thing that prevents real mistakes.

And I would settle the compliance question before adoption rather than after: where the second copy of personal data lives, how deletion propagates, and whether that propagation has a completion guarantee. That question has killed more adoptions late than performance ever has, and asking it early is cheap.

🏋️ Exercises

1 (easy): Characterise three workloads before naming any engine.
Solution 
-- Fill in the six dimensions. Only then name a candidate.

-- ── A) A BANK'S CORE LEDGER ─────────────────────────────────────────────
-- access:      point lookups by account; short statement histories
-- writes:      moderate (thousands/sec), update-in-place on balances
-- consistency: ABSOLUTE. multi-statement transactions, FKs, CHECK
--              constraints, zero tolerance for lost updates
-- scale:       100M accounts, ~1 TB. Growth predictable.
-- latency:     p99 < 100ms; RPO must be ZERO for committed transfers
-- ops:         regulated, audited, long-lived; team runs Postgres
-- → RELATIONAL, decisively. The consistency requirement eliminates most
--   alternatives before performance is discussed. Postgres or a
--   commercial RDBMS, with synchronous replication to a quorum for the
--   ledger writes specifically (WAL lesson).

-- ── B) A MOBILE GAME'S PLAYER STATE ─────────────────────────────────────
-- access:      read the whole player document by id, ~50/sec/player
-- writes:      very high, update-in-place, every action
-- consistency: per-player only. No cross-player transactions.
-- scale:       50M players × ~20 KB = 1 TB
-- latency:     p99 < 50ms globally
-- ops:         small team, wants managed
-- → The document IS the access unit and there are no cross-entity
--   invariants — a genuine document-store fit (DynamoDB, Mongo).
--   ⚠ But Postgres with a JSONB column and a primary-key lookup also
--     serves this, and keeps SQL for the surrounding features. The
--     deciding factor is the GLOBAL latency requirement, which points at
--     a managed multi-region store.

-- ── C) A LOGISTICS COMPANY'S TELEMETRY ──────────────────────────────────
-- access:      "last 24h for vehicle X" (frequent) + fleet aggregates
-- writes:      200k points/sec, APPEND-ONLY
-- consistency: none needed beyond per-write durability
-- scale:       6 TB/year, 2-year retention
-- latency:     seconds acceptable for aggregates
-- ops:         team runs Postgres
-- → TWO WORKLOADS wearing one name: high-rate ingest with per-vehicle
--   point reads, plus analytical aggregation.
--   ✓ Postgres + TimescaleDB handles both adequately (partitioning +
--     compression + continuous aggregates) with ONE operational system.
--   Escalate to ClickHouse only if measured ingest exceeds what one
--   node sustains.

-- ── THE PATTERN ─────────────────────────────────────────────────────────
-- In all three, the CONSISTENCY dimension did most of the work, and in
-- two of three the answer was "the database the team already runs".
-- Notice also that (C) was two workloads described as one — a very
-- common source of over-engineering.
2 (easy): Rewrite four weak justifications into testable ones.
Solution 
-- ── ✗ "We need MongoDB because our schema changes often." ───────────────
-- ✓ TESTABLE: "Product adds 2-3 fields per quarter to the listings
--    entity. Each requires a migration. With PG11+ ADD COLUMN is
--    metadata-only and takes milliseconds, so the migration cost is
--    approximately zero. The genuine question is whether attributes vary
--    PER LISTING — and if so, JSONB alongside real columns handles that
--    while keeping constraints and joins."
-- → The rewrite reveals the original was about migration friction that
--   no longer exists on modern Postgres.

-- ── ✗ "We need Cassandra because we have a lot of writes." ──────────────
-- ✓ TESTABLE: "We measure 12k writes/sec peak, growing 40%/year. A tuned
--    single Postgres node sustains 40-80k with append-only data. We have
--    3-5 years of headroom. Revisit at 30k/sec sustained."
-- → A number turns an anxiety into a scheduled decision.

-- ── ✗ "We need a data warehouse, analytics are slow." ───────────────────
-- ✓ TESTABLE: "14 dashboard queries take 8-40s. All 14 are FIXED and
--    aggregate immutable history. Materialised views refreshed hourly
--    bring them to <10ms — 2 weeks of work, no new system. The residual
--    is ~20 ad-hoc analyst queries/week over 3 years of history, which
--    pre-aggregation cannot serve. THAT is the columnar case, and it is
--    much smaller than the original request."
-- → Separating the fixed from the ad-hoc shrank the problem by 90%.

-- ── ✗ "We should use CockroachDB to future-proof for multi-region." ─────
-- ✓ TESTABLE: "We have no multi-region requirement today. If one arrives,
--    the likely shape is EU data residency, which is solved by a second
--    regional Postgres with routing by user home region — not by
--    multi-primary writes. Adopting distributed SQL now costs consensus
--    latency on EVERY write, permanently, for a requirement that may
--    never arrive."
-- → Naming what the future requirement would actually look like usually
--   shows it does not need the thing being proposed.

-- ── THE COMMON THREAD ───────────────────────────────────────────────────
-- Every weak justification became tractable once it contained a
-- MEASUREMENT and a specific PROPERTY. The test is whether you can
-- complete: "We need X because our workload has property Y, which the
-- incumbent handles at cost Z, and we have measured Z."
3 (medium): Design a PoC that is capable of failing.
Solution 
-- PROPOSAL: replace Postgres with ClickHouse for the events pipeline.
-- Design the evaluation.

-- ── 1. PASS/FAIL CRITERIA, WRITTEN FIRST ────────────────────────────────
-- MUST PASS ALL:
--   [ ] p99 < 3s for the 20 sampled analyst queries at 3× current volume
--   [ ] sustained ingest ≥ 150k events/sec while those queries run
--   [ ] full restore from backup completes in < 4 hours (our RTO)
--   [ ] a schema change (add a column) completes with ingest running
--   [ ] deletion of one user's events completes and is VERIFIABLE
--       within 24h  ← the GDPR requirement
--   [ ] an engineer unfamiliar with it can diagnose a slow query in <1h
-- ⚠ Written BEFORE running anything. Criteria chosen after seeing
--   results are conclusions, not tests.

-- ── 2. THE DATA ─────────────────────────────────────────────────────────
-- ✓ A production snapshot, anonymised, at 3× volume — with its REAL
--   SKEW: the tenant that is 40% of rows, the NULL-heavy join column,
--   the correlated status/timestamp pair.
-- ✗ NOT generate_series with uniform random values. Uniform data hides
--   exactly the problems that will occur (cost-models lesson).
-- ✓ Size it BEYOND MEMORY. Everything looks fast in the buffer pool.

-- ── 3. THE WORKLOAD ─────────────────────────────────────────────────────
-- ✓ Replay real query logs, at real concurrency, WHILE ingest runs.
--   Analytical engines behave very differently under concurrent write
--   load than in isolation.
-- ✓ Run for DAYS, not minutes — compaction and merges only matter once
--   the system has had to clean up after itself.

-- ── 4. TEST THE ARCHITECTURE'S KNOWN WEAK CORNER ────────────────────────
-- From the engine-landscape lesson, we PREDICT ClickHouse is weak at:
--   point lookups, single-row updates, small inserts, transactions.
-- ✓ Test each deliberately. We are not looking for it to win — we are
--   confirming the weakness is survivable for our workload. If the
--   application needs any of them, we have learned something decisive.

-- ── 5. TEST THE FAILURE PATHS ───────────────────────────────────────────
--   kill a node mid-ingest → what is lost? how long to recover?
--   fill the disk → does it degrade gracefully or wedge?
--   restore from backup → TIME IT. That number is the RTO.
--   run a mutation (delete) → measure completion time and verifiability
-- ⚠ These reveal more than any throughput number, and they are what you
--   will actually be doing during an incident.

-- ── 6. THE OPERATIONAL TEST ─────────────────────────────────────────────
-- Give it to an engineer who has never used it. Time: setup, diagnosing
-- a deliberately slow query, restoring a backup, performing an upgrade.
-- ✓ This is a direct measurement of a cost paid for years, and it is the
--   dimension benchmarks never capture.

-- ── 7. THE HONEST COMPARISON ────────────────────────────────────────────
-- Run the SAME criteria against:
--   (a) Postgres as-is
--   (b) Postgres + columnar extension on old partitions
--   (c) Parquet export + DuckDB
--   (d) ClickHouse
-- ⚠ Evaluating only the new option against the status quo is how
--   pre-decided outcomes happen. Options (b) and (c) frequently pass and
--   cost an order of magnitude less.

-- ── 8. THE DECISION RULE ────────────────────────────────────────────────
-- "We adopt the SIMPLEST option that passes all criteria." Stated in
-- advance, this prevents the result being argued afterwards.
4 (medium): Write an architecture decision record.
Solution 
-- ADR-014: Telemetry storage for the fleet platform
-- STATUS: accepted · 2026-08-06 · supersedes nothing

-- ── CONTEXT ─────────────────────────────────────────────────────────────
-- We ingest 180k telemetry points/sec from 40k vehicles, growing ~30%/yr.
-- Retention 2 years (~9 TB compressed estimate). Two query shapes:
--   (1) "last 24h for vehicle X" — 4k/sec, must be <200ms p99
--   (2) fleet aggregates over weeks — ~200/day, <10s acceptable
-- Current: a single Postgres 16 instance, unpartitioned. Ingest is at
-- 85% of capacity; the 90-day DELETE for retention takes 6 hours and
-- causes a bloat incident each quarter.
-- Team: 6 engineers, all fluent in Postgres, no Kafka/ClickHouse
-- experience. No dedicated data platform team.

-- ── WHAT WE TRIED FIRST ─────────────────────────────────────────────────
-- [x] indexes + query tuning on shape (1)      → 400ms → 90ms ✓
-- [x] moved aggregates to a replica            → removed contention
-- [ ] partitioning                             → not yet done
-- The remaining problems are the retention DELETE and ingest headroom.

-- ── DECISION ────────────────────────────────────────────────────────────
-- Adopt PostgreSQL + TimescaleDB on the existing instance.
-- Hypertables partitioned by time (1-day chunks), native compression on
-- chunks older than 7 days, continuous aggregates for shape (2),
-- retention via drop_chunks().

-- ── ALTERNATIVES CONSIDERED ─────────────────────────────────────────────
-- (a) PLAIN POSTGRES PARTITIONING. Solves retention (DETACH instead of
--     DELETE) and is zero new technology. Does NOT give compression, so
--     9 TB stays 9 TB. REJECTED as insufficient, but it is the fallback
--     if Timescale disappoints — and it is a subset of what we chose.
-- (b) CLICKHOUSE + CDC. Predicted 5-10× better on shape (2) and far
--     better compression. REJECTED: shape (1) at 4k/sec point-ish reads
--     is not its strength; it needs a CDC pipeline nobody on the team
--     can operate; and DELETE-by-user for GDPR becomes an asynchronous
--     mutation with no completion guarantee, which our DPO rejected.
-- (c) A MANAGED TIME-SERIES SERVICE. Attractive operationally.
--     REJECTED on cost at our volume (3× our current spend) and on data
--     residency — our contracts require EU-only storage.
-- (d) PARQUET + DUCKDB FOR AGGREGATES. Genuinely appealing and much
--     cheaper. REJECTED for now because shape (2) needs data no more
--     than 1 hour stale; a nightly export does not meet that. RECORDED
--     AS THE NEXT STEP if Timescale's continuous aggregates prove
--     insufficient.

-- ── CONSEQUENCES ────────────────────────────────────────────────────────
-- MAKES EASY:  retention becomes drop_chunks (seconds, no bloat);
--   compression estimated 8-12× (~9 TB → ~1 TB); one operational system;
--   full SQL and transactions with our vehicle/customer tables; the team
--   already knows how to operate it.
-- MAKES HARD:  Timescale is an extension, so major-version upgrades are
--   coupled to its release cycle. Compressed chunks are effectively
--   immutable — late-arriving data older than 7 days requires
--   decompressing a chunk.
-- WE ARE ACCEPTING: shape (2) over the FULL 2 years will take 10-60s
--   rather than the 1-3s ClickHouse would give. Analysts have confirmed
--   this is acceptable for a query they run a few times a week.

-- ── REVISIT WHEN (measurable triggers) ──────────────────────────────────
--   • sustained ingest exceeds 400k points/sec, OR
--   • shape (2) p99 exceeds 60s, OR
--   • analysts run >20 full-history queries/day (the pattern shifts from
--     occasional to routine), OR
--   • we hire a data platform team (changes the operational calculus)
-- Review scheduled: 2027-02-06.

-- ── WHY THE RECORD MATTERS ──────────────────────────────────────────────
-- In 18 months someone will propose ClickHouse again. This record means
-- the discussion starts from "have the triggers been met?" rather than
-- relitigating from zero — and if they HAVE been met, the answer is
-- already written down.
5 (hard): Untangle a system that has too many databases.
Solution 
-- INHERITED SYSTEM: Postgres, MongoDB, Redis, Elasticsearch, ClickHouse,
-- DynamoDB, Neo4j. Team of 8. Six pipelines. Nobody understands all of
-- it. Three outages last quarter were sync failures, not database
-- failures.

-- ── STEP 1: MAP WHAT EACH ACTUALLY HOLDS AND WHY ────────────────────────
-- For each: what data, what access pattern, what depends on it, who
-- added it and when, and IS THE ORIGINAL REASON STILL TRUE?
--  Postgres      orders, users, payments        core, justified ✓
--  MongoDB       product catalogue              "flexible schema", 2021
--  Redis         sessions, cart, rate limits    justified ✓
--  Elasticsearch product search                 justified ✓
--  ClickHouse    analytics events               justified ✓
--  DynamoDB      feature flags (400 rows!)      a hackathon, 2022
--  Neo4j         "recommendations"              a POC that shipped, 2023

-- ── STEP 2: FIND THE ONES WITH NO LIVING JUSTIFICATION ──────────────────
-- DynamoDB: 400 rows of feature flags. Costs a client library, IAM
--   config, a monitoring gap and a second failure mode — for data that
--   is a single Postgres table.
--   → MIGRATE. An afternoon's work, removes a whole system.
-- Neo4j: recommendations are computed nightly in ClickHouse anyway and
--   served from Redis. The graph queries run twice a week and complete
--   in 40s as recursive CTEs in Postgres.
--   → MIGRATE. Removes a system nobody can debug.
-- MongoDB: the catalogue has variable attributes on a stable core —
--   exactly the JSONB-alongside-real-columns case. It also needs joins
--   to inventory and pricing that currently happen in application code.
--   → MIGRATE to Postgres JSONB. Biggest effort, biggest win: it also
--     removes a pipeline AND recovers referential integrity.

-- ── STEP 3: CONFIRM THE ONES THAT STAY ──────────────────────────────────
-- Redis: ephemeral, high-churn, TTL-native. Wrong for Postgres MVCC.  ✓
-- Elasticsearch: relevance ranking and faceting exceed Postgres FTS.  ✓
-- ClickHouse: ad-hoc analytics over billions of rows.                 ✓
-- ✓ Each has a property Postgres genuinely lacks. That is the test.

-- ── STEP 4: THE PIPELINES ARE THE REAL PROBLEM ──────────────────────────
-- Six pipelines caused three of last quarter's outages. Removing three
-- databases removes three pipelines — which is a bigger reliability win
-- than any database change.
-- ⚠ Worth stating explicitly: the systems were not failing; the SEAMS
--   between them were. That is the usual pattern in polyglot
--   architectures and it is rarely what gets attention.

-- ── STEP 5: SEQUENCE BY RISK AND REWARD ─────────────────────────────────
-- 1. DynamoDB → Postgres      1 day.  Lowest risk, immediate win.
-- 2. Neo4j → Postgres         1 week. Low traffic, easy rollback.
-- 3. MongoDB → Postgres JSONB 6 weeks. Dual-write, backfill, verify,
--                             cut over, keep rollback for a month.
-- ✓ Each step is independently valuable and reversible. Do NOT attempt
--   them in parallel with a team of 8.

-- ── STEP 6: WRITE THE RULE THAT PREVENTS RECURRENCE ─────────────────────
-- "Adding a datastore requires an ADR naming the specific property the
--  incumbent lacks, with a measurement, plus a named owner for any
--  pipeline it introduces."
-- ⚠ Every one of the three removals began as a reasonable local decision
--   by someone solving a real problem. The failure was organisational —
--   no forcing function to justify the ONGOING cost. The rule is the
--   actual deliverable here, more than the migrations.

-- ── THE OUTCOME ─────────────────────────────────────────────────────────
-- 7 databases → 4. 6 pipelines → 3. The team can now hold the
-- architecture in their heads, which is a real engineering property even
-- though it appears on no dashboard.
6 (hard): Decide under genuine uncertainty.
Solution 
-- SITUATION: a startup, 6 weeks to launch. Product is a collaborative
-- document editor with real-time editing, comments, version history and
-- full-text search. Nobody knows if it will have 100 users or 1 million.
-- Team of 4, all comfortable with Postgres, none with distributed
-- systems. This is the hardest kind of decision: real uncertainty, real
-- deadline, and irreversible-feeling choices.

-- ── STEP 1: SEPARATE WHAT IS KNOWN FROM WHAT IS NOT ─────────────────────
-- KNOWN:   the data model (documents, users, comments, versions), the
--          access patterns, the team's skills, the deadline
-- UNKNOWN: scale, which features matter, whether the product survives
-- ✓ Design for what is KNOWN. Designing for unknown scale is designing
--   for a hypothesis, and it costs you the deadline you definitely have
--   to serve growth you might not get.

-- ── STEP 2: OPTIMISE FOR THE MOST LIKELY OUTCOME ────────────────────────
-- ⚠ The most likely outcome for a pre-launch startup is NOT 1M users. It
--   is that the product changes substantially or does not survive. The
--   correct optimisation target is ITERATION SPEED and OPTIONALITY, not
--   throughput.
-- → One Postgres. Everything in it.

-- ── STEP 3: THE SPECIFIC DESIGN ─────────────────────────────────────────
-- documents, users, comments  → ordinary tables, FKs, transactions
-- version history             → append-only table, partitioned by month
--                               from day one (cheap now, a migration
--                               later)
-- full-text search            → tsvector + GIN. Adequate to a
--                               surprisingly large scale.
-- real-time collaboration     → ⚠ NOT a database question. CRDTs or OT
--                               in the application, with Postgres for
--                               durable snapshots. Choosing a database
--                               for this would be a category error.
-- presence / ephemeral state  → Redis IF needed; start with in-memory
--                               per-instance state and add Redis when
--                               there is a second instance.

-- ── STEP 4: MAKE THE FUTURE CHEAPER WITHOUT PAYING NOW ──────────────────
-- Decisions that cost nothing today and preserve options:
-- ✓ bigint keys, not random UUIDs (btrees lesson) — irreversible later
-- ✓ timestamptz everywhere — permanently unfixable if wrong
-- ✓ partition version history from the start — a migration later
-- ✓ keep the schema normalised; denormalise with evidence
-- ✓ put search behind a thin interface so swapping to Elasticsearch is
--   one module, not a rewrite
-- ⚠ THAT LAST ONE IS THE KEY MOVE: an abstraction at the likely
--   substitution boundary costs almost nothing now and converts a
--   scary future migration into a contained one. Do it at the boundaries
--   you can NAME — not everywhere, which is just speculative
--   abstraction.

-- ── STEP 5: WHAT I WOULD REFUSE TO DO ───────────────────────────────────
-- ✗ adopt a distributed database "in case we grow" — consensus latency
--   on every write, from day one, for scale that probably will not come
-- ✗ add Elasticsearch before Postgres FTS is measured as insufficient
-- ✗ add a warehouse before there are analysts
-- ✗ microservice the data layer — every cross-entity invariant becomes a
--   distributed transaction problem, for an unproven product
-- ✓ Each refusal buys weeks of the six we have.

-- ── STEP 6: THE TRIGGERS, WRITTEN DOWN NOW ──────────────────────────────
--   search p99 > 500ms or relevance complaints → Elasticsearch
--   write throughput > 20k/sec sustained       → partition, then split
--   analytics requests from a real analyst     → replica, then
--                                                pre-aggregate
--   a second app instance                      → Redis for presence
-- ✓ Writing triggers at decision time is what converts "we'll deal with
--   it later" into an actual plan — and it takes ten minutes.

-- ── THE HONEST SUMMARY ──────────────────────────────────────────────────
-- The right answer under uncertainty is usually the SIMPLEST thing that
-- meets known requirements, plus cheap decisions that preserve
-- optionality, plus written triggers. Scaling problems are good problems
-- — they mean the product worked. Missing the launch because you built
-- for scale you never reached is a bad problem, and it is the more
-- common one.

🎯 Key Takeaways

  • Characterise the workload in six dimensions — access, writes, consistency, scale, latency, operations — before naming any engine.
  • The consistency requirement usually does most of the work and is the least negotiable constraint.
  • Default to PostgreSQL because one system a team can operate beats two it cannot, not because it wins every category.
  • Justify leaving with a completed sentence: "we need X because our workload has property Y, which the incumbent handles at cost Z, and we measured Z".
  • Design for 10× current scale, not 1000× — the cost is paid continuously and the benefit only arrives if the growth does.
  • Evaluations systematically miss backups and restores, upgrades, team capability, pipeline ownership, compliance and three-year engineering time.
  • A proof of concept must be able to fail: criteria written first, real skewed data beyond memory, running long enough for background work, and the failure paths tested.
  • Deliberately test the corner the architecture did not optimise for — you can predict where it is weak before running anything.
  • Write a decision record with alternatives, consequences and a measurable revisit trigger; the alternatives section is what has value in two years.
  • In polyglot systems the seams fail more often than the systems — removing a database usually removes a pipeline, which is the larger reliability win.
