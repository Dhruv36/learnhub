SELECT & Filtering Basics

What you'll master: why SQL being declarative changes how you debug it, the logical order of execution that explains almost every "why can't I use that here" error, three-valued logic and the silent row loss NULL causes in filters and negations, the WHERE toolkit and which predicates a database can actually use an index for, CASE and conditional expressions, and why SELECT * is fine in a console and a liability in application code. Examples are PostgreSQL; differences from MySQL are called out where they matter.

Part 1 — Declarative Thinking

-- You describe WHAT you want. The planner decides HOW.
SELECT name, email, score
FROM   users
WHERE  score >= 80 AND active
ORDER BY score DESC
LIMIT  10;

-- The database may choose to:
--   scan the whole table, or use an index on (active, score)
--   sort the results, or read them pre-sorted from an index
--   evaluate `active` first, or `score >= 80` first
-- Nothing in your query specifies any of that. Two queries that look
-- different can produce identical plans, and two that look nearly
-- identical can differ by three orders of magnitude.

-- ── THE PRACTICAL CONSEQUENCE ───────────────────────────────────────────
-- When SQL is slow, you do not read the query harder. You ask the
-- database what it did:
EXPLAIN ANALYZE SELECT ...;      -- covered fully in Indexes & Query Plans

-- ── SET-BASED, NOT ROW-BY-ROW ───────────────────────────────────────────
-- The instinct from procedural languages is to loop. In SQL that is
-- almost always the wrong shape:
--   for user in users:                  ✗ N round trips, N plans, no
--       db.execute("UPDATE ...", user)    chance to use a bulk path
UPDATE users SET tier = 'gold' WHERE score >= 90;   -- ✓ one statement
-- The engine is optimised for operating on sets. A loop of single-row
-- statements gives up every optimisation it has.

-- ── WHAT A QUERY IS MADE OF ─────────────────────────────────────────────
SELECT   name, score * 1.1 AS adjusted   -- PROJECTION: which columns
FROM     users                            -- SOURCE
WHERE    score >= 80                      -- SELECTION: which rows
ORDER BY adjusted DESC                    -- ORDERING
LIMIT    10 OFFSET 20;                    -- PAGINATION

-- Aliases: AS is optional but write it. `SELECT name email FROM users`
-- is a valid query that silently renames the column instead of the typo
-- you meant.

-- ── QUOTING: THE RULE THAT SURPRISES PEOPLE ─────────────────────────────
WHERE name = 'Ada'        -- SINGLE quotes = a string LITERAL
WHERE "name" = 'Ada'      -- DOUBLE quotes = an IDENTIFIER (column/table)
WHERE name = "Ada"        -- ✗ Postgres: column "Ada" does not exist
-- MySQL accepts double quotes for strings by default, which is why code
-- written against MySQL breaks on Postgres. Single quotes always.

Part 2 — The Logical Order of Execution

-- YOU WRITE:
SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT

-- THE DATABASE EVALUATES:
--   1. FROM / JOIN     assemble the source rows
--   2. WHERE           filter ROWS
--   3. GROUP BY        collapse rows into groups
--   4. HAVING          filter GROUPS
--   5. SELECT          compute the output columns (aliases exist HERE)
--   6. DISTINCT
--   7. ORDER BY        sort
--   8. LIMIT / OFFSET  cut

-- This single list explains most beginner errors.

-- ── WHY AN ALIAS FAILS IN WHERE BUT WORKS IN ORDER BY ───────────────────
SELECT price * qty AS total FROM orders WHERE total > 100;
-- ✗ ERROR: column "total" does not exist
--   WHERE runs at step 2; the alias is not created until step 5.
SELECT price * qty AS total FROM orders WHERE price * qty > 100;   -- ✓
SELECT price * qty AS total FROM orders ORDER BY total;            -- ✓
--   ORDER BY runs at step 7, after SELECT. So it CAN see the alias.
-- (MySQL permits the alias in WHERE as an extension. Portable code does
--  not rely on it.)

-- ── WHY AGGREGATES ARE ILLEGAL IN WHERE ─────────────────────────────────
SELECT dept, AVG(salary) FROM emp WHERE AVG(salary) > 50000 GROUP BY dept;
-- ✗ grouping happens at step 3, after WHERE. There is no average yet.
SELECT dept, AVG(salary) FROM emp GROUP BY dept HAVING AVG(salary) > 50000;
-- ✓ HAVING runs at step 4, after the groups exist.
--
-- WHERE filters rows BEFORE grouping; HAVING filters groups AFTER.
-- That is a performance difference too, not only a syntax one: filtering
-- in WHERE means fewer rows to group.

-- ── WHY LIMIT WITH ORDER BY IS NOT "THE FIRST 10 ROWS" ───────────────────
SELECT * FROM users LIMIT 10;
-- No ORDER BY = NO GUARANTEED ORDER. Not insertion order, not primary key
-- order. It is whatever the plan produced, and it changes when the table
-- grows, when a row is updated, or when the planner picks a different
-- index. "It was ordered on my machine" is the classic version of this
-- bug reaching production.
SELECT * FROM users ORDER BY created_at DESC, id DESC LIMIT 10;   -- ✓
-- Add a TIEBREAKER (id) — otherwise rows with equal created_at can swap
-- between pages and a user paging through sees duplicates and gaps.

-- ── OFFSET DOES NOT SCALE ───────────────────────────────────────────────
SELECT * FROM events ORDER BY id LIMIT 20 OFFSET 100000;
-- The database produces 100,020 rows and throws away 100,000. Page 5000
-- is thousands of times slower than page 1.
SELECT * FROM events WHERE id > :last_seen_id ORDER BY id LIMIT 20;
-- ✓ KEYSET PAGINATION. Constant time at any depth, and stable when rows
--   are inserted mid-scroll. Its limitation is that you cannot jump to
--   an arbitrary page number — which is usually fine for feeds.

Part 3 — NULL and Three-Valued Logic

-- NULL is not zero. It is not an empty string. It means UNKNOWN.
-- Every comparison involving it returns UNKNOWN, and WHERE keeps only
-- rows where the condition is TRUE.

WHERE email = NULL       -- ✗ matches NOTHING, ever. No error, no warning.
WHERE email IS NULL      -- ✓
WHERE email IS NOT NULL  -- ✓
WHERE email IS DISTINCT FROM 'x'    -- NULL-safe inequality (Postgres)
WHERE email <=> 'x'                  -- MySQL's NULL-safe equals

-- ── THE TRUTH TABLE ─────────────────────────────────────────────────────
--   TRUE  AND UNKNOWN = UNKNOWN        TRUE  OR UNKNOWN = TRUE
--   FALSE AND UNKNOWN = FALSE          FALSE OR UNKNOWN = UNKNOWN
--   NOT UNKNOWN       = UNKNOWN   ← the one that causes real bugs

-- ── THE NEGATION TRAP ───────────────────────────────────────────────────
SELECT count(*) FROM users WHERE score > 50;        -- 60
SELECT count(*) FROM users WHERE NOT (score > 50);  -- 30
SELECT count(*) FROM users;                          -- 100
-- 60 + 30 = 90. Ten rows have a NULL score and appear in NEITHER.
-- The two queries look exhaustive and are not. This is the single most
-- common source of "the numbers don't add up" in reports.
WHERE score <= 50 OR score IS NULL                   -- ✓ the real complement

-- ── NOT IN WITH A NULL IS CATASTROPHIC ──────────────────────────────────
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM banned);
-- If ANY banned.user_id is NULL, this returns ZERO ROWS. Always.
-- Because `id NOT IN (1, 2, NULL)` expands to
--   id <> 1 AND id <> 2 AND id <> NULL
-- and the last term is UNKNOWN, so the whole AND can never be TRUE.
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM banned b WHERE b.user_id = u.id);  -- ✓
-- NOT EXISTS is NULL-safe and usually plans better. Prefer it.

-- ── WHERE NULL BEHAVES DIFFERENTLY FROM WHAT YOU EXPECT ─────────────────
SELECT count(email) FROM users;      -- SKIPS NULLs. count(*) does not.
SELECT sum(amount) FROM refunds;     -- NULL if there are no rows (not 0)
SELECT 'a' || NULL;                  -- NULL — concatenation is contagious
SELECT DISTINCT status FROM t;       -- NULLs GROUP TOGETHER here...
WHERE status = status;               -- ...but this excludes them
ORDER BY score;                      -- Postgres: NULLs LAST by default
                                     -- MySQL:    NULLs FIRST
ORDER BY score NULLS FIRST;          -- be explicit when it matters
UNIQUE (email)                       -- allows MANY NULLs — they are not
                                     -- equal to each other

-- ── HANDLING IT ─────────────────────────────────────────────────────────
COALESCE(nickname, name, 'anonymous')    -- first non-NULL
NULLIF(divisor, 0)                        -- turn 0 into NULL to avoid a
                                          -- division-by-zero error
CASE WHEN score IS NULL THEN 'unrated' ELSE 'rated' END

-- ── AND THE DESIGN LESSON ───────────────────────────────────────────────
-- The best fix is usually to not allow the NULL. A column that is
-- conceptually always present should be NOT NULL with a default. Every
-- nullable column is a branch every future query has to remember.
Key insight: the two ideas in this lesson explain most SQL confusion for years afterwards. The logical order of execution tells you what exists at each point, so an alias missing in WHERE, an aggregate rejected before GROUP BY, and a LIMIT that returns different rows each run all stop being arbitrary rules. Three-valued logic tells you that a row can fail both a condition and its negation, which is why filters silently lose rows and why NOT IN against a nullable column returns nothing at all. Neither produces an error message — that is precisely why they are worth internalising early.

Part 4 — The Filtering Toolkit

WHERE score BETWEEN 80 AND 100      -- INCLUSIVE on both ends
WHERE role IN ('admin', 'editor')   -- set membership
WHERE name LIKE 'A%'                 -- % = any run, _ = exactly one char
WHERE name ILIKE 'a%'                -- case-insensitive (Postgres)
WHERE email IS NOT NULL
WHERE tags @> ARRAY['sql']            -- Postgres array containment
WHERE data->>'plan' = 'pro'           -- JSONB field

-- ── DATE RANGES: THE BETWEEN BUG ────────────────────────────────────────
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31'
-- ✗ '2026-01-31' means 2026-01-31 00:00:00. Everything after midnight on
--   the 31st is MISSING — a whole day, silently, every month.
WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'
-- ✓ half-open interval. Works for dates, timestamps, and timestamps with
--   fractional seconds, and needs no thought about the last instant.
-- Use half-open ranges for time. Always.

-- ── SARGABILITY: WHETHER AN INDEX CAN BE USED ───────────────────────────
-- A predicate is "sargable" if the database can seek in an index rather
-- than computing something for every row.

WHERE YEAR(created_at) = 2026                  -- ✗ function on the COLUMN
WHERE created_at >= '2026-01-01'               -- ✓ index range scan
      AND created_at < '2027-01-01'

WHERE LOWER(email) = 'a@b.com'                 -- ✗ unless you built an
                                               --   index on LOWER(email)
WHERE email = 'a@b.com'                        -- ✓  (or use citext)

WHERE price * 1.2 > 100                        -- ✗
WHERE price > 100 / 1.2                        -- ✓ move the maths to the
                                               --   constant side

WHERE name LIKE '%smith%'                      -- ✗ a leading % cannot
                                               --   seek a b-tree
WHERE name LIKE 'smith%'                       -- ✓ prefix = a range scan
-- For infix search you need a trigram index (pg_trgm) or full-text
-- search — see Indexes & Query Plans.

-- ── OR IS OFTEN THE ENEMY ───────────────────────────────────────────────
WHERE email = :x OR phone = :x        -- may scan; one index cannot serve
                                      -- both sides
SELECT ... WHERE email = :x
UNION ALL
SELECT ... WHERE phone = :x;          -- ✓ each branch uses its own index

-- ── IN vs EXISTS ────────────────────────────────────────────────────────
WHERE id IN (SELECT user_id FROM orders)              -- fine, and NULL-risky
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id)   -- ✓ safer
-- EXISTS short-circuits on the first match and is NULL-safe. Modern
-- planners often produce the same plan for both, but NOT IN and NOT
-- EXISTS are genuinely different (see Part 3).

-- ── NEVER BUILD SQL BY CONCATENATION ────────────────────────────────────
-- "SELECT * FROM users WHERE email = '" + input + "'"     ✗ INJECTION
cur.execute("SELECT * FROM users WHERE email = %s", (email,))   -- ✓
-- The driver sends the value separately from the statement, so it can
-- never be parsed as SQL. This is not a style preference; string
-- formatting is how databases get dropped.

Part 5 — Expressions, CASE, and Types

-- ── CASE: CONDITIONAL LOGIC IN A COLUMN ─────────────────────────────────
SELECT name,
       CASE WHEN score >= 90 THEN 'A'
            WHEN score >= 80 THEN 'B'
            WHEN score IS NULL THEN 'unrated'    -- handle it EXPLICITLY
            ELSE 'C'
       END AS grade
FROM users;
-- Evaluated top to bottom, first match wins — so order the branches from
-- most specific to least. With no ELSE, unmatched rows get NULL.

-- CASE inside an aggregate is the pivot idiom (see Aggregates):
SELECT count(*) FILTER (WHERE status = 'paid')   AS paid,      -- Postgres
       count(*) FILTER (WHERE status = 'refunded') AS refunded
FROM orders;
SELECT sum(CASE WHEN status = 'paid' THEN 1 ELSE 0 END) AS paid  -- portable
FROM orders;

-- ── TYPE COERCION BITES ─────────────────────────────────────────────────
WHERE user_id = '42'          -- Postgres: may cast, may error, may kill
                              -- the index depending on the types
WHERE user_id = 42            -- ✓ match the column's type
-- MySQL is worse here: comparing a string column to a NUMBER silently
-- coerces the COLUMN, disabling its index across the whole table.

SELECT 1 / 2;                 -- 0   — INTEGER division in both engines
SELECT 1.0 / 2;               -- 0.5
SELECT count(*) / count(DISTINCT x);   -- ✗ integer division in a metric

-- ── MONEY IS NOT A FLOAT ────────────────────────────────────────────────
amount FLOAT          -- ✗ 0.1 + 0.2 != 0.3; sums drift; audits fail
amount NUMERIC(12,2)  -- ✓ exact decimal
-- The bug appears months later as a one-cent reconciliation difference
-- that nobody can trace.

-- ── TIMESTAMPS: STORE UTC, WITH A TIME ZONE ─────────────────────────────
created_at TIMESTAMP              -- ✗ no zone. Ambiguous during DST, and
                                  --   the meaning depends on who reads it
created_at TIMESTAMPTZ            -- ✓ stored as UTC, converted on display
now()                             -- transaction start time (Postgres)
clock_timestamp()                 -- actual wall clock, changes mid-query

-- ── STRING BASICS ───────────────────────────────────────────────────────
'a' || 'b'                        -- concatenation (Postgres standard)
CONCAT('a', 'b')                  -- portable, and NULL-tolerant
LOWER(x)  UPPER(x)  TRIM(x)  LENGTH(x)  SUBSTRING(x FROM 1 FOR 3)
SPLIT_PART(email, '@', 2)         -- Postgres

-- ── DISTINCT ────────────────────────────────────────────────────────────
SELECT DISTINCT country FROM users;
SELECT DISTINCT ON (user_id) *    -- Postgres: first row per user_id,
FROM events ORDER BY user_id, created_at DESC;   -- per the ORDER BY
-- DISTINCT is often a symptom rather than a fix: if a join is producing
-- duplicates, DISTINCT hides the duplication instead of correcting the
-- join. Ask why the duplicates exist first (see JOINs).

Part 6 — SELECT * and Query Hygiene

SELECT * FROM users WHERE id = 1;
-- Perfect for exploring. A liability in application code, for five
-- separate reasons:

-- 1. IT BREAKS ON SCHEMA CHANGE
--    Code that indexes results positionally shifts silently when a
--    column is inserted. Code that maps by name breaks when a column is
--    renamed — but at least loudly.

-- 2. IT SHIPS DATA YOU DO NOT NEED
--    A `bio TEXT` or a `payload JSONB` column is fetched, serialised,
--    sent over the network and parsed on every row of every query.

-- 3. IT PREVENTS INDEX-ONLY SCANS
--    If an index contains (user_id, created_at) and you select only
--    those, the database never touches the table. SELECT * forces a heap
--    fetch per row — often the difference between 2ms and 200ms.

-- 4. IT LEAKS COLUMNS
--    Add `password_hash` or `internal_notes` to the table and it is
--    immediately in every API response built from SELECT *.

-- 5. IT BREAKS ON JOINS
SELECT * FROM users u JOIN orders o ON o.user_id = u.id;
--    Two `id` columns, two `created_at` columns. Which one did your ORM
--    map? It depends on the driver.

SELECT u.id, u.name, o.id AS order_id, o.total   -- ✓ explicit, stable
FROM users u JOIN orders o ON o.user_id = u.id;

-- ── FORMATTING THAT SURVIVES REVIEW ─────────────────────────────────────
SELECT u.id,
       u.name,
       count(o.id) AS order_count
FROM       users  u
LEFT JOIN  orders o ON o.user_id = u.id
WHERE      u.created_at >= '2026-01-01'
GROUP BY   u.id, u.name
HAVING     count(o.id) > 5
ORDER BY   order_count DESC;
-- Keywords starting each line, one column per line, tables aliased
-- consistently and briefly. A query is read far more often than written,
-- and a diff of a well-formatted query shows what actually changed.

-- ── COMMENT THE WHY ─────────────────────────────────────────────────────
-- Exclude test tenants: they inflate the funnel by ~8% (see TICKET-4412)
WHERE tenant_id NOT IN (SELECT id FROM tenants WHERE is_internal)
-- Business rules that live only in a WHERE clause are the ones nobody
-- can explain a year later.

-- ── THE HABIT THAT PREVENTS DISASTERS ───────────────────────────────────
-- Write every destructive statement as a SELECT first:
SELECT * FROM users WHERE last_login < '2020-01-01';   -- 1. inspect
DELETE FROM users WHERE last_login < '2020-01-01';     -- 2. same WHERE
-- And run it inside a transaction you can roll back (see Transactions).

Interview Questions

Beginner: Explain the logical order of execution and one bug it prevents.

Although you write SELECT first, the database evaluates FROM and any joins, then WHERE, then GROUP BY, then HAVING, then SELECT, then ORDER BY, and finally LIMIT. Knowing that sequence turns several apparently arbitrary rules into consequences of one fact: things only exist once the step that creates them has run.

The clearest example is a column alias. Writing SELECT price * qty AS total ... WHERE total > 100 fails, because WHERE runs before SELECT has computed the alias, while the same alias works fine in ORDER BY because that runs afterwards. The same reasoning explains why an aggregate is illegal in WHERE but legal in HAVING: grouping has not happened yet at the point WHERE runs. That is also a performance distinction rather than only a syntactic one — filtering in WHERE removes rows before they have to be grouped, so pushing conditions there when you can is strictly cheaper.

Beginner: What is NULL and how does it break naive queries?

NULL means unknown — not zero, not an empty string. Any comparison involving it evaluates to UNKNOWN rather than true or false, and since WHERE keeps only rows where the condition is true, any row whose condition touched a NULL is dropped. That is why WHERE email = NULL matches nothing at all and IS NULL is the only correct test.

The consequence that actually causes bugs is that NOT UNKNOWN is still UNKNOWN, so a condition and its negation are not exhaustive. If ten of a hundred users have a NULL score, then WHERE score > 50 and WHERE NOT (score > 50) return sixty and thirty rows — the ten NULLs appear in neither, and the report quietly does not add up. The tools for handling it are COALESCE to substitute a default, an explicit OR col IS NULL when you want those rows, and IS DISTINCT FROM for NULL-safe inequality. Best of all is preventing it: a column that is conceptually always present should be declared NOT NULL, because every nullable column is a branch every future query has to remember.

Mid: Why does NOT IN with a subquery sometimes return zero rows?

Because one of the values the subquery returned was NULL. id NOT IN (1, 2, NULL) expands to id <> 1 AND id <> 2 AND id <> NULL, and that last term is UNKNOWN for every row. UNKNOWN ANDed with anything can never be TRUE, so the predicate is never satisfied and the query returns nothing — no error, no warning, just an empty result where there should have been thousands of rows.

What makes it dangerous is that it depends on the data rather than the query. The statement works correctly for months and then returns nothing the day a single NULL appears in that column, which is usually long after whoever wrote it has moved on. The fix is NOT EXISTS with a correlated condition, which uses a genuine join semantic rather than a value comparison and so is unaffected by NULLs; it also tends to plan better, because the optimiser can turn it into an anti-join and short-circuit at the first match. A left join with an IS NULL check on the right side is a third correct formulation. I would treat NOT IN against a subquery as something to flag in review unless the column is provably NOT NULL.

Mid: What makes a WHERE clause unable to use an index?

The general rule is that the indexed column has to appear on its own, so the database can seek to a position in the index rather than computing a value for every row. Wrapping the column in a function breaks that: WHERE YEAR(created_at) = 2026 requires evaluating YEAR on every row, whereas WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01' is a range scan on the same index. The same applies to arithmetic on the column, which should be moved to the constant side, and to LOWER(email) = ..., which needs either an expression index on LOWER(email) or a case-insensitive column type.

A leading wildcard has the same effect for a different reason: LIKE 'smith%' is a prefix and therefore a contiguous range in a B-tree, while LIKE '%smith%' could match anywhere and has no range to seek, so it needs a trigram or full-text index instead. Type mismatches are the subtle one — comparing a string literal to a numeric column can force the database to cast the column, which disables the index across the whole table; MySQL does this silently and it is a classic cause of a query that was fast in testing and scans in production. And OR across two different columns often cannot use either index, in which case splitting the query into a UNION ALL of two indexed branches is usually much faster. The way to confirm any of this is EXPLAIN ANALYZE rather than reasoning, because the planner also weighs selectivity — it will correctly choose a sequential scan over an index when the predicate matches most of the table.

Senior: A query returns different rows on each run and nobody changed the data. Why?

Almost certainly a LIMIT without a fully deterministic ORDER BY. SQL guarantees no row order unless you ask for one — not insertion order, not primary key order — so the result is whatever the plan happened to produce. That is stable enough to look correct in development and changes when the table grows past the point where the planner switches from an index scan to a sequential scan, when a row is updated and physically relocated, when autovacuum reorganises pages, or when parallel workers return in a different sequence.

The subtler version is an ORDER BY that is not unique. Ordering by created_at alone when several rows share a timestamp leaves their relative order undefined, and with pagination that is worse than cosmetic: a user paging through can see the same row twice and never see another one at all, because the tie broke differently between two queries. The fix is to append a unique tiebreaker, typically the primary key, to make the ordering total.

For pagination specifically I would go further and move off OFFSET altogether. Deep offsets are both slow — the database materialises and discards every skipped row — and unstable, because an insert or delete near the front shifts every subsequent page. Keyset pagination, remembering the last (created_at, id) seen and asking for rows after it, is constant time at any depth and immune to concurrent inserts. It cannot jump to an arbitrary page number, which is the trade-off, and for feeds and infinite scroll that is not a real requirement.

Senior: How do you approach a query you did not write that is now too slow?

I would resist reading it harder and instead ask the database what it actually did. EXPLAIN ANALYZE gives the real plan with real timings and row counts, and the first thing I look for is the gap between estimated and actual rows — a planner that expects five rows and gets five hundred thousand has made every downstream decision on bad information, and the cause is usually stale statistics or a correlation it cannot see. Then I look for the operation actually consuming the time, which is often a nested loop over a large outer set, a sequential scan on a table that has an index the query cannot use, or a sort spilling to disk.

The fixes cluster into a few categories. Non-sargable predicates — a function on the column, a type mismatch, a leading wildcard — are the most common and often the easiest, since rewriting a YEAR(created_at) = 2026 as a half-open range can change a scan into a seek with no semantic change. Missing or wrong indexes come next, keeping in mind that composite column order matters and that an index which lets the query avoid touching the table at all is worth much more than one that does not. Then there are shape problems: SELECT * preventing an index-only scan, OR across columns that would be better as a union, DISTINCT papering over a join that fans out rows, and pagination by deep offset.

Two things I would check before optimising anything. Whether the query is slow or merely called too often — a two-millisecond query executed in a loop per row is an application problem that no amount of index tuning fixes, and it is more common than a genuinely slow statement. And whether the result is even correct, because a surprising number of slow queries are slow precisely because a join is producing duplicate rows that a DISTINCT then removes. Fixing the join makes it both faster and right, which is a better outcome than making the wrong answer arrive sooner.

🏋️ Exercises

1 (easy): This query is meant to find users who have not scored above 50. It returns the wrong count. Fix it.
Solution 
-- Setup
CREATE TABLE users (id int, name text, score int);
INSERT INTO users VALUES (1,'a',80), (2,'b',30), (3,'c',NULL);

-- ✗ BEFORE
SELECT count(*) FROM users WHERE NOT (score > 50);      -- 1
SELECT count(*) FROM users WHERE score > 50;            -- 1
SELECT count(*) FROM users;                              -- 3
-- 1 + 1 = 2, not 3. Row 3 satisfies NEITHER condition.

-- WHY: score > 50 with score = NULL evaluates to UNKNOWN.
--      NOT UNKNOWN is still UNKNOWN.
--      WHERE keeps only TRUE, so the NULL row is dropped by BOTH.

-- ✓ AFTER — decide what a NULL score MEANS, then say so
SELECT count(*) FROM users WHERE score <= 50 OR score IS NULL;   -- 2
--   "unrated counts as not-passing"

SELECT count(*) FROM users WHERE COALESCE(score, 0) <= 50;       -- 2
--   same result, treats unrated as zero — but this is NOT sargable,
--   so on a large table prefer the explicit OR form

SELECT count(*) FROM users WHERE score <= 50;                    -- 1
--   "unrated is not counted at all" — also a valid answer, if that is
--   what the business means. The bug was never stating which.

-- ── THE SAME TRAP, THREE MORE PLACES ────────────────────────────────────
SELECT count(score) FROM users;         -- 2 — count(col) SKIPS NULLs
SELECT count(*) FROM users;             -- 3 — count(*) counts ROWS
SELECT avg(score) FROM users;           -- 55, not 36.67 — the NULL is
                                        -- excluded from BOTH sum and n
SELECT sum(score) FROM users WHERE 1=0; -- NULL, not 0 — sum over no rows

-- ── THE REAL FIX ────────────────────────────────────────────────────────
ALTER TABLE users ALTER COLUMN score SET NOT NULL;   -- if it should be
-- Or add an explicit `is_rated boolean NOT NULL` so the state is a value
-- rather than an absence. Every nullable column is a branch every future
-- query must remember.
2 (easy): This monthly report has been missing data for a year. Find the bug.
Solution 
-- ✗ BEFORE
SELECT count(*), sum(total)
FROM orders
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31';

-- created_at is a TIMESTAMP. '2026-01-31' is parsed as
-- 2026-01-31 00:00:00, so BETWEEN excludes everything from 00:00:00.001
-- on the 31st onward.
--
-- One full day missing per month, ~3% of annual revenue, and the totals
-- look plausible enough that nobody notices.

-- ✓ AFTER — half-open interval
SELECT count(*), sum(total)
FROM orders
WHERE created_at >= '2026-01-01'
  AND created_at <  '2026-02-01';
-- Correct for dates, timestamps, and fractional seconds, and it needs no
-- reasoning about "the last instant of the month".

-- ── WHAT NOT TO DO INSTEAD ──────────────────────────────────────────────
WHERE created_at <= '2026-01-31 23:59:59'
-- ✗ still loses 2026-01-31 23:59:59.5. Chasing precision is the wrong
--   approach; half-open ranges sidestep it entirely.

WHERE DATE(created_at) BETWEEN '2026-01-01' AND '2026-01-31'
-- ✗ correct results, but DATE() wraps the COLUMN so the index cannot be
--   used. On a large orders table this turns a range scan into a full
--   scan.

WHERE to_char(created_at, 'YYYY-MM') = '2026-01'
-- ✗ same problem, plus it is now a string comparison.

-- ── AND THE TIME ZONE QUESTION ──────────────────────────────────────────
-- If created_at is TIMESTAMPTZ (stored UTC) and "January" means January
-- in Sydney, the boundaries are NOT UTC midnight:
WHERE created_at >= '2026-01-01 00:00:00 Australia/Sydney'
  AND created_at <  '2026-02-01 00:00:00 Australia/Sydney'
-- Still sargable — the constants are resolved once, and the column is
-- untouched. Getting this wrong shifts every daily figure by a few
-- hours' worth of orders, which is invisible in aggregate and wrong in
-- every drill-down.
3 (medium): A search endpoint takes 4 seconds. Rewrite the predicates so indexes can be used.
Solution 
-- ✗ BEFORE — four separate reasons no index can be used
SELECT * FROM users
WHERE LOWER(email) = LOWER(:email)
   OR phone = :phone
  AND YEAR(created_at) = 2026
  AND status <> 'deleted';

-- PROBLEM 0: PRECEDENCE. AND binds tighter than OR, so this parses as
--   LOWER(email) = :email  OR  (phone = ... AND YEAR(...) AND status...)
-- The query does not mean what it looks like. Parenthesise every mixed
-- AND/OR — this is a correctness bug hiding inside a performance one.

-- PROBLEM 1: LOWER(email) — a function on the column.
CREATE INDEX ON users (LOWER(email));        -- an EXPRESSION index, or
ALTER TABLE users ALTER COLUMN email TYPE citext;   -- case-insensitive
                                                    -- type (Postgres)
WHERE email = :email                          -- ✓ now seekable

-- PROBLEM 2: YEAR(created_at) — same issue.
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'   -- ✓

-- PROBLEM 3: OR across two different columns. One index cannot serve
-- both, so the planner usually gives up and scans.
SELECT * FROM users
WHERE email = :email AND created_at >= ... AND status <> 'deleted'
UNION ALL
SELECT * FROM users
WHERE phone = :phone AND created_at >= ... AND status <> 'deleted'
  AND email IS DISTINCT FROM :email;      -- avoid double-counting
-- Each branch now uses its own index. (Postgres CAN do a BitmapOr for
-- some shapes — check EXPLAIN before assuming the union is needed.)

-- PROBLEM 4: status <> 'deleted' — an inequality matching most rows is
-- not selective, so it will not drive an index. Better as a PARTIAL
-- index, which also shrinks it:
CREATE INDEX ON users (email) WHERE status <> 'deleted';

-- ── AND THE ONE THAT IS NOT ABOUT INDEXES ───────────────────────────────
SELECT *                    -- forces a heap fetch for every matched row
SELECT id, name, email      -- ✓ can be served index-only if the index
                            --   covers these columns
-- Often the single biggest win, and the easiest to overlook.

-- ── VERIFY, DO NOT ASSUME ───────────────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
-- Look for: Seq Scan → Index Scan, and the gap between "rows=" estimated
-- and "actual rows=". A large gap means the planner is working from bad
-- statistics, and no rewrite fixes that — ANALYZE the table.
4 (medium): Paginating a feed shows duplicate and missing rows. Diagnose and fix.
Solution 
-- ✗ BEFORE
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 40;

-- TWO INDEPENDENT BUGS.

-- BUG 1: THE ORDER IS NOT TOTAL
-- Many posts share a created_at (bulk imports, same-second inserts).
-- Their relative order is UNDEFINED and can differ between the query for
-- page 2 and the query for page 3, so a row can appear on both or on
-- neither.
ORDER BY created_at DESC, id DESC           -- ✓ a unique tiebreaker makes
                                            --   the ordering total

-- BUG 2: OFFSET IS RELATIVE TO A MOVING TARGET
-- Between fetching page 2 and page 3, five new posts are inserted at the
-- top. Every row shifts down five positions, so OFFSET 40 now starts
-- five rows earlier — the user sees five rows they already saw.
-- Deletes cause the mirror image: rows are skipped entirely.

-- ✓ KEYSET PAGINATION — remember WHERE you were, not HOW MANY you skipped
-- page 1:
SELECT * FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- page N+1, passing the last row of page N:
SELECT * FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)   -- ROW comparison
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- The row-value syntax is exactly equivalent to
--   created_at < :c OR (created_at = :c AND id < :i)
-- and Postgres can use a composite index on (created_at DESC, id DESC)
-- for it directly.

CREATE INDEX ON posts (created_at DESC, id DESC);

-- ── WHY THIS ALSO FIXES THE SPEED ───────────────────────────────────────
--   OFFSET 100000 → the database produces 100,020 rows and discards
--                   100,000. Page 5000 is thousands of times slower than
--                   page 1.
--   Keyset        → seeks straight to the position in the index. Page
--                   5000 costs exactly what page 1 costs.

-- ── THE TRADE-OFF, STATED HONESTLY ──────────────────────────────────────
-- Keyset cannot jump to "page 47" — it only moves forward and backward
-- from a known row. For feeds, infinite scroll and exports that is not a
-- real requirement. For an admin table with numbered pages it is, and
-- there the pragmatic answer is to keep OFFSET but cap how deep it can
-- go, since nobody legitimately browses to page 5000.
5 (hard): Two analysts produce different revenue numbers from the same table. Find every possible cause.
Solution 
-- Analyst A: 1,240,332.00     Analyst B: 1,238,901.55

-- ── CAUSE 1: NULL EXCLUSION IN A FILTER ─────────────────────────────────
WHERE region <> 'internal'        -- A: drops rows where region IS NULL
WHERE region IS DISTINCT FROM 'internal'   -- B: keeps them
-- Any row with a NULL region silently disappears from A's total. This is
-- the most common cause and produces a small, plausible difference.

-- ── CAUSE 2: THE BETWEEN BOUNDARY ───────────────────────────────────────
WHERE created_at BETWEEN '2026-01-01' AND '2026-03-31'    -- loses day 90
WHERE created_at >= '2026-01-01' AND created_at < '2026-04-01'   -- ✓

-- ── CAUSE 3: TIME ZONE ──────────────────────────────────────────────────
-- created_at is TIMESTAMPTZ. A's client session is UTC, B's is
-- America/New_York, so "March 31" is a five-hour-different window. Every
-- daily figure is shifted; the quarter total differs by the orders in
-- those boundary hours.
SET TIME ZONE 'UTC';              -- pin it, in the query or the session
SELECT created_at AT TIME ZONE 'UTC' ...

-- ── CAUSE 4: A JOIN THAT FANS OUT ───────────────────────────────────────
SELECT sum(o.total)
FROM orders o JOIN order_items i ON i.order_id = o.id;
-- ✗ o.total is counted ONCE PER ITEM. An order with 3 items contributes
--   3x its value. The number is inflated and looks like a good quarter.
-- The tell: adding DISTINCT "fixes" it. That is a signal the join is
-- wrong, not that DISTINCT was missing.
SELECT sum(total) FROM orders WHERE EXISTS (
    SELECT 1 FROM order_items i WHERE i.order_id = orders.id);   -- ✓

-- ── CAUSE 5: FLOAT vs NUMERIC ───────────────────────────────────────────
-- If total is DOUBLE PRECISION, summing 400,000 rows accumulates
-- representation error, and the result depends on the ORDER of summation
-- — which parallel workers can change between runs. The same query gives
-- slightly different answers on the same data.
ALTER TABLE orders ALTER COLUMN total TYPE numeric(12,2);

-- ── CAUSE 6: STATUS SEMANTICS ───────────────────────────────────────────
-- A includes status='pending', B does not. Neither is wrong; nobody
-- wrote down what "revenue" means. Refunds, chargebacks, test tenants,
-- internal accounts and cancelled-but-shipped orders are all judgement
-- calls that live in a WHERE clause nobody can find later.

-- ── CAUSE 7: DIFFERENT SNAPSHOTS ────────────────────────────────────────
-- A ran at 09:00, B at 14:00, and the table is live. Or A queried a read
-- REPLICA with replication lag. Compare against a fixed cut:
WHERE created_at < '2026-04-01' AND ingested_at < '2026-04-02'

-- ── HOW TO ACTUALLY FIND IT ─────────────────────────────────────────────
-- Do not compare totals. Compare ROW SETS:
SELECT id FROM (A's query) EXCEPT SELECT id FROM (B's query);
SELECT id FROM (B's query) EXCEPT SELECT id FROM (A's query);
-- The rows that appear in one and not the other point straight at the
-- predicate that differs. Then look at those rows' columns and the cause
-- is usually obvious in seconds.

-- ── AND THE STRUCTURAL FIX ──────────────────────────────────────────────
CREATE VIEW recognised_revenue AS
SELECT ... -- the definition, in ONE place, reviewed once
-- Two analysts writing the same business rule independently will differ.
-- The problem is not their SQL; it is that the rule was never written
-- down as an artifact.
6 (hard): Design the query layer conventions for a team, and justify each rule.
Solution 
-- ── 1. BOUND PARAMETERS. NEVER STRING CONCATENATION ─────────────────────
cur.execute("SELECT * FROM users WHERE email = %s", (email,))
-- Not a style rule. The driver sends the value out of band, so it can
-- never be parsed as SQL. Concatenation is how databases get dropped,
-- and an ORM does not protect you the moment someone writes raw SQL for
-- one "quick" report.
-- Enforce with a linter rule banning f-strings and + near execute().

-- ── 2. NAME COLUMNS. NO SELECT * IN APPLICATION CODE ─────────────────────
-- Stops a new column leaking into every API response, allows index-only
-- scans, avoids duplicate column names on joins, and makes a schema
-- change a compile-time-ish failure rather than silent data drift.
-- SELECT * remains fine in a console.

-- ── 3. HALF-OPEN TIME RANGES, ALWAYS ────────────────────────────────────
WHERE t >= :start AND t < :end
-- BETWEEN on a timestamp loses the final day. This one rule removes an
-- entire recurring class of reporting bug.

-- ── 4. EVERY ORDER BY THAT FEEDS A LIMIT ENDS IN A UNIQUE COLUMN ─────────
ORDER BY created_at DESC, id DESC
-- Without a tiebreaker the order is undefined among equal keys, which
-- makes pagination show duplicates and skip rows. Cheap to add,
-- impossible to debug later.

-- ── 5. KEYSET PAGINATION FOR ANYTHING USER-FACING ───────────────────────
WHERE (created_at, id) < (:last_c, :last_id) ORDER BY ... LIMIT :n
-- Constant time at any depth and stable under concurrent inserts.
-- Numbered pages may keep OFFSET, but cap the maximum depth.

-- ── 6. NOT EXISTS INSTEAD OF NOT IN ─────────────────────────────────────
-- NOT IN against a nullable column returns zero rows, correctly, forever,
-- with no error. The failure is data-dependent so it passes review and
-- appears months later.

-- ── 7. NOT NULL BY DEFAULT; JUSTIFY EVERY NULLABLE COLUMN ───────────────
-- A nullable column is a branch every future query must remember, and
-- forgetting it loses rows silently rather than raising. If "absent" is
-- a real state, model it explicitly (a status enum) rather than as an
-- absence.

-- ── 8. NUMERIC FOR MONEY, TIMESTAMPTZ FOR TIME ──────────────────────────
-- FLOAT drift shows up as a one-cent reconciliation failure nobody can
-- trace. Naive TIMESTAMP is ambiguous across DST and means different
-- things to different readers. Both are unfixable-in-place once there is
-- data, so they must be right at CREATE TABLE time.

-- ── 9. BUSINESS RULES LIVE IN VIEWS, NOT IN EACH QUERY ──────────────────
CREATE VIEW active_users AS SELECT * FROM users WHERE deleted_at IS NULL;
-- Two people writing "active user" independently will disagree. One
-- reviewed definition beats fifteen copies drifting apart.

-- ── 10. EVERY DESTRUCTIVE STATEMENT IS A SELECT FIRST ───────────────────
BEGIN;
SELECT count(*) FROM users WHERE last_login < '2020-01-01';   -- inspect
DELETE FROM users WHERE last_login < '2020-01-01';             -- same WHERE
-- verify the row count, THEN
COMMIT;   -- or ROLLBACK
-- Also: require a WHERE clause on UPDATE/DELETE in review, and enable
-- the client's safe-update mode where available.

-- ── 11. EXPLAIN ANALYZE BEFORE CLAIMING SOMETHING IS FASTER ─────────────
-- Intuition about SQL performance is unreliable; the planner weighs
-- selectivity and statistics you cannot see. "It looks like it should
-- use the index" is not evidence.

-- ── 12. COMMENT THE WHY, NEVER THE WHAT ─────────────────────────────────
-- Exclude internal tenants: they inflate the funnel ~8% (TICKET-4412)
WHERE NOT t.is_internal
-- Business rules encoded only as a predicate are the ones nobody can
-- explain a year later, and therefore the ones nobody dares change.

-- ── WHAT I WOULD ENFORCE MECHANICALLY vs BY REVIEW ──────────────────────
-- Linter/CI: no string-built SQL, no SELECT * outside migrations, an
--            EXPLAIN check on new queries in the slow-query budget
-- Review:    time ranges, NULL semantics, join fan-out, ordering
-- Schema:    NOT NULL, NUMERIC, TIMESTAMPTZ enforced at CREATE TABLE —
--            the constraints you cannot add later without a migration
--            are the ones worth arguing about now.

🎯 Key Takeaways

  • SQL is declarative: you specify what, the planner decides how — so debug with EXPLAIN ANALYZE, not by re-reading the query.
  • Logical order is FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT, which explains every alias and aggregate rule.
  • NULL means unknown, so a condition and its negation are not exhaustive and rows vanish from both.
  • NOT IN against a nullable subquery returns zero rows — use NOT EXISTS.
  • Use half-open ranges for time; BETWEEN on a timestamp silently drops the last day.
  • LIMIT without a total ORDER BY returns arbitrary rows, and deep OFFSET is both slow and unstable — paginate by keyset.
  • A function or type mismatch on the column side of a predicate disables the index.
  • SELECT * leaks columns, blocks index-only scans, and breaks on schema change and on joins.
  • Money is NUMERIC and timestamps are TIMESTAMPTZ — both are painful to change once data exists.
  • Always bind parameters; string-built SQL is the injection vector, whatever the ORM elsewhere.
