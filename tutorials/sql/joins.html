JOINs Basics→Intermediate

What you'll master: the join types and why the Venn-diagram picture misleads once duplicates exist, ON versus WHERE on an outer join and the silent conversion to INNER, the anti-join pattern and its three formulations, fan-out — the reason totals triple and DISTINCT is the wrong fix, self-joins and LATERAL, the N+1 problem that ORMs generate invisibly, and how the planner actually executes a join so you can read what EXPLAIN tells you. Prerequisites: SELECT & Filtering and Sorting, Limiting & Aggregates.

Part 1 — The Join Types

SELECT u.name, o.total
FROM users u
JOIN orders o ON o.user_id = u.id;      -- INNER: rows matching on BOTH sides

-- ── THE MENTAL MODEL THAT ACTUALLY WORKS ────────────────────────────────
-- Conceptually a join takes every row on the left paired with every row
-- on the right, keeps the pairs where ON is TRUE, and then (for outer
-- joins) adds back the unmatched rows with NULLs on the other side.
--
-- The planner never literally does this — it hashes, sorts or loops
-- (Part 6) — but it is the only model that predicts the right ROW COUNT,
-- which is where the bugs are.
JoinReturnsTypical use
INNER JOINOnly rows matching on both sides"Users with orders"
LEFT JOINEvery left row; NULLs where the right has no match"All users, with their orders or none"
RIGHT JOINEvery right row; NULLs on the leftRare — flip the tables and use LEFT
FULL OUTER JOINEvery row from both sides, NULL-paddedReconciling two datasets
CROSS JOINEvery combination (Cartesian product)Generating grids; usually accidental
LATERAL / APPLYRight side re-evaluated per left rowTop-N per group, correlated subqueries
-- ── WHY THE VENN DIAGRAM IS A LIE ───────────────────────────────────────
-- The circles suggest a join picks a SUBSET of rows. It does not — it can
-- produce MORE rows than either table has.
--   users: 1 row.  orders: 3 rows for that user.
--   INNER JOIN → 3 ROWS. The "intersection" is bigger than the left side.
-- Venn diagrams describe SETS. Joins operate on MULTISETS, and every
-- serious join bug lives in that difference (Part 4).

-- ── EXPLICIT JOIN SYNTAX, ALWAYS ────────────────────────────────────────
SELECT * FROM users u, orders o WHERE o.user_id = u.id;   -- ✗ implicit
SELECT * FROM users u JOIN orders o ON o.user_id = u.id;  -- ✓ explicit
-- The comma form separates the join condition from the join, so dropping
-- a WHERE term turns it into a silent CROSS JOIN. It also cannot express
-- outer joins portably. Legacy code only.

-- ── USING AND NATURAL JOIN ──────────────────────────────────────────────
JOIN orders USING (user_id)        -- when both columns share a name;
                                   -- produces ONE merged column
NATURAL JOIN orders                -- ✗ joins on EVERY same-named column
-- NATURAL JOIN is a landmine: adding a `created_at` column to both tables
-- silently adds it to the join condition and the query starts returning
-- nothing. Never use it.

-- ── ALIAS EVERYTHING ────────────────────────────────────────────────────
SELECT u.id, u.name, o.id AS order_id, o.total
FROM users u JOIN orders o ON o.user_id = u.id;
-- With SELECT * you get two columns called `id` and the driver picks one
-- arbitrarily. Short, consistent aliases also make a 5-table join
-- readable, which is the actual reason.

Part 2 — ON versus WHERE

-- ── THE MOST COMMON OUTER-JOIN BUG ──────────────────────────────────────
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 'paid';            -- ✗ this is now an INNER JOIN

-- WHY: the LEFT JOIN produces a row for every user, with NULL columns
-- where there was no order. WHERE runs AFTER the join, and
-- `NULL = 'paid'` is UNKNOWN, not TRUE — so every unmatched user is
-- filtered out. The LEFT JOIN did its job and WHERE undid it.

-- ✓ Filter the right table in ON — applied DURING the join, before the
--   NULL-padding happens:
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'paid';
-- Every user appears. Users with no paid order have NULL for o.total.

-- ── THE RULE ────────────────────────────────────────────────────────────
--   ON    = which rows PAIR UP        (part of the join)
--   WHERE = which resulting rows SURVIVE (after the join)
--
-- On an INNER JOIN the two are interchangeable — the planner will move
-- conditions between them freely, and the answer is identical.
-- On an OUTER JOIN they mean completely different things.
--
-- If you ever see a LEFT JOIN with a WHERE condition on the right table,
-- either it is a bug, or it is a deliberate anti-join (Part 3) and
-- deserves a comment saying so.

-- ── THE LEGITIMATE EXCEPTION ────────────────────────────────────────────
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;                 -- ✓ INTENTIONAL: the anti-join
-- The only right-table WHERE condition that preserves the LEFT semantics
-- is IS NULL, because that is precisely the unmatched rows.

-- ── THE SAME TRAP WITH COUNT ────────────────────────────────────────────
SELECT u.id, count(*) AS orders                       -- ✗ counts ROWS, so
FROM users u LEFT JOIN orders o ON o.user_id = u.id   --   a user with no
GROUP BY u.id;                                        --   orders gets 1

SELECT u.id, count(o.id) AS orders                    -- ✓ counts non-NULL
FROM users u LEFT JOIN orders o ON o.user_id = u.id   --   order ids, so
GROUP BY u.id;                                        --   no orders → 0
-- count(*) counts the padded row; count(right.column) does not. Any
-- LEFT JOIN feeding an aggregate needs this care.

-- ── AND WITH sum ────────────────────────────────────────────────────────
COALESCE(sum(o.total), 0)     -- sum over only-NULLs is NULL, not 0

Part 3 — Anti-Joins and Semi-Joins

-- ── SEMI-JOIN: "left rows that HAVE a match" — without duplicating ──────
SELECT u.* FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
-- Returns each user ONCE, however many orders they have. A plain
-- INNER JOIN would return one row per order — the fan-out of Part 4.
-- Use EXISTS whenever the right table is a FILTER, not a data source.

-- ── ANTI-JOIN: "left rows with NO match" — three formulations ───────────

-- 1. NOT EXISTS  ✓ the default choice
SELECT u.* FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
--    NULL-safe, short-circuits on the first match, and the planner
--    recognises it as an anti-join.

-- 2. LEFT JOIN ... IS NULL  ✓ equivalent, sometimes clearer
SELECT u.* FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
--    Must test a column that is NOT NULL in the right table (its primary
--    key). Testing a nullable column also matches rows that DID join but
--    happen to have a NULL there — a real and easily-missed bug.

-- 3. NOT IN  ✗ dangerous
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);
--    Returns ZERO ROWS if ANY orders.user_id is NULL, because
--    `id <> NULL` is UNKNOWN and the AND chain can never be TRUE.
--    Works for months, then silently returns nothing the day one NULL
--    appears. Only safe when the column is provably NOT NULL.

-- ── WHAT THESE ARE FOR ──────────────────────────────────────────────────
-- users who never ordered · products never sold · accounts with no
-- subscription · orders with no shipment · reconciliation between two
-- systems ("what is in A but not B?")

-- ── FULL OUTER JOIN FOR RECONCILIATION ──────────────────────────────────
SELECT COALESCE(a.id, b.id) AS id,
       a.amount AS ours, b.amount AS theirs,
       CASE WHEN a.id IS NULL THEN 'missing_locally'
            WHEN b.id IS NULL THEN 'missing_remotely'
            WHEN a.amount <> b.amount THEN 'mismatch'
            ELSE 'ok' END AS status
FROM our_ledger a
FULL OUTER JOIN their_ledger b ON b.id = a.id
WHERE a.id IS NULL OR b.id IS NULL OR a.amount IS DISTINCT FROM b.amount;
-- IS DISTINCT FROM, not <>, so a NULL amount on one side is reported as
-- a mismatch rather than silently passing. This query shape is the
-- backbone of every reconciliation job.

-- ── SET OPERATORS DO THIS TOO ───────────────────────────────────────────
SELECT id FROM a EXCEPT SELECT id FROM b;      -- in a, not in b
SELECT id FROM a INTERSECT SELECT id FROM b;
SELECT id FROM a UNION ALL SELECT id FROM b;   -- keeps duplicates, FAST
SELECT id FROM a UNION SELECT id FROM b;       -- deduplicates: a SORT
-- UNION ALL unless you actually need deduplication. UNION on a large
-- result adds a full sort or hash for nothing.
Key insight: a join does not select rows, it multiplies them. Joining a one-row parent to three children produces three rows, and joining that to two payments produces six — so any sum of a parent column is now six times too large. This is why the Venn diagram, which describes sets, is the wrong picture for an operation on multisets, and why the single most useful habit in join work is to check count(*) against count(DISTINCT parent_id) before trusting any total. When those two numbers differ, the query is fanning out, and DISTINCT suppresses the symptom while leaving the arithmetic wrong.

Part 4 — Fan-Out

-- ── THE BUG ─────────────────────────────────────────────────────────────
SELECT sum(o.total) AS revenue
FROM orders o
JOIN order_items i ON i.order_id = o.id;
-- An order with 3 items appears in 3 rows, so o.total is added 3 times.
-- Revenue is inflated by the average item count. It looks like a good
-- quarter.

-- ── IT COMPOUNDS ────────────────────────────────────────────────────────
SELECT u.id, sum(o.total), sum(p.amount)
FROM users u
JOIN orders   o ON o.user_id = u.id      -- 3 orders
JOIN payments p ON p.user_id = u.id;     -- 2 payments
-- → 3 × 2 = 6 rows per user.
--   sum(o.total)  is 2x too high (each order seen twice)
--   sum(p.amount) is 3x too high (each payment seen three times)
-- Two independent one-to-many joins produce a CROSS PRODUCT of the
-- children. Both totals are wrong, by different factors.

-- ── WHY DISTINCT IS NOT THE FIX ─────────────────────────────────────────
SELECT sum(DISTINCT o.total) ...     -- ✗ two orders that both cost
                                     --   49.99 now count ONCE
SELECT count(DISTINCT o.id) ...      -- ✓ this one IS correct — ids are
                                     --   unique, so dedup is meaningful
-- DISTINCT on a MEASURE is almost always wrong; DISTINCT on an ID is
-- fine. If adding DISTINCT changes a total, treat it as evidence the
-- join is wrong rather than as a fix.

-- ── FIX 1: AGGREGATE BEFORE JOINING (the general answer) ────────────────
SELECT u.id, o.revenue, p.paid
FROM users u
LEFT JOIN (SELECT user_id, sum(total)  AS revenue
           FROM orders   GROUP BY user_id) o ON o.user_id = u.id
LEFT JOIN (SELECT user_id, sum(amount) AS paid
           FROM payments GROUP BY user_id) p ON p.user_id = u.id;
-- Each subquery yields ONE row per user, so no multiplication is
-- possible. This is usually faster too: the aggregation happens on the
-- smaller intermediate result rather than on the join's output.

-- ── FIX 2: EXISTS, WHEN THE CHILD IS ONLY A FILTER ──────────────────────
SELECT sum(total) FROM orders o
WHERE EXISTS (SELECT 1 FROM order_items i WHERE i.order_id = o.id);
-- "Revenue from orders that have items." No duplication because EXISTS
-- does not produce rows.

-- ── FIX 3: A CORRELATED SCALAR SUBQUERY ─────────────────────────────────
SELECT u.id,
       (SELECT sum(total)  FROM orders   WHERE user_id = u.id) AS revenue,
       (SELECT sum(amount) FROM payments WHERE user_id = u.id) AS paid
FROM users u;
-- Readable, and modern planners often rewrite it into Fix 1. Verify with
-- EXPLAIN on a large table rather than assuming.

-- ── DETECTING IT ────────────────────────────────────────────────────────
SELECT count(*) AS rows, count(DISTINCT o.id) AS orders, sum(o.total)
FROM orders o JOIN order_items i ON i.order_id = o.id;
--   rows = 15,000   orders = 5,000   ← the join tripled the rows, so the
--                                      sum is 3x too high
-- Put count(*) beside every sum() while developing. An inflated total is
-- invisible; an inflated row count is not.

Part 5 — Self-Joins, LATERAL, and N+1

-- ── SELF-JOIN: A TABLE RELATED TO ITSELF ────────────────────────────────
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;      -- LEFT keeps the CEO
-- Aliases are mandatory here — they are what make the two roles distinct.

-- Finding duplicates:
SELECT a.id, b.id, a.email
FROM users a JOIN users b ON b.email = a.email AND b.id > a.id;
-- `b.id > a.id` gives each pair ONCE rather than twice, and stops rows
-- matching themselves.

-- ── LATERAL: THE RIGHT SIDE SEES THE LEFT ROW ───────────────────────────
SELECT u.name, r.*
FROM users u
CROSS JOIN LATERAL (
  SELECT * FROM orders o
  WHERE o.user_id = u.id                 -- ← references the outer row
  ORDER BY o.created_at DESC LIMIT 3     --   which a plain join cannot do
) r;
-- "The 3 most recent orders per user." With an index on
-- (user_id, created_at DESC) this reads 3 rows per user instead of
-- ranking every order in the table — much faster than a window function
-- when there are many children per parent.
-- LEFT JOIN LATERAL (...) ON true      keeps users with no orders.
-- (SQL Server spells this CROSS APPLY / OUTER APPLY.)

-- ── THE N+1 PROBLEM ─────────────────────────────────────────────────────
users = db.query("SELECT * FROM users LIMIT 100")     -- 1 query
for u in users:
    u.orders = db.query("SELECT * FROM orders WHERE user_id = %s", u.id)
                                                       -- 100 more
-- 101 round trips. Each is 1ms of query and 2ms of network, so a page
-- that should take 5ms takes 300ms — and the database sees 101x the
-- connections it needed.
--
-- It is almost always an ORM doing it silently: accessing `user.orders`
-- inside a loop triggers a lazy load per user. Nothing in the code looks
-- like a query.

-- ── FIX A: ONE JOIN ─────────────────────────────────────────────────────
SELECT u.*, o.* FROM users u LEFT JOIN orders o ON o.user_id = u.id
WHERE u.id IN (...);
-- ⚠ transfers each user's columns once per order. With wide parent rows
--   and many children that can be more bytes than the N+1 version.

-- ── FIX B: TWO QUERIES, BATCHED (usually best) ──────────────────────────
users  = db.query("SELECT * FROM users LIMIT 100")
orders = db.query("SELECT * FROM orders WHERE user_id = ANY(%s)", [ids])
-- then group in memory. 2 round trips, no duplicated parent data. This
-- is what a good ORM's eager loading and what DataLoader both do.

-- ── FIX C: AGGREGATE INTO JSON ──────────────────────────────────────────
SELECT u.*, COALESCE(json_agg(o.*) FILTER (WHERE o.id IS NOT NULL), '[]')
FROM users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id;
-- One query, one row per user, children nested. The FILTER is needed or
-- users with no orders get [null].

-- ── DETECTING IT ────────────────────────────────────────────────────────
-- Log SQL in development and count statements per request. The signature
-- is the same query repeated with a different parameter. Assert on the
-- query count in tests for hot endpoints — it is the only way it stays
-- fixed after someone adds an innocent-looking attribute access.

Part 6 — How Joins Execute

-- The planner picks one of three algorithms. Reading EXPLAIN means
-- knowing which one you got and why.

-- ── NESTED LOOP ─────────────────────────────────────────────────────────
-- For each outer row, look up matches in the inner table.
-- Cost ≈ outer_rows × cost_of_one_inner_lookup
-- ✓ Great when the outer side is SMALL and the inner side has an index.
-- ✗ Catastrophic when the outer side is large or the index is missing —
--   this is the classic "fast in dev, 40 seconds in production" plan,
--   because the planner estimated 5 outer rows and got 500,000.

-- ── HASH JOIN ───────────────────────────────────────────────────────────
-- Build a hash table on the smaller side, then scan the larger side.
-- ✓ The workhorse for large, unsorted, equality joins.
-- ✗ Equality only, and the hash table must fit in work_mem or it spills
--   to disk in batches — often several times slower.

-- ── MERGE JOIN ──────────────────────────────────────────────────────────
-- Sort both sides, then walk them in step.
-- ✓ Good when both inputs are already sorted (an index scan in the join
--   order), and it handles range conditions.
-- ✗ Otherwise you pay for two sorts.

EXPLAIN (ANALYZE, BUFFERS)
SELECT ... FROM users u JOIN orders o ON o.user_id = u.id;
--  Hash Join  (cost=... rows=5000 width=...) (actual rows=1500000 ...)
--                       ^^^^^^^^^             ^^^^^^^^^^^^^^^^^^
-- THE MOST IMPORTANT THING IN THE OUTPUT: estimated vs actual rows.
-- A 300x gap means every decision above this node was made on bad
-- information. Causes: stale statistics (run ANALYZE), correlated
-- columns the planner assumes are independent, or a function it cannot
-- estimate through.

-- ── WHAT ACTUALLY MAKES JOINS FAST ──────────────────────────────────────
-- 1. INDEX THE FOREIGN KEY. Postgres does NOT create one automatically
--    for an FK constraint — only for the primary key.
CREATE INDEX ON orders (user_id);
--    Without it, every join and every ON DELETE CASCADE scans the child
--    table. This is the single most common missing index in real schemas.

-- 2. MATCH THE TYPES. Joining bigint to int, or text to varchar with a
--    different collation, can prevent index use entirely.

-- 3. FILTER EARLY. A WHERE on the large table shrinks the join input.
--    The planner usually pushes this down, but it cannot see through
--    some subqueries and volatile functions.

-- 4. SELECT FEWER COLUMNS. Wide rows mean bigger hash tables, more spill
--    to disk, more bytes over the wire.

-- ── JOIN ORDER IS THE PLANNER'S JOB ─────────────────────────────────────
-- Written order does not determine execution order; the planner
-- reorders inner joins freely by cost. Past ~8 tables (join_collapse_limit)
-- it stops exhaustive search and uses a heuristic — one reason very wide
-- joins get unpredictable plans, and an argument for splitting a
-- 15-table report into CTEs or a rollup table.
--
-- OUTER joins constrain the order: a LEFT JOIN cannot generally be
-- reordered without changing the result, which is why converting an
-- unnecessary LEFT JOIN to INNER sometimes produces a dramatically
-- better plan.

Interview Questions

Beginner: What is the difference between INNER and LEFT JOIN, and how do you find rows with no match?

INNER JOIN returns only the pairs where the ON condition matched, so a left row with no counterpart disappears entirely. LEFT JOIN keeps every left row and pads the right-hand columns with NULL when nothing matched. So "users with orders" is an inner join, and "all users, with their orders where they exist" is a left join.

Finding rows without a match is called an anti-join, and the classic formulation is a LEFT JOIN followed by WHERE right.id IS NULL — the unmatched rows are exactly the ones whose right-hand columns are NULL. The detail that matters is testing a column that is NOT NULL in the right table, normally its primary key: testing a nullable column also matches rows that did join but happen to have a NULL there. NOT EXISTS expresses the same thing more directly and is what I would usually write, and NOT IN is the formulation to avoid because a single NULL in the subquery makes it return nothing at all.

Beginner: Why does a WHERE condition on the right table break a LEFT JOIN?

Because of ordering. The join runs first and produces a row for every left row, with NULLs in the right-hand columns where there was no match. WHERE then runs on that result, and a condition like o.status = 'paid' evaluates to UNKNOWN against those NULLs rather than TRUE — so every unmatched row is filtered out and the query behaves exactly like an INNER JOIN. The join did what you asked and the WHERE undid it.

The fix is to move the condition into the ON clause, where it participates in deciding which rows pair up, before any NULL padding happens. The general rule is that ON controls which rows match and WHERE controls which resulting rows survive; on an inner join the two are interchangeable and the planner moves conditions between them freely, but on an outer join they mean different things. The one legitimate right-table WHERE condition is IS NULL, which is the anti-join — and because it looks identical to the bug, it is worth a comment.

Mid: A report's revenue total is three times too high after adding a join. Explain.

The join is fanning out. Joining orders to order_items produces one row per item, so summing orders.total adds each order's value once per item — an order with three items contributes three times. The inflation factor is the average number of children, which is why the number is wrong by a suspiciously consistent multiple rather than randomly.

It gets worse with two independent one-to-many joins in the same query. Joining users to both orders and payments gives the cross product of the children, so with three orders and two payments you get six rows per user, and the order total is doubled while the payment total is tripled — two wrong numbers, wrong by different factors, in one query.

The reliable fix is to aggregate each child table in its own subquery and join those one-row-per- parent results, which is usually faster as well as correct because the aggregation happens on a smaller intermediate set. When the child table is only there as a filter, EXISTS avoids producing rows at all. What I would not do is add DISTINCT: it appears to fix the total and silently breaks whenever two children legitimately share a value, and its only correct use here is count(DISTINCT id), where the deduplication is meaningful because ids are unique. The diagnostic habit is putting count(*) and count(DISTINCT parent_id) beside every sum — an inflated total is invisible, an inflated row count is not.

Mid: What is the N+1 query problem, and how do you fix it?

Fetching a list with one query and then issuing one more query per item to load related data — a hundred users becomes a hundred and one round trips. Each individual query is fast, so nothing looks slow in the database's slow-query log; the cost is entirely in the round trips and the connection churn, which turns a five-millisecond page into three hundred milliseconds and multiplies the connection count under load.

It is almost always an ORM doing it invisibly. Accessing user.orders inside a loop triggers a lazy load, and nothing at that line of code looks like a query, which is why it survives review and appears in production.

There are three fixes. A single join returns everything at once but repeats each parent's columns per child, so with wide parent rows and many children it can move more bytes than the N+1 version did. Two batched queries — fetch the parents, then fetch all children with WHERE user_id = ANY(ids) and group in memory — is usually the best shape, and is exactly what good eager loading and DataLoader implement. Aggregating children into JSON with json_agg gives one row per parent with the children nested, which suits API responses well. For detection, log statements per request in development and look for the same query repeated with different parameters; for prevention, assert on the query count in tests for hot endpoints, because otherwise it reappears the next time someone adds an innocuous attribute access.

Senior: How does a database actually execute a join, and why does that matter?

There are three algorithms and the planner picks by estimated cost. A nested loop iterates the outer side and looks up matches in the inner side, so its cost is the outer row count times the cost of one lookup — excellent when the outer side is small and the inner side is indexed, and catastrophic otherwise. A hash join builds a hash table on the smaller input and probes it with the larger one, which is the workhorse for big equality joins but requires the hash table to fit in working memory or it spills to disk in batches. A merge join sorts both inputs and walks them together, which is cheap when the inputs already arrive sorted from index scans and expensive when it has to sort them.

This matters because the most common production join failure is a nested loop chosen on a bad estimate. The planner expects five outer rows, gets five hundred thousand, and performs half a million index lookups — a query that was instant in development and takes forty seconds against real data. That is why the first thing I look at in EXPLAIN ANALYZE is the gap between estimated and actual rows rather than the total time: a large gap means every decision above that node was made on wrong information, and the fix is usually statistics or a correlation the planner cannot see, not a rewrite.

The practical levers follow from the algorithms. Index the foreign key — Postgres creates an index for a primary key but not for a foreign key constraint, so the child side of most joins is unindexed unless someone did it deliberately, and that also makes every ON DELETE CASCADE a table scan. Match the column types, since joining a bigint to an int or text with mismatched collation can disable the index. Select fewer columns, because wide rows make hash tables spill. And be aware that the planner reorders inner joins freely but is constrained by outer joins, which is why converting an unnecessary LEFT JOIN to INNER sometimes unlocks a much better plan.

Senior: When would you deliberately avoid a join?

Several situations, and they are all about the join being the wrong shape rather than joins being slow. The clearest is fetching a parent with many children for an API response: a join returns the parent's columns repeated once per child, so for wide parents that is genuinely more bytes than two batched queries, and the application has to deduplicate afterwards anyway. Two queries or a json_agg is both cheaper and simpler.

Second, when the second table is only a filter. EXISTS expresses "has at least one match" without producing rows, so it avoids fan-out entirely and lets the planner stop at the first match instead of materialising every child. Any time a join is followed by DISTINCT, the join was probably meant to be a semi-join.

Third, across service or database boundaries. Once the data lives in different systems there is no join to write, and the answer is either denormalising the field you keep needing, maintaining a read model, or accepting an application-side batched lookup. Trying to preserve a relational join across a network is how people end up with a distributed query engine they did not plan for.

Fourth, very wide reporting joins. Past roughly eight tables the planner stops exhaustively searching join orders and falls back to a heuristic, so plans become unstable and a small data change flips the query from seconds to minutes. Splitting into CTEs with materialisation, or maintaining a rollup table for the parts that do not change, trades a little redundancy for predictability — and in reporting, predictable is worth more than optimal.

What I would not do is avoid joins on principle. Denormalising to escape a join means every write now has to maintain consistency across copies, and that trade is only worth making when you have measured the join and understood why it is the constraint.

🏋️ Exercises

1 (easy): This query should list all users with their paid orders, but users without one are missing.
Solution 
-- ✗ BEFORE
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 'paid';

-- The LEFT JOIN produced a row for every user, with NULLs where there
-- was no order. Then WHERE ran on that result, and NULL = 'paid' is
-- UNKNOWN — not TRUE — so every unmatched user was filtered out.
-- The LEFT JOIN worked and the WHERE undid it. This is now an INNER JOIN
-- with extra syntax.

-- ✓ AFTER — the condition belongs to the JOIN, not to the result
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'paid';
-- Every user appears; those with no paid order have NULL for o.total.

-- ── THE RULE ────────────────────────────────────────────────────────────
--   ON    → which rows PAIR UP        (before NULL-padding)
--   WHERE → which rows SURVIVE        (after NULL-padding)
-- Interchangeable on an INNER JOIN. Completely different on an OUTER one.

-- ── THE SAME BUG, IN AN AGGREGATE ───────────────────────────────────────
SELECT u.name, count(*) AS paid_orders                    -- ✗ a user with
FROM users u                                              --   none gets 1
LEFT JOIN orders o ON o.user_id = u.id AND o.status='paid'
GROUP BY u.id, u.name;

SELECT u.name,
       count(o.id) AS paid_orders,                        -- ✓ 0
       COALESCE(sum(o.total), 0) AS revenue               -- ✓ 0, not NULL
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status='paid'
GROUP BY u.id, u.name;
-- count(*) counts the padded ROW. count(o.id) counts non-NULL ids.
-- sum() over only-NULLs is NULL, so COALESCE it.

-- ── THE ONE RIGHT-TABLE `WHERE` THAT IS CORRECT ─────────────────────────
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;         -- ✓ deliberate ANTI-JOIN: users who never
                            --   ordered. Looks like the bug — comment it.
2 (easy): Write three ways to find users who have never ordered, and rank them.
Solution 
-- ── 1. NOT EXISTS  ✓ what I would ship ──────────────────────────────────
SELECT u.* FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
-- NULL-safe. Short-circuits at the first match rather than finding all
-- of them. The planner recognises the shape and produces a true
-- anti-join. Reads as the English sentence.

-- ── 2. LEFT JOIN ... IS NULL  ✓ equivalent ──────────────────────────────
SELECT u.* FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
-- Same plan in Postgres. Two cautions:
--   * test the right table's PRIMARY KEY. Testing a nullable column
--     (o.cancelled_at IS NULL) also matches rows that DID join and just
--     happen to be NULL there — a silent, common bug.
--   * it produces the join first, so on some engines it materialises
--     more rows before discarding them.

-- ── 3. NOT IN  ✗ do not use ─────────────────────────────────────────────
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);
-- If ANY orders.user_id is NULL, this returns ZERO ROWS. Forever.
--   id NOT IN (1, 2, NULL)
--     → id <> 1 AND id <> 2 AND id <> NULL
--     → the last term is UNKNOWN, so the AND can never be TRUE.
-- No error. It works for months and breaks the day one NULL arrives —
-- long after whoever wrote it has moved on. Only safe when the column
-- is provably NOT NULL, and "provably" means a constraint, not a habit.

-- ── PROVE IT ────────────────────────────────────────────────────────────
INSERT INTO orders (user_id) VALUES (NULL);
-- run all three again: 1 and 2 unchanged, 3 now returns nothing.

-- ── THE RELATED SHAPE: SEMI-JOIN ────────────────────────────────────────
SELECT u.* FROM users u JOIN orders o ON o.user_id = u.id;   -- ✗ one row
                                                             --   PER ORDER
SELECT u.* FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);-- ✓ one row
                                                             --   per user
-- Use EXISTS whenever the second table is a FILTER rather than a source
-- of columns. It sidesteps fan-out completely.
3 (medium): Two totals in one report are both wrong, by different amounts. Diagnose and fix.
Solution 
-- ✗ BEFORE
SELECT u.id, u.name,
       sum(o.total)  AS lifetime_value,
       sum(p.amount) AS total_paid
FROM users u
JOIN orders   o ON o.user_id = u.id
JOIN payments p ON p.user_id = u.id
GROUP BY u.id, u.name;

-- ── WHY BOTH ARE WRONG, DIFFERENTLY ─────────────────────────────────────
-- A user with 3 orders and 2 payments produces 3 × 2 = 6 rows. Two
-- independent one-to-many joins give the CROSS PRODUCT of the children.
--   each order   appears in 2 rows → lifetime_value is 2x too high
--   each payment appears in 3 rows → total_paid     is 3x too high
-- The multipliers differ per user, so the error is not even a constant
-- factor you could spot in a ratio.

-- ── PROVE IT FIRST ──────────────────────────────────────────────────────
SELECT count(*) AS rows,
       count(DISTINCT o.id) AS orders,
       count(DISTINCT p.id) AS payments
FROM users u JOIN orders o ON ... JOIN payments p ON ...
WHERE u.id = 42;
--   rows = 6 | orders = 3 | payments = 2
-- rows > orders means the query fans out. Always check this before
-- trusting a total.

-- ── ✓ FIX: AGGREGATE EACH SIDE FIRST ────────────────────────────────────
SELECT u.id, u.name,
       COALESCE(o.lifetime_value, 0) AS lifetime_value,
       COALESCE(p.total_paid, 0)     AS total_paid
FROM users u
LEFT JOIN (SELECT user_id, sum(total)  AS lifetime_value
           FROM orders   GROUP BY user_id) o ON o.user_id = u.id
LEFT JOIN (SELECT user_id, sum(amount) AS total_paid
           FROM payments GROUP BY user_id) p ON p.user_id = u.id;
-- Each subquery returns ONE row per user, so multiplication is
-- impossible. LEFT JOIN + COALESCE keeps users with neither.
-- Usually FASTER too: aggregation runs on the smaller inputs rather than
-- on the join's inflated output.

-- ── ALTERNATIVE: CORRELATED SCALAR SUBQUERIES ───────────────────────────
SELECT u.id, u.name,
       (SELECT COALESCE(sum(total),0)  FROM orders   WHERE user_id=u.id),
       (SELECT COALESCE(sum(amount),0) FROM payments WHERE user_id=u.id)
FROM users u;
-- More readable; modern planners often rewrite it into the form above.
-- Verify with EXPLAIN on a large table rather than assuming.

-- ── WHY DISTINCT IS NOT A FIX ───────────────────────────────────────────
sum(DISTINCT o.total)     -- ✗ two orders that both cost 49.99 now count
                          --   ONCE. Wrong in a new way.
count(DISTINCT o.id)      -- ✓ correct — ids are unique, so dedup is
                          --   meaningful
-- If adding DISTINCT changes a total, that is EVIDENCE the join is
-- wrong, not a fix for it.
4 (medium): An endpoint issues 200 queries per request. Find and fix it three ways.
Solution 
# ✗ BEFORE — and nothing here LOOKS like a query
users = User.objects.all()[:100]              # 1 query
for u in users:
    print(u.name, u.profile.city, len(u.orders))   # 2 MORE, per user
# 201 round trips. Each query is 1ms and each round trip is 2ms, so a
# page that should take 5ms takes ~600ms — and the connection pool sees
# 201x the traffic it needed.
#
# The database's slow-query log shows NOTHING: every individual query is
# fast. That is what makes N+1 hard to find from the server side.

# ── DETECT IT ───────────────────────────────────────────────────────────
# Log SQL in development and count statements per request. The signature
# is the same statement repeated with a different parameter:
#   SELECT * FROM orders WHERE user_id = 1
#   SELECT * FROM orders WHERE user_id = 2   ... × 100
django.db.connection.queries        # or SQLAlchemy echo, or py-spy

# ── FIX A: ONE JOIN ─────────────────────────────────────────────────────
SELECT u.id, u.name, p.city, o.id AS order_id, o.total
FROM users u
LEFT JOIN profiles p ON p.user_id = u.id
LEFT JOIN orders   o ON o.user_id = u.id
WHERE u.id = ANY(:ids);
# 1 round trip. But u.name and p.city are REPEATED once per order. With
# a wide parent row and 50 orders each, this can move more bytes than
# the N+1 version did — and the app must still regroup the rows.

# ── FIX B: BATCHED QUERIES  ← usually the best shape ────────────────────
users    = db.query("SELECT * FROM users LIMIT 100")
ids      = [u.id for u in users]
profiles = db.query("SELECT * FROM profiles WHERE user_id = ANY(%s)",[ids])
orders   = db.query("SELECT * FROM orders   WHERE user_id = ANY(%s)",[ids])
# then group in memory by user_id
# 3 round trips regardless of user count. No duplicated parent data.
# This is exactly what a good ORM's eager loading does:
User.objects.select_related("profile").prefetch_related("orders")[:100]
#   select_related   → a JOIN     (for to-one)
#   prefetch_related → a 2nd query (for to-many) — the right default

# ── FIX C: AGGREGATE INTO JSON ──────────────────────────────────────────
SELECT u.*, p.city,
       COALESCE(json_agg(o.*) FILTER (WHERE o.id IS NOT NULL), '[]') AS orders
FROM users u
LEFT JOIN profiles p ON p.user_id = u.id
LEFT JOIN orders   o ON o.user_id = u.id
GROUP BY u.id, p.city;
# One query, one row per user, children nested — a good match for an API
# response. The FILTER is REQUIRED: without it, users with no orders get
# [null] instead of [].

# ── AND THE COUNT-ONLY CASE ─────────────────────────────────────────────
len(u.orders)        # ✗ loads every order row to count them

5 (hard): A join is instant in staging and takes 40 seconds in production. Diagnose.
Solution 
SELECT o.*, u.name
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.created_at >= now() - interval '1 day'
  AND o.status = 'pending';

-- ── STEP 1: GET THE REAL PLAN, NOT THE ESTIMATE ─────────────────────────
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
--  Nested Loop  (cost=... rows=12 ...) (actual rows=480000 loops=1)
--                             ^^^^^^^              ^^^^^^^^^^^^
-- THE ANSWER IS IN THAT GAP. The planner expected 12 outer rows and got
-- 480,000, so it chose a nested loop — 480,000 index lookups instead of
-- one hash join. In staging there really WERE 12 rows, so the same plan
-- was correct there.
--
-- A nested loop chosen on a bad estimate is the single most common
-- "fast in dev, catastrophic in prod" failure.

-- ── STEP 2: WHY WAS THE ESTIMATE WRONG? ─────────────────────────────────

-- a) STALE STATISTICS — the table grew 1000x since the last ANALYZE
ANALYZE orders;
SELECT last_analyze, last_autoanalyze, n_live_tup
FROM pg_stat_user_tables WHERE relname = 'orders';
-- Bulk loads and a too-high autovacuum_analyze_scale_factor on a large
-- table are the usual causes.

-- b) CORRELATED COLUMNS — the planner assumes independence
--    P(status='pending') = 0.02 and P(created_at >= yesterday) = 0.001
--    → it estimates 0.00002 of the table. But pending orders are almost
--      ALL recent, so the real fraction is ~0.02. Off by 1000x.
CREATE STATISTICS orders_corr (dependencies)
  ON status, created_at FROM orders;       -- Postgres 10+ extended stats
ANALYZE orders;

-- c) now() is STABLE, not immutable, so range estimates on a moving
--    boundary are weaker than on a literal.

-- ── STEP 3: THE INDEXES ─────────────────────────────────────────────────
CREATE INDEX ON orders (status, created_at DESC);   -- drives the WHERE
CREATE INDEX ON orders (user_id);                   -- drives the JOIN
-- ⚠ Postgres creates an index for a PRIMARY KEY but NOT for a FOREIGN
--   KEY constraint. The child side of most joins is unindexed unless
--   someone did it deliberately — the most common missing index in real
--   schemas, and it also makes every ON DELETE CASCADE a full scan.

-- Check for a type mismatch, which silently disables the index:
\d orders     -- user_id bigint?
\d users      -- id integer?     ← join cannot use the index

-- ── STEP 4: OTHER PRODUCTION-ONLY DIFFERENCES ───────────────────────────
-- work_mem too small → the hash table SPILLS to disk in batches. Look
--   for "Batches: 8  Memory Usage: ..." in the plan; batches > 1 means
--   spilling, often several times slower.
-- BLOATED table → "Buffers: shared read=..." far larger than the live
--   row count suggests. Dead tuples from heavy updates; check
--   n_dead_tup and vacuum.
-- A read REPLICA with different settings or a cold cache.
-- CONCURRENCY: 200 sessions each getting work_mem is a memory problem
--   staging never reproduces.

-- ── WHY STAGING WAS MISLEADING ──────────────────────────────────────────
--   data volume    thousands vs hundreds of millions → different plan
--   distribution   staging fixtures are uniform; production is skewed
--   statistics     freshly loaded and ANALYZEd vs months of drift
--   concurrency    one query vs hundreds competing for memory and I/O
-- Staging proves the query is CORRECT. It cannot prove it is FAST.

-- ── THE ORDER I WOULD WORK IN ───────────────────────────────────────────
-- 1. ANALYZE — free, and fixes it outright surprisingly often
-- 2. Add the missing FK index
-- 3. Extended statistics for the correlated predicates
-- 4. Only then consider rewriting the query
6 (hard): Design the read path for an order-history page with per-order items, payments and shipping.
Solution 
-- REQUIREMENT: 20 orders per page; each with its items (0-50), payments
-- (0-3), a shipment (0-1), and a per-order total.

-- ── ✗ ATTEMPT 1: ONE BIG JOIN ───────────────────────────────────────────
SELECT o.*, i.*, p.*, s.*
FROM orders o
LEFT JOIN order_items i ON i.order_id = o.id
LEFT JOIN payments    p ON p.order_id = o.id
LEFT JOIN shipments   s ON s.order_id = o.id
WHERE o.user_id = :uid;
-- 50 items × 3 payments = 150 rows for ONE order. Order and shipment
-- columns repeated 150 times. Any sum(o.total) is 150x too high.
-- Three independent one-to-many joins is the worst case of fan-out.

-- ── ✗ ATTEMPT 2: LAZY LOADING ───────────────────────────────────────────
-- 1 + 20×3 = 61 round trips per page view. Fast queries, slow page,
-- invisible in the slow-query log.

-- ── ✓ THE DESIGN: PAGE THE PARENT, BATCH THE CHILDREN ───────────────────

-- QUERY 1 — the page of orders, with pre-aggregated scalars.
-- Keyset pagination, not OFFSET (constant time, stable under inserts).
SELECT o.id, o.created_at, o.status, o.total,
       s.tracking_number, s.delivered_at,          -- to-ONE: safe to join
       COALESCE(i.item_count, 0) AS item_count,     -- pre-aggregated, so
       COALESCE(p.paid, 0)       AS paid            -- NO fan-out
FROM orders o
LEFT JOIN shipments s ON s.order_id = o.id
LEFT JOIN (SELECT order_id, count(*) AS item_count
           FROM order_items GROUP BY order_id) i ON i.order_id = o.id
LEFT JOIN (SELECT order_id, sum(amount) AS paid
           FROM payments GROUP BY order_id) p ON p.order_id = o.id
WHERE o.user_id = :uid
  AND (o.created_at, o.id) < (:last_created_at, :last_id)
ORDER BY o.created_at DESC, o.id DESC
LIMIT 20;

-- QUERY 2 — all items for exactly those 20 orders, in one round trip
SELECT * FROM order_items WHERE order_id = ANY(:order_ids)
ORDER BY order_id, line_no;

-- QUERY 3 — same for payments
SELECT * FROM payments WHERE order_id = ANY(:order_ids);

-- Group in the application. THREE queries, regardless of page size or
-- how many items an order has.

-- ── WHY THIS SHAPE ──────────────────────────────────────────────────────
-- to-ONE (shipment)      → join it. No fan-out possible, one round trip.
-- to-MANY scalars        → pre-aggregate in a subquery. Correct totals,
--                          and a count does not transfer 50 rows.
-- to-MANY collections    → a separate batched query. Parent columns are
--                          never duplicated.
-- pagination on the PARENT only — paginating a fanned-out result gives
--   partial orders at the page boundary, which is a genuinely confusing
--   bug for a user.

-- ── THE INDEXES THIS NEEDS ──────────────────────────────────────────────
CREATE INDEX ON orders      (user_id, created_at DESC, id DESC); -- Q1: the
                                                    -- keyset seek, exactly
CREATE INDEX ON order_items (order_id);             -- Q2 + the subquery
CREATE INDEX ON payments    (order_id);             -- Q3 + the subquery
CREATE INDEX ON shipments   (order_id);             -- the to-one join
-- Postgres does NOT index foreign keys automatically. Every one of these
-- is a missing index in a default schema.

-- ── THE JSON ALTERNATIVE ────────────────────────────────────────────────
SELECT o.*,
       COALESCE(json_agg(i.*) FILTER (WHERE i.id IS NOT NULL),'[]') AS items
FROM orders o LEFT JOIN order_items i ON i.order_id = o.id
WHERE o.id = ANY(:ids) GROUP BY o.id;
-- One round trip, no duplication, shape matches the API response.
-- Costs: JSON serialisation in the database, harder to page the
-- children, and the result is opaque to further SQL. Good for a fixed
-- API payload; not for something you will query again.

-- ── WHAT I WOULD MEASURE BEFORE OPTIMISING FURTHER ──────────────────────
-- Query count per request (assert it in a test — 3, not 61).
-- Bytes returned: a join that repeats a 2KB parent row 150 times moves
--   300KB where 2KB would do.
-- p95 latency, not the mean.
-- Whether item_count and paid are even used on the page. The cheapest
--   join is the one you delete.

🎯 Key Takeaways

  • A join multiplies rows rather than selecting them — the Venn diagram describes sets, and joins operate on multisets.
  • On an outer join, ON decides which rows pair up and WHERE filters afterwards, so a right-table WHERE silently makes it an inner join.
  • After a LEFT JOIN, use count(right.id) and COALESCE(sum(...), 0) — count(*) counts the NULL-padded row.
  • Anti-joins: prefer NOT EXISTS; LEFT JOIN … IS NULL must test a NOT NULL column; NOT IN breaks on a single NULL.
  • Use EXISTS when the second table is a filter rather than a source of columns — it cannot fan out.
  • Two one-to-many joins produce the cross product of the children and corrupt both totals; aggregate before joining.
  • If DISTINCT changes a total, that is evidence the join is wrong, not a fix.
  • Index foreign keys yourself — Postgres indexes primary keys, not foreign key constraints.
  • N+1 is invisible in the slow-query log because every query is fast; batch the children and assert the query count in tests.
  • In EXPLAIN ANALYZE, the gap between estimated and actual rows explains more than the timings do.
