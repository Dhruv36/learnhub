Constraints & Transactions Intermediate

What you'll master: constraints as the mechanism that makes invalid data impossible rather than merely discouraged, what each ACID letter actually promises and what it conspicuously does not, why the read-modify-write cycle in application code is the most common correctness bug in production systems and the three distinct ways to fix it, how COMMIT really reaches disk and where durability quietly stops, why deferred constraints exist and when you need them, how transactions interact with connection pools, ORMs, retries and background jobs, and why a transaction that spans an HTTP call is an outage waiting for traffic. Prerequisites: INSERT, UPDATE, DELETE and Schema Design. The next lesson, Isolation Levels & Locking, covers the I in ACID in full — this lesson deliberately holds it at arm's length.

Part 1 — Constraints: Making Invalid States Unrepresentable

-- A constraint is not validation. Validation is a check you REMEMBERED to
-- run. A constraint is a property of the data that the database enforces
-- on every writer, forever, including the ones written after you leave.

CREATE TABLE accounts (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    owner_id    bigint      NOT NULL REFERENCES users(id),
    currency    char(3)     NOT NULL,
    balance_cents bigint    NOT NULL DEFAULT 0,
    status      text        NOT NULL DEFAULT 'active',
    closed_at   timestamptz,

    CONSTRAINT balance_non_negative CHECK (balance_cents >= 0),
    CONSTRAINT status_known         CHECK (status IN ('active','frozen','closed')),
    CONSTRAINT closed_has_timestamp CHECK (
        (status = 'closed') = (closed_at IS NOT NULL))
);

-- Read that last one again. It is the interesting kind of constraint: it
-- ties two columns together so the pair cannot disagree. A row claiming
-- to be closed without a closing time cannot exist. Neither can a row
-- with a closing time that claims to still be active.
ConstraintGuaranteesThe bug it prevents
PRIMARY KEYUnique + NOT NULL identityDuplicate rows; "which one is the real record?"
UNIQUENo duplicate values (NULLs exempt by default)Two accounts with one email, created by a race
NOT NULLValue is presentSilent NULL propagation through arithmetic and joins
FOREIGN KEYThe referenced row existsOrphans — an order pointing at a deleted user
CHECKAn arbitrary per-row predicateNegative balances, unknown status strings, contradictory column pairs
EXCLUDENo two rows conflict on an operator (PG)Overlapping bookings — see Schema Design
DEFAULTA value when none is suppliedNot a constraint; it fills gaps, it does not enforce anything
-- ── THE NULL RULE IN UNIQUE ─────────────────────────────────────────────
-- Standard SQL says NULLs are DISTINCT from each other, so a UNIQUE
-- column accepts unlimited NULLs:
CREATE UNIQUE INDEX ON users (deleted_marker);   -- many NULLs allowed

-- That surprises people implementing soft delete:
--   UNIQUE (email) with deleted rows still present blocks re-registration.
-- ✓ A PARTIAL unique index expresses the real rule:
CREATE UNIQUE INDEX users_active_email
    ON users (email) WHERE deleted_at IS NULL;
-- "emails are unique AMONG LIVE USERS" — which was always the rule; the
-- plain UNIQUE was just the closest thing you could say before.

-- Postgres 15+ can also say it directly:
--   UNIQUE NULLS NOT DISTINCT (email)   -- treats NULLs as equal

-- ── FOREIGN KEY ACTIONS ─────────────────────────────────────────────────
user_id bigint REFERENCES users(id) ON DELETE RESTRICT   -- default-ish
                                    ON DELETE CASCADE    -- delete children
                                    ON DELETE SET NULL   -- orphan, keep row
-- CASCADE is convenient and occasionally catastrophic: deleting one user
-- can delete a million rows in a single statement, holding locks the
-- whole time. For big child tables prefer RESTRICT and delete in
-- explicit, chunked batches (see the DML lesson).
🛡️ The database is the last writer standing. Your application is not the only thing that touches this data. There is a migration, a backfill script, an admin console, a data-fix someone ran at 2am, a second service written by another team, and next year a rewrite in a different language. Every one of them bypasses your application-layer validation. A constraint is the only rule that survives all of them — and unlike an app check, it cannot lose a race.

Part 2 — Transactions and What ACID Actually Promises

BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 10000 WHERE id = 1;
UPDATE accounts SET balance_cents = balance_cents + 10000 WHERE id = 2;
COMMIT;
-- Either both rows change or neither does. There is no execution of this
-- program, and no crash timing, that debits account 1 without crediting
-- account 2. That is the entire point.
LetterThe promiseWhat it does NOT promise
AtomicityAll statements take effect, or none doThat the transaction succeeds. Rollback is a normal outcome, not an error you can ignore.
ConsistencyConstraints hold at commit; the DB never persists a rule violationThat your business logic is right. C is about declared constraints, not correctness in general. It is the weakest letter, and arguably a property of your schema rather than the engine.
IsolationConcurrent transactions do not corrupt each otherFull serialisability — not by default. Most engines default to Read Committed, which permits real anomalies. See the next lesson.
DurabilityOnce COMMIT returns, the change survives a crashThat it survives disk loss, or that replicas have it. Durability is local and configurable — see Part 5.
-- ── ATOMICITY IS ALSO A ROLLBACK PROMISE ────────────────────────────────
-- A common misreading: "atomic means my two updates happen together".
-- The stronger and more useful reading is that a FAILED transaction
-- leaves NO TRACE. You never have to write compensating cleanup code for
-- a half-applied change, because a half-applied change cannot be
-- observed and cannot persist.
--
-- This is why "wrap the request in a transaction" is such a powerful
-- default: an exception anywhere in the handler undoes everything the
-- handler wrote, with no cleanup path to get wrong.

-- ── POSTGRES: AN ERROR POISONS THE TRANSACTION ──────────────────────────
BEGIN;
INSERT INTO accounts (owner_id, currency) VALUES (1, 'USDD');  -- ERROR
INSERT INTO accounts (owner_id, currency) VALUES (1, 'USD');
-- ERROR: current transaction is aborted, commands ignored until
--        end of transaction block
COMMIT;    -- behaves as ROLLBACK
-- Postgres refuses to continue. MySQL/InnoDB does NOT — the failed
-- statement rolls back but the transaction continues, so a COMMIT will
-- happily persist a PARTIAL result. If you write portable code, check
-- errors explicitly rather than relying on the engine to stop you.

Part 3 — Savepoints and Partial Rollback

BEGIN;
INSERT INTO orders (user_id, total) VALUES (42, 99.00) RETURNING id;  -- 5001

SAVEPOINT items_start;
INSERT INTO order_items VALUES (5001, :product, :qty);
-- if that raises (say, a CHECK on qty):
ROLLBACK TO SAVEPOINT items_start;   -- undo to the mark; order survives
                                     -- and the transaction is USABLE again
INSERT INTO order_items VALUES (5001, :product, 1);   -- adjusted retry
RELEASE SAVEPOINT items_start;       -- optional: discard the mark
COMMIT;

-- A savepoint is the recovery mechanism for Postgres' poisoned-
-- transaction rule: it is the ONLY way to continue after an error
-- without abandoning everything.

-- ── THE HIDDEN COST ─────────────────────────────────────────────────────
-- Savepoints are not free. Each one takes a subtransaction id, and
-- Postgres tracks up to 64 per backend cheaply — beyond that it spills to
-- disk and readers start doing extra lookups for every row they check.
--
-- Why you should care even if you never type SAVEPOINT:
--   ORMs emit them implicitly. Django's atomic() inside another atomic(),
--   Rails' nested transaction(requires_new: true), and SQLAlchemy's
--   begin_nested() are all savepoints.
-- A loop importing 50,000 rows with a nested atomic() per row creates
-- 50,000 subtransactions in one transaction and can collapse throughput
-- across the WHOLE DATABASE, not just that job. Handle per-row failures
-- by validating first, or by committing per batch — not by nesting a
-- savepoint per iteration.

Part 4 — The Lost Update, and Three Correct Fixes

-- ── THE BUG ─────────────────────────────────────────────────────────────
-- Read-modify-write in application code:
row = SELECT balance_cents FROM accounts WHERE id = 1;   -- both read 50000
new = row.balance - 10000                                -- both compute 40000
UPDATE accounts SET balance_cents = new WHERE id = 1;    -- both write 40000

-- Two concurrent transfers of $100 each. Final balance: $400.
-- Correct answer: $300. One withdrawal vanished — the money moved, the
-- debit did not. Wrapping this in BEGIN/COMMIT does NOT fix it at Read
-- Committed: both transactions are individually atomic and both commit.
--
-- ⚠ This is the single most common data-corruption bug in web
--   applications, and it is invisible in testing because it requires
--   concurrency to reproduce.
❌ Check-then-act 
if (balance >= amount) {        // read
    setBalance(balance - amount) // write
}
-- The gap between the check and the
-- act is where the other transaction
-- lives. Nothing holds the value
-- still while you think about it.
✅ One atomic statement 
UPDATE accounts
   SET balance_cents = balance_cents - :amt
 WHERE id = :id
   AND balance_cents >= :amt;
-- The read and the write are the same
-- operation, under the row lock. Check
-- rows-affected: 0 means insufficient
-- funds, and no update happened.
-- ── FIX 1: ATOMIC UPDATE (the default choice) ───────────────────────────
UPDATE accounts SET balance_cents = balance_cents - :amt
WHERE id = :id AND balance_cents >= :amt;
-- The database reads the current value and writes the new one while
-- holding the row lock. Concurrency is handled for you.
-- ⚠ The affected-row count IS the business result. Ignoring it is the
--   second half of this bug: the statement "succeeded" and did nothing.
if (rowsAffected == 0) throw new InsufficientFunds();

-- ── FIX 2: SELECT ... FOR UPDATE (when you must compute in the app) ─────
BEGIN;
SELECT balance_cents, tier FROM accounts WHERE id = :id FOR UPDATE;
-- ↑ row is now locked; other FOR UPDATE readers WAIT here
--   compute a fee schedule, call a pure pricing function, whatever
UPDATE accounts SET balance_cents = :computed WHERE id = :id;
COMMIT;                                   -- lock released
-- Correct, and sometimes necessary. But it serialises every writer of
-- that row for the duration — so keep the middle short, and NEVER put a
-- network call between the SELECT and the COMMIT.

-- ── FIX 3: OPTIMISTIC CONCURRENCY (best for user-facing edit forms) ─────
UPDATE documents
   SET body = :body, version = version + 1
 WHERE id = :id AND version = :version_the_user_loaded;
-- 0 rows affected → someone else saved first. Nothing was overwritten.
-- Show the user a conflict rather than silently discarding their edit or
-- the other person's. No locks are held while the user is typing, which
-- is the whole point: you cannot hold a database lock across a
-- think-time gap measured in minutes.
ApproachUse whenCost
Atomic UPDATEThe new value is a function of the old one (counters, balances, stock)None. Always prefer it.
FOR UPDATEThe computation genuinely cannot be expressed in SQLSerialises writers; blocks; deadlock risk if you lock several rows in inconsistent order
Version columnLong think-time between read and write (edit forms, APIs)The caller must handle a conflict response
SERIALIZABLEMulti-row invariants too complex to express otherwiseReal serialisation failures; you must implement a retry loop — see next lesson

Part 5 — Durability: What COMMIT Actually Does

-- ── THE WRITE-AHEAD LOG ─────────────────────────────────────────────────
-- Data pages are NOT written to disk at commit time. That would be
-- random I/O all over the file, and far too slow. Instead:
--
--   1. change the page in the shared buffer pool (memory)
--   2. append a record describing the change to the WAL (SEQUENTIAL I/O)
--   3. fsync the WAL   ← THIS is the durability point
--   4. COMMIT returns
--   5. ...later, a checkpoint flushes the dirty pages to their real homes
--
-- Crash at step 4.5? On restart the engine replays the WAL and the
-- committed change reappears. The rule is WRITE-AHEAD: the log record
-- reaches durable storage BEFORE the data page it describes.
-- (Postgres calls this the WAL; MySQL/InnoDB, the redo log.)

-- ── DURABILITY IS A DIAL, NOT A CONSTANT ────────────────────────────────
SET synchronous_commit = off;     -- Postgres, session-scoped
-- COMMIT now returns WITHOUT waiting for the fsync. Massively faster for
-- bulk work. The trade: a crash can lose the last ~600ms of COMMITTED
-- transactions. Not corruption — the database is consistent — but
-- acknowledged writes are gone.
--
-- Legitimate: bulk imports, analytics staging, rebuildable derived data.
-- Not legitimate: payments, orders, anything a user was told "saved".
-- (MySQL's equivalent knob is innodb_flush_log_at_trx_commit.)

-- ── WHERE DURABILITY STOPS ──────────────────────────────────────────────
-- D means "survives a crash of THIS server". It does not mean:
--   ✗ survives the disk dying          → that is replication + backups
--   ✗ the replica has it               → async replication lags; a
--                                        failover can lose committed
--                                        transactions. Use synchronous
--                                        replication if that is
--                                        unacceptable, and pay the
--                                        latency.
--   ✗ you can recover from a bad
--     migration                        → that is backups + PITR
-- ⚠ A read-replica is not a backup. It replicates your DELETE faithfully
--   and within milliseconds.

Part 6 — Transactions in Real Applications

-- ── THE #1 PRODUCTION SIN: I/O INSIDE A TRANSACTION ─────────────────────
BEGIN;
UPDATE orders SET status='paid' WHERE id=:id;
charge = stripe.charge(...);          -- ✗✗✗ 200ms, or 30s on a bad day
INSERT INTO payments (order_id, ref) VALUES (:id, charge.id);
COMMIT;
-- Every row you touched stays locked for the entire HTTP call. The
-- connection is held. Under load the pool exhausts, unrelated endpoints
-- start timing out, and the incident looks like "the database is down".
-- Worse: if the API succeeds and the COMMIT fails, you have charged a
-- customer and have no record of it.
--
-- ✓ SPLIT IT. Transaction → external call → transaction:
BEGIN;                                       -- 1. reserve, commit fast
UPDATE orders SET status='charging' WHERE id=:id AND status='pending';
INSERT INTO payment_attempts (order_id, idem_key) VALUES (:id, :key);
COMMIT;
charge = stripe.charge(idempotency_key=:key);    -- 2. outside any txn
BEGIN;                                       -- 3. record the outcome
UPDATE orders SET status='paid' WHERE id=:id;
INSERT INTO payments (order_id, ref) VALUES (:id, charge.id);
COMMIT;
-- The idempotency key makes step 2 safe to retry after a crash between
-- steps, which is the part people skip. "Exactly once" across a network
-- does not exist; "at least once + idempotent" does.

-- ── TRANSACTIONS AND THE CONNECTION POOL ────────────────────────────────
-- A transaction lives on ONE connection and holds it exclusively from
-- BEGIN to COMMIT. Open transaction time IS connection-pool occupancy.
-- 20 connections and a 2-second transaction caps you at 10 txn/s, no
-- matter how much CPU the database has spare.
-- ⚠ With a pooler in TRANSACTION mode (PgBouncer), session state does
--   not survive the transaction — session advisory locks, temp tables,
--   and prepared statements can vanish underneath you.

-- ── IDLE IN TRANSACTION IS AN OUTAGE IN WAITING ─────────────────────────
SELECT pid, state, now()-xact_start AS open_for, query
FROM pg_stat_activity
WHERE state = 'idle in transaction' AND now()-xact_start > interval '1 min';
-- A BEGIN with no COMMIT (an exception path that forgot to roll back)
-- holds locks AND pins the oldest snapshot, so autovacuum cannot reclaim
-- dead rows anywhere in the database. Tables bloat, plans degrade.
-- Defend with a server-side timeout rather than good intentions:
SET idle_in_transaction_session_timeout = '30s';
SET statement_timeout = '10s';
SET lock_timeout = '3s';

-- ── DEFERRED CONSTRAINTS ────────────────────────────────────────────────
-- Checked at COMMIT instead of per statement. The classic need is a
-- circular reference, or reordering rows under a UNIQUE constraint:
ALTER TABLE items ADD CONSTRAINT items_pos_uniq UNIQUE (list_id, position)
    DEFERRABLE INITIALLY IMMEDIATE;
BEGIN;
SET CONSTRAINTS items_pos_uniq DEFERRED;
UPDATE items SET position = position + 1 WHERE list_id = 7;
-- transiently duplicated positions are fine mid-transaction...
COMMIT;   -- ...and must be unique HERE, or the whole thing rolls back
-- Use sparingly: an error at COMMIT is harder to attribute than an error
-- at the statement that caused it.

-- ── DDL IS TRANSACTIONAL (in Postgres) ──────────────────────────────────
BEGIN;
ALTER TABLE users ADD COLUMN nickname text;
CREATE INDEX ON users (nickname);
COMMIT;    -- all-or-nothing schema change. Wonderful for migrations.
-- ⚠ MySQL does NOT do this: DDL commits implicitly, so a half-finished
--   migration leaves a half-changed schema.
-- ⚠ Even in Postgres, ALTER TABLE takes an ACCESS EXCLUSIVE lock. Behind
--   a slow query it queues, and everything queues behind IT. Always set
--   lock_timeout before a migration.
CREATE INDEX CONCURRENTLY ...   -- no write lock, but CANNOT run in a txn
⏱️ Every transaction has a length budget. Open transactions hold row locks, occupy a pooled connection, and pin the snapshot horizon that vacuum needs to advance. The discipline that prevents most database incidents fits in one line: open late, commit early, and never wait on anything outside the database in between — no HTTP calls, no queue publishes, no user input, no sleep.

Interview Questions

Beginner: Explain ACID using a money transfer.

Moving $100 from A to B is two statements — debit A, credit B — and every letter maps to a way that pair can go wrong. Atomicity: both apply or neither does, so a crash between them cannot leave money debited but not credited; the rollback leaves no trace to clean up. Consistency: declared constraints hold at commit, so a CHECK (balance >= 0) means no committed state has a negative balance. Isolation: a concurrent transfer on the same accounts cannot interleave to corrupt the result — though how much protection you actually get depends on the isolation level, and the default is not full serialisability. Durability: once COMMIT returns, the change is in the write-ahead log on durable storage and survives a crash.

The honest addition most candidates miss: C is the weakest letter. It only says your declared constraints are not violated — it says nothing about whether your business logic is correct. And D means "survives a crash of this machine", not "survives disk loss" and not "the replica has it".

Beginner: Why enforce rules with constraints when the application already validates?

Because the application is not the only writer. Migrations, backfill scripts, an admin console, a second service, a data fix someone runs by hand, and whatever replaces your code in three years all write to the same tables, and none of them run your validation. A constraint is enforced by the engine on every write path unconditionally.

The second reason is that application checks race. "Is this email taken?" followed by INSERT is a check-then-act: two concurrent signups both see "no" and both insert. Only a UNIQUE constraint can actually prevent that, because only the database can make the check and the write one indivisible operation. Use both layers — app validation for fast, friendly, field-level error messages; constraints for the guarantee.

Mid: Two users buy the last item in stock at the same instant. Walk through what goes wrong and how you fix it.

The naive implementation reads stock (1), checks it is greater than zero, and writes stock = 0. Both requests read 1 before either writes, both pass the check, both write 0, and two orders exist for one item. Wrapping each request in a transaction does not help at Read Committed: both transactions are individually atomic and both commit successfully. The bug is not a missing transaction, it is that the read and the write are separate operations with a gap between them.

The fix is to make the check and the decrement a single statement: UPDATE products SET stock = stock - 1 WHERE id = :id AND stock >= 1. The engine evaluates the predicate and applies the change while holding the row lock, so the second transaction re-reads the updated row, finds stock = 0, matches nothing, and affects zero rows. The application must then treat zero affected rows as "out of stock" — that count is the business result, and discarding it reintroduces the bug in a subtler form.

If the decision genuinely cannot be expressed in SQL, SELECT ... FOR UPDATE is the fallback: it locks the row for the rest of the transaction. It is correct but it serialises every buyer of that product, so the window must stay short. For a hot product that becomes the bottleneck, at which point you stop fighting the row and change the model — allocate from a pool of reservation rows, or accept an oversell and reconcile.

Mid: What is wrong with calling a payment API inside a transaction, and what is the correct shape?

Three separate problems. First, every lock the transaction holds is held for the duration of the network call — hundreds of milliseconds normally, and unbounded when the provider is degraded. Second, the transaction pins a pooled connection for that whole time, so a slow third party converts directly into pool exhaustion and your entire application starts timing out on endpoints that have nothing to do with payments. Third and worst, the two systems cannot commit together: if the charge succeeds and the COMMIT then fails, you have taken the customer's money and have no record that you did.

The correct shape is transaction, call, transaction. In the first transaction, move the order to a pending state and persist an idempotency key, then commit immediately. Make the API call outside any transaction, passing that key. In a second short transaction, record the outcome. Now no lock is held across the network, the connection is returned to the pool, and a crash at any point is recoverable: a reconciliation job finds attempts with no outcome and safely retries with the same key, which the provider deduplicates. The key point is that you cannot get atomicity across two systems, so you engineer for at-least-once delivery plus idempotency instead of pretending exactly-once exists.

Senior: A COMMIT returned successfully and the data was gone after a failover. Explain how that is possible without any bug.

Because durability is local and replication is, by default, asynchronous. COMMIT returns once the write-ahead log record is fsynced on the primary. Replicas receive that WAL afterwards, over the network, with lag that is normally milliseconds but grows under write bursts, network problems, or a slow replica. If the primary dies after acknowledging the commit but before the replica has consumed the record, and you promote that replica, the committed transaction is not in the new timeline. The database never lied — it promised to survive a crash of that server, and that server is not coming back.

The other route to the same outcome is synchronous_commit = off, where COMMIT returns before the fsync at all and a crash loses a window of acknowledged transactions on the primary itself.

The fix is to decide the RPO deliberately. Synchronous replication to at least one replica makes commit wait for a remote acknowledgement — correctness bought with write latency and an availability question when the replica is down, which is why synchronous_standby_names with quorum (ANY 1 (a, b)) is the usual compromise. Most systems should run async and accept a small RPO for most tables, and route the genuinely unrecoverable operations — payments, ledger entries — through a synchronous path or an external durable record. What you must not do is assume asynchronous replication gives zero data loss, because that assumption is only tested during an incident.

Senior: Your API degrades under load. Metrics show high connection-pool wait and many sessions "idle in transaction". Diagnose it.

idle in transaction means a session executed BEGIN, did some work, and is now waiting on something that is not the database while its transaction stays open. That state is expensive in three compounding ways: it holds every lock the transaction acquired, it holds a pooled connection exclusively, and it pins the oldest snapshot so autovacuum cannot reclaim dead tuples anywhere in the database. So the symptom is pool exhaustion, but the second-order effect is table bloat and progressively worse plans, which slows every query and deepens the hole.

Almost always the cause is I/O inside the transaction — an HTTP call, a queue publish, an S3 upload, occasionally a slow template render — or an error path that returned without rolling back. I would confirm by querying pg_stat_activity for sessions with a long now() - xact_start, grouping by the last query to find the offending code path, and checking pg_locks for what is being pinned.

The immediate mitigation is server-side timeouts, because they are configuration rather than a deploy: idle_in_transaction_session_timeout kills the leaked sessions, statement_timeout caps runaway queries, and lock_timeout stops a migration from creating a queue. The real fix is moving the external call out of the transaction, and the durable fix is making that structural — a lint rule or a wrapper that refuses to issue HTTP requests while a transaction is open — because this recurs indefinitely once it is possible.

1 (easy): Add constraints to this table so that invalid rows cannot exist.
Solution 
-- GIVEN: everything nullable, everything text, no rules.
CREATE TABLE subscriptions (
    id         serial,
    user_id    integer,
    plan       text,
    price      float,
    started_at timestamp,
    ended_at   timestamp,
    is_active  boolean
);

-- ✓ REBUILT
CREATE TABLE subscriptions (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id    bigint      NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    plan       text        NOT NULL CHECK (plan IN ('free','pro','team')),
    price_cents integer    NOT NULL CHECK (price_cents >= 0),
    started_at timestamptz NOT NULL DEFAULT now(),
    ended_at   timestamptz,

    CONSTRAINT ends_after_start CHECK (ended_at IS NULL OR ended_at > started_at)
);

-- One active subscription per user, enforced not merely intended:
CREATE UNIQUE INDEX subs_one_active
    ON subscriptions (user_id) WHERE ended_at IS NULL;

-- ── WHAT CHANGED AND WHY ────────────────────────────────────────────────
-- float → integer cents. NEVER store money in a binary float: 0.1 + 0.2
--   is not 0.3 and the error compounds across a ledger. Integer minor
--   units, or numeric(12,2).
-- timestamp → timestamptz. `timestamp` has no zone, so the same value
--   means different instants depending on who reads it. This is not
--   recoverable later — you cannot infer the zone that was intended.
-- is_active DELETED. It duplicates `ended_at IS NULL` and the two will
--   eventually disagree; then no one knows which is true. Derive it.
-- CHECK on plan: a typo'd 'pro ' becomes an error instead of a user who
--   silently has no plan.
-- Partial unique index: "one active subscription per user" is a real
--   business rule. Written this way it cannot be violated even by a
--   race. As a comment in the service layer, it will be.
2 (easy): Demonstrate atomicity: transfer money, force a failure, and prove nothing was applied.
Solution 
INSERT INTO accounts (id, owner_id, currency, balance_cents)
VALUES (1, 1, 'USD', 50000), (2, 2, 'USD', 0);

-- ── THE FAILING TRANSFER ────────────────────────────────────────────────
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 60000 WHERE id = 1;
-- ERROR: new row violates check constraint "balance_non_negative"
UPDATE accounts SET balance_cents = balance_cents + 60000 WHERE id = 2;
-- ERROR: current transaction is aborted...
COMMIT;                      -- Postgres reports ROLLBACK

SELECT id, balance_cents FROM accounts ORDER BY id;
-- 1 | 50000     ← untouched
-- 2 |     0     ← the credit never happened either

-- THE POINT: the debit was rejected, and atomicity ensured the credit
-- could not land on its own. Without the transaction, statement 2 would
-- have created $600 out of nothing.

-- ── PROVING IT THE OTHER WAY (deliberate rollback) ──────────────────────
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 10000 WHERE id = 1;
UPDATE accounts SET balance_cents = balance_cents + 10000 WHERE id = 2;
SELECT id, balance_cents FROM accounts ORDER BY id;   -- 40000 / 10000
ROLLBACK;
SELECT id, balance_cents FROM accounts ORDER BY id;   -- 50000 / 0

-- Inside the transaction you SEE your own uncommitted changes. No other
-- session does. Rollback leaves no trace — no compensating update to
-- write, no half-state to detect.

-- ── AND THE CONSTRAINT DOES THE REAL WORK ───────────────────────────────
-- Note which mechanism actually stopped the overdraft: the CHECK, not
-- the transaction. The transaction only ensured the failure was clean.
-- Both are needed and they do different jobs.
3 (medium): Reproduce a lost update with two sessions, then fix it three different ways.
Solution 
-- ── REPRODUCE (two psql windows, interleaved as numbered) ───────────────
-- setup:  UPDATE accounts SET balance_cents = 50000 WHERE id = 1;

-- S1 (1)  BEGIN;
-- S1 (2)  SELECT balance_cents FROM accounts WHERE id = 1;   -- 50000
-- S2 (3)  BEGIN;
-- S2 (4)  SELECT balance_cents FROM accounts WHERE id = 1;   -- 50000
-- S1 (5)  UPDATE accounts SET balance_cents = 40000 WHERE id = 1;
-- S1 (6)  COMMIT;
-- S2 (7)  UPDATE accounts SET balance_cents = 40000 WHERE id = 1;
-- S2 (8)  COMMIT;

SELECT balance_cents FROM accounts WHERE id = 1;   -- 40000
-- Two $100 withdrawals. Expected 30000. One is GONE, and both
-- transactions reported success. No error anywhere in the logs.

-- ── FIX 1: ATOMIC UPDATE ────────────────────────────────────────────────
-- S1 (1)  UPDATE accounts SET balance_cents = balance_cents - 10000
--           WHERE id = 1 AND balance_cents >= 10000;
-- S2 (2)  same statement  → BLOCKS on S1's row lock
-- S1 (3)  COMMIT;
-- S2      unblocks, RE-READS the row (Read Committed re-evaluates the
--         predicate on the updated version), sees 40000, subtracts.
SELECT balance_cents FROM accounts WHERE id = 1;   -- 30000 ✓
-- No application-side locking, no retry, no reasoning about interleaving.
-- This is why it is the default answer.

-- ── FIX 2: SELECT ... FOR UPDATE ────────────────────────────────────────
BEGIN;
SELECT balance_cents FROM accounts WHERE id = 1 FOR UPDATE;   -- locks
--   ...compute in the app: fees, tier rules, whatever needs code...
UPDATE accounts SET balance_cents = :computed WHERE id = 1;
COMMIT;
-- S2's identical SELECT ... FOR UPDATE waits at the SELECT, so it reads
-- the value only after S1 commits. Correct, but every writer of this row
-- now queues behind the app-side computation.
-- ⚠ Lock multiple rows in a CONSISTENT ORDER (e.g. ORDER BY id) or two
--   transfers between the same pair of accounts deadlock:
SELECT * FROM accounts WHERE id IN (1,2) ORDER BY id FOR UPDATE;

-- ── FIX 3: OPTIMISTIC / VERSION COLUMN ──────────────────────────────────
ALTER TABLE accounts ADD COLUMN version integer NOT NULL DEFAULT 0;
-- read:
SELECT balance_cents, version FROM accounts WHERE id = 1;   -- 50000, v7
-- write:
UPDATE accounts SET balance_cents = 40000, version = version + 1
 WHERE id = 1 AND version = 7;
-- S2 does the same with version = 7 → 0 rows affected. It did NOT
-- overwrite S1. The app re-reads and retries, or reports a conflict.

-- ── CHOOSING ────────────────────────────────────────────────────────────
-- delta on a number             → FIX 1, always
-- must compute in app code      → FIX 2, keep the window tiny
-- human think-time between
-- read and write (edit forms)   → FIX 3; you cannot hold a lock while a
--                                 user is at lunch with the form open
4 (medium): Rewrite this order-placement handler to be correct and safe under load.
Solution 
-- ── ✗ THE ORIGINAL ──────────────────────────────────────────────────────
BEGIN;
  SELECT stock FROM products WHERE id = :pid;          -- check-then-act
  -- app: if (stock < qty) throw
  UPDATE products SET stock = stock - :qty WHERE id = :pid;
  INSERT INTO orders (user_id, total) VALUES (:uid, :total) RETURNING id;
  charge = stripe.charge(:total);                      -- network I/O
  UPDATE orders SET status = 'paid' WHERE id = :oid;
  email.send(:uid, 'Order confirmed');                 -- more I/O
COMMIT;
-- Four distinct defects:
--   1. check-then-act on stock → oversell
--   2. payment API inside the transaction → locks + pool held for the
--      whole call
--   3. email inside the transaction → sent even if COMMIT then fails
--   4. no idempotency → a retry double-charges

-- ── ✓ TRANSACTION 1: RESERVE, THEN COMMIT FAST ──────────────────────────
BEGIN;
UPDATE products SET stock = stock - :qty
 WHERE id = :pid AND stock >= :qty;
-- rowsAffected == 0 → ROLLBACK; return 409 "out of stock"

INSERT INTO orders (user_id, total_cents, status, idem_key)
VALUES (:uid, :total, 'pending_payment', :idem_key)
RETURNING id;                                          -- :oid
COMMIT;   -- total open time: sub-millisecond, no I/O

-- ── OUTSIDE ANY TRANSACTION: THE EXTERNAL CALL ──────────────────────────
charge = stripe.charge(amount=:total, idempotency_key=:idem_key);
-- Crash here? The order sits in 'pending_payment'. A sweeper retries
-- with the SAME key; Stripe returns the original charge rather than
-- making a second one. That key is the entire safety mechanism.

-- ── TRANSACTION 2: RECORD THE OUTCOME ───────────────────────────────────
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = :oid AND status = 'pending_payment';
INSERT INTO payments (order_id, provider_ref) VALUES (:oid, charge.id);
INSERT INTO outbox (topic, payload)                    -- ✓ transactional
VALUES ('order.paid', jsonb_build_object('order_id', :oid));
COMMIT;

-- ── THE OUTBOX, AND WHY THE EMAIL MOVED ─────────────────────────────────
-- Sending the email inside the transaction risks sending it for an order
-- that then rolls back. Sending it after COMMIT risks losing it if the
-- process dies. Neither is acceptable, and there is no third option that
-- makes a network send atomic with a database commit.
-- So: write the INTENT to an outbox table in the same transaction — that
-- IS atomic — and let a separate worker poll and send.
SELECT * FROM outbox WHERE sent_at IS NULL ORDER BY id
FOR UPDATE SKIP LOCKED LIMIT 100;    -- lets N workers run without
                                     -- stepping on each other
-- Delivery becomes at-least-once, so the consumer must be idempotent.
-- That is the honest trade and the standard one.

-- ── THE FAILURE PATH THAT IS STILL REQUIRED ─────────────────────────────
-- If the charge is DECLINED, the reserved stock must go back:
UPDATE products SET stock = stock + :qty WHERE id = :pid;
UPDATE orders   SET status = 'payment_failed' WHERE id = :oid;
-- Reserving before charging means you own the compensation. That is the
-- price of not holding a lock across the network, and it is worth it.
5 (hard): Design an append-only ledger where the balance can never disagree with its history.
Solution 
-- REQUIREMENT: every balance change is auditable, balances are fast to
-- read, and the two can never drift apart.

-- ── THE MODEL: ENTRIES ARE TRUTH, BALANCE IS DERIVED ────────────────────
CREATE TABLE ledger_entries (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    account_id bigint      NOT NULL REFERENCES accounts(id),
    amount_cents bigint    NOT NULL CHECK (amount_cents <> 0),  -- ±
    transfer_id uuid       NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON ledger_entries (account_id, id);
CREATE INDEX ON ledger_entries (transfer_id);

-- NO UPDATE, NO DELETE — ever. A mistake is corrected by a REVERSING
-- entry, so the history shows both what happened and the correction.
-- Enforce it rather than documenting it:
REVOKE UPDATE, DELETE ON ledger_entries FROM app_user;

-- ── DOUBLE ENTRY: EVERY TRANSFER SUMS TO ZERO ───────────────────────────
BEGIN;
INSERT INTO ledger_entries (account_id, amount_cents, transfer_id) VALUES
    (1, -10000, :tid),
    (2, +10000, :tid);
UPDATE accounts SET balance_cents = balance_cents - 10000 WHERE id = 1;
UPDATE accounts SET balance_cents = balance_cents + 10000 WHERE id = 2;
COMMIT;
-- Atomicity is what makes the invariant hold: entries and balances move
-- together or not at all. Money is never created or destroyed, only
-- moved, because the pair always sums to zero.

-- ── WHY KEEP A BALANCE COLUMN AT ALL? ───────────────────────────────────
SELECT sum(amount_cents) FROM ledger_entries WHERE account_id = 1;
-- Correct by construction, and O(number of entries). At 10M entries this
-- is seconds — unusable on a page load, and it gets worse forever.
-- The cached balance is a DELIBERATE denormalisation. What makes it safe
-- is that it is updated in the SAME TRANSACTION as its source rows, so
-- there is no window in which they disagree.

-- ── MAKE DRIFT DETECTABLE ANYWAY ────────────────────────────────────────
-- Because a future bug, a manual fix, or a bad migration can still
-- break it, and silent divergence in a ledger is the worst outcome:
SELECT a.id, a.balance_cents, COALESCE(sum(e.amount_cents), 0) AS derived
FROM accounts a LEFT JOIN ledger_entries e ON e.account_id = a.id
GROUP BY a.id, a.balance_cents
HAVING a.balance_cents <> COALESCE(sum(e.amount_cents), 0);
-- Run nightly. It must return zero rows; alert if it ever does not.
-- A denormalisation without a drift check is a bug with a delay on it.

-- ── ENFORCING NON-NEGATIVE, PROPERLY ────────────────────────────────────
UPDATE accounts SET balance_cents = balance_cents - 10000
 WHERE id = 1 AND balance_cents >= 10000;
-- 0 rows → ROLLBACK the whole transfer. The CHECK constraint is the
-- backstop; the predicate is the control flow. You want both, because
-- the CHECK turns a logic bug into an error instead of an overdraft.

-- ── IDEMPOTENCY ON THE TRANSFER ─────────────────────────────────────────
CREATE UNIQUE INDEX ON ledger_entries (transfer_id, account_id);
-- A client retry with the same transfer_id hits a unique violation
-- instead of moving the money twice. In a ledger, "the request was
-- retried" must not mean "the money moved again" — and the constraint
-- guarantees that even if the retry logic is wrong.

-- ── SNAPSHOTS, WHEN HISTORY GETS LONG ───────────────────────────────────
CREATE TABLE balance_snapshots (
    account_id bigint NOT NULL REFERENCES accounts(id),
    as_of_entry_id bigint NOT NULL,
    balance_cents  bigint NOT NULL,
    PRIMARY KEY (account_id, as_of_entry_id)
);
-- Reconstruct any point in time as: nearest snapshot + entries since.
-- Bounded work regardless of history length, and the entries remain the
-- source of truth — the snapshot is only a checkpoint.

-- ── THE CONTENTION LIMIT, STATED HONESTLY ───────────────────────────────
-- Every transfer touching a shared account (a platform fee account, say)
-- serialises on that one row. Thousands of writes per second to a single
-- account will not work no matter how the transaction is written.
-- At that point you shard the hot account into N sub-accounts, write to
-- a random one, and sum them for the balance — trading a cheap read for
-- write throughput, deliberately.
6 (hard): Investigate a production incident: pool exhausted, sessions idle in transaction, tables bloating.
Solution 
-- SYMPTOMS: API p99 climbing, "timeout acquiring connection" in logs,
-- disk usage rising faster than data volume.

-- ── STEP 1: WHAT ARE THE CONNECTIONS DOING? ─────────────────────────────
SELECT state, count(*), max(now() - xact_start) AS longest_txn
FROM pg_stat_activity WHERE backend_type = 'client backend'
GROUP BY state ORDER BY 2 DESC;
--  state                | count | longest_txn
--  idle in transaction  |    38 | 00:04:12     ← the whole problem
--  active               |     6 |
--  idle                 |     2 |
-- 38 of 46 connections are holding a transaction open while doing
-- NOTHING in the database. The pool is exhausted by sessions that are
-- not using it.

-- ── STEP 2: WHICH CODE PATH? ────────────────────────────────────────────
SELECT pid, now() - xact_start AS open_for, wait_event_type, wait_event,
       left(query, 90) AS last_query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start LIMIT 10;
-- `query` shows the LAST statement executed, not a running one — that is
-- the fingerprint of the code path that then went off to do I/O.
-- Here: UPDATE orders SET status='charging' ... → the payment handler.

-- ── STEP 3: CONFIRM THE SECOND-ORDER DAMAGE ─────────────────────────────
SELECT relname, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables WHERE n_dead_tup > 100000
ORDER BY n_dead_tup DESC LIMIT 5;
-- Millions of dead tuples, autovacuum hours stale.
SELECT min(now() - xact_start) FROM pg_stat_activity WHERE xact_start IS NOT NULL;
-- The OLDEST open transaction pins the snapshot horizon: vacuum cannot
-- remove any row version newer than it, DATABASE-WIDE. One forgotten
-- transaction bloats tables it never touched. That is the disk growth,
-- and the bloat is why the plans are degrading too.

-- ── STEP 4: STOP THE BLEEDING (config, not a deploy) ────────────────────
ALTER SYSTEM SET idle_in_transaction_session_timeout = '30s';
ALTER SYSTEM SET statement_timeout = '30s';
ALTER SYSTEM SET lock_timeout = '5s';
SELECT pg_reload_conf();
-- Leaked sessions are now killed and their locks released. Then, only if
-- still critical, terminate the worst offenders by hand:
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
WHERE state='idle in transaction' AND now()-xact_start > interval '2 min';
-- ⚠ These sessions are rolled back. That is safe by definition — an
--   uncommitted transaction has no effects — but the requests behind
--   them fail, so it is mitigation, not a fix.

-- ── STEP 5: THE ACTUAL FIX ──────────────────────────────────────────────
-- The handler wraps the payment API call in the request transaction.
-- Split it (exercise 4): commit the reservation, call outside any
-- transaction, commit the outcome.

-- ── STEP 6: MAKE IT NOT RECUR ───────────────────────────────────────────
-- 1. Keep the timeouts permanently. They are a safety net, and the cost
--    of not having one is this incident.
-- 2. Alert on `idle in transaction` older than 60s — it is a leading
--    indicator, visible long before the pool exhausts.
-- 3. Instrument transaction DURATION as a histogram, not just query
--    duration. This class of bug is invisible in query metrics: every
--    individual query was fast.
-- 4. Structurally prevent it: an HTTP client wrapper that refuses to
--    send while a transaction is open, failing loudly in CI. Reviews
--    catch this once; a guard catches it every time.

-- ── AFTERMATH ───────────────────────────────────────────────────────────
VACUUM (ANALYZE) orders;        -- reclaim, refresh statistics
-- Check whether bloat left indexes inflated; REINDEX CONCURRENTLY if so.
-- The lesson to write down: transaction duration is a first-class
-- production metric, because open transactions cost locks, connections
-- AND vacuum progress simultaneously.

🎯 Key Takeaways

  • Constraints are the only rules that survive migrations, scripts, other services and future code — application validation is a convenience layer, not a guarantee.
  • UNIQUE treats NULLs as distinct; a partial unique index expresses rules like "unique among live rows" that plain UNIQUE cannot.
  • Atomicity's strongest promise is that a failure leaves no trace — no compensating cleanup code to get wrong.
  • C is the weakest ACID letter (declared constraints only) and D is narrower than it sounds (this server's crash, not disk loss and not the replica).
  • Read-modify-write in application code loses updates, and a transaction alone does not fix it — the read and write must be one operation.
  • Three correct fixes: atomic UPDATE for deltas, FOR UPDATE when you must compute in code, a version column across human think-time.
  • The affected-row count is the business result; a statement that matched nothing succeeded and did nothing.
  • Never hold a transaction across a network call — commit, call with an idempotency key, commit again; use an outbox for side effects that must not be lost.
  • Open transactions hold locks, pin a pooled connection, and block vacuum database-wide; idle in transaction is an outage forming.
  • Set statement_timeout, lock_timeout and idle_in_transaction_session_timeout — safety nets beat good intentions.
