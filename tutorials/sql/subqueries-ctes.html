Subqueries & CTEs Intermediate

What you'll master: every subquery form and where each is legal, correlated versus non-correlated execution and when the planner can flatten one into a join, why EXISTS beats IN and why NOT IN is a landmine, CTEs as named pipeline steps plus the optimisation-fence change that altered Postgres performance advice, recursive CTEs for trees and graphs including cycle protection, LATERAL for per-row subqueries, and data-modifying CTEs with the snapshot rule that surprises everyone. Prerequisites: JOINs and Sorting, Limiting & Aggregates.

Part 1 — The Subquery Forms

-- ── 1. SCALAR: returns exactly ONE row, ONE column ──────────────────────
SELECT name, score,
       (SELECT avg(score) FROM users) AS avg_all      -- runs ONCE
FROM users;
-- Usable anywhere a value is: SELECT, WHERE, ORDER BY, an expression.
-- ⚠ Returning more than one row is a RUNTIME error, not a parse error:
--   "more than one row returned by a subquery used as an expression"
--   It passes tests on small data and fails when a second row appears.
--   Guarantee singularity with an aggregate, or LIMIT 1 + ORDER BY.
-- Returning NO rows yields NULL, silently — which then propagates.

-- ── 2. IN / NOT IN: membership in a set ─────────────────────────────────
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders WHERE total > 100);
-- Deduplicates implicitly, so no fan-out.

-- ── 3. EXISTS: does at least one row match? ─────────────────────────────
SELECT * FROM users u WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id);
-- SELECT 1 by convention — the column list is never evaluated. Writing
-- SELECT * costs nothing either; the planner ignores it.

-- ── 4. DERIVED TABLE: a subquery in FROM ────────────────────────────────
SELECT dept, avg_sal FROM (
  SELECT dept, avg(salary) AS avg_sal FROM emp GROUP BY dept
) t                                    -- ⚠ the alias is MANDATORY in
WHERE avg_sal > 50000;                 --   Postgres and MySQL

-- ── 5. ROW CONSTRUCTOR: compare several columns at once ─────────────────
WHERE (created_at, id) < (:last_created_at, :last_id)     -- keyset paging
WHERE (dept, salary) IN (SELECT dept, max(salary) FROM emp GROUP BY dept);
-- The second is the classic "highest paid per department" — and it
-- returns EVERY tied employee, unlike a window function with row_number.

-- ── 6. ANY / ALL ────────────────────────────────────────────────────────
WHERE score > ANY (SELECT score FROM users WHERE dept = 'eng')  -- > the MIN
WHERE score > ALL (SELECT score FROM users WHERE dept = 'eng')  -- > the MAX
-- `= ANY` is exactly `IN`. Rare in practice; clearer as an aggregate.
-- ⚠ ALL against an empty set is TRUE; ANY against an empty set is FALSE.
--   Both are logically correct and both surprise people.

-- ── WHERE EACH FORM IS LEGAL ────────────────────────────────────────────
--   SELECT list   scalar only
--   FROM          derived table, LATERAL
--   WHERE         scalar, IN, EXISTS, ANY/ALL, row constructor
--   GROUP BY      no
--   HAVING        scalar, IN, EXISTS
--   ORDER BY      scalar

Part 2 — Correlated Subqueries

-- NON-CORRELATED: independent of the outer query. Runs ONCE, result reused.
SELECT * FROM users WHERE score > (SELECT avg(score) FROM users);

-- CORRELATED: references the outer row, so CONCEPTUALLY runs once per row.
SELECT u.name,
       (SELECT count(*) FROM orders o WHERE o.user_id = u.id) AS orders
FROM users u;
--                                              ^^^^ the outer row

-- ── "CONCEPTUALLY" IS DOING REAL WORK IN THAT SENTENCE ──────────────────
-- Modern planners often DECORRELATE this into a hash join with a grouped
-- aggregate — one pass instead of N lookups. But they cannot always:
--   * a LIMIT inside the subquery blocks it
--   * a volatile function (random(), now() in some contexts) blocks it
--   * an OR combining correlated and uncorrelated conditions blocks it
--   * some engines simply do not try
-- So the honest answer is: it depends on the planner, and you check.
EXPLAIN ANALYZE ...      -- "SubPlan" per row = NOT decorrelated
                         -- "Hash Join" / "Hash Aggregate" = decorrelated

-- ── THE SET-BASED REWRITE ───────────────────────────────────────────────
SELECT u.name, count(o.id) AS orders
FROM users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;
-- One pass over each table. Predictable, and portable across engines
-- that do not decorrelate. Note LEFT JOIN + count(o.id) so users with no
-- orders get 0 rather than disappearing.

-- ── SEVERAL CORRELATED COLUMNS: rewrite as ONE pre-aggregate ────────────
-- ✗ three correlated subqueries = potentially three passes per row
SELECT u.name,
       (SELECT count(*)   FROM orders WHERE user_id = u.id),
       (SELECT sum(total) FROM orders WHERE user_id = u.id),
       (SELECT max(created_at) FROM orders WHERE user_id = u.id)
FROM users u;
-- ✓ one pass
SELECT u.name, o.n, o.total, o.last_order
FROM users u
LEFT JOIN (SELECT user_id, count(*) n, sum(total) total,
                  max(created_at) last_order
           FROM orders GROUP BY user_id) o ON o.user_id = u.id;

-- ── EXISTS IS CORRELATED AND STILL CHEAP ────────────────────────────────
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id)
-- It SHORT-CIRCUITS: the planner stops at the first matching row instead
-- of counting them all. With an index on orders(user_id) that is one
-- index probe per user. This is why EXISTS is the right tool for "has
-- any" and count(*) > 0 is the wrong one.

-- ✗ the anti-pattern
WHERE (SELECT count(*) FROM orders WHERE user_id = u.id) > 0
-- Counts EVERY order to answer a yes/no question. On a user with 50,000
-- orders that is 50,000 rows read to learn "yes".

Part 3 — IN, EXISTS, and the NOT IN Landmine

-- ── IN vs EXISTS: usually the same plan ─────────────────────────────────
WHERE id IN     (SELECT user_id FROM orders)
WHERE EXISTS    (SELECT 1 FROM orders o WHERE o.user_id = u.id)
-- Postgres turns both into a semi-join. Choose on readability:
--   IN      when the subquery is a simple independent list
--   EXISTS  when it is correlated, or when NULLs are possible

-- ── NOT IN IS NOT THE MIRROR OF IN ──────────────────────────────────────
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);
-- If ANY orders.user_id is NULL → ZERO ROWS. Always. No error.
--
--   id NOT IN (1, 2, NULL)
--     ≡ id <> 1 AND id <> 2 AND id <> NULL
--     ≡ TRUE    AND TRUE    AND UNKNOWN
--     ≡ UNKNOWN                      → never TRUE → row dropped
--
-- The predicate can never be satisfied by any row, so the result is
-- empty. It is DATA-DEPENDENT: correct for months, then silently empty
-- the day one NULL arrives — usually long after review.

-- ✓ NOT EXISTS: NULL-safe, short-circuits, plans as an anti-join
SELECT * FROM users u WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- ✓ LEFT JOIN ... IS NULL: equivalent
SELECT u.* FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;          -- ⚠ must test a NOT NULL column (the PK).
                             --   Testing a nullable column also matches
                             --   rows that DID join.

-- ⚠ Even guarding the subquery is fragile:
WHERE id NOT IN (SELECT user_id FROM orders WHERE user_id IS NOT NULL)
-- Correct, but it relies on every future editor remembering why that
-- filter is there. NOT EXISTS needs no such note.

-- ── THE OTHER ASYMMETRY: DUPLICATES ─────────────────────────────────────
WHERE id IN (SELECT user_id FROM orders)     -- dedupes; no fan-out
JOIN orders o ON o.user_id = u.id            -- ONE ROW PER ORDER
-- A join where you meant a semi-join is the fan-out bug from the JOINs
-- lesson. If you find yourself adding DISTINCT after a join, you wanted
-- EXISTS.
Key insight: subqueries, CTEs and joins mostly express the same questions, and the planner is free to rewrite between them — so the choice is usually about readability rather than speed. The exceptions are the ones worth memorising, because they change correctness rather than cost: NOT IN returns nothing when the subquery yields a NULL, a join where you meant a semi-join multiplies rows, and a scalar subquery that starts returning two rows fails at runtime rather than at parse time. Optimise for the version a colleague can verify at a glance, then check EXPLAIN if it is hot.

Part 4 — CTEs

WITH high_spenders AS (
    SELECT user_id, sum(total) AS spend
    FROM orders GROUP BY user_id HAVING sum(total) > 1000
),
recent AS (
    SELECT DISTINCT user_id FROM orders
    WHERE created_at >= now() - interval '30 days'
)
SELECT u.name, hs.spend
FROM users u
JOIN high_spenders hs ON hs.user_id = u.id
JOIN recent        r  ON r.user_id  = u.id;

-- Reads top to bottom as a pipeline. The same logic as nested subqueries
-- three levels deep, but each step is named, individually runnable, and
-- reviewable.

-- ── THE OPTIMISATION FENCE — POSTGRES CHANGED THIS ──────────────────────
-- BEFORE Postgres 12: every CTE was MATERIALISED. It ran to completion
--   into a temp result, and outer predicates could NOT be pushed into it.
--   That made CTEs a deliberate optimiser barrier — and an accidental
--   performance trap for anyone using them purely for readability.
-- POSTGRES 12+: a CTE referenced ONCE and free of side effects is INLINED
--   like a subquery, so predicates push down normally.

WITH big AS MATERIALIZED     (SELECT ...)   -- force the fence
WITH big AS NOT MATERIALIZED (SELECT ...)   -- force inlining

-- WHEN TO FORCE MATERIALIZED:
--   * the CTE is referenced several times and is expensive to compute
--   * it contains a volatile function you want evaluated exactly once
--   * the planner's inlined choice is measurably worse
-- MySQL 8 inlines or materialises by cost; SQL Server always inlines.
-- Advice written before 2019 about "CTEs are slow in Postgres" is stale.

-- ── A CTE IS NOT A VARIABLE ─────────────────────────────────────────────
WITH t AS (SELECT ...) SELECT * FROM t UNION ALL SELECT * FROM t;
-- If inlined, this EXECUTES THE QUERY TWICE. Referencing a CTE twice does
-- not mean "compute once and reuse" unless it is materialised.

-- ── SCOPE ───────────────────────────────────────────────────────────────
-- A CTE is visible to the statement it belongs to and to LATER CTEs in
-- the same WITH — not to earlier ones (except in the recursive case).
-- It vanishes when the statement ends: no temp table, no cleanup.

-- ── WHEN A CTE IS NOT THE ANSWER ────────────────────────────────────────
-- If the same pipeline is recomputed by many queries, a VIEW gives the
-- same readability and one definition to maintain. If it is expensive
-- and the data is not real-time, a MATERIALIZED VIEW computes it once.
CREATE MATERIALIZED VIEW mv_high_spenders AS SELECT ...;
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_high_spenders;   -- no read lock

Part 5 — Recursive CTEs

WITH RECURSIVE subordinates AS (
    -- ANCHOR: the starting rows, evaluated once
    SELECT id, name, manager_id, 1 AS depth
    FROM employees WHERE id = :ceo_id

    UNION ALL                    -- ⚠ UNION ALL, not UNION (see below)

    -- RECURSIVE STEP: joins back to the CTE, repeats until it yields
    -- nothing
    SELECT e.id, e.name, e.manager_id, s.depth + 1
    FROM employees e
    JOIN subordinates s ON e.manager_id = s.id
)
SELECT * FROM subordinates ORDER BY depth, name;

-- ── HOW IT ACTUALLY EVALUATES ───────────────────────────────────────────
-- 1. run the anchor → working set
-- 2. run the recursive term against ONLY the rows added last iteration
-- 3. append them to the result; the new rows become the working set
-- 4. repeat until an iteration adds no rows
-- Despite the name it is ITERATIVE, not stack recursion — there is no
-- depth limit from the engine, only from your data.

-- ── UNION vs UNION ALL: A CORRECTNESS DECISION ──────────────────────────
-- UNION ALL keeps duplicates and is fast. On a genuine TREE (one parent
--   per node) duplicates cannot occur, so it is correct and cheaper.
-- UNION deduplicates against the whole accumulated result on every
--   iteration — which is how you terminate on a CYCLIC graph, at the
--   cost of a comparison per row per iteration.
-- With UNION ALL on a cyclic graph you get an INFINITE LOOP that
-- consumes memory until the connection dies. This is the classic way to
-- take out a database with a SELECT.

-- ── CYCLE PROTECTION FOR REAL GRAPHS ────────────────────────────────────
WITH RECURSIVE reachable AS (
    SELECT id, ARRAY[id] AS path, false AS cycle
    FROM nodes WHERE id = :start
  UNION ALL
    SELECT e.to_id, r.path || e.to_id, e.to_id = ANY(r.path)
    FROM edges e JOIN reachable r ON e.from_id = r.id
    WHERE NOT r.cycle                     -- stop expanding a cycle
      AND array_length(r.path, 1) < 50    -- and a hard depth guard
)
SELECT * FROM reachable WHERE NOT cycle;

-- Postgres 14+ has syntax for this:
WITH RECURSIVE r AS (...) CYCLE id SET is_cycle USING path
WITH RECURSIVE r AS (...) SEARCH DEPTH FIRST BY id SET ordercol

-- ── WHAT THESE ARE FOR ──────────────────────────────────────────────────
-- org charts · category and menu trees · threaded comments ·
-- bill-of-materials explosion · folder hierarchies · permission
-- inheritance · graph reachability · generating series and calendars

WITH RECURSIVE days AS (
    SELECT '2026-01-01'::date AS d
  UNION ALL
    SELECT d + 1 FROM days WHERE d < '2026-12-31'
)
SELECT * FROM days;      -- a date axis without generate_series

-- ── THE ALTERNATIVES, WHEN TREES ARE READ-HEAVY ─────────────────────────
-- Recursive CTEs cost a join per LEVEL. For deep trees read constantly:
--   * MATERIALISED PATH  path text '1/4/9/'  → WHERE path LIKE '1/4/%'
--                        one index scan for a whole subtree
--   * CLOSURE TABLE      (ancestor, descendant, depth) rows
--                        instant queries, more write cost
--   * ltree              a Postgres extension for exactly this
-- The trade is always read speed against write complexity.

Part 6 — LATERAL and Data-Modifying CTEs

-- ── LATERAL: a subquery in FROM that CAN see the outer row ──────────────
SELECT u.name, r.*
FROM users u
CROSS JOIN LATERAL (
  SELECT id, total, created_at FROM orders o
  WHERE o.user_id = u.id                -- ← a plain derived table
  ORDER BY o.created_at DESC LIMIT 3    --   cannot do this
) r;
-- "The 3 most recent orders per user." A normal subquery in FROM is
-- evaluated once, independently; LATERAL is evaluated per outer row.
-- LEFT JOIN LATERAL (...) ON true       keeps users with no orders.
-- SQL Server spells it CROSS APPLY / OUTER APPLY.

-- ── WHY IT BEATS A WINDOW FUNCTION HERE ─────────────────────────────────
-- row_number() OVER (PARTITION BY user_id ...) ranks EVERY order in the
-- table and then discards all but three per user. With an index on
-- orders(user_id, created_at DESC), LATERAL reads exactly 3 rows per
-- user. On a large child table that is the difference between seconds
-- and milliseconds.
-- The window function wins when you need a rank over everything anyway.

-- ── DATA-MODIFYING CTEs (Postgres) ──────────────────────────────────────
WITH archived AS (
    DELETE FROM orders WHERE created_at < :cutoff
    RETURNING *
)
INSERT INTO orders_archive SELECT * FROM archived;
-- Move rows in ONE statement, atomically, with one pass over the data.

WITH new_user AS (
    INSERT INTO users (email) VALUES (:email) RETURNING id
)
INSERT INTO profiles (user_id, plan)
SELECT id, 'free' FROM new_user;
-- Insert a parent and its child without a round trip in between.

-- ── THE RULE THAT SURPRISES EVERYONE ────────────────────────────────────
-- Every sub-statement sees the SAME SNAPSHOT of the data. The CTE's
-- changes are NOT visible to sibling statements in the same query.
WITH upd AS (UPDATE accounts SET balance = balance - 100
             WHERE id = 1 RETURNING *)
SELECT balance FROM accounts WHERE id = 1;
-- Returns the OLD balance. Read the new value from the CTE's RETURNING,
-- never by re-selecting the table.

-- And execution order between sibling CTEs is NOT guaranteed. Two CTEs
-- modifying the same rows have undefined behaviour — do not rely on
-- "the first one runs first".

-- ── A GOOD USE: A QUEUE CLAIM ───────────────────────────────────────────
WITH claimed AS (
  SELECT id FROM jobs WHERE status = 'pending'
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED                  -- concurrent workers do not
  LIMIT 10                                -- block each other
)
UPDATE jobs SET status = 'running', started_at = now()
FROM claimed WHERE jobs.id = claimed.id
RETURNING jobs.*;
-- Claim and return work atomically. SKIP LOCKED is what makes several
-- workers able to poll the same table without contention. See Isolation
-- Levels & Locking.

Interview Questions

Beginner: What is the difference between a correlated and a non-correlated subquery?

A non-correlated subquery is self-contained — it does not reference the outer query, so it can be evaluated once and its result reused for every row. A correlated subquery references a column from the outer row, so conceptually it has to be re-evaluated for each of those rows. The classic example is counting each user's orders by referencing u.id inside the subquery.

The performance implication is the usual reason for the question, and the honest answer is that it depends on the planner. Modern optimisers frequently decorrelate a simple correlated subquery into a join with a grouped aggregate, turning N lookups into one pass — but they cannot always do it, and a LIMIT or a volatile function inside the subquery typically blocks the rewrite. So the safe approach is to write the set-based version with a join and GROUP BY when the query is hot, and to check EXPLAIN rather than assume: a SubPlan node executing per row means it was not decorrelated. EXISTS is the interesting exception — it is correlated by definition and still cheap, because it stops at the first matching row instead of evaluating all of them.

Beginner: Why prefer NOT EXISTS over NOT IN?

Because NOT IN breaks in the presence of NULLs, and it breaks silently. id NOT IN (1, 2, NULL) expands to a chain of inequality tests joined by AND, and the comparison against NULL is UNKNOWN, so the whole predicate can never be TRUE for any row — the query returns nothing at all. There is no error and no warning, and because it depends on the data rather than the query, it typically works for months and then returns an empty result the day the first NULL appears in that column.

NOT EXISTS is unaffected because it tests row existence rather than value equality, it short-circuits at the first match, and planners recognise it as an anti-join. A left join with an IS NULL check on the right side is an equally correct third formulation, with the caveat that you must test a column that is NOT NULL in the right table — usually its primary key — since testing a nullable column also matches rows that did join. You can make NOT IN safe by filtering NULLs out of the subquery, but that relies on every future editor understanding why the filter is there, whereas NOT EXISTS needs no such note.

Mid: What is a CTE, and is it faster or slower than a subquery?

A CTE is a named subquery defined in a WITH clause and referenced by the main statement. Its primary value is readability: a three-level nested subquery becomes a top-to-bottom pipeline of named steps, each of which can be run and reviewed independently, which matters a great deal for queries people have to maintain.

On performance the answer has changed, and stale advice is still widely repeated. Before Postgres 12, every CTE was an optimisation fence: it was materialised into a temporary result and outer predicates could not be pushed down into it, so using CTEs purely for readability could make a query dramatically slower. From Postgres 12 onward a CTE referenced once and free of side effects is inlined like an ordinary subquery, so predicates push down normally and the choice is usually performance-neutral. You can still force either behaviour with AS MATERIALIZED or AS NOT MATERIALIZED.

Two things remain worth knowing. Materialising deliberately is right when a CTE is expensive and referenced several times, or when it contains a volatile function that must be evaluated exactly once. And a CTE is not a variable — if it is inlined and referenced twice, the query underneath executes twice. If the same pipeline is used across many queries, a view is the better tool, and if it is expensive and does not need to be real-time, a materialised view.

Mid: When would you use a recursive CTE, and what can go wrong?

For hierarchical and graph-shaped data where the depth is not known in advance: org charts, category and menu trees, threaded comments, bill-of-materials explosions, folder structures, permission inheritance, and graph reachability. The structure is an anchor query that produces the starting rows, then UNION ALL a recursive term that joins the source table back to the CTE, repeating until an iteration produces no new rows. Despite the name it is iterative rather than stack-based, so there is no engine-imposed depth limit.

The failure that matters is cycles. UNION ALL keeps duplicates, which is correct and fast on a genuine tree where each node has one parent, but on a cyclic graph it never terminates — the query loops, accumulating rows until it exhausts memory or the connection dies. That is one of the few ways a plain SELECT can take down a database. UNION deduplicates against the accumulated result and therefore terminates, at the cost of a comparison per row per iteration. For real graphs I would carry a path array and stop when a node repeats, plus an absolute depth guard so that one bad row of data cannot become an outage; Postgres 14 added CYCLE and SEARCH clauses that express this directly.

The other consideration is cost. A recursive CTE pays a join per level, so for deep trees read constantly it is worth denormalising into a materialised path or a closure table, which turn a subtree query into a single index scan at the price of more work on writes.

Senior: When is LATERAL the right tool over a window function?

LATERAL lets a subquery in FROM reference columns from the rows to its left, so it is evaluated per outer row rather than once independently. That makes it the natural way to express "the top N per group" when the source table is large: with an index on (user_id, created_at DESC), a lateral subquery with ORDER BY … LIMIT 3 reads exactly three rows per user. The window-function equivalent computes row_number() over every order in the table and then discards everything above rank three, so it does work proportional to the whole child table rather than to the result. On a hundred users and fifty million orders that is the difference between milliseconds and a full scan.

The window function is better when you genuinely need a ranking over everything — percentiles, running totals, comparisons to a neighbouring row — or when there is no useful index to seek with, in which case one sorted pass beats N lookups. It is also the more portable choice; LATERAL exists everywhere but is spelled CROSS APPLY in SQL Server.

The general shape of the decision is the same one that governs nested loops versus hash joins: a per-outer-row lookup wins when the outer set is small and the lookup is indexed, and loses badly otherwise. So I would reach for LATERAL when the outer side is a bounded set — a page of users, a list of categories — and check EXPLAIN before using it on an unbounded one.

Senior: What are data-modifying CTEs good for, and what is the trap?

They let several write operations, and reads of what those writes produced, happen in a single atomic statement. Archiving is the canonical example: a DELETE … RETURNING * in a CTE feeding an INSERT moves rows in one pass, atomically, without round-tripping the data through the application. Inserting a parent and its child with the generated id, or claiming work from a queue and returning it, are the other common shapes — the queue case combining FOR UPDATE SKIP LOCKED so that concurrent workers do not block one another.

The trap is the snapshot rule. Every sub-statement in the query sees the same snapshot of the data as of the start of the statement, so a CTE's modifications are not visible to its siblings. Updating a balance in a CTE and then selecting that row in the main query returns the old value, which looks like a bug in the database and is in fact defined behaviour. The correct pattern is always to read the new state from the modifying CTE's RETURNING clause rather than by re-querying the table.

The related hazard is that execution order between sibling CTEs is not guaranteed, so two CTEs touching the same rows have genuinely undefined behaviour — the classic mistake being an UPDATE and a DELETE against overlapping sets and an assumption about which wins. When ordering matters, the honest answer is separate statements inside an explicit transaction, which costs one round trip and removes the ambiguity entirely. It is also worth noting this is a Postgres feature; most other engines do not allow data modification inside a CTE at all, so it is portability you are spending.

🏋️ Exercises

1 (easy): This query returned 4,000 rows last week and returns 0 today. Nothing changed in the code.
Solution 
-- ✗ THE QUERY
SELECT * FROM users
WHERE id NOT IN (SELECT user_id FROM orders WHERE status = 'cancelled');

-- ── WHAT HAPPENED ───────────────────────────────────────────────────────
-- Someone inserted a cancelled order with a NULL user_id — a guest
-- checkout, an import, a soft-deleted account. One NULL is enough.
--
--   id NOT IN (7, 12, NULL)
--     ≡ id <> 7 AND id <> 12 AND id <> NULL
--     ≡ TRUE   AND TRUE     AND UNKNOWN
--     ≡ UNKNOWN                          → never TRUE → every row dropped
--
-- No error. No warning. The result is simply empty, and the cause is in
-- the DATA rather than the query — which is why it passed review and why
-- it broke a month later.

-- ── PROVE IT ────────────────────────────────────────────────────────────
SELECT count(*) FROM orders WHERE status='cancelled' AND user_id IS NULL;
-- 1

-- ── ✓ FIX: NOT EXISTS ───────────────────────────────────────────────────
SELECT u.* FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.user_id = u.id AND o.status = 'cancelled');
-- NULL-safe by construction: it asks "does a matching row exist?", not
-- "is this value unequal to every value in that list?". It also
-- short-circuits at the first match and plans as an anti-join.

-- ── ✓ ALTERNATIVE: LEFT JOIN ... IS NULL ────────────────────────────────
SELECT u.* FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'cancelled'
WHERE o.id IS NULL;             -- ⚠ test the PRIMARY KEY. Testing a
                                --   nullable column (o.cancelled_at)
                                --   also matches rows that DID join.
-- Note the status condition is in ON, not WHERE — in WHERE it would
-- undo the LEFT JOIN (see the JOINs lesson).

-- ── ⚠ THE "FIX" THAT IS NOT ONE ─────────────────────────────────────────
WHERE id NOT IN (SELECT user_id FROM orders
                 WHERE status='cancelled' AND user_id IS NOT NULL)
-- Correct today. It relies on every future editor knowing why that guard
-- exists — and it will be deleted in a refactor as "redundant".

-- ── THE STRUCTURAL FIX ──────────────────────────────────────────────────
ALTER TABLE orders ALTER COLUMN user_id SET NOT NULL;
-- If an order must have a user, say so. A nullable column is a branch
-- every future query has to remember.
2 (easy): Rewrite these three subqueries into their better forms.
Solution 
-- ── 1. COUNTING TO ANSWER YES/NO ────────────────────────────────────────
-- ✗
SELECT * FROM users u
WHERE (SELECT count(*) FROM orders WHERE user_id = u.id) > 0;
-- Reads EVERY order for every user. A user with 50,000 orders costs
-- 50,000 row reads to establish "yes".
-- ✓
SELECT * FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
-- Stops at the FIRST match. With an index on orders(user_id) that is one
-- index probe per user.

-- ── 2. A JOIN WHERE A SEMI-JOIN WAS MEANT ───────────────────────────────
-- ✗
SELECT DISTINCT u.* FROM users u JOIN orders o ON o.user_id = u.id;
-- The join produces one row PER ORDER, then DISTINCT throws the extras
-- away — the database materialises 5M rows to return 100K.
-- The DISTINCT is the tell.
-- ✓
SELECT u.* FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
-- No duplication is ever produced, so none has to be removed.

-- ── 3. THREE CORRELATED SUBQUERIES OVER ONE TABLE ───────────────────────
-- ✗
SELECT u.name,
       (SELECT count(*)        FROM orders WHERE user_id = u.id) AS n,
       (SELECT sum(total)      FROM orders WHERE user_id = u.id) AS spend,
       (SELECT max(created_at) FROM orders WHERE user_id = u.id) AS last
FROM users u;
-- Potentially three passes over orders per user.
-- ✓
SELECT u.name,
       COALESCE(o.n, 0)     AS n,
       COALESCE(o.spend, 0) AS spend,
       o.last
FROM users u
LEFT JOIN (
  SELECT user_id, count(*) AS n, sum(total) AS spend,
         max(created_at) AS last
  FROM orders GROUP BY user_id
) o ON o.user_id = u.id;
-- ONE pass over orders, aggregated once. LEFT JOIN + COALESCE keeps
-- users with no orders and reports 0 rather than NULL.

-- ── VERIFY RATHER THAN ASSUME ───────────────────────────────────────────
EXPLAIN ANALYZE ...
-- "SubPlan" executing per row  → the planner did NOT decorrelate
-- "Hash Join" / "HashAggregate" → it did, and the rewrite may be moot
-- Postgres decorrelates simple cases well; a LIMIT or a volatile
-- function inside the subquery blocks it.
3 (medium): Turn this nested query into a readable CTE pipeline, and decide on materialisation.
Solution 
-- ✗ BEFORE — read it inside-out
SELECT * FROM (
  SELECT u.id, u.name, o.spend,
         rank() OVER (ORDER BY o.spend DESC) AS rnk
  FROM users u
  JOIN (SELECT user_id, sum(total) AS spend FROM orders
        WHERE created_at >= now() - interval '90 days'
        GROUP BY user_id HAVING sum(total) > 1000) o ON o.user_id = u.id
  WHERE u.id NOT IN (SELECT user_id FROM refunds
                     WHERE created_at >= now() - interval '90 days')
) t WHERE rnk <= 100;

-- ✓ AFTER — reads top to bottom
WITH recent_orders AS (
    SELECT user_id, sum(total) AS spend
    FROM orders
    WHERE created_at >= now() - interval '90 days'
    GROUP BY user_id
    HAVING sum(total) > 1000
),
refunders AS (
    SELECT DISTINCT user_id FROM refunds
    WHERE created_at >= now() - interval '90 days'
      AND user_id IS NOT NULL
),
ranked AS (
    SELECT u.id, u.name, r.spend,
           rank() OVER (ORDER BY r.spend DESC) AS rnk
    FROM users u
    JOIN recent_orders r ON r.user_id = u.id
    WHERE NOT EXISTS (SELECT 1 FROM refunders f WHERE f.user_id = u.id)
)
SELECT * FROM ranked WHERE rnk <= 100 ORDER BY rnk;

-- ── WHAT CHANGED BEYOND FORMATTING ──────────────────────────────────────
-- 1. NOT IN → NOT EXISTS. The original returns ZERO ROWS the moment one
--    refunds.user_id is NULL. That is a correctness fix, not cosmetics.
-- 2. Each step is independently runnable:  SELECT * FROM recent_orders;
--    Debugging a 6-line CTE beats debugging a 3-level nest.
-- 3. The window function is isolated, so it is obvious it ranks the
--    filtered set rather than everything.

-- ── MATERIALIZED OR NOT? ────────────────────────────────────────────────
-- Postgres 12+ INLINES a CTE referenced once and free of side effects,
-- so predicates push down and this is performance-neutral versus the
-- nested version. Pre-12 every CTE was a fence — advice written before
-- 2019 saying "CTEs are slow in Postgres" is stale.
--
-- Force it when you have a reason:
WITH recent_orders AS MATERIALIZED (...)
--   * referenced several times and expensive to recompute
--   * contains a volatile function that must run exactly once
--   * the inlined plan measures worse
WITH x AS NOT MATERIALIZED (...)     -- force inlining

-- ⚠ A CTE IS NOT A VARIABLE. If it is inlined and referenced twice, the
--   underlying query RUNS TWICE.

-- ── AND IF THIS PIPELINE IS USED BY MANY QUERIES ────────────────────────
CREATE VIEW recent_high_spenders AS SELECT ...;
-- One reviewed definition instead of fifteen copies drifting apart. If
-- it is expensive and need not be real-time:
CREATE MATERIALIZED VIEW mv_high_spenders AS ...;
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_high_spenders;
4 (medium): Write a recursive CTE for an org chart, then make it safe for a graph with cycles.
Solution 
-- ── THE TREE CASE ───────────────────────────────────────────────────────
WITH RECURSIVE org AS (
    SELECT id, name, manager_id, 1 AS depth,
           name::text AS path
    FROM employees WHERE id = :root          -- ANCHOR: runs once
  UNION ALL
    SELECT e.id, e.name, e.manager_id, o.depth + 1,
           o.path || ' > ' || e.name
    FROM employees e
    JOIN org o ON e.manager_id = o.id        -- RECURSIVE: joins back
)
SELECT repeat('  ', depth - 1) || name AS tree, depth, path
FROM org ORDER BY path;

-- HOW IT EVALUATES: run the anchor → working set. Run the recursive term
-- against ONLY the rows added in the last iteration. Append. Repeat until
-- an iteration adds nothing. It is ITERATIVE, not stack recursion.

-- ── AGGREGATING UP THE TREE ─────────────────────────────────────────────
SELECT o.id, o.name, count(*) - 1 AS total_reports
FROM employees e
CROSS JOIN LATERAL (WITH RECURSIVE sub AS (...) SELECT ...) o
GROUP BY o.id, o.name;

-- ── THE CYCLE PROBLEM ───────────────────────────────────────────────────
-- Employee A reports to B, B reports to A. Bad data, a circular
-- reporting line, or a genuine graph (permissions, dependencies).
-- With UNION ALL this NEVER TERMINATES: it accumulates rows until memory
-- is exhausted and the connection dies. A plain SELECT taking down a
-- database.

-- ── ✓ FIX 1: CARRY THE PATH ─────────────────────────────────────────────
WITH RECURSIVE org AS (
    SELECT id, name, manager_id, 1 AS depth,
           ARRAY[id] AS path, false AS is_cycle
    FROM employees WHERE id = :root
  UNION ALL
    SELECT e.id, e.name, e.manager_id, o.depth + 1,
           o.path || e.id,
           e.id = ANY(o.path)                -- have we been here before?
    FROM employees e
    JOIN org o ON e.manager_id = o.id
    WHERE NOT o.is_cycle                     -- stop expanding this branch
      AND o.depth < 50                       -- AND a hard guard
)
SELECT * FROM org WHERE NOT is_cycle;
-- BOTH protections. The path array is precise; the depth limit is the
-- backstop for the case the path logic misses. One bad row should never
-- be able to become an outage.

-- ── ✓ FIX 2: UNION INSTEAD OF UNION ALL ─────────────────────────────────
-- UNION deduplicates against the accumulated result each iteration, so a
-- cycle terminates naturally. Costs a comparison per row per iteration,
-- and it does not tell you a cycle EXISTS — it just stops.

-- ── ✓ FIX 3: POSTGRES 14+ SYNTAX ────────────────────────────────────────
WITH RECURSIVE org AS (...)
CYCLE id SET is_cycle USING path
SEARCH DEPTH FIRST BY id SET ordercol
SELECT * FROM org ORDER BY ordercol;

-- ── WHEN A RECURSIVE CTE IS THE WRONG TOOL ──────────────────────────────
-- It costs a join per LEVEL. For deep trees queried constantly:
--   MATERIALISED PATH   path text '1/4/9/'  → WHERE path LIKE '1/4/%'
--                       a whole subtree in ONE index scan
--   CLOSURE TABLE       (ancestor, descendant, depth)
--                       instant reads, more write cost
--   ltree               a Postgres extension built for this
-- The trade is always read speed against write complexity — worth it
-- when the tree changes rarely and is read constantly, which describes
-- most category trees and permission hierarchies.
5 (hard): This CTE-based archive job produces wrong results. Find the bugs.
Solution 
-- ✗ BEFORE
WITH to_archive AS (
    SELECT * FROM orders WHERE created_at < :cutoff
),
archived AS (
    INSERT INTO orders_archive SELECT * FROM to_archive RETURNING id
),
deleted AS (
    DELETE FROM orders WHERE created_at < :cutoff RETURNING id
)
SELECT (SELECT count(*) FROM archived) AS archived_count,
       (SELECT count(*) FROM orders WHERE created_at < :cutoff) AS remaining;

-- ── BUG 1: SIBLING EXECUTION ORDER IS UNDEFINED ─────────────────────────
-- Nothing guarantees `archived` runs before `deleted`. Both read the same
-- snapshot, so they happen to agree here — but the moment the predicates
-- differ, or a row is concurrently inserted, the two sets diverge and
-- rows are deleted without being archived. Silent data loss.

-- ── BUG 2: THE SNAPSHOT RULE ────────────────────────────────────────────
(SELECT count(*) FROM orders WHERE created_at < :cutoff)
-- Reads the table AS IT WAS AT STATEMENT START. It reports the count
-- BEFORE the delete, always. Looks like the delete did nothing.
-- ⇒ Never re-select a table modified in the same statement. Read the new
--   state from RETURNING.

-- ── BUG 3: to_archive IS RE-EXECUTED, NOT REUSED ────────────────────────
-- Referenced once, so Postgres 12+ INLINES it. The DELETE re-evaluates
-- its own predicate independently. If a row is inserted between the two
-- evaluations within the statement's visibility, the sets differ.
-- A CTE is not a snapshot variable.

-- ── BUG 4: SELECT * INTO A DIFFERENT TABLE ──────────────────────────────
INSERT INTO orders_archive SELECT * FROM to_archive;
-- Positional. Add a column to `orders` and every archived row silently
-- shifts into the wrong columns. Name them.

-- ── ✓ FIX A: ONE CTE, DELETE FEEDS INSERT ───────────────────────────────
WITH archived AS (
    DELETE FROM orders
    WHERE created_at < :cutoff
    RETURNING id, user_id, total, created_at
)
INSERT INTO orders_archive (id, user_id, total, created_at)
SELECT id, user_id, total, created_at FROM archived;
-- ONE set of rows, produced once, atomically. Impossible for the archive
-- and the delete to disagree — the delete IS the source.
-- Get the count from the statement's own row count, not a re-select.

-- ✓ Chunked, so it does not lock 40M rows (see the DML lesson):
WITH batch AS (
    SELECT id FROM orders WHERE created_at < :cutoff
    ORDER BY id LIMIT 10000 FOR UPDATE SKIP LOCKED
),
archived AS (
    DELETE FROM orders WHERE id IN (SELECT id FROM batch)
    RETURNING id, user_id, total, created_at
)
INSERT INTO orders_archive (id, user_id, total, created_at)
SELECT id, user_id, total, created_at FROM archived;
-- repeat until 0 rows affected

-- ── ✓ FIX B: EXPLICIT STATEMENTS, WHEN ORDER MUST BE GUARANTEED ─────────
BEGIN;
INSERT INTO orders_archive (id, user_id, total, created_at)
SELECT id, user_id, total, created_at FROM orders WHERE created_at < :cutoff;
DELETE FROM orders WHERE created_at < :cutoff;
COMMIT;
-- Costs a round trip and removes all ambiguity. When ordering between
-- writes matters, this is the honest answer — data-modifying CTEs are
-- for cases where ONE set of rows flows through, not for sequencing.

-- ── VERIFY ──────────────────────────────────────────────────────────────
SELECT count(*) FROM orders WHERE created_at < :cutoff;   -- separate
                                                          -- statement: 0
6 (hard): Design the query layer for a category tree that is read constantly and written rarely.
Solution 
-- REQUIREMENT: 50,000 categories, up to 8 levels. Every product page
-- needs the breadcrumb; every category page needs the full subtree.
-- ~10,000 reads/sec, a few writes per day.

-- ── OPTION A: ADJACENCY LIST + RECURSIVE CTE ────────────────────────────
CREATE TABLE categories (id int PRIMARY KEY, parent_id int, name text);

WITH RECURSIVE subtree AS (
    SELECT id, parent_id, name, 1 AS depth FROM categories WHERE id = :id
  UNION ALL
    SELECT c.id, c.parent_id, c.name, s.depth + 1
    FROM categories c JOIN subtree s ON c.parent_id = s.id
    WHERE s.depth < 20
)
SELECT * FROM subtree;
-- ✓ trivial writes: one row, one parent_id. Always consistent.
-- ✗ a join PER LEVEL, every read. At 10k reads/sec with 8 levels that is
--   80k index lookups a second for data that changes twice a week.
--   Paying a traversal cost repeatedly for a structure that is static.

-- ── OPTION B: MATERIALISED PATH  ← what I would ship ────────────────────
ALTER TABLE categories ADD COLUMN path text;      -- '/1/7/23/'
CREATE INDEX ON categories (path text_pattern_ops);

-- whole subtree: ONE index range scan, no recursion
SELECT * FROM categories WHERE path LIKE '/1/7/%';
-- breadcrumb: no query at all — parse the ids out of the path, or
SELECT * FROM categories
WHERE id = ANY(string_to_array(trim(both '/' from :path), '/')::int[])
ORDER BY array_position(...);
-- depth: length(path) - length(replace(path,'/','')) - 1

-- writes must maintain it — a trigger, so it cannot be forgotten:
CREATE FUNCTION set_path() RETURNS trigger AS $$
BEGIN
  NEW.path := COALESCE(
    (SELECT path FROM categories WHERE id = NEW.parent_id), '/')
    || NEW.id || '/';
  RETURN NEW;
END $$ LANGUAGE plpgsql;
-- ⚠ MOVING a subtree must rewrite descendants' paths:
UPDATE categories SET path = :new_prefix || substr(path, length(:old)+1)
WHERE path LIKE :old || '%';
-- Rare, bounded, and correct. This is the write cost you are buying
-- read speed with.

-- Postgres has a purpose-built type for this:
CREATE EXTENSION ltree;
ALTER TABLE categories ADD COLUMN path ltree;
CREATE INDEX ON categories USING GIST (path);
SELECT * FROM categories WHERE path <@ 'root.electronics';   -- descendants
SELECT * FROM categories WHERE path @> 'root.a.b.c';         -- ancestors

-- ── OPTION C: CLOSURE TABLE ─────────────────────────────────────────────
CREATE TABLE category_paths (
  ancestor int, descendant int, depth int,
  PRIMARY KEY (ancestor, descendant));
-- one row per ancestor-descendant PAIR, including self at depth 0
SELECT c.* FROM category_paths p JOIN categories c ON c.id = p.descendant
WHERE p.ancestor = :id;                        -- subtree: one index scan
WHERE p.descendant = :id ORDER BY depth DESC;  -- breadcrumb: same
-- ✓ the fastest reads in both directions, and it handles a DAG (a
--   category with several parents) which a path string cannot.
-- ✗ O(depth) rows per node; a move rewrites a subtree's worth of pairs.

-- ── THE DECISION ────────────────────────────────────────────────────────
--                    reads      writes        handles DAG   complexity
-- adjacency+CTE      slow       trivial       yes           lowest
-- materialised path  fast       moderate      no            low
-- closure table      fastest    highest       yes           highest
--
-- 10,000 reads/sec against a few writes a day makes this an easy call:
-- pay on WRITE. Materialised path (via ltree) — near-closure-table read
-- speed at a fraction of the write complexity, and a strict tree does
-- not need DAG support.

-- ── AND THE LAYER ABOVE ─────────────────────────────────────────────────
-- 50,000 categories is a few MB. The real answer for 10k reads/sec is to
-- cache the whole tree in application memory and rebuild it on change
-- notification — the database should not see this traffic at all. Choose
-- the storage that makes the CACHE REBUILD cheap and correct, which is
-- again the materialised path: one indexed scan loads everything in
-- order.
--
-- Denormalising is right when the read/write ratio justifies it AND the
-- maintenance is enforced by the schema (a trigger) rather than by
-- convention. Both conditions hold here.

🎯 Key Takeaways

  • Subqueries come in scalar, IN/EXISTS, derived-table and row-constructor forms, each legal in different clauses.
  • A correlated subquery references the outer row; planners often decorrelate it, but a LIMIT or volatile function blocks that — check EXPLAIN.
  • EXISTS short-circuits at the first match, so it beats count(*) > 0 and avoids the fan-out of a join.
  • NOT IN returns zero rows if the subquery yields any NULL — always prefer NOT EXISTS.
  • A scalar subquery fails at runtime if it ever returns two rows, and silently yields NULL if it returns none.
  • CTEs name pipeline steps; since Postgres 12 single-use CTEs are inlined, so pre-2019 "CTEs are a fence" advice is stale.
  • A CTE is not a variable — an inlined CTE referenced twice executes twice.
  • Recursive CTEs traverse trees and graphs; UNION ALL over a cycle loops forever, so carry a path array and a depth guard.
  • LATERAL beats a window function for top-N per group when the outer set is small and the child table is indexed.
  • Data-modifying CTEs are atomic but all see the same snapshot, so read results from RETURNING and never rely on sibling execution order.
