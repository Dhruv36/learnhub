Indexes & Query Plans Advanced

What you'll master: what a B-tree physically is and why that shape dictates every rule you have been told to memorise, the leftmost-prefix rule derived rather than recited, why an index on a low-selectivity column is correctly ignored, the heap-fetch cost that makes index-only scans worth engineering for, how to read EXPLAIN (ANALYZE, BUFFERS) including the loops multiplier that misleads nearly everyone, why the planner picks a sequential scan and is usually right, how statistics and correlated predicates cause bad plans, the index types beyond B-tree and when each is the answer, and how to add and remove indexes in production without locking a live table. Prerequisites: JOINs and Schema Design. Examples are PostgreSQL; the concepts carry to MySQL/InnoDB with differences called out.

Part 1 — What a B-tree Actually Is

CREATE INDEX idx_users_email ON users (email);

-- A B+tree is a shallow, balanced tree of PAGES (8KB each in Postgres).
-- Internal pages hold separator keys and child pointers; LEAF pages hold
-- the indexed values in SORTED order, each with a pointer to the row.
--
--                    [ f | m | s ]                    root
--                   /    |    |   \
--          [b|d]  [g|j]  [n|p]  [t|w]                 internal
--          /  |     |      |       \
--       leaf leaf  leaf   leaf     leaf  ← sorted, doubly linked
--       (a..) (e..) (g..)  (n..)   (t..)
--
-- TWO PROPERTIES EXPLAIN EVERYTHING ELSE:
--   1. it is SORTED       → equality, ranges, prefixes and ORDER BY all
--                           work; anything needing a different order does
--                           not
--   2. it is BALANCED     → every lookup costs the same, ~3-4 page reads
--
-- ── HOW SHALLOW? THE ARITHMETIC MATTERS ─────────────────────────────────
-- An 8KB page holds roughly 200-400 entries for a typical key. So:
--   depth 1 → ~300 rows        depth 3 → ~27,000,000 rows
--   depth 2 → ~90,000 rows     depth 4 → ~8,100,000,000 rows
-- A 100-million-row table is a 4-level tree. Finding one row costs FOUR
-- page reads, and the top levels are permanently cached — so in practice
-- it is one disk read, versus ~12 million page reads for a full scan.
--
-- CONSEQUENCE: index lookups do not meaningfully get slower as tables
-- grow. Going from 1M to 100M rows adds ONE level. This is why "it was
-- fast in dev with 10k rows" tells you nothing about a sequential scan,
-- but almost everything about an index scan.

-- ── WHAT IT COSTS ───────────────────────────────────────────────────────
-- Every INSERT, DELETE, and every UPDATE OF AN INDEXED COLUMN must
-- maintain every affected index: locate the leaf, insert in sorted
-- position, split the page if full. Six indexes means an insert does
-- seven write operations, and each is a separate place to dirty a page.
-- Indexes are a deliberate trade of write throughput and storage for
-- read latency. "Add an index" is never free advice.
📐 Stop memorising index rules and derive them. Every rule in this lesson follows from "the leaves are sorted by the indexed expression, in the column order given". Why does LIKE '%son' fail? Because a sorted structure cannot find entries by their suffix. Why does LOWER(email) fail? Because the tree is sorted by email, not by its lowercase form. Why is the leftmost prefix required? Because (a, b) sorts by b only within a fixed a. One property, all the rules.

Part 2 — What an Index Can and Cannot Serve

-- ✓ SARGABLE (Search ARGument ABLE — the planner can descend the tree)
WHERE email = 'a@b.com'                 -- equality: one descent
WHERE email > 'm'                       -- range: descend, then walk leaves
WHERE email LIKE 'asha%'                -- LEFT-anchored: a prefix IS a range
WHERE created_at >= :d AND created_at < :d + 1   -- half-open range
WHERE id IN (3, 17, 92)                 -- several descents
ORDER BY created_at DESC LIMIT 10       -- walk the leaves backwards, stop
                                        -- at 10. No sort, no full read.

-- ✗ NOT SARGABLE, and exactly why
WHERE LOWER(email) = 'a@b.com'          -- tree sorted by email, not
                                        -- lower(email)
WHERE email LIKE '%gmail.com'           -- no prefix → no subtree to enter
WHERE score + 10 > 100                  -- sorted by score, not score+10
WHERE EXTRACT(year FROM created_at) = 2026
WHERE age::text = '42'                  -- cast on the column side
WHERE status != 'active'                -- matches most rows; see Part 3

-- ── THE FIXES ───────────────────────────────────────────────────────────
CREATE INDEX ON users (lower(email));   -- expression index: the tree is
WHERE lower(email) = 'a@b.com';         -- now sorted by the expression,
                                        -- which must match EXACTLY

WHERE score > 90                        -- move arithmetic to the constant
WHERE created_at >= '2026-01-01'        -- rewrite the function away;
  AND created_at <  '2027-01-01'        -- half-open avoids every
                                        -- boundary bug (see Aggregates)

CREATE INDEX ON users USING gin (email gin_trgm_ops);  -- trigram index
WHERE email LIKE '%gmail.com';          -- genuinely needs a different
                                        -- index TYPE, not a rewrite

-- ── THE INVISIBLE ONE: TYPE MISMATCH ────────────────────────────────────
-- user_id is bigint, the driver sends a string:
WHERE user_id = '12345'                 -- fine: literal is cast, index used
WHERE varchar_col = 12345               -- ⚠ MySQL coerces the COLUMN to a
                                        -- number → index unusable, and it
                                        -- tells you nothing
-- Silent, plan-only failures like this are why you read EXPLAIN rather
-- than reasoning about what "should" happen.

Part 3 — Selectivity: Why a Correct Index Gets Ignored

-- "I added the index and Postgres still does a Seq Scan. It's broken."
-- It is not broken. It did arithmetic you did not.

-- ── THE HEAP FETCH ──────────────────────────────────────────────────────
-- An index scan is TWO steps: walk the tree to get row pointers, then
-- FETCH EACH ROW from the table (the "heap"). Those fetches are in index
-- order, which is RANDOM order with respect to the table's physical
-- layout. Random single-page reads are far more expensive per row than
-- the sequential read the scan uses.
--
-- So the planner compares:
--   Seq Scan   = read all N pages sequentially (cheap per page)
--   Index Scan = ~4 index pages + one random heap fetch per matching row
--
-- SELECTIVITY is the fraction of rows matched, and it decides the winner.

--   matches      typical choice
--   ─────────    ─────────────────────────────────────────────
--   0.01%        Index Scan — obviously
--   1%           Index Scan
--   ~5-10%       Bitmap Heap Scan — the crossover region
--   30%          Seq Scan — reading everything sequentially is cheaper
--                than 30% of the rows in random order
--   100%         Seq Scan, and it is not close

-- ⚠ THE COUNTER-INTUITIVE PART: at 30% selectivity a Seq Scan can be
--   faster than a perfectly good index. The planner is not ignoring your
--   index; it costed both and your index lost. This is correct.

-- ── HENCE: LOW-CARDINALITY COLUMNS ──────────────────────────────────────
CREATE INDEX ON orders (status);   -- 'paid' is 95% of rows → never used
                                   -- for status='paid'; possibly used for
                                   -- a rare value like 'refunded'
-- ✓ What actually works:
CREATE INDEX ON orders (status, created_at);       -- composite: the
                                                   -- second column adds
                                                   -- the selectivity
CREATE INDEX ON orders (created_at) WHERE status = 'pending';
-- ↑ PARTIAL: index ONLY the rare rows. If 0.1% of orders are pending,
--   this index is 1000× smaller than the full one, stays cached, and is
--   cheaper to maintain — writes only touch it when status is 'pending'.
--   For queue tables ("find unprocessed work") this is the single most
--   effective index in the whole toolbox.

-- ── THE BITMAP SCAN, THE MIDDLE GROUND ──────────────────────────────────
-- Too many rows for random fetches, too few to read everything:
--   1. scan the index, build a BITMAP of the pages needed
--   2. read those pages in PHYSICAL order — sequential-ish, not random
--   3. recheck the condition on each row
-- Postgres can also AND/OR bitmaps from SEVERAL indexes:
WHERE user_id = 5 AND status = 'paid'   -- BitmapAnd of two single-column
                                        -- indexes. Useful, but a proper
                                        -- composite index beats it.

Part 4 — Composite Indexes and Index-Only Scans

CREATE INDEX ON orders (user_id, status, created_at);
-- Sorted by user_id; WITHIN each user_id by status; within each pair by
-- created_at. Exactly like sorting a spreadsheet by three columns.

WHERE user_id = 5                                          -- ✓ full use
WHERE user_id = 5 AND status = 'paid'                      -- ✓ full use
WHERE user_id = 5 AND status = 'paid' AND created_at > :d  -- ✓ full use
WHERE user_id = 5 ORDER BY status, created_at              -- ✓ no sort!
WHERE status = 'paid'                                      -- ✗ 'paid' rows
                                                           -- are scattered
                                                           -- across every
                                                           -- user_id
WHERE user_id = 5 AND created_at > :d                      -- ~ partial:
    -- descends on user_id, then must check created_at on every row for
    -- that user because `status` between them is unconstrained.

-- ── THE RULE, DERIVED ───────────────────────────────────────────────────
-- Think of a phone book sorted by (last, first). Finding "Smith, John" is
-- instant. Finding everyone named "John" is a full scan — Johns are
-- spread through every letter. Nothing about that is a database quirk;
-- it is what "sorted by two things" means.

-- ── COLUMN ORDER: EQUALITY FIRST, THEN ONE RANGE ────────────────────────
-- A range STOPS the descent: after it, later columns are only filters.
CREATE INDEX ON events (created_at, tenant_id);   -- ✗ wrong way round
CREATE INDEX ON events (tenant_id, created_at);   -- ✓
WHERE tenant_id = 7 AND created_at > now() - interval '1 day';
-- Version 1: descend to created_at > X (millions of rows across ALL
--   tenants), then discard the ~99% belonging to other tenants.
-- Version 2: descend straight to tenant 7's slice, walk the last day.
-- Same two columns. Orders of magnitude apart.
--
-- ⚠ ORDER BY must also agree in DIRECTION to skip the sort:
CREATE INDEX ON events (tenant_id, created_at DESC);   -- for newest-first
--   (mixed directions like (a ASC, b DESC) need an index declared that
--    way — a plain index can be walked backwards, but not zig-zag.)

-- ── INDEX-ONLY SCANS: SKIPPING THE HEAP ENTIRELY ────────────────────────
-- If every column the query needs is IN the index, the heap fetch — the
-- expensive half — disappears.
CREATE INDEX ON orders (user_id, created_at) INCLUDE (total_cents);
SELECT created_at, total_cents FROM orders WHERE user_id = 5;
-- → Index Only Scan. No table access at all.
--
-- INCLUDE columns are stored ONLY in the leaves: they are payload, not
-- part of the sort key. That keeps the tree narrow (fast descent) while
-- still covering the query. Putting them in the key instead would bloat
-- every internal page for no lookup benefit.
--
-- ⚠ POSTGRES CAVEAT: an index entry does not record whether its row is
--   visible to your snapshot, so Postgres checks the VISIBILITY MAP. If
--   the page is not marked all-visible, it must fetch the heap row after
--   all. A heavily-updated table that vacuum has not caught up on gets
--   "Index Only Scan ... Heap Fetches: 48213" — the plan says index-only
--   and the performance says otherwise. Check that line; it is the most
--   commonly missed number in EXPLAIN output.
--
-- ⚠ InnoDB differs by design: secondary indexes store the PRIMARY KEY,
--   not a row pointer, so a non-covering lookup does a second B-tree
--   descent on the clustered PK. Hence "keep the PK narrow" matters far
--   more in MySQL — the PK is copied into every secondary index.

-- ── HOW TO READ IT ──────────────────────────────────────────────────────
-- 1. INSIDE OUT, BOTTOM UP. The most indented nodes run first and feed
--    their parents. Read the leaves, then how they combine.
--
-- 2. THE LOOPS MULTIPLIER — the #1 misreading. `actual time=0.028..0.029`
--    on the users scan is PER LOOP, and there are 50 loops. Real total is
--    50 × 0.029 ≈ 1.45ms, most of this query. A node showing 0.03ms with
--    loops=40000 is 1.2 seconds and is your problem. Always multiply.
--
-- 3. ESTIMATED rows= vs ACTUAL rows=. This is the planner's report card.
--    Off by 10× or more → it is choosing plans from bad information, and
--    no amount of index tuning fixes a bad estimate. Run ANALYZE.
--
-- 4. BUFFERS: hit = found in cache, read = fetched from the OS/disk.
--    This is the honest cost metric. Timing varies with cache warmth;
--    buffer counts are stable and comparable between runs.
--
-- 5. Planning Time vs Execution Time. Planning of 0.3ms against 2ms of
--    execution is fine; 40ms of planning on a 2ms query means too many
--    indexes or partitions to consider, or a very complex query.

Part 6 — Statistics, Index Types, and Production Changes

-- ── WHEN THE PLANNER IS WRONG, IT IS USUALLY MISINFORMED ────────────────
ANALYZE orders;                          -- refresh statistics now
SELECT last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables WHERE relname = 'orders';
-- Classic failure: a nightly bulk load inserts 10M rows and queries go
-- bad until autoanalyze catches up. Fix: ANALYZE at the end of the load.

-- ── CORRELATED COLUMNS: THE INDEPENDENCE ASSUMPTION ─────────────────────
WHERE city = 'Paris' AND country = 'France'
-- The planner multiplies selectivities as if independent:
--   P(Paris) = 0.001, P(France) = 0.01 → estimate 0.00001 of the table.
-- Reality: every Paris row IS France, so the true selectivity is 0.001 —
-- a 1000× underestimate. It then picks a nested loop sized for 5 rows
-- and gets 50,000, and the query takes minutes instead of milliseconds.
CREATE STATISTICS city_country (dependencies, ndistinct)
    ON city, country FROM addresses;
ANALYZE addresses;
-- Extended statistics teach the planner the correlation. This is THE fix
-- for "the plan flips between fast and catastrophic" on multi-column
-- filters, and it is almost never the first thing people try.

-- ── SKEWED DATA AND MORE DETAIL ─────────────────────────────────────────
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;  -- default 100
-- More histogram buckets. Worth it for columns with heavy skew where one
-- value dominates and the rest matter.

-- ── INDEX TYPES BEYOND B-TREE ───────────────────────────────────────────
-- B-tree   default; equality, ranges, sorting, prefixes. ~95% of cases.
-- GIN      "many values inside one row": JSONB, arrays, full-text,
--          trigram LIKE '%x%'. Slower to write, superb for containment.
CREATE INDEX ON docs USING gin (attrs jsonb_path_ops);
WHERE attrs @> '{"type":"invoice"}';
-- GiST     geometry, ranges, nearest-neighbour, EXCLUDE constraints.
CREATE INDEX ON bookings USING gist (during);
-- BRIN     tiny; stores min/max per block range. Only for huge tables
--          PHYSICALLY ORDERED by the column (append-only time series).
--          A 50GB table's BRIN index can be a few MB.
CREATE INDEX ON metrics USING brin (recorded_at);
--          ⚠ Useless if the physical order does not match the column.
-- Hash     equality only, no ranges, no sorting. B-tree is nearly always
--          as good and far more flexible.

-- ── FINDING WHAT TO DROP ────────────────────────────────────────────────
SELECT s.relname, s.indexrelname, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
FROM pg_stat_user_indexes s
JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0 AND NOT i.indisunique
ORDER BY pg_relation_size(s.indexrelid) DESC;
-- Zero scans since the last stats reset = dead weight, still costing
-- every write. ⚠ Check uptime first — an index used only by a monthly
-- report looks unused on a server restarted last week. And never drop a
-- unique index that is enforcing a constraint.

-- Redundant by prefix: (a) is fully contained in (a, b). Drop (a).
-- Duplicates with different names are common after years of migrations.

-- ── CHANGING INDEXES ON A LIVE TABLE ────────────────────────────────────
CREATE INDEX CONCURRENTLY idx_orders_user ON orders (user_id);
-- Plain CREATE INDEX takes a SHARE lock and BLOCKS ALL WRITES for the
-- entire build — minutes on a big table, and an outage during traffic.
-- CONCURRENTLY does two passes without blocking writes. It is slower,
-- CANNOT run inside a transaction, and can leave an INVALID index if it
-- fails:
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
DROP INDEX CONCURRENTLY idx_orders_user;   -- then retry
-- ⚠ It also waits for all transactions older than itself to finish. One
--   long-running query delays the whole build.

DROP INDEX CONCURRENTLY ...;               -- dropping locks too
BEGIN; ALTER INDEX ... RENAME TO ...; COMMIT;   -- swap pattern

-- ── HYPOTHETICAL INDEXES: TEST BEFORE YOU BUILD ─────────────────────────
CREATE EXTENSION hypopg;
SELECT hypopg_create_index('CREATE INDEX ON orders (user_id, created_at)');
EXPLAIN SELECT ... ;    -- would the planner even use it?
-- Ask the question in seconds instead of building a 40GB index to find
-- out the answer was no.
🎯 Index the query, not the column. The unit of design is a query shape: its WHERE equalities, then its range, then its ORDER BY, then the columns it returns. One well-ordered composite index usually replaces three single-column ones, serves the sort for free, and can be made covering with INCLUDE. Ask what the top twenty queries need, not what the columns are called.

Interview Questions

Beginner: How does an index make a query fast, and what does it cost?

A B-tree index keeps the indexed values in sorted order in a shallow balanced tree. Instead of examining every row, the engine descends from the root comparing keys, reaching the matching entries in about three or four page reads regardless of table size — an 8KB page holds a few hundred keys, so even a hundred million rows is only four levels deep. The upper levels stay cached, so a lookup is typically one physical read against millions for a full scan. Because the leaves are sorted, the same structure also serves range queries, left-anchored prefixes, and ORDER BY without a separate sort step.

The costs are real and ongoing. Every insert and delete, and every update touching an indexed column, must also maintain each index, sometimes splitting pages. Indexes consume storage and cache that would otherwise hold table data, and more of them means slower planning. So an index is a deliberate trade: faster reads for slower writes. You add them for measured query shapes, and you drop the ones that turn out to be unused.

Beginner: Why can't an index be used for WHERE LOWER(email) = 'x' or LIKE '%son'?

Both follow from the same fact: the index is sorted by the exact expression it was built on. An index on email stores 'Asha@Example.com' in its original form, so the engine has no way to descend a tree looking for the lowercase version — the values it would need to compare against simply are not there in that order. The fix is an expression index, CREATE INDEX ON users (lower(email)), which builds the tree over the computed value; the query's expression must then match the index's exactly.

LIKE '%son' fails for a related reason: a sorted structure lets you find things by what they start with, because a shared prefix defines a contiguous range of the sort order. A suffix does not — entries ending in "son" are scattered throughout. LIKE 'son%' is therefore fine, since it is really just the range from 'son' up to the next prefix. Genuine infix search needs a different index type, such as a GIN trigram index, or a full-text index. The general lesson is that wrapping the column in anything — a function, arithmetic, a cast — hides the sorted value from the planner.

Mid: Explain the leftmost-prefix rule, and how you choose column order.

An index on (a, b, c) is sorted by a, then by b within each a, then by c within each pair. Like a phone book sorted by surname then first name: finding "Smith, John" is immediate, but finding every John requires reading everything, because Johns appear under every surname. So the index serves a leftmost run of columns — a, or a and b, or all three — but not b alone.

For ordering, the rule is equality predicates first, then a single range, and the range column last among the useful ones. A range stops the tree descent: once you are scanning a span of b, the c values within that span are not in any single sorted run, so c can only act as a filter on rows already read. The practical example is (tenant_id, created_at) versus (created_at, tenant_id) for tenant_id = 7 AND created_at > X. The first descends directly to that tenant's recent slice; the second reads every tenant's recent rows and discards most of them. Same columns, wildly different performance.

I would also check whether the index can serve the ORDER BY, since a matching column order eliminates the sort node, and whether adding INCLUDE columns makes it covering. The design unit is the query shape, not the column.

Mid: You add an index and the planner still chooses a sequential scan. How do you respond?

My first assumption is that the planner is right, because it costed both options and mine lost. An index scan pays a random heap fetch per matching row, while a sequential scan reads pages in physical order, which is far cheaper per page. Once the query matches a large fraction of the table — very roughly above five or ten percent — reading everything sequentially genuinely beats thousands of scattered fetches. If the column is low-cardinality, like a status where one value covers most rows, the index is correctly ignored for that value.

So I check three things. First, selectivity: how many rows actually match, and is a plain index the wrong tool — a partial index restricted to the rare rows, or a composite index adding a selective column, is often the real answer. Second, sargability: is there a function, cast or type mismatch hiding the column, which shows up as the predicate appearing under Filter rather than Index Cond. Third, statistics: if estimated and actual row counts differ wildly the planner is deciding on bad data, so I run ANALYZE, and for correlated columns add extended statistics.

Only after all that would I test with SET enable_seqscan = off — purely as a diagnostic to see the alternative plan's cost, never as a fix. If the forced index plan really is faster, that gap is telling me the cost model has bad inputs, and it is usually estimates or random_page_cost still set for spinning disks on SSD hardware.

Senior: A query is 50ms in staging and 30s in production on the same schema. Diagnose it.

Same schema and different behaviour means the difference is data or environment, not SQL, so I stop reading the query and get the production plan with EXPLAIN (ANALYZE, BUFFERS), ideally alongside the staging one. The single most informative line is the estimated versus actual row counts on each node.

The most common cause is data volume interacting with plan shape. Staging has a hundred thousand rows, production a hundred million. A nested loop that is perfectly good over a few hundred outer rows becomes catastrophic over a million, and the per-loop timings hide it: a node reporting 0.03ms with loops=1000000 is thirty seconds. That is why multiplying by loops is the first thing I do. Related: an in-memory sort or hash join in staging spills to disk in production when the data exceeds work_mem, which shows as external merge or Batches > 1.

Next I check statistics and skew. Production has a skew staging does not — one tenant with ten million rows while the sampled average is a thousand — so the planner's estimate is right on average and disastrous for that parameter. This is where a generic plan for a prepared statement can also bite, since it is chosen without knowing the actual value. Correlated predicates cause the same failure and are fixed with CREATE STATISTICS. Then environmental factors: is the index actually present and valid in production, did a CREATE INDEX CONCURRENTLY fail and leave it invalid, is the table bloated so that the plan is index-only but doing hundreds of thousands of heap fetches, and is the working set simply not cached — which the read versus hit buffer counts answer directly.

The general principle is that staging performance is not evidence about production unless the data distribution matches, which it essentially never does. Plans are chosen from statistics, and statistics are a property of the data. I would fix the immediate cause, then close the loop by adding pg_stat_statements monitoring and auto_explain for slow queries so the next instance is caught by measurement rather than by a user complaint.

Senior: How do you decide the index set for a table — and how do you add and remove them safely?

I start from workload, not schema. pg_stat_statements ranked by total time gives the queries that actually matter, and I take the top handful rather than trying to serve everything. For each, I extract the shape: which columns are equality-filtered, which one is a range, what the ORDER BY is, and which columns are returned. That maps directly onto an index — equalities first in descending selectivity, the range last, direction matched to the sort, and INCLUDE for returned columns if making it covering is worthwhile.

Then I consolidate, because the total number matters as much as any individual one. An index on (a) is redundant beside (a, b). Several single-column indexes that the planner only ever combines with a bitmap AND usually want to be one composite. Anything filtering a small subset — pending jobs, undeleted rows — should be a partial index, which is dramatically smaller, stays cached, and is only maintained when a write actually touches those rows. Before building anything large I test with hypopg, since asking whether the planner would even use it costs seconds and building the index costs hours.

For removal I look at idx_scan = 0 in pg_stat_user_indexes, but only after checking uptime and stats-reset time, because an index serving a quarterly report looks unused all quarter. I exclude anything backing a unique or exclusion constraint. On a replica-heavy setup I check usage on the replicas too, since read traffic there does not appear in the primary's counters. Rather than dropping outright I sometimes mark it invisible first — ALTER INDEX ... SET (indisvalid) style approaches in MySQL, or simply a scheduled drop with a tested rollback — so recovery is a rebuild rather than an incident.

All changes go through CREATE INDEX CONCURRENTLY and DROP INDEX CONCURRENTLY, because a plain CREATE INDEX blocks every write for the length of the build. Concurrent builds cannot run in a transaction, take roughly twice as long, wait on transactions older than themselves, and leave an invalid index behind on failure — so the runbook includes checking pg_index.indisvalid afterwards and dropping and retrying if needed. I also set lock_timeout first, so a migration that cannot get its lock fails fast instead of queueing every query in the system behind it.

1 (easy): Build a million-row table and measure a scan against an index.
Solution 
CREATE TABLE events (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id  int         NOT NULL,
    kind       text        NOT NULL,
    created_at timestamptz NOT NULL
);

INSERT INTO events (tenant_id, kind, created_at)
SELECT (random()*1000)::int,
       (ARRAY['click','view','purchase'])[1 + (random()*2)::int],
       now() - (random() * interval '365 days')
FROM generate_series(1, 1000000);
ANALYZE events;            -- ← never skip this; the planner is blind
                           --   until statistics exist

-- ── BEFORE ──────────────────────────────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE tenant_id = 42;
-- Seq Scan on events (cost=0..20406 rows=1010 width=41)
--                    (actual time=0.312..71.4 rows=983 loops=1)
--   Filter: (tenant_id = 42)
--   Rows Removed by Filter: 999017      ← read 1M rows to return 983
--   Buffers: shared read=8334           ← 65MB off disk
-- Execution Time: 71.8 ms

-- ── AFTER ───────────────────────────────────────────────────────────────
CREATE INDEX idx_events_tenant ON events (tenant_id);
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE tenant_id = 42;
-- Bitmap Heap Scan on events (actual time=0.201..1.05 rows=983 loops=1)
--   Recheck Cond: (tenant_id = 42)
--   Buffers: shared hit=947 read=8
--   ->  Bitmap Index Scan on idx_events_tenant
--         (actual time=0.089..0.089 rows=983 loops=1)
-- Execution Time: 1.14 ms                ← 63× faster

-- Note it chose a BITMAP scan, not a plain index scan: 983 scattered
-- rows are better collected and read in physical page order.

-- ── NOW WATCH THE INDEX CORRECTLY LOSE ──────────────────────────────────
EXPLAIN ANALYZE SELECT * FROM events WHERE kind = 'click';
-- Seq Scan ... Rows Removed by Filter: 666482
-- The index on kind would match a THIRD of the table. Reading 333k rows
-- via random heap fetches is far worse than one sequential pass. The
-- planner is right, and this is why "just add an index" is not a plan.
2 (easy): Break an index four ways, then fix each.
Solution 
CREATE INDEX idx_users_email ON users (email);

-- ── 1. FUNCTION ON THE COLUMN ───────────────────────────────────────────
EXPLAIN SELECT * FROM users WHERE lower(email) = 'asha@example.com';
-- Seq Scan ... Filter: (lower(email) = ...)
CREATE INDEX idx_users_email_lower ON users (lower(email));
-- ✓ Index Scan. The expression must match EXACTLY — an index on
--   lower(email) does not serve upper(email) or btrim(lower(email)).
-- ✓ Better still, use `citext` or a case-insensitive collation and stop
--   fighting it at every call site.

-- ── 2. LEADING WILDCARD ─────────────────────────────────────────────────
EXPLAIN SELECT * FROM users WHERE email LIKE '%@gmail.com';
-- Seq Scan. A sorted tree cannot find things by suffix.
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_users_email_trgm ON users USING gin (email gin_trgm_ops);
-- ✓ Now infix and suffix matching are indexed. Costs more to maintain —
--   worth it for genuine search, not for a query that should have been
--   `WHERE email_domain = 'gmail.com'` on a stored column.

-- ── 3. ARITHMETIC ON THE COLUMN ─────────────────────────────────────────
EXPLAIN SELECT * FROM users WHERE score + 10 > 100;      -- Seq Scan
EXPLAIN SELECT * FROM users WHERE score > 90;            -- ✓ Index Scan
-- Algebraically identical, operationally not. Move arithmetic to the
-- constant side ALWAYS — it is free and it is a habit worth having.

-- ── 4. DATE TRUNCATION ──────────────────────────────────────────────────
EXPLAIN SELECT * FROM events
WHERE date_trunc('day', created_at) = DATE '2026-08-05';    -- Seq Scan
EXPLAIN SELECT * FROM events
WHERE created_at >= DATE '2026-08-05'
  AND created_at <  DATE '2026-08-06';                      -- ✓ range
-- The half-open rewrite is sargable AND avoids the classic
-- BETWEEN '...00:00' AND '...23:59:59' bug that silently drops the final
-- second of the day.

-- ── 5. THE ONE WITH NO WARNING: TYPE MISMATCH ───────────────────────────
-- external_id is varchar; the ORM binds an integer:
WHERE external_id = 12345
-- MySQL coerces the COLUMN to a number and the index becomes unusable
-- across the whole table. Postgres usually errors instead, which is
-- kinder. Check bound parameter types when a plan makes no sense.
3 (medium): Design one index for this query and prove each part earns its place.
Solution 
-- THE QUERY (an app's busiest endpoint)
SELECT id, total_cents, created_at
FROM orders
WHERE tenant_id = :t AND status = 'pending' AND created_at > :since
ORDER BY created_at DESC
LIMIT 20;

-- ── BUILD IT UP, MEASURING EACH STEP ────────────────────────────────────
-- v1 — one column
CREATE INDEX i1 ON orders (tenant_id);
-- Index Scan + Filter. Reads every order for the tenant (say 400k),
-- discards non-pending and old ones, then SORTS them all for the LIMIT.
-- Buffers: read=3100   Time: 240ms

-- v2 — add the equality
CREATE INDEX i2 ON orders (tenant_id, status);
-- Descends to (tenant, pending). Far fewer rows, but STILL a sort node:
-- within that group, created_at is unordered.
-- Sort Method: quicksort  Memory: 812kB    Time: 31ms

-- v3 — add the range/sort column LAST
CREATE INDEX i3 ON orders (tenant_id, status, created_at DESC);
-- Leaves are already in the required order, so the engine walks them and
-- STOPS AFTER 20. No sort node at all.
-- Time: 0.4ms

-- v4 — make it covering
CREATE INDEX i4 ON orders (tenant_id, status, created_at DESC)
       INCLUDE (total_cents);
-- id is the PK and already present in the leaves. Adding total_cents as
-- payload removes the heap fetch entirely.
-- Index Only Scan  Heap Fetches: 0   Buffers: hit=6   Time: 0.09ms
DROP INDEX i1, i2, i3;        -- all subsumed by i4

-- ── WHY THIS ORDER, EXPLICITLY ──────────────────────────────────────────
-- tenant_id, status  equalities → they FIX a position in the sort order,
--                    so the descent lands on an exact subtree
-- created_at DESC    the range AND the sort → last, so the matching rows
--                    form one contiguous, already-ordered run
-- INCLUDE            payload only. In the KEY it would widen every
--                    internal page and slow the descent for no benefit.
--
-- The LIMIT is what makes this dramatic: with the sort eliminated the
-- engine reads 20 leaf entries and stops. With a sort it must produce
-- and order the ENTIRE matching set to find the top 20.

-- ── AND WHERE IT STOPS WORKING ──────────────────────────────────────────
-- If 'pending' is 95% of a tenant's orders, `status` adds nothing to the
-- descent. Then the better index is partial:
CREATE INDEX i5 ON orders (tenant_id, created_at DESC)
       INCLUDE (total_cents) WHERE status = 'pending';
-- Same plan, smaller index, and writes only touch it for pending rows.
-- Which is right depends on YOUR distribution — check it, don't assume.
4 (medium): Read this plan and find the real bottleneck.
Solution 
-- THE PLAN
HashAggregate  (actual time=8412.9..8413.2 rows=48 loops=1)
  ->  Nested Loop  (actual time=0.089..8102.4 rows=214882 loops=1)
        ->  Seq Scan on orders o (actual time=0.021..48.3
                                  rows=214882 loops=1)
              Filter: (created_at > (now() - '30 days'::interval))
              Rows Removed by Filter: 41
        ->  Index Scan using users_pkey on users u
              (actual time=0.034..0.036 rows=1 loops=214882)   ★
              Index Cond: (id = o.user_id)
Execution Time: 8413.6 ms

-- ── STEP 1: FIND THE TIME, DO NOT GUESS ─────────────────────────────────
-- ★ 0.036ms looks trivially fast. It is PER LOOP.
--     214,882 loops × 0.036ms ≈ 7,736ms
--   That inner index scan is 92% of an 8.4-second query. The Seq Scan
--   everyone's eye jumps to costs 48ms — 0.6%.
--
-- ⚠ The instinct "there's a Seq Scan, add an index" would spend a day
--   optimising 0.6% of the runtime. Always multiply by loops FIRST.

-- ── STEP 2: WHY IS THE LOOP COUNT SO HIGH? ──────────────────────────────
-- The Seq Scan on orders is CORRECT: it matches 214,882 of 214,923 rows
-- (Rows Removed by Filter: 41). Reading essentially the whole table
-- sequentially is the right choice — an index would be far worse here.
--
-- The mistake is the JOIN STRATEGY. A nested loop does 214,882
-- individual B-tree descents into users. For that many outer rows a HASH
-- JOIN — build a hash of users once, stream orders through it — is the
-- right algorithm.

-- ── STEP 3: WHY DID IT CHOOSE A NESTED LOOP? ────────────────────────────
EXPLAIN (ANALYZE) ...        -- look for estimated vs actual
-- If the estimate said rows=200 and reality is 214,882, the planner
-- chose a plan that is optimal FOR 200 ROWS. It was not being stupid; it
-- was misinformed.
ANALYZE orders;
SELECT last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables WHERE relname = 'orders';
-- Typical cause: a bulk load that autoanalyze has not caught up with.

-- ── STEP 4: VERIFY THE HYPOTHESIS ───────────────────────────────────────
SET enable_nestloop = off;   -- DIAGNOSTIC ONLY, never a deployed fix
EXPLAIN ANALYZE ...;
-- Hash Join ... Execution Time: 412 ms      ← 20× faster. Confirmed.
RESET enable_nestloop;
-- If ANALYZE alone now produces the hash join, the fix is fixing
-- statistics freshness, not the query.

-- ── STEP 5: THE REAL QUESTION ───────────────────────────────────────────
-- This aggregates 30 days of orders and returns 48 rows. Even at 412ms
-- it does not belong on a request path.
CREATE MATERIALIZED VIEW daily_order_stats AS SELECT ... ;
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_order_stats;
-- The fastest query is the one that already ran. Sometimes the answer to
-- "why is this analytical query slow" is "why is it running live".
5 (hard): Audit and rationalise the index set on a table with fourteen of them.
Solution 
-- SITUATION: `orders` has 14 indexes, 60GB of them against 40GB of table.
-- Inserts have degraded from 1.2ms to 9ms over two years.

-- ── STEP 1: INVENTORY WITH USAGE ────────────────────────────────────────
SELECT s.indexrelname, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size,
       i.indisunique, pg_get_indexdef(s.indexrelid) AS def
FROM pg_stat_user_indexes s
JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.relname = 'orders'
ORDER BY s.idx_scan, pg_relation_size(s.indexrelid) DESC;

-- ⚠ FIRST, ESTABLISH THE WINDOW. Counters reset on restart:
SELECT stats_reset FROM pg_stat_database WHERE datname = current_database();
-- Two weeks of data cannot judge a monthly report's index. Ideally
-- snapshot idx_scan over a full business cycle before deciding.

-- ── STEP 2: CLASSIFY ────────────────────────────────────────────────────
-- A. NEVER SCANNED (idx_scan = 0), not unique → candidates to drop.
-- B. REDUNDANT BY PREFIX:
--      idx_a  (tenant_id)                  ← subsumed
--      idx_b  (tenant_id, created_at)      ← keep
--    Any leftmost-prefix subset is served by the longer index. Note the
--    longer one is bigger, so a very hot lookup on (tenant_id) alone can
--    justify keeping both — measure rather than assume.
-- C. EXACT DUPLICATES under different names (migration archaeology):
SELECT array_agg(indexrelid::regclass), indrelid::regclass
FROM pg_index GROUP BY indrelid, indkey, indpred, indexprs
HAVING count(*) > 1;
-- D. CONSTRAINT-BACKING — untouchable regardless of scan count.
-- E. LOW-VALUE SINGLE COLUMN: (status) where one value is 95% of rows.
--    Replace with a PARTIAL index on the selective values.

-- ── STEP 3: DO NOT TRUST ONE SERVER ─────────────────────────────────────
-- idx_scan is PER NODE. An index used only by reporting queries on a
-- read replica shows zero on the primary. Aggregate across all replicas
-- before dropping anything.

-- ── STEP 4: TEST THE CONSOLIDATION BEFORE BUILDING ──────────────────────
CREATE EXTENSION IF NOT EXISTS hypopg;
SELECT hypopg_create_index(
  'CREATE INDEX ON orders (tenant_id, status, created_at DESC)');
EXPLAIN SELECT ...;    -- does the planner take it, for each top query?
-- Answers in seconds what building a 6GB index answers in an hour.

-- ── STEP 5: EXECUTE, REVERSIBLY ─────────────────────────────────────────
SET lock_timeout = '5s';
CREATE INDEX CONCURRENTLY idx_orders_tenant_status_created
  ON orders (tenant_id, status, created_at DESC) INCLUDE (total_cents);
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;  -- verify

-- Drop ONE per deploy, watching pg_stat_statements for regressions:
DROP INDEX CONCURRENTLY idx_orders_tenant;
-- Keep the exact CREATE statement for every dropped index in the PR
-- description. Recovery is then a copy-paste, not an archaeology
-- exercise during an incident.

-- ── STEP 6: MEASURE THE OUTCOME ─────────────────────────────────────────
-- 14 → 6 indexes. 60GB → 22GB. Insert latency 9ms → 2.1ms.
-- The second-order win is bigger than the write path: 38GB of freed
-- cache now holds table data, so the hit rate rises and READS get
-- faster too. Fewer indexes also means faster planning on every query.

-- ── THE PRINCIPLE ───────────────────────────────────────────────────────
-- Index sets accumulate because adding one fixes today's slow query and
-- nobody owns the total. Cost is per-write and invisible per-index but
-- compounding in aggregate. Audit on a schedule, not after an incident.
6 (hard): A query is fast for most users and times out for your largest customer. Explain and fix.
Solution 
-- SELECT ... FROM events WHERE tenant_id = :t AND created_at > :since
-- p50: 4ms.  tenant 88 (12M of the 50M rows): 45s, intermittently.

-- ── THE MECHANISM: SKEW BREAKS AVERAGES ─────────────────────────────────
SELECT tenant_id, count(*) FROM events
GROUP BY 1 ORDER BY 2 DESC LIMIT 5;
--  88 | 12,000,000       ← 24% of the table
--  17 |     41,232
--   4 |     38,901
SELECT most_common_vals, most_common_freqs FROM pg_stats
WHERE tablename='events' AND attname='tenant_id';
-- If tenant 88 is in the MCV list, the planner knows it is huge and can
-- plan accordingly. If it is NOT (too many distinct tenants for the
-- default 100 buckets), the planner uses the AVERAGE — about 50,000 rows
-- — and chooses a plan that is 240× too small.

-- ── WHY IT IS INTERMITTENT (the part that confuses everyone) ────────────
-- Postgres re-plans a prepared statement per execution for the first
-- five runs using the actual parameter, then may switch to a GENERIC
-- plan chosen without the value. So the same query is fast for a while
-- and then locks onto one plan that suits the average and destroys
-- tenant 88. Or vice versa.
SET plan_cache_mode = force_custom_plan;    -- re-plan every time
-- Costs a little planning time; removes an entire class of "it was fine
-- yesterday". For skewed multi-tenant workloads this is often correct.

-- ── FIX 1: LET THE PLANNER SEE THE SKEW ─────────────────────────────────
ALTER TABLE events ALTER COLUMN tenant_id SET STATISTICS 1000;
ANALYZE events;
-- 1000 histogram buckets instead of 100 → the big tenants land in the
-- MCV list and get correctly-sized plans. Cheapest fix; try it first.

-- ── FIX 2: AN INDEX THAT MATCHES THE ACCESS PATTERN ─────────────────────
CREATE INDEX CONCURRENTLY idx_events_tenant_created
  ON events (tenant_id, created_at DESC);
-- Within tenant 88, rows are ordered by time, so "last 24 hours" is a
-- contiguous leaf range regardless of how many rows that tenant has.
-- This alone often fixes it: the query stops scaling with tenant size
-- and starts scaling with RESULT size, which is the property you want.

-- ── FIX 3: PARTITION, IF THE SIZE IS STRUCTURAL ─────────────────────────
CREATE TABLE events (...) PARTITION BY RANGE (created_at);
-- Monthly partitions. A 24-hour query touches one partition; the planner
-- prunes the rest before execution. Also makes retention a DETACH
-- instead of a 12-million-row DELETE — which matters more than the read
-- speedup in practice.
-- ⚠ Every query must include the partition key or you scan them all.
-- LIST partitioning by tenant_id is possible but usually wrong: tenants
-- are added constantly and most are tiny.

-- ── FIX 4: STOP THE BLEEDING NOW ────────────────────────────────────────
SET statement_timeout = '10s';
-- A 45-second query holds a connection and, if it is in a transaction,
-- blocks vacuum. Better to fail one request fast than to degrade
-- everyone. This is mitigation, not a fix — but ship it first.

-- ── FIX 5: RENEGOTIATE THE REQUIREMENT ──────────────────────────────────
-- Ask what the endpoint is FOR. If it is a dashboard count over 12M
-- rows, no index makes an exact count fast, and nobody reads the digits
-- past the third.
--   • pre-aggregate into events_daily, refreshed incrementally
--   • or accept an estimate:
SELECT reltuples::bigint FROM pg_class WHERE relname='events';
--   • or cap the window: "last 30 days" instead of all time
-- The senior move is recognising that the fastest query is the one you
-- do not run — and that "exact, unbounded, real-time" is usually three
-- requirements where only one was actually needed.

-- ── AND CLOSE THE LOOP ──────────────────────────────────────────────────
-- Seed staging with a production-like DISTRIBUTION, not just a
-- production-like row count. This bug is invisible against uniform test
-- data, which is precisely why it reached production.

🎯 Key Takeaways

  • A B-tree is sorted and balanced; every index rule you know follows from those two properties — derive them rather than memorising them.
  • Index depth grows logarithmically, so lookups barely slow as tables grow — but sequential scans grow linearly, which is why dev-sized data proves nothing.
  • Anything wrapping the column — a function, arithmetic, a cast — hides the sorted value; fix with an expression index or by rewriting the constant side.
  • Selectivity decides everything: past roughly 5–10% of rows a sequential scan legitimately beats an index, so a "correct" index being ignored is usually correct behaviour.
  • Partial indexes are the strongest tool for skewed columns — dramatically smaller, cache-resident, and only maintained on relevant writes.
  • Composite order is equalities first, one range last, direction matched to ORDER BY; the wrong order can be orders of magnitude slower with identical columns.
  • INCLUDE columns are leaf payload, enabling index-only scans without widening the tree — but watch Heap Fetches, which betrays a stale visibility map.
  • In EXPLAIN, multiply actual time by loops before concluding anything; the per-loop figure hides most real bottlenecks.
  • A large estimated-versus-actual gap means the planner is misinformed, not stupid — ANALYZE first, and CREATE STATISTICS for correlated columns.
  • Build and drop with CONCURRENTLY, set lock_timeout before migrations, and audit the whole index set periodically — write cost is per-index and compounds silently.
