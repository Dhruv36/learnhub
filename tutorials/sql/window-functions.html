Window Functions Intermediate

What you'll master: why a window function keeps rows where GROUP BY collapses them, the anatomy of OVER — partition, order and frame — and the default frame that silently produces wrong running totals, the three ranking functions and which one your requirement actually means, LAG/LEAD and the gaps-and-islands pattern, frames in ROWS versus RANGE versus GROUPS, where window functions sit in the execution order and why you cannot filter on them directly, and when LATERAL or a rollup beats a window entirely. Prerequisites: Sorting, Limiting & Aggregates and Subqueries & CTEs.

Part 1 — Aggregating Without Collapsing

-- GROUP BY collapses 500 employees into 8 department rows. The individual
-- rows are GONE, which is a problem when you want to compare each one
-- against its group.

SELECT name, department, salary,
       avg(salary) OVER (PARTITION BY department)              AS dept_avg,
       salary - avg(salary) OVER (PARTITION BY department)     AS vs_avg,
       count(*)    OVER (PARTITION BY department)              AS dept_size,
       salary::numeric / sum(salary) OVER ()                   AS share_of_all
FROM employees;
-- 500 rows in, 500 rows out — each carrying facts about its group.
-- PARTITION BY = the group. Omit it and the window is the WHOLE result.

-- ── THE PRE-WINDOW WAY, FOR CONTRAST ────────────────────────────────────
SELECT e.name, e.salary, d.avg_salary
FROM employees e
JOIN (SELECT department, avg(salary) AS avg_salary
      FROM employees GROUP BY department) d ON d.department = e.department;
-- Two passes over the table and a join, to express one idea. Add a
-- second metric and it is a second subquery. Window functions replaced
-- an entire genre of self-joins.

-- ── ANATOMY OF OVER ─────────────────────────────────────────────────────
func(...) OVER (
    PARTITION BY expr      -- split rows into independent groups
    ORDER BY     expr      -- order WITHIN each partition
    frame_clause           -- which rows of the partition are visible
)
-- All three are optional, and each one changes the meaning:
avg(x) OVER ()                                -- whole result set
avg(x) OVER (PARTITION BY dept)               -- per department
avg(x) OVER (PARTITION BY dept ORDER BY hire) -- ⚠ RUNNING average — the
                                              --   ORDER BY silently adds
                                              --   a frame. See Part 3.

-- ── NAMED WINDOWS: DEFINE ONCE, REUSE ───────────────────────────────────
SELECT name, salary,
       rank()       OVER w,
       avg(salary)  OVER w,
       count(*)     OVER w
FROM employees
WINDOW w AS (PARTITION BY department ORDER BY salary DESC);
-- Repeating the same OVER clause three times is how they drift apart
-- during maintenance.

-- ── ALMOST ANY AGGREGATE WORKS AS A WINDOW FUNCTION ─────────────────────
sum() avg() count() min() max() stddev()
string_agg() array_agg() jsonb_agg()
percentile_cont(0.5) WITHIN GROUP (ORDER BY x) OVER (PARTITION BY dept)
count(*) FILTER (WHERE status = 'paid') OVER (PARTITION BY user_id)
-- FILTER composes with OVER, which covers a lot of conditional analytics
-- in one pass.

Part 2 — Ranking

SELECT name, department, salary,
       row_number() OVER (PARTITION BY department ORDER BY salary DESC) AS rn,
       rank()       OVER (PARTITION BY department ORDER BY salary DESC) AS rnk,
       dense_rank() OVER (PARTITION BY department ORDER BY salary DESC) AS drnk,
       percent_rank() OVER (PARTITION BY department ORDER BY salary)    AS pct,
       ntile(4)     OVER (PARTITION BY department ORDER BY salary)      AS quartile
FROM employees;

-- salaries 100, 100, 90, 80:
--   row_number   1, 2, 3, 4     always distinct; ties broken ARBITRARILY
--   rank         1, 1, 3, 4     ties share, then a GAP
--   dense_rank   1, 1, 2, 3     ties share, no gap
--
-- These are not stylistic choices. "Top 3" means something different
-- under each one when there is a tie for third.
NeedFunctionWhy
Exactly N rows, deduplication, "latest per key"row_number()Guarantees one row per position
Leaderboards, sports standingsrank()Tied competitors share a place, and the next place skips
"The 3 distinct highest salaries"dense_rank()Counts distinct values, not rows
Quartiles, deciles, bucketingntile(n)Splits a partition into n near-equal buckets
"Better than X% of peers"percent_rank(), cume_dist()Relative position as a fraction
-- ── row_number NEEDS A DETERMINISTIC ORDER ──────────────────────────────
row_number() OVER (PARTITION BY dept ORDER BY salary DESC)
-- Two employees on the same salary get 1 and 2 in an order the engine
-- chooses — and it can differ between runs, after a VACUUM, or when the
-- plan changes. If you then take rn = 1 you have a non-deterministic
-- result that passes every test.
row_number() OVER (PARTITION BY dept ORDER BY salary DESC, id)   -- ✓
-- Always append a unique tiebreaker.

-- ── THE MOST USEFUL PATTERN IN THE LESSON: LATEST PER KEY ───────────────
SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY user_id
                               ORDER BY created_at DESC, id DESC) AS rn
  FROM orders
) t WHERE rn = 1;
-- The current row per group: latest order per user, current price per
-- product, most recent status per ticket, newest version per document.

-- Postgres shortcut for exactly this:
SELECT DISTINCT ON (user_id) *
FROM orders ORDER BY user_id, created_at DESC, id DESC;
-- The ORDER BY must START with the DISTINCT ON columns. Shorter, and
-- often faster because it stops at the first row per group.

-- ── DEDUPLICATION ───────────────────────────────────────────────────────
DELETE FROM users WHERE id IN (
  SELECT id FROM (
    SELECT id, row_number() OVER (PARTITION BY lower(email)
                                  ORDER BY created_at, id) AS rn
    FROM users) t
  WHERE rn > 1);
-- Keeps the oldest row per email, deletes the rest. ORDER BY decides
-- WHICH duplicate survives — an explicit business decision, so state it.

Part 3 — Frames

-- ── THE DEFAULT FRAME IS THE BIGGEST TRAP HERE ──────────────────────────
avg(x) OVER (PARTITION BY dept)                  -- frame = WHOLE partition
avg(x) OVER (PARTITION BY dept ORDER BY hire)    -- frame = RANGE BETWEEN
                                                 -- UNBOUNDED PRECEDING
                                                 -- AND CURRENT ROW
-- Adding ORDER BY silently turns a partition-wide aggregate into a
-- RUNNING one. People add it "to make the output tidy" and change every
-- number in the column.

-- ── ROWS vs RANGE: THE DIFFERENCE THAT BREAKS RUNNING TOTALS ────────────
-- ROWS  counts PHYSICAL rows
-- RANGE counts rows with the same ORDER BY VALUE as peers — all ties are
--       included together

-- sales: (Mon,100) (Mon,50) (Tue,80)
sum(amt) OVER (ORDER BY day)                              -- RANGE default
--   Mon → 150, Mon → 150, Tue → 230     both Monday rows show the full
--                                       Monday total
sum(amt) OVER (ORDER BY day ROWS UNBOUNDED PRECEDING)
--   Mon → 100, Mon → 150, Tue → 230     a true row-by-row running total
--
-- If your ORDER BY column has duplicates — and dates almost always do —
-- the default RANGE frame is probably not what you want. Be explicit.

-- ── FRAME SYNTAX ────────────────────────────────────────────────────────
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW    -- running total
ROWS BETWEEN 6 PRECEDING AND CURRENT ROW            -- 7-row moving window
ROWS BETWEEN 3 PRECEDING AND 3 FOLLOWING            -- centred
ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING    -- remaining total
RANGE BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING  -- whole partition
GROUPS BETWEEN 2 PRECEDING AND CURRENT ROW          -- 3 distinct VALUES
                                                    -- (Postgres 11+)

-- ── A MOVING AVERAGE OVER TIME, NOT OVER ROWS ───────────────────────────
avg(amount) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
-- ✗ "the last 7 ROWS". Miss a day and the window silently spans 8 days.
avg(amount) OVER (ORDER BY day
                  RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW)
-- ✓ "the last 7 DAYS", regardless of gaps. Needs a date/numeric ORDER BY.
-- Gaps in a time series are common (no sales on a public holiday), and
-- this distinction is the difference between a 7-day average and an
-- arbitrary one.

-- ── EVERYDAY FRAME PATTERNS ─────────────────────────────────────────────
SELECT day, revenue,
       sum(revenue) OVER (ORDER BY day ROWS UNBOUNDED PRECEDING) AS cumulative,
       avg(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING
                                        AND CURRENT ROW)         AS ma7,
       max(revenue) OVER (ORDER BY day ROWS BETWEEN 29 PRECEDING
                                        AND CURRENT ROW)         AS peak_30d,
       revenue / sum(revenue) OVER ()                            AS share
FROM daily_sales;
Key insight: a window function is evaluated after WHERE, GROUP BY and HAVING, but before ORDER BY and LIMIT. Two consequences follow, and between them they explain nearly every window function error. You cannot reference a window function in WHERE — it does not exist yet — which is why top-N-per-group always needs a subquery or CTE wrapping it. And the window only ever sees rows that survived WHERE, so filtering to one month and then computing a running total gives a total that starts at zero on the first of that month rather than continuing from history.

Part 4 — LAG, LEAD, and Row Comparisons

SELECT day, revenue,
       lag(revenue)  OVER (ORDER BY day)                 AS prev_day,
       lead(revenue) OVER (ORDER BY day)                 AS next_day,
       revenue - lag(revenue) OVER (ORDER BY day)        AS delta,
       round(100.0 * (revenue - lag(revenue) OVER (ORDER BY day))
             / nullif(lag(revenue) OVER (ORDER BY day), 0), 1) AS pct_change,
       lag(revenue, 7) OVER (ORDER BY day)               AS same_day_last_week,
       lag(revenue, 1, 0) OVER (ORDER BY day)            AS prev_or_zero
FROM daily_sales;
-- lag(col, offset, default). The first row's lag is NULL unless you
-- supply a default — and nullif guards the division when the previous
-- value is 0.

-- ── first_value, last_value, nth_value ──────────────────────────────────
first_value(price) OVER (PARTITION BY product ORDER BY day)   -- opening
last_value(price)  OVER (PARTITION BY product ORDER BY day
                         ROWS BETWEEN UNBOUNDED PRECEDING
                              AND UNBOUNDED FOLLOWING)        -- ← REQUIRED
-- ⚠ WITHOUT that frame, last_value returns the CURRENT ROW, because the
--   default frame ends at the current row. It is the single most
--   reported "window functions are broken" bug, and it is the default
--   frame doing exactly what it says.
nth_value(price, 2) OVER (...)

-- ── GAPS AND ISLANDS: consecutive runs ──────────────────────────────────
-- "How many consecutive days did each user log in?"
WITH marked AS (
  SELECT user_id, day,
         day - (row_number() OVER (PARTITION BY user_id ORDER BY day))::int
           AS grp                          -- constant within a run
  FROM logins
)
SELECT user_id, min(day) AS start, max(day) AS end, count(*) AS streak
FROM marked GROUP BY user_id, grp
ORDER BY streak DESC;
-- The trick: for consecutive dates, (date - row_number) is CONSTANT
-- within a run and changes at every gap. Grouping by it gives the runs.
-- Used for: login streaks, uptime windows, contiguous seat blocks,
-- sessionisation, detecting missing sequence numbers.

-- ── SESSIONISATION: split events into sessions on a 30-minute gap ───────
WITH gaps AS (
  SELECT *, CASE WHEN ts - lag(ts) OVER (PARTITION BY user_id ORDER BY ts)
                      > interval '30 min'
                 THEN 1 ELSE 0 END AS is_new_session
  FROM events
)
SELECT *, sum(is_new_session) OVER (PARTITION BY user_id ORDER BY ts)
            AS session_id
FROM gaps;
-- A running sum of a 0/1 flag is the general "assign a group id that
-- increments at each boundary" idiom. Worth memorising.

-- ── DETECTING CHANGES ───────────────────────────────────────────────────
SELECT * FROM (
  SELECT *, lag(status) OVER (PARTITION BY order_id ORDER BY changed_at)
              AS prev_status
  FROM order_history
) t WHERE status IS DISTINCT FROM prev_status;
-- IS DISTINCT FROM, not <>, so the first row (prev NULL) counts as a
-- change rather than disappearing.

Part 5 — Execution Order and Filtering

-- WHERE FUNCTIONS ARE EVALUATED:
--   FROM/JOIN → WHERE → GROUP BY → HAVING → WINDOW FUNCTIONS
--     → SELECT → DISTINCT → ORDER BY → LIMIT

SELECT name, row_number() OVER (ORDER BY salary DESC) AS rn
FROM employees WHERE rn <= 10;          -- ✗ ERROR: column "rn" does not
                                        --   exist. WHERE runs first.

SELECT * FROM (                          -- ✓ wrap it
  SELECT name, row_number() OVER (ORDER BY salary DESC) AS rn
  FROM employees) t
WHERE rn <= 10;

WITH ranked AS (                         -- ✓ or a CTE, which reads better
  SELECT name, row_number() OVER (ORDER BY salary DESC) AS rn
  FROM employees)
SELECT * FROM ranked WHERE rn <= 10;

-- Postgres 15+ has QUALIFY-like filtering via... nothing, actually.
-- Snowflake, BigQuery and DuckDB have QUALIFY:
SELECT * FROM employees QUALIFY row_number() OVER (...) <= 10;
-- Worth knowing it exists; it is not standard SQL and Postgres/MySQL
-- do not have it.

-- ── THE WINDOW ONLY SEES ROWS THAT SURVIVED WHERE ───────────────────────
SELECT day, sum(revenue) OVER (ORDER BY day) AS running
FROM daily_sales
WHERE day >= '2026-06-01';
-- The running total RESTARTS at zero on 1 June. It does not continue
-- from the year's history, because those rows were filtered out before
-- the window ran. Almost never what a "cumulative revenue" chart wants.

-- ✓ compute over everything, then filter
WITH running AS (
  SELECT day, sum(revenue) OVER (ORDER BY day) AS total FROM daily_sales)
SELECT * FROM running WHERE day >= '2026-06-01';

-- ── WINDOWS AND GROUP BY COMPOSE ────────────────────────────────────────
SELECT department, count(*) AS headcount,
       sum(count(*)) OVER () AS total_headcount,
       round(100.0 * count(*) / sum(count(*)) OVER (), 1) AS pct
FROM employees GROUP BY department;
-- The window operates on the GROUPED rows, because it runs after
-- GROUP BY. `sum(count(*)) OVER ()` looks bizarre and is the standard
-- way to compute a percentage of total in one pass.

-- ── PERFORMANCE ─────────────────────────────────────────────────────────
-- A window function needs its partition sorted. An index matching
-- (partition_key, order_key) lets the planner skip the sort entirely:
CREATE INDEX ON orders (user_id, created_at DESC);
EXPLAIN ANALYZE ...
--   "WindowAgg" over a "Sort"       → paying for a sort
--   "WindowAgg" over an "Index Scan" → sort avoided
-- Several windows sharing one OVER clause are computed in a single pass;
-- different clauses each need their own sort, so consolidate where you
-- can (and use a named WINDOW so it is obvious when they match).

Part 6 — When Not to Use a Window Function

-- ── TOP-N PER GROUP: LATERAL IS OFTEN FAR FASTER ────────────────────────
-- ✗ ranks EVERY order in the table, then discards all but 3 per user
SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY user_id
                               ORDER BY created_at DESC) rn
  FROM orders) t WHERE rn <= 3;
-- 50M orders sorted to return 300 rows.

-- ✓ reads exactly 3 rows per user, with the right index
SELECT u.id, o.*
FROM users u
CROSS JOIN LATERAL (
  SELECT * FROM orders WHERE user_id = u.id
  ORDER BY created_at DESC LIMIT 3) o;
CREATE INDEX ON orders (user_id, created_at DESC);
--
-- THE RULE: LATERAL wins when the outer set is SMALL and the child table
-- is INDEXED — it seeks. The window function wins when you need the rank
-- over everything anyway, or when there is no useful index, because one
-- sorted pass beats N lookups.

-- ── RUNNING TOTALS OVER ALL HISTORY, RECOMPUTED CONSTANTLY ──────────────
-- A cumulative sum over 500M immutable rows, recalculated on every
-- dashboard load, is work you already did yesterday. Materialise it:
CREATE MATERIALIZED VIEW daily_running AS
SELECT day, revenue, sum(revenue) OVER (ORDER BY day) AS cumulative
FROM daily_sales;
-- Or keep an incremental rollup table. Windows are for computing an
-- answer, not for caching one.

-- ── DEDUPLICATION AT SOURCE ─────────────────────────────────────────────
-- Using row_number() = 1 to hide duplicates on every read means the
-- duplicates are still there, growing, and every query must remember the
-- trick. A unique constraint prevents them:
CREATE UNIQUE INDEX ON users (lower(email)) WHERE deleted_at IS NULL;

-- ── THINGS WINDOWS CANNOT DO ────────────────────────────────────────────
-- * Nest them: sum(row_number() OVER ()) OVER ()  → error. Use a CTE.
-- * Appear in WHERE, GROUP BY, or HAVING.
-- * Recurse. A running balance where each row DEPENDS on the previous
--   computed value (compound interest, inventory that cannot go
--   negative) is not expressible as a window — that needs a recursive
--   CTE.
-- * See rows that WHERE removed.

-- ── ENGINE SUPPORT ──────────────────────────────────────────────────────
-- Postgres: full support, including GROUPS frames and RANGE intervals.
-- MySQL 8.0+: window functions added; 5.7 has NONE, which is why so much
--   legacy MySQL code uses self-joins and user variables.
-- SQLite 3.25+: supported.
-- Emulating them with correlated subqueries is dramatically slower —
-- if you are on MySQL 5.7, that is an argument for upgrading.

Interview Questions

Beginner: What is the difference between a window function and GROUP BY?

GROUP BY collapses each group into a single summary row, so the individual rows are gone — five hundred employees become eight department rows. A window function computes across a set of related rows but keeps every original row, adding the computed value as another column. So you can show each employee's salary alongside their department's average, or their rank within the department, in one pass.

The window is defined by the OVER clause: PARTITION BY splits rows into independent groups, ORDER BY orders rows within each partition, and the frame decides which rows of the partition are visible to the current row. All three are optional, and omitting PARTITION BY makes the window the entire result set. Before window functions existed you expressed this with a self-join to a grouped subquery — two passes and a join for one idea — which is why they replaced an entire genre of SQL. They also compose with GROUP BY rather than competing with it, because they run afterwards: sum(count(*)) OVER () beside a GROUP BY gives each group's percentage of the total in a single query.

Beginner: Explain row_number(), rank() and dense_rank().

All three assign a position within a partition according to an ORDER BY, and they differ only in how they handle ties. With salaries of 100, 100, 90 and 80, row_number() gives 1, 2, 3, 4 — always distinct, with the tie broken arbitrarily. rank() gives 1, 1, 3, 4 — tied rows share a rank and the next rank skips, like sports standings. dense_rank() gives 1, 1, 2, 3 — tied rows share and there is no gap.

The choice is a requirement, not a preference, because "the top 3" means three different things here. row_number() <= 3 always returns exactly three rows but arbitrarily drops one of the tied employees; rank() <= 3 returns four rows when two tie for first, which is usually what a leaderboard should do; dense_rank() <= 3 means the three highest distinct salaries, which could be many rows. The detail people miss is that row_number() with a non-unique ORDER BY is non-deterministic — which row gets 1 can change between runs or after a plan change — so it needs a unique tiebreaker appended, especially in the very common "latest row per key" pattern where you then filter to rank 1.

Mid: Why can't you filter on a window function in WHERE?

Because of evaluation order. Window functions are computed after FROM, WHERE, GROUP BY and HAVING, and before ORDER BY and LIMIT. So at the point WHERE runs, the window function has not been evaluated and its alias does not exist — the error is the same class as trying to use any SELECT alias in WHERE. The fix is to wrap the query in a subquery or CTE and filter the alias in the outer level, which is why every top-N-per-group solution has that shape. Some engines — Snowflake, BigQuery, DuckDB — add a QUALIFY clause for exactly this, but it is not standard and Postgres and MySQL do not have it.

The more consequential half of the same fact is that a window only sees rows that survived WHERE. Computing a running total while filtering to the last month gives a cumulative figure that restarts at zero on the first of that month rather than continuing from history — the query is doing exactly what it was asked and the chart is wrong. The fix is to compute the window over the full set in a CTE and apply the date filter outside it.

Mid: What is the default window frame, and when does it cause bugs?

With PARTITION BY alone the frame is the whole partition, which is what people expect. Adding ORDER BY silently changes the default to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — so the aggregate becomes a running one. Someone adding an ORDER BY to make output tidier changes every number in that column, with no error.

The second and subtler problem is RANGE versus ROWS. RANGE treats rows with the same ORDER BY value as peers and includes all of them together, so a running total ordered by day shows every row from the same day the full end-of-day total rather than a row-by-row accumulation. Since dates almost always contain duplicates, the default is usually not what is wanted, and ROWS UNBOUNDED PRECEDING is the correct spelling for a true running total.

The most reported version of this is last_value() returning the current row instead of the partition's last row — because the default frame ends at the current row, so the last visible row is the current one. It needs an explicit ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING. A related trap is a moving average written as ROWS BETWEEN 6 PRECEDING, which is the last seven rows; if the series has gaps, that spans more than seven days, and RANGE BETWEEN INTERVAL '6 days' PRECEDING is the honest version.

Senior: Solve gaps and islands — find consecutive runs — and explain the trick.

The problem is identifying maximal runs of consecutive values: login streaks, contiguous uptime windows, blocks of adjacent seats, or missing sequence numbers. The standard solution is to compute a value that is constant within a run and changes at every gap, then group by it.

For consecutive dates, subtracting row_number() from the date does exactly that. Within a run both increase in lockstep so the difference is constant; at a gap the date jumps while the row number does not, so the difference changes and a new group begins. Grouping by that derived value and taking min, max and count yields each run's start, end and length. The same idea works for integer sequences.

The related and more general pattern is a running sum over a boundary flag. Compare each row to its predecessor with lag(), emit 1 when the gap exceeds a threshold and 0 otherwise, then take sum(flag) OVER (PARTITION BY user ORDER BY ts) — that running sum is a session identifier that increments at each boundary. That is how sessionisation is done, and it generalises to any "assign a group id that increments at each change" requirement, including detecting status transitions in an audit table.

Two details worth stating. Comparisons against lag() should use IS DISTINCT FROM rather than <>, or the first row of each partition — where lag is NULL — silently fails the test and disappears. And the whole approach depends on a deterministic ORDER BY, so ties need a unique tiebreaker or the run boundaries move between runs.

Senior: When is a window function the wrong tool?

The clearest case is top-N per group over a large child table. A window ranks every row in the table and then discards all but a few per partition, so returning three orders per user from fifty million orders sorts fifty million rows. LATERAL with an index on (user_id, created_at DESC) reads exactly three rows per user instead. The rule mirrors nested loops versus hash joins: seeking per outer row wins when the outer set is small and the lookup is indexed, and one sorted pass wins otherwise — so I would use LATERAL for a page of users and a window when the ranking over everything is genuinely needed.

Second, windows compute answers rather than caching them. A cumulative total over hundreds of millions of immutable historical rows recomputed on every dashboard load is repeating yesterday's work; that belongs in a materialised view or an incrementally maintained rollup table.

Third, using row_number() = 1 to hide duplicates on read is treating a symptom. The duplicates still accumulate, and every future query has to remember the trick — a unique constraint prevents them instead.

And there are things windows simply cannot express. They cannot be nested or referenced in WHERE, and crucially they are not recursive: a running balance where each row depends on the previously computed value — compound interest, or inventory clamped so it cannot go negative — cannot be written as a window, because a window reads input rows rather than its own output. That requires a recursive CTE. Knowing that boundary saves a lot of time trying to force a frame to do something it structurally cannot.

🏋️ Exercises

1 (easy): Show each employee alongside their department average and their rank, without losing any rows.
Solution 
-- ✗ GROUP BY collapses the detail you wanted to keep
SELECT department, avg(salary) FROM employees GROUP BY department;
-- 8 rows. The employees are gone.

-- ✗ The pre-window workaround: two passes and a join
SELECT e.name, e.salary, d.avg_salary
FROM employees e
JOIN (SELECT department, avg(salary) avg_salary
      FROM employees GROUP BY department) d USING (department);
-- Works, but every extra metric is another subquery.

-- ✓ ONE pass, all rows kept
SELECT name, department, salary,
       avg(salary)  OVER w                       AS dept_avg,
       salary - avg(salary) OVER w               AS vs_avg,
       count(*)     OVER w                       AS dept_size,
       rank()       OVER (PARTITION BY department
                          ORDER BY salary DESC)  AS salary_rank,
       round(100.0 * salary / sum(salary) OVER w, 1) AS pct_of_dept
FROM employees
WINDOW w AS (PARTITION BY department);
-- The named WINDOW defines the partition once. Repeating an identical
-- OVER clause four times is how they drift apart during maintenance —
-- and several windows sharing one clause are computed in a single pass.

-- ── ⚠ THE TRAP: ADDING ORDER BY CHANGES THE MEANING ─────────────────────
avg(salary) OVER (PARTITION BY department)                   -- dept average
avg(salary) OVER (PARTITION BY department ORDER BY hire_date)-- RUNNING avg
-- Adding ORDER BY silently switches the default frame from "the whole
-- partition" to "everything up to the current row". Someone adds it to
-- tidy the output and every number in the column changes, with no error.
-- If you want the whole partition AND an ordering, say so:
avg(salary) OVER (PARTITION BY department ORDER BY hire_date
                  RANGE BETWEEN UNBOUNDED PRECEDING
                            AND UNBOUNDED FOLLOWING)

-- ── PERCENTAGE OF TOTAL, COMBINED WITH GROUP BY ─────────────────────────
SELECT department, count(*) AS headcount,
       round(100.0 * count(*) / sum(count(*)) OVER (), 1) AS pct
FROM employees GROUP BY department;
-- sum(count(*)) OVER () looks bizarre and is idiomatic: the window runs
-- AFTER GROUP BY, so it aggregates the grouped rows.
2 (easy): Get the most recent order per customer. Two ways, and one non-determinism bug.
Solution 
-- ✗ THE SUBQUERY VERSION — returns TWO rows on a tie
SELECT * FROM orders o
WHERE created_at = (SELECT max(created_at) FROM orders
                    WHERE user_id = o.user_id);

-- ✓ WINDOW FUNCTION
SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY user_id
                               ORDER BY created_at DESC, id DESC) AS rn
  FROM orders
) t WHERE rn = 1;

-- ── THE BUG THIS FIXES ──────────────────────────────────────────────────
ORDER BY created_at DESC              -- ✗ two orders in the same second
ORDER BY created_at DESC, id DESC     -- ✓ deterministic
-- Without a unique tiebreaker, WHICH row gets rn = 1 is whatever the
-- engine produced — and it can differ between runs, after a VACUUM, or
-- when the plan changes. The query passes every test and returns a
-- different order on Tuesday.

-- ── WHY THE SUBQUERY GOES IN A WRAPPER ──────────────────────────────────
SELECT *, row_number() OVER (...) AS rn FROM orders WHERE rn = 1;
-- ✗ ERROR: column "rn" does not exist.
-- Window functions run AFTER WHERE, so the alias does not exist yet.
-- Same reason a SELECT alias is illegal in WHERE.

-- ── ✓ POSTGRES SHORTCUT ─────────────────────────────────────────────────
SELECT DISTINCT ON (user_id) *
FROM orders
ORDER BY user_id, created_at DESC, id DESC;
-- The ORDER BY must START with the DISTINCT ON columns. Shorter, and
-- often faster — it can stop at the first row per group instead of
-- numbering all of them.

-- ── ✓ AND WHEN THE TABLE IS LARGE ───────────────────────────────────────
SELECT u.id, o.*
FROM users u
CROSS JOIN LATERAL (SELECT * FROM orders WHERE user_id = u.id
                    ORDER BY created_at DESC, id DESC LIMIT 1) o;
CREATE INDEX ON orders (user_id, created_at DESC, id DESC);
-- Reads ONE row per user via the index instead of sorting 50M orders to
-- keep 100K of them.

-- ── THE PATTERN GENERALISES ─────────────────────────────────────────────
-- current price per product · newest status per ticket · latest version
-- per document · most recent reading per sensor. Change rn = 1 to
-- rn <= 3 for top-N.
3 (medium): Build a revenue dashboard: running total, 7-day moving average, and day-over-day growth.
Solution 
SELECT day, revenue,
       sum(revenue) OVER (ORDER BY day ROWS UNBOUNDED PRECEDING)
         AS cumulative,
       round(avg(revenue) OVER (ORDER BY day
              RANGE BETWEEN INTERVAL '6 days' PRECEDING AND CURRENT ROW), 2)
         AS ma7,
       revenue - lag(revenue) OVER (ORDER BY day)
         AS dod_change,
       round(100.0 * (revenue - lag(revenue) OVER (ORDER BY day))
             / nullif(lag(revenue) OVER (ORDER BY day), 0), 1)
         AS dod_pct,
       revenue - lag(revenue, 7) OVER (ORDER BY day)
         AS vs_same_day_last_week
FROM daily_sales
ORDER BY day;

-- ── EVERY FRAME DECISION, AND WHY ───────────────────────────────────────

-- ROWS UNBOUNDED PRECEDING, not the default
--   The default with ORDER BY is RANGE, which treats equal order values
--   as PEERS. If two rows share a day, both show the full end-of-day
--   total instead of a true row-by-row accumulation. With one row per
--   day it happens to agree; the moment the grain changes it silently
--   does not. Say ROWS.

-- RANGE BETWEEN INTERVAL '6 days' PRECEDING, not ROWS BETWEEN 6 PRECEDING
--   ROWS means "the last 7 ROWS". If a day is missing — a holiday, an
--   outage, a day with no sales — that window silently spans 8 or 9
--   days and the "7-day average" is not one. RANGE with an interval is
--   defined in TIME, so gaps are handled correctly.

-- nullif(lag(...), 0)
--   Yesterday's revenue of 0 would be a division-by-zero error, which
--   fails the whole query rather than one row. nullif turns it into
--   NULL, which renders as "no data" instead.

-- lag(revenue, 7)
--   Weekly seasonality is real: comparing Monday to Sunday is noise.
--   Same-day-last-week is the honest comparison for a business metric.

-- ── ⚠ THE BUG THAT BREAKS THE CUMULATIVE LINE ───────────────────────────
SELECT day, sum(revenue) OVER (ORDER BY day) AS cumulative
FROM daily_sales
WHERE day >= '2026-06-01';        -- ✗ the running total RESTARTS AT ZERO
-- Window functions only see rows that survived WHERE. Filtering first
-- discards the history the cumulative sum was supposed to build on.

WITH running AS (                 -- ✓ compute over EVERYTHING...
  SELECT day, revenue, sum(revenue) OVER (ORDER BY day
                                          ROWS UNBOUNDED PRECEDING) AS cum
  FROM daily_sales)
SELECT * FROM running WHERE day >= '2026-06-01';   -- ...then filter

-- ── AND THE MISSING-DAYS PROBLEM ────────────────────────────────────────
-- A day with no sales produces NO ROW, so the chart draws a straight
-- line through the outage and the moving average skips it. Generate the
-- axis first (see Aggregates):
FROM generate_series(:from, :to, '1 day') d(day)
LEFT JOIN daily_sales s ON s.day = d.day
4 (medium): Find each user's longest streak of consecutive daily logins.
Solution 
-- ── THE TRICK ───────────────────────────────────────────────────────────
-- Within a run of consecutive dates, both the date and the row number
-- increase by 1 each step, so (date - row_number) is CONSTANT. At a gap
-- the date jumps but the row number does not, so the difference changes
-- and a new group begins. Group by that value and you have the runs.

WITH numbered AS (
  SELECT user_id, day,
         row_number() OVER (PARTITION BY user_id ORDER BY day) AS rn
  FROM (SELECT DISTINCT user_id, day::date AS day FROM logins) d
  --          ^^^^^^^^ two logins on one day would break the arithmetic
),
runs AS (
  SELECT user_id, day, day - rn * interval '1 day' AS grp
  FROM numbered
)
SELECT user_id,
       min(day)  AS streak_start,
       max(day)  AS streak_end,
       count(*)  AS streak_length
FROM runs
GROUP BY user_id, grp
ORDER BY streak_length DESC;

-- ── WALK THROUGH IT ─────────────────────────────────────────────────────
--  day        rn   day - rn
--  2026-03-01  1   2026-02-28  ┐
--  2026-03-02  2   2026-02-28  ├ run A (3 days)
--  2026-03-03  3   2026-02-28  ┘
--  2026-03-07  4   2026-03-03  ┐ run B — the gap shifted the constant
--  2026-03-08  5   2026-03-03  ┘

-- ── THE GENERAL FORM: A RUNNING SUM OVER A BOUNDARY FLAG ────────────────
-- Works for any "new group when X changes" rule, not just dates:
WITH flagged AS (
  SELECT *, CASE WHEN day - lag(day) OVER (PARTITION BY user_id
                                           ORDER BY day) > 1
                 THEN 1 ELSE 0 END AS is_new_run
  FROM (SELECT DISTINCT user_id, day::date AS day FROM logins) d
)
SELECT user_id, min(day), max(day), count(*)
FROM (SELECT *, sum(is_new_run) OVER (PARTITION BY user_id ORDER BY day)
                  AS grp
      FROM flagged) t
GROUP BY user_id, grp;
-- A running sum of a 0/1 flag is a group id that increments at each
-- boundary. Worth memorising — it is the same shape as sessionisation:

-- ── SESSIONISATION: split events on a 30-minute gap ─────────────────────
SELECT *, sum(CASE WHEN ts - lag(ts) OVER (PARTITION BY user_id ORDER BY ts)
                        > interval '30 min' THEN 1 ELSE 0 END)
            OVER (PARTITION BY user_id ORDER BY ts) AS session_id
FROM events;

-- ── ALSO USED FOR ───────────────────────────────────────────────────────
-- contiguous seat blocks · uptime/downtime windows · missing invoice
-- numbers · detecting status transitions in an audit table
-- (use IS DISTINCT FROM there, or the first row's NULL lag is skipped)
5 (hard): A "top 3 products per category" query works but takes 40 seconds. Fix it.
Solution 
-- ✗ BEFORE — 40s over 80M order_items, 200 categories
WITH ranked AS (
  SELECT p.category_id, p.id, p.name, sum(oi.quantity) AS units,
         row_number() OVER (PARTITION BY p.category_id
                            ORDER BY sum(oi.quantity) DESC) AS rn
  FROM products p
  JOIN order_items oi ON oi.product_id = p.id
  GROUP BY p.category_id, p.id, p.name
)
SELECT * FROM ranked WHERE rn <= 3;

-- ── EXPLAIN SAYS ────────────────────────────────────────────────────────
-- HashAggregate over 80M rows → Sort (2.1 GB, spilled to disk) → WindowAgg
-- It aggregates every product, SORTS all 400,000 of them, numbers them,
-- and then discards 399,400 rows to return 600.

-- ── FIX 1: PRE-AGGREGATE, THEN RANK THE SMALL RESULT ────────────────────
WITH totals AS (                        -- 80M rows → 400K, ONCE
  SELECT product_id, sum(quantity) AS units
  FROM order_items GROUP BY product_id
),
ranked AS (                             -- sort 400K, not 80M
  SELECT p.category_id, p.id, p.name, t.units,
         row_number() OVER (PARTITION BY p.category_id
                            ORDER BY t.units DESC, p.id) AS rn
  FROM products p JOIN totals t ON t.product_id = p.id
)
SELECT * FROM ranked WHERE rn <= 3;
-- ~6s. Aggregating before the window is the single biggest win: the
-- window now sorts the aggregate, not the fact table.
-- Note `, p.id` — without a tiebreaker, which product wins a tie varies
-- between runs.

-- ── FIX 2: LATERAL — seek instead of sort ───────────────────────────────
WITH totals AS (
  SELECT product_id, sum(quantity) AS units
  FROM order_items GROUP BY product_id
)
SELECT c.id, c.name, t.*
FROM categories c
CROSS JOIN LATERAL (
  SELECT p.id, p.name, tt.units
  FROM products p JOIN totals tt ON tt.product_id = p.id
  WHERE p.category_id = c.id
  ORDER BY tt.units DESC, p.id
  LIMIT 3                               -- ← only 3 rows per category
) t;
-- 200 categories × 3 rows = 600 rows examined for the ranking step.
-- THE RULE: LATERAL wins when the outer set is SMALL and the inner
-- lookup is INDEXED. A window function wins when you need the rank over
-- everything anyway, or when no useful index exists.

-- ── FIX 3: MATERIALISE — the real answer for a dashboard ────────────────
CREATE MATERIALIZED VIEW product_units AS
SELECT product_id, sum(quantity) AS units FROM order_items GROUP BY 1;
CREATE UNIQUE INDEX ON product_units (product_id);
REFRESH MATERIALIZED VIEW CONCURRENTLY product_units;   -- nightly
-- ~200ms. Historical order_items do not change, so recomputing an
-- 80M-row aggregate on every page load is repeating yesterday's work.
-- Windows compute answers; they do not cache them.

-- ── ALSO CHECK ──────────────────────────────────────────────────────────
CREATE INDEX ON order_items (product_id) INCLUDE (quantity);  -- index-only
SET work_mem = '256MB';   -- the 2.1 GB sort SPILLED TO DISK. Look for
                          -- "external merge Disk:" in EXPLAIN ANALYZE —
                          -- an in-memory sort is several times faster.
-- Consolidate windows: several different OVER clauses each need their
-- own sort. Identical ones are computed in a single pass — use a named
-- WINDOW so matches are visible.
6 (hard): Compute a running inventory balance that can never go below zero. Explain why a window function cannot do it.
Solution 
-- movements: +100, -30, -200, +50   starting from 0
-- Required: the balance never goes negative; an oversized withdrawal
-- takes only what is available.
--   +100 → 100
--   -30  →  70
--   -200 →   0   (only 70 was available; 130 rejected)
--   +50  →  50

-- ── ✗ THE WINDOW ATTEMPT ────────────────────────────────────────────────
SELECT ts, delta,
       greatest(0, sum(delta) OVER (ORDER BY ts ROWS UNBOUNDED PRECEDING))
FROM movements;
--   +100 → 100
--   -30  →  70
--   -200 → greatest(0, -130) = 0     ✓ by luck
--   +50  → greatest(0,  -80) = 0     ✗ WRONG — should be 50
--
-- The running sum still carries the -130 forward internally. Clamping
-- the OUTPUT does not clamp the STATE.

-- ── WHY NO FRAME CAN FIX THIS ───────────────────────────────────────────
-- A window function reads INPUT ROWS. Each row's value is a function of
-- other rows' INPUTS, never of another row's COMPUTED OUTPUT. Here row N
-- depends on the clamped balance at row N-1 — that is genuine recursion,
-- and it is outside what the window model can express. No frame, no
-- combination of lag() and sum(), no ordering will do it.
--
-- The general test: if the formula references its OWN previous result,
-- it is not a window function.

-- ── ✓ RECURSIVE CTE ─────────────────────────────────────────────────────
WITH RECURSIVE ordered AS (
  SELECT ts, delta, row_number() OVER (ORDER BY ts, id) AS rn
  FROM movements
),
running AS (
  SELECT rn, ts, delta,
         greatest(0, delta) AS balance
  FROM ordered WHERE rn = 1
UNION ALL
  SELECT o.rn, o.ts, o.delta,
         greatest(0, r.balance + o.delta)      -- ← r.balance is the
  FROM ordered o                               --   PREVIOUS COMPUTED
  JOIN running r ON o.rn = r.rn + 1            --   value
)
SELECT ts, delta, balance FROM running ORDER BY rn;
-- Each iteration reads the previous iteration's OUTPUT. That is exactly
-- the capability a window lacks.
-- ⚠ It is inherently SEQUENTIAL — one row per iteration, no
--   parallelism. Fine for thousands of rows, wrong for millions.

-- ── THE SAME SHAPE APPEARS IN ───────────────────────────────────────────
-- compound interest · a queue drained by variable capacity · inventory
-- with backorders · rate limiters with a token bucket · any state
-- machine over an ordered event stream

-- ── ✓ WHAT I WOULD ACTUALLY SHIP ────────────────────────────────────────
-- Store the balance as a COLUMN maintained on write:
UPDATE inventory SET qty = greatest(0, qty + :delta) WHERE id = :id
RETURNING qty;
-- O(1) reads, correct by construction, and the clamping rule lives in
-- one place. Recomputing a whole history to answer "what is the balance
-- now?" is the wrong shape for an operational question — the recursive
-- CTE is for AUDIT and BACKFILL, where you must reconstruct history
-- from the event log.
--
-- ⚠ And note the clamping makes the operation ORDER-DEPENDENT and
--   non-commutative: applying the same movements in a different order
--   gives a different answer. That is a business rule, so it belongs
--   somewhere explicit, tested, and written down — not implicit in a
--   greatest() buried in a reporting query.

🎯 Key Takeaways

  • Window functions aggregate across related rows without collapsing them, replacing a genre of self-joins.
  • OVER has three parts — partition, order, frame — and each changes the meaning.
  • Adding ORDER BY to a partition aggregate silently makes it a running aggregate.
  • The default frame is RANGE, which groups ties as peers; use ROWS for a true running total.
  • last_value needs an explicit frame ending at UNBOUNDED FOLLOWING, or it returns the current row.
  • Pick the ranking function by tie behaviour, and always give row_number() a unique tiebreaker.
  • Windows run after WHERE, so you cannot filter on them directly and they never see filtered-out rows.
  • A running sum over a 0/1 boundary flag is the general idiom for gaps, islands and sessionisation.
  • For top-N per group over a large child table, LATERAL with the right index beats ranking everything.
  • Windows cannot reference their own previous output — a clamped running balance needs a recursive CTE or a maintained column.
