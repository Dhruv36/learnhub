INSERT, UPDATE, DELETE Basics

What you'll master: the safety discipline that prevents the most famous production disaster in SQL, bulk loading with multi-row inserts and COPY, RETURNING to avoid extra round trips, upserts as the race-free alternative to select-then-insert and the concurrency subtleties they still have, why a large DELETE causes lock contention, replication lag and table bloat — and how to chunk it, soft delete and the unique-constraint problem it creates, and how UPDATE physically works so that MVCC bloat and write amplification stop being mysterious. Prerequisites: SELECT & Filtering and JOINs.

Part 1 — INSERT

INSERT INTO users (name, email, score) VALUES ('Asha', 'a@b.com', 92);

-- ── ALWAYS NAME THE COLUMNS ─────────────────────────────────────────────
INSERT INTO users VALUES ('Asha', 'a@b.com', 92);   -- ✗ positional
-- Depends on column ORDER. Someone adds a column in the middle, or
-- reorders during a migration, and every insert silently writes values
-- into the wrong fields. No error — `score` ends up in `phone`.

-- ── MULTI-ROW: ONE STATEMENT, NOT N ─────────────────────────────────────
INSERT INTO users (name, email) VALUES
  ('Bo', 'bo@x.com'),
  ('Cy', 'cy@x.com'),
  ('Di', 'di@x.com');
-- One parse, one plan, one round trip, one transaction. Inserting 10,000
-- rows one statement at a time is typically 50-100x slower — and almost
-- all of that is round-trip latency, not database work.

-- ── INSERT ... SELECT ───────────────────────────────────────────────────
INSERT INTO archive (id, name, archived_at)
SELECT id, name, now() FROM users WHERE last_login < '2024-01-01';
-- Never leaves the database. Moving a million rows through the
-- application to write them back is pure waste.

-- ── RETURNING: GET GENERATED VALUES BACK ────────────────────────────────
INSERT INTO users (name) VALUES ('Ed')
RETURNING id, created_at;              -- Postgres, and MariaDB
-- Without it: INSERT, then SELECT to find the id — two round trips, and
-- a race if you look it up by a non-unique column.
-- MySQL has no RETURNING; use LAST_INSERT_ID() on the same connection.

INSERT INTO orders (...) SELECT ... RETURNING id;   -- works with SELECT too
UPDATE ... RETURNING *;   DELETE ... RETURNING *;   -- and with UPDATE/DELETE

-- ── BULK LOADING: COPY, NOT INSERT ──────────────────────────────────────
COPY users (name, email) FROM '/path/file.csv' CSV HEADER;      -- Postgres
COPY users (name, email) FROM STDIN;                            -- from an app
LOAD DATA INFILE 'file.csv' INTO TABLE users;                   -- MySQL
-- COPY bypasses per-row statement overhead entirely: often 10-20x faster
-- than even multi-row INSERT for millions of rows.
--
-- For a very large load, dropping non-essential INDEXES first and
-- rebuilding them afterwards is usually faster than maintaining every
-- index per row — each index is a separate write per inserted row.

-- ── DEFAULTS AND GENERATED COLUMNS ──────────────────────────────────────
CREATE TABLE users (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- standard
  created_at timestamptz NOT NULL DEFAULT now(),
  email      citext NOT NULL UNIQUE,
  full_name  text GENERATED ALWAYS AS (first || ' ' || last) STORED
);
-- Let the DATABASE supply ids and timestamps. An application-generated
-- created_at is the clock of whichever machine happened to run the code,
-- which drifts and is not monotonic across servers.

-- ⚠ SEQUENCES ARE NOT TRANSACTIONAL. A rolled-back insert still consumes
--   the id, so identity columns have GAPS. That is correct behaviour, not
--   a bug — but it means you cannot use "max(id) - min(id)" as a count,
--   and gap-free numbering (invoice numbers) needs a different mechanism.

Part 2 — UPDATE and the WHERE Discipline

UPDATE users SET score = score + 10 WHERE id = 42;
UPDATE users SET tier = 'gold', updated_at = now() WHERE spend > 1000;

UPDATE users SET score = 0;          -- 💀 EVERY ROW. No confirmation.
DELETE FROM users;                   -- 💀 EVERY ROW.

-- ── THE SAFETY PROCEDURE ────────────────────────────────────────────────
-- 1. SELECT with the EXACT same WHERE, and read the count
SELECT count(*) FROM users WHERE last_login < '2020-01-01';   -- 1,204

-- 2. Run the write inside a transaction
BEGIN;
UPDATE users SET active = false WHERE last_login < '2020-01-01';
-- UPDATE 1204          ← does this match step 1?
-- 3. only then
COMMIT;                  -- or ROLLBACK; if the number is wrong
-- The row count is the check. A mismatch means the WHERE is not what you
-- thought — and inside a transaction that costs nothing.

-- ── DEFENCES WORTH ENABLING ─────────────────────────────────────────────
SET SESSION sql_safe_updates = 1;    -- MySQL: rejects UPDATE/DELETE with
                                     -- no WHERE on an indexed column
-- Postgres has no built-in equivalent; psql users often set
--   \set AUTOCOMMIT off
-- so every statement is in a transaction until they type COMMIT.
-- Production access should be read-only by default, with writes going
-- through reviewed migrations rather than a console.

-- ── UPDATE ... FROM: SETTING FROM ANOTHER TABLE ─────────────────────────
UPDATE orders o                              -- Postgres
SET    customer_name = c.name
FROM   customers c
WHERE  c.id = o.customer_id AND o.customer_name IS NULL;

UPDATE orders o JOIN customers c ON c.id = o.customer_id   -- MySQL
SET    o.customer_name = c.name;

-- ⚠ If the FROM side matches MULTIPLE rows per target row, Postgres picks
--   one ARBITRARILY and does not warn. Verify the join is unique first,
--   or you get a non-deterministic result that differs between runs.

-- ── ORDER OF ASSIGNMENT ─────────────────────────────────────────────────
UPDATE t SET a = b, b = a;      -- SWAPS them. All right-hand sides are
                                -- evaluated against the ROW AS IT WAS.
-- SQL is not procedural here — this is one of the few places that
-- surprises people coming from imperative languages.

-- ── CONDITIONAL UPDATE INSTEAD OF READ-MODIFY-WRITE ─────────────────────
-- ✗ RACE: two sessions both read 100, both write 110. One increment lost.
score = SELECT score FROM users WHERE id = 1;   -- app reads 100
UPDATE users SET score = 110 WHERE id = 1;      -- app writes back

-- ✓ ATOMIC: the database computes it, holding the row lock
UPDATE users SET score = score + 10 WHERE id = 1;

-- ✓ OPTIMISTIC LOCKING, when the app must compute the value
UPDATE users SET score = :new, version = version + 1
WHERE id = 1 AND version = :version_i_read;
-- 0 rows affected means someone else changed it — re-read and retry.
-- Checking the affected-row count is the whole mechanism.
Key insight: the affected-row count is the single most useful safety signal in DML, and almost every disaster in this lesson comes from not looking at it. It tells you whether an UPDATE hit the one row you meant or all four million, whether an optimistic- locking write lost a race, whether a chunked delete has finished, and whether an upsert inserted or updated. Wrapping a write in a transaction costs nothing and turns that number into something you can act on before it is permanent — which is why "SELECT first, then BEGIN, then check the count" is a habit rather than a ceremony.

Part 3 — DELETE, TRUNCATE, and Soft Delete

DELETE FROM sessions WHERE expires_at < now();
DELETE FROM orders WHERE id = 42 RETURNING *;      -- see what you removed

-- ── DELETE vs TRUNCATE ──────────────────────────────────────────────────
--   DELETE            row-by-row · fires triggers · WAL-logged per row ·
--                     transactional and rollback-able · WHERE allowed ·
--                     leaves dead tuples that need VACUUM · SLOW at scale
--   TRUNCATE          deallocates whole pages · no per-row triggers ·
--                     resets identity sequences · instant regardless of
--                     size · no WHERE · takes an ACCESS EXCLUSIVE lock
--
-- TRUNCATE *is* transactional in Postgres (it can be rolled back); in
-- MySQL/InnoDB it causes an implicit commit and cannot. That difference
-- catches people migrating between the two.
TRUNCATE staging_import RESTART IDENTITY CASCADE;

-- ── FOREIGN KEYS DECIDE WHAT HAPPENS TO CHILDREN ────────────────────────
REFERENCES users(id) ON DELETE RESTRICT   -- default: refuse (safest)
                     ON DELETE CASCADE    -- delete the children too
                     ON DELETE SET NULL   -- orphan them deliberately
-- ⚠ CASCADE is convenient and dangerous: deleting one user can silently
--   remove millions of rows across a dozen tables, in one long
--   transaction, holding locks. And it CANNOT use an index unless you
--   created one on the child's foreign key — Postgres does not do that
--   for you, so every cascade is a full scan of every child table.

-- ── SOFT DELETE ─────────────────────────────────────────────────────────
ALTER TABLE users ADD COLUMN deleted_at timestamptz;
UPDATE users SET deleted_at = now() WHERE id = 42;      -- "delete"
SELECT * FROM users WHERE deleted_at IS NULL;           -- every query,
                                                        -- forever

-- COSTS, honestly:
-- 1. EVERY query must filter. One forgotten filter and deleted data
--    reappears in a UI, an export, or an email campaign.
-- 2. UNIQUE CONSTRAINTS BREAK. A deleted user holds a@b.com forever, so
--    the address can never be reused:
CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL;  -- partial
--    (MySQL has no partial indexes; the common workaround is a
--     generated column or including deleted_at in the key.)
-- 3. The table grows forever; indexes cover rows nobody queries.
-- 4. GDPR/CCPA erasure requires ACTUAL deletion, so you need a purge job
--    regardless — soft delete defers the problem, it does not remove it.

-- ✓ Make it structural, not a convention:
CREATE VIEW active_users AS SELECT * FROM users WHERE deleted_at IS NULL;
-- Application code queries the view. Forgetting the filter is then
-- impossible rather than merely discouraged. Postgres row-level security
-- can enforce it even harder.

-- ── ARCHIVE-THEN-DELETE: often the better answer ────────────────────────
BEGIN;
INSERT INTO orders_archive SELECT * FROM orders WHERE created_at < :cutoff;
DELETE FROM orders                              WHERE created_at < :cutoff;
COMMIT;
-- History preserved, the hot table stays small, and normal queries need
-- no filter at all. This is what most teams actually want when they
-- reach for soft delete.

Part 4 — Upserts

-- ── THE RACE YOU ARE FIXING ─────────────────────────────────────────────
-- Session A: SELECT ... WHERE key='visits'  → not found
-- Session B: SELECT ... WHERE key='visits'  → not found
-- Session A: INSERT                          → ok
-- Session B: INSERT                          → duplicate key error
-- Under load this happens constantly. Checking first does not help,
-- because the check and the write are not atomic.

-- ── POSTGRES: ON CONFLICT ───────────────────────────────────────────────
INSERT INTO counters (key, n) VALUES ('visits', 1)
ON CONFLICT (key) DO UPDATE SET n = counters.n + 1;
-- Atomic. `counters.n` is the EXISTING row; `excluded.n` is the value
-- that was proposed:
INSERT INTO users (email, name, updated_at)
VALUES (:email, :name, now())
ON CONFLICT (email) DO UPDATE
SET name = excluded.name, updated_at = excluded.updated_at
WHERE users.name IS DISTINCT FROM excluded.name    -- skip no-op writes
RETURNING id, (xmax = 0) AS was_inserted;          -- did it insert or
                                                   -- update?
INSERT ... ON CONFLICT DO NOTHING;                 -- ignore duplicates

-- ⚠ THE CONFLICT TARGET NEEDS A UNIQUE CONSTRAINT OR EXCLUSION
--   CONSTRAINT. Without one there is nothing for the database to detect
--   a conflict against, and it errors at parse time. The constraint is
--   the mechanism, not decoration.

-- ── MYSQL ───────────────────────────────────────────────────────────────
INSERT INTO counters (key, n) VALUES ('visits', 1)
ON DUPLICATE KEY UPDATE n = n + 1;
-- Fires on ANY unique key conflict, not one you name — so with two
-- unique constraints you cannot tell which one matched.

-- ── STANDARD SQL: MERGE ─────────────────────────────────────────────────
MERGE INTO target t USING source s ON t.id = s.id
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;     -- Postgres 15+, SQL Server, Oracle
-- More expressive (it can DELETE too), but NOT atomic against concurrent
-- inserts the way ON CONFLICT is — MERGE can still raise a unique
-- violation under concurrency. For simple insert-or-update, prefer
-- ON CONFLICT.

-- ── THE PARTS PEOPLE MISS ───────────────────────────────────────────────
-- 1. A failed ON CONFLICT DO NOTHING still CONSUMES A SEQUENCE VALUE.
--    High-conflict upserts burn through identity ranges quickly.
-- 2. ON CONFLICT takes a row lock, so many sessions upserting the SAME
--    key serialise on it — a global counter row becomes the bottleneck.
--    Shard the counter across N rows and sum them if that matters.
-- 3. It is a WRITE even when nothing changed: MVCC creates a new row
--    version, indexes update, WAL grows, replicas receive it. The
--    `WHERE ... IS DISTINCT FROM` clause above avoids that.
-- 4. DEADLOCK RISK on multi-row upserts: two sessions upserting the same
--    keys in different orders deadlock. Sort the batch by key before
--    sending it.

Part 5 — Large Writes at Scale

-- ── WHY ONE BIG DELETE IS A PRODUCTION INCIDENT ─────────────────────────
DELETE FROM events WHERE created_at < '2024-01-01';    -- 200M rows
-- 1. LOCKS held on every affected row for the whole transaction
-- 2. The transaction cannot be interrupted without losing all the work
-- 3. WAL grows by the size of the change; replicas fall behind, and a
--    replica applying it single-threaded can lag for hours
-- 4. Postgres leaves 200M DEAD TUPLES that VACUUM must clean up; the
--    table does not shrink and queries stay slow afterwards
-- 5. It can block autovacuum from cleaning ANY table in the meantime

-- ── ✓ CHUNK IT ──────────────────────────────────────────────────────────
DELETE FROM events
WHERE id IN (SELECT id FROM events
             WHERE created_at < '2024-01-01'
             ORDER BY id LIMIT 10000);
-- Repeat until 0 rows are affected, with a short sleep between batches so
-- replicas and autovacuum can catch up. Each chunk is its own
-- transaction: interruptible, resumable, and it never holds locks long.
-- (MySQL supports DELETE ... LIMIT directly.)

-- ── ✓✓ BETTER: PARTITION AND DROP ───────────────────────────────────────
CREATE TABLE events (...) PARTITION BY RANGE (created_at);
ALTER TABLE events DETACH PARTITION events_2023;
DROP TABLE events_2023;
-- Instant, no dead tuples, no WAL flood, no lock contention. If a table
-- has a retention policy, partition it BEFORE it gets large — retrofitting
-- partitioning onto a 200M-row table is itself a migration project.
-- See Scaling.

-- ── THE SAME APPLIES TO UPDATES ─────────────────────────────────────────
UPDATE users SET tier = 'standard' WHERE tier IS NULL;   -- 50M rows
-- In Postgres an UPDATE writes a NEW row version and marks the old one
-- dead — physically the same cost as a delete plus an insert. Every
-- index on the table is updated too, so a wide table with 8 indexes does
-- 9 writes per row. Chunk it the same way.

-- ── BACKFILLING A NEW COLUMN, SAFELY ────────────────────────────────────
ALTER TABLE users ADD COLUMN tier text;                 -- instant (no
                                                        -- default = no
                                                        -- rewrite)
-- then backfill in chunks, then:
ALTER TABLE users ALTER COLUMN tier SET NOT NULL;       -- after the data
                                                        -- is there
-- ⚠ Adding a column WITH a volatile default rewrote the whole table on
--   older Postgres (before 11) and still does in some engines — an
--   ACCESS EXCLUSIVE lock for the duration, which is an outage on a
--   large table.

-- ── ALWAYS SET A STATEMENT TIMEOUT FOR MIGRATIONS ───────────────────────
SET lock_timeout = '5s';          -- fail fast rather than queue behind a
SET statement_timeout = '30s';    -- long query and block everything
-- A migration that waits for a lock does not just wait — every query
-- arriving after it queues behind it too. That is how one ALTER TABLE
-- takes down a service.

Part 6 — How Writes Physically Work

-- ── AN UPDATE IS NOT AN EDIT IN PLACE (Postgres MVCC) ───────────────────
UPDATE users SET score = 10 WHERE id = 1;
-- 1. The existing row version is marked dead (xmax set)
-- 2. A COMPLETELY NEW row version is written
-- 3. Every index entry pointing at the row is updated to the new location
-- 4. The old version stays until VACUUM reclaims it
--
-- Consequences that explain a lot of production behaviour:
-- * a table of "only 1M rows" can occupy 10GB after heavy updates (BLOAT)
-- * UPDATE cost scales with the NUMBER OF INDEXES, not just the changed
--   column — 8 indexes means 8 extra writes per row
-- * a long-running SELECT holds back VACUUM, because the old versions
--   might still be visible to it. An idle-in-transaction session is the
--   classic cause of unexplained table growth.
-- * HOT (heap-only tuple) updates avoid the index writes IF no indexed
--   column changed and the page has free space — which is why leaving
--   fillfactor headroom on update-heavy tables helps.

SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;

-- MySQL/InnoDB updates in place and keeps old versions in an UNDO LOG
-- instead. Different mechanism, similar consequence: long transactions
-- make undo grow and slow everything down.

-- ── WRITE AMPLIFICATION ─────────────────────────────────────────────────
-- One logical row write becomes:
--   the WAL record  +  the heap page  +  one entry per index
--   +  the replica's copy of all of it
-- This is why "just add an index" is not free, and why bulk loads are
-- faster with indexes dropped and rebuilt afterwards.

-- ── TRIGGERS RUN PER ROW ────────────────────────────────────────────────
CREATE TRIGGER audit AFTER UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION log_change();
-- A 10M-row UPDATE now executes 10M function calls inside the same
-- transaction. Triggers are invisible in application code and are a
-- frequent reason a "simple" bulk update runs for hours.
FOR EACH STATEMENT     -- runs ONCE; use with transition tables when you
                       -- only need aggregate effects

-- ── ORDER YOUR WRITES TO AVOID DEADLOCKS ────────────────────────────────
-- Session A: UPDATE accounts WHERE id=1; then id=2
-- Session B: UPDATE accounts WHERE id=2; then id=1
-- → deadlock. The database kills one; the application must retry.
-- Prevention: always touch rows in a consistent order (sort your batch
-- by primary key), keep transactions short, and expect to retry
-- serialisation failures. See Isolation Levels & Locking.

Interview Questions

Beginner: How do you safely run a large UPDATE in production?

Start by running a SELECT count(*) with the exact same WHERE clause, so you know how many rows should change before anything changes. Then run the UPDATE inside an explicit transaction and compare the reported affected-row count against that number — if it does not match, the WHERE is not doing what you thought and you ROLLBACK at no cost. Only commit when the number is right. That row count is the whole safety mechanism, and skipping the check is what turns a typo into an incident.

For genuinely large updates there is a second concern beyond correctness: a single statement touching millions of rows holds locks for its whole duration, generates a proportional amount of write-ahead log that replicas must replay, and in Postgres leaves behind dead row versions that bloat the table. So I would chunk it — update ten thousand rows at a time, each in its own transaction, with a brief pause between batches — which is interruptible, resumable, and lets autovacuum and replication keep pace. Running it during low traffic and setting a lock_timeout so it fails fast rather than queueing behind another query are the other two habits worth having.

Beginner: Why is an upsert better than checking then inserting?

Because the check and the write are two separate operations, and another session can act in between. Two requests both query for a key, both find nothing, and both insert — one gets a unique-constraint violation, or if there is no constraint, you silently get duplicate rows. Under load this is not rare; it is constant, and it is the classic bug behind duplicate user records and double-counted metrics.

INSERT … ON CONFLICT DO UPDATE makes the database perform the detection and the write as one atomic operation, using a unique constraint as the mechanism — which is why the constraint is required rather than optional. It is also a single round trip. The details worth knowing are that excluded refers to the row you proposed while the table name refers to the existing row, that a conflict still consumes a sequence value even when nothing is inserted, and that many sessions upserting the same key serialise on that row's lock, so a single global counter row becomes a bottleneck. MySQL spells it ON DUPLICATE KEY UPDATE but fires on any unique key rather than one you name.

Mid: What are the real costs of soft delete?

Four, and they compound. Every query in the system must now filter on deleted_at IS NULL, and a single forgotten filter resurfaces deleted data in a UI, an export, or worse, an email campaign — the failure is silent and the blast radius is reputational. Unique constraints break, because a deleted user still occupies their email address forever, so the address can never be reused; the fix is a partial unique index restricted to non-deleted rows, which MySQL does not support and needs a workaround. The table and all its indexes grow without bound, covering rows nobody ever queries. And regulatory erasure requests require genuine deletion regardless, so you end up needing a purge job anyway — soft delete defers the problem rather than removing it.

Where it genuinely helps is recoverability and audit: an accidental deletion is an UPDATE away from being undone, and referential history stays intact for reporting. But I would make it structural rather than conventional — expose an active_users view, or use row-level security, so omitting the filter is impossible rather than merely discouraged. Often the better answer is archive-then-delete: copy the rows to an archive table in the same transaction and delete them from the hot table. History is preserved, the working set stays small, and normal queries need no filter at all, which is usually what people actually wanted.

Mid: Why does deleting millions of rows cause problems well beyond the delete itself?

Because the statement is only the visible part. It holds locks on every affected row for the entire transaction, so anything touching those rows waits, and in Postgres a long transaction also prevents autovacuum from reclaiming dead tuples anywhere, not just in that table. It generates write-ahead log proportional to the data removed, which replicas must receive and replay — often single-threaded — so read replicas can fall hours behind and start serving stale data or get taken out of rotation. And the transaction is all-or-nothing, so cancelling it after three hours throws away three hours of work and then spends time rolling back.

Afterwards, in Postgres the space is not returned: the deleted rows become dead tuples that vacuum must clean, the table stays physically the same size, and until that happens scans still read the dead pages, so queries remain slow after the delete "finished". Reclaiming the space properly needs VACUUM FULL or a table rewrite, both of which take an exclusive lock.

Chunking fixes most of this: ten thousand rows per transaction, repeated until nothing matches, with a short sleep so replication and autovacuum keep up. Each batch is short-lived, interruptible and resumable. The better answer where the access pattern allows it is partitioning by time, because then retention is DETACH PARTITION plus DROP TABLE — instantaneous, no dead tuples, no WAL flood. That has to be set up before the table gets large, though; retrofitting partitioning onto a 200-million-row table is its own migration project.

Senior: What actually happens on disk when you run an UPDATE?

In Postgres, nothing is edited in place. The existing row version is marked as no longer visible to new transactions, a complete new version of the row is written elsewhere, and every index on the table is updated to point at the new location. The old version remains until vacuum determines no running transaction can still see it. So an update is physically a delete plus an insert, and its cost scales with the number of indexes rather than with how many columns you changed — a table with eight indexes performs roughly nine writes for a one-column update.

That single mechanism explains a lot of otherwise mysterious production behaviour. A table with a million live rows occupying ten gigabytes is bloat from accumulated dead versions. A long-running analytical query or, more commonly, a connection sitting idle inside a transaction holds back vacuum across the database, because those old versions might still be visible to it — which is why unexplained table growth so often traces back to a connection pool that never commits. There is an optimisation, heap-only tuple updates, which skips the index writes when no indexed column changed and the page has free space, and that is the practical reason for leaving fillfactor headroom on update-heavy tables.

MySQL's InnoDB takes the other approach: it updates in place and keeps prior versions in an undo log, so it does not bloat the table the same way, but a long transaction makes the undo log grow and degrades everything reading through it. Different mechanism, same underlying lesson — long transactions are expensive in ways that are invisible from the application. The broader point is write amplification: one logical row change becomes a WAL record, a heap page write, an entry per index, and a copy of all of it shipped to every replica, which is why an extra index is never free and why bulk loads are faster with indexes dropped and rebuilt afterwards.

Senior: Design a safe process for a data migration that touches every row of a large table.

The first decision is to make the schema change and the data change separate steps, because a schema change takes a lock and a data change takes time, and combining them takes a long lock. So: add the new column as nullable with no default, which is metadata-only and instant on modern Postgres; backfill it in chunks; then add the NOT NULL constraint once the data is there, ideally as NOT VALID followed by a separate VALIDATE so the enforcing step does not block writes.

The backfill itself runs in bounded batches driven by the primary key, each in its own transaction, with a checkpoint of the last processed id persisted so an interrupted run resumes rather than starts over. Between batches I would pause briefly and watch replication lag and dead-tuple counts, throttling if either climbs — the job should be a background citizen, not a spike. Every statement gets a lock_timeout and a statement_timeout so it fails fast rather than queueing; a migration that waits for a lock also blocks every query that arrives behind it, which is the specific mechanism by which one ALTER TABLE takes down a service.

For the application side, the safe pattern is expand-migrate-contract across releases. First deploy code that writes both the old and new representation while still reading the old, so old and new code can coexist during a rolling deploy. Then backfill. Then switch reads. Then, in a later release, stop writing the old column and finally drop it. Dropping or renaming a column that a still-running instance selects is an instant outage, and rolling deploys guarantee both versions run simultaneously.

Two things I would insist on regardless of size. A verification query that proves the backfill is complete and consistent, run before the contract step rather than assumed. And a rehearsal on a production-sized copy — the interesting failures are all volume-dependent, and staging with ten thousand rows proves only that the SQL parses. If the table is large enough that even chunked backfill is impractical, the alternative is a shadow table written by triggers or change data capture and then swapped in, which trades complexity for the ability to abort at any point.

🏋️ Exercises

1 (easy): Write the safe procedure for deactivating dormant accounts, and explain each step.
Solution 
-- ✗ THE DANGEROUS VERSION
UPDATE users SET active = false WHERE last_login < '2020-01-01';
-- Typed directly into a production console. If the date is wrong, or the
-- column is nullable, or you fat-finger the WHERE, it is already done.

-- ✓ THE PROCEDURE

-- STEP 1: count first, with the EXACT same predicate
SELECT count(*) FROM users WHERE last_login < '2020-01-01';
-- 1204
-- Also look at what you are about to touch:
SELECT id, email, last_login FROM users
WHERE last_login < '2020-01-01' ORDER BY last_login LIMIT 20;

-- STEP 2: check the NULL case explicitly — this is the usual surprise
SELECT count(*) FROM users WHERE last_login IS NULL;
-- 8,932   ← users who NEVER logged in are NOT matched by `< date`,
--            because NULL comparisons are UNKNOWN. Did you want them?
--            Decide now, not after.

-- STEP 3: run inside a transaction and CHECK THE COUNT
BEGIN;
UPDATE users SET active = false, updated_at = now()
WHERE last_login < '2020-01-01';
-- UPDATE 1204        ← matches step 1 ✓
COMMIT;               -- if it said 4,000,000 → ROLLBACK;

-- The affected-row count is the safety mechanism. Inside a transaction
-- it costs nothing to verify, and after COMMIT it costs a restore.

-- ── DEFENCES WORTH HAVING ───────────────────────────────────────────────
SET SESSION sql_safe_updates = 1;   -- MySQL: rejects unqualified writes
\set AUTOCOMMIT off                 -- psql: everything is a transaction
SET lock_timeout = '5s';            -- fail rather than block others

-- Production credentials should be READ-ONLY by default; writes go
-- through a reviewed migration, not a console. Process beats care.

-- ── AND IF IT WERE 4 MILLION ROWS ───────────────────────────────────────
-- Chunk it — one statement holding locks over 4M rows blocks writers,
-- floods the WAL and lags replicas:
UPDATE users SET active = false
WHERE id IN (SELECT id FROM users
             WHERE last_login < '2020-01-01' AND active
             ORDER BY id LIMIT 10000);
-- repeat until 0 rows affected. Note `AND active` makes it idempotent,
-- so re-running is safe and the loop terminates.
2 (easy): Replace this racy counter update with a correct one, three ways.
Solution 
# ✗ BEFORE — read-modify-write in application code
row = db.query("SELECT n FROM counters WHERE key = 'visits'")   # reads 100
db.execute("UPDATE counters SET n = %s WHERE key = 'visits'", row.n + 1)

# THE RACE: two requests both read 100, both write 101. One increment is
# lost. It is not rare under load — it is the default outcome.

-- ── ✓ 1. LET THE DATABASE COMPUTE IT ────────────────────────────────────
UPDATE counters SET n = n + 1 WHERE key = 'visits';
-- The row lock is held for the whole read-modify-write inside the
-- statement, so concurrent increments serialise correctly. Always prefer
-- this when the new value is a function of the old one.

-- ── ✓ 2. UPSERT, WHEN THE ROW MAY NOT EXIST YET ─────────────────────────
INSERT INTO counters (key, n) VALUES ('visits', 1)
ON CONFLICT (key) DO UPDATE SET n = counters.n + 1
RETURNING n;
-- Handles create-or-increment atomically. Requires a UNIQUE constraint on
-- `key` — that constraint IS the mechanism.
--   counters.n → the EXISTING row      excluded.n → the PROPOSED value

-- ── ✓ 3. OPTIMISTIC LOCKING, when the app must compute the value ────────
UPDATE documents
SET    content = :new_content, version = version + 1
WHERE  id = :id AND version = :version_i_read;
-- 0 rows affected  → someone else changed it since you read; re-read,
--                    re-apply, retry
-- 1 row affected   → you won
-- Checking the affected-row count is the entire protocol. Ignoring it
-- silently discards the other writer's changes.

-- ── THE FAILURE MODE OF #1 AT SCALE ─────────────────────────────────────
-- Every session incrementing the SAME row serialises on its lock. A
-- global counter becomes a hard throughput ceiling and a deadlock
-- hotspot. Shard it:
INSERT INTO counters (key, shard, n) VALUES ('visits', :random_0_15, 1)
ON CONFLICT (key, shard) DO UPDATE SET n = counters.n + 1;
SELECT sum(n) FROM counters WHERE key = 'visits';    -- read path
-- 16x the write concurrency, at the cost of an aggregate on read.
3 (medium): A nightly cleanup deleting 40M rows causes replica lag and slow queries all morning. Redesign it.
Solution 
-- ✗ BEFORE
DELETE FROM events WHERE created_at < now() - interval '90 days';

-- ── WHY IT HURTS, IN FIVE WAYS ──────────────────────────────────────────
-- 1. Locks on 40M rows held for the entire (hours-long) transaction
-- 2. ~40M WAL records shipped to replicas, replayed SINGLE-THREADED →
--    hours of lag; replicas serve stale data or drop out of rotation
-- 3. 40M DEAD TUPLES left behind. The table does not shrink; scans still
--    read those pages, so queries stay slow AFTER the delete "finished"
-- 4. The long transaction blocks autovacuum from reclaiming anything,
--    ANYWHERE — bloat appears in unrelated tables
-- 5. All-or-nothing: cancelling after 3 hours discards 3 hours of work,
--    then spends more time rolling back

-- ── ✓ FIX A: CHUNK IT ───────────────────────────────────────────────────
-- run in a loop from the application or a shell script
DELETE FROM events
WHERE id IN (
  SELECT id FROM events
  WHERE created_at < now() - interval '90 days'
  ORDER BY id
  LIMIT 10000
);
-- repeat until 0 rows affected; sleep ~100ms between batches
--
-- Each batch is its own short transaction: interruptible, resumable,
-- locks held for milliseconds, and replication + autovacuum keep pace.
-- Throttle on a real signal rather than a fixed sleep:
SELECT extract(epoch FROM (now() - pg_last_xact_replay_timestamp()));
-- pause while lag > 30s.

CREATE INDEX ON events (created_at);   -- or the subquery scans every time

-- ── ✓✓ FIX B: PARTITION AND DROP (the real answer) ──────────────────────
CREATE TABLE events (
  id bigint, created_at timestamptz NOT NULL, ...
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_08 PARTITION OF events
  FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

-- retention becomes:
ALTER TABLE events DETACH PARTITION events_2026_04;
DROP TABLE events_2026_04;
-- INSTANT. Zero dead tuples, zero WAL for the data, no lock contention,
-- nothing for vacuum to do. Deleting a month costs the same as deleting
-- a row.
--
-- Queries with a created_at predicate also get partition PRUNING for
-- free, so the cleanup change speeds up reads too.

-- ── THE CATCH ───────────────────────────────────────────────────────────
-- Partitioning must be in place BEFORE the table is large. Retrofitting
-- it onto a 200M-row table is its own migration project (create the
-- partitioned table, backfill in chunks, dual-write, swap). Which is the
-- argument for doing it the day a table gets a retention policy, not the
-- day it becomes a problem.

-- ── AND SCHEDULE IT HONESTLY ────────────────────────────────────────────
-- "Nightly at 2am" is a spike. A continuous low-rate delete (a few
-- thousand rows every minute, all day) never creates a backlog and never
-- shows up as a morning incident.
4 (medium): Implement "create user or update their profile" correctly, including the edge cases.
Solution 
-- ✗ BEFORE — a race, and two round trips
SELECT id FROM users WHERE email = :email;
-- if found:  UPDATE users SET name = :name WHERE id = :id;
-- else:      INSERT INTO users (email, name) VALUES (:email, :name);

-- Two concurrent signups with the same email: both SELECT nothing, both
-- INSERT, one gets a unique violation (or you get duplicate users if
-- there is no constraint — which is worse).

-- ── ✓ THE UPSERT ────────────────────────────────────────────────────────
INSERT INTO users (email, name, updated_at)
VALUES (:email, :name, now())
ON CONFLICT (email) DO UPDATE
SET   name       = excluded.name,
      updated_at = excluded.updated_at
WHERE users.name IS DISTINCT FROM excluded.name      -- ← see below
RETURNING id, (xmax = 0) AS was_inserted;

-- excluded.*  = the row you PROPOSED
-- users.*     = the row that ALREADY EXISTS
-- xmax = 0    = Postgres trick to report whether it inserted or updated

-- ── THE PREREQUISITE ────────────────────────────────────────────────────
CREATE UNIQUE INDEX ON users (email);
-- Without a unique constraint on the conflict target there is nothing to
-- detect a conflict against, and the statement errors at parse time. The
-- constraint is the mechanism, not decoration.

-- ── WHY THE WHERE CLAUSE MATTERS ────────────────────────────────────────
-- Without it, an upsert with unchanged data is still a WRITE: MVCC
-- creates a new row version, every index is updated, WAL is generated and
-- shipped to replicas. A sync job upserting 1M unchanged rows nightly
-- produces 1M dead tuples for nothing. `IS DISTINCT FROM` (not `<>`, so
-- NULLs compare correctly) skips the no-op.

-- ── THE EDGE CASES ──────────────────────────────────────────────────────

-- 1. SEQUENCE BURN: a conflicting INSERT still consumes an id. High-
--    conflict upserts chew through the identity range. Harmless with
--    bigint; a real problem with int.

-- 2. LOCK CONTENTION: many sessions upserting the SAME key serialise on
--    that row's lock. Fine for user records; a bottleneck for a global
--    counter.

-- 3. DEADLOCKS on multi-row upserts. Two sessions sending
--    [A, B] and [B, A] deadlock. SORT THE BATCH BY KEY before sending:
INSERT INTO users (email, name) VALUES (...), (...), (...)   -- sorted
ON CONFLICT (email) DO UPDATE SET name = excluded.name;

-- 4. TWO UNIQUE CONSTRAINTS: `ON CONFLICT (email)` only handles email
--    conflicts. A clash on `username` still raises. You cannot name two
--    targets — either catch the error, or reconsider the model.

-- 5. SOFT DELETE + UPSERT: if deleted rows keep their email, the upsert
--    "revives" a deleted account. Usually not intended:
CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL;
--    ⚠ ON CONFLICT cannot target a partial index in all versions —
--      verify, or handle deleted rows explicitly.

-- ── MYSQL ───────────────────────────────────────────────────────────────
INSERT INTO users (email, name) VALUES (:email, :name)
ON DUPLICATE KEY UPDATE name = VALUES(name);
-- Fires on ANY unique key, not one you name — so with several unique
-- constraints you cannot tell which one matched.
5 (hard): A table has 2M live rows and occupies 14GB. Diagnose.
Solution 
-- ── STEP 1: CONFIRM IT IS BLOAT ─────────────────────────────────────────
SELECT relname,
       n_live_tup, n_dead_tup,
       pg_size_pretty(pg_total_relation_size(relid)) AS total,
       last_vacuum, last_autovacuum
FROM pg_stat_user_tables WHERE relname = 'orders';
--  n_live_tup 2,000,000 | n_dead_tup 41,000,000 | 14 GB | autovacuum NULL
-- 20 dead versions per live row, and autovacuum has never completed.

-- ── STEP 2: WHY DEAD TUPLES EXIST AT ALL ────────────────────────────────
-- In Postgres an UPDATE does NOT edit in place:
--   1. the old row version is marked dead
--   2. a COMPLETE new version is written
--   3. every index is updated to point at the new location
--   4. the old version survives until VACUUM proves nobody can see it
-- So an UPDATE is physically a DELETE + INSERT, and its cost scales with
-- the NUMBER OF INDEXES, not the number of columns changed.

-- ── STEP 3: WHY VACUUM NEVER RECLAIMED THEM — the usual culprit ─────────
SELECT pid, state, xact_start, now() - xact_start AS age, query
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'active')
ORDER BY xact_start;
--  pid 8821 | idle in transaction | 6 days | BEGIN
-- A connection that opened a transaction and never committed. Vacuum
-- cannot remove ANY version newer than the oldest running transaction —
-- because that transaction might still need to see it. One leaked
-- connection in a pool bloats the whole database.
SELECT max(age(backend_xid)) FROM pg_stat_activity;    -- the age gap

-- Other causes worth checking:
--   * a long-running analytics query or an open replication slot
SELECT slot_name, active, pg_size_pretty(
  pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) FROM pg_replication_slots;
--     an INACTIVE slot pins WAL and old versions forever — a
--     decommissioned replica whose slot was never dropped
--   * autovacuum too slow: scale factor 0.2 on a huge table means it only
--     triggers after 400K dead rows, and cost limits throttle it

-- ── STEP 4: FIX THE CAUSE, THEN THE SYMPTOM ─────────────────────────────
SELECT pg_terminate_backend(8821);                 -- kill the leak
SET idle_in_transaction_session_timeout = '60s';   -- prevent recurrence
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.02);  -- tune

-- Reclaiming the space (only AFTER the cause is fixed, or it re-bloats):
VACUUM (VERBOSE, ANALYZE) orders;   -- marks space reusable; file stays 14GB
VACUUM FULL orders;                 -- rewrites; ACCESS EXCLUSIVE LOCK —
                                    -- an outage on a large table
-- ✓ pg_repack rewrites it with only a brief lock — the production answer.

-- ── STEP 5: REDUCE THE WRITE VOLUME AT SOURCE ───────────────────────────
UPDATE orders SET last_seen = now() WHERE id = :id;   -- on EVERY request
-- A hot-path update on a wide, heavily-indexed table is the usual
-- generator. Options: move volatile columns to a narrow side table,
-- batch the updates, or keep last_seen in Redis and flush periodically.

ALTER TABLE orders SET (fillfactor = 85);
-- Leaves free space per page so HOT (heap-only tuple) updates can put the
-- new version on the SAME page and skip the index writes entirely —
-- but only when no INDEXED column changed. Cheapest available win on an
-- update-heavy table.

-- ── THE ONE-LINE SUMMARY ────────────────────────────────────────────────
-- Bloat is almost never "vacuum is broken". It is something PREVENTING
-- vacuum: a long transaction, an idle-in-transaction connection, or an
-- abandoned replication slot.
6 (hard): Plan a zero-downtime migration splitting users.full_name into first_name and last_name.
Solution 
-- 80M rows, continuous traffic, rolling deploys (old and new application
-- code run SIMULTANEOUSLY for several minutes — that constraint drives
-- the entire design).

-- ══ RELEASE 1: EXPAND ═══════════════════════════════════════════════════
ALTER TABLE users ADD COLUMN first_name text;      -- nullable, no default
ALTER TABLE users ADD COLUMN last_name  text;      -- → metadata-only,
                                                   --   INSTANT
-- ⚠ Adding a column WITH a volatile default rewrites the entire table
--   under an ACCESS EXCLUSIVE lock. On 80M rows that is an outage.
--   Nullable now, backfill separately, constrain later.

-- Deploy code that WRITES BOTH and still READS full_name. Old instances
-- writing only full_name must stay correct, so a trigger keeps the new
-- columns in sync for them:
CREATE FUNCTION sync_names() RETURNS trigger AS $$
BEGIN
  IF NEW.first_name IS NULL AND NEW.full_name IS NOT NULL THEN
    NEW.first_name := split_part(NEW.full_name, ' ', 1);
    NEW.last_name  := nullif(substr(NEW.full_name,
                             strpos(NEW.full_name, ' ') + 1), '');
  END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER sync_names BEFORE INSERT OR UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION sync_names();

-- ══ BACKFILL (a background job, not a migration step) ═══════════════════
-- Chunked, resumable, throttled:
UPDATE users SET first_name = split_part(full_name, ' ', 1),
                 last_name  = nullif(substr(full_name,
                              strpos(full_name,' ')+1), '')
WHERE id BETWEEN :lo AND :lo + 9999
  AND first_name IS NULL;          -- ← IDEMPOTENT: safe to re-run, and
                                   --   the loop terminates
-- persist :lo after each batch so a crash resumes rather than restarts
SET lock_timeout = '5s';           -- fail fast; never queue behind a
SET statement_timeout = '30s';     -- long query and block everyone

-- Throttle on a REAL signal, not a fixed sleep:
SELECT extract(epoch FROM (now() - pg_last_xact_replay_timestamp()));
-- pause while replica lag > 30s or n_dead_tup climbs

-- ⚠ 80M UPDATEs = 80M new row versions + index writes + WAL. This is the
--   expensive part and it must be paced. Continuous and slow beats a
--   nightly spike.

-- ══ VERIFY — before trusting it ═════════════════════════════════════════
SELECT count(*) FROM users WHERE first_name IS NULL AND full_name IS NOT NULL;
-- must be 0
SELECT count(*) FROM users
WHERE full_name IS DISTINCT FROM
      trim(coalesce(first_name,'') || ' ' || coalesce(last_name,''));
-- inspect the non-zero remainder: mononyms, suffixes, "van der Berg".
-- Name splitting is LOSSY — decide the rule deliberately and record how
-- many rows it could not represent.

-- ══ RELEASE 2: SWITCH READS ═════════════════════════════════════════════
-- Code reads first_name/last_name, still writes both. Deployable and
-- fully reversible — full_name is still current.

ALTER TABLE users ADD CONSTRAINT first_name_not_null
  CHECK (first_name IS NOT NULL) NOT VALID;      -- instant, no scan
ALTER TABLE users VALIDATE CONSTRAINT first_name_not_null;
-- VALIDATE scans but takes only a SHARE UPDATE EXCLUSIVE lock, so
-- writes continue. A direct SET NOT NULL would block everything.

-- ══ RELEASE 3: STOP WRITING full_name ═══════════════════════════════════
DROP TRIGGER sync_names ON users;
-- Wait one full release cycle. Any instance still running Release 1 code
-- would break the moment the column disappears.

-- ══ RELEASE 4: CONTRACT ═════════════════════════════════════════════════
ALTER TABLE users DROP COLUMN full_name;
-- Only once NOTHING reads or writes it. Verify against query logs, not
-- against a grep of the repo — reports, exports, BI tools and other
-- services also select from this table.

-- ══ WHY FOUR RELEASES ═══════════════════════════════════════════════════
-- A rolling deploy runs old and new code at the same time. Every step
-- must be correct for BOTH. Collapsing this into one release means the
-- window where instances disagree is the window where writes are lost or
-- queries reference a dropped column — an instant, self-inflicted outage.
--
-- ── AND REHEARSE IT ─────────────────────────────────────────────────────
-- On a production-sized restore. Every interesting failure here is
-- volume-dependent; staging with 10,000 rows proves only that the SQL
-- parses.

🎯 Key Takeaways

  • The affected-row count is the safety mechanism: SELECT first, wrap in a transaction, verify, then commit.
  • Always name columns in INSERT; positional inserts silently misalign after a schema change.
  • Use multi-row INSERT or COPY for bulk, and RETURNING to avoid a second round trip.
  • Upserts are atomic and race-free, and require the unique constraint that makes conflict detection possible.
  • Let the database compute derived values (n = n + 1) or use optimistic locking — never read-modify-write in the application.
  • Large deletes cause lock contention, replication lag and bloat — chunk them, or partition and drop.
  • Soft delete needs a partial unique index and a view or RLS to enforce the filter; archive-then-delete is often better.
  • In Postgres an UPDATE writes a new row version and updates every index, so its cost scales with index count.
  • Bloat is almost always something blocking vacuum: a long transaction, an idle-in-transaction connection, or an abandoned replication slot.
  • Migrations take four releases — expand, backfill, switch reads, contract — because rolling deploys run old and new code simultaneously.
