Sorting, Limiting & Aggregates Basics

What you'll master: how each aggregate treats NULL and why COUNT(*), COUNT(col) and COUNT(DISTINCT col) give three different answers, the GROUP BY rule and the MySQL default that silently returned wrong values for years, WHERE versus HAVING as both a correctness and a performance distinction, conditional aggregation with FILTER for pivots, GROUPING SETS and ROLLUP for subtotals, the empty-group problem that makes dashboards lie, and ordering and pagination that stay stable under concurrent writes. Prerequisites: SELECT & Filtering.

Part 1 — Aggregate Functions and NULL

SELECT count(*)                  AS rows,        -- EVERY row, NULLs included
       count(email)              AS with_email,  -- non-NULL emails ONLY
       count(DISTINCT country)   AS countries,   -- distinct non-NULL values
       sum(score), avg(score), min(score), max(score)
FROM users;

-- ── THE RULE: EVERY AGGREGATE EXCEPT count(*) IGNORES NULL ──────────────
-- users: (80), (30), (NULL)
count(*)      -- 3   counts ROWS
count(score)  -- 2   counts NON-NULL VALUES
sum(score)    -- 110
avg(score)    -- 55      NOT 36.67 — it divides by 2, not by 3
min(score)    -- 30
max(score)    -- 80

-- avg() is the one that bites. It is sum() / count(col), so a NULL is
-- treated as "this row does not participate" rather than as zero. If a
-- NULL genuinely means zero in your domain, say so:
avg(COALESCE(score, 0))          -- 36.67
-- Neither is right in general. The bug is not choosing.

-- ── SUM OVER NO ROWS IS NULL, NOT ZERO ──────────────────────────────────
SELECT sum(amount) FROM refunds WHERE user_id = 999;   -- NULL
-- The application does `total + sum` and gets NULL, or renders "null" in
-- a UI, or a NOT NULL insert fails. Guard at the boundary:
SELECT COALESCE(sum(amount), 0) FROM refunds WHERE user_id = 999;   -- 0
-- count() is the exception: count over zero rows is 0.

-- ── count(DISTINCT) IS EXPENSIVE ────────────────────────────────────────
count(DISTINCT user_id)          -- must deduplicate: a sort or a hash
                                 -- over every value. On 100M rows this
                                 -- is the whole query's cost.
-- Postgres: approximate alternatives exist (postgresql-hll,
-- approx_count_distinct extensions) when "within 2%" is acceptable for
-- a dashboard. Exact distinct counts do not scale for free.

-- ── OTHER AGGREGATES WORTH KNOWING ──────────────────────────────────────
bool_and(active)  bool_or(active)          -- all / any     (Postgres)
string_agg(name, ', ' ORDER BY name)       -- concatenate   (Postgres)
GROUP_CONCAT(name ORDER BY name)           --               (MySQL)
array_agg(id ORDER BY created_at)          -- collect into an array
jsonb_agg(row_to_json(t))                  -- collect into JSON
percentile_cont(0.5) WITHIN GROUP (ORDER BY latency)   -- MEDIAN
percentile_cont(0.95) WITHIN GROUP (ORDER BY latency)  -- p95
stddev(score)  variance(score)

-- Averages hide the problem. A mean latency of 40ms with a p99 of 30s
-- looks healthy on a dashboard while a percent of users cannot use the
-- product. Report percentiles for anything users experience.

Part 2 — GROUP BY

SELECT country, count(*) AS users, avg(score) AS avg_score
FROM users
GROUP BY country
ORDER BY users DESC;

-- ── THE RULE ────────────────────────────────────────────────────────────
-- Every column in SELECT must EITHER appear in GROUP BY or be inside an
-- aggregate. Nothing else is meaningful: the group has many rows, so
-- "the name" of a group of 4,000 users does not exist.

SELECT country, name, count(*) FROM users GROUP BY country;
-- ✗ Postgres: column "users.name" must appear in the GROUP BY clause
-- ✗ MySQL 5.7+ with ONLY_FULL_GROUP_BY: same error
-- ⚠ MySQL BEFORE 5.7 (and with the mode disabled): runs, and returns an
--   ARBITRARY name from each group. No error, no warning, wrong data.
--   If you inherit a MySQL codebase, check this setting first:
SELECT @@sql_mode;   -- ONLY_FULL_GROUP_BY should be present

-- ── THE FUNCTIONAL-DEPENDENCY EXCEPTION ─────────────────────────────────
SELECT u.id, u.name, count(o.id)
FROM users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id;                   -- ✓ valid in Postgres
-- Grouping by a PRIMARY KEY makes every other column of that table
-- functionally dependent — there can only be one name per u.id — so the
-- planner allows it. Convenient and portable-ish; listing the columns
-- explicitly is safer across engines.

-- ── GROUPING BY AN EXPRESSION ───────────────────────────────────────────
SELECT date_trunc('month', created_at) AS month, count(*)
FROM orders
GROUP BY 1                       -- ordinal: refers to the 1st SELECT item
ORDER BY 1;
-- GROUP BY 1 is fine in ad-hoc analysis and a liability in stored
-- queries: inserting a column silently regroups by something else.
GROUP BY date_trunc('month', created_at)     -- explicit; repeat it

-- ── NULL FORMS ITS OWN GROUP ────────────────────────────────────────────
SELECT region, count(*) FROM users GROUP BY region;
-- region = NULL produces one group containing all the NULLs. GROUP BY
-- treats NULLs as equal to each other, which is the OPPOSITE of what
-- `WHERE region = region` does. Two different equality rules in one
-- language — worth remembering rather than deriving.

-- ── DISTINCT IS GROUP BY WITH NO AGGREGATE ──────────────────────────────
SELECT DISTINCT country FROM users;
SELECT country FROM users GROUP BY country;    -- identical plan, usually

Part 3 — WHERE vs HAVING

SELECT country, count(*) AS users
FROM   users
WHERE  active                    -- filters ROWS,   BEFORE grouping
GROUP BY country
HAVING count(*) > 100            -- filters GROUPS, AFTER  aggregation
ORDER BY users DESC;

-- It falls out of the execution order from the previous lesson:
--   FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
-- WHERE runs at step 2, before any group exists, so it cannot reference
-- an aggregate. HAVING runs at step 4, when the groups do exist.

SELECT dept, avg(salary) FROM emp WHERE avg(salary) > 50000 GROUP BY dept;
-- ✗ ERROR: aggregate functions are not allowed in WHERE

-- ── IT IS ALSO A PERFORMANCE DECISION ───────────────────────────────────
SELECT country, count(*) FROM users
GROUP BY country
HAVING country <> 'internal';       -- ✗ groups EVERYTHING, then discards

SELECT country, count(*) FROM users
WHERE country <> 'internal'          -- ✓ discards first; less to group
GROUP BY country;
-- Same answer, less work. On a large table the difference is large,
-- because grouping is the expensive step and WHERE shrinks its input.
--
-- RULE: a condition that only mentions columns belongs in WHERE. Only a
-- condition mentioning an AGGREGATE requires HAVING.

-- ── AND THE NULL TRAP APPLIES HERE TOO ──────────────────────────────────
WHERE country <> 'internal'          -- silently drops rows where
                                     -- country IS NULL
WHERE country IS DISTINCT FROM 'internal'   -- keeps them (Postgres)

-- ── HAVING WITHOUT GROUP BY ─────────────────────────────────────────────
SELECT count(*) FROM orders HAVING count(*) > 1000;
-- Legal: the whole table is one implicit group. Returns one row or zero
-- rows. Rare, but it explains why HAVING does not require GROUP BY.
Key insight: aggregation is where "the query ran without error" and "the number is correct" separate most sharply. Nothing warns you that avg quietly excluded the NULLs, that sum returned NULL because no rows matched, that a join fanned rows out and doubled the total, or that a month with zero sales is missing from the report entirely rather than showing zero. Every one of those produces a plausible-looking number. The habit that catches them is checking the row count alongside the aggregate — count(*) next to every sum — because a wrong total is invisible while a wrong row count usually is not.

Part 4 — Conditional Aggregation and Pivots

-- ── ONE PASS, SEVERAL CONDITIONAL MEASURES ─────────────────────────────
SELECT
  count(*)                                   AS total,
  count(*) FILTER (WHERE status = 'paid')    AS paid,        -- Postgres
  count(*) FILTER (WHERE status = 'refunded')AS refunded,
  sum(total) FILTER (WHERE status = 'paid')  AS revenue
FROM orders;

-- Portable equivalent (works everywhere):
SELECT
  count(*)                                          AS total,
  sum(CASE WHEN status = 'paid' THEN 1 ELSE 0 END)  AS paid,
  count(CASE WHEN status = 'paid' THEN 1 END)       AS paid_alt,
  sum(CASE WHEN status = 'paid' THEN total END)     AS revenue
FROM orders;
-- Note the two count() forms: count() ignores NULL, so a CASE with no
-- ELSE (returning NULL for non-matches) counts only the matches. That
-- idiom is everywhere in older SQL.

-- ⚠ The classic mistake: count(CASE WHEN ... THEN 1 ELSE 0 END) counts
--   EVERY row, because 0 is not NULL. Use sum() with ELSE 0, or count()
--   with no ELSE. Never count() with ELSE 0.

-- ── ROWS TO COLUMNS (a pivot) ───────────────────────────────────────────
SELECT
  date_trunc('month', created_at)                       AS month,
  sum(total) FILTER (WHERE region = 'EU') AS eu,
  sum(total) FILTER (WHERE region = 'US') AS us,
  sum(total) FILTER (WHERE region = 'AP') AS ap
FROM orders
GROUP BY 1 ORDER BY 1;
-- SQL cannot pivot on values it does not know at parse time. A dynamic
-- set of columns requires generating the SQL, or returning long-format
-- rows and pivoting in the application — which is usually the better
-- answer, because a query whose SHAPE depends on data is hard to cache,
-- test and type.

-- ── SUBTOTALS: GROUPING SETS, ROLLUP, CUBE ──────────────────────────────
SELECT region, product, sum(total)
FROM sales
GROUP BY ROLLUP (region, product);
-- Produces: each (region, product), then a subtotal per region, then a
-- grand total — in ONE pass instead of three UNIONed queries.

GROUP BY GROUPING SETS ((region, product), (region), ())   -- the same,
                                                           -- written out
GROUP BY CUBE (region, product)     -- every combination, including
                                    -- (product) alone

-- Subtotal rows have NULL in the columns they aggregate over, which is
-- ambiguous when the data ALSO contains NULLs. Disambiguate:
SELECT region, product, sum(total),
       GROUPING(region) AS is_region_subtotal    -- 1 = this is a subtotal
FROM sales GROUP BY ROLLUP (region, product);

-- ── DISTINCT INSIDE AN AGGREGATE ────────────────────────────────────────
SELECT user_id,
       count(*)                  AS events,
       count(DISTINCT session_id) AS sessions,
       count(DISTINCT date_trunc('day', ts)) AS active_days
FROM events GROUP BY user_id;
-- Three genuinely different metrics that are easy to conflate in a
-- specification. "Active users" almost always means DISTINCT.

Part 5 — The Empty Group Problem

-- ── AGGREGATION CANNOT INVENT ROWS THAT DO NOT EXIST ────────────────────
SELECT date_trunc('day', created_at) AS day, count(*)
FROM orders
WHERE created_at >= '2026-01-01'
GROUP BY 1 ORDER BY 1;
-- A day with zero orders produces NO ROW. The chart draws a line
-- straight from the 3rd to the 5th, and the outage on the 4th is
-- invisible — the exact day you most needed to see.

-- ✓ GENERATE THE AXIS, THEN LEFT JOIN THE DATA
SELECT d.day, COALESCE(count(o.id), 0) AS orders
FROM generate_series('2026-01-01'::date, '2026-01-31'::date,
                     '1 day') AS d(day)                      -- Postgres
LEFT JOIN orders o ON o.created_at >= d.day
                  AND o.created_at <  d.day + 1
GROUP BY d.day
ORDER BY d.day;
-- Now every day appears, with 0 where there were no orders.
-- The same applies to categories: LEFT JOIN from the dimension table,
-- not from the fact table.

-- ⚠ COALESCE the AGGREGATE, not the column:
COALESCE(count(o.id), 0)    -- count is already 0 for an empty group here
COALESCE(sum(o.total), 0)   -- ✓ NECESSARY — sum over no rows is NULL

-- ── THE OTHER DIRECTION: A JOIN THAT INFLATES THE TOTAL ─────────────────
SELECT sum(o.total)
FROM orders o JOIN order_items i ON i.order_id = o.id;
-- ✗ o.total is summed ONCE PER ITEM. A 3-item order counts 3x. The
--   number is too high and looks like a good quarter.
--
-- The tell: adding DISTINCT changes the answer. That means the join is
-- wrong, not that DISTINCT was missing.
SELECT sum(total) FROM orders o
WHERE EXISTS (SELECT 1 FROM order_items i WHERE i.order_id = o.id);   -- ✓

-- Or aggregate each side separately before combining:
SELECT o.id, o.total, i.item_count
FROM orders o
JOIN (SELECT order_id, count(*) AS item_count
      FROM order_items GROUP BY order_id) i ON i.order_id = o.id;
-- Aggregating BEFORE joining is the general fix for fan-out, and it is
-- usually faster as well as correct.

-- ── SANITY CHECKS WORTH BUILDING IN ─────────────────────────────────────
SELECT count(*) AS rows, count(DISTINCT order_id) AS orders, sum(total)
FROM ...;
-- If rows > orders, the join fanned out. Putting count(*) next to every
-- sum() turns an invisible wrong number into an obvious one.

Part 6 — Ordering and Pagination

SELECT * FROM users
ORDER BY score DESC, name ASC, id;      -- multi-key, with a unique last key
ORDER BY score DESC NULLS LAST;         -- Postgres default for DESC is
                                        -- NULLS FIRST — be explicit
-- MySQL sorts NULLs first ascending and last descending, with no
-- NULLS FIRST/LAST syntax; you emulate it with
ORDER BY (score IS NULL), score DESC;

-- ── ORDER BY AN ALIAS OR AN ORDINAL: BOTH LEGAL ─────────────────────────
SELECT count(*) AS n FROM users GROUP BY country ORDER BY n DESC;   -- ✓
ORDER BY 2 DESC;                        -- ordinal — brittle, avoid in
                                        -- stored queries

-- ── ORDERING MUST BE TOTAL, OR PAGINATION LIES ──────────────────────────
ORDER BY created_at DESC LIMIT 20 OFFSET 20;
-- Rows sharing a created_at have UNDEFINED relative order, and it can
-- differ between the query for page 2 and the query for page 3. A user
-- sees the same row twice and never sees another one.
ORDER BY created_at DESC, id DESC       -- ✓ unique tiebreaker = total order

-- ── DEEP OFFSET IS SLOW AND UNSTABLE ────────────────────────────────────
... ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 100000;
-- The database produces 100,020 rows and discards 100,000. Cost grows
-- linearly with page number. And an insert near the top shifts every
-- page boundary underneath the user.

-- ✓ KEYSET (SEEK) PAGINATION
SELECT * FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
CREATE INDEX ON posts (created_at DESC, id DESC);
-- Constant time at any depth, stable under concurrent inserts. The row
-- comparison (a, b) < (x, y) is exactly
--   a < x OR (a = x AND b < y)
-- and Postgres can drive the composite index with it directly.
-- Trade-off: no jumping to page 47. For feeds that is not a requirement.

-- ── TOP-N PER GROUP NEEDS A WINDOW FUNCTION ─────────────────────────────
SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY country
                               ORDER BY score DESC) AS rn
  FROM users) t
WHERE rn <= 3;
-- "The top 3 per country" cannot be done with GROUP BY, because grouping
-- collapses the rows you want to keep. This is the canonical reason
-- window functions exist — see Window Functions.

SELECT DISTINCT ON (country) *          -- Postgres shortcut for TOP-1
FROM users ORDER BY country, score DESC;

-- ── LIMIT WITH TIES ─────────────────────────────────────────────────────
FETCH FIRST 10 ROWS WITH TIES           -- standard SQL: include rows
                                        -- tied with the 10th
-- Plain LIMIT 10 cuts arbitrarily through a tie, which for a leaderboard
-- means two players on the same score where one is shown and one is not.

Interview Questions

Beginner: What is the difference between count(*), count(col) and count(DISTINCT col)?

count(*) counts rows, including rows where every column is NULL. count(col) counts only the rows where that column is not NULL, because every aggregate except count(*) ignores NULLs. count(DISTINCT col) counts distinct non-NULL values. On a users table where some emails are missing, those three give three different numbers, and picking the wrong one produces a plausible figure that is quietly wrong.

The same NULL rule catches people harder with avg, which is sum divided by count(col) rather than by the row count — so NULLs are excluded from both halves rather than treated as zero. Whether that is right depends on what a missing value means in the domain, and the actual bug is usually that nobody decided. One related detail worth knowing: sum over zero matching rows returns NULL rather than 0, which then propagates into application code or fails a NOT NULL insert, so it is worth wrapping in COALESCE at the boundary. count is the exception and returns 0.

Beginner: Explain WHERE versus HAVING precisely.

WHERE filters individual rows before grouping happens, and therefore cannot reference an aggregate — at that point in the execution order no group exists yet, so there is no count to compare against. HAVING filters groups after aggregation, which is where conditions like count(*) > 100 belong. It follows directly from the logical order: FROM, then WHERE, then GROUP BY, then HAVING.

It is also a performance distinction, not only a syntactic one. A condition that mentions only columns will work in HAVING and give the right answer, but it makes the database group every row first and then throw groups away, whereas the same condition in WHERE shrinks the input to the expensive grouping step. So the rule I would state is that a condition mentioning only columns goes in WHERE, and only a condition mentioning an aggregate requires HAVING.

Mid: A revenue total is roughly triple what finance expects. What is the most likely cause?

A join that fans out rows. If orders is joined to order_items and then sum(orders.total) is taken, each order's total is added once per item, so a three-item order contributes three times its value. The result is inflated by roughly the average number of child rows, which is why the figure is wrong by a suspiciously round-ish multiple rather than by a small amount.

The diagnostic tell is that adding DISTINCT changes the answer — and that is a signal the join is wrong, not that DISTINCT was missing, because it would still be wrong if two orders legitimately had the same total. The correct fixes are to aggregate the child table first and join to that result, or to use EXISTS when the child table is only there as a filter. More generally I would put count(*) and count(DISTINCT order_id) beside every sum during development: if the row count exceeds the entity count, the query is fanning out, and that turns an invisible wrong number into an obvious one.

Mid: Why do dashboards built on GROUP BY over dates often mislead?

Because aggregation can only summarise rows that exist. A day with no orders produces no row at all, so the chart connects the third to the fifth with a straight line and the outage on the fourth is invisible — precisely the day someone needed to see. The same happens with categories: a product that sold nothing this month simply disappears from the report rather than showing zero.

The fix is to generate the axis and left join the data onto it, using generate_series for dates or the dimension table for categories, then COALESCE the aggregate — necessary for sum, which is NULL over an empty group. The related distortion is reporting means. An average latency of forty milliseconds alongside a p99 of thirty seconds looks healthy while a measurable fraction of users cannot use the product, so anything users experience should be reported as percentiles via percentile_cont. Both problems share a shape: the query is technically correct and the picture it paints is false, which makes them much harder to catch than an error.

Senior: Why is deep OFFSET pagination a problem, and what would you use instead?

Two separate problems. The performance one is that OFFSET N requires the database to produce and then discard the first N ordered rows, so cost grows linearly with page depth and page five thousand is thousands of times more expensive than page one. The correctness one is subtler: OFFSET counts positions in a result set that is changing underneath the user, so an insert near the top shifts every subsequent page and they see rows they already saw, while a delete makes rows skip past unseen.

Keyset pagination fixes both by remembering where you were rather than how many you skipped: WHERE (created_at, id) < (:last_created_at, :last_id) with a matching composite index seeks straight to the position, so any page costs what the first page costs and concurrent inserts cannot shift it. The row-value comparison is exactly equivalent to the expanded OR form and Postgres can drive the index with it directly. The trade-off is honest: keyset only moves forward and backward from a known row, so it cannot jump to an arbitrary page number. For feeds, infinite scroll and exports that is not a real requirement, and for an admin table with numbered pages I would keep OFFSET but cap how deep it can go, since nobody legitimately browses to page five thousand.

Both approaches need a total ordering. Ordering by a non-unique column leaves ties in undefined relative order, and with pagination that alone causes duplicates and gaps even with no concurrent writes — so the sort key must end in something unique, normally the primary key.

Senior: How would you compute several conditional metrics efficiently, and when does SQL stop being the right tool?

In one pass with conditional aggregation rather than one query per metric. count(*) FILTER (WHERE status = 'paid') in Postgres, or the portable sum(CASE WHEN … THEN 1 ELSE 0 END), computes every measure during a single scan instead of scanning the table once per metric and joining the results. That matters more than it sounds on a large fact table, where the scan dominates and running six of them is six times the I/O for the same answer. One trap in the portable form: count(CASE WHEN c THEN 1 ELSE 0 END) counts every row because zero is not NULL — either use sum with the ELSE 0, or count with no ELSE at all.

For subtotals I would reach for GROUPING SETS or ROLLUP, which produce the detail rows, per-dimension subtotals and grand total in one pass rather than as several UNIONed queries, using the GROUPING() function to distinguish a subtotal's NULL from a NULL in the data.

Where I would stop is dynamic pivots. SQL cannot produce a column set that depends on values it does not know at parse time, so a genuine pivot over an open-ended dimension means either generating SQL strings — which is hard to cache, test and type-check — or returning long-format rows and pivoting in the application, which is usually the better answer. I would also move off exact count(DISTINCT …) on very large tables, since it has to deduplicate every value and can dominate the whole query; a HyperLogLog-based approximation within a couple of percent is almost always acceptable for a dashboard and is orders of magnitude cheaper. And once the same aggregation is being recomputed continuously over historical data that cannot change, the answer stops being query tuning and becomes a materialised view or a rollup table refreshed incrementally.

🏋️ Exercises

1 (easy): These four aggregates over the same column give four different answers. Explain each.
Solution 
CREATE TABLE users (id int, country text, score int);
INSERT INTO users VALUES
  (1,'US',80), (2,'US',30), (3,'US',NULL), (4,NULL,50), (5,'EU',80);

SELECT count(*)                 FROM users;   -- 5  every ROW
SELECT count(score)             FROM users;   -- 4  non-NULL VALUES
SELECT count(DISTINCT score)    FROM users;   -- 3  {80, 30, 50}
SELECT count(DISTINCT country)  FROM users;   -- 2  {US, EU} — NULL is NOT
                                              --    a distinct value here

SELECT avg(score) FROM users;                 -- 60   = 240 / 4
SELECT sum(score) / count(*) FROM users;      -- 48   = 240 / 5
-- avg() divides by the count of NON-NULL scores. If a missing score
-- means "zero", avg() is wrong for you:
SELECT avg(COALESCE(score, 0)) FROM users;    -- 48
-- Neither is universally right. The bug is not deciding.

-- ── GROUP BY PUTS ALL NULLS IN ONE GROUP ────────────────────────────────
SELECT country, count(*) FROM users GROUP BY country;
--  US   | 3
--  EU   | 1
--  NULL | 1        ← one group, not "excluded"
-- Note this is the OPPOSITE rule to WHERE: `WHERE country = country`
-- would drop that row. GROUP BY treats NULLs as equal to each other.

-- ── SUM OVER NOTHING ────────────────────────────────────────────────────
SELECT sum(score) FROM users WHERE country = 'ZZ';           -- NULL
SELECT COALESCE(sum(score), 0) FROM users WHERE country='ZZ';-- 0
SELECT count(*) FROM users WHERE country = 'ZZ';             -- 0
-- count is the exception; every other aggregate returns NULL over an
-- empty set. This breaks callers that expect a number.

-- ── THE HABIT ───────────────────────────────────────────────────────────
SELECT count(*) AS rows, count(score) AS scored, avg(score)
FROM users;
-- Reporting the row count next to the aggregate makes the gap visible.
-- An average alone is a number you cannot audit.
2 (easy): Fix this query, then explain why the fix is also faster.
Solution 
-- ✗ BEFORE
SELECT country, name, count(*) AS n
FROM users
GROUP BY country
HAVING country <> 'internal' AND active = true;

-- ── PROBLEM 1: `name` is neither grouped nor aggregated ─────────────────
-- Postgres: ERROR: column "users.name" must appear in the GROUP BY clause
-- MySQL without ONLY_FULL_GROUP_BY: RUNS, returning an ARBITRARY name
--   from each group. No error. Wrong data in a report nobody re-checks.
-- A group of 4,000 users does not have "a name" — the column is
-- meaningless here, so drop it (or group by it, making different groups).

-- ── PROBLEM 2: row conditions in HAVING ─────────────────────────────────
-- `country <> 'internal'` and `active = true` mention only COLUMNS, so
-- they belong in WHERE. In HAVING they still give the right answer, but
-- the database groups EVERY row first and then discards whole groups.

-- ✓ AFTER
SELECT country, count(*) AS n
FROM users
WHERE active
  AND country IS DISTINCT FROM 'internal'    -- ← and this fixes a THIRD
GROUP BY country                             --   bug: `<> 'internal'`
ORDER BY n DESC;                             --   silently drops NULLs

-- ── WHY IT IS FASTER ────────────────────────────────────────────────────
-- Grouping is the expensive step: it sorts or hashes its entire input.
-- WHERE shrinks that input before the work happens. If `active` filters
-- out 60% of rows, the group step does 40% of the work — and if there is
-- an index on (active, country), the planner may not read the other rows
-- at all.
--
-- RULE: a condition mentioning only columns → WHERE.
--       a condition mentioning an aggregate → HAVING. Nothing else.

-- ── THE ONE THAT GENUINELY NEEDS HAVING ─────────────────────────────────
SELECT country, count(*) AS n
FROM users WHERE active
GROUP BY country
HAVING count(*) > 100;        -- ✓ the group does not exist until step 4
3 (medium): Build a monthly report with per-status columns, and no missing months.
Solution 
-- ✗ BEFORE — three queries, and February is missing entirely
SELECT date_trunc('month', created_at) AS m, count(*) FROM orders
WHERE status = 'paid' GROUP BY 1;
SELECT date_trunc('month', created_at) AS m, count(*) FROM orders
WHERE status = 'refunded' GROUP BY 1;
-- Three scans of the fact table, joined in the application, and any
-- month with zero orders simply does not appear.

-- ✓ AFTER — one scan, every month present
SELECT
  m.month,
  count(o.id)                                          AS orders,
  count(o.id) FILTER (WHERE o.status = 'paid')         AS paid,
  count(o.id) FILTER (WHERE o.status = 'refunded')     AS refunded,
  COALESCE(sum(o.total) FILTER (WHERE o.status = 'paid'), 0) AS revenue,
  COALESCE(round(avg(o.total) FILTER (WHERE o.status='paid'), 2), 0)
                                                       AS avg_order
FROM generate_series('2026-01-01'::date,
                     '2026-12-01'::date, '1 month') AS m(month)
LEFT JOIN orders o
       ON o.created_at >= m.month
      AND o.created_at <  m.month + interval '1 month'   -- HALF-OPEN
GROUP BY m.month
ORDER BY m.month;

-- ── EVERY DECISION ──────────────────────────────────────────────────────
--
-- generate_series + LEFT JOIN
--   Aggregation cannot invent rows. Without the generated axis, a month
--   with no orders vanishes and the chart draws a straight line through
--   the outage — the one month you needed to see.
--
-- FILTER (Postgres) / sum(CASE ...) portable
--   All measures computed in ONE pass over the table instead of one
--   scan per metric. On a large fact table the scan IS the cost.
--
-- COALESCE on sum and avg, but not on count
--   sum/avg over an empty group return NULL. count returns 0.
--   Getting this wrong renders "null" in the UI or breaks a NOT NULL
--   insert downstream.
--
-- Half-open date range in the JOIN
--   BETWEEN would drop the last day of every month.

-- ── THE PORTABLE FORM ───────────────────────────────────────────────────
  sum(CASE WHEN o.status = 'paid' THEN 1 ELSE 0 END)   AS paid
-- ⚠ NOT count(CASE WHEN ... THEN 1 ELSE 0 END) — that counts EVERY row,
--   because 0 is not NULL. Use sum() with ELSE 0, or count() with no
--   ELSE at all. This is the single most common conditional-aggregation
--   bug.

-- ── SUBTOTALS FOR FREE ──────────────────────────────────────────────────
GROUP BY ROLLUP (m.month)       -- adds a grand-total row (month = NULL)
-- Use GROUPING(m.month) = 1 to tell a subtotal's NULL apart from a NULL
-- that is genuinely in the data.
4 (medium): "Top 3 products per category" — why GROUP BY cannot do it.
Solution 
-- ✗ THE ATTEMPT
SELECT category, name, max(revenue)
FROM products GROUP BY category;
-- ERROR: "name" must appear in GROUP BY.
-- And the reason is not pedantry: GROUP BY COLLAPSES the rows. Once a
-- category is one row, the individual products are gone — there is
-- nothing left to take the top 3 of.

-- ✗ AND THIS IS WRONG, NOT JUST INEFFICIENT
SELECT category, name, revenue FROM products p
WHERE revenue = (SELECT max(revenue) FROM products
                 WHERE category = p.category);
-- Only gives the top 1, and returns TWO rows on a tie.

-- ✓ WINDOW FUNCTION — ranks WITHOUT collapsing
SELECT category, name, revenue
FROM (
  SELECT category, name, revenue,
         row_number() OVER (PARTITION BY category
                            ORDER BY revenue DESC, id) AS rn
  FROM products
) t
WHERE rn <= 3
ORDER BY category, rn;

-- The window is computed per row, so every row survives and carries its
-- rank. The outer WHERE then cuts. (You cannot filter on rn in the same
-- SELECT — window functions are evaluated after WHERE, so it needs the
-- subquery or a CTE.)

-- ── CHOOSING THE RANKING FUNCTION ───────────────────────────────────────
-- revenue: 100, 100, 90, 80
--   row_number() → 1, 2, 3, 4    arbitrary tiebreak, always exactly 3
--   rank()       → 1, 1, 3, 4    ties share; gaps after
--   dense_rank() → 1, 1, 2, 3    ties share; no gaps
--
-- "Top 3" is ambiguous when there is a tie for third. row_number() gives
-- exactly three rows but drops one of the tied products arbitrarily —
-- add a deterministic tiebreaker (, id) or it varies between runs.
-- rank() <= 3 returns four rows on a tie, which is usually what a user
-- expects from a leaderboard. Decide, do not default.

-- ── THE POSTGRES SHORTCUT, FOR TOP-1 ────────────────────────────────────
SELECT DISTINCT ON (category) *
FROM products ORDER BY category, revenue DESC, id;
-- The ORDER BY must start with the DISTINCT ON columns.

-- ── LATERAL, WHEN THE TABLE IS LARGE ────────────────────────────────────
SELECT c.name, p.*
FROM categories c
CROSS JOIN LATERAL (
  SELECT * FROM products WHERE category_id = c.id
  ORDER BY revenue DESC LIMIT 3) p;
-- With an index on (category_id, revenue DESC) this reads only 3 rows
-- per category, instead of ranking every product in the table. Much
-- faster when there are many products and few categories.
5 (hard): A dashboard shows healthy averages while users complain. Diagnose the query.
Solution 
-- THE DASHBOARD QUERY
SELECT date_trunc('day', ts) AS day,
       avg(duration_ms)      AS avg_latency,
       count(*)              AS requests
FROM api_requests
WHERE ts >= now() - interval '30 days'
GROUP BY 1 ORDER BY 1;
-- Shows a steady 42ms. Support says the app "hangs constantly".

-- ── PROBLEM 1: THE MEAN HIDES THE TAIL ──────────────────────────────────
SELECT date_trunc('day', ts) AS day,
       count(*),
       round(avg(duration_ms))                                  AS mean,
       percentile_cont(0.50) WITHIN GROUP (ORDER BY duration_ms) AS p50,
       percentile_cont(0.95) WITHIN GROUP (ORDER BY duration_ms) AS p95,
       percentile_cont(0.99) WITHIN GROUP (ORDER BY duration_ms) AS p99,
       max(duration_ms)                                          AS worst
FROM api_requests WHERE ts >= now() - interval '30 days'
GROUP BY 1 ORDER BY 1;
--  mean 42 | p50 18 | p95 240 | p99 31000 | worst 60000
-- One percent of requests take 31 SECONDS. At 2M requests/day that is
-- 20,000 users a day, every one of whom will report the app as broken.
-- The mean is 42 because the other 99% are fast. It was never wrong —
-- it was answering a question nobody asked.

-- ── PROBLEM 2: FAILURES ARE NOT IN THE DATA ─────────────────────────────
-- A request that TIMED OUT never logged a duration. The worst
-- experiences are systematically absent from the table, so every metric
-- is computed over survivors only. Survivorship bias, in a latency
-- dashboard.
SELECT count(*) FILTER (WHERE duration_ms IS NULL) AS no_duration,
       count(*) FILTER (WHERE status >= 500)       AS errors
FROM api_requests WHERE ts >= now() - interval '30 days';
-- Always report an error rate NEXT to a latency number.

-- ── PROBLEM 3: AGGREGATING ACROSS ENDPOINTS ─────────────────────────────
-- /health is 2ms and called every second by the load balancer; it
-- dominates the row count and drags the mean down. Slice by what the
-- user actually experiences:
GROUP BY 1, endpoint
-- One /checkout at p99 = 30s matters more than a million fast /health
-- calls, and the combined average cannot show that.

-- ── PROBLEM 4: NULLs SILENTLY EXCLUDED ──────────────────────────────────
avg(duration_ms)     -- skips NULL rows entirely, without saying so
count(*)             -- 2,000,000
count(duration_ms)   --   1,890,000   ← 110,000 rows have no duration
-- Putting these side by side is what makes the gap visible.

-- ── PROBLEM 5: THE TIME AXIS ────────────────────────────────────────────
-- If the API was fully down for six hours, those rows do not exist, so
-- the day shows FEWER requests at a NORMAL latency — the outage looks
-- like a quiet day. Generate the axis and plot the request count next to
-- the latency; a volume drop is the outage signal.

-- ── WHAT THE DASHBOARD SHOULD SHOW ──────────────────────────────────────
-- per endpoint, per interval:
--   request count      (a drop = an outage the latency cannot show)
--   error rate         (excluded requests are the worst experiences)
--   p50 / p95 / p99    (never the mean)
--   count(*) vs count(duration_ms)  (how much data is missing)
--
-- The general lesson: an aggregate answers exactly the question it was
-- given. "Is the API healthy?" is not "what is the mean of the durations
-- we successfully recorded?", and the gap between those two questions is
-- where the outage lived for a month.
6 (hard): An hourly aggregation over 500M rows takes 8 minutes. Redesign it.
Solution 
-- ✗ BEFORE — recomputes all of history, every hour
SELECT date_trunc('day', ts) AS day, tenant_id,
       count(*), count(DISTINCT user_id), sum(amount)
FROM events
WHERE ts >= '2025-01-01'
GROUP BY 1, 2;

-- ── STEP 1: WHY IS IT SLOW? MEASURE ─────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS) ...
-- Typically: a sequential scan of 500M rows, then a HashAggregate that
-- spills to disk because the distinct-user hash tables do not fit in
-- work_mem. The count(DISTINCT) is usually the dominant cost — it must
-- materialise every distinct value per group.

-- ── STEP 2: STOP RECOMPUTING IMMUTABLE HISTORY ──────────────────────────
-- Yesterday's totals cannot change. Computing them 24 times a day is
-- the actual bug; index tuning only makes the waste faster.
CREATE TABLE daily_rollup (
  day date, tenant_id int,
  events bigint, distinct_users bigint, revenue numeric(14,2),
  PRIMARY KEY (day, tenant_id)
);

INSERT INTO daily_rollup
SELECT date_trunc('day', ts)::date, tenant_id,
       count(*), count(DISTINCT user_id), sum(amount)
FROM events
WHERE ts >= :last_completed_day AND ts < :today   -- ONLY new data
GROUP BY 1, 2
ON CONFLICT (day, tenant_id) DO UPDATE SET
  events = EXCLUDED.events, ...;
-- Each run touches one day's rows, not 500M. 8 minutes → ~2 seconds.

SELECT day, sum(events), sum(revenue) FROM daily_rollup   -- the dashboard
WHERE day >= :from GROUP BY day;                          -- reads THIS

-- ── STEP 3: THE COUNT(DISTINCT) PROBLEM ─────────────────────────────────
-- Distinct counts are NOT additive: you cannot sum daily distinct users
-- to get monthly distinct users — someone active on two days is counted
-- twice. Two honest options:
--
-- a) Store a HyperLogLog sketch per day. Sketches MERGE, so monthly and
--    quarterly uniques are computed from daily rollups, within ~2%:
CREATE EXTENSION postgresql_hll;
ALTER TABLE daily_rollup ADD COLUMN users_hll hll;
SELECT hll_cardinality(hll_union_agg(users_hll)) FROM daily_rollup
WHERE day >= :from;        -- exact enough for a dashboard, ~1000x cheaper
--
-- b) Keep exact counts only for the periods you actually publish
--    (day, month), computed once each, and accept that arbitrary ranges
--    are approximate.
-- What you must NOT do is sum the daily numbers and call it monthly
-- uniques. That is a wrong metric, not a slow one.

-- ── STEP 4: PARTITION THE FACT TABLE ────────────────────────────────────
CREATE TABLE events (...) PARTITION BY RANGE (ts);
-- Queries touching one day scan one partition (partition pruning), and
-- dropping old data becomes DROP TABLE — instantaneous — instead of a
-- DELETE that bloats the table and blocks. See Scaling.

-- ── STEP 5: THE INDEX, ONLY IF STILL NEEDED ─────────────────────────────
CREATE INDEX ON events (tenant_id, ts) INCLUDE (amount);
-- Only helps if a query reads a SMALL fraction. For a full-history
-- aggregate a sequential scan is correct and an index would be slower.
-- work_mem also matters: a HashAggregate that spills to disk can be
-- several times slower than one that fits.

-- ── THE ORDER THAT MATTERS ──────────────────────────────────────────────
-- 1. Do less work        incremental rollups — the 100x win
-- 2. Change the metric   HLL for distincts — the next 100x
-- 3. Change the layout   partitioning — prune and cheap retention
-- 4. Tune                indexes, work_mem — the last 2x
--
-- Most teams start at 4 and never reach 1. Materialised views
-- (REFRESH CONCURRENTLY) are the managed version of step 1 when the
-- refresh cost is acceptable; a rollup table wins when you need
-- incremental updates rather than a full recompute.

🎯 Key Takeaways

  • Every aggregate except count(*) ignores NULL, so avg divides by the non-NULL count and sum over no rows is NULL.
  • Every selected column must be grouped or aggregated — and legacy MySQL returned arbitrary values instead of an error.
  • Conditions on columns belong in WHERE; only conditions on aggregates need HAVING, which also makes the query cheaper.
  • Aggregating across a one-to-many join multiplies totals — aggregate before joining, and never patch it with DISTINCT.
  • Empty periods produce no rows: generate the axis and LEFT JOIN, or outages become straight lines.
  • Report percentiles rather than means for anything users experience, and show the error rate beside them.
  • FILTER or CASE computes many conditional measures in one pass — but never count(CASE … ELSE 0).
  • ROLLUP and GROUPING SETS give subtotals in one pass; GROUPING() distinguishes their NULLs from real ones.
  • Top-N per group needs a window function, because GROUP BY collapses the rows you wanted to keep.
  • Order by something unique before paginating, use keyset instead of deep OFFSET, and roll up history incrementally rather than recomputing it.
