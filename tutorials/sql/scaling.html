Scaling: Replication, Partitioning, Sharding Ultra-Advanced

What you'll master: how much a single well-tuned node genuinely handles — with arithmetic, because the number is far higher than most teams assume — how streaming replication actually works and why replication lag is a correctness problem rather than a performance one, the read-your-writes patterns that make replicas safe to use, why partitioning is a manageability tool that adds zero write capacity and the conditions under which pruning silently stops working, what sharding really costs once cross-shard joins, distributed transactions, rebalancing and hot keys arrive, how to choose a shard key you cannot cheaply change later, and the migration path that gets you there without downtime. Prerequisites: Query Optimization and Indexes. This is the capstone of the SQL track and the bridge to the System Design track — where CAP, consistent hashing and consensus are covered in full.

Part 1 — Step Zero: What One Node Actually Does

-- Before any distributed system, know the number you are walking away
-- from. Teams shard at 5% of a single node's capacity because nobody did
-- this arithmetic.

-- ── A MODERN SINGLE NODE (32 cores, 128GB RAM, NVMe) ────────────────────
--   simple indexed reads       50,000-100,000 /s
--   writes (small txns)         5,000-20,000 /s
--   data size on one node       up to ~10TB before it gets awkward
--   connections                 a few hundred, POOLED
--
-- Stack Overflow famously served the entire site from one SQL Server
-- primary for years. Most products never legitimately outgrow one node.

-- ── THE LADDER, IN COST ORDER ───────────────────────────────────────────
-- 1. FIX THE QUERIES         often 10-100×. Free. See the optimisation
--                            lesson — most "we need to scale" is three
--                            missing indexes and an N+1.
-- 2. CACHE                   removes reads entirely
-- 3. POOL CONNECTIONS        400 connections on 32 cores is SLOWER than
--                            60. More is not better.
-- 4. BIGGER MACHINE          the most underrated move: doubling RAM is a
--                            few hundred dollars a month and an hour of
--                            downtime. An engineer-year of sharding is
--                            not.
-- 5. READ REPLICAS           scale reads; lag becomes your problem
-- 6. PARTITION               manageability for big tables; NO extra
--                            write capacity
-- 7. SHARD                   scale writes; everything gets harder

-- ── WHICH RESOURCE IS ACTUALLY EXHAUSTED? ───────────────────────────────
SELECT sum(blks_hit)*100/NULLIF(sum(blks_hit+blks_read),0) AS cache_pct
FROM pg_stat_database WHERE datname=current_database();
-- <95% → memory-bound. Buy RAM before you buy a distributed system.
SELECT count(*) FROM pg_stat_activity WHERE state='active';
-- Consistently above core count → CPU-bound. Fix queries, or pool.
SELECT wait_event_type, count(*) FROM pg_stat_activity
WHERE wait_event IS NOT NULL GROUP BY 1 ORDER BY 2 DESC;
-- Dominated by IO → disk-bound. By Lock → contention, not capacity, and
-- sharding will NOT help.
-- ⚠ "The database is slow" is not a bottleneck. Name the resource.
💸 Vertical scaling is underrated because it is boring. Doubling a machine is reversible, takes an afternoon, and needs no application changes. Sharding is a multi-quarter project that permanently constrains every future query, every migration, and every new engineer's mental model. The honest comparison is not "one big server versus many small ones" — it is "a predictable hardware bill versus an ongoing engineering tax". Take the hardware until it genuinely runs out.

Part 2 — Replication: Scaling Reads, Inheriting Lag

--        writes            WAL stream (async)
--  App ──────────▶ PRIMARY ─────────────────▶ REPLICA 1  (read-only)
--       reads  ◀───────────────────────────── REPLICA 2  (read-only)
--
-- The primary ships its write-ahead log; replicas replay it continuously.
-- Same WAL that provides durability (transactions lesson) provides
-- replication — which is why it is cheap and why replicas are byte-exact.

-- ── PHYSICAL vs LOGICAL ─────────────────────────────────────────────────
-- PHYSICAL   block-level WAL shipping. Whole cluster, identical copy,
--            low overhead, same major version. The default for HA and
--            read scaling.
-- LOGICAL    decoded row changes, published per table. Cross-version,
--            selective, replica is writable. The tool for zero-downtime
--            upgrades, CDC into a warehouse, and — later — resharding.
CREATE PUBLICATION orders_pub FOR TABLE orders;              -- primary
CREATE SUBSCRIPTION s CONNECTION '...' PUBLICATION orders_pub;

-- ── THE CENTRAL PROBLEM: LAG IS A CORRECTNESS ISSUE ─────────────────────
SELECT client_addr, state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes,
       replay_lag
FROM pg_stat_replication;
-- On the replica:
SELECT now() - pg_last_xact_replay_timestamp() AS lag;

-- User saves their profile (primary), the redirect reads a replica that
-- is 400ms behind, and the page shows the OLD name. The user thinks the
-- save failed and does it again. Nothing is broken; the data is simply
-- from the past.
--
-- ⚠ Lag is normally milliseconds and occasionally seconds or minutes:
--   a bulk load, a long query on the replica blocking replay, a network
--   hiccup, or vacuum activity. Your code must be correct at BOTH ends
--   of that range — designing for the median is how this bites.

-- ── READ-YOUR-WRITES: FOUR PATTERNS ─────────────────────────────────────
-- 1. STICKY PRIMARY AFTER WRITE (simplest, most common)
--    On any write, mark the session "primary-only" for N seconds
--    (N > p99 lag). Correct, and costs a little primary read traffic.
if session.wrote_within(seconds=5): use_primary()

-- 2. LSN TOKEN (precise; no wasted primary reads)
SELECT pg_current_wal_insert_lsn();          -- after the write, store it
SELECT pg_last_wal_replay_lsn() >= :token;   -- on the replica: caught up?
--    Route to the replica only when it has passed your write. This is
--    the "monotonic reads" mechanism done properly.

-- 3. ROUTE BY QUERY CLASS (coarse, effective, easy to reason about)
--    Anything user-visible-after-write → primary.
--    Analytics, search, exports, admin reports → replica.

-- 4. SYNCHRONOUS REPLICATION (correctness by construction)
SET synchronous_commit = 'remote_apply';     -- per transaction
ALTER SYSTEM SET synchronous_standby_names = 'ANY 1 (r1, r2)';
--    COMMIT waits for the replica to APPLY. No lag for those writes.
--    Costs a network round trip on every commit, and quorum ('ANY 1')
--    matters: naming a single required standby means that standby going
--    down BLOCKS ALL WRITES. Availability traded for consistency, which
--    is the CAP conversation made concrete.

-- ── WHAT REPLICAS DO NOT SOLVE ──────────────────────────────────────────
-- ✗ WRITE capacity — every replica applies EVERY write. Ten replicas do
--   not give you 10× write throughput; they give you ten copies of the
--   same write load. This is the single most common misunderstanding.
-- ✗ Data size — each replica holds the full dataset.
-- ✗ Backups — a replica faithfully replicates your DELETE in
--   milliseconds. Backups and PITR are a separate, non-optional thing.

-- ── FAILOVER ────────────────────────────────────────────────────────────
-- Promotion is easy; the surrounding questions are not: who decides
-- (Patroni, RDS multi-AZ), how clients learn the new address, and how
-- you prevent SPLIT BRAIN when the old primary returns believing it is
-- still primary. With async replication, promotion LOSES the
-- transactions the replica had not yet received. Know your RPO before
-- the incident, not during it. Use a managed service unless you have a
-- strong reason not to.

Part 3 — Partitioning: Manageability, Not Capacity

CREATE TABLE events (
    id         bigint GENERATED ALWAYS AS IDENTITY,
    tenant_id  bigint      NOT NULL,
    created_at timestamptz NOT NULL,
    payload    jsonb       NOT NULL,
    PRIMARY KEY (id, created_at)       -- ⚠ the partition key MUST be in
) PARTITION BY RANGE (created_at);     --   every unique constraint

CREATE TABLE events_2026_08 PARTITION OF events
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
CREATE TABLE events_default PARTITION OF events DEFAULT;   -- catch-all
-- ⚠ A row that matches no partition ERRORS on insert. The default
--   partition prevents that outage, and monitoring it non-empty tells
--   you your partition-creation job has stopped. Automate creation
--   (pg_partman or a cron job that builds three months ahead).

-- ── WHAT YOU ACTUALLY GAIN ──────────────────────────────────────────────
-- 1. PRUNING — the planner skips irrelevant partitions entirely
EXPLAIN SELECT * FROM events WHERE created_at >= '2026-08-01';
--   Append -> Seq Scan on events_2026_08     (one partition, not 60)
-- 2. INSTANT RETENTION — the real reason most teams partition:
ALTER TABLE events DETACH PARTITION events_2023_01 CONCURRENTLY;
DROP TABLE events_2023_01;              -- milliseconds, no bloat
--   versus DELETE FROM events WHERE created_at < ... — hours of I/O,
--   millions of dead tuples, and a vacuum backlog afterwards.
-- 3. SMALLER INDEXES — per-partition B-trees are shallower and the hot
--    partition's index stays cached.
-- 4. CHEAPER MAINTENANCE — vacuum, ANALYZE and REINDEX run per
--    partition instead of over one enormous table.

-- ── WHAT YOU DO NOT GAIN ────────────────────────────────────────────────
-- ✗ WRITE CAPACITY. It is still one server, one WAL, one fsync stream.
--   Partitioning is a manageability and query-pruning tool. If your
--   bottleneck is write throughput, this step does nothing for you —
--   and confusing it with sharding is the most common conceptual error
--   in this area.

-- ── WHERE PRUNING SILENTLY STOPS WORKING ────────────────────────────────
WHERE created_at > now() - interval '7 days'   -- ✓ runtime pruning
WHERE date_trunc('day', created_at) = :d       -- ✗ function → NO pruning
WHERE tenant_id = 42                           -- ✗ key absent → ALL
                                               --   partitions scanned
-- ⚠ A query missing the partition key touches EVERY partition, so
--   partitioning made it SLOWER than the unpartitioned table. Before
--   partitioning, verify the key appears in the dominant query shapes —
--   this is a schema decision driven by the workload, not by table size.

-- ── CHOOSING THE STRATEGY ───────────────────────────────────────────────
-- RANGE by time   the default. Time-series, logs, events, orders.
--                 Retention becomes DETACH. Most partitioning is this.
-- LIST by region/tenant   for a handful of large, stable groups, or for
--                 data-residency requirements.
-- HASH by id      even spread when there is no natural range, but you
--                 lose the retention win — nothing to drop.

-- ── COSTS TO KNOW BEFORE COMMITTING ─────────────────────────────────────
-- • Every unique/primary key must INCLUDE the partition key. That is a
--   real modelling constraint: a globally unique `id` alone is no longer
--   enforceable.
-- • Planning time grows with partition count. Hundreds are fine;
--   thousands hurt. Keep partitions coarse enough to stay countable.
-- • Cross-partition queries append many scans.
-- • Foreign keys REFERENCING a partitioned table have historically been
--   limited — check your version.
-- • Converting a large existing table means creating the partitioned
--   parent and migrating data in batches; there is no in-place switch.

Part 4 — Sharding: What It Really Costs

shard = hash(tenant_id) % 8      → tenant 4291 lives on shard 3, always
-- Each shard is an INDEPENDENT database with its own primary, WAL and
-- replicas. Writes finally scale horizontally. Everything else gets
-- harder — permanently.

-- ── WHAT BREAKS, CONCRETELY ─────────────────────────────────────────────
-- 1. CROSS-SHARD QUERIES
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20;
--    Now: query all 8 shards, merge, sort, take 20. Latency becomes the
--    SLOWEST shard's, not the average — p99 of one shard is p99 of the
--    request. And LIMIT 20 with an OFFSET requires fetching
--    offset+limit from EVERY shard to merge correctly.
-- 2. NO CROSS-SHARD JOINS. Fetch both sides, join in application code,
--    with no planner, no statistics, and no index help.
-- 3. NO CROSS-SHARD TRANSACTIONS. Two-phase commit is slow and blocks
--    on coordinator failure; the practical answer is sagas —
--    compensating actions, eventual consistency, and idempotency
--    everywhere.
-- 4. AGGREGATES. count/sum fan out and merge; DISTINCT, median and
--    percentiles are genuinely hard.
-- 5. UNIQUENESS. A globally unique email cannot be enforced by a
--    constraint across shards. You need a separate lookup table (itself
--    a distributed system) or a different guarantee.
-- 6. AUTO-INCREMENT IDS collide. Use UUIDv7, Snowflake ids, or
--    per-shard ranges.
-- 7. SCHEMA MIGRATIONS run N times, and a partial failure leaves shards
--    on different versions.
-- 8. REBALANCING. Adding a shard with `% N` remaps almost EVERY key.
--    Consistent hashing or virtual buckets — decided UP FRONT, because
--    retrofitting it is a data migration. See the System Design track's
--    consistent-hashing lesson.

-- ── CHOOSING THE SHARD KEY (the decision you cannot undo) ───────────────
-- ✓ 1. MOST QUERIES FILTER BY IT → they stay single-shard. This
--       dominates every other consideration.
-- ✓ 2. HIGH CARDINALITY, EVEN DISTRIBUTION → no hot shard.
-- ✓ 3. CO-LOCATES DATA THAT TRANSACTS TOGETHER → transactions stay
--       local. In B2B SaaS, tenant_id satisfies all three, which is why
--       it is the usual answer.
--
-- ✗ TIMESTAMP for write-heavy data — every write today lands on ONE
--   shard. You built a distributed system with a single write node.
-- ✗ LOW CARDINALITY (country, status) — a few enormous shards.
-- ✗ A KEY ORTHOGONAL TO QUERIES — every request fans out to all shards,
--   so you pay all the costs and get none of the benefit.
-- ✗ ANYTHING MUTABLE — changing a row's shard key means moving the row
--   between databases. Shard keys must be immutable.

-- ── THE HOT-KEY PROBLEM SHARDING DOES NOT SOLVE ─────────────────────────
-- One tenant is 40% of your traffic. Hashing puts them on one shard, and
-- that shard is now the bottleneck. Real mitigations:
--   • dedicated shard for the whale (explicit routing table, not a hash)
--   • cache aggressively in front of that tenant
--   • sub-shard within the tenant by a secondary key
-- ⚠ A LOOKUP TABLE of key → shard is more flexible than pure hashing:
--   it lets you move individual tenants, isolate whales, and rebalance
--   incrementally. The cost is a lookup (cached) on every request. For
--   multi-tenant systems this is usually the better design, and it is
--   what most mature systems converge on.

-- ── USE SOMETHING THAT ALREADY EXISTS ───────────────────────────────────
-- Citus (Postgres extension: distributed tables, parallel queries)
-- Vitess (MySQL; what YouTube runs on)
-- CockroachDB / Yugabyte / Spanner — distribution built in
-- AWS Aurora Limitless, Azure Cosmos for PG
-- DIY sharding means writing a query router, a rebalancer, a
-- distributed-migration tool and a cross-shard transaction story. That
-- is a product, not a sprint.
BottleneckMoveBuysCosts
Slow queriesIndexes, rewrites, cachingOften 10–100×Nearly nothing — always do this first
Read trafficRead replicasNear-linear read capacityReplication lag becomes an application concern
Memory / CPU / diskA bigger machine2–4× for a credit cardA ceiling, and a maintenance window

Part 5 — Getting There Without Downtime

-- ── ADDING A READ REPLICA ───────────────────────────────────────────────
-- 1. provision, let it catch up, verify lag under peak load
-- 2. route ONE low-risk read path to it (an export, a report)
-- 3. add lag monitoring with an alert BEFORE broadening usage
-- 4. move query classes across gradually; keep read-your-writes on the
--    primary
-- 5. build the kill switch first: one config flag sends all reads back
--    to the primary. You will need it during a lag incident.

-- ── PARTITIONING AN EXISTING BIG TABLE ──────────────────────────────────
-- There is no in-place conversion. Expand → backfill → contract:
CREATE TABLE events_new (LIKE events INCLUDING ALL)
    PARTITION BY RANGE (created_at);
--   create partitions covering all existing data plus the future
-- 2. dual-write to both tables (application or trigger)
-- 3. backfill in resumable chunks, oldest first:
INSERT INTO events_new SELECT * FROM events
WHERE created_at >= :lo AND created_at < :hi
ON CONFLICT DO NOTHING;
-- 4. verify counts and checksums per range
-- 5. swap inside one transaction (DDL is transactional in Postgres):
BEGIN;
SET lock_timeout = '3s';
ALTER TABLE events RENAME TO events_old;
ALTER TABLE events_new RENAME TO events;
COMMIT;
-- 6. keep events_old for a rollback window, then drop it

-- ── SHARDING AN EXISTING DATABASE ───────────────────────────────────────
-- The hard part is not the split; it is that the application assumes one
-- database everywhere.
-- 1. PICK THE KEY and confirm it against real query logs — what
--    percentage of queries carry it? Below ~90%, reconsider the key.
-- 2. Add the shard key to every table that lacks it (a tenant_id
--    backfill is often the biggest single task).
-- 3. Introduce a ROUTING LAYER while still on one database, so all
--    traffic already flows through it. This is the step that makes the
--    rest survivable.
-- 4. Eliminate cross-shard queries in application code while you can
--    still run them — this is where the real work is.
-- 5. Move ONE tenant to shard 2 using logical replication, verify, cut
--    over, keep the rollback path.
-- 6. Migrate in waves, smallest tenants first.
-- ⚠ Build a shard-map service, not `% N` arithmetic in code. Moving one
--   tenant must not require a global rebalance.

-- ── AND THE OPTION PEOPLE FORGET ────────────────────────────────────────
-- FUNCTIONAL / VERTICAL SPLIT: move a whole subsystem — analytics
-- events, audit logs, sessions, the search index — to its own database.
-- Often 80% of the relief for 20% of the effort, because those tables
-- are usually the biggest and the least joined to anything else. Try
-- this before sharding the core domain.
🧭 Every distributed step trades a guarantee for capacity. Replicas trade read-your-writes for read throughput. Partitioning trades unique-key freedom for manageability. Sharding trades ACID transactions, joins and easy migrations for write throughput. None of these trades is wrong — but each must be made deliberately, in response to a measured bottleneck, with the lost guarantee replaced by something explicit. Complexity acquired without a measured reason is never given back.

Interview Questions

Beginner: What is a read replica and what problem does it solve?

A read replica is a second database server that continuously replays the primary's write-ahead log, so it holds a near-identical copy of the data and can serve read-only queries. Because most applications read far more than they write, often by ten to one or more, moving reads to one or more replicas takes a large fraction of the load off the primary and leaves it free to handle writes. Replicas also serve as failover targets, so the same mechanism provides both read scaling and high availability.

The important limitation is that replicas do not add write capacity. Every replica applies every write, so ten replicas mean ten copies of the same write workload, not ten times the throughput. If the primary is saturated by writes, replicas will not help at all.

The catch to design around is replication lag. Replication is asynchronous by default, so a replica trails the primary by milliseconds normally and sometimes much longer. A user who saves a change and is immediately shown a replica read may see stale data and conclude the save failed. That is why reads which must reflect a user's own recent write are routed to the primary for a short window afterwards.

Beginner: Distinguish partitioning from sharding precisely.

Partitioning splits one large table into multiple physical pieces inside a single database server. It stays one logical table — queries are written exactly as before — and the gains are partition pruning, where the planner skips pieces that cannot match, and cheap data lifecycle management, because dropping a month of old data becomes detaching a partition rather than deleting millions of rows. Maintenance work like vacuum and reindexing also becomes per-partition instead of operating on one enormous table. Crucially, the server's write capacity is unchanged: same machine, same WAL, same disk.

Sharding splits data across independent database servers, each owning a slice of the data selected by a shard key. This is the step that actually adds write capacity, because each shard has its own primary and its own write path. The price is that the application or a middleware layer must route every query, joins and transactions that span shards stop being possible in the ordinary way, unique constraints no longer hold globally, and schema migrations must be applied to every shard.

The short version I would give: partitioning is manageability within one node, sharding is capacity beyond one node. Reaching for partitioning when the bottleneck is write throughput is a very common and completely ineffective move.

Mid: How do you handle read-your-writes consistency with replicas?

The problem is that a write commits on the primary and the user's next read hits a replica that has not applied it yet, so the interface shows stale data immediately after an action the user just took. There are four practical approaches, and I would pick by how much precision the situation justifies.

The simplest is sticky routing: when a session performs a write, mark it primary-only for a window longer than observed p99 lag, typically a few seconds. It is easy to reason about and correct, costing only some extra primary read traffic. More precise is an LSN token: capture the primary's log position after the write, carry it with the session, and let a replica serve the read only once it has replayed past that position, otherwise falling back to the primary. That gives monotonic reads without wasting primary capacity, at the cost of plumbing the token through the request path.

A coarser approach that works well in practice is routing by query class — anything rendered to a user right after their own action goes to the primary, while analytics, search, exports and admin reporting go to replicas. Finally, synchronous replication with remote_apply removes lag for the transactions that use it, but it adds a network round trip to every such commit and creates an availability coupling, so it should be reserved for the small set of operations that genuinely require it, and configured with a quorum rather than a single named standby.

Whichever is chosen, replication lag needs monitoring and alerting, and there should be a kill switch that sends all reads back to the primary during a lag incident. Correctness must hold when lag is seconds, not just when it is the median.

Mid: How do you choose a shard key, and what goes wrong with a bad one?

Three properties matter, in order. First and most important, most queries must filter by it, so they resolve to a single shard; a key that queries do not carry means every request fans out to every shard and you pay all of sharding's costs while getting none of its benefit. Second, it needs high cardinality and even distribution so no shard becomes a hotspot. Third, it should co-locate data that is modified together, so transactions stay within one shard and you avoid distributed commits. In B2B SaaS, tenant identifier usually satisfies all three, which is why it is the standard answer.

The classic failures are instructive. A timestamp for write-heavy data sends every write today to one shard, producing a distributed system with a single effective write node. A low-cardinality field like country or status yields a handful of enormous shards. A key orthogonal to the query patterns forces scatter-gather on everything. And a mutable key is a design error in itself, because changing it means physically moving a row between databases.

Two things remain hard even with a good key. Hot keys — one tenant being a large share of traffic — are not solved by hashing, and need a dedicated shard, aggressive caching, or sub-sharding within that tenant. And rebalancing must be designed up front: hash % N remaps almost every key when N changes, so you want consistent hashing or, better for multi-tenant systems, a shard-map lookup table that lets you relocate individual tenants incrementally and isolate the whales.

Senior: Your primary is at 90% CPU with a 15:1 read/write ratio. Walk through your plan.

Before adding infrastructure I want to know what the CPU is doing, because 90% caused by three bad queries is a completely different problem from 90% of genuine capacity. I would pull pg_stat_statements ordered by total execution time, which is almost always heavily concentrated, and check the cache hit rate and the wait-event breakdown. A hit rate below about 95% means the working set does not fit in memory, and more RAM will do more than any topology change. High lock waits would mean contention rather than capacity, and sharding would not help at all. In my experience most databases at 90% have a small number of fixable queries or a missing index, and that is the cheapest possible win.

Assuming the queries are already reasonable, a 15:1 ratio points straight at read replicas, since reads are the overwhelming majority and they parallelise across replicas cleanly. I would add one, verify lag under peak load, and move low-risk read classes across first — reports, exports, search — while keeping anything a user reads immediately after their own write on the primary. Caching sits alongside this and is often better still, because a cached read costs the database nothing at all, and the highest-call-count queries from pg_stat_statements are usually excellent cache candidates.

In parallel I would consider simply upsizing the primary, because it is reversible, needs no application changes, and buys a factor of two to four for a predictable monthly cost. That is frequently the right answer while the replica work proceeds, and it is undervalued because it feels unsophisticated.

What I would not do is shard. With a 15:1 ratio the write load is a small fraction of the total, and sharding solves writes while making everything else harder. I would revisit that only when writes alone saturate a well-tuned primary, and even then I would first look at a functional split — moving a self-contained subsystem such as events, audit logs or sessions to its own database, which is usually most of the relief for a fraction of the effort. Throughout, I would set targets and alerting so the next capacity conversation starts with data rather than with a feeling.

Senior: Design the migration from a single database to a sharded one, without downtime.

The hardest part of this project is not splitting the data — it is that every line of application code assumes one database. So I would sequence the work so that the risky data movement happens last, after the application already behaves as though it were sharded.

I start with the shard key, validated against real query logs rather than intuition: what fraction of production queries already carry the candidate key? If it is well below ninety percent, either the key is wrong or a lot of code must change, and I want to know that before committing. Tenant identifier is usually the answer for multi-tenant systems. Then comes the unglamorous prerequisite: adding and backfilling that key on every table that lacks it, which is often the single largest task in the project.

Next I introduce a routing layer while everything is still on one database. All traffic flows through it, resolving a key to a connection via a shard-map service rather than modulo arithmetic, so that later I can move an individual tenant without a global rebalance. With routing in place I eliminate cross-shard queries while they still work — finding them by instrumenting the router to log any query without a shard key. This is where the real engineering is, and doing it while a single database still answers everything means each fix can be verified immediately instead of discovered as an outage.

Only then does data move. I use logical replication to copy one small tenant to a second shard, verify with row counts and checksums, flip that tenant's routing entry, and keep the rollback path for a while. Then migrate in waves, smallest first, monitoring after each. Global uniqueness needs an explicit answer before cutover — usually a lookup table for things like email — and identifiers must move to UUIDv7 or Snowflake so they do not collide. Schema migrations become an orchestrated per-shard process with partial-failure handling.

Finally, I would be honest in the design review that this is a multi-quarter commitment with a permanent tax on every future feature, and I would confirm that a functional split and vertical scaling have genuinely been exhausted. Sharding is the right answer for some systems, and it should be chosen with that cost stated out loud rather than discovered afterwards.

1 (easy): Set up a replica, measure lag, and reproduce a read-your-writes failure.
Solution 
-- ── PRIMARY ─────────────────────────────────────────────────────────────
-- postgresql.conf:  wal_level = replica
--                   max_wal_senders = 10
-- pg_hba.conf:      host replication repl 0.0.0.0/0 scram-sha-256
CREATE ROLE repl WITH REPLICATION LOGIN PASSWORD '...';

-- ── REPLICA ─────────────────────────────────────────────────────────────
pg_basebackup -h primary -U repl -D /var/lib/pgsql/data -R -P
-- -R writes standby.signal + primary_conninfo. Start it; it streams.

-- ── VERIFY ──────────────────────────────────────────────────────────────
-- on primary:
SELECT client_addr, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
FROM pg_stat_replication;
--  10.0.1.7 | streaming | async | 0
-- on replica:
SELECT pg_is_in_recovery();                        -- t
SELECT now() - pg_last_xact_replay_timestamp();    -- 00:00:00.004

-- ── REPRODUCE THE BUG ───────────────────────────────────────────────────
-- primary:
UPDATE users SET name='New Name' WHERE id=1;
-- replica, IMMEDIATELY:
SELECT name FROM users WHERE id=1;   -- 'Old Name'  ← the user's save
                                     --   appears to have failed

-- ── MAKE THE LAG BIG ENOUGH TO SEE ──────────────────────────────────────
-- primary:
INSERT INTO events SELECT ... FROM generate_series(1,5000000);
-- replica during the load:
SELECT now() - pg_last_xact_replay_timestamp();    -- 00:00:47  ← 47s
-- ⚠ THE POINT: lag is 4ms at rest and 47 SECONDS during a bulk load,
--   a long replica query, or a network problem. Code that is correct
--   only at the median is code that fails during every incident.

-- ── FIX A: STICKY PRIMARY ───────────────────────────────────────────────
def get_connection(session, write=False):
    if write or session.wrote_within(seconds=10):
        session.mark_write()
        return primary
    return replica

-- ── FIX B: LSN TOKEN (precise) ──────────────────────────────────────────
-- after the write, on primary:
SELECT pg_current_wal_insert_lsn();      -- '0/16B3748' → store in session
-- before a replica read:
SELECT pg_last_wal_replay_lsn() >= '0/16B3748'::pg_lsn;
-- false → use the primary for this read. No fixed timeout to tune, and
-- no wasted primary traffic once the replica has caught up.

-- ── AND MONITOR IT ──────────────────────────────────────────────────────
-- Alert on replay_lag > 5s, and build the kill switch that routes all
-- reads back to the primary. You will want it before you need it.
2 (easy): Partition a table by time; prove pruning works and prove where it does not.
Solution 
CREATE TABLE events (
    id bigint GENERATED ALWAYS AS IDENTITY,
    tenant_id bigint NOT NULL,
    created_at timestamptz NOT NULL,
    payload jsonb,
    PRIMARY KEY (id, created_at)      -- partition key REQUIRED in the PK
) PARTITION BY RANGE (created_at);

DO $$ DECLARE m date := '2026-01-01';
BEGIN
  WHILE m < '2027-01-01' LOOP
    EXECUTE format(
      'CREATE TABLE events_%s PARTITION OF events
       FOR VALUES FROM (%L) TO (%L)',
      to_char(m,'YYYY_MM'), m, m + interval '1 month');
    m := m + interval '1 month';
  END LOOP;
END $$;
CREATE TABLE events_default PARTITION OF events DEFAULT;   -- ⚠ essential

INSERT INTO events (tenant_id, created_at, payload)
SELECT (random()*1000)::int,
       '2026-01-01'::timestamptz + (random()*365*interval '1 day'),
       '{}'::jsonb
FROM generate_series(1,5000000);
ANALYZE events;

-- ── ✓ PRUNING WORKS ─────────────────────────────────────────────────────
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM events WHERE created_at >= '2026-08-01'
                              AND created_at <  '2026-09-01';
-- Aggregate
--   -> Seq Scan on events_2026_08          ← ONE partition
-- Buffers: shared hit=2841     Time: 24ms
-- (Unpartitioned equivalent: 5M rows, ~1.2s.)

-- ── ✗ WHERE IT SILENTLY STOPS ───────────────────────────────────────────
EXPLAIN SELECT count(*) FROM events
WHERE date_trunc('month', created_at) = '2026-08-01';
-- Append -> Seq Scan on events_2026_01 ... events_2026_12 (ALL 13)
-- The function hides the raw column, exactly as it defeats an index.

EXPLAIN SELECT count(*) FROM events WHERE tenant_id = 42;
-- Append over ALL partitions. The key is absent, so nothing can be
-- pruned — and this is now SLOWER than the unpartitioned table was.
-- ⚠ If tenant_id is your dominant filter, you partitioned on the wrong
--   column. Verify against real query logs BEFORE partitioning.

-- ── THE RETENTION WIN (usually the real reason) ─────────────────────────
\timing
DELETE FROM events WHERE created_at < '2026-02-01';
-- 412,000 rows, 8.4s, 412k dead tuples, vacuum backlog afterwards
ALTER TABLE events DETACH PARTITION events_2026_01 CONCURRENTLY;
DROP TABLE events_2026_01;
-- 12ms. No dead tuples. No bloat. This alone justifies partitioning for
-- most time-series tables.

-- ── AUTOMATE OR IT WILL BREAK AT MIDNIGHT ───────────────────────────────
-- Without a job creating future partitions, inserts land in the default
-- partition (or fail outright if there is none). Use pg_partman, or a
-- cron job that keeps three months ahead, and ALERT when the default
-- partition is non-empty — that is the signal the job has stopped.
3 (medium): Choose a shard key for a SaaS product and defend it against alternatives.
Solution 
-- PROJECT-MANAGEMENT SaaS: organisations → projects → tasks → comments.
-- 40k orgs. Largest is 8% of all data. Writes saturate one primary.

-- ── EVALUATE THE CANDIDATES ─────────────────────────────────────────────
-- ✗ task_id (or a hash of it)
--    Even distribution, but "all tasks in project X" — the single most
--    common query — hits EVERY shard. Scatter-gather on the hot path.
--    Fails criterion 1, which is the one that matters most.
-- ✗ created_at
--    All of today's writes land on one shard. A distributed system with
--    a single effective write node.
-- ✗ region / plan_tier
--    Low cardinality → a few enormous shards. And plan_tier is MUTABLE:
--    an upgrade would physically relocate the customer's data.
-- ✓ org_id
--    1. Nearly every query is already scoped to an org (it is the
--       security boundary, so it MUST be in every query anyway).
--    2. 40k orgs → good spread.
--    3. Projects, tasks and comments all belong to one org, so
--       transactions stay local.
--    4. Immutable.

-- ── CO-LOCATE THE WHOLE HIERARCHY ───────────────────────────────────────
ALTER TABLE projects ADD COLUMN org_id bigint NOT NULL;
ALTER TABLE tasks    ADD COLUMN org_id bigint NOT NULL;  -- denormalised
ALTER TABLE comments ADD COLUMN org_id bigint NOT NULL;  -- deliberately
-- Every table carries the shard key even when it is derivable through a
-- join. That denormalisation is what keeps a join single-shard, and it
-- is correct here rather than sloppy.

-- ── ROUTING: A MAP, NOT MODULO ──────────────────────────────────────────
CREATE TABLE shard_map (org_id bigint PRIMARY KEY, shard_id int NOT NULL);
-- ✓ move ONE org without touching any other
-- ✓ pin the 8% whale to its own shard
-- ✓ add shard 9 and migrate incrementally
-- ✗ a lookup per request — cached, and worth it
-- hash(org_id) % N is simpler and traps you: changing N remaps almost
-- every org at once. For multi-tenant systems the map wins, and it is
-- what mature systems converge on.

-- ── WHAT STILL BREAKS, AND THE ANSWERS ──────────────────────────────────
-- 1. "My tasks across all orgs" (users belong to several orgs)
--    → fan out to the user's orgs only (usually 1-3 shards), or keep a
--      per-user index table.
-- 2. Global unique email
--    → a separate users/auth database, not sharded. Identity is
--      genuinely global and does not belong in the sharded domain.
-- 3. Admin analytics across all orgs
--    → do NOT fan out over production shards. CDC into a warehouse.
-- 4. The 8% whale
--    → dedicated shard via the map. This is exactly why the map exists.
-- 5. Ids
--    → UUIDv7 or Snowflake. Per-shard sequences collide on merge.

-- ── THE HONEST CHECK BEFORE STARTING ────────────────────────────────────
-- Is it really WRITE throughput? A 40k-org SaaS saturating a modern
-- primary on writes alone is unusual. If reads dominate, replicas plus
-- caching are far cheaper. And moving events/audit/sessions to their own
-- database (a functional split) often removes most of the write load —
-- try that first.
4 (medium): Design the read/write routing layer for a replicated system.
Solution 
-- ── THE ROUTING RULES ───────────────────────────────────────────────────
class Router:
    def get(self, *, write=False, consistency='eventual', session=None):
        if write:
            session.record_write(lsn=None)      # filled in after commit
            return self.primary
        if consistency == 'strong':
            return self.primary                 # explicit opt-in
        if session and session.needs_own_writes():
            return self.primary                 # read-your-writes
        if self.all_replicas_lagging():
            return self.primary                 # ← the kill switch
        return self.pick_replica()

-- ── READ-YOUR-WRITES VIA LSN (precise) ──────────────────────────────────
    def record_write(self, conn):
        session.lsn = conn.execute(
            "SELECT pg_current_wal_insert_lsn()").scalar()
        session.lsn_expires = now() + 30s        # bound the memory

    def needs_own_writes(self):
        if not session.lsn: return False
        r = self.pick_replica()
        caught_up = r.execute(
            "SELECT pg_last_wal_replay_lsn() >= %s", session.lsn).scalar()
        if caught_up: session.lsn = None         # stop checking
        return not caught_up
-- Simpler fallback if plumbing the LSN is too invasive: a fixed sticky
-- window of ~2× p99 lag. Less precise, far less code.

-- ── HEALTH AND LAG GATING ───────────────────────────────────────────────
    def pick_replica(self):
        healthy = [r for r in self.replicas
                   if r.lag_seconds < 5 and r.is_up]
        if not healthy: return self.primary      # fail SAFE, not closed
        return random.choice(healthy)            # or least-connections
-- Poll lag every second in the background. NEVER measure it inline in
-- the request path — you would add a round trip to every read, and make
-- the database's bad day worse.

-- ── THE FOUR THINGS PEOPLE GET WRONG ────────────────────────────────────
-- 1. NO KILL SWITCH. During a lag incident you need one config flag to
--    send everything to the primary. Build it on day one.
-- 2. READS INSIDE A WRITE TRANSACTION going to a replica. Once a
--    transaction has written, ALL of its reads must use the primary.
--    Route per transaction, not per statement.
-- 3. LAG CHECKED SYNCHRONOUSLY per request. Background poll, cached
--    value.
-- 4. FAILING CLOSED. If every replica is unhealthy, use the primary and
--    alert. Degraded is better than down.

-- ── WHERE TO PUT IT ─────────────────────────────────────────────────────
-- Application layer  full context (session, transaction, intent), so the
--                    routing can be correct. Must be implemented once
--                    per language/framework.
-- Proxy (pgpool,     language-agnostic, but it must GUESS intent from
--  ProxySQL)         SQL text, and it cannot know about read-your-writes.
--                    Fine for coarse splits, wrong for correctness.
-- ✓ Correctness decisions belong in the application; connection
--   management and pooling belong in the proxy. Use both, for what each
--   is actually good at.

-- ── VERIFY IT ───────────────────────────────────────────────────────────
def test_read_after_write_uses_primary():
    with router.session() as s:
        s.execute("UPDATE users SET name='x' WHERE id=1")
        assert router.get(session=s) is router.primary
-- And in staging, artificially delay a replica (pg_wal_replay_pause())
-- to prove the application stays correct at 30 seconds of lag.
5 (hard): A 4TB single-node database is out of headroom. Produce a staged plan.
Solution 
-- SITUATION: 4TB, 85% CPU at peak, writes 3k/s, reads 45k/s, p99 900ms.
-- events = 3.1TB of the 4TB. Retention "forever" (nobody ever decided).
-- Leadership is asking about sharding.

-- ── STAGE 0: MEASURE (a day, and it usually changes the plan) ───────────
SELECT substr(query,1,60), calls, round(total_exec_time::numeric) AS ms,
       round(100*total_exec_time/sum(total_exec_time) OVER (),1) AS pct
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
SELECT sum(blks_hit)*100/NULLIF(sum(blks_hit+blks_read),0)
FROM pg_stat_database WHERE datname=current_database();  -- 78% ← !!
-- 78% cache hit rate on OLTP means the working set does not fit in RAM.
-- The database is doing physical I/O for nearly a quarter of reads. That
-- is the actual bottleneck, and it is not solved by sharding.

-- ── STAGE 1: DELETE DATA NOBODY NEEDS (week 1, free) ────────────────────
SELECT max(created_at) FROM events;    -- and: who queries old events?
-- Interview the users. Almost always the answer is "the last 90 days"
-- and the rest exists because deleting felt risky.
-- Archive to S3/Parquet, then drop. 3.1TB → 400GB.
-- ⚠ Do this FIRST. Every subsequent step is cheaper on a smaller
--   database: backups, restores, vacuum, replica builds, and the
--   migration itself.

-- ── STAGE 2: PARTITION events BY MONTH (week 2-3) ───────────────────────
-- So retention is permanent policy rather than a one-off heroic cleanup:
ALTER TABLE events DETACH PARTITION events_2025_11 CONCURRENTLY;
-- Monthly, automated. Never again a 3TB table nobody dares delete from.

-- ── STAGE 3: BUY RAM (week 3, one afternoon) ────────────────────────────
-- 128GB → 512GB. With the database now at ~900GB, the working set fits.
-- Cache hit rate 78% → 99%. p99 900ms → 120ms. CPU 85% → 40%.
-- ⚠ THIS IS USUALLY THE BIGGEST SINGLE WIN, and it is a purchase order
--   rather than a project. It is skipped because it feels like cheating.

-- ── STAGE 4: FIX THE TOP QUERIES (week 4) ───────────────────────────────
-- The top 5 from stage 0 are ~60% of database time. Two missing
-- composite indexes and one N+1 (see the optimisation lesson).

-- ── STAGE 5: REPLICAS + CACHE (week 5-6) ────────────────────────────────
-- 45k reads/s against 3k writes/s: overwhelmingly read-bound.
-- Two replicas + Redis for the hottest lookups. Primary load drops
-- roughly 70%.

-- ── STAGE 6: RE-MEASURE, THEN DECIDE ────────────────────────────────────
-- Typical outcome: CPU 30%, p99 80ms, 900GB, years of headroom.
-- NO SHARDING NEEDED. Six weeks, no permanent architectural tax.

-- ── STAGE 7: ONLY IF WRITES STILL SATURATE ──────────────────────────────
-- Next step is a FUNCTIONAL SPLIT, not sharding: move events, audit
-- logs and sessions to their own database. Those tables are large,
-- append-heavy and barely joined to the core domain — usually most of
-- the remaining write load, with none of sharding's costs.
-- Shard the core domain only when a single well-tuned primary genuinely
-- cannot absorb the writes.

-- ── THE ARGUMENT TO MAKE TO LEADERSHIP ──────────────────────────────────
-- "Sharding is 2-3 engineer-quarters and permanently constrains every
--  future query and migration. Here is a six-week plan that measures the
--  real bottleneck and probably removes it. If it does not, we will have
--  the data to justify sharding — and the smaller, partitioned database
--  will make that migration significantly easier anyway."
-- Every stage has standalone value and none is wasted if you do end up
-- sharding.
6 (hard): Design a multi-region deployment and be honest about what it costs.
Solution 
-- REQUIREMENT: users in US, EU and APAC. "Fast everywhere", GDPR
-- residency for EU personal data, survive losing a region.

-- ── THE PHYSICS YOU CANNOT ARGUE WITH ───────────────────────────────────
-- us-east ↔ eu-west     ~80ms round trip
-- us-east ↔ ap-south   ~220ms round trip
-- A synchronous cross-region commit costs AT LEAST one round trip. A
-- single global primary in us-east means EVERY APAC write waits 220ms
-- before the database even starts working. No amount of engineering
-- reduces the speed of light.

-- ── OPTION A: SINGLE PRIMARY + REGIONAL READ REPLICAS ───────────────────
-- primary us-east; streaming replicas in eu-west and ap-south
-- ✓ simple, strongly consistent, one place to reason about writes
-- ✓ local reads are fast everywhere (the majority of traffic)
-- ✗ writes are slow for distant users
-- ✗ losing us-east means promoting a replica and accepting RPO > 0
-- → THE RIGHT DEFAULT for read-heavy products. Start here.

-- ── OPTION B: PARTITION BY REGION (data residency) ──────────────────────
-- EU users' data lives in eu-west and NEVER leaves; US in us-east.
-- Routing by the user's home region; each region is an independent
-- primary with local replicas.
-- ✓ fast local reads AND writes
-- ✓ GDPR residency by construction, which is the actual requirement
-- ✗ cross-region queries are hard (a global leaderboard, admin search)
-- ✗ users who relocate need data migration
-- → This is sharding with geography as the shard key, and for a
--   residency requirement it is usually the correct answer.

-- ── OPTION C: MULTI-PRIMARY / GLOBALLY DISTRIBUTED ──────────────────────
-- Spanner, CockroachDB, Yugabyte. Consensus (Paxos/Raft) per write.
-- ✓ write anywhere, strong consistency, survives region loss
-- ✗ every write pays cross-region consensus latency
-- ✗ operationally and financially expensive; different SQL dialect and
--   different failure modes to learn
-- → Justified when you genuinely need global strong consistency. Rare.

-- ── OPTION D: ACTIVE-ACTIVE WITH CONFLICT RESOLUTION ────────────────────
-- Asynchronous bidirectional replication.
-- ✗ CONCURRENT CONFLICTING WRITES ARE INEVITABLE and there is no
--   correct generic resolution. Last-write-wins silently discards data,
--   and clock skew decides which. CRDTs work for a narrow class of data
--   structures.
-- → Only with data designed for it. Not a general-purpose choice, and
--   the option most likely to be chosen for the wrong reasons.

-- ── THE RECOMMENDATION ──────────────────────────────────────────────────
-- Given the stated requirements: OPTION B, because residency is a hard
-- legal constraint that A cannot satisfy and C satisfies expensively.
--   • eu-west primary owns EU personal data, with local replicas
--   • us-east primary owns everything else
--   • ap-south gets read replicas of us-east (reads are the majority)
--   • a small GLOBAL, non-personal reference dataset (product catalogue,
--     pricing) replicated read-only everywhere
--   • cross-region analytics via CDC into a warehouse — NEVER by
--     querying production across regions

-- ── WHAT TO TELL THE ROOM ───────────────────────────────────────────────
-- 1. "Fast everywhere" cannot mean fast strongly-consistent WRITES
--    everywhere. Pick which regions get local writes; the rest get fast
--    reads and slower writes. That is a product decision, not a
--    technical one, and it must be made explicitly.
-- 2. Multi-region multiplies operational complexity: N times the
--    failover runbooks, N times the migrations, and debugging that now
--    involves inter-region lag.
-- 3. Most products that "need multi-region" need a CDN and regional
--    read replicas. The database rarely needs to be multi-primary.
-- 4. Test region failure deliberately, on a schedule. An untested
--    failover is a hypothesis, not a capability.

🎯 Key Takeaways

  • Know what one node does — tens of thousands of reads per second and terabytes of data — before buying distributed complexity; most "we must scale" is three missing indexes and an N+1.
  • Name the exhausted resource: cache hit rate, CPU, I/O, or lock waits. Sharding does not fix contention, and replicas do not fix writes.
  • Vertical scaling is reversible, needs no code changes, and is undervalued precisely because it is boring.
  • Replicas scale reads only — every replica applies every write — and a replica is never a backup.
  • Replication lag is a correctness problem: handle read-your-writes with sticky routing or LSN tokens, and stay correct when lag is seconds rather than milliseconds.
  • Partitioning buys pruning, instant retention via DETACH, and cheap maintenance — and zero write capacity.
  • A query without the partition key scans every partition, so partitioning the wrong column makes things slower; verify against real query logs first.
  • The shard key must be one that most queries filter by, high-cardinality, co-locating transactional data, and immutable — and you cannot cheaply change it later.
  • Prefer a shard-map lookup over hash % N: it lets you relocate one tenant, isolate whales, and rebalance incrementally.
  • Try a functional split — moving events, audit logs or sessions to their own database — before sharding the core domain; it is often most of the relief for a fraction of the cost.
