Schema Design & Normalization Intermediate

What you'll master: keys and the surrogate-versus-natural argument including where UUIDs hurt, the normal forms explained by the anomalies they prevent rather than by their definitions, when denormalisation is correct modelling versus premature optimisation, choosing types you cannot cheaply change later, using constraints to make invalid states unrepresentable, modelling time and history, JSONB and the schemaless temptation, and the anti-patterns — EAV, polymorphic associations, god tables — that look reasonable at design time and are expensive forever after. Prerequisites: JOINs and INSERT, UPDATE, DELETE.

Part 1 — Keys and Relationships

CREATE TABLE users (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      citext NOT NULL UNIQUE,
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id  bigint NOT NULL REFERENCES users(id),
    total    numeric(12,2) NOT NULL CHECK (total >= 0),
    status   text NOT NULL DEFAULT 'pending'
             CHECK (status IN ('pending','paid','shipped','cancelled'))
);
CREATE INDEX ON orders (user_id);        -- ⚠ NOT automatic. See below.

-- ── SURROGATE vs NATURAL KEYS ───────────────────────────────────────────
-- SURROGATE: a meaningless generated id. Never changes, compact, uniform.
-- NATURAL:   a real-world value that identifies the row (email, ISBN).
--
-- Default to a surrogate PK, and put a UNIQUE constraint on the natural
-- key. The reason is that "immutable real-world identifiers" mostly are
-- not: emails change, usernames change, ISBNs get reissued, and country
-- codes have been reassigned. When a natural key changes and it is
-- referenced by six tables, you are updating six tables under a lock.
--
-- The surrogate gives stable identity; the UNIQUE constraint still gives
-- you the business rule. You want both.

-- ── bigint vs UUID ──────────────────────────────────────────────────────
id bigint GENERATED ALWAYS AS IDENTITY    -- 8 bytes, sequential
id uuid DEFAULT gen_random_uuid()         -- 16 bytes, RANDOM

-- Random UUIDv4 as a primary key has a real cost that surprises people:
-- inserts land in random positions of the B-tree, so every insert dirties
-- a different page. That means page splits, poor cache locality, and a
-- much larger working set than a sequential key. On a large table the
-- write throughput difference is substantial.
--
-- ✓ Use UUIDv7 (time-ordered) if you need UUIDs — it keeps insert
--   locality while staying globally unique. Or ULID/Snowflake ids.
-- ✓ Legitimate reasons for UUIDs: ids generated by clients or other
--   services, merging data from several databases, or not wanting to
--   leak row counts in public URLs.
-- ✗ Not a reason: "it feels more modern". A bigint plus a separate
--   public_id column is often the better answer — internal joins stay
--   compact, external references stay opaque.

-- ── FOREIGN KEYS EARN THEIR KEEP ────────────────────────────────────────
user_id bigint NOT NULL REFERENCES users(id)
-- The database now guarantees no order can reference a user that does
-- not exist. Application-level checks cannot make that guarantee: they
-- race, they get bypassed by a migration or a console session, and they
-- are only as good as the last person who remembered them.
--
-- ⚠ Postgres indexes the PRIMARY KEY automatically but NOT the foreign
--   key. Without an index on the child column, every join scans the
--   child table and every ON DELETE CASCADE is a full scan. This is the
--   single most common missing index in real schemas.

-- ── RELATIONSHIPS ───────────────────────────────────────────────────────
-- one-to-many    FK on the MANY side               orders.user_id
-- many-to-many   a JUNCTION table with both FKs    enrollments
-- one-to-one     FK + UNIQUE, or a shared PK

CREATE TABLE enrollments (
    student_id  bigint NOT NULL REFERENCES students(id) ON DELETE CASCADE,
    course_id   bigint NOT NULL REFERENCES courses(id),
    enrolled_at timestamptz NOT NULL DEFAULT now(),
    grade       text,
    PRIMARY KEY (student_id, course_id)      -- the pair is the identity,
);                                           -- and it prevents duplicates
CREATE INDEX ON enrollments (course_id);     -- the PK covers student_id
                                             -- first; queries by course
                                             -- need their own index
-- A junction table is not just plumbing — it is the natural home for
-- attributes OF THE RELATIONSHIP (when, what grade, which role).

Part 2 — Normalisation by the Anomalies It Prevents

-- ✗ THE UNNORMALISED TABLE
orders(id, user_name, user_email, product1, product2, product3, ...)

-- It causes three distinct kinds of bug, and the normal forms are named
-- after fixing them:
--
-- UPDATE ANOMALY   a user changes email → update every order row they
--                  have. Miss one and the database now holds two
--                  contradictory facts, with no way to tell which is
--                  right.
-- INSERT ANOMALY   you cannot record a user who has not ordered yet;
--                  there is nowhere to put them.
-- DELETE ANOMALY   deleting a user's last order deletes the only copy of
--                  their email. Information vanishes as a side effect.

-- ✓ NORMALISED: each fact stored exactly once
users(id, name, email)
orders(id, user_id, created_at)
order_items(order_id, product_id, quantity, unit_price)
FormRuleThe violation it fixes
1NFAtomic values; no repeating groupsproduct1, product2, product3, or a comma-separated list in one column
2NF1NF + no non-key column depends on only part of a composite keyStoring product_name in order_items(order_id, product_id) — it depends on the product alone
3NF2NF + no non-key column depends on another non-key columnStoring city and state when the city determines the state
BCNFEvery determinant is a candidate keyRare; overlapping candidate keys
-- ── THE MNEMONIC ────────────────────────────────────────────────────────
-- "Every non-key fact depends on the key, the whole key, and nothing but
--  the key."
--   the key         → 1NF
--   the WHOLE key   → 2NF
--   NOTHING BUT     → 3NF
-- 3NF is the practical target. BCNF and above matter in exams far more
-- than in production.

-- ── WHY 1NF MATTERS MORE THAN IT SOUNDS ─────────────────────────────────
tags text          -- 'sql,database,indexing'
-- Cannot be indexed usefully, cannot be joined, cannot be constrained,
-- and every query is a LIKE '%sql%' that also matches 'nosql'. Renaming
-- a tag means a string rewrite across the table.
CREATE TABLE post_tags (post_id bigint, tag_id bigint, PRIMARY KEY (post_id, tag_id));
-- Now: indexed, joinable, countable, and a tag rename is one UPDATE.

-- ⚠ Postgres arrays and JSONB are a genuine, indexable exception —
--   they do not violate the SPIRIT of 1NF the way a CSV string does.
--   But they still cannot have foreign keys, so use them for values, not
--   for references.

-- ── WHEN "REDUNDANCY" IS ACTUALLY CORRECT ───────────────────────────────
order_items(order_id, product_id, quantity, unit_price)
--                                            ^^^^^^^^^^
-- This looks like it duplicates products.price and violates 3NF. It does
-- not: the price AT THE TIME OF PURCHASE is a different fact from the
-- product's current price. Joining to products for the price means every
-- historical order silently changes when someone runs a sale.
--
-- The same applies to a shipping address on an order, and a tax rate on
-- an invoice. Snapshotting an immutable historical fact is CORRECT
-- MODELLING, not denormalisation — the test is whether the value is
-- allowed to change independently of its source. If yes, store it.
Key insight: normalisation is not a style preference — it is what makes a contradiction impossible to represent. If a user's email exists in exactly one place, the database cannot hold two different answers to "what is their email?", and no amount of buggy application code can make it. Every denormalisation trades that guarantee for read speed, and the correct question is never "is this normalised?" but "what keeps these two copies in agreement, and what happens when that mechanism fails?" A denormalisation with a trigger maintaining it is a decision; one maintained by remembering to update both places is a future incident.

Part 3 — Denormalisation, Deliberately

-- Normalisation optimises WRITES and CONSISTENCY. Reads may then need
-- joins and aggregates. At scale, controlled duplication buys read speed
-- — and costs you a synchronisation problem forever.

-- ── 1. COUNTER / SUMMARY COLUMNS ────────────────────────────────────────
ALTER TABLE users ADD COLUMN order_count int NOT NULL DEFAULT 0;
-- Avoids count(*) on every profile view. Now: what keeps it correct?
CREATE FUNCTION bump_order_count() RETURNS trigger AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE users SET order_count = order_count + 1 WHERE id = NEW.user_id;
  ELSIF TG_OP = 'DELETE' THEN
    UPDATE users SET order_count = order_count - 1 WHERE id = OLD.user_id;
  END IF;
  RETURN NULL;
END $$ LANGUAGE plpgsql;
-- ⚠ Every order insert now takes a row lock on the USER. Two orders for
--   the same user serialise; a popular seller becomes a write hotspot.
-- ⚠ And it must handle UPDATE that moves an order between users.
-- Enforce it in the DATABASE (trigger), not in application code — code
-- gets bypassed by migrations, imports and console sessions.

-- ── 2. MATERIALISED VIEWS ───────────────────────────────────────────────
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT date_trunc('day', created_at) AS day, sum(total) AS revenue
FROM orders GROUP BY 1;
CREATE UNIQUE INDEX ON daily_revenue (day);      -- required for
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;   -- ← this
-- The honest denormalisation: the staleness is explicit and bounded by
-- the refresh schedule, and there is no per-write cost at all. Best
-- choice when the data need not be real time.

-- ── 3. SNAPSHOTTING HISTORY ─────────────────────────────────────────────
-- (Part 2) — not really denormalisation, just correct modelling.

-- ── 4. WIDE / REPORTING TABLES ──────────────────────────────────────────
-- A star schema for analytics: a fact table plus dimension tables, with
-- values pre-joined. Rebuilt by a pipeline, never written by the app.
-- Correct for OLAP; wrong for the transactional path.

-- ── THE DECISION PROCEDURE ──────────────────────────────────────────────
-- 1. Normalise first. It is far easier to denormalise a clean schema
--    than to normalise a messy one with production data in it.
-- 2. MEASURE. "Joins are slow" is usually a missing index, an N+1, or
--    a query returning far more rows than it needs.
-- 3. If denormalising, decide the sync mechanism BEFORE writing the
--    column: trigger, materialised view, or scheduled job.
-- 4. Add a reconciliation check that detects drift, because the sync
--    WILL fail eventually and silent divergence is the worst outcome:
SELECT u.id FROM users u
WHERE u.order_count <> (SELECT count(*) FROM orders WHERE user_id = u.id);

-- ── THE ANTI-PATTERN ────────────────────────────────────────────────────
-- Denormalising before there is a measured read problem. You accept the
-- sync cost and the consistency risk permanently, in exchange for a
-- speedup you never verified you needed.

Part 4 — Types and Constraints

-- Types and constraints are the cheapest correctness you will ever buy,
-- and the most expensive to change once there is data.

-- ── MONEY ───────────────────────────────────────────────────────────────
amount float                -- ✗ 0.1 + 0.2 ≠ 0.3. Sums drift. Audits fail
                            --   months later with a one-cent difference
                            --   nobody can trace.
amount numeric(12,2)        -- ✓ exact decimal
amount_cents bigint         -- ✓ also fine, and unambiguous about scale
-- Store the CURRENCY too, unless you are certain there will only ever be
-- one — and there is almost always eventually a second.

-- ── TIME ────────────────────────────────────────────────────────────────
created_at timestamp        -- ✗ no zone. Ambiguous across DST, and its
                            --   meaning depends on who reads it.
created_at timestamptz      -- ✓ stored as UTC, rendered per client zone
birth_date  date            -- ✓ a birthday has no time zone
duration    interval

-- ── TEXT ────────────────────────────────────────────────────────────────
name varchar(255)           -- 255 is an inherited MySQL habit with no
                            -- meaning in Postgres, where varchar(n) and
                            -- text perform identically
name text CHECK (length(name) BETWEEN 1 AND 200)   -- ✓ a real rule,
                                                   --   stated once
email citext                -- ✓ case-insensitive comparison and
                            --   uniqueness without LOWER() everywhere

-- ── ENUMS: THREE OPTIONS ────────────────────────────────────────────────
status text CHECK (status IN ('pending','paid','shipped'))   -- ✓ default:
                                          -- simple, and adding a value
                                          -- is one ALTER of the CHECK
CREATE TYPE order_status AS ENUM (...);   -- ⚠ compact and type-safe, but
                                          -- REMOVING or reordering values
                                          -- is painful
CREATE TABLE order_statuses (...)         -- ✓ when statuses carry
                                          -- attributes (label,
                                          -- is_terminal, sort order) or
                                          -- are edited by users

-- ── CONSTRAINTS MAKE BAD STATES UNREPRESENTABLE ─────────────────────────
CHECK (total >= 0)
CHECK (ends_at > starts_at)
CHECK (discount_pct BETWEEN 0 AND 100)
CHECK ((paid_at IS NULL) = (status <> 'paid'))   -- cross-column invariant
UNIQUE (email)
UNIQUE (email) WHERE deleted_at IS NULL          -- partial: lets a
                                                 -- deleted user free
                                                 -- their address
EXCLUDE USING gist (room WITH =, during WITH &&) -- no double-booking a
                                                 -- room for overlapping
                                                 -- time ranges
NOT NULL                                         -- the most valuable one

-- Default columns to NOT NULL and justify every nullable one. A nullable
-- column is a branch that every future query has to remember — and
-- forgetting it loses rows silently rather than raising an error.

-- ── VALIDATE WITHOUT LOCKING (large tables) ─────────────────────────────
ALTER TABLE orders ADD CONSTRAINT c CHECK (total >= 0) NOT VALID;  -- instant
ALTER TABLE orders VALIDATE CONSTRAINT c;   -- scans, but takes only a
                                            -- SHARE UPDATE EXCLUSIVE
                                            -- lock, so writes continue

Part 5 — Modelling Time, History, and Hierarchies

-- ── AUDIT COLUMNS ───────────────────────────────────────────────────────
created_at timestamptz NOT NULL DEFAULT now(),
updated_at timestamptz NOT NULL DEFAULT now()   -- maintained by a TRIGGER,
                                                -- not by application code
-- Application-maintained timestamps are wrong whenever anything writes
-- outside the application — migrations, imports, a console fix.

-- ── FULL HISTORY: TEMPORAL TABLES ───────────────────────────────────────
CREATE TABLE prices (
    product_id bigint NOT NULL REFERENCES products(id),
    price      numeric(12,2) NOT NULL,
    valid_from timestamptz NOT NULL,
    valid_to   timestamptz,                      -- NULL = current
    EXCLUDE USING gist (
      product_id WITH =,
      tstzrange(valid_from, valid_to) WITH &&)   -- ← no overlapping
);                                               --   periods, enforced
-- "What was the price on 3 March?" becomes answerable, and the exclusion
-- constraint makes contradictory history structurally impossible.
SELECT price FROM prices
WHERE product_id = :id AND valid_from <= :t AND (valid_to > :t OR valid_to IS NULL);

-- ── EVENT LOG ───────────────────────────────────────────────────────────
CREATE TABLE order_events (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id bigint NOT NULL, event_type text NOT NULL,
    payload jsonb, occurred_at timestamptz NOT NULL DEFAULT now()
);
-- Append-only. Current state is derived, or kept as a maintained
-- projection. Full auditability at the cost of read complexity.

-- ── STATUS AS A COLUMN vs A STATE MACHINE ───────────────────────────────
status text CHECK (status IN (...))
-- Fine, but it records only WHERE the order is, not how it got there.
-- If "when was it shipped?" or "who cancelled it?" is ever asked, you
-- need timestamps per transition or an event log. Adding that later
-- means the history before the change is simply gone.

-- ── HIERARCHIES ─────────────────────────────────────────────────────────
parent_id bigint REFERENCES categories(id)   -- adjacency list: trivial
                                             -- writes, recursive reads
path ltree                                   -- materialised path: one
                                             -- index scan per subtree
closure table (ancestor, descendant, depth)  -- fastest reads, most write
                                             -- cost, handles DAGs
-- Choose by the read/write ratio (see Subqueries & CTEs).

-- ── MULTI-TENANCY ───────────────────────────────────────────────────────
tenant_id bigint NOT NULL      -- shared tables + a tenant column
-- Simplest and scales well, but EVERY query must filter by tenant and
-- one forgotten filter is a cross-tenant data leak. Enforce it in the
-- database rather than by convention:
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY t ON orders USING (tenant_id = current_setting('app.tenant')::bigint);
-- Also: put tenant_id FIRST in composite indexes, since every query
-- filters on it.

Part 6 — Anti-Patterns

-- ── 1. EAV (ENTITY-ATTRIBUTE-VALUE) ─────────────────────────────────────
CREATE TABLE attributes (entity_id bigint, name text, value text);
-- "Infinitely flexible." What you actually lose:
--   * no types — everything is text, so no range queries, no arithmetic
--   * no constraints — nothing can be NOT NULL or CHECKed
--   * reading one entity with 20 attributes = a 20-way self-join
--   * the query planner has no statistics that mean anything
-- ✓ Use JSONB for genuinely sparse, user-defined attributes:
attributes jsonb
CREATE INDEX ON products USING gin (attributes);
SELECT * FROM products WHERE attributes @> '{"colour":"red"}';
-- ✓ Or accept that you have a fixed set of columns, because you usually do.

-- ── 2. POLYMORPHIC ASSOCIATIONS ─────────────────────────────────────────
CREATE TABLE comments (
  commentable_id bigint, commentable_type text);   -- 'Post' | 'Photo'
-- ✗ NO FOREIGN KEY IS POSSIBLE. The database cannot enforce that the
--   referenced row exists, so orphans accumulate silently. Joining
--   requires a CASE or a UNION, and none of it is indexable well.
-- ✓ Separate FK columns with a CHECK that exactly one is set:
post_id bigint REFERENCES posts(id),
photo_id bigint REFERENCES photos(id),
CHECK (num_nonnulls(post_id, photo_id) = 1)
-- ✓ Or a shared parent table ("commentable") that both reference.

-- ── 3. THE GOD TABLE ────────────────────────────────────────────────────
-- users with 90 columns: profile, billing, preferences, session state,
-- feature flags. Every read pulls a wide row; every write updates a
-- heavily-indexed one; unrelated concerns lock the same row. Split by
-- lifecycle and access pattern, especially separating hot volatile
-- columns (last_seen_at) from cold stable ones.

-- ── 4. NULLABLE EVERYTHING ──────────────────────────────────────────────
-- A schema where every column is nullable encodes no rules at all. Every
-- query must handle every absence, and three-valued logic quietly drops
-- rows from filters and their negations.

-- ── 5. NO FOREIGN KEYS "FOR PERFORMANCE" ────────────────────────────────
-- The cost of an FK check is an indexed lookup. The cost of orphaned
-- rows is a data-cleanup project and reports that silently undercount.
-- If FK checks are genuinely hot, the answer is usually the missing
-- index on the child column.

-- ── 6. STORING DERIVED DATA WITH NO SYNC MECHANISM ──────────────────────
-- A total_amount column updated by application code in three places. It
-- will diverge. Use a generated column, a trigger, or compute it.
total numeric GENERATED ALWAYS AS (quantity * unit_price) STORED;

-- ── 7. PREMATURE SHARDING / OVER-ABSTRACTION ────────────────────────────
-- Postgres handles hundreds of millions of rows on one machine. A
-- generic "entity" table with a "type" column, or a sharding scheme
-- adopted at 100k rows, is complexity purchased against a problem you
-- may never have — and it makes every simple query harder in the
-- meantime.

Interview Questions

Beginner: What problems does normalisation actually solve?

It removes the anomalies that duplication causes. If a user's email is copied onto every one of their order rows, then changing it means updating all of them — and missing one leaves the database holding two contradictory facts with no way to tell which is correct. That is the update anomaly. There is also an insert anomaly, where you cannot record a user who has not ordered yet because there is nowhere to put them, and a delete anomaly, where removing someone's last order destroys the only copy of their contact details as a side effect.

Normalising means each fact lives in exactly one place and everything else references it by key, which makes the contradiction structurally impossible rather than merely unlikely. The usual mnemonic for third normal form is that every non-key fact depends on the key, the whole key, and nothing but the key — the three clauses corresponding to 1NF, 2NF and 3NF respectively. Third normal form is the practical target; the higher forms come up far more in exams than in production.

Beginner: How do you model a many-to-many relationship?

With a junction table holding foreign keys to both sides — students and courses linked by an enrolments table, with a composite primary key on the pair. A single foreign key column can only express one-to-many, and storing a list of ids in a column violates first normal form: it cannot be indexed, joined or constrained, so you lose everything the database was going to do for you.

The composite primary key does double duty: it identifies the row and prevents the same student being enrolled twice. Worth noting that the junction table is also the natural home for attributes of the relationship itself — when the enrolment happened, what grade was awarded, what role someone has on a project — which is often what makes the table clearly a real entity rather than plumbing. One practical detail: a composite key on (student_id, course_id) gives you an index leading with student, so queries filtering by course need their own index.

Mid: When would you denormalise, and what does it cost?

When a measured read pattern is too slow in normalised form and the alternatives have been ruled out. I would check first whether the real problem is a missing index, an N+1 query, or a query returning far more rows than it needs, because "joins are slow" is much more often one of those than a genuine modelling issue.

The cost is that you now own a synchronisation problem permanently. A cached order_count on users is only correct while something keeps it correct, and that something must live in the database — a trigger, a generated column, or a materialised view — because application code gets bypassed by migrations, bulk imports and console sessions. There are second-order costs too: a counter trigger takes a row lock on the parent for every child insert, so a popular seller becomes a write hotspot and concurrent orders serialise. And whatever the mechanism, it will eventually fail, so a denormalisation without a reconciliation query that detects drift is a silent-divergence incident waiting to happen.

Of the available techniques, materialised views are the most honest, because the staleness is explicit and bounded by the refresh schedule and there is no per-write penalty at all. The thing I would push back on is denormalising during initial design — it is far easier to denormalise a clean schema later than to normalise a messy one that already has production data in it.

Mid: Should the primary key be a natural key, a bigint, or a UUID?

Default to a surrogate bigint and put a unique constraint on the natural key, which gives stable identity and still enforces the business rule. The argument against natural primary keys is that supposedly immutable real-world identifiers usually are not — emails change, usernames change, ISBNs get reissued — and when the key changes while six tables reference it, you are updating six tables under a lock. A surrogate never changes, is compact in indexes, and is uniform across the schema.

UUIDs solve a specific problem: identifiers generated by clients or other services, merging data from multiple databases, or not wanting sequential ids in public URLs to leak row counts and growth rates. But random UUIDv4 as a primary key has a real cost, which is that inserts land at random positions in the B-tree, dirtying a different page each time. That causes page splits, poor cache locality and a much larger working set, and on a write-heavy table the throughput difference is substantial. UUIDv7 is time-ordered and keeps insert locality while remaining globally unique, so it is the right choice when UUIDs are genuinely needed.

Often the better answer is both: a bigint primary key for internal joins and foreign keys, plus a separate indexed public_id UUID for external references. Internal work stays compact and sequential while external identifiers stay opaque, and you are not paying the random-insert cost on every index in the schema.

Senior: Which schema decisions are expensive to reverse, and how does that change your approach?

The ones that require rewriting existing data or that other systems have already come to depend on. Changing a money column from float to numeric means a table rewrite plus reconciling values that have already drifted. Changing timestamp to timestamptz requires deciding retroactively what zone the existing values were in, which is frequently unanswerable. Adding NOT NULL to a column that accumulated nulls means inventing data. Switching primary key types means rewriting every referencing table. And splitting a god table after five services query it directly is a coordination project rather than a migration.

So I spend design effort asymmetrically. Types, keys, and NOT NULL get argued about properly up front because they are effectively permanent. Indexes, denormalisations, materialised views and partitioning strategy I treat as reversible and defer until there is evidence — adding an index later is routine, and adding one prematurely just costs write throughput for no measured gain.

The other thing that changes is how I add constraints to a live table. NOT VALID followed by a separate VALIDATE lets a check constraint go on instantly and be verified under a weak lock, so writes continue. And any schema change on a large table needs a lock_timeout, because a migration that waits for a lock also blocks every query queuing behind it — which is the specific mechanism by which one ALTER TABLE takes a service down.

The habit that matters most is making invalid states unrepresentable while it is still cheap. A CHECK constraint that a paid order has a paid_at, or an exclusion constraint that price periods cannot overlap, costs nothing at design time and removes a category of bug that application code would otherwise have to prevent everywhere, forever.

Senior: A team wants to store product attributes in an EAV table for flexibility. What do you say?

That the flexibility is real and the price is higher than it looks. In an entity-attribute-value table every value is text, so there are no types — no range queries on numeric attributes, no date arithmetic, no arithmetic at all without casting that the planner cannot use an index for. There are no constraints, so nothing can be required or bounded. Reading one product with twenty attributes becomes a twenty-way self-join or a pivot. And the planner's statistics become meaningless, because from its perspective the table is one enormous heap of unrelated rows, so cardinality estimates go wrong and plans degrade unpredictably as it grows.

The usual motivation is that attributes differ per category and nobody wants to add columns. JSONB handles that directly: it keeps the flexibility, preserves types within the document, supports containment and path queries, and can be indexed with GIN so filters are fast. It is the right tool for genuinely sparse, user-defined, or third-party-supplied attributes.

But I would also question the premise, because the set of attributes is usually smaller and more stable than it feels during design. If every product has a price, a weight and a status, those are columns — with types, constraints and indexes — and the genuinely variable remainder goes in a JSONB column beside them. That hybrid is almost always the right shape: relational for what you query, constrain and join on, JSONB for the long tail. What I would not accept is EAV chosen to avoid writing a migration, because migrations are a solved problem and the query cost of EAV is paid on every read forever.

Solution 
-- ✗ BEFORE
orders(id, user_name, user_email, user_city, user_state,
       product1, product1_qty, product2, product2_qty, product3, ...)

-- ── STEP 1 → 1NF: no repeating groups ───────────────────────────────────
-- product1/2/3 caps orders at three items and makes "how many of product
-- X did we sell?" require checking three columns. Move to a child table:
orders(id, user_name, user_email, user_city, user_state)
order_items(order_id, product_id, quantity)
-- FIXES: an arbitrary limit, and unqueryable data.

-- ── STEP 2 → 2NF: no partial dependency on a composite key ──────────────
-- If order_items were (order_id, product_id, quantity, product_name),
-- product_name depends on product_id ALONE — part of the key, not all of
-- it. Renaming a product means updating every line item that ever
-- referenced it.
order_items(order_id, product_id, quantity, unit_price)
products(id, name, current_price)
-- FIXES: the same product name duplicated across every order.
-- ⚠ unit_price STAYS on the line item — see below.

-- ── STEP 3 → 3NF: no transitive dependency ──────────────────────────────
-- user_email depends on the USER, not on the ORDER. A user changing
-- email means updating every order row they have — miss one and the
-- database holds two contradictory answers.
users(id, name, email, city_id)
orders(id, user_id, created_at)
-- FIXES the three anomalies:
--   UPDATE  change an email in one place
--   INSERT  a user can exist before their first order
--   DELETE  removing the last order no longer destroys the email

-- city → state is also transitive:
cities(id, name, state_id)     -- if you actually query by state.
-- ⚠ Judgement: a cities/states lookup is often over-engineering for an
--   address field nobody aggregates on. Normalise where the data is
--   QUERIED, not everywhere it is theoretically possible.

-- ── WHAT LOOKS LIKE A VIOLATION AND IS NOT ──────────────────────────────
order_items(order_id, product_id, quantity, unit_price)
--                                          ^^^^^^^^^^
-- This is NOT redundant with products.current_price. The price AT
-- PURCHASE is a different fact from the price today. Joining to products
-- for it means every historical order silently changes when someone runs
-- a sale — and your revenue reports change retroactively.
--
-- THE TEST: may this value change independently of its source? If yes,
-- store it. The same applies to a shipping address on an order and a tax
-- rate on an invoice.
2 (easy): Fix the types and constraints in this table.
Solution 
-- ✗ BEFORE
CREATE TABLE orders (
  id           varchar(50),
  user_id      varchar(50),
  total        float,
  currency     varchar(10),
  status       varchar(255),
  discount_pct float,
  created_at   timestamp,
  shipped_at   timestamp
);

-- ✓ AFTER
CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users(id),
  total      numeric(12,2) NOT NULL CHECK (total >= 0),
  currency   char(3) NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
  status     text NOT NULL DEFAULT 'pending'
             CHECK (status IN ('pending','paid','shipped','cancelled')),
  discount_pct numeric(5,2) NOT NULL DEFAULT 0
             CHECK (discount_pct BETWEEN 0 AND 100),
  created_at timestamptz NOT NULL DEFAULT now(),
  shipped_at timestamptz,
  CHECK (shipped_at IS NULL OR shipped_at >= created_at),
  CHECK ((status = 'shipped') = (shipped_at IS NOT NULL))
);
CREATE INDEX ON orders (user_id);          -- NOT automatic for an FK

-- ── EVERY CHANGE, AND WHY ───────────────────────────────────────────────
-- varchar id → bigint     8 bytes vs ~50, and it cannot hold 'abc'.
--                         String ids also break index-ordered inserts.
-- float → numeric(12,2)   0.1 + 0.2 ≠ 0.3. Sums drift, and the audit
--                         fails months later over one cent nobody can
--                         trace. THE most expensive type mistake here.
-- currency added          There is almost always eventually a second
--                         currency, and retrofitting it is a migration.
-- varchar(255) → text     255 is an inherited MySQL habit with no meaning
--                         in Postgres. The CHECK is the real constraint.
-- timestamp → timestamptz Naive timestamps are ambiguous across DST and
--                         mean different things to different readers.
-- NOT NULL everywhere     Every nullable column is a branch every future
--                         query must remember — and forgetting it drops
--                         rows silently rather than raising.
-- FK on user_id           The database now guarantees the user exists.
--                         Application checks race and get bypassed.
-- cross-column CHECK      Makes "shipped with no shipped_at" — and its
--                         mirror — UNREPRESENTABLE rather than merely
--                         discouraged.

-- ── ADDING THESE TO A LIVE TABLE ────────────────────────────────────────
ALTER TABLE orders ADD CONSTRAINT total_positive
  CHECK (total >= 0) NOT VALID;             -- instant, no scan
ALTER TABLE orders VALIDATE CONSTRAINT total_positive;
-- VALIDATE scans but takes only SHARE UPDATE EXCLUSIVE, so writes
-- continue. A direct ADD CONSTRAINT locks the table for the whole scan.
3 (medium): Design the schema for a course platform: students, courses, enrolments, lessons, progress.
Solution 
CREATE TABLE students (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email citext NOT NULL UNIQUE,              -- case-insensitive, no
  name text NOT NULL CHECK (length(name) BETWEEN 1 AND 200),
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE courses (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slug text NOT NULL UNIQUE,                 -- natural key, UNIQUE not PK
  title text NOT NULL,
  price numeric(12,2) NOT NULL CHECK (price >= 0),
  published_at timestamptz
);

-- ── MANY-TO-MANY, WITH RELATIONSHIP ATTRIBUTES ──────────────────────────
CREATE TABLE enrollments (
  student_id bigint NOT NULL REFERENCES students(id) ON DELETE CASCADE,
  course_id  bigint NOT NULL REFERENCES courses(id)  ON DELETE RESTRICT,
  enrolled_at timestamptz NOT NULL DEFAULT now(),
  price_paid numeric(12,2) NOT NULL,         -- ← SNAPSHOT, not a join to
  completed_at timestamptz,                  --   courses.price
  PRIMARY KEY (student_id, course_id)        -- identity AND prevents
);                                           -- double enrolment
CREATE INDEX ON enrollments (course_id);     -- the PK leads with
                                             -- student_id; course
                                             -- queries need their own

-- CASCADE on student (deleting a student removes their enrolments)
-- RESTRICT on course (refuse to delete a course people are enrolled in)
-- These are business rules. State them deliberately, per FK.

CREATE TABLE lessons (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  course_id bigint NOT NULL REFERENCES courses(id) ON DELETE CASCADE,
  position int NOT NULL,
  title text NOT NULL,
  UNIQUE (course_id, position)               -- no two lessons at #3
);
CREATE INDEX ON lessons (course_id);

CREATE TABLE lesson_progress (
  student_id bigint NOT NULL,
  lesson_id  bigint NOT NULL REFERENCES lessons(id) ON DELETE CASCADE,
  course_id  bigint NOT NULL,
  started_at   timestamptz NOT NULL DEFAULT now(),
  completed_at timestamptz,
  PRIMARY KEY (student_id, lesson_id),
  FOREIGN KEY (student_id, course_id)
    REFERENCES enrollments(student_id, course_id) ON DELETE CASCADE,
  CHECK (completed_at IS NULL OR completed_at >= started_at)
);
-- ⚠ THE INTERESTING BIT: the composite FK to enrollments makes it
--   IMPOSSIBLE to record progress for a course the student is not
--   enrolled in. course_id is carried here purely to enable that
--   constraint — a deliberate, useful redundancy that BUYS integrity
--   rather than costing it.
--   (Add a CHECK or trigger to ensure lesson_id really belongs to
--    course_id, or the pair could disagree.)

-- ── THE QUESTIONS THIS DESIGN ANSWERS ───────────────────────────────────
-- Can a student enrol twice?          No — composite PK.
-- What did they pay in March?         price_paid, unaffected by later
--                                     price changes.
-- Progress without enrolment?         Impossible — composite FK.
-- Two lessons at position 3?          Impossible — UNIQUE.
-- Delete a course with students?      Refused — RESTRICT.

-- ── WHAT I DELIBERATELY DID NOT DO ──────────────────────────────────────
-- No completion_percent column on enrollments. It is derivable, and a
-- cached copy needs a trigger, a lock on the parent per progress write,
-- and a drift check. Compute it until a measurement says otherwise:
SELECT count(*) FILTER (WHERE completed_at IS NOT NULL)::numeric
       / nullif(count(*), 0) FROM lesson_progress WHERE ...;
4 (medium): A cached order_count on users has drifted. Diagnose and fix properly.
Solution 
-- ── STEP 1: MEASURE THE DRIFT ───────────────────────────────────────────
SELECT u.id, u.order_count AS cached,
       (SELECT count(*) FROM orders o WHERE o.user_id = u.id) AS actual
FROM users u
WHERE u.order_count <> (SELECT count(*) FROM orders o WHERE o.user_id=u.id);
-- 3,412 users wrong. Some high, some low.

-- ── STEP 2: WHY IT DRIFTED ──────────────────────────────────────────────
-- The counter was maintained in APPLICATION CODE. Everything that writes
-- outside that code path silently diverges:
--   * a data-fix migration that inserted orders directly
--   * a bulk CSV import
--   * an engineer running DELETE in psql
--   * a second service writing to the same database
--   * a transaction that inserted the order and then FAILED after
--     incrementing (or vice versa — two statements, not atomic)
-- Application-maintained derived data is not a bug in the code. It is a
-- bug in WHERE the rule lives.

-- ── STEP 3: BACKFILL ────────────────────────────────────────────────────
UPDATE users u SET order_count = c.n
FROM (SELECT user_id, count(*) n FROM orders GROUP BY user_id) c
WHERE c.user_id = u.id AND u.order_count <> c.n;
UPDATE users SET order_count = 0
WHERE NOT EXISTS (SELECT 1 FROM orders WHERE user_id = users.id)
  AND order_count <> 0;                   -- ← users with ZERO orders are
                                          --   missing from the join

-- ── STEP 4: MOVE THE RULE INTO THE DATABASE ─────────────────────────────
CREATE FUNCTION sync_order_count() RETURNS trigger AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    UPDATE users SET order_count = order_count + 1 WHERE id = NEW.user_id;
  ELSIF TG_OP = 'DELETE' THEN
    UPDATE users SET order_count = order_count - 1 WHERE id = OLD.user_id;
  ELSIF TG_OP = 'UPDATE' AND NEW.user_id IS DISTINCT FROM OLD.user_id THEN
    UPDATE users SET order_count = order_count - 1 WHERE id = OLD.user_id;
    UPDATE users SET order_count = order_count + 1 WHERE id = NEW.user_id;
  END IF;                                 -- ← the UPDATE case is what
  RETURN NULL;                            --   hand-written code forgets
END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_order_count
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW EXECUTE FUNCTION sync_order_count();

-- ── STEP 5: THE COST YOU JUST BOUGHT ────────────────────────────────────
-- Every order insert now takes a ROW LOCK on the user. Two concurrent
-- orders for the same user SERIALISE. For a marketplace seller with
-- 10k orders/hour that is a write hotspot and a deadlock source
-- (insert order → lock user, in a transaction that also touches users
-- in the other order).
-- Denormalisation is never free. It moves cost from read to write.

-- ── ✓ THE ALTERNATIVES I WOULD CONSIDER FIRST ───────────────────────────
-- a) Just count it. With an index on orders(user_id), count(*) for one
--    user is an index-only scan — often microseconds. MEASURE before
--    caching.
CREATE INDEX ON orders (user_id);

-- b) A materialised view, if it feeds a dashboard rather than a profile
CREATE MATERIALIZED VIEW user_order_counts AS
SELECT user_id, count(*) AS n FROM orders GROUP BY user_id;
CREATE UNIQUE INDEX ON user_order_counts (user_id);
REFRESH MATERIALIZED VIEW CONCURRENTLY user_order_counts;
--    Staleness is EXPLICIT and bounded, and there is zero per-write cost.
--    The most honest denormalisation.

-- ── STEP 6: WHATEVER YOU CHOOSE, MONITOR THE DRIFT ──────────────────────
-- Schedule the query from step 1 and alert if it returns rows. Every
-- sync mechanism eventually fails, and silent divergence is worse than
-- a slow query — it produces confidently wrong numbers.
5 (hard): A product catalogue uses EAV. Migrate it, and justify the target design.
Solution 
-- ✗ THE EAV SCHEMA
CREATE TABLE product_attributes (
  product_id bigint, attr_name text, attr_value text);
-- ('colour','red') ('weight_kg','2.5') ('in_stock','true')

-- ── WHAT IT COSTS ───────────────────────────────────────────────────────
-- 1. NO TYPES. weight_kg is text, so:
SELECT * FROM product_attributes
WHERE attr_name='weight_kg' AND attr_value::numeric < 5;
--    A cast per row, no usable index, and it THROWS if any row contains
--    'heavy'. Nothing prevents that row existing.
-- 2. NO CONSTRAINTS. Nothing can be NOT NULL, bounded, or a foreign key.
-- 3. READING ONE PRODUCT = a self-join per attribute:
SELECT p.id, c.attr_value AS colour, w.attr_value AS weight
FROM products p
LEFT JOIN product_attributes c ON c.product_id=p.id AND c.attr_name='colour'
LEFT JOIN product_attributes w ON w.product_id=p.id AND w.attr_name='weight_kg';
--    20 attributes = a 20-way join.
-- 4. NO USEFUL STATISTICS. The planner sees one enormous heap; estimates
--    are meaningless and plans degrade unpredictably as it grows.

-- ── ✓ THE TARGET: HYBRID ────────────────────────────────────────────────
ALTER TABLE products
  ADD COLUMN weight_kg numeric(8,3) CHECK (weight_kg > 0),
  ADD COLUMN colour    text,
  ADD COLUMN in_stock  boolean NOT NULL DEFAULT false,
  ADD COLUMN attrs     jsonb NOT NULL DEFAULT '{}';
CREATE INDEX ON products USING gin (attrs);
CREATE INDEX ON products (weight_kg);

-- COLUMNS for what you FILTER, SORT, CONSTRAIN or JOIN on.
-- JSONB for the genuinely sparse long tail.
SELECT * FROM products WHERE weight_kg < 5;                -- indexed range
SELECT * FROM products WHERE attrs @> '{"material":"oak"}'; -- GIN index

-- ── WHY NOT PURE JSONB? ─────────────────────────────────────────────────
-- It keeps types within the document and is properly indexable, so it is
-- a huge improvement on EAV. But a JSONB field cannot have a FOREIGN
-- KEY, a UNIQUE constraint, or a NOT NULL, and typos are invisible:
-- {"color":"red"} and {"colour":"red"} coexist happily forever.
-- So: relational for the stable core, JSONB for the variable remainder.

-- ── THE MIGRATION (expand → backfill → contract) ────────────────────────
-- 1. add the columns (nullable, no default → instant)
-- 2. dual-write: application writes BOTH old and new; a trigger covers
--    anything writing only the old form
-- 3. backfill in chunks, resumable:
UPDATE products p SET
  weight_kg = (SELECT attr_value::numeric FROM product_attributes
               WHERE product_id=p.id AND attr_name='weight_kg'),
  attrs = COALESCE((SELECT jsonb_object_agg(attr_name, attr_value)
                    FROM product_attributes
                    WHERE product_id=p.id
                      AND attr_name NOT IN ('weight_kg','colour','in_stock')
                   ), '{}')
WHERE p.id BETWEEN :lo AND :lo+9999;
-- ⚠ EXPECT DIRTY DATA. Ten years of untyped text WILL contain
--   'approx 3kg', '', 'N/A' and '3,5'. Quarantine failures rather than
--   letting the job die at 80%:
SELECT product_id, attr_value FROM product_attributes
WHERE attr_name='weight_kg' AND attr_value !~ '^[0-9]+(\.[0-9]+)?$';
-- 4. verify, then switch reads
-- 5. stop writing the old table
-- 6. drop it — one release later, because rolling deploys run old and
--    new code simultaneously

-- ── WHAT I WOULD SAY IN THE DESIGN REVIEW ───────────────────────────────
-- The motivation for EAV is always "attributes vary per category and we
-- don't want a migration for each". But the set of attributes is nearly
-- always smaller and more stable than it feels at design time, and
-- migrations are a solved problem. EAV pays its cost on EVERY READ,
-- FOREVER, to avoid a cost you pay a few times a year.
6 (hard): Design a schema for a booking system where double-booking must be impossible.
Solution 
-- REQUIREMENT: rooms booked for time ranges. Two bookings for the same
-- room must never overlap — under concurrency, forever, regardless of
-- application bugs.

-- ── ✗ WHAT NEARLY EVERYONE WRITES FIRST ─────────────────────────────────
SELECT count(*) FROM bookings
WHERE room_id = :r AND starts_at < :end AND ends_at > :start;
-- if 0 → INSERT
--
-- A CHECK-THEN-ACT RACE. Two requests both see 0, both insert, the room
-- is double-booked. It is not rare under load — it is the default
-- outcome, and it is exactly the class of bug the database exists to
-- prevent.

-- ── ✓ MAKE IT STRUCTURALLY IMPOSSIBLE ───────────────────────────────────
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE bookings (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id bigint NOT NULL REFERENCES rooms(id),
  guest_id bigint NOT NULL REFERENCES guests(id),
  during  tstzrange NOT NULL,
  status  text NOT NULL DEFAULT 'confirmed'
          CHECK (status IN ('confirmed','cancelled')),
  created_at timestamptz NOT NULL DEFAULT now(),

  CHECK (NOT isempty(during)),
  CHECK (lower(during) IS NOT NULL AND upper(during) IS NOT NULL),

  EXCLUDE USING gist (
    room_id WITH =,
    during  WITH &&                      -- && = "overlaps"
  ) WHERE (status = 'confirmed')          -- cancelled bookings may overlap
);
CREATE INDEX ON bookings (guest_id);
CREATE INDEX ON bookings USING gist (during);

-- The EXCLUSION CONSTRAINT is the whole design. It says: no two rows may
-- share a room_id AND have overlapping `during` ranges. The database
-- enforces it with a lock, so the concurrent insert simply FAILS:
INSERT INTO bookings ... ;
-- ERROR: conflicting key value violates exclusion constraint
-- The application catches that and reports "no longer available".
-- No SELECT-then-INSERT, no advisory lock, no SERIALIZABLE retry loop.

-- ── WHY A RANGE TYPE, NOT TWO COLUMNS ───────────────────────────────────
starts_at timestamptz, ends_at timestamptz
-- Overlap logic (a.start < b.end AND a.end > b.start) is easy to get
-- subtly wrong, and there is no operator for a constraint to use.
tstzrange(:start, :end, '[)')     -- HALF-OPEN: a booking ending at 11:00
                                  -- and one starting at 11:00 do NOT
                                  -- overlap. The default '[)' is exactly
                                  -- the semantics you want, and it
                                  -- removes an entire class of
                                  -- off-by-one bug.

-- ── THE QUERIES IT ENABLES ──────────────────────────────────────────────
SELECT * FROM bookings                                   -- room's day
WHERE room_id=:r AND during && tstzrange(:d, :d + 1);
SELECT r.* FROM rooms r WHERE NOT EXISTS (               -- free rooms
  SELECT 1 FROM bookings b
  WHERE b.room_id=r.id AND b.status='confirmed'
    AND b.during && tstzrange(:start, :end));
-- The GiST index serves both.

-- ── WHAT THIS DOES NOT SOLVE ────────────────────────────────────────────
-- 1. FAIRNESS. Under contention, whoever commits first wins and the
--    other gets an error. That is correct, but the UX needs a friendly
--    message and ideally a suggested alternative slot.
-- 2. HOLDS. "Reserved for 10 minutes while you pay" is a separate state
--    with an expiry, not a confirmed booking:
--      status IN ('held','confirmed','cancelled') and the exclusion
--      constraint covering held AND confirmed, plus a job that expires
--      stale holds.
-- 3. MULTI-RESOURCE atomicity. Booking a room AND equipment together
--    needs both inserts in ONE transaction — either both succeed or
--    neither does. The exclusion constraints then compose for free.
-- 4. CANCELLED overlaps. The partial WHERE clause is deliberate:
--    without it, a cancelled booking would block the slot forever.

-- ── THE PRINCIPLE ───────────────────────────────────────────────────────
-- Any rule enforced only in application code is a rule that races, gets
-- bypassed by a migration, and is one refactor from being lost. Push
-- invariants into the schema where they hold unconditionally — that is
-- what a database is FOR.

🎯 Key Takeaways

  • Normalisation makes contradictions unrepresentable; the normal forms are named after the anomalies they prevent.
  • Default to a surrogate bigint key with a UNIQUE constraint on the natural key — real-world identifiers change.
  • Random UUIDv4 primary keys scatter B-tree inserts; use UUIDv7, or a bigint with a separate public id.
  • Foreign keys give a guarantee application code cannot — and Postgres does not index the child column for you.
  • Snapshotting a historical value like unit_price is correct modelling, not denormalisation.
  • Denormalise only after measuring, and decide the sync mechanism — trigger, generated column, materialised view — before adding the column.
  • Every denormalisation needs a drift check, because silent divergence is worse than a slow query.
  • Types and NOT NULL are effectively permanent; indexes and denormalisations are reversible — spend design effort accordingly.
  • Use CHECK, partial UNIQUE and EXCLUDE constraints to make invalid states impossible rather than merely discouraged.
  • EAV and polymorphic associations buy flexibility by discarding types, constraints and foreign keys — JSONB beside real columns is almost always better.
