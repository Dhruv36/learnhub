Async Patterns & Pitfalls Async & Concurrency

What you'll master: the production patterns that turn "I know await" into "I can ship async systems": bounded concurrency (SemaphoreSlim, Parallel.ForEachAsync); async streams (IAsyncEnumerable); producer/consumer pipelines with Channel<T>; TaskCompletionSource for bridging callback APIs; async-safe lazy initialization; retry with backoff; and the pitfalls that fill incident reports — sync-over-async under load, lock + await, async in constructors. Prerequisite: async/await & Tasks — this lesson assumes the state-machine mental model and builds the patterns layer on it.

Part 1 — Bounded Concurrency: The Throttle Every Fan-Out Needs

// Unbounded fan-out is a self-inflicted DoS:
await Task.WhenAll(urls.Select(FetchAsync));       // 10,000 urls = 10,000 concurrent
// requests → socket exhaustion, rate-limit bans, downstream timeouts. ALWAYS bound it.

// TOOL 1 — Parallel.ForEachAsync (.NET 6+): the go-to for "do this async thing N-wide":
await Parallel.ForEachAsync(urls,
    new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
    async (url, token) =>
    {
        var data = await FetchAsync(url, token);
        await SaveAsync(data, token);
    });
// 8 in flight at any moment; new items start as slots free; cancellation flows in.

// TOOL 2 — SemaphoreSlim: the manual throttle, when you need results back or the
// work isn't a clean foreach. A semaphore = a counter of "permits":
using var gate = new SemaphoreSlim(8);             // 8 concurrent permits
var tasks = urls.Select(async url =>
{
    await gate.WaitAsync(ct);                      // take a permit (async — no thread blocked)
    try     { return await FetchAsync(url, ct); }
    finally { gate.Release(); }                    // ALWAYS release — finally, not after
});
var results = await Task.WhenAll(tasks);           // results in input order

// How to pick the limit: it protects the DOWNSTREAM, so match its capacity —
// DB pool size, API rate limit, disk throughput. Make it config, load-test it.
// ponytail: fixed limit; adaptive throttling (react to 429/latency) if the target varies.
SemaphoreSlim is also the async lock. C#'s lock statement cannot contain await (the compiler refuses — the resuming thread may differ from the one that took the monitor). The idiom for "one at a time, but the work is async" is a semaphore of 1: await _gate.WaitAsync(); try { await ... } finally { _gate.Release(); }. .NET 9 added System.Threading.Lock, but for awaitable critical sections, SemaphoreSlim(1,1) remains the standard answer — and a favorite interview question.

Part 2 — Async Streams: IAsyncEnumerable<T>

// IEnumerable pulls values synchronously; Task<List<T>> waits for ALL before yielding ANY.
// IAsyncEnumerable<T> streams items AS THEY ARRIVE, each awaited:
public async IAsyncEnumerable<Order> ReadOrdersAsync(
    [EnumeratorCancellation] CancellationToken ct = default)   // token wires into await foreach
{
    string? line;
    using var reader = File.OpenText("orders.jsonl");
    while ((line = await reader.ReadLineAsync(ct)) is not null)   // await INSIDE the iterator
        yield return JsonSerializer.Deserialize<Order>(line)!;    // yield per item
}

// Consuming — await foreach:
await foreach (var order in ReadOrdersAsync(ct))
    await ProcessAsync(order);
// Memory: ONE order at a time — a 10GB file streams in constant memory, vs
// Task<List<Order>> materializing everything. First result arrives immediately, not
// after the whole read. EF Core (AsAsyncEnumerable), gRPC streaming, and
// System.Text.Json (DeserializeAsyncEnumerable) all speak this shape.

// WithCancellation attaches a token at the consumption site:
await foreach (var o in source.WithCancellation(ct)) { ... }

Part 3 — Channel<T>: Producer/Consumer Done Right

// A Channel is an async-native queue: producers write, consumers read, backpressure
// built in. It replaces hand-rolled Queue+lock+event contraptions.
var channel = Channel.CreateBounded<Job>(new BoundedChannelOptions(100)
{
    FullMode = BoundedChannelFullMode.Wait      // producer AWAITS when full = BACKPRESSURE
});                                             // (DropOldest/DropWrite for lossy telemetry)

// PRODUCER(S) — e.g. a web endpoint enqueueing work:
public async Task EnqueueAsync(Job job, CancellationToken ct)
    => await channel.Writer.WriteAsync(job, ct);   // waits if the queue is full

// CONSUMER(S) — N background workers (see di-hosting.html for BackgroundService):
async Task ConsumeAsync(CancellationToken ct)
{
    await foreach (var job in channel.Reader.ReadAllAsync(ct))   // IAsyncEnumerable!
        await HandleAsync(job, ct);
}
var workers = Enumerable.Range(0, 4).Select(_ => ConsumeAsync(ct)).ToArray();

// SHUTDOWN protocol:
channel.Writer.Complete();          // no more writes
await Task.WhenAll(workers);        // ReadAllAsync ends when channel drains → workers exit

// Why BOUNDED matters: an unbounded channel with a slow consumer grows until OOM —
// the queue hides the overload instead of surfacing it. Bounded + Wait pushes the
// slowdown back to producers (backpressure), which is what you want: fail/slow at the
// edge, not explode in the middle. Same principle as message-broker queue limits.

Part 4 — TaskCompletionSource: Bridging Callbacks Into Tasks

// Old APIs signal completion via callbacks/events. TaskCompletionSource<T> (TCS)
// manufactures a Task YOU complete manually — the adapter between worlds:
public Task<string> ScanAsync(Scanner scanner, CancellationToken ct = default)
{
    var tcs = new TaskCompletionSource<string>(
        TaskCreationOptions.RunContinuationsAsynchronously);   // ALWAYS pass this (below)

    scanner.ScanCompleted += (s, e) => tcs.TrySetResult(e.Barcode);   // callback → result
    scanner.ScanFailed    += (s, e) => tcs.TrySetException(e.Error);  // callback → exception
    ct.Register(() => tcs.TrySetCanceled(ct));                        // cancellation → canceled

    scanner.StartScan();
    return tcs.Task;                       // awaitable handle over the event-based API
}
var barcode = await ScanAsync(scanner, ct);   // caller lives in clean async land

// Notes that separate senior answers:
// - TrySet* (not Set*): events may fire twice/race — Set* throws on second call.
// - RunContinuationsAsynchronously: without it, awaiting continuations run INLINE on
//   the thread calling TrySetResult — a library thread suddenly executes your app's
//   continuation chain → surprise deadlocks/stalls. This flag is essentially mandatory.
// - This is exactly how the runtime builds Task.Delay, WhenAll, and every I/O task.

Part 5 — Initialization, Caching & Retry Patterns

// ASYNC LAZY INIT — "load once, everyone awaits the same load":
// Lazy<Task<T>> = thread-safe once-only START of the task; all callers share it.
private readonly Lazy<Task<Settings>> _settings =
    new(() => LoadSettingsAsync(), LazyThreadSafetyMode.ExecutionAndPublication);
public Task<Settings> GetSettingsAsync() => _settings.Value;
// First caller triggers LoadSettingsAsync; concurrent callers await the SAME task;
// later callers get the completed task (zero cost). Caveat: a FAULTED task is cached
// too — wrap with retry-on-fault if the load can transiently fail.

// This also fixes "async constructor" (constructors can't await):
// ❌ public Service() { _data = LoadAsync().Result; }        // sync-over-async in ctor!
// ✅ ctor stores the Lazy; first use awaits. Or a static factory:
public static async Task<Service> CreateAsync(CancellationToken ct)
{
    var data = await LoadAsync(ct);
    return new Service(data);              // private ctor takes the loaded data
}

// RETRY WITH EXPONENTIAL BACKOFF + JITTER (transient faults only — see
// exceptions-nullability.html for the filter discipline):
public static async Task<T> RetryAsync<T>(Func<CancellationToken, Task<T>> op,
    int attempts = 4, CancellationToken ct = default)
{
    for (int i = 1; ; i++)
    {
        try { return await op(ct); }
        catch (Exception ex) when (IsTransient(ex) && i < attempts)
        {
            var delay = TimeSpan.FromMilliseconds(
                100 * Math.Pow(2, i)                       // 200, 400, 800ms...
                + Random.Shared.Next(0, 100));             // JITTER: desynchronize retriers
            await Task.Delay(delay, ct);
        }
    }
}
// Backoff gives the dependency room to recover; jitter prevents every client
// retrying in lockstep (thundering herd). In real services use Polly (retry +
// circuit breaker + timeout policies, composable) — but know what it does inside.
// ponytail: no circuit breaker here; add one (Polly) when a dependency can brown-out.

Part 6 — The Pitfalls That Cause Incidents

// PITFALL 1 — sync-over-async UNDER LOAD (thread-pool starvation):
// .Result in a request path doesn't just risk deadlock — each call PARKS a pool thread.
// Under burst traffic: all threads blocked → continuations can't run → the tasks being
// waited on can't complete → timeouts cascade while CPU sits at 5%. The signature
// symptom: low CPU, high latency, ThreadPool queue length climbing. Fix: async end-to-end.

// PITFALL 2 — lock + await:
lock (_sync) { await SaveAsync(); }        // ❌ compile error — and for good reason:
// the continuation may resume on a DIFFERENT thread, which can't release a Monitor
// owned by the original. Use SemaphoreSlim(1,1) (Part 1) for async critical sections.
// Never "work around" with Monitor.Enter/Exit split across an await.

// PITFALL 3 — async work in a request outliving the request:
_ = Task.Run(() => SendEmailAsync(user));  // ❌ in ASP.NET: the DI scope (and its
// DbContext etc.) is disposed when the response returns → ObjectDisposedException at
// random. Real fix: enqueue to a Channel consumed by a BackgroundService with its own
// scope (Part 3 + di-hosting.html) — that's the minimal correct "fire and forget".

// PITFALL 4 — Task.Delay for periodic work drifts and overlaps:
while (true) { await DoWorkAsync(); await Task.Delay(60_000); }   // period = 60s + work time
// ✅ PeriodicTimer (.NET 6+): fixed cadence, no overlap, clean cancellation:
using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));
while (await timer.WaitForNextTickAsync(ct))
    await DoWorkAsync(ct);

// PITFALL 5 — awaiting inside foreach when order doesn't matter (revisited):
// sequential-await loops are the #1 latency bug; WhenAll/ForEachAsync (Part 1) —
// but remember the opposite trap: DbContext is NOT thread-safe; EF work must stay
// sequential per context (efcore.html).

Interview Questions

Q1 (Beginner): Why is firing 5,000 HTTP requests with one Task.WhenAll a bad idea, and what do you do instead?

All 5,000 start immediately and run concurrently: you exhaust outbound sockets/ports, trip the target's rate limits, saturate your bandwidth, and induce timeouts that look like downstream failures. Instead, bound the concurrency: Parallel.ForEachAsync with MaxDegreeOfParallelism set to what the downstream can handle, or gate each task with a SemaphoreSlim when you need per-item results. The limit protects the dependency, so size it from the dependency's capacity (connection pool, documented rate limit) and make it configurable.

Q2 (Beginner): What is IAsyncEnumerable<T> and when is it better than Task<List<T>>?

It's the async version of a sequence: items are produced one at a time, each potentially awaited, consumed with await foreach. Prefer it when results arrive incrementally and you don't need them all at once — reading large files/DB result sets, paging an API, gRPC streams. Benefits: constant memory (one item in flight instead of the whole list) and immediate first results (processing starts before the source finishes). Task<List<T>> buffers everything, so memory scales with result size and nothing is available until the end.

Q3 (Mid): How do you protect a critical section that contains an await? Why won't lock work?

lock compiles to Monitor.Enter/Exit, which is thread-affine — the thread that acquires must release. An await may resume on a different thread, which couldn't release the monitor, so C# makes await inside lock a compile error. The idiom is SemaphoreSlim(1,1): await _gate.WaitAsync(); try { /* async work */ } finally { _gate.Release(); }. WaitAsync queues waiters without blocking threads, and a semaphore has no thread affinity — any thread may release. The finally is essential: a leaked permit permanently shrinks the gate.

Q4 (Mid): What is TaskCompletionSource for? Name two details that make a TCS-based adapter production-grade.

It creates a Task whose completion you control via SetResult/SetException/SetCanceled — the bridge that wraps callback- or event-based APIs (device SDKs, message replies, old Begin/End patterns) into awaitable methods; it's also how the runtime itself constructs I/O tasks. Production details: (1) construct with TaskCreationOptions.RunContinuationsAsynchronously, otherwise awaiters' continuations execute synchronously on whatever thread calls SetResult — hijacking a library/timer thread and inviting deadlocks; (2) use TrySet* variants since callbacks can race or fire twice; (3) register cancellation (ct.Register(() => tcs.TrySetCanceled(ct))) and unhook event handlers to avoid leaks.

Q5 (Senior): Design a background work queue inside a web app: requests enqueue jobs, workers process them, the app must not lose jobs on overload or use disposed services. What do you build?

A bounded Channel<Job> registered as a singleton: endpoints WriteAsync (which awaits when full — backpressure instead of unbounded memory growth; or return 429/503 if waiting is unacceptable). Consumers are a BackgroundService (hosted service) running N workers over Reader.ReadAllAsync; each job execution creates its own DI scope (IServiceScopeFactory.CreateScope) so it never touches request-scoped services that die with the response. Shutdown: StopAsync completes the writer and awaits drain within the host's shutdown timeout. Failures: per-job try/catch, retry transient errors with backoff, dead-letter poison jobs. Honest caveat: an in-process queue loses jobs if the process dies — if durability matters, the same design moves to a broker (Redis/RabbitMQ/Azure Queue) with the BackgroundService as consumer.

Q6 (Senior): Production symptom: latency spikes to seconds, CPU is at 10%, thread count climbing. Diagnose the likely async pathology and the fix.

Classic thread-pool starvation from sync-over-async. Blocking calls (.Result, .Wait(), GetAwaiter().GetResult(), or sync DB/HTTP calls) in request paths park pool threads; under load all threads end up blocked, so queued continuations — including the completions of the very tasks being waited on — can't run. The pool injects new threads only gradually (hence climbing thread count), latency soars while CPU idles. Confirm via EventCounters (ThreadPool Queue Length growing, thread count rising) or a dump showing pool threads in Monitor.Wait/Task.Wait. Fix: remove the blocking — async end-to-end on hot paths (controllers, middleware, repositories); interim mitigation is ThreadPool.SetMinThreads, but that's a bandage, not the cure.

🏋️ Graded Exercises

1 (Easy): Download 50 URLs, at most 5 concurrently, with results collected — using SemaphoreSlim.
Solution
using var gate = new SemaphoreSlim(5);
var tasks = urls.Select(async url =>
{
    await gate.WaitAsync();
    try     { return await http.GetStringAsync(url); }
    finally { gate.Release(); }                    // finally — permits never leak
});
string[] pages = await Task.WhenAll(tasks);        // input order preserved
// All 50 tasks exist immediately, but only 5 hold permits at once — the other
// 45 are queued INSIDE WaitAsync without blocking any thread.
2 (Easy): Write an async stream CountdownAsync(int from) yielding one number per second, and consume it with await foreach, stopping cleanly on a token.
Solution
async IAsyncEnumerable<int> CountdownAsync(int from,
    [EnumeratorCancellation] CancellationToken ct = default)
{
    for (int i = from; i >= 0; i--)
    {
        await Task.Delay(1000, ct);     // token flows into the delay
        yield return i;
    }
}

using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
try
{
    await foreach (var n in CountdownAsync(10).WithCancellation(cts.Token))
        Console.Write($"{n} ");         // 9 8 7 6 5 — then cancelled
}
catch (OperationCanceledException) { Console.Write("stopped"); }
// [EnumeratorCancellation] is what connects WithCancellation's token to the
// iterator's ct parameter — without it the token silently doesn't flow.
3 (Medium): Build a log pipeline: many producers call Log(string); one consumer writes batches of up to 100 lines to disk every flush. Bursts must not allocate unboundedly — drop oldest entries under extreme pressure (it's telemetry).
Solution
var channel = Channel.CreateBounded<string>(new BoundedChannelOptions(10_000)
{
    FullMode = BoundedChannelFullMode.DropOldest,   // lossy is CORRECT for telemetry —
    SingleReader = true                             // losing a log line beats OOM/blocking
});

public void Log(string line) => channel.Writer.TryWrite(line);   // never blocks producers

async Task ConsumeAsync(CancellationToken ct)
{
    var batch = new List<string>(100);
    await foreach (var line in channel.Reader.ReadAllAsync(ct))
    {
        batch.Add(line);
        // drain whatever else is immediately available, up to batch size:
        while (batch.Count < 100 && channel.Reader.TryRead(out var more))
            batch.Add(more);
        await File.AppendAllLinesAsync("app.log", batch, ct);   // ONE write per batch
        batch.Clear();
    }
}
// Design notes: TryWrite keeps the hot path synchronous and allocation-free for
// producers; batching amortizes disk I/O; DropOldest chooses WHICH failure mode
// you get under pressure — an explicit decision, not an accident.
4 (Medium): Wrap this callback API into a task, production-grade: geo.LocationFound += handler; geo.LocationError += handler; geo.Start(); — with a 10-second timeout and no handler leaks.
Solution
public async Task<Location> GetLocationAsync(Geolocator geo, CancellationToken ct = default)
{
    var tcs = new TaskCompletionSource<Location>(
        TaskCreationOptions.RunContinuationsAsynchronously);

    void OnFound(object? s, LocationEventArgs e) => tcs.TrySetResult(e.Location);
    void OnError(object? s, ErrorEventArgs e)    => tcs.TrySetException(e.Error);

    geo.LocationFound += OnFound;                  // named handlers → removable
    geo.LocationError += OnError;
    using var reg = ct.Register(() => tcs.TrySetCanceled(ct));
    try
    {
        geo.Start();
        return await tcs.Task.WaitAsync(TimeSpan.FromSeconds(10), ct);  // timeout
    }
    finally
    {
        geo.LocationFound -= OnFound;              // ALWAYS unhook — success, timeout,
        geo.LocationError -= OnError;              // or cancel — no leaked subscriptions
        geo.Stop();                                // (delegates-events.html Part 5)
    }
}
// TrySet* everywhere (events can race the timeout), RunContinuationsAsynchronously
// so geo's callback thread never runs our caller's continuations inline.
5 (Hard): Spot the two production bugs and fix them: 
public class RatesService {
    private Task<Rates>? _rates;
    public Task<Rates> GetRatesAsync() {
        if (_rates == null) _rates = FetchRatesAsync();   // fetch takes ~2s, can fail
        return _rates;
    }
}
Solution
// BUG 1 — RACE: two concurrent first callers both see null and BOTH fetch
//         (check-then-act isn't atomic). Mostly wasteful; can double-hit a rate-limited API.
// BUG 2 — FAULT CACHING: if the first fetch throws, the FAULTED task is stored forever;
//         every future call re-throws the old error until process restart.
public class RatesService
{
    private readonly SemaphoreSlim _gate = new(1, 1);
    private Task<Rates>? _rates;

    public async Task<Rates> GetRatesAsync(CancellationToken ct = default)
    {
        var t = _rates;
        if (t is { IsFaulted: false, IsCanceled: false }) return await t;  // fast path

        await _gate.WaitAsync(ct);                    // async lock (Part 1 note)
        try
        {
            if (_rates is null or { IsFaulted: true } or { IsCanceled: true })
                _rates = FetchRatesAsync(ct);         // (re)start ONCE under the gate
            return await _rates;
        }
        finally { _gate.Release(); }
    }
}
// Single-flight: concurrent callers share one fetch; a failed fetch is retried on
// the next call instead of being cached forever. (Lazy<Task<T>> fixes bug 1
// alone — the reset-on-fault requirement is what forces the explicit gate.)
6 (Hard): Implement HedgedGetAsync: send a request; if no response within 300ms, send a second (hedge) request to a mirror; return whichever answers first; cancel the loser; propagate failure only if both fail.
Solution
public async Task<Response> HedgedGetAsync(string url, string mirrorUrl,
    CancellationToken ct = default)
{
    using var linked = CancellationTokenSource.CreateLinkedTokenSource(ct);
    var primary = GetAsync(url, linked.Token);

    var first = await Task.WhenAny(primary, Task.Delay(300, linked.Token));
    if (first == primary && primary.IsCompletedSuccessfully)
    {
        linked.Cancel();                             // nothing else to cancel yet, tidy
        return primary.Result;                       // fast path: answered under 300ms
    }

    // Slow (or already failed) → launch the hedge; race both:
    var hedge = GetAsync(mirrorUrl, linked.Token);
    var tasks = new List<Task<Response>> { primary, hedge };
    while (tasks.Count > 0)
    {
        var winner = await Task.WhenAny(tasks);
        if (winner.IsCompletedSuccessfully)
        {
            linked.Cancel();                         // cancel the loser — free its resources
            return winner.Result;
        }
        tasks.Remove(winner);                        // that one failed; wait for the other
    }
    linked.Cancel();
    throw new HttpRequestException($"Both {url} and {mirrorUrl} failed");
}
// Hedging trades a little extra load for tail-latency cuts (the P99 saver used by
// Google/BigTable et al.). Key details: linked CTS so the caller's cancel reaches
// both; cancel the loser (don't leak in-flight requests); only fail when BOTH fail.

🎯 Key Takeaways

  • Bound every fan-out: Parallel.ForEachAsync or a SemaphoreSlim gate sized to the downstream's capacity; Release() lives in finally.
  • SemaphoreSlim(1,1) is the async lock — lock can't contain await because monitors are thread-affine.
  • IAsyncEnumerable + await foreach streams items as they arrive in constant memory; [EnumeratorCancellation] wires tokens through.
  • Bounded Channel<T> is the producer/consumer backbone: backpressure by design, Complete() + drain for shutdown, DI-scoped consumers for background work.
  • TaskCompletionSource bridges callbacks to tasks — always RunContinuationsAsynchronously, TrySet*, and unhook handlers.
  • Know the incident patterns: sync-over-async starves the pool (low CPU + high latency), fire-and-forget outlives its DI scope, unbounded queues hide overload until OOM, retries need backoff + jitter + transient filters.
