Memory & GC: Span, IDisposable Runtime & Performance

What you'll master: how the .NET garbage collector actually works — generations, the Large Object Heap, GC modes; what makes memory leak in a garbage-collected runtime; deterministic cleanup with IDisposable/using (and when finalizers matter); and the modern allocation-avoidance toolkit — Span<T>, Memory<T>, ArrayPool, stackalloc. Prerequisites: Types & Variables (stack vs heap, value vs reference) and Delegates & Events (the classic leak). This is the lesson that turns "the GC handles it" into an actual model you can debug against.

Part 1 — The Generational GC: Why Most Allocations Are Nearly Free

// Allocation in .NET = bump a pointer. ~10ns. The COST is collection, and the GC
// is built around one empirical fact: MOST OBJECTS DIE YOUNG.
//
//  Gen 0  — the nursery. New small objects land here. Collected OFTEN, very fast
//           (only survivors are touched — a mostly-dead gen0 costs almost nothing).
//  Gen 1  — survivors of gen0. A buffer between "died young" and "long-lived".
//  Gen 2  — survivors again: caches, singletons, static data. Collected RARELY —
//           a gen2 ("full") collection walks the whole heap. This is the expensive one.
//  LOH    — Large Object Heap: objects ≥ 85,000 bytes (big arrays, huge strings).
//           Collected only with gen2, NOT compacted by default → fragmentation risk.
//
// Collection: pause → MARK everything reachable from ROOTS (thread stacks, static
// fields, GC handles) → SWEEP/COMPACT the dead → resume. "Reachable" is the whole
// definition of alive. Unreachable ≠ collected immediately — collected WHEN the GC
// next runs that generation.

// Promotion is the enemy: an object that survives gen0 gets copied to gen1, then gen2.
// MID-LIFED objects (live a few seconds — e.g. per-request caches under load) are the
// GC's worst case: too old to die in gen0, too young to sit quietly in gen2 —
// they inflate gen2 collections. Design for "die immediately" or "live forever".

// GC modes (server apps should know their own):
// Workstation — small heaps, minimal pauses, client apps.
// Server GC   — per-core heaps + parallel collection: higher throughput, bigger heap.
//               ASP.NET Core defaults to Server GC.
// Background GC does gen2 concurrently with your code (short pauses, not none).
What the GC does NOT manage: file handles, sockets, DB connections, OS handles, GPU/native memory. The GC sees only managed heap bytes; a FileStream is 100 managed bytes wrapping an OS handle the GC can't see or count. That's why disposal (Part 3) exists — and why "the GC will get to it" is exactly wrong for resources: it might get to it in minutes, and the OS ran out of handles in seconds.

Part 2 — Memory Leaks in a GC'd Runtime: Reachability Is the Leak

// A .NET "leak" = objects that are REACHABLE but USELESS. The GC is doing its job;
// your object graph lies about what you still need. The usual suspects:

// 1. EVENTS (the #1 — full mechanics in delegates-events.html Part 5):
//    static/long-lived publisher → delegate → Target keeps every subscriber alive.

// 2. STATIC COLLECTIONS that only grow:
static readonly Dictionary<string, Session> _sessions = new();   // who ever removes?
//    Every static root is a lifetime promise: "until process exit". Cache without
//    eviction = leak with a nicer name. Use MemoryCache with size/expiry, or evict.

// 3. CLOSURES captured by long-lived things (timers, callbacks, cached delegates):
_timer = new Timer(_ => Report(this.Stats), ...);   // 'this' lives as long as the timer

// 4. IDisposable NOT disposed — not a managed leak but a RESOURCE leak (handles,
//    connections). Symptoms arrive as "too many open files"/pool exhaustion, not RAM.

// DIAGNOSIS WORKFLOW (works with dotnet-counters + dotnet-gcdump / VS profiler):
// 1. dotnet-counters: is gen2 size climbing across collections? (If gen0/1 churn but
//    gen2 is flat → not a leak, just allocation pressure.)
// 2. Take TWO heap snapshots minutes apart → diff → which TYPE is accumulating?
// 3. Pick an instance → RETENTION PATH to root → the path names the culprit:
//    "static _sessions → Dictionary → Session" or "EventHandler → Target → View".
// The retention path IS the answer; everything before it is guessing.

Part 3 — IDisposable & using: Deterministic Cleanup

// The contract: "I hold a resource; call Dispose() the moment you're done with me."
// using guarantees it (compiles to try/finally — exceptions included):
using (var stream = File.OpenRead("data.bin"))
{
    Process(stream);
}                                   // stream.Dispose() here, even if Process threw

// using DECLARATION (C# 8) — disposes at end of enclosing scope; less nesting:
using var conn = new SqlConnection(cs);
using var reader = ExecuteReader(conn);
// both disposed (reverse order) when the method exits

// await using for IAsyncDisposable (flush needs I/O — e.g. streams, EF contexts):
await using var db = new AppDbContext(options);

// IMPLEMENTING it — modern guidance, three tiers:
// TIER 1 (95% of your classes): you hold MANAGED disposables → simple Dispose, NO finalizer:
public sealed class ReportWriter : IDisposable
{
    private readonly StreamWriter _writer;      // the resource we own
    private bool _disposed;
    public ReportWriter(string path) => _writer = new StreamWriter(path);

    public void Dispose()
    {
        if (_disposed) return;                  // idempotent — double-dispose is legal
        _writer.Dispose();                      // cascade to owned disposables
        _disposed = true;
    }
}
// Ownership rule: WHOEVER CREATES IT DISPOSES IT (or explicitly hands ownership off).
// If a class stores an injected disposable it does NOT own, it does NOT dispose it —
// the DI container does (di-hosting.html).

// TIER 2: you hold RAW native handles → derive from SafeHandle (the BCL's wrapper
// with a hardened finalizer) rather than writing your own finalizer.
// TIER 3 (rare, library-authors): the classic Dispose(bool) pattern + finalizer —
// only when you directly own an unmanaged pointer/handle no SafeHandle covers.
// Finalizers are a SAFETY NET, not cleanup: they run late, on a dedicated thread,
// maybe never (process kill), and keep the object alive an extra GC cycle.

Part 4 — Span<T>: Slicing Without Allocating

// Span<T> = a (pointer, length) view over EXISTING memory — array, string, stack,
// native. Reading/slicing through a Span allocates NOTHING.
string csv = "2026-07-27,ORDER-9931,499.99";

// OLD WAY — Substring/Split allocate a new string per piece:
var parts = csv.Split(',');                    // 1 array + 3 strings on the heap

// SPAN WAY — zero allocations, same logic:
ReadOnlySpan<char> s = csv;                    // a VIEW, not a copy
int c1 = s.IndexOf(',');
ReadOnlySpan<char> date   = s[..c1];           // slices are just (offset, length) —
ReadOnlySpan<char> rest   = s[(c1 + 1)..];     // no new strings anywhere
int c2 = rest.IndexOf(',');
ReadOnlySpan<char> id     = rest[..c2];
decimal amount = decimal.Parse(rest[(c2 + 1)..]);   // BCL parses spans directly

// stackalloc — a scratch buffer ON THE STACK (freed by returning, GC never involved):
Span<byte> buffer = stackalloc byte[256];      // small (< ~1KB), method-lifetime only
Random.Shared.NextBytes(buffer);

// THE RESTRICTION that makes it safe: Span is a ref struct — it may live ONLY on the
// stack. The compiler REJECTS: Span fields in classes, Span locals crossing await/yield,
// Span in async signatures. Why: a Span could point at stack memory; letting it
// escape to the heap could outlive that stack frame → dangling pointer. The compiler
// makes the dangerous case unrepresentable.

// Memory<T> is the heap-safe sibling: storable in fields, usable across await
// (Stream.ReadAsync takes Memory<byte>); call .Span inside sync code to work on it.

// ArrayPool<T> — rent/return big temporary buffers instead of allocating (LOH-saver):
byte[] rented = ArrayPool<byte>.Shared.Rent(1024 * 1024);
try     { await stream.ReadAsync(rented.AsMemory(0, len), ct); Use(rented); }
finally { ArrayPool<byte>.Shared.Return(rented); }   // ALWAYS return; may be dirty
// Repeated 1MB allocations = LOH churn = gen2 pressure; a pool reuses the same buffers.
Where Span actually pays: parsing hot paths (the BCL's own parsers, formatters, and System.Text.Json are built on it), serialization, string processing in request pipelines, and buffer management. Where it doesn't: cold paths, code that was already allocation-light, anything crossing awaits (use Memory<T>). Adopt it where the profiler shows allocation pressure — Substring/Split in a loop lighting up gen0 — not by reflex. Readability still wins by default (measure first).

Part 5 — Deep Dive: Reading GC Behavior in Production

// The numbers that matter (dotnet-counters monitor --process-id N):
//   GC Heap Size / Gen 2 Size   — trending up forever? → leak workflow (Part 2).
//   Gen 0/1/2 collection counts — healthy apps: MANY gen0, few gen2.
//   % Time in GC                — >10–15% sustained = allocation pressure is taxing you.
//   LOH Size                    — sawtooth is fine; monotonic growth = large-object leak
//                                 or fragmentation (pin-heavy code, no compaction).
//   Allocation Rate             — MB/s; correlate spikes with endpoints/jobs.

// PATTERNS AND THEIR MEANINGS:
// "Memory climbs, GC runs, memory doesn't drop" → reachable objects: LEAK (Part 2).
// "Memory sawtooths aggressively, CPU high in GC" → allocation PRESSURE, not a leak:
//     hunt per-request allocations (closures, LINQ in hot loops, Substring storms,
//     large temp arrays) → static lambdas, Span, ArrayPool, pooling.
// "P99 latency spikes every N minutes, heap large" → gen2/LOH pauses: reduce mid-lifed
//     objects and LOH churn; consider GC settings LAST, allocations FIRST.
// "Works for days, then OutOfMemoryException on a 64-bit box" → check LOH fragmentation
//     and pinned buffers (sockets!) — address-space isn't the limit, contiguity is.

// GC.Collect() in production code: virtually always wrong — it forces the expensive
// full collection the GC was avoiding, promotes half-dead objects, and hides the real
// issue. Acceptable: test harnesses, and rare "just unloaded a huge one-off dataset"
// moments — with a comment justifying it.

Interview Questions

Q1 (Beginner): What does the garbage collector do, and what does "reachable" mean?

The GC automatically reclaims heap memory: it pauses the application, marks every object reachable by following references from roots — thread stacks (local variables), static fields, and GC handles — then reclaims everything unmarked, typically compacting survivors. "Reachable" means there's a reference chain from a root to the object; reachability is the GC's entire definition of alive. Two corollaries: unreferenced objects aren't freed instantly (only when a collection runs), and anything referenced from a static field or live event lives forever no matter how "done" you are with it.

Q2 (Beginner): What is IDisposable, and what does a using statement guarantee?

IDisposable is the contract for deterministic cleanup: the object holds a resource the GC can't manage (file handle, socket, DB connection) and Dispose() releases it immediately. using compiles to try/finally, so Dispose() is called when the block/scope exits — even via exception or early return. This matters because GC timing is unpredictable: a server can exhaust its OS handles or connection pool in seconds while the unhelpfully-still-reachable wrappers wait for a collection that hasn't happened.

Q3 (Mid): Explain the generational hypothesis and why gen2 collections are the ones you tune against.

The generational hypothesis: most objects die young (temporaries, per-request data), and objects that survive a while tend to live long (caches, singletons). The GC exploits this by collecting gen0 (new objects) frequently and cheaply — cost scales with survivors, and a mostly-dead nursery has few — while gen2 is collected rarely because it requires walking the entire heap (plus the LOH), making it orders of magnitude more expensive and the source of noticeable pauses. Tuning therefore focuses on: minimizing objects that get promoted (mid-lifed objects are the worst case — too old for gen0, too transient for gen2), and avoiding LOH churn, since large objects go straight to the heap that only full collections touch.

Q4 (Mid): What is Span<T>, why is it a ref struct, and when do you need Memory<T> instead?

Span<T> is a stack-only view (pointer + length) over existing memory — array segments, strings, stackalloc buffers, native memory — enabling slicing and parsing with zero allocations (s[..10] creates no new string). It's a ref struct so the compiler can guarantee it never escapes to the heap: a Span might reference stack memory, and if it could be stored in a class field or captured across an await, it could outlive the stack frame it points into. Hence the rules: no class fields, no boxing, no use across await/yield. Memory<T> is the heap-storable equivalent for those cases — keep it in fields, pass it through async methods (Stream.ReadAsync(Memory<byte>)), and call .Span when synchronous work begins.

Q5 (Senior): A service's memory grows from 300MB to 6GB over two days, then OOMs. Walk through your diagnosis end to end.

First confirm it's managed and reachable: dotnet-counters — if Gen 2 + LOH size climbs monotonically across collections, it's a leak (reachable objects); if heap sawtooths but working set grows, suspect native/pinned memory instead. For a managed leak: capture two dotnet-gcdump snapshots an hour apart, diff by type to find what's accumulating (say, 4M OrderContext instances), then inspect retention paths on samples — the path to root names the mechanism: a static event's invocation list (EventHandler.Target), a static dictionary/cache with no eviction, an IServiceScope never disposed, timers holding closures. Fix the reachability (unsubscribe in Dispose, bounded cache with expiry, dispose scopes), redeploy, and verify the gen2 trend is flat under load. If instead the diff shows churn (high allocation rate, %GC time) rather than growth, the problem is pressure, not leak — different fix (reduce per-request allocations). The discipline: never guess from code review alone; the retention path is evidence.

Q6 (Senior): When do you implement a finalizer? Describe the modern guidance and what finalizers cost.

Almost never. Finalizers exist as a last-resort safety net for unmanaged resources when Dispose was forgotten — but they're expensive and unreliable: finalizable objects survive at least one extra collection (they're promoted while queued), finalization runs on a single dedicated thread at an unpredictable time (a slow finalizer stalls all others), order is unspecified, and on process termination they may never run. Modern guidance: wrap raw OS handles in a SafeHandle subclass — it provides a hardened, critical finalizer written by the BCL team — and your class then just implements plain IDisposable that disposes the SafeHandle; no finalizer of your own. Hand-written finalizers (with the full Dispose(bool) + GC.SuppressFinalize pattern) are justified only when you directly own unmanaged memory/handles that no SafeHandle can represent — rare outside interop libraries.

🏋️ Graded Exercises

1 (Easy): This method leaks a resource on exceptions. Fix it two ways (statement and declaration form). 
public string ReadConfig() {
    var reader = new StreamReader("app.config");
    var text = reader.ReadToEnd();      // may throw
    reader.Dispose();
    return text;
}
Solution
// If ReadToEnd throws, Dispose is skipped — the file handle leaks until a GC
// eventually finalizes the underlying stream (maybe minutes later, maybe never).

// Form 1 — using statement:
public string ReadConfig()
{
    using (var reader = new StreamReader("app.config"))
    {
        return reader.ReadToEnd();      // Dispose runs on return AND on throw
    }
}
// Form 2 — using declaration (C# 8+, less nesting):
public string ReadConfig()
{
    using var reader = new StreamReader("app.config");
    return reader.ReadToEnd();          // disposed when the method scope exits
}
// (For this exact task, File.ReadAllText("app.config") is the real answer —
// the BCL manages the handle for you.)
2 (Easy): For each, say which generation/heap it likely ends its life in and why: (a) a string built inside a request handler and returned as the response; (b) a singleton configuration object; (c) a 2MB report buffer allocated per report; (d) a per-request DTO held in a static "recent requests" list.
Solution
// (a) Gen 0 — allocated, serialized into the response, unreachable within the
//     request: dies young in the nursery. The ideal case.
// (b) Gen 2 — allocated once at startup, survives collections, promoted to gen2,
//     lives until process exit. Also fine: stable long-lived data.
// (c) LOH — ≥85,000 bytes goes straight to the Large Object Heap; collected only
//     with gen2 and not compacted by default. Per-report 2MB allocations = LOH churn
//     → rent from ArrayPool instead.
// (d) THE PROBLEM CHILD: it would die in gen0, but the static list ROOTS it —
//     promoted to gen2 and retained forever. This is how "leaks" look: reachable
//     but useless. Bound the list or use an evicting cache.
3 (Medium): Implement TempDirectory : IDisposable — creates a unique temp folder on construction, deletes it on dispose, idempotent, usable with using.
Solution
public sealed class TempDirectory : IDisposable
{
    public string Path { get; }
    private bool _disposed;

    public TempDirectory()
    {
        Path = System.IO.Path.Combine(
            System.IO.Path.GetTempPath(), Guid.NewGuid().ToString("N"));
        Directory.CreateDirectory(Path);
    }

    public void Dispose()
    {
        if (_disposed) return;                       // idempotent contract
        try { Directory.Delete(Path, recursive: true); }
        catch (DirectoryNotFoundException) { }       // already gone = fine
        _disposed = true;
    }
}

// Usage — cleanup guaranteed even when the test/work throws:
using var tmp = new TempDirectory();
File.WriteAllText(System.IO.Path.Combine(tmp.Path, "work.txt"), "data");
// sealed + no finalizer: Tier 1 — we hold no raw OS handles, only behavior.
// (A finalizer here would be wrong: Directory.Delete on the finalizer thread at
//  an arbitrary time is exactly the nondeterminism Dispose exists to avoid.)
4 (Medium): Rewrite this hot-path parser to zero allocations with ReadOnlySpan<char>: it extracts the status code (chars 9–11) and reason from lines like "HTTP/1.1 404 Not Found". 
public (int code, string reason) Parse(string line) {
    var parts = line.Split(' ', 3);
    return (int.Parse(parts[1]), parts[2]);
}
Solution
public (int code, string reason) Parse(ReadOnlySpan<char> line)
{
    // "HTTP/1.1 404 Not Found"
    int firstSpace  = line.IndexOf(' ');                       // after version
    var afterVer    = line[(firstSpace + 1)..];
    int secondSpace = afterVer.IndexOf(' ');
    int code   = int.Parse(afterVer[..secondSpace]);           // parses the SLICE — no string
    var reason = afterVer[(secondSpace + 1)..];
    return (code, reason.ToString());   // ONE allocation: the reason we must return
}
// Split allocated: 1 string[] + 3 strings per line. The span version allocates only
// the returned reason string (a returned value can't stay a stack-only span).
// If callers only COMPARE the reason, return the span-friendly shape instead:
public int ParseCode(ReadOnlySpan<char> line) { ... }          // zero allocations
// — pushing the "when do we materialize a string" decision to the caller is the
// standard span-API design move (it's how the BCL's own parsers are shaped).
5 (Hard): A file-processing service allocates a new byte[5 * 1024 * 1024] per uploaded file, 50 uploads/min. Ops reports periodic multi-hundred-ms latency spikes and high %GC time. Explain the mechanism and fix it with ArrayPool.
Solution
// MECHANISM: 5MB ≥ the 85KB threshold → every buffer lands on the LOH. The LOH is
// collected only during gen2 (full) collections and isn't compacted by default.
// 50/min × 5MB = 250MB/min of LOH garbage → the GC must run frequent full
// collections to keep up — each walks the ENTIRE heap → the periodic latency spikes.

public async Task ProcessUploadAsync(Stream upload, long length, CancellationToken ct)
{
    byte[] buffer = ArrayPool<byte>.Shared.Rent((int)length);   // reused, not allocated
    try
    {
        int read = 0;
        while (read < length)
            read += await upload.ReadAsync(
                buffer.AsMemory(read, (int)length - read), ct);
        Process(buffer.AsSpan(0, read));       // NOTE: Rent may return a BIGGER array —
    }                                          // always slice to the length you filled
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer); // ALWAYS return (finally). Buffer may
    }                                          // contain old data — clear if sensitive:
}                                              // Return(buffer, clearArray: true)
// Steady state: a handful of pooled 5MB buffers cycle forever — LOH allocation rate
// ~0, full collections become rare, spikes disappear.
// Even better when possible: STREAM the upload (process in 64KB chunks) and never
// hold whole files in memory at all.
6 (Hard): Diagnose from evidence: heap snapshots show 800,000 HttpClient instances… wait — actually 800,000 SocketsHttpHandler objects and the OS reports ~64k TIME_WAIT sockets. The code does using var client = new HttpClient(); await client.GetAsync(url); per request. Explain why "correct disposal" is the bug here, and fix it.
Solution
// The developer followed "dispose your IDisposables" — but HttpClient is the
// documented EXCEPTION: it's designed to be long-lived and shared. Creating one
// per request means a new connection pool per request; disposing it closes the
// pooled connections, and closed TCP sockets linger in TIME_WAIT (~2 min by OS
// design) → socket/port exhaustion under load. The heap shows the handler churn;
// the OS shows the real damage. Disposal was "correct" per the interface and wrong
// per the resource's semantics: the expensive thing is the POOL, not the object.

// FIX — one shared client (or IHttpClientFactory in DI apps — di-hosting.html):
public static class Http
{
    public static readonly HttpClient Client = new(new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5)   // rotate connections so
    });                                                       // DNS changes are honored
}
// services.AddHttpClient<CatalogClient>() does the same management for you, plus
// named/typed clients and Polly integration. PooledConnectionLifetime matters:
// an immortal client without it never re-resolves DNS (stale endpoints after failover).
// LESSON: ownership rules are per-resource-semantics, not just per-interface —
// connection-pooling types (HttpClient, DbContext pools, connection pools) are
// managed by lifetime, not by using-blocks.

🎯 Key Takeaways

  • Allocation is a pointer bump; collection is the cost. Generations exploit "most objects die young" — many cheap gen0 collections, rare expensive gen2 ones; mid-lifed and large (LOH ≥85KB) objects are the GC's worst cases.
  • A managed "leak" is reachable-but-useless memory: static collections, event subscriptions, timer closures. Diagnose with snapshot diffs and the retention path — never by guessing.
  • The GC doesn't manage handles/sockets/connections: IDisposable + using gives deterministic cleanup; creator disposes; finalizers only via SafeHandle.
  • Span<T> slices existing memory with zero allocations and is compiler-confined to the stack; Memory<T> crosses awaits and fields; ArrayPool recycles big buffers away from the LOH.
  • Read production memory via counters: gen2/LOH trending up = leak; sawtooth + %GC high = allocation pressure — two different problems, two different fixes.
  • Semantics beat rules: pooled resources like HttpClient are shared by design; GC.Collect() is almost never the answer; optimize allocations only where measured.
