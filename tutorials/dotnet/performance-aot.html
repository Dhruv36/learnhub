Performance, Benchmarking & NativeAOT Runtime & Performance

What you'll master: the performance method — measure, don't guess: profiling with the dotnet CLI tools, micro-benchmarking correctly with BenchmarkDotNet (and why Stopwatch benchmarks lie); the optimizations that actually move .NET services (allocation reduction, caching, batching, the string toolbox); how the JIT works for you (tiered compilation, PGO); and the deployment axis — ReadyToRun and NativeAOT, with their real trade-offs. Prerequisites: Memory & GC (allocation pressure is half of .NET performance), Collections (Big-O first), LINQ (its costs). The senior skill isn't making code fast — it's knowing which code needs to be.

Part 1 — The Method: Where Performance Work Actually Starts

// The performance hierarchy — fix the top before touching the bottom:
// 1. ARCHITECTURE   N+1 queries, missing cache, chatty APIs, sync-over-async
//                   → 10–1000× wins live here (efcore.html, async-patterns.html)
// 2. ALGORITHM      O(n²) scans, wrong collection for the access pattern
//                   → the List.Contains-in-a-loop → HashSet fix (collections-generics.html)
// 3. ALLOCATIONS    closures, LINQ chains, Substring storms in hot paths
//                   → GC pressure taxes EVERYTHING (memory.html)
// 4. MICRO          struct layout, span tricks, SIMD — last, and only measured
//
// A dev who vectorizes a loop inside an N+1 query pattern has optimized nothing.

// THE WORKFLOW when "the service is slow":
// 1. dotnet-counters monitor -p <pid>     — vital signs: CPU, %GC, threadpool queue,
//                                           exception rate, allocation rate
// 2. Which resource is saturated?
//    High CPU        → dotnet-trace collect → flame graph → the hot method names itself
//    High %GC        → allocation profiling → who allocates (memory.html Part 5)
//    Low CPU + slow  → waiting: threadpool starvation, lock contention, or the
//                      DEPENDENCY is slow (check DB/HTTP latencies first!)
// 3. Fix the ONE thing the evidence names. Re-measure. Repeat.
// Most "slow service" tickets end at a database query or a missing cache —
// not at C# code at all. Profile before editing.

Part 2 — Benchmarking: Why Naive Timing Lies, and BenchmarkDotNet

// ❌ The Stopwatch benchmark every beginner writes:
var sw = Stopwatch.StartNew();
for (int i = 0; i < 1000; i++) Method();
Console.WriteLine(sw.ElapsedMilliseconds);
// Lies because: 1st iterations measure the JIT compiling, not the code (tiered
// compilation recompiles hot code ~30 calls in!); Debug builds disable optimization;
// GC pauses from PREVIOUS code land in your window; the CPU boosts/throttles;
// dead-code elimination may delete the very thing you measured.

// ✅ BenchmarkDotNet — the industry standard (used by the .NET team itself):
[MemoryDiagnoser]                          // allocations per op — half the story!
public class ParseBenchmarks
{
    private readonly string _line = "2026-07-27,ORDER-9931,499.99";

    [Benchmark(Baseline = true)]
    public string[] Split() => _line.Split(',');

    [Benchmark]
    public decimal SpanParse()
    {
        var s = _line.AsSpan();
        return decimal.Parse(s[(s.LastIndexOf(',') + 1)..]);
    }
}
// Run: BenchmarkRunner.Run<ParseBenchmarks>();  (Release build, no debugger)
// It handles: warmup until steady-state, process isolation, statistical analysis
// (mean ± error, outlier detection), and [MemoryDiagnoser] shows B/op + Gen0 rate.

// READING RESULTS — the two traps:
// 1. ns/op differences don't matter unless the op is HOT. 50ns → 20ns on something
//    called 100×/s is nothing. The same on 10M×/s is 0.3 CPU-seconds per second.
// 2. Allocations/op can matter MORE than time/op: 200B/op × 1M ops/s = 200MB/s of
//    GC pressure taxing the whole process, invisible in the per-op timing.
Micro vs macro: BenchmarkDotNet answers "which of these two implementations is faster in isolation". It cannot answer "will this make my service faster" — that needs a load test (k6/NBomber/JMeter) against realistic traffic, watching P50/P95/P99 latency and throughput. Services are queueing systems: contention, pool sizes, and GC behavior under sustained load don't exist in a microbenchmark. Use both, for different questions — and always state which question you're answering.

Part 3 — The Optimizations That Actually Move Services

// 1. STOP DOING THE WORK (the biggest wins are subtractions):
//    - Cache computed/fetched values with bounded MemoryCache (+ expiry):
var user = await _cache.GetOrCreateAsync($"user:{id}", async e =>
{
    e.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
    e.Size = 1;                                    // pair with a SizeLimit on the cache
    return await _db.Users.FindAsync(id);
});
//    - Batch: 1 query for 100 ids beats 100 queries (efcore.html); 1 bulk insert
//      beats a loop of inserts; pipeline HTTP calls (async-await.html WhenAll).

// 2. STRINGS (the classic hot-path tax — see strings.html):
//    - Concatenation in a loop is O(n²): StringBuilder.
//    - string.Create / interpolation handlers for formatted hot paths.
//    - StringComparison.Ordinal(-IgnoreCase) for comparisons — culture-aware
//      comparison is surprisingly costly and usually not what you meant anyway.
//    - Span slicing over Substring/Split (memory.html Part 4).

// 3. ALLOCATION HYGIENE in measured hot paths only:
//    static lambdas (delegates-events.html), ArrayPool for big buffers,
//    ValueTask on hit-dominated async APIs (async-await.html), structs for small
//    short-lived aggregates (records-structs.html) — each with a benchmark receipt.

// 4. LET THE JIT WORK: tiered compilation compiles cold code fast/unoptimized
//    (tier 0), then RE-compiles hot methods optimized (tier 1) — with Dynamic PGO
//    using observed runtime behavior (which branch is taken, which concrete type
//    flows) to devirtualize and inline. Consequences for you:
//    - Long-running services get faster after warmup — benchmark steady state.
//    - Write straightforward code: the JIT inlines small methods, hoists bounds
//      checks in simple loops (foreach over T[]), devirtualizes sealed calls.
//      'sealed' on classes is a free micro-optimization AND a design statement.

Part 4 — Deployment Performance: ReadyToRun & NativeAOT

// THE STARTUP PROBLEM: JIT compiles methods on first call → cold start = JIT time.
// Three compilation strategies, one axis: compile earlier ⟷ optimize with more info.

// 1. DEFAULT (JIT + tiered + PGO)
//    Slowest start, FASTEST steady state (PGO optimizes with runtime knowledge).
//    Right for: long-running services — almost everything.

// 2. READYTORUN (R2R): <PublishReadyToRun>true</PublishReadyToRun>
//    AOT-compiles to native at publish, KEEPS the JIT: starts from precompiled code,
//    hot paths still re-optimized by tiered/PGO later. ~30–50% faster start,
//    larger binaries. Right for: services where cold start matters but you want
//    full runtime compatibility. The low-risk middle option.

// 3. NATIVEAOT: <PublishAot>true</PublishAot>
//    Fully native single binary, NO JIT, NO runtime dependency. Millisecond starts,
//    tiny memory (tens of MB → few MB), trimmed to reachable code.
dotnet publish -c Release -r linux-x64 /p:PublishAot=true
//    THE PRICE — no runtime code generation, and trimming needs static reachability:
//    ✗ Reflection.Emit, runtime proxies (Castle/Moq), some serializers/DI containers
//    ✗ unconstrained reflection: Type.GetType(runtimeString), Activator over
//      arbitrary types — the trimmer can't see them → members trimmed → runtime break
//    ✓ source generators replace reflection: System.Text.Json srcgen, DI srcgen,
//      [LibraryImport] interop — the AOT-era pattern: do at COMPILE TIME what
//      reflection did at RUNTIME.
//    Right for: CLI tools (instant start), serverless/lambdas (cold-start billing),
//    sidecars/edge with tight memory, containers wanting minimal images.
//    Wrong for: apps leaning on reflection-heavy libraries — check compatibility first.

Part 5 — Deep Dive: A Worked Optimization, End to End

// TICKET: "P95 latency on GET /catalog/search went from 80ms to 900ms."
// STEP 1 — counters: CPU 85%, %GC 22%, allocation rate 1.9GB/s. CPU+GC bound.
// STEP 2 — dotnet-trace flame graph: 60% of CPU inside SearchService.Rank →
//          String.ToLower + LINQ OrderBy chain; allocation profile: string[] from
//          Split, closures, and List growth in the same method. The evidence names it:
public List<Product> Rank(string query, List<Product> items) =>
    items.Where(p => p.Name.ToLower().Contains(query.ToLower()))   // 2 new strings
         .OrderByDescending(p => Score(p, query))                  //   PER PRODUCT
         .ToList();                                                // per REQUEST

// STEP 3 — fix what the profile showed (and nothing else):
public List<Product> Rank(string query, List<Product> items)
{
    var result = new List<Product>(64);
    foreach (var p in items)
        if (p.Name.Contains(query, StringComparison.OrdinalIgnoreCase))  // 0 allocations
            result.Add(p);
    result.Sort((a, b) => Score(b, query).CompareTo(Score(a, query)));   // in-place
    return result;
}
// STEP 4 — receipts: BenchmarkDotNet on Rank: 41μs→6μs, 38KB→1.2KB per op.
//          Load test: P95 900ms→85ms, %GC 22%→4%. SHIP with both numbers in the PR.
// STEP 5 — the architectural question AFTER the bleeding stops: why is search
//          scanning a List per request at all? (Index it, or push to the DB/search
//          engine — the tier-1 fix that makes the micro-fix irrelevant at 10× scale.)

Part 6 — Keeping It Fast: Budgets, Regression Gates & Production Signals

// Part 5 fixed one regression. The senior questions: how did it ship, and what
// stops the next one? Performance that is not measured CONTINUOUSLY decays.

// LAYER 1 — MICRO: benchmark the hot paths in CI against a baseline.
//   BenchmarkDotNet over the few methods that matter (Rank, serializers, parsers).
//   Export results on every run, compare with main's stored baseline, and FAIL the PR
//   on a significant regression: more than 10% slower, or any allocation on a path

//   The budget is the contract. A PR that breaks it does not merge. A PR that must

Interview Questions

Q1 (Beginner): A colleague timed two methods with Stopwatch in a Debug build and picked the winner. What's wrong?

Almost every part of that measurement is wrong, and the conclusion can easily be inverted. The first problem is the build. A Debug build compiles IL without optimisation, and an attached debugger stops the JIT optimising even Release code. Neither method ran the code production will run: inlining, bounds-check elimination and register allocation were missing, and their absence does not hurt both methods equally.

The second is warm-up. The first calls include JIT compilation, and under tiered compilation a method runs as quick, unoptimised tier-0 code until it has been called about 30 times, after which it is recompiled with PGO. A short loop measures an unknown blend of compile time, tier-0 code and tier-1 code.

The third is noise and dead code. A GC triggered by earlier allocations can land inside the timing window; frequency scaling and other processes skew a single run; and if the result is never used, the optimiser may delete the work entirely. One run with no variance gives no way to tell whether a 10% difference is real.

  [MemoryDiagnoser]
  public class Candidates
  {
      private readonly Order[] _orders = TestData.Orders(10_000);   // realistic size

      [Benchmark(Baseline = true)] public decimal A() => Pricing.TotalA(_orders);
      [Benchmark]                  public decimal B() => Pricing.TotalB(_orders);
  }   // results are returned, so the work cannot be eliminated
  // dotnet run -c Release, with BenchmarkRunner.Run<Candidates>() in Main

BenchmarkDotNet fixes each of these. It refuses non-optimised assemblies by default, runs in a separate process, warms up to steady state, runs many iterations and reports mean, error and standard deviation, consumes return values, and with [MemoryDiagnoser] reports bytes allocated per operation, often the more important number.

The interviewer is probing scepticism about measurement. A strong answer also asks whether the difference matters at all, meaning how hot the method is in production, and whether the inputs were realistic, because a benchmark over ten items says little about ten thousand.

Q2 (Beginner): What order do you attack a "the API is slow" ticket?

The order is measure, localise, then fix the tier the evidence names, and never start by editing code. First, scope it: which endpoints, which percentile, since when, and on every instance or one? A P50 that doubled everywhere is systemic; a P99 that grew on one endpoint after a deploy points at a specific change, and "since when" gives you a diff to read.

Second, check dependencies, the cheapest suspect to rule out. Distributed tracing or request telemetry shows how much of each request is spent in the database, a downstream HTTP call or a cache. If 700 of 800 milliseconds are one SQL query, the investigation moves to the query plan and the C# is irrelevant.

Third, read the process's vital signs:

  dotnet-counters monitor -p <pid> --counters System.Runtime
  # high CPU                  → dotnet-trace, flame graph: the hot method names itself
  # high % time in GC         → allocation profiling: who allocates per request
  # low CPU, rising latency   → waiting: thread-pool queue, lock contention,
  #                             connection-pool waits, sync-over-async

Only then work down the lesson's hierarchy: architecture first (N+1 queries, missing caches, sequential awaits of independent calls, chatty APIs), then algorithms (quadratic scans, the wrong collection), then allocations in the proven hot path, and micro-optimisation last. Fix one thing, re-measure, and repeat, so every change carries its own evidence.

The interviewer is checking discipline. A weak answer lists optimisation tricks. A strong one says that most slow-API tickets end at a query or a missing cache, that the 10–1000× wins live in architecture, and that low CPU with high latency means the process is waiting, not working, so no amount of faster C# will help.

Q3 (Mid): What is tiered compilation with dynamic PGO, and how does it change how you write and benchmark code?

Tiered compilation resolves the JIT's basic tension: optimising well takes time, but startup wants code now. A method is first compiled at tier 0, quickly and with minimal optimisation. The runtime counts calls, and once a method has been called about 30 times it is queued for recompilation at tier 1, fully optimised, on a background thread. Long loops in methods called only once, such as Main, are handled by on-stack replacement, which switches a running loop to optimised code mid-execution.

Dynamic PGO, on by default since .NET 8, inserts an instrumented stage for hot methods. While instrumented, the method records what actually happens: which branches are taken and which concrete types appear at virtual and interface call sites. Tier 1 then compiles with that profile. The biggest win is guarded devirtualisation: if a call site almost always sees one concrete class, the JIT emits a cheap type check and a direct, inlinable call, keeping the virtual call as a fallback.

  // what the JIT effectively emits for a mostly-monomorphic interface call
  if (comparer.GetType() == typeof(OrdinalComparer))
      result = /* OrdinalComparer.Compare, inlined */;
  else
      result = comparer.Compare(a, b);      // rare path: normal interface dispatch

The consequences are practical. Benchmarks must reach steady state, because early iterations measure tier-0 code; BenchmarkDotNet's warm-up handles that. Services are slower just after a deploy, which matters for latency SLOs; warm-up traffic before joining the load balancer, or ReadyToRun to start from precompiled code, helps. Straightforward code optimises best: small methods inline, sealed classes devirtualise without a guard, and simple loops over arrays lose their bounds checks.

One more: a benchmark with an unrealistic type mix misleads, because PGO specialises for what it observes. The interviewer is probing whether you know the runtime keeps optimising after startup, and why a NativeAOT binary, having no JIT, cannot.

Q4 (Mid): Compare JIT, ReadyToRun, and NativeAOT — and pick one for (a) a high-traffic API, (b) a CLI tool, (c) a serverless function.

The three sit on one axis: compile earlier, or optimise with more information. The JIT compiles at run time, so startup pays for compilation, but tiered compilation and dynamic PGO optimise hot code using real runtime behaviour, which gives the best steady-state throughput. ReadyToRun precompiles IL to native code at publish time and ships both. The app starts from precompiled code, typically 30–50% faster, and because the JIT is still present, hot methods are later recompiled at tier 1 with PGO. The cost is larger binaries, with no loss of compatibility.

NativeAOT compiles the whole app, trimmed to reachable code, into one native executable with no JIT at all. Startup takes milliseconds and memory is a fraction of a JIT app's. The price is that nothing can be generated or discovered at run time: Reflection.Emit and dynamic proxies fail, unconstrained reflection can hit trimmed members, and steady-state code is good but not PGO-tuned. Dependencies must be trim- and AOT-compatible, which in practice means source-generated JSON, DI and logging.

  <!-- ReadyToRun: faster start, full compatibility -->
  <PublishReadyToRun>true</PublishReadyToRun>

  <!-- NativeAOT: also enables the trim and AOT analyzers at build time -->
  <PublishAot>true</PublishAot>

The picks follow from what each workload pays for. (a) A high-traffic API runs for days, so startup is amortised and throughput dominates: the default JIT, or ReadyToRun if scale-out events and deploys make cold instances hurt latency. (b) A CLI tool runs for a second, so startup is the user experience: NativeAOT, which also gives a single file with no runtime to install. (c) A serverless function pays for cold starts in both latency and billing: NativeAOT where the dependencies support it, otherwise ReadyToRun.

The interviewer is probing whether you treat AOT as a trade rather than an upgrade. A strong answer adds the verification step: publish AOT in CI from day one and treat trim warnings as errors, because the failures only appear in the published binary.

Q5 (Senior): Your benchmark shows implementation B is 3× faster than A, but after shipping B the service's P99 got worse. Explain plausible mechanisms and what you'd do differently.

Microbenchmarks measure isolated per-op cost; services are queueing systems. Plausible mechanisms: B allocates more (or larger/LOH) objects — per-op time won, but GC pressure rose and gen2/LOH pauses land in the tail; B uses more parallelism internally — faster alone, but under concurrent load it oversubscribes cores and increases contention; B holds a lock or pooled resource longer, queueing requests at high percentiles; B's memory access patterns blow the cache when many instances run concurrently; or B changed tail behavior only under rare inputs the benchmark never fed. Differently: benchmark with [MemoryDiagnoser] and realistic inputs, then validate with a load test at production-like concurrency watching percentiles and GC counters before shipping — and canary the rollout, comparing P99 and %GC between cohorts, so the queueing effects show up on 5% of traffic instead of all of it.

Q6 (Senior): You're moving a minimal API to NativeAOT for serverless. What breaks, and what's the modern remediation for each?

Everything that generates code or reflects at runtime. (1) Reflection-based JSON serialization — remediate with System.Text.Json source generation (JsonSerializerContext with [JsonSerializable] per root type). (2) Unconstrained reflection — Type.GetType(string), scanning assemblies for handlers — replace with source generators or explicit registration; where unavoidable, annotate with [DynamicallyAccessedMembers] so the trimmer preserves members. (3) Runtime proxy libraries (Castle DynamicProxy–based mocking, some interceptor-based DI/AOP) — no Reflection.Emit; use source-generated alternatives or design around them. (4) Some DI patterns (open-generic resolution edge cases, assembly scanning) — register explicitly. Process guidance: enable <PublishAot> from day one in CI so trim/AOT warnings surface immediately, treat those warnings as errors, and smoke-test the published native binary — the failure mode is runtime MissingMetadataException-style errors that unit tests on the JIT build never see.

3 (Medium): This endpoint code is called 2,000×/s. Find the four allocation/perf problems and rewrite. 
public string BuildKey(HttpRequest req) {
    var parts = req.Path.ToString().ToLower().Split('/');
    var key = "";
    foreach (var p in parts) key = key + ":" + p;
    return "cache" + key;
}
Solution
// 1. ToString().ToLower() — TWO full string copies per call (culture-aware, too).
// 2. Split('/') — string[] + one string per segment.
// 3. key = key + ":" + p in a loop — O(n²) copying, a new string per iteration.
// 4. "cache" + key — one more concat.
public string BuildKey(HttpRequest req)
{
    var path = req.Path.Value.AsSpan();               // no copy
    // Path segments are already ':'-joinable by replacing '/' — do it in one pass:
    return string.Create(path.Length + 5, path, static (dest, src) =>
    {
        "cache".CopyTo(dest);                         // prefix
        var target = dest[5..];
        for (int i = 0; i < src.Length; i++)
        {
            char c = src[i];
            target[i] = c == '/' ? ':' : char.ToLowerInvariant(c);
        }
    });
}
// ONE allocation: the final string, written in place (string.Create gives a writable
// span over the not-yet-frozen string). Same output, ~10× less garbage at 2,000/s.
// Benchmark receipt before merging — and note Ordinal-style lowering (invariant),
// not culture-aware, which is also CORRECT for cache keys (strings.html).

5 (Hard): Design the measurement plan (not the fix) for: "checkout latency doubled after last week's release, only during evening peak." What do you collect, compare, and rule out — in order?

// 1. SCOPE IT: which percentile moved? (P50 doubled = systemic; P99 only = tail/GC/
//    contention). Which endpoints — checkout only, or everything? One instance or all?
// 2. DIFF THE RELEASE: git log for the deploy window — new queries, new dependency
//    calls, serialization changes, config/pool-size changes. Suspects, not verdicts.
// 3. DEPENDENCY LATENCIES FIRST (cheapest to rule out): DB query timings, external
//    API latencies from telemetry, DURING peak vs before the release. If checkout's
//    DB calls doubled, the C# investigation is over before it starts.
// 4. VITALS during peak, old vs new (canary or rollback window if you have one):
//    %GC time + gen2/LOH counts   → new allocation pattern (e.g. per-request buffer)?
//    ThreadPool queue length      → new blocking call under load?
//    Lock contention counters     → new shared state?
//    Connection pool wait times   → pool now undersized for the new call pattern?
// 5. ONLY THEN profile: dotnet-trace on a peak-hour instance, flame-graph diff
//    against a baseline trace. The "evening peak only" detail says: the defect is
//    LOAD-DEPENDENT (queueing/contention/GC), so any profile taken at 2pm with no
//    load is worthless — measure in the condition where the symptom lives.
// 6. Confirm cause by REVERSING it (rollback/canary the one suspect commit) before
//    writing the fix. Correlation from steps 1–5, causation from step 6.
6 (Hard): A JSON-lines ingest loop processes 500MB files: for each line it does line.Split(','), builds a DTO, and adds to a List that's returned at the end. Memory peaks at 3GB and %GC hits 30%. Rework the design (streaming + spans + pooling) and say what you'd measure to prove each change.
Solution
// THREE compounding problems:
// 1. Whole-result List → 500MB of DTOs live simultaneously (plus List growth copies).
// 2. Split per line → string[] + N strings per line = gigabytes of gen0 churn.
// 3. Returning everything forces the caller to also hold everything.

// REWORK — stream end to end (IAsyncEnumerable), parse with spans, never hold the file:
public async IAsyncEnumerable<Order> IngestAsync(string path,
    [EnumeratorCancellation] CancellationToken ct = default)
{
    using var reader = new StreamReader(path);
    string? line;
    while ((line = await reader.ReadLineAsync(ct)) is not null)
    {
        var s = line.AsSpan();
        int c1 = s.IndexOf(',');
        int c2 = s[(c1 + 1)..].IndexOf(',') + c1 + 1;
        yield return new Order(                       // ONE object per line lives
            Id:     long.Parse(s[..c1]),              //   only as long as the consumer
            Sku:    s[(c1 + 1)..c2].ToString(),       //   needs it
            Amount: decimal.Parse(s[(c2 + 1)..]));
    }
}
// Consumer batches to the DB (threading.html Ex 6) instead of collecting.

// PROOF PER CHANGE (measure one change at a time):
// streaming:   peak working set 3GB → ~flat (dotnet-counters GC Heap Size)
// span parse:  allocation rate (B/s) and Gen0 collections/s — expect ~10× drop;
//              BenchmarkDotNet on ParseLine: B/op before/after
// end to end:  total ingest wall time + %GC (30% → single digits target)
// If Sku strings still dominate allocations: string-intern/pool repeated SKUs —
// but only if the profiler says they matter (rule: every fix ships with its receipt).

🎯 Key Takeaways

  • Method over heroics: counters → profile → fix the named hotspot → re-measure. The hierarchy is architecture → algorithm → allocations → micro; most tickets die in the first two tiers.
  • Benchmark with BenchmarkDotNet (Release, warmed, isolated, [MemoryDiagnoser]); Stopwatch-in-Debug measures the JIT, not your code. Microbenchmarks answer "which is faster", load tests answer "is the service faster".
  • Allocations are half of .NET performance: B/op × ops/s = GC tax on the whole process; watch P95/P99, because tails are where GC pauses and contention live.
  • Tiered compilation + PGO reward warm services and straightforward code — small inlinable methods, sealed types, simple loops; benchmark steady state.
  • Deployment axis: JIT for steady-state throughput, ReadyToRun for cheaper cold starts with full compatibility, NativeAOT for millisecond starts and tiny footprints at the price of runtime codegen — source generators are the AOT-era replacement for reflection.
  • Every optimization ships with its receipt: the before/after benchmark or load-test numbers in the PR.
  • Debug builds and attached debuggers disable JIT optimisation.
  • A benchmark must use its result, or the work may be eliminated.
  • Benchmark with realistic input sizes and shapes.
  • Report variance, not a single number.
  • Scope a slowdown by endpoint, percentile and start time before profiling.
  • Rule out slow dependencies first; they are the cheapest suspect.
  • Low CPU with high latency means the process is waiting, not working.
  • Methods start at tier 0 and are recompiled after about 30 calls.
  • Dynamic PGO devirtualises call sites based on the types it observes.
  • Services run slower just after a deploy until hot code tiers up.
  • ReadyToRun speeds startup without giving up the JIT.
  • Trim warnings are run-time failures reported early.
