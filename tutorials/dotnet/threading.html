Threads, Parallelism & Synchronization Async & Concurrency

What you'll master: the layer beneath async — threads and the thread pool; CPU-bound parallelism (Parallel, PLINQ); what a race condition actually is at the hardware level; the synchronization toolbox (lock, Interlocked, ReaderWriterLockSlim); the concurrent collections; and deadlock — how to create one, recognize one, and design them away. Prerequisites: async/await (this lesson is the CPU-bound counterpart) and Collections (we make them thread-safe here). Async handles waiting; threads handle working. Mid/senior interviews probe whether you know which is which — and what happens when two threads touch one variable.

Part 1 — Threads & the Thread Pool: The Resource Model

// A thread = an OS scheduling unit + ~1MB reserved stack + kernel bookkeeping.
// Creating one costs ~milliseconds. That's why .NET pools them:
// ThreadPool: pre-warmed worker threads that execute queued work items.
// Task.Run queues to it; ASP.NET runs requests on it; await continuations resume on it.

// You almost NEVER 'new Thread(...)' anymore. The one legitimate case: a dedicated,
// very-long-running loop you don't want occupying a pool worker:
var t = new Thread(ConsumeForever) { IsBackground = true };   // background = doesn't
t.Start();                                                    // block process exit

// Task.Run — CPU offload onto the pool (the 99% case):
var summary = await Task.Run(() => Summarize(hugeText), ct);
// WHERE it belongs: client apps (keep UI thread free) and genuinely CPU-heavy server
// work you deliberately shift. NOT around I/O (async-await.html Part 6).

// Pool sizing intuition: for CPU-bound work, ~1 busy thread per core is optimal.
// MORE threads than cores doing CPU work = context-switch overhead, cache thrashing —
// slower, not faster. (For waiting, the answer was: don't hold threads at all — async.)
Console.WriteLine(Environment.ProcessorCount);     // your parallelism budget

Part 2 — Data Parallelism: Parallel.For/ForEach & PLINQ

// CPU-bound work over many items → split across cores:
Parallel.ForEach(images, new ParallelOptions
    { MaxDegreeOfParallelism = Environment.ProcessorCount, CancellationToken = ct },
    img => ApplyFilter(img));        // blocks until ALL done; partitions work per core

Parallel.For(0, matrix.Length, i => row[i] = Compute(matrix[i]));

// PLINQ — LINQ, but partitioned across cores:
var primes = numbers.AsParallel()
                    .Where(IsPrime)              // each partition filters on its own core
                    .ToArray();                  // ⚠ result ORDER not guaranteed —
var ordered = numbers.AsParallel().AsOrdered()   //   AsOrdered() restores it (some cost)
                     .Where(IsPrime).ToArray();

// WHEN parallel pays: per-item work is substantial (μs+, not ns) and items are
// independent. Parallelizing x => x * 2 over 1000 ints is SLOWER than a loop —
// partitioning/coordination overhead swamps the work. Measure (performance-aot.html).

// THE TRAP that defines this topic — shared mutable state:
long total = 0;
Parallel.ForEach(orders, o => total += o.Amount);   // ❌ WRONG ANSWER, RANDOMLY
// total += is read-modify-write: two threads read 100, both add, one update LOST.
// FIXES, best first:
// 1. Don't share: thread-local accumulate, merge once at the end:
Parallel.ForEach(orders,
    () => 0L,                                   // per-thread init
    (o, _, sub) => sub + o.Amount,              // accumulate privately (no contention)
    sub => Interlocked.Add(ref total, sub));    // merge N times total, not N-million
// 2. Or just: orders.Sum(o => o.Amount) — sequential is often fast enough. Check first.
Parallel vs async vs concurrent — the interview-clean definitions. Concurrency = dealing with many things in progress at once (structure). Parallelism = literally executing on multiple cores at the same instant (hardware). Async = not holding a thread while waiting (resource efficiency). A web server is concurrent (thousands of requests in flight) and asynchronous (threads released during I/O) but each request is mostly not parallel. Image processing is parallel. You can be concurrent without parallel (one core, interleaved) and parallel without async (Parallel.ForEach of pure CPU).

Part 3 — Race Conditions: What Actually Goes Wrong

// count++ is THREE operations: load count → add 1 → store. Two threads interleave:
//   T1 loads 5        T2 loads 5        T1 stores 6       T2 stores 6   ← one ++ LOST
int count = 0;
Parallel.For(0, 100_000, _ => count++);
Console.WriteLine(count);        // 61,847? 73,210? — different every run, never 100,000

// Fix 1 — Interlocked: hardware-level atomic instructions. Cheapest, for single ops:
Interlocked.Increment(ref count);                 // atomic ++
Interlocked.Add(ref total, amount);               // atomic +=
Interlocked.CompareExchange(ref state, newV, expectedV);   // atomic compare-and-swap —
// the primitive lock-free algorithms are built from (returns what it saw).

// Fix 2 — lock: mutual exclusion for MULTI-step invariants:
private readonly object _sync = new();            // dedicated private lock object
lock (_sync)
{
    if (_balance >= amount)                       // check and act must be ATOMIC —
        _balance -= amount;                       // Interlocked can't span two steps
}
// lock = Monitor.Enter/Exit + memory barriers. Uncontended cost: ~20ns (cheap!).
// Contended: threads QUEUE — your parallel code becomes sequential at the lock.
// Rules: lock on a private readonly object (never 'this', never a string, never a Type);
// hold locks BRIEFLY; never call unknown/virtual code while holding one; never lock
// across an await (async-patterns.html — SemaphoreSlim for that).

// Fix 3 — don't share: immutable data (records-structs.html), thread-local, or
// message passing (Channels). The best synchronization is none to need.
// volatile / memory-model footnote: without a lock or Interlocked, one thread's write
// may not be VISIBLE to another (caches, reordering). lock/Interlocked insert the
// barriers that publish changes — another reason "it works without the lock" is luck.

Part 4 — The Concurrent Collections

// Regular collections CORRUPT under concurrent mutation (Dictionary can infinite-loop
// on a torn resize). The thread-safe family:
ConcurrentDictionary<K,V>   // the workhorse — fine-grained striped locking + lock-free reads
ConcurrentQueue<T>          // lock-free FIFO       ConcurrentStack<T> — lock-free LIFO
ConcurrentBag<T>            // unordered, per-thread-local lists (producer==consumer fast)
BlockingCollection<T>       // blocking producer/consumer (sync threads; Channels for async)

var cache = new ConcurrentDictionary<string, User>();
cache.TryAdd(id, user);                          // false if present (no throw)
cache.TryGetValue(id, out var u);
cache.AddOrUpdate(id, addFn, (key, old) => Merge(old));   // atomic upsert
var v = cache.GetOrAdd(id, key => LoadUser(key));         // atomic get-or-create... almost:

// ⚠ SUBTLETY every senior answer includes: the FACTORY is called OUTSIDE the lock.
// Two racing threads may BOTH run LoadUser(key); one result wins, both callers get
// the winner. Fine for cheap/idempotent factories. For expensive ones, the
// Lazy trick makes creation once-only:
var lazyCache = new ConcurrentDictionary<string, Lazy<User>>();
var user = lazyCache.GetOrAdd(id,
    key => new Lazy<User>(() => LoadUser(key))).Value;
// Racers may create two Lazy wrappers (cheap), but .Value runs LoadUser ONCE.
// (Async version: Lazy<Task<User>> — async-patterns.html Part 5.)

// Enumeration is SAFE but a moving snapshot — no lock, may reflect concurrent edits.
// Count/Keys/Values momentarily coordinate — don't poll .Count in hot loops.

Part 5 — Deadlock: The Four Conditions and the Two Cures

// Deadlock = circular wait. The canonical two-lock recipe:
//   T1: lock(A) ... wants B          T2: lock(B) ... wants A       → both wait forever
object a = new(), b = new();
// Thread 1:  lock (a) { Thread.Sleep(50); lock (b) { } }
// Thread 2:  lock (b) { Thread.Sleep(50); lock (a) { } }   // hangs, no exception, ever

// CURE 1 — LOCK ORDERING: all code acquires locks in one global order (A before B,
// e.g. by account ID). A cycle becomes impossible:
public void Transfer(Account x, Account y, decimal amt)
{
    var (first, second) = x.Id < y.Id ? (x, y) : (y, x);   // canonical order
    lock (first.Sync) lock (second.Sync)
    { x.Balance -= amt; y.Balance += amt; }
}

// CURE 2 — DON'T HOLD TWO LOCKS: redesign so each critical section needs one lock
// (coarser lock, message passing, or lock-free). Fewer locks > cleverer locks.

// Detection in production: the app is ALIVE but requests hang; CPU near zero.
// Capture a dump → parallel stacks → two threads each inside Monitor.Enter waiting
// on the lock the other holds. (The async flavor — .Result under a UI context — is
// the same circular wait with a SynchronizationContext instead of a second lock.)

// Honorable mentions:
// ReaderWriterLockSlim — many concurrent readers, exclusive writers; wins only when
//   reads are long + frequent (uncontended 'lock' is cheap — measure before upgrading).
// SemaphoreSlim(N) — at most N in a region (throttle; also the async lock).
// Barrier / CountdownEvent — phase coordination in specialized parallel algorithms.

Interview Questions

Q1 (Beginner): When do you use Task.Run vs plain await?

await (without Task.Run) is for I/O-bound work — the operation is naturally asynchronous and holds no thread while waiting. Task.Run is for CPU-bound work you want off the current thread: it queues the delegate to the thread pool. In a desktop app, await Task.Run(() => Crunch()) keeps the UI responsive during computation. In ASP.NET, wrapping I/O in Task.Run is an anti-pattern — the request is already on a pool thread, so you just burn a second thread; and even CPU offload rarely helps there since you're trading the same pool's capacity.

Q2 (Beginner): What is a race condition? Why does counter++ from two threads lose increments?

A race condition is when correctness depends on the timing/interleaving of threads. counter++ compiles to load-add-store — three steps. If thread A and thread B both load 5, both compute 6, and both store 6, one increment is lost; over 100k parallel iterations the final count is a different wrong number each run. Fixes: make the operation atomic (Interlocked.Increment), serialize access (lock), or restructure so threads don't share the variable (per-thread accumulation merged at the end — usually fastest).

Q3 (Mid): lock vs Interlocked vs SemaphoreSlim — when is each the right tool?

Interlocked: single atomic operations on a numeric/reference field (increment, add, compare-and-swap) — cheapest, hardware-level, but can't protect multi-step logic. lock: mutual exclusion for compound invariants (check-then-act, updating two fields together) — cheap uncontended (~tens of ns), serializes under contention; must not contain await. SemaphoreSlim: (a) as (1,1), the async-compatible mutex — WaitAsync doesn't block a thread and release isn't thread-affine; (b) as (N), a concurrency throttle admitting N at once. Rule of thumb: single field → Interlocked; sync invariant → lock; anything async or a throttle → SemaphoreSlim.

Q4 (Mid): Does ConcurrentDictionary.GetOrAdd guarantee the value factory runs only once per key? Consequences and fix?

No. The add is atomic (exactly one value wins and is stored) but the factory executes outside any lock — two threads racing on the same missing key may both invoke it; the loser's result is discarded. For cheap or idempotent factories that's fine. If the factory is expensive (DB call) or side-effecting (creates a connection, increments a metric), duplicates hurt. Fix: store Lazy<V> — GetOrAdd(key, k => new Lazy<V>(() => Load(k))).Value. Racers may build two cheap Lazy wrappers, but only the stored winner's .Value executes Load, exactly once (the async variant uses Lazy<Task<V>>).

Q5 (Senior): Two service endpoints intermittently hang forever in production; CPU is near zero. Walk through diagnosis and the likely fix.

Hanging-not-crashing with idle CPU points at a circular wait: either a classic two-lock deadlock or sync-over-async under a context. Diagnosis: capture a process dump during the hang (dotnet-dump collect), inspect parallel stacks — a lock deadlock shows two threads each blocked in Monitor.Enter, and cross-referencing which locks are held (dumpheap sync blocks / !syncblk) reveals the cycle: thread 1 holds lock A wants B, thread 2 holds B wants A. The two endpoints will map to code paths that acquire the same pair of locks in opposite orders — e.g. transfer(x→y) vs transfer(y→x). Fix: impose a canonical acquisition order (sort by resource ID before locking), or restructure to never hold two locks (single coarser lock, or queue the operation to a single-writer channel). Then add a regression test that exercises both orders concurrently.

Q6 (Senior): You must process 10M records: parse (CPU), enrich via an API (I/O), write to DB (I/O). Design the pipeline — what's parallel, what's async, what's bounded?

Match each stage to its resource. Structure it as a pipeline with bounded channels between stages so backpressure flows end-to-end. Stage 1, parse (CPU-bound): Parallel.ForEach /parallel workers with degree ≈ core count, reading from the source, writing parsed records to a bounded Channel. Stage 2, enrich (I/O-bound): N async workers (no extra threads) consuming the channel, each awaiting the API, concurrency bounded by a semaphore/worker count sized to the API's rate limit — not core count, which is irrelevant for waiting. Stage 3, DB write: async workers batching records (e.g. 1,000 per bulk insert) with concurrency sized to the DB connection pool. Bounded channels mean a slow DB stalls enrichment, which stalls parsing — memory stays flat instead of ballooning. Add cancellation flowing to all stages, per-record error isolation with a dead-letter sink, and metrics on each channel's depth to see which stage is the bottleneck (deepest queue feeds the slowest stage).

🏋️ Graded Exercises

1 (Easy): Sum the squares of 1..10,000,000 with PLINQ, then explain when the sequential version would be preferable.
Solution
long sum = ParallelEnumerable.Range(1, 10_000_000)
    .Sum(n => (long)n * n);          // PLINQ partitions across cores; Sum merges safely

// Sequential preference: if this runs INSIDE an already-parallel context (a web server
// handling many requests — parallelizing each request steals cores from the others),
// or when per-item work is this tiny, sequential may win outright: benchmark both.
// (long)n * n — note the cast BEFORE multiply: int*int overflows at n ≈ 46,341.
2 (Easy): This parallel word counter prints a different number each run. Fix it two ways. 
int words = 0;
Parallel.ForEach(files, f => words += CountWords(f));
Solution
// Race: += is load-add-store; parallel updates lose increments.

// FIX 1 — Interlocked (single atomic op):
int words = 0;
Parallel.ForEach(files, f => Interlocked.Add(ref words, CountWords(f)));

// FIX 2 — thread-local accumulation (better: zero contention during the loop):
int words = 0;
Parallel.ForEach(files,
    () => 0,                                   // per-thread subtotal
    (f, _, sub) => sub + CountWords(f),        // no shared state touched
    sub => Interlocked.Add(ref words, sub));   // one merge per thread
// FIX 2 scales better when files are many and CountWords is fast — Interlocked on
// every item creates cache-line contention; thread-local touches shared state
// only once per worker.
3 (Medium): Implement a thread-safe BankAccount with Deposit, Withdraw (fails on insufficient funds), and Balance. Explain why Interlocked alone can't implement Withdraw.
Solution
public class BankAccount
{
    private readonly object _sync = new();      // private, readonly, dedicated
    private decimal _balance;

    public decimal Balance { get { lock (_sync) return _balance; } }

    public void Deposit(decimal amount)
    {
        ArgumentOutOfRangeException.ThrowIfNegative(amount);
        lock (_sync) _balance += amount;
    }

    public bool Withdraw(decimal amount)
    {
        ArgumentOutOfRangeException.ThrowIfNegative(amount);
        lock (_sync)
        {
            if (_balance < amount) return false;   // CHECK...
            _balance -= amount;                    // ...THEN ACT — one atomic region
            return true;
        }
    }
}
// Interlocked can make the subtraction atomic, but Withdraw's invariant spans TWO
// steps: "only subtract if sufficient funds". Between an unlocked check and an
// Interlocked subtract, another thread can withdraw — balance goes negative.
// check-then-act ⇒ mutual exclusion (lock), not per-op atomicity.
// (Also: Interlocked has no decimal overload — but that's incidental; the invariant
// is the real reason.)
4 (Medium): Build a thread-safe memoizing cache GetOrCompute(key) where an expensive Compute runs at most once per key, even under races.
Solution
public class Memoizer<TKey, TValue> where TKey : notnull
{
    private readonly ConcurrentDictionary<TKey, Lazy<TValue>> _cache = new();
    private readonly Func<TKey, TValue> _compute;

    public Memoizer(Func<TKey, TValue> compute) => _compute = compute;

    public TValue GetOrCompute(TKey key) =>
        _cache.GetOrAdd(key, k => new Lazy<TValue>(
            () => _compute(k),
            LazyThreadSafetyMode.ExecutionAndPublication)).Value;
}
// Why the Lazy wrapper: GetOrAdd's factory may run concurrently for the same key,
// but only ONE Lazy instance is stored; every caller then awaits that instance's
// .Value, and ExecutionAndPublication guarantees _compute executes exactly once.
// Racers waste only a Lazy allocation, never a Compute.
// Caveat: a thrown Compute is CACHED by the Lazy (rethrown to all callers) —
// remove the entry on failure if retry-on-next-call is wanted.
5 (Hard): This transfer code deadlocks under load. Show the interleaving that hangs it, then fix it without removing concurrency. 
public void Transfer(Account from, Account to, decimal amt) {
    lock (from.Sync) {
        lock (to.Sync) {
            from.Balance -= amt; to.Balance += amt;
        }
    }
}
Solution
// DEADLOCK INTERLEAVING (accounts A and B, concurrent opposite transfers):
//   T1: Transfer(A, B) → locks A.Sync           T2: Transfer(B, A) → locks B.Sync
//   T1: wants B.Sync (held by T2) — waits       T2: wants A.Sync (held by T1) — waits
//   Circular wait. Both hang forever; no exception, CPU idle.

// FIX — global lock ordering: acquire in a canonical order (by stable ID),
// so a cycle cannot form:
public void Transfer(Account from, Account to, decimal amt)
{
    if (ReferenceEquals(from, to)) return;                 // self-transfer guard
    var (first, second) = from.Id.CompareTo(to.Id) < 0
        ? (from, to) : (to, from);                          // SAME order for everyone
    lock (first.Sync)
    lock (second.Sync)
    {
        if (from.Balance < amt) throw new InvalidOperationException("Insufficient funds");
        from.Balance -= amt;
        to.Balance += amt;
    }
}
// T1 and T2 now both try first=min(A,B): one wins both locks, the other waits its
// turn — serialized per account-pair, still concurrent across unrelated accounts.
// (Alternative architecture: route transfers through a single-writer Channel per
// account shard — no multi-lock regions at all.)
6 (Hard): Build the 3-stage pipeline from Q6 in miniature: parse strings to ints (CPU), "enrich" via an async lookup (I/O, max 4 concurrent), and batch-write results (batches of 10) — bounded end to end, with clean shutdown.
Solution
var parsed   = Channel.CreateBounded<int>(100);
var enriched = Channel.CreateBounded<string>(100);

// STAGE 1 — parse (CPU; parallel producers) then complete the channel:
var parseStage = Task.Run(async () =>
{
    await Parallel.ForEachAsync(rawLines,
        new ParallelOptions { MaxDegreeOfParallelism = Environment.ProcessorCount },
        async (line, _) =>
        {
            if (int.TryParse(line, out var n))
                await parsed.Writer.WriteAsync(n);      // awaits when full → backpressure
        });
    parsed.Writer.Complete();
});

// STAGE 2 — enrich (I/O; 4 async workers, no extra threads):
var enrichStage = Task.WhenAll(Enumerable.Range(0, 4).Select(async _ =>
{
    await foreach (var n in parsed.Reader.ReadAllAsync())
        await enriched.Writer.WriteAsync(await LookupAsync(n));
})).ContinueWith(_ => enriched.Writer.Complete());

// STAGE 3 — batch write (batches of 10):
var writeStage = Task.Run(async () =>
{
    var batch = new List<string>(10);
    await foreach (var item in enriched.Reader.ReadAllAsync())
    {
        batch.Add(item);
        if (batch.Count == 10) { await WriteBatchAsync(batch); batch.Clear(); }
    }
    if (batch.Count > 0) await WriteBatchAsync(batch);   // FLUSH the remainder
});

await Task.WhenAll(parseStage, enrichStage, writeStage);
// Shutdown cascade: source ends → parsed completes → workers drain → enriched
// completes → writer flushes and exits. Bounded(100) everywhere: a slow DB stalls
// the whole pipeline instead of buffering 10M items in RAM.
// ponytail: ContinueWith for completion is terse but adequate here; a wrapper
// try/finally per stage is the upgrade if stages can fault mid-stream.

🎯 Key Takeaways

  • Threads are for working, async is for waiting: Task.Run/Parallel for CPU-bound, await for I/O — and CPU parallelism beyond core count only adds overhead.
  • Parallel.ForEach/PLINQ split independent work across cores; the enemy is shared mutable state — prefer thread-local accumulation merged once over per-item synchronization.
  • Races come from non-atomic read-modify-write: Interlocked for single ops, lock (private readonly object, held briefly) for multi-step invariants like check-then-act.
  • ConcurrentDictionary et al. keep structure safe, but GetOrAdd factories can race — the Lazy<V> wrapper makes creation exactly-once.
  • Deadlock is circular wait: prevent it with global lock ordering or single-lock designs; diagnose hangs with dumps and parallel stacks, not guesswork.
  • Compose systems as bounded pipelines (parallel CPU stages, async I/O stages, channels between) so backpressure, not memory growth, absorbs slow stages.
