Testing with xUnit Professional .NET

What you'll master: xUnit as the .NET default — facts, theories, fixtures, and lifecycle; writing tests that survive refactoring (test behavior through public APIs, not implementation details); test doubles done judiciously — hand-rolled fakes vs NSubstitute/Moq, and when mocking is the wrong tool; async and exception testing; integration testing with WebApplicationFactory and Testcontainers; and the strategy layer — what to test, what not to, and how a test suite earns (or loses) a team's trust. Prerequisites: DI & Hosting (DI is what makes substitution possible), EF Core (the InMemory-provider lesson carries straight in), async/await. Tests are a design pressure: hard-to-test code is telling you something about the code, not about testing.

Part 1 — xUnit Mechanics: Facts, Theories, Lifecycle

// dotnet new xunit ; dotnet test
public class PriceCalculatorTests
{
    // [Fact] — a single case. Name = the BEHAVIOR, readable as a sentence in failures:
    [Fact]
    public void Bulk_discount_applies_at_ten_units()
    {
        var calc = new PriceCalculator();                       // Arrange
        var total = calc.Total(unitPrice: 10m, quantity: 10);   // Act
        Assert.Equal(90m, total);                               // Assert (10% off)
    }

    // [Theory] — one test, many cases. Boundaries make the BEST rows:
    [Theory]
    [InlineData(1,  10)]     // no discount
    [InlineData(9,  90)]     // just below the threshold ← boundary
    [InlineData(10, 90)]     // exactly at it            ← boundary
    [InlineData(100, 850)]   // next tier
    public void Total_applies_tiered_discounts(int qty, decimal expected)
        => Assert.Equal(expected, new PriceCalculator().Total(10m, qty));
    // [MemberData]/[ClassData] feed complex objects when InlineData's constants
    // (compile-time only) can't express them.

    // LIFECYCLE — xUnit's sharpest difference from JUnit/NUnit:
    // a NEW test-class INSTANCE per test method. The constructor IS your setup,
    // IDisposable.Dispose IS your teardown — no [SetUp]/[TearDown] attributes,
    // and instance fields CANNOT leak state between tests. Isolation by construction.
}

// SHARED (expensive) state — explicit, not accidental:
public class DbFixture : IAsyncLifetime { /* start Testcontainer, migrate */ }
public class OrderTests : IClassFixture<DbFixture>      // ONE fixture per class
{
    public OrderTests(DbFixture fx) { ... }             // injected into each instance
}
// [Collection("db")] shares one fixture across MULTIPLE classes (one container for
// the whole suite — efcore.html Ex 6). Classes in a collection run sequentially;
// separate collections run in parallel — know this when tests share a database.

Part 2 — Assertions That Fail Usefully

Assert.Equal(expected, actual);          // order matters — failure says exp/act correctly
Assert.Equal(0.333m, result, precision: 3);   // decimals/doubles: never raw == on floats
Assert.True(order.IsValid);              // ⚠ failure says "Expected: True" — USELESS.
                                         // Prefer an assert that shows the DATA:
Assert.Empty(order.ValidationErrors);    // failure prints the actual errors. Better.

// Collections:
Assert.Contains(item, list);             Assert.All(orders, o => Assert.True(o.Total > 0));
Assert.Equivalent(expectedDto, actualDto);   // structural comparison, ignores ref identity

// EXCEPTIONS — assert the type AND the interesting details:
var ex = Assert.Throws<OutOfStockException>(() => cart.Add(sku, 999));
Assert.Equal(sku, ex.Sku);
// Async version (never .Result in tests — async-await.html rules apply here too):
await Assert.ThrowsAsync<OrderNotFoundException>(() => svc.ShipAsync(badId));

// One BEHAVIOR per test — not one assert per test. Three asserts that together
// describe "a placed order is persisted, priced, and confirmed" are one behavior.
// Two unrelated scenarios sharing a test = two tests hiding in one failure report.

Part 3 — Test Doubles: Fakes First, Mocks Deliberately

// The seam is DI (di-hosting.html): the subject takes interfaces; tests hand it doubles.

// HAND-ROLLED FAKE — a real, tiny implementation. Often the best double:
public class InMemoryOrderRepository : IOrderRepository
{
    public readonly Dictionary<Guid, Order> Saved = new();
    public Task SaveAsync(Order o, CancellationToken ct = default)
    { Saved[o.Id] = o; return Task.CompletedTask; }
    public Task<Order?> FindAsync(Guid id, CancellationToken ct = default)
        => Task.FromResult(Saved.GetValueOrDefault(id));
}
// Fakes shine because they have BEHAVIOR: save-then-find works, tests read like
// prose, and refactoring internal call patterns doesn't break them.

// MOCKING LIBRARY (NSubstitute here; Moq is equivalent) — for stubbing awkward
// edges and VERIFYING interactions that ARE the requirement:
var gateway = Substitute.For<IPaymentGateway>();
gateway.ChargeAsync(Arg.Any<Payment>()).Returns(PaymentResult.Declined("insufficient"));

var svc = new CheckoutService(new InMemoryOrderRepository(), gateway);
var result = await svc.CheckoutAsync(cart);

Assert.Equal(CheckoutStatus.PaymentFailed, result.Status);
await gateway.Received(1).ChargeAsync(Arg.Is<Payment>(p => p.Amount == cart.Total));
// Verifying the charge happened once with the right amount IS the behavior here —
// money moved. That's a legitimate interaction assertion.

// THE LINE: verify interactions that are OBSERVABLE REQUIREMENTS (charged the
// gateway, sent the email, published the event). Do NOT verify incidental plumbing
// ("repository.FindAsync was called before SaveAsync") — those tests break on
// every refactor while catching nothing. Over-mocked suites are how teams end up
// with 4,000 green tests and no confidence.
Hard-to-test is a design smell, not a testing problem. If you need five mocks to construct the subject, the class has five reasons to change. If you can't test time-dependent logic, inject a clock (TimeProvider — di-hosting.html Ex 1). If static calls block substitution, wrap them behind an interface you own. The fix is in the production code's shape; reaching for ever-more-powerful mocking (statics, privates, reflection) treats the symptom and cements the design.

Part 4 — Integration Tests: WebApplicationFactory & Real Dependencies

// Unit tests prove logic; integration tests prove the WIRING: routing, DI,
// middleware, serialization, EF + real SQL. ASP.NET Core makes this first-class:
public class ApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;
    public ApiTests(WebApplicationFactory<Program> factory)
    {
        _client = factory.WithWebHostBuilder(b =>
            b.ConfigureServices(services =>
            {
                // swap ONLY the true externals — keep the app's real wiring:
                services.RemoveAll<IPaymentGateway>();
                services.AddScoped<IPaymentGateway, FakeGateway>();
                // point EF at the Testcontainer DB (efcore.html Ex 6), NOT InMemory
            })).CreateClient();       // in-memory server — no ports, no network
    }

    [Fact]
    public async Task Post_order_returns_201_and_persists()
    {
        var resp = await _client.PostAsJsonAsync("/orders", new { Sku = "X", Qty = 2 });

        Assert.Equal(HttpStatusCode.Created, resp.StatusCode);
        var created = await resp.Content.ReadFromJsonAsync<OrderDto>();
        Assert.NotNull(resp.Headers.Location);          // the contract, end to end:
        Assert.Equal(2, created!.Qty);                  // routing → validation → handler
    }                                                   // → EF → real SQL → serialization
}
// This one test exercises what a dozen mocked unit tests can only assume.

// THE PYRAMID, honestly: many fast unit tests (pure logic: pricing, validation,
// parsing) → a solid layer of integration tests (each endpoint's happy path +
// key failures, against real SQL) → a few E2E smoke tests. The classic failure
// mode is the INVERSE: mob of brittle mocked tests + zero integration coverage =
// "all green, prod is down". The HttpClient seam (di-hosting.html Ex 5) and
// Testcontainers make the middle layer cheap — use them.

Interview Questions

Q1 (Beginner): Difference between [Fact] and [Theory]? How does xUnit isolate tests?

[Fact] is a single test case; [Theory] is a parameterized test run once per data row ([InlineData] for constants, [MemberData]/[ClassData] for complex objects) — ideal for boundary tables. Isolation: xUnit creates a new instance of the test class for every test method, so the constructor acts as setup, Dispose as teardown, and instance fields can't carry state between tests. Expensive shared resources are opt-in and explicit via IClassFixture<T> (per class) or collections (across classes).

Q2 (Beginner): What's the difference between a unit test and an integration test, and why do you need both?

A unit test exercises a small piece of logic in isolation, with external dependencies replaced by doubles — fast (milliseconds), precise failure localization, great for business rules and boundaries. An integration test exercises real collaboration: HTTP through the actual pipeline, EF against a real database, DI wiring as configured — slower but it proves the parts fit. You need both because they fail differently: unit tests can all pass while the app 500s on every request (mis-registered DI, wrong route, serialization mismatch, SQL constraint) — exactly what integration tests catch; integration tests alone are too slow and coarse to cover every rule boundary. The pyramid: many units, solid middle of integrations, few E2E.

Q3 (Mid): Fake vs stub vs mock — and when is a mocking library the wrong choice?

A fake is a working lightweight implementation (in-memory repository) with real behavior. A stub returns canned answers to make a path executable (gateway that always declines). A mock additionally records calls so the test can verify interactions (Received(1).ChargeAsync(...)). Libraries (Moq/NSubstitute) excel at stubs and requirement-level interaction verification — "we charged the gateway exactly once with the right amount" is a genuine observable behavior. They're the wrong tool when: the double needs behavior (save-then-find coherence — write a fake); the test starts asserting internal choreography (which methods called in what order — refactor-brittle); or you're mocking types you don't own (mock DbContext/HttpClient internals — use the real thing via Testcontainers or a stub HttpMessageHandler instead).

Q4 (Mid): How do you test time-dependent logic like "orders older than 30 days are archived" without flaky tests?

Never let the subject read ambient time. Inject the clock — .NET 8+ ships TimeProvider precisely for this: production registers TimeProvider.System; tests pass a controllable fake (FakeTimeProvider from Microsoft.Extensions.TimeProvider.Testing, or a hand-rolled one) and set the moment explicitly. The test then reads: create an order at T, advance the fake clock 31 days, run the archiver, assert archived; a sibling case advances 29 days and asserts untouched — boundary rows in a theory. The same principle covers all ambient nondeterminism: inject seeded Random, avoid real delays by making the fake clock also drive timers (FakeTimeProvider.Advance fires PeriodicTimer waits synchronously). Tests that Thread.Sleep and hope are flakiness with extra steps.

Q5 (Senior): Your team has 3,800 unit tests, 90% mock-based, and production still breaks weekly on deploys. Diagnose and prescribe.

The suite is testing implementation, not the system. Symptoms to confirm: tests assert mock choreography (breaks on refactor, blind to behavior); every collaborator is mocked, so DI wiring, configuration, serialization, SQL, and migrations — where deploy-time failures actually live — have zero coverage; and likely the InMemory EF provider stands in for the database. Prescription: (1) build the missing middle layer — WebApplicationFactory integration tests per endpoint (happy path + key errors) against Testcontainers SQL, swapping only true externals; these catch the weekly breakage class directly. (2) Stop the bleeding: new tests assert outcomes, interaction verification only for requirement-level effects; delete (don't skip) choreography tests as they break. (3) Add startup smoke: ValidateOnBuild/options ValidateOnStart (di-hosting.html) turns config/DI mistakes into deploy failures. (4) Track escaped-defect causes for a quarter and point new tests at those categories — the data, not ideology, justifies the rebalance to the team.

Q6 (Senior): Design the test strategy for the checkout flow: cart → payment gateway (external) → order persistence → confirmation email. Be specific about layers and doubles.

Unit layer (fast, exhaustive): pricing/discount/tax rules as pure functions with boundary-table theories; checkout orchestration with a hand-rolled in-memory repository fake + stubbed gateway, covering outcomes per gateway response (approved → order Placed; declined → PaymentFailed, no order persisted; gateway timeout → retriable state) and verifying the two requirement-level interactions: charged exactly once with the cart total, email enqueued on success only. Integration layer: WebApplicationFactory + Testcontainers Postgres — POST /checkout happy path (201, order row exists with correct totals, outbox/email record written), declined-payment path (4xx, no order row), idempotency (same request twice = one charge — the money bug), and concurrency-token behavior on stock (efcore.html Ex 3). The real gateway is faked at the IPaymentGateway seam; its HTTP client gets contract tests against the provider's sandbox in a separate, non-blocking pipeline (sandbox flakiness must not gate deploys). E2E: one smoke test in staging post-deploy hitting the full path with a test card. Explicitly untested: the gateway's internals (theirs), email rendering pixel-perfection (snapshot test at most). The structure mirrors risk: money and persistence get the density.

🏋️ Graded Exercises

1 (Easy): Test this with a boundary-focused theory: public static string Grade(int score) => score >= 90 ? "A" : score >= 80 ? "B" : score >= 70 ? "C" : "F"; (0–100 valid).
Solution
public class GradeTests
{
    [Theory]
    [InlineData(100, "A")]   // top edge
    [InlineData(90,  "A")]   // exact threshold ↓ the boundary pairs are the point
    [InlineData(89,  "B")]   // one below
    [InlineData(80,  "B")]
    [InlineData(79,  "C")]
    [InlineData(70,  "C")]
    [InlineData(69,  "F")]
    [InlineData(0,   "F")]   // bottom edge
    public void Grade_maps_score_to_letter(int score, string expected)
        => Assert.Equal(expected, Grader.Grade(score));
}
// Eight rows, six of them hugging thresholds — that's where the >= vs > bugs live.
// (If 0–100 is a real contract, Grade should also throw on -1/101 — and THAT
// deserves two more rows via Assert.Throws. Validate at boundaries: methods.html.)
2 (Easy): This test is broken in three ways. Fix them. 
[Fact]
public void Ship_missing_order_fails() {
    var svc = new ShippingService(_repo);
    try { svc.ShipAsync(Guid.NewGuid()).Result; }
    catch (Exception e) { Assert.True(e != null); }
}
Solution
[Fact]
public async Task Ship_missing_order_throws_OrderNotFound()
{
    var svc = new ShippingService(new InMemoryOrderRepository());   // empty repo = miss

    var ex = await Assert.ThrowsAsync<OrderNotFoundException>(
        () => svc.ShipAsync(Guid.NewGuid()));
    Assert.NotEqual(Guid.Empty, ex.OrderId);
}
// FIX 1: .Result → async Task + await (deadlock-prone and wraps the exception in
//        AggregateException, so the catch was testing the wrong type anyway).
// FIX 2: catch(Exception)+Assert.True(e != null) passes for ANY exception — an NRE
//        from a bug also "passes". ThrowsAsync pins the exact expected type.
// FIX 3: the original would also PASS IF NOTHING THREW... actually worse: it had no
//        assertion on the no-throw path at all. ThrowsAsync FAILS if no exception —
//        the test now actually tests the behavior its name claims.
3 (Medium): Using a fake repository and a stubbed IEmailSender, test that RegisterAsync: saves the user with a normalized email, sends one welcome email, and rejects duplicate emails without sending anything.
Solution
public class RegistrationTests
{
    private readonly InMemoryUserRepository _repo = new();
    private readonly IEmailSender _email = Substitute.For<IEmailSender>();
    private RegistrationService Svc => new(_repo, _email);

    [Fact]
    public async Task Registers_normalizes_and_welcomes()
    {
        await Svc.RegisterAsync("  Ada@Example.COM ");

        var user = Assert.Single(_repo.Saved.Values);          // state via the FAKE
        Assert.Equal("ada@example.com", user.Email);           // normalization behavior
        await _email.Received(1).SendAsync(                    // requirement-level
            "ada@example.com", Arg.Is<string>(s => s.Contains("Welcome")));
    }

    [Fact]
    public async Task Duplicate_email_rejected_and_silent()
    {
        await Svc.RegisterAsync("ada@example.com");
        _email.ClearReceivedCalls();

        await Assert.ThrowsAsync<DuplicateEmailException>(
            () => Svc.RegisterAsync("ADA@example.com"));       // dupe despite casing

        Assert.Single(_repo.Saved.Values);                     // nothing extra saved
        await _email.DidNotReceive().SendAsync(Arg.Any<string>(), Arg.Any<string>());
    }
}
// Division of labor: the fake carries STATE behavior (dupe detection reads what was
// saved); the substitute stubs/verifies the one interaction that IS a requirement
// (the email). No verification of internal call order anywhere — refactor-safe.
4 (Medium): Write the WebApplicationFactory integration test for GET /products/{id}: 200 with the right DTO for an existing product, 404 for a missing one — with test data seeded through the app's own DbContext.
Solution
public class ProductApiTests : IClassFixture<TestAppFactory>
{
    private readonly TestAppFactory _factory;
    public ProductApiTests(TestAppFactory factory) => _factory = factory;
    // TestAppFactory : WebApplicationFactory<Program> — overrides ConfigureServices
    // to point ShopContext at a Testcontainers DB and run migrations (efcore.html Ex 6).

    [Fact]
    public async Task Existing_product_returns_200_with_dto()
    {
        Guid id;                                        // SEED via the app's own context:
        using (var scope = _factory.Services.CreateScope())
        {
            var db = scope.ServiceProvider.GetRequiredService<ShopContext>();

    [Fact]
    public async Task Missing_product_returns_404()
    {
        var resp = await _factory.CreateClient().GetAsync($"/products/{Guid.NewGuid()}");
        Assert.Equal(HttpStatusCode.NotFound, resp.StatusCode);
    }
}
// Seeding through a DI scope uses the real mappings/constraints (no SQL strings to
// drift); unique data per test (fresh Guid/Sku) keeps tests order-independent when
// the container is shared. The 404 test guards the exception-middleware mapping
// from exceptions-nullability.html Part 3 — a wiring behavior units can't see.
5 (Hard): The archiver from di-hosting Ex 3 ("delete sessions older than 30 days, every 15 minutes") must be tested without waiting 15 minutes or touching real time. Restructure for testability and write the tests.
Solution
// RESTRUCTURE: split the SCHEDULE (BackgroundService loop) from the LOGIC —
// the logic becomes a plain, injectable, clock-aware class:
public class SessionArchiver(ShopContext db, TimeProvider clock)
{
    public Task<int> ArchiveAsync(CancellationToken ct = default) =>
        db.Sessions
          .Where(s => s.LastSeenAt < clock.GetUtcNow().AddDays(-30).UtcDateTime)
          .ExecuteDeleteAsync(ct);
}
// The BackgroundService shrinks to: PeriodicTimer + CreateScope + call ArchiveAsync
// — thin enough that the integration suite's smoke coverage suffices.

public class SessionArchiverTests : IClassFixture<DbFixture>   // Testcontainers
{
    [Fact]
    public async Task Deletes_only_sessions_older_than_30_days()
    {
        await using var db = _fx.CreateContext();
        var clock = new FakeTimeProvider(DateTimeOffset.Parse("2026-07-27T00:00:00Z"));
        db.Sessions.AddRange(
            new Session { Id = "old",  LastSeenAt = clock.GetUtcNow().AddDays(-31).UtcDateTime },
            new Session { Id = "edge", LastSeenAt = clock.GetUtcNow().AddDays(-30).UtcDateTime },
            new Session { Id = "new",  LastSeenAt = clock.GetUtcNow().AddDays(-1).UtcDateTime });
        await db.SaveChangesAsync();

        int deleted = await new SessionArchiver(db, clock).ArchiveAsync();

        Assert.Equal(1, deleted);                          // ONLY "old" — strictly <
        var remaining = await db.Sessions.Select(s => s.Id).ToListAsync();
        Assert.Equivalent(new[] { "edge", "new" }, remaining);
    }
}
// Wins: no sleeping, no real time, the exact-30-days boundary is pinned as a
// deliberate decision (<, not <=), and ExecuteDelete runs against REAL SQL so
// the translation is proven. The 15-minute cadence isn't unit-tested at all —
// PeriodicTimer is framework; the schedule earns a staging smoke check instead.
6 (Hard): A teammate's PR adds this test. Review it: list every problem and rewrite it properly. 
[Fact]
public async Task Test1() {
    var repo = Substitute.For<IOrderRepository>();
    var gw = Substitute.For<IPaymentGateway>();
    var log = Substitute.For<ILogger<CheckoutService>>();
    gw.ChargeAsync(Arg.Any<Payment>()).Returns(PaymentResult.Ok());
    var svc = new CheckoutService(repo, gw, log);
    await svc.CheckoutAsync(TestCart());
    Received.InOrder(() => {
        repo.FindAsync(Arg.Any<Guid>());
        gw.ChargeAsync(Arg.Any<Payment>());
        repo.SaveAsync(Arg.Any<Order>());
        log.LogInformation(Arg.Any<string>());
    });
}
Solution
// PROBLEMS:
// 1. Name "Test1" — says nothing; failures are unreadable in CI.
// 2. NO OUTCOME ASSERTED — it never checks the checkout RESULT or the saved order's
//    contents. A CheckoutService that saves a corrupted order still passes.
// 3. Received.InOrder choreography — Find→Charge→Save→Log ORDER is implementation;
//    any refactor (batch the find, log first) breaks the test with zero bugs caught.
// 4. Verifying LOGGING as behavior (and mocking ILogger's extension-method surface
//    is fragile anyway). Logging is diagnostics, not a requirement here.
// 5. Everything mocked incl. the repository → no state behavior; Arg.Any everywhere
//    → even the charge AMOUNT is unchecked.

[Fact]
public async Task Successful_checkout_charges_total_and_persists_placed_order()
{
    var repo = new InMemoryOrderRepository();                  // fake: real state
    var gw = Substitute.For<IPaymentGateway>();
    gw.ChargeAsync(Arg.Any<Payment>()).Returns(PaymentResult.Ok());
    var svc = new CheckoutService(repo, gw, NullLogger<CheckoutService>.Instance);
    var cart = TestCart(total: 129.99m);

    var result = await svc.CheckoutAsync(cart);

    Assert.Equal(CheckoutStatus.Success, result.Status);       // OUTCOME
    var order = Assert.Single(repo.Saved.Values);              // persisted STATE
    Assert.Equal(OrderStatus.Placed, order.Status);
    Assert.Equal(129.99m, order.Total);
    await gw.Received(1).ChargeAsync(                          // the ONE interaction
        Arg.Is<Payment>(p => p.Amount == 129.99m));            // that IS a requirement
}
// Named for the behavior; asserts result + persisted state + the money interaction
// with the amount pinned; logger neutralized with NullLogger (not verified);
// no ordering assertions — the test survives any refactor that keeps the behavior.

🎯 Key Takeaways

  • xUnit isolates by construction: new class instance per test, constructor/Dispose as lifecycle, fixtures for explicit expensive sharing; theories with boundary-hugging rows are your highest-density tests.
  • Test behavior through public APIs — outcomes and state, plus interactions only when they are the requirement (money moved, email sent). Choreography tests break on refactors and catch nothing.
  • Fakes first (real behavior, readable tests), mocking libraries for stubbing edges and requirement-level verification; five mocks to build a subject is a design smell, not a testing chore.
  • The middle layer is where deploy breakage dies: WebApplicationFactory + Testcontainers exercise routing, DI, EF, and real SQL; the EF InMemory provider is not a database.
  • Control ambient inputs — TimeProvider, seeded randomness, awaited async — because flaky tests destroy the suite's authority; fix or delete them fast.
  • Spend tests where risk lives: rules, boundaries, error paths, contracts, and every fixed bug; skip framework behavior, trivia, and privates.
