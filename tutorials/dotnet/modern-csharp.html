Modern C# & Project Idioms Professional .NET

What you'll master: the capstone — how modern C# codebases are actually shaped. The recent language features that changed daily idiom (primary constructors, collection expressions, file-scoped types, interpolated string handlers, required/init-only models); project hygiene (csproj essentials, Directory.Build.props, analyzers, central package management); source generators as the new runtime-reflection replacement; and a final consolidation exercise that assembles the whole track — records, pattern matching, LINQ, async, DI, EF, testing — into one production-shaped feature. Prerequisites: the entire track; this lesson deliberately cross-references earlier lessons instead of re-teaching them. It's the "how it all fits" pass every section capstone promised.

Part 1 — The Idioms That Replaced Older C#

// PRIMARY CONSTRUCTORS (C# 12) — the boilerplate killer you've seen all track:
public class OrderService(IOrderRepository repo, ILogger<OrderService> log)
{                          // parameters are in scope for the whole class body
    public async Task PlaceAsync(Order o)
    {
        log.LogInformation("Placing {OrderId}", o.Id);
        await repo.SaveAsync(o);
    }
}
// vs the old field + ctor + assignment ×N ceremony. Notes: the parameters are
// CAPTURED (not readonly fields) — declare an explicit 'private readonly' field
// from the parameter if you need readonly guarantees or want to expose it.
// For DATA, records' positional form is still the right tool (records-structs.html).

// COLLECTION EXPRESSIONS (C# 12) — one literal syntax for all collection types:
int[] a = [1, 2, 3];
List<string> names = ["ada", "grace"];
Span<byte> buf = [0xFF, 0x00];
int[] merged = [..a, 4, 5, ..b];         // spread — replaces Concat chains
// Empty: [] — replaces new List<T>(), Array.Empty<T>() (and is optimized like it).

// FILE-SCOPED NAMESPACES + GLOBAL USINGS — the modern file header:
namespace Shop.Orders;                    // no braces, whole file — one indent saved
// csproj: <ImplicitUsings>enable</ImplicitUsings> brings System, Linq, Tasks...
// GlobalUsings.cs: global using Shop.Common; — once, project-wide.

// REQUIRED + INIT — models that are valid by construction (types.html, records-structs.html):
public class CreateOrderRequest
{
    public required string Sku { get; init; }         // compiler forces initialization
    public required int Quantity { get; init; }       // init: immutable after creation
    public string? CouponCode { get; init; }          // optional is EXPLICIT (NRT)
}
// new CreateOrderRequest { Sku = "X" }  → compile error: Quantity missing.
// This trio — required, init, string? — is the modern DTO shape: no invalid
// instances, no mutation, honest nullability (exceptions-nullability.html).

// SWITCH EXPRESSIONS + PATTERNS everywhere (pattern-matching.html recap in idiom form):
public static decimal ShippingFee(Order o) => o switch
{
    { Total: >= 100m }                    => 0m,
    { Destination.Country: "US" }         => 5.99m,
    { Items.Count: 1, Weight: < 0.5 }     => 3.49m,
    _                                     => 9.99m,
};

Part 2 — Project Hygiene: The csproj a Senior Ships

<!-- The modern csproj is tiny — SDK defaults do the rest: -->
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net9.0</TargetFramework>
    <Nullable>enable</Nullable>                        <!-- NRT on, always -->
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors> <!-- warnings rot otherwise -->
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
  </PropertyGroup>
</Project>

// DIRECTORY.BUILD.PROPS — settings ONCE for the whole solution (sits at repo root;
// every csproj inherits automatically). Team-wide TFM, NRT, analyzers, version:
//   repo/
//   ├─ Directory.Build.props        ← Nullable, TreatWarningsAsErrors, LangVersion
//   ├─ Directory.Packages.props    ← CENTRAL PACKAGE MANAGEMENT: every package's
//   │                                 version in ONE file; csprojs reference by name
//   │                                 only → no version drift between projects
//   ├─ src/Shop.Api/Shop.Api.csproj
//   └─ tests/Shop.Tests/...
// <PackageVersion Include="xunit" Version="2.9.0" />      (Directory.Packages.props)
// <PackageReference Include="xunit" />                     (any csproj — no version)

// ANALYZERS — the compiler as reviewer:
// .editorconfig carries style + analyzer severities (dotnet_diagnostic.CA1848.severity)
// Built-in .NET analyzers catch real bugs: disposed-twice, async-void, culture-blind
// string ops (strings.html), non-constant logging templates. Turn the meaningful
// ones to 'error' and the build enforces what code review used to argue about.
// dotnet format in CI = zero style comments in PRs ever again.
The senior take on "modern": new syntax is adopted for what it deletes, not for novelty. Primary constructors delete assignment ceremony; collection expressions delete Concat chains; required deletes constructor overloads and runtime null checks; file-scoped namespaces delete an indent level. If a feature makes the diff bigger or the next reader slower, skip it — "compiles on the team's brain" beats "uses C# 13". Set LangVersion once in Directory.Build.props and keep the whole repo on one dialect.

Part 3 — Source Generators: Compile-Time Replaces Runtime Reflection

// The pattern of the AOT era (performance-aot.html): work that reflection did at
// RUNTIME moves to COMPILE TIME. You mostly CONSUME generators — know the big four:

// 1. System.Text.Json — serializers generated per type (no reflection, AOT-safe):
[JsonSerializable(typeof(OrderDto))]

// 2. LOGGING — LoggerMessage generator: zero-allocation structured logging:
public static partial class Log
{

        Message = "Payment declined for {OrderId}: {Reason}")]
    public static partial void PaymentDeclined(ILogger log, Guid orderId, string reason);
}
Log.PaymentDeclined(_log, order.Id, result.Reason);
// vs LogWarning("...", ...): no boxing, no template re-parsing, compile-checked
// argument count/order. The idiom for hot-path logging.

// 3. REGEX — compiled at build, AOT-safe (strings.html):
public static partial class Patterns
{
    [GeneratedRegex(@"^[A-Z]{2}-\d{4}$")]
    public static partial Regex SkuFormat();
}
if (Patterns.SkuFormat().IsMatch(input)) ...

// 4. INTEROP — [LibraryImport] replaces [DllImport]'s runtime marshalling stub.

// HOW they work (one sentence for interviews): a generator is a compiler plugin that
// READS your syntax trees at build time and EMITS additional C# (the 'partial'

Part 4 — Idiomatic Error & Result Shapes

// The track taught exceptions for exceptional paths (exceptions-nullability.html).
// Modern APIs increasingly make EXPECTED failures part of the RETURN TYPE:

// The lightweight in-house Result — a sealed record hierarchy + pattern matching
// (records-structs.html + pattern-matching.html doing what they were built for):
public abstract record CheckoutResult
{
    public sealed record Success(Order Order) : CheckoutResult;
    public sealed record PaymentDeclined(string Reason) : CheckoutResult;
    public sealed record OutOfStock(string Sku) : CheckoutResult;
}

public async Task<IResult> Handle(CheckoutRequest req, CheckoutService svc) =>
    await svc.CheckoutAsync(req) switch
    {
        CheckoutResult.Success s         => Results.Created($"/orders/{s.Order.Id}", s.Order),
        CheckoutResult.PaymentDeclined d => Results.Problem(d.Reason, statusCode: 402),
        CheckoutResult.OutOfStock o      => Results.Conflict(new { o.Sku }),
        _                                => Results.StatusCode(500),
    };
// Every outcome is in the signature; the compiler's exhaustiveness pressure means a
// new outcome type FORCES every call site to decide. Exceptions still cover the
// truly exceptional (DB down) — the two coexist: results for business outcomes,
// exceptions for infrastructure failures. Don't adopt a Result LIBRARY until the
// team feels the need; a record hierarchy is 10 lines and reads like the domain.

Part 5 — Capstone: One Feature, Whole Track

// "Gift cards: purchase creates a card; redemption debits it; balance queryable."
// Watch the lessons compose — each line names its source lesson.

// DOMAIN — records-structs.html, exceptions-nullability.html:
public sealed record GiftCard
{
    public required Guid Id { get; init; }
    public required decimal Balance { get; init; }
    [Timestamp] public byte[] Version { get; init; } = default!;   // efcore.html: token

    public GiftCard Debit(decimal amount) => amount switch        // pattern-matching
    {
        <= 0            => throw new ArgumentOutOfRangeException(nameof(amount)),
        _ when amount > Balance
                        => throw new InsufficientBalanceException(Id, Balance, amount),
        _               => this with { Balance = Balance - amount },   // immutable update
    };
}

// RESULT SHAPE — Part 4:
public abstract record RedeemResult
{
    public sealed record Redeemed(decimal NewBalance) : RedeemResult;
    public sealed record Insufficient(decimal Balance) : RedeemResult;
    public sealed record NotFound : RedeemResult;
}

// SERVICE — di-hosting.html (scoped, ctor injection), efcore.html (tracking,
// concurrency retry), async-await.html (token flows):
public class GiftCardService(ShopContext db, TimeProvider clock)
{
    public async Task<RedeemResult> RedeemAsync(Guid id, decimal amount,
        CancellationToken ct = default)
    {
        for (int attempt = 1; ; attempt++)
        {
            var card = await db.GiftCards.FindAsync([id], ct);
            if (card is null) return new RedeemResult.NotFound();
            try
            {
                var debited = card.Debit(amount);
                db.Entry(card).CurrentValues.SetValues(debited);
                db.Redemptions.Add(new Redemption(id, amount, clock.GetUtcNow()));
                await db.SaveChangesAsync(ct);                    // one transaction
                return new RedeemResult.Redeemed(debited.Balance);
            }
            catch (InsufficientBalanceException e)
            { return new RedeemResult.Insufficient(e.Balance); }  // expected → result
            catch (DbUpdateConcurrencyException) when (attempt < 3)
            { db.ChangeTracker.Clear(); }                         // race → retry
        }
    }
}

// TESTS — testing.html: boundary theories on Debit (0, exact balance, over),
// Testcontainers integration on RedeemAsync (concurrent redemptions can't
// overspend — the efcore.html Ex 3 pattern), FakeTimeProvider pins timestamps.
// The point of the capstone: NOTHING here is new. Mastery of a stack is exactly
// this — familiar pieces composing without friction.

Part 6 — Modernising a Legacy Codebase Without a Rewrite

// Most seniors inherit C# 7 on .NET Framework, not a greenfield .NET 9 app.
// The job: get the benefits of Parts 1–5 INCREMENTALLY, with the build green daily.

// STEP 1 — SDK-style projects first: no behaviour change, a large hygiene win.
//   Convert verbose old .csproj files to SDK style and packages.config to
//   PackageReference; Microsoft's migration tooling automates most of it.

// STEP 2 — multi-target shared libraries so both worlds can consume them:
<TargetFrameworks>net48;net8.0</TargetFrameworks>

// STEP 3 — move the leaves first: libraries, then services, then the host.
//   ASP.NET (System.Web) to ASP.NET Core is the hard part. Take the incremental
//   "strangler" route: a new ASP.NET Core app with YARP proxying unmigrated routes to
//   the old app, and System.Web adapters for shared session and auth — route by route.

// STEP 4 — NULLABLE, incrementally. Turning it on repo-wide produces 4,000 warnings,
//   and 4,000 warnings get ignored. Instead:
#nullable enable                       // opt in file by file, domain and leaf types first
//   Annotate the most-used types first: every annotation improves the analysis in
//   every caller. Then enable it for the project, then make the warnings errors:
<Nullable>enable</Nullable>
<WarningsAsErrors>nullable</WarningsAsErrors>

// STEP 5 — RATCHET analysers rather than fixing everything at once.
//   In .editorconfig, promote one rule at a time to error once its count is zero:
//     dotnet_diagnostic.CA2016.severity = error    // forward the CancellationToken
//   The build, not code review, then holds the line.
//   Run dotnet format to apply mechanical fixes in their OWN commits, so behavioural
//   diffs stay reviewable.

// STEP 6 — adopt modern idioms opportunistically: file-scoped namespaces, records for
//   new DTOs, collection expressions, primary constructors — when a file is touched
//   for real work. A 2,000-file "modernise the syntax" PR buys churn, merge conflicts
//   and blame noise, not value.
The principle: every step leaves the codebase shippable. Tooling and project hygiene first; the framework migration by leaves and routes; nullable and analysers by ratchet; new syntax only where you are already working. The failure mode to avoid is the big-bang rewrite that spends a year reproducing behaviour the old system already had.

Interview Questions

Q1 (Beginner): What do required and init accomplish together on a model class?

Together they give you immutable objects that cannot be created half-initialised, without long constructors.

init makes a property settable only during initialisation — in a constructor, an object initialiser, or a with expression — and read-only afterwards. required, added in C# 11, makes the compiler insist that every caller sets the member in the object initialiser; leaving it out is a compile error.

  public sealed class CreateOrder
  {
      public required Guid CustomerId { get; init; }
      public required string Currency  { get; init; }
      public string? Notes             { get; init; }
  }

  var cmd = new CreateOrder { CustomerId = id, Currency = "EUR" };   // fine
  var bad = new CreateOrder { CustomerId = id };  // error CS9035: Currency must be set
  cmd.Currency = "USD";                           // error: init-only after creation

Before these features, the choice was a constructor with many positional parameters — immutable but unreadable at the call site, and fragile as parameters were added — or settable properties, which were readable but let callers forget mandatory values and change them later. required init gives named, readable construction with both guarantees.

Know the limits. These are compile-time rules. A constructor marked [SetsRequiredMembers] switches the check off, so it must genuinely set everything. Reflection can bypass them. System.Text.Json honours required since .NET 7, failing deserialisation when a required property is missing, but other serialisers may not. And required only proves a value was assigned, not that it is valid: an empty string still passes, so value rules still need validation.

Q2 (Beginner): What are collection expressions and what older code do they replace?

Collection expressions, introduced in C# 12, are a single target-typed syntax for creating collections: square brackets around the elements, with .. to spread another collection in.

  int[] primes              = [2, 3, 5, 7];
  List<string> names        = ["Ada", "Grace"];
  ReadOnlySpan<byte> header = [0x50, 0x4B];
  ImmutableArray<int> ids   = [1, 2, 3];
  IReadOnlyList<Order> none = [];                       // empty
  int[] all                 = [..primes, 11, ..more];    // spread

  // what they replace
  new int[] { 2, 3, 5, 7 };
  new List<string> { "Ada", "Grace" };
  Array.Empty<Order>();  Enumerable.Empty<Order>();
  ImmutableArray.Create(1, 2, 3);
  primes.Concat(new[] { 11 }).Concat(more).ToArray();

They replace a zoo of type-specific forms: array initialisers, collection initialisers, Array.Empty, Enumerable.Empty, the Create factories of immutable collections, and Concat chains for combining sequences. One syntax now works for arrays, lists, spans, immutable collections and interface types.

Beyond readability, the compiler chooses an efficient construction for the target: it presizes when the length is known, can use a cached empty instance for [], and can build spans without heap allocation. Library types opt in with the CollectionBuilder attribute.

Two caveats. A collection expression needs a target type: var x = [1, 2]; does not compile. And for an interface target such as IReadOnlyList<T>, the compiler picks the implementation — so do not cast it back to List<T> to mutate it; declare List<T> if you need a list.

Q3 (Mid): What is a source generator, and why has the ecosystem moved toward them? Name concrete examples.

A source generator is a compiler plug-in. While your project compiles, it inspects your code — syntax and semantic model, typically looking for an attribute or a pattern — and emits additional C# source that is compiled alongside yours. It can only add code, never change existing code, which is why generated members usually land in partial classes and methods. Modern generators are incremental, rerunning only when their inputs change so the IDE stays responsive.

  [JsonSerializable(typeof(Order))]
  internal partial class AppJsonContext : JsonSerializerContext { }   // serializer generated

  public static partial class Log
  {
      [LoggerMessage(Level = LogLevel.Warning, Message = "Order {OrderId} rejected: {Reason}")]
      public static partial void OrderRejected(ILogger logger, Guid orderId, string reason);
  }

  [GeneratedRegex(@"^[A-Z]{3}-\d{4}$")]
  private static partial Regex SkuPattern();

The ecosystem moved to them because they replace runtime reflection and runtime code generation — work that used to happen at startup or on first use now happens at build time. That brings faster startup and fewer allocations; compatibility with trimming and NativeAOT, which cannot see or support reflection-driven code; compile-time errors instead of runtime surprises; and generated code you can read and step through in the debugger.

Concrete examples: System.Text.Json source generation; [LoggerMessage] for allocation-free logging; [GeneratedRegex]; [LibraryImport] for native interop; the configuration-binding generator; ASP.NET Core's request-delegate generator for AOT minimal APIs; and community tools such as the MVVM Toolkit's [ObservableProperty] and Mapperly for object mapping.

The costs are build-time complexity and another layer to understand when something goes wrong.

Q4 (Mid): How do you keep 30 projects in one solution consistent — language version, warnings, package versions?

By moving shared settings out of individual project files into files that MSBuild and the tooling apply automatically to every project beneath them.

  global.json                 pins the .NET SDK version
  Directory.Build.props       shared MSBuild properties for every project
  Directory.Packages.props    one version per NuGet package (Central Package Management)
  .editorconfig               code style and analyser severities

  <!-- Directory.Build.props -->
  <Project>
    <PropertyGroup>
      <TargetFramework>net9.0</TargetFramework>
      <Nullable>enable</Nullable>
      <ImplicitUsings>enable</ImplicitUsings>
      <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
      <AnalysisLevel>latest-recommended</AnalysisLevel>
      <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
    </PropertyGroup>
  </Project>

Directory.Build.props at the repository root is imported by every project, so the target framework, nullable setting, warnings-as-errors and analysis level are declared once. Leave LangVersion unset, so it follows the target framework's default rather than drifting per project. A nested props file can adjust test projects while importing the parent's settings.

Central Package Management — Directory.Packages.props with ManagePackageVersionsCentrally — lists each package's version once. Projects reference packages without versions, which ends the drift where one project uses a library version the others do not, and the version conflicts that follow.

global.json pins the SDK so every developer and CI agent compiles with the same compiler and analysers. .editorconfig holds style and analyser severities.

Finally, CI enforces it: build with warnings as errors, run dotnet format --verify-no-changes, and consider lock files for reproducible restores. Settings that are only conventions erode; settings the build fails on stay consistent.

Q5 (Senior): Result types vs exceptions for failure handling — where do you draw the line in a codebase you own?

By expectedness at the call site, made explicit in signatures. Business outcomes that every caller must handle — payment declined, insufficient balance, validation failure, not-found in a user-driven lookup — belong in the return type: a small sealed record hierarchy per operation (or T? for simple absence), consumed with exhaustive switch expressions so adding an outcome forces every call site to decide. Infrastructure failures — connection loss, timeouts, bugs — stay exceptions: they're not per-call-site decisions, they're cross-cutting policy (retry, circuit-break, 500) handled at boundaries (exceptions-nullability.html's architecture). The anti-patterns on each side: exceptions as control flow for expected outcomes (performance + readability tax, invisible in signatures), and Result-wrapping everything including infrastructure (every call site drowns in plumbing it can't meaningfully handle). I'd also defer adopting a Result library until the in-house 10-line record hierarchy demonstrably falls short — domain-named results read better than generic Result<T, E>.

Q6 (Senior): You're setting conventions for a brand-new .NET service repo. Walk through your first-hour setup and justify each choice.

(1) Directory.Build.props: latest LTS TargetFramework, Nullable enable, ImplicitUsings, TreatWarningsAsErrors, EnforceCodeStyleInBuild — null safety and warning hygiene are free on day one and expensive to retrofit. (2) Directory.Packages.props with CPM — version drift never starts. (3) .editorconfig + dotnet format --verify-no-changes in CI — style leaves code review permanently. (4) Solution shape: src/ + tests/, one integration-test project wired with WebApplicationFactory + Testcontainers from the first endpoint (testing.html's middle layer exists before habits form). (5) Program.cs: Generic Host with options validation (ValidateOnStart), scope validation (ValidateOnBuild), structured logging, health endpoint — the di-hosting.html failure classes become startup failures. (6) CI: build + test + dotnet format + (if AOT/trimming is plausible) a PublishAot canary job so incompatible dependencies are rejected at PR time, not discovery time. Each choice's theme: make the compiler and pipeline enforce what would otherwise be tribal knowledge.

1 (Easy): Modernize this 2015-era class using the full current idiom set (primary ctor is NOT the right tool here — say why): 
public class Money {
    private readonly decimal amount; private readonly string currency;
    public Money(decimal amount, string currency) {
        this.amount = amount; this.currency = currency;
    }
    public decimal Amount { get { return amount; } }
    public string Currency { get { return currency; } }

// for (records-structs.html): you get the properties, value equality, ToString,
// 'with' updates, and deconstruction free. A primary-constructor CLASS would be
// wrong because it wouldn't add equality — Money(5,"USD") should equal Money(5,"USD").
// If validation is needed, add it in a compact body:
public sealed record Money(decimal Amount, string Currency)

    public Money { ArgumentException.ThrowIfNullOrWhiteSpace(Currency); }  // C# 14-style

4 (Medium): Design the Result shape and endpoint mapping for user registration with outcomes: created, email taken, weak password (with which rules failed), banned domain. Exceptions or results — justify per outcome.
Solution
public abstract record RegisterResult
{
    public sealed record Created(Guid UserId)                     : RegisterResult;
    public sealed record EmailTaken                               : RegisterResult;
    public sealed record WeakPassword(IReadOnlyList<string> Failures) : RegisterResult;
    public sealed record BannedDomain(string Domain)              : RegisterResult;
}
// ALL FOUR are results, none are exceptions: every one is an EXPECTED, per-request
// business outcome the caller must translate for the user (exceptions-nullability
// .html's expectedness test). Exceptions remain for: DB unreachable, email service
// down — infrastructure, handled once by middleware as 500/503.

app.MapPost("/register", async (RegisterRequest req, RegistrationService svc) =>
    await svc.RegisterAsync(req) switch
    {
        RegisterResult.Created c      => Results.Created($"/users/{c.UserId}", null),
        RegisterResult.EmailTaken     => Results.Conflict(
                                           new { error = "email_taken" }),
        RegisterResult.WeakPassword w => Results.ValidationProblem(
                                           new Dictionary<string, string[]>
                                           { ["password"] = [..w.Failures] }),
        RegisterResult.BannedDomain b => Results.UnprocessableEntity(
                                           new { error = "banned_domain", b.Domain }),
        _ => Results.StatusCode(500),
    });
// Adding a fifth outcome (e.g. RequiresVerification) later: the new record type
// makes this switch's discard arm reachable for it — code review + tests catch the
// unhandled case immediately, which is the maintainability payoff of the pattern.

6 (Hard): Track-capstone code review. This endpoint "works". Find at least six track-lesson violations and rewrite it production-shaped. 
public class CardController {
    public static ShopContext db = new ShopContext();
    [HttpPost("/redeem")]
    public string Redeem(string id, string amt) {
        var card = db.GiftCards.ToList().Where(c => c.Id.ToString() == id).FirstOrDefault();
        card.Balance -= decimal.Parse(amt);
        db.SaveChangesAsync();
        return "ok: " + card.Balance;
    }
}
Solution
// VIOLATIONS (lesson in parentheses):
// 1. static ShopContext = new — one context forever, shared across all requests/
//    threads: not thread-safe, tracker grows unbounded (efcore.html, di-hosting.html).
// 2. ToList() BEFORE Where — materializes the ENTIRE table, filters in C# (linq.html).
// 3. card possibly null → NullReferenceException as a 500 (exceptions-nullability.html).
// 4. decimal.Parse(amt) — unvalidated user input at a trust boundary; culture-
//    sensitive parse; throws as 500 (strings.html, methods.html).
// 5. SaveChangesAsync() NOT awaited — fire-and-forget write: response says "ok"
//    whether or not it saved; exceptions vanish (async-await.html Part 4).
// 6. No concurrency control — two concurrent redemptions both read then write:
//    lost update / negative balance (efcore.html Part 4, threading.html).
// 7. Sync signature doing async work; no CancellationToken (async-await.html).
// 8. Stringly-typed API: string id, string amt, "ok: " + balance response.

app.MapPost("/redeem", async (RedeemRequest req, GiftCardService svc,
                              CancellationToken ct) =>
    await svc.RedeemAsync(req.CardId, req.Amount, ct) switch      // Part 5's service:
    {                                                             // scoped DbContext,
        RedeemResult.Redeemed r     => Results.Ok(new { r.NewBalance }),   // token retry,
        RedeemResult.Insufficient i => Results.Conflict(new { i.Balance }),// awaited save
        RedeemResult.NotFound       => Results.NotFound(),
        _                           => Results.StatusCode(500),
    });

public sealed record RedeemRequest
{
    public required Guid CardId { get; init; }                    // typed, required
    [Range(0.01, 10_000)] public required decimal Amount { get; init; }  // validated
}

🎯 Key Takeaways

  • Adopt modern syntax for what it deletes: primary constructors (ceremony), collection expressions (Concat chains, empty-collection idioms), required/init/NRT (invalid states), file-scoped namespaces (an indent).
  • Push consistency into the build: Directory.Build.props (one TFM/LangVersion/strictness), Directory.Packages.props (one version per package), analyzers + TreatWarningsAsErrors + dotnet format in CI.
  • Source generators move reflection's work to compile time — JSON contexts, [LoggerMessage], [GeneratedRegex] — faster, checked, and AOT-safe by construction.
  • Model expected business outcomes as sealed record results consumed by exhaustive switches; keep exceptions for infrastructure, handled once at boundaries.
  • Structured logging via templates/generators — never interpolated strings — so logs are queryable data and cost nothing when disabled.
  • Mastery is composition: the capstone used nothing new — records, patterns, LINQ, async, DI, EF, and tests fitting together without friction is the actual skill.
  • init makes a property settable only during initialisation.
  • required forces callers to set a member in the object initialiser.
  • required and init are compile-time contracts, not value validation.
  • System.Text.Json honours required during deserialisation.
  • Collection expressions give one syntax for arrays, lists, spans and immutable collections.
  • The spread operator .. splices one collection into another.
  • Collection expressions need a target type.
  • Source generators add code at compile time and never modify existing code.
  • Generators replace runtime reflection, which makes code faster to start and AOT-friendly.
  • Directory.Build.props shares build settings with every project below it.
  • Central Package Management gives each package one version per solution.
  • global.json pins the SDK so every machine builds the same way.
