Delegates, Events & Lambdas Core Libraries

What you'll master: delegates as typed, first-class references to methods; the built-in Action/Func/Predicate family; lambdas and — the part that causes real bugs — closure capture semantics; multicast delegates; the event keyword and the standard .NET event pattern; event-driven memory leaks and how to avoid them; and when to reach for callbacks vs events vs IObservable. Prerequisites: Methods (signatures are what delegates type-check) and LINQ (every LINQ operator takes a delegate). Delegates are the machinery under LINQ, events, DI factories, and async continuations — this is load-bearing knowledge.

Part 1 — Delegates: A Type for "a Method With This Shape"

A delegate type declares a method signature as a type. A delegate instance holds a reference to a concrete method (plus, for instance methods, the object to call it on). That's the whole idea: methods become values you can store, pass, and invoke later.

// Declaring a delegate type: "any method taking (string) and returning int"
public delegate int WordScorer(string word);

int LengthScore(string w) => w.Length;
int VowelScore(string w)  => w.Count("aeiou".Contains);

WordScorer scorer = LengthScore;      // method group conversion — no () — we're not CALLING it
Console.WriteLine(scorer("hello"));   // 5 — invoking the delegate invokes the target method

scorer = VowelScore;                  // rebind to a different method with the same shape
Console.WriteLine(scorer("hello"));   // 2

// A delegate instance stores TWO things:
//   Target — the object instance to call on (null for static methods)
//   Method — the MethodInfo to invoke
// That pairing is why "obj.SomeMethod" as a delegate keeps obj alive (Part 5 — leaks).

In practice you almost never declare custom delegate types anymore, because the BCL ships a generic family that covers every shape:

Action                    // void, no parameters
Action<T>                 // void, one parameter        Action<T1,T2,...> up to 16
Func<TResult>             // no parameters, returns TResult
Func<T, TResult>          // one parameter → result     Func<T1,T2,TResult> ...
Predicate<T>              // T → bool (older; LINQ uses Func<T,bool> instead)

Func<string, int> scorer = LengthScore;         // same as WordScorer, no custom type needed
Action<string> log = Console.WriteLine;          // method group of an instance method
Func<int, int, int> add = (a, b) => a + b;       // lambda (Part 2)

// Where you've already used them without noticing:
list.Where(x => x > 3)      // Where(Func<T,bool>)
list.Select(x => x * 2)     // Select(Func<T,TResult>)
list.ForEach(Console.WriteLine)  // ForEach(Action<T>)
list.Sort((a, b) => a.Age - b.Age)  // Comparison<T> — another named delegate
When would you still declare a custom delegate type? Two cases: (1) the signature has ref/out/in parameters or ref struct types like Span<T>, which generic type parameters can't express (e.g. SpanAction<T,TArg> in the BCL exists for exactly this reason); or (2) the name itself documents intent in a public API (EventHandler is more readable than Action<object?, EventArgs>). Otherwise use Action/Func.

Part 2 — Lambdas & Closures: Where the Real Bugs Live

// A lambda is an inline anonymous method. The compiler turns it into a real method
// (on a hidden class if it captures variables) and hands you a delegate to it.
Func<int, int> square = x => x * x;              // expression lambda
Func<int, int> verbose = x => { var r = x * x; return r; };  // statement lambda

// CLOSURE: a lambda that uses a variable from the enclosing scope CAPTURES it.
int factor = 3;
Func<int, int> scale = x => x * factor;   // captures 'factor'
Console.WriteLine(scale(10));             // 30
factor = 5;
Console.WriteLine(scale(10));             // 50 ← captures the VARIABLE, not its value at creation!

That last line is the single most important fact about closures: C# captures the variable, not a snapshot of its value. The compiler hoists the captured variable into a heap-allocated "closure class" shared by the enclosing method and the lambda — both read and write the same storage. Every classic closure bug follows from this:

// THE CLASSIC LOOP-CAPTURE BUG (still bites in for-loops):
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.Write(i + " "));
foreach (var a in actions) a();       // prints "3 3 3" — all three captured the SAME i,
                                      // and i is 3 by the time they run
// FIX: copy into a fresh variable each iteration — each lambda captures its own copy:
for (int i = 0; i < 3; i++) { int copy = i; actions.Add(() => Console.Write(copy + " ")); }
// → "0 1 2"
// Note: foreach loop variables got fresh-per-iteration semantics in C# 5, so
// foreach (var x in items) list.Add(() => Use(x)) is SAFE. for-loops were never changed.

// CAPTURE COST: a capturing lambda allocates (closure object + delegate) EVERY time the
// enclosing code runs. In hot paths, prefer static lambdas — the compiler ENFORCES no capture:
var evens = numbers.Where(static n => n % 2 == 0);   // 'static' = compile error if it captures
// Many BCL APIs offer a state-passing overload to avoid capture:
// e.g. ConcurrentDictionary.GetOrAdd(key, static (k, state) => Create(k, state), state)
Senior insight — what capture does to lifetimes. Capturing a local moves it from the stack to a heap closure object that lives as long as the delegate does. If a long-lived object stores your lambda (an event, a cache, a timer), everything the lambda captured — including this if you touched a field or instance method — is kept alive with it. A lambda that captures this inside a large object and gets handed to a static event is a memory leak with extra steps (Part 5). When reviewing code, read every lambda and ask: what does it capture, and who holds the delegate?

Part 3 — Multicast: One Delegate, Many Targets

// Every delegate is MULTICAST: += chains another target onto its invocation list.
Action notify = () => Console.Write("email ");
notify += () => Console.Write("sms ");
notify += () => Console.Write("push ");
notify();                       // "email sms push " — invoked in subscription order

// Delegates are IMMUTABLE like strings: += builds a NEW combined delegate.
// So copying then invoking is snapshot-safe:
Action? snapshot = notify;      // later += / -= on notify don't affect snapshot

// -= removes by EQUALITY: it works only if you pass an EQUAL delegate. A newly written
// lambda with identical code is NOT equal — so it silently removes nothing (Part 4 trap).

// Gotchas of multicast:
//  - Return values: invoking a multicast Func returns ONLY the LAST target's result.
//  - Exceptions: if target 2 of 5 throws, targets 3–5 NEVER RUN. To guarantee all run:
foreach (Action handler in notify.GetInvocationList())
    try { handler(); } catch (Exception ex) { Log(ex); }   // isolate each subscriber

Part 4 — Events: Multicast Delegates With Access Control

An event is a delegate field — plus a compiler-enforced access rule: outside the declaring class, you can only += and -=. You cannot invoke it, read it, or overwrite it. That's the entire difference, and it's exactly what makes publish/subscribe safe: no subscriber can fire your event or wipe out other subscribers.

// The standard .NET event pattern, piece by piece:
public class Downloader
{
    // 1. Declare with EventHandler<TEventArgs> — (object? sender, TEventArgs e)
    public event EventHandler<ProgressChangedEventArgs>? ProgressChanged;

    // 2. Payload class derives from EventArgs, immutable:
    public class ProgressChangedEventArgs : EventArgs
    {
        public int Percent { get; }
        public ProgressChangedEventArgs(int percent) => Percent = percent;
    }

    // 3. A protected virtual raiser — lets subclasses intercept, centralizes the null check:
    protected virtual void OnProgressChanged(ProgressChangedEventArgs e)
        => ProgressChanged?.Invoke(this, e);
        // ?.Invoke is the thread-safe idiom: reads the field ONCE into a temp, checks null,
        // invokes the temp. "if (ProgressChanged != null) ProgressChanged(...)" reads TWICE —
        // a subscriber could unsubscribe between the check and the call → NullReferenceException.

    public async Task DownloadAsync(string url)
    {
        for (int pct = 0; pct <= 100; pct += 20)
        {
            await Task.Delay(100);                       // simulate work
            OnProgressChanged(new ProgressChangedEventArgs(pct));
        }
    }
}

// SUBSCRIBING — and unsubscribing correctly:
var d = new Downloader();
void Report(object? s, Downloader.ProgressChangedEventArgs e) => Console.Write($"{e.Percent}% ");
d.ProgressChanged += Report;      // method group: you hold a name you can later remove
await d.DownloadAsync("...");     // 0% 20% 40% 60% 80% 100%
d.ProgressChanged -= Report;      // works — same method group produces an EQUAL delegate

// THE UNSUBSCRIBE TRAP:
d.ProgressChanged += (s, e) => Console.Write(e.Percent);   // anonymous lambda...
d.ProgressChanged -= (s, e) => Console.Write(e.Percent);   // ...silently removes NOTHING —
// this is a NEW, non-equal delegate. To unsubscribe a lambda, store it in a variable first:
EventHandler<Downloader.ProgressChangedEventArgs> h = (s, e) => Console.Write(e.Percent);
d.ProgressChanged += h;  /* later */  d.ProgressChanged -= h;
Why event instead of a public Action field? With public Action? Changed; any consumer can do obj.Changed = null (nuking every other subscriber) or obj.Changed() (firing your notification from outside). event restricts outsiders to +=/-= — encapsulation for the publisher/subscriber contract. In interviews, "an event is a delegate with restricted access from outside the class" is the crisp answer.

Part 5 — Deep Dive: Events Are the #1 Managed Memory Leak

// The publisher holds a delegate; the delegate holds Target = the SUBSCRIBER.
// So: publisher outlives subscriber  ⇒  publisher keeps subscriber ALIVE.

public static class AppEvents               // static = lives for the whole process
{
    public static event EventHandler? SettingsChanged;
    public static void Raise() => SettingsChanged?.Invoke(null, EventArgs.Empty);
}

public class SettingsView                   // created per page/dialog
{
    private readonly byte[] _bigBuffer = new byte[10_000_000];
    public SettingsView() => AppEvents.SettingsChanged += OnChanged;   // subscribes...
    private void OnChanged(object? s, EventArgs e) { /* refresh UI */ }
    // ...and if nothing ever does AppEvents.SettingsChanged -= OnChanged,
    // EVERY SettingsView ever created stays reachable via the static event's
    // invocation list — 10MB each, forever. The GC is working correctly:
    // static event → delegate → Target (the view) is a live reference chain.
}

// FIXES, in order of preference:
// 1. Deterministic unsubscribe — implement IDisposable, -= in Dispose, and make the
//    OWNER dispose the view when done. (See memory.html for the Dispose pattern.)
public class FixedView : IDisposable
{
    public FixedView() => AppEvents.SettingsChanged += OnChanged;
    private void OnChanged(object? s, EventArgs e) { }
    public void Dispose() => AppEvents.SettingsChanged -= OnChanged;
}
// 2. Don't use a long-lived/static event at all — prefer scoped publishers whose lifetime
//    matches their subscribers (DI scopes help: di-hosting.html).
// 3. Weak-event patterns (WeakReference to the subscriber) exist in UI frameworks —
//    a last resort; deterministic unsubscription is simpler to reason about.

// Diagnosing: memory profiler → "why is this object alive?" → retention path will show
// EventHandler → Target. That path IS the diagnosis.

// Callbacks compose into APIs very cleanly — this is the pattern LINQ, ASP.NET middleware,
// and options configuration all use:
public class RetryPolicy
{
    public static T Execute<T>(Func<T> operation, Action<Exception, int>? onRetry = null)
    {
        for (int attempt = 1; ; attempt++)
        {
            try { return operation(); }
            catch (Exception ex) when (attempt < 3)
            {
                onRetry?.Invoke(ex, attempt);        // optional hook — null-safe invoke
                Thread.Sleep(100 * attempt);
            }
        }
    }
}
var data = RetryPolicy.Execute(
    () => FetchFromApi(),
    (ex, n) => Console.WriteLine($"retry {n}: {ex.Message}"));

Interview Questions

Q1 (Beginner): What is a delegate, and what are Action and Func?

A delegate is a type-safe reference to a method. It is a type describing a method signature — its parameters and return type — and an instance of it can point to any method with a matching signature, whether static or instance. Calling the delegate calls the method. It is how C# treats behaviour as a value: something you can store in a field, pass as an argument, or return.

  delegate decimal PriceRule(decimal price);          // a custom delegate type

  Func<decimal, decimal> discount = p => p * 0.9m;  // takes decimal, returns decimal
  Action<string> log = Console.WriteLine;           // takes string, returns nothing
  Predicate<Order> isLarge = o => o.Total > 1000;   // takes Order, returns bool

Action and Func are general-purpose delegate types built into .NET, so you rarely need to declare your own. Action represents a method that returns nothing, with up to sixteen parameters: Action, Action<T>, Action<T1, T2>. Func represents a method that returns a value, and its last type argument is the return type: Func<int, string> takes an int and returns a string.

Lambdas and method groups convert to delegates automatically, which is why they are everywhere: LINQ's Where takes a Func<T, bool>, Task.Run takes a Func or Action, and minimal APIs map routes to delegates.

A custom delegate type is still worth declaring when a name documents intent better than a generic signature, when parameters need ref or out, or for events. Delegates are also multicast: one delegate can hold several methods and invoke them all in order, which is the foundation of events.

Q2 (Beginner): What's the difference between a delegate and an event?

An event is a delegate with restricted access. The event keyword wraps a delegate field so that code outside the declaring class can only subscribe with += and unsubscribe with -=. Only the class that declares the event can raise it or replace its subscribers.

  public class Order
  {
      public Action? StatusChangedField;                 // a public delegate field
      public event EventHandler<StatusEventArgs>? StatusChanged;   // an event

      void SetStatus(Status s) => StatusChanged?.Invoke(this, new StatusEventArgs(s));
  }

  order.StatusChangedField = null;       // compiles — wipes out every subscriber
  order.StatusChangedField();            // compiles — anyone can fire it
  order.StatusChanged = null;            // error: only += and -= are allowed outside

With a public delegate field, any code can make three damaging mistakes. It can assign with = instead of +=, silently removing every other subscriber. It can invoke the delegate, raising a notification for something that did not happen. And it can read the invocation list. The event keyword forbids all three, giving you the publish–subscribe pattern with the publisher in control.

Events follow a convention: the EventHandler or EventHandler<TEventArgs> signature with a sender and an arguments object, raised with ?.Invoke so that an event with no subscribers does not throw.

The key design caveat is lifetime: the publisher holds references to its subscribers, so a long-lived publisher keeps short-lived subscribers alive until they unsubscribe — a classic memory leak, and the subject of Q4.

Q3 (Mid): What does a closure capture in C# — the value or the variable? Show a bug this causes.

A closure captures the variable, not its value at the time the lambda is created. The compiler moves a captured local into a hidden class shared by the method and the lambda, so both see and change the same storage. When the lambda eventually runs, it reads the variable's current value.

The classic bug is a for loop:

  var actions = new List<Action>();
  for (int i = 0; i < 3; i++)
      actions.Add(() => Console.WriteLine(i));

  foreach (var a in actions) a();     // prints 3, 3, 3 — not 0, 1, 2

  for (int i = 0; i < 3; i++)
  {
      int copy = i;                   // a new variable per iteration
      actions.Add(() => Console.WriteLine(copy));
  }

There is one i for the whole loop. All three lambdas capture that one variable, and by the time they run the loop has finished and i is 3. Copying into a variable declared inside the loop body gives each lambda its own variable.

foreach was changed in C# 5 so that each iteration has a fresh variable, which is why it no longer has this bug — but for still does, because its counter is genuinely shared across iterations.

The same behaviour causes subtler problems in real code: a lambda passed to Task.Run that reads a variable the method keeps modifying; a captured variable that makes a large object live as long as the delegate, causing a memory leak; and allocations on hot paths from the hidden closure class. static lambdas, which cannot capture anything, make the compiler enforce that a lambda is closure-free.

Q4 (Mid): Why can myObj.Event -= (s,e) => Handler(s,e) fail to unsubscribe?

Because -= removes a handler by delegate equality, and the lambda in the unsubscribe line is a different delegate from the one used to subscribe.

Delegate equality compares the target object and the method. Each lambda expression in source code compiles to its own compiler-generated method. So (s,e) => Handler(s,e) written in the subscribe line and the identical-looking lambda in the unsubscribe line are two different methods. The removal searches the invocation list for a matching delegate, finds none, and silently does nothing — no exception, no warning.

  // broken: two different lambdas
  bus.Changed += (s, e) => OnChanged(s, e);
  bus.Changed -= (s, e) => OnChanged(s, e);    // removes nothing

  // fixed: use a method group — same target and method both times
  bus.Changed += OnChanged;
  bus.Changed -= OnChanged;

  // or keep the delegate instance
  _handler = (s, e) => OnChanged(s, e);
  bus.Changed += _handler;
  bus.Changed -= _handler;

Method groups work because each OnChanged conversion produces a delegate with the same target and method, which compare equal even though they are separate objects.

The consequences of the failed unsubscription are the real danger. The handler keeps running, so a closed view keeps reacting to events and may throw on disposed resources; handlers accumulate, so each reopen adds another and events are handled several times; and the publisher holds a reference to the subscriber, a memory leak that keeps it and everything it references alive. Unsubscribe in Dispose, and for publishers that outlive their subscribers, consider weak event patterns.

Q5 (Senior): Explain how events cause memory leaks in a garbage-collected runtime, how you'd diagnose one, and the fixes.

A delegate stores its target object, so a publisher's invocation list holds strong references to every subscriber. If the publisher outlives subscribers — a static or app-lifetime event with per-request/per-view subscribers — unsubscribed instances remain reachable through the event and are never collected; the GC is behaving correctly, the object graph genuinely holds them. Diagnose with a memory profiler: take a snapshot, find the accumulating type, inspect its retention path — it will run through an EventHandler's Target. Fixes: deterministic unsubscribe (implement IDisposable, -= in Dispose, ensure owners dispose); align publisher lifetime with subscriber lifetime (scoped services instead of statics); weak-event patterns as a last resort in UI frameworks.

Q6 (Senior): A multicast Func<int> has three targets. What does invoking it return? And what happens if the second target throws?

Invocation calls targets in subscription order and returns only the last target's result — earlier return values are discarded, which is why multicast really only makes sense for void/event signatures. If the second target throws, the exception propagates immediately and the third target never runs. When subscriber isolation matters (event dispatch in a robust system), iterate GetInvocationList() and invoke each target in its own try/catch, aggregating failures — that guarantees every subscriber gets notified regardless of others' bugs.

Solution
int n = 1;
Func<int> f = () => n * 10;
n = 7;

int snapshot = n;                        // copy first
Func<int> g = () => snapshot * 10;      // captures the copy
3 (Medium): Build a TemperatureSensor class with a ThresholdExceeded event carrying the reading, following the full standard pattern (EventArgs subclass, protected raiser, thread-safe invoke). Subscribe, trigger, unsubscribe.
Solution
public class TemperatureSensor
{
    public event EventHandler<ReadingEventArgs>? ThresholdExceeded;
    public class ReadingEventArgs : EventArgs
    {
        public double Celsius { get; }
        public ReadingEventArgs(double c) => Celsius = c;
    }
    protected virtual void OnThresholdExceeded(ReadingEventArgs e)
        => ThresholdExceeded?.Invoke(this, e);       // single-read, null-safe raise

    public void Submit(double celsius)
    {
        if (celsius > 40) OnThresholdExceeded(new ReadingEventArgs(celsius));
    }
}

var sensor = new TemperatureSensor();
void Alarm(object? s, TemperatureSensor.ReadingEventArgs e)
    => Console.WriteLine($"ALERT: {e.Celsius}°C");
sensor.ThresholdExceeded += Alarm;   // method group → removable later
sensor.Submit(25);                   // nothing
sensor.Submit(42);                   // ALERT: 42°C
sensor.ThresholdExceeded -= Alarm;   // same method group = equal delegate = removed
sensor.Submit(45);                   // nothing — unsubscribed
4 (Medium): This code leaks. Identify the leak and fix it with IDisposable. 
class Dashboard {
    public Dashboard() => Ticker.Tick += Refresh;   // Ticker.Tick is static
    void Refresh(object? s, EventArgs e) { }
}
Solution
// LEAK: Ticker.Tick is static → app-lifetime. Its invocation list holds a delegate whose
// Target is each Dashboard. Dashboards are never collectable while subscribed — every
// dashboard ever created accumulates.
class Dashboard : IDisposable
{
    public Dashboard() => Ticker.Tick += Refresh;
    void Refresh(object? s, EventArgs e) { }
    public void Dispose() => Ticker.Tick -= Refresh;   // break the chain deterministically
}
// AND the owner must actually dispose it:
using var dash = new Dashboard();     // or DI container manages disposal
// Rule: subscribing to something longer-lived than you = you now have a disposal duty.
5 (Hard): Implement SafeRaise: an extension that invokes every subscriber of an EventHandler<T> even if some throw, then throws an AggregateException if any failed.
Solution
public static class EventExtensions
{
    public static void SafeRaise<T>(this EventHandler<T>? handler, object? sender, T args)
    {
        if (handler is null) return;
        List<Exception>? errors = null;
        foreach (EventHandler<T> h in handler.GetInvocationList())   // snapshot of targets
        {
            try { h(sender, args); }
            catch (Exception ex) { (errors ??= new()).Add(ex); }     // isolate each subscriber
        }
        if (errors is not null) throw new AggregateException(errors);
    }
}
// Usage inside a publisher:  ThresholdExceeded.SafeRaise(this, e);
// Default multicast invoke stops at the FIRST throwing subscriber; this guarantees
// delivery to all, then reports all failures — the semantics robust dispatchers need.
6 (Hard): A hot path calls items.Where(x => x.Category == category) millions of times per second and profiling shows closure allocations. Eliminate them two ways.
Solution
// The lambda captures 'category' → new closure + delegate allocated per call.

// WAY 1 — hoist the delegate: if 'category' is stable, build the delegate ONCE and cache it:
private readonly Func<Item, bool> _filter;
public Service(string category)
{
    _filter = x => x.Category == category;   // ONE closure for the object's lifetime
}
public IEnumerable<Item> Filter(IEnumerable<Item> items) => items.Where(_filter);

// WAY 2 — remove the capture entirely with a static lambda + explicit state.
// LINQ's Where has no state overload, so drop to a plain loop (fine in a hot path —
// see linq.html Part 6: hand-rolled loops beat LINQ where measured):
public static List<Item> Filter(List<Item> items, string category)
{
    var result = new List<Item>();
    foreach (var x in items)
        if (x.Category == category) result.Add(x);   // no delegate, no closure, no enumerator
    return result;
}
// 'static' lambdas (static x => ...) PROVE no capture at compile time — use them wherever
// the lambda needs nothing from the enclosing scope; pair with state-passing overloads
// (e.g. ConcurrentDictionary.GetOrAdd(key, static (k, s) => ..., state)) when it does.

🎯 Key Takeaways

  • A delegate is a type for a method signature; instances pair a method with a target object. Action/Func cover nearly all shapes — custom delegate types only for ref/span signatures or self-documenting names.
  • Closures capture variables, not values — the compiler hoists captured locals to a shared heap object. Copy per-iteration in for loops; use static lambdas to forbid capture in hot paths.
  • Delegates are immutable and multicast: += builds a new invocation list; a throwing target skips the rest; a multicast Func returns only the last result; GetInvocationList() + per-target try/catch when isolation matters.
  • An event is a delegate with outsider access limited to +=/-=. Standard pattern: EventHandler<TArgs>, an EventArgs payload, a protected On… raiser, and ?.Invoke (single read, race-free).
  • Events are the classic managed leak: publisher's delegate → Target → subscriber stays alive. Unsubscribe deterministically (IDisposable), match lifetimes, and read profiler retention paths through EventHandler.Target.
  • Choose the lightest mechanism: callback parameter for one customization point, event for N dynamic listeners, DI-injected handlers for services, Rx/Channels for streams (Async Patterns).
  • A delegate is a type-safe reference to a method.
  • Action returns nothing; Func's last type argument is its return type.
  • Lambdas and method groups convert to delegates.
  • Delegates are multicast.
  • An event restricts outsiders to += and -=.
  • Only the declaring class can raise or reset an event.
  • Raise events with ?.Invoke.
  • Closures capture variables, not values.
  • for counters are shared; foreach variables are fresh.
  • Each lambda expression is a distinct delegate.
  • Unsubscribe with a method group or a stored delegate.
  • Publishers keep subscribers alive until they unsubscribe.
