Exceptions & Nullable Reference Types Core Libraries

What you'll master: how exceptions actually propagate (and what they cost); the try/catch/finally machinery including exception filters; designing exception strategy — what to throw, where to catch, what "handling" really means; custom exception types; throw vs throw ex and stack-trace preservation; and the second half of null-safety: nullable reference types (NRT) — the annotations, the flow analysis, the attributes, and how to actually eliminate NullReferenceException from a codebase. Prerequisites: Types & Variables (reference vs value null), Methods. Exceptions and null are the two ways .NET code fails at runtime; this lesson is about making both failures loud, early, and rare.

Part 1 — The Exception Model: What Actually Happens on throw

// throw creates an Exception object and starts UNWINDING the call stack:
// each frame is searched for a matching catch; finally blocks run as frames unwind;
// if no frame catches, the process crashes (or the host logs it — ASP.NET turns it into a 500).

try
{
    var order = ParseOrder(json);          // may throw JsonException
    Save(order);                           // may throw DbUpdateException
}
catch (JsonException ex)                   // most-DERIVED first — order matters!
{
    _log.LogWarning(ex, "Bad payload");    // handled: we can respond 400 and continue
    return Results.BadRequest();
}
catch (Exception ex) when (ex is not OperationCanceledException)   // FILTER (Part 2)
{
    _log.LogError(ex, "Order failed");
    throw;                                 // rethrow — we logged, but can't actually handle
}
finally
{
    _metrics.Increment("orders.attempted"); // ALWAYS runs: normal exit, catch, or unwind
}

// Key structural facts:
//  - catch blocks are tested TOP-DOWN; a base-class catch above a derived one is unreachable
//    (compiler error). catch (Exception) catches everything managed.
//  - finally runs on every exit path — it's how using/lock guarantee cleanup.
//  - An exception thrown INSIDE finally replaces the in-flight exception (losing it) — keep
//    finally blocks trivial.

The exception object carries the diagnostic payload: Message, StackTrace (captured as it propagates), InnerException (the cause chain), and a Data dictionary. The stack trace is why exceptions beat error codes for debuggability — and also why they cost more:

Cost model (the senior framing): a try block that never throws is essentially free in .NET — the JIT lays out handlers out-of-band; there's no per-entry cost. Throwing is expensive: object allocation, stack-trace capture, two-pass unwinding — microseconds each, thousands of times slower than a branch. Conclusion: exceptions are for exceptional paths. Never use them as control flow (TryParse exists precisely so parsing user input doesn't throw per bad row); but don't contort code to avoid a throw that happens once per process either. "Throw rarely, catch rarely, try freely."

Part 2 — Filters, Rethrow, and the Exception Hierarchy

// EXCEPTION FILTERS: 'when (condition)' decides whether this catch matches —
// WITHOUT unwinding the stack if it doesn't. Filters run at the throw site's stack state.
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.TooManyRequests)
{
    await Task.Delay(RetryAfter(ex));      // catch ONLY 429s; other HTTP errors fly past
}
catch (Exception ex) when (LogAndFalse(ex)) { }   // logging filter trick: LogAndFalse logs
// and returns false → nothing is caught, stack intact, but every exception got logged.

// RETHROW — the #1 exception idiom interviewers check:
catch (Exception ex)
{
    _log.LogError(ex, "context");
    throw;        // ✅ rethrows the ORIGINAL — stack trace preserved
    // throw ex;  // ❌ RESETS the stack trace to THIS line — the true origin is lost
}
// Wrapping (adding context while keeping the cause) uses InnerException:
catch (SqlException ex)
{
    throw new OrderPersistenceException($"Saving order {id} failed", ex);  // cause chained
}
// ExceptionDispatchInfo.Capture(ex).Throw() rethrows preserving the trace from ANOTHER
// location (used by the async machinery to rethrow task exceptions on await).

// THE HIERARCHY — know these:
Exception
├── SystemException
│   ├── NullReferenceException      // BUG: you dereferenced null — never catch, FIX
│   ├── IndexOutOfRangeException    // BUG
│   ├── InvalidOperationException   // object in wrong state for the call
│   ├── ArgumentException / ArgumentNullException / ArgumentOutOfRangeException
│   └── OperationCanceledException  // cooperative cancellation — catch to exit gracefully
├── IOException, HttpRequestException, SocketException...   // ENVIRONMENT: retryable-ish
└── (your domain exceptions)        // e.g. OrderNotFoundException : Exception
// Guard-clause helpers (modern BCL) — validate at trust boundaries (methods.html):
ArgumentNullException.ThrowIfNull(order);                 // .NET 6+
ArgumentException.ThrowIfNullOrWhiteSpace(name);          // .NET 8+
ArgumentOutOfRangeException.ThrowIfNegative(amount);      // .NET 8+
// These throw with the PARAMETER NAME auto-captured (CallerArgumentExpression) — one line,
// perfect message, and the JIT can inline the happy path.

Part 3 — Exception Strategy: Who Throws, Who Catches, Who Logs

QuestionRuleWhy
When to throw?When a method cannot do what its name promisesGetOrder(id) that can't find the order either throws or returns Order? — never a half-built object
When to catch?Only where you can meaningfully respond: retry, fallback, convert to a user-facing result, or add context and rethrowA catch that just logs-and-swallows turns a loud failure into silent corruption

// A custom domain exception — the complete, conventional shape:
public class OrderNotFoundException : Exception
{
    public Guid OrderId { get; }
    public OrderNotFoundException(Guid orderId)
        : base($"Order {orderId} was not found") => OrderId = orderId;
    public OrderNotFoundException(Guid orderId, Exception inner)
        : base($"Order {orderId} was not found", inner) => OrderId = orderId;
}

// ...and the single place that translates domain exceptions to HTTP (ASP.NET middleware):
app.UseExceptionHandler(a => a.Run(async ctx =>
{
    var ex = ctx.Features.Get<IExceptionHandlerFeature>()?.Error;
    (int status, string title) = ex switch
    {
        OrderNotFoundException => (404, "Order not found"),
        ValidationException    => (400, "Invalid request"),
        _                      => (500, "Unexpected error"),   // logged with full trace
    };
    ctx.Response.StatusCode = status;
    await ctx.Response.WriteAsJsonAsync(new ProblemDetails { Status = status, Title = title });
}));
// Result: business code throws domain exceptions freely; ONE boundary catches, logs once,
// and shapes the response. No try/catch litter in handlers or services.

Part 4 — Nullable Reference Types: The Compiler vs. NullReferenceException

Historically every reference type in C# could be null, and the compiler said nothing until the runtime blew up with NullReferenceException — "the billion-dollar mistake." NRT (on by default in new projects via <Nullable>enable</Nullable>) makes intent part of the type: string means "never null," string? means "null is a legal value — callers must check." The compiler then flow-analyzes every dereference and warns where null could slip through.

#nullable enable
string  name  = null;      // ⚠ CS8600: assigning null to non-nullable
string? maybe = null;      // ✅ declared nullable — null is expected here

Console.Write(maybe.Length);          // ⚠ CS8602: possible null dereference
if (maybe is not null)
    Console.Write(maybe.Length);      // ✅ FLOW ANALYSIS: inside the check, maybe is string

// The compiler tracks null-state through your logic:
string? s = Find(key);
if (string.IsNullOrEmpty(s)) return;  // BCL is annotated: after this, s is NOT null
Console.Write(s.Length);              // ✅ no warning — analysis understood the guard

// The operators that interact with null-state:
maybe?.Length          // null-conditional: null in → null out (int? here), no throw
maybe ?? "fallback"    // null-coalescing: non-null result → flows as non-nullable
maybe ??= "default";   // assign only if currently null
maybe!                 // null-forgiving: "compiler, trust me, it's not null here"
                       // ⚠ ! is an unchecked promise — if you're wrong, NRE at runtime.
                       // Legitimate uses: test setup, DTOs materialized by serializers,
                       // patterns the analysis can't follow. A codebase full of ! has
                       // disabled NRT while pretending not to.
// CRITICAL HONESTY: NRT is COMPILE-TIME ONLY. Annotations erase; nothing checks at runtime.
// Null can still arrive from: reflection, serializers, un-annotated libraries, DB nulls,
// and any #nullable disable code. Therefore the discipline is:
//   Annotations INSIDE the codebase + runtime GUARDS at trust boundaries.
public Order Create(CustomerDto dto)          // dto claims non-null, but it came from JSON...
{
    ArgumentNullException.ThrowIfNull(dto);   // ...so verify at the boundary anyway
    ...
}
// Constructor warnings you WILL meet: "Non-nullable property 'Name' must contain a
// non-null value when exiting constructor" — fix by initializing, requiring, or admitting:
public class Customer
{
    public string Name { get; set; } = "";            // option 1: safe default
    public required string Email { get; set; }        // option 2: 'required' — callers MUST set
    public string? Nickname { get; set; }             // option 3: it's genuinely optional
}

Part 5 — Deep Dive: Nullability Attributes (Teaching the Analysis)

// Sometimes your METHOD knows more about null than its signature can say.
// The BCL's nullability attributes express those contracts:

// TryGet pattern: 'value' is non-null WHEN we return true:
public bool TryGetUser(string id, [NotNullWhen(true)] out User? user) { ... }
if (repo.TryGetUser(id, out var u))
    Console.Write(u.Name);            // ✅ no warning — analysis trusts NotNullWhen(true)

// "Returns null only if the input was null":
[return: NotNullIfNotNull(nameof(path))]
public string? Normalize(string? path) => path?.Trim().ToLowerInvariant();

// "After this method runs, the field/param is not null":
private string? _connection;
[MemberNotNull(nameof(_connection))]
private void EnsureConnection() => _connection ??= Build();
public void Query() { EnsureConnection(); Use(_connection); }   // ✅ no warning

// Others: [NotNull] (out/ref is non-null on exit even if typed nullable),
// [MaybeNullWhen(false)], [DoesNotReturn] (method always throws — analysis prunes the path).
// These matter most when writing LIBRARIES: they make YOUR API as pleasant under NRT
// as the BCL is. Generic code: 'T?' means "default of T" — constrain with 'where T : class'
// or 'where T : notnull' when null-freedom matters.
Migration strategy for a legacy codebase (a common senior interview question): enable NRT file by file or project by project, not big-bang. Set <Nullable>enable</Nullable> in the csproj, add #nullable disable atop unconverted files, then burn the list down — innermost/leaf projects first so annotations flow outward to callers. Treat warnings as errors (<WarningsAsErrors>nullable</WarningsAsErrors>) once a project converts, or the annotations rot. Resist mass-!: every forgiveness operator is a place the compiler told you null could escape and you overrode it.

Part 6 — Exceptions + Null: The Failure-Design Playbook

// "Not found" — exception, null, or Try-pattern? Choose by EXPECTEDNESS at the call site:
public Order  GetOrder(Guid id);        // throws OrderNotFoundException — absence is a BUG
public Order? FindOrder(Guid id);       // returns null — absence is NORMAL; NRT forces check
public bool   TryGetOrder(Guid id, [NotNullWhen(true)] out Order? order);  // hot paths/parsing

// All three are legitimate; a good API often pairs Get (throwing) with Find (nullable).
// What is NOT legitimate: returning null from a method typed to return non-null Order,
// or throwing for a case every caller must routinely handle (forces try/catch control flow).

// Async note (full story in async-await.html): exceptions in an async method are captured
// into the returned Task and rethrown at await. async VOID has no Task — its exceptions
// crash the process. One more reason async void is only for event handlers.

Interview Questions

Q1 (Beginner): What do try, catch, and finally each do? When does finally not run?

try marks code whose exceptions you want to intercept; catch blocks handle matching exception types (tested top-down, most-derived first); finally runs on every exit path — normal completion, a caught exception, or an exception unwinding past the frame — making it the place for cleanup (it's what using compiles into). It doesn't run only in process-killing scenarios: Environment.FailFast, stack overflow, or the process being terminated externally.

Q2 (Beginner): What does string? mean under nullable reference types, and what do ?. and ?? do?

With NRT enabled, string declares "never null" and string? declares "null is a legal value" — the compiler warns when you dereference a possibly-null value or assign null to a non-nullable one. x?.Member (null-conditional) evaluates to null instead of throwing when x is null; x ?? fallback (null-coalescing) yields x unless it's null, in which case the fallback. Together: user?.Name ?? "guest" — safe navigation with a default.

Q3 (Mid): throw; vs throw ex; — what's the difference and why does it matter?

throw; rethrows the in-flight exception object with its stack trace intact — the trace still points at the original failure site. throw ex; treats it as a new throw: the stack trace is reset to the rethrow line, so the true origin is erased — in production, your log now says the error happened in your catch block. Use bare throw; to propagate after logging/inspection; to add context, wrap in a new exception passing the original as InnerException; ExceptionDispatchInfo preserves traces when rethrowing from a different context (it's how await rethrows task exceptions).

Q4 (Mid): What are exception filters (when) and what can they do that catch-type matching can't?

A filter is a boolean expression evaluated to decide whether a catch matches, before the stack unwinds. They enable: catching by condition, not just type (when (ex.StatusCode == 429)) so non-matching exceptions continue with the original stack intact; excluding types from a broad catch (when (ex is not OperationCanceledException)); and the logging-filter trick — a filter that logs and returns false observes every exception without catching anything or disturbing the stack. Catch-then-rethrow approximates some of this but unwinds the stack first, losing dump/debugger fidelity at the throw point.

Q5 (Senior): NRT is compile-time only. Design a null-safety strategy for a service that deserializes external JSON and calls un-annotated legacy libraries.

Annotations govern only code the compiler sees — serializers materialize objects via reflection and will happily put null in a string-typed property, and un-annotated (oblivious) libraries return unknown null-state. Strategy: (1) enable NRT with WarningsAsErrors=nullable for internal code, so intra-codebase flows are proven; (2) treat deserialization and legacy-library returns as trust boundaries — validate right there: required members on DTOs, ThrowIfNull guards, or a validation layer (FluentValidation/DataAnnotations) that rejects bad payloads with a 400 before domain code runs; (3) type DTO properties honestly (string? if the field can be absent) and map to non-nullable domain types only after validation; (4) confine ! to those boundary files with justification. Inside the boundary, non-nullable types are then genuinely trustworthy.

Q6 (Senior): Design the exception-handling architecture for a web API: where do try/catch blocks live, who logs, and how do domain errors become HTTP responses?

Three tiers. (1) A single top-level exception middleware catches everything unhandled: logs once with full trace and correlation ID, and maps exception type → status via a switch (NotFoundException→404, ValidationException→400, default→500 with an opaque ProblemDetails body — never leak stack traces to clients). (2) Mid-tier catches exist only where the code can meaningfully respond: retry with backoff on transient infrastructure errors (or delegate to Polly), fallback to cache, or wrap low-level exceptions in domain types for context (throw new OrderPersistenceException(id, ex)). (3) Business code throws domain exceptions freely and contains almost no try/catch. Rules that keep it sane: log at exactly one frame; never catch bug-class exceptions (NRE); treat OperationCanceledException as graceful shutdown, not an error; use Result-style returns instead of exceptions where the "failure" occurs on most requests (validation).

🏋️ Graded Exercises

1 (Easy): Predict the full output: 
try {
    Console.Write("A");
    throw new InvalidOperationException();
    Console.Write("B");
} catch (ArgumentException) { Console.Write("C"); }
  catch (InvalidOperationException) { Console.Write("D"); }
  finally { Console.Write("E"); }
Console.Write("F");
Solution
// Output: ADEF
// A prints; the throw skips B; ArgumentException doesn't match (unrelated type);
// InvalidOperationException matches → D; finally always runs → E; execution
// continues after the try statement because the exception was handled → F.
2 (Easy): Rewrite with null-safety operators, no if: "print the customer's city uppercased, or N/A if customer, address, or city is null."
Solution
Console.Write(customer?.Address?.City?.ToUpper() ?? "N/A");
// ?. short-circuits the whole chain to null at the first null link (ToUpper never
// runs on null); ?? supplies the fallback. The expression's type is string (non-null),
// so it can flow into non-nullable contexts without warnings.
3 (Medium): This retry helper is wrong three ways. Find and fix them. 
public T Retry<T>(Func<T> op) {
    for (int i = 0; i < 3; i++) {
        try { return op(); }
        catch (Exception ex) { Log(ex); throw ex; }
    }
    return default;
}
Solution
// BUG 1: 'throw ex' on EVERY failure → the loop never actually retries (first
//         exception propagates immediately) AND the stack trace is reset.
// BUG 2: retrying ALL exceptions — NullReferenceException or ArgumentException
//         will fail identically 3 times; only transient errors deserve retries.
// BUG 3: 'return default' — default(T) (null for classes!) returned as if success.
public T Retry<T>(Func<T> op, int attempts = 3)
{
    for (int i = 1; ; i++)
    {
        try { return op(); }
        catch (Exception ex) when (IsTransient(ex) && i < attempts)
        {
            Log(ex);                                  // filter: only transient, only
            Thread.Sleep(100 * i);                    // while retries remain — final
        }                                             // failure propagates with its
    }                                                 // ORIGINAL stack trace intact
}
static bool IsTransient(Exception ex) =>
    ex is IOException or HttpRequestException or TimeoutException;
// No 'return default' path exists — the method either succeeds or throws truthfully.
4 (Medium): Define PaymentDeclinedException (carrying a decline code) properly, and add it to an exception-handler middleware mapping as HTTP 402.
Solution
public class PaymentDeclinedException : Exception
{
    public string DeclineCode { get; }
    public PaymentDeclinedException(string code)
        : base($"Payment declined ({code})") => DeclineCode = code;
    public PaymentDeclinedException(string code, Exception inner)
        : base($"Payment declined ({code})", inner) => DeclineCode = code;
}

// In the single top-level handler:
(int status, string title) = ex switch
{
    PaymentDeclinedException p => (402, $"Payment declined: {p.DeclineCode}"),
    OrderNotFoundException     => (404, "Order not found"),
    _                          => (500, "Unexpected error"),
};
// The type earns its existence because a catcher DISTINGUISHES it (maps to 402 and
// exposes the decline code). Payment code just throws; no try/catch in the flow.
5 (Hard): Annotate this cache so callers get correct NRT analysis, using the right nullability attribute: 
public class Cache {
    private readonly Dictionary<string, object> _map = new();
    public bool TryGet(string key, out object value) { ... }   // may not find the key!
}
Solution
public class Cache
{
    private readonly Dictionary<string, object> _map = new();

    // 'out object value' is a LIE when the key is missing — we'd have to assign null.
    // Honest signature: value is object? — but NON-null whenever we return true:
    public bool TryGet(string key, [NotNullWhen(true)] out object? value)
        => _map.TryGetValue(key, out value);
}

// Caller experience — the analysis now understands the contract:
if (cache.TryGet("k", out var v))
    Console.Write(v.ToString());     // ✅ no warning: true ⇒ v is not null
else
    Console.Write(v?.ToString());    // v is (correctly) object? here
// This mirrors the BCL's own Dictionary.TryGetValue annotation. Without the attribute
// you'd either warn on every success path or use ! at every call site.
6 (Hard): A message consumer processes queue items in a loop. Requirements: one poison message must not kill the loop; cancellation must stop it cleanly; every failure logged once with the message ID. Write the loop's exception structure.
Solution
public async Task RunAsync(CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        Message? msg = null;
        try
        {
            msg = await _queue.ReceiveAsync(ct);
            await ProcessAsync(msg, ct);
            await _queue.AckAsync(msg, ct);
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            break;                     // graceful shutdown — NOT an error, no log spam
        }
        catch (Exception ex)           // poison-message isolation: catch EVERYTHING else
        {
            _log.LogError(ex, "Failed processing {MessageId}", msg?.Id);   // log ONCE
            if (msg is not null)
                await _queue.DeadLetterAsync(msg, CancellationToken.None); // don't lose it
            // loop continues — one bad message can't take down the consumer
        }
    }
}
// Key decisions: the broad catch is CORRECT here (top-level handler for this entry
// point — the loop is where we can meaningfully respond: dead-letter and continue);
// the OCE filter distinguishes real cancellation from a dependency's timeout;
// dead-lettering uses CancellationToken.None so shutdown can't lose the message.

🎯 Key Takeaways

  • try is free, throw is expensive: exceptions for exceptional paths, Try-patterns for expected failures; catch blocks match top-down; finally runs on every exit.
  • throw; preserves the stack trace, throw ex; destroys it; wrap with InnerException to add context; filters (when) match by condition without unwinding.
  • Strategy: throw when a method can't keep its promise; catch only where you can respond; one top-level handler per entry point logs once and maps domain exceptions to responses; custom types only if a catcher distinguishes them.
  • NRT makes null part of the type: string? + flow analysis + ?./??/required; ! is an unchecked promise — use rarely and deliberately.
  • NRT is compile-time only — pair annotations inside with runtime guards (ThrowIfNull) at deserialization/library boundaries; migrate legacy code project-by-project with warnings-as-errors.
  • Nullability attributes ([NotNullWhen], [MemberNotNull], [NotNullIfNotNull]) teach the analysis your contracts — essential for Try-patterns and libraries.
