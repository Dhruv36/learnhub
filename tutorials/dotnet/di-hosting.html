Dependency Injection & the Generic Host Professional .NET

What you'll master: why DI exists (it's about composition and lifetime, not testing tricks); the built-in container — registration, the three lifetimes and their failure modes (captive dependencies!); constructor injection idioms; the Generic Host as the backbone of every modern .NET app — configuration, logging, options, hosted services; and the patterns pros use daily: IOptions, IHttpClientFactory, keyed services, decorators. Prerequisites: Interfaces, Delegates (factory registrations), Async Patterns (background work needs scopes). This lesson is the bridge from "C# programmer" to ".NET application engineer" — and the foundation ASP.NET Core (the next track) assumes cold.

Part 1 — The Problem DI Solves

// WITHOUT DI — classes construct their own dependencies:
public class OrderService
{
    private readonly SqlOrderRepository _repo = new("Server=prod;...");   // hard-wired!
    private readonly SmtpEmailSender _email = new("smtp.prod.local");
}
// Consequences: OrderService is welded to SQL + SMTP (can't swap, can't fake for
// tests); the connection string hides inside a class; EVERY class re-creates
// dependencies (how many SmtpEmailSenders exist? who disposes them?); and changing
// SqlOrderRepository's constructor breaks every class that news it up.

// WITH DI — classes DECLARE dependencies; one composition root provides them:
public class OrderService(IOrderRepository repo, IEmailSender email)   // primary ctor
{
    public async Task PlaceAsync(Order order)
    {
        await repo.SaveAsync(order);
        await email.SendAsync(order.CustomerEmail, "Order confirmed!");
    }
}
// Registration — the ONE place that knows concrete types (Program.cs):
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddScoped<IEmailSender, SmtpEmailSender>();
builder.Services.AddScoped<OrderService>();
// The container builds the GRAPH: resolving OrderService constructs (or reuses) its
// dependencies, their dependencies, and so on — and DISPOSES everything it created
// at the right time. DI = composition + lifetime management, centralized.
The principle underneath (SOLID's D — Dependency Inversion): depend on abstractions the consumer needs, not on concretions. But don't cargo-cult interfaces: an interface with exactly one implementation that exists only "for DI" is ceremony — the container injects concrete classes just fine (AddScoped<OrderService>()). Add the interface when there's a genuine second implementation (prod/fake, SQL/InMemory) or a boundary you want to isolate in tests. Abstraction is a tool, not a tax.

Part 2 — Lifetimes: The Part Everyone Gets Wrong Once

builder.Services.AddSingleton<IClock, SystemClock>();      // ONE instance, forever
builder.Services.AddScoped<AppDbContext>();                // one per SCOPE (= per request)
builder.Services.AddTransient<IValidator, OrderValidator>(); // NEW instance per resolve

// WHAT EACH IS FOR:
// Singleton — stateless services or thread-safe shared state: config, caches,
//             HttpClient handlers, loggers. MUST be thread-safe (threading.html).
// Scoped    — one consistent instance per unit of work: DbContext (one transaction
//             view per request), per-request context. In ASP.NET, scope == request.
// Transient — cheap, stateless, or deliberately fresh: validators, small helpers.

// ⚠ THE CAPTIVE DEPENDENCY BUG (the classic DI production incident):
builder.Services.AddSingleton<ReportCache>();     // singleton...
public class ReportCache(AppDbContext db) { }     // ...injecting a SCOPED DbContext
// The singleton is built ONCE and CAPTURES that one DbContext forever: the "scoped"
// context now lives for the whole app — shared across requests (DbContext is NOT
// thread-safe → corruption), holding a stale change tracker, its connection pinned.
// RULE: a service may only depend on lifetimes AS LONG OR LONGER than its own.
//   Singleton → Singleton only.   Scoped → Scoped/Singleton.   Transient → anything.
// ASP.NET's dev-time scope validation catches direct cases (ValidateScopes) —
// enable ValidateOnBuild too, and it fails at STARTUP instead of first request:
builder.Host.UseDefaultServiceProvider(o => { o.ValidateScopes = true; o.ValidateOnBuild = true; });

// When a singleton legitimately needs scoped work (background jobs!): make a scope:
public class CleanupJob(IServiceScopeFactory scopeFactory)   // factory is a singleton
{
    public async Task RunAsync(CancellationToken ct)
    {
        using var scope = scopeFactory.CreateScope();               // OWN scope
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        await db.Orders.Where(o => o.IsExpired).ExecuteDeleteAsync(ct);
    }   // scope disposal disposes the DbContext — lifetimes stay honest
}

// Disposal: the container disposes IDisposables IT created — scoped/transient at
// scope end, singletons at app shutdown. (Transients resolved FROM THE ROOT provider
// are kept until shutdown — a slow leak; another reason transient disposables
// belong in scopes.) You don't dispose injected services — you don't own them
// (memory.html ownership rule).

Part 3 — Registration Techniques Beyond the Basics

// FACTORY registration — when construction needs logic/config:
builder.Services.AddSingleton<IPaymentGateway>(sp =>
{
    var cfg = sp.GetRequiredService<IConfiguration>();
    return cfg["Payments:Mode"] == "sandbox"
        ? new SandboxGateway()
        : new StripeGateway(cfg["Payments:ApiKey"]!);
});

// MULTIPLE implementations of one interface → inject them ALL:
builder.Services.AddScoped<INotifier, EmailNotifier>();
builder.Services.AddScoped<INotifier, SmsNotifier>();
builder.Services.AddScoped<INotifier, PushNotifier>();
public class Broadcaster(IEnumerable<INotifier> notifiers)      // gets all three
{
    public Task NotifyAsync(string msg) =>
        Task.WhenAll(notifiers.Select(n => n.SendAsync(msg)));
}

// KEYED services (.NET 8+) — pick one by name:
builder.Services.AddKeyedScoped<IStorage, S3Storage>("cloud");
builder.Services.AddKeyedScoped<IStorage, DiskStorage>("local");
public class Exporter([FromKeyedServices("cloud")] IStorage storage) { }

// DECORATOR — wrap a registration with cross-cutting behavior (caching, logging):
builder.Services.AddScoped<SqlProductCatalog>();                 // the real one
builder.Services.AddScoped<IProductCatalog>(sp => new CachedCatalog(
    sp.GetRequiredService<SqlProductCatalog>(),                  // wrapped
    sp.GetRequiredService<IMemoryCache>()));
public class CachedCatalog(SqlProductCatalog inner, IMemoryCache cache) : IProductCatalog
{
    public async Task<Product?> GetAsync(string sku) =>
        await cache.GetOrCreateAsync($"p:{sku}", e =>
        { e.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);
          return inner.GetAsync(sku); });
}
// Consumers still ask for IProductCatalog — the cache is invisible to them.

// TryAdd — register only if absent (library defaults the app can override):
builder.Services.TryAddSingleton<IClock, SystemClock>();

// ANTI-PATTERN — service locator: injecting IServiceProvider and resolving inside:
public class Bad(IServiceProvider sp)
{ void Work() => sp.GetRequiredService<IEmailSender>().Send(...); }   // hidden deps!
// Dependencies vanish from the constructor signature — callers and tests can't see
// them; scope bugs hide. Legit uses of IServiceProvider: composition-root factories
// and IServiceScopeFactory in background services. Everywhere else: constructor.

Part 4 — The Generic Host: Every Modern .NET App's Skeleton

// Console daemons, workers, and ASP.NET all share ONE bootstrap: the Generic Host.
// It wires four things: DI + Configuration + Logging + app Lifetime.
var builder = Host.CreateApplicationBuilder(args);      // (WebApplication.CreateBuilder
                                                        //  is this + HTTP)
// 1. CONFIGURATION — layered; later sources OVERRIDE earlier:
//    appsettings.json → appsettings.{Environment}.json → user-secrets (dev)
//    → environment variables → command line
//    So secrets/prod values come from env vars, NOT files in git.
var conn = builder.Configuration.GetConnectionString("Main");
var retries = builder.Configuration.GetValue<int>("Jobs:MaxRetries");

// 2. LOGGING — ILogger<T> everywhere, config-driven levels:
public class ImportJob(ILogger<ImportJob> log)
{
    public void Run(string file) =>
        log.LogInformation("Importing {File} at {Time}", file, DateTime.UtcNow);
        // STRUCTURED logging: {File} is a named property, queryable in your log
        // system — never $"interpolate {file}" into log messages (kills querying,
        // and formats even when the level is off).
}

// 3. SERVICES — everything from Parts 1–3:
builder.Services.AddHostedService<QueueWorker>();       // background work (below)

// 4. RUN — blocks until shutdown (SIGTERM/Ctrl-C), then graceful teardown:
await builder.Build().RunAsync();

// BACKGROUND SERVICES — the standard long-running worker:
public class QueueWorker(IServiceScopeFactory scopes, ILogger<QueueWorker> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {   // stoppingToken fires on shutdown — honor it (async-await.html Part 5)
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                using var scope = scopes.CreateScope();          // fresh scope per batch
                var handler = scope.ServiceProvider.GetRequiredService<JobHandler>();
                await handler.ProcessBatchAsync(stoppingToken);
            }
            catch (OperationCanceledException) { break; }        // graceful exit
            catch (Exception ex)
            {
                log.LogError(ex, "Batch failed; continuing");    // worker survives
                await Task.Delay(5_000, stoppingToken);          // backoff before retry
            }
        }
    }
}
// This + a bounded Channel = the production work-queue design from async-patterns.html.

Part 5 — Options & HttpClientFactory: The Two Patterns You'll Use Weekly

// IOPTIONS — typed, validated configuration instead of magic strings:
public class SmtpOptions
{
    public required string Host { get; set; }
    public int Port { get; set; } = 587;
    public string? User { get; set; }
}
builder.Services.AddOptions<SmtpOptions>()
    .Bind(builder.Configuration.GetSection("Smtp"))
    .ValidateDataAnnotations()
    .ValidateOnStart();                       // bad config fails AT STARTUP, not at
                                              // first email 3 hours into production
public class SmtpSender(IOptions<SmtpOptions> options) : IEmailSender
{
    private readonly SmtpOptions _opt = options.Value;
}
// Variants: IOptions<T> (singleton snapshot, 99% case) · IOptionsSnapshot<T>
// (scoped — re-reads per request, picks up config reloads) · IOptionsMonitor<T>
// (singleton + change notifications, for long-lived services).

// IHTTPCLIENTFACTORY — the correct way to use HttpClient in DI apps
// (the why: memory.html Ex 6 — per-request clients exhaust sockets; immortal
//  clients never see DNS changes; the factory pools + rotates handlers):
builder.Services.AddHttpClient<CatalogClient>(c =>
{
    c.BaseAddress = new Uri("https://api.catalog.internal");
    c.Timeout = TimeSpan.FromSeconds(5);
})
.AddStandardResilienceHandler();              // .NET 8+: retry + circuit breaker +
                                              // timeout policies, preconfigured
public class CatalogClient(HttpClient http)   // TYPED client: http is preconfigured
{
    public Task<Product?> GetAsync(string sku) =>
        http.GetFromJsonAsync<Product>($"/products/{sku}");
}
// Inject CatalogClient anywhere; the factory manages handler lifetime underneath.

Interview Questions

Q1 (Beginner): What is dependency injection and what problems does it solve?

Instead of classes constructing their own dependencies, they declare them (usually as constructor parameters) and an external composer — the DI container — supplies them. This centralizes composition (one place knows which concrete types are used), enables swapping implementations (test fakes, sandbox vs production gateways), makes dependencies explicit in the constructor signature, and — the underrated half — manages lifetimes: the container creates, shares, and disposes instances correctly (per-request DbContexts, app-wide singletons) so individual classes don't have to know how long anything lives.

Q2 (Beginner): Explain singleton, scoped, and transient with a correct example of each.

Singleton: one instance for the application lifetime — right for stateless or thread-safe shared services (an IMemoryCache, a clock, configuration). Scoped: one instance per scope, which in ASP.NET means per HTTP request — right for unit-of-work state like a DbContext, where everything in one request should share one instance but requests must not share with each other. Transient: a new instance every time it's resolved — right for cheap stateless helpers like validators. The dependency rule ties them together: a service may only depend on things that live as long or longer than itself.

Q3 (Mid): What is a captive dependency? Describe the bug it causes with a DbContext and how to catch it early.

A longer-lived service "captures" a shorter-lived dependency: e.g. a singleton whose constructor takes a scoped DbContext. The singleton is constructed once, so that DbContext instance — designed to live one request — is held forever: it's shared across concurrent requests (DbContext isn't thread-safe → corrupted tracking/random failures), its change tracker grows stale and unbounded, and its connection behavior degrades. Catch it early with UseDefaultServiceProvider(o => { o.ValidateScopes = true; o.ValidateOnBuild = true; }) — the graph is checked at startup and the app fails fast with a clear error instead of corrupting data at 3am. When a singleton genuinely needs scoped work, inject IServiceScopeFactory and create a scope per operation.

Q4 (Mid): Why does a BackgroundService need IServiceScopeFactory instead of injecting its dependencies directly?

Hosted services are singletons — constructed once at startup. Directly injecting scoped services (DbContext, unit-of-work repositories) is the captive-dependency bug: one instance shared across every iteration forever, never disposed at sensible boundaries. The pattern: inject the (singleton) IServiceScopeFactory, and per batch/message create a scope, resolve the scoped services from it, do the work, and dispose the scope — giving each unit of work the same fresh, bounded lifetime an HTTP request would get. It also protects you from the related fire-and-forget bug (async-patterns.html): background work must never borrow a request's scope, because that scope dies when the response is sent.

Q5 (Senior): Design the configuration/options strategy for a service deployed to dev/staging/prod: layering, secrets, validation, and hot-reload.

Layer configuration in the host's standard order so later sources override earlier: appsettings.json holds safe defaults and structure; appsettings.{Environment}.json holds per-environment non-secrets; secrets never touch files in the repo — user-secrets for local dev, and environment variables or a secret manager (Key Vault/AWS Secrets Manager via a configuration provider) in staging/prod. Expose settings to code exclusively through the options pattern: typed classes bound per section, with DataAnnotations or Validate(...) rules and ValidateOnStart() so a missing/invalid value fails deployment at startup rather than at first use hours later. Choose the interface by consumer lifetime: IOptions<T> for fixed config, IOptionsMonitor<T> in singletons that must observe hot-reload (reloadOnChange file providers or config-service refresh), and treat reloadable settings as an explicit, tested feature — not an accident. Log the resolved non-secret config at startup for diagnosability, and keep the set of env-var overrides documented next to the options classes.

Q6 (Senior): How would you add caching to an existing IProductCatalog used in 40 places, without touching its implementation or any consumer?

A decorator registered in the composition root. Register the concrete SqlProductCatalog as itself, then register IProductCatalog with a factory that wraps it: sp => new CachedProductCatalog(sp.GetRequiredService<SqlProductCatalog>(), sp.GetRequiredService<IMemoryCache>()). The decorator implements the same interface, delegates on miss, and caches with bounded size + expiration. All 40 consumers keep asking for IProductCatalog and transparently get the cached version; the SQL implementation remains untouched and independently testable; the composition root is the only changed file — which is exactly the point of DI: cross-cutting concerns (caching, logging, retries, metrics) compose at registration time. Libraries like Scrutor automate the wrapping (services.Decorate<IProductCatalog, CachedProductCatalog>()) when you do this often. The design caveat to state: cache invalidation policy (expiry vs explicit eviction on writes) is now a first-class decision — put writes through the decorator too so it can evict.

🏋️ Graded Exercises

1 (Easy): Register and consume: an IClock (singleton, returns DateTime.UtcNow) injected into a GreetingService (scoped) that returns "Good morning/afternoon". Then explain why IClock exists at all instead of calling DateTime.UtcNow directly.
Solution
public interface IClock { DateTime UtcNow { get; } }
public sealed class SystemClock : IClock { public DateTime UtcNow => DateTime.UtcNow; }

public class GreetingService(IClock clock)
{
    public string Greet() => clock.UtcNow.Hour < 12 ? "Good morning" : "Good afternoon";
}

builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddScoped<GreetingService>();

// Why IClock: DateTime.UtcNow is an AMBIENT dependency — invisible and uncontrollable.
// With IClock, a test injects FakeClock { UtcNow = 11:59 } and asserts "Good morning"
// deterministically. This is the rare interface-with-one-prod-implementation that
// EARNS its existence: the second implementation is the test fake you'll write today.
// (.NET 8+ ships TimeProvider in the BCL for exactly this — prefer it to rolling your own.)
2 (Easy): Each line has a lifetime bug or smell — name it: 
a) services.AddSingleton<AppDbContext>();
b) services.AddScoped<IMemoryCache, MemoryCache>();
c) services.AddSingleton<AuditLog>();   // AuditLog has: public List<string> Entries
d) services.AddTransient<IConnectionPool, ConnectionPool>();
Solution
// a) DbContext as singleton: shared across all requests/threads — DbContext is not
//    thread-safe; change tracker grows forever. → AddDbContext (scoped).
// b) A cache that's per-request isn't a cache — every request starts empty and the
//    "shared" memory is discarded per scope. → Singleton (that's the whole point).
// c) Singleton with mutable, unsynchronized state: List<string> appended by
//    concurrent requests = race/corruption (threading.html). → thread-safe structure
//    (ConcurrentQueue / Channel) or make it a real logging sink.
// d) A connection POOL created fresh per resolve pools nothing — each instance has
//    its own "pool" of one-time connections. → Singleton; pooling types are shared
//    by definition (same logic as HttpClient — memory.html Ex 6).
3 (Medium): Build a BackgroundService that every 15 minutes deletes expired sessions via the scoped AppDbContext — correct lifetimes, graceful shutdown, survives transient failures.
Solution
public class SessionCleanup(IServiceScopeFactory scopes, ILogger<SessionCleanup> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(15));  // no drift,
        try                                                             // no overlap
        {
            while (await timer.WaitForNextTickAsync(stoppingToken))
            {
                try
                {
                    using var scope = scopes.CreateScope();      // fresh scope per run
                    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                    int n = await db.Sessions
                        .Where(s => s.ExpiresAt < DateTime.UtcNow)
                        .ExecuteDeleteAsync(stoppingToken);      // set-based delete
                    log.LogInformation("Deleted {Count} expired sessions", n);
                }
                catch (Exception ex) when (ex is not OperationCanceledException)
                {
                    log.LogError(ex, "Session cleanup failed; next run in 15m");
                }   // swallow → the WORKER survives a bad run (poison-run isolation)
            }
        }
        catch (OperationCanceledException) { }                   // shutdown: exit quietly
    }
}
builder.Services.AddHostedService<SessionCleanup>();
// Singleton worker + scope-per-run = honest lifetimes; PeriodicTimer honors the
// stoppingToken so SIGTERM stops the service inside the graceful-shutdown window.

6 (Hard): Production incident: after a deploy, every request intermittently fails with ObjectDisposedException: Cannot access a disposed context instance. The diff added services.AddSingleton<RecommendationEngine>() where RecommendationEngine takes AppDbContext, and a Task.Run in the checkout handler calling a scoped service. Explain BOTH failure mechanisms and fix each.
Solution
// MECHANISM 1 — captive dependency: the singleton RecommendationEngine captured ONE
// scoped AppDbContext at first resolve. That context belongs to whichever request
// happened to construct the singleton; when that request ENDED, its scope disposed
// the context — the singleton now holds a DISPOSED DbContext forever. Every later
// use: ObjectDisposedException (intermittent because it depends on call paths).
// FIX: engine takes IServiceScopeFactory (or becomes scoped, if cheap):
public class RecommendationEngine(IServiceScopeFactory scopes)
{
    public async Task<List<Product>> RecommendAsync(Guid userId, CancellationToken ct)
    {
        using var scope = scopes.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        return await db.Products.Where(...).Take(10).ToListAsync(ct);
    }
}

// MECHANISM 2 — fire-and-forget borrowing the request scope: Task.Run(() =>
// scopedService.DoAsync(...)) captures a service from the REQUEST's scope; the
// response returns, the scope disposes (with its DbContext), and the still-running
// task then touches disposed services — same exception, different road.
// FIX: don't borrow — enqueue to a channel consumed by a BackgroundService that
// creates ITS OWN scope per job (async-patterns.html Part 6 / Q5 design):
await _checkoutQueue.Writer.WriteAsync(new CheckoutJob(orderId), ct);

// PREVENTION for both: ValidateScopes + ValidateOnBuild in dev (catches #1 at
// startup) and a code-review rule: no Task.Run on request paths — background work
// goes through the queue. The shared root cause is one sentence: A SERVICE MUST
// NEVER OUTLIVE THE SCOPE THAT BUILT ITS DEPENDENCIES.

🎯 Key Takeaways

  • DI centralizes composition and lifetime: classes declare dependencies; the composition root wires concretes; the container builds the graph and disposes what it created. Interfaces where a real second implementation exists — not as ceremony.
  • Lifetimes: singleton (stateless/thread-safe, forever), scoped (per request/unit of work — DbContext), transient (cheap and fresh). Depend only on equal-or-longer lifetimes; ValidateOnBuild + ValidateScopes makes violations fail at startup.
  • Singletons doing scoped work (background services) create a scope per operation via IServiceScopeFactory; fire-and-forget must never borrow a request's scope.
  • The Generic Host is the app skeleton: layered configuration (env vars over files, secrets never in git), structured logging with ILogger<T> templates, hosted services with honored stop tokens.
  • Options pattern (Bind + validation + ValidateOnStart) turns config into typed, startup-verified objects; IHttpClientFactory typed clients solve HttpClient lifetime with resilience built in.
  • Compose cross-cutting behavior at the root: factories, decorators, keyed services, IEnumerable<T> fan-out — consumers stay oblivious.
