EF Core in Production Professional .NET

What you'll master: Entity Framework Core as professionals run it — the DbContext mental model (change tracker + unit of work); querying that stays on the server (IQueryable, projections, split queries); the N+1 problem and every loading strategy; writing data correctly (SaveChanges, transactions, concurrency tokens, ExecuteUpdate); migrations as a deployment discipline; and the performance toolkit (AsNoTracking, compiled queries, pooling). Prerequisites: LINQ (especially IQueryable vs IEnumerable — EF is that lesson's payoff), DI & Hosting (DbContext lifetime), and SQL basics (SQL track). EF questions in interviews are really "do you know what SQL your C# generates" questions — that's the skill this lesson builds.

Part 1 — The DbContext Mental Model

// A DbContext is TWO machines in one object:
// 1. A QUERY TRANSLATOR: LINQ over DbSet<T> → SQL (via the provider).
// 2. A UNIT OF WORK: every entity it loads is TRACKED — a snapshot is kept;
//    SaveChanges() diffs current values against snapshots and emits exactly the
//    INSERT/UPDATE/DELETE statements needed, in one transaction.

public class ShopContext : DbContext
{
    public DbSet<Order> Orders => Set<Order>();
    public DbSet<Customer> Customers => Set<Customer>();
    protected override void OnModelCreating(ModelBuilder b)
    {
        b.Entity<Order>(e =>
        {
            e.Property(o => o.Total).HasPrecision(18, 2);
            e.HasIndex(o => o.CustomerId);                  // indexes live in the model
            e.HasOne(o => o.Customer).WithMany(c => c.Orders)
             .HasForeignKey(o => o.CustomerId);
            e.Property(o => o.Status).HasConversion<string>();   // enum → readable column
        });
    }
}

// The unit-of-work flow:
var order = await db.Orders.FirstAsync(o => o.Id == id);   // loaded → TRACKED
order.Status = OrderStatus.Shipped;                        // just mutate the object
await db.SaveChangesAsync();                               // diff → UPDATE Orders SET
                                                           // Status=@p WHERE Id=@id
// No "Update" call needed for tracked entities — the tracker saw the change.

// LIFETIME (di-hosting.html): one context per request/unit of work — short-lived.
builder.Services.AddDbContext<ShopContext>(o => o.UseNpgsql(conn));   // scoped
// DbContext is NOT thread-safe: never share one across parallel tasks
// (threading.html) — parallel queries need separate contexts (or sequential awaits).

Part 2 — Querying: Keep It on the Server

// DbSet<T> is IQueryable — LINQ builds an EXPRESSION TREE that becomes SQL
// (linq.html Part 4). The whole game: let the DATABASE do the filtering/paging.

var page = await db.Orders
    .Where(o => o.Status == OrderStatus.Paid && o.Total > 100)   // → WHERE
    .OrderByDescending(o => o.CreatedAt)                          // → ORDER BY
    .Skip(40).Take(20)                                            // → OFFSET/FETCH
    .Select(o => new OrderSummaryDto(o.Id, o.Total, o.Customer.Name))  // → JOIN + 3 cols
    .AsNoTracking()                       // read-only: skip snapshot bookkeeping
    .ToListAsync(ct);                     // ← SQL executes HERE, once
// The projection (Select to DTO) is the biggest everyday win: SELECT 3 columns,
// not SELECT * of two tables, and no tracking overhead — DTOs aren't entities.

// THE CLIENT-EVALUATION CLIFF (linq.html Part 6 exercise): anything EF can't
// translate THROWS. The subtle version is the premature materializer:
var expensive = (await db.Orders.ToListAsync())      // ❌ ENTIRE TABLE into memory...
    .Where(o => ComplexRule(o));                      // ...then filter in C#
var right = await db.Orders
    .Where(o => o.Total > 500)                        // SQL-translatable pre-filter
    .ToListAsync(ct);
var final = right.Where(o => ComplexRule(o)).ToList(); // C# rule on a SMALL set — deliberate

// Streaming big result sets without materializing (constant memory):
await foreach (var o in db.Orders.AsNoTracking().AsAsyncEnumerable().WithCancellation(ct))
    Export(o);                                        // async-patterns.html Part 2

Part 3 — Relationships & the N+1 Problem

// THE N+1 — the most common ORM performance bug in existence:
var customers = await db.Customers.ToListAsync();          // 1 query
foreach (var c in customers)
    Console.Write(c.Orders.Count);                         // lazy-load: +1 query EACH
// 1000 customers = 1001 round-trips. Dashboards that "got slow with growth" = this.

// STRATEGY 1 — EAGER load what you'll traverse (JOIN / batched):
var customers = await db.Customers
    .Include(c => c.Orders)                                // 1 query (or 2 split — below)
        .ThenInclude(o => o.Items)
    .ToListAsync(ct);

// STRATEGY 2 — PROJECT instead (usually better — you rarely need whole entities):
var stats = await db.Customers
    .Select(c => new { c.Name, OrderCount = c.Orders.Count,
                       Total = c.Orders.Sum(o => (decimal?)o.Total) ?? 0 })
    .ToListAsync(ct);          // ONE query with GROUP-BY-ish aggregation, 3 columns.
// EF translates navigations INSIDE Select — no Include needed for projections.

// CARTESIAN EXPLOSION: Include of MULTIPLE collections multiplies rows
// (customer × orders × addresses). Fix: split queries —
var data = await db.Customers
    .Include(c => c.Orders).Include(c => c.Addresses)
    .AsSplitQuery()            // → one query per collection, joined by EF in memory
    .ToListAsync(ct);          // trade: 3 round-trips for no row multiplication

// Lazy loading (virtual navs + proxies): OFF by default in EF Core — leave it off.
// It's the N+1 generator. Explicit is better: Include, Select, or db.Entry(c)
// .Collection(x => x.Orders).LoadAsync() for the rare on-demand case.
The habit that prevents all of this: log the SQL in development and read it. optionsBuilder.LogTo(Console.WriteLine, LogLevel.Information) (or the standard logging pipeline) shows every query EF emits. A PR that changes EF queries should quote the generated SQL when the shape isn't obvious — "1 query, indexed WHERE, 4 columns" is reviewable; "the LINQ looks fine" is not. Pair with EnableSensitiveDataLogging() locally (parameter values) and never in prod.

Part 4 — Writing Data: Transactions, Concurrency, Bulk Ops

// SaveChanges IS a transaction: all queued changes commit or roll back together.
db.Orders.Add(order);                       // Added
db.Remove(oldDraft);                        // Deleted
existing.Status = OrderStatus.Paid;         // Modified (tracked)
await db.SaveChangesAsync(ct);              // ONE transaction, correct order, FK-aware

// EXPLICIT transaction — when logic must see intermediate state or span operations:
await using var tx = await db.Database.BeginTransactionAsync(ct);
var stock = await db.Stock.FirstAsync(s => s.Sku == sku, ct);
if (stock.Quantity < qty) throw new OutOfStockException(sku);
stock.Quantity -= qty;
db.Orders.Add(order);
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

// OPTIMISTIC CONCURRENCY — two users edit the same row; last-write-wins silently
// loses data. A concurrency token detects the conflict:
public class Product
{
    [Timestamp] public byte[] RowVersion { get; set; } = default!;   // SQL Server rowversion
}   // (Postgres: b.Entity<Product>().Property(p => p.Version).IsRowVersion() via xmin)
// UPDATE ... WHERE Id=@id AND RowVersion=@original → 0 rows affected = someone else won:
try { await db.SaveChangesAsync(ct); }
catch (DbUpdateConcurrencyException ex)
{
    // choose: reload-and-retry, merge fields, or surface 409 Conflict to the user
    var entry = ex.Entries.Single();
    await entry.ReloadAsync(ct);            // e.g. retry policy re-applies the change
}

// BULK operations (EF 7+) — set-based, NO loading, NO change tracker:
await db.Sessions.Where(s => s.ExpiresAt < DateTime.UtcNow)
    .ExecuteDeleteAsync(ct);                            // one DELETE ... WHERE
await db.Orders.Where(o => o.Status == Status.Stale)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, Status.Archived), ct);
// The old way (load 100k entities, mutate, SaveChanges) is 100k tracked snapshots
// and 100k UPDATEs. ⚠ Execute* bypasses the tracker: already-loaded entities in
// this context won't reflect the change — use in maintenance paths, not mid-workflow.

Part 5 — Migrations: Schema Change as Code

dotnet ef migrations add AddOrderStatusIndex     # scaffold Up()/Down() from model diff
dotnet ef migrations script --idempotent -o deploy.sql   # SQL script for deployment

// THE DISCIPLINE:
// 1. REVIEW the generated migration — EF diffs the model, but only YOU know that
//    "rename" (it may scaffold as DROP + ADD = data loss!) or that the new NOT NULL
//    column needs a backfill. Edit migrations; they're code.
// 2. Apply via SQL SCRIPT or a migration bundle in the DEPLOY pipeline — not
//    db.Database.Migrate() at app startup in multi-instance deployments (two
//    instances racing the same DDL = lovely outage).
// 3. EXPAND/CONTRACT for zero-downtime: additive migration first (new nullable
//    column) → deploy code writing both → backfill → contract migration
//    (drop old column) LAST, once no code reads it. Never break the schema the
//    currently-running version depends on.
// 4. Down() is a courtesy for dev; production rollback = a new forward migration.

// TESTING with a real database — the modern default is Testcontainers:
// spin up throwaway Postgres/SQL Server in Docker per test run; run migrations;
// test against REAL SQL semantics. The InMemory provider is NOT a database:
// no transactions, no constraints, different LINQ translation — it passes tests
// your production DB fails. SQLite in-memory is the lightweight middle ground
// when its SQL dialect covers your usage. (More in testing.html.)

Interview Questions

Q1 (Beginner): What does "change tracking" mean, and why does SaveChanges know what to update without you telling it?

When a query materializes entities, the context stores a snapshot of each entity's original values and keeps a reference in its change tracker. You then mutate the objects like normal C#. SaveChanges compares current values against the snapshots, computes each entity's state (Added/Modified/Deleted/Unchanged), and generates exactly the needed SQL statements, wrapped in a single transaction. That's the unit-of-work pattern: the context represents "one business operation's changes," committed atomically. It's also why read-only queries should skip tracking (AsNoTracking) — the bookkeeping costs memory and time you'll never use.

Q2 (Beginner): What is the N+1 query problem? How do you detect and fix it in EF Core?

Loading a list (1 query) and then accessing a navigation property per item, causing one additional query per row — 1000 items = 1001 round-trips; pages get slower as data grows. Detect it by logging SQL in development (LogTo) and watching for repeated identical queries with different parameters, or via APM showing hundreds of queries per request. Fixes: eager-load the navigations you traverse (Include/ThenInclude), or — usually better — project exactly what the view needs with Select, which EF translates into one joined/aggregated query. EF Core keeps lazy loading off by default precisely because it silently manufactures this bug.

Q3 (Mid): Why is DbContext scoped per request, and what specifically breaks when it's a singleton or shared across threads?

A context is a unit of work with mutable, non-thread-safe state (the change tracker and an active connection/transaction). As a singleton: the tracker accumulates every entity ever loaded (unbounded memory, stale data served from the tracker), and concurrent requests hit the same non-thread-safe object — causing "a second operation was started on this context" exceptions or corrupted tracking. Shared across parallel tasks within one request, same crash. Scoped-per-request gives each request an isolated, short-lived unit of work, disposed (connection released) when the request ends — and it composes with DI's captive-dependency rule: never inject a context into a singleton; background workers create their own scope per batch (di-hosting.html).

Q4 (Mid): Explain optimistic concurrency in EF Core end to end: mechanism, what the developer handles, and when you'd prefer it over pessimistic locking.

Add a concurrency token (e.g. a [Timestamp]/rowversion column the DB bumps on every update). EF includes the token's original value in the UPDATE's WHERE clause; if another transaction changed the row since you read it, the WHERE matches zero rows and EF throws DbUpdateConcurrencyException instead of silently overwriting. The developer decides the resolution: reload-and-retry (apply the change to fresh data), field-level merge, or bubble a 409 to the user ("this record was modified — review and resubmit"). Optimistic wins when conflicts are rare — no locks held during user think-time, full read concurrency; pessimistic locking (SELECT … FOR UPDATE inside a transaction) wins for hot contended rows where conflicts are the norm and retry storms would be worse — e.g. inventory decrement, seat booking.

Q5 (Senior): Design the migration/deployment strategy for a 24/7 service with 6 instances and a large table needing a column rename. No downtime allowed.

Never let instances run DDL: migrations execute once in the pipeline (idempotent script or EF bundle) before rollout, not Migrate() at startup. A rename is expand/contract, since EF's scaffolded diff may produce drop+add (data loss) and a hard rename breaks the running version: (1) Expand — migration adds the new column, nullable; review/edit the scaffold. (2) Dual-write deploy — code writes both columns, reads old-preferring; ship to all instances. (3) Backfill — batched ExecuteUpdate/SQL job copying old→new (batched to bound lock time on the large table; concurrently-created rows are covered by dual-writes). (4) Flip reads to the new column; verify. (5) Contract — after a bake period, deploy code that ignores the old column, then a final migration drops it. Each step is individually roll-back-able by deploying the previous code, because the schema always supports both the current and previous app versions — that invariant is the whole strategy.

Q6 (Senior): An endpoint using EF is slow. Walk through your diagnosis path and name the most likely fixes in order of probability.

Get evidence first: enable query logging/APM for the endpoint and answer three questions — how many queries, what SQL shape, how long each. Most likely findings, in order: (1) N+1 — dozens/hundreds of small queries → Include or project (single biggest hit rate). (2) Missing index — one query, table scan on the WHERE/JOIN column → check the DB's execution plan, add HasIndex + migration. (3) Over-fetching — SELECT * of wide entities plus unneeded Includes for a list view → DTO projection with just the columns, AsNoTracking. (4) Cartesian explosion from multiple collection Includes → AsSplitQuery. (5) Client evaluation/premature materialization — ToList mid-query → recompose on IQueryable. (6) Only after query shape is right: contention/pool exhaustion (too few connections, long transactions) and, rarely, EF overhead itself → compiled queries, context pooling, or raw SQL for the one pathological query. The meta-answer interviewers want: read the generated SQL and the execution plan before touching any C#.

2 (Easy): This page renders a customer list with their order counts and last order date, and it's slow. Count the queries it runs for 500 customers, then fix it to one. 
var customers = await db.Customers.ToListAsync();
foreach (var c in customers) {
    model.Add(new Row(c.Name, c.Orders.Count, c.Orders.Max(o => o.CreatedAt)));
}
Solution
// Query count: 1 (customers) + 500 (Orders loaded per customer for .Count) = 501.
// (With lazy loading off, it's worse: c.Orders is EMPTY/null → silent wrong data —
//  both failure modes come from traversing navigations post-materialization.)
var model = await db.Customers
    .Select(c => new Row(
        c.Name,
        c.Orders.Count,
        c.Orders.Max(o => (DateTime?)o.CreatedAt)))   // nullable: customer w/ 0 orders
    .ToListAsync(ct);
// ONE query — EF translates the navigation aggregates into a grouped JOIN.
// The (DateTime?) cast matters: Max over an empty set is NULL in SQL; the nullable
// cast makes that legal instead of throwing (same trick as linq.html's Sum).
3 (Medium): Implement "decrement stock and create the order atomically; oversell must be impossible even under concurrent checkouts." Show the transaction and explain where optimistic concurrency fits.
Solution
public async Task<Order> CheckoutAsync(string sku, int qty, CancellationToken ct)
{
    for (int attempt = 1; ; attempt++)
    {
        try
        {
            var stock = await db.Stock.FirstAsync(s => s.Sku == sku, ct);
            if (stock.Quantity < qty) throw new OutOfStockException(sku);

            stock.Quantity -= qty;                     // tracked change
            var order = new Order { Sku = sku, Qty = qty };
            db.Orders.Add(order);
            await db.SaveChangesAsync(ct);             // ONE transaction: UPDATE + INSERT.
            return order;                              // Stock has a RowVersion token ↓
        }
        catch (DbUpdateConcurrencyException) when (attempt < 3)
        {
            db.ChangeTracker.Clear();                  // drop stale state, re-read, retry
        }
    }
}
// Why this is oversell-proof: Stock carries a [Timestamp] RowVersion. Two concurrent
// checkouts both read Quantity=5; both try UPDATE ... WHERE RowVersion=@orig; the
// DB serializes them — the second's WHERE matches 0 rows → concurrency exception →
// retry re-reads Quantity=3 and re-checks the guard. The check-then-act is made
// atomic by token + retry, without holding locks during the read.
// Alternative for HOT skus: pessimistic (SELECT ... FOR UPDATE inside an explicit
// transaction) or a set-based guard:
//   ExecuteUpdate(s => s.SetProperty(x => x.Quantity, x => x.Quantity - qty))
//     on .Where(x => x.Sku == sku && x.Quantity >= qty) → 0 rows = out of stock.

Solution
// WRONG: drop+add DESTROYS every value in Login — EF's model diff can't know
// "rename" from "delete one property, add another". Migrations are code: REVIEW & EDIT.
public partial class RenameLoginToEmail : Migration
{
    protected override void Up(MigrationBuilder mb)
        => mb.RenameColumn(name: "Login", table: "Users", newName: "Email");
    protected override void Down(MigrationBuilder mb)
        => mb.RenameColumn(name: "Email", table: "Users", newName: "Login");
}
// RenameColumn preserves data (sp_rename / ALTER ... RENAME under the hood).
// Ship: take the maintenance window, run the migration via idempotent script
// (dotnet ef migrations script --idempotent), deploy the code that uses Email.
// (Zero-downtime multi-instance would need expand/contract instead — Q5 —
//  but with a window and one instance, the direct rename is the lazy CORRECT fix.)
5 (Hard): A nightly job archives ~2M old orders by loading them, setting Status = Archived, and calling SaveChanges in a loop. It takes 4 hours and OOMs sometimes. Rewrite it, then explain the caveat your rewrite introduces.
Solution
// PROBLEMS: 2M tracked entities (snapshots → OOM risk — memory.html), 2M UPDATE
// statements, hours of round-trips, growing change tracker slowing every SaveChanges.

// REWRITE — set-based, batched (bound transaction size / lock time):
public async Task ArchiveOldOrdersAsync(CancellationToken ct)
{
    const int batch = 50_000;
    int total = 0, affected;
    do
    {
        affected = await db.Orders
            .Where(o => o.Status == OrderStatus.Completed
                     && o.CompletedAt < DateTime.UtcNow.AddYears(-1))
            .OrderBy(o => o.Id).Take(batch)             // batched: short transactions,
            .ExecuteUpdateAsync(s =>                    // no lock-the-table-for-minutes
                s.SetProperty(o => o.Status, OrderStatus.Archived), ct);
        total += affected;
        _log.LogInformation("Archived {N} (running total {T})", affected, total);
    } while (affected == batch && !ct.IsCancellationRequested);
}
// Nothing is loaded or tracked: each batch is ONE UPDATE ... WHERE ... in the DB.
// 4 hours → minutes; memory flat.
// CAVEAT: ExecuteUpdate bypasses the change tracker AND all EF-level behaviors —
// any tracked Order instances in this context are now stale, no domain events/
// interceptors/audit hooks fire, and updated-at columns must be set explicitly in
// SetProperty. Fine for a maintenance job; NOT a substitute for tracked updates
// inside business workflows that rely on those behaviors.
6 (Hard): Your team's integration tests use the InMemory provider and are green, but production hit three bugs the tests missed: a unique-constraint violation, a transaction that didn't roll back, and a LINQ query that threw "could not be translated". Explain why InMemory missed each, and set up the better harness.
Solution
// WHY INMEMORY MISSED THEM (it is a fake object store, not a database):
// 1. Unique constraint — InMemory doesn't enforce relational constraints (unique
//    indexes, FKs): duplicate insert "succeeds" in tests, violates in Postgres.
// 2. Transactions — InMemory ignores them (BeginTransaction is a no-op shell):
//    the "rolled back" write persisted in the test, hiding the missing rollback path.
// 3. Translation — InMemory executes LINQ as LINQ-to-Objects: EVERYTHING is
//    "translatable". The real provider's SQL translator rejected the expression.

// BETTER HARNESS — Testcontainers: the real engine, throwaway per test class:
public class DbFixture : IAsyncLifetime
{
    private readonly PostgreSqlContainer _pg = new PostgreSqlBuilder()
        .WithImage("postgres:16-alpine").Build();
    public ShopContext CreateContext() => new(new DbContextOptionsBuilder<ShopContext>()
        .UseNpgsql(_pg.GetConnectionString()).Options);

    public async Task InitializeAsync()
    {
        await _pg.StartAsync();
        await using var db = CreateContext();
        await db.Database.MigrateAsync();       // REAL schema via REAL migrations —
    }                                           // which also tests the migrations!
    public Task DisposeAsync() => _pg.DisposeAsync().AsTask();
}

[Collection("db")]                              // share the container across the class
public class OrderRepositoryTests(DbFixture fx)
{
    [Fact]
    public async Task Duplicate_sku_violates_unique_index()
    {
        await using var db = fx.CreateContext();
        db.Products.Add(new Product { Sku = "X" });
        await db.SaveChangesAsync();
        db.Products.Add(new Product { Sku = "X" });
        await Assert.ThrowsAsync<DbUpdateException>(() => db.SaveChangesAsync());
    }   // now the test sees what production sees
}
// Cost: Docker + ~2s container start per run (amortized via fixture). Worth it:
// constraints, transactions, translation, and migrations are all REAL.
// (SQLite in-memory is the lighter option when your SQL stays inside its dialect.)

🎯 Key Takeaways

  • DbContext = query translator + unit of work: tracked entities diff at SaveChanges into one transaction; scoped per request; never shared across threads.
  • Keep queries on the server: compose on IQueryable, project to DTOs (Select), page and aggregate in SQL, materialize last; read the generated SQL as a habit.
  • N+1 is the ORM bug: Include what you traverse or project instead; AsSplitQuery for multi-collection includes; lazy loading stays off.
  • Writes: SaveChanges is atomic; concurrency tokens + DbUpdateConcurrencyException handling prevent silent last-write-wins; ExecuteUpdate/Delete for set-based bulk work (bypasses the tracker — knowingly).
  • Migrations are reviewed code, applied once per deploy from the pipeline; zero-downtime = expand/contract; rollback = forward migration.
  • Performance order: fix query shape (N+1, projections, indexes) before EF machinery (pooling, compiled queries); test against a real database (Testcontainers), not the InMemory provider.
