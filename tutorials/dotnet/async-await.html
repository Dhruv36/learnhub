async/await & Tasks Async & Concurrency

What you'll master: the real mental model of async/await — what a Task is, what the compiler generates, and which thread runs what; why async exists (scalability, not speed); composing tasks with WhenAll/WhenAny; exception behavior in async code; async void; ValueTask; and cancellation with CancellationToken. Prerequisites: Delegates (continuations are delegates), Exceptions (async changes where they surface). Async is the single most-tested .NET topic in mid/senior interviews — and the most misunderstood, because the syntax hides the machinery. This lesson shows the machinery.

Part 1 — Why Async Exists: Threads Are Expensive, Waiting Is Free

// SYNCHRONOUS I/O — the thread is HELD HOSTAGE while the network does the work:
public string Download(string url)
{
    var response = _http.GetString(url);   // thread BLOCKS here ~200ms doing NOTHING
    return response.ToUpper();             // ...then 0.1ms of actual CPU work
}
// A web server with 200 threads handling requests like this saturates at ~200 concurrent
// requests — not because the CPU is busy (it's idle!) but because every thread is parked
// waiting on I/O. Each thread costs ~1MB of stack. Threads are the scarce resource.

// ASYNCHRONOUS I/O — the thread is RELEASED during the wait:
public async Task<string> DownloadAsync(string url)
{
    var response = await _http.GetStringAsync(url);   // thread goes back to the pool;
    return response.ToUpper();                        // resumed (on some thread) when done
}
// The OS notifies .NET when the network completes (I/O completion ports — no thread
// waits). The same 200 threads now serve tens of thousands of concurrent requests.

// THE POINT: async does NOT make one request faster (it adds a hair of overhead).
// It makes the SERVER scale — throughput under concurrency, not latency of one call.
// For CPU-bound work there is nothing to await; that's threads/parallelism (threading.html).

Part 2 — What a Task Is, and What await Actually Does

// Task<T> = a HANDLE to an ongoing or completed operation. It carries:
//   Status     (Created / Running / RanToCompletion / Faulted / Canceled)
//   Result     (T, once complete)
//   Exception  (if faulted — exceptions are STORED in the task, not thrown at you)
// A Task is a promise, not a thread. Most I/O tasks occupy NO thread while "running."

// await, precisely:
var data = await FetchAsync();
// 1. Calls FetchAsync() — which runs SYNCHRONOUSLY until ITS first incomplete await,
//    then returns a Task to us. (async methods start on the CALLER's thread!)
// 2. If that task is ALREADY COMPLETE → continue immediately, same thread. Zero cost.
// 3. If not complete → the method RETURNS to its caller right there, freeing the thread.
//    The rest of the method is registered as a CONTINUATION (a delegate) on the task.
// 4. When the task completes, the continuation is scheduled and the method RESUMES
//    from this exact point — locals intact, possibly on a DIFFERENT thread.
// 5. If the task faulted → the stored exception is RETHROWN here (trace preserved).

// The compiler rewrites the whole method into a STATE MACHINE (a struct implementing
// IAsyncStateMachine): each await is a state; locals become fields so they survive
// suspension. "async/await" is syntax over continuation-passing — delegates all the
// way down (delegates-events.html).
The mental model that answers every interview follow-up: "an async method runs synchronously until the first incomplete await, then returns its Task to the caller; the remainder is a continuation that resumes when the awaited task completes." From this one sentence you can derive: why exceptions before the first await surface synchronously, why an already-complete await costs nothing, why the code after await may run on another thread, and why forgetting await means the method keeps running unobserved in the background.
// Where does the continuation RESUME? SynchronizationContext decides:
//  - UI apps (WPF/WinForms/MAUI): captured context = the UI thread → continuation resumes
//    ON the UI thread. Convenient (touch controls safely) but enables a classic DEADLOCK:
//    button click calls DoAsync().Result → UI thread blocks waiting for the task →
//    the continuation needs the UI thread to complete → both wait forever.
//  - ASP.NET Core: NO SynchronizationContext → continuations run on any pool thread;
//    .Result deadlocks don't occur (but .Result still BLOCKS a thread — don't).
//  - ConfigureAwait(false): "resume anywhere, don't capture context" — library code
//    should use it (avoids deadlocks under UI hosts + skips a context hop).
await SomethingAsync().ConfigureAwait(false);   // in libraries; app code rarely needs it

Part 3 — Composition: Sequential vs Concurrent, WhenAll, WhenAny

// SEQUENTIAL awaits — each starts only after the previous finishes (300ms total):
var user   = await GetUserAsync(id);       // 100ms
var orders = await GetOrdersAsync(id);     // 100ms
var recs   = await GetRecsAsync(id);       // 100ms

// CONCURRENT — start ALL, then await all (100ms total — the slowest one):
var userTask   = GetUserAsync(id);         // calling WITHOUT await STARTS the work
var ordersTask = GetOrdersAsync(id);       // all three now in flight
var recsTask   = GetRecsAsync(id);
await Task.WhenAll(userTask, ordersTask, recsTask);
var user = userTask.Result;                // safe: task known complete (no blocking)
// or: var (u, o, r) = (await userTask, await ordersTask, await recsTask);

// Only compose independent operations — orders needing user.Id must stay sequential.

// Task.WhenAny — first one wins (hedging, timeouts):
var winner = await Task.WhenAny(primary, fallback);
var result = await winner;                 // await the winner to get value/exception

// Timeout, the modern way (.NET 6+):
var data = await FetchAsync().WaitAsync(TimeSpan.FromSeconds(5));   // TimeoutException

// Fan-out over a collection:
var results = await Task.WhenAll(ids.Select(GetUserAsync));         // User[]
// ⚠ Unbounded fan-out (10,000 ids = 10,000 concurrent calls) can DoS your own
// dependency — bound it with Parallel.ForEachAsync or SemaphoreSlim (async-patterns.html).

Part 4 — Exceptions, async void, and Fire-and-Forget

// Exceptions in an async method are CAPTURED into the returned Task,
// and rethrown when (and only when) the task is AWAITED:
async Task BoomAsync() { await Task.Delay(10); throw new InvalidOperationException(); }

var t = BoomAsync();          // no throw here — the exception sits in t
try { await t; }              // rethrown HERE, original stack preserved
catch (InvalidOperationException) { }

// FORGOTTEN task = UNOBSERVED exception = silent failure:
_ = BoomAsync();              // fire-and-forget: exception vanishes (crashes nothing,
                              // logs nothing). If you MUST fire-and-forget, wrap:
_ = SafeFireAndForget(BoomAsync());
static async Task SafeFireAndForget(Task t)
{ try { await t; } catch (Exception ex) { Log(ex); } }

// Task.WhenAll with multiple failures: awaiting it rethrows only the FIRST exception.
// To see all: catch, then inspect whenAllTask.Exception (AggregateException) —
try { await Task.WhenAll(a, b, c); }
catch { foreach (var ex in new[]{a,b,c}.Where(t => t.IsFaulted)
                                        .SelectMany(t => t.Exception!.InnerExceptions))
            Log(ex); }

// ASYNC VOID — the special disaster:
async void Handler() { await Task.Delay(10); throw new Exception(); }
// No Task is returned → nothing can await or observe it → the exception is rethrown
// on the SynchronizationContext and CRASHES THE PROCESS. async void exists ONLY
// because event handler signatures are void:
button.Click += async (s, e) => { try { await SaveAsync(); } catch (Exception ex) { Show(ex); } };
// Rule: async void ONLY for event handlers, and those must catch their own exceptions.
// Everything else returns Task — even if the caller ignores it, it's OBSERVABLE.

Part 5 — Cancellation: The Cooperative Contract

// .NET cancellation is COOPERATIVE — nothing is killed; work is politely asked to stop.
// CancellationTokenSource creates; CancellationToken flows through the call chain.
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30));  // auto-cancel
CancellationToken ct = cts.Token;

public async Task<Report> BuildReportAsync(CancellationToken ct)
{
    var raw = await FetchAsync(url, ct);          // 1. PASS the token to everything async
    foreach (var chunk in raw.Chunks)
    {
        ct.ThrowIfCancellationRequested();        // 2. CHECK it in CPU loops
        Process(chunk);
    }
    return Assemble(raw);
}
// Cancelled operations throw OperationCanceledException — that's the protocol, not an
// error: catch it at the entry point and exit quietly (exceptions-nullability.html Ex 6).
// ASP.NET Core gives you HttpContext.RequestAborted — pass it down so abandoned
// requests stop burning your database.

// Linking tokens (user cancel + timeout together):
using var linked = CancellationTokenSource.CreateLinkedTokenSource(userCt, timeoutCt);
await WorkAsync(linked.Token);      // fires when EITHER source cancels

// Conventions: token is the LAST parameter, named cancellationToken, default(CancellationToken)
// optional in public APIs. Accept-and-flow even if you don't check it — the methods you
// call will.

Part 6 — ValueTask, Task.Run, and the Rules That Keep You Safe

// ValueTask<T>: a struct that avoids allocating a Task WHEN THE RESULT IS ALREADY
// AVAILABLE (cache hits, buffered reads). Task<T> allocates even for sync completion.
public ValueTask<User> GetUserAsync(Guid id)
    => _cache.TryGetValue(id, out var u)
        ? new ValueTask<User>(u)                       // sync path: ZERO allocation
        : new ValueTask<User>(LoadFromDbAsync(id));    // async path: normal task
// Constraints (why Task is still the default): await a ValueTask ONCE, never twice;
// no WhenAll composition without .AsTask(). Use in hot APIs where the sync path
// dominates — that's why Stream.ReadAsync and channels use it.

// Task.Run = "do this CPU work on a thread-pool thread" — for OFFLOADING, not I/O:
var report = await Task.Run(() => CrunchNumbers(data), ct);   // keeps UI responsive
// ❌ In ASP.NET: wrapping I/O in Task.Run burns an extra thread and helps nothing;
//    request handlers are already on pool threads. Task.Run is a client-app tool.

// THE RULES (each one prevents a production incident):
// 1. Async all the way down — never .Result/.Wait()/.GetAwaiter().GetResult() on an
//    incomplete task (deadlock under a SynchronizationContext; blocked thread everywhere).
// 2. async void only for event handlers; they catch their own exceptions.
// 3. Suffix async methods with Async; accept a CancellationToken and FLOW it.
// 4. Don't await in a loop what you could WhenAll (and bound your fan-out).
// 5. Libraries: ConfigureAwait(false). Apps: usually irrelevant.
// 6. Never ignore a returned Task — un-awaited tasks hide exceptions.

Interview Questions

Q1 (Beginner): What problem does async/await solve? Does it make code faster?

async/await solves the problem of waiting without blocking a thread. Most server and UI code spends its time waiting on I/O — a database query, an HTTP call, a file read. With synchronous code, the thread that made the call sits idle, blocked, until the result arrives.

That is expensive in two settings. On a server, each blocked thread is a thread the thread pool cannot use for another request. Under load, blocked threads pile up, the pool grows slowly, and requests queue — the classic symptom of thread-pool starvation: CPU is low but latency climbs. In a UI application, blocking the UI thread freezes the window.

With await, the method registers a continuation and returns the thread while the I/O is in flight. When the result arrives, the rest of the method runs. The compiler turns the method into a state machine so the code still reads top to bottom, instead of a chain of callbacks.

  public async Task<Order> GetOrderAsync(int id)
  {
      var order = await _db.Orders.FindAsync(id);    // thread is free while the query runs
      order.Lines = await _api.GetLinesAsync(id);
      return order;
  }

Does it make code faster? Not an individual operation. The query takes exactly as long, and the state machine adds a small overhead. What async improves is scalability and responsiveness: the same server handles far more concurrent requests with fewer threads, and the UI stays responsive. It can make a workflow faster only when you use it to run independent operations concurrently, as in Q4. For CPU-bound work, async does nothing; that needs parallelism, such as Task.Run or Parallel.For.

Q2 (Beginner): What is a Task, and what's the difference between Task and Task<T>?

A Task is an object representing an operation that may not have finished yet — a promise of a future outcome. It tracks the operation's state: running, completed successfully, faulted with an exception, or cancelled. You can await it, attach continuations, and combine it with others.

The difference is whether the operation produces a value:

  Task SaveAsync(Order o);                // completes, no result — the async "void"
  Task<Order> LoadAsync(int id);         // completes with an Order

  await SaveAsync(order);
  Order o = await LoadAsync(42);          // await unwraps the T

Task is the asynchronous equivalent of a void method: awaiting it tells you the operation finished, or throws its exception. Task<T> is the equivalent of a method returning T: awaiting it gives you the value.

Several details follow. A task is not a thread: an I/O-bound task may involve no thread at all while it waits. Exceptions are stored in the task and rethrown when it is awaited, which is why an exception from an un-awaited task can go unnoticed. And the one legitimate use of async void is an event handler; anywhere else it makes the operation impossible to await, and an exception crashes the process.

There is also ValueTask<T>, a struct that avoids allocating a task when the result is often available synchronously, such as a cache hit. It has restrictions — await it only once — so return Task by default and reach for ValueTask only on measured hot paths.

Q3 (Mid): Walk through exactly what happens, thread-wise, when a method hits await client.GetStringAsync(url).

1. The call runs synchronously first. GetStringAsync is called on the current thread. It builds the request and starts the network I/O, handing it to the operating system, then returns an incomplete Task. No thread is dedicated to waiting on the network.

2. The await checks the task. If the task has already completed — a cached result — execution simply continues on the same thread with no suspension at all.

3. Otherwise the method suspends. The compiler-generated state machine records where it is and its local variables, registers a continuation on the task, and returns to its caller. The caller receives an incomplete task of its own, and so on up the chain. The thread is released — in ASP.NET Core it goes back to the thread pool to serve other requests.

4. While waiting, no thread is involved. The OS tracks the socket; the pending operation is just data in memory.

5. The I/O completes. The OS signals completion through an I/O completion port, and a thread-pool thread marks the task complete and runs the continuation.

6. Where the continuation runs depends on the synchronisation context. In ASP.NET Core there is none, so the rest of the method runs on whichever pool thread is available — often a different thread from the one that started. In a UI application, the captured context posts the continuation back to the UI thread, so the code can update controls.

That last point explains the classic deadlock: blocking on .Result in a UI thread while the continuation waits to run on that same thread. It is also why library code uses ConfigureAwait(false), which says "do not return to the captured context".

Q4 (Mid): Three independent API calls take 100ms each. Show the difference between awaiting them sequentially and concurrently, including how to get the results and what happens if two of them fail. 
  // sequential: ~300ms — each call starts only after the previous one finishes
  var user   = await GetUserAsync(id);
  var orders = await GetOrdersAsync(id);
  var prefs  = await GetPrefsAsync(id);

  // concurrent: ~100ms — start all three, then await them together
  var userTask   = GetUserAsync(id);
  var ordersTask = GetOrdersAsync(id);
  var prefsTask  = GetPrefsAsync(id);
  await Task.WhenAll(userTask, ordersTask, prefsTask);

  var user   = userTask.Result;      // safe: the task has already completed
  var orders = await ordersTask;     // or await again — completes immediately

The key is starting all the tasks before awaiting any of them. Calling an async method starts the operation; await only waits for it. Writing await on each call in turn makes independent calls wait for each other, and total time becomes the sum instead of the maximum.

To get the results, keep the individual task variables and read them after WhenAll. Reading .Result is safe at that point, because every task has completed; awaiting them again is equally correct and reads more naturally. If the calls return the same type, await Task.WhenAll(tasks) returns an array of results.

If two fail, WhenAll waits for all three to finish, then its task faults with an AggregateException containing both exceptions. But await rethrows only the first, so a catch sees one error and the other is easily lost. To handle every failure, inspect the WhenAll task's Exception.InnerExceptions, or check each task's IsFaulted. And decide deliberately whether a partial failure should fail the whole operation or return the results that did succeed.

Q5 (Senior): Explain the classic .Result deadlock: why it hangs in a WPF app but not in ASP.NET Core, and the fixes.

In WPF, await captures the UI thread's SynchronizationContext, so the async method's continuation must run on the UI thread. If the UI thread calls DoAsync().Result, it blocks waiting for the task — but the task can only complete by running its continuation on that same blocked UI thread: circular wait, permanent hang. ASP.NET Core removed the SynchronizationContext; continuations resume on any pool thread, so the circularity disappears — .Result merely blocks one thread (still harmful for scalability, occasionally pool-starving under load, but not a guaranteed deadlock). Fixes: go async all the way (make the caller async — the real fix); in library code use ConfigureAwait(false) so continuations don't need the captured context; as a last resort for legacy sync entry points, Task.Run(() => DoAsync()).GetAwaiter().GetResult() escapes the context at the cost of a pool thread.

Q6 (Senior): When would you use ValueTask<T> over Task<T>, and what constraints does it impose?

Task<T> allocates a heap object even when the method completes synchronously. For APIs called at very high frequency where the synchronous path dominates — cache lookups that usually hit, stream reads served from a buffer — ValueTask<T> (a struct) wraps either an immediate result (zero allocation) or an underlying task. That's why Stream.ReadAsync and Channel APIs return it. Constraints: a ValueTask may be awaited only once and must not be awaited concurrently or stored for re-use (its backing object may be pooled and recycled — double-await is undefined behavior); composition like WhenAll requires .AsTask(), forfeiting the benefit. Default to Task; adopt ValueTask from profiling evidence in hot paths, and keep the awaiting pattern trivial (immediately await the call).

🏋️ Graded Exercises

1 (Easy): Predict the output order: 
async Task<int> WorkAsync() {
    Console.Write("B");
    await Task.Delay(50);
    Console.Write("D");
    return 42;
}
Console.Write("A");
var t = WorkAsync();
Console.Write("C");
Console.Write(await t);
Solution
// A B C D 42
// A: before the call. B: WorkAsync runs SYNCHRONOUSLY on the caller's thread until
// its first incomplete await (Task.Delay) — so B prints during the call itself.
// At the await, WorkAsync returns an incomplete Task → caller continues → C.
// ~50ms later the continuation resumes → D, task completes with 42 → await t yields 42.
// If Task.Delay(50) were Task.Delay(0)/already complete, order could be A B D C 42 —
// "runs synchronously until the first INCOMPLETE await" is the governing rule.
2 (Easy): This UI click handler freezes the app for 3 seconds. Fix it, and explain why your fix works. 
void OnClick(object s, EventArgs e) {
    var report = BuildReportAsync().Result;   // BuildReportAsync takes ~3s
    Show(report);
}
Solution
async void OnClick(object s, EventArgs e)      // async void OK: it IS an event handler
{
    try
    {
        var report = await BuildReportAsync(); // UI thread released during the 3s;
        Show(report);                          // continuation resumes ON the UI thread
    }                                          // (captured context) so Show is safe
    catch (Exception ex) { ShowError(ex); }    // async void must catch its own errors
}
// .Result BLOCKED the UI thread (no message pumping → frozen window), and under a
// SynchronizationContext it risks full deadlock. await keeps the UI live and returns
// to the UI thread automatically for Show(report).
3 (Medium): A dashboard loads profile (120ms), orders (200ms), and notifications (80ms) sequentially — 400ms total. Rewrite for minimum latency with per-call error isolation: any one failing shows a placeholder, the others still render.
Solution
var profileTask = SafeLoad(GetProfileAsync(id),      Profile.Placeholder);
var ordersTask  = SafeLoad(GetOrdersAsync(id),       Array.Empty<Order>());
var notifsTask  = SafeLoad(GetNotificationsAsync(id), Array.Empty<Notif>());
await Task.WhenAll(profileTask, ordersTask, notifsTask);   // ~200ms (the slowest)
Render(profileTask.Result, ordersTask.Result, notifsTask.Result);

static async Task<T> SafeLoad<T>(Task<T> task, T fallback)
{
    try { return await task; }
    catch (Exception ex) { Log(ex); return fallback; }   // isolate: one failure ≠ page failure
}
// Start all three BEFORE any await (they run concurrently); wrap each so a fault
// resolves to a fallback instead of faulting WhenAll. Latency: max(120,200,80)=200ms.
4 (Medium): Add proper cancellation to this worker: it should stop within a second of being asked, and its caller should distinguish "cancelled" from "failed". 
public async Task ProcessAllAsync(List<Item> items) {
    foreach (var item in items)
        await ProcessOneAsync(item);          // each takes ~1s
}
Solution
public async Task ProcessAllAsync(List<Item> items, CancellationToken ct)
{
    foreach (var item in items)
    {
        ct.ThrowIfCancellationRequested();     // fast exit between items
        await ProcessOneAsync(item, ct);       // FLOW the token so an in-flight item
    }                                          // can also stop (~within 1s guaranteed)
}

// Caller:
using var cts = new CancellationTokenSource();
var run = ProcessAllAsync(items, cts.Token);
// ... user clicks Stop:
cts.Cancel();
try { await run; }
catch (OperationCanceledException) { Status("Stopped by user"); }     // CANCELLED
catch (Exception ex)               { Status($"Failed: {ex.Message}"); } // FAILED
// The OCE-vs-Exception split IS the distinction — cancellation isn't an error;
// it must not page anyone or hit error dashboards.
5 (Hard): Find the three async bugs: 
public async void SyncInventory() {
    foreach (var sku in _skus)
        _ = UpdateSkuAsync(sku);
    _log.LogInformation("All inventory synced");
}
Solution
// BUG 1: async void — no Task returned; callers can't await or observe; any exception
//         escaping SyncInventory crashes the process.
// BUG 2: discarded tasks (_ =) — every UpdateSkuAsync runs unobserved: failures vanish
//         silently, and nothing waits for completion.
// BUG 3: the log line lies — it runs immediately after STARTING the updates,
//         not after they finish. Classic "sometimes data is missing" incident.
public async Task SyncInventoryAsync(CancellationToken ct = default)
{
    var results = await Task.WhenAll(_skus.Select(async sku =>
    {
        try { await UpdateSkuAsync(sku, ct); return (sku, error: (Exception?)null); }
        catch (Exception ex) { return (sku, error: ex); }      // per-SKU isolation
    }));
    foreach (var (sku, error) in results.Where(r => r.error is not null))
        _log.LogError(error, "SKU {Sku} failed", sku);
    _log.LogInformation("Inventory sync complete: {Ok}/{Total}",
        results.Count(r => r.error is null), results.Length);   // now TRUE
}
// (Real systems also bound the fan-out — SemaphoreSlim/Parallel.ForEachAsync,
//  covered in async-patterns.html.)
6 (Hard): Implement GetConfigAsync: returns a cached config with zero allocation on hits; on a miss, loads it (once) from disk. Use ValueTask. State the constraint your API imposes on callers.
Solution
private Config? _cached;

public ValueTask<Config> GetConfigAsync(CancellationToken ct = default)
{
    // HOT PATH — cache hit: struct ValueTask wraps the value, NO heap allocation:
    if (_cached is not null) return new ValueTask<Config>(_cached);
    // COLD PATH — delegate to a normal async method (allocates once, fine):
    return new ValueTask<Config>(LoadAndCacheAsync(ct));
}

private async Task<Config> LoadAndCacheAsync(CancellationToken ct)
{
    var json = await File.ReadAllTextAsync(_path, ct);
    return _cached = JsonSerializer.Deserialize<Config>(json)!;
}

// CALLER CONSTRAINT: await the ValueTask exactly ONCE, immediately:
//   var cfg = await store.GetConfigAsync(ct);          ✅
//   var vt = store.GetConfigAsync(); await vt; await vt;   ❌ undefined behavior
//   Task.WhenAll(vt1.AsTask(), vt2.AsTask())           — convert if composing.
// With Task<Config> every hit would allocate a Task object; under millions of
// calls/sec that's real GC pressure (memory.html). ValueTask exists for exactly
// this hit-dominated shape. (Concurrent first-misses may double-load; add a
// SemaphoreSlim gate if the load must be strictly once — async-patterns.html.)

🎯 Key Takeaways

  • Async is about scalability: await releases the thread during I/O; a Task is a handle/promise, not a thread. CPU-bound work is a different tool (threading).
  • The model: an async method runs synchronously until its first incomplete await, returns its Task, and resumes as a continuation — possibly on another thread, per SynchronizationContext (ConfigureAwait(false) in libraries).
  • Compose: start tasks without await, then WhenAll (latency = slowest, not sum); WhenAny/WaitAsync for racing and timeouts; bound large fan-outs.
  • Exceptions live in the task and rethrow at await; unawaited tasks fail silently; async void crashes the process — event handlers only, with their own try/catch.
  • Cancellation is cooperative: accept a CancellationToken last, flow it everywhere, check it in loops; OperationCanceledException means "stopped", not "failed".
  • Never block on async (.Result/.Wait = deadlock risk + starved threads); ValueTask for allocation-free hot paths with the await-once constraint.
  • async/await waits for I/O without blocking a thread.
  • It improves scalability and responsiveness, not the speed of one operation.
  • Blocked threads cause thread-pool starvation under load.
  • A Task represents an operation that may not have finished.
  • Task is async void; Task<T> returns a value.
  • A task is not a thread.
  • Exceptions are stored in the task and rethrown on await.
  • Await releases the thread; a continuation runs when the I/O completes.
  • In ASP.NET Core, continuations run on any pool thread.
  • Start independent tasks before awaiting them.
  • Awaiting WhenAll rethrows only the first exception.
  • Avoid async void except for event handlers.
