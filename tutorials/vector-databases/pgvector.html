pgvector & SQL-Native Vectors The Landscape

What you'll master: how to model vectors alongside the rows they describe and why transactional consistency between them matters more than it sounds, the three operator classes and the silent sequential-scan trap when they mismatch, how Postgres's planner decides between an index scan and a filtered scan and why that decision is pgvector's biggest advantage, tuning HNSW and IVFFlat inside Postgres, and the specific scale and workload signals that mean it is time to leave. Prerequisites: Tuning Recall vs Latency; familiarity with SQL helps.

Part 1 — Vectors as a Column Type

pgvector adds a vector type to Postgres. That single design decision is what makes it different from every dedicated store: a vector is a column, so everything Postgres already does — joins, transactions, constraints, permissions, backups — applies to it unchanged.

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id          bigserial PRIMARY KEY,
  document_id bigint NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  tenant_id   bigint NOT NULL,
  chunk_index int    NOT NULL,
  content     text   NOT NULL,          -- the source of truth
  token_count int    NOT NULL,
  model       text   NOT NULL,          -- which embedding model produced this
  embedding   vector(1536) NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (document_id, chunk_index)
);

CREATE INDEX ON chunks (tenant_id);
CREATE INDEX ON chunks (document_id);
ColumnWhy it is there
contentThe system of record — the index is a rebuildable derived artefact
modelDetects a partially-migrated index; see Embeddings
tenant_idFiltering and isolation, evaluated by the planner
document_id FKDeleting a document removes its chunks atomically
UNIQUE (document_id, chunk_index)Makes re-ingestion idempotent via ON CONFLICT
🔑 The foreign key is the feature. With a dedicated vector store, deleting a document means deleting the row in Postgres and then deleting its vectors over the network — two operations that can partially fail, leaving orphaned vectors that surface as results citing documents that no longer exist. In pgvector it is one DELETE inside one transaction. That class of bug simply does not occur, and eliminating it is worth more than most of the performance differences people argue about.

Ingestion is an ordinary upsert, which makes re-running the pipeline safe:

INSERT INTO chunks (document_id, tenant_id, chunk_index, content, token_count, model, embedding)
VALUES ($1, $2, $3, $4, $5, 'text-embedding-3-small', $6)
ON CONFLICT (document_id, chunk_index) DO UPDATE
  SET content = EXCLUDED.content,
      embedding = EXCLUDED.embedding,
      model = EXCLUDED.model;

Part 2 — Operators and Operator Classes

pgvector provides three distance operators, and each needs an index built with the matching operator class. Getting this pairing wrong is the single most common pgvector performance bug.

OperatorDistanceOperator classBest value
<=>Cosine distancevector_cosine_ops0 (identical)
<#>Negative inner productvector_ip_ops−1 for normalised identical
<->L2 distancevector_l2_ops0
<+>L1 (Manhattan)vector_l1_ops0
-- All operators sort ASCENDING — smaller is better, uniformly
SELECT id, content, embedding <=> $1 AS distance
FROM chunks
ORDER BY embedding <=> $1
LIMIT 10;

-- Inner product returns a NEGATIVE score; negate it for display
SELECT id, (embedding <#> $1) * -1 AS similarity
FROM chunks
ORDER BY embedding <#> $1
LIMIT 10;

Normalise at ingestion and use <#>. As Similarity Metrics established, inner product on unit vectors computes cosine exactly, and it is the cheapest operator — no division, no square root:

CREATE INDEX chunks_embedding_idx ON chunks
  USING hnsw (embedding vector_ip_ops)
  WITH (m = 16, ef_construction = 64);

The mismatch trap: querying with an operator the index was not built for does not error. Postgres simply cannot use the index and falls back to a sequential scan — correct results, hundreds of times slower:

EXPLAIN ANALYZE SELECT id FROM chunks ORDER BY embedding <-> $1 LIMIT 10;
                                    -- index is vector_ip_ops, query uses <->

 Limit  (actual time=1841.2..1841.3 rows=10)
   ->  Sort  (actual time=1841.2..1841.2 rows=10)
         Sort Method: top-N heapsort
         ->  Seq Scan on chunks  (actual rows=2400000)     ← no index used
 Execution Time: 1843.91 ms

Part 3 — HNSW and IVFFlat in Postgres

HNSWIVFFlat
Build parametersm, ef_constructionlists
Query parameterhnsw.ef_searchivfflat.probes
Build speedSlowFast
Requires data presentNo — can build on an empty tableYes — needs rows to cluster
Recall per unit of workBetterNeeds more probes
MemoryHigherLower
Handles updatesDegrades over timeBetter; centroids drift
-- HNSW: the usual choice
CREATE INDEX ON chunks USING hnsw (embedding vector_ip_ops)
  WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 100;                 -- per session or per transaction

-- IVFFlat: build AFTER loading data; lists ≈ rows/1000 up to 1M, then sqrt(rows)
CREATE INDEX ON chunks USING ivfflat (embedding vector_ip_ops) WITH (lists = 1000);
SET ivfflat.probes = 20;

Build time is the practical constraint, and it is worth planning for:

-- Parallel build: dramatically faster on multi-core machines
SET max_parallel_maintenance_workers = 7;   -- plus the leader = 8
SET maintenance_work_mem = '8GB';           -- must fit the graph, or it spills to disk
CREATE INDEX CONCURRENTLY ON chunks USING hnsw (embedding vector_ip_ops);

Rough build times, 1536-dim, m=16, 8 workers:
     100k rows  →  ~1 min
   1,000k rows  →  ~12 min
  10,000k rows  →  ~3 hours       ← plan a maintenance window

maintenance_work_mem matters more than people expect: if the graph does not fit, the build spills to disk and can take an order of magnitude longer. Size it to roughly the index size before building.

CREATE INDEX CONCURRENTLY avoids locking the table for writes, at the cost of a slower build and the risk of leaving an invalid index if it fails — always check pg_index.indisvalid afterwards.

Part 4 — Filtering: The Real Advantage

This is where pgvector separates itself. Combining a similarity search with predicates is a query-planner problem, and Postgres has spent decades on query planning.

SELECT c.id, c.content, d.title, c.embedding <#> $1 AS score
FROM chunks c
JOIN documents d ON d.id = c.document_id
WHERE c.tenant_id = $2
  AND d.status = 'published'
  AND d.updated_at > now() - interval '90 days'
ORDER BY c.embedding <#> $1
LIMIT 10;

In a dedicated store this is either impossible, or requires denormalising every filterable attribute into the vector store's metadata and keeping it in sync. Here it is one query, correctly filtered, with the planner choosing the strategy.

Filter selectivityPlanner choiceWhy it is right
Broad (>20% of rows pass)HNSW index scan, filter applied afterEnough survivors in the candidate set
Narrow (<1% pass)Filter first, then exact scanThe subset is small; brute force is faster AND exact
MiddleDepends on statistics and cost estimatesThis is exactly what a planner is for
-- Narrow filter: the planner chooses the btree and skips the vector index entirely
EXPLAIN ANALYZE
SELECT id FROM chunks WHERE tenant_id = 4821
ORDER BY embedding <#> $1 LIMIT 10;

 Limit  (actual time=3.1..3.2 rows=10)
   ->  Sort  (actual time=3.1..3.1 rows=10)
         ->  Bitmap Heap Scan on chunks  (actual rows=1204)
               Recheck Cond: (tenant_id = 4821)
               ->  Bitmap Index Scan on chunks_tenant_id_idx  (actual rows=1204)
 Execution Time: 3.28 ms                     -- exact, and fast

That plan is exactly right and requires no configuration. A dedicated store doing post-filtering on 128 ANN candidates would have returned near-zero results here, as the filtering interaction showed.

Partial indexes handle the case where one filter dominates every query:

CREATE INDEX ON chunks USING hnsw (embedding vector_ip_ops)
  WHERE tenant_id = 1 AND deleted_at IS NULL;
-- a smaller, faster index that only serves matching queries

Part 5 — Operating It

pgvector inherits Postgres's operational model, which is mostly an advantage and has two specific gotchas.

Gotcha 1: TOAST. A 1536-dimension vector is about 6 KB, which exceeds Postgres's inline tuple limit, so vectors are stored out-of-line in a TOAST table. That means an extra fetch per row unless the index scan avoids it:

-- Check how much of the table is TOAST
SELECT pg_size_pretty(pg_relation_size('chunks'))            AS heap,
       pg_size_pretty(pg_total_relation_size('chunks'))      AS total,
       pg_size_pretty(pg_indexes_size('chunks'))             AS indexes;

-- Storing vectors as PLAIN avoids TOAST compression attempts (they never compress well)
ALTER TABLE chunks ALTER COLUMN embedding SET STORAGE PLAIN;

Gotcha 2: index memory and the buffer cache. HNSW index pages must be in shared_buffers or the OS page cache, or every query pays disk reads:

-- Is the index actually resident?
SELECT pg_size_pretty(pg_relation_size('chunks_embedding_idx')) AS index_size,
       current_setting('shared_buffers') AS shared_buffers;

-- Typical settings for a vector-heavy instance
shared_buffers = 25% of RAM
effective_cache_size = 75% of RAM
maintenance_work_mem = enough to build the index in memory

Monitoring that matters:

-- Index bloat and dead tuples (HNSW degradation)
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS dead_pct
FROM pg_stat_user_tables WHERE relname = 'chunks';

-- Is the vector index being used at all?
SELECT indexrelname, idx_scan, idx_tup_read
FROM pg_stat_user_indexes WHERE relname = 'chunks';
-- idx_scan = 0 on the vector index means every query is sequential-scanning

That last query is the single most valuable pgvector check. idx_scan = 0 on the embedding index means an operator mismatch, a missing LIMIT, or a planner decision — and it is the difference between 3 ms and 1800 ms.

❌ Assuming the vector index is being used because the query returns correct results. pgvector never errors on a metric mismatch or a missing LIMIT — it silently sequential-scans. The results are exactly right (it is brute-force kNN), so tests pass, and only the latency graph knows. Teams ship this and discover it weeks later when the corpus grows.

✅ Assert on the query plan, not just the results. An EXPLAIN-based test checking for Index Scan and the absence of Seq Scan catches operator mismatches, a dropped LIMIT, and an invalid index after a failed CREATE INDEX CONCURRENTLY. Pair it with a pg_stat_user_indexes check that idx_scan is growing in production.

Part 6 — When to Leave

pgvector should be the default, and there are honest signals that it has stopped being the right answer.

SignalWhy it mattersThreshold, roughly
Index no longer fits in RAMEvery query hits disk; latency collapsesDepends on instance; watch cache hit rate
Index build exceeds the maintenance windowCannot rebuild after a model change> 10–20M rows at 1536 dims
Vector search degrades OLTP p99Shared CPU, memory and buffer cacheWhen search is a meaningful fraction of load
You need aggressive quantisationpgvector's options are more limited than FAISS-based storesWhen PQ is required to fit memory
Sustained very high write throughputIndex maintenance competes with transactionsWorkload-specific

Note what is not on that list: "we have a million vectors" and "we want to use a real vector database". A million 1536-dimension vectors is about 6 GB of vectors plus a modest graph — entirely reasonable for a Postgres instance, and the operational simplicity of one system is worth real money.

The migration is cheap if you designed for it. Because content and metadata live in Postgres and the index is derived, moving to a dedicated store is a re-index rather than a data migration — and re-indexing is a pipeline you need anyway for model changes:

-- Everything needed to rebuild elsewhere is already here
SELECT id, content, tenant_id, document_id, model FROM chunks WHERE model = $1;

The half-way option is worth knowing: keep Postgres as the system of record and replicate to a dedicated store for search only, accepting eventual consistency on the search path. That preserves the transactional guarantees where they matter and gets the specialised index where it helps — at the cost of a sync pipeline, which is exactly the complexity pgvector was avoiding.

Interview Questions

Beginner: What does pgvector add to Postgres?

A vector column type, distance operators, and ANN index types. That is deliberately small, and the smallness is the point — a vector becomes an ordinary column, so everything Postgres already does applies to it.

CREATE EXTENSION vector;
CREATE TABLE chunks (
  id bigserial PRIMARY KEY,
  document_id bigint REFERENCES documents(id) ON DELETE CASCADE,
  content text NOT NULL,
  embedding vector(1536) NOT NULL
);
CREATE INDEX ON chunks USING hnsw (embedding vector_ip_ops);

What you get for free is substantial: transactions spanning vectors and the rows they describe, foreign keys so deleting a document removes its chunks atomically, joins against any other table, row-level security, existing backups and monitoring, and one system to operate rather than two.

The foreign key example is worth dwelling on. With a separate vector store, deleting a document means a DELETE in Postgres and a delete call over the network — two operations that can partially fail, leaving orphaned vectors that surface as citations to documents that no longer exist. In pgvector that class of bug cannot occur.

It provides three main distance operators — <=> cosine, <#> negative inner product, <-> L2 — and two index types, HNSW and IVFFlat.

Beginner: What are the pgvector operators and what do they return?
OperatorReturnsIndex operator class
<=>Cosine distance, 0 = identicalvector_cosine_ops
<#>Negative inner productvector_ip_ops
<->L2 distance, 0 = identicalvector_l2_ops

All of them sort ascending — pgvector negates the inner product specifically so that "smaller is better" holds uniformly and the index can always sort one way.

That negation is the sharp edge. A perfect match under <#> scores -1, so code written as WHERE score > 0.7 returns precisely the wrong rows. Negate for display:

SELECT id, (embedding <#> $1) * -1 AS similarity
FROM chunks ORDER BY embedding <#> $1 LIMIT 10;

The operator must match the index's operator class. Querying with <-> against a vector_cosine_ops index does not error — Postgres just cannot use the index and sequential-scans instead. Correct results, hundreds of times slower.

The recommended setup is to normalise vectors at ingestion and use <#> with vector_ip_ops: on unit vectors inner product equals cosine exactly, and it is the cheapest operator to compute.

Mid: Why is pgvector better at filtered vector search than most dedicated stores?

Because filtering is a query-planning problem, and Postgres has a mature cost-based planner that chooses a strategy per query based on statistics.

The hard case for a dedicated store is a selective filter. It searches the ANN index for, say, 128 nearest candidates and then applies the filter. If the filter keeps 0.1% of the corpus, roughly zero candidates survive — the user asked for 10 results and gets none, from an index reporting excellent recall.

Postgres decides differently per query:

SelectivityPlan
Broad filterHNSW index scan, filter after
Narrow filterbtree on the filter column, then exact scan of the subset

The narrow case is both faster and exactly correct — with 1,200 matching rows, a brute-force scan is a few milliseconds and has recall 1.0. No configuration required; the planner reads the statistics and picks.

It also handles joins, which most vector stores cannot: filtering on a column of a related table means denormalising it into vector metadata and keeping it in sync, or doing the join in application code. In pgvector it is a JOIN.

The caveat is that the planner needs good statistics. A stale ANALYZE or a correlated predicate it estimates badly can produce a poor plan — so EXPLAIN ANALYZE on the real query shapes matters, as with any Postgres workload.

Mid: How do you choose and tune between HNSW and IVFFlat in pgvector?

HNSW is the default choice. Better recall per unit of work, and it can be created on an empty table so it works naturally with an incremental ingestion pipeline.

CREATE INDEX ON chunks USING hnsw (embedding vector_ip_ops)
  WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 100;                  -- the live tuning dial

IVFFlat is the alternative when build time dominates:

CREATE INDEX ON chunks USING ivfflat (embedding vector_ip_ops) WITH (lists = 1000);
SET ivfflat.probes = 20;

It builds far faster, uses less memory, and handles churn better — but it must be built after loading data, because it needs rows to cluster. Building it on an empty table produces a useless index, which is a real and easily-made mistake in a migration script.

Sizing: for IVFFlat, lists ≈ rows/1000 up to a million rows, then sqrt(rows). For HNSW, m=16 is a good default; raise it for high dimensionality or if recall plateaus below target.

Tuning is the same discipline as any ANN index: sweep hnsw.ef_search or ivfflat.probes until recall@k reaches the target, then confirm latency fits. Both are session-level settings, so they can be changed live without a rebuild — unlike m and lists.

The build itself needs attention: set maintenance_work_mem large enough to hold the index or it spills to disk, and raise max_parallel_maintenance_workers — the difference is hours at scale.

Senior: Design a RAG data model in Postgres for a multi-tenant application.

I would treat Postgres as the system of record and the vector index as a derived artefact, then let the schema enforce the invariants.

CREATE TABLE documents (
  id          bigserial PRIMARY KEY,
  tenant_id   bigint NOT NULL,
  source_uri  text   NOT NULL,
  content_hash text  NOT NULL,          -- skip re-embedding unchanged documents
  status      text   NOT NULL DEFAULT 'active',
  updated_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, source_uri)
);

CREATE TABLE chunks (
  id          bigserial PRIMARY KEY,
  document_id bigint NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  tenant_id   bigint NOT NULL,          -- denormalised for filtering
  chunk_index int    NOT NULL,
  content     text   NOT NULL,
  model       text   NOT NULL,
  embedding   vector(1536) NOT NULL,
  UNIQUE (document_id, chunk_index)
);

CREATE INDEX ON chunks USING hnsw (embedding vector_ip_ops) WITH (m = 16, ef_construction = 64);
CREATE INDEX ON chunks (tenant_id, document_id);

The design decisions worth defending:

1. ON DELETE CASCADE makes document deletion atomic. With a separate vector store this is a two-system operation that can leave orphans citing deleted documents — the exact failure that produces "the assistant quoted a document I removed".

2. tenant_id denormalised onto chunks so tenant filtering never needs a join, and so row-level security can be applied directly:

ALTER TABLE chunks ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON chunks
  USING (tenant_id = current_setting('app.tenant_id')::bigint);

That is enforced by the database rather than by every query being written correctly — a materially stronger guarantee than filtering in application code, and the reason I would prefer Postgres for anything with real tenancy requirements.

3. content_hash so re-ingestion skips unchanged documents. Re-embedding is the dominant cost in most pipelines.

4. model per chunk so a partially-completed migration is detectable, and partial indexes can serve each model during a rollout.

5. Source text retained, which makes the index rebuildable — required for model changes, and it turns a future move to a dedicated store into a re-index rather than a data migration.

Operationally I would add: a read replica for search if it competes with OLTP, an EXPLAIN assertion in CI that the vector index is used, and monitoring on idx_scan and dead-tuple percentage.

Senior: When would you move off pgvector, and how would you plan it?

I would require a measured signal rather than a scale milestone, because the operational cost of a second stateful system is permanent and the benefits are frequently assumed rather than demonstrated.

The signals that genuinely justify it:

SignalWhy it forces the move
Index no longer fits in RAMEvery query hits disk; no tuning recovers it
Rebuild exceeds the maintenance windowYou cannot change embedding models any more
Search degrades OLTP p99Shared buffer cache and CPU; a real business impact
Quantisation is required to fit memoryFAISS-based stores implement PQ far more thoroughly

What does not justify it: vector count alone. A million 1536-dimension vectors is ~6 GB plus a modest graph — comfortable for a Postgres instance, and the simplicity is worth real money.

The migration is cheap if the schema was designed for it. Because source text and metadata live in Postgres and the index is derived, moving is a re-index:

SELECT id, content, tenant_id, model FROM chunks WHERE model = $1;
-- feed into the new store's ingestion; no data migration, no dual-write of truth

And that pipeline has to exist anyway for embedding-model changes, so it is not new work.

I would run them in parallel before cutting over: dual-write to both, shadow-evaluate recall on the same eval set, compare latency percentiles under real load, and only then move traffic percentage by percentage with an env-var revert. Shadow evaluation frequently reveals that the new store is better on aggregate recall and worse on some query class — which is information you want before the cutover, not after.

The intermediate option worth considering is keeping Postgres as the system of record and replicating to a dedicated store for search only. That preserves transactional integrity where it matters and gets the specialised index where it helps — at the cost of a sync pipeline and eventual consistency on the search path, which is precisely the complexity pgvector was avoiding. Whether that trade is worth it depends on how much the specialised index actually buys, which is why the shadow evaluation comes first.

3 (medium): Watch the planner switch strategies as filter selectivity changes.
Solution 
CREATE TABLE chunks (
  id bigserial PRIMARY KEY,
  tenant_id int NOT NULL,
  embedding vector(384) NOT NULL
);
-- 500k rows: tenant 1 has 90%, tenants 2..200 share the rest
INSERT INTO chunks (tenant_id, embedding)
SELECT CASE WHEN random() < 0.9 THEN 1 ELSE 2 + floor(random()*199)::int END,
       (SELECT ARRAY(SELECT random()-0.5 FROM generate_series(1,384)))::vector
FROM generate_series(1, 500000);

CREATE INDEX ON chunks USING hnsw (embedding vector_ip_ops);
CREATE INDEX ON chunks (tenant_id);
ANALYZE chunks;

Broad filter — the planner uses the vector index:

EXPLAIN ANALYZE
SELECT id FROM chunks WHERE tenant_id = 1
ORDER BY embedding <#> (SELECT embedding FROM chunks LIMIT 1) LIMIT 10;

 Limit  (actual time=2.4..2.6 rows=10)
   ->  Index Scan using chunks_embedding_idx on chunks  (actual rows=10)
         Filter: (tenant_id = 1)
         Rows Removed by Filter: 1
 Execution Time: 2.81 ms

Only one row filtered out, because 90% of the corpus matches — post-filtering is fine here.

Narrow filter — the planner switches entirely:

EXPLAIN ANALYZE
SELECT id FROM chunks WHERE tenant_id = 147
ORDER BY embedding <#> (SELECT embedding FROM chunks LIMIT 1) LIMIT 10;

   ->  Sort  (actual time=4.1..4.1 rows=10)

               Recheck Cond: (tenant_id = 147)
               ->  Bitmap Index Scan on chunks_tenant_id_idx  (actual rows=254)
 Execution Time: 4.38 ms

The planner chose the btree and an exact scan of 254 rows. Fast, and recall is exactly 1.0 — no approximation at all.

         0        ← asked for 10, got none

Zero survivors. That is the post-filtering failure a dedicated store hits here, and the planner avoided it automatically.

4 (medium): Tune hnsw.ef_search against measured recall.
Solution 
-- ground truth: exact search with the index disabled
CREATE TABLE eval_queries AS SELECT embedding FROM vecs ORDER BY random() LIMIT 100;

CREATE OR REPLACE FUNCTION exact_topk(q vector, k int)
RETURNS bigint[] AS $$
  SELECT array_agg(id ORDER BY d) FROM (
    SELECT id, embedding <#> q AS d FROM vecs ORDER BY d LIMIT k
  ) s;
$$ LANGUAGE sql;

-- measure recall at each ef_search
DO $$
DECLARE ef int; q record; truth bigint[]; got bigint[]; hits int; total int;
BEGIN
  FOREACH ef IN ARRAY ARRAY[10, 40, 100, 200, 400] LOOP
    PERFORM set_config('hnsw.ef_search', ef::text, false);
    hits := 0; total := 0;
    FOR q IN SELECT embedding FROM eval_queries LOOP
      SET LOCAL enable_indexscan = off;
      truth := exact_topk(q.embedding, 10);
      SET LOCAL enable_indexscan = on;
      SELECT array_agg(id) INTO got FROM (
        SELECT id FROM vecs ORDER BY embedding <#> q.embedding LIMIT 10) s;
      hits := hits + (SELECT count(*) FROM unnest(got) g WHERE g = ANY(truth));
      total := total + 10;
    END LOOP;
    RAISE NOTICE 'ef_search=% recall@10=%', ef, round(hits::numeric/total, 4);
  END LOOP;
END $$;

NOTICE:  ef_search=10  recall@10=0.7420
NOTICE:  ef_search=40  recall@10=0.9310
NOTICE:  ef_search=100 recall@10=0.9840
NOTICE:  ef_search=200 recall@10=0.9950
NOTICE:  ef_search=400 recall@10=0.9990

5 (hard): Build a complete multi-tenant RAG schema with row-level security.
Solution 
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
  id           bigserial PRIMARY KEY,
  tenant_id    bigint NOT NULL,
  source_uri   text   NOT NULL,
  content_hash text   NOT NULL,
  status       text   NOT NULL DEFAULT 'active'
                 CHECK (status IN ('active','archived','deleted')),
  updated_at   timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, source_uri)
);

CREATE TABLE chunks (
  id          bigserial PRIMARY KEY,
  document_id bigint NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  tenant_id   bigint NOT NULL,
  chunk_index int    NOT NULL,
  content     text   NOT NULL,
  token_count int    NOT NULL CHECK (token_count > 0),
  model       text   NOT NULL,
  embedding   vector(384) NOT NULL,
  UNIQUE (document_id, chunk_index)
);

CREATE INDEX ON chunks USING hnsw (embedding vector_ip_ops) WITH (m=16, ef_construction=64);
CREATE INDEX ON chunks (tenant_id, document_id);
CREATE INDEX ON documents (tenant_id, status);

Row-level security — enforced by the database, not by every query:

ALTER TABLE chunks    ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_chunks ON chunks
  USING (tenant_id = current_setting('app.tenant_id', true)::bigint);
CREATE POLICY tenant_docs ON documents
  USING (tenant_id = current_setting('app.tenant_id', true)::bigint);

CREATE ROLE app_user LOGIN PASSWORD 'pw';
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_user;

Prove the isolation holds even for a deliberately unfiltered query:

SET app.tenant_id = '1';

That is a materially stronger guarantee than application-level filtering, and it is the single best argument for pgvector in a multi-tenant product — a forgotten WHERE clause cannot leak data.

The search query, with a join the vector store could not do:

Idempotent ingestion:

-- skip unchanged documents entirely
WITH upsert AS (
  INSERT INTO documents (tenant_id, source_uri, content_hash)
  VALUES ($1, $2, $3)
  ON CONFLICT (tenant_id, source_uri) DO UPDATE
    SET content_hash = EXCLUDED.content_hash, updated_at = now()
    WHERE documents.content_hash IS DISTINCT FROM EXCLUDED.content_hash
  RETURNING id
)
SELECT id FROM upsert;      -- empty result = unchanged, skip re-embedding

6 (hard): Decide with evidence whether to stay on pgvector.
Solution

The scenario: 8M chunks at 1536 dimensions, growing 15% per quarter. Search is ~40 QPS at peak on the same instance as the application's OLTP workload. Someone proposes migrating to a managed vector database.

1. Measure the actual footprint:

SELECT pg_size_pretty(pg_total_relation_size('chunks'))          AS total,
       pg_size_pretty(pg_relation_size('chunks'))                AS heap,
       pg_size_pretty(pg_relation_size('chunks_embedding_idx'))  AS hnsw_index,
       (SELECT setting FROM pg_settings WHERE name='shared_buffers') AS shared_buffers;

  total  |  heap  | hnsw_index | shared_buffers
---------+--------+------------+----------------
 71 GB   | 49 GB  | 21 GB      | 2097152        (16 GB)

21 GB of index against 16 GB of shared_buffers on a 64 GB instance — tight but the OS page cache covers it. Worth checking:

       round(100.0*heap_blks_hit/NULLIF(heap_blks_hit+heap_blks_read,0),2) AS cache_hit_pct

99.4% cache hit rate — the index is effectively resident. Not a reason to migrate.

2. Measure whether search hurts OLTP:

       round((100*total_exec_time/sum(total_exec_time) OVER ())::numeric,1) AS pct_time
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;

 queryid | calls  | mean_ms | pct_time
---------+--------+---------+----------
 vector  | 412048 |    8.42 |     31.2      ← vector search
 oltp_1  |8204188 |    0.41 |     29.8
 oltp_2  |4102944 |    0.28 |     10.1

Search is 31% of database time. Not dominant, but material — worth watching, and the argument for a read replica rather than a different database.

3. Measure the rebuild time — the constraint that actually binds:

\timing on
SET maintenance_work_mem='24GB'; SET max_parallel_maintenance_workers=7;
CREATE INDEX CONCURRENTLY chunks_emb_new ON chunks USING hnsw (embedding vector_ip_ops);
Time: 9,412,882 ms (2h 36min)

2.6 hours, and growing with the corpus. That is the number that matters: a model change requires re-embedding 8M chunks and a 2.6-hour index build.

4. Project forward:

$ python3 -c "
n = 8_000_000
for q in range(1, 9):
    n *= 1.15
    idx_gb = n*1536*4*0.08/1e9 + n*8*16/1e9   # rough HNSW graph estimate
    build_h = 2.6 * (n/8e6) * 1.1              # superlinear
    print(f'Q+{q}: {n/1e6:5.1f}M rows, index ~{idx_gb:4.1f} GB, rebuild ~{build_h:4.1f}h')
"
Q+1:   9.2M rows, index ~ 5.7 GB, rebuild ~ 3.3h
Q+4:  14.0M rows, index ~ 8.7 GB, rebuild ~ 5.0h
Q+8:  24.5M rows, index ~15.2 GB, rebuild ~ 8.7h

5. The recommendation:

FindingVerdict
Index resident, 99.4% cache hitMemory is not a problem yet
Search is 31% of DB timeMove search to a read replica — cheap, solves the contention
Rebuild 2.6h now, ~9h in two yearsThe real constraint — partition by date or tenant
Managed vector DBNot justified — no measured problem it uniquely solves

Stay on pgvector, and take two actions: route search to a read replica so it stops competing with OLTP, and partition chunks by tenant or by month so index builds become per-partition and incremental rather than one monolithic 9-hour operation.

Define the trigger for revisiting: cache hit rate below 95%, rebuild exceeding the maintenance window even when partitioned, or quantisation becoming necessary. And keep content as the system of record so the migration stays a re-index if those fire.

🎯 Key Takeaways

  • pgvector makes a vector an ordinary column, so transactions, foreign keys, joins, row-level security, backups and monitoring all apply unchanged.
  • ON DELETE CASCADE eliminates orphaned vectors — a whole class of two-system consistency bug that dedicated stores cannot avoid.
  • Three operators — <=> cosine, <#> negative inner product, <-> L2 — all sort ascending, and <#> returns −1 for a perfect match.
  • Each operator needs the matching operator class; a mismatch silently sequential-scans with correct results and 100–500× the latency.
  • Normalise at ingestion and use vector_ip_ops with <#> — cosine semantics at the cheapest operator.
  • Always include LIMIT; HNSW is only used for top-k ordering.
  • HNSW is the default; IVFFlat builds faster but must be created after loading data, since it needs rows to cluster.
  • Set maintenance_work_mem and max_parallel_maintenance_workers before building, or the build spills to disk and takes an order of magnitude longer.
  • Filtered search is pgvector's biggest advantage: the planner uses the vector index for broad filters and switches to a btree plus exact scan for narrow ones — automatically, and exactly correct.
  • Where a dedicated store post-filters 128 candidates through a 0.1% filter and returns nothing, Postgres returns 10 correct results in milliseconds.
  • Row-level security enforces tenant isolation in the database, so a forgotten WHERE clause cannot leak data.
  • Monitor idx_scan in pg_stat_user_indexes — zero means every query is sequential-scanning.
  • Assert on the query plan in CI, because a metric mismatch produces correct results and no test failure.
  • Leave pgvector for measured reasons — index no longer resident, rebuild exceeds the window, search degrades OLTP, or quantisation is required — never for vector count alone.
  • Keep source text in Postgres so the index stays a derived artefact and any future migration is a re-index, not a data migration.
