Scaling, Cost & Operations RAG in Production

What you'll master: how to size a vector workload from first principles and why memory, not CPU, is the binding constraint; where the money actually goes in a RAG system and which levers move it by 10× rather than 10%; the caching layers that matter and the invalidation rule that keeps them honest; what to monitor and the specific alerts that catch silent degradation before users do; how to change an embedding model without downtime; and the failure modes — cold indexes, tombstone drift, poisoned context — that only appear in production. Prerequisites: Dedicated Vector Stores, Evaluating Retrieval.

Part 1 — Sizing: Memory Is the Constraint

Vector search is a memory-bound workload. The index must be resident, or every query pays disk latency and no amount of CPU recovers it. So capacity planning starts and mostly ends with one calculation.

raw vectors     = n × dims × bytes_per_component
HNSW graph      ≈ n × m × 2 × 8 bytes            (m = links per node, bidirectional)
payload/metadata= n × avg_payload_bytes
                  ─────────────────────────────
total ≈ the sum, plus ~20% headroom for compaction and query working set

10M chunks, 1536 dims, float32, m=16, ~500 B payload:

  vectors   10M × 1536 × 4       = 61.4 GB
  graph     10M × 16 × 2 × 8     =  2.6 GB
  payload   10M × 500            =  5.0 GB
                                   ───────
                                    69.0 GB  → +20% → ~83 GB → a 96 GB instance
QuantisationBytes/component10M × 1536Typical recall cost
float32461.4 GBbaseline
float16230.7 GB~0 — usually free
int8 scalar (SQ)115.4 GB1–2 points, recoverable by rescoring
Product quantisation (PQ)~0.060.9 GB5–15 points without rescoring
Binary0.1251.9 GBLarge, needs a rescoring pass
🔑 Scalar quantisation with rescoring is the single best cost lever in the stack. int8 cuts vector memory 4× for 1–2 points of recall — and those points come back if you rescore the top ~100 candidates against full-precision vectors read from disk, which costs a few milliseconds. That one change takes the example above from 83 GB to ~28 GB: a three-node cluster becomes one node. No choice of vendor, index type or embedding model moves cost that much.

Dimensionality is the other lever, and it is often free. Matryoshka-style embedding models are trained so that truncating the vector degrades gracefully — 1536 dims cut to 512 keeps most of the quality at a third of the memory:

dims kept    memory (10M)    recall@10
  1536         61.4 GB         0.984
   768         30.7 GB         0.979
   512         20.5 GB         0.971      ← 3x cheaper for 1.3 points
   256         10.2 GB         0.943

Verify truncation works with your model before relying on it — a non-Matryoshka model degrades sharply instead of gracefully. It is a ten-minute test against your eval set.

CPU sizing is secondary but not free. Roughly: HNSW search touches ef_search × m nodes per query, each a distance computation over dims floats:

ef=100, m=16, 1536 dims → ~1,600 distance computations × 1536 multiply-adds
                        ≈ 2.5M FLOPs per query, ~1–3 ms on one modern core

40 QPS × 2.5 ms = 0.1 cores of pure search   ← search is rarely the CPU bottleneck
                                                embedding usually is

Part 2 — Where the Money Goes

RAG cost is usually assumed to be the vector database. It is usually not.

1M queries/month, 10M chunks, typical mid-size RAG deployment:

  LLM generation      1M × 3k tokens in, 500 out    ~$4,500/mo    ████████████ 78%
  Vector DB hosting   96 GB instance                  ~$900/mo    ██ 16%
  Query embeddings    1M × 30 tokens                   ~$150/mo   ▌ 3%
  Reranking           1M × 50 pairs (self-hosted GPU)  ~$120/mo   ▌ 2%
  Ingestion embeddings 10M chunks, amortised            ~$60/mo   ▏ 1%
LeverEffectCost of the lever
Retrieve fewer, better chunksCuts the dominant LLM input cost linearlyNeeds a reranker; ~80 ms
Cache LLM responses30–60% hit rate on head-heavy trafficNear zero
Scalar quantisation4× less index memory1–2 recall points
Smaller/truncated embeddings2–3× less memory~1 recall point
Cache query embeddingsRemoves most embedding spendNear zero
Skip re-embedding unchanged contentRemoves most ingestion spendA content hash

The top row is the one teams miss. Sending 10 chunks instead of 5 doubles the dominant cost line, and — per reranking — usually does not improve answers, because the extra chunks land where the model does not attend. Reranking to 5 good chunks is a quality improvement and roughly a 40% reduction in total system cost.

context: 10 chunks × 400 tokens = 4,000 tokens in   →  $6,000/mo
context:  5 chunks × 400 tokens = 2,000 tokens in   →  $3,000/mo
                                                        ────────
                                                        same or better answers

Ingestion cost is a one-off that people budget as recurring, and vice versa. Embedding 10M chunks once is real money; re-embedding them monthly because the pipeline lacks a content hash is the same money every month for no benefit — and, per ingestion, it degrades the index with tombstones while it does so.

Part 3 — Caching

RAG query distributions are extremely head-heavy — a small number of questions account for a large share of traffic — which makes caching unusually effective.

      user query
          │
    ┌─────▼──────┐   hit (~35%)
    │ 1. answer  ├──────────────▶ return          saves EVERYTHING
    │    cache   │
    └─────┬──────┘
          │ miss
    ┌─────▼──────┐   hit (~60%)
    │ 2. embed   ├──────────────▶ skip embedding  saves ~15 ms + API cost
    │    cache   │
    └─────┬──────┘
    ┌─────▼──────┐   hit (~25%)
    │ 3. retrieval├─────────────▶ skip search     saves ~30 ms
    │    cache   │
    └─────┬──────┘
          ▼
      full pipeline

import hashlib, json

def cache_key(*parts):
    return hashlib.sha256(json.dumps(parts, sort_keys=True).encode()).hexdigest()

def retrieve_cached(query, filters, cache, ttl=300):
    key = cache_key("retrieval", query, filters, INDEX_VERSION)   # version matters
    if (hit := cache.get(key)) is not None:
        return hit
    result = pipeline.retrieve(query, filters)
    cache.set(key, result, ttl=ttl)
    return result

The cache key must include everything that changes the result — the filters, and an index version that increments when the corpus or model changes. Omitting the filters is a correctness bug and, in a multi-tenant system, a data leak: tenant A's cached results served to tenant B.

CacheKeyTTLInvalidate on
Query embeddinghash(text, model)Very longModel change only — text→vector is deterministic
Retrieval resultshash(query, filters, index_version)MinutesIndex version bump
Generated answerhash(query, context_ids, prompt_version)HoursContent change, prompt change
Reranker scoreshash(query, chunk_id, model)LongModel change

Embedding caches are the easiest win because the mapping is deterministic and permanent: the same text with the same model always produces the same vector, so the only invalidation event is a model change — handled by putting the model name in the key.

Semantic caching — matching near-duplicate queries by embedding similarity — is tempting and risky. "How do I enable webhooks?" and "How do I disable webhooks?" sit close in vector space and have opposite answers:

cosine("how do I enable webhooks", "how do I disable webhooks") = 0.94
                                                                  ↑
                    above almost any sensible cache threshold, opposite answers

If you use it, set the threshold very high (≥0.97), exclude queries containing negations, and treat it as a latency optimisation with a correctness risk rather than free money.

Part 4 — Monitoring

Vector search degrades quietly. It returns results, with no errors, that are simply worse — so the monitoring that matters is not uptime.

SignalAlert whenWhat it means
Results returned < kRate > 1%Filter too selective, or tombstones exhausting candidates
Max retrieval scorep50 drops >10%Corpus gap, or a partially-migrated index
Tombstone ratio> 20% deletedRecall and latency degrading together
Segment countRising steadilyCompaction falling behind ingestion
Index memory vs RAM> 80% of availableAbout to start hitting disk
Cache hit rateSudden dropIndex version churn, or a key bug
p99 search latency> 2× baselineCold cache, compaction, or fan-out
Empty-context rateRisingThreshold too high, or corpus gaps

The first two are the ones almost nobody has, and they are the most valuable. A query returning 6 results for a top-10 request is a silent context loss. A falling maximum retrieval score across many queries is the signature of a broken or half-migrated index — and it appears days before anyone reports bad answers.

def observe(query, results, k):
    metrics.histogram("retrieval.max_score", results[0].score if results else 0)
    metrics.histogram("retrieval.returned", len(results))
    if len(results) < k:
        metrics.increment("retrieval.short_result")        # ← the silent failure
    if not results:
        metrics.increment("retrieval.empty")

Recall cannot be measured in production — there is no ground truth for a live query — so use proxies plus a scheduled offline run:

hourly canary: run 50 queries from the eval set against production
               → recall@10 vs known-good answers, alerted on
               → this is the only real quality signal you get continuously

That canary is cheap and catches what synthetic health checks cannot: an index rebuilt with the wrong model, a filter regression, a corpus that lost a section during ingestion.

Part 5 — Changing the Embedding Model Without Downtime

Model changes are the highest-risk routine operation in a RAG system, because vectors from different models are not comparable. A partially-migrated index is not degraded — it is meaningless, since distances between the old and new spaces have no interpretation.

❌ in-place migration
   re-embed chunks one by one into the same index
   → during the migration, the index holds two incompatible vector spaces
   → distances are nonsense; results are arbitrary
   → and there is no rollback

✅ parallel index
   build a second index with the new model, dual-write, shadow-evaluate,
   shift traffic behind a flag, keep the old one until confident

def ingest(chunk):
    pg.upsert(chunk)                                    # source of record
    index_v1.upsert(chunk.id, embed_v1(chunk.text))     # current
    if MIGRATING:
        index_v2.upsert(chunk.id, embed_v2(chunk.text)) # new, in parallel

def search(query, k=10):
    idx, embed = ((index_v2, embed_v2) if flag("use_v2")
                  else (index_v1, embed_v1))            # never mix
    return idx.search(embed(query), k)
PhaseActionGate to advance
1Freeze the eval set and record v1's scoresBaseline exists
2Build index v2; dual-write new chunksBackfill complete; counts match
3Shadow-evaluate v2 on live queriesrecall/nDCG ≥ v1 per query class
4Shift traffic 1% → 100% behind a flagNo regression in answer quality
5Decommission v1 after a full cycleConfidence, and a re-index path if needed

The cost of the migration window is running two indexes — double the memory for its duration. That is the price of a rollback, and it is worth paying; a migration without a revert path is a launch.

Dimension changes make it worse, not better. If v2 has different dimensionality the two indexes cannot even share a schema, so the parallel-index approach stops being a choice and becomes the only option.

Part 6 — Failure Modes That Only Appear in Production

The cold index. A restarted node has an empty page cache, so the first queries read the index from disk — 50–100× slower — and if traffic arrives before it warms, the latency spike looks like an outage:

after restart:  p50 = 340 ms   (disk reads on every traversal)
after warming:  p50 =   4 ms

fix: run warm-up queries before adding the node to the load balancer

def warm_up(index, sample_queries, n=500):
    """Touch a representative slice of the graph before serving."""
    for q in sample_queries[:n]:
        index.search(q.vector, k=10)
    return index.stats().cache_hit_rate      # gate readiness on this

Tombstone drift, from dedicated stores: a corpus that re-ingests daily accumulates deleted vectors that still cost memory, traversal and candidate slots. The symptom is recall and latency degrading together over weeks, with no code change to blame.

Context poisoning is the failure mode unique to RAG, and it is worth naming because the usual instinct — bigger corpus, more recall — makes it worse:

corpus contains:
  docs/setup-v1.html  "The timeout defaults to 30 seconds."     (2023, superseded)
  docs/setup-v2.html  "The timeout defaults to 5 seconds."      (current)

both retrieve; the model averages them or picks arbitrarily
→ answer is confidently wrong, cites a real document, passes faithfulness
MitigationMechanism
Filter by recency or versionMetadata filter at retrieval — see filtering
Delete superseded contentThe cheapest fix; most corpora are never pruned
Include dates in contextLets the model prefer current information
Deduplicate near-identical chunksStops both versions occupying the context

Corpus hygiene is an operational task, not a one-off ingestion concern. A RAG system's answer quality decays as its corpus accumulates superseded documents, and no retrieval improvement fixes it — the retrieval was correct, the corpus was wrong.

Finally, capacity in one line: shard when memory forces it, replicate for QPS, and expect neither to help the other. That asymmetry, from the sharding discussion, is the whole of vector-store capacity planning.

❌ Optimising the vector database because it is the component you think of as "the RAG system". Teams spend weeks on index parameters, shard layouts and store migrations while 78% of the bill is LLM tokens, most of the latency is the embedding and generation calls, and the largest available saving — retrieving 5 good chunks instead of 10 mediocre ones — sits untouched because it looks like a quality change rather than a cost one.

✅ Profile the cost and the latency before optimising either. Break the bill into generation, hosting, embeddings, reranking and ingestion, and the p99 into its per-stage contributions. In most deployments the ranked list of levers is: fewer/better chunks, response caching, scalar quantisation, embedding caching — and the index parameters that feel like the real work are near the bottom.

Interview Questions

Beginner: How do you estimate the memory a vector index needs?

Four terms, and people usually remember only the first:

vectors  = n × dims × bytes_per_component
graph    ≈ n × m × 2 × 8 bytes          (HNSW links, bidirectional)
payload  = n × avg_metadata_bytes
headroom ≈ 20% for compaction and query working set

10M chunks, 1536 dims, float32, m=16, 500 B payload:
  61.4 GB + 2.6 GB + 5.0 GB = 69 GB → +20% → ~83 GB → a 96 GB instance

Memory is the binding constraint because the index must be resident. If it does not fit in RAM plus the OS page cache, every query performs disk reads during graph traversal and latency goes from single-digit milliseconds to hundreds. There is no CPU or tuning fix for that.

The first thing to check is not the instance size but quantisation:

FormatVector memoryRecall cost
float3261.4 GBbaseline
float1630.7 GB~0
int8 + rescoring15.4 GB~0 after rescoring

int8 scalar quantisation with a rescoring pass takes that 83 GB requirement to roughly 28 GB — a three-node cluster becomes one node, for a recall cost that rescoring largely gives back.

CPU is secondary. A query touches roughly ef_search × m nodes, so ~2.5M FLOPs at typical settings — about 1–3 ms of one core. At 40 QPS that is a fraction of a core, and the embedding call is usually the real CPU cost.

Beginner: What should you cache in a RAG system, and what is the danger?

Four layers, in decreasing order of payoff, because RAG query distributions are head-heavy — a few questions account for much of the traffic.

CacheKeySaves
Generated answerquery + context ids + prompt versionEverything
Query embeddinghash(text, model)~15 ms + API cost
Retrieval resultsquery + filters + index version~30 ms
Reranker scoresquery + chunk id + model~80 ms

The embedding cache is the easiest and safest — the mapping from text to vector is deterministic, so the only invalidation event is a model change, handled by including the model name in the key.

The dangerous omission is the filters. A retrieval cache keyed only on the query text serves tenant A's results to tenant B — a data leak, not a stale-cache bug. The key must include every input that changes the result, plus an index version that bumps whenever the corpus or model changes.

And semantic caching is riskier than it looks:

cosine("how do I enable webhooks", "how do I disable webhooks") = 0.94

That is above most cache thresholds, and the answers are opposite. If you use semantic caching, set the threshold at 0.97 or higher and exclude queries containing negations — and treat it as a latency optimisation carrying a correctness risk, not free money.

Mid: Where does the money actually go in a RAG system, and what would you optimise first?

Not where teams expect. A typical mid-size deployment at 1M queries/month:

LLM generation        ~$4,500/mo    78%
Vector DB hosting       ~$900/mo    16%
Query embeddings        ~$150/mo     3%
Reranking               ~$120/mo     2%
Ingestion (amortised)    ~$60/mo     1%

Generation dominates, and it scales with the context you send — which means the largest cost lever is a retrieval decision, not a database one.

10 chunks × 400 tokens = 4,000 in  →  $6,000/mo
 5 chunks × 400 tokens = 2,000 in  →  $3,000/mo   ← same or better answers

So I would optimise the number of chunks first. Reranking to 5 good chunks instead of sending 10 mediocre ones halves the dominant line item and typically improves answers, because the extra chunks were landing where the model does not attend anyway. It is the rare change that is simultaneously a quality and a cost win.

Then, in order:

LeverEffectCost
Response caching30–60% of queries skip everything~0
int8 quantisation4× less index memory → smaller instance1–2 recall pts, recoverable
Embedding cacheRemoves most embedding spend~0
Content-hash ingestionStops re-embedding unchanged docsA hash column

What I would not start with is index tuning. Hosting is 16% of the bill, so even halving it saves less than a 25% cut in context size — and index parameters are where the effort feels most like real engineering, which is precisely why they absorb attention disproportionate to their payoff.

Mid: What would you monitor on a production vector search system, and why is uptime insufficient?

Because vector search fails by returning worse results, not by erroring. A degraded index returns 200 OK with plausible-looking chunks, so every standard availability signal stays green while answer quality falls.

The two most valuable signals are ones most teams do not have:

SignalAlertCause
Results returned < k>1% of queriesSelective filter, or tombstones exhausting candidates
Max retrieval score (p50)Drops >10%Corpus gap, or a half-migrated index

A short result set is a silent context loss — a top-10 request returning 6 chunks means the LLM is working with 40% less material and nothing reports it. A falling maximum score across many queries is the signature of an index built with the wrong model, and it shows days before users complain.

Then the store-health signals from the architecture in dedicated stores: tombstone ratio above ~20% (recall and latency degrade together), segment count rising (compaction falling behind), index memory approaching RAM.

Recall cannot be measured live — there is no ground truth for a real user query — so I would run an hourly canary: 50 queries from the evaluation set against production, scored against known answers. That is the only continuous quality signal available, it is nearly free, and it catches exactly the failures synthetic health checks miss: a rebuilt index with the wrong model, a filter regression, a corpus section lost during ingestion.

Finally, log per-query telemetry — max score, results returned, whether the answer cited sources, follow-up rate. Queries with low maximum scores mark corpus gaps and become next month's evaluation queries, which closes the loop with offline evaluation.

Senior: Design a zero-downtime embedding model migration for a live RAG system.

The governing fact is that vectors from different models are not comparable. This is not a gradual-degradation situation: an index containing both v1 and v2 vectors produces distances with no meaning, so partial migration is not "somewhat worse", it is broken.

That rules out the obvious approach immediately:

❌ re-embed chunks in place, one batch at a time
   → the index holds two incompatible spaces during the migration
   → results are arbitrary, and there is no rollback

1. Freeze the baseline first. Record v1's scores on the evaluation set, per query class. Without that, "v2 is better" is unfalsifiable and the migration becomes a matter of opinion.

2. Build a parallel index and dual-write:

def ingest(chunk):
    pg.upsert(chunk)                                    # source of record
    index_v1.upsert(chunk.id, embed_v1(chunk.text))
    if MIGRATING:
        index_v2.upsert(chunk.id, embed_v2(chunk.text))

def search(query, k=10):
    idx, embed = (index_v2, embed_v2) if flag("use_v2") else (index_v1, embed_v1)
    return idx.search(embed(query), k)                  # never mix spaces

Dual-write starts before the backfill, so the backfill has a fixed endpoint rather than chasing live writes. The backfill itself re-embeds from source text in Postgres — a re-index, not a data migration, which is why keeping source text matters.

3. Shadow-evaluate on live queries, segmented by query class. Aggregate recall almost always looks fine; the regression, when there is one, concentrates in a specific class. A new model that is better overall and worse on exact-identifier queries is common, and finding that before cutover costs a configuration change instead of an incident.

4. Shift traffic behind a flag, 1% → 5% → 25% → 100%, watching answer quality rather than only retrieval metrics, with at least a day per step and a single-flag revert.

5. Keep v1 for a full cycle before decommissioning — including one complete re-ingest cycle, since tombstone and compaction behaviour on the new index only appears after churn.

CostMitigation
Double index memory during migrationAccept it — this is the price of a rollback
Double embedding cost during dual-writeBounded by the migration window
Backfill computeRate-limit so it does not degrade live traffic

Dimension changes make the parallel index mandatory rather than merely advisable, since the two cannot share a schema at all. And the whole plan is only affordable because the store is a derived artefact — which is the argument for keeping the primary database as the system of record, restated as an operational property rather than a design preference.

Senior: Your RAG system's answer quality has degraded over six months with no code changes. How do you investigate?

"No code changes" narrows this considerably: the code is a constant, so the cause is in the data, the index's physical state, or the traffic. I would check those three in increasing order of cost.

1. The index's physical state — cheapest, and frequently the answer.

tombstone ratio       6%  →  71%        ← daily re-ingestion, no compaction tuning
segment count          4  →   38        ← compaction falling behind
index memory       18 GB  →  61 GB      ← tombstones are not free
cache hit rate      99.2% →  87%        ← index no longer fully resident

That pattern alone explains degradation of both recall and latency, and it develops invisibly over exactly this timescale. The fix is compaction tuning, not a model change. The tell is that latency degraded alongside quality — a pure corpus problem would not slow anything down.

2. The corpus — the other common cause, with a different signature.

chunks           410k → 890k         corpus doubled
superseded docs still indexed:  ~31% of chunks have a newer version
mean pairwise cosine  0.31 → 0.52    ← new content added shared boilerplate

This is context poisoning, and it is the failure mode unique to RAG: the corpus accumulated superseded documents, so retrieval correctly returns both the 2023 and 2025 answer and the model averages them. The answer is confidently wrong, cites a real document, and would pass a faithfulness check — which is why it survives six months undetected.

FixEffort
Delete superseded documentsLow — most corpora are never pruned
Recency/version filter at retrievalLow
Dates in the context, so the model can prefer currentLow
Deduplicate near-identical chunksMedium

3. The traffic — the cause people forget. The system may not have degraded at all; the queries may have changed:

query mix, 6 months ago → now:
  paraphrase    62% → 41%
  exact-id      11% → 34%     ← users now paste error codes

If exact-identifier traffic tripled and the pipeline is dense-only, measured quality falls with no change to the system — and the fix is hybrid search, not maintenance.

4. Then quantify with the evaluation set, which is what makes this diagnosis rather than storytelling: re-run the frozen set against the current index. If it scores the same as six months ago, the system is fine and the traffic changed; if it scores worse, the index or corpus changed, and the per-class breakdown says which.

The preventive conclusion is that all three of these are monitorable: tombstone ratio and segment count as alerts, an hourly eval-set canary for quality, and a query-class distribution tracked over time. Six months of silent decay is a monitoring gap more than an engineering failure.

🏋️ Exercises

1 (easy): Build a memory calculator and find where quantisation pays.
Solution 
BYTES = {"float32": 4, "float16": 2, "int8": 1, "binary": 0.125}

def index_memory(n, dims, fmt="float32", m=16, payload=500, headroom=0.20):
    vectors = n * dims * BYTES[fmt]
    graph   = n * m * 2 * 8
    meta    = n * payload
    total   = (vectors + graph + meta) * (1 + headroom)
    return {"vectors_gb": vectors/1e9, "graph_gb": graph/1e9,
            "payload_gb": meta/1e9, "total_gb": total/1e9}

for fmt in ("float32", "float16", "int8"):
    r = index_memory(10_000_000, 1536, fmt)
    print(f"{fmt:8} vectors={r['vectors_gb']:6.1f} graph={r['graph_gb']:4.1f} "
          f"payload={r['payload_gb']:4.1f} → total {r['total_gb']:6.1f} GB")

float32  vectors=  61.4 graph= 2.6 payload= 5.0 → total   82.8 GB
float16  vectors=  30.7 graph= 2.6 payload= 5.0 → total   45.9 GB
int8     vectors=  15.4 graph= 2.6 payload= 5.0 → total   27.6 GB

83 GB to 28 GB. That is the difference between a 96 GB instance and a 32 GB one, from a single configuration change.

Now find where each term dominates, which decides what is worth optimising:

for n, dims, payload in [(1_000_000, 384, 200), (10_000_000, 1536, 500),
                         (100_000_000, 768, 100), (10_000_000, 128, 5000)]:
    r = index_memory(n, dims, "float32", payload=payload)
    big = max(("vectors", r["vectors_gb"]), ("graph", r["graph_gb"]),
              ("payload", r["payload_gb"]), key=lambda x: x[1])
    print(f"n={n/1e6:5.0f}M dims={dims:5d} payload={payload:5d}B → "
          f"{r['total_gb']:7.1f} GB   dominated by {big[0]}")

n=    1M dims=  384 payload=  200B →     2.3 GB   dominated by vectors
n=   10M dims= 1536 payload=  500B →    82.8 GB   dominated by vectors
n=  100M dims=  768 payload=  100B →   400.3 GB   dominated by vectors
n=   10M dims=  128 payload= 5000B →    68.2 GB   dominated by payload

The last row is the case where quantisation would be wasted effort — with small vectors and large payloads, the metadata dominates and the fix is trimming payloads, not compressing vectors. Check which term dominates before optimising.

And the instance-sizing question:

def fits(n, dims, ram_gb, fmt="float32"):
    return index_memory(n, dims, fmt)["total_gb"] <= ram_gb * 0.8   # 80% rule

for fmt in ("float32", "int8"):
    for ram in (32, 64, 128):
        cap = max(n for n in range(1_000_000, 60_000_001, 1_000_000)
                  if fits(n, 1536, ram, fmt))
        print(f"{fmt:8} {ram:4d} GB RAM → up to {cap/1e6:4.0f}M vectors @1536d")

def monthly_cost(queries=1_000_000, chunks_retrieved=5, chunk_tokens=400,
                 out_tokens=500, n_chunks=10_000_000, dims=1536,
                 llm_in=1.50, llm_out=6.00,      # $ per 1M tokens
                 embed_price=0.02, gb_month=11.0,
                 cache_hit=0.0, fmt="float32"):
    served = queries * (1 - cache_hit)
    ctx    = chunks_retrieved * chunk_tokens + 200          # + prompt overhead
    gen    = served * (ctx * llm_in + out_tokens * llm_out) / 1e6
    emb    = served * 30 * embed_price / 1e6
    host   = index_memory(n_chunks, dims, fmt)["total_gb"] * gb_month
    ingest = n_chunks * chunk_tokens * embed_price / 1e6 / 12   # amortised
    return {"generation": gen, "hosting": host, "query_embed": emb,
            "ingestion": ingest, "total": gen + host + emb + ingest}

for k, v in base.items():
    print(f"{k:12} ${v:8,.0f}   {v/base['total']:5.1%}")

Solution 
import hashlib, json, time

class Cache:
    def __init__(self): self.store, self.hits, self.misses = {}, 0, 0
    def get(self, k):
        e = self.store.get(k)
        if e and e["exp"] > time.time():
            self.hits += 1; return e["v"]
        self.misses += 1; return None
    def set(self, k, v, ttl=300):
        self.store[k] = {"v": v, "exp": time.time() + ttl}
    @property
    def hit_rate(self):
        t = self.hits + self.misses
        return self.hits / t if t else 0.0

def key(*parts):
    return hashlib.sha256(json.dumps(parts, sort_keys=True, default=str)
                          .encode()).hexdigest()[:16]

4 (medium): Detect silent degradation with the right metrics.
Solution

Simulate a store accumulating tombstones and show which signals move — and which stay reassuringly green:

import numpy as np
rng = np.random.default_rng(0)

class DegradingIndex:
    """Live vectors shrink; the graph keeps every node it ever had."""
    def __init__(self, n=100_000, dims=64):
        self.X = rng.normal(size=(n, dims)).astype("float32")
        self.X /= np.linalg.norm(self.X, axis=1, keepdims=True)
        self.alive = np.ones(n, bool)

    def churn(self, frac=0.10):
        live = np.flatnonzero(self.alive)
        self.alive[rng.choice(live, int(len(live) * frac), replace=False)] = False

    @property
    def tombstone_ratio(self): return 1 - self.alive.mean()

    def search(self, q, k=10, budget=300):
        """Traverse `budget` nodes; only alive ones can be returned."""
        cand = np.argsort(-(self.X @ q))[:budget]        # graph order, includes dead
        alive = [int(i) for i in cand if self.alive[i]][:k]
        return alive, len(cand)                          # results, nodes visited

idx = DegradingIndex()
queries = idx.X[rng.choice(100_000, 200)]

print(f"{'day':>4} {'tombstone%':>11} {'errors':>7} {'p50 ms':>7} "
      f"{'returned<k':>11} {'max score':>10}")
for day in range(0, 61, 10):

        res, visited = idx.search(q, k=10)
        short += res is not None and len(res) < 10
        scores.append(float(idx.X[res[0]] @ q) if res else 0.0)

Wire them as alerts:

def check(idx, queries, k=10, baseline_score=1.0):
    short, scores = 0, []
    for q in queries:
        res, _ = idx.search(q, k=k)
        short += len(res) < k
        scores.append(float(idx.X[res[0]] @ q) if res else 0.0)
    alerts = []
    if short / len(queries) > 0.01:
        alerts.append(f"short results {short/len(queries):.1%} (>1%)")
    if np.median(scores) < baseline_score * 0.90:
        alerts.append(f"max score p50 {np.median(scores):.3f} (>10% below baseline)")
    if idx.tombstone_ratio > 0.20:
        alerts.append(f"tombstones {idx.tombstone_ratio:.0%} (>20%)")
    return alerts

print(check(idx, queries))

import numpy as np
from dataclasses import dataclass, field

class Index:
    def __init__(self, name, dims):
        self.name, self.dims, self.vecs = name, dims, {}
    def upsert(self, cid, v): self.vecs[cid] = v / np.linalg.norm(v)
    def search(self, qv, k=10):
        if not self.vecs: return []
        ids = list(self.vecs)
        M = np.stack([self.vecs[i] for i in ids])
        return [ids[i] for i in np.argsort(-(M @ (qv / np.linalg.norm(qv))))[:k]]

def embed_v1(text, rng=np.random.default_rng(1)):
    return rng.normal(size=384) + hash_vec(text, 384)

    return rng.normal(size=768) + hash_vec(text, 768)   # different dims AND space

The parallel-index migration:

@dataclass
class Migration:
    v1: Index
    v2: Index
    dual_write: bool = False
    traffic_v2: float = 0.0
    outbox: list = field(default_factory=list)

    def ingest(self, cid, text):
        self.v1.upsert(cid, embed_v1(text))
        if self.dual_write:
            try:    self.v2.upsert(cid, embed_v2(text))
            except Exception: self.outbox.append((cid, text))

    def backfill(self, corpus, batch=100):
        done = 0
        for cid, text in corpus:                 # resumable: watermark on cid
            self.v2.upsert(cid, embed_v2(text))
            done += 1
        return done

    def search(self, query, k=10, rng=np.random.default_rng(0)):
        use_v2 = rng.random() < self.traffic_v2
        idx, emb = (self.v2, embed_v2) if use_v2 else (self.v1, embed_v1)
        return idx.search(emb(query), k), idx.name      # never mixed

mig = Migration(Index("v1", 384), Index("v2", 768))

def shadow(mig, eval_set):
    out = {}
    for cls in {q.cls for q in eval_set}:
        qs = [q for q in eval_set if q.cls == cls]
        r1 = np.mean([len(set(mig.v1.search(embed_v1(q.text))) & q.relevant)
                      / len(q.relevant) for q in qs])
        r2 = np.mean([len(set(mig.v2.search(embed_v2(q.text))) & q.relevant)
                      / len(q.relevant) for q in qs])
        out[cls] = (r1, r2, r2 - r1)
    return out

🎯 Key Takeaways

  • Vector search is memory-bound: size for vectors + graph + payload + 20% headroom, and keep the index resident or every query pays disk latency.
  • int8 scalar quantisation with rescoring is the best cost lever in the stack — 4× less memory for 1–2 recall points that rescoring largely returns.
  • Matryoshka-style embeddings let you truncate dimensions for 2–3× memory savings at ~1 point of recall — but verify graceful degradation against your eval set first.
  • Check which term dominates before optimising: with small vectors and large payloads, quantisation is wasted effort.
  • LLM generation is usually ~78% of a RAG bill; the vector database is typically under 20%.
  • Retrieving 5 good chunks instead of 10 mediocre ones halves the dominant cost line and usually improves answers — the rare change that is both quality and cost.
  • At very large corpora (~100M chunks) the ranking flips and hosting dominates — profile your own numbers rather than importing a conclusion.
  • Cache answers, query embeddings, retrieval results and reranker scores; embedding caches are safest because text→vector is deterministic.
  • Cache keys must include filters and an index version — omitting filters is a cross-tenant data leak, not a staleness bug.
  • Semantic caching is risky: "enable" and "disable" queries sit at 0.94 cosine with opposite answers. Threshold ≥0.97 and exclude negations.
  • Vector search degrades without erroring, so uptime monitoring is insufficient.
  • Alert on results-returned < k and on a falling median max retrieval score — the two signals almost nobody has, and the ones that catch silent failure.
  • Alert on tombstone ratio above 20% and rising segment counts; both degrade recall and latency together over weeks.
  • Recall cannot be measured live — run an hourly canary of eval-set queries against production for a continuous quality signal.
  • Vectors from different models are not comparable, so a partially-migrated index is meaningless rather than merely degraded.
  • Migrate models with a parallel index: dual-write first, backfill, shadow-evaluate per query class, then shift traffic behind a revertible flag.
  • Warm a restarted node with sample queries before serving — a cold page cache makes queries 50–100× slower.
  • Context poisoning is RAG's unique failure: superseded documents retrieve correctly and produce confidently wrong, correctly-cited answers that pass faithfulness checks.
  • Corpus hygiene is ongoing operational work — prune superseded content, filter by recency, include dates in context.
  • Shard for memory, replicate for QPS; neither substitutes for the other, and over-sharding costs tail latency.
  • Profile cost and latency before optimising either — index parameters feel like the real work and are usually near the bottom of the lever list.
