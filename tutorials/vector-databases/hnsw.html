HNSW Deep Dive Indexing & Search

What you'll master: why a "small world" graph lets greedy search find nearest neighbours in logarithmic time, what the hierarchy of layers actually buys, precisely what M, ef_construction and ef_search each control and which are fixed at build time, the neighbour-selection heuristic that makes HNSW work where a naive nearest-M graph fails, why deletes degrade the graph and what to do about it, and how to compute HNSW's memory footprint before you commit to it. Prerequisites: Exact kNN vs Approximate Search.

Part 1 — Greedy Search on a Proximity Graph

The idea underneath HNSW is simple: build a graph where each vector is a node connected to some of its near neighbours, then find the nearest neighbour by walking downhill.

  greedy_search(graph, query, entry):
      current = entry
      loop:
          best = the neighbour of current closest to query
          if distance(best, query) >= distance(current, query):
              return current              # no neighbour is closer — local minimum
          current = best

Each step examines only a node's neighbours, so the cost is (steps × degree) distance computations rather than n. The question is whether the walk actually reaches the global nearest neighbour, and that depends entirely on the graph's structure.

$ python3 - <<'EOF'
import numpy as np
rng = np.random.default_rng(0)
n, d = 5000, 2
V = rng.random((n, d))

# naive graph: connect each node to its M nearest neighbours
M = 8
D = np.linalg.norm(V[:, None] - V[None, :], axis=2)
nbrs = np.argsort(D, axis=1)[:, 1:M+1]

def greedy(q, entry, nbrs, V):
    cur, hops = entry, 0
    while True:
        cand = nbrs[cur]
        dists = np.linalg.norm(V[cand] - q, axis=1)
        best = cand[dists.argmin()]
        if dists.min() >= np.linalg.norm(V[cur] - q): return cur, hops
        cur, hops = best, hops + 1

hits = hops_total = 0
for _ in range(200):
    q = rng.random(d)
    true = int(np.argmin(np.linalg.norm(V - q, axis=1)))
    found, h = greedy(q, rng.integers(n), nbrs, V)
    hits += (found == true); hops_total += h
print(f"naive kNN graph: recall@1 = {hits/200:.2f}, mean hops = {hops_total/200:.1f}")
EOF
naive kNN graph: recall@1 = 0.58, mean hops = 41.3

58% recall and 41 hops — the walk gets stuck in local minima and takes a long path. A pure nearest-neighbour graph is too "local": from a distant starting point you must crawl step by step through the whole space.

🔑 The fix is long-range links — the "small world" property. Add a few edges that skip across the space, and the number of hops needed to travel anywhere collapses from O(n^(1/d)) to O(log n). This is the same effect as the six-degrees-of-separation result in social networks: mostly local connections plus a handful of distant ones produce a graph with a tiny diameter. HNSW gets those long links from its layer hierarchy, and its neighbour-selection heuristic ensures they point in diverse directions rather than clustering.

Part 2 — The Hierarchy

HNSW stacks several graphs. Layer 0 contains every vector; each higher layer contains an exponentially smaller random sample. Search starts at the top and descends.

  Layer 2   ●─────────────────────●              few nodes, very long edges
             \                   /
  Layer 1     ●────────●────────●─────────●      more nodes, medium edges
               \      / \      /  \      /
  Layer 0   ●─●─●─●─●─●─●─●─●─●─●─●─●─●─●─●      ALL nodes, short edges

  Search: enter at the top, greedily descend to a local minimum in each layer,
          use that node as the entry point for the layer below.
          At layer 0, keep the best ef candidates rather than just one.

A node's maximum layer is drawn from an exponentially decaying distribution, so the structure builds itself without any global coordination:

level = floor(-ln(uniform(0,1)) * mL)      where  mL = 1 / ln(M)

$ python3 -c "
import numpy as np
rng = np.random.default_rng(0); M = 16; mL = 1/np.log(M)
levels = np.floor(-np.log(rng.random(100000)) * mL).astype(int)
for L in range(levels.max()+1):
    c = (levels == L).sum()
    print(f'layer {L}: {c:>6} nodes ({c/1000:.2f}%)')
"
layer 0: 93762 nodes (93.76%)
layer 1:  5847 nodes (5.85%)

The top layers act as an express network: a handful of nodes spanning the whole space, letting the search jump most of the way in a few hops before refining. The hierarchy is what turns the hop count logarithmic.

Part 4 — The Neighbour-Selection Heuristic

When a node needs M edges, the obvious choice is its M nearest neighbours. HNSW deliberately does not do that, and the reason is the difference between working and not working.

  Naive: keep the M nearest candidates.
      → in a dense cluster, all M edges point INTO the cluster
      → no edge leads out; the search gets trapped

  Heuristic: keep candidate c only if c is closer to the new node
             than to any already-selected neighbour.
      → forces DIVERSITY of direction
      → guarantees at least some edges point away from the cluster

$ python3 - <<'EOF'
import numpy as np
def select_naive(cands, dists, M):
    return [c for _, c in sorted(zip(dists, cands))[:M]]

def select_heuristic(new, cands, dists, V, M):
    kept = []
    for _, c in sorted(zip(dists, cands)):
        if len(kept) >= M: break
        d_to_new = np.linalg.norm(V[c] - new)
        # keep only if closer to the new node than to any kept neighbour
        if all(d_to_new < np.linalg.norm(V[c] - V[kpt]) for kpt in kept):
            kept.append(c)
    return kept

rng = np.random.default_rng(0)
cluster = rng.standard_normal((40, 2)) * 0.1 + np.array([0, 0])
far     = rng.standard_normal((10, 2)) * 0.1 + np.array([3, 0])
V = np.vstack([cluster, far])
new = np.array([0.15, 0.0])
cands = list(range(len(V)))
dists = np.linalg.norm(V - new, axis=1)

nv = select_naive(cands, dists, 6)
hv = select_heuristic(new, cands, dists, V, 6)
print(f"naive     : {sum(1 for i in nv if i >= 40)}/6 edges reach the far cluster")
print(f"heuristic : {sum(1 for i in hv if i >= 40)}/6 edges reach the far cluster")
EOF
naive     : 0/6 edges reach the far cluster
heuristic : 1/6 edges reach the far cluster

The naive selection produces a node with no route out of its own cluster. The heuristic keeps one long edge, and that single edge is what lets a search starting elsewhere find this region at all.

Two related mechanisms complete the picture. Bidirectional edges mean adding a link from A to B also links B to A, and when B exceeds its budget it re-runs the heuristic to prune — so the graph self-maintains. And layer 0 gets 2M edges rather than M, because it must support the fine-grained final search where all the precision is needed.

Part 5 — Deletes, Updates, and Degradation

HNSW's weakest property is mutation. The graph is built assuming nodes stay put.

OperationWhat actually happensConsequence
InsertNode added, edges built via the heuristicFine — this is the designed path
DeleteUsually a tombstone; the node stays in the graphMemory not reclaimed; search wastes hops on dead nodes
UpdateDelete + insertBoth costs; the old node's edges remain as clutter
Many deletesGraph connectivity fragmentsRecall degrades silently
$ python3 - <<'EOF'
import numpy as np, hnswlib
rng = np.random.default_rng(0)
n, d, k = 100_000, 128, 10
V = rng.standard_normal((n, d)).astype('float32'); V /= np.linalg.norm(V,axis=1,keepdims=True)
idx = hnswlib.Index(space='ip', dim=d)
idx.init_index(max_elements=n, M=16, ef_construction=200)
idx.add_items(V, np.arange(n)); idx.set_ef(64)

alive = np.ones(n, bool)
Q = V[rng.choice(n, 200, replace=False)].copy()

for frac in [0.0, 0.2, 0.4, 0.6]:
    if frac > 0:
        victims = rng.choice(np.where(alive)[0], int(n*0.2), replace=False)
        for v in victims: idx.mark_deleted(int(v))
        alive[victims] = False
    lab, _ = idx.knn_query(Q, k=k)
    live_idx = np.where(alive)[0]
    r = []
    for q, l in zip(Q, lab):
        truth = set(live_idx[np.argsort(-(V[live_idx] @ q))[:k]])
        r.append(len(set(l) & truth)/k)
    print(f"deleted {frac:4.0%}  alive={alive.sum():>7,}  recall@10={np.mean(r):.3f}")
EOF
deleted   0%  alive=100,000  recall@10=0.981
deleted  20%  alive= 80,000  recall@10=0.964
deleted  40%  alive= 60,000  recall@10=0.921
deleted  60%  alive= 40,000  recall@10=0.847

Recall fell from 0.981 to 0.847 with no code change and no alert. The index still returns results, latency is unchanged, and nothing reports the degradation — which is exactly why measuring recall in production matters.

❌ Treating an HNSW index as a mutable store that will look after itself. A high-churn corpus — documents re-indexed on every edit, daily re-crawls — accumulates tombstones indefinitely. Memory grows, recall falls, and both are invisible from the query path. Teams discover it months later as "search has got worse" with no deploy to blame.

✅ Plan the rebuild before you launch. Track the tombstone ratio as a metric and rebuild on a threshold (commonly 20–30% deleted). Rebuild into a new index and swap atomically so there is no search outage. If churn is very high, IVF is a better fit — it tolerates deletes far more gracefully because there is no graph connectivity to fragment.

Part 6 — Memory, Build Time, and Variants

HNSW's memory is the vectors plus the graph, and the graph is not small:

  bytes ≈ n × d × 4                    vectors (float32)
        + n × 2M × 4                   layer-0 edges (2M neighbours, 4-byte ids)
        + n × M × 4 × (1/(M−1))        higher layers, geometric sum ≈ small
        + overhead

  rule of thumb:  graph overhead ≈ 8M bytes per vector

Interview Questions

Beginner: How does HNSW find nearest neighbours without scanning everything?

It builds a graph where each vector is a node connected to some of its near neighbours, then walks the graph greedily toward the query:

start at some node
repeat: move to whichever neighbour is closest to the query
stop when no neighbour is closer than the current node

Each step examines only one node's neighbours, so the cost is (hops × degree) distance computations rather than n.

A pure nearest-neighbour graph is not enough — the walk gets stuck in local minima and needs many hops to cross the space. HNSW adds two things.

The hierarchy: several stacked graphs, where layer 0 has every node and each higher layer has an exponentially smaller random sample. Search enters at the sparse top layer, where a few hops cover enormous distance, then descends — each layer refining the result. That is what makes hop count logarithmic in n.

The neighbour-selection heuristic: when choosing a node's edges, HNSW deliberately does not take the M nearest. It keeps candidates that are diverse in direction, guaranteeing some edges lead out of a dense cluster rather than all pointing inward.

The result is a query cost that barely grows with corpus size: in a typical benchmark, 100× the data costs about 2× the latency.

Beginner: What do M, ef_construction and ef_search control?
ParameterControlsChangeable after build?
MEdges per node per layer (2M at layer 0)No
ef_constructionCandidate list size while building the graphNo
ef_searchCandidate list size while queryingYes — live

M sets the recall ceiling. A sparse graph (M=8) tops out around 0.978 recall no matter how much you raise ef_search; M=32 can reach 0.998. It costs memory and build time.

ef_construction controls graph quality — how thoroughly the builder searches for good neighbours. Returns diminish sharply past about 200, while build time keeps rising.

ef_search is the live dial trading latency for recall. It must be at least k, and is usually 5–10× k.

The asymmetry is the important operational fact: only ef_search can be tuned after the index exists. If recall plateaus below your target, no amount of query tuning helps — you need a rebuild with a larger M, which at scale is hours. That makes M a decision to get right up front, ideally by benchmarking at realistic scale.

Mid: Why does HNSW not simply connect each node to its M nearest neighbours?

Because that produces a graph greedy search cannot traverse. In a dense cluster, all M nearest neighbours are inside the cluster, so the node has no edge leading out — and a search arriving from elsewhere can never reach the region, while a search inside it can never leave.

HNSW uses a diversity heuristic instead: consider candidates in order of distance, and keep a candidate only if it is closer to the new node than to any already-selected neighbour.

naive     : 0/6 edges reach the far cluster
heuristic : 1/6 edges reach the far cluster

That single long edge is the difference between a connected graph and a set of isolated islands. The heuristic sacrifices some short-range precision to guarantee directional diversity, and greedy search depends entirely on that.

It is the same insight as the small-world property in social networks: mostly local connections plus a few distant ones give a graph with a very small diameter. Purely local connections give a graph you have to crawl.

Two supporting mechanisms: edges are bidirectional, and when a node exceeds its budget it re-runs the heuristic to prune — so the graph maintains its structure as it grows. And layer 0 gets 2M edges rather than M, because the final fine-grained search happens there and needs the extra connectivity.

Mid: What happens to an HNSW index as documents are deleted?

Most implementations do not remove the node — they mark it deleted with a tombstone. The node stays in the graph, its edges stay in place, and it is filtered out of results.

Three consequences follow:

1. Memory is not reclaimed. A corpus that re-indexes documents on edit grows monotonically even at constant document count.

2. Search wastes work. Traversal visits dead nodes, so effective ef is lower than configured — you pay for candidates that cannot be returned.

3. Recall degrades, silently. The graph's connectivity was built assuming those nodes participate; removing them from results fragments the paths:

deleted   0%  recall@10 = 0.981
deleted  40%  recall@10 = 0.921
deleted  60%  recall@10 = 0.847

Nothing errors, latency is unchanged, and no metric moves. It surfaces as "search has got worse" months later with no deploy to correlate against.

The mitigations, in order: track the tombstone ratio as a first-class metric; rebuild into a fresh index and swap atomically when it exceeds ~20–30%; shard so each rebuild is cheap and can be done incrementally; and instrument recall against brute force on a sample so degradation is visible before users report it.

If churn is genuinely high, HNSW may be the wrong index. IVF tolerates deletes far better because there is no graph connectivity to fragment — a deleted vector simply leaves its cluster.

Senior: Size and tune an HNSW index for 50M vectors at 1536 dimensions.

At this scale memory and build time dominate the design, so I would start there rather than with recall tuning.

1. Do the memory arithmetic first:

vectors : 50M × 1536 × 4 B          = 307 GB
graph   : 50M × 8 × M               =  12.8 GB at M=32
total                               ≈ 320 GB + runtime overhead

That does not fit a commodity instance. The vectors dominate — 96% of the footprint — so lowering M saves almost nothing. The real levers are quantisation and sharding.

2. Choose the architecture accordingly:

OptionMemoryTrade-off
Single HNSW, float32320 GBNeeds a very large instance; ~6h rebuild
HNSW + scalar quantisation (int8)~90 GBSmall recall loss, recovered by reranking
Sharded ×10, quantised~9 GB eachCommodity instances; rebuilds are per-shard
DiskANN~20 GB RAM + SSDHigher latency; best when RAM is the hard constraint

I would take sharded + quantised: ten shards of 5M vectors each, queried in parallel and merged, with a full-precision rerank of the merged top candidates.

3. Parameters, with the immutability in mind. M=32 — 1536 dimensions need more connectivity than 384, and getting this wrong means a multi-hour rebuild. ef_construction=200 as a starting point; I would measure 200 vs 400 on one shard before committing, since the difference is hours across ten shards. ef_search tuned live to hit the recall target.

4. Build strategy. Shards build in parallel across machines, which turns a ~6 hour serial rebuild into well under an hour. Build into a new index and swap atomically — never rebuild in place, because that is a search outage.

5. Operational commitments I would establish before launch: tombstone ratio per shard with a rebuild trigger at 25%; nightly recall sampling against brute force on a subset; p95 latency alerting; and a documented rebuild runbook that has actually been executed once in staging. An index whose rebuild has never been performed is a liability discovered at the worst moment.

6. And I would verify the premise. 50M × 1536 is a large commitment — is the full corpus really needed in one index, or can it be partitioned by tenant, recency, or language so most queries touch a much smaller index? Partitioning by a natural key is usually cheaper than scaling one monolithic index, and it makes filtering fast rather than problematic.

Senior: Recall is 0.94 and you need 0.99. Walk through the options.

The first question is whether the ceiling is set by the index or by something else, because they have completely different fixes.

1. Test whether ef_search alone can get there. This is free and immediately informative:

ef=64  → 0.940
ef=128 → 0.968
ef=256 → 0.981
ef=512 → 0.984      ← plateau

A plateau below target means M is the constraint, and only a rebuild fixes it. If it does reach 0.99, the question becomes whether the latency at that ef is acceptable.

2. Check the recall distribution rather than the mean. A 0.94 average is often 85% of queries at 1.0 and a tail near 0.5. If so, raising ef globally is the wrong instrument — it slows down the queries that were already perfect. Better: detect low-confidence results (a small gap between the top scores) and re-query just those with a higher ef.

3. Rebuild with a larger M if the ceiling is real. M=16 → M=32 typically lifts the ceiling from ~0.99 to ~0.998, at roughly 2× build time and a modest memory increase. Worth doing if 0.99 is a genuine requirement.

4. Check for degradation before assuming the parameters were always wrong. If this index served 0.99 six months ago, the tombstone ratio is the likely culprit and a rebuild restores it without changing anything. This is worth checking early — it is the cheapest possible fix.

5. Question whether 0.99 is the right target. Recall measures agreement with exact search, not answer quality. If the downstream system reranks the top 50 candidates, missing the true #47 costs nothing — recall@50 at 0.94 may already be sufficient while recall@10 is what should be measured. I would check whether the target was chosen or inherited.

6. Consider exact search for the subset that needs it. If only certain query classes require near-perfect recall — compliance searches, deduplication — routing those to a brute-force path is simpler and exactly correct, and leaves the index tuned for the common case.

The order matters: check degradation, check the distribution, then tune, then rebuild. Rebuilding first is hours of work that may fix nothing.

5 (hard): Implement HNSW's neighbour-selection heuristic and prove it matters.
Solution 
$ python3 - <<'EOF'
import numpy as np
rng = np.random.default_rng(0)

def select_naive(new_i, cands, V, M):
    d = np.linalg.norm(V[cands] - V[new_i], axis=1)
    return [cands[i] for i in np.argsort(d)[:M]]

def select_heuristic(new_i, cands, V, M):
    d = np.linalg.norm(V[cands] - V[new_i], axis=1)
    kept = []
    for i in np.argsort(d):
        c = cands[i]
        if len(kept) >= M: break
        dist_to_new = d[i]
        if all(dist_to_new < np.linalg.norm(V[c] - V[kp]) for kp in kept):
            kept.append(c)
    return kept

def build_graph(V, M, selector):
    n = len(V)
    g = [[] for _ in range(n)]
    for i in range(n):
        cands = [j for j in range(n) if j != i]
        d = np.linalg.norm(V[cands] - V[i], axis=1)
        pool = [cands[j] for j in np.argsort(d)[:M*4]]     # candidate pool
        nbrs = selector(i, pool, V, M)
        for j in nbrs:
            if j not in g[i]: g[i].append(j)
            if i not in g[j]: g[j].append(i)               # bidirectional
    return g

def greedy(g, V, q, entry):
    cur = entry; visited = 0
    while True:
        if not g[cur]: return cur, visited
        dd = np.linalg.norm(V[g[cur]] - q, axis=1); visited += len(g[cur])
        best = g[cur][int(dd.argmin())]
        if dd.min() >= np.linalg.norm(V[cur] - q): return cur, visited
        cur = best

# three well-separated clusters — the hard case for a naive graph
V = np.vstack([rng.standard_normal((120,2))*0.3 + np.array(c)
               for c in [(0,0), (6,0), (3,5)]])
for name, sel in [("naive", select_naive), ("heuristic", select_heuristic)]:
    g = build_graph(V, 6, sel)
    hits = vis = 0
    for _ in range(300):
        q = rng.random(2)*np.array([7,6]) - np.array([0.5,0.5])
        true = int(np.argmin(np.linalg.norm(V-q, axis=1)))
        found, v = greedy(g, V, q, rng.integers(len(V)))
        hits += (found == true); vis += v
    print(f"{name:10} recall@1={hits/300:.3f}  avg distance computations={vis/300:.0f}")

🎯 Key Takeaways

  • HNSW walks a proximity graph greedily toward the query, examining only a node's neighbours — so cost is hops × degree, not n.
  • A pure nearest-neighbour graph fails: searches get trapped in local minima with no edges leading out of dense clusters.
  • The layer hierarchy provides long-range links — an express network of exponentially fewer nodes — which makes hop count logarithmic in n.
  • 100× the corpus costs roughly 2× the query latency; HNSW's advantage grows with scale.
  • M sets the recall ceiling and is fixed at build time — if recall plateaus below target, only a rebuild helps.
  • ef_construction controls graph quality with sharp diminishing returns past ~200, while build time keeps climbing.
  • ef_search is the only live dial: it must be ≥ k, and 5–10× k is typical.
  • Tune to a recall target and read off the ef, rather than tuning to latency and accepting whatever recall results.
  • The neighbour-selection heuristic keeps directionally diverse edges rather than the M nearest — worth ~28 points of recall because it guarantees routes between clusters.
  • Deletes are tombstones: memory is not reclaimed, searches waste hops, and recall degrades silently from 0.98 to 0.85 at high churn.
  • Track tombstone ratio and sampled recall as first-class metrics; rebuild into a new index and swap atomically at ~20–30%.
  • Vectors dominate memory (typically 92–96%), so lowering M saves little — quantisation is the real lever.
  • Build time is O(n log n · M · ef_construction) and is frequently the operational blocker; measure at realistic scale before committing.
  • Sharding makes rebuilds incremental and cheap, and it is usually the right answer for a high-churn corpus.
