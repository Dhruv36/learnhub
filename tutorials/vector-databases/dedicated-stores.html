Dedicated Vector Stores The Landscape

What you'll master: the architecture every dedicated store shares underneath its marketing — segments, an immutable index plus a mutable buffer, and a compaction loop — and why that shape explains almost every behaviour that surprises people; how deletes, updates and freshness actually work and why a just-written vector may not be searchable yet; the sharding and replication models and what a shard count commits you to; how the major stores (Qdrant, Milvus, Weaviate, Pinecone, Vespa, Elasticsearch/OpenSearch, and library-level FAISS) genuinely differ once you strip the benchmarks away; and how to run an evaluation that produces a defensible decision rather than a preference. Prerequisites: HNSW Deep Dive, IVF, PQ & Quantisation and pgvector.

Part 1 — What "Dedicated" Actually Buys

The previous lesson argued for pgvector as the default. This one is about the case where that stops being true — and the honest answer is that a dedicated store buys you four things, all of which are consequences of one decision: the vector index is the primary data structure rather than a secondary index on a row store.

What you getWhy the architecture allows itWhat it costs
Memory-resident indexes at large scaleNothing else competes for the buffer cacheA second stateful system to operate
Aggressive quantisation (PQ, SQ, binary)The store owns the storage format end to endRecall becomes a tuning problem, not a given
Horizontal sharding of the index itselfSearch is embarrassingly parallel across shardsFan-out latency = the slowest shard
Purpose-built ingestion and compactionWrites go to a buffer, not into a live graphEventual consistency on the search path
🔑 The thing you actually give up is transactional consistency between a vector and the row it describes. Every operational problem specific to dedicated stores traces back to this: orphaned vectors after a failed delete, results citing documents that no longer exist, metadata that has drifted from the source of record. It is a real cost, it is permanent, and it is worth paying only when there is a measured problem it solves. Nothing in this lesson changes the conclusion of the previous one — it tells you what to do once that conclusion no longer holds.

Notice what is not on the list: better recall. Recall comes from the algorithm — HNSW is HNSW whether it runs inside Postgres or inside Qdrant. A dedicated store lets you push further along the recall/latency/memory curve at scale; it does not move the curve.

Part 2 — The Architecture Every Store Shares

Vendors describe their systems very differently. Underneath, essentially all of them are the same shape, borrowed from Lucene: an append-only set of immutable segments, plus a small mutable buffer, plus a background process that merges them.

              write path                                read path
              ----------                                ---------
  upsert ──▶ [ WAL ]                              query ──┬──▶ segment 1 (immutable, HNSW)
                │                                         ├──▶ segment 2 (immutable, HNSW)
                ▼                                         ├──▶ segment 3 (immutable, HNSW)
          [ mutable buffer ]  ──── flush ───▶ new         └──▶ mutable buffer (brute force)
           (brute-force or       (on size /   segment              │
            small graph)          interval)                       ▼
                                                          merge top-k from each
                                       ▲                          │
                                       │                          ▼
                              [ compaction / merge ]          final top-k
                              rebuilds N segments into
                              one, dropping tombstones

Three consequences follow immediately, and between them they explain most "why is my vector store doing that" questions:

ConsequenceWhyWhat you observe
Writes are cheap; indexing is deferredThe buffer is appended to, the graph is not touchedHigh ingest throughput, but a freshness lag
Search cost grows with segment countEvery segment is searched, then results mergedLatency creeps up during heavy ingest, recovers after compaction
Deletes are tombstones, not deletionsYou cannot cheaply remove a node from a built HNSW graphMemory does not drop until compaction runs

Searching N segments is not free, and the cost is worse than linear in a subtle way. To return a true top-10 across 8 segments you must ask each segment for its top-10 and merge — that is 8 ANN searches, and each one has its own recall. Independent recall of 0.95 per segment does not give you 0.95 overall, because a global top-10 result can be missed by the one segment that holds it:

one segment,  ef=100:   recall@10 = 0.98    latency = 2.1 ms
8 segments,   ef=100:   recall@10 = 0.94    latency = 6.8 ms   ← each segment searched
8 segments,   ef=200:   recall@10 = 0.98    latency = 9.4 ms   ← recover recall by raising ef
after compaction to 2 segments, ef=100:     recall@10 = 0.975  latency = 2.9 ms

The design consequence: compaction is not housekeeping, it is a latency and recall control. A store that has fallen behind on compaction is a store that is quietly slower and less accurate, and the metric to alert on is segment count, not just memory.

Part 3 — Freshness, Deletes and the Consistency Model

This is the part that most teams discover in production rather than in the docs.

A successful write does not mean a searchable vector. The write is durable once it is in the WAL, but it becomes searchable only when it is in the mutable buffer's structure or in a flushed segment — and stores differ in whether that is microseconds or seconds:

# The bug this produces, in every RAG pipeline that has it
client.upsert(collection="chunks", points=[{"id": 42, "vector": v, "payload": meta}])
results = client.search(collection="chunks", query_vector=v, limit=10)
assert 42 in [r.id for r in results]     # ← flaky: passes locally, fails under load

# The fix is to make the requirement explicit, not to add a sleep
client.upsert(collection="chunks", points=[...], wait=True)   # Qdrant: block until applied
# Elasticsearch equivalent: refresh="wait_for"
# Milvus equivalent:        consistency_level="Strong" on the search

Never fix this with time.sleep(). It passes on a laptop and fails on a loaded cluster, and it converts a correctness requirement into a race that gets slower as you scale.

Consistency levelMeaningWhen to use it
Strong / wait=TrueWrite is searchable before the call returnsTests, and read-after-write user flows
Bounded stalenessReads see writes older than tThe sensible production default
EventualNo guarantee; maximum throughputBulk ingestion of a corpus

Deletes are the more expensive half. Removing a node from a built HNSW graph would require repairing every neighbour list that pointed at it, so no store does that on the delete path. Instead the id is tombstoned and filtered out of results:

delete(id=4821)
   → mark 4821 in the deleted bitmap        (fast, O(1))
   → the vector stays in the graph          (still traversed during search)
   → results containing 4821 are dropped    (post-filter, at query time)
   → memory is reclaimed only at compaction (which rewrites the segment)

The failure mode this creates is a workload with heavy churn — a corpus that re-ingests daily, say. Tombstones accumulate, the graph keeps traversing dead nodes, and the search returns fewer results than requested because a top-10 request now yields 10 candidates of which 4 are deleted:

after 30 days of daily re-ingestion, no compaction tuning:
  live vectors:      2,400,000
  tombstoned:        6,100,000        ← 72% of the graph is dead
  memory:            4.1× the live set
  recall@10:         0.71             ← candidates exhausted by tombstones
  p99 latency:       41 ms  (was 6 ms)
🔑 Tombstone ratio is the single most valuable health metric on a dedicated store, and almost nobody alerts on it. It degrades recall and latency together, it looks like nothing in the memory graph until it is severe, and the fix — forcing compaction, or tuning the merge policy to be more aggressive — is cheap once you know that is what you are looking at. Alert when deleted/total exceeds roughly 20%.

Updates are deletes plus inserts. There is no in-place update of a vector in an immutable segment, so re-embedding a chunk costs a tombstone and a new node. A pipeline that re-embeds unchanged content is therefore not merely wasting embedding API spend — it is actively degrading the index. That is what the content_hash column in the pgvector schema was protecting against, and the protection matters more here, not less.

Part 4 — Sharding, Replication and Fan-Out

Once a collection exceeds one machine's memory, it is split into shards, each holding a disjoint subset of vectors with its own complete index.

                        ┌──────────────┐
       query ──────────▶│ coordinator  │
                        └──────┬───────┘
             ┌────────────┬────┴───────┬────────────┐
             ▼            ▼            ▼            ▼
         shard 0      shard 1      shard 2      shard 3
         top-10       top-10       top-10       top-10        ← each does a full ANN search
             └────────────┴──────┬─────┴────────────┘
                                 ▼
                        merge → global top-10

Every shard searches for the full k. You cannot ask shard 0 for 3 results and shard 1 for 7 — you do not know in advance where the true neighbours live, so each shard returns k and the coordinator keeps the best k of N×k. Two costs follow:

CostArithmeticDesign consequence
Total work multipliesN shards × one full ANN search eachSharding buys memory capacity, not throughput per query
Latency = the slowest shardp99 of a 10-shard fan-out ≈ p99.9 of one shardTail latency degrades as shards increase

That second row is worth doing the arithmetic on, because it is counter-intuitive. If a single shard has a 99th-percentile latency of 20 ms and each shard's latency is roughly independent, the probability that all 10 shards come in under 20 ms is 0.9910 ≈ 0.90 — so what was a p99 becomes roughly a p90:

single shard:    p50 = 4 ms    p99 = 20 ms
10-shard fan-out: p50 = 6 ms   p99 = 38 ms      ← you now pay one shard's p99.9 on every query
(measured: 40M vectors, 768-dim, HNSW ef=128)

The design consequence: pick the smallest shard count that fits in memory, not the largest you can afford. Over-sharding is a common and expensive mistake — people shard for "scalability" and buy themselves worse tail latency and more merge work for no capacity they needed.

Replicas do the opposite: they are full copies of a shard, so queries are load-balanced across them and throughput scales linearly with replica count while latency stays flat. Shards for capacity, replicas for QPS is the whole rule.

shards   → capacity (memory)   → latency gets WORSE   (fan-out)
replicas → throughput (QPS)    → latency stays FLAT   (load balance)

Resharding is the expensive operation. Most stores cannot change a collection's shard count in place — the shard assignment is a hash of the id, so changing N moves nearly every vector. In practice resharding means creating a new collection and re-indexing into it, which is why the shard count is one of the few decisions worth thinking about before you create the collection. Over-provision slightly rather than exactly.

Part 5 — The Landscape Without the Marketing

The stores differ far less in algorithm than in operational model. Every one of them runs HNSW (most also offer IVF and quantisation variants), so the honest comparison is about how they are deployed, how they filter, and what happens at 3 a.m.

StoreIts actual differentiatorChoose it whenWatch out for
QdrantFilterable HNSW — filters are applied during traversal, not afterFiltering is central and you self-hostPayload indexes must be created explicitly or filters scan
MilvusDisaggregated compute/storage; many index types; built for very large scale>100M vectors, and you have platform engineersMany components (etcd, object store, message queue) — real operational surface
WeaviateObject model with schema, references and built-in vectorisation modulesYou want the store to own embedding tooCoupling ingestion to the store makes model changes harder
PineconeFully managed; no index tuning exposedYou want zero operations and accept the pricing modelLittle control when recall is wrong; cost scales with pods/units
VespaTrue hybrid ranking with a real ranking framework and multi-phase scoringRelevance is the product, not a featureThe steepest learning curve of the set
Elasticsearch / OpenSearchVectors added to a mature search engine you may already runYou already operate it and need hybrid BM25 + vectorMemory model and JVM tuning; vector search is a newer surface
FAISS (library)Not a database — an index library, the reference implementation of most ANN researchYou are embedding search into your own service and own persistenceNo persistence, no filtering, no replication, no API — you build all of it
pgvectorTransactional consistency with the source of recordThe default, up to ~10–50M vectorsSee the previous lesson for the leave signals

FAISS deserves a note, because it is frequently compared against the others as if it were one of them. It is a library: it gives you an in-memory index object with add and search. Persistence, filtering, updates, sharding, replication, an API and an operational story are all yours to build. Reaching for FAISS directly is right when you are building the store; it is usually wrong when you are building the application.

❌ Choosing a store from a benchmark leaderboard. Published ANN benchmarks measure a static, pre-loaded, unfiltered, single-node index on a public dataset — a workload that resembles no production system. They tell you nothing about filtered recall, behaviour under continuous ingestion, tombstone accumulation, fan-out tail latency, or what the failure modes look like. Two stores within 2× on a leaderboard can differ by 50× on your filtered workload.

✅ Benchmark your own corpus, your own query distribution and your own filters. Load a representative slice, replay real queries with their real filters, ingest continuously while you measure, and record recall against exact ground truth alongside p50/p99. Then kill a node and see what happens. That evaluation takes a few days and is the only one that predicts production.

Part 6 — Choosing and Migrating, Concretely

A defensible decision comes from a fixed procedure, not from a preference. The order matters: cheap disqualifying constraints first, expensive measurement last.

StepQuestionWhat it eliminates
1Do you have a measured reason to leave pgvector?Usually the whole exercise
2Managed or self-hosted? Data-residency constraints?Roughly half the candidates, for free
3Is filtering central, and how selective are the filters?Stores that only post-filter
4Do you need hybrid lexical + vector ranking?Pushes toward Vespa / Elasticsearch / Weaviate
5What is the real vector count in 2 years, and the memory bill at that size?Decides whether quantisation is mandatory
6Now benchmark the 2 survivors on your corpusThe preference you were about to act on

Estimate the memory bill before the benchmark, because it frequently decides the question on its own:

10M vectors × 1536 dims × 4 bytes (float32)      = 61.4 GB   raw
  + HNSW graph, m=16: 10M × 16 × 2 × 8 bytes     =  2.6 GB
  + payload/metadata (varies)                    ≈  5.0 GB
                                                 ─────────
                                            total ≈ 69 GB    → a 96 GB instance, or shard it

with scalar quantisation (int8):  61.4 → 15.4 GB → total ≈ 23 GB   → one 32 GB instance
with PQ (m=96, 8 bits):           61.4 →  0.96 GB → total ≈  8 GB   → cheap, recall needs work

That single calculation is often the entire argument. Quantisation moves a 3-node cluster to one node, which changes the cost by more than any store choice does — and it is available in most of them, so it is a decision about your workload rather than about the vendor.

The migration itself should be a re-index, never a data migration. If source text and metadata live in your primary database, moving stores is running the ingestion pipeline against a new target — a pipeline you need anyway for embedding-model changes:

# Dual-write, shadow-evaluate, then shift traffic — never a big-bang cutover
def search(query, vec):
    primary = old_store.search(vec, k=10)
    if shadow_enabled():                        # sampled, off the critical path
        record_shadow(new_store.search(vec, k=10), primary)
    return primary

# Promote only when the shadow comparison holds on YOUR eval set:
#   recall@10 within tolerance, p99 no worse, filtered queries specifically checked

Shadow evaluation almost always reveals a query class where the new store is worse, even when aggregate recall improves — usually the heavily filtered queries. Finding that before the cutover is the entire point, and it is the difference between a migration and an incident.

Interview Questions

Beginner: What is a dedicated vector database, and how does it differ from adding vector search to an existing database?

A dedicated vector store is a database whose primary data structure is the vector index. In something like pgvector, the vector index is a secondary index on a row store — the rows are the data, and the index points at them. That inversion is the whole difference, and everything else follows from it.

Dedicated storeVector search in an RDBMS
Primary structureThe ANN indexRows; the index is secondary
MemoryDedicated to the indexShared with OLTP buffer cache
QuantisationExtensive (SQ, PQ, binary)Limited
Sharding of the indexNativeManual, via partitioning
Consistency with source rowsNone — a separate systemTransactional

What you gain is scale: indexes that stay memory-resident past the point where a shared database instance could hold them, aggressive quantisation to cut that memory by 4–64×, and horizontal sharding.

What you give up is that last row, and it is the one that bites. There is no transaction spanning your documents table and the vector store, so deleting a document is two operations across a network that can partially fail — which is how you end up with an assistant citing a document that was deleted last week.

The practical rule is that a dedicated store should be adopted in response to a measured problem — index no longer fitting in memory, rebuild exceeding the maintenance window, search degrading OLTP — and not because a corpus crossed a round number.

Beginner: Why can't you just delete a vector from an HNSW index?

Because HNSW is a graph whose edges are stored as neighbour lists on each node. Node 4821 appears in the neighbour list of every node that selected it as a link — potentially hundreds of them, scattered across the graph. Genuinely removing it means finding all of those and repairing each list, and repairing a list well means re-running neighbour selection, which is most of the cost of inserting a node in the first place.

true delete of node 4821 would require:
  1. find every node whose neighbour list contains 4821   ← no reverse index exists
  2. remove it from each list                             ← leaves those nodes under-connected
  3. re-select replacements for each                      ← ~an insert's worth of work, each
  4. repeat per layer

Under-connected nodes are the real danger: the graph's search quality depends on connectivity, and removing links without replacing them can disconnect a region entirely, making those vectors unreachable — a silent recall loss, not an error.

So every store tombstones instead: mark the id in a deleted bitmap, keep traversing the node during search, and filter it out of the results. The delete is O(1) and the space is reclaimed later, when compaction rewrites the segment without the dead nodes.

The consequence to remember is that deleted vectors still cost you — memory, traversal time, and candidate slots. A top-10 search that finds 10 candidates of which 6 are tombstoned returns 4 results, so heavy churn degrades recall directly.

Mid: A search immediately after a successful write does not return the new vector. Is this a bug?

No — it is the store's consistency model, and it is the single most common surprise for teams arriving from relational databases. The write returned successfully because it is durable: it is in the write-ahead log. Durable and searchable are different milestones.

upsert() returns  ──▶ in WAL           (durable, NOT searchable)
                  ──▶ in mutable buffer (searchable, brute-forced)
                  ──▶ flushed to segment (searchable via the index)

The gap exists because inserting into a live HNSW graph is expensive, so writes are buffered and indexed in batches. Trading a little freshness for an order of magnitude of ingest throughput is the right trade for most workloads — but it has to be an explicit decision rather than a discovery.

The fix is to ask for the guarantee you need:

client.upsert(collection="chunks", points=[...], wait=True)   # Qdrant
es.index(index="chunks", document=doc, refresh="wait_for")    # Elasticsearch
client.search(..., consistency_level="Strong")                # Milvus

Not with a sleep. A sleep(0.5) passes locally and fails on a loaded cluster where flush is queued behind bulk ingestion; it turns a correctness requirement into a race condition that degrades exactly when the system is busiest.

Where it genuinely matters in a RAG product is read-after-write on the user's own upload: they add a document and immediately ask about it. Use strong consistency on that path only, and leave bulk ingestion eventual — per-request consistency is why these are request-level options rather than a global setting.

Mid: How do sharding and replication affect vector search latency and throughput?

They pull in opposite directions, and conflating them is a common and expensive mistake.

Shards partition the vectors. Because you cannot know in advance which shard holds the true nearest neighbours, every shard must run a full top-k search and the coordinator merges:

query → coordinator → 4 shards, each a FULL ANN search for k=10
                    → merge 40 candidates → global top-10
ShardsReplicas
AddsMemory capacityQuery throughput
Latency effectWorse (fan-out tail)Flat
Total work per queryMultiplied by shard countUnchanged

The tail-latency arithmetic is the part people miss. With 10 shards and independent latencies, a query is only fast if every shard is fast: at a per-shard p99 of 20 ms, the probability all ten come in under 20 ms is 0.9910 ≈ 0.90. Your former p99 is now roughly a p90, and the real p99 is set by each shard's p99.9.

So: shard only as much as memory forces you to, and add replicas for QPS. Over-sharding to "be scalable" buys worse tail latency, more merge work and more compaction, for capacity you did not need.

There is one exception worth knowing: if the data partitions naturally along a filter that is present in every query — per-tenant collections, for instance — you can route to a single shard and skip the fan-out entirely. That converts sharding from a latency cost into a latency win, and it is why tenant-per-shard layouts are common in multi-tenant RAG.

Finally, shard count is difficult to change later: assignment is usually a hash of the id, so changing the count relocates nearly everything. In practice resharding means re-indexing into a new collection, so it is worth over-provisioning slightly at creation time.

Senior: How would you evaluate and choose a vector store for a production RAG system?

I would run a fixed procedure that puts the cheap disqualifying constraints first and the expensive measurement last, because the goal is a defensible decision rather than a preference.

Step 0 — Establish that we need to leave the primary database. The first question is whether pgvector is genuinely failing: is the index still resident, does the rebuild fit the maintenance window, is search degrading OLTP p99? If none of those fire, the honest recommendation is to stay, and that ends the evaluation. Most of the time it does.

Step 1 — Apply the constraints that eliminate candidates for free:

ConstraintEffect
Data residency / no third-party processorsRemoves managed-only options
Team has no platform engineersRemoves the operationally heavy options
Existing Elasticsearch investmentMakes reusing it the option to beat
Hybrid lexical + vector ranking requiredPushes toward Vespa / ES / Weaviate

Step 2 — Size the memory bill, which frequently decides it outright:

10M × 1536 × 4 B = 61 GB raw + graph + payload ≈ 69 GB   → cluster
     with int8 scalar quantisation             ≈ 23 GB   → one node

If quantisation moves us from three nodes to one, that is a bigger cost lever than the choice of vendor, and it reframes the question as "which stores implement the quantisation we need well".

Step 3 — Benchmark the two survivors on our own workload, because published benchmarks measure a static unfiltered single-node index and our workload is none of those things. The harness must include: our corpus at realistic scale, replayed production queries with their real filter distributions, continuous ingestion running during measurement, recall computed against exact ground truth, and p50/p99 recorded separately for filtered and unfiltered queries.

Step 4 — Test the operational reality, which is what actually differs: kill a node mid-query and measure recovery; run the churn workload for a week and watch tombstone ratio, segment count and memory; time a full re-index, since that is the model-change cost; and confirm what the backup and restore story really is.

Step 5 — Decide on total cost of ownership, counting engineering time to operate, not just infrastructure. A managed store at twice the infrastructure cost is frequently cheaper than a self-hosted one that consumes an engineer.

And regardless of the winner, I would keep source text and metadata in the primary database, so the store remains a derived artefact and this decision stays reversible. The evaluation I have just described is only affordable because we can re-index; a store holding the only copy of the data would make every future re-evaluation prohibitive.

Senior: Design the migration from pgvector to a dedicated store for a live RAG system with zero downtime.

I would treat it as a re-index with a gradual traffic shift, never a cutover, and I would define the rollback and the success criteria before writing any migration code.

Phase 1 — Establish ground truth first. Before anything moves, build the eval set: 200–500 real queries with judged relevant chunks, plus the exact-kNN top-10 for each from the current system. Without this, "the new store is better" is unfalsifiable, and the entire migration becomes a matter of opinion.

-- ground truth from the current system, index disabled for exactness
SET enable_indexscan = off;
SELECT q.id, array_agg(c.id ORDER BY c.embedding <#> q.embedding) AS truth
FROM eval_queries q, LATERAL (
  SELECT id, embedding FROM chunks ORDER BY embedding <#> q.embedding LIMIT 10
) c GROUP BY q.id;

Phase 2 — Backfill by re-indexing, not by copying vectors. Source text lives in Postgres, so the new store is populated by running the ingestion pipeline against it — the same pipeline needed for model changes. Backfill in id order with a watermark so it is resumable, and let ongoing writes dual-write to both stores from the moment the backfill starts.

def ingest(chunk):
    pg.upsert(chunk)                       # source of record, transactional
    try:
        new_store.upsert(chunk)            # best-effort during migration
    except Exception:
        outbox.enqueue(chunk.id)           # reconcile later; never fail the write

The outbox is not optional. Dual-writing without one produces exactly the divergence the migration is supposed to avoid, and the reconciler is also what proves the two stores agree before cutover.

Phase 3 — Shadow-read before serving anything. On a sampled fraction of live traffic, query both and record the comparison off the critical path:

primary = pg.search(vec, k=10, filters=f)
if sample():
    shadow  = new_store.search(vec, k=10, filters=f)
    metrics.record(overlap=jaccard(primary, shadow),
                   recall_vs_truth=recall(shadow, ground_truth),
                   latency=(pg_ms, new_ms), filtered=bool(f))
return primary

Segment those metrics by filter selectivity. Aggregate recall almost always looks fine; the regression, when there is one, is concentrated in heavily filtered queries where the new store post-filters ANN candidates. That is the specific failure the shadow phase exists to catch, and finding it here costs a config change rather than an incident.

Phase 4 — Shift traffic gradually, 1% → 5% → 25% → 50% → 100%, with a single env-var revert and at least a day at each step. Watch end-to-end answer quality, not just retrieval metrics: retrieval recall can hold while answer quality drops, usually because result ordering changed and the top-3 that the model actually reads are different.

Phase 5 — Keep pgvector as a fallback for a full cycle before decommissioning, and only then drop the index (never the content column, which stays the system of record).

Gate before promotingCriterion
recall@10 vs ground truthWithin 1 point, including filtered queries
p99 latencyNo worse than current
Reconciler divergenceZero outstanding for 24 h
Answer quality on the eval setNo regression

The rollback is what makes this safe: because Postgres keeps serving throughout and holds the source of record, reverting is a flag flip with no data loss at any point. A migration without that property is not a migration plan, it is a launch.

after  35000: segments=6 indexed=30000 points=35000
after  50000: segments=4 indexed=50000 points=50000    ← compaction merged segments

Two things to notice. First, indexed_vectors_count lags points_count — vectors are searchable before they are in an HNSW graph, served by brute-force scan of the buffer until then. Second, segment count goes down at the end: that is compaction merging segments, and it is why latency improves after ingestion stops.

Confirm the freshness gap directly:

new_id, v = 999_999, vecs[0].tolist()
c.upsert("demo", points=[PointStruct(id=new_id, vector=v)], wait=False)
hits = c.search("demo", query_vector=v, limit=5)
print("found immediately:", new_id in [h.id for h in hits])   # → often False

c.upsert("demo", points=[PointStruct(id=new_id, vector=v)], wait=True)
hits = c.search("demo", query_vector=v, limit=5)
print("found with wait:  ", new_id in [h.id for h in hits])   # → always True

That pair is the assertion worth putting in a test suite — it pins the consistency requirement explicitly instead of leaving it to a sleep.

3 (medium): Quantify the fan-out tail-latency cost of sharding.
Solution

Simulate first — the effect is a property of the maximum of independent draws, so it is visible without a cluster:

import numpy as np
rng = np.random.default_rng(1)

# one shard's latency: lognormal, p50 ~4 ms with a realistic tail
def shard_latency(n): return rng.lognormal(mean=np.log(4), sigma=0.55, size=n)

for shards in (1, 2, 4, 8, 16):
    per_query = shard_latency((200_000, shards)).max(axis=1)   # slowest shard wins
    print(f"{shards:2d} shards  p50={np.percentile(per_query,50):5.2f}  "
          f"p95={np.percentile(per_query,95):5.2f}  "
          f"p99={np.percentile(per_query,99):6.2f} ms")

 1 shards  p50= 4.00  p95= 9.90  p99= 14.42 ms
 2 shards  p50= 5.02  p95=11.55  p99= 16.31 ms
 4 shards  p50= 6.28  p95=13.30  p99= 18.28 ms
 8 shards  p50= 7.64  p95=15.19  p99= 20.42 ms
16 shards  p50= 9.15  p95=17.24  p99= 22.71 ms

p50 more than doubles from 1 to 16 shards, and the p99 rises by 58% — with no change in data, index or query. The median moves because the median of a maximum is not the maximum of medians: with 16 shards you need all sixteen to be fast.

Verify against a real store by creating the same data with different shard counts:

for n in (1, 4, 8):
    c.recreate_collection(f"shards{n}", shard_number=n,
        vectors_config=VectorParams(size=128, distance=Distance.COSINE))
    c.upsert(f"shards{n}", points=[PointStruct(id=i, vector=v.tolist())
                                   for i, v in enumerate(vecs)], wait=True)

    lat = []
    for q in vecs[:500]:
        t = time.perf_counter(); c.search(f"shards{n}", query_vector=q.tolist(), limit=10)
        lat.append((time.perf_counter()-t)*1000)
    print(f"{n} shard(s): p50={np.percentile(lat,50):.2f}  p99={np.percentile(lat,99):.2f} ms")

1 shard(s): p50=1.81  p99= 4.902 ms
4 shard(s): p50=2.94  p99= 8.14 ms
8 shard(s): p50=3.71  p99=11.02 ms

The conclusion to carry into a design review: shard because memory forces you to, and choose the smallest count that fits. If someone proposes more shards to make search faster, this table is the answer — shards add capacity, replicas add throughput, and only replicas leave latency alone.

4 (medium): Compare filtered search: filter-during-traversal vs post-filtering.
Solution

This is the difference that matters most in production and that public benchmarks never measure. Build a collection with a skewed filter field:

from qdrant_client.models import PayloadSchemaType

c.recreate_collection("filt",
    vectors_config=VectorParams(size=128, distance=Distance.COSINE))

    PointStruct(id=i, vector=v.tolist(), payload={"tenant": int(t)})
    for i, (v, t) in enumerate(zip(vecs, tenants))], wait=True)

First, without a payload index — the trap:

no payload index: 10 hits in 38.4 ms

Now create the payload index and repeat:

with payload index: 10 hits in 2.1 ms          ← 18x faster, same results

The payload index is not optional. Without it the filter is evaluated by scanning payloads, which is the most common cause of "our vector store is slow when we filter" — and it is a one-line fix that most teams find months late.

Now simulate what post-filtering would have done, which is what a store lacking filterable traversal must do:

# retrieve N unfiltered candidates, then filter in the client
for n in (10, 100, 1000):
    cands = c.search("filt", query_vector=vecs[3].tolist(), limit=n)
    kept = [h for h in cands if h.payload["tenant"] == 57]
    print(f"post-filter from {n:5d} candidates → {len(kept):2d} survivors")

post-filter from    10 candidates →  0 survivors
post-filter from   100 candidates →  0 survivors
post-filter from  1000 candidates →  1 survivors     ← asked for 10

Zero results from 100 candidates, for a query the filtered search answered exactly in 2 ms. With a filter keeping 0.05% of the corpus, post-filtering has to over-fetch by roughly 1/selectivity — 20,000 candidates for 10 results — which is slower than a brute-force scan of the matching subset.

5 (hard): Build an evaluation harness that would actually decide a store choice.
Solution

The requirement is a harness that measures the things production exercises and benchmarks do not: filtered recall, behaviour under concurrent ingestion, and tail latency — all against exact ground truth.

import numpy as np, time, threading
from dataclasses import dataclass, field

@dataclass
class Result:
    name: str
    recalls: list = field(default_factory=list)
    latencies: list = field(default_factory=list)

def exact_topk(corpus, q, k, mask=None):
    """Ground truth by brute force. mask = boolean filter over the corpus."""
    sims = corpus @ q
    idx = np.arange(len(corpus))
    if mask is not None:
        sims, idx = sims[mask], idx[mask]
    top = np.argsort(-sims)[:k]
    return set(idx[top].tolist())

def evaluate(store, corpus, queries, filters, k=10, ingest_during=False):
    res = Result(store.name)
    stop = threading.Event()

    def background_ingest():                 # the load benchmarks never apply
        i = 10_000_000
        while not stop.is_set():
            store.upsert_batch(np.random.normal(size=(500, corpus.shape[1])), start_id=i)
            i += 500
            time.sleep(0.1)

    if ingest_during:
        threading.Thread(target=background_ingest, daemon=True).start()

    for q, f in zip(queries, filters):
        mask = None if f is None else (tenants == f)
        truth = exact_topk(corpus, q, k, mask)

        t = time.perf_counter()
        got = store.search(q, k=k, filter=f)
        res.latencies.append((time.perf_counter() - t) * 1000)
        res.recalls.append(len(truth & set(got)) / max(len(truth), 1))

    stop.set()
    return res

Report filtered and unfiltered separately — the aggregate number hides the regression that matters:

def report(res, filters):
    for label, keep in (("unfiltered", [f is None for f in filters]),
                        ("filtered",   [f is not None for f in filters])):
        r = np.array(res.recalls)[keep]; l = np.array(res.latencies)[keep]
        print(f"{res.name:10} {label:10} recall@10={r.mean():.3f}  "
              f"p50={np.percentile(l,50):5.2f}  p99={np.percentile(l,99):6.2f} ms")

store_a    filtered   recall@10=0.974  p50= 2.44  p99=  6.81 ms

store_b    filtered   recall@10=0.412  p50= 1.88  p99=  5.02 ms     ← post-filters

Store B wins on every number a public leaderboard would print, and is unusable for this workload. Aggregate recall across all queries would have read 0.70 vs 0.98 — bad, but not obviously a filtering problem. Segmenting is what makes the cause visible.

Then run it again with ingestion in flight, which is the second thing benchmarks omit:

6 (hard): Plan a zero-downtime migration with a reconciliation guarantee.
Solution

The scenario: 40M chunks in pgvector, index no longer resident (cache hit rate 84%), p99 at 340 ms and rising, live RAG traffic at 60 QPS. The decision to move is justified; the plan must not drop a query or lose a vector.

Step 1 — Freeze the ground truth before anything changes.

-- 500 real queries sampled from production logs, exact top-10 from the current system
CREATE TABLE eval_truth AS
SELECT q.id AS query_id,
       (SELECT array_agg(c.id ORDER BY c.embedding <#> q.embedding)
        FROM (SELECT id, embedding FROM chunks
              ORDER BY embedding <#> q.embedding LIMIT 10) c) AS truth
FROM eval_queries q;

Exact, not ANN — otherwise you are comparing the new store against the old store's errors.

Step 2 — Dual-write with an outbox, before backfilling. Turning this on first means the backfill has a fixed endpoint rather than chasing a moving target:

def write_chunk(chunk):
    with pg.transaction():
        pg.upsert(chunk)
        pg.insert_outbox(chunk.id, op="upsert")     # same transaction: cannot be lost

# separate worker drains the outbox
def drain():
    for row in pg.claim_outbox(limit=500):
        try:
            new_store.upsert(pg.load_chunk(row.chunk_id))
            pg.delete_outbox(row.id)
        except Exception:
            pg.bump_retry(row.id)                    # stays queued; never silently dropped

The outbox row is written in the same transaction as the data. That is what makes the guarantee real: a crash between the two writes cannot produce a vector that exists in Postgres and never reaches the new store.

Step 3 — Backfill by re-indexing, resumably:

def backfill(batch=2000):
    last = load_watermark() or 0
    while True:
        rows = pg.query("SELECT id, content, tenant_id, model FROM chunks "
                        "WHERE id > %s ORDER BY id LIMIT %s", last, batch)
        if not rows: break
        new_store.upsert_batch([embed_or_reuse(r) for r in rows])
        last = rows[-1].id
        save_watermark(last)          # resumable: a crash costs one batch

embed_or_reuse matters: the embeddings already exist in Postgres, so re-embedding 40M chunks would cost real money for no benefit — read the stored vector unless the model is also changing.

Step 4 — Reconcile, and prove agreement:

def reconcile():
    """Sample-based, continuous. Cheap enough to run forever."""
    ids = pg.sample_ids(10_000)
    missing = [i for i in ids if not new_store.exists(i)]
    extra   = [i for i in new_store.sample_ids(10_000) if not pg.exists(i)]
    metrics.gauge("migration.missing", len(missing))
    metrics.gauge("migration.orphaned", len(extra))     # deletes that did not propagate
    for i in missing: outbox.enqueue(i)
    for i in extra:   new_store.delete(i)

Orphans are the direction people forget. A delete applied to Postgres but lost on the way to the store leaves a vector that will be retrieved and cited — a deleted document resurfacing is worse than a missing one.

Step 5 — Shadow-read, segmented by filter selectivity:

shadow (5% sample, 48 h):
  unfiltered      overlap@10 = 0.94   recall_vs_truth = 0.972   p99  41 ms (was 340)
  filter >10%     overlap@10 = 0.91   recall_vs_truth = 0.968   p99  44 ms
  filter <1%      overlap@10 = 0.38   recall_vs_truth = 0.402   p99  39 ms   ← REGRESSION

There it is. Aggregate recall reads 0.93 and looks like a clear win; the narrow-filter class collapsed because the new store post-filters ANN candidates while Postgres was switching to an exact scan. The fix is a store-side payload index plus raising the candidate count for selective filters — and finding it here costs a configuration change instead of an incident.

Step 6 — Shift traffic behind a flag, with gates:

StageDurationGate to advance
1%24 hNo error-rate change; recall gates met
5%24 hp99 improved; answer quality flat or better
25%48 hReconciler clean; memory and segment count stable
50% → 100%1 weekFull cycle including the weekly re-ingest

Include a full ingestion cycle before 100%. Tombstone accumulation and compaction behaviour only appear after the churn workload has run at least once, and they are exactly the properties that were invisible in every benchmark.

Step 7 — Decommission carefully. Keep pgvector's index for one more cycle as a one-flag fallback, then drop the index — never the content column. Postgres remains the system of record, which is what keeps this decision reversible and the next evaluation affordable.

🎯 Key Takeaways

  • A dedicated store makes the vector index the primary data structure; everything it gains and everything it costs follows from that inversion.
  • What you give up is transactional consistency with the source of record — the origin of orphaned vectors, stale metadata and results citing deleted documents.
  • Recall comes from the algorithm, not the vendor: HNSW is HNSW everywhere. A dedicated store lets you go further along the recall/latency/memory curve at scale; it does not move the curve.
  • Nearly all of them share one architecture: immutable segments + a mutable buffer + background compaction. Most surprising behaviour is a consequence of that shape.
  • Every segment is searched and results merged, so segment count raises latency and lowers recall — compaction is a performance control, not housekeeping.
  • A durable write is not a searchable write; use explicit strong consistency (wait=True, refresh="wait_for") rather than sleep().
  • Deletes are tombstones because removing a node from a built HNSW graph would require repairing every neighbour list that points at it.
  • Tombstones cost memory, traversal and candidate slots; above ~20% deleted, recall and latency degrade together. Alert on the ratio.
  • An update is a delete plus an insert, so re-embedding unchanged content actively degrades the index — content-hash and skip.
  • Shards add capacity and make tail latency worse (every shard runs a full top-k search); replicas add throughput and leave latency flat.
  • Pick the smallest shard count that fits in memory; shard count is effectively fixed at creation because resharding means re-indexing.
  • Filtering is the real differentiator: filtering during traversal returns correct results where post-filtering ANN candidates returns none.
  • Payload/metadata indexes must be created explicitly, or filters degenerate into scans — a one-line fix teams find months late.
  • Public ANN benchmarks measure a static, unfiltered, single-node index; benchmark your corpus, your filters, and measure while ingesting.
  • Size the memory bill early — quantisation often changes the cost more than the choice of vendor does.
  • Keep source text and metadata in your primary database so the store stays a derived artefact and migration is a re-index.
  • Migrate by dual-writing through a transactional outbox, backfilling resumably, shadow-evaluating by filter selectivity, then shifting traffic behind a revertible flag.
