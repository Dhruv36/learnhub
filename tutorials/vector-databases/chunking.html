Chunking & Ingestion RAG in Production

What you'll master: why chunking is the highest-leverage decision in a RAG system and the two competing pressures that set every chunk size; the strategies that matter — fixed, recursive, structural, semantic — and the honest evidence on which wins where; what overlap actually buys and why the usual 10–20% is mostly cargo cult; how to keep a chunk retrievable without making it unreadable, via contextual headers and the small-to-big pattern; and how to build an ingestion pipeline that is idempotent, resumable and cheap to re-run, because you will re-run it. Prerequisites: Embeddings & Vector Space, Metadata Filtering & Hybrid Search.

Part 1 — Why Chunking Decides Everything Downstream

Every other component in a RAG system operates on chunks it did not choose. The embedding model encodes the chunk you gave it, the index searches over those encodings, the reranker reorders them, and the LLM answers from whatever survived. A fact split across two chunks is not retrievable by any of them, no matter how good they are.

source document
     │
     ▼
  CHUNKING  ────────────────────────────────────▶  everything below inherits this
     │                                              and cannot repair it
     ▼
  embedding → index → retrieval → rerank → LLM

The reason it is hard is that two pressures pull in opposite directions, and there is no size that satisfies both:

Small chunks (100–200 tokens)Large chunks (800–1500 tokens)
Embedding precisionHigh — one topic, one vectorLow — the vector is an average of several topics
Self-containednessLow — pronouns and references dangleHigh — the context is inside the chunk
Retrieval behaviourPrecise, but you need many of themRecall-friendly, but dilutes the match
Context budgetMany chunks fit; more of them are noiseFew fit; each carries more irrelevant text

The dilution effect is the part worth understanding mechanically. An embedding is a single vector for the whole chunk, so it approximates the average of the content. Put one relevant sentence in a chunk with nine irrelevant ones and the vector mostly encodes the nine:

query: "what is the retry limit for webhook delivery?"

chunk A (120 tokens, just the retry policy)        cosine = 0.81
chunk B (1400 tokens, whole webhooks page          cosine = 0.58   ← contains the answer
         including the retry policy)                                  but ranks lower

Chunk B contains the answer and loses to a chunk that also contains it. That is not a model failure — the vector for B genuinely is less similar to the query, because most of B is about something else. This is why "just use big chunks so nothing gets split" does not work.

🔑 Chunk for retrieval, then expand for generation. The two jobs have opposite optimal sizes, so stop trying to solve both with one number. Embed small, precise units so the vector is sharp; at retrieval time, return the surrounding context the LLM needs to actually answer. That decoupling — the small-to-big pattern in Part 4 — resolves the tension rather than compromising between its halves, and it is the single most valuable idea in this lesson.

Part 2 — The Strategies, and What They Actually Buy

Four families, in ascending order of cost. The useful question is not "which is best" but "what does each one buy over the one below it".

Fixed-size chunking splits every N tokens regardless of content. It is the baseline, and its problem is visible immediately:

...the retry limit is 5 attempts. After the fifth failure the endpoint is
marked unhealthy and dis|                                    ← chunk boundary
|abled for 24 hours. To re-enable it, call POST /webhooks/{id}/enable...

A query about re-enabling a webhook now matches a chunk starting mid-word. Fixed-size is only reasonable for text with no structure at all — transcripts without speaker turns, OCR output — and even then, split on sentence boundaries rather than token counts.

Recursive character splitting is the sensible default. It tries a list of separators in order, splitting on the most semantically meaningful one that produces small-enough pieces:

separators = ["\n\n",   # paragraphs   — try first
              "\n",     # lines
              ". ",     # sentences
              " ",      # words
              ""]       # characters   — last resort

def split(text, size, seps):
    if len(text) <= size or not seps:
        return [text]
    sep, rest = seps[0], seps[1:]
    parts, out, buf = text.split(sep) if sep else list(text), [], ""
    for p in parts:
        candidate = (buf + sep + p) if buf else p
        if len(candidate) <= size:
            buf = candidate
        else:
            if buf: out.append(buf)
            out.extend(split(p, size, rest) if len(p) > size else [p])
            buf = ""
    if buf: out.append(buf)
    return out

It keeps paragraphs whole when it can and degrades gracefully when it cannot. That is most of the value of "smart" chunking, for about fifteen lines of code.

Structural chunking uses the document's own boundaries, and where the format supports it this beats everything else — because the author already decided what belongs together:

FormatNatural boundaryExtra to carry
MarkdownHeadings (#, ##)The heading path as a prefix
HTML<section>, <h2>, <article>Breadcrumb / page title
CodeFunction / class (AST, not regex)File path, imports, class name
PDFSections; never pagesDocument title, section number
SlidesOne slide per chunkDeck title, slide number
Tables/CSVRow groups with the header repeatedColumn headers on every chunk

Two of those rows are worth calling out. Splitting a PDF by page is the most common ingestion bug in production RAG: a page break is a typesetting artefact, not a semantic boundary, and it reliably cuts sentences and tables in half. And a table chunked without repeating its header is unusable — the numbers survive, the meaning does not.

Semantic chunking embeds each sentence and cuts where consecutive similarity drops, putting boundaries at topic shifts:

def semantic_chunks(sentences, embed, threshold_pct=90, max_tokens=500):
    E = embed(sentences)                       # normalised
    sims = [float(E[i] @ E[i+1]) for i in range(len(E)-1)]
    cut = np.percentile(sims, 100 - threshold_pct)   # lowest-similarity joins

    chunks, buf = [], [sentences[0]]
    for i, s in enumerate(sentences[1:]):
        if sims[i] < cut or count_tokens(buf) > max_tokens:
            chunks.append(" ".join(buf)); buf = []
        buf.append(s)
    return chunks + ([" ".join(buf)] if buf else [])

The honest verdict on semantic chunking: it costs an embedding call per sentence at ingestion and typically buys 1–3 points of recall over recursive splitting on prose — and roughly nothing on documents that already have structure, because the structure already encodes the topic shifts. It is worth it for long unstructured prose (transcripts, reports, scanned books) and is usually not worth it for documentation, which is the corpus most teams actually have.

StrategyIngestion costTypical recall vs recursiveUse when
Fixed-sizeFree−5 to −10 ptsGenuinely unstructured text, as a baseline
RecursiveFreebaselineThe default
StructuralFree (a parser)+3 to +8 ptsWhenever the format has structure
Semantic1 embed / sentence+1 to +3 pts on prose, ~0 on structuredLong unstructured prose only

So the ordering that matters is structural > recursive > semantic > fixed, which is not the ordering by sophistication. Parse the format you have before reaching for an embedding-based splitter.

Part 3 — Size and Overlap, With the Numbers

Chunk size is usually copied from a tutorial. It should come from the query length distribution and the corpus, and it is cheap to measure because chunking is the one parameter you can re-run in minutes.

Documentation corpus, 500 judged queries, recall@10:

  chunk size    recall@10   chunks    notes
  ──────────    ─────────   ──────    ─────
    100 tok       0.71      41,200    precise but fragmentary; answers span chunks
    250 tok       0.86      17,400    ← knee
    400 tok       0.88      11,100    ← best
    600 tok       0.85       7,600    dilution starting
   1000 tok       0.79       4,500    clear dilution
   1500 tok       0.72       3,100    a chunk covers several topics
Content typeSensible starting sizeWhy
API / reference docs200–400 tokensOne endpoint or parameter per chunk
Narrative prose, articles400–800Arguments develop across paragraphs
Legal contractsBy clause, whatever the sizeA clause is the unit of meaning

Chat / support transcriptsBy turn group, 200–400Question and answer belong together

Overlap is more cargo cult than technique. The standard advice — 10–20% overlap — exists to stop a fact being cut in half at a boundary. It does work for that, and it costs proportionally:

10,000 chunks at 400 tokens, 20% overlap
  → storage:   +20% vectors, +20% index memory
  → ingestion: +20% embedding spend
  → retrieval: near-duplicate chunks compete for the same top-k slots

That last line is the cost nobody counts. With heavy overlap, positions 1 and 2 in your results are frequently the same text shifted by 80 tokens, so a top-5 context window holds three distinct passages instead of five.

SituationOverlapReasoning
Structural chunking (headings, clauses, functions)0Boundaries are already semantic — overlap only duplicates
Recursive on prose10–15%Cheap insurance against mid-argument splits
Fixed-size on unstructured text15–25%Boundaries are arbitrary, so cover them
Small-to-big / sentence windows0Expansion at retrieval already supplies the neighbours

If you are using structural chunking or small-to-big, set overlap to zero and spend the 20% on retrieving more candidates instead — which, per the previous lesson, buys more recall than overlap does.

Part 4 — Making Chunks Retrievable Without Making Them Unreadable

A chunk taken out of its document loses the context that made it meaningful. The fix is not bigger chunks — it is putting the context back in a form the embedding can see.

Contextual headers prepend the document's structural path to each chunk before embedding:

raw chunk:
  "The maximum is 5. After that the endpoint is disabled for 24 hours."
  → embeds as almost nothing: "maximum of what?"

with a contextual header:
  "Webhooks > Delivery > Retry policy
   The maximum is 5. After that the endpoint is disabled for 24 hours."
  → embeds as a chunk about webhook retry limits

def contextualise(chunk_text, doc_title, heading_path):
    header = " > ".join([doc_title] + heading_path)
    return f"{header}\n\n{chunk_text}"

# embed the contextualised text; STORE the raw text for display and citation
embedding = embed(contextualise(raw, doc.title, chunk.headings))
store(id=chunk.id, embedding=embedding, content=raw, headings=chunk.headings)

Embed the contextualised version, store the raw version. The header is a retrieval aid, not content — showing it to the user as part of the quoted passage is confusing, and feeding it to the LLM wastes context on a breadcrumb the model does not need.

This is nearly free and typically worth 5–10 points of recall on documentation, which is a better return than any chunking-strategy upgrade in Part 2.

Small-to-big is the pattern that resolves Part 1's tension directly: index small units for precision, return large units for comprehension.

   INDEXED (embedded)              RETURNED (to the LLM)
   ──────────────────              ─────────────────────
   sentence / small chunk    ──▶   its parent section
   200 tokens, sharp vector        1200 tokens, complete context

def index_small_to_big(doc):
    for section in split_by_heading(doc):
        parent_id = store_parent(section.text)                 # not embedded
        for child in recursive_split(section.text, size=200):
            store_child(embed(contextualise(child, doc.title, section.headings)),
                        content=child, parent_id=parent_id)

def retrieve(query, k=5):
    children = vector_search(embed(query), limit=k * 3)
    parent_ids = dedupe([c.parent_id for c in children])[:k]    # dedupe matters
    return [load_parent(pid) for pid in parent_ids]

The dedupe is the whole trick. Several matching children usually share a parent — which is a signal that the parent is highly relevant — and without deduplication you return the same section three times and fill the context window with duplicates.

PatternIndexReturnBest for
PlainChunkSame chunkUniform, self-contained content
Contextual headersHeader + chunkChunkAlmost always — nearly free
Small-to-bigSmall childParent sectionStructured docs; the strongest general pattern
Sentence windowOne sentenceSentence ± n neighboursDense prose, precise fact lookup
Summary indexingLLM summary of a sectionFull sectionLong documents where queries are thematic

Summary indexing deserves a caution: it costs an LLM call per section at ingestion, and it is the only pattern here that can lose information — if the summary omits a detail, that detail becomes unretrievable. Use it to supplement chunk-level indexing, not to replace it.

Part 5 — The Ingestion Pipeline

Ingestion is a data pipeline, and it should be built like one: idempotent, resumable, observable. The reason is simple — you will re-run it, on a model change, a chunking change, or a bug fix, and if re-running is expensive or risky, you will avoid improving the system.

source → extract → clean → chunk → contextualise → embed → upsert
   │        │        │        │          │            │       │
 hash    parser   dedupe   strategy   headers      batch   idempotent
 skip    per      boiler-  per type   + metadata   + cache   key
 unchanged type   plate

def ingest(doc, store, embedder):
    content_hash = sha256(doc.raw_bytes).hexdigest()
    if store.get_doc_hash(doc.uri) == content_hash:
        return "unchanged"                      # the cheapest possible path

    text   = extract(doc)                       # per-format parser
    chunks = chunk_for(doc.content_type, text)

    texts = [contextualise(c.text, doc.title, c.headings) for c in chunks]
    vecs  = embedder.embed_batch(texts)         # ONE call per batch, not per chunk

    store.replace_document_chunks(              # atomic: delete old + insert new
        doc.uri,
        [Chunk(id=f"{doc.uri}#{i}", vector=v, content=c.text,
               headings=c.headings, model=embedder.name, doc_hash=content_hash)
         for i, (c, v) in enumerate(zip(chunks, vecs))],
    )
    return "reindexed"
PropertyMechanismWhy it matters
IdempotentDeterministic chunk id {uri}#{index}Re-running produces no duplicates
IncrementalContent hash per documentRe-ingestion skips unchanged docs — usually 95%+
ResumableWatermark on document idA crash costs one batch, not the run
Atomic per documentDelete-then-insert in one transactionNo window where a doc is half-indexed
Traceablemodel + doc_hash on every chunkDetects a partially-migrated index

Deleting removed chunks is the step that gets skipped. When a document shrinks from 12 chunks to 8, chunks 9–12 remain in the index and keep being retrieved — stale content citing a document that no longer says it. replace_document_chunks must delete by document, not upsert by chunk.

Embedding is the dominant cost, so batch and cache it:

# per-chunk calls: 10,000 requests, network-bound, ~25 minutes
for c in chunks: c.vector = embed(c.text)

# batched: ~100 requests, ~90 seconds
for batch in chunked(chunks, 100):
    for c, v in zip(batch, embed_batch([x.text for x in batch])):
        c.vector = v

# cache by hash of the exact embedded text — survives chunking-strategy changes
def embed_cached(texts, cache, embedder):
    keys    = [sha256(t.encode()).hexdigest() for t in texts]
    missing = [t for t, k in zip(texts, keys) if k not in cache]
    for k, v in zip([sha256(t.encode()).hexdigest() for t in missing],
                    embedder.embed_batch(missing)):
        cache[k] = v
    return [cache[k] for k in keys]

On a re-run after a chunking tweak, most chunk texts are unchanged, so the cache turns a full re-embed into a partial one. That is what makes iterating on chunking affordable — and iterating on chunking is where the recall gains are.

❌ Treating chunk size as a constant to be chosen once from a blog post. Teams set chunk_size=1000, overlap=200 on day one, build everything on top, and then tune the embedding model, the reranker and the prompt — the three most expensive knobs — while the cheapest and highest-leverage one is never revisited. When recall is poor, the chunking is usually why.

✅ Treat chunking as the first parameter to sweep, and build the pipeline so sweeping is cheap. Content-hash skipping, an embedding cache keyed by text, and deterministic chunk ids make a full re-chunk-and-re-index a routine operation rather than a project. Then run the sweep against a judged query set: size, strategy, overlap, contextual headers — four experiments, hours not weeks, and typically worth more than a model upgrade.

Part 6 — What Breaks in Real Corpora

Everything above assumes clean text. Extraction is where most ingestion bugs actually live, and they are silent — a bad parse produces plausible-looking chunks that simply do not retrieve.

SourceWhat goes wrongFix
PDFMulti-column text interleaved line by lineA layout-aware parser; verify on a sample
PDFHeaders/footers/page numbers in every chunkStrip repeated lines across pages
HTMLNav, cookie banners and footers dominateExtract the main content region only
WordTracked changes and comments inlined as textAccept revisions during extraction
SlidesSpeaker notes silently dropped — often the real contentInclude notes; label them
CodeRegex splitting cuts mid-functionParse the AST
ScansOCR noise embeds as gibberishConfidence threshold; quarantine low-confidence pages
AnyBoilerplate repeated in thousands of chunksDetect and strip near-duplicate leading/trailing lines

Boilerplate is the quiet one. If every page of a corpus ends with the same 60-word legal footer, then every chunk containing it shares a large common component — which pulls those vectors toward each other and makes them all mildly similar to any query mentioning the boilerplate's vocabulary:

before stripping footers:  mean pairwise cosine between random chunks = 0.62
after:                                                                 0.31
                                                          recall@10:   0.74 → 0.86

Mean pairwise similarity between random chunks is the diagnostic worth running once on any new corpus. Above roughly 0.5 for unrelated chunks, something is shared across everything — boilerplate, a template, a repeated header — and stripping it is usually the single largest recall win available.

Finally: log what you produced, and look at it. A chunk-length histogram catches more ingestion bugs than any metric:

chunk length distribution after ingestion:
   < 50 tokens:  4,210  (18%)   ← suspicious: fragments from a bad parse
  50-200:        6,100  (26%)
 200-400:        9,800  (42%)
 400-600:        2,900  (12%)
   > 600:          410   (2%)

sample the <50 bucket:
  "Table 4.2"
  "See Appendix B."
  "|---|---|---|"                ← markdown table separators as standalone chunks

Those fragments are unretrievable noise that still costs index memory and can occupy top-k slots. Drop chunks below a minimum token count, or merge them into their neighbour.

Interview Questions

Beginner: What is chunking and why is it necessary?

Chunking is splitting source documents into the units you embed and retrieve. It is necessary for two independent reasons.

1. Embedding models have a token limit — commonly 512 or 8192 tokens — so a 50-page document cannot be embedded at all without splitting.

2. More importantly, one vector per document would be useless even if it fit. An embedding is a single point representing the whole input, so a document covering ten topics produces a vector that is an average of ten topics and is close to none of them:

query: "what is the webhook retry limit?"

whole 40-page API doc as one vector      cosine = 0.31   ← contains the answer
just the retry-policy paragraph          cosine = 0.81

The document contains the answer and does not retrieve, because most of it is about something else. That dilution is the real reason for chunking.

The retrieval unit is also the context unit, which is the second half of the job: what you retrieve is what the LLM gets. Too small and the answer is fragmentary; too large and most of the context window is irrelevant text. Chunk size is where those two pressures meet, which is why it is the parameter that most affects RAG quality.

Beginner: What is chunk overlap and when do you actually need it?

Overlap repeats the last N tokens of each chunk at the start of the next, so a fact that would otherwise be cut in half by a boundary appears whole in at least one chunk.

chunk 1: "...the retry limit is 5 attempts. After the fifth failure"
chunk 2: "After the fifth failure the endpoint is disabled for 24 hours..."
          └──────── overlap ────────┘

It works, and it is not free: 20% overlap means 20% more vectors, 20% more index memory, 20% more embedding spend — and a subtler cost that people miss, which is that near-duplicate chunks compete for the same top-k slots. A top-5 result set can contain three copies of essentially the same passage, so the context window holds less distinct information than it appears to.

ChunkingOverlapWhy
Structural (headings, clauses, functions)0Boundaries are already semantic
Recursive on prose10–15%Cheap insurance at arbitrary-ish boundaries
Fixed-size15–25%Boundaries are entirely arbitrary
Small-to-big0Retrieval-time expansion already provides neighbours

So overlap is compensation for bad boundaries. If the boundaries are good — because you split on headings, or because you expand to the parent section at retrieval time — overlap buys nothing and costs 20%. Spend that 20% retrieving more candidates instead, which measurably buys more.

Mid: Compare fixed, recursive, structural and semantic chunking. Which would you reach for?

They are four points on a cost curve, and the surprise is that the most expensive is not the best.

StrategyMechanismCostRecall vs recursive
FixedEvery N tokensFree−5 to −10 pts
RecursiveTry ¶ → line → sentence → wordFreebaseline
StructuralThe document's own boundariesA parser+3 to +8 pts
SemanticCut where sentence similarity drops1 embed/sentence+1 to +3 on prose, ~0 on structured

I would reach for structural first, and fall back to recursive. Structural wins because the author already did the work — a heading, a clause, a function signature is a human decision about what belongs together, and no algorithm infers that better than reading it directly.

Semantic chunking is the one people over-value. It costs an embedding per sentence at ingestion and buys 1–3 points on unstructured prose. On documentation — which is what most teams actually have — it buys close to nothing, because the structure already marks the topic shifts that semantic chunking is trying to detect.

In practice I would dispatch on content type:

markdown / html  → split by heading, carry the heading path
code             → AST, one function per chunk
pdf              → sections (never pages), strip headers/footers
tables           → row groups, repeat the header row
plain prose      → recursive, 400 tokens, 10% overlap
transcripts      → turn groups; semantic if genuinely unstructured

And I would spend the effort elsewhere: contextual headers are nearly free and typically worth 5–10 points — more than the gap between any two strategies in that table. Chunking strategy matters less than what you attach to the chunk.

Mid: What is the small-to-big pattern and what problem does it solve?

It decouples the unit you index from the unit you return: embed small chunks for retrieval precision, return their parent section for generation.

The problem it solves is that those two jobs have opposite optimal sizes. Small chunks give sharp vectors — one topic, one embedding, high similarity to a matching query. Large chunks give the LLM enough context to answer. There is no single size that does both, and picking a middle value does neither well.

INDEXED: 200-token child   → sharp vector, retrieves precisely
RETURNED: 1200-token parent → complete context, LLM can actually answer

def retrieve(query, k=5):
    children   = vector_search(embed(query), limit=k * 3)
    parent_ids = dedupe([c.parent_id for c in children])[:k]
    return [load_parent(pid) for pid in parent_ids]

The deduplication is essential and easy to omit. Several matching children usually share a parent — retrieve 15 children and you may get only 4 distinct parents. That is actually a useful signal (multiple hits in one section means the section is relevant), but without dedupe you return the same section three times and waste the context window.

Overlap becomes unnecessary, because expansion to the parent already supplies the surrounding text that overlap existed to preserve. So the pattern pays for itself: you drop 10–20% of storage and embedding spend.

The variants trade off along the same axis: a sentence window (index one sentence, return it ± 2 neighbours) is small-to-big with a fixed radius instead of a structural parent — better for dense prose without clear sections, worse when sections are meaningful. Summary indexing (embed an LLM summary, return the full section) goes further and is the only variant that can lose information, so it should supplement chunk-level indexing rather than replace it.

Senior: Design the ingestion pipeline for a RAG system over a heterogeneous corpus — PDFs, Confluence, source code, support tickets.

The design principle is that ingestion will be re-run many times — model changes, chunking changes, parser fixes — so the pipeline's most important property is that re-running is cheap and safe. Everything else follows from that.

1. Dispatch on content type; there is no universal chunker.

SourceExtractionChunking
PDFLayout-aware; strip repeated headers/footersBy section, never by page
ConfluenceAPI → markdown; drop nav/macrosBy heading, carry the heading path
CodeAST per languageOne function/class, with file path + imports
TicketsThread → turnsProblem + resolution together; strip signatures

Support tickets deserve a note: the useful retrieval unit is the problem paired with its resolution, not each message. Chunking by message produces thousands of "thanks, that worked" chunks that retrieve for everything and answer nothing.

2. Make every stage idempotent and incremental.

def ingest(doc):
    h = sha256(doc.raw_bytes).hexdigest()
    if store.doc_hash(doc.uri) == h:
        return "unchanged"                     # 95%+ of a typical re-run

    chunks = CHUNKERS[doc.content_type](extract(doc))
    texts  = [contextualise(c.text, doc.title, c.headings) for c in chunks]
    vecs   = embed_cached(texts)               # cache keyed by hash of the text

    store.replace_document_chunks(doc.uri, build(chunks, vecs, model, h))
    return "reindexed"

Three details carry the weight here. Deterministic chunk ids ({uri}#{index}) make re-runs produce no duplicates. replace_document_chunks deletes by document rather than upserting by chunk — otherwise a document that shrinks from 12 chunks to 8 leaves 4 stale chunks retrievable forever, which is a real and common bug. And the embedding cache is keyed by the hash of the exact embedded text, so a chunking tweak only re-embeds the chunks that actually changed.

3. Quality gates before anything is indexed, because bad extraction is silent:

reject or quarantine when:
  - chunk token count < 20                    (fragments: "Table 4.2", "|---|---|")
  - OCR mean confidence < threshold
  - >40% of a document's chunks are near-duplicates  (boilerplate not stripped)
  - extraction produced <10% of the expected character count  (parse failure)

4. Observability that catches parse failures: a chunk-length histogram per source type, mean pairwise cosine between random chunks (above ~0.5 means shared boilerplate), and a sample of chunks written to a reviewable file every run. I have found more ingestion bugs by reading twenty random chunks than by any metric.

5. Metadata for filtering and for lifecycle: source system, permissions/tenant, updated_at, model, and doc_hash on every chunk. Permissions must be on the chunk because retrieval filters on it — see filtering; model makes a partially-migrated index detectable.

6. Run it as a queue, not a batch job. Documents arrive continuously, so the pipeline is a worker consuming a change feed, with a periodic full sweep to catch deletions the feed missed. The full sweep is affordable precisely because of the content-hash skip.

What I would deliberately not build initially: semantic chunking (1–3 points on prose, zero on the structured majority of this corpus) and summary indexing (an LLM call per section, and it can lose information). Both are additions to make once the sweep in the next answer says chunking is still the bottleneck.

Senior: Retrieval quality is poor and the team wants to upgrade the embedding model. How would you decide whether that is the right move?

I would insist on locating the failure before spending on a fix, because "upgrade the model" is the most expensive hypothesis on the list and usually not the correct one. The diagnostic order runs cheapest first.

1. Establish whether retrieval is even the problem. Split the failures: is the right chunk absent from the retrieved set (retrieval), or present and ignored (generation)?

100 failing queries, manually labelled:
  relevant chunk not retrieved at all     61   ← retrieval
  retrieved but ranked below k            17   ← ranking → reranker
  retrieved in top-3, answer still wrong  22   ← generation, not retrieval

If most failures were in the third bucket, no embedding model would help at all.

2. Check whether the answer exists in any single chunk. This is the check that most often ends the discussion:

of the 61 retrieval failures:
  answer split across two chunks       28   ← CHUNKING
  answer in a chunk with no context
    ("The maximum is 5.")              14   ← CONTEXTUAL HEADERS
  answer in a table split from header   9   ← CHUNKING
  genuine semantic miss                10   ← the model

51 of 61 failures are chunking and context, and 10 are the model. An embedding upgrade addresses the smallest bucket at the highest cost — it means re-embedding the entire corpus, changing dimensions, rebuilding indexes, and re-validating everything.

3. Run the cheap sweep first, since a well-built pipeline makes it hours of work:

                                     recall@10
  baseline (1000 tok, 200 overlap)      0.62
  + size 400                            0.71
  + structural (by heading)             0.79
  + contextual headers                  0.86
  + small-to-big                        0.89
  + new embedding model                 0.91    ← +0.02, for a full re-index

+27 points from chunking and context; +2 from the model. That is the typical shape, and it is why chunking is the first parameter to sweep rather than the last.

4. Check the corpus for a shared-text problem, which is a single-line fix with an outsized effect:

mean pairwise cosine, random chunk pairs = 0.62      ← far too high
→ every page carries the same 60-word legal footer
→ strip it: 0.31, and recall@10 0.74 → 0.86

5. Then, if the model is still the bottleneck, upgrade it properly: evaluate candidates on our own judged query set rather than MTEB, check the dimension change against memory and cost, and run it as a shadow index with dual-write before any cutover — as with any store migration.

The general principle I would argue for: fix the data before the model. Chunking is reversible in hours, costs nothing but compute, and is where the failures overwhelmingly are. A model upgrade is a multi-day re-index that fixes the smallest bucket — worth doing eventually, worth doing last.

2 (easy): Implement recursive splitting and compare it to fixed-size.

def fixed_split(text, size=200):
    return [text[i:i+size] for i in range(0, len(text), size)]

def recursive_split(text, size=200, seps=("\n\n", "\n", ". ", " ", "")):
    if len(text) <= size or not seps:
        return [text]
    sep, rest = seps[0], seps[1:]
    parts = text.split(sep) if sep else list(text)
    out, buf = [], ""
    for p in parts:
        cand = (buf + sep + p) if buf else p
        if len(cand) <= size:
            buf = cand
        else:
            if buf:
                out.append(buf)
            out.extend(recursive_split(p, size, rest) if len(p) > size else [p])
            buf = ""
    if buf:
        out.append(buf)
    return [c for c in out if c.strip()]

The request body contains the event payload as JSON.

Delivery is retried up to 5 times with exponential backoff. After the fifth

    step = size - overlap
    return [text[i:i+size] for i in range(0, len(text), step) if text[i:i+size].strip()]

    E = m.encode(chunks, normalize_embeddings=True)

        top = np.argsort(-(E @ qv))[:k]
        hits += any(needle in chunks[i] for i in top)
    return hits / len(queries)

Solution 
import re, numpy as np
from dataclasses import dataclass, field
from sentence_transformers import SentenceTransformer
m = SentenceTransformer("all-MiniLM-L6-v2")

@dataclass
class Store:
    parents: dict = field(default_factory=dict)     # pid -> text
    children: list = field(default_factory=list)    # (text, pid)
    E: np.ndarray = None

    def build(self, doc_title, sections, child_size=120):
        for pid, (heading, body) in enumerate(sections):
            self.parents[pid] = f"{heading}\n{body}"
            for c in recursive_split(body, child_size):
                ctx = f"{doc_title} > {heading}\n\n{c}"     # contextualised for embedding
                self.children.append((ctx, c, pid))
        self.E = m.encode([c[0] for c in self.children], normalize_embeddings=True)

    def search_small(self, q, k=5):
        qv = m.encode([q], normalize_embeddings=True)[0]
        return [self.children[i] for i in np.argsort(-(self.E @ qv))[:k]]

    def search_big(self, q, k=3, fetch=9):
        qv = m.encode([q], normalize_embeddings=True)[0]
        seen, out = set(), []
        for i in np.argsort(-(self.E @ qv))[:fetch]:
            pid = self.children[i][2]
            if pid not in seen:                              # DEDUPE — the whole trick
                seen.add(pid)
                out.append(self.parents[pid])
            if len(out) == k:
                break
        return out

6 (hard): Build an idempotent, incremental ingestion pipeline and prove its properties.
Solution 
import hashlib, json
from dataclasses import dataclass

def sha(s): return hashlib.sha256(s.encode()).hexdigest()[:12]

class Index:
    """Stand-in for a vector store; tracks calls so we can assert on behaviour."""
    def __init__(self):
        self.chunks, self.doc_hash = {}, {}
        self.embed_calls = 0

    def replace_document(self, uri, chunks, h):
        for cid in [c for c, v in self.chunks.items() if v["uri"] == uri]:
            del self.chunks[cid]                      # DELETE by document first
        for c in chunks:
            self.chunks[c["id"]] = c
        self.doc_hash[uri] = h

EMBED_CACHE = {}

def embed_cached(texts, index):
    """Cache keyed by the hash of the exact embedded text."""
    out = []
    for t in texts:
        k = sha(t)
        if k not in EMBED_CACHE:
            EMBED_CACHE[k] = f"vec({k})"
            index.embed_calls += 1
        out.append(EMBED_CACHE[k])
    return out

def ingest(doc, index, chunk_size=200):
    h = sha(doc["text"])
    if index.doc_hash.get(doc["uri"]) == h:
        return "unchanged"

    chunks = recursive_split(doc["text"], chunk_size)
    texts  = [f"{doc['title']}\n\n{c}" for c in chunks]
    vecs   = embed_cached(texts, index)

    index.replace_document(doc["uri"], [
        {"id": f"{doc['uri']}#{i}", "uri": doc["uri"], "content": c,
         "vector": v, "doc_hash": h, "model": "v1"}
        for i, (c, v) in enumerate(zip(chunks, vecs))], h)
    return "reindexed"

Property 1 — idempotent: re-running changes nothing.

🎯 Key Takeaways

  • Chunking is the highest-leverage decision in RAG: every component downstream operates on chunks it did not choose, and a fact split across two chunks is retrievable by none of them.
  • Small chunks give precise vectors but lose context; large chunks keep context but dilute the vector, because an embedding averages everything in the chunk.
  • Dilution is real and measurable — the same answer buried in filler drops from cosine 0.74 to 0.29, and loses to chunks that do not contain it.
  • Chunk for retrieval, expand for generation: index small, return the parent. Small-to-big resolves the size tension instead of compromising between its halves.
  • Strategy ordering by value is structural > recursive > semantic > fixed — not by sophistication.
  • Structural chunking wins because the author already decided what belongs together; parse the format before reaching for an embedding-based splitter.
  • Semantic chunking costs an embedding per sentence and buys 1–3 points on unstructured prose, ~0 on documents that already have structure.
  • Never split PDFs by page, tables from their headers, or code with regex instead of an AST.
  • Overlap compensates for arbitrary boundaries — use 10–15% for recursive prose, and zero with structural chunking or small-to-big.
  • Overlap's hidden cost is that near-duplicate chunks compete for the same top-k slots, so the context window holds less distinct information than it appears to.
  • Contextual headers (document + heading path, prepended before embedding) are nearly free and typically worth more than any chunking-strategy upgrade.
  • Embed the contextualised text; store and display the raw text, so citations and LLM context carry no breadcrumbs.
  • Deduplicate parent ids in small-to-big, or several matching children return the same section repeatedly.
  • Make ingestion idempotent (deterministic chunk ids), incremental (content hash per document) and resumable (watermark) — because you will re-run it.
  • Delete by document rather than upserting by chunk, or a shrunken document leaves stale chunks retrievable forever.
  • Batch embedding calls and cache by hash of the embedded text — that is what makes iterating on chunking affordable.
  • Extraction is where the silent bugs are: multi-column PDFs, repeated footers, dropped speaker notes, OCR noise.
  • Mean pairwise cosine between random chunks above ~0.5 means shared boilerplate is flattening the space; stripping it is often the largest single recall win.
  • Log a chunk-length histogram and read samples — twenty random chunks find more ingestion bugs than any metric.
  • When retrieval is poor, sweep chunking before upgrading the embedding model: the failures are usually split answers and missing context, not semantic misses.
