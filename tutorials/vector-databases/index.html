What a Vector Database Is For Foundations

What you'll master: the specific problem vector search solves that a WHERE clause cannot, why "semantic search" is a geometric operation rather than a linguistic one, the honest trade-off that makes approximate search acceptable, where a vector database fits in a RAG system and which parts of RAG have nothing to do with vectors at all, when you should not reach for one, and the vocabulary the rest of this track depends on. No prerequisites beyond basic SQL familiarity — Database Concepts is useful background but not required.

Part 1 — The Query You Cannot Write in SQL

Relational databases answer questions about values. Given exact values or ranges, they find rows. That covers an enormous amount of software, and it completely fails at one specific kind of question.

-- Works perfectly: exact match
SELECT * FROM articles WHERE title = 'Postgres replication lag';

-- Works: substring match
SELECT * FROM articles WHERE title ILIKE '%replication%';

-- Cannot be written: "articles ABOUT the same thing as this one"
SELECT * FROM articles WHERE title MEANS_ROUGHLY 'my standby is falling behind';

The third query is what users actually want. A search for "my standby is falling behind" should find "Postgres replication lag" even though the two strings share not one word in common. Keyword search cannot do it, because the connection is in the meaning, not the characters.

Query typeMatches onFinds "replication lag" from "standby falling behind"?
= / INExact valueNo
LIKE / ILIKESubstringNo
Full-text search (BM25)Shared tokens, weighted by rarityNo — zero shared tokens
Vector similarityProximity in a learned semantic spaceYes

The move that makes this possible is turning text into numbers in a way that preserves meaning. An embedding model maps a piece of text to a list of floating-point numbers — a vector — such that texts with similar meanings land close together:

"Postgres replication lag"       → [ 0.021, -0.184,  0.093, ...,  0.045]   (1536 numbers)
"my standby is falling behind"   → [ 0.019, -0.177,  0.101, ...,  0.041]   ← very close
"chocolate chip cookie recipe"   → [-0.203,  0.318, -0.257, ..., -0.192]   ← far away

Once text is a point in space, "find things that mean the same" becomes "find the nearest points" — a geometry problem with well-studied algorithms. That substitution is the entire idea, and everything else in this track is engineering consequences of it.

🔑 A vector database is a database whose primary index is a distance function. That is the whole definition. It stores vectors alongside metadata and answers one core query well: "given this vector, return the k stored vectors closest to it." Everything a vector database adds beyond that — filtering, hybrid search, persistence, replication — exists to make that one query usable in a real application. Understanding it this way makes the rest of the track predictable rather than a list of product features.

Part 2 — Nearest Neighbours, Exactly and Approximately

The naive way to find the nearest vectors is to compare the query against every stored vector. That is exact k-nearest-neighbour search, and it is genuinely correct — it just does not scale:

# Exact kNN, conceptually
def knn(query, vectors, k):
    scored = [(distance(query, v), i) for i, v in enumerate(vectors)]   # O(n·d)
    scored.sort()
    return scored[:k]
Corpus sizeComparisons per query (1536-dim)Rough exact-search latency
10,00015 million multiply-adds~5 ms — fine, just scan
1,000,0001.5 billion~500 ms — too slow for interactive use
100,000,000150 billion~50 s — completely impractical

So production systems use approximate nearest neighbour (ANN) search: index structures that examine a small fraction of the corpus and return almost the right answer, thousands of times faster. The quality of the approximation is measured as recall:

recall@10  =  (how many of the true top-10 the index returned)  /  10

# An index returning 9 of the true top 10 has recall@10 = 0.9

This is the central bargain of the entire field, and it is worth being comfortable with it early: you give up a small, measurable amount of correctness in exchange for a large, measurable amount of speed. Unlike most database trade-offs, this one is a dial you set deliberately — Tuning Recall vs Latency is entirely about where to set it.

The reason 95% recall is usually acceptable is worth stating plainly: the embedding itself is an approximation of meaning. If your embedding model's notion of "similar" is imperfect — and it always is — then the difference between the true 10th-nearest vector and the 12th-nearest is usually noise. Insisting on exact search over approximate embeddings is precision in the wrong place.

Part 3 — Anatomy of a Vector Database

Every vector store, from a 200-line Python script to a distributed cluster, has the same four parts:

   ┌─────────────────────────────────────────────────────┐
   │  1. STORAGE     vectors + their metadata + payload  │
   │  2. INDEX       an ANN structure over the vectors   │
   │  3. QUERY       k-NN search, with metadata filters  │
   │  4. LIFECYCLE   insert, update, delete, rebuild     │
   └─────────────────────────────────────────────────────┘

# A record in a vector store is not just a vector
{
  "id":       "doc-4821-chunk-3",
  "vector":   [0.021, -0.184, ..., 0.045],      # the searchable part
  "metadata": {"source": "runbook.md", "team": "platform", "updated": "2026-07-14"},
  "text":     "If the standby falls behind, check wal_sender_timeout first..."
}

The metadata matters more than newcomers expect. Almost no real query is "find similar text" — it is "find similar text that this user is allowed to see, from the current document version, in this language". Combining a distance search with predicate filtering is harder than it looks, and it is where vector stores differ most.

OperationRelational DBVector DB
Primary queryMatch values, join relationsRank by distance to a query vector
Index typeB-tree, hashHNSW graph, IVF lists, quantised codes
ResultThe rows that match — exact setTop-k ranked by similarity — approximate, always returns something
DeletesImmediateOften tombstoned; graph indexes degrade until rebuilt
Correctness measureRight or wrongRecall — a percentage you choose

Note the fourth row especially. A vector query never returns "no results" — ask for the top 10 and you get 10, however irrelevant. There is no such thing as a non-match, only a worse match. Any system built on vector search needs an explicit relevance threshold, or it will confidently serve nonsense when the corpus contains no answer.

Part 4 — Where This Fits: RAG

The dominant use of vector databases today is retrieval-augmented generation: giving a language model relevant private context at query time instead of relying on what it memorised during training.

  INGESTION (offline, runs when documents change)
  ─────────────────────────────────────────────────
  documents → chunk → embed → store (vector + metadata + text)

  QUERY (online, per user request)
  ─────────────────────────────────────────────────
  question → embed → ANN search → top-k chunks
                                       │
                                    rerank  (optional, usually worth it)
                                       │
                          prompt = instructions + chunks + question
                                       │
                                      LLM → answer + citations
StageDeterminesCovered in
ChunkingWhether an answer can be retrieved at allChunking & Ingestion
EmbeddingWhat "similar" means for your dataEmbeddings & Vector Space
IndexingLatency and recall at scaleHNSW, IVF & PQ
Retrieval + rerankPrecision of what reaches the modelRetrieval Pipelines
GenerationFaithfulness to the retrieved contextPrompt design — outside this track

Most RAG quality problems are retrieval problems, and most retrieval problems are chunking problems. Teams reliably reach for a better model or a bigger context window when the actual failure is that the answer was split across two chunks and neither one alone matched the question. This track spends four lessons on the retrieval half for exactly that reason.

❌ "Our RAG answers are wrong, let's upgrade to a bigger LLM." If the retrieved chunks do not contain the answer, no model can produce it — it will either say it does not know, or hallucinate something plausible from adjacent context. Upgrading the generator is expensive and changes nothing.

✅ Measure retrieval separately from generation. Take the failing questions, look at the top-k chunks actually retrieved, and ask whether a human could answer from them. If no — it is a retrieval bug: chunking, embedding choice, filtering, or missing reranking. If yes — then it is a prompt or model problem. Evaluating Retrieval makes this a metric rather than an opinion.

Part 5 — When Not to Use a Vector Database

Vector search is genuinely the wrong tool more often than the current enthusiasm suggests. Recognising that is a senior skill.

SituationBetter toolWhy
Users search by exact identifiers, SKUs, error codesB-tree indexSemantic similarity actively hurts — you want exact
Under ~10k documentsBrute-force scan, or pgvector without an indexExact search is fast enough; no index to tune or rebuild
Queries are keyword-shaped ("invoice 4821")BM25 / full-text searchLexical matching beats embeddings on rare exact tokens
The corpus fits in the model's context windowSend it allRetrieval only adds a failure mode
The answer requires aggregation ("how many tickets last month?")SQLRetrieval finds passages; it cannot count
Strict, provable access control per documentFilter first in a real databasePost-filtering ANN results can silently drop or leak

The last row deserves emphasis. It is the failure mode that turns into a security incident rather than a quality complaint, and it comes directly from the "always returns something" property from Part 3. Systems that retrieve first and filter afterwards can return fewer than k results, or — with a careless implementation — the wrong tenant's data.

Notice too that several rows above point at keyword search. Vector and lexical search fail in different, complementary ways: embeddings are strong on paraphrase and weak on rare exact tokens like product codes; BM25 is the exact inverse. That is why serious production systems run both and fuse the results, which is the subject of Metadata Filtering & Hybrid Search.

These terms recur in every remaining lesson. Getting them precise now avoids confusion later:

One clarification that saves confusion throughout: "distance" and "similarity" run in opposite directions. Cosine similarity of 1.0 means identical; cosine distance of 0.0 means identical. Different libraries return different ones, and mixing them up produces a search that confidently returns the least relevant results — a bug that looks like a broken embedding model. Similarity Metrics covers this properly.

Interview Questions

Beginner: What is a vector database and what problem does it solve?

It is a database whose primary index is a distance function. It stores vectors — fixed-length lists of numbers produced by an embedding model — alongside metadata, and answers one core query efficiently: "given this vector, return the k stored vectors closest to it."

The problem it solves is semantic search. A relational database matches values: exact equality, ranges, substrings. It cannot answer "find documents that mean roughly the same thing as this", because meaning is not in the characters:

Query:  "my standby is falling behind"
Target: "Postgres replication lag"
Shared words: zero — keyword search finds nothing

An embedding model maps both to points in a high-dimensional space such that semantically similar texts land near each other. "Find similar meaning" then becomes "find nearby points", which is a geometry problem with efficient algorithms.

The dominant application today is retrieval-augmented generation: retrieving relevant private context so a language model can answer questions about data it was never trained on.

Worth adding: it is not a replacement for a relational database. Most systems use both — the vector index for meaning-based retrieval, the relational store for the actual records, permissions and aggregates.

Beginner: What is the difference between exact and approximate nearest neighbour search?

Exact kNN compares the query against every stored vector and returns the genuinely closest k. It is correct by construction and costs O(n·d) — the corpus size times the dimensionality.

1M vectors × 1536 dimensions = 1.5 billion multiply-adds per query ≈ 500 ms

Approximate (ANN) search uses an index — a navigable graph, or clusters — to examine only a small fraction of the corpus. It is typically 100–1000× faster and returns almost the right answer.

Quality is measured as recall@k: the fraction of the true top-k that the index actually returned. Recall of 0.95 at k=10 means 9.5 of the true top 10 came back on average.

Why approximate is acceptable is the part worth articulating: the embedding is itself an approximation of meaning. If the model's notion of similarity is imperfect — and it always is — the difference between the true 10th result and the 12th is usually noise. Demanding exactness over approximate inputs is precision in the wrong place.

That said, exact search is the right choice below roughly 10,000 vectors, where a brute-force scan takes single-digit milliseconds and you avoid building, tuning and rebuilding an index entirely.

Mid: Walk through the architecture of a RAG system.

Two pipelines, one offline and one online.

Ingestion (offline, when documents change):

  1. Chunk documents into retrievable units — this decision determines whether an answer can be found at all, and it is where most RAG quality is won or lost.
  2. Embed each chunk with the embedding model.
  3. Store the vector, the source text, and metadata (source, tenant, version, timestamp).

Query (online, per request):

  1. Embed the question with the same model — a different model produces an incompatible space.
  2. ANN search for the top-k chunks, with metadata filters applied for tenancy and permissions.
  3. Rerank the candidates with a cross-encoder — usually retrieve ~50, rerank to ~5.
  4. Assemble the prompt from instructions, retrieved chunks, and the question.
  5. Generate, with citations back to the source chunks.

The two design points that matter most are chunking and reranking. Chunking because a chunk that splits an answer in half means neither piece matches the question. Reranking because embedding similarity is a coarse signal — a cross-encoder that sees the question and passage together is substantially more accurate, and it only has to score 50 candidates rather than a million.

I would also insist on evaluating the two halves separately. Retrieval metrics (recall@k, MRR) and generation metrics (faithfulness, correctness) answer different questions, and conflating them means every failure looks like a model problem.

Mid: When would you advise against using a vector database?

More often than the current enthusiasm suggests. The specific cases:

1. The queries are exact-match. Users searching for order IDs, SKUs, or error codes want exactly that string. Semantic similarity actively hurts — it returns things that are like the code rather than the code. A B-tree index is correct and faster.

2. The corpus is small. Under about 10,000 vectors, a brute-force scan is single-digit milliseconds. Adding a dedicated store means an index to build, tune, monitor and rebuild — real operational cost for no latency benefit. pgvector without an index, in the database you already run, is the right answer.

3. Queries are keyword-shaped. Embeddings are notably weak on rare exact tokens; BM25 is strong there. If the workload is "invoice 4821", lexical search wins outright.

4. The whole corpus fits in the context window. Retrieval then only adds a failure mode — the risk of not retrieving the right passage. Send everything.

5. The question requires aggregation. "How many tickets did we close last month?" is a SQL question. Retrieval finds passages; it cannot count, and a language model asked to count retrieved chunks will confidently get it wrong.

6. Access control must be provable. Post-filtering ANN results can return fewer than k and, with a careless implementation, leak across tenants. That is a security incident rather than a quality complaint, so it needs filtering during search or hard partitioning.

The general principle: a vector database is the right tool when the relation you need is semantic similarity. When the relation is equality, containment, or aggregation, existing tools are better — and often the honest answer is hybrid search rather than either alone.

Senior: A team reports their RAG system "hallucinates". How do you diagnose it?

"Hallucination" is a symptom with several distinct causes, and they have unrelated fixes. I would decompose before touching anything.

1. Split retrieval from generation. For each failing question, look at the chunks actually retrieved and ask: could a competent human answer correctly from only these? That single question separates the two halves:

  • No → a retrieval failure. The model is filling a gap, which is what it does when context is insufficient.
  • Yes → a generation failure. The context was there and the model ignored or misread it.

In my experience the great majority land in the first category, which is why upgrading the model so rarely helps.

2. If retrieval failed, isolate which stage:

CheckIndicates
Is the answer present in the corpus at all?An ingestion or coverage gap — no retrieval fix exists
Is it present but split across chunk boundaries?A chunking problem — the commonest single cause
Does exact search find it when ANN does not?Recall is too low — tune the index
Does a metadata filter exclude it?Over-restrictive filtering, or stale version metadata
Is it retrieved but ranked 30th?Ranking, not retrieval — add a reranker
Is the query keyword-shaped?Embedding weakness — add BM25 and fuse

3. If generation failed, the usual causes are a prompt that does not instruct the model to abstain, context ordering that buries the relevant passage in the middle, contradictory retrieved chunks (often stale and current versions of the same document), or simply too much context diluting the signal.

4. Build the measurement before the fix. A labelled set of question/expected-source pairs turns this from anecdote into recall@k and MRR that move when you change something. Without it, every change is a guess and nobody can tell whether the system improved.

5. Then address the highest-frequency cause — usually chunking, then reranking, then hybrid search. And regardless of cause, require citations and enforce an abstention path: a system that says "I don't have that information" when retrieval is weak is dramatically more useful than one that always answers.

Senior: How would you decide between pgvector and a dedicated vector database?

I would start from the position that pgvector is the default and a dedicated store must justify itself, because the operational cost of a second stateful system is real and permanent.

What pgvector gives you for free: one database to back up, monitor, secure and staff; genuine transactional consistency between vectors and the rows they describe; and — the underrated one — real SQL joins and filters evaluated by a mature query planner. "Find similar documents where tenant_id = X and status = 'published' and the author is in this team" is one query, correctly filtered, with no post-filtering gymnastics.

What would push me to a dedicated store:

SignalWhy it matters
Beyond ~10–50M vectorspgvector's index build and memory footprint become the operational problem
Need for quantisation to fit memoryDedicated stores implement PQ/binary quantisation far more thoroughly
High write throughput with live index updatesIndex maintenance competes with OLTP work on the same instance
Independent scaling of search from transactional loadSearch traffic should not affect the primary database
Built-in hybrid search and rerankingOtherwise you build the fusion layer yourself

The decision I would actually make depends on scale and on team size. At a few million vectors with a team already running Postgres, pgvector wins clearly — the second system costs more than it saves. At hundreds of millions of vectors with a dedicated search workload, a purpose-built store wins just as clearly.

The middle ground is where judgement matters, and I would weight two things heavily: who operates it at 3am, and whether the filtering requirements are complex. Complex, security-relevant filters are much safer in a database with a real query planner than in a vector store where filtering is bolted onto ANN traversal.

I would also plan the migration path either way. Keeping the source text and metadata in Postgres and treating the vector index as a rebuildable derived artefact means switching stores later is a re-index, not a data migration — and since re-embedding is required whenever the model changes anyway, that pipeline has to exist regardless.

2 (easy): Measure how exact search scales, and find where it stops being viable.
Solution 
$ python3 - <<'EOF'
import numpy as np, time
rng = np.random.default_rng(42)
DIM = 1536

for n in [1_000, 10_000, 100_000, 500_000]:
    corpus = rng.standard_normal((n, DIM), dtype=np.float32)
    corpus /= np.linalg.norm(corpus, axis=1, keepdims=True)
    q = rng.standard_normal(DIM).astype(np.float32); q /= np.linalg.norm(q)

    t0 = time.perf_counter()
    for _ in range(5):
        scores = corpus @ q                    # every vector, every query
        top10 = np.argpartition(-scores, 10)[:10]
    ms = (time.perf_counter() - t0) / 5 * 1000
    print(f"n={n:>7,}  {ms:7.1f} ms/query   {n*DIM*4/1e6:6.0f} MB corpus")

3 (medium): Build a minimal vector store with metadata filtering, and find its flaw.
Solution 
$ python3 - <<'EOF'
import numpy as np
from sentence_transformers import SentenceTransformer

class TinyVectorStore:
    def __init__(self, model='all-MiniLM-L6-v2'):
        self.m = SentenceTransformer(model)
        self.vectors, self.records = [], []

    def add(self, text, **metadata):
        v = self.m.encode([text], normalize_embeddings=True)[0]
        self.vectors.append(v)
        self.records.append({"text": text, **metadata})

    def search(self, query, k=3, **filters):
        V = np.vstack(self.vectors)
        q = self.m.encode([query], normalize_embeddings=True)[0]
        scores = V @ q                                    # cosine, since normalised
        order = np.argsort(-scores)
        out = []
        for i in order:                                   # filter DURING the scan
            r = self.records[i]
            if all(r.get(f) == v for f, v in filters.items()):
                out.append((float(scores[i]), r))
                if len(out) == k: break
        return out

s = TinyVectorStore()
s.add("Postgres replication lag runbook", team="platform", public=True)
s.add("Internal salary bands 2026",       team="hr",       public=False)
s.add("Standby promotion procedure",      team="platform", public=True)
s.add("Kubernetes eviction policy",       team="platform", public=True)

for score, r in s.search("my replica is behind", k=2, public=True):
    print(f"{score:.3f}  {r['text']}  [{r['team']}]")
EOF
0.531  Postgres replication lag runbook  [platform]
0.478  Standby promotion procedure  [platform]

Working semantic search with filtering in about 25 lines. This is a real vector database, just a slow one.

Now demonstrate the "always returns something" flaw:

$ python3 -c "
# ... same store ...

    print(f'{score:.3f}  {r[\"text\"]}')
"

0.043  Postgres replication lag runbook

Nothing in the corpus is remotely about bread, and it confidently returns two results. A vector search never says 'no match'.

The fix is an explicit threshold:

    def search(self, query, k=3, min_score=0.25, **filters):
        ...
            if all(...) and float(scores[i]) >= min_score:
                out.append(...)

results = s.search("how do I bake sourdough bread", min_score=0.25)
print(results or "No relevant results found")
No relevant results found

Choosing the threshold requires data, not intuition — score distributions differ per model and per corpus:

$ python3 -c "
import numpy as np
# score every known-relevant pair and every known-irrelevant pair
relevant   = [0.531, 0.478, 0.612, 0.445]
irrelevant = [0.081, 0.043, 0.152, 0.098]
print('relevant   min:', min(relevant))
print('irrelevant max:', max(irrelevant))
print('threshold  →   ', (min(relevant) + max(irrelevant)) / 2)
"
relevant   min: 0.445
irrelevant max: 0.152
threshold  →    0.2985

Note also that this implementation filters during the scan, which is correct. Filtering after taking the top-k would silently return fewer results — the post-filtering trap that becomes a real bug at scale and a security issue with per-tenant filters.

4 (medium): Show where embeddings beat keywords — and where they lose.
Solution

from rank_bm25 import BM25Okapi
from sentence_transformers import SentenceTransformer
import numpy as np

docs = [
  "Resolving replication delay on a hot standby server",
  "Error PG-4821: could not connect to WAL sender",
  "Guide to baking sourdough bread at home",
  "Increasing max_wal_senders in postgresql.conf",
  "Diagnosing slow queries with EXPLAIN ANALYZE",

D = m.encode(docs, normalize_embeddings=True)

def compare(q):
    print(f"\n=== {q!r}")
    b = bm25.get_scores(q.lower().split())
    v = D @ m.encode([q], normalize_embeddings=True)[0]
    print(f"  BM25   → {docs[int(np.argmax(b))]}  (score {max(b):.2f})")
    print(f"  Vector → {docs[int(np.argmax(v))]}  (score {max(v):.2f})")

compare("my replica is lagging behind the primary")   # paraphrase
compare("PG-4821")                                     # rare exact token
EOF

=== 'my replica is lagging behind the primary'
  BM25   → Guide to baking sourdough bread at home  (score 0.00)
  Vector → Resolving replication delay on a hot standby server  (score 0.58)

=== 'PG-4821'
  BM25   → Error PG-4821: could not connect to WAL sender  (score 2.31)
  Vector → Diagnosing slow queries with EXPLAIN ANALYZE  (score 0.14)

Each wins decisively where the other fails. BM25 scored zero on the paraphrase and picked an arbitrary document; the embedding model completely missed an exact error code that appears verbatim in the corpus.

Why the embedding misses the code: "PG-4821" is a rare token the model never learned a meaningful representation for. It embeds to something near the centre of the space, close to everything and nothing.

      float(m.encode(['PG-4821'], normalize_embeddings=True)[0] @

Two entirely unrelated codes score 0.78 similarity — the model sees "short alphanumeric identifier" and nothing more. This is precisely why product catalogues and error-code search cannot be vector-only.

The conclusion is hybrid search, covered fully in Metadata Filtering & Hybrid Search: run both retrievers and fuse the rankings, so paraphrase queries and exact-token queries each get answered by the retriever that handles them well.

5 (hard): Build an end-to-end RAG pipeline and break it deliberately.
Solution 
$ python3 - <<'EOF'
from sentence_transformers import SentenceTransformer
import numpy as np, textwrap

DOC = """
Our Postgres cluster runs one primary and two standbys. Streaming replication
is asynchronous by default. If a standby falls behind, the usual cause is a
long-running query on the standby holding back WAL replay.
The recommended fix is to set max_standby_streaming_delay to 30s, which allows
the standby to cancel conflicting queries rather than delaying replay
indefinitely. Monitor lag with pg_stat_replication.replay_lag.
Backups run nightly at 02:00 UTC via pgBackRest to S3 with 30-day retention.
"""

def chunk(text, size, overlap=0):
    words, out, i = text.split(), [], 0
    while i < len(words):
        out.append(" ".join(words[i:i+size]))
        i += size - overlap
    return out

m = SentenceTransformer('all-MiniLM-L6-v2')

def rag(question, chunks, k=2):
    C = m.encode(chunks, normalize_embeddings=True)
    q = m.encode([question], normalize_embeddings=True)[0]
    idx = np.argsort(-(C @ q))[:k]
    return [(float((C @ q)[i]), chunks[i]) for i in idx]

Q = "What should max_standby_streaming_delay be set to?"

print("=== GOOD chunking (40 words, 10 overlap) ===")
for s, c in rag(Q, chunk(DOC, 40, 10)):
    print(f"{s:.3f} {textwrap.shorten(c, 90)}")
EOF

=== GOOD chunking (40 words, 10 overlap) ===
0.641 The recommended fix is to set max_standby_streaming_delay to 30s, which allows [...]
0.402 Our Postgres cluster runs one primary and two standbys. Streaming [...]

The answer ("30s") is in the top chunk. The pipeline works.

Now break it with chunks that are too small:

$ python3 -c "

for s, c in rag(Q, chunk(DOC, 8, 0), k=3):
    print(f'{s:.3f} {c}')

0.518 The recommended fix is to set max_standby_streaming_delay to

The setting name and its value are now in different chunks. The top result says what to set but not to what. An LLM given only that chunk will either say it does not know, or invent a plausible value — which is reported as "hallucination" when the actual bug is chunk size.

Break it the other way — chunks too large:

Score dropped from 0.641 to 0.361. The relevant sentence is diluted by unrelated content about backups, so the whole chunk embeds to something less similar to the question. At scale this chunk loses to genuinely less relevant but tighter ones.

Demonstrate the retrieval-vs-generation split:

$ python3 - <<'EOF'
def diagnose(question, retrieved, expected_fact):
    present = any(expected_fact in c for _, c in retrieved)
    print(f"Q: {question}")
    print(f"  fact in retrieved context: {present}")
    print(f"  → {'GENERATION problem' if present else 'RETRIEVAL problem'}")

diagnose("What should max_standby_streaming_delay be?",
         rag(Q, chunk(DOC, 8, 0), k=3), "30s")
diagnose("What should max_standby_streaming_delay be?",
         rag(Q, chunk(DOC, 40, 10), k=2), "30s")
EOF
Q: What should max_standby_streaming_delay be?
  fact in retrieved context: False
  → RETRIEVAL problem
Q: What should max_standby_streaming_delay be?
  fact in retrieved context: True
  → GENERATION problem

This check is the single most valuable diagnostic in RAG. Automating it over a labelled question set turns "the system hallucinates" into a number that tells you which half to fix — and, in the great majority of cases, points at chunking.

The fix here is overlap: chunks that overlap by 20–25% mean a fact spanning a boundary still appears intact in one chunk. Chunking & Ingestion covers the strategies properly.

6 (hard): Decide, with evidence, whether a given workload needs a vector database at all.
Solution

The scenario: an internal support tool. 40,000 knowledge-base articles, ~200 searches per minute at peak, queries a mix of natural-language questions and exact error codes, with per-team access control. Someone has proposed a managed vector database.

1. Measure whether exact search is actually too slow:

$ python3 - <<'EOF'
import numpy as np, time
rng = np.random.default_rng(1)
n, DIM = 40_000, 768                      # a smaller model is plausible here
C = rng.standard_normal((n, DIM), dtype=np.float32)
C /= np.linalg.norm(C, axis=1, keepdims=True)
t0 = time.perf_counter()
for _ in range(100):
    q = rng.standard_normal(DIM).astype(np.float32); q /= np.linalg.norm(q)
    _ = np.argpartition(-(C @ q), 10)[:10]
el = time.perf_counter() - t0
print(f"{el/100*1000:.1f} ms/query, {100/el:.0f} QPS single-core, corpus {n*DIM*4/1e6:.0f} MB")
EOF
19.4 ms/query, 52 QPS single-core, corpus 123 MB

19 ms per query and 52 QPS on one core. Peak demand is 200/min = 3.3 QPS. Exact search has roughly 15× headroom on a single core. No ANN index is needed at all.

2. Check the query mix, since it determines whether vectors alone even work:

$ python3 - <<'EOF'
import re
sample = ["how do I reset a user's MFA", "ERR-3021", "printer offline in HQ",
          "TICKET-88421 status", "vpn keeps disconnecting on mac", "SKU-99120 return policy"]
code = re.compile(r'\b[A-Z]{2,}[-_]?\d{3,}\b')
codes = [q for q in sample if code.search(q)]
print(f"{len(codes)}/{len(sample)} = {len(codes)/len(sample):.0%} contain exact identifiers")
EOF
3/6 = 50% contain exact identifiers

Half the queries are exact-token lookups where embeddings are actively bad (exercise 4 showed two unrelated codes scoring 0.78 similarity). A vector-only system would regress those queries.

3. Consider the access-control requirement. Per-team filtering with 40k documents in a relational store is an indexed WHERE clause evaluated by a query planner. In a separate vector store it is either pre-filtering (which the store must support well) or post-filtering (which can return fewer than k results and, done carelessly, leak across teams).

4. The recommendation, with the reasoning:

OptionVerdict
Managed vector DBNo — a second stateful system, permanent ops cost, no latency benefit at this scale, and it regresses 50% of queries
pgvector, no ANN index + Postgres FTS, fusedYes — exact vector search is fast enough, FTS handles the codes, filters and permissions stay in SQL
Keyword search onlyNo — loses the paraphrase queries that motivated the project

5. Define the trigger for revisiting, so the decision is not permanent:

Add an HNSW index when:   p95 vector-search latency > 100 ms
Move to a dedicated store when:  corpus > ~10M vectors,
                                 OR search load affects OLTP p99,
                                 OR memory for the index exceeds the DB instance
Instrument now:  per-query latency histogram, corpus size, index memory

The general lesson: the question is never "should we use a vector database" but "what relation does this query need, and at what scale". Here it needs both semantic and lexical relations at a scale where the boring answer is comfortably sufficient — and the boring answer has a real migration path if that changes, because the vector index is a derived artefact that can be rebuilt.

🎯 Key Takeaways

  • A vector database is a database whose primary index is a distance function — it answers "find the k stored vectors closest to this one" and everything else exists to make that usable.
  • Embeddings turn meaning into geometry, so semantic search becomes nearest-neighbour search — a well-studied algorithmic problem.
  • Exact kNN is O(n·d): fine under ~10k vectors, ~100 ms at 100k, impractical beyond that, which is what forces approximate search.
  • ANN trades a measurable amount of recall for a large speedup, and recall@k is the dial you set deliberately.
  • Approximation is acceptable because the embedding is itself an approximation of meaning — exactness over approximate inputs is precision in the wrong place.
  • A stored record is a vector plus metadata plus source text; the metadata is what makes real queries (tenant, version, permissions) possible.
  • Vector search never returns "no match" — ask for k and you get k, so an explicit similarity threshold is mandatory.
  • RAG = chunk → embed → store, then embed query → search → rerank → prompt → generate; the retrieval half is where most quality is won or lost.
  • Most "hallucination" reports are retrieval failures, and most retrieval failures are chunking failures — diagnose by asking whether a human could answer from the retrieved chunks.
  • Embeddings are weak on rare exact tokens like SKUs and error codes, where BM25 is strong — the two fail in complementary ways, which is the argument for hybrid search.
  • Filtering after retrieval can return fewer than k results and leak across tenants; filter during search or partition.
  • Vectors from different embedding models live in incompatible spaces — changing models means re-embedding the entire corpus.
  • pgvector is the sensible default; a dedicated store must justify a second stateful system with scale, quantisation needs, or workload isolation.
