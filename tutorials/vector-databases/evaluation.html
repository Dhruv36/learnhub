Evaluating Retrieval RAG in Production

What you'll master: how to build a judged evaluation set that is worth trusting, including how many queries you actually need and how to bootstrap one when you have none; the retrieval metrics — recall@k, precision@k, MRR, nDCG — and specifically which one to optimise for RAG and why; how to evaluate generation separately from retrieval, and how to use an LLM as a judge without fooling yourself; the statistics that decide whether a 2-point improvement is real; and how to wire all of it into CI so regressions are caught before users find them. Prerequisites: Retrieval Pipelines & Reranking, Chunking & Ingestion.

Part 1 — Why Evaluation Is the Bottleneck

Every previous lesson ended with a number: chunk size 400 beats 1000, hybrid beats dense, reranking moves nDCG from 0.71 to 0.86. None of those numbers exist without an evaluation set, and a team without one is not tuning a RAG system — it is guessing, then defending the guess.

The failure is specific and extremely common:

Week 1:  "Retrieval seems bad."      → switch embedding model
Week 2:  "Still seems bad."          → add a reranker
Week 3:  "Better? Hard to say."      → tune chunk size
Week 4:  "Someone says it regressed" → revert something, unsure what

Nothing in that sequence is measurable, so nothing in it is reversible. Each change is evaluated by vibes on whichever five queries someone remembered, and the five queries are different every week.

Without an eval setWith one
"This feels better""recall@10: 0.79 → 0.86, n=500, p=0.003"
Regressions found by usersRegressions found by CI
Every change is permanent (nobody dares revert)Changes are reversible because impact is known
Tuning order set by fashionTuning order set by measured contribution
🔑 Build the evaluation set before the optimisation, not after. It feels like a detour — you have a working pipeline and no metrics, and writing 200 judged queries is a day of unglamorous work. But every hour of tuning without it is unattributable, and the cheapest moment to build it is before you have made ten changes you cannot untangle. A day spent here pays for itself in the first week.

Part 2 — Building an Evaluation Set

An evaluation set is a list of queries, each with the chunk ids that should be retrieved, and ideally a reference answer. The quality of everything downstream depends on this being representative.

{
  "query_id": "q_0142",
  "query": "how long is an old API key valid after rotation?",
  "relevant_chunk_ids": ["docs/api-keys#3"],       # judged, not guessed
  "reference_answer": "One hour.",
  "query_class": "exact-lookup",
  "source": "production_log"
}

Sample queries from production logs, not from imagination. Invented queries are systematically better-formed than real ones — real users write "key rotate how long", not "how long is an old API key valid after rotation?" — and a system tuned on well-formed queries under-performs on the actual distribution.

Source of queriesQualityNotes
Production query logsBestThe real distribution, including malformed ones
Support tickets / search logsVery goodReal questions, often with a known answer
LLM-generated from chunksUsable to bootstrapBiased toward the chunk's own phrasing
Written by the teamWeakestReflects what the team expects, not what users ask

When you have no logs, bootstrap with an LLM — it is a legitimate starting point provided you know its bias:

GEN = """Read the passage and write 3 questions a user might ask that this
passage answers. Vary the phrasing: one natural-language question, one
terse keyword-style query, one that uses different words than the passage.
Output one per line, no numbering.

Passage:
{chunk}"""

def bootstrap(chunks, llm, n=200):
    out = []
    for c in random.sample(chunks, n):
        for q in llm(GEN.format(chunk=c.content)).strip().split("\n"):
            out.append({"query": q.strip(), "relevant_chunk_ids": [c.id],
                        "source": "llm_generated"})
    return out

The bias is that generated queries share vocabulary with their source chunk, which makes retrieval look easier than it is — a lexical retriever scores unrealistically well, and the whole set reports inflated numbers. Asking explicitly for a paraphrase variant mitigates it; replacing generated queries with real ones as logs accumulate fixes it.

The other trap is single-chunk labelling. Bootstrapping marks exactly one chunk relevant — the one the query came from — but other chunks may answer equally well. That undercounts recall systematically:

query: "how many webhook retries?"
labelled relevant:  ["docs/webhooks#3"]
actually relevant:  ["docs/webhooks#3", "docs/webhooks#4", "faq/retries#1"]

→ a system that retrieves faq/retries#1 is scored as WRONG

The cheap fix is pooling, borrowed from TREC: run several different systems, take the union of their top-10, and judge that pool. Anything no system retrieved goes unjudged — an accepted limitation — but everything a real system might return has a label.

def build_pool(query, systems, k=10):
    pool = set()
    for s in systems:                    # dense, bm25, hybrid, hybrid+rerank
        pool.update(s.search(query, k))
    return sorted(pool)                  # judge these, once

How many queries? Enough that the confidence interval is narrower than the differences you care about:

detecting a 5-point difference in recall@10 (0.80 vs 0.85), 80% power:

   n =  50 queries  → 95% CI ≈ ±0.11   cannot distinguish 0.80 from 0.85
   n = 100          → ±0.08            still cannot
   n = 200          → ±0.055           marginal
   n = 500          → ±0.035           ← usable
   n = 1000         → ±0.025           comfortable

200 is the practical floor and 500 is the target for a set you will use to make decisions. Below 200, a 3-point "improvement" is indistinguishable from noise, which is how teams ship regressions believing they shipped gains.

Stratify by query class, because the aggregate hides everything that matters — as hybrid search demonstrated, where all the gain came from two classes and one class regressed:

class distribution, weighted to match production traffic:
  paraphrase / conceptual   52%
  exact identifier          18%
  rare term                 14%
  compound / multi-part     11%
  negation                   5%

Part 3 — Retrieval Metrics, and Which One to Use

Four metrics matter, and they answer different questions. Reporting the wrong one is how a genuinely useful change gets rejected.

retrieved (k=5):  [ ✓,  ✗,  ✓,  ✗,  ✗ ]        relevant total = 3

recall@5    = 2/3  = 0.67    "of everything relevant, how much did we get?"
precision@5 = 2/5  = 0.40    "of what we returned, how much was useful?"
MRR         = 1/1  = 1.00    "how high was the FIRST relevant one?"
nDCG@5      = 0.85           "are the good ones near the top?" (graded, discounted)
MetricAnswersUse for RAG when
recall@kDid the answer make it into the context?The primary metric — the LLM cannot use what it never saw
nDCG@kAre the best results near the top?Evaluating reranking; long contexts
precision@kHow much noise is in the context?Small context budgets; cost control
MRRHow high is the first hit?Single-answer lookup, not multi-chunk synthesis

recall@k is the primary RAG metric, and the reason is structural. Retrieval's job is to ensure the answer is in the context window; the LLM does the rest. Moving a relevant chunk from position 4 to position 2 changes little — the model reads both. Moving it from position 12 to position 8 with k=10 changes everything.

def recall_at_k(retrieved, relevant, k):
    if not relevant: return None                    # skip, don't score as 0
    return len(set(retrieved[:k]) & set(relevant)) / len(relevant)

def ndcg_at_k(retrieved, relevance, k):             # relevance: id -> grade
    dcg  = sum(relevance.get(d, 0) / math.log2(i + 2)
               for i, d in enumerate(retrieved[:k]))
    ideal = sorted(relevance.values(), reverse=True)[:k]
    idcg = sum(g / math.log2(i + 2) for i, g in enumerate(ideal))
    return dcg / idcg if idcg else 0.0

But report recall and nDCG together, because they move independently and each one alone tells a misleading story:

                    recall@10   nDCG@10   what happened
  baseline             0.79      0.71
  + reranker           0.79      0.86     found nothing new, ordered it much better
  + more candidates    0.88      0.74     found more, ordered it worse

A recall-only view says the reranker did nothing. An nDCG-only view says more candidates hurt. Both conclusions are wrong, and both are common.

Graded relevance is worth the extra labelling effort for nDCG, because binary relevance throws away the distinction that matters most:

3 = directly answers the question
2 = contains part of the answer
1 = related context, useful background
0 = irrelevant

Part 4 — Evaluating Generation

Retrieval metrics say nothing about whether the answer was correct. Generation needs its own evaluation, and it must be separable from retrieval or you cannot attribute a failure.

DimensionQuestionHow to measure
FaithfulnessIs every claim supported by the context?LLM judge, claim by claim
Answer relevanceDoes it address what was asked?LLM judge, or similarity to a reference
CompletenessIs anything important missing?LLM judge against a reference answer
AbstentionDoes it say "I don't know" when it should?A held-out set with no answer in the corpus

Faithfulness is the one that detects hallucination, and it is measurable because it does not require knowing the true answer — only whether the claims follow from the supplied context:

FAITHFULNESS = """Break the ANSWER into individual factual claims.
For each claim, say SUPPORTED if it follows from the CONTEXT, or
UNSUPPORTED if it does not. Output one line per claim: "SUPPORTED: <claim>".

CONTEXT:
{context}

ANSWER:
{answer}"""

def faithfulness(answer, context, judge):
    lines = judge(FAITHFULNESS.format(context=context, answer=answer)).splitlines()
    claims = [l for l in lines if l.strip().startswith(("SUPPORTED", "UNSUPPORTED"))]
    if not claims: return None
    return sum(l.startswith("SUPPORTED") for l in claims) / len(claims)

The abstention set is the one teams forget, and its absence is why systems confidently answer questions their corpus cannot support. Include 10–15% of queries whose answers are genuinely absent and score the system on saying so:

abstention set: 60 questions with no answer in the corpus
  correctly abstained    41   (68%)
  fabricated an answer   19   (32%)     ← every one of these is a production incident

Using an LLM as judge works, with two specific precautions. First, validate the judge against human labels before trusting it — on a sample of 100, agreement below about 80% means the judge's output is not a measurement:

judge vs 2 human annotators, n=100:
  judge–human agreement    0.86        ← acceptable
  human–human agreement    0.91        ← the realistic ceiling

Second, know the biases — they are systematic, not random:

BiasEffectMitigation
PositionPrefers whichever answer is shown firstRandomise order; run both orders
VerbosityPrefers longer answersScore dimensions separately; control length
Self-preferencePrefers output from its own model familyUse a different model as judge
Score clusteringGives 4/5 to almost everythingBinary or 3-point scales, with rubrics

Prefer binary judgements with an explicit rubric over 1–5 scores. "Is this claim supported: yes/no" is far more reliable than "rate faithfulness 1–5", where the judge clusters everything at 4 and the metric barely moves between a good system and a mediocre one.

Part 5 — Deciding Whether a Change Is Real

A metric moved from 0.79 to 0.82. Is that a win? Without a statistical test the honest answer is "unknown" — and with n=100, it very often is noise.

Use a paired test, because both systems are evaluated on the same queries and the pairing removes the variance caused by some queries being harder than others:

from scipy import stats

def compare(scores_a, scores_b):
    """Paired, per-query scores from the same eval set."""
    diff = np.array(scores_b) - np.array(scores_a)
    t, p = stats.ttest_rel(scores_a, scores_b)
    ci = stats.bootstrap((diff,), np.mean, confidence_level=0.95).confidence_interval
    return {"mean_delta": diff.mean(), "p": p,
            "ci95": (ci.low, ci.high),
            "wins": int((diff > 0).sum()), "losses": int((diff < 0).sum())}

n=100:   delta = +0.030   p = 0.21    CI95 = [-0.018, +0.078]   → NOT significant
n=500:   delta = +0.030   p = 0.004   CI95 = [+0.010, +0.050]   → real

Identical effect size, opposite conclusions. The only difference is the sample size — which is why Part 2 argued for 500 queries rather than 50.

Report wins and losses, not just the mean. A +3 point average hides very different realities:

change A:  mean +0.03    wins 62   losses 8    unchanged 30    ← broad improvement
change B:  mean +0.03    wins 18   losses 14   unchanged 68    ← noisy, few affected

Change B moved 32 queries and helped 18 of them — a coin flip dressed as an improvement. Change A is the one worth shipping.

❌ Tuning against the evaluation set until the number goes up. Run the sweep, pick the configuration with the best score, ship it, repeat weekly. After ten iterations the pipeline is tuned to the specific 200 queries in the set — the score keeps rising and production quality does not move, because the set stopped measuring generalisation several iterations ago.

✅ Split the set, and refresh it. A development split for iteration and a held-out test split touched only when a change is ready to ship — a gap between the two is the signal that overfitting has begun. Add fresh queries from production logs each month, and rotate a portion of the test split out so it never becomes a fixed target.

Part 6 — Evaluation in CI

An evaluation set used manually is used twice. Wired into CI it becomes the thing that lets you change the pipeline without fear.

def evaluate_pipeline(pipeline, eval_set, k=10):
    per_query = []
    for q in eval_set:
        retrieved = pipeline.retrieve(q["query"], k=k)
        ids = [d.id for d in retrieved]
        per_query.append({
            "query_id": q["query_id"], "class": q["query_class"],
            "recall": recall_at_k(ids, q["relevant_chunk_ids"], k),
            "ndcg":   ndcg_at_k(ids, q["relevance_grades"], k),
        })
    return per_query

def summarise(per_query):
    out = {"overall": mean(r["recall"] for r in per_query)}
    for cls in {r["class"] for r in per_query}:
        rows = [r for r in per_query if r["class"] == cls]
        out[cls] = mean(r["recall"] for r in rows)
    return out

# ci_gate.py — fails the build on a regression
BASELINE = json.load(open("eval/baseline.json"))
current  = summarise(evaluate_pipeline(build_pipeline(), load_eval_set()))

failed = []
for cls, base in BASELINE.items():
    delta = current[cls] - base
    if delta < -0.02:                              # tolerance, not zero
        failed.append(f"{cls}: {base:.3f} → {current[cls]:.3f} ({delta:+.3f})")

print(json.dumps(current, indent=2))
if failed:
    sys.exit("REGRESSION:\n" + "\n".join(failed))

Gate per class, not only on the aggregate. A change that adds 5 points to paraphrase queries and removes 15 from exact-identifier queries can leave the overall number flat — and that is exactly the change you most want the build to catch.

What to gateToleranceWhy
Overall recall@10−0.02Catches broad regressions
Each query class−0.05Catches class-specific collapses the aggregate hides
p95 retrieval latency+20%Quality changes that quietly cost latency
Faithfulness−0.03Hallucination regressions
Abstention rate−0.05The system starting to answer what it should not

Track the index alongside the code, because retrieval quality depends on data that CI does not version: the corpus changed, the embedding model changed, the index was rebuilt. Record the corpus hash, chunk count and model name with every evaluation run, or a "regression" will send someone hunting through code that did not change.

Finally, evaluation is not only offline. Offline metrics predict; production tells you what happened. The signals worth logging are cheap:

per-query production telemetry:
  retrieval scores (max, mean)     → low max = likely no good match
  number of results returned       → fewer than k means a FILTER or tombstone problem
  whether the answer cited sources → uncited answers correlate with hallucination
  user feedback (thumbs, retries)  → the ground truth you cannot generate
  follow-up rate                   → a proxy for "the first answer was inadequate"

Queries with a low maximum retrieval score are the highest-value thing to sample: they are where the corpus has a gap, and they become next month's evaluation queries — which closes the loop between production and the set you started with in Part 2.

Interview Questions

Beginner: What is a RAG evaluation set and what goes in it?

It is a fixed collection of queries with judged answers, used to measure the pipeline consistently as it changes. Each entry pairs a query with the chunks that should be retrieved:

{
  "query_id": "q_0142",
  "query": "how long is an old API key valid after rotation?",
  "relevant_chunk_ids": ["docs/api-keys#3", "faq/rotation#1"],
  "reference_answer": "One hour.",
  "query_class": "exact-lookup"
}

The point is comparability over time. Without one, "did that change help?" is answered by trying a few queries someone remembers — different queries each time, so the answers are not comparable and regressions are invisible until users complain.

FieldWhy it is there
relevant_chunk_idsEnables recall@k — the primary retrieval metric
reference_answerEnables answer-quality evaluation separately from retrieval
query_classEnables stratification — the aggregate hides class collapses

Queries should come from production logs where possible, because invented queries are systematically better-formed than real ones. Users type "key rotate how long"; a team writes "how long is an old API key valid after rotation?" — and a system tuned on the second under-performs on the first.

Size matters more than people expect: 200 is a practical floor and 500 is a reasonable target, because below that the confidence interval is wider than the improvements you are trying to detect.

Beginner: Which retrieval metric should you optimise for a RAG system, and why?

recall@k — the fraction of relevant chunks that made it into the top k.

retrieved (k=5): [ ✓, ✗, ✓, ✗, ✗ ]     relevant total = 3

recall@5    = 2/3 = 0.67
precision@5 = 2/5 = 0.40
MRR         = 1/1 = 1.00

The reason is structural: the LLM cannot use a chunk it never saw. Retrieval's entire job in RAG is to get the answer into the context window; the model handles selection and synthesis from there. So a chunk missing from the context is an unrecoverable failure, while a chunk at position 4 instead of position 2 is barely a failure at all.

That asymmetry explains why the other metrics are secondary:

MetricWhy it is not primary for RAG
precision@kModern models tolerate some irrelevant context; missing context they cannot fix
MRROnly measures the first hit — but answers often need several chunks
nDCG@kMeasures ordering, which matters less than presence — though see below

The important caveat is to report nDCG alongside recall, because they move independently. A reranker typically leaves recall unchanged (it finds nothing new) while moving nDCG substantially (it orders much better). Looking only at recall, you would conclude the reranker did nothing and remove it.

Precision becomes relevant when the context budget is tight or cost matters, since every irrelevant chunk is tokens paid for — but the default should be to retrieve generously and let reranking handle precision.

Mid: How would you build an evaluation set for a corpus with no query logs?

Bootstrap with an LLM, then replace it with real data as it arrives — knowing exactly which biases the bootstrap introduces.

1. Generate candidate queries from sampled chunks, deliberately varying phrasing:

GEN = """Write 3 questions this passage answers. Vary the phrasing:
one natural question, one terse keyword query, one using DIFFERENT words
than the passage. One per line.

Passage: {chunk}"""

The "different words" instruction matters because the main bias of generated queries is that they share vocabulary with their source chunk — which makes lexical retrieval look far better than it is and inflates every number in the set.

2. Fix the single-label problem with pooling. Bootstrapping marks exactly one chunk relevant, but others may answer equally well, so any system retrieving those is scored wrong:

def build_pool(query, systems, k=10):
    pool = set()
    for s in systems:              # dense, bm25, hybrid, hybrid+rerank
        pool.update(s.search(query, k))
    return sorted(pool)            # judge the union, once

This is the TREC approach: judge the union of what several systems retrieve. Anything no system found stays unjudged — an accepted limitation — but everything a realistic system might return has a label.

3. Have a human review a sample. LLM labels on 500 queries with human verification of 100 is far better than either alone, and the verification also tells you whether the judge is trustworthy for the rest.

4. Stratify deliberately, since generated queries skew toward well-formed conceptual questions. I would force coverage of exact identifiers, rare terms, compound questions and negations, plus 10–15% unanswerable queries for abstention.

5. Then replace it. Log production queries from day one, sample them monthly, and migrate the set toward real traffic. The bootstrapped set is scaffolding — good enough to start measuring, not good enough to trust indefinitely, and its inflated absolute numbers matter less than the fact that it makes changes comparable.

Mid: How do you evaluate whether a RAG system hallucinates, and how do you use an LLM as a judge safely?

Hallucination is measured as faithfulness: is every claim in the answer supported by the retrieved context? The useful property is that this does not require knowing the true answer — only whether the answer follows from what was supplied.

FAITHFULNESS = """Break the ANSWER into individual factual claims. For each,
output "SUPPORTED: <claim>" if it follows from the CONTEXT, else
"UNSUPPORTED: <claim>".

CONTEXT: {context}
ANSWER:  {answer}"""

score = supported_claims / total_claims

Claim-level decomposition is what makes it work. Asking "is this answer faithful, 1–5?" produces a judge that says 4 for everything; asking "is this specific claim supported, yes or no?" produces a signal that actually moves.

The complement is an abstention set — 10–15% of queries whose answers are genuinely not in the corpus. A system that never abstains is a system that fabricates:

60 unanswerable questions:
  correctly abstained    41   (68%)
  fabricated an answer   19   (32%)   ← each is a potential incident

Before trusting the judge, validate it against humans. Label 100 examples manually and measure agreement; below ~80% the judge is not measuring anything:

judge–human   0.86      ← acceptable
human–human   0.91      ← the realistic ceiling

And design around the known biases, which are systematic rather than random:

BiasMitigation
Position — prefers the first answer shownRandomise order; evaluate both orders
Verbosity — prefers longer answersScore dimensions separately; control length
Self-preference — prefers its own family's outputJudge with a different model
Clustering — gives 4/5 to everythingBinary judgements with rubrics

Judging with the same model that generated the answer is the mistake worth naming explicitly — it is convenient, it is one API key, and it systematically inflates the score of the system you are trying to measure.

Senior: Design the complete evaluation strategy for a production RAG system.

I would build it in three layers — offline, CI, and production telemetry — because each catches failures the others cannot, and each has a different cost and latency.

Layer 1 — the offline evaluation set. 500 queries sampled from production logs, stratified to match the real traffic mix, with pooled relevance judgements from several retrieval configurations and graded labels (0–3) so nDCG is meaningful. Split into a development half for iteration and a held-out test half touched only when a change is ready to ship. 10–15% of queries are deliberately unanswerable, to measure abstention.

LayerRunsCatches
Offline eval setOn demand, during developmentWhether a change helps, per query class
CI gateEvery PRRegressions before merge
Production telemetryContinuouslyWhat offline evaluation failed to predict

Layer 2 — the CI gate, with per-class tolerances rather than a single aggregate:

overall recall@10       tolerance −0.02
each query class        tolerance −0.05      ← the one that matters
p95 retrieval latency   tolerance +20%
faithfulness            tolerance −0.03
abstention rate         tolerance −0.05

The per-class gate is the important one: a change that gains 5 points on paraphrase queries and loses 15 on exact-identifier queries can leave the aggregate flat, and that is precisely the change I want blocked.

I would also version the data with the run — corpus hash, chunk count, embedding model — because retrieval quality depends on inputs CI does not version, and a "regression" caused by a corpus change otherwise sends someone searching code that did not change.

Layer 3 — production telemetry, which is the only layer that sees the real distribution:

per query: max/mean retrieval score, results returned, cited sources,
           user feedback, follow-up rate, latency

Queries with a low maximum retrieval score are the highest-value sample — they mark corpus gaps, and they become next month's evaluation queries, which closes the loop back to layer 1.

The process discipline matters as much as the mechanics: refresh the set monthly from logs, rotate part of the test split so it never becomes a fixed target, and require a paired significance test before declaring any win. A team that iterates against a static set for six months has a rising number and a static product.

What I would build first, if the budget were one week: 200 queries from logs, recall@10 stratified by class, and the CI gate. That is most of the value — the graded labels, faithfulness judging and telemetry can follow, but without the gate nothing prevents the next regression.

Senior: A change improves your eval metric by 3 points. How do you decide whether to ship it?

I would treat "+3 points" as a hypothesis rather than a result, because at typical evaluation-set sizes it is frequently noise, and because a mean can hide a change that helps most queries slightly while breaking a few badly.

1. Test whether it is real. A paired test, since both systems ran on the same queries and pairing removes the variance from some queries simply being harder:

n=100:   delta +0.030   p=0.21    CI95 [-0.018, +0.078]   → cannot distinguish from 0
n=500:   delta +0.030   p=0.004   CI95 [+0.010, +0.050]   → real

Same effect, opposite conclusions — the difference is only sample size. If the set is 100 queries, the honest answer is that I do not know yet, and the fix is a larger set rather than a bolder claim.

2. Look at the distribution, not the mean:

change A:  +0.03   wins 62  losses  8  unchanged 30    ← broad, consistent
change B:  +0.03   wins 18  losses 14  unchanged 68    ← a coin flip

Change B affected 32 queries and helped 18 — that is not an improvement, it is variance. I would ship A and investigate B's 14 losses before considering it.

3. Check the per-class breakdown, which is where the dangerous changes hide:

                 overall  paraphrase  exact-id  rare-term
  before          0.79       0.86       0.71      0.68
  after           0.82       0.91       0.52      0.74
                  +0.03      +0.05     −0.19     +0.06
                                        ↑ a 19-point collapse, invisible in the mean

An aggregate gain concealing a class collapse is the single most common way a "win" degrades production, and exact-identifier queries are frequently the class that breaks.

4. Check the costs the metric does not include: latency (p50 and p95), infrastructure, and whether the change adds an operational dependency. A 3-point gain for 400 ms is usually a bad trade; the same gain for 3 ms is free.

5. Confirm end-to-end. Retrieval recall is a proxy — the question is whether answers improved. I would run answer-quality judging on the same query set, because recall can rise while quality does not if the extra chunks land where the model does not attend.

6. Then ship it behind a flag with a production check. Offline evaluation predicts; production decides. A percentage rollout with user-feedback and follow-up-rate monitoring is what confirms the offline number transferred — and occasionally it does not, which is itself the most valuable thing the evaluation could have told me.

🏋️ Exercises

1 (easy): Implement the four retrieval metrics and see how they disagree.
Solution 
import math

def recall_at_k(retrieved, relevant, k):
    if not relevant: return None
    return len(set(retrieved[:k]) & set(relevant)) / len(relevant)

def precision_at_k(retrieved, relevant, k):
    if k == 0: return 0.0
    return len(set(retrieved[:k]) & set(relevant)) / k

def mrr(retrieved, relevant):
    for i, d in enumerate(retrieved, 1):
        if d in relevant:
            return 1.0 / i
    return 0.0

def ndcg_at_k(retrieved, grades, k):
    dcg = sum(grades.get(d, 0) / math.log2(i + 2)
              for i, d in enumerate(retrieved[:k]))
    ideal = sorted(grades.values(), reverse=True)[:k]
    idcg = sum(g / math.log2(i + 2) for i, g in enumerate(ideal))
    return dcg / idcg if idcg else 0.0

import numpy as np
from scipy import stats
rng = np.random.default_rng(0)

def simulate(n, true_a=0.79, true_b=0.82, trials=2000):
    """Per-query binary outcomes; how often do we call it significant?"""
    calls = []
    for _ in range(trials):
        a = rng.random(n) < true_a
        b = rng.random(n) < true_b
        _, p = stats.ttest_rel(a.astype(float), b.astype(float))
        calls.append(p < 0.05)
    return np.mean(calls)

Now the false-positive direction, which is the failure people actually make:

def false_positive(n, true=0.80, trials=2000):
    """Two IDENTICAL systems. How often does a naive 'number went up' call a win?"""
    naive = sig = 0
    for _ in range(trials):
        a = rng.random(n) < true
        b = rng.random(n) < true                 # same true quality
        naive += (b.mean() - a.mean()) >= 0.03   # "+3 points, ship it"
        _, p = stats.ttest_rel(a.astype(float), b.astype(float))
        sig += p < 0.05
    return naive/trials, sig/trials

for n in (50, 100, 500):
    naive, sig = false_positive(n)
    print(f"n={n:4d}  '+3pts = win': {naive:5.1%} false positives   "
          f"with a test: {sig:4.1%}")

n=  50  '+3pts = win': 31.6% false positives   with a test:  5.2%
n= 100  '+3pts = win': 24.8% false positives   with a test:  4.9%
n= 500  '+3pts = win': 10.2% false positives   with a test:  5.1%

With 50 queries and no test, two identical systems produce a "+3 point win" nearly a third of the time. Ship weekly on that basis and most of what you ship is noise.

Report the interval and the win/loss split instead:

Significant, but 118 wins against 102 losses — a modest net effect on a minority of queries, not the broad improvement "+3 points" suggests. The split is what tells you that.

FAITHFULNESS = """Break the ANSWER into individual factual claims. For each,
output "SUPPORTED: <claim>" if it follows from the CONTEXT, otherwise
"UNSUPPORTED: <claim>". Output nothing else.

CONTEXT:
{context}

ANSWER:
{answer}"""

def faithfulness(answer, context, judge):
    lines = judge(FAITHFULNESS.format(context=context, answer=answer)).splitlines()
    claims = [l.strip() for l in lines
              if l.strip().startswith(("SUPPORTED", "UNSUPPORTED"))]
    if not claims:
        return None                       # judge failed; don't score it as 0
    return sum(l.startswith("SUPPORTED") for l in claims) / len(claims)

5 (hard): Build the full evaluation harness with stratification and significance testing.
Solution 
import numpy as np, math, json
from dataclasses import dataclass, field
from scipy import stats

@dataclass
class EvalQuery:
    query_id: str
    query: str
    relevant: set
    grades: dict = field(default_factory=dict)
    cls: str = "general"

def evaluate(pipeline, eval_set, k=10):
    rows = []
    for q in eval_set:
        ids = pipeline.retrieve(q.query, k=k)
        rows.append({
            "query_id": q.query_id, "cls": q.cls,
            "recall": len(set(ids[:k]) & q.relevant) / len(q.relevant),
            "ndcg":   ndcg_at_k(ids, q.grades or {d: 1 for d in q.relevant}, k),
        })
    return rows

def summarise(rows):
    out = {"overall": float(np.mean([r["recall"] for r in rows])),
           "overall_ndcg": float(np.mean([r["ndcg"] for r in rows]))}
    for cls in sorted({r["cls"] for r in rows}):
        sub = [r["recall"] for r in rows if r["cls"] == cls]
        out[cls] = float(np.mean(sub))
        out[f"{cls}_n"] = len(sub)
    return out

def compare(rows_a, rows_b, metric="recall"):
    """Paired comparison on the same queries."""
    by_id = {r["query_id"]: r[metric] for r in rows_a}
    a = np.array([by_id[r["query_id"]] for r in rows_b])
    b = np.array([r[metric] for r in rows_b])
    diff = b - a
    _, p = stats.ttest_rel(a, b)
    ci = stats.bootstrap((diff,), np.mean,
                         confidence_level=0.95, random_state=0).confidence_interval
    return {"delta": float(diff.mean()), "p": float(p),
            "ci95": (float(ci.low), float(ci.high)),
            "wins": int((diff > 0).sum()), "losses": int((diff < 0).sum()),
            "significant": bool(p < 0.05)}

def compare_by_class(rows_a, rows_b):
    out = {}
    for cls in sorted({r["cls"] for r in rows_b}):
        ra = [r for r in rows_a if r["cls"] == cls]
        rb = [r for r in rows_b if r["cls"] == cls]
        out[cls] = compare(ra, rb)
    return out

6 (hard): Wire evaluation into CI as a regression gate.
Solution

The goal: a build that fails on a quality regression, gates per class, and cannot be confused by a corpus change masquerading as a code change.

# eval/gate.py
import json, sys, hashlib, numpy as np

TOLERANCE = {"overall": -0.02, "overall_ndcg": -0.02,
             "_per_class": -0.05, "p95_latency_pct": 0.20}

def fingerprint(corpus, model_name):
    """Version the DATA, not just the code."""
    h = hashlib.sha256()
    for c in sorted(corpus, key=lambda x: x.id):
        h.update(c.id.encode()); h.update(c.content.encode())
    return {"corpus_sha": h.hexdigest()[:12], "n_chunks": len(corpus),
            "model": model_name}

def compare_to_baseline(current, baseline):
    """Pure comparison — no I/O, so it is directly testable."""
    # A data change is not a code regression — say so explicitly.
    if baseline.get("_fingerprint") != current.get("_fingerprint"):
        print("NOTE: corpus/model changed since baseline:")
        print(f"  was {baseline.get('_fingerprint')}")
        print(f"  now {current.get('_fingerprint')}")

    failures = []
    for key, tol in (("overall", TOLERANCE["overall"]),
                     ("overall_ndcg", TOLERANCE["overall_ndcg"])):
        d = current[key] - baseline[key]
        if d < tol:
            failures.append(f"{key}: {baseline[key]:.3f} → {current[key]:.3f} ({d:+.3f})")

    for key in current:
        if key.startswith("_") or key.startswith("overall") or key.endswith("_n"):
            continue
        if key not in baseline: continue
        d = current[key] - baseline[key]
        if d < TOLERANCE["_per_class"]:
            failures.append(f"class {key}: {baseline[key]:.3f} → {current[key]:.3f} ({d:+.3f})")

    lat = (current["p95_latency"] - baseline["p95_latency"]) / baseline["p95_latency"]
    if lat > TOLERANCE["p95_latency_pct"]:
        failures.append(f"p95 latency +{lat:.0%}")

    return current, failures

def run_gate(pipeline, eval_set, baseline_path="eval/baseline.json"):
    rows = evaluate(pipeline, eval_set, k=10)
    current = summarise(rows)
    current["p95_latency"] = float(np.percentile([r["latency_ms"] for r in rows], 95))
    current["_fingerprint"] = fingerprint(pipeline.corpus, pipeline.model_name)
    return compare_to_baseline(current, json.load(open(baseline_path)))

if __name__ == "__main__":
    current, failures = run_gate(build_pipeline(), load_eval_set())
    print(json.dumps({k: v for k, v in current.items()
                      if not k.endswith("_n")}, indent=2))
    if failures:
        sys.exit("QUALITY GATE FAILED:\n  " + "\n  ".join(failures))
    print("quality gate passed")

A self-check for the gate itself:

def test_gate():
    base = {"overall": 0.80, "overall_ndcg": 0.85, "exact-id": 0.90,
            "p95_latency": 100.0, "_fingerprint": {"corpus_sha": "x"}}
    cur  = dict(base, overall=0.79, **{"exact-id": 0.55})     # class collapse
    _, failures = compare_to_baseline(cur, base)
    assert any("exact-id" in f for f in failures), "must catch class regression"
    assert not any("overall" in f for f in failures), "overall is within tolerance"

    cur2 = dict(base, p95_latency=130.0)                      # +30% latency
    _, f2 = compare_to_baseline(cur2, base)
    assert any("latency" in f for f in f2)
    print("ok")

test_gate()    # → ok

The first assertion is the important one: it verifies that the gate catches exactly the regression an aggregate-only check would miss.

🎯 Key Takeaways

  • Without an evaluation set you are not tuning a RAG system, you are guessing — every change is unattributable and therefore irreversible.
  • Build the set before the optimisation; a day of judging pays for itself in the first week of tuning.
  • Sample queries from production logs. Invented queries are systematically better-formed than real ones, and a system tuned on them under-performs on real traffic.
  • LLM-generated queries are a legitimate bootstrap, but they share vocabulary with their source chunk and inflate every number — replace them with real queries as logs accumulate.
  • Labelling one relevant chunk per query undercounts recall; pool the top-k of several systems and judge the union.
  • 200 queries is the practical floor and 500 the target — below that the confidence interval is wider than any improvement you can make.
  • Stratify by query class and always report per class; an aggregate gain routinely hides a class collapsing.
  • recall@k is the primary RAG metric: the LLM cannot use a chunk it never saw, and presence matters more than position.
  • Report nDCG alongside recall — a reranker leaves recall unchanged while moving nDCG substantially, and a recall-only view says it did nothing.
  • Graded relevance (0–3) makes nDCG meaningful; binary labels discard the distinction between "answers it" and "mentions it".
  • Evaluate generation separately: faithfulness (claim-by-claim support), answer relevance, and abstention on questions the corpus cannot answer.
  • Validate an LLM judge against human labels before trusting it; below ~80% agreement it is not a measurement.
  • Prefer binary judgements with rubrics over 1–5 scores, which cluster at 4 and barely discriminate.
  • Use a different model family as judge — self-preference bias systematically inflates the system you are measuring.
  • A +3 point move at n=100 is usually noise; use a paired test, report the confidence interval, and show wins versus losses rather than only the mean.
  • Split dev and test, and refresh from production logs — iterating against a static set produces a rising number and a static product.
  • Gate CI per query class with a tolerance, not on the aggregate alone, because the dangerous change is the one that trades one class for another.
  • Version the corpus hash, chunk count and model with every run, or a data change will be debugged as a code regression.
  • Never auto-update the baseline: tolerated regressions ratchet quality downward one acceptable step at a time.
  • Close the loop with production telemetry — queries with low maximum retrieval scores mark corpus gaps and become next month's evaluation queries.
