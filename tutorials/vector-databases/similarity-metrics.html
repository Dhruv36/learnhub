Similarity Metrics & Normalisation Foundations

What you'll master: the three metrics every vector store offers and what each one actually measures, the algebraic identity that makes cosine and dot product the same operation on normalised vectors, why dot product on unnormalised vectors quietly ranks by document length, the distance-versus-similarity sign confusion that produces a search returning the worst results with total confidence, when Euclidean is genuinely the right choice, and how to verify your index is using the metric you think it is. Prerequisites: Embeddings & Vector Space.

Part 1 — Three Metrics, One Geometry

Every vector store offers essentially the same three ways to compare two vectors. They differ in what they are sensitive to.

Given vectors a and b in ℝᵈ:

  dot product      a · b   =  Σ aᵢbᵢ                         → sensitive to BOTH angle and magnitude
  cosine sim       (a · b) / (‖a‖ ‖b‖)                        → angle ONLY, magnitude cancelled
  Euclidean (L2)   ‖a − b‖ = √( Σ (aᵢ − bᵢ)² )                → straight-line distance in the space
MetricRangeBest match isSensitive to magnitude?
Cosine similarity−1 … 1HighestNo
Cosine distance0 … 2LowestNo
Dot product (inner product)unboundedHighestYes
Euclidean (L2) distance0 … ∞LowestYes
Squared L20 … ∞LowestYes — same ranking, avoids the sqrt

The geometric intuition is worth carrying: cosine asks "do these point the same way?" while Euclidean asks "are these in the same place?" and dot product asks both at once. For text embeddings, direction carries the meaning and magnitude is mostly an artefact of how the model processed the input — which is why cosine dominates in practice.

$ python3 - <<'EOF'
import numpy as np
a = np.array([1.0, 2.0, 3.0])
b = np.array([2.0, 4.0, 6.0])        # same direction, twice the length
c = np.array([3.0, 1.0, 0.5])        # different direction

def cos(x, y): return float(x @ y / (np.linalg.norm(x) * np.linalg.norm(y)))
for name, v in [("b (2x a)", b), ("c (different)", c)]:
    print(f"{name:14} cos={cos(a,v):+.3f}  dot={float(a@v):7.2f}  L2={np.linalg.norm(a-v):.3f}")
EOF
b (2x a)       cos=+1.000  dot=  28.00  L2=3.742
c (different)  cos=+0.630  dot=   6.50  L2=3.354

Read that carefully — the three metrics disagree about which is closer. Cosine says b is a perfect match (identical direction). Euclidean says c is closer (smaller straight-line distance). Dot product says b, but only because b is longer. For text retrieval, cosine's answer is the one you want.

Part 2 — The Identity That Matters

When both vectors have unit length, cosine similarity and dot product are the same number. This is not an approximation; it falls straight out of the definition:

  cosine(a, b) = (a · b) / (‖a‖ ‖b‖)

  if ‖a‖ = ‖b‖ = 1:

  cosine(a, b) = (a · b) / (1 × 1) = a · b

$ python3 - <<'EOF'
import numpy as np
rng = np.random.default_rng(0)
a, b = rng.standard_normal(768), rng.standard_normal(768)
an, bn = a/np.linalg.norm(a), b/np.linalg.norm(b)

print(f"cosine(a, b)        = {a@b/(np.linalg.norm(a)*np.linalg.norm(b)):+.9f}")
print(f"dot(normalised)     = {an@bn:+.9f}")
print(f"identical: {np.isclose(a@b/(np.linalg.norm(a)*np.linalg.norm(b)), an@bn)}")
EOF
cosine(a, b)        = -0.021847193
dot(normalised)     = -0.021847193
identical: True
🔑 Normalise at ingestion, then use dot product. This is the single most useful operational rule in this lesson. Dot product is one fused multiply-add per dimension with no division and no square root, so it is the fastest path in every index implementation — and on normalised vectors it computes exactly cosine similarity. You get cosine semantics at inner-product speed. Many stores (FAISS IndexFlatIP, pgvector's vector_ip_ops) are built around this assumption.

There is a related identity for Euclidean distance on normalised vectors, which explains why L2 and cosine produce identical rankings once you normalise:

  ‖a − b‖²  =  ‖a‖² + ‖b‖² − 2(a · b)
            =  1 + 1 − 2(a · b)          (unit vectors)
            =  2 − 2·cosine(a, b)

Euclidean distance is a strictly decreasing function of cosine similarity, so sorting by one is sorting by the other. On normalised vectors the choice between cosine, dot product and L2 is a performance decision, not a semantic one.

Part 3 — What Goes Wrong Without Normalisation

Dot product on unnormalised vectors ranks partly by magnitude. Since many embedding models produce longer vectors for longer or more "content-dense" inputs, this silently becomes a length bias:

$ python3 - <<'EOF'
import numpy as np
query = np.array([1.0, 0.0])

short_exact = np.array([1.0, 0.0])          # perfect direction, unit length
long_vague  = np.array([2.0, 2.5])          # wrong direction, but long

for name, v in [("short exact match", short_exact), ("long vague match", long_vague)]:
    dot = float(query @ v)
    cos = dot / (np.linalg.norm(query) * np.linalg.norm(v))
    print(f"{name:20} dot={dot:5.2f}  cos={cos:.3f}  ‖v‖={np.linalg.norm(v):.2f}")
EOF
short exact match    dot= 1.00  cos=1.000  ‖v‖=1.00
long vague match     dot= 2.00  cos=0.625  ‖v‖=3.20

Dot product ranks the vague long document above the perfect short match. Cosine gets it right. On a real corpus this manifests as long documents dominating every result set — a failure that looks like "the embedding model prefers verbose text" and is actually a metric bug.

SituationCorrect metricReasoning
Text retrieval, vectors normalisedDot product (= cosine)Fastest path, cosine semantics
Text retrieval, vectors NOT normalisedCosineDot product introduces a length bias
Recommendation with a popularity signal in the normDot product, deliberatelyMagnitude is meaningful here — a design choice
Coordinates, colours, physical measurementsEuclideanMagnitude is the data; direction alone is meaningless
Binary or hashed vectorsHammingCounting differing bits is the natural distance

The third row is worth noting because it is the legitimate use of dot product on unnormalised vectors: some recommender systems deliberately encode item quality or popularity in the vector's magnitude, so that a strong match to a popular item outranks an equally strong match to an obscure one. That is a feature, but it must be intentional.

Part 4 — Distance vs Similarity: The Sign Trap

The most common runtime bug in vector search is sorting the wrong way, because libraries disagree about whether they return similarity (higher is better) or distance (lower is better).

  cosine SIMILARITY:  1.0 = identical,  0.0 = orthogonal,  −1.0 = opposite   → sort DESC
  cosine DISTANCE  :  0.0 = identical,  1.0 = orthogonal,   2.0 = opposite   → sort ASC

  relationship:  cosine_distance = 1 − cosine_similarity
Library / storeOperator or callReturnsBest is
pgvector<=>Cosine distanceLowest — ORDER BY ... ASC
pgvector<#>Negative inner productLowest (because negated)
pgvector<->L2 distanceLowest
FAISS IndexFlatIPsearch()Inner productHighest
FAISS IndexFlatL2search()Squared L2Lowest
Qdrant / PineconequerySimilarity scoreHighest
scikit-learncosine_similaritySimilarityHighest

pgvector's <#> deserves special attention: it returns the negative inner product specifically so that "smaller is better" holds uniformly across all its operators and its index can always sort ascending. A score of -0.87 is a strong match, and code that filters WHERE score > 0.7 against it returns exactly the wrong rows.

-- pgvector: all three operators sort ASCENDING
SELECT id, embedding <=> $1 AS distance      -- cosine distance, 0 = identical
FROM chunks ORDER BY embedding <=> $1 LIMIT 10;

SELECT id, (embedding <#> $1) * -1 AS similarity   -- negate to get a readable score
FROM chunks ORDER BY embedding <#> $1 LIMIT 10;

❌ Assuming the score means what its name suggests and sorting accordingly. Sorting a distance descending returns the least similar documents, ranked by how irrelevant they are. Nothing errors, results look plausible at a glance, and the system confidently serves the worst possible answers — a bug that has survived in production for months because "it returns results".

✅ Write one assertion that pins the direction, and keep it in the test suite. Embed a text, search for that exact text, and assert it ranks first. That single test catches sign errors, metric mismatches between ingestion and query, and a normalisation change made months later — all of which are otherwise silent.

Part 5 — Choosing and Verifying the Metric

The metric must match what the embedding model was trained with. Nearly all modern text models are trained with cosine similarity, and using L2 on unnormalised vectors from such a model degrades recall measurably.

$ python3 - <<'EOF'
from sentence_transformers import SentenceTransformer
import numpy as np
m = SentenceTransformer('all-MiniLM-L6-v2')

docs = ["Postgres streaming replication lag",
        "A very long document about database replication that repeats the topic "
        "many times over, covering replication, replication configuration, and "
        "replication monitoring in exhaustive and repetitive detail throughout.",
        "Kubernetes pod scheduling"]
q = "replication delay"

raw = m.encode(docs)                                  # NOT normalised
nrm = m.encode(docs, normalize_embeddings=True)
qr  = m.encode([q])[0]
qn  = m.encode([q], normalize_embeddings=True)[0]

print("norms:", [round(float(np.linalg.norm(v)), 2) for v in raw])
print("\nranking by DOT on raw vectors:")
for s, d in sorted(zip(raw @ qr, docs), reverse=True): print(f"  {s:7.3f}  {d[:48]}")
print("\nranking by COSINE (normalised):")
for s, d in sorted(zip(nrm @ qn, docs), reverse=True): print(f"  {s:7.3f}  {d[:48]}")
EOF

The verbose document wins on dot product purely because its vector is longer (6.92 vs 4.81). Cosine puts the concise, precise match first. Note that some models normalise internally — check rather than assume:

BGE normalises internally; MiniLM does not. A pipeline that assumes one behaviour and gets the other has a metric bug that only shows as slightly worse recall.

Part 6 — Practical Consequences

Normalisation must be consistent across ingestion and query. Half-normalised systems are common and produce a subtle, permanent quality loss:

# WRONG — the metric is now neither cosine nor a meaningful dot product
docs  = model.encode(texts, normalize_embeddings=True)
query = model.encode([q])[0]                    # forgot to normalise
scores = docs @ query                            # scaled by ‖query‖, ranking still OK...

# ...but any THRESHOLD is now wrong, and it breaks entirely if you ever
# compare scores across queries.

Ranking within a single query survives, because scaling every score by the same constant does not change order. What breaks is anything comparing scores between queries: thresholds, confidence reporting, and score-based fusion in hybrid search.

Changing the metric requires rebuilding the index, because ANN structures are built around a specific distance function:

-- pgvector: the index is metric-specific
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);   -- for <=>
CREATE INDEX ON chunks USING hnsw (embedding vector_ip_ops);       -- for <#>
CREATE INDEX ON chunks USING hnsw (embedding vector_l2_ops);       -- for <->

-- A query using <-> against a vector_cosine_ops index does NOT use the index.
-- It silently falls back to a sequential scan: correct results, terrible latency.

That silent fallback is worth internalising — a metric mismatch in pgvector does not error, it just stops using the index. The symptom is a query that got 500× slower after a refactor, with correct results.

Squared L2 is a free optimisation. Since the square root is monotonic, ranking by ‖a−b‖² gives the same order as ‖a−b‖ while avoiding a square root per comparison. Most libraries return squared L2 by default for exactly this reason — which is another source of surprising score magnitudes.

Interview Questions

Beginner: What is cosine similarity and why is it the usual choice for text?

Cosine similarity measures the angle between two vectors, ignoring their lengths:

cosine(a, b) = (a · b) / (‖a‖ ‖b‖)      range −1 … 1
                1.0 = same direction
                0.0 = orthogonal (unrelated)
               −1.0 = opposite

It is the usual choice for text because direction carries the meaning and magnitude mostly does not. An embedding model's output length varies with input length and content density — artefacts of how the text was processed, not of what it means. A concise sentence and a verbose passage on the same topic should be equally similar to a query about it, and cosine gives exactly that by cancelling the magnitudes.

The contrast makes it concrete. Dot product on the same vectors ranks the verbose document higher simply because its vector is longer, so long documents dominate every result set — a failure that looks like a model problem and is actually a metric problem.

It also matches how the models were trained: nearly all modern text embedding models use a contrastive objective defined in terms of cosine similarity, so using cosine at query time is using the model the way it was built.

Beginner: What is the difference between similarity and distance?

They express the same relationship with opposite sign conventions:

similarity: HIGHER is better    cosine similarity 1.0 = identical    → sort DESC
distance  : LOWER  is better    cosine distance   0.0 = identical    → sort ASC

cosine_distance = 1 − cosine_similarity

The practical importance is that libraries disagree about which they return, and getting it wrong produces a search that confidently serves the worst results:

ToolReturns
pgvector <=>Cosine distance — lowest is best
pgvector <#>Negative inner product — lowest is best
FAISS IndexFlatIPInner product — highest is best
Qdrant, PineconeSimilarity score — highest is best

pgvector's <#> is the sharpest edge: it negates deliberately so "smaller is better" holds across all its operators. A score of -0.87 is a strong match, and WHERE score > 0.7 against it returns precisely the wrong rows.

The defence is one test: embed a document, search for its exact text, assert it comes back first. That catches sign errors, metric mismatches, and normalisation changes made later — all of which are otherwise completely silent.

Mid: When are cosine similarity and dot product the same thing?

When both vectors have unit length. It falls straight out of the definition:

cosine(a, b) = (a · b) / (‖a‖ ‖b‖)
if ‖a‖ = ‖b‖ = 1:   cosine(a, b) = a · b

This is the basis of the standard operational rule: normalise at ingestion, then use dot product. Dot product is one fused multiply-add per dimension — no division, no square root — so it is the fastest path in every index implementation. On normalised vectors it computes exactly cosine similarity, so you get cosine semantics at inner-product speed.

There is a companion identity for Euclidean distance:

‖a − b‖² = ‖a‖² + ‖b‖² − 2(a·b) = 2 − 2·cosine(a, b)     (unit vectors)

L2 distance is a strictly decreasing function of cosine similarity, so on normalised vectors all three metrics produce identical rankings. The choice becomes purely a performance decision.

Two caveats worth stating. The rankings coincide but the scores do not, so thresholds are not transferable between metrics. And some models normalise internally (BGE) while others do not (MiniLM) — checking np.linalg.norm once at pipeline setup is worth doing rather than assuming.

Mid: Your search returns long documents disproportionately. What would you check?

My first hypothesis is a metric problem rather than a model or content problem, because this is its classic signature.

1. Check whether dot product is being used on unnormalised vectors. Embedding norms correlate with input length, so dot product ranks partly by document length:

$ python3 -c "
import numpy as np
print([round(float(np.linalg.norm(v)),2) for v in model.encode(docs)])
"
[4.81, 6.92, 4.44]     # the long document's vector is ~40% longer

A concise perfect match then loses to a verbose partial match. Switching to cosine, or normalising at ingestion, fixes it outright.

2. Check normalisation consistency. If documents are normalised and queries are not, ranking within one query survives (every score scales by the same constant) but thresholds and any cross-query comparison break.

3. If the metric is correct, look at chunking. A long chunk covers more topics, so it has a broader "surface" for matching many queries mediocrely. That is a genuinely different problem with a different fix — smaller chunks — and it is worth distinguishing, because the symptom is identical.

4. Consider whether it is actually correct. Sometimes long documents genuinely are the best answers, and the complaint is about diversity rather than relevance. That calls for result diversification or deduplication by source, not a metric change.

I would settle this with a measurement rather than a debate: score the same eval set under cosine and under dot-on-raw, and compare recall and mean result length. If cosine improves recall and shortens results, it was the metric.

Senior: Design the normalisation and metric strategy for a production retrieval system.

The goal is that the metric is unambiguous, verified, and impossible to get wrong accidentally in a codebase that several people touch.

1. Normalise at ingestion, unconditionally, in one place. A single embed() function used by both the ingestion job and the query path, which normalises and returns unit vectors. Two code paths embedding independently is how prefix and normalisation mismatches happen months later:

def embed(texts: list[str], *, role: str) -> np.ndarray:
    prefixed = [f"{PREFIX[role]}{t}" for t in texts]
    v = MODEL.encode(prefixed, normalize_embeddings=True)
    assert np.allclose(np.linalg.norm(v, axis=1), 1.0, atol=1e-5)
    return v

2. Use inner product as the index metric, since the vectors are normalised. It is the fastest path and computes cosine exactly. In pgvector that means vector_ip_ops and the <#> operator, with the negation handled in one query helper rather than at every call site.

3. Record the metric and normalisation convention as index metadata, alongside the model name and version. A mixed index is then detectable instead of silently degraded — and this is the same metadata that makes a model migration safe.

4. Pin the direction with a test that runs in CI:

def test_self_match_ranks_first():
    doc = "Postgres streaming replication lag"
    store.add(doc)
    results = store.search(doc, k=3)
    assert results[0].text == doc
    assert results[0].score > results[1].score      # pins sort direction too

This single test catches sign inversions, operator/index-class mismatches, and a normalisation change made by someone else later. All three are otherwise silent.

5. Verify the index is actually being used. In pgvector, querying with an operator the index was not built for does not error — it falls back to a sequential scan. Correct results, 500× slower. An EXPLAIN assertion in the test suite, or a latency alert, catches it:

EXPLAIN SELECT id FROM chunks ORDER BY embedding <#> $1 LIMIT 10;
--  Index Scan using chunks_embedding_idx     ← must not say "Seq Scan"

6. Derive thresholds empirically and store them with the model. Score known-relevant and known-irrelevant pairs, put the cutoff between the distributions, and treat it as configuration that changes when the model changes — never as a constant in the code.

The exception I would document explicitly: if we ever deliberately encode a popularity or quality signal in vector magnitude for recommendations, that subsystem opts out of normalisation, and the reason is written down. Unintentional magnitude sensitivity is a bug; intentional magnitude sensitivity is a design choice, and the difference must be visible in the code.

Senior: A refactor made vector search 500× slower but results are still correct. What happened?

"Correct but catastrophically slower" points at the index no longer being used, rather than at the index being wrong. In pgvector the commonest cause is an operator that does not match the index's operator class.

1. Confirm with EXPLAIN:

EXPLAIN ANALYZE SELECT id FROM chunks ORDER BY embedding <-> $1 LIMIT 10;
  Limit  (cost=... rows=10)
    ->  Sort  (cost=...)
          ->  Seq Scan on chunks  (rows=2400000)      ← the smoking gun

A sequential scan over every vector gives exactly the right answer — it is brute-force exact kNN — and takes as long as brute force takes.

2. Find the mismatch. HNSW indexes in pgvector are built for one distance function:

CREATE INDEX ... USING hnsw (embedding vector_cosine_ops);   -- serves <=> only
CREATE INDEX ... USING hnsw (embedding vector_ip_ops);       -- serves <#> only
CREATE INDEX ... USING hnsw (embedding vector_l2_ops);       -- serves <-> only

If someone changed the query from <=> to <-> — perhaps while "simplifying" the scoring, or because L2 read more naturally — the index is silently bypassed. There is no warning and no error; the planner simply has no usable index for that ordering.

3. Rule out the other silent-fallback causes, which have the same signature:

CauseCheck
Operator/opclass mismatchCompare the query operator to the index definition
A WHERE clause the planner prefers to filter onEXPLAIN shows a different index chosen
Missing LIMITHNSW is only used for top-k ordering
Dimension change without rebuildingIndex invalid; check pg_index.indisvalid
Query vector passed as text, not vectorImplicit cast can defeat the index
hnsw.ef_search unset after a session changeSlower but still indexed — different symptom

4. Fix and prevent. Either restore the original operator or add an index with the matching operator class — and note that changing the metric means a full index rebuild, which on a large table is a maintenance window, so restoring the operator is usually the right immediate action.

5. Make it impossible to regress silently. I would add an EXPLAIN-based test asserting the plan contains an index scan, plus a p95 latency alert on the search path. The deeper lesson is that a system whose failure mode is "correct but slow" needs latency assertions, because correctness tests will never catch it — and it is precisely the kind of regression that ships on a Friday and is noticed the following week.

2 (easy): Determine what your tools return: similarity or distance.
Solution

The reliable method is to compare something with itself — the answer must be the extreme value:

$ python3 - <<'EOF'
import numpy as np

IndexFlatIP : 1.0   ← 1.0, similarity, sort DESC
IndexFlatL2 : 0.0   ← 0.0, SQUARED distance, sort ASC

Turn this into a permanent test:

5 (hard): Build a metric-safe search wrapper that cannot be used incorrectly.
Solution

The design goal: make the ambiguous parts impossible to get wrong at the call site.

$ python3 - <<'EOF'
from dataclasses import dataclass
from enum import Enum
import numpy as np

class Metric(Enum):
    COSINE = "cosine"          # normalised vectors, dot product internally
    L2     = "l2"
    DOT    = "dot"             # deliberate: magnitude is meaningful

@dataclass(frozen=True)
class Hit:
    id: str
    similarity: float          # ALWAYS higher-is-better, whatever the metric
    text: str

class SafeStore:
    def __init__(self, metric: Metric = Metric.COSINE):
        self.metric = metric
        self.normalise = metric is Metric.COSINE
        self.ids, self.texts, self.vecs = [], [], []

    def _prep(self, v):
        v = np.asarray(v, dtype=np.float32)
        if self.normalise:
            n = np.linalg.norm(v)
            if n == 0: raise ValueError("zero vector cannot be normalised")
            v = v / n
        return v

    def add(self, id_, text, vector):
        self.ids.append(id_); self.texts.append(text)
        self.vecs.append(self._prep(vector))

    def search(self, vector, k=5, min_similarity=None):
        V, q = np.vstack(self.vecs), self._prep(vector)
        if self.metric in (Metric.COSINE, Metric.DOT):
            sims = V @ q                                   # higher is better
        else:                                              # L2 → convert to similarity
            sims = -np.linalg.norm(V - q, axis=1)          # negate: higher is better
        order = np.argsort(-sims)[:k]
        hits = [Hit(self.ids[i], float(sims[i]), self.texts[i]) for i in order]
        if min_similarity is not None:
            hits = [h for h in hits if h.similarity >= min_similarity]
        return hits
EOF

The invariant: Hit.similarity is always higher-is-better, regardless of the underlying metric. Callers never see a distance and never have to know the sort direction.

Verify the invariant holds for every metric:

    for k, v in docs.items(): s.add(k, f"text of {k}", v)
    hits = s.search(docs["d7"], k=3)
    assert hits[0].id == "d7", f"{metric}: self-match not first"
    assert hits[0].similarity >= hits[1].similarity >= hits[2].similarity
    print(f"{metric.value:7} ✓ self-match first, scores descending "
          f"({hits[0].similarity:+.3f} > {hits[1].similarity:+.3f})")
EOF

l2      ✓ self-match first, scores descending (+0.000 > -11.412)

Note the L2 scores are negative — that is intentional, and callers still just sort descending.

    hits = 0
    for q, gold in evalset:
        top = set(np.argsort(-scores_fn(q))[:k])
        hits += len(top & set(gold)) / len(gold)
    return hits / len(evalset)

print(f"dot on raw    recall@10 = {recall_at_k(dot_raw, EVAL):.3f}")

3. But keep the speed, by normalising:

$ python3 - <<'EOF'
import numpy as np, time
rng = np.random.default_rng(0)
V = rng.standard_normal((500_000, 384), dtype=np.float32)
Vn = V / np.linalg.norm(V, axis=1, keepdims=True)
q = rng.standard_normal(384).astype(np.float32); qn = q/np.linalg.norm(q)

for label, fn in [
    ("dot on normalised (= cosine)", lambda: Vn @ qn),
    ("cosine computed each query  ", lambda: (V @ q)/(np.linalg.norm(V,axis=1)*np.linalg.norm(q))),
]:
    t0 = time.perf_counter(); [fn() for _ in range(5)]
    print(f"{label}  {(time.perf_counter()-t0)/5*1000:6.1f} ms")

cosine computed each query     341.8 ms

Normalising once at ingestion gives cosine's quality at dot product's speed — 3.7× faster than computing cosine per query, and identical results.

4. Handle the popularity requirement separately, not through the metric:

# WRONG: encode popularity in the norm — it distorts semantic similarity
v_item = v_semantic * popularity_factor

# RIGHT: keep the metric clean, blend scores after retrieval
final = 0.85 * cosine_similarity + 0.15 * normalised_popularity

Blending after retrieval keeps the two signals independently tunable and inspectable. Encoding popularity in the magnitude makes it invisible, untunable, and entangled with the semantics.

5. The recommendation:

DecisionChoiceReason
NormalisationAt ingestion, alwaysRemoves a 15-point recall loss from length bias
Index metricInner productFastest path, computes exact cosine on unit vectors
PopularityPost-retrieval blendIndependently tunable; keeps similarity interpretable
VerificationSelf-match test + EXPLAIN assertionCatches sign and index-usage regressions
ThresholdDerived from eval distributions, stored with the modelNot transferable across metrics or models

The general principle worth taking away: "fastest metric" is the wrong question. Normalise, and the fastest metric and the correct metric become the same computation — after which any remaining ranking signals belong in an explicit, tunable scoring layer rather than smuggled into vector magnitudes.

🎯 Key Takeaways

  • Cosine measures angle only, dot product measures angle and magnitude, Euclidean measures straight-line distance — for text, direction carries the meaning.
  • On unit vectors, cosine similarity equals dot product exactly, and L2 distance is a strictly decreasing function of it — so all three rank identically.
  • Normalise at ingestion and use inner product: cosine semantics at the fastest index path, with no division or square root per comparison.
  • Dot product on unnormalised text vectors ranks partly by length, so verbose documents dominate — a metric bug that looks like a model problem.
  • Similarity is higher-is-better, distance is lower-is-better, and libraries disagree about which they return.
  • pgvector's <#> returns the negative inner product, so a perfect match scores −1 and naive threshold filters invert.
  • One test — search for a document's exact text and assert it ranks first, with scores descending — catches sign errors, metric mismatches and later normalisation changes.
  • Some models normalise internally (BGE) and some do not (MiniLM); check the norm once rather than assuming.
  • Normalise consistently on both sides: ranking survives a mismatch but thresholds and cross-query comparison break silently.
  • ANN indexes are metric-specific — in pgvector, querying with the wrong operator silently falls back to a sequential scan: correct results, hundreds of times slower.
  • Assert on the query plan in CI, because a "correct but slow" regression is invisible to correctness tests.
  • Squared L2 ranks identically to L2 and avoids a square root, which is why many libraries return it and scores look unfamiliar.
  • Similarity scores are not probabilities and not comparable across models — derive thresholds from your own relevant/irrelevant distributions.
  • Ranking signals like popularity belong in an explicit post-retrieval blend, never encoded in vector magnitude.
