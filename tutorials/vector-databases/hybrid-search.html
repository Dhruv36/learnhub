Metadata Filtering & Hybrid Search The Landscape

What you'll master: the three filtering strategies — pre-, post- and during-traversal — and the arithmetic that says which one a given selectivity demands; why a filtered HNSW search can silently return three results instead of ten and how filterable graphs avoid it; why dense embeddings fail on exact identifiers, rare terms and negation, and why BM25 still beats them there; how to combine two rankings whose scores are not comparable, using Reciprocal Rank Fusion and when a weighted score is defensible instead; and how to build and tune a hybrid retriever that measurably beats either half. Prerequisites: HNSW Deep Dive, Dedicated Vector Stores.

Part 1 — Why Filtering Breaks ANN Search

Filtering looks like the most ordinary feature in a database. In a vector index it is the hardest one, because the index was built to answer exactly one question — "what is near this point?" — and a filter asks a different one.

The problem is structural. HNSW finds neighbours by walking a graph whose edges were chosen at build time, when nobody knew what filter you would apply. Restrict the result set to tenant = 57 and the graph's edges still point wherever they pointed — mostly at vectors that are no longer eligible.

    graph neighbourhood of the query          eligible under tenant=57
    ────────────────────────────────          ────────────────────────
         ○ ○ ○ ○ ○ ○ ○ ○ ○ ○                        ●
         ○ ○ ○ ● ○ ○ ○ ○ ○ ○                              ●
         ○ ○ ○ ○ ○ ○ ● ○ ○ ○            ●
         ○ ○ ● ○ ○ ○ ○ ○ ○ ○                    ●
         ○ = filtered out (99.95%)     ● = eligible (0.05%)

    the traversal walks through ○ nodes to reach ● nodes — or gives up first

There are only three ways to resolve this, and the whole subject is knowing which one applies:

StrategyHow it worksCorrect whenFails when
Post-filterANN search for k′ > k, then drop non-matchingFilter is broad (>10% pass)Selective filters — returns too few or none
Pre-filterResolve the filter first, then exact-scan the subsetFilter is narrow (<1% pass)Broad filters — the subset is the whole corpus
Filter during traversalSkip ineligible nodes while walking the graphEverywhere in betweenVery narrow filters — the graph becomes disconnected

Post-filtering's cost is exactly 1/selectivity, and that number decides everything. To return k results after filtering, you must fetch roughly k/s candidates where s is the fraction that passes:

want k = 10 results

selectivity 50%   →  fetch ~20    candidates    fine
selectivity 10%   →  fetch ~100   candidates    fine
selectivity  1%   →  fetch ~1,000 candidates    getting slow
selectivity 0.1%  →  fetch ~10,000 candidates   slower than scanning the 0.1% exactly
selectivity 0.05% →  fetch ~20,000 candidates   ← and HNSW recall degrades badly at that k

The design consequence: there is a crossover point where scanning the filtered subset exactly is both faster and more accurate than approximating over the whole corpus. With 10M vectors and a 0.05% filter, the eligible subset is 5,000 vectors — a brute-force scan of 5,000 vectors takes about 2 ms and has recall 1.0. No approximation can beat exact-and-fast.

🔑 This is precisely the choice Postgres's planner makes automatically — vector index for broad filters, btree plus exact scan for narrow ones — and it is why pgvector often beats dedicated stores on filtered workloads despite a less specialised index. In a dedicated store the same decision exists, but you usually have to make it yourself, per query, in application code.

Part 2 — Filtered Traversal, and How It Fails

The middle strategy is what stores like Qdrant mean by "filterable HNSW": the filter is evaluated during the graph walk, so ineligible nodes are traversed but never enter the result heap.

def search_filtered(query, entry_point, ef, is_eligible):
    candidates, visited, results = [entry_point], {entry_point}, []
    while candidates:
        node = pop_closest(candidates, query)
        if worse_than_worst(node, results, ef):
            break
        for nb in node.neighbours:                  # walk the FULL graph
            if nb in visited:
                continue
            visited.add(nb)
            candidates.push(nb)
            if is_eligible(nb):                     # but only collect eligible ones
                results.push(nb)
    return top_k(results)

This gets the recall right where post-filtering does not, because the search keeps going until it has found ef eligible candidates rather than stopping after ef candidates of any kind. The cost is that it may traverse far more nodes to get there.

The failure mode is graph disconnection. Below some selectivity, the eligible nodes are so sparse that they are not reachable from one another through eligible-or-not edges within the search budget — the walk exhausts its candidate list among ineligible nodes and returns early:

10M vectors, HNSW m=16, ef=128, filter selectivity varied:

  selectivity   nodes visited   results returned   recall@10   latency
  ───────────   ─────────────   ────────────────   ─────────   ───────
      50%             310              10            0.98       2.4 ms
      10%             820              10            0.97       3.1 ms
       1%           4,100              10            0.94       8.7 ms
     0.1%          28,400              10            0.81      41 ms
    0.05%          61,200               6            0.58      93 ms   ← degrading badly
    0.01%         140,000               2            0.19     210 ms   ← unusable

Read the "results returned" column, not just recall. At 0.05% the store returned six results for a top-10 request, with no error and no warning. A RAG pipeline consuming that silently loses 40% of its context, and the answer quality drops for reasons that never appear in the retrieval metrics.

So real systems switch strategies by selectivity, and the switch is the thing you have to build if the store does not:

def search(query_vec, filters, k=10):
    est = estimate_selectivity(filters)          # from field cardinality stats

    if est < 0.01:                               # narrow: exact scan of the subset
        ids = metadata_index.lookup(filters)     # e.g. an inverted index on payload
        return exact_topk(query_vec, ids, k)     # recall 1.0, and fast because small

    if est > 0.20:                               # broad: ANN then filter
        return post_filter(ann_search(query_vec, k * 3), filters, k)

    return filtered_traversal(query_vec, filters, k)   # the middle

Estimating selectivity is the part people skip, and it is not hard: keep approximate cardinality per filter field, multiply for conjunctions (accepting the independence assumption), and correct with observed values over time. A rough estimate is enough, because the strategies overlap comfortably — the boundaries are wide, not knife-edged.

One more option is worth knowing because it is often the best of all: partition by the filter. If nearly every query filters on tenant_id, build a separate index per tenant. The filter stops being a filter and becomes routing — no selectivity problem, no traversal penalty, and each index is small enough to search exhaustively. It costs you cross-tenant queries and works badly with a long tail of tiny tenants, but where it fits, it is strictly better than any filtering strategy.

Part 3 — Where Dense Retrieval Actually Fails

Embeddings capture meaning, which is exactly why they lose the parts of a query that are not meaning. This is not a quality problem to be fixed with a better model — it is inherent to compressing text into a few hundred floats.

QueryWhat dense retrieval doesWhy
ERR_CONN_4021Returns generic connection-error docsA rare token contributes almost nothing to the embedding
invoice #A-99183Returns other invoicesIdentifiers have no semantics to encode
Kubernetes 1.29 changelogMixes in 1.27, 1.28, 1.30Version numbers are near-identical in vector space
Contract without an arbitration clauseReturns contracts with arbitration clausesNegation is not represented; the topic dominates
Torvalds' 2003 email about BitKeeperReturns general BitKeeper historyConjunctions of rare specifics dilute in a single vector

BM25 gets every one of these right, because it does the opposite thing: it scores on exact term overlap, weighted so that rare terms count for more.

                    n - df(t) + 0.5              f(t,d) · (k₁ + 1)
BM25(q,d) =  Σ  ln ────────────────── · ─────────────────────────────────────
            t∈q        df(t) + 0.5       f(t,d) + k₁ · (1 - b + b · |d|/avgdl)
                    └──────────────┘     └───────────────────────────────────┘
                     IDF: rare terms          saturating term frequency,
                     dominate the score        normalised by length

Two properties matter for retrieval, and both are the mirror image of what dense retrieval gives you:

That last row is the honest statement of the trade. BM25 returns nothing for a paraphrase that shares no vocabulary; dense retrieval returns ten results for a query about something the corpus does not contain. The failures are complementary, which is the entire argument for combining them.

Part 4 — Fusing Two Rankings

Having two result lists is easy. Combining them is where hybrid search is usually got wrong, because the two scores are not comparable in any principled way.

cosine similarity:  bounded [-1, 1], typically clustered in 0.6–0.9 for a real corpus
BM25:               unbounded [0, ∞), depends on corpus size, term rarity, document length

  0.7 * cosine + 0.3 * bm25     ← adding a bounded number to an unbounded one

Score normalisation does not rescue this, though it is the usual first attempt. Min-max normalising per query makes the top result 1.0 and the bottom 0.0 in every query — including queries where the best BM25 hit was terrible. It manufactures confidence that was not there:

query A (good lexical match):   raw BM25 = [31.2, 28.4, 12.1]  → normalised [1.0, 0.89, 0.0]
query B (no lexical match):     raw BM25 = [ 2.1,  1.9,  1.8]  → normalised [1.0, 0.60, 0.0]
                                                                            ↑
                        a 2.1 and a 31.2 both become "1.0" — the signal is destroyed

Reciprocal Rank Fusion sidesteps the problem entirely by discarding the scores and using only the ranks, which are comparable by construction:

                        1
RRF(d) =  Σ    ──────────────────         k ≈ 60 by convention
        r∈rankers   k + rank_r(d)

rank 1  → 1/61 = 0.01639
rank 2  → 1/62 = 0.01613     ← differences between adjacent ranks are small
rank 10 → 1/70 = 0.01429
rank 50 → 1/110 = 0.00909    ← and shrink further down the list

The constant k is a damping term, and its role is worth understanding rather than copying: it flattens the difference between rank 1 and rank 2, so a document ranked #2 by both rankers beats one ranked #1 by a single ranker. Agreement across rankers outweighs a strong showing in one.

doc   dense rank   bm25 rank   RRF score                       result
────  ──────────   ─────────   ─────────────────────────       ──────
A         1           47       1/61 + 1/107 = 0.0258            3rd
B         3            2       1/63 + 1/62  = 0.0320            1st   ← agreed by both
C         2           12       1/62 + 1/72  = 0.0300            2nd

Doc A was the dense ranker's top hit and finishes third, because only one ranker liked it. That is RRF working as intended — and also its main weakness, since a document that only one ranker could find (an exact ID match, say) is penalised for the other's ignorance.

def rrf(rankings, k=60, weights=None):
    """rankings: list of lists of doc ids, best first."""
    weights = weights or [1.0] * len(rankings)
    scores = {}
    for ranking, w in zip(rankings, weights):
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + w / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

fused = rrf([dense_results, bm25_results], k=60, weights=[1.0, 0.7])
Fusion methodUse whenWeakness
RRFDefault — no tuning, no score comparability neededDiscards confidence; penalises single-ranker finds
Weighted normalised scoresYou have labelled data to fit the weightsNormalisation distorts; weights are corpus-specific
Learned fusion / rerankerRelevance is the product and you have judgementsCost, latency, and a model to maintain — see reranking
Convex combination on raw scoresEssentially neverThe scores are on incomparable scales

Tune k against your own data rather than accepting 60. Lower k sharpens the advantage of top ranks (closer to "trust the best ranker"); higher k flattens it (closer to "reward agreement"). The useful range is roughly 10–100, and the difference between k=20 and k=60 on a real corpus is typically worth a point or two of nDCG — small, but free.

❌ Blending raw or min-max-normalised scores with a hand-picked weight. 0.7·cosine + 0.3·bm25 adds numbers on incomparable scales, and per-query min-max normalisation makes every query's best result look equally confident — so a query with no lexical match at all contributes a spurious 1.0. The weights are then tuned by eye on a handful of queries and quietly overfit to them.

✅ Fuse on ranks with RRF, and only move to weighted scores if labelled data justifies it. Ranks are comparable by construction, RRF needs no per-corpus calibration, and it degrades gracefully when one ranker returns nothing useful. If you do want weights, fit them against judged relevance on a held-out query set and re-fit when the corpus changes.

Part 5 — Building the Hybrid Retriever

The complete shape, with filtering and fusion in their proper places:

                     query text
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
      embed → dense search      analyse → BM25 search
      (filter applied)          (filter applied)
              │                       │
         top-50 ids               top-50 ids
              └───────────┬───────────┘
                          ▼
                    RRF fusion (k=60)
                          │
                      top-20
                          │
                          ▼
               [optional] cross-encoder rerank
                          │
                       top-5 → LLM context

def hybrid_search(query, filters=None, k=10, candidates=50):
    dense = vector_store.search(embed(query), filter=filters, limit=candidates)
    lexical = text_index.search(query, filter=filters, limit=candidates)

    fused = rrf([[d.id for d in dense], [l.id for l in lexical]], k=60)
    return fused[:k]

Both branches must apply the same filter. Filtering only the dense side is a real and common bug: the lexical branch then contributes ineligible documents that survive fusion, and in a multi-tenant system that is a data leak, not a relevance problem.

Retrieve more candidates than you need — the standard mistake is fetching k from each branch. If both return only 10 and they agree on 7, fusion has 13 documents to choose a top-10 from, and the benefit of hybrid retrieval mostly evaporates. Fetch 5–10× k per branch; the extra ANN work is cheap relative to the LLM call downstream.

candidates per branch    recall@10 after fusion    added latency
─────────────────────    ──────────────────────    ─────────────
        10                       0.79                 +0 ms
        25                       0.88                 +1 ms
        50                       0.93                 +3 ms       ← the knee
       100                       0.945                +7 ms
       200                       0.948                +18 ms

Run the two branches concurrently. They are independent, so hybrid search should cost roughly max(dense, lexical) rather than their sum — and the embedding call usually dominates both:

import asyncio

async def hybrid_search(query, filters=None, k=10, candidates=50):
    vec = await embed_async(query)                      # ~15 ms, the real cost
    dense, lexical = await asyncio.gather(
        vector_store.search_async(vec, filter=filters, limit=candidates),   # ~4 ms
        text_index.search_async(query, filter=filters, limit=candidates),   # ~6 ms
    )
    return rrf([[d.id for d in dense], [l.id for l in lexical]], k=60)[:k]

Sparse vectors are the third option, and they blur the distinction usefully. Models like SPLADE produce a high-dimensional sparse vector whose non-zero dimensions are vocabulary terms — including terms not present in the text, learned by the model as expansions. That gives exact-term matching plus a degree of semantic expansion, in one index, and stores that support sparse vectors can fuse them natively. The cost is another model in the ingestion path and larger indexes; the benefit is that it fixes BM25's vocabulary-mismatch failure without giving up its precision on rare terms.

Part 6 — Measuring Whether It Helped

Hybrid search is usually adopted on the strength of an argument rather than a measurement, which is how teams end up maintaining two indexes for a result they never verified.

The measurement needs three arms and query-class segmentation, because the aggregate number reliably hides the effect:

                        overall   paraphrase   exact-ID   rare-term   negation
                        ───────   ──────────   ────────   ─────────   ────────
dense only               0.72        0.89        0.21       0.34        0.31
BM25 only                0.61        0.38        0.98       0.91        0.44
hybrid (RRF)             0.84        0.86        0.94       0.88        0.41

Three things in that table are worth stating explicitly. Hybrid is best overall, but it is slightly worse than dense alone on paraphrase queries — fusion costs a little where one ranker was already right. It recovers nearly all of BM25's exact-ID performance, which is the main reason to adopt it. And nothing fixes negation: 0.41 is barely better than either half, because neither retriever represents "without". That is a query-understanding problem, not a retrieval one.

MetricWhat it answersWhen it is the right one
recall@kDid the relevant chunk make it into the context?The primary RAG metric — the LLM cannot use what it never saw
nDCG@kAre the good results near the top?When position matters — long contexts bury later chunks
MRRHow high is the first relevant result?Single-answer lookups
End-to-end answer qualityDid retrieval changes help the user?The only one that ultimately matters

Recall@k is the metric to optimise for RAG, and it is worth being precise about why: ranking within the retrieved set matters far less than the LLM seeing the right chunk at all. Moving the answer from position 5 to position 2 changes little; moving it from position 12 to position 8 with k=10 changes everything. That asymmetry is why reranking is applied after a generous retrieval rather than instead of one — and why the next lesson pairs a wide net with a precise second pass.

Interview Questions

Beginner: What is hybrid search and why would you use it instead of pure vector search?

Hybrid search runs a dense (embedding) retriever and a sparse/lexical retriever such as BM25 over the same corpus, then fuses the two ranked lists into one. You use it because the two methods fail in opposite directions, so their union is much stronger than either.

Dense retrieval understands meaning and therefore handles paraphrase: "how do I stop the pod from restarting" finds a document titled "CrashLoopBackOff explained" despite zero shared vocabulary.

It fails on anything that is not meaning:

QueryDense result
ERR_CONN_4021Generic connection-error docs — the rare token barely affects the embedding
invoice #A-99183Other invoices — identifiers carry no semantics
Kubernetes 1.291.27, 1.28 and 1.30 mixed in — version numbers sit almost on top of each other

BM25 gets all of those right, because it scores exact term overlap weighted by rarity — a token appearing in 3 of 2M documents dominates the score. What it cannot do is match a paraphrase that shares no words, and it returns nothing at all when there is no term overlap.

So: dense always returns something, sometimes irrelevant; lexical returns nothing unless words match, but is precise when they do. Fusing them covers both, which in practice is worth 10–15 points of recall on a mixed query workload — concentrated almost entirely in the exact-identifier and rare-term classes.

Beginner: Why can a filtered vector search return fewer results than you asked for?

Because the filter is applied to candidates the index produced without knowing about the filter, and there may not be k eligible ones among them.

With post-filtering the mechanism is direct: fetch 100 nearest neighbours, discard those that fail the filter, return what is left. If the filter keeps 0.05% of the corpus, roughly zero of the 100 survive.

ANN top-100 → filter tenant=57 → 0 survive → return 0 results (asked for 10)

With filtered traversal it is subtler. The search walks the graph collecting eligible nodes, but the walk has a budget — it stops when the candidate queue is exhausted or the beam finds nothing better. If eligible nodes are sparse, the walk runs out of graph before it finds ten:

selectivity 0.05%:  visited 61,200 nodes → 6 eligible found → returns 6

The dangerous part is that this is not an error. The API returns 200 with six results; nothing in the response says "I gave up". A RAG pipeline consuming it loses 40% of its context and produces a worse answer for reasons invisible in the retrieval logs.

So assert on it: alert when len(results) < k for a query that should have had matches. The fix is usually to pre-filter instead — resolve the filter through a metadata index and exact-scan the (small) eligible set, which gives recall 1.0 and is fast precisely because the set is small.

Mid: Explain pre-filtering, post-filtering and filtered traversal, and how you would choose between them.

They are three answers to the same problem — the ANN index was built without knowledge of the filter — and the choice is driven almost entirely by selectivity.

StrategyMechanismCostCorrect when
Post-filterANN for k′, then drop non-matchingMust fetch ~k/s candidatess > ~10%
Pre-filterResolve filter, exact-scan the subsetO(size of subset)s < ~1%
During traversalSkip ineligible nodes while walkingVisits many more nodesIn between

The arithmetic that decides it: post-filtering must over-fetch by 1/s. At 50% selectivity that is 20 candidates for 10 results — nothing. At 0.1% it is 10,000, and HNSW recall degrades at that k anyway, so you pay more and get less.

Meanwhile pre-filtering gets cheaper as the filter narrows, which is the key insight — the two strategies have opposite cost curves, so there is always a crossover. With 10M vectors and a 0.05% filter the eligible set is 5,000 vectors: a brute-force scan is ~2 ms with recall exactly 1.0. Nothing approximate beats that.

In practice I would implement the switch explicitly:

s = estimate_selectivity(filters)          # cardinality stats per field
if   s < 0.01: exact_topk(vec, metadata_index.lookup(filters), k)
elif s > 0.20: post_filter(ann(vec, k*3), filters, k)
else:          filtered_traversal(vec, filters, k)

The estimate does not need to be good — the strategies overlap comfortably, so the boundaries are wide. A per-field cardinality table with the independence assumption for conjunctions is enough.

And the strategy that beats all three where it applies is partitioning: if nearly every query filters on tenant, build one index per tenant. The filter becomes routing, and the selectivity problem disappears entirely.

Mid: How does Reciprocal Rank Fusion work, and why not just add the two scores together?

RRF scores each document by the sum of the reciprocals of its ranks in each result list:

RRF(d) = Σ_r  1 / (k + rank_r(d)),     k ≈ 60

Adding raw scores does not work because they are not on comparable scales. Cosine similarity is bounded in [-1, 1] and clusters in 0.6–0.9 on a real corpus; BM25 is unbounded and depends on corpus size, term rarity and document length. 0.7·cosine + 0.3·bm25 is adding a bounded quantity to an unbounded one, and the weights are meaningless.

Per-query min-max normalisation is worse than it looks, and it is the usual first attempt:

query A (strong lexical match):  BM25 [31.2, 28.4, 12.1] → [1.0, 0.89, 0.0]
query B (no lexical match):      BM25 [ 2.1,  1.9,  1.8] → [1.0, 0.60, 0.0]

A score of 2.1 and a score of 31.2 both become 1.0. The normalisation has manufactured confidence for query B that never existed, and the fusion now trusts a bad lexical result as much as a great one.

Ranks are comparable by construction, so RRF needs no calibration at all — which is why it works across corpora and survives a model change without re-tuning.

The constant k is a damping term that rewards agreement:

doc   dense   bm25    RRF
A       1      47     1/61 + 1/107 = 0.0258   → 3rd
B       3       2     1/63 + 1/62  = 0.0320   → 1st   ← both rankers liked it

Doc A topped the dense ranking and still lost, because only one ranker found it. That is usually right, and it is also RRF's weakness: a document only one ranker can find — an exact ID match — is penalised for the other's ignorance. When that matters, weight the rankers (w_r / (k + rank)), or move to a cross-encoder reranker which scores query and document jointly and sidesteps fusion altogether.

Senior: Design filtered hybrid search for a multi-tenant knowledge base with highly variable tenant sizes.

The defining constraint is the variance: if the largest tenant is 40% of the corpus and the smallest is 200 documents, no single strategy is correct for both. So the design is a router, and the routing key is tenant size.

1. Partition by tenant where it pays, and only there. Every query filters on tenant, so for large tenants I would give each its own collection — the filter becomes routing, and the selectivity problem disappears:

Tenant sizeLayoutRetrieval strategy
> 1M chunksDedicated collectionANN, no filter needed
10k–1MDedicated collectionANN, no filter needed
< 10kShared "small tenants" collectionPre-filter + exact scan

The small-tenant pool is the important detail: thousands of tiny collections would be operationally awful (per-collection memory overhead, index build churn), and they do not need an ANN index at all — a brute-force scan of 8,000 vectors is ~3 ms with recall 1.0.

2. Enforce tenancy below the retrieval layer. A tenant filter that is applied by application code is one forgotten parameter away from a cross-tenant leak, and it must be applied to both branches:

async def search(tenant_id, query, k=10):
    coll = route(tenant_id)                    # collection, not a filter, when possible
    flt  = None if coll.is_dedicated else {"tenant_id": tenant_id}
    vec  = await embed(query)
    dense, lexical = await asyncio.gather(
        coll.vector_search(vec,  filter=flt, limit=50),
        coll.text_search(query,  filter=flt, limit=50),   # SAME filter — non-negotiable
    )
    return rrf([ids(dense), ids(lexical)], k=60)[:k]

Filtering only the dense branch is the bug I would specifically test for, because it is easy to write, produces plausible results, and leaks another tenant's documents through the lexical side. An automated test that queries as tenant A for a string unique to tenant B belongs in CI.

3. Fetch generously, fuse on ranks. 50 candidates per branch (5× k) — fusion needs material to work with, and 10-per-branch fusion is barely better than either branch alone. RRF rather than weighted scores, because with thousands of tenants there is no per-corpus calibration that could possibly hold across all of them.

4. Run the branches concurrently, so hybrid costs max(dense, lexical) rather than the sum. The embedding call dominates anyway.

5. Handle the failure modes explicitly: alert when a query returns fewer than k results, monitor tenant size to trigger promotion from the shared pool to a dedicated collection, and cache embeddings for repeated queries. Promotion is a re-index of one tenant, which is cheap precisely because source text lives in the primary database.

What I would not do is one giant collection with a tenant filter and a single retrieval strategy. It is the simplest thing to build and it fails at both ends — post-filtering returns nothing for small tenants, and filtered traversal is slow for them while being unnecessary for large ones.

Senior: Your team wants to add hybrid search. How would you evaluate whether it actually helps, and what would you expect to find?

I would treat it as a hypothesis with a specific predicted shape, because "hybrid is better" is unfalsifiable and the aggregate number hides the effect that matters.

1. Build a query set that reflects reality, segmented by class. This is the step that determines whether the evaluation is worth anything:

3. Read the table honestly, including the parts that argue against the change. Hybrid is +12 points overall — but it is 0.03 worse than dense on paraphrase queries, because fusion costs a little where one ranker was already right. If 90% of my traffic were paraphrase, hybrid would be a net loss, and that is a genuine possibility worth checking before committing to a second index.

And negation does not improve. 0.41 versus 0.44 for BM25 alone: neither retriever represents "without", so no amount of fusion helps. That is a query-understanding problem — parse the negation into a filter — and it is worth naming explicitly so the team does not expect hybrid to solve it.

4. Confirm end-to-end, not just retrieval. Retrieval recall can improve while answer quality does not, usually because the extra recall arrived at positions the model does not attend to. An LLM-judged answer-quality comparison on the same query set is the check that matters.

5. Price it. A second index means more ingestion work, more memory, more operational surface, and roughly +3 ms of latency if the branches run concurrently. For a 12-point recall gain concentrated in identifier queries, that is clearly worth it for a technical-support corpus and plausibly not worth it for a corpus of narrative prose where identifiers never appear.

My expectation before running any of this is that hybrid wins overall, that essentially the entire gain comes from the exact-ID and rare-term classes, and that paraphrase regresses slightly. Stating the prediction up front is what makes the evaluation informative — if the results come out differently, something about the corpus or the embedding model is worth understanding.

Solution 
def rrf(rankings, k=60, weights=None):
    weights = weights or [1.0] * len(rankings)
    scores = {}
    for ranking, w in zip(rankings, weights):
        for rank, doc in enumerate(ranking, start=1):
            scores[doc] = scores.get(doc, 0.0) + w / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])

C  0.02997      ← dense #2, bm25 #3
A  0.02580      ← dense #1 but bm25 #5

A was the dense ranker's top hit and finished third, because only one ranker rated it highly. Agreement outweighs a single strong opinion — that is RRF's core behaviour.

def post_filter(q, X, mask, k, candidates):
    """Simulate ANN + post-filter: take top-`candidates` overall, then filter."""
    top = np.argpartition(-(X @ q), candidates)[:candidates]
    top = top[np.argsort(-(X[top] @ q))]
    return [i for i in top if mask[i]][:k]

    """Exact scan of the eligible subset."""
    idx = np.flatnonzero(mask)
    sims = X[idx] @ q
    return idx[np.argsort(-sims)[:k]].tolist()

5 (hard): Build a selectivity-aware filtered search router.
Solution

The goal is a retriever that picks its filtering strategy per query, with the estimate derived from maintained statistics rather than guessed.

from collections import Counter
import numpy as np, time

class SelectivityStats:
    """Per-field value cardinality, maintained on ingest."""
    def __init__(self):
        self.total = 0
        self.fields = {}                       # field -> Counter(value -> count)

    def add(self, payload):
        self.total += 1
        for f, v in payload.items():
            self.fields.setdefault(f, Counter())[v] += 1

    def estimate(self, filters):
        """Product of per-field selectivities (independence assumption)."""
        s = 1.0
        for f, v in filters.items():
            c = self.fields.get(f, {}).get(v, 0)
            s *= (c / self.total) if self.total else 1.0
        return s

class Router:
    NARROW, BROAD = 0.01, 0.20

    def __init__(self, X, payloads, stats):
        self.X, self.payloads, self.stats = X, payloads, stats

    def _mask(self, filters):
        return np.array([all(p.get(f) == v for f, v in filters.items())
                         for p in self.payloads])

    def search(self, q, filters, k=10):
        s = self.stats.estimate(filters)
        if s < self.NARROW:
            return "pre-filter", self._pre(q, filters, k)
        if s > self.BROAD:
            return "post-filter", self._post(q, filters, k, candidates=k * 5)
        return "traversal", self._post(q, filters, k, candidates=int(k / max(s, 1e-6) * 2))

    def _pre(self, q, filters, k):
        idx = np.flatnonzero(self._mask(filters))
        if len(idx) == 0: return []
        return idx[np.argsort(-(self.X[idx] @ q))[:k]].tolist()

    def _post(self, q, filters, k, candidates):
        candidates = min(candidates, len(self.X))
        top = np.argpartition(-(self.X @ q), candidates - 1)[:candidates]
        top = top[np.argsort(-(self.X[top] @ q))]
        mask = self._mask(filters)
        return [int(i) for i in top if mask[i]][:k]

🎯 Key Takeaways

  • An ANN index is built without knowledge of your filters, so filtering is the hardest thing to add to it — the graph's edges point at vectors the filter has excluded.
  • Three strategies exist: post-filter (broad filters), pre-filter and exact-scan (narrow filters), and filter-during-traversal (in between).
  • Post-filtering costs 1/selectivity — 10 results at 0.1% selectivity needs ~10,000 candidates, which is slower and less accurate than scanning the eligible subset exactly.
  • Pre-filtering gets cheaper as the filter narrows, so the two strategies have opposite cost curves and a crossover always exists.
  • Filtered HNSW can return fewer than k results with no error — a silent context loss. Alert when len(results) < k.
  • Estimate selectivity from per-field cardinality and switch strategy per query; the boundaries are wide, so a rough estimate suffices.
  • Where a filter appears in nearly every query, partition by it — the filter becomes routing and the problem disappears.
  • Dense retrieval fails on exact identifiers, rare terms, version numbers and negation, because those are not "meaning" and do not survive compression into a single vector.
  • BM25 fixes the first three via IDF weighting, and scores 0 when no terms overlap — the opposite failure mode to dense retrieval's always-returning-something.
  • Cosine and BM25 scores are not comparable (bounded vs unbounded), and per-query min-max normalisation manufactures confidence that was never there.
  • Reciprocal Rank Fusion fuses on ranks instead of scores, needs no calibration, and rewards agreement between rankers; k≈60 is a damping constant worth sweeping but rarely worth much.
  • Apply identical filters to both branches — filtering only the dense side is a tenancy leak, not just a relevance bug.
  • Fetch 5–10× k candidates per branch; fusing two lists of 10 leaves fusion almost nothing to work with.
  • Run the branches concurrently: hybrid should cost max(dense, lexical), not their sum.
  • Sparse learned vectors (SPLADE-style) give term-level matching plus semantic expansion in one index, at the cost of another model in the ingestion path.
  • Measure three arms segmented by query class — the aggregate hides that essentially all the gain is in exact-ID and rare-term queries, and that paraphrase regresses slightly.
  • recall@k is the primary RAG retrieval metric: the model cannot use a chunk it never saw, and position within the retrieved set matters far less.
  • Nothing here fixes negation — that is query understanding, and it needs a rewriting or filter-extraction step upstream of retrieval.
