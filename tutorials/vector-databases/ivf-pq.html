IVF, PQ & Quantisation Indexing & Search

What you'll master: how inverted-file partitioning turns a full scan into a scan of a few cells and why that fails at cell boundaries, how product quantisation compresses a 6 KB vector into 64 bytes and still ranks usefully, the asymmetric distance computation that makes quantised search fast, why every quantised index needs a full-precision reranking pass, when binary quantisation's 32× compression is enough on its own, and how to pick nlist, nprobe and code size from your own constraints. Prerequisites: HNSW Deep Dive.

Part 1 — IVF: Search Fewer Vectors

The inverted file index partitions the corpus with k-means, then searches only the cells nearest the query. It is the simplest idea in ANN and it scales further than anything else.

  BUILD
    1. k-means the corpus into nlist centroids
    2. assign every vector to its nearest centroid  →  nlist "inverted lists"

  QUERY
    1. compare the query to all nlist centroids       (cheap: nlist ≪ n)
    2. pick the nprobe nearest cells
    3. scan every vector in those cells               (the actual work)
    4. return top k

  n = 10,000,000   nlist = 4,096   nprobe = 16

  centroid comparisons :      4,096
  vectors scanned      : 16 × (10M / 4096) ≈ 39,000
  total                ≈     43,000  vs  10,000,000  →  230x less work

$ pip install faiss-cpu
$ python3 - <<'EOF'
import numpy as np, faiss, time
rng = np.random.default_rng(0)
n, d, k = 500_000, 128, 10
c = rng.standard_normal((80, d))
V = (c[rng.integers(0,80,n)] + rng.standard_normal((n,d))*0.3).astype('float32')
faiss.normalize_L2(V)
Q = V[rng.choice(n, 200, replace=False)].copy()

flat = faiss.IndexFlatIP(d); flat.add(V)
t0=time.perf_counter(); _, truth = flat.search(Q, k); ex=(time.perf_counter()-t0)/len(Q)*1000

quant = faiss.IndexFlatIP(d)
ivf = faiss.IndexIVFFlat(quant, d, 2048, faiss.METRIC_INNER_PRODUCT)
t0=time.perf_counter(); ivf.train(V); ivf.add(V); build=time.perf_counter()-t0
print(f"exact: {ex:.2f} ms/query   IVF build: {build:.1f}s\n")
print(f"{'nprobe':>7} {'recall@10':>10} {'ms':>8} {'scanned':>9}")
for np_ in [1, 4, 16, 64, 256]:
    ivf.nprobe = np_
    t0=time.perf_counter(); _, got = ivf.search(Q, k); ms=(time.perf_counter()-t0)/len(Q)*1000
    r = np.mean([len(set(a)&set(b))/k for a,b in zip(got, truth)])
    print(f"{np_:>7} {r:10.3f} {ms:8.3f} {np_*n//2048:>9,}")
EOF

🔑 IVF's weakness is the cell boundary. A query sitting near the edge of its nearest cell has true neighbours in the adjacent cell, and with nprobe=1 those are invisible — which is exactly the 0.41 recall above. Raising nprobe is the fix, and it is why IVF needs more probes than intuition suggests. HNSW does not have this failure mode, because a graph has no boundaries; that is the core reason it achieves better recall per unit of work at moderate scale.
ParameterControlsRule of thumb
nlistNumber of cells (k-means clusters)≈ 4·√n — 4k for 1M, 16k for 16M
nprobeCells searched per queryTune to recall; 1–10% of nlist
Training sampleVectors used to fit k-means≥ 39 × nlist, ideally 100×

nlist trades cell-scan cost against centroid-comparison cost. Too few cells and each is huge; too many and comparing against every centroid dominates. The √n heuristic balances the two, and unlike HNSW's M, a bad choice is cheap to fix — IVF rebuilds in a fraction of HNSW's time.

Part 2 — Product Quantisation

IVF reduces how many vectors you scan. PQ reduces what each vector costs — turning 1536 floats (6 KB) into 64 bytes, a 96× reduction.

  A 128-dim vector, m = 8 subvectors of 16 dimensions each:

  [ ──16── | ──16── | ──16── | ──16── | ──16── | ──16── | ──16── | ──16── ]
      │        │        │        │        │        │        │        │
   codebook  codebook  ...                                        codebook
    (256      (256                                                 (256
   centroids) centroids)                                        centroids)
      │        │                                                    │
     0x2A     0x91     0x03     0xFF     0x47     0x18     0xB2     0x6C

  Result: 8 bytes instead of 128 × 4 = 512 bytes.   64x compression.

Each subvector is replaced by the id of its nearest centroid in a small learned codebook. With 256 centroids per subspace, each id is exactly one byte — which is why nbits=8 is the near-universal choice.

$ python3 - <<'EOF'
import numpy as np, faiss
rng = np.random.default_rng(0)
n, d = 200_000, 128
c = rng.standard_normal((50, d))
V = (c[rng.integers(0,50,n)] + rng.standard_normal((n,d))*0.3).astype('float32')
faiss.normalize_L2(V)

print(f"{'m':>4} {'bytes/vec':>10} {'compression':>12} {'total MB':>9}")
print(f"{'-':>4} {d*4:>10} {'1x':>12} {n*d*4/1e6:9.1f}   (float32)")
for m in [8, 16, 32, 64]:
    pq = faiss.IndexPQ(d, m, 8)
    pq.train(V[:50_000]); pq.add(V)
    print(f"{m:>4} {m:>10} {d*4//m:>11}x {n*m/1e6:9.1f}")
EOF
   m  bytes/vec  compression  total MB
   -        512           1x      102.4   (float32)
   8          8          64x        1.6
  16         16          32x        3.2
  32         32          16x        6.4
  64         64           8x       12.8

The clever part is how distances are computed without decompressing. This is asymmetric distance computation (ADC), and it is what makes PQ fast rather than merely small:

  At query time, ONCE:
    for each of the m subspaces:
      compute the distance from the query's subvector to all 256 centroids
    → an m × 256 lookup table

  For each database vector:
    distance ≈ sum over m subspaces of  table[subspace][code_byte]
    → m table lookups and m additions.  No multiplications, no decompression.

  128-dim float32 distance : 128 multiply-adds
  128-dim PQ (m=8) distance:   8 table lookups

"Asymmetric" because the query stays at full precision while the database vectors are quantised — which preserves noticeably more accuracy than quantising both sides.

Part 3 — Quantisation Error and Reranking

PQ is lossy. The reconstructed vector is not the original, and the ranking it produces is approximate on top of whatever approximation the index already introduces.

$ python3 - <<'EOF'
import numpy as np, faiss
rng = np.random.default_rng(0)
n, d = 100_000, 128
c = rng.standard_normal((40, d))
V = (c[rng.integers(0,40,n)] + rng.standard_normal((n,d))*0.3).astype('float32')
faiss.normalize_L2(V)

for m in [8, 16, 32]:
    pq = faiss.IndexPQ(d, m, 8); pq.train(V[:40_000]); pq.add(V)
    recon = pq.reconstruct_n(0, 2000)
    err = np.linalg.norm(V[:2000] - recon, axis=1)
    cos = (V[:2000] * recon).sum(1) / np.linalg.norm(recon, axis=1)
    print(f"m={m:>3}  mean L2 error={err.mean():.4f}  "
          f"cos(original, reconstructed)={cos.mean():.4f}")
EOF
m=  8  mean L2 error=0.4812  cos(original, reconstructed)=0.8814
m= 16  mean L2 error=0.3204  cos(original, reconstructed)=0.9482
m= 32  mean L2 error=0.1918  cos(original, reconstructed)=0.9812

At m=8 the reconstruction is only 0.88 similar to the original — enough to identify roughly the right region of space, not enough to rank precisely within it.

Reranking recovers almost all of the loss. Retrieve a generous candidate set using the quantised codes, then score those candidates against the full-precision vectors:

$ python3 - <<'EOF'
import numpy as np, faiss, time
rng = np.random.default_rng(0)
n, d, k = 300_000, 128, 10
c = rng.standard_normal((60, d))
V = (c[rng.integers(0,60,n)] + rng.standard_normal((n,d))*0.3).astype('float32')
faiss.normalize_L2(V)
Q = V[rng.choice(n, 200, replace=False)].copy()
flat = faiss.IndexFlatIP(d); flat.add(V); _, truth = flat.search(Q, k)

quant = faiss.IndexFlatIP(d)
ivfpq = faiss.IndexIVFPQ(quant, d, 1024, 16, 8)
ivfpq.train(V); ivfpq.add(V); ivfpq.nprobe = 32

def measure(fetch):
    t0 = time.perf_counter()
    _, cand = ivfpq.search(Q, fetch)
    if fetch > k:
        out = []
        for q, cs in zip(Q, cand):
            cs = cs[cs >= 0]
            out.append(cs[np.argsort(-(V[cs] @ q))[:k]])     # rerank on full vectors
        cand = np.array(out)
    ms = (time.perf_counter()-t0)/len(Q)*1000
    r = np.mean([len(set(a[:k])&set(b))/k for a,b in zip(cand, truth)])
    return r, ms

for fetch in [10, 50, 100, 300]:
    r, ms = measure(fetch)
    tag = "no rerank" if fetch == k else f"rerank top {fetch}"
    print(f"{tag:>16}: recall@10={r:.3f}  {ms:.3f} ms")
EOF
       no rerank: recall@10=0.812  0.194 ms
   rerank top 50: recall@10=0.951  0.281 ms
  rerank top 100: recall@10=0.974  0.352 ms
  rerank top 300: recall@10=0.989  0.628 ms

Reranking 100 candidates lifts recall from 0.81 to 0.97 for 0.16 ms. This is why quantised indexes are never deployed without reranking — the compression buys memory, and the rerank buys back the accuracy.

❌ Deploying IVF-PQ with k=10 and no rerank because the memory numbers looked great. You get the 64× compression and 0.81 recall — two of ten results wrong on every query, which in RAG means the answer chunk is regularly missing. The memory win is real and the quality cost is invisible until someone measures it.

✅ Always over-fetch and rerank on full-precision vectors. Retrieve 10–30× k from the quantised index, score those against the originals, return the top k. That requires keeping the full vectors somewhere — on SSD or in a separate store is fine, since only a hundred are read per query — and it turns a memory optimisation into one that costs almost no quality.

Scalar quantisation is underrated. Mapping each float32 to an int8 within the observed min/max is trivially simple, gives 4× compression, and typically costs under a point of recall:

$ python3 - <<'EOF'
import numpy as np
rng = np.random.default_rng(0)
V = rng.standard_normal((50_000, 256)).astype('float32')
V /= np.linalg.norm(V, axis=1, keepdims=True)

lo, hi = V.min(), V.max()
q8 = np.round((V - lo) / (hi - lo) * 255).astype('uint8')
back = q8.astype('float32') / 255 * (hi - lo) + lo

q = V[0]
true = np.argsort(-(V @ q))[:10]
approx = np.argsort(-(back @ q))[:10]
print(f"float32: {V.nbytes/1e6:.1f} MB    int8: {q8.nbytes/1e6:.1f} MB  (4x)")
print(f"mean reconstruction error: {np.abs(V-back).mean():.6f}")
print(f"top-10 overlap with exact : {len(set(true)&set(approx))}/10")
EOF
float32: 51.2 MB    int8: 12.8 MB  (4x)
mean reconstruction error: 0.000982
top-10 overlap with exact : 10/10

Perfect top-10 agreement at a quarter of the memory. If 4× is enough, scalar quantisation is the whole answer and PQ's complexity is unnecessary.

Binary quantisation takes the sign of each dimension, giving one bit per dimension and distance as a XOR plus a population count — the fastest distance computation available:

$ python3 - <<'EOF'
import numpy as np, time
rng = np.random.default_rng(0)
n, d = 200_000, 512
V = rng.standard_normal((n, d)).astype('float32')
V /= np.linalg.norm(V, axis=1, keepdims=True)
B = np.packbits(V > 0, axis=1)                    # 1 bit per dimension
q, qb = V[0], np.packbits(V[0] > 0)

t0=time.perf_counter()
for _ in range(5): np.argsort(-(V @ q))[:100]
float_ms = (time.perf_counter()-t0)/5*1000

t0=time.perf_counter()
for _ in range(5):
    ham = np.unpackbits(B ^ qb, axis=1).sum(1)
    np.argsort(ham)[:100]
bin_ms = (time.perf_counter()-t0)/5*1000

true = set(np.argsort(-(V @ q))[:10])
approx = set(np.argsort(np.unpackbits(B ^ qb, axis=1).sum(1))[:10])
print(f"float32 {V.nbytes/1e6:6.1f} MB  {float_ms:6.1f} ms")
print(f"binary  {B.nbytes/1e6:6.1f} MB  {bin_ms:6.1f} ms   ({V.nbytes/B.nbytes:.0f}x smaller)")
print(f"top-10 overlap without rerank: {len(true & approx)}/10")
EOF
float32  409.6 MB    91.2 ms
binary    12.8 MB    28.4 ms   (32x smaller)
top-10 overlap without rerank: 6/10

32× smaller and 3× faster, but only 6 of 10 correct — binary quantisation is a candidate generator, not a final ranker. Fetch 200 by Hamming distance, rerank on full vectors, and recall returns to the high nineties.

Part 5 — Composing Them

Production indexes stack these techniques. FAISS's index-factory strings name the combinations directly:

"Flat"                    exact, no compression
"IVF4096,Flat"            IVF partitioning, full vectors
"IVF4096,PQ64"            IVF + product quantisation, 64 bytes/vector
"IVF4096,PQ64x4fsr"       + fast scan + reranking
"HNSW32"                  graph, full vectors
"HNSW32,PQ64"             graph over quantised vectors
"OPQ64,IVF4096,PQ64"      + a learned rotation before PQ

OPQ deserves a mention. PQ assumes the subspaces are independent, which real embeddings violate. OPQ learns a rotation that decorrelates the dimensions before splitting them, and it costs nothing at query time:

$ python3 - <<'EOF'
import numpy as np, faiss
rng = np.random.default_rng(0)
n, d, k = 200_000, 128, 10
c = rng.standard_normal((50, d))
V = (c[rng.integers(0,50,n)] + rng.standard_normal((n,d))*0.3).astype('float32')
faiss.normalize_L2(V)
Q = V[rng.choice(n, 200, replace=False)].copy()
flat = faiss.IndexFlatIP(d); flat.add(V); _, truth = flat.search(Q, k)

for spec in ["IVF512,PQ16", "OPQ16_128,IVF512,PQ16"]:
    idx = faiss.index_factory(d, spec, faiss.METRIC_INNER_PRODUCT)
    idx.train(V); idx.add(V)
    faiss.extract_index_ivf(idx).nprobe = 32
    _, got = idx.search(Q, k)
    r = np.mean([len(set(a)&set(b))/k for a,b in zip(got, truth)])
    print(f"{spec:26} recall@10 = {r:.3f}")
EOF
IVF512,PQ16                recall@10 = 0.784
OPQ16_128,IVF512,PQ16      recall@10 = 0.871

Part 6 — IVF vs HNSW in Practice

PropertyHNSWIVF (+PQ)

Memory (compressed)Awkward to combineNatural fit with PQ

The decision usually comes down to churn and scale rather than raw recall. A 5M-vector corpus that changes constantly is better served by IVF, whose deletes are clean and whose rebuild is minutes rather than hours. A 5M-vector corpus that is largely static is better served by HNSW's superior recall-per-millisecond. Past about 50M, PQ becomes mandatory and IVF is its natural host.

One IVF-specific operational note: centroids drift. The k-means fit reflects the corpus at training time, and as the data distribution shifts, cells become unbalanced — some huge, some empty — and recall degrades. Retraining on a fresh sample is cheap and worth scheduling, in the same way HNSW needs rebuilds for tombstones.

Interview Questions

Beginner: How does an IVF index work?

It partitions the corpus so a query only scans part of it.

Build: run k-means to find nlist centroids, then assign every vector to its nearest centroid. Each centroid owns an "inverted list" of the vectors nearest to it.

Query: compare the query against all nlist centroids (cheap, since nlist ≪ n), pick the nprobe closest cells, and scan only the vectors in those cells.

10M vectors, nlist=4096, nprobe=16:
  4,096 centroid comparisons + ~39,000 vector comparisons
  = 43,000 instead of 10,000,000     → 230x less work

Its characteristic weakness is the cell boundary. A query near the edge of its nearest cell has true neighbours in the adjacent cell, and with nprobe=1 they are simply invisible — recall can be as low as 0.4. Raising nprobe is the fix, which is why IVF generally needs more probing than people expect.

Its strengths are build speed and clean deletes: a k-means fit plus one assignment pass, versus HNSW's O(n log n) graph construction, and a deleted vector simply leaves its list rather than becoming a tombstone that degrades a graph.

Beginner: What is product quantisation and how much does it compress?

PQ splits each vector into m subvectors and replaces each one with the id of its nearest centroid in a small learned codebook for that subspace:

128-dim vector, m=8 subvectors of 16 dims, 256 centroids each:
  [16][16][16][16][16][16][16][16]  →  8 bytes  (one byte per subvector)
  512 bytes → 8 bytes = 64x compression

256 centroids is the standard choice because the id fits in exactly one byte.

The clever part is computing distances without decompressing. At query time, once per query, PQ builds an m × 256 lookup table of distances from the query's subvectors to every codebook centroid. Then each database vector's distance is m table lookups and m additions — no multiplications at all. That is asymmetric distance computation, and it is what makes PQ fast as well as small.

"Asymmetric" because the query stays full precision while the stored vectors are quantised, which preserves more accuracy than quantising both.

The cost is real error. At m=8 the reconstructed vector has only about 0.88 cosine similarity to the original — good enough to find roughly the right region, not good enough to rank within it. That is why PQ is always paired with a reranking pass on full-precision vectors.

Mid: Why must a quantised index be paired with reranking?

Because quantisation error compounds with the index's own approximation, and the result is a ranking too coarse to trust at the top.

IVF-PQ, no rerank            : recall@10 = 0.812
IVF-PQ + rerank top 100      : recall@10 = 0.974

0.81 means two of every ten results are wrong. In RAG that regularly means the chunk containing the answer is missing, and no downstream model can recover it.

Reranking works because the two stages have different jobs. The quantised index is a cheap, high-recall candidate generator — it is reliably good at finding the right neighbourhood. Exact scoring is expensive but only needs to run on a hundred candidates rather than ten million:

retrieve 100 with PQ codes   →  ~0.2 ms over the whole corpus
score 100 full vectors       →  ~0.15 ms
total                        →  0.35 ms at recall 0.974

The operational requirement is keeping the full-precision vectors. They do not need to be in RAM — only ~100 are read per query, so SSD or the source database is fine. Teams that discard originals after quantising make the accuracy loss permanent and irreversible, which is a decision worth making deliberately rather than by omission.

The same pattern appears throughout retrieval: cheap wide recall followed by expensive narrow precision. It is exactly the structure of cross-encoder reranking one layer up.

Mid: When would you choose IVF over HNSW?

HNSW gives better recall per unit of work, so I would default to it — and switch to IVF when one of four specific constraints applies.

1. Scale beyond tens of millions. HNSW's graph plus full-precision vectors stops fitting in RAM. IVF composes naturally with PQ, which is the only way to hold a billion vectors on reasonable hardware.

2. High churn. HNSW deletes are tombstones that fragment the graph — recall degrades from 0.98 to 0.85 at high delete rates, silently. In IVF a deleted vector simply leaves its inverted list; there is no connectivity to damage.

3. Build time matters. IVF is a k-means fit plus one assignment pass — minutes where HNSW takes hours at the same scale. If the corpus is rebuilt nightly, that difference dominates the design.

4. Memory is the binding constraint. HNSW carries graph overhead on top of the vectors; IVF-PQ can hold 100M vectors in a few gigabytes.

SituationChoice
5M vectors, mostly static, memory availableHNSW
5M vectors, heavy daily churnIVF-Flat
200M vectorsOPQ + IVF + PQ + rerank
< 100k vectorsNeither — exact search

One IVF-specific caveat: centroids drift. The k-means fit reflects the corpus at training time, and as the distribution shifts, cells become unbalanced and recall falls. Periodic retraining on a fresh sample is IVF's equivalent of HNSW's rebuild, and it needs to be scheduled rather than discovered.

Senior: Design an index for 500M vectors at 1024 dimensions on limited hardware.

At 500M the memory arithmetic determines the architecture before anything else does.

1. Establish what does not fit:

float32 vectors : 500M × 1024 × 4 = 2,048 GB       impossible
+ HNSW graph    : + ~64 GB                          irrelevant, already impossible
int8 scalar     : 512 GB                            still too much
PQ m=64         : 500M × 64 B = 32 GB               fits comfortably
PQ m=32         : 16 GB                             fits with room to spare

PQ is not an optimisation here; it is the only option.

2. The configuration: OPQ64_1024,IVF65536,PQ64.

  • OPQ — a learned rotation before quantisation, decorrelating the subspaces. Several points of recall for zero query cost.
  • IVF with nlist ≈ 65,536 — roughly 4·√500M, giving ~7,600 vectors per cell.
  • PQ64 — 64 bytes per vector, 64× compression, 32 GB total.

3. Reranking is mandatory, and it shapes the storage design. PQ alone will land around 0.8 recall. Full-precision vectors must be retrievable — on SSD or in the source store — so the top ~200 candidates can be rescored. Only 200 random reads per query, which SSD handles easily.

4. Shard for both memory and rebuild: 10 shards of 50M each, ~3.2 GB of PQ codes per shard, queried in parallel and merged before the rerank. That fits commodity instances and makes retraining incremental.

5. Expected performance:

per shard: centroid scan (65k) + nprobe=64 cells × 7.6k vectors ≈ 550k PQ distances
           ≈ 2 ms with SIMD fast-scan
merge 10 shards × 200 candidates                                 ≈ 0.3 ms
rerank 200 full vectors from SSD                                 ≈ 3 ms
────────────────────────────────────────────────────────────────────────
p50 ≈ 6 ms, recall@10 ≈ 0.96 after rerank

6. The operational commitments: retrain OPQ and centroids on a fresh sample quarterly or when cell-size skew exceeds a threshold; monitor recall nightly against a brute-force sample; alert on cell imbalance; and keep the full vectors as the system of record so the whole index is a rebuildable derived artefact.

7. And I would challenge the premise once. 500M vectors in one searchable space is rarely a genuine requirement — partitioning by tenant, language, or recency usually means most queries touch a far smaller index, which is cheaper, faster, and makes filtering trivial rather than problematic.

Senior: Recall dropped from 0.95 to 0.78 after enabling quantisation. Diagnose it.

A 17-point drop is larger than well-configured PQ should cost, so I would look for a configuration error rather than accepting it as the price of compression.

1. Check whether reranking is enabled at all. This is the most common cause and the easiest to fix:

PQ, no rerank        : 0.812
PQ + rerank top 100  : 0.974

If the pipeline searches the quantised index with k=10 and returns those directly, adding over-fetch and a full-precision rescore recovers nearly everything.

2. Check the code size against the dimensionality. A code that is too aggressive for the data loses information that reranking on too few candidates cannot recover:

m= 8 (64x): reconstruction cosine 0.88
m=16 (32x): 0.948
m=32 (16x): 0.981

Doubling m halves the compression and typically recovers several points.

3. Check whether OPQ is being used. PQ assumes the subspaces are independent; real embeddings are correlated, and the rotation is free at query time — worth ~9 points in the example earlier in this lesson.

4. Check the training set. k-means and the PQ codebooks need enough data — at least 39× nlist vectors, ideally 100×. Training on 10,000 vectors for nlist=4096 produces poor centroids and badly unbalanced cells, and the symptom is exactly a recall drop.

5. Separate the IVF loss from the PQ loss, since "enabling quantisation" often means switching from HNSW to IVF-PQ and changing two things at once:

HNSW (baseline)      : 0.95
IVF-Flat, nprobe=32  : 0.94     ← partitioning costs ~1 point
IVF-PQ,  nprobe=32   : 0.78     ← quantisation costs 16 more
IVF-PQ + rerank      : 0.97

That decomposition tells you immediately which stage to fix, and it is worth running before changing parameters.

6. Verify the training data matches production. Codebooks fitted on a stale or unrepresentative sample quantise current vectors poorly — the same drift problem that affects IVF centroids, and a reason to retrain on a schedule rather than once at launch.

import numpy as np
rng = np.random.default_rng(0)
n, d, m, nbits = 20_000, 64, 8, 8
sub_d, K = d // m, 2**nbits

V = rng.standard_normal((n, d)).astype('float32')
V /= np.linalg.norm(V, axis=1, keepdims=True)

# --- train codebooks: one k-means per subspace
from scipy.cluster.vq import kmeans2
codebooks = np.zeros((m, K, sub_d), dtype='float32')
codes = np.zeros((n, m), dtype='uint8')

    sub = V[:, j*sub_d:(j+1)*sub_d]
    cb, lbl = kmeans2(sub, K, minit='points', seed=0)
    codebooks[j] = cb
    codes[:, j] = lbl
print(f"stored: {codes.nbytes/1e6:.2f} MB of codes + "
      f"{codebooks.nbytes/1e6:.2f} MB of codebooks")
print(f"vs {V.nbytes/1e6:.2f} MB original → {V.nbytes/codes.nbytes:.0f}x")

Now the ADC lookup table — the heart of PQ:

$ python3 - <<'EOF'
def adc_search(query, codes, codebooks, k=10):
    m, K, sub_d = codebooks.shape
    # 1. build the lookup table ONCE per query: m x K inner products
    table = np.empty((m, K), dtype='float32')
    for j in range(m):
        qs = query[j*sub_d:(j+1)*sub_d]
        table[j] = codebooks[j] @ qs           # distance to every centroid
    # 2. every vector's score is m table lookups summed
    scores = table[np.arange(m), codes].sum(axis=1)
    return np.argsort(-scores)[:k]

q = V[0]
true = set(np.argsort(-(V @ q))[:10])
got  = set(adc_search(q, codes, codebooks, 10))
print(f"ADC top-10 overlap with exact: {len(true & got)}/10")
EOF
ADC top-10 overlap with exact: 7/10

🎯 Key Takeaways

  • IVF partitions the corpus with k-means and scans only the nprobe nearest cells, cutting work by two orders of magnitude.
  • IVF's weakness is the cell boundary: at nprobe=1 recall can be 0.4, because true neighbours sit in unvisited cells.
  • Set nlist ≈ 4·√n and train k-means on at least 39×nlist vectors; tune nprobe to a recall target.
  • Product quantisation splits a vector into m subvectors and stores one codebook id per subvector — 64 bytes for a 1536-dim vector, 96× compression.
  • Asymmetric distance computation builds an m×256 lookup table once per query, so each vector costs m lookups and m additions with no multiplications.
  • PQ is lossy: at m=8 the reconstruction is only ~0.88 cosine-similar to the original, enough to find the region but not to rank within it.
  • Always over-fetch and rerank on full-precision vectors — it lifts IVF-PQ from ~0.81 to ~0.97 recall for a fraction of a millisecond.
  • Reranking requires keeping the original vectors somewhere; discarding them makes the quality loss permanent.
  • Scalar int8 quantisation gives 4× compression at ~0.99 recall with no reranking — try it before reaching for PQ.
  • Binary quantisation gives 32× and the fastest distance computation, but only ~0.61 recall alone — it is a candidate generator.
  • OPQ learns a rotation that decorrelates subspaces before PQ, worth several points of recall at zero query cost — always include it.
  • IVF builds ~5× faster than HNSW and handles deletes cleanly, where HNSW's tombstones drag recall from 0.98 to 0.84 under churn.
  • HNSW gives better recall per unit of work; choose IVF for scale beyond tens of millions, heavy churn, fast rebuilds, or tight memory.
  • IVF centroids drift as the corpus changes — schedule retraining, just as HNSW needs scheduled rebuilds.
