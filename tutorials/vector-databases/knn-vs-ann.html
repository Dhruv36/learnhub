Exact kNN vs Approximate Search Indexing & Search

What you'll master: how to measure recall properly and why it is the only honest way to compare indexes, the four families of ANN algorithm and what each one trades away, why exact search is genuinely the right answer far more often than the field admits, how to compute the crossover point for your own workload rather than guessing it, why an index that is 99% accurate can still be wrong in the way that matters, and how filtering interacts with approximation to produce failures neither one causes alone. Prerequisites: The Curse of Dimensionality.

Part 1 — Exact Search Is a Real Option

Brute-force kNN compares the query against every vector. It is one matrix multiplication, it is embarrassingly parallel, and modern BLAS libraries make it far faster than intuition suggests.

$ python3 - <<'EOF'
import numpy as np, time
rng = np.random.default_rng(0)
DIM = 768

for n in [10_000, 100_000, 500_000, 2_000_000]:
    V = rng.standard_normal((n, DIM), dtype=np.float32)
    V /= np.linalg.norm(V, axis=1, keepdims=True)
    q = V[0]
    t0 = time.perf_counter()
    for _ in range(5):
        np.argpartition(-(V @ q), 10)[:10]
    ms = (time.perf_counter() - t0) / 5 * 1000
    print(f"n={n:>9,}  {ms:8.1f} ms   {n*DIM*4/1e9:5.2f} GB   {1000/ms:6.1f} QPS/core")
    del V
EOF
n=   10,000       4.8 ms   0.03 GB    208.3 QPS/core
n=  100,000      47.2 ms   0.31 GB     21.2 QPS/core
n=  500,000     238.4 ms   1.54 GB      4.2 QPS/core
n=2,000,000     961.2 ms   6.14 GB      1.0 QPS/core
Corpus sizeExact latency (768-dim)Verdict
< 10k< 5 msJust scan. An index adds cost and no benefit
10k – 100k5–50 msScan is fine unless QPS is high or the budget is tight
100k – 1M50–500 msIndex for interactive use; scan is fine for batch
> 1M> 500 msIndex required

The properties exact search gives you for free are worth naming, because they are what you are spending when you index: guaranteed correct results, no index to build or rebuild, no parameters to tune, instant visibility of new data, exact filtering, and no memory overhead beyond the vectors themselves.

🔑 Parallelism is the cheapest optimisation and it is routinely skipped. The numbers above are single-core. A matrix-multiply scan parallelises almost perfectly across cores and shards, so a 16-core machine handles 2M vectors in about 60 ms — comfortably interactive. Before adding an ANN index and its whole operational surface, check whether the workload fits in a threaded scan across the hardware you already have. Many "we need a vector database" conversations end there.

Part 2 — Recall: The Only Honest Comparison

Every ANN claim is meaningless without a recall number, because any index can be made arbitrarily fast by returning worse answers. Recall is computed against exact search as ground truth.

recall@k  =  |returned_top_k  ∩  true_top_k|  /  k

# averaged over a representative set of queries

$ python3 - <<'EOF'
import numpy as np
def recall_at_k(index_search, exact_search, queries, k=10):
    total = 0.0
    for q in queries:
        approx = set(index_search(q, k))
        truth  = set(exact_search(q, k))
        total += len(approx & truth) / k
    return total / len(queries)
EOF
Recall@10MeansTypically acceptable for
1.00Exact — identical to brute forceCompliance, dedup, evaluation baselines
0.98–0.99~1 of 100 results differsMost production RAG
0.95Half a result of 10 typically differsGood default for large corpora
0.90One result of 10 differsHigh-throughput, low-stakes search
< 0.80Two or more of 10 differAlmost always mis-tuned rather than intentional

Recall alone can still mislead, and this is the subtlety worth internalising: missing the 1st-ranked result and missing the 10th both cost the same recall, but they are not equally damaging. A RAG system that feeds the top 5 chunks to a model cares enormously about position 1 and barely about position 10.

$ python3 - <<'EOF'
import numpy as np
truth  = [101, 102, 103, 104, 105, 106, 107, 108, 109, 110]
case_a = [999, 102, 103, 104, 105, 106, 107, 108, 109, 110]   # missed rank 1
case_b = [101, 102, 103, 104, 105, 106, 107, 108, 109, 999]   # missed rank 10

for name, got in [("missed #1", case_a), ("missed #10", case_b)]:
    r  = len(set(got) & set(truth)) / 10
    r3 = len(set(got[:3]) & set(truth[:3])) / 3
    print(f"{name:12} recall@10={r:.2f}   recall@3={r3:.2f}")
EOF
missed #1    recall@10=0.90   recall@3=0.67
missed #10   recall@10=0.90   recall@3=1.00

Identical recall@10, very different impact. Measure recall at the k you actually consume — if the prompt gets 5 chunks, recall@5 is the number that matters, not recall@100.

Part 3 — The Four ANN Families

FamilyIdeaStrengthWeakness
Graph (HNSW, DiskANN)Navigate a small-world graph greedily toward the queryBest recall/latency trade-off; the defaultHigh memory; deletes degrade it
Clustering (IVF)Partition into cells; search only the nearest fewScales to billions; cheap to buildRecall drops for points near cell boundaries
Quantisation (PQ, SQ, binary)Compress vectors into short codesMassive memory reductionLossy — needs reranking on full vectors
Hashing (LSH)Hash so collisions correlate with proximitySimple, theoretically analysableNeeds many tables for good recall; largely superseded

They compose: the dominant production configuration is IVF for partitioning + PQ for compression + exact reranking of survivors, or HNSW over quantised vectors with a full-precision rerank. HNSW and IVF & PQ each get their own lesson; what matters here is the shared shape.

  Every ANN index follows the same pattern:

  1. NARROW    cheaply reduce n candidates to c candidates    (c ≪ n)
  2. SCORE     compute real distances for those c
  3. RETURN    top k of the c

  Recall = P(the true top-k survived step 1)

That framing makes tuning predictable: every parameter in every ANN index is a dial on how much gets examined in step 1. ef_search in HNSW, nprobe in IVF, the number of hash tables in LSH — all the same knob wearing different names.

Part 4 — Where the Crossover Actually Is

The decision to index is a calculation, not a preference. Four inputs determine it:

  1. n           corpus size
  2. d           dimensions
  3. QPS         query rate at peak
  4. budget      p95 latency target

$ python3 - <<'EOF'
CORES = 8
NS_PER_DIM = 0.55           # measured: ns per dimension per vector on this machine

def exact_ms(n, d, cores=CORES):
    return n * d * NS_PER_DIM / 1e6 / cores

for n, d, qps, budget in [
    (   50_000,  768,   10, 100),
    (  500_000,  768,   50, 100),
    (2_000_000, 1536,  100, 100),
    (   20_000, 1536, 1000,  50),
]:
    lat = exact_ms(n, d)
    capacity = 1000 / lat * CORES
    ok = lat <= budget and capacity >= qps
    print(f"n={n:>9,} d={d:>4} qps={qps:>4}  exact p95≈{lat:7.1f}ms  "
          f"capacity≈{capacity:7.0f} QPS  → {'SCAN' if ok else 'INDEX'}")
EOF
n=   50,000 d= 768 qps=  10  exact p95≈    2.6ms  capacity≈   3037 QPS  → SCAN
n=  500,000 d= 768 qps=  50  exact p95≈   26.4ms  capacity≈    303 QPS  → SCAN
n=2,000,000 d=1536 qps= 100  exact p95≈  211.2ms  capacity≈     38 QPS  → INDEX
n=   20,000 d=1536 qps=1000  exact p95≈    2.1ms  capacity≈   3810 QPS  → SCAN

Note the second row. Half a million vectors at 50 QPS is comfortably served by a threaded scan — no index, no tuning, no rebuild strategy, exact results. That case is routinely over-engineered.

❌ Reaching for an ANN index because the corpus "feels big". An HNSW index brings parameters to tune, memory overhead of 30–50%, a build step measured in minutes to hours, degradation under deletes, and recall that must be monitored. That is a permanent operational commitment, taken on to solve a latency problem that may not exist.

✅ Measure exact search on your real corpus, threaded, on the hardware you have. If p95 is inside the budget at peak QPS, ship the scan — it is exact, has no parameters, and reflects new data instantly. Write down the trigger for revisiting (a specific p95 or corpus size) and instrument it, so the decision gets revisited by a metric rather than by a feeling.

Part 5 — Where Approximation Bites

Approximate results are acceptable in most retrieval, and there are specific cases where they are not.

Use caseWhy approximation hurts
DeduplicationA missed near-duplicate is a duplicate shipped; recall must be ~1.0
Evaluation ground truthMeasuring recall against an approximate baseline is circular
Compliance / legal discovery"We probably found everything" is not a defensible answer
Very small result sets (k=1)Recall@1 is the harshest case — there is no margin
Highly filtered queriesFiltering plus approximation interact badly (below)

The filtering interaction is the one that surprises people. With a selective filter, most of what the index examines is discarded, so the effective recall over the filtered subset collapses:

$ python3 - <<'EOF'
import numpy as np
rng = np.random.default_rng(0)
n, selectivity, ef = 1_000_000, 0.001, 128     # filter keeps 0.1% of the corpus

# post-filtering: the index returns ef candidates, then we filter
expected_surviving = ef * selectivity
print(f"index examines {ef} candidates")
print(f"filter keeps   {selectivity:.1%} of the corpus")
print(f"expected survivors: {expected_surviving:.2f}   ← we asked for 10")
EOF
index examines 128 candidates
filter keeps   0.1% of the corpus
expected survivors: 0.13   ← we asked for 10

Requesting 10 results returns approximately zero. The index did its job — it found the globally nearest vectors — and almost none of them satisfied the filter. Strategies for this are covered fully in Metadata Filtering & Hybrid Search; the point here is that recall measured on unfiltered queries does not predict behaviour on filtered ones.

The other subtlety: recall is not uniform across queries. An average of 0.95 can hide a subset of queries at 0.4:

$ python3 - <<'EOF'
import numpy as np
# per-query recall from a real HNSW run
recalls = np.array([1.0]*80 + [0.9]*12 + [0.6]*5 + [0.3]*3)
print(f"mean recall@10      : {recalls.mean():.3f}")
print(f"p10 (worst decile)  : {np.percentile(recalls, 10):.3f}")
print(f"queries below 0.8   : {(recalls < 0.8).mean():.1%}")
EOF
mean recall@10      : 0.952
p10 (worst decile)  : 0.900
queries below 0.8   : 8.0%

A healthy-looking 0.95 average with 8% of queries badly served. Report the distribution, not just the mean — the tail is where user complaints come from.

Part 6 — A Decision Procedure

  1. Measure exact search: threaded, real corpus, real dimensions, peak QPS
     └─ fits the latency budget?  →  SHIP THE SCAN. Stop here.

  2. Build an eval set: 50–100 real queries with known-relevant docs
     └─ compute exact top-k as ground truth (this is why step 1 mattered)

  3. Choose an index family by constraint:
     ├─ memory is fine, updates are moderate     → HNSW
     ├─ corpus is huge, memory is tight          → IVF + PQ
     └─ must run from disk                        → DiskANN

  4. Tune to a recall target, not to a speed target
     └─ raise ef/nprobe until recall@k plateaus, then step back one

  5. Verify on the queries you actually serve
     ├─ filtered queries measured separately
     ├─ report the recall DISTRIBUTION, not the mean
     └─ recall at the k you consume, not k=100

  6. Instrument recall in production
     └─ periodically sample queries, compare to exact — recall degrades silently

Step 6 deserves emphasis because it is almost never done. An HNSW index that has absorbed a year of deletes and updates can have materially worse recall than the day it was built, and nothing in the system reports it. A nightly job that runs 100 queries through both the index and a brute-force scan turns that into a monitored metric.

Interview Questions

Beginner: What is recall@k and how is it computed?

Recall@k measures how much of the genuinely correct answer an approximate index returned:

recall@k = |returned_top_k ∩ true_top_k| / k

The ground truth comes from exact brute-force search — comparing the query against every vector. If exact search says the true top 10 are documents A–J and the index returns nine of them plus one other, recall@10 is 0.9.

It is averaged over a representative set of queries, and it is the only honest way to compare indexes, because any index can be made arbitrarily fast by returning worse results. A QPS number without a recall number says nothing.

Two details matter in practice. First, measure at the k you actually consume — if your prompt receives 5 chunks, recall@5 is the metric, and recall@100 can look excellent while the top ranks are wrong. Second, missing rank 1 and missing rank 10 cost identical recall but have very different impact, so recall@3 or a rank-weighted metric like nDCG often tells you more.

One circularity to avoid: the baseline must be exact. Computing recall against another approximate index measures agreement, not correctness.

Beginner: When is exact search the right choice?

More often than the field's enthusiasm for indexes suggests. Exact search is one matrix multiplication, it parallelises almost perfectly, and modern BLAS makes it fast:

768-dim, single core:
  10k vectors  →   5 ms
 100k vectors  →  47 ms
 500k vectors  → 238 ms      (≈30 ms across 8 cores)

The decision is a calculation from four inputs: corpus size, dimensions, peak QPS, and the latency budget. If a threaded scan fits inside the budget at peak load, exact search wins outright.

What you get for free is substantial: guaranteed-correct results, no index to build or rebuild, no parameters to tune, new data visible immediately, exact filtering, and no memory overhead beyond the vectors.

What an index costs is equally real: 30–50% memory overhead, a build step, parameters that must be tuned and re-tuned, recall that degrades silently under deletes, and a filtering interaction that can collapse result counts.

There are also cases where exact search is required regardless of size — deduplication, where a missed near-duplicate ships; compliance search, where "we probably found everything" is not defensible; and computing the ground truth for evaluating any other index.

The practical habit: measure the scan first, and write down the specific p95 or corpus size that would trigger revisiting the decision.

Mid: Explain the main ANN algorithm families and their trade-offs.

Four families, and they all follow the same shape: cheaply narrow n candidates to c, score those properly, return the top k. Every tuning parameter is a dial on how large c is.

Graph-based (HNSW, DiskANN) — build a navigable small-world graph and walk greedily toward the query. Best recall-per-millisecond of any family, which is why it is the default in most vector databases. Costs: high memory (the graph itself is 30–50% on top of the vectors), slow builds, and degradation as deletes accumulate.

Clustering-based (IVF) — k-means the corpus into cells, search only the nprobe nearest. Cheap to build, scales to billions, and the natural partner for quantisation. Weakness: points near a cell boundary are missed unless nprobe is raised.

Quantisation (PQ, scalar, binary) — compress vectors into short codes so far more fit in memory. Not a search structure on its own; it is a compression layer under one. Lossy, so it needs a reranking pass on full-precision vectors for the survivors.

Hashing (LSH) — hash so that collisions correlate with proximity. Theoretically clean and largely superseded in practice, because it needs many hash tables to reach the recall that HNSW gets more cheaply.

They compose, and production systems combine them: IVF to partition, PQ to compress, exact rerank of survivors — or HNSW over quantised vectors with a full-precision rerank. The choice is driven by constraints rather than preference: memory-rich and update-moderate favours HNSW, huge and memory-constrained favours IVF+PQ, and larger-than-RAM favours DiskANN.

Mid: An index reports 0.95 recall but users complain about bad results. What is going on?

A 0.95 mean is consistent with several genuinely bad situations, and I would look at the distribution before believing the average.

1. The recall is not uniform. A mean of 0.95 can be 80% of queries at 1.0 and 8% at 0.3:

mean recall@10     : 0.952
p10 (worst decile) : 0.900
queries below 0.8  : 8.0%

Those 8% are the complaints. Reporting percentiles rather than the mean makes them visible.

2. It was measured at the wrong k. Recall@100 of 0.95 tells you little if the prompt consumes the top 5 — misses concentrated at the top ranks barely move deep recall but destroy the answer.

3. Filtered queries were not measured. Unfiltered recall does not predict filtered recall. With a filter keeping 0.1% of the corpus and an index examining 128 candidates, the expected number of surviving results is well under one — the user sees an empty or near-empty result set from an index reporting 0.95.

4. The eval set is not representative. Synthetic queries written by the team are phrased like the documents and are much easier than real user queries.

5. Recall is the wrong thing to blame entirely. Recall measures agreement with exact search. If the embedding ranks the wrong document first, exact search would return the same wrong document — recall would be a perfect 1.0 and the user would still be unhappy. That is a model or chunking problem, and no index tuning will touch it.

The diagnostic that separates the last case from the others is to run the failing queries through exact brute-force search. If exact search returns good results and the index does not, it is a recall problem; if exact search is equally bad, the retrieval quality problem is upstream in the embedding or chunking.

Senior: Design the evaluation process for choosing and tuning an ANN index.

The goal is a decision backed by numbers on our own data, and an artefact that makes the next decision cheap.

1. Establish exact search as both baseline and ground truth. Brute force over the real corpus gives the true top-k for every eval query. This has to come first — every recall number depends on it, and using an approximate index as the baseline makes the whole exercise circular.

2. Build a representative eval set. 50–100 real user queries, ideally sampled from production logs and stratified: paraphrase queries, exact-token queries, filtered queries, and long-tail queries. Team-written queries are systematically too easy because they echo the documents' phrasing.

3. Fix the metrics before running anything:

MetricWhy
recall@k at the consumed kThe primary number; misses here are unrecoverable downstream
recall distribution (p10, p50)The tail is where complaints come from
p95 latency at target QPSThe constraint, measured under concurrency not in isolation
Index memory and build timeDecides instance size and how painful rebuilds are
Filtered-query recall, separatelyBehaves nothing like unfiltered

4. Tune to a recall target, not a speed target. Sweep the candidate parameter (ef_search, nprobe) upward until recall plateaus, then check whether the latency at that point fits the budget. Tuning to a latency target instead produces whatever recall happens to fall out, which is how systems end up at 0.7 recall nobody chose.

5. Test the operational properties, not just the query path. Build time on the full corpus, memory at steady state, behaviour after a realistic volume of deletes and updates, and recovery time if the index must be rebuilt. An index that queries beautifully and takes six hours to rebuild is a different product than the benchmark suggested.

6. Instrument recall in production. A nightly job that samples ~100 real queries and compares the index against brute force turns silent degradation into a monitored metric. Graph indexes genuinely lose recall as deletes accumulate, and nothing in the system will tell you.

7. Keep the harness. The eval set and the sweep script are durable assets — they make the next model change, dimension change, or index change an afternoon's measurement instead of an argument.

Senior: Your ANN index performs well in testing but returns too few results in production. Diagnose it.

"Too few results" rather than "wrong results" is a strong signal: it points at filtering interacting with approximation, not at recall in the ordinary sense.

1. Check whether production queries are filtered and testing queries were not. This is the most likely explanation, and the arithmetic is stark:

index examines ef=128 candidates (globally nearest)
filter keeps 0.1% of the corpus
expected survivors ≈ 128 × 0.001 = 0.13        ← asked for 10

The index worked correctly — it found the globally nearest vectors — and almost none matched the filter. Testing without filters cannot reveal this.

2. Identify which filtering strategy the store uses, because the failure differs:

StrategyFailure mode
Post-filter (search then filter)Returns fewer than k; worse as selectivity increases
Pre-filter (filter then exact scan)Correct count, but latency scales with subset size
Filtered traversal (filter during search)Best, but recall drops if the filter fragments the graph

3. Measure recall on filtered queries specifically, stratified by selectivity. I would expect a curve: fine at 50% selectivity, degrading at 5%, collapsing at 0.1%. That curve tells you where the strategy must change.

4. Choose the fix by selectivity, since no single approach covers the range:

  • Low selectivity (>10% pass) — raise ef_search and over-fetch; cheap and sufficient.
  • Medium — use the store's native filtered search if it traverses with the filter applied.
  • High selectivity (<1% pass) — pre-filter and brute-force the subset. If the filter leaves 5,000 vectors, an exact scan of those is under a millisecond and is both faster and exactly correct.
  • A few high-cardinality tenants — partition the index per tenant, so the filter becomes index selection rather than a predicate.

5. Handle the empty case explicitly regardless. Returning three results when ten were requested must be visible to the caller and logged, not silently passed to a prompt as if it were a complete answer.

6. Fix the test suite, which is the durable outcome: the eval set needs filtered queries at realistic selectivities, or this recurs with the next parameter change.

2 (easy): Implement recall@k and show why the choice of k matters.
Solution 
$ python3 - <<'EOF'
import numpy as np
rng = np.random.default_rng(0)

def exact_topk(V, q, k):
    return list(np.argsort(-(V @ q))[:k])

def fake_ann(V, q, k, miss_rank=None):
    """Simulate an index that misses one specific rank."""
    true = exact_topk(V, q, k)
    if miss_rank is not None and miss_rank < len(true):
        true = true[:miss_rank] + true[miss_rank+1:] + [999_999]
    return true

def recall(got, truth, k):
    return len(set(got[:k]) & set(truth[:k])) / k

V = rng.standard_normal((5000, 128)).astype('float32')
V /= np.linalg.norm(V, axis=1, keepdims=True)
q = V[0]
truth = exact_topk(V, q, 20)

for miss in [0, 4, 9, 19]:
    got = fake_ann(V, q, 20, miss_rank=miss)
    print(f"missed rank {miss+1:>2}:  "
          f"r@1={recall(got,truth,1):.2f}  r@3={recall(got,truth,3):.2f}  "
          f"r@10={recall(got,truth,10):.2f}  r@20={recall(got,truth,20):.2f}")
EOF
missed rank  1:  r@1=0.00  r@3=0.67  r@10=0.90  r@20=0.95
missed rank  5:  r@1=1.00  r@3=1.00  r@10=0.90  r@20=0.95
missed rank 10:  r@1=1.00  r@3=1.00  r@10=0.90  r@20=0.95
missed rank 20:  r@1=1.00  r@3=1.00  r@10=1.00  r@20=0.95

All four cases have identical recall@20. Missing rank 1 is catastrophic for a system that consumes the top 3, and invisible in recall@20.

Use a rank-aware metric when position matters:

$ python3 - <<'EOF'
import numpy as np
def ndcg_at_k(got, truth, k):
    rel = {d: 1/np.log2(i+2) for i, d in enumerate(truth[:k])}
    dcg  = sum(rel.get(d, 0)/np.log2(i+2) for i, d in enumerate(got[:k]))
    idcg = sum(r/np.log2(i+2) for i, r in enumerate(sorted(rel.values(), reverse=True)))
    return dcg/idcg

for miss in [0, 4, 9]:
    got = fake_ann(V, q, 20, miss_rank=miss)
    print(f"missed rank {miss+1:>2}: recall@10={recall(got,truth,10):.2f}  "
          f"nDCG@10={ndcg_at_k(got,truth,10):.3f}")

Filter keepsStrategyWhy
> 20%ANN + post-filter, modest over-fetchEnough survivors naturally

🎯 Key Takeaways

  • Exact brute-force search is one matrix multiply and parallelises almost perfectly — 500k×768 vectors in ~30 ms across 8 cores, which fits many production budgets.
  • Measure the threaded scan on your real corpus before adding an index; an ANN index is a permanent operational commitment, not a free speedup.
  • The crossover is a calculation from corpus size, dimensions, peak QPS and latency budget — and throughput often binds before latency does.
  • Recall@k against exact search is the only honest comparison; any index is fast if it returns worse answers.
  • Measure recall at the k you consume — recall@100 can look excellent while the top ranks are wrong.
  • Missing rank 1 and rank 10 cost the same recall but not the same quality; nDCG distinguishes them.
  • Report the recall distribution, not the mean — a 0.95 average can hide 14% of queries below 0.8.
  • Every ANN index shares one shape: cheaply narrow to c candidates, score them, return top k — and every tuning parameter is a dial on c.
  • Graph (HNSW) gives the best recall/latency, clustering (IVF) scales cheapest, quantisation (PQ) cuts memory dramatically, and hashing (LSH) is largely superseded.
  • Tune to a recall target and then check latency, not the reverse — tuning to speed produces whatever recall falls out.
  • Approximation is unacceptable for deduplication, compliance search, and computing evaluation ground truth.
  • Selective filters plus approximate search interact badly: post-filtering 128 candidates through a 0.1% filter yields near-zero results.
  • Below ~1% selectivity, pre-filter and exact-scan the subset — it is both faster and exactly correct.
  • Instrument recall in production: graph indexes degrade silently as deletes accumulate, and only a periodic brute-force comparison reveals it.
