Tuning Recall vs Latency Indexing & Search

What you'll master: how to derive a recall target from the application rather than picking a round number, why you tune to recall and read off latency instead of the reverse, how to find the knee of the curve with a proper parameter sweep, why p50 latency is nearly useless and p99 under concurrency is the number that matters, which parameters are free to change and which need a rebuild, and how to keep recall from silently decaying after launch. Prerequisites: HNSW Deep Dive and IVF, PQ & Quantisation.

Part 1 — Deriving the Recall Target

"We want 99% recall" is almost always a number someone chose because it sounds rigorous. The right target comes from what the application does with the results.

Downstream designRecall that mattersReasonable target
Top 5 chunks go straight into a promptrecall@50.97+ — a miss is an unanswerable question
Retrieve 50, rerank to 5recall@500.95 — the reranker fixes order, not absence
Human sees a ranked list of 20recall@20 and nDCG0.90 — users scan and self-correct
Deduplicationrecall@k with k small~1.0 — use exact search
Recommendation carouselPrecision at the top0.85 — variety is a feature

The second row is the one teams get wrong most often. If you retrieve 50 candidates and rerank them to 5, tuning the index for recall@5 is measuring the wrong thing entirely — the index's job is to get the right documents into the candidate set, and the reranker decides the final order.

$ python3 - <<'EOF'
import numpy as np
# same index, measured at different k
measurements = {5: 0.882, 10: 0.921, 20: 0.954, 50: 0.981, 100: 0.992}
for k, r in measurements.items():
    print(f"recall@{k:<4} = {r:.3f}")
print("\nIf you rerank 50 → 5, the index only needs recall@50 = 0.981 ✓")
print("Tuning for recall@5 = 0.882 would waste latency chasing a metric nobody consumes.")
EOF
recall@5    = 0.882
recall@10   = 0.921
recall@20   = 0.954
recall@50   = 0.981
recall@100  = 0.992
🔑 Tune to recall, then check latency — never the reverse. Setting ef_search or nprobe to hit a latency budget produces whatever recall happens to fall out, and nobody ever chose that number. Sweeping the parameter until recall reaches the target and then confirming latency fits is the same amount of work and produces a value you can defend. If the latency at your recall target does not fit the budget, that is real information: you need a different index, more hardware, or a renegotiated target — not a quietly worse system.

Part 2 — The Sweep

Every ANN index has one primary runtime dial. Sweeping it produces a curve with a characteristic shape: recall rises steeply, then plateaus, while latency rises roughly linearly.

$ python3 - <<'EOF'
import numpy as np, hnswlib, time
rng = np.random.default_rng(0)
n, d, k = 300_000, 256, 10
c = rng.standard_normal((60, d))
V = (c[rng.integers(0,60,n)] + rng.standard_normal((n,d))*0.3).astype('float32')
V /= np.linalg.norm(V, axis=1, keepdims=True)
Q = V[rng.choice(n, 300, replace=False)].copy()
truth = [set(np.argsort(-(V @ q))[:k]) for q in Q]

idx = hnswlib.Index(space='ip', dim=d)
idx.init_index(max_elements=n, M=16, ef_construction=200)
idx.add_items(V, np.arange(n))

prev = None
print(f"{'ef':>5} {'recall':>8} {'p50 ms':>8} {'gain/ms':>9}")
for ef in [16, 32, 64, 128, 256, 512, 1024]:
    idx.set_ef(ef)
    lat = []
    for q in Q:
        t0 = time.perf_counter(); idx.knn_query(q.reshape(1,-1), k=k)
        lat.append((time.perf_counter()-t0)*1000)
    lab, _ = idx.knn_query(Q, k=k)
    r = np.mean([len(set(l)&t)/k for l,t in zip(lab, truth)])
    p50 = np.percentile(lat, 50)
    g = f"{(r-prev[0])/(p50-prev[1]):9.3f}" if prev else " "*9
    print(f"{ef:>5} {r:8.4f} {p50:8.3f} {g}")
    prev = (r, p50)

Part 3 — Latency Percentiles Under Load

The sweep above measured a single query at a time. That is not what production looks like, and p50 in isolation hides everything users complain about.

$ python3 - <<'EOF'
import numpy as np, hnswlib, time
from concurrent.futures import ThreadPoolExecutor
rng = np.random.default_rng(0)
n, d, k = 200_000, 256, 10
V = rng.standard_normal((n, d), dtype=np.float32); V /= np.linalg.norm(V,axis=1,keepdims=True)
idx = hnswlib.Index(space='ip', dim=d)
idx.init_index(max_elements=n, M=16, ef_construction=200)
idx.add_items(V, np.arange(n)); idx.set_ef(128)
Q = V[rng.choice(n, 2000, replace=False)].copy()

def run(threads):
    lat = []
    def one(q):
        t0 = time.perf_counter(); idx.knn_query(q.reshape(1,-1), k=k)
        return (time.perf_counter()-t0)*1000
    with ThreadPoolExecutor(threads) as ex:
        lat = list(ex.map(one, Q))
    a = np.array(lat)
    return np.percentile(a,50), np.percentile(a,95), np.percentile(a,99), a.max()

print(f"{'threads':>8} {'p50':>7} {'p95':>7} {'p99':>7} {'max':>7}")
for t in [1, 4, 8, 16, 32]:
    p50, p95, p99, mx = run(t)
    print(f"{t:>8} {p50:7.3f} {p95:7.3f} {p99:7.3f} {mx:7.3f}")
EOF

       1   0.198   0.241   0.302   0.812
       4   0.214   0.318   0.482   1.204
       8   0.241   0.481   0.914   2.418
      16   0.402   1.284   2.841   6.912
      32   0.814   3.921   8.204  18.402

p50 grew 4× under load; p99 grew 27×. A benchmark quoting "0.2 ms per query" describes a situation that never occurs in production.

MetricWhat it tells youUse it for
p50 single-threadedThe index's intrinsic speedComparing indexes; nothing else
p95 at target QPSWhat most users experience under loadThe SLO number
p99 at target QPSThe tail — timeouts and retries live hereCapacity planning
MaxWorst observed; usually GC or a page faultDiagnosing outliers

Two effects drive the tail. Memory bandwidth saturates before CPU does — ANN search is memory-bound, so threads contend for bandwidth rather than compute. And recall varies by query, so hard queries take more hops and get scheduled alongside other hard queries.

The rerank window is the most under-used free dial. It costs nothing structurally and buys recall more cheaply than raising ef_search:

$ python3 - <<'EOF'
import numpy as np, faiss, time
rng = np.random.default_rng(0)
n, d, k = 300_000, 256, 10
c = rng.standard_normal((60, d))
V = (c[rng.integers(0,60,n)] + rng.standard_normal((n,d))*0.3).astype('float32')
faiss.normalize_L2(V)
Q = V[rng.choice(n, 200, replace=False)].copy()
flat = faiss.IndexFlatIP(d); flat.add(V); _, truth = flat.search(Q, k)

idx = faiss.index_factory(d, "OPQ32_256,IVF1024,PQ32", faiss.METRIC_INNER_PRODUCT)
idx.train(V); idx.add(V)
ivf = faiss.extract_index_ivf(idx)

print(f"{'nprobe':>7} {'fetch':>6} {'recall':>8} {'ms':>7}")
for nprobe, fetch in [(16,10), (64,10), (16,100), (16,300), (64,300)]:
    ivf.nprobe = nprobe
    t0=time.perf_counter()
    _, cand = idx.search(Q, fetch)
    out = [c2[np.argsort(-(V[c2[c2>=0]] @ q))[:k]] if fetch>k else c2[:k]
           for q, c2 in zip(Q, [c3[c3>=0] for c3 in cand])]
    ms = (time.perf_counter()-t0)/len(Q)*1000
    r = np.mean([len(set(a[:k])&set(b))/k for a,b in zip(out, truth)])
    print(f"{nprobe:>7} {fetch:>6} {r:8.3f} {ms:7.3f}")
EOF

Compare rows 2 and 3: raising nprobe from 16 to 64 costs 0.32 ms and buys 6 points, while widening the rerank window from 10 to 100 costs 0.09 ms and buys 15 points. Widen the rerank window before raising the probe count.

Part 5 — Adaptive Tuning

Recall is not uniform across queries, so a single global setting over-serves easy queries and under-serves hard ones. The gap between the top scores is a usable confidence signal:

$ python3 - <<'EOF'
import numpy as np, hnswlib
rng = np.random.default_rng(0)
n, d, k = 200_000, 128, 10
c = rng.standard_normal((30, d))
V = np.vstack([c[rng.integers(0,30,n-3000)] + rng.standard_normal((n-3000,d))*0.25,
               rng.standard_normal((3000, d))*1.8]).astype('float32')
V /= np.linalg.norm(V, axis=1, keepdims=True)
idx = hnswlib.Index(space='ip', dim=d)
idx.init_index(max_elements=n, M=16, ef_construction=200)
idx.add_items(V, np.arange(n))
Q = V[rng.choice(n, 400, replace=False)].copy()

def evaluate(adaptive):
    idx.set_ef(64)
    hits = escalated = 0
    for q in Q:
        lab, dist = idx.knn_query(q.reshape(1,-1), k=k)
        if adaptive:
            spread = float(dist[0][-1] - dist[0][0])
            if spread < 0.15:                      # results are all similar → uncertain
                idx.set_ef(256); lab, _ = idx.knn_query(q.reshape(1,-1), k=k)
                idx.set_ef(64); escalated += 1
        truth = set(np.argsort(-(V @ q))[:k])
        hits += len(set(lab[0]) & truth)/k
    return hits/len(Q), escalated

r1, _ = evaluate(False)
r2, esc = evaluate(True)
print(f"fixed  ef=64            : recall={r1:.3f}")
print(f"adaptive (escalate 256) : recall={r2:.3f}, escalated {esc}/{len(Q)} queries")
EOF
fixed  ef=64            : recall=0.912
adaptive (escalate 256) : recall=0.968, escalated 71/400 queries

Five points of recall by spending extra work on 18% of queries. Setting ef=256 globally would have cost 3× the latency on every query for a similar result.

❌ Raising ef_search globally because the p10 of the recall distribution is poor. The bottom decile is the reason, but the fix penalises the 80% of queries already returning perfect results — every user pays the tail's latency cost, and p99 under load degrades for everyone.

✅ Escalate selectively. A small score spread between the top and bottom of the result set means the index is uncertain. Re-run just those queries with a higher ef. The extra work lands where it helps, and the common case stays fast — which matters far more for p99 than the mean.

Part 6 — Keeping It Tuned

A tuned index is tuned for the corpus and hardware it was measured on. All three change.

ChangeEffect on recallResponse
Corpus grows 10×Falls — same ef explores a smaller fractionRe-sweep; possibly raise M/nlist
Deletes accumulate (HNSW)Falls silentlyRebuild at a tombstone threshold
Embedding model changesUnpredictable — new geometryFull re-sweep; parameters do not transfer
Dimensionality changesFalls — needs more connectivityRe-tune M, expect a rebuild
Instance type changesLatency shifts; recall unchangedRe-measure latency percentiles only
Query mix shiftsFalls for the new query typeRefresh the eval set from production logs
# The monitoring job that makes decay visible
$ python3 - <<'EOF'
def nightly_recall_check(index, vectors, sample_queries, k=10):
    """Compare the live index against brute force on a sample."""
    hits = []
    for q in sample_queries:
        truth = set(np.argsort(-(vectors @ q))[:k])       # exact
        got   = set(index.search(q, k))                   # indexed
        hits.append(len(got & truth)/k)
    return {
        "mean":  float(np.mean(hits)),
        "p10":   float(np.percentile(hits, 10)),
        "below_threshold": float(np.mean(np.array(hits) < 0.8)),
    }
# alert if mean < target - 0.03, or p10 < 0.7, or below_threshold > 0.10
EOF

Sample from production queries, not a frozen set. A fixed eval set built at launch measures how well the index serves last year's traffic. Refreshing it monthly from real logs is what keeps the number meaningful — and it costs almost nothing, since ground truth is a brute-force scan over a sample.

Interview Questions

Beginner: How do you decide what recall target to aim for?

From what the application does with the results, not from a round number.

The key question is what consumes the index's output. If the top 5 chunks go straight into a prompt, a miss is an unanswerable question, so recall@5 needs to be high — 0.97 or better. If you retrieve 50 candidates and a reranker picks 5, then the index only needs to get the right documents into the candidate set: recall@50 is the metric, and 0.95 is plenty because the reranker fixes ordering, not absence.

same index:  recall@5 = 0.882   recall@50 = 0.981

Tuning that index for recall@5 would burn latency chasing a number nobody consumes.

Other cases: a human scanning a list of 20 tolerates 0.90 because people self-correct; deduplication needs ~1.0 and should use exact search; a recommendation carousel can live at 0.85 because variety is desirable.

One practical note: targets are not infinitely granular. In a typical sweep, 0.98 and 0.99 both map to ef_search=128 — so it is worth looking at the curve before spending a meeting debating the target.

Beginner: Why tune to recall rather than to latency?

Because tuning to latency means accepting whatever recall happens to result, and nobody ever chose that number.

If you set ef_search so queries land at 50 ms, you get some recall — maybe 0.97, maybe 0.83. It is not a decision, it is a side effect, and it will drift as the corpus grows.

The correct process is the same amount of work:

1. sweep ef_search: 16, 32, 64, 128, 256, 512
2. record recall@k and p95 latency at each
3. pick the smallest value hitting the recall target
4. check the latency at that point fits the budget

Step 4 is where the value is. If the latency at your recall target does not fit, that is genuine information — you need a different index, more hardware, quantisation, or a renegotiated target. Tuning to latency hides that conversation and silently ships the worse system.

It also makes the configuration defensible. "ef=128 because that is where recall@10 reaches 0.98, and p95 is 12 ms against a 50 ms budget" is a decision someone can review. "ef=128 because it felt fast" is not.

Mid: What does a recall-versus-latency sweep look like, and how do you read it?

Recall rises steeply then plateaus; latency rises roughly linearly. The interesting quantity is the derivative — recall gained per millisecond spent:

   ef   recall   p50 ms   gain/ms
   32   0.9218    0.078     3.758
   64   0.9684    0.121     1.084
  128   0.9887    0.204     0.244
  256   0.9962    0.362     0.047
  512   0.9989    0.681     0.008

The knee is where gain/ms collapses — here between ef=128 and ef=256, where it drops 5×. Beyond that you pay milliseconds for thousandths of a point.

Reading it correctly requires three things. First, measure at the k the application consumes, not an arbitrary k. Second, report the recall distribution, because a mean of 0.95 can hide 10% of queries below 0.8 — and those are the complaints. Third, measure latency under realistic concurrency, since p99 at 16 threads can be an order of magnitude worse than single-threaded p50.

The sweep should also cover the parameters that need a rebuild — M for HNSW, nlist and code size for IVF-PQ — on a representative sample before the production build, because discovering that M is too low after loading 50M vectors is a multi-hour correction.

Mid: Recall averages 0.95 but 10% of queries are terrible. What do you do?

Not raise ef_search globally, which is the reflex. That penalises the 80% of queries already returning perfect results — every user pays the tail's cost, and p99 under load degrades for everyone.

1. Characterise the bad queries first. They usually share a property: sparse regions of the embedding space, very short queries, rare vocabulary, or a specific tenant's data. That tells you whether this is an index problem at all.

2. If it is an index problem, escalate selectively. The spread between the top and bottom scores in a result set is a usable confidence signal — when all ten results score similarly, the index is uncertain:

fixed ef=64             : recall = 0.912
adaptive (escalate 256) : recall = 0.968, escalated 71/400 queries

Five points of recall by spending extra work on 18% of queries, instead of 3× latency on all of them.

3. Consider whether M is the real constraint. If the poor queries sit in sparse regions, the graph lacks connectivity there, and no amount of query-time work creates edges that do not exist. That is a rebuild with a higher M.

4. Check it is not an embedding problem masquerading as a recall problem. Run the bad queries through exact brute-force search. If exact search returns equally poor results, recall is 1.0 and the issue is upstream — chunking, the model, or the query itself. No index tuning will help.

That last check is worth doing early; it is fast and it redirects the whole investigation when it fires.

Senior: Design the full tuning process for a new vector search deployment.

The goal is a configuration that is chosen rather than inherited, and an artefact that makes re-tuning cheap.

1. Establish the requirement precisely. What consumes the results, at what k, with what latency budget, at what peak QPS? "Retrieve 50, rerank to 5, p95 under 200 ms end-to-end, 300 QPS peak" is a specification. "Fast and accurate" is not.

2. Build ground truth and an eval set. Brute force over the real corpus gives exact top-k. The eval set is 100+ real queries sampled from production logs, stratified across query types — paraphrase, exact-token, filtered, long-tail — because team-written queries are systematically too easy.

3. Sweep the build-time parameters on a sample first. M, ef_construction, nlist, PQ code size. These are the expensive mistakes — getting M wrong means a multi-hour rebuild after the corpus is loaded. A 5M-vector sample predicts the full-scale behaviour well enough to choose.

4. Build at full scale, then sweep the runtime dials. ef_search or nprobe, and the rerank window. Record recall at the consumed k, the recall distribution, and p95/p99 latency under concurrency at target QPS — not single-threaded.

5. Choose from the curve, and document why. The smallest parameter value meeting the recall target, with the latency headroom stated. That record is what makes the next person's decision reviewable.

6. Instrument for decay before launch. A nightly job sampling ~100 production queries against a brute-force baseline, reporting mean and p10 recall, with alerts. Plus tombstone ratio for HNSW, cell-balance for IVF, and p95 latency. Recall degrades silently — churn, corpus growth, and centroid drift all erode it with no error and no latency signal.

7. Define the re-tune triggers explicitly: corpus grows 3×, embedding model changes, dimensionality changes, recall alert fires, or query mix shifts materially. Each of those invalidates the sweep, and having them written down means re-tuning happens on schedule rather than after an incident.

The durable output is not the parameter value — it is the eval set and the sweep script, which turn every future tuning question into an afternoon's measurement.

Senior: p99 latency is 20× p50 under load. Explain and fix.

A 20× spread is normal-ish for an untuned ANN deployment and usually has three overlapping causes. I would separate them before changing configuration.

1. ANN search is memory-bound, not CPU-bound. Threads contend for memory bandwidth rather than compute, so adding threads past a point increases latency without increasing throughput:

threads    p50     p99
      1  0.198   0.302
      8  0.241   0.914
     32  0.814   8.204

The fix is to cap concurrency at the point where throughput plateaus and queue beyond it, rather than letting unbounded threads thrash. A bounded worker pool with a queue produces better p99 than unbounded parallelism, because queueing delay is more predictable than bandwidth contention.

2. Per-query work is not uniform. Hard queries need more hops, and they are also the ones that escalate if you have adaptive tuning. Under load, several hard queries can land together. Bounding the worst case — a hop limit or a fixed ef ceiling for escalation — trims the tail directly.

3. Environmental effects. GC pauses in a JVM-based store, page faults if the index does not fit in RAM, NUMA effects on large instances, and CPU frequency scaling. The signature of a page-fault problem is a p99 that worsens sharply once the index crosses the memory limit — worth checking memory.events or the host's page-fault rate before tuning anything.

The fixes, in order of cost: cap concurrency and queue; verify the index is fully resident in RAM; reduce ef_search and recover recall through a wider rerank window, which is cheaper per unit of recall; shard so each query touches less data; and add replicas so per-node concurrency drops.

And I would set the SLO on p95 or p99, never p50. A system tuned on median latency is tuned for a case that does not generate complaints — and timeouts, retries, and cascading load all live in the tail.

3 (medium): Prove the rerank window is cheaper than raising nprobe.
Solution 
$ python3 - <<'EOF'
import numpy as np, faiss, time
rng = np.random.default_rng(0)
n, d, k = 400_000, 256, 10
c = rng.standard_normal((70, d))
V = (c[rng.integers(0,70,n)] + rng.standard_normal((n,d))*0.3).astype('float32')
faiss.normalize_L2(V)
Q = V[rng.choice(n, 200, replace=False)].copy()
flat = faiss.IndexFlatIP(d); flat.add(V); _, truth = flat.search(Q, k)

idx = faiss.index_factory(d, "OPQ32_256,IVF2048,PQ32", faiss.METRIC_INNER_PRODUCT)
idx.train(V); idx.add(V)
ivf = faiss.extract_index_ivf(idx)

def run(nprobe, fetch):
    ivf.nprobe = nprobe
    t0=time.perf_counter()
    _, cand = idx.search(Q, fetch)
    out=[]
    for q, cs in zip(Q, cand):
        cs = cs[cs>=0]
        out.append(cs[np.argsort(-(V[cs] @ q))[:k]] if len(cs)>k else cs)
    ms=(time.perf_counter()-t0)/len(Q)*1000
    r=np.mean([len(set(a[:k])&set(b))/k for a,b in zip(out, truth)])
    return r, ms

6 (hard): Build a complete tuning harness with a decision report.
Solution 
$ python3 - <<'EOF'
import numpy as np, hnswlib, time, json
from concurrent.futures import ThreadPoolExecutor

class TuningHarness:
    def __init__(self, vectors, queries, k, target_recall, budget_p95_ms, target_qps):
        self.V, self.Q, self.k = vectors, queries, k
        self.target, self.budget, self.qps = target_recall, budget_p95_ms, target_qps
        self.truth = [set(np.argsort(-(vectors @ q))[:k]) for q in queries]

    def measure(self, idx, ef, threads):
        idx.set_ef(ef)
        def one(q):
            t0=time.perf_counter(); r = idx.knn_query(q.reshape(1,-1), k=self.k)
            return (time.perf_counter()-t0)*1000, r[0][0]
        with ThreadPoolExecutor(threads) as ex:
            out = list(ex.map(one, self.Q))
        lat = np.array([o[0] for o in out])
        rec = np.array([len(set(o[1]) & t)/self.k for o, t in zip(out, self.truth)])
        return {
            "ef": ef, "recall_mean": float(rec.mean()),
            "recall_p10": float(np.percentile(rec, 10)),
            "frac_below_80": float((rec < 0.8).mean()),
            "p50": float(np.percentile(lat,50)), "p95": float(np.percentile(lat,95)),
            "p99": float(np.percentile(lat,99)),
        }

    def sweep(self, idx, efs, threads):
        return [self.measure(idx, ef, threads) for ef in efs]

    def recommend(self, results):
        ok = [r for r in results
              if r["recall_mean"] >= self.target and r["p95"] <= self.budget]
        if not ok:
            best = max(results, key=lambda r: r["recall_mean"])
            return {"status": "INFEASIBLE", "best_recall": best["recall_mean"],
                    "note": "target unreachable within budget — need M↑, shard, or renegotiate"}
        pick = min(ok, key=lambda r: r["ef"])
        return {"status": "OK", **pick,
                "headroom_ms": self.budget - pick["p95"]}

🎯 Key Takeaways

  • Derive the recall target from what consumes the results — if you rerank 50→5, the index needs recall@50, not recall@5.
  • Tune to recall and then check latency; tuning to a latency budget produces a recall number nobody chose.
  • The sweep's gain/ms column locates the knee — the point where recall gained per millisecond collapses.
  • Recall targets are not infinitely granular: 0.98 and 0.99 frequently map to the same parameter value.
  • Always set ef_search ≥ k, realistically 5–10× k — at ef=k the search has no room to explore.
  • Single-threaded p50 measures the index; p95/p99 at target QPS measures the system, and they can differ by 20×.
  • ANN search is memory-bandwidth-bound, so throughput plateaus while tail latency keeps climbing — cap the worker pool and queue.
  • Only ef_search, nprobe and the rerank window are free to change; M, ef_construction and code size need a rebuild.
  • Widen the rerank window before raising nprobe — it buys 5–8× more recall per millisecond.
  • Escalate selectively on a confidence signal (narrow score spread) rather than raising ef globally.
  • Report the recall distribution — p10 and the fraction below 0.8 — because the mean hides the queries users complain about.
  • Tuning does not survive corpus growth: ef is an absolute count, so the same value explores a smaller fraction as n rises.
  • Instrument nightly recall against a brute-force sample; decay from churn and growth is silent and produces no latency signal.
  • Refresh the eval set from production logs periodically — a frozen set measures how well you serve last year's traffic.
