Probes: Liveness, Readiness & Startup Scaling & Reliability

What you'll master: the single rule that prevents almost every probe-caused outage — a probe may only test what its own remedy can fix; the three probes and their three distinct remedies (restart, remove from endpoints, keep waiting); the arithmetic that turns timing fields into an actual detection window, and why the defaults give you up to 180 seconds; the cascading outage a dependency-checking liveness probe produces, measured as every replica restarting simultaneously during an eight-second database blip; startup probes, which replace the initialDelaySeconds guess with a real boot budget; how readiness interacts with termination — the endpoint-removal race that drops requests on every deploy; and the anti-patterns that make probes expensive, useless, or actively harmful. Prerequisites: Pods, Services & Endpoints, and Docker: Health Checks.

Part 1 — Three Probes, Three Remedies

ProbeQuestionRemedy on failureMay it check dependencies?
LivenessIs this process wedged?Restart the container❌ Absolutely not
ReadinessCan it serve right now?Remove from Service endpoints⚠️ Only hard dependencies
StartupHas it finished booting?Keep waiting; suppress liveness❌ No
🔑 The rule: a probe may only test things its own remedy can fix. Restarting a container cannot repair someone else's database, so a liveness probe that consults one guarantees correlated failure of every replica at once. Shedding traffic is a proportionate response to a missing dependency, so readiness may consult one. Every probe design question reduces to asking what will act on the answer and whether that action helps.
containers:
- name: api
  startupProbe:                        ← runs FIRST; liveness/readiness are suppressed
    httpGet: { path: /healthz, port: 8080 }
    periodSeconds: 5
    failureThreshold: 30               ← 5 × 30 = 150 s of boot budget
  livenessProbe:                       ← begins only after startup succeeds
    httpGet: { path: /healthz, port: 8080 }
    periodSeconds: 10
    timeoutSeconds: 2
    failureThreshold: 3
  readinessProbe:
    httpGet: { path: /readyz, port: 8080 }
    periodSeconds: 5
    timeoutSeconds: 2
    failureThreshold: 2
HandlerCostNotes
httpGetCheap — the kubelet makes the request itself2xx/3xx is success; sets Host to the pod IP unless overridden
tcpSocketCheapestOnly proves something is listening, not that it works
grpcCheapUses the standard gRPC health protocol
execExpensive — forks a process every periodLast resort; see Part 6

Part 2 — Timing Arithmetic

⚠️ timeoutSeconds defaults to 1 second, and that is the most common cause of spurious restarts. A JVM in a stop-the-world GC pause, a Node process with a busy event loop, or a container being CPU-throttled (Requests & Limits) will exceed 1 second regularly. The probe times out, three of those in a row restart a perfectly healthy container — and the restart makes the next one more likely, because a cold process is slower.

Part 3 — The Cascading Outage

This is the failure mode worth memorising, because it converts a degraded dependency into a total outage and then lengthens it.

  the health endpoint everyone writes first:

    GET /healthz  →  SELECT 1 from postgres
                     PING redis
                     GET /health on the payments API
                     200 only if all three answered

  wired to LIVENESS. Then the database fails over for 8 seconds:

  t=0     db refuses connections
  t=0-8   EVERY replica's liveness probe fails — they share the dependency
  t=8     failureThreshold reached on all 12 → all 12 containers RESTART
  t=9     db recovers
  t=9-45  12 cold processes reconnect at once: connection storm, empty caches,
          JIT cold, and the herd re-fails the probes
  t=45    service restored

  dependency downtime 8 s  →  user-visible outage 45 s
EndpointTestsWired toWhy
/healthzThe process responds. Nothing else.LivenessA restart cannot fix a database
/readyzDependencies it cannot serve withoutReadinessShedding traffic is proportionate and reversible
/startupzMigrations applied, caches warmStartupSlow boot is not sickness
/debug/depsEverything, verboselyA dashboard. Nothing automated.Diagnosis, not control

Even readiness needs judgement. If every replica marks itself unready during a dependency blip, the Service has zero endpoints and callers get connection failures rather than useful errors. Where the service can still do something useful — serve cached reads, return a degraded response — staying ready and failing individual requests is better than removing the whole fleet from rotation.

Part 4 — Startup Probes

Before startup probes existed, a slow-booting application forced an impossible choice: a long initialDelaySeconds (which delays failure detection for the container's entire life) or a liveness probe that kills the container mid-boot, forever.

  WITHOUT a startup probe — an app that boots in 90 s:
    livenessProbe: { periodSeconds: 10, failureThreshold: 3 }
    → declared dead at t=30 s, restarted, dies again at t=30 s, forever
    $ kubectl get pod api
    api   0/1   CrashLoopBackOff   7   4m       ← a healthy app, never allowed to boot

  the old workaround:
    livenessProbe: { initialDelaySeconds: 150, periodSeconds: 10, failureThreshold: 3 }
    → boots fine, but a wedged process is now undetected for up to 180 s, for ever

  WITH a startup probe:
    startupProbe:  { periodSeconds: 5, failureThreshold: 30 }   ← 150 s of budget
    livenessProbe: { periodSeconds: 10, failureThreshold: 3 }   ← 30 s once running
    → slow boot tolerated AND fast detection afterwards
PropertyStartup probe
Boot budgetfailureThreshold × periodSeconds
While it runsLiveness and readiness are suppressed entirely
On successNever runs again; the other probes take over
On exhausting the budgetThe container is killed and restarted
Cost of a generous budgetNone on a fast boot — it stops at the first success
🔑 Set the startup budget from measured p99 boot time with real headroom, and be generous. There is no penalty for a budget that is too long, because the probe stops at the first success; there is a severe penalty for one that is too short, namely a restart loop that can never complete a boot. Anything that migrates a schema, warms a cache or loads a model at start-up needs one.

Part 5 — Readiness During Shutdown

Readiness is not only about starting. When a pod is deleted, two things happen in parallel, and the race between them drops requests:

  t=0   deletionTimestamp set
        ├─► kubelet sends SIGTERM immediately
        └─► endpoints controller removes the endpoint      (asynchronous)
              └─► kube-proxy on EVERY node rewrites rules  (asynchronous, ~0.5–2 s)

  if the process stops accepting before every node's rules are updated,
  packets still arrive at a socket that is closed → connection refused

lifecycle:
  preStop:
    exec: { command: ["sleep", "10"] }      ← keep serving while rules propagate
terminationGracePeriodSeconds: 45           ← must exceed preStop + real drain time

The endpoint conditions make the intended behaviour explicit — a terminating pod is ready: false but serving: true, so it receives no new traffic while in-flight work drains:

$ kubectl get endpointslices -l kubernetes.io/service-name=api \
    -o jsonpath='{range .items[0].endpoints[*]}{.addresses[0]} ready={.conditions.ready} serving={.conditions.serving} term={.conditions.terminating}{"\n"}{end}'
10.244.1.7 ready=false serving=true  term=true      ← draining
10.244.2.4 ready=true  serving=true  term=false

Full measurements of that race, and the PodDisruptionBudget side of graceful shutdown, are in Disruptions, Draining & Zero-Downtime.

Part 6 — Anti-patterns

Anti-patternWhy it hurts
Liveness = readiness = the same endpointAny dependency failure restarts every replica
/healthz that always returns 200Proves the HTTP server is up and nothing else — but harmless; better than checking a database
exec probes running a runtimeForks a process every period; a JVM probe can cost more than the traffic
timeoutSeconds: 1 on a GC'd runtimeSpurious restarts under load — and restarts make it worse
timeoutSeconds ≥ periodSecondsProbes overlap and pile up
No liveness probe at allA deadlocked process serves errors for ever
Liveness probe on a queue worker's HTTP portThe port answers while the consumer loop is wedged
Readiness that never failsTraffic reaches a pod that cannot serve
Probing through a service-mesh sidecarFails during sidecar restarts, unrelated to the app
For a worker with no HTTP server, check liveness on PROGRESS, not on a port:

  livenessProbe:
    exec:
      command: ["sh","-c","[ $(( $(date +%s) - $(stat -c %Y /tmp/heartbeat) )) -lt 120 ]"]
    periodSeconds: 30
  → the loop touches /tmp/heartbeat each iteration; a wedged consumer is detected
    even though its process is alive and its port is open

❌ One /health endpoint that queries Postgres, Redis and a payments API, wired to both liveness and readiness, with default timings and no startup probe. An eight-second database failover fails the probe on all twelve replicas simultaneously — they share the dependency, so the failures are perfectly correlated — and all twelve containers restart at once. Twelve cold processes then reconnect together, so the connection storm and empty caches make the probes fail again, and an eight-second dependency blip becomes a forty-five-second outage. Separately, the application takes ninety seconds to warm its cache, so with the default thirty-second detection window it is killed mid-boot and crash-loops for ever — which someone "fixes" with initialDelaySeconds: 150, leaving a genuinely wedged process undetected for three minutes for the rest of the container's life. And the one-second default timeout means every stop-the-world GC pause counts as a failure, so healthy pods restart under exactly the load where restarts are most damaging.

✅ Split the endpoints by remedy, give slow boots a startup probe, and size the timings from measurement. Point liveness at a /healthz that touches nothing external — its only remedy is a restart, and a restart cannot repair someone else's database — and expose a separate /readyz for the load balancer, which may consult hard dependencies because shedding traffic is proportionate and reversible. Keep a verbose /debug/deps for humans and wire it to nothing automated. Add a startup probe whose failureThreshold × periodSeconds comfortably exceeds measured p99 boot time — it costs nothing on a fast boot and removes the initialDelaySeconds trade-off entirely, so liveness can then detect a wedged process in ten seconds instead of a hundred and eighty. Raise timeoutSeconds above the runtime's worst GC pause and keep it well under periodSeconds. Prefer httpGet over exec, and for workers with no HTTP server check progress via a heartbeat file rather than a port that answers while the loop is wedged. Finally, pair readiness with a preStop delay so pods keep serving while endpoint removal propagates.

Interview Questions

Beginner: What is the difference between a liveness and a readiness probe?

They have different remedies, and that difference is the whole design.

LivenessReadiness
QuestionIs the process wedged?Can it serve right now?
On failureRestart the containerRemove from Service endpoints
ReversibleNo — the process is killedYes — it comes back when it passes
Check dependencies?NeverHard dependencies only

The rule that follows: a probe may only test what its remedy can fix. Restarting a container cannot repair a database, so a liveness probe must never consult one.

What that looks like in practice: a pod showing Running but 0/1 has failed readiness — the process is fine and receives no traffic. A pod with a climbing restart count has failed liveness.

The third probe, startup, answers "has it finished booting?" and suppresses the other two while it runs, so a slow boot is never mistaken for sickness.

Beginner: An app takes 90 seconds to start and keeps restarting. What is wrong?

The liveness probe is killing it mid-boot. With defaults — periodSeconds: 10, failureThreshold: 3 — the container is declared dead at 30 seconds, restarted, and dies again at 30 seconds, for ever.

$ kubectl get pod api
api   0/1   CrashLoopBackOff   7   4m
$ kubectl get events --field-selector reason=Unhealthy | tail -1
Liveness probe failed: Get "http://10.244.1.7:8080/healthz": connection refused

The wrong fix is initialDelaySeconds: 150. It works, and it delays detection of a genuinely wedged process by 180 seconds for the rest of the container's life.

startupProbe:  { periodSeconds: 5, failureThreshold: 30 }   ← 150 s of boot budget
livenessProbe: { periodSeconds: 10, failureThreshold: 3 }   ← 30 s detection afterwards

Why a startup probe is strictly better: liveness and readiness are suppressed entirely while it runs, and it stops at the first success. A generous budget therefore costs nothing on a fast boot, while a budget that is too short causes a restart loop that can never complete — so err generously.

Mid: A brief database outage caused every replica to restart. Explain.

A liveness probe that checked the database. Every replica shares that dependency, so the probe failures are perfectly correlated — they all fail within the same few seconds and all restart together.

t=0     db fails over: 8 s of refused connections
t=0-8   all 12 replicas' liveness probes fail
t=8     failureThreshold reached → 12 simultaneous restarts
t=9     db recovers
t=9-45  12 cold processes reconnect at once: connection storm, cold caches,
        probes fail again under the herd
t=45    restored

8 seconds of dependency downtime became 45 seconds of outage, and the probe both caused and extended it.

The fix is which endpoint each probe hits: /healthz for liveness, touching nothing external; /readyz for readiness, which may check dependencies because its remedy — stop sending traffic here — is proportionate and reversible.

The subtler point: even readiness needs care. If every replica marks itself unready, the Service has zero endpoints and callers get connection failures instead of useful errors. Where the service can serve cached reads or a degraded response, staying ready and failing individual requests is better than removing the whole fleet.

Mid: How do you size probe timings, and what do the defaults get wrong?

Compute the detection window explicitly, then check each field against how the application actually behaves.

worst-case detection = initialDelaySeconds + failureThreshold × periodSeconds
  defaults:  0 + 3 × 10 = 30 s
  tuned:     0 + 2 × 5  = 10 s
FieldDefaultProblem
timeoutSeconds1Shorter than a JVM GC pause or a throttled container's response
periodSeconds10Fine; trade detection speed against probe cost
failureThreshold3Reasonable — enough to ride out one blip
initialDelaySeconds0Should stay 0; use a startup probe instead

The one-second timeout is the biggest offender. A stop-the-world GC pause, a busy event loop, or CPU throttling from a tight CPU limit will exceed it regularly. Three of those in a row restart a healthy container — and because a cold process is slower, the restart makes the next failure more likely.

Keep timeoutSeconds well below periodSeconds, or probes overlap and pile up under load, and note that successThreshold must be 1 for liveness and startup — the API rejects anything else.

Senior: Design health checking for a service with a database, a cache and an external API.

Classify each dependency by what should happen when it fails, then wire probes to match.

DependencyService without itAppears in
DatabaseCannot serve core requests/readyz
CacheSlower, still correctNeither probe
External payments APISome endpoints fail, most workNeither — circuit breaker instead
The process itselfNothing works/healthz
/healthz   → event loop responds. Nothing external. → liveness
/readyz    → database pool has a usable connection   → readiness / load balancer
/debug/deps→ everything, verbosely                   → a dashboard only

The cache row is the interesting one. Putting Redis in readiness means a Redis blip removes the entire fleet from rotation, when the service could have served every request slightly slower. Optional dependencies belong in neither probe — degrade, and expose the state as a metric.

Beyond the endpoints, three things shorten the tail of any dependency incident: a circuit breaker so failures are absorbed at the call site rather than propagating into health state; jitter so recovery is staggered instead of a thundering herd; and serving stale-but-flagged data where the domain allows it.

The framing I would give: a health check is a control-plane input, and every control-plane input is an amplifier. Before adding a condition, ask what will act on it and whether that action helps. Most "outages caused by monitoring" are exactly this mistake.

Senior: How do you health-check workloads with no HTTP server — queue workers, batch consumers?

Check progress, not presence. A port that answers, or a process that exists, both stay true while the consumer loop is deadlocked — which is precisely the failure a liveness probe should catch.

livenessProbe:
  exec:
    command: ["sh","-c","[ $(( $(date +%s) - $(stat -c %Y /tmp/heartbeat) )) -lt 120 ]"]
  periodSeconds: 30
  timeoutSeconds: 5
  → the worker touches /tmp/heartbeat each loop iteration
ApproachDetects a wedged loop?Cost
TCP probe on any open port❌Lowest
Process exists❌—
Heartbeat file mtime✅test builtin — negligible
Tiny HTTP server exposing last-progress✅Cheap; also gives metrics

Sizing the heartbeat threshold is the subtle part. It must exceed the longest legitimate gap between iterations — an empty queue, a long poll, a slow single item — or you restart a worker that is merely idle. Where item processing time varies widely, heartbeat at the start of each item and size the threshold to the p99 item duration rather than to the loop period.

Readiness for a worker is usually meaningless — nothing routes traffic to it — so I normally omit it, with one exception: if the worker is behind a Service for metrics scraping, readiness should reflect whether the metrics endpoint is up, not whether the queue is being consumed.

And prefer the tiny HTTP server where you can add one: it avoids forking a process every period, and the same endpoint can expose last-processed timestamps and queue depth, which is what you actually want on a dashboard.

6 (hard): Audit a cluster's probe configuration for the known failure modes.
Solution 
$ cat > tools/probe-audit.sh <<'SH'
#!/usr/bin/env bash
# Read-only audit of probe configuration against known failure modes.
set -uo pipefail
kubectl get deploy,statefulset,daemonset -A -o json | jq -r '
  .items[] as $w | $w.spec.template.spec.containers[] as $c |
  ($w.metadata.namespace + "/" + $w.metadata.name + "/" + $c.name) as $id |

  # 1. liveness and readiness on the SAME path
  (if ($c.livenessProbe.httpGet.path // "L") == ($c.readinessProbe.httpGet.path // "R")
      and $c.livenessProbe != null and $c.readinessProbe != null
   then "  FAIL \($id) liveness and readiness share \($c.livenessProbe.httpGet.path)" else empty end),

  # 2. no liveness probe at all
  (if $c.livenessProbe == null
   then "  WARN \($id) no liveness probe — a deadlock is undetectable" else empty end),

  # 3. default 1s timeout
  (if $c.livenessProbe != null and ($c.livenessProbe.timeoutSeconds // 1) == 1
   then "  WARN \($id) liveness timeoutSeconds=1 (default) — GC pauses restart it" else empty end),

  # 4. long initialDelaySeconds instead of a startup probe
  (if ($c.livenessProbe.initialDelaySeconds // 0) > 30 and $c.startupProbe == null
   then "  FAIL \($id) initialDelaySeconds=\($c.livenessProbe.initialDelaySeconds) with no startupProbe" else empty end),

  # 5. timeout >= period (overlapping probes)
  (if $c.livenessProbe != null and
      ($c.livenessProbe.timeoutSeconds // 1) >= ($c.livenessProbe.periodSeconds // 10)
   then "  FAIL \($id) liveness timeout >= period — probes overlap" else empty end),

  # 6. exec probes (fork cost)
  (if $c.livenessProbe.exec != null
   then "  INFO \($id) exec liveness probe: \($c.livenessProbe.exec.command | join(" ") | .[0:50])" else empty end),

  # 7. slow detection
  (if $c.livenessProbe != null and
      ((($c.livenessProbe.initialDelaySeconds // 0) +
        (($c.livenessProbe.failureThreshold // 3) * ($c.livenessProbe.periodSeconds // 10))) > 120)
   then "  WARN \($id) worst-case detection \((($c.livenessProbe.initialDelaySeconds // 0) + (($c.livenessProbe.failureThreshold // 3) * ($c.livenessProbe.periodSeconds // 10))))s" else empty end),

  # 8. no readiness on something behind a Service
  (if $c.readinessProbe == null
   then "  WARN \($id) no readiness probe — traffic arrives before it can serve" else empty end)
'
SH

🎯 Key Takeaways

  • A probe may only test what its own remedy can fix — restart, shed traffic, or keep waiting. Every probe design question reduces to that.
  • Liveness restarts the container (irreversible); readiness removes it from endpoints (reversible) — verified with restart counts of 1 and 0 respectively.
  • Liveness must never consult a dependency: an 8-second database blip restarted 4 of 4 replicas and produced 137 failures on endpoints that never touch the database.
  • Repointing the same probe at a process-only /healthz gave 0 restarts and 0 failures under the identical fault.
  • Even readiness needs judgement: if every replica marks itself unready, the Service has zero endpoints — serve degraded where the domain allows.
  • Worst-case detection is initialDelaySeconds + failureThreshold × periodSeconds — measured at 29 s for the defaults.
  • timeoutSeconds defaults to 1 second and is the most common cause of spurious restarts: a 2-second response restarted a healthy server twice in 30 s, and 0 times at timeout: 4.
  • Keep timeoutSeconds well under periodSeconds, or probes overlap and add load to a struggling container.
  • A 90-second boot with default liveness crash-loops for ever — killed at ~30 s, five times over.
  • initialDelaySeconds fixes the boot and permanently blinds detection; a startup probe gave ready-at-94 s and 11-second wedge detection.
  • A generous startup budget costs nothing, because the probe stops at the first success — err generously, size from measured p99 boot.
  • Startup probes suppress liveness and readiness entirely while running, then never run again.
  • successThreshold must be 1 for liveness and startup; the API rejects anything else.
  • Readiness also matters at shutdown: endpoint removal and SIGTERM are concurrent, so a preStop delay is needed while kube-proxy rules propagate.
  • A terminating pod is ready: false, serving: true — no new traffic, in-flight work drains.
  • A TCP probe on a worker's port never detects a wedged loop — demonstrated: the consumer was dead for two minutes with 0 restarts.
  • Check progress instead — a heartbeat file's mtime caught the same wedge in 48 s using a test builtin.
  • Size the heartbeat threshold above p99 item duration, and heartbeat at item start, or slow items cause false restarts.
  • Prefer httpGet over exec: exec forks a process every period, and a runtime-based probe can cost more than the traffic.
  • A health check is a control-plane input, and every control-plane input is an amplifier — most "outages caused by monitoring" are this mistake.
