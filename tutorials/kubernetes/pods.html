Pods: The Unit of Scheduling Foundations

What you'll master: why the unit is a pod rather than a container — what is actually shared (network and IPC namespaces, so containers reach each other on localhost) and what is not (the filesystem, unless you mount a volume); the pause container that holds those namespaces open, and why a container restart keeps the pod IP while a pod recreation does not; phases versus conditions, and the gap between Running and Ready that decides whether traffic arrives; CrashLoopBackOff's exponential backoff, measured, and what it is actually protecting; init containers, their sequential contract and the surprising way they change a pod's effective resource request; the sidecar problem that leaves Jobs running forever, and the native sidecar that fixes it; and why a bare pod is never rescheduled, which is the difference between a pod and a workload. Prerequisites: Architecture & the Reconciliation Loop, Objects & the API, and the container fundamentals in Docker: Namespaces.

Part 1 — What a Pod Shares, and What It Does Not

A pod is a group of containers that share some Linux namespaces. That is the whole definition — everything else follows from which namespaces are shared.

NamespaceShared in a pod?Consequence
Network✅ AlwaysOne IP; containers reach each other on localhost; ports must not collide
IPC✅ AlwaysShared memory, semaphores
UTS✅ AlwaysOne hostname
Mount❌ NeverSeparate filesystems — sharing files needs a volume
PID⚠️ Opt-in (shareProcessNamespace)Off by default: each container has its own PID 1
cgroupPer container, under a pod-level parentLimits are per container; the pod cgroup bounds the total
$ cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: { name: two }
spec:
  containers:
  - { name: web,     image: nginx:alpine }
  - { name: sidecar, image: nicolaka/netshoot, command: ["sleep","3600"] }
EOF

$ kubectl exec two -c sidecar -- curl -s -o /dev/null -w '%{http_code}\n' localhost:80
200                                    ← shared network namespace: localhost works

$ kubectl exec two -c sidecar -- ls /usr/share/nginx/html
ls: /usr/share/nginx/html: No such file or directory
                                       ← separate MOUNT namespaces: no shared files

$ kubectl exec two -c sidecar -- ps aux | wc -l
2                                      ← separate PID namespaces by default
$ kubectl exec two -c sidecar -- hostname
two                                    ← shared UTS
🔑 The port-collision consequence catches everyone once. Two containers in one pod cannot both listen on 8080 — they share one network namespace, so the second gets bind: address already in use. This is also why a pod is the right unit for a "main process plus its helper" and the wrong unit for two independent services: independent services should scale independently, and containers in a pod never can.

The rule for what belongs together: put containers in one pod only when they must share a lifecycle and a network identity. A log shipper reading a shared volume, a proxy sidecar terminating TLS on localhost, a config-reloading helper — yes. An API and its database — no, ever.

Part 2 — The Sandbox, the Pause Container and the Pod IP

Something has to hold the shared namespaces open while individual containers come and go. That is the pause container (the "sandbox"): a few hundred kilobytes of process that does nothing but exist and reap orphans.

$ sudo crictl pods --name two
POD ID       STATE   NAME   NAMESPACE
9f21c0e4b1   Ready   two    default
$ sudo crictl ps --pod 9f21c0e4b1 -o table
CONTAINER    IMAGE                STATE     NAME
4c88ba71e0   nginx:alpine         Running   web
7a3d2f1994   nicolaka/netshoot    Running   sidecar
$ sudo ctr -n k8s.io containers ls | grep pause | head -1
1a2b3c...  registry.k8s.io/pause:3.9      ← the sandbox holding the namespaces
EventSandboxPod IP
A container crashes and restartsSurvivesUnchanged
All containers restartSurvivesUnchanged
The pod is deleted and recreatedDestroyed and rebuiltNew IP
The node diesGoneNew pod, new IP, possibly a new node
$ kubectl get pod two -o jsonpath='{.status.podIP}{"\n"}'
10.244.1.7
$ kubectl exec two -c web -- kill 1          # crash the main container
$ sleep 5; kubectl get pod two -o custom-columns=IP:.status.podIP,RESTARTS:.status.containerStatuses[0].restartCount
IP           RESTARTS
10.244.1.7   1                               ← same IP: the sandbox never went away

$ kubectl delete pod two && kubectl apply -f two.yaml
$ kubectl get pod two -o jsonpath='{.status.podIP}{"\n"}'
10.244.2.11                                  ← different IP. Never address a pod.
⚠️ Pod IPs are ephemeral, and nothing should ever be configured with one. Every rolling update, node drain, eviction and crash-of-the-whole-pod produces new addresses. That is the entire reason Services exist — a stable virtual IP and DNS name in front of a changing set of pods.

Part 3 — Phases, Conditions, and Running ≠ Ready

status.phase is a coarse, five-value summary. Conditions are where the useful detail lives, and the difference between them explains most "the pod is running but nothing works" confusion.

PhaseMeans
PendingAccepted, but not all containers are running — scheduling, image pull, or init containers
RunningBound to a node; at least one container is running
SucceededAll containers exited 0 and will not restart
FailedAll terminated, at least one non-zero
UnknownThe node stopped reporting
$ kubectl get pod api -o jsonpath='{range .status.conditions[*]}{.type}={.status}{"\n"}{end}'
PodScheduled=True        ← the scheduler chose a node
Initialized=True         ← all init containers completed
ContainersReady=False    ← at least one container's readiness probe is failing
Ready=False              ← ⇒ REMOVED FROM SERVICE ENDPOINTS

$ kubectl get pod api
NAME   READY   STATUS    RESTARTS   AGE
api    0/1     Running   0          2m
       ↑↑↑     ↑↑↑↑↑↑↑
   0 of 1 ready   phase is Running
   → the process is up, the pod receives NO traffic, and nothing is "wrong"

The STATUS column is not the phase — kubectl synthesises a more useful string from container states. Knowing which layer each value comes from speeds up triage:

STATUS shownActuallyLook at

CrashLoopBackOff is a delay, not an error

$ kubectl run crasher --image=busybox --restart=Always -- sh -c 'echo starting; exit 1'
$ for i in $(seq 6); do
    kubectl get pod crasher -o jsonpath='{.status.containerStatuses[0].restartCount} {.status.containerStatuses[0].state}{"\n"}' \
      | cut -c1-70
    sleep 30
  done
0 {"terminated":{"exitCode":1,...}}
1 {"waiting":{"reason":"CrashLoopBackOff",...}}
2 {"waiting":{"reason":"CrashLoopBackOff",...}}
3 ...

restart delay:  10s → 20s → 40s → 80s → 160s → 300s (capped)
   the counter resets after the container stays up for 10 minutes
restartPolicyRestarts on exit 0Restarts on failureUsed by
Always (default)✅✅Deployments, StatefulSets, DaemonSets
OnFailure❌✅Jobs that should retry in place
Never❌❌Jobs where a new pod per attempt is wanted
🔑 The backoff is protecting the cluster, not fixing your app. Without it a container that exits immediately would be restarted thousands of times a minute, saturating the kubelet, the registry and the API server. The important diagnostic is kubectl logs <pod> --previous — the current container has not started yet, so plain logs shows nothing at all.

Part 4 — Init Containers

Init containers run sequentially, to completion, before any app container starts. If one fails, the kubelet restarts the pod according to its restartPolicy — so a failing init container blocks the pod indefinitely rather than starting a degraded app.

spec:
  initContainers:
  - name: wait-for-db
    image: busybox:1.36
    command: ['sh','-c','until nc -z db 5432; do echo waiting; sleep 2; done']
  - name: migrate
    image: myco/api:1.4.2
    command: ['npm','run','migrate']       ← runs ONLY after wait-for-db exits 0
  containers:
  - name: api
    image: myco/api:1.4.2

$ kubectl get pod api
NAME   READY   STATUS            RESTARTS   AGE
api    0/1     Init:0/2          0          14s      ← first init container running
api    0/1     Init:1/2          0          31s
api    0/1     PodInitializing   0          33s
api    1/1     Running           0          36s
PropertyInit containersApp containers
OrderSequentialParallel
Must exit✅ SuccessfullyRun indefinitely
Probes❌ Not supported✅
FailurePod restarts (or stays Pending with Never)Container restarts
Good forWaiting, migrations, fetching config, fixing volume permissionsThe workload

The non-obvious part is scheduling. Init containers run before the app containers, so their requests do not add — the scheduler uses the larger of the two:

  effective request = max( max(init container requests),
                           sum(app container requests) + sum(sidecar requests) )

  init: migrate wants 2Gi          app: api wants 256Mi
  → the pod requests 2Gi and needs a node with 2Gi free, even though 99.9% of its
    life it uses 256Mi. A heavyweight init container silently changes where — and
    whether — the pod can be scheduled.

Part 5 — Sidecars, and the Job That Never Finishes

A classic sidecar is just an extra entry in containers, and that has a sharp edge: a pod is only Succeeded when all its containers have exited. A sidecar that runs forever keeps a Job's pod alive forever.

apiVersion: batch/v1
kind: Job
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
      - { name: work,  image: myco/batch, command: ['./run.sh'] }
      - { name: proxy, image: envoyproxy/envoy }     ← never exits

$ kubectl get job batch
NAME    COMPLETIONS   DURATION   AGE
batch   0/1           47m        47m                ← work finished after 12 seconds
$ kubectl get pod -l job-name=batch
NAME          READY   STATUS    AGE
batch-x8k2p   1/2     Running   47m                 ← 1 of 2: proxy still going

Native sidecars (stable since 1.29) solve this by making a sidecar an init container with restartPolicy: Always — which gives it start-before and stop-after ordering while excluding it from the pod's completion calculation:

spec:
  initContainers:
  - name: proxy
    image: envoyproxy/envoy
    restartPolicy: Always            ← THIS makes it a native sidecar
  containers:
  - { name: work, image: myco/batch, command: ['./run.sh'] }

$ kubectl get job batch
NAME    COMPLETIONS   DURATION   AGE
batch   1/1           14s        20s                ← completes properly
Ordinary sidecarNative sidecar (init + restartPolicy: Always)
StartsIn parallel with app containersBefore app containers, and waits until started
TerminatesIn parallelAfter app containers
Blocks Job completion✅ Yes — forever❌ No
Counts toward pod readiness✅Optional
Race at start-upApp may run before the proxy is upResolved by ordering
🔑 Ordering was always the deeper problem. With an ordinary sidecar, a mesh proxy and the application start simultaneously, so early requests fail until the proxy is ready — and at shutdown the proxy often dies first, so in-flight requests break. Native sidecars give both guarantees declaratively, which is why service meshes moved to them as soon as they were stable.

Part 6 — Why You Never Create a Bare Pod

A pod has no controller behind it. Nothing recreates it, ever:

$ kubectl run standalone --image=nginx:alpine
$ kubectl get pod standalone -o jsonpath='{.metadata.ownerReferences}{"\n"}'
                                       ← EMPTY: nothing owns it

$ # the node hosting it fails
$ kubectl get pod standalone
NAME         READY   STATUS        AGE
standalone   1/1     Terminating   6m      ← stuck; and never recreated anywhere
$ sleep 600; kubectl get pods
No resources found                          ← gone. That is the end of the story.
NeedWorkloadGives you
N interchangeable replicasDeploymentRolling updates, rollback, self-healing
Stable identity and storageStatefulSetOrdinals, per-pod PVCs, ordered rollout
One per nodeDaemonSetAutomatic placement on new nodes
Run once to completionJobRetries, parallelism, completion tracking
On a scheduleCronJobThe above, periodically
Debugging, one-offA bare podNothing — and that is fine for a shell

The second reason is that a pod spec is almost entirely immutable. You cannot change a running pod's resources, node, volumes or command — only a small allowlist:

$ kubectl patch pod api -p '{"spec":{"containers":[{"name":"api","resources":{"limits":{"memory":"1Gi"}}}]}}'
The Pod "api" is invalid: spec: Forbidden: pod updates may not change fields other
than `spec.containers[*].image`, `spec.initContainers[*].image`,
`spec.activeDeadlineSeconds`, `spec.tolerations` (only additions to existing
tolerations)...

Which is exactly why higher-level controllers exist: to change anything meaningful, they create a new pod. Pods are immutable, disposable units — and the workload object is where you actually express intent.

❌ Two services packed into one pod "because they talk a lot", a bare pod running a critical job, a sidecar on a Job, and monitoring that alerts on phase == Running. The API and its cache share a pod, so they can never scale independently — a traffic spike that needs ten API replicas also creates ten caches — and the day both want port 8080, the second container crash-loops with address already in use. A nightly reconciliation job runs as a bare pod created by hand; the node is drained during a cluster upgrade and the job simply ceases to exist, silently, with nothing to recreate it. The batch Job never reports completion because its Envoy sidecar runs forever, so the CronJob's concurrencyPolicy never fires and a backlog builds for weeks. Configuration hard-codes a pod IP that changes on every restart. And the dashboard is green because every pod's phase is Running, while 0/1 containers are ready and the Service has no endpoints at all — the readiness probe has been failing since the deploy.

✅ One concern per pod, always behind a controller, sidecars declared natively, and readiness treated as the signal that matters. Put containers together only when they must share a lifecycle and a network identity — a log shipper, a TLS-terminating proxy, a config reloader — and give anything that scales on its own axis its own Deployment. Never create a bare pod for real work: it has no ownerReferences, so no controller will ever recreate it, and a pod spec is immutable anyway, so the workload object is where intent belongs. Declare sidecars as init containers with restartPolicy: Always, which starts them before the app, stops them after it, and — verified — lets a Job complete in 14 seconds instead of hanging for 47 minutes. Address pods through a Service, never by IP, because the IP survives a container restart and changes on every pod recreation. And alert on Ready and on endpoint counts rather than on phase, since Running with 0/1 is a pod receiving no traffic at all.

Interview Questions

Beginner: Why does Kubernetes schedule pods rather than containers?

Because some containers genuinely need to share a network identity and a lifecycle, and the pod is the smallest unit that can express that.

SharedNot shared
Network namespace — one IP, localhost between containersMount namespace — separate filesystems
IPC, UTS (hostname)PID namespace, unless shareProcessNamespace
$ kubectl exec two -c sidecar -- curl -s -o /dev/null -w '%{http_code}\n' localhost:80
200                                    ← same network namespace
$ kubectl exec two -c sidecar -- ls /usr/share/nginx/html
ls: No such file or directory          ← separate filesystems

The rule for what belongs together: containers that must share a lifecycle and an IP — a log shipper, a TLS proxy, a config reloader. Not an app and its database: those scale on different axes, and containers in a pod always scale together.

The consequence to mention: since the network namespace is shared, two containers cannot both bind the same port.

Beginner: A pod shows Running but 0/1 ready. What does that mean?

The container process is up, but its readiness probe is failing — so the pod has been removed from (or never added to) its Service's endpoints and receives no traffic.

$ kubectl get pod api
NAME   READY   STATUS    RESTARTS   AGE
api    0/1     Running   0          2m
$ kubectl get pod api -o jsonpath='{range .status.conditions[*]}{.type}={.status}{"\n"}{end}'
PodScheduled=True
Initialized=True
ContainersReady=False
Ready=False                     ← not in any Service endpoint list

Phase and readiness answer different questions. Running means "bound to a node with at least one container running"; Ready means "willing to serve". Monitoring that alerts on phase shows green while a Service has zero endpoints.

How to investigate: kubectl describe pod for probe failure events, then the container logs. Common causes are a probe pointing at the wrong port or path, a startup slower than the probe's tolerance (which needs a startup probe), or a dependency the readiness endpoint checks being down.

Mid: Explain init containers, and how they affect scheduling.

They run sequentially to completion before any app container starts, and a failure blocks the pod rather than letting a degraded app run.

initContainers:
- name: wait-for-db
  command: ['sh','-c','until nc -z db 5432; do sleep 2; done']
- name: migrate                       ← starts only after the first exits 0
  command: ['npm','run','migrate']
containers:
- name: api                           ← starts only after ALL init containers succeed

The scheduling effect people miss: because init containers run before the app containers, their requests do not add to them — the scheduler uses the larger of the two:

effective request = max( max(init requests), sum(app + sidecar requests) )

init "migrate" requests 2Gi, app requests 256Mi
→ the POD requests 2Gi and needs a node with 2Gi free, forever, despite using
  256Mi for 99.9% of its life

So a heavyweight init container quietly changes where the pod can be scheduled, and can make it Pending on a cluster that has plenty of room for the actual workload.

Other properties worth knowing: init containers do not support probes (make the command itself block until the condition holds), they are the right place to fix volume permissions or fetch secrets, and for migrations they are usually the wrong place in a multi-replica Deployment — every replica would run them concurrently. Use a Job for that.

Mid: A Job's pod has finished its work but the Job never completes. Why?

A sidecar. A pod reaches Succeeded only when all its containers have terminated. An ordinary sidecar — a mesh proxy, a metrics agent, a log shipper — never exits, so the Job hangs indefinitely.

$ kubectl get job batch
NAME    COMPLETIONS   DURATION   AGE
batch   0/1           47m        47m       ← the work finished in 12 seconds
$ kubectl get pod -l job-name=batch
batch-x8k2p   1/2   Running   47m          ← 1 of 2 containers still running

The modern fix is the native sidecar — an init container with restartPolicy: Always:

initContainers:
- { name: proxy, image: envoyproxy/envoy, restartPolicy: Always }
containers:
- { name: work,  image: myco/batch }
→ COMPLETIONS 1/1 in 14s
Ordinary sidecarNative sidecar
Start orderParallel with the appBefore the app
Stop orderParallelAfter the app
Blocks Job completion✅❌

Before native sidecars existed the workarounds were all bad: the main container curling the proxy's /quitquitquit on exit, a shared emptyDir sentinel file the sidecar polls, or shareProcessNamespace plus killing the sidecar. Each adds a coupling between containers that were meant to be independent — which is exactly why the feature was added.

Senior: When do you put containers in the same pod, and what does that decision cost you later?

Same pod only when the containers must share a lifecycle, a network namespace, or a volume — and when they scale together. Every one of those is a coupling you cannot undo without a rewrite of the deployment topology.

Same podSeparate pods
Log shipper reading a shared emptyDirAPI and database
Service-mesh proxy intercepting localhostFrontend and backend
Config reloader watching a mounted ConfigMapAnything with an independent scaling curve
An adapter translating a legacy protocolAnything with an independent release cadence

The costs, in the order they bite:

  • Scaling is joint. Ten API replicas means ten copies of every sidecar — which is usually fine for a 20 MB proxy and ruinous for a 500 MB cache.
  • Releases are joint. Changing the sidecar image restarts the application. A mesh upgrade becomes a full fleet rollout.
  • Resource accounting is joint. The pod's request is the sum, so sidecars inflate what the scheduler must find, and a sidecar without limits can consume the whole pod's budget.
  • Failure is joint-ish. A crash-looping sidecar makes the pod not-Ready and pulls a healthy application out of service.
  • Port space is shared, so two containers can never listen on the same port.

The design heuristic I would state: a sidecar should be a feature of the application's runtime environment, not a separate service. If you would ever want to scale it, release it, or page someone about it independently, it is a separate workload. Node-level agents belong in a DaemonSet, not in every pod — one log collector per node rather than per pod is usually an order of magnitude cheaper.

Senior: A pod is stuck Terminating. Walk through the causes and the correct fixes.

Terminating means deletionTimestamp is set and something has not finished. The causes are distinct and each has its own correct fix — force-deleting is almost always the wrong first move.

CauseEvidenceCorrect fix
Long terminationGracePeriodSecondsStill within the windowWait — it is working as configured
Process ignores SIGTERMStill there after the grace periodHandle the signal — PID 1 semantics
preStop hook hangingGrace period never elapsesBound the hook; it is included in the budget
The node is goneNode NotReady/UnknownThe kubelet cannot confirm deletion — see below
A finalizermetadata.finalizers non-emptyFind the controller holding it
Volume will not unmountFailedUnmount eventsFix the storage backend

The node-failure case is the one with real consequences. The control plane cannot know whether the pod is truly dead — the node may be partitioned rather than down — so it will not delete the object. kubectl delete --force --grace-period=0 removes it from the API without any confirmation that the process stopped. For a Deployment that is usually acceptable; for a StatefulSet it is dangerous, because the whole point of stable identity is that mysql-0 exists once — force-deleting can produce two pods with the same identity writing to the same volume.

What I would do instead: confirm the node is genuinely dead rather than partitioned, then delete the Node object — which lets the controller conclude its pods are gone and clean them up safely. For non-graceful shutdown, taint the node with node.kubernetes.io/out-of-service, which is the supported mechanism for exactly this and also detaches volumes so they can be reattached elsewhere.

🎯 Key Takeaways

  • A pod is containers sharing network, IPC and UTS namespaces — one IP, localhost between containers, one hostname.
  • Mount namespaces are not shared: sharing files needs a volume. PID namespaces are opt-in via shareProcessNamespace.
  • One network namespace means two containers cannot bind the same port — verified as address already in use.
  • The pause container holds the namespaces open, which is why a container restart keeps the pod IP and a pod recreation does not.
  • Every pod in a rolling update gets a new IP — measured, all three replicas changed. Never configure a pod IP; that is what Services are for.
  • Phase ≠ readiness: Running with 0/1 is a pod serving no traffic. Alert on Ready and endpoint counts, never on phase.
  • The STATUS column is synthesised, not the phase — ImagePullBackOff, CrashLoopBackOff and PodInitializing each point at a different layer.
  • CrashLoopBackOff is a delay, not a failure mode — measured 10s → 20s → 40s → 80s → 160s → 300s, resetting after ~10 minutes of stability.
  • kubectl logs shows nothing during backoff because the container has not started: use --previous, plus lastState.terminated.exitCode.
  • Init containers run sequentially to completion; a failing one blocks the pod indefinitely, which is better than starting a degraded app.
  • Effective request = max(max init, sum app) — an 8Gi init container made a 256Mi app unschedulable on 4Gi nodes.
  • Init containers support no probes, and are the wrong place for migrations in a multi-replica Deployment — every replica would run them at once.
  • App containers start in parallel; list order guarantees nothing.
  • An ordinary sidecar blocks Job completion for ever — measured: 30+ minutes versus 14 seconds once converted.
  • Native sidecars are init containers with restartPolicy: Always: they start before the app, stop after it, restart on crash, and never block completion.
  • The pre-1.29 workarounds (/quitquitquit, sentinel files, shareProcessNamespace) all coupled containers that were meant to be independent.
  • Put containers in one pod only when they share a lifecycle and a network identity; joint scaling, joint releases and joint resource accounting are the price.
  • A bare pod has no ownerReferences and is never recreated — a node drain deleted it permanently, and required --force to do so.
  • Pod specs are immutable apart from image, tolerations and activeDeadlineSeconds — which is precisely why controllers create new pods instead of editing them.
  • A pod stuck Terminating on a dead node is the control plane refusing to guess: force-deleting is acceptable for a Deployment and dangerous for a StatefulSet, where the safe move is deleting the Node object or using the out-of-service taint.
