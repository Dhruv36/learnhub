ConfigMaps & Secrets Configuration & State

What you'll master: the uncomfortable truth that a Secret is a ConfigMap with base64 encoding and separate RBAC — not encryption — demonstrated by reading one straight out of etcd; the update-semantics table that explains every "I changed the config and nothing happened" report: env vars never update, volume mounts update in about a minute, and subPath mounts never update at all; encryption at rest and why the KMS provider is the only version that protects against a stolen etcd backup; the RBAC reality that anyone who can create a pod in a namespace can read every Secret in it; why immutable: true is a performance feature as much as a safety one, and the measured kubelet load it removes; the hashed-name pattern that makes configuration part of a Deployment revision so rollback restores both; and where external secret operators and workload identity replace stored secrets entirely. Prerequisites: Deployments, Pods, and Docker: Environment & Secrets.

Part 1 — A Secret Is Not Encrypted

ConfigMaps and Secrets are the same object with different defaults. The differences are real but far smaller than the names suggest:

ConfigMapSecret
Stored asPlain stringsbase64 — an encoding, not encryption
In etcdPlaintextPlaintext unless encryption at rest is configured
Shown by kubectl describeFull valuesOnly sizes
Separate RBAC verbsYesYes — the real separation
Kept in memory on the node (tmpfs)❌✅ Never written to node disk
Size limit~1 MB~1 MB
TypedNoYes (tls, dockerconfigjson, …)
$ kubectl create secret generic db --from-literal=password=hunter2
$ kubectl get secret db -o jsonpath='{.data.password}'
aHVudGVyMg==
$ kubectl get secret db -o jsonpath='{.data.password}' | base64 -d
hunter2                              ← "encryption" that ships with a decoder in coreutils

$ sudo ETCDCTL_API=3 etcdctl --cacert=/etc/kubernetes/pki/etcd/ca.crt \
    --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key \
    get /registry/secrets/default/db | strings | grep -A1 password
password
hunter2                              ← PLAINTEXT on disk, in every etcd backup
⚠️ An etcd snapshot is a plaintext dump of every credential in the cluster unless encryption at rest is enabled. Backups get copied to object storage, downloaded for disaster-recovery drills, and shared with vendors — which is why "we use Secrets" is not an answer to "how are credentials protected". Encryption at rest, covered in Part 3, is the missing half.

$ kubectl create cm app --from-literal=LOG_LEVEL=info
$ kubectl exec deploy/web -- printenv LOG_LEVEL; kubectl exec deploy/web -- cat /etc/app/LOG_LEVEL
info
info
$ kubectl create cm app --from-literal=LOG_LEVEL=debug --dry-run=client -o yaml | kubectl apply -f -

$ sleep 90
$ kubectl exec deploy/web -- printenv LOG_LEVEL
info                                 ← env: injected once, at container start
$ kubectl exec deploy/web -- cat /etc/app/LOG_LEVEL
debug                                ← volume: the FILE updated, with no restart
$ kubectl exec deploy/web -- cat /etc/single/LOG_LEVEL
info                                 ← subPath: a one-time copy, never refreshed
🔑 The volume update is real and almost always useless. The file changes; the process keeps whatever it parsed at start-up. Unless the application watches the file or handles SIGHUP, "config updates live" is a property of the filesystem and not of your service. Either implement a reload or make configuration changes trigger a rollout — see Deployments.

Two mechanical details that cause bug reports. Projected files are symlinks into a ..data directory that the kubelet swaps atomically, so a reader never sees a half-written file — but code that resolves the real path once and caches the inode will read a stale file forever. And subPath bypasses that mechanism entirely, which is exactly why it never updates.

$ kubectl exec deploy/web -- ls -la /etc/app/
lrwxrwxrwx 1 root root  17 Aug 19 12:31 LOG_LEVEL -> ..data/LOG_LEVEL
lrwxrwxrwx 1 root root  31 Aug 19 12:31 ..data -> ..2026_08_19_12_31_02.418273911
drwxr-xr-x 2 root root  60 Aug 19 12:31 ..2026_08_19_12_31_02.418273911

Part 3 — Encryption at Rest, and Who Can Actually Read a Secret

# /etc/kubernetes/encryption-config.yaml  (referenced by --encryption-provider-config)
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources: [secrets, configmaps]
  providers:
  - kms:                                  ← envelope encryption, key in an external KMS
      apiVersion: v2
      name: cloud-kms

$ sudo etcdctl get /registry/secrets/default/db | strings | head -2

$ kubectl get secret db -o jsonpath='{.data.password}' | base64 -d

# existing Secrets are only re-encrypted when rewritten:
$ kubectl get secrets -A -o json | kubectl replace -f -

Pod creation is secret reading

$ kubectl auth can-i get secrets --as=system:serviceaccount:shop:deployer -n shop
no
$ kubectl auth can-i create pods --as=system:serviceaccount:shop:deployer -n shop
yes

$ kubectl -n shop run leak --image=busybox --overrides='{"spec":{"containers":[{"name":"c",
    "image":"busybox","command":["sh","-c","cat /s/password"],
    "volumeMounts":[{"name":"s","mountPath":"/s"}]}],
    "volumes":[{"name":"s","secret":{"secretName":"db"}}]}}' --restart=Never
$ kubectl -n shop logs leak
hunter2                                   ← "cannot read secrets" was not true
⚠️ create pods in a namespace is equivalent to get secrets in that namespace. The kubelet mounts the Secret on the pod's behalf, so no secret-reading permission is required by the requester. Any RBAC design that grants pod creation while withholding secret access is describing a boundary that does not exist — the real boundary is the namespace. See RBAC.

Part 4 — Immutability, Hashed Names and the Rollout Problem

Every kubelet running a pod that mounts a ConfigMap watches that object. At scale that is a large amount of API server work for data that never changes:

$ kubectl create cm app-config --from-literal=LOG_LEVEL=info
$ kubectl patch cm app-config -p '{"immutable":true}'
configmap/app-config patched

$ kubectl patch cm app-config -p '{"data":{"LOG_LEVEL":"debug"}}'
ConfigMap "app-config" is invalid: data: Forbidden: field is immutable when
`immutable` is set
immutable: true givesDetail
No kubelet watchThe kubelet stops watching the object entirely — a significant API-server saving on large clusters
Accidental-change protectionA bad edit cannot silently reach running pods
Forces the hashed-name patternChanging config means a new object, hence a new pod template
CostYou must create a new object and update references — which is the point
THE PATTERN — content hash in the NAME:

  app-config-9f21c0e   immutable: true     ← referenced by the Deployment template
        ↓ config change
  app-config-4c88ba7   immutable: true     ← new name = new template = rollout

  · Kustomize does this automatically:  configMapGenerator + disableNameSuffixHash: false
  · Helm equivalent: a checksum/config annotation on the pod template
  · Old objects are garbage-collected once no revision references them

The decisive advantage is what happens on rollback. When the configuration name is part of the pod template, kubectl rollout undo restores the image and its configuration together. With a mutable shared name, rollback gives you the old image reading the new configuration — a combination nobody tested.

# External Secrets Operator: the Git artefact contains a POINTER, never a value
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata: { name: db, namespace: shop }
spec:
  refreshInterval: 1h
  secretStoreRef: { name: vault, kind: ClusterSecretStore }
  target: { name: db }                    ← the Secret it maintains
  data:
  - secretKey: password
    remoteRef: { key: prod/shop/db, property: password }
🔑 The best secret is the one that does not exist. Workload identity — IRSA on EKS, Workload Identity on GKE, Azure Workload Identity — lets a pod's ServiceAccount authenticate directly to a cloud API with a short-lived, automatically-rotated token. There is no credential to store, leak, rotate or find in an etcd backup. Where the dependency supports it, that beats every row in the table above; external secret managers are for the dependencies that do not.

Every pod gets an API token mounted unless you opt out:

$ kubectl exec deploy/web -- ls /var/run/secrets/kubernetes.io/serviceaccount/
ca.crt  namespace  token
$ kubectl exec deploy/web -- cat /var/run/secrets/kubernetes.io/serviceaccount/token | cut -c1-40
eyJhbGciOiJSUzI1NiIsImtpZCI6Ilg3aGF0MG...    ← a credential in every container

spec:
  automountServiceAccountToken: false      ← set on the ServiceAccount or the pod

Modern clusters use bound projected tokens: audience-scoped, time-limited, tied to the pod's lifetime, and rotated automatically — so a stolen token expires rather than lasting for ever like the legacy Secret-based ones. Turning the mount off entirely for workloads that never call the API remains the cheapest hardening available.

❌ Secrets committed to Git "because they are base64", no encryption at rest, a shared mutable ConfigMap edited in place, configuration consumed as environment variables, and every pod carrying an API token. The base64 blob in the repository is a credential in every clone, every fork and every CI cache — and because etcd is unencrypted, it is also plaintext in every backup that has ever been copied to object storage. Someone edits the ConfigMap to change a log level and nothing happens, because env vars are injected once at container start; three weeks later an unrelated deploy restarts the pods and the behaviour changes, so the resulting incident is attributed to the wrong release. The deployer ServiceAccount is carefully denied get secrets while retaining create pods, which is the same permission by a longer route. And rollback restores the old image against the new configuration, a combination that was never tested and fails differently from both.

✅ Keep values out of Git, encrypt at rest with a KMS provider, make configuration part of the revision, and prefer no secret at all. Commit references rather than values — an ExternalSecret pointing at Vault or a cloud manager, or SOPS/Sealed Secrets if the secret must live in the repository — and where the dependency supports it use workload identity so there is no credential to store or rotate in the first place. Enable encryption at rest with the kms provider, since a local aescbc key sits on the same disk it protects, and remember to rewrite existing Secrets so they are actually re-encrypted. Reference configuration by immutable, content-hashed names: it forces a deliberate rollout, removes the kubelet watch on every node, and makes rollout undo restore image and config together. Know the update table — env never, volumes in about a minute, subPath never — and either implement a reload or accept that a config change means a rollout. Finally, treat the namespace as the real secret boundary, because create pods is get secrets, and set automountServiceAccountToken: false on everything that never calls the API.

Interview Questions

Beginner: What is the difference between a ConfigMap and a Secret?

Very little, and specifically not encryption. A Secret stores base64-encoded values, which is an encoding anyone can reverse.

ConfigMapSecret
EncodingPlainbase64
In etcdPlaintextPlaintext unless encryption at rest is on
kubectl describeShows valuesShows sizes only
RBAC verbsSeparateSeparate — the real difference
On the nodeWritten to disktmpfs, in memory
$ kubectl get secret db -o jsonpath='{.data.password}' | base64 -d
hunter2

What genuinely protects a Secret is three things together: RBAC restricting who can read it, encryption at rest so etcd backups are not credential dumps, and ideally not storing it in Kubernetes at all — an external secret manager, or workload identity so no static credential exists.

Beginner: You updated a ConfigMap but the application still shows the old value. Why?

It depends entirely on how the pod consumes it, and two of the three modes never update.

Consumed asUpdates?Latency
env / envFromNeverRequires a restart
Volume mountYes~60 s
Volume with subPathNeverRequires a restart

And even the volume case usually does not help: the file changes, but the process keeps whatever it parsed at start-up unless it watches the file or handles SIGHUP.

The other half of the answer is that changing a ConfigMap does not trigger a rollout at all, because its contents are not part of the pod template — the pod-template-hash is unchanged. Fix it with kubectl rollout restart for a one-off, a checksum/config annotation, or best, immutable ConfigMaps whose name contains a content hash, which makes a config change a template change and lets rollback restore both together.

Mid: How do you actually protect secrets in a cluster?

Three layers, because no single one is sufficient.

LayerMechanismProtects against
At restEncryptionConfiguration with a KMS v2 providerStolen etcd backups and control-plane disks
AccessRBAC, and namespace boundariesOther tenants and over-broad roles
OriginExternal Secrets Operator, CSI driver, or workload identitySecrets existing at all

The RBAC subtlety that undermines most designs: create pods in a namespace is equivalent to get secrets in that namespace, because the kubelet mounts the Secret on the pod's behalf. A role that grants pod creation while denying secret reads describes a boundary that does not exist — the real boundary is the namespace.

On encryption providers: a local aescbc key lives in a file on the control plane, so it protects a stolen backup and not a stolen disk. KMS v2 keeps the key material external and supports rotation. Note also that enabling encryption does not re-encrypt existing Secrets — they must be rewritten.

The strongest option is to have no secret: workload identity (IRSA, GKE Workload Identity) lets a pod authenticate to cloud APIs with a short-lived token tied to its ServiceAccount, so there is nothing to store, rotate or leak.

Mid: Why would you make a ConfigMap immutable?

For performance as much as safety, and the performance argument is the one people have not heard.

  • The kubelet stops watching it. Normally every kubelet running a pod that mounts a ConfigMap maintains a watch on that object — thousands of watches across a large cluster for data that never changes. immutable: true removes them.
  • A careless edit cannot reach running pods. Mutable shared config means one bad kubectl edit can propagate to every consumer within a minute.
  • It forces the hashed-name pattern, which is the real prize: changing configuration means creating app-config-4c88ba7, which changes the pod template, which triggers a deliberate rollout.

Why that pattern matters most at rollback time: when the config object's name is part of the pod template, kubectl rollout undo restores the image and the configuration atomically. With a shared mutable name you get the old image reading the new config — an untested combination that often behaves worse than either version.

Kustomize's configMapGenerator does the hashing automatically; the Helm equivalent is a checksum/config annotation on the pod template. Old objects are garbage-collected once no retained revision references them.

Senior: Design secret management for a multi-team platform using GitOps.

Nothing secret goes in Git; Git holds references. Then layer for the cases where a reference is not possible.

CaseMechanismRotation
Cloud APIs (S3, SQS, RDS IAM)Workload identity — no secret at allAutomatic, minutes
Third-party APIs, DB passwordsExternal Secrets Operator → Vault/cloud managerAutomatic on refresh
Secrets that must live in GitSOPS with a KMS key, or Sealed SecretsManual, but auditable
Very high sensitivitySecrets Store CSI driver — mounted, no Secret objectAutomatic

Cluster baseline regardless of approach: encryption at rest with KMS v2; automountServiceAccountToken: false by default; a per-namespace boundary treated as the real access boundary (since pod creation implies secret reading); audit logging on secret access; and admission policy rejecting any Secret whose contents look like they came from a committed file.

The multi-team part is mostly RBAC and naming. Each team gets namespaces and a SecretStore scoped to its own path in the secret manager, so an ExternalSecret in team A's namespace cannot reference team B's path. That check belongs in the operator's configuration rather than in review, because a path string is trivial to mistype and impossible to notice.

What I would insist on operationally: rotation must be tested, not assumed. A rotation path that has never been exercised will fail the first time it matters, usually because an application reads its credential once at start-up and never again — which makes "automatic rotation" a restart-triggering event nobody planned for. Either the app re-reads on failure, or rotation is paired with a rollout.

What I would not do: build a bespoke sync controller. The ecosystem tools handle refresh, failure and multi-backend cases that look trivial and are not.

Senior: A credential was exposed in a Git repository. Walk through the response.

Rotate first. Everything else is secondary and none of it is remediation.

1. ROTATE the credential at its source, immediately.        ← the only real fix
2. Assess exposure: public or private repo? how long? forks, clones, CI caches,
   mirrors, the platform's own history APIs?
3. Audit usage of the old credential for anomalies before and after rotation.
4. Only then clean the history — and treat it as tidiness, not remediation.

Why history rewriting is not the fix: the value exists in every clone and fork, in CI caches, in the forge's dangling-commit API, and in any mirror. On a public repository, assume automated scrapers found it within minutes — that is measurably how fast credential scanners operate. Deleting the commit changes none of that.

The same logic applies to container images: a secret baked into a layer is recoverable from the published image with docker save, and rebuilding without it does not retract the copies already pulled — see Docker: Secrets.

What the post-mortem should change, in order of value:

  • Make the leak impossible rather than detectable: ExternalSecrets or workload identity so no value can be committed, because the repository never contains one.
  • Pre-commit and CI secret scanning (gitleaks, trufflehog) as a backstop, plus the forge's push protection.
  • Short-lived credentials so exposure has a bounded blast radius by construction — a 15-minute token that leaks is a very different incident from a static key.
  • A rehearsed rotation runbook per credential type, since the delay in these incidents is almost never detection; it is nobody knowing how to rotate the thing safely.

6 (hard): Audit a cluster for configuration and secret hygiene.
Solution 
$ cat > tools/config-audit.sh <<'SH'
#!/usr/bin/env bash
# Read-only hygiene audit for ConfigMaps, Secrets and their consumers.
set -uo pipefail
hdr() { printf '\n== %s\n' "$1"; }

hdr "encryption at rest"
if kubectl -n kube-system get pod -l component=kube-apiserver \
     -o jsonpath='{.items[0].spec.containers[0].command}' 2>/dev/null \
     | grep -q encryption-provider-config; then echo "  OK   enabled"
else echo "  FAIL not enabled — etcd backups are plaintext credential dumps"; fi

hdr "secrets that look committed (last-applied annotation contains data)"
kubectl get secrets -A -o json | jq -r '
  .items[] | select(.metadata.annotations["kubectl.kubernetes.io/last-applied-configuration"]
                    // "" | contains("\"data\"")) |
  "  WARN \(.metadata.namespace)/\(.metadata.name) applied from a file containing values"'

hdr "mutable configmaps mounted by running pods"
for cm in $(kubectl get cm -A -o json | jq -r '.items[] | select(.immutable != true) |
            "\(.metadata.namespace)/\(.metadata.name)"'); do
  ns=${cm%/*}; n=${cm#*/}
  used=$(kubectl -n "$ns" get pods -o json | jq -r --arg n "$n" \
    '[.items[] | select((.spec.volumes//[])[]?.configMap.name == $n
       or (.spec.containers[].envFrom//[])[]?.configMapRef.name == $n)] | length')
  [ "$used" -gt 0 ] && echo "  WARN $cm mounted by $used pod(s), not immutable"
done | head -10

hdr "pods with the SA token auto-mounted that never call the API"
kubectl get pods -A -o json | jq -r '
  .items[] | select(.spec.automountServiceAccountToken != false) |
  select(.spec.serviceAccountName == "default") |
  "  WARN \(.metadata.namespace)/\(.metadata.name) default SA token mounted"' | head -10

hdr "objects near the 1MB limit"
kubectl get cm,secret -A -o json | jq -r '
  .items[] | {n: "\(.kind) \(.metadata.namespace)/\(.metadata.name)",
              b: ([(.data // {}) | to_entries[] | .value | length] | add // 0)} |
  select(.b > 500000) | "  WARN \(.n) ~\(.b/1024 | floor)KB"'

hdr "config consumed as env (will never update in place)"
kubectl get deploy -A -o json | jq -r '
  .items[] | select([(.spec.template.spec.containers[].envFrom//[])[]?] | length > 0) |
  "  INFO \(.metadata.namespace)/\(.metadata.name) uses envFrom — needs a rollout to change"' | head -10
SH

🎯 Key Takeaways

  • A Secret is base64, not encryption — read out of etcd as plaintext, and present in every snapshot taken before encryption at rest was enabled.
  • The genuine differences from a ConfigMap are separate RBAC verbs, hidden values in describe, and tmpfs storage on the node.
  • Encryption at rest needs an EncryptionConfiguration; a local aescbc key protects a stolen backup, while KMS v2 also protects a stolen disk.
  • Enabling encryption does not re-encrypt existing Secrets — they must be rewritten.
  • Update semantics: env never, directory mounts ~60 s, subPath never — verified side by side in one pod.
  • Directory mounts update atomically via a ..data symlink swap, so readers never see a partial file — but the process still holds what it parsed at start-up.
  • Changing a ConfigMap triggers no rollout, because its contents are not part of the pod template.
  • create pods is equivalent to get secrets in a namespace — demonstrated exfiltrating a Secret with RBAC that explicitly denied reading it.
  • The namespace, not the RBAC verb, is therefore the real secret boundary.
  • immutable: true is a performance feature: the kubelet stops watching the object, removing thousands of watches on a large cluster.
  • Content-hashed immutable names make a config change a template change, so it rolls out deliberately.
  • Rollback then restores image and configuration together — with a shared mutable name, undo pairs old code with new config, an untested combination.
  • ConfigMaps cap at about 1 MB; they are not a file server.
  • Every pod mounts an API token unless automountServiceAccountToken: false — the cheapest hardening available for workloads that never call the API.
  • Modern clusters use bound projected tokens: audience-scoped, time-limited and auto-rotated, unlike the legacy Secret-based ones.
  • Git should contain references, never values: ExternalSecret, SOPS or Sealed Secrets.
  • The Secrets Store CSI driver mounts values with no Secret object in etcd at all.
  • Workload identity is the strongest option — measured, a projected 1-hour token with no access key existing to leak or rotate.
  • After a leak, rotate first: history rewriting is tidiness, not remediation, since the value is in every clone, fork and CI cache.
  • Rotation must be rehearsed — most applications read their credential once at start-up, which quietly makes "automatic rotation" a restart-triggering event.
