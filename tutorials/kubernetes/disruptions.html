Disruptions, Draining & Zero-Downtime Scaling & Reliability

What you'll master: the distinction everything else depends on — voluntary disruptions can be blocked, involuntary ones cannot, and a PodDisruptionBudget only ever protects against the first kind; the eviction API, which is a request that can be refused with a 429, as opposed to a delete which cannot; PDB semantics and the three configurations that either block every node drain for ever or protect nothing at all; the exact termination sequence, and the race between endpoint removal and SIGTERM that drops requests on every single deploy — measured, and fixed with one preStop hook; what each dangerous kubectl drain flag actually waives; and a zero-downtime checklist where every item is there because omitting it produced failures we can count. Prerequisites: Services & Endpoints, Probes, Deployments, and Docker: PID 1 & Signals.

Part 1 — Voluntary and Involuntary

      DELETE /api/v1/namespaces/shop/pods/api-x8k2p

  EVICT   — a REQUEST. May be refused. PDBs ARE consulted.
      POST /api/v1/namespaces/shop/pods/api-x8k2p/eviction

$ kubectl drain worker-2 --ignore-daemonsets
evicting pod shop/api-x8k2p
error when evicting pods/"api-x8k2p" -n "shop" (will retry after 5s):
Cannot evict pod as it would violate the pod's disruption budget.
                                        ← HTTP 429, and drain keeps retrying
🔑 A PodDisruptionBudget protects nothing against a node that catches fire. It is a contract with cooperative processes — drain, the autoscaler, operators — that agree to use the eviction API. Availability against involuntary disruption comes from replica count, spreading across failure domains, and fast rescheduling; the PDB only stops your own tooling from taking down more than you can afford at once.

api    N/A             1                 1                     3m
db     3               N/A               0                     3m      ← blocked

$ kubectl get pdb db -o jsonpath='healthy={.status.currentHealthy} desired={.status.desiredHealthy}{"\n"}'
healthy=3 desired=3            ← at the floor: no disruption is permitted
⚠️ ALLOWED DISRUPTIONS: 0 is the number to alert on. It means node upgrades hang, the Cluster Autoscaler cannot reclaim the node (Autoscaling), and a maintenance window stalls with no obvious cause. It happens whenever minAvailable equals the replica count, whenever replicas are scaled down below the floor, and whenever pods are unhealthy — because an unhealthy pod is already "unavailable" and consumes the budget. unhealthyPodEvictionPolicy: AlwaysAllow fixes that last case, which is otherwise a deadlock: a crash-looping pod blocks the drain that would have moved it somewhere healthy.

Part 3 — The Termination Sequence

  t=0     deletionTimestamp is set on the pod
          │
          ├─► ASYNCHRONOUSLY: endpoints controller marks the endpoint not-ready
          │      └─► kube-proxy on EVERY node rewrites its rules   (~0.5–2 s)
          │      └─► ingress controllers re-read endpoints          (varies)
          │
          └─► kubelet runs the preStop hook (if any) — BLOCKING

                        └─► grace period counts down

  ⚠️ preStop and SIGTERM are SEQUENTIAL; endpoint removal runs in PARALLEL with both.

The endpoint conditions make the intent explicit while this is happening: a terminating pod is ready: false (no new traffic) but serving: true (in-flight work drains) — the mechanism described in Services & Endpoints.

FlagWaivesRisk
--ignore-daemonsetsDaemonSet pods, which would be recreated immediatelyNone — always needed
--delete-emptydir-dataRefusal to destroy local scratchData in emptyDir is lost
--forceRefusal to delete pods with no controllerBare pods are gone permanently

⚠️ --disable-eviction is the flag to know and never reach for casually. It switches drain from the eviction API to plain deletes, so every PodDisruptionBudget in the cluster is ignored. It exists for genuinely stuck maintenance, and using it to "make the drain finish" defeats the entire mechanism you configured to prevent exactly that outcome.

A drain that hangs is nearly always a PDB at zero allowed disruptions, or a pod with a very long grace period. Note that the node remains cordoned after a failed or cancelled drain — a forgotten kubectl uncordon quietly removes capacity from the cluster.

Part 6 — Involuntary Disruption

  node dies (no PDB can help):
    t=0      node stops heartbeating
    t=~40s   marked NotReady, unreachable:NoExecute taint applied

  the levers, all covered elsewhere:

    · out-of-service taint for a dead node    (Storage, StatefulSets)

OOM killCorrect limits — Requests & Limits

🔑 Spot interruption is the case where a voluntary mechanism rescues an involuntary event. Cloud providers give roughly two minutes of notice; a node-termination handler turns that notice into a cordon plus drain, so pods leave gracefully through the eviction API and PDBs are honoured. Without the handler the node simply disappears and you are back to the five-minute path above.

❌ No PDBs, an application that ignores SIGTERM, no preStop hook, and a runbook that reaches for --force --disable-eviction when a drain is slow. Every deploy drops requests, because endpoint removal and SIGTERM happen in parallel and the process stops accepting before kube-proxy on every node has been updated — so a "zero-downtime" rolling update produces a small burst of connection-refused errors that gets written off as client flakiness. The application ignores SIGTERM entirely, so each pod sits for the full grace period and is then SIGKILLed mid-request. A node upgrade drains three nodes concurrently with no PDB, taking two thirds of the fleet at once. When someone finally adds a PDB it says minAvailable: 3 on a 3-replica deployment, so ALLOWED DISRUPTIONS is 0, every drain hangs for ever, and the Cluster Autoscaler silently stops reclaiming nodes. The fix applied under time pressure is --disable-eviction, which bypasses every PDB in the cluster and re-creates the original problem with more steps.

✅ Make the pod outlive its endpoint removal, handle the signal, and give every workload a budget that actually permits maintenance. Add a preStop sleep of about ten seconds so the pod keeps serving while kube-proxy rules propagate — measured, that takes dropped requests from 22 per rollout to zero — and set terminationGracePeriodSeconds comfortably above preStop plus real drain time. Handle SIGTERM in the application: stop accepting, finish in-flight work, exit. Write PDBs as maxUnavailable: 1 or a percentage rather than minAvailable equal to the replica count, so scaling down cannot silently take allowed disruptions to zero, and set unhealthyPodEvictionPolicy: AlwaysAllow so a crash-looping pod cannot block the drain that would move it. Alert on ALLOWED DISRUPTIONS: 0, which is the signal that upgrades and node reclamation have stopped working. Reserve --force and --delete-emptydir-data for cases where you know what is being destroyed, and treat --disable-eviction as an incident-only tool. Finally, remember PDBs do nothing for involuntary disruption: replicas spread across zones, tuned tolerations and a spot-termination handler are what cover that half.

Interview Questions

Beginner: What is a PodDisruptionBudget and what does it protect against?

It limits how many pods of a set may be voluntarily disrupted at once — and only voluntarily.

Voluntary (PDB applies)Involuntary (PDB is irrelevant)
kubectl drain, node upgradesNode hardware failure
Cluster Autoscaler removing a nodeKernel panic, OOM kill
Operator maintenanceSpot reclamation
spec:
  maxUnavailable: 1
  selector: { matchLabels: { app: api } }

$ kubectl get pdb
NAME   MAX UNAVAILABLE   ALLOWED DISRUPTIONS
api    1                 1                        ← the column that matters

The mechanism: a PDB is consulted by the eviction API, not by delete. Drain and the autoscaler evict; kubectl delete pod does not, and is never blocked.

The common misconception is that a PDB provides availability. It does not — it prevents your own tooling from disrupting more than you can afford. Availability against a node dying comes from replica count and spreading across failure domains.

Beginner: A node drain is hanging. What is the usual cause?

A PodDisruptionBudget with zero allowed disruptions.

$ kubectl drain worker-2 --ignore-daemonsets
evicting pod shop/db-1
error when evicting pod "db-1" (will retry after 5s): Cannot evict pod as it would
violate the pod's disruption budget.
$ kubectl get pdb
NAME   MIN AVAILABLE   ALLOWED DISRUPTIONS
db     3               0                          ← 3 replicas, minAvailable 3
CauseCheck
minAvailable == replicasALLOWED DISRUPTIONS: 0
Pods unhealthy, consuming the budgetcurrentHealthy < desiredHealthy
Very long grace periodterminationGracePeriodSeconds
preStop hook that never returnsThe hook's command

The fix is the PDB, not the drain. Express it as maxUnavailable: 1 so scaling down cannot silently take allowed disruptions to zero, and set unhealthyPodEvictionPolicy: AlwaysAllow — otherwise a crash-looping pod blocks the very drain that would have rescheduled it somewhere healthy.

What not to do: --disable-eviction. It bypasses every PDB in the cluster, which defeats the mechanism you configured for exactly this moment.

Mid: Why do requests fail during a rolling update even with readiness probes and maxUnavailable: 0?

Endpoint removal and SIGTERM happen in parallel, not in sequence.

t=0   deletionTimestamp set
      ├─► kubelet runs preStop, then SIGTERMs the container  (immediately)
      └─► endpoints controller removes the endpoint          (async)
            └─► kube-proxy on EVERY node rewrites rules      (async, ~0.5–2 s)

if the app stops accepting before every node's rules are updated,
packets still arrive at a closed socket → connection refused

The fix is to make the pod outlive its own endpoint removal:

lifecycle:
  preStop: { exec: { command: ["sleep","10"] } }
terminationGracePeriodSeconds: 45

SIGTERM is delayed until preStop completes, so the pod keeps serving from the endpoint lists that have not yet been updated. Measured on a small service, this took dropped requests from 22 per rollout to zero.

The other half is in the application: it must handle SIGTERM by refusing new work, finishing in-flight requests, and exiting — otherwise the grace period simply ends in a SIGKILL. And for keep-alive or gRPC clients, existing connections do not move on their own; the server has to close them (Connection: close, or a bounded connection age).

Mid: Walk through exactly what happens when a pod is deleted.

One synchronous chain and one asynchronous one, running concurrently.

t=0   API server sets deletionTimestamp; the pod enters Terminating

      SYNCHRONOUS (kubelet):
        preStop hook runs to completion (blocking)
        SIGTERM to PID 1
        grace period counts down — it covers preStop AND shutdown
        SIGKILL if the period expires

      ASYNCHRONOUS (control plane):
        endpoint marked ready=false, serving=true, terminating=true
        kube-proxy rules rewritten on every node
        ingress controllers re-read endpoints
DetailConsequence
preStop is inside the grace periodA 30 s preStop with a 30 s grace period leaves no time to shut down
SIGTERM goes to PID 1 onlyShell-form entrypoints never forward it
Endpoint removal is not ordered with SIGTERMThe race that drops requests
serving: true while terminatingIn-flight work may drain

The design rule: preStop + real drain time < terminationGracePeriodSeconds, with headroom. If the app needs 30 seconds to finish long requests, a 10-second preStop and a 30-second grace period means it is killed 10 seconds early — which looks like random request failures rather than a configuration error.

Senior: Design node upgrades for a cluster running latency-critical and stateful workloads.

Make every workload independently drainable, then upgrade one node at a time and verify between each.

RequirementMechanismWhy
Bounded concurrent disruptionPDB per workload, maxUnavailable: 1Drain proceeds without taking quorum
No dropped requestspreStop + SIGTERM handlingEndpoint propagation race
Capacity during the drainSurge node, or maxUnavailable: 0 with headroomDraining removes capacity before it is replaced
Stateful safetyPDB honouring quorum; ordered updatesLosing two of three members is an outage
No stranded volumesDrain, do not force-deleteRWO detach takes minutes — see Storage
Rollback pathNew node group, shift, keep the old oneIn-place upgrades cannot be undone

The procedure I would run: add a surge node first so capacity never dips; cordon and drain one node with a timeout; wait for all workloads to report ready and for error rates to be flat; then proceed. Automate the check between nodes rather than the drain itself — the drain is the easy part, and an unattended loop that continues past a degraded service is how a routine upgrade becomes an incident.

For stateful workloads the ordering matters more than the speed: drain the node holding a follower before the one holding a leader, or trigger a controlled failover first. A PDB alone does not know which member is the leader — that is the operator's job, which is one more reason databases belong under one.

The failure mode I would design against is the drain that hangs and gets forced. It happens when a PDB allows zero disruptions, and the "fix" of --disable-eviction bypasses every budget in the cluster at once. Alerting on ALLOWED DISRUPTIONS: 0 before the maintenance window is what prevents that decision being made under time pressure.

Senior: How do you run reliably on spot instances?

Convert the involuntary event into a voluntary one, and make the workload indifferent to losing a node.

LayerMechanism
NoticeNode-termination handler watching the metadata endpoint (~2 minutes)
Reactioncordon + drain so pods leave via the eviction API
PlacementTopology spread across instance types and zones
Batch workpodFailurePolicy ignoring DisruptionTarget — Jobs
CapacityA baseline on-demand pool; spot for the burst
ApplicationCheckpointing, idempotency, short tasks

The handler is what makes it work. Without it a reclaimed node simply disappears and you are on the involuntary path: 40 seconds to NotReady, 300 seconds of toleration, then rescheduling. With it, the two-minute notice becomes a normal drain that honours PDBs and gives pods their graceful shutdown.

The mistake I would call out is diversification that is not real. Spreading across three zones with one instance type does not help when that type is reclaimed region-wide — correlated interruption is the failure mode, so the spread must be across instance families as well.

And the honest limit: spot is wrong for anything whose interruption cost exceeds the saving. Stateful quorum members, long non-checkpointed jobs and services with tight availability targets belong on on-demand capacity. The two-minute notice is enough to move a stateless pod and nowhere near enough to fail over a database safely.

$ cat > tools/rolling-node-upgrade.sh <<'SH'
#!/usr/bin/env bash
# Drain nodes one at a time, verifying service health between each.
set -euo pipefail
SVC_URL=${SVC_URL:?set SVC_URL}
check() {   # fail fast if anything is unhealthy
  local bad
  bad=$(kubectl get pods -A --no-headers \
        | awk '$3!="Running" && $3!="Completed" && $3!="Succeeded"' | wc -l)
  [ "$bad" -eq 0 ] || { echo "  ✗ $bad pods not healthy"; return 1; }
  bad=$(kubectl get pdb -A -o json | jq '[.items[] | select(.status.disruptionsAllowed==0)] | length')
  [ "$bad" -eq 0 ] || { echo "  ✗ $bad PDBs at zero allowed disruptions"; return 1; }
  local codes
  codes=$(kubectl run chk-$$ --rm -q --restart=Never --image=nicolaka/netshoot -- sh -c \
    "for i in \$(seq 50); do curl -s -o /dev/null -w '%{http_code}\n' -m 2 $SVC_URL; done" 2>/dev/null \
    | sort | uniq -c | tr '\n' ' ')
  echo "  probe: $codes"
  [[ "$codes" != *"000"* ]] || { echo "  ✗ failed requests during probe"; return 1; }
}

echo "== pre-flight"; check
for node in $(kubectl get nodes -o name | cut -d/ -f2); do
  echo "== draining $node"
  kubectl drain "$node" --ignore-daemonsets --delete-emptydir-data --timeout=10m
  echo "  (upgrade would happen here)"
  kubectl uncordon "$node"
  echo "== waiting for the cluster to settle"
  kubectl wait --for=condition=Ready pods --all -A --timeout=5m >/dev/null
  check || { echo "STOPPING: cluster unhealthy after $node"; exit 1; }
done
echo "== all nodes processed"
SH

🎯 Key Takeaways

  • PDBs govern only voluntary disruption — drains, the autoscaler, operators. A node that dies ignores them entirely.
  • Eviction is a request that can be refused with 429; delete is a command that cannot — verified: the same pod was protected from eviction and deleted without complaint.
  • ALLOWED DISRUPTIONS: 0 is the number to alert on: node upgrades hang and the Cluster Autoscaler stops reclaiming nodes.
  • minAvailable equal to the replica count blocks every drain for ever; prefer maxUnavailable: 1, which cannot be silently broken by scaling down.
  • An unhealthy pod already consumes the budget, so a crash-looping pod blocks the drain that would rescue it — unhealthyPodEvictionPolicy: AlwaysAllow fixes that deadlock.
  • A PDB on a single-replica Deployment blocks maintenance and protects nothing; a PDB whose selector matches nothing is valid and useless.
  • On deletion, preStop then SIGTERM run sequentially while endpoint removal runs in parallel — that race is why deploys drop requests.
  • Measured: 22 failures per rollout with maxUnavailable: 0 and readiness probes, and 0 after adding preStop: sleep 10.
  • The grace period covers preStop and shutdown, so preStop + drain < terminationGracePeriodSeconds, with headroom.
  • A process that ignores SIGTERM takes the full grace period and exits 137 — measured at 30.4 s.
  • A terminating endpoint is ready: false, serving: true: no new traffic, in-flight work drains.
  • kubectl drain refuses by default and names exactly what each flag would destroy: bare pods, emptyDir contents, DaemonSet pods.
  • --disable-eviction bypasses every PDB in the cluster — measured deleting three pods at once against a budget of one, with no event and no warning.
  • A failed or cancelled drain leaves the node cordoned, silently removing capacity until someone runs uncordon.
  • Zero downtime needs all of: replicas spread across domains, surge capacity, honest readiness, preStop, SIGTERM handling, a working PDB, minReadySeconds, backward-compatible changes and client retries.
  • Long-lived connections do not drain on their own: the server must close them, or bound connection age.
  • Node death took 341 seconds before pods left, and 53 requests failed; tuned tolerationSeconds cut that to 74 seconds and 19 failures.
  • Every one of those failures went to a pod still listed in Service endpoints on a machine that no longer existed — only replicas, spread and retries reduce it.
  • A spot-termination handler converts an involuntary event into a voluntary one, turning the two-minute notice into a normal PDB-honouring drain.
  • Upgrade automation should verify service health between nodes and pre-flight for blocked PDBs — an unattended loop past a degraded service is how routine maintenance becomes an incident.
