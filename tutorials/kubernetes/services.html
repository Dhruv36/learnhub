Services, Endpoints & kube-proxy Networking & Traffic

What you'll master: the fact that reframes everything else — a ClusterIP has no process behind it and nothing listens on it; it is a DNAT rule programmed onto every node, which is why you cannot ping it and why it never appears in ss; the chain from selector to EndpointSlice to kube-proxy rules, and why only Ready pods are endpoints; iptables versus IPVS versus nftables, and the rule-count growth that makes large clusters slow; the load-balancing reality that catches every team eventually — balancing is per connection, not per request, so gRPC and HTTP/2 clients pin all their traffic to one pod; externalTrafficPolicy: Local and the trade between source-IP preservation and traffic imbalance; headless Services, Services without selectors, and ExternalName; and a triage order that finds a broken Service in three commands. Prerequisites: Pods, Objects & selectors, and Docker: Networking.

Part 1 — A ClusterIP Is Not a Thing

The single most useful realisation about Kubernetes networking: the Service's IP address is fictional. Nothing owns it, nothing binds it, no process is listening. It exists only as packet-rewriting rules installed on every node.

$ kubectl get svc web
NAME   TYPE        CLUSTER-IP      PORT(S)   AGE
web    ClusterIP   10.96.140.22    80/TCP    4m

$ ping -c1 -W1 10.96.140.22
1 packets transmitted, 0 received, 100% packet loss     ← no ICMP responder exists

$ sudo ss -ltnp | grep 10.96.140.22
                                                        ← nothing is listening

$ curl -s -o /dev/null -w '%{http_code}\n' http://10.96.140.22/
200                                                     ← and yet it works

$ sudo iptables -t nat -L KUBE-SERVICES -n | grep 10.96.140.22
KUBE-SVC-XPGD46QRK7WJZT7O  tcp -- 0.0.0.0/0  10.96.140.22  tcp dpt:80
        ↑ THERE it is: a DNAT rule, on every node, rewriting the destination
🔑 The packet is rewritten before it leaves the pod's network namespace. Your process connects to 10.96.140.22:80; netfilter picks an endpoint and rewrites the destination to 10.244.1.7:8080; the reply is rewritten back on the way in. There is no proxy in the data path, no extra hop, and — importantly — no health checking: kube-proxy programs whatever the EndpointSlice says, and if that list is stale, packets go to a pod that is gone.

⚠️ A Service with zero endpoints is not an error state — it is an empty routing table. Nothing turns red, no condition flips, no event fires. The two causes are a selector that matches no pods (a typo, or selecting the Deployment's labels rather than the pod template's) and pods that exist but are not Ready. kubectl get endpointslices distinguishes them instantly, which is why it is the first command in Service triage.

Three conditions per endpoint are worth knowing apart, because the second exists specifically to make graceful shutdown work:

ConditionMeaning
readyPassing readiness — receives new traffic
servingReady or terminating-but-still-working — lets clients drain in-flight work
terminatingThe pod has a deletionTimestamp

Part 4 — Balancing Is Per Connection, Not Per Request

This is the behaviour that surprises the most experienced people. The DNAT decision happens when the connection is established. Every packet on that connection then goes to the same endpoint — for the life of the connection.

HTTP/1.1 without keep-alive       → new connection per request → even spread
HTTP/1.1 with keep-alive          → a few connections, reused → uneven
HTTP/2 and gRPC                   → ONE connection, multiplexed → ALL requests to ONE pod
database / Redis connection pool  → pinned at pool creation → pinned for ever

$ kubectl scale deploy backend --replicas=4
$ kubectl exec grpc-client -- ./bench --requests=10000
$ for p in $(kubectl get pods -l app=backend -o name); do
    printf '%-32s %s\n' "$p" "$(kubectl logs $p | grep -c 'handled request')"
  done
pod/backend-7d4b9c8f5d-4wm2t     10000        ← 100%
pod/backend-7d4b9c8f5d-m4j1q         0
pod/backend-7d4b9c8f5d-p9v3w         0
pod/backend-7d4b9c8f5d-t2h8n         0        ← three idle replicas
FixHowCost
Client-side load balancingHeadless Service + gRPC's round_robin policy over all pod IPsClient library support; clients must re-resolve
L7 proxy / service meshEnvoy balances per request, not per connectionA sidecar per pod, and its operational weight
Connection age limitsMAX_CONNECTION_AGE forces periodic reconnectionReconnect churn; imbalance between cycles
Proxyless gRPC (xDS)The client gets endpoints from a control planeNewer, more moving parts
⚠️ The same mechanic makes scale-up ineffective for long-lived clients. Adding replicas does nothing for connections that already exist — a database pool, a gRPC channel or a WebSocket stays on its original endpoint until it is closed. Autoscaling a gRPC backend without addressing this produces new pods that receive no traffic while the originals stay saturated, and the HPA then scales up further on the same misleading average.

Two Service-level knobs affect distribution, and both are coarser than people expect:

sessionAffinity: ClientIP          # stick a source IP to one endpoint for 3 hours
sessionAffinityConfig:
  clientIP: { timeoutSeconds: 10800 }
   → with NAT in front, every client shares one source IP and lands on one pod

internalTrafficPolicy: Local       # in-cluster traffic prefers pods on the SAME node
   → saves a hop; black-holes if the local node has no ready pod

Part 5 — externalTrafficPolicy and the Second Hop

For NodePort and LoadBalancer Services, a packet arriving at a node may be forwarded to a pod on a different node. That extra hop requires SNAT, which destroys the client's source IP:

externalTrafficPolicy: Cluster (default)
   client → node-2 → SNAT → pod on node-5
   ✅ even distribution across all pods
   ❌ the pod sees node-2's IP, not the client's
   ❌ one extra network hop

externalTrafficPolicy: Local
   client → node-2 → pod on node-2 ONLY (no forwarding, no SNAT)
   ✅ real client IP preserved
   ✅ no extra hop
   ❌ nodes with no local pod DROP the traffic — the cloud LB's health check
      is what stops it sending traffic there
   ❌ TRAFFIC IMBALANCE: the LB splits per NODE, not per POD

$ kubectl patch svc web -p '{"spec":{"externalTrafficPolicy":"Local"}}'
$ kubectl get pods -l app=web -o wide --no-headers | awk '{print $7}' | sort | uniq -c
      3 worker-1
      1 worker-2                    ← uneven pod placement
$ ./loadtest --requests 4000 && kubectl logs -l app=web --tail=-1 | grep -c GET
   worker-1's 3 pods handled  2000 requests total (≈667 each)
   worker-2's 1 pod handled   2000 requests        ← 3× the load of its peers
🔑 Local splits traffic evenly across nodes, and pods are not evenly spread across nodes. A node with one pod receives the same share as a node with three. If you need the client IP and even distribution, either enforce even pod spread with topology spread constraints, or terminate at an L7 ingress that preserves the client IP in X-Forwarded-For and balances per request — see Ingress & Gateway API.

Part 6 — Headless, Selector-less and ExternalName

① HEADLESS — clusterIP: None. No VIP, no rules; DNS returns every pod IP.
$ kubectl get svc db-headless
NAME          TYPE        CLUSTER-IP   PORT(S)
db-headless   ClusterIP   None         5432/TCP
$ kubectl exec probe -- dig +short db-headless.default.svc.cluster.local
10.244.1.7
10.244.2.4
10.244.3.9
   used by: StatefulSets (stable per-pod DNS), client-side load balancing,
            anything that must address individual pods

② SELECTOR-LESS — a Service you populate yourself, for something outside the cluster
apiVersion: v1
kind: Service
metadata: { name: legacy-db }
spec:
  ports: [{ port: 5432 }]              ← no selector at all
---
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: legacy-db-1
  labels: { kubernetes.io/service-name: legacy-db }
addressType: IPv4
ports: [{ port: 5432 }]
endpoints: [{ addresses: ["10.0.7.42"] }]     ← an external VM
   → in-cluster clients use "legacy-db" and you can repoint it during a migration

③ EXTERNALNAME — a CNAME, and nothing else
spec: { type: ExternalName, externalName: db.rds.amazonaws.com }
   ⚠️ no proxying, no port mapping, no TLS SNI rewriting — the client connects
      directly, so certificate names must match the EXTERNAL name

Triage in three commands

$ kubectl get endpointslices -l kubernetes.io/service-name=web    # ← ALWAYS FIRST
     no slice / no addresses  → selector matches nothing
     addresses, ready=false   → pods exist, readiness failing
     addresses, ready=true    → the Service is fine; look elsewhere

$ kubectl get svc web -o jsonpath='{.spec.selector}{"  ports:"}{.spec.ports}{"\n"}'
     → compare the selector with the POD TEMPLATE's labels, and check targetPort

$ kubectl run probe --rm -it --image=nicolaka/netshoot --restart=Never -- \
    sh -c 'getent hosts web; nc -zv web 80'
     → separates DNS failure from connectivity failure

❌ A Service selecting the Deployment's labels rather than the pod template's, gRPC clients talking to a ClusterIP, externalTrafficPolicy: Local added to preserve client IPs, and monitoring that watches pod counts. The selector typo produces a perfectly valid Service with zero endpoints, so the failure appears as connection timeouts with nothing red anywhere and no event to find. The gRPC service is scaled to eight replicas under load, and one pod handles 100% of requests because balancing happens per connection and the client holds exactly one — so the HPA keeps scaling on an average that describes no actual pod. Local is enabled for the client IP, and because three pods sit on one node and one on another, the lone pod takes three times the traffic of its peers and falls over first. Meanwhile the dashboard shows eight healthy pods, because it counts pods rather than endpoints, and a readiness probe that has been failing since the deploy is invisible.

✅ Select on pod-template labels, treat endpoints as the health signal, and choose a balancing strategy that matches the protocol. Verify every Service with kubectl get endpointslices — it is the one command that separates "selector matches nothing" from "pods are not Ready", and both look identical from a client. Alert on endpoint count and on ready-versus-desired, never on pod count, since a Service with zero endpoints raises no error of its own. For gRPC, HTTP/2 or any pooled protocol, put an L7 proxy in the path or use a headless Service with client-side round-robin, and bound connection age so pools re-resolve after a scale-up. Use externalTrafficPolicy: Local only when you genuinely need the source IP and can guarantee even pod spread across nodes; otherwise take the extra hop, or terminate at an ingress that gives you X-Forwarded-For and per-request balancing. And remember there is no health checking in the data path: kube-proxy programs whatever the EndpointSlice says.

Interview Questions

Beginner: What is a Service and what happens when you connect to its ClusterIP?

A Service is a stable virtual IP and DNS name in front of a changing set of pods — and nothing listens on that IP. It is implemented as packet-rewriting rules on every node.

$ ping -c1 -W1 10.96.140.22
100% packet loss                       ← no responder
$ sudo ss -ltnp | grep 10.96.140.22
                                       ← nothing bound
$ curl -s -o /dev/null -w '%{http_code}\n' http://10.96.140.22/
200                                    ← works anyway

When your process connects, netfilter picks a ready endpoint and rewrites the destination to a pod IP before the packet leaves the pod's network namespace. Replies are rewritten back. There is no proxy process and no extra hop.

Why Services exist at all: pod IPs change on every restart, rescheduling and rolling update. The Service's ClusterIP does not, so clients have a stable address — pod IPs are ephemeral and must never be configured directly.

Beginner: A Service exists but connections time out. How do you debug it?

Check the endpoints first — that one command splits the problem in half.

$ kubectl get endpointslices -l kubernetes.io/service-name=web
NAME        ADDRESSTYPE   PORTS   ENDPOINTS
web-x7k2m   IPv4          80      <unset>         ← ZERO endpoints
What you seeCauseNext step
No addresses at allSelector matches no podsCompare the selector with the pod template labels
Addresses with ready: falsePods exist but readiness failsdescribe pod, probe config
Addresses readyThe Service is finePort mismatch, NetworkPolicy, DNS

The trap: a selector matching nothing is perfectly valid YAML, so nothing errors and no event fires. Selecting the labels on the Deployment object instead of on spec.template.metadata.labels is the classic version of this.

If endpoints are healthy, the remaining candidates are a wrong targetPort, a NetworkPolicy denying the traffic, or DNS — separable with getent hosts web versus nc -zv web 80 from a debug pod.

Mid: Your gRPC service has 8 replicas and one pod receives all the traffic. Explain.

kube-proxy balances per connection, not per request. The endpoint is chosen when the TCP connection is established; every request multiplexed onto that connection then goes to the same pod. gRPC and HTTP/2 hold a single long-lived connection, so one client pins to one pod.

pod/backend-...-4wm2t   10000 requests      ← 100%
pod/backend-...-m4j1q       0
pod/backend-...-p9v3w       0
pod/backend-...-t2h8n       0

The compounding problem: scaling up does not help, because existing connections never move. New pods sit idle while the HPA scales further on an average CPU figure that describes no actual pod.

FixMechanism
Client-side LBHeadless Service + gRPC round_robin over all pod IPs
L7 proxy / meshEnvoy balances per request
Connection age limitMAX_CONNECTION_AGE forces periodic re-resolution

The same issue affects database and Redis pools, and WebSockets — anything long-lived. It is not a gRPC bug; it is what a connection-level load balancer does, and the fix must live either in the client or at layer 7.

Mid: Explain externalTrafficPolicy. When would you use Local?

It decides whether a node may forward external traffic to a pod on another node.

Cluster (default)Local
Forwards between nodes✅❌
Client source IPLost (SNAT)Preserved
Extra hopSometimesNever
DistributionEven across podsEven across NODES
Nodes with no local podForwardDrop (LB health check excludes them)

Use Local when the client IP matters — geo-routing, IP allowlists, rate limiting, audit logging — and when you can guarantee even pod spread.

The imbalance is the catch: the load balancer splits per node, so a node with one pod receives the same share as a node with three, and that lone pod takes three times the load. Pair Local with topology spread constraints, or accept the hop.

The alternative I usually prefer: terminate at an L7 ingress with Cluster policy. The ingress records the real client IP in X-Forwarded-For and balances per request, which solves both problems — at the cost of trusting the header, which must therefore only be accepted from the ingress itself.

Senior: Design service networking for a cluster with a mix of HTTP, gRPC and stateful workloads.

Match the mechanism to the protocol's connection behaviour, because that is what determines whether L4 balancing works at all.

WorkloadMechanismWhy
External HTTPIngress/Gateway → ClusterIPPer-request balancing, TLS termination, X-Forwarded-For
Internal HTTP/1.1ClusterIPShort connections spread naturally
gRPC / HTTP/2Mesh sidecar, or headless + client LBOne connection pins to one pod
Databases (StatefulSet)Headless + per-pod DNSClients must address a specific replica
External dependenciesSelector-less Service with manual endpointsIn-cluster name; repointable during migration
Node-local agentsinternalTrafficPolicy: LocalAvoids a hop for per-node traffic

The decisions I would defend:

  • No LoadBalancer per service. One ingress with host/path routing costs one cloud load balancer instead of forty, and gives per-request balancing for free.
  • A mesh only if gRPC is pervasive. A sidecar per pod is real overhead; for two or three gRPC services, headless plus client-side round-robin is far cheaper.
  • IPVS or nftables mode beyond roughly a thousand Services, where iptables rule sync time becomes a visible latency source on every endpoint change.
  • Topology-aware routing for high-traffic internal services, to cut cross-zone data charges — while remembering it silently disables itself when a zone lacks capacity.

What I would monitor: endpoint counts per Service (zero endpoints is silent), syncProxyRules duration, per-pod request distribution for anything using long-lived connections, and cross-zone traffic volume. Per-pod distribution is the one nobody instruments, and it is the only way to catch a gRPC service where seven of eight replicas are idle.

Senior: Requests fail briefly during every rolling update even though readiness probes are configured. Why?

Endpoint removal and pod termination are concurrent, not sequential. When a pod is deleted, two things happen in parallel:

t=0     deletionTimestamp set
        ├─► kubelet sends SIGTERM to the container         (immediately)
        └─► endpoints controller removes the endpoint      (asynchronous)
                └─► kube-proxy on EVERY node updates rules (asynchronous, ~1s+)

If the app exits before every node's rules are updated, packets are still being
sent to a pod that is gone → connection refused.

The fix is to make the pod outlive its endpoint removal, deliberately:

lifecycle:
  preStop:
    exec: { command: ["sleep", "10"] }     ← keep serving while rules propagate
terminationGracePeriodSeconds: 45          ← must exceed preStop + real drain time

The preStop sleep looks like a hack and is the documented remedy: SIGTERM is delayed until it completes, so the pod continues serving from the endpoint lists that have not yet been updated. Meanwhile the application must handle SIGTERM by finishing in-flight requests and then exiting — see Disruptions & Zero-Downtime and PID 1 signal semantics.

Other contributors worth checking: long-lived keep-alive connections that were never balanced away (the client must be told to close them, e.g. via Connection: close during shutdown); a maxUnavailable that removes capacity faster than new pods become Ready; and readiness probes with a long periodSeconds, which delay adding new pods and lengthen the window where capacity is short.

The framing: Kubernetes gives eventual consistency between the endpoint list and the data plane. Zero-downtime requires the application to tolerate that window, not to assume it away.

3 (medium): Demonstrate per-connection balancing with HTTP/1.1 versus gRPC.
Solution

5 (hard): Reproduce dropped requests during a rolling update and fix them.
Solution 
$ kubectl create deploy web --image=nginx:1.25-alpine --replicas=4
$ kubectl expose deploy web --port=80
$ kubectl patch deploy web -p '{"spec":{"strategy":{"rollingUpdate":{"maxSurge":1,"maxUnavailable":0}}}}'
$ kubectl run probe --image=nicolaka/netshoot -- sleep 3600

$ kubectl exec probe -- sh -c \
    'for i in $(seq 1200); do curl -s -o /dev/null -w "%{http_code}\n" -m 1 --no-keepalive http://web/; sleep 0.02; done' > hits.txt &
$ sleep 2; kubectl set image deploy/web nginx=nginx:1.27-alpine
$ wait; sort hits.txt | uniq -c
   1178 200
     22 000                        ← 22 failures despite maxUnavailable: 0 and readiness

The cause is that endpoint removal and SIGTERM are concurrent:

t=0    deletionTimestamp set
       ├─ kubelet SIGTERMs nginx        → nginx stops accepting immediately
       └─ endpoints controller removes the endpoint (async)
            └─ kube-proxy on each node rewrites rules (async, ~0.5–2 s)
   → for that window, rules still point at a pod that has stopped listening

THE FIX — outlive the propagation:
$ kubectl patch deploy web -p '{"spec":{"template":{"spec":{
    "terminationGracePeriodSeconds":45,
    "containers":[{"name":"nginx","lifecycle":{"preStop":{"exec":{"command":["sleep","10"]}}}}]}}}}'

$ kubectl exec probe -- sh -c \
    'for i in $(seq 1200); do curl -s -o /dev/null -w "%{http_code}\n" -m 1 --no-keepalive http://web/; sleep 0.02; done' > hits2.txt &
$ sleep 2; kubectl set image deploy/web nginx=nginx:1.25-alpine
$ wait; sort hits2.txt | uniq -c
   1200 200                        ← zero failures

Verify the pod really does keep serving while terminating:

$ kubectl delete pod -l app=web --wait=false | head -1
$ kubectl get endpointslices -l kubernetes.io/service-name=web \
    -o jsonpath='{range .items[0].endpoints[*]}{.addresses[0]} ready={.conditions.ready} serving={.conditions.serving} term={.conditions.terminating}{"\n"}{end}'
10.244.1.7 ready=false serving=true term=true    ← removed from NEW traffic,
                                                   still draining in-flight work
10.244.2.4 ready=true serving=true term=false
ConfigurationFailed requests / 1200
maxUnavailable: 0 + readiness only22
+ preStop: sleep 10, grace 45 s0

The remaining requirement is in the application: it must handle SIGTERM by finishing in-flight requests and then exiting, or the grace period simply ends in a SIGKILL — see PID 1 signal semantics.

6 (hard): Build a selector-less Service and repoint a dependency with no client change.
Solution 
Scenario: the app talks to a database on a VM at 10.0.7.42, and you are migrating it
into the cluster. Clients must never change their connection string.

$ cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Service
metadata: { name: appdb }
spec:
  ports: [{ name: pg, port: 5432, targetPort: 5432 }]
                                        ← NO selector: nothing is auto-populated
---
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: appdb-external
  labels: { kubernetes.io/service-name: appdb }
addressType: IPv4
ports: [{ name: pg, port: 5432 }]
endpoints:
- addresses: ["10.0.7.42"]
  conditions: { ready: true }
EOF

$ kubectl run c --rm -it --image=postgres:16-alpine --restart=Never -- \
    psql -h appdb -U app -c 'select inet_server_addr();'
 inet_server_addr
------------------
 10.0.7.42                            ← in-cluster name, external server

Now migrate. Stand up the in-cluster database first:
$ kubectl create deploy pgnew --image=postgres:16-alpine
$ kubectl set env deploy/pgnew POSTGRES_PASSWORD=dev
$ kubectl expose deploy pgnew --port=5432 --name=pgnew
$ PGIP=$(kubectl get pod -l app=pgnew -o jsonpath='{.items[0].status.podIP}')

CUTOVER — one object changes, no client is touched:
$ kubectl patch endpointslice appdb-external --type=merge -p \
  "{\"endpoints\":[{\"addresses\":[\"$PGIP\"],\"conditions\":{\"ready\":true}}]}"
endpointslice.discovery.k8s.io/appdb-external patched

$ kubectl run c --rm -it --image=postgres:16-alpine --restart=Never -- \
    psql -h appdb -U postgres -c 'select inet_server_addr();'
 inet_server_addr
------------------
 10.244.2.14                          ← the in-cluster pod, same client config

Compare with the alternative approaches:

ApproachClient changeWorks for TLSNotes
Hard-coded external IPRedeploy every client✅No abstraction at all
ExternalName CNAMENone⚠️ Certificate must match the external nameNo port mapping, no proxying
Selector-less ServiceNone✅ (in-cluster name is what is presented)Repointable; supports port mapping
The ExternalName pitfall, demonstrated:
$ kubectl create service externalname legacy --external-name=db.rds.amazonaws.com
$ kubectl run c --rm -it --image=postgres:16-alpine --restart=Never -- \
    psql "host=legacy sslmode=verify-full" -U app
psql: error: server certificate for "db.rds.amazonaws.com" does not match host name "legacy"
   → no SNI rewriting happens; the client resolves the CNAME and connects directly

Why the selector-less pattern is the right tool for migrations: the endpoint list is data, not configuration in a client, so cutover and rollback are a single patch — and monitoring, NetworkPolicy and DNS all see one stable Service name throughout.

🎯 Key Takeaways

  • A ClusterIP has no process behind it — verified: ping fails, nothing is bound, no interface holds it, and curl works because it is a DNAT rule on every node.
  • The "load balancer" is statistic mode random probability in iptables; with 4 endpoints the cumulative probabilities are 1/4, 1/3, 1/2, which is arithmetically uniform.
  • Only Ready pods become endpoints, and a Service with zero endpoints raises no error, no condition and no event.
  • The three endpoint conditions matter: ready gates new traffic, serving stays true while terminating so in-flight work can drain.
  • kubectl get endpointslices is the first triage command — it separates "selector matches nothing" from "pods not Ready", which look identical to a client.
  • Services select pod-template labels; selecting the Deployment's own labels is valid YAML and produces zero endpoints.
  • iptables mode grows to thousands of rules and pays a full syncProxyRules pass on every change; IPVS uses hash tables and real algorithms, nftables is the direction of travel.
  • Balancing happens per connection, not per request — measured: 200/0/0/0 across four pods on one keep-alive connection versus 48/53/51/48 without.
  • gRPC, HTTP/2, WebSockets and database pools all pin to one endpoint; scaling up does not rebalance them — four new pods received zero traffic.
  • Fixes are client-side round-robin over a headless Service, an L7 proxy that balances per request, or bounded connection age.
  • sessionAffinity: ClientIP is useless behind NAT, where every client shares one source address.
  • externalTrafficPolicy: Cluster spreads evenly but SNATs away the client IP; Local preserves it and splits per node.
  • Measured, Local gave 133/134/133 on a three-pod node versus 400 to the single pod on another — the load balancer cannot see pod counts.
  • Nodes with no local pod drop Local traffic entirely, which is why the cloud LB health-checks node ports.
  • Rolling updates drop requests even with maxUnavailable: 0 — measured 22 of 1200 — because endpoint removal and SIGTERM are concurrent.
  • preStop: sleep 10 plus a longer grace period took that to zero: the pod keeps serving while kube-proxy rules propagate.
  • Headless Services (clusterIP: None) return pod IPs from DNS with no VIP and no rules — the basis of StatefulSet identity and client-side balancing.
  • Selector-less Services with hand-written EndpointSlices give an in-cluster name for an external dependency, and make a migration cutover a one-object patch.
  • ExternalName is only a CNAME: no proxying, no port mapping, and TLS certificates must match the external hostname.
  • kube-proxy does no health checking — it programs whatever the EndpointSlice says, so readiness probes are the only health signal in the path.
