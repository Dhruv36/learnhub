Debugging Production Clusters Operating Clusters

What you'll master: a triage order that identifies the failing layer before you start guessing; how to read every pod state as a pointer to a specific subsystem — Pending is the scheduler, ContainerCreating is CNI or volumes, Running 0/1 is readiness; the fact that wastes more incident time than any other — Events expire after about an hour, so describe on an old problem shows nothing at all; kubectl debug and ephemeral containers, which are how you get a shell into a distroless pod that has none; a layered network test that separates DNS from policy from endpoints in three commands; node-level triage with crictl when the kubelet and the API disagree; and the cluster-wide symptoms — a failing webhook, etcd latency, an event flood — that look like every application being broken at once. Prerequisites: the whole track, particularly Pods, Services, Requests & Limits.

Part 1 — Triage Order

  ① WHAT LAYER?           is one pod broken, one service, one node, or everything?
  ② EVENTS FIRST          kubectl get events --sort-by=.lastTimestamp   ← THEY EXPIRE
  ③ STATUS, NOT SPEC      .status.conditions, containerStatuses, lastState
  ④ LOGS                  --previous for a restarted container
  ⑤ INSIDE                exec, or an ephemeral container
  ⑥ THE NODE              conditions, kubelet, crictl
  ⑦ THE CONTROL PLANE     apiserver latency, webhooks, etcd
Symptom scopeStart at
One poddescribe pod → events → logs
Every pod of one workloadThe image, the config, the probe
Every pod on one nodeThe node — conditions, kubelet, disk
One service unreachableEndpointSlices → DNS → NetworkPolicy
Everything, all at onceControl plane — webhooks, etcd, DNS
Nothing can be createdAn admission webhook, or quota
⚠️ Events expire — by default after one hour. kubectl describe pod on a pod that failed this morning shows Events: <none>, which reads as "no information" and actually means "the information was deleted". This is the single biggest time-waster in Kubernetes debugging, and the fix is to ship events to your logging pipeline so they outlive the incident.
$ kubectl get events --sort-by=.lastTimestamp -A | tail -20
$ kubectl get events --field-selector involvedObject.name=api-x8k2p,type=Warning
$ kubectl get events -w                      ← live, during a reproduction
$ kubectl get events -A -o json | jq -r '.items[] |
    "\(.lastTimestamp) \(.type) \(.reason) \(.involvedObject.kind)/\(.involvedObject.name): \(.message)"' \
  | sort | tail -30

🔑 Ephemeral containers cannot be removed. They persist for the pod's lifetime and appear in describe output, so a debugged pod is permanently marked. That is usually acceptable — but on a pod you intend to keep, prefer --copy-to, which leaves the original untouched and gives you something you can delete.

🔑 A sudden event flood is a symptom worth alerting on. Thousands of identical warnings mean a controller is retrying something that will never succeed — and because Events live in etcd, a flood also consumes the database, which can turn one broken workload into cluster-wide slowness. Counting events by reason is often faster than reading any of them.

❌ Debugging by restarting things, reading spec instead of status, and reaching for logs before events. A pod is crash-looping, so someone deletes it — which destroys the evidence and the --previous logs along with it, and the replacement crash-loops identically. kubectl describe shows Events: <none> because they expired an hour ago, and that is read as "nothing wrong here" rather than "the record is gone". The real cause was lastState.terminated.reason: OOMKilled, visible in the status the whole time, but everyone is reading the manifest instead. A service is unreachable, so three people simultaneously check DNS, the ingress and the application logs, and nobody checks the EndpointSlice — which has been empty since a readiness probe started failing. Meanwhile every write in the cluster is failing after a ten-second timeout because a webhook's Service was deleted, and each team debugs their own application in isolation.

✅ Establish the layer first, read events before logs, and read status before spec. Ask whether one pod, one workload, one node, or everything is affected — that single question eliminates most of the search space before any command is run. Then get the events, sorted by timestamp and early, because they expire in about an hour; ship them to your logging pipeline so they outlive the incident. Read status.containerStatuses[].lastState, which distinguishes OOMKilled from a plain crash and points at limits rather than code. Never delete a broken pod before capturing logs --previous and describe — the replacement will fail the same way and you will have destroyed the evidence. For unreachable services, test in layers: pod IP, then DNS, then ClusterIP, then ingress, each step eliminating one subsystem. When the symptom is "everything at once", stop debugging applications and check webhooks, etcd and CoreDNS — a cluster-wide cause never looks like a cluster-wide cause from inside a single namespace.

Interview Questions

Beginner: A pod is in CrashLoopBackOff. Walk through debugging it.

CrashLoopBackOff is a restart delay, not a cause — the container started, exited, and Kubernetes is waiting before trying again.

$ kubectl logs api
Error from server (BadRequest): container "api" in pod "api" is waiting to start:
CrashLoopBackOff                       ← the CURRENT container has not started
$ kubectl logs api --previous          ← the one that DIED
Error: connect ECONNREFUSED 10.96.140.22:5432
$ kubectl get pod api -o jsonpath='{.status.containerStatuses[0].lastState.terminated}' | jq -c
{"exitCode":1,"reason":"Error","finishedAt":"..."}
$ kubectl describe pod api | tail -5    ← events, if they have not expired
lastStateCause
reason: OOMKilled, exit 137Memory limit — limits
exit 1/2Application error — the previous logs have it
exit 127Command not found
exit 0 with restartPolicy: AlwaysA process that exits normally in a Deployment

The mistake to avoid is deleting the pod to "try again". That destroys the --previous logs, and the replacement fails identically. Capture first.

Beginner: kubectl describe pod shows Events: <none>. What does that mean?

Almost always that the events expired, not that nothing happened. Events have a TTL — one hour by default — and are deleted by the API server afterwards.

$ kubectl describe pod api | tail -2
Events:  <none>                        ← the pod failed three hours ago
$ kubectl get pod api -o jsonpath='{.status.containerStatuses[0].lastState}' | jq -c
{"terminated":{"exitCode":137,"reason":"OOMKilled","finishedAt":"2026-08-19T09:14:22Z"}}
                                       ← STATUS persists; events do not
SourceSurvives?
Events❌ ~1 hour
status.lastState✅ While the pod exists
restartCount✅
Container logsUntil the pod is deleted (or rotated)
Shipped events / metrics✅ As long as you retain them

The fix is architectural: ship events to your logging pipeline (an events exporter is a small DaemonSet or Deployment). Otherwise every post-incident investigation starts by discovering that the most useful record was deleted while people were still on the call.

Mid: A Service is unreachable. What is your test order?

Layer by layer, so each test eliminates a subsystem. Start with endpoints, because that single command splits the problem in half.

$ kubectl get endpointslices -l kubernetes.io/service-name=api
   no addresses      → selector matches nothing, or no pod is Ready
   ready=false       → readiness failing
   ready=true        → the Service is fine; look further out

then, from a debug pod:
  ① nc -zv <pod-ip> 8080        raw connectivity — CNI/NetworkPolicy
  ② getent hosts api.shop       DNS
  ③ curl http://api.shop/       the Service VIP and kube-proxy
  ④ curl -H 'Host: ...' $LB     the ingress
Failure pointDiagnosis
① failsNetworkPolicy or CNI
② NXDOMAINWrong name/namespace
② times outPolicy blocking port 53
③ fails, endpoints existWrong targetPort
④ 503Ingress sees no endpoints
④ 502Backend refused — port or protocol

The distinction that saves the most time is between "no endpoints" and "endpoints that refuse". The first is a Service problem — selector or readiness; the second is an application or port problem. They look identical from a client and are one command apart.

Mid: How do you debug a distroless container with no shell?

An ephemeral container in the same pod, sharing its namespaces.

$ kubectl exec -it api -- sh
OCI runtime exec failed: exec: "sh": executable file not found in $PATH

$ kubectl debug -it api --image=nicolaka/netshoot --target=api
~ # ps aux                     ← --target shares the PID namespace
1 1000 /server
~ # ls /proc/1/root/app        ← the target's filesystem, through /proc
~ # ss -ltnp                   ← its sockets: same network namespace
~ # curl -s localhost:8080/healthz
VariantUse when
--target=CThe container is running; you need its processes and files
--copy-to=X --set-image=*=busyboxIt will not start at all
--copy-to=X --share-processesA disposable copy with a shared PID namespace
kubectl debug node/NNode-level triage, filesystem at /host

Two caveats: ephemeral containers cannot be removed and persist for the pod's lifetime, so use --copy-to on a pod you intend to keep. And under restricted Pod Security the debug image must satisfy the same policy — which is why the --profile flag exists.

The alternative people reach for and should not is shipping a :debug image variant with a shell to production. That reintroduces exactly the attack surface distroless removed.

Senior: "Everything is broken." How do you triage a cluster-wide incident?

Determine the layer before touching any application. Cluster-wide causes never look cluster-wide from inside one namespace, which is why ten teams debug ten symptoms of one problem.

SignatureCauseConfirm
Writes fail, reads workA failing admission webhookget validatingwebhookconfigurations
Everything slowetcd latency / apiserver saturationapiserver_request_duration_seconds
Name resolution fails everywhereCoreDNS or an egress policyCoreDNS endpoints
Nothing schedulesScheduler down; nodes taintedScheduler pod; node taints
Deploys hang, traffic fineControl plane unavailable/readyz?verbose
Pods failing on one node onlyThe nodeNode conditions, kubelet

The first command I run is an event histogram, not a log:

$ kubectl get events -A --field-selector type=Warning -o json \
    | jq -r '.items[].reason' | sort | uniq -c | sort -rn | head
   4821 FailedCreate
    193 Unhealthy

Four thousand identical warnings tell you which controller is retrying something impossible, and that is usually the whole diagnosis. An event flood also consumes etcd, so it can convert one broken workload into cluster-wide slowness — a second reason to alert on the rate.

The webhook case deserves naming explicitly because it is the most common and the most confusing: admission is synchronous, so a webhook whose Service is gone makes every write in the cluster fail after its timeout while reads stay perfectly healthy. Everything else in Kubernetes retries and converges; admission is the one step that stops convergence.

What I would have prepared in advance: events shipped to logging, control-plane metrics with alerts on apiserver latency and etcd fsync, and a runbook whose first line is the layer question — because under pressure people debug what they can see rather than what is broken.

Senior: What would you put in place so incidents are debuggable at all?

Everything that matters is either ephemeral or invisible by default. The work is making it outlive the incident.

SignalDefaultFix
EventsDeleted after ~1 hourShip to logging with an events exporter
Container logsLost when the pod is deletedNode-level log shipping
MetricsAbsent unless scrapedPrometheus, with per-pod and per-node series
OOM kills, evictionsInvisible in logsAlert on the events
CPU throttlingInvisible in utilisationnr_throttled — limits
Endpoint countsNo alert exists by defaultAlert on zero endpoints
API audit trailOff in many distributionsAudit logging to storage

The principle: anything that can kill your process cannot be observed by your process. A SIGKILLed container writes nothing, so OOM kills, evictions and node failures must be observed from outside — events, kernel messages and externally-scraped metrics are the layers that survive.

What I would add beyond signals: a debug image standardised and pre-pulled (so kubectl debug works in an air-gapped or rate-limited cluster), RBAC that permits pods/exec and ephemeral containers through an audited break-glass path rather than standing access, and a triage runbook that starts with the layer question.

And one cultural item: capture before you restart. The instinct to delete a broken pod is strong, it destroys the only copy of the evidence, and the replacement reproduces the fault anyway — so a one-line "capture" script that dumps describe, previous logs and events into a file is worth more than most dashboards.

A capture script, so evidence survives a restart:
$ cat > tools/capture.sh <<'SH'
#!/usr/bin/env bash
set -uo pipefail
NS=${1:?ns}; POD=${2:?pod}; OUT="capture-$POD-$(date +%s)"
mkdir -p "$OUT"
kubectl -n "$NS" describe pod "$POD"                       > "$OUT/describe.txt" 2>&1
kubectl -n "$NS" get pod "$POD" -o yaml                    > "$OUT/pod.yaml" 2>&1
kubectl -n "$NS" logs "$POD" --all-containers --timestamps > "$OUT/logs.txt" 2>&1
kubectl -n "$NS" logs "$POD" --all-containers --previous --timestamps > "$OUT/logs-previous.txt" 2>&1
kubectl -n "$NS" get events --field-selector "involvedObject.name=$POD" \
  --sort-by=.lastTimestamp                                 > "$OUT/events.txt" 2>&1
kubectl -n "$NS" get pod "$POD" -o jsonpath='{.status.containerStatuses[*].lastState}' \
  | jq . > "$OUT/laststate.json" 2>&1
echo "captured to $OUT"
SH

# Layered connectivity test: each step eliminates one subsystem.

6 (hard): Build a whole-cluster triage script and use it on a cluster-wide fault.
Solution 
$ cat > tools/cluster-triage.sh <<'SH'
#!/usr/bin/env bash
# Read-only whole-cluster triage. Answers "what layer?" before anything else.
set -uo pipefail
hdr() { printf '\n== %s\n' "$1"; }

hdr "control plane readiness"
kubectl get --raw='/readyz?verbose' 2>/dev/null | grep -v ' ok$' | head -5 || echo "  apiserver UNREACHABLE"

hdr "nodes not Ready, or under pressure"
kubectl get nodes -o json | jq -r '.items[] | .metadata.name as $n |
  (.status.conditions[] | select((.type=="Ready" and .status!="True")
     or (.type|test("Pressure")) and .status=="True")) |
  "  \($n): \(.type)=\(.status) (\(.reason))"'

hdr "pods not Running/Completed, grouped by node"
kubectl get pods -A -o json | jq -r '.items[] |
  select(.status.phase != "Running" and .status.phase != "Succeeded") |
  "\(.spec.nodeName // "unscheduled")"' | sort | uniq -c | sort -rn | head -5 | sed 's/^/  /'

hdr "pods not Running, grouped by reason"
kubectl get pods -A -o json | jq -r '.items[] |
  select(.status.phase != "Running" and .status.phase != "Succeeded") |
  ([.status.containerStatuses[]?.state.waiting.reason] | first) // .status.reason // .status.phase' \
  | sort | uniq -c | sort -rn | head -5 | sed 's/^/  /'

hdr "warning events by reason (last hour)"
kubectl get events -A --field-selector type=Warning -o json 2>/dev/null \
  | jq -r '.items[].reason' | sort | uniq -c | sort -rn | head -5 | sed 's/^/  /'

hdr "admission webhooks (a failing one blocks ALL writes)"
for k in validatingwebhookconfigurations mutatingwebhookconfigurations; do
  kubectl get "$k" -o json | jq -r --arg k "$k" '.items[] |
    select(.metadata.name | startswith("kube-") | not) | .metadata.name as $n |
    .webhooks[]? | select((.failurePolicy // "Fail") == "Fail") |
    "  \($k)/\($n): failurePolicy=Fail svc=\(.clientConfig.service.namespace)/\(.clientConfig.service.name)"'
done

hdr "core services with zero endpoints"
for ns_svc in kube-system/kube-dns ingress-nginx/ingress-nginx-controller; do
  ns=${ns_svc%/*}; svc=${ns_svc#*/}
  n=$(kubectl -n "$ns" get endpointslices -l "kubernetes.io/service-name=$svc" \
      -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]} {end}' 2>/dev/null | wc -w)
  [ "$n" -eq 0 ] && echo "  ZERO ENDPOINTS: $ns_svc" || echo "  ok $ns_svc ($n)"
done
SH
$ chmod +x tools/cluster-triage.sh

🎯 Key Takeaways

  • Ask what layer is failing before running anything else: one pod, one workload, one node, or everything — that question eliminates most of the search space.
  • Failures concentrated on a single node mean the node, not the workloads.
  • Events expire after about an hour, so Events: <none> means the record was deleted, not that nothing happened.
  • Ship events to your logging pipeline — otherwise every post-incident review starts by discovering the most useful record is gone.
  • Read status, not spec: lastState.terminated distinguished OOMKilled from a plain crash where the logs were completely empty.
  • Exit 137 is SIGKILL — OOM only when reason: OOMKilled; otherwise a stop timeout on an ignored SIGTERM.
  • CrashLoopBackOff is a restart delay, not a cause; logs --previous is where the evidence lives.
  • Capture before you restart — deleting a broken pod destroys --previous logs, and the replacement fails identically.
  • Each pod state names a subsystem: Pending → scheduler, ContainerCreating → CNI/volumes, Running 0/1 → readiness, Evicted → the node.
  • Ephemeral containers (kubectl debug --target) give a shell into a distroless pod, sharing its PID and network namespaces with its filesystem at /proc/1/root.
  • They cannot be removed; --copy-to leaves the original untouched and is right when the container will not start at all.
  • Under restricted Pod Security the debug image must comply too — that is what --profile is for.
  • Test networking in layers — pod IP, DNS, ClusterIP, ingress — because each step eliminates one subsystem.
  • Pod IP works but names fail is the signature of a NetworkPolicy blocking port 53; zero endpoints with healthy pods is a selector problem.
  • kubectl debug node/ plus crictl is ground truth when the API and the node disagree — a pod reported Running that was not running at all.
  • DiskPressure from accumulated images left every pod on one node in ContainerCreating; crictl rmi --prune recovered 44 GB and all three pods.
  • "Everything is broken" with reads working and writes failing is an admission webhook — the one synchronous step that can stop cluster-wide convergence.
  • An event flood is itself a diagnosis: counting warnings by reason names the controller retrying something impossible, and the flood also consumes etcd.
  • Anything that can kill your process cannot be observed by your process — events, kernel messages and externally-scraped metrics are the layers that survive.
  • A triage script that answers the layer question in seconds is worth more than any dashboard, because under pressure people debug what they can see rather than what is broken.
