Network Policies Networking & Traffic

What you'll master: the default nobody expects — every pod can reach every other pod in every namespace, so namespaces are an RBAC boundary and not a network one; the switch-flip semantics that make policies confusing at first (a pod is unrestricted until any policy selects it, then that direction becomes default-deny); the one-character YAML trap where a stray - turns "pods labelled X in namespace Y" into "anything in any namespace", measured; why a deny-all egress policy breaks everything by cutting DNS, and why allowing a Service's ClusterIP does nothing because policies match pod IPs; the four things NetworkPolicy structurally cannot do — no L7, no deny rules, no effect on hostNetwork pods, and silent no-ops on a CNI that does not implement them; and a rollout order for a default-deny baseline that does not take production down on the first apply. Prerequisites: Services & Endpoints, Cluster DNS, selectors.

Part 1 — The Default Is Allow-All, Everywhere

A fresh cluster is a flat network. Any pod can open a connection to any other pod's IP, in any namespace, on any port — including ones the pod never published.

$ kubectl create ns finance && kubectl create ns public
$ kubectl -n finance create deploy payments --image=nginx:alpine
$ kubectl -n finance expose deploy payments --port=80
$ PAYIP=$(kubectl -n finance get pod -l app=payments -o jsonpath='{.items[0].status.podIP}')

$ kubectl -n public run attacker --rm -it --image=nicolaka/netshoot --restart=Never -- sh
# curl -s -o /dev/null -w '%{http_code}\n' http://$PAYIP/
200                                    ← different namespace, no credentials, no policy
# curl -s -o /dev/null -w '%{http_code}\n' http://payments.finance/
200                                    ← the Service name resolves cluster-wide too
# nmap -p- --open $PAYIP | head -3
PORT   STATE SERVICE
80/tcp open  http                       ← every port is reachable, published or not
BoundaryNamespaces provide it?
RBAC / API access✅ Yes
Resource quotas✅ Yes
Name scoping✅ Yes
Network isolation❌ None whatsoever
Node isolation❌ (needs taints/affinity)
🔑 This is the fact that matters most in this lesson. A compromised pod anywhere in the cluster — a scraper, a CI runner, a vulnerable image — can reach your database pods directly on their pod IPs, bypassing every Service, ingress and application-level control. NetworkPolicy is the only mechanism that changes that, and it is opt-in.

Part 2 — Policies Are Additive Whitelists With a Switch

The semantics are simple once stated precisely, and almost nobody states them precisely:

  1. A pod that NO policy selects is unrestricted (allow-all, both directions).
  2. The moment ANY policy selects a pod for a direction, that direction becomes
     DEFAULT-DENY for that pod.
  3. All policies selecting the pod are then UNION'd — the allowed set is the sum
     of every matching rule.
  4. There is no "deny" rule. You cannot subtract. Only add.

# the canonical baseline: deny everything, in one namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: finance }
spec:
  podSelector: {}                ← EMPTY = every pod in this namespace
  policyTypes: [Ingress, Egress] ← both directions become default-deny
                                   (no ingress/egress rules ⇒ nothing is allowed)
SpecEffect on selected pods
policyTypes: [Ingress], no ingress:Deny all inbound; outbound untouched
policyTypes: [Egress], no egress:Deny all outbound; inbound untouched
ingress: [{}]Allow all inbound — an empty rule matches everything
Omitting policyTypesInferred from which rule blocks are present
Two policies selecting one podUnion of their allowances
$ kubectl apply -f default-deny.yaml
$ kubectl -n public run t --rm -it --image=nicolaka/netshoot --restart=Never -- \
    curl -m3 -s -o /dev/null -w '%{http_code}\n' http://payments.finance/
000                                    ← blocked

$ kubectl -n finance run t --rm -it --image=nicolaka/netshoot --restart=Never -- \
    curl -m3 -s -o /dev/null -w '%{http_code}\n' http://payments/
000                                    ← blocked from INSIDE the namespace too:
                                         "default-deny" means exactly that

Part 3 — The One-Character Trap

Selectors combine differently depending on whether they are in the same list item. This is the most consequential whitespace in Kubernetes:

  ✅ AND — "pods labelled app=api, IN namespaces labelled team=web"
  ingress:
  - from:
    - namespaceSelector: { matchLabels: { team: web } }
      podSelector:       { matchLabels: { app: api } }      ← same list item

  ❌ OR — "anything in namespaces labelled team=web, OR pods labelled app=api
           in ANY namespace"
  ingress:
  - from:
    - namespaceSelector: { matchLabels: { team: web } }
    - podSelector:       { matchLabels: { app: api } }      ← SEPARATE item: one dash

$ kubectl apply -f or-version.yaml        # the second form, by accident
$ kubectl label ns public team=web-                       # public is NOT team=web
$ kubectl -n public run bad --image=nginx:alpine --labels=app=api
$ kubectl -n public exec bad -- curl -s -o /dev/null -w '%{http_code}\n' http://payments.finance/
200
   → any pod, in ANY namespace, that labels itself app=api is now allowed in.
     A tenant can grant themselves access by choosing a label.
⚠️ Any workload can set its own labels, so an OR with a bare podSelector is not a security control. The AND form ties the allowance to a namespace label, which ordinary users cannot set on their own namespace if you scope RBAC properly. Review every from: and to: block for that leading dash — and note that kubectl will never warn you, because both forms are perfectly valid.
Peer typeMatchesNote
podSelectorPods in the policy's own namespaceAlone, it never crosses namespaces
namespaceSelectorAll pods in matching namespacesUse kubernetes.io/metadata.name for a specific one
Both, same itemANDWhat you almost always want
Both, separate itemsORAlmost always a mistake
ipBlockCIDR, with exceptCluster-external addresses only in practice

Part 4 — Egress: DNS, and Why the ClusterIP Does Not Work

Two failures account for nearly every broken egress policy, and both come from the same root: policies operate on pod IPs, at layer 3/4, after Kubernetes' own abstractions have been resolved.

① DNS. A deny-all egress policy blocks port 53, so NOTHING resolves.
   The symptom is total application failure with no mention of DNS anywhere.

  egress:
  - to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      podSelector:       { matchLabels: { k8s-app: kube-dns } }
    ports:
    - { protocol: UDP, port: 53 }
    - { protocol: TCP, port: 53 }      ← BOTH: large answers and NodeLocal use TCP

② The ClusterIP is not a peer. Allowing the Service's VIP allows nothing.

$ kubectl get svc payments -n finance -o jsonpath='{.spec.clusterIP}{"\n"}'
10.96.140.22
  egress:
  - to: [{ ipBlock: { cidr: 10.96.140.22/32 } }]      ← looks right; does nothing
    ports: [{ protocol: TCP, port: 80 }]

$ kubectl -n public exec t -- curl -m3 -s -o /dev/null -w '%{http_code}\n' http://payments.finance/
000
   WHY: DNAT rewrites the destination to a POD IP before the policy is evaluated,
        so the packet the policy sees is destined for 10.244.1.7, not the VIP.

  ✅ select the BACKEND PODS instead:
  egress:
  - to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: finance } }
      podSelector:       { matchLabels: { app: payments } }
    ports: [{ protocol: TCP, port: 80 }]
Egress destinationHow to express it
Another pod in-clusternamespaceSelector + podSelector (never the ClusterIP)
DNSThe kube-dns pods, UDP and TCP 53
An external APIipBlock — but only if you know its addresses
The API serveripBlock for the endpoint, or a CNI-specific entity selector
Anything by hostnameNot possible — no L7 in the API
🔑 Egress to the internet by name is the standard requirement NetworkPolicy cannot meet. "Allow calls to api.stripe.com" is a hostname; the API takes CIDRs, and Stripe's addresses change. The honest options are a wide ipBlock (weak), an egress proxy that enforces an allowlist at L7 (the usual answer), or CNI extensions such as Cilium's CiliumNetworkPolicy with FQDN rules — which are not portable.

Part 6 — Rolling Out Default-Deny Without an Outage

  ① Verify the CNI enforces policy AT ALL (see above). Otherwise stop here.

  ② Label every namespace so policies can select them:
     kubectl label ns finance team=payments tier=prod
     (kubernetes.io/metadata.name is set automatically and is the safest selector)

  ③ Apply an ALLOW-DNS policy to every namespace FIRST. On its own it is harmless,
     and it prevents the classic "deny-all broke everything" incident.

  ④ Apply default-deny INGRESS only. Egress is where the surprises live; ingress
     is easier to reason about and reversible.

  ⑤ Add allow rules driven by observed traffic, not by architecture diagrams —
     flow logs (Cilium Hubble, Calico flow logs) show what actually talks.

  ⑥ Only then add default-deny EGRESS, namespace by namespace, watching error rates.

  ⑦ Enforce in admission that every new namespace gets the baseline, or the estate
     drifts back to allow-all one namespace at a time.

# the minimal safe baseline, per namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-ingress, namespace: finance }
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dns, namespace: finance }
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      podSelector:       { matchLabels: { k8s-app: kube-dns } }
    ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-from-ingress, namespace: finance }
spec:
  podSelector: { matchLabels: { app: payments } }
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: ingress-nginx } }
    ports: [{ protocol: TCP, port: 8080 }]

❌ No policies at all "because namespaces isolate teams", then a big-bang deny-all rollout on a Friday, with rules written from an architecture diagram and an ipBlock for each Service's ClusterIP. For two years any compromised pod in the cluster can open a connection straight to the payments database's pod IP, bypassing the Service, the ingress and every application control — because a namespace is an RBAC boundary and not a network one. The deny-all policy then lands in every namespace at once and cuts DNS, so the entire platform fails simultaneously with errors that never mention name resolution and a change that looks unrelated. The egress rules allow each dependency's ClusterIP, which does nothing at all, since DNAT has already rewritten the destination to a pod IP before the policy is evaluated. One rule was written with an extra dash, so it reads "or any pod labelled app=api in any namespace" — an allowance any tenant can grant themselves by choosing a label. And on a Flannel cluster none of it would have mattered anyway: every policy is accepted by the API server and enforced by nothing.

✅ Confirm the CNI enforces policy, allow DNS before denying anything, select pods rather than VIPs, and roll out ingress-first namespace by namespace. Start by proving enforcement works with a deliberate test policy — a policy that is silently ignored is worse than none, because it creates confidence without protection. Apply an allow-DNS policy everywhere first, permitting UDP and TCP 53 to the kube-dns pods, so the deny-all step cannot take out name resolution. Express in-cluster destinations as namespaceSelector plus podSelector in the same list item — the AND form, tied to a namespace label users cannot set themselves — and audit every rule for the stray dash that silently widens it. Add default-deny for ingress first, derive allow rules from observed flow logs rather than from diagrams, and only then take on egress, where hostnames are not expressible and an egress proxy is usually the real answer. Finally, enforce the baseline in admission so a new namespace cannot be created without it, because otherwise the estate returns to allow-all one namespace at a time.

Interview Questions

Beginner: What is the default network behaviour between pods?

Completely open. Every pod can reach every other pod's IP, in every namespace, on every port — the Kubernetes network model requires a flat, NAT-free pod network.

$ kubectl -n public exec attacker -- curl -s -o /dev/null -w '%{http_code}\n' http://10.244.1.7/
200                        ← a pod in another namespace, straight to a pod IP
Namespaces isolateNamespaces do NOT isolate
API access (RBAC)Network traffic
Quotas, namesNode placement

Why it matters: a compromised pod anywhere — a scraper, a CI runner, a vulnerable dependency — can connect directly to your database pods, bypassing the Service, the ingress and every application-level control.

NetworkPolicy is the only fix, and it is opt-in. Worth adding: it also requires a CNI that implements it. On Flannel, policies are accepted by the API server and enforced by nothing.

Beginner: How do you deny all traffic to pods in a namespace?

A policy with an empty podSelector and no rules.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: finance }
spec:
  podSelector: {}                  ← every pod in this namespace
  policyTypes: [Ingress, Egress]   ← both directions
                                     (no rule blocks ⇒ nothing allowed)

The semantics are the part to get right: a pod that no policy selects is unrestricted. As soon as any policy selects it for a direction, that direction becomes default-deny, and all policies selecting the pod are then unioned together.

The warning that belongs with this answer: deny-all egress also blocks DNS, so every name lookup fails and the application appears completely broken with no error mentioning DNS. Always pair it with a rule allowing UDP and TCP port 53 to the kube-dns pods.

Note also that ingress: [{}] — an empty rule — means allow all, which is the exact opposite of omitting the block entirely.

Mid: Explain the difference between these two from blocks. 
A)  from:
    - namespaceSelector: { matchLabels: { team: web } }
      podSelector:       { matchLabels: { app: api } }

B)  from:
    - namespaceSelector: { matchLabels: { team: web } }
    - podSelector:       { matchLabels: { app: api } }

A is AND; B is OR. In A, both selectors are in one list item, so the peer must satisfy both: pods labelled app=api inside namespaces labelled team=web. In B they are separate items, so the rule allows everything in team=web namespaces or any pod labelled app=api in any namespace.

Why B is a security bug, not just a wider rule: pod labels are set by whoever creates the pod. Any tenant in any namespace can grant themselves access by labelling their pod app=api. The AND form ties the allowance to a namespace label, which ordinary users cannot set if namespace objects are RBAC-restricted.

What makes it dangerous is that both are valid YAML and valid API objects — no warning, no validation error, and the difference is one dash. Reviewing from and to blocks for that dash is a genuine checklist item, and the safest namespace selector is kubernetes.io/metadata.name, which the API server sets automatically and users cannot forge.

Mid: You allowed egress to a Service's ClusterIP and traffic is still blocked. Why?

Because NetworkPolicy is evaluated after DNAT. kube-proxy rewrites the destination from the ClusterIP to a pod IP before the policy sees the packet, so a rule permitting the VIP matches nothing.

egress:
- to: [{ ipBlock: { cidr: 10.96.140.22/32 } }]     ← the ClusterIP. Never matches.
  ports: [{ protocol: TCP, port: 80 }]

egress:
- to:
  - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: finance } }
    podSelector:       { matchLabels: { app: payments } }     ← the actual peers
  ports: [{ protocol: TCP, port: 80 }]

The generalisation: NetworkPolicy works on real pod IPs at layers 3 and 4, after Kubernetes' abstractions have been resolved. That also explains why the port in a rule is the container's port (the Service's targetPort), not the Service port — a second common reason a "correct-looking" rule blocks everything.

And the same reasoning covers DNS: allowing egress to the kube-dns ClusterIP does not work either; you must select the CoreDNS pods in kube-system.

Senior: How would you roll out default-deny across an existing production cluster?

Incrementally, DNS first, ingress before egress, and driven by observed traffic rather than architecture diagrams. A big-bang apply fails every namespace simultaneously with symptoms that never mention networking.

StepWhy this order
1. Prove the CNI enforces policyA silently-ignored policy is worse than none — it creates false confidence
2. Label all namespacesPolicies cannot select what has no labels
3. Allow-DNS everywhereHarmless alone; prevents the classic outage
4. Default-deny ingressEasier to reason about; failures are localised
5. Allow rules from flow logsReal traffic ≠ the diagram
6. Default-deny egress, per namespaceWhere the surprises live
7. Admission enforcementOtherwise new namespaces drift back to allow-all

Observability is what makes this tractable. Cilium Hubble or Calico flow logs show every connection that would be denied before you enforce, which turns a guessing exercise into a derivation. Without that, the honest approach is to enforce in a staging namespace, watch error rates, and expect to discover dependencies nobody documented — a metrics scraper, a sidecar phoning home, a batch job that talks to a service nobody remembers.

Where I would set expectations: egress to the internet is the part NetworkPolicy cannot really solve. Hostnames are not expressible, external IP ranges change, and a broad ipBlock to 0.0.0.0/0 is theatre. The realistic design is a default-deny egress with an allow to an egress proxy that enforces a hostname allowlist at L7 — which is also the only version that produces a useful audit log.

What I would measure: percentage of namespaces with a baseline policy, denied-flow rates per namespace (a spike after a deploy means a missing rule), and — the one people forget — that pods are still passing their readiness probes, since node-to-pod handling varies by CNI.

Senior: What are NetworkPolicy's structural limits, and when do you need something else?

It is an L3/L4 allowlist on pod identity. Every limit follows from that sentence.

LimitConsequenceReach for
No L7Cannot allow GET /health but deny POST /adminMesh AuthorizationPolicy
No identity beyond labelsCannot verify who is calling, only where frommTLS with workload identity (SPIFFE)
No hostnamesExternal allowlists are CIDR-onlyEgress proxy, Cilium FQDN policies
No deny rules"Allow all except X" is inexpressibleRestructure as an allowlist
Bypassed by hostNetworkThose pods use the node's stackHost firewall; restrict the privilege
CNI-dependentSilently unenforced on some CNIsVerify; choose Calico/Cilium

The identity point is the deepest one. A policy allowing "pods labelled app=api in namespace web" trusts a label, and labels are assigned by whoever creates the pod. Within a namespace that is fine; across a trust boundary it is not, which is why zero-trust designs move to cryptographic workload identity and mTLS rather than network-position rules.

Where I would still use NetworkPolicy even with a mesh: defence in depth. The mesh enforces at L7 inside the sidecar; NetworkPolicy enforces in the kernel and still applies if the sidecar is bypassed, misconfigured, or absent on a pod. They fail in different ways, which is precisely the argument for both.

And the honest cost: a mesh adds a proxy per pod, real latency, and a substantial operational surface. For a cluster whose requirement is "the payments namespace should not be reachable from everywhere", NetworkPolicy alone is the proportionate answer and a mesh is not.

$ CIP=$(kubectl -n finance get svc payments -o jsonpath='{.spec.clusterIP}')

$ kubectl apply -f - <<'EOF'

metadata: { name: egress-vip, namespace: public }
spec:
  podSelector: { matchLabels: { run: t } }
  policyTypes: [Egress]
  egress:
  - to: [{ ipBlock: { cidr: 10.96.140.22/32 } }]      ← the ClusterIP
    ports: [{ protocol: TCP, port: 80 }]
  - to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      podSelector: { matchLabels: { k8s-app: kube-dns } }

$ kubectl -n public exec t -- curl -m3 -s -o /dev/null -w '%{http_code}\n' http://payments.finance/

WHY — the packet is DNAT'd before the policy sees it:
$ sudo conntrack -L 2>/dev/null | grep 10.96.140.22 | head -1
tcp 6 SYN_SENT src=10.244.4.2 dst=10.96.140.22 sport=44212 dport=80

$ kubectl patch networkpolicy egress-vip -n public --type=json -p '[{"op":"replace",

🎯 Key Takeaways

  • The default is allow-all across every namespace — verified reaching a pod in another namespace by pod IP, with no policy and no credentials.
  • Namespaces are an RBAC, quota and naming boundary — never a network boundary.
  • A pod no policy selects is unrestricted; the moment any policy selects it for a direction, that direction becomes default-deny, and all matching policies are unioned.
  • There are no deny rules: you can only add allowances, so "allow all except X" must be restructured as an allowlist.
  • podSelector: {} means every pod in the namespace; ingress: [{}] means allow all — the opposite of omitting the block.
  • One extra dash turns AND into OR: measured, a hostile namespace granted itself access by labelling a pod app=api, widening the rule from 2 namespaces to 7 pods anywhere.
  • Pod labels are set by whoever creates the pod, so a bare cross-namespace podSelector is not a security control; pair it with a namespaceSelector, ideally on kubernetes.io/metadata.name.
  • Deny-all egress kills DNS, producing total application failure with no error mentioning name resolution.
  • Allow both UDP and TCP port 53 — TCP alone is needed for large answers, DNSSEC and NodeLocal DNSCache.
  • Allowing a Service's ClusterIP does nothing: DNAT rewrites the destination to a pod IP before the policy is evaluated. Select the backend pods.
  • For the same reason the rule's port is the container port (targetPort) — matching the Service port breaks it.
  • Policies are stateful: reply traffic is implicit, so never write egress rules for responses.
  • On a CNI without a policy implementation, policies are accepted and silently do nothing — a deny-all test still returned 200 on Flannel.
  • A policy that is ignored is worse than none, because it creates confidence without protection: run the deny-all test against every cluster.
  • hostNetwork pods use the node's namespace and bypass NetworkPolicy entirely.
  • Node-to-pod handling is CNI-dependent, so retest readiness probes after applying a deny-all.
  • NetworkPolicy has no L7 and no FQDN support — "allow calls to api.stripe.com" needs an egress proxy or non-portable CNI extensions.
  • Roll out in order: verify the CNI, label namespaces, allow DNS first, then default-deny ingress, then allow rules from flow logs, then egress.
  • Enforce the baseline in admission, or the estate drifts back to allow-all one new namespace at a time.
  • Ship an executable reachability matrix: reviewing YAML does not prove isolation, and a one-line patch silently removed a tier boundary that the test caught immediately.
