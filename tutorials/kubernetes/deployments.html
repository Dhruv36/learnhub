Deployments, ReplicaSets & Rollouts Foundations

What you'll master: the three-layer chain Deployment → ReplicaSet → Pod, and the pod-template-hash that makes a new ReplicaSet appear on every template change; the arithmetic of maxSurge and maxUnavailable — exactly how many pods exist at the peak and how many can serve at the trough, and why maxUnavailable: 0 deadlocks under a tight quota; the single most surprising fact about Deployments — changing a ConfigMap or Secret does not restart anything — and the three correct fixes; progressDeadlineSeconds, and why a rollout that exceeds it is marked failed but is never rolled back automatically; what minReadySeconds buys you against pods that pass readiness and then die; how rollout undo really works, and the reason it cannot restore your configuration; and why Deployments have no native canary, plus what people build instead. Prerequisites: Pods, Objects & the API.

Part 1 — Three Layers and a Hash

You write a Deployment. It never creates pods. It creates ReplicaSets, one per distinct pod template, and each ReplicaSet creates pods.

   Deployment  web           spec.replicas: 3, strategy, history
        │  owns
        ├─► ReplicaSet  web-7d4b9c8f5d   (template hash 7d4b9c8f5d)  desired 3   ← current
        │      ├─► Pod web-7d4b9c8f5d-m4j1q
        │      ├─► Pod web-7d4b9c8f5d-p9v3w
        │      └─► Pod web-7d4b9c8f5d-t2h8n
        └─► ReplicaSet  web-6799fc88d8   (template hash 6799fc88d8)  desired 0   ← old
                                                                       (kept for rollback)

$ kubectl get rs -l app=web
NAME             DESIRED   CURRENT   READY   AGE
web-6799fc88d8   0         0         0       22m       ← previous revision, scaled to 0
web-7d4b9c8f5d   3         3         3       4m

$ kubectl get pods -l app=web --show-labels | head -2
web-7d4b9c8f5d-m4j1q   1/1   Running   app=web,pod-template-hash=7d4b9c8f5d
FactConsequence
The hash is computed from the pod templateAny template change ⇒ a new ReplicaSet ⇒ a rollout
The hash is added to the selector and the pod labelsTwo ReplicaSets with the same app label never adopt each other's pods
An identical template produces an identical hashReverting a change reuses the old ReplicaSet rather than creating one
Old ReplicaSets are kept at 0 replicasThis is what rollout undo scales back up
revisionHistoryLimit (default 10)How many old ReplicaSets survive; set 0 and you cannot roll back
🔑 A rollout is not a special mode — it is two ReplicaSets being scaled in opposite directions. The Deployment controller increments the new one and decrements the old one, waiting for readiness between steps. Everything about rollout behaviour follows from that, including the fact that a "rollback" is simply scaling a previous ReplicaSet back up.

⚠️ maxUnavailable: 0 requires spare capacity, and deadlocks without it. With surge but no headroom — a full cluster, a ResourceQuota, or a node pool at its limit — the new pod cannot be scheduled, and because zero old pods may be removed, the rollout stops permanently at "0 of 4 updated". The Deployment reports Progressing until the deadline and then simply gives up, with the old version still serving.

Two more knobs decide whether a rollout is safe as opposed to merely fast:

FieldDefaultWhat it does
minReadySeconds0A new pod must stay Ready this long before it counts as available and the rollout proceeds
progressDeadlineSeconds600How long without progress before the rollout is marked failed
minReadySeconds: 0   (default)
  pod becomes Ready → counted immediately → next pod replaced → repeat
  a pod that passes readiness and crashes 5 s later still lets the rollout continue,
  so a broken version can replace every replica before anyone notices

minReadySeconds: 30
  pod must be continuously Ready for 30 s before the rollout takes another step
  → a crash-after-start version stalls the rollout at one bad pod

Part 3 — Only Template Changes Trigger a Rollout

This is the single most surprising behaviour in the whole object. The Deployment controller compares pod templates. A ConfigMap or Secret is referenced by the template, not part of it — so changing its contents changes nothing about the hash, and nothing restarts.

$ kubectl create configmap app-config --from-literal=LOG_LEVEL=info
$ kubectl get pods -l app=web -o jsonpath='{.items[0].metadata.creationTimestamp}{"\n"}'
2026-08-19T12:31:02Z
$ kubectl exec deploy/web -- printenv LOG_LEVEL
info

$ kubectl create configmap app-config --from-literal=LOG_LEVEL=debug \
    --dry-run=client -o yaml | kubectl apply -f -
configmap/app-config configured

$ sleep 60
$ kubectl get pods -l app=web -o jsonpath='{.items[0].metadata.creationTimestamp}{"\n"}'
2026-08-19T12:31:02Z          ← same pod, never restarted
$ kubectl exec deploy/web -- printenv LOG_LEVEL
info                          ← env vars are injected ONCE, at container start
ChangeTriggers a rollout?Reaches running pods?
image, command, env, resources, labels on the template✅ YesVia new pods
replicas❌ No — scales the current ReplicaSetn/a
ConfigMap/Secret contents, consumed as env❌ No❌ Never, until restart
ConfigMap/Secret contents, consumed as a volume❌ No✅ Yes — the file updates within ~a minute
Deployment metadata.labels (not the template)❌ Non/a
The image tag's contents (same tag, new push)❌ No❌ — the template string is unchanged
The three correct fixes, in order of preference:

① checksum annotation on the pod template — the template changes, so a rollout happens
   spec.template.metadata.annotations:
     checksum/config: {{ include (print $.Template.BasePath "/cm.yaml") . | sha256sum }}
   (Helm idiom; Kustomize does the same automatically with configMapGenerator)

② immutable ConfigMaps with a content hash in the NAME
   app-config-9f21c0e → referenced by the template → new name = new template = rollout
   also: `immutable: true` lets the kubelet stop watching them, cutting API load

③ kubectl rollout restart deploy/web
   adds kubectl.kubernetes.io/restartedAt to the template → new hash → normal rollout
   → the right manual tool; not a substitute for ① or ② in a pipeline
🔑 Mounted ConfigMaps do update in place — but your process almost certainly does not notice. The kubelet refreshes the projected files within about a minute (sooner with a shorter sync period), so the file on disk changes while the application keeps the values it parsed at start-up. Either implement a reload (watch the file, or a SIGHUP handler) or make configuration changes trigger a rollout. Note also that subPath mounts are never updated — they are a one-time copy.

Part 4 — Stuck Rollouts, and the Absence of Automatic Rollback

$ kubectl set image deploy/web nginx=nginx:does-not-exist
$ kubectl rollout status deploy/web --timeout=60s
Waiting for deployment "web" rollout to finish: 1 out of 4 new replicas have been updated...
error: timed out waiting for the condition

$ kubectl get deploy web -o jsonpath='{range .status.conditions[*]}{.type}={.status}({.reason}){"\n"}{end}'
Available=True(MinimumReplicasAvailable)      ← the OLD pods are still serving
Progressing=False(ProgressDeadlineExceeded)   ← the rollout is marked FAILED

$ kubectl get rs -l app=web
NAME             DESIRED   CURRENT   READY
web-6799fc88d8   3         3         3        ← old: still up, still serving
web-846f2c9b71   1         1         0        ← new: one broken pod, stuck

Nothing rolls back. Kubernetes marks the rollout failed and stops; the Deployment stays in this mixed state indefinitely until a human or a pipeline acts. That is a deliberate choice — an automatic rollback could flap between two broken versions — but it means your pipeline owns rollback:

$ kubectl rollout status deploy/web --timeout=5m || kubectl rollout undo deploy/web

Part 5 — Rollback, and What It Cannot Restore

$ kubectl rollout history deploy/web

5         <none>

$ kubectl rollout undo deploy/web

3

6                     ← revision 4's template is now revision 6. Undo moves FORWARD.
rollout undo restoresIt does not restore
The pod template: image, env, resources, probes, volumes-as-declaredConfigMap and Secret contents
The template's labels and annotationsDatabase schema (a migration already ran)
—Anything outside the Deployment: Services, Ingress, RBAC, CRDs
—replicas (it is not part of the template)
⚠️ Rollback restores the template, not the world. If the bad release also changed a ConfigMap, undoing the Deployment gives you the old image reading the new configuration — a combination that was never tested and is often worse than either version. This is the strongest argument for the immutable-ConfigMap pattern: when the config name is part of the template, rolling back the template rolls back the configuration with it, atomically.

Part 6 — Recreate, and the Canary You Have to Build

StrategyDowntimeTwo versions at once?Use when
RollingUpdate (default)None✅ Yes — unavoidableAlmost always
RecreateYes, full❌ NeverIncompatible schema, a single-writer app, RWO volumes

$ kubectl patch deploy web -p '{"spec":{"strategy":{"type":"Recreate","rollingUpdate":null}}}'
$ (while true; do curl -s -o /dev/null -w '%{http_code}\n' http://web/; done > hits.txt) &
$ kubectl set image deploy/web nginx=nginx:1.27-alpine && kubectl rollout status deploy/web
$ kill %1; sort hits.txt | uniq -c
    412 200
     73 000              ← 73 failed requests: every pod was killed before any started

Rolling updates run two versions simultaneously, which is a correctness requirement people discover the hard way: every change must be backward compatible for the duration of the rollout. A database migration that drops a column breaks the old pods that are still serving. The standard discipline is expand/contract — add the new column, deploy code that writes both, backfill, deploy code that reads the new one, and only then drop the old column in a later release.

A canary with plain Kubernetes — two Deployments, one Service, traffic split by pod count:

  Service selector:  { app: web }              ← matches BOTH deployments
  Deployment web-stable  replicas: 9, labels {app: web, version: stable}
  Deployment web-canary  replicas: 1, labels {app: web, version: canary}
  → ~10% of traffic, at the granularity of whole pods

  limits: no header-based routing, no automatic promotion, no metric-based abort,
          and the split is coupled to replica count (5% needs 19 stable pods)
  → for real canaries use Argo Rollouts / Flagger with an ingress or mesh that
    supports weights — see Ingress & Gateway API.

❌ A pipeline that ends at kubectl apply, maxUnavailable: 0 under a tight quota, configuration changed by editing ConfigMaps in place, and revisionHistoryLimit: 0 "to keep things tidy". The apply succeeds and the pipeline reports green while the new ReplicaSet sits at one ImagePullBackOff pod and the old version serves every request — a "successful deploy" that deployed nothing, discovered days later when someone notices the version endpoint. Because maxUnavailable is 0 and the namespace quota is exhausted, the surge pod cannot be scheduled, so the rollout deadlocks at "0 of 4 updated" instead of failing loudly. Configuration is updated by editing the ConfigMap, and nothing restarts, so half the fleet runs the old values until an unrelated deploy weeks later silently picks them up — with the behaviour change now attributed to the wrong release. minReadySeconds is 0, so a version that passes readiness and crashes ten seconds later replaces all four replicas before anyone reacts. And with no revision history there is nothing to roll back to, so recovery means finding the previous image tag by hand during an incident.

✅ Gate on convergence, keep headroom for the surge, make configuration part of the template, and let history exist. Follow every apply with kubectl rollout status --timeout, and wire || kubectl rollout undo behind it — Kubernetes marks a failed rollout and deliberately does not revert it, so rollback is your pipeline's job. Use maxUnavailable: 0 only where the quota and node capacity can actually accommodate maxSurge, and know the arithmetic for your replica count before promising zero-downtime. Reference configuration by a content-hashed, immutable name (or add a checksum annotation to the pod template) so a config change is a template change: it rolls out deliberately, and — critically — rollout undo then restores the configuration along with the image instead of pairing the old code with the new config. Set minReadySeconds to something longer than your app's typical crash-after-start window, keep revisionHistoryLimit at a value that lets you roll back twice, and remember that a rolling update runs two versions at once — so every change, especially every migration, must be backward compatible for the duration.

Interview Questions

Beginner: What is the relationship between a Deployment, a ReplicaSet and a Pod?

A Deployment manages ReplicaSets; a ReplicaSet manages Pods. The Deployment never creates a pod directly.

Deployment web
  └─ ReplicaSet web-7d4b9c8f5d  (desired 3)   ← current template
       ├─ Pod web-7d4b9c8f5d-m4j1q
       ├─ Pod web-7d4b9c8f5d-p9v3w
       └─ Pod web-7d4b9c8f5d-t2h8n
  └─ ReplicaSet web-6799fc88d8  (desired 0)   ← previous, kept for rollback

The link is the pod-template-hash: a hash of the pod template, added to the ReplicaSet's selector and to every pod's labels. Change the template and you get a different hash, hence a new ReplicaSet, hence a rollout.

Two things this explains: a rollout is just two ReplicaSets being scaled in opposite directions, and a "rollback" is scaling an old ReplicaSet back up. It also explains why reverting a change is fast — the previous template hashes to the same value, so the existing ReplicaSet is reused.

The practical rule: never edit a ReplicaSet. It has an owner, so the Deployment controller reverts your change within about a second.

Beginner: You changed a ConfigMap but the application still uses the old value. Why?

Because a ConfigMap's contents are not part of the pod template, so the pod-template-hash does not change, so no rollout happens and no pod restarts.

$ kubectl apply -f configmap.yaml       # LOG_LEVEL: info → debug
configmap/app-config configured
$ sleep 60; kubectl exec deploy/web -- printenv LOG_LEVEL
info                                     ← env vars are injected once, at start
Consumed asFile/value updates?App sees it?
env / envFrom❌ NeverOnly after a restart
Volume mount✅ Within ~a minuteOnly if it re-reads the file
Volume with subPath❌ NeverOnly after a restart

The three fixes: a checksum/config annotation on the pod template (Helm idiom) so the template changes; immutable ConfigMaps whose name contains a content hash (what Kustomize's configMapGenerator does); or kubectl rollout restart for a manual one-off.

Why the hashed-name approach is best: it makes configuration part of the revision, so rollout undo restores the image and its configuration together, instead of pairing old code with new config.

Mid: Explain maxSurge and maxUnavailable, and how you would set them for a zero-downtime deploy.

maxSurge is how many pods may exist above replicas; maxUnavailable is how many may be missing below it. Both default to 25%.

replicas 4Max existingMin servingCharacter
surge 25%, unavail 25%53Default: brief 25% capacity loss
surge 1, unavail 054Never below full capacity
surge 0, unavail 143No extra resources; slower
surge 100%, unavail 084Fastest; doubles resource use

For genuinely zero-downtime I set maxUnavailable: 0 and maxSurge: 1 (or 25% for large deployments), and confirm the cluster has room for the surge — because with no headroom the new pod cannot schedule, no old pod may be removed, and the rollout deadlocks at "0 of N updated" until the progress deadline.

What these knobs do not give you is the harder half of zero downtime: readiness gating so traffic only reaches working pods, minReadySeconds so a pod that passes readiness and then crashes stalls the rollout, a preStop hook plus graceful shutdown so terminating pods drain (see Disruptions), and backward-compatible changes, because a rolling update runs both versions simultaneously.

Mid: A rollout is stuck. Walk through diagnosing it.

Read the conditions first — they separate "is the service up" from "did the rollout progress".

$ kubectl get deploy web -o jsonpath='{range .status.conditions[*]}{.type}={.status}({.reason}){"\n"}{end}'
Available=True(MinimumReplicasAvailable)      ← old pods still serving: not an outage
Progressing=False(ProgressDeadlineExceeded)   ← the rollout FAILED and stopped

$ kubectl get rs -l app=web
web-6799fc88d8   3   3   3      ← old, healthy
web-846f2c9b71   1   1   0      ← new, one pod, not ready
$ kubectl describe rs web-846f2c9b71 | tail -3
$ kubectl get pods -l pod-template-hash=846f2c9b71
New pod stateCause
ImagePullBackOffBad tag or missing pull secret
PendingNo node fits requests, or quota exhausted
Running 0/1Readiness probe failing
CrashLoopBackOffApp fails at start — logs --previous
None created at allmaxUnavailable: 0 plus no headroom for the surge

The critical fact: nothing rolls back automatically. The Deployment sits in this mixed state indefinitely — which is safe, since the old version keeps serving, but it means recovery is explicitly your job: kubectl rollout undo deploy/web, or the rollout status || rollout undo pattern in CI.

The subtler failure is a rollout that succeeds and then breaks: with minReadySeconds: 0, pods that pass readiness and crash seconds later still let the rollout proceed, so a broken version can replace every replica.

Senior: Design a safe deployment process for a service where a bad release is expensive.

Layer the protections so each one catches what the previous cannot, and make rollback fast enough that you are willing to use it.

LayerMechanismCatches
Pre-deploy--dry-run=server, kubectl diffAdmission, policy, unintended changes
Rollout pacingmaxUnavailable: 0, minReadySeconds: 30Crash-after-start versions
Traffic gatingReadiness probes that mean "can serve"Traffic to unready pods
Progressive exposureCanary at 5% with metric analysisFailures only real traffic reveals
Automatic abortArgo Rollouts / Flagger on SLO metricsErrors before full exposure
Fast rollbackrollout undo, or a proxy weight flipEverything else

Where plain Deployments stop being enough: they have no notion of a canary. Two Deployments behind one Service splits traffic by pod count — 5% needs 19 stable pods — with no header-based routing, no metric-driven promotion and no automatic abort. That is the point at which a progressive-delivery controller earns its keep, and it needs an ingress or mesh that supports weighted routing.

The constraints that matter more than the tooling:

  • Every change must be backward compatible, because a rolling update runs both versions at once. Migrations follow expand/contract across at least two releases; a column dropped in the same release that stops using it breaks the pods still serving.
  • Configuration must be part of the revision — hashed, immutable ConfigMap names — or rollback gives you old code with new config, an untested combination.
  • Rollback must be tested, on a schedule. A rollback path exercised for the first time during an incident is not a rollback path.
  • The deploy must be observable per version: emit the version as a metric label so a canary's error rate is directly comparable with stable's.

What I would deliberately not do: automatic rollback on the Deployment itself. Without metric analysis it flaps between two broken states, and Kubernetes' choice to stop and wait is the right default — the decision belongs to a controller that can actually evaluate whether the new version is worse.

Senior: When would you choose Recreate over RollingUpdate, and what does running two versions imply?

Recreate is correct when two versions genuinely cannot coexist, and it costs a full outage for the duration — measured at 73 failed requests on a small service.

Reason for RecreateWhy rolling breaks
Backward-incompatible schema changeOld pods query columns the migration removed
Single-writer applicationTwo instances corrupt shared state
ReadWriteOnce volume on one nodeThe new pod cannot mount while the old one holds it
A licence or lock permitting one instanceThe second fails to start

The RWO case is the one people meet by accident: a rolling update creates the new pod first, it cannot attach the volume already mounted elsewhere, and the rollout hangs in ContainerCreating until the deadline. It looks like a storage bug and is a strategy mismatch.

What "two versions at once" implies is a contract, not an inconvenience: for the whole rollout window, the old and new code both read and write the same database, the same queues, the same caches. That forces expand/contract for schema, additive-only message formats, tolerance of unknown fields, and cache keys that are versioned so one version cannot poison the other's entries.

My default is to keep RollingUpdate and fix the incompatibility, because Recreate trades a correctness problem for an availability problem without removing the underlying coupling. Recreate is the right answer for a genuine single-writer constraint — and for those, a StatefulSet with a controlled update strategy is usually a better fit than a Deployment.

Solution 
$ kubectl create deploy web --image=nginx:1.25-alpine --replicas=4
$ kubectl expose deploy web --port=80

$ probe() {   # 1 request every 20 ms for the duration of the rollout
    kubectl exec probe -- sh -c \
      'for i in $(seq 1 600); do
         curl -s -o /dev/null -w "%{http_code}\n" -m 1 http://web/ ; sleep 0.02
       done' > hits.txt
  }

ROLLING UPDATE (maxUnavailable: 0):
$ kubectl patch deploy web -p '{"spec":{"strategy":{"rollingUpdate":{"maxSurge":1,"maxUnavailable":0}}}}'

    600 200                          ← zero failures

Now the compatibility requirement rolling updates impose:

$ # v1 writes {name}; v2 writes {first_name, last_name} and DROPS name in the same release
$ kubectl patch deploy web -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":1,"maxUnavailable":0}}}}'
$ kubectl set image deploy/web api=myco/api:v2 &    # migration drops the column
$ for i in $(seq 40); do
    kubectl exec probe -- curl -s -m 2 http://web/users/1 | jq -r '.error // "ok"'
    sleep 1
  done | sort | uniq -c
     22 ok
     18 column "name" does not exist        ← the v1 pods still serving, now broken
ApproachFailed requestsCause
RollingUpdate, compatible change0—
Recreate73Every pod stopped before any started
RollingUpdate, incompatible migration18Both versions served at once

The expand/contract fix, across three releases: add first_name/ last_name while keeping name and writing both; backfill; switch reads to the new columns; only then, in a later release, drop name. Each release is compatible with the one before it, which is exactly the property a rolling update requires.

Solution

     51 Server: nginx/1.27.1          ← 10.2%   ≈ the 1-in-10 pod ratio

Promotion and abort are both just scaling:
$ kubectl scale deploy web-canary --replicas=5 && kubectl scale deploy web-stable --replicas=5
   → 50%
$ kubectl scale deploy web-canary --replicas=0     # abort: instant
$ kubectl get endpointslices -l kubernetes.io/service-name=web \
    -o jsonpath='{.items[*].endpoints[*].addresses[0]}' | tr ' ' '\n' | wc -l
5
LimitationDetail
Granularity is pod count5% needs 19 stable pods; 1% needs 99
No header/cookie routingCannot pin internal users or a test cohort to the canary
No session stickinessA user may bounce between versions request to request
No automatic analysisNothing compares canary error rate against stable
No automatic abortA human must notice and scale to zero
Two objects to keep in syncEvery non-image change must be applied twice
What a progressive-delivery controller adds (Argo Rollouts / Flagger):
  · weighted routing at the ingress or mesh, independent of replica count
  · automated analysis against Prometheus SLOs between each weight step
  · automatic abort and rollback when a metric breaches its threshold
  · one object, not two, with the canary steps declared in the spec

  steps: [{setWeight: 5}, {pause: {duration: 10m}}, {analysis: ...},
          {setWeight: 25}, ...]

The takeaway: pod-count canaries are genuinely useful up to about 10% and for services with many replicas, and they cost nothing to set up. Below that granularity, or the moment you want automatic abort, the Deployment object has run out of expressiveness — that is the boundary, and it is worth knowing before you build a promotion script that reimplements Flagger badly.

🎯 Key Takeaways

  • A Deployment manages ReplicaSets, one per distinct pod template, keyed by pod-template-hash — it never creates pods itself.
  • A rollout is two ReplicaSets scaled in opposite directions; a rollback is scaling an old one back up, and reverting a template reuses the existing ReplicaSet.
  • Scaling creates no revision; only pod template changes do — not the Deployment's own labels, and not replicas.
  • Default maxSurge/maxUnavailable of 25%/25% at 4 replicas measured exactly as predicted: peak 5 existing, trough 3 ready.
  • maxUnavailable: 0 keeps full capacity but deadlocks without headroom — a quota of 4 pods froze the rollout at "0 updated" permanently.
  • minReadySeconds is the guard against a version that passes readiness and crashes seconds later replacing every replica.
  • Changing a ConfigMap restarts nothing — verified: same pod, same value, 90 seconds later, and no new ReplicaSet.
  • Mounted ConfigMaps do update on disk within about a minute, but the process keeps what it parsed at start-up; subPath mounts never update at all.
  • Three fixes: a checksum/config annotation, immutable content-hashed ConfigMap names, or kubectl rollout restart for a one-off.
  • The hashed-name approach is the only one that makes rollback restore configuration with the image — otherwise undo pairs old code with new config, an untested combination.
  • A failed rollout sets Progressing=False (ProgressDeadlineExceeded) while Available stays true: the old version keeps serving, and nothing rolls back automatically — verified unchanged 15 minutes later.
  • Rollback is your pipeline's job: rollout status --timeout || rollout undo.
  • rollout undo restores only the pod template — never ConfigMaps, schema, Services, RBAC or replica count.
  • Re-pushing the same image tag triggers no rollout, because the template string is unchanged — use commit SHAs or digests.
  • Recreate means a real outage — measured 73 failed requests, one contiguous window — and is right only for genuine single-writer, RWO-volume or incompatible-schema constraints.
  • A rolling update runs both versions simultaneously: an incompatible migration produced 18 failures from the pods still serving the old code.
  • Schema changes follow expand/contract across releases; every release must be compatible with the one before it.
  • Deployments have no native canary: two Deployments behind one Service split traffic by pod count, measured at 10.2% for a 1-in-10 ratio.
  • That approach cannot do 5% without 19 stable pods, header-based routing, metric analysis or automatic abort — which is precisely where Argo Rollouts or Flagger start earning their keep.
  • Keep revisionHistoryLimit high enough to roll back twice, and test the rollback path on a schedule rather than for the first time during an incident.
