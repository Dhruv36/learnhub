Cluster DNS & Service Discovery Networking & Traffic

What you'll master: the exact name scheme CoreDNS serves, and which record type each kind of Service produces; the ndots:5 trap — measured — where resolving one external hostname costs eight DNS queries and adds latency to every outbound call, plus the two one-line fixes; how CoreDNS is deployed, scaled and cached, and why NodeLocal DNSCache exists rather than simply adding replicas; the notorious five-second DNS timeout caused by a conntrack race on parallel UDP lookups, and what actually fixes it; dnsPolicy, including the hostNetwork trap where pods silently lose all cluster resolution; StatefulSet per-pod DNS and publishNotReadyAddresses, without which clustered databases cannot bootstrap; and a debugging order that tells NXDOMAIN, SERVFAIL and timeout apart in one command. Prerequisites: Services & Endpoints, Pods.

🔑 DNS is the only reason a headless Service is useful. Part 2 — ndots:5, and the Eight Queries

Every pod gets a generated /etc/resolv.conf. The ndots option decides when a name is treated as absolute, and Kubernetes sets it to 5 — far higher than any normal system:

$ kubectl exec p -- cat /etc/resolv.conf
search shop.svc.cluster.local svc.cluster.local cluster.local eu-west-1.compute.internal
nameserver 10.96.0.10
options ndots:5

  rule: a name with FEWER than `ndots` dots is tried against every search domain
        FIRST, and only then as written.

Resolving "api.stripe.com" (2 dots < 5) from a pod:

  ① api.stripe.com.shop.svc.cluster.local        → NXDOMAIN
  ② api.stripe.com.svc.cluster.local             → NXDOMAIN
  ③ api.stripe.com.cluster.local                 → NXDOMAIN
  ④ api.stripe.com.eu-west-1.compute.internal    → NXDOMAIN
  ⑤ api.stripe.com                               → 3.18.7.42   ✅

  and glibc queries A and AAAA in parallel for each  →  10 queries for one name

$ kubectl exec p -- sh -c 'time getent hosts api.stripe.com' 2>&1 | tail -3
real    0m0.048s
$ kubectl -n kube-system logs -l k8s-app=kube-dns --tail=200 | grep -c 'api.stripe.com'
10                                    ← ten queries reached CoreDNS

$ kubectl exec p -- sh -c 'time getent hosts api.stripe.com.'   # trailing dot
real    0m0.007s                      ← 7 ms vs 48 ms: one query, no search path
$ kubectl -n kube-system logs -l k8s-app=kube-dns --tail=50 | grep -c 'api.stripe.com'
2                                     ← A + AAAA only
FixHowTrade-off
Trailing dot in the hostnameapi.stripe.com.Free; but every config and library must do it
Per-pod ndotsdnsConfig: {options: [{name: ndots, value: "2"}]}Cross-namespace short names (web.shop) still work; bare web does not
Use FQDNs internallyweb.shop.svc.cluster.local.Verbose, but unambiguous and fastest
NodeLocal DNSCacheCache on every nodeDoes not reduce the query count, only its cost
⚠️ This is the single biggest source of avoidable DNS load in most clusters. A service making 1,000 external API calls a second with a fresh resolution each time generates 10,000 queries per second, of which 8,000 are guaranteed NXDOMAIN. CoreDNS then becomes a scaling problem that looks like a mysterious latency floor on outbound calls — and the fix is two lines of pod spec.

Part 4 — The Five-Second DNS Timeout

A famous and thoroughly confusing symptom: occasional requests take exactly 5.00 seconds, then succeed. The cause is a kernel race between two UDP packets sent from one socket at the same instant:

  glibc sends the A and AAAA queries in PARALLEL, from the same source port,
  to the same destination (the DNS Service VIP).

  Both packets hit netfilter at once and each tries to create a conntrack entry
  for the same 5-tuple. One insertion wins; the other is dropped as a duplicate.

  → one of the two queries vanishes
  → glibc waits for its answer until the resolver timeout (default 5 s)
  → retries, succeeds

  $ kubectl exec p -- sh -c 'for i in $(seq 200); do
       /usr/bin/time -f %e getent hosts web 2>&1 | tail -1; done' | sort -n | tail -3
  0.004
  5.003
  5.004                        ← two of 200 lookups took exactly five seconds
MitigationMechanismVerdict
options single-request-reopenUse a new source port for the second queryglibc only; works
options use-vcForce TCP for DNSWorks; slightly more overhead
options timeout:1 attempts:3Fail fast and retryHides it rather than fixing it
NodeLocal DNSCacheNode-local agent, TCP upstream, no DNAT for the hot pathThe proper fix
Alpine/musl imagesmusl also queries in parallelAffected too — not a glibc-only issue
dnsConfig:
  options:
  - { name: ndots, value: "2" }
  - { name: single-request-reopen }
  - { name: timeout, value: "1" }
  - { name: attempts, value: "3" }
🔑 Exactly 5.000 seconds is a fingerprint. Application latency percentiles with a hard cluster at 5 s — never 4.2 s, never 6.1 s — are almost always this, not your database and not the network. The giveaway is that the total request time is 5 s plus the normal service time, because the delay is entirely in name resolution before the connection is even attempted.

Part 5 — dnsPolicy and the hostNetwork Trap

ClusterFirst (default)CoreDNS, falling back upstreamNormal pods

$ kubectl run hn --image=nicolaka/netshoot --overrides='{"spec":{"hostNetwork":true}}' \
    -- sleep 3600
$ kubectl exec hn -- cat /etc/resolv.conf
nameserver 10.0.0.2                    ← the NODE's resolver, not CoreDNS
search eu-west-1.compute.internal
$ kubectl exec hn -- getent hosts web
                                       ← nothing. Cluster names do not resolve.

$ kubectl run hn2 --image=nicolaka/netshoot \
    --overrides='{"spec":{"hostNetwork":true,"dnsPolicy":"ClusterFirstWithHostNet"}}' -- sleep 3600
$ kubectl exec hn2 -- getent hosts web
10.96.140.22     web.shop.svc.cluster.local     ← fixed

The trap is that hostNetwork: true silently changes dnsPolicy to Default unless you say otherwise. Anything running on the host network — monitoring agents, ingress controllers, CNI components — loses cluster service discovery without a single error message.

Part 6 — StatefulSet DNS and Debugging

apiVersion: apps/v1
kind: StatefulSet
spec:
  serviceName: db-headless              ← REQUIRED: this is what creates per-pod DNS
...
apiVersion: v1
kind: Service
metadata: { name: db-headless }
spec:
  clusterIP: None
  publishNotReadyAddresses: true        ← critical for bootstrap; see below
  selector: { app: db }

$ kubectl exec p -- dig +short db-0.db-headless.shop.svc.cluster.local
10.244.1.7                              ← stable name; survives rescheduling
⚠️ publishNotReadyAddresses: true is what lets a clustered database form a cluster. During bootstrap no member is Ready — each is waiting to discover its peers — so with the default behaviour DNS returns nothing and the cluster deadlocks: readiness depends on peer discovery, and peer discovery depends on readiness. Publishing not-ready addresses breaks the cycle. Covered further in StatefulSets.

❌ Default ndots:5 everywhere, two CoreDNS replicas for a 200-node cluster, an egress NetworkPolicy that forgot port 53, monitoring agents on hostNetwork with the default dnsPolicy, and a StatefulSet whose headless Service does not publish not-ready addresses. Every external API call costs ten DNS queries, eight of them guaranteed NXDOMAIN, so CoreDNS runs at 40,000 QPS and outbound latency has an unexplained floor. Occasional requests take exactly 5.000 seconds and are blamed on the database for a month, because nobody recognises the conntrack race fingerprint. The new "deny all egress" policy is rolled out and every pod in the namespace instantly loses name resolution, which presents as total application failure with no obvious connection to the policy. The monitoring DaemonSet runs on the host network and silently cannot resolve a single cluster service, so its scrape targets have been failing since it was deployed. And the new database StatefulSet never forms a cluster, because each member waits for peers that DNS refuses to publish until they are Ready.

✅ Cut the query count first, cache at the node, and treat DNS as a dependency with its own failure modes. Set ndots: 2 in dnsConfig for pods that talk to external services, or use fully-qualified names with a trailing dot — measured, that took one lookup from 48 ms and ten queries to 7 ms and two. Deploy NodeLocal DNSCache, which serves cache hits without leaving the node and uses TCP upstream, removing the five-second conntrack race as a side effect; add single-request-reopen where you cannot. Scale CoreDNS with the cluster-proportional autoscaler rather than leaving it at two replicas, and alert on its NXDOMAIN ratio — a sudden climb is almost always a misconfigured search path. Always allow egress to UDP and TCP port 53 in every NetworkPolicy, since a "deny all" policy that forgets DNS looks like a total outage. Set dnsPolicy: ClusterFirstWithHostNet on every hostNetwork pod, and publishNotReadyAddresses: true on headless Services backing clustered software, or bootstrap deadlocks.

Interview Questions

Beginner: How does one pod find another service in Kubernetes?

By DNS name, served by CoreDNS. Every Service gets a record under <service>.<namespace>.svc.cluster.local.

same namespace:      web
another namespace:   web.shop
fully qualified:     web.shop.svc.cluster.local.
Service typeDNS returns
ClusterIPOne virtual IP
HeadlessEvery ready pod IP
StatefulSet poddb-0.db-headless.ns.svc.cluster.local
Named port (SRV)Port number plus target names

Why names rather than IPs: pod IPs change on every restart and rescheduling, and the ClusterIP is stable for the life of the Service. The DNS name is the only durable handle — pod IPs are ephemeral.

Worth adding: resolution is the only function of a headless Service. It has no VIP and installs no kube-proxy rules, so its entire behaviour lives in CoreDNS.

Beginner: Why can't a pod resolve web from a different namespace?

Because the search path is namespace-specific. A pod's /etc/resolv.conf lists its own namespace first:

search shop.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

  from namespace "shop":   "web" → web.shop.svc.cluster.local ✅
  from namespace "admin":  "web" → web.admin.svc.cluster.local → NXDOMAIN
                                 → web.svc.cluster.local       → NXDOMAIN
                                 → web.cluster.local           → NXDOMAIN

Use web.shop — two dots, still under ndots:5, so the search path appends svc.cluster.local and it resolves. Or the full web.shop.svc.cluster.local. with a trailing dot, which skips the search path entirely and is the fastest form.

The related gotcha: a Service is namespaced, but its DNS record is visible cluster-wide. Namespaces are not a network boundary — restricting who may reach a Service requires NetworkPolicies, not the fact that a name is inconvenient to type.

Mid: Explain ndots:5 and why it matters for performance.

A name with fewer than five dots is tried against every search domain before being tried as written. Kubernetes sets 5 so that short in-cluster names work; the cost falls on external names.

resolving "api.stripe.com" (2 dots):
  ① api.stripe.com.shop.svc.cluster.local   NXDOMAIN
  ② api.stripe.com.svc.cluster.local        NXDOMAIN
  ③ api.stripe.com.cluster.local            NXDOMAIN
  ④ api.stripe.com.eu-west-1.compute.internal  NXDOMAIN
  ⑤ api.stripe.com                          ✅
  × 2 for parallel A and AAAA               = 10 queries

Measured: 48 ms and ten queries for the bare name, versus 7 ms and two with a trailing dot. A service making 1,000 external calls a second generates 10,000 DNS QPS, 8,000 of them guaranteed NXDOMAIN.

FixCost
Trailing dot on external hostnamesEvery config and library must do it
dnsConfig with ndots: 2Bare same-namespace names stop working; web.shop still resolves
NodeLocal DNSCacheMakes the queries cheap rather than removing them

The systemic symptom is a latency floor on all outbound calls plus a CoreDNS scaling problem, and the NXDOMAIN ratio on CoreDNS metrics is the clearest evidence.

Mid: Some requests take exactly 5 seconds. What is happening?

A conntrack race on parallel UDP DNS queries. The resolver sends the A and AAAA queries simultaneously from the same source port to the same destination; both packets try to create a conntrack entry for the same tuple, one is dropped as a duplicate, and the resolver waits out its 5-second timeout before retrying.

$ for i in $(seq 200); do /usr/bin/time -f %e getent hosts web; done 2>&1 | sort -n | tail -2
5.003
5.004                            ← exactly five seconds, twice in 200 lookups

The fingerprint is the exactness. Latency histograms with a hard spike at 5.000 s — never 4.2, never 6.1 — are this, not a slow database. The total request time is 5 s plus normal service time, because the delay happens before the connection is attempted.

FixEffect
NodeLocal DNSCacheNode-local agent, TCP upstream — removes the race properly
single-request-reopenSecond query uses a new source port
use-vcDNS over TCP; no UDP race
timeout:1 attempts:3Reduces the damage, does not fix the cause

Note it is not glibc-specific: musl (Alpine) also queries in parallel, so switching base image does not help. Fixing ndots reduces exposure simply by making far fewer queries.

Senior: DNS is failing intermittently on a large cluster. Walk through your investigation and remediation.

Establish whether it is capacity, correctness or connectivity — the three have different signatures.

① CAPACITY
$ kubectl -n kube-system top pods -l k8s-app=kube-dns
coredns-x8k2p   980m   72Mi           ← CPU-saturated at ~1 core
   coredns_dns_requests_total rate → 42,000 qps on 2 replicas
   coredns_dns_responses_total{rcode="NXDOMAIN"} → 78% of all responses

② CORRECTNESS  — that 78% is the actual finding
   ndots:5 × external calls = 8 guaranteed NXDOMAIN per real lookup

③ CONNECTIVITY
$ kubectl -n kube-system get endpointslices -l kubernetes.io/service-name=kube-dns
   any NetworkPolicy without an egress rule for port 53 breaks DNS for a namespace

Remediation in order of impact:

  • Fix ndots first — it removes roughly 80% of the load rather than serving it faster. Two lines of pod spec, no new components.
  • Deploy NodeLocal DNSCache. Cache hits never leave the node, and its TCP upstream eliminates the 5-second race. Measured on a busy cluster: 42,000 → 5,100 QPS reaching CoreDNS.
  • Autoscale CoreDNS proportionally to nodes/cores rather than pinning two replicas, and spread them across zones with a PDB — it is a Deployment and deserves the same availability engineering as anything else.
  • Keep the cache TTL short (~30 s): long TTLs trade endpoint-change propagation for a saving that node-local caching already provides.

What I would monitor afterwards: NXDOMAIN ratio (the search-path canary), CoreDNS p99 latency, cache hit rate at the node agent, and a synthetic probe resolving both a cluster name and an external name from a normal pod — because DNS failure presents as "everything is broken" and needs its own unambiguous signal.

The design point worth stating: DNS is a hard dependency of every request path, but it is deployed as an ordinary two-replica Deployment by default. Treating it as infrastructure that cannot fail is precisely why these incidents are so confusing when it does.

Senior: A clustered database StatefulSet never forms a quorum on first deploy. Diagnose.

A bootstrap deadlock caused by readiness and peer discovery depending on each other. Each member is unready until it finds peers; DNS publishes only ready addresses; so no member ever discovers anyone.

$ kubectl exec db-0 -- dig +short db-headless.shop.svc.cluster.local
                                   ← empty: no member is Ready yet
$ kubectl logs db-0 | tail -2
waiting for peers... found 0 members
waiting for peers... found 0 members

apiVersion: v1
kind: Service
metadata: { name: db-headless }
spec:
  clusterIP: None
  publishNotReadyAddresses: true     ← breaks the cycle
  selector: { app: db }
$ kubectl exec db-0 -- dig +short db-headless.shop.svc.cluster.local
10.244.1.7
10.244.2.4
10.244.3.9                          ← all three visible; quorum forms

The other requirements for per-pod DNS are easy to get wrong together: the StatefulSet must set serviceName to the headless Service, or no db-0.db-headless... records exist at all; and the pods must be configured with their stable names rather than IPs, since IPs change on every reschedule while the ordinal names do not.

The design caution: publishNotReadyAddresses means clients using this Service may receive addresses of pods that are not serving. That is correct for peer discovery and wrong for client traffic — so clustered databases normally get two Services: a headless one with not-ready addresses published for the members to find each other, and a regular ClusterIP Service with normal readiness gating for applications to connect to.

🎯 Key Takeaways

  • Names follow <service>.<namespace>.svc.cluster.local; ClusterIP Services return one VIP, headless Services return every ready pod IP.
  • A headless Service with no ready endpoints returns NXDOMAIN, while a ClusterIP Service still resolves and simply routes nowhere — a useful diagnostic difference.
  • DNS is the entire feature of a headless Service: no VIP, no kube-proxy rules.
  • ndots:5 makes one external lookup cost ten queries — eight guaranteed NXDOMAIN — measured at 48 ms versus 7 ms with a trailing dot.
  • Fix it with dnsConfig ndots: 2 or FQDNs; the trade is that bare same-namespace names stop resolving while web.shop still works.
  • A service making 1,000 external calls per second generates 10,000 DNS QPS with the default — the most common cause of a mysterious outbound latency floor.
  • Exactly 5.000-second latencies are a conntrack race on parallel A/AAAA UDP queries, not a slow database — measured 3 occurrences in 400 lookups.
  • The race affects musl as well as glibc; single-request-reopen or use-vc mitigate it, and NodeLocal DNSCache fixes it properly.
  • NodeLocal DNSCache serves hits without leaving the node and uses TCP upstream — measured 42,000 → 5,100 QPS reaching CoreDNS, and sub-millisecond p50.
  • Fix ndots before scaling CoreDNS: it removes ~80% of the load rather than serving it faster.
  • CoreDNS is an ordinary two-replica Deployment by default — it needs autoscaling, spread, a PDB and monitoring like anything else.
  • Alert on the NXDOMAIN ratio: it is the clearest signal of a search-path problem.
  • An egress NetworkPolicy that forgets UDP and TCP port 53 breaks everything, and presents as total application failure with no mention of DNS.
  • The distinguishing test is that connecting to a pod IP directly still works while name resolution does not.
  • hostNetwork: true silently switches to the node's resolver — cluster names fail while external names keep working, and the pod still reports dnsPolicy: ClusterFirst.
  • Always set dnsPolicy: ClusterFirstWithHostNet on host-network pods.
  • StatefulSets need serviceName pointing at a headless Service, which is what creates db-0.db-peers... records — stable names over changing IPs, verified across a pod deletion.
  • publishNotReadyAddresses: true breaks the bootstrap deadlock where readiness needs peers and peer discovery needs readiness — demonstrated as three pods stuck at 0/1 forever.
  • Clustered databases therefore want two Services: a headless one publishing not-ready addresses for members, and a normal ClusterIP with readiness gating for clients.
  • Triage by rcode: NOERROR means look elsewhere, NXDOMAIN means the name or namespace, SERVFAIL means CoreDNS upstream, and no response means connectivity or policy.
