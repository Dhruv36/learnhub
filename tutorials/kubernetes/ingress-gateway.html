Ingress, Gateway API & Load Balancers Networking & Traffic

What you'll master: the fact that trips up everyone on day one — an Ingress object does nothing at all without a controller, and the controller is itself just a Deployment behind a LoadBalancer Service; why one ingress replaces N cloud load balancers, with the bill arithmetic; what layer 7 buys you that a Service cannot provide — per-request balancing, which fixes the gRPC pinning problem from Services; pathType semantics and the /foo versus /foobar trap; the annotation sprawl that made Ingress unextendable and led to the Gateway API, with its role-separated GatewayClass/Gateway/HTTPRoute model, built-in traffic splitting and ReferenceGrant for cross-namespace routing; TLS termination, passthrough and the default-certificate trap; and how to tell a 404 from a 502 from a 504 — each of which points at a different layer. Prerequisites: Services & Endpoints, Cluster DNS.

Part 1 — An Ingress Is Data, Not a Proxy

Creating an Ingress object routes nothing. It is a routing table waiting for a program to read it. The program is an ingress controller — ingress-nginx, Traefik, HAProxy, Envoy Gateway, or a cloud controller — and it is an ordinary Deployment.

    Ingress object (routing rules)          ← what you write
            │  watched by
            ▼
    ingress controller Deployment           ← an ordinary workload, in a namespace
            │  which configures
            ▼
    its own proxy process (nginx/Envoy)     ← the thing packets actually traverse
            │  exposed by
            ▼
    Service type: LoadBalancer              ← one cloud load balancer for EVERYTHING
            │
            ▼
    cloud LB → node → ingress pod → (L7 routing) → your Service → your pod

$ kubectl apply -f ingress.yaml
ingress.networking.k8s.io/shop created
$ kubectl get ingress shop
NAME   CLASS    HOSTS         ADDRESS   PORTS   AGE
shop   <none>   shop.example             80      3m
                                ↑ no ADDRESS, ever: nothing is watching this object

$ kubectl get ingressclass
No resources found                    ← there is no controller installed

$ helm install ingress-nginx ingress-nginx/ingress-nginx
$ kubectl get ingress shop
NAME   CLASS   HOSTS         ADDRESS        PORTS   AGE
shop   nginx   shop.example  203.0.113.40   80      6m
                                ↑ the controller adopted it and published its own LB address
🔑 ingressClassName is what assigns ownership, and omitting it is the most common cause of an Ingress that silently does nothing. With several controllers installed — an internal one and an external one, say — an Ingress with no class is picked up by whichever IngressClass is annotated as default, or by none at all. Always set it explicitly; the failure mode is total silence, not an error.

Part 3 — pathType, and the /foobar Trap

spec:
  ingressClassName: nginx
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix                 ← element-wise prefix, NOT string prefix
        backend: { service: { name: api, port: { number: 80 } } }
      - path: /
        pathType: Prefix
        backend: { service: { name: web, port: { number: 80 } } }
pathTypeMatching/api matchesDoes NOT match
ExactThe whole path, exactly/api/api/, /api/v1
PrefixPath element by element/api, /api/, /api/v1/apifoo
ImplementationSpecificWhatever the controller does — often regexController-dependentUnportable
$ curl -s -o /dev/null -w '%{http_code} ' https://shop.example.com/api      # → api
200
$ curl -s -o /dev/null -w '%{http_code} ' https://shop.example.com/api/v1   # → api
200
$ curl -s -o /dev/null -w '%{http_code}\n' https://shop.example.com/apifoo  # → web!
200
   Prefix splits on "/", so "/api" does NOT match "/apifoo" — it falls through to "/".
   With a naive string prefix it would have matched, which is the confusion.

Two more routing subtleties that produce bafflement in production. Longest match wins regardless of rule order, so listing / first is harmless. And path rewriting is not part of the Ingress API — every controller does it with its own annotation:

  ingress-nginx:  nginx.ingress.kubernetes.io/rewrite-target: /$2
                  path: /api(/|$)(.*)
  Traefik:        a middleware CRD
  HAProxy:        haproxy.org/path-rewrite
  ALB:            alb.ingress.kubernetes.io/actions.*
     → four incompatible mechanisms for one universal need. This is Part 4.

Part 4 — Annotation Sprawl and the Gateway API

The Ingress spec covers host, path and TLS. Everything else — rewrites, timeouts, body size, CORS, auth, canaries, gRPC, websockets — is vendor annotations. A production Ingress becomes controller-specific configuration wearing a portable resource's clothing:

metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "300"
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/backend-protocol: "GRPC"
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"
    cert-manager.io/cluster-issuer: letsencrypt-prod
   → none of this is portable, none is validated by the API server, and a typo
     is silently ignored
Ingress limitationGateway API answer
Behaviour lives in unvalidated annotationsTyped fields, validated by the API server
One object mixes infra and app concernsSplit across three roles
No traffic splittingweight on each backendRef
No header/method matchingFirst-class match rules
Cross-namespace routing unsafeReferenceGrant — explicit consent
HTTP only in practiceHTTPRoute, GRPCRoute, TCPRoute, TLSRoute
   ROLE                        OBJECT           owns
   ────────────────────────────────────────────────────────────────────────
   infrastructure provider     GatewayClass     which implementation exists
   cluster operator            Gateway          listeners, ports, TLS certs,
                                                which namespaces may attach
   application developer       HTTPRoute        paths, headers, backends, weights

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: prod, namespace: infra }
spec:
  gatewayClassName: envoy
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    tls: { certificateRefs: [{ name: wildcard-tls }] }
    allowedRoutes:
      namespaces: { from: Selector, selector: { matchLabels: { gateway-access: "true" } } }
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: shop, namespace: shop }
spec:
  parentRefs: [{ name: prod, namespace: infra }]
  hostnames: ["shop.example.com"]
  rules:
  - matches:
    - path: { type: PathPrefix, value: /api }
      headers: [{ name: x-canary, value: "true" }]     ← header matching, typed
    backendRefs: [{ name: api-canary, port: 80 }]
  - matches: [{ path: { type: PathPrefix, value: /api } }]
    backendRefs:                                        ← weighted split, no annotations
    - { name: api-stable, port: 80, weight: 90 }
    - { name: api-canary, port: 80, weight: 10 }
    filters:
    - type: RequestHeaderModifier
      requestHeaderModifier: { add: [{ name: x-env, value: prod }] }
🔑 The role split is the point, not the syntax. With Ingress, a developer who needs a timeout change edits an object that also carries the TLS configuration and the load balancer's identity. With Gateway API, the platform team owns the Gateway (listeners, certificates, which namespaces may attach) and application teams own HTTPRoutes in their own namespaces — so RBAC finally matches the actual ownership boundary. ReferenceGrant extends the same consent model to cross-namespace backend references.

     the controller hot-reloads the certificate with no restart

⚠️ The default-certificate trap. A request whose SNI matches no configured host is served the controller's default certificate — usually a self-signed Kubernetes Ingress Controller Fake Certificate. Browsers show a scary warning and API clients fail verification, and the cause is almost always a hostname mismatch or a missing TLS block, not a broken certificate. openssl s_client -servername tells you in one command which certificate you are actually being served.

Part 6 — Operating It, and Reading the Status Code

The ingress controller is now on the critical path of every external request, so it needs the availability engineering of any tier-1 service: several replicas, a PodDisruptionBudget, spread across zones, generous resources, and its own monitoring. It also ships with defaults that will surprise you:

proxy-connect-timeout5 s504 when backends are slow to accept

❌ Forty Services of type LoadBalancer, an Ingress with no ingressClassName, production behaviour encoded in a dozen nginx annotations, a single-replica controller, and TLS certificates renewed by hand. The cloud bill carries $800/month of load balancers and forty DNS records that drift out of sync with reality. A new Ingress is created and never gets an address, because no class was set and the default IngressClass annotation was removed months ago — the object simply sits there, valid and inert, with no event to explain it. Uploads larger than a megabyte fail with a 413 that nobody can reproduce locally, because the 1 MB body-size default only exists in the cluster. The controller runs one replica with no PodDisruptionBudget, so a node drain takes every external request down at once. And when the wildcard certificate expires on a Saturday, every host starts serving the controller's fake self-signed default certificate, which looks like a catastrophic misconfiguration rather than an expiry.

✅ One ingress with host routing, an explicit class, typed configuration where possible, and the controller treated as a tier-1 service. Consolidate onto a single load balancer with host- and path-based routing — the bill difference is roughly $800 versus $20 a month, and certificates and DNS collapse to one place. Always set ingressClassName explicitly, since an unclaimed Ingress fails silently rather than loudly. Know the defaults that bite — proxy-body-size: 1m and a 60-second read timeout — and set them deliberately rather than discovering them in production. Run the controller with multiple replicas, a PDB, topology spread and real resource requests, because it is now on the path of every external request. Automate certificates with cert-manager so expiry is not an operational event, and alert on days-to-expiry as well. And where the annotation list is getting long or several teams share one entry point, move to the Gateway API: typed and validated fields instead of unchecked strings, weighted splits and header matching built in, and a role split that lets the platform team own listeners and certificates while application teams own their own routes.

Interview Questions

Beginner: What is an Ingress and why is it not enough on its own?

An Ingress is a routing table — an API object describing host and path rules. It does nothing until an ingress controller reads it.

$ kubectl get ingress shop
NAME   CLASS    HOSTS         ADDRESS   PORTS
shop   <none>   shop.example             80        ← no ADDRESS: nothing is watching

The controller (ingress-nginx, Traefik, Envoy Gateway, a cloud controller) is an ordinary Deployment. It watches Ingress objects, configures its own proxy, and is itself exposed by a Service type: LoadBalancer — so one cloud load balancer fronts every application.

LayerWhat it is
Ingress objectRules, as data
Ingress controllerA Deployment that reads them
Its proxyWhat packets traverse
LoadBalancer ServiceHow the outside world reaches it

The most common day-one failure: omitting ingressClassName. The object is valid, nothing claims it, no event is emitted, and it never gets an address.

Beginner: When would you use an Ingress instead of Service type: LoadBalancer?

Almost always for HTTP — the cost and capability differences are both large.

LoadBalancer per appOne ingress
40 services40 LBs ≈ $800/month1 LB ≈ $20/month
RoutingPort onlyHost, path, header, method
TLSPer load balancerCentralised
BalancingPer connectionPer request

Use LoadBalancer directly when the protocol is not HTTP (a database, a game server, raw TCP/UDP), when you need the lowest possible latency and cannot accept the proxy hop, or when the client requires the real source IP at L4 and TLS passthrough is not sufficient.

The capability worth calling out is per-request balancing: a Service balances per connection, so a gRPC client pins all its traffic to one pod. An L7 ingress balances each request, which is the standard fix for that problem — see Services.

Mid: Explain pathType, and a routing bug it causes.

Three types, and Prefix matches path elements, not string prefixes.

Type/api matchesDoes not match
Exact/api only/api/, /api/v1
Prefix/api, /api/, /api/v1/apifoo
ImplementationSpecificController-defined (often regex)Unportable

The classic bug is the opposite of what people fear: /apifoo falls through to the / rule and hits the wrong service, because element-wise matching does not treat api as a prefix of apifoo.

Two more behaviours worth knowing: longest match wins regardless of the order rules appear in, so a broad / rule cannot shadow a specific one; and rewriting is not in the API — each controller invents its own annotation, which is a concrete example of the sprawl that motivated the Gateway API.

Mid: Requests through the ingress return 502. How do you find the cause?

The status code tells you which layer failed — that is most of the diagnosis.

CodeMeansFirst check
Connection refused/DNSNever reached the ingressDNS record, cloud LB
404 (controller's page)No rule matchedHost header, pathType, class
503Service has no endpointskubectl get endpointslices
502Backend reached, connection failedPort, protocol, app crash
504Backend too slowproxy-read-timeout, app latency

502 specifically means the proxy connected (or tried to) and got a refusal, a reset, or a malformed response. In order of likelihood: the Service's targetPort does not match what the container listens on; the backend speaks HTTPS or gRPC while the ingress is speaking plain HTTP (needs backend-protocol); the pod crashed mid-request; or the response headers exceed the proxy's buffer.

$ kubectl logs -n ingress-nginx deploy/ingress-nginx-controller | tail -2
2026/08/19 12:31:02 [error] connect() failed (111: Connection refused) while
connecting to upstream, upstream: "http://10.244.1.7:8080/"
                                                     ↑ the exact endpoint and port

The distinction that saves the most time is 502 versus 503: 503 means the endpoint list was empty (a Service problem — selector or readiness), while 502 means an endpoint existed and did not answer correctly (an application or port problem).

Senior: When would you move from Ingress to the Gateway API, and what does the migration involve?

When the annotations stop being incidental — or when more than one team shares an entry point. Those are the two thresholds where Ingress stops modelling reality.

SignalWhy Ingress is failing
A dozen vendor annotations per objectUnvalidated strings; typos ignored silently
Several teams editing one IngressNo ownership boundary — TLS and routes in one object
Canary deploys wantedTraffic splitting is not in the spec
Header or method routingNot expressible
Cross-namespace backendsNo consent model
Portability between controllersThe annotations are the configuration

What actually changes: configuration becomes typed and validated, so a mistake is rejected at apply time rather than ignored; weights and header matches are first-class; and the object model splits along the real ownership boundary — the platform team owns the Gateway (listeners, ports, certificates, which namespaces may attach), application teams own HTTPRoutes in their own namespaces, and ReferenceGrant makes cross-namespace references explicit consent rather than an implicit hole.

How I would migrate: run both simultaneously. Install a Gateway API implementation alongside the existing controller, move one low-risk service by creating an HTTPRoute and shifting DNS, verify, then proceed service by service. Both can share the same load balancer address or use a second one during the transition; there is no big-bang step, and that is the main advantage over replacing an ingress controller in place.

What I would not do: migrate for its own sake. A single team with three annotations and one hostname gains nothing but a newer API and a smaller pool of people who have operated it. The justification has to be the ownership split or a capability you genuinely need.

Senior: Design external traffic ingress for a multi-tenant production cluster.

Separate entry points by trust and blast radius, and treat each one as a tier-1 service.

Entry pointExposureWhy separate
Public ingressInternet, WAF in frontHostile traffic; strictest limits
Internal ingressVPC only, private LBAdmin UIs must never be internet-reachable
Partner/API ingressInternet + mTLSDifferent auth model and rate limits

Availability engineering, because it is now on every request path: at least three replicas with a PodDisruptionBudget and topology spread across zones; generous requests and no CPU limit (throttling a proxy is uniquely damaging — see Requests & Limits); readiness that reflects config-reload health; and a preStop drain so rolling the controller does not drop connections.

Security defaults I would enforce: TLS 1.2 minimum with a modern cipher list; HSTS; cert-manager with alerting on days-to-expiry; X-Forwarded-For trusted only from the load balancer's ranges, since clients can forge it; body-size and timeout limits set explicitly rather than inherited; and rate limiting at the edge so one tenant cannot exhaust shared capacity.

Multi-tenancy specifics: each tenant's routes live in their own namespace, and with Gateway API the Gateway's allowedRoutes selector controls who may attach — RBAC that matches the ownership boundary instead of a shared object everyone can edit. I would also enforce, via policy, that a tenant cannot claim a hostname belonging to another tenant, which Ingress cannot express at all and which is a real attack in shared clusters.

Monitoring that reflects the layering: status codes split by ingress-generated versus backend-generated, per-host and per-route latency, certificate expiry, controller reload failures (a failed reload means the running config silently diverges from the objects), and upstream connection errors — which distinguish "no endpoints" from "endpoints that refuse".

6 (hard): Build a status-code triage runbook for the whole path.
Solution 
$ cat > tools/ingress-triage.sh <<'SH'
#!/usr/bin/env bash
# Usage: tools/ingress-triage.sh HOST PATH [INGRESS_IP]   — read-only.
set -uo pipefail
HOST=${1:?host}; P=${2:-/}; IP=${3:-$(kubectl -n ingress-nginx get svc ingress-nginx-controller \
     -o jsonpath='{.status.loadBalancer.ingress[0].ip}')}
say() { printf '%-24s %s\n' "$1" "$2"; }

code=$(curl -s -o /tmp/body -w '%{http_code}' -m 10 -H "Host: $HOST" "http://$IP$P")
say "status" "$code"
say "served by" "$(grep -qi 'nginx\|openresty' /tmp/body && echo 'THE INGRESS (error page)' || echo 'the backend')"

ING=$(kubectl get ingress -A -o json | jq -r --arg h "$HOST" \
      '.items[] | select(.spec.rules[]?.host == $h) | "\(.metadata.namespace)/\(.metadata.name)"' | head -1)
say "matching ingress" "${ING:-NONE — no Ingress claims this host}"
[ -z "$ING" ] && exit 0
NS=${ING%/*}; NAME=${ING#*/}
say "class"    "$(kubectl -n "$NS" get ing "$NAME" -o jsonpath='{.spec.ingressClassName}')"
say "address"  "$(kubectl -n "$NS" get ing "$NAME" -o jsonpath='{.status.loadBalancer.ingress[0].ip}')"

for svc in $(kubectl -n "$NS" get ing "$NAME" -o jsonpath='{.spec.rules[*].http.paths[*].backend.service.name}'); do
  eps=$(kubectl -n "$NS" get endpointslices -l kubernetes.io/service-name="$svc" \
        -o jsonpath='{range .items[*].endpoints[*]}{.addresses[0]}={.conditions.ready} {end}')
  say "backend $svc" "${eps:-NO ENDPOINTS}"
  say "  targetPort" "$(kubectl -n "$NS" get svc "$svc" -o jsonpath='{.spec.ports[0].targetPort}')"
done

echo; echo "recent controller errors:"
kubectl -n ingress-nginx logs deploy/ingress-nginx-controller --since=2m 2>/dev/null \
  | grep -E '\[error\]|\[warn\]' | tail -3
SH

🎯 Key Takeaways

  • An Ingress object is data, not a proxy — with no controller it never gets an ADDRESS and emits no events at all.
  • The controller is an ordinary Deployment fronted by one LoadBalancer Service that serves every Ingress in the cluster.
  • Omitting ingressClassName is the most common silent failure: unclaimed objects sit valid and inert, adopted only if some IngressClass is annotated default.
  • One ingress replaces N load balancers: roughly $800/month versus $20 for 40 services, plus one DNS record and one certificate story.
  • L7 buys host/path/header routing, TLS termination, retries, real client IP — and per-request balancing, which is the standard fix for gRPC connection pinning.
  • pathType: Prefix matches path elements, not string prefixes: /api matches /api/v1 but not /apifoo, which falls through to /.
  • Longest match wins regardless of rule order — verified identical results with the rules reversed.
  • Path rewriting is not in the Ingress API; every controller invents its own annotation, which is the sprawl in miniature.
  • Annotations are unvalidated strings — a typo'd proxy-body-sizes and a weight of "ninety" were both accepted and silently ignored.
  • The Gateway API replaces them with typed, validated fields: an invalid weight was rejected at apply time.
  • Its real contribution is the role split: GatewayClass (provider), Gateway (platform team — listeners, TLS, allowedRoutes), HTTPRoute (app team), with ReferenceGrant for cross-namespace consent.
  • Weighted splits and header matching are first-class in HTTPRoute; with Ingress they need a second shadow object and vendor annotations.
  • Migration is incremental — run both, move one service, shift DNS — which is its main advantage over replacing a controller in place.
  • proxy-body-size defaults to 1 MB: uploads fail with 413 in the cluster and work perfectly in local development.
  • proxy-read-timeout defaults to 60 s — measured a 504 at exactly 60.18 s — and breaks SSE and long-polling.
  • An SNI matching no configured host is served the controller's fake self-signed certificate, which looks like a compromise and is really a hostname mismatch.
  • openssl s_client -servername is the one command that shows which certificate you are actually being served.
  • The controller is on every external request path: multiple replicas, a PDB, zone spread, no CPU limit, and cert-manager with expiry alerting.
  • 503 means zero endpoints; 502 means endpoints exist and refused — a Service problem versus a port/protocol/app problem.
  • Distinguishing the controller's error page from the application's response halves the search space before any deeper investigation.
