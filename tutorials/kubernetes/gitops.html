GitOps with Argo CD & Flux Operating Clusters

What you'll master: what GitOps actually changes — a controller inside the cluster continuously reconciles against Git, so the deploy stops being an event and becomes a loop; the pull model and why it removes cluster credentials from CI entirely; Argo CD's Application object, and the distinction between Sync status and Health status that confuses everyone on day one; selfHeal and prune, including the pruning accident that deletes production; ignoreDifferences, without which an HPA and your Git repo fight over replicas for ever; sync waves for ordering; Flux's equivalent model; the secrets problem GitOps creates and the three real answers; and the operational realities — bootstrapping, self-management, and the repository becoming a single point of failure. Prerequisites: Objects & Apply, Helm, ConfigMaps & Secrets.

Part 1 — Push Versus Pull

  PUSH (traditional CI/CD)
    CI runner ──(kubectl apply, holding cluster credentials)──► cluster
      · CI needs a kubeconfig for every environment
      · the deploy is an EVENT; drift afterwards is invisible
      · the cluster must be reachable from CI

  PULL (GitOps)
    CI ──► builds the image, commits the manifest ──► Git
                                                       ▲
    cluster ──(a controller polls or is webhooked)─────┘
      · NO cluster credentials in CI
      · the deploy is a LOOP: drift is corrected continuously
      · the cluster reaches out; it need not be reachable
PrincipleConsequence
DeclarativeThe whole system is described in files
Versioned and immutableGit history is the audit log; git revert is the rollback
Pulled automaticallyNo credentials leave the cluster
Continuously reconciledManual changes are reverted, not merely detected
🔑 The fourth principle is the one that changes your operational life. kubectl apply and helm upgrade run when you run them; a GitOps controller runs every few minutes, for ever. That makes the cluster's state a function of the repository rather than the accumulated result of everyone's commands — and it means "I just fixed it with kubectl" now has a three-minute half-life.

Part 2 — The Argo CD Application

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shop
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/example/deploy.git
    targetRevision: main                  ← a branch, tag, or commit SHA
    path: apps/shop/overlays/prod
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true                         ← delete what Git no longer declares
      selfHeal: true                      ← revert manual cluster changes
      allowEmpty: false                   ← refuse to sync an empty manifest set
    syncOptions:
      - CreateNamespace=true
      - ServerSideApply=true
StatusMeansCommon cause when unexpected
SyncedThe cluster matches Git—
OutOfSyncLive state differs from GitOften expected — mutating webhooks, defaulted fields, an HPA
HealthyResources report ready—
ProgressingA rollout is under wayNormal for a minute
DegradedResources are failingThe actual problem
MissingDeclared in Git, absent from the clusterNot yet synced, or a failed sync
⚠️ Sync and Health are independent, and confusing them wastes hours. An Application can be Synced and Degraded — Git was applied faithfully and the pods are crash-looping. It can equally be OutOfSync and Healthy, which is the normal state when a mutating webhook injects a sidecar or an HPA owns replicas. Alert on Degraded; treat OutOfSync as information.

Part 3 — Drift, selfHeal and What You Must Ignore

$ kubectl -n shop scale deploy api --replicas=10
deployment.apps/api scaled
$ sleep 20; kubectl -n shop get deploy api -o jsonpath='{.spec.replicas}{"\n"}'
3                                       ← selfHeal reverted it, within seconds
$ argocd app history shop | tail -1
5   2026-08-19 12:31:02   main (9f21c0e)   ← no new revision: it corrected to the same commit

That is the desired behaviour for hand edits. It is a disaster when another controller legitimately owns a field — most often an HPA:

  Git says          spec.replicas: 3
  the HPA says      spec.replicas: 12       (from real load)

  → Argo syncs to 3, the HPA scales to 12, Argo syncs to 3 ...
  → capacity oscillates, and the Deployment churns

spec:
  ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers: ["/spec/replicas"]        ← let the HPA own it
  - group: ""
    kind: Service
    jsonPointers: ["/spec/clusterIP"]       ← assigned by the API server
  - group: admissionregistration.k8s.io
    kind: ValidatingWebhookConfiguration
    jqPathExpressions: [".webhooks[].clientConfig.caBundle"]   ← injected by cert-manager

The better fix for the HPA case is the same one as in field ownership: remove replicas from the manifest entirely, so nothing in Git claims it. An ignore rule silences the symptom; deleting the field removes the contention.

FieldOwned byHandling
spec.replicas with an HPAThe HPAOmit from Git, or ignore
clusterIPAPI serverIgnore
caBundlecert-managerIgnore
Injected sidecarsThe mesh webhookIgnore, or use ServerSideApply
Defaulted fieldsAPI serverServerSideApply=true handles most
metadata.annotations from operatorsVariousIgnore by path

Part 4 — Pruning, Waves and App-of-Apps

  prune: true    → anything Argo previously created that Git no longer declares
                   is DELETED

  the accident:
    someone changes `path:` to a directory that does not exist, or a Kustomize
    build fails and produces zero manifests
    → Argo sees "Git declares nothing" → prunes EVERYTHING

  the guards:
    allowEmpty: false                              ← refuse to sync an empty result
    annotation: argocd.argoproj.io/sync-options: Prune=false    ← per resource
    PVCs and namespaces excluded from pruning by policy

metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-1"      ← lower waves run FIRST
    argocd.argoproj.io/hook: PreSync        ← migrations, before anything else
    argocd.argoproj.io/hook-delete-policy: HookSucceeded

  typical ordering:
    wave -2  namespaces, CRDs
    wave -1  secrets, configmaps, RBAC
    wave  0  databases, StatefulSets            (the default)
    wave  1  applications
    wave  2  ingresses, monitoring

For managing many applications, the app-of-apps pattern makes Argo manage its own Applications, and ApplicationSet generates them from a template:

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: { name: all-services, namespace: argocd }
spec:
  generators:
  - git:
      repoURL: https://github.com/example/deploy.git
      revision: main
      directories: [{ path: "apps/*/overlays/prod" }]     ← one App per directory
  template:
    metadata: { name: '{{path[1]}}-prod' }
    spec:
      project: prod
      source: { repoURL: ..., targetRevision: main, path: '{{path}}' }
      destination: { server: https://kubernetes.default.svc, namespace: '{{path[1]}}' }
      syncPolicy: { automated: { prune: true, selfHeal: true } }

The secrets problem GitOps creates

Everything must be in Git — but credentials must not be. The three real answers, in order of preference:

ApproachWhat is in GitRotation
External Secrets OperatorA reference to Vault or a cloud managerAutomatic
SOPS (with age or KMS)The value, encryptedManual, but auditable
Sealed SecretsThe value, encrypted to the cluster's keyManual; cluster-specific
Plain Secrets in GitThe valueNever do this
Workload identityNothing — there is no secretn/a — the best option where it applies

Part 6 — Operational Realities

RealityConsequenceHandling
Git becomes a production dependencyA repo outage blocks all deploysMirror; the controller keeps last-known state and keeps reconciling
The controller manages itselfA bad commit can break the thing that would fix itBootstrap manifests kept applyable by hand
Reconcile interval is a latency floorA commit takes up to interval to applyWebhooks from the forge for instant sync
kubectl edit stops workingEmergency fixes are reverted in minutesA documented break-glass: disable auto-sync, fix, commit
Promotion between environmentsCopying YAML by hand driftsOverlays plus an image-tag bump commit
Rendered vs templatedReviewing templates hides real changesRender in CI and commit the output
BREAK-GLASS, documented in advance so nobody improvises during an incident:

  1. argocd app set shop --sync-policy none        (or: suspend the Flux Kustomization)
  2. kubectl edit / scale / patch — do the emergency fix
  3. commit the same change to Git
  4. argocd app set shop --sync-policy automated   (re-enable)

  Skipping step 3 means the controller silently reverts your fix minutes later,
  usually after the incident channel has gone quiet.

❌ Auto-sync with prune enabled across every application, no ignoreDifferences, plain Secrets committed to the repository, and no break-glass procedure. A refactor renames a directory, the Kustomize build produces zero manifests, and Argo faithfully concludes that Git declares nothing — pruning every workload in the namespace including the PersistentVolumeClaims. An HPA and the repo fight over replicas continuously, so the Deployment churns and capacity is wrong half the time, while a mutating webhook injects a sidecar that keeps every Application permanently OutOfSync — which trains everyone to ignore the status entirely, so the one genuinely degraded app goes unnoticed for a day. Base64 Secrets sit in the repository, meaning every clone, fork and CI cache contains production credentials. And during an incident someone fixes production with kubectl, the controller reverts it four minutes later, and the outage resumes after everyone has moved on.

✅ Guard pruning, ignore fields other controllers own, keep credentials as references, and rehearse the break-glass path. Set allowEmpty: false so a build producing no manifests can never be read as "delete everything", and annotate PVCs and namespaces with Prune=false — pruning is correct and must not be able to fire on a rendering accident. Remove replicas from any manifest whose Deployment is autoscaled rather than adding an ignore rule, and use ignoreDifferences for the fields other controllers genuinely own: clusterIP, caBundle, injected sidecars. Understand that Sync and Health are independent — alert on Degraded, treat OutOfSync as information, and fix the causes of permanent drift so the signal stays meaningful. Commit references to secrets, never values: an ExternalSecret pointing at a secret manager, or SOPS/Sealed Secrets where the value must live in the repo, and workload identity where the dependency supports it. Finally, write the break-glass procedure down — disable auto-sync, fix, commit, re-enable — because the failure mode of forgetting step three is an outage that reappears once the incident channel is quiet.

Interview Questions

Beginner: What is GitOps and how does it differ from a CI/CD pipeline that runs kubectl apply?

Git is the source of truth, and a controller inside the cluster continuously reconciles against it. The deploy stops being an event and becomes a loop.

Push (CI applies)Pull (GitOps)
Cluster credentialsIn CINone leave the cluster
Drift after deployInvisibleCorrected continuously
Network directionCI → clusterCluster → Git
RollbackRe-run an old pipelinegit revert
Audit trailPipeline logsGit history

The practical difference people feel first is that kubectl edit stops working — a manual change is reverted within the reconcile interval. That is the point, and it is why a documented break-glass procedure matters.

The security benefit is underrated: no CI system holds a production kubeconfig, and the cluster does not need to be reachable from the internet.

Beginner: An Argo CD application shows Synced but Degraded. What does that mean?

Argo applied Git faithfully; the resulting workload is not healthy. The two statuses answer different questions.

CombinationMeaning
Synced + HealthyEverything is fine
Synced + DegradedGit was applied; the app is broken — bad image, crash loop, failing probes
OutOfSync + HealthyUsually normal — a webhook, an HPA, a defaulted field
OutOfSync + DegradedA sync failed and the app is unhealthy

So Synced is exactly as meaningful as kubectl apply returning 0 — it says the objects were stored, not that they work. This is the same distinction as apply versus rollout status.

Alert on Degraded, not on OutOfSync. If drift is permanent because of a webhook or an HPA, fix it with ignoreDifferences — otherwise everyone learns to ignore the status and the one real problem hides among them.

Mid: Your GitOps controller and your HPA are fighting over replica count. Fix it.

Two controllers own one field. Git says 3, the HPA writes 12, each corrects the other, and capacity oscillates indefinitely.

$ kubectl -n shop get deploy api -o jsonpath='{.spec.replicas}{"\n"}'; sleep 180
12
3                            ← Argo re-synced
$ argocd app get shop | grep -c OutOfSync
1                            ← and the app flaps between statuses
FixEffect
Remove replicas from the manifestNothing in Git claims it — best
ignoreDifferences on /spec/replicasArgo stops diffing it
Disable selfHealFixes the symptom; loses drift correction everywhere

Deleting the field is better than ignoring it, because an ignore rule silences a difference that still exists in your source of truth, and the next person to read the manifest sees a replica count that is not real.

The same class of clash covers clusterIP (assigned by the API server), caBundle (injected by cert-manager) and mesh sidecars. ServerSideApply=true resolves many of them properly, because field ownership is then tracked per field by the API server — see field ownership.

Mid: How do you handle secrets in GitOps?

Commit references, not values. Everything else is a compromise on that principle.

ApproachIn GitRotationNotes
External Secrets OperatorA referenceAutomaticNeeds Vault or a cloud manager
SOPS + KMS/ageEncrypted valueManualDiffable, auditable, key management needed
Sealed SecretsEncrypted valueManualTied to one cluster's key — awkward for DR
Workload identityNothingn/aBest where the dependency supports it

Why plain Secrets are never acceptable, even in a private repo: base64 is not encryption, and the value ends up in every clone, every fork, every CI cache and every backup of the forge. Deleting the commit does not retract it — the only remediation is rotation.

My default is ESO, because it also solves rotation: the secret manager rotates, the operator re-syncs, and Git never changes. The remaining question is whether the application re-reads its credential — most read it once at start-up, which quietly makes "automatic rotation" a restart-triggering event that has to be planned for.

Senior: Design a GitOps setup for many services across several environments.

One repository structure, generated Applications, and promotion by commit.

deploy/
  apps/
    shop/
      base/                     ← plain manifests or a chart
      overlays/{dev,staging,prod}/
    payments/...
  infrastructure/
    {ingress,cert-manager,monitoring}/
  clusters/
    prod/apps.yaml              ← ApplicationSet generating one App per overlay
DecisionChoiceReason
Repo layoutOne deploy repo, separate from app sourceAn image bump must not retrigger CI
EnvironmentsDirectories, not branchesBranch-per-env drifts and merges badly
App generationApplicationSet from directoriesNew service = a new directory
PromotionA commit changing the image tag in the next overlayAuditable, revertable
Renderinghelm template in CI, output committedPRs show real object diffs
SecretsExternalSecret referencesNo values in Git
OrderingSync waves: CRDs → RBAC/config → data → appsCRs before CRDs otherwise fail

Environments as directories rather than branches is the decision people most often get wrong. Branch-per-environment means promotion is a merge, which drags along every unrelated change and makes cherry-picking normal — whereas a directory promotion is a single, reviewable commit that changes one image tag.

The operational guards I would insist on: allowEmpty: false everywhere, Prune=false on PVCs and namespaces, a bootstrap manifest that can be applied by hand if the controller breaks itself, and a documented break-glass procedure. Also a mirror of the deploy repo, because Git is now a production dependency — though a controller that already has the manifests keeps reconciling during an outage; only new deploys stop.

Senior: What are GitOps's real downsides?

It is the right default, and it is not free. The honest list:

DownsideMitigation
Emergency changes are revertedA rehearsed break-glass procedure
Latency floor from the reconcile intervalForge webhooks for instant sync
Git is now a production dependencyMirrors; controllers keep last-known state
The controller can break itselfHand-applyable bootstrap manifests
Debugging gains a layer"Is it Git, the controller, or the workload?"
Permanent OutOfSync noiseIgnore rules — or people stop reading the status
Not everything is declarativeDatabase migrations, one-off jobs, manual failovers
Pruning can be catastrophicallowEmpty: false, Prune=false on stateful objects

The one that bites hardest culturally is the first. Every engineer has muscle memory for fixing production with kubectl, and under GitOps that fix has a three-minute half-life. If the break-glass path is not documented and practised, people either improvise or quietly disable auto-sync and never re-enable it — which leaves you with the costs of GitOps and none of the benefits.

The one that surprises operationally is that not everything fits the model. A schema migration, a failover, a cache flush — these are actions, not states, and forcing them into Git as Jobs with hooks produces a lot of complexity. It is fine to keep a small imperative surface, as long as it is explicit.

Where I would still choose it: anywhere with more than a couple of environments or more than a handful of engineers. The audit trail, the removal of cluster credentials from CI, and continuous drift correction are each worth the cost on their own.

✅ THE BREAK-GLASS PROCEDURE:
$ cat > tools/break-glass.sh <<'SH'
#!/usr/bin/env bash
# Suspend GitOps for one app so an emergency fix survives. ALWAYS pair with commit.
set -euo pipefail
APP=${1:?app}; REASON=${2:?reason}
argocd app set "$APP" --sync-policy none
kubectl -n argocd annotate app "$APP" --overwrite \
  break-glass/at="$(date -Iseconds)" \
  break-glass/by="${USER}" \
  break-glass/reason="$REASON"
echo "⚠️  auto-sync DISABLED for $APP"
echo "    1. make the fix with kubectl"
echo "    2. COMMIT THE SAME CHANGE TO GIT"
echo "    3. tools/break-glass-end.sh $APP"
SH
$ cat > tools/break-glass-end.sh <<'SH'
#!/usr/bin/env bash
set -euo pipefail
APP=${1:?app}
echo "checking Git matches the live cluster before re-enabling..."
if ! argocd app diff "$APP" --exit-code; then
  echo "❌ Git does NOT match the cluster — commit your fix first, or it will be reverted"
  exit 1
fi
argocd app set "$APP" --sync-policy automated --self-heal --auto-prune
kubectl -n argocd annotate app "$APP" break-glass/at- break-glass/by- break-glass/reason- || true
echo "✅ auto-sync re-enabled"
SH

🎯 Key Takeaways

  • GitOps makes deployment a loop, not an event: a controller in the cluster reconciles against Git continuously.
  • The pull model removes cluster credentials from CI entirely and means the cluster need not be reachable from outside.
  • Sync and Health are independent: Synced + Degraded means Git was applied faithfully and the app is broken — exactly like kubectl apply returning 0.
  • Alert on Degraded, not OutOfSync, and fix permanent drift, or people stop reading the status altogether.
  • selfHeal reverted a manual scale within seconds and created no new revision — it re-synced the same commit.
  • An HPA and Git both owning replicas oscillates for ever; removing the field beats an ignore rule, because an ignore rule leaves a false value in your source of truth.
  • ignoreDifferences is right for fields other controllers genuinely own — clusterIP, caBundle, injected sidecars — and ServerSideApply=true resolves many properly.
  • A missing path produces a safe ComparisonError; a path that renders zero resources prunes everything, PVCs included.
  • allowEmpty: false is not optional, and irreversible objects need Prune=false annotations.
  • A CI check that refuses a render producing fewer resources than expected catches the accident in the pull request.
  • Sync waves order CRDs → config → data → apps; PreSync hooks run before everything, and a failing one correctly blocks the entire deploy.
  • Without waves, a custom resource can be applied before its CRD exists — no matches for kind.
  • ApplicationSets generate one Application per directory, so adding a service is adding a directory.
  • Secrets: commit references, not values. ESO rotates with no Git commit at all; SOPS and Sealed Secrets keep encrypted values in the repo; plain Secrets are in every clone for ever.
  • Sealed Secrets are tied to one cluster's key, which makes disaster recovery awkward.
  • Git becomes a production dependency, the controller can break itself, and the reconcile interval is a latency floor — mitigated by mirrors, hand-applyable bootstrap manifests, and forge webhooks.
  • An emergency kubectl fix has a three-minute half-life — measured: the outage resumed after selfHeal reverted it, with the audit trail attributing the change to Argo.
  • The break-glass procedure is disable → fix → commit → re-enable; a gate that diffs Git against the cluster before re-enabling catches the forgotten commit.
  • Audit for applications left with auto-sync disabled — they silently stop deploying, and nobody notices for weeks.
  • Environments as directories, not branches: promotion becomes a single reviewable commit rather than a merge dragging unrelated changes with it.
