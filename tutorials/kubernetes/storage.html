Volumes, PVs, PVCs & StorageClasses Configuration & State

What you'll master: the volume taxonomy and which kinds survive what — emptyDir dies with the pod and can get your pod evicted for filling the node's disk; the PVC → StorageClass → PersistentVolume chain, and the reclaimPolicy: Delete default that destroys your data when a PVC is removed; volumeBindingMode, and why Immediate binding produces pods that can never be scheduled in a multi-zone cluster; the access mode almost everyone misreads — ReadWriteOnce means one node, not one pod, demonstrated with two pods sharing a volume; CSI attach limits, which cap pods per node far below what CPU and memory suggest; volume expansion, which is online and one-way; and the failure modes that matter at 3am — the multi-attach error, the six-minute detach timeout on a dead node, and why a snapshot is not a backup. Prerequisites: Pods, Scheduling, Docker: Storage.

- name: scratch
  emptyDir: { sizeLimit: 2Gi }         ← ALWAYS set this

                                                     MEMORY limit, not the disk
⚠️ An emptyDir with no sizeLimit can fill the node's disk and get pods evicted — including pods that had nothing to do with it. The kubelet's nodefs eviction threshold applies to the whole node, so one container writing an unbounded log or cache into scratch space triggers DiskPressure, which taints the node and evicts by QoS class. Setting sizeLimit turns a node-wide incident into one pod being evicted for exceeding its own limit.

hostPath deserves its own warning: it mounts a path from the node into the pod, so a pod that can mount / or /var/run/docker.sock effectively owns the node — the same escalation shown in Docker: Security. Restricting it is a core job of Pod Security admission.

🔑 The default reclaim policy on every managed cluster's default StorageClass is Delete. One kubectl delete pvc, one helm uninstall, one overzealous namespace cleanup, and the data is destroyed at the cloud provider — not merely unmounted. Create a Retain StorageClass for stateful workloads and make it the one your database charts reference. A Retain PV must then be manually cleared before it can bind again, which is the small price for not being one command away from data loss.

volumeBindingMode: the zone trap

Immediate (the old default)
  PVC created → PV provisioned NOW, in some zone → THEN the pod is scheduled
  → if the volume lands in eu-west-1a and the only free capacity is in 1b:

$ kubectl describe pod db-0 | tail -2
  Warning  FailedScheduling  0/6 nodes are available: 2 node(s) had volume node
  affinity conflict, 4 Insufficient cpu.
  → permanently unschedulable; the fix is to delete the PVC and try again, and hope

WaitForFirstConsumer (the correct default)
  PVC created → stays Pending → the scheduler picks a node → THEN the volume is
  provisioned IN THAT NODE'S ZONE
$ kubectl get pvc data-db-0
NAME        STATUS    VOLUME   CAPACITY   STORAGECLASS

$ kubectl describe pvc data-db-0 | grep -A1 Events
  Normal  WaitForFirstConsumer  waiting for first consumer to be created

Part 3 — Access Modes Do Not Mean What You Think

ModeActually meansCommon misreading
ReadWriteOnce (RWO)Mounted read-write by one node — any number of pods on that node"Only one pod can use it"
ReadOnlyMany (ROX)Read-only by many nodes—
ReadWriteMany (RWX)Read-write by many nodes — needs NFS, CephFS, EFS, Azure Files"Any storage can do this"
ReadWriteOncePod (RWOP)Exactly one pod, cluster-wideThe mode people think RWO is
$ kubectl get pvc data -o jsonpath='{.spec.accessModes}{"\n"}'
["ReadWriteOnce"]
$ kubectl get pods -o wide --no-headers | awk '{print $1, $7}'
writer-a   worker-2
writer-b   worker-2                    ← BOTH mount the same RWO volume, same node

$ kubectl exec writer-a -- sh -c 'echo from-a >> /data/shared.txt'
$ kubectl exec writer-b -- sh -c 'echo from-b >> /data/shared.txt'
$ kubectl exec writer-a -- cat /data/shared.txt
from-a
from-b                                 ← two writers, no protection whatsoever
⚠️ RWO does not protect a database from a second writer. A rolling update that happens to place the new pod on the same node as the old one gives you two processes writing to one filesystem — which is how single-writer databases get corrupted. The protections are ReadWriteOncePod (true single-pod exclusivity), strategy: Recreate, or a StatefulSet, whose ordered update guarantees the old pod is gone first.

The corollary is that an RWO volume does block a rolling update when the new pod lands on a different node — the classic "stuck in ContainerCreating with Multi-Attach error" that looks like a storage bug and is a strategy mismatch.

Two CSI features worth knowing because they change how you handle data operations:

① SNAPSHOTS — a point-in-time copy at the storage layer
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata: { name: db-2026-08-19 }
spec:
  volumeSnapshotClassName: csi-snapclass
  source: { persistentVolumeClaimName: data-postgres-0 }

② CLONING — a new PVC seeded from an existing one (or a snapshot)
spec:
  dataSource: { name: db-2026-08-19, kind: VolumeSnapshot,
                apiGroup: snapshot.storage.k8s.io }
  resources: { requests: { storage: 200Gi } }     ← must be ≥ the source
🔑 A snapshot is not a backup, and a crash-consistent snapshot is not a restore. It lives in the same account and region as the volume, so it does not survive account compromise or accidental project deletion, and it captures whatever was on disk at that instant — including a database mid-write. For a database, either quiesce it (pg_start_backup, an fsfreeze hook) or use the database's own backup tooling and treat snapshots as a fast rollback mechanism rather than as disaster recovery.

Part 6 — Failure Modes That Matter at 3am

NODE DIES with an RWO volume attached:

t=~40s   node marked NotReady

The non-graceful shutdown path, which is the supported way to speed up recovery:
$ kubectl taint node worker-2 node.kubernetes.io/out-of-service=nodeshutdown:NoExecute
   → pods are deleted immediately and volumes force-detached, so the replacement
     starts in seconds instead of ~12 minutes
   ⚠️ ONLY when the node is genuinely dead. If it is merely partitioned, this
      permits two pods to mount one volume — exactly the corruption RWO implies.

❌ Databases on the default StorageClass with reclaimPolicy: Delete and Immediate binding, unbounded emptyDir scratch space, RWO volumes assumed to prevent two writers, and snapshots treated as backups. A namespace cleanup deletes a PVC and 200 GB of production data is destroyed at the cloud provider — not detached, destroyed. Volumes are provisioned before scheduling, so a database pod lands permanently Pending with volume node affinity conflict whenever its zone lacks capacity, and the only remedy is to delete the PVC and roll the dice again. A batch job writes an unbounded cache into emptyDir, fills the node's disk, and the kubelet evicts three unrelated pods for DiskPressure. A rolling update places the new pod on the same node as the old one, both mount the RWO volume — which permits exactly that — and the database is corrupted by two writers. And when the account's storage is accidentally deleted, the "backups" turn out to be snapshots in the same account and region, taken crash-consistently mid-write.

✅ Use a Retain class for real data, bind late, bound your scratch space, enforce single-writer explicitly, and back up somewhere else. Create a StorageClass with reclaimPolicy: Retain and point every stateful chart at it, so deleting a PVC detaches rather than destroys, and accept that a Released PV needs a manual step before reuse. Keep volumeBindingMode: WaitForFirstConsumer everywhere so the volume is created in the zone the scheduler actually chose — a PVC sitting Pending until a consumer exists is correct behaviour, not a fault. Always set sizeLimit on emptyDir, which turns a node-wide DiskPressure eviction into one pod exceeding its own limit. Remember that RWO means one node, not one pod: use ReadWriteOncePod, a StatefulSet, or strategy: Recreate when a second writer would corrupt data. Watch CSI attach limits, which cap pods per node long before CPU does. And treat snapshots as fast rollback while real backups go to a different account and region, taken with the database's own consistent tooling and restore-tested on a schedule.

Interview Questions

Beginner: What is the difference between a PV, a PVC and a StorageClass?

The PVC is the request, the StorageClass is the recipe, the PV is the actual disk.

PVC  "I want 20Gi, ReadWriteOnce, class gp3"      ← written by the app team, namespaced
SC   provisioner + parameters + reclaimPolicy      ← written by the platform team
PV   the real volume that got created               ← cluster-scoped
Static provisioningDynamic (normal)
Who creates the PVAn administrator, in advanceThe StorageClass provisioner, on demand
BindingPVC matched to an existing PVPV created to fit the PVC

The separation is the point: the application declares what it needs without knowing whether it is EBS, Ceph or NFS, and the platform decides the implementation, the reclaim policy and whether expansion is allowed.

The field to check first on any new cluster is reclaimPolicy: the default StorageClass almost always says Delete, which means deleting a PVC destroys the underlying disk at the cloud provider.

Beginner: A PVC is stuck in Pending. Is that a problem?

Usually not — read the events before doing anything.

$ kubectl describe pvc data-db-0 | grep -A2 Events
  Normal  WaitForFirstConsumer  waiting for first consumer to be created before binding
        ↑ CORRECT behaviour: the volume will be created once a pod is scheduled,
          in whichever zone the scheduler picks
EventMeaningAction
WaitForFirstConsumerWaiting for a podNothing
ProvisioningFailedQuota, IAM, bad parametersRead the message
No events, no classNo default StorageClass existsSet storageClassName
storageclass not foundTypo or missing classkubectl get sc

Why WaitForFirstConsumer is the correct default: with Immediate binding the volume is created before scheduling, so in a multi-zone cluster it can land in a zone where the pod cannot be placed — producing volume node affinity conflict and a pod that can never be scheduled. Binding late lets the scheduler choose first.

Mid: Explain the access modes. What does ReadWriteOnce actually guarantee?

RWO means one node, not one pod. Any number of pods on that node can mount it read-write simultaneously.

$ kubectl get pods -o wide --no-headers | awk '{print $1, $7}'
writer-a  worker-2
writer-b  worker-2                 ← both mounting the same RWO PVC
$ kubectl exec writer-a -- sh -c 'echo a >> /data/f'; kubectl exec writer-b -- sh -c 'echo b >> /data/f'
$ kubectl exec writer-a -- cat /data/f
a
b                                  ← two writers, no protection
ModeGuarantee
RWOOne node, many pods
ROXMany nodes, read-only
RWXMany nodes read-write — needs a shared filesystem (NFS/EFS/CephFS)
RWOPExactly one pod, cluster-wide

Why this matters: a rolling update that places the new pod on the same node as the old one gives two processes writing one filesystem — a standard way to corrupt a single-writer database. The protections are ReadWriteOncePod, a StatefulSet with its ordered update, or strategy: Recreate.

The mirror-image symptom is a rolling update where the new pod lands on a different node and hangs with Multi-Attach error — the same RWO semantics, and again a strategy mismatch rather than a storage fault.

Mid: A database pod is stuck with Multi-Attach error after a node failure. Explain and resolve.

The RWO volume is still attached to the dead node, and Kubernetes will not attach it elsewhere until it is detached. That is the guarantee working, not a bug.

t=0     node stops responding
t=40s   marked NotReady
t=5-6m  pods evicted (the default 300 s toleration)
t=+6m   attach-detach controller force-detaches after its own timeout
t=~12m  the replacement pod attaches and starts

Why the wait exists: the control plane cannot distinguish a dead node from a partitioned one. If the node is alive but unreachable, its pod is still writing — attaching the volume elsewhere would give two writers and corrupt the data. The delay is deliberate caution.

Fast, supported recovery when you know the node is dead:

$ kubectl taint node worker-2 node.kubernetes.io/out-of-service=nodeshutdown:NoExecute
   → pods deleted immediately, volumes force-detached; recovery in seconds

The caveat that must accompany that command: apply it only when the node is genuinely gone. Using it on a partitioned node deliberately permits the two-writer scenario the whole mechanism exists to prevent — which for a database is worse than the outage.

The architectural answer is to stop relying on a single attached disk for availability: replicated databases with their own failover, or RWX storage where the volume is not exclusively attached at all.

Senior: Design storage for a production database on Kubernetes. Should it even be there?

Start with the honest question: a managed database is usually the better answer. RDS or Cloud SQL gives you backups, failover, patching and point-in-time recovery that you would otherwise build and operate yourself. Running a database in-cluster is justified by a specific requirement — cost at scale, an engine the provider does not offer, data residency, or an operator that genuinely automates the hard parts.

If it is in the cluster, the storage design:

DecisionChoiceReason
StorageClassRetain + WaitForFirstConsumerPVC deletion must not destroy data; zone-correct provisioning
WorkloadStatefulSetStable identity, per-pod PVCs, ordered updates
Access modeRWO, plus RWOP where supportedBlock storage performance; genuine single-writer
AvailabilityReplication, not shared storageA single attached disk is a single point of failure
BackupsEngine-native, to another account/regionSnapshots are same-account and often crash-consistent
ExpansionallowVolumeExpansion: trueGrowth without migration; shrinking is impossible

The point I would press hardest: volume-level HA is a trap. Failing a disk over to another node takes minutes, may need a force-detach, and gives you an unreplicated database that must recover its own WAL. Replication at the database layer fails over in seconds and does not depend on the attach-detach controller at all — so storage should be treated as per-replica local state rather than as the availability mechanism.

And what I would insist on operationally: restore drills on a schedule. An untested backup is a hypothesis, and the failure is nearly always discovered during the incident it was supposed to solve. I would also alert on volume free space with enough lead time to expand — expansion is online, but a full disk is an outage that expansion cannot fix quickly.

Senior: How would you migrate a stateful workload to a different StorageClass or zone?

You cannot change either in place — a PVC's class, access mode and zone are all immutable. Every approach is a copy.

MethodDowntimeWorks acrossNotes
Snapshot → restoreMinutesClass, sometimes zoneSame driver only; check consistency
Two pods, rsync between mountsMinutesAnythingSimple, auditable, slow for large volumes
Database-native replicationSecondsAnythingNew replica on the new class, promote, retire the old
Backup → restoreLongestAnything, including clustersAlso proves the backup works

For a database I would always use replication, because it is the only option whose cutover is measured in seconds and whose rollback is "do not promote". Add a replica whose PVC uses the new StorageClass, let it catch up, verify lag is zero, promote it, and keep the old primary read-only for a soak period before removing it.

The Retain detail that makes this safe: with a Retain class the old PV survives PVC deletion, so the pre-migration data is still there if the new volume disappoints. It must be manually cleared before it can bind again, which is exactly the friction you want at that moment.

The failure I would plan around is capacity: provisioning the new volumes alongside the old ones doubles storage consumption temporarily and can hit account quotas or per-node CSI attach limits mid-migration. Check both before starting, because discovering an attach-limit ceiling halfway through a cutover is an unpleasant surprise.

$ cat > tools/storage-audit.sh <<'SH'
#!/usr/bin/env bash
# Read-only audit of storage configuration that leads to data loss or Pending pods.
set -uo pipefail
hdr() { printf '\n== %s\n' "$1"; }

hdr "StorageClasses"
kubectl get sc -o json | jq -r '.items[] |
  "  \(.metadata.name)\treclaim=\(.reclaimPolicy)\tbinding=\(.volumeBindingMode)\texpand=\(.allowVolumeExpansion // false)\(
   if .metadata.annotations["storageclass.kubernetes.io/is-default-class"] == "true" then "\t(DEFAULT)" else "" end)"'

hdr "PVCs on a Delete-reclaim class (data destroyed with the PVC)"
DEL=$(kubectl get sc -o json | jq -r '.items[] | select(.reclaimPolicy=="Delete") | .metadata.name')
kubectl get pvc -A -o json | jq -r --arg del "$DEL" '
  ($del | split("\n")) as $d | .items[] |
  select(.spec.storageClassName as $c | $d | index($c)) |
  "  WARN \(.metadata.namespace)/\(.metadata.name) class=\(.spec.storageClassName) size=\(.status.capacity.storage // "?")"'

hdr "Immediate-binding classes (zone conflicts in multi-zone clusters)"
kubectl get sc -o json | jq -r '.items[] | select(.volumeBindingMode=="Immediate") |
  "  WARN \(.metadata.name) binds before scheduling"'

hdr "emptyDir volumes without sizeLimit"
kubectl get pods -A -o json | jq -r '.items[] |
  .metadata.namespace as $ns | .metadata.name as $n |
  (.spec.volumes // [])[] | select(.emptyDir != null and .emptyDir.sizeLimit == null) |
  "  WARN \($ns)/\($n) volume \(.name) is unbounded"' | head -10

hdr "hostPath volumes"
kubectl get pods -A -o json | jq -r '.items[] |
  .metadata.namespace as $ns | .metadata.name as $n |
  (.spec.volumes // [])[] | select(.hostPath != null) |
  "  FAIL \($ns)/\($n) mounts host path \(.hostPath.path)"' | head -10

hdr "RWO PVCs used by multi-replica Deployments (two-writer risk)"
kubectl get deploy -A -o json | jq -r '.items[] | select(.spec.replicas > 1) |
  .metadata.namespace as $ns | .metadata.name as $n |
  (.spec.template.spec.volumes // [])[] | select(.persistentVolumeClaim != null) |
  "  WARN \($ns)/\($n) has >1 replica sharing PVC \(.persistentVolumeClaim.claimName)"'

hdr "CSI attach-slot headroom"
kubectl get csinode -o json | jq -r '.items[] | .metadata.name as $n |
  (.spec.drivers // [])[] | select(.allocatable.count != null) |
  "  \($n) \(.name) limit=\(.allocatable.count)"'

hdr "PVs Released (Retain policy, awaiting manual cleanup)"
kubectl get pv -o json | jq -r '.items[] | select(.status.phase=="Released") |
  "  INFO \(.metadata.name) was \(.spec.claimRef.namespace)/\(.spec.claimRef.name) — data retained"'

🎯 Key Takeaways

  • emptyDir dies with the pod; without sizeLimit it can fill the node and evict unrelated pods — measured, an innocent pod evicted for DiskPressure.
  • medium: Memory makes an emptyDir tmpfs that counts against the pod's memory limit — measured as an OOMKill.
  • hostPath is node-level filesystem access and effectively a node takeover; restrict it with Pod Security.
  • PVC = request, StorageClass = recipe, PV = the actual disk; dynamic provisioning creates the PV to fit the claim.
  • reclaimPolicy: Delete is the default and destroys the disk at the cloud provider when the PVC is deleted — verified as an unrecoverable PV.
  • A Retain PV survives, but stays Released until its claimRef is cleared manually — the friction is the safety.
  • Immediate binding provisions before scheduling, producing permanent volume node affinity conflict; WaitForFirstConsumer binds in the scheduler's chosen zone.
  • A PVC sitting Pending under WaitForFirstConsumer is correct behaviour, not a fault.
  • ReadWriteOnce means one node — two pods on that node both mounted and wrote to the same volume, 100 interleaved lines each.
  • ReadWriteOncePod is the mode people think RWO is: the scheduler refuses the second pod cluster-wide.
  • The mirror-image symptom of RWO is Multi-Attach error when the new pod lands on another node — a strategy mismatch, not a storage fault.
  • CSI attach limits (~25 volumes per node on EBS) cap pod density long before CPU or memory, and appear as exceed max volume count.
  • Volume expansion is online and one-way: growth needed no restart, and shrinking, class changes and access-mode changes are all rejected as immutable.
  • Expanding on a class without allowVolumeExpansion is accepted and silently never happens — check for the ExternalExpanding warning.
  • Node failure with an attached RWO volume takes ~12 minutes end to end: ~40 s to NotReady, 300 s toleration, then a ~6-minute force-detach.
  • The out-of-service taint recovers in seconds but only when the node is genuinely dead — on a partitioned node it permits two writers.
  • A snapshot is not a backup: same account, same region, and crash-consistent unless the database is quiesced.
  • Real availability for databases comes from replication, not shared storage — disk failover is minutes and needs WAL recovery; replica promotion is seconds.
  • Migrating class or zone is always a copy: replication for databases, snapshot-restore or rsync otherwise — and plan for double storage consumption and attach limits mid-migration.
