RBAC & ServiceAccounts Security & Multi-tenancy

What you'll master: the fact that reframes Kubernetes authentication — there is no User object, users are strings asserted by an external authenticator, while ServiceAccounts are real API objects; the four Role/Binding combinations and the genuinely useful oddity (a ClusterRole bound with a RoleBinding); why RBAC is purely additive with no deny rules, so a permission granted anywhere cannot be revoked elsewhere; the escalation paths that make careful role design pointless — create pods is read every secret, and creating a pod with another ServiceAccount inherits its permissions; the escalate and bind verbs that exist to stop you granting what you do not have; what the built-in edit role really includes; bound projected tokens and why the old permanent Secret tokens were replaced; and an audit that finds the dangerous bindings in a real cluster. Prerequisites: ConfigMaps & Secrets, Pods.

$ kubectl get users
error: the server doesn't have a resource type "users"

$ openssl x509 -in alice.crt -noout -subject
subject=CN = alice, O = platform, O = oncall
   → the API server sees user "alice" in groups "platform" and "oncall".
     Revoking her access means revoking the CERTIFICATE, not deleting an object.

$ kubectl create sa deployer -n shop
$ kubectl get sa deployer -n shop
NAME       SECRETS   AGE
deployer   0         3s
   → its identity is system:serviceaccount:shop:deployer,
     and it is automatically in the groups system:serviceaccounts
     and system:serviceaccounts:shop
🔑 Because users are not objects, Kubernetes cannot list them, disable them, or tell you who exists. User lifecycle belongs to whatever issues the credentials — your OIDC provider, or your certificate authority. This is also why certificate-based access is awkward in practice: certificates cannot be revoked without a CRL the API server does not consult, so the only real remedy is a short expiry. Use OIDC for humans and ServiceAccounts for workloads.

Part 3 — Rules: Verbs, Resources and Subresources

apiVersion: rbac.authorization.k8s.io/v1
kind: Role

- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get","list","watch","create","update","patch"]
- apiGroups: ["apps"]
  resources: ["deployments/scale"]        ← a SUBRESOURCE, separately grantable
  verbs: ["update"]
- apiGroups: [""]                          ← "" is the core group
  resources: ["pods","pods/log"]
  verbs: ["get","list"]
- apiGroups: [""]
  resources: ["configmaps"]
  resourceNames: ["app-config"]            ← ONE named object
  verbs: ["get","update"]
SubresourceGrantsRisk
pods/logRead logsLogs often contain secrets
pods/execA shell in any podReads mounted Secrets and the SA token
pods/portforwardTunnel to any podReaches internal services
deployments/scaleChange replica count onlyLow — useful for autoscalers

⚠️ RBAC is purely additive — there are no deny rules. A subject's permissions are the union of every binding that names them, so you cannot grant broad access and carve out an exception. "Everything except Secrets" must be written as an explicit list of what is allowed, which is why resourceNames and per-resource rules matter. Note also that resourceNames cannot restrict list or watch: listing returns collections, so a rule naming one object simply does not grant list at all.

Part 4 — Escalation Paths

Careful role design is undone by a handful of permissions that are transitively equivalent to much more. These are the ones to know:

$ kubectl auth can-i get secrets --as=system:serviceaccount:shop:deployer -n shop
no
$ kubectl -n shop --as=system:serviceaccount:shop:deployer run leak --image=busybox \
    --restart=Never --overrides='{"spec":{"containers":[{"name":"c","image":"busybox",
    "command":["cat","/s/password"],"volumeMounts":[{"name":"s","mountPath":"/s"}]}],
    "volumes":[{"name":"s","secret":{"secretName":"db"}}]}}'
$ kubectl -n shop logs leak
hunter2                             ← "cannot read secrets" was never true

RBAC does contain one built-in protection against the most direct escalation: you cannot grant permissions you do not hold, unless you have the escalate verb.

$ kubectl create clusterrole superuser --verb='*' --resource='*' --as=carol
Error from server (Forbidden): clusterroles.rbac.authorization.k8s.io is forbidden:
user "carol" (groups=["team-a"]) is attempting to grant RBAC permissions not
currently held: {APIGroups:["*"], Resources:["*"], Verbs:["*"]}
🔑 The practical conclusion: the namespace is the real security boundary, not the Role. Splitting "can deploy" from "can read secrets" inside one namespace describes a boundary that does not exist, because anyone who can create a pod can mount any Secret there. If two workloads must not see each other's credentials, they belong in different namespaces.

❌ A cluster-admin binding for the CI ServiceAccount "temporarily", the default ServiceAccount used by every workload with its token auto-mounted, wildcard roles, and RBAC that carefully denies get secrets while allowing create pods. The CI binding was added during an incident two years ago and never removed, so a compromised build has complete control of every namespace. Every pod carries an API token it never uses, so any container breakout starts with a working cluster credential. Roles are written with verbs: ["*"], resources: ["*"] because enumerating them was tedious, which means every new API type added by an operator is automatically granted too. The "least privilege" deployer role denies secret reads and permits pod creation, which is the same permission by a longer route — and it can also create a pod running as the admin ServiceAccount that happens to exist in the same namespace. And because RBAC is additive with no deny rules, an old group binding grants edit cluster-wide, silently overriding every careful namespaced role in the cluster.

✅ Grant named verbs on named resources, treat the namespace as the boundary, and turn off the token nobody uses. Define permission sets once as ClusterRoles and bind them per namespace with RoleBindings, so a team gets exactly the same rules in exactly the namespaces they own. Enumerate verbs and resources explicitly — wildcards silently grant every future API type — and use resourceNames where a role genuinely needs one object, remembering it cannot restrict list. Give every workload its own ServiceAccount, never the default one, and set automountServiceAccountToken: false for the majority that never call the API; for cloud access use workload identity so no Kubernetes-issued credential exists to steal. Accept that create pods equals reading every Secret in the namespace and separate workloads that must not see each other's credentials into different namespaces rather than pretending a Role can do it. Audit for cluster-admin bindings, wildcards, and the escalate/bind/impersonate verbs on a schedule — these are the permissions that make everything else decorative.

Interview Questions

Beginner: Explain Roles, ClusterRoles and their bindings.

Roles define permissions; bindings attach them to subjects. The namespaced and cluster-scoped variants combine four ways, one of which is invalid.

RoleBindingResult
RoleRoleBindingThat namespace
ClusterRoleClusterRoleBindingCluster-wide
ClusterRoleRoleBindingCluster-role rules, scoped to that namespace
RoleClusterRoleBindingInvalid

The third combination is the useful one — define a permission set once and grant it per namespace. It is how the built-in view, edit and admin ClusterRoles are meant to be used.

Two things worth adding: ClusterRoles are also required for cluster-scoped resources (Nodes, PersistentVolumes, Namespaces), which a Role cannot cover at all. And RBAC is additive — permissions are the union of every binding naming the subject, with no way to subtract.

Beginner: What is a ServiceAccount and how does it differ from a user?

A ServiceAccount is a real API object for workloads; a user is just a string asserted by an external authenticator.

$ kubectl get users
error: the server doesn't have a resource type "users"
$ kubectl get sa
NAME       SECRETS   AGE
default    0         10d
UserServiceAccount
API object❌✅
Created byYour IdP or CAkubectl create sa
IdentityCertificate CN, OIDC claimsystem:serviceaccount:ns:name
CredentialCertificate or OIDC tokenA projected, time-limited token

Every pod gets a ServiceAccount — the namespace's default if none is specified — and its token is mounted at /var/run/secrets/kubernetes.io/serviceaccount/token.

The practical consequence: because users are not objects, Kubernetes cannot list or disable them. Revoking a human's access means revoking the credential at the identity provider — which is exactly why client certificates are a poor choice: they cannot be revoked, only expired.

Mid: You granted a ServiceAccount pod-creation but not secret access. Is it restricted?

No. create pods is equivalent to reading every Secret in the namespace. The kubelet mounts the Secret on the pod's behalf, so the requester needs no secret permission at all.

$ kubectl auth can-i get secrets --as=system:serviceaccount:shop:deployer -n shop
no
$ kubectl -n shop --as=system:serviceaccount:shop:deployer apply -f pod-mounting-secret.yaml
pod/leak created
$ kubectl -n shop logs leak
hunter2
Also granted by create podsHow
Any other SA's permissionsSet serviceAccountName on the pod
Node filesystem accesshostPath, if admission allows it
Host network and PIDSame, absent Pod Security

The design conclusion: the namespace is the security boundary, not the Role. Splitting "deploy" from "read secrets" inside one namespace describes a boundary that does not exist. If two workloads must not see each other's credentials, they need different namespaces.

The complementary control is Pod Security admission, which is what stops create pods from also meaning hostPath and privileged containers.

Mid: What do the escalate, bind and impersonate verbs do?

Each is effectively cluster-admin, and each exists because RBAC otherwise prevents you granting what you do not hold.

$ kubectl create clusterrole superuser --verb='*' --resource='*' --as=carol
Error from server (Forbidden): ... is attempting to grant RBAC permissions not
currently held: {APIGroups:["*"], Resources:["*"], Verbs:["*"]}
   ← the built-in privilege-escalation prevention
VerbEffect
escalate on rolesBypasses that check — write any rule you like
bind on rolesBind an existing role you do not hold
impersonateAct as any user or group, including system:masters

Impersonation is the starkest: kubectl --as=system:admin --as-group=system:masters is cluster-admin for anyone holding the verb, and it appears in audit logs as the impersonated identity with the real one alongside.

Why they exist at all: bind and escalate let a platform team delegate role management without holding every permission themselves, and impersonation is genuinely useful for testing (kubectl auth can-i --as=...) and for admin proxies.

In an audit these are the first thing to search for, above cluster-admin bindings, because a role granting them looks innocuous and is not.

Senior: Design RBAC for a multi-team platform.

Namespaces are the boundary; ClusterRoles define the vocabulary; RoleBindings do the granting.

SubjectGrantScope
Developersedit-like ClusterRole via RoleBindingTheir own namespaces
On-callview everywhere + break-glass execCluster read; exec time-boxed and audited
CINamed verbs on Deployments/Services/ConfigMapsOne namespace per pipeline
Platform teamCluster-scoped adminSmall, named group
WorkloadsOne SA each, usually no permissionsToken auto-mount off

The decisions I would defend:

  • Namespace per team per environment, because pod creation implies secret reading — no Role can subdivide that, so the namespace is the only real boundary.
  • No wildcards. A role with resources: ["*"] silently gains every CRD an operator installs later.
  • Groups, not individuals, in bindings. Individual bindings become a graveyard of people who left.
  • Workload identity for cloud access, so there is no long-lived credential to steal and no Secret to rotate.
  • Break-glass is a separate, alerting path — a binding that is created, used, and removed, rather than a standing grant that nobody remembers.

What I would audit continuously: cluster-admin bindings, wildcard rules, the escalate/bind/impersonate verbs, ServiceAccounts with cluster-scoped bindings, and pods still using the default SA. Those five queries find essentially every real RBAC problem, and none of them require reading the roles by hand.

And the limit worth stating: RBAC governs the API only. It does nothing about network reachability (NetworkPolicy) or what a container may do on its node (Pod Security). A "secure namespace" needs all three.

Senior: How do you give a workload access to a cloud API without storing credentials?

Workload identity: federate the pod's projected ServiceAccount token to the cloud provider's IAM, so no Kubernetes-stored credential exists.

$ kubectl -n shop get sa app -o jsonpath='{.metadata.annotations}{"\n"}'
{"eks.amazonaws.com/role-arn":"arn:aws:iam::123456789012:role/shop-app"}
$ kubectl -n shop exec deploy/api -- aws sts get-caller-identity
{ "Arn": "arn:aws:sts::123456789012:assumed-role/shop-app/botocore-session-1755598931" }
$ kubectl -n shop get secrets | grep -c aws
0                                  ← no access key exists anywhere

How it works: the pod gets a projected token with a cloud-specific audience; the cloud provider trusts the cluster's OIDC issuer and maps system:serviceaccount:shop:app to an IAM role; the SDK exchanges the token for a short-lived cloud credential and refreshes it automatically.

Stored access keyWorkload identity
Credential in etcd✅❌ None
In backups✅❌
RotationManualAutomatic
Blast radius if leakedUnbounded in time~1 hour

The part that needs care is the trust policy: it must pin both the namespace and the ServiceAccount name, or any pod in the cluster that can create a SA with the right name assumes the role. A trust policy scoped only to the cluster's OIDC issuer is a cluster-wide grant wearing a workload-specific label.

For non-cloud dependencies the equivalent is an external secret manager with Kubernetes auth — Vault verifying the same projected token — which gives short-lived credentials for the same reason. Both are strictly better than a Secret because the credential never rests anywhere.

# Read-only audit for the RBAC grants that make everything else decorative.

hdr() { printf '\n== %s\n' "$1"; }

hdr "cluster-admin bindings"
kubectl get clusterrolebindings -o json | jq -r '.items[] |

  select(.metadata.name | startswith("system:") | not) |
  "  \(.metadata.name) → \([.subjects[]? | "\(.kind):\(.namespace // "-"):\(.name)"] | join(", "))"'

hdr "escalate / bind / impersonate"
kubectl get clusterroles,roles -A -o json | jq -r '.items[] |
  .metadata.name as $n | (.metadata.namespace // "cluster") as $ns |
  (.rules // [])[] | select((.verbs // []) | any(. == "escalate" or . == "bind" or . == "impersonate")) |
  "  \($ns)/\($n): verbs=\(.verbs) resources=\(.resources)"'

hdr "wildcard rules (grant every future API type)"
kubectl get clusterroles -o json | jq -r '.items[] |
  select(.metadata.name | startswith("system:") | not) |
  .metadata.name as $n | (.rules // [])[] |
  select(((.verbs // []) | index("*")) and ((.resources // []) | index("*"))) |
  "  ClusterRole/\($n): verbs=* resources=* apiGroups=\(.apiGroups)"'

hdr "who can read secrets cluster-wide"
kubectl get clusterroles -o json | jq -r '.items[] |
  select(.metadata.name | startswith("system:") | not) | .metadata.name as $n |
  (.rules // [])[] |
  select(((.resources // []) | any(. == "secrets" or . == "*")) and
         ((.verbs // []) | any(. == "get" or . == "list" or . == "*"))) |
  "  ClusterRole/\($n)"' | sort -u

hdr "ServiceAccounts with CLUSTER-scoped bindings"
kubectl get clusterrolebindings -o json | jq -r '.items[] |
  select(.metadata.name | startswith("system:") | not) | .roleRef.name as $r |
  (.subjects // [])[] | select(.kind == "ServiceAccount") |
  "  \(.namespace)/\(.name) → ClusterRole/\($r)"'

hdr "pods using the default ServiceAccount with a token mounted"
kubectl get pods -A -o json | jq -r '[.items[] |
  select(.spec.serviceAccountName == "default" and .spec.automountServiceAccountToken != false)] |
  length | "  \(.) pods"'

$ cat > tools/new-tenant.sh <<'SH'
#!/usr/bin/env bash
# Create a tenant namespace with RBAC, quota, network and pod-security defaults.
set -euo pipefail
NS=${1:?namespace}; GROUP=${2:?group}
kubectl create namespace "$NS" --dry-run=client -o yaml | kubectl apply -f -
kubectl label namespace "$NS" tenant="$GROUP" \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted --overwrite

# 1. RBAC — a shared ClusterRole, scoped by a RoleBinding
kubectl -n "$NS" create rolebinding tenant-edit \
  --clusterrole=tenant-editor --group="$GROUP" --dry-run=client -o yaml | kubectl apply -f -

# 2. the default SA must not carry a token
kubectl -n "$NS" patch sa default -p '{"automountServiceAccountToken":false}'

# 3. quota and defaults
kubectl -n "$NS" apply -f - <<EOF
apiVersion: v1
kind: LimitRange
metadata: { name: defaults }
spec:
  limits:
  - type: Container
    default:        { cpu: "500m", memory: "512Mi" }
    defaultRequest: { cpu: "100m", memory: "128Mi" }
---
apiVersion: v1
kind: ResourceQuota
metadata: { name: quota }
spec:
  hard: { requests.cpu: "20", requests.memory: 40Gi, pods: "100" }
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-ingress }
spec: { podSelector: {}, policyTypes: [Ingress] }
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dns }
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      podSelector:       { matchLabels: { k8s-app: kube-dns } }
    ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]
EOF
echo "tenant $NS ready for group $GROUP"
SH

The point of the exercise: RBAC alone secures none of rows 4–5. A tenant boundary needs RBAC and Pod Security and NetworkPolicy, applied together at namespace creation — which is why it belongs in a script rather than in a runbook.

🎯 Key Takeaways

  • There is no User object — users and groups are strings asserted by certificates or OIDC, so Kubernetes cannot list or disable them.
  • Client certificates cannot be revoked; use OIDC with short expiry for humans and ServiceAccounts for workloads.
  • Four Role/Binding combinations, one invalid; ClusterRole + RoleBinding is the pattern that defines rules once and scopes them per namespace.
  • The built-in edit role includes Secrets and pods/exec; view deliberately excludes Secrets.
  • RBAC is purely additive with no deny rules: permissions are the union of every binding, so a cluster-wide grant silently overrides careful namespaced roles.
  • resourceNames cannot restrict list or watch, because listing returns collections.
  • Subresources are separately grantable — pods/log leaks secrets from logs, and pods/exec grants everything the pod can do.
  • create pods is equivalent to reading every Secret in the namespace — demonstrated against RBAC that explicitly denied secret access.
  • It also grants any other ServiceAccount's permissions: a "restricted" SA created a pod as an admin SA and granted itself admin.
  • RBAC cannot express "may create pods but only with SA X" — that needs an admission policy.
  • The privilege-escalation check stops you granting what you do not hold; escalate, bind and impersonate each bypass it and are effectively cluster-admin.
  • The namespace is the real security boundary, not the Role — workloads that must not see each other's credentials need separate namespaces.
  • Projected tokens are audience-scoped, ~1 hour, and bound to the pod — verified returning Unauthorized seconds after the pod was deleted.
  • Legacy Secret-based tokens never expired; that is why they were replaced.
  • automountServiceAccountToken: false is the cheapest hardening available — one audit found 47 pods carrying a credential they never use.
  • Workload identity removes the credential entirely, but its trust policy must pin both namespace and ServiceAccount name or it is a cluster-wide grant.
  • kubectl auth can-i --list --as=... is the fastest way to see what a subject really has, including everything inherited.
  • Audit for five things: cluster-admin bindings, wildcard rules, escalate/bind/impersonate, SAs with cluster-scoped bindings, and default-SA token mounts.
  • Wildcard rules automatically grant every CRD an operator installs later.
  • RBAC governs the API only: network reachability needs NetworkPolicy and node-level capability needs Pod Security — a tenant boundary requires all three, applied together.
