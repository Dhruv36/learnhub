Pod Security & Admission Control Security & Multi-tenancy

What you'll master: the layer RBAC cannot reach — what a container may do on its node once it is allowed to exist; the admission chain and why a failing webhook can make the entire cluster read-only; Pod Security Admission's three levels and three modes, including the warn/audit combination that lets you roll out restricted without breaking production; every field restricted requires and why each one exists; hostPath, privileged and the daemon-socket mount as complete cluster takeovers, demonstrated; where PSA stops being enough and a policy engine (Kyverno, OPA Gatekeeper) takes over — mutation, cross-object rules, image provenance; and the ordering fact that decides all of it: mutating webhooks run before validating ones, so a sidecar injector can insert exactly what your policy would have rejected. Prerequisites: RBAC, Pods, and Docker: Security.

Part 1 — The Admission Chain

  request
    → AUTHENTICATION  who are you
    → AUTHORIZATION   may you (RBAC)
    → MUTATING ADMISSION      ← webhooks CHANGE the object (sidecars, defaults)
    → OBJECT SCHEMA VALIDATION
    → VALIDATING ADMISSION    ← webhooks ACCEPT or REJECT (PSA, Kyverno, OPA)
    → persist to etcd
StageAnswersCan it modify?
AuthenticationWho are you?No
Authorization (RBAC)May you create a pod?No
Mutating admission—✅ Yes
Validating admissionMay you create this pod?No
🔑 RBAC answers "may you create a pod"; admission answers "may you create this pod". That gap is the whole subject: as shown in RBAC, create pods also grants mounting any Secret, using any ServiceAccount, and — without admission control — hostPath, privileged and host namespaces. Admission is what stops "can deploy" from meaning "owns the node".

Admission is the one synchronous step in an otherwise asynchronous system, which makes a broken webhook uniquely damaging:

$ time kubectl create deploy canary --image=nginx:alpine
Error from server (InternalError): Internal error occurred: failed calling webhook
"policy.example.com": Post "https://svc.ns.svc:443/validate": service "svc" not found
real    0m10.240s              ← every write pays the timeout, then fails
$ kubectl get pods
NAME                READY   STATUS
web-7d4b9c-m4j1q    1/1     Running    ← reads are fine; the cluster is READ-ONLY

failurePolicyIgnore unless it is a security controlFail + an outage = a read-only cluster

Part 2 — Pod Security Admission

PSA is built in, needs no components, and is configured entirely with namespace labels. Three levels, three modes.

LevelAllowsUse for
privilegedEverything — no restrictions at allkube-system, CNI, storage drivers
baselineBlocks known escalations: privileged, hostPath, host namespaces, most capabilitiesA sane minimum
restrictedAlso requires non-root, seccomp, dropped capabilities, no privilege escalationEverything you can
$ kubectl label ns shop \
    pod-security.kubernetes.io/enforce=restricted \
    pod-security.kubernetes.io/enforce-version=v1.31 \
    pod-security.kubernetes.io/warn=restricted \
    pod-security.kubernetes.io/audit=restricted
ModeEffectUse for
enforceRejects the podThe final state
warnReturns a warning to the client; the pod is createdRolling it out
auditAnnotates the audit log onlyMeasuring the blast radius first
THE ROLLOUT ORDER that avoids breaking production:

  ① warn + audit at `restricted`, enforce nothing
       → the audit log and kubectl warnings list every workload that would fail
  ② fix the workloads
  ③ enforce=baseline           (blocks the escalations, tolerates non-root gaps)
  ④ enforce=restricted

$ kubectl label ns shop pod-security.kubernetes.io/warn=restricted
$ kubectl apply -f legacy-app.yaml
Warning: would violate PodSecurity "restricted:latest": allowPrivilegeEscalation != false
(container "app" must set securityContext.allowPrivilegeEscalation=false),
unrestricted capabilities (container "app" must set securityContext.capabilities.drop=["ALL"]),
runAsNonRoot != true, seccompProfile (pod or container "app" must set
securityContext.seccompProfile.type to "RuntimeDefault" or "Localhost")
deployment.apps/legacy-app created        ← created, with the full list of what to fix
⚠️ PSA applies to pods, so a Deployment is accepted and its pods are rejected. The Deployment object is created successfully; the ReplicaSet then fails to create pods, and the failure appears as a FailedCreate event rather than an error on your apply. That is exactly why warn exists — it surfaces the violation on the object you actually applied.

Part 3 — What restricted Requires

spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile: { type: RuntimeDefault }
  containers:
  - name: app
    image: myco/api:1.4.2
    securityContext:
      allowPrivilegeEscalation: false

RequirementBlocksCross-reference
runAsNonRoot: trueUID 0 in the container is UID 0 on the hostDocker: Security
allowPrivilegeEscalation: falseRegaining root via a setuid binarySets NoNewPrivs
capabilities.drop: ["ALL"]The 14 default capabilities, including NET_RAWARP spoofing between pods
seccompProfile: RuntimeDefault~44 syscalls used by kernel exploitskeyctl, kexec, bpf
No hostPathNode filesystem accessPart 4
No host namespacesSeeing and signalling host processeshostPID, hostNetwork
No privilegedAll capabilities, all devices, no seccompPart 4

The one requirement that breaks real applications is runAsNonRoot, and it usually breaks for two reasons: a process binding a port below 1024, and volume ownership. Both have standard answers — listen on 8080 and publish 80 at the Service, and use fsGroup so mounted volumes are group-writable by the pod's UID.

Part 4 — Three Complete Takeovers

① hostPath — mount the node's filesystem
   volumes: [{ name: h, hostPath: { path: / } }]
   → read /etc/kubernetes/admin.conf, or every container's secrets under
     /var/lib/kubelet/pods/*/volumes/kubernetes.io~secret/
   → write to /etc/cron.d, or add an SSH key

② privileged: true
   → all capabilities, seccomp off, AppArmor off, ALL HOST DEVICES in /dev
   → mount the host's root disk directly

③ the daemon socket
   volumes: [{ name: s, hostPath: { path: /var/run/docker.sock } }]
   → ask the root daemon to start a privileged container mounting /
   → the outer pod's own UID and capabilities are irrelevant

$ kubectl -n unrestricted run p --image=busybox --restart=Never \
    --overrides='{"spec":{"volumes":[{"name":"h","hostPath":{"path":"/"}}],
    "containers":[{"name":"c","image":"busybox","command":["sh","-c",
    "cat /host/etc/kubernetes/admin.conf | head -3"],
    "volumeMounts":[{"name":"h","mountPath":"/host"}]}]}}'
$ kubectl -n unrestricted logs p
apiVersion: v1
clusters:
- cluster:                             ← cluster-admin credentials, from a "restricted" SA

$ kubectl -n restricted run p --image=busybox --restart=Never --overrides='(same)'
Error from server (Forbidden): pods "p" is forbidden: violates PodSecurity
"restricted:latest": hostPath volumes (volume "h" uses restricted volume type "hostPath")
🔑 Any of the three makes the pod's own RBAC irrelevant. A ServiceAccount with no permissions at all, in a namespace with no Pod Security enforcement, can read the cluster's admin kubeconfig off the node. This is why admission control is not "extra hardening" on top of RBAC — it is the control that makes RBAC's boundaries mean anything.

Part 5 — Where PSA Stops

RequirementPSAPolicy engine
Block privileged, hostPath, host namespaces✅✅
Require non-root, seccomp, dropped capabilities✅✅
Require resource limits❌✅
Ban :latest tags❌✅
Require images from an approved registry❌✅
Require a signature or provenance❌✅
Require specific labels or annotations❌✅
Restrict which ServiceAccount a pod may use❌✅
Cross-object rules (unique Ingress hosts)❌✅
Mutate — add defaults, inject sidecars❌✅
Needs extra componentsNoYes
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: platform-baseline }
spec:
  validationFailureAction: Enforce
  rules:
  - name: require-limits
    match: { any: [{ resources: { kinds: [Pod] } }] }
    validate:
      message: "every container must set resources.limits.memory"
      foreach:
      - list: "request.object.spec.containers"
        deny: { conditions: { all: [{ key: "{{ element.resources.limits.memory || '' }}",
                                      operator: Equals, value: "" }] } }
  - name: approved-registries
    match: { any: [{ resources: { kinds: [Pod] } }] }
    validate:
      message: "images must come from registry.example.com"
      pattern: { spec: { containers: [{ image: "registry.example.com/*" }] } }
  - name: default-seccomp                 ← MUTATION: PSA cannot do this
    match: { any: [{ resources: { kinds: [Pod] } }] }
    mutate:
      patchStrategicMerge:
        spec: { securityContext: { seccompProfile: { type: RuntimeDefault } } }

The Validating Admission Policy feature brings CEL-based rules into the API server itself, removing the webhook availability problem for validation. It does not mutate, so a policy engine remains necessary for defaulting and injection — but for pure "reject this" rules, in-tree policy avoids the read-only-cluster failure mode entirely.

Part 6 — Ordering: Mutation Before Validation

  you submit:            a pod with no sidecar, compliant with `restricted`
  mutating webhook:      the mesh injects an Envoy sidecar
                         → which requires NET_ADMIN to program iptables
  validating admission:  PSA evaluates the MUTATED pod
                         → REJECTED: capabilities.add NET_ADMIN
  the error blames YOUR pod for a container you did not write.
ConsequenceHandling
Injected sidecars must satisfy policyCNI-mode mesh injection, or a policy exemption for the sidecar
Defaulting webhooks can fix violationsMutate seccompProfile in, then enforce
Mutating webhook order is not guaranteedDo not chain mutations that depend on each other
Policies must evaluate the final objectTest with --dry-run=server, never client
⚠️ Ordering also gives you the clean rollout path. A mutating policy that adds seccompProfile: RuntimeDefault and allowPrivilegeEscalation: false to every pod means the validating rule that requires them never fires — existing workloads become compliant without a single manifest change. Mutate first, enforce second.

❌ No Pod Security labels anywhere, a webhook with failurePolicy: Fail and no namespace selector, and restricted enforced across the cluster in one change. Because nothing constrains pods, any ServiceAccount that can create one can mount hostPath: / and read /etc/kubernetes/admin.conf — so every carefully scoped Role in the cluster is decorative. The policy webhook's Service is deleted during an unrelated cleanup, and since it matches all resources in all namespaces with failurePolicy: Fail, every write in the cluster now fails after a ten-second timeout: no deploys, no scaling, and no way to delete the webhook without the webhook answering. Separately, someone enforces restricted on every namespace at once, so the monitoring DaemonSet that legitimately needs hostPath stops being able to create pods — silently, because the DaemonSet object is accepted and only the pods are rejected, surfacing as FailedCreate events nobody is watching. And the service mesh's injected sidecar requires NET_ADMIN, so every application pod is rejected with an error naming a container the developers did not write.

✅ Label every namespace, roll out with warn before enforce, and make webhooks fail open unless they are genuinely security controls. Set Pod Security labels at namespace creation — enforce=baseline at minimum, restricted wherever possible — and pin enforce-version so a cluster upgrade cannot tighten the rules under you. Roll out by setting warn and audit to restricted first: the warnings list every field each workload must add, on the object you actually applied, before anything is rejected. Give infrastructure that genuinely needs hostPath its own privileged namespace rather than weakening the whole cluster. Configure webhooks with short timeouts, narrow rules, a namespaceSelector that excludes kube-system, and failurePolicy: Ignore unless failing closed is the point — and never let a webhook gate the pods that run it. Remember that mutation happens before validation: use it deliberately, defaulting seccompProfile and allowPrivilegeEscalation in so existing workloads become compliant without manifest changes, and always validate with --dry-run=server, which is the only check that evaluates the final mutated object.

Interview Questions

Beginner: What is admission control and how does it differ from RBAC?

RBAC answers "may you create a pod"; admission answers "may you create this pod".

authn → authz (RBAC) → MUTATING admission → validation → VALIDATING admission → etcd
StageQuestionModifies?
RBACMay this subject create pods here?No
Mutating admission—Yes — sidecars, defaults
Validating admissionDoes this specific object comply?No

Why the gap matters: a ServiceAccount with only create pods can mount hostPath: / and read the cluster's admin kubeconfig off the node. RBAC permitted a pod; only admission can say which pods.

Pod Security Admission is the built-in implementation — no components to install, configured entirely with namespace labels — and it is the baseline every cluster should have.

Beginner: What are the Pod Security levels and modes?

Three levels of strictness and three modes of reaction, set as namespace labels.

LevelAllows
privilegedEverything — the default when unlabelled
baselineBlocks privileged, hostPath, host namespaces, most capabilities
restrictedAlso requires non-root, seccomp, drop ALL capabilities, no escalation
ModeEffect
enforceRejects the pod
warnWarns the client; pod is created
auditAudit-log annotation only
kubectl label ns shop \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=v1.31 \
  pod-security.kubernetes.io/warn=restricted

The rollout order matters: start with warn and audit at restricted to see what would break, fix it, then enforce. And pin enforce-version, or a cluster upgrade can tighten the rules under you.

Mid: Why is hostPath considered a cluster takeover?

Because the node's filesystem contains the credentials for everything running on it.

volumes: [{ name: h, hostPath: { path: / } }]

/etc/kubernetes/admin.conf                      ← cluster-admin kubeconfig (control plane)
/var/lib/kubelet/pods/*/volumes/*~secret/       ← EVERY pod's mounted Secrets
/var/lib/kubelet/pki/                           ← the kubelet's client certificate
/etc/cron.d, /root/.ssh/authorized_keys         ← persistence
/var/run/docker.sock                            ← ask the root daemon to do anything

The pod's own identity is irrelevant. A ServiceAccount with no RBAC permissions at all reads the admin kubeconfig and becomes cluster-admin — so every scoped Role in the cluster is decorative while hostPath is permitted.

The same applies to privileged: true, which grants all capabilities, disables seccomp and AppArmor, and exposes every host device — including the disks — (Docker: Security measures all four).

PSA baseline already blocks all of these. Infrastructure that genuinely needs them — CNI, CSI, monitoring agents — belongs in its own privileged namespace with RBAC restricting who can deploy there, rather than weakening the whole cluster.

Mid: A validating webhook is down and nothing can be deployed. What happened, and how do you prevent it?

Admission is synchronous, so failurePolicy: Fail plus an unavailable webhook makes the cluster read-only.

$ time kubectl create deploy canary --image=nginx:alpine
Error from server (InternalError): failed calling webhook "policy.example.com":
service "svc" not found
real    0m10.240s              ← every write pays the full timeout, then fails
$ kubectl get pods              ← reads still work

Recovery is to delete the ValidatingWebhookConfiguration — which is itself a write, and succeeds only because webhooks do not gate their own configuration objects. If the webhook's rules had covered kube-system, you would also have been unable to restart the components needed to fix it.

MitigationEffect
failurePolicy: IgnoreWrites proceed when it is down — right for anything not a security control
namespaceSelector excluding kube-systemNever block the components that fix it
Narrow rulesScope the blast radius
timeoutSeconds: 1–5Bounds latency added to every write
HA webhook, not gated by itselfOtherwise its own pods cannot be recreated

The general principle: everything else in Kubernetes retries and eventually converges; admission is the one step that stops convergence entirely. It is the most common cause of a cluster that is up and completely unable to change.

Senior: Design a pod-security policy for a multi-tenant cluster.

Namespace-level defaults with PSA, a policy engine for what PSA cannot express, and an explicit exemption path for infrastructure.

Namespace classPSA levelWho may deploy
Tenant workloadsrestrictedTenant groups
Platform servicesbaselinePlatform team
Infrastructure (CNI, CSI, monitoring)privilegedCluster admins only

The exemption is the design, not a loophole: some workloads genuinely need hostPath. Putting them in a small number of privileged namespaces with tight RBAC keeps the exception auditable — "who can deploy into a privileged namespace" is one query, and it is a much better control than a per-pod annotation nobody reviews.

Layered on top with a policy engine: required resource limits, approved registries, image signature verification, banning :latest, restricting which ServiceAccount a pod may use (which closes the escalation path RBAC cannot express), and mutation to default seccompProfile and allowPrivilegeEscalation so workloads become compliant without manifest changes.

Rollout: warn and audit first, measure from the audit log, fix, then enforce=baseline, then restricted. Enforcing everywhere in one change breaks infrastructure silently, because PSA rejects pods while the Deployment is accepted.

What I would also enforce organisationally: namespace creation goes through a template that sets PSA labels, quotas and a default-deny NetworkPolicy together. A tenant boundary needs RBAC, Pod Security and NetworkPolicy — any one alone leaves a complete path around it.

Senior: Your service mesh injects a sidecar that violates policy. How do you resolve it?

This is an ordering problem: mutating webhooks run before validating ones, so PSA evaluates the pod after injection. The rejection names a container the developers never wrote.

you submit           → compliant pod
mutating webhook     → mesh injects Envoy with capabilities.add: [NET_ADMIN]
validating admission → PSA rejects: "restricted" forbids adding capabilities
OptionTrade-off
CNI-mode injectionThe mesh programs iptables from a node agent — no NET_ADMIN in the pod. Best answer.
Exempt the sidecar container in policyPossible with a policy engine, not with PSA — PSA has no per-container exemptions
Run mesh namespaces at baselineWeakens every workload there, not just the sidecar
Ambient / sidecar-less meshRemoves the problem entirely; a larger migration

I would take CNI-mode injection, because it removes the elevated capability rather than tolerating it, and keeps restricted intact for the application containers where it matters.

The generalisable lesson is that ordering can also be used deliberately: a mutating policy that adds seccompProfile: RuntimeDefault and allowPrivilegeEscalation: false to every pod makes existing workloads compliant with restricted without touching a single manifest. Mutate first, enforce second.

And test with --dry-run=server: it runs the full chain including mutation, so it is the only way to see the object that will actually be validated. A client dry run parses YAML and proves nothing.

5 (hard): Express with a policy engine what PSA cannot.
Solution 
$ helm install kyverno kyverno/kyverno -n kyverno --create-namespace
$ kubectl apply -f - <<'EOF'
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: platform-rules }
spec:
  validationFailureAction: Enforce
  background: true
  rules:
  - name: require-memory-limits
    match: { any: [{ resources: { kinds: [Pod], namespaces: ["shop","payments"] } }] }
    validate:
      message: "every container must set resources.limits.memory"
      foreach:
      - list: "request.object.spec.containers"
        deny:
          conditions:
            all:
            - key: "{{ element.resources.limits.memory || '' }}"
              operator: Equals
              value: ""
  - name: no-latest-tag
    match: { any: [{ resources: { kinds: [Pod] } }] }
    validate:
      message: "image tags must be immutable — :latest is not allowed"
      pattern:
        spec:
          containers:
          - image: "!*:latest"
  - name: approved-registry
    match: { any: [{ resources: { kinds: [Pod], namespaces: ["shop"] } }] }
    validate:
      message: "images must come from registry.example.com"
      pattern: { spec: { containers: [{ image: "registry.example.com/*" }] } }
  - name: restrict-serviceaccount
    match: { any: [{ resources: { kinds: [Pod], namespaces: ["shop"] } }] }
    validate:
      message: "pods in shop may only use the 'app' ServiceAccount"
      pattern: { spec: { serviceAccountName: "app" } }
EOF

🎯 Key Takeaways

  • RBAC answers "may you create a pod"; admission answers "may you create this pod" — that gap is where hostPath and privileged live.
  • Admission is the only synchronous step in an otherwise self-healing system, which is why a broken webhook stops convergence entirely.
  • A webhook with failurePolicy: Fail and no namespaceSelector made every write in the cluster fail after a 10-second timeout, including in kube-system.
  • Recovery worked only because webhooks do not gate their own configuration objects; self-healing was also broken, since replacement pods could not be created.
  • Safe webhook config: Ignore unless it is a security control, 1–5 s timeout, narrow rules, exclude system namespaces, and never gate the webhook's own pods.
  • PSA is built in and configured with namespace labels — three levels (privileged, baseline, restricted) and three modes (enforce, warn, audit).
  • Unlabelled namespaces default to privileged — no restrictions at all.
  • PSA validates pods, not Deployments: under enforce the Deployment is accepted and the failure appears as FailedCreate events nobody is watching.
  • That is why warn matters: it returns the exact list of required fields on the object you applied, without breaking anything.
  • Roll out as warn+audit → fix → baseline → restricted, and pin enforce-version so an upgrade cannot tighten rules under you.
  • restricted requires runAsNonRoot, allowPrivilegeEscalation: false, capabilities.drop: [ALL] and seccompProfile: RuntimeDefault — verified as CapEff 0, NoNewPrivs 1, Seccomp 2.
  • hostPath: / read other pods' mounted Secrets and the kubelet's identity from a ServiceAccount whose only permission was create pods.
  • privileged: true and a mounted daemon socket are equally complete takeovers, and one baseline label blocked all three.
  • Infrastructure that genuinely needs those belongs in its own privileged namespace with tight RBAC — an auditable exception rather than a cluster-wide weakening.
  • PSA cannot require resource limits, ban :latest, enforce registries or signatures, restrict which ServiceAccount a pod uses, or mutate — a policy engine does those.
  • Restricting the ServiceAccount closes the escalation path neither RBAC nor PSA can express.
  • Mutating webhooks run before validating ones, so an injected sidecar requiring NET_ADMIN got a compliant pod rejected for a container its author never wrote.
  • Used deliberately, that ordering makes legacy workloads compliant: mutating the four restricted fields in meant a bare kubectl run succeeded under enforcement.
  • --dry-run=client never sees the mutated object; --dry-run=server is the only valid check.
  • A tenant boundary needs RBAC and Pod Security and NetworkPolicy — any one alone leaves a complete path around it.
