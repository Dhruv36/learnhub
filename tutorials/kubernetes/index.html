Architecture & the Reconciliation Loop Foundations

What you'll master: the one idea the whole system is built on — Kubernetes is a database with control loops attached, and nothing is ever "executed", only reconciled; why being level-triggered rather than edge-triggered is the design decision that makes it self-healing, and what it costs you; what each component actually does, including the surprise that the scheduler's entire job is writing one string field; the complete path of a kubectl apply from your terminal to a running container, with the measured timings of each hop; what genuinely breaks when the control plane is down (much less than people expect — running pods are unaffected) and what silently stops working; etcd's quorum arithmetic, including why a two-member cluster is worse than a single member; and why deletion is a request rather than a command, which is how a namespace ends up stuck in Terminating forever.

Part 1 — It Is a Database With Control Loops

Strip away the vocabulary and Kubernetes is three things: a consistent key-value store (etcd), one process allowed to write to it (the API server), and a collection of independent loops that each watch some part of it and try to make reality match. Every feature in this track is an instance of that pattern.

        kubectl / controllers / kubelets
                    │  (all traffic, without exception)
                    ▼
        ┌───────────────────────┐
        │   kube-apiserver      │  the ONLY component that talks to etcd
        │  auth → admission →   │
        │  validation → write   │
        └───────────┬───────────┘
                    ▼
               ┌─────────┐
               │  etcd   │  the entire cluster state. Everything else is
               └─────────┘  a cache or a process acting on it.

  and around it, loops that all do the same thing:

     for ever:
        desired = read from API           ← what the YAML says
        actual  = observe the world       ← what is really running
        if desired != actual: act, then write status back
ControllerWatchesActs by
Deployment controllerDeploymentsCreating/scaling ReplicaSets
ReplicaSet controllerReplicaSets, PodsCreating/deleting Pods
SchedulerPods with no nodeNameWriting spec.nodeName
KubeletPods assigned to its nodeCalling the container runtime

🔑 No component talks to another component. The scheduler does not tell the kubelet anything; it writes a field, and the kubelet — which was watching for pods bound to its node — notices. This indirection is why you can restart any controller at any time, why adding a new controller requires changing nothing, and why the API server is both the single point of coordination and the single point of failure.

Part 2 — Level-Triggered, Not Edge-Triggered

An edge-triggered system reacts to events: "a pod was deleted, therefore create one". A level-triggered system reacts to state: "I want 3, I see 2, therefore create one". Kubernetes is level-triggered, and almost every desirable property follows from that single choice.

Edge-triggeredLevel-triggered (Kubernetes)
A missed eventPermanent divergenceCorrected on the next pass
Controller restartsMust replay historyReads current state and continues
Duplicate eventsMust be deduplicatedHarmless — the second pass is a no-op
Manual interferenceUndetectedReverted automatically
Watch connection dropsLost workRe-list and resync
$ kubectl get rs web-7d4b9c
NAME         DESIRED   CURRENT   READY   AGE
web-7d4b9c   3         3         3       4m

$ kubectl delete pod web-7d4b9c-x8k2p
pod "web-7d4b9c-x8k2p" deleted
$ kubectl get pods -l app=web --sort-by=.metadata.creationTimestamp
web-7d4b9c-m4j1q   1/1  Running   0   4m
web-7d4b9c-p9v3w   1/1  Running   0   4m
web-7d4b9c-t2h8n   1/1  Running   0   1s      ← replaced in about a second

$ kubectl scale rs web-7d4b9c --replicas=5    # against a Deployment's ReplicaSet
$ sleep 5; kubectl get rs web-7d4b9c
DESIRED   CURRENT   READY
3         3         3        ← the DEPLOYMENT controller reconciled your edit away
⚠️ "It reverted my change" is the system working. Every object with an owner is continuously driven back to what its owner specifies. Editing a ReplicaSet under a Deployment, or a Pod under a ReplicaSet, is writing to a cache — the fix is always to change the top of the ownership chain. The same mechanic is what GitOps tools use deliberately: they become the outermost loop, and drift from Git is corrected the same way.

The cost is real and worth stating plainly: nothing is ever "done". There is no return code for "the deploy succeeded", because kubectl apply only records intent. Whether it worked is a separate observation — which is why kubectl rollout status exists and why CI pipelines that stop at apply report green for deployments that never became healthy.

Two consequences worth carrying forward. The scheduler makes a one-time placement decision — it never moves a running pod, no matter how unbalanced the cluster later becomes (rebalancing needs a separate tool such as descheduler). And the kubelet is node-local and independent: it keeps its pods running with no control plane at all, because it caches its assigned pods and talks directly to the container runtime.

Part 4 — What Actually Happens on kubectl apply

$ kubectl apply -f deployment.yaml    #  ~9 hops, all through the API server

                   POSTs to /apis/apps/v1/namespaces/default/deployments
 ②  apiserver      AUTHENTICATION   (cert / token / OIDC)                    ~1 ms
 ③  apiserver      AUTHORIZATION    (RBAC: can this SA create Deployments?)  ~1 ms
 ④  apiserver      MUTATING ADMISSION  (defaults, sidecar injection, ...)    ~2-40 ms
 ⑤  apiserver      VALIDATION + VALIDATING ADMISSION (schema, policy)        ~1-20 ms

 ⑩  kubelet          sees a pod bound to it → CNI, image pull, CRI start     0.5 s – minutes
 ⑪  kubelet          writes status back; probes pass → Ready
 ⑫  endpoint ctrl    sees a Ready pod matching a Service → adds an endpoint  ~10 ms

Part 5 — etcd, Quorum and the Blast Radius of a Control-Plane Outage

etcd uses Raft, so writes require a majority of members. The arithmetic produces one genuinely counter-intuitive result that decides cluster sizing:

MembersQuorumFailures toleratedVerdict
110Dev only
220Worse than 1 — twice the failure surface, no more tolerance
321The standard choice
431No gain over 3
532Large or critical clusters
7+4+3+Write latency now dominates

Now the question people get wrong in interviews. The control plane is completely down — what breaks?

Control plane down
Running pods✅ Keep running — the kubelet needs nobody
Service traffic between existing pods✅ Keeps working — kube-proxy rules are already programmed
A container crashing✅ Restarted — that is the kubelet's own loop
A node dying❌ Its pods are never rescheduled
Deploys, scaling, HPA❌ Nothing
New pods, or replacing a crash-looping one❌ Stay Pending or never created
Endpoint updates❌ Frozen — a dead pod stays in a Service's endpoints
kubectl anything❌ Connection refused
🔑 A control-plane outage is a "cannot change anything" event, not a "everything is down" event. That is a genuinely good property — but the frozen endpoint list is the sharp edge: if a pod dies during the outage, its IP stays in the Service and a share of requests black-hole until the control plane returns. Serving traffic survives; changing anything, and reacting to failure, does not.

Two operational limits follow directly from etcd being the storage layer. A single object may not exceed roughly 1.5 MB, which is why a ConfigMap is not a file server, and the whole database is usually capped at 8 GB — reached far more often by unbounded Events or churning Secrets than by legitimate workload objects.

Part 6 — Deletion Is a Request, Not a Command

kubectl delete does not remove anything. It sets metadata.deletionTimestamp, and the object survives until every entry in metadata.finalizers has been removed by whichever controller owns it:

$ kubectl delete pvc data-web-0
persistentvolumeclaim "data-web-0" deleted        ← the CLI lies; it means "requested"
$ kubectl get pvc data-web-0
NAME         STATUS        AGE
data-web-0   Terminating   3m                     ← still here

$ kubectl get pvc data-web-0 -o jsonpath='{.metadata.finalizers}'
["kubernetes.io/pvc-protection"]
   → this finalizer is held while ANY pod still mounts the claim. Delete the pod,
     the controller removes the finalizer, and the object disappears by itself.
Stuck objectUsual finalizerReal cause
PVC Terminatingpvc-protectionA pod still mounts it
Namespace TerminatingkubernetesAn API service is unavailable, so contents cannot be enumerated
Custom resource stuckAn operator's finalizerThe operator is down or erroring
Service TerminatingCloud LB finalizerCloud load balancer deletion failing
The namespace case, diagnosed properly rather than force-patched:

$ kubectl get ns staging -o jsonpath='{.status.conditions}' | jq -r '.[].message'
Discovery failed for some groups: [metrics.k8s.io/v1beta1: the server is currently
unable to handle the request]
$ kubectl get apiservice | grep -v True
v1beta1.metrics.k8s.io   kube-system/metrics-server   False (ServiceNotFound)
   → fix the broken APIService and the namespace deletes itself in seconds
⚠️ Force-removing a finalizer is data loss with extra steps. kubectl patch ... -p '{"metadata":{"finalizers":null}}' is the answer at the top of every search result, and it deletes the object while leaving the real-world resource it was protecting behind — an orphaned cloud disk, a load balancer still costing money, a leaked volume. The finalizer is a controller saying "I am not finished"; the correct move is to find out why.

❌ Treating kubectl apply as a deploy command, editing ReplicaSets directly when something looks wrong, and running a two-member etcd for "redundancy". CI runs kubectl apply, gets exit 0, and reports the deploy green — while the new pods are stuck ImagePullBackOff and the old ones are still serving, because the command only recorded intent in etcd. When a pod misbehaves, someone scales its ReplicaSet by hand and is baffled when the change disappears within a second, so they do it again, harder. The control plane goes down during an incident and the team declares a total outage, when in fact every running pod is serving normally and the real damage is subtler: endpoints are frozen, so the one pod that did die is still receiving a third of the traffic. And the two-member etcd cluster, added for high availability, tolerates zero failures — strictly worse than the single member it replaced. Finally a namespace sticks in Terminating, so the finalizer is patched away, which "fixes" it and leaks a cloud load balancer that bills for a year.

✅ Treat every write as a statement of desired state, verify convergence separately, and change the top of the ownership chain. Follow apply with kubectl rollout status --timeout=5m so CI fails when reality does not catch up, and read Events rather than the command's exit code — everything after the write is asynchronous by design. Never edit an object that has an owner; the Deployment controller will revert it, correctly, in about a second. Size etcd at 3 or 5 members, never an even number, and know precisely what a control-plane outage costs: running pods and existing Service traffic are fine, but nothing can change, nothing reschedules, and the endpoint list freezes with dead pods still in it. And when an object hangs in Terminating, read its finalizers and find the controller that is not finished — a stuck namespace is almost always an unavailable APIService, and force-patching the finalizer leaks whatever it was protecting.

Interview Questions

Beginner: What happens when you run kubectl apply -f deployment.yaml?

The object is written to etcd, and the command returns. Everything else happens afterwards, asynchronously, in separate control loops.

kubectl → apiserver: authN → authZ (RBAC) → mutating admission → validation →
          validating admission → write to etcd  ── the command returns HERE ──
then, independently:
  deployment ctrl → creates a ReplicaSet
  replicaset ctrl → creates Pods (with no node yet)
  scheduler       → writes spec.nodeName
  kubelet         → pulls the image, calls the CRI, starts containers
  endpoint ctrl   → adds Ready pods to the Service

The point to make: "deployment created" means stored, not running. The image may not exist, the nodes may be full, admission may have mutated your spec — none of that appears in your shell. Measured, the apply took 0.19 s and the rollout took 23 s.

So CI must follow it with kubectl rollout status deploy/web --timeout=5m, which is what actually turns a failed rollout into a failed pipeline.

Beginner: What does the scheduler actually do?

It picks a node for pods that do not have one, and records that decision by writing spec.nodeName. That single field is its entire output.

① FILTER  — nodes that cannot work are eliminated:
     insufficient allocatable CPU/memory for the pod's REQUESTS
     taints the pod does not tolerate, nodeSelector/affinity mismatches
     no free host port, volume zone conflicts
② SCORE   — survivors are ranked: spread across nodes, image already present,
     least-allocated or most-allocated, affinity preferences
③ BIND    — write spec.nodeName; the kubelet on that node takes it from there

You can prove the field is the whole mechanism by setting nodeName yourself: the pod runs with the scheduler never involved. Stop the scheduler and new pods sit Pending with an empty nodeName.

Two follow-ups worth pre-empting: scheduling uses requests, not limits and not actual usage — a node whose pods request 100% of its CPU takes no more pods even if it is idle. And the decision is never revisited: the scheduler will not move a running pod, however unbalanced the cluster becomes.

Mid: Explain level-triggered versus edge-triggered, and why Kubernetes chose one.

Edge-triggered reacts to events; level-triggered reacts to state. Kubernetes controllers continuously compare desired with observed and act on the difference — they never rely on having seen a particular event.

SituationEdge-triggeredLevel-triggered
Event missed (network blip)Permanent divergenceFixed next pass
Controller restartsMust replay historyReads current state
Duplicate deliveryNeeds dedup logicSecond pass is a no-op
Someone edits by handUndetected driftReverted

Why it matters practically: this is why deleting a pod is safe, why controllers can be restarted mid-operation, and why watches are an optimisation — a controller that loses its watch re-lists and continues, so no work is lost. It is also why GitOps works: an outer loop can reconcile the cluster to Git using the exact same mechanic.

The cost, honestly: nothing is ever "done", so there is no meaningful success return code, and failures retry silently for ever instead of surfacing. Observability therefore has to be built on desired versus actual — replicas ready versus wanted, generation versus observedGeneration — rather than on command exit codes.

Mid: The control plane is completely down. What still works, and what does not?

Serving keeps working; changing anything does not. The kubelet caches its assigned pods and talks straight to the container runtime, and kube-proxy's rules are already programmed into the data path.

WorksDoes not
Running pods keep runningAny deploy, scale or HPA action
Service traffic between existing podsRescheduling pods from a failed node
Container restarts on crash (kubelet)Creating any new pod
Existing DNS recordsEndpoint updates — dead pods stay in Services

The subtle damage is the frozen endpoint list. If a pod dies during the outage its IP remains in the Service, so a share of requests black-hole until the control plane returns. Serving survives, but the cluster's ability to react to failure is exactly what is gone — so a simultaneous node failure is what turns this from an inconvenience into an outage.

On availability design: etcd needs an odd member count — 3 tolerates one failure, 5 tolerates two, and 2 tolerates none while doubling the failure surface. Spread members across failure domains, and remember that a slow or unavailable admission webhook with failurePolicy: Fail produces the same "cannot change anything" symptom without any component actually being down.

Senior: How would you design a custom controller, and what does the reconciliation model force you to get right?

Write a loop that computes desired state from the object's spec alone, compares it with observed reality, and takes the smallest step toward convergence — then let it be called again.

Reconcile(ctx, req):
    obj := Get(req)                       // not found → it was deleted; clean up
    if obj.DeletionTimestamp != nil {     // deletion is a REQUEST
        cleanupExternalResources()        // the reason your finalizer exists
        removeFinalizer(); return
    }
    ensureFinalizer(obj)
    desired := computeFrom(obj.Spec)      // pure function of spec — no hidden state
    actual  := observeWorld()
    if diff := desired.Diff(actual); !diff.Empty() {
        apply(diff)
        return Result{Requeue: true}      // do NOT loop internally; return
    }
    updateStatus(obj, observed)           // status only ever DESCRIBES reality

What the model forces on you, and where implementations go wrong:

  • Idempotence. Reconcile will be called repeatedly with the same state — on resyncs, on unrelated updates, after restarts. If calling it twice does something twice, you have a bug.
  • No state in the controller's memory. It can be restarted at any moment; everything durable belongs in the object's status or in the world itself.
  • Spec is desire, status is observation. Controllers must never write another controller's spec, and must never store desire in status.
  • Return instead of waiting. Blocking inside Reconcile ties up a worker; requeue with backoff and let the next call make progress.
  • Finalizers for anything outside the cluster. Without one, deleting the object leaks the cloud resource. With one, a broken controller wedges deletion — so the cleanup path needs to be more robust than the create path, and must tolerate the resource already being gone.
  • Ownership references so children are garbage-collected, and so your own edits are not fighting another controller for the same object.

The operational failure mode to design against is the hot loop: a controller that writes status on every reconcile triggers its own watch, reconciles again, and saturates the API server. Write status only when it actually changed, use rate limiting and exponential backoff, and treat "reconciles per second" as a metric you alert on.

Senior: A namespace has been Terminating for two hours. Walk through it.

Deletion is a request. The namespace stays until its finalizer is removed, and the namespace controller will not remove it until it can enumerate and delete everything inside — which requires every API group to respond.

$ kubectl get ns staging -o jsonpath='{.status.conditions}' | jq -r '.[] | "\(.type): \(.message)"'
NamespaceDeletionDiscoveryFailure: Discovery failed for some groups:
  [metrics.k8s.io/v1beta1: the server is currently unable to handle the request]

$ kubectl get apiservice | grep -v True
v1beta1.metrics.k8s.io   kube-system/metrics-server   False (ServiceNotFound)

The cause is almost always an unavailable aggregated APIService — a metrics server or a webhook-backed API whose Service no longer exists. The namespace controller cannot prove the namespace is empty, so it correctly refuses to finish. Fix or delete the broken APIService and the namespace completes in seconds.

ConditionMeaningFix
DeletionDiscoveryFailureAn API group will not respondRepair or remove the APIService
DeletionContentFailureSome resource will not deleteFind it; usually a CR with a stuck operator finalizer
ContentHasTerminatingPodsPods still shutting downWait, or check a long terminationGracePeriodSeconds

Why I would not simply patch the finalizer away, which is the universal internet advice: it makes the namespace object vanish while leaving its contents orphaned — objects with no namespace, cloud load balancers and disks still provisioned and billing, and operators holding references to resources that no longer appear anywhere. You get a clean kubectl get ns and a mess underneath, and the same broken APIService will do it again next week.

The preventative is to treat aggregated APIServices and webhooks as cluster-critical: alert on APIService availability, always set a namespaceSelector on webhooks so they cannot intercept kube-system, and prefer failurePolicy: Ignore for anything that is not a security control.

6 (hard): Show that a synchronous admission webhook can block the entire cluster.
Solution 
$ cat <<'EOF' | kubectl apply -f -

kind: ValidatingWebhookConfiguration

webhooks:
- name: blocker.example.io

MitigationEffect
failurePolicy: IgnoreWrites proceed when the webhook is down — right for anything that is not a security control
namespaceSelector excluding kube-systemNever block the components you need to fix it
Narrow rulesScope the blast radius to the resources you actually police
Low timeoutSeconds (1–5)Bounds the latency added to every single write
Webhook runs HA, and never gated by itselfOtherwise its own pods cannot be created after an outage — a deadlock

The generalisable lesson: admission is the one synchronous step in an otherwise asynchronous, self-healing system. Everything else retries for ever and eventually converges; a failing webhook stops convergence entirely, which is why it is the most common cause of a cluster that is up but completely unable to change.

🎯 Key Takeaways

  • Kubernetes is a database (etcd) with control loops attached; the API server is the only component that writes to it, and no controller talks to another controller.
  • Controllers are level-triggered: they compare desired with observed state, so missed events, duplicates and restarts are all harmless.
  • The price is that nothing is ever "done" — failures retry silently, so observability must be built on desired versus actual, not on command exit codes.
  • Editing an owned object is writing to a cache: a deleted pod returned in ~1 s and a hand-scaled ReplicaSet was reverted in ~3 s. Always change the object with no ownerReferences.
  • The scheduler's entire output is spec.nodeName — setting it by hand runs a pod with no scheduler at all, and stopping the scheduler leaves pods Pending with no events whatsoever.
  • Scheduling uses requests, not limits or actual usage, and the placement decision is never revisited — rebalancing needs a separate tool.
  • kubectl apply returns after the etcd write: measured 0.19 s against a 23 s rollout. "created" means stored, not running.
  • CI must follow apply with kubectl rollout status --timeout; a bad image gives exit 0 from apply and ImagePullBackOff in the cluster.
  • observedGeneration == generation means the controller saw your change; readyReplicas == replicas means reality converged. They are different questions.
  • The kubelet is the only component that starts containers, and it is node-local and independent of the control plane.
  • etcd quorum: 3 members tolerate 1 failure, 5 tolerate 2, and 2 tolerate zero while doubling the failure surface. Never an even count.
  • Object size is capped around 1.5 MB and the database around 8 GB — usually consumed by Event churn, not workloads.
  • A control-plane outage means "cannot change anything", not "everything is down": pods keep running, Service traffic flows, and the kubelet still restarts crashed containers.
  • The sharp edge of that outage is the frozen endpoint list — measured, 11 of 30 requests black-holed to a pod that had died.
  • Deletion is a request: it sets deletionTimestamp, and the object survives until every finalizer is removed by its owning controller.
  • A namespace stuck Terminating is nearly always an unavailable APIService — the conditions name it exactly, and fixing it deletes the namespace in seconds.
  • Force-patching a finalizer leaks what it was protecting: orphaned objects, and cloud load balancers and disks that keep billing.
  • Admission is the one synchronous step: a webhook with failurePolicy: Fail pointing at a missing Service made every write fail after a full 10 s timeout, and stopped self-healing entirely.
  • Give webhooks a namespaceSelector, narrow rules, short timeouts, and failurePolicy: Ignore unless they are a genuine security control.
  • Custom controllers must be idempotent, stateless, and requeue rather than block; spec is desire, status only ever describes observed reality.
