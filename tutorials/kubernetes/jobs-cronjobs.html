Jobs, CronJobs & One-shot Work Configuration & State

What you'll master: the two retry mechanisms people constantly conflate — restartPolicy restarts the container, backoffLimit creates new pods — and how choosing wrongly produces either lost logs or a hundred pod objects; the exponential backoff schedule a failing Job actually follows; activeDeadlineSeconds, which is the only thing that stops a hung Job running forever; Indexed completion and the work-queue pattern; podFailurePolicy, which finally lets you tell an application bug from a preempted node; CronJob semantics including concurrencyPolicy and the startingDeadlineSeconds trap that permanently stops a CronJob after 100 missed schedules; why every Job must be idempotent because delivery is at-least-once; and the sidecar that keeps a Job "running" for ever. Prerequisites: Pods, Deployments.

Part 1 — A Job Runs Pods Until They Succeed

apiVersion: batch/v1
kind: Job
metadata: { name: migrate }
spec:
  backoffLimit: 4                 ← how many POD failures before the Job gives up
  activeDeadlineSeconds: 600      ← wall-clock cap on the whole Job
  ttlSecondsAfterFinished: 3600   ← auto-delete an hour after finishing
  template:
    spec:
      restartPolicy: Never        ← or OnFailure; NOT Always (rejected)
      containers:
      - name: migrate
        image: myco/api:1.4.2
        command: ["npm","run","migrate"]
FieldDefaultControls
completions1How many pods must succeed
parallelism1How many run at once
backoffLimit6Pod failures tolerated before the Job fails
activeDeadlineSecondsnoneWall-clock limit; overrides backoffLimit
ttlSecondsAfterFinishednoneAuto-cleanup after completion
completionModeNonIndexedIndexed gives each pod a fixed index
suspendfalsePause without deleting

The two retry mechanisms

restartPolicy: OnFailure         restartPolicy: Never
  the CONTAINER restarts           a NEW POD is created per attempt
  in the same pod                  ↓
  ↓                                job-x8k2p  Error
  job-x8k2p  0/1  CrashLoop        job-p9v3w  Error
             RESTARTS: 4           job-t2h8n  Error
                                   job-m4j1q  Error
  · one pod object                 · one pod object PER attempt
  · logs overwritten each restart  · every attempt's logs preserved
  · faster (no scheduling)         · a fresh node, fresh volumes, fresh IP

$ kubectl create job fail --image=busybox -- sh -c 'echo attempt; exit 1'
$ kubectl patch job fail -p '{"spec":{"backoffLimit":4}}' 2>/dev/null
$ sleep 300; kubectl get pods -l job-name=fail --no-headers | wc -l
5                                ← 1 initial + 4 retries, each its own pod
$ kubectl get job fail -o jsonpath='{.status.conditions[0].type}={.status.conditions[0].reason}{"\n"}'
Failed=BackoffLimitExceeded
🔑 backoffLimit counts pod failures, not container restarts. With restartPolicy: OnFailure a container can restart many times inside one pod without consuming the budget — so a Job can crash-loop far longer than backoffLimit: 4 suggests. Use Never when you want each attempt auditable and the budget honest; OnFailure when retries are cheap and you want to avoid rescheduling.

The retries are not immediate. A failing Job backs off exactly as a container does:

retry delay:  10s → 20s → 40s → 80s → 160s → 320s (capped at 6 minutes)

  a Job with backoffLimit: 6 that fails every time takes
  10+20+40+80+160+320 ≈ 10.5 minutes before it reports Failed
  → alerting on "job failed" is inherently delayed; alert on duration too

  completions: 6

  completionMode: Indexed

    spec:

$ kubectl get pods -l job-name=shards -o custom-columns=\
NAME:.metadata.name,INDEX:.metadata.annotations.batch\\.kubernetes\\.io/job-completion-index
NAME             INDEX
shards-0-x8k2p   0
shards-1-p9v3w   1
shards-2-t2h8n   2                ← the index is stable and in the pod NAME

Indexed Jobs are the right tool whenever work partitions deterministically — sharded reprocessing, per-day backfills, per-region exports — because each pod can compute its own slice with no coordinator and no queue. The work-queue pattern is for the opposite case, where items arrive from an external queue and workers are interchangeable.

Part 3 — Distinguishing Your Bug From the Cluster's

By default every pod failure is equal: an application exception, an OOM kill, and a node preemption all consume one unit of backoffLimit. podFailurePolicy separates them:

spec:
  backoffLimit: 3
  podFailurePolicy:
    rules:
    - action: FailJob               ← stop immediately; retrying cannot help
      onExitCodes: { containerName: main, operator: In, values: [42] }
    - action: Ignore                ← do NOT count against backoffLimit
      onPodConditions:
      - { type: DisruptionTarget }  ← preemption, node drain, eviction
    - action: Count
      onExitCodes: { containerName: main, operator: In, values: [1] }
ActionEffectUse for
FailJobFail the whole Job nowBad input, invalid config — retrying is pointless
IgnoreRetry without consuming the budgetPreemption, node drain, spot reclaim
CountThe defaultGenuine application failures
⚠️ Without this, a long Job on spot instances can never finish. Each preemption consumes a retry, so a six-hour job with backoffLimit: 6 fails after six interruptions that had nothing to do with the code. Ignore on DisruptionTarget is what makes batch work viable on preemptible capacity.

Part 4 — CronJob: Schedules and the 100-Miss Trap

apiVersion: batch/v1
kind: CronJob
metadata: { name: nightly }
spec:
  schedule: "0 3 * * *"
  timeZone: "Europe/London"          ← without this: UTC (DST bugs twice a year)
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  suspend: false
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 3600
      template:
        spec:
          restartPolicy: Never
          containers: [{ name: c, image: myco/nightly }]
concurrencyPolicyIf the previous run is still goingUse for
Allow (default)Start anyway — overlapping runsIndependent, idempotent work
ForbidSkip this occurrence entirelyAnything touching shared state
ReplaceKill the running Job, start a new oneOnly the latest result matters
THE TRAP: startingDeadlineSeconds and 100 missed schedules

  The CronJob controller counts missed schedules since the last run. If it counts
  more than 100 it gives up PERMANENTLY and logs:

$ kubectl -n kube-system logs -l component=kube-controller-manager | grep -i cronjob
Cannot determine if job needs to be started: too many missed start times (> 100).
Set or decrease .spec.startingDeadlineSeconds or check clock skew

$ kubectl get cronjob nightly
NAME      SCHEDULE    SUSPEND   ACTIVE   LAST SCHEDULE
nightly   */5 * * * *  False    0        <none>          ← never runs again
🔑 A control-plane outage longer than 100 schedule intervals silently kills the CronJob. At */5 that is 8 hours; at * * * * * it is 100 minutes. Setting startingDeadlineSeconds bounds the look-back window, so only misses within that window are counted and the controller resumes normally. Every CronJob should set it — a value slightly larger than one interval is usually right.

Two more schedule facts worth knowing. Without timeZone, schedules run in the controller's time zone (UTC on managed clusters), which is why "the 3am job ran at 4am" appears twice a year. And a CronJob guarantees at least one run per schedule, not exactly one — which brings us to idempotency.

Part 5 — At-Least-Once, and Idempotency

Ways one logical execution becomes two:

  · the node running the pod dies mid-job → the Job creates a replacement
  · concurrencyPolicy: Allow and a slow run overlaps the next schedule
  · a controller restart re-evaluates a schedule at the boundary
  · someone re-runs it manually after a partial failure

  → EVERY Job must be safe to run twice. This is not optional.
Non-idempotent workMade idempotent by
"Send invoice emails"A sent_at column, checked and set transactionally
"Charge every pending order"An idempotency key per charge
"Increment a counter"Recompute from source, or a per-run dedup key
"Apply migration 007"A migrations table plus an advisory lock
"Delete records older than 30 days"Naturally idempotent — safe
For a true singleton, the Job takes a lock itself:

  BEGIN;
  SELECT pg_try_advisory_xact_lock(4815162342);   -- false ⇒ another run holds it
  ...work...
  COMMIT;                                          -- lock released automatically

  Kubernetes cannot give you exactly-once. Coordination belongs in the workload,
  and concurrencyPolicy: Forbid is a convenience, not a guarantee.

Part 6 — Sidecars, Cleanup and Monitoring

A pod is Succeeded only when all containers exit. An ordinary sidecar — a mesh proxy, a log shipper, a metrics agent — never exits, so the Job never completes. This is covered in full in Pods; the fix is a native sidecar:

spec:
  template:
    spec:
      initContainers:
      - { name: proxy, image: envoyproxy/envoy, restartPolicy: Always }   ← native sidecar
      containers:
      - { name: work, image: myco/batch }
ConcernMechanism
Finished Jobs accumulatingttlSecondsAfterFinished; CronJob history limits
Hung JobsactiveDeadlineSeconds — the only real timeout
Pausing without deletingsuspend: true
Manual run of a CronJobkubectl create job --from=cronjob/nightly manual-1
Alertingkube_job_failed, and time since last success
$ kubectl get jobs -A --no-headers | wc -l
1847                             ← two years of nightly runs, all in etcd
$ kubectl patch cronjob nightly -p '{"spec":{"successfulJobsHistoryLimit":3,"failedJobsHistoryLimit":3}}'
$ sleep 60; kubectl get jobs -l cronjob=nightly --no-headers | wc -l
6
⚠️ Alert on "time since last success", not on "a job failed". A failed Job fires an alert; a CronJob that stopped scheduling — suspended, hit the 100-miss trap, or had its schedule broken — fires nothing at all, because nothing is failing. The silent-stop failure mode is far more common and far more damaging than a noisy failure.

❌ A nightly CronJob with the default concurrencyPolicy: Allow, no startingDeadlineSeconds, no activeDeadlineSeconds, non-idempotent work, a mesh sidecar, and alerting only on failure. A slow run overlaps the next schedule, so two jobs process the same queue simultaneously and customers receive duplicate invoices. One run hangs on a network call and stays Active for eleven days, holding a database connection and blocking nothing visibly. A three-hour control-plane upgrade means more than 100 missed */1 schedules, so the controller gives up permanently — and because nothing failed, no alert fires and nobody notices for a fortnight. The Envoy sidecar means every Job pod shows 1/2 Running for ever, so Completions stays at 0/1 and Forbid would have blocked every subsequent run anyway. And two years of Job objects accumulate in etcd because nothing ever cleans them up.

✅ Bound every dimension, make the work idempotent, and alert on absence rather than failure. Set concurrencyPolicy: Forbid for anything touching shared state, but treat it as a convenience rather than a guarantee — delivery is at-least-once, so the work itself must be safe to run twice, with an idempotency key or an advisory lock doing the real coordination. Always set startingDeadlineSeconds so a control-plane outage cannot silently retire the CronJob after 100 missed schedules, and timeZone so schedules do not drift with DST. Give every Job an activeDeadlineSeconds, which is the only mechanism that stops a hung run, and ttlSecondsAfterFinished plus history limits so finished objects do not accumulate in etcd. Declare sidecars as init containers with restartPolicy: Always so the Job can actually complete. Use podFailurePolicy to ignore DisruptionTarget failures, or batch work on spot capacity exhausts its retry budget on preemptions. And alert on time since last success — a CronJob that silently stopped scheduling produces no failures to alert on.

Interview Questions

Beginner: What is the difference between a Job and a Deployment?

A Deployment keeps pods running; a Job runs pods until they succeed and then stops.

DeploymentJob
GoalN pods always runningN pods successfully completed
restartPolicyAlwaysNever or OnFailure
Pod exits 0RestartedCounted as success
EndsNeverWhen completions is met

Use a Job for: database migrations, backfills, batch processing, one-off imports. A CronJob is a Job on a schedule.

The follow-up worth pre-empting: why not run a migration as an init container in the Deployment? Because every replica runs it concurrently — ten pods racing the same schema. A Job runs once, and dependents gate on service_completed_successfully.

Beginner: A Job keeps creating new pods that fail. How do you control that?

Two independent knobs, and they do different things.

restartPolicy: Never      → each attempt is a NEW POD (logs preserved per attempt)
restartPolicy: OnFailure  → the CONTAINER restarts inside one pod (logs overwritten)

backoffLimit: 4           → how many POD failures before the Job is marked Failed

With Never and backoffLimit: 4 you get 5 pod objects: the initial attempt plus four retries. That is often mistaken for a runaway loop and is exactly the configured behaviour.

The nuance: backoffLimit counts pod failures. With OnFailure, a container can restart many times inside one pod without consuming the budget, so the Job can crash-loop for much longer than the number suggests.

Retries are also delayed — 10s, 20s, 40s, 80s, 160s, capped at six minutes — so a Job with the default backoffLimit: 6 takes over ten minutes to report failure. activeDeadlineSeconds is the wall-clock cap that overrides all of it.

Mid: A CronJob stopped running and nothing failed. What happened?

Most likely the 100-missed-schedules trap. The controller counts missed start times since the last run; above 100 it gives up permanently.

$ kubectl -n kube-system logs -l component=kube-controller-manager | grep -i cronjob
Cannot determine if job needs to be started: too many missed start times (> 100).
Set or decrease .spec.startingDeadlineSeconds or check clock skew
$ kubectl get cronjob nightly
nightly   */5 * * * *   False   0   <none>        ← LAST SCHEDULE is empty for ever

At */5 that is an 8-hour outage; at * * * * * only 100 minutes. Setting startingDeadlineSeconds bounds the look-back window so only recent misses count.

Other silent-stop causesCheck
suspend: truekubectl get cronjob SUSPEND column
Schedule edited incorrectlyCron syntax; UTC vs timeZone
Forbid with a stuck previous JobAn Active Job that never ends
Clock skew on the control planeNTP

The lesson for monitoring: alert on time since last success. Every one of those causes produces silence, not failure, so failure-based alerting never fires.

Mid: Why must every Job be idempotent?

Because Kubernetes guarantees at-least-once, never exactly-once.

Duplication routeMechanism
Node dies mid-runThe Job creates a replacement pod; the original may have partly completed
concurrencyPolicy: AllowA slow run overlaps the next schedule
Controller restart at a boundaryThe schedule is re-evaluated
Manual re-runSomeone retries after a partial failure

The first is the important one: a partitioned node's pod may still be running and writing while the replacement starts — the same problem as force-deleting a StatefulSet pod.

Making work idempotent means a dedup key checked and set in the same transaction as the effect: a sent_at column, an idempotency key on the payment API, a migrations table plus a pg_try_advisory_lock. concurrencyPolicy: Forbid reduces the probability of overlap and guarantees nothing — coordination has to live in the workload.

Senior: Design the batch layer for a platform with nightly reports, migrations and spot-instance processing.

Three workloads with genuinely different failure semantics, so three configurations.

Nightly reportsMigrationsSpot batch
ObjectCronJobJob, per releaseIndexed Job
ConcurrencyForbidAdvisory lockparallelism: 20
backoffLimit20 — fail loudly6
podFailurePolicy—FailJob on bad inputIgnore on DisruptionTarget
Deadline4h10m12h
Alert onTime since last successFailure, immediatelyCompletion rate

The spot row is where podFailurePolicy earns its place: without it a preemption consumes a retry, so a long job on preemptible capacity fails after six interruptions that had nothing to do with the code. Ignore on DisruptionTarget is what makes batch work on spot viable at all.

Migrations deserve their own treatment: backoffLimit: 0, because a half-applied migration retried automatically is worse than a stopped deploy; an advisory lock so concurrent deploys cannot race; and gating dependents with service_completed_successfully rather than running them as init containers, which would have every replica racing the same schema.

Platform-wide I would enforce ttlSecondsAfterFinished and history limits so etcd does not accumulate thousands of Job objects, startingDeadlineSeconds and timeZone on every CronJob, and a dashboard keyed on last success time — because every serious CronJob failure mode is silence rather than an error.

Senior: How do you run database migrations safely in Kubernetes?

A separate Job with a lock, gated ahead of the application, and written so both schema versions work simultaneously.

ApproachProblem
Init container in the DeploymentEvery replica runs it concurrently
Application entrypointSame, plus it runs on every restart
Helm pre-install hookBetter — but a hook failure can leave the release wedged
A Job, gated on completionThe right shape

What the Job itself needs: backoffLimit: 0 so a half-applied migration is not retried blindly; an advisory lock so two concurrent deploys serialise; an activeDeadlineSeconds so a lock wait cannot hang for ever; and a migrations table making re-runs safe, since the pod may be replaced mid-run.

The harder half is not Kubernetes at all. A rolling update runs both versions simultaneously, so every migration must be backward compatible for the duration — expand/contract across releases: add the column, deploy code writing both, backfill, deploy code reading the new one, and only then drop the old column in a later release. A migration that drops a column in the same release that stops using it breaks the pods still serving, as demonstrated in Deployments.

What I would not do: run migrations automatically on every pod start. It looks convenient, races on every scale-up, and turns a routine restart during an incident into a schema change nobody authorised.

5 (hard): Make batch work survive spot preemption with podFailurePolicy.
Solution 
WITHOUT a policy — preemptions burn the retry budget:
$ kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata: { name: naive }
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never
      containers: [{ name: c, image: busybox, command: ['sh','-c','sleep 600'] }]
EOF

$ for i in 1 2 3 4; do
    sleep 20
    POD=$(kubectl get pods -l job-name=naive -o name --field-selector=status.phase=Running | head -1)
    kubectl delete $POD --wait=false      # simulate a preemption/eviction
  done
$ sleep 30; kubectl get job naive -o jsonpath='{.status.conditions[0].type}={.status.conditions[0].reason}{"\n"}'
Failed=BackoffLimitExceeded
$ kubectl get job naive -o jsonpath='failed={.status.failed}{"\n"}'
failed=4
   → the code never ran wrong once; four infrastructure events killed the Job

WITH podFailurePolicy:
$ kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata: { name: resilient }
spec:
  backoffLimit: 3
  podFailurePolicy:
    rules:
    - action: Ignore                       ← do not count disruptions
      onPodConditions: [{ type: DisruptionTarget }]
    - action: FailJob                      ← unrecoverable input: stop now
      onExitCodes: { containerName: c, operator: In, values: [42] }
  template:
    spec:
      restartPolicy: Never
      containers: [{ name: c, image: busybox, command: ['sh','-c','sleep 600'] }]
EOF

$ for i in $(seq 1 6); do
    sleep 20
    POD=$(kubectl get pods -l job-name=resilient -o name --field-selector=status.phase=Running | head -1)
    kubectl delete $POD --wait=false
  done
$ kubectl get job resilient -o jsonpath='failed={.status.failed} active={.status.active}{"\n"}'
failed=0 active=1
   ↑ SIX disruptions, zero counted, the Job is still going
$ kubectl get pods -l job-name=resilient -o json \
    | jq -r '.items[] | select(.status.phase=="Failed") |
             "\(.metadata.name) \([.status.conditions[]|select(.type=="DisruptionTarget")|.reason][0])"' | head -2
resilient-x8k2p   DeletionByKubelet
resilient-p9v3w   DeletionByKubelet        ← recognised as disruptions

6 (hard): Build a safe migration Job and monitoring for silent CronJob failure.
Solution 
THE MIGRATION JOB:
$ kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata: { name: migrate-1-4-2 }          # versioned name: immutable, auditable
spec:
  backoffLimit: 0                          # never retry a half-applied migration
  activeDeadlineSeconds: 600               # a lock wait cannot hang for ever
  ttlSecondsAfterFinished: 86400
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: migrate
        image: postgres:16-alpine
        env: [{ name: PGPASSWORD, valueFrom: { secretKeyRef: { name: db, key: password } } }]
        command:
        - sh
        - -c
        - |
          set -e
          psql -h db -U app -d shop -v ON_ERROR_STOP=1 <<'SQL'
          BEGIN;
          SELECT pg_advisory_xact_lock(4815162342);            -- serialise deploys
          CREATE TABLE IF NOT EXISTS schema_migrations(version text primary key);
          DO $$
          BEGIN
            IF NOT EXISTS (SELECT 1 FROM schema_migrations WHERE version='1.4.2') THEN
              ALTER TABLE orders ADD COLUMN first_name text;   -- ADDITIVE only
              INSERT INTO schema_migrations VALUES ('1.4.2');
              RAISE NOTICE 'applied 1.4.2';
            ELSE
              RAISE NOTICE 'already applied — no-op';
            END IF;
          END $$;
          COMMIT;
          SQL
EOF
$ kubectl wait --for=condition=complete job/migrate-1-4-2 --timeout=10m
job.batch/migrate-1-4-2 condition met
$ kubectl logs -l job-name=migrate-1-4-2 | grep NOTICE
NOTICE:  applied 1.4.2

Prove it is safe to run twice (a node failure mid-run does exactly this):
$ kubectl delete job migrate-1-4-2 && kubectl apply -f migrate.yaml
$ kubectl wait --for=condition=complete job/migrate-1-4-2 --timeout=5m
$ kubectl logs -l job-name=migrate-1-4-2 | grep NOTICE
NOTICE:  already applied — no-op         ← idempotent

And that concurrent deploys serialise rather than race:
$ for i in 1 2 3; do kubectl create job "m-$i" --from=job/migrate-1-4-2 & done; wait
$ sleep 30; kubectl logs -l job-name -c migrate --tail=1 --prefix | grep -c 'already applied'
2                                        ← one applied, two no-ops, none corrupted

MONITORING — the alert that actually catches silent failure:
$ cat > tools/cron-health.sh <<'SH'
#!/usr/bin/env bash
# Alert on TIME SINCE LAST SUCCESS, not on failure. Exit 1 if any CronJob is stale.
set -uo pipefail
FAIL=0
now=$(date +%s)
kubectl get cronjob -A -o json | jq -r '.items[] |
  "\(.metadata.namespace) \(.metadata.name) \(.spec.schedule) \(.spec.suspend) \(.status.lastSuccessfulTime // "never")"' |
while read -r ns name sched susp last; do
  # crude expected interval: minutes field only
  case "$sched" in
    "* * * * *")   max=300   ;;
    "*/5 * * * *") max=1200  ;;
    "0 * * * *")   max=7200  ;;
    *)             max=172800 ;;
  esac
  if [ "$susp" = "true" ]; then
    printf '  SUSPENDED %s/%s\n' "$ns" "$name"; FAIL=1; continue
  fi
  if [ "$last" = "never" ]; then
    printf '  NEVER-RAN %s/%s (%s)\n' "$ns" "$name" "$sched"; FAIL=1; continue
  fi
  age=$(( now - $(date -d "$last" +%s) ))
  if [ "$age" -gt "$max" ]; then
    printf '  STALE     %s/%s last success %ss ago (max %ss)\n' "$ns" "$name" "$age" "$max"
    FAIL=1
  else
    printf '  OK        %s/%s last success %ss ago\n' "$ns" "$name" "$age"
  fi
done
exit $FAIL
SH
$ chmod +x tools/cron-health.sh && tools/cron-health.sh
  OK        default/nightly last success 1204s ago
  STALE     default/frequent last success 7891s ago (max 300s)
  SUSPENDED ops/cleanup
  NEVER-RAN default/new-report (0 3 * * *)
$ echo $?
1

🎯 Key Takeaways

  • A Job runs pods until completions succeed; restartPolicy: Always is rejected outright.
  • restartPolicy restarts the container; backoffLimit creates new pods — measured: 4 pod objects with Never versus 1 pod with 5 restarts under OnFailure.
  • Never preserves every attempt's logs; OnFailure overwrites them and does not consume the backoff budget per restart.
  • Retries back off 10s → 20s → 40s → 80s → 160s → 320s (capped at 6 min), so a default Job takes over ten minutes to report failure.
  • activeDeadlineSeconds is the only thing that stops a hung Job, and it overrides backoffLimit.
  • Indexed completion gives each pod a stable index in its name and environment — work partitions with no coordinator.
  • With completions unset, a Job is a work queue: it ends when any pod exits 0 and none remain.
  • podFailurePolicy separates your bug from the cluster's: Ignore on DisruptionTarget survived six preemptions with failed=0, where the default failed after four.
  • FailJob on a known-fatal exit code stops after one attempt instead of retrying pointlessly.
  • More than 100 missed schedules stops a CronJob permanently — 100 minutes at */1, and the only symptom is an empty LAST SCHEDULE.
  • startingDeadlineSeconds bounds the look-back window and fixes it instantly; every CronJob should set it.
  • Without timeZone, schedules run in the controller's zone (UTC) and drift with DST.
  • Allow produced 3 concurrent runs; Forbid skipped occurrences and emitted JobAlreadyActive events; Replace killed every long run so only the last completed.
  • Delivery is at-least-once: node failure, overlap, controller restarts and manual re-runs all duplicate work.
  • Idempotency must live in the workload — a dedup key set in the same transaction as the effect, or an advisory lock. Forbid is a convenience, not a guarantee.
  • An ordinary sidecar keeps a Job pod running for ever; use a native sidecar (init container with restartPolicy: Always).
  • Migrations belong in a versioned Job with backoffLimit: 0 and an advisory lock, gated with service_completed_successfully — never an init container, where every replica races the schema.
  • Every migration must still be backward compatible, because a rolling update runs both versions at once.
  • ttlSecondsAfterFinished and history limits stop thousands of Job objects accumulating in etcd.
  • Alert on time since last success, not on failure — four of the five most common CronJob failure modes are completely silent.
