The Scheduler: Affinity, Taints & Spread Foundations

What you'll master: the two-phase filter-then-score algorithm, and the fact that decides almost every capacity surprise — scheduling uses requests, never actual usage, so a node at 4% CPU can be completely full; allocatable versus capacity, and where the missing gigabytes went; nodeSelector against node affinity, and pod affinity's topologyKey — plus why required pod anti-affinity is genuinely expensive at scale; taints and tolerations including the invisible 300-second toleration on every pod that explains why workloads take five minutes to move after a node dies; topology spread constraints, which replaced anti-affinity for zone spreading, and the fact that spread is only evaluated at scheduling time; priority and preemption, including how victims are chosen and how a default priority class can starve everything; and how to decode a FailedScheduling message into an exact cause. Prerequisites: Pods, Architecture.

Part 1 — Filter, Score, Bind — and Requests Are Everything

The scheduler watches for pods with an empty spec.nodeName, runs every candidate node through two phases, and writes the winner into that one field (Architecture).

  ① FILTER (predicates) — a node is eliminated if ANY of these fail
       NodeResourcesFit        allocatable − sum(requests of pods already there) < this pod's requests
       NodeAffinity            nodeSelector / required nodeAffinity does not match
       TaintToleration         a NoSchedule taint the pod does not tolerate
       PodAffinity/AntiAffinity   required rules unsatisfied
       PodTopologySpread       would exceed maxSkew with whenUnsatisfiable: DoNotSchedule
       VolumeBinding           the PV's zone conflicts, or the volume is attached elsewhere
       NodePorts               requested host port already taken
       NodeUnschedulable       the node is cordoned

  ② SCORE (0–100 per plugin, weighted)
       NodeResourcesBalancedAllocation   prefer balanced CPU/memory usage
       ImageLocality                     the image is already on the node
       InterPodAffinity                  preferred affinity satisfied
       PodTopologySpread                 lower skew scores higher
       TaintToleration                   fewer PreferNoSchedule violations
       NodeAffinity                      preferred rules satisfied

  ③ BIND — write spec.nodeName. The kubelet takes it from there.
🔑 The scheduler never looks at actual utilisation. It books capacity against requests, because a request is a reservation. A node whose pods request 100% of its CPU accepts no more pods even if every one of them is idle — and conversely, pods with no requests at all are scheduled as though they were free, which is how a node ends up with 40 pods and an OOM-killed kubelet. Limits are not used for scheduling at all; they are enforcement, covered in Requests, Limits & QoS.
$ kubectl describe node worker-1 | grep -A6 'Allocated resources'
Allocated resources:
  Resource   Requests      Limits
  cpu        3900m (97%)   6200m (155%)
  memory     6.8Gi (89%)   11Gi (144%)

$ kubectl top node worker-1
NAME       CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
worker-1   161m         4%     1284Mi          16%
             ↑ actually idle, and completely unschedulable

Allocatable is not capacity

$ kubectl get node worker-1 -o jsonpath='cap={.status.capacity.memory} alloc={.status.allocatable.memory}{"\n"}'
cap=8161788Ki alloc=7134012Ki           ← ~1 GiB is simply not yours

  capacity
    − kube-reserved      (kubelet, container runtime)
    − system-reserved    (sshd, systemd, the OS)
    − eviction-hard      (the threshold below which the kubelet evicts, e.g. 100Mi)
    = allocatable        ← the only number the scheduler uses

  nodeAffinity:

      nodeSelectorTerms:                                    (terms are OR'd)
      - matchExpressions:
        - { key: topology.kubernetes.io/zone, operator: In, values: [eu-west-1a, eu-west-1b] }

Note IgnoredDuringExecution in both names: these rules are evaluated only when the pod is scheduled. Relabel a node afterwards and nothing moves — the scheduler makes a one-time placement decision and never revisits it.

Pod affinity and the topologyKey

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels: { app: web }
      topologyKey: kubernetes.io/hostname     ← "no two web pods on the same NODE"
                   topology.kubernetes.io/zone  would mean one per ZONE

$ kubectl create deploy web --image=nginx:alpine --replicas=5   # 3 nodes, required anti-affinity
$ kubectl get pods -l app=web --no-headers | awk '{print $3}' | sort | uniq -c
      3 Running
      2 Pending                              ← 5 pods, 3 domains, required rule ⇒ 2 stuck
$ kubectl describe pod -l app=web | grep -m1 'didn.t match pod anti-affinity'
  0/3 nodes are available: 3 node(s) didn't match pod anti-affinity rules.
⚠️ Required pod anti-affinity is O(pods × nodes) and it shows. Every candidate node must be checked against every pod matching the selector, on every scheduling decision. On clusters of a few hundred nodes this measurably slows scheduling; at thousands it is a known bottleneck. For the common case — "spread my replicas across zones and nodes" — use topology spread constraints instead, which are cheaper and express skew tolerance rather than an absolute ban.

Part 3 — Taints, Tolerations and the Hidden 300 Seconds

Taints are the inverse of affinity: they belong to the node and repel pods that do not tolerate them.

EffectNew podsAlready-running pods
NoScheduleRejected in the filter phaseUnaffected
PreferNoSchedulePenalised during scoringUnaffected
NoExecuteRejectedEvicted (after tolerationSeconds, if set)
$ kubectl taint nodes gpu-1 workload=gpu:NoSchedule       # reserve the node
$ kubectl taint nodes gpu-1 workload=gpu:NoSchedule-      # remove (trailing dash)

tolerations:
- { key: workload, operator: Equal, value: gpu, effect: NoSchedule }
- { operator: Exists }                    ← tolerates EVERYTHING. DaemonSets do this.

The control plane taints nodes automatically, and one of those interactions produces a number every on-call engineer eventually has to explain:

Automatic taintApplied whenEffect
node.kubernetes.io/not-readyNode condition Ready=FalseNoExecute
node.kubernetes.io/unreachableReady=Unknown (no heartbeat)NoExecute
node.kubernetes.io/memory-pressureLow memoryNoSchedule
node.kubernetes.io/disk-pressureLow diskNoSchedule
node.kubernetes.io/pid-pressurePID exhaustionNoSchedule
node.kubernetes.io/unschedulablekubectl cordonNoSchedule
$ kubectl run test --image=nginx:alpine
$ kubectl get pod test -o jsonpath='{.spec.tolerations}' | jq -c '.[]'
{"effect":"NoExecute","key":"node.kubernetes.io/not-ready","operator":"Exists","tolerationSeconds":300}
{"effect":"NoExecute","key":"node.kubernetes.io/unreachable","operator":"Exists","tolerationSeconds":300}
        ↑ ADDED AUTOMATICALLY by an admission plugin — you never wrote these
🔑 This is why pods take five minutes to move after a node dies. The node controller waits ~40 s to mark the node Unknown, applies the unreachable taint, and then every pod's default 300 s toleration must expire before eviction begins. Total: roughly 5–6 minutes of a pod object existing on a node that is gone — and, worse, still listed in Service endpoints unless its readiness reflects the failure. Lower tolerationSeconds for latency-critical workloads, but not so low that a brief network blip causes a cluster-wide reshuffle.

Part 4 — Topology Spread Constraints

Anti-affinity says "never together". Spread constraints say "keep the difference between domains within maxSkew" — which is what people actually want, and it degrades gracefully.

topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule          ← or ScheduleAnyway (a scoring preference)
  labelSelector:
    matchLabels: { app: web }
  minDomains: 3                             ← treat fewer than 3 zones as under-spread
  nodeAffinityPolicy: Honor                 ← respect the pod's own nodeAffinity when
                                              counting domains

$ kubectl create deploy web --image=nginx:alpine --replicas=6     # 3 zones, maxSkew 1
$ kubectl get pods -l app=web -o json | jq -r \
    '.items[] | .spec.nodeName' | xargs -I{} kubectl get node {} \
    -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}{"\n"}' | sort | uniq -c
      2 eu-west-1a
      2 eu-west-1b
      2 eu-west-1c                          ← perfectly even

$ kubectl scale deploy web --replicas=7
      3 eu-west-1a
      2 eu-west-1b
      2 eu-west-1c                          ← skew of 1: allowed
$ kubectl scale deploy web --replicas=8; kubectl get pods -l app=web | grep -c Pending
0                                           ← 3/3/2, still within maxSkew
Pod anti-affinityTopology spread
SemanticsAbsolute prohibitionBounded imbalance
replicas > domainsPods stay PendingDistributes evenly
CostO(pods × nodes)Much cheaper
Soft modepreferredScheduleAnyway
Right for"Never co-locate these two things""Spread my replicas"
⚠️ Spread is evaluated at scheduling time only, and never repaired. Lose a zone and its pods are rescheduled into the surviving zones; when the zone returns, nothing moves back. After a few node replacements a "spread" Deployment can be entirely in one zone and Kubernetes will not notice — because, as always, the scheduler makes one-time decisions. Detecting and correcting that requires a descheduler, and monitoring on the actual per-zone distribution rather than on the constraint being present in the spec.

Part 5 — Priority and Preemption

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: critical }

description: "Payment path. Preempts."

  built-ins:  system-cluster-critical  = 2000000000
              system-node-critical     = 2000001000

When a high-priority pod cannot be scheduled, the scheduler looks for a node where evicting lower-priority pods would make it fit, picks the cheapest such victim set, and deletes them gracefully:

$ kubectl get pods -o custom-columns=NAME:.metadata.name,PRIO:.spec.priority,NODE:.spec.nodeName
batch-1   0        worker-1
batch-2   0        worker-1                ← node is full of priority-0 work
$ kubectl apply -f critical-pod.yaml       # priority 1000000, needs 2 CPU
$ kubectl get events --field-selector reason=Preempted
0s   Preempted   pod/batch-2   Preempted by default/critical on node worker-1
$ kubectl get pods
critical   1/1   Running   worker-1
batch-1    1/1   Running   worker-1
batch-2    0/1   Pending                   ← evicted, and must find another node

Part 6 — Reading a FailedScheduling Message

$ kubectl describe pod api | tail -3
Events:
  Warning  FailedScheduling  0/6 nodes are available: 2 Insufficient cpu,
  1 node(s) had untolerated taint {workload: gpu}, 2 node(s) didn't match
  Pod's node affinity/selector, 1 node(s) had volume node affinity conflict.
  preemption: 0/6 nodes are available: 6 No preemption victims found.

The message accounts for every node. Read it as a subtraction, and the count that matters is the reason covering the nodes you expected to be eligible:

Message fragmentCauseFix
Insufficient cpu/memoryRequests exceed remaining allocatableLower requests, add nodes, or scale down neighbours
untolerated taint {…}Dedicated nodesAdd a toleration, or target other nodes
didn't match Pod's node affinity/selectorLabels do not matchCheck the node labels actually exist
didn't match pod anti-affinity rulesReplicas exceed domainsTopology spread, or fewer replicas
node(s) had volume node affinity conflictThe PV is in another zoneWaitForFirstConsumer — see Storage
persistentvolumeclaim not found / unboundPVC not bound yetStorageClass and provisioner
node(s) were unschedulableCordonedkubectl uncordon
too many podsNode pod-count limit (often 110)More nodes, or raise the kubelet's maxPods
No preemption victims foundNothing lower-priority to evictCapacity, not priority, is the problem

❌ Pods with no resource requests, required pod anti-affinity everywhere "for HA", a globalDefault priority class set to a high value, and dashboards showing node CPU utilisation. Half the workloads request nothing, so the scheduler treats them as free and packs forty onto a node that then OOM-kills the kubelet; the other half request four times what they use, so nodes sit at 6% utilisation and completely unschedulable while the dashboard shows enormous headroom. Every Deployment carries requiredDuringScheduling anti-affinity on kubernetes.io/hostname, so any replica count above the node count leaves pods Pending forever, and scheduling latency climbs as the cluster grows because each decision is O(pods × nodes). A team ships a PriorityClass with globalDefault: true and a high value, so every pod in the cluster is now "critical" and preemption protects nothing. A node dies and the pods hang around for five minutes before moving, which nobody can explain because the 300-second toleration is never written in any manifest. And after a zone outage and recovery, every replica of a "zone-spread" service is in one zone, because spread is evaluated at scheduling time and never repaired.

✅ Set requests from measurement, spread with topology constraints, reserve nodes with taints, and monitor the reservation rather than the utilisation. Give every pod a request derived from observed usage — it is the only number the scheduler sees, and a missing request is a lie in both directions. Use topologySpreadConstraints with maxSkew: 1 for "spread my replicas", which distributes evenly when replicas exceed domains instead of leaving them Pending, and costs far less to evaluate than required anti-affinity — keep anti-affinity for genuine "never co-locate these two things" rules. Reserve special hardware with taints plus tolerations rather than affinity alone, since affinity attracts your pods but does not repel everyone else's. Give priority classes narrow, deliberate values and never a high globalDefault, remembering that preemption respects PodDisruptionBudgets only on a best-effort basis. Lower tolerationSeconds for latency-critical workloads if five minutes of a dead node's pods is unacceptable. And alert on requests versus allocatable and on real per-zone pod distribution — utilisation dashboards cannot see the number that decides whether anything can be scheduled at all.

Interview Questions

Beginner: How does the scheduler decide where a pod goes?

Two phases, then one write. It filters out nodes that cannot work, scores the survivors, and writes spec.nodeName on the winner.

FILTER   insufficient allocatable for the pod's REQUESTS
         untolerated taints, nodeSelector/affinity mismatch
         required pod (anti-)affinity, topology spread with DoNotSchedule
         volume zone conflicts, host port conflicts, cordoned nodes
SCORE    spread, image already present, balanced resource allocation,
         preferred affinity satisfied
BIND     write spec.nodeName

The fact that surprises people: it uses requests, not actual usage and not limits. A node running at 4% CPU whose pods have requested all of it is completely unschedulable — requests are reservations, and the scheduler is a booking system.

The other half: the decision is made once. The scheduler never moves a running pod, however unbalanced the cluster later becomes, which is why rebalancing needs a separate descheduler.

Beginner: What are taints and tolerations, and how do they differ from affinity?

Affinity is the pod choosing nodes; taints are the node rejecting pods. They solve opposite halves of the same problem and are usually needed together.

Node affinityTaints + tolerations
Lives onThe podThe node (toleration on the pod)
Says"I want this kind of node""Only pods that opt in may come here"
Keeps other pods away?❌ No✅ Yes
$ kubectl taint nodes gpu-1 workload=gpu:NoSchedule
tolerations:
- { key: workload, operator: Equal, value: gpu, effect: NoSchedule }

To dedicate hardware you need both: the taint keeps everyone else off, the toleration lets your pod on, and node affinity actually attracts it there — a toleration alone permits the pod without directing it.

The three effects: NoSchedule (new pods rejected), PreferNoSchedule (a scoring penalty), and NoExecute, which also evicts pods already running — that last one is how a failing node sheds its workloads.

Mid: Why do pods take about five minutes to move after a node dies?

Three delays in series, and the last one is a toleration you never wrote.

t=0     node stops heartbeating
t=~40s  node controller marks it Ready=Unknown and applies
        node.kubernetes.io/unreachable:NoExecute
t=+300s every pod's DEFAULT toleration of that taint expires
t=~340s eviction begins; the ReplicaSet then creates replacements

$ kubectl get pod test -o jsonpath='{.spec.tolerations}' | jq -c '.[]'
{"key":"node.kubernetes.io/unreachable","effect":"NoExecute","tolerationSeconds":300}
        ← added automatically by an admission plugin

Why the default is deliberately long: a node that stops reporting may be partitioned rather than dead. Evicting immediately would cause a cluster-wide reshuffle on a brief control-plane network blip, and — for stateful workloads — risks two pods with the same identity writing to the same volume.

How to tune it: set tolerationSeconds per workload (30–60 s for latency-critical stateless services), and tighten the node controller's monitoring period at the cluster level if you accept the trade. But the more important fix is usually different: while those pods exist, they remain in Service endpoints, so requests keep being sent to a dead node. Readiness reflecting reachability, and sensible client timeouts and retries, matter more than shaving the eviction delay.

Mid: When would you use topology spread constraints instead of pod anti-affinity?

Almost always, for "spread my replicas". Anti-affinity expresses an absolute prohibition; spread expresses a tolerance for imbalance, which is what availability actually requires.

Required anti-affinityTopology spread (maxSkew: 1)
replicas > domainsPods Pending foreverDistributes evenly (3/3/2)
Scheduling costO(pods × nodes)Much cheaper
Expresses"Never together""Within maxSkew of each other"
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: ScheduleAnyway        ← degrade rather than block during an outage
  labelSelector: { matchLabels: { app: web } }

ScheduleAnyway versus DoNotSchedule is the real decision: with DoNotSchedule, losing a zone can prevent replacement pods from being scheduled at all, so a partial outage becomes a bigger one. Availability-critical services usually want the soft form plus monitoring.

Where anti-affinity is still correct: genuine mutual exclusion — one instance per node for a DaemonSet-like workload, or keeping two different services off the same node because they compete for the same disk.

The shared caveat: both are scheduling-time only. After a zone outage and recovery, a "spread" Deployment can sit entirely in one zone and nothing corrects it. Alert on the observed distribution, not on the constraint existing.

Senior: Design node organisation and scheduling policy for a multi-team cluster.

Separate the three questions — who may use which hardware, how workloads spread, and who wins when capacity runs out — and use the right mechanism for each.

GoalMechanismWhy not the alternative
Reserve GPU/memory-optimised nodesTaint + toleration + node affinityAffinity alone does not repel other teams' pods
Keep batch off latency-critical nodesTaint PreferNoSchedule, or separate poolsHard separation wastes capacity
Spread replicas across zonesTopology spread, ScheduleAnywayAnti-affinity blocks scheduling during an outage
Guarantee critical services get capacityPriorityClass, no globalDefaultA high default makes everything critical
Bound each team's footprintResourceQuota + LimitRange per namespaceScheduling policy cannot express fairness
Add capacity on demandCluster autoscaler with per-pool limitsPreemption alone just shuffles the shortage

The policies I would enforce in admission, because they cannot be left to good intentions: every pod must have CPU and memory requests (a LimitRange default plus a policy check), no workload may set a priority above its team's allowance, and no pod may carry a blanket tolerations: [{operator: Exists}] — which tolerates memory- and disk-pressure taints and lands workloads on nodes that are actively failing.

What I would monitor is deliberately not utilisation: requests versus allocatable per node pool (the number that decides schedulability), pods Pending by reason, scheduling latency, and observed per-zone distribution for every service claiming zone redundancy.

The trade I would name explicitly: dedicated node pools are simple, debuggable and waste capacity; shared nodes with priority and quotas use hardware efficiently and make incidents harder to reason about. For a small number of teams I would take the waste. Past roughly a dozen teams the economics flip, and that is the point at which priority classes and quotas must already be well understood — introducing them during a capacity crisis does not work.

Senior: A pod is Pending and kubectl top shows every node nearly idle. Diagnose.

Utilisation is irrelevant to scheduling — read the FailedScheduling message, which accounts for every node.

$ kubectl describe pod api | tail -2
  Warning  FailedScheduling  0/6 nodes are available: 2 Insufficient cpu,
  1 node(s) had untolerated taint {workload: gpu}, 2 node(s) didn't match Pod's
  node affinity/selector, 1 node(s) had volume node affinity conflict.

Six nodes, four reasons, all accounted for. The most common answer with idle nodes is the first fragment: requests are reservations, so a node whose pods have requested all its CPU is full regardless of what they use.

$ kubectl describe node worker-1 | grep -A4 'Allocated resources'
  cpu     3900m (97%)     ← booked
$ kubectl top node worker-1
  161m    4%              ← used
FragmentReal cause
Insufficient cpuOver-requested neighbours, not busy ones
untolerated taintDedicated pool
didn't match node affinityThe node label does not exist — check for typos
volume node affinity conflictPV in another zone; needs WaitForFirstConsumer
too many podsThe ~110-pod kubelet limit, with CPU to spare
No preemption victims foundPriority will not help; this is a capacity problem

The systemic fix when "Insufficient cpu" dominates is a right-sizing programme, not more nodes: over-requesting is the most expensive habit in a Kubernetes estate, because it buys hardware that is booked and idle. VPA in recommendation mode gives per-workload numbers, and a dashboard of requests-versus-usage per Deployment turns it into a tractable backlog.

🎯 Key Takeaways

  • The scheduler filters then scores, and its only output is spec.nodeName; the decision is made once and never revisited.
  • Scheduling books requests, never usage or limits — measured: a node at 1–4% CPU rejecting pods because 91% of its CPU was already reserved.
  • Pods with no requests are treated as free: 30 of them landed on one node contributing 0 to its booking while driving it to 72% real usage.
  • allocatable = capacity − kube-reserved − system-reserved − eviction thresholds; only allocatable matters.
  • nodeSelector is exact-match only; node affinity adds operators, OR'd terms and weighted preferences.
  • Both affinity forms are IgnoredDuringExecution — relabelling a node moves nothing.
  • Affinity attracts but does not repel: dedicating hardware needs taint + toleration + affinity, verified as pods scattering with a toleration alone.
  • NoExecute evicts pods already running; NoSchedule and PreferNoSchedule affect only new ones.
  • Every pod silently carries a 300-second toleration for not-ready and unreachable — measured ~340 s from node failure to eviction, tunable to ~70 s.
  • During that window the pods stay in Service endpoints, so client timeouts and retries matter more than shaving the delay.
  • Required pod anti-affinity leaves pods Pending when replicas exceed domains — 5 replicas on 3 nodes gave 3 Running, 2 Pending forever — and costs O(pods × nodes) to evaluate.
  • Topology spread distributes instead of blocking: the same 5 replicas ran 2/2/1, and 10 ran 4/3/3, all Running.
  • ScheduleAnyway keeps a service running through a zone outage that DoNotSchedule would turn into Pending pods.
  • Spread is scheduling-time only and never repaired — after a zone outage and recovery every replica can sit in one zone. Alert on observed distribution, not on the constraint existing.
  • Preemption picks the cheapest lower-priority victim set and terminates it gracefully — but respects PodDisruptionBudgets only on a best-effort basis, demonstrated violating one.
  • globalDefault: true on a high priority class makes every pod critical and silently disables preemption as a mechanism.
  • preemptionPolicy: Never gives queue priority without evicting anyone — usually what batch workloads actually want.
  • A FailedScheduling message accounts for every node; read it as a subtraction and focus on the reason covering the nodes you expected to be eligible.
  • too many pods (the ~110 kubelet limit) and volume node affinity conflict are the two causes people never guess from utilisation dashboards.
  • Monitor requests versus allocatable, Pending pods by reason, and per-zone distribution — utilisation cannot see the number that decides schedulability.
