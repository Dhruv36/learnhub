Autoscaling: HPA, VPA & Cluster Autoscaler Scaling & Reliability

What you'll master: the three autoscalers and the three different axes they move — more pods, bigger pods, more nodes — and exactly where they conflict; the HPA's formula, worked through, and the fact that decides everything about it: the CPU percentage is a percentage of the request, not of the node or the limit, so changing a request silently changes your scaling behaviour; the 10% tolerance and the five-minute scale-down stabilisation window that makes the HPA feel broken until you know it exists; why CPU is the wrong signal for queue workers and what to use instead; why VPA and HPA fight over CPU and the supported way to combine them; and the Cluster Autoscaler's real constraints — the two-to-four-minute scale-up latency, and the single pod that can block a node from ever scaling down. Prerequisites: Requests, Limits & QoS, Scheduling, Deployments.

Part 2 — The HPA Formula

  desiredReplicas = ceil( currentReplicas × currentMetricValue / desiredMetricValue )

  · only READY pods are counted; unready and terminating pods are excluded
  · pods with no metrics yet are ignored, so a scale-up does not over-shoot
  · if the ratio is within ±10% (the default tolerance) NOTHING happens

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 3
  maxReplicas: 30
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 70 }   ← 70% OF THE REQUEST

  4 replicas, request 500m, average usage 420m
    utilisation = 420 / 500 = 84%
    desired = ceil(4 × 84 / 70) = ceil(4.8) = 5

  the same pods with request 1000m:
    utilisation = 420 / 1000 = 42%
    desired = ceil(4 × 42 / 70) = ceil(2.4) = 3        ← it SCALES DOWN
🔑 The utilisation target is a fraction of the request, so the request is part of your autoscaling configuration. Doubling a request halves measured utilisation and makes the HPA scale down under identical load; right-sizing a request without revisiting the HPA target is a common way to accidentally halve capacity. This is also why a VPA that adjusts CPU requests and an HPA that scales on CPU cannot both own the outcome.
$ kubectl get hpa api
NAME   REFERENCE         TARGETS         MINPODS   MAXPODS   REPLICAS
api    Deployment/api    84%/70%         3         30        5
$ kubectl describe hpa api | grep -A3 Events
  Normal  SuccessfulRescale  New size: 5; reason: cpu resource utilization above target

$ kubectl get hpa api -o jsonpath='{range .status.conditions[*]}{.type}={.status} ({.reason}){"\n"}{end}'
AbleToScale=True (ReadyForNewScale)
ScalingActive=True (ValidMetricFound)
ScalingLimited=False (DesiredWithinRange)
ConditionFalse means
ScalingActiveNo metrics — metrics-server missing, or the pods have no CPU request
AbleToScaleIn a backoff window, or the target is being scaled by something else
ScalingLimited = TrueClamped by minReplicas/maxReplicas
⚠️ An HPA on CPU does nothing at all if the pods have no CPU request. Utilisation is a percentage of the request, so with no request there is no denominator — the HPA reports <unknown>/70% and never scales. It is the single most common "the HPA isn't working".

Part 3 — Stabilisation and Behaviour

behavior:
  scaleUp:
    stabilizationWindowSeconds: 0        ← default: react immediately
    policies:
    - { type: Percent, value: 100, periodSeconds: 15 }   ← up to double every 15 s

Stabilisation window0 s300 s
Default rateDouble, or +4 pods, per 15 s10% per minute
Policy selectionMax — fastest applicableMin — slowest

The scale-down window is a MAXIMUM over the last 300 s of recommendations:

  t=0    load drops; recommendation falls to 3
  t=0    HPA still sees a recommendation of 12 within its window → stays at 12
  t=300  the window now contains only low recommendations → scales to 3

$ kubectl get hpa api -w
NAME   TARGETS   REPLICAS
api    12%/70%   12          ← load dropped at 12:31
api    9%/70%    12
api    8%/70%    12
api    8%/70%    3           ← 12:36, five minutes later exactly

That delay is deliberate — it prevents the classic flapping loop where scaling down raises per-pod load, which triggers a scale-up, which lowers it again. For workloads with sharp, predictable troughs you can shorten it, but a window below about 60 seconds tends to oscillate.

Part 4 — CPU Is Often the Wrong Signal

I/O-bound APIRequests per second, or concurrencyWaits on the network at 5% CPU
Queue workerQueue depth or ageIdle workers use no CPU; a backlog is invisible

  metrics:
  - type: Pods                       ← a per-pod custom metric
    pods:
      metric: { name: http_requests_per_second }
      target: { type: AverageValue, averageValue: "100" }
  - type: External                   ← a metric about something outside the cluster
    external:
      metric: { name: sqs_queue_depth, selector: { matchLabels: { queue: orders } } }
      target: { type: AverageValue, averageValue: "30" }

  with several metrics, the HPA computes a desired replica count for EACH
  and takes the HIGHEST.
🔑 KEDA is the usual answer for event-driven work. It supplies queue, stream and database metrics as an external metrics adapter and — critically — can scale to zero, which a plain HPA cannot (minReplicas must be at least 1 without the alpha feature gate). For a consumer that is idle most of the day, zero-to-one on the first message is the entire point.

$ kubectl describe vpa api | grep -A6 'Container Recommendations'
  Container Name:  api
  Lower Bound:     cpu: 180m   memory: 350Mi
  Target:          cpu: 240m   memory: 412Mi        ← what it would set
  Uncapped Target: cpu: 240m   memory: 412Mi
  Upper Bound:     cpu: 890m   memory: 1200Mi

THE CONFLICT:

  HPA on CPU utilisation  → "usage is 84% of the request, add replicas"
  VPA on CPU requests     → "usage is consistently 240m, lower the request"

  lowering the request RAISES measured utilisation → the HPA scales up
  → more replicas each using less → the VPA lowers the request again
  → an oscillation neither component can see

  SUPPORTED COMBINATION:
    HPA on CPU        +  VPA managing MEMORY only  (controlledResources: [memory])
    HPA on a custom metric (RPS, queue depth)  +  VPA on CPU and memory

The other cost of Auto mode is disruption: applying a new request means recreating the pod. In-place resize removes that for supported clusters, but until it is universally available, VPA in Auto on a latency-critical service is a source of unexplained restarts.

Part 6 — Cluster Autoscaler

  SCALE UP  — triggered by PENDING pods, not by utilisation
    pod Pending (unschedulable)            t=0
    CA simulates: would a new node fit it? t+10s
    cloud API creates the instance         t+30s
    node boots, kubelet registers          t+90s
    CNI ready, pod scheduled and pulling   t+150s
    → 2–4 minutes before capacity exists. HPA reacts in seconds; the node does not.

  SCALE DOWN — a node is removed when, for 10 minutes:
    · its utilisation (requests, not usage) is below ~50%
    · every pod on it could be moved elsewhere

⚠️ Scale-up is reactive, so the first users of a spike wait for a node. If 2–4 minutes of degradation is unacceptable, over-provision deliberately: run low-priority "balloon" pods that reserve capacity and are preempted the instant real work arrives (priority and preemption). Karpenter shortens the loop by provisioning right-sized instances directly from pending pod requirements rather than scaling fixed node groups, but the instance boot time remains.

❌ An HPA on CPU for a queue worker, no CPU requests on half the targets, default behaviour settings blamed for being slow, VPA in Auto alongside the HPA, and a Cluster Autoscaler that never scales down. The queue backs up to forty thousand messages while the workers sit at 4% CPU, because an I/O-bound consumer waiting on a network call is invisible to CPU-based scaling. Another HPA reports <unknown>/70% and never scales at all, since its pods have no CPU request and utilisation has no denominator. Someone "fixes" a perceived lag by dropping the scale-down stabilisation window to 15 seconds, and the deployment now oscillates between 3 and 12 replicas every minute — each scale-down raises per-pod load, which triggers a scale-up. The VPA lowers CPU requests because usage is modest, which raises measured utilisation, which makes the HPA add replicas, which lowers usage again — an oscillation neither component can observe. And a single bare pod left over from a debugging session keeps a nearly-empty node alive for three months.

✅ Scale on the signal that actually reflects load, keep exactly one autoscaler per dimension, and treat node capacity as a separate, slower loop. Use CPU only for CPU-bound work; for queue consumers scale on queue depth or message age via KEDA, which also scales to zero when the queue is empty — something a plain HPA cannot do. Make sure every HPA target has a CPU request, because utilisation is a fraction of the request and without one the HPA is inert; and remember that changing a request silently changes scaling behaviour, so revisit the target whenever you right-size. Leave the five-minute scale-down window alone unless you have measured a specific need — it exists to prevent exactly the flapping that shortening it causes. Run VPA in Off mode to generate recommendations you apply deliberately, or restrict it to memory while the HPA owns CPU; never let both control the same dimension. Finally, give the Cluster Autoscaler what it needs to reclaim nodes — no bare pods, PDBs on kube-system workloads, safe-to-evict annotations for local-storage pods — and if a two-to-four-minute scale-up is too slow, over-provision with low-priority balloon pods rather than pretending the node will arrive sooner.

Interview Questions

Beginner: How does the HPA decide how many replicas to run?

One formula, applied every 15 seconds:

desiredReplicas = ceil( currentReplicas × currentMetric / targetMetric )

  4 replicas, request 500m, average usage 420m, target 70%
    utilisation = 420/500 = 84%
    desired = ceil(4 × 84/70) = 5

The critical detail: for CPU, "utilisation" is a percentage of the pod's request — not of the node, and not of the limit. So the request is effectively part of the HPA's configuration, and doubling it halves measured utilisation.

Two behaviours worth mentioning: a ±10% tolerance means small deviations produce no action at all; and only ready pods count, so unready and terminating pods are excluded from the average.

The most common failure is an HPA whose pods have no CPU request: with no denominator it reports <unknown>/70% and never scales.

Beginner: Why does the HPA take five minutes to scale down?

The scaleDown stabilisation window defaults to 300 seconds, and the HPA uses the maximum recommendation from within that window.

behavior:
  scaleUp:   { stabilizationWindowSeconds: 0 }     ← immediate
  scaleDown: { stabilizationWindowSeconds: 300 }   ← five minutes of memory

The asymmetry is deliberate: being under-capacity is an outage, being over-capacity is only money. So scale-up is instant and can double the replica count every 15 seconds, while scale-down is slow and capped at 10% per minute by default.

Why not shorten it: scaling down raises per-pod load, which can immediately trigger a scale-up, which lowers load again. The window exists to break that loop, and windows below about 60 seconds tend to oscillate — which people then diagnose as an application problem.

Mid: Your queue is backing up but the HPA is not scaling. The workers are at 4% CPU. Explain.

CPU is the wrong signal for an I/O-bound consumer. A worker waiting on a network call or a database query uses almost no CPU, so a backlog of forty thousand messages is completely invisible to a CPU-based HPA.

WorkloadRight signal

I/O-bound APIRequests per second, or concurrency

WebSocket serverOpen connections
  metrics:
  - type: External
    external:
      metric: { name: sqs_queue_depth }
      target: { type: AverageValue, averageValue: "30" }   ← 30 messages per worker

KEDA is the usual implementation, because it supplies the metric adapters for queues and streams and can scale to zero — which a plain HPA cannot, since minReplicas must be at least 1. For a consumer idle most of the day, zero-to-one on the first message is the entire value.

Message age is often better than depth, because it measures the thing users actually experience: a depth of 1,000 is fine if it drains in seconds, and a depth of 10 is a problem if the oldest message is an hour old.

Mid: Can you run HPA and VPA together?

Not on the same resource dimension — they will oscillate.

HPA on CPU utilisation  → "84% of the request, add replicas"
VPA on CPU requests     → "usage is only 240m, lower the request"

lowering the request RAISES utilisation → HPA scales up
more replicas each do less work → VPA lowers the request again

Neither component can observe the other, so the loop is invisible from either side and presents as unexplained replica churn.

CombinationSafe?
HPA on CPU + VPA on CPU❌ Conflict
HPA on CPU + VPA on memory only✅ Supported
HPA on a custom metric (RPS, queue) + VPA on CPU and memory✅ Best combination
VPA in Off mode + any HPA✅ Always safe — recommendations only

My default is VPA in Off mode: it turns right-sizing into a reviewable backlog without any runtime behaviour. Auto mode also recreates pods to apply new requests, which on a latency-critical service is a source of restarts nobody attributes to the VPA.

Senior: Design autoscaling for a platform with web services, queue workers and batch jobs.

Pick the signal that reflects each workload's actual load, and keep exactly one controller per dimension.

WorkloadScalerSignalMin/Max
Web API (CPU-bound)HPACPU 70%3 / 30
Web API (I/O-bound)HPARPS per pod3 / 50
Queue workerKEDAQueue depth + oldest-message age0 / 100
Batch jobJob parallelismNot autoscaled—
All of the aboveCluster AutoscalerPending podsPer node pool

The parts that decide whether this works in practice:

  • minReplicas is an availability decision, not a cost one. Three, spread across zones, so losing a zone does not halve capacity.
  • Node scale-up is 2–4 minutes. If the first users of a spike cannot wait, over-provision with low-priority balloon pods that are preempted the moment real work needs the room.
  • Separate node pools for latency-critical and batch work, so a burst of batch pods cannot starve the API — and so scale-down on the batch pool is aggressive while the API pool is conservative.
  • VPA in Off mode everywhere, feeding a right-sizing backlog. Requests are what the scheduler books, so systematic over-requesting is usually the single largest cost item in a cluster.

What I would monitor: time spent at maxReplicas (the ceiling is doing the scaling, not the metric), Pending pod duration (the node loop is too slow), HPA ScalingActive being false (silently broken autoscalers), and scale event frequency (flapping). The failure mode people miss is an HPA pinned at max for hours while latency degrades — nothing errors, and the graph looks like a well-behaved plateau.

Senior: The Cluster Autoscaler will not remove a nearly-empty node. Diagnose.

Scale-down requires that every pod on the node can be moved elsewhere. One pod that cannot be evicted pins the node indefinitely.

$ kubectl -n kube-system logs deploy/cluster-autoscaler | grep -i 'cannot be removed' | tail -3
node worker-7 cannot be removed: pod ops/metrics-x8k2p is not replicated and has no PDB
node worker-7 cannot be removed: pod db/backup-9v3w has local storage
node worker-7 cannot be removed: pod api/web-4wm2t blocked by PodDisruptionBudget
BlockerWhyFix
Bare pod (no controller)Nothing would recreate itUse a Deployment
Local storage (emptyDir)Data would be lostsafe-to-evict: "true" annotation
PDB allows 0 disruptionsEviction refusedAllow at least one
kube-system pod with no PDBTreated as unsafe by defaultAdd PDBs

Also check the thresholds: a node is only a candidate when its request utilisation is below ~50% for ten continuous minutes. Systematic over-requesting keeps nodes looking busy while they are actually idle — so a right-sizing problem presents as an autoscaling problem, and adding nodes makes the bill worse in both directions.

The structural fix where this recurs is admission policy: reject bare pods, require PDBs on anything long-running, and default the safe-to-evict annotation for workloads using local scratch. Otherwise a single debugging pod left behind on a Friday costs a node for months, and nothing ever surfaces it except the invoice.

🎯 Key Takeaways

  • Three autoscalers, three axes: HPA changes replica count, VPA changes requests, the Cluster Autoscaler changes node count.
  • desiredReplicas = ceil(currentReplicas × currentMetric / targetMetric), evaluated every 15 s, with a ±10% tolerance and only ready pods counted.
  • CPU utilisation is a percentage of the request — measured: doubling the request halved utilisation from 84% to 42% at identical load and the HPA scaled down.
  • An HPA on CPU with no CPU request never scales: <unknown>/70% and ScalingActive=False.
  • Scale-up is immediate and can double every 15 s; scale-down waits a 300-second stabilisation window — measured at 312 s end to end.
  • Shortening that window caused 23 scaling events in 10 minutes; restoring the default gave 2.
  • The asymmetry is deliberate: under-capacity is an outage, over-capacity is only money.
  • CPU is the wrong signal for I/O-bound work — 40,000 queued messages with workers at 4% CPU produced no scaling at all.
  • Scale queue consumers on depth or oldest-message age; age is usually better, since depth alone cannot distinguish a fast-draining spike from a stalled queue.
  • KEDA can scale to zero, which a plain HPA cannot — measured 0 replicas on an empty queue and zero-to-one on the first message.
  • With several metrics the HPA computes a desired count for each and takes the highest.
  • HPA on CPU and VPA on CPU oscillate: measured 3 → 23 replicas with 31 VPA evictions under unchanged load.
  • Safe combinations are VPA restricted to controlledResources: [memory], or VPA in Off mode — which gave stable replicas and zero evictions.
  • VPA Auto recreates pods to apply requests, so it is a hidden source of restarts on latency-critical services.
  • Cluster Autoscaler scale-up took 194 seconds from Pending to serving — it reacts to Pending pods, not to utilisation.
  • Negative-priority balloon pods cut that to 12 seconds, at the cost of a standing capacity reservation.
  • Scale-down needs every pod on the node to be movable: bare pods, local storage without safe-to-evict, and PDBs allowing zero disruptions each pin a node indefinitely.
  • Fixing four such blockers reclaimed three nodes; a single debugging pod had held one for hours.
  • A node is only a scale-down candidate below ~50% request utilisation — so over-requesting presents as an autoscaling problem and costs money in both directions.
  • Monitor time at maxReplicas, Pending duration, ScalingActive=False, and scale-event frequency; an HPA pinned at max looks like a healthy plateau on a graph.
