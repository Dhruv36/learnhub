Helm & Templating Operating Clusters

What you'll master: what Helm actually is — a template renderer plus a release ledger stored as Secrets in your cluster, which means the cluster, not Git, is the source of truth for what a release contains; the full values precedence chain and the --set type coercion that silently turns a version number into a float; the template mechanics that cause real outages — nindent, required, and why Release.Name is not Chart.Name; hooks, which live outside the release and can wedge an upgrade; the pending-upgrade state that blocks every subsequent deploy and how to recover from it; CRDs in crds/, which are installed once and then never upgraded or deleted; and the honest comparison with Kustomize and rendered-manifest pipelines. Prerequisites: Objects & Apply, Deployments, ConfigMaps & Secrets.

Part 1 — A Renderer and a Ledger

   chart (templates + values)
        │  render locally with Go templates
        ▼
   plain Kubernetes manifests
        │  server-side apply / create
        ▼
   the cluster
        +
   a RELEASE SECRET recording exactly what was applied, per revision

$ helm install shop ./chart -n shop
$ kubectl -n shop get secrets -l owner=helm
NAME                          TYPE                 DATA   AGE
sh.helm.release.v1.shop.v1    helm.sh/release.v1   1      20s
$ kubectl -n shop get secret sh.helm.release.v1.shop.v1 \
    -o jsonpath='{.data.release}' | base64 -d | base64 -d | gzip -d | jq -r '.info.status, .chart.metadata.version'
deployed
1.4.2
FactConsequence
Rendering happens on your machinehelm template gives you the exact manifests, with no cluster needed
Release state lives in cluster SecretsDeleting the namespace deletes your release history
Each revision is a full snapshotRollback is possible; --history-max bounds the Secrets
Helm 3 has no TillerYour kubeconfig's RBAC is what applies — no cluster-wide component

🔑 Helm is not declarative, and that is the root of most surprises. A Deployment controller continuously reconciles; Helm does not. Someone edits a Deployment by hand, Helm knows nothing about it, and the next helm upgrade performs a three-way merge that may or may not correct it. If you want continuous reconciliation, that is what GitOps adds on top.

Part 2 — Values Precedence

  lowest  ①  the subchart's own values.yaml
          ②  the parent chart's values.yaml
          ③  the parent's values for the subchart (overrides the subchart)
          ④  -f values-a.yaml
          ⑤  -f values-b.yaml            ← later -f files win
  highest ⑥  --set / --set-string / --set-file / --set-json

$ helm template shop ./chart \
    -f values-prod.yaml -f values-eu.yaml \
    --set image.tag=sha-9f21c0e \
    | grep 'image:'
        image: registry.example.com/api:sha-9f21c0e     ← --set beats every file

$ helm get values shop -n shop           # what the RELEASE was given
image:
  tag: sha-9f21c0e
$ helm get values shop -n shop --all     # merged with every default

The --set type coercion trap

$ helm template ./chart --set image.tag=1.20 | grep image:
        image: nginx:1.2                 ← "1.20" was parsed as the FLOAT 1.20 → 1.2

$ helm template ./chart --set-string image.tag=1.20 | grep image:
        image: nginx:1.20                ← correct

  other coercions that bite:
    --set enabled=true       → boolean, not the string "true"
    --set replicas=010       → 10 (leading zero dropped)
    --set version=1.0.0      → string (three dots is not a number) — inconsistent!
    --set key=a,b            → --set parses commas as SEPARATORS; escape them: a\,b
⚠️ Always use --set-string for image tags and version numbers. The failure is silent: 1.20 becomes 1.2, which is a real tag on many images, so the deploy succeeds and runs the wrong version. The same class of bug appears with --set on any value that looks numeric — port numbers with leading zeros, phone-number-like identifiers, and Git SHAs that happen to be all digits.

Part 4 — Hooks, and the Wedged Release

apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "chart.fullname" . }}-migrate
  annotations:
    "helm.sh/hook": pre-upgrade,pre-install
    "helm.sh/hook-weight": "-5"                  ← lower runs first
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  backoffLimit: 0
  template: { spec: { restartPolicy: Never, containers: [ ... ] } }
HookRunsTypical use
pre-install, pre-upgradeBefore manifests are appliedMigrations
post-install, post-upgradeAfter, once resources are readySmoke tests, seeding
pre-delete, post-deleteAround uninstallBackups, cleanup
testOn helm testVerification
⚠️ Hook resources are not part of the release. They are created outside the normal lifecycle, so they are not deleted by helm uninstall unless a delete policy says so, they are not rolled back, and a failing pre-upgrade hook leaves the release in pending-upgrade — which blocks every subsequent helm upgrade with "another operation is in progress".
$ helm upgrade shop ./chart -n shop
Error: UPGRADE FAILED: pre-upgrade hooks failed: job failed: BackoffLimitExceeded
$ helm list -n shop
NAME  REVISION  STATUS            CHART
shop  4         pending-upgrade                  ← wedged

$ helm upgrade shop ./chart -n shop
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress

RECOVERY, in order of preference:

  ① helm rollback shop 3 -n shop        ← usually enough; returns to the last good revision
  ② helm upgrade shop ./chart --force   ← replaces resources; can cause downtime
  ③ delete the pending release Secret:
       kubectl -n shop delete secret sh.helm.release.v1.shop.v4
     → Helm forgets the failed attempt; the previous revision becomes current again

The flags that stop this happening in the first place are worth using by default:

FlagEffect
--waitBlock until resources are Ready
--timeout 10mBound the wait
--atomic--wait plus automatic rollback on failure — no wedged state
--cleanup-on-failRemove resources created by a failed upgrade
--history-max 10Bound the release Secrets in etcd

Part 5 — Upgrades, Drift and CRDs

Helm 3 performs a three-way merge — old manifest, new manifest, live state — the same shape as kubectl apply (Objects & Apply). Fields Helm never set are left alone, which is what lets an HPA own replicas:

$ kubectl scale deploy shop-api --replicas=10 -n shop        # manual change
$ helm upgrade shop ./chart -n shop                          # chart says replicas: 3
$ kubectl get deploy shop-api -n shop -o jsonpath='{.spec.replicas}{"\n"}'
3                                   ← Helm SET replicas before, so it corrects it

$ # but a field the chart never rendered:
$ kubectl annotate deploy shop-api owner=platform -n shop
$ helm upgrade shop ./chart -n shop
$ kubectl get deploy shop-api -n shop -o jsonpath='{.metadata.annotations.owner}{"\n"}'
platform                            ← untouched: Helm never owned this field

CRDs are special, and the rule surprises everyone

CRD locationInstalledUpgradedDeleted on uninstall
crds/ directory✅ Once, before templates❌ Never❌ Never
templates/ with a hook✅✅Depends on the policy
$ helm upgrade cert-manager jetstack/cert-manager --version 1.15.0 -n cert-manager
Release "cert-manager" has been upgraded.
$ kubectl get crd certificates.cert-manager.io -o jsonpath='{.metadata.annotations.helm\.sh/chart}{"\n"}'
cert-manager-1.12.0                 ← the CRD is still the OLD version
   → new fields in the chart's CRs are silently dropped by the old schema
   → the documented fix is applying the CRDs manually before the upgrade:
     kubectl apply -f https://.../cert-manager.crds.yaml

🔑 Use Helm to consume third-party software; think twice before writing a chart for your own. Nothing beats helm install for installing someone else's operator with its CRDs, RBAC and defaults. For internal services, a chart with two hundred values is a programming language nobody chose, expressed in Go templates over whitespace-sensitive YAML — Kustomize overlays or rendered manifests are usually easier to review and to reason about.
THE RENDERED-MANIFEST PATTERN — the best of both:

  CI:   helm template shop ./chart -f values-prod.yaml > rendered/prod/shop.yaml
        git commit rendered/prod/
  CD:   Argo CD / Flux applies rendered/prod/

  · the pull request diff shows the ACTUAL Kubernetes objects that will change
  · no template rendering in the cluster; no Helm state in etcd
  · you keep Helm's packaging for upstream charts, and lose the ledger

❌ A chart with 180 values, deploys via helm upgrade with no --atomic, image tags passed with --set, migrations in a pre-upgrade hook with no delete policy, and CRDs left to Helm. Reviewers approve template changes they cannot mentally render, so a whitespace change ships an invalid nodeSelector that silently makes pods unschedulable. --set image.tag=1.20 deploys 1.2, which is a real tag, so an eighteen-month-old version runs in production with no error anywhere. A migration hook fails once and leaves the release pending-upgrade, so every subsequent deploy fails with "another operation is in progress" during an incident. The hook Jobs accumulate because nothing deletes them, and the next upgrade fails on a name conflict. And after upgrading the cert-manager chart, its CRDs are still the old version, so new fields in Certificate resources are silently dropped and certificates stop renewing weeks later.

✅ Render before you review, deploy atomically, and treat CRDs as a separate step. Put helm template and helm diff upgrade in CI so the pull request shows the actual objects that will change — reviewing templates instead of rendered output is how whitespace bugs reach production. Always deploy with --atomic --timeout 10m, which waits for readiness and rolls back automatically instead of leaving a wedged pending-upgrade that blocks the next deploy. Use --set-string for every image tag and version number, because --set coerces numeric-looking values silently. Give hooks a hook-delete-policy of before-hook-creation,hook-succeeded, keep backoffLimit: 0 on migrations so a half-applied schema is not retried, and remember hooks are outside the release and are never rolled back. Apply CRDs explicitly before upgrading any chart that ships them, since anything in crds/ is installed once and never updated. And keep charts small: use Helm to consume upstream software, and prefer Kustomize overlays or committed rendered manifests for your own services, where reviewability matters more than parameterisation.

Interview Questions

Beginner: What does Helm actually do?

Two things: it renders Go templates into Kubernetes manifests locally, and it records what it applied as a release, revision by revision, in Secrets in the cluster.

chart + values → (rendered on your machine) → manifests → applied to the cluster
                                                        + sh.helm.release.v1.<name>.vN
CapabilityComes from
Parameterised manifestsTemplating
Rollback, historyThe release Secrets
Packaging, versions, dependenciesChart repositories
Ordering, migrationsHooks

The important qualifier: Helm is imperative. Nothing reconciles a release — it changes the cluster only when you run it. Manual edits go unnoticed until the next upgrade, when a three-way merge may or may not correct them. Continuous reconciliation is what GitOps adds.

Since Helm 3 there is no Tiller: helm uses your kubeconfig, so it can do exactly what your RBAC allows and nothing more.

Beginner: How do values precedence and --set work?

Later sources win, and --set wins over everything.

subchart values.yaml → parent values.yaml → -f a.yaml → -f b.yaml → --set

Multiple -f files are merged in order, so the last one listed takes precedence — which is how a values-prod.yaml plus a values-eu.yaml layering works.

The trap is type coercion:

--set image.tag=1.20         → the FLOAT 1.20 → renders as "1.2"
--set-string image.tag=1.20  → the string "1.20"    ✅

It fails silently, because 1.2 is often a real tag — so the deploy succeeds and the wrong version runs. Always use --set-string for tags and versions. --set also treats commas as separators, so values containing commas must be escaped.

To debug what a release actually received: helm get values <release> shows the supplied values, and --all shows them merged with every chart default.

Mid: A helm upgrade failed and now every upgrade says "another operation is in progress". Explain.

The release is stuck in pending-upgrade. Helm marks the release as in-progress before applying and only clears it on success; a failure that Helm did not handle — most often a failing pre-upgrade hook — leaves it set.

$ helm list -n shop
NAME  REVISION  STATUS            CHART
shop  4         pending-upgrade
$ helm upgrade shop ./chart -n shop
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress
RecoveryNotes
helm rollback shop 3Usually sufficient; returns to the last good revision
helm upgrade --forceReplaces resources — can cause downtime
Delete the pending release SecretHelm forgets the failed attempt

The prevention is --atomic, which waits for readiness and rolls back automatically on failure, so the release never sits in a pending state. Pair it with --timeout, and use --cleanup-on-fail to remove resources a failed upgrade created.

Note what rollback does not undo: hooks are outside the release, so a migration that ran is not reversed. Migrations therefore have to be backward compatible and idempotent — the same requirement as in Jobs.

Mid: Why did upgrading a chart not upgrade its CRDs?

Anything in the chart's crds/ directory is installed once, before templates, and is then never upgraded or deleted. This is deliberate: modifying a CRD can data-loss every custom resource of that type, and deleting one deletes all of them.

$ helm upgrade cert-manager jetstack/cert-manager --version 1.15.0
Release "cert-manager" has been upgraded.
$ kubectl get crd certificates.cert-manager.io -o jsonpath='{.metadata.annotations.helm\.sh/chart}{"\n"}'
cert-manager-1.12.0                  ← still the old CRD

The consequence is subtle: new fields the upgraded chart writes into its custom resources are silently pruned by the old schema, so the operator behaves as though you never set them. There is no error — the API server simply drops unknown fields.

ApproachTrade-off
kubectl apply -f crds.yaml before upgradingExplicit; what most projects document
CRDs in templates/ with hooksUpgradable, but risks deletion on uninstall
A separate CRD-only chartClean lifecycle; two releases to manage

Operationally I treat CRD upgrades as their own change with their own review, because they are the one part of a chart upgrade that can be destructive and is not covered by helm rollback.

Senior: Would you write Helm charts for internal services? Argue it.

Usually not. Helm's strength is packaging and distributing third-party software; for internal services the templating cost usually exceeds the benefit.

Helm is right forHelm is wrong for
Installing someone else's operator with CRDs and RBACTen near-identical internal services
Software with genuine variability across usersConfiguration that differs by three values
Anything needing hooks and orderingStraightforward Deployments
Distributing to people you cannot talk toYour own team

The core problem with a large chart is reviewability. Go templates over whitespace-sensitive YAML, with conditionals and loops and 180 values, is a programming language nobody chose. Reviewers approve template diffs they cannot mentally render, and whitespace bugs produce YAML that is valid and wrong.

What I would do instead: a shared Kustomize base with per-service overlays, or a small internal chart with fewer than twenty values. Kustomize also hashes ConfigMaps automatically, which gives you the rollout-on-config-change behaviour that in Helm needs a manual checksum/config annotation.

And the pattern I would push hardest: render in CI and commit the output. helm template into a rendered/ directory means the pull request diff shows the actual Kubernetes objects changing, GitOps applies plain manifests, and no template rendering happens in the cluster. You keep Helm for upstream charts and lose only the release ledger — which GitOps replaces with something better.

Senior: Design a Helm-based deployment pipeline.

Render early, diff before applying, deploy atomically, and keep CRDs separate.

StageCommandCatches
Linthelm lint, helm template | kubeconformTemplate errors, invalid schema
Policyhelm template | conftestMissing limits, :latest, root
Diffhelm diff upgradeWhat will actually change
Server validationhelm template | kubectl apply --dry-run=serverAdmission, quota, RBAC
Deployhelm upgrade --install --atomic --timeout 10mFailure → automatic rollback
Verifyhelm test, plus SLO checksThat it works, not just that it applied

The non-obvious requirements:

  • Values live in Git; secrets do not. Reference an ExternalSecret rather than templating credentials — a --set dbPassword= ends up in CI logs and in the release Secret.
  • Image tags with --set-string, always, and as an immutable digest or commit SHA rather than a moving tag.
  • CRDs applied as a separate, reviewed step before the chart upgrade.
  • --history-max 10, or release Secrets accumulate in etcd — each is a full gzip'd snapshot of every rendered manifest.
  • Post-deploy verification is part of the deploy: --atomic proves resources became Ready, not that the service works.

Where I would evolve it: once several teams share the pipeline, move to rendered manifests in Git plus a GitOps controller. Helm then runs in CI only, drift is detected continuously rather than at the next deploy, and the audit trail is the Git history instead of a Secret in a namespace someone might delete.

$ cat > tools/render.sh <<'SH'
#!/usr/bin/env bash
# Render every environment to plain manifests, for review and for GitOps to apply.
set -euo pipefail
CHART=${CHART:-./chart}
for env in dev staging prod; do
  out="rendered/$env"
  mkdir -p "$out"
  helm template shop "$CHART" \
    --namespace "shop-$env" \
    --values "values/base.yaml" \
    --values "values/$env.yaml" \
    --set-string image.tag="${IMAGE_TAG:?set IMAGE_TAG}" \
    > "$out/manifests.yaml"
  # validate what will actually be applied
  kubeconform -strict -kubernetes-version 1.31.0 "$out/manifests.yaml"
  conftest test "$out/manifests.yaml"
done
SH

🎯 Key Takeaways

  • Helm is a local template renderer plus a release ledger stored as Secrets in the cluster — each revision is a full gzip'd snapshot of every rendered manifest.
  • Deleting a namespace destroys the release history; helm uninstall is the supported path, and --history-max bounds the Secrets in etcd.
  • Helm is imperative: nothing reconciles a release, so drift is invisible until the next upgrade.
  • Values precedence runs subchart → parent → each -f in order → --set; the last -f wins.
  • --set image.tag=1.20 renders 1.2 — and because 1.2 is often a real tag, the deploy succeeds and runs the wrong version. Use --set-string.
  • The same coercion drops leading zeros and .0 suffixes; 1.0.0 survives only because three dots is not a number.
  • indent where nindent is needed produces YAML that is sometimes invalid and sometimes valid and wrong — a rendered nodeSelector silently became null.
  • required turns a missing value into a render-time failure; without it a missing tag renders repo: and pulls :latest.
  • default treats false and 0 as unset — use hasKey for booleans.
  • Hooks live outside the release: they are not rolled back, and without a delete policy their Jobs accumulate until a name conflict fails the next upgrade.
  • A failed hook leaves the release pending-upgrade, which blocks every subsequent deploy — including the one that fixes it.
  • Recovery is helm rollback, or deleting the pending release Secret; --atomic prevents the state entirely by rolling back automatically.
  • Helm 3's three-way merge corrects drift on fields the chart owns and leaves fields it never set alone — verified with a manual annotation surviving an upgrade.
  • A chart that renders replicas alongside an HPA oscillates; the fix is to omit the field when autoscaling is enabled.
  • CRDs in crds/ are installed once and never upgraded or deleted — new fields are silently pruned by the old schema, with no error.
  • Apply CRDs explicitly before upgrading any chart that ships them, and treat it as its own reviewed change.
  • Use Helm to consume third-party software; for internal services a 180-value chart is an unreviewable programming language in whitespace-sensitive YAML.
  • Kustomize hashes ConfigMaps automatically, giving rollout-on-config-change that Helm needs a manual checksum/config annotation for.
  • Render in CI and commit the output: a template one-liner that quartered production memory limits was invisible in the template diff and obvious in the rendered one.
  • Deploy with --atomic --timeout, gate on helm diff and --dry-run=server, and keep secrets out of values entirely.
