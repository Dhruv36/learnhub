Objects, the API & How Apply Works Foundations

What you'll master: the single shape every Kubernetes object shares, and why spec is desire while status is observation — a distinction that decides which field you are allowed to write; generation versus observedGeneration, and Conditions as the standard vocabulary controllers report through; labels versus annotations versus selectors, and why a Deployment's selector is immutable; the real difference between create, apply, replace and patch, including the three-way merge and the last-applied-configuration annotation that makes deleting a field work — or silently not work; server-side apply and field ownership, which is the modern answer and the reason your GitOps tool and your HPA can fight over replicas forever; and the API mechanics that decide whether your automation is correct — optimistic concurrency and resourceVersion, kubectl diff, and why --dry-run=server catches what --dry-run=client cannot. Prerequisites: Architecture & the Reconciliation Loop.

Part 1 — Every Object Has the Same Shape

Pods, Deployments, Services, CRDs your company wrote last week — all five top-level fields, always. Once you internalise the shape, an unfamiliar resource is only unfamiliar in its spec.

apiVersion: apps/v1          ← GROUP/VERSION  ("v1" alone means the core group)
kind: Deployment             ← KIND
metadata:                    ← name, namespace, labels, annotations, ownerRefs,
  name: web                    finalizers, resourceVersion, generation, uid
  namespace: shop
  labels: { app: web }
spec:                        ← DESIRED state. You write this.
  replicas: 3
status:                      ← OBSERVED state. Controllers write this. You do not.
  readyReplicas: 3
  observedGeneration: 4
TermMeansExample
GVK (Group/Version/Kind)What you write in YAMLapps/v1, Deployment
GVR (Group/Version/Resource)The URL path — lowercase plural/apis/apps/v1/deployments
NamespacedLives in a namespacePod, Deployment, Secret
Cluster-scopedHas no namespaceNode, PersistentVolume, ClusterRole, Namespace
SubresourceA separate endpoint with its own RBAC/status, /scale, /exec
The API is self-describing — you never need to guess a field:

$ kubectl api-resources | head -4
NAME          SHORTNAMES   APIVERSION   NAMESPACED   KIND
configmaps    cm           v1           true         ConfigMap
deployments   deploy       apps/v1      true         Deployment
nodes         no           v1           false        Node

$ kubectl explain deployment.spec.strategy.rollingUpdate
FIELDS:
  maxSurge       <IntOrString>  The maximum number of pods that can be scheduled
                                above the desired number of pods...
  maxUnavailable <IntOrString>  The maximum number of pods that can be unavailable...

$ kubectl explain pod.spec --recursive | head -5     ← the entire tree, offline
$ kubectl get --raw /apis/apps/v1 | jq -r '.resources[].name' | head -3
controllerrevisions
daemonsets
daemonsets/status                                    ← subresources are real endpoints
🔑 Subresources are why RBAC can be precise. /status and /scale are separate endpoints, so you can grant an HPA permission to scale a Deployment without permission to change its image, and let a controller update status without letting it rewrite spec. It is also why kubectl scale succeeds when a restrictive role blocks update on the deployment itself.

Part 2 — Spec Is Desire, Status Is Observation

The split is the entire contract between you and the controllers. You state what you want; they report what they see. Writing to the wrong half is the most common way to confuse yourself.

$ kubectl patch deploy web --type=merge -p '{"status":{"readyReplicas":99}}'
The Deployment "web" is invalid: status is read-only from the main resource endpoint
   → status lives on the /status subresource, and controllers overwrite it anyway:
     it DESCRIBES reality, so writing to it is like editing a thermometer.

Two fields turn "did my change take effect?" from a guess into an observation:

FieldMeaningUse to answer
metadata.generationIncremented by the API server on every spec change"Which version of my intent is this?"
status.observedGenerationThe generation the controller has processed"Has the controller seen my change yet?"
status.conditionsStructured judgements about current state"Did it actually work?"
$ kubectl set image deploy/web c=nginx:1.27
$ kubectl get deploy web -o jsonpath='gen={.metadata.generation} observed={.status.observedGeneration}{"\n"}'
gen=5 observed=4          ← the controller has NOT yet acted on your change
$ sleep 1
gen=5 observed=5          ← now it has. Whether it SUCCEEDED is a separate question.

$ kubectl get deploy web -o jsonpath='{range .status.conditions[*]}{.type}={.status} ({.reason}){"\n"}{end}'
Available=True (MinimumReplicasAvailable)
Progressing=False (ProgressDeadlineExceeded)     ← it was seen, and it FAILED
Condition patternConvention
typeA positive-polarity noun: Ready, Available, Progressing
status"True" / "False" / "Unknown" — strings, not booleans
reasonA CamelCase machine-readable code — what to alert on
messageHuman prose. Never parse it.
lastTransitionTimeWhen it last changed — how you measure flapping
⚠️ Unknown is a real value and it is not False. It means nobody could observe the truth — a node stopped heartbeating, a controller is down. Automation that treats conditions as booleans turns "we cannot tell" into "it is broken" and takes remediation action on a monitoring failure. Compare against "True" explicitly.

Part 3 — Labels, Annotations and Selectors

LabelsAnnotations
PurposeIdentify and selectAttach arbitrary metadata
Queryable✅ -l app=web, and by controllers❌ Never
SizeValue ≤ 63 chars, restricted charsetLarge — up to the object limit
Used byServices, ReplicaSets, affinity, network policyTools: ingress controllers, GitOps, last-applied
Rule of thumbIf something selects on itIf something reads it
Selectors are how the whole system is wired together — nothing is by name:

  Service ──selector: {app: web}──► any Pod carrying that label
  ReplicaSet ──selector──► its Pods (plus a pod-template-hash it adds itself)
  NetworkPolicy, affinity, topology spread, PDB ──► all label selectors

$ kubectl get pods -l 'app=web,env in (staging,prod),!deprecated'
   equality: app=web, tier!=cache      set-based: in (…), notin (…), exists, !exists

Two consequences bite constantly. First, a Deployment's spec.selector is immutable — you must delete and recreate the Deployment to change it, which is a real outage on a live service. Second, the labels that matter are on the pod template, not on the Deployment:

metadata:
  labels: { app: web }        ← labels on the DEPLOYMENT. Services ignore these.
spec:
  selector:
    matchLabels: { app: web } ← IMMUTABLE
  template:
    metadata:
      labels: { app: web }    ← THESE are what a Service selects. Must match above.

$ kubectl patch deploy web -p '{"spec":{"selector":{"matchLabels":{"app":"web2"}}}}'
The Deployment "web" is invalid: spec.selector: Invalid value: field is immutable
🔑 A Service with a typo in its selector is not an error — it is a Service with zero endpoints. Selectors that match nothing are perfectly valid, so the failure appears as connection timeouts rather than a rejected manifest. kubectl get endpointslices is the one-command check, and it is the first thing to run whenever a Service "does not work".

Part 4 — create vs apply vs replace vs patch

CommandDoesIf the object existsDeletes removed fields?
create -fPOSTFailsn/a
apply -fThree-way mergeMerges✅ Yes — if it owns them
replace -fPUT — whole objectOverwrites entirely✅ Yes, all of them
patch --type=mergeMerge patchMerges the fields givenOnly with explicit null
patch --type=strategicKubernetes-aware mergeMerges lists by keyWith directives
patch --type=jsonRFC 6902 operationsExact opsWith remove
editInteractive, then apply-likeMerges✅

The interesting one is apply, because deleting a field has to work — and doing that requires knowing what you previously asked for, as opposed to what someone else set:

THREE-WAY MERGE — apply compares three documents:

  ① last-applied  (metadata.annotations["kubectl.kubernetes.io/last-applied-configuration"])
  ② your new YAML
  ③ the live object

  in ① and NOT in ②   → you removed it   → DELETE from live
  in ②                → you want it      → SET on live
  only in ③           → someone else set it → LEAVE ALONE   ← this is the point

Which produces the classic failure: an object first created imperatively has no last-applied annotation, so the first apply cannot tell what you had previously asked for, and cannot delete anything:

$ kubectl create deploy web --image=nginx:alpine
$ kubectl apply -f web.yaml
Warning: resource deployments/web is missing the kubectl.kubernetes.io/last-applied-configuration
annotation which is required by kubectl apply. kubectl apply should only be used on resources
created declaratively... The missing annotation will be patched automatically.

   → the warning is real: on THAT first apply, fields you removed from the YAML are
     not deleted, because there was no record of you ever having set them.
⚠️ Never mix imperative creation with declarative management. Once an object is created with create, run or expose, the first apply is silently a partial merge. Use apply from the very beginning — or --server-side, which does not use the annotation at all and does not have this problem.

Part 5 — Server-Side Apply and Field Ownership

Server-side apply (SSA) moves the merge into the API server and replaces the annotation with per-field ownership. Every field records which manager set it, in metadata.managedFields:

$ kubectl apply --server-side -f web.yaml
deployment.apps/web serverside-applied

$ kubectl get deploy web --show-managed-fields -o json \
    | jq -r '.metadata.managedFields[] | "\(.manager) \(.operation)"'
kubectl              Apply
kube-controller-manager Update
Client-side applyServer-side apply
Where the merge happensIn kubectlIn the API server
Records intent inAn annotation (subject to the 1.5 MB object limit)managedFields
GranularityWhole objectPer field
Two writers on one fieldLast writer wins, silentlyConflict error
Needs prior apply history✅ Yes❌ No
$ kubectl apply --server-side -f web.yaml
error: Apply failed with 1 conflict: conflict with "kubectl-scale" using apps/v1:
  .spec.replicas
Please review the fields above--they currently have another manager. Either remove
the field from your manifest, or use --force-conflicts to overwrite.

That error is a feature: it is the system telling you two things are trying to own one field. The canonical instance is an HPA fighting a GitOps tool:

  Argo CD applies:  spec.replicas: 3          (from Git, every 3 minutes)
  HPA writes:       spec.replicas: 12         (from load, continuously)

  → the cluster oscillates between 3 and 12 for ever, capacity is wrong half the
    time, and the Deployment shows constant rollout churn.

  THE FIX is not tuning either tool — it is deleting the field:
    remove `replicas` from the manifest entirely, so the HPA is its only owner.
    (Argo CD: ignoreDifferences on /spec/replicas.)
🔑 If two controllers write one field, one of them must stop. An autoscaled Deployment must not specify replicas in Git, because "how many replicas" is now a runtime observation, not a declared intent. SSA surfaces this as a conflict instead of letting it flap silently — and --force-conflicts is the wrong reflex, because it takes ownership away from the controller that was legitimately managing the field.

Part 6 — Concurrency, Diffing and Dry Runs

Every object carries a resourceVersion. Send an update with a stale one and the API server rejects it — optimistic concurrency, which is what stops two controllers clobbering each other:

$ RV=$(kubectl get deploy web -o jsonpath='{.metadata.resourceVersion}')
$ kubectl scale deploy web --replicas=5             # someone else writes first
$ kubectl replace -f <(kubectl get deploy web -o json | jq ".metadata.resourceVersion=\"$RV\"")
Error from server (Conflict): Operation cannot be fulfilled on deployments.apps "web":
the object has been modified; please apply your changes to the latest version and try again

   The correct client behaviour is GET → modify → PUT → on 409, repeat.
   `resourceVersion` is an opaque token: never compare, order or do arithmetic on it.

Before changing anything, two commands remove almost all of the risk:

$ kubectl diff -f web.yaml
diff -u -N /tmp/LIVE-.../apps.v1.Deployment.shop.web /tmp/MERGED-.../...
-        image: nginx:1.25-alpine
+        image: nginx:1.27-alpine
-      replicas: 3
+      replicas: 5
   → exactly what WOULD change, computed by the same merge apply would perform

$ kubectl apply -f web.yaml --dry-run=client -o yaml   # local only: schema, nothing more
$ kubectl apply -f web.yaml --dry-run=server
Error from server: admission webhook "policy.kyverno.io" denied the request:
  validation error: every Pod must define resources.limits.memory
   → the SERVER dry run goes through the FULL pipeline: defaulting, admission
     webhooks, validation, quota — everything except the etcd write.
--dry-run=client--dry-run=server
Catches YAML/schema errors✅✅
Applies defaulting❌✅
Runs admission webhooks and policy❌✅
Enforces quota and RBAC❌✅
Needs a cluster❌✅

❌ Objects created with kubectl create and later managed with apply, replicas committed in Git alongside an HPA, automation that patches status, and a CI pipeline whose only validation is --dry-run=client. The first apply emits a warning nobody reads and silently fails to remove the fields deleted from the YAML, so a stale nodeSelector from a debugging session stays on the Deployment for months. Git says replicas: 3 and the HPA says 12, so the cluster oscillates between them indefinitely and someone "fixes" it by disabling the HPA during peak. A script reads conditions[?type=="Ready"].status as a boolean, so when a node stops heartbeating and the value becomes Unknown, the automation reads "not ready" and starts evicting a service that was fine. The Service selector has a typo, which is a perfectly valid manifest, so the failure surfaces as timeouts rather than a rejected apply. And CI validates with a client dry run, so a manifest that every policy webhook will reject passes review and fails at deploy time in production.

✅ Manage objects declaratively from creation, let exactly one writer own each field, read conditions as three-valued, and validate against the real API. Create everything with apply — or better apply --server-side, which records per-field ownership instead of an annotation and cannot suffer the missing-last-applied problem. Remove replicas from any manifest whose Deployment is autoscaled, so the HPA is its sole owner, and treat an SSA conflict as a design question rather than something to silence with --force-conflicts. Never write status: compare observedGeneration with generation to know the controller saw your change, and read conditions — comparing against the string "True", since "Unknown" means "cannot observe", not "broken". Check kubectl get endpointslices whenever a Service misbehaves, because a selector matching nothing is valid YAML. And put kubectl diff and --dry-run=server in CI, so defaulting, quota and every admission webhook are exercised before the change reaches a cluster.

Interview Questions

Beginner: What are the standard fields of a Kubernetes object?

Five, and every object has them: apiVersion, kind, metadata, spec, status.

apiVersion: apps/v1     group/version — "v1" alone is the core group
kind: Deployment        the type
metadata:               name, namespace, labels, annotations, ownerReferences,
                        finalizers, generation, resourceVersion, uid
spec:                   DESIRED state — you write this
status:                 OBSERVED state — controllers write this

The distinction that matters: spec is what you want, status is what is. You never write status — it lives on a separate /status subresource and a controller will overwrite it in the next reconcile anyway.

The follow-up worth pre-empting: how do you find fields you do not know? kubectl explain deployment.spec.strategy --recursive reads the schema straight from the API server, so it is always correct for your cluster version, including CRDs. That beats searching documentation for a different release.

Beginner: What is the difference between labels and annotations?

Labels are for selecting; annotations are for carrying information. The test is whether anything needs to query by it.

LabelsAnnotations
Selectable✅ -l app=web, and by controllers❌ Never
Size limits≤ 63 chars, restricted charsetLarge
ConsumersServices, ReplicaSets, affinity, NetworkPolicy, PDBIngress controllers, GitOps tools, last-applied

Labels are how everything in Kubernetes is wired: a Service does not name pods, it selects on their labels. That indirection is what lets a rolling update swap every pod without the Service changing.

Two practical traps: the labels a Service selects are on the pod template, not on the Deployment object; and a Deployment's spec.selector is immutable, so getting it wrong means deleting and recreating the Deployment — an outage on a live service.

Mid: Explain how kubectl apply knows to delete a field you removed from your YAML.

A three-way merge against the last-applied-configuration annotation. Apply compares three documents:

① last-applied   what you asked for LAST time (stored as an annotation)
② your new YAML  what you are asking for now
③ the live object what is actually there

in ① but not ②   → you removed it        → DELETE it from live
in ②             → you want it            → SET it
only in ③        → someone else set it    → LEAVE IT ALONE

The third rule is the important one: it is why apply does not wipe fields added by a mutating webhook, by the HPA, or by a defaulting controller.

The failure mode this produces: an object created with kubectl create has no annotation, so the first apply has no ① and cannot delete anything. You get a warning most people ignore, and a stale field survives indefinitely.

Server-side apply fixes it properly by tracking ownership per field in managedFields instead of using an annotation — no history required, no 1.5 MB annotation bloat, and a genuine conflict error when two managers want the same field instead of a silent last-writer-wins.

Mid: Your GitOps tool and your HPA keep fighting over replica count. Diagnose and fix.

Two controllers own one field. Git declares replicas: 3; the HPA writes replicas: 12 from observed load. Each write triggers the other to correct it, for ever.

$ kubectl get deploy web -o jsonpath='{.spec.replicas}{"\n"}'; sleep 60
12
3                       ← Argo re-synced
$ kubectl get events --field-selector involvedObject.name=web | grep -c ScalingReplicaSet
47                      ← in ten minutes

The fix is to delete the field, not to tune either tool. Once a Deployment is autoscaled, replica count is a runtime observation, not a declared intent — so it must not appear in the manifest at all:

  · remove `replicas:` from the Deployment in Git
  · Argo CD:  ignoreDifferences: [{group: apps, kind: Deployment, jsonPointers: [/spec/replicas]}]
  · Flux:     spec.patches, or simply omit the field

What SSA adds: with --server-side this stops being an invisible flap and becomes an explicit error — conflict with "horizontal-pod-autoscaler" using apps/v1: .spec.replicas. That is the system asking you to decide who owns the field. --force-conflicts answers "me, and I will keep fighting", which is the wrong answer here.

The generalisable rule: exactly one writer per field. The same clash appears with VPA and resource requests, with service meshes and sidecar containers, and with any mutating webhook whose output you also declare in Git.

Senior: How would you design CI validation for Kubernetes manifests?

Layer the checks so each one catches what the previous cannot, and put the expensive, cluster-dependent checks last.

StageToolCatchesNeeds a cluster?
Syntax/schemakubeconform against the target versionTypos, wrong fields, removed APIs❌
Policy (offline)Conftest/OPA, Kyverno CLIMissing limits, :latest, running as root❌
Rendered diffhelm template / kustomize build → kubectl diffWhat will actually change✅
Server dry runapply --dry-run=serverDefaulting, admission webhooks, quota, RBAC✅
Convergencerollout status --timeoutThat it actually became healthy✅

Why the server dry run is non-negotiable: a client dry run only parses YAML. Every policy webhook, every quota, every defaulting rule and all RBAC are server-side. A manifest that passes client validation and is rejected by Kyverno in production is a review that provided false confidence — and the server dry run is the only step that exercises the same pipeline the real apply will.

What I would additionally insist on:

  • Validate against the cluster's actual version, so removed APIs are caught at upgrade time rather than after it.
  • Post kubectl diff into the pull request. Reviewing rendered diffs rather than templates is the single biggest reduction in "we didn't realise that changed".
  • Fail the pipeline on rollout status, since apply returning 0 says only that the object was stored — see the reconciliation loop.
  • Guard against ownership clashes: a lint rule rejecting replicas on any Deployment that has an HPA prevents the most common flap outright.

What I would not do: rely on a shared staging cluster as the only validation — it drifts, and it catches problems a day late. And I would avoid gating on offline policy alone, because the policies that actually run in production are the ones installed in production.

Senior: When would you use server-side apply, and what changes about how you write controllers and pipelines?

SSA is the right default for anything with more than one writer — which in a real cluster is nearly everything: your pipeline, HPAs and VPAs, service-mesh injectors, defaulting webhooks and operators all write to the same objects.

Problem with client-side applyWhat SSA does
Intent stored in an annotation (counts toward the ~1.5 MB limit)Ownership in managedFields
Object must have apply historyWorks on anything, however created
Two writers → silent last-writer-winsExplicit conflict error
Whole-object granularityPer-field

What changes in practice:

  • Every writer needs a stable fieldManager name. If your pipeline's manager name changes between runs, it orphans its own fields and stops being able to delete them.
  • Controllers should apply only the fields they own, sending a small partial object rather than a whole one. Sending the full spec claims ownership of everything in it — including fields another controller manages.
  • Conflicts are design feedback. The correct response is almost always to remove the field from one side, not to add --force-conflicts.
  • List merge semantics need listType markers on CRDs (map/set/atomic), or lists behave as atomic and one manager silently owns the whole list — the most common CRD authoring bug in this area.

The migration hazard worth naming: switching an existing pipeline to --server-side makes previously-invisible conflicts appear all at once, which looks like a regression and is actually years of accumulated ambiguity becoming visible. Do it in a low-traffic namespace first, expect a burst of conflicts, and resolve each by deciding the owner rather than forcing.

$ kubectl label deploy web tier=frontend           # on the DEPLOYMENT object
$ kubectl patch svc web -p '{"spec":{"selector":{"tier":"frontend"}}}'
$ kubectl get endpointslices -l kubernetes.io/service-name=web -o jsonpath='{.items[0].endpoints}{"\n"}'
                                ← empty again: pods do not carry that label

Habit: when a Service "does not work", check its EndpointSlice before anything else. It separates "no pods selected" from "pods selected but not Ready" in one command.

3 (medium): Demonstrate the three-way merge, and the imperative-creation trap.
Solution 
$ cat > web.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata: { name: web }

  replicas: 2
  selector: { matchLabels: { app: web } }
  template:
    metadata: { labels: { app: web } }
    spec:

$ kubectl apply -f web.yaml
$ kubectl get deploy web -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}' \
    | jq -r '.spec.template.spec.nodeSelector'
{ "disktype": "ssd" }                       ← recorded intent

$ sed -i '/nodeSelector/d' web.yaml && kubectl apply -f web.yaml

6 (hard): Write a safe read-modify-write loop against optimistic concurrency.
Solution 
$ RV=$(kubectl get deploy web -o jsonpath='{.metadata.resourceVersion}')
$ echo $RV
84213704
$ kubectl scale deploy web --replicas=5                 # someone else writes first
$ kubectl get deploy web -o json | jq ".metadata.resourceVersion=\"$RV\" | .spec.replicas=9" \
    | kubectl replace -f -
Error from server (Conflict): Operation cannot be fulfilled on deployments.apps "web":
the object has been modified; please apply your changes to the latest version and try again

That 409 is the protection working. The correct client pattern is retry-on-conflict:

$ cat > tools/annotate-retry.sh <<'SH'
#!/usr/bin/env bash
# Read-modify-write with bounded retry on optimistic-concurrency conflicts.
set -euo pipefail
obj=${1:?deploy/name}; key=${2:?key}; val=${3:?value}
for attempt in $(seq 1 5); do
  cur=$(kubectl get "$obj" -o json)                     # GET — fresh resourceVersion
  new=$(jq --arg k "$key" --arg v "$val" \
        '.metadata.annotations[$k] = $v' <<<"$cur")     # MODIFY
  if out=$(kubectl replace -f - <<<"$new" 2>&1); then   # PUT
    echo "ok on attempt $attempt"; exit 0
  fi
  grep -q Conflict <<<"$out" || { echo "$out" >&2; exit 1; }   # a real error
  sleep $(awk "BEGIN{print 0.1 * 2 ^ $attempt}")        # backoff, then re-READ
  echo "conflict, retrying ($attempt)" >&2
done
echo "gave up after 5 attempts" >&2; exit 1
SH
$ chmod +x tools/annotate-retry.sh

$ (while true; do kubectl scale deploy web --replicas=$((RANDOM%5+1)) >/dev/null; done) &
$ tools/annotate-retry.sh deploy/web deployed-by ci-4821
conflict, retrying (1)
conflict, retrying (2)
ok on attempt 3
$ kill %1
$ kubectl get deploy web -o jsonpath='{.metadata.annotations.deployed-by}{"\n"}'
ci-4821

Or avoid the whole problem — a patch never sends a resourceVersion, so it cannot conflict:

$ (while true; do kubectl scale deploy web --replicas=$((RANDOM%5+1)) >/dev/null; done) &
$ for i in $(seq 20); do
    kubectl patch deploy web --type=merge -p '{"metadata":{"annotations":{"n":"'$i'"}}}' >/dev/null
  done; echo "20 patches, 0 conflicts"
20 patches, 0 conflicts
$ kill %1
Write styleConflicts?Risk
replace with a stale RV409None — it protected you
replace with a fresh RV + retryHandledCorrect for whole-object rewrites
patch --type=mergeNeverBlindly overwrites concurrent edits to the same field
apply --server-sideConflict only on contended fieldsBest: precise, and it tells you who owns it

The nuance: a patch is not "safer" than a conflicting replace — it is simply not checking. For a single field you own, that is fine; for a read-modify-write on a value someone else may also be changing, the 409 is the only thing standing between you and a lost update.

🎯 Key Takeaways

  • Every object has the same five fields; the only unfamiliar part of a new resource is its spec.
  • spec is desire, status is observation — status lives on its own subresource and controllers overwrite anything you write there within seconds.
  • observedGeneration == generation answers "has the controller seen my change"; conditions answer "did it work". They are different questions.
  • Condition status is a string with three values: "Unknown" means unobservable, not false — automation that treats it as a boolean remediates on monitoring failures.
  • Alert on reason (machine-readable), never on message (human prose that changes between releases).
  • Labels are for selecting, annotations for carrying data; nothing in Kubernetes references a pod by name.
  • The labels a Service selects are on the pod template, and a Deployment's spec.selector is immutable — changing it means delete and recreate.
  • A selector that matches nothing is valid YAML — the failure is timeouts, and kubectl get endpointslices is the one-command diagnosis.
  • apply performs a three-way merge: in last-applied but not your YAML → delete; in your YAML → set; only on the live object → leave alone.
  • That third rule is why apply does not wipe fields added by webhooks, HPAs or defaulting controllers.
  • An object created with create has no last-applied, so the first apply cannot delete anything — verified: a stale nodeSelector survived the apply that removed it.
  • Server-side apply tracks ownership per field in managedFields, needs no history, and turns silent last-writer-wins into an explicit conflict.
  • An HPA and a GitOps tool both owning replicas oscillates forever — measured at 23 scaling events in ten minutes. The fix is deleting the field, not tuning either tool.
  • --force-conflicts is the wrong reflex: it takes ownership from a controller that was legitimately managing the field.
  • SSA writers need a stable fieldManager and should apply only the fields they own; CRDs need listType markers or lists behave as atomic.
  • resourceVersion gives optimistic concurrency: a stale one returns 409 Conflict, and the correct pattern is GET → modify → PUT → retry with backoff.
  • A merge patch never conflicts because it never checks — convenient for a field you own, a lost update for anything contended.
  • --dry-run=client only parses YAML; --dry-run=server runs defaulting, admission webhooks, quota and RBAC — the only rung that proves the cluster will accept it.
  • kubectl diff shows the rendered change and belongs in the pull request; reviewing templates instead of diffs is how surprises ship.
  • CI ladder: schema → offline policy → server dry run → diff → rollout status, because apply returning 0 means only that the object was stored.
