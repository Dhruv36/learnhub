StatefulSets & Stable Identity Configuration & State

What you'll master: the three guarantees a Deployment cannot give — stable ordinal names, stable per-pod storage, and ordered operations — and the mechanics that produce them; why a StatefulSet requires a headless Service and what breaks without it; the cost of OrderedReady, measured, where one stuck pod blocks every higher ordinal indefinitely, and when podManagementPolicy: Parallel is the right escape; partition-based rolling updates, which give you a canary by ordinal that Deployments have no equivalent for; the PVC lifecycle surprise — scaling down does not delete PVCs, and neither does deleting the StatefulSet — plus the retention policy that changes it; the force-delete hazard that turns a stuck pod into a split-brain database; and the honest question of when a StatefulSet is the wrong tool, which is more often than its reputation suggests. Prerequisites: Storage, Cluster DNS, Deployments.

apiVersion: apps/v1
kind: StatefulSet
metadata: { name: db }
spec:
  serviceName: db-headless          ← REQUIRED: this is what creates per-pod DNS
  replicas: 3
  selector: { matchLabels: { app: db } }
  template:
    metadata: { labels: { app: db } }
    spec:
      terminationGracePeriodSeconds: 60
      containers:
      - name: pg
        image: postgres:16-alpine
        volumeMounts: [{ name: data, mountPath: /var/lib/postgresql/data }]
  volumeClaimTemplates:             ← ONE PVC PER POD, created automatically
  - metadata: { name: data }
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: retain      ← see Storage: never the Delete default
      resources: { requests: { storage: 100Gi } }
