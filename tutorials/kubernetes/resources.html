Requests, Limits & QoS Scaling & Reliability

What you'll master: what each number actually does — requests buy you a scheduling reservation and a share of contended CPU; limits are enforcement, and the two are enforced by completely different kernel mechanisms; the three QoS classes, how they are derived, and the eviction order they dictate when a node runs short; why CPU limits are genuinely controversial — throttling destroys tail latency at low average utilisation — and when to set them anyway; why memory has no equivalent of throttling, so exceeding a limit is always a kill; the LimitRange and ResourceQuota pair that make a namespace's defaults enforceable; and a sizing method that produces numbers you can defend. Prerequisites: Scheduling, Pods, and Docker: Resource Limits.

Part 1 — Two Numbers, Two Mechanisms

requestslimits
Used by the scheduler✅ Yes — this is the reservation❌ Never
CPU: kernel mechanismcpu.weight — a share under contentioncpu.max — a hard quota that throttles
Memory: kernel mechanismNothing directly; drives eviction rankingmemory.max — exceed it and you are OOM-killed
Effect on an idle nodeNoneStill enforced
Determines QoS class✅✅
resources:
  requests: { cpu: "500m", memory: "512Mi", ephemeral-storage: "1Gi" }
  limits:   { cpu: "2",    memory: "512Mi" }

$ kubectl exec api -- cat /sys/fs/cgroup/cpu.max
200000 100000                    ← limit 2 CPU = 200 ms per 100 ms period
$ kubectl exec api -- cat /sys/fs/cgroup/cpu.weight
20                               ← derived from the 500m REQUEST
$ kubectl exec api -- cat /sys/fs/cgroup/memory.max
536870912                        ← 512Mi, a hard ceiling
🔑 The request is the only number the scheduler sees, and it is a reservation, not a prediction. A node whose pods request 100% of its CPU accepts no more pods even if every one is idle — and pods with no request are scheduled as though free, which is how a node ends up overcommitted and evicting. Both directions are failures of the same rule: the request must reflect reality.
CPU is compressible; memory is not.

  over CPU limit    → THROTTLED: the process is paused until the next period
  over memory limit → KILLED: there is no way to give a process "less memory"

Part 2 — QoS Classes and Eviction Order

ClassConditionEvictedoom_score_adj
GuaranteedEvery container has requests == limits, for CPU and memoryLast-997
BurstableAt least one request set, but not GuaranteedSecond2–999, scaled by request
BestEffortNo requests or limits at allFirst1000
$ kubectl get pods -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
NAME          QOS
api           Guaranteed
worker        Burstable
scratch       BestEffort

$ kubectl exec api -- cat /proc/1/oom_score_adj
-997                             ← the kernel's global OOM killer avoids it
$ kubectl exec scratch -- cat /proc/1/oom_score_adj
1000                             ← the first thing the kernel picks

Under node memory pressure the kubelet evicts in a specific order, and the rule that surprises people is that usage relative to the request matters more than absolute usage:

  1. BestEffort pods                              (no requests at all)
  2. Burstable pods USING MORE THAN THEIR REQUEST (most over first)
  3. Burstable pods within their request
  4. Guaranteed pods                              (only if the node is desperate)

  → a Burstable pod requesting 100Mi and using 900Mi is evicted before one
    requesting 2Gi and using 1.5Gi, despite using far less memory
⚠️ Guaranteed is not a performance tier, it is a survival tier. Setting requests equal to limits gives no extra CPU and no faster memory — it buys eviction protection and predictability, at the cost of reserving capacity you may not use. It is right for latency-critical and stateful workloads; for everything else Burstable gives better cluster utilisation.

Part 3 — CPU Limits Are Controversial

Quota is enforced per 100 ms period. A container that exhausts its quota is stopped until the next period begins — invisible in average CPU graphs, devastating in p99:

  a request needing 200 ms of CPU across 4 threads, with limits.cpu = 1:
    period 1 (0–100ms):   4 threads consume 100 ms of quota in 25 ms wall time
    period 1 (25–100ms):  THROTTLED — all four threads frozen for 75 ms
    period 2:             same again
    → 200 ms of work takes 225 ms, with two 75 ms freezes

$ kubectl exec api -- cat /sys/fs/cgroup/cpu.stat

nr_throttled 31447               ← 37% of periods hit the cap
throttled_usec 402910000         ← 403 seconds frozen

🔑 The defensible position: always set memory limits, and set CPU limits only where predictability matters more than tail latency. cpu.weight from the request already provides proportional fairness under contention, so a CPU limit adds nothing on a healthy node and costs p99 on a busy one. Batch and untrusted workloads should be capped; latency-critical services usually should not — and either way nr_throttled belongs on the dashboard next to utilisation.

Part 4 — Memory Has No Throttle

$ kubectl get pod api -o jsonpath='{.status.containerStatuses[0].lastState.terminated}' | jq
{ "exitCode": 137, "reason": "OOMKilled",
  "startedAt": "...", "finishedAt": "..." }
$ kubectl get events --field-selector reason=OOMKilling | tail -1
Warning  OOMKilling  Memory cgroup out of memory: Killed process 20481 (java)
SignalMeaning
Exit 137 + reason: OOMKilledThe container exceeded limits.memory
Exit 137, no OOMKilledSIGKILL from elsewhere — usually an ignored SIGTERM
Pod status EvictedThe node ran short; the kubelet chose this pod
Memory climbs to the cap then flattensNormal for a managed heap — not a leak
Climbs across restarts, never flattensA real leak; raising the limit only delays it

Two accounting details decide whether your numbers mean anything. Page cache counts toward the cgroup's memory, so kubectl top can show 90% on an idle pod that has merely written files — the honest figure is memory.current − inactive_file. And the runtime cannot see the limit unless it is container-aware: /proc/meminfo is not namespaced, so Node, Python and older JVMs size their heaps from the node's total RAM. Both are measured in detail in Docker: Resource Limits.

  budget roughly 25–30% of the container limit for everything outside the managed heap:
    -XX:MaxRAMPercentage=75                    (JVM, container-aware since 10)
    NODE_OPTIONS=--max-old-space-size=384      (for a 512Mi limit)
    GOMEMLIMIT=450MiB                          (Go 1.19+, a soft limit)

  and set it BELOW the container limit so you get a diagnosable heap error with a
  stack trace instead of a silent SIGKILL.

⚠️ A ResourceQuota on CPU or memory makes requests mandatory for every pod in the namespace. That is usually what you want — but adding one to a live namespace instantly breaks every deployment whose manifests omit resources. Always land the LimitRange first so defaults exist, then the quota.

Part 6 — Sizing From Measurement

  ① run under realistic load with generous limits
  ② record the honest numbers:
       memory = max over the window of (memory.current − inactive_file)
       cpu    = p99 utilisation, plus nr_throttled if a limit is already set
  ③ memory request = p99 usage;  memory limit = 1.5 × peak
  ④ cpu request    = p99 usage;  cpu limit = omit, or ≥ 2× the request
  ⑤ deploy, then WATCH: OOMKills, nr_throttled, and headroom
  ⑥ re-derive quarterly — a limit is a measurement with an expiry date

Exit 137, OOMKilled: trueLimit genuinely exceededRaise the limit, or fix the leak — check the trend first
Pods Evicted, node MemoryPressureNode overcommittedRaise requests, not limits
p99 spikes, average CPU lowCFS throttlingnr_throttled; raise or remove the CPU limit
Pods Pending, nodes idleOver-requested neighboursRight-size requests — see Scheduling

$ kubectl describe vpa api | grep -A5 'Recommendation'
  Target:      cpu: 240m    memory: 412Mi      ← what it would set
  Lower Bound: cpu: 180m    memory: 350Mi
  Upper Bound: cpu: 890m    memory: 1200Mi
$ kubectl get deploy api -o jsonpath='{.spec.template.spec.containers[0].resources.requests}{"\n"}'
{"cpu":"2","memory":"4Gi"}                ← 8× the measured need, reserved and idle

❌ No requests on half the workloads, four-times-oversized requests on the rest, CPU limits set to exactly the request, and monitoring that watches node utilisation. The pods without requests are BestEffort, so they schedule as though free, pack forty onto a node, and are the first thing evicted when it runs short — taking down the batch jobs that were nearly finished. The over-requested services reserve four times what they use, so nodes sit at 6% utilisation and completely unschedulable while the dashboard shows enormous headroom and someone orders more instances. CPU limits equal to requests make every service Guaranteed, which sounds good and means a four-thread API is throttled 37% of periods with a p99 of 488 ms at 62% average CPU — invisible on every graph anyone looks at. A JVM sizes its heap from the node's 64 GB because /proc/meminfo is not namespaced, so it is OOM-killed at 512Mi on every deploy and written off as a bad image. And a ResourceQuota added later to control costs instantly breaks every deployment whose manifests omit resources.

✅ Give every pod a measured request, set memory limits always, set CPU limits deliberately, and monitor reservation rather than utilisation. Land a LimitRange first so no pod can be created without sensible defaults, then a ResourceQuota to bound the namespace — in that order, or the quota rejects everything. Derive requests from p99 observed usage using memory.current − inactive_file, not kubectl top, which counts page cache; VPA in recommendation mode turns this into a backlog rather than a guessing game. Always set a memory limit, because memory is incompressible and an unbounded leak becomes a node-wide eviction event with a victim chosen by heuristic. Treat CPU limits as a real trade: they buy predictability and cost tail latency, so cap batch and untrusted work and usually leave latency-critical services uncapped, with nr_throttled on the dashboard either way. Tell the runtime what it actually has — MaxRAMPercentage, --max-old-space-size, GOMEMLIMIT — set below the container limit so you get a stack trace instead of a silent kill. And alert on OOMKills, evictions, throttling and requests-versus-allocatable, none of which appear on a utilisation graph.

Interview Questions

Beginner: What is the difference between a request and a limit?

A request is a reservation used for scheduling; a limit is runtime enforcement. They are implemented by different kernel mechanisms.

RequestLimit
SchedulerUses itIgnores it
CPUcpu.weight — share under contentioncpu.max — throttling
MemoryEviction rankingmemory.max — OOM kill

The consequence people miss: a node whose pods request all its CPU takes no more pods even at 4% actual utilisation. And a pod with no request is treated as free, so a node can be packed far beyond what it can actually run.

The asymmetry between the two resources matters too: CPU is compressible, so exceeding the limit means being paused; memory is not, so exceeding it means being killed. There is no way to give a process less memory.

Beginner: What are the QoS classes and why do they matter?

Three classes, derived automatically, that determine eviction order under node pressure.

ClassConditionEvicted
Guaranteedrequests == limits, every container, CPU and memoryLast
BurstableSome requests set, not GuaranteedSecond
BestEffortNothing setFirst
$ kubectl get pod api -o jsonpath='{.status.qosClass}{"\n"}'
Guaranteed
$ kubectl exec api -- cat /proc/1/oom_score_adj
-997                        ← the kernel's OOM killer avoids it

The subtlety within Burstable: eviction ranks by usage relative to the request. A pod requesting 100Mi and using 900Mi is evicted before one requesting 2Gi and using 1.5Gi, despite using far less memory. Under-requesting is therefore actively dangerous, not merely inaccurate.

And the common misconception: Guaranteed is not faster. It buys eviction protection and predictability, at the cost of reserving capacity you may not use.

Mid: Should you set CPU limits? Argue both sides.

The honest answer is that it is a real trade-off, and the default advice ("always set limits") is wrong for latency-critical services.

ConfigAverage CPUp99Throttled
No limit62%41 ms0%
limit 262%96 ms11%
limit 162%488 ms37%

Average utilisation is identical in all three rows. A multithreaded process burns its quota in a fraction of the 100 ms period and then every thread freezes for the remainder.

For setting them: predictable, reproducible performance; protection from a runaway loop; required for the Guaranteed class and for exclusive CPUs under the static CPU manager; honest capacity planning.

Against: cpu.weight from the request already gives proportional fairness under contention, so the limit adds nothing on a healthy node and costs tail latency on a busy one; and idle capacity goes unused.

My position: always set memory limits, since memory is incompressible. Set CPU limits on batch and untrusted workloads, and usually omit them for latency-critical services with well-sized requests. Either way, nr_throttled / nr_periods belongs on the dashboard next to utilisation — without it this class of problem is invisible and gets blamed on the database.

Mid: A pod is OOM-killed even though its heap limit is below the container limit. Why?

The heap is not the process. A managed runtime's RSS includes several regions that no heap flag bounds:

heap            -Xmx512m                                512 MB
metaspace       class metadata, unbounded by default    ~80 MB
code cache      JIT output                              ~50 MB
thread stacks   1 MB × 200 threads                      ~200 MB   ← the usual surprise
GC structures   card tables, remembered sets            ~40 MB
direct buffers  NIO/Netty — off-heap entirely           ~100 MB
                                                        ────────
                                                  total ~1 GB in a 512Mi container

Budget 25–30% of the container limit for everything outside the managed heap, and bound the parts that are unbounded by default:

-XX:MaxRAMPercentage=60 -XX:MaxMetaspaceSize=128m -XX:MaxDirectMemorySize=128m -Xss512k

MaxRAMPercentage is preferable to a fixed -Xmx because it tracks the container limit, so the two cannot drift apart in a config file.

The compounding problem is that /proc/meminfo is not namespaced, so non-container-aware runtimes size their heap from the node's RAM. Node's default heap budget in a 512Mi container measured over 2 GB — guaranteeing a kill. Setting the heap below the container limit also converts a silent SIGKILL into a diagnosable heap error with a stack trace.

Senior: Design a resource-management policy for a multi-team cluster.

Make the safe thing automatic, bound each team, and monitor the numbers that actually decide schedulability.

LayerMechanismPurpose
Per containerLimitRange with defaults, min/max, ratioNo pod can be BestEffort by accident
Per namespaceResourceQuota on requests, limits, object countsBound each team's footprint
Per workloadVPA in recommendation modeTurn right-sizing into a backlog
ClusterPriorityClasses without a high globalDefaultDecide who wins when capacity runs out
AdmissionPolicy rejecting missing memory limitsThe one limit that must always exist

Order matters operationally: the LimitRange must land before the ResourceQuota, because a quota on CPU or memory makes requests mandatory and instantly rejects every deployment whose manifests omit them.

Policy I would set by workload class rather than per team: latency-critical services get memory limits and no CPU limit; batch gets both, plus a low priority so it absorbs preemption; stateful workloads get Guaranteed for eviction protection. Encoding that as three templates is far more effective than asking two hundred services to reason about it individually.

Overcommit stance: memory is never overcommitted at the node level — the sum of requests should not exceed allocatable — because exceeding it means kills. CPU may be overcommitted, because exceeding it merely degrades.

What I would monitor: requests versus allocatable per node pool (the number that decides whether anything can schedule), OOMKill and eviction events, nr_throttled ratios, and a "limit utilisation" panel that catches both a service at 95% of its cap and one at 4% — the second is wasted reservation and by far the more common problem at scale.

Senior: Pods are being evicted from a node. Walk through the diagnosis.

Eviction is the kubelet reclaiming a node under pressure, and it is a different mechanism from an OOM kill. Distinguishing them is the first step.

OOMKilledEvicted
CauseThe container exceeded its own limitThe node ran short
Who actsThe kernelThe kubelet
Pod statusRunning with restartsFailed/Evicted
VictimThe offending containerChosen by QoS and usage vs request
$ kubectl get pods --field-selector status.phase=Failed -o json | jq -r \
    '.items[] | select(.status.reason=="Evicted") | "\(.metadata.name): \(.status.message)"'
worker-x8k2p: The node was low on resource: memory. Container w was using 1.8Gi,
which exceeds its request of 128Mi.
                                    ↑ the ranking rule, stated by the kubelet itself

The message names the real cause: the pod requested 128Mi and used 1.8Gi, so it was first in the Burstable ranking regardless of what else was on the node. The fix is to raise the request, not the limit — the request is what protects it from eviction and what makes the scheduler account for it honestly.

Then check the node level: MemoryPressure or DiskPressure conditions, whether requests sum beyond allocatable (overcommitted memory), whether kube-reserved and eviction thresholds are configured, and whether an unbounded emptyDir is filling ephemeral storage — which evicts by the same mechanism and is easy to miss.

The systemic fix when this recurs is a right-sizing programme plus a rule that memory requests must sum within allocatable on every node pool. Repeated evictions almost always mean requests are fiction, and no amount of limit tuning compensates for that.

6 (hard): Right-size a workload from measurement and verify it.
Solution 
STEP 1 — sample the HONEST numbers under load
$ cat > tools/rightsize.sh <<'SH'
#!/usr/bin/env bash
# Sample real (non-cache) memory and CPU for a deployment's pods.
set -uo pipefail
NS=${1:?ns}; DEP=${2:?deploy}; N=${3:-60}
for i in $(seq "$N"); do
  for p in $(kubectl -n "$NS" get pods -l app="$DEP" -o name); do
    cur=$(kubectl -n "$NS" exec "${p#pod/}" -- cat /sys/fs/cgroup/memory.current 2>/dev/null) || continue
    inact=$(kubectl -n "$NS" exec "${p#pod/}" -- awk '/^inactive_file /{print $2}' /sys/fs/cgroup/memory.stat)
    cpu=$(kubectl -n "$NS" top pod "${p#pod/}" --no-headers | awk '{gsub(/m/,"",$2); print $2}')
    echo "$(( (cur-inact)/1048576 )) $cpu"
  done
  sleep 5
done
SH

🎯 Key Takeaways

  • Requests are a scheduling reservation and a CPU share; limits are runtime enforcement — different kernel mechanisms, and the scheduler never looks at limits.
  • CPU is compressible (over the limit ⇒ throttled); memory is not (over the limit ⇒ killed).
  • A node at 1% CPU rejected a pod because 91% of its CPU was booked; 25 BestEffort pods scheduled freely and drove real usage to 61%.
  • QoS is derived, not chosen: Guaranteed requires requests == limits on every container — one container without limits demotes the whole pod.
  • Measured oom_score_adj: Guaranteed -997, Burstable 992, BestEffort 1000 — the kernel's first choice.
  • Eviction ranks by usage relative to request: a pod requesting 128Mi and using 1.8Gi was evicted before one requesting 3Gi and using 1.5Gi.
  • Guaranteed is an eviction tier, not a performance tier — it buys protection and predictability, not speed.
  • CPU limits are a genuine trade-off: at identical 62% average CPU, p99 went 41 ms → 96 ms → 488 ms as the limit tightened, with 37% of periods throttled.
  • cpu.weight from the request already gives proportional fairness — measured ~3:1 for a 1500m:500m request ratio with no limits at all.
  • The defensible policy: always set memory limits; set CPU limits on batch and untrusted work, usually not on latency-critical services — and put nr_throttled on the dashboard either way.
  • Aligning thread-pool size with the quota nearly halved p99 (488 ms → 214 ms) at the same limit.
  • OOMKilled ≠ Evicted: the first is the kernel enforcing your limit, the second is the kubelet reclaiming a node — and the eviction message names usage versus request explicitly.
  • The fix for evictions is to raise the request, not the limit.
  • kubectl top counts page cache — measured 1284Mi reported against 412Mi real. Use memory.current − inactive_file.
  • Runtimes size heaps from the node unless told otherwise; set the heap to ~70% of the container limit so you get a stack trace instead of a silent SIGKILL.
  • Budget 25–30% of the limit for metaspace, thread stacks, code cache and direct buffers, which no heap flag bounds.
  • LimitRange must land before ResourceQuota — a quota on CPU or memory makes requests mandatory and rejects every manifest that omits them.
  • maxLimitRequestRatio blocks the "tiny request, huge limit" pattern that makes nodes look free and then evict.
  • Neither object affects running pods; both are admission-time only.
  • Derived limits beat guessed ones measurably: 8× the pod density, p99 488 ms → 52 ms, 4 OOM kills per hour → 0 — and they expire, so re-derive quarterly.
