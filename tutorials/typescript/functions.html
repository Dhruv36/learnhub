Functions, Overloads & Signatures Foundations

What you'll master: how parameters, returns and callbacks get their types, and where annotation earns its place; overloads — the declaration form, why the implementation signature is invisible to callers, and why a union or a generic is usually the better tool; this as a typed parameter, and how strictBindCallApply makes call and bind type-checked; type predicates and assertion functions, including the rule that assertion functions must be referenced through an explicitly annotated name; the three "returns nothing" types (void, undefined, never) and why a value-returning callback is accepted where void is expected; and how to design a signature other people can read. Prerequisites: Structural Typing & Assignability.

Part 1 — Parameters, Returns and Contextual Typing

Parameters must be typed (noImplicitAny is part of strict, so on by default in TypeScript 7). Return types are inferred, and usually should be — except at module boundaries, where an annotation is a contract.

function area(w: number, h: number) { return w * h; }     // returns number, inferred

export function parseUser(raw: unknown): User { … }       // annotate EXPORTED returns:
                                                          // the contract stops drifting silently

const nums = [1, 2, 3];
nums.map(n => n * 2);         // n is number — CONTEXTUAL typing from the array
FormMeaningNote
(a: string, b?: number)b may be omittedIts type is number | undefined inside the body
(a: string, b = 0)Default valueCallers may omit it; b is number inside
(...rest: string[])VariadicTuples give precise rest types: ...args: [string, number]
(cb: (e: Event) => void)Callback as a property typeParameters checked contravariantly (lesson 3)
function f(this: T, …)Typed thisErased: it is not a real parameter
🔑 Annotate contracts, infer the rest. Inferred return types stay correct as the body changes, which is usually what you want inside a module. At an exported boundary the opposite is true: an inferred return silently becomes part of your public API, so a refactor can change what consumers see without any warning. Annotating exported functions turns that into a compile error in your own code, where it belongs.

Part 2 — Overloads, and Why They Disappoint

Overloads declare several call signatures for one implementation. The implementation signature is not one of them — callers never see it.

function parse(x: string): string[];        // overload 1
function parse(x: number): number[];        // overload 2
function parse(x: string | number): unknown[] { return [x]; }   // implementation: INVISIBLE

parse("s");      // string[]
parse(5);        // number[]

declare const either: string | number;
parse(either);
// error TS2769: No overload matches this call.
//   The last overload gave the following error.
//     Argument of type 'string | number' is not assignable to parameter of type 'number'.

That error surprises people: the implementation clearly accepts string | number, but callers may only use the declared overloads, and neither accepts a union. Resolution picks the first matching overload in declaration order, so ordering matters — put the most specific first.

Problem with overloadsConsequence
The implementation signature is invisibleA union argument fails even though the body handles it
The implementation is checked loosely against the overloadsAn implementation can claim a return type it does not deliver
Order is significantA broad overload placed first shadows the specific ones
No relationship between argument and returnEvery combination must be written out by hand
// usually better: a union parameter
function parse(x: string | number): unknown[] { … }

// or, when the RETURN depends on the argument, a generic — one signature, related types
function first<T>(xs: readonly T[]): T | undefined { return xs[0]; }

// or a conditional return type, for genuinely dependent shapes (later in the track)

Where overloads are still right: describing existing JavaScript whose behaviour genuinely differs by argument type (document.createElement returning a different element per tag), and APIs where a generic would be less readable than two clear signatures. In new code, reach for a union or a generic first, and treat overloads as a fallback.

Part 3 — this, and Checked call/bind

this can be declared as a fake first parameter. It is erased, costs nothing, and makes the compiler enforce how the function may be called.

function withThis(this: { n: number }, k: number) { return this.n + k; }

withThis(1);
// error TS2684: The 'this' context of type 'void' is not assignable to method's 'this'
//               of type '{ n: number; }'.

withThis.call({ n: 1 }, 2);        // ✔ correct

strictBindCallApply (part of strict) type-checks call, apply and bind instead of accepting anything:

const f = (a: string, b: number) => a + b;
f.call(null, "x", "y");
// error TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.
SituationBehaviour
Arrow functionNo this of its own — it closes over the enclosing one, so a this parameter is meaningless
Method extracted from an objectLoses its receiver; a this parameter makes that a compile error rather than a runtime one
Callback libraries that set thisDeclare this in the callback type so handlers can use it safely
strictBindCallApply offcall/apply/bind accept any arguments

Part 4 — Type Predicates and Assertion Functions

Two special return forms let a function teach the compiler something. They are the bridge between runtime checks and static types — the mechanism behind every custom narrowing helper.

// a type PREDICATE: returns boolean, and narrows in the true branch
function isString(v: unknown): v is string { return typeof v === "string"; }

if (isString(u)) u.toUpperCase();    // ✔ narrowed to string

// an ASSERTION function: returns void, and narrows everything after the call
function assertIsString(v: unknown): asserts v is string {
  if (typeof v !== "string") throw new Error("not a string");
}

assertIsString(u);
u.toUpperCase();                     // ✔ narrowed from here on

❌ Storing an assertion function in a variable and calling it. The narrowing silently stops working, with an error that reads like a compiler bug: error TS2775: Assertions require every name in the call target to be declared with an explicit type annotation.

✅ Call assertion functions through a name with an explicit type annotation — a function declaration, or a const annotated with the assertion signature. The restriction exists because the compiler must know the signature before checking the call, which inference cannot guarantee.

const anon = assertIsString;          // inferred type
anon(u);                              // error TS2775 …
u.toUpperCase();                      // error TS18046: 'u' is of type 'unknown'

const named: (v: unknown) => asserts v is string = assertIsString;   // explicit annotation
named(u);
u.toUpperCase();                      // ✔ works

Both forms are promises the compiler cannot verify. A predicate that returns true for the wrong values, or an assertion that fails to throw, produces a type the rest of the program believes and the data does not support. Keep their bodies small, obvious, and ideally derived from a schema — which is what the runtime-validation lesson does.

Part 5 — The Three Ways to Return Nothing

Return typeMeansUse for
voidThe caller should not use the valueCallbacks, event handlers, side-effecting functions
undefinedThe function genuinely returns the value undefinedWhen the caller may legitimately read it
neverThe function never returns normallyThrowing helpers, infinite loops, exhaustiveness checks
Promise<T>An async function always returns a promiseAnnotate Promise<T>, never bare T
// void accepts a value-returning function — deliberately
const ids = new Set<number>();
[1, 2, 3].forEach(n => ids.add(n));     // add() returns the Set; forEach expects void. ✔ fine

// never proves a branch is unreachable
function fail(msg: string): never { throw new Error(msg); }

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2;
    case "square": return s.side ** 2;
    default: return fail(`unhandled: ${(s as never).kind}`);   // add a Shape → compile error here
  }
}

The void rule is why callbacks are pleasant. If void meant "must return undefined", half the idiomatic one-liners in JavaScript would be type errors. The trade is that a callback's return value is silently discarded — which is correct for forEach and a real bug when someone expected the values to be collected.

Optional parameters are a contract too. Adding one to an exported function is safe; making an existing one required is a breaking change, and so is adding a parameter before an existing one. Options objects absorb both kinds of change, which is why they dominate public APIs.

Interview Questions

Beginner: When should you annotate a function's return type?

At contracts, and rarely elsewhere. For a function exported from a module or package, the return type is part of the public API, so I annotate it: the annotation stops a refactor from changing what consumers see without anyone noticing, and it puts the error in the file being changed rather than in a consumer's build.

Inside a module, inference is usually better. It stays correct as the body evolves, it is less to read, and it cannot drift out of date the way a hand-written annotation can.

There are two other cases worth annotating. Recursive functions sometimes need one to avoid a circular inference error. And a function whose body currently returns something narrower than intended — a helper that returns "a" today but is meant to return a whole union — should be annotated, or the narrow inferred type becomes an accidental constraint on callers.

Parameters are different: they must be typed under noImplicitAny, except where contextual typing supplies them, as in a callback passed to map.

Beginner: What is a type predicate?

A function whose return type is written v is T rather than boolean. It returns a boolean at runtime, and it tells the compiler that when the result is true, the argument may be treated as T in that branch.

It is how you write a custom narrowing helper for a check the compiler cannot do itself — validating a shape, distinguishing two interfaces, checking a value came from a known set. Without the predicate, a helper returning plain boolean narrows nothing, and callers are left doing the check twice or reaching for an assertion.

Its close relative is an assertion function, written asserts v is T, which returns void and narrows everything after the call rather than inside an if. Assertion functions have an extra rule: they must be called through a name with an explicit type annotation, or the compiler reports TS2775 and does not narrow.

The important caveat is that both are promises the compiler cannot check. If the body returns true for a value that is not a T, everything downstream is wrong, with no warning — which is why predicates are best kept tiny or derived from a schema validator.

Mid: Why does calling an overloaded function with a union argument fail?

Because overload resolution tries each declared signature in order and needs one that accepts the whole argument type. A union like string | number matches neither (x: string) nor (x: number) — for each overload, part of the union is invalid — so resolution fails with TS2769.

What confuses people is that the implementation signature usually does accept the union; it has to, in order to handle both cases. But the implementation signature is not callable: it exists only to type-check the body, and callers see only the declared overloads.

The fixes, in the order I would consider them: narrow before calling, since the caller usually knows which case it has; replace the overloads with a single union-parameter signature if the return type does not depend on the argument; or use a generic or conditional return type if it does. Adding a third overload accepting the union is possible, but it also means declaring what that call returns, which is often the union of both returns and no more useful than the first option.

More broadly this is why I treat overloads as a tool for describing existing JavaScript rather than a default for new APIs: they do not compose with unions, they are order-sensitive, and the implementation is checked only loosely against them.

Mid: What does a this parameter do, and when do you need one?

It declares the type this must have when the function is called. It is written as a first parameter, is not a real argument, and is erased — but the compiler then rejects calls where this would be wrong, with TS2684.

I need it in three situations. When a function is meant to be used as a method of a particular shape and would break if extracted and called alone. When a library invokes my callback with a specific this — jQuery-style APIs, some test frameworks — so handlers can use it with types. And when writing a declaration file for existing JavaScript that depends on its receiver.

Arrow functions are the exception: they have no this of their own, so a this parameter on one is meaningless. That is also why arrows are the usual fix for callbacks that lose their receiver.

Alongside it, strictBindCallApply — part of strict — type-checks call, apply and bind, so passing the wrong argument through call is an error rather than being accepted as it once was. Together they turn a classic class of JavaScript runtime bug into compile errors.

Senior: Design the signature for a data-fetching helper used across a large codebase.

I would optimise for readability at the call site, evolvability, and honest error handling — the three things that hurt when a helper is used in hundreds of places.

export async function request<T>(
  url: string,
  options: {
    method?: "GET" | "POST" | "PUT" | "DELETE";
    body?: unknown;
    headers?: Readonly<Record<string, string>>;
    timeoutMs?: number;
    signal?: AbortSignal;
    parse: (raw: unknown) => T;          // required: the caller says how to validate
  },
): Promise<T>;

Why each choice: an options object rather than positional parameters, so adding a feature is never a breaking change and call sites read as prose. Literal unions for method, so typos are compile errors. body: unknown rather than any, so it must be serialised deliberately. A required parse function returning T, which is the important decision: it makes validation unavoidable and means T is earned rather than asserted — the lesson-1 point that an annotation on a response is a claim.

What I would avoid: overloads for the different methods, because they multiply without adding information; a Promise<any> return, which disables checking everywhere it is used; and boolean flags such as request(url, true).

Error handling deserves an explicit decision: either the helper throws and callers use try/catch, or it returns a discriminated result type. I would pick one and apply it everywhere, because a codebase where half the helpers throw and half return results is the worst of both — that is the subject of the errors lesson.

Senior: A team's helpers use type predicates heavily and bugs still slip through. What would you change?

Type predicates are unchecked promises, so heavy use concentrates risk in exactly the places the compiler cannot help. I would look at what the predicates actually assert.

First, find the lying predicates. A body like return typeof v === "object" && v !== null && "id" in v asserting v is User checks one property and promises a whole interface. Everything downstream then trusts fields nobody verified. The tell is a predicate whose body is much smaller than the type it claims.

Second, replace hand-written predicates at boundaries with schema validation. A schema library gives a parse function that both checks at runtime and produces the type, so the type is derived from the check rather than promised alongside it. Inside the program, where values are already typed, predicates are usually unnecessary — a discriminated union and a switch narrow without any custom helper, and the compiler verifies the narrowing.

Third, make the remaining predicates testable. Keep them tiny, one property each, and unit-test the negative cases — the value that should not pass is the one that matters.

Recommendation: schemas at the edges, discriminated unions inside, and predicates only for small structural checks that are covered by tests. The pattern to eliminate is the predicate that asserts a rich domain type after checking one field, because it converts a data problem into a type-system lie that propagates silently.

4 (medium): Show why void accepts value-returning callbacks — and when that hides a bug.
Solution 
const ids = new Set<number>();
[1, 2, 3].forEach(n => ids.add(n));     // add() returns Set; forEach wants void — ✔ allowed

// the same rule hides this:
type Validator = (value: string) => void;
const validators: Validator[] = [
  (v) => v.length > 0,                  // ✔ accepted — the boolean is DISCARDED
];
function runAll(v: string) { return validators.every(f => f(v)); }
// every() sees undefined from each call → falsy → runAll always returns false
DesignBehaviour
(value: string) => voidAny return is accepted and thrown away
(value: string) => booleanCallers must return; every works
(value: string) => string | nullReturns an error message or nothing — usually the most useful

The rule itself is correct and necessary; the lesson is to type a callback as void only when you genuinely intend to ignore its result, because the compiler will not tell you that the value you expected is being dropped.

🎯 Key Takeaways

  • Parameters must be typed; return types are usually better inferred — except at exported boundaries, where they are a contract.
  • Contextual typing gives callback parameters their types, so annotating them is usually noise.
  • An overload's implementation signature is invisible to callers, which is why a union argument fails with TS2769.
  • Overload resolution takes the first matching signature, so order most specific first.
  • Prefer a union parameter or a generic to overloads in new code; keep overloads for describing existing JavaScript.
  • A this parameter is erased but enforced (TS2684), turning a classic runtime bug into a compile error.
  • Arrow functions have no this of their own, so a this parameter on one means nothing.
  • strictBindCallApply type-checks call, apply and bind.
  • A type predicate (v is T) narrows in the true branch; an assertion function (asserts v is T) narrows everything after the call.
  • Assertion functions must be called through an explicitly annotated name, or TS2775 and no narrowing.
  • Predicates and assertions are unchecked promises — keep them tiny or derive them from schemas.
  • void means "ignore the result", not "returns undefined", and it accepts value-returning callbacks.
  • never means the function does not return normally, which powers exhaustiveness checks.
  • async functions return Promise<T> — annotate the promise, not the value.
  • Options objects beat positional booleans: readable calls, and adding a field is never breaking.
