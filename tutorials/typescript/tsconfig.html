tsconfig in Depth Modules, Config & Build

What you'll master: what tsc --init actually writes in TypeScript 7 — a short, opinionated file that turns on more than strict does; target and lib, and the targets that no longer exist; module and moduleResolution as matched pairs, with classic, node10, amd, umd and system all gone; the single-file-emit family — isolatedModules, verbatimModuleSyntax and moduleDetection — and the TS1484, TS1205 and TS1295 errors they produce; file selection with include, exclude and extends; and project references for a repo with more than one build. Prerequisites: Strictness Flags.

Part 1 — What tsc --init Writes

The generated file is the best single statement of what the TypeScript team considers a sane default, and in version 7 it is short:

$ npx tsc --init                       ◄── comments stripped for brevity
{
  "compilerOptions": {
    "module": "nodenext",
    "target": "esnext",
    "types": [],
    "sourceMap": true,
    "declaration": true,
    "declarationMap": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "strict": true,
    "jsx": "react-jsx",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "moduleDetection": "force",
    "skipLibCheck": true
  }
}
🔑 Two of those are not part of strict. noUncheckedIndexedAccess and exactOptionalPropertyTypes are the two flags lesson 10 argued for separately, and the default config now enables both. A new project that starts from tsc --init gets them; one that inherited a hand-written config from years ago almost certainly does not.

Part 2 — target and lib

target decides the syntax level of the emitted JavaScript and the default lib. lib decides which global APIs the compiler believes exist.

$ npx tsc t.ts --noEmit --target es5
error TS5108: Option 'target=ES5' has been removed. Please remove it from your configuration.
OptionControlsGetting it wrong
targetOutput syntax; default libDownlevelled output nobody needed
libWhich globals exist at compile timeCompiles, then undefined is not a function
typesWhich @types packages load globallyDOM types in a Node project

lib and target are independent, and that is the source of a real class of bug. Setting lib: ["esnext"] while deploying to an older runtime makes Array.prototype.at type-check and then fail at run time — the compiler was told the API exists, not asked to provide it. lib should describe the runtime you actually deploy to; polyfills are a separate decision the compiler knows nothing about.

The nodenext family reads package.json, which is where the confusing errors come from. Under module: nodenext, whether a .ts file is an ES module or CommonJS depends on the nearest package.json's type field — so ESM syntax in a package without "type": "module" gives:

error TS1295: ECMAScript imports and exports cannot be written in a CommonJS file under
  'verbatimModuleSyntax'. Adjust the 'type' field in the nearest 'package.json' ...
                                        ◄── verified

The fix is the one the message names: set "type": "module", or use the bundler/preserve combination where the bundler resolves modules and the compiler stays out of it.

Part 4 — The Single-File-Emit Family

Three options exist because modern build tools transpile one file at a time, with no view of the program. They forbid the constructs that need whole-program knowledge.

// isolatedModules: a re-export cannot be resolved file-locally
export { A } from "./dep.js";
// error TS1205: Re-exporting a type when 'isolatedModules' is enabled
//               requires using 'export type'.                        ◄── verified

// verbatimModuleSyntax: a type imported as a value would be emitted as a real import
import { A } from "./dep.js";
export type Use = A;
// error TS1484: 'A' is a type and must be imported using a type-only import
//               when 'verbatimModuleSyntax' is enabled.              ◄── verified
OptionRequiresBecause
isolatedModulesexport type for type re-exportsA single-file transpiler cannot tell a type from a value
verbatimModuleSyntaximport type for type importsImports are emitted exactly as written
moduleDetection: "force"Nothing — it makes every file a moduleNo accidental script-scope globals
noUncheckedSideEffectImportsSide-effect imports to resolveA typo used to be silently ignored

verbatimModuleSyntax replaced the older importsNotUsedAsValues and preserveValueImports, both of which TS7 removed. Its rule is simple and worth stating as a habit rather than a setting: if you import something only for its type, write import type. That is good practice regardless of the flag, because it makes the runtime cost of every import visible at the import site.

Part 5 — File Selection and extends

{
  "extends": "./tsconfig.base.json",
  "compilerOptions": { "outDir": "dist", "rootDir": "src" },
  "include": ["src/**/*"],
  "exclude": ["**/*.test.ts"]

KeyMeaningTrap
includeGlobs to compileDefaults to everything if omitted
excludeFilters include onlyDoes not exclude imported files
filesAn explicit listIgnores include/exclude
extendsInherit a base configRelative paths resolve from the base file
rootDirThe input root for output layoutWrong value scatters dist

❌ Assuming exclude keeps a file out of the build. It only narrows what include picked up. A file that is excluded but imported from an included file is still compiled, still type-checked, and still emitted — so excluding **/*.test.ts does nothing at all if a source file imports a test helper, and the surprise usually shows up as test code in a production bundle.

✅ Use separate projects when you need real separation. A tsconfig.json for src and a tsconfig.test.json that extends it and includes the tests keeps the two sets genuinely apart, and lets the test project have looser settings if it needs them. exclude is for keeping node_modules and dist out of the default glob, not for enforcing a boundary.

Part 6 — Project References

One tsconfig per buildable unit, with explicit dependencies, lets the compiler skip work and enforce layering.

// packages/app/tsconfig.json
{
  "compilerOptions": { "composite": true, "outDir": "dist", "rootDir": "src" },
  "references": [{ "path": "../core" }],
  "include": ["src/**/*"]
}

$ npx tsc --build            // builds dependencies in order, skips what is up to date
$ npx tsc --build --watch
$ npx tsc --build --force    // ignore the caches
RequirementWhy
composite: trueEmits .tsbuildinfo so builds can be skipped
declaration (implied by composite)Dependents read .d.ts, not source
referencesDeclares the dependency; an undeclared import errors
tsc --buildPlain tsc ignores references

The layering enforcement is often worth more than the speed. Because a project may only import from what it references, an accidental import from core into a leaf package — or a circular dependency between two packages — becomes a compile error instead of a convention nobody checks.

Interview Questions

Beginner: What is the difference between target and lib?

target controls the syntax level of the emitted JavaScript — whether an arrow function or a class field is downlevelled. lib controls which global APIs the compiler believes exist, such as Array.prototype.at or structuredClone.

target sets a default lib, which is why most projects never mention lib at all. But the two are independent, and that independence is where bugs come from: setting lib: ["esnext"] while deploying to an older runtime makes new APIs type-check perfectly and then throw at run time. The compiler was told the API exists, not asked to provide it.

So the rule is that lib should describe the runtime you actually deploy to. Polyfills are a separate decision the compiler knows nothing about — if you polyfill at, you are responsible for both including the polyfill and telling lib it is there.

In TypeScript 7 the default target from tsc --init is esnext, and es5 has been removed entirely — --target es5 is now TS5108.

Beginner: What does tsc --init give you in TypeScript 7?

A short, opinionated config rather than the long commented catalogue older versions produced. The compiler options it sets are module: nodenext, target: esnext, types: [], source maps, declaration and declarationMap, noUncheckedIndexedAccess, exactOptionalPropertyTypes, strict, jsx: react-jsx, verbatimModuleSyntax, isolatedModules, noUncheckedSideEffectImports, moduleDetection: force and skipLibCheck.

The notable part is that two of those are not members of strict: noUncheckedIndexedAccess and exactOptionalPropertyTypes. A project created today gets them; a project running a config written a few years ago almost certainly does not, which is worth checking rather than assuming.

types: [] is also worth understanding — without it, every @types/* package in node_modules is loaded into the global scope, which is how a Node project ends up with DOM globals it cannot actually use.

It is a good baseline to start from and to compare an existing config against, since the diff shows exactly which modern defaults a project is missing.

Mid: How do module and moduleResolution relate?

They have to agree, and the compiler enforces it. Setting module: esnext with moduleResolution: node16 gives TS5110: "Option 'module' must be set to 'Node16' when option 'moduleResolution' is set to 'Node16'" — I verified that.

In practice there are two combinations. For Node, module: nodenext with the matching resolution, which follows Node's own rules — including reading the nearest package.json's type field to decide whether each file is ESM or CommonJS. For anything behind a bundler, module: preserve or esnext with moduleResolution: bundler, which leaves module resolution to the tool that will actually do it.

TypeScript 7 removed several old values. moduleResolution: classic and node/node10 are both TS5108, and the accepted module list — which the compiler prints on an invalid value — no longer includes amd, umd or system.

The error people actually hit is TS1295, ESM syntax in a file the compiler considers CommonJS, which happens under nodenext when package.json lacks "type": "module". The message names the fix, and the underlying point is that under the nodenext family the package manifest is part of your TypeScript configuration whether you think of it that way or not.

Mid: Why do isolatedModules and verbatimModuleSyntax exist?

Because modern build tools — esbuild, SWC, Vite, Babel — transpile one file at a time with no view of the rest of the program, and some TypeScript constructs cannot be compiled correctly that way.

isolatedModules forbids the ones that need whole-program knowledge. Re-exporting a name that turns out to be a type is the clearest case: a single-file transpiler cannot tell whether export { A } from "./dep" should emit a runtime re-export or nothing at all. The error is TS1205, "Re-exporting a type when 'isolatedModules' is enabled requires using 'export type'" — verified.

verbatimModuleSyntax goes further: imports are emitted exactly as written, so a type imported as a value would become a real runtime import of something that does not exist. That is TS1484, "'A' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled" — also verified.

It replaced the older importsNotUsedAsValues and preserveValueImports, both removed in TS7. And its rule is worth adopting as a habit rather than treating as a setting: if something is imported only for its type, write import type. That makes the runtime cost of each import visible at the import site, which is useful even where no flag requires it.

Senior: Design the TypeScript configuration for a monorepo.

The goals are that each package builds independently, that layering is enforced rather than merely documented, and that a change to a leaf package does not rebuild the world.

A base config plus one per package. A single tsconfig.base.json holds the compiler options every package shares — strictness, target, the module pair, declaration, composite. Each package extends it and adds only rootDir, outDir, include and its references. The trap to watch is that relative paths inside an extended config resolve from the base file, so path-valued options belong in the leaf configs.

Project references for real boundaries. With composite: true and explicit references, a package can only import from what it declares, so an import that violates the intended layering fails to compile and a cycle between two packages is caught immediately. That is usually worth more than the build-time saving, because conventions about layering decay and compiler errors do not.

Separate projects rather than exclude for tests. exclude only filters what include matched; an excluded file that is imported is still compiled. So tests get their own tsconfig.test.json that extends the package config, which also lets test code run under slightly looser settings without weakening the source build.

Recommendation: one base config, one per package with composite and references, tsc --build everywhere including CI — plain tsc silently ignores references — a separate test project per package, and a CI check that the base config has not drifted from what tsc --init currently generates. That last one is how you notice new recommended defaults instead of carrying a config from three years ago forever.

Senior: A team has one 5,000-file tsconfig and slow builds. What do you change?

I would treat it as two separate problems — how much work the compiler does, and how often it has to redo it — because the fixes are different and only the second one needs restructuring.

Measure first. tsc --diagnostics gives check time, memory and instantiation counts; --generateTrace produces a profile that names the expensive types and files. That distinguishes a genuinely large program from one pathological conditional type, and I have seen both diagnosed as "TypeScript is slow". The compiler-performance lesson goes through reading that output.

Cheap wins before restructuring. skipLibCheck on, which stops type-checking every dependency's declarations; types: [] so only the @types packages actually needed are loaded; incremental so a warm rebuild reuses .tsbuildinfo; and confirming that include is not quietly picking up dist or generated code.

Then split into projects. Project references let the compiler skip packages whose inputs have not changed, and make each rebuild proportional to the change rather than to the repo. The migration is real work — every cross-package import has to become a declared reference, which surfaces the cycles that were previously invisible — but that surfacing is itself valuable.

Separate type-checking from emit, if the split does not get there. Let esbuild or SWC produce the JavaScript fast and run tsc --noEmit as a parallel check. That is why isolatedModules and verbatimModuleSyntax exist, and a project that already has them on is ready for it.

Recommendation: trace before touching anything, apply the cheap options, then split into referenced projects along the boundaries the trace shows are expensive. Set a build-time budget in CI afterwards, because without one the improvement erodes over the following year.

🎯 Key Takeaways

  • tsc --init in TS7 writes a short, opinionated config — use it as the baseline.
  • It enables noUncheckedIndexedAccess and exactOptionalPropertyTypes, which strict does not.
  • types: [] stops every @types package loading globally.
  • target is output syntax; lib is which globals exist — they are independent.
  • lib ahead of the runtime type-checks and then throws — match it to deployment.
  • target: es5 and moduleResolution: classic/node10 are removed (TS5108).
  • amd, umd and system are gone from module — pass a bad value to print the list.
  • module and moduleResolution must match — otherwise TS5110.
  • Under nodenext, package.json's type field is part of your config — TS1295.
  • isolatedModules requires export type for type re-exports (TS1205).
  • verbatimModuleSyntax requires import type for type imports (TS1484).
  • exclude only filters include — an imported file is still compiled and emitted.
  • Relative paths in an extended config resolve from the base file.
  • Project references enforce layering, which usually beats the build-time saving.
  • tsc --build honours references; plain tsc ignores them.
