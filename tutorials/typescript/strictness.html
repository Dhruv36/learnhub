Strictness Flags Correctness at the Boundary

What you'll master: exactly which checks strict turns on — seven of them, each verified here by its error code; why TypeScript 7 is strict by default and what that changes; the strictness flags that strict does not include and that most teams should turn on anyway — noUncheckedIndexedAccess, exactOptionalPropertyTypes, noImplicitReturns and three more; the options TS7 removed outright, including the old error-suppression escape hatches; and how to adopt strictness in a codebase that was not written for it, without a six-month branch. Prerequisites: Narrowing, Guards & Unions.

Part 1 — What strict Actually Turns On

strict is not a check. It is a switch that sets a group of other flags, and knowing which ones makes every "why is this an error" question answerable.

// one file, seven violations, compiled with tsc 7.0.2 and NO flags at all
declare const a: string | null; const a2: string = a;
function f(x) { return x; }
function g() { return this.x; }
class C { x: number; }
try {} catch (e) { e.message; }
declare function h(n: number): void; h.call(undefined, "s");
declare const fn: (x: string) => void; const q: (x: string | number) => void = fn;

$ npx tsc s.ts --noEmit
s.ts(2,39): error TS2322: Type 'string | null' is not assignable to type 'string'.
s.ts(4,12): error TS7006: Parameter 'x' implicitly has an 'any' type.

Part 2 — strictNullChecks Is the One That Matters

The other flags close specific holes. This one changes the meaning of every type in the program.

It is also the flag that makes narrowing (lesson 5) worth anything: without it, the compiler has no null to narrow away, so guards are decoration. Turning it on is most of the value of strictness, and most of the effort — which is why Part 5 treats it as its own project.

Part 3 — What strict Leaves Out

Six checks are not part of strict. All of them catch real bugs, and the first two catch the ones that reach production.

declare const arr: string[]; const a: string = arr[0];
interface O { name?: string } const o: O = { name: undefined };
function f(b: boolean) { if (b) return 1; }
switch (n) { case 1: console.log(1); case 2: console.log(2); break; }
declare const rec: { [k: string]: number }; rec.foo;
class A { m() {} } class B extends A { m() {} }

Part 4 — The Two Flags Worth Arguing About

noUncheckedIndexedAccess adds undefined to every index access, including array indexing:

const first = arr[0];        // string | undefined, even if arr.length is obviously 3
for (const s of arr) { … }   // string — iteration is unaffected
arr.at(0);                   // string | undefined either way

The complaint is real: a loop over arr[i] now needs a check the author knows is redundant. The answer is that the compiler cannot know it, and the same code with a wrong bound is the most common way a TypeScript program throws. Where the index is genuinely proven, a for…of loop, destructuring or .at() with an explicit guard reads better than the assertion anyway.

exactOptionalPropertyTypes makes name?: string mean "absent or a string", not "absent, a string, or explicitly undefined":

const o: O = { name: undefined };
// error TS2375: ... with 'exactOptionalPropertyTypes: true'.
//   Consider adding 'undefined' to the types of the target's properties.
You meanWrite
May be absentname?: string
Always present, may be undefinedname: string | undefined
Eithername?: string | undefined

This matters wherever the difference is observable: Object.keys and in see an explicitly-undefined property, JSON.stringify drops it, and a spread-based patch treats the two cases differently. If none of that applies to your code, the flag is churn.

Part 5 — Adopting Strictness in an Existing Codebase

The failure mode is a long-lived branch that flips strict globally, accumulates thousands of errors, conflicts with everything, and is abandoned. Every successful migration is incremental.

StepActionWhy this order
1noImplicitAny aloneMechanical fixes; no behaviour questions
2The cheap flags: returns, fallthrough, overrideSmall error counts; immediate value
3strictNullChecks, file by fileThe bulk of the work and the real bugs
4The rest of strictMostly clean once 3 is done
5noUncheckedIndexedAccessLarge but shallow; do it last

For step 3, the practical mechanism is per-file rather than per-project. Turn the flag on globally, then use // @ts-nocheck or a separate looser tsconfig project for the files not yet converted, and shrink that list in normal PRs. New files are strict from the start, which is what stops the problem growing while you fix it.

ToolUseCaution
// @ts-expect-errorOne known violationFails if the error goes away — good
// @ts-ignoreAvoidSilent when the code is fixed
// @ts-nocheckA whole file, temporarilyTrack the count; it should fall
! non-null assertionA proven invariantEach one is a promise the compiler cannot check
Two tsconfig projectsStrict and legacy setsExtra build config to maintain

❌ Clearing the migration with ! and as any. Turning strictNullChecks on and then silencing every error with a non-null assertion produces a codebase that compiles under strict mode and has exactly the same bugs it had before — with the added problem that the assertions now hide them from the next person who looks. The error count went to zero and nothing was learned from it.

✅ Treat each error as a question about the data. Most are one of three answers: the value genuinely can be missing, so handle it; it cannot, so the type upstream is wrong and should be fixed; or it comes from outside the program, so it needs validation at the boundary — which is the next lesson. Assertions are for the small residue where an invariant is real but unprovable, and each one deserves a comment naming the invariant.

Part 6 — What Strictness Does Not Buy

Strict mode makes the type system honest about what the code says. It does not make the code's assumptions about the outside world true.

BoundaryStrict mode's viewReality
JSON.parseReturns anyAnything at all
fetch().json()any, then whatever you assertWhatever the server sent
process.env.Xstring | undefinedCorrect, and usually asserted away
An untyped dependencyany from its .d.tsWhatever it does
A database rowThe model type you wroteThe schema as migrated

Every one of those is an any or an unverified claim entering a strict program, and strictness cannot help because the lie happens before any checking starts. That is the argument for the next two lessons: strict flags make the interior trustworthy, and runtime validation is what makes the boundary trustworthy. Neither substitutes for the other.

Interview Questions

Beginner: What does the strict flag do?

It is a shorthand that enables a family of individual checks rather than being a check itself. In TypeScript 7 it is on by default, so a file compiled with no flags at all already gets them.

The members are strictNullChecks, noImplicitAny, noImplicitThis, strictPropertyInitialization, useUnknownInCatchVariables, strictBindCallApply, strictFunctionTypes and alwaysStrict. I verified the first seven by compiling one file containing a violation of each: all seven errored with no flags, and all seven went silent under --strict false.

By far the most important is strictNullChecks, which stops null and undefined being assignable to every type. It is what makes optional properties and functions like find return honest types, and it is where nearly all the migration effort goes.

None of it costs anything at runtime — the checks happen during compilation and the types are erased. A strict build and a non-strict build of the same passing code emit identical JavaScript, so the decision is purely about which mistakes the compiler is willing to tell you about.

The one thing worth knowing beyond the list is that strict is a moving target: new releases have added members to it. That is why compiling a violation and checking whether --strict false silences it is a better answer than memorising a list — it is correct for the compiler you actually have.

Beginner: What does noUncheckedIndexedAccess change?

It adds undefined to the result of every index access — array indexing, and lookups on a type with an index signature such as Record<string, V>.

Without it, arr[0] is typed string even for an empty array, and rec.missing is typed as present. That is simply untrue, and it is one of the most common ways a strictly-typed program still throws at runtime.

It is not part of strict because it is noisy in code that indexes in loops: the compiler cannot know that i is within bounds. In practice the noise usually points at code that would read better as for…of, destructuring or .at() with a real check.

Iteration is unaffected — for (const s of arr) still gives string — so the cost is smaller than people expect, and I would turn it on in any new project. Destructuring with a default, const [first = ""] = arr, handles the rest without an assertion.

The cases it cannot help with are the ones where the bound is genuinely known — a fixed-length tuple, or an index derived from a length check two lines earlier. There a non-null assertion with a comment is honest, and it is a much smaller set of places than the flag's reputation suggests.

Mid: Which useful checks are outside strict, and which would you enable?

Six: noUncheckedIndexedAccess, exactOptionalPropertyTypes, noImplicitReturns, noFallthroughCasesInSwitch, noPropertyAccessFromIndexSignature and noImplicitOverride. I verified that a file violating all six produces no errors under strict alone, and one error each with the flags on.

I would enable four without discussion: the index-access flag because it catches the bugs that actually reach production; noImplicitReturns and noFallthroughCasesInSwitch because they are nearly free; and noImplicitOverride in class-heavy code, where a base-class rename silently turning an override into a new method is a nasty bug.

exactOptionalPropertyTypes is a judgement call. It makes name?: string reject an explicit undefined, which matters when the difference is observable — in checks, Object.keys, JSON.stringify dropping the key, spread-based patches. If none of that is in play, it is churn.

noPropertyAccessFromIndexSignature is a style rule: it forces rec["foo"] over rec.foo to make the dynamic lookup visible. Reasonable, but it is about readability rather than correctness, so I would put it to the team rather than assert it.

The reason none of these are inside strict is compatibility: adding a member to strict breaks every project that upgrades, so the bar is high and useful checks stay outside it for a long time. Treating strict: true as the finish line therefore leaves value on the table, and the six are worth reviewing deliberately rather than inheriting by default.

Mid: What changed about compiler options in TypeScript 7?

Two things matter on upgrade: strict is on by default, and a set of legacy options was removed outright, so an old tsconfig.json can fail to load rather than quietly behaving differently.

The removals I verified include suppressExcessPropertyErrors, suppressImplicitAnyIndexErrors, noImplicitUseStrict, keyofStringsOnly, importsNotUsedAsValues and preserveValueImports — each now TS5023, "unknown compiler option".

alwaysStrict is a different case: the option exists but its false value was removed, giving TS5108, "Option 'alwaysStrict=false' has been removed". Emitted output is always strict now, which is a non-issue for modules — they are strict regardless — and only affects script files.

The two suppress* removals are the ones with migration cost, because they were the only blanket way to silence a category of error. That is a better world, but a team upgrading a large old codebase should expect to replace them with real fixes or targeted @ts-expect-error comments.

Senior: Plan a strict-mode migration for a 200k-line codebase.

The constraint that shapes everything is that a long-lived migration branch will lose to merge conflicts. So the plan has to keep main shippable every day and let normal feature work continue.

Order the flags by cost, not by importance. Start with noImplicitAny, whose fixes are mechanical and rarely raise behaviour questions. Then the cheap ones — noImplicitReturns, noFallthroughCasesInSwitch, noImplicitOverride — which typically produce tens of errors, not thousands, and pay for themselves immediately. strictNullChecks is the real project and goes third. noUncheckedIndexedAccess goes last: large, shallow, and easy once the null work is done.

For strictNullChecks, go per-file with a ratchet. Turn it on globally, add // @ts-nocheck to the files that fail, and commit the count. Every PR removes some files; CI fails if the count goes up. That converts an intractable branch into ordinary reviewed work, and new files are strict from day one, so the backlog only shrinks.

Set the rule for how errors get cleared, because this is where migrations go wrong. A non-null assertion is allowed only with a comment naming the invariant; as any is not allowed; @ts-expect-error over @ts-ignore always, since it fails once the underlying issue is fixed. Without that rule, the error count reaches zero and the bug count does not.

Recommendation: ratcheted per-file adoption, cheap flags first, strictness in the editor and CI from the same config so authors see errors as they write, and a review norm that every silenced error carries a written justification. Expect the null work to dominate the timeline, and budget for it finding real bugs — that is the return on the investment, not a side effect.

Senior: A team says strict mode "did not help — we still get runtime type errors". What is going on?

Almost certainly the errors are entering at the boundary, where strictness has nothing to check. Strict flags verify that the program is consistent with what it claims; they cannot verify that the claims match reality.

The usual entry points: JSON.parse returns any; response.json() returns any and is usually immediately asserted to a model type; hand-written or generated .d.ts files describe a library as its author hoped; database rows are typed from a model that the last migration changed. In each case an unverified value is given a precise type, and every strict check downstream then reasons correctly from a false premise.

any is the specific mechanism, because it is contagious and silent. One any from an untyped dependency flows through strictly-typed code without a single error, which is why a codebase can be "100% strict" and still be unchecked along its most important path.

The fix is a parse step, not a tighter flag. Every external value arrives as unknown and becomes a typed value only by passing a validator — which is the next lesson. Alongside that: ban as at boundaries in review, use noImplicitAny plus a lint rule against explicit any, and type the surface of untyped dependencies in a wrapper module rather than at every call site.

Recommendation: keep strict mode — it is doing its job on the interior — and add validation at every point data enters. Then measure: if runtime type errors persist afterwards, they will be in a specific boundary that has not been covered yet, and that is a findable problem rather than a vague one.

🎯 Key Takeaways

  • TypeScript 7 is strict by default — no flags, no config, and the checks are on.
  • strict is a switch for eight flags, not a check of its own.
  • Confirm membership empirically: compile once plain, once with --strict false.
  • strictNullChecks is the one that matters — and most of the migration cost.
  • Six useful checks are outside strict and must be enabled by name.
  • noUncheckedIndexedAccess makes every index access T | undefined; iteration is unaffected.
  • exactOptionalPropertyTypes separates "absent" from "explicitly undefined" — enable it when that is observable.
  • noImplicitReturns is for inferred return types; annotated ones already fail with TS2366.
  • TS7 removed suppressExcessPropertyErrors and friends — TS5023, no blanket silencing left.
  • alwaysStrict: false is gone (TS5108); emitted output is always strict.
  • Migrate flag by flag, file by file, with a ratchet that CI enforces.
  • @ts-expect-error over @ts-ignore — it fails once the code is fixed.
  • Clearing errors with ! and as any keeps every bug and hides it better.
  • Strictness verifies the interior; it cannot verify the boundary — JSON.parse is still any.
  • All of it is erased — strict mode has no runtime cost and no runtime effect.
