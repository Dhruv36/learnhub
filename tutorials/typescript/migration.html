Migrating to TypeScript Scale & Migration

What you'll master: the migration ladder that keeps main shippable every day — allowJs, then // @ts-check file by file, then checkJs, then renaming, then strictness; JSDoc annotations in .js files, which are fully type-checked and let a codebase gain types before a single file is renamed; @ts-expect-error versus @ts-ignore, where the first reports TS2578 once the underlying error is fixed and the second stays silent forever — which is what makes a ratchet possible; the flag order from lesson 10 applied to a real codebase; and how to count progress so the work cannot slide backwards. Prerequisites: Strictness Flags.

Part 1 — The Ladder

The failure mode is a long-lived branch that converts everything, accumulates conflicts and is abandoned. Every rung below is shippable on its own.

RungChangeGains
1allowJs: trueTypeScript can build the project; nothing is checked
2// @ts-check in chosen filesReal checking, one file at a time
3JSDoc types on shared modulesTypes flow outward with no renames
4checkJs: trueEvery .js file checked
5Rename .js → .ts, file by fileReal syntax; better tooling
6Strictness flags, in lesson 10's orderThe actual bug-finding
🔑 Rung 2 is where the value starts and the cost is lowest. A single // @ts-check comment at the top of one .js file turns checking on for that file only — verified below — so a team can begin with the three modules that break most often rather than with an alphabetical march through the repo.

Part 2 — JSDoc Is Fully Checked

This is the part people do not expect: type annotations written as JSDoc in a plain .js file are checked exactly as TypeScript annotations are.

// plain.js
/**
 * @param {string} name
 * @param {number} [times]
 * @returns {string}
 */
function greet(name, times) { return name.repeat(times ?? 1); }

const bad = greet(42);

/** @type {{ a: number }} */
const obj = { a: "wrong" };

$ npx tsc plain.js --noEmit --allowJs
                                        ◄── nothing: allowJs alone checks nothing

$ npx tsc plain.js --noEmit --allowJs --checkJs
plain.js(7,19): error TS2345: Argument of type 'number' is not assignable to
               parameter of type 'string'.
plain.js(9,15): error TS2322: Type 'string' is not assignable to type 'number'.
                                        ◄── verified: real checking, no .ts files
JSDocEquivalent
@param {string} namename: string
@param {number} [times]times?: number
@returns {string}: string
@type {{ a: number }}: { a: number }
@typedeftype / interface
@template T<T>
@satisfiessatisfies

Why this matters for sequencing: annotating the three or four modules everything imports gives the whole codebase better inference immediately, without renaming anything or changing the build. The types then flow outward, and files that were silently full of any start producing real errors — which is the point.

The limits are real though: JSDoc is verbose, has no equivalent for some advanced constructs, and editors give it slightly weaker support. It is a stepping stone rather than a destination — good for the migration period and for build tooling that cannot process .ts.

Part 3 — @ts-expect-error and the Ratchet

// @ts-expect-error  a real error, suppressed
const a: number = "x";
// @ts-expect-error  NO error here
const b: number = 1;
// @ts-ignore
const c: number = "y";

$ npx tsc sup.ts --noEmit
sup.ts(3,1): error TS2578: Unused '@ts-expect-error' directive.   ◄── verified
                                        ▲ only ONE error: the unnecessary directive

@ts-expect-error asserts that the next line does have an error. When the underlying problem is fixed, the directive itself becomes an error — so suppressions clean themselves up. The @ts-ignore on line 5 suppressed a genuine error and reported nothing, and it will keep reporting nothing after that line is fixed, forever.

DirectiveScopeSelf-cleaning?Use
@ts-expect-errorNext lineYes — TS2578Always prefer this
@ts-ignoreNext lineNoAvoid
@ts-nocheckWhole fileNoMigration only; count them
@ts-checkWhole .js file—Opting in

The ratchet is what makes a migration finish. Turn a flag on globally, add @ts-nocheck to the files that fail, commit the count, and make CI fail if it rises. Every normal PR is then free to reduce it, new files are strict from day one, and the work happens as reviewed increments rather than as a branch.

$ grep -rl "@ts-nocheck" src | wc -l > .type-debt
$ git add .type-debt
# CI: fail if the current count exceeds the committed one

Part 4 — The Flag Order, Applied

Lesson 10 established the order by cost. In a migration it looks like this:

StepFlagTypical volumeNature of the fixes
1noImplicitAnyHundredsMechanical annotations
2noImplicitReturns, noFallthroughCasesInSwitchTensEach one a real bug
3strictNullChecksThousandsGenuine design questions
4The rest of strictTensMostly clean after step 3
5noUncheckedIndexedAccessHundredsShallow; easy after step 3
6exactOptionalPropertyTypesTensJudgement per case

strictNullChecks is the whole project and deserves its own plan. Each error is one of three answers: the value genuinely can be missing, so handle it; it cannot, so a type upstream is wrong and fixing that resolves many errors at once; or it comes from outside the program and needs validation, which is lesson 11. Only the third category needs new code.

Part 5 — Dependencies During a Migration

SituationAction
Package ships its own typesNothing
@types/pkg existsInstall it as a dev dependency
No types at allA minimal .d.ts for the parts you use
Types exist but are wrongA wrapper module — lesson 16
Types use any pervasivelyWrapper with honest signatures
Errors inside a dependency's .d.tsskipLibCheck, which should be on anyway

Declare only what you use. A hand-written declaration for a large untyped library is tempting to complete, and a waste: five lines covering the two functions you call is accurate, reviewable and cheap to maintain, where a full transcription of the API is an unverified 500-line claim that will drift. Lesson 16's point applies — declare means "trust me", and a smaller claim is a smaller lie surface.

❌ Renaming every file to .ts first and adding any to make it compile. It feels like progress and produces the worst possible state: the codebase reports itself as TypeScript, the editor and CI say it passes, and the types are decorative. Worse, the anys are now invisible — nothing distinguishes a deliberate one from a migration artefact, so the remaining work has no boundary and nobody can tell what has actually been converted.

✅ Keep the file extension honest and let the checking lead. A .js file with // @ts-check and JSDoc types is genuinely checked and genuinely typed; a .ts file full of any is neither. Rename when a file is ready, count what is not, and put the count in CI — then "how far through are we" has an answer, and the last 20% does not become permanent.

Gate the ratchet, report the rest. A count that blocks a merge must be one a developer can always satisfy — reducing @ts-nocheck files or not adding @ts-ignore qualifies. Gating on "no .js files remaining" blocks work that has nothing to do with the migration, and the gate gets removed rather than met.

Interview Questions

Beginner: What do allowJs and checkJs do?

allowJs lets .js files be part of the TypeScript program, so the compiler will read and emit them. It does no checking at all — I verified that a .js file with obviously wrong JSDoc types compiles silently under allowJs alone.

checkJs turns checking on for those files. With it, the same file produced TS2345 for a number passed where the JSDoc said string, and TS2322 for a property whose value contradicted its @type annotation.

There is a per-file version too: a // @ts-check comment at the top of a .js file enables checking for that file only, with allowJs on and checkJs off. I verified that as well, and it is the rung of a migration with the best ratio of value to cost — you can start with the modules that cause the most bugs rather than converting alphabetically.

So the order is: allowJs to get TypeScript building the project at all, then @ts-check on chosen files, then checkJs once most of them pass.

Beginner: Why prefer @ts-expect-error over @ts-ignore?

Because @ts-expect-error cleans itself up and @ts-ignore does not.

@ts-expect-error asserts that the following line has an error. If the error is fixed — or was never there — the directive itself becomes an error: TS2578, "Unused '@ts-expect-error' directive". I verified that a file with one genuine suppression, one unnecessary one and one @ts-ignore reported exactly one error, the unnecessary directive.

@ts-ignore silences whatever is on the next line and keeps silencing it forever, including after the underlying problem is fixed and including any new, unrelated error that appears on that line later. It is a permanent blind spot rather than a temporary one.

In a migration that property is what makes a ratchet possible: suppressions that expire on their own mean the debt count reflects reality without anyone auditing it. I would add a lint rule banning @ts-ignore outright.

Mid: How does JSDoc change a migration plan?

It means adding types and renaming files are separate pieces of work, which lets you do the valuable one first.

JSDoc annotations in a .js file are checked exactly as TypeScript annotations are — @param, @returns, @type, @typedef, @template for generics, even @satisfies. I confirmed a .js file producing TS2345 and TS2322 from JSDoc alone.

So the highest-leverage first move is annotating the few modules that everything imports, with no renames and no build changes. Types then flow outward through inference, and files that were silently full of any start producing real errors — which is the entire point, and it happens before the conversion work starts.

The limits are worth stating: JSDoc is verbose, has no form for some advanced type-level constructs, and editor support is slightly weaker. It is a stepping stone, and the reason to know about it is that it lets a team demonstrate value in week one instead of week twelve — which is usually what decides whether a migration gets finished.

Mid: How do you handle dependencies with no types or bad types?

Three cases, three different answers, and the common mistake is to do more work than necessary.

No types at all: write a minimal .d.ts covering only the functions you actually call. Transcribing a whole library's API is tempting and wrong — lesson 16's point is that declare means "trust me" and nothing checks it, so a 500-line hand-written declaration is a large unverified claim that will drift. Five accurate lines beat it.

Types exist but are wrong, or pervasively any: a wrapper module. One file imports the dependency and exports honest signatures, converting the any to unknown at the boundary and validating if the value feeds real logic. That contains the problem in one reviewable place and makes replacing the dependency a local change.

Errors inside a dependency's own declarations: skipLibCheck, which should be on regardless — lesson 20 measured it taking a trivial program from 35,328 types to 342, and it never weakens checking of your own code.

What I would avoid is module augmentation to correct wrong types, since as lesson 15 showed augmentation adds and cannot contradict — declaring a member with a different type is a conflict rather than an override.

Senior: Plan a migration of a 500k-line JavaScript codebase.

The constraint that shapes everything is that feature work continues throughout, so nothing can depend on a long-lived branch. Every step has to be mergeable the day it is written.

Week one is about demonstrating value without conversion. allowJs plus skipLibCheck so TypeScript can build the project, then // @ts-check and JSDoc types on the handful of modules everything imports. Because JSDoc is fully checked, this finds real bugs immediately in files that have not been renamed — which is what buys the political room for the rest.

Then the ratchet, which is the mechanism rather than a step. Turn a flag on globally, add @ts-nocheck to the files that fail, commit the count, and make CI fail if it rises. That converts an intractable branch into ordinary reviewed PRs, and crucially makes new files compliant from day one so the backlog only shrinks. Ban @ts-ignore by lint at the same time, so that every suppression is a @ts-expect-error that will report TS2578 when it becomes unnecessary.

Flags in order of cost, not importance. noImplicitAny first — hundreds of mechanical fixes, no design questions, and it builds momentum. Then the cheap ones, noImplicitReturns and noFallthroughCasesInSwitch, which produce few errors and nearly every one is a real bug. Then strictNullChecks, which is the actual project and the only step I would resource as such. noUncheckedIndexedAccess last, being large but shallow once nulls are handled.

Set the rule for how errors get cleared before starting, because this is where migrations produce nothing: a non-null assertion only with a comment naming the invariant, no as any, and upstream type fixes preferred since one of those often resolves dozens of errors. Without that rule the error count reaches zero and the bug count does not move.

Recommendation: JSDoc on core modules in week one, a CI ratchet on @ts-nocheck, flags in cost order, renaming as a trailing consequence rather than a goal, and a published count so "how far through are we" has an answer. Budget most of the calendar time for strictNullChecks, and expect it to find real bugs — that is the return, not a side effect.

Senior: A migration stalled at 80% two years ago. How do you finish it?

I would start by finding out whether the remaining 20% is hard or merely unowned, because those need completely different responses and teams usually assume the first when it is the second.

Measure what is actually left. Count @ts-nocheck files, @ts-ignore occurrences, remaining .js files, and — with the flags on and suppressions removed — the real error count per file. That distinguishes three populations: files that are nearly done, files nobody understands, and files that are dead. The third is common and the cheapest win available: code that has not been touched in two years and is not reachable should be deleted rather than typed.

Then diagnose why it stopped, since it will stop again otherwise. The usual causes are that there was no ratchet — so debt grew back as fast as it was paid — that @ts-ignore was allowed, so nobody can tell what is genuinely broken, or that the remaining files are the scary ones nobody owns. Each has a different fix, and only the last is actually about TypeScript.

Install the ratchet retroactively. Commit today's counts as the ceiling and make CI enforce them. That alone stops the regression, costs nothing, and makes every subsequent PR contribute. Replace every @ts-ignore with @ts-expect-error in one mechanical pass — the ones that then report TS2578 were suppressing errors that no longer exist, which is usually a surprising number and free progress.

For the genuinely hard files, change the approach rather than trying harder. A file nobody understands is a rewrite-with-tests candidate, not an annotation exercise. And a file at the boundary — parsing, external APIs — is lesson 11's problem, where the right move is a validated boundary rather than types that describe what the author hoped was arriving.

Recommendation: delete what is dead, ratchet what is left, convert @ts-ignore to @ts-expect-error to reveal the free wins, assign explicit owners to the remaining files, and publish the count weekly. The last 20% stalls because it has no deadline and no owner, not because it is impossible.

5 (hard): Build the ratchet.
Solution 
# record today's ceiling, once
$ grep -rl "@ts-nocheck" src | wc -l | tr -d ' ' > .type-debt
$ git add .type-debt && git commit -m "chore: record type debt ceiling"

// scripts/ratchet.mjs — run in CI
import { readFileSync } from "node:fs";
import { execSync } from "node:child_process";

const ceiling = Number(readFileSync(".type-debt", "utf8").trim());
const current = execSync('grep -rl "@ts-nocheck" src | wc -l').toString().trim();

console.log(`type debt: ${current} file(s), ceiling ${ceiling}`);
if (Number(current) > ceiling) {
  console.error("✘ type debt increased — add types instead of @ts-nocheck");
  process.exit(1);
}
if (Number(current) < ceiling) {
  console.error(`✔ debt reduced — commit the new ceiling (${current})`);
  process.exit(1);          // force the ceiling to be lowered
}
PropertyWhy it matters
Fails when debt risesStops regression — the main job
Fails when debt fallsForces the ceiling down; progress cannot be undone later
Always satisfiableA developer can fix it in one commit
Prints the numbersProgress is visible in every CI run

Failing on a decrease looks perverse and is the important half: without it, the count drifts back up to the stale ceiling and the ratchet only ever holds the original line.

🎯 Key Takeaways

  • Every rung must be shippable — a long-lived conversion branch loses to conflicts.
  • allowJs permits .js files; it checks nothing.
  • // @ts-check enables checking for one file — the cheapest first rung.
  • JSDoc annotations are fully type-checked — TS2345 and TS2322 from a .js file.
  • Annotate the modules everything imports first — types flow outward with no renames.
  • @ts-expect-error reports TS2578 once the error is gone — it self-cleans.
  • @ts-ignore is silent forever, including for new errors on that line.
  • A CI ratchet is what makes a migration finish — commit the count, fail on a rise.
  • Fail on a decrease too, so the ceiling comes down and progress is locked in.
  • New files are compliant from day one — otherwise debt grows as you pay it.
  • Flags in order of cost: noImplicitAny, the cheap ones, then strictNullChecks.
  • Declare only the parts of an untyped library you use — a bigger claim is a bigger lie.
  • Wrap dependencies with wrong or any-heavy types; do not augment them.
  • Rename last — a .ts file full of any is worse than a checked .js one.
  • Publish the count so "how far through are we" has an answer.
