Narrowing, Guards & Unions Type-Level Programming

What you'll master: control-flow analysis — how the compiler turns a runtime check into a narrower static type; every built-in narrowing operator and the traps in each, including typeof null === "object" and falsy 0; discriminated unions and the never trick that makes the compiler tell you about the case you forgot; exactly when narrowing survives into a callback — const keeps it, let loses it, both verified; the aliasing hole where an intervening function call mutates a value and the compiler keeps believing the old type; and the patterns that replace defensive checks with types that cannot be wrong. Prerequisites: Functions, Overloads & Signatures.

Part 1 — Control-Flow Analysis

TypeScript tracks what each binding must be at every point in the flow. A check, a return, a throw or an assignment all change what it knows from that line onward.

function describe(v: string | number | null) {
  if (v === null) return "nothing";     // v: string | number below this line
  if (typeof v === "number") {
    return v.toFixed(2);                // v: number
  }
  return v.toUpperCase();               // v: string — by elimination
}
ConstructEffect on the type
if / elseDifferent narrowings in each branch
Early return, throw, continueRemoves that possibility from everything after
&&, ||, ??, ternaryNarrow within the expression
AssignmentRe-narrows to the assigned value's type
switch on a literal propertyNarrows to the matching union member per case
A call returning neverMarks the rest of the branch unreachable
🔑 Narrowing is per binding, not per value. The compiler tracks the name you checked. Check user.profile and then read user.profile.name and it works; copy it to a local first and the local is what narrows. This is why extracting a value into a const before checking it is the most reliable way to keep a narrow type — and, as Part 4 shows, the only way to keep one inside a callback.

  if (typeof v === "object") {

}

function pageSize(n: number | undefined) {
  if (n) return n;            // ✘ 0 is falsy: a legitimate 0 becomes the default
  return 20;
}
function pageSizeFixed(n: number | undefined) {
  return n ?? 20;             // ✔ only null/undefined trigger the default
}

Use the check that matches the question. "Is it missing?" is === undefined or ?? ; "is it empty or missing?" is truthiness. Reaching for truthiness by habit is how 0, "" and false quietly become the default value.

Part 3 — Discriminated Unions and Exhaustiveness

A discriminated union gives every member a literal property in common. That one field lets the compiler narrow the whole object from a single check, and it is the most valuable modelling tool in the language.

type Shape =
  | { kind: "circle"; r: number }
  | { kind: "square"; side: number }
  | { kind: "tri";    base: number; height: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2;      // s: the circle member — r is available
    case "square": return s.side ** 2;
    case "tri":    return (s.base * s.height) / 2;
    default: {
      const _exhaustive: never = s;                 // every member handled → s is never
      return _exhaustive;
    }
  }
}

Delete the "tri" case and the compiler names the omission, verified with tsc 7.0.2:

error TS2322: Type '{ kind: "tri"; base: number; height: number; }' is not assignable to type 'never'.

That is the whole point: adding a member to the union turns every incomplete switch in the codebase into a compile error, naming exactly what was missed. Without the never line the new member falls through the default silently.

Instead ofUseWhy
{ ok: boolean; data?: T; error?: Error }{ ok: true; data: T } | { ok: false; error: Error }Impossible states — success with an error — stop being representable
Checking if (res.data)Checking if (res.ok)One discriminant narrows every field at once
Optional fields that go togetherA union of the real shapesThe type documents which combinations exist
A string status plus loose fieldsA union keyed on statusEach state carries exactly the data it has

Make the discriminant a literal type. If kind is typed string it narrows nothing — which is why widening (lesson 2) and discriminated unions interact: build these objects with as const or an explicit annotation, or the discriminant is lost before the compiler ever sees it.

Part 4 — Where Narrowing Survives, and Where It Does Not

This is the part that produces confused bug reports, so here is the verified behaviour rather than folklore.

// ✔ KEPT — a parameter that is never reassigned stays narrowed inside a callback
function keeps(v: string | number) {
  if (typeof v === "string") {
    setTimeout(() => v.toUpperCase(), 0);        // no error
  }
}

// ✘ LOST — a mutable outer binding read inside a callback
let outer: string | number = "a";
if (typeof outer === "string") {
  setTimeout(() => { outer.toUpperCase(); }, 0);
}
// error TS2339: Property 'toUpperCase' does not exist on type 'string | number'.
//   Property 'toUpperCase' does not exist on type 'number'.
BindingRead inside a callbackReason
constNarrowing keptIt can never change, so the check stays true
Parameter never reassignedNarrowing keptTreated as effectively constant
let that may be reassignedNarrowing discardedThe callback runs later; the value may have changed
Property of an objectDiscarded in callbacksAnything could have written to it

The fix is always the same: copy to a const before checking, and use the copy.

let outer: string | number = "a";
const snapshot = outer;                            // capture the value
if (typeof snapshot === "string") {
  setTimeout(() => snapshot.toUpperCase(), 0);      // ✔ narrowing survives
}

❌ Assuming an intervening function call re-checks the value. It does not — and this is unsound, verified: after if (typeof mutable === "string"), calling a function that sets mutable = 1 leaves the compiler still believing it is a string, and mutable.toUpperCase() compiles. The same holds for object properties: check b.value, call something that clears it, and b.value.toUpperCase() still passes. Both throw at runtime.

✅ Do not rely on the compiler to model aliasing. Read the value into a const at the point of the check and use that, so later mutation cannot invalidate what you already proved. It is the same habit that makes callbacks work, and it removes a whole class of "impossible" runtime errors.

Part 5 — Custom Guards, Applied

When a built-in operator cannot express the check, a type predicate or assertion function carries the knowledge — the mechanism from the functions lesson, used in anger.

// narrowing a union of interfaces that share no discriminant
type Cat = { meow(): void };
type Dog = { bark(): void };

function isDog(a: Cat | Dog): a is Dog { return "bark" in a; }

// filtering out nullish values so the ARRAY type improves
function isPresent<T>(v: T | null | undefined): v is T { return v != null; }

const names: string[] = ["a", null, "b"].filter(isPresent);   // ✔ string[], not (string | null)[]
SituationReach for
Members share a literal fieldA discriminated union and switch — no custom guard needed
Members differ only by shape"k" in x, or a small predicate
Filtering nullish values from an arrayA generic isPresent predicate
Data arriving from outside the programA schema parser, not a hand-written predicate
A condition that must hold for the rest of the functionAn assertion function (asserts v is T)

Prefer discriminants to predicates. A switch on kind is checked by the compiler; a predicate is a promise it accepts on trust. Every guard you delete by adding a discriminant is one fewer place that can lie.

Part 6 — Designing So Narrowing Is Unnecessary

The best narrowing is the check you never have to write, because the type already rules the case out.

// defensive: every caller re-checks the same things
function send(user?: User, email?: string) {
  if (!user) throw new Error("no user");
  if (!email) throw new Error("no email");
  …
}

// designed: the signature makes those states unrepresentable
function send(user: User, email: Email) { … }      // Email is branded and parsed at the edge

Non-empty tuple [T, ...T[]]if (xs.length === 0) in every consumer
Discriminated result instead of data?/error?Checks for combinations that cannot occur
Branded types for validated valuesRe-validating the same string repeatedly
State machines as unions of statesif (status === "loading" && data) confusion
// a state machine where each state carries exactly its own data
type Request =
  | { state: "idle" }
  | { state: "loading"; startedAt: number }
  | { state: "success"; data: User }
  | { state: "error";   error: Error; retryable: boolean };

// impossible by construction: loading with data, success without it, error without a reason

This is the same idea as parse-don't-validate, and it is what separates a codebase where types are decoration from one where they do work: the compiler can only help with distinctions you have actually written down.

Interview Questions

Beginner: What is narrowing?

It is the compiler using a runtime check to give a value a more specific type for the rest of that branch. A parameter typed string | number becomes string inside if (typeof v === "string"), so string methods are available there and nowhere else.

It works through ordinary JavaScript constructs, because types do not exist at runtime: typeof, instanceof, in, truthiness, equality against literals, Array.isArray, and early returns or throws that eliminate a case from everything after them.

Narrowing is what makes unions usable. Without it you could only call members that every union member has, which for string | number is almost nothing.

The important subtlety is that it tracks a binding, not a value: the compiler knows something about the name you checked. That is why copying a value into a const before checking it is the reliable pattern, especially when a callback is involved.

Beginner: What is a discriminated union and why is it useful?

It is a union whose members all carry a common property with a distinct literal type — usually called kind, type or status. Checking that one property tells the compiler exactly which member it has, so every other field narrows with it.

The benefit is that impossible states stop being representable. A result modelled as { ok: boolean; data?: T; error?: Error } allows success with an error and failure with data, and every consumer writes defensive checks. Modelled as { ok: true; data: T } | { ok: false; error: Error }, those combinations cannot be constructed, and one check on ok gives access to exactly the right fields.

It also enables exhaustiveness checking: with a switch on the discriminant and a default that assigns the value to never, adding a new member makes every incomplete switch a compile error that names the missing case.

The one requirement is that the discriminant must be a literal type. If it widens to string — by being built in a variable without as const — the narrowing silently stops working.

Mid: Why does narrowing sometimes stop working inside a callback?

Because the callback runs later, and the compiler has to decide whether what you proved is still true when it does.

For a const, or a parameter that is never reassigned, the value cannot change, so the narrowing is kept — verified: a narrowed parameter used inside setTimeout compiles fine.

For a let that could be reassigned, the narrowing is discarded inside the callback, and you get an error like Property 'toUpperCase' does not exist on type 'string | number'. The compiler cannot know whether something reassigned the variable between the check and the callback running.

The fix is to capture the value: const snapshot = outer; then check and use snapshot. That is not a workaround — it is the correct semantics, because the callback should be operating on the value that was checked, not on whatever the variable holds later.

Worth knowing alongside it: within a single synchronous flow, TypeScript does not invalidate narrowing after a function call that might mutate the variable. That case is unsound, and the same const habit protects against it.

Mid: How do you make the compiler tell you when a new union member is unhandled?

With an exhaustiveness check: in the default branch of a switch on the discriminant, assign the value to a variable of type never.

default: {
  const _exhaustive: never = s;
  return _exhaustive;
}

If every member is handled, the compiler has eliminated them all and the value's type in default is never, so the assignment is legal. Add a member and forget a case, and that member reaches the default: the assignment fails with a message naming the exact type that is not assignable to never.

It works because never is the bottom type — nothing is assignable to it — so it is a compile-time proof that a branch is unreachable.

The same pattern works in an if/else chain, and a shared helper function assertNever(x: never): never { throw new Error(...) } keeps it to one line per switch. I treat it as mandatory for any union that models domain states: it converts "we forgot to handle cancelled orders" from a production incident into a build failure.

Senior: A codebase is full of defensive null checks and non-null assertions. How do you clean it up?

Defensive checks are usually a symptom: the types admit states the code knows cannot happen, so every function re-proves the same thing. I would attack the types rather than the checks.

First, find where the optionality enters. Usually it is a boundary — a parsed response, a database row, a config object — typed loosely and then carried through the whole program. Parsing there into a precise type removes the checks everywhere downstream. That is the single biggest win, and it replaces assertions with a real runtime check in one place.

Second, replace optional-field soup with discriminated unions. A type with data? and error? forces a check at every use; a union keyed on ok or status makes each state carry exactly its own data and lets one check unlock all of it.

Third, tighten signatures. A function that throws when an argument is missing should not accept a missing argument: making the parameter required moves the error to the caller, where the information is.

Treat every ! as a question. Some are legitimate — the compiler lost narrowing across a callback or an aliasing boundary — and those should be restructured with a const capture instead. The rest are claims about data that nothing verified, and they are where the runtime errors come from.

Recommendation: parse at the edges, model states as unions, tighten signatures, then enable a lint rule against non-null assertions so new ones require a deliberate exception. The checks disappear because the situations do, not because someone silenced them.

Senior: Where is TypeScript's narrowing unsound, and how do you defend against it?

Three places, all of which come from the compiler not modelling what happens between your check and your use.

Aliasing and mutation. After narrowing a variable, calling a function that reassigns it does not invalidate the narrowing — verified: the value is a number at runtime while the compiler still believes it is a string. The same applies to object properties: check obj.value, call something that clears it, and the subsequent access still type-checks.

Custom predicates and assertions. v is T is a promise the compiler accepts without verification. A predicate that checks one property and claims a rich type makes everything downstream unsound, silently.

Type assertions. as narrows nothing at runtime; it just instructs the compiler to stop disagreeing.

The defences are structural. Read values into const bindings at the point of the check, so later mutation cannot matter. Prefer discriminated unions to predicates, because the compiler verifies those. Derive predicates from schema validators rather than hand-writing them. And keep mutable shared state out of the paths where narrowing matters — most of this unsoundness needs a mutable binding or a mutable property to bite.

Recommendation: teach the const-capture habit explicitly, lint against non-null assertions and bare as, and reserve custom predicates for small structural checks that are unit-tested on their negative cases. The holes are few and learnable, which makes them manageable — as long as the team knows they exist.

5 (hard): Replace optional-field soup with a union.
Solution 
// before — four booleans' worth of states, most of them impossible
type Req = {
  loading: boolean;
  data?: User;
  error?: Error;
  retryCount?: number;
};

function render(r: Req) {
  if (r.loading) return "Loading…";
  if (r.error) return `Error: ${r.error.message}`;
  if (r.data) return r.data.name;
  return "???";                    // reachable, and nobody knows what it means
}

// after — each state carries exactly its own data
type Req =
  | { state: "idle" }
  | { state: "loading"; startedAt: number }
  | { state: "success"; data: User }
  | { state: "error"; error: Error; retryCount: number };

function render(r: Req): string {
  switch (r.state) {
    case "idle":    return "Ready";
    case "loading": return `Loading since ${r.startedAt}`;
    case "success": return r.data.name;                       // data is guaranteed
    case "error":   return `Error (${r.retryCount}): ${r.error.message}`;
    default: { const _x: never = r; return _x; }
  }
}

6 (hard): Design away the narrowing.
Solution 
// before — the same three checks in every function that touches a user
function sendWelcome(user?: User) {
  if (!user) throw new Error("no user");
  if (!user.email) throw new Error("no email");
  if (!user.email.includes("@")) throw new Error("bad email");
  mailer.send(user.email, "Welcome");
}

// after — parse once at the boundary, then the checks are impossible to need
type Email = Brand<string, "Email">;

const UserSchema = z.object({
  id: z.string(),
  email: z.string().email().transform(e => e as Email),
});
type User = z.infer<typeof UserSchema>;            // { id: string; email: Email }

function sendWelcome(user: User) {                  // required, and email is validated by type
  mailer.send(user.email, "Welcome");
}
CheckWhere it went
!userThe parameter is required: callers cannot omit it
!user.emailThe schema requires it; User has no optional email
includes("@")Ran once at the boundary; the brand records that it ran

The three runtime checks became one parse at the edge plus a type that carries the result. Every downstream function gets shorter, the error message improves (the schema says which field was wrong), and a new consumer cannot forget a check that no longer exists.

The judgement to state: branding every string would be worse than the disease. Brand what is validated or easily confused — emails, ids, units — and leave ordinary strings alone.

🎯 Key Takeaways

  • Narrowing turns runtime checks into static types through ordinary JavaScript operators, because types are erased.
  • It tracks bindings, not values, so copying into a const before checking is the reliable pattern.
  • typeof null === "object" — that branch narrows to null, not to an object.
  • Truthiness drops 0, "", NaN and false; use !== undefined or ?? when you mean "missing".
  • instanceof fails across realms and does not work for interfaces.
  • Discriminated unions narrow every field from one literal check and make impossible states unrepresentable.
  • The discriminant must be a literal type; widening to string silently disables narrowing.
  • Assign to never in the default branch so a new union member becomes a compile error that names itself.
  • Narrowing survives into callbacks for const and never-reassigned parameters, and is discarded for mutable let (TS2339).
  • An intervening function call does not invalidate narrowing — verified unsound for both variables and properties.
  • Capture into a const at the point of the check to close both the callback and the aliasing hole.
  • Prefer discriminants to custom predicates, because the compiler verifies the first and merely believes the second.
  • A generic isPresent predicate improves an array's type, turning (T | null)[] into T[].
  • The best narrowing is the check you never write — parse at the boundary and model states as unions.
  • Every ! is either a lost narrowing to restructure or an unverified claim.
