Compiler Performance Scale & Migration

What you'll master: how to find out why a build is slow instead of guessing — --diagnostics first, --generateTrace second; the measured effect of skipLibCheck and lib, which on a one-line file take the type count from 35,328 to 342 and the build from 0.319s to 0.016s; why Instantiations is the number that matters, shown with a type whose cost quadruples when a union doubles — 621, 2,441, 9,681; what TypeScript 7's trace output reveals about its four parallel checkers; and how to set a budget so an improvement does not erode. Prerequisites: Build Pipeline, Conditional Types & infer.

Part 1 — Measure First

Almost every "TypeScript is slow" diagnosis is wrong, because the plausible causes are unrelated and only one command distinguishes them.

$ npx tsc --noEmit --diagnostics

Lines:           58449       Instantiations:  34231
Identifiers:     49725       Memory used:    64853K

🔑 That output is from a file containing one line: export const x: number = 1;. 83 files, 58,449 lines and 35,328 types are almost entirely the standard library and DOM declarations — which is why the first thing to check is never your own code.

Part 2 — The Cheapest Wins Are Configuration

Same one-line file, three configurations, measured:

$ npx tsc tiny.ts --noEmit --diagnostics
Files: 83    Types: 35328   Instantiations: 34231   Total: 0.319s

$ npx tsc tiny.ts --noEmit --diagnostics --skipLibCheck
Files: 83    Types:   342   Instantiations:     0   Total: 0.049s      ◄── 6.5× faster

$ npx tsc tiny.ts --noEmit --diagnostics --skipLibCheck --lib es2022
Files: 58    Types:   342   Instantiations:     0   Total: 0.016s      ◄── 20× faster

skipLibCheck took the type count from 35,328 to 342. Lesson 16 explained why: without it, every declaration file in the program is type-checked for internal consistency, and the standard library plus DOM is vastly larger than most application code. Dropping DOM from lib then removed 25 files as well.

None of these touch your code, and together they often account for more than any refactor. They are the first thing to try precisely because they are reversible in one line.

Part 3 — Instantiations and Non-Linear Cost

A conditional type distributed over a union costs one instantiation per member, as lesson 7 described. Two nested distributions cost the product — and here is that measured:

type Keys = "k0" | "k1" | … ;                                  // n members
type Pair<A, B> = A extends string ? (B extends string ? `${A}-${B}` : never) : never;
type Cross  = Pair<Keys, Keys>;
type Mapped = { [K in Cross]: { v: K } };

n=10    Types:  486    Instantiations:   621
n=20    Types:  816    Instantiations:  2441      ◄── union ×2, cost ×3.9
n=40    Types: 2076    Instantiations:  9681      ◄── union ×2, cost ×4.0

Doubling the union quadrupled the work. That is the shape to watch for, because it means a helper can be free during development and dominate the build later with no change to the code that uses it — a variant union that grows from ten members to forty is a sixteenfold cost increase in that one type.

For contrast, a single distribution is linear:

type Deep<T> = T extends string ? { a: T; b: T; c: Uppercase<T> } : never;
n=10  → 21 instantiations     n=40 → 81     n=160 → 321          ◄── roughly 2n
PatternGrowthWatch it?

Part 4 — --generateTrace

$ npx tsc sq40.ts --noEmit --generateTrace tr
$ ls tr
legend.json  trace.json  types_0.json  types_1.json  types_2.json  types_3.json

Four types_N.json files, with checkerId 0 to 3 — TypeScript 7's native compiler type-checks in parallel across several checkers, and the trace is emitted per checker. That is worth knowing before reading the output, because a single file's types are split across them.

Use --diagnostics to decide whether to trace at all. A trace is detailed and slow to read; it is worth producing when Check time or Instantiations is unexplained, and a waste of time when the numbers already point at Files or a missing skipLibCheck.

Part 5 — Structural Fixes

SymptomFixEffort
High Filesinclude, types: [], skipLibCheckMinutes

High Instantiations in one areaName intermediate types; reduce nestingHours

Naming an intermediate type is the cheapest code-level fix, because a named type alias gives the compiler something it can compute once and reuse, and gives error messages something short to print. A five-deep inline conditional recomputes on every use and prints its whole expansion when it fails.

❌ Rewriting the expensive type first. The instinct when Check time is high is to go and simplify the clever conditional type someone wrote, because that is the interesting problem. It is usually not the problem: on a file containing a single line, 34,231 of the 34,231 instantiations came from the standard library, and skipLibCheck removed all of them. Refactoring application types before checking the configuration can spend a day to gain nothing measurable.

✅ Work in order of cost: configuration, then caching, then structure, then types. Run --diagnostics, apply skipLibCheck, types: [] and a minimal lib, re-measure. Then incremental, then project references. Only when the numbers still point at Instantiations in your own code is --generateTrace and a type refactor the right move — and by then you know which type to change.

Part 6 — Keeping the Win

// a budget check that fails CI when the numbers regress
$ npx tsc --noEmit --diagnostics > diag.txt
$ node -e "
  const t = require('fs').readFileSync('diag.txt','utf8');
  const get = (k) => Number(t.match(new RegExp(k + ':\\\\s+(\\\\d+)'))[1]);
  const limits = { Files: 1200, Instantiations: 2_000_000 };
  for (const [k, max] of Object.entries(limits)) {
    const v = get(k);
    if (v > max) { console.error(\`\${k} \${v} exceeds budget \${max}\`); process.exit(1); }
  }"

Interview Questions

Beginner: How do you find out why a TypeScript build is slow?

Run tsc --noEmit --diagnostics. It reports file, line, symbol and type counts, the number of instantiations, memory used, and parse, bind and check times separately.

Those numbers partition the problem before any investigation. A high Files count is a configuration issue — something is in the program that should not be. A high Check time with high Instantiations is expensive type-level code. High parse time with a modest check time is simply a large program.

The first surprise when you run it is the scale. I measured a file containing one line, export const x: number = 1;, and it reported 83 files, 58,449 lines and 35,328 types — essentially all of it the standard library and DOM declarations.

Which is why the rule is to measure before changing anything: the intuition that your own clever types are the cost is usually wrong, and the command that tells you takes a second to run.

Beginner: What does skipLibCheck do for performance?

It stops the compiler type-checking declaration files for internal consistency. It does not stop them being used, and it does not weaken checking of your own code at all — which is the misconception that leads people to turn it off.

The effect is large. On that same one-line file I measured 35,328 types and 34,231 instantiations without it, and 342 types and zero instantiations with it — total time falling from 0.319s to 0.049s. Dropping DOM from lib as well removed 25 files and took it to 0.016s.

The reason the ratio is so extreme is that the standard library plus DOM is much larger than most application code, and checking it is work that produces no information about your program.

It is also the option that fixes errors you cannot act on — a dependency whose .d.ts was written for a different compiler version, or two dependencies with conflicting declarations. Keeping it on is the right default; turning it off temporarily is a reasonable diagnostic step when a dependency's types look wrong.

Mid: Why is Instantiations the number to watch?

Because it is the one that can grow non-linearly with data that is not code. Files and lines grow as people write things; instantiations can multiply because a union gained members.

I measured it. A type nesting two distributive conditionals over the same union, feeding a mapped type, gave 621 instantiations at 10 members, 2,441 at 20, and 9,681 at 40 — so doubling the union roughly quadrupled the cost. A variant union growing from ten to forty members is a sixteenfold increase in that one type, with no change to the code using it.

For contrast, a single distribution is linear: the same shape with one conditional gave 21, 81 and 321 instantiations for 10, 40 and 160 members, about 2n. So the thing to look for specifically is nesting — nested conditionals, template literal cross products, and mapped types over computed unions, which lessons 7 and 8 covered as TS2589 and TS2590 in their extreme forms.

It is also deterministic for a given source and config, unlike wall-clock time, which makes it the right number to put a CI budget on. A change to it is always a real change to the program rather than a noisy machine.

Mid: What does --generateTrace give you, and when would you use it?

It writes a profile of the compile: trace.json with timed events in Chrome-trace format, types_N.json listing every type created along with where it came from, and legend.json tying them together.

A detail worth knowing in TypeScript 7 is that there are several types_N.json files — I got four, with checkerId 0 to 3 — because the native compiler type-checks in parallel across multiple checkers. So the types for one file are spread across them, and legend.json is what tells you which is which.

You can load trace.json into chrome://tracing, but for a first look a few lines of Node that filter for events with a duration and sort descending is faster and tells you the same thing.

I would reach for it only after --diagnostics, and only when the diagnostics are unexplained — a high check time with a modest file count and a high instantiation count I cannot attribute. When the numbers already point at a missing skipLibCheck or an include picking up dist, a trace is detailed information about a question already answered.

Senior: A 300k-line monorepo takes 12 minutes to type-check. Plan the work.

I would order the work by cost-to-try rather than by how interesting it is, and re-measure after each step, because the steps have wildly different effort and the cheap ones frequently win.

First, configuration, which is minutes of work. --diagnostics on each package to see where the time is. skipLibCheck on — I measured it taking a trivial program from 35,328 types to 342. types: [] so only the @types packages actually needed load rather than every transitive one. A lib matching the deployment target. include verified not to be picking up dist or generated code. It is common for this alone to halve the time.

Second, caching. incremental: true so warm rebuilds reuse work, and a CI cache for .tsbuildinfo keyed on the compiler version and a hash of the config — unkeyed is lesson 17's green-locally-red-in-CI failure.

Third, project references, which is the days-of-work step and the one that changes the shape of the problem: with composite and declared references, tsc --build skips packages whose inputs have not changed, so a check becomes proportional to the change rather than to the repo. Expect the migration to surface circular dependencies between packages, which is a benefit disguised as an obstacle.

Fourth, and only if diagnostics still point there, the types themselves. --generateTrace to find the expensive ones, then name intermediate types and un-nest distributive conditionals. A helper whose cost is the product of two union sizes is the usual find.

Recommendation: do the configuration pass this week and publish the before/after numbers, add caching, then scope the project-references migration with the trace data in hand. Finish by putting a budget on Files and Instantiations in CI, because a twelve-minute build did not appear overnight and will come back without one.

Senior: How do you stop build performance regressing after you fix it?

By measuring something deterministic in CI and failing on it, because every other mechanism depends on someone noticing gradual change, which nobody does.

Budget the counts, not the time. Wall-clock time varies with the CI machine and produces flaky failures, and a check that fails randomly gets disabled within a month. Instantiations and Files are deterministic for a given source and configuration, so a change to either is always a real change to the program — which makes the failure actionable and therefore survivable.

Set the limits generously and tighten them. A budget at 10% above current usage fails on the next legitimate feature and teaches people to raise the number without looking. Something like double the current figure catches the tenfold regression that actually matters — a nested conditional type, or a union that grew from ten members to forty — while ignoring ordinary growth.

Attribute failures automatically where possible. The check should print which number moved and by how much; the person who broke it then has a starting point rather than a mystery, and the diagnostics output is cheap enough to attach to every CI run as an artefact.

Then revisit the configuration periodically, because the defaults improve. Re-running tsc --init once a year and diffing against the project's config is how a codebase picks up things like the noUncheckedIndexedAccess and exactOptionalPropertyTypes that lesson 14 found in the TS7 template, instead of carrying a config written three years ago indefinitely.

Recommendation: a CI step that parses --diagnostics and enforces generous budgets on Files and Instantiations, the raw output kept as an artefact for trend analysis, and an annual config diff. That is perhaps thirty lines of setup and it converts performance from something someone has to care about into something the build enforces.

6 (hard): Write the CI budget.
Solution 
# package.json
"scripts": { "typecheck:budget": "tsc --noEmit --diagnostics > diag.txt && node scripts/budget.mjs" }

// scripts/budget.mjs
import { readFileSync } from "node:fs";
const text = readFileSync("diag.txt", "utf8");
const read = (key) => {
  const m = text.match(new RegExp(`${key}:\\s+(\\d+)`));
  if (!m) throw new Error(`missing ${key} in diagnostics`);
  return Number(m[1]);
};
const budgets = { Files: 1200, Instantiations: 2_000_000 };
let failed = false;
for (const [key, max] of Object.entries(budgets)) {
  const value = read(key);
  const pct = Math.round((value / max) * 100);
  console.log(`${key}: ${value} / ${max} (${pct}%)`);
  if (value > max) { console.error(`  ✘ ${key} over budget`); failed = true; }
}
process.exit(failed ? 1 : 0);
DecisionReason
Counts, not secondsDeterministic; no flaky failures
Limits ≈ 2× currentCatches 10× regressions, ignores growth
Print usage as a percentageVisible drift before it fails
Throw on a missing keyA silent no-op check is worse than none
Keep diag.txt as an artefactTrend data for later

The percentage line is what makes it useful rather than merely blocking: a reviewer sees "Instantiations: 1,900,000 / 2,000,000 (95%)" and can act before the build fails for someone else.

  • Run --diagnostics before changing anything — the causes need different fixes.
  • A one-line file already costs 83 files and 35,328 types — your code is rarely the baseline.
  • skipLibCheck took that to 342 types and 0 instantiations — the largest single win.
  • A minimal lib removed 25 more files — 20× faster in total.
  • skipLibCheck never weakens checking of your own code.
  • types: [] stops transitive @types loading — check it is set.
  • Instantiations is the number to watch — it grows with data, not just code.
  • Nested distributions cost the product: 621 → 2,441 → 9,681 as a union doubled.

  • Name intermediate types so the compiler computes once and errors stay readable.
  • TS7 emits one types_N.json per parallel checker — read legend.json.
