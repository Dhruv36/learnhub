Declaration Files Modules, Config & Build

What you'll master: what declaration: true actually emits, read from real output — private members elided, non-exported types inlined, and the trailing export {}; writing .d.ts by hand with declare, export = and declare global; isolatedDeclarations, the flag that lets other tools generate your declarations, and the two errors it produces — TS9013 for an un-annotated expression and TS9009 for an accessor; how @types, typeRoots, types and skipLibCheck decide which declarations reach your program; and the publishing failures that make a package's types unusable for consumers. Prerequisites: Modules & Interop.

Part 1 — What Declaration Emit Produces

A .d.ts file is the type surface of a module with all implementation removed. The compiler generates it, and reading real output teaches more than a description.

// lib.ts — input
interface Hidden { x: number }
export function make(): Hidden { return { x: 1 }; }
export const inferred = () => ({ a: 1, b: "s" });
export class C { private secret = 1; get val() { return this.secret; } }

$ npx tsc lib.ts --declaration --emitDeclarationOnly --outDir d --module nodenext
$ cat d/lib.d.ts                              ◄── verified output

interface Hidden {
    x: number;
}
export declare function make(): Hidden;
export declare const inferred: () => {
    a: number;
    b: string;
};
export declare class C {
    private secret;
    get val(): number;
}
export {};
InputOutputWhy
interface Hidden (not exported)Included, un-exportedmake's signature needs it
export function make(): Hiddenexport declare functionNo body in a declaration
An inferred arrowThe full inferred type, written outConsumers get the real shape
private secret = 1private secret;The type is elided, the slot is not
get val()get val(): numberInferred and written
—export {}Marks the file as a module
🔑 private secret; keeps the member but drops its type. A private field still affects assignability — it is part of what makes two classes incompatible — so it cannot be removed, but its type is nobody's business. That is also why a private field gives real nominal typing, as lesson 13 mentioned.

The inlined Hidden interface is worth noticing. The compiler did not error about a private type appearing in a public signature; it simply wrote the declaration into the output. That is convenient and it means a type you never exported can still become part of your public API — consumers can use the shape, they just cannot import it by name.

Part 2 — Writing Declarations by Hand

You write .d.ts when there is no TypeScript source to generate from: an untyped dependency, a global script, a build-tool-provided value.

// a module with no types of its own
declare module "legacy-lib" {
  export function compute(n: number): number;
  export default compute;
}

// a CommonJS module whose export IS the function
declare module "single-export" {
  function fn(x: string): void;
  export = fn;
}

// globals injected by a bundler or a script tag
declare global {
  const __BUILD_ID__: string;
  interface Window { analytics?: { track(e: string): void } }
}
ConstructDeclaresNote
declare const/function/classA value that exists elsewhereNo initialiser, no body
declare module "pkg"A whole module's typesAmbient in a script file — see lesson 15
export =The module's export is one thingCommonJS only; cannot mix with export default
declare global { }Additions to the global scopeOnly valid inside a module file
/// <reference types="node" />A dependency on another declaration setPrefer types in tsconfig

declare means "this exists, trust me". Nothing in a declaration file is checked against an implementation, because there is no implementation to check against — so a hand-written .d.ts is exactly as accurate as whoever wrote it, and a wrong one produces the same silent failures as the lying type predicate from lesson 11. That is the argument for preferring generated declarations wherever source exists.

Part 3 — isolatedDeclarations

Generating a .d.ts normally requires the whole type-checker, which is why only tsc could do it. isolatedDeclarations restricts your code to what a single-file tool can transform, so esbuild, SWC or a bundler can emit declarations too — the same motivation as isolatedModules in lesson 14.

// verified with tsc 7.0.2, each line compiled alone
export function f() { return { a: 1 }; }          // ✔ no error
export const h = 1;                                // ✔
export const k: number = 1;                        // ✔
export const m = (n: number): number => n * 2;     // ✔ return type annotated

export const g = (n: number) => n * 2;
// error TS9013: Expression type can't be inferred with --isolatedDeclarations.

export class D { get v() { return 1; } }
// error TS9009: At least one accessor must have an explicit type annotation
//               with --isolatedDeclarations.
CodeMeaningFix
TS9013An exported value's type needs inference from an expressionAnnotate the return type or the variable
TS9009An accessor pair has no explicit typeAnnotate the getter's return type

The interesting result is which cases pass. A function declaration with an inferred return type is accepted, and so is a variable initialised with a literal — so the flag is narrower than "annotate all exports". What it rejects is an exported binding whose type can only be determined by evaluating an expression, which is precisely what a tool without a type-checker cannot do.

The cost is annotations on exported arrow functions and accessors; the benefit is that declaration emit stops being the slowest part of a library build. For a library it is usually worth it. For an application that emits no declarations, it buys nothing.

Part 4 — How Declarations Reach Your Program

MechanismEffect
A package's own types/exports fieldTypes ship with the package — the modern default
@types/pkg in node_modulesCommunity declarations from DefinitelyTyped
typeRootsWhich folders are scanned for global type packages
types: []Which of those are loaded globally — [] means none
Your own .d.ts in the projectPicked up by include like any file
skipLibCheckDo not type-check declaration files themselves

types: [] is the one most projects should set, and lesson 14 showed that tsc --init now does. Without it, every @types/* package anywhere in node_modules is loaded into the global scope — including transitive ones you did not install — which is how a Node service ends up believing document exists, or how two packages' conflicting global declarations produce an error in a file that imports neither.

skipLibCheck is worth understanding rather than cargo-culting. It does not skip using declarations; it skips type-checking them for internal consistency. Two dependencies with incompatible declarations, or a .d.ts written for a newer compiler, otherwise produce errors in code you do not own and cannot fix. Leaving it on is the right default; turning it off temporarily is a reasonable diagnostic step.

❌ Referencing a devDependency's types in a public signature. export function h(app: Express): void compiles perfectly in the library, because @types/express is installed there. A consumer who does not have it gets a declaration file referring to a module that does not resolve — and the error names your .d.ts, which makes it look like your package is broken rather than under-declared.

✅ Decide deliberately which types are part of your contract. If the dependency really is part of the API, it belongs in dependencies or peerDependencies so consumers get it. If only a small part is used, declare the minimal structural shape yourself — { use(fn: Handler): void } — and keep the dependency private. The test that catches this is installing the packed tarball into an empty project and type-checking there; nothing inside the repo will reveal it.

Part 6 — Reading Someone Else's Declarations

A .d.ts is the most reliable documentation a package has, because it is what the compiler actually believes. Knowing how to read one is a practical skill.

What you seeWhat it tells you
export =CommonJS; import with a default import or import = require
Overloads, most specific firstWhich argument combinations are intended
any in a return typeUnchecked from here on — wrap it
declare globalThe package adds globals; order of imports can matter
A phantom or branded propertyValues must come from the package's own functions
@deprecated JSDocEditors will strike it through

An any in a dependency's declarations is the boundary problem from lesson 11 wearing a type. It is not a warning anywhere — it silently disables checking from that point outward, inside your otherwise strict program. The response is the same as for any untrusted input: wrap the call in one module, give that module an honest signature, and validate if the value crosses into logic that matters.

Interview Questions

Beginner: What is a .d.ts file?

It is a declaration file: the type surface of a module with every implementation removed. It contains signatures, types and declared values, and no function bodies or initialisers.

There are two ways to get one. The compiler generates it from TypeScript source when declaration: true is set, which is how a library ships types. Or you write one by hand, which is what you do for something that has no TypeScript source at all — an untyped dependency, a global injected by a bundler, or a file type like .svg.

The important property is that a declaration file is never checked against an implementation, because there is no implementation present. declare means "this exists, trust me". A generated one is accurate because it came from real code; a hand-written one is exactly as accurate as whoever wrote it.

That asymmetry is the practical rule: generate them wherever source exists, and treat a hand-written declaration as a claim to be verified rather than a guarantee.

Beginner: What happens to private class members in declaration emit?

The member stays and its type is removed. A field declared private secret = 1 appears in the .d.ts as private secret; — I verified that in real output.

It cannot be removed entirely because a private member affects assignability. Two classes with structurally identical public surfaces are not interchangeable if either has a private member, so the slot is part of the type even though its contents are not. That is also the mechanism behind using a private field for genuine nominal typing.

The same output shows two other things worth knowing: inferred types are written out in full, so an exported arrow returning { a: 1, b: "s" } becomes an explicit () => { a: number; b: string }; and a non-exported interface used in an exported signature is inlined into the declaration file rather than being an error.

That last point surprises people: a type you deliberately did not export can still become part of your public API by appearing in a signature. Consumers can use the shape, they just cannot import it by name.

Mid: What is isolatedDeclarations for?

It lets tools other than tsc generate declaration files. Normally producing a .d.ts needs the full type-checker, because inferring an exported value's type may require looking across the whole program — which is why declaration emit is often the slowest part of a library build, and why esbuild and SWC could not do it.

The flag restricts your exports to what a single-file tool can determine locally. I verified the two errors: TS9013, "Expression type can't be inferred with --isolatedDeclarations", for export const g = (n: number) => n * 2; and TS9009, "At least one accessor must have an explicit type annotation", for a getter with no return type.

What passes is narrower than people assume. A function declaration with an inferred return type is fine, and so is export const h = 1. So the flag is not "annotate every export" — it rejects exported bindings whose type requires evaluating an expression, which is exactly what a tool without a type-checker cannot do.

It is the same idea as isolatedModules: accept a small restriction on the source so the build can be split across faster tools. Worth it for a library; for an application that emits no declarations it buys nothing.

Mid: What do types, typeRoots and skipLibCheck do?

typeRoots lists the folders scanned for global type packages, defaulting to every node_modules/@types up the tree. types lists which of those are actually loaded into the global scope.

Leaving types unset means all of them load, including transitive ones you never installed. That is how a Node service ends up believing document exists, and how two packages' conflicting global declarations produce an error in a file that imports neither. Setting types: [] and adding back what you need is the fix, and TypeScript 7's tsc --init now generates exactly that.

skipLibCheck is different and often misunderstood: it does not stop declarations being used, only from being type-checked for internal consistency. Without it, a dependency whose .d.ts was written for a different compiler version, or two dependencies with incompatible declarations, produce errors in code you do not own and cannot fix.

So I keep skipLibCheck on as a default and turn it off temporarily when diagnosing something odd about a dependency's types. It is worth noting it does not weaken checking of your own code at all — which is the misconception that leads people to disable it.

Senior: A published package's types do not work for consumers, though they work in the repo. How do you debug it?

The framing that matters is that everything inside the repo is a different environment from a consumer's: different node_modules, different tsconfig, and a different set of files. So I would stop testing in the repo immediately and reproduce as a consumer.

Pack and install into an empty project. npm pack, then install the tarball into a fresh directory with a strict tsconfig and import the package. That single step catches the majority of these: dist missing from files, so the package ships with nothing; no types condition in the exports map, so the import is implicitly any; or a subpath that resolves at run time but has no declarations.

Then look for devDependency leakage, which is the subtlest cause. A public signature mentioning a type from a package that is only a dev dependency compiles fine in the repo and produces an unresolvable import in the shipped .d.ts. The error names your declaration file, so it reads as your package being broken. Either promote the dependency or declare the minimal structural shape yourself.

Check the strictness the declarations were built under. Declarations generated from a loose config can contain types that a strict consumer rejects — the classic being an implicit any or a missing undefined that only fails under strictNullChecks. Building the library with at least the strictness you expect consumers to use avoids reports you cannot reproduce.

Recommendation: add a CI job that packs the tarball, installs it into a throwaway project with strict settings, imports every documented entry point and runs tsc --noEmit. It is about twenty lines and it makes this entire class of bug impossible to ship, which no amount of in-repo checking can do.

Senior: How do you handle a dependency whose types are wrong or use any?

I would treat the dependency's declarations as untrusted input — the same category as network data from lesson 11 — and contain it in one place rather than patching it globally.

Why any in a dependency is worse than it looks: it produces no error and no warning anywhere, and it disables checking outward from every call site. A codebase can be fully strict and completely unchecked along the path that matters most, which is precisely the failure that makes teams conclude strict mode "did not help".

The wrapper module is my default answer. One file imports the dependency, exports functions with honest signatures, and is the only place the loose types are visible. That gives one location to review, one place to add validation if the values feed real logic, and a seam that makes replacing or upgrading the dependency a local change. It also documents which part of a large library you actually depend on.

Augmentation is for adding, not correcting. As lesson 15 covered, declare module in a module file adds to a package's types but cannot contradict them — declaring a member with a different type is a conflict, not an override. So augmentation is right for a plugin that genuinely adds a property, and wrong for fixing a signature that is simply incorrect.

Recommendation: wrapper modules for loose or wrong types, augmentation only for genuine additions, a patch file or a fork for declarations that are actively broken, and a PR to DefinitelyTyped or upstream so the fix eventually stops being yours to carry. And a lint rule against explicit any in your own code, so the only any in the program is the one you deliberately wrapped.

5 (hard): Write a wrapper for a dependency that returns any.
Solution 
// the dependency's declarations
declare module "sloppy-lib" {
  export function fetchRecord(id: string): any;      // ← unchecked from here outward
}

// wrapper.ts — the ONLY module that imports it
import { fetchRecord } from "sloppy-lib";
import { z } from "zod";

const Record = z.object({ id: z.string(), name: z.string(), score: z.number() });
export type Record = z.infer<typeof Record>;

export function getRecord(id: string): Record {
  const raw: unknown = fetchRecord(id);      // the any stops here
  return Record.parse(raw);                  // and becomes a checked value
}
Without the wrapperWith it
any spreads from every call siteContained in one file
No validation anywhereOne parse, at the boundary
Replacing the dependency touches everythingA local change
Nothing records which parts are usedThe wrapper's exports document it

Assigning the result to unknown immediately is the key line — it is what converts the dependency's any into something the compiler will insist is checked, which is the same discipline lesson 11 applied to JSON.parse.

🎯 Key Takeaways

  • A .d.ts is a type surface with no implementation — generated, or hand-written.
  • Nothing in a declaration file is checked against an implementation — declare means "trust me".
  • Generate declarations wherever source exists; hand-written ones drift silently.
  • Private members survive as private secret; — the slot affects assignability, the type does not.
  • A non-exported type used in a signature is inlined — its shape becomes public anyway.
  • Inferred export types are written out, so an implementation change can alter your public API.
  • export = declares a CommonJS single export and cannot mix with ES exports.
  • declare global only works inside a module file.
  • isolatedDeclarations lets non-tsc tools emit declarations.
  • It rejects expression-level inference — TS9013 — and un-annotated accessors — TS9009 — not all inference.
  • types: [] stops every transitive @types loading globally.
  • skipLibCheck skips checking declarations, not using them — keep it on.
  • A devDependency type in a public signature breaks consumers and blames your .d.ts.
  • Put types before default in an exports condition — order decides the match.
  • Pack, install into an empty project, and type-check — the only test that sees what consumers see.
