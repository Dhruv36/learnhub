Modules & Interop Modules, Config & Build

What you'll master: import type and the inline type modifier, and what each one emits; the explicit .js extension that the nodenext family requires in relative imports, and the TS2835 that tells you so; CommonJS interop, where TypeScript 7 removed the ability to turn esModuleInterop and allowSyntheticDefaultImports off — both are now permanent; ambient modules and declare module augmentation, for assets and for patching a dependency's types; and circular imports, which type-check with zero errors and throw a ReferenceError at run time. Prerequisites: tsconfig in Depth.

Part 1 — Type-Only Imports

Two syntaxes mark an import as existing only at the type level, and the difference is granularity.

import type { A } from "./dep.js";          // the whole clause is type-only
import { type A, b } from "./dep.js";       // A is type-only, b is a real import
FormEmitsUse when
import type { A }NothingEverything in the clause is a type
import { type A, b }An import of b onlyMixed types and values from one module
import { A, b }Depends on the flagsRejected under verbatimModuleSyntax (TS1484)
import "./side-effect.js"The import, alwaysDeliberate side effects

Under verbatimModuleSyntax — on by default from tsc --init, as lesson 14 showed — importing a type without marking it is TS1484. That is worth treating as a habit rather than a flag, because marking type-only imports makes the runtime cost of every import line visible where it is written. A reader can tell at a glance which imports pull code into the bundle.

🔑 The inline modifier is the one to reach for by default. import { type Config, loadConfig } from "./config.js" keeps a module's types and values in one statement, so adding a type import later does not mean adding a second line from the same path — which is how duplicate-import lint noise starts.

Part 2 — Extensions and Resolution

Under module: nodenext the compiler resolves the way Node does, and Node requires the extension in an ES module.

import { b } from "./dep";
// error TS2835: Relative import paths need explicit file extensions in ECMAScript
//   imports when '--moduleResolution' is 'node16' or 'nodenext'.
//   Did you mean './dep.js'?                                        ◄── verified

You write .js even though the file on disk is .ts. That reads wrong the first time and is correct: the import specifier describes the emitted output, which is what the runtime will actually resolve, and the compiler maps it back to the source when type-checking.

SetupWriteWhy
nodenext, source .ts"./dep.js"The specifier is the runtime path
nodenext, source .mts"./dep.mjs"Same rule

The other half of nodenext resolution is that the nearest package.json's type field decides whether each file is an ES module or CommonJS — which, as lesson 14 showed, is where TS1295 comes from. Under moduleResolution: bundler neither rule applies, because the bundler is doing the resolving.

Part 3 — CommonJS Interop, and What TS7 Removed

Two long-standing interop flags can no longer be disabled:

$ npx tsc a.ts --noEmit --module nodenext --esModuleInterop false
error TS5108: Option 'esModuleInterop=false' has been removed.            ◄── verified

$ npx tsc a.ts --noEmit --module nodenext --allowSyntheticDefaultImports false
error TS5108: Option 'allowSyntheticDefaultImports=false' has been removed. ◄── verified

The behaviour they enabled is now simply how TypeScript works: a CommonJS module with module.exports = fn can be imported as import fn from "pkg", and the compiler emits the helper that makes that correct at run time. The old world where the same import worked or failed depending on a tsconfig flag is gone, which removes a whole category of "works in my project" bug reports.

SituationWrite
CJS module with a single exportimport fn from "pkg"
CJS module with named exportsimport { a, b } from "pkg"
You need the whole namespace objectimport * as ns from "pkg"
A .d.ts using export =import x = require("pkg"), or a default import
Loading a CJS-only package from ESM at run timeconst m = await import("pkg")

import * as ns is not a default import and never was — it binds the module namespace object, which is not callable even if the underlying CommonJS export is a function. Using it to work around a missing default is the mistake that esModuleInterop existed to make unnecessary.

Part 4 — Ambient Modules and Augmentation

declare module has two distinct jobs, and conflating them causes confusion.

// 1. an ambient module: declare types for something with no .d.ts — assets, for instance
declare module "*.svg" {
  const url: string;
  export default url;
}

import icon from "./logo.svg";       // ✔ typed as string   ◄── verified

// 2. augmentation: ADD to an existing module's types
import "./dep.js";                   // the import is required — it makes this an augmentation
declare module "./dep.js" {
  export const extra: number;
}
import { extra } from "./dep.js";    // ✔ compiles          ◄── verified
GoalFormRequires an import of the module?
Type an untyped moduledeclare module "pkg"No — it declares it wholesale
Type a file patterndeclare module "*.svg"No
Add to an existing moduleSame syntax, in a file with importsYes
Add to the global scopedeclare global { … }Yes, in a module file

Whether declare module "x" declares or augments depends on whether the containing file is a module, which is decided by whether it has any top-level import or export. A file with no imports declares the module from scratch and shadows the real types; add an import and the same block augments them. That is the whole explanation for the common symptom of an augmentation that silently replaces a package's types instead of extending them.

Augmentation is the right tool for patching a dependency — adding a property to Express's Request, or a method to a library's prototype that a plugin installs. It is the wrong tool for fixing wrong types in a dependency, where the honest options are a wrapper module or a patch-package-style fix, because an augmentation that contradicts the original produces a conflict rather than an override.

Part 5 — Circular Imports

The type system tolerates cycles completely. The runtime does not.

// x.ts
import { y } from "./y.js";
export const x = "x";
export const combined = x + y;

// y.ts
import { x } from "./x.js";
export const y = x + "y";

$ npx tsc x.ts y.ts main.ts --module nodenext --outDir out
                                    ◄── zero errors; the cycle is fine for types
$ node out/main.js
ReferenceError: Cannot access 'x' before initialization      ◄── verified

y.ts runs while x.ts is still initialising, so x is in its temporal dead zone. The compiler cannot warn about this because module evaluation order is a runtime property, and for type-only cycles there is nothing wrong at all — two modules referring to each other's types is normal and harmless.

CycleType-checksRuns
Types only (import type)YesYes — nothing is emitted
Functions called laterYesUsually — the binding is live by call time
Values read during module initYesNo — ReferenceError
Class extends across a cycleYesNo — the base is undefined

❌ Treating a ReferenceError: Cannot access 'x' before initialization as a bundler bug. It looks like tooling because it appears only in some build configurations and only for some entry points — the same cycle can work under one bundler's module ordering and fail under another, and adding an unrelated import can change which module initialises first. Chasing it through bundler configuration can burn a day.

✅ Read it as what it is: a genuine import cycle with a value read during initialisation. Find it with madge --circular or an equivalent, then break it properly — move the shared value into a third module that both import, convert an eagerly-read constant into a function called later, or use import type if only the type was needed. Reordering imports makes the symptom move rather than fixing it.

Barrel files deserve the specific warning because they cause both of this lesson's runtime problems at once: importing one name from a barrel evaluates every module it re-exports, which both pulls unused code into the bundle and creates exactly the initialisation-order cycles that produce ReferenceError. A barrel at a package boundary, listing a deliberately small public surface, is reasonable; a barrel per directory is where the trouble starts.

Interview Questions

Beginner: What is the difference between import type and import { type X }?

Both mark something as existing only at the type level, so nothing is emitted for it. The difference is scope: import type { A } from "./dep.js" makes the whole clause type-only, while import { type A, b } from "./dep.js" marks just A and leaves b as a real runtime import.

The inline form is usually the better default, because a module often exports both types and values and the alternative is two import statements from the same path — which then drift apart as the file changes.

Marking matters because of verbatimModuleSyntax, which is on by default in a config generated by tsc --init. Under it, importing a type without marking it is TS1484, "'A' is a type and must be imported using a type-only import".

Beyond satisfying the flag, it is worth doing as a habit: it makes the runtime cost of each import line visible at the import site, so a reader can tell which imports pull code into the bundle and which cost nothing.

Beginner: Why do you write .js when importing a .ts file?

Because the import specifier describes the emitted output, not the source file. Under module: nodenext the compiler resolves imports the way Node does, and Node requires an explicit extension in an ES module — so the string in your source has to be the path the runtime will actually look for, which is the compiled .js.

Omitting it gives TS2835: "Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './dep.js'?" — I verified that, and the message helpfully includes the fix.

The compiler maps the specifier back to ./dep.ts when type-checking, so everything resolves correctly at build time. It reads oddly the first time and it is the only arrangement that works for both phases at once.

Under moduleResolution: bundler the rule does not apply, because the bundler is doing the resolution and is happy with extensionless specifiers. That is one of the practical differences between the two setups.

Mid: What changed about CommonJS interop in TypeScript 7?

The two flags that controlled it can no longer be turned off. esModuleInterop: false and allowSyntheticDefaultImports: false are both TS5108, "has been removed" — I verified both.

So the behaviour they enabled is now just how TypeScript works. A CommonJS module whose export is a single function can be imported with import fn from "pkg", and the compiler emits the interop helper that makes that correct at run time.

That matters because it removes a class of confusion that used to be genuinely hard to debug: the same import statement worked or failed depending on a tsconfig setting, so a snippet copied from another project might not compile, and a library's documentation might contradict your build. There is now one answer.

The mistake that survives is using import * as fn from "pkg" and then calling fn(). A namespace import binds the module namespace object, which is not callable regardless of what the underlying CommonJS export is — and reaching for it to work around a missing default is exactly what the interop behaviour makes unnecessary.

Mid: When does declare module "x" augment, and when does it replace?

It depends entirely on whether the file containing it is a module, which in turn depends on whether that file has any top-level import or export.

In a file with no imports or exports — a plain .d.ts script — declare module "x" declares an ambient module from scratch. That is how you type something with no declarations at all, including wildcard patterns: I verified that declare module "*.svg" with a default string export makes import icon from "./logo.svg" type-check as a string.

In a file that is a module, the same syntax augments the existing declarations. I verified that importing "./dep.js" and then writing declare module "./dep.js" { export const extra: number } makes extra importable alongside the module's real exports.

The failure this explains is common: an augmentation intended to add one property silently replaces a package's entire type surface, because the file it was written in had no imports. Adding a single import "pkg" fixes it. It is also worth knowing that augmentation adds and cannot override — declaring a member with a type that contradicts the original produces a conflict, so fixing wrong third-party types needs a wrapper module instead.

Senior: A ReferenceError: Cannot access 'x' before initialization appears only in the production bundle. How do you approach it?

I would treat it as a real import cycle from the start, because that is what the message means, and resist the pull toward bundler configuration — which is where this usually gets misdiagnosed.

Why it looks like tooling: the error depends on module evaluation order, which differs between the dev server and the production bundle, and between bundlers. The same cycle can work in one and fail in the other, and adding an unrelated import elsewhere can change which module initialises first. That makes it feel non-deterministic when it is in fact a fixed structural problem being exposed intermittently.

Why the compiler said nothing: TypeScript tolerates cycles completely, and correctly — two modules referring to each other's types is normal, and nothing is emitted for it. I verified that a value cycle type-checks with zero errors and then throws at run time. Module evaluation order is not something the type system models.

How I would find and fix it: madge --circular or the equivalent to get the actual cycles, then look for one where a value is read during module initialisation rather than inside a function. The fixes, in order of preference: change the import to import type if only the type was needed, which removes the runtime edge entirely; extract the shared value into a third module both sides import; or defer the read into a function called after initialisation. Reordering imports makes the symptom move, which is worse than leaving it.

Recommendation: fix the specific cycle, then add a circular-dependency check to CI, and look hard at barrel files — importing one name from a barrel evaluates everything it re-exports, which is the most common way a cycle gets created by accident in a codebase that has no obvious mutual dependency.

Senior: How would you design the module surface of a shared library?

The goal is that consumers can import what they need without pulling in what they do not, and that the surface can evolve without breaking them — which mostly comes down to being explicit about entry points.

Named exports throughout, and an exports map in package.json. Named exports make renames visible and let auto-import and refactoring tools work; default exports get renamed silently at every call site. The exports field declares which paths are public, which is what lets internal files move freely — without it, consumers deep-import into internals and the next reorganisation is a breaking change nobody intended.

Subpath entry points rather than one barrel. A single index that re-exports everything means importing one helper evaluates every module in the package, which both defeats tree-shaking and creates initialisation-order cycles. A small number of coherent subpaths — pkg, pkg/testing — gives consumers granularity without exposing the file layout.

Types travel with the values, and are re-exported explicitly. export type { … } rather than export *, both because isolatedModules requires it for type re-exports and because export * makes collisions silent and the public surface impossible to read from the source.

Publish for the stricter consumer. Building with module: nodenext means the package satisfies Node's resolution rules, which bundler-based consumers will also accept; the reverse is not true, so a package that only works under bundler resolution will generate issues from Node users.

Recommendation: named exports, an explicit exports map with a few coherent subpaths, no cross-subpath barrels, declaration and declarationMap so consumers can navigate to source, and a test that imports the built package from a fresh directory — which is the only way to catch a broken exports map before a user does.

🎯 Key Takeaways

  • import type marks a whole clause; import { type X } marks one name.
  • Prefer the inline modifier — one import line per module path as the file grows.
  • Marking type-only imports makes each import's runtime cost visible where it is written.
  • Under nodenext, write the .js extension — the specifier is the output path.
  • Omitting it is TS2835, and the message names the fix.
  • "./dep.js" is correct under both nodenext and bundler — use it either way.
  • esModuleInterop: false was removed in TS7 (TS5108); interop is permanent.
  • allowSyntheticDefaultImports: false was removed too.
  • import * as ns is a namespace object, not a default — it is not callable.
  • declare module declares in a script and augments in a module — the difference is whether the file has imports.
  • Augmentation adds; it cannot override — wrong third-party types need a wrapper.
  • Circular imports type-check with zero errors and throw ReferenceError at run time.
  • Type-only cycles are harmless; value cycles read during init are not.
  • Reordering imports moves a cycle's symptom — extract the shared value instead.
  • Barrel files cause both problems at once — eager evaluation and accidental cycles.
