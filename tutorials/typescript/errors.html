Typed Errors Correctness at the Boundary

What you'll master: why catch (e) is unknown and why that is correct — JavaScript lets you throw anything, and the type system has no way to know what a call might throw; the TS1196 rule that a catch annotation may only be any or unknown; narrowing a caught value properly; custom error classes, name, and cause, which is typed unknown; the ES5 prototype workaround that TypeScript 7 made obsolete by removing the target entirely; and the real trade between throwing and returning a Result, including where each belongs. Prerequisites: Runtime Validation.

Part 1 — throw Accepts Anything

JavaScript places no constraint on what may be thrown, and TypeScript does not add one.

function f(): never { throw "a string"; }    // ✔ compiles
function g(): never { throw 42; }            // ✔ compiles
function h(): never { throw { code: 1 }; }   // ✔ compiles

A function signature cannot declare what it throws either — there is no throws clause. So at a catch, the compiler genuinely has no information, and says so:

try { … } catch (e) {
  const x: 0 = e;
  // error TS2322: Type 'unknown' is not assignable to type '0'.   ◄── verified: e is unknown
}
🔑 unknown in catch is not pessimism — it is accuracy. The value could be an Error from your code, a DOMException, a string thrown by a dependency, a rejected promise's non-error value, or undefined from throw undefined. Anything that assumes otherwise is guessing.

The behaviour comes from useUnknownInCatchVariables, a member of strict and therefore on by default in TypeScript 7. And the annotation you might reach for is not allowed:

try { … } catch (e: Error) { … }
// error TS1196: Catch clause variable type annotation must be 'any' or 'unknown' if specified.

Part 2 — Narrowing a Caught Value

Everything from lesson 5 applies: instanceof, typeof and property checks turn unknown into something usable.

try { … } catch (e) {
  if (e instanceof AppError)      handle(e.code);      // e.code: number   ◄── verified
  else if (e instanceof Error)    log(e.message);      // e.message: string
  else                            log(String(e));      // a string, a number, anything
}

The else branch is not defensive padding. Rejected promises from other libraries, values thrown across a worker boundary and deserialised errors all routinely arrive as non-Error values, and code that assumes e.message exists throws a second error inside its own error handler — which is how a handled failure becomes an unhandled one.

Part 3 — Custom Error Classes

A custom class gives a value that instanceof can identify and a place to put structured fields.

class AppError extends Error {
  constructor(message: string, readonly code: number, options?: ErrorOptions) {
    super(message, options);
    this.name = "AppError";        // without this, the stack says "Error: save failed"
  }
}

// compiled to ES2015 and run under Node — verified
instanceof AppError: true
instanceof Error:    true
name: AppError | code: 500
stack first line:    AppError: save failed

The historical workaround is gone. Under a downlevel ES5 target, subclassing built-ins broke instanceof, and every custom error carried Object.setPrototypeOf(this, new.target.prototype). TypeScript 7 removed the target outright:

$ npx tsc t.ts --noEmit --target es5
error TS5108: Option 'target=ES5' has been removed. Please remove it from your configuration.

So that line can be deleted from new code. If you meet it in an existing codebase, it is a fossil of an ES5 build, not something the current compiler needs.

Part 4 — cause, and Why It Is unknown

Error.cause attaches the original failure to a wrapping error, so context accumulates without the underlying detail being lost.

try {
  await db.save(user);
} catch (e) {
  throw new AppError("could not save user", 500, { cause: e });
}

Reading it back requires the same discipline as catch itself, for the same reason:

if (e instanceof Error) {
  const c: 0 = e.cause;
  // error TS2322: Type 'unknown' is not assignable to type '0'.   ◄── verified
}

cause is unknown because anything can be thrown and therefore anything can be a cause. Walking a chain means narrowing at each step — which is correct, and is why a small helper is worth writing once:

function* causes(e: unknown): Generator<unknown> {
  let cur = e;
  while (cur instanceof Error && cur.cause !== undefined) { yield cur.cause; cur = cur.cause; }
}

Part 5 — Throwing vs Returning a Result

A Result type moves failure into the return type, where the compiler can see it.

type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E };

const r = parseConfig(text);
if (r.ok) use(r.value);        // r.value: T      ◄── verified
else      report(r.error);     // r.error: Error

Because it is a discriminated union, the failure branch cannot be skipped silently — that is the entire advantage over an exception, which is invisible in every signature it passes through.

throwResult
Visible in the signatureNoYes
Can be ignoredYes, silentlyNot without a compile error
Propagates without ceremonyYesNo — every caller unwraps
Works with async/awaitNaturallyYes, but wrapping is manual
Interops with the ecosystemYesAt every library edge you convert
SuitsGenuinely exceptional failuresExpected, branchable outcomes

❌ Converting an entire codebase to Result. Because Result does not propagate on its own, every intermediate function that cannot handle a failure still has to unwrap it and re-wrap it, and TypeScript has no ? operator to do that for you. Twenty layers of plumbing later, the error handling is more code than the logic, and the boundary with every library — all of which throw — needs a conversion anyway.

✅ Use Result where the failure is an expected outcome the caller must branch on — parsing, validation, a lookup that may legitimately miss, an operation the UI renders differently when it fails. Throw for genuinely exceptional conditions: a broken invariant, a missing config at startup, a database that is down. That keeps the plumbing proportional to the number of decisions actually being made.

Part 6 — Async, and the Boundary

Promise<T> describes only the success value. There is no place in the type for the rejection, so an async function's failures are as invisible as a synchronous throw.

async function save(u: User): Promise<void> { throw new Error("db down"); }   // ✔ compiles
SituationWhat arrivesHandling
await a rejected promiseThe rejection value — unknownNarrow as usual
Promise.allThe first rejection onlyallSettled if you need all
Promise.allSettled{ status, value | reason }reason is any
A floating promiseAn unhandled rejectionLint rule; void deliberately
fetch on a 500A resolved promiseCheck res.ok — it does not reject

The fetch row is the one that produces real bugs: it rejects only on network failure, so a 500 response resolves normally and the error path is never taken. Checking res.ok and turning a bad status into a typed error at that boundary is the fix, and it belongs with the validation from the previous lesson — one place where the response becomes either a trusted typed value or a named failure.

Interview Questions

Beginner: Why is catch (e) typed unknown?

Because JavaScript allows anything to be thrown, and nothing in the type system records what a given call might throw. throw "a string", throw 42 and throw { code: 1 } all compile, and there is no throws clause on a function signature to declare the possibility.

So at the catch site the compiler has no information at all, and unknown is the accurate answer. I verified it: assigning the caught variable to another type gives TS2322 with "Type 'unknown' is not assignable".

It comes from useUnknownInCatchVariables, part of strict and therefore on by default in TypeScript 7. Before that flag the variable was any, which meant e.message compiled and threw whenever a non-Error arrived.

The practical handling is to narrow: e instanceof Error for the common case, plus a fallback that uses String(e), which is safe for any value at all.

The fallback is not theoretical. Rejected promises from older libraries, values thrown across a worker or iframe boundary, and errors that have been serialised and revived all commonly arrive as something other than an Error, and a handler that reads e.message unconditionally throws a second time — inside the code that was supposed to contain the first failure.

Beginner: Can you annotate a catch variable?

Only with any or unknown. Anything else is TS1196: "Catch clause variable type annotation must be 'any' or 'unknown' if specified" — I verified that catch (e: Error) is rejected.

The restriction exists because an annotation there would be a claim about what was thrown, and the compiler has no way to check it. Allowing catch (e: Error) would be exactly the unsafe assertion that useUnknownInCatchVariables was introduced to prevent.

catch (e: any) is allowed and is the wrong choice: it restores the old behaviour, so e.message compiles and throws a second error inside the handler when a string or a plain object arrives.

Writing catch (e: unknown) explicitly is fine and identical to the default under strict. Some teams prefer it as documentation, since it makes the narrowing requirement obvious to a reader who has not internalised the flag.

If a handler genuinely needs a typed value, the way to get one is a check rather than an annotation — a narrowing if, or a small toError(e: unknown): Error helper that wraps anything non-Error in one. That puts the conversion in a single tested place instead of asserting it at every catch site.

Mid: How do you write a custom error class, and what has changed?

Extend Error, pass the message and options to super, set this.name, and add whatever fields callers need to branch on.

Setting name matters more than people expect: without it, the stack trace and every log line say Error: save failed rather than AppError: save failed. I verified the difference by compiling and running the class — instanceof AppError and instanceof Error are both true, and the stack's first line carries the custom name.

Accepting options?: ErrorOptions and forwarding it to super is what preserves cause, which is how the original failure survives a wrap. It is easy to omit, and the symptom is a chain that silently stops one level down.

I would also keep the hierarchy shallow — a base class carrying a stable code, and a handful of subclasses. Handlers branch on two or three distinctions in practice, so deeper trees add naming work without adding decisions.

What has changed is that the old prototype workaround is unnecessary. Subclassing built-ins used to break instanceof under a downlevel ES5 target, so every custom error carried Object.setPrototypeOf(this, new.target.prototype). TypeScript 7 removed the ES5 target entirely — --target es5 is now TS5108, "Option 'target=ES5' has been removed" — so that line is dead code in new projects.

Mid: What is Error.cause and why is it unknown?

cause is a standard property for attaching the original failure to a wrapping error: throw new AppError("could not save user", 500, { cause: e }). It lets a layer add context without discarding the underlying error's message and stack.

It is typed unknown for the same reason the catch variable is: anything can be thrown, so anything can be a cause. I verified that reading e.cause after narrowing e to Error still gives unknown.

That means walking a chain requires narrowing at each step, which is slightly tedious and entirely correct. A small generator or a rootCause helper written once removes the repetition.

The alternative patterns are all worse: swallowing the original and throwing a fresh error loses the stack that identifies the real problem; concatenating messages into a string produces something no tool can parse; and logging at every level produces five log lines for one failure. Wrapping with cause keeps the chain intact and lets a single handler at the boundary decide what to report.

Senior: Would you adopt Result types across a codebase?

Not across a codebase — at specific layers where the failure is an expected outcome the caller must branch on. The value is real but it is local, and the cost grows with distance.

What Result genuinely fixes: exceptions are invisible in signatures. A function returning Promise<User> tells you nothing about what it can fail with, and forgetting to handle that is silent. A Result<User, NotFound | Unauthorised> is a discriminated union, so skipping the failure branch is a compile error and the possible failures are enumerated.

What it costs: no automatic propagation. TypeScript has no ? operator, so every intermediate function that cannot handle a failure unwraps and re-wraps by hand. Across a deep call stack that plumbing exceeds the logic, and since every library throws, each edge needs a conversion anyway. Teams that adopt it globally usually end up with a tryCatch wrapper around everything, which is the same exception handling with more ceremony.

Where I would use it: parsing and validation, domain operations with enumerable failure modes the UI renders differently, and any boundary whose failures are part of the contract. And I would throw for broken invariants, missing startup config, and infrastructure being down — conditions where no caller has a meaningful branch to write.

Recommendation: Result at the boundaries of the domain layer, exceptions inside it and at the infrastructure edge, one conversion point between them, and a lint rule against floating promises so the exception path is not silently dropped. Mixing deliberately is not a compromise here — it matches the two genuinely different kinds of failure.

Senior: Design error handling for a service, end to end.

I would organise it around one idea: errors accumulate context as they travel outward and are translated exactly once, at the boundary.

A shallow class hierarchy. One base AppError carrying a stable code, an HTTP status, and a flag for whether the message is safe to show a client; a handful of subclasses — NotFound, Unauthorised, ValidationError, UpstreamError. Deep hierarchies never pay off, because handlers branch on two or three distinctions in practice.

Wrap, do not swallow. Every layer that adds context rethrows with { cause: e }, so the chain from "HTTP 500 to the client" back to "connection refused on port 5432" is intact in one object. No layer logs; logging at every level produces five entries for one failure and makes the real cause harder to find.

One translation point. Error-handling middleware at the edge decides the status code, logs the full chain with a correlation id, and returns a public shape — a stable code, a safe message, the correlation id, and nothing else. Raw messages and stacks never cross that line, because they leak table names, file paths and internal structure.

Cover the async gaps explicitly, since they are where handling silently fails to apply: a lint rule for floating promises, res.ok checks because fetch resolves on a 500, and allSettled where partial failure is acceptable rather than Promise.all's first-rejection-wins.

Recommendation: shallow hierarchy with a stable code per error, wrap with cause on the way out, log and translate once at the edge, and alert on the code rather than on the message — messages get edited, codes are a contract. That gives operators something greppable and clients something stable.

5 (hard): Implement Result and show what it forces.
Solution 
type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E };

const ok  = <T,>(value: T): Result<T, never> => ({ ok: true, value });
const err = <E,>(error: E): Result<never, E> => ({ ok: false, error });

function parsePort(s: string): Result<number, "not-a-number" | "out-of-range"> {
  const n = Number(s);
  if (!Number.isInteger(n)) return err("not-a-number");
  if (n < 1 || n > 65535)   return err("out-of-range");
  return ok(n);
}

const r = parsePort(input);
r.value;                     // error: does not exist on the failure member
if (r.ok) r.value;           // ✔ number
else      r.error;           // "not-a-number" | "out-of-range"
PropertyException versionResult version
Failure modes visibleNoEnumerated in the type
Skipping the failureCompilesCompile error
Exhaustive handlingNot checkableswitch with never check

Using a literal union for E rather than Error is what makes the failure branch exhaustively checkable — adding a third failure mode then breaks every caller that switches on it, which is the behaviour worth having.

🎯 Key Takeaways

  • Anything can be thrown — strings, numbers, plain objects, undefined.
  • There is no throws clause, so a signature never describes its failures.
  • catch (e) is unknown under strict — accuracy, not pessimism.
  • A catch annotation may only be any or unknown — otherwise TS1196.
  • catch (e: any) restores the crash the check was preventing.
  • Always have a non-Error fallback; String(e) never throws.
  • instanceof fails across realms — use a discriminant field if that matters.
  • Set this.name or every stack and log line says Error.
  • TS7 removed the ES5 target (TS5108), so Object.setPrototypeOf is dead code.
  • cause is unknown — narrow at every step of a chain.
  • Wrap with { cause: e }; never swallow, never log at every level.
  • Result makes failure visible and unskippable — that is its whole advantage.
  • Result does not propagate by itself, so global adoption becomes plumbing.
  • Promise<T> says nothing about rejections.
  • fetch resolves on a 500 — check res.ok or the error path never runs.
