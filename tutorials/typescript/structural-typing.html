Structural Typing & Assignability Foundations

What you'll master: the one question the compiler keeps asking — is this assignable to that? — and the rules behind its answer; variance, and why arrays are covariant and therefore unsound in a way you can demonstrate in four lines; the difference between a function-typed property and a method, where only the property gets the strict check; excess property checks and the three ways code escapes them; how private and # fields make classes behave nominally; why a function taking fewer parameters is assignable; and where structural typing actively hurts — domain types that collapse into each other, which the branded-types lesson repairs. Prerequisites: Types, Unions & Literals.

Part 1 — The Assignability Question

Every type error in TypeScript is ultimately the same check: can a value of type S be used where type T is expected? For object types the rule is shape containment: S is assignable to T if it has, at minimum, everything T requires, with compatible types.

type T = { a: string; b: number };

{ a: "x", b: 1 }            → assignable          exactly right
{ a: "x", b: 1, c: true }   → assignable          MORE than required is fine
{ a: "x" }                  → not assignable      missing 'b'
{ a: 1,   b: 1 }            → not assignable      'a' has the wrong type
DirectionRuleIntuition
Extra propertiesAllowed (except for fresh literals — Part 3)Having more than required still satisfies the requirement
Missing propertiesRejectedThe consumer would read something that is not there
Optional in targetSource may omit itThe consumer already handles absence
Wider type in sourceRejectedstring where "a" | "b" is required could be anything
Narrower type in sourceAllowed"a" is always a valid string
🔑 Nothing declares a relationship. There is no implements requirement, no shared base class, no registration. Two types written by two teams who have never met are compatible if their shapes line up — which is what makes TypeScript describe existing JavaScript so well, and what makes UserId and OrderId interchangeable when both are string.

Part 2 — Variance, and the Unsound Array

Variance is how a type's assignability follows from its parts. If Dog extends Animal, is Dog[] assignable to Animal[]? TypeScript says yes — and that answer is unsound by design:

class Animal { name = "a" }
class Dog extends Animal { breed = "x" }

const dogs: Dog[] = [new Dog()];
const animals: Animal[] = dogs;     // ✔ allowed: arrays are COVARIANT
animals.push(new Animal());         // ✔ allowed: animals is an Animal[]

dogs[1].breed;                      // typed string … and undefined at runtime
                                    // verified with tsc 7.0.2: NO errors reported

Nothing in that program is rejected, and the last line reads a property that does not exist. A sound type system would forbid the second line, because a Dog[] is not safe to use as a thing you can push any Animal into. TypeScript accepts it because the alternative — invariant arrays — rejects an enormous amount of correct, ordinary JavaScript.

PositionVarianceMeaning
Object property, array elementCovariantDog fits where Animal is expected
Function return typeCovariantReturning something more specific is always safe
Function parameter (function-typed property)Contravariant under strictFunctionTypesA handler must accept at least what callers may pass
Method parameterBivariant, alwaysDeliberate: it keeps common JavaScript patterns working
readonly T[]Covariant, and safeNo push, so the unsound hole is closed

The method exception is the one to remember, because it is invisible in the syntax:

type FnProp   = { f: (a: Animal) => void };   // property whose type is a function
type MethodOf = { f(a: Animal): void };       // method shorthand — looks equivalent, is not

const p: FnProp   = { f: (a: Dog) => {} };
// error TS2322: Type '(a: Dog) => void' is not assignable to type '(a: Animal) => void'.
//   Property 'breed' is missing in type 'Animal' but required in type 'Dog'.

const m: MethodOf = { f(a: Dog) {} };         // NO ERROR — methods are bivariant

Verified with tsc 7.0.2: the property form is rejected and the method form is accepted, in the same file, under the same settings. strictFunctionTypes (part of strict, so on by default in TypeScript 7) applies the sound rule to function-typed properties only. Methods were exempted because arrays and the DOM are full of signatures that would otherwise become errors.

Why it matters in practice: when you want the compiler to check a callback's parameter properly, declare it as a property (onEvent: (e: Event) => void) rather than as a method (onEvent(e: Event): void). The difference is one character of syntax and a real difference in safety.

Part 3 — Excess Property Checks, and the Three Escapes

Structural typing says extra properties are fine — but a fresh object literal assigned directly to a typed target is checked for unknown properties anyway. It is a targeted defence against typos, not a change to assignability.

type Point = { x: number; y: number };

const a: Point = { x: 1, y: 2, z: 3 };
// error TS2353: Object literal may only specify known properties, and 'z' does not exist in type 'Point'.

// escape 1 — a variable: freshness is lost, structural rules apply
const obj = { x: 1, y: 2, z: 3 };
const b: Point = obj;                    // ✔ allowed

// escape 2 — satisfies keeps the check but not the target type
const c = { x: 1, y: 2 } satisfies Point;

// escape 3 — an index signature on the target invites extra keys
type Loose = { x: number; y: number; [k: string]: unknown };
const d: Loose = { x: 1, y: 2, z: 3 };   // ✔ allowed by design
CaseChecked?Why it behaves that way
Literal assigned to a typed variableYesThe literal is "fresh": the extra key is almost certainly a mistake
Literal passed directly as an argumentYesSame reasoning
Literal in a return statementYesSame reasoning
Object referenced through a variableNoFreshness is lost; plain structural assignability applies
Spread of another objectGenerally noThe result is not a fresh literal in the same sense
Target has an index signatureNoThe type explicitly says extra keys are expected

The practical consequence is that the check catches typos where you write them, and does not protect you from data. An object built at runtime, parsed from JSON, or passed through a variable can carry any number of extra properties — which is fine structurally, and is exactly why validation at boundaries is a separate concern.

Part 4 — Classes: Where TypeScript Goes Nominal

Classes are structural like everything else — until they contain a private or # field. Then two identically-shaped classes stop being interchangeable:

class P1 { private secret = 1 }
class P2 { private secret = 1 }

const p: P1 = new P2();
// error TS2322: Type 'P2' is not assignable to type 'P1'.
//   Types have separate declarations of a private property 'secret'.

Each private declaration has its own identity, so only instances of P1 (or a subclass) satisfy P1. It is the one place the language is nominal without any extra machinery, and it is why a class with private state makes a good opaque handle.

ConstructAssignabilityRuntime
Class with only public membersStructural — any matching shape worksOrdinary class
Class with private membersNominal — only that class's instancesThe field is public at runtime; private is erased
Class with # fieldsNominalGenuinely private — enforced by the runtime
implements FooOnly a check on the class declarationNothing — it is erased
abstract classCannot be instantiated; still structural for assignabilityAn ordinary class, minus the new

implements does less than people expect. It verifies that the class satisfies the interface at its declaration site and adds nothing to the type: a class that happens to match the interface is assignable whether or not it says implements. It is useful as a guard rail — the error appears on the class rather than at every call site — and useless as a way to make a type exclusive.

The "fewer parameters" rule is what makes callbacks pleasant: forEach passes three arguments and almost nobody wants all three. The void return rule is the same idea — a callback that happens to return something can be used where nothing is expected, which is why arr.forEach(x => set.add(x)) type-checks even though add returns the set.

Part 6 — When Structural Typing Hurts

type UserId  = string;
type OrderId = string;

function cancelOrder(id: OrderId) { /* … */ }

const userId: UserId = "u_123";
cancelOrder(userId);          // ✔ NO ERROR — both are just string

// same shape, different meaning: the compiler cannot tell them apart
type Meters = number;
type Feet   = number;
SymptomCauseFix
Ids of different entities mixed upBoth are string aliasesBranded types (next section of the track)
Units confused (ms vs s, meters vs feet)Both are numberBranded types, or wrapper objects

A type alias is not a new type. type UserId = string creates a name, not a distinction — and every function accepting UserId accepts any string, including an order id, a product code and a user's email. That is fine for documentation and misleading as a safety claim. Making it real needs a brand, which costs nothing at runtime and is covered in its own lesson.

Interview Questions

Beginner: What does it mean that TypeScript is structurally typed?

Compatibility is decided by shape rather than by name or declared relationship. A value is assignable to a type if it has at least the required members with compatible types — no implements, no shared base class, no registration needed.

So a class Cat with a bark() method satisfies a Dog type that only requires bark(), and an object literal with extra properties satisfies a narrower type, because having more than required is still enough.

This models JavaScript honestly: real code passes objects around by shape, and library authors cannot require consumers to implement their interfaces. It is also what lets TypeScript describe existing JavaScript libraries from the outside, with declaration files.

The cost is that meaning is not part of the type. Two aliases of string — a user id and an order id — are the same type, so nothing stops you passing one where the other is expected. That is the case for branded types, and it is a deliberate addition rather than something the language gives you.

Beginner: Why does assigning an object literal with an extra property fail, when the same object in a variable succeeds?

Because of the excess property check, which applies only to fresh object literals. When you write a literal directly in an assignment, an argument or a return, TypeScript assumes an unknown property is a mistake — a misspelled name, or a field the target type does not support — and reports TS2353.

Once the object is stored in a variable, its "freshness" is gone. From then on the ordinary structural rule applies: the object has at least what the target requires, so it is assignable, extra properties and all.

The asymmetry is deliberate. Structural typing must allow extra properties, or composition would break everywhere; but the most common reason to write an unknown key inline is a typo, so that one case gets a special check.

Practically it means the check helps while you are writing literals and does nothing for data arriving at runtime — another reason boundary validation is a separate job from typing.

Mid: Are TypeScript's arrays sound? Show why or why not.

They are not, and it takes four lines to show:

class Animal { name = "a" }
class Dog extends Animal { breed = "x" }
const dogs: Dog[] = [new Dog()];
const animals: Animal[] = dogs;     // allowed: arrays are covariant
animals.push(new Animal());         // allowed: animals is an Animal[]
dogs[1].breed;                      // typed string, undefined at runtime

Every line type-checks, and the last one reads a property that does not exist. The unsoundness comes from treating Dog[] as assignable to Animal[] while arrays are mutable: reading is safe, but writing through the wider view corrupts the narrower one.

TypeScript chose this deliberately. Invariant arrays would reject a great deal of correct code — passing a Dog[] to a function that only reads Animals is overwhelmingly the common case — so the design accepts a hole in exchange for usability.

The defence is readonly T[]: it is covariant and safe, because there is no push to exploit. Taking readonly arrays in parameters you do not mutate is the habit that closes this in your own code, and it documents intent at the same time.

Mid: What is the difference between declaring a callback as a method and as a property?

Variance, and therefore how strictly the compiler checks it.

With strictFunctionTypes — part of strict, so on by default in TypeScript 7 — function-typed properties have their parameters checked contravariantly, which is the sound rule: a handler must accept at least everything callers might pass. Assigning (a: Dog) => void where (a: Animal) => void is expected is correctly rejected.

Method declarations — f(a: Animal): void — are exempt, and their parameters are compared bivariantly. The identical assignment is accepted. I verified both in one file: the property form errors with TS2322 and the method form does not.

The exemption exists for compatibility. A great deal of JavaScript, including array methods and DOM interfaces, relies on patterns that the sound rule would reject, and making methods strict would have made the flag unadoptable.

The practical takeaway: if you want the compiler's help on a callback's parameter type, declare it as a property. It is a one-character difference in the type, and it decides whether a whole class of mistakes is caught.

Senior: Two teams' identically-shaped types keep getting mixed up. What do you do?

First establish whether it is a real defect or aesthetic discomfort, because structural compatibility is usually a feature. The question is whether substituting one for the other can actually cause harm: a UserId passed to cancelOrder, a value in milliseconds treated as seconds, an unvalidated string used where a validated one is required. If harm is possible, the types should be distinguishable; if not, leave them alone.

The lightest fix is a brand: intersect the primitive with a phantom property that exists only in the type, so the two aliases stop being interchangeable while remaining plain strings at runtime. Values enter the branded type only through a function that validates, which means the type itself proves the check ran — that is the pattern the branded-types lesson builds.

For object types, a discriminant is often better: adding a literal kind field makes the types genuinely different, improves error messages, and enables discriminated-union narrowing elsewhere.

For classes, private state does it automatically — two classes with separate private declarations are not assignable to each other, which is the one place TypeScript is nominal without extra work.

Recommendation: brand the identifiers and units where mixing them is a real bug, add discriminants to DTOs that travel together, and resist branding everything — each brand adds friction at every boundary, and a codebase where every string is branded spends its time converting rather than computing.

Senior: How would you explain TypeScript's soundness trade-offs to a team coming from a stricter language?

I would frame it as a deliberate engineering choice rather than a set of bugs, and be precise about where the holes are, because the holes are learnable and the benefit is large.

TypeScript's job is to describe JavaScript as it is already written — a language with no types at runtime, enormous existing libraries, and idioms that a sound system would reject. A sound type system for that language would either reject a lot of correct code or require pervasive annotation, and in either case nobody would have adopted it. The team's existing intuition that "the type checker proves the program correct" simply does not transfer.

The specific holes worth teaching on day one: any disables checking and spreads; type assertions assert without verifying; arrays and object properties are covariant, so mutation through a wider view is unchecked; method parameters are bivariant; index access returns the element type even when the element is missing; and anything crossing a runtime boundary is unverified.

The corresponding defences: strict (already the default in TypeScript 7), noUncheckedIndexedAccess, readonly parameters, function-typed properties for callbacks, lint rules against any and bare assertions, and schema validation at every boundary.

Recommendation: set the flags, write the boundary validation, and teach the holes explicitly in onboarding — a team that knows exactly what the checker does not prove writes better code than one that either trusts it completely or dismisses it.

6 (hard): Audit an API surface for accidental compatibility.
Solution 
// the surface as written
type UserId    = string;
type OrderId   = string;
type Email     = string;
type Timestamp = number;   // milliseconds? seconds?
type Amount    = number;   // major units? minor units?

export function refund(order: OrderId, amount: Amount, at: Timestamp): void;
RiskCan it actually happen?Action
UserId passed as OrderIdYes — both strings, both in scope at call sitesBrand both
Email passed as an idYesBrand, and parse into it during validation
Seconds passed as millisecondsYes, and silently wrong by 1000×Brand, or take a Date
Major units passed as minorYes — the classic money bugBrand, or a Money object with a currency

// after: same runtime representation, distinct types
declare const brand: unique symbol;
type Brand<T, B> = T & { readonly [brand]: B };

type UserId    = Brand<string, "UserId">;
type OrderId   = Brand<string, "OrderId">;
type Millis    = Brand<number, "Millis">;
type Cents     = Brand<number, "Cents">;

export function refund(order: OrderId, amount: Cents, at: Millis): void;
refund(userId, 500 as Cents, Date.now() as Millis);   // error: UserId is not OrderId ✔

Brand where a mix-up is plausible and harmful — identifiers, units, money, validated strings — and not everywhere. The cost is a conversion at each boundary, which is exactly where you want it: the brand is created once, by the code that checked the value, and carried thereafter.

🎯 Key Takeaways

  • Every type error is one question: is the source assignable to the target?
  • Object types need at least the required members; extra ones are fine except on fresh literals.
  • Arrays and object properties are covariant, and therefore unsound — mutation through a wider view type-checks.
  • readonly T[] is covariant and safe, which makes it the right parameter type when you only read.
  • Function-typed properties get contravariant parameter checks under strictFunctionTypes; methods stay bivariant.
  • Declare callbacks as properties when you want that check to apply.
  • Excess property checks apply to fresh literals only — a variable, a spread or an index signature escapes them.
  • Classes are structural until they hold private or # state, which makes them nominal.
  • implements checks the class and changes nothing about the type.
  • private is erased at runtime; # is genuinely private.
  • A function with fewer parameters is assignable, which is why callbacks can ignore arguments.
  • A function returning a value is assignable where void is expected.
  • A type alias is a name, not a new type: UserId and OrderId are both string.
  • Brand the types where a mix-up is plausible and harmful, and only those.
  • Read confusing errors by direction — usually the callback demands more than the contract promises.
