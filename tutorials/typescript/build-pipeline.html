Build Pipeline Modules, Config & Build

What you'll master: the split that every modern setup uses — a transpiler emits the JavaScript, tsc --noEmit checks the types — and why it is safe only when you understand what each half does; direct proof that a transpiler does no checking, since esbuild compiles const n: number = "not a number" and exits 0; the place the two genuinely disagree, where mixing their output for a const enum produces a runtime SyntaxError, demonstrated end to end; erasableSyntaxOnly and TS1294 as the guard against that whole class of problem; incremental and --build modes; and reading --diagnostics instead of guessing why a build is slow. Prerequisites: Declaration Files.

Part 1 — Two Jobs, Two Tools

Compiling TypeScript is two separable jobs: removing the types, and checking them. Only the first is needed to produce runnable code.

JobNeedsTools
Strip types, downlevel syntaxOne file at a timeesbuild, SWC, Babel, Vite, tsc
Check typesThe whole programtsc only
Emit .d.tsThe whole program, or isolatedDeclarationstsc, or a tool under that flag
BundleThe module graphesbuild, Rollup, Vite, webpack

Splitting them is what makes a modern dev server fast: the transpiler rebuilds one changed file in milliseconds, and the checker runs separately, in the editor and in CI. TypeScript 7's native compiler makes tsc itself far faster than it was, but the split remains the norm because bundling and transpiling belong together.

🔑 isolatedModules and verbatimModuleSyntax exist to make this split safe, as lessons 14 and 16 showed. They forbid exactly the constructs a single-file tool cannot handle, so the flags are not bureaucracy — they are the contract between your source and the transpiler.

Part 2 — A Transpiler Checks Nothing

This is worth seeing rather than being told, because it is the assumption that makes pipelines unsafe.

// broke.ts
const n: number = "definitely not a number";
export const out = n;

$ npx esbuild broke.ts                      ◄── verified
const n = "definitely not a number";
export const out = n;
$ echo $?
0

$ npx tsc broke.ts --noEmit
broke.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.

esbuild removed the annotation and emitted the string, successfully. It is not being lax — it was never asked to check anything, and it has no type-checker to do it with. A pipeline whose only TypeScript step is a transpiler has no type safety at all, however strict the tsconfig.json says it is.

SetupTypes checked?
Vite / esbuild dev server aloneNo
Editor with the TS language serviceYes, for open files
tsc --noEmit in CIYes, whole program
tsc as the only build stepYes
A pre-commit hook running tsc --noEmitYes, if it is not skipped

The editor is not a substitute for CI. The language service checks the files you have open and their dependencies, not the program — so a change that breaks a module nobody opened is invisible until something checks everything.

Part 3 — Where tsc and a Transpiler Disagree

Both tools handle enums and namespaces, contrary to folklore — esbuild emits a real runtime object for each. The genuine problem is that they emit different code for a const enum:

// ce.ts
export const enum E { A = 1 }
// ceuse.ts
import { E } from "./ce.js";
export const v = E.A;

// tsc output — verified
ce.js:     export {};                       ◄── the enum is erased entirely
ceuse.js:  export const v = 1 /* E.A */;    ◄── the value is inlined

// esbuild output — verified
ce.js:     var E = ((E2) => { E2[E2["A"] = 1] = "A"; return E2; })(E || {});
           export { E };                    ◄── a real runtime object
ceuse.js:  import { E } from "./ce.js";
           const v = E.A;                   ◄── a real runtime import

Each output runs correctly on its own — both print 1. The failure appears when the two are mixed, which is exactly what happens when one part of a build uses tsc and another uses a transpiler:

// tsc's ce.js + esbuild's ceuse.js, run under Node
SyntaxError: The requested module './ce.js' does not provide an export named 'E'
                                        ◄── verified
ConstructtscesbuildMixed
enumRuntime objectRuntime objectCompatible
const enumInlined; module erasedRuntime objectBreaks
namespaceRuntime objectRuntime objectCompatible
Declaration mergingUnderstoodNot modelledRisky
Parameter propertiesEmittedEmittedCompatible

The flag that removes the whole category is erasableSyntaxOnly:

$ npx tsc en.ts --noEmit --erasableSyntaxOnly
en.ts(1,6):  error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
en.ts(3,11): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
                                        ◄── verified: the enum and the namespace

Under it, every TypeScript-specific construct that emits runtime code is an error, so the source contains nothing the two tools could disagree about. The cost is giving up enums, namespaces and parameter properties; the benefit is that the transpiler's output and tsc's output are necessarily the same. For a new project that is a good trade — a union of string literals does what an enum does, with better narrowing.

Part 4 — Incremental and --build

$ npx tsc --noEmit                  // full check
$ npx tsc --noEmit --incremental    // writes .tsbuildinfo; later runs reuse it
$ npx tsc --watch                   // rechecks on change, in-process
$ npx tsc --build                   // honours project references (lesson 14)
$ npx tsc --build --watch
$ npx tsc --build --force           // ignore all caches
ModeReuses work?Use for
Plain tscNoCI, one-shot checks
--incrementalVia .tsbuildinfoLocal rebuilds, warm CI caches
--watchIn memoryDevelopment
--buildPer referenced projectMonorepos
--build --forceNoDiagnosing a stale cache

.tsbuildinfo must be treated as a build artefact: it belongs in .gitignore, and it should be keyed to the compiler version and config in any CI cache. A .tsbuildinfo written by a different compiler version or a different tsconfig is the usual cause of "it passes locally and fails in CI", and --build --force is how you confirm that diagnosis in one command.

Instantiations is the number to watch, because it is the one that grows non-linearly. A deep conditional type applied across a large union, as lesson 7 described, multiplies — so a helper that was cheap when a union had five members can dominate the build when it has fifty, with no change to the code. --generateTrace produces a profile naming the specific types responsible.

❌ Concluding "TypeScript is slow" and reaching for a faster transpiler. The transpiler was almost certainly never the slow part — it does no checking, which is why it is fast. Replacing tsc's emit with esbuild makes the build feel faster while moving the type-check somewhere else, and if that somewhere else is "the editor only", the project has traded build time for undetected errors rather than fixing anything.

✅ Run --diagnostics first and let the numbers say what to do. A high Files count is a configuration problem — include picking up dist, or every transitive @types loading because types is unset. A high Instantiations count is one or two expensive type helpers, findable with --generateTrace. A genuinely large program is what project references are for. Each of those has a different fix, and only measuring distinguishes them.

Part 6 — A Pipeline That Holds

{

    "dev":        "vite",
    "build":      "tsc --noEmit && vite build",
    "typecheck":  "tsc --noEmit",
    "typecheck:watch": "tsc --noEmit --watch",
    "build:types": "tsc -p tsconfig.build.json"
  }
}
StageRunsBlocks on failure?
EditorLanguage serviceNo — advisory
Dev serverTranspile onlyNo — keep it fast
Pre-committsc --noEmit (changed projects)Yes, if cheap enough
CItsc --noEmit, whole programYes — the real gate
Releasetsc -p tsconfig.build.json for .d.tsYes, with noEmitOnError

The single rule that makes the split safe is that tsc --noEmit is a required CI check. Everything else is an optimisation: the dev server can skip checking, the pre-commit hook can be scoped or skipped, the editor can lag. If CI does not check the whole program with the same config the editor uses, then nothing does, and the type system becomes documentation.

Interview Questions

Beginner: Why do projects use esbuild or SWC alongside tsc?

Because compiling TypeScript is two separate jobs and only one of them needs the type-checker. Removing type annotations is a per-file text transformation; checking types requires understanding the whole program.

A transpiler does the first job extremely quickly precisely because it skips the second. That is what makes a dev server rebuild a changed file in milliseconds, and it is why the bundler and the transpiler are usually the same tool — they both need the module graph, not the type graph.

tsc then runs separately as tsc --noEmit, checking everything and emitting nothing. In TypeScript 7 the native compiler makes that much faster than it used to be, but the split is still the norm because bundling and transpiling belong together.

The essential consequence is that the transpiler provides no safety whatsoever. If tsc --noEmit is not running somewhere that blocks a merge, the project has strict settings and no checking.

Beginner: What does tsc --noEmit do, and where should it run?

It type-checks the whole program and produces no output files. It is the checking half of the compiler, used when something else is responsible for emitting JavaScript.

It should run in CI as a check that blocks merging, over the whole program, with the same configuration the editor uses. That last part matters: a separate stricter CI config produces errors that authors never saw while writing the code, which is the worst time to find them.

The editor is not a substitute. The language service checks open files and their dependencies, so a change that breaks a module nobody has open is invisible. Neither is the dev server, which typically only transpiles — I verified that esbuild compiles const n: number = "definitely not a number" and exits 0.

A watch-mode check (tsc --noEmit --watch) running beside the dev server is a good addition locally, and a pre-commit hook is reasonable if it is fast enough not to be routinely skipped. But CI is the gate that actually has to hold.

Mid: Where do tsc and a transpiler actually produce different output?

The commonly repeated answer — that transpilers cannot handle enums and namespaces — is wrong. I checked: esbuild emits a real runtime object for both, essentially the same shape tsc does.

The real divergence is const enum. tsc inlines its values and erases the module entirely — the emitted ce.js was literally export {}, and the consumer became export const v = 1. esbuild instead emits a runtime enum object and keeps the import.

Each output works on its own; mixing them does not. Combining tsc's output for the enum module with esbuild's output for the consumer gives SyntaxError: The requested module './ce.js' does not provide an export named 'E' at run time — verified. That is a realistic scenario whenever one part of a build is compiled by tsc and another by a bundler, which is common in monorepos consuming locally-built packages.

The clean answer is erasableSyntaxOnly, which makes every construct that emits runtime code an error — TS1294 for both an enum and a namespace. Then the source contains nothing the tools could disagree about. Losing enums costs little, since a union of string literals narrows better anyway.

Mid: How do you diagnose a slow TypeScript build?

By measuring before changing anything, because the plausible causes need completely different fixes and guessing usually lands on the transpiler, which was never the slow part.

tsc --noEmit --diagnostics is the first command. It reports file, symbol and type counts, instantiations, memory, and parse, bind and check times separately. Those numbers partition the problem immediately: high Files is a configuration issue, high Check time with high Instantiations is expensive type-level code, and high parse time with a reasonable check time is simply a large program.

Instantiations is the one I watch, because it grows non-linearly. A conditional type distributed over a union costs one instantiation per member, so a helper that was free when a union had five members can dominate when it has fifty — with no change to the code that uses it. --generateTrace gives a profile naming the specific types.

The configuration causes are worth ruling out first because they are nearly free to fix: include accidentally matching dist or generated files, types left unset so every transitive @types package loads, and skipLibCheck off so every dependency's declarations are checked.

Only then would I restructure — project references so rebuilds are proportional to the change, or splitting emit from checking. And I would set a diagnostics budget in CI afterwards, because without one the gain erodes over the next year.

Senior: Design the build and check pipeline for a large application.

The organising principle is that fast feedback and authoritative checking are different jobs, and trying to get both from one step makes both worse.

The dev server transpiles only. esbuild or SWC through Vite, no type-checking in the hot path, so a save-to-refresh cycle stays in the tens of milliseconds. Correctness comes from the editor's language service and a separate tsc --noEmit --watch process, which developers can watch without it blocking anything.

CI is the gate, and it checks the whole program with the same config. tsc --noEmit as a required status check, using the config the editor uses — extended, not replaced. A stricter CI-only config means authors meet errors long after writing the code, which is the expensive time to find them.

Make the split structurally safe rather than relying on discipline. isolatedModules, verbatimModuleSyntax and erasableSyntaxOnly together guarantee the source contains nothing a single-file tool can misinterpret — which is what prevents the const enum class of bug, where two tools emit incompatible code for the same input and the failure is a runtime SyntaxError in a bundle.

For a monorepo, project references and tsc --build, so a check is proportional to what changed and cross-package imports are validated against declared dependencies. Cache .tsbuildinfo in CI keyed on the compiler version and config hash — an unkeyed cache is the classic cause of a green local build and a red CI one.

Recommendation: transpile for speed, tsc --noEmit in CI as the only authority, one shared config, the erasability flags on, project references in a monorepo, and a --diagnostics budget checked in CI so regressions are caught by a build rather than by someone's patience.

Senior: A bundle throws SyntaxError: does not provide an export named 'E' in production only. How do you approach it?

I would read it as a build-output mismatch rather than a source bug, because that specific error means one module was compiled expecting an export that the other module's compiler chose not to emit.

The likely cause is two emitters on one graph. A const enum is the textbook case: tsc inlines its values and erases the module — I verified output where ce.js was just export {} — while esbuild emits a real enum object and a runtime import. Each is internally consistent; combining them produces exactly this SyntaxError.

Why production only: the dev server usually transpiles everything with one tool, so the two halves agree. The production build is where a locally-built package compiled by tsc, or a pre-built dist from a workspace dependency, gets combined with application code compiled by the bundler. The difference is which tool touched which file, not the environment.

How I would confirm it in minutes: look at the emitted module named in the error. If the export genuinely is not there, the question is only which tool produced that file and which produced the importer. Checking whether the identifier is a const enum, a type-only export, or a namespace usually ends the investigation immediately.

Recommendation: fix the immediate case by removing the const enum — a literal union is better anyway — then prevent the class by turning on erasableSyntaxOnly, which makes any construct with runtime emit an error (TS1294), and by ensuring a single emitter owns each file. And add a smoke test that imports the production bundle's entry point in Node, since every one of these is caught by actually loading the built artefact once.

🎯 Key Takeaways

  • Transpiling and type-checking are separate jobs; only checking needs the whole program.
  • A transpiler checks nothing — esbuild compiled const n: number = "…" and exited 0.
  • If tsc --noEmit does not run in CI, nothing checks your types.
  • The editor only checks open files and their imports — not a substitute for CI.
  • esbuild does compile enums and namespaces — that folklore is wrong.
  • const enum is the real divergence: tsc inlines and erases, esbuild keeps a runtime object.
  • Mixing the two emitters gives a runtime SyntaxError about a missing export.
  • erasableSyntaxOnly removes the whole class — TS1294 on anything with runtime emit.
  • A literal union beats an enum anyway — better narrowing, no runtime object.
  • .tsbuildinfo is a build artefact — gitignore it, key CI caches on version and config.
  • tsc --build honours project references; plain tsc ignores them.
  • Measure with --diagnostics before changing anything.
  • Instantiations grows non-linearly — it is the number that signals expensive types.
  • A high Files count is usually configuration — include, types, skipLibCheck.
  • One config, extended for builds, so editor, CI and release never disagree.
