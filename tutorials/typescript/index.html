What TypeScript Actually Is Foundations

What you'll master: that TypeScript is a type layer erased before your code runs — and the three pieces of syntax that are not erased, which is why Node's type stripping rejects them; structural typing, and why a Cat is assignable to a Dog; the excess property check that fires on a literal but not on a variable; the places the compiler is deliberately unsound, including arr[10] typed as string on a one-element array; why your bundler does not type-check and CI must run the compiler itself; and what changed in TypeScript 7 — a native compiler, strict on by default, and a far stricter tsc --init. Prerequisites: working JavaScript, ideally the JavaScript track.

Part 1 — A Type Layer That Disappears

TypeScript adds types to JavaScript, checks them, and then throws them away. The output is JavaScript with the annotations removed; nothing about your types exists while the program runs.

// input.ts
type User = { id: string; name: string };
interface Repo { get(id: string): User }
const u: User = { id: "1", name: "a" };
export { u };

// emitted JavaScript — verified with tsc 7.0.2
const u = { id: "1", name: "a" };
export { u };
You wroteAt runtime it is
type and interface declarationsNothing — they vanish entirely
: User annotations, generics, as assertionsNothing
satisfies, implementsNothing (implements is a check, not behaviour)
Everything elseOrdinary JavaScript
🔑 Every consequence in this track follows from erasure. You cannot test a type at runtime, so typeof and instanceof — not your annotations — are what narrow a value. Data arriving from a network, a file or a database is unchecked: annotating a fetch result as User asserts a belief and verifies nothing. And a type error is a message from a tool you must actually run; it cannot stop a deployment by itself.

Part 2 — The Three Things That Are Not Erasable

Most TypeScript syntax is annotation. Three constructs are not: they generate JavaScript, which makes them different in kind from the rest of the language.

enum Color { Red, Green }              // emits an object
namespace Legacy { export const x = 1 } // emits an IIFE
class P { constructor(private readonly n: number) {} }   // parameter property: emits an assignment

// emitted JavaScript — verified with tsc 7.0.2
var Color;
(function (Color) {
    Color[Color["Red"] = 0] = "Red";
    Color[Color["Green"] = 1] = "Green";
})(Color || (Color = {}));
var Legacy;
(function (Legacy) { Legacy.x = 1; })(Legacy || (Legacy = {}));
class P {
    n;
    constructor(n) { this.n = n; }     // the parameter property became real code
}

This matters because of how modern runtimes handle TypeScript. Node can strip types — remove the annotations and run the result — which is fast and needs no build step, but it can only remove what is erasable. TypeScript provides a flag that rejects anything else:

$ tsc app.ts --erasableSyntaxOnly --noEmit
app.ts(3,6):  error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.   ← enum
app.ts(4,11): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.   ← namespace
app.ts(5,23): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.   ← parameter property
Instead ofUseWhy
enum Color { Red, Green }const Color = { Red: "Red", Green: "Green" } as const plus a union typeErasable, tree-shakeable, and the values are what you actually wrote
namespaceES modulesNamespaces predate modules and are legacy in new code
Parameter propertiesAn explicit field and assignmentErasable, and obvious to a reader

Part 3 — Structural Typing: Shape, Not Name

TypeScript compares types by shape, not by declared name. If a value has the required members, it is assignable — whatever it was declared as.

class Dog { bark() {} }
class Cat { bark() {} }
const d: Dog = new Cat();     // NO ERROR: same shape, so a Cat is a Dog

That is deliberate: it models how JavaScript is actually written, where objects are passed around by shape and nobody implements an interface formally. It also means a type is a constraint on shape rather than a club with a membership list — and that two unrelated domain types with the same fields (UserId and OrderId, both string) are interchangeable, which the branded-types lesson fixes deliberately.

The excess property check is the exception people trip over. Object literals assigned directly are checked for unknown properties; the same object through a variable is not:

type Point = { x: number; y: number };

const literal: Point = { x: 1, y: 2, z: 3 };
// error TS2353: Object literal may only specify known properties, and 'z' does not exist in type 'Point'.

const obj = { x: 1, y: 2, z: 3 };
const viaVar: Point = obj;      // ALLOWED — obj has at least x and y, which is all Point requires
SituationChecked for extra properties?
Object literal assigned to a typed targetYes — a freshness check, to catch typos
Literal passed directly as an argumentYes
A variable holding the same objectNo — plain structural assignability
Result of a function returning a wider typeNo

Part 4 — Where the Compiler Is Deliberately Unsound

TypeScript is not a proof system; it trades some soundness for practicality. Knowing exactly where is what separates "the types pass" from "the code is correct".

anyOne any flows through a whole call chain uncheckedunknown plus narrowing; lint against any
Type assertionsvalue as User asserts without checking anythingValidation at boundaries; treat as as a claim you must justify
Index accessarr[10] on a one-element array is typed stringnoUncheckedIndexedAccess
JSON.parseReturns any: whatever you annotate is believedParse with a schema validator

const arr: string[] = ["a"];
const s: string = arr[10];     // no error by default — the type says string, the value is undefined
s.toUpperCase();               // TypeError at runtime

$ tsc checks.ts --noUncheckedIndexedAccess --noEmit
error TS2322: Type 'string | undefined' is not assignable to type 'string'.   ← now it is visible

These are choices, not bugs. Unchecked index access, for instance, would force a null check on every array read; TypeScript's designers judged that too noisy for the default. The flag exists precisely so a team can decide for itself — which is the theme of the strictness lesson.

Part 5 — Your Build Probably Does Not Type-Check

Modern toolchains separate transpiling (strip the types, emit JavaScript — fast) from type-checking (prove the program is consistent — slower). Most bundlers do only the first.

ToolRemoves typesChecks types
tscYesYes
esbuild, swc, Vite, BunYesNo
Babel (preset-typescript)YesNo
Node's type strippingYes (erasable syntax only)No
Your editor—Yes, for open files

❌ Assuming a green build means the types pass. The bundler strips annotations without reading them, so a project can accumulate hundreds of type errors while every build succeeds and every deploy goes out. The errors appear only in the editors of whoever happens to open the file — and get worse, because nothing fails.

✅ Run the compiler in CI as its own step: tsc --noEmit, failing the build on any error. It is the only thing that checks the whole project, and it is why the build pipeline lesson treats type-checking and bundling as two separate jobs.

TypeScript 7 changed the economics of that check. The compiler was rewritten as a native binary rather than JavaScript, and the npm package ships a per-platform executable — installing it pulls @typescript/typescript-linux-x64, -darwin-arm64, -win32-x64 and so on. Type-checking that was slow enough to be skipped in a watch loop is much less painful, which removes the main excuse for not running it.

Part 6 — What TypeScript 7 Changed by Default

Almost every tutorial you will find online describes TypeScript 5.x defaults. Two of them are now different, and both matter on day one.

// defaults.ts, compiled with NO tsconfig and NO flags — tsc 7.0.2
const a: string = null;          // error TS2322: Type 'null' is not assignable to type 'string'
let b;  b.foo();                 // error TS18048: 'b' is possibly 'undefined'
function f(p) { return p; }      // error TS7006: Parameter 'p' implicitly has an 'any' type

$ tsc defaults.ts --strict false --noEmit
(no errors)                      ← strict is ON by default; you now opt OUT, not in

$ tsc --init      # the generated tsconfig.json, trimmed
{
  "compilerOptions": {
    "module": "nodenext",          "target": "esnext",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "verbatimModuleSyntax": true,  "isolatedModules": true,
    "moduleDetection": "force",    "skipLibCheck": true,
    "declaration": true,           "declarationMap": true,  "sourceMap": true

Interview Questions

Beginner: What does TypeScript actually do to your code?

It checks the annotations you wrote and then removes them. The emitted JavaScript contains none of the types: type and interface declarations, annotations, generics and assertions all disappear, leaving ordinary JavaScript.

That single fact explains most of TypeScript's behaviour. You cannot ask at runtime whether a value is a User, because User does not exist then — narrowing has to use JavaScript's own operators, typeof, instanceof and property checks. Data crossing a boundary is unchecked, so annotating a parsed JSON response is a claim rather than a verification. And type errors only stop something if a tool is run that reads them.

There are three exceptions that do emit code — enum, namespace and constructor parameter properties — which is why runtimes that strip types reject them, and why erasableSyntaxOnly exists to keep a codebase free of them.

So the honest summary is that TypeScript is a static analysis tool with a very good editor experience, not a runtime type system.

Beginner: What is structural typing?

Types are compared by shape rather than by name. A value is assignable to a type if it has the required members with compatible types, regardless of what it was declared as or which interface it claims to implement.

So a class Cat with a bark() method is assignable to Dog if Dog only requires bark(). Nothing needs to declare a relationship, which matches how JavaScript is written — objects are passed around by shape.

The practical consequences are worth knowing. Two domain types that happen to share a shape are interchangeable, so a UserId and an OrderId that are both string can be mixed up freely; branded types exist to reintroduce that distinction deliberately. And extra properties are generally fine, because having more than required still satisfies the shape.

The exception is the excess property check: an object literal assigned directly to a typed target is checked for unknown properties, to catch typos. The same object referenced through a variable is not — which surprises people until they know the rule.

Mid: Where is TypeScript deliberately unsound, and why?

Several places, each a trade of soundness for practicality.

any switches checking off for everything it touches, and it spreads through call chains silently. Type assertions (value as User) assert without verifying — useful when you know something the compiler cannot, dangerous as an error-silencer. Index access is the one that surprises people most: arr[10] on an array of one element is typed as the element type, not T | undefined, so a perfectly typed program can throw on the next line.

JSON.parse returns any, so any annotation on the result is believed without checking. And method parameters are compared bivariantly rather than contravariantly, for compatibility with common JavaScript patterns — strictFunctionTypes tightens function-typed properties but deliberately leaves methods alone.

The reasoning in each case is ergonomic: fully sound rules would force null checks on every array read and reject idiomatic patterns that are fine in practice. TypeScript's designers chose a type system people will actually adopt over one that is provably correct.

What matters professionally is knowing which of these your codebase has opted out of. noUncheckedIndexedAccess closes the array hole, runtime validation closes the boundary hole, and lint rules close the any hole — but each has a cost, and the choices should be deliberate.

Mid: A project's build is green but the editor shows type errors. How is that possible?

Because the build almost certainly does not type-check. Modern bundlers — esbuild, swc, Vite, Bun, Babel — strip the annotations to produce JavaScript without ever reading them. That is why they are fast, and it means a project can accumulate any number of type errors while every build and deploy succeeds.

The editor, meanwhile, runs the TypeScript language service over the files that are open, which is how the errors are visible there and nowhere else. Nobody sees the errors in files they do not open.

The fix is a dedicated step: tsc --noEmit over the whole project, in CI, failing the build on any error. It checks everything, including files nobody has opened in months, and it is the only place the guarantee actually exists.

This is also why TypeScript 7's native compiler matters operationally rather than just aesthetically: when the full-project check is fast, teams stop treating it as an optional slow job — which was the usual reason the check drifted away from the build in the first place.

Senior: A team says "we have TypeScript, so we don't need runtime validation". Respond.

I would agree with the half that is true and be specific about the half that is not. TypeScript guarantees that the code is internally consistent with the types written in it. It guarantees nothing about values that enter the process from outside, because by then the types no longer exist.

Concretely: JSON.parse returns any; fetch gives you a body you annotate rather than verify; environment variables are strings the compiler never sees; a database driver hands back rows shaped by whatever the schema is today. In each case, annotating the result is a claim, and if the claim is wrong the failure surfaces later and somewhere else — a TypeError deep in a call chain, or bad data written to storage.

So the rule I would set is: parse at the boundary, trust inside it. Every external input is validated once with a schema validator that produces a typed value, and from that point the static types are meaningful because something checked them. Inside the boundary, no further validation — that is what the type system is for.

I would also name the cost honestly, because the team is reacting to something real: schemas are extra code, they can drift from the types, and validation costs a little at runtime. Deriving the type from the schema rather than writing both is what keeps them in step, and it turns the schema into the single definition rather than a duplicate.

Recommendation: validators at every external boundary with types inferred from the schemas, tsc --noEmit in CI, and a lint rule against bare as on external data — so the boundary is the only place that needs discipline.

Senior: How would you decide whether adopting TypeScript is worth it for an existing JavaScript codebase?

By asking what problem it is expected to solve, and whether the codebase's shape lets it deliver.

Where it pays: code with many collaborators and long life, where the types serve as always-current documentation and refactoring becomes mechanical; data-heavy code where shapes flow through many layers; public APIs and shared libraries, where consumers get the contract in their editor. The refactoring argument is usually the strongest: renaming a field across 400 files is a compiler-guided operation rather than a search.

Where it pays less: small scripts, short-lived code, and teams that will adopt the syntax without the discipline — a codebase full of any and assertions carries the cost and none of the benefit.

The costs to state plainly: a build or type-check step in CI; a learning curve that is real for generics and conditional types; type definitions for dependencies that lack them; and an initial period where the error count is large. Migration is incremental — allowJs, file-by-file conversion, strictness raised as a ratchet — which the migration lesson covers, so it need not be a project-wide stop.

Recommendation: adopt it for anything that several people will maintain for more than a year, migrate incrementally with a strictness ratchet so the codebase cannot get worse, and commit to tsc --noEmit in CI from the first day — because a TypeScript codebase nobody type-checks is strictly worse than JavaScript: the same safety, plus a build step and false confidence.

3 (medium): Find an unsound spot and close it.
Solution 
const arr: string[] = ["a"];

const s = arr[10];              // string | undefined
if (s !== undefined) console.log(s.toUpperCase());
// or
const s2 = arr.at(10) ?? "fallback";

5 (hard): Show that an annotation is a claim, not a check.
Solution 
type User = { id: string; email: string };

const res = await fetch("/api/user");
const user: User = await res.json();      // res.json() is Promise<any>: the annotation is believed
console.log(user.email.toLowerCase());

the API actually returns: { "id": "1", "email": null }

$ npx tsc api.ts --noEmit
(no errors)                                ← nothing checked the response

at runtime:
TypeError: Cannot read properties of null (reading 'toLowerCase')

The fix is to parse rather than assert, deriving the type from the schema so the two cannot drift:

import { z } from "zod";

const User = z.object({ id: z.string(), email: z.string() });
type User = z.infer<typeof User>;          // the type comes FROM the schema

const user = User.parse(await res.json()); // throws here, at the boundary, with a precise message
console.log(user.email.toLowerCase());     // now the static type is backed by a runtime check
ApproachFailure appearsDiagnosis
Annotation (as or : User)Later, wherever the bad value is usedA TypeError far from the cause
Schema parseAt the boundary, immediatelyNames the field and what was wrong

This is the single most valuable habit in a TypeScript codebase, and the runtime-validation lesson builds it out: every external input — HTTP, queues, files, environment variables, database rows — is parsed once, and the rest of the program can then trust its types.

🎯 Key Takeaways

  • TypeScript is erased before the code runs; no annotation exists at runtime.
  • Narrowing uses JavaScript's own operators — typeof, instanceof, property checks — because types are gone.
  • enum, namespace and parameter properties emit real code, which is why type-stripping runtimes reject them.
  • erasableSyntaxOnly enforces a fully erasable codebase (TS1294 on the three exceptions).
  • Typing is structural: a same-shaped Cat is assignable to Dog, and same-shaped domain types are interchangeable.
  • Excess property checks fire on object literals, not on variables — a freshness rule for catching typos.
  • arr[10] is typed as the element type unless noUncheckedIndexedAccess is on.
  • any, assertions and JSON.parse are the main soundness holes; each is a deliberate trade.
  • An annotation on external data is a claim, not a check.
  • Bundlers strip types without reading them, so a green build says nothing about type errors.
  • tsc --noEmit in CI is the only whole-project guarantee; editors check only open files.
  • TypeScript 7 is a native compiler shipping per-platform binaries, which makes full checks cheap.
  • In TypeScript 7, strict is on by default — you opt out rather than in.
  • tsc --init now generates a strict, modern config, including noUncheckedIndexedAccess and exactOptionalPropertyTypes.
  • Most TypeScript advice online predates these defaults; check which version it targets.
