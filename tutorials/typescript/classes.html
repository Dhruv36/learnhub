Classes in TypeScript In Practice

What you'll master: the difference between private and #private that matters most — private soft appears in Object.keys and JSON.stringify; #hard does not, verified at run time; which class syntax is erasable and which is not, since accessor and # are real JavaScript while parameter properties are TS1294 under erasableSyntaxOnly; a genuine target: esnext hazard where accessor emits syntax Node cannot parse; noImplicitOverride and the TS4117 typo message that justifies it; abstract classes and constructor types; and when a class is the wrong tool. Prerequisites: Structural Typing & Variance.

Part 1 — private Is Not Private

TypeScript has two privacy mechanisms and they are not variations on a theme — one is a compile-time annotation, the other is a JavaScript language feature.

class A { #hard = 1; private soft = 2; m() { return this.#hard + this.soft; } }
const a = new A();

// compiled to ES2022 and run under Node — verified
keys:         [ 'soft' ]
json:         {"soft":2}
bracket soft: 2
bracket hard: undefined
⚠️ private is erased, so the field is an ordinary property at run time. It serialises into JSON, appears in Object.keys, and is reachable through obj["soft"] or any cast. #hard is genuinely inaccessible — it is not a property at all, so none of those reach it.

The JSON.stringify row is the one that causes incidents. A field marked private passwordHash is in the serialised output of any object returned from an endpoint — lesson 9's argument about deriving DTOs applies here too. If a field must not leave the process, use #, or do not put it on the object.

Part 2 — What Is Erasable, and What Is Not

Modern class syntax is a mix of real JavaScript and TypeScript-only constructs, and lesson 17's erasableSyntaxOnly draws the line exactly:

class A {
  #real = 1;                              // JavaScript
  private soft = 2;                       // TypeScript — but erasable (just an annotation)
  readonly r = 3;                         // TypeScript — erasable
  static s = 4;                           // JavaScript
  accessor acc = 5;                       // JavaScript (decorators proposal)
  static { A.s = 6; }                     // JavaScript
  constructor(public param: string) {}    // TypeScript — NOT erasable
}

$ npx tsc c1.ts --noEmit --target esnext --erasableSyntaxOnly
c1.ts(8,15): error TS1294: This syntax is not allowed when 'erasableSyntaxOnly' is enabled.
                                        ◄── verified: ONLY the parameter property

A parameter property generates an assignment in the constructor body, so it cannot be erased. Everything else in that class either is standard JavaScript or is purely an annotation.

And accessor carries a target hazard worth knowing:

// target: es2022 — tsc downlevels it            ◄── verified
class A {
    #acc_accessor_storage = 5;
    get acc() { return this.#acc_accessor_storage; }
    set acc(value) { this.#acc_accessor_storage = value; }
}

// target: esnext — tsc emits it verbatim        ◄── verified
class A { accessor acc = 5; }

$ node out/c1.js
SyntaxError: Unexpected identifier 'acc'          ◄── Node 24 cannot parse it

target: esnext means "emit whatever I wrote", which is only safe if every runtime you deploy to supports every proposal you use. Pinning to a concrete version such as es2022 makes the compiler downlevel where needed, which is why it is the safer default despite tsc --init offering esnext.

Part 3 — override

class Base { greet() { return "hi"; } }
class Good extends Base { override greet() { return "yo"; } }
class Bare extends Base { greet() { return "yo"; } }
class Typo extends Base { override greeet() { return "yo"; } }

$ npx tsc c4.ts --noEmit --noImplicitOverride
c4.ts(3,27): error TS4114: This member must have an 'override' modifier because it
             overrides a member in the base class 'Base'.
c4.ts(4,36): error TS4117: This member cannot have an 'override' modifier because it is
             not declared in the base class 'Base'. Did you mean 'greet'?   ◄── verified

TS4117 is the reason the flag is worth enabling. Without it, a typo in an override name silently creates a brand-new method: the base implementation keeps running, the subclass method is never called, and nothing anywhere is wrong enough to error. The same applies when a base class renames a method — every subclass quietly stops overriding it.

Genuinely new methodFineFine, with no modifier

Part 4 — Abstract Classes and Constructor Types

abstract class Repo<T> {
  abstract find(id: string): Promise<T | undefined>;
  async require(id: string): Promise<T> {          // shared, concrete
    const found = await this.find(id);
    if (!found) throw new Error(`not found: ${id}`);
    return found;
  }
}

new Repo();                  // error: cannot create an instance of an abstract class

Passing a class around as a value needs a constructor type, and the two forms are not interchangeable:

type Ctor<T>         = new (...args: never[]) => T;              // concrete classes only
type AbstractCtor<T> = abstract new (...args: never[]) => T;     // also accepts abstract

declare function register<T>(c: Ctor<T>): void;
register(Repo);              // error — an abstract class has no callable constructor

A class used only for instanceof or extendsabstract new (…) => T

Note the lesson 9 point recurring: InstanceType<C> is a constraint error, because C is already the instance type — you need typeof C, the constructor.

Part 5 — implements Does Less Than You Think

interface Logger { log(msg: string): void }

class ConsoleLogger implements Logger {
  log(msg: string) { console.log(msg); }
}

// but this also satisfies Logger, with no `implements` anywhere
const objectLogger = { log(msg: string) { console.log(msg); } };
declare function use(l: Logger): void;
use(objectLogger);           // ✔ structural typing — lesson 3
implementsDoesDoes not
CheckingVerify the class satisfies the interfaceMake the interface required of others
AssignabilityNothing — structural rules applyCreate a nominal relationship
EmitNothing — erasedAppear at run time
InferenceNothing — member types are not inferred from itSupply parameter types

The inference point catches people: implements does not give a method's parameters their types. Writing log(msg) { … } in a class that implements Logger is an implicit-any error, not an inference of string. If you want the interface to drive the types, an object literal annotated with the interface does that; a class body does not.

Part 6 — When Not to Use a Class

A group of pure functionsA moduleTree-shakeable; no instance to construct

A discriminated union of statesA union of object typesExhaustiveness checking; see lesson 5

❌ A class whose only members are a constructor storing config and one method. new EmailSender(apiKey).send(to, body) has a construction step, a this to reason about, an instance to pass around or re-create, and no state that survives the call. Every consumer now needs the class, the key, and the knowledge of when to instantiate — and it will not tree-shake, because the class is a value.

✅ A function that closes over the config, or a plain function taking it as a parameter. const send = makeSender(apiKey) or send(apiKey, to, body) is testable without construction, trivially mockable, and tree-shakeable. Reach for a class when you have genuine invariants to protect, identity that instanceof must see, or fields that must be unreachable at run time — those are real reasons, and "it groups related code" is not one, because a module does that.

Interview Questions

Beginner: What is the difference between private and #private?

private is a TypeScript annotation checked at compile time and then erased. #field is JavaScript syntax for a genuinely private field enforced by the runtime.

The practical difference is what happens to the value. I verified it by running compiled output: for a class with #hard = 1 and private soft = 2, Object.keys returned ['soft'], JSON.stringify gave {"soft":2}, and obj["soft"] returned 2 — while #hard was invisible to all three.

So private stops your colleagues, and # stops the program. That matters most for anything sensitive: a field marked private passwordHash is in the JSON of any object serialised from an endpoint, which is a real incident rather than a theoretical one.

Both affect assignability, which is the other half — a class with either kind of private member is not structurally compatible with a class that lacks it, which is the nominal behaviour lesson 13 mentioned.

Beginner: What does implements actually do?

It checks that the class satisfies the interface. That is all — it creates no assignability relationship, emits nothing, and does not restrict anyone else.

Because TypeScript is structural, any object with the right shape satisfies the interface whether or not it declared implements. A plain object literal with a matching log method is accepted anywhere a Logger is expected, which is the design rather than a loophole.

The part that surprises people is that implements does not infer member types. Writing log(msg) { … } in a class that implements Logger is an implicit-any error, not an inference of string — the interface is a check applied afterwards, not a source of contextual types. An object literal annotated with the interface does get contextual typing; a class body does not.

So its value is as documentation plus a guard: it states the intent and fails the build if the class drifts from the contract. Useful, but much less than the keyword suggests to someone arriving from a nominal language.

Mid: Which class syntax is not erasable, and why does it matter?

Parameter properties. constructor(public param: string) {} generates an assignment in the constructor body, so removing the types is not enough to compile it — and that is precisely what erasableSyntaxOnly forbids.

I checked a class using #private, private, readonly, static, accessor, a static block and a parameter property. Under erasableSyntaxOnly only the parameter property errored, with TS1294. Everything else is either real JavaScript or purely an annotation.

It matters because of lesson 17's pipeline split: non-erasable syntax is where tsc and a single-file transpiler can disagree, which is the same category as the const enum problem that produced a runtime SyntaxError when two emitters were mixed.

There is a separate accessor hazard worth knowing, which is about targets rather than erasability. At target: es2022 the compiler downlevels it into a #-backed getter/setter pair. At target: esnext it emits accessor acc = 5; verbatim, and Node 24 fails with SyntaxError: Unexpected identifier 'acc'. That is a good argument for pinning a concrete target rather than using esnext.

Mid: Why enable noImplicitOverride?

Because without it, two silent failure modes are possible, and both leave a subclass that looks correct and does nothing.

The first is a typo. override greeet() instead of greet() creates a brand-new method: the base implementation keeps running, the subclass method is never called, and no error appears anywhere. With the flag it is TS4117, and I verified the message includes a suggestion — "Did you mean 'greet'?" — which turns a debugging session into a one-line fix.

The second is a rename in the base class. Every subclass that used to override the old name silently stops overriding anything, so behaviour reverts to the base implementation across the hierarchy. With the flag, each of those subclasses errors immediately.

The cost is writing override on genuine overrides, which is also useful documentation — a reader can tell at a glance whether a method is new or replacing something. The flag is not part of strict, as lesson 10 covered, so it has to be enabled by name; in class-heavy code I would always do so.

Senior: A codebase has deep class hierarchies and is hard to change. How would you approach it?

I would treat the depth itself as the problem rather than any individual class, because the cost of inheritance is that behaviour for one object is distributed across several files and no single one tells you what happens.

The concrete symptoms to look for: a method whose behaviour depends on three super calls; protected fields mutated at several levels, so no layer owns an invariant; subclasses that override a method to do nothing, which means the hierarchy is wrong; and base classes with members only some subclasses use, which is the clearest sign that a shared parent was created for code reuse rather than for a real "is-a" relationship.

The refactor I would aim for is composition with explicit dependencies. Replace a protected hook with an injected function or strategy object; replace shared state with a value passed in; replace a template-method base class with a function taking the varying steps as parameters. Each step makes the behaviour readable in one place and testable without constructing a hierarchy.

Where I would keep classes: real invariants protected by # fields, error types that instanceof must identify, and value objects with guarded operations — lesson 13's money case. Those are things a plain function cannot do. "It groups related code" is not one of them, because a module does that with no construction step and better tree-shaking.

Recommendation: enable noImplicitOverride first, since it will immediately reveal overrides that silently do nothing; cap new hierarchies at two levels by convention; and convert the hierarchies that change most often, driven by where the pain actually is rather than by doing all of them. A deep hierarchy that nobody touches is not costing anything.

Senior: Design the class-related conventions for a team.

I would aim for a small number of rules that are checkable, because conventions that need judgement at every call site decay.

Privacy: # for anything that must not escape, private otherwise. The deciding question is whether the field appearing in JSON.stringify would be a problem — I verified that private fields do serialise. Credentials, tokens and internal handles get #; ordinary implementation details can stay private, which is easier to debug and to test.

Flags over discipline where possible. noImplicitOverride on, because the failure it prevents is silent and the error it gives includes a suggestion. erasableSyntaxOnly on if the build uses a transpiler, which rules out parameter properties and keeps tsc and the transpiler in agreement. A pinned target rather than esnext, so new proposal syntax is downlevelled rather than shipped to a runtime that cannot parse it.

A written test for when a class is justified: an invariant to protect, identity for instanceof, or runtime-private state. If none of those apply, a module of functions is the default. That single rule removes most of the "service class with one method and a constructor" pattern.

Two levels of inheritance at most, and implements used freely as documentation while understanding it guarantees nothing about assignability. Abstract classes are fine for a shared concrete method over an abstract one, as a repository base would be, and that is usually the only inheritance a codebase needs.

Recommendation: put the three flags in the shared config so they are not negotiable per file, write the class-justification test into the review checklist, and revisit if the team finds a case the rules handle badly — which is more useful than trying to anticipate every case up front.

🎯 Key Takeaways

  • private is compile-time only — it appears in Object.keys and JSON.stringify.
  • #field is runtime-private — unreachable by keys, JSON, brackets or casts.
  • A private secret on a serialised object ships to the client.
  • Both kinds of private affect assignability, giving classes nominal behaviour.
  • Only parameter properties are non-erasable — TS1294 under erasableSyntaxOnly.
  • #, static blocks and accessor are real JavaScript and erase fine.
  • accessor at target: esnext emits syntax Node cannot parse — pin a concrete target.
  • noImplicitOverride catches a typo'd override with TS4117 and a suggestion.
  • Without it, a base-class rename silently un-overrides every subclass.
  • Use abstract new (…) => T when a class is not going to be instantiated.
  • InstanceType<typeof C> — the bare class is already the instance type.
  • implements only checks; it creates no assignability relationship.
  • implements does not type method parameters — that is an implicit any.
  • A class needs an invariant, an identity, or runtime-private state to be justified.
  • A module of functions is the default for grouping related code.
