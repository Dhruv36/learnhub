Types, Unions & Literals Foundations

What you'll master: the type zoo and its two extremes — unknown at the top, never at the bottom — and why any is not a type but a switch that turns checking off; inference and widening, so you can predict when const gives you the literal "hello" and let gives you string; as const and what it really produces; unions as the replacement for enum; intersections; the difference between optional and "present but undefined", which exactOptionalPropertyTypes makes visible; index signatures and the lie Record<string, T> tells about missing keys; tuples and readonly; and when type and interface genuinely differ. Prerequisites: What TypeScript Actually Is.

🔑 unknown is what people think any is. Both accept any value. The difference is what happens next: unknown forces you to prove what the value is before using it, while any lets every subsequent operation through unchecked — and spreads, because anything derived from an any is also any. When you genuinely do not know a type, that is unknown; when you want the compiler to stop arguing, that is any, and it is worth being honest about which one you are doing.
function handle(u: unknown, a: any) {
  u.toUpperCase();          // error TS18046: 'u' is of type 'unknown'
  if (typeof u === "string") u.toUpperCase();   // fine: narrowed
  a.whatever().chain.of.nonsense;               // no error, and no safety
}

never earns its place in exhaustiveness checks. Because no value is assignable to it, a variable that the compiler believes is never proves a branch is unreachable — which is how you make the compiler tell you about a case you forgot after adding a union member. The narrowing lesson builds that into a pattern.

Part 2 — Inference and Widening

TypeScript infers a type for every value, and the type it chooses depends on whether the value can change. These are the compiler's own answers, from the declarations it generates:

const a = "hello";          declare const a = "hello";        ◄── the LITERAL type
let   b = "hello";          declare let b: string;            ◄── widened, because b can be reassigned
const arr = [1, 2];         declare const arr: number[];      ◄── an array of numbers, not a tuple
const tup = [1, 2] as const;  declare const tup: readonly [1, 2];
const o  = { k: "v" };      declare const o: { k: string };   ◄── properties widen too
const oc = { k: "v" } as const;  declare const oc: { readonly k: "v" };
DeclarationInferred asWhy
const x = "a""a"It can never change, so the literal type is safe and useful
let x = "a"stringIt may be reassigned, so the type widens to the whole set
{ k: "v" }{ k: string }Object properties are mutable, so they widen
{ k: "v" } as const{ readonly k: "v" }as const freezes the type: literal and readonly, recursively
[1, 2]number[]Array literals infer as arrays, not tuples
[1, 2] as constreadonly [1, 2]Exactly two elements, with those values

This is why a config object "loses" its literal types. Passing { method: "GET" } to a function expecting { method: "GET" | "POST" } works, because the literal is checked in place — but assigning it to a variable first widens method to string, and the call then fails. as const is the fix, and the reason it appears everywhere in real codebases.

Annotate deliberately, not reflexively. Inference is usually better than what you would write: it stays correct when the code changes. Annotate where the type is a contract — function parameters, exported return types, module boundaries — and let inference handle local values.

Part 3 — Unions: the Workhorse

A union type says the value is one of these. It is the most useful construct in the language, and it replaces enum for most purposes (with the erasure advantage from lesson 1).

type Status = "pending" | "paid" | "shipped";     // a union of literal types
type Id     = string | number;
type Maybe  = User | null;

const Color = { Red: "red", Green: "green" } as const;
type Color = typeof Color[keyof typeof Color];    // "red" | "green" — derived, not duplicated
Union of literalsenum
Erased entirelyEmits runtime code (lesson 1)
The values are exactly what you wroteNumeric enums map both ways and accept stray numbers
Works with any string from JSON without conversionNeeds mapping at boundaries
Exhaustiveness checking via neverAlso possible, with more ceremony

What you may do with a union is the intersection of its members. On string | number you can call only what both support, which is why narrowing (the next lesson) is the constant companion of unions. And never disappears from unions — string | never is just string — which is what makes exhaustiveness checks work.

Part 4 — Intersections, Optionals and Index Signatures

An intersection A & B is a value that satisfies both. It is how you compose object types, and how mixins are typed.

type WithId        = { id: string };
type WithTimestamps = { createdAt: Date; updatedAt: Date };
type Entity        = WithId & WithTimestamps;      // all four properties required

type Impossible = string & number;                  // never: no value is both

Optional is not the same as "may be undefined", and the distinction has its own flag:

type A = { x?: number };        // x may be ABSENT

const a1: A = {};               // fine everywhere
const a2: A = { x: undefined }; // fine by default; an error under exactOptionalPropertyTypes

$ tsc opt.ts --exactOptionalPropertyTypes --noEmit
error TS2375: Type '{ x: undefined; }' is not assignable to type 'A' with
              'exactOptionalPropertyTypes: true'. Consider adding 'undefined' to the
              types of the target's properties.
DeclarationAbsent allowedExplicit undefined allowed
x?: number (flag off)YesYes
x?: number (flag on)YesNo
x: number | undefinedNo — the key must existYes
x?: number | undefinedYesYes

It matters where the difference is observable: "x" in obj, Object.keys, a JSON body that includes "x": null, and database updates where "absent" means "leave it alone" while "undefined" means "clear it". Note that exactOptionalPropertyTypes is not part of strict — verified: with strict on by default in TypeScript 7 the assignment above still passes — but tsc --init now turns it on for new projects.

Index signatures and Record claim more than they can deliver:

type R = Record<string, number>;
const r: R = { a: 1 };
const n: number = r.missing;      // NO ERROR by default — the type says number, the value is undefined

$ tsc opt.ts --noUncheckedIndexedAccess --noEmit
error TS2322: Type 'number | undefined' is not assignable to type 'number'.

The same unsoundness as array indexing from lesson 1, and the same flag closes it. Where the set of keys is known, prefer a closed object type or Record<Status, X> over Record<string, X> — then the compiler knows which keys exist and can check exhaustiveness for you.

Part 5 — Arrays, Tuples and readonly

[string, number]A tuple: exactly two elements, in that orderGreat for useState-style returns

readonly [1, 2]What as const produces for an array literalLiteral element types, fixed length
function sum(xs: readonly number[]): number {     // signals: I will not modify your array
  return xs.reduce((a, b) => a + b, 0);
}

const frozen = [1, 2] as const;
sum(frozen);                 // fine
frozen.push(3);              // error: push does not exist on a readonly tuple

readonly is shallow and compile-time only. A readonly array of objects still allows mutating those objects, and nothing prevents mutation at runtime — it is not Object.freeze. It is a statement of intent the compiler enforces within your own code, which is exactly its value in function signatures.

Part 6 — type or interface?

Object shapesYesYes

// declaration merging — an interface can be reopened, which is how ambient types are extended
interface Window { myApp: App }          // adds to the DOM's Window, rather than replacing it

// a type alias cannot be reopened
type T = { a: string };
type T = { b: number };                  // error: Duplicate identifier 'T'

The practical rule: use interface for object shapes that others may extend or augment — public API surfaces, and anything that needs to merge into an existing declaration — and type for everything else, because unions, intersections and the type-level operators in the next section need it. Being consistent matters more than the choice; what should not happen is a codebase where the two are used at random and nobody can say why.

Interview Questions

Beginner: What is the difference between any and unknown?

Both accept any value. The difference is what you may do with the value afterwards.

With unknown, you may do nothing until you narrow it: calling a method or reading a property is an error until a typeof check, an instanceof check or a type guard proves what it is. It is the honest type for a value you genuinely do not know — an API response, a caught error, a parsed JSON payload.

With any, every operation is permitted and unchecked. Worse, it spreads: anything derived from an any value is itself any, so one escape hatch can silently disable checking across a whole call chain. That is why any is better described as an instruction to stop checking than as a type.

In the type lattice, unknown is the top type — everything is assignable to it — and never is the bottom, assignable to everything and inhabited by nothing. any sits outside that structure because it is assignable in both directions, which is exactly why it breaks the guarantees the rest of the system provides.

Beginner: Why does const infer a literal type but let does not?

Because the compiler infers the narrowest type that will stay true. A const binding can never be reassigned, so const a = "hello" can safely have the literal type "hello". A let binding may be reassigned to any other string, so its type widens to string.

The same widening happens inside object literals, because properties are mutable: { k: "v" } infers as { k: string } even when declared with const, since the binding is constant but the property is not.

That is what as const is for. It marks the whole literal as deeply readonly and keeps the literal types: { k: "v" } as const becomes { readonly k: "v" }, and [1, 2] as const becomes readonly [1, 2] rather than number[].

It matters in practice when a value must match a union of literals. Passing { method: "GET" } inline works, but assigning it to a variable first widens the property to string and the call then fails — one of the most common early TypeScript puzzles, and as const is the answer.

Mid: When would you use a union of string literals instead of an enum?

Almost always, in modern TypeScript.

A union of literals is erased completely, so it costs nothing at runtime and works in codebases that strip types rather than compile them — where enum is rejected outright. The values are exactly the strings you wrote, so data arriving as JSON needs no mapping, and logs and database rows read naturally.

enum also has behaviours people do not expect. Numeric enums are bidirectional maps and historically accepted arbitrary numbers, which weakens the checking they were adopted for; and an enum is a value as well as a type, so it participates in bundling and tree-shaking in ways a union does not.

Where an enum-like value is genuinely needed — to iterate the options, or to hold the canonical list — I use a const object with as const and derive the union from it with typeof Color[keyof typeof Color]. That gives one definition, a runtime array to iterate, and a type that cannot drift from it.

The one case for a real enum is interoperability with generated code or an existing API that uses them, where matching the surrounding convention is worth more than erasability.

Mid: What is the difference between an optional property and one typed | undefined?

x?: number means the property may be absent. x: number | undefined means the property must be present, and its value may be undefined. By default TypeScript is lenient and lets you assign { x: undefined } to the optional form too, so the two look interchangeable.

exactOptionalPropertyTypes separates them: with it on, assigning an explicit undefined to an optional property is an error (TS2375). It is not part of strict — even in TypeScript 7 where strict is the default — but tsc --init now enables it for new projects.

The distinction is observable whenever presence matters rather than value: "x" in obj, Object.keys, spreading, JSON serialisation (an absent key disappears; an explicit undefined also disappears, but null does not), and especially patch semantics — in an update payload, "absent" usually means "leave unchanged" while "present and undefined" means "clear it".

So I would model the API's actual semantics: optional when the field may be omitted, and | undefined (or | null) when the caller must state it explicitly. Turning the flag on makes the codebase say which it means, which is worth the noise on any API that distinguishes the two.

Senior: Your codebase uses Record<string, User> for lookups and gets runtime undefined errors. Diagnose and fix.

The type is claiming something the data cannot support. Record<string, User> says every string key maps to a User, so map[id] is typed User even when the key is absent — and by default the compiler agrees. The first property access on the missing entry then throws at runtime, in code the types said was safe.

The direct fix is noUncheckedIndexedAccess. With it, every index access on a record or array yields T | undefined, so the absence becomes visible and must be handled. It is noisy in code that indexes heavily, which is why it is a separate flag rather than part of strict — and why TypeScript 7 generating it for new projects is a meaningful shift.

The better fix, where it applies, is a closed key set. If the keys are known — statuses, locales, feature names — Record<Status, User> tells the compiler exactly which keys exist, so lookups are genuinely safe and a missing case in a mapping becomes a compile error. That converts a runtime failure class into a type error.

For genuinely open key spaces — arbitrary ids — I prefer Map, whose get honestly returns V | undefined regardless of flags, and which does not confuse prototype keys with data.

Recommendation: turn on noUncheckedIndexedAccess and fix the fallout with a ratchet, replace open Record<string, T> lookups with Map, and reserve Record for closed key unions where it adds exhaustiveness checking rather than removing safety.

Senior: How do you decide between type and interface in a shared library?

I decide on capability and on how consumers will use the declarations, then apply it consistently.

Use interface for object shapes that consumers may extend or augment. Only interfaces support declaration merging, which is what lets a consumer add a property to an ambient type — extending Window, adding a field to a framework's request object, augmenting a module's options. If a published type might need that, an interface keeps the door open; a type alias closes it permanently. Interfaces also tend to appear by name in editor hints and error messages, which reads better than a large expanded shape.

Use type for everything else, because the interesting type-level work requires it: unions, intersections, conditional and mapped types, template literal types, tuples and function types. Any public type that is a union — a status, a discriminated result — must be a type alias.

The one caution about merging is that it is a two-edged capability: it lets consumers extend your types, and it also means a duplicate declaration silently merges instead of erroring, which can hide a mistake in a large codebase.

Recommendation: interfaces for extensible public object shapes, type aliases for everything else, written down in the contributing guide so the codebase is uniform. The worst outcome is not either choice — it is a library where both appear at random and nobody can tell whether a given type is meant to be augmentable.

2 (easy): Replace an enum with a union without losing the value list.
Solution 
// before
enum Status { Pending = "pending", Paid = "paid", Shipped = "shipped" }

// after: one definition, erasable, with both a runtime list and a type
const Status = { Pending: "pending", Paid: "paid", Shipped: "shipped" } as const;
type Status = typeof Status[keyof typeof Status];    // "pending" | "paid" | "shipped"

const all = Object.values(Status);                   // runtime iteration still works
function advance(s: Status) { /* ... */ }

Solution

5 (hard): Diagnose a widening bug in a config object.
Solution 
type Request = { url: string; method: "GET" | "POST" };
function send(r: Request) { /* ... */ }

send({ url: "/a", method: "GET" });        // ✔ fine: the literal is checked in place

const req = { url: "/a", method: "GET" };
send(req);
// error TS2345: Argument of type '{ url: string; method: string; }' is not assignable to
//               parameter of type 'Request'. Types of property 'method' are incompatible.
//               Type 'string' is not assignable to type '"GET" | "POST"'.

The object is identical; the difference is that assigning it to a variable widened method to string. Four fixes, with different trade-offs:

FixCodeWhen
Annotate the variableconst req: Request = { … }Best: the shape is checked at the declaration, where the error belongs
as constconst req = { … } as constAlso makes it readonly — fine, and often desirable
satisfiesconst req = { … } satisfies RequestChecks against Request while keeping the narrow inferred type
Widen the parametermethod: stringWrong: throws away the constraint that made the type useful
const req = { url: "/a", method: "GET" } satisfies Request;
req.method;    // still "GET", not string — the literal type survives
send(req);     // ✔

satisfies is the one to remember: annotation checks and widens to the annotation, while satisfies checks without widening — which is what you usually want for configuration objects you also read from.

6 (hard): Model an API payload precisely, then defend the choices.
Solution 
requirements
  • an order has an id and a status of exactly: pending, paid, shipped, cancelled
  • "items" is a non-empty list; each item has a sku and a quantity
  • "note" may be omitted entirely, or sent as null to clear it
  • "discount" is optional and, when present, is a number
  • nothing in the object may be mutated by consumers

type Status = "pending" | "paid" | "shipped" | "cancelled";

type Item = { readonly sku: string; readonly quantity: number };

type Order = {
  readonly id: string;
  readonly status: Status;
  readonly items: readonly [Item, ...Item[]];   // non-empty by construction
  readonly note?: string | null;                // absent = unchanged; null = clear
  readonly discount?: number;                    // absent only — never explicitly undefined
};
DecisionReason
Union of literals, not enumErasable; matches raw JSON strings; exhaustiveness via never
readonly [Item, ...Item[]]Encodes "non-empty" in the type, so no runtime length check is needed downstream
note?: string | nullThe API distinguishes three states; the type says so explicitly
discount?: number with exactOptionalPropertyTypesSending undefined explicitly becomes an error, matching the server
readonly throughoutCompile-time intent; consumers cannot mutate shared state by accident

The type is still only a claim about incoming data — lesson 1's point — so this shape is the output of a schema parse at the boundary, not a substitute for one. Written this way it also documents the API's semantics better than prose: a reader can see that note has three states and that an order can never have zero items.

🎯 Key Takeaways

  • unknown is the top type and never the bottom; any sits outside the system because it disables checking.
  • Prefer unknown wherever you are tempted by any — it forces a narrowing step rather than removing one.
  • const infers literal types; let widens, and object properties widen even under const.
  • as const produces deeply readonly, literal types — readonly [1, 2], { readonly k: "v" }.
  • satisfies checks a value against a type without widening it, which annotation cannot do.
  • Unions of string literals replace enum and are fully erasable.
  • Derive the union from a const object when you also need the values at runtime.
  • A union only permits what all members support, so unions and narrowing always travel together.
  • never vanishes from unions, which is what makes exhaustiveness checks work.
  • Optional (x?: T) and x: T | undefined differ in presence, and exactOptionalPropertyTypes enforces the difference.
  • That flag is not part of strict — but tsc --init now enables it.
  • Record<string, T> types missing keys as T unless noUncheckedIndexedAccess is on; a closed key union or a Map is often better.
  • readonly is shallow, compile-time only, and belongs in parameter types to signal intent.
  • Tuples need as const or an explicit type; array literals infer as arrays.
  • Only interfaces merge; use them for extensible public shapes and type for everything else.
