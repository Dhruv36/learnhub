Utility Types in Practice Type-Level Programming

What you'll master: the standard library's type helpers as they actually behave — Partial and Readonly are shallow; Pick rejects a misspelled key while Omit silently accepts one; Omit over a discriminated union destroys it, leaving a type with no properties at all; Exclude, Extract and NonNullable and why they distribute; ReturnType, Parameters, Awaited and InstanceType; and Record's two very different personalities depending on whether the key is string or a literal union. Prerequisites: Mapped & Template Literal Types.

Part 1 — The Shape Transformers

Five utilities cover most day-to-day use, and all five are the mapped types from the previous lesson with names attached.

interface User { readonly id: string; name?: string; age: number; nested: { a: number } }

type A = Partial<User>;             // every property optional
type B = Required<User>;            // every property required
type C = Readonly<User>;            // every property readonly
type D = Pick<User, "id" | "name">; // only those two
type E = Omit<User, "age">;         // all but that one

All of them preserve the source's modifiers, which is homomorphism from lesson 8 doing its job:

// verified with tsc 7.0.2
declare const o: Omit<User, "age">;
o.id = "x";
// error TS2540: Cannot assign to 'id' because it is a read-only property.   ◄── readonly kept
const n: string = o.name;
// error TS2322: Type 'string | undefined' is not assignable to type 'string'. ◄── optional kept

Part 2 — Shallow Means Shallow

This is the single most common misunderstanding about utility types, and nothing in the name warns you.

// verified with tsc 7.0.2
declare const p: Partial<User>;
const x: 0 = p.nested;
// error TS2322: Type '{ a: number; } | undefined' is not assignable to type '0'.
//   ▲ nested itself is optional — but its CONTENTS are untouched

declare const r: Readonly<User>;
r.nested.a = 1;      // ✔ COMPILES — Readonly stopped at the first level
⚠️ Readonly<T> prevents reassigning a property, not mutating what it points at. A "frozen" config object typed as Readonly<Config> still lets any caller reach into config.db.host and change it. If the guarantee matters, write a DeepReadonly deliberately, and remember that neither version does anything at runtime — Object.freeze is a separate decision.

Required<Opts>Top-level fields must be presentNested optionals stay optional

Part 3 — The Omit Asymmetry

Pick constrains its key parameter to keyof T. Omit does not — its key parameter is just PropertyKey.

type BadPick = Pick<User, "agee">;
// error TS2344: Type '"agee"' does not satisfy the constraint 'keyof User'.   ◄── caught

type BadOmit = Omit<User, "agee">;
// no error at all — and 'age' is still there                                  ◄── verified

The typo compiles, the type is unchanged, and the mistake surfaces later as a property that should not exist. The reason for the loose constraint is deliberate — Omit is meant to work when you know a key might not be present — but the cost is that it cannot warn you.

The second problem is worse, because the result looks empty rather than wrong:

type Shape = { kind: "circle"; r: number } | { kind: "square"; s: number };
type Stripped = Omit<Shape, "kind">;

declare const st: Stripped;
st.r;   // error TS2339: Property 'r' does not exist on type 'Stripped'.   ◄── verified
st.s;   // error TS2339: Property 's' does not exist on type 'Stripped'.   ◄── verified

Omit is built on keyof T, and keyof of a union is only the keys the members have in common — here, just "kind". Omitting it leaves nothing. The union was flattened into a single object type before anything was removed.

// the fix: distribute over the union first
type DistOmit<T, K extends PropertyKey> = T extends unknown ? Omit<T, K> : never;
type Ok = DistOmit<Shape, "kind">;
// Omit<{ kind: "circle"; r: number }, "kind"> | Omit<{ kind: "square"; s: number }, "kind">

Part 4 — Union Utilities

Three utilities operate on unions rather than objects, and all three are distributive conditionals from lesson 7.

// verified with tsc 7.0.2
Exclude<"a" | "b" | "c", "a">                   // "b" | "c"
Extract<string | number | boolean, string | number>  // string | number
NonNullable<string | null | undefined>          // string
UtilityDefinitionReads as
Exclude<T, U>T extends U ? never : TRemove the members assignable to U
Extract<T, U>T extends U ? T : neverKeep only those members
NonNullable<T>T & {}Drop null and undefined

Extract with an object pattern is the idiomatic way to select a union member:

type Shape = { kind: "circle"; r: number } | { kind: "square"; s: number };
type Circle = Extract<Shape, { kind: "circle" }>;    // { kind: "circle"; r: number }

That is worth preferring over a second hand-written type, because it cannot drift: add a member to Shape and the extraction still means what it said.

The overload caveat bites in real code. A function with three overloads has a ReturnType equal to the last one's return type, silently. The fix is to extract from a specific signature rather than the whole function, or to avoid deriving from overloaded functions at all.

Part 6 — Record, and Index Signatures

Record<K, V> behaves completely differently depending on K, and the difference is the one worth knowing.

// verified with tsc 7.0.2
const r: Record<"a" | "b", number> = { a: 1 };
// error TS2741: Property 'b' is missing in type '{ a: number; }'
//               but required in type 'Record<"a" | "b", number>'.   ◄── EXHAUSTIVE

declare const rec: Record<string, number>;
const v: number = rec.missing;    // ✔ compiles — every key "exists"

A literal-union key gives an exhaustive table: add a variant to the union and every Record built from it fails to compile until it is handled. That makes it the right tool for lookup tables keyed by a discriminant.

A string key gives an index signature, and the compiler will hand you a number for a key that is not there. That is what noUncheckedIndexedAccess fixes:

$ tsc --strict --noUncheckedIndexedAccess
// error TS2322: Type 'number | undefined' is not assignable to type 'number'.   ◄── verified

❌ Record<string, User> for a lookup you index by an unknown key. Every access is typed as User, including users[idFromQueryString], so the missing-key case never appears in the type. The first null-property crash in production is the first time anyone finds out, and it will be in a branch nobody tested.

✅ Turn on noUncheckedIndexedAccess, or use a Map. The flag makes every index access User | undefined, which forces the check where it belongs. Map<string, User> gets the same honesty by default from get(): User | undefined, and is the better choice when keys are dynamic anyway. Reserve Record with a literal union for tables whose keys are known at compile time.

Interview Questions

Beginner: What does Partial<T> do, and what does it not do?

It produces a version of T where every top-level property is optional. It is defined as { [K in keyof T]?: T[K] } — a mapped type that adds the ? modifier.

What it does not do is go deeper. Given { nested: { a: number } }, the Partial version makes nested itself optional, but if it is present it must still be a complete { a: number } — I verified the property type is { a: number } | undefined, not a partial one. A patch payload built on Partial therefore cannot express "update just one nested field".

It also does nothing at runtime. Partial is erased like every type, so it describes what callers may omit — it does not make the code tolerate missing values.

Readonly has the matching shallowness: it stops property reassignment at the top level, and nested objects stay fully mutable.

Beginner: What is the difference between Pick and Omit?

Pick<T, K> keeps the named keys; Omit<T, K> keeps everything else. Omit is defined in terms of the others — Pick<T, Exclude<keyof T, K>>.

The difference that matters is the constraint. Pick requires K extends keyof T, so a misspelled key is caught: Pick<User, "agee"> is TS2344, "does not satisfy the constraint 'keyof User'". Omit takes any PropertyKey, so Omit<User, "agee"> compiles happily and returns User unchanged — I verified that age is still present.

That looseness is intentional, because Omit is meant to be usable when a key may not exist, but the practical effect is that a rename can leave an Omit quietly doing nothing.

Teams that care about this write a stricter wrapper — type OmitStrict<T, K extends keyof T> = Omit<T, K> — which costs one line and turns the typo back into an error.

Mid: What happens when you use Omit on a discriminated union?

It destroys it. The result is not a union with the key removed from each member — it is a single object type built from the keys the members had in common, with the named key taken out.

With type Shape = { kind: "circle"; r: number } | { kind: "square"; s: number }, Omit<Shape, "kind"> gives a type where neither r nor s exists — I verified both accesses fail with TS2339. The cause is that Omit is built on keyof T, and keyof of a union is the intersection of its members' keys, which here is just "kind". Remove that and nothing is left.

The fix is to distribute before omitting: type DistOmit<T, K extends PropertyKey> = T extends unknown ? Omit<T, K> : never. The naked type parameter makes the conditional distributive, so Omit is applied to each member separately and the union survives.

The same trap applies to Pick and to anything else built on keyof T. It is one of the better arguments for writing derived union types explicitly rather than deriving them: the failure is silent and the resulting type is not obviously broken until someone uses it.

Mid: When should you use Record and when a Map?

It comes down to whether the keys are known at compile time, because Record behaves like two different types depending on the key.

With a literal union key, Record<"a" | "b", number> is exhaustive — I verified that omitting b is TS2741, "Property 'b' is missing". That is exactly what you want for a handler table keyed by a discriminant: add a new variant to the union and every table fails to compile until it is handled.

With a string key it becomes an index signature, and every lookup is typed as present. rec.missing is number, not number | undefined — which is a lie for any dynamic key. noUncheckedIndexedAccess fixes it by making every index access include undefined, and I would turn that on in any new project.

For genuinely dynamic keys I prefer Map: get returns V | undefined without needing a flag, keys are not limited to strings, it does not inherit Object.prototype members, and iteration order and size are well defined. The main reason to stay with an object is JSON serialisation.

Senior: A team derives all its API types from database models with Omit and Partial. What is your view?

It is a pattern that works until it fails silently, and the failure mode is a security one, so I would push back on it for anything crossing a trust boundary.

The core problem is that derivation defaults to exposure. type UserDto = Omit<UserModel, "passwordHash"> is correct today. When someone adds internalNotes or failedLoginCount to the model, the DTO gains it automatically and nothing fails. An explicitly declared DTO has the opposite default: a new model column is invisible until someone adds it, and adding it is a reviewable diff.

The Omit-specific hazards compound it. Its key parameter is unconstrained, so renaming passwordHash leaves Omit<UserModel, "passwordHash"> compiling and omitting nothing. And if the model is a union, Omit collapses it to the common keys — I verified that case produces a type with no usable properties at all.

Where derivation is right: inside one layer, where both types change together — form state from a model, a patch type from an entity, test fixtures. There the whole point is that they cannot drift.

Recommendation: declare API and DTO types explicitly, derive internal shapes freely, add an OmitStrict wrapper so typos are caught, and if derivation must be kept at the boundary, back it with a runtime serialiser that allow-lists fields — because the type is erased and cannot protect anything at run time.

Senior: How do you decide between a built-in utility, a local helper, and writing the type out?

My ordering is built-in, then local helper, then explicit — but with a strong bias towards explicit at module boundaries, and the deciding question is whether the type should track its source or be independent of it.

Built-ins first, because they are shared vocabulary. Every reader knows what Partial<T> means without opening a file, they are maintained against compiler changes, and the error messages name them. Re-implementing Awaited or ReturnType gets edge cases wrong — Awaited unwraps recursively, handles thenables and distributes over unions, which a hand-rolled conditional usually does not.

A local helper when the same composition appears three times, and always named after the domain concept rather than the mechanics: EntityPatch<T> rather than PartialExceptId<T>. A small number of well-named helpers in one file is far better than the same four-utility chain inlined across twenty modules, where nobody can change it.

Explicit when the type is a contract. API responses, DTOs, public function signatures, anything another team consumes. There the cost of drift is higher than the cost of duplication, and an explicit type makes every change visible in review. That is also where derived types create silent security problems, as the previous question covers.

Recommendation: built-ins for mechanics, a small named helper layer for repeated domain shapes, explicit declarations at every boundary — and a rule that no type alias chains more than two utilities without an intermediate name, because that is where tooltips stop being readable.

2 (easy): Find the Pick/Omit asymmetry.
Solution 
interface User { id: string; age: number }

type BadPick = Pick<User, "agee">;
type BadOmit = Omit<User, "agee">;

$ npx tsc asym.ts --noEmit --strict
asym.ts(3,27): error TS2344: Type '"agee"' does not satisfy the constraint 'keyof User'.

One error, from Pick. Omit's key parameter is PropertyKey, so the typo is accepted and BadOmit is just User. The one-line guard:

type OmitStrict<T, K extends keyof T> = Omit<T, K>;
type Caught = OmitStrict<User, "agee">;   // now TS2344

Worth adding to a shared types module in any codebase that renames fields, since the failure is otherwise invisible — the Omit keeps compiling and stops removing anything.

3 (medium): Destroy a discriminated union with Omit, then repair it.
Solution 
type Shape = { kind: "circle"; r: number } | { kind: "square"; s: number };

type Stripped = Omit<Shape, "kind">;
declare const st: Stripped;
st.r;
st.s;

$ npx tsc omitunion.ts --noEmit --strict
omitunion.ts(5,4): error TS2339: Property 'r' does not exist on type 'Stripped'.
omitunion.ts(6,4): error TS2339: Property 's' does not exist on type 'Stripped'.

Both gone. keyof Shape is "kind" — only the common key — so removing it leaves an empty type.

type DistOmit<T, K extends PropertyKey> = T extends unknown ? Omit<T, K> : never;
declare const dt: DistOmit<Shape, "kind">;
dt.r;   // error: does not exist on Omit<{ kind: "square"; s: number }, "kind">

The repaired version errors differently, and correctly: r is not available until the union is narrowed, which is the behaviour a discriminated union should have. The error message naming both members is the proof that the union survived.

// case 3, why Partial is not a patch type
interface User { name: string; nickname: string | null }

The pattern across the four: derive when both types live in the same layer and must move together; declare when the type is a contract with someone else, or when it needs to express something the source type does not. "Less typing" is not a reason on its own.

🎯 Key Takeaways

  • Utility types are ordinary mapped and conditional types with well-known names.
  • Partial and Readonly are shallow — nested objects are untouched.
  • Readonly<T> blocks reassignment, not mutation of what a property points at.
  • Pick catches a misspelled key; Omit does not — its key is unconstrained.
  • Omit over a union collapses it to the common keys, often leaving nothing.
  • Distribute first — T extends unknown ? Omit<T, K> : never — to keep a union.
  • Exclude, Extract and NonNullable are distributive conditionals.
  • Extract<Union, { kind: "x" }> is the idiomatic member selector.
  • Parameters keeps labels and optionality — [a: string, b?: number].
  • ReturnType and Parameters use the last overload, silently.
  • Awaited is recursive and union-aware — do not hand-roll it.
  • Record<"a"|"b", V> is exhaustive; Record<string, V> is an index signature.
  • noUncheckedIndexedAccess makes index access V | undefined — turn it on.
  • Derive inside a layer; declare at a boundary, where a derived type leaks new fields silently.
  • Name intermediate types rather than chaining four utilities into one unreadable alias.
