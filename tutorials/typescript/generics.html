Generics & Constraints Type-Level Programming

What you'll master: what a type parameter is actually for — relating one type to another, which is the difference between a generic and any; how inference picks a type from the arguments, and the cases where it cannot; constraints with extends, and the keyof pairing that makes property access provably safe; const type parameters, which turn string[] into readonly ["a", "b"]; default type parameters; the smell that a type parameter used once is probably wrong; and the patterns — typed stores, event maps, results — where generics pay for themselves. Prerequisites: Narrowing, Guards & Unions.

Part 1 — A Generic Relates Types; any Discards Them

A type parameter is a variable at the type level. Its value is filled in per call, which lets a signature state a relationship the compiler can then enforce.

function firstAny(xs: any[]): any { return xs[0]; }
const a = firstAny([1, 2]);        // a: any      — every downstream check is now off

function first<T>(xs: readonly T[]): T | undefined { return xs[0]; }
const b = first([1, 2]);           // b: number | undefined   ◄── verified with tsc 7.0.2
anyGeneric
Relationship between input and outputNoneStated and enforced
Caller's typeLostPreserved exactly
Errors downstreamSilencedStill checked
Refactor safetyNothing breaks, nothing is checkedMismatches surface at compile time
🔑 The test for a good generic: does the type parameter appear at least twice? Once to take information in, once to give it back — in a parameter and the return, or in two parameters that must agree. A parameter that appears only once relates nothing, and is almost always a disguised any or unknown. Part 5 has the examples.

Part 2 — Inference: What the Compiler Works Out

You rarely write the type argument. TypeScript infers it from the values you pass, matching the argument types against the parameter types.

first([1, 2]);              // T = number, from the array's element type
first<string>([]);          // explicit, because [] gives nothing to infer from

declare function bad<T>(x: T): T;
const r: string = bad(42);
// error TS2322: Type 'number' is not assignable to type 'string'.
//   T was inferred as number from the ARGUMENT — the annotation does not drive it
SituationInferenceWhat to do
Argument has the typeInferred from itNothing — let it work
Empty array or null argumentFalls back to never/unknownSupply the type argument explicitly
Return position onlyCannot infer from argumentsAnnotate at the call, or pass a witness value
Multiple candidatesUsually the union, or the best common typeConstrain, or annotate
Literal argumentWidened, unless const is used (Part 4)<const T>, or as const at the call

Inference flows from arguments, not from the assignment target. That is why const r: string = bad(42) fails: T is already number by the time the assignment is checked. The exception is contextual typing of callbacks, where the expected type does supply parameter types — as in map(n => n * 2).

Part 3 — Constraints, and the keyof Pairing

extends restricts what a type parameter may be, which both rejects bad calls and lets the body use the constrained members.

function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;      // .length is available because of the constraint
}
longest([1, 2], [3]);        // ✔ T = number[]
longest(1, 2);               // error: number does not satisfy { length: number }

The most valuable pairing in everyday TypeScript is a type parameter for the object and a second one constrained to its keys:

function pick<T extends object, K extends keyof T>(o: T, k: K): T[K] {
  return o[k];
}

const value = pick({ x: 1, y: "s" }, "y");   // value: string   ◄── verified: the EXACT property type
pick({ x: 1 }, "nope");
// error TS2345: Argument of type '"nope"' is not assignable to parameter of type '"x"'.

The return type T[K] is an indexed access: the type of property K on T. Together they give a helper that is safer than the object it wraps — misspelled keys are compile errors, and the result keeps its precise type instead of collapsing to a union of all value types.

T extends { id: string }Read idEntity helpers, caches keyed by id
T extends readonly unknown[]Use array members and tuple positionsVariadic helpers, zip, pipelines
T extends (...args: never[]) => unknownAccept any functionDecorators, memoisers, wrappers

Part 4 — const Type Parameters and Defaults

By default, inference widens literals — the same widening from lesson 2. A const type parameter keeps them, without the caller writing as const:

function pair<const T>(x: T): T { return x; }
function pairWide<T>(x: T): T { return x; }

const c = pair(["a", "b"]);          // readonly ["a", "b"]   ◄── verified
const d = pairWide(["a", "b"]);      // string[]              ◄── verified

It matters for APIs that build types from the values you pass — route tables, state machines, form schemas, column definitions. Without it, every caller must remember as const, and forgetting it produces a vague type and a confusing downstream error rather than a clear one.

type Box<T = string> = { v: T };     // default type argument
const e: Box = { v: "default" };      // Box<string>
const f: Box<number> = { v: 1 };
FeatureUse whenCaution
<const T>The API derives types from literal valuesResults are readonly: mutating helpers need a different signature
Default type argumentOne type is right for most callersA default of any quietly disables checking for everyone
Constraint plus default<T extends object = Record<string, unknown>>The default must satisfy the constraint

Part 5 — When a Generic Is the Wrong Tool

Generics have a cost: harder signatures, worse error messages, slower compilation at scale. They earn it only when they carry information.

// ✘ the type parameter appears ONCE — it relates nothing
function log<T>(value: T): void { console.log(value); }
// identical in behaviour, simpler to read:
function log(value: unknown): void { console.log(value); }

// ✘ a parameter the caller must assert to satisfy
function parse<T>(json: string): T { return JSON.parse(json); }
const user = parse<User>(raw);     // the function CANNOT produce a T — this is `as T` in disguise

// ✔ the parameter appears twice: it carries the caller's type through
function tap<T>(value: T, fn: (v: T) => void): T { fn(value); return value; }
SmellWhy it is wrongInstead
Type parameter used onceRelates nothing; it is unknown with extra syntaxunknown or a concrete type
Generic return with no generic inputThe body cannot produce the type; callers assert itReturn unknown and parse, or take a validator
Deeply nested type parametersUnreadable errors; slow checkingName intermediate types; simplify the API
Constraint of anyConstrains nothingunknown, or a real shape
Generic added "for flexibility"Speculative; nobody passes anything elseConcrete types until a second caller exists

❌ function parse<T>(json: string): T. It reads like a safe, reusable helper and is exactly as unsafe as JSON.parse(raw) as User — the function has no idea what a T is and never checks. Every call site gets a fully typed value backed by nothing, which is the lesson-1 failure with a generic wrapper around it.

✅ Make the caller supply the proof, not just the name. Take a validator — parse<T>(json: string, check: (v: unknown) => T): T — or return unknown and let a schema parse it. The type parameter then appears twice, and T is produced by something that actually inspected the data.

Part 6 — Patterns Worth Knowing

// 1. a typed store: keys and value types stay related
class Store<T extends object> {
  constructor(private state: T) {}
  get<K extends keyof T>(k: K): T[K] { return this.state[k]; }
  set<K extends keyof T>(k: K, v: T[K]): void { this.state[k] = v; }
}

// 2. an event map: the payload follows the event name
type Events = { login: { userId: string }; error: { code: number } };
function emit<K extends keyof Events>(name: K, payload: Events[K]): void { … }
emit("login", { userId: "u1" });     // ✔
emit("login", { code: 500 });        // error: payload does not match

// 3. a result type, generic in both directions
type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E };

// 4. carrying a type through a pipeline
function pipe<A, B, C>(a: A, ab: (a: A) => B, bc: (b: B) => C): C { return bc(ab(a)); }
PatternThe relationship it encodes
Typed store / repositoryKey implies value type
Event emitter mapEvent name implies payload shape
Result<T, E>Success and failure carry different data
pipe / builder chainsEach step's output is the next step's input
Wrapper that preserves a signatureThe wrapped function's parameters and return survive

Each of these replaces a runtime convention with a compile-time one. An untyped emitter needs documentation saying which payload goes with which event, and a code review to enforce it; the generic version makes the wrong payload a build error, and the editor completes the right one.

Interview Questions

Beginner: What problem do generics solve that any does not?

They preserve the relationship between types. function first(xs: any[]): any accepts any array and returns something unchecked, so the caller's type information is destroyed at the boundary and every subsequent operation is unverified. function first<T>(xs: readonly T[]): T | undefined says the element type comes back out, so passing number[] gives number | undefined.

The same idea covers relationships between parameters: a function whose two arguments must have the same type, a callback that receives exactly what was passed in, a key whose value type depends on the object. None of that can be expressed with concrete types or with any.

Generics are also erased, like everything else, so this costs nothing at runtime — you cannot write new T() or check x instanceof T; if the body needs to construct a T, the caller has to pass a constructor or factory.

The rule of thumb I use is that a type parameter should appear at least twice in the signature. If it appears once, it is not relating anything, and unknown would say the same thing more honestly.

Beginner: What does K extends keyof T give you?

It constrains a second type parameter to the property names of the first, so the compiler can check the key and compute the exact result type.

In function pick<T extends object, K extends keyof T>(o: T, k: K): T[K], calling pick({ x: 1, y: "s" }, "y") returns string — not string | number, and not unknown. Passing a key that does not exist is a compile error naming the valid keys: Argument of type '"nope"' is not assignable to parameter of type '"x"'.

The T[K] return type is an indexed access — "the type of property K on T" — which is what keeps the precision. Without the constraint you would have to accept string as the key and return a union of every property type, which is strictly less useful than the object itself.

This pattern is behind most well-typed library APIs: form field getters, ORM column selectors, event emitters, state stores. Anywhere a string names part of a structure, this is how the string and the result stay in step.

Mid: Why does const r: string = identity(42) fail?

Because inference runs from the arguments, not from the assignment target. By the time the assignment is checked, T has already been inferred as number from the argument, so the function returns number and assigning it to string fails with TS2322.

People expect the annotation to "ask for" a string, but an annotation is a requirement placed on the result, not an instruction to the inference algorithm. To choose the type argument you supply it explicitly — identity<string>(42) — which then correctly reports that 42 is not a string, at the argument rather than at the assignment.

The genuine exception is contextual typing: when a function expression is passed as an argument, the expected parameter type does flow inward, which is why nums.map(n => n * 2) knows n is a number without annotation.

The practical lesson is that when inference produces something unexpected, the fix is usually to look at which argument drove it — or to pass the type argument explicitly — rather than to add an assertion at the call site.

Mid: What is a const type parameter for?

It makes inference preserve literal types at the call site, without the caller writing as const.

With function pair<T>(x: T): T, calling pair(["a", "b"]) infers string[] — the array widens, exactly as lesson 2 described. With function pair<const T>(x: T): T, the same call infers readonly ["a", "b"]: the tuple shape and the literal members survive.

It matters for APIs that build types out of values. A router that derives route names from an array, a state machine defined as an object, a table component whose column keys must match the row type — all of them need the literals. Before const type parameters, every caller had to remember as const, and forgetting it produced a puzzling error far from the cause.

The caveat is that the inferred type becomes readonly, so a function that intends to mutate what it was given needs a different signature. That is usually a good constraint rather than a limitation.

Senior: A codebase has generics everywhere and the errors are unreadable. How do you improve it?

I would start by separating generics that carry information from generics that are decoration, because only the second kind is pure cost.

The single-use test finds most of them: a type parameter that appears once in a signature relates nothing and can be replaced by unknown or a concrete type immediately. Closely related is the fake generic — parse<T>(json: string): T — which is an assertion in disguise and should take a validator or return unknown.

Then attack error message quality. Deeply nested inline generics produce errors that print the whole expanded type. Naming intermediate types gives the compiler something short to say, and adding explicit constraints makes failures point at the constraint rather than at a wall of structure. Where an API is genuinely complex, a small number of well-named helper types beats one clever signature.

Check compile time as well: deep conditional and mapped types over large unions are the usual cause of slow builds, and the compiler-performance lesson covers measuring that with --diagnostics. A generic that is expensive and unused is easy to justify removing.

Recommendation: delete single-use type parameters, replace fake generics with validators, name intermediate types, and set a team norm that a generic must be justified by a second caller or a real relationship. The goal is not fewer generics — it is that every remaining one earns its signature.

Senior: Design a typed event emitter and defend the signature.

The requirement is that the event name determines the payload type, so that a wrong payload is a compile error and the editor completes the right shape.

type EventMap = {
  login:  { userId: string };
  logout: { userId: string; reason: "manual" | "timeout" };
  error:  { code: number; message: string };
};

class Emitter<M extends Record<string, unknown>> {
  private handlers: { [K in keyof M]?: Array<(payload: M[K]) => void> } = {};

  on<K extends keyof M>(name: K, handler: (payload: M[K]) => void): () => void {
    (this.handlers[name] ??= []).push(handler);
    return () => { … };                       // unsubscribe
  }

  emit<K extends keyof M>(name: K, payload: M[K]): void {
    this.handlers[name]?.forEach(h => h(payload));
  }
}

Why each decision: M is a map type rather than a union, so keyof M gives the event names and M[K] gives the matching payload — the keyof/indexed-access pairing doing the real work. on and emit are generic in K rather than the class being generic per event, so one emitter handles all events. The handler is a function-typed property, so its parameter is checked contravariantly (lesson 3) rather than bivariantly. And on returns an unsubscribe function, because an emitter whose listeners cannot be removed is a leak.

What I would not do: accept string for the name, which loses the whole benefit; make the payload optional, which forces every handler to check; or use overloads per event, which does not scale past a handful.

The honest limitation: none of this survives the boundary. If events arrive from a WebSocket, the payload is unverified data and the emitter's types are a claim — so the parse happens where the message enters, and the emitter is used inside that boundary.

5 (hard): Type a state store so keys and values stay related.
Solution 
class Store<T extends object> {
  private listeners = new Set<(state: Readonly<T>) => void>();
  constructor(private state: T) {}

  get<K extends keyof T>(key: K): T[K] { return this.state[key]; }

  set<K extends keyof T>(key: K, value: T[K]): void {
    this.state = { ...this.state, [key]: value };
    this.listeners.forEach(l => l(this.state));
  }

  update(patch: Partial<T>): void { … }
  subscribe(l: (state: Readonly<T>) => void): () => void { … }
}

const store = new Store({ count: 0, user: "ana", admin: false });
store.get("count");            // number
store.set("count", 1);         // ✔
store.set("count", "one");     // error: 'string' is not assignable to 'number'
store.set("nope", 1);          // error: '"nope"' is not assignable to the key union

// the memoize signature, written out
function memoize<A extends readonly never[], R>(fn: (...args: A) => R): (...args: A) => R {
  const cache = new Map<string, R>();
  return (...args: A): R => {
    const key = JSON.stringify(args);
    if (!cache.has(key)) cache.set(key, fn(...args));
    return cache.get(key)!;
  };
}
const fast = memoize((a: number, b: string) => a + b);
fast(1, "x");        // ✔ parameters and return preserved exactly
fast("x", 1);        // ✔ error — the wrapped signature is enforced

The pattern in the decisions: generalise when a caller's type must travel through the function, tighten with literal unions when the problem is a loose primitive, and delete the parameter when it only appears once. "Might be useful later" is not on the list.

🎯 Key Takeaways

  • A generic relates types; any discards them — that is the whole difference.
  • A type parameter should appear at least twice, or it is unknown with extra syntax.
  • parse<T>(json): T is an assertion in disguise; take a validator instead.
  • Inference flows from arguments, not from the assignment target (TS2322 at the assignment).
  • Supply the type argument explicitly when there is nothing to infer from, such as an empty array.
  • Contextual typing is the exception: callback parameters do get types from the expected signature.
  • extends both rejects bad calls and unlocks members inside the body.
  • K extends keyof T with a T[K] return gives key-safe access and the exact property type.
  • <const T> preserves literals — readonly ["a", "b"] instead of string[].
  • Default type arguments help callers; a default of any silently disables checking.
  • Generics are erased: no new T(), no instanceof T — pass a factory.
  • Function as a constraint types nothing; use (...args: never[]) => unknown.
  • Deeply nested generics cost readable errors and compile time.
  • Parameterise the method, not the class, when only one member needs the type.
  • Generalise on the second caller, not in anticipation of one.
