Branded Types Correctness at the Boundary

What you'll master: how to make two types that are structurally identical incompatible — UserId and OrderId are both strings, and mixing them up is a real bug the compiler will happily allow; the intersection-with-a-phantom-property technique and the unique symbol variant; the one-way assignability that makes brands usable; the smart constructor, which confines the single as to one audited function and is what connects branding to the validation from lesson 11; and the limits, honestly measured — arithmetic strips a brand, and adding Cents to Meters compiles. Prerequisites: Structural Typing & Variance, Runtime Validation.

Part 1 — The Problem Structural Typing Cannot See

TypeScript compares shapes. Two types that are both string are the same type, whatever you called them.

type UserId  = string;
type OrderId = string;

declare function cancelOrder(id: OrderId): void;
declare const userId: UserId;

cancelOrder(userId);        // ✔ compiles — and cancels nothing, or the wrong thing

Validated vs unvalidated emailstringBad data stored
Seconds vs millisecondsnumberTimeouts 1000× off

A type alias does not help, because an alias is a name for a type and not a new type. What is needed is nominal typing — identity by declaration rather than by shape — which TypeScript does not have and which brands simulate.

Part 2 — The Brand

Intersect the underlying type with an object carrying a property that exists only at the type level.

type UserId  = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };

// verified with tsc 7.0.2
declare const uid: UserId;

const s: string = uid;          // ✔ compiles — a UserId IS a string
const u: UserId = "raw";
// error TS2322: Type 'string' is not assignable to type 'UserId'.
const x: OrderId = uid;
// error TS2322: Type 'UserId' is not assignable to type 'OrderId'.
//   Types of property '__brand' are incompatible.
//     Type '"UserId"' is not assignable to type '"OrderId"'.
🔑 The assignability is deliberately one-way. A UserId can be used anywhere a string is expected — so it prints, concatenates and goes into a Map key without ceremony — but a bare string cannot become a UserId. That asymmetry is the entire mechanism: it is easy to widen and impossible to narrow by accident.

No property called __brand ever exists at runtime. The type says the value has it, no value ever does, and since types are erased nothing ever checks. That is why it is called a phantom property.

A unique symbol is the stricter variant, because the key cannot be written by accident elsewhere:

declare const brand: unique symbol;
type Email = string & { readonly [brand]: "Email" };

const e: Email = "a@b.com";
// error TS2322: Type 'string' is not assignable to type 'Email'.   ◄── verified
TechniqueCollision riskReadability of errors
{ __brand: "Name" }Low — the literal differsGood: the literals are named
{ [sym]: "Name" }NoneSlightly noisier
enum member as the brandNoneDrags in a runtime value
A private class fieldNoneReal nominal typing, but a real class

Part 3 — The Smart Constructor

A brand only has value if it cannot be created carelessly. The pattern is a single function that validates and performs the one assertion, exported alongside the type.

declare const brand: unique symbol;
export type Email = string & { readonly [brand]: "Email" };

export function toEmail(raw: string): Email {
  if (!raw.includes("@")) throw new TypeError(`not an email: ${raw}`);
  return raw as Email;               // the ONLY `as` in the program for this type
}

export function isEmail(raw: string): raw is Email { return raw.includes("@"); }

This is where branding and validation meet. Lesson 11 established that external data enters as unknown and leaves through a check; a brand records in the type system that the check happened. A function taking Email rather than string cannot be called with an unvalidated value — not by convention, but because the only route to an Email runs through toEmail.

ExportPurpose
The branded typeWhat consumers annotate with

The discipline that makes it work is keeping the type and its constructor in one module, and treating as Email anywhere else as a defect in review. The compiler cannot enforce that — "anything" as Email compiles anywhere — so it is a convention, but a convention with exactly one thing to look for.

Part 4 — What a Brand Does Not Survive

This is the part that is usually left out, and it decides whether branding is worth it for a given type.

// verified with tsc 7.0.2
declare const uid: UserId;
const up = uid.toUpperCase();      // string — NOT UserId. The brand is gone.

type Cents  = number & { readonly __brand: "Cents" };
type Meters = number & { readonly __brand: "Meters" };
declare const c: Cents;
declare const m: Meters;

const sum = c + c;                 // number — arithmetic strips the brand
const mixed = c + m;               // ✔ COMPILES — adding cents to metres is fine

+, * and the rest operate on the number side of the intersection and produce a plain number. So a branded number protects the boundaries of a calculation — what goes into a function and what comes out — and nothing inside it. That is a much weaker guarantee than people expect when they reach for units.

Collection methods behave better, because they are generic in the element type:

const arr: Cents[] = [c];
arr.map(x => x);        // Cents[]   ◄── verified
arr.filter(x => x > 0); // Cents[]   ◄── verified
OperationBrand survives?
Passing to a function, returningYes
map identity, filterYes
Storing in Cents[], Map<K, Cents>Yes
str.toUpperCase(), slice, template literalsNo — plain string
a + b, a * 2No — plain number
JSON.parse round tripNo — erased, so nothing to restore

❌ Branding numbers to prevent unit mix-ups in calculations. It looks like the textbook use — Meters and Feet can never be confused again — and it does not work: c + m compiles with no error, and the result of any arithmetic is a plain number that has to be re-branded by hand. The protection covers function signatures and stops at the first +.

✅ Either accept that the brand guards the boundary only, or use a wrapper object. Branding is still worthwhile for a value that is passed around far more often than it is computed with — a timestamp in milliseconds, a currency amount in cents that is stored and displayed rather than summed in twenty places. When the arithmetic itself must be safe, a real value object ({ amount: number; currency: "USD" } with add and times methods) is the honest tool, and costs allocation rather than nothing.

Part 5 — Where Branding Pays

The deciding question is the ratio of passing to computing. An id is passed through dozens of signatures and never added to anything, so a brand catches real mistakes at every one of them. A measurement that is multiplied and summed loses its brand at the first operation, so the same technique buys far less.

The template literal row is worth understanding precisely: `user_${string}` constrains the shape of the string, so any literal matching the pattern is assignable. That is useful — it catches an order key passed where a user key belongs — but it says nothing about whether the value was validated, which is the property a brand records.

Interview Questions

Beginner: Why does type UserId = string not stop you passing an order id?

Because a type alias is a name for a type, not a new type. UserId and OrderId both resolve to string, so as far as the compiler is concerned they are the same type and fully interchangeable.

That follows from TypeScript being structural: compatibility is decided by shape, not by declaration. It is the behaviour you want almost everywhere — it is why an object literal satisfies an interface without declaring that it implements it — and it is exactly wrong for domain distinctions, where two values have identical shapes and completely different meanings.

The languages that catch this are nominal: a UserId in Java or Rust is a distinct type because it was declared as one. TypeScript has no such mechanism, so the technique is to simulate it by making the shapes genuinely differ.

The cost of the gap is real: mixing up two id types touches the wrong record, and cents against dollars is wrong by a factor of a hundred. Both compile without a warning.

Beginner: How does a branded type work?

You intersect the underlying type with an object type carrying a property that never exists at runtime: type UserId = string & { readonly __brand: "UserId" }. The property is phantom — no value ever has it, and since types are erased nothing ever looks.

What this buys is that the shapes now differ. I verified the three assignability results: a UserId is assignable to string, so it prints and concatenates freely; a plain string is not assignable to UserId; and a UserId is not assignable to OrderId, with the error naming the mismatched brand literals.

The one-way direction is what makes it usable rather than merely strict. Widening is free, so branded values work with every existing string API, and narrowing is impossible by accident, which is where the bugs were.

The cost is zero at runtime — the intersection is entirely a compile-time construct, and the emitted JavaScript is the same as for a plain string.

Mid: What is a smart constructor and why does it matter?

It is the single exported function that validates a raw value and performs the one assertion that creates a branded value: function toEmail(raw: string): Email, throwing if the check fails and returning raw as Email if it passes.

It matters because a brand with no gatekeeper is decoration. Nothing in the compiler stops "nonsense" as Email anywhere in the program, so the guarantee is only as strong as the convention that the assertion lives in one place. Confining it to one function makes that convention enforceable in review — there is exactly one thing to grep for.

It is also where branding connects to validation. Lesson 11's rule is that external data enters as unknown and leaves through a real check; a brand records in the type that the check happened. A function whose parameter is Email rather than string cannot be called with unvalidated input, because the only route to an Email runs through the validator.

I would export the type, a throwing constructor, and a predicate or Result-returning variant — and specifically not an unsafeAsEmail escape hatch, because once one exists it becomes the path of least resistance and the brand stops meaning anything.

Mid: What are the limits of branded types?

The one that surprises people is that operations strip the brand. uid.toUpperCase() returns a plain string, and arithmetic on a branded number returns a plain number — I verified both.

Worse for the unit-safety use case, mixing brands in arithmetic compiles. With Cents and Meters both branded, c + m produces no error at all, because + operates on the number side of the intersection. So a branded number guards what goes into and comes out of a function, and nothing inside it.

Collections behave better — I verified that map with an identity function and filter both preserve Cents[], since those methods are generic in the element type.

The other limits are that nothing survives serialisation, because the brand is erased and there is nothing to restore, so a value coming back from JSON.parse must be re-validated; and that as Brand works anywhere, so the whole scheme rests on a convention rather than on the compiler. If arithmetic itself must be safe, a wrapper object with plus and times methods is the honest alternative, paying allocation for a guarantee that actually holds.

Senior: A team wants to brand every domain type. What is your advice?

I would push for branding a short list and leaving the rest alone, because the technique's cost is spread across every call site while its benefit is concentrated in a few genuinely confusable types.

The test I would apply is the ratio of passing to computing. An entity id is threaded through dozens of signatures and never participates in arithmetic, so a brand catches real mistakes everywhere it appears and loses nothing. A measurement that is summed and scaled loses its brand at the first operator, so the same ceremony buys much less — and as I verified, adding two differently-branded numbers does not even error.

The costs of branding everything are concrete: every literal needs a constructor call, every test fixture needs one, error messages grow an intersection type that obscures the real mismatch, and developers who meet resistance reach for as Brand — at which point the guarantee is gone but the ceremony remains, which is the worst outcome available.

My list would be: entity ids where more than one kind flows through the same functions; values whose validity was established by a check worth recording, such as a verified email or a parsed URL; and anything where confusion is a security issue, escaped versus raw HTML being the clearest case. Money I would brand only for storage and transport, and compute with a value object.

Recommendation: brand that list, colocate each type with its smart constructor, ban as Brand outside those modules in review, and skip everything else. If the team later finds a class of bug the list missed, add that type — but drive it from bugs rather than from symmetry.

Senior: Design an id-branding scheme for a service with twenty entity types.

At twenty types the thing that decides success is whether the scheme is mechanical, because anything requiring twenty hand-written blocks will be inconsistent within a month.

One generic brand helper, one factory. A single type Brand<T, N extends string> = T & { readonly __brand: N }, then type UserId = Brand<string, "UserId"> per entity, with a shared makeIdType<N>() returning the validator, predicate and parser for that brand. Adding an entity becomes two lines, which is the only way consistency survives.

Then decide where ids get created, which is the part teams skip. Ids enter from three places: generated locally, read from the database, and arriving in a request. Generation and request parsing both go through the constructor. Database rows are the interesting case — I would brand at the repository layer, so the mapping from row to entity is the one place the assertion happens, rather than asserting at every query site.

Watch the error-message cost at this scale. Intersection types make mismatches verbose, and with twenty brands a wrong argument produces a message where the real information — two brand literals differing — is buried. Naming each type and keeping the brand property short helps materially, and it is worth checking what a typical error actually looks like before committing.

Recommendation: a generic Brand helper, a per-entity module exporting the type and its constructors, branding applied at the three entry points and nowhere else, a lint rule for as *Id outside those modules, and no brands on anything that gets computed with. Roll it out to the two or three entity pairs that have actually been confused first — if that catches nothing in a month, the remaining seventeen are not worth the migration.

🎯 Key Takeaways

  • A type alias creates no new type — UserId and OrderId are both string.
  • TypeScript has no nominal typing; brands simulate it by making shapes differ.
  • A brand is an intersection with a phantom property that no value ever has.
  • Assignability is one-way: branded → base is free, base → branded is an error.
  • A unique symbol brand cannot collide with a key written elsewhere.
  • A brand with no gatekeeper is decoration — the smart constructor is the pattern.
  • Confine as Brand to one module and treat it as a defect elsewhere.
  • Never export an unsafeAsX — it becomes the path of least resistance.
  • String and number operations strip the brand — toUpperCase, +, *.
  • Cents + Meters compiles — branded numbers do not guard arithmetic.
  • map and filter preserve brands, being generic in the element type.
  • Nothing survives JSON — re-validate on the way back in.
  • Brand what is passed, not what is computed with.
  • A wrapper object is the honest tool when arithmetic must be safe — it costs allocation.
  • A template literal type checks format, not provenance — different guarantee.
