Patterns That Hold Up Scale & Migration

What you'll master: the handful of patterns worth applying everywhere, and the judgement to tell them from cleverness — exhaustiveness checking with never, which turns "someone added a variant and forgot a case" into a compile error naming the variant; as const satisfies, which keeps literal precision and validates the shape, verified both ways; parse, don't validate, tying lessons 11 and 13 into one rule; making illegal states unrepresentable with discriminated unions instead of optional flags; deriving types from a single source of truth; and a decision table covering the whole track. Prerequisites: the rest of this track.

Part 1 — Exhaustiveness With never

If one pattern is worth taking from this track, it is this. Assigning the narrowed value to never in the default branch makes a missing case a compile error.

type Shape =
  | { kind: "circle"; r: number }
  | { kind: "square"; s: number }
  | { kind: "tri"; b: number; h: number };      // ← added later

function area(sh: Shape): number {
  switch (sh.kind) {
    case "circle": return Math.PI * sh.r ** 2;
    case "square": return sh.s ** 2;
    default: {
      const _never: never = sh;
      throw new Error(`unhandled: ${JSON.stringify(_never)}`);
    }
  }
}

$ npx tsc p1.ts --noEmit --strict
p1.ts(7,22): error TS2322: Type '{ kind: "tri"; b: number; h: number; }'
             is not assignable to type 'never'.            ◄── verified, and it names the case
🔑 The error names the exact variant that was forgotten. Adding a member to the union produces a compile error at every place that switches on it, listing what is missing — which is the difference between a type system that documents and one that enforces. The runtime throw is there for values that arrive from outside the program, where the type was a claim.

Part 2 — as const satisfies

Lesson 2 covered satisfies and lesson 6 covered as const. Together they solve a problem neither solves alone: keeping literal types while still validating the shape.

// verified with tsc 7.0.2 — three variants, three different outcomes

// 1. annotation — shape checked, ALL precision lost
const a: Record<string, { path: string; auth: boolean }> = { home: { path: "/", auth: false } };
keyof typeof a        // string          ◄── the key names are gone

// 2. satisfies alone — keys kept, values widened
const b = { home: { path: "/", auth: false } } satisfies Record<string, { path: string; auth: boolean }>;
keyof typeof b        // "home"
typeof b.home.path    // string          ◄── the value widened

// 3. as const satisfies — everything kept, shape still checked
const c = { home: { path: "/", auth: false }, admin: { path: "/admin", auth: true } }
  as const satisfies Record<string, { path: string; auth: boolean }>;
typeof c.home.path                              // "/"              ◄── literal
typeof c[keyof typeof c]["path"]                // "/" | "/admin"   ◄── a usable union

And the validation still works — it is not merely decorative:

const bad = { home: { path: "/", auth: "yes" } }
  as const satisfies Record<string, { path: string; auth: boolean }>;
// error TS2322: Type 'string' is not assignable to type 'boolean'.   ◄── verified

satisfies TYesYesNo

This is the default for any configuration object — route tables, feature flags, theme tokens, column definitions. The derived union typeof c[keyof typeof c]["path"] cannot drift from the data, which is the property that makes it worth the syntax.

Part 3 — Parse, Don't Validate

Lessons 11 and 13 are one rule: a check should produce a value with a different type, not a boolean that the caller has to remember.

// ✘ validate: returns a boolean; the type is unchanged, so nothing downstream knows
function isValidEmail(s: string): boolean { … }
if (isValidEmail(input)) sendTo(input);          // sendTo takes a plain string — no guarantee

// ✔ parse: returns a different type, so the guarantee travels
function toEmail(s: string): Email { … }         // Email is branded — lesson 13
sendTo(toEmail(input));                          // sendTo takes Email; it cannot be called wrong
BoundaryParse intoFrom lesson
HTTP bodyA schema-derived type11
A validated stringA branded type13
Environment variablesA parsed config object, at startup11
An untyped dependencyA wrapper with honest signatures16
A caught valueA narrowed Error subclass12

The test is whether the guarantee survives being passed to another function. A boolean check guarantees something only within the if that called it; a parse produces a value whose type carries the guarantee everywhere it goes. That is why Email beats string plus a convention, and why a schema beats a hand-written predicate.

Part 4 — Make Illegal States Unrepresentable

// ✘ four boolean-ish fields — 16 combinations, 4 of them meaningful
interface State {
  loading: boolean;
  data?: User;
  error?: Error;
}
// what does { loading: true, data: user, error: err } mean?

// ✔ a discriminated union — exactly the states that exist
type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: User }
  | { status: "error"; error: Error };
Optional-flag versionUnion version
Impossible combinations compileThey cannot be written
Every read needs a checkdata exists exactly where it is valid
Adding a state adds a flagAdding a state breaks every switch
No exhaustiveness possiblePart 1's check applies
data! everywhereNo assertions needed

The count is the argument: three optional fields is eight representable states for four real ones, and every consumer has to know which four. The union has no invalid state to handle, so the code that reads it has no defensive branches — and the exhaustiveness pattern from Part 1 then makes adding a fifth state a compile error rather than a code review question.

❌ Adding a boolean for each new condition. It is the smallest diff at every step, which is exactly why it happens: loading, then refreshing, then stale, then optimistic. Four booleans is sixteen representable states, of which perhaps five are real, and no single place in the codebase documents which. Every component then reimplements a slightly different guess, and the bugs are the disagreements between those guesses.

✅ Add a variant to a discriminated union instead. The diff is larger — every switch fails to compile until it handles the new case — and that is the entire value: the compiler produces the list of places that need a decision, naming each one. A bigger diff you did not have to find beats a one-line diff plus an unbounded search.

Part 5 — One Source of Truth

The recurring test across this whole track: does the type derive from something, or does it restate it?

// the schema is the source; the type follows                        — lesson 11
const User = z.object({ id: z.string(), role: z.enum(["admin", "user"]) });
type User = z.infer<typeof User>;

// the data is the source; the union follows                         — Part 2
const ROUTES = { home: "/", admin: "/admin" } as const satisfies Record<string, string>;
type RouteName = keyof typeof ROUTES;                 // "home" | "admin"

// the model is the source; form state follows                       — lesson 8
type FormState<T> = { [K in keyof T]: { value: T[K]; touched: boolean; error?: string } };

// the union is the source; the handler table follows                — lesson 9
type Handlers = Record<State["status"], (s: State) => void>;

Both live in the same layerThe type is a contract with someone else
Drift would be a bugDrift would be a deliberate version change

Lesson 9's warning is the boundary case worth restating: deriving a DTO from a database model with Omit defaults to exposure, so a new column leaks without failing a build. Derive inside a layer; declare at the edge.

The through-line is that the type system is good at relationships and blind to values. Every pattern here works by encoding a relationship — between a key and a value, a state and its data, a check and its result — so the compiler can enforce it. Every failure in this track came from expecting types to know something about a value they had never seen: a JSON.parse, a lying predicate, a const enum compiled by another tool, a promise nobody held.

Interview Questions

Beginner: How do you make the compiler catch a missing switch case?

Assign the narrowed value to never in the default branch. Once every case has been handled, the value's type in that branch is never and the assignment is legal; if a case is missing, the remaining member is not assignable to never and you get an error.

I verified it with a three-member Shape union where only two cases were handled: the error was TS2322, "Type '{ kind: "tri"; b: number; h: number; }' is not assignable to type 'never'" — so it names the exact variant that was forgotten.

The value is in what happens later. Adding a member to the union produces an error at every place that switches on it, with a list of what each one is missing. Without the check, a default that returns a fallback is silently wrong and a default that throws fails in production.

I keep the runtime throw as well as the type check, because the compile-time guarantee only covers values the program created. A tag arriving from outside — parsed JSON, a database row — can be anything, so the throw is the honest handling for that case.

Beginner: Why as const satisfies T rather than one or the other?

Because each one alone gives up something you want, and together they give up nothing.

An annotation validates the shape and destroys all precision — I verified that const a: Record<string, …> makes keyof typeof a just string, so the key names are gone. satisfies alone keeps the keys but the values widen: typeof b.home.path was string, not "/". as const alone keeps everything and validates nothing.

as const satisfies T keeps both: I verified typeof c.home.path as "/", and the derived union typeof c[keyof typeof c]["path"] as "/" | "/admin". And the validation still runs — an object with auth: "yes" gave TS2322, "Type 'string' is not assignable to type 'boolean'".

So it is the right default for any configuration object: route tables, feature flags, theme tokens. The point is not the syntax but the derived union, which cannot drift from the data it came from.

Mid: What does "make illegal states unrepresentable" mean concretely?

It means choosing a type whose inhabitants are exactly the valid states, rather than a type that can express invalid ones and relying on convention to avoid them.

The standard example is a fetch state modelled as { loading: boolean; data?: User; error?: Error }. That is eight representable combinations for four real states, and nothing says what { loading: true, data: user, error: err } means. Every consumer has to know which combinations are real, and the bugs are the places where two consumers guessed differently.

The union version — { status: "idle" } | { status: "loading" } | { status: "success"; data: User } | { status: "error"; error: Error } — has no invalid inhabitant. data exists exactly where it is meaningful, so there are no non-null assertions and no defensive branches, and narrowing on status gives each branch the right fields.

It also composes with exhaustiveness: adding a fifth state breaks every switch with a never check, so the compiler produces the list of places needing a decision. The optional-flag version cannot do that at all, which is why the pattern is worth the larger initial diff.

Mid: When should a type be derived, and when declared?

Derive when both types live in the same layer and drift between them would be a bug. Declare when the type is a contract with someone else and a change should be deliberate.

Derivation is right for: form state from a model, a handler table from a union of states, test fixtures from an entity, a type from a validation schema. In each case the whole point is that a change to the source propagates — adding a field to the model should break the code that must handle it.

Declaration is right for API DTOs and public signatures, and lesson 9's argument is the sharpest version: type UserDto = Omit<UserModel, "passwordHash"> is correct today and silently exposes internalNotes the moment someone adds that column. Derivation defaults to exposure; an explicit declaration defaults to omission and makes additions a reviewable diff.

The test I apply is to ask what the right behaviour is when the source gains a field. If the answer is "everything downstream should have to handle it", derive. If it is "nothing should change until someone decides", declare. That single question resolves nearly every case, including the ones where the convenient answer and the correct answer differ.

Senior: Which of these patterns would you require on a team, and which would you leave to judgement?

I would require the ones with a cheap, mechanical test and leave to judgement the ones that need a cost estimate — because a rule nobody can apply consistently becomes noise in review.

Required, because they are checkable: exhaustiveness via never on any switch over a union, since the alternative fails in production and the pattern is four lines; unknown plus a parse at every boundary, with as on external data treated as a defect; discriminated unions rather than optional flags for state, which is the single highest-value modelling decision; and as const satisfies for configuration objects. Each is a yes/no question a reviewer can answer without knowing the domain.

Left to judgement, because they trade cost against benefit: branded types, which I would restrict to a short list of genuinely confusable values — lesson 13 measured that they do not guard arithmetic at all, and branding everything produces ceremony that people route around with as. Generics, which need the "does the parameter appear twice" test rather than a rule. Result versus throw, which depends on whether a caller has a real decision. And anything involving conditional or mapped types, where the question is whether it removes a drift hazard or adds a maintenance one.

Actively discouraged: conditional return types on public APIs, deep inheritance, speculative generics, and any type-level cleverness that a reviewer cannot evaluate in the time they have. Lesson 20's measurement is relevant — a nested conditional type's cost is the product of its union sizes, so cleverness has a build-time price that grows with the domain.

Recommendation: put the four required patterns in a short written guide with one example each, enforce the flags and lint rules from lessons 10 and 19 in CI so the mechanical parts are not a review burden, and keep the judgement list explicitly a judgement list. The goal is that reviews spend their attention on domain modelling rather than on re-litigating whether a helper should be generic.

Senior: What is the honest summary of what TypeScript's type system does and does not give you?

It gives you enforced relationships within the program, and it gives you nothing about values it has not seen. Almost every failure in this track is an instance of the second half.

What it genuinely delivers: a key implies a value type, a state implies its data, a check implies a narrowed type, an input type implies an output type. Those relationships are checked across the whole program, every build, for free at run time — and they are what makes a large refactor possible at all, because the compiler produces the list of places that need to change.

What it cannot do, with the concrete cases: it cannot verify data — JSON.parse returns any and a type predicate's body is never checked, so a program can type-check under full strict mode and throw TypeError immediately. It cannot see runtime behaviour — a circular import type-checks and then throws ReferenceError, and arr.forEach(async …) is perfectly typed and awaits nothing. It cannot enforce anything after erasure — private fields serialise into JSON, brands vanish, and business rules encoded in types are documentation. And it does not model the build — two tools compiling the same const enum produced incompatible output and a runtime SyntaxError.

So the practical stance is a boundary discipline. Parse at every edge so the interior is trustworthy; use strict flags plus the two lint rules that cover what types structurally cannot; and spend the type system's budget on modelling — unions that cannot express invalid states, derived types that cannot drift — rather than on type-level programming that impresses reviewers and costs build time.

Recommendation: judge a type by whether it prevents a mistake someone actually made. A union that makes an impossible state unwritable pays for itself the first time a variant is added; a six-deep conditional type usually pays for nothing and bills you at every build. That test is the most useful thing to take from the whole track.

type User = z.infer<typeof User>;

export async function getUser(id: UserId): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new UpstreamError(`users/${id} -> ${res.status}`, res.status);
  return User.parse(await res.json());          // unknown in, User out
}

export async function processAll(ids: readonly UserId[]): Promise<void> {
  const users = await Promise.all(ids.map(getUser));
  users.forEach(save);
}

Five defects, none of which the compiler reported on the original — the any made everything downstream unchecked, and the forEach was correctly typed. That is the track's thesis in one function: strict flags make the interior trustworthy, and the boundary needs a parse plus lint rules for what types structurally cannot see.

🎯 Key Takeaways

  • Assign to never in the default branch — the error names the forgotten variant.
  • Keep the runtime throw too — external tags were never checked by the compiler.
  • as const satisfies T keeps keys and value literals and validates the shape.
  • An annotation loses both; satisfies alone loses the values; as const alone validates nothing.
  • Parse, don't validate — a check should produce a value of a different type.
  • A boolean check's guarantee stops at the if; a parsed type travels everywhere.
  • Discriminated unions over optional flags — three optionals is eight states for four.
  • A data! after flag checks means the state type can express the impossible.
  • Adding a variant should break every switch — that list is the benefit.
  • Derive inside a layer; declare at a boundary — derivation defaults to exposure.
  • Ask what should happen when the source gains a field — that answers derive-or-declare.
  • The type system enforces relationships and knows nothing about values.
  • Every failure in this track was that second half — any, a lying predicate, a cycle, a floating promise.
  • Strict flags make the interior trustworthy; a parse makes the boundary trustworthy.
  • Judge a type by whether it prevents a mistake someone actually made.
