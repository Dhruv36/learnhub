Runtime Validation Correctness at the Boundary

What you'll master: why a fully strict program still throws type errors — every value entering from outside arrives as any or an unverified claim; unknown as the correct entry type and why as is not validation; type predicates, and the fact that the compiler never checks their bodies — a predicate that lies compiles clean and crashes at runtime, demonstrated here end to end; assertion functions and the TS2775 rule that catches people; schema libraries that produce one definition and two artefacts, a validator and a type; and where to put the boundary so validation happens once rather than everywhere. Prerequisites: Strictness Flags.

Part 1 — Where Strict Mode Stops

The previous lesson's flags verify that the program is consistent with what it claims. They cannot verify that the claims are true, and at every boundary the claims are guesses.

const parsed = JSON.parse('{"id": 42}');    // parsed: any   ◄── verified
const user = parsed as User;                 // a claim, checked by nobody
user.id.toUpperCase();                       // compiles; throws

🔑 any is the mechanism, and it is silent. One any entering a strictly-typed program flows through every downstream check without producing a single error, which is how a codebase can be "100% strict" and still be unchecked along its most important path. That is not a gap in strict mode — strict mode is doing exactly what it promised.

Part 2 — unknown In, Typed Value Out

The discipline is one rule: external data enters as unknown, and the only way out of unknown is a check the compiler can see.

// ✘ the assertion route
const user = JSON.parse(body) as User;          // zero runtime checking

// ✔ the parse route
const raw: unknown = JSON.parse(body);
if (!isUser(raw)) throw new BadRequest("malformed user");
raw.id.toUpperCase();                            // raw is User here, and it really is

satisfies does not help here either. It checks a literal you wrote against a type at compile time; it has no opinion about a value that arrived over the network, and like everything else it is erased.

Part 3 — Type Predicates, and What the Compiler Does Not Check

A type predicate — v is User — turns a boolean function into a narrowing tool. It is the standard hand-written validator, and it has one serious property.

interface User { id: string; age: number }

// this compiles with NO error under full strict mode
function isUserBad(v: unknown): v is User {
  return typeof v === "object" && v !== null;      // checks almost nothing
}

The compiler does not verify that the body establishes the claim. v is User is a promise, and the promise is accepted at face value. Here is the whole consequence, start to finish:

const raw: unknown = JSON.parse('{"id": 42}');
if (isUserBad(raw)) {
  console.log(raw.id.toUpperCase());     // the compiler is certain this is a string
}

$ npx tsc crash.ts --target es2022 --module commonjs
                                         ◄── compiles clean, no errors
$ node crash.js
TypeError: raw.id.toUpperCase is not a function      ◄── verified

An honest predicate has to do the work property by property:

function isUser(v: unknown): v is User {
  return typeof v === "object" && v !== null
    && "id" in v && typeof (v as { id: unknown }).id === "string"
    && "age" in v && typeof (v as { age: unknown }).age === "number";
}
Hand-written predicatesCost
Verbose for anything nestedGrows faster than the type

The drift problem is the one that gets teams, because it is silent in the direction that matters: add email: string to User and isUser keeps compiling, keeps returning true, and now certifies objects with no email as User.

Part 4 — Assertion Functions

asserts v is T narrows for the rest of the scope instead of inside an if, which suits a boundary where failure means throwing anyway.

function assertUser(v: unknown): asserts v is User {
  if (!isUser(v)) throw new TypeError("not a User");
}

declare const raw: unknown;
assertUser(raw);
raw.id;          // User from here on   ◄── verified

They carry a rule that produces a confusing error the first time you hit it:

const assertAlias = assertUser;
assertAlias(raw2);
// error TS2775: Assertions require every name in the call target to be declared
//               with an explicit type annotation.                     ◄── verified

Control-flow analysis has to know statically that the call is an assertion, so the callee needs an explicit type annotation — const assertAlias: typeof assertUser = assertUser. The same applies to assertion methods reached through an object whose type is inferred.

Part 5 — Schema Libraries: One Definition, Two Artefacts

The drift problem disappears if the type and the validator come from the same declaration. That is what schema libraries do — the examples here use Zod 4, verified locally, but the shape is the same for Valibot, ArkType or io-ts.

import { z } from "zod";

const User = z.object({
  id: z.string(),
  age: z.number(),
  tags: z.array(z.string()).optional(),
});

type User = z.infer<typeof User>;
// { id: string; age: number; tags?: string[] | undefined }    ◄── verified

Adding a field to the schema changes the type, and every place that must handle it fails to compile. That is the property a hand-written predicate cannot have.

// throwing form
const user = User.parse(raw);        // { id: string; age: number; tags?: string[] }

// result form — a discriminated union, so the error case cannot be skipped
const r = User.safeParse(raw);       // ZodSafeParseResult<User>   ◄── verified
if (r.success) {
  r.data;      // User
} else {
  r.error;     // ZodError<User> — which field, what was expected
}
ConcernHand-written predicateSchema
Type and check stay in syncNo — silent driftYes, by construction
Error detailA booleanPath, expected, received
Nested and recursive shapesPainfulComposed
Transformation and defaultsSeparate codePart of the schema
Bundle sizeNothingReal — measure it
Right choice forOne or two small stable shapesAnything that evolves

❌ Declaring the interface and the schema separately. Writing interface User { … } alongside const UserSchema = z.object({ … }) reintroduces exactly the drift the schema was meant to remove: the two are only related by the author's intention, so adding email to the interface leaves the schema silently accepting payloads without it, and nothing anywhere fails.

✅ Derive the type from the schema — type User = z.infer<typeof User>. One declaration, one source of truth, and a change to the schema propagates into every consumer as a compile error. When an existing interface must stay, invert the direction instead: keep the interface and assert the schema satisfies it, so a mismatch is a build failure rather than a runtime surprise.

Part 6 — Where the Boundary Goes

Validation is worth its cost when it happens once, at a place data enters, and everything inside that line can then be trusted. Scattered validation is the worst of both worlds: the runtime cost of checking everywhere and the confidence of checking nowhere.

HTTP request bodyYes, always400 with the field path
HTTP response from a third partyYesFail the operation; log the payload shape
Environment variablesYes, at startupExit — crash early, not on first use
Config filesYes, at startupExit with the path and reason
localStorage / cookiesYesDiscard and reset to default

Function calls inside a moduleNoThe type system covers this

Failure handling differs by boundary in a way that matters. A bad request body is the caller's fault and deserves a 400 naming the field. A bad third-party response is an outage and deserves a log with enough detail to file a bug against them. Bad config at startup should stop the process rather than produce a service that fails on its first real request. Treating all three the same — usually as a generic 500 — throws away the information the validator just produced.

Interview Questions

Beginner: Why is JSON.parse(body) as User unsafe?

Because neither half does any checking. JSON.parse returns any — I verified its result is assignable to anything at all — and as User is an assertion, which tells the compiler to stop asking questions rather than verifying anything.

The result is a value the compiler treats as a fully known User and that may be a number, an array, null, or an object with entirely different fields. The mismatch surfaces later, wherever a property is first used, as an error that points at innocent code rather than at the boundary.

Both parts are erased at build time, so there is no runtime cost — and no runtime effect. The assertion produces exactly zero JavaScript.

The fix is to receive it as unknown and pass it through a check the compiler can see, whether that is a type predicate or a schema parse. Then the type is earned rather than claimed.

Beginner: What is a type predicate, and what does the compiler check about it?

A type predicate is a function whose return type is written v is T instead of boolean. When it returns true, the compiler narrows the argument to T inside that branch.

What the compiler checks is almost nothing. It does not verify that the body establishes the claim — I confirmed that function isUser(v: unknown): v is User { return typeof v === "object" && v !== null } compiles with no error under full strict mode, despite checking none of User's properties.

The consequence is a program that compiles cleanly and throws. Feeding it JSON.parse('{"id": 42}') and then calling raw.id.toUpperCase() gives TypeError: raw.id.toUpperCase is not a function at runtime, with no compile-time warning anywhere.

So a type predicate is a place where the type system trusts you completely, which makes it exactly as reliable as the code inside it. That is fine for a small, stable shape and a well-tested function; it is a poor foundation for a validation layer that has to keep up with an evolving API.

Mid: Compare hand-written predicates with a schema library.

The deciding difference is not verbosity, it is whether the type and the check can drift apart.

With a hand-written predicate they are two independent pieces of code related only by intention. Adding email: string to interface User leaves isUser compiling, returning true, and certifying objects with no email. Nothing fails — the type says one thing, the check enforces another, and the gap is invisible.

With a schema, the type is derived: type User = z.infer<typeof User>. I verified that a Zod object with an optional array infers { id: string; age: number; tags?: string[] | undefined } — so a change to the schema changes the type, and every consumer that must handle the new field fails to compile.

Schemas also win on error detail. A predicate returns a boolean, so the caller cannot say which field was wrong. safeParse returns a discriminated union — verified as ZodSafeParseResult<T>, where the success branch carries the typed data and the failure branch a ZodError with paths and expected types — which is what a useful 400 response is built from.

The honest cost is bundle size, which matters in a browser and not on a server. For one or two small stable shapes I would write the predicate; for anything that evolves with an API, the schema pays for itself the first time the backend changes.

Mid: When would you use an assertion function rather than a predicate?

When failure means the operation cannot continue, so there is no second branch to write. A predicate returns a boolean and forces the caller to handle both cases; an assertion function throws, and narrows for the rest of the scope.

That suits boundaries and invariants — assertUser(body) at the top of a request handler, or assertDefined(x) where a value is genuinely guaranteed. The handler body then reads as straight-line code rather than being nested inside a check, and the failure is one throw handled by middleware.

The rule to know is TS2775: "Assertions require every name in the call target to be declared with an explicit type annotation." Calling an assertion function through an inferred alias fails, because control-flow analysis must know statically that the call asserts. Annotating the alias — const f: typeof assertUser = assertUser — fixes it.

I would use a predicate where both outcomes are ordinary — deciding which of two shapes a message is, or filtering a list — and an assertion where the failure is exceptional. The compiler checks neither body, so the choice is about how the call site reads, not about safety.

Senior: Design the validation strategy for a service with several data sources.

The principle I would hold to is that validation happens once, at a named boundary, and everything inside that line is trusted — because scattered validation costs as much as thorough validation and buys none of the confidence.

Draw the boundaries explicitly. Inbound HTTP bodies, responses from third-party APIs, environment and config at startup, anything read from browser storage, and messages between workers or tabs. Inside those, function-to-function calls are covered by the type system and need nothing. Rows from a database owned by the same service are usually a migration problem rather than a validation problem, though I would validate if the schema is shared with other writers.

One schema per boundary, types derived from it. That is the only arrangement where a change cannot silently desynchronise, and it means the parse result can be passed inward as a trusted typed value rather than re-checked.

Failure handling differs per boundary, and this is where teams lose the value. A bad request body is a 400 naming the field path. A bad third-party response is an outage — fail the operation and log the shape so someone can file the bug. Bad config exits the process at startup, so the failure happens on deploy rather than on the first real request. Collapsing all of these into a generic 500 discards the information the validator just produced.

Recommendation: schemas at the edges with derived types, one parse per boundary, per boundary failure policy, and a review rule that as on external data is a defect. Then measure the parse cost on the hot paths — it is usually negligible, and where it is not, that is a specific optimisation rather than a reason to skip validating.

Senior: Your team wants to skip validation because "the API is ours and it is typed". What do you say?

I would agree the risk is lower and still argue for validating, because the argument rests on an assumption that decays and fails silently when it does.

Shared types prove agreement at build time, not at run time. The deployed API is whatever version is actually running. A backend that shipped a change an hour ago, a client on a stale cached bundle, a rolled-back deploy, a proxy returning an HTML error page with a 200 — in every case the types matched when both sides compiled and do not match now. Validation is what converts that from a confusing downstream crash into a clear, attributable failure.

The failure mode is the real problem. Without validation, a missing field becomes undefined, flows several layers inward, and throws somewhere with no connection to its cause — or worse, does not throw and writes bad data. With validation it is one error at the boundary, naming the field, with the payload available for the bug report.

Where I would accept the trade: a browser bundle where the schema library measurably hurts load time and the endpoints are small and stable. Then I would validate the few fields the code actually branches on, rather than nothing — a cheap hand-written check at the boundary is far better than an as.

Recommendation: validate all inbound data, keep the schema as the single source for both the type and the check, and revisit only if profiling shows a real cost. Note too that a typed client generated from a spec has the same gap: it describes the contract, not the response, and generated types are assertions like any other.

🎯 Key Takeaways

  • Strict mode verifies claims, not data — every boundary is a claim.
  • JSON.parse returns any, and any passes every downstream check silently.
  • as T on external data is a lie with syntax — zero runtime effect.
  • External data enters as unknown and leaves only through a real check.
  • The compiler never checks a type predicate's body — v is T is a promise.
  • A lying predicate compiles clean and throws — verified, TypeError at runtime.
  • Hand-written predicates drift from their interface, silently, in the unsafe direction.
  • asserts v is T narrows for the rest of the scope and throws on failure.
  • Assertion calls need an explicitly annotated callee — otherwise TS2775.
  • A schema gives one declaration and two artefacts: a validator and a derived type.
  • Never declare the interface and the schema separately — that restores the drift.
  • safeParse returns a discriminated union, so the failure case cannot be skipped.
  • Validate once, at a named boundary, then trust everything inside it.
  • Validate env and config at startup so bad deploys fail immediately.
  • Failure policy differs per boundary — 400, outage, or exit; a generic 500 wastes the detail.
