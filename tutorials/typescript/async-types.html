Async Types In Practice

What you'll master: why Promise<T> describes only success and what to do about it; await and Awaited, including that await 42 keeps the literal type 42; the exact inferred types of the four combinators — Promise.all gives a tuple, not an array, and Promise.any rejects with an AggregateError carrying every failure; the void-return loophole that makes arr.forEach(async …) compile cleanly and do nothing, demonstrated at run time; floating promises, which the compiler will never report; and typing async iterables. Prerequisites: Typed Errors, Functions, Overloads & Signatures.

Part 1 — Promise<T> Describes Half the Outcome

A promise type names the value on success. There is no slot for the rejection, and no throws clause to put one in.

async function save(u: User): Promise<void> { throw new Error("db down"); }   // ✔ compiles
QuestionAnswered by the type?
What does it resolve with?Yes
Can it reject?No
With what?No
Will it ever settle?No

So everything from lesson 12 applies: the rejection arrives at catch as unknown and must be narrowed, and if the failures are part of the contract a Result<T, E> inside the promise — Promise<Result<User, NotFound>> — is what puts them in the signature.

Part 2 — await and Awaited

await on a non-promise is legal and yields the value unchanged — useful for a function that may return either a value or a promise. Awaited<T> is the type-level equivalent, and as lesson 9 covered it unwraps recursively and handles thenables, which a hand-rolled T extends Promise<infer U> ? U : T does not.

Part 3 — The Four Combinators

declare function n(): Promise<number>;
declare function s(): Promise<string>;

// verified inferred types
await Promise.all([n(), s()]);
// [number, string]                                    ◄── a TUPLE, positionally typed

await Promise.allSettled([n(), s()]);
// [PromiseSettledResult<number>, PromiseSettledResult<string>]

await Promise.race([n(), s()]);
// string | number
🔑 Promise.all on a literal array gives a tuple. That is what makes const [user, orders] = await Promise.all([getUser(), getOrders()]) type each variable correctly instead of as a union. Pass an Array variable instead of a literal and you get T[], losing the positional information — so keep the array inline at the call.

Promise.any is the one with a distinct failure type. When every input rejects, it rejects with an AggregateError:

try { await Promise.any([Promise.reject(new Error("a")), Promise.reject(new Error("b"))]); }
catch (e) { … }

// at run time — verified
any -> AggregateError 2                    ◄── e.errors.length === 2
CombinatorResolves whenRejects whenType
allAll succeedAny rejects — the first oneTuple of values
allSettledAll settleNeverTuple of PromiseSettledResult
raceFirst settles, either wayIf the first to settle rejectsUnion of values
anyFirst succeedsAll rejectUnion; AggregateError on failure

Promise.all's failure behaviour is the trap: it rejects on the first rejection but does not cancel the others, which keep running and can produce unhandled rejections of their own. When partial failure is acceptable, allSettled is the correct choice — and its reason field is typed any, so narrow it like any caught value.

Part 4 — The void Loophole

Lesson 4 established that a function returning something is assignable where void is expected. Combined with async, that produces the most common async bug in TypeScript — and it compiles with zero errors.

const sleep = (ms: number) => new Promise<void>(r => setTimeout(r, ms));
const items = [3, 1, 2];
const done: number[] = [];

items.forEach(async (i) => { await sleep(i * 10); done.push(i); });
console.log("after forEach:", done);

$ npx tsc a2.ts --target es2022 && node o/a2.js
after forEach: []                          ◄── verified: nothing was awaited

forEach expects (x: T) => void. An async callback returns Promise<void>, which is assignable to void, so the compiler is satisfied. forEach then discards every promise, returns immediately, and the work completes later with nobody watching — including its errors.

// the fix: use map, and await the collection
await Promise.all(items.map(async (i) => { await sleep(i * 10); done.push(i); }));
// or a sequential loop, when order or backpressure matters
for (const i of items) { await sleep(i * 10); done.push(i); }
ConstructAwaits the work?Concurrency
arr.forEach(async …)NoUnbounded, unobserved
await Promise.all(arr.map(async …))YesUnbounded, observed
for (const x of arr) await …YesOne at a time
for await (const x of stream)YesOne at a time, over an async source
A pool with a concurrency limitYesBounded

The same loophole applies to any void-returning callback — event handlers, addEventListener, middleware signatures typed as void. An async handler there is accepted and its rejection is unhandled, which is why an async Express handler without a wrapper silently fails to send a response.

Part 5 — Floating Promises

declare function n(): Promise<number>;
function g() { n(); }        // ✔ no error, under full strict mode   ◄── verified

The compiler has no rule about using a promise's result. Nothing in strict reports an unawaited promise, so the only defence is a lint rule.

ToolCatches
@typescript-eslint/no-floating-promisesUnawaited promise expressions
@typescript-eslint/no-misused-promisesAsync callbacks where void is expected — the Part 4 bug
@typescript-eslint/await-thenableawait on a non-promise, where it is a mistake

❌ Assuming strict mode covers async mistakes. A project with every flag from lesson 10 enabled still compiles n() as a statement, still accepts forEach(async …), and still lets an async Express handler drop its rejection. These are the highest-frequency bugs in real TypeScript codebases and the type system reports none of them, because none is a type error — the types genuinely line up.

✅ Treat no-floating-promises and no-misused-promises as part of the type system. Both require type information, so they need the typed ESLint configuration rather than a plain parser, which is the reason teams often skip them. That configuration is the single highest return per line of setup in a TypeScript project, and it belongs in CI beside tsc --noEmit.

Part 6 — Async Iterables

async function* pages(url: string): AsyncGenerator<Page, void, undefined> {
  let next: string | undefined = url;
  while (next) {
    const res = await fetch(next);
    const page: Page = Page.parse(await res.json());      // lesson 11 at the boundary
    yield page;
    next = page.nextUrl;
  }
}

for await (const page of pages("/api/items")) { … }
TypeMeans
AsyncIterable<T>Can be consumed by for await
AsyncGenerator<T, TReturn, TNext>What an async function* returns
AsyncIterableIterator<T>The common middle ground for parameters
ReadableStream<T>Web streams — async iterable in modern runtimes

Accept the widest type you can consume and return the most specific you produce: a function that iterates should take AsyncIterable<T>, so callers can pass a generator, a stream or an array-backed helper. Requiring AsyncGenerator in a parameter position rejects every source that is not literally a generator, for no benefit.

Async iteration also needs lib to include a recent enough ES target, which is lesson 14's point recurring: for await on a ReadableStream type-checks only if lib says the runtime supports it.

Interview Questions

Beginner: What does Promise<T> tell you, and what does it not?

It tells you the type of the value on success. It says nothing about failure — there is no slot in the type for a rejection, and TypeScript has no throws clause to declare one.

So async function save(u: User): Promise<void> compiles perfectly while unconditionally throwing, and a caller reading the signature cannot tell whether it can fail or with what. The rejection arrives at a catch as unknown, for the same reason any thrown value does.

It also says nothing about whether the promise will ever settle. A promise that hangs forever has the same type as one that resolves immediately, which is why timeouts are a runtime concern.

If the failures are part of the contract, the way to express them is to put them in the resolved value — Promise<Result<User, NotFound | Unauthorised>> — which makes the failure modes visible and unskippable, with the trade-offs lesson 12 covered.

Beginner: What type does Promise.all produce?

For an array literal, a tuple — the positional types are preserved. I verified that Promise.all([n(), s()]) where those return Promise<number> and Promise<string> resolves to [number, string].

That is what makes destructuring work properly: const [user, orders] = await Promise.all([getUser(), getOrders()]) types each variable individually rather than as a union of both.

The catch is that it depends on the argument being a literal. Passing an array variable gives T[] instead, because the positional information was already lost when the variable was typed — so the practical rule is to keep the array inline at the call site.

Its failure behaviour is worth knowing too: it rejects with the first rejection but does not cancel the other promises, which keep running. When partial failure is acceptable, allSettled is correct, and its result is a tuple of PromiseSettledResult — verified — whose reason field is any and needs narrowing.

Mid: Why does arr.forEach(async x => …) compile, and what goes wrong?

It compiles because of the void-return rule from lesson 4: a function that returns something is assignable where a void-returning function is expected. forEach wants (x: T) => void, an async callback returns Promise<void>, and that is assignable — so the types genuinely line up.

What goes wrong is that forEach discards every returned promise and returns immediately. I verified the consequence: a loop whose callback awaits and then pushes to an array leaves the array empty on the next line. The work completes later, unobserved.

The worse half is errors. Because nothing holds the promises, a rejection inside the callback becomes an unhandled rejection rather than something the surrounding try/catch can see — so the failure is both invisible and detached from its context.

The fix is await Promise.all(arr.map(async …)) for concurrent work, or a for…of loop with await when order or backpressure matters. And because this is a whole class of bug rather than one mistake — it applies to every void-returning callback, including event handlers and middleware — the real answer is the no-misused-promises lint rule.

Mid: Does the compiler catch unawaited promises?

No. I verified that function g() { n(); } where n returns a promise compiles with no error under full strict mode. There is no rule anywhere in the type system about using a promise's result.

That is defensible in principle — discarding a value is legal for any type, and fire-and-forget is sometimes intended — but in practice an unawaited promise is nearly always a bug, and it fails in the worst way: the operation may not have completed when the function returns, and its rejection is unhandled.

The defence is lint, specifically @typescript-eslint/no-floating-promises and no-misused-promises. Both need type information, so they require the typed ESLint setup rather than a plain parser — which is exactly why teams skip them, and why they are the highest-value configuration in a TypeScript project.

For a genuinely deliberate fire-and-forget I would write void someAsync(), which satisfies the lint rule and documents the intent, plus a .catch() so the rejection is still handled somewhere.

Senior: Design the concurrency approach for a service that fans out to many upstreams.

The decisions that matter are how many requests run at once, what happens on partial failure, and who observes the errors — and the type system helps with none of them, so they have to be deliberate.

Bound the concurrency. Promise.all over a mapped array is the right shape but has no limit, so a thousand items become a thousand simultaneous requests, exhausting the connection pool and usually tripping the upstream's rate limits. A small pool helper, or a batching loop, keeps it bounded — and the bound should be a configured number rather than a constant, because the right value depends on the upstream.

Choose the combinator from the failure policy, not from habit. Promise.all is correct when the operation is all-or-nothing, remembering that it does not cancel the siblings on rejection — they keep running, and their own rejections need handling. allSettled is correct when partial results are useful, and its reason is any, so each failure needs narrowing before it is logged. any suits redundant upstreams, and its AggregateError carries every failure — verified — which is what you want in the log when all of them fail.

Add cancellation, because the types imply none. An AbortSignal threaded through the calls is what makes a timeout actually stop work rather than just stop waiting for it. A promise that has been abandoned is still running.

Then make the whole thing observable. no-floating-promises in CI so nothing is accidentally detached, one place that logs failures with the upstream name, and a timeout per call rather than only on the aggregate.

Recommendation: a bounded pool with a configured limit, allSettled as the default for fan-out because partial success is usually more useful than none, abort signals for cancellation, and the typed lint rules enforcing that every promise is observed.

Senior: A service intermittently returns before its work is done. How do you find the cause?

The symptom — a response sent, and the side effect appearing seconds later or not at all — points strongly at a detached promise, so I would look for the two ways that happens rather than start instrumenting.

First, async callbacks in void positions. arr.forEach(async …) is the canonical one: I verified that it compiles and that the work has not happened on the following line. The same shape hides in event handlers, middleware typed as returning void, and any library callback whose signature is () => void — all of which accept an async function silently because Promise<void> is assignable to void.

Second, plain floating promises — a call whose result is simply not awaited. The compiler reports nothing, so these accumulate invisibly, especially around logging, cache warming and metrics.

The fastest way to find both is to turn the lint rules on and read the list, rather than to reason about it. no-floating-promises and no-misused-promises over a codebase that has never had them typically produce a few dozen hits, and the bug is almost always among them. That is minutes of work compared to tracing request lifecycles.

Then look at process lifetime, because it explains the "or not at all" half: in a serverless or short-lived worker, a detached promise is killed when the invocation ends, which makes the behaviour depend on load and look intermittent.

Recommendation: enable both rules and fix what they report; make the two correct patterns — await Promise.all(map) and for…of with await — the reviewed norm; require void with a .catch() for anything deliberately detached; and add the rules to CI so the class does not come back.

5 (hard): Write a concurrency-limited pool.
Solution 
async function pool<T, R>(
  items: readonly T[],
  limit: number,
  fn: (item: T, index: number) => Promise<R>,
): Promise<R[]> {
  const results: R[] = new Array(items.length);
  let next = 0;

  async function worker(): Promise<void> {
    while (next < items.length) {
      const i = next++;                       // claim an index
      results[i] = await fn(items[i]!, i);
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}

const out = await pool(urls, 5, (u) => fetchJson(u));    // R[] preserved
DecisionReason
readonly T[] parameterThe pool does not mutate the input
Two type parametersBoth appear twice — lesson 6's test
Index claimed before awaitKeeps results positional and avoids double work
items[i]!Needed under noUncheckedIndexedAccess; bound is proven
Math.min(limit, length)Do not start more workers than items

The non-null assertion is the one place an unprovable-to-the-compiler invariant is asserted, which is exactly the narrow use lesson 10 allowed — the bound is guaranteed by the while condition, and it deserves the comment.

This version fails fast on the first rejection, inheriting Promise.all's behaviour. A variant returning Result per item would suit partial-failure cases.

6 (hard): Type an async paginator.
Solution 
import { z } from "zod";
const Page = z.object({ items: z.array(z.string()), nextUrl: z.string().optional() });
type Page = z.infer<typeof Page>;

async function* pages(url: string): AsyncGenerator<Page, void, undefined> {
  let next: string | undefined = url;
  while (next) {
    const res = await fetch(next);
    if (!res.ok) throw new Error(`${next} returned ${res.status}`);   // lesson 12
    const page = Page.parse(await res.json());                        // lesson 11
    yield page;
    next = page.nextUrl;
  }
}

// consume — note the parameter type is the WIDE one
async function collect(src: AsyncIterable<Page>): Promise<string[]> {
  const out: string[] = [];
  for await (const p of src) out.push(...p.items);
  return out;
}

🎯 Key Takeaways

  • Promise<T> describes success only — no rejection type, no throws clause.
  • await on a non-promise is legal and keeps the value's type — await 42 is 42.
  • Awaited<T> unwraps recursively and distributes — do not hand-roll it.
  • Promise.all on a literal array gives a tuple, which is what makes destructuring type correctly.
  • Pass a variable instead and you get T[] — keep the array inline.
  • Promise.all rejects on the first failure but cancels nothing.
  • allSettled never rejects; its reason is any and needs narrowing.
  • Promise.any rejects with an AggregateError carrying every failure.
  • No combinator cancels anything — that needs an AbortSignal.
  • Promise<void> is assignable to void, so forEach(async …) compiles.
  • It awaits nothing and detaches every error — verified: the array is still empty.
  • The same loophole hits every void callback — handlers, middleware, listeners.
  • The compiler never reports a floating promise.
  • no-floating-promises and no-misused-promises are part of the type system in practice — they need typed lint.
  • Accept AsyncIterable, return AsyncGenerator — wide in, specific out.
