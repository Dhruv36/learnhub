Conditional Types & infer Type-Level Programming

What you'll master: T extends U ? X : Y and why extends here means assignable to, not inherits from; distribution over unions — the single most surprising rule in the language, and the [T] extends [U] trick that switches it off; why T extends string ? … : … applied to never gives never; infer for pulling types out of structures, with constrained and multi-site inference; recursive conditional types and the TS2589 wall; and the judgement call of when a conditional type is the right tool versus when overloads or plain unions are clearer. Prerequisites: Generics & Constraints.

Part 1 — T extends U ? X : Y

A conditional type chooses between two types based on an assignability test. It is the if of the type system, and it only means something inside a generic — otherwise the answer is fixed.

type IsString<T> = T extends string ? "yes" : "no";

type A = IsString<"hello">;    // "yes"  — a string literal IS assignable to string
type B = IsString<number>;     // "no"
type C = IsString<string[]>;   // "no"
🔑 extends in a conditional type asks "is the left side assignable to the right side?" — the structural question from lesson 3, not a class-inheritance question. That is why { a: 1; b: 2 } extends { a: number } ? … takes the true branch: it has the required property, regardless of where it came from.
TestResultWhy
"a" extends stringtrueA literal is assignable to its primitive
string extends "a"falseNot every string is "a"
{a:1;b:2} extends {a:number}trueStructural: it has the members
never extends stringtruenever is assignable to everything
any extends stringbothResolves to the union of both branches
unknown extends stringfalseunknown is assignable only to unknown/any

The any row is worth remembering: IsString<any> is "yes" | "no", because any is assignable to string and also is not. When a conditional type returns a suspicious union, an any upstream is the usual cause.

Part 2 — Distribution Over Unions

When the checked type is a naked type parameter and the argument is a union, the conditional applies to each member separately and unions the results.

type IsString<T>  = T extends string ? "yes" : "no";
type Tupled<T>    = [T] extends [string] ? "yes" : "no";

type Naked   = IsString<string | number>;   // "yes" | "no"   ◄── distributed
type Wrapped = Tupled<string | number>;     // "no"           ◄── evaluated once

// verified with tsc 7.0.2:
const a1: IsString<string | number> = "yes";   // ✔ compiles
const a2: IsString<string | number> = "no";    // ✔ compiles — so the type is the UNION
const a3: Tupled<string | number>   = "no";    // ✔
const a4: Tupled<string | number>   = "yes";
// error TS2322: Type '"yes"' is not assignable to type '"no"'.

Distribution is what makes filtering possible, and it is how Exclude and Extract are built:

type Keep<T> = T extends string ? T : never;
type K = Keep<string | number | boolean>;    // string
// each member is tested; the non-strings become never, and never vanishes from a union
FormDistributes?Use for
T extends U ? …YesFiltering and mapping union members
[T] extends [U] ? …NoAsking about the union as a whole
T[] extends U[] ? …NoSame effect, less conventional
Foo<T> extends U ? …NoThe checked type is not naked

The never case follows from the same rule, and catches people every time:

type FromNever = IsString<never>;       // never   ◄── verified, NOT "no"
type NeverWrapped = Tupled<never>;      // "yes"   ◄── verified

never is the empty union. Distributing over zero members produces zero results, so the whole conditional is never. Wrap it in a tuple and the test runs once — and [never] extends [string] is true, because never is assignable to everything. If a type-level helper mysteriously evaluates to never, an empty union reaching a distributive conditional is the first thing to check.

Part 3 — infer: Pulling Types Out

infer declares a type variable inside the extends clause, capturing whatever matched at that position.

type Ret<T>  = T extends (...a: never[]) => infer R ? R : never;
type Elem<T> = T extends readonly (infer E)[] ? E : never;

type R1 = Ret<() => Promise<number>>;   // Promise<number>   ◄── verified
type E1 = Elem<string[]>;                // string            ◄── verified
type E2 = Elem<[1, "a"]>;                // "a" | 1           ◄── verified

Two refinements matter in real code. A constraint on the inferred variable makes the match itself conditional:

type FirstStr<T> = T extends [infer H extends string, ...unknown[]] ? H : "none";

type F1 = FirstStr<["x", 1]>;   // "x"      ◄── verified
type F2 = FirstStr<[1, "x"]>;   // "none"   ◄── verified: the head was not a string, so no match

And the same variable inferred in several places collects candidates:

type Both<T> = T extends { a: infer U; b: infer U } ? U : never;
type M = Both<{ a: string; b: number }>;   // string | number   ◄── verified

⚠️ Reach for the built-in first. Most infer patterns you are about to write already exist as a utility type, are better tested, and produce better error messages. Write your own when the shape is genuinely yours — a domain-specific route string, a discriminated event map, a builder chain.

Part 4 — Recursion, and Where It Stops

A conditional type may refer to itself, which is how unwrapping and string parsing work:

type Unwrap<T> = T extends Promise<infer U> ? Unwrap<U> : T;
type U1 = Unwrap<Promise<Promise<number>>>;      // number          ◄── verified

type Split<S> = S extends `${infer H}.${infer R}` ? [H, ...Split<R>] : [S];
type S1 = Split<"a.b.c">;                         // ["a", "b", "c"]  ◄── verified

The compiler enforces a depth limit, and hitting it is a hard error rather than a slow build:

type Grow<T extends unknown[]> = T["length"] extends 1000 ? T : Grow<[...T, 0]>;
type Big = Grow<[]>;
// error TS2589: Type instantiation is excessively deep and possibly infinite.
SymptomCauseFix
TS2589Recursion deeper than the limit, or unboundedAdd a depth counter, or cap the input
Editor hangs on hoverLarge union × deep conditionalPrecompute a named type; narrow the input
Slow whole-project buildAn expensive type used in a hot pathMeasure with --diagnostics; simplify
Type silently becomes neverEmpty union hit a distributive conditionalWrap in a tuple, or guard the empty case
Type silently becomes a wide unionany reached the conditionFix the any at its source

A depth counter is the standard defence for genuinely recursive helpers: carry a tuple of fixed length and stop when it runs out, so the type is bounded by construction rather than by the compiler's patience.

Part 5 — When Not to Write One

Conditional types are the most expensive feature in the type system, both for the compiler and for the next reader. Most code does not need them.

Instead ofPreferWhy
A conditional return type on a public functionOverloadsBetter completions; readable errors
T extends A ? X : Y with two callersTwo functionsSimpler names beat cleverness
A hand-rolled ReturnTypeThe built-inTested; recognised by other readers
Deep conditionals over a big unionA precomputed map typeCompile time, and better errors
Conditionals to encode business rulesRuntime checksTypes are erased; rules need enforcement

❌ A conditional return type on an API other people call. function get<T>(k: string): T extends "user" ? User : Config looks precise, but the editor shows the unresolved conditional in tooltips, a wrong call produces an error mentioning T extends "user" ? User : Config rather than the actual mismatch, and the implementation still needs an internal assertion because the compiler cannot verify that the body honours the condition.

✅ Use overloads for the public surface. Two signatures — get(k: "user"): User and get(k: "config"): Config — give exact completions, plain errors, and no type-level machinery for readers to decode. Keep conditional types for internal helper types where they genuinely compute something, not for the shape of the API itself.

Part 6 — Patterns That Earn Their Keep

// 1. filtering a union (this is Extract / Exclude)
type Extract2<T, U> = T extends U ? T : never;
type Exclude2<T, U> = T extends U ? never : T;

// 2. picking the members of an object that have a given value type
type KeysOfType<T, V> = { [K in keyof T]-?: T[K] extends V ? K : never }[keyof T];
type StringKeys = KeysOfType<{ id: string; age: number; name: string }, string>;  // "id" | "name"

// 3. the payload for a discriminated union member
type Event = { kind: "click"; x: number } | { kind: "key"; code: string };
type ByKind<K extends Event["kind"]> = Extract<Event, { kind: K }>;
type Click = ByKind<"click">;      // { kind: "click"; x: number }

// 4. making a helper tolerate both a value and a promise
type Awaitable<T> = T | Promise<T>;
type Resolved<T> = T extends Promise<infer U> ? U : T;
PatternWhat it replaces
Union filteringHand-maintained parallel union types
KeysOfTypeA hand-written list of key names that drifts
Extract<Event, {kind: K}>A second lookup type duplicating the union
Promise unwrappingOverloads for the sync and async cases
String parsing with inferStringly-typed route and key APIs

What these share is that the derived type cannot drift. A hand-written list of the string keys of an interface is correct until someone adds a field; KeysOfType is correct by construction. That is the test worth applying before writing one — does it remove a thing that can go stale, or is it cleverness for its own sake?

Interview Questions

Beginner: What does extends mean in a conditional type?

It is an assignability test, not inheritance. T extends U ? X : Y asks whether a value of type T could be used where a U is expected, and resolves to X if so and Y otherwise.

Because TypeScript is structural, the answer does not depend on declarations. { a: 1; b: 2 } extends { a: number } because it has a compatible a, even though no class or interface relationship exists between them. And "hello" extends string is true while string extends "hello" is false, because the literal is one of the strings but not every string is that literal.

Two edge cases are worth knowing: never is assignable to everything, so never extends U is true; and any satisfies both directions, so a conditional applied to any returns the union of both branches.

It also only does useful work inside a generic. Written with a concrete type on the left, the answer is fixed at the point you wrote it, which makes it an elaborate way of writing that answer directly.

Beginner: What is infer and where is it valid?

infer declares a type variable inside the extends clause of a conditional type, capturing whatever matched at that position so the true branch can use it. It is the destructuring of the type system.

type Ret<T> = T extends (...a: never[]) => infer R ? R : never captures a function's return type, so Ret<() => Promise<number> is Promise<number>. The same shape works for element types (readonly (infer E)[]), promise values (Promise<infer U>) and constructor instances.

It is only valid in the condition of a conditional type — not in a parameter, not in a type alias body, not on the right of an assignment. Outside that position it is a syntax error.

In practice, the first thing to check is whether a built-in already does it: ReturnType, Parameters, Awaited and InstanceType cover most of what people hand-roll, with better error messages and no maintenance.

Mid: Explain distributive conditional types, and how to turn distribution off.

When the checked type is a bare type parameter and it receives a union, the conditional is applied to each member independently and the results are unioned. It is not evaluated once against the whole union.

So with type IsString<T> = T extends string ? "yes" : "no", IsString<string | number> is "yes" | "no" — I verified this by checking that both "yes" and "no" are assignable to it. Wrapping both sides in a tuple, [T] extends [string] ? "yes" : "no", defeats distribution because the checked type is no longer naked, and the result is just "no".

Distribution is a feature, not an accident: it is what makes filtering possible. T extends string ? T : never applied to string | number | boolean gives string, because the non-matching members become never and never disappears from a union. That is exactly how Extract and Exclude are defined.

The rule to internalise is which question you are asking: "what happens to each member of this union?" wants distribution; "what is true of this union as a whole?" wants the tuple form. Choosing the wrong one is a common source of types that look right and are not.

Mid: Why does a conditional type applied to never give never?

Because never is the empty union, and distribution over zero members produces zero results. The conditional never runs, so there is nothing to union, and the answer is never.

It surprises people because never extends string is true when you ask directly — never is assignable to everything. But type IsString<T> = T extends string ? "yes" : "no" applied to never is never, not "yes". Wrap it — [never] extends [string] — and the test runs once and gives "yes".

Where this bites is a helper that filters a union down to nothing and then feeds the result into another conditional: everything downstream silently collapses to never, and the eventual error appears far from the cause, usually as something being unassignable to never.

My habit is that when a type-level helper unexpectedly evaluates to never, I check for an empty union reaching a distributive conditional before I check anything else. If the empty case is meaningful, I handle it explicitly with a [T] extends [never] ? … guard at the top.

Senior: A colleague proposes a conditional return type for a public function. What do you say?

I would push back for the public surface and keep conditional types for internal helpers, because the costs land on callers rather than on the author.

The concrete problems: tooltips show the unresolved conditional instead of a type, so hovering teaches the caller nothing; a mistaken call produces an error that quotes the conditional expression rather than the actual mismatch; and the implementation body is not checked against the condition — the compiler cannot prove that the "user" branch really returns a User, so there is an assertion inside regardless. The safety is narrower than it looks.

Overloads give the same call-site experience without any of that: exact completions per argument, plain error messages, and an implementation signature that is visibly the unsafe part. They do not scale past a handful of cases, which is the honest trade — but a handful is what most APIs have.

When I would accept the conditional: when the cases are open-ended and derived from a caller-supplied type, such as a query builder where the result shape follows the selected columns. Overloads cannot express that at all. Even then, I would ask for named intermediate types so the tooltip shows something readable, and a test file that asserts the resolved types.

Recommendation: overloads for the API, conditionals for the internal types that compute shapes, and a rule that any conditional appearing in a public signature needs a named alias and a type-level test.

Senior: A type-level helper causes TS2589 and slow builds. How do you diagnose and fix it?

TS2589 — "type instantiation is excessively deep and possibly infinite" — means recursion hit the compiler's depth limit. It is nearly always either unbounded recursion or recursion whose depth follows the size of the input.

First, find the actual input. The error points at the instantiation, not at the type definition, so the fastest path is to check what was passed: a union that grew, a string that got longer, a tuple built up somewhere else. A helper that worked for a 5-member union and fails at 50 is a bound problem, not a logic problem.

Then bound it. The standard technique is a depth counter — carry a tuple of fixed length and stop when it empties — so the type is bounded by construction. Rewriting recursion as a mapped type or a precomputed lookup map removes it entirely where the shape allows.

For build time, measure rather than guess. tsc --diagnostics shows check time and instantiation counts, and --generateTrace gives a profile that names the expensive types. Deep conditionals over large unions are the usual culprit because the cost is multiplicative; the compiler-performance lesson goes through reading that output.

Recommendation: bound the recursion, replace the hottest helper with a named precomputed type, and add a check on instantiation count so the regression is caught by CI rather than by whoever opens the editor next.

2 (easy): Show distribution and switch it off.
Solution 
type IsString<T> = T extends string ? "yes" : "no";
type Tupled<T>   = [T] extends [string] ? "yes" : "no";

const a1: IsString<string | number> = "yes";
const a2: IsString<string | number> = "no";
const a3: Tupled<string | number>   = "no";
const a4: Tupled<string | number>   = "yes";

$ npx tsc dist.ts --noEmit --strict
dist.ts(7,7): error TS2322: Type '"yes"' is not assignable to type '"no"'.

Only line 7 failed, which proves both halves at once: the distributive version accepts either literal because it is the union "yes" | "no", and the tupled version accepts only "no" because it evaluated the test once against string | number.

Assigning literals is a better probe than reading a tooltip here, because tooltips often show the alias name rather than the resolved type.

5 (hard): Hit TS2589, then bound the recursion.
Solution 
type Grow<T extends unknown[]> = T["length"] extends 1000 ? T : Grow<[...T, 0]>;
type Big = Grow<[]>;

$ npx tsc deep.ts --noEmit --strict
deep.ts(2,12): error TS2589: Type instantiation is excessively deep and possibly infinite.

The bounded version carries a depth budget as a tuple and stops when it empties, so no input can drive it past the limit:

type Unwrap<T, D extends unknown[] = [0,0,0,0,0,0,0,0]> =
  D extends [unknown, ...infer Rest]
    ? T extends Promise<infer U> ? Unwrap<U, Rest> : T
    : T;                                  // budget spent — stop, return what we have

type Ok = Unwrap<Promise<Promise<number>>>;   // number
TechniqueBoundCost
Depth-counter tupleFixed by constructionAn extra type parameter
Precomputed map typeNo recursion at allMust enumerate the cases
Built-in (Awaited)Handled by the compilerNone — prefer this

For this specific example Awaited<T> is the right answer and handles thenables too; the hand-rolled version is worth writing once to understand the bound, then deleting.

6 (hard): Decide, for four cases, whether a conditional type is the right tool.
Solution

get(key) returning User or ConfigOverloadsTwo fixed cases; callers get clean completions and errors

// case 2, the one that pays for itself
type KeysOfType<T, V> = { [K in keyof T]-?: T[K] extends V ? K : never }[keyof T];

interface User { id: string; age: number; name: string; active: boolean }

The dividing line across all four is whether the type is derived from something that changes. A derived type removes a maintenance hazard and earns its complexity; a conditional standing in for two known cases just adds one.
