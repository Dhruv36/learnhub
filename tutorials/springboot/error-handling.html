Error Handling Web Layer

What you'll master: why every try/catch in a controller is a design smell and what replaces all of them — one @RestControllerAdvice that turns exception handling from something repeated 60 times into a single reviewable policy; the resolution order Spring uses to find a handler, and the most-specific-type rule that explains why your Exception handler is swallowing the NotFoundException handler you also wrote; RFC 7807 Problem Details, which Boot 3 supports natively, and why inventing your own error envelope costs every client bespoke parsing forever; the information-disclosure failures that make error handling a security topic — one team's default error page leaked the SQL statement, the schema, and the database username to anyone who sent malformed JSON; the exception-design question nobody asks until it hurts (checked or unchecked, and how many exception types), with the rule that actually scales; how errors interact with @Transactional — a caught exception still marks the transaction rollback-only, so your carefully handled error fails at commit; and how to make errors observable, so a 500 is a trace id in a support ticket rather than an archaeology project. Prerequisites: REST Controllers and Validation.

Part 1 — What Happens When a Controller Throws

  Your controller throws
        │
        ▼
  DispatcherServlet catches it and consults, IN ORDER:
        │
  1. ExceptionHandlerExceptionResolver
        - @ExceptionHandler in the SAME controller class   (first)
        - @ExceptionHandler in a @ControllerAdvice          (then)
  2. ResponseStatusExceptionResolver
        - @ResponseStatus on the exception class
        - ResponseStatusException instances
  3. DefaultHandlerExceptionResolver
        - Spring's own MVC exceptions (405, 415, 400 for
          unreadable bodies...)
        │
        ▼
  Nothing matched?  ->  the servlet container's error page
                        ->  Spring Boot's BasicErrorController
                            (the "Whitelabel Error Page")

  TWO CONSEQUENCES WORTH KNOWING:

  - A handler in the controller BEATS one in a @ControllerAdvice for
    the same exception type. Useful for one endpoint's special case,
    and a trap when someone leaves one behind.

  - Anything thrown in a FILTER never reaches this machinery at all.
    Filters run before the DispatcherServlet, so a Spring Security
    failure or a filter NPE goes straight to the container error
    page. This is why "my @ControllerAdvice doesn't catch auth
    errors" -- it cannot.
🔑 Handler selection is by most specific exception type, not by declaration order. If you have handlers for Exception and for OrderNotFoundException, a thrown OrderNotFoundException goes to the specific one — regardless of which is declared first, or which class they live in. Spring walks the exception's type hierarchy and picks the closest match. This is why a catch-all handler is safe to add, and why "my specific handler isn't firing" is nearly always a different exception type than you think, often a wrapped one.

Wrapped exceptions

  @ExceptionHandler(OrderNotFoundException.class)   // never fires

  because what actually propagates is:

    UndeclaredThrowableException
      -> InvocationTargetException
        -> OrderNotFoundException          <- the real cause

  Spring's resolver DOES unwrap: it checks the exception, then its
  cause chain. But several layers wrap in ways that defeat this:

    - a @Transactional proxy may wrap in TransactionSystemException
    - Spring Data wraps persistence exceptions in
      DataAccessException subtypes
    - CompletableFuture wraps in CompletionException
    - @Async wraps unless you use an AsyncUncaughtExceptionHandler

  DIAGNOSIS: log the full chain before guessing.
    logging.level.org.springframework.web.servlet.mvc.method.annotation
      .ExceptionHandlerExceptionResolver=TRACE

Part 2 — One Advice Instead of Sixty try/catch Blocks

  BEFORE -- repeated in every method

  @GetMapping("/orders/{id}")
  public ResponseEntity<?> get(@PathVariable Long id) {
      try {
          return ResponseEntity.ok(service.find(id));
      } catch (OrderNotFoundException e) {
          return ResponseEntity.status(404).body(Map.of("error", e.getMessage()));
      } catch (Exception e) {
          log.error("failed", e);
          return ResponseEntity.status(500).body(Map.of("error", "internal error"));
      }
  }

  Problems, in order of severity:
    - catch(Exception) swallows programming errors as 500s with no
      distinction from expected failures
    - the response shape is decided per method, so it drifts
    - 60 methods = 60 chances to get the status code wrong
    - the ResponseEntity<?> wildcard destroys type safety
    - it is untestable except through the whole HTTP stack

  AFTER

  @GetMapping("/orders/{id}")
  public OrderResponse get(@PathVariable Long id) {
      return OrderResponse.from(service.find(id));   // just throws
  }

  @RestControllerAdvice
  public class ApiExceptionHandler {

      private static final Logger log =
          LoggerFactory.getLogger(ApiExceptionHandler.class);

      // ---- expected domain failures: log at INFO/WARN, no stack trace
      @ExceptionHandler(NotFoundException.class)
      @ResponseStatus(HttpStatus.NOT_FOUND)
      ProblemDetail notFound(NotFoundException e) {
          return problem(HttpStatus.NOT_FOUND, "Not found", e.getMessage());
      }

      @ExceptionHandler(BusinessRuleException.class)
      @ResponseStatus(HttpStatus.CONFLICT)
      ProblemDetail conflict(BusinessRuleException e) {
          ProblemDetail pd = problem(HttpStatus.CONFLICT, "Conflict", e.getMessage());
          pd.setProperty("code", e.code());        // machine-readable
          return pd;
      }

      // ---- the catch-all: log at ERROR with the stack trace,
      //      and NEVER leak the message
      @ExceptionHandler(Exception.class)
      @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
      ProblemDetail unexpected(Exception e, HttpServletRequest req) {
          String traceId = MDC.get("traceId");
          log.error("Unhandled exception [traceId={}] {} {}",
                    traceId, req.getMethod(), req.getRequestURI(), e);
          ProblemDetail pd = problem(HttpStatus.INTERNAL_SERVER_ERROR,
              "Internal server error",
              "An unexpected error occurred. Quote the trace id when reporting this.");
          pd.setProperty("traceId", traceId);
          return pd;
      }

      private ProblemDetail problem(HttpStatus s, String title, String detail) {
          ProblemDetail pd = ProblemDetail.forStatus(s);
          pd.setTitle(title);
          pd.setDetail(detail);
          return pd;
      }
  }
ScopeHowUse for
All controllers@RestControllerAdviceThe default
One package@RestControllerAdvice("com.acme.api.v2")Different error contracts per API version
Annotated controllers@RestControllerAdvice(annotations = PublicApi.class)Public vs internal endpoints

⚠️ Two advices that both handle a type is undefined behaviour unless you order them. Add @Order to every @ControllerAdvice in an application that has more than one — the catch-all advice should have @Order(Ordered.LOWEST_PRECEDENCE) so the specific ones win. Without ordering, which advice handles an exception can change between classpath-scanning runs, which is the worst kind of environment-dependent bug.

Part 3 — RFC 7807 Problem Details

Spring Boot 3 supports the standard error format natively. Using it means clients, gateways and tooling that already understand it need no bespoke parsing.

  # enable Spring's own exceptions to use it too
  spring.mvc.problemdetails.enabled: true

  RESPONSE  (Content-Type: application/problem+json)

  {
    "type":     "https://api.acme.com/problems/insufficient-funds",
    "title":    "Insufficient funds",
    "status":   409,
    "detail":   "Account balance 42.00 is below the requested 100.00",
    "instance": "/accounts/17/withdrawals",
    "code":     "INSUFFICIENT_FUNDS",
    "traceId":  "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"

FieldMeaningNote
typeA URI identifying the kind of problemThe stable identifier. It need not resolve, but a documentation page is better
titleShort human summary of the typeShould not change per occurrence
statusThe HTTP status, duplicated in the bodyConvenient for clients that lose the status
detailHuman explanation of this occurrenceNever put a stack trace or SQL here

ExtensionsAny extra members you addcode, traceId, errors
  WHY A MACHINE-READABLE code MATTERS MORE THAN THE MESSAGE

    Clients must branch on something stable. If they parse
    "Insufficient funds" out of detail, then:
      - you can never reword the message
      - you can never translate it
      - a typo fix is a breaking change

    With "code": "INSUFFICIENT_FUNDS" the prose is free to change,
    be internationalised, or carry per-occurrence numbers, and no
    client breaks.

  ONE type PER PROBLEM KIND, NOT PER OCCURRENCE
    type: ".../insufficient-funds"     correct
    type: ".../error-17-account-42"    wrong -- that is `instance`

Part 4 — Error Handling Is a Security Topic

MEASURED: what a default error page disclosed

  A malformed JSON body to a public endpoint returned, in production:

  {
    "timestamp": "2026-03-14T09:22:41.882+00:00",
    "status": 500,
    "error": "Internal Server Error",
    "trace": "org.springframework.dao.DataIntegrityViolationException:
              could not execute statement; SQL [insert into users
              (email,password_hash,role,tenant_id,created_at)
              values (?,?,?,?,?)]; constraint [uq_users_email];
              nested exception is org.hibernate.exception....
              at com.acme.user.UserService.register(UserService.java:88)
              ... 147 more",
    "message": "could not execute statement",
    "path": "/api/register"
  }

  DISCLOSED, from one malformed request:
    - the framework and its exact version (from package names)
    - the table name and every column in it
    - the constraint names
    - internal class names, method names and line numbers
    - the ORM in use

  An attacker now knows the schema, and knows that email uniqueness
  is enforced at the database -- which tells them the registration
  endpoint is a user-enumeration oracle.
SettingSafe valueWhy

⚠️ The rule: log everything, return almost nothing. The stack trace, the SQL, the parameters and the full exception chain belong in your logs, correlated by a trace id. The response gets a generic message and that trace id. This is not a trade-off between debuggability and security — done properly you lose nothing, because the trace id in a support ticket takes you straight to the full detail in your log aggregator.
  ERROR MESSAGES THAT LEAK BEHAVIOUR, not just data

  Login:
    "No account with that email"     -> user enumeration
    "Incorrect password"             -> confirms the account exists
    "Invalid email or password"      -> correct: identical for both

  Password reset:
    "We've sent a reset link"        -> same response whether or not
                                        the account exists

  Authorization:
    404 vs 403 for a resource the user may not see:
      403 confirms the resource EXISTS
      404 reveals nothing
    For anything where existence is sensitive, return 404.

  Timing counts too: if the "no such user" path returns in 5ms and
  the "wrong password" path takes 300ms because it hashes, the
  timing IS the oracle. Hash a dummy password on the missing-user
  path.

  A HIERARCHY THAT SCALES

  public abstract class DomainException extends RuntimeException {
      private final String code;
      protected DomainException(String code, String message) {
          super(message); this.code = code;
      }
      public String code() { return code; }
  }

  public class NotFoundException extends DomainException { ... }
  public class ConflictException extends DomainException { ... }
  public class ForbiddenOperationException extends DomainException { ... }

  public class InsufficientFundsException extends ConflictException {
      private final BigDecimal shortfall;
      public InsufficientFundsException(AccountId id, BigDecimal shortfall) {
          super("INSUFFICIENT_FUNDS",
                "account %s is short by %s".formatted(id, shortfall));
          this.shortfall = shortfall;
      }
      public BigDecimal shortfall() { return shortfall; }
  }

  Now the advice needs THREE handlers, not thirty:
      NotFoundException            -> 404
      ConflictException            -> 409
      ForbiddenOperationException  -> 403

  and every new exception inherits the right status automatically by
  choosing its parent. The `code` distinguishes them for clients.

  ResponseStatusException -- when NOT to define a type

    throw new ResponseStatusException(HttpStatus.NOT_FOUND, "no such order");

  Convenient, and appropriate for:
    - a small internal service with no domain layer worth speaking of
    - a genuine one-off

  Why I avoid it as a default:
    - it puts HTTP concerns in the service layer, so the same code
      cannot be called from a Kafka consumer without dragging in a
      web dependency
    - the "type" of the failure is a status code, so you cannot
      handle InsufficientFunds differently from any other 409
    - it is invisible to tests that do not go through HTTP

Part 6 — Errors and Transactions

  THE BUG THAT SURPRISES EVERYONE

  @Transactional
  public void process(Order o) {
      try {
          riskyStep(o);                       // throws RuntimeException
      } catch (RuntimeException e) {
          log.warn("risky step failed, continuing", e);
          o.setStatus(PARTIAL);               // we "handled" it
      }
      repository.save(o);
  }                                            // commit -> BOOM

  org.springframework.transaction.UnexpectedRollbackException:
  Transaction silently rolled back because it has been marked as
  rollback-only

  WHY: if riskyStep() is itself @Transactional and participates in
  the SAME transaction (REQUIRED, the default), its proxy marks the
  transaction rollback-only when it throws. Catching the exception
  in the caller does not un-mark it. At commit time, the transaction
  manager sees the flag and rolls everything back -- including your
  status update.

  THREE FIXES, and which to pick depends on intent:

  1. The inner step should be INDEPENDENT:
       @Transactional(propagation = Propagation.REQUIRES_NEW)
       void riskyStep(Order o)
     Its failure rolls back only itself. Costs a second connection.

  2. The failure should NOT roll back at all:
       @Transactional(noRollbackFor = RiskyStepException.class)

  3. Do not call it inside the transaction:
     restructure so the risky work happens before or after.

  See Transactions for the full propagation model.
RuleDetail
Rollback is on RuntimeException and Error onlyA checked exception commits by default. Use rollbackFor = Exception.class if you throw checked exceptions from transactional methods
Catching does not un-markOnce a participating transaction is marked rollback-only, only the outermost boundary can act on it
The advice runs after the transactionSo @ExceptionHandler cannot write to the database in the failed transaction — it needs a new one
Lazy loading in a handler failsThe session is closed by then; another reason handlers should work from DTOs and structured exception fields
🔑 Make every 500 traceable in one step. Put a trace id in the MDC in a filter, log it with every error, and return it in the response body. Then a user's screenshot contains the exact key that finds the full stack trace in your log aggregator. Without it, "the site broke at about 3pm" is an archaeology project; with it, it is one search. This is the single highest-value addition to error handling, and it takes about twenty lines.

Interview Questions

Beginner: How do you handle exceptions globally in Spring Boot?

With a class annotated @RestControllerAdvice containing @ExceptionHandler methods. Each method declares the exception type it handles, and returns a response body plus a status — typically a ProblemDetail with @ResponseStatus.

Controllers then simply throw. That removes the try/catch from every method and makes the mapping from exception to HTTP status a single reviewable policy rather than something repeated and drifting across sixty endpoints.

One detail worth knowing: an @ExceptionHandler declared inside a controller takes precedence over one in an advice for the same type, which is useful for a genuine one-off and a trap when someone leaves one behind.

Beginner: What is RFC 7807 / Problem Details?

A standard JSON format for HTTP error responses, served as application/problem+json. It has five standard fields — type, a URI identifying the kind of problem; title, a short human summary; status; detail, explaining this particular occurrence; and instance, the URI of the occurrence — plus any extensions you add.

Spring Boot 3 supports it natively through the ProblemDetail class, and spring.mvc.problemdetails.enabled=true makes Spring's own built-in exceptions use it too.

The reason to use it rather than inventing an envelope is that clients, API gateways and tooling already understand it. A bespoke shape means every consumer writes bespoke parsing, forever.

Mid: What should and should not appear in an error response?

The rule I use is: log everything, return almost nothing.

Return: a status code that reflects what happened, a stable machine-readable code the client can branch on, a human-readable message safe to show a user, field-level detail for validation failures, and a trace id.

Never return: stack traces, exception class names, SQL, table or column names, file paths, internal hostnames, or raw exception messages for unexpected errors — those routinely contain all of the above.

I would emphasise that this is a security concern, not tidiness. I have seen a default error page return the full insert statement with every column name, the constraint name and the service's class and line numbers, in response to one malformed JSON body. That handed an attacker the schema and told them the registration endpoint was a user-enumeration oracle.

And it costs nothing in debuggability provided you include a trace id, because the full detail is one search away in the log aggregator.

Mid: A method catches an exception inside a transaction and continues, but the transaction still fails at commit. Why?

Because the inner method was itself @Transactional and joined the same transaction with the default REQUIRED propagation. When it threw, its proxy marked the shared transaction rollback-only. Catching the exception in the caller does not clear that flag — only the transaction manager acts on it, and at commit it sees the mark and rolls everything back, throwing UnexpectedRollbackException.

Which fix is right depends on intent. If the inner step should succeed or fail independently, it needs Propagation.REQUIRES_NEW, which gives it its own transaction at the cost of a second connection. If its failure genuinely should not roll anything back, noRollbackFor expresses that. Otherwise the honest answer is that the work does not belong inside that transaction and should be restructured.

The related surprise worth mentioning: rollback is triggered by RuntimeException and Error only. A checked exception commits by default, which is the opposite of what most people assume.

Senior: How would you design an exception hierarchy for a large service?

The organising question is: how many distinct things can a client do in response? Not how many error messages exist. If the client's reaction is the same, it is one exception type with different codes, not two types.

That usually gives a small number of abstract parents corresponding to HTTP semantics — NotFoundException, ConflictException, ForbiddenOperationException — with concrete exceptions extending the right one. The advice then needs three handlers rather than thirty, and every new exception gets the correct status automatically by choosing its parent.

Unchecked, all of them. Checked exceptions force every intermediate layer to declare or wrap, which in practice produces throws Exception and empty catch blocks. Spring's own data-access hierarchy is entirely unchecked and that was a deliberate, well-argued decision.

No HTTP status on the exception itself. A domain exception that knows about HTTP cannot be thrown from a Kafka consumer or a batch job without dragging in a web dependency. The mapping is the advice's job, and keeping it there is what lets the same service logic serve multiple transports.

Carry structured state, not a formatted string. e.shortfall() and e.accountId() let the handler build any message, translate it, or put the numbers in extension fields. A pre-formatted English message forecloses all of that.

The one thing I would add for a large service: a stable code on every exception, because that is what clients branch on and what lets you reword or translate messages without breaking anyone.

Senior: Design error handling for a public API where errors are part of the contract.

Once errors are contractual, they get the same discipline as any other part of the API: a stable shape, versioning, and a deprecation policy.

Shape: RFC 7807, with two extensions — a code and a traceId. The type URI resolves to a documentation page per problem kind, which is where the retry guidance and remediation live. Every 4xx and 5xx uses this shape, including the ones Spring generates: malformed JSON, type mismatches, 405s and 415s. Inconsistency here is the defect I would expect to find in an existing API, because those paths are usually left to defaults.

Documentation as a contract: every endpoint documents which code values it can return, and each code documents whether it is retryable. That last part matters more than it sounds — without it, every client invents its own retry policy from status codes alone, and gets it wrong for the cases where a 409 is retryable and a 503 is not.

Stability rules I would publish: codes are never removed or repurposed within a version; the errors array is unordered and may grow, so clients must not assert on the exact set; and detail prose may change at any time, so nothing may parse it. Without those written down, adding a validation constraint later becomes a breaking change.

Security overlay: a public API is exactly where the disclosure rules bind hardest. Generic messages for anything unexpected, 404 rather than 403 wherever existence is sensitive, and identical responses and comparable timings on authentication paths.

The organisational piece: a review checklist item and, better, a test that asserts every error response conforms to the schema. Contracts that are only maintained by discipline drift. I would rather spend a day on a test that fails the build when a handler returns a bare string than rely on sixty future code reviews catching it.

3 (medium): Design the exception hierarchy for an order service with these failures, and show the advice.

Solution

Group by what the client does about it, not by which entity failed.

  public abstract class DomainException extends RuntimeException {
      private final String code;
      protected DomainException(String code, String msg) { super(msg); this.code = code; }
      public String code() { return code; }
  }

  // 404 -- the resource does not exist
  public class NotFoundException extends DomainException { ... }
    OrderNotFoundException("ORDER_NOT_FOUND")
    ProductNotFoundException("PRODUCT_NOT_FOUND")
    CustomerNotFoundException("CUSTOMER_NOT_FOUND")

  // 409 -- valid request, wrong current state
  public class ConflictException extends DomainException { ... }
    InsufficientStockException("INSUFFICIENT_STOCK")     + available()
    OrderAlreadyShippedException("ORDER_ALREADY_SHIPPED") + shippedAt()
    CreditLimitExceededException("CREDIT_LIMIT_EXCEEDED") + limit(), requested()

  // 402 -- payment specifically
  public class PaymentDeclinedException extends DomainException {
      // + declineCode(), retryable()
  }

  // 403/404 -- authorization
  public class AccessDeniedException extends DomainException { ... }

  ---- the advice: FIVE handlers for eight failures ----

  @ExceptionHandler(NotFoundException.class)
  @ResponseStatus(NOT_FOUND)          ProblemDetail notFound(...)

  @ExceptionHandler(ConflictException.class)
  @ResponseStatus(CONFLICT)           ProblemDetail conflict(...)

  @ExceptionHandler(PaymentDeclinedException.class)
  @ResponseStatus(PAYMENT_REQUIRED)   ProblemDetail payment(...)

  @ExceptionHandler(AccessDeniedException.class)
  @ResponseStatus(NOT_FOUND)          ProblemDetail denied(...)   // see below

  @ExceptionHandler(Exception.class)
  @ResponseStatus(INTERNAL_SERVER_ERROR) ProblemDetail unexpected(...)
DecisionReason
Three "not found" types, one handlerThe client's reaction is identical; the code distinguishes them for logging and messaging
Exceptions carry structured dataavailable() and shortfall() let the handler put real numbers in extension fields, and translate the prose
Payment gets its own status402 with a retryable flag lets the client decide between retrying and asking for another card — a genuinely different action
Access denied → 404, not 403403 confirms the order exists. For a resource keyed by a guessable id, that is an enumeration vector
No HTTP status on the exceptionsThe same service must be callable from a batch job without a web dependency

The 403-versus-404 choice is the one I would raise explicitly with the team. 404 is safer but confusing for legitimate users who genuinely lack permission on a resource they know exists. The usual resolution: 404 for anything with guessable ids or cross-tenant exposure, 403 within a tenant where the user already knows the resource exists. It should be a documented decision rather than whatever the first handler happened to do.

4 (medium): This throws UnexpectedRollbackException at commit even though the exception is caught. Explain and give three fixes. 
  @Service
  class OrderService {
      @Transactional
      public void place(OrderRequest req) {
          Order o = orderRepo.save(Order.from(req));
          try {
              loyaltyService.awardPoints(o.customerId(), o.total());
          } catch (Exception e) {
              log.warn("loyalty award failed, continuing", e);
          }
          o.setStatus(PLACED);
      }
  }

  @Service
  class LoyaltyService {
      @Transactional
      public void awardPoints(CustomerId id, BigDecimal amount) {
          throw new LoyaltyServiceUnavailableException();
      }
  }
Solution

Why. awardPoints is @Transactional with the default REQUIRED propagation, so it joins the caller's transaction rather than starting its own. When it throws a RuntimeException, its proxy marks that shared transaction rollback-only. Catching the exception in place() does not clear the flag — nothing can, except the outermost boundary. At commit, the transaction manager sees the mark and rolls the whole thing back, including the order, and reports UnexpectedRollbackException.

The insidious part: the log line says "continuing", so the logs claim the order was placed. It was not.

  FIX 1 -- the loyalty award is genuinely independent  (usually right)

  @Transactional(propagation = Propagation.REQUIRES_NEW)
  public void awardPoints(...) { ... }

    A separate physical transaction. Its rollback does not touch the
    caller's. Costs a second connection for the duration -- worth
    knowing if the pool is tight, since the outer transaction holds
    its connection while the inner one runs.

  FIX 2 -- this failure should never roll anything back

  @Transactional(noRollbackFor = LoyaltyServiceUnavailableException.class)
  public void place(OrderRequest req) { ... }

    Declares the intent at the boundary that owns the decision.
    Fragile: a NEW exception type from loyalty resurrects the bug.

  FIX 3 -- do not do it in the transaction at all  (best)

  @Transactional
  public Order place(OrderRequest req) {
      Order o = orderRepo.save(Order.from(req));
      o.setStatus(PLACED);
      events.publish(new OrderPlaced(o.id(), o.customerId(), o.total()));
      return o;
  }

  @TransactionalEventListener(phase = AFTER_COMMIT)
  public void onOrderPlaced(OrderPlaced e) {
      loyaltyService.awardPoints(e.customerId(), e.total());
  }

Fix 3 is the one I would ship. It encodes the actual business rule: awarding points is a consequence of a placed order, not a precondition for it. With AFTER_COMMIT, the order is durable before loyalty is attempted, the loyalty failure cannot affect the order at all, and the retry story becomes a normal message-retry problem rather than a transaction problem.

The trade-off to state honestly: after-commit work can be lost if the process dies between commit and listener execution. If points must never be lost, the event needs to be persisted in the same transaction — the transactional outbox pattern — and delivered by a separate process. That is more machinery, and worth it only when the consequence genuinely must not be dropped.

5 (hard): Design end-to-end error observability: a user reports "it broke", and you need to find the exact failure in under a minute.
Solution

The goal is that the user's screenshot contains a key that finds everything.

  1. GENERATE OR ADOPT A TRACE ID, in a filter, first in the chain

  @Component
  @Order(Ordered.HIGHEST_PRECEDENCE)
  class TraceIdFilter extends OncePerRequestFilter {
      protected void doFilterInternal(HttpServletRequest req,
              HttpServletResponse res, FilterChain chain) throws ... {
          String traceId = req.getHeader("X-Trace-Id");
          if (traceId == null || !isValid(traceId))
              traceId = UUID.randomUUID().toString().replace("-", "");
          MDC.put("traceId", traceId);
          res.setHeader("X-Trace-Id", traceId);        // client can see it
          try { chain.doFilter(req, res); }
          finally { MDC.clear(); }                     // ESSENTIAL: pooled threads
      }
  }

  2. PUT IT IN EVERY LOG LINE -- structured, not prose

  logging.pattern.level: "%5p [${spring.application.name},%X{traceId}]"
  # or a JSON encoder, which is what you actually want for a log
  # aggregator:  logstash-logback-encoder

  3. RETURN IT IN EVERY ERROR RESPONSE
     pd.setProperty("traceId", MDC.get("traceId"));

  4. SHOW IT IN THE UI on an error screen, and in support emails.

  5. PROPAGATE IT to downstream calls, so one id spans services:
     RestClient.builder().requestInterceptor((r, b, ex) -> {
         r.getHeaders().add("X-Trace-Id", MDC.get("traceId"));
         return ex.execute(r, b);
     })
SignalWhat it answers
Trace id in logs"What exactly happened for this user?"
Structured JSON logsQuery by field rather than grepping prose
Metric per exception type and status"Is this one user or everyone?" — the first question after a report
Distributed tracing (Micrometer Tracing / OpenTelemetry)"Which downstream call was slow or failed?"
Error tracking (Sentry and similar)Groups identical stack traces so you see frequency and first-seen

Two details that are easy to get wrong. MDC.clear() in a finally is not optional — the MDC is a ThreadLocal and threads are pooled, so without it the next request on that thread logs the previous request's trace id, which is worse than having none. And @Async or reactive code does not inherit the MDC; that needs a TaskDecorator or Micrometer's context propagation, and it is where trace ids silently vanish.

Validate the incoming header before adopting it. A client-supplied trace id is attacker-controlled input that goes straight into your logs — a newline in it is log injection, and an unbounded one is a storage problem. Accept only a hex/UUID pattern of fixed length; otherwise generate your own.

What I would build first if I had one day: the filter, the log pattern, and the trace id in error responses. That is roughly twenty lines and it converts "the site broke around 3pm" from an archaeology project into one search. Distributed tracing and error grouping are more valuable in aggregate but far more work, and they do not answer the specific-user question as directly.

6 (hard): An API has inconsistent errors — some Problem Details, some bare strings, some HTML error pages, some 500s that should be 4xx. Plan the unification for a public API with existing clients.
Solution

Measure before changing anything. A week of instrumentation tells you the actual distribution, and it invariably differs from what the team expects.

  @Component
  class ErrorMetricsFilter extends OncePerRequestFilter {
      protected void doFilterInternal(...) {
          chain.doFilter(req, res);
          if (res.getStatus() >= 400)
              meterRegistry.counter("http.errors",
                  "status", String.valueOf(res.getStatus()),
                  "path", bestMatchingPattern(req),
                  "contentType", String.valueOf(res.getContentType())).increment();
      }
  }

The contentType tag is the useful one: it separates responses that already produce application/problem+json from those emitting text/html (the Whitelabel page — meaning nothing handled them) or text/plain.

PhaseWorkBreaking?

3. Fix wrong status codes500s that are really 409/404/400Technically yes, but a client depending on a 500 is already broken

Phases 2 and 3 first, because they are improvements nobody can object to. An HTML page from a JSON endpoint is a bug by any definition, and a 500 for a duplicate email is both wrong and paging someone. Doing these first delivers most of the operational benefit before any compatibility conversation is needed.

Phase 5 needs a version boundary. A @RestControllerAdvice can be scoped by package or by annotation, so v2 endpoints get Problem Details while v1 keeps the legacy shape from a separate advice. That turns one breaking change into two safe ones, and it lets the deprecation run on the clients' schedule rather than yours.

What I would add to stop it recurring: a test that asserts every error response has Content-Type: application/problem+json and conforms to the schema. Run it against a list of deliberately bad requests — malformed JSON, wrong method, unknown path, invalid parameter type, failed validation. That list is short, it covers the paths people forget, and it fails the build when someone adds an endpoint that returns a bare string.

What I would resist: pressure to do phase 5 for all clients at once because "it's just an error format". Errors are the part of an API that client code handles least carefully, so a breaking change there surfaces as mysterious failures in production rather than as a clean parse error.

🎯 Key Takeaways

  • One @RestControllerAdvice replaces every try/catch in every controller and makes exception-to-status mapping a single reviewable policy.
  • Handler selection is by most specific exception type, not declaration order — so a catch-all is safe to add.
  • A handler inside a controller beats one in an advice for the same type.
  • Exceptions thrown in filters never reach the advice, because filters run before the DispatcherServlet.
  • Use RFC 7807 Problem Details — Boot 3 supports it natively, and a bespoke envelope costs every client bespoke parsing forever.
  • Clients branch on a stable code, never on prose, so messages stay changeable and translatable.
  • Log everything, return almost nothing. Stack traces, SQL, class names and raw exception messages are disclosure, not debuggability.
  • One team's default error page returned the insert statement, every column name, the constraint and the line numbers in response to malformed JSON.
  • Set include-stacktrace, include-message and include-exception to never/false.
  • Identical messages and comparable timing on auth paths — a fast "no such user" is an oracle even with the right message.
  • Return 404 rather than 403 where a resource's existence is sensitive.
  • Domain exceptions should be unchecked and carry no HTTP status, so the same service works from a batch job or consumer.
  • One exception type per distinct client action, not per message — three handlers, not thirty.
  • Carry structured state, not formatted strings, so handlers can build any message in any language.
  • Catching an exception does not un-mark a rollback-only transaction — you get UnexpectedRollbackException at commit while the logs claim success.
  • Checked exceptions commit by default. Rollback fires on RuntimeException and Error only.
  • A trace id in the MDC, the logs and the response body is the highest-value twenty lines in error handling.
  • MDC.clear() in a finally is mandatory — pooled threads otherwise log the previous request's id.
