Request Mapping & Binding Web Layer

What you'll master: how Spring decides which method handles a request when several could — the five-level specificity ordering that resolves ambiguity, and why /users/me and /users/{id} coexist safely while /users/{id} and /users/{name} is an IllegalStateException at startup; every way data gets from an HTTP request into a method parameter, including the resolvers you did not know existed and the -parameters compiler flag that makes half of them work; how type conversion actually happens (Converter, Formatter, WebDataBinder) and how to add your own so LocalDate and your domain IDs bind natively; the mass-assignment vulnerability in @ModelAttribute binding that let one team's users set their own role field by adding a query parameter, and the three defences; @RequestBody versus @ModelAttribute and why they are not interchangeable; the PATCH problem — distinguishing "set this field to null" from "don't touch this field" — which plain DTOs cannot express and which breaks partial updates in a way that is invisible until a user clears a field; and how to write a custom HandlerMethodArgumentResolver for the cross-cutting parameter every controller otherwise repeats. Prerequisites: REST Controllers.

Part 1 — How a Mapping Is Chosen

  @RequestMapping is the general form. The rest are shortcuts:

    @GetMapping     = @RequestMapping(method = GET)
    @PostMapping    = @RequestMapping(method = POST)
    @PutMapping     @PatchMapping     @DeleteMapping

  A mapping can discriminate on FIVE things, and all of them
  participate in matching:

    path      @GetMapping("/orders/{id}")
    method    GET vs POST vs ...
    params    @GetMapping(value="/orders", params="status")
    headers   @GetMapping(value="/orders", headers="X-Api-Version=2")
    consumes  what Content-Type the request must have
    produces  what Accept type the response can satisfy

When more than one mapping matches, Spring sorts by specificity and takes the best. The ordering is deterministic, and knowing it removes an entire class of confusion:

  MOST SPECIFIC WINS, compared in this order:

   1. Literal path segments beat variables
        /users/me           beats   /users/{id}
   2. More path variables beats a wildcard
        /users/{id}/orders  beats   /users/**
   3. Single wildcard beats double
        /files/*.txt        beats   /files/**
   4. More params/headers conditions beats fewer
        params="status,type"  beats  params="status"
   5. More specific media type beats a wildcard
        produces="application/json" beats produces="*/*"

  SO THIS IS SAFE AND BEHAVES AS YOU EXPECT:

    @GetMapping("/users/me")        Profile me()          // literal
    @GetMapping("/users/{id}")      User byId(...)        // variable

    GET /users/me  -> me(), because a literal beats a variable.
    GET /users/42  -> byId(), the only match.

  AND THIS FAILS AT STARTUP:

    @GetMapping("/users/{id}")      User byId(@PathVariable String id)
    @GetMapping("/users/{name}")    User byName(@PathVariable String name)

    java.lang.IllegalStateException: Ambiguous mapping. Cannot map
    'userController' method ... There is already 'userController'
    bean method ... mapped.

    The variable NAME is not part of the pattern -- both are
    "/users/{*}". Spring cannot choose, and it tells you at startup
    rather than picking one at random. That is the right behaviour.
🔑 An ambiguous mapping is a startup failure, not a runtime surprise. Spring builds the whole mapping table when the context starts and refuses to start if two mappings are indistinguishable. This is the same design principle as eager singleton creation: a configuration error becomes a build failure rather than a 3am page. When you do hit it, the fix is to differentiate — a distinct path (/users/by-name/{name}), or a params/headers condition.

The trailing-slash change

  Spring Boot 2.x:  /orders and /orders/ both matched (default)
  Spring Boot 3.x:  they DO NOT. Trailing-slash matching was
                    deprecated in 6.0 and is off by default.

  This breaks real clients on upgrade, silently, with 404s that
  look like a routing bug. If you must restore it temporarily:

    @Configuration
    class WebConfig implements WebMvcConfigurer {
        @Override
        public void configurePathMatch(PathMatchConfigurer c) {
            c.setUseTrailingSlashMatch(true);   // deprecated
        }
    }

  Better: fix the clients, or add a redirect at the ingress. The
  deprecation exists because two URLs for one resource is bad for
  caching, for analytics and for security rules that match on path.

  Part 1 when you genuinely want both routes.

Part 3 — Type Conversion

Every value arrives as a String. Spring converts it, and the mechanism is extensible — which is how you make your domain types bind directly instead of parsing them in every controller.

  BUILT IN, no configuration:
    primitives and wrappers, String, enum (by name),
    LocalDate/LocalDateTime/Instant (ISO-8601),
    UUID, Currency, Locale, Duration (ISO-8601 or "5s"),
    arrays and collections from repeated or comma-separated params,
    Optional<T> for any of the above

  @GetMapping("/orders")
  List<Order> search(
      @RequestParam Set<OrderStatus> status,       // ?status=PAID&status=SHIPPED
      @RequestParam LocalDate from,                // ?from=2026-08-01
      @RequestParam Optional<UUID> batchId) { ... }

  NON-ISO DATE FORMATS need @DateTimeFormat:
    @RequestParam @DateTimeFormat(pattern = "dd/MM/yyyy") LocalDate from

  YOUR OWN TYPES -- register a Converter once, use it everywhere

  public record OrderId(UUID value) {
      public static OrderId parse(String s) { return new OrderId(UUID.fromString(s)); }
  }

  @Component
  class OrderIdConverter implements Converter<String, OrderId> {
      public OrderId convert(String source) { return OrderId.parse(source); }
  }

  // now this just works, in every controller:
  @GetMapping("/orders/{id}")
  Order get(@PathVariable OrderId id) { ... }

  A Converter bean is picked up automatically -- no registration
  needed. This is worth doing early: it moves parsing (and the
  400 for a malformed id) out of every controller into one place,
  and it makes the domain type the parameter type, so you cannot
  accidentally pass a customer id where an order id is expected.
MechanismUse forScope

Part 4 — The Mass-Assignment Vulnerability

@ModelAttribute binds query and form parameters onto an object by matching names to setters. That is convenient, and it is a security hole if the object has fields the user should not control.

  @Entity
  public class User {
      private Long id;
      private String email;
      private String displayName;
      private String role;          // "USER" or "ADMIN"
      private boolean emailVerified;
      // getters and setters for all of them
  }

  @PostMapping("/profile")
  String update(@ModelAttribute User user) {     // BINDS EVERYTHING
      userRepository.save(user);
      return "redirect:/profile";
  }

  THE ATTACK, and it is this simple:

    POST /profile
    displayName=Alice&role=ADMIN&emailVerified=true

  Spring calls setRole("ADMIN") and setEmailVerified(true) because
  the parameter names match setters. The user has just promoted
  themselves.

  MEASURED: one team found this in a code review 14 months after
  the endpoint shipped. Audit of the users table found 3 accounts
  with role=ADMIN that had never been granted it through the admin
  UI. All three were the same curious employee, not an attacker --
  but the vulnerability was identical either way.
DefenceHowStrength
Bind to a DTO, not an entityA record with only the fields a user may setStrongest. Opt-in: a field the DTO does not have cannot be bound
@InitBinder allow-listbinder.setAllowedFields("displayName","email")Good, but per-controller and easy to forget on a new endpoint
@InitBinder deny-listbinder.setDisallowedFields("role")Weak. Opt-out — a new sensitive field is exposed by default
  THE FIX

  public record UpdateProfileRequest(
      @NotBlank @Size(max = 80) String displayName,
      @Email String email) {}

  @PostMapping("/profile")
  String update(@Valid @ModelAttribute UpdateProfileRequest req,
                @AuthenticationPrincipal UserPrincipal principal) {
      userService.updateProfile(principal.id(), req);
      return "redirect:/profile";
  }

  Three things changed and all three matter:
    - the DTO cannot express role or emailVerified, so they cannot
      be bound at any price
    - the user id comes from the AUTHENTICATED PRINCIPAL, not from
      the request -- otherwise the same endpoint lets you edit
      someone else's profile by sending their id
    - @Valid enforces the field constraints declaratively
⚠️ The identity of the acting user must never come from the request body. This is a separate vulnerability from mass assignment and it travels with it. If the DTO or the entity carries an id and you save what you bound, any user can modify any record by changing one parameter. Take the id from @AuthenticationPrincipal or the security context, always — and treat any userId field arriving from a client as untrusted input to be authorised, never as an identity.

@RequestBody is not immune either

  Binding JSON to an entity has the same problem:

    @PutMapping("/users/{id}")
    User update(@PathVariable Long id, @RequestBody User user) {
        return repository.save(user);      // body can contain role
    }

  Jackson populates every matching field. The defences are the same:
  bind to a DTO. @JsonIgnore works but is opt-out, and
  FAIL_ON_UNKNOWN_PROPERTIES (on by default in plain Jackson, but
  DISABLED by Spring Boot's auto-configuration) will not save you
  because "role" is not an unknown property -- it is a real one.

Part 5 — The PATCH Problem

Partial updates expose a gap that plain DTOs cannot express, and it produces a bug that is invisible until a user tries to clear a field.

  public record UpdateUser(String displayName, String phone, String bio) {}

  @PatchMapping("/users/{id}")
  User patch(@PathVariable Long id, @RequestBody UpdateUser req) {
      User u = repository.findById(id).orElseThrow();
      if (req.displayName() != null) u.setDisplayName(req.displayName());
      if (req.phone()       != null) u.setPhone(req.phone());
      if (req.bio()         != null) u.setBio(req.bio());
      return repository.save(u);
  }

  THE BUG: null means two different things and the DTO cannot tell
  them apart.

    { "displayName": "Alice" }              phone absent -> leave it
    { "displayName": "Alice", "phone": null }  phone explicitly
                                               cleared by the user

  Both arrive as phone == null. The null-check treats the second as
  "not provided", so THE USER CANNOT EVER DELETE THEIR PHONE NUMBER.
  Support tickets for this look like "the save button doesn't work",
  and they are very hard to reproduce.
ApproachHowTrade-off
JsonNullable<T>A wrapper with three states: absent, present-null, present-valueCorrect and explicit. Needs the jackson-databind-nullable library
Optional<T> fieldsJackson distinguishes absent from Optional.empty()Works, but Optional as a field is discouraged and needs the JDK8 module
JSON Merge PatchContent-Type: application/merge-patch+json; apply to a JsonNodeStandards-based (RFC 7386), but you lose typed validation
Separate endpointsDELETE /users/{id}/phoneUnambiguous and boring. Often the best answer for a small number of clearable fields
Use PUT insteadClient sends the whole resourceNo ambiguity at all — absent means null. Costs bandwidth and risks lost updates
  public record UpdateUser(
      JsonNullable<String> displayName,
      JsonNullable<String> phone,
      JsonNullable<String> bio) {}

  @PatchMapping("/users/{id}")
  UserResponse patch(@PathVariable Long id, @RequestBody UpdateUser req) {
      User u = repository.findById(id).orElseThrow();
      req.displayName().ifPresent(u::setDisplayName);   // absent -> skipped
      req.phone().ifPresent(u::setPhone);               // null   -> cleared
      req.bio().ifPresent(u::setBio);
      return UserResponse.from(repository.save(u));
  }

  ifPresent() fires when the FIELD was present in the JSON, whether
  its value was null or not. That is exactly the distinction the
  plain record could not make.

Part 6 — Custom Argument Resolvers

When the same derived parameter appears in every controller, a resolver removes the repetition and the chance of getting it wrong once.

  BEFORE -- repeated in 40 methods
    @GetMapping("/orders")
    List<Order> list(@RequestHeader("X-Tenant-Id") String tenantHeader) {
        TenantId tenant = tenantService.resolve(tenantHeader);   // and
        if (!tenant.isActive()) throw new TenantSuspendedException();
        return service.findByTenant(tenant);
    }

  AFTER
    @GetMapping("/orders")
    List<Order> list(CurrentTenant tenant) { return service.findByTenant(tenant); }

  @Component
  class CurrentTenantResolver implements HandlerMethodArgumentResolver {

      private final TenantService tenants;
      CurrentTenantResolver(TenantService tenants) { this.tenants = tenants; }

      @Override
      public boolean supportsParameter(MethodParameter p) {
          return CurrentTenant.class.equals(p.getParameterType());
      }

      @Override
      public Object resolveArgument(MethodParameter p, ModelAndViewContainer mav,
                                    NativeWebRequest req, WebDataBinderFactory b) {
          String header = req.getHeader("X-Tenant-Id");
          if (header == null) throw new MissingTenantException();
          CurrentTenant t = tenants.resolve(header);
          if (!t.isActive()) throw new TenantSuspendedException(t.id());
          return t;
      }
  }

  @Configuration
  class WebConfig implements WebMvcConfigurer {
      private final CurrentTenantResolver resolver;
      WebConfig(CurrentTenantResolver r) { this.resolver = r; }

      @Override
      public void addArgumentResolvers(List<HandlerMethodArgumentResolver> list) {
          list.add(resolver);
      }
  }
Use a resolver whenUse something else when
The value is derived from the request and used by many controllersIt applies to every request regardless of signature — use a filter or interceptor
You want it to be an explicit, typed method parameterYou need to short-circuit the request before mapping — a filter runs earlier
Getting it wrong once would be a security bug (tenant, principal)It is a one-off in a single controller — just read the header
🔑 A resolver makes an implicit dependency explicit and typed. The version with @RequestHeader("X-Tenant-Id") String in every method means 40 opportunities to forget the active-tenant check. The version with CurrentTenant as a parameter cannot be called without the check having run, and a reader can see from the signature that the endpoint is tenant-scoped. That is the same argument as constructor injection over field injection: making the dependency visible is what makes it correct.

Interview Questions

Beginner: What is the difference between @PathVariable, @RequestParam and @RequestBody?

@PathVariable binds a segment of the URL path, declared in the mapping — the {id} in /orders/{id}. It is used for identifying which resource.

@RequestParam binds a query-string parameter, or a field from a form-encoded body. It is used for filtering, paging and options — things that modify the request rather than identify the resource. It is required by default, which surprises people: a missing parameter is a 400, not a null.

@RequestBody binds the entire request body, converted by an HttpMessageConverter — in practice Jackson deserialising JSON into an object. There can be only one per method, and it is used for the payload of POST, PUT and PATCH.

Beginner: How does Spring choose between /users/me and /users/{id}?

By specificity: a literal path segment always beats a path variable. So GET /users/me matches the literal mapping, and GET /users/42 matches the variable one. They coexist safely and the ordering is deterministic, not dependent on declaration order.

The full ordering, most specific first, is: literal segments, then more path variables, then a single wildcard over a double wildcard, then more params/headers conditions, then a more specific media type.

What is not safe is two mappings that differ only in the variable's name — /users/{id} and /users/{name} are both /users/{*} as patterns. Spring cannot distinguish them and fails at startup with an ambiguous-mapping error, which is the right behaviour.

Mid: What is mass assignment and how do you prevent it in Spring?

It is binding request parameters directly onto an object that has fields the user should not control. With @ModelAttribute User user, Spring calls every setter whose name matches a parameter — so a form post of displayName=Alice&role=ADMIN calls setRole("ADMIN") and the user has promoted themselves. The same applies to @RequestBody, where Jackson populates every matching field.

The strongest defence is to bind to a DTO that contains only the fields a user may set. It is opt-in: a field the DTO does not have cannot be bound at any price, and adding a sensitive field to the entity later does not silently expose it.

@InitBinder with setAllowedFields is a reasonable second choice, though it is per-controller and easy to forget on a new endpoint. setDisallowedFields I would argue against — it is opt-out, so the default is exposure.

The related bug that always travels with this one: taking the acting user's id from the request. If the payload carries an id and you save what you bound, any user can edit any record. The identity must come from the authenticated principal.

Mid: How do you implement PATCH so a client can clear a field?

The difficulty is that a plain DTO cannot distinguish "the field was absent" from "the field was explicitly null". Both arrive as null, so the usual null-check treats an explicit clear as "not provided" — and the user can never delete their phone number. The support ticket reads "the save button doesn't work" and is very hard to reproduce.

The clean fix is a wrapper with three states. JsonNullable<T> from jackson-databind-nullable distinguishes absent, present-and-null, and present-with-value, so ifPresent() fires when the field was in the JSON at all — which is exactly the distinction needed.

Alternatives worth knowing: JSON Merge Patch (RFC 7386) is standards-based but gives up typed validation; a dedicated DELETE /users/{id}/phone endpoint is unambiguous and often the right answer when only one or two fields are clearable; and using PUT with the whole resource sidesteps the problem entirely at the cost of bandwidth and a lost-update risk.

Which I would choose depends on how many clearable fields there are. For one or two, separate endpoints are simpler than adding a library. For a profile object with a dozen optional fields, JsonNullable earns its place.

Senior: When would you write a custom HandlerMethodArgumentResolver rather than a filter or interceptor?

When the value is a parameter that specific controllers need, rather than a concern that applies to every request. The distinction I use is whether the thing should be visible in the method signature.

A filter or interceptor runs for every request and communicates through side channels — a ThreadLocal, an MDC entry, a request attribute. That is right for logging, tracing, authentication and rate limiting, where no controller should have to know it happened.

A resolver makes the value an explicit, typed parameter. My usual example is a tenant: with @RequestHeader("X-Tenant-Id") String repeated in 40 methods, there are 40 places to forget the active-tenant check, and a reader cannot tell from the signature that the endpoint is tenant-scoped. With a CurrentTenant parameter, the method cannot be invoked without the resolution and validation having run.

That is the same argument as constructor injection over field injection — making a dependency visible is what makes it correct, and it converts a convention that people must remember into something the type system enforces. The cases where I reach for it are exactly the ones where getting it wrong once would be a security bug.

Senior: You are reviewing an endpoint that binds a form to a JPA entity. Walk through what you would raise.

I would raise four things, in order of severity.

Mass assignment, first. Every settable field on the entity is bindable from a parameter, including role, emailVerified, and anything added to the entity in future. This is a privilege-escalation vulnerability, not a style issue. One team found exactly this fourteen months after shipping, with three accounts holding an ADMIN role never granted through the admin UI.

Identity from the request, second. If the entity has an id and the handler saves what it bound, changing one parameter edits someone else's record. The acting user must come from @AuthenticationPrincipal.

Persisting a partially-populated entity, third. Binding produces an object with only the submitted fields set; saving it can null out columns the form never included. This is a data-loss bug distinct from the security ones, and it is the reason "bind to a DTO, load the entity, copy the permitted fields" is the correct shape rather than an extra step.

Coupling, fourth. The entity's field names have become the form's parameter names, so a schema refactor breaks the UI.

The fix for all four is the same: a request DTO with only user-settable fields, @Valid, the id from the principal, and a service method that loads the entity and applies the permitted changes. I would also suggest an ArchUnit rule asserting that no controller method parameter is an @Entity type — the review caught it this time, and a rule catches it every time.

🏋️ Exercises

1 (easy): Which method handles each request, and which pair fails at startup? 
  a) @GetMapping("/users/me")            profile()
  b) @GetMapping("/users/{id}")          byId(@PathVariable Long id)
  c) @GetMapping("/users/{username}")    byName(@PathVariable String username)
  d) @GetMapping("/users/**")            catchAll()

  Requests:  GET /users/me     GET /users/42     GET /users/a/b
Solution

The application does not start. Mappings (b) and (c) are both the pattern /users/{*} — the variable's name is not part of the pattern — so Spring cannot distinguish them and throws IllegalStateException: Ambiguous mapping at startup.

Assuming (c) is removed, the routing is:

RequestHandlerWhy
GET /users/me(a) profile()A literal segment beats a path variable
GET /users/42(b) byId()A path variable beats a double wildcard
GET /users/a/b(d) catchAll()Only ** matches multiple segments

If you genuinely want both id and username lookups, differentiate the patterns with a regex so they are no longer identical:

  @GetMapping("/users/{id:[0-9]+}")        User byId(@PathVariable Long id)
  @GetMapping("/users/{username:[a-z].*}") User byName(@PathVariable String username)

Distinct paths — /users/by-name/{username} — are also fine and arguably clearer, since a regex in a mapping is easy to miss when reading. I would prefer the explicit path for a public API and the regex only when the URL shape is fixed by an existing contract.

2 (easy): Fix the binding problems. 
  @GetMapping("/orders")
  List<Order> search(
      @RequestParam String status,
      @RequestParam String from,
      @RequestParam(required = false) String sort) {

      LocalDate fromDate = LocalDate.parse(from);

Solution

ProblemFix

Spring's conversion layer produces a MethodArgumentTypeMismatchException, which a @ControllerAdvice maps to a 400 with a useful message — for free, consistently, across every endpoint.

Note the enum case-sensitivity change: Spring matches enum constants exactly, so ?status=paid now fails where toUpperCase() accepted it. If lower-case values are part of an existing contract, register a Converter<String, OrderStatus> rather than reverting.

  public record UpdateAccountRequest(
      @NotBlank @Size(max = 80) String displayName,
      @NotBlank @Email String email) {}

  @PostMapping("/account/update")
  String update(@Valid @ModelAttribute UpdateAccountRequest req,
                @AuthenticationPrincipal AccountPrincipal principal) {
      accountService.updateProfile(principal.id(), req);
      return "redirect:/account";
  }

  @Service
  class AccountService {
      @Transactional
      public void updateProfile(Long accountId, UpdateAccountRequest req) {
          Account a = accounts.findById(accountId).orElseThrow();
          a.setDisplayName(req.displayName());     // only these two
          a.setEmail(req.email());
      }
  }

Problem 4 is the one that gets missed, and it is worth dwelling on because it is not a security bug. Binding creates a new Account with only the submitted fields populated; everything else is null. Calling save() on it overwrites the stored row, wiping balance, role and verified. Even with no attacker, a legitimate user updating their display name silently destroys their own balance.

That is why the correct shape is always bind a DTO → load the entity → apply permitted fields, not bind an entity → save. The load step is what preserves everything the request did not mention.

What I would add beyond the fix: an ArchUnit rule that no controller method parameter is annotated @Entity. This review caught it once; the rule catches it on every future endpoint, including the ones written under deadline pressure.

      User u = repo.findById(me.id()).orElseThrow();
      if (req.displayName() != null) u.setDisplayName(req.displayName());
      if (req.bio()         != null) u.setBio(req.bio());
      if (req.website()     != null) u.setWebsite(req.website());
      return Profile.from(repo.save(u));
  }
Solution

Diagnosis. The client sends {"bio": null} to clear the field, and {"displayName": "Alice"} — with bio absent — to leave it alone. Both deserialise to bio == null. The null-check treats the explicit clear as "not provided", so the bio is never cleared. The UI appears to save successfully and the old value persists.

This is the reason such tickets are hard to reproduce: everything works except the one path nobody tests, and the request is well-formed.

  // build.gradle: implementation 'org.openapitools:jackson-databind-nullable'
  // and register the module (Boot picks up Module beans automatically):
  @Bean JsonNullableModule jsonNullableModule() { return new JsonNullableModule(); }

  public record UpdateProfile(
      JsonNullable<String> displayName,
      JsonNullable<String> bio,
      JsonNullable<String> website) {}

  @PatchMapping("/profile")
  Profile patch(@RequestBody UpdateProfile req,
                @AuthenticationPrincipal UserPrincipal me) {
      User u = repo.findById(me.id()).orElseThrow();
      req.displayName().ifPresent(u::setDisplayName);
      req.bio().ifPresent(u::setBio);          // null -> cleared
      req.website().ifPresent(u::setWebsite);
      return Profile.from(repo.save(u));
  }

ifPresent() fires when the field appeared in the JSON at all, regardless of its value — exactly the three-state distinction the plain record could not represent.

Validation caveat worth knowing: constraints on a JsonNullable field need the wrapper unwrapped — @NotBlank on JsonNullable<String> does not do what you expect. Either validate inside the service, or use JsonNullable<@Size(max = 500) String> with a validator that supports value extraction.

The alternative I would consider first for a small API: if only bio and website are clearable, two endpoints — DELETE /profile/bio — are unambiguous, need no library, and are trivially testable. I would reach for JsonNullable when there are many optional fields, and for the explicit endpoint when there are two.

5 (hard): Every endpoint in a 40-controller multi-tenant application starts by reading and validating an X-Tenant-Id header. Design the removal of that duplication, and compare the options.
Solution
OptionMechanismVerdict
Argument resolverCurrentTenant as a typed method parameterChoose this. Explicit, typed, and impossible to invoke the method without resolution having run
Filter + ThreadLocalSet context early, read it anywhereWorks, but the dependency is invisible; breaks across @Async; easy to leak between pooled threads if not cleared
Interceptor + request attributerequest.getAttribute("tenant")Untyped, requires a cast, and every controller must remember to read it
Request-scoped beanInject a proxySame ThreadLocal limitations; see Bean Scopes & Lifecycle
Leave it40 controllers keep repeating it40 chances to omit the active-tenant check — a cross-tenant data leak waiting to happen
  @Component
  class CurrentTenantResolver implements HandlerMethodArgumentResolver {
      private final TenantService tenants;
      CurrentTenantResolver(TenantService tenants) { this.tenants = tenants; }

      public boolean supportsParameter(MethodParameter p) {
          return CurrentTenant.class.equals(p.getParameterType());
      }

      public Object resolveArgument(MethodParameter p, ModelAndViewContainer m,
                                    NativeWebRequest req, WebDataBinderFactory b) {
          String header = req.getHeader("X-Tenant-Id");
          if (header == null || header.isBlank())
              throw new MissingTenantException();
          CurrentTenant t = tenants.resolve(header);   // throws UnknownTenant
          if (!t.isActive()) throw new TenantSuspendedException(t.id());
          return t;
      }
  }

Why the resolver beats the filter here specifically. Both eliminate the duplication. The difference is what a reader and the compiler can see. With a filter, an endpoint that is tenant-scoped and one that is not look identical, and a new controller that forgets to read the context compiles and runs — returning data across tenants. With a resolver, the parameter is in the signature, so the scoping is visible in review and the method cannot execute without the check.

What I would still put in a filter: the tenant id in the logging MDC, so every log line is attributable. That genuinely applies to every request including error paths, and no controller should have to know about it. The two mechanisms are complementary, not competing.

The migration, since 40 controllers cannot change at once: add the resolver, then convert controllers incrementally — both forms work simultaneously because the resolver only triggers on the new parameter type. Then add an ArchUnit rule forbidding @RequestHeader("X-Tenant-Id") so no new endpoint reintroduces the old pattern, and finally delete the last stragglers.

The security concern I would raise separately: a tenant id in a client-supplied header is only as trustworthy as your authorisation. The resolver must verify that the authenticated principal is entitled to that tenant, not merely that the tenant exists — otherwise the header is an invitation to read another customer's data. That check belongs in the resolver, which is another argument for having exactly one of them.

6 (hard): Design the request-binding layer for a public API with strict backwards-compatibility guarantees, three client generations, and a security review requirement.
Solution

The constraint that shapes everything: a public API's request shape is a contract you cannot change. So the binding layer's job is to make the contract explicit, reviewable, and decoupled from anything internal.

  1. VERSIONED REQUEST DTOs -- never entities, never shared with the domain

     package com.acme.api.v2.request;
     public record CreateOrderRequest(
         @NotNull @Size(max=64)  String idempotencyKey,
         @NotEmpty @Size(max=100) List<@Valid LineItem> items,
         @NotNull ShippingAddress shipping) {

         public CreateOrderCommand toCommand(CustomerId customer) { ... }
     }

  2. VERSION BY HEADER, not by URL path

     @PostMapping(value = "/orders", headers = "X-Api-Version=2")
     ResponseEntity<OrderResponseV2> createV2(@Valid @RequestBody CreateOrderRequest r)

     @PostMapping(value = "/orders", headers = "X-Api-Version=1")
     @Deprecated
     ResponseEntity<OrderResponseV1> createV1(@Valid @RequestBody CreateOrderRequestV1 r)

  3. EXPLICIT PARAMETER NAMES everywhere

     @RequestParam("customer_id") CustomerId customerId

     -- so a Java parameter rename is never a breaking API change,
        and binding does not depend on the -parameters compiler flag

  4. DOMAIN TYPES VIA CONVERTERS

     @Component class CustomerIdConverter implements Converter<String, CustomerId>

     -- one place that parses and rejects malformed ids, with one
        consistent 400 across every endpoint
DecisionReason
Header versioning over URL versioningThe resource identity stays stable — /orders is always /orders — so caches, links and analytics do not fragment per version. The trade is that it is less obvious in a browser, which is why I would also accept a URL form if the API is browsed by humans
Separate DTO per version, no sharingSharing a DTO between versions means changing v2 silently changes v1. Duplication here is correct: the versions are genuinely different contracts with different lifetimes
DTOs in a version-scoped packageMakes "what is v1's contract?" answerable by listing a directory, and makes deleting a version a package deletion
@Size on every collectionAn unbounded list in a public API is a denial-of-service vector — 100,000 line items is a valid request otherwise
Idempotency key as a required fieldPublic clients retry. Without it, a network timeout on POST creates duplicate orders and the client cannot tell

For the security review, the properties I would want to be able to demonstrate: no controller parameter is an entity (enforced by an ArchUnit rule, not by discipline); no identity is taken from a request body (the principal is always @AuthenticationPrincipal); every collection and string has a bound; and every DTO field is one a client is permitted to set, provable by reading the record declaration rather than by auditing an entity's annotations.

What I would deliberately not do: accept arbitrary JSON into a Map or JsonNode for flexibility. It makes every field an undocumented, unvalidated part of the contract, and it defeats the review property above — you cannot demonstrate what a client may set if the answer is "anything".

The hard trade-off I would put to the team: three client generations means three request shapes to keep working, and each one constrains refactoring. I would want a written deprecation policy with dates attached, because the alternative is that v1 lives forever and every future change costs three times. That is a product decision, not an engineering one, and it should be made deliberately rather than by default.

🎯 Key Takeaways

  • Mappings are chosen by specificity, most specific first: literals, then path variables, then single wildcard, then more conditions, then media type.
  • A literal beats a variable, so /users/me and /users/{id} coexist safely.
  • The variable's name is not part of the pattern — /users/{id} and /users/{name} are ambiguous and fail at startup.
  • Regex constraints ({id:[0-9]+}) disambiguate when you genuinely need two similar routes.
  • Trailing-slash matching is off in Boot 3 — a silent source of 404s after an upgrade.
  • Binding to an entity is a mass-assignment vulnerability. One team's users could set their own role=ADMIN with a form parameter.
  • A DTO is opt-in; setDisallowedFields is opt-out. Prefer the one whose default is safe.
  • The acting user's identity must never come from the request — always @AuthenticationPrincipal.
  • Saving a bound entity nulls every column the form omitted. Always bind a DTO, load the entity, then apply permitted fields.
  • A plain DTO cannot distinguish "absent" from "explicitly null", so users can never clear a PATCH field.
  • JsonNullable<T> gives the three states PATCH needs; a dedicated DELETE endpoint is simpler when only a field or two is clearable.
  • Every manual parse in a controller is a 500 waiting to happen. Declare the real type and let Spring's conversion produce a clean 400.
  • A Converter<String,T> bean is picked up automatically and makes domain types bind natively everywhere.
  • @RequestParam is required by default; use defaultValue or Optional.
  • Name parameters explicitly so binding never depends on the -parameters flag and a rename is not a breaking change.
  • Use a resolver for typed parameters, a filter for ambient concerns. The resolver makes the dependency visible in the signature and impossible to skip.
  • Bound every collection parameter — an unbounded list is a denial-of-service vector.
