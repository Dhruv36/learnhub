Spring Security Cross-Cutting

What you'll master: the architecture that makes everything else make sense — Spring Security is a chain of servlet filters that runs entirely before Spring MVC, which is why your @ControllerAdvice cannot handle a 401 and why a security rule can never be bypassed by a controller; the difference between authentication and authorisation stated precisely enough to be useful, and the SecurityContextHolder ThreadLocal that carries the answer — including why it is empty in every @Async method and the one-line fix; the Boot 3 configuration model, since WebSecurityConfigurerAdapter is gone and every pre-2022 tutorial you find is wrong; why permitAll() order matters — one team put a catch-all rule first and made every endpoint in the application public for eleven days; CSRF explained by the attack it prevents, so you can tell when disabling it is correct and when it is negligent; method security versus URL security and why the former is the one that survives refactoring; password storage, where the only correct answer is a deliberately slow adaptive hash; and JWT versus sessions with the trade-off that actually decides it (you cannot revoke a JWT, and pretending otherwise is how teams build a session store with extra steps). Prerequisites: REST Controllers and AOP & Proxies.

Part 1 — It Is a Filter Chain

  HTTP request
      │
      ▼
  ┌── Servlet container ─────────────────────────────────────┐
  │  springSecurityFilterChain  (a FilterChainProxy bean)     │
  │                                                            │
  │   1. SecurityContextHolderFilter   restore the context     │
  │   2. CsrfFilter                    validate the token      │
  │   3. LogoutFilter                                          │
  │   4. UsernamePasswordAuthenticationFilter  form login      │
  │   5. BearerTokenAuthenticationFilter       JWT / OAuth2    │
  │   6. ExceptionTranslationFilter    401/403 handling        │
  │   7. AuthorizationFilter           the URL rules           │
  │                                                            │
  │   ~15 filters by default, in a fixed order                 │
  └────────────────────────┬───────────────────────────────────┘
                           ▼
                   DispatcherServlet  →  your controller

  TWO CONSEQUENCES THAT EXPLAIN MOST QUESTIONS:

  1. Security runs BEFORE Spring MVC. A 401 or 403 never reaches
     your @ControllerAdvice, because no controller was ever invoked.
     To customise those responses you configure an
     AuthenticationEntryPoint / AccessDeniedHandler, not an
     @ExceptionHandler.

  2. A controller cannot bypass a URL rule, because the rule was
     already evaluated. Security is not advice on your code -- it is
     a gate in front of it.

  SEE THE CHAIN for any request:

    logging.level.org.springframework.security: DEBUG

    Securing GET /api/orders
    Set SecurityContextHolder to JwtAuthenticationToken [...]
    Authorized filter invocation [GET /api/orders] with attributes
      [authenticated]
    Secured GET /api/orders

  This single setting answers nearly every "why was I rejected?"
  question, and it names the exact filter that made the decision.
🔑 Authentication answers "who are you?" and produces a Principal. Authorisation answers "may you do this?" and produces a yes or no. The HTTP codes follow: 401 means not authenticated (log in and try again) and 403 means authenticated but not permitted (logging in again will not help). The name "Unauthorized" for 401 is a historical error in the spec and the source of endless confusion.

Part 2 — Configuration in Boot 3

  WebSecurityConfigurerAdapter WAS REMOVED in Spring Security 6.
  Every tutorial that extends it is wrong. The replacement is a
  SecurityFilterChain bean.

  @Configuration
  @EnableWebSecurity
  public class SecurityConfig {

      @Bean
      SecurityFilterChain api(HttpSecurity http) throws Exception {
          return http
              .securityMatcher("/api/**")
              .csrf(csrf -> csrf.disable())               // see Part 4
              .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
              .authorizeHttpRequests(auth -> auth
                  .requestMatchers("/api/public/**").permitAll()
                  .requestMatchers(HttpMethod.GET, "/api/orders/**")
                      .hasAuthority("SCOPE_orders:read")
                  .requestMatchers("/api/admin/**").hasRole("ADMIN")
                  .anyRequest().authenticated())          // LAST, always
              .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
              .exceptionHandling(e -> e
                  .authenticationEntryPoint(problemDetailEntryPoint())
                  .accessDeniedHandler(problemDetailDeniedHandler()))
              .build();
      }

      @Bean
      PasswordEncoder passwordEncoder() {
          return PasswordEncoderFactories.createDelegatingPasswordEncoder();
      }
  }

  tests passed because they sent credentials anyway, and the only
  symptom was the absence of 401s in the logs, which nobody was

   - most specific first, anyRequest() ALWAYS last
   - never put permitAll() on a broad pattern
   - alert on "count of 401 responses == 0", which is the signal
     that would have caught this on day one

Part 3 — SecurityContextHolder

  Authentication auth = SecurityContextHolder.getContext().getAuthentication();
  String username = auth.getName();
  Collection<? extends GrantedAuthority> authorities = auth.getAuthorities();

  IT IS A ThreadLocal. That single fact produces the common bugs:

  IN A CONTROLLER -- prefer injection over the static holder:
      @GetMapping("/me")
      Profile me(@AuthenticationPrincipal UserPrincipal user) { ... }

      Testable without a security context, explicit in the signature,
      and typed.

  IN @Async -- THE CONTEXT IS EMPTY:
      @Async
      public void process() {
          SecurityContextHolder.getContext().getAuthentication();  // null
      }

      FIX, application-wide:
        SecurityContextHolder.setStrategyName(
            SecurityContextHolder.MODE_INHERITABLETHREADLOCAL);
      or, better and pool-safe:
        @Bean
        TaskDecorator securityAwareDecorator() {
            return runnable -> {
                SecurityContext ctx = SecurityContextHolder.getContext();
                return () -> {
                    SecurityContextHolder.setContext(ctx);
                    try { runnable.run(); }
                    finally { SecurityContextHolder.clearContext(); }
                };
            };
        }

  THE finally IS NOT OPTIONAL. Without it a pooled thread retains
  the previous request's principal, and the next task on that thread
  runs as the wrong user. That is a cross-user data leak, not a
  bug you can ship and fix later.

Part 4 — CSRF, Explained by the Attack

  THE ATTACK

  1. You log in to bank.com. The browser stores a session cookie.
  2. You visit evil.com, which contains:

       <form action="https://bank.com/transfer" method="POST">
         <input name="to" value="attacker">
         <input name="amount" value="1000">
       </form>
       <script>document.forms[0].submit()</script>

  3. The browser sends the request TO BANK.COM WITH YOUR COOKIE,
     because cookies are attached by ORIGIN, not by which page
     initiated the request.
  4. bank.com sees a valid session and transfers the money.

  THE DEFENCE: require a value the attacker cannot read or guess --
  a CSRF token in a header or form field. evil.com cannot read
  bank.com's DOM or cookies (same-origin policy), so it cannot
  supply it.

  WHEN IS CSRF PROTECTION UNNECESSARY?
    ONLY when the browser does not attach credentials automatically.

    Cookie/session auth        -> REQUIRED
    Authorization: Bearer ...  -> not needed; the attacker cannot
                                  make the browser attach a header
    Basic auth in a browser    -> required (browsers cache and
                                  re-send it)

  So `csrf.disable()` is correct for a stateless token API and
  NEGLIGENT for a cookie-authenticated one. The mistake is copying
  the line from a JWT tutorial into a session-based app.

  CSRF WITH A JAVASCRIPT FRONT END (cookie-based auth)

    http.csrf(csrf -> csrf
        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
        .csrfTokenRequestHandler(new SpaCsrfTokenRequestHandler()));

  The token goes into a readable XSRF-TOKEN cookie; the SPA reads it
  and echoes it in an X-XSRF-TOKEN header. Axios and Angular do this
  automatically.

  ALSO SET SameSite, which is defence in depth, not a replacement:

    server.servlet.session.cookie.same-site: lax
    server.servlet.session.cookie.secure: true
    server.servlet.session.cookie.http-only: true

  SameSite=Lax blocks the cross-site POST above in modern browsers.
  It is not sufficient alone: it does not protect older browsers,
  and it does not protect against same-site subdomain attacks.

      public void bulkUpdate(List<Order> orders) { ... }
  }

⚠️ @PostAuthorize runs after the method, including its side effects. On a read it is fine — the object is fetched and then the check rejects it. On anything that writes, the write has already happened and only the response is suppressed, in a transaction that is not rolled back by the access-denied exception unless it propagates out of the transactional boundary. Never use @PostAuthorize on a mutating method; check the ownership before acting, with @PreAuthorize and a guard bean.

Part 6 — Passwords, Sessions and JWTs

  PASSWORD STORAGE -- the only correct shape

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }

  Stores hashes prefixed with the algorithm:
    {bcrypt}$2a$10$N9qo8uLOickgx2ZMRZoMye...

  WHY THE PREFIX MATTERS: you can migrate algorithms without a big
  bang. Old hashes keep verifying with their original algorithm;
  new ones use the current default; and you can re-encode on
  successful login.

  THE PROPERTY THAT MATTERS: the hash must be SLOW and adaptive.
    SHA-256      ~ 1,000,000,000 guesses/sec on a GPU
    bcrypt(10)   ~        20,000 guesses/sec
    argon2id     ~         5,000 guesses/sec, and memory-hard

  NEVER: MD5, SHA-1, SHA-256, "SHA-256 with a salt", or anything you
  designed. Fast hashes are the wrong tool -- speed is the
  vulnerability.

  SESSIONS vs JWT -- the trade-off that actually decides it

                        Session cookie        JWT
  ────────────────────  ────────────────────  ────────────────────
  State                 server-side store     none (self-contained)
  Horizontal scaling    needs shared store    trivially stateless
                        (Redis)
  REVOCATION            immediate --          IMPOSSIBLE until it
                        delete the session    expires
  Size per request      ~32 bytes             ~800+ bytes
  Works cross-domain    awkward               easy
  CSRF                  required              not applicable
  XSS impact            httpOnly cookie is    a token in
                        not readable by JS    localStorage IS

  THE DECIDING QUESTION: what happens when you need to log someone
  out RIGHT NOW -- a compromised account, a fired employee, a
  revoked API key?

  With sessions: delete the row. Done.
  With JWTs: you cannot. The token remains valid until it expires.

  THE USUAL "FIX" -- a revocation blacklist checked on every request
  -- reintroduces exactly the shared state that JWTs were chosen to
  avoid, plus a network hop, plus a new failure mode. At that point
  you have built a session store with extra steps and worse
  ergonomics.

  MY DEFAULT: sessions with Spring Session + Redis for a first-party
  web app; JWTs for service-to-service and third-party API access,
  with SHORT expiry (5-15 min) and refresh tokens that ARE
  revocable and stored server-side.

Interview Questions

Beginner: How does Spring Security work at a high level?

It is a chain of servlet filters registered in front of the application — roughly fifteen by default, in a fixed order. Early filters restore the security context and attempt authentication from a cookie, header or form submission; later ones evaluate the authorisation rules for the request.

The important structural point is that all of this happens before Spring MVC. The DispatcherServlet is only reached if the request passes, which is why a controller cannot bypass a security rule, and equally why a 401 or 403 never reaches your @ControllerAdvice — no controller was ever invoked.

Beginner: What is the difference between 401 and 403?

401 means not authenticated — we do not know who you are, so log in and try again. 403 means authenticated but not permitted — we know who you are and you may not do this, so logging in again will not help.

The confusion comes from the spec calling 401 "Unauthorized", which is simply a naming error that has been preserved for compatibility. In Spring, 401 comes from the AuthenticationEntryPoint and 403 from the AccessDeniedHandler.

One nuance worth adding: where a resource's very existence is sensitive, returning 403 tells an attacker the resource exists. In those cases 404 is the safer answer.

Mid: When is it acceptable to disable CSRF protection?

Only when the browser does not attach credentials automatically. CSRF works because a cookie is sent based on the request's destination, not on which page initiated it — so a form on evil.com can POST to bank.com with your session cookie attached.

If authentication is a bearer token in an Authorization header, the attacker cannot make the browser add that header, so there is nothing to forge and disabling CSRF is correct. If authentication is a cookie or HTTP Basic in a browser, CSRF protection is required, and disabling it is negligent.

The mistake I see most often is copying csrf.disable() out of a JWT tutorial into a session-based application, where it silently makes every state-changing endpoint vulnerable. I would also set SameSite=Lax on the session cookie as defence in depth, while being clear that it is not a replacement — it does not help older browsers or same-site subdomain attacks.

Mid: Why is SecurityContextHolder empty inside an @Async method?

Because it stores the context in a ThreadLocal, and @Async executes the method on a different thread from a pool. That thread has no context, so getAuthentication() returns null.

The fix is a TaskDecorator on the executor that captures the context before submission and installs it on the worker thread. The critical detail is clearing it in a finally block: pooled threads are reused, so without the clear the next task on that thread inherits the previous request's principal. That is a cross-user data leak, and it is far worse than the original null.

MODE_INHERITABLETHREADLOCAL also works for threads created directly, but it does not help with pooled executors, which is where the problem usually arises.

Senior: URL-based or method-based security?

Both, with method security as the real boundary and URL rules as a coarse outer gate.

URL rules are cheap and they run before anything else, which makes them right for broad statements — /actuator/** is internal, /api/** requires authentication. But they are coupled to paths, so renaming an endpoint silently stops a rule matching, and they protect only HTTP. A Kafka consumer or scheduled job invoking the same service gets no protection at all.

Method security sits on the service layer, so it survives URL refactoring and covers every caller regardless of transport. It also sees arguments, which is what ownership checks need — @PreAuthorize("@orderGuard.isOwner(#orderId, authentication)") is the kind of rule URL security cannot express.

Two caveats I would raise. It is implemented by a proxy, so self-invocation bypasses it entirely — the same trap as @Transactional. And @PostAuthorize runs after the method has already executed, so it must never guard a mutating operation; the write has happened and only the response is suppressed.

Senior: Sessions or JWTs?

The question I use to decide is: what happens when you need to revoke access right now — a compromised account, a departing employee, a leaked key?

With a server-side session you delete the row and the next request fails. With a JWT you cannot: the token is self-contained and valid until it expires. The common answer is a revocation blacklist checked on every request, but that reintroduces exactly the shared state JWTs were chosen to avoid, adds a network hop to every request, and creates a new availability dependency. At that point you have built a session store with worse ergonomics.

So my default is sessions — with Spring Session and Redis if horizontal scaling matters — for first-party web applications, and JWTs for service-to-service and third-party API access where statelessness genuinely pays and revocation windows are acceptable.

When JWTs are the right choice, I would keep access tokens short-lived (5–15 minutes) and pair them with refresh tokens that are stored server-side and revocable. That gives most of the statelessness benefit on the hot path while keeping a real revocation mechanism.

The other factor worth stating is storage: a JWT in localStorage is readable by any XSS, whereas an httpOnly cookie is not. Teams often adopt JWTs for security reasons and then store them in the one place that makes an XSS bug into a full account takeover.

🏋️ Exercises

1 (easy): What is wrong with this configuration? 
  http.authorizeHttpRequests(auth -> auth
      .anyRequest().permitAll()
      .requestMatchers("/api/admin/**").hasRole("ADMIN")
      .requestMatchers("/api/**").authenticated());
Solution

Rules are evaluated top to bottom and the first match wins. anyRequest() matches every request, so it matches /api/admin/** before the admin rule is ever consulted. Both later rules are dead code, and every endpoint in the application is public.

  http.authorizeHttpRequests(auth -> auth
      .requestMatchers("/api/public/**").permitAll()
      .requestMatchers("/api/admin/**").hasRole("ADMIN")
      .requestMatchers("/api/**").authenticated()
      .anyRequest().denyAll());          // explicit default-deny
ChangeWhy
Most specific firstMatching is ordered; specificity must decrease down the list
anyRequest() lastIt is a catch-all and can only ever be the final rule
denyAll() rather than authenticated()A new endpoint added outside /api/** is then denied by default rather than silently exposed

Why this is worth taking seriously: this exact ordering reached production and survived eleven days. Nothing failed — authenticated users worked normally, and the test suite passed because the tests sent credentials anyway. The only observable symptom was the absence of 401 responses.

Two things would have caught it: an alert on "count of 401s over 24h == 0", and a test that asserts an unauthenticated request to a protected endpoint returns 401. The second is three lines and belongs in every project — security configuration is exactly the kind of code where the failure mode is silence rather than an exception.

2 (easy): A @ControllerAdvice handles every exception, but 401 and 403 responses still return Spring's default body. Explain and fix.
Solution

Security runs in the filter chain, before the DispatcherServlet. When authentication or authorisation fails, no controller is invoked, so no @ExceptionHandler can possibly run — the request never reached Spring MVC.

  @Bean
  SecurityFilterChain chain(HttpSecurity http) throws Exception {
      return http
          .exceptionHandling(e -> e
              .authenticationEntryPoint((req, res, ex) -> {   // 401
                  res.setStatus(401);
                  res.setContentType("application/problem+json");
                  res.getWriter().write("""
                      {"type":"https://api.acme.com/problems/unauthenticated",
                       "title":"Authentication required","status":401}""");
              })
              .accessDeniedHandler((req, res, ex) -> {        // 403
                  res.setStatus(403);
                  res.setContentType("application/problem+json");
                  res.getWriter().write("""
                      {"type":"https://api.acme.com/problems/forbidden",
                       "title":"Access denied","status":403}""");
              }))
          .build();
  }
HandlerFires when
AuthenticationEntryPointThe user is not authenticated → 401
AccessDeniedHandlerAuthenticated but not permitted → 403

The exception to this rule is AccessDeniedException thrown by method security. That happens inside the controller call stack, after MVC has taken over, so it does reach @ControllerAdvice. Which means a complete application needs both mechanisms — and if the two produce different response shapes, clients see inconsistent 403s depending on which layer rejected them. Worth making them identical deliberately.

For consistency I would extract the JSON generation into a shared component used by both the handlers and the advice, rather than duplicating the literal.

3 (medium): After adding @Async, an audit aspect started recording the wrong username — sometimes a different user entirely. Diagnose and fix.
Solution

Diagnosis. SecurityContextHolder uses a ThreadLocal. An @Async method runs on a pooled thread, which has no context — so the first symptom is a null principal.

The "wrong user entirely" symptom means someone has already applied a partial fix: either MODE_INHERITABLETHREADLOCAL, or a TaskDecorator that copies the context but never clears it. Because the executor's threads are reused, a thread retains the previous task's principal after finishing, and the next task on that thread runs as that user.

That is a cross-user data leak, and it is intermittent and load-dependent — the worst combination to debug.

  @Bean
  TaskDecorator securityContextDecorator() {
      return runnable -> {
          SecurityContext captured = SecurityContextHolder.getContext();
          return () -> {
              SecurityContext previous = SecurityContextHolder.getContext();
              SecurityContextHolder.setContext(captured);
              try {
                  runnable.run();
              } finally {
                  SecurityContextHolder.setContext(previous);   // ALWAYS
              }
          };
      };
  }

  @Bean
  ThreadPoolTaskExecutor taskExecutor(TaskDecorator decorator) {
      var ex = new ThreadPoolTaskExecutor();
      ex.setTaskDecorator(decorator);
      ex.setCorePoolSize(4);
      ex.initialize();
      return ex;
  }
DetailWhy it matters
Capture outside the returned lambdaThe capture must happen on the submitting thread, not the worker
Restore in finallyThe whole fix. Without it, pooled threads leak principals between users
Restore the previous context, not clearContext()Slightly safer with nested executors; either is acceptable as long as it always runs

What I would add: Spring Security ships DelegatingSecurityContextAsyncTaskExecutor, which does exactly this correctly. I would use it rather than hand-rolling, and treat the hand-rolled version as something to recognise in review.

The deeper design point: ambient thread-local identity is fragile across every async boundary — @Async, CompletableFuture, parallel streams, reactive pipelines. Where correctness genuinely matters, I would pass the acting user as an explicit method parameter. It is more typing and it survives every threading model, which is the same argument made for request scope in Bean Scopes & Lifecycle.

4 (medium): Users can read other users' orders by changing the id in the URL. The endpoint requires authentication. Fix it properly. 
  @GetMapping("/api/orders/{id}")
  public OrderResponse get(@PathVariable Long id) {
      return OrderResponse.from(orderService.find(id));
  }

  // security config
  .requestMatchers("/api/orders/**").authenticated()
Solution

This is broken object-level authorisation — the endpoint checks whether you are logged in, never which records you may see. URL rules fundamentally cannot express this, because the answer depends on the data behind the id.

  @Component("orderGuard")
  public class OrderGuard {
      private final OrderRepository orders;

      public boolean canRead(Long orderId, Authentication auth) {
          return orders.findCustomerIdById(orderId)      // projection, 1 column
                       .map(customerId -> customerId.equals(currentUserId(auth)))
                       .orElse(false);                   // absent -> deny
      }
  }

  @Service
  public class OrderService {
      @PreAuthorize("@orderGuard.canRead(#id, authentication)")
      public Order find(Long id) { ... }
  }
DecisionReason
@PreAuthorize, not @PostAuthorizeCheck before loading. @PostAuthorize would work for a read, but establishing the habit matters — on a mutating method it would let the write happen first
On the service, not the controllerA Kafka consumer or scheduled job calling find() is protected too, and a URL rename cannot silently disable it
A projection in the guardLoads one column rather than the whole entity, so the check is cheap enough to run on every call
.orElse(false)A missing order denies rather than throwing — fail closed

The question the fix raises: 403 or 404? Returning 403 for someone else's order confirms that order exists, which for sequential ids is an enumeration oracle — an attacker can map your order volume. For anything with guessable identifiers I would return 404 for both "does not exist" and "not yours", and I would make that a documented, deliberate choice rather than whatever the default produces.

The alternative worth considering: scope the query itself — findByIdAndCustomerId(id, currentUserId()). The unauthorised row is then never loaded at all, and the endpoint naturally returns 404. It is often simpler than a guard, and it makes the security property a consequence of the query rather than a check layered on top.

Prevention: broken object-level authorisation is consistently the most common serious API vulnerability, and it is invisible in code review because the endpoint looks secured. A test per resource type — authenticate as user A, request user B's record, assert not-200 — is the cheapest control available.

5 (hard): Design authentication for a system with a browser SPA, a mobile app, and third-party API clients. Justify the choices.
Solution

Three clients with genuinely different constraints — one mechanism for all three would be wrong for at least two of them.

ClientMechanismWhy
Browser SPASession cookie, httpOnly + Secure + SameSite=Lax, with CSRF tokensAn httpOnly cookie is unreadable by XSS; a token in localStorage is not. Immediate revocation. Same-origin, so cookies are natural
Mobile appOAuth2 with PKCE; short-lived access token + revocable refresh token in the platform keystoreNo cookie jar to rely on; PKCE handles the public-client problem; the keystore is hardware-backed
Third-party APIOAuth2 client credentials, scoped access tokensNo user present; scopes give per-integration least privilege and independent revocation
  // separate filter chains, ordered -- @Order matters
  @Bean @Order(1)
  SecurityFilterChain api(HttpSecurity http) throws Exception {
      return http
          .securityMatcher("/api/**")
          .csrf(c -> c.disable())                      // bearer tokens
          .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
          .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(
              scopeConverter())))
          .authorizeHttpRequests(a -> a
              .requestMatchers(GET, "/api/orders/**").hasAuthority("SCOPE_orders:read")
              .requestMatchers(POST, "/api/orders/**").hasAuthority("SCOPE_orders:write")
              .anyRequest().denyAll())
          .build();
  }

  @Bean @Order(2)
  SecurityFilterChain web(HttpSecurity http) throws Exception {
      return http
          .securityMatcher("/**")
          .csrf(c -> c.csrfTokenRepository(
              CookieCsrfTokenRepository.withHttpOnlyFalse()))   // cookies
          .sessionManagement(s -> s
              .sessionCreationPolicy(IF_REQUIRED)
              .maximumSessions(5))
          .formLogin(Customizer.withDefaults())
          .authorizeHttpRequests(a -> a
              .requestMatchers("/", "/login", "/assets/**").permitAll()
              .anyRequest().authenticated())
          .build();
  }

Why two chains rather than one: the CSRF and session requirements are opposites. The API is stateless with bearer tokens, so CSRF does not apply; the web app is cookie-authenticated, so CSRF is mandatory. Trying to express both in one chain produces a configuration where one of them is wrong. securityMatcher plus @Order makes the split explicit.

Authorisation is scope-based for the API and role-based for the web app, and both are backed by method security on the shared service layer — because the same OrderService.cancel() is reachable from three transports and the ownership rule must hold for all of them.

Revocation, which is the requirement that shapes the token design: access tokens are 10 minutes, refresh tokens are stored server-side and revocable. Disabling an account invalidates the refresh token immediately and the access token within 10 minutes. That bounded window is a decision to write down, not an accident.

The trade-off I would put to the team: mobile could also use cookies and share the web chain, which would simplify the design considerably. I would resist it because mobile clients handle cookie expiry and refresh poorly and cannot use CSRF tokens naturally — but if the mobile app is a thin web view, sharing the chain is the simpler and correct answer. The decision depends on what the mobile client actually is, which is a question I would ask before writing any of this.

6 (hard): A security review of an existing service is due in two weeks. Design what you would check and in what order.
Solution

Order by the likelihood of finding something serious, not by the structure of a checklist. Two weeks is enough for a genuine review only if it is prioritised.

What I would deliberately not spend the two weeks on: a line-by-line read of the whole codebase. The findings that matter cluster in configuration and in authorisation logic, and a broad read trades depth in those for coverage that finds little.

What I would deliver alongside the findings: the tests above, in the repository. A review report ages immediately; a failing build does not. The single most valuable outcome of a security review is usually not the list of issues but the three or four assertions that stop them recurring — particularly the object-level authorisation test, which is the one class of bug that reliably reappears as new endpoints are added.

One thing I would flag about scope: a two-week review of the application says nothing about infrastructure, the deployment pipeline, or dependencies at runtime. I would state that boundary explicitly in the report, because "we had a security review" tends to be remembered without the qualifier.

🎯 Key Takeaways

  • Spring Security is a filter chain that runs before Spring MVC. A controller cannot bypass a rule, and a 401 never reaches your @ControllerAdvice.
  • logging.level.org.springframework.security=DEBUG names the exact filter that made any decision.
  • 401 = not authenticated; 403 = authenticated but not permitted. Use 404 where existence is sensitive.
  • WebSecurityConfigurerAdapter is removed in Spring Security 6 — every pre-2022 tutorial is wrong. Use a SecurityFilterChain bean.
  • Rules are first-match-wins: most specific first, anyRequest() last, and prefer denyAll() as the default.
  • A misordered permitAll() made every endpoint public for 11 days with no failing test — alert on zero 401s.
  • SecurityContextHolder is a ThreadLocal, so it is empty in every @Async method.
  • A TaskDecorator without a finally clear leaks principals between users on pooled threads.
  • Prefer @AuthenticationPrincipal injection to the static holder — typed, testable, explicit.
  • CSRF matters only when the browser attaches credentials automatically. Required for cookies, unnecessary for bearer tokens.
  • Method security survives URL refactoring and protects non-HTTP callers; URL security does neither.
  • Method security is proxy-based, so self-invocation bypasses it entirely.
  • Never use @PostAuthorize on a mutating method — the write has already happened.
  • Passwords need a deliberately slow adaptive hash. SHA-256 allows ~10⁹ guesses/sec on a GPU; bcrypt allows ~20,000.
  • Use DelegatingPasswordEncoder so the algorithm prefix lets you migrate without a big bang.
  • You cannot revoke a JWT. A blacklist reintroduces the shared state JWTs were chosen to avoid.
  • Sessions for first-party web apps; short-lived JWTs plus revocable refresh tokens for APIs and mobile.
  • Broken object-level authorisation is the most common serious API flaw — write the "user A requests user B's record" test for every resource.
