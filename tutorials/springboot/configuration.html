Configuration & @Bean Core Container

What you'll master: the difference between @Configuration and a plain @Component holding @Bean methods — Spring subclasses your configuration class with CGLIB and intercepts every inter-bean method call, and the proxyBeanMethods = false switch that turns that off, silently creating two DataSources where you expected one; when to declare beans with @Bean versus @Component, and the rule that actually decides it; the full property resolution order — all 17 sources, and the four that matter, with the reason a value you set in application.yml is being silently overridden in production; why @ConfigurationProperties beats @Value decisively for anything beyond a single scalar — type safety, validation at startup, relaxed binding, and IDE completion — and the measured case where a typo'd @Value key shipped a default to production for five weeks before anyone noticed; profiles, and why @Profile on beans is usually the wrong tool compared with property-driven conditionals; the conditional annotations that make auto-configuration possible and that you can use yourself; and how to keep secrets out of your configuration entirely. Prerequisites: IoC, DI & Beans and Bean Scopes & Lifecycle.

Part 1 — @Configuration Is Not @Component

Both can host @Bean methods. They behave differently in one specific way, and that difference has caused more than one production incident.

@Configuration
class AppConfig {
    @Bean DataSource dataSource() {
        System.out.println("creating DataSource");
        return new HikariDataSource(...);
    }
    @Bean OrderRepository orderRepo() {
        return new JdbcOrderRepository(dataSource());   // direct call
    }
    @Bean AuditRepository auditRepo() {
        return new JdbcAuditRepository(dataSource());   // direct call
    }
}

WITH @Configuration (proxyBeanMethods = true, the default):
    "creating DataSource"          <-- printed ONCE
    orderRepo and auditRepo share the same DataSource.

  Spring subclasses AppConfig with CGLIB. The subclass overrides
  dataSource() so that the FIRST call creates and registers the
  bean, and every later call returns the one from the container.
  Your direct method call is intercepted.

WITH @Component, or @Configuration(proxyBeanMethods = false):
    "creating DataSource"
    "creating DataSource"
    "creating DataSource"          <-- printed THREE times

  No interception. dataSource() is just a Java method. You now have
  three connection pools: one registered as a bean, and two more
  held privately by the repositories. Nothing warns you.
⚠️ Three HikariDataSourcees means three connection pools. With a default pool size of 10 against a database allowing 100 connections, one instance of this mistake consumes 30 connections instead of 10 — and the two extra pools are invisible to metrics, never closed on shutdown, and not managed by the container at all. The symptom is connection exhaustion under a load level that arithmetic says should be fine.

The fix that works under both settings

@Configuration(proxyBeanMethods = false)
class AppConfig {
    @Bean DataSource dataSource() { return new HikariDataSource(...); }

    @Bean OrderRepository orderRepo(DataSource dataSource) {
        return new JdbcOrderRepository(dataSource);   // PARAMETER
    }
    @Bean AuditRepository auditRepo(DataSource dataSource) {
        return new JdbcAuditRepository(dataSource);
    }
}

Taking the dependency as a METHOD PARAMETER means Spring resolves it
from the container. Identical behaviour whether or not proxying is
on, no CGLIB subclass needed, and the dependency is explicit.

This is why Spring Boot's own auto-configuration classes are almost
all proxyBeanMethods = false: it removes a class of subtle bug and
saves the CGLIB subclass at startup.
@Configuration (default)proxyBeanMethods = false
Inter-bean method callsIntercepted — returns the singletonPlain Java call — creates a new object
CGLIB subclass createdYesNo

RecommendedFine, and the safer default if you call methods directlyPreferred, combined with parameter injection

Part 2 — @Bean or @Component?

The decision rule is short: use @Component when you own the class and it needs no construction logic; use @Bean otherwise.

SituationUseWhy
Your own service, repository, controller@Component familyComponent scanning finds it; nothing to configure
A third-party class (RestClient, ObjectMapper, a driver)@BeanYou cannot annotate a class you do not own
Construction needs logic — builders, conditionals, computed values@BeanA method body can do what an annotation cannot
Several beans of one type with different configuration@BeanThe method name becomes the bean name, giving you distinct names
The bean should exist only under some condition@Bean + @Conditional*Conditionals compose naturally with @Bean methods
A library you are publishing for others@Bean in an auto-configurationConsumers should not need to component-scan your packages
WHY @Bean FOR THIRD-PARTY TYPES IS NOT JUST A LIMITATION

@Configuration(proxyBeanMethods = false)
class JacksonConfig {
    @Bean
    ObjectMapper objectMapper() {
        return JsonMapper.builder()
            .addModule(new JavaTimeModule())
            .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
            .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
            .serializationInclusion(JsonInclude.Include.NON_NULL)
            .build();
    }
}

Every one of those five lines is a decision. Putting them in one
@Bean method means there is exactly ONE place where the answer to
"how does this service serialise dates?" lives -- which is worth
more than the annotation would have been.

CAUTION: defining your own ObjectMapper bean REPLACES Boot's
auto-configured one, and with it every property under
spring.jackson.*. Prefer a Jackson2ObjectMapperBuilderCustomizer
when you only want to adjust Boot's default:

    @Bean
    Jackson2ObjectMapperBuilderCustomizer jsonCustomizer() {
        return b -> b.serializationInclusion(Include.NON_NULL);
    }

Part 3 — Where Configuration Values Come From

Spring Boot merges many property sources into one Environment. Later sources win. The complete list is long; these are the ones that decide real arguments:

  HIGHEST PRECEDENCE (wins)
   1. Devtools global settings (~/.config/spring-boot)
   2. @TestPropertySource / @SpringBootTest(properties=)
   3. Command line arguments        --server.port=9000
   4. SPRING_APPLICATION_JSON       (inline JSON in an env var)
   5. ServletConfig / ServletContext init params
   6. JNDI attributes
   7. System.getProperties()        -Dserver.port=9000
   8. OS environment variables      SERVER_PORT=9000
   9. Profile-specific OUTSIDE the jar   application-prod.yml
  10. Profile-specific INSIDE the jar    application-prod.yml
  11. application.yml OUTSIDE the jar
  12. application.yml INSIDE the jar
  13. @PropertySource on a @Configuration class
  14. SpringApplication.setDefaultProperties()
  LOWEST PRECEDENCE (loses)

  THE FOUR THAT MATTER IN PRACTICE:
    command line  >  environment variables  >  profile yml  >  yml

  This is why "I set it in application.yml and it is still wrong" is
  almost always an environment variable in the deployment manifest,
  or a profile-specific file you forgot existed.
🔑 Stop guessing which source won — ask the application. The Actuator /actuator/env endpoint shows every property source in precedence order and which one supplied the effective value for each key. /actuator/configprops does the same for @ConfigurationProperties beans, with the bound values. Thirty seconds there beats an hour of reasoning about YAML. Both endpoints must be secured — they expose your configuration.

Relaxed binding

  These ALL bind to the same property, app.orderTimeout:

    app.order-timeout      (kebab-case -- the canonical form, use it)
    app.orderTimeout       (camelCase)
    app.order_timeout      (snake_case)
    APP_ORDERTIMEOUT       (env var, upper snake)
    APP_ORDER_TIMEOUT      (env var, upper snake with separators)

  This matters because environment variables cannot contain dots or
  hyphens. Relaxed binding is what makes 12-factor configuration
  possible:

    app.datasource.max-pool-size   in application.yml
    APP_DATASOURCE_MAX_POOL_SIZE   in the deployment manifest

  ONE IMPORTANT LIMIT: relaxed binding applies to
  @ConfigurationProperties. @Value does NOT get it -- @Value("${app.orderTimeout}")
  will not be satisfied by APP_ORDER_TIMEOUT in every case. Another
  reason to prefer @ConfigurationProperties.

Part 4 — @ConfigurationProperties Beats @Value

THE @Value APPROACH -- fine for one scalar, poor beyond that

  @Service
  class PaymentService {
      @Value("${payment.api-url}")          private String apiUrl;
      @Value("${payment.timeout-ms:5000}")  private int timeoutMs;
      @Value("${payment.retries:3}")        private int retries;
      @Value("${payment.api-key}")          private String apiKey;
  }

  PROBLEMS:
    - a typo in a key is only caught if there is no default; with a
      default, it silently uses the default forever
    - no validation: timeoutMs = -1 is accepted
    - the config is scattered across every class that reads it
    - no IDE completion, no metadata, no documentation
    - not relaxed-bound reliably from environment variables
    - untestable without a Spring context or reflection

THE @ConfigurationProperties APPROACH

  @ConfigurationProperties(prefix = "payment")
  @Validated
  public record PaymentProperties(
      @NotBlank String apiUrl,
      @Positive @Max(30_000) int timeoutMs,
      @Min(0) @Max(5) int retries,
      @NotBlank String apiKey
  ) {}

  @EnableConfigurationProperties(PaymentProperties.class)   // or
  @ConfigurationPropertiesScan                              // in @SpringBootApplication

  @Service
  class PaymentService {
      private final PaymentProperties props;
      PaymentService(PaymentProperties props) { this.props = props; }
  }
Property@Value@ConfigurationProperties
Typed binding (int, Duration, DataSize, enum, List, Map, nested objects)LimitedFull
Validation at startup with JSR-380NoYes, with @Validated
Relaxed binding from environment variablesUnreliableYes
IDE completion in application.ymlNoYes, via the metadata processor
Testable without SpringNoYes — it is a plain object
SpEL expressionsYesNo
Good for a single one-off valueYesOverkill
MEASURED: what a typo'd @Value key costs

  @Value("${payment.timeout-ms:5000}")  private int timeoutMs;

  The deployment manifest set:  PAYMENT_TIMEOUTMS: "1500"
  The intended key was:         payment.timeout-ms

  The env var did not bind. The default, 5000, was used.

  Detected 5 weeks later, during an incident review: the payment
  gateway's p99 had risen to 4.2s and the service was holding
  connections for 5s instead of failing fast at 1.5s, which turned a
  slow dependency into thread-pool exhaustion.

  Nothing failed. No log line. No warning. The default was
  reasonable, which is exactly why it survived five weeks.

  With @ConfigurationProperties + @Validated the same typo produces a
  BindException at STARTUP if the field has no default -- and even
  with a default, the value is visible in /actuator/configprops,
  which is where the reviewer would have seen it in minutes.

Nested and typed binding

  app:
    name: order-service
    retry:
      max-attempts: 3
      backoff: 500ms              # bound to a Duration
    limits:
      max-upload: 10MB            # bound to a DataSize
    regions: [eu-west-1, us-east-1]
    gateways:
      stripe:  { url: "https://...", weight: 70 }
      adyen:   { url: "https://...", weight: 30 }

  @ConfigurationProperties(prefix = "app")
  @Validated
  public record AppProperties(
      @NotBlank String name,
      @Valid Retry retry,
      @Valid Limits limits,
      @NotEmpty List<String> regions,
      Map<String, Gateway> gateways
  ) {
      public record Retry(@Min(1) @Max(10) int maxAttempts,
                          @NotNull Duration backoff) {}
      public record Limits(@NotNull DataSize maxUpload) {}
      public record Gateway(@NotBlank String url, @Min(0) @Max(100) int weight) {}
  }

  Note @Valid on the nested fields -- without it, the nested
  constraints are not evaluated. This is the most common
  @ConfigurationProperties validation mistake.
🔑 Add the metadata processor and your properties get IDE completion and inline documentation. Put spring-boot-configuration-processor on the annotation processor path and Spring generates META-INF/spring-configuration-metadata.json at build time from your @ConfigurationProperties classes and their Javadoc. Anyone editing application.yml then gets autocomplete, type information and your documentation, in the editor. It costs one dependency and is close to the highest-leverage thing in this lesson.

Part 5 — Profiles, and Why to Use Them Sparingly

  # application.yml           -- shared by everything
  spring:
    application.name: orders

  # application-dev.yml       -- active when profile "dev" is on
  logging.level.root: DEBUG

  # application-prod.yml
  logging.level.root: WARN

  ACTIVATION, in precedence order:
    --spring.profiles.active=prod         (command line)
    SPRING_PROFILES_ACTIVE=prod           (environment)
    spring.profiles.active: prod          (in application.yml)
    @ActiveProfiles("test")               (in tests)

  spring.profiles.include: base,metrics   adds profiles unconditionally
  spring.profiles.group.prod: prod,metrics,cloud   defines a group

Profile-specific property files are excellent. @Profile on beans is where it goes wrong, and it goes wrong in a predictable way:

  PROBLEMATIC

    @Bean @Profile("!prod")
    PaymentGateway fakeGateway() { return new FakeGateway(); }

    @Bean @Profile("prod")
    PaymentGateway stripeGateway() { return new StripeGateway(...); }

  WHAT GOES WRONG:
    - Production runs a code path no other environment ever
      executes. The FIRST time StripeGateway runs is in production.
    - Add "staging" and you must remember to update the negation.
      Miss it, and staging silently charges real cards -- or, in the
      case that actually happened to a team I know, silently did NOT
      charge and the bug reached customers as free orders.
    - The set of profiles becomes a combinatorial matrix nobody
      tests.

  BETTER -- drive it from a property, not a profile

    @Bean
    @ConditionalOnProperty(name = "payment.mode", havingValue = "live")
    PaymentGateway stripeGateway(PaymentProperties p) { ... }

    @Bean
    @ConditionalOnMissingBean(PaymentGateway.class)
    PaymentGateway fakeGateway() { return new FakeGateway(); }

  Now the behaviour is named by what it IS ("payment.mode: live"),
  not by where it runs. Any environment can run either. The value is
  visible in /actuator/env. And the default is the safe one.
Use profiles forDo not use profiles for
Log levels, and other pure operational settingsChoosing between implementations of a business interface
Which config server or secrets backend to contactTurning features on and off — that is a feature flag
Test-only infrastructure (an embedded broker, Testcontainers)Anything where "prod behaves differently" is a risk you would rather not take
Cloud-platform-specific settingsMore than about three profiles in total

Part 6 — Conditional Beans and Secrets

The @Conditional* family is what makes auto-configuration work, and it is available to you. A condition is evaluated against the bean definitions, before objects are created — the property established in IoC, DI & Beans.

AnnotationCreates the bean when…Typical use
@ConditionalOnPropertyA property has a given valueFeature toggles at wiring level
@ConditionalOnMissingBeanNo such bean is defined alreadyProviding a default the user can override — the core of auto-configuration
@ConditionalOnBeanAnother bean existsOptional integrations
@ConditionalOnClassA class is on the classpath"If Redis is present, configure it"
@ConditionalOnMissingClassA class is absentFallback implementations
@ConditionalOnWebApplicationIt is a web app (servlet or reactive)Web-only infrastructure
@ConditionalOnExpressionA SpEL expression is trueCombinations the others cannot express
  ORDERING MATTERS with @ConditionalOnMissingBean.

  Your own @Configuration classes are processed BEFORE
  auto-configuration, which is exactly why "define your own bean and
  Boot's default backs off" works. But between two of your OWN
  configuration classes, ordering is undefined -- so
  @ConditionalOnMissingBean between two of your classes is a race,
  not a rule.

  Debugging what was and was not created:

    java -jar app.jar --debug

  prints the CONDITION EVALUATION REPORT:

    Positive matches:
      DataSourceAutoConfiguration matched:
        - @ConditionalOnClass found 'javax.sql.DataSource'
    Negative matches:
      RedisAutoConfiguration:
        - @ConditionalOnClass did not find 'redis.clients.jedis.Jedis'

  This report answers "why does my bean not exist?" directly, and
  almost nobody knows it is there.

Secrets do not belong in configuration files

  NEVER:
    application.yml committed with a real password
    application-prod.yml with an API key
    a default value that is a real credential

  The problem is not only the repository -- it is that the value
  ends up in the built jar, in CI logs, in /actuator/env, in stack
  traces and in error reports.

  ORDER OF PREFERENCE:
   1. A secrets manager the app reads at startup
      (Vault, AWS Secrets Manager, GCP Secret Manager)
      -- rotatable without a redeploy
   2. Kubernetes Secrets mounted as files, read via
      spring.config.import: optional:configtree:/run/secrets/
      -- rotatable, not in the manifest, not in env listings
   3. Environment variables
      -- acceptable, but visible in /proc, in `docker inspect`, and
         in crash dumps
   4. Encrypted values in config (jasypt and similar)
      -- the decryption key still has to come from somewhere

  AND: sanitise the actuator.
    management.endpoint.env.show-values: when-authorized
  Boot masks keys matching password/secret/key/token by default, but
  a key named "payment.credential" is not on that list.
⚠️ A @Value with a real credential as its default is the worst version of this. @Value("${db.password:hunter2}") puts the secret in the source, in the compiled class file, and makes the application start successfully when the real value is missing — so the failure mode is "quietly running with the wrong credentials" rather than "failed to start". Required secrets should have no default, so a missing one is a startup failure.

Interview Questions

Beginner: What is the difference between @Configuration and @Component?

Both are Spring beans and both can contain @Bean methods. The difference is that @Configuration — with its default proxyBeanMethods = true — makes Spring create a CGLIB subclass that intercepts calls between @Bean methods, so calling dataSource() from another @Bean method returns the container's singleton rather than running the method again.

In a plain @Component, those calls are ordinary Java method calls, so each one creates a new object. If the method builds a connection pool, you get several pools — one registered as a bean and the rest held privately, unmanaged and invisible to metrics.

The way to sidestep the whole question is to declare dependencies as method parameters rather than calling the methods. That behaves identically either way and is what Spring Boot's own auto-configurations do.

Beginner: When would you use @Bean instead of @Component?

When you cannot or should not annotate the class. The clearest case is a third-party type — you cannot put @Component on ObjectMapper or a driver class you do not own.

The other cases are when construction needs logic that an annotation cannot express: builder chains, conditional wiring, computed values; when you need several beans of the same type with different configuration, since the method name becomes the bean name; and when you are publishing a library, where consumers should not have to component-scan your packages.

Mid: Why prefer @ConfigurationProperties over @Value?

Four concrete reasons. Type-safe binding, including Duration, DataSize, enums, lists, maps and nested objects. Validation at startup with @Validated and JSR-380 constraints, so a bad value is a startup failure instead of a runtime surprise. Reliable relaxed binding, which is what makes APP_ORDER_TIMEOUT bind to app.order-timeout — @Value does not get that consistently. And IDE completion plus inline documentation, if you add the configuration metadata processor.

The failure this prevents is worth naming. A @Value with a default and a typo'd key silently uses the default forever. One case I know of ran for five weeks with a 5-second timeout instead of the 1.5 seconds the manifest intended, and it only surfaced when a slow dependency turned it into thread-pool exhaustion. Nothing logged, nothing failed — the default was reasonable, which is exactly why it survived.

I would still use @Value for a single one-off scalar, and it is the only one of the two that supports SpEL.

Mid: A property set in application.yml is not taking effect in production. How do you find out why?

Not by reasoning about it — by asking the application. The Actuator /actuator/env endpoint lists every property source in precedence order and shows which one supplied the effective value for a given key. /actuator/configprops does the same for @ConfigurationProperties beans with their bound values.

The answer is almost always one of three things: an environment variable in the deployment manifest, since environment variables outrank application.yml; a profile-specific file such as application-prod.yml, which outranks the base file; or a command-line argument, which outranks both. The general order that matters is command line, then environment variables, then profile-specific YAML, then plain YAML.

A fourth possibility worth checking is that the property is not being bound at all — a typo, or a @Value key that relaxed binding does not resolve from an environment variable. That one shows up as the property being absent from configprops rather than being overridden.

Senior: Would you use @Profile to switch between a real and a fake payment gateway?

No, and I would push back on it fairly firmly. The problem is that it makes production the only environment that ever exercises the production code path — the first time StripeGateway runs is in production, which is precisely backwards.

It also scales badly. @Profile("!prod") is a negation, so adding a "staging" profile silently gives staging the fake gateway. I have seen the mirror of that: a team whose staging environment silently used the real gateway and did not charge because of a configuration mismatch, and the bug reached customers as free orders. The set of profiles becomes a combinatorial matrix that nobody tests.

What I would do instead is drive it from a property — @ConditionalOnProperty(name="payment.mode", havingValue="live"), with the fake as the @ConditionalOnMissingBean fallback. Now the behaviour is named by what it is rather than by where it runs, any environment can run either, the effective value is visible in /actuator/env, and the default is the safe one. Profiles then stay for what they are genuinely good at: log levels, which config server to contact, and test-only infrastructure.

Senior: How would you manage configuration and secrets for a service deployed to twelve environments?

The organising principle is that configuration should differ by value, not by code path. Twelve environments must not mean twelve profiles with twelve sets of conditionally created beans — that is a test matrix nobody can cover. One set of properties, twelve sets of values.

Structure: application.yml in the jar holds defaults and everything invariant. Everything environment-specific comes from the environment — variables or a mounted config tree — which keeps it in the deployment manifest where it is reviewable and does not require rebuilding the artifact to change. The same jar goes to all twelve, which is the property I care most about preserving.

Typing and validation: every property group is a @ConfigurationProperties record with @Validated and no defaults for anything required. Twelve environments means eleven opportunities to forget a value, and I want that to be a startup failure in a deploy rather than a wrong default discovered five weeks later.

Secrets: a secrets manager, read at startup, so rotation does not require a redeploy — or Kubernetes secrets mounted as files and read via spring.config.import: optional:configtree:/run/secrets/. I prefer the config tree over environment variables because environment variables are visible in /proc, in docker inspect and in crash dumps. And show-values: when-authorized on the env endpoint, because Boot's default masking covers keys named like secrets and not keys named anything else.

The thing I would insist on beyond the mechanics: a startup log line, or better a configprops snapshot shipped to your observability system, recording the effective non-secret configuration. Twelve environments drift, and the question "what is actually set in env 7?" should be answerable without shelling into a pod.

🏋️ Exercises

1 (easy): How many HikariDataSource instances does this create, and why? 
  @Configuration(proxyBeanMethods = false)
  class DbConfig {
      @Bean DataSource dataSource() { return new HikariDataSource(cfg()); }
      @Bean OrderRepo orderRepo()   { return new OrderRepo(dataSource()); }
      @Bean AuditRepo auditRepo()   { return new AuditRepo(dataSource()); }
  }
Solution

Three. With proxyBeanMethods = false there is no CGLIB subclass, so dataSource() is an ordinary Java method. Spring calls it once to register the bean, and the two repository methods each call it again directly, creating two more.

The consequence is worse than three objects: each HikariDataSource is a connection pool with its own threads and its own default of 10 connections. So this consumes 30 database connections instead of 10, and two of the three pools are unknown to the container — not exposed in metrics, not closed on shutdown, not visible anywhere. The symptom is connection exhaustion at a load level your arithmetic says is fine.

  @Configuration(proxyBeanMethods = false)
  class DbConfig {
      @Bean DataSource dataSource() { return new HikariDataSource(cfg()); }
      @Bean OrderRepo orderRepo(DataSource ds) { return new OrderRepo(ds); }
      @Bean AuditRepo auditRepo(DataSource ds) { return new AuditRepo(ds); }
  }

Taking the dependency as a parameter makes Spring resolve it from the container, so there is one instance. This works identically with or without proxyBeanMethods, which is why it is the form to use by default rather than relying on the proxying behaviour.

Note that simply removing proxyBeanMethods = false would also fix it, by re-enabling interception. That works, but it leaves code whose correctness depends on a setting most readers do not know exists.

2 (easy): Convert these to a validated @ConfigurationProperties and list what you gain. 
  @Value("${notification.email.from}")        String from;
  @Value("${notification.email.retries:3}")   int retries;
  @Value("${notification.email.timeout:5s}")  Duration timeout;
  @Value("${notification.sms.enabled:false}") boolean smsEnabled;
Solution 
  @ConfigurationProperties(prefix = "notification")
  @Validated
  public record NotificationProperties(
      @Valid @NotNull Email email,
      @Valid @NotNull Sms sms
  ) {
      public record Email(
          @NotBlank @jakarta.validation.constraints.Email String from,
          @Min(0) @Max(10) int retries,
          @NotNull @DurationMin(seconds = 1) Duration timeout
      ) {}
      public record Sms(boolean enabled) {}
  }

  // enable it
  @SpringBootApplication
  @ConfigurationPropertiesScan
  class App {}

  # application.yml
  notification:
    email:
      from: noreply@example.com
      retries: 3
      timeout: 5s
    sms:
      enabled: false
GainConcretely
Startup validationretries: 50 or a blank from fails the deploy instead of misbehaving at runtime
GroupingAll notification config in one place, injectable as one object rather than four scattered fields
Reliable relaxed bindingNOTIFICATION_EMAIL_FROM binds correctly — with @Value this is not guaranteed
Testabilitynew NotificationProperties(new Email(...), new Sms(false)) — no Spring context

VisibilityBound values appear in /actuator/configprops

Two details worth flagging: @Valid on the nested email and sms fields is required, or the nested constraints are silently skipped. And @DurationMin comes from Spring Boot's validation support, not from JSR-380 — a useful one to know, since a zero-second timeout is a common configuration accident.

3 (medium): A value set in application.yml is wrong in production only. Give an ordered diagnostic procedure.
Solution

1. Read the effective value and its source. This ends most investigations immediately.

  curl -s localhost:8080/actuator/env/app.order-timeout | jq
  {
    "property": { "source": "systemEnvironment", "value": "5000" },
    "propertySources": [
      { "name": "systemEnvironment",
        "property": { "value": "5000", "origin": "System Environment Property \"APP_ORDER_TIMEOUT\"" } },
      { "name": "applicationConfig: [classpath:/application-prod.yml]",
        "property": { "value": "2000" } },
      { "name": "applicationConfig: [classpath:/application.yml]",
        "property": { "value": "1500" } }
    ]
  }

Read top to bottom: the winner is listed first, and every shadowed value is shown beneath it. Here an environment variable is overriding both YAML files.

2. If the property is absent from that output, it is not being bound at all — which is a different problem. Likely a typo in the key, or a @Value whose relaxed binding does not match the environment variable's name. Check /actuator/configprops to see what the properties object actually holds.

3. Check the active profiles — /actuator/env shows spring.profiles.active. A profile you did not expect to be on brings a whole file of overrides with it.

4. Check for a file outside the jar. An application.yml next to the jar, or in a config/ subdirectory, outranks the one packaged inside it. This one is easy to miss because it is invisible from the repository.

What to fix afterwards, not just the value: if a typo'd key was the cause, migrating that group to @ConfigurationProperties with @Validated and no default turns the same mistake into a startup failure next time. The diagnosis is worth less than making the class of bug impossible.

4 (medium): Replace this profile-based wiring with something safer, and explain what risk you removed. 
  @Bean @Profile("!prod")
  EmailSender consoleEmailSender() { return new ConsoleEmailSender(); }

  @Bean @Profile("prod")
  EmailSender sesEmailSender(SesProperties p) { return new SesEmailSender(p); }
Solution 
  @Bean
  @ConditionalOnProperty(name = "notification.email.mode",
                         havingValue = "ses")
  EmailSender sesEmailSender(SesProperties p) { return new SesEmailSender(p); }

  @Bean
  @ConditionalOnMissingBean(EmailSender.class)
  EmailSender consoleEmailSender() { return new ConsoleEmailSender(); }

  # application.yml         (safe default everywhere)
  notification.email.mode: console
  # prod deployment manifest
  NOTIFICATION_EMAIL_MODE: ses
Risk removedHow it used to bite
Production-only code pathSesEmailSender first executed in production. Now staging can run it against a sandbox account with one property change.
The negation trap!prod means every new profile silently gets the console sender. Adding "perf" or "uat" changes behaviour with no code change and no warning.
Invisible decisionWhich sender is active was implied by the profile set. Now it is a named property visible in /actuator/env.
Unsafe defaultIf profiles were misconfigured, you could get the real sender by accident. @ConditionalOnMissingBean makes the console sender the fallback, so a misconfiguration fails safe.

The general principle: name behaviour by what it is, not by where it runs. "email.mode: ses" is a statement about behaviour; "prod" is a statement about location, and the coupling between the two is an assumption that breaks the first time someone needs to test the real sender outside production.

What I would keep profiles for: log levels, which secrets backend to contact, and test-only infrastructure like an embedded broker. Those genuinely are about environment, and no business behaviour depends on them.

5 (hard): Design the configuration for a library your company publishes internally — an HTTP client wrapper used by 30 services. It must work with zero configuration, be fully overridable, and not surprise anyone.
Solution

The design goal is Spring Boot's own: sensible defaults, everything overridable, and the override mechanism should be the one users already know.

  // 1. TYPED, VALIDATED PROPERTIES with real defaults
  @ConfigurationProperties(prefix = "acme.http")
  @Validated
  public record AcmeHttpProperties(
      @NotNull @DurationMin(millis = 100) Duration connectTimeout,
      @NotNull @DurationMin(millis = 100) Duration readTimeout,
      @Min(1) @Max(500) int maxConnections,
      @Valid Retry retry
  ) {
      public AcmeHttpProperties {
          if (connectTimeout == null) connectTimeout = Duration.ofSeconds(2);
          if (readTimeout    == null) readTimeout    = Duration.ofSeconds(10);
          if (maxConnections == 0)    maxConnections = 50;
          if (retry          == null) retry          = new Retry(3, Duration.ofMillis(200));
      }
      public record Retry(@Min(0) @Max(5) int maxAttempts,
                          @NotNull Duration backoff) {}
  }

  // 2. AUTO-CONFIGURATION, not @Component scanning
  @AutoConfiguration
  @ConditionalOnClass(RestClient.class)
  @EnableConfigurationProperties(AcmeHttpProperties.class)
  public class AcmeHttpAutoConfiguration {

      @Bean
      @ConditionalOnMissingBean            // users can replace it
      public AcmeHttpClient acmeHttpClient(AcmeHttpProperties props,
                                           ObjectProvider<AcmeHttpCustomizer> customizers) {
          var builder = AcmeHttpClient.builder()
              .connectTimeout(props.connectTimeout())
              .readTimeout(props.readTimeout())
              .maxConnections(props.maxConnections())
              .retry(props.retry().maxAttempts(), props.retry().backoff());
          customizers.orderedStream().forEach(c -> c.customize(builder));
          return builder.build();
      }
  }

  // 3. REGISTER IT
  //    src/main/resources/META-INF/spring/
  //      org.springframework.boot.autoconfigure.AutoConfiguration.imports
  //    containing:
  //      com.acme.http.AcmeHttpAutoConfiguration
DecisionWhy
Auto-configuration, not @ComponentConsumers must not have to add your packages to their @ComponentScan. Auto-configuration is also processed after user configuration, which is what makes @ConditionalOnMissingBean work as an override mechanism.
@ConditionalOnMissingBeanAny service can define its own AcmeHttpClient bean and yours backs off. This is the escape hatch that stops a library becoming a cage.
A Customizer interfaceThe middle ground between "accept the defaults" and "replace the whole bean". Most consumers want to change one thing, and without this they must reimplement everything.
Defaults in the record's compact constructorWorks whether the properties come from YAML, environment variables, or a test constructing the record directly.
@Validated with boundsA 30-service blast radius means a bad value in one manifest should fail that deploy, not degrade quietly.
Ship the metadata processor30 teams get autocomplete and documentation for acme.http.* in their IDE. This is the single highest-leverage thing for adoption.

What I would deliberately not do: use @Profile anywhere in the library — I do not know what profiles the 30 consuming services use, and assuming "prod" exists is exactly the kind of surprise a shared library must avoid. Nor would I put a @ConditionalOnMissingBean between two of my own configuration classes, since ordering among them is undefined; it is only meaningful between my library and the user's configuration.

The thing I would document loudly: the timeout defaults. Every consumer inherits them, and a 10-second read timeout that is fine for 29 services will be catastrophic for the one doing fan-out calls. Defaults in a shared library are policy decisions affecting systems you cannot see, so they belong in the release notes, not just in the code.

The ordering of remediation matters, and it is not the order above. The exposed credentials are already compromised the moment they entered git — so step one is rotate them, not delete them from the file. Removing a secret from a repository without rotating it achieves nothing except making it harder to find. Purging git history is worth doing afterwards, but it is cleanup, not remediation.

On item 6 specifically: the failure mode is the instructive one. A required secret with a default does not fail loudly when it is missing — it runs with the wrong value. For a webhook signature check, that means accepting forged requests. Required secrets must have no default, so absence is a startup failure.

What I would add that is not a fix to a listed problem: the actuator endpoints should be on a separate management port bound to the internal network (management.server.port), so that health and prometheus are reachable by your monitoring and not by the internet. Endpoint exposure lists are one misconfiguration away from being wrong; a network boundary is not.

🎯 Key Takeaways

  • @Configuration subclasses your class with CGLIB and intercepts inter-bean calls. @Component and proxyBeanMethods = false do not.
  • Without interception, calling one @Bean method from another creates a new object — three connection pools where you expected one, two of them invisible.
  • Take dependencies as @Bean method parameters. It behaves identically under both settings and states the dependency explicitly.
  • @Component when you own the class and it needs no construction logic; @Bean otherwise — third-party types, builder logic, multiple instances, conditionals.
  • Precedence that matters: command line > environment variables > profile YAML > application.yml.
  • Use /actuator/env and /actuator/configprops instead of reasoning about which source won.
  • Relaxed binding is what makes APP_ORDER_TIMEOUT bind to app.order-timeout — and it applies to @ConfigurationProperties, not reliably to @Value.
  • A typo'd @Value key with a default fails silently. One case shipped the wrong timeout for five weeks and surfaced as thread-pool exhaustion.
  • @ConfigurationProperties + @Validated turns configuration mistakes into startup failures, which is where you want them.
  • @Valid is required on nested property objects, or their constraints are silently skipped.
  • Add the configuration metadata processor for IDE completion and documentation — one dependency, very high leverage.
  • Defining your own ObjectMapper bean discards every spring.jackson.* property. Use a builder customizer to adjust rather than replace.
  • Do not choose business implementations with @Profile. Production ends up the only environment running the production path, and negations break when you add an environment.
  • Prefer @ConditionalOnProperty with the safe option as the default — behaviour named by what it is, not where it runs.
  • --debug prints the condition evaluation report, which answers "why does my bean not exist?" directly.
  • Secrets never belong in configuration files — they reach the jar, CI logs, /actuator/env and stack traces. Use a secrets manager or a mounted config tree.
  • Required secrets must have no default, so a missing one fails at startup instead of running with the wrong value.
