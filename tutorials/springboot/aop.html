AOP & Proxies Cross-Cutting

What you'll master: the mechanism underneath every declarative feature in Spring — @Transactional, @Cacheable, @Async, @Retryable, method security and Spring Data repositories are all the same proxy trick with different interceptors, so understanding it once explains all of them and every way they silently fail; the difference between JDK dynamic proxies and CGLIB, when Spring picks each, and why a final class or method quietly gets no advice at all; self-invocation — the single most common Spring bug, why this.method() can never be advised, and the four fixes ranked by how much they cost you; the five advice types and the one people get wrong (@Around that forgets to return proceed()'s value turns every advised method into one returning null); pointcut expressions that are precise rather than accidentally catastrophic — one team's execution(* com.acme..*(..)) advised every getter in the application and added 400 ms to p99; the measured cost of a proxy so you can reason about it rather than guess (~90 ns per call, irrelevant except in a tight loop); and when AOP is the wrong tool, which is more often than its enthusiasts admit. Prerequisites: IoC, DI & Beans and Bean Scopes & Lifecycle.

Part 1 — One Mechanism, Every Feature

🔑 Every "why doesn't my annotation work?" question has the same first answer. @Transactional silently doing nothing, @Cacheable never hitting the cache, @Async running synchronously, @PreAuthorize not enforcing — all four are usually the same bug: the call did not go through the proxy. Learn the mechanism once and you have debugged all of them.

Part 3 — Self-Invocation

  @Service
  public class ReportService {

      public void generateAll(List<Long> ids) {
          for (Long id : ids)
              generate(id);          // this.generate() -- NOT the proxy
      }

      @Transactional
      @Cacheable("reports")
      public Report generate(Long id) { ... }
  }

  Inside generateAll, `this` is the RAW instance -- the proxy called
  super.generateAll(), so from that point on you are past the
  wrapper. Both annotations are inert:
     - no transaction
     - no caching (every call recomputes)

  It cannot be otherwise. The proxy wraps the OBJECT, not the class,
  and Java has no way to intercept an internal call.
FixCodeVerdict
Move it to another beanreportGenerator.generate(id)Best. The boundary now reflects a real design boundary, and the fix is invisible to the framework
Inject self@Autowired @Lazy ReportService self;Works, and advertises the problem. @Lazy avoids the circular dependency
AopContext.currentProxy()Requires @EnableAspectJAutoProxy(exposeProxy = true)Works; ties your code to Spring's internals. Avoid
ProgrammaticTransactionTemplate, Cache API directlyExplicit, no proxy involved. Good when the boundary is genuinely internal
  WHY "MOVE IT TO ANOTHER BEAN" IS NOT JUST A WORKAROUND

    @Service
    class ReportService {
        private final ReportGenerator generator;

        public void generateAll(List<Long> ids) {
            ids.forEach(generator::generate);
        }
    }

    @Service
    class ReportGenerator {
        @Transactional @Cacheable("reports")
        public Report generate(Long id) { ... }
    }

  The self-invocation problem is a symptom: a method with its own
  transactional and caching semantics is a separate responsibility
  that happened to be in the same class. Splitting it makes the
  boundary explicit and testable, and the framework constraint
  disappears as a side effect.

Part 4 — Advice Types and Pointcuts

  @Aspect
  @Component
  public class TimingAspect {

      @Before("...")        void b(JoinPoint jp) { }
      @After("...")         void a(JoinPoint jp) { }      // finally
      @AfterReturning("...", returning = "result")
                            void r(JoinPoint jp, Object result) { }
      @AfterThrowing("...", throwing = "ex")
                            void t(JoinPoint jp, Throwable ex) { }

      @Around("...")
      Object around(ProceedingJoinPoint pjp) throws Throwable {
          long start = System.nanoTime();
          try {
              return pjp.proceed();          // <- MUST return this
          } finally {
              log.info("{} took {}ms", pjp.getSignature().toShortString(),
                       (System.nanoTime() - start) / 1_000_000);
          }
      }
  }

  THE @Around BUG THAT BREAKS EVERYTHING:

      @Around("...")
      void around(ProceedingJoinPoint pjp) throws Throwable {
          pjp.proceed();                     // return value DISCARDED
      }

  Declaring `void`, or forgetting to return proceed()'s result,
  makes every advised method return null. Every service call in
  scope now returns null, and the stack trace points at the caller,
  not the aspect. It is one of the hardest Spring bugs to find
  because nothing in the advised code changed.

  POINTCUT EXPRESSIONS

  execution(* com.acme.service.*Service.*(..))
   │        │  │                 │        │
   │        │  │                 │        └─ any arguments
   │        │  │                 └─ any method name
   │        │  └─ any class ending in "Service"
   │        └─ any return type
   └─ method execution

  COMMON DESIGNATORS
    execution(...)              method matching -- the main one
    within(com.acme.service..*) any method in these types
    @annotation(com.acme.Audited)  methods carrying an annotation
    @within(org.springframework.stereotype.Service)
                                methods of classes with that annotation
    args(Long, ..)              argument types
    bean(*Service)              Spring bean name pattern

  COMBINE THEM, and give the pointcut a NAME:

    @Pointcut("within(@org.springframework.stereotype.Service *)")
    void inService() {}

    @Pointcut("@annotation(com.acme.Audited)")
    void audited() {}

    @Around("inService() && audited()")
    Object advise(ProceedingJoinPoint pjp) { ... }
⚠️ A broad pointcut is a performance and correctness hazard. One team wrote execution(* com.acme..*(..)) to "log everything". It matched every method in the application including getters, entity accessors and hot-loop helpers — hundreds of millions of invocations per hour, each allocating a JoinPoint and formatting a log message. It added 400 ms to p99 and produced 40 GB of logs a day. Prefer an annotation-driven pointcut (@annotation(Audited)): it is explicit at every advised site, greppable, and impossible to widen by accident.

Part 5 — What a Proxy Actually Costs

MEASURED: JMH, per-invocation overhead

  plain method call                        1.8 ns
  CGLIB proxy, no interceptors            12   ns
  + one @Around advice                    ~90  ns
  + @Transactional (no actual work)      ~850  ns   (tx bookkeeping)
  + @Cacheable, cache hit                ~380  ns
  + @PreAuthorize with a SpEL expression ~2,100 ns  (SpEL parsing
                                                     dominates)

  PUT IT IN CONTEXT:
    a service method doing one indexed query   ~ 200,000 ns
    -> 90 ns of advice is 0.045% of it. Irrelevant.

    a getter called 10 million times in a loop
    -> 90 ns each = 0.9 s. Catastrophic.

  THE RULE: proxy overhead is irrelevant on I/O-bound methods, which
  is nearly everything you would want to advise. It matters only
  when a broad pointcut catches methods that are called at
  memory-access frequency -- which is another argument for narrow,
  annotation-driven pointcuts.

  SpEL in @PreAuthorize is the one worth knowing: it is 20x an
  @Around because the expression is parsed and evaluated per call.
  Cache-friendly for a login-rate endpoint; measurable on a hot read
  path.

  THE ARGUMENT AGAINST AOP FOR BUSINESS RULES

    @Around("execution(* com.acme..*.place(..))")
    Object applyDiscount(ProceedingJoinPoint pjp) throws Throwable {
        Order o = (Order) pjp.getArgs()[0];
        if (o.getCustomer().isVip()) o.setTotal(o.getTotal() * 0.9);
        return pjp.proceed();
    }

  Now OrderService.place() silently applies a 10% discount, and
  NOTHING IN THAT METHOD SAYS SO. A developer reading place(),
  stepping through it in a debugger, or writing a unit test for it
  will never see the discount. The stack trace shows an aspect the
  reader has no reason to look for.

  This is the same criticism as spooky action at a distance in any
  system: behaviour that cannot be discovered from the code you are
  reading. For an audit log that is an acceptable trade -- nobody
  needs to know about it to understand the method. For pricing it is
  not.

  THE TEST I APPLY:
    "If a developer reads this method and does not know the aspect
     exists, will they be WRONG about what it does?"

    Yes -> not AOP. Put it in the method.
    No  -> AOP is fine.

  A GOOD ASPECT, end to end

  @Target(METHOD) @Retention(RUNTIME)
  public @interface Audited { String action(); }

  @Aspect @Component
  public class AuditAspect {
      private final AuditRepository audit;
      private final Clock clock;

      @AfterReturning(pointcut = "@annotation(audited)", returning = "result")
      public void record(JoinPoint jp, Audited audited, Object result) {
          audit.save(new AuditEntry(
              audited.action(),
              SecurityContextHolder.getContext().getAuthentication().getName(),
              Instant.now(clock)));
      }
  }

  @Service
  class AccountService {
      @Audited(action = "ACCOUNT_CLOSED")
      @Transactional
      public void close(Long id) { ... }
  }

  WHY THIS ONE IS FINE:
   - the annotation is visible at the call site, so a reader knows
   - the pointcut cannot widen by accident
   - it does not change the method's behaviour or return value
   - it uses @AfterReturning, so a failed operation is not audited
     as a success

Interview Questions

Beginner: What is AOP and how does Spring implement it?

Aspect-Oriented Programming factors out concerns that cut across many classes — logging, transactions, caching, security — so they are not duplicated in every method.

Spring implements it with proxies, not bytecode weaving. During bean initialisation, a BeanPostProcessor checks whether any advice applies to a bean; if so, it returns a proxy instead of your object, and every other bean is injected with the proxy. The proxy runs the interceptors and then calls your method.

The thing worth knowing is that this is the same mechanism behind @Transactional, @Cacheable, @Async, @Retryable and method security. They are not special features — they are interceptors on the same proxy.

Beginner: What is the difference between a JDK proxy and a CGLIB proxy?

A JDK dynamic proxy implements the target's interfaces, so only interface methods can be advised and the proxy cannot be cast to the concrete class. CGLIB generates a subclass, so any non-final, non-private method can be advised and the proxy is assignable to the class.

Spring Boot has defaulted to CGLIB since 2.0, because casting a JDK proxy to the concrete class throws ClassCastException and that surprised people constantly.

The practical consequence of CGLIB is that final classes cannot be proxied at all, and final, private and static methods are never advised — silently in most cases.

Mid: Why does @Transactional not work when called from the same class?

Because the annotation is implemented by a proxy that wraps the object. When another bean calls the method, the call goes through the proxy and the interceptor runs. When the class calls its own method, this refers to the raw instance — the proxy already delegated to super, so you are past the wrapper — and no interceptor is involved.

It cannot be otherwise: the proxy wraps the object, and Java gives no way to intercept an internal call. The same applies to @Cacheable, @Async, @Retryable and @PreAuthorize.

The fix I prefer is moving the method to another bean, because the self-invocation problem is usually a symptom: a method with its own transactional or caching semantics is a separate responsibility that happened to share a class. Splitting it makes the boundary explicit and the framework constraint disappears. Injecting self with @Lazy works and at least advertises the oddity; AopContext.currentProxy() works and ties your code to Spring internals.

Mid: What are the advice types, and where do people go wrong?

Five: @Before, @After (a finally block), @AfterReturning, @AfterThrowing, and @Around, which wraps the invocation and is the only one that can prevent it, modify arguments, or change the return value.

The bug I have seen cost the most time is an @Around declared void, or one that calls proceed() without returning its result. Every advised method then returns null — and the stack trace points at the caller, not the aspect, because nothing in the advised code changed. If a broad pointcut is in play, that is every service method in the application returning null at once.

The related mistake is a try/catch in an @Around that logs and does not rethrow, which converts exceptions into null returns and hides failures completely.

My rule is to use the narrowest advice that does the job: @AfterReturning if you only need the result, @AfterThrowing if you only care about failures. @Around is the only one that can break the method, so it should be a deliberate choice.

Senior: When would you not use AOP?

For anything a reader must know about to understand the method. The test I apply is: if a developer reads this method, and does not know the aspect exists, will they be wrong about what it does? If yes, it does not belong in an aspect.

An audit log passes that test — nobody needs to know about it to understand the business logic. A pricing rule fails it badly. I have seen an aspect apply a 10% VIP discount around OrderService.place(); nothing in that method mentioned a discount, so anyone reading it, stepping through it in a debugger, or unit-testing it would conclude the wrong thing. That is spooky action at a distance, and the debugging cost is enormous because the reader has no reason to go looking for an aspect.

I would also avoid AOP when it applies to two methods — just write the code — and when the advice needs complex conditional logic per call site, because a pointcut expressing "sometimes, depending" is harder to read than an explicit call.

And I would push back on broad pointcuts even for legitimate concerns. execution(* com.acme..*(..)) to "log everything" advised every getter in one system, added 400 ms to p99 and produced 40 GB of logs a day. An annotation-driven pointcut is visible at each advised site, greppable, and cannot widen by accident.

Senior: A team reports that @Cacheable, @Transactional and @Async all "randomly stop working". How do you investigate?

Three symptoms, one mechanism — so I would look for a proxy problem before investigating any of them individually.

First, confirm the bean is proxied at all. Log service.getClass().getName(): OrderService$$SpringCGLIB$$0 means proxied, a plain class name means not. If it is not a bean — created with new, or in a package that is not scanned — nothing else matters.

Second, look for self-invocation, which is by far the most common cause. A quick structural check is to grep for calls to annotated methods from within their own class. If the team has a pattern of "orchestrator method loops and calls the annotated worker method", that is it.

Third, check the method modifiers. final, private, static and package-private methods are never advised by CGLIB, and only the final-class case produces a startup error. The rest fail silently, which is why "randomly" is a plausible description — it depends on which code path was taken.

Fourth, per-feature confirmation. For transactions, logging.level.org.springframework.transaction.interceptor=TRACE logs every boundary the interceptor opens; no line means the proxy was never reached. Cache and async have equivalent debug loggers.

What I would put in place afterwards is a test rather than a rule. A small integration test asserting AopUtils.isAopProxy(bean) for the beans that depend on advice, plus a query-count or cache-hit assertion on one representative path, converts "randomly stops working" into a build failure. This class of bug is invisible in review precisely because the annotation is right there in the code looking correct.

2 (easy): Every service method in the application started returning null after this aspect was added. Explain. 
  @Aspect @Component
  public class LoggingAspect {
      @Around("execution(* com.acme.service..*(..))")
      public void log(ProceedingJoinPoint pjp) throws Throwable {
          log.info("entering {}", pjp.getSignature().getName());
          pjp.proceed();
          log.info("exiting {}", pjp.getSignature().getName());
      }
  }
Solution

The advice is declared void and discards proceed()'s result. An @Around advice's return value becomes the advised method's return value. A void advice returns nothing, so Spring returns null to every caller.

The target method still runs — the log lines appear, the database is written — but the result is thrown away. That combination makes it particularly confusing: the side effects work and only the return values vanish.

And because the pointcut covers the whole service package, this happens to every service method at once, with stack traces pointing at callers rather than at the aspect.

  @Aspect @Component
  @Order(Ordered.LOWEST_PRECEDENCE)
  public class LoggingAspect {
      @Around("@annotation(com.acme.Timed)")
      public Object log(ProceedingJoinPoint pjp) throws Throwable {
          long start = System.nanoTime();

              return pjp.proceed();          // RETURN it
          } finally {
              log.debug("{} took {}ms", pjp.getSignature().toShortString(),
                        (System.nanoTime() - start) / 1_000_000);
          }
      }
  }

3 (medium): Write an aspect that retries a method on a specific exception, with backoff, and explain what you would check before shipping it.
Solution 
  @Target(METHOD) @Retention(RUNTIME)
  public @interface RetryOnConflict {
      int maxAttempts() default 3;
      long initialDelayMs() default 50;
  }

  @Aspect @Component
  @Order(Ordered.HIGHEST_PRECEDENCE)     // OUTSIDE @Transactional
  public class RetryAspect {

      @Around("@annotation(retry)")
      public Object retry(ProceedingJoinPoint pjp, RetryOnConflict retry)
              throws Throwable {
          int attempt = 0;
          long delay = retry.initialDelayMs();
          while (true) {
              try {
                  return pjp.proceed();
              } catch (OptimisticLockingFailureException e) {
                  if (++attempt >= retry.maxAttempts()) throw e;
                  long jittered = delay / 2
                      + ThreadLocalRandom.current().nextLong(delay);
                  Thread.sleep(jittered);
                  delay *= 2;
              }
          }
      }
  }
Check before shippingWhy
Aspect order relative to @TransactionalThe retry must be outside the transaction. Retrying inside a failed transaction retries within a rollback-only context and every attempt fails. HIGHEST_PRECEDENCE puts it first
Is the operation idempotent?Retrying a non-idempotent method duplicates work. An optimistic-lock failure implies nothing committed, which is why this specific exception is safe — a generic retry on Exception would not be
JitterWithout it, contending threads retry in lockstep and collide again. This is what turns retry from a fix into a thundering herd
Bounded attemptsUnbounded retries under contention collapse throughput rather than degrading it
Thread.sleep holds the request threadAcceptable for 50–200 ms; not for seconds. On a servlet container that is a thread out of a bounded pool
Self-invocationLike every annotation here, it does nothing if called from within the same class

What I would actually do before writing any of this: use spring-retry's @Retryable, which is this aspect plus circuit breaking, listeners, recovery methods and stateful retry, already tested. I would write my own only if I needed behaviour it does not support.

The exercise is still worth doing because it makes the ordering constraint concrete — that is the detail people get wrong with @Retryable too, and the symptom is a retry that never succeeds no matter how many attempts are configured.

4 (medium): An aspect meant to log slow methods added 400 ms to p99. Diagnose and fix. 
  @Aspect @Component
  public class PerfAspect {
      @Around("execution(* com.acme..*(..))")
      public Object measure(ProceedingJoinPoint pjp) throws Throwable {
          long t = System.currentTimeMillis();
          Object r = pjp.proceed();
          long took = System.currentTimeMillis() - t;
          log.info("{}.{} args={} took={}ms",

              Arrays.toString(pjp.getArgs()), took);
          return r;
      }
  }
Solution
ProblemCost
com.acme..* matches everythingEvery getter, every entity accessor, every helper. Hundreds of millions of invocations per hour at ~90 ns of advice each
Logs unconditionally at infoA log line per invocation — 40 GB/day in the measured case, and the I/O is synchronous

  @Aspect @Component
  @Order(Ordered.LOWEST_PRECEDENCE)
  public class PerfAspect {
      private static final long SLOW_MS = 500;

      @Around("@annotation(com.acme.Timed)")
      public Object measure(ProceedingJoinPoint pjp) throws Throwable {
          long start = System.nanoTime();
          try {
              return pjp.proceed();
          } finally {
              long ms = (System.nanoTime() - start) / 1_000_000;
              if (ms > SLOW_MS)                       // only slow ones
                  log.warn("slow: {} took {}ms",
                           pjp.getSignature().toShortString(), ms);
          }
      }
  }

The fixes in order of impact: the annotation-driven pointcut removes 99.9% of the invocations; logging only above a threshold removes almost all the I/O; dropping arguments removes both the formatting cost and the data-leak risk; nanoTime makes the measurement monotonic; and finally means failing calls are timed too.

What I would ship instead: Micrometer's @Timed with the Actuator. It produces percentile histograms rather than log lines, costs a counter increment, and integrates with Prometheus — which is what someone actually wants when they ask for "slow method logging". A log line per slow call answers "was this call slow"; a histogram answers "is this method getting slower", which is the real question.

5 (hard): A method annotated @Transactional, @Cacheable and @Retryable behaves unpredictably. Explain the interactions and define the correct order.
Solution

Three interceptors on one method, and their nesting order changes the semantics completely. Spring orders advice by @Order; without explicit ordering it is undefined, which is why the behaviour looks random and can differ between environments.

  THE CORRECT NESTING, outermost first

    @Cacheable        ← outermost: a cache hit should skip everything
      @Retryable      ← retry the whole transaction, not within it
        @Transactional ← innermost: each attempt is its own transaction
          your method
If ordered wronglyWhat breaks
Transaction outside retryRetries happen inside a transaction already marked rollback-only. Every attempt fails, and the final failure is UnexpectedRollbackException rather than the real cause
Cache inside transactionThe transaction opens on every call even for a cache hit — a connection acquired and released to return a cached value
Cache inside retryEach retry attempt re-checks the cache; harmless but pointless work
Retry outside cacheA failure retries the cache lookup too, which cannot help
  spring.aop.proxy-target-class: true

  # Spring's built-in orders (lower = more outer)
  #   @Cacheable        CacheAspectSupport   -> Ordered.LOWEST_PRECEDENCE by default
  #   @Transactional    tx advisor           -> configurable
  #   @Retryable        retry advisor        -> configurable

  @EnableTransactionManagement(order = 200)
  @EnableRetry(order = 100)
  @EnableCaching(order = 50)
  @Configuration
  class AopOrderConfig {}

The most consequential interaction is retry versus transaction, and it is the one people get wrong. If the transaction is outermost, a retryable failure has already poisoned the transaction: it is marked rollback-only, so every subsequent attempt operates in a doomed context and fails at commit regardless of whether the underlying problem cleared. The symptom is a retry configuration that appears to do nothing.

A second interaction worth knowing: @Cacheable caches the return value before the transaction commits if the cache advice is inside the transaction. If the transaction then rolls back, the cache holds a value that was never persisted — a phantom read served to every subsequent caller until eviction. Keeping cache outermost avoids this, and for write-through caching @CachePut plus a TransactionalEventListener on AFTER_COMMIT is safer still.

What I would actually recommend: do not stack three declarative behaviours on one method. Split them — a caching facade calling a retrying service calling a transactional repository operation — so the order is explicit in the call graph rather than encoded in @Order values that no reader will check. The stacking works, but it makes the method's semantics depend on configuration that lives somewhere else entirely.

6 (hard): Design an audit-logging capability for a regulated system: every state change recorded with actor, timestamp, before and after values, guaranteed not to be bypassed. Say where AOP fits and where it does not.
Solution

The requirement that shapes everything is "guaranteed not to be bypassed". An aspect cannot provide that guarantee, and recognising why is the point of the exercise.

Aspect-based auditing fails whenBecause
A method is self-invokedNo proxy, no advice, no audit record
Someone adds a final modifierSilently unadvised
A new service forgets the annotationNothing enforces it
A bulk @Modifying query updates rowsNever passes through any advised method
A migration script or another service writesNever touches your application at all

For a regulated system, "we annotated all the methods we could think of" is not a control. So the design has to be layered, with the guarantee at the bottom.

  LAYER 1 -- THE GUARANTEE: database triggers or temporal tables

    create table account_history (like account);
    create trigger account_audit after insert or update or delete
      on account for each row execute function record_history();

    Or PostgreSQL system-versioned tables / SQL Server temporal
    tables. Captures EVERY write regardless of origin -- your app,
    another service, a DBA at a psql prompt, a migration.

    This is the layer a regulator can be shown.

  LAYER 2 -- BUSINESS CONTEXT: an explicit domain event

    @Transactional
    public void closeAccount(Long id, String reason) {
        Account a = accounts.findById(id).orElseThrow();
        a.close(reason);
        auditRepository.save(AuditEntry.of(          // SAME transaction
            "ACCOUNT_CLOSED", currentUser(), id, reason, clock.instant()));
    }

    The trigger records WHAT changed. Only the application knows WHY,
    and who asked. Writing it in the same transaction makes the audit
    row and the change atomic -- neither can exist without the other.

  LAYER 3 -- AOP: convenience for the uniform parts only

    @Audited(action = "ACCOUNT_CLOSED")
    @Transactional
    public void closeAccount(Long id, String reason) { ... }

    Fine for capturing actor, timestamp, method and outcome. NOT the
    guarantee -- a convenience so layer 2 is less repetitive.
LayerGuaranteesKnows whyBypassable
DB triggersEvery writeNoOnly by a DBA disabling them
Explicit domain writeAtomic with the changeYesBy forgetting to write it
AOPNothingPartiallyEasily

Enforcement for layer 2, since "remember to write the audit row" is not a control either: an ArchUnit rule asserting that every public method on a class annotated @AuditedAggregate is annotated @Audited, failing the build otherwise. That turns a convention into something CI checks on every commit.

What I would not do: rely on @EntityListeners / @PreUpdate for the guarantee. Those fire inside the persistence context and are bypassed by bulk @Modifying updates and native queries — the exact operations most likely to touch many rows, and therefore the ones most worth auditing.

The honest cost: triggers add write latency and are invisible to application developers, so a schema change that forgets to update a trigger is a real risk. In a regulated system that is the correct trade, and it should be documented as a deliberate one — the alternative is a control that depends on nobody ever writing this.closeAccount().

🎯 Key Takeaways

  • Every declarative Spring feature is the same proxy with a different interceptor. Understanding the mechanism once explains all of them.
  • The proxy is a wrapper around the object. A call that does not go through it gets none of the behaviour.
  • Spring Boot uses CGLIB by default, subclassing your class rather than implementing its interfaces.
  • final, private and static methods are never advised — silently, in most cases.
  • Self-invocation is the most common Spring bug. this.method() can never be advised, and it cannot be otherwise.
  • Prefer moving the method to another bean — the self-invocation problem is usually a missing design boundary.
  • An @Around that does not return proceed()'s value makes every advised method return null, with stack traces pointing at callers.
  • Use the narrowest advice type; @Around is the only one that can break the method.
  • Always try/finally around proceed(), or failing calls are never measured or logged.
  • Broad pointcuts are hazardous — one added 400 ms to p99 and 40 GB of logs a day.
  • Prefer @annotation(...) pointcuts: visible at each site, greppable, impossible to widen by accident.
  • Proxy overhead is ~90 ns — 0.045% of one indexed query, and catastrophic only on methods called at memory-access frequency.
  • Never format arguments unconditionally in advice — it costs work on every call and can trigger lazy loading and leak secrets.
  • Aspect order is undefined without @Order, and cache/retry/transaction ordering changes semantics.
  • Retry must be outside the transaction, or every attempt runs in a rollback-only context.
  • Caching inside a transaction can cache a value that then rolls back.
  • Do not put business logic in aspects. If a reader of the method would be wrong without knowing the aspect exists, it belongs in the method.
  • AOP cannot guarantee anything — for audit requirements the guarantee belongs in the database, with aspects as convenience on top.
