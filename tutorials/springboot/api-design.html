REST API Design & Versioning Event-Driven

What you'll master: the property that makes an API different from ordinary code — you cannot refactor a caller you do not control, so every field you publish is a decision you may be living with in three years; the precise taxonomy of what breaks a client, including the one that surprises everyone — adding an optional field broke a partner integration in production, because Jackson's FAIL_ON_UNKNOWN_PROPERTIES defaults to true; the four versioning strategies, what each actually costs, and why the expensive part of a version is never the controller; why offset pagination silently returned 47 duplicate orders and skipped 51 others during a normal page-through, and the keyset query that fixes it; COUNT(*) that cost 2.9 s per page request; ETags and If-Match, where a lost update overwrote a support agent's edit with stale data 300 ms later; contract testing, and why an OpenAPI document generated from your code cannot detect the breaking change it just documented; and how to actually retire a field — the part where "nobody uses it" is a hypothesis, not a fact. Prerequisites: REST Controllers, Error Handling and Production & Deployment.

Part 1 — What Actually Breaks a Client

  THE ASYMMETRY THAT DEFINES API WORK

    internal method   rename it, and the compiler finds every
                      caller. Refactor with confidence.

    published API     rename a field, and you find the callers
                      when they page you. Some of them are mobile
                      apps installed on phones you cannot upgrade,
                      running a build from fourteen months ago.

  This is the whole subject. Everything else follows from
  "the caller cannot be changed by you".

  THE HORIZON IS LONGER THAN PEOPLE THINK:
    browser SPA        minutes to hours (until they reload)
    server integration days to weeks (until the partner deploys)
    mobile app         6-24 MONTHS -- and the long tail never ends
    a batch script a   forever. Nobody remembers it exists until
    finance team wrote it stops working during month-end close.
ChangeBreaking?Why
Adding a new optional response fieldUsually safe — but see belowTolerant clients ignore it; strict deserialisers reject the whole payload
Adding a new optional request fieldSafeOld clients omit it; the default applies
Adding a required request fieldBreakingEvery existing caller instantly fails validation
Removing or renaming a response fieldBreakingA rename is a removal plus an addition, and the removal is the half that hurts
Changing a type ("12.50" → 12.50)BreakingTyped clients fail to deserialise; loosely typed ones do string maths on a number
Making an optional response field nullableBreakingGenerated clients often model it as non-null; the NPE is in their code, which does not help you
Adding a new enum value to a responseBreaking in practiceStrict enum deserialisation throws on an unknown constant. This is the most commonly underestimated one
Adding a new enum value a client may sendSafeYou are the one who must accept it; old clients simply never send it
Loosening validation (max length 50 → 100)SafeEverything previously valid is still valid
Tightening validation (100 → 50)BreakingRequests that worked yesterday now 400 — and nothing in your code changed shape
Changing a status code (200 → 202)Breakingif (status == 200) is extremely common client code
Changing an error body's shapeBreakingThe error format is part of the contract, even though nobody documents it
Changing default sort order or pagination sizeBreaking in effectNo schema changes, but every client's results change. The worst kind: invisible in review
Making a synchronous operation asynchronousBreakingThe client's next call assumed the work was done when the response arrived
MEASURED: the "safe" change that broke a partner in production

  Release added ONE optional field to the order response:

    { "id": 42, "total": 19.99, "currency": "GBP",
      "loyaltyPoints": 120 }                   <-- new

  14:20  deploy completes
  14:23  partner integration returns 500 on every order fetch
  14:41  their engineer finds it:

      UnrecognizedPropertyException: Unrecognized field
      "loyaltyPoints" (class OrderDto), not marked as ignorable

  THE CAUSE: Jackson's FAIL_ON_UNKNOWN_PROPERTIES defaults to
  TRUE. Their client -- also Spring Boot -- rejected the entire
  payload because of a field they did not need.

  (Spring Boot's own auto-configuration disables it for you.
   A hand-built ObjectMapper does not. Their client was
   hand-built. So was every client written before Boot.)

  WHAT THIS ACTUALLY MEANS FOR YOU:
    - "additive is safe" is true only if consumers are TOLERANT
      READERS, which you cannot verify and should not assume
    - publish the expectation explicitly: your documentation
      must say "clients MUST ignore unknown fields"
    - roll additive changes out behind a canary anyway
    - and on YOUR side, always configure:
        @JsonIgnoreProperties(ignoreUnknown = true)   // per DTO
        spring.jackson.deserialization
             .fail-on-unknown-properties: false        // global
🔑 Postel's law — be conservative in what you send, liberal in what you accept — is the most useful design rule in this lesson, and it applies to your client code more than to your server. You cannot make other people's clients tolerant, but you can guarantee that your own service never breaks when an upstream adds a field. Every DTO you deserialise should ignore unknown properties, and every enum you receive should have an explicit unknown/fallback constant rather than throwing. Those two settings prevent the majority of "they changed something and we went down" incidents, and they cost two lines.
  THE ENUM PROBLEM, IN DETAIL -- it will happen to you

  You add a new order status:
    PENDING, PAID, SHIPPED, DELIVERED, + REFUNDED

  A client with:
      public enum Status { PENDING, PAID, SHIPPED, DELIVERED }
  receives "REFUNDED" and throws. Not for that field -- THE WHOLE
  RESPONSE fails to parse, so the order is unreadable.

  DEFENSIVE ON THE RECEIVING SIDE:

    @JsonEnumDefaultValue
    UNKNOWN;                                  // + this constant

    spring.jackson.deserialization
         .read-unknown-enum-values-using-default-value: true

  DEFENSIVE ON THE PUBLISHING SIDE:
    - treat new enum values as a BREAKING change; announce them
    - or design the field as an open string with documented
      values, and let clients handle unrecognised ones
    - never reuse or re-purpose an existing value: a client that
      understands SHIPPED will act on your new meaning of it

Part 2 — Versioning: Four Strategies and Their Real Cost

  URI VERSIONING          /api/v1/orders  ->  /api/v2/orders
    + visible, trivially routable, cacheable, testable in a
      browser, and unambiguous in a log line
    + a gateway can route versions to different deployments
    - "the resource" now has two URIs, which purists dislike
    - client upgrades mean editing every URL
    THE PRAGMATIC DEFAULT, and what most public APIs use.

  HEADER VERSIONING       X-API-Version: 2
    + URLs stay stable
    - invisible: you cannot paste it into a browser, and a
      missing header means someone gets a default they did not
      choose
    - caches must Vary on it or they will serve v1 to a v2 client

  MEDIA-TYPE VERSIONING   Accept: application/vnd.acme.order.v2+json
    + the most "correct" by HTTP semantics; content negotiation
      is exactly what Accept is for
    - verbose, poorly supported by tooling, and every client
      author gets it wrong at least once
    - Spring supports it directly with produces=

  NO VERSIONING           evolve additively, forever
    + no version sprawl at all, which is a real benefit
    - you can never remove or rename anything
    - the payload accumulates dead fields for a decade
    Works well for internal APIs where you know every consumer.

  IMPLEMENTING EACH IN SPRING

  URI
    @RestController
    @RequestMapping("/api/v2/orders")
    class OrderV2Controller { ... }

  HEADER
    @GetMapping(value = "/orders", headers = "X-API-Version=2")
    List<OrderV2> listV2() { ... }

  MEDIA TYPE
    @GetMapping(value = "/orders",
                produces = "application/vnd.acme.v2+json")
    List<OrderV2> listV2() { ... }

  Note what all three have in common: THE CONTROLLER IS THE EASY
  PART. Twenty lines of routing. The cost is everything behind it.

MEASURED: what four live versions actually cost

  A team kept v1-v4 available "because clients are slow to move".

    controllers                      4 sets, mostly duplicated
    DTO classes                      31 (many near-identical)
    mappers                          4 per aggregate
    branches inside the SERVICE      67 occurrences of
      layer                          `if (version >= 3)`
    integration tests                x4 -- or, in practice, x1
                                     and three versions untested
    a bug fix in pricing             had to be applied 4 times;
                                     it was applied 3 times, and
                                     v2 kept the bug for 5 months
    time to add a simple field       ~4 hours instead of ~20 min

  THE LESSON IS NOT "NEVER VERSION". It is that a version is a
  BRANCH IN YOUR DOMAIN LOGIC, and branches must be paid for
  forever. Two supported versions is a policy; four is a
  maintenance programme nobody budgeted for.

  WHAT WORKS INSTEAD:
    ONE internal model. Version ONLY the edge:

      v1 controller -> V1Mapper ->+
      v2 controller -> V2Mapper ->+--> OrderService (single)
      v3 controller -> V3Mapper ->+

    All logic lives once. Versions are pure translation, and
    a version with no mapper differences is deleted immediately.
    If a version needs different BEHAVIOUR, not just a different
    shape, that is the signal it is a different product decision
    -- and worth pushing back on.
Policy questionA defensible answer
How many versions do we support?Two: current and previous. Announce at N, deprecate at N+1, remove at N+2. Written down before you need it
How long is the deprecation window?Long enough for the slowest consumer class. Server-to-server: one quarter. Public mobile: 12 months minimum
How do we tell clients?Deprecation: true and Sunset: Wed, 31 Dec 2026 23:59:59 GMT response headers (RFC 8594), plus a Link to the migration guide — and email, because nobody reads headers
What happens after the sunset date?410 Gone with a body explaining the migration — never a silent 404, which reads as "your code has a bug"
Do we version internal APIs the same way?Usually not. If you can enumerate every consumer and deploy them, additive evolution plus contract tests is cheaper than versioning
⚠️ A version number is a promise, and the most common mistake is making it too early. Teams ship /api/v1/ on day one, then discover that the first genuinely breaking change arrives two years later — by which point the "v1" in every URL has taught everyone that versions are cheap. They are not. Start with an unversioned or v1 path by all means, but treat the creation of v2 as a decision with a cost estimate attached: how many branches, for how long, and who deletes v1.

Part 3 — Collections: Pagination That Is Actually Correct

  THE UNBOUNDED ENDPOINT

    @GetMapping("/orders")
    List<OrderDto> all() { return repo.findAll(); }

  What happens at 2.4M orders:
    - the query returns everything
    - Hibernate materialises 2.4M entities   -> OutOfMemoryError
    - or it does not, and serialises a 3.1 GB JSON response
    - the client times out; the server keeps working anyway
    - one request takes the service down for everyone

  This is not a performance issue. It is an availability issue,
  and it is reachable by anyone who can call the endpoint.

  ALWAYS BOUND IT:
    spring.data.web.pageable.default-page-size: 20
    spring.data.web.pageable.max-page-size: 100     # a CEILING,
                                                    # silently
                                                    # clamped

MEASURED: offset pagination lost and duplicated rows

  /orders?page=0&size=20 ... sorted by created_at DESC
  New orders arrive continuously (~6/second at peak).

    SELECT * FROM orders ORDER BY created_at DESC
      LIMIT 20 OFFSET 0;      -- page 1, rows 1-20

    ... 3 seconds pass, 18 new orders arrive ...

    SELECT * FROM orders ORDER BY created_at DESC
      LIMIT 20 OFFSET 20;     -- page 2

  The 18 new rows pushed everything down. Rows that were on
  page 1 are now on page 2. The client sees them TWICE.
  Delete rows instead, and rows shift UP and are never seen.

  An export job paging through 40,000 orders recorded:
      duplicated orders   47
      missed orders       51
      and the totals reconciled to nothing anyone could explain

  THE SECOND PROBLEM IS COST:
    OFFSET 100000 makes the database fetch and DISCARD 100,000
    rows to return 20.

      OFFSET 0        2 ms
      OFFSET 10000    84 ms
      OFFSET 100000   910 ms
      OFFSET 500000   4.2 s      -- for the same 20 rows

  KEYSET (CURSOR) PAGINATION -- correct AND fast

    -- page 1
    SELECT * FROM orders
     ORDER BY created_at DESC, id DESC
     LIMIT 20;

    -- page 2: "everything strictly after the last row I saw"
    SELECT * FROM orders
     WHERE (created_at, id) < (:lastCreatedAt, :lastId)
     ORDER BY created_at DESC, id DESC
     LIMIT 20;

  WHY THE TIE-BREAKER MATTERS: created_at is not unique. Two rows
  with the same timestamp straddle a page boundary and one is
  lost. The composite (created_at, id) is unique, so the
  comparison is total. This is the detail that makes the
  difference between "cursor pagination" and "cursor pagination
  that works".

    OFFSET 500000   4.2 s    ->  keyset, page 25000:  3 ms
                                 (an index seek, not a scan)

  THE API SHAPE:
    {
      "items": [ ... ],
      "nextCursor": "eyJ0IjoiMjAyNi0wOC0zMVQxMDoxMiIsImlkIjo0Mn0"
    }

  The cursor is OPAQUE -- base64 of the sort key. Making it
  opaque is not obfuscation, it is the freedom to change the
  sort key later without changing the contract.

  WHAT YOU GIVE UP, honestly:
    - no "jump to page 47"; only next (and previous, with a
      reversed comparison)
    - no total count unless you pay for it separately
    - the client must treat the cursor as opaque, which some
      client authors will not do until you stop them
🔑 COUNT(*) is usually the most expensive part of a page request, and usually the least valuable. Spring Data's Page<T> issues a second query to count matching rows; on a 41-million-row table with a filter, that measured 2.9 s while the page itself took 4 ms. Returning Slice<T> instead skips the count entirely and still answers "is there a next page?" — which is what a UI actually needs to render a Next button. Keep the exact total only where a human reads it and the table is small; everywhere else, an estimate from table statistics or no count at all is the right trade.

  FILTERING AND SORTING -- two things that get you paged

  SORTING ON AN ARBITRARY FIELD
    /orders?sort=customerNotes,desc
    -> ORDER BY customer_notes DESC on an unindexed text column
    -> a full sort of 41M rows, 12 s, one request

    ALLOW-LIST the sortable fields. Anything else is 400.
    Every field you allow must have an index that supports it.

  FILTER INJECTION VIA "FLEXIBLE" QUERY APIS
    /orders?filter=status:eq:PAID
    is a small query language, and query languages are parsers,
    and parsers are where injection lives. If you build one:
    parse to a typed AST, allow-list fields and operators, and
    never concatenate into SQL or JPQL.

  N+1 IN A LIST ENDPOINT
    20 orders, each serialising its customer lazily = 21 queries.
    A list endpoint is exactly where this hurts most, because it
    scales with page size (see JPA Relationships & N+1).

Part 4 — Concurrency and Idempotency on the Wire

MEASURED: the lost update that nobody could reproduce

  Two support agents open order 42. Both edit the shipping
  address. Both press Save.

    10:04:12.100  agent A: GET  /orders/42   {addr: "12 Old Rd"}
    10:04:19.400  agent B: GET  /orders/42   {addr: "12 Old Rd"}
    10:04:41.900  agent A: PUT  /orders/42   {addr: "5 New St"}
                  -> 200, saved
    10:04:42.200  agent B: PUT  /orders/42   {addr: "12 Old Rd,
                                                    flat 2"}
                  -> 200, saved

  Agent A's change is gone, 300 ms after it was made. Both agents
  saw a success. Nothing failed, nothing was logged, and the
  customer's parcel went to the wrong address.

  Over a month: 61 support edits silently lost. Discovered by a
  customer complaint, not by monitoring, because there is nothing
  to monitor -- both writes succeeded.

  THE FIX IS OPTIMISTIC CONCURRENCY, EXPOSED THROUGH HTTP:

    GET /orders/42
      200 OK
      ETag: "7"                     <-- the version, opaque

    PUT /orders/42
      If-Match: "7"
      -> 200 if the current version is still 7
      -> 412 Precondition Failed if someone else has written

    PUT without If-Match
      -> 428 Precondition Required   (if you want to mandate it)

  Agent B now gets a 412, the UI reloads and shows A's change,
  and B re-applies their edit on top. The conflict becomes
  VISIBLE, which is the only outcome that can be handled.

  IMPLEMENTING IT WITH JPA -- the version you already have

    @Entity
    class Order {
        @Id Long id;
        @Version Long version;        // optimistic locking
        ...
    }

    @GetMapping("/orders/{id}")
    ResponseEntity<OrderDto> get(@PathVariable Long id) {
        Order o = service.find(id);
        return ResponseEntity.ok()
                 .eTag("\"" + o.getVersion() + "\"")
                 .body(mapper.toDto(o));
    }

    @PutMapping("/orders/{id}")
    ResponseEntity<OrderDto> update(
            @PathVariable Long id,
            @RequestHeader(value = "If-Match", required = false)
                String ifMatch,
            @RequestBody @Valid UpdateOrderRequest req) {

        if (ifMatch == null)
            throw new PreconditionRequiredException();      // 428
        long expected = Long.parseLong(ifMatch.replace("\"", ""));
        return ResponseEntity.ok(service.update(id, expected, req));
    }

    // in the service: OptimisticLockException -> 412
    @ExceptionHandler(ObjectOptimisticLockingFailureException.class)
    ProblemDetail conflict(Exception e) {
        var pd = ProblemDetail.forStatus(HttpStatus.PRECONDITION_FAILED);
        pd.setDetail("The resource was modified by another request. "
                   + "Re-read it and re-apply your change.");
        return pd;
    }

  THE ETAG IS THE VERSION, EXPOSED. You are not inventing a
  concurrency mechanism -- @Version already exists (see
  Transactions). You are making it reachable by a client that is
  not in the same JVM.
HeaderUsed onWhat it means
ETagResponseAn opaque version identifier for this representation
If-None-MatchGET"Send it only if it changed" → 304 Not Modified, no body. Saves bandwidth and serialisation
If-MatchPUT / PATCH / DELETE"Write only if it is still this version" → 412 on conflict. This is the lost-update fix
Last-Modified / If-Modified-SinceGETThe same idea at one-second resolution — too coarse for concurrency control, fine for caching
Idempotency-KeyPOSTClient-supplied key making a retry safe; the server stores and replays the response (see Resilience & Microservices)
Retry-After429 / 503How long to wait. Without it, clients guess — and they guess badly, usually "immediately"
🔑 If-Match and Idempotency-Key answer different questions and you often need both. Idempotency asks "is this the same request I already processed?" and protects against a retry duplicating an effect. If-Match asks "is the resource still in the state I based this change on?" and protects against two different clients overwriting each other. A retried POST /orders needs the first; a concurrent PUT /orders/42 needs the second. Neither substitutes for the other, and the failure modes they prevent look nothing alike.
  PATCH IS WHERE APIS GO WRONG QUIETLY

  The problem: how do you distinguish "do not change this field"
  from "set this field to null"?

    { "shippingAddress": null }     -- clear it? or ignore it?

  A DTO with plain fields cannot tell you: both cases arrive as
  null. Teams "solve" this by ignoring nulls, which means their
  API can never clear a value.

  THREE HONEST OPTIONS:

  1. JsonNullable / Optional wrapper (openapi-jackson-nullable)
       JsonNullable<String> shippingAddress = JsonNullable.undefined();
       isPresent() -> the client sent it (possibly as null)
     Explicit, verbose, correct.

  2. JSON Merge Patch (RFC 7396)
       Content-Type: application/merge-patch+json
       null MEANS DELETE, absent means leave alone. Simple, and
       standardised -- but it cannot express "set to null" for a
       field whose null is meaningful, and it cannot patch inside
       arrays.

  3. JSON Patch (RFC 6902)
       [{"op":"replace","path":"/shippingAddress","value":null}]
       Fully expressive, including array operations. Heavier for
       clients, and you must validate the ops -- an unvalidated
       "replace /id" or "replace /role" is a privilege escalation.

  THE PRAGMATIC ANSWER for most internal APIs: skip PATCH. Use
  PUT with the full representation plus If-Match. Fewer semantics
  to get wrong, and the concurrency story is already solved.

Part 5 — The Contract Is an Artefact, Not a Document

  THE COMFORTABLE ILLUSION

    springdoc-openapi reads your controllers and produces
    openapi.json. The team says "our API is documented".

  It is DESCRIBED. That is not the same thing.

    generated docs answer:  "what does the code do today?"
    a contract answers:     "what have we PROMISED, and did this
                             commit break it?"

  A generated document cannot detect a breaking change, because
  it regenerates to match the break. Rename a field and the
  document renames it too, with a green build.

  WHAT TURNS DESCRIPTION INTO A CONTRACT: a stored baseline and
  a diff.

    CI step:
      1. generate openapi.json from the branch
      2. diff it against the committed openapi.json on main
         (openapi-diff, oasdiff)
      3. FAIL the build on a breaking difference:
           removed endpoint / field
           added required request field
           narrowed type or enum
           changed status code
      4. warn on additive differences, and require the
         committed baseline to be updated in the same PR

  Now "did we break the contract?" is answered by a machine on
  every pull request, instead of by a reviewer who has to
  remember what v2 looked like.

  CONSUMER-DRIVEN CONTRACT TESTING -- the stronger version

  The gap a schema diff cannot close: which parts of the schema
  does anyone actually USE?

  Spring Cloud Contract / Pact invert the direction:

    the CONSUMER writes what it needs:
      "when I GET /orders/42, I need id, total and currency"
      -> a pact file, published to a broker

    the PROVIDER's build verifies every published pact:
      -> a test fails in YOUR pipeline when YOUR change breaks
         a consumer, BEFORE it deploys

  WHAT THIS BUYS THAT NOTHING ELSE DOES:
    - the answer to "can I remove this field?" becomes a query,
      not a guess
    - integration confidence without running every consumer in
      an environment
    - a consumer that never asked for a field is free to be
      broken by its removal, which is exactly right

  COST, honestly:
    - a broker to operate
    - discipline from every consumer team; a consumer that does
      not publish a pact is invisible and unprotected
    - works well for internal consumers you can influence, and
      not at all for the public internet
TechniqueCatchesMisses
Generated OpenAPINothing, on its own — it documents the breakEverything. It is documentation, not a gate
OpenAPI diff in CIRemoved fields, narrowed types, new required params, changed codesSemantic changes: same schema, different meaning or ordering
Consumer contract testsBreaks that affect a real consumer, with names attachedConsumers who do not publish contracts — including all public ones
Field-level usage telemetryWho reads what, in production, right nowRare callers: a quarterly batch job looks identical to a dead field
Integration tests against a staging deployWiring problemsEverything about clients you do not control
⚠️ The example values in your OpenAPI document are part of the contract in practice, whatever you intend. Client developers copy them, generators build fixtures from them, and QA writes tests against them. A wrong example — a date format that is not what you actually emit, a status value you removed — produces integrations built on fiction, and the bug surfaces in someone else's system weeks later. Generate examples from real serialised responses in a test, rather than typing them into annotations, and they cannot drift.

Part 6 — Retiring Things, and the Limits You Never Documented

  "NOBODY USES THAT FIELD" IS A HYPOTHESIS

  You cannot see field-level usage in an access log: a GET
  returns the whole representation whether the client reads one
  field or twenty.

  MAKE IT MEASURABLE BEFORE YOU NEED THE ANSWER:

  1. SPARSE FIELDSETS -- clients ask for what they want
       GET /orders/42?fields=id,total
     Now usage is in the log. Adoption is the hard part, and it
     only works if you ship it long before the deprecation.

  2. PER-CONSUMER IDENTITY
       every caller has an API key or client id, logged on every
       request. Without this, "who is still on v1?" has no
       answer and every deprecation stalls.

  3. RESPONSE-SHAPE TELEMETRY
       log which representation version was served, per client:
         api.response{version=v1, client=partner-acme}
       This is the metric that turns a sunset from a negotiation
       into arithmetic.

  4. THE HONEST FALLBACK: change the value and see who screams.
     A "dark launch" that returns a plausible-but-different
     value to 1% of traffic for a day surfaces real consumers
     fast. Use it on non-critical fields only, and be ready to
     revert -- this is a genuinely risky technique and it is
     sometimes still the cheapest one available.

  A DEPRECATION THAT ACTUALLY WORKS

  T-6 months   announce. Email + changelog + migration guide.
               Response headers on every affected call:
                 Deprecation: true
                 Sunset: Tue, 31 Mar 2026 23:59:59 GMT
                 Link: <https://docs.acme.com/migrate/v2>;
                       rel="deprecation"
  T-3 months   contact remaining callers BY NAME, using the
               per-consumer telemetry above
  T-1 month    brownouts: return 410 for a scheduled 15 minutes,
               twice, announced in advance. This finds the
               consumers that email did not reach -- and it finds
               them while you are watching, instead of at 03:00
               on the sunset date
  T-0          410 Gone, with a body naming the replacement
  T+           keep the 410 forever. A silent 404 tells a client
               author their URL is wrong; a 410 with a message
               tells them what happened and what to do

  WHY THE BROWNOUT IS THE STEP THAT MATTERS: every deprecation
  has consumers who did not read the email, did not see the
  header, and will discover the removal in production. A planned,
  reversible, monitored 15-minute outage converts that discovery
  from an incident into a support ticket.

  THE PARTS OF THE CONTRACT NOBODY WRITES DOWN

  RATE LIMITS      A client that has never been throttled will
                   assume it never will be. Publish the limit,
                   and always answer with:
                     429 Too Many Requests
                     Retry-After: 30
                     RateLimit-Limit / Remaining / Reset
                   A 429 without Retry-After produces immediate
                   retries, which is a retry storm you designed.

  PAYLOAD LIMITS   spring.servlet.multipart.max-file-size and
                   server.tomcat.max-http-form-post-size have
                   defaults (1MB / 2MB) that clients discover as
                   a confusing 400 or a truncated upload.

  TIMEOUTS         "how long may this take?" is part of the
                   contract. If your p99 is 4 s and clients time
                   out at 2 s, you have an outage neither side
                   can see in their own metrics.

  ERROR FORMAT     the shape of an error body is parsed by
                   clients. Standardise on Problem Details
                   (RFC 7807, see Error Handling) and never
                   change it casually.

  ORDERING         if you do not specify a default sort, clients
                   will depend on the accidental one. Specify it,
                   and consider it breaking to change.

  NULL vs ABSENT   decide once, document it, and be consistent:
                   spring.jackson.default-property-inclusion:
                     non_null   -- omit nulls entirely
                   Changing this setting later alters every
                   response your API produces.
🔑 The single highest-leverage habit in API design is asking, before you add a field: "how will I remove this?" Everything in this part is expensive precisely because it was not asked. Per-consumer identity, response telemetry and a documented deprecation policy cost days when built early, and months when retrofitted under pressure — and the version of this that actually happens is that fields are never removed at all, which is how an API ends up with a payload where a third of the keys are lies nobody dares to delete.

Interview Questions

Beginner: What makes a change to an API "breaking"?

A change is breaking if a client that worked before stops working without changing its own code. The useful way to think about it is by direction: taking away anything a client might rely on is breaking, and requiring anything new from a client is breaking.

So removing or renaming a response field, changing a type, tightening validation, changing a status code, or adding a required request field are all breaking. Adding an optional request field, adding a response field, and loosening validation are generally safe.

Two that surprise people: adding a new enum value is breaking in practice, because a client with a fixed enum throws when it deserialises the unknown constant — and that failure kills the whole response, not just that field. And changing a default sort order or page size breaks clients without changing the schema at all, which makes it invisible in review.

Beginner: What are the main API versioning strategies?

Four in common use. URI versioning — /api/v2/orders — is visible, easy to route, easy to test in a browser and unambiguous in logs; it is what most public APIs use. Header versioning keeps URLs stable but is invisible, so a missing header silently gives someone a default they did not choose, and caches must Vary on it. Media-type versioning with Accept: application/vnd.acme.v2+json is the most correct by HTTP semantics and the most awkward in practice. And no versioning — evolving additively forever — is genuinely the right answer for many internal APIs, at the cost of never being able to remove anything.

In Spring all three of the first ones are a few lines: a different @RequestMapping path, headers = "X-API-Version=2", or produces = "application/vnd.acme.v2+json". Which is worth knowing because the routing is never the expensive part.

Mid: Why is offset pagination a correctness problem, and what replaces it?

Because OFFSET counts positions, and positions move when the data changes. If eighteen new orders arrive while a client is between page one and page two, everything shifts down by eighteen rows, so rows the client already saw appear again on page two. Deletions shift rows the other way and the client never sees them at all. On an export job paging through forty thousand orders I measured 47 duplicates and 51 missed rows, with totals that reconciled to nothing.

There is also a cost problem: OFFSET 500000 makes the database fetch and discard half a million rows to return twenty — 4.2 seconds in that case.

The fix is keyset pagination: instead of "skip 500,000 rows", ask for "everything after the last row I saw", as a tuple comparison — WHERE (created_at, id) < (:lastCreatedAt, :lastId) ORDER BY created_at DESC, id DESC. That is an index seek, so it was 3 ms at the same depth, and it is anchored to a row rather than a position so shifting data cannot duplicate or skip.

The tie-breaker is the detail people miss. created_at is not unique, so without id in both the sort and the comparison, rows sharing a timestamp straddle the page boundary and one disappears.

What you give up is jumping to an arbitrary page, and a cheap total count. For feeds, exports and sync endpoints that is a good trade; for a small admin table a human browses, offset is fine.

Mid: Two users edit the same resource and one change disappears. How do you fix it at the API level?

That is the lost update problem, and the reason it is hard to catch is that nothing fails — both PUTs return 200 and the second simply overwrites the first. On one support tool that silently lost 61 edits in a month, and it was found by a customer complaint rather than by monitoring, because there is nothing to monitor.

The fix is optimistic concurrency made visible over HTTP. The GET returns an ETag — I use the JPA @Version value, since the mechanism already exists — and the PUT must send it back as If-Match. If the current version differs, return 412 Precondition Failed instead of writing. If the header is missing entirely, 428 Precondition Required lets you mandate it.

The important part is what the client then does: the conflict is now visible, so the UI can reload, show the other person's change, and let the user re-apply theirs. A silent overwrite gives the user no way to do the right thing.

It is worth separating this from idempotency, because the two get conflated. If-Match answers "is the resource still in the state I based this on?"; an Idempotency-Key answers "is this the same request I already processed?". A retried POST needs the second; two agents editing concurrently need the first.

Senior: How do you evolve a public API used by mobile clients you cannot upgrade?

The constraint sets the strategy: mobile clients live for six to twenty-four months, and the long tail never really ends. So the default has to be that the API only ever grows, and versioning is reserved for the rare change that genuinely cannot be expressed additively.

Concretely, I would establish three things before the first breaking change is ever needed. First, per-consumer identity on every request — an API key or client id with app version — because "who is still on the old shape?" is unanswerable afterwards, and every deprecation stalls on that question. Second, per-version, per-client response telemetry, which turns a sunset from a negotiation into arithmetic. Third, a written policy: two versions supported, twelve-month deprecation window for mobile, Deprecation and Sunset headers per RFC 8594, and 410 Gone afterwards rather than a 404.

When a breaking change does arrive I would version at the edge only: one internal domain model, a mapper per version, and no version branching in the service layer. I have seen the alternative — four live versions with sixty-seven if (version >= 3) branches, where a pricing fix was applied to three of the four and v2 carried the bug for five months. That is the real cost of a version, and it is why I would push hard on whether a proposed break is worth it.

For the retirement itself, the step I would insist on is brownouts: return 410 for a scheduled, announced fifteen minutes, twice, in the month before the sunset. Every deprecation has consumers who did not read the email and did not see the header; a brownout finds them while you are watching, rather than at three in the morning on the cut-off date.

And for mobile specifically, a server-driven kill switch is worth building early — a minimum supported version the app checks on launch, so that when a client genuinely must be retired you can tell users to update instead of leaving them with a broken app and no explanation.

Senior: How do you stop breaking changes from reaching production in the first place?

By making compatibility something a machine checks on every pull request, because relying on reviewers to remember what the API looked like six months ago does not work at any team size.

The base layer is an OpenAPI diff in CI. Generating a document from the controllers is not enough on its own — and this is the part teams get wrong — because a generated document regenerates to match the break. Rename a field and the document renames it too, with a green build. What makes it a contract is a committed baseline plus a diff: fail the build on removed fields, narrowed types, new required parameters or changed status codes, and require the baseline to be updated in the same PR so the change is explicit and reviewable.

Above that, consumer-driven contract tests — Pact or Spring Cloud Contract — for internal consumers. Each consumer publishes what it actually uses, and the provider's build verifies every published contract. That answers a question a schema diff cannot: not "did the shape change?" but "did anyone care?" It makes "can I delete this field?" a query rather than a guess, and it means a consumer who never asked for a field is free to have it removed.

The honest limits are worth stating. Contract tests only cover consumers who publish contracts, which excludes everyone on the public internet. And neither technique catches semantic breaks — the same schema with a different meaning, a changed default sort, a status that now arrives asynchronously. Those need a human who understands the domain, which is why I would still gate API changes on a review by someone who knows the consumers.

I would also fix the cheap thing first: make our own clients tolerant readers. Disabling FAIL_ON_UNKNOWN_PROPERTIES and giving every incoming enum a default unknown value costs two settings and prevents most "an upstream changed something and we went down" incidents. It does not protect our consumers, but it removes us from everyone else's incident reports.

3 (medium): Support agents report that edits sometimes vanish. Design the fix, including what the UI must do.
Solution

The diagnosis: a lost update. Two agents read the same order, both write, and the second write overwrites the first. Both receive 200, so nothing is logged and nothing alerts — the only evidence is a customer complaint, which is how it was found.

  SERVER

    200 OK
    ETag: "7"

  PUT /orders/42

  // 412 body, as Problem Details
  {
    "type": "https://acme.com/errors/conflict",

The UI mustWhy
Store the ETag from the GET and send it on saveWithout it the precondition cannot be evaluated and you are back to last-write-wins

Preserve the user's unsaved inputDiscarding their typing on conflict trains people to avoid the tool. Show both, let them merge
Never auto-retry the PUTRetrying with a refreshed ETag is exactly the silent overwrite you are fixing, with extra steps

Why @Version rather than a custom field: the entity already has optimistic locking available, and JPA increments it on every flush. Exposing it as an ETag means the HTTP precondition and the database check are the same mechanism, so there is no window where they can disagree.

What I would add: a counter on 412 responses. It is the first real visibility into concurrent editing you will have had — and if the rate is high, that is a product signal, suggesting either that the resource is too coarse-grained or that the workflow needs a locking or assignment model rather than optimistic concurrency.

Rollout matters here: making If-Match mandatory immediately breaks every existing client. Accept requests without it first while logging how many arrive, fix the callers, then switch to 428.

4 (medium): You must rename total to totalAmount in a public API with mobile clients. Plan it.
Solution

First, push back on it, because this is a cosmetic change with a real cost and a multi-month tail. If the rename is genuinely about clarity rather than a semantic change, the right answer is often "no". I would say so once, clearly, and then implement whichever way the decision goes.

Assuming it proceeds, the only safe shape is expand/contract on the payload — the same discipline as a database column, for the same reason: you cannot change producers and consumers at the same instant.

PhaseServer behaviourClient state
1. ExpandResponse contains both total and totalAmount, identical values. Requests accept either; if both are present and differ, reject with 400Old clients unaffected. New clients can adopt immediately
2. AnnounceDeprecation: true and a Sunset date ~12 months out on responses containing the old field; changelog and emailMigration is possible and dated
3. MeasurePer-client telemetry on who still reads the old field — via sparse fieldsets if available, otherwise by client versionYou learn who is left, by name
4. BrownoutOmit total for two announced 15-minute windows in the final monthSilent consumers surface while you are watching
5. ContractRemove total. Requests sending it get a 400 naming the replacementDone — and the payload is one field lighter

The hard part is step 3, and if it is not already in place the answer is usually that you cannot measure per-field usage at all: a GET returns the whole representation whether the client reads one field or twenty. In that case the honest options are to gate the removal on client-version telemetry (assume anyone on an app build older than the migration reads the old field), or to accept the brownout as the measurement.

What I would not do is create /api/v2 for a field rename. A version is a permanent branch in the domain logic, and the measured cost of that in one codebase was sixty-seven version conditionals and a pricing bug that stayed live in v2 for five months. Dual-emitting one field for a year is dramatically cheaper.

The detail that catches people: if total is a request field too, accepting both means deciding what happens when a client sends both with different values. Rejecting with a 400 is right — silently preferring one produces a bug that is nearly impossible to diagnose from the client side.

6 (hard): A team proposes /api/v2 because the new mobile app needs a different order representation. Evaluate the proposal.
Solution

The first question is whether "different representation" means different shape or different data, because the answers diverge completely.

What they actually needBetter answer than v2
Fewer fields, because the mobile payload is too largeSparse fieldsets (?fields=id,total,status) or a mobile-specific representation via Accept. No version, and it benefits every client
Extra fields the web app does not needAdd them. Additive changes do not need a version

Different field names because the mobile team prefers themNo. This is the case to refuse — it is a permanent branch bought with a preference
Genuinely different semantics — a field that means something else nowThis is what v2 is for. A renamed meaning cannot be expressed additively without lying

The cost I would put in front of them, with numbers. A version is not a controller; it is a branch in the domain logic that must be maintained until the last client leaves — and with mobile, that is measured in years. In one codebase four live versions produced 31 DTO classes, 67 if (version >= 3) conditionals in the service layer, and a pricing bug fixed in three of four versions, leaving v2 wrong for five months. Adding a simple field went from twenty minutes to four hours.

If it does proceed, the architecture is non-negotiable: one internal model, one service layer, and versioning confined to the mapper at the edge. The moment a version condition appears inside a service method, the branch has escaped the boundary and the maintenance curve above is what follows.

The alternative I would propose instead is a mobile-specific representation negotiated by media type, served by the same controller and the same service, with its own mapper. That gives the mobile team the payload they want, costs one class, and creates no version to retire — and if their needs diverge further later, it is already the seam a version would have needed.

The organisational read, which matters as much as the technical one: requests for a new version are often really requests for autonomy — a team that does not want to coordinate with the web team's release. That is a legitimate problem and a version is an expensive way to solve it. Sparse fieldsets and additive evolution give the same autonomy without the permanent branch, and it is worth naming that dynamic directly rather than litigating the API design.

🎯 Key Takeaways

  • You cannot refactor a caller you do not control. Mobile clients live 6–24 months; a finance team's script lives forever.
  • Safe changes give clients freedom; breaking changes take something away or demand something new. That single test classifies almost everything.
  • "Additive is safe" assumes tolerant readers. One added field 500'd a partner integration, because Jackson's FAIL_ON_UNKNOWN_PROPERTIES defaults to true.
  • Make your own clients tolerant — ignore unknown properties, give every enum a default unknown constant. Two settings, most of the incidents.
  • A new enum value is a breaking change, and it fails the whole response rather than one field.
  • Changing a default sort or page size breaks clients without changing the schema — the kind of break no diff tool sees.
  • The controller is the cheap part of a version. The cost is 67 version conditionals in the service layer and a bug fixed in three versions out of four.
  • Two versions maximum, one internal model, versioning confined to the edge mapper.
  • Deprecate with Deprecation and Sunset headers, retire with 410 Gone — never a silent 404, which reads as the client's own bug.
  • Brownouts find the consumers email did not reach, while you are watching.
  • An unbounded list endpoint is an availability bug, reachable by anyone who can call it. Enforce a server-side ceiling.
  • Offset pagination duplicates and skips rows when data changes — 47 duplicates and 51 missed rows in one export — and costs 4.2 s at OFFSET 500000.
  • Keyset pagination needs a unique tie-breaker: sort and compare (created_at, id), or rows sharing a timestamp vanish.
  • COUNT(*) is often the most expensive part of a page — 2.9 s against a 4 ms page. Use Slice unless a human reads the total.
  • Allow-list sortable fields, and index every one you allow.
  • Lost updates are silent — 61 support edits overwritten in a month, both writes returning 200. Expose @Version as an ETag and require If-Match.
  • If-Match and Idempotency-Key solve different problems: concurrent writers versus a retried request.
  • Generated OpenAPI documents the break. A committed baseline plus a diff gate is what makes it a contract.
  • Consumer contract tests answer "did anyone care?" — but only for consumers who publish contracts, never for the public internet.
  • "Nobody uses that field" is a hypothesis. Per-consumer identity and response telemetry are cheap early and impossible to retrofit under deadline.
