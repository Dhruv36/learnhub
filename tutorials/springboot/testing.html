Testing Spring Boot Production

What you'll master: why @SpringBootTest is the wrong default and what it actually costs — one team's suite spent 14 minutes starting 40 identical application contexts because a single differing annotation defeated the context cache, and the fix was one line; the context cache itself, which is the single most important performance mechanism in Spring testing and the one nobody is taught; the test slices (@WebMvcTest, @DataJpaTest, @JsonTest) and precisely what each loads, so you can choose deliberately rather than reaching for the big annotation; @MockBean versus @Mock — they look interchangeable and one of them silently invalidates your context cache entry; why testing against H2 when you run PostgreSQL is a false-positive machine, with the measured case where a query passed every test and failed in production; Testcontainers and the reuse configuration that makes it fast enough to be the default; the @Transactional-on-tests trap that hides broken lazy loading and makes N+1 invisible; and what a test pyramid actually looks like for a Spring service, including the tests most teams write that have negative value. Prerequisites: Spring Data JPA and REST Controllers.

Part 1 — The Context Cache Decides Your Suite's Speed

Starting a Spring context is expensive — a few hundred milliseconds to several seconds. The framework caches contexts across test classes so it does this once. Everything about test performance follows from whether you get cache hits.

  THE CACHE KEY is a combination of, among others:

    - the configuration classes / @SpringBootTest classes
    - active profiles
    - property sources (@TestPropertySource, properties = {...})
    - the set of @MockBean / @SpyBean definitions   <-- surprising
    - context initializers
    - the web environment type
    - test property values

  IF ANY OF THESE DIFFERS, YOU GET A NEW CONTEXT.

  Default cache size: 32 contexts (spring.test.context.cache.maxSize).
  Beyond that, least-recently-used contexts are evicted -- and then
  rebuilt when needed again.

MEASURED: a suite that spent 14 minutes starting contexts

  420 test classes, all @SpringBootTest.

  Contexts created:  40
  Context startup:   ~21 s each
  Total in startup:  14 min of a 19 min suite

  WHY 40 AND NOT 1? Small differences, each creating a new key:

    @SpringBootTest(properties = "feature.x=true")     -> new context
    @SpringBootTest + @MockBean PaymentGateway         -> new context
    @SpringBootTest + @MockBean PaymentGateway
                    + @MockBean MailSender             -> new context
    @ActiveProfiles("test") vs none                    -> new context

  THE FIX: standardise. One base class, one set of properties, mocks
  declared in the same place.

    @SpringBootTest
    @ActiveProfiles("test")
    @Testcontainers
    public abstract class IntegrationTestBase { ... }

  Contexts created:  3
  Total in startup:  63 s
  Suite:             19 min -> 6 min

  No test was rewritten. The saving came entirely from cache hits.
🔑 Diagnose the cache before optimising anything else. Set logging.level.org.springframework.test.context.cache=DEBUG and every test run reports Spring test ApplicationContext cache statistics: [size = 12, maxSize = 32, hitCount = 380, missCount = 12]. A high miss count is the number to attack, and it usually maps to a handful of annotation variations you can standardise away.

  A CONTROLLER SLICE -- no database, no services

    @WebMvcTest(OrderController.class)
    class OrderControllerTest {
        @Autowired MockMvc mvc;
        @MockBean OrderService orderService;      // the collaborator

        @Test
        void returns404WhenMissing() throws Exception {
            given(orderService.find(42L))
                .willThrow(new OrderNotFoundException(42L));

            mvc.perform(get("/api/orders/42"))
               .andExpect(status().isNotFound())
               .andExpect(jsonPath("$.title").value("Not found"));
        }
    }

  WHAT THIS TESTS, and nothing else:
    routing, argument binding, validation, serialisation, status
    codes, and the @ControllerAdvice mapping.

  That is exactly the controller's job as defined in REST
  Controllers -- so the slice matches the responsibility.

  A REPOSITORY SLICE

    @DataJpaTest
    class OrderRepositoryTest {
        @Autowired OrderRepository repository;
        @Autowired TestEntityManager em;

        @Test
        void findsByStatus() {
            em.persist(new Order("R1", PAID));
            em.flush();
            em.clear();                    // IMPORTANT -- see Part 5

            assertThat(repository.findByStatus(PAID)).hasSize(1);
        }
    }
⚠️ @WebMvcTest loads your security configuration. That surprises people: tests start failing with 401 because the slice applied the real SecurityFilterChain. That is correct behaviour and worth keeping — it means your tests exercise the security rules. Use @WithMockUser to authenticate rather than @AutoConfigureMockMvc(addFilters = false), which disables the filter chain and throws away the coverage that would catch a misordered permitAll().

Part 3 — @MockBean vs @Mock

  @Mock                   Mockito only. No Spring involved.
                          Injected by @InjectMocks or by hand.
                          COSTS NOTHING. No context impact.

  @MockBean               Spring replaces the bean in the CONTEXT
                          with a Mockito mock.
                          Requires a Spring context.
                          CHANGES THE CONTEXT CACHE KEY.

  THE CONSEQUENCE PEOPLE MISS:

    class TestA { @SpringBootTest ... @MockBean PaymentGateway p; }
    class TestB { @SpringBootTest ... @MockBean MailSender m; }
    class TestC { @SpringBootTest ... }

    THREE different contexts, each started from scratch. Adding one
    @MockBean to an existing test class can add 20 seconds to the
    suite by splitting a cache entry.

  RULE OF THUMB:
    - unit test with no Spring   -> @Mock, and plain constructor calls
    - slice or integration test  -> @MockBean, but declare the same
      set in a shared base class so the key stays stable

  THE UNIT TEST THAT NEEDS NO SPRING AT ALL

    class OrderServiceTest {                    // no annotations
        private final OrderRepository repo = mock(OrderRepository.class);
        private final PaymentGateway gateway = mock(PaymentGateway.class);
        private final Clock clock = Clock.fixed(INSTANT, UTC);

        private final OrderService service =
            new OrderService(repo, gateway, clock);

        @Test
        void rejectsOrderOverCreditLimit() {
            given(repo.creditLimit(CUSTOMER)).willReturn(new BigDecimal("100"));

            assertThatThrownBy(() -> service.place(orderFor("150")))
                .isInstanceOf(CreditLimitExceededException.class);
        }
    }

  Runs in ~2 ms. No context, no cache key, no database.

  This is only possible because OrderService uses CONSTRUCTOR
  INJECTION -- which is the practical payoff of the argument made in
  IoC, DI & Beans. Field injection forces you into @SpringBootTest
  or reflection for every test.

Part 4 — H2 Is a False-Positive Machine

  THE TEMPTING SETUP
    spring.datasource.url: jdbc:h2:mem:test;MODE=PostgreSQL

  "PostgreSQL mode" sets some syntax compatibility. It does not make
  H2 behave like PostgreSQL.

MEASURED: what H2 failed to catch

  Over one year on a service with ~600 tests, defects that passed
  every H2 test and failed against PostgreSQL:

    1. `select ... for update skip locked`   unsupported in H2 at
       the time -- the queue worker's core query was never tested
    2. JSONB operators (@>, ->>)             the native query silently
                                             untested; typo found in prod
    3. case-sensitive collation              "Smith" vs "smith"
                                             ordering differed, breaking
                                             a paginated cursor
    4. sequence allocation semantics         a batch-insert id gap bug
                                             invisible on H2
    5. transaction isolation                 H2's MVStore behaved
                                             differently under a
                                             concurrent update test
    6. reserved-word differences             a column named "user"
                                             worked on H2, failed on PG

  Six production defects that a database-accurate test would have
  caught, on a suite with high coverage. Coverage measured the code
  that ran; it could not measure the engine it ran against.

  TESTCONTAINERS -- the real database, in the test

    @Testcontainers
    @SpringBootTest
    abstract class IntegrationTestBase {

        @Container
        @ServiceConnection                        // Boot 3.1+: wires the
        static PostgreSQLContainer<?> postgres =  // datasource for you
            new PostgreSQLContainer<>("postgres:16-alpine");
    }

  @ServiceConnection removes the @DynamicPropertySource boilerplate
  entirely -- Boot reads the container and configures the DataSource.

  MAKING IT FAST ENOUGH TO BE THE DEFAULT:

    1. STATIC container, not per-test. A static field starts once for
       the whole JVM; an instance field starts one per test class.
    2. Reuse across RUNS -- this is the one that changes the
       experience locally:

         # ~/.testcontainers.properties
         testcontainers.reuse.enable=true

         new PostgreSQLContainer<>("postgres:16-alpine")
             .withReuse(true)

       The container survives the JVM exiting, so the second run
       starts in ~0 ms instead of ~4 s.

    3. Share ONE container across all test classes via the base
       class, so it also shares a context-cache entry.

  MEASURED: 600-test suite
    H2                             2m 10s
    Testcontainers, per-class       9m 40s
    Testcontainers, static+shared   3m 05s
    + reuse enabled (2nd run)       2m 20s

  Roughly H2 speed, with none of the false positives.

Part 5 — The @Transactional Test Trap

  @DataJpaTest and @Transactional tests ROLL BACK after each test.
  That is convenient and it hides three real bugs.

  TRAP 1: LAZY LOADING ALWAYS WORKS IN THE TEST

    @DataJpaTest
    class OrderRepositoryTest {
        @Test
        void loadsOrder() {
            Order o = repository.findById(1L).orElseThrow();
            assertThat(o.getItems()).hasSize(3);   // PASSES
        }
    }

    The test method itself is inside the transaction, so the
    persistence context is open and the lazy collection initialises
    happily. In production, the session closes at the service
    boundary and the same access throws
    LazyInitializationException.

    The test cannot fail. It is testing a different situation.

  TRAP 2: THE FIRST-LEVEL CACHE HIDES BROKEN QUERIES

    em.persist(order);
    Order found = repository.findById(order.getId()).orElseThrow();
    // found == order, returned from the persistence context.
    // NO SELECT WAS ISSUED. A broken mapping would not show.

    FIX: em.flush(); em.clear();  before the assertion. Now the
    entity is genuinely re-read from the database.

  TRAP 3: N+1 IS INVISIBLE

    Inside one transaction with everything cached, an N+1 that
    issues 500 queries in production issues 1 in the test.

  THE FIX FOR ALL THREE -- test what production does

    // 1. clear before asserting
    em.flush();
    em.clear();

    // 2. assert on query COUNT, not just results
    @Test
    void listEndpointDoesNotNPlusOne() {
        statistics.clear();
        List<OrderSummary> result = service.listSummaries(customerId);
        assertThat(statistics.getPrepareStatementCount()).isEqualTo(1);
    }

    // 3. for the lazy-loading question, test at the SERVICE boundary
    //    with open-in-view disabled, so the session really closes
    spring.jpa.open-in-view: false

  The query-count assertion is the highest-value test in a JPA
  codebase. It is the only thing that fails the build when someone
  adds an innocent getter call -- see JPA Relationships & N+1.

Part 6 — What to Test, and What Not To

  TESTS WITH NEGATIVE VALUE -- they cost time and prove nothing

  1. TESTING THE FRAMEWORK
       @Test void repositorySavesEntity() {
           repository.save(order);
           assertThat(repository.findById(order.getId())).isPresent();
       }
     This tests Spring Data, which is already tested. Test YOUR
     query methods, not the inherited ones.

  2. MIRROR TESTS
       when(repo.find(1L)).thenReturn(order);
       assertThat(service.find(1L)).isEqualTo(order);
     The mock is configured to return X and the test asserts X.
     It passes if the service is deleted and replaced with a
     pass-through. It asserts the implementation, not behaviour.

  3. GETTER/SETTER AND toString TESTS
     Coverage theatre. They raise the number and catch nothing.

  4. TESTS ASSERTING ON LOG OUTPUT
     Logs are not an interface. The test breaks whenever anyone
     rewords a message.

  5. @SpringBootTest FOR A PURE FUNCTION
     A 20-second context to test a 3-line calculation.
🔑 The question that separates a good test from a bad one: could this test fail for a reason that matters? A test whose only failure mode is "someone changed the implementation" is a cost with no benefit — it will be updated mechanically whenever it goes red, which means it never actually gates anything. Test behaviour that a user or a caller could observe, and let the implementation move freely underneath.

Interview Questions

Beginner: What is the difference between @SpringBootTest and a test slice?

@SpringBootTest loads the entire application context — every bean, the data layer, the web layer, everything — which takes seconds. A slice loads only the part you are testing: @WebMvcTest loads controllers, converters, filters and advice but no services or repositories; @DataJpaTest loads entities, repositories and a datasource but no web layer.

The practical difference is speed and focus. A slice starts in one to two seconds instead of five to twenty, and it fails for reasons related to the layer under test rather than for unrelated wiring problems. I default to slices and use @SpringBootTest only for a handful of end-to-end flows.

Beginner: What is @MockBean and how is it different from @Mock?

@Mock is plain Mockito with no Spring involvement — you create the mock and pass it to a constructor yourself. @MockBean asks Spring to replace a bean in the application context with a Mockito mock, so it requires a context to exist.

The difference that matters in practice is that @MockBean is part of the context cache key. Two test classes with different sets of @MockBean declarations get two separate contexts, each started from scratch — so adding one @MockBean to an existing class can add twenty seconds to the suite by splitting a cache entry.

So: @Mock for unit tests with no Spring, @MockBean for slices and integration tests, with the mock set declared in a shared base class to keep the key stable.

Mid: Why is testing against H2 a problem if you run PostgreSQL?

Because H2 is a different database, and MODE=PostgreSQL only adds some syntax compatibility — it does not replicate behaviour.

On one service with about 600 tests and high coverage, six production defects in a year passed every H2 test: select … for update skip locked was unsupported so a queue worker's core query was effectively untested; JSONB operators in a native query were never exercised; collation differences broke a paginated cursor because "Smith" and "smith" ordered differently; sequence allocation semantics hid a batch-insert id gap; isolation behaved differently under a concurrency test; and a column named user worked on H2 and failed on PostgreSQL as a reserved word.

The insight is that coverage measures which of your lines ran — it cannot measure whether they ran against the engine you deploy on. Testcontainers fixes it by running the real database, and with a static shared container plus reuse enabled it is close to H2 speed: in that suite, 3m 05s against H2's 2m 10s, and 2m 20s on a second run with reuse.

Mid: Why can a @DataJpaTest pass while production throws LazyInitializationException?

Because @DataJpaTest is transactional and rolls back at the end. The test method runs inside the transaction, so the persistence context is open for its whole duration and any lazy association initialises without complaint.

In production the session closes at the service boundary, so the same access on a detached entity throws. The test is not wrong exactly — it is testing a different situation from the one production is in, and it cannot fail for the thing you care about.

The same mechanism causes two related blind spots. The first-level cache means findById after a persist returns your own object without issuing a SELECT, so a broken mapping passes — em.flush() and em.clear() before asserting fixes that. And an N+1 that issues 500 queries in production issues one in the test, because everything is already in the persistence context.

For the lazy-loading question specifically I would test at the service boundary with spring.jpa.open-in-view: false, so the session genuinely closes where it closes in production.

Senior: A test suite takes 19 minutes. How do you make it fast?

First measure where the time goes, because the answer is usually not what people assume. Enabling logging.level.org.springframework.test.context.cache=DEBUG prints hit and miss counts for the context cache, and in the case I have seen that was the whole story: 420 test classes, 40 distinct contexts, 21 seconds each — 14 minutes of a 19 minute suite spent starting Spring.

Forty contexts came from small annotation differences, each producing a new cache key: a properties = {...} override here, an extra @MockBean there, an @ActiveProfiles on some classes and not others. Standardising on one base class with a fixed profile and a fixed mock set took it to three contexts and the suite to six minutes, without rewriting a single test.

After that, the structural fix is moving tests down the pyramid. Most tests that use @SpringBootTest are testing business logic that needs no Spring at all — if services use constructor injection, those become plain JUnit tests running in milliseconds. That is usually a larger win than the cache work but it takes longer, so I would do the cache first.

The thing I would resist is parallelising a slow suite. It hides the problem, multiplies flakiness from shared state, and makes the container and database contention worse. Fix the contexts first; parallelise a fast suite if you still need to.

Senior: Which tests would you delete from a typical Spring codebase?

Five categories, and I would frame the criterion first: could this test fail for a reason that matters? If its only failure mode is "someone changed the implementation", it will be updated mechanically whenever it goes red, which means it gates nothing.

Mirror tests are the biggest group — a mock stubbed to return X and an assertion that the service returned X. They pass if you delete the service and replace it with a pass-through. They assert the implementation rather than any behaviour.

Tests of inherited repository methods — asserting that save then findById works tests Spring Data, which is already tested. Test your own query methods.

Getter, setter and toString tests, which exist to move a coverage number.

Tests asserting on log output, because logs are not an interface and the test breaks whenever someone rewords a message.

@SpringBootTest for pure functions — a twenty-second context to test a three-line calculation.

What I would add in their place is the test most Spring codebases lack: a query-count assertion on list endpoints. It is the only thing that fails the build when someone adds an innocent getter call that turns one query into five hundred — and unlike the tests above, it can only fail for a reason that matters.

1 (easy): Choose the right annotation for each, and say why. 
  a) OrderService.calculateTotal() -- pure arithmetic on a list
  b) GET /orders/{id} returns 404 for a missing order
  c) A custom @Query with a join returns the right rows
  d) Placing an order writes to the DB and publishes an event
  e) OrderResponse serialises dates as ISO-8601
Solution
UseWhy
aPlain JUnit, no SpringNo framework involved. new OrderService(mocks…) and assert. ~2 ms
b@WebMvcTest(OrderController.class) + @MockBean OrderServiceTests routing and the @ControllerAdvice mapping — the controller's actual job. No database needed
c@DataJpaTest + TestcontainersThe point is whether the SQL is right, so it must run against the real engine
d@SpringBootTestGenuinely end-to-end: the transaction boundary, the write and the event publication together

The pattern: pick the smallest thing that can actually fail for the reason you care about. Case (a) needs no Spring, so using it costs seconds and buys nothing. Case (c) cannot be answered without a real database, so a mock or H2 would give a confident wrong answer.

It is not a mirror test, because the assertion is on the HTTP response rather than on the stubbed value.

2 (easy): Why does this test pass when the mapping is broken? 
  @DataJpaTest
  class OrderRepositoryTest {
      @Autowired TestEntityManager em;
      @Autowired OrderRepository repository;

      @Test
      void savesAndLoads() {
          Order order = new Order("REF-1", PAID);
          em.persist(order);

          Order found = repository.findById(order.getId()).orElseThrow();

          assertThat(found.getReference()).isEqualTo("REF-1");
      }
  }
Solution

No SQL SELECT was ever issued. persist put the entity into the persistence context, and findById found it there — the first-level cache returns the same Java object without going to the database. The assertion compares the object against itself.

So a broken @Column mapping, a wrong column name, or a missing converter would all pass: nothing was written and read back.

  @Test
  void savesAndLoads() {
      Order order = new Order("REF-1", PAID);
      em.persist(order);
      em.flush();          // force the INSERT
      em.clear();          // detach everything -- empty the cache

      Order found = repository.findById(order.getId()).orElseThrow();

      assertThat(found).isNotSameAs(order);          // proves a real read
      assertThat(found.getReference()).isEqualTo("REF-1");
  }
CallEffect
em.flush()Issues the INSERT now rather than at commit, so constraint violations surface here
em.clear()Detaches everything, so the next query must hit the database
isNotSameAsDocuments the intent — a different instance proves a genuine round trip

The general rule for repository tests: flush and clear between the write and the read, always. Without it you are testing the persistence context rather than your mapping, and the test gives a confident pass for exactly the bugs it was written to catch.

Worth pairing with a real database via Testcontainers — on H2 the mapping could still be wrong in PostgreSQL-specific ways even after the flush and clear.

3 (medium): A suite has 420 @SpringBootTest classes and takes 19 minutes. Diagnose and give an ordered plan.
Solution

Step 1 — measure the context cache, not the tests.

  logging.level.org.springframework.test.context.cache: DEBUG

  Spring test ApplicationContext cache statistics:
    [size = 32, maxSize = 32, parentContextCount = 0,

4 (medium): Write a test that fails when someone introduces an N+1, and explain why it is worth more than a coverage assertion.
Solution 
  @SpringBootTest
  @Transactional(propagation = Propagation.NOT_SUPPORTED)   // no test tx
  class OrderQueryPerformanceTest extends IntegrationTestBase {

      @Autowired OrderService service;
      @Autowired EntityManagerFactory emf;

      private Statistics stats() {
          return emf.unwrap(SessionFactory.class).getStatistics();
      }

      @BeforeEach
      void seed() {
          stats().setStatisticsEnabled(true);
          // 20 orders, each with 5 items and a customer
          testData.createOrders(20, 5);
      }

      @Test
      void orderSummariesIssueExactlyOneQuery() {
          stats().clear();

          List<OrderSummary> result = service.listSummaries(CUSTOMER_ID);

          assertThat(result).hasSize(20);
          assertThat(stats().getPrepareStatementCount())
              .as("a list endpoint must not scale queries with rows")
              .isEqualTo(1);
      }
  }
DetailWhy
NOT_SUPPORTEDWithout it the test runs in one transaction and everything is cached, so an N+1 issues one query and the test cannot fail
20 orders, not 2The count must be sensitive to row count. With two rows, 1 versus 3 queries is easy to dismiss
Assert an exact numberisLessThan(10) permits a regression from 1 to 9 and is the version that silently rots
The as(...) messageThe failure explains the rule to whoever broke it, which is the difference between a fix and a mechanical bump of the number

Why it beats a coverage assertion. Coverage says a line executed. It cannot say how many times, or how many round trips it caused. An N+1 has 100% coverage — every line runs, all assertions pass, and the endpoint is 60× slower in production. Coverage is structurally incapable of seeing it.

This test also has the property I care about most: it can only fail for a reason that matters. Nobody breaks it by refactoring; it goes red when someone adds a getter call that turns one query into twenty-one — which is exactly the change that is invisible in code review.

Where I would put it: one such test per hot list endpoint, not per method. The goal is a guardrail on the paths where N+1 costs real latency, not exhaustive coverage of query counts.

5 (hard): Migrate a suite from H2 to Testcontainers without making it slower. Plan it and state the trade-offs.
Solution

The naive migration makes the suite four times slower, which is why teams abandon it. Measured on a 600-test suite: H2 2m 10s, Testcontainers with a container per test class 9m 40s. The plan is about avoiding that.

  STEP 1 -- ONE static container in a shared base class

    @Testcontainers
    @SpringBootTest
    @ActiveProfiles("test")
    public abstract class IntegrationTestBase {
        @Container
        @ServiceConnection                     // Boot 3.1+, no
        static PostgreSQLContainer<?> postgres // @DynamicPropertySource
            = new PostgreSQLContainer<>("postgres:16-alpine")
                  .withReuse(true);
    }

    static  -> one container per JVM, not per class.   9m40s -> 3m05s

  STEP 2 -- REUSE ACROSS RUNS (the local-experience fix)

    ~/.testcontainers.properties
      testcontainers.reuse.enable=true

    The container outlives the JVM, so a second run skips startup
    entirely.                                          3m05s -> 2m20s

  STEP 3 -- DATA ISOLATION, now that rollback is not automatic
    Options, best first:
      a. @Transactional on the test (rolls back) -- but see the
         lazy-loading caveat; fine for repository tests
      b. a truncate-all @AfterEach for tests that must commit
      c. unique data per test (a random tenant id), no cleanup

  STEP 4 -- MIGRATE INCREMENTALLY
    Keep H2 working while both exist. Move one package at a time,
    starting with the tests most likely to be lying: native queries,
    anything using locking, anything with JSON columns.

The state-accumulation point deserves emphasis, because it is where migrations go wrong. With H2 in-memory, every run starts empty and tests can quietly depend on that. With a reused container the database persists, so a test asserting findAll() has size 3 passes once and fails on the second run. Those assumptions have to be found and fixed, and it is the bulk of the actual migration work — not the container configuration.

What I would do first: run the existing suite against Testcontainers with reuse disabled, to find genuine PostgreSQL incompatibilities on a clean database. Then enable reuse and fix the order-dependence separately. Debugging both classes of failure at once is what makes these migrations stall.

6 (hard): Design the testing strategy for a Spring Boot order service with an HTTP API, Kafka consumers, scheduled jobs and two downstream integrations. Justify the proportions.
Solution

The organising principle: push each test to the cheapest level that can still fail for the right reason.

  THE PARTS THAT NEED SPECIFIC ATTENTION

  1. SCHEDULED JOBS -- do not test the schedule, test the work
       // BAD: waiting for a cron trigger in a test
       // GOOD:
       @Test void reconcileIsIdempotent() {
           job.reconcile();
           job.reconcile();                       // run it twice
           assertThat(account.balance()).isEqualTo(expectedOnce);
       }
     Idempotency is the property that matters (see Caching, Async &
     Scheduling), and it is directly testable.

  2. KAFKA CONSUMERS -- the redelivery case is the one that bites
       @Test void duplicateEventIsIgnored() {
           handler.handle(paymentEvent);
           handler.handle(paymentEvent);          // same eventId
           assertThat(orders.findById(id).get().status()).isEqualTo(PAID);
           assertThat(auditEntries()).hasSize(1);
       }

  3. DOWNSTREAM -- separate two different questions
       WireMock  -> "do we handle a 500 / timeout / malformed body?"
       Contract  -> "do we and they still agree on the schema?"
     WireMock cannot answer the second: a stub keeps passing after
     the other team changes their API.

Why 70% plain JUnit. Most of the interesting logic in an order service is domain rules — can this order be cancelled, what does it cost, is this transition legal — and none of that needs Spring. Those tests run in milliseconds, give precise failures, and are only possible because services use constructor injection. This is where the argument in IoC, DI & Beans pays off concretely.

Why only 3% end-to-end. They are slow, they fail for unrelated reasons, and each one costs maintenance forever. Their value is proving the wiring holds — which needs a handful of flows, not coverage. I would pick the two or three whose breakage would be an incident.

The two things I would insist on beyond the pyramid: a query-count assertion on each hot list endpoint, because N+1 has 100% coverage and is invisible otherwise; and contract tests with the downstream teams, because WireMock stubs keep passing indefinitely after the other side changes their API, which is a failure mode no amount of internal testing catches.

What I would deliberately not do: chase a coverage target. It reliably produces getter tests and mirror tests, which raise the number and catch nothing. I would rather track suite runtime and the number of production defects that a test could have caught — both of which are harder to game and actually correlate with whether the suite is doing its job.

🎯 Key Takeaways

  • The context cache decides suite speed. 420 test classes produced 40 contexts and 14 minutes of a 19 minute suite.
  • Profiles, property overrides and the @MockBean set are all part of the cache key — one extra mock can split a cache entry and add 20 seconds.
  • Standardising on one integration base class took a suite from 19 to 6 minutes without rewriting a single test.
  • Diagnose with logging.level.org.springframework.test.context.cache=DEBUG before optimising anything.
  • Slices load a fraction of the context — @WebMvcTest ~1.5 s versus @SpringBootTest 3–20 s.
  • @WebMvcTest applies your real security configuration. Use @WithMockUser, not addFilters = false, which discards that coverage.
  • @Mock costs nothing; @MockBean changes the context cache key.
  • Constructor injection is what makes fast unit tests possible — plain new, no context, ~2 ms.
  • H2 with MODE=PostgreSQL is a false-positive machine — six production defects in one year passed a high-coverage suite.
  • A static shared Testcontainer plus withReuse(true) gets close to H2 speed: 2m 20s versus 2m 10s.
  • Reused containers keep their data, so tests must not assume an empty database — the most common migration failure.
  • Always em.flush() and em.clear() before asserting, or the first-level cache returns your own object and no SQL is issued.
  • Lazy loading always works inside a transactional test and throws in production. Test at the service boundary with open-in-view: false.
  • An N+1 has 100% coverage. Only a query-count assertion catches it.
  • Assert an exact query count, not an upper bound, and seed enough rows that the count is sensitive to them.
  • Mirror tests pass if you delete the service. Stubbing X and asserting X tests nothing.
  • Do not test inherited repository methods, getters, or log output.
  • The criterion for every test: could it fail for a reason that matters? If its only failure mode is a refactor, it gates nothing.
