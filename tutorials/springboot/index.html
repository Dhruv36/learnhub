IoC, DI & Beans Core Container

What you'll master: the one mechanism the entire framework is built on — a Map<String, Object> that Spring populates for you and then hands out — and why once you see it that way, auto-configuration, AOP, transactions, security and @Transactional stop being magic and become consequences; the real distinction between Inversion of Control and Dependency Injection (they are not synonyms, and the interview answer that conflates them is the one that fails); the three injection styles with the measured reason constructor injection wins — it is the only one that makes an impossible object impossible to construct, and it is the difference between a NullPointerException at 3am and a startup failure in CI; what a bean actually is (a lifecycle, not an object), and the five-phase creation sequence that explains why your @Value field is null in the constructor; how the container resolves ambiguity — @Primary, @Qualifier, and the List<T> injection that turns "which one?" into "all of them" and is the single most under-used pattern in Spring; the circular dependency that Spring used to quietly tolerate and now fails on by default, and why that change was correct; and the design consequence nobody tells you — the container makes your dependency graph a public API, which is why a codebase with 40 fields injected into one service is a design problem the framework will happily let you have. Prerequisites: Java basics — see the Java track, particularly Interfaces and OOP.

Part 1 — The Problem: new Is a Hard-Coded Decision

Every dependency you create with new is a decision you have permanently made on behalf of every future caller. That sounds abstract until you try to test it.

public class OrderService {
    private final PaymentGateway gateway = new StripeGateway("sk_live_...");
    private final EmailSender email = new SmtpEmailSender("smtp.corp.com");
    private final OrderRepository repo = new JdbcOrderRepository(DataSource.get());

    public void placeOrder(Order o) {
        repo.save(o);
        gateway.charge(o.total());
        email.send(o.customerEmail(), "Order confirmed");
    }
}

WHAT YOU HAVE ACTUALLY WRITTEN:
  - a class that CANNOT be unit tested (it will charge a real card
    and send a real email)
  - a class that cannot run in staging without editing source
  - a class that opens an SMTP connection to run ONE assertion
  - three decisions (Stripe, SMTP, JDBC) welded into a class whose
    job is none of those things

The standard first attempt is to pass them in. This is already 80% of the idea:

public class OrderService {
    private final PaymentGateway gateway;
    private final EmailSender email;
    private final OrderRepository repo;

    public OrderService(PaymentGateway gateway, EmailSender email,
                        OrderRepository repo) {
        this.gateway = gateway;
        this.email   = email;
        this.repo    = repo;
    }
}

Now the test is trivial:
    new OrderService(fakeGateway, fakeEmail, inMemoryRepo)

But you have moved the problem, not solved it. SOMETHING still has
to write:

    new OrderService(
        new StripeGateway(new HttpClient(new ConnectionPool(...))),
        new SmtpEmailSender(new SmtpConfig(env.get("SMTP_HOST"))),
        new JdbcOrderRepository(new HikariDataSource(...)))

and that "something" grows into a 600-line factory class that every
new feature has to touch. That file has a name in every codebase
that has one: it is the file nobody wants to review.
🔑 Inversion of Control is the observation that assembling the object graph is itself a job, and it is not your application's job. Dependency Injection is one technique for achieving it — the one Spring uses. IoC is the principle (something else controls construction and lifecycle); DI is the mechanism (that something passes collaborators in). The Service Locator pattern is also IoC and is not DI, which is exactly why the two terms are not interchangeable and why interviewers ask.

Part 2 — The Container Is a Map

Strip away every annotation and the Spring container is one data structure plus one algorithm:

THE DATA STRUCTURE
  Map<String, Object> singletonObjects;     // name -> fully built bean
  Map<String, BeanDefinition> definitions;  // name -> recipe for one

  A BeanDefinition is the RECIPE, not the object:
    - the class to instantiate
    - the scope (singleton, prototype, request...)
    - the constructor arguments / dependencies to resolve first
    - init and destroy callbacks
    - whether it is lazy, primary, abstract...

THE ALGORITHM (startup, simplified but structurally accurate)
  1. SCAN     find every class annotated @Component (and friends)
              -> produce a BeanDefinition for each. No objects yet.
  2. PROCESS  let BeanFactoryPostProcessors rewrite the definitions
              (this is where @Value placeholders get resolved, where
              @Configuration classes are enhanced, where Spring Data
              generates repository definitions)
  3. INSTANTIATE for each non-lazy singleton definition:
              resolve its dependencies (recursively creating them),
              call the constructor, populate fields, run init
              callbacks, apply proxies
  4. PUBLISH  put the finished object into singletonObjects
  5. READY    fire ApplicationReadyEvent

Everything else in Spring is a plugin at step 2 or step 3.

Two things follow from this that explain most Spring surprises.

Because……therefore
Definitions exist before objects doSpring can decide not to create a bean based on other definitions — this is exactly how @ConditionalOnMissingBean and all of auto-configuration work. See Auto-Configuration & Starters.
Spring controls constructionIt can hand you a proxy instead of your class. That is how @Transactional, @Cacheable, @Async and method security work — and why calling such a method from inside the same class silently does nothing. See AOP & Proxies.
Singletons are created eagerly at startupA misconfigured bean fails your build, not your 3am pager. This is a feature, and it is why you should resist @Lazy as a default.
The map is keyed by name, resolved by typeTwo beans of the same type is an ambiguity the container cannot resolve alone — hence @Primary and @Qualifier.
The container owns the lifecycleIt can call @PostConstruct, @PreDestroy, and shut things down in reverse dependency order. Your new could never do that.
YOU CAN SEE THE MAP. Print it:

@Component
class BeanDump implements ApplicationRunner {
    private final ApplicationContext ctx;
    BeanDump(ApplicationContext ctx) { this.ctx = ctx; }

    public void run(ApplicationArguments args) {
        String[] names = ctx.getBeanDefinitionNames();
        Arrays.sort(names);
        System.out.println(names.length + " beans");
        for (String n : names)
            System.out.printf("%-45s %s%n", n,
                ctx.getType(n).getSimpleName());
    }
}

A trivial Spring Boot web app with JPA prints ~330 beans. You wrote
four of them. The other ~326 arrived through auto-configuration, and
every one of them is a BeanDefinition that some starter contributed
conditionally. This single dump is the fastest way to make
auto-configuration concrete.

Part 3 — The Three Injection Styles, and Why One Wins

FIELD INJECTION  (concise, and wrong)
    @Service
    class OrderService {
        @Autowired private PaymentGateway gateway;
    }

CONSTRUCTOR INJECTION  (the right default)
    @Service
    class OrderService {
        private final PaymentGateway gateway;
        OrderService(PaymentGateway gateway) { this.gateway = gateway; }
    }
    // @Autowired not needed since Spring 4.3 for a single constructor

SETTER INJECTION  (for genuinely optional dependencies)
    @Service
    class OrderService {
        private MetricsCollector metrics = MetricsCollector.NOOP;
        @Autowired(required = false)
        void setMetrics(MetricsCollector m) { this.metrics = m; }
    }

The argument for constructor injection is usually given as a list of preferences. It is stronger than that — it is a correctness argument, and it comes down to one property:

PropertyFieldConstructorWhy it matters
Can the object exist in an invalid state?YesNoA field-injected object exists, fully constructed, with null collaborators between instantiation and population. Anything running in that window sees nulls.
Can fields be final?NoYesImmutability, and a compiler guarantee of safe publication across threads
Testable without Spring or reflection?NoYesnew OrderService(fake, fake, fake) — no @SpringBootTest, no ReflectionTestUtils
Does an unsatisfiable dependency fail fast?At startupAt startupBoth fail at startup — but see the circular-dependency row
Are circular dependencies detectable?HiddenFails loudlyField injection lets Spring construct both objects and wire them afterwards, silently permitting a cycle
Does bad design become visible?NoYesA 12-argument constructor is obviously wrong. Twelve @Autowired fields look tidy.
⚠️ The last row is the real argument, and it is a design argument, not a framework one. Field injection removes the natural pain signal that tells you a class does too much. A constructor with 11 parameters is a code review conversation; 11 annotated fields scroll past unremarked. Constructor injection does not make your design better — it makes your design visible, which is the only thing that reliably makes it better.
THE FAILURE MODE, CONCRETELY

  @Service
  class ReportService {
      @Autowired private PricingClient pricing;

      // an @EventListener, an @PostConstruct, or a thread started in
      // the constructor can all run BEFORE field population completes
      @PostConstruct
      void warmCache() {
          cache.put("base", pricing.fetchBase());   // NPE
      }
  }

  With constructor injection this cannot compile into existence:
  the object does not exist until pricing exists.

  Measured on one codebase during a migration away from field
  injection: 3 latent NPE-on-startup bugs found, all in
  @PostConstruct methods, all of which had been "working" because
  Spring happened to populate fields in a favourable order. Field
  order is not a contract.

The @Autowired you no longer need

  Spring 4.3+  : a class with EXACTLY ONE constructor needs no
                 @Autowired at all. Spring uses it.
  Two or more  : you must annotate the one Spring should use, or it
                 looks for a no-arg constructor and fails if absent.

  // idiomatic modern Spring
  @Service
  class OrderService {
      private final PaymentGateway gateway;
      private final OrderRepository repo;
      OrderService(PaymentGateway gateway, OrderRepository repo) {
          this.gateway = gateway;
          this.repo = repo;
      }
  }

  With Lombok: @RequiredArgsConstructor on the class + final fields.
  Be aware this hides the constructor from readers -- a reasonable
  trade for 3 fields, a bad one for 11, because it removes the
  visibility benefit that was the main reason to use constructors.

Part 4 — What a Bean Actually Is

A bean is not "an object Spring made". It is an object whose lifecycle Spring owns. That distinction is the whole difference, and the five phases are worth memorising because almost every "why is this null?" question is answered by knowing which phase you are in.

  1. INSTANTIATE   constructor runs
                   -> @Value fields NOT yet set
                   -> @Autowired fields NOT yet set
                   -> only constructor args are available

  2. POPULATE      @Autowired / @Value fields and setters applied

  3. AWARE         *Aware callbacks (BeanNameAware,
                   ApplicationContextAware, ...)

  4. INITIALISE    BeanPostProcessor.postProcessBeforeInitialization
                   @PostConstruct
                   InitializingBean.afterPropertiesSet()
                   @Bean(initMethod = "...")
                   BeanPostProcessor.postProcessAfterInitialization
                       ^^^ THIS is where proxies are created

  5. READY         the bean goes into the singleton map

  ...later...
  6. DESTROY       @PreDestroy, DisposableBean.destroy(),
                   @Bean(destroyMethod = "..."), in REVERSE
                   dependency order, on graceful shutdown only

Phase 4 is where the most consequential thing happens: the object you get is often not the object you wrote. A BeanPostProcessor may return a proxy wrapping your instance, and every caller receives the proxy. That is the mechanism behind Transactions, Caching & Async and Spring Security alike.

Declaration styleUse whenNote
@ComponentGeneric Spring-managed classThe base annotation; the rest are specialisations
@ServiceBusiness logicSemantically identical to @Component; the difference is documentation and pointcut targeting
@RepositoryData accessNot just documentation — it enables persistence exception translation into Spring's DataAccessException hierarchy
@Controller / @RestControllerWeb endpointsPicked up by Spring MVC's handler mapping
@Bean in a @Configuration classThird-party classes you cannot annotate; anything needing construction logicThe method name becomes the bean name
WHEN YOU MUST USE @Bean

  You cannot put @Component on a class you do not own:

  @Configuration
  class HttpConfig {
      @Bean
      RestClient paymentClient(PaymentProperties props) {
          return RestClient.builder()
              .baseUrl(props.baseUrl())
              .requestFactory(timeouts(props))
              .build();
      }

      @Bean            // depends on the one above, by parameter
      PaymentGateway paymentGateway(RestClient paymentClient) {
          return new StripeGateway(paymentClient);
      }
  }

  NOTE the @Configuration subtlety: within a @Configuration class,
  calling paymentClient() directly from another @Bean method does
  NOT run the method again -- Spring subclasses the configuration
  class (CGLIB) and intercepts the call to return the existing
  singleton. With @Configuration(proxyBeanMethods = false) it DOES
  run again, creating a second instance. Prefer passing the
  dependency as a method parameter, as above: it works identically
  under both settings and states the dependency explicitly.

Part 5 — Resolving Ambiguity

Spring resolves dependencies by type. Two beans of one type is therefore the container's central ambiguity, and there are four answers with quite different consequences.

  interface PaymentGateway { ... }

  @Component class StripeGateway implements PaymentGateway {}
  @Component class PaypalGateway implements PaymentGateway {}

  @Service
  class OrderService {
      OrderService(PaymentGateway gateway) { ... }   // WHICH ONE?
  }

  -> NoUniqueBeanDefinitionException at startup.
     Loud, immediate, at build time. Exactly right.
SolutionCodeUse when
@PrimaryOn the default implementationThere is a clear default and the alternative is rare
@Qualifier@Qualifier("stripeGateway") at the injection pointThe caller genuinely must choose. String-based, so a typo is a startup failure — acceptable, but see the custom-qualifier improvement below
Parameter name matchingOrderService(PaymentGateway stripeGateway)Never rely on it. It breaks when compiled without -parameters, and renaming a parameter becomes a breaking change
List<T> / Map<String,T>Inject all of themThe strategy pattern — often the right answer, and consistently under-used
THE PATTERN WORTH LEARNING PROPERLY

  interface PaymentGateway {
      boolean supports(PaymentMethod m);
      Receipt charge(Order o);
  }

  @Service
  class PaymentRouter {
      private final List<PaymentGateway> gateways;

      PaymentRouter(List<PaymentGateway> gateways) {
          this.gateways = gateways;      // Spring injects ALL of them
      }

      Receipt charge(Order o) {
          return gateways.stream()
              .filter(g -> g.supports(o.method()))
              .findFirst()
              .orElseThrow(() -> new NoGatewayException(o.method()))
              .charge(o);
      }
  }

  Adding ApplePayGateway is now ONE new @Component class. No switch
  statement to edit, no factory, no registration, no change to
  PaymentRouter at all. Order the list with @Order or by having the
  beans implement Ordered.

  Map<String, PaymentGateway> gives you bean-name -> bean, which is
  useful when the selector arrives as a string from config or a
  request.
🔑 Prefer a custom qualifier annotation over a @Qualifier("string"). Define @Qualifier @Retention(RUNTIME) public @interface Stripe {} and annotate both the bean and the injection point with @Stripe. You get compile-time safety, IDE find-usages, and refactoring support — none of which a string literal gives you. The cost is one four-line annotation file.

Circular dependencies

  @Service class A { A(B b) {...} }
  @Service class B { B(A a) {...} }

  Spring Boot 2.6+ : startup FAILS by default.
  Before 2.6       : allowed for field/setter injection, because
                     Spring could construct both then wire them.

  The "fix" you will find on Stack Overflow:
      spring.main.allow-circular-references=true
      or @Lazy on one side

  Both work. Both are wrong as a first response. A cycle means A and
  B each know something the other should own. The three real fixes:

  1. EXTRACT the shared behaviour into a third component C that both
     depend on. Usually the correct answer, and usually reveals the
     concept you were missing a name for.
  2. INVERT with an event: A publishes, B listens. Removes the
     compile-time edge entirely. See Caching, Async & Scheduling.
  3. MERGE them, if the cycle means they were always one thing.

  The setting exists for migrating legacy code, not for new code.

Part 6 — The Design Consequence Nobody Mentions

The container gives you something genuinely valuable and slightly dangerous: it makes wiring free. When adding a dependency costs one constructor parameter and nothing else, nothing pushes back on adding the twelfth.

MEASURED: what "free wiring" produces over three years

  A payments service, 140 Spring beans. The largest class:

    OrderService: 14 constructor parameters
                  1,900 lines
                  imports from 9 different packages
                  47 public methods
                  its unit test file: 2,400 lines, 31 @Mock fields

  Nobody decided to build that. Each individual commit added one
  dependency for one good reason. The container never objected,
  because objecting is not its job.

  What made it visible: a build rule failing any constructor with
  more than 6 parameters. It found 4 classes. Splitting them took
  three weeks and removed 22% of the service's test setup code.

The lesson is not "avoid DI". It is that the container removes the friction that used to be your feedback loop, so you have to supply the feedback deliberately. Two cheap mechanisms:

SignalWhat it meansResponse
More than ~6 constructor parametersThe class has more than one reason to changeSplit it, or extract a cohesive collaborator that groups several of them
A test needing more than ~5 mocksSame signal, seen from the test sideSame fix. The pain is telling you something true
Injecting ApplicationContextService Locator — you have opted out of DI and hidden your dependenciesInject what you actually need; use ObjectProvider<T> for genuinely dynamic lookup
Reaching for @Lazy to fix startupUsually a cycle or a slow bean being deferred rather than fixedFix the cycle; move slow work out of @PostConstruct into an ApplicationReadyEvent listener
@Autowired on a field in new codeDesign pain is being hiddenConstructor injection; enforce with a static analysis rule
🔑 The container makes your dependency graph a public, inspectable artifact — use that. ctx.getBeanDefinitionNames(), the Actuator /beans endpoint, and a constructor-parameter-count build rule turn architecture from an opinion into something you can measure and fail a build on. Very few teams do this, and it is close to free.

Interview Questions

Beginner: What is Inversion of Control, and how is it different from Dependency Injection?

Inversion of Control is the principle: something other than your class controls the creation and lifecycle of its collaborators. Dependency Injection is one technique for implementing it — the collaborators are handed in from outside, via constructor, setter or field.

They are not synonyms, and the clearest proof is that Service Locator is also IoC but is not DI: the class asks a registry for what it needs instead of being given it. That is inverted control, but the dependencies are hidden inside method bodies rather than declared in the signature — which is why DI is preferred. Spring supports both; ApplicationContext.getBean() is the locator, and reaching for it is usually a mistake.

Beginner: What is a Spring bean?

An object whose lifecycle is managed by the Spring IoC container — created by it, wired by it, initialised and destroyed by it. The important word is lifecycle, not object.

The practical consequence is that a bean can be more than what you wrote. During initialisation Spring may wrap your instance in a proxy, and callers get the proxy. That is how @Transactional, @Cacheable, @Async and method-level security all work — and it is why an object you create with new has none of those behaviours even though the annotations are still on the class.

Mid: Why is constructor injection preferred over field injection?

The core reason is that it makes an invalid object impossible to construct. With field injection the object exists, fully instantiated, with null collaborators between phase 1 and phase 2 of the lifecycle — so anything running in that window, such as a @PostConstruct method or a thread started in the constructor, can see nulls. With constructor injection that state has no representation.

Then the practical benefits: fields can be final, so they are immutable and safely published across threads; the class is testable with plain new and no reflection or Spring context; and circular dependencies fail loudly instead of being silently permitted.

But the argument I actually find most persuasive is a design one: a constructor with 11 parameters is obviously wrong and gets discussed in review, whereas 11 @Autowired fields look tidy and scroll past. Constructor injection does not improve your design; it makes your design visible, which is the thing that reliably leads to it being improved.

Mid: You have two implementations of an interface. How does Spring choose, and what are your options?

It does not choose — it throws NoUniqueBeanDefinitionException at startup, which is the correct behaviour: a build-time failure rather than a runtime coin flip.

Four options. @Primary on the default, when one clearly is the default. @Qualifier at the injection point when the caller must genuinely choose — and I would define a custom qualifier annotation rather than use a string literal, because that gives compile-time safety and refactoring support for four lines of code. Parameter-name matching works but I would never rely on it, since it breaks when the code is compiled without -parameters and turns a parameter rename into a breaking change.

The fourth is the one people forget and is often the best: inject List<PaymentGateway> and let the beans declare what they support. Adding a new implementation becomes one new class with no edit to any existing file — no switch statement, no factory, no registration. When the question "which one?" has a data-driven answer, injecting all of them is usually better than picking one at wiring time.

Senior: Spring Boot 2.6 made circular dependencies fail at startup. Was that the right call, and how do you fix one?

Yes, and for the same reason that any latent problem is better as a build failure than a runtime surprise. A cycle that Spring tolerates still exists — it just becomes load-bearing on initialisation order, which is not something the framework guarantees or that any test asserts. That is a bug waiting for an unrelated refactor to trigger it.

The two escape hatches, spring.main.allow-circular-references=true and @Lazy on one side, both work and both are wrong as a first response. They exist for migrating legacy code on a deadline.

The real fixes, in the order I would try them: extract the shared behaviour into a third component that both depend on — this is usually correct and usually reveals a domain concept that was missing a name; or invert one direction with an application event, so A publishes and B listens, removing the compile-time edge; or merge the two classes, if the cycle is telling you they were always one thing. In practice the first option resolves most cycles, and the resulting code is better independently of the framework.

Senior: A service has grown to 14 constructor dependencies. What does that tell you and what would you do?

It tells me the class has at least 14 reasons to change, which means it is not one class. It also tells me something about the process: nobody decided to build that. Each commit added one dependency for one good reason, and the container never pushed back, because reducing wiring friction is precisely its job.

What I would do first is not refactor. I would look at the test file, because the test is where the cost is concentrated — in the case I have seen, 2,400 lines and 31 @Mock fields for a 1,900-line service. That tells me which clusters of dependencies are always used together, and those clusters are the extraction seams. Grouping by "which methods use which dependencies" gives a much better decomposition than grouping by package or by noun.

Then I would add the mechanism that stops it recurring: a build rule failing any constructor above about six parameters. On one codebase that found four classes; splitting them took three weeks and removed 22% of the service's test setup. The rule matters more than the refactor, because the refactor fixes today and the rule fixes every subsequent year.

The thing I would push back on is treating this as a framework problem. DI did not cause it — it removed the friction that used to serve as the feedback signal, so the team has to supply that signal deliberately. That is a cheap thing to do and almost nobody does it.

1 (easy): This class cannot be unit tested. Fix it, and say exactly what each change buys you. 
  @Service
  public class InvoiceService {
      @Autowired private TaxCalculator taxCalculator;
      @Autowired private InvoiceRepository repository;
      private final Clock clock = Clock.systemUTC();

      public Invoice create(Order order) {

      }

Solution 
  @Service
  public class InvoiceService {
      private final TaxCalculator taxCalculator;
      private final InvoiceRepository repository;
      private final Clock clock;

      public InvoiceService(TaxCalculator taxCalculator,
                            InvoiceRepository repository,
                            Clock clock) {
          this.taxCalculator = taxCalculator;
          this.repository = repository;
          this.clock = clock;
      }
      ...
  }

  @Configuration
  class TimeConfig {
      @Bean Clock clock() { return Clock.systemUTC(); }
  }
ChangeWhat it buys
Fields become constructor parametersThe object cannot exist without its collaborators; testable with plain new, no Spring context and no ReflectionTestUtils
Fields become finalImmutable and safely published — a compiler guarantee, not a convention
Clock injected rather than new'dThe one people miss. Clock.systemUTC() hard-codes "now", so you cannot test month-end, leap years, or timezone boundaries without changing the system clock. Injecting it lets a test pass Clock.fixed(...).

The Clock change is the interesting one, because @Autowired was never the only problem — new on a value that varies is equally untestable. The general rule: if a dependency's behaviour differs between production and test, it must be injected, regardless of whether it looks like a "service".

2 (easy): This fails at startup with NoUniqueBeanDefinitionException. Give three different working fixes and say when each is appropriate. 
  @Component class SmtpEmailSender  implements EmailSender {}
  @Component class SesEmailSender   implements EmailSender {}

  @Service
  class NotificationService {
      NotificationService(EmailSender sender) { ... }
  }
Solution 
  FIX 1 -- @Primary. Use when one is genuinely the default.
    @Primary @Component class SesEmailSender implements EmailSender {}
    // NotificationService unchanged

  FIX 2 -- custom qualifier. Use when the caller must choose.
    @Qualifier @Retention(RUNTIME) public @interface Ses {}

    @Ses @Component class SesEmailSender implements EmailSender {}

    NotificationService(@Ses EmailSender sender) { ... }

  FIX 3 -- inject all of them. Use when the choice is data-driven.
    interface EmailSender { boolean supports(Message m); void send(Message m); }

    NotificationService(List<EmailSender> senders) { ... }
FixAppropriate whenCost
@PrimaryOne clear default; the other is used rarely and explicitlyThe default is declared on the bean, far from the injection point — easy to miss when reading the consumer

3 (medium): This @PostConstruct throws NullPointerException intermittently — it works on some machines and fails on others. Explain precisely why, and fix it. 
  @Service
  public class PricingService {
      @Autowired private RateClient rateClient;
      @Value("${pricing.base-currency}") private String baseCurrency;
      private Map<String, BigDecimal> rates;

      @PostConstruct
      void loadRates() {
          rates = rateClient.fetchRates(baseCurrency);
      }
  }
Solution

Why it is intermittent. Field population (phase 2) and @PostConstruct (phase 4) are ordered relative to each other, so this specific case usually works. What is not ordered is population among fields, and more importantly the creation order of PricingService relative to RateClient when the dependency is expressed as a field rather than a constructor parameter. Spring knows it must create RateClient before injecting it, but with field injection there is no constructor edge forcing the ordering to be discovered early, so cycles and conditional definitions can produce a partially initialised RateClient. Add a cycle, a @Lazy, or an auto-configuration ordering difference between environments and the behaviour changes per machine — which is exactly the symptom described.

The deeper problem is that this is not detectable by reading the class. Field order and bean creation order are not a contract, so "it works here" carries no information.

  @Service
  public class PricingService {
      private final RateClient rateClient;
      private final String baseCurrency;
      private volatile Map<String, BigDecimal> rates = Map.of();

      public PricingService(RateClient rateClient,
              @Value("${pricing.base-currency}") String baseCurrency) {
          this.rateClient = rateClient;
          this.baseCurrency = baseCurrency;
      }

      @EventListener(ApplicationReadyEvent.class)
      void loadRates() {
          this.rates = rateClient.fetchRates(baseCurrency);
      }
  }

Three changes, each doing separate work:

  • Constructor injection — including @Value, which works perfectly well as a constructor parameter. Now the object cannot be constructed before its dependencies exist, and the ordering is a real edge in the dependency graph rather than a hope.
  • ApplicationReadyEvent instead of @PostConstruct — a network call during bean initialisation blocks startup, so a slow or down rate service turns into a failed deploy and a health check timing out. Moving it to "ready" means the app starts, reports healthy, and warms afterwards.
  • volatile and a non-null default — the field is written by one thread and read by request threads, so it needs safe publication; and callers must have defined behaviour during the window before it loads.

The remaining design question I would raise: what should the service do if rates have not loaded? Returning an empty map silently prices everything at zero. Whether it should fail closed, serve a cached snapshot from disk, or refuse traffic via a readiness probe is a business decision, and it needs making explicitly rather than defaulting to whatever an empty map does.

4 (medium): Replace this switch with the List<T> pattern, and state honestly what you lose. 
  @Service
  public class ExportService {
      private final CsvExporter csv;
      private final PdfExporter pdf;
      private final XlsxExporter xlsx;
      // + constructor

      public byte[] export(Report r, String format) {
          switch (format) {
              case "csv":  return csv.export(r);
              case "pdf":  return pdf.export(r);
              case "xlsx": return xlsx.export(r);
              default: throw new IllegalArgumentException(format);
          }
      }
  }
Solution 
  public interface Exporter {
      String format();                 // "csv"
      byte[] export(Report r);
  }

  @Component class CsvExporter implements Exporter {
      public String format() { return "csv"; }
      public byte[] export(Report r) { ... }
  }

  @Service
  public class ExportService {
      private final Map<String, Exporter> exporters;

      public ExportService(List<Exporter> list) {
          this.exporters = list.stream().collect(
              toMap(Exporter::format, identity()));
      }

      public byte[] export(Report r, String format) {
          Exporter e = exporters.get(format);
          if (e == null)
              throw new UnsupportedFormatException(format,
                                                   exporters.keySet());
          return e.export(r);
      }
  }

What you gain: adding JSON export is one new class and zero edits to existing files. The ExportService stops changing for reasons that are not about exporting. The error message can list the supported formats, computed rather than maintained. And the set of exporters becomes something you can filter by profile or conditional — an enterprise-only exporter is just a @ConditionalOnProperty on its class.

What you lose — and this deserves an honest answer:

LossSeverity
You can no longer see the full set of formats by reading one fileReal. The switch was discoverable; the registry is assembled at runtime. Mitigate by logging the registered keys at startup.
The compiler no longer checks exhaustivenessMinor here, since the input is a string anyway. It would matter if the input were an enum — with an enum and a sealed interface, a switch has real advantages.
Duplicate format() values fail at startup with a toMap collisionActually a gain — a loud, immediate failure. But the default message is poor, so supply a merge function that throws with both class names.
Indirection cost for a readerReal. Finding "what handles pdf?" is now a find-usages rather than a scroll. Worth it at 3+ implementations, over-engineering at 2.

I would apply this at three or more implementations, or when the set varies by deployment. For two stable implementations, the switch is clearer and I would leave it.

5 (hard): A team reports that @Transactional "doesn't work" on one of their methods. Diagnose the likely causes from most to least common, and explain the mechanism that makes each one fail.
Solution

Every cause traces back to one fact: @Transactional is implemented by a proxy created in phase 4 of the bean lifecycle. The annotation does nothing by itself; the proxy is what opens the transaction. So the question is always "did the call go through the proxy?"

#CauseMechanism
1Self-invocation — another method of the same class calls itThe internal call uses this, which is the raw instance, not the proxy. The interceptor is never reached. By far the most common cause.
2Method is not publicSpring's default proxy-based AOP only applies to public methods; a private or package-private @Transactional method is silently ignored.
3The object was created with newNot a bean, so no proxy exists at all. Common in tests and in manually constructed helpers.
4The exception thrown is checkedDefault rollback is on RuntimeException and Error only. A checked exception commits. Fix with @Transactional(rollbackFor = Exception.class).
5The exception is caught inside the methodNo exception propagates to the proxy, so it commits. "The transaction didn't roll back" usually means "you swallowed the exception".
6Wrong @Transactional importedjavax/jakarta.transaction versus org.springframework.transaction.annotation — both compile, and the Spring one supports options the other does not.
7The class is final, or the method isCGLIB proxying works by subclassing. A final class cannot be subclassed, so proxy creation fails or is skipped.
8Multiple DataSources, wrong TransactionManagerThe transaction opens against a different data source than the one the repository uses. Specify with @Transactional("orderTxManager").
9A new thread inside the methodThe transaction is bound to a ThreadLocal. Work handed to another thread — including @Async — is outside it entirely.

How I would actually diagnose it rather than guess: turn on logging.level.org.springframework.transaction.interceptor=TRACE. It logs every transaction the interceptor opens and completes. If no line appears for the method, the proxy was never reached — causes 1, 2, 3 or 7. If a line appears and it says "committing", the proxy ran and the rollback rule did not match — causes 4 or 5. That single log setting splits the space in half before any code is read, and it takes thirty seconds.

See Transactions and AOP & Proxies for the full mechanism.

6 (hard): You inherit a Spring Boot service with 140 beans, one 1,900-line class with 14 constructor dependencies, and a 2,400-line test file with 31 mocks. Plan the work, and be honest about what you would not do.
Solution

First, do not start refactoring. A 1,900-line class with 31 mocks is a class whose tests are the only specification anyone has, and those tests are coupled to the current structure. If I break it apart first, I lose the safety net while I am relying on it.

Step 1 — build the dependency-usage matrix. For each of the 14 dependencies, list which of the 47 methods use it. This is mechanical and takes an afternoon with an IDE. The output is almost always striking: dependencies cluster, and the clusters correspond to responsibilities nobody ever named. Methods 1–9 use dependencies A, B, C and nothing else; methods 10–18 use D, E, F. Those clusters are the extraction seams, and they are far better seams than "group by noun" or "group by package" would give.

Step 2 — characterise before extracting. For each cluster, write coarse tests against the public behaviour of those methods, using the real class. Not unit tests with mocks — those already exist and are the problem. These are the tests that must survive the refactor, so they must not know about the structure.

Step 3 — extract one cluster at a time, smallest first. Move the methods and their dependencies into a new bean, inject it into the original class, and have the original delegate. The public API does not change, so no caller is touched and each step is independently shippable and revertible. The original class shrinks by one cluster per step; the mock count in its test drops with it.

Step 4 — the mechanism that stops recurrence. A build rule failing constructors above about six parameters, and a rule banning field @Autowired in new code. On the codebase I have seen this done, the rule found four offenders, the splits took three weeks, and it removed 22% of the service's test setup code. The rule matters more than the refactor — the refactor fixes today, the rule fixes every year after.

What I would not do:

Not doingWhy
A big-bang rewriteNo behavioural specification exists outside the tests I would be discarding. The failure mode is a six-week branch that never merges.
Extracting interfaces for every new classOne implementation, one interface, no seam gained. Add the interface when a second implementation or a test double genuinely needs it.
Chasing the other 139 beans140 beans in a Spring Boot service is unremarkable — most are auto-configured infrastructure. The problem is the distribution, not the count.
Converting the 31 mocks to a slice test as step oneTempting, but it changes the safety net and the structure in the same commit. Structure first, then simplify the tests the structure no longer needs.

The thing I would raise with the team rather than fix silently: whether this class is one bounded context or several. If methods 1–9 are "pricing" and 10–18 are "fulfilment", the extraction is not just a refactor — it is a statement about where a future service boundary would go, and that is worth deciding deliberately rather than discovering three years later. See Resilience & Microservices.

🎯 Key Takeaways

  • The container is a Map<String, Object> plus an algorithm that reads definitions, resolves dependencies and publishes finished beans. Everything else is a plugin to that.
  • IoC is the principle, DI is one technique. Service Locator is IoC and not DI — which is why the terms are not interchangeable.
  • Definitions exist before objects, which is precisely what makes @ConditionalOnMissingBean and all of auto-configuration possible.
  • A bean is a lifecycle, not an object. The instance you get may be a proxy, which is how @Transactional, @Cacheable, @Async and security all work.
  • Constructor injection makes an invalid object impossible to construct. Field injection leaves a window where collaborators are null.
  • Constructor injection makes bad design visible — 11 parameters get discussed in review, 11 annotated fields do not. That is the strongest argument for it.
  • @Value fields are null in the constructor — population is phase 2, the constructor is phase 1. Take them as constructor parameters instead.
  • A single constructor needs no @Autowired since Spring 4.3.
  • Two beans of one type fail at startup, which is correct. Resolve with @Primary, a custom qualifier annotation, or by injecting them all.
  • List<T> injection is the most under-used pattern in Spring — it turns "which one?" into a data-driven decision and makes new implementations zero-edit additions.
  • Prefer a custom qualifier annotation to @Qualifier("string") for compile-time safety and refactoring support, at a cost of four lines.
  • Circular dependencies fail by default since Boot 2.6, and that is right. Fix by extracting a third component or inverting with an event — not with allow-circular-references.
  • Self-invocation bypasses the proxy, which is the number-one reason @Transactional "does not work".
  • Singleton beans must be stateless — mutable fields are shared across every request thread, with no error to tell you.
  • A prototype injected into a singleton is injected once. Use ObjectProvider<T> or a scoped proxy.
  • Heavy work in @PostConstruct blocks startup and times out health checks — listen for ApplicationReadyEvent instead.
  • The container makes wiring free, which removes your design feedback loop. Supply it deliberately: fail the build above ~6 constructor parameters.
