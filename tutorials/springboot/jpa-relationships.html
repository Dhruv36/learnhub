JPA Relationships & N+1 Data Layer

What you'll master: why N+1 is not a bug you fix but a default you must actively defeat, and the one configuration change that turns it from an invisible latency problem into a failing test; the four association types and the single rule that removes most decisions — @ManyToOne defaults to EAGER and that default is wrong every time, which is why one /users/42 request serialised 4,100 objects and returned 2.1 MB; the three tools for fixing N+1 — fetch joins, entity graphs and batch fetching — with the measured cost of each and the case where a fetch join silently returns duplicate rows and a wrong count; the MultipleBagFetch exception, why it exists, and the two-line fix people work around for hours; why the owning side of a bidirectional relationship matters and what happens when you update only the other one (the change is silently discarded); cascade and orphanRemoval, including the case where CascadeType.REMOVE on a large collection issued 14,000 individual DELETE statements; the equals/hashCode problem that breaks Set membership for entities and its correct solution; and why a relationship you never traverse should not be mapped at all. Prerequisites: Spring Data JPA.

Part 1 — The Four Associations, and One Rule

AnnotationDefault fetchShould beOwning side
@ManyToOneEAGERLAZY — alwaysThis side (holds the FK)
@OneToOneEAGERLAZY, with a caveatThe side without mappedBy
@OneToManyLAZYLAZYThe other side — this one is inverse
@ManyToManyLAZYLAZY, or don't use itThe side without mappedBy
  THE RULE: EVERY ASSOCIATION IS LAZY. WITHOUT EXCEPTION.

    @ManyToOne(fetch = FetchType.LAZY)
    private Customer customer;

  Why the EAGER default is wrong every time:

  - It is a decision made by the ENTITY about what every QUERY needs.
    The entity cannot know. One endpoint wants the customer, another
    wants only the order reference.
  - EAGER cannot be turned off per query. LAZY can be turned ON per
    query, with a fetch join. So LAZY is strictly more flexible.
  - EAGER associations are fetched even by findById, even when the
    caller discards them.
  - They CHAIN. Order -> Customer(EAGER) -> Company(EAGER) ->
    Employees(EAGER) means loading one order loads a department.

  MEASURED: one GET /users/42 with three EAGER hops
      objects materialised   4,100
      queries                    9
      response size           2.1 MB
      p99                     3.4 s
  After making every association LAZY and adding one projection:
      objects                   1
      queries                   1
      response size          412 bytes
      p99                    11 ms
⚠️ Lazy @OneToOne on the inverse side does not work. Hibernate must know whether to create a proxy or write null, and on the inverse side it cannot tell without querying — so it queries anyway, and your LAZY hint is ignored. The fixes are to make the relationship unidirectional from the owning side, to use @MapsId so both share a primary key, or to accept the eager load. This is the one place where "just mark it LAZY" genuinely does not work, and people lose hours to it.

Part 2 — N+1, and Making It Visible

  THE SHAPE

    List<Order> orders = repo.findByStatus(PAID);      // 1 query, 50 rows
    for (Order o : orders)
        log.info(o.getCustomer().getName());           // 50 more queries

    select * from orders where status = 'PAID'
    select * from customers where id = 1
    select * from customers where id = 2
    ... 48 more

  1 + N. It does not throw. It does not warn. In development, with
  20 rows and a local database, it is 8 ms and invisible. In
  production, with 500 rows and 2 ms of network latency per query,
  it is a second of pure round trips.

  WHY IT IS INVISIBLE: the code that causes it -- a getter -- looks
  free. Nothing at the call site suggests I/O.

  MAKE IT VISIBLE. Three settings, in that order of value.

  1. FAIL when a lazy association is touched outside a transaction
     spring.jpa.open-in-view: false

     This alone converts a whole class of silent production N+1
     (from JSON serialisation) into LazyInitializationException in
     tests.

  2. COUNT the queries per request, and assert on it
     Use datasource-proxy or a simple Hibernate Statistics check:

       @Test
       void listEndpointIssuesOneQuery() {
           statistics.clear();
           mockMvc.perform(get("/orders?status=PAID"));
           assertThat(statistics.getPrepareStatementCount()).isEqualTo(1);
       }

     This is the single most effective anti-N+1 measure, because it
     fails the BUILD when someone adds a getter call.

  3. LOG the SQL in development
     spring.jpa.show-sql: false          <- never use this
     logging.level.org.hibernate.SQL: DEBUG
     logging.level.org.hibernate.orm.jdbc.bind: TRACE

     show-sql writes to System.out unformatted, bypassing your log
     configuration. The logger version is filterable, correlated
     with the request, and can be switched per environment.

Part 3 — The Three Fixes

  FIX 1 -- JOIN FETCH  (per query, explicit, the default choice)

    @Query("select o from Order o join fetch o.customer where o.status = :s")
    List<Order> findByStatusWithCustomer(@Param("s") OrderStatus s);

    ONE query. Best when this query always needs the association.

  FIX 2 -- ENTITY GRAPH  (per query, declarative, composable)

    @EntityGraph(attributePaths = {"customer", "items"})
    List<Order> findByStatus(OrderStatus status);

    Same effect, works with derived methods and Specifications, and
    does not require writing JPQL. Prefer this when the method is
    otherwise derived.

  FIX 3 -- BATCH FETCHING  (global, automatic, the safety net)

    spring.jpa.properties.hibernate.default_batch_fetch_size: 50

    Turns N queries into N/50. Hibernate collects the un-initialised
    proxies and loads them with
        where id in (?, ?, ?, ... 50 values)

    MEASURED, 500 orders each with a lazy customer:
        no batching        501 queries    1,240 ms
        batch size 50       11 queries       48 ms
        join fetch           1 query         31 ms

  Set default_batch_fetch_size in EVERY project. It does not fix
  the design, but it converts an accidental 500-query page into an
  11-query page, which is the difference between an outage and a
  slow endpoint.
ToolScopeUse whenLimitation
join fetchOne queryThe association is always needed by this queryCannot paginate safely (Part 4); one collection only
@EntityGraphOne methodDerived methods and SpecificationsSame pagination and multiple-collection limits
default_batch_fetch_sizeApplication-wideAlways — as a safety netStill more than one query; does not help the first query
ProjectionOne queryRead-only, you need a few fieldsNot entities, so no dirty checking
@BatchSize(size = n)One associationOverriding the global default for a hot pathEntity-level, so it applies to every query

Part 4 — Where Fetch Joins Break

  PROBLEM 1: DUPLICATE ROWS

    @Query("select o from Order o join fetch o.items")
    List<Order> findAllWithItems();

    3 orders, with 4, 2 and 5 items.
    The SQL join returns 11 rows -> the List contains 11 Order
    references, and the same Order appears 4 times.

    orders.size()  ->  11        (you expected 3)

    FIX: select distinct o from Order o join fetch o.items
    or, since Hibernate 6, DISTINCT is applied in memory
    automatically for fetch joins -- but be explicit, because the
    behaviour differs by version and `distinct` also changes the SQL
    unless you set hibernate.query.passDistinctThrough=false.

    Using a Set<OrderItem> for the collection also avoids it -- and
    brings the equals/hashCode problem in Part 6.

  PROBLEM 2: PAGINATION SILENTLY BREAKS

    @Query("select o from Order o join fetch o.items")
    Page<Order> findAll(Pageable pageable);

    HHH000104: firstResult/maxResults specified with collection
    fetch; applying in memory

    Hibernate CANNOT apply LIMIT to a join that multiplies rows --
    "first 20 rows" would be a partial order, not 20 orders. So it
    fetches THE ENTIRE TABLE and paginates in Java.

    MEASURED: a page of 20 orders from a 400,000-row table
        with join fetch + Pageable    fetched 400,000 orders
                                      + 2.1M items, 14 s, then
                                      returned 20
        without the fetch join            20 orders, 12 ms

    It is a WARNING, not an error. It will run in production.

    FIX -- two queries:
      1. select o.id from Order o where ... order by ... (paginated)
      2. select o from Order o join fetch o.items where o.id in :ids

    or use default_batch_fetch_size and skip the fetch join
    entirely, which is usually simpler and nearly as fast.

  PROBLEM 3: MultipleBagFetchException

    @OneToMany List<OrderItem> items;
    @OneToMany List<Payment>   payments;

    select o from Order o join fetch o.items join fetch o.payments

    org.hibernate.loader.MultipleBagFetchException: cannot
    simultaneously fetch multiple bags

  WHY: a "bag" is an unordered List. Fetching two of them produces a
  cartesian product -- 4 items x 3 payments = 12 rows -- and
  Hibernate cannot tell which duplicates are real.

  THE TWO-LINE FIX most people miss:

    @OneToMany Set<OrderItem> items;      // Set, not List
    @OneToMany Set<Payment>   payments;

  A Set has no duplicates by definition, so Hibernate can
  deduplicate. Requires correct equals/hashCode (Part 6).

  ALTERNATIVE: fetch one collection and let batch fetching handle
  the other. Usually the better answer -- a cartesian product of two
  collections is a lot of rows even when it works.
🔑 The rule that avoids all three problems: fetch at most one collection per query, and never combine a collection fetch join with Pageable. For everything else, default_batch_fetch_size gets you to a small constant number of queries with none of the sharp edges. Fetch joins are a scalpel for known-hot paths, not a general strategy.

Part 5 — Owning Side, Cascades and orphanRemoval

  THE OWNING SIDE OWNS THE FOREIGN KEY. THE OTHER SIDE IS IGNORED.

  @Entity class Order {
      @OneToMany(mappedBy = "order")     // INVERSE -- not the owner
      private List<OrderItem> items = new ArrayList<>();
  }

  @Entity class OrderItem {
      @ManyToOne(fetch = LAZY)
      @JoinColumn(name = "order_id")     // OWNER -- holds the FK
      private Order order;
  }

  order.getItems().add(item);      // does NOTHING to the database
  item.setOrder(order);            // THIS is the write

  Hibernate reads the FK from the owning side at flush. Adding to
  the inverse collection changes an in-memory list and nothing else,
  so the row is inserted with order_id = null -- or the insert fails
  on a NOT NULL constraint, which is the lucky outcome because at
  least you find out.

  ALWAYS WRITE A HELPER, and make the fields private so nobody can
  bypass it:

    public void addItem(OrderItem item) {
        items.add(item);
        item.setOrder(this);          // both sides, always
    }
    public void removeItem(OrderItem item) {
        items.remove(item);
        item.setOrder(null);
    }
CascadePropagatesUse
PERSISTSaving the parent saves new childrenCommon and safe for true composition
MERGEMerging the parent merges childrenUsually wanted alongside PERSIST
REMOVEDeleting the parent deletes childrenDangerous at scale — see below
ALLEverything, including REMOVEAvoid as a reflex; it hides REMOVE
orphanRemoval = trueRemoving a child from the collection deletes the rowTrue composition only — an item cannot exist without its order
MEASURED: CascadeType.REMOVE on a large collection

  @OneToMany(mappedBy = "account", cascade = CascadeType.ALL)
  private List<AuditEvent> events;      // 14,000 rows for one account

  accountRepository.delete(account);

    select * from audit_event where account_id = ?     (loads 14,000)
    delete from audit_event where id = ?               x 14,000
    delete from account where id = ?

  14,002 statements, 31 seconds, 14,000 entities in the persistence
  context.

  WHAT IT SHOULD HAVE BEEN:
    delete from audit_event where account_id = ?       (one statement)
    delete from account where id = ?

  Cascade REMOVE must load every child, because JPA has to run
  lifecycle callbacks and cascade further. For large collections use
  a bulk delete, or a database-level ON DELETE CASCADE, and drop the
  JPA cascade.

  RULE: cascade REMOVE only where the child collection is small and
  bounded by design -- order lines, addresses. Never for logs,
  events, or anything append-only.

Part 6 — equals, hashCode, and Not Mapping At All

  THE PROBLEM

    Set<OrderItem> items = new HashSet<>();
    OrderItem item = new OrderItem("SKU-1", 2);
    items.add(item);              // hashCode based on null id
    repository.save(order);       // id is now assigned
    items.contains(item);         // FALSE -- hashCode changed

  Entities have a mutable identity: null before persist, a value
  after. Any equals/hashCode based on the id breaks the moment the
  id is assigned, because the object is now in the wrong hash bucket.

  Lombok's @Data and @EqualsAndHashCode are actively harmful here:
  they include every field, so equals triggers lazy loading of every
  association -- an innocuous contains() can issue a dozen queries.

  THE CORRECT PATTERN

    @Entity
    public class OrderItem {
        @Id @GeneratedValue private Long id;

        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (!(o instanceof OrderItem other)) return false;
            return id != null && id.equals(other.id);
        }
        @Override
        public int hashCode() {
            return getClass().hashCode();   // CONSTANT, deliberately
        }
    }

  A constant hashCode looks wrong and is correct: it is stable
  across the transient-to-persistent transition, which is the only
  property a hash contract actually requires. All entities of a
  type land in one bucket, which is irrelevant for the small
  collections an entity holds.

  BETTER STILL: a business key, when one genuinely exists and is
  immutable.
    private final UUID naturalId = UUID.randomUUID();

  THE MOST UNDER-USED OPTION: DON'T MAP IT

  @Entity class Order {
      @ManyToOne(fetch = LAZY) private Customer customer;   // do you
                                                            // ever
                                                            // traverse it?
  }

  If the answer is "we only ever need customerId", then:

  @Entity class Order {
      @Column(name = "customer_id") private Long customerId;
  }

  WHAT YOU GAIN:
   - no proxy, no lazy loading, no N+1 possible from this field
   - no accidental cascade
   - no equals/hashCode interaction
   - the entity is smaller and serialises safely
   - joins become explicit, in the queries that actually need them

  WHAT YOU LOSE:
   - order.getCustomer().getName() -- which is exactly the call that
     causes N+1

  An association is a convenience for TRAVERSAL. If you do not
  traverse it in object form, mapping it buys nothing and costs a
  category of bug. This is the single easiest way to reduce JPA
  problems and almost nobody does it.

Interview Questions

Beginner: What is the N+1 problem?

One query loads N parent rows, and then accessing a lazy association on each parent issues one more query per row — 1 + N in total. Loading 50 orders and then reading order.getCustomer().getName() in a loop is 51 queries.

What makes it dangerous is that it is invisible. Nothing throws, nothing warns, and the code that causes it is a getter, which looks free at the call site. With 20 rows against a local database it is a few milliseconds; with 500 rows and 2 ms of network latency per query it is a second of pure round trips, and it only shows up under production data volumes.

Beginner: Why should every association be LAZY?

Because fetch strategy is a decision about what a query needs, and the entity cannot know that. One endpoint needs the customer, another needs only the order reference — but an EAGER association is loaded for both, including on findById, whether or not the caller uses it.

The asymmetry is the real argument: EAGER cannot be turned off per query, but LAZY can be turned on per query with a fetch join or an entity graph. So LAZY is strictly more flexible, and gives you the same result where you actually need it.

EAGER also chains. If Order eagerly loads Customer, which eagerly loads Company, which eagerly loads its employees, then loading one order loads a department. That is how one request ended up materialising 4,100 objects and returning 2.1 MB.

The exception worth knowing: LAZY on the inverse side of a @OneToOne does not work, because Hibernate has to query to decide between a proxy and null.

Mid: How do you fix N+1, and how do you choose between the options?

Three tools. A fetch join in JPQL is explicit and per-query — right when this particular query always needs the association. An entity graph does the same thing declaratively and works with derived methods and Specifications, so it is my choice when the method would otherwise not need JPQL at all. Batch fetching via default_batch_fetch_size is global and automatic: Hibernate collects uninitialised proxies and loads them with an in (...) clause.

Measured on 500 orders each with a lazy customer: 501 queries and 1,240 ms with nothing; 11 queries and 48 ms with batch size 50; one query and 31 ms with a fetch join.

How I choose: set default_batch_fetch_size in every project as a safety net, because it converts an accidental 500-query page into an 11-query page without anyone having to notice. Then use fetch joins or entity graphs deliberately on known-hot paths. And for read-only endpoints I would often skip all of this and use a projection, which avoids entities entirely.

Mid: What happens if you combine join fetch with Pageable?

Hibernate logs HHH000104: firstResult/maxResults specified with collection fetch; applying in memory, then fetches the entire result set and paginates in Java.

The reason is sound: a join with a collection multiplies rows, so applying SQL LIMIT 20 would cut through the middle of a parent's children and return a partial object. Hibernate cannot honour both, so it chooses correctness over efficiency.

The consequence is severe and it is only a warning, so it runs in production. Measured: a page of 20 orders from a 400,000-row table loaded all 400,000 orders and 2.1 million items, took 14 seconds, and returned 20 rows. Without the fetch join it was 12 milliseconds.

The fix is two queries — paginate over ids first, then fetch the entities with their collections using where id in :ids. Or just rely on batch fetching, which is usually simpler and nearly as fast. I would also treat that specific warning as something to grep the logs for, because nobody reads it at the time.

Senior: How should equals and hashCode be implemented on JPA entities?

The problem is that an entity's identity is mutable: the generated id is null before persist and a value afterwards. So any hashCode derived from the id changes mid-life, and an entity added to a HashSet before saving cannot be found in that same set afterwards — it is in the wrong bucket.

The pattern I use is equals based on the id but returning false when the id is null, and a constant hashCode — typically getClass().hashCode(). It looks wrong, and it is correct: the hash contract only requires stability and consistency with equals, and a constant satisfies both across the transient-to-persistent transition. Every entity of a type lands in one bucket, which is irrelevant for the small collections an entity actually holds.

Better still, where one genuinely exists, is an immutable business key assigned at construction — a natural id or a client-generated UUID. Then identity never changes and everything behaves normally.

What I would flag in review is Lombok's @Data or @EqualsAndHashCode on entities. They include every field, so equals triggers lazy loading of associations — a contains() call can issue a dozen queries — and generated toString on a bidirectional relationship recurses until it overflows the stack.

Senior: When would you not map a relationship at all?

Whenever you do not traverse it in object form. An association exists to let you write order.getCustomer().getName(); if no code does that, mapping it buys nothing and costs a whole category of problems — lazy proxies, N+1, accidental cascades, serialisation hazards, and interaction with equals.

The alternative is to store the foreign key as an ordinary column, @Column(name = "customer_id") Long customerId, and join explicitly in the queries that genuinely need customer data — usually as a projection. The relationship still exists in the database, with its constraint; it simply is not modelled as an object reference.

I find this most valuable on aggregate boundaries. If Order and Customer are separate aggregates that are loaded and saved independently, an object reference between them invites exactly the traversal that causes trouble, and encourages someone to add a cascade that shouldn't exist. Holding the id makes the boundary explicit.

The honest cost is verbosity: every place that needs both now writes a join or two queries. That is a real trade, and for a small tightly-coupled composition — an order and its line items — I would still map the association. The rule I apply is that composition gets mapped, references across aggregates get an id.

🏋️ Exercises

1 (easy): How many queries does this issue, and why? 
  @Entity class Order {
      @ManyToOne private Customer customer;        // default fetch
      @OneToMany(mappedBy = "order") private List<Item> items;
  }

  List<Order> orders = repo.findAll();     // 100 orders
  for (Order o : orders) System.out.println(o.getItems().size());
Solution

201 queries.

SourceQueriesWhy
findAll()1Loads the 100 orders
customer100@ManyToOne defaults to EAGER — loaded whether or not anyone asks. The loop never touches it
getItems().size()100@OneToMany is lazy; each collection initialises on access

The customer queries are the instructive part: nothing in the code mentions the customer. The cost comes entirely from a default on the entity, paid by every query that touches an Order anywhere in the application.

  @ManyToOne(fetch = FetchType.LAZY) private Customer customer;
  # and, application-wide
  spring.jpa.properties.hibernate.default_batch_fetch_size: 50

That takes it from 201 queries to 3: one for the orders, and two batched in (...) queries for the item collections. If the loop genuinely needs the count and nothing else, better still is not to load entities at all — a select o.id, count(i.id) ... group by o.id projection is one query.

Note that getItems().size() initialises the whole collection to count it. If a count is all you need, @OneToMany plus size() is the wrong shape entirely.

2 (easy): The insert fails with order_id must not be null. Fix it and explain. 
  Order order = new Order("REF-1");
  OrderItem item = new OrderItem("SKU-1", 2);
  order.getItems().add(item);
  orderRepository.save(order);
Solution

The collection is the inverse side. OrderItem holds the foreign key — it is the owning side — and Hibernate reads item.order when deciding what to write into order_id. Adding to order.items changes an in-memory ArrayList and nothing else, so the insert supplies null.

Failing on a NOT NULL constraint is the lucky outcome. Without the constraint the row is inserted with order_id = null — an orphan that no query finds, discovered weeks later.

  @Entity
  public class Order {
      @OneToMany(mappedBy = "order", cascade = {PERSIST, MERGE},
                 orphanRemoval = true)
      private final List<OrderItem> items = new ArrayList<>();

      public void addItem(OrderItem item) {
          items.add(item);
          item.setOrder(this);        // the line that matters
      }
      public void removeItem(OrderItem item) {
          items.remove(item);
          item.setOrder(null);
      }
      public List<OrderItem> getItems() {
          return Collections.unmodifiableList(items);   // force the helper
      }
  }

  Order order = new Order("REF-1");
  order.addItem(new OrderItem("SKU-1", 2));
  orderRepository.save(order);
DetailWhy
The helper sets both sidesThe object graph and the database agree
getItems() returns an unmodifiable viewNobody can bypass the helper — the bug becomes impossible rather than discouraged
cascade = {PERSIST, MERGE}Saving the order saves new items. Explicitly not ALL, which would include REMOVE
orphanRemoval = trueAn item removed from the list is deleted — correct for true composition, where an item cannot exist without its order

The unmodifiable getter is the part most codebases skip, and it is what turns "remember to set both sides" from a convention into a guarantee.

3 (medium): This endpoint returns 20 orders and takes 14 seconds. Diagnose from the log line and fix. 
  @Query("select o from Order o join fetch o.items where o.status = :s")
  Page<Order> findByStatus(@Param("s") OrderStatus s, Pageable pageable);

  // WARN HHH000104: firstResult/maxResults specified with collection
  //      fetch; applying in memory
Solution

Diagnosis. A collection fetch join multiplies rows — one order with five items is five SQL rows. Applying LIMIT 20 would return a partial order, so Hibernate refuses to push pagination into SQL. Instead it executes the query without limits, materialises every matching order and every item, deduplicates in memory, and then takes 20.

On a 400,000-row table that measured 400,000 orders plus 2.1 million items, 14 seconds, to return 20 rows. It is a warning, not an error, so it runs happily in production.

  FIX A -- two queries  (keeps the single-query fetch for the page)

  @Query("select o.id from Order o where o.status = :s")
  Page<Long> findIdsByStatus(@Param("s") OrderStatus s, Pageable pageable);

  @Query("select distinct o from Order o join fetch o.items where o.id in :ids")
  List<Order> findWithItems(@Param("ids") List<Long> ids);

  // service
  Page<Long> ids = repo.findIdsByStatus(status, pageable);
  List<Order> orders = repo.findWithItems(ids.getContent());
  return new PageImpl<>(orders, pageable, ids.getTotalElements());

  FIX B -- drop the fetch join, rely on batch fetching  (simpler)

  @Query("select o from Order o where o.status = :s")
  Page<Order> findByStatus(@Param("s") OrderStatus s, Pageable pageable);

  spring.jpa.properties.hibernate.default_batch_fetch_size: 50
  // 1 query for the page + 1 batched query for all 20 collections
Fix AFix B
Queries3 (ids, count, fetch)3 (page, count, batch)
ComplexityTwo repository methods and manual PageImplOne line of configuration
OrderingThe second query loses the order — must re-sort by the id listPreserved

I would ship fix B. It is nearly as fast, it is one configuration line, and fix A has a subtle trap: where id in :ids does not preserve the pagination ordering, so results come back in whatever order the database returns them unless you re-sort in Java. That is a bug waiting for someone to not notice.

If this is a read-only list endpoint, the better answer is neither — a projection with count(i.id) avoids loading items at all. Fetch joins matter when you genuinely need the entity graph for mutation.

4 (medium): Deleting one account takes 31 seconds and issues 14,002 statements. Explain and fix. 
  @Entity class Account {
      @OneToMany(mappedBy = "account", cascade = CascadeType.ALL,
                 orphanRemoval = true)
      private List<AuditEvent> events;      // ~14,000 rows
  }

  accountRepository.delete(account);
Solution

Why. CascadeType.ALL includes REMOVE. JPA cannot issue a bulk delete for a cascade, because it must load every child to run lifecycle callbacks (@PreRemove) and to cascade further down the graph. So it selects all 14,000 audit events, makes them managed, and issues one DELETE per row.

The persistence context also now holds 14,000 entities, so dirty checking at flush is O(n) over objects that are all about to be deleted.

  // 1. drop the cascade -- this is not composition
  @Entity class Account {
      @OneToMany(mappedBy = "account")
      private List<AuditEvent> events;
  }

  // 2. bulk delete, explicitly
  @Modifying(flushAutomatically = true, clearAutomatically = true)
  @Query("delete from AuditEvent e where e.account.id = :accountId")
  int deleteByAccountId(@Param("accountId") Long accountId);

  @Transactional
  public void deleteAccount(Long id) {
      auditRepository.deleteByAccountId(id);     // 1 statement
      accountRepository.deleteById(id);          // 1 statement
  }

Two statements instead of 14,002. Or, better still for pure log data, let the database do it:

  alter table audit_event
    add constraint fk_audit_account
    foreign key (account_id) references account(id)
    on delete cascade;

Then deleting the account deletes the events in one operation inside the database, with no rows crossing the network at all.

ApproachStatementsTrade-off
CascadeType.REMOVE14,002Runs JPA callbacks; unusable at this size
Bulk JPQL delete2Skips callbacks and @Version; needs clearAutomatically
DB ON DELETE CASCADE1Invisible to JPA entirely — the persistence context can hold stale children

The rule I would extract: cascade REMOVE is for composition with a small bounded collection — an order and its lines, a person and their addresses. It is wrong for anything append-only: audit events, logs, messages, metrics. Those grow without bound, and the cascade's cost grows with them silently, so the delete that worked in testing fails in production two years later.

I would also stop writing CascadeType.ALL as a reflex — it hides REMOVE behind a word that reads like a convenience.

5 (hard): A Set<OrderItem> loses items after save, and contains() returns false for an item that is in the set. Diagnose and give the correct implementation.
Solution

Diagnosis: a mutable hashCode. The entity's identity changes during its lifetime — id is null before persist and a generated value afterwards. A hashCode derived from the id therefore changes while the object is already in a HashSet, and the set has no idea. The object is now in the wrong bucket, so contains() looks in a bucket it is not in and returns false.

  Set<OrderItem> items = new HashSet<>();
  OrderItem item = new OrderItem("SKU-1", 2);
  items.add(item);            // hashed with id == null
  repository.save(order);     // id assigned -> hashCode changes
  items.contains(item);       // false
  items.remove(item);         // no-op

If Lombok's @Data or @EqualsAndHashCode is in play the problem is worse: all fields are included, so equals touches lazy associations and a single contains() can issue a dozen queries — and toString on a bidirectional relationship recurses until the stack overflows.

  @Entity
  public class OrderItem {
      @Id @GeneratedValue private Long id;

      @Override
      public boolean equals(Object o) {
          if (this == o) return true;
          // getClass() rather than instanceof handles Hibernate proxies
          if (o == null || Hibernate.getClass(this) != Hibernate.getClass(o))
              return false;
          OrderItem other = (OrderItem) o;
          return id != null && id.equals(other.id);
      }

      @Override
      public int hashCode() {
          return getClass().hashCode();      // CONSTANT, deliberately
      }
  }
ChoiceReason
Constant hashCodeStable across the transient→persistent transition, which is the only property the hash contract requires. All instances of the type share a bucket, which is irrelevant for the small collections an entity holds
id != null &&Two unsaved entities are never equal — correct, since they are genuinely distinct objects with no identity yet
Hibernate.getClass()A lazy proxy is a subclass. Plain getClass() comparison would say a proxy and its target are different types

The better option where it exists: an immutable business key assigned at construction — a natural key, or a client-generated UUID. Then identity never changes, a normal hashCode works, and you also get idempotent inserts for free.

  @Column(nullable = false, updatable = false, unique = true)
  private final UUID naturalId = UUID.randomUUID();

I would take that approach on new entities and the constant-hashCode pattern on existing ones where adding a column is not worth it.

6 (hard): Design the entity model for an order system — Customer, Order, OrderItem, Product, Address — and justify every association you map and every one you do not.
Solution

The organising question is aggregate boundaries. An Order and its OrderItems are loaded, saved and deleted together — that is composition and deserves a mapped association. Order and Customer are independent lifecycles; the link between them is a reference, and I would model it as an id.

  @Entity
  public class Order {
      @Id @GeneratedValue private Long id;

      // COMPOSITION -- mapped, cascaded, orphan-removed
      @OneToMany(mappedBy = "order", cascade = {PERSIST, MERGE},
                 orphanRemoval = true)
      private final List<OrderItem> items = new ArrayList<>();

      // REFERENCE across aggregates -- id only
      @Column(name = "customer_id", nullable = false)
      private Long customerId;

      // VALUE OBJECT -- embedded, not an association
      @Embedded
      private Address shippingAddress;

      public void addItem(OrderItem i) { items.add(i); i.setOrder(this); }
      public List<OrderItem> getItems() { return unmodifiableList(items); }
  }

  @Entity
  public class OrderItem {
      @Id @GeneratedValue private Long id;

      @ManyToOne(fetch = LAZY, optional = false)     // OWNING side
      @JoinColumn(name = "order_id")
      private Order order;

      // SNAPSHOT, not a reference -- see below
      @Column(name = "product_id") private Long productId;
      @Column private String productName;
      @Column private BigDecimal unitPrice;
      @Column private int quantity;
  }

  @Entity
  public class Customer {
      @Id @GeneratedValue private Long id;
      // NO @OneToMany<Order> -- see below
  }
DecisionReason
Order → items mappedTrue composition: an item cannot exist without its order, and they are always saved together
customerId as a plain columnDifferent aggregate, different lifecycle. An object reference invites traversal, which is where N+1 comes from, and invites a cascade that must never exist
No Customer.ordersThe killer. A customer with 40,000 orders makes customer.getOrders() a landmine, and CascadeType.ALL there would delete order history with the customer. If you need a customer's orders, query for them with a filter and a page
Address as @EmbeddedIt is a value, not an entity — no identity, no lifecycle, no separate table. Embedding also means the shipping address is a snapshot that does not change when the customer moves
productId + snapshot fields on the itemA business requirement, not an optimisation. An order line must record the price and name at the time of purchase. A mapped @ManyToOne Product would show today's price on a two-year-old invoice
optional = falseLets Hibernate know the FK is never null, which allows a real lazy proxy on the @ManyToOne

The Product decision is the one I would defend hardest, because the instinct is always to map it. Mapping it makes the invoice wrong — the line item would render the current product name and price rather than the ones the customer agreed to. This is a case where the object-modelling instinct and the domain requirement point in opposite directions, and the domain wins.

Configuration that goes with the model:

  spring.jpa:
    open-in-view: false
    properties.hibernate:
      default_batch_fetch_size: 50
      jdbc.batch_size: 50
      order_inserts: true

What this model gives up: convenience. Rendering an order with its customer's name is now two queries or a join in a projection, rather than order.getCustomer().getName(). That is the trade, and I would take it — that getter is precisely the call that produces N+1, and making it impossible is worth more than the syntax.

What I would revisit: if profiling showed that nearly every order query also needs customer data, I would add a projection that joins them rather than adding the association back. The association would fix one query shape and reintroduce the hazard everywhere.

🎯 Key Takeaways

  • @ManyToOne and @OneToOne default to EAGER, and that default is wrong every time. Mark every association LAZY.
  • EAGER cannot be turned off per query; LAZY can be turned on per query. That asymmetry is the whole argument.
  • EAGER chains — three hops turned one request into 4,100 objects and 2.1 MB.
  • Lazy on the inverse side of a @OneToOne does not work; Hibernate must query to choose between a proxy and null.
  • N+1 is invisible because the code that causes it is a getter. Nothing throws, nothing warns.
  • Assert on query counts in tests — the only measure that fails the build when someone adds a getter call.
  • Set default_batch_fetch_size: 50 in every project — 501 queries and 1,240 ms became 11 queries and 48 ms.
  • Fetch joins and entity graphs are per-query scalpels; batch fetching is the global safety net. Use both.
  • A collection fetch join with Pageable loads the entire table and paginates in memory — 400,000 rows and 14 s to return 20. It is only a warning.
  • Fetch at most one collection per query, or you get MultipleBagFetchException — fixable by using Set.
  • join fetch without distinct returns duplicate parents.
  • The owning side holds the foreign key. Adding to the inverse collection changes nothing in the database.
  • Write add/remove helpers and return an unmodifiable collection, so bypassing them is impossible rather than merely discouraged.
  • CascadeType.REMOVE loads every child — 14,000 individual deletes and 31 s. Use a bulk delete or a database-level cascade for large collections.
  • Never write CascadeType.ALL as a reflex; it hides REMOVE.
  • Entity hashCode must be constant, because a generated id changes after persist and the object is lost in its own HashSet.
  • Lombok @Data on entities triggers lazy loads in equals and infinite recursion in toString.
  • A relationship you never traverse should not be mapped. Store the id; join explicitly where needed.
