Transactions Data Layer

What you'll master: the single fact that explains nearly every @Transactional bug — it is implemented by a proxy, so a call that does not cross the proxy boundary gets no transaction at all, which is why self-invocation silently does nothing and why the annotation on a private method is ignored without a warning; the default rollback rule that surprises everyone: a checked exception commits, so a method throwing IOException after a partial write leaves the partial write in place; all seven propagation modes with the two that matter in practice, and the measured cost of REQUIRES_NEW (it holds two connections simultaneously, so a pool of 10 deadlocks at 10 concurrent requests); isolation levels explained by the anomalies they prevent rather than by their names, and why your database's default is probably not what the JPA enum says; why transaction boundaries and HTTP boundaries must not be the same — one team's @Transactional controller held a connection through a 40-second third-party call and exhausted the pool; the never-call-a-remote-service-inside-a-transaction rule and the outbox pattern that replaces it; optimistic versus pessimistic locking with the arithmetic for choosing; and how to make transactions observable so a leak is a metric rather than a mystery. Prerequisites: Spring Data JPA and AOP & Proxies.

Part 1 — It Is a Proxy, and That Explains Everything

  WHAT @Transactional COMPILES TO -- conceptually

    class OrderService$$SpringCGLIB extends OrderService {
        @Override
        public void place(Order o) {
            TransactionStatus tx = txManager.getTransaction(definition);
            try {
                super.place(o);                 // YOUR code
                txManager.commit(tx);
            } catch (RuntimeException | Error e) {
                txManager.rollback(tx);         // note: NOT checked
                throw e;
            }
        }
    }

  The annotation itself does nothing. The PROXY does everything. So
  the only question that ever matters is:

              DID THIS CALL GO THROUGH THE PROXY?
CallThrough the proxy?Transaction?
Another bean calls service.place()Yes — it holds the proxyYes
this.place() from another method of the same classNo — this is the raw instanceNo, silently
A private or package-private methodNo — CGLIB cannot override itNo, silently
A final method or classNo — cannot be subclassedNo; often a startup error
An object created with newNo — not a beanNo
A call from a new thread inside the methodYes, but…The transaction is a ThreadLocal — the new thread has none
  THE SELF-INVOCATION BUG, which is 80% of "it doesn't work"

    @Service
    public class OrderService {
        public void placeAll(List<Order> orders) {
            for (Order o : orders) place(o);     // this.place() -- NO PROXY
        }

        @Transactional
        public void place(Order o) { ... }       // annotation ignored
    }

  Every place() call runs with NO transaction. Writes still happen
  (auto-commit per statement), so it looks like it works -- until a
  failure halfway through leaves half the orders saved.

  DIAGNOSIS, in thirty seconds:
    logging.level.org.springframework.transaction.interceptor=TRACE

  If no line appears for the method, the proxy was never reached.

  THE FIXES, best first:
   1. Move place() to a different bean. The boundary then reflects a
      real design boundary rather than a framework constraint.
   2. Inject self:  @Autowired @Lazy private OrderService self;
      then self.place(o). Works, and advertises the problem.
   3. TransactionTemplate -- explicit, no proxy involved at all.
🔑 When someone says "@Transactional doesn't work", set logging.level.org.springframework.transaction.interceptor=TRACE before reading any code. If no line is logged for the method, the proxy was never reached — self-invocation, a non-public method, or an object created with new. If a line appears and says "committing", the proxy ran and the rollback rule did not match — a checked exception, or one that was caught. That single setting splits the problem space in half.

Part 2 — The Rollback Rule

  BY DEFAULT, SPRING ROLLS BACK ON:
      RuntimeException  and  Error

  BY DEFAULT, SPRING COMMITS ON:
      any CHECKED exception

  @Transactional
  public void transfer(Long from, Long to, BigDecimal amount) {
      accounts.debit(from, amount);            // succeeds
      auditFile.write(...);                    // throws IOException
  }

  IOException is checked -> the transaction COMMITS.
  The money left the account. The audit record does not exist.

  THE FIX, when you throw checked exceptions from a transactional
  method:
      @Transactional(rollbackFor = Exception.class)

  WHY THE DEFAULT IS THIS WAY: it mirrors EJB, where checked
  exceptions were "business exceptions" the caller was expected to
  handle and recover from, and unchecked ones were failures. That
  distinction did not survive contact with real code, and the
  default is now a trap rather than a feature.

  THE SECOND RULE: CATCHING DOES NOT UN-MARK

    @Transactional
    public void process(Order o) {
        try {
            inner.riskyStep(o);        // @Transactional, joins THIS tx
        } catch (RuntimeException e) {
            log.warn("continuing", e);  // we "handled" it
        }
        o.setStatus(PARTIAL);
    }                                   // commit -> UnexpectedRollbackException

  When riskyStep's proxy caught the exception it called
  setRollbackOnly() on the SHARED transaction. Your catch block
  cannot clear that flag. At commit, the manager sees it and rolls
  everything back.

  The log says "continuing". Nothing continued.

  FIXES:
    - REQUIRES_NEW on riskyStep, so its rollback is its own
    - noRollbackFor on the outer method for that exception type
    - move the risky work outside the transaction (usually right)

⚠️ Propagation is evaluated by the proxy, so it too is defeated by self-invocation. REQUIRES_NEW on a method called via this. from the same class does not start a new transaction — it does not start anything. This is a particularly nasty version of the bug, because the code reads as though it has explicit, deliberate transaction semantics.

Part 4 — Isolation, by the Anomalies It Prevents

LevelDirty readNon-repeatable readPhantom read
READ_UNCOMMITTEDPossiblePossiblePossible

  WHAT THE ANOMALIES ACTUALLY LOOK LIKE

  DIRTY READ -- you read another transaction's uncommitted write,
  which may then roll back. You acted on data that never existed.

  NON-REPEATABLE READ -- you read row 42 twice in one transaction
  and get different values, because someone committed between them.
      balance check: 100   -> decide to allow a 100 withdrawal
      actual debit:   50   -> another transaction took 50 meanwhile

  PHANTOM READ -- you run the same QUERY twice and get a different
  number of ROWS, because someone inserted a matching row.
      select count(*) where status='PENDING'  -> 5
      ... same transaction ...                -> 6

  * PostgreSQL's REPEATABLE READ uses snapshot isolation and
    prevents phantoms too. MySQL InnoDB's uses next-key locking and
    also largely prevents them. The standard permits them; real
    databases mostly do not. This is why reasoning from the SQL
    standard's table alone will mislead you.

  DEFAULTS DIFFER, AND @Transactional's DEFAULT IS "WHATEVER THE
  DATABASE SAYS"

    Isolation.DEFAULT  -> the datasource's level, NOT a fixed value

    PostgreSQL   READ_COMMITTED
    MySQL        REPEATABLE_READ
    Oracle       READ_COMMITTED
    SQL Server   READ_COMMITTED

  So the same code has different concurrency semantics on MySQL and
  PostgreSQL, and a test suite on H2 tells you about neither.

  RAISING ISOLATION IS RARELY THE RIGHT FIX. SERIALIZABLE on
  PostgreSQL does not block -- it ABORTS transactions with
  serialization_failure, so the application MUST have retry logic.
  Adding SERIALIZABLE without retries converts a rare wrong answer
  into a common 500.

  Prefer a targeted lock (Part 6) over a global isolation change.

Part 5 — Boundaries: Where @Transactional Goes

  ON THE SERVICE METHOD THAT IS ONE UNIT OF WORK.
  Not the controller. Not the repository.

  CONTROLLER -- too wide
    @Transactional
    @GetMapping("/orders/{id}")
    public OrderResponse get(...) { ... }

    The transaction stays open through response serialisation, so
    connection hold time is bounded by CLIENT speed. A slow mobile
    connection holds a database connection.

  REPOSITORY -- too narrow
    Every call is its own transaction, so entities detach between
    calls and multi-step operations have no atomicity at all.

  SERVICE -- correct
    @Transactional
    public Order place(PlaceOrderCommand cmd) {
        Order o = orders.save(Order.from(cmd));
        inventory.reserve(cmd.items());
        return o;
    }
    One business operation, one transaction, all-or-nothing.

MEASURED: what a remote call inside a transaction costs

  @Transactional
  public void place(Order o) {
      orders.save(o);
      paymentGateway.charge(o);       // HTTP to a third party
      o.setStatus(PAID);
  }

  Normal:            gateway p50 180 ms  -> connection held ~200 ms
  Gateway incident:  gateway p99  40 s   -> connection held 40 s

  With pool size 20 and 25 req/s, the pool was exhausted in 0.8 s.
  Then EVERY endpoint failed -- including ones that do not touch
  payments -- because they could not get a connection.

  A third-party slowdown became a total outage of the service.

  THE RULE: NEVER call a remote service inside a transaction.

  THE FIX -- transactional outbox:

  @Transactional
  public Order place(PlaceOrderCommand cmd) {
      Order o = orders.save(Order.from(cmd));
      outbox.save(new ChargeRequested(o.getId(), o.getTotal()));
      return o;                                   // commit: ~5 ms
  }

  A separate poller reads the outbox and calls the gateway, with
  retries and a circuit breaker, outside any database transaction.
  The order and the intent to charge commit atomically; the remote
  call is decoupled from the connection pool entirely.

Part 6 — Locking

  THE LOST UPDATE, which neither isolation level below SERIALIZABLE
  prevents:

    T1: read balance = 100
    T2: read balance = 100
    T1: write 100 - 30 = 70
    T2: write 100 - 50 = 50      <- T1's withdrawal vanished

  OPTIMISTIC -- assume no conflict, detect it at write time

    @Entity class Account {
        @Version private Long version;       // that is the whole change
    }

    update account set balance = ?, version = 4
     where id = ? and version = 3

    0 rows updated -> OptimisticLockException -> retry

  PESSIMISTIC -- prevent the conflict by locking on read

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select a from Account a where a.id = :id")
    Account findForUpdate(@Param("id") Long id);

    select ... for update    -- other readers block

  THE ARITHMETIC FOR CHOOSING

    conflict rate 1%   optimistic: 1% of requests do 2x work  = 1.01x
                       pessimistic: 100% pay lock overhead
                       -> OPTIMISTIC

    conflict rate 60%  optimistic: many retries, and retries
                       collide with each other -- throughput can
                       COLLAPSE rather than degrade
                       -> PESSIMISTIC

  Optimistic locking also solves a problem pessimistic cannot: a
  user opens an edit form, thinks for five minutes, and submits.
  You cannot hold a database lock for five minutes, but you can send
  the version in the form and reject the save if it changed.

  ALWAYS BOUND THE RETRIES, and use jitter:
    @Retryable(retryFor = OptimisticLockingFailureException.class,
               maxAttempts = 3,
               backoff = @Backoff(delay = 50, multiplier = 2, random = true))
🔑 Add @Version to every mutable entity by default. It costs one column and one integer comparison per update, and it converts silent lost updates — the class of bug that produces wrong balances and vanished edits with no error anywhere — into a loud, retryable exception. Bulk @Modifying updates bypass it, which is one more reason to prefer entity updates for anything where correctness under concurrency matters.

Interview Questions

Beginner: How does @Transactional work?

Spring creates a proxy around the bean. When a call arrives through that proxy, an interceptor opens a transaction before your method runs, then commits if it returns normally or rolls back if it throws a RuntimeException or Error.

The annotation itself does nothing — the proxy does everything. That single fact explains all the common failures: a call that does not cross the proxy boundary gets no transaction. Self-invocation within the same class, a private method, a final method, or an object created with new all bypass it silently.

Beginner: Which exceptions cause a rollback?

By default, RuntimeException and Error. Checked exceptions commit, which is the opposite of what almost everyone expects.

So a transactional method that debits an account and then throws IOException writing an audit file will commit the debit. If you throw checked exceptions from transactional methods, set @Transactional(rollbackFor = Exception.class).

The default comes from EJB, where checked exceptions were meant to be recoverable business conditions and unchecked ones were failures. That distinction did not survive contact with real code, so today it is a trap rather than a feature.

Mid: What is REQUIRES_NEW for, and what does it cost?

It suspends any existing transaction and starts an independent one, so the inner work commits or rolls back on its own. The usual reason is something that must survive the outer rollback — an audit record of a failed attempt, or an outbox row.

The cost people miss is that the suspended outer transaction still holds its connection. So each in-flight request needs two connections simultaneously. With a HikariCP pool of 10, ten concurrent requests deadlock: all ten hold an outer connection and wait for an eleventh that will never exist. The symptom is a connection-timeout error with the pool showing 10 active and 0 idle, and no slow query anywhere — every thread is waiting on the pool, not the database.

So the pool must exceed peak concurrency times nesting depth. Often the better answer is a @TransactionalEventListener(phase = AFTER_COMMIT), which achieves "survives the outer outcome" without nesting connections at all.

And note that propagation is evaluated by the proxy, so REQUIRES_NEW on a self-invoked method does nothing — a particularly nasty variant, because the code reads as though it has explicit transaction semantics.

Mid: Optimistic or pessimistic locking?

It depends on the conflict rate, and the arithmetic is straightforward. Optimistic locking costs nothing when there is no conflict — one version column and one comparison — and costs a full retry when there is. Pessimistic locking costs a held lock on every access regardless.

At a 1% conflict rate, optimistic means 1% of requests do double work: about 1.01× total cost, versus 100% of requests paying lock overhead. At a 60% conflict rate, optimistic retries start colliding with each other and throughput can collapse rather than degrade, so pessimistic wins.

There is also a case only optimistic can handle: a user opens an edit form, thinks for five minutes, and submits. You cannot hold a database lock across that, but you can send the version with the form and reject the save if it changed. That is optimistic locking spanning transactions, which pessimistic simply cannot do.

My default is @Version on every mutable entity, because it converts silent lost updates into a loud retryable exception for the cost of one column. I would reach for pessimistic locking only on a specifically identified hot row.

Senior: Where should transaction boundaries be, and why?

On the service method that represents one business operation — one unit of work that must be all-or-nothing.

Not the controller. The transaction then stays open through response serialisation, so connection hold time is bounded by client speed rather than query speed. A slow mobile connection holds a database connection.

Not the repository. Every call becomes its own transaction, so entities detach between calls and a multi-step operation has no atomicity at all.

The rule I care most about is what must not be inside the boundary: a remote call. I have seen a payment gateway's p99 go from 180 ms to 40 seconds during an incident; because the HTTP call was inside @Transactional, connections were held for the duration, a 20-connection pool exhausted in under a second, and every endpoint in the service failed — including ones that never touch payments. A third-party slowdown became a total outage.

The fix is a transactional outbox: commit the state change and a row describing the intent in one short transaction, and have a separate poller make the remote call with retries and a circuit breaker, outside any transaction. The database work commits in milliseconds and the remote call is decoupled from the connection pool entirely.

Senior: A transfer occasionally loses money under load. How would you investigate and fix it?

First I would establish which of three distinct failure modes it is, because the fixes are unrelated.

Is there a transaction at all? Interceptor TRACE logging answers this immediately. If the transfer method is self-invoked, or private, or the object was constructed with new, there is no transaction and each statement auto-commits — so a failure between the debit and the credit leaves money destroyed. This is the most common cause and the cheapest to check.

Is it committing when it should roll back? If the method throws a checked exception after the debit, the default rule commits it. Or the code catches an exception from a joined transactional call and continues, in which case the transaction is already marked rollback-only and the commit throws UnexpectedRollbackException — while the logs claim it continued.

Is it a lost update? Two concurrent transfers both read a balance of 100, one writes 70 and the other writes 50, and one withdrawal vanishes. No isolation level below SERIALIZABLE prevents this, and it produces no error.

For the third, the fix is @Version on the account entity plus bounded, jittered retries on OptimisticLockingFailureException — or, if the same accounts are contended frequently, a pessimistic select … for update with a consistent lock ordering to avoid deadlock.

What I would not do is raise isolation to SERIALIZABLE as a first move. On PostgreSQL it does not block, it aborts with a serialization failure, so without retry logic you have converted a rare wrong answer into a frequent 500. A targeted lock on the specific contended row is both cheaper and more predictable.

Beyond the fix I would want a test that runs concurrent transfers and asserts the invariant that total balance is conserved. Concurrency bugs that produce no exception are exactly the ones that need an explicit invariant test, because nothing else will catch a regression.

  public class OrderService {
      public void a(Order o) { save(o); }              // calls b's neighbour
      @Transactional public void b(Order o) { ... }
      @Transactional private void c(Order o) { ... }
      @Transactional public final void d(Order o) { ... }
  }

  orderService.a(order);
  orderService.b(order);
  new OrderService().b(order);

The dangerous property is that all four failures are silent. The writes still happen, because each statement auto-commits, so everything looks like it works until a failure part-way through leaves inconsistent data.

Verify rather than reason:

  logging.level.org.springframework.transaction.interceptor: TRACE

  # a transactional call logs:
  Getting transaction for [com.acme.OrderService.b]
  Completing transaction for [com.acme.OrderService.b]

No lines means no proxy was reached. For d specifically, Spring may also log a warning at startup that the method cannot be advised — worth grepping the startup log for.

2 (easy): Why is the money gone but no audit record written? 
  @Transactional
  public void withdraw(Long accountId, BigDecimal amount) throws IOException {
      accountRepository.debit(accountId, amount);
      auditLog.appendToFile(accountId, amount);     // throws IOException
  }
Solution

IOException is checked, and Spring commits on checked exceptions. The debit is committed; the audit write failed; the caller sees an exception and reasonably assumes nothing happened.

  @Transactional(rollbackFor = Exception.class)
  public void withdraw(Long accountId, BigDecimal amount) throws IOException {
      ...
  }

That is the direct fix. But there is a deeper problem the fix does not address: a file write is not transactional. Rolling back the database does not un-write the file, and if the file write succeeds and the commit then fails, you have an audit record for a withdrawal that never happened. The two resources cannot be made atomic without a distributed transaction, which is not worth it here.

  @Transactional
  public void withdraw(Long accountId, BigDecimal amount) {
      accountRepository.debit(accountId, amount);
      auditRepository.save(new AuditEntry(accountId, amount));  // same DB
  }

Writing the audit record to the same database makes it genuinely atomic with the debit — one commit, both or neither — and removes the checked exception entirely. If the audit must ultimately land in a file or an external system, write it to an outbox table here and have a separate process ship it, which keeps the atomic part atomic and the unreliable part retryable.

The general rule: only operations on the same transactional resource are atomic together. Files, HTTP calls, message brokers and caches are not, and treating them as though they are is how partial states arise.

3 (medium): Under load this fails with Connection is not available, request timed out after 30000ms, but every query is fast and the database is idle. Explain. 
  spring.datasource.hikari.maximum-pool-size: 10

  @Transactional
  public void placeOrder(OrderCommand cmd) {
      Order o = orderRepository.save(Order.from(cmd));
      auditService.recordAttempt(o);
      inventoryService.reserve(cmd.items());
  }

  @Service class AuditService {
      @Transactional(propagation = Propagation.REQUIRES_NEW)
      public void recordAttempt(Order o) { auditRepository.save(...); }
  }
Solution

Connection starvation from nested transactions, not slow queries.

REQUIRES_NEW suspends the outer transaction — but suspension does not release its connection. Hibernate must keep it to resume the same transactional context afterwards. So while recordAttempt runs, the request holds two connections.

  request 1: outer conn #1  +  inner conn #2
  request 2: outer conn #3  +  inner conn #4
  ...
  request 5: outer conn #9  +  inner conn #10     pool exhausted

  request 6: outer conn ... waits forever

  At 10 concurrent requests: all 10 connections are held by OUTER
  transactions, every one waiting for an inner connection. Nothing
  can complete, so nothing is released. Deadlock, resolved only by
  the 30-second timeout.

The database is idle because no query is running — every thread is blocked on the pool.

FixTrade-off
Drop REQUIRES_NEW; audit joins the outer transactionSimplest. But the audit row disappears if the order rolls back — which may be exactly what you did not want
@TransactionalEventListener(AFTER_COMMIT)Audit runs after commit in its own transaction, with no nesting. Loses the "record the attempt even if it failed" case
BEFORE_COMMIT + a separate audit datasourceTrue independence, at the cost of a second pool to size and operate
Raise the pool to > 2 × peak concurrencyTreats the symptom; the ratio breaks again at the next nesting level

What I would ship: if the audit row is genuinely required even when the order fails, keep REQUIRES_NEW and size the pool for it explicitly — with a comment stating the invariant, because a future pool-size reduction would silently reintroduce the deadlock. If the audit is only interesting for successful orders, use an AFTER_COMMIT listener and remove the nesting entirely.

The general rule: pool size must exceed peak concurrency × maximum nesting depth. Most teams size pools for query throughput and never account for nesting.

4 (medium): Two concurrent transfers each debit 50 from a balance of 100, and the final balance is 50 instead of 0. Fix it three ways and choose.
Solution

This is a lost update: both transactions read 100, both compute 50, and the second write overwrites the first. No isolation level below SERIALIZABLE prevents it, and it produces no exception.

  FIX 1 -- OPTIMISTIC LOCKING

  @Entity class Account {
      @Version private Long version;
  }

  @Retryable(retryFor = OptimisticLockingFailureException.class,
             maxAttempts = 3,
             backoff = @Backoff(delay = 50, multiplier = 2, random = true))
  @Transactional
  public void transfer(Long from, Long to, BigDecimal amount) { ... }

  FIX 2 -- PESSIMISTIC LOCKING

  @Lock(LockModeType.PESSIMISTIC_WRITE)
  @Query("select a from Account a where a.id = :id")
  Account findForUpdate(@Param("id") Long id);

  @Transactional
  public void transfer(Long from, Long to, BigDecimal amount) {
      // ALWAYS lock in a consistent order, or two transfers in
      // opposite directions deadlock
      Long first = Math.min(from, to), second = Math.max(from, to);
      accounts.findForUpdate(first);
      accounts.findForUpdate(second);
      ...
  }

  FIX 3 -- ATOMIC UPDATE, no read-modify-write at all

  @Modifying
  @Query("""
      update Account a set a.balance = a.balance - :amount
      where a.id = :id and a.balance >= :amount
      """)
  int debit(@Param("id") Long id, @Param("amount") BigDecimal amount);

  // 0 rows updated -> insufficient funds, atomically checked
No-conflict costConflict costDeadlock risk
OptimisticZeroFull retryNone
PessimisticLock on every accessWaitReal without ordering
Atomic updateZeroRow lock for one statementLow

I would ship fix 3 for the debit, with fix 1 as the general safety net. The atomic update eliminates the read-modify-write window entirely rather than detecting or preventing conflicts on it, and it checks sufficiency in the same statement — so there is no window between "check balance" and "debit" either. It is the only one of the three where the race cannot occur by construction.

I would still add @Version to the entity, because other code paths will load and modify accounts normally, and the version column protects those without anyone having to remember.

The detail that matters in fix 2 is the consistent lock ordering. Without it, a transfer from A to B and a simultaneous transfer from B to A each hold one lock and wait for the other — a textbook deadlock that appears only under concurrent load.

5 (hard): A payment gateway incident took down every endpoint of a service, including ones unrelated to payments. Explain the mechanism and redesign it.
Solution

Mechanism: a remote call inside a transaction converts a dependency's latency into connection exhaustion.

  @Transactional
  public void place(Order o) {
      orders.save(o);
      paymentGateway.charge(o);      // HTTP, 40 s during the incident
      o.setStatus(PAID);
  }

  normal:   gateway 180 ms -> connection held ~200 ms
  incident: gateway  40 s  -> connection held 40 s

  pool = 20, arrival rate = 25 req/s
    connections consumed per second: 25
    connections released per second: 0.5
  -> pool exhausted in ~0.8 s

  Then EVERY endpoint fails, including /health and read-only pages,
  because none of them can obtain a connection. A partial failure in

The connection is the shared resource that couples unrelated endpoints together. That is why the blast radius is the whole service rather than the payment path.

  REDESIGN -- transactional outbox

  @Transactional
  public Order place(PlaceOrderCommand cmd) {
      Order o = orders.save(Order.from(cmd).withStatus(PENDING_PAYMENT));
      outbox.save(new OutboxMessage("ChargeRequested", o.getId(), o.getTotal()));
      return o;
  }                                          // commits in ~5 ms

  @Scheduled(fixedDelay = 500)
  public void dispatch() {
      for (OutboxMessage m : outbox.claimBatch(50)) {     // own tx, short
          try {
              gateway.charge(m);                          // NO transaction
              outbox.markDone(m);
          } catch (Exception e) {
              outbox.markForRetry(m, backoff(m.attempts()));
          }
      }
  }

Why an outbox rather than just publishing to a queue after commit: a plain AFTER_COMMIT listener that publishes to Kafka can lose the message if the process dies between commit and publish. The outbox writes the intent in the same transaction as the order, so the two cannot diverge. That is the whole point of the pattern.

What the redesign costs, honestly: the API becomes asynchronous. place() returns PENDING_PAYMENT, not PAID, so the client needs a status endpoint or a webhook, and the UI must handle a pending state. That is a real product change, not a transparent refactor, and it is the reason teams resist it until an incident forces the conversation.

What I would add regardless of the redesign: a timeout on the gateway client. An HTTP call with no timeout is unbounded by construction, and in the original design that alone would have capped the damage. It is a one-line mitigation to ship on day one while the outbox is built.

6 (hard): Design the transaction strategy for an order service: synchronous API, Kafka consumers, scheduled jobs, and a nightly reconciliation. State the rules and where you would deviate.
Solution

Four entry points, one set of rules, deliberately different boundaries.

Entry pointBoundaryRationale
HTTP APIOne transaction per service methodOne business operation, all-or-nothing. Never on the controller
Kafka consumerOne transaction per message, inside the listenerThe offset commit must follow the database commit, and processing must be idempotent because redelivery is guaranteed
Scheduled jobOne transaction per chunk, never per runA single transaction over a million rows holds a snapshot for an hour, blocking vacuum and bloating tables
ReconciliationreadOnly = true, on a replicaA long analytical scan must not compete with transactional load or hold a write snapshot

  @Transactional
  public Order place(PlaceOrderCommand cmd) {
      Order o = orders.save(Order.from(cmd));
      outbox.save(new OrderPlaced(o.getId()));   // no remote calls here
      return o;
  }

  // 2. KAFKA -- idempotent, transaction inside the listener
  @KafkaListener(topics = "payments")
  public void onPayment(PaymentEvent e) {
      handler.handle(e);            // separate bean -> real proxy
  }

  @Transactional
  public void handle(PaymentEvent e) {
      if (processed.existsById(e.eventId())) return;   // idempotency guard
      processed.save(new ProcessedEvent(e.eventId()));  // same tx
      orders.markPaid(e.orderId());
  }

  // 3. SCHEDULED -- chunked
  public void expireStaleOrders() {
      List<Long> ids;
      while (!(ids = orders.findStaleIds(PAGE)).isEmpty())
          expireChunk(ids);          // separate bean, @Transactional
  }

  // 4. RECONCILIATION
  @Transactional(readOnly = true)
  public Report reconcile(LocalDate day) { ... }

The rules that apply everywhere:

  • No remote calls inside a transaction. Outbox for anything outbound.
  • @Version on every mutable entity, with bounded jittered retries.
  • Transactions on service methods only — never controllers, listeners or repositories. Note that both the Kafka and scheduled cases delegate to a separate bean, because a @Transactional method invoked from the same class gets no transaction at all.
  • rollbackFor = Exception.class anywhere checked exceptions are thrown.
  • Pool sized for concurrency × nesting depth, with nesting kept at one.

Where I would deviate, and why:

The idempotency guard in the Kafka path must be in the same transaction as the business change. If it is in its own transaction, a crash between the two produces either a duplicate (guard not written) or a lost message (guard written, work rolled back). This is the one place where I insist the two writes are atomic, and it is why the consumer cannot use the outbox pattern for its own bookkeeping.

The chunked job deliberately gives up all-or-nothing semantics: if it fails at chunk 40 of 100, the first 39 are committed. That is the correct trade — it must be restartable and idempotent instead, which is a design requirement on the job rather than a property of the transaction.

What I would put in place beyond the code: a metric for transaction duration and one for pool wait time. The failure modes in this lesson — a long transaction, a nested one, a remote call inside a boundary — all show up first as pool wait time rising while query latency stays flat. That signal is what turns a mystery outage into a five-minute diagnosis, and almost nobody instruments it.

🎯 Key Takeaways

  • @Transactional is implemented by a proxy. The only question that ever matters is whether the call crossed the proxy boundary.
  • Self-invocation, private methods, final methods and new all bypass it — silently, with writes still happening via auto-commit.
  • Diagnose with logging.level.org.springframework.transaction.interceptor=TRACE before reading any code.
  • Checked exceptions commit by default. Use rollbackFor = Exception.class if you throw them.
  • Catching an exception does not clear setRollbackOnly — commit throws UnexpectedRollbackException while your log says "continuing".
  • REQUIRES_NEW holds two connections at once. A pool of 10 deadlocks at 10 concurrent requests, with the database completely idle.
  • Pool size must exceed peak concurrency × nesting depth.
  • Propagation is also proxy-evaluated, so REQUIRES_NEW on a self-invoked method does nothing.
  • Isolation.DEFAULT means the database's default — MySQL and PostgreSQL differ, and H2 tells you about neither.
  • SERIALIZABLE on PostgreSQL aborts rather than blocks, so it requires retry logic or it turns rare wrong answers into frequent 500s.
  • Transaction boundaries belong on service methods — controllers hold connections through serialisation, repositories give no atomicity.
  • Never call a remote service inside a transaction. A 40 s third-party p99 exhausted a 20-connection pool in 0.8 s and failed every endpoint.
  • The transactional outbox decouples remote calls from the connection pool while keeping the state change and the intent atomic.
  • Only same-resource operations are atomic together. Files, HTTP, brokers and caches are not.
  • Lost updates produce no error at all. @Version on every mutable entity converts them into a retryable exception for the cost of one column.
  • Choose locking by conflict rate: optimistic below ~5%, pessimistic when contention is high and retries would collide.
  • An atomic update … where balance >= :amount beats both, because the race cannot occur by construction.
  • Instrument transaction duration and pool wait time — every failure mode here shows up as pool wait rising while query latency stays flat.
