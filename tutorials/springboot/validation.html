Validation Web Layer

What you'll master: the distinction that decides where every rule belongs — validation answers "is this input well-formed?", business rules answer "is this allowed right now?", and conflating them is why teams end up with a repository call inside a ConstraintValidator; the difference between @Valid and @Validated and the two cases where picking the wrong one means your validation silently does not run at all; why @Valid on a nested object is mandatory and easy to forget — one omission meant a 40-field nested address was never validated in production; the three exceptions Spring throws for validation failures and why they need different handlers (the most common error-handling gap in Spring applications); writing custom constraints properly, including the cross-field @AssertTrue trick and a class-level constraint with a correct property path; validation groups for the create-versus-update problem; why validating a JPA entity is a trap that fires at flush time, far from the request, inside a transaction that is already doomed; and how to produce error responses a client can actually act on — field-level, machine-readable, and internationalised. Prerequisites: REST Controllers and Request Mapping & Binding.

Part 1 — Validation Is Not Business Rules

Nearly every validation design problem comes from putting a rule at the wrong layer. The test is whether the answer can change without the input changing.

ValidationBusiness rule
QuestionIs this input well-formed?Is this allowed, given current state?
Depends onThe input aloneDatabase, time, other users, external systems
Answer isAlways the same for the same inputCan differ minute to minute
ExamplesEmail format, not blank, max 100 chars, quantity ≥ 1, date is in the pastEmail already registered, insufficient funds, order already shipped, user lacks permission
Belongs inA JSR-380 constraint on the DTOThe service, as a domain exception
Status code400 Bad Request409 Conflict, 402, 403, 422 — depends on the rule
  THE TRAP THIS PREVENTS:

    @Constraint(validatedBy = UniqueEmailValidator.class)
    public @interface UniqueEmail {}

    class UniqueEmailValidator implements ConstraintValidator<UniqueEmail, String> {
        @Autowired UserRepository repository;          // a DB call
        public boolean isValid(String email, ConstraintValidatorContext c) {
            return !repository.existsByEmail(email);
        }
    }

  It compiles, it works in tests, and it is wrong for four reasons:

  1. TOCTOU race. The check and the insert are not atomic. Two
     concurrent registrations both pass validation and one hits a
     constraint violation you did not handle -- a 500.
  2. It runs OUTSIDE the transaction, so it cannot see uncommitted
     state and cannot lock.
  3. It fires on every validation of that type, including on a
     PATCH that does not change the email -- an unnecessary query
     on every request.
  4. Entity validation on flush (Part 6) runs it again inside the
     persistence context, doubling the queries.

  THE CORRECT SHAPE:
    - @Email @NotBlank on the DTO        (well-formed?)
    - a UNIQUE INDEX in the database     (the actual guarantee)
    - catch DataIntegrityViolationException in the service, or
      check-then-insert and handle the race, and throw
      EmailAlreadyRegisteredException -> 409
🔑 Uniqueness is never a validation constraint — it is a database constraint. Only the database can make "no two rows with this email" true under concurrency, because only it can enforce it atomically with the insert. A pre-check is a nicety that improves the error message for the 99.9% non-concurrent case; the unique index is what makes it correct. Design for the index and treat the pre-check as optional.

Part 2 — @Valid vs @Validated

  @Valid       jakarta.validation.Valid       -- the JSR-380 standard
               - triggers validation of a method parameter
               - CASCADES into nested objects and collections
               - does NOT support validation groups

  @Validated   org.springframework.validation.annotation.Validated
               - Spring's variant
               - SUPPORTS validation groups
               - on a CLASS, enables method-level validation via AOP
               - does NOT cascade on its own
WhereUseWhy
Controller method parameter@ValidStandard, cascades into nested objects
Controller parameter needing groups@Validated(OnCreate.class)Only Spring's annotation carries groups
A nested field inside a DTO@ValidCascading is a @Valid feature — @Validated does nothing here
On a service class, to validate its method parameters@Validated on the classEnables the AOP interceptor; then constraints on parameters take effect
On a @ConfigurationProperties class@ValidatedThe documented mechanism — see Configuration & @Bean
THE TWO WAYS VALIDATION SILENTLY DOES NOTHING

  (1) MISSING @Valid ON A NESTED FIELD

    public record CreateOrder(
        @NotBlank String reference,
        Address shipping,                       // NOT VALIDATED
        @Valid List<LineItem> items) {}         // validated

    public record Address(
        @NotBlank String street,
        @NotBlank @Size(min=2,max=2) String countryCode) {}

    POST with { "reference":"R1", "shipping": {}, "items":[...] }
    -> 200. The empty address passed, because nothing told the
       validator to descend into it.

    FIX: @Valid Address shipping

    MEASURED: one team shipped this for 5 months. A 40-field nested
    address object had full constraints and none of them ever ran.
    Discovered when a downstream shipping API started rejecting
    orders with blank country codes -- 2,300 unshippable orders
    already in the database.

  (2) METHOD VALIDATION WITHOUT @Validated ON THE CLASS

    @Service
    class PricingService {
        BigDecimal quote(@NotNull @Positive BigDecimal amount) { ... }
    }

    -> the annotations do NOTHING. Method validation needs the AOP
       interceptor, which is enabled by @Validated ON THE CLASS:

    @Service
    @Validated                          // <- this line is required
    class PricingService { ... }

    And because it is proxy-based, it has all the proxy caveats from
    AOP & Proxies: self-invocation bypasses it, and the method must
    be public.

  CONTAINER ELEMENT CONSTRAINTS (Bean Validation 2.0) -- underused

    List<@NotBlank String> tags;             // each element
    Map<@NotBlank String, @Positive Integer> quantities;
    Optional<@Email String> contactEmail;
    List<@Valid LineItem> items;             // cascade per element

  This is how you validate the CONTENTS of a collection rather than
  the collection itself. @Size bounds the list; the element
  annotation constrains each entry.

  @Email IS DELIBERATELY LOOSE
    "a@b" passes. The spec's regex accepts almost anything with an @.
    That is correct behaviour -- the only real validation of an email
    address is sending mail to it. Do NOT bolt on a stricter regex:
    RFC 5321 permits far more than people expect, and every custom
    email regex on the internet rejects valid addresses. Use @Email
    for shape and a confirmation link for truth.

Part 4 — Cross-Field and Custom Constraints

  THE CHEAP WAY -- @AssertTrue on a derived method

    public record DateRange(
        @NotNull LocalDate from,
        @NotNull LocalDate to) {

        @AssertTrue(message = "'from' must not be after 'to'")
        public boolean isRangeValid() {
            return from == null || to == null || !from.isAfter(to);
        }
    }

  Two details that matter:
    - the method name must follow the isX()/getX() convention, and
      the property path in the error will be "rangeValid"
    - it MUST tolerate nulls, because @AssertTrue runs even when
      @NotNull has already failed -- otherwise you get an NPE
      inside the validator instead of a 400

  THE PROPER WAY -- a class-level constraint with a real property path

  @Target(TYPE) @Retention(RUNTIME)
  @Constraint(validatedBy = DateRangeValidator.class)
  public @interface ValidDateRange {
      String message() default "'from' must not be after 'to'";
      Class<?>[] groups() default {};
      Class<? extends Payload>[] payload() default {};
  }

  public class DateRangeValidator
          implements ConstraintValidator<ValidDateRange, DateRange> {
      @Override
      public boolean isValid(DateRange r, ConstraintValidatorContext ctx) {
          if (r.from() == null || r.to() == null) return true;   // @NotNull's job
          if (!r.from().isAfter(r.to())) return true;

          ctx.disableDefaultConstraintViolation();
          ctx.buildConstraintViolationWithTemplate(ctx.getDefaultConstraintMessageTemplate())
             .addPropertyNode("from")        // <-- attaches the error to a FIELD
             .addConstraintViolation();
          return false;
      }
  }

  The addPropertyNode call is the reason to prefer this over
  @AssertTrue: the client receives an error attached to "from"
  rather than to a synthetic "rangeValid" property, so a form can
  highlight the actual input.

  The three members -- message, groups, payload -- are REQUIRED by
  the spec. Omitting them is a runtime error, and the message is
  unhelpful.
Rule of thumbUse
One field, reusable across DTOsA field-level custom constraint (@Iban, @Sku)
Two fields, one DTO, quick@AssertTrue on a derived method
Two fields, needs a good client errorClass-level constraint with addPropertyNode
Needs the database, another service, or the clockNot a constraint. A business rule in the service

Part 5 — The Three Exceptions

This is the gap in most Spring applications: validation failures arrive as three different exceptions depending on where they were triggered, and a handler for one does not catch the others.

ExceptionThrown whenWhere the errors are
MethodArgumentNotValidException@Valid @RequestBody failsgetBindingResult().getFieldErrors()
BindException@Valid @ModelAttribute (query/form) failsSame — it is a BindingResult
ConstraintViolationExceptionMethod validation on a @Validated class, or constraints directly on @RequestParam/@PathVariablegetConstraintViolations() — a different API
HandlerMethodValidationExceptionBoot 3.2+, parameter constraints on controller methodsA newer unified type
  THE COMMON BUG:

    @RestControllerAdvice
    class ApiExceptionHandler {
        @ExceptionHandler(MethodArgumentNotValidException.class)
        ProblemDetail handle(MethodArgumentNotValidException e) { ... }
    }

  Body validation returns a nice 400 with field detail.
  A constraint on a @RequestParam returns... a 500, because
  ConstraintViolationException is unhandled and Spring has no
  default mapping for it.

  You need BOTH:

  @RestControllerAdvice
  class ValidationExceptionHandler {

      @ExceptionHandler(MethodArgumentNotValidException.class)
      @ResponseStatus(BAD_REQUEST)
      ProblemDetail onBody(MethodArgumentNotValidException e) {
          var pd = ProblemDetail.forStatus(BAD_REQUEST);
          pd.setTitle("Validation failed");
          pd.setProperty("errors", e.getBindingResult().getFieldErrors().stream()
              .map(f -> Map.of("field", f.getField(),
                               "message", f.getDefaultMessage(),
                               "rejected", String.valueOf(f.getRejectedValue())))
              .toList());
          return pd;
      }

      @ExceptionHandler(ConstraintViolationException.class)
      @ResponseStatus(BAD_REQUEST)
      ProblemDetail onParams(ConstraintViolationException e) {
          var pd = ProblemDetail.forStatus(BAD_REQUEST);
          pd.setTitle("Validation failed");
          pd.setProperty("errors", e.getConstraintViolations().stream()
              .map(v -> Map.of("field", lastNode(v.getPropertyPath()),
                               "message", v.getMessage()))
              .toList());
          return pd;
      }
  }
⚠️ Never echo the rejected value back for sensitive fields. f.getRejectedValue() is genuinely useful for debugging a malformed date, and it will cheerfully put a rejected password, token or card number into your response body — and into every log and error-tracking system that records it. Either exclude known-sensitive field names, or omit rejected entirely on any DTO that carries credentials.

Validation groups: create vs update

  public interface OnCreate {}
  public interface OnUpdate {}

  public record UserRequest(
      @Null(groups = OnCreate.class)      // must be absent on create
      @NotNull(groups = OnUpdate.class)   // must be present on update
      Long id,

      @NotBlank(groups = {OnCreate.class, OnUpdate.class})
      String email,

      @NotBlank(groups = OnCreate.class)  // required only at creation
      @Size(min = 12) String password) {}

  @PostMapping   User create(@Validated(OnCreate.class) @RequestBody UserRequest r)
  @PutMapping    User update(@Validated(OnUpdate.class) @RequestBody UserRequest r)

  NOTE: @Valid cannot do this -- groups need @Validated.

  MY HONEST OPINION: groups are worth knowing and usually worth
  avoiding. Two records -- CreateUserRequest and UpdateUserRequest --
  are clearer, need no group interfaces, cannot be validated with
  the wrong group by accident, and let the two contracts evolve
  independently. Reach for groups when the DTO is large and the
  overlap genuinely is 95%.

Part 6 — Do Not Validate Entities

  @Entity
  public class User {
      @Id @GeneratedValue Long id;
      @NotBlank @Email String email;         // Hibernate WILL enforce this
      @NotNull BigDecimal balance;
  }

  Hibernate integrates Bean Validation and validates entities on
  PRE-PERSIST and PRE-UPDATE -- that is, at FLUSH time.

  WHY THAT IS BAD:

  1. IT FIRES FAR FROM THE CAUSE. Flush can happen at commit, or
     when a query needs to see pending writes. The stack trace
     points at a repository call or a transaction commit, not at
     the code that set the bad value.

  2. THE TRANSACTION IS ALREADY DOOMED. A ConstraintViolationException
     at flush leaves the transaction marked rollback-only. Anything
     you try to do in response -- write an audit row, return a
     partial result -- also fails.

  3. IT PRODUCES A 500, NOT A 400. The exception type is
     jakarta.validation.ConstraintViolationException thrown from
     deep in the persistence layer, usually wrapped, and there is no
     BindingResult to build a field-level response from.

  4. IT VALIDATES DATA YOU DID NOT CHANGE. Loading a legacy row that
     predates a constraint and touching any field re-validates the
     whole entity -- so an unrelated update fails on old data. This
     is the same failure mode as tightening a database constraint,
     covered in Schema Validation & Evolution on the MongoDB track.

  WHAT TO DO INSTEAD:
    - validate the DTO at the boundary, where you get a clean 400
    - enforce invariants in the DOMAIN OBJECT's methods, by throwing
    - enforce data integrity with DATABASE constraints (NOT NULL,
      CHECK, UNIQUE), which is the only layer that holds under
      concurrency and against other writers
    - if you want the belt-and-braces entity check, keep it but
      treat it as an assertion, and turn it off in production if it
      is costing you: spring.jpa.properties.jakarta.persistence.validation.mode=none
🔑 Three layers, three jobs. The DTO validates shape and gives the client a 400 with field detail. The domain object enforces invariants by throwing — account.withdraw() refuses to go negative regardless of who calls it. The database enforces integrity under concurrency and against every writer, including scripts and other services. Each catches what the others cannot, and none of them is redundant.

Interview Questions

Beginner: How do you validate a request body in Spring Boot?

Put JSR-380 constraints on the DTO — @NotBlank, @Email, @Size, @Positive — and annotate the controller parameter with @Valid. You also need spring-boot-starter-validation on the classpath; since Boot 2.3 it is not included transitively, and without it the annotations are silently inert.

When validation fails, Spring throws MethodArgumentNotValidException before your method runs. Boot's default handler turns that into a 400, but the body is not especially useful, so in practice you add a @RestControllerAdvice that converts the field errors into a structured response.

Beginner: What is the difference between @NotNull, @NotEmpty and @NotBlank?

@NotNull only requires the value to be present, so an empty string passes. @NotEmpty requires not-null and a size greater than zero — it applies to strings, collections, maps and arrays — so "" fails but " " passes. @NotBlank is strings only and requires at least one non-whitespace character.

For a string field that a user types, @NotBlank is almost always the one you want. @NotNull on a String is a common bug because it accepts the empty value that the check was meant to prevent.

Mid: What is the difference between @Valid and @Validated?

@Valid is the JSR-380 standard annotation. It triggers validation and, importantly, it cascades into nested objects and collection elements. @Validated is Spring's variant: it supports validation groups, and on a class it enables method-level validation through an AOP proxy.

The practical rules: use @Valid on controller parameters and on nested fields — cascading is a @Valid feature and @Validated will not do it. Use @Validated when you need groups, on a service class whose method parameters carry constraints, and on @ConfigurationProperties.

The failure that catches people is method validation: constraints on a service method's parameters do nothing unless the class itself is annotated @Validated, because the interceptor is what enforces them. And since it is proxy-based, self-invocation bypasses it and the method must be public.

Mid: Why should uniqueness not be a validation constraint?

Because a validator cannot make it true. A ConstraintValidator that queries the repository performs a check that is not atomic with the subsequent insert, so two concurrent registrations both pass and one hits a database constraint violation you did not expect — typically surfacing as a 500.

It also runs outside the transaction, so it cannot lock or see uncommitted state; it fires on every validation of that type, including updates that do not touch the field, adding a query per request; and if the entity carries the same constraint it runs again at flush time.

The correct design is a unique index in the database — the only layer that can enforce it atomically — with the service catching the integrity violation and translating it to a domain exception mapped to 409. A pre-check is fine as a nicety for a better error message in the non-concurrent case, but it is not the guarantee, and treating it as one is how the race ships.

Senior: Where should validation live in a layered application?

Three layers with three distinct jobs, and none of them is redundant.

The DTO validates shape — well-formedness that depends only on the input. Email format, required fields, lengths, ranges, collection bounds. It runs before any business code and produces a 400 with field-level detail the client can act on.

The domain object enforces invariants by throwing. account.withdraw(amount) refuses to make the balance negative regardless of which caller invoked it, so the rule cannot be bypassed by a new entry point — a batch job or a message consumer gets the same protection as the HTTP endpoint. These become domain exceptions mapped to 409 or 422.

The database enforces integrity under concurrency and against every writer, including scripts and other services. NOT NULL, UNIQUE, CHECK, foreign keys. This is the only layer that holds when your application is not the only thing writing.

The distinction I would emphasise is that validation answers "is this input well-formed?" and business rules answer "is this allowed right now?". The test is whether the answer can change without the input changing. If it can — email already taken, order already shipped, insufficient funds — it is a business rule, and putting it in a ConstraintValidator is how you end up with a repository call in your validation layer.

Senior: Design the validation error contract for a public API.

I would start from RFC 7807 Problem Details, which Spring Boot 3 supports natively with ProblemDetail. Inventing a bespoke error envelope means every client writes bespoke parsing, and there is now a standard that libraries and gateways already understand.

  {
    "type": "https://api.acme.com/problems/validation-error",
    "title": "Validation failed",
    "status": 400,
    "detail": "The request contains 2 invalid fields",
    "instance": "/orders",
    "traceId": "00-4bf92f...-01",
    "errors": [
      { "field": "items[0].quantity", "code": "Positive",
        "message": "must be greater than 0" },
      { "field": "shipping.countryCode", "code": "Size",
        "message": "must be exactly 2 characters" }
    ]
  }
DecisionReason
A machine-readable code per errorClients branch on codes, not on English prose. It also lets the message change without breaking anyone
Full property paths (items[0].quantity)A form can highlight the exact input. A flat field name cannot address a nested collection
All errors, not the firstReturning one at a time means a user with three mistakes makes three round trips

The consistency requirement matters more than the shape. Every 400 in the API must use this structure — body validation, parameter validation, malformed JSON, type mismatches. That means handling MethodArgumentNotValidException, ConstraintViolationException, HttpMessageNotReadableException and MethodArgumentTypeMismatchException in one place, which is the gap I would expect to find in an existing codebase.

What I would document explicitly: that the errors array is unordered and may grow, so clients must not depend on position or on the set being exhaustive. Otherwise adding a constraint later becomes a breaking change.

🏋️ Exercises

1 (easy): Why does this request succeed with a 200? 
  public record CreateOrder(
      @NotBlank String reference,
      Address shipping,
      List<LineItem> items) {}

  public record Address(@NotBlank String street,
                        @NotBlank @Size(min=2,max=2) String countryCode) {}

  public record LineItem(@NotBlank String sku, @Positive int quantity) {}

  @PostMapping("/orders")
  Order create(@Valid @RequestBody CreateOrder req) { ... }

  POST { "reference":"R1", "shipping":{}, "items":[{"sku":"","quantity":-5}] }
Solution

Because validation does not cascade automatically. @Valid on the controller parameter validates CreateOrder's own constraints — here just @NotBlank on reference, which passes. To descend into shipping and into each LineItem, those members need @Valid themselves.

So the empty address and the line item with a blank SKU and a negative quantity are never examined.

  public record CreateOrder(
      @NotBlank String reference,
      @Valid @NotNull Address shipping,
      @Valid @NotEmpty @Size(max = 100) List<LineItem> items) {}
AdditionCatches
@Valid on shippingThe empty address object
@NotNull on shippingAn omitted address — @Valid alone permits null
@Valid on itemsCascades into each element
@NotEmptyAn order with no lines
@Size(max = 100)A 100,000-item list — a denial-of-service vector in a public API

This is the failure mode worth remembering: it is silent. There is no warning, no log line, and the endpoint appears to work. One team shipped an unvalidated 40-field nested address for five months and found it only when a downstream shipping API began rejecting orders with blank country codes — by which point 2,300 unshippable orders were already stored.

2 (easy): A constraint on a query parameter returns 500 instead of 400. Explain and fix. 
  @RestController
  @Validated
  class SearchController {
      @GetMapping("/search")
      List<Result> search(@RequestParam @Size(min=3) String q) { ... }
  }

  @RestControllerAdvice
  class Handler {
      @ExceptionHandler(MethodArgumentNotValidException.class)
      ProblemDetail handle(MethodArgumentNotValidException e) { ... }
  }
Solution

Different trigger, different exception. A constraint on a method parameter (rather than on a @RequestBody object) is enforced by the method-validation interceptor that @Validated enables, and it throws ConstraintViolationException — not MethodArgumentNotValidException. The advice does not match, nothing handles it, and Spring's fallback produces a 500.

  @ExceptionHandler(ConstraintViolationException.class)
  @ResponseStatus(HttpStatus.BAD_REQUEST)
  ProblemDetail onConstraint(ConstraintViolationException e) {
      var pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
      pd.setTitle("Validation failed");
      pd.setProperty("errors", e.getConstraintViolations().stream()
          .map(v -> Map.of(
              "field", StreamSupport.stream(v.getPropertyPath().spliterator(), false)
                          .reduce((a, b) -> b).map(Path.Node::getName).orElse("?"),
              "code", v.getConstraintDescriptor().getAnnotation()
                          .annotationType().getSimpleName(),
              "message", v.getMessage()))
          .toList());
      return pd;
  }

Note the property path handling: for method validation the path is search.q — method name then parameter — so you want the last node, not the whole path, to give the client a usable field name.

The general lesson: Spring has three or four different validation exceptions depending on where the failure occurred, and they have incompatible APIs — getBindingResult() versus getConstraintViolations(). A @ControllerAdvice that handles only one of them is the most common error-handling gap in Spring applications, and it fails as a 500 rather than a wrong 400, which makes it look like an application bug.

On Boot 3.2+ you may also encounter HandlerMethodValidationException, which unifies some of this. Worth handling both while migrating.

  // 1. DTO validates SHAPE only
  public record RegisterRequest(
      @NotBlank @Email @Size(max = 254) String email,
      @NotBlank @Size(min = 12, max = 128) String password) {}

  // 2. The DATABASE provides the guarantee
  CREATE UNIQUE INDEX uq_users_email ON users (lower(email));

  // 3. The SERVICE owns the rule and the race
  @Service
  class RegistrationService {
      @Transactional
      public User register(RegisterRequest req) {
          try {
              return users.save(User.create(req.email(), hash(req.password())));
          } catch (DataIntegrityViolationException e) {
              if (isUniqueViolation(e, "uq_users_email"))
                  throw new EmailAlreadyRegisteredException(req.email());
              throw e;
          }
      }
  }

  // 4. Mapped to the right status
  @ExceptionHandler(EmailAlreadyRegisteredException.class)
  @ResponseStatus(HttpStatus.CONFLICT)
  ProblemDetail handle(EmailAlreadyRegisteredException e) { ... }

Catch-the-violation rather than check-then-insert is the important choice. It is correct under concurrency without a lock, it costs no extra query on the happy path, and it cannot drift out of sync with the index. Inspecting the constraint name matters — a blind catch would translate any integrity violation into "email already registered", which is a confusing lie when the real cause was something else.

A pre-check is still reasonable as a nicety — an existsByEmail in the service before the insert gives a cleaner message in the 99.9% non-concurrent case. But it must be understood as an optimisation of the error path, not as the guarantee, and the catch block must stay either way.

The security consideration I would raise: a distinct "email already registered" response is a user-enumeration vector — an attacker can test which addresses have accounts. For a consumer application that is often an accepted trade for usability; for anything sensitive, the better pattern is to return 202 regardless and send an email that says either "confirm your new account" or "someone tried to register with your address". That is a product decision worth making deliberately rather than inheriting from the obvious implementation.

5 (hard): Design validation for a create-and-update API where the two operations share 90% of their fields but differ on required fields and immutability.
Solution

Two credible designs, and I would choose the second despite the duplication.

  OPTION A -- validation groups, one DTO

  public interface OnCreate {}
  public interface OnUpdate {}

  public record ProductRequest(
      @Null(groups = OnCreate.class)
      @NotNull(groups = OnUpdate.class) Long id,

      @NotBlank(groups = {OnCreate.class, OnUpdate.class})
      @Size(max = 200) String name,

      @NotNull(groups = OnCreate.class)          // immutable after create
      String sku,

      @NotNull @DecimalMin("0.00") @Digits(integer=8, fraction=2)
      BigDecimal price) {}

  @PostMapping create(@Validated(OnCreate.class) @RequestBody ProductRequest r)
  @PutMapping  update(@Validated(OnUpdate.class) @RequestBody ProductRequest r)

  OPTION B -- two records

  public record CreateProductRequest(
      @NotBlank @Size(max=200) String name,
      @NotBlank @Pattern(regexp="[A-Z]{3}-[0-9]{6}") String sku,
      @NotNull @DecimalMin("0.00") @Digits(integer=8,fraction=2) BigDecimal price) {}

  public record UpdateProductRequest(
      @NotBlank @Size(max=200) String name,
      @NotNull @DecimalMin("0.00") @Digits(integer=8,fraction=2) BigDecimal price) {}

I would ship option B. The decisive argument is the immutability row: with groups, sku is still present on the update DTO, so a careless service that copies all fields will happily change it. With two records the field does not exist, so no amount of carelessness in the service can mutate it. That converts a rule people must remember into one the type system enforces.

The near-miss failure in option A is also worth weighing: writing @Valid instead of @Validated on the parameter means the grouped constraints silently do not run — validation appears to pass and nothing is checked. That is the same class of silent failure as a missing @Valid on a nested field, and it is invisible in review.

Where I would accept option A: a DTO with 30 fields where genuinely two differ. Then the duplication is real and the group interfaces earn their cost. Below about ten fields, two records are cheaper to read and impossible to misuse.

Either way, the immutability of sku also belongs in the service and the database — the DTO shape prevents the API from expressing the change, and a domain check plus a trigger or a lack of an update path prevents every other writer from making it.

6 (hard): A public API returns inconsistent 400s — some with field detail, some with a bare message, some 500s that should be 400s. Design the unified contract and the migration.
Solution

The 500s are the priority, because they are the ones breaking clients and paging on-call. They almost always come from the same cause: a @ControllerAdvice that handles MethodArgumentNotValidException and nothing else, so every other input failure falls through to the default handler.

  @RestControllerAdvice
  class ApiErrorHandler {

      // 1. @Valid @RequestBody
      @ExceptionHandler(MethodArgumentNotValidException.class)
      ProblemDetail body(MethodArgumentNotValidException e) {
          return problem(e.getBindingResult().getFieldErrors().stream()
              .map(f -> err(f.getField(), f.getCode(), f.getDefaultMessage())));
      }

      // 2. @Valid @ModelAttribute (query/form)
      @ExceptionHandler(BindException.class)
      ProblemDetail bind(BindException e) { ... }

      // 3. method / parameter constraints
      @ExceptionHandler(ConstraintViolationException.class)
      ProblemDetail params(ConstraintViolationException e) { ... }

      // 4. malformed JSON  -- often the missing one
      @ExceptionHandler(HttpMessageNotReadableException.class)
      ProblemDetail unreadable(HttpMessageNotReadableException e) {
          return problem(Stream.of(err(fieldFrom(e), "Malformed",
                                       "request body could not be parsed")));
      }

      // 5. ?page=abc for an int parameter
      @ExceptionHandler(MethodArgumentTypeMismatchException.class)
      ProblemDetail typeMismatch(MethodArgumentTypeMismatchException e) { ... }

      // 6. missing required parameter
      @ExceptionHandler(MissingServletRequestParameterException.class)
      ProblemDetail missing(MissingServletRequestParameterException e) { ... }
  }

The contract, RFC 7807 with one extension:

Migration, given clients depend on the current shapes. This is a breaking change to a public contract, so it needs the same discipline as any other: (1) instrument first — log which handler produced each 4xx/5xx for a week, so you know the real distribution rather than guessing; (2) fix the 500s immediately, since nobody can be depending on an unhandled exception, and this is pure improvement with no compatibility risk; (3) add the new shape behind a version header or content type, so v2 clients get Problem Details while v1 keeps the old body; (4) publish, give a deprecation window with a date, then remove.

What I would document explicitly, because it determines whether this contract can ever evolve: the errors array is unordered, may grow, and is not guaranteed exhaustive. Without that, adding a constraint later is a breaking change for any client that asserts on the exact set.

What I would refuse: a "quick fix" that catches Exception in the advice and returns 400. It converts genuine server errors into client errors, which hides outages from your own monitoring — the same failure mode as returning 200 for errors, one level up.

🎯 Key Takeaways

  • Validation asks "is this well-formed?"; business rules ask "is this allowed now?" If the answer can change without the input changing, it is a business rule.
  • Uniqueness is a database constraint, never a validator. Only the database can enforce it atomically with the insert.
  • @Valid cascades; @Validated supports groups and enables method validation. They are not interchangeable.
  • A missing @Valid on a nested field silently skips all its constraints — one team shipped an unvalidated 40-field address for five months.
  • Method constraints do nothing without @Validated on the class, and being proxy-based, self-invocation bypasses them.
  • Validation failures arrive as three or four different exceptions with incompatible APIs — handling only MethodArgumentNotValidException turns parameter failures into 500s.
  • @NotBlank is almost always what you want for strings; @NotNull accepts "".
  • Bound every collection with @Size — an unbounded list is a denial-of-service vector.
  • @Email is deliberately permissive, and that is correct. Never bolt on a stricter regex; use a confirmation link for truth.
  • Cross-field validators must tolerate nulls, because they run even after @NotNull has failed.
  • Use addPropertyNode in a class-level constraint so the error attaches to a real field a form can highlight.
  • Custom constraints must declare message, groups and payload — the spec requires all three.
  • Do not put constraints on JPA entities. They fire at flush time, far from the cause, in a transaction already marked rollback-only, as a 500.
  • Prefer two DTOs to validation groups. An absent field is structurally impossible to send; a grouped field is only protected by remembering the group.
  • Never echo rejected values — they carry passwords and tokens into responses, logs and error trackers.
  • Return all errors at once, with machine-readable codes and full property paths.
  • Three layers, three jobs: DTO validates shape, domain objects enforce invariants, the database enforces integrity. None is redundant.
