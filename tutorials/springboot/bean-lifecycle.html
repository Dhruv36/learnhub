Bean Scopes & Lifecycle Core Container

What you'll master: the phase diagram that answers almost every "why is this null?" question in Spring, and the one phase in it — post-processing — where the object you wrote gets replaced by a proxy, which is the mechanism behind every declarative feature in the framework; why singleton is a container guarantee and not the Singleton pattern, and why conflating them leads people to write thread-unsafe beans with total confidence; the scoped-proxy problem — a prototype injected into a singleton is injected exactly once, so your "new instance every time" bean is the same instance forever, and the three fixes with their measured costs; how request and session scope actually work (a ThreadLocal and a CGLIB proxy, nothing more), and why they break the moment you touch @Async or WebFlux; the initialisation callbacks in their true order and why @PostConstruct is the wrong place for anything slow — one team's 47-second startup was four @PostConstruct methods making network calls, and moving them cut it to 4 seconds; what @PreDestroy does and does not guarantee (it never runs on SIGKILL, on OOM-kill, or on a System.exit), and what graceful shutdown really requires in Kubernetes; and the reason @Lazy should almost never be your answer to a startup problem. Prerequisites: IoC, DI & Beans.

Part 1 — The Lifecycle, Phase by Phase

Every bean goes through the same sequence. Knowing where you are in it explains what is available and what is not.

  ┌─ 1. INSTANTIATE ────────────────────────────────────────────┐
  │  constructor runs                                            │
  │  AVAILABLE: constructor arguments only                       │
  │  NOT YET:   @Autowired fields, @Value fields, setters        │
  └──────────────────────────────────────────────────────────────┘
  ┌─ 2. POPULATE ───────────────────────────────────────────────┐
  │  @Autowired / @Value fields set, setters called             │
  └──────────────────────────────────────────────────────────────┘
  ┌─ 3. AWARE ──────────────────────────────────────────────────┐
  │  BeanNameAware.setBeanName()                                 │
  │  BeanFactoryAware.setBeanFactory()                           │
  │  ApplicationContextAware.setApplicationContext()             │
  └──────────────────────────────────────────────────────────────┘
  ┌─ 4. INITIALISE ─────────────────────────────────────────────┐
  │  BeanPostProcessor.postProcessBeforeInitialization()         │
  │  @PostConstruct                                              │
  │  InitializingBean.afterPropertiesSet()                       │
  │  @Bean(initMethod = "...")                                   │
  │  BeanPostProcessor.postProcessAfterInitialization()          │
  │       ^^^^ PROXIES ARE CREATED HERE ^^^^                     │
  └──────────────────────────────────────────────────────────────┘
  ┌─ 5. READY ──────────────────────────────────────────────────┐
  │  placed in the singleton map; injected into other beans      │
  └──────────────────────────────────────────────────────────────┘
              ... application runs ...
  ┌─ 6. DESTROY (graceful shutdown only) ───────────────────────┐
  │  @PreDestroy                                                 │
  │  DisposableBean.destroy()                                    │
  │  @Bean(destroyMethod = "...")                                │
  │  in REVERSE dependency order                                 │
  └──────────────────────────────────────────────────────────────┘
🔑 Phase 4's last step is the most consequential line in Spring. postProcessAfterInitialization may return a different object — a proxy wrapping yours. Every other bean is then injected with the proxy, not your instance. This is how @Transactional, @Cacheable, @Async, @Retryable, method security and Spring Data repositories all work. It also means that inside your own object, this is not the proxy — which is why self-invocation silently skips every one of those features. See AOP & Proxies.

Seeing it happen

@Component
class LifecycleDemo implements BeanNameAware, InitializingBean,
                               DisposableBean {
    private final Dependency dep;
    @Value("${app.name:unset}") private String appName;

    LifecycleDemo(Dependency dep) {
        this.dep = dep;
        System.out.println("1 constructor: dep=" + (dep != null)
                         + " appName=" + appName);   // appName NULL
    }
    public void setBeanName(String name) {
        System.out.println("3 aware: appName=" + appName);  // set now
    }
    @PostConstruct void post() { System.out.println("4a @PostConstruct"); }
    public void afterPropertiesSet() { System.out.println("4b afterPropertiesSet"); }
    @PreDestroy void pre() { System.out.println("6a @PreDestroy"); }
    public void destroy() { System.out.println("6b destroy"); }
}

OUTPUT:
  1 constructor: dep=true appName=null      <-- the classic surprise
  3 aware: appName=demo-service
  4a @PostConstruct
  4b afterPropertiesSet
  ... running ...
  6a @PreDestroy
  6b destroy

The first line is the one worth internalising. dep is available because it is a constructor argument; appName is null because @Value field injection is phase 2 and the constructor is phase 1. The fix is not @PostConstruct — it is to take the value as a constructor parameter, which also makes the field final.

Part 2 — Singleton Is Not the Singleton Pattern

This is a genuine source of confusion, and it produces real bugs.

  GoF Singleton          : one instance per CLASSLOADER, enforced by
                           a private constructor and a static getter
  Spring singleton scope : one instance per BEAN NAME per CONTAINER

  Consequences of the difference:

  - You can have TWO beans of the same class:
        @Bean OrderService usOrders()  { return new OrderService(US); }
        @Bean OrderService euOrders()  { return new OrderService(EU); }
    Two instances, same class, both singletons. Impossible with GoF.

  - You can have two containers in one JVM (common in tests), each
    with its own instance.

  - Nothing prevents you constructing the class yourself with new.
    That instance simply is not a bean, and gets no proxy.
⚠️ The bug this causes: state in a singleton bean is shared by every request thread simultaneously. A singleton is created once and used concurrently by the whole thread pool — there is no per-request isolation of any kind. A mutable field in a @Service is a data race, and it will not throw; it will return the wrong customer's data under load and be untestable locally, because you cannot reproduce it with one thread.
BROKEN -- and it will pass every test you write

  @Service
  public class ReportService {
      private String currentUser;              // SHARED. Always.
      private final List<Row> buffer = new ArrayList<>();

      public Report generate(String user) {
          this.currentUser = user;             // thread A writes
          buffer.clear();                      // thread B clears A's data
          buffer.addAll(load(user));
          return new Report(currentUser, buffer);
      }
  }

  Under concurrency: user A gets user B's rows, ArrayList throws
  ArrayIndexOutOfBoundsException from concurrent mutation, or
  silently returns a mixed result. Which of the three you get is
  timing-dependent.

CORRECT -- stateless, all state on the stack

  @Service
  public class ReportService {
      public Report generate(String user) {
          List<Row> rows = load(user);         // local = per-call
          return new Report(user, rows);
      }
  }

The rule is simple and absolute: a singleton bean's fields must be either immutable (final collaborators, configuration values) or explicitly thread-safe (AtomicLong, ConcurrentHashMap, a properly synchronised cache). Everything else belongs on the stack.

The prototype row contains a trap significant enough to be worth stating on its own: Spring does not manage the full lifecycle of a prototype bean. It instantiates, populates and initialises it, then hands it to you and keeps no reference. @PreDestroy will never run. If a prototype bean holds a resource — a file handle, a connection, a thread — you own closing it.

The prototype-in-singleton trap

  @Component
  @Scope("prototype")
  class Task { ... }                    // "a new one every time"

  @Service
  class TaskRunner {
      private final Task task;          // injected ONCE, at startup
      TaskRunner(Task task) { this.task = task; }

      void run() { task.execute(); }    // THE SAME INSTANCE. FOREVER.
  }

  WHY: injection happens during TaskRunner's creation, which happens
  once. The prototype scope governs how many instances Spring will
  CREATE on request -- it cannot reach back and change how many
  times an already-built singleton holds a reference.

  This is the single most common misunderstanding of scopes, and it
  fails silently: the code looks right and the scope annotation is
  right there.
FixCodeTrade-off
ObjectProvider<T>provider.getObject() per callCleanest and type-safe. Slight coupling to Spring in the signature. The recommended default.
Scoped proxy@Scope(value="prototype", proxyMode=TARGET_CLASS)Injection point unchanged, but every method call creates a new instance — surprising, and CGLIB cannot proxy final classes
A factoryInject a Supplier<Task> or a hand-written factory beanNo Spring types in the consumer at all. More code, best testability
ApplicationContext.getBean()Look it up each timeWorks, but it is Service Locator — hidden dependency, needs a context in tests. Avoid
  @Service
  class TaskRunner {
      private final ObjectProvider<Task> tasks;
      TaskRunner(ObjectProvider<Task> tasks) { this.tasks = tasks; }

      void run() {
          Task t = tasks.getObject();   // a genuinely new instance
          t.execute();
      }
  }

  ObjectProvider also gives you the optional-dependency methods that
  make it worth knowing beyond this case:
      tasks.getIfAvailable()            // null if no such bean
      tasks.getIfUnique()               // null if 0 or 2+ candidates
      tasks.stream()                    // all candidates, lazily
      tasks.getIfAvailable(Task::new)   // with a fallback

Request and session scope: a ThreadLocal and a proxy

  @Component
  @Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
  public class RequestContext {
      private String correlationId;
      // getters/setters
  }

  @Service
  class AuditService {
      private final RequestContext ctx;      // a PROXY, injected once
      AuditService(RequestContext ctx) { this.ctx = ctx; }

      void log(String event) {
          audit.write(ctx.getCorrelationId(), event);
          //          ^^^ the proxy resolves the REAL instance for
          //              the CURRENT thread's request, on each call
      }
  }

  HOW THE PROXY WORKS:
    RequestContextHolder holds a ThreadLocal<RequestAttributes>.
    The servlet container binds it at the start of the request and
    unbinds it at the end. The CGLIB proxy delegates every method
    call to whatever instance that ThreadLocal currently points at.

  proxyMode is MANDATORY here. Without it Spring cannot inject a
  request-scoped bean into a singleton at all -- there is no request
  in progress at startup, so there is nothing to inject.
⚠️ Request scope is bound to a thread, so it evaporates the moment you leave that thread. An @Async method, a CompletableFuture continuation, a manually started thread, or a parallel stream will all throw BeanCreationException: No thread-bound request found — or worse, in a thread pool that recycles threads, silently read another request's context. Under WebFlux the concept does not apply at all, because one request is not one thread. Propagate the values explicitly (pass them as parameters, or use Micrometer's context propagation) rather than reaching for request scope in asynchronous code.

Part 4 — Initialisation: Fast Startup Is a Feature

MEASURED: a service with a 47-second startup

  Profiled with -Dspring.context.startup=true and the
  ApplicationStartup actuator endpoint:

    RateService.@PostConstruct          14.2 s  (HTTP call, no timeout)
    CatalogCache.@PostConstruct         11.8 s  (loads 400k rows)
    FeatureFlags.@PostConstruct          9.1 s  (calls LaunchDarkly)
    GeoIpDatabase.@PostConstruct         8.4 s  (downloads a 60MB file)
    everything else                      3.5 s
                                        ------
                                        47.0 s

  Consequences beyond the number:
    - Kubernetes readiness probe timeout was 30s -> the pod was
      killed and restarted, forever, during an incident when the
      rate service was slow
    - a rolling deploy of 12 pods took 9+ minutes
    - a developer's edit-compile-test loop was 50 seconds

  FIX: move all four to ApplicationReadyEvent, serve a degraded
  response until loaded, and make readiness reflect it.

    startup                     4.1 s
    time to READY (fully warm) 46  s  (unchanged -- the work is the
                                       same, it just is not blocking)
    rolling deploy              90 s
    pod restart loop            gone

The insight is that startup time and warm-up time are different things, and only one of them should block. Spring gives you the hook to separate them:

  @Component
  class CatalogCache {
      private volatile Map<String, Product> catalog = Map.of();
      private volatile boolean warm = false;

      @EventListener(ApplicationReadyEvent.class)
      void warmUp() {
          this.catalog = load();
          this.warm = true;
      }

      // and make readiness honest about it
      @Component
      static class CatalogHealth implements HealthIndicator {
          public Health health() {
              return warm ? Health.up().build()
                          : Health.outOfService()
                                  .withDetail("state","warming").build();
          }
      }
  }

  Now the pod starts in 4s, reports NOT ready until warm, and the
  load balancer sends it no traffic until it can serve it. That is
  the behaviour you actually wanted; @PostConstruct only ever
  approximated it by blocking.

Part 5 — Destruction: What You Are and Are Not Promised

  @PreDestroy RUNS on:
    - ctx.close() called explicitly
    - SIGTERM, with a registered shutdown hook (Spring Boot does
      this for you by default)
    - a normal main() return

  @PreDestroy DOES NOT RUN on:
    - SIGKILL  (kill -9, and what Kubernetes sends after the
                terminationGracePeriodSeconds expires)
    - the OOM killer
    - System.exit() from within a shutdown hook
    - a JVM crash, a power loss, a container host failure
    - Runtime.halt()

  THEREFORE: @PreDestroy is a courtesy, not a guarantee. Any
  correctness that depends on cleanup running must ALSO be
  recoverable without it. If a lock is only released in @PreDestroy,
  design the lock to expire.
🔑 Graceful shutdown in Kubernetes needs three settings that must agree, and most services get one of them wrong. (1) server.shutdown=graceful — Spring stops accepting new requests and lets in-flight ones finish. (2) spring.lifecycle.timeout-per-shutdown-phase=20s — how long it will wait. (3) The pod's terminationGracePeriodSeconds must be larger than that timeout, or Kubernetes sends SIGKILL while Spring is still politely waiting, and you get the abrupt termination you configured graceful shutdown to avoid. A pod with a 20s Spring timeout and the default 30s grace period is fine; 20s against a 10s grace period is not.
  # application.yml
  server:
    shutdown: graceful
  spring:
    lifecycle:
      timeout-per-shutdown-phase: 20s

  # deployment.yaml
  spec:
    terminationGracePeriodSeconds: 30      # MUST exceed 20s above
    containers:
      - lifecycle:
          preStop:
            exec:
              command: ["sh","-c","sleep 5"]
              # gives the ingress/endpoints controller time to stop
              # routing to this pod BEFORE the app starts refusing.
              # Without it you drop requests that arrive in the
              # window between SIGTERM and deregistration.

Part 6 — @Lazy, and Why It Is Rarely the Answer

Eager singleton creation is deliberate: it converts configuration errors into build failures. Reaching for @Lazy usually trades that away to hide a different problem.

Why people add @LazyWhat is actually wrongBetter fix
To break a circular dependencyA design cycle; two beans each own part of the other's jobExtract a third component, or invert with an event
Startup is slowBlocking work in @PostConstructMove it to ApplicationReadyEvent; the work is the same, it just stops blocking
A bean is expensive and rarely usedLegitimate — this is the real use case@Lazy is correct here. An admin-only report engine, a rarely used client
A bean needs config not available at startupThe design assumes runtime state at wiring timeObjectProvider, or restructure so the bean takes the value as a method parameter
Tests are slowThe test loads a full context it does not needUse slices — @WebMvcTest, @DataJpaTest — or plain unit tests
  THE COST OF @Lazy, stated plainly:

  - A misconfigured bean now fails on the FIRST REQUEST that touches
    it, in production, at 3am -- instead of in CI.
  - The failure surfaces far from its cause, wrapped in whatever
    request was unlucky.
  - First-request latency includes construction, so your p99 gets a
    cold-start spike that does not reproduce under steady load.
  - spring.main.lazy-initialization=true (global) is a development
    convenience. Using it in production trades every startup
    guarantee the container gives you for a few seconds of boot.

  Use it for the rarely-used-and-expensive case. Not as a fix.

Interview Questions

Beginner: What are the Spring bean scopes?

Singleton (the default) — one instance per bean name per container. Prototype — a new instance every time it is requested. And four web-only scopes: request, session, application and websocket.

Two things worth adding beyond the list. Singleton means one per container, not the GoF Singleton pattern: you can have two beans of the same class with different names, and two containers in one JVM. And prototype is the odd one out for lifecycle — Spring creates and initialises the instance then hands it over and keeps no reference, so @PreDestroy never runs on a prototype bean.

Beginner: Why is a @Value field null inside the constructor?

Because they happen in different phases. The constructor is phase 1, instantiation. Field injection — both @Autowired and @Value — is phase 2, population. At the moment the constructor body runs, Spring has not yet touched any field.

The fix is not to move the logic into @PostConstruct, though that works. It is to take the value as a constructor parameter: MyBean(@Value("${app.name}") String name). That makes the field final, makes the dependency visible in the signature, and lets you construct the object in a test with plain new.

Mid: You inject a prototype-scoped bean into a singleton. What happens?

You get one instance, forever. The prototype scope controls how many instances Spring creates when one is requested — but the singleton requests it exactly once, during its own construction at startup. Nothing subsequently re-injects it.

This fails silently, which is what makes it a good question: the scope annotation is right there in the code and looks like it is working.

The fix I would reach for is ObjectProvider<Task> and calling getObject() per use — it is type-safe, explicit at the call site, and ObjectProvider is worth knowing anyway for its optional-dependency methods. A scoped proxy with proxyMode = TARGET_CLASS also works and leaves the injection point unchanged, but I like it less: every method call silently creates an instance, which surprises readers, and CGLIB cannot proxy final classes. I would avoid ApplicationContext.getBean() — it works but it is Service Locator, so the dependency becomes invisible and the test needs a full context.

Mid: How does request scope work, and when does it break?

Mechanically it is a ThreadLocal plus a proxy. The servlet container binds a RequestAttributes object to the current thread at the start of the request via RequestContextHolder, and unbinds it at the end. The request-scoped bean is injected into singletons as a CGLIB proxy, and that proxy delegates each method call to whichever instance the current thread's request attributes point at. That is why proxyMode is mandatory — at startup there is no request, so there is nothing concrete to inject.

It breaks the moment you leave the request thread. @Async, a CompletableFuture continuation, a manually started thread, or a parallel stream all throw No thread-bound request found. The more dangerous version is a pooled thread that has previously served a different request — depending on how the context was propagated, you can read another user's data rather than get an error.

It also does not apply under WebFlux at all, where one request is not one thread. My default position is to avoid request scope for anything beyond trivial per-request metadata, and to pass values explicitly as method parameters instead — it is more typing and it survives every threading model.

Senior: A service takes 47 seconds to start and its pods restart-loop during incidents. Diagnose and fix.

The restart loop is the real bug and the startup time is its cause: if the readiness probe timeout is 30 seconds and startup takes 47, Kubernetes kills the pod before it can ever report ready. During an incident, when a downstream dependency is slow, startup gets slower still and the loop becomes permanent — the service cannot recover precisely when you need it to.

To diagnose I would enable ApplicationStartup tracking and read the actuator /startup endpoint, which attributes time per bean. In the case I have seen, four @PostConstruct methods accounted for 43.5 of the 47 seconds, all doing network or bulk data work: fetching rates, loading a 400k-row catalogue, calling a feature-flag service, downloading a 60MB GeoIP file.

The fix is to separate two things that had been conflated: startup and warm-up. The work moves to ApplicationReadyEvent so it no longer blocks the context, and a HealthIndicator reports OUT_OF_SERVICE until warming completes. The pod then starts in about 4 seconds, reports not-ready honestly, and receives no traffic until it can serve it. Total warm time is unchanged — but it stops being a deploy failure.

Two further things I would insist on. The HTTP calls need timeouts; a @PostConstruct with no timeout on the client is an unbounded startup. And the degraded path needs a decision: what does the service return between ready and warm? Serving zeros because a map is empty is worse than refusing traffic, and that has to be chosen deliberately rather than inherited from whatever an empty collection does.

Senior: What does @PreDestroy guarantee, and how do you actually shut down gracefully in Kubernetes?

@PreDestroy guarantees very little. It runs on an explicit close(), on a normal main return, and on SIGTERM via the shutdown hook Spring Boot registers. It does not run on SIGKILL, on an OOM-kill, on a JVM crash, or on host failure. So it is a courtesy, and any correctness that depends on it must also be recoverable without it — a distributed lock released only in @PreDestroy should have a TTL, because one kill -9 otherwise wedges the system.

For Kubernetes, graceful shutdown needs three settings that have to agree. server.shutdown=graceful makes Spring stop accepting new requests and drain in-flight ones. spring.lifecycle.timeout-per-shutdown-phase bounds how long it waits. And the pod's terminationGracePeriodSeconds must exceed that timeout — otherwise Kubernetes sends SIGKILL while Spring is still draining, and the graceful configuration accomplishes nothing. That mismatch is the most common version of this bug.

The piece most teams miss entirely is that SIGTERM and endpoint deregistration are concurrent, not ordered. For a few hundred milliseconds the ingress may still route to a pod that has begun refusing connections, and those requests are dropped. A preStop hook that simply sleeps a few seconds before the signal is delivered gives the endpoints controller time to remove the pod first. It looks like a hack and it is the standard remedy.

🏋️ Exercises

1 (easy): Predict the exact output order, and explain why configValue is null on the first line. 
  @Component
  class Demo implements InitializingBean {
      @Value("${app.mode}") private String configValue;
      private final Helper helper;

      Demo(Helper helper) {
          this.helper = helper;
          System.out.println("A " + configValue + " " + helper);
      }
      @PostConstruct void p() { System.out.println("B " + configValue); }
      public void afterPropertiesSet() { System.out.println("C"); }
  }
Solution 
  A null com.example.Helper@1a2b3c
  B production
  C

Line A: the constructor is phase 1. helper is non-null because it is a constructor argument — Spring resolved and created it before calling the constructor. configValue is null because @Value field injection is phase 2, which has not happened yet.

Line B before C: within phase 4 the order is postProcessBeforeInitialization → @PostConstruct → afterPropertiesSet() → @Bean(initMethod) → postProcessAfterInitialization. The annotation always runs before the interface callback.

The fix, and the reason this matters: take the value as a constructor parameter.

  Demo(Helper helper, @Value("${app.mode}") String configValue) {
      this.helper = helper;
      this.configValue = configValue;      // now final, now non-null
      System.out.println("A " + configValue);
  }

Worth noting that InitializingBean has no advantage over @PostConstruct here and couples the class to a Spring interface. I would delete it.

2 (easy): This bean is thread-unsafe. Find every problem and fix them. 
  @Service
  public class OrderCounter {
      private int count = 0;
      private String lastOrderId;
      private final SimpleDateFormat fmt =
          new SimpleDateFormat("yyyy-MM-dd");

      public String record(Order o) {
          count++;
          lastOrderId = o.id();
          return fmt.format(new Date()) + "-" + count;
      }
  }
Solution

Three distinct problems, all from the same root cause: this is a singleton, so every request thread shares these fields simultaneously.

ProblemConsequence
count++ is read-modify-writeNot atomic. Concurrent increments are lost, so the counter under-reports and two callers can receive the same number.
lastOrderId sharedMeaningless under concurrency — it is whichever thread wrote last, and there is no safe publication so other threads may not see it at all.
SimpleDateFormat is mutable and not thread-safeThe classic one. Concurrent format() calls corrupt its internal calendar and produce wrong dates or throw ArrayIndexOutOfBoundsException.
  @Service
  public class OrderCounter {
      private final AtomicLong count = new AtomicLong();
      private static final DateTimeFormatter FMT =
          DateTimeFormatter.ofPattern("yyyy-MM-dd");   // immutable
      private final Clock clock;

      public OrderCounter(Clock clock) { this.clock = clock; }

      public String record(Order o) {
          long n = count.incrementAndGet();
          return LocalDate.now(clock).format(FMT) + "-" + n;
      }
  }

lastOrderId is simply deleted — it was never usable. If something genuinely needs "the last order recorded", that is state belonging in a store, not in a field of a shared object.

DateTimeFormatter replaces SimpleDateFormat because it is immutable and thread-safe, so it can be a static final constant. And Clock is injected rather than using new Date(), so the formatting is testable.

The bigger point: a counter that must be correct across replicas cannot live in a field at all — two pods have two counters. If this number is a business identifier, it needs a database sequence. In-process state in a singleton is not just a threading question; it is a scaling question.

3 (medium): A @Scope("prototype") bean is being reused. Show three fixes with working code and recommend one. 
  @Component @Scope("prototype")
  class ReportBuilder {
      private final List<Row> rows = new ArrayList<>();
      void add(Row r) { rows.add(r); }
      Report build() { return new Report(rows); }
  }

  @Service
  class ReportService {
      private final ReportBuilder builder;
      ReportService(ReportBuilder builder) { this.builder = builder; }

      Report generate(List<Row> rows) {
          rows.forEach(builder::add);
          return builder.build();      // rows ACCUMULATE across calls
      }
  }
Solution

The symptom is memorable: every report contains every row ever added, because the builder was injected once and never replaced. Report 3 contains reports 1, 2 and 3.

  FIX 1 -- ObjectProvider  (recommended)

  @Service
  class ReportService {
      private final ObjectProvider<ReportBuilder> builders;
      ReportService(ObjectProvider<ReportBuilder> b) { this.builders = b; }

      Report generate(List<Row> rows) {
          ReportBuilder builder = builders.getObject();   // fresh
          rows.forEach(builder::add);
          return builder.build();
      }
  }

  FIX 2 -- scoped proxy

  @Component
  @Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
  class ReportBuilder { ... }
  // ReportService unchanged -- but note EVERY method call now hits a
  // new instance, so builder.add() and builder.build() would act on
  // DIFFERENT objects. For a stateful builder this fix is WRONG.

  FIX 3 -- no Spring at all

  @Service
  class ReportService {
      Report generate(List<Row> rows) {
          ReportBuilder builder = new ReportBuilder();
          rows.forEach(builder::add);
          return builder.build();
      }
  }

Recommendation: fix 3, then fix 1. Fix 2 is actively wrong here and is worth understanding as a trap — a per-method-call proxy breaks any object that accumulates state across calls, which is exactly what a builder does.

Between 1 and 3: ReportBuilder has no injected dependencies. It is a plain object that holds a list. Making it a Spring bean at all buys nothing and costs indirection, so new is the honest answer, and the class stops needing any Spring annotation.

Fix 1 becomes the right answer the moment ReportBuilder needs a collaborator — a formatter, a repository, a configuration value. Then it must be container-created, and ObjectProvider is how a singleton asks for a fresh one.

Also note: @PreDestroy on ReportBuilder would never run in any of these, because Spring does not track prototype instances. If it held a resource, the consumer must close it.

4 (medium): This works in a controller and throws in an @Async method. Explain precisely, and fix it. 
  @Component
  @Scope(value="request", proxyMode=ScopedProxyMode.TARGET_CLASS)
  class RequestContext {
      private String tenantId;
      // getter / setter
  }

  @Service
  class ImportService {
      private final RequestContext ctx;
      ImportService(RequestContext ctx) { this.ctx = ctx; }

      @Async
      public void importAsync(List<Row> rows) {
          String tenant = ctx.getTenantId();      // throws
          rows.forEach(r -> save(tenant, r));
      }
  }
Solution

Why. Request scope is implemented with a ThreadLocal. The servlet container binds RequestAttributes to the request thread and unbinds them when the request completes. @Async hands the method to a different thread from a TaskExecutor pool, and that thread has no bound request — so the proxy cannot resolve a target and throws BeanCreationException: No thread-bound request found.

The worse variant to be aware of: if someone "fixes" it with RequestContextHolder.setRequestAttributes(..., true) to inherit into child threads, a pooled thread can retain a previous request's attributes after the originating request has completed. Then it does not throw — it silently returns another tenant's id. A cross-tenant data leak is a considerably worse outcome than an exception.

  @Service
  class ImportService {
      @Async
      public void importAsync(String tenantId, List<Row> rows) {
          rows.forEach(r -> save(tenantId, r));
      }
  }

  // caller, still on the request thread:
  @PostMapping("/import")
  void importRows(@RequestBody List<Row> rows) {
      importService.importAsync(ctx.getTenantId(), rows);
  }

Read the value while you are still on the request thread, and pass it as a parameter. This is not a workaround — it is the correct design. The async method's dependency on a tenant is now explicit in its signature instead of hidden in ambient thread state, which also makes it testable without any web context.

What I would not do: reach for context propagation machinery (TaskDecorator, Micrometer context propagation) as the first move. It is the right tool when you must propagate many values across many async boundaries — tracing context, for instance — but for one tenant id it adds a framework dependency to avoid adding a parameter.

Note this whole class of problem disappears and reappears differently under WebFlux, where one request is not one thread and request scope does not apply at all.

5 (hard): A service starts in 52 seconds. Its readiness probe has a 30-second timeout, so pods restart-loop. Plan the investigation and the fix.
Solution

Step 1 — measure per bean, do not guess.

  # enable startup tracking
  spring.main.cloud-platform=kubernetes
  management.endpoints.web.exposure.include=startup

  // in main()
  SpringApplication app = new SpringApplication(App.class);
  app.setApplicationStartup(new BufferingApplicationStartup(4096));
  app.run(args);

  # then
  curl localhost:8080/actuator/startup | jq '
    .timeline.events
    | sort_by(-.duration)
    | .[:15]
    | .[] | {name: .startupStep.name, tags: .startupStep.tags, ms: .duration}'

This attributes wall-clock time to individual bean initialisations. In every case I have seen, the distribution is extremely skewed — a handful of beans account for nearly all of it, and they are almost always doing I/O in @PostConstruct.

Step 2 — classify each offender.

Kind of workFix
Network call to fetch data (rates, flags, config)Move to ApplicationReadyEvent; add a client timeout; serve a documented degraded response until loaded
Bulk data load into memoryMove to ApplicationReadyEvent, or load lazily on first use with a warm-up trigger
Large file downloadBake into the image, or mount as a volume. It is not startup work at all
Genuinely expensive but rarely used bean@Lazy — this is its legitimate use
Slow auto-configuration or classpath scanningNarrow @ComponentScan; exclude unused auto-configurations

Step 3 — make readiness honest. Moving work off the startup path is only half the fix. If the pod reports ready before it can serve, you have traded a restart loop for a period of failed requests. A HealthIndicator that reports OUT_OF_SERVICE until warm means the load balancer holds traffic back, and the readiness probe measures readiness rather than process liveness.

Step 4 — fix the probe configuration too. Separate liveness from readiness: /actuator/health/liveness should only fail if the process is unrecoverable, while /actuator/health/readiness reflects warm-up. A single probe doing both is what turns a slow start into a kill. Add a startupProbe so Kubernetes allows a longer window at boot without loosening the steady-state timeouts.

Expected outcome, from a comparable case: 47s → 4.1s startup, rolling deploy 9 min → 90s, restart loop eliminated. Total warm-up time was unchanged — the work did not get faster, it stopped blocking.

What I would push back on: "just raise the probe timeout to 60s". It stops the restart loop and leaves every other consequence — nine-minute deploys, a 50-second local dev loop, and a service that still cannot start when a dependency is slow, which is precisely when you need it to.

6 (hard): Design graceful shutdown for a Spring Boot service on Kubernetes that serves HTTP, consumes from Kafka, and runs scheduled jobs. State what you cannot guarantee.
Solution

Three subsystems with different shutdown semantics, and the ordering between them matters.

  application.yml
    server:
      shutdown: graceful
    spring:
      lifecycle:
        timeout-per-shutdown-phase: 25s

  deployment.yaml
    terminationGracePeriodSeconds: 45      # MUST exceed 25s
    lifecycle:
      preStop:
        exec: { command: ["sh","-c","sleep 5"] }
SubsystemOn SIGTERMWhat to configure
HTTPStop accepting new connections, drain in-flightserver.shutdown=graceful. The preStop sleep covers the window where the ingress still routes here.
KafkaStop polling, commit offsets for processed records, leave the group cleanlySpring's KafkaListenerEndpointRegistry is a SmartLifecycle and stops automatically. Ensure max.poll.interval.ms is not longer than the grace period, and that offsets are committed after processing, not before.
Scheduled jobsNothing, by default — a running job is abandoned mid-flightsetWaitForTasksToCompleteOnShutdown(true) and an awaitTerminationSeconds below the grace budget.
  @Configuration
  class SchedulingConfig implements SchedulingConfigurer {
      @Bean(destroyMethod = "shutdown")
      ThreadPoolTaskScheduler taskScheduler() {
          var s = new ThreadPoolTaskScheduler();
          s.setPoolSize(4);
          s.setWaitForTasksToCompleteOnShutdown(true);
          s.setAwaitTerminationSeconds(20);      // < 25s phase timeout
          return s;
      }
      public void configureTasks(ScheduledTaskRegistrar r) {
          r.setTaskScheduler(taskScheduler());
      }
  }

The budget has to add up, and this is where most designs quietly break: 5s preStop + 25s Spring drain must be less than 45s terminationGracePeriodSeconds. If the numbers do not fit, SIGKILL arrives mid-drain and every one of these settings is decorative.

What I cannot guarantee, and must therefore design around:

  • SIGKILL happens. Node failure, OOM-kill, an exceeded grace period. No callback runs. Therefore Kafka processing must be idempotent — the same message will be redelivered after an abrupt death, and correctness cannot depend on the offset having been committed.
  • A scheduled job may be killed mid-execution. So a job holding a distributed lock needs a TTL on that lock, not just a release in a finally block. Otherwise one hard kill wedges the schedule until a human intervenes.
  • In-flight HTTP requests can still be lost if they exceed the drain window. A 25-second drain does not save a 40-second request; long operations should be asynchronous with a status endpoint rather than a held connection.
  • Deregistration and SIGTERM are concurrent, not ordered. The preStop sleep reduces the dropped-request window but does not eliminate it.

The principle: graceful shutdown is an optimisation that reduces errors in the common case. It is never a correctness mechanism. Every guarantee the system actually needs — no duplicate charges, no lost messages, no stuck locks — has to hold under kill -9, because kill -9 will happen. If a design only works when shutdown is graceful, it does not work.

🎯 Key Takeaways

  • Six phases: instantiate → populate → aware → initialise → ready → destroy. Almost every "why is this null?" is answered by knowing which phase you are in.
  • postProcessAfterInitialization can return a different object — the proxy. This is the mechanism behind every declarative feature in Spring.
  • @Value and @Autowired fields are null in the constructor. Take them as constructor parameters instead.
  • Spring singleton ≠ GoF Singleton. One per bean name per container — you can have two beans of one class, and two containers in one JVM.
  • Singleton beans are used concurrently by every request thread. Mutable fields are a silent data race, not a theoretical one.
  • SimpleDateFormat as a bean field is the classic version of that bug — use the immutable DateTimeFormatter.
  • A prototype injected into a singleton is injected once, so you get one instance forever. Use ObjectProvider.getObject().
  • Spring never calls @PreDestroy on a prototype bean — it keeps no reference. You own the cleanup.
  • Request scope is a ThreadLocal plus a proxy, so proxyMode is mandatory when injecting into a singleton.
  • Request scope breaks across @Async — and in a recycled pool thread it can silently return another request's data, which is worse than an exception.
  • Startup time and warm-up time are different things, and only one should block. Move slow work to ApplicationReadyEvent: 47s → 4.1s in the measured case.
  • Pair that with an honest HealthIndicator, or you trade a restart loop for a window of failed requests.
  • @PreDestroy never runs on SIGKILL, OOM-kill or a crash. Anything that must be cleaned up needs a TTL or an idempotent restart path.
  • terminationGracePeriodSeconds must exceed timeout-per-shutdown-phase, or graceful shutdown is purely decorative.
  • A preStop sleep is the standard remedy for the window where the ingress still routes to a pod that has begun shutting down.
  • @Lazy is right only for expensive, rarely-used beans. As a fix for cycles or slow startup it hides the problem and moves failures from CI to production.
  • ContextRefreshedEvent can fire more than once — use ApplicationReadyEvent for one-time work.
