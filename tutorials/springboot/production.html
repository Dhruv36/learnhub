Production & Deployment Production

What you'll master: what actually happens when a Spring Boot application is shipped — the executable jar's nested classloader and why layering it cut image pushes from 4m10s to 11 seconds; why ddl-auto in production is a data-loss mechanism, not a shortcut, and the Flyway checksum change that refused to start all 24 pods at 02:00; the migration nobody tests — an ALTER TABLE that took an ACCESS EXCLUSIVE lock and stalled every query for 4m38s; expand/contract, which is not a style preference but the only schema discipline compatible with a rolling deploy, because two versions of your code run simultaneously for several minutes; graceful shutdown, and the race that made a "graceful" deploy still drop 1,847 requests — Kubernetes removes an endpoint after it sends SIGTERM, not before; the JVM in a container, where a 1-CPU limit and -Xmx guesses cost either an OOMKill or 40% of the heap, and CFS throttling pushed p99 from 180 ms to 2.4 s at 34% average CPU; startup cost, from 47 s to 1.4 s via CDS and AOT, with the honest trade-offs of native images; and the deployment strategies that these constraints actually permit. Prerequisites: Configuration & Profiles, Actuator & Observability and Resilience & Microservices.

Part 1 — The Executable Jar Is Not an Ordinary Jar

  WHAT ./gradlew bootJar ACTUALLY PRODUCES

    app.jar
    |- META-INF/MANIFEST.MF
    |     Main-Class:       org.springframework.boot.loader.launch.JarLauncher
    |     Start-Class:      com.acme.OrderApplication      <-- YOURS
    |- org/springframework/boot/loader/...   the launcher itself
    |- BOOT-INF/classes/                     your compiled code
    |- BOOT-INF/lib/                         every dependency, as JARS
    |- BOOT-INF/classpath.idx                layer/order metadata

  java -jar app.jar does NOT run your main method first.
  It runs JarLauncher, which:
    1. builds a classloader that can read NESTED jars in place
       (the standard JDK classloader cannot -- jar-inside-jar is
       not a thing it supports)
    2. reads Start-Class from the manifest
    3. calls YOUR main() on a new thread with that classloader

  CONSEQUENCES PEOPLE HIT:
    - BOOT-INF/lib/*.jar are stored UNCOMPRESSED so they can be
      memory-mapped and read in place. The jar is bigger than the
      sum of its parts looks like it should be. That is deliberate.
    - Class-Path in the manifest is meaningless here.
    - java -cp app.jar com.acme.OrderApplication FAILS: the nested
      jars are invisible to the ordinary classloader. Use
      -Dloader.main or just -jar.
    - A library that scans the classpath with file:// assumptions
      may not find resources inside a nested jar. This is the usual
      cause of "works in the IDE, fails in the jar".

  LAYERED JARS -- the change that makes container builds fast

  A fat jar is ONE 62 MB file. Change one line of your code and
  every byte is new, so every deploy pushes 62 MB.

    bootJar { layered { enabled = true } }     # default in Boot 2.4+

  Four layers, ordered by how often they change:

    dependencies          released third-party jars     58 MB
    spring-boot-loader    the launcher                  0.3 MB
    snapshot-dependencies your own SNAPSHOT libs        2 MB
    application           YOUR classes and resources    1.7 MB

MEASURED: what layering is worth

  Unlayered fat jar in a single COPY:
    layers changed per deploy        1 of 1  (62 MB)
    docker push (CI to registry)     4m10s
    docker pull on 24 nodes          58 s each, staggered
    deploy wall-clock                6m40s

  Layered, one COPY per layer:
    layers changed per deploy        1 of 4  (1.7 MB)
    docker push                      11 s
    docker pull                      3 s (deps layer cached)
    deploy wall-clock                1m20s

  Same jar, same code. The only difference is that Docker can
  cache the 58 MB that did not change.
🔑 The layer order is the whole trick, and it is the same principle as any cache: put the stable things first. Dependencies change on a dependency bump — weekly at most; your classes change every commit. A COPY of everything in one step means Docker invalidates a 58 MB layer because you edited a controller. If you take one thing from this part, it is that a Dockerfile with a single COPY app.jar is silently costing you minutes on every deploy.

Part 2 — Migrations: ddl-auto Is a Data-Loss Mechanism

  WHAT EACH SETTING DOES, AND WHY ONLY ONE IS ACCEPTABLE

    create        DROP everything, recreate. Data gone. Every start.
    create-drop   Same, plus drop on shutdown.
    update        Add missing tables/columns. NEVER removes,
                  NEVER changes a type, NEVER adds an index you
                  wanted, and applies whatever the entity happens
                  to say -- differently per Hibernate version.
    validate      Compare entities to the schema, fail fast on
                  mismatch. SAFE, and useful.
    none          Do nothing.

  PRODUCTION: validate or none. Nothing else, ever.

  WHY "update" IS WORSE THAN IT LOOKS -- it is not that it is
  destructive (it is not); it is that it is UNDEFINED:
    - you cannot review it: there is no artefact to read
    - you cannot test it: the DDL depends on runtime state
    - you cannot repeat it: two environments drift silently
    - you cannot roll it back: nothing recorded what it did
    - it will not drop the column you renamed, so the old one
      lingers NOT NULL and every insert fails
    - it happens N times concurrently when N pods start

  FLYWAY: THE MECHANISM, NOT THE TUTORIAL

  src/main/resources/db/migration/
    V1__create_orders.sql
    V2__add_status_index.sql
    V3__add_customer_ref.sql
    R__order_summary_view.sql        # Repeatable, runs on change

  On startup Flyway:
    1. takes a LOCK on the history table (or a DB advisory lock)
    2. reads flyway_schema_history
    3. CHECKSUMS every applied script and compares
    4. applies pending versions in order, each in its own
       transaction where the database supports transactional DDL
    5. records version, checksum, duration, success

  flyway_schema_history
    installed_rank | version | description | checksum   | success
    1              | 1       | create orders| -1290384756| t
    2              | 2       | add status index| 88372910| t

  THE LOCK IS WHY 24 PODS STARTING TOGETHER IS SAFE: one wins,
  the rest wait, then find nothing pending. Safe -- but see the
  timeout problem below.

MEASURED: the checksum change that would not start

  A developer fixed a typo in a comment inside V7__add_index.sql,
  which had been applied in production three weeks earlier.

    02:00  deploy starts, rolling
    02:00  pod 1 boots
           FlywayValidateException: Migration checksum mismatch
           for version 7
           -> applicationContext fails -> exit code 1
    02:01  CrashLoopBackOff. Pod 2, 3, ... same.
    02:14  rollback attempted -- the OLD image has the OLD file,
           so the old pods start fine. Service restored.
    02:14  BUT: the new version cannot deploy at all until the
           file is restored byte-for-byte or the checksum is
           repaired.

  APPLIED MIGRATIONS ARE IMMUTABLE. Not by convention -- by
  mechanism. Flyway is protecting you from "this script ran, but
  not the version you are reading."

  IF IT HAPPENS: `flyway repair` rewrites the stored checksums to
  match the files. Correct only when you are certain the change
  was cosmetic. If the SQL itself changed, the environments have
  diverged and repair hides that.

MEASURED: the ALTER TABLE that stopped the site for 4m38s

  V12__add_country_to_orders.sql, on PostgreSQL, orders = 41M rows:

    ALTER TABLE orders ADD COLUMN country varchar(2) NOT NULL
                       DEFAULT 'US';

  On PG 11+ this is instant (the default is stored in the
  catalogue). On PG 10, it REWRITES THE WHOLE TABLE.
  This database was PG 10.

    17:42:11  migration starts, takes ACCESS EXCLUSIVE
    17:42:11  every SELECT on orders begins queueing behind it
    17:42:40  connection pool exhausted; requests time out
    17:43:20  liveness probes fail on pods still starting
    17:46:49  migration completes (4m38s)
    17:47:10  recovered

  WHAT MAKES DDL DANGEROUS IS THE LOCK, NOT THE DURATION.
  A 4-minute lock on a hot table is a 4-minute outage.

  THE RULES THAT FOLLOW:
    - know YOUR database version's behaviour: ADD COLUMN with a
      default, changing a type, adding NOT NULL -- all vary
    - CREATE INDEX CONCURRENTLY (and note it cannot run inside a
      transaction: Flyway needs the script marked accordingly)
    - add columns NULLABLE, backfill in batches, then constrain
    - a lock_timeout so a migration FAILS instead of queueing:
        SET lock_timeout = '3s';
    - long backfills belong in a batch job, not a migration
⚠️ Where migrations run is a real decision. Running Flyway inside the application on startup is simple and keeps schema and code in one artefact — but it means a slow migration delays every pod's readiness, and a failed one crash-loops the deployment. Running it as a separate Kubernetes Job or init container gives you one place to watch, a clean failure before any pod starts, and a migration timeout that is independent of your startup probe. The hybrid most teams land on is: migrations run as a pipeline step, and the application keeps ddl-auto: validate so it refuses to start against a schema it does not recognise.

Part 3 — Expand/Contract: Two Versions Run at Once

  THE FACT THAT DICTATES EVERYTHING

  A rolling deploy of 24 pods takes 3-6 minutes. During ALL of it,
  v1 and v2 are BOTH serving traffic, against ONE database.

    t=0    24 x v1
    t=90s  16 x v1, 8 x v2      <-- both must work
    t=4m   0 x v1, 24 x v2

  So any migration that is only valid for v2 breaks v1 while it is
  still serving. And any rollback puts v1 back against v2's
  schema.

  THE BREAKING CHANGE PEOPLE MAKE FIRST:

    V8__rename_column.sql
      ALTER TABLE orders RENAME COLUMN total TO total_amount;

    v1 pods:  SELECT total FROM orders    -> ERROR: column does
                                             not exist
    Every v1 pod starts 500ing INSTANTLY, and there are still 16
    of them. Rollback does not help: the column is gone.

  EXPAND / CONTRACT -- three deploys, never a broken state

  RELEASE 1 (EXPAND) -- add, never change
    ALTER TABLE orders ADD COLUMN total_amount numeric(12,2);
    -- backfill in batches
    UPDATE orders SET total_amount = total WHERE id BETWEEN ...;
    -- application writes BOTH columns, reads the OLD one
    v1 (old) still works: it only knows `total`, still populated
    v2 works: writes both

  RELEASE 2 (MIGRATE READS)
    -- application reads total_amount, still writes both
    rollback to release 1 is safe: both columns are current

  RELEASE 3 (CONTRACT)
    -- application stops writing `total`
    ALTER TABLE orders DROP COLUMN total;
    only safe once NOTHING deployed still reads it -- verify,
    do not assume

  THE COST IS HONEST: three deploys and a week or two of
  double-writing for one rename. That is the price of never
  having a broken minute, and on a hot table it is worth it.

  THE STEP EVERYONE SKIPS is release 3. Ship a ticket for the
  contract phase with the expand phase, or the schema accumulates
  dead columns nobody dares remove.
ChangeRolling-deploy safe?How to do it
Add a nullable columnYesStraightforward. Old code ignores it
Add a NOT NULL columnNoOld code's inserts omit it and fail. Add nullable with a default, backfill, constrain in a later release
Rename a columnNoExpand/contract: add, dual-write, migrate reads, drop
Drop a columnNoOnly after a release where nothing reads it — and verify with a query on pg_stat or logs, not memory
Change a column typeNoNew column, dual-write, migrate, drop. In-place type changes also rewrite the table

Add an enum valueYes to write, no to readOld code deserialising an unknown enum throws. Deploy the reader first, then start writing the value
Add a required request fieldNoSame problem one layer up — see REST API Design & Versioning

Part 4 — Graceful Shutdown, and the Race That Still Drops Requests

  WHAT SIGTERM DOES BY DEFAULT

    kill -TERM <pid>
      -> the JVM runs shutdown hooks
      -> Spring closes the context: @PreDestroy, DisposableBean,
         pools closed, executors shut down
      -> IN-FLIGHT HTTP REQUESTS ARE KILLED MID-RESPONSE

  Every request being served when the signal arrives gets a
  connection reset. At 250 req/s with a 400 ms p99, that is
  ~100 requests per pod, per deploy.

  TURN ON GRACEFUL SHUTDOWN -- one line, and it is not the default

    server:
      shutdown: graceful
    spring:
      lifecycle:
        timeout-per-shutdown-phase: 30s

  WHAT IT CHANGES:
    1. the connector stops ACCEPTING new connections
    2. in-flight requests are allowed to finish
    3. after they finish (or 30 s elapses) the context closes

  The timeout must exceed your slowest request or you have merely
  moved the cut-off. It must also be SHORTER than Kubernetes'
  terminationGracePeriodSeconds (default 30 s), or the kubelet
  sends SIGKILL while Spring is still draining -- and SIGKILL is
  exactly the ungraceful shutdown you were avoiding.

MEASURED: "graceful shutdown" that still dropped 1,847 requests

  server.shutdown: graceful was set. Deploys still produced a
  spike of 502s: ~77 per pod, 24 pods.

  THE CAUSE IS A RACE IN KUBERNETES, NOT IN SPRING:

  When a pod is deleted, TWO THINGS HAPPEN IN PARALLEL:
    (a) the kubelet sends SIGTERM to your container
    (b) the endpoints controller removes the pod from Endpoints,
        which then propagates to kube-proxy on every node, to
        iptables/IPVS rules, and to any ingress or service mesh

  (a) is immediate. (b) takes 1-5 SECONDS to propagate.

    T+0.00  SIGTERM delivered; Spring stops accepting connections
    T+0.00  the load balancer STILL SENDS TRAFFIC HERE
    T+0.30  new connections refused -> 502
    T+2.10  iptables rules updated on the last node
    T+2.10  traffic finally stops arriving

  Two seconds of traffic to a pod that already refused to accept
  it. That is the 502 spike, and no Spring setting fixes it
  because Spring did the right thing.

  THE FIX IS TO DELAY THE SIGTERM RESPONSE, NOT THE SIGNAL:

    lifecycle:
      preStop:
        exec: { command: ["sh","-c","sleep 5"] }
    terminationGracePeriodSeconds: 45

  preStop runs BEFORE SIGTERM is sent. The pod keeps serving
  normally for 5 seconds while endpoint removal propagates, THEN
  gets SIGTERM, THEN drains gracefully.

  RESULT: 1,847 dropped requests per deploy -> 0.

  Note the budget: terminationGracePeriod (45) must exceed
  preStop (5) + timeout-per-shutdown-phase (30) + slack.
🔑 The general shape of this bug is worth remembering beyond Kubernetes: shutdown is a distributed operation, and the signal to stop arrives before everyone has been told to stop sending you work. The same race exists behind any load balancer with a health-check interval — the balancer needs a full check cycle to notice, and your process needs to keep answering during it. A pod that starts failing readiness the instant it receives SIGTERM is not being safe; it is being unavailable while still receiving traffic. Keep serving, and let the routing catch up.
  WHAT ELSE MUST DRAIN -- the HTTP connector is the easy part

  @Async EXECUTORS         a queue with 4,000 pending tasks is
                           discarded silently at shutdown unless:
      executor.setWaitForTasksToCompleteOnShutdown(true);
      executor.setAwaitTerminationSeconds(20);
    Even then, a task submitted at T+0 with a 60 s runtime is cut
    off. Durable work belongs in a queue, not an executor (see
    Caching, Async & Scheduling).

  @Scheduled JOBS          a job that started 10 s ago is
                           interrupted mid-transaction; the next
                           pod may or may not repeat it. Jobs must
                           be idempotent and restartable.

  KAFKA CONSUMERS          must commit offsets before exiting or
                           the partition is reprocessed. Boot's
                           container does this on close; a manual
                           consumer thread does not.

  MESSAGE LISTENERS        stop accepting deliveries first, finish
                           the in-flight message, then close.

  DATABASE CONNECTIONS     HikariCP closes the pool; a transaction
                           still open at that point is rolled back
                           by the database when the socket drops.

  THE TEST: send SIGTERM under load and count non-2xx responses,
  orphaned rows and reprocessed messages. Everyone assumes this
  works. Almost nobody has measured it.

Part 5 — The JVM in a Container

  THE TWO NUMBERS THE JVM GETS WRONG, AND WHY

  Before JDK 8u191 the JVM read the HOST's memory and CPU count.
  A 4 GB container on a 256 GB node saw 256 GB and sized a 64 GB
  heap. Modern JVMs read cgroup limits (UseContainerSupport, on
  by default), so this is fixed -- but the DERIVED settings still
  surprise people.

  MEMORY: -Xmx IS NOT THE CONTAINER LIMIT

    container limit                          2048 MB
    -Xmx                                     1536 MB
    + metaspace                              ~140 MB
    + code cache (JIT)                       ~80 MB
    + thread stacks (200 x 1 MB)             ~200 MB
    + GC structures, symbol table            ~90 MB
    + direct/mapped byte buffers (Netty!)    ~100 MB
    ------------------------------------------------
    actual RSS                               ~2146 MB  -> OOMKilled

  THE HEAP IS NOT THE PROCESS. Non-heap is 25-40% of RSS in a
  typical Spring service, and the OOMKill has NO Java stack trace,
  no OutOfMemoryError, nothing in the logs -- just exit code 137
  and a pod restart, which is why it is so often misdiagnosed as
  "random crashes".

  USE A PERCENTAGE, NOT A GUESS:
    -XX:MaxRAMPercentage=70          # of the CGROUP limit
    -XX:InitialRAMPercentage=70      # avoid heap-growth pauses

  70-75% is the usual safe band. It also survives changing the
  container limit, which a hard-coded -Xmx does not: raise the
  pod to 4 GB with -Xmx1536m and you have bought 2.5 GB of
  nothing.

MEASURED: a CPU limit that cost 13x the latency

  Deployment: requests 500m, limits 1000m. 16-core nodes.

  WHAT THE JVM DID WITH IT:
    Runtime.availableProcessors()      1     (correct)
    but the pod was ALLOWED 100ms of CPU per 100ms period, and
    the JVM happily ran GC threads, JIT compiler threads and
    Tomcat workers concurrently across many cores.

  CFS THROTTLING is the mechanism: when the container uses its
  quota inside a 100 ms period, EVERY THREAD IS FROZEN until the
  next period begins.

    container_cpu_cfs_throttled_seconds_total  rising steadily
    average CPU utilisation                    34%
    p99 latency                                2.4 s
    p50 latency                                190 ms
    GC pauses reported by the JVM              12 ms
    actual stop-the-world wall time            up to 84 ms

  34% average utilisation WITH SEVERE THROTTLING is the signature:
  a burst of parallel work exhausts the quota in 30 ms, then
  everything sleeps for 70 ms. Averages hide it completely.

  THE FIX, in order of effect:
    1. raise or REMOVE the CPU limit (requests still guarantee
       the floor; limits mainly cause this)
    2. size thread pools to the CPU allocation, not the node:
         -XX:ActiveProcessorCount=2
         GC threads, ForkJoinPool.commonPool, Netty event loops
         and @Async defaults all derive from it
    3. p99 fell 2.4 s -> 180 ms after removing the limit
⚠️ CPU limits and memory limits are not symmetric, and treating them the same is the mistake. Exceeding a memory limit is fatal and instant — the kernel kills the process — so memory limits are non-negotiable. Exceeding a CPU limit merely means the kernel throttles you, and the JVM is unusually bad at being throttled, because a stop-the-world pause that gets frozen mid-pause stops the entire application for the rest of the CFS period. The common production posture is therefore: always set memory requests and limits equal, set CPU requests, and think hard before setting a CPU limit at all.
  STARTUP TIME -- what it costs and what actually reduces it

  A typical Spring Boot service, 250 beans, JPA + web + security:

    baseline                                        47.0 s  (!)
      of which: classpath scanning ~9 s, Hibernate
      metadata ~7 s, JIT warm-up dominating the rest

  MEASURES, MEASURED:

    -XX:TieredStopAtLevel=1 -noverify        47.0 -> 31.0 s
      (C1 only. Great for CLI/short-lived jobs; BAD for a
       long-running server -- you lose C2 and steady-state
       throughput drops ~30%)

    Class Data Sharing (AppCDS)              47.0 -> 28.4 s
      java -XX:ArchiveClassesAtExit=app.jsa -jar app.jar
      java -XX:SharedArchiveFile=app.jsa -jar app.jar
      Shares parsed class metadata; no runtime downside.

    Spring AOT processing (Boot 3)           47.0 -> 21.0 s
      bootBuildImage / processAot: bean definitions and proxies
      computed at BUILD time instead of at startup.

    GraalVM native image                     47.0 ->  1.4 s
      and RSS 1.2 GB -> 210 MB

  THE NATIVE-IMAGE TRADE-OFFS, HONESTLY:
    + 1.4 s start, tiny memory, ideal for scale-to-zero and
      serverless
    - build takes 6-9 MINUTES instead of 40 seconds
    - closed world: reflection, dynamic proxies, resource loading
      need hints; a library without them fails AT RUNTIME
    - peak throughput is LOWER (no JIT profiling): ~15-25% less
      on hot paths
    - a different runtime to debug, with different tooling

  WHEN IT IS WORTH IT: functions, CLIs, and services that scale to
  zero or run hundreds of replicas. For a steady-state service
  running 24 pods all day, AOT + CDS gets most of the startup win
  with none of the compatibility risk.

Part 6 — Deployment Strategies and the Readiness Checklist

StrategyHow it fails safeWhat it demands of you
Rolling (the Kubernetes default)Bad version rolls out gradually; a failing readiness probe halts the rollout automaticallyTwo versions run simultaneously — so expand/contract schemas and backwards-compatible APIs are mandatory, not optional
Blue/greenInstant switch, instant rollback by flipping traffic backDouble the capacity during the switch; the database is still shared, so the schema must satisfy both anyway
Canary1% of traffic sees the new version; you compare error rate and latency before proceedingTraffic splitting, per-version metrics, and an automated abort rule. Without the abort rule it is just a slow rolling deploy
Feature flagsDeploy is decoupled from release; disable the feature without a deployFlag hygiene — dead flags become permanent branching. Every flag needs a removal ticket
RecreateNothing overlaps, so no compatibility burdenFull downtime. Legitimate for internal batch services, never for user traffic
  THE VERSION SKEW NOBODY PLANS FOR

  Even with blue/green, the following run at the same time:
    - the OLD pods still draining (up to 45 s)
    - the NEW pods
    - a Kafka consumer group with members on BOTH versions
    - browser tabs holding a JS bundle from the PREVIOUS release
    - mobile clients on a version from three months ago
    - a scheduled job that started before the deploy

  So "backwards compatible for one release" is the MINIMUM.
  Mobile clients make it months. This is why message schemas need
  the same expand/contract discipline as database columns (see
  Messaging & Kafka), and why removing an API field is a
  multi-release project (see REST API Design & Versioning).

  THE RELEASE CHECKLIST -- the whole track, condensed

  CONFIGURATION
    [ ] no secrets in the image or in git; injected at runtime
    [ ] profiles per environment, no `if (env.equals("prod"))`
    [ ] @ConfigurationProperties validated at startup, so a bad
        value fails the boot rather than the 3 a.m. code path

  DATA
    [ ] ddl-auto: validate (or none)
    [ ] migrations reviewed for LOCKS, not just correctness
    [ ] expand/contract for anything that is not an addition
    [ ] connection pool sized from Little's Law, and
        hikaricp.connections.pending exported

  RESILIENCE
    [ ] every remote call: connect + read + pool timeouts
    [ ] one connection pool per downstream
    [ ] breakers with SLOW-CALL thresholds, not just failure rate
    [ ] retries only where idempotent, one layer, with jitter

  LIFECYCLE
    [ ] server.shutdown: graceful
    [ ] preStop sleep >= endpoint propagation time
    [ ] terminationGracePeriod > preStop + shutdown timeout
    [ ] async executors and consumers drain explicitly

  RUNTIME
    [ ] MaxRAMPercentage, not -Xmx
    [ ] memory requests == limits; CPU limit questioned
    [ ] ActiveProcessorCount matches the CPU allocation

  OBSERVABILITY
    [ ] separate liveness/readiness groups, startupProbe
    [ ] trace id propagated into logs and error responses
    [ ] alerts on symptoms (error rate, latency, throughput
        collapse), not on CPU

  SECURITY
    [ ] actuator on a separate port, explicit exposure list
    [ ] non-root user, read-only root filesystem
    [ ] dependency and image scanning in CI
🔑 The three items on that list that cause outages rather than merely inconvenience are the schema discipline, the timeouts, and the shutdown budget. Everything else degrades something; those three take a service down completely, and all three are invisible in a code review unless someone is specifically looking. If you introduce one review gate for this checklist, make it the migration file — it is the only artefact in a normal pull request that can lock a production table for four minutes.

Interview Questions

Beginner: What is inside a Spring Boot executable jar, and how does java -jar run it?

It is a normal jar with an unusual layout. BOOT-INF/classes holds your compiled code, BOOT-INF/lib holds every dependency as its own jar file, and the root contains Spring Boot's loader classes.

The manifest's Main-Class is not your application — it is JarLauncher. It builds a classloader that can read jars nested inside a jar, which the standard JDK classloader cannot do, then reads Start-Class from the manifest and invokes your main with that classloader.

Two practical consequences: the nested jars are stored uncompressed so they can be read in place, which is why the file is larger than you expect; and java -cp app.jar com.acme.App fails, because that path uses the ordinary classloader which cannot see them.

Beginner: Why should spring.jpa.hibernate.ddl-auto never be update in production?

Because it produces schema changes that nobody wrote, reviewed, or can reproduce. There is no artefact to read in a pull request, the generated DDL depends on the Hibernate version and on runtime state, and nothing records what it did, so two environments drift apart silently and there is nothing to roll back.

It is also incomplete in a way that breaks things: update only adds. It will not drop a column you renamed, so the old one stays behind — and if it was NOT NULL, every insert from the new code fails. It will not change a column type and it will not create the index you actually needed for performance.

Production should be validate, which compares the entities to the real schema and refuses to start on a mismatch, with a migration tool such as Flyway owning the schema. That gives you reviewable SQL, an ordered history with checksums, and a schema that is identical in every environment.

Mid: You enabled graceful shutdown and deploys still produce a spike of 502s. Why?

Because the dropped requests are not being cut off by Spring — they are arriving after Spring correctly stopped accepting them.

When a pod is deleted, Kubernetes does two things in parallel: the kubelet sends SIGTERM immediately, and the endpoints controller removes the pod from the Service, which then has to propagate to kube-proxy on every node and rewrite iptables or IPVS rules. The first is instant; the second takes one to five seconds. During that window the load balancer is still sending traffic to a pod that has already closed its connector, and every one of those requests is refused.

The fix is not a Spring setting, because Spring did the right thing. It is a preStop hook — sleep 5 — which runs before SIGTERM is sent, so the pod keeps serving normally while endpoint removal propagates, and only then begins draining. On the deployment I measured, that took 1,847 dropped requests per deploy to zero.

The budget has to line up too: terminationGracePeriodSeconds must exceed the preStop sleep plus spring.lifecycle.timeout-per-shutdown-phase, or the kubelet sends SIGKILL while Spring is still draining and you are back where you started.

Mid: Your pods are restarting with exit code 137 and nothing in the logs. Diagnose it.

Exit 137 is SIGKILL, and with no Java stack trace and no OutOfMemoryError it is almost always the kernel OOM killer acting on the container's memory limit. The JVM never saw it coming, which is exactly why there is nothing in the logs.

The usual cause is treating the heap as if it were the process. A 2 GB container with -Xmx1536m looks like it has 500 MB of headroom, but metaspace, the JIT code cache, two hundred 1 MB thread stacks, GC structures and direct byte buffers — Netty is a big consumer — add another 500–600 MB. Non-heap is routinely 25–40% of RSS in a Spring service.

I would confirm it by graphing container working-set memory next to JVM heap used: if heap is flat at 60% while the container ceiling is being touched, it is non-heap. Then I would switch from a hard-coded -Xmx to -XX:MaxRAMPercentage=70, which sizes from the cgroup limit and keeps working when someone changes the pod's memory. If direct memory is the culprit I would cap it explicitly with -XX:MaxDirectMemorySize so it fails as a Java error rather than an invisible kill.

The other possibility worth ruling out is a genuine heap leak that the JVM would eventually report but the kernel kills first. Enabling -XX:+HeapDumpOnOutOfMemoryError with the dump written to a mounted volume distinguishes the two cases.

Senior: Design a zero-downtime deployment for a service that needs to rename a database column.

The constraint that decides everything is that a rolling deploy runs two versions of the code against one database for several minutes. So there is no single deploy that renames a column safely — the old pods are still selecting the old name, and once it is gone they fail instantly. Rollback does not help, because the column no longer exists.

So it is three releases, expand then migrate then contract.

Release 1, expand. Add total_amount as a nullable column. Backfill it in batches from a job, not in the migration — a 41-million-row update inside a migration holds locks and blocks the deploy. The application writes both columns and still reads the old one. Old pods are unaffected because total is still current; new pods work too.

Release 2, migrate reads. The application reads total_amount and continues writing both. This release is fully reversible: both columns are up to date, so rolling back to release 1 is safe.

Release 3, contract. Stop writing total, then drop it — and only after verifying that nothing still reads it, which I would check against query logs rather than memory, because reporting jobs and analytics queries are the usual surprise.

Two things I would insist on. The migration review must look at locks, not just correctness: I have seen an ALTER TABLE ADD COLUMN NOT NULL DEFAULT rewrite a 41-million row table under ACCESS EXCLUSIVE and take the site down for four and a half minutes, because that database version did not have the metadata-only optimisation. A lock_timeout so the migration fails fast instead of queueing behind a long query is cheap insurance.

And the contract release needs a ticket created at the same time as the expand release. The step everyone skips is release 3, which is why mature schemas are full of columns nobody dares to remove.

If the column is on a hot path and the double-write period is uncomfortable, the alternative is a database view presenting the old name while the physical column is renamed — but that trades a temporary application complexity for a permanent schema indirection, and I would rather pay the three releases.

Senior: A service has p99 latency of 2.4 s but average CPU utilisation of 34%. What do you investigate?

The combination of high tail latency and low average utilisation is the signature of something stopping, not something slow, so I would look for pauses rather than for hot code.

First, CFS throttling, because in containers this is the most common cause and it is invisible in CPU averages. If the pod has a CPU limit, the kernel gives it a quota per 100 ms period, and when a burst of parallel work — GC threads, JIT compilation, a spike of requests — exhausts that quota, every thread freezes until the next period. The metric is container_cpu_cfs_throttled_seconds_total. I have seen exactly this: 34% average utilisation, p50 of 190 ms, p99 of 2.4 s, and removing the CPU limit brought p99 to 180 ms.

The mechanism is worth spelling out because it explains the paradox: throttling makes the JVM look idle, since a frozen thread consumes no CPU. Averaging over a minute hides a pattern of 30 ms of work and 70 ms of sleep.

Second, thread-pool sizing derived from the wrong CPU count. GC threads, the common ForkJoinPool, Netty event loops and @Async defaults all size from availableProcessors(). If that reports the node's cores rather than the allocation, the JVM creates far more parallel work than the quota permits, which causes the throttling in the first place. -XX:ActiveProcessorCount pins it.

Third, if throttling is ruled out: blocking, not computing. Low CPU with high tail latency also means threads waiting — on a connection pool, on a downstream call, on a lock. I would look at hikaricp.connections.pending first, because pool starvation shows up there before it shows up in query latency, and then at per-dependency client timers.

Fourth, GC. Worth checking, but note that the JVM's own reported pause times can understate the truth under throttling — a stop-the-world pause that gets frozen mid-pause stops the application for the remainder of the CFS period, and the JVM does not count the frozen time as its own.

What I would not do first is profile the application code. A 13× gap between p50 and p99 with a third of the CPU idle is an infrastructure or contention problem; profiling would show a flat, unremarkable flame graph and waste a day.

The signal-forwarding point is the one that bites hardest, because it silently disables everything from Part 4. In shell form the JVM is not PID 1, SIGTERM goes to the shell, and the container is killed after the grace period expires. Exec form (ENTRYPOINT ["java", ...]) makes the JVM PID 1 and gives it the signal directly.

The layer order matters and is not arbitrary: dependencies first because they change rarely, application last because it changes every commit. Reversing them gives you a layered image with none of the caching benefit.

2 (easy): A deploy at 02:00 put every pod into CrashLoopBackOff with FlywayValidateException: Migration checksum mismatch for version 7. What happened, and what do you do now?
Solution

What happened: the file V7__...sql in the new build no longer matches the checksum Flyway recorded when that migration was applied weeks ago. Someone edited an applied migration — very often a comment, a reformat, or a line-ending change from a different editor. Flyway refuses to start because it can no longer prove that the schema you have is the schema that script describes.

Right now, at 02:00: roll back to the previous image. The old build contains the original file, so its checksum matches and the pods start. Service is restored in a couple of minutes and the fix happens with people awake.

Then, depending on what actually changedAction
Only a comment, whitespace, or line endingsRestore the file byte-for-byte and redeploy, or run flyway repair to rewrite the stored checksum. Both are safe because the applied SQL is unchanged
The SQL itself was changedDo not repair. Production has the old DDL and any freshly-created environment would get the new one — they have diverged. Restore the original file and add V8 with the intended change

How to prevent it: a CI check that fails when a file under db/migration is modified rather than added — a three-line git diff --diff-filter=M in the pipeline. That catches it in the pull request instead of at two in the morning.

The deeper point is that this is Flyway working correctly. The alternative — silently accepting an edited script — is how environments drift apart in ways nobody discovers until a migration months later fails on one environment and succeeds on another.

3 (medium): Every deploy produces a spike of 502s and a handful of truncated responses. Fix it end to end. 
  # application.yml -- nothing about shutdown
  # deployment.yaml
  spec:
    terminationGracePeriodSeconds: 30
    containers:
      - name: api
        readinessProbe:
          httpGet: { path: /actuator/health/readiness, port: 8081 }
          periodSeconds: 5
Solution

There are two separate defects producing two different symptoms, and fixing only one leaves the other.

SymptomCause
Truncated responsesNo graceful shutdown. SIGTERM closes the context immediately and every in-flight request is cut mid-response
502sThe endpoint-removal race: SIGTERM arrives instantly, but removing the pod from the Service takes 1–5 s to reach every node's iptables rules. Traffic keeps arriving at a pod that has stopped accepting connections
  # application.yml
  server:
    shutdown: graceful
  spring:
    lifecycle:
      timeout-per-shutdown-phase: 25s     # > slowest request

  # deployment.yaml
  spec:
    terminationGracePeriodSeconds: 45     # > 5 preStop + 25 drain
    containers:
      - name: api
        lifecycle:
          preStop:
            exec: { command: ["sh","-c","sleep 5"] }

The sequence that results: the pod is marked Terminating and preStop starts; for five seconds the pod serves traffic completely normally while endpoint removal propagates; SIGTERM is then delivered; Tomcat stops accepting new connections and finishes what is in flight; the context closes; the container exits — all inside the 45 s grace period.

The budget arithmetic is the part to get right: 5 s preStop + 25 s drain = 30 s, leaving 15 s of slack before the kubelet sends SIGKILL. Set the grace period to 30 and a slow request at the end of the drain is killed by SIGKILL — which is the exact failure you were fixing.

What I would not do is make the readiness probe fail on SIGTERM. It is a common suggestion and it is too slow: with a 5 s period plus propagation, the pod is still receiving traffic for several seconds, and meanwhile it has told the cluster it is unhealthy. The preStop sleep is simpler and strictly better.

To verify rather than assume: run a load generator at production-like rate, delete a pod, and count non-2xx responses. The measured case here went from 1,847 dropped requests per deploy to zero, and the only way to know which of the two fixes mattered is to test them separately.

4 (medium): Make this migration safe to run against a 40-million-row table during a rolling deploy. 
  V14__orders_add_channel.sql

    ALTER TABLE orders ADD COLUMN channel varchar(16) NOT NULL
                       DEFAULT 'WEB';
    CREATE INDEX idx_orders_channel ON orders(channel);
    UPDATE orders SET channel = 'MOBILE'
      WHERE user_agent LIKE '%Mobile%';
Solution
StatementProblem
ADD COLUMN NOT NULL DEFAULTMetadata-only on PostgreSQL 11+ and MySQL 8 with INSTANT, but a full table rewrite under ACCESS EXCLUSIVE on older versions. Version-dependent behaviour is not something to guess at
NOT NULL at allOld pods are still inserting orders without a channel. With a default they survive; without one every insert fails for the whole rollout
CREATE INDEXLocks the table against writes for the duration — minutes on 40M rows
The UPDATERewrites millions of rows in one transaction: a huge lock footprint, enormous WAL, replication lag, and it blocks the deploy while it runs
  -- V14__orders_add_channel.sql   (structure only, fast)
  SET lock_timeout = '3s';
  ALTER TABLE orders ADD COLUMN channel varchar(16);   -- nullable

  -- V15__orders_channel_index.sql
  -- flyway: executeInTransaction=false
  CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_channel
    ON orders(channel);

  -- backfill: a JOB, not a migration
  --   UPDATE orders SET channel = ... WHERE id BETWEEN ? AND ?
  --   10,000 rows per batch, commit each, brief pause between
  --   restartable, and it can be paused if replication lags

  -- LATER RELEASE, once the backfill is complete and every
  -- deployed version writes the column:
  --   ALTER TABLE orders ALTER COLUMN channel SET DEFAULT 'WEB';
  --   ALTER TABLE orders ALTER COLUMN channel SET NOT NULL;

lock_timeout is the cheapest safety measure here. Without it, a migration that cannot get its lock immediately queues — and in PostgreSQL a queued ACCESS EXCLUSIVE request blocks every subsequent reader behind it, so one long-running SELECT turns a fast migration into a full outage. With it, the migration simply fails and you retry.

Why the backfill belongs outside: a migration is a gate on your deploy. A batched job is restartable, observable, throttleable, and can be paused when replication lag rises — none of which is true of an UPDATE inside V14.

Note SET NOT NULL is deferred to a later release, and even then it scans the table to verify. On PostgreSQL 12+ you can avoid the long lock by adding a NOT VALID check constraint, validating it concurrently, and then setting NOT NULL — which is worth knowing exists, and worth skipping unless the table is genuinely too hot for a brief scan.

5 (hard): Size the container and JVM for a service handling 300 req/s with a p99 of 250 ms, and justify every number.
Solution 
  STEP 1 -- CONCURRENCY, from Little's Law
    threads in flight = 300 req/s x 0.25 s = 75

    server.tomcat.threads.max: 150          # 2x headroom
    server.tomcat.accept-count: 100
    server.tomcat.threads.min-spare: 25

  STEP 2 -- CONNECTION POOL, from the DB portion of the work
    DB time per request ~40 ms -> 300 x 0.04 = 12 concurrent
    spring.datasource.hikari.maximum-pool-size: 20
    (NOT 150. A pool sized to the thread count moves the queue
     into the database, where it is far more expensive.)

  STEP 3 -- MEMORY, bottom up
    heap: working set measured after warm-up      ~900 MB
      (live set after a forced full GC x 2.5)
    metaspace                                     ~140 MB
    code cache                                     ~80 MB
    thread stacks 150 x 1 MB                      ~150 MB
    GC + symbol tables + direct buffers           ~200 MB
    ------------------------------------------------------
    total                                        ~1470 MB
    container limit                               2048 MB
    -XX:MaxRAMPercentage=70  -> heap 1434 MB      fits, with room

  STEP 4 -- CPU
    measured: 0.8 cores at 300 req/s in load test
    requests: 1000m        # the guaranteed floor
    limits:   none         # avoid CFS throttling entirely
    -XX:ActiveProcessorCount=2   # pin derived pool sizes
DecisionJustification
Threads 150, not 500More threads than the work needs adds context switching and memory without adding throughput. At 75 in flight, 150 is headroom for a latency excursion, not a plan for one
Pool 20, not 150A database has a concurrency sweet spot far below the app's thread count. Queueing in the pool with a 250 ms acquisition timeout fails fast; queueing in the database degrades every query
MaxRAMPercentage, not -XmxSurvives a change to the container limit, which a hard-coded value silently does not
Memory requests == limitsGuarantees the QoS class and makes the OOM behaviour predictable
No CPU limitThrottling freezes all threads mid-work; the request already guarantees the floor. This is the setting most likely to be argued about, and the measured p99 difference was 2.4 s versus 180 ms
ActiveProcessorCountGC threads, ForkJoinPool, Netty loops and @Async defaults all derive from it — left unpinned they size to the node, not the allocation

The number I would be least confident in is the heap, and I would say so. "Live set × 2.5" is a starting heuristic; the real figure comes from running the load test for an hour and watching the post-GC live set, because a service with a large cache or big request payloads behaves nothing like one without. I would deploy with the estimate, then tighten it from production data rather than defending a spreadsheet.

What I would set up alongside it: alerts on container working-set memory (not heap — the OOMKill comes from RSS), on hikaricp.connections.pending, and on cfs_throttled_seconds in case someone adds a CPU limit later. Sizing is a hypothesis; those three metrics are how you find out you were wrong before a customer does.

6 (hard): A service takes 47 seconds to start. It runs 24 pods, scales during peaks, and deploys four times a day. What do you do, and what do you decline to do?
Solution

First, decide whether it matters, because that determines how much this is worth. Four deploys a day across 24 pods is not the expensive part — rolling deploys overlap. The costs that actually hurt are: autoscaling cannot respond to a spike for 47 s, so scale-up is useless for anything shorter than a minute; a crash-loop takes 47 s per cycle to diagnose; and the liveness probe needs a startup window generous enough to cover it, which weakens the probe unless a startupProbe is used.

Then measure where the time goes, because guessing here is expensive. Boot's own ApplicationStartup instrumentation, or simply -Dspring.context.checkpoint plus a debug log of bean initialisation times, will usually show three culprits: classpath scanning, Hibernate metadata building, and JIT warm-up.

DoEffectCost
Narrow component scanning; remove unused startersOften several seconds, occasionally most of the problem — an unused starter can auto-configure an entire subsystemA morning, and it usually shrinks the image too
startupProbe with a generous failureThresholdFixes the probe weakening immediately, whatever else you doFour lines of YAML. Do this first
AppCDS47 s → 28 s measured, and no runtime downsideAn extra build step producing the archive, and it must be regenerated per build
Spring AOT (Boot 3)47 s → 21 s: bean definitions and proxies computed at build timeLonger builds; some dynamic configuration patterns stop working and must be made static
Lazy initialisation for genuinely rare beansSeconds, sometimesUse sparingly — it moves failures from startup to the first request, which trades a fast, obvious failure for a slow, customer-facing one

What I would decline: a GraalVM native image. It is the dramatic answer — 1.4 s and 210 MB — and it is the wrong trade here. Builds go from 40 s to 6–9 minutes, which taxes every one of those four daily deploys; the closed-world assumption means reflection and dynamic proxies need hints, and a library without them fails at runtime rather than at build time; and peak throughput drops 15–25% without JIT profiling, which matters for a service that runs all day. Native images earn their cost when instances are short-lived or scale to zero. Twenty-four long-running pods are the opposite case.

What I would also decline: -XX:TieredStopAtLevel=1. It genuinely cuts startup to 31 s, and it costs roughly 30% of steady-state throughput because C2 never compiles anything. That is an excellent trade for a CLI or a short-lived job and a bad one for a server.

The order I would actually ship in: startupProbe today, scanning and unused starters this week, CDS next, and AOT only if the remaining number still blocks autoscaling. Each step is independently useful and none of them changes the runtime you debug — which is the property that makes them safe to do four times a day.

🎯 Key Takeaways

  • The executable jar is launched by JarLauncher, not your main — a custom classloader is what makes nested jars readable, and why java -cp app.jar fails.
  • Layer the jar. One COPY invalidates 62 MB on every commit; four layers took pushes from 4m10s to 11 s and deploys from 6m40s to 1m20s.
  • ddl-auto: update is unreviewable, unrepeatable and incomplete. Production is validate, with Flyway owning the schema.
  • Applied migrations are immutable by mechanism. A comment edit failed the checksum and crash-looped 24 pods at 02:00.
  • Review migrations for locks, not correctness. One ALTER TABLE held ACCESS EXCLUSIVE for 4m38s on 41M rows — a full outage from a three-line file.
  • Set lock_timeout so a migration fails fast instead of queueing and blocking every reader behind it.
  • A rolling deploy runs two versions against one database for minutes. That single fact makes expand/contract mandatory, not stylistic.
  • Add nullable, backfill in a job, constrain later. Backfills inside migrations block the deploy and hold locks.
  • The step everyone skips is contract — file the drop ticket with the expand release.
  • server.shutdown: graceful is not the default, and without it every in-flight request is cut mid-response on every deploy.
  • Kubernetes sends SIGTERM before endpoint removal propagates. A preStop: sleep 5 took 1,847 dropped requests per deploy to zero.
  • Budget the shutdown: terminationGracePeriod > preStop + shutdown-phase timeout, or SIGKILL undoes the graceful drain.
  • Async executors, scheduled jobs and consumers must drain explicitly — queued tasks are discarded silently otherwise.
  • The heap is not the process. Non-heap is 25–40% of RSS; the OOMKill is exit 137 with no stack trace and no log line.
  • Use -XX:MaxRAMPercentage, not -Xmx, so sizing follows the container limit instead of contradicting it.
  • CPU limits cause CFS throttling, which freezes every thread. p99 was 2.4 s at 34% average CPU; removing the limit gave 180 ms.
  • Pin ActiveProcessorCount — GC threads, ForkJoinPool, Netty loops and @Async all size from it.
  • Startup: CDS 47→28 s, AOT 47→21 s, native 47→1.4 s — and native costs 6–9 minute builds, reflection hints and 15–25% of peak throughput.
  • Exec-form ENTRYPOINT or SIGTERM never reaches the JVM, silently disabling every graceful-shutdown setting you configured.
