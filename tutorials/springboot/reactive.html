Reactive Spring & WebFlux Event-Driven

What you'll master: the problem reactive programming actually solves — a blocked thread costs about 1 MB of stack and answers nobody, so 10,000 slow connections need 10,000 threads under thread-per-request and four under an event loop; and the part that gets left out of the pitch — reactive does not make a single request faster, it raises the concurrency ceiling, and the measured p99 at low load was worse; why virtual threads now take most of the reason to rewrite anything, and the cases they do not cover; nothing happens until you subscribe — the bug that silently discarded 4,100 saves with no error anywhere; flatMap's default concurrency of 256, which turned one request into 256 simultaneous downstream calls; the single blocking JDBC call that took p99 from 90 ms to 6.4 s because it froze one of four event-loop threads; why try/catch and ThreadLocal both stop working — losing the trace id from every log line and, worse, leaking one user's SecurityContext into another's request; backpressure as a real protocol rather than a slogan, and the unbounded buffer that OOM'd in 40 seconds; and the honest cost, which is that a stack trace stops telling you where anything went wrong. Prerequisites: Caching, Async & Scheduling, Resilience & Microservices and Spring Data JPA.

Part 1 — The Problem It Solves, and the One It Does Not

  THREAD-PER-REQUEST, PRECISELY

    Tomcat: 200 threads. Each request owns one for its whole life.

    request arrives -> take a thread
      call pricing (40 ms)      thread BLOCKED, doing nothing
      query the database (8 ms) thread BLOCKED, doing nothing
      serialise (1 ms)          thread working
    release the thread

    Of 49 ms, the thread did ~1 ms of work and spent 48 ms
    holding memory while waiting for someone else.

  WHAT A BLOCKED THREAD COSTS:
    stack                 ~1 MB reserved (default -Xss)
    kernel scheduling     a context switch is ~1-3 us, and with
                          thousands of threads the scheduler
                          itself becomes measurable
    GC roots              every thread stack is scanned

  So the ceiling is not CPU. It is THREADS. At 200 threads and
  50 ms of latency you can serve 4,000 req/s -- and if latency
  rises to 500 ms, 400 req/s, with the CPU still idle. That is
  the Little's Law failure from the Resilience lesson.

  THE EVENT LOOP INSTEAD

    4 event-loop threads (one per core, typically)

    request arrives -> loop thread starts it
      call pricing        -> REGISTER A CALLBACK, RELEASE THE
                             THREAD, go serve someone else
      (40 ms later) response bytes arrive -> a loop thread picks
                             the continuation up
      ...
    No thread is ever blocked waiting for I/O.

  THE TRADE IS EXPLICIT: you give up a linear call stack -- the
  thing that makes stack traces, ThreadLocal, try/catch and
  step-debugging work -- and you get concurrency that is bounded
  by memory and sockets rather than by threads.

MEASURED: the same service, MVC vs WebFlux

  Endpoint: calls one downstream (p99 500 ms), returns 2 KB.
  4 vCPU, 2 GB container.

  10,000 CONCURRENT CONNECTIONS
                          Spring MVC        WebFlux
    threads               200 (max)         4 event loop + 8
    memory (RSS)          1.9 GB            420 MB
    throughput            ~380 req/s        ~9,700 req/s
    p99                   14.2 s            580 ms
    errors                timeouts, refused none
                          connections

  200 CONCURRENT CONNECTIONS -- the load most services actually see
                          Spring MVC        WebFlux
    throughput            ~390 req/s        ~395 req/s
    p99                   520 ms            545 ms
    memory                640 MB            390 MB
    CPU                   38%               41%

  READ THE SECOND TABLE AGAIN. At ordinary concurrency the
  reactive version is NOT faster -- it is marginally SLOWER on
  p99, because operator assembly and scheduler hand-offs add
  overhead that blocking code does not pay.

  REACTIVE DOES NOT REDUCE LATENCY. It removes the thread
  ceiling. If you are not near that ceiling, it buys memory and
  nothing else.
⚠️ Virtual threads changed this decision more than any framework release. On Java 21 with spring.threads.virtual.enabled: true, a blocking Spring MVC application gets a thread per request that costs a few hundred bytes instead of a megabyte and parks without holding a carrier thread — so the same 10,000-connection test lands close to the WebFlux numbers with ordinary blocking code, an ordinary stack trace, ordinary ThreadLocal, and JPA. If the reason you are considering WebFlux is "we need to handle many concurrent slow requests", try virtual threads first: it is a configuration flag, not a rewrite. What virtual threads do not give you is backpressure, streaming semantics, or a composition model for fan-out — which is what the rest of this lesson is really about.

Part 2 — Nothing Happens Until You Subscribe

  A Mono/Flux IS A RECIPE, NOT A RESULT.

    Mono<Order> m = repo.save(order);      // NOTHING HAS HAPPENED
                                            // no database call,
                                            // no row, nothing

  Building the chain is ASSEMBLY TIME. The work starts at
  SUBSCRIPTION TIME, when something subscribes:

    - returning it from a @RestController method (WebFlux
      subscribes for you)
    - .subscribe() explicitly
    - .block() (which subscribes and waits -- see Part 3)

  If nobody subscribes, NOTHING RUNS -- and nothing complains.

MEASURED: 4,100 saves that never happened

  Inside a listener that was itself blocking:

    public void handle(OrderEvent e) {
        Order o = map(e);
        repo.save(o);              // returns Mono, DISCARDED
        auditRepo.save(audit(e));  // returns Mono, DISCARDED
        log.info("saved order {}", o.getId());   // logs happily
    }

    orders processed per the log        4,100
    rows in the database                    0
    errors, warnings, failed health checks  0
    time to notice                     2 days, via a report

  The compiler is fine with it. The linter is fine with it. The
  log says "saved". This is the single most common reactive bug
  and it fails in the quietest possible way.

  DEFENCES:
    - never call a reactive method from non-reactive code without
      an explicit terminal operation
    - IDE inspection "Reactive Streams result unused" -- turn it
      on and make it an ERROR
    - ArchUnit/errorprone rule: a method returning Publisher must
      have its result used

  THE OPERATORS THAT MATTER, AND THE ONES THAT SURPRISE

  map          synchronous transform, 1-to-1
                 flux.map(o -> toDto(o))

  flatMap      ASYNCHRONOUS transform, 1-to-many, INTERLEAVED
                 flux.flatMap(o -> enrich(o))     // order LOST
               Default concurrency: 256 inner subscriptions AT
               ONCE. This is the number that surprises people.

  concatMap    asynchronous, ORDERED, one at a time
                 the sequential, safe version of flatMap

  flatMapSequential  runs concurrently, EMITS in order
                     (buffers, so watch memory)

  zip          combine several sources when all have emitted
  then/thenReturn    sequence without using the value

MEASURED: flatMap's default hammered a downstream

  A batch endpoint enriched 5,000 ids:

    Flux.fromIterable(ids)
        .flatMap(id -> pricingClient.get(id))    // 256 at once
        .collectList();

  ONE request produced 256 concurrent HTTP calls to pricing.
  Ten such requests: 2,560 concurrent calls.

    pricing p99            40 ms  ->  8.7 s
    pricing error rate     0%     ->  31% (its pool exhausted)
    the batch endpoint     "worked", so nobody suspected it

  THE FIX IS THE SECOND ARGUMENT, and it should be deliberate
  every single time:

    .flatMap(id -> pricingClient.get(id), 8)     // 8 concurrent

  Reactive removes the thread limit that used to bound your
  concurrency accidentally. Nothing replaces it unless you set
  it. This is the reactive version of the bulkhead lesson, and
  the number belongs in code review.

  ERROR HANDLING: try/catch CATCHES NOTHING

    try {
        return service.findOrder(id)         // returns a Mono
                      .map(this::toDto);
    } catch (NotFoundException e) {          // NEVER RUNS
        return Mono.error(new ApiException());
    }

  Assembly happens inside the try; the actual work happens after
  it returns. The exception travels through the pipeline as an
  ERROR SIGNAL, not as a thrown exception.

  THE REACTIVE EQUIVALENTS:

    .onErrorMap(NotFound.class, e -> new ApiException(e))
        translate one error to another

    .onErrorResume(e -> Mono.just(fallbackValue))
        substitute a fallback stream -- the reactive fallback
        from the Resilience lesson

    .onErrorReturn(Order.EMPTY)
        a constant fallback

    .doOnError(e -> log.error("failed", e))
        a SIDE EFFECT ONLY -- it does not handle anything, and
        the error continues downstream. Frequently mistaken for
        a handler.

    .retryWhen(Retry.backoff(3, Duration.ofMillis(200))
                    .jitter(0.5))
        retries WITH JITTER -- and every caveat from the
        Resilience lesson applies: only for idempotent work

  AND THE EMPTY-VS-ERROR DISTINCTION, which has no blocking
  analogue: Mono.empty() completes with NO value. It is not an
  error, so onErrorResume never fires; use switchIfEmpty for
  "not found".
🔑 The mental shift that makes the rest easy: you are not writing code that runs, you are building a description of work that will run later, somewhere else, on a thread you did not pick. Every confusing reactive bug — the silent no-op, the try/catch that never fires, the missing trace id, the ThreadLocal that is empty — is the same fact in a different costume. Once you read a chain as a value being constructed rather than statements being executed, the failures stop being surprising.

Part 3 — One Blocking Call Ruins the Whole Server

  THE ARITHMETIC THAT MAKES THIS SO SEVERE

    Tomcat, 200 threads: one slow request occupies 1/200th of
    your capacity.

    Netty, 4 event-loop threads: one BLOCKED call occupies
    1/4 OF THE ENTIRE SERVER, and every other request already
    assigned to that loop waits behind it.

MEASURED: one JDBC call in a WebFlux service

  A "small" repository was left on JDBC during a migration:

    public Mono<Order> find(Long id) {
        return Mono.just(jdbcTemplate.queryForObject(...));
        //              ^^ blocking, ON THE EVENT LOOP
    }

    query time                       12 ms (fast!)
    load                             1,200 req/s
    event loop threads               4

    p99 before                       90 ms
    p99 after                        6,400 ms
    throughput ceiling               ~330 req/s
    CPU                              22%

  12 ms of blocking, at 1,200 req/s, on 4 threads is 3.6 seconds
  of blocking demand per second of wall clock. The loops
  saturate, and EVERY endpoint degrades -- including the ones
  that never touch the database, because they share the loops.

  In the blocking model the same code was invisible. In the
  reactive model it is an outage.

  FIND THEM MECHANICALLY -- BlockHound, in tests:

    testImplementation 'io.projectreactor.tools:blockhound-junit-platform'

  It instruments the JVM and throws when blocking code runs on a
  non-blocking thread. It is the only reliable way to keep a
  reactive codebase honest, because a blocking call added in an
  unrelated PR has no visible symptom until production.

  SCHEDULERS: WHERE WORK RUNS

    Schedulers.parallel()       fixed pool, ~one per core.
                                CPU-bound work only.
    Schedulers.boundedElastic() elastic pool, capped at
                                10 x cores by default, with a
                                queue. FOR BLOCKING CALLS.
    Schedulers.immediate()      the current thread.

  publishOn    changes the thread for everything DOWNSTREAM
  subscribeOn  changes the thread the SOURCE subscribes on --
               it affects upstream, and only the first
               subscribeOn in a chain wins

    Mono.fromCallable(() -> jdbcTemplate.query(...))  // blocking
        .subscribeOn(Schedulers.boundedElastic())     // moved off
        .map(this::toDto)                             // loop
⚠️ boundedElastic makes a blocking call safe; it does not make it scalable. The work still needs one thread for its whole duration, so you are back to thread-per-request — with an extra hand-off, worse cache locality, and a pool cap of 10 × cores that is easy to exhaust. A WebFlux service whose repository layer is JDBC wrapped in boundedElastic has all of reactive's debugging cost and none of its concurrency benefit. That configuration is worth recognising quickly, because it is extremely common in half-finished migrations, and the honest answer is usually to go back to Spring MVC with virtual threads.
  R2DBC -- non-blocking database access, and what it costs

    interface OrderRepository extends ReactiveCrudRepository<Order, Long> {
        Flux<Order> findByStatus(String status);
    }

  + genuinely non-blocking, so the event loop stays free
  + backpressure reaches the database: a slow consumer means
    fewer rows fetched, not a full buffer

  WHAT YOU GIVE UP -- and it is a lot:
    - NO JPA. No entity manager, no persistence context, no
      dirty checking, no lazy loading, no @OneToMany traversal.
      R2DBC is closer to JdbcTemplate with a mapper.
    - relationships are YOUR job: a second query and a join in
      code. The N+1 lesson applies with no fetch joins to save
      you.
    - no second-level cache, no @Version convenience, fewer
      drivers, thinner ecosystem
    - transactions work (TransactionalOperator, or @Transactional
      with a ReactiveTransactionManager) but the semantics and
      the tooling are less mature

  So the cost of an end-to-end reactive stack is usually
  "rewrite the persistence layer without an ORM". That is the
  real budget line, not the controllers.

Part 4 — ThreadLocal Is Gone, and What Broke With It

  THE ASSUMPTION THAT NO LONGER HOLDS

    Blocking: one request = one thread, start to finish.
              So "state attached to the thread" == "state
              attached to the request". ThreadLocal works.

    Reactive: one request touches SEVERAL threads; one thread
              serves THOUSANDS of requests, interleaved.
              ThreadLocal is meaningless at best -- and at
              worst, it is a data leak.

  WHAT DEPENDS ON ThreadLocal AND THEREFORE BREAKS:

    MDC (logging context)      traceId, userId in every log line
    SecurityContextHolder      the authenticated principal
    TransactionSynchronization the JDBC transaction
    RequestContextHolder       the current HttpServletRequest
    Locale/timezone context    resolved per request

MEASURED: two failures from the same cause

  (a) THE TRACE ID DISAPPEARED

    A team migrated one service to WebFlux. Log lines went from

      2026-03-11 [orders,4bf9a1,ab12] Charging order 8891

    to

      2026-03-11 [orders,,] Charging order 8891

    Nobody noticed for six weeks -- until an incident, when the
    trace-id search that works for every other service returned
    nothing for this one, and diagnosis took 3h40m instead of
    the usual minutes.

  (b) THE SECURITY CONTEXT LEAKED -- much worse

    Custom code that copied the principal into a ThreadLocal
    "for convenience" inside a reactive chain:

      request A on loop-2  -> sets principal = alice
      request A awaits I/O -> loop-2 picks up request B
      request B reads the ThreadLocal   -> SEES ALICE

    In a load test this produced cross-user data in 0.4% of
    responses. In production it would be a breach.

  THE RULE: in reactive code, request state lives in the
  REACTOR CONTEXT, which travels with the subscription, not
  with the thread.

  THE REACTOR CONTEXT -- immutable, and it flows UPSTREAM

    // writing (at the end of the chain, counter-intuitively)
    return orderService.place(cmd)
             .contextWrite(Context.of("traceId", traceId));

    // reading, anywhere upstream
    Mono.deferContextual(ctx -> {
        String traceId = ctx.get("traceId");
        return doWork(traceId);
    });

  contextWrite affects operators ABOVE it in the chain, because
  the subscription travels upward. This is the single most
  confusing thing about Context and worth stating plainly.

  IN PRACTICE YOU RARELY WRITE THIS YOURSELF:

    Security   ReactiveSecurityContextHolder.getContext()
               -- reads from the Reactor Context, and Spring
               Security's WebFilter puts it there

    Logging    micrometer-context-propagation + Reactor's
               automatic context propagation:
                   Hooks.enableAutomaticContextPropagation();
               restores MDC around operator execution, so
               %X{traceId} works again

    Tracing    micrometer-tracing does this for you once the
               context-propagation library is present -- which
               is exactly the dependency the team in case (a)
               had not added
Blocking idiomReactive equivalent
SecurityContextHolder.getContext()ReactiveSecurityContextHolder.getContext()

Part 5 — Backpressure: The Part That Is Actually New

  BACKPRESSURE IS A PROTOCOL, NOT AN ADJECTIVE

    subscriber -> request(32)      "send me at most 32"
    publisher  -> onNext x32
    subscriber -> request(32)      "32 more"

  The CONSUMER states its demand. A publisher that respects it
  never produces faster than the consumer can handle. That is
  what "reactive" means in Reactive Streams -- not "async".

  WHY IT MATTERS: without it, a fast producer and a slow
  consumer means an unbounded queue, and an unbounded queue
  means an OutOfMemoryError with a delay attached.

MEASURED: an unbounded buffer OOM'd in 40 seconds

  An SSE endpoint streaming database rows to a browser:

    return Flux.fromIterable(hugeList)      // 2.1M rows
               .map(this::toDto)
               .onBackpressureBuffer();     // "fixes" the error

  Browser consumed ~200 rows/s over a slow connection.
  Producer emitted as fast as memory allowed.

    T+0    stream starts
    T+18s  heap 1.1 GB, GC time climbing
    T+31s  GC 60% of CPU, everything else on the loop starving
    T+40s  OutOfMemoryError, pod killed, ALL streams on that
           pod dropped

  onBackpressureBuffer WITHOUT A BOUND IS A MEMORY LEAK WITH A
  FRIENDLY NAME. The strategies, and what each is for:

    onBackpressureBuffer(1000, DROP_OLDEST)   bounded, lossy
    onBackpressureDrop()      drop new items when unwanted --
                              right for live telemetry
    onBackpressureLatest()    keep only the newest -- right for
                              a price ticker or a dashboard
    (no operator)             the source honours demand
                              natively -- the best case

  THE REAL FIX HERE was the source: R2DBC's Flux respects
  request(n), so the database fetches rows at the pace the
  browser consumes them. Backpressure works end to end only if
  EVERY link honours it.

  WHERE BACKPRESSURE CANNOT SAVE YOU

    An HTTP request that has already arrived cannot be slowed
    down. A Kafka poll returns what it returns. A webhook
    pushes at the sender's pace.

    For those, the correct pattern is not backpressure but LOAD
    SHEDDING: bound the queue and reject with 503 + Retry-After
    when it is full (the Resilience lesson's fast-failure
    argument, unchanged).

  STREAMING RESPONSES -- where reactive genuinely shines

    @GetMapping(value = "/orders/stream",
                produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<OrderDto> stream() {
        return repo.findAllBy()            // R2DBC, streaming
                   .map(mapper::toDto);
    }

    - the first byte reaches the client in milliseconds
    - memory stays flat regardless of result size
    - a client that disconnects CANCELS the subscription, and
      the database query stops. That cancellation propagating
      all the way to the driver is something the blocking stack
      cannot express at all.

    application/x-ndjson is usually the better content type for
    machine consumers: one JSON object per line, no SSE framing.

  THE OPERATIONAL CATCHES:
    - proxies and load balancers buffer responses by default,
      which silently converts streaming into batching
    - idle timeouts kill a quiet stream; send heartbeats
    - browsers cap concurrent SSE connections per host
🔑 Streaming with cancellation is the capability that has no blocking equivalent. Everything else in this lesson — concurrency, non-blocking I/O, composition — has an alternative that is cheaper for most teams. But a client disconnecting and having that propagate as a cancellation through the mapper, the query and the database driver, freeing every resource, is expressible only in this model. If your product has long-lived streams, that alone can justify WebFlux for the streaming endpoints specifically — which is a much smaller commitment than converting a whole service.

Part 6 — Living With It: Debugging, Testing, Deciding

  THE STACK TRACE PROBLEM

  A failure inside an operator produces this:

    java.lang.NullPointerException
      at reactor.core.publisher.FluxMap$MapSubscriber.onNext
      at reactor.core.publisher.FluxOnAssembly...
      at reactor.netty.http.client.HttpClientOperations...
      ... 60 frames of Reactor internals ...

  NOTHING in it names your code, your endpoint, or which of the
  four flatMaps failed. The call stack is a description of the
  machinery, because the logical stack was never a stack.

  THREE TOOLS, IN THE ORDER I WOULD REACH FOR THEM:

  1. checkpoint() -- zero cost, production-safe
       .flatMap(this::price).checkpoint("price-lookup")
       .flatMap(this::reserve).checkpoint("inventory-reserve")
     The error now names the checkpoint it passed. This is the
     single highest-value habit in a reactive codebase.

  2. Reactor debug agent -- development and staging
       ReactorDebugAgent.init();     // instruments at class load
     Reassembles a meaningful trace with modest overhead.

  3. Hooks.onOperatorDebug() -- DEVELOPMENT ONLY
     Captures a stack trace at ASSEMBLY of every operator.
     Excellent traces, and 10-100x overhead. Never in
     production, and it is depressingly often left on.

  TESTING -- StepVerifier, and virtual time

    @Test
    void retriesTwiceThenFails() {
        StepVerifier.create(service.priceWithRetry(cart))
            .expectNext(new Price(19.99))
            .verifyComplete();
    }

    @Test
    void emitsEveryFiveMinutesWithoutWaiting() {
        StepVerifier.withVirtualTime(() ->
                Flux.interval(Duration.ofMinutes(5)).take(3))
            .thenAwait(Duration.ofMinutes(15))     // instant
            .expectNextCount(3)
            .verifyComplete();
    }

  VIRTUAL TIME is a genuine advantage over blocking tests: a
  15-minute backoff schedule is verified in milliseconds,
  deterministically. Testing the same retry policy in a blocking
  codebase usually means mocking a clock or not testing it.

  AND ALWAYS ASSERT THE ERROR PATH:
    .expectErrorMatches(e -> e instanceof PricingUnavailable)
    .verify();
  because a chain that silently completes empty passes a naive
  "no exception thrown" test.

⚠️ The most defensible position in 2026 is that WebFlux is a specialist tool, not a default. Virtual threads removed its main general-purpose argument — high concurrency without a thread per request — while leaving its specialist ones intact: streaming with cancellation, backpressure as a real protocol, and composition of large fan-outs. A reasonable architecture uses Spring MVC with virtual threads for the ordinary service and WebFlux where those specific properties are needed. Mixing them in one application is possible but rarely worth it; mixing them across services is straightforward.

Interview Questions

Beginner: What problem does reactive programming solve?

Thread exhaustion under I/O-bound load. In the thread-per-request model each request owns a thread for its whole life, including all the time it spends waiting on a database or another service. A blocked thread reserves about a megabyte of stack and does no work, so the concurrency ceiling is set by the thread pool rather than by CPU — 200 threads at 50 ms of latency is roughly 4,000 requests a second, and if latency rises to half a second it collapses to 400 with the CPU idle.

An event loop inverts that: a handful of threads, and when a request waits on I/O the thread is released to serve someone else, with a callback resuming the work when the response arrives. In a measured comparison at 10,000 concurrent connections, the blocking version managed about 380 requests a second with a 14-second p99, and the reactive version about 9,700 with a 580 ms p99 and a quarter of the memory.

The part worth adding is what it does not solve: it does not make an individual request faster. At ordinary concurrency the same benchmark showed reactive marginally slower on p99. It raises a ceiling; if you are not near that ceiling it buys memory and complexity.

Beginner: What does "nothing happens until you subscribe" mean?

A Mono or Flux is a description of work, not the work itself. Calling repo.save(order) builds a pipeline and returns it; no database call has been made. The work starts when something subscribes — which in a WebFlux controller happens because you returned the publisher and the framework subscribed to it.

The consequence is the most common reactive bug: if you call a reactive method and ignore the result, nothing runs and nothing complains. I have seen a listener log "saved order" 4,100 times with zero rows written, discovered two days later by a report. There is no exception, no warning, and the log line is perfectly truthful about having been reached.

Defences are turning on the IDE's "reactive result unused" inspection as an error, and never calling a reactive method from non-reactive code without an explicit terminal operation.

Mid: What happens if you make a blocking call in a WebFlux handler?

You block one of a very small number of event-loop threads — typically one per core — and every request already assigned to that loop waits behind it. In the blocking model a slow call occupies one of two hundred threads; here it occupies a quarter of the entire server.

The measured case was a JDBC query left in place during a migration. The query itself was fast, 12 ms, but at 1,200 requests a second that is 3.6 seconds of blocking demand per second of wall clock across four loops. p99 went from 90 ms to 6.4 seconds, throughput capped around 330 requests a second, and CPU sat at 22% — so every dashboard said the service was healthy while every endpoint degraded, including the ones that never touched the database.

The fixes are R2DBC for genuinely non-blocking access, or subscribeOn(Schedulers.boundedElastic()) to move the blocking work off the loop. But I would be explicit that boundedElastic makes it safe rather than scalable — the call still needs a thread for its duration, so you are back to thread-per-request with extra hand-offs. A service whose whole repository layer is JDBC on boundedElastic has all of reactive's debugging cost and none of its benefit.

To catch these mechanically I would add BlockHound to the test suite, because a blocking call introduced in an unrelated pull request has no visible symptom until production.

Mid: Why do ThreadLocal, MDC and SecurityContextHolder stop working?

Because they all encode the assumption that one request equals one thread. That is true in the blocking model, so attaching state to the thread is equivalent to attaching it to the request. In the reactive model one request runs across several threads and one thread interleaves thousands of requests, so the assumption is simply false.

The mild failure is that things go missing: a team I know migrated one service and every log line lost its trace id. Nobody noticed for six weeks, until an incident where the trace search that works for every other service returned nothing and diagnosis took nearly four hours.

The severe failure is a leak. Code that copied the authenticated principal into a ThreadLocal inside a reactive chain produced cross-user data in 0.4% of responses under load, because the loop thread picked up another request while the first was awaiting I/O. That is a security incident, not a bug.

The replacement is the Reactor Context, which travels with the subscription rather than the thread — written with contextWrite and read with deferContextual. In practice you rarely touch it directly: ReactiveSecurityContextHolder reads from it, and the micrometer context-propagation library plus Hooks.enableAutomaticContextPropagation() restores MDC around operator execution so the logging pattern works again. The one genuinely confusing detail is that contextWrite affects operators above it in the chain, because the subscription travels upward.

Senior: What is backpressure, and where does it stop helping?

It is a protocol, not an adjective. The subscriber signals demand — request(n) — and a conforming publisher never emits more than that. It is what distinguishes Reactive Streams from ordinary asynchronous callbacks: without it, a fast producer and a slow consumer means an unbounded queue, and an unbounded queue is an OutOfMemoryError with a delay attached.

The failure I have seen is an SSE endpoint streaming two million rows to a browser on a slow connection. Someone had added onBackpressureBuffer() to make an error go away, which is an unbounded buffer: heap hit 1.1 GB in eighteen seconds, GC took 60% of CPU, and the pod OOM'd in forty — killing every other stream on it. The real fix was the source: R2DBC's Flux honours request(n), so the database fetches rows at the pace the browser consumes them. Backpressure only works end to end if every link honours it.

Where it stops helping is anything you do not pull. An HTTP request that has already arrived cannot be slowed down; a Kafka poll returns what it returns; a webhook sender does not care about your demand. For those the correct pattern is load shedding — a bounded queue and a fast 503 with Retry-After — not backpressure. Confusing the two leads to designs that assume the pressure will propagate to a producer who has no way to receive the signal.

The capability I would actually sell backpressure on is streaming with cancellation: a client disconnecting propagates as a cancellation through the mapper, the query and the driver, releasing everything. There is no blocking equivalent for that, and it is the strongest technical argument for WebFlux on the endpoints that need it.

Senior: A team proposes migrating a service to WebFlux for scalability. How do you evaluate it?

I would start by asking which ceiling they are hitting, because the answer usually decides it without any architectural argument. If the symptom is thread exhaustion under I/O-bound load — requests queued while CPU is idle — then in 2026 the first thing to try is virtual threads: spring.threads.virtual.enabled on Java 21. That gives a thread per request costing a few hundred bytes rather than a megabyte, with blocking code, ordinary stack traces, working ThreadLocal and JPA intact. It is a configuration flag against a rewrite, and it closes most of the gap the benchmarks show.

Then I would check whether "scalability" is even the right diagnosis. High latency with idle CPU is often a connection pool sized wrong, a missing timeout, or an N+1 — problems that reactive does not fix and can hide. And if the work is CPU-bound, reactive makes it strictly worse, because the event loop is competing for the same cores.

Where I would agree is the three cases with no good alternative: tens of thousands of mostly-idle connections such as SSE or WebSocket; streaming large or unbounded results where cancellation must propagate to the database; and gateway-shaped services that are almost pure I/O composition with little domain logic.

If it does go ahead, I would put the real cost in front of them rather than the controller syntax. The persistence layer is the budget: R2DBC has no ORM, so no persistence context, no lazy loading, no relationship traversal — every association becomes a second query and a join written by hand. Debugging changes character, because a stack trace names sixty frames of Reactor internals and none of your code, so checkpoint() has to become a habit and BlockHound has to be in the test suite from day one. And ThreadLocal-based infrastructure — logging context, security, transactions — needs deliberate migration, with the trace-id and context-leak failures I would call out specifically.

My concrete counter-proposal would usually be to scope it: keep the service on Spring MVC with virtual threads, and put only the endpoints that genuinely need streaming or huge connection counts behind WebFlux — ideally as their own service. That gets the capability where it is needed without making every future bug in the domain logic harder to diagnose for everyone.

And the constraint I would treat as decisive is not technical: whether the whole team, including whoever is on call, can debug this at three in the morning. A codebase only a couple of people can diagnose is an availability risk regardless of its throughput numbers.

1 (easy): The log says orders are saved. The table is empty. Explain and fix. 
  public void handle(OrderEvent e) {
      Order o = map(e);
      repo.save(o);
      log.info("saved order {}", o.getId());
  }
Solution

repo.save(o) returns a Mono that nobody subscribes to. The call builds a description of a save and discards it, so no database work is ever scheduled. The log line is truthful about being reached and misleading about what happened. In the measured case: 4,100 orders logged, zero rows, discovered two days later by a report.

  // if the caller is reactive: RETURN the publisher
  public Mono<Void> handle(OrderEvent e) {
      return repo.save(map(e))
                 .doOnSuccess(o -> log.info("saved order {}", o.getId()))
                 .then();
  }

  // if the caller is genuinely blocking (a Kafka listener):
  public void handle(OrderEvent e) {
      Order saved = repo.save(map(e))
                        .block(Duration.ofSeconds(5));
      log.info("saved order {}", saved.getId());
  }
DetailWhy
Log in doOnSuccess, not after the callIt then fires when the save actually completed, rather than when the pipeline was assembled
block() takes a timeoutAn untimed block() can hang forever — the same infinite-timeout problem as any remote call
block() only at a non-reactive boundaryInside a reactive chain it blocks an event-loop thread, and Reactor throws on some schedulers for exactly that reason

How to stop it recurring: enable the IDE inspection for unused reactive results and treat it as an error, not a warning. This bug produces no exception, no metric change and no failed health check, so static detection is the only reliable defence — and a mixed blocking/reactive codebase is where it thrives.

2 (easy): This endpoint took the pricing service down. Find the defect. 
  public Mono<List<PricedItem>> priceAll(List<Long> ids) {
      return Flux.fromIterable(ids)          // up to 5,000 ids
                 .flatMap(id -> pricingClient.price(id))
                 .collectList();
  }
Solution

flatMap's default concurrency is 256. One call to this endpoint opens up to 256 simultaneous HTTP requests to pricing; ten concurrent callers is 2,560. In the measured case pricing's p99 went from 40 ms to 8.7 seconds and its error rate to 31% as its connection pool exhausted — while this endpoint kept "working", so nobody suspected it.

The underlying point is that in the blocking model your thread pool bounded outbound concurrency by accident. Reactive removes that bound and replaces it with nothing unless you say otherwise.

  public Mono<List<PricedItem>> priceAll(List<Long> ids) {
      return Flux.fromIterable(ids)
                 .flatMap(id -> pricingClient.price(id)
                                    .timeout(Duration.ofMillis(400))
                                    .onErrorResume(e -> Mono.empty()),
                          8)                     // explicit limit
                 .collectList();
  }
AdditionWhy
Concurrency limit of 8The bulkhead from the Resilience lesson, expressed in Reactor. The number belongs in code review
Per-call timeoutWithout it one hung call keeps a slot forever and the effective concurrency decays to zero
onErrorResume per itemOtherwise one failed lookup fails the entire batch — a partial result is usually far better here

What I would question beyond the fix: whether the endpoint should accept 5,000 ids at all. A bulk endpoint with no size limit is the same availability bug as an unbounded list endpoint, and a cap plus a documented maximum is cheaper than tuning the fan-out. And if pricing supports a batch API, one call for 5,000 ids beats 5,000 calls at any concurrency.

3 (medium): After migrating to WebFlux, p99 went from 90 ms to 6.4 s at 22% CPU. Diagnose it and describe the fix.
Solution

High latency with idle CPU in a reactive service means the event loops are blocked, not busy. With typically one loop thread per core, a single blocking call occupies a large fraction of the entire server, and every request assigned to that loop queues behind it.

StepWhat you find
Thread dump under loadThreads named reactor-http-nio-* parked in SocketInputStream.read or a JDBC driver — loop threads should never be there
Look for blocking APIs in handlersJdbcTemplate, RestTemplate, File I/O, Thread.sleep, synchronised sections, and .block()
Do the arithmetic12 ms of blocking × 1,200 req/s = 3.6 s of demand per second against 4 loops — saturated several times over
Confirm mechanicallyAdd BlockHound to the test suite; it throws precisely where blocking happens on a non-blocking thread
  // OPTION A -- non-blocking driver (the real fix)
  interface OrderRepository extends ReactiveCrudRepository<Order, Long> { }

  // OPTION B -- isolate the blocking call (a bridge, not a
  //             destination)
  Mono<Order> find(Long id) {
      return Mono.fromCallable(() -> jdbcTemplate.queryForObject(...))
                 .subscribeOn(Schedulers.boundedElastic());
  }

Option B restores correctness, not scalability. The query still holds a thread for its whole duration, so you are back to thread-per-request with an extra hand-off and a pool capped at 10 × cores. It is the right temporary bridge during a migration and the wrong permanent state.

The strategic question this raises is whether the migration should continue. If the persistence layer is JPA with real relationships, "finish the migration" means rewriting it without an ORM — no persistence context, no lazy loading, every association a hand-written second query. If the original goal was concurrency rather than streaming, Spring MVC with virtual threads gets the same ceiling with none of that work, and reverting is a legitimate outcome to put on the table.

What I would add regardless: BlockHound in CI. A blocking call introduced by an unrelated pull request has no symptom until production load, and this failure mode is severe enough that detection needs to be mechanical rather than cultural.

4 (medium): After the migration, every log line lost its trace id, and a security review found cross-user data in 0.4% of responses. Explain both and fix them.
Solution

Both come from the same broken assumption: one request equals one thread. In the reactive model a request crosses several threads and a thread interleaves thousands of requests, so anything built on ThreadLocal is at best empty and at worst wrong.

SymptomMechanism
Missing trace idThe logging pattern reads %X{traceId} from the MDC, which is a ThreadLocal. The loop thread executing the operator is not the thread the filter set it on, so it is empty
Cross-user dataCustom code stored the principal in a ThreadLocal. Request A set it, awaited I/O, and the same loop thread then served request B — which read A's principal. Under load that was 0.4% of responses
  // 1. context propagation for logging/tracing
  //    build.gradle
  implementation 'io.micrometer:context-propagation'
  implementation 'io.micrometer:micrometer-tracing-bridge-brave'

  @PostConstruct
  void init() { Hooks.enableAutomaticContextPropagation(); }

  // 2. delete the ThreadLocal entirely; read from the context
  Mono<Order> place(OrderRequest req) {
      return ReactiveSecurityContextHolder.getContext()
          .map(SecurityContext::getAuthentication)
          .flatMap(auth -> orders.place(req, auth.getName()));
  }

  // 3. anything custom goes in the Reactor Context, not a field
  return handle(req)
           .contextWrite(ctx -> ctx.put("tenantId", tenantId));

The leak is the serious half and deserves incident treatment, not a fix-and-move-on: it is a cross-user data exposure, it was reachable in production, and its rate depends on load, so a quiet staging environment will not reproduce it. I would search the codebase for every ThreadLocal and every static mutable field touched from a reactive path, and add an ArchUnit rule forbidding them in reactive packages.

Note that contextWrite applies upward. It affects operators above it in the chain, because the subscription travels upstream — which is genuinely counter-intuitive and is the usual reason a context value appears to be missing after someone "fixed" it by moving the call earlier.

The verification I would insist on: a load test asserting that a trace id appears in every log line and that a per-request principal never differs from the one the request authenticated with. Both failures here were invisible in functional tests and only appear under concurrency.

5 (hard): Design a streaming endpoint that sends 2 million rows to slow clients without OOM, and say what could still go wrong in production.
Solution 
  @GetMapping(value = "/orders/export",
              produces = MediaType.APPLICATION_NDJSON_VALUE)
  public Flux<OrderDto> export(@RequestParam String status) {
      return repo.findByStatus(status)          // R2DBC: streams
                 .map(mapper::toDto)
                 .limitRate(256)                // demand in chunks
                 .timeout(Duration.ofMinutes(30))
                 .doOnCancel(() -> log.info("client disconnected"))
                 .doFinally(sig -> metrics.recordExport(sig));
  }
DecisionWhy
R2DBC source, not a ListThe driver fetches rows as demand arrives, so memory is flat regardless of result size. A List materialises 2M rows before the first byte
No onBackpressureBufferAn unbounded buffer is the OOM — in the measured case, 1.1 GB in 18 s and a dead pod in 40. If the source honours demand, no buffering operator is needed at all
NDJSON rather than SSEOne JSON object per line, no event framing, trivially consumable by jq or a script. SSE is for browsers
limitRate(256)Requests demand in bounded chunks rather than an unbounded initial request, which keeps the driver's fetch size sane
doOnCancelA disconnect cancels the subscription and the query stops — the property with no blocking equivalent. Logging it makes the behaviour observable

What still goes wrong in production, in the order I would expect it:

ProblemFix
A proxy buffers the response, converting streaming into batching — nginx does this by defaultproxy_buffering off, and verify by watching first-byte time rather than trusting the config
Idle timeouts kill quiet streams at the load balancerHeartbeat lines (SSE comments, or a keepalive record), and align the LB timeout with the export duration
A long-lived database cursor holds a connection and, on some engines, blocks vacuum or holds a snapshotBound the export duration; consider keyset paging under the stream for very long exports
Clients that retry a failed export from the startSupport a resume cursor, or the retry is a self-inflicted load multiplier
No backpressure past the pod — many concurrent exports each holding a connectionCap concurrent exports explicitly and return 429; the connection pool is the real limit

The honest framing: the reactive part of this is the easy part and it works. The failures are all at the boundaries — proxies, timeouts, database sessions and client behaviour — and none of them are visible in a local test where the client is fast and there is no proxy. I would test this against a deliberately slow client through the real ingress before believing any of it.

6 (hard): Your team is choosing between Spring MVC with virtual threads and WebFlux for a new service. Make the decision and defend it.
Solution

The decision turns on which of three specific capabilities you need, because for raw concurrency the two are now close enough that the difference is not the deciding factor.

RequirementChoiceReason
Tens of thousands of long-lived, mostly-idle connectionsWebFluxEven a cheap thread per connection is a thread; an idle connection on an event loop is a socket and a callback
Streaming with cancellation propagating to the databaseWebFluxNo blocking equivalent exists. This is the strongest single argument
Backpressure through the whole pipelineWebFluxVirtual threads give cheap concurrency, not a demand protocol
Ordinary CRUD at high concurrencyMVC + virtual threadsA configuration flag, and you keep JPA, stack traces, ThreadLocal and step debugging
CPU-bound workMVCNeither model helps; an event loop competing for the same cores makes it worse
Rich domain logic that will be debugged for yearsMVC + virtual threadsDebuggability is a permanent operating cost paid by everyone on call

For a typical new service my answer is Spring MVC with virtual threads, and I would defend it on four grounds. The concurrency ceiling that used to force the choice is gone — spring.threads.virtual.enabled gives a per-request thread costing a few hundred bytes that parks without holding a carrier. The persistence layer stays JPA, which is the majority of what a WebFlux migration actually costs, since R2DBC has no ORM. Debugging stays ordinary: a stack trace names your code rather than sixty frames of Reactor. And every piece of ThreadLocal-based infrastructure — MDC, security context, transactions — keeps working, which removes an entire class of subtle failures including the context leak that is a security incident rather than a bug.

Where I would go the other way without hesitation is a service whose job is streaming or connection-holding: SSE feeds, WebSockets, a gateway fanning out to many backends, an export API. Those need capabilities virtual threads do not provide, and the domain logic in such services is usually thin, so the debugging cost is small.

The architecture I would actually propose is not one or the other but a boundary: MVC with virtual threads for the domain service, and a separate small WebFlux service for the streaming or connection-heavy endpoints. That confines reactive code to where it earns its cost and to a codebase small enough that everyone can hold it in their head.

Two caveats I would state honestly. Virtual threads have their own sharp edge: a synchronized block pins the virtual thread to its carrier, so a library that synchronises around I/O can still exhaust the carrier pool — worth checking against the specific drivers in use. And if the team has genuine reactive expertise and an existing reactive codebase, the calculus changes; consistency with what people already operate well is a real engineering argument, not a concession.

🎯 Key Takeaways

  • Reactive solves thread exhaustion, not latency. At 10,000 connections it was 9,700 req/s against 380 — and at 200 connections its p99 was slightly worse.
  • Virtual threads removed the main general-purpose reason to adopt WebFlux — a configuration flag, with JPA, stack traces and ThreadLocal intact.
  • What virtual threads do not give you: backpressure, streaming with cancellation, or a composition model for large fan-outs.
  • Nothing happens until you subscribe. A discarded Mono logged 4,100 saves and wrote zero rows, with no error anywhere.
  • flatMap defaults to 256 concurrent inner subscriptions — one request became 256 downstream calls and took pricing from 40 ms to 8.7 s. Always pass a limit.
  • concatMap when order matters; flatMap interleaves by design.
  • try/catch catches nothing — errors are signals. Use onErrorResume; doOnError is a side effect, not a handler.
  • Mono.empty() is not an error — "not found" needs switchIfEmpty.
  • One blocking call occupies a quarter of the server. 12 ms of JDBC took p99 from 90 ms to 6.4 s at 22% CPU, degrading endpoints that never touched the database.
  • BlockHound in tests is the only mechanical defence against a blocking call added in an unrelated pull request.
  • boundedElastic makes blocking safe, not scalable — JDBC on it is thread-per-request with extra hand-offs and all of reactive's debugging cost.
  • R2DBC has no ORM. No persistence context, no lazy loading, relationships by hand — that is the real migration budget, not the controllers.
  • ThreadLocal assumes one request per thread and that is false here — trace ids vanished for six weeks, and a hand-rolled principal leaked across users in 0.4% of responses.
  • Request state belongs in the Reactor Context, and contextWrite applies upstream, which is the detail everyone trips on.
  • Backpressure is a demand protocol, and it only works if every link honours it.
  • Unbounded onBackpressureBuffer is a memory leak with a friendly name — OOM in 40 seconds, taking every other stream on the pod with it.
  • Backpressure cannot slow an inbound flood. For arrived requests the answer is load shedding: a bounded queue and a fast 503.
  • Streaming with cancellation is the capability with no blocking equivalent — a disconnect stops the query at the driver.
  • Stack traces stop naming your code. checkpoint() is free and belongs everywhere; Hooks.onOperatorDebug() costs 10–100× and belongs in development only.
  • The deciding constraint is usually not technical: whether everyone on call can debug it at 3am.
