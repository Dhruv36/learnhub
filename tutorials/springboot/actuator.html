Actuator & Observability Production

What you'll master: the distinction that decides whether your monitoring is useful — liveness answers "should this process be killed?" and readiness answers "should it receive traffic?", and conflating them is why one team's database blip restart-looped every pod in the cluster and turned a 40-second outage into 20 minutes; why a health check that calls a downstream service is almost always a mistake, and the cascade it creates; the metrics that actually diagnose a Spring service, including the two nobody exports and then wishes they had (connection-pool wait time and async queue depth); why percentiles cannot be averaged — the single most common observability error, which makes every dashboard aggregating p99 across instances quietly wrong; cardinality, where one well-intentioned tag produced 2.4 million time series and cost more than the service; distributed tracing and the trace id that turns a support ticket into one search; and the security posture for Actuator, where include: "*" exposes /heapdump — every secret in memory, downloadable. Prerequisites: Configuration & Profiles and Error Handling.

Part 1 — Liveness Is Not Readiness

  LIVENESS   "Is this process broken beyond recovery?"
             FAIL -> Kubernetes KILLS and restarts the pod.
             Should fail ONLY for unrecoverable in-process state:
             a deadlocked thread pool, an unrecoverable OOM,
             corrupted internal state.

  READINESS  "Can this instance serve traffic right now?"
             FAIL -> Kubernetes REMOVES IT FROM THE LOAD BALANCER.
             The process keeps running and can recover.
             Should fail for: still warming up, dependency
             unavailable, shedding load.

  THE RULE THAT FOLLOWS:
    A DOWNSTREAM DEPENDENCY BEING DOWN IS NEVER A LIVENESS FAILURE.
    Restarting your process does not fix someone else's database.

MEASURED: what conflating them costs

  One health endpoint, wired to both probes, including a database check.

    livenessProbe:  httpGet /actuator/health   failureThreshold 3
    readinessProbe: httpGet /actuator/health

  T+0     the database fails over. 40 seconds of unavailability.
  T+15s   health returns DOWN on all 24 pods
  T+30s   liveness fails 3x -> Kubernetes kills ALL 24 pods
  T+45s   database recovers
  T+45s   24 pods are restarting; JVM start + warm-up is 50 s each
  T+90s   pods start, hammer the just-recovered database
          simultaneously with connection storms and cold caches
  T+3m    thundering herd causes the database to degrade again
  T+20m   stabilised after manual intervention

  A 40-second dependency blip became a 20-minute outage, caused
  entirely by the monitoring configuration.

  WITH SEPARATE PROBES:
    liveness  -> stays UP (the JVM is fine)
    readiness -> goes DOWN (cannot serve)
    pods stay alive, stop receiving traffic, recover in 40 s
    Total impact: 40 seconds.

  SPRING BOOT'S BUILT-IN GROUPS -- use them

    management:
      endpoint:
        health:
          probes:
            enabled: true          # exposes the two sub-endpoints
          group:
            liveness:
              include: livenessState
            readiness:
              include: readinessState, db, redis
          show-details: when-authorized

    /actuator/health/liveness    -> only the JVM's own state
    /actuator/health/readiness   -> state + the dependencies you
                                    genuinely cannot serve without

  Boot enables probes automatically when it detects Kubernetes.

  deployment.yaml
    livenessProbe:
      httpGet: { path: /actuator/health/liveness, port: 8081 }
      failureThreshold: 6            # be generous: killing is drastic
    readinessProbe:
      httpGet: { path: /actuator/health/readiness, port: 8081 }
      failureThreshold: 2            # be quick: removing traffic is cheap
    startupProbe:
      httpGet: { path: /actuator/health/liveness, port: 8081 }
      failureThreshold: 30           # allows a slow start without
      periodSeconds: 5               # loosening steady-state timeouts
🔑 The asymmetry is the whole point: removing an instance from the load balancer is cheap and reversible; killing it is expensive and destroys warm state. So readiness should be sensitive and fast to trip, liveness should be slow and reluctant. A startupProbe handles the slow-boot case so you never need to loosen liveness thresholds to accommodate startup — see Bean Scopes & Lifecycle for the 47-second-startup case this solves.

Part 2 — Health Indicators, and What Not to Check

  Boot auto-configures indicators for what it finds: db, diskSpace,
  redis, mongo, rabbit, kafka, mail, elasticsearch.

  A CUSTOM ONE -- for internal state you own

    @Component
    class CatalogWarmupHealthIndicator implements HealthIndicator {
        private final CatalogCache cache;

        @Override
        public Health health() {
            if (!cache.isWarm())
                return Health.outOfService()
                             .withDetail("state", "warming")
                             .withDetail("loaded", cache.size())
                             .build();
            return Health.up().withDetail("entries", cache.size()).build();
        }
    }

  THE ANTI-PATTERN -- checking a downstream SERVICE

    @Component
    class PaymentGatewayHealthIndicator implements HealthIndicator {
        public Health health() {
            return gateway.ping().isOk()          // an HTTP call
                 ? Health.up().build()
                 : Health.down().build();
        }
    }

  WHY THIS IS WRONG:

  1. CASCADING FAILURE. The gateway has a hiccup; your readiness
     goes DOWN; every instance is removed from the load balancer;
     your service is now 100% unavailable -- including the 90% of
     endpoints that never touch payments.

  2. A LOAD MULTIPLIER. 24 pods x every 10 s = 8,640 ping requests
     per hour to a service that is already struggling. Health checks
     become a denial-of-service on your dependency.

  3. IT MEASURES THE WRONG THING. "Can I reach the gateway right
     now?" is not "can I serve traffic?" You can queue the work,
     degrade gracefully, or serve the other 90% of endpoints.

  WHAT TO DO INSTEAD:
    - a CIRCUIT BREAKER around the call (see Resilience &
      Microservices) so failures are handled per-request
    - a METRIC for gateway availability, and alert on that
    - readiness stays UP; the endpoint that needs payments returns
      503 with a Retry-After, and everything else keeps working
Include in readiness?Reasoning
The application's own databaseUsually yes — you genuinely cannot serve without it, and every instance shares the same fate anyway
A cache like RedisOnly if it is not optional. If you can fall back to the database, a Redis outage should degrade, not remove you from the load balancer
Warm-up state you ownYes — this is exactly what readiness is for
A downstream HTTP serviceNo — cascading failure and a load multiplier
Disk spaceRarely. It fails all instances simultaneously and restarting fixes nothing
Anything in liveness other than the JVMNo. Liveness answers only "is this process unrecoverable?"

Part 3 — The Metrics That Matter

  Micrometer is the facade; the registry (Prometheus, Datadog,
  CloudWatch) is the backend. Boot auto-instruments a great deal.

  THE FOUR SIGNALS, and where they come from in a Spring service:

  LATENCY     http.server.requests            {uri, method, status,
                                               outcome, exception}
  TRAFFIC     http.server.requests_count      same tags
  ERRORS      http.server.requests{status=5xx}
  SATURATION  jvm.memory.used / jvm.gc.pause
              hikaricp.connections.pending    <-- the one people miss
              executor.queued                 <-- and this one

  THE TWO NOBODY EXPORTS AND THEN WISHES THEY HAD:

  1. hikaricp.connections.pending
     Threads WAITING for a database connection. Every failure mode
     in Transactions -- a remote call inside a transaction, a
     REQUIRES_NEW nesting deadlock, a long-running job -- shows up
     here FIRST, while query latency still looks perfectly normal.

  2. executor.queued  (needs ExecutorServiceMetrics.monitor(...))
     Async backlog. The Caching, Async & Scheduling case reached
     1.9M queued tasks with CPU, latency and error rate all normal,
     because nothing exported the queue.

  Both are invisible by default and both are the first sign of the
  problem, not a symptom of it.

  CUSTOM METRICS -- three types, and picking the right one matters

  COUNTER -- monotonically increasing
    meterRegistry.counter("orders.placed", "channel", channel).increment();

  TIMER -- duration + count together
    Timer.Sample s = Timer.start(registry);
    ...
    s.stop(registry.timer("payment.gateway", "outcome", "success"));

  GAUGE -- a current value, sampled
    Gauge.builder("outbox.pending", outboxRepo, OutboxRepo::countPending)
         .register(registry);

  THE GAUGE TRAP: a gauge holds a WEAK reference to its source.
  If nothing else holds `outboxRepo`, it is garbage collected and
  the gauge silently reports NaN forever. Always keep a strong
  reference -- usually by making the source a Spring bean field.

  @Timed IS AVAILABLE, but only on beans, and it is proxy-based:
    @Timed(value = "order.processing", percentiles = {0.5, 0.95, 0.99})
    public Order place(...) { ... }

Part 4 — Percentiles Cannot Be Averaged

  THE MOST COMMON OBSERVABILITY ERROR

    instance A: p99 = 100 ms
    instance B: p99 = 900 ms

    "cluster p99" = (100 + 900) / 2 = 500 ms      <-- MEANINGLESS

  There is no arithmetic that recovers the true p99 from two
  pre-computed p99s. The real cluster p99 depends on the underlying
  distributions and the request volumes, and could be anywhere from
  ~100 ms to ~900 ms.

  If A serves 99% of traffic, the true p99 is near 100 ms.
  If B does, it is near 900 ms.
  The average, 500 ms, is right in neither case.

  THE FIX: export HISTOGRAMS, not pre-computed percentiles.

    management:
      metrics:
        distribution:
          percentiles-histogram:
            http.server.requests: true
          slo:
            http.server.requests: 50ms,100ms,200ms,500ms,1s,2s

  This exports BUCKETS (count of requests under 50ms, under 100ms...).
  Buckets are additive across instances, so Prometheus can compute a
  correct cluster-wide percentile:

    histogram_quantile(0.99,
      sum(rate(http_server_requests_seconds_bucket[5m])) by (le))

  The `sum ... by (le)` is what makes it correct: bucket counts add,
  percentiles do not.
⚠️ Histograms are not free. Each histogram-enabled timer exports one time series per bucket per tag combination. A timer with 10 buckets and 50 URI values is 500 series from one metric. Enable percentiles-histogram deliberately on the handful of metrics you actually graph — usually http.server.requests and your critical business timers — not globally.

Part 5 — Cardinality Will Bankrupt You

  Every unique combination of tag values is a separate TIME SERIES,
  stored and billed independently.

MEASURED: one tag, 2.4 million series

  Someone added what looked like a helpful tag:

    registry.counter("orders.placed",
        "customer", order.getCustomerId().toString(),   // 400,000 values
        "status",   order.getStatus().name(),           // 6 values
        "channel",  order.getChannel()                  // 4 values
    ).increment();

    400,000 x 6 x 4 = 9,600,000 possible series
    2,400,000 actually created within a week

  CONSEQUENCES:
    - the Prometheus server OOM'd and stopped scraping everything
    - the vendor bill for that month exceeded the service's own
      compute cost
    - queries on ALL metrics slowed to timeouts
    - the JVM held 2.4M Meter objects: ~900 MB of heap

  THE RULE: a tag value must come from a BOUNDED, LOW-CARDINALITY
  SET. Roughly: if you cannot list the possible values, it is not a
  tag.

  NEVER A TAG:            user id, order id, email, session id,
                          request id, trace id, raw URL with ids,
                          exception message, timestamp
  FINE AS A TAG:          status, channel, region, http method,
                          outcome, endpoint TEMPLATE, error CLASS

  WHERE THE HIGH-CARDINALITY DATA BELONGS:
    logs (searchable, cheap per event) and TRACES (sampled).
    Not metrics.

  THE URI TAG IS ALREADY HANDLED -- do not break it

    /api/orders/42     ->  uri="/api/orders/{id}"      GOOD
    /api/orders/43     ->  uri="/api/orders/{id}"      same series

  Spring tags with the MAPPING TEMPLATE, not the raw path, which is
  why http.server.requests is safe by default.

  YOU CAN BREAK IT: a request to an unmapped path is tagged
  uri="/**" -- but a misconfigured filter or a custom tag provider
  that uses request.getRequestURI() reintroduces unbounded
  cardinality immediately.

  A GUARD WORTH ADDING:
    management.metrics.web.server.max-uri-tags: 100
    Beyond that, Boot stops creating new uri tags rather than
    letting cardinality run away.

Part 6 — Tracing, and Securing the Endpoints

  DISTRIBUTED TRACING -- one id across every service

    implementation 'io.micrometer:micrometer-tracing-bridge-brave'
    implementation 'io.zipkin.reporter2:zipkin-reporter-brave'

    management.tracing.sampling.probability: 0.1     # 10%

  Micrometer Tracing (Boot 3's replacement for Spring Cloud Sleuth)
  propagates a trace id via W3C traceparent headers, and puts it in
  the MDC so every log line carries it:

    logging.pattern.level:
      "%5p [${spring.application.name},%X{traceId},%X{spanId}]"

  SAMPLING is a real trade-off:
    1.0  every request traced; high storage cost, high overhead
    0.1  10%; the usual starting point
    0.01 1%; large systems

  The catch: a sampled-out request has NO trace, so the one
  customer complaint you need may not be there. Use tail-based
  sampling (keep 100% of errors and slow requests) if your backend
  supports it -- that is the configuration that makes tracing
  actually useful for support.

  SECURING ACTUATOR -- the /heapdump problem

    management:
      endpoints:
        web:
          exposure:
            include: "*"                # NEVER

  What "*" exposes:
    /actuator/heapdump   a full heap dump -- EVERY SECRET IN MEMORY,
                         downloadable by anyone who can reach it
    /actuator/env        configuration, including values
    /actuator/threaddump internal structure
    /actuator/loggers    WRITABLE -- an attacker can turn on DEBUG
                         logging and flood your disks
    /actuator/shutdown   disabled by default, and people enable it

  THE CORRECT POSTURE:

    management:
      server:
        port: 8081                     # SEPARATE PORT, internal only
      endpoints:
        web:
          exposure:
            include: health,info,metrics,prometheus
      endpoint:
        health:
          show-details: when-authorized
        env:
          show-values: never

  The separate management port is the control that matters. An
  exposure list is one careless edit from being wrong; a port that
  is not routed from the internet is a network boundary. Bind it to
  the pod network and let only Prometheus and the kubelet reach it.

Interview Questions

Beginner: What is Spring Boot Actuator?

A module that adds production endpoints to an application — health, metrics, environment, thread dumps, mappings, conditions and more — over HTTP or JMX, without you writing them.

In practice the ones used constantly are /actuator/health for Kubernetes probes, /actuator/prometheus for metrics scraping, and — during debugging — /actuator/env, /actuator/conditions and /actuator/mappings, which answer "what configuration is actually in effect?", "why does this bean exist?" and "why is this URL 404-ing?".

Endpoints are disabled by default except health, and that default matters — enabling them all exposes /heapdump, which is a complete dump of everything in memory.

Beginner: What is the difference between a liveness and a readiness probe?

Liveness answers "is this process broken beyond recovery?" — if it fails, Kubernetes kills and restarts the pod. Readiness answers "can this instance serve traffic right now?" — if it fails, the pod is removed from the load balancer but keeps running and can recover.

The consequence is an asymmetry: removing an instance from the load balancer is cheap and reversible, while killing it destroys warm caches and costs a full startup. So readiness should be sensitive and quick to trip, and liveness should be slow and reluctant.

The rule that follows is that a downstream dependency being down is never a liveness failure — restarting your process does not fix someone else's database.

Mid: Why should a health check not call a downstream service?

Three reasons, and the first is the serious one.

Cascading failure. If the payment gateway has a hiccup and that makes your readiness DOWN, every instance is removed from the load balancer and your service becomes 100% unavailable — including the ninety percent of endpoints that never touch payments. You have converted a partial dependency failure into a total outage of your own service.

It is a load multiplier. Twenty-four pods checking every ten seconds is 8,640 requests an hour aimed at a service that is already struggling. Health checks become a denial-of-service on the dependency at exactly the wrong moment.

It measures the wrong thing. "Can I reach the gateway this instant?" is not "can I serve traffic?" — you can queue the work, degrade, or serve everything else.

What I would do instead is a circuit breaker around the call so failures are handled per request, and a metric for gateway availability with an alert on it. Readiness stays UP, the payment endpoint returns 503 with a Retry-After, and the rest of the service keeps working.

Mid: Why can you not average percentiles across instances?

Because a percentile is a property of a distribution, not a value you can do arithmetic on. If instance A reports p99 of 100 ms and instance B reports 900 ms, the cluster p99 is not 500 ms — it depends entirely on the underlying distributions and on how much traffic each instance served. If A handles 99% of requests the true answer is near 100 ms; if B does, it is near 900 ms. The average is correct in neither case.

The fix is to export histograms rather than pre-computed percentiles. Setting management.metrics.distribution.percentiles-histogram makes Micrometer export bucket counts, and bucket counts are additive across instances — so Prometheus can compute a correct cluster percentile with histogram_quantile(0.99, sum(rate(..._bucket[5m])) by (le)).

The caveat is cost: each histogram exports a series per bucket per tag combination, so I would enable it deliberately on the few metrics I actually graph rather than globally.

Senior: What is metric cardinality and why does it matter?

Every unique combination of tag values is a separate time series, stored and billed independently. So cardinality is multiplicative: three tags with 400,000, six and four possible values is up to 9.6 million series from a single counter.

I have seen that exact case. Someone added a customer tag to an order counter — helpful in intent — and within a week it had created 2.4 million series. The Prometheus server ran out of memory and stopped scraping everything, so the whole platform went blind; the vendor bill for that month exceeded the service's own compute cost; and the JVM was holding 2.4 million Meter objects, about 900 MB of heap.

The rule I use is that a tag value must come from a bounded set you could list. Status, channel, region, HTTP method, outcome, endpoint template — fine. User id, order id, email, session id, trace id, raw URL, exception message — never. High-cardinality data belongs in logs, which are cheap per event and searchable, or in traces, which are sampled.

The specific thing I would check in a Spring service is that nothing rebuilds the URI tag from getRequestURI(). Spring tags with the mapping template, so /orders/42 and /orders/43 share a series — a custom tag provider using the raw path silently reintroduces the problem. Setting max-uri-tags is a cheap guard.

Senior: Design the observability setup for a new Spring Boot service.

I would build it in the order that gets the most diagnostic value per hour spent, because observability work is easy to over-invest in.

First, the trace id. A filter that generates or adopts a request id, puts it in the MDC, returns it in a response header, and includes it in every error response. Roughly twenty lines, and it turns "the site broke around 3pm" into a single log search. Nothing else on this list has a better ratio.

Second, probes done correctly. Separate liveness and readiness groups, a startupProbe so slow boots do not force loose liveness thresholds, and no downstream services in either. This is the piece whose absence causes outages rather than merely making them harder to diagnose.

Third, the four signals plus the two that are invisible by default. Latency, traffic, errors and saturation come mostly free from http.server.requests and the JVM metrics. The two I always add explicitly are hikaricp.connections.pending and executor queue depth, because every failure mode from the transactions and async lessons shows up in one of those first, while latency and error rate still look normal.

Fourth, histograms on the handful of metrics that get graphed, so cluster percentiles are computed correctly rather than averaged.

Fifth, tracing at 10% sampling, moving to tail-based sampling if the backend supports it — keeping 100% of errors and slow requests is what makes tracing useful for support rather than just for aggregate analysis.

And throughout, the security posture: Actuator on a separate management port bound to the internal network, an explicit exposure list, and show-values: never. The separate port is the control I actually rely on — an exposure list is one careless edit from being wrong, whereas a port that is not routed from the internet is a network boundary.

What I would not do early is build dashboards. They are the visible part and the least useful until the underlying signals are right; a dashboard averaging p99 across instances is worse than no dashboard, because people trust it.

    periodSeconds: 10
    failureThreshold: 6           # ~60 s of failure before killing

    periodSeconds: 5

Note that db is in readiness but not liveness — the database being unavailable means this instance cannot serve, but restarting the JVM would not help.

2 (easy): This counter created 2.4 million time series. Fix it and say where the lost detail should go.

3 (medium): A dashboard shows cluster p99 as the average of each instance's p99. Explain why it is wrong and fix it end to end.
Solution

Why it is wrong. A percentile summarises a distribution; it is not a quantity that can be averaged. Given instance A at p99 = 100 ms and instance B at p99 = 900 ms, the true cluster p99 depends on both distributions and on the traffic split.

  A serves 99% of traffic  -> true cluster p99 ≈ 100 ms
  B serves 99% of traffic  -> true cluster p99 ≈ 900 ms
  reported "average"        = 500 ms         (wrong in both cases)

The dashboard is not merely imprecise — it can be wrong in either direction, which makes it worse than no dashboard because people act on it.

  STEP 1 -- export histogram BUCKETS instead of percentiles

    management:
      metrics:
        distribution:
          percentiles-histogram:
            http.server.requests: true
          slo:
            http.server.requests: 50ms,100ms,200ms,500ms,1s,2s,5s

  STEP 2 -- aggregate the buckets, then compute the quantile

    histogram_quantile(0.99,
      sum(rate(http_server_requests_seconds_bucket[5m])) by (le))

    The `sum ... by (le)` adds bucket COUNTS across instances --
    which is valid, because counts are additive. The quantile is
    computed once, from the combined distribution.

  STEP 3 -- per-endpoint, since a cluster-wide number hides the
            endpoint that is actually slow

    histogram_quantile(0.99,
      sum(rate(http_server_requests_seconds_bucket[5m])) by (le, uri))
ConsiderationDetail
Bucket boundaries matterhistogram_quantile interpolates within a bucket. If everything falls between 1s and 2s, the p99 is a guess. Choose SLO boundaries around the values you care about
CostOne series per bucket per tag combination. Seven buckets × 50 URIs = 350 series from one metric — enable deliberately, not globally
Client-side percentilespercentiles: [0.99] exports a pre-computed value that is correct per instance and still cannot be aggregated. Useful for a single-instance view only

What I would also fix: the alert built on that dashboard. An alert on an averaged p99 fires late when one instance degrades and fires spuriously when traffic shifts between instances. The corrected query fixes both, and it is worth checking whether anyone tuned alert thresholds to compensate for the broken metric — those thresholds will now be wrong.

4 (medium): A payment gateway had a 90-second incident and your service was down for 12 minutes. The gateway is checked in /actuator/health. Explain the chain and redesign it.
Solution 
  THE CHAIN

  T+0     gateway starts failing
  T+10s   PaymentGatewayHealthIndicator returns DOWN
          -> /actuator/health returns DOWN on all 20 pods
  T+20s   readiness fails -> ALL 20 pods removed from the LB
          -> service is now 100% unavailable, including the ~90%
             of endpoints that never touch payments
  T+30s   liveness (same endpoint) fails threshold -> pods KILLED
  T+90s   gateway recovers
  T+90s   20 pods restarting: 50 s JVM start + warm-up each
  T+3m    pods start together, cold caches, connection storms
  T+12m   stabilised

  Two independent faults compounded:
    1. a downstream service gated readiness
    2. the same endpoint gated liveness
FixEffect
Remove the gateway indicator from health entirelyA gateway outage no longer removes any pod from the load balancer
Separate liveness and readiness groupsNo dependency can ever cause a restart
Circuit breaker around the gateway callFailures handled per request, and the breaker stops hammering a recovering service
A metric plus an alert for gateway availabilityYou still find out — through the channel designed for it
  // the payment path degrades; nothing else notices
  @CircuitBreaker(name = "payments", fallbackMethod = "unavailable")
  public Receipt charge(Order o) { return gateway.charge(o); }

  private Receipt unavailable(Order o, Throwable t) {
      meterRegistry.counter("payments.unavailable").increment();
      throw new PaymentTemporarilyUnavailableException();   // -> 503
  }

  # health: no downstream services
  management.endpoint.health.group:
    liveness:  { include: livenessState }
    readiness: { include: readinessState, db }

The result: during a 90-second gateway outage, payment endpoints return 503 with a Retry-After, every other endpoint serves normally, no pod is removed or restarted, and recovery is immediate when the gateway returns. Total customer impact drops from a 12-minute total outage to 90 seconds of degraded payments.

The principle worth extracting: a health check should report on this instance's ability to serve, not on the state of the world. Anything shared by all instances — a downstream service, a third-party API — cannot be fixed by removing instances or restarting them, so putting it in a probe can only make things worse.

What I would add to the postmortem: an alert on "readiness DOWN across more than 50% of pods". If health checks ever take the whole fleet out again, that fires before the outage rather than after.

5 (hard): Design alerting for an order service. Say what you would alert on, what you would not, and why.
Solution

The organising principle: alert on symptoms users feel, not on causes. Cause-based alerts multiply — every possible cause needs its own — and they fire when nothing is actually wrong. A symptom alert fires once, for any cause, including causes nobody anticipated.

Page a humanConditionWhy it is worth waking someone
Error rate5xx > 1% for 5 minUsers are getting failures right now
Latency SLO burnp99 > 2 s for 10 minUsers are waiting; computed from buckets, not averaged
Order throughput collapseOrders/min < 20% of the 7-day-ago valueThe business symptom. Catches failures that produce no errors at all — the most valuable alert on the list
Fleet readiness> 50% of pods NOT ready for 2 minCapacity is gone or a health check is misbehaving

Ticket, do not pageWhy
Certificate expiring in 14 daysImportant, not urgent. Paging at 3am for something with a two-week window trains people to ignore pages
Disk 70% fullNeeds action this week
Cache hit rate below targetA performance concern, not an outage
A single pod restartedKubernetes handling it is the system working. Alert on the rate of restarts instead
Do not alert at allWhy
CPU > 80%Not a symptom. High CPU with good latency is efficient use of hardware; low CPU with bad latency is the actual problem
Memory > 80%The JVM is supposed to use its heap. Alert on OOM kills or GC pause time instead
Individual query slownessCause, not symptom. It matters only if it moves the latency SLO
Any downstream's healthTheir on-call owns it; you care whether your users are affected

The one I would fight hardest to include is the throughput-collapse alert. Every other alert on the list assumes the failure produces errors or latency. The failures that cause the most damage often produce neither — a misordered permitAll(), a bad feature flag, a validation change that silently rejects valid input. Orders simply stop, with a 200 status and a healthy p99. Comparing against the same time last week handles daily and weekly seasonality without a hand-tuned threshold.

The one I would fight hardest to remove is CPU. It is the most commonly configured alert and it fires when nothing is wrong, which is how a team learns to dismiss pages — and that habit is what makes the real alert get missed.

Every page needs a runbook link stating what to check first. An alert nobody knows how to act on is an interruption, not a control.

6 (hard): A user reports "checkout failed around 2:15pm". Design the observability that answers this in under two minutes, and be honest about the cost.
Solution

The goal is that the user's report contains a key that finds everything. Without one, this question is an archaeology project regardless of how many dashboards exist.

  1. TRACE ID EVERYWHERE -- the foundation

     filter (first in the chain):
       traceId = header X-Trace-Id, validated, else a new UUID
       MDC.put("traceId", traceId)
       response.setHeader("X-Trace-Id", traceId)
       finally { MDC.clear(); }        // pooled threads!

     - in every log line, via the log pattern
     - in every error response body
     - SHOWN IN THE UI on the error screen, and in the support form
     - propagated to downstream calls via traceparent

  2. STRUCTURED LOGS -- queryable by field, not grep

     logstash-logback-encoder -> JSON with traceId, userId, uri,
     status, durationMs as FIELDS

  3. TRACING WITH TAIL-BASED SAMPLING

     management.tracing.sampling.probability: 0.1

     10% head sampling means a 90% chance the one trace you need
     does not exist. Tail-based sampling -- keep 100% of errors and
     slow requests, sample the rest -- is what makes tracing useful
     for support rather than only for aggregate analysis.

The two-minute path, with the trace id: paste it into the log search → every line for that request across every service, with the exception and the failing downstream call → open the trace → see exactly which span failed and how long each took. Done.

Without a trace id, the path is: filter logs to a five-minute window and the checkout endpoint; find 4,000 requests; guess at the user id if you have one; find nothing if the failure was a 200 with a wrong body. That is the difference the twenty-line filter buys.

CostHonest assessment
Structured logs are larger2–3× the volume of plain text; the storage bill is real
Tail-based sampling needs a collectorAn OpenTelemetry collector to operate — genuine infrastructure, not a library
Trace ids in the UIA product change; someone must design the error screen
Log retention"Around 2:15pm" may be days ago. 30 days of structured logs is expensive; 7 days is not enough for this question
PII in logsStructured logging makes it easier to log too much. Needs a review discipline and probably redaction

What I would build first if I had one day: the filter, the log pattern, and the trace id in error responses. That is most of the value for a fraction of the cost, and it works even without tracing infrastructure, because a trace id in structured logs already answers the question.

What I would defer: tail-based sampling. It is the correct end state and it needs a collector, a rollout and tuning. Head sampling at 10% plus complete structured logs answers the support question adequately, because the logs are not sampled — the trace merely adds the timing breakdown.

The thing I would raise that is not technical: the support form must capture the trace id, and the error screen must show it in a way a user will actually copy. If it is in small grey text at the bottom, nobody sends it and the entire investment is wasted. That is a design conversation, and it determines whether any of this works.

🎯 Key Takeaways

  • Liveness asks "should this process be killed?"; readiness asks "should it receive traffic?" Conflating them turned a 40-second blip into a 20-minute outage.
  • A downstream dependency is never a liveness failure — restarting your process does not fix someone else's database.
  • Readiness should be fast and sensitive; liveness slow and reluctant. Removing traffic is cheap; killing destroys warm state.
  • Use a startupProbe so a slow boot never forces you to weaken liveness thresholds.
  • Never put a downstream HTTP service in a health check — cascading failure, plus 8,640 pings/hour at a struggling dependency.
  • Export hikaricp.connections.pending — pool starvation appears there first, while query latency still looks normal.
  • Export executor queue depth — 1.9M queued tasks accumulated with every other metric healthy.
  • Percentiles cannot be averaged. Averaging p99 across instances is arithmetically meaningless and wrong in either direction.
  • Export histogram buckets and aggregate with histogram_quantile — counts are additive, percentiles are not.
  • Enable histograms per metric, not globally — one series per bucket per tag combination.
  • Cardinality is multiplicative. One customerId tag created 2.4M series, OOM'd Prometheus, and cost more than the service's compute.
  • If you cannot list a tag's possible values, it is not a tag. High-cardinality data belongs in logs and traces.
  • Spring tags URIs with the mapping template, so /orders/42 and /orders/43 share a series — do not rebuild it from getRequestURI().
  • A gauge holds a weak reference to its source; if it is collected the gauge reports NaN forever, silently.
  • A trace id in the MDC, logs, and error responses is the highest-value twenty lines in observability.
  • Head sampling at 10% means the trace you need probably does not exist — tail-based sampling keeps every error and slow request.
  • exposure.include: "*" exposes /heapdump — every secret in memory, downloadable — and a writable /loggers.
  • Put Actuator on a separate management port. An exposure list is one edit from wrong; a network boundary is not.
