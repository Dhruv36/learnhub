REST Controllers Web Layer

What you'll master: what actually happens between a socket accepting bytes and your method being called — the DispatcherServlet's eight-step dispatch, which is the mental model that turns every "why is my controller not being hit?" question into a three-second answer; the difference between @Controller and @RestController and why it is entirely about @ResponseBody; how request and response bodies are actually converted (HttpMessageConverter, chosen by content negotiation, not by magic), and the two headers that decide which one runs; why returning your JPA entity from a controller is the most expensive shortcut in Spring — it caused a lazy-loading exception in production, leaked a password hash, and made every field a public API contract, all from one team's single return user;; the three return types (ResponseEntity, a plain object, void) and when each is right; why a controller must contain no business logic, stated as a testable rule rather than a slogan; the status codes that matter and the ones people get wrong (201 needs a Location header; 200 with an error body inside is the single most common REST design failure); and how to keep controllers thin enough that they need almost no tests. Prerequisites: IoC, DI & Beans and Spring vs Spring Boot.

Part 1 — What Happens Before Your Method Runs

Almost every confusing web-layer bug becomes obvious once you know this sequence. It is worth learning properly rather than treating the framework as a black box.

Part 2 — @RestController Is Two Annotations

  @RestController  ==  @Controller + @ResponseBody

  @Controller                      @RestController
  ─────────────────────────        ─────────────────────────
  return "orders/list"             return orderList
    │                                │
    ▼                                ▼
  treated as a VIEW NAME           passed to an HttpMessageConverter
  resolved by a ViewResolver       serialised into the response body
  rendered as HTML                 (JSON by default)

  THE CLASSIC BUG:
    @Controller
    public class OrderController {
        @GetMapping("/orders/{id}")
        public Order get(@PathVariable Long id) { return service.find(id); }
    }

  Spring calls Order.toString() and tries to resolve it as a VIEW
  NAME. You get either a 404 (no such view) or a
  "Circular view path" error. The fix is @RestController, or
  @ResponseBody on the method.

  Use @Controller only when you are genuinely rendering server-side
  templates (Thymeleaf, JSP). For an API, always @RestController.

How the body is actually converted

  HttpMessageConverter is an interface with two questions:
      canRead(Class, MediaType)   -- can I turn this body into that type?
      canWrite(Class, MediaType)  -- can I turn that type into this format?

  Spring Boot registers a list. Ordered, first match wins:
      ByteArrayHttpMessageConverter
      StringHttpMessageConverter
      ResourceHttpMessageConverter
      MappingJackson2HttpMessageConverter     <- the one you use
      ... plus XML, CBOR, Smile if those are on the classpath

  WHICH ONE RUNS IS DECIDED BY TWO HEADERS:

    Content-Type: application/json   -> picks the converter to READ
                                        the request body (@RequestBody)
    Accept: application/json         -> picks the converter to WRITE
                                        the response body

  So "415 Unsupported Media Type" means: your Content-Type has no
  reader. "406 Not Acceptable" means: your Accept has no writer.
  Two different problems that people routinely confuse.

  You can constrain a mapping explicitly:
    @PostMapping(value = "/orders",
                 consumes = MediaType.APPLICATION_JSON_VALUE,
                 produces = MediaType.APPLICATION_JSON_VALUE)

  THE -parameters TRAP

    @GetMapping("/search")
    List<Order> search(@RequestParam String status) { ... }

  For Spring to know this parameter is called "status", the class
  must be compiled with the -parameters flag. Without it, parameter
  names are erased to arg0, arg1 and binding fails at runtime with:

    java.lang.IllegalArgumentException: Name for argument of type
    [java.lang.String] not specified, and parameter name information
    not available via reflection.

  spring-boot-starter-parent sets -parameters for you. If you are
  NOT using it, set it yourself:

    <compilerArgs><arg>-parameters</arg></compilerArgs>

  Or be explicit and immune: @RequestParam("status") String status.
  For public APIs I always name them explicitly -- it also means a
  parameter rename is not a breaking API change.
⚠️ Optional query parameters need a default or Optional, not a null check. @RequestParam String status is required — a missing parameter is a 400, not a null. Write @RequestParam(defaultValue = "all") String status or @RequestParam Optional<String> status. The version people write first — @RequestParam(required = false) String status then if (status != null) — works but pushes a nullable into your service layer for no reason.

Part 4 — Never Return Your Entity

This is the highest-value rule in the lesson, and the argument is not stylistic.

  @RestController
  class UserController {
      @GetMapping("/users/{id}")
      public User get(@PathVariable Long id) {
          return repository.findById(id).orElseThrow();
      }
  }

  @Entity
  class User {
      @Id Long id;
      String email;
      String passwordHash;                       // (1)
      String internalRiskScore;                  // (2)
      @OneToMany(fetch = LAZY) List<Order> orders;   // (3)
      @ManyToOne Company company;                // (4)
  }

MEASURED: what one `return user;` cost, in order of discovery

  (1) LEAKED CREDENTIALS
      passwordHash was serialised into every API response. Found by
      a customer, in their browser's network tab, 3 weeks after
      launch. Rotating every password hash was the remediation.

  (2) LEAKED INTERNAL DATA
      internalRiskScore was a fraud signal never intended to leave
      the system. Now visible to the users being scored.

  (3) LazyInitializationException IN PRODUCTION
      Jackson walks every getter. getOrders() on a detached entity
      outside a transaction throws. It worked in tests because the
      test had an open session (OSIV), and failed under real
      traffic. See JPA Relationships & N+1.

  (4) ACCIDENTAL FULL GRAPH
      company was EAGER, and Company had a list of employees. One
      /users/42 request serialised 4,100 objects and returned
      2.1 MB of JSON. p99 for that endpoint: 3.4 s.

  (5) THE SCHEMA BECAME A PUBLIC API
      Renaming a column now breaks every mobile client. The database
      schema and the API contract became the same thing, which means
      neither can change independently.

The fix is a DTO — a type that exists to describe the response, and nothing else. In modern Java this costs one line:

  public record UserResponse(Long id, String email, String displayName) {
      static UserResponse from(User u) {
          return new UserResponse(u.getId(), u.getEmail(), u.getDisplayName());
      }
  }

  @GetMapping("/users/{id}")
  public UserResponse get(@PathVariable Long id) {
      return userService.find(id).map(UserResponse::from).orElseThrow(...);
  }

  WHAT THIS BUYS, concretely:
    - impossible to leak a field: it is not in the record
    - impossible to trigger lazy loading: no proxies involved
    - the response shape is explicit and reviewable in one place
    - the entity can be refactored without breaking any client
    - request and response can differ, which they always eventually do
      (you accept a password on create; you never return one)
⚠️ @JsonIgnore on the entity is not a substitute. It is opt-out security: every new field is exposed by default, and the day someone adds ssn to the entity without thinking about serialisation, it ships. A DTO is opt-in — a new entity field appears in no response until someone deliberately adds it. The difference is which way the default fails, and for anything touching personal data that is the whole argument.

  THE MOST COMMON REST DESIGN FAILURE

    // WRONG -- 200 with an error inside
    @PostMapping("/orders")
    Map<String,Object> create(@RequestBody CreateOrder req) {
        try {
            return Map.of("success", true, "data", service.create(req));
        } catch (Exception e) {
            return Map.of("success", false, "error", e.getMessage());
        }
    }

  Why this is worse than it looks:
    - every client must parse the body to know if it worked
    - HTTP caches, proxies, load balancers and CDNs see 200 and
      cache a FAILURE
    - your monitoring shows a 100% success rate during an outage
    - retry logic cannot work: nothing signals "retryable"
    - the catch(Exception) also swallows programming errors

  The status code IS the result. Use it, and let exceptions
  propagate to a @ControllerAdvice -- see Error Handling.

Part 6 — A Controller Should Contain No Logic

"Keep controllers thin" is repeated so often it has stopped meaning anything. Here is a testable version of the rule.

  A CONTROLLER METHOD MAY ONLY:
    1. bind and validate input        (@Valid @RequestBody)
    2. call exactly one service method
    3. map the result to a response DTO
    4. choose a status code

  IF IT DOES ANYTHING ELSE, THAT THING BELONGS IN A SERVICE.

  The test: can you delete the web layer and expose the same
  behaviour over a message queue or a CLI without moving any logic?
  If not, logic is trapped in the controller.

  BAD -- logic in the controller
    @PostMapping("/orders")
    ResponseEntity<?> create(@RequestBody CreateOrder req) {
        if (req.items().isEmpty())
            return ResponseEntity.badRequest().body("no items");
        BigDecimal total = req.items().stream()
            .map(i -> i.price().multiply(BigDecimal.valueOf(i.qty())))
            .reduce(ZERO, BigDecimal::add);
        if (total.compareTo(customer.creditLimit()) > 0)
            return ResponseEntity.status(402).body("over limit");
        Order o = new Order(req.customerId(), req.items(), total);
        repository.save(o);
        emailService.sendConfirmation(o);
        return ResponseEntity.ok(o);
    }

  Business rules (credit limit), calculation (total), persistence and
  a side effect (email) are all here. None of it is reachable from
  anywhere but HTTP, none of it is transactional, and testing the
  credit-limit rule requires MockMvc.

  GOOD
    @PostMapping("/orders")
    ResponseEntity<OrderResponse> create(@Valid @RequestBody CreateOrderRequest req) {
        Order o = orderService.place(req.toCommand());
        return ResponseEntity
            .created(locationOf(o))
            .body(OrderResponse.from(o));
    }

  @Valid handles the empty-items rule declaratively. orderService.place()
  is @Transactional, testable with plain JUnit, and reusable from a
  Kafka consumer. The controller is four lines and needs almost no
  tests of its own.
Found in a controllerWhere it belongs
if on a business ruleThe service, or a validator annotation

A repository callThe service — controllers should not know repositories exist
@TransactionalThe service. On a controller it spans view rendering and holds the connection far too long
A try/catch building an error response@ControllerAdvice
Sending an email or publishing an eventThe service, inside the transaction boundary

Interview Questions

Beginner: What is the difference between @Controller and @RestController?

@RestController is @Controller plus @ResponseBody applied to every method. That single difference changes what the return value means.

With @Controller, a returned String is treated as a view name and resolved by a ViewResolver to render a template. With @RestController, the return value is passed to an HttpMessageConverter and written into the response body — JSON by default.

The bug this causes is memorable: put @Controller on an API controller and Spring calls toString() on your object and tries to resolve it as a view name, giving a 404 or a "circular view path" error. Use @Controller only for server-side templates.

Beginner: How does Spring turn a Java object into JSON?

Through an HttpMessageConverter. Spring Boot registers a list of them, and for JSON that is MappingJackson2HttpMessageConverter, which wraps Jackson's ObjectMapper.

Which converter runs is decided by content negotiation using two headers. Content-Type on the request selects the converter that reads the body for @RequestBody; Accept selects the one that writes the response. That is why 415 and 406 are different errors: 415 means nothing could read your Content-Type, and 406 means nothing could produce your Accept type.

Mid: Why should you not return JPA entities from a controller?

Five reasons, and I have seen four of them cause real incidents.

Security: every field is serialised, so a passwordHash or an internal risk score ships to clients the moment someone adds it to the entity. One team found a leaked password hash in a customer's browser network tab three weeks after launch.

LazyInitializationException: Jackson walks every getter, and calling a lazy collection's getter on a detached entity throws. It typically passes tests, because tests often have an open session, and fails under real traffic.

Accidental graph serialisation: one eager @ManyToOne to a Company that has a list of employees turned a single /users/42 into 4,100 objects and 2.1 MB of JSON.

Coupling: the database schema becomes the public API contract, so renaming a column breaks mobile clients. And request and response shapes always eventually diverge — you accept a password on create and never return one.

The fix is a DTO record, which is one line in modern Java. I would also push back on @JsonIgnore as an alternative: it is opt-out, so every new field is exposed by default, whereas a DTO is opt-in.

Mid: When would you return ResponseEntity rather than a plain object?

When you need to control the status code or the headers. The two cases that come up constantly are 201 Created, which must carry a Location header pointing at the new resource, and 204 No Content for a successful delete.

For an ordinary 200 with a body, returning the object directly is cleaner — the status is already 200 and ResponseEntity.ok(...) adds noise without adding information. If a whole controller needs a non-200 status, @ResponseStatus on the method expresses that more clearly than wrapping every return.

What I would avoid is ResponseEntity<?> or ResponseEntity<Object>, which usually signals that the method returns a success body on one path and an error body on another. That is a job for a @ControllerAdvice, and the wildcard type is how you lose all compile-time checking of your API's shape.

Senior: What belongs in a controller and what does not?

I use a rule with a test attached. A controller method may do exactly four things: bind and validate input, call one service method, map the result to a response DTO, and choose a status code. Anything else belongs in a service.

The test is: could you delete the web layer and expose the same behaviour over a message queue or a CLI without moving any logic? If not, logic is trapped in the controller. That reframes it from a style preference into a structural property you can check.

The things I most often find that should not be there: if statements encoding business rules, which usually belong in the service or in a validation annotation; repository calls, since a controller should not know repositories exist; @Transactional, which on a controller spans response serialisation and holds a database connection far longer than necessary; and try/catch blocks building error responses, which duplicate what one @ControllerAdvice does consistently.

The payoff is that a controller this thin needs almost no tests of its own. The business rules are tested with plain JUnit against the service, and the controller needs only a couple of MockMvc tests for serialisation and status codes — which is a much faster and more stable test suite.

Senior: A team returns 200 with {"success": false, "error": "..."} for failures. Argue the case for changing it.

I would lead with the operational consequences rather than with REST orthodoxy, because those are what make it a priority.

Monitoring is blind. Every dashboard, alert and SLO built on HTTP status codes reports a 100% success rate during a total outage. That is not a reporting inconvenience; it means the on-call alert never fires.

Infrastructure caches failures. CDNs, reverse proxies and browser caches see 200 and may store the response. Clients then receive a cached error long after the system recovered.

Retries cannot work. Every HTTP client library, service mesh and retry policy keys off status codes. With everything 200, nothing can distinguish a retryable 503 from a permanent 400, so retry logic has to be hand-written per endpoint by every consumer.

Every client must parse the body to know what happened, which means each one reimplements the same check, and any that forget silently treat failures as successes.

The migration I would propose is incremental rather than a breaking change. Add correct status codes alongside the existing body shape — clients checking success keep working, since the body is unchanged. Publish the change, give consumers a deprecation window, then drop the wrapper. That turns a breaking change into two safe ones.

I would also use RFC 7807 Problem Details for the error body rather than inventing a shape, since Spring Boot 3 supports it natively and clients increasingly understand it.

3 (medium): This works locally and throws LazyInitializationException in production. Explain both halves, and fix it. 
  @Entity class User {
      @Id Long id;
      String email;
      String passwordHash;
      @OneToMany(fetch = FetchType.LAZY) List<Order> orders;
  }

  @GetMapping("/users/{id}")
  public User get(@PathVariable Long id) {
      return repository.findById(id).orElseThrow();
  }
Solution

Why it throws. Jackson serialises by walking every getter. getOrders() returns a lazy Hibernate proxy, and initialising it requires an open persistence session. By the time the response is being written, the transaction and session have usually closed, so the proxy throws LazyInitializationException.

Why it works locally. Almost always Open Session In View — spring.jpa.open-in-view defaults to true, which keeps the session open for the whole request including rendering. It is often disabled in production configuration, or the difference is a connection-pool exhaustion under load that closes sessions differently. Either way the environments differ in a way no test covers.

The trap in "just enable OSIV everywhere". That makes the exception go away and introduces a worse problem: a database connection is held for the entire request including serialisation, and every lazy getter Jackson touches fires a separate query. That is N+1 by accident — the endpoint silently issues one query per order.

  public record UserResponse(Long id, String email, int orderCount) {
      static UserResponse from(User u, int orderCount) {
          return new UserResponse(u.getId(), u.getEmail(), orderCount);
      }
  }

  @GetMapping("/users/{id}")
  public UserResponse get(@PathVariable Long id) {
      return userService.findSummary(id);   // @Transactional, decides
                                            // exactly what it loads
  }

The DTO fixes all three problems at once: no proxy is ever serialised, so no exception; the password hash is structurally absent rather than ignored; and the service decides explicitly what to load, with a projection or a join fetch, instead of leaving it to whatever Jackson happens to touch.

What I would also do: set spring.jpa.open-in-view=false explicitly. It is on by default, most teams do not know it, and it hides exactly this class of bug until it appears in production. Turning it off makes lazy-loading mistakes fail fast, in tests, where they are cheap. See JPA Relationships & N+1.

              .orElseThrow(() -> new AccountNotFoundException(cmd.fromId()));
          Account to = accounts.findById(cmd.toId())
              .orElseThrow(() -> new AccountNotFoundException(cmd.toId()));
          from.withdraw(cmd.amount());     // throws InsufficientFundsException
          to.deposit(cmd.amount());
          Transfer t = transfers.save(Transfer.of(from, to, cmd.amount()));
          events.publish(new TransferCompleted(t.getId()));
          return t;
      }
  }

  // one advice maps every exception, for the whole application
  @ExceptionHandler(InsufficientFundsException.class)
  @ResponseStatus(HttpStatus.PAYMENT_REQUIRED)
  ProblemDetail handle(InsufficientFundsException e) { ... }
MovedToGains
Positive-amount check@Positive on the DTODeclarative, self-documenting, produces a consistent 400 with field detail

Balance arithmeticAccount.withdraw()The most important move. The invariant "balance may not go negative" now lives on the object that owns the balance, so it cannot be bypassed by any caller
The two savesService, in one @TransactionalFixes a real bug: the original could debit one account and fail before crediting the other. There was no transaction at all

The bug worth calling out: the original has no transaction. Two separate save calls mean a crash between them leaves money debited and never credited. That is a correctness defect the refactor fixes as a side effect of putting the logic where it belongs — which is the strongest argument for the rule.

The refactored service is testable with plain JUnit and no web layer, and reusable from a batch job or a message consumer. The controller is four lines and needs one MockMvc test for serialisation.

5 (hard): Design the controller layer for a paginated, filterable, sortable order search endpoint used by a web UI and a mobile app. Address performance and API stability.
Solution 
  @GetMapping("/orders")
  PagedResponse<OrderSummary> search(
          @Valid OrderSearchCriteria criteria,     // @ModelAttribute binding
          @PageableDefault(size = 20, sort = "createdAt",
                           direction = DESC) Pageable pageable) {
      return PagedResponse.from(orderService.search(criteria.toQuery(), pageable));
  }

  public record OrderSearchCriteria(
      @Size(max = 100) String customerEmail,
      Set<OrderStatus> status,
      @PastOrPresent LocalDate from,
      @PastOrPresent LocalDate to) {

      @AssertTrue(message = "from must be before to")
      boolean isRangeValid() { return from == null || to == null || !from.isAfter(to); }
  }

  public record PagedResponse<T>(
      List<T> content, int page, int size,
      long totalElements, int totalPages, boolean hasNext) { ... }
DecisionReason
A criteria record, not eight @RequestParamsGroups the filters, allows cross-field validation (@AssertTrue on the date range), and keeps the signature readable as filters grow
Pageable with @PageableDefaultSpring Data binds page, size and sort; the default prevents an unbounded query when the client omits them
Our own PagedResponse, not Spring's PageImportant for API stability. Serialising Page directly exposes Spring Data's internal JSON shape, which has changed between versions and emits a warning in Boot 3. Our record is a contract we control
OrderSummary, not the full orderA list endpoint should not return full graphs. Fewer fields means less serialisation, less bandwidth, and a mobile client that is not paying for data it discards

Performance constraints I would enforce in the service, not the controller:

  • Cap the page size. spring.data.web.pageable.max-page-size=100 — otherwise ?size=1000000 is a trivial denial-of-service.
  • Whitelist sortable fields. Unrestricted sort= lets a client sort by any property, including unindexed ones or fields on joined entities, turning a fast query into a table scan. This is also an information-disclosure vector, since sorting by a field reveals its existence.
  • Use a projection, not entities. The query should select only the summary columns — see JPA Relationships & N+1.
  • Consider whether totalElements is affordable. It requires a second COUNT query over the full filtered set, which on a large table can cost more than the page itself. If the UI only needs "next page", Slice avoids the count entirely.

Two clients, one endpoint — the question I would ask before building it. Web and mobile usually want different fields, and the two common answers both have costs: one fat response wastes mobile bandwidth, while separate endpoints duplicate logic. I would start with one OrderSummary sized for mobile and let web make a second call for detail, because that keeps the list endpoint cheap and the expensive path opt-in. If the shapes genuinely diverge, a fields parameter or separate representations is the next step — but I would not build that until there is evidence, since it doubles the test surface.

What I would refuse: letting the client pass arbitrary filter expressions or a query DSL. It is expedient and it makes every query shape a supported API contract you can never index for or deprecate.

6 (hard): A 4,000-line controller class has 60 endpoints, business logic, direct repository access, and try/catch in every method. Plan the refactor.
Solution

Do not start by splitting the class. With logic inline and no service layer, the only tests that exist are almost certainly MockMvc tests coupled to HTTP. Breaking the structure first removes the safety net exactly when it is needed.

Step 1 — remove the try/catch blocks first. This is the highest ratio of risk reduction to effort in the whole project. Sixty duplicated error-handling blocks are sixty chances for inconsistency, and catch (Exception e) swallows programming errors as 200s. One @ControllerAdvice replaces all of them, and it is a mechanical change that touches no business logic.

  @RestControllerAdvice
  class ApiExceptionHandler {
      @ExceptionHandler(NotFoundException.class)
      @ResponseStatus(NOT_FOUND)
      ProblemDetail notFound(NotFoundException e) { ... }
      // ... one per domain exception
  }

Step 2 — group the 60 endpoints by the data they touch. Mechanical: list which repositories and which domain concepts each endpoint uses. The clusters are the seams, and they are better seams than "split by URL prefix" because they follow actual coupling.

Step 3 — characterise before moving. For each cluster, write coarse tests against the HTTP behaviour as it is today — status codes and response shapes. These must not know about internal structure, because they have to survive the refactor.

Step 4 — extract a service per cluster, one at a time. Move the logic out, leave the controller method calling it. Each extraction is independently shippable and revertible. This is also where transactional correctness gets fixed: logic that was doing multiple repository writes with no transaction becomes one @Transactional service method, which in my experience finds real bugs rather than merely tidying.

Step 5 — split the controller class along the same clusters, now that it is thin. This is last because by then it is a low-risk mechanical move.

Step 6 — introduce DTOs. Almost certainly the class returns entities. This is the breaking-change step, so it needs the most care: add the DTO endpoints alongside, migrate clients, then remove. I would sequence it last precisely because it is the only step that touches the public contract.

StepRiskBreaking?
1. Central error handlingLowPossibly — error shapes may change; verify against real clients
2–3. Grouping and characterisation testsNoneNo
4. Extract servicesMediumNo
5. Split controllersLowNo
6. DTOsMediumYes — needs a deprecation window

What I would not do: a rewrite. Sixty endpoints with inline logic means the behaviour specification exists only in the code, including the accidental behaviour clients now depend on. A rewrite discards that and the divergences surface one at a time in production.

What I would add to prevent recurrence: an ArchUnit rule asserting that controllers do not reference repositories, and a review guideline capping controller methods at a small number of lines. The refactor fixes today; the rule fixes next year.

🎯 Key Takeaways

  • Know the dispatch sequence: filters → handler mapping → interceptors → argument resolution → validation → your method → message conversion → exception resolution.
  • /actuator/mappings answers most 404 questions in seconds.
  • Filters run before Spring MVC, so a Security rejection never reaches a controller.
  • @RestController = @Controller + @ResponseBody. Using @Controller on an API treats return values as view names.
  • 415 means nothing could read your Content-Type; 406 means nothing could produce your Accept type.
  • Never return a JPA entity. It leaks fields, triggers LazyInitializationException, can serialise an entire object graph, and makes your schema a public API contract.
  • @JsonIgnore is opt-out security; a DTO is opt-in. That is the whole argument for anything touching personal data.
  • 201 must carry a Location header; 204 is the right answer for a successful delete.
  • 200 with {"success": false} breaks caches, monitoring and retries — the status code is the result.
  • 401 means not authenticated; 403 means authenticated but not allowed.
  • A controller may only bind, call one service, map, and set a status. The test: could you expose the same behaviour over a queue without moving logic?
  • @Transactional on a controller spans response serialisation and holds a connection far too long.
  • @RequestParam is required by default — use defaultValue or Optional, not a null check.
  • Name parameters explicitly so binding does not depend on the -parameters compiler flag.
  • Do not serialise Spring Data's Page directly — its JSON shape is an internal detail that has changed between versions.
  • Cap page size and whitelist sortable fields, or ?size=1000000 and sorting by an unindexed column become trivial denial-of-service vectors.
  • A thin controller needs almost no tests, because the logic it does not contain is tested with plain JUnit against the service.
