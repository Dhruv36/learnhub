Caching, Async & Scheduling Cross-Cutting

What you'll master: three features that share one implementation — proxies — and therefore share one family of silent failures, plus three quite different sets of production hazards; why the hardest part of caching is not caching but invalidation, and the four strategies with the measured staleness each accepts; the @Cacheable defaults that will hurt you — an unbounded ConcurrentHashMap with no TTL and no eviction, which is a memory leak with a friendly annotation; the cache stampede that turned one expired key into 340 simultaneous identical queries and a database outage, and the one-parameter fix; why @Async returning void discards every exception so failures vanish without a log line; the executor defaults that make @Async dangerous — an unbounded queue means a slow downstream turns into an OutOfMemoryError rather than backpressure; and why @Scheduled on more than one replica runs your "nightly" job once per instance, with the three ways to fix it ranked by what they actually guarantee. Prerequisites: AOP & Proxies and Transactions.

Part 1 — All Three Are Proxies

  @EnableCaching     -> CacheInterceptor
  @EnableAsync       -> AsyncExecutionInterceptor
  @EnableScheduling  -> a post-processor that REGISTERS tasks
                        (not an interceptor -- see below)

  SO ALL THE PROXY RULES FROM AOP & PROXIES APPLY:

    self-invocation      -> no caching, no async, silently
    private method       -> ignored
    final method         -> ignored
    new SomeService()    -> no proxy at all

  THE MOST COMMON VERSION:

    @Service
    class PriceService {
        public List<Price> all(List<Long> ids) {
            return ids.stream().map(this::lookup).toList();   // this.
        }

        @Cacheable("prices")
        public Price lookup(Long id) { ... }        // NEVER CACHED
    }

  Every lookup recomputes. The cache is populated only by external
  callers, so hit rates look inexplicably low and the fix looks
  like "the cache isn't working".

  DIAGNOSE:
    logging.level.org.springframework.cache: TRACE
    logging.level.org.springframework.aop: DEBUG
🔑 @Scheduled is the odd one out. It is not an interceptor around your call — a post-processor scans beans at startup and registers the method with a TaskScheduler. So self-invocation is irrelevant, but a different rule applies: the method must take no arguments, and it will be invoked whether or not anything else in your application ever calls it. That also means a @Scheduled method on a @Component in a library you imported starts running as soon as it is on the classpath.

Part 2 — Caching: the Defaults Are a Trap

  @EnableCaching
  @Cacheable("products")
  public Product find(Long id) { ... }

  WITH NO CACHE PROVIDER ON THE CLASSPATH, Spring Boot gives you
  ConcurrentMapCacheManager:

      a ConcurrentHashMap.  That is all.

      no maximum size      -> grows until OutOfMemoryError
      no TTL               -> entries never expire
      no eviction policy   -> nothing is ever removed
      no statistics        -> you cannot measure the hit rate
      per-instance         -> 6 replicas = 6 divergent caches

  It is a MEMORY LEAK WITH A FRIENDLY ANNOTATION, and it is the
  default. It works beautifully in a demo with 20 products and
  fails in production with 4 million.

  MINIMUM VIABLE CACHE -- Caffeine, one dependency:

    implementation 'com.github.ben-manes.caffeine:caffeine'

    spring.cache.caffeine.spec: >
      maximumSize=10000,expireAfterWrite=10m,recordStats

  Now it is bounded, entries expire, and /actuator/metrics exposes
  cache.gets{result=hit|miss} so you can see whether it works.
ProviderScopeUse when
ConcurrentMapCacheManagerOne JVM, unboundedNever in production
CaffeineOne JVM, bounded, TTLDefault choice. Nanosecond reads, no network
RedisShared across instancesWhen replicas must agree, or the cache must survive restarts
Two-level (Caffeine + Redis)BothHigh read volume where a Redis round trip per read is too slow
  THE ANNOTATIONS

    @Cacheable("products")                  read through
    @CachePut("products")                   always execute, then store
    @CacheEvict("products")                 remove
    @CacheEvict(value="products", allEntries=true)
    @Caching(evict = { @CacheEvict(...), @CacheEvict(...) })

  KEY GENERATION -- the default is a hazard

    Default: SimpleKeyGenerator over ALL parameters.

    @Cacheable("orders")
    public List<Order> search(SearchCriteria c, Pageable p) { ... }

    The key is SimpleKey[criteria, pageable]. If SearchCriteria has
    no equals/hashCode, every call is a cache MISS and the cache
    only grows. Silent, and the symptom is a 0% hit rate.

    BE EXPLICIT:
      @Cacheable(value = "products", key = "#id")
      @Cacheable(value = "orders", key = "#customerId + ':' + #status")

  CONDITIONS

    @Cacheable(value="products", condition = "#id != null",
               unless = "#result == null")

    condition -- evaluated BEFORE the call, on arguments
    unless    -- evaluated AFTER, and can see #result

    `unless = "#result == null"` is almost always wanted: without it
    you cache the absence of a product forever.

Part 3 — Invalidation and Stampedes

  "There are only two hard things in computer science: cache
   invalidation and naming things."

  FOUR STRATEGIES, and what staleness each accepts:

  1. TTL ONLY                     staleness ≤ the TTL
     Simplest. Correct when data changes rarely and bounded
     staleness is acceptable. Most caches should be this.

  2. EVICT ON WRITE               staleness ≈ 0 in one instance
     @CacheEvict(value="products", key="#product.id")
     public Product update(Product product) { ... }
     Correct only if ALL writes go through this method. A bulk
     @Modifying update, another service, or a DBA bypasses it.

  3. WRITE-THROUGH                staleness ≈ 0
     @CachePut(value="products", key="#result.id")
     Updates the cache with the new value rather than removing it.
     Beware: it caches BEFORE the transaction commits (Part 6).

  4. EVENT-DRIVEN                 staleness = propagation delay
     Publish a change event; every instance evicts its local copy.
     The only approach that works across replicas with a local
     cache.

MEASURED: the cache stampede

  @Cacheable("product-catalog")     // TTL 10 minutes
  public Catalog load() { ... }     // a 2.1 s query

  At the moment the entry expires:
    - 340 concurrent requests all miss
    - ALL 340 execute the 2.1 s query simultaneously
    - the database saturates; query time rises to 19 s
    - requests time out; the retry storm makes it worse
    - the cache is never repopulated because every attempt fails

  A single key expiring took the service down for 6 minutes.

  THE FIX -- one parameter:

    @Cacheable(value = "product-catalog", sync = true)

  sync=true makes Spring hold a lock per key: one thread computes,
  the other 339 wait for its result. 340 queries become 1.

  Not all providers support it (Caffeine and Redis do,
  ConcurrentMapCacheManager does). It is the single most valuable
  cache setting nobody uses.

  ALSO CONSIDER for very hot keys:
    - refresh-ahead: Caffeine's refreshAfterWrite serves the stale
      value while ONE thread refreshes in the background
    - jittered TTLs, so 10,000 keys written together do not all
      expire in the same second
⚠️ The synchronised-expiry problem is easy to miss. If you warm a cache at startup, every entry gets the same expireAfterWrite and therefore expires within the same millisecond ten minutes later — turning one stampede into thousands. Add jitter to the TTL, or use refreshAfterWrite so entries are refreshed in the background before they are ever evicted.

Part 4 — @Async: Exceptions and Executors

  @Async
  public void sendEmail(Order o) {
      throw new MailException("SMTP down");
  }

  WHERE DOES THAT EXCEPTION GO?

  NOWHERE. The caller received a void return immediately and moved
  on. The exception is thrown on a pool thread with no handler, and
  by default it is logged by SimpleAsyncUncaughtExceptionHandler --
  at a level and format nobody is watching. In practice, failures
  vanish.

  TWO FIXES, and you want both:

  1. RETURN A FUTURE so the caller can observe failure
     @Async
     public CompletableFuture<Receipt> send(Order o) {
         return CompletableFuture.completedFuture(mailer.send(o));
     }
     Exceptions surface when the caller calls get()/join().

  2. A GLOBAL HANDLER for the void cases you cannot avoid
     @Configuration
     class AsyncConfig implements AsyncConfigurer {
         @Override
         public AsyncUncaughtExceptionHandler
                 getAsyncUncaughtExceptionHandler() {
             return (ex, method, params) ->
                 log.error("Async failure in {} args={}",
                           method.getName(), Arrays.toString(params), ex);
         }
     }

  THE EXECUTOR DEFAULT IS WORSE THAN THE EXCEPTION PROBLEM

  Spring Boot's auto-configured applicationTaskExecutor:

     core pool size    8
     max pool size     Integer.MAX_VALUE
     queue capacity    Integer.MAX_VALUE     <-- the problem

  Because the queue is unbounded, the pool NEVER grows past 8:
  a ThreadPoolExecutor only adds threads when the queue is FULL,
  and this one never fills. So:

    - throughput is capped at 8 concurrent tasks, always
    - a slow downstream causes tasks to accumulate in the queue
    - the queue grows until the heap is exhausted
    - you get OutOfMemoryError, not backpressure

  MEASURED: a mail service degraded from 200 ms to 8 s. Within
  40 minutes the queue held 1.9M tasks and the JVM died. No alert
  fired, because CPU, latency and error rate all looked normal --
  the queue is invisible unless you export it.

  CONFIGURE IT EXPLICITLY:

    @Bean("taskExecutor")
    ThreadPoolTaskExecutor taskExecutor(MeterRegistry registry) {
        var ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(8);
        ex.setMaxPoolSize(32);
        ex.setQueueCapacity(500);              // BOUNDED
        ex.setThreadNamePrefix("async-");
        ex.setRejectedExecutionHandler(
            new ThreadPoolExecutor.CallerRunsPolicy());   // backpressure
        ex.setWaitForTasksToCompleteOnShutdown(true);
        ex.setAwaitTerminationSeconds(20);
        ex.initialize();
        return ExecutorServiceMetrics.monitor(registry, ex, "async");
    }
Rejection policyBehaviour when the queue is fullUse when
AbortPolicy (default)Throws RejectedExecutionExceptionYou want to fail loudly and shed load
CallerRunsPolicyThe submitting thread runs the taskUsually right — it applies natural backpressure by slowing the producer
DiscardPolicySilently drops the taskAlmost never — silent data loss
DiscardOldestPolicyDrops the oldest queued taskOnly where the newest value supersedes older ones

Part 5 — @Scheduled and Multiple Replicas

  @Scheduled(cron = "0 0 2 * * *")     // "nightly at 02:00"
  public void generateReports() { ... }

  DEPLOYED TO 6 REPLICAS: it runs SIX TIMES, at 02:00, in parallel.

  Consequences seen in practice:
    - six copies of every report emailed to customers
    - six concurrent bulk jobs competing for the same rows,
      deadlocking each other
    - a payment reconciliation job double-crediting accounts

  THREE FIXES, and they guarantee different things:
ApproachGuaranteeCost
A profile / property so only one replica schedulesNone — a deploy or restart can produce zero or twoFree, and fragile
ShedLock (a database lock)At most one execution per windowOne table, one dependency. Usually right
A separate single-replica deploymentAt most one, with isolationA second deployment to operate
An external scheduler (Kubernetes CronJob, Quartz clustered)At most one, with retries and historyMost machinery; right when jobs are first-class
  SHEDLOCK -- the pragmatic default

    @Scheduled(cron = "0 0 2 * * *")
    @SchedulerLock(name = "generateReports",
                   lockAtMostFor = "55m",     // released if the JVM dies
                   lockAtLeastFor = "1m")     // guards against clock skew
    public void generateReports() { ... }

  lockAtMostFor is the important one: if the instance holding the
  lock crashes, the lock must expire or the job never runs again.
  Set it comfortably above the expected duration and below the
  interval.

  THE SCHEDULER'S OWN DEFAULT IS ALSO A TRAP:

    Spring's default TaskScheduler is SINGLE-THREADED.

    Two @Scheduled methods, one of which takes 10 minutes, means
    the other does not run for 10 minutes. Three jobs, one hangs,
    and NOTHING is scheduled ever again.

    spring.task.scheduling.pool.size: 5

  And @Scheduled methods never overlap themselves: fixedDelay and
  cron both wait for the previous run of the SAME method to finish.
  If a nightly job takes 25 hours, you silently skip a day.

Part 6 — The Transaction Interactions

  TRAP 1: @Async INSIDE A TRANSACTION LOSES THE TRANSACTION

    @Transactional
    public void place(Order o) {
        orders.save(o);
        notifier.notifyAsync(o);      // @Async -- DIFFERENT THREAD
    }

    The transaction is a ThreadLocal. The async method runs with NO
    transaction, and worse, it may run BEFORE the outer transaction
    commits -- so it can read a database that does not yet contain
    the order it was told about.

    FIX:
      @TransactionalEventListener(phase = AFTER_COMMIT)
      @Async
      public void onOrderPlaced(OrderPlaced e) { ... }

    Guaranteed to run after commit, and on another thread.

  TRAP 2: @Cacheable CACHES BEFORE COMMIT

    @Transactional
    @CachePut(value = "orders", key = "#result.id")
    public Order update(OrderCommand cmd) { ... }

    If the cache advice runs inside the transaction and the
    transaction then rolls back, the cache holds a value that was
    never persisted -- served to every subsequent caller until it
    expires.

    FIXES:
      - order the aspects so caching is OUTSIDE the transaction
      - or use a transaction-aware cache manager:
          @Bean
          CacheManager cacheManager(CacheManager delegate) {
              var m = new TransactionAwareCacheManagerProxy(delegate);
              return m;     // defers writes until after commit
          }

  TRAP 3: @Scheduled + @Transactional ON THE SAME METHOD

    Works, but the transaction spans the ENTIRE job. A job
    processing a million rows holds one transaction for an hour,
    which on PostgreSQL blocks vacuum and bloats tables.

    Chunk it: the scheduled method loops, and calls a separate
    @Transactional bean per chunk.

Interview Questions

Beginner: How does @Cacheable work?

A proxy intercepts the call, builds a key from the method arguments, and looks it up in the named cache. On a hit it returns the cached value without invoking your method at all; on a miss it invokes the method and stores the result.

Because it is a proxy, it has the usual limitation: calling the method from within the same class bypasses it entirely, so the cache is silently never used.

The thing to know beyond the mechanism is that Spring Boot's default cache manager is an unbounded ConcurrentHashMap — no size limit, no TTL, no eviction. It is fine for a demo and a memory leak in production, so a real cache provider such as Caffeine is effectively mandatory.

Beginner: What happens to an exception thrown in an @Async void method?

It is lost, for practical purposes. The caller got its void return the moment the task was submitted, so there is nothing to propagate to. The exception surfaces on a pool thread and is passed to SimpleAsyncUncaughtExceptionHandler, which logs it in a form nobody is monitoring.

The fix is to return a CompletableFuture so the caller can observe the failure when it joins, and to configure an AsyncUncaughtExceptionHandler via AsyncConfigurer for the void cases that genuinely cannot return anything. I would do both — the handler is the safety net for code you did not write.

Mid: What is a cache stampede and how do you prevent it?

When a hot cache entry expires, every concurrent request misses simultaneously and they all execute the expensive operation at once. I have seen a 2.1-second catalogue query run by 340 threads in the same instant; the database saturated, query time rose to 19 seconds, requests timed out, and because every attempt failed the cache was never repopulated. One key expiring took the service down for six minutes.

The direct fix is @Cacheable(sync = true), which makes Spring hold a per-key lock so one thread computes and the rest wait for its result. Caffeine and Redis support it. It is one parameter and almost nobody sets it.

Two related measures matter at scale. Uniform TTLs are dangerous — if you warm a cache at startup, every entry expires in the same millisecond later, turning one stampede into thousands, so TTLs want jitter. And Caffeine's refreshAfterWrite serves the stale value while a single thread refreshes in the background, which avoids the miss entirely for keys that are read continuously.

Mid: What is wrong with Spring Boot's default task executor?

Its queue is unbounded, and that has two consequences people do not expect.

First, the pool never grows. A ThreadPoolExecutor only creates threads beyond the core size when the queue is full, and an unbounded queue never fills — so despite a maximum pool size of Integer.MAX_VALUE, you permanently have 8 threads.

Second, and worse, there is no backpressure. If a downstream dependency slows down, tasks accumulate in memory until the heap is exhausted. I have seen a mail service degrade from 200 ms to 8 seconds and the queue reach 1.9 million tasks in forty minutes before the JVM died — with no alert firing, because CPU, latency and error rate all looked normal. Queue depth is invisible unless you export it.

So I would always define the executor explicitly with a bounded queue, and use CallerRunsPolicy so that when it fills, the submitting thread runs the task and the producer slows down. That converts a memory leak into natural backpressure. And I would register the executor with Micrometer so queue depth is a metric with an alert on it.

Senior: How do you run a scheduled job exactly once across six replicas?

The first thing to say is that "exactly once" is not achievable — the honest target is "at most once per window, with the job itself idempotent". Any lock can be lost to a crash or a clock problem, so the job must tolerate being re-run.

My default is ShedLock: a shared database table where the instance acquires a named lock before running. It needs one table and one dependency, and the parameter that matters is lockAtMostFor — if the instance holding the lock dies, the lock must expire or the job never runs again. I set it comfortably above the expected duration and below the interval.

The alternatives: a profile or property so only one replica schedules is free and fragile, because a rolling deploy can leave you with zero or two. A separate single-replica deployment gives real isolation and is worth it when the job is heavy enough to disturb request serving. An external scheduler — a Kubernetes CronJob or clustered Quartz — is the right answer when jobs need retries, history and alerting, at the cost of more machinery.

Two adjacent defaults I would check at the same time. Spring's TaskScheduler is single-threaded, so one long job blocks every other scheduled task — and if it hangs, nothing is scheduled ever again. And a @Scheduled method never overlaps itself, so a nightly job that takes 25 hours silently skips a day rather than running twice.

Senior: How do caching and async interact with transactions?

Three interactions, and all three produce wrong data rather than errors.

@Async inside a transaction loses the transaction, because it is a ThreadLocal. Worse than having no transaction, the async task can run before the outer transaction commits, so it queries a database that does not yet contain the row it was told about. The symptom is an intermittent "record not found" that only appears under load. The fix is @TransactionalEventListener(phase = AFTER_COMMIT) combined with @Async, which guarantees ordering and still moves the work off the request thread.

Caching can store a value that is then rolled back. If the cache advice runs inside the transaction, a @CachePut writes the new value and a subsequent rollback leaves the cache holding something that was never persisted — served to every caller until it expires. Either order the aspects so caching is outermost, or use TransactionAwareCacheManagerProxy, which defers cache writes until after commit.

@Transactional on a whole scheduled job holds one transaction for the entire run. On PostgreSQL an hour-long transaction blocks vacuum and bloats tables, which is a database-wide problem caused by one job. Chunking — the scheduled method loops and calls a separate transactional bean per batch — is the fix, and it also makes the job restartable.

The common thread is that all three come from combining declarative features whose boundaries are invisible at the call site. That is an argument for keeping them on separate methods in separate beans, where the ordering is explicit in the call graph.

  public class PriceLookup {

Verify rather than assume: recordStats plus Actuator exposes cache.gets{result=hit} and {result=miss}, so the hit rate becomes a dashboard number. 2 (easy): Emails silently stop sending. No errors anywhere. Explain. 
  @Async
  public void sendConfirmation(Order order) {
      mailClient.send(buildMessage(order));    // throws MailException
  }
Solution

An @Async void method has nowhere to report failure. The caller received its void return the instant the task was submitted and moved on. The exception is thrown on a pool thread with no caller to propagate to, and Spring's default SimpleAsyncUncaughtExceptionHandler logs it in a form that is easy to miss and not attributable to a request.

So the mail fails, the order flow reports success, and nothing correlates the two.

  // 1. return a future so failure is observable
  @Async
  public CompletableFuture<Void> sendConfirmation(Order order) {
      return CompletableFuture.runAsync(() -> mailClient.send(buildMessage(order)));
  }

  // 2. a global handler for the void cases you cannot avoid
  @Configuration
  @EnableAsync
  class AsyncConfig implements AsyncConfigurer {
      @Override
      public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
          return (ex, method, params) -> {
              log.error("Async failure in {}.{} args={}",
                        method.getDeclaringClass().getSimpleName(),
                        method.getName(), Arrays.toString(params), ex);
              failureCounter.increment();     // and a metric
          };
      }
  }

The metric matters as much as the log. A log line for a failure nobody is looking for is barely better than silence; a counter with an alert on it turns "emails stopped three weeks ago" into a page within minutes.

The design question underneath: if sending the confirmation genuinely must not be lost, @Async is the wrong mechanism entirely — an in-memory task queue disappears on restart. That is a job for the transactional outbox from Transactions, where the intent is committed with the order and a separate process retries it. @Async is appropriate for work that is genuinely best-effort.

3 (medium): A nightly job runs six times and double-credits accounts. Fix it and say what your fix does and does not guarantee. 
  @Component
  public class ReconciliationJob {
      @Scheduled(cron = "0 0 2 * * *")
      @Transactional
      public void reconcile() {
          List<Payment> pending = payments.findUnreconciled();  // 400k rows
          for (Payment p : pending) accounts.credit(p);
      }
  }
Solution

Three separate problems.

ProblemEffect
Six replicas all schedule itSix concurrent runs, each crediting the same payments — accounts credited up to six times
@Transactional over 400k rowsOne transaction for the whole run: on PostgreSQL it blocks vacuum for the duration and bloats tables. It is also all-or-nothing, so an hour of work is lost on any failure
No idempotencyEven with one runner, a retry after a partial failure re-credits
  @Component
  public class ReconciliationJob {
      private final ReconciliationChunk chunk;      // separate bean

      @Scheduled(cron = "0 0 2 * * *")
      @SchedulerLock(name = "reconcile",
                     lockAtMostFor = "55m", lockAtLeastFor = "1m")
      public void reconcile() {
          List<Long> ids;
          while (!(ids = payments.findUnreconciledIds(500)).isEmpty())
              chunk.process(ids);                   // own transaction each
      }
  }

  @Service
  public class ReconciliationChunk {
      @Transactional
      public void process(List<Long> ids) {
          for (Payment p : payments.findAllById(ids)) {
              if (p.isReconciled()) continue;             // idempotent
              accounts.credit(p);
              p.markReconciled();                          // same tx
          }
      }
  }
FixGuaranteesDoes not guarantee
ShedLockAt most one runner per windowThat it runs at all — if the holder crashes, the run is skipped until lockAtMostFor expires
Chunked transactionsRestartable; bounded transaction ageAll-or-nothing — a mid-run failure leaves some chunks committed
markReconciled in the same transactionIdempotency — the real safety netNothing further; this is what makes re-runs safe

The idempotency check is the part that actually protects the money. Locks can be lost — to a crash, a clock skew, a network partition — so a design whose correctness depends on the lock holding is fragile. Marking each payment reconciled in the same transaction as the credit means a second run is a no-op regardless of how many runners there are.

I would also add spring.task.scheduling.pool.size: 5, because the default scheduler is single-threaded and a 55-minute job would otherwise block every other scheduled task in the application.

4 (medium): After a downstream slowdown, the service died with OutOfMemoryError while CPU, latency and error rate all looked normal. Explain and fix.
Solution

An unbounded async queue. Spring Boot's auto-configured executor has core size 8 and an effectively unbounded queue. When the downstream slowed, tasks arrived faster than they completed and accumulated in that queue — in memory, invisibly.

The monitoring looked healthy because every metric being watched was about requests: the controller returned immediately after submitting the task, so latency and error rate were unaffected, and 8 busy threads generate little CPU. Queue depth is the only signal that would have shown it, and it was not exported.

There is a second, subtler consequence: because the queue never fills, the pool never grows past its core size of 8, so maxPoolSize is meaningless and throughput is capped no matter how many cores the machine has.

  @Bean("taskExecutor")
  ThreadPoolTaskExecutor taskExecutor(MeterRegistry registry) {
      var ex = new ThreadPoolTaskExecutor();
      ex.setCorePoolSize(8);
      ex.setMaxPoolSize(32);
      ex.setQueueCapacity(500);                       // BOUNDED
      ex.setThreadNamePrefix("async-");
      ex.setRejectedExecutionHandler(
          new ThreadPoolExecutor.CallerRunsPolicy()); // backpressure
      ex.setWaitForTasksToCompleteOnShutdown(true);
      ex.setAwaitTerminationSeconds(20);
      ex.initialize();
      return ExecutorServiceMetrics.monitor(registry, ex, "async");
  }
SettingWhat it changes
queueCapacity(500)Memory is bounded, and the pool can now grow to 32 when the queue fills
CallerRunsPolicyWhen the queue is full, the submitting thread runs the task. The producer slows down — genuine backpressure rather than a crash
ExecutorServiceMetrics.monitorExports queue depth, active threads and completed tasks to Micrometer
waitForTasksToCompleteOnShutdownQueued work is not silently discarded on a rolling deploy

The alert that matters: executor.queued above roughly half of capacity for several minutes. That fires long before memory becomes a problem and points directly at the slow downstream.

The trade-off CallerRunsPolicy makes explicit: under sustained overload, the request thread does the async work, so request latency rises. That is the correct failure mode — the system slows down visibly instead of accumulating invisible debt and then dying — but it should be a conscious choice, because it turns an async path into a synchronous one exactly when the system is under stress.

5 (hard): Design caching for a product catalogue: 2 million products, 50,000 reads/sec, updates from an admin UI and a nightly import, six replicas, staleness tolerance of one minute.
Solution

The numbers decide the architecture. 50,000 reads/sec against Redis alone would be 50,000 network round trips per second — feasible but costly in latency and Redis CPU. Two million products will not fit comfortably in each replica's heap. So neither a purely local nor a purely remote cache is right.

  TWO-LEVEL CACHE

    L1  Caffeine, per replica
        maximumSize = 20,000            (hot subset, ~1% of catalogue)
        expireAfterWrite = 60s          (matches the staleness budget)
        refreshAfterWrite = 45s         (background refresh, no miss)

    L2  Redis, shared
        TTL = 10 minutes
        holds the full working set; survives replica restarts

    read:  L1 -> L2 -> database
    write: update DB, then invalidate BOTH levels
DecisionReason
L1 sized at ~1% of the catalogueProduct access is heavily skewed; a small hot set absorbs most reads at nanosecond latency and near-zero cost
L1 TTL = 60sThe staleness budget is the invalidation mechanism for L1 — no cross-replica messaging needed for correctness
refreshAfterWrite below the TTLHot keys are refreshed in the background and never miss, which eliminates stampedes on exactly the keys that would cause them
Redis as L2Shared across replicas, survives restarts, and absorbs the L1 misses so the database sees very little
sync = trueProtects the database on a cold start or a mass eviction
  INVALIDATION -- different for the two write paths

  1. ADMIN UI (single product)
       @Transactional
       public Product update(ProductCommand cmd) { ... }

       @TransactionalEventListener(AFTER_COMMIT)
       void onProductChanged(ProductChanged e) {
           redisCache.evict(e.id());              // L2, immediate
           events.publish(e);                     // fan out to replicas
       }
       // each replica evicts its own L1 on receiving the event

     AFTER_COMMIT matters: evicting before commit lets a concurrent
     read repopulate the cache with the OLD value.

  2. NIGHTLY IMPORT (bulk, ~2M rows)
       Do NOT evict 2 million keys individually.
       Bump a version prefix instead:

         key = "products:v" + currentVersion + ":" + id

       Incrementing currentVersion invalidates the entire cache in
       one operation, and old entries expire naturally by TTL.

Why the version-prefix trick for the import: two million individual evictions would take minutes, saturate Redis, and leave the cache in a half-updated state during the run. A version bump is atomic and O(1) — at the cost of a cold cache afterwards, which is why I would run the import before the traffic peak and warm the top few thousand products immediately after.

The honest limitation: L1 gives up to 60 seconds of staleness per replica, so two users hitting different replicas can briefly see different prices. That is exactly the stated tolerance, but it is the kind of thing that must be confirmed with the business rather than assumed — for prices specifically, "briefly showing an old price" can have contractual implications, and if so the answer is to skip L1 for price fields and accept the Redis round trip.

What I would measure from day one: hit rate per level. If L1 is below about 80% the sizing is wrong; if L2 is low the TTL is too short or the key space is fragmented. Without those two numbers, tuning is guesswork.

6 (hard): An order-placed flow needs to send an email, update a search index, and notify a partner API. Design it, and justify what is synchronous, asynchronous, or neither.
Solution

Start by classifying each side effect by what happens if it is lost, because that determines the mechanism far more than latency does.

Side effectIf lostMechanism
Email confirmationCustomer is confused; recoverable by resendAsync, best-effort, with a failure metric
Search index updateStale search results; self-heals on the next reindexAsync, best-effort
Partner notificationContractual breach; the partner never ships the orderOutbox — must not be lost
  @Transactional
  public Order place(PlaceOrderCommand cmd) {
      Order o = orders.save(Order.from(cmd));

      // MUST NOT BE LOST -> committed with the order
      outbox.save(OutboxMessage.of("PARTNER_NOTIFY", o.getId()));

      // best-effort -> after commit
      events.publish(new OrderPlaced(o.getId()));
      return o;                                    // commits in ~5 ms
  }

  @TransactionalEventListener(phase = AFTER_COMMIT)
  @Async("notificationExecutor")
  public void onOrderPlaced(OrderPlaced e) {
      mailer.sendConfirmation(e.orderId());
      searchIndexer.index(e.orderId());
  }

  @Scheduled(fixedDelay = 500)
  @SchedulerLock(name = "outboxDispatch", lockAtMostFor = "2m")
  public void dispatchOutbox() {
      for (OutboxMessage m : outbox.claimBatch(50)) {
          try { partnerClient.notify(m); outbox.markDone(m); }
          catch (Exception ex) { outbox.markForRetry(m, backoff(m.attempts())); }
      }
  }
DecisionReason
No remote call inside the transactionA slow partner would hold a database connection and exhaust the pool — see Transactions
AFTER_COMMIT for the async workA plain @Async call inside the transaction can run before commit and query a database without the order
Outbox for the partner onlyIt is the only effect that must survive a crash. Applying the outbox to all three would be more machinery for no benefit
ShedLock on the dispatcherSix replicas would otherwise each poll and double-notify. Combined with an idempotency key on the partner call
A dedicated executorA bounded queue with CallerRunsPolicy, so a mail outage cannot exhaust the heap

The distinction I would emphasise: @Async is an in-memory queue. It disappears on restart, on OOM, on a rolling deploy. That is perfectly acceptable for an email that a customer can request again, and unacceptable for a partner notification with a contract behind it. Teams get into trouble by using one mechanism for both and discovering the difference during an incident.

What I would push back on: a request to make the partner notification synchronous "so we know it worked". It couples order placement to a third party's availability — the order would fail because the partner is down, which is precisely backwards. If the business needs confirmation, the answer is an order status that reflects partner acknowledgement, updated when the outbox dispatch succeeds, not a synchronous call in the request path.

🎯 Key Takeaways

  • Caching and async are proxies, so self-invocation silently disables both. @Scheduled is registered at startup instead, and needs a no-argument method.
  • Boot's default cache manager is an unbounded ConcurrentHashMap — no size limit, no TTL, no statistics. A memory leak with a friendly annotation.
  • Use Caffeine with maximumSize, expireAfterWrite and recordStats as the minimum viable cache.
  • Specify key explicitly. The default generator over argument objects without equals/hashCode gives a 0% hit rate, silently.
  • Add unless = "#result == null" or you cache "not found" forever.
  • sync = true prevents cache stampedes — 340 concurrent misses ran 340 identical 2.1 s queries and took a database down for six minutes.
  • Jitter TTLs or use refreshAfterWrite, or a warmed cache expires entirely within one millisecond.
  • A local cache with evict-on-write serves stale data on every other replica.
  • @Async void discards exceptions. Return CompletableFuture and configure an AsyncUncaughtExceptionHandler.
  • The default executor's unbounded queue means the pool never grows past 8 and a slow downstream causes OutOfMemoryError rather than backpressure.
  • Use a bounded queue with CallerRunsPolicy so the producer slows down instead of the heap filling.
  • Export queue depth. 1.9M queued tasks accumulated with CPU, latency and error rate all looking normal.
  • @Async loses the transaction and can run before commit — use @TransactionalEventListener(AFTER_COMMIT).
  • Caching inside a transaction can store a value that then rolls back. Use TransactionAwareCacheManagerProxy or order caching outermost.
  • @Scheduled runs once per replica. ShedLock is the pragmatic fix; job idempotency is what actually protects you.
  • The default TaskScheduler is single-threaded, so one long or hung job blocks every other scheduled task.
  • Never wrap a whole scheduled job in one transaction — chunk it, one transaction per batch.
  • @Async is an in-memory queue that disappears on restart. Anything that must not be lost needs an outbox.
