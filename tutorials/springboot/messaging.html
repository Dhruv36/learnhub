Messaging & Kafka Event-Driven

What you'll master: what a broker actually is — Kafka is a partitioned log, not a queue, and that one fact explains ordering, replay, consumer groups and every scaling limit you will hit; why ordering is guaranteed per partition and nowhere else, so a null key processed a cancellation before its order and shipped 214 cancelled items; the delivery guarantee nobody has — "exactly once" is a Kafka-to-Kafka property and says nothing about your database or the email you just sent; offset commits, where the default enable.auto.commit acknowledged 1,412 messages that were never processed; the rebalance death spiral, where processing slower than max.poll.interval.ms evicted a consumer every 5 minutes and rebuilt a 4.1M backlog it could never clear; the poison pill that blocked one partition for 9 hours while the others looked perfectly healthy; retry topics and the ordering they quietly trade away; schema evolution, where a required field broke every consumer still reading a 7-day retention window; consumer lag as the only metric that matters and the way it is usually alerted wrong; and when a database table is a better queue than Kafka. Prerequisites: Resilience & Microservices (the outbox), Transactions and Caching, Async & Scheduling.

Part 1 — A Log Is Not a Queue

  THE TWO MODELS, AND WHY THE DIFFERENCE IS NOT COSMETIC

  A QUEUE (RabbitMQ, SQS, ActiveMQ)
    - a message is DELIVERED, then ACKED, then DELETED
    - consumers compete; the broker decides who gets what
    - the broker tracks per-message state
    - once consumed, it is gone. No replay.
    - routing is rich: exchanges, bindings, topics, priorities

  A LOG (Kafka)
    - a message is APPENDED to a partition and stays for the
      retention period whether anyone read it or not
    - a CONSUMER tracks its own position: an OFFSET
    - reading does not remove anything
    - a new consumer group can start from offset 0 and replay
      everything that is still retained
    - routing is trivial: topic + partition. That is all.

  CONSEQUENCE 1: replay is free in a log and impossible in a
  queue. Add a new service, point it at the topic, and it can
  process six months of history.

  CONSEQUENCE 2: a slow consumer in a queue is a growing queue;
  in a log it is a growing OFFSET LAG, and if it lags past the
  retention window THE DATA IS SIMPLY GONE.

  THE ANATOMY THAT DECIDES EVERYTHING

    topic "orders", 6 partitions

      P0: [o1][o4][o9 ][o12] ...    <-- append only, ordered
      P1: [o2][o5][o7 ][o15] ...
      P2: [o3][o6][o11][o18] ...
      ...

    partition = hash(key) % partitionCount      (if a key is set)
    partition = sticky/round-robin              (if key is null)

    CONSUMER GROUP "billing", 3 consumers
      c1 -> P0, P1
      c2 -> P2, P3
      c3 -> P4, P5

    EACH PARTITION IS ASSIGNED TO EXACTLY ONE CONSUMER IN A GROUP.

  THE THREE RULES THAT FOLLOW, AND THEY ARE THE WHOLE MODEL:

  1. ORDER IS GUARANTEED WITHIN A PARTITION. Never across a topic.
  2. PARALLELISM IS BOUNDED BY PARTITION COUNT. A group with 10
     consumers on a 6-partition topic has 4 CONSUMERS DOING
     NOTHING, forever.
  3. THE KEY CHOOSES THE PARTITION, so the key is what decides
     which messages are ordered relative to each other.

MEASURED: a null key shipped 214 cancelled orders

  Producer published order events with no key:

    kafkaTemplate.send("orders", new OrderEvent(...));   // no key

  Two events for order 8891, 40 ms apart:
    OrderPlaced(8891)     -> partition 2
    OrderCancelled(8891)  -> partition 5

  Partition 2's consumer was 900 ms behind; partition 5's was
  current. So the fulfilment service processed:

    OrderCancelled(8891)   "cancel an order I have never seen" ->
                           logged a warning, ignored it
    OrderPlaced(8891)      "new order!" -> SHIPPED IT

  Over three weeks: 214 cancelled orders shipped, plus 1,900
  "cancellation for unknown order" warnings nobody read.

  THE FIX IS ONE ARGUMENT:
    kafkaTemplate.send("orders", order.getId().toString(), event);

  Now every event for order 8891 lands on the same partition and
  is processed in publication order, by definition.

  THE RULE: THE KEY IS THE ORDERING SCOPE. Pick the entity whose
  events must not overtake each other -- usually the aggregate
  id -- and use it as the key. Ordering across different keys is
  not something you are given, and designs that need it are
  designs that need rethinking.
NeedKafkaRabbitMQ / SQS
Replay history, add a consumer laterYes — the log is retained independently of consumptionNo — consumed messages are gone
Very high throughput, sequential I/OYes — millions/s on modest hardwareLower; per-message broker bookkeeping
Strict ordering per entityYes, via the keyOnly with a single consumer per queue
Per-message retry/delay/priorityAwkward — retry topics, and they break orderingNative — DLX, TTL, priorities, per-message ack

🔑 The question that picks the technology is not throughput, it is whether you need replay and per-entity ordering. Those are the two things a log gives you that a queue cannot, and they are worth real operational cost. If what you actually have is a work queue — independent tasks, each retryable on its own, order irrelevant — then Kafka's per-partition ordering is not a feature you are using, it is a constraint you are paying for, because one slow task blocks every message behind it on that partition.

Part 2 — Delivery Guarantees and the Offset Commit

  THE THREE GUARANTEES, AND WHICH ONE YOU ACTUALLY HAVE

  AT MOST ONCE    commit the offset BEFORE processing.
                  Crash after the commit = the message is never
                  processed. Loss is possible, duplicates are not.

  AT LEAST ONCE   commit the offset AFTER processing.
                  Crash before the commit = the message is
                  processed again. Duplicates are possible, loss
                  is not.   <-- WHAT YOU WANT, ALMOST ALWAYS

  EXACTLY ONCE    Kafka transactions: consume, produce and commit
                  offsets atomically, WITHIN KAFKA.

  THE SENTENCE THAT MATTERS ABOUT EXACTLY-ONCE:

    It applies to Kafka-to-Kafka pipelines. The moment your
    consumer writes to a database, calls an API, or sends an
    email, that side effect is NOT in the Kafka transaction, and
    exactly-once says nothing about it.

  So for a service that consumes an event and writes to Postgres,
  the honest design is:

      at-least-once delivery + an IDEMPOTENT CONSUMER

  which gives you effectively-once processing, and is achievable
  with tools you already have.

MEASURED: auto-commit acknowledged 1,412 unprocessed messages

  Default consumer configuration:
    enable.auto.commit: true
    auto.commit.interval.ms: 5000

  WHAT AUTO-COMMIT ACTUALLY DOES: on poll(), if 5 s have elapsed,
  it commits the offsets of everything RETURNED BY THE PREVIOUS
  POLL -- regardless of whether your code finished with them.

    10:14:02.0  poll() returns 500 records
    10:14:02.1  processing starts
    10:14:07.0  poll() called again -> COMMITS all 500
                (only 88 have actually been processed)
    10:14:07.4  pod is evicted mid-batch
    10:14:31    new consumer starts from the committed offset

  412 records in that batch were never processed and never will
  be. Across the incident: 1,412 orders silently missing from
  the billing service. Found by a finance reconciliation three
  weeks later.

  THE FIX -- Spring Kafka, explicit acknowledgement:

    spring.kafka.consumer.enable-auto-commit: false
    spring.kafka.listener.ack-mode: RECORD

    @KafkaListener(topics = "orders", groupId = "billing")
    public void handle(OrderEvent e) {
        billingService.process(e);      // throws -> NOT committed
    }

  With RECORD, Spring commits after your listener returns
  normally, per record. An exception means no commit, so the
  record is redelivered. That is at-least-once, and it is the
  behaviour almost everyone assumed they already had.
ack-modeCommits whenUse it when
RECORDAfter each record's listener returnsThe safe default. Most commits, least reprocessing on failure
BATCH (Spring's default)After all records from one poll() are processedHigher throughput; a crash reprocesses the whole batch
TIME / COUNTAfter an interval or a record countRarely — you are trading a defined guarantee for throughput
MANUALYou call ack.acknowledge(); committed at the end of the batchWhen commit must follow your own transaction boundary
MANUAL_IMMEDIATEYou call ack.acknowledge(); committed at onceLong-running per-record work where you must not reprocess
  THE IDEMPOTENT CONSUMER -- what makes at-least-once acceptable

  DUPLICATES ARE NOT AN EDGE CASE. They happen on every
  rebalance, every crash, every deploy, and every retry. Design
  for them or be surprised by them.

  OPTION 1 -- a dedupe table (works for anything)

    @Transactional
    public void handle(OrderEvent e) {
        try {
            processed.insert(e.eventId());     // unique PK
        } catch (DuplicateKeyException dup) {
            return;                            // already done
        }
        billing.charge(e);       // same transaction as the insert
    }

    The insert and the effect COMMIT TOGETHER, so there is no
    window where one happened and the other did not. Add a TTL
    job; the table is not allowed to grow forever.

  OPTION 2 -- make the write naturally idempotent (better)

    UPDATE orders SET status = 'PAID' WHERE id = ? AND status = 'PENDING';
    INSERT ... ON CONFLICT (id) DO NOTHING;
    UPDATE inventory SET qty = ? WHERE sku = ? AND version = ?;

    No bookkeeping at all. An absolute assignment applied twice
    is the same as applied once -- which is why "set status to
    PAID" is safe and "decrement stock by 1" is not.

  OPTION 3 -- version/sequence checks (for ordered updates)

    UPDATE customer SET email = ?, last_event_seq = ?
     WHERE id = ? AND last_event_seq < ?;

    Also protects against an OUT-OF-ORDER replay overwriting
    newer data with older data, which a plain dedupe does not.
⚠️ The most common broken pattern is a consumer that writes to the database and publishes another event. That is the dual write from Resilience & Microservices, one layer along: the database commit and the produce are not atomic, so a crash between them either loses the downstream event or emits one for work that rolled back. The answer is the same — write the outgoing event to an outbox table inside the same transaction and let a relay publish it. Kafka transactions do not help here, because your database is not a participant in them.

Part 3 — Consumers, Polling, and the Rebalance Death Spiral

  THE CONSUMER LOOP, AND THE TWO CLOCKS PEOPLE CONFUSE

    while (true) {
        records = consumer.poll(timeout);   // fetches a BATCH
        process(records);                   // your code
        commit();
    }

  CLOCK 1 -- session.timeout.ms (default 45 s)
    A background HEARTBEAT thread proves the consumer is alive.
    Miss heartbeats for this long and the group evicts you.
    Independent of your processing. Rarely the problem.

  CLOCK 2 -- max.poll.interval.ms (default 300 s = 5 minutes)
    The maximum time allowed BETWEEN POLLS. If your processing
    of one batch takes longer than this, the broker concludes the
    consumer is stuck and REVOKES ITS PARTITIONS -- even though
    the heartbeat thread is happily beating.

  THE SECOND ONE IS WHERE OUTAGES COME FROM, because it depends
  on max.poll.records (default 500) times your per-record time:

      500 records x 800 ms  =  400 seconds  >  300 second limit
      -> evicted, mid-batch, on every single poll

MEASURED: the rebalance death spiral, and a 4.1M backlog

  A consumer began calling a downstream service that had slowed
  from 60 ms to 800 ms per record.

    T+0     poll() returns 500 records
    T+300s  max.poll.interval exceeded (only 372 done)
            -> broker revokes partitions
            -> REBALANCE: the whole group stops consuming
    T+305s  partitions reassigned; the batch restarts FROM THE
            LAST COMMITTED OFFSET -- 372 records reprocessed
    T+605s  the same thing happens again
    ...

    over 4 hours:
      rebalances                            47
      time the group spent NOT consuming    ~38 minutes
      records processed more than once      181,000
      consumer lag                          4.1 MILLION and rising
      CPU on the consumers                  11%

  THE SPIRAL: slow processing causes eviction; eviction causes
  reprocessing; reprocessing means MORE work; the group never
  catches up, and every rebalance stops every consumer in the
  group, not just the slow one.

  THE FIXES, in order of effect:

  1. REDUCE THE BATCH so a poll cycle fits comfortably:
       max.poll.records: 50           # 50 x 800ms = 40 s << 300 s

  2. RAISE THE CEILING only if the work is genuinely long:
       max.poll.interval.ms: 900000   # 15 min
     (the cost: a genuinely dead consumer is detected 15 min late)

  3. FIX THE PROCESSING -- the 800 ms downstream call needs the
     timeout and circuit breaker from the Resilience lesson.
     A consumer inherits every latency problem of what it calls.

  4. COOPERATIVE REBALANCING so a rebalance does not stop the
     whole group:
       partition.assignment.strategy:
         org.apache.kafka.clients.consumer.CooperativeStickyAssignor

  CONCURRENCY IN SPRING KAFKA IS PARTITIONS, NOT THREADS

    @KafkaListener(topics = "orders", concurrency = "6")

  This creates 6 consumer instances in this application, each
  taking whole partitions. So:

    topic has 6 partitions, concurrency 6   -> 1 partition each
    topic has 6 partitions, concurrency 12  -> 6 IDLE CONSUMERS
    topic has 6 partitions, 3 pods x 4      -> 6 idle again

  THE HARD CEILING: total consumers in a group <= partitions.
  Scaling out past the partition count does nothing at all,
  which is the most common "we added pods and it did not get
  faster" in Kafka.

  AND PARTITIONS ARE NEARLY IMMUTABLE:
    - you can ADD partitions to a topic
    - adding them CHANGES hash(key) % count, so existing keys
      move to different partitions, and ordering across the
      change is broken for every key that moves
    - you can NEVER reduce them

  So partition count is a capacity decision made early, with
  little room to correct. Size for future parallelism (2-3x
  current need is a common rule), and accept the small cost of
  extra partitions rather than the large cost of re-keying a
  live topic.
🔑 A Kafka consumer is a scheduled batch job with a deadline, and thinking of it that way prevents most of these failures. Every poll must finish its work before max.poll.interval.ms; anything slow, remote or unbounded inside the listener eats that budget. That is why remote calls in a listener need the same timeouts and breakers as anything else, why max.poll.records is a real tuning parameter rather than a default to ignore, and why genuinely long work belongs somewhere else — the listener should record the intent and hand off, not do forty minutes of processing while the broker waits.

Part 4 — Poison Pills, Retries, and the Dead Letter Topic

MEASURED: one message blocked a partition for 9 hours

  A producer published an event with a malformed timestamp.
  The consumer's deserialiser threw before the listener ran.

    03:12  record at offset 88,214 fails deserialisation
    03:12  the container catches it, does not commit, and
           re-polls -- FROM THE SAME OFFSET
    03:12  fails again. And again. ~40 times per second.
    ...
    12:07  a human notices lag on partition 3

  During those 9 hours:
    partition 3 lag                 612,000 and climbing
    partitions 0,1,2,4,5            perfectly healthy, zero lag
    total consumer lag on a graph   looked "slightly elevated"
    error log lines                 1.3 million identical
    records processed on p3         zero

  THIS IS THE DEFINING KAFKA FAILURE MODE. A queue would have
  redelivered the bad message and moved on; a log CANNOT skip an
  offset without committing past it, so an unhandled failure at
  offset N means offset N+1 is never reached.

  AND IT HIDES: five of six partitions were fine, so every
  aggregate dashboard looked acceptable. Alert on MAX lag across
  partitions, never on the sum or the average.

  DESERIALISATION ERRORS NEED A DIFFERENT FIX FROM LOGIC ERRORS

  A deserialisation failure happens BEFORE your listener, so no
  listener-level error handler can see it. Wrap the deserialiser:

    spring.kafka.consumer:
      key-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.ErrorHandlingDeserializer
      properties:
        spring.deserializer.key.delegate.class: org.apache.kafka.common.serialization.StringDeserializer
        spring.deserializer.value.delegate.class: org.springframework.kafka.support.serializer.JsonDeserializer

  Now a bad payload arrives at your listener as a null value with
  the exception in the record headers, so the normal error
  handler can route it to a dead letter topic instead of looping
  forever.

  BLOCKING RETRY -- DefaultErrorHandler (the default in Boot 3)

    @Bean
    DefaultErrorHandler errorHandler(KafkaTemplate<?,?> template) {
        var recoverer = new DeadLetterPublishingRecoverer(template);
        var backoff   = new ExponentialBackOffWithMaxRetries(3);
        backoff.setInitialInterval(500);
        backoff.setMultiplier(2.0);

        var handler = new DefaultErrorHandler(recoverer, backoff);
        handler.addNotRetryableExceptions(       // never retry
            ValidationException.class,
            JsonProcessingException.class);
        return handler;
    }

  WHAT IT DOES: retries the record IN PLACE, blocking the
  partition, then publishes it to <topic>.DLT and commits past
  it so the partition can continue.

  + ORDER IS PRESERVED: nothing overtakes the failing record
  - the partition STALLS for the whole retry sequence:
      3 retries x (0.5 + 1 + 2 s) = 3.5 s of nothing else
    which is fine for 3 retries and catastrophic for 10 with
    long backoffs

  CLASSIFY BEFORE YOU RETRY. A validation error will fail
  identically forever; retrying it three times just triples the
  stall. Only transient failures -- a timeout, a 503, a lock
  conflict -- deserve a retry at all.

  NON-BLOCKING RETRY -- @RetryableTopic

    @RetryableTopic(
        attempts = "4",
        backoff = @Backoff(delay = 1000, multiplier = 3),
        dltStrategy = DltStrategy.FAIL_ON_ERROR)
    @KafkaListener(topics = "orders", groupId = "billing")
    public void handle(OrderEvent e) { ... }

  Spring creates the topics for you:
    orders            -> fails
    orders-retry-0    (after 1 s)
    orders-retry-1    (after 3 s)
    orders-retry-2    (after 9 s)
    orders-dlt

  + the MAIN partition is never blocked; throughput continues
  + long backoffs become affordable

  - ORDERING IS GONE FOR THAT KEY. The failed record is now
    seconds or minutes behind records that came after it. If
    OrderPlaced fails and retries while OrderCancelled succeeds,
    the cancellation is processed first.

  THE CHOICE IS THE TRADE-OFF, and it is a domain question:

    ordering matters for this key   -> blocking retry, few
                                       attempts, then DLT
    independent records            -> retry topics, generous
                                       backoff
FailureRetry?Where it should end up
Deserialisation error / malformed payloadNeverStraight to the DLT — it will fail identically forever, and it blocks the partition until it does
Validation failure (business rule)NeverDLT, or a domain "rejected" event. It is data, not an outage
Downstream timeout / 503YesRetry with backoff; DLT only after the breaker and retries are exhausted
Optimistic lock conflictYes, immediatelyA short retry almost always succeeds — this is what retries are for
Referenced entity does not exist yetYes, with delayUsually an ordering problem. Retry with a delay, but fix the key or the producer
Bug in your consumerNoDLT — then fix the code and replay the DLT, which is the whole reason to keep it
⚠️ A dead letter topic that nobody reads is a data-loss mechanism with extra steps. The DLT exists so a partition can make progress, which means every message in it is work that silently did not happen. It needs three things the day it is created: an alert on > 0 messages (not on a threshold — one is already a problem), enough headers to understand the failure (Spring's recoverer adds the exception, stack trace, original topic, partition and offset), and a documented replay path. Without the replay path the DLT is a landfill, and teams discover months later that it holds fourteen thousand orders.

Part 5 — Events Are a Published Contract

  THE SAME PROBLEM AS API VERSIONING, WITH A LONGER TAIL

  An HTTP response is consumed the instant it is produced. An
  event sits in a topic for the retention period -- 7 days, 30
  days, or forever on a compacted topic -- and may be read:

    - now, by three services on three different versions
    - tomorrow, by a consumer catching up after an outage
    - next month, by a new service replaying from offset 0
    - during an incident, by someone reprocessing history

  So a schema change is not "coordinate two deploys". It is
  "every version of this event that still exists must remain
  readable by every consumer that still exists".

MEASURED: a required field broke a 7-day window

  Producer added a required `channel` field to OrderPlaced, and
  updated its own Avro schema. Consumers using the old schema:

    org.apache.avro.AvroTypeException: missing required field

  - live traffic broke immediately for 2 of 5 consumer groups
  - and so did EVERY event in the 7-day retention window, so
    rolling the producer back did not restore consumption; the
    already-published events were still unreadable
  - one consumer group was down for 6 h 20 m, and had to be
    fixed forward under pressure at 23:00
Compatibility modeGuaranteesYou may
BACKWARD (the usual default)New consumers can read old dataDelete a field; add an optional field with a default. Upgrade consumers first
FORWARDOld consumers can read new dataAdd a field; delete an optional one. Upgrade producers first
FULLBoth directionsOnly add or remove optional fields with defaults. Deploy order does not matter — and this is what you want for events with many consumers
NONENothingAnything, including the incident above
  THE RULES THAT KEEP EVENTS EVOLVABLE

  ALWAYS SAFE
    - add an OPTIONAL field WITH A DEFAULT
    - add a new event TYPE to a topic (consumers filter)
    - relax a constraint

  NEVER SAFE
    - add a required field           (the incident above)
    - remove or rename a field       (rename = remove + add)
    - change a type or its meaning
    - reuse a field name for a new purpose  -- the worst of all,
      because it deserialises successfully and is WRONG

  ENFORCE IT MECHANICALLY: a schema registry with compatibility
  set to FULL rejects an incompatible schema at REGISTRATION,
  which means the build fails instead of the consumers. Without a
  registry, the same effect needs a schema file in the repo and
  a compatibility check in CI -- see the OpenAPI diff gate in
  REST API Design & Versioning; it is the identical idea.

  EVENT DESIGN -- three choices that decide your coupling

  1. FACT, NOT COMMAND
       OrderPlaced          a thing that happened. Past tense.
                            The producer does not know or care
                            who reacts.
       SendConfirmationEmail  a command dressed as an event. The
                            producer now knows about the email
                            service, and you have built RPC with
                            extra latency.

     Events describe the past; commands describe intent. Putting
     commands on an event topic recreates the coupling that
     events were supposed to remove.

  2. HOW MUCH STATE TO CARRY

     THIN EVENT      { "orderId": 8891 }
       + small, no stale data, no schema surface
       - every consumer calls back for details:
         5 consumers x 3,000 events/min = 15,000 extra requests
         per minute at the producer, which is a load amplifier
         AND a coupling: the producer must stay available for
         its own events to be processable

     FAT EVENT       { "orderId": 8891, "customerId": 412,
                       "total": 19.99, "items": [...] }
       + consumers are self-sufficient; replay works even if the
         producer is down
       - a bigger contract to keep compatible
       - the data is a SNAPSHOT AT PUBLICATION TIME, and someone
         will treat it as current

     The usual answer: carry what consumers need to ACT, plus
     ids for anything they might need to look up. Reassess when
     a consumer is calling back on every message.

  3. IDENTITY AND TIME -- put these in every event, always
       eventId       a UUID: the dedupe key for consumers
       occurredAt    when the fact happened (not when published)
       version       schema version, for the humans
       traceId       so the log search spans producer and
                     consumer (see Actuator & Observability)
       aggregateId   usually also the partition key

Part 6 — Operating It: Lag, Retention, and When Not To

  CONSUMER LAG IS THE METRIC. But it is usually alerted wrong.

    lag = latest offset in the partition - committed offset

  THE THREE MISTAKES:

  1. ALERTING ON THE SUM ACROSS PARTITIONS
     One partition stuck at 612,000 while five are at zero
     averages out to "slightly elevated". ALERT ON MAX PER
     PARTITION.

  2. ALERTING ON AN ABSOLUTE NUMBER
     "lag > 10,000" fires during every normal traffic burst and
     stays silent during a slow leak. What you care about is
     TIME:
         estimated delay = lag / (records processed per second)
     Alert on "estimated delay > 5 minutes for 10 minutes", which
     is a statement about user impact rather than about a queue.

  3. NOT ALERTING ON ZERO THROUGHPUT
     A consumer that is stuck has CONSTANT lag, not growing lag,
     if the topic is also quiet. Alert on "consumer group has
     committed no offsets in 10 minutes while records exist".

  ALSO WATCH:
    - rebalance rate (a spiral shows here first)
    - DLT message count, alerting at > 0
    - per-partition skew: one hot key means one hot partition,
      and no amount of scaling fixes it

MEASURED: retention deleted the backlog

  Consumer group down for a deploy problem, 8 hours.
  Topic retention: 6 hours (a default nobody revisited).

    T+6h    the broker begins deleting segments the consumer
            has not read
    T+8h    consumer restarts, requests its committed offset
            OffsetOutOfRangeException
            auto.offset.reset: latest    -> JUMPS TO THE END

    2.9M events between the committed offset and the end were
    never processed and no longer exist anywhere.

  Nothing failed loudly. The consumer started, reported healthy,
  lag was zero, and the data was gone.

  WHAT TO SET, AND WHY:
    retention.ms         longer than your worst realistic
                         outage. 7 days is a common floor;
                         6 hours is a trap.
    auto.offset.reset    earliest for most consumers -- when in
                         doubt, reprocess (you are idempotent)
                         rather than skip.
    an ALERT on          OffsetOutOfRange / offset reset events.
                         This is silent data loss and it deserves
                         a page, not a log line.
SituationUseWhy
Work queue inside one service, < 100 jobs/sA database table + SELECT ... FOR UPDATE SKIP LOCKEDTransactional with your data, no broker to run, trivially inspectable in SQL. The most under-used option on this list
Decoupling services, replay matters, high volumeKafkaThe log model is exactly this
Task distribution, per-message retry and delayRabbitMQ / SQSPer-message ack, DLX and TTL are native, and one slow task blocks nothing
Request/response between servicesHTTPMessaging for request/response gives you correlation ids, a reply topic and a timeout you have to build — this is RPC with extra parts
Fan-out to many independent consumersKafka or SNSConsumer groups read the same log independently
Scheduled/deferred workA scheduler + a tableKafka has no native delay; retry topics are a workaround, not a scheduler
🔑 The honest default for a single team's asynchronous work is a table in the database you already have. SELECT ... FOR UPDATE SKIP LOCKED gives competing consumers, the enqueue is in the same transaction as the state change that caused it — so the dual write simply does not exist — and every debugging question is answerable with a SQL query rather than a CLI against a cluster. Kafka earns its operational cost when you need replay, per-entity ordering at volume, or genuinely independent consumers; reach for it then, not because asynchronous work has appeared.

Interview Questions

Beginner: How is Kafka different from a traditional message queue?

Kafka is an append-only log, not a queue. A message published to a queue is delivered, acknowledged and then deleted — the broker tracks per-message state, and once consumed the message is gone. Kafka appends to a partition and keeps the message for the retention period whether anyone read it or not; each consumer group tracks its own position, an offset, and reading changes nothing.

Two consequences follow. Replay is free: a new service can join and read six months of history from offset zero, which a queue simply cannot do. And a slow consumer is not a growing queue but a growing offset lag — which matters, because if it lags past the retention window the data is deleted whether it was processed or not.

The structure is a topic split into partitions. Each partition is assigned to exactly one consumer in a group, which is why ordering is guaranteed per partition and why parallelism is capped by the partition count.

Beginner: What does the message key do?

The key chooses the partition — hash(key) % partitionCount — so all messages with the same key go to the same partition and are therefore processed in publication order relative to each other.

With a null key, Kafka spreads messages across partitions, and then two events for the same entity can land on different partitions with different consumers at different positions in the log. I have seen exactly that ship 214 cancelled orders: the cancellation went to a partition whose consumer was current, the placement to one lagging by 900 milliseconds, so the cancellation was processed for an order that did not yet exist and then the placement created and shipped it.

So the practical rule is that the key is your ordering scope. Pick the entity whose events must not overtake each other — usually the aggregate id — and key on that.

Mid: Your consumer is rebalancing constantly and lag is growing. Diagnose it.

The usual cause is that processing a batch takes longer than max.poll.interval.ms, which defaults to five minutes. That is the maximum time allowed between polls, and it is separate from the heartbeat — the heartbeat thread keeps beating happily while your listener is busy, so the consumer looks alive right up until the broker revokes its partitions.

The arithmetic is max.poll.records times your per-record time. The default 500 records at 800 milliseconds each is 400 seconds, well past the limit. The consumer is evicted mid-batch, the group rebalances — which stops every consumer in the group, not just the slow one — and processing restarts from the last committed offset, so the work already done is repeated. That is more work, which makes the next cycle slower. In one case that produced 47 rebalances in four hours, 181,000 reprocessed records, and 4.1 million lag with the consumers at 11% CPU.

The tell is exactly that: high lag with idle CPU, plus a high rebalance rate. It is not a throughput problem.

I would fix it by lowering max.poll.records so a poll cycle fits comfortably inside the interval — 50 records at 800 ms is 40 seconds against a 300-second budget — and by putting a timeout and circuit breaker on whatever downstream call went from 60 ms to 800 ms, because a consumer inherits every latency problem of what it calls. Raising max.poll.interval.ms is available but it delays detection of a genuinely dead consumer, so I would treat it as the second lever. Switching to the cooperative sticky assignor also stops a rebalance from halting the whole group.

Mid: A single bad message stopped one partition for hours. Why can that happen, and how do you prevent it?

Because a log has no way to skip a message. Offsets are sequential, so a consumer cannot get to offset N+1 without committing past offset N. If processing N fails and nothing handles the failure, the container re-polls the same offset forever — in one incident about forty times a second for nine hours, producing 1.3 million identical log lines and 612,000 lag on that one partition.

What makes it dangerous is that it hides. The other five partitions were completely healthy, so total lag looked only slightly elevated and no aggregate dashboard showed a problem. Alerting has to be on the maximum per-partition lag, never the sum or average.

The specific case here was a deserialisation failure, which needs its own fix because it happens before the listener runs, where no listener error handler can see it. Wrapping the deserialiser in ErrorHandlingDeserializer turns it into a null payload with the exception in the headers, so the normal error handler can route it to a dead letter topic.

Then the error handler needs to be configured to give up: a DefaultErrorHandler with a bounded backoff and a DeadLetterPublishingRecoverer, plus addNotRetryableExceptions for things like validation and JSON errors that will fail identically forever. And the DLT needs an alert at greater than zero messages — a dead letter topic nobody watches is just data loss with extra steps.

Senior: Design an order-events pipeline that is correct under duplicates, failures and replays.

I would start from the guarantee I can actually get: at-least-once delivery with idempotent consumers. Exactly-once in Kafka is real but it is a Kafka-to-Kafka property — the moment a consumer writes to Postgres or calls a payment API, that side effect is outside the transaction, so designing around exactly-once gives false confidence.

Producing. Events go through an outbox: the state change and the outbox row commit in one database transaction, and a relay publishes from the table. Publishing directly after a commit is a dual write, and in one system that lost 0.015% of events, which was 311 orders nobody downstream ever heard about. Every event is keyed by order id so all events for an order are ordered, and carries an eventId, occurredAt, schema version and trace id.

The event shape. Facts, past tense — OrderPlaced, not SendConfirmationEmail, because a command on an event topic rebuilds the coupling events were meant to remove. It carries enough state for consumers to act without calling back; five consumers each fetching details on every message is a load amplifier and a coupling that makes replay impossible when the producer is down.

Consuming. Auto-commit off, ack-mode: RECORD. Each consumer dedupes on eventId with a unique constraint, in the same transaction as its effect, so there is no window where one happened without the other — or better, writes are naturally idempotent, like UPDATE ... WHERE status = 'PENDING' rather than a relative decrement. max.poll.records is sized so a batch finishes well inside max.poll.interval.ms, and every remote call in the listener has a timeout and a breaker.

Failures. ErrorHandlingDeserializer so a poison pill cannot block a partition, a bounded blocking retry for transient errors — blocking, because ordering per order id matters here and retry topics would let a cancellation overtake its placement — then the DLT, with an alert at greater than zero and a documented replay path.

Schema. A registry set to FULL compatibility, so incompatible changes fail at registration rather than in consumers. That is not optional for events: a required field added to OrderPlaced breaks not just live traffic but every event already sitting in the retention window, so rolling the producer back does not fix it.

Operations. Retention comfortably longer than a realistic outage — a six-hour retention and an eight-hour outage silently deleted 2.9 million unprocessed events and the consumer came back reporting zero lag. Alerts on max per-partition lag expressed as estimated delay in minutes, on rebalance rate, on DLT depth, and on offset resets.

The property I would design for above all is replayability: if consumers are idempotent and events are self-contained facts, then recovery from almost any failure is "reset the group's offsets and let it run again". That single capability is worth more than any individual guarantee.

Senior: When would you argue against introducing Kafka?

Whenever the requirement is "we need to do this asynchronously" rather than "we need replay or per-entity ordering at volume". Those two properties are what a log gives you that nothing else does, and they are what justifies the operational cost — a cluster, schema management, consumer lag monitoring, partition sizing, and a class of failure modes the team has to learn.

For a single service's background work, a table in the database you already have is usually better. SELECT ... FOR UPDATE SKIP LOCKED gives competing consumers; the enqueue happens in the same transaction as the state change that caused it, so the dual-write problem does not exist at all; and every operational question — what is queued, what failed, what is stuck — is a SQL query rather than a CLI against a cluster. It scales further than people expect, comfortably into the low hundreds of jobs per second.

For task distribution where messages are independent and each needs its own retry, delay or priority, a queue is a better fit than a log. Kafka's per-partition ordering becomes a liability there: one slow or failing task blocks everything behind it on that partition, which is exactly what competing consumers on a queue avoid.

And for request/response, messaging is the wrong tool outright. Building correlation ids, a reply topic and a timeout is reimplementing HTTP with more moving parts and worse latency.

The version of this I would put to a team is a question rather than a rule: who is the second consumer, and do we need to replay? If there is no second consumer and no replay requirement, the event-driven architecture is buying coupling reduction that a well-placed table would buy more cheaply. If the answer is "not yet, but soon", I would still start with the table — moving from a table to Kafka later is a contained piece of work, whereas operating a cluster you did not need is a permanent tax.

🏋️ Exercises

1 (easy): Cancelled orders are occasionally shipped. Find the bug. 
  // producer
  kafkaTemplate.send("orders", new OrderPlaced(order));
  kafkaTemplate.send("orders", new OrderCancelled(order));

  // consumer
  @KafkaListener(topics = "orders", groupId = "fulfilment",
                 concurrency = "6")
  public void handle(OrderEvent e) { ... }
Solution

No message key. With a null key, Kafka distributes records across partitions, so OrderPlaced and OrderCancelled for the same order can land on different partitions — consumed by different threads, at different positions in their logs.

If the cancellation's partition is current and the placement's is 900 ms behind, the consumer processes the cancellation for an order it has never seen (logging a warning nobody reads), then processes the placement and ships the item. In the measured case that was 214 cancelled orders shipped over three weeks.

  String key = order.getId().toString();
  kafkaTemplate.send("orders", key, new OrderPlaced(order));
  kafkaTemplate.send("orders", key, new OrderCancelled(order));

Why this is sufficient: the same key hashes to the same partition, a partition is assigned to exactly one consumer in the group, and a partition is strictly ordered. So the two events are now processed in publication order by construction, not by luck.

What it does not fix, and is worth checking: if the consumer uses non-blocking retry topics, a failed OrderPlaced is republished to a retry topic and lands seconds later — after the cancellation. Keying is necessary but not sufficient; where ordering matters, the retry strategy has to be blocking too.

Also note concurrency = "6" is only meaningful if the topic has at least six partitions. With fewer, the extra consumers sit idle.

2 (easy): Finance found 1,412 orders missing from billing after a pod eviction. The consumer never logged an error. Explain. 
  spring.kafka.consumer:
    enable-auto-commit: true
    auto-commit-interval-ms: 5000
    max-poll-records: 500
Solution

Auto-commit commits by the clock, not by your progress. On each poll(), if the interval has elapsed, the consumer commits the offsets of everything the previous poll returned — whether your listener finished with those records or not.

  10:14:02.0  poll() -> 500 records
  10:14:02.1  processing begins
  10:14:07.0  poll() -> commits all 500   (88 actually processed)
  10:14:07.4  pod evicted mid-batch
  10:14:31    new consumer resumes AFTER the committed offset
              -> 412 records never processed, and unreachable

There is no error because nothing failed. The offsets were committed successfully; the work simply never happened. This is at-most-once delivery, which almost nobody wants and many people have by default.

  spring.kafka:
    consumer:
      enable-auto-commit: false
      max-poll-records: 100
    listener:
      ack-mode: RECORD

With RECORD, Spring commits after your listener returns normally, one record at a time. An exception means no commit, so the record is redelivered — at-least-once, which is the behaviour everyone assumed they already had.

The necessary companion change is a dedupe in the consumer, because at-least-once means duplicates on every rebalance and crash. Inserting the eventId into a table with a unique constraint, in the same transaction as the billing write, makes reprocessing harmless.

How to detect this class of bug going forward: compare the count of published events with the count of processed events per hour. A silent gap is invisible in error rates and lag alike — the only signal is the reconciliation, and here it took three weeks.

4 (medium): You must add a channel field to OrderPlaced. Five consumer groups read the topic; retention is 7 days. Plan it.
Solution

The constraint that makes this different from an API change: events already published stay readable for seven days, and consumers replay them. So a schema change must keep every event already in the log readable by every consumer that exists. A producer rollback does not undo events that were already written in the new shape — which is what turned one team's incident into a six-hour consumer outage they had to fix forward at 23:00.

Add channel as optional with a defaultYes. Old consumers ignore it; new consumers read the default for old events. Safe in both directions

          fails instead of the consumers

What I would verify before shipping: that the registry compatibility is genuinely FULL and not NONE. Teams frequently have a registry with compatibility disabled, which provides the appearance of safety and none of the mechanism. A deliberate test — try to register an incompatible schema in CI and assert that it is rejected — is worth the twenty minutes.

The detail that catches people: "optional" must mean optional in the schema, with a default. A field that is nullable in Java but required in the Avro or JSON schema still fails deserialisation on old data — the language type and the wire contract are different things.

5 (hard): Design lag alerting for a topic with 24 partitions and five consumer groups, and say what each alert means to whoever gets paged.
Solution

The framing: lag in records is not a symptom anyone experiences. Convert it to time — "how far behind reality is this consumer?" — because that is the thing a human can act on and reason about.

  estimated delay = max_per_partition_lag / records_per_second

  A lag of 50,000 at 5,000 rec/s is 10 seconds: fine.
  A lag of 3,000 at 2 rec/s is 25 minutes: not fine.
  The absolute number tells you neither.
AlertConditionWhat it means
Consumer falling behind (page)Estimated delay > 5 min, sustained 10 min, per groupUsers are seeing stale results. Check downstream latency first — a consumer inherits it
Partition stalled (page)One partition's lag > 20× the median partition's, for 5 minAlmost certainly a poison pill or a hot key. Look at that partition's offset, not the topic

What I would deliberately not alert on: total or average lag across partitions, which is the alert most teams have. One partition stuck at 612,000 with five at zero averages to something unremarkable, so the alert that exists is precisely the one that misses the failure that happens.

The one that is hardest to get right is "not progressing". Lag stops growing when the topic goes quiet, so a stuck consumer at 3am looks identical to a healthy idle one. Comparing committed offsets over time against the presence of unread records is the only reliable distinction, and it is worth the extra query.

What every one of these needs is a runbook line, because "consumer lag high" tells the person paged nothing about what to do. For each alert: the first metric to check, the command to inspect the partition, and whether skipping a record is an acceptable mitigation for that consumer — which is a decision that must be made in advance, calmly, not at 3am against a growing backlog.

6 (hard): A team wants to move all inter-service communication to Kafka "for decoupling". Evaluate the proposal.
Solution

The proposal conflates two things: asynchronous communication and event-driven design. Moving a synchronous call onto Kafka without changing the interaction shape does not decouple anything — it adds latency, a broker, and a correlation problem.

InteractionKafka appropriate?Why
"Tell everyone this happened" — order placed, user registeredYesThe producer does not know or care who reacts. This is what events are for, and consumers can be added later with replay
"I need this answer to continue" — price this cart, is this card validNoRequest/response over messaging means building correlation ids, a reply topic and a timeout: HTTP with extra parts and worse latency
"Do this work for me" — send an email, generate a PDFSometimesIt is a command, not an event. A queue fits better: per-message retry, and one slow task blocks nothing
"Give me the current state of X"NoA query. Events are facts about the past; using them for state means every consumer rebuilds a replica

What genuinely improves with events is the fan-out case: today the order service calls billing, then email, then analytics, then loyalty, and each new consumer means a code change and a new failure mode in the order path. Publishing OrderPlaced once removes four synchronous dependencies from the critical path and lets consumers be added without touching the producer. That is real decoupling and worth doing.

What gets worse, and should be said explicitly. Debugging: a request that spans four services and a broker needs distributed tracing before anything else. Consistency: every consumer is now eventually consistent, so "I placed an order but the dashboard does not show it" becomes a support category rather than a bug. Correctness burden: every consumer needs idempotency, because duplicates are routine. And the schema becomes a published contract with a longer tail than an API — events in the retention window must stay readable by every consumer version.

What I would propose instead is to move the fan-out first and leave request/response on HTTP. Concretely: pick the one interaction with the most consumers, publish it as an event with an outbox, migrate consumers one at a time, and run both paths until the event path is proven. That delivers most of the decoupling benefit for one topic's worth of operational cost, and it teaches the team the failure modes on a system where the fallback still exists.

The organisational read: "move everything to Kafka" is often a proxy for "we are tired of coordinating deploys". That is a real problem, and it is worth checking whether the actual constraint is a synchronous dependency at all — frequently it is a shared database or a shared release process, and neither is fixed by a broker.

🎯 Key Takeaways

  • Kafka is a log, not a queue. Reading does not delete; consumers track their own offsets; replay is free and retention is a deadline.
  • Ordering is per partition only. A null key put a cancellation and its order on different partitions and shipped 214 cancelled items.
  • The key is the ordering scope — usually the aggregate id. Ordering across keys is not something you are given.
  • Parallelism is capped by partition count, partitions can be added but never removed, and adding them re-keys existing data.
  • "Exactly once" is Kafka-to-Kafka. Your database write and your email are outside the transaction; design for at-least-once plus idempotency.
  • enable.auto.commit commits by the clock, not by your progress — 1,412 orders were acknowledged and never processed, with no error.
  • Use ack-mode: RECORD so a failing listener leaves the offset uncommitted and the record is redelivered.
  • Duplicates are normal operation, not an edge case. Dedupe in the same transaction as the effect, or make the write naturally idempotent.
  • A consumer that writes to the DB and publishes is a dual write — the outbox applies here exactly as it does to producers.
  • max.poll.interval.ms is a deadline on your processing, separate from the heartbeat: 500 records × 800 ms exceeded it and produced 47 rebalances and 4.1M lag at 11% CPU.
  • High lag with idle CPU and frequent rebalances is the death spiral — lower max.poll.records before touching anything else.
  • A log cannot skip an offset. One malformed record blocked a partition for 9 hours while five others looked perfectly healthy.
  • Deserialisation errors happen before your listener — only ErrorHandlingDeserializer can catch them.
  • Classify failures before retrying. A validation error retried three times just triples the partition stall.
  • Retry topics trade ordering for throughput — the failed record returns after records that came later.
  • A DLT nobody reads is silent data loss. Alert at greater than zero, keep the failure headers, document the replay.
  • An event schema is a contract with a retention-window tail. A required field broke live consumers and seven days of already-published events.
  • Events are facts, past tense. A command on an event topic rebuilds the coupling events were meant to remove.
  • Alert on max per-partition lag as estimated delay in time, plus stalled consumers, rebalance rate, DLT depth and offset resets.
  • Retention shorter than a realistic outage deletes unprocessed data silently — 2.9M events, and the consumer came back reporting zero lag.
  • For one team's async work, a table with FOR UPDATE SKIP LOCKED beats a cluster — transactional, inspectable, and no dual write at all.
