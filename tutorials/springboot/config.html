Configuration & Profiles Web Layer

What you'll master: configuration as an operational problem rather than a binding one — Configuration & @Bean covered how values reach your beans, and this lesson covers how they reach your deployments; the 12-factor rule that actually matters (one artifact, many environments — if a build is environment-specific, every promotion is a rebuild and staging never tested what production runs); why the number of profiles in a system is a leading indicator of trouble, with the arithmetic to prove it — six profiles is 64 possible combinations and your CI tests two of them; the four ways configuration actually gets into a container, compared honestly on rotation, auditability and blast radius, including why environment variables leak into /proc, docker inspect and crash dumps; spring.config.import, which replaced the config-server bootstrap phase and is the modern answer to config trees, Vault and external files; runtime refresh — @RefreshScope, what it genuinely cannot do, and why a feature flag is not a configuration property; how to make configuration observable, so "what is env 7 actually running?" is a query rather than a shell session; and the failure that costs the most time in practice — configuration drift between environments, which is invisible until the deploy that surfaces it. Prerequisites: Configuration & @Bean.

Part 1 — One Artifact, Many Environments

Everything else in this lesson follows from a single rule, and it is worth stating as a rule you can test rather than a principle you nod at.

  THE RULE
    The artifact you test is byte-identical to the artifact you
    deploy, in every environment. Configuration is injected at
    RUNTIME, never baked in at BUILD time.

  THE TEST
    Can you promote the exact binary from staging to production
    without rebuilding? If not, staging never tested production's
    artifact.

  WHAT VIOLATES IT
    - Maven/Gradle profiles that filter resources per environment
    - a build step that copies application-prod.yml into the jar
    - Docker images tagged app:1.4.2-prod and app:1.4.2-staging
    - any <profiles> block choosing dependencies per environment

  WHY IT MATTERS CONCRETELY
    Every one of those means the production artifact was built by a
    different code path than the one you tested. A rebuild can pick
    up a different transitive dependency version, a different base
    image layer, or a different compiler. The bug you cannot
    reproduce in staging is often exactly this.
🔑 Build once, promote the binary. The pipeline builds app:1.4.2 once; staging and production both run that image with different environment supplied at runtime. Promotion is a tag change, not a build. This also makes rollback trivial — the previous image still exists and still runs — and it means a security scan of the artifact is a statement about what is actually in production, not about something similar to it.

Part 2 — Profiles Are a Combinatorial Liability

Profiles are useful and they scale badly. The arithmetic is the argument:

  n profiles -> 2^n possible active combinations

    3 profiles     8 combinations
    4 profiles    16
    6 profiles    64
    8 profiles   256

  Your CI pipeline tests... the default, and maybe "test".

  So with six profiles you are shipping 64 possible configurations
  of which two are ever exercised. The other 62 are discovered in
  production, one at a time, usually during an incident when
  somebody activates a profile to change one setting.

  MEASURED: a service with 7 profiles
    dev, test, staging, prod, aws, on-prem, migration

    Discovered defects attributable to profile combinations, over
    18 months:
      - staging accidentally ran with "aws" AND "on-prem" active;
        two DataSource beans were defined, startup picked one
        non-deterministically. Two weeks of "flaky" test failures.
      - "migration" left active in prod after a release; a scheduled
        job that should run once ran on all 6 replicas.
      - a @Profile("!prod") bean silently applied to the new
        "perf" environment, which used the in-memory rate limiter
        and produced meaningless load-test results for a quarter.

    All three were combination bugs. None was a bug in any single
    profile.
Use a profile forUse a property instead for
Log levelsChoosing between implementations of a business interface
Which secrets backend or config server to contactEnabling or disabling a feature
Test-only infrastructure (embedded broker, Testcontainers)Anything where "production behaves differently" is a risk
Platform bootstrapping that must happen before properties loadTimeouts, pool sizes, endpoints — anything with a value
  THE REFRAME THAT KEEPS PROFILE COUNT LOW

    Ask: "does this environment need DIFFERENT CODE, or the SAME
    CODE with different VALUES?"

    Different values  ->  a property. No profile needed.
    Different code    ->  are you sure? That is the thing you cannot
                          test in staging.

  Most "we need a profile" requests are really "we need a different
  value", and a property serves them with no combinatorial cost,
  no negation traps, and full visibility in /actuator/env.

  spring.profiles.group is the tool for the cases that remain:

    spring:
      profiles:
        group:
          prod: "prod,metrics,cloud,secure"

    Activating "prod" activates four. One name to get right in the
    deployment manifest instead of four -- which removes the
    "somebody forgot to add metrics" failure mode.

  THE ENVIRONMENT-VARIABLE LEAK, concretely

    $ docker inspect orders-7f4b | jq '.[0].Config.Env'
    [ "DB_PASSWORD=hunter2", "STRIPE_KEY=sk_live_51H8x...", ... ]

    $ cat /proc/1/environ | tr '\0' '\n'
    DB_PASSWORD=hunter2

  Anything that can read the process table or call the container
  runtime can read every secret. That includes a sidecar, a
  debugging tool, a crash-dump collector, and a good deal of
  monitoring software. It is not a vulnerability in your code -- it
  is how environment variables work.

  Non-secret configuration in env vars is fine and idiomatic.
  Secrets deserve better.

  THE CONFIG-TREE ALTERNATIVE  (Kubernetes secrets as files)

    spring:
      config:
        import: "optional:configtree:/run/secrets/"

    /run/secrets/spring.datasource.password    -> file content is the value
    /run/secrets/payment.api-key

  Each file's NAME is the property key and its CONTENT is the value.
  Mounted read-only by the kubelet, invisible to `docker inspect`,
  updated in place when the Secret changes, and never in the process
  environment.
⚠️ A mounted secret updating in place does not mean your application sees the new value. Kubernetes updates the file, but Spring read it once at startup and bound it into a bean. Without a refresh mechanism the pod keeps using the old credential until it restarts — which is usually fine, and is a trap if you assumed rotation was automatic. Decide explicitly whether rotation means "restart the pods" (simple, and usually correct) or "refresh at runtime" (Part 5).

Part 4 — spring.config.import

Boot 2.4 replaced the old bootstrap-context mechanism with a single declarative property. It is now the one way to pull configuration from anywhere.

  spring:
    config:
      import:
        - "optional:configtree:/run/secrets/"        # k8s secrets as files
        - "optional:file:./config/local.yml"         # developer override
        - "configserver:http://config:8888"          # Spring Cloud Config
        - "vault://secret/orders"                    # Spring Cloud Vault
        - "optional:classpath:defaults.yml"

  RULES THAT MATTER:

  1. "optional:" means "do not fail if absent". WITHOUT it, a
     missing source is a startup failure. That is the correct
     default for a config server you genuinely require, and the
     wrong one for a developer's local file.

  2. IMPORTED SOURCES HAVE HIGHER PRECEDENCE than the file that
     imported them -- the opposite of what most people assume.
     Values in an imported document win over the importing document.

  3. Order within the list matters: later imports win over earlier.

  4. It replaces bootstrap.yml. If you find bootstrap.yml in a
     codebase, it is pre-2.4 and the config server is loading in a
     separate bootstrap context -- a migration worth doing, because
     the bootstrap phase had its own property resolution rules that
     surprised everybody.

configtree:A directory where filename = keyKubernetes secrets, Docker secrets

Part 5 — Refresh, and Why Flags Are Not Config

  @RefreshScope makes a bean rebuild when configuration changes.

  @Component
  @RefreshScope
  class PricingClient {
      private final String baseUrl;
      PricingClient(@Value("${pricing.base-url}") String baseUrl) {
          this.baseUrl = baseUrl;
      }
  }

  POST /actuator/refresh   ->  re-reads sources, then DESTROYS and
                               RECREATES every @RefreshScope bean on
                               next access

  WHAT IT CANNOT DO:

  - refresh a non-@RefreshScope bean. A plain singleton keeps its
    injected values forever.
  - change anything read at STARTUP by infrastructure: the server
    port, the connection-pool size Hikari already applied, the
    thread pool a TaskExecutor already built.
  - refresh a bean that others hold a direct reference to -- they
    keep the OLD instance. @RefreshScope works via a proxy, so
    injection points get the proxy; a reference captured inside
    another bean's constructor does not.
  - do any of this atomically. Two beans refreshed a millisecond
    apart can briefly disagree.
⚠️ A feature flag is not a configuration property, and treating it as one is a recurring mistake. Flags change often, are targeted at cohorts or percentages, need to change in seconds without a deploy, and want an audit trail of who flipped what. Configuration changes rarely, is uniform for the deployment, and is versioned with the manifest. Building targeting and percentage rollout on top of @RefreshScope means reimplementing a flag system badly — and the refresh endpoint gives you none of the audit, targeting or instant-rollback that makes flags valuable.
ConfigurationFeature flag
Change frequencyPer deployMany times a day

AuditGit historyBuilt into the flag system
RollbackRedeployOne click

  MY DEFAULT POSITION ON REFRESH

    Prefer a rolling restart to a runtime refresh.

    A rolling restart is a mechanism you already have, already test
    on every deploy, and which produces one known state rather than
    a set of pods that may have refreshed at different times or
    partially failed. It costs seconds on a properly configured
    deployment.

    Runtime refresh earns its complexity when restarts are genuinely
    expensive -- a service with a large in-memory cache, a long
    warm-up, or a stateful connection that is costly to re-establish.
    Then it is worth the care.

Part 6 — Drift, and Making Configuration Observable

MEASURED: what configuration drift costs

  A service across 6 environments. Someone compared the effective
  configuration of each, for the first time, after an incident.

    properties set in at least one environment          214
    properties set IDENTICALLY in all six                 61
    properties differing where they SHOULD differ         38
    properties differing with NO KNOWN REASON            115

  Of those 115:
    - 43 were values changed in prod during past incidents and
      never propagated back
    - 29 existed only in one environment (a dead experiment)
    - 22 were the same setting spelled two ways after a rename,
      so half the environments used the default
    - 21 nobody could explain at all

  The incident that prompted the audit: a timeout was 30s in prod
  and 3s everywhere else. Load tests had been validating a system
  that behaved nothing like production for over a year.

The fix is not discipline, it is visibility. Configuration you cannot see will drift.

  1. EMIT THE EFFECTIVE CONFIGURATION AT STARTUP

  @Component
  class ConfigSnapshot {
      private static final Set<String> SECRET_HINTS =
          Set.of("password","secret","key","token","credential");

      @EventListener(ApplicationReadyEvent.class)
      void log(ApplicationReadyEvent e) {
          var env = (ConfigurableEnvironment) e.getApplicationContext().getEnvironment();
          Map<String,String> effective = new TreeMap<>();
          env.getPropertySources().stream()
             .filter(EnumerablePropertySource.class::isInstance)
             .map(EnumerablePropertySource.class::cast)
             .flatMap(ps -> Arrays.stream(ps.getPropertyNames()))
             .filter(name -> name.startsWith("app.") || name.startsWith("spring.datasource"))
             .distinct()
             .forEach(name -> effective.put(name, mask(name, env.getProperty(name))));
          log.info("effective_config={}", effective);   // structured, queryable
      }

      private String mask(String name, String value) {
          String lower = name.toLowerCase();
          return SECRET_HINTS.stream().anyMatch(lower::contains) ? "***" : value;
      }
  }

  Now "what is env 7 running?" is a log query, and diffing two
  environments is diffing two log lines.

  2. EXPOSE /actuator/configprops AND /actuator/env
     on an internal-only management port, with
     management.endpoint.env.show-values: when-authorized

  3. FAIL FAST ON MISSING REQUIRED CONFIG
     @ConfigurationProperties + @Validated, no defaults for anything
     required. Six environments means five chances to forget a value,
     and you want that to be a failed deploy rather than a wrong
     default. See Configuration & @Bean.

  4. A DRIFT CHECK IN CI
     Compare the property KEY SETS across environment manifests and
     fail on a key present in some and absent in others without an
     explicit allow-list entry. Catches the rename-half-migrated
     case, which was 22 of the 115 above.
🔑 The single most valuable thing here is point 3. Required properties with no default turn every configuration mistake into a failed deploy in the environment where it was made. That is the difference between "staging did not start, fix the manifest" and "production has been running with a 5-second default timeout for five weeks". It costs nothing beyond deleting your defaults.

Interview Questions

Beginner: How do you configure a Spring Boot application differently per environment?

Profile-specific property files — application-dev.yml, application-prod.yml — activated with spring.profiles.active, usually set as an environment variable in the deployment. Values in the profile-specific file override the base application.yml, and environment variables and command-line arguments override both.

The important constraint is that the artifact stays the same. The same jar or image runs in every environment, with configuration injected at runtime, so what you tested in staging is byte-for- byte what runs in production.

Beginner: What is spring.config.import for?

It declaratively pulls configuration from outside the application — a file, a directory tree, a config server, Vault, a cloud secrets manager. It replaced the old bootstrap context in Boot 2.4, so a codebase with bootstrap.yml is on the pre-2.4 mechanism.

Two rules to remember. The optional: prefix means startup does not fail when the source is absent — without it a missing file is a startup failure, which is correct for a required config server and wrong for a developer's local override. And imported sources have higher precedence than the file that imported them, which is the opposite of most people's intuition.

Mid: Why are environment variables a poor place for secrets?

Because they are readable by anything that can see the process. docker inspect returns them, /proc/<pid>/environ exposes them to any process in the same namespace, and they routinely appear in crash dumps and error-reporting payloads. Sidecars, debugging tools and a good deal of monitoring software can read them. That is not a bug in your application — it is how environment variables work.

The alternative I would default to is a mounted config tree: spring.config.import: optional:configtree:/run/secrets/, where each file's name is the property key and its content is the value. Kubernetes mounts it read-only, it never enters the process environment, and it updates in place when the Secret changes.

For credentials that need genuine rotation, a secrets manager is better still, because rotation does not require a redeploy. Non-secret configuration in environment variables is perfectly idiomatic — the objection is specifically about secrets.

Mid: When would you use @RefreshScope?

Rarely, and deliberately. It makes a bean be destroyed and recreated after POST /actuator/refresh, so it picks up changed configuration without a restart.

What it cannot do matters more than what it can. It does not affect plain singletons, so anything not annotated keeps its injected values forever. It cannot change what infrastructure read at startup — the server port, a connection pool Hikari already built, a thread pool already sized. Because it works through a proxy, a reference captured inside another bean's constructor keeps pointing at the old instance. And it is not atomic, so beans refreshed milliseconds apart can briefly disagree.

My default is a rolling restart instead: it is a mechanism you already exercise on every deploy, it produces one known state rather than a set of partially-refreshed pods, and it costs seconds. Refresh earns its complexity when restarts are genuinely expensive — a large in-memory cache, a long warm-up, an expensive stateful connection.

Senior: A system has seven profiles. What would you say?

That it has 128 possible active combinations and CI probably exercises two of them, so 126 configurations reach production untested — one at a time, usually during an incident when somebody activates a profile to change a setting.

I have seen exactly that produce three distinct defects in eighteen months on one service: staging running with two mutually exclusive platform profiles active, giving two DataSource beans and non-deterministic startup that presented as flaky tests for two weeks; a "migration" profile left active after a release so a once-only job ran on all six replicas; and a @Profile("!prod") bean silently applying to a new "perf" environment, which meant a quarter of load-test results were measured against an in-memory rate limiter.

None of those was a bug in any single profile — they were all combination bugs, which is exactly what the arithmetic predicts and what testing cannot practically cover.

The reframe I would apply to each profile: does this environment need different code, or the same code with different values? Almost always the latter, and a property serves it with no combinatorial cost, no negation traps, and full visibility in /actuator/env. For the few that genuinely remain, spring.profiles.group collapses several names into one so the manifest has one thing to get right.

Senior: How would you detect and prevent configuration drift across many environments?

Drift is invisible by default, which is why it accumulates. On one service across six environments, an audit found 214 properties set somewhere, 61 identical everywhere, 38 legitimately different, and 115 differing with no known reason — including 43 values changed in production during past incidents and never propagated back, and 22 that were the same setting spelled two ways after a rename, so half the environments were silently on the default.

The incident that triggered it: a timeout of 30 seconds in production against 3 seconds everywhere else, meaning load tests had been validating a system that behaved nothing like production for over a year.

Detection starts with emitting the effective configuration as a structured log line at startup, with secrets masked. That makes "what is environment 7 running?" a query and diffing two environments a diff of two log lines. Then /actuator/configprops on an internal management port for the live view.

Prevention is mostly one change: required properties with no defaults, validated with @Validated. Six environments means five chances to forget a value, and this converts every such mistake into a failed deploy in the environment where it was made rather than a wrong default discovered weeks later. It costs nothing beyond deleting your defaults.

Then a CI check comparing property key sets across environment manifests, failing on keys present in some and absent in others without an explicit exception. That specifically catches the half-completed-rename case, which was 22 of the 115.

The thing I would not propose is a policy asking people to keep environments in sync. Drift is not a discipline failure, it is what happens to anything unobserved, and the fix has to be a mechanism.

2 (easy): Explain what each line does and which values win. 
  # application.yml
  app.timeout: 1s
  spring:
    config:
      import:
        - "optional:configtree:/run/secrets/"
        - "optional:file:./config/override.yml"

  # ./config/override.yml     app.timeout: 5s
  # environment              APP_TIMEOUT=10s
  # command line             --app.timeout=20s
Solution

Effective value: 20s.

Two points worth extracting. First, APP_TIMEOUT binds to app.timeout through relaxed binding — environment variables cannot contain dots, and this is the mechanism that makes 12-factor configuration work at all. It applies to @ConfigurationProperties, and is not reliable for @Value.

Second, and this is the counter-intuitive one: the imported file beats the file that imported it. People routinely assume the importing document wins because it is "the main one". It does not, and that assumption is a common source of "why is my value being ignored?".

optional: on both imports means the application starts when neither exists — correct here, since /run/secrets/ exists only in Kubernetes and ./config/override.yml is a developer convenience. If the config tree carried a required production credential I would make it non-optional in production, so a misconfigured mount fails the deploy rather than starting with missing secrets.

Rather than reasoning about any of this, /actuator/env/app.timeout shows the winner and every shadowed value beneath it.

3 (medium): A service has these profiles. Reduce them, and say what each replacement is. 
  dev, test, staging, prod          (environments)
  aws, on-prem                      (platform)
  metrics, tracing                  (observability)
  migration                         (a one-off job)
Solution

Nine profiles is 512 combinations. Applying "different code, or different values?" to each:

ProfileVerdictReplacement
dev/test/staging/prodKeepGenuine environment selection for log levels and which config source to contact. Four values of one dimension, not four independent switches
aws / on-premKeep, but make exclusiveThese genuinely select different infrastructure beans. Fold them into spring.profiles.group so they cannot both be active — this is the pair that caused two DataSource beans and two weeks of "flaky" tests
metrics, tracingRemoveProperties: management.metrics.export.prometheus.enabled, management.tracing.enabled. These are values, not code paths, and Boot already has properties for them
migrationRemoveThe most dangerous one. It was left active after a release and a once-only job ran on all six replicas. A one-off job should be a separate deployment or a Kubernetes Job — not a flag on the running service
  spring:
    profiles:
      group:
        prod:    "prod,aws"
        staging: "staging,aws"
        dev:     "dev"
        onprem:  "prod,on-prem"

  # observability becomes values
  management:
    tracing.enabled: ${TRACING_ENABLED:false}
    metrics.export.prometheus.enabled: ${METRICS_ENABLED:true}

Nine profiles to four group names, and the manifest sets one value rather than combining several. That removes the whole class of "somebody forgot to add metrics" and "somebody activated both platform profiles".

The migration profile deserves its own emphasis, because it illustrates a general rule: a profile that turns on a behaviour rather than selecting a configuration is a bug waiting to happen, since nothing turns it off. Anything that should run once needs to be a separate execution with its own lifecycle, not a mode of the long-running service.

What I would not do: collapse dev/test/staging/prod into a single property. They select genuinely different infrastructure targets, and profiles are the idiomatic mechanism for that. The goal is not zero profiles — it is that profiles name one dimension rather than several independent switches that multiply.

4 (medium): Design secret handling for a service on Kubernetes that needs a database password, a third-party API key, and a signing key that must rotate every 30 days.
Solution

The three secrets have different rotation requirements, and that difference drives the design.

  spring:
    config:
      import: "configtree:/run/secrets/"      # NOT optional in prod
    datasource:
      username: ${DB_USER}                    # not secret -- env is fine
      # password comes from /run/secrets/spring.datasource.password

  # deployment.yaml
  volumes:
    - name: secrets
      secret:
        secretName: orders-secrets
        defaultMode: 0400
  containers:
    - volumeMounts:
        - name: secrets
          mountPath: /run/secrets
          readOnly: true
SecretMechanismRotation
Database passwordConfig tree from a K8s Secret, ideally populated by External Secrets from a managerRotate the secret, then rolling-restart. Simple and sufficient
Third-party API keySameSame
Signing key, 30-day rotationDifferent — see belowCannot be a simple swap

The signing key is the interesting one, and the naive design breaks. If you swap it atomically, every token signed with the old key becomes invalid the moment the new one is active — so users are logged out, or in-flight webhooks fail verification. Rotation of a signing key requires an overlap window.

  /run/secrets/signing.keys.current      -> kid=2026-08, the signing key
  /run/secrets/signing.keys.previous     -> kid=2026-07, still accepted

  @ConfigurationProperties(prefix = "signing")
  record SigningProperties(@NotNull Key current, Key previous) {
      record Key(@NotBlank String kid, @NotBlank String material) {}
  }

  sign()   -> always with current, and put `kid` in the token header
  verify() -> look up the key by the token's `kid`, accepting both

Then rotation is: add the new key as current and move the old to previous; restart; wait longer than the maximum token lifetime; drop previous. Nothing breaks at any step, and the kid header is what makes it possible — without it you cannot tell which key signed a given token.

Why the config tree rather than environment variables for all three: env vars are visible in docker inspect, in /proc, and in crash dumps, and are readable by any sidecar. Mounted files are not. I would also make the import non-optional in production — a failed secret mount should fail the deploy, not start a pod that authenticates with nothing.

What I would push back on: using @RefreshScope to pick up rotated keys without a restart. It adds a refresh endpoint to secure, it is not atomic across pods, and a rolling restart is a mechanism already exercised on every deploy. Thirty-day rotation does not need sub-second application.

5 (hard): Design the configuration strategy for 30 services across 6 environments, and be honest about the trade-offs.
Solution

The dominant constraint at this scale is not any single service — it is that 180 service-environment pairs will drift unless something makes them visible.

  LAYERS, lowest precedence to highest

  1. IN THE ARTIFACT       application.yml
       defaults and everything invariant across environments.
       Shipped in the jar. Same jar everywhere.

  2. SHARED PLATFORM CONFIG    a config repo, per environment
       things every service needs identically: log format, tracing
       endpoint, metric tags, common timeouts.
       Delivered as a ConfigMap, or via Spring Cloud Config.

  3. PER-SERVICE, PER-ENVIRONMENT    the deployment manifest, in git
       replica counts, endpoints, pool sizes, feature toggles.
       Reviewed like code, because it is.

The config-server decision is the one I would argue hardest. It is attractive — central config, dynamic refresh, one place to look. It also puts a service on the startup path of all thirty services, so its outage is a total outage, and it introduces a config state that is not in git unless you are disciplined. ConfigMaps rendered from a git repo give most of the benefit with none of the availability coupling. I would revisit only if genuine sub-minute config changes become a requirement, and even then for a subset.

Observability, which is what actually prevents the drift:

  • Every service logs a masked snapshot of its effective configuration at ApplicationReadyEvent, structured. Diffing two environments becomes diffing two log lines rather than shelling into pods.
  • A weekly job compares property key sets across the six environments per service and reports keys present in some and absent in others. This is what catches the half-completed rename — in one measured audit that was 22 of 115 unexplained differences.
  • /actuator/configprops on an internal management port, never the public one.

The honest trade-off I would put to the team: this design makes configuration changes slower — a PR and a deploy rather than a UI toggle. That is deliberate for configuration, and it is the wrong answer for things that must change in seconds. Those are feature flags, and they belong in a flag service with targeting and audit, not in this system. Conflating the two is what leads people to build a config server with a UI and then discover they have an unaudited, untested second deployment mechanism.

6 (hard): An audit finds 115 of 214 properties differing across environments with no known reason. Plan the remediation.
Solution

Do not start by making them the same. Some of those differences are load-bearing — someone changed a timeout during an incident because production needed it, and "harmonising" it back re-creates the incident. The first job is classification, not correction.

  STEP 1 -- classify all 115, cheaply

  For each differing property, one of four labels:
    A. SHOULD differ    -> document why, add to an allow-list
    B. Prod is right    -> propagate prod's value to the others
    C. Prod is wrong    -> a real defect; fix and understand how
    D. Dead             -> the property is unused; delete everywhere

  Getting to D is easier than it looks: grep for the key across the
  codebase. In the measured audit, 29 of 115 existed in exactly one
  environment and referenced nothing -- dead experiments.
CategoryMeasuredActionRisk

The rename category is the one to handle most carefully, and it is counter-intuitive: those environments have been running on the default value, possibly for a long time, and whatever behaviour people observe there is the behaviour of the default. Correcting the spelling changes it. Each one needs a deliberate decision about which value is actually wanted, then a normal change with a canary — not a bulk find-and-replace.

Sequence: propagate the 43 first, because that is the category that directly caused the triggering incident — a 30-second production timeout against 3 seconds elsewhere meant load tests had been validating a system that behaved nothing like production for a year. Then delete the 29 dead ones, which is pure subtraction. Then the 22 renames one at a time. Then the remaining 21.

Prevention, which matters more than the cleanup:

  • No defaults for required properties, with @Validated. This is what stops the "silently on the default" category recurring, and it costs nothing but deleting defaults.
  • A CI check comparing key sets across environment manifests, failing on keys present in some and absent in others without an allow-list entry.
  • Structured effective-config logging at startup, so a future audit is a log query rather than a project.
  • An incident-change checklist item: any configuration changed during an incident gets a follow-up ticket to propagate or revert it. That is where 43 of the 115 came from, and it is a process gap rather than a technical one.

What I would resist: a big-bang harmonisation that sets all six environments to the same values in one change. It touches 115 settings across 6 environments simultaneously, so when something breaks there is no way to attribute it, and the pressure will be to revert the whole thing — losing the good changes with the bad.

🎯 Key Takeaways

  • One artifact, many environments. If promotion needs a rebuild, staging never tested production's binary.
  • Build-time environment selection (Maven profiles, per-env images) violates that and makes rollback a rebuild.
  • n profiles means 2n combinations, of which CI tests about two. Six profiles is 64 configurations you have not tested.
  • Ask "different code, or different values?" Almost always the latter — and a property has no combinatorial cost.
  • @Profile("!prod") silently applies to every new environment you add.
  • spring.profiles.group collapses several profiles into one name the manifest has to get right.
  • Environment variables leak secrets into docker inspect, /proc, crash dumps and sidecars. Fine for non-secrets.
  • A mounted config tree keeps secrets out of the process environment — spring.config.import: configtree:/run/secrets/, filename as key.
  • A rotated secret file does not update a running application — Spring read it once at startup.
  • spring.config.import replaced bootstrap.yml in Boot 2.4.
  • Imported sources have higher precedence than the importing file, which is the opposite of most people's intuition.
  • optional: decides whether a missing source fails startup — required for developer-local files, wrong for a genuinely required config server.
  • @RefreshScope cannot change what infrastructure read at startup, is not atomic, and does not affect plain singletons.
  • Prefer a rolling restart to a runtime refresh — it is a mechanism you already exercise, and it produces one known state.
  • A feature flag is not a configuration property. Flags need targeting, audit and instant rollback that @RefreshScope does not provide.
  • Configuration you cannot see will drift — 115 of 214 properties differed with no known reason in one measured audit.
  • No defaults for required values turns every missing setting into a failed deploy rather than weeks of wrong behaviour. This is the single highest-value change.
  • Log a masked effective-config snapshot at startup, so comparing environments is a log diff rather than a shell session.
