Spring Data JPA Data Layer

What you'll master: the mental model that makes JPA predictable — the persistence context is a write-behind cache with dirty checking, and once you see that, "why did my object save without me calling save?" and "why did nothing happen when I did?" become the same question with one answer; how Spring Data actually creates a repository (a JDK dynamic proxy over a shared implementation, not generated source), and why that explains both the magic and its limits; derived query methods and the point at which a method name becomes unreadable enough to be a bug (findByStatusAndCustomerIdAndCreatedAtBetweenOrderByTotalDesc); the four ways to write a query and when each is right, including why @Query with JPQL beats a derived method the moment there is a join; projections, which are the single most under-used performance feature in Spring Data — one endpoint went from 2.4 s to 40 ms by selecting five columns instead of hydrating entities; the save() trap that turns an insert into a select-then-insert and why saveAll() on 10,000 rows took 94 seconds before batching and 1.2 s after; getReferenceById versus findById, and the case where the lazy reference saves a query and the case where it throws in the wrong place; and why open-in-view defaults to true and should not. Prerequisites: IoC, DI & Beans and a working knowledge of SQL — see the SQL track.

Part 1 — The Persistence Context Is the Whole Model

Almost every JPA surprise is explained by one structure: a map of managed entities, held for the duration of a transaction, that Spring compares against their original state at flush time.

  ┌── Persistence Context (EntityManager, one per transaction) ──┐
  │                                                               │
  │   Map<EntityKey, Object>  managed entities                    │
  │   Map<EntityKey, Object[]> LOADED STATE (a snapshot)          │
  │                                                               │
  │   At FLUSH: for every managed entity, compare current field   │
  │   values against the snapshot. Any difference becomes an       │
  │   UPDATE. This is DIRTY CHECKING.                              │
  └───────────────────────────────────────────────────────────────┘

  ENTITY STATES

    TRANSIENT   new Order(...)          not in the context, no id
    MANAGED     findById(), save()      in the context, dirty-checked
    DETACHED    context closed          has an id, NOT tracked
    REMOVED     delete()                scheduled for DELETE

  WHEN DOES FLUSH HAPPEN?
    - before the transaction commits              (always)
    - before a JPQL/native query that might read
      pending changes                             (AUTO mode)
    - when you call flush() yourself

  NOT when you call save(). save() on a managed entity does nothing
  at all -- which is the source of half the confusion.

  THE TWO QUESTIONS THIS ANSWERS

  (1) "I never called save() and it still updated"

      @Transactional
      public void rename(Long id, String name) {
          Order o = repository.findById(id).orElseThrow();
          o.setName(name);            // MANAGED -> dirty checking
      }                               // flush at commit -> UPDATE

      Correct behaviour, and the reason JPA feels magical. It is
      also why an accidental setter call inside a transaction writes
      to the database.

  (2) "I called save() and nothing happened"

      public void rename(Long id, String name) {     // NO @Transactional
          Order o = repository.findById(id).orElseThrow();
          o.setName(name);
          repository.save(o);
      }

      findById opens and closes its own transaction, so `o` comes
      back DETACHED. save() on a detached entity with an id calls
      merge(), which SELECTs the row, copies your fields onto a
      fresh managed copy, and updates. It works -- at the cost of an
      extra select -- but any lazy association on `o` is unusable,
      and changes made to `o` after save() are lost.
🔑 The transaction boundary is the persistence-context boundary. Everything about detachment, lazy loading and dirty checking follows from where you put @Transactional. Put it on the service method that represents one unit of work — not on the repository (too narrow, so every call is its own context) and not on the controller (too wide, so it spans response serialisation and holds a connection while writing JSON).

Part 2 — What a Repository Actually Is

  public interface OrderRepository extends JpaRepository<Order, Long> { }

  You wrote an interface with no implementation. At startup:

  1. RepositoryConfigurationDelegate scans for Repository interfaces
  2. For each, it registers a JpaRepositoryFactoryBean
  3. The factory creates a JDK DYNAMIC PROXY implementing your
     interface
  4. Calls are routed by a chain of interceptors to:
       - SimpleJpaRepository        (the shared implementation of
                                     findById, save, delete, ...)
       - a derived-query executor   (parses the method NAME)
       - @Query execution           (uses your JPQL/SQL)
       - your own custom impl       (OrderRepositoryImpl)

  NOTHING IS CODE-GENERATED. There is no source file to read, which
  is why the behaviour must be understood rather than inspected.

  CONSEQUENCES:
   - a typo in a derived method name fails at STARTUP, not runtime:
       "No property 'stauts' found for type 'Order'"
   - method resolution order is: @Query beats derived name; a custom
     implementation beats both
   - you cannot debug into "the generated repository" -- step into
     SimpleJpaRepository instead
InterfaceAddsUse when
Repository<T,ID>Nothing — a markerYou want to expose only your own methods
CrudRepositorysave, findById, delete, countMinimal surface
PagingAndSortingRepositoryfindAll(Pageable), findAll(Sort)Paging without the rest
ListCrudRepositoryReturns List rather than IterableBoot 3+; usually what you want
JpaRepositoryAll of the above plus flush, saveAndFlush, getReferenceById, batch deletesThe default choice
⚠️ Extending JpaRepository exposes deleteAll() and findAll() on every repository, to every caller. On a table with 40 million rows, an autocompleted findAll() is an out-of-memory error and deleteAll() is an incident. For repositories over large or critical tables, extend Repository<T,ID> and declare only the methods you actually want. It costs three lines and removes a whole category of accident.

Part 3 — Four Ways to Write a Query

  1. DERIVED FROM THE METHOD NAME
     List<Order> findByStatusAndCustomerId(OrderStatus s, Long customerId);

     + validated at startup, refactor-safe, no SQL to maintain
     - unreadable past ~3 conditions, cannot express joins or
       projections well

  2. @Query WITH JPQL
     @Query("select o from Order o join fetch o.items where o.status = :s")
     List<Order> findWithItems(@Param("s") OrderStatus status);

     + full JPQL: joins, fetch joins, projections, aggregates
     + still database-portable, still validated at startup
     - a string, so renames are not automatically applied

  3. @Query(nativeQuery = true)
     @Query(value = "select * from orders where data @> :json",
            nativeQuery = true)

     + database-specific features: JSONB, window functions, CTEs, hints
     - not portable, not validated at startup, returns raw types

  4. CRITERIA / SPECIFICATIONS / QUERYDSL
     repository.findAll(hasStatus(PAID).and(createdAfter(cutoff)));

     + composable at runtime -- the right answer for dynamic filters
     - verbose, and the generated SQL is harder to predict

  WHERE DERIVED QUERIES STOP BEING A GOOD IDEA

    findByStatusAndCustomerIdAndCreatedAtBetweenOrderByTotalDesc

  This is a method name, and it is worse than the SQL it replaces:
    - nobody can read it without counting words
    - adding one condition changes the name, so every caller changes
    - it cannot express a join, so it will silently N+1 if the
      caller touches an association

  THE RULE I USE: three conditions, or a join, and it becomes
  @Query. The name then says what it is FOR, not how it filters:

    @Query("""
        select o from Order o
        where o.status = :status
          and o.customer.id = :customerId
          and o.createdAt between :from and :to
        order by o.total desc
        """)
    List<Order> findRecentHighValueOrders(...);
SituationUse
1–2 conditions, no joinDerived method name
3+ conditions, or any join@Query with JPQL
Returning a subset of columnsA projection (Part 4)
Filters chosen at runtime by the callerSpecification or QueryDSL
Database-specific SQL, or performance-criticalNative query
Bulk update or delete@Modifying @Query — with the caveat in Part 6

Part 4 — Projections: Stop Loading Entities

This is the highest-leverage technique in the lesson, and most codebases do not use it at all.

MEASURED: an order-list endpoint, 50 rows per page

  BEFORE -- returning entities
    List<Order> findByCustomerId(Long id);

    SQL: select o.* from orders o where o.customer_id = ?
    Then, because the DTO mapper touched o.getCustomer().getName()
    and o.getItems().size():
       + 1 query per order for customer      (50)
       + 1 query per order for items         (50)
    = 101 queries, 2.4 s, 18 MB of heap for objects that were
      immediately discarded after mapping 5 fields.

  AFTER -- an interface projection
    public interface OrderSummary {
        Long getId();
        String getReference();
        BigDecimal getTotal();
        OrderStatus getStatus();
        String getCustomerName();          // maps to customer.name
    }

    @Query("""
        select o.id as id, o.reference as reference, o.total as total,
               o.status as status, c.name as customerName
        from Order o join o.customer c
        where c.id = :customerId
        """)
    List<OrderSummary> findSummariesByCustomerId(@Param("customerId") Long id);

    SQL: ONE query, five columns, one join.
    = 1 query, 40 ms, 0.4 MB.

  60x faster, and the numbers get better as the entity grows,
  because a projection does not care how many columns the table has.
Projection typeDeclarationNotes
Interface (closed)Getters matching property namesSpring selects only those columns. The one to reach for
Interface (open)A getter with @Value("#{target.x + target.y}")Loads the whole entity — it needs the target to evaluate SpEL, so it loses the performance benefit
Class / record (DTO)select new com.acme.OrderSummary(o.id, o.total)Immutable and explicit; constructor signature must match exactly
Dynamic<T> List<T> findByStatus(Status s, Class<T> type)One query method, several shapes chosen by the caller
⚠️ An open projection silently defeats the purpose. The moment a getter carries @Value("#{target...}"), Spring must materialise the full entity to evaluate the expression — so you pay the entity cost and get a projection-shaped result. If you need a computed field, compute it in the JPQL select clause or in the calling code, and keep the projection closed.

Part 5 — save(), Batching, and References

  WHAT save() ACTUALLY DOES

    if (entity has no id)     -> persist()      one INSERT
    else                      -> merge()        SELECT, then UPDATE

  So saving a NEW entity that already carries an id -- because you
  assigned a UUID yourself -- costs a pointless SELECT on every
  insert:

    @Id private UUID id = UUID.randomUUID();     // assigned id

    repository.save(new Order(...));
      select * from orders where id = ?     <- always misses
      insert into orders ...

  MEASURED: 10,000 inserts with assigned UUIDs
    with the pointless selects       11.4 s
    implementing Persistable          6.9 s
    + batching (below)                1.2 s

  THE FIX for assigned ids:
    @Entity
    class Order implements Persistable<UUID> {
        @Id private UUID id = UUID.randomUUID();
        @Transient private boolean isNew = true;

        @Override public UUID getId() { return id; }
        @Override public boolean isNew() { return isNew; }

        @PostPersist @PostLoad
        void markNotNew() { this.isNew = false; }
    }

  BATCHING IS OFF BY DEFAULT AND COSTS ONE CONFIG BLOCK

  spring:
    jpa:
      properties:
        hibernate:
          jdbc.batch_size: 50
          order_inserts: true
          order_updates: true
          batch_versioned_data: true

  MEASURED: saveAll() of 10,000 rows
    default (no batching)        94 s      10,000 round trips
    batch_size: 50                1.2 s       200 round trips

  TWO THINGS THAT SILENTLY DISABLE BATCHING:
   1. GenerationType.IDENTITY. Hibernate must ask the database for
      each generated id, so it cannot batch inserts at all. Use
      SEQUENCE with an allocationSize matching your batch size.
   2. Flushing between saves -- including any query that triggers an
      AUTO flush inside the loop.

  getReferenceById() vs findById()

    findById(1L)          -> SELECT now, returns the entity or empty
    getReferenceById(1L)  -> NO query; returns a lazy PROXY

  USE getReferenceById WHEN YOU ONLY NEED THE FOREIGN KEY:

    Order o = new Order();
    o.setCustomer(customerRepo.getReferenceById(customerId));  // no SELECT
    orderRepo.save(o);            // insert ... customer_id = ?

    Saves a query per insert. On a bulk import of 100k orders that
    is 100k queries not run.

  THE TRAP: if the id does NOT exist, you get no error here. The
  proxy throws EntityNotFoundException the first time something
  touches a field -- which may be during JSON serialisation, in a
  different layer, wrapped in something unhelpful. And the insert
  will fail on the foreign key anyway.

  So: getReferenceById for setting associations you trust;
      findById when you need the data or need to validate existence.

Part 6 — Bulk Operations and open-in-view

  @Modifying BYPASSES THE PERSISTENCE CONTEXT

    @Modifying
    @Query("update Order o set o.status = :s where o.createdAt < :cutoff")
    int expireOldOrders(@Param("s") OrderStatus s, @Param("cutoff") Instant cutoff);

  One UPDATE statement instead of loading a million entities. But:

   - entities ALREADY in the persistence context are NOT updated;
     they keep their stale values and dirty checking may write them
     back over your bulk update
   - @Version is not incremented, so optimistic locking is bypassed
   - entity callbacks (@PreUpdate) do not fire
   - cascades do not apply

  MITIGATION:
    @Modifying(clearAutomatically = true, flushAutomatically = true)

  flushAutomatically: flush pending changes BEFORE the bulk update,
                      so they are not lost
  clearAutomatically: clear the context AFTER, so stale entities
                      cannot be written back

  Both default to FALSE, which is the wrong default for almost every
  real use.

  spring.jpa.open-in-view DEFAULTS TO TRUE. TURN IT OFF.

  What it does: keeps the EntityManager (and therefore a database
  connection) open for the ENTIRE request, including view rendering
  and JSON serialisation.

  Why it exists: so lazy associations still work when the view layer
  touches them. It makes tutorials work.

  Why it is wrong in production:
   - a connection is held while writing the response, so connection
     hold time is bounded by client speed, not query speed
   - every lazy getter Jackson touches fires a SELECT -- N+1 by
     accident, from the serialisation layer
   - it HIDES LazyInitializationException in development and
     produces it in production the moment someone disables OSIV or
     moves work to another thread

  spring.jpa.open-in-view: false

  Turning it off converts a class of latent production bug into a
  loud test failure. Expect to fix some lazy-loading sites; that is
  the point -- each one is a place you were doing unplanned I/O.
🔑 Boot logs a warning about open-in-view at startup precisely because the default is not the right choice and cannot be changed without breaking existing applications. Set it to false explicitly in every new service, and fix the resulting failures with fetch joins or projections — which is the work you would otherwise be doing later, under time pressure, in production.

Interview Questions

Beginner: How does Spring Data JPA implement a repository interface?

At startup, Spring scans for interfaces extending Repository and registers a factory for each. The factory creates a JDK dynamic proxy implementing your interface, and routes each call through a chain: to SimpleJpaRepository for the inherited CRUD methods, to a derived-query executor that parses the method name, to your @Query, or to a custom implementation class if you provided one.

Nothing is code-generated, so there is no source file to read — which is why the behaviour has to be understood rather than inspected. One useful consequence: a typo in a derived method name fails at startup with "No property 'stauts' found for type 'Order'", not at runtime.

Beginner: Why did my entity update without calling save()?

Because it was managed. An entity loaded inside a transaction lives in the persistence context, which keeps a snapshot of its loaded state. At flush — normally just before commit — Hibernate compares every managed entity against its snapshot and issues an UPDATE for any difference. That is dirty checking, and it is the intended behaviour.

The mirror-image question is more instructive: if you modify an entity outside a transaction, it is detached, nothing tracks it, and no update happens no matter how many setters you call. Both behaviours come from the same rule — the transaction boundary is the persistence-context boundary.

Mid: What is a projection and when would you use one?

A projection returns a subset of columns instead of a full entity — either as an interface with getters, or as a record populated by a constructor expression in JPQL. Spring generates a select for exactly those columns.

I reach for one on any read-only endpoint, especially list endpoints. The measured case I remember: an order-list page returning entities issued 101 queries and took 2.4 seconds, because the mapper touched two lazy associations per row. The same data as a closed interface projection with a join was one query and 40 milliseconds — and it stays fast as the entity grows, because a projection does not care how many columns the table has.

The trap is open projections. As soon as a getter has @Value("#{target...}"), Spring must load the full entity to evaluate the expression, so you pay the entity cost and get nothing back. Keep projections closed and compute derived values in the query or the caller.

Mid: Why is saveAll() slow, and how do you fix it?

Two independent reasons, and both need fixing.

First, JDBC batching is off by default. Without hibernate.jdbc.batch_size, every insert is its own round trip — 10,000 rows measured at 94 seconds, versus 1.2 seconds with a batch size of 50. You also want order_inserts and order_updates so statements for the same table group together, since a batch breaks whenever the statement changes.

Second, GenerationType.IDENTITY silently disables batching entirely, because Hibernate must ask the database for each generated key as it goes. Switching to SEQUENCE with an allocationSize matching the batch size lets it pre-allocate a block of ids and batch properly.

There is a third case worth knowing: if the entities carry ids you assigned yourself, save() treats them as detached and issues a SELECT before every INSERT. Implementing Persistable with an isNew flag removes that, and was worth 11.4 seconds down to 6.9 on its own.

Senior: What is open-in-view and what is your position on it?

It keeps the EntityManager — and therefore a database connection — open for the whole request, including view rendering and JSON serialisation, so lazy associations still resolve in the web layer. It defaults to true, and Spring Boot logs a warning about it at startup precisely because the default is not the right choice and cannot be changed without breaking existing applications.

I turn it off in every new service. Three reasons. Connection hold time becomes bounded by client speed rather than query speed, so a slow consumer occupies a pooled connection. Every lazy getter Jackson touches fires a query, which is N+1 arriving from the serialisation layer where nobody is looking for it. And most importantly it hides lazy-loading bugs — the code works in development and fails the moment someone disables OSIV, moves work to another thread, or introduces an async path.

Turning it off converts a class of latent production bug into loud test failures. You then fix each site with a fetch join or a projection, and that is work you would otherwise do later under production pressure. The honest cost is that enabling it on an existing codebase surfaces a batch of failures at once, so it wants doing deliberately rather than in a busy week.

Senior: When would you not use Spring Data JPA at all?

JPA is an object-graph mapper, and it earns its complexity when you are loading, mutating and saving object graphs inside a transaction — dirty checking, cascades and optimistic locking are genuinely valuable there. The cases where it stops paying:

Reporting and analytics. Aggregates, window functions and multi-table joins produce no object graph and no mutation. Spring's JdbcClient or jOOQ gives you the SQL you actually want with a fraction of the surprise. I would happily have JPA and JdbcClient in the same service using the same DataSource.

Bulk data movement. Loading a million entities to change one column is the wrong shape entirely — that is one UPDATE statement, or a database-side job.

Heavily database-specific work. JSONB operators, CTEs, upserts with on conflict, partitioning hints. You can reach them through native queries, but at that point JPA is providing connection handling and little else.

Very high write throughput. The persistence context costs memory and dirty-checking time proportional to the number of managed entities, which is why the standard advice for batch jobs is to clear() periodically — a sign you are working against the model.

The framing I would offer: the question is not "JPA or not" for a whole service, it is per use case. Mixing is normal and healthy, and a team that treats JPA as the only permitted data access ends up writing native queries through the repository interface anyway, with worse ergonomics than just using a SQL library for those paths.

Solution
Persists?Why
AYesThe entity is managed for the whole method, so dirty checking issues an UPDATE at commit. No save() needed.
BNofindById ran in its own short transaction and returned a detached entity. Nothing tracks it, so the setter changes an ordinary Java object and that is all.
CYes — inefficientlysave() on a detached entity with an id calls merge(): a SELECT to load a fresh managed copy, then field-by-field copy, then UPDATE at commit. Correct, at the cost of an extra query.

3 (medium): This endpoint takes 2.4 s for 50 rows. Diagnose and fix. 
  @GetMapping("/customers/{id}/orders")
  public List<OrderDto> list(@PathVariable Long id) {
      return repo.findByCustomerId(id).stream()

Solution

Diagnosis: N+1, twice over. findByCustomerId issues one query for the 50 orders. Then the mapper calls getCustomer().getName(), which initialises a lazy proxy — one query per order — and getItems().size(), which initialises a lazy collection — another query per order. 1 + 50 + 50 = 101 queries.

It also loads every column of every order and every line item to produce five fields.

  public interface OrderSummary {
      Long getId();
      String getReference();
      BigDecimal getTotal();
      String getCustomerName();
      long getItemCount();
  }

  @Query("""
      select o.id as id,
             o.reference as reference,
             o.total as total,
             c.name as customerName,
             count(i.id) as itemCount
      from Order o
      join o.customer c
      left join o.items i
      where c.id = :customerId
      group by o.id, o.reference, o.total, c.name
      """)
  List<OrderSummary> findSummaries(@Param("customerId") Long customerId);

One query, five columns. Measured on a comparable endpoint: 2.4 s → 40 ms, and heap per request from 18 MB to 0.4 MB.

DetailWhy
left join on itemsAn inner join would drop orders with no line items
count(i.id), not count(*)With a left join, count(*) returns 1 for an order with no items
Closed projectionNo @Value anywhere, so Spring selects only these columns
Aliases match getter namesRequired — as customerName binds to getCustomerName()

The alternative, if you genuinely need the entities (say the endpoint also mutates them), is join fetch to load associations in the same query. But for a read-only list endpoint, a projection is better: it avoids the persistence context entirely, so there is no dirty checking, no snapshot memory, and no risk of an accidental write.

Worth noting this endpoint would have failed loudly with open-in-view: false, because the lazy access happens in the mapper. That is the argument for turning OSIV off — it makes this bug a test failure instead of a production latency mystery.

4 (medium): A nightly import of 200,000 rows takes 31 minutes. Make it fast and explain each change. 
  @Entity
  class Reading {
      @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
      private Long id;
      private String sensorId;
      private Instant at;
      private BigDecimal value;
  }

  @Transactional
  public void importAll(List<Reading> readings) {

  }
Solution 
  // 1. SEQUENCE, not IDENTITY -- IDENTITY makes batching impossible
  @Id
  @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "reading_seq")
  @SequenceGenerator(name = "reading_seq", sequenceName = "reading_seq",
                     allocationSize = 100)
  private Long id;

  # 2. turn batching on
  spring.jpa.properties.hibernate:
    jdbc.batch_size: 100
    order_inserts: true
    order_updates: true

  // 3. clear the context periodically
  @Transactional
  public void importAll(List<Reading> readings) {
      int i = 0;
      for (Reading r : readings) {
          entityManager.persist(r);            // persist, not save
          if (++i % 100 == 0) {
              entityManager.flush();
              entityManager.clear();
          }
      }
  }
ChangeWhyEffect

Expected result, extrapolating from the measured 10,000-row case (94 s → 1.2 s): roughly 31 minutes down to under a minute.

The question I would ask before doing any of it: does this import need JPA? Inserting 200,000 rows with no object graph, no cascades and no dirty checking is exactly the shape JPA is worst at. A JdbcClient batch insert, or the database's native bulk loader (COPY on PostgreSQL), would be simpler and faster still. I would ship the JPA fixes because they are cheap, and raise the bulk loader as the real answer if this grows.

5 (hard): A bulk status update runs, and afterwards some rows have the old status again. Explain and fix. 
  @Transactional
  public void expireOrders(Instant cutoff) {
      List<Order> recent = repository.findByStatus(PENDING);   // loads 500
      auditService.record(recent.size());

      repository.expireOlderThan(cutoff);                       // bulk update

      for (Order o : recent) o.setLastCheckedAt(Instant.now());
  }

  @Modifying
  @Query("update Order o set o.status = 'EXPIRED' where o.createdAt < :cutoff")
  int expireOlderThan(@Param("cutoff") Instant cutoff);
Solution

Why some rows revert. findByStatus loaded 500 orders into the persistence context as managed entities, each with a snapshot showing status = PENDING. The @Modifying query bypasses the persistence context entirely — it issues one UPDATE straight to the database and does not tell Hibernate that anything changed.

Then the loop sets lastCheckedAt, which makes those entities dirty. At commit, dirty checking writes each one back — using the snapshot-based full entity state, which still says status = PENDING. Every order that was both in the loaded set and matched the cutoff gets its status silently overwritten back to PENDING.

The failure is data-dependent: it only affects the intersection of the two sets, which is why it looks intermittent.

  @Modifying(flushAutomatically = true, clearAutomatically = true)
  @Query("update Order o set o.status = 'EXPIRED' where o.createdAt < :cutoff")
  int expireOlderThan(@Param("cutoff") Instant cutoff);
FlagDoes
flushAutomatically = trueFlushes pending changes before the bulk update, so in-memory edits are not silently discarded by the clear
clearAutomatically = trueClears the context after, so no stale entity can be written back

Both default to false, which is the wrong default for essentially every real use of @Modifying.

But clearing has a consequence the fix must account for: after the clear, the recent list holds detached entities, so the setLastCheckedAt loop now silently does nothing. The honest fix restructures rather than just adding flags:

  @Transactional
  public void expireOrders(Instant cutoff) {
      long count = repository.countByStatus(PENDING);   // no entities loaded
      auditService.record(count);

      int expired = repository.expireOlderThan(cutoff);

      repository.touchLastChecked(Instant.now(), PENDING);   // second bulk update
  }

No entities are loaded at all, so there is no context to go stale. Two bulk statements instead of 500 entity loads plus 500 updates.

The general lesson: mixing bulk statements and managed entities in one transaction is a correctness hazard, not just a performance question. Pick one mode per transaction — either work through the persistence context, or work through bulk statements — and if you must mix, clear between them and treat everything loaded before the clear as gone. Note also that the bulk update bypasses @Version, so optimistic locking gives no protection here either.

6 (hard): Design the data-access strategy for a service with three workloads: a transactional order API, a reporting endpoint with 8-table aggregations, and a nightly 50-million-row export. Justify each choice.
Solution

Three workloads, three tools, one DataSource. The instinct to standardise on one data-access technology is what produces native queries smuggled through repository interfaces and batch jobs fighting the persistence context.

WorkloadToolWhy
Order APISpring Data JPAGenuine object graphs, mutation inside transactions, cascades, optimistic locking. This is exactly what JPA is for
ReportingJdbcClient (or jOOQ)8-table aggregates produce no object graph and mutate nothing. JPQL cannot express window functions or CTEs, and the entity machinery adds only overhead
50M-row exportStreaming JDBC, or the database's native exportJPA would hold 50M entities or need constant clear() calls. This is not an ORM problem
  // 1. ORDER API -- JPA, narrow repository interfaces
  interface OrderRepository extends Repository<Order, Long> {
      Optional<Order> findById(Long id);
      Order save(Order order);
      // NOT JpaRepository -- no findAll()/deleteAll() on a big table
  }

  // 2. REPORTING -- JdbcClient, read-only, on a replica
  @Repository
  class RevenueReportDao {
      private final JdbcClient jdbc;

      @Transactional(readOnly = true)
      List<RevenueRow> monthlyByRegion(YearMonth month) {
          return jdbc.sql("""
              with monthly as (
                select r.region, date_trunc('day', o.created_at) d,
                       sum(o.total) total
                from orders o join customers c on c.id = o.customer_id
                              join regions r on r.id = c.region_id
                where o.created_at >= :from and o.created_at < :to
                group by 1, 2)
              select region, d, total,
                     sum(total) over (partition by region order by d) running
              from monthly
              """)
              .param("from", month.atDay(1))
              .param("to", month.plusMonths(1).atDay(1))
              .query(RevenueRow.class).list();
      }
  }

  // 3. EXPORT -- stream, never materialise
  @Transactional(readOnly = true)
  void export(Writer out) {
      jdbc.sql("select id, reference, total, created_at from orders")
          .query(rs -> {                       // ResultSetExtractor
              while (rs.next()) writeCsvRow(out, rs);
              return null;
          });
  }
Cross-cutting decisionReason
spring.jpa.open-in-view: falseNon-negotiable with three workloads — connection hold time must track query time, not response time
Separate connection pools per workloadThe export must not be able to exhaust the pool the order API needs. A small dedicated pool for batch is the cheapest isolation available
Reporting and export on a read replicaAn 8-table aggregate and a 50M-row scan both evict the primary's buffer cache, which degrades the transactional workload for everyone
@Transactional(readOnly = true) on readsSkips dirty-checking snapshots in JPA, and routes to the replica if you use a routing DataSource
Fetch size on the exportWithout it, the JDBC driver may materialise the entire result set client-side — a 50M-row OOM regardless of streaming intent

The export is the one I would design most carefully, because the obvious failure is not slowness but a 50-million-row transaction holding a snapshot open for an hour, which on PostgreSQL blocks vacuum and bloats the table. If the export can tolerate it, chunking by id range in separate transactions is better than one long read — and if it cannot, that constraint should be written down, because it has an operational cost someone else will pay.

What I would push back on: a request to do all three through JPA repositories "for consistency". The consistency gained is in the import statements; the cost is native queries with no type safety returning Object[], and a batch job whose main logic is entityManager.clear(). Using the right tool per workload is not inconsistency — it is the same reason you do not use a single collection type for every job.

🎯 Key Takeaways

  • The persistence context is a write-behind cache with dirty checking. Managed entities are compared against a snapshot at flush and updated automatically.
  • The transaction boundary is the persistence-context boundary — put @Transactional on the service method that is one unit of work.
  • Modifying an entity outside a transaction does nothing, silently. It is detached.
  • save() on a detached entity calls merge(): an extra SELECT, and changes made to your reference afterwards are lost. Assign the result back.
  • Repositories are JDK dynamic proxies over SimpleJpaRepository, not generated code — which is why a typo'd method name fails at startup.
  • Extending JpaRepository exposes findAll() and deleteAll() on every table. Use Repository<T,ID> for large or critical ones.
  • Three conditions or any join, and a derived name should become a @Query named for its purpose.
  • Closed projections are the biggest easy win in Spring Data — 101 queries and 2.4 s became 1 query and 40 ms.
  • An open projection with @Value loads the whole entity, defeating the point.
  • Batching is off by default — 10,000 inserts took 94 s versus 1.2 s with jdbc.batch_size.
  • GenerationType.IDENTITY makes batching impossible. Use SEQUENCE with a matching allocationSize.
  • Assigned ids cause a SELECT before every INSERT unless the entity implements Persistable.
  • getReferenceById avoids a query when you only need the foreign key, but throws far away if the id does not exist.
  • @Modifying bypasses the persistence context, so stale managed entities can be written back over your bulk update — and @Version is not incremented.
  • Always use @Modifying(flushAutomatically = true, clearAutomatically = true); both default to false.
  • Set spring.jpa.open-in-view: false — it holds a connection through serialisation, causes accidental N+1, and hides lazy bugs until production.
  • Do not force one tool on every workload. JPA for object graphs, JdbcClient/jOOQ for reporting, streaming JDBC for bulk export.
