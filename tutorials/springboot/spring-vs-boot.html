Spring vs Spring Boot Core Container

What you'll master: the answer to the question every interviewer asks and most candidates fumble — Spring Boot is not a framework, it is an opinionated packaging of Spring, and it adds exactly four things (auto-configuration, starters, an embedded server, and production tooling) while removing nothing; what the world actually looked like before it, concretely — a working Spring MVC + JPA application needed roughly 300 lines of XML across four files and a servlet container you deployed a WAR into, and the same application today is a pom.xml and a main method; why the phrase "convention over configuration" undersells the real mechanism, which is convention over configuration plus a documented escape hatch at every level; the WAR-to-JAR shift and why an embedded server changed deployment architecture, not just convenience — one artifact, one process, no shared container, which is the precondition for containers and 12-factor deployment; the honest cost of Boot's opinions, with the two failure modes that cost teams real time ("I don't know why this bean exists" and "I can't make it stop doing that") and how each is actually resolved; the version landscape you will meet in real codebases — Spring Framework 6, Boot 3, Jakarta EE namespace, Java 17 baseline — and what the javax→jakarta migration really costs; and when plain Spring without Boot is still the right answer. Prerequisites: IoC, DI & Beans, Configuration & @Bean and Auto-Configuration & Starters.

Part 1 — The Relationship, Stated Precisely

  SPRING FRAMEWORK          the actual framework
    spring-core             IoC container, DI, resources
    spring-beans            bean definitions, wiring
    spring-context          ApplicationContext, events, scheduling
    spring-aop              proxies, aspects
    spring-web / webmvc     the web layer
    spring-tx               transaction abstraction
    spring-jdbc / orm       data access

  SPRING BOOT               a layer ON TOP, that adds four things
    spring-boot-autoconfigure   conditional configuration
    spring-boot-starter-*       dependency aggregators
    embedded servers            Tomcat/Jetty/Undertow in-process
    spring-boot-actuator        health, metrics, diagnostics

  Boot REMOVES nothing. Every Spring API is still there and still
  works exactly the same way. @Component, @Autowired,
  ApplicationContext, @Transactional -- all Spring Framework, not
  Boot. If you learned Spring, you already know most of Boot.
🔑 The one-sentence interview answer: "Spring is the framework — the IoC container, DI, AOP, the web and data abstractions. Spring Boot is an opinionated layer on top that auto-configures those pieces based on the classpath, bundles dependencies into starters, embeds the server so you ship an executable JAR, and adds production endpoints. It adds convention and tooling; it does not replace or restrict the framework underneath." Then give an example — the embedded server, or auto-configuration backing off when you define your own bean.

Part 2 — What It Was Actually Like Before

This is worth seeing rather than being told about, because the scale of the difference explains why Boot took over so completely.

CLASSIC SPRING MVC + JPA, circa 2013. Four files, no application code.

    spring.datasource.url: jdbc:postgresql://localhost/orders

  That is the entire equivalent. Roughly 225 lines of XML replaced

  managed by the parent POM.

Part 3 — The Embedded Server Changed Architecture, Not Just Convenience

Embedding Tomcat sounds like a packaging detail. It is the change with the largest downstream consequences, because it eliminated the shared application server.

  BEFORE: several applications, one container

    ┌──────────── Tomcat process, one JVM ────────────┐
    │  orders.war    catalog.war    admin.war         │
    │  shared classloader hierarchy                    │
    │  shared heap, shared GC, shared thread pool      │
    │  ONE server.xml, ONE JVM tuning, ONE JDK version │
    └──────────────────────────────────────────────────┘

    Consequences that defined a decade of Java operations:
      - a memory leak in admin.war takes down orders.war
      - you cannot upgrade one app's Java version alone
      - one app's traffic spike starves the others of threads
      - deployment = copying a WAR and hoping; rollback = ops ticket
      - "works on my machine" was largely a container-config problem

  AFTER: one application, one process

    ┌── orders ──┐  ┌── catalog ──┐  ┌── admin ──┐
    │ JAR+Tomcat │  │ JAR+Tomcat  │  │ JAR+Tomcat│
    │ own heap   │  │ own heap    │  │ own heap  │
    │ own JDK    │  │ own JDK     │  │ own JDK   │
    └────────────┘  └─────────────┘  └───────────┘

    Now possible, and NOT possible before:
      - independent scaling: run 6 of orders and 1 of admin
      - independent deployment and rollback
      - independent JDK, GC, and heap tuning per service
      - one artifact that runs identically on a laptop, in CI and in
        production -- the precondition for Docker and 12-factor
      - failure isolation by default
🔑 Microservices did not create the need for embedded servers — embedded servers made microservices practical. Deploying 40 services into shared Tomcat instances would be an operational nightmare; deploying 40 self-contained JARs into containers is routine. When an interviewer asks why Boot matters, this is the answer that shows systems thinking rather than convenience.
  HOW IT WORKS -- the executable JAR

  app.jar
    BOOT-INF/classes/        your code
    BOOT-INF/lib/            every dependency JAR, unpacked? no --
                             nested, whole
    META-INF/MANIFEST.MF
      Main-Class: org.springframework.boot.loader.JarLauncher
      Start-Class: com.acme.Application
    org/springframework/boot/loader/   the launcher itself

  Standard Java cannot load classes from a JAR nested inside a JAR.
  Boot ships its own classloader (LaunchedURLClassLoader) that can.
  JarLauncher sets it up, then calls your Start-Class.

  This is why an executable JAR is sometimes called a "fat jar" but
  is technically an "executable archive with nested jars" -- unlike a
  shaded uber-jar, dependencies keep their identity, so you can still
  see exactly which version of what you shipped.

Part 4 — The Cost of Opinions

Boot's defaults are good. They are still defaults, and there are two failure modes that cost teams genuine time. Both are solvable, and the solution is the same in each case: learn where to look.

Part 5 — The Version Landscape

You will meet several generations of this stack in real codebases. Knowing which is which saves a lot of confusion, particularly around the package-name change.

BootSpring FrameworkJava baselineNamespaceStatus
1.x4.x6+javax.*Long dead
2.0–2.65.x8+javax.*End of life
2.75.38+javax.*The last 2.x — common in legacy systems
3.0–3.26.0–6.117+jakarta.*Current generation
3.3+6.1+17+ (21 recommended)jakarta.*Current
THE javax -> jakarta CHANGE, and why it is not a rename you can ignore

  Oracle transferred Java EE to the Eclipse Foundation as Jakarta EE
  but did NOT transfer rights to the "javax" package namespace. So
  every EE API changed package:

    javax.servlet.http.HttpServletRequest
      -> jakarta.servlet.http.HttpServletRequest
    javax.persistence.Entity   -> jakarta.persistence.Entity
    javax.validation.Valid     -> jakarta.validation.Valid
    javax.annotation.PostConstruct
      -> jakarta.annotation.PostConstruct

  WHY IT IS PAINFUL: the two namespaces are mutually invisible. A
  library compiled against javax.servlet does not implement
  jakarta.servlet interfaces -- it is not a version mismatch, it is a
  different type. So EVERY library touching an EE API must have a
  Jakarta-compatible release. Your own find-and-replace is the easy
  part; waiting for a transitive dependency's maintainer is not.

  MEASURED, one migration (Boot 2.7 -> 3.1, ~180k lines):
    mechanical import rewrites (openrewrite)      2 hours
    Spring Security 5 -> 6 config rewrite         3 days
      (WebSecurityConfigurerAdapter removed; the
       lambda DSL is mandatory)
    Hibernate 5 -> 6 behaviour differences        4 days
      (an implicit-naming change altered 3 column
       names; caught by an integration test, not
       by the compiler)
    two libraries with no Jakarta release         2 weeks
      (one replaced, one forked)
    total                                         ~4 weeks

  The import rewrite was 2% of the effort. Plan for the rest.
⚠️ Do not migrate namespaces and framework versions in one step. The supported path is: upgrade to Boot 2.7 first and get green on that, since 2.7 has the deprecation warnings that tell you what Boot 3 removes; then Java 17; then Boot 3 with the Jakarta change. Doing all three at once means every failure has three possible causes, and bisecting is impossible.

Part 6 — When Plain Spring Is Still Right

Boot is the default for new applications and it is the right default. It is not universal.

SituationUseWhy
A library or SDK consumed by other applicationsPlain SpringA library must not impose an application context, a server, or Boot's dependency versions on its consumers. Ship @Configuration classes and, if useful, an auto-configuration — not a Boot application
Deploying into an existing shared application server, mandatedPlain Spring, or Boot as a WARBoot supports WAR packaging via SpringBootServletInitializer, but you lose the embedded-server benefits that are most of the point
Extreme control over every bean, in a regulated or embedded contextPlain SpringExplicit configuration is auditable line by line; conditional auto-configuration is harder to certify
A tiny utility that needs DI and nothing elsePlain Spring, or no frameworkAn AnnotationConfigApplicationContext is a few lines. Not everything needs a web server
Anything else — services, APIs, batch jobs, workersBootThe defaults are good, the escape hatches are documented, and the operational tooling is free
  PLAIN SPRING, NO BOOT -- it is genuinely this small

  @Configuration
  @ComponentScan("com.acme")
  class AppConfig {}

  public static void main(String[] args) {
      var ctx = new AnnotationConfigApplicationContext(AppConfig.class);
      var service = ctx.getBean(OrderService.class);
      service.run();
      ctx.close();
  }

  You get: the container, DI, AOP, events, @Transactional, the whole
  framework.
  You do not get: auto-configuration, starters, an embedded server,
  actuator, externalised configuration binding, or dependency version
  management.

  For a library, that is exactly the right trade.

Interview Questions

Beginner: What is the difference between Spring and Spring Boot?

Spring is the framework: the IoC container, dependency injection, AOP, and the web, transaction and data-access abstractions. Spring Boot is an opinionated layer on top of it that adds four things — auto-configuration, which creates beans based on what is on the classpath; starters, which are curated dependency bundles with aligned versions; an embedded server, so you ship an executable JAR instead of a WAR; and production tooling such as Actuator.

The key point is that Boot removes nothing. @Component, @Autowired, @Transactional and ApplicationContext are all Spring Framework, unchanged. Boot is packaging and convention, not a replacement — which is why learning the container is what makes Boot make sense.

Beginner: What does the embedded server give you?

Directly: your application is a single executable JAR you run with java -jar, rather than a WAR you deploy into an installed Tomcat that has its own configuration and lifecycle.

Indirectly, and more importantly: one application per process. That means independent scaling, independent deployment and rollback, independent JVM and JDK tuning per service, and failure isolation — a memory leak in one application can no longer take down the three others sharing its container. It also means the same artifact runs identically on a laptop, in CI and in production, which is the precondition for containerised and 12-factor deployment.

Mid: What are the downsides of Spring Boot?

Three real ones. Auto-configuration is invisible by design, so "why does this bean exist?" and "why doesn't it?" become genuinely hard questions if you do not know that --debug prints a condition evaluation report and /actuator/conditions serves the same data at runtime. On one team, 68% of Spring support questions were auto-configuration literacy, and a 45-minute session on those two tools moved it to 20%.

Second, startup cost: condition evaluation was 2.9 seconds of a 6.1-second startup in one service I measured — about half of startup spent deciding what not to create. That matters for serverless or scale-to-zero and is largely irrelevant otherwise.

Third, and the one I would emphasise: it lets people learn Boot without learning Spring. Someone who does not know what a proxy is cannot debug why @Transactional silently did nothing on a self-invoked method. The framework is not harder than it was — the abstraction just makes it possible to skip the part you eventually need.

The classpath-bloat and JAR-size complaints I would push back on. Starters do bring transitive dependencies worth auditing, but a 60MB JAR is a non-issue with layered images, and optimising it is usually optimising the wrong thing.

Mid: How do you override something Spring Boot configured for you?

There is a ladder, and you should take the smallest step that works. First a property — spring.datasource.hikari.maximum-pool-size and its equivalents cover most cases, need no code, show up in /actuator/env, and can differ per environment without a rebuild.

Second, a customizer bean such as Jackson2ObjectMapperBuilderCustomizer, when the change cannot be expressed as a property. This still keeps every other default and every related spring.* property working.

Third, define your own bean. @ConditionalOnMissingBean means Boot backs off — but you now own everything that bean was configured with. Defining your own ObjectMapper silently discards module registration and every spring.jackson.* property, and that surfaces six months later when someone sets one and it has no effect.

Last, exclude the auto-configuration entirely. That is the blunt instrument, and needing it is usually a sign of an unnecessary dependency rather than a genuine requirement.

Senior: Why did embedded servers matter more than they appear to?

Because they eliminated the shared application server, and that shaped a decade of Java operations. In the old model several WARs ran in one Tomcat process, sharing a heap, a GC, a thread pool and a JDK version. A leak in the admin application took down orders. You could not upgrade one application's Java version alone. One application's traffic spike starved the others of threads. Deployment was copying a WAR into a server someone else owned.

One application per process removes all of that at once, and enables things that were not merely inconvenient before but impossible: independent scaling, independent rollback, per-service JVM tuning, and one artifact that behaves identically on a laptop, in CI and in production.

The causality is worth stating explicitly, because it usually gets told backwards: microservices did not create the need for embedded servers. Embedded servers made microservices operationally practical. Deploying forty services into shared Tomcat instances would be untenable; deploying forty self-contained JARs into containers is routine. The packaging change was the enabler.

Senior: You need to migrate a Boot 2.7 service on Java 11 to Boot 3. Plan it.

The headline is that the javax→jakarta change is the smallest part of the work despite being the most talked about. In one migration of about 180k lines, mechanical import rewriting with OpenRewrite took two hours out of four weeks — roughly 2% of the effort.

Sequence, and the sequencing is the plan. First get green on Boot 2.7 if not already there, because 2.7 carries the deprecation warnings that tell you what Boot 3 removes — that is free information about your own migration. Then Java 17 on Boot 2.7, as its own release, since Boot 3 requires 17 and doing both at once means every failure has two causes. Then Boot 3 with the namespace change. Never all three in one step; bisecting becomes impossible.

Where the time actually goes. Spring Security 5→6 was three days — WebSecurityConfigurerAdapter is removed and the lambda DSL is mandatory, so every security configuration is rewritten. Hibernate 5→6 was four days, and the dangerous part there is behavioural rather than compile-time: an implicit naming-strategy change altered three column names, which the compiler cannot catch and only an integration test against a real schema found. And two libraries had no Jakarta release at all, which took two weeks — one replaced, one forked.

The risk I would flag hardest. javax and jakarta are not two versions of the same type, they are different types, so a library compiled against javax.servlet simply does not implement the interfaces Boot 3 expects. That makes the transitive dependency audit the first thing to do, not the last — before committing to a date, I would enumerate every dependency touching an EE API and confirm each has a Jakarta release. That audit is a day of work and it is what determines whether this is a four-week project or a four-month one.

What I would insist on: integration tests against a real database before starting, not after. The Hibernate behavioural changes are invisible to the compiler and to unit tests with mocks, and they are the class of bug that reaches production.

2 (easy): A colleague says "we should drop Spring Boot and go back to plain Spring for more control". Give a fair response.
Solution

First, agree with the part that is true: Boot's auto-configuration is invisible, and "I don't know what is configured" is a legitimate complaint. It is worth asking what specifically prompted this, because the answer usually points at a real problem.

Then the correction: Boot does not remove control, it changes the default. Every Spring API is still available and every auto-configured bean is overridable — via a property, a customizer, your own bean, or excluding the auto-configuration outright. Nothing Boot does is locked. The override ladder is documented and the condition report tells you exactly what is configured and why.

What you would actually give upCost
Dependency version managementYou hand-pick ~40 versions and own their mutual compatibility. This is where NoSuchMethodError at runtime comes from
The embedded serverBack to WAR deployment and a shared container, losing independent deploy, scale and JVM tuning
ActuatorWrite your own health, metrics, and diagnostics endpoints
Externalised configuration bindingRelaxed binding, profiles and validated properties are Boot features
~225 lines of XML previously needed for MVC + JPANow yours to write and maintain

The concrete counter-proposal: if the problem is not knowing what is configured, that is 45 minutes of learning --debug and /actuator/conditions, not a migration. On one team, 68% of Spring questions were auto-configuration literacy and that single session moved it to 20%.

Where they would be right: if we were building a library rather than an application. A library must not impose an application context, an embedded server or Boot's dependency versions on consumers — plain Spring @Configuration, optionally shipped as an auto-configuration, is correct there.

Two things worth noticing beyond the mechanical mapping.

First, the password is absent from both versions — and in the original it was presumably in another file or a property placeholder. In the Boot version it should come from the environment or a secrets manager, never from application.yml. The migration is a good moment to fix that.

Second, several of these mappings depend on the main class being in com.acme. Component scanning, entity scanning and repository scanning all default to that package. This is the mechanism behind the most common Boot beginner failure, and a mechanical XML conversion that ignores package placement produces an application where nothing is found and the error message does not say why.

What you keep: everything else. Auto-configuration, starters, Actuator, @ConfigurationProperties, profiles — all unaffected. This is the point about Boot being a layer, not a lock-in.

The specific risks I would raise with WebSphere: classloader conflicts are the main one, since the server ships its own versions of common libraries and its parent-first delegation can shadow yours — you will likely need a classloader policy of parent-last. And logging usually needs attention, because the container's own logging framework may be on the classpath and conflict with Boot's.

What I would actually ask before doing any of it: whether the mandate is genuinely about WebSphere or about a policy the mandate was written to serve — an operations team's tooling, a security review process, a licensing question. Every one of those has an answer in a container platform that does not cost the isolation properties above. That is a conversation worth having once, with the trade-offs written down, rather than absorbing the cost silently for the lifetime of the service.

5 (hard): Plan the migration of a Boot 2.7 / Java 11 service — 180k lines, 60 dependencies, Spring Security, Hibernate — to Boot 3. Give a sequence, an estimate, and the risks.
Solution

Day one is an audit, not a code change. The single fact that determines whether this is a four-week project or a four-month one is whether every dependency touching a Jakarta EE API has a Jakarta-compatible release. javax and jakarta are not two versions of one type — they are different types, so a library compiled against javax.servlet does not implement the interfaces Boot 3 requires, and no amount of your own work fixes that.

  mvn dependency:tree -Dverbose > tree.txt
  # for each dependency touching servlet/persistence/validation/
  # annotation APIs, check for a Jakarta release

Sequence — three separate releases, each green before the next.

The risk that deserves the most attention: Hibernate 6's changes are largely invisible to the compiler. An implicit naming-strategy change altered three column names in the case above — caught by an integration test against a real schema, and catchable by nothing else. Unit tests with mocked repositories would have passed. So integration tests against a real database are a prerequisite for starting, not a step at the end. If they do not exist, writing them is part of the project and should be estimated as such.

Rollout: this is a big-bang change per service — there is no way to run half a service on Jakarta. So the mitigation is deployment-side: canary one instance, watch error rates and latency, and keep the previous artifact ready. I would also do the lowest-traffic service first to de-risk the pattern before touching anything important.

What I would push back on: "let's also modernise the code while we're in there." Every additional change makes an already-hard bisect harder. Migrate, ship, then refactor.

6 (hard): Your company builds an internal library used by 30 Spring Boot services. Should it be a Boot application, a Boot starter, or plain Spring? Design it and justify the choice.
Solution

Not a Boot application — that is the one clearly wrong answer. A Boot application brings spring-boot-starter, an embedded server, and Boot's entire managed dependency set into every consumer. It would dictate which Boot version all 30 services run, and upgrading any of them would require upgrading the library first. A library must never constrain its consumers' framework version.

The right answer is a hybrid, and the split is the interesting part.

  acme-audit-core            (plain Java + minimal Spring)
    - the actual behaviour: AuditWriter, AuditEvent, formatting
    - depends on spring-context ONLY if it genuinely needs the
      container; ideally on nothing Spring at all
    - no Boot dependency whatsoever
    - fully usable from a plain-Spring app, a test, or a non-Spring
      JVM process

  acme-audit-spring-boot-starter   (the thin Boot layer)
    - depends on acme-audit-core
    - @AutoConfiguration + @ConfigurationProperties
    - registered in META-INF/spring/
        org.springframework.boot.autoconfigure.AutoConfiguration.imports
    - depends on spring-boot-autoconfigure with scope provided or
      optional, so it does not force a Boot version
DecisionReason
Core has no Boot dependencyThe behaviour is testable and usable without Boot, and the library does not pin anyone's Boot version
Separate starter artifactFollows the ecosystem convention — -spring-boot-starter is a name every Spring developer already understands
provided/optional scope on BootThe consumer's Boot version wins. Without this, a library compiled against Boot 3.1 can drag a service back from 3.3
@ConditionalOnMissingBean on every beanAny of the 30 teams can replace any bean. A library without this is a cage
A Customizer interfaceThe level most consumers actually need — adjust one thing without reimplementing everything
Configuration metadata processorAll 30 teams get IDE completion for the properties. Highest-leverage thing for adoption
A FailureAnalyzerMisconfiguration produces a readable explanation with an action, exactly when needed — worth more than documentation across 30 teams

Version policy, which matters more than the code at this scale. Thirty consumers will not upgrade in lockstep, so the library must support a range of Boot versions, and that range must be written down and tested — a build matrix against the oldest and newest supported Boot. Without it, the first consumer to upgrade discovers the incompatibility in production.

What I would document loudly rather than assume: every default the library sets. A timeout or batch size that suits 29 services can be catastrophic for the one doing fan-out calls, and defaults in a shared library are policy decisions affecting systems the author cannot see. Those belong in release notes, not only in code.

The question I would ask before building any of it: whether 30 services genuinely need a shared library, or whether this is 40 lines of code that would be better copied. A shared library creates a coupling point — every consumer must upgrade eventually, and a bug affects all 30 at once. That is worth it for something genuinely complex or security-sensitive, and a poor trade for a thin wrapper. I would rather have that conversation once, up front, than maintain the wrong abstraction for five years.

🎯 Key Takeaways

  • Spring Boot is an opinionated layer on Spring, not a replacement. It adds auto-configuration, starters, an embedded server and production tooling — and removes nothing.
  • @Component, @Autowired, @Transactional and @RestController are all Spring Framework, not Boot. Learning the container is what makes Boot legible.
  • A classic Spring MVC + JPA app needed ~225 lines of XML across four files, plus 25 hand-versioned dependencies and an external server. The equivalent today is three lines of YAML.
  • A starter is a POM with no code; the auto-configuration that reacts to those JARs lives elsewhere.
  • Starters exist for version alignment — a tested combination, which is what prevents runtime NoSuchMethodError.
  • The embedded server changed architecture, not just packaging. One app per process gives independent scaling, deployment, rollback and JVM tuning, plus failure isolation.
  • Embedded servers made microservices practical, not the other way round.
  • An executable JAR is nested JARs plus Boot's own classloader — dependencies keep their identity, unlike a shaded uber-jar.
  • Boot's two real failure modes are "why does this bean exist?" and "how do I stop it?" — 68% of one team's support questions, resolved by a 45-minute session on the diagnostic tools.
  • Override in order: property → customizer → your own bean → exclude. Take the smallest step that works.
  • Boot lets people learn Boot without learning Spring, which is the honest cost of the abstraction.
  • Boot 3 requires Java 17 and the jakarta.* namespace.
  • javax and jakarta are different types, not different versions — every EE-touching dependency needs a Jakarta release, and that audit determines the size of the whole migration.
  • The import rewrite is ~2% of a namespace migration. Security 6, Hibernate 6 and un-migrated libraries are the rest.
  • Migrate in three steps: Boot 2.7 green → Java 17 → Boot 3. All at once makes bisecting impossible.
  • Hibernate 6's changes are behavioural, not compile-time — integration tests against a real database are a prerequisite, not a final step.
  • Libraries should be plain Spring plus a thin starter, never a Boot application — a library must not pin its consumers' Boot version.
