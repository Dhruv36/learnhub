Auto-Configuration & Starters Core Container

What you'll master: exactly how Spring Boot turns "a JAR is on the classpath" into "a fully configured bean", and why once you can read a condition evaluation report the framework stops being magic — the whole mechanism is a text file listing class names, plus conditions evaluated against bean definitions before any object exists; the three annotations inside @SpringBootApplication and what each one actually contributes; why @ConditionalOnMissingBean works only because auto-configuration is deliberately processed last, and what breaks when people forget that ordering guarantee; the difference between a starter (a dependency aggregator with almost no code) and an auto-configuration (the code), which is the distinction most candidates get wrong; how to debug the two questions that actually come up — "why does this bean exist?" and "why doesn't it?" — using --debug and the /actuator/conditions endpoint; the real cost of auto-configuration, measured (a service importing 148 auto-configurations evaluated 1,100 conditions and spent 2.9 s of a 6.1 s startup deciding what not to create), and the two supported ways to cut it; how to write your own auto-configuration properly, including the registration file that replaced spring.factories; and when auto-configuration is the wrong tool entirely. Prerequisites: Configuration & @Bean and IoC, DI & Beans.

Part 1 — @SpringBootApplication Is Three Annotations

@SpringBootApplication
public class App { public static void main(String[] a) { SpringApplication.run(App.class, a); } }

  is exactly equivalent to:

@Configuration                    // this class may declare @Bean methods
@ComponentScan                    // scan THIS package and below for @Component
@EnableAutoConfiguration          // apply Boot's conditional configuration
public class App { ... }
AnnotationWhat it contributesCommon mistake it causes
@ConfigurationThe class itself is a configuration classRarely a problem
@ComponentScanScans the package of this class and all sub-packagesPutting App.java in com.acme.app while services live in com.acme.services — nothing is found, and the error is a confusing "no qualifying bean"
@EnableAutoConfigurationImports every registered auto-configuration class and evaluates its conditionsAssuming it scans your code. It does not — it only applies pre-registered configurations from JARs
⚠️ The package-placement rule is the single most common Spring Boot beginner failure. Component scanning starts at the package of the @SpringBootApplication class. Put your main class in the root package of your application — com.acme.orders — with everything else beneath it. If you must scan elsewhere, be explicit with @ComponentScan(basePackages = {...}), but know that a main class in a leaf package is usually a sign the packages need rearranging rather than the scan needing widening.

Part 2 — The Mechanism, End to End

Auto-configuration has a reputation for being magic. It is not — it is four concrete steps, and you can inspect the output of every one.

STEP 1 -- DISCOVER
  @EnableAutoConfiguration reads, from EVERY jar on the classpath:

    META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

  (Boot 2.7+. Before that: the "EnableAutoConfiguration" key in
   META-INF/spring.factories, now deprecated and removed.)

  It is a plain text file, one fully-qualified class name per line:

    org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
    org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration
    ... ~150 lines in spring-boot-autoconfigure alone

STEP 2 -- FILTER (cheaply, before loading classes)
  Each entry may be excluded by:
    - spring.autoconfigure.exclude in properties
    - @SpringBootApplication(exclude = ...)
    - AutoConfigurationImportFilter, which uses a pre-built index
      (META-INF/spring-autoconfigure-metadata.properties) to reject
      candidates on @ConditionalOnClass WITHOUT loading the class.
      This is a real optimisation: class loading is the expensive part.

STEP 3 -- EVALUATE CONDITIONS
  Surviving classes are processed as @Configuration, and every
  @Conditional* on the class and on each @Bean method is evaluated
  against the CURRENT BeanDefinitionRegistry.

STEP 4 -- REGISTER
  Bean definitions from matching configurations are registered.
  Objects are created later, in the normal lifecycle.

A real auto-configuration is unremarkable once you see one. This is the shape of essentially all of them:

@AutoConfiguration
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })
@ConditionalOnMissingBean(type = "io.r2dbc.spi.ConnectionFactory")
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {

    @Configuration(proxyBeanMethods = false)
    @ConditionalOnMissingBean(DataSource.class)
    @ConditionalOnProperty(name = "spring.datasource.type",
                           havingValue = "com.zaxxer.hikari.HikariDataSource",
                           matchIfMissing = true)
    static class Hikari {
        @Bean
        HikariDataSource dataSource(DataSourceProperties properties) {
            return createDataSource(properties, HikariDataSource.class);
        }
    }
}

READ IT AS A SENTENCE:
  "If a JDBC DataSource class is on the classpath, and the user has
   not defined their own DataSource bean, and they have not asked for
   a different pool type, then create a Hikari pool configured from
   spring.datasource.* properties."

That is the whole idea. Every auto-configuration is that sentence
with different nouns.

Why @ConditionalOnMissingBean works at all

  ORDERING IS THE ENTIRE TRICK:

    1. Your @Configuration classes and @Component scanning run FIRST
    2. Auto-configuration runs LAST

  So by the time DataSourceAutoConfiguration asks "is there already
  a DataSource bean?", YOUR definition is already registered, and the
  answer is yes. Boot backs off silently.

  This is why "just define your own bean and Boot's default goes
  away" works, and it is a deliberate design guarantee, not luck.

  THE COROLLARY PEOPLE MISS:
  @ConditionalOnMissingBean between TWO OF YOUR OWN configuration
  classes is meaningless -- there is no ordering guarantee among user
  configurations, so which one "wins" depends on classpath scanning
  order. It is only well-defined between a library's
  auto-configuration and the user's configuration.

Part 3 — Starters Are Not Auto-Configurations

This distinction is asked in interviews constantly and answered incorrectly nearly as often.

StarterAuto-configuration
What it isA POM with dependencies and no codeA @Configuration class with conditions
PurposeBring a coherent, version-aligned set of JARsCreate beans when those JARs are present
Examplespring-boot-starter-webWebMvcAutoConfiguration
Where it livesIts own artifact, usually emptyspring-boot-autoconfigure, or a library's own JAR
Can you have one without the other?Yes — a starter with no auto-config is just a dependency bundleYes — add the JAR manually and the auto-config still fires
  spring-boot-starter-web's ENTIRE content is its pom.xml:

    spring-boot-starter          (core: context, logging, autoconfigure)
    spring-boot-starter-json     (Jackson)
    spring-boot-starter-tomcat   (the embedded server)
    spring-web
    spring-webmvc

  No classes. No configuration. It is a shopping list.

  The auto-configuration that reacts to those jars lives elsewhere,
  in spring-boot-autoconfigure, and would fire just the same if you
  added the five dependencies by hand.

  WHY STARTERS STILL MATTER: version alignment. The starter's
  versions are managed by spring-boot-dependencies, so you get a
  combination that Spring actually tested together. Hand-picking
  versions is how you end up with a Jackson/Spring mismatch that
  fails at runtime with NoSuchMethodError.
🔑 Swapping an embedded server is the clearest demonstration that starters are just dependency lists. Exclude spring-boot-starter-tomcat from spring-boot-starter-web and add spring-boot-starter-undertow. You change no code and no configuration. ServletWebServerFactoryAutoConfiguration has a @ConditionalOnClass for each server and picks whichever is present. The classpath is the configuration.

MEASURED: what auto-configuration costs

  A typical service: web + JPA + security + actuator + kafka.

    auto-configurations on the classpath        148
    conditions evaluated                      1,104
    auto-configurations that MATCHED             61
    time in condition evaluation                2.9 s
    total startup                               6.1 s

  So ~48% of startup was spent deciding what NOT to create.

  Two supported ways to reduce it:

  1. EXCLUDE what you know you do not need
       spring.autoconfigure.exclude: >
         org.springframework.boot.autoconfigure.jmx.JmxAutoConfiguration,
         org.springframework.boot.autoconfigure.gson.GsonAutoConfiguration
     Measured saving on the above: 0.4 s. Modest, and it is a
     maintenance burden -- the list rots as dependencies change.

  2. REMOVE THE DEPENDENCY
     If GsonAutoConfiguration is being evaluated, Gson is on your
     classpath. Ask why. Removing an unused transitive dependency
     removes its auto-configuration, its classes, and its CVE
     surface.  This is strictly better than excluding it.

  For a genuinely large win, AOT processing and a native image move
  condition evaluation to BUILD time -- the same app started in
  0.09 s as a native binary. That is a different trade (build
  complexity, reflection configuration), covered in
  Production & Deployment.

Part 5 — Writing Your Own

The moment you have two services sharing setup code, you have a candidate. The mechanics are simple; the discipline is in the conditions.

  src/main/java/com/acme/audit/AuditAutoConfiguration.java

  @AutoConfiguration
  @ConditionalOnClass(AuditWriter.class)
  @ConditionalOnProperty(prefix = "acme.audit", name = "enabled",
                         havingValue = "true", matchIfMissing = true)
  @EnableConfigurationProperties(AuditProperties.class)
  public class AuditAutoConfiguration {

      @Bean
      @ConditionalOnMissingBean
      public AuditWriter auditWriter(AuditProperties props,
                                     ObjectProvider<AuditCustomizer> customizers) {
          var w = new AuditWriter(props.destination(), props.batchSize());
          customizers.orderedStream().forEach(c -> c.customize(w));
          return w;
      }

      @Bean
      @ConditionalOnMissingBean
      @ConditionalOnBean(DataSource.class)
      public AuditRepository auditRepository(DataSource ds) {
          return new JdbcAuditRepository(ds);
      }
  }

  src/main/resources/META-INF/spring/
      org.springframework.boot.autoconfigure.AutoConfiguration.imports

  com.acme.audit.AuditAutoConfiguration
RuleWhy
Every bean gets @ConditionalOnMissingBeanUsers must always be able to replace your bean. Without it your library is a cage.
Guard on @ConditionalOnClass for optional integrationsYour JAR may be present when its optional dependency is not. Referencing an absent class throws NoClassDefFoundError at configuration time.
Provide an enabled propertyConsumers need an off switch that does not involve removing a dependency
Offer a Customizer interfaceThe middle ground between accepting defaults and replacing the whole bean — which is what most users actually want
Use @AutoConfiguration(after = ...) for orderingIf you depend on another auto-configuration's beans existing, say so. @ConditionalOnBean is order-sensitive.
Never @ComponentScan from an auto-configurationIt scans the user's classpath from your package and creates beans they never asked for. Declare beans explicitly.
Ship the configuration metadata processorConsumers get IDE completion for your properties
⚠️ @ConditionalOnBean is order-dependent and @ConditionalOnMissingBean is not, in the way that matters. @ConditionalOnMissingBean is safe against user beans because user configuration is processed first. But @ConditionalOnBean checks for a bean that may be registered by another auto-configuration that has not run yet — so without an explicit @AutoConfiguration(after = TheirAutoConfiguration.class), the condition can evaluate to false purely because of ordering. This produces the worst kind of bug: it works on one machine and not another, because classpath order differed.

When auto-configuration is the wrong tool

SituationBetter approach
Code used by exactly one applicationA plain @Configuration class in that app. Auto-configuration adds indirection with no reuse benefit
Configuration that must always applyA @Configuration the app imports explicitly — conditions imply optionality you do not want
Behaviour that should be obvious to readersExplicit wiring. Auto-configuration is invisible by design, which is a cost as well as a benefit
Something needing runtime decisionsConditions are evaluated once at startup. For per-request choices, inject a strategy and decide in code

Part 6 — Overriding and Failure Analysis

FOUR WAYS TO OVERRIDE, in increasing order of bluntness

  1. A PROPERTY -- always try this first
       spring.datasource.hikari.maximum-pool-size: 20
     No code. Visible in /actuator/env. Reversible.

  2. A CUSTOMIZER BEAN -- adjust without replacing
       @Bean
       Jackson2ObjectMapperBuilderCustomizer json() {
           return b -> b.serializationInclusion(NON_NULL);
       }
     Keeps every other default and every spring.jackson.* property.

  3. YOUR OWN BEAN -- replaces Boot's entirely
       @Bean ObjectMapper objectMapper() { ... }
     @ConditionalOnMissingBean means Boot backs off. But you now own
     EVERYTHING that bean was configured with, including properties
     that silently stop working.

  4. EXCLUDE THE AUTO-CONFIGURATION -- the blunt instrument
       @SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
     Disables a whole family of beans. Occasionally necessary (a
     service with the JPA starter but no database), usually a sign
     of an unnecessary dependency.

Boot also ships a diagnostic layer most people never notice until it saves them: the failure analyzer. When startup fails, Boot tries to translate the stack trace into a readable explanation with a suggested action.

  ***************************
  APPLICATION FAILED TO START
  ***************************

  Description:

  Failed to configure a DataSource: 'url' attribute is not specified
  and no embedded datasource could be configured.

  Reason: Failed to determine a suitable driver class

  Action:

  Consider the following:
      If you want an embedded database (H2, HSQL or Derby), please
      put it on the classpath.
      If you have database settings to be loaded from a particular
      profile you may need to activate it (no profiles are currently
      active).

  This comes from DataSourceBeanCreationFailureAnalyzer. You can
  write your own for a library: implement AbstractFailureAnalyzer<T>
  and register it in META-INF/spring.factories under
  org.springframework.boot.diagnostics.FailureAnalyzer.

  For a library used by 30 teams, a good failure analyzer is worth
  more than a page of documentation -- it appears exactly when it is
  needed and nowhere else.

Interview Questions

Beginner: What does @SpringBootApplication do?

It combines three annotations. @Configuration makes the class itself a source of bean definitions. @ComponentScan scans the class's own package and everything beneath it for @Component and its specialisations. And @EnableAutoConfiguration imports every auto-configuration class registered by JARs on the classpath and evaluates their conditions.

The practical detail worth knowing is the second one: component scanning starts at the package of this class. If the main class sits in com.acme.app and services live in com.acme.services, nothing is found, and the resulting "no qualifying bean" error gives no hint about why. Put the main class in the root package.

Beginner: What is the difference between a starter and an auto-configuration?

A starter is a POM — a curated, version-aligned list of dependencies with essentially no code. spring-boot-starter-web contains nothing but a pom.xml pulling in spring-web, spring-webmvc, Jackson and Tomcat.

An auto-configuration is the code: a @Configuration class guarded by conditions that creates beans when the relevant classes are present. WebMvcAutoConfiguration is what actually configures Spring MVC.

They are independent. You can add the five dependencies by hand and the auto-configuration still fires, because it reacts to the classpath, not to the starter. What the starter buys you is version alignment — a combination Spring has actually tested together, which is how you avoid a runtime NoSuchMethodError from a Jackson mismatch.

Mid: How does auto-configuration actually work?

Four steps. First, discovery: @EnableAutoConfiguration reads META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports from every JAR on the classpath — a plain text file of class names. Second, a cheap filter pass that uses a pre-built metadata index to reject candidates on @ConditionalOnClass without loading the classes, since class loading is the expensive part. Third, the surviving classes are processed as configuration classes and their @Conditional annotations are evaluated against the current bean definition registry. Fourth, matching definitions are registered; objects are created later in the normal lifecycle.

The crucial detail is when this happens: auto-configuration is processed last, after your own configuration and component scanning. That ordering is what makes @ConditionalOnMissingBean work — by the time Boot asks "does a DataSource already exist?", yours is registered, so it backs off.

None of it is magic, and you can see the whole decision tree with --debug, which prints the condition evaluation report with positive and negative matches and the exact condition that decided each one.

Mid: A bean you expect from a starter is not being created. How do you find out why?

Run with --debug and read the condition evaluation report, or hit /actuator/conditions for the same data as JSON without a restart. Find the auto-configuration under "Negative matches" and it tells you precisely which condition failed.

In practice it is nearly always one of four things. A missing class, meaning the dependency is not actually on the classpath — often because someone excluded a transitive dependency. A property condition not satisfied, such as a feature that requires enabled: true. A @ConditionalOnMissingBean that matched something you did not realise you had defined, so Boot correctly backed off. Or an explicit exclusion in spring.autoconfigure.exclude or on @SpringBootApplication.

The report distinguishes all four directly, which is why I would read it before reading any source code. It takes thirty seconds and removes all the guessing.

Senior: Your service takes 6 seconds to start and 148 auto-configurations are evaluated. What would you do?

First I would confirm where the time actually goes rather than assuming it is auto-configuration. The /actuator/startup endpoint with a BufferingApplicationStartup attributes time per step. In the case I have measured, condition evaluation was 2.9 s of 6.1 s — about half — with the rest in bean initialisation, and it is common for a couple of @PostConstruct methods doing I/O to dominate instead.

If it genuinely is auto-configuration, there are two levers and they are not equal. spring.autoconfigure.exclude saved 0.4 s in that measurement — modest, and the list rots as dependencies change, so it becomes maintenance debt. Far better is to ask why those auto-configurations are being evaluated at all: if GsonAutoConfiguration is in the report, Gson is on the classpath. Removing an unused transitive dependency removes its auto-configuration, its classes and its vulnerability surface at once. Strictly better than excluding it.

For a step change rather than a trim, AOT processing moves condition evaluation to build time, and a native image starts in around 90 milliseconds. That is a real trade — build complexity, reflection configuration, a slower CI pipeline — and worth it for scale-to-zero or serverless workloads, not for a service that starts twice a day.

The question I would actually ask first, though, is why six seconds matters. If it is failing a readiness probe or making deploys slow, that is worth fixing. If it is only a developer's inner loop, devtools restart or a smaller test slice addresses it far more cheaply than re-architecting startup.

Senior: Design an auto-configuration for an internal library used by 30 services.

The design constraint that dominates everything: 30 consumers means every default I choose is a policy decision applied to systems I cannot see, and every mistake has a 30-service blast radius.

Structure. An @AutoConfiguration class registered in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports — not spring.factories, which was deprecated in 2.7 and removed in 3.0 and will silently stop working on upgrade. Properties as a @ConfigurationProperties record with @Validated, and the configuration metadata processor shipped so all 30 teams get IDE completion.

Three levels of override, because different consumers need different amounts of control. Properties for the common case. A Customizer interface for teams that want to adjust one thing — this is the level most people actually need, and omitting it forces them to reimplement the whole bean. And @ConditionalOnMissingBean on every bean so a team can replace it entirely. A library without that last one is a cage.

Conditions. @ConditionalOnClass for anything optional, so my JAR being present when its optional dependency is not does not throw NoClassDefFoundError. An enabled property with matchIfMissing = true so there is an off switch that is not "remove the dependency". And explicit @AutoConfiguration(after = ...) wherever I use @ConditionalOnBean, because that condition is order-sensitive and the failure mode is that it works on one machine and not another.

Two things I would add that most libraries skip. A FailureAnalyzer, so a misconfiguration produces a readable explanation with a suggested action rather than a stack trace — for 30 teams that is worth more than documentation, because it appears exactly when needed. And a written note in the release notes whenever a default changes, since a timeout that suits 29 services can be catastrophic for the one doing fan-out calls.

What I would not do: @ComponentScan from the auto-configuration. It scans the consumer's classpath starting from my package and creates beans nobody asked for. Every bean gets declared explicitly.

🏋️ Exercises

1 (easy): A developer reports that no controllers or services are being found. The layout is below. Diagnose and give two fixes. 
  src/main/java/
    com/acme/boot/Application.java        <- @SpringBootApplication
    com/acme/web/OrderController.java     <- @RestController
    com/acme/service/OrderService.java    <- @Service
Solution

Diagnosis. @ComponentScan, included in @SpringBootApplication, scans the package of the annotated class and its sub-packages — here, com.acme.boot and below. com.acme.web and com.acme.service are siblings, not children, so neither is scanned. Nothing is registered, and the resulting error is usually a "no qualifying bean" or a 404 with no explanation of the cause.

  FIX 1 -- move the main class to the root package  (preferred)

    com/acme/Application.java             <- now scans com.acme.**
    com/acme/web/OrderController.java
    com/acme/service/OrderService.java

  FIX 2 -- widen the scan explicitly

    @SpringBootApplication(scanBasePackages = "com.acme")
    public class Application { ... }

Prefer fix 1. Fix 2 works, but the placement of the main class is a convention that many other things rely on: @EntityScan and @EnableJpaRepositories default to the same base package, and so does @ConfigurationPropertiesScan. Widening only the component scan fixes one symptom and leaves the others to surface later as separate confusing failures.

A main class in a leaf package is usually a signal that the package structure needs rearranging rather than the scan needing widening.

2 (easy): Explain, line by line, what this auto-configuration does and when each bean is created. 
  @AutoConfiguration
  @ConditionalOnClass(RedisTemplate.class)
  @ConditionalOnProperty(prefix = "acme.cache", name = "enabled",
                         havingValue = "true", matchIfMissing = true)
  @EnableConfigurationProperties(CacheProperties.class)
  public class CacheAutoConfiguration {

      @Bean
      @ConditionalOnMissingBean
      CacheManager cacheManager(RedisConnectionFactory f) { ... }

      @Bean
      @ConditionalOnBean(MeterRegistry.class)
      CacheMetrics cacheMetrics(CacheManager cm, MeterRegistry r) { ... }
  }
Solution
LineMeaning
@AutoConfigurationThis class is an auto-configuration: processed after all user configuration, and only if listed in the AutoConfiguration.imports file. The annotation alone does not register it.
@ConditionalOnClass(RedisTemplate.class)The whole class is skipped unless Spring Data Redis is on the classpath. This guard is what lets the library be a dependency of a service that does not use Redis.
@ConditionalOnProperty(... matchIfMissing = true)On by default; a consumer can set acme.cache.enabled=false to switch it off without removing the dependency.
@EnableConfigurationPropertiesRegisters CacheProperties as a bean, so it need not be component-scanned from the consumer's packages.
cacheManager + @ConditionalOnMissingBeanCreated only if the consumer has not defined their own CacheManager. This is the override mechanism, and it works because user config is processed first.
cacheMetrics + @ConditionalOnBean(MeterRegistry.class)Created only if Micrometer is configured — an optional integration that adds metrics when the consumer has monitoring, and stays silent otherwise.

The bug hiding in this code: @ConditionalOnBean(MeterRegistry.class) is order-sensitive. MeterRegistry is created by Spring Boot's own MetricsAutoConfiguration, and if that has not been processed yet when this condition is evaluated, the condition is false and cacheMetrics silently does not exist. Whether it works can depend on classpath ordering.

  @AutoConfiguration(after = MetricsAutoConfiguration.class)
  public class CacheAutoConfiguration { ... }

This is the difference between @ConditionalOnMissingBean, which is safe against user beans because of the guaranteed ordering, and @ConditionalOnBean, which is not safe against other auto-configurations without an explicit after.

3 (medium): You add spring-boot-starter-data-redis, but RedisTemplate cannot be injected. Give an ordered diagnostic procedure.
Solution

1. Read the condition report before anything else.

  java -jar app.jar --debug 2>&1 | grep -A6 "RedisAutoConfiguration"

  # or, at runtime:
  curl -s localhost:8080/actuator/conditions \
    | jq '.contexts.application.negativeMatches
          | with_entries(select(.key | test("Redis")))'

This distinguishes the four possible causes immediately, which is why it comes first.

Report saysCauseFix
Under negative matches, @ConditionalOnClass did not find RedisOperationsThe dependency is not really on the classpath — usually a dependency exclusion, a wrong scope (provided/test), or a failed resolutionmvn dependency:tree | grep redis and fix the build file
Under negative matches, @ConditionalOnMissingBean found beans of type RedisConnectionFactorySomething already defines one, so Boot correctly backed off — and yours may be misconfiguredFind your own definition; that is the bean being injected
Under positive matches, but injection still failsThe auto-configuration ran; the problem is in the consumer — a component-scan package issue, or injecting the wrong typeCheck package placement and the exact type requested
Under exclusionsExplicitly excluded in properties or on @SpringBootApplicationRemove the exclusion

2. If it is genuinely a missing class, confirm with the dependency tree rather than reading the POM — an exclusion three levels up in a parent or BOM is invisible in your own file.

3. Check the type you are injecting. A frequent version of this is asking for RedisTemplate<String, MyObject> when Boot auto-configures RedisTemplate<Object, Object> and StringRedisTemplate. Generics are part of the bean type for injection purposes, so the parameterised one does not match and you must define it yourself.

4. Check for a startup failure being swallowed. If Redis is unreachable, connection failures usually surface lazily on first use rather than at startup, so "cannot inject" and "cannot connect" are different problems that can look similar in a stack trace.

Point 3 is the one I have seen waste the most time, because the condition report shows everything matching correctly — the auto-configuration did its job, and the mismatch is at the injection point.

4 (medium): Boot auto-configures an ObjectMapper. You need NON_NULL inclusion and ISO dates. Show three ways, and say which you would ship.
Solution 
  WAY 1 -- properties  (no code at all)
    spring:
      jackson:
        default-property-inclusion: non_null
        serialization:
          write-dates-as-timestamps: false

  WAY 2 -- a customizer  (code, but keeps every default)
    @Bean
    Jackson2ObjectMapperBuilderCustomizer jsonCustomizer() {
        return b -> b.serializationInclusion(JsonInclude.Include.NON_NULL)
                     .featuresToDisable(
                         SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);
    }

  WAY 3 -- your own bean  (replaces Boot's entirely)
    @Bean
    ObjectMapper objectMapper() {
        return JsonMapper.builder()
            .addModule(new JavaTimeModule())
            .serializationInclusion(JsonInclude.Include.NON_NULL)
            .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
            .build();
    }
WayKeeps Boot's defaults?spring.jackson.* still works?Verdict
1 — propertiesYesYes, it is themShip this. No code, visible in /actuator/env, changeable per environment without a rebuild
2 — customizerYesYesRight choice when the change cannot be expressed as a property — a custom serialiser, a naming strategy
3 — own beanNoNo — silently ignoredAvoid unless you genuinely need total control

Why way 3 is a trap. It works, and the code looks clearer than the alternatives. What it silently discards is everything Boot's builder does for you: registering every Jackson module found on the classpath (including JavaTimeModule, Jdk8Module, and Kotlin support), applying the parameter-names module so constructor binding works, and honouring every spring.jackson.* property. Six months later someone sets spring.jackson.date-format in a manifest, it has no effect, and nobody connects that to a bean defined in a different file.

The general rule this illustrates: reach for a property first, then a customizer, then your own bean, then excluding the auto-configuration. Each step gives up more of what Boot did for you, so take the smallest step that solves the problem.

5 (hard): A service starts in 6.1 s; the report shows 148 auto-configurations and 1,104 conditions evaluated. Produce an ordered plan with expected gains, and say what you would refuse to do.
Solution

Step 0 — establish that startup time is a problem worth solving. Six seconds is irrelevant for a service that deploys twice a day and holds connections for hours. It matters if it is failing a readiness probe, making rolling deploys slow, or if this is a scale-to-zero workload. The right fix differs completely between those, so I would ask before optimising anything.

Step 1 — measure per step, do not assume.

  SpringApplication app = new SpringApplication(App.class);
  app.setApplicationStartup(new BufferingApplicationStartup(8192));

  curl -s :8080/actuator/startup | jq '.timeline.events
    | sort_by(-.duration) | .[:20]
    | .[] | {name: .startupStep.name, ms: .duration}'

In the measured case: 2.9 s in condition evaluation, ~2.4 s in bean initialisation, ~0.8 s elsewhere. It is very common for one or two @PostConstruct methods doing I/O to dominate instead, and that is a much cheaper fix — so this step decides everything after it.

ActionExpected gainCost
Move I/O out of @PostConstruct to ApplicationReadyEventOften seconds — the largest single win when it appliesLow; needs an honest HealthIndicator
Remove unused dependencies0.3–0.8 s, plus fewer classes and less CVE surfaceLow; needs a dependency-tree audit
spring.autoconfigure.exclude~0.4 s measuredOngoing maintenance — the list rots
Narrow @ComponentScan0.1–0.3 sLow, but easy to break later
Lazy initialisation globally1–2 sHigh — moves failures from CI to production

The order I would actually work in: fix @PostConstruct I/O first if the profile shows any, since it is cheap and often decisive. Then audit the dependency tree — if GsonAutoConfiguration is being evaluated, Gson is on the classpath, and asking why is strictly better than excluding it, because removing the dependency removes the classes and the vulnerability surface as well. Then stop, and re-measure against the original goal.

What I would refuse to do. spring.main.lazy-initialization=true in production: it buys a second or two by converting configuration errors from build-time failures into first-request failures at 3am, and it gives every cold endpoint a latency spike that does not reproduce under load. It is a development convenience. And I would not maintain a long spring.autoconfigure.exclude list for 0.4 s — it is the kind of configuration that is correct on the day it is written and quietly wrong a year later.

What I would propose if the requirement is genuinely sub-second: AOT and a native image, as a deliberate project with its own testing, not as a startup tweak. That is the only option on the list that changes the order of magnitude, and it should be chosen for a reason — serverless, scale-to-zero — rather than to make a number smaller.

6 (hard): Write a complete auto-configuration for an internal rate-limiting library, including registration, override points and a failure analyzer.
Solution 
  // 1. PROPERTIES -- typed, validated, documented
  @ConfigurationProperties(prefix = "acme.ratelimit")
  @Validated
  public record RateLimitProperties(
      boolean enabled,
      @Min(1) int defaultLimit,
      @NotNull Duration window,
      @NotNull Backend backend,
      Map<String, @Valid Rule> rules
  ) {
      public enum Backend { MEMORY, REDIS }
      public record Rule(@Min(1) int limit, @NotNull Duration window) {}

      public RateLimitProperties {
          if (window  == null) window  = Duration.ofMinutes(1);
          if (backend == null) backend = Backend.MEMORY;
          if (rules   == null) rules   = Map.of();
          if (defaultLimit == 0) defaultLimit = 100;
      }
  }

  // 2. AUTO-CONFIGURATION
  @AutoConfiguration(after = RedisAutoConfiguration.class)
  @ConditionalOnProperty(prefix = "acme.ratelimit", name = "enabled",
                         havingValue = "true", matchIfMissing = true)
  @EnableConfigurationProperties(RateLimitProperties.class)
  public class RateLimitAutoConfiguration {

      @Bean
      @ConditionalOnMissingBean
      RateLimiter rateLimiter(RateLimitProperties props,
                              ObjectProvider<RateLimitStore> store,
                              ObjectProvider<RateLimitCustomizer> customizers) {
          RateLimitStore s = store.getIfAvailable(
              () -> new InMemoryStore(props.window()));
          var b = RateLimiter.builder(s)
                     .defaultLimit(props.defaultLimit())
                     .window(props.window());
          props.rules().forEach((k, r) -> b.rule(k, r.limit(), r.window()));
          customizers.orderedStream().forEach(c -> c.customize(b));
          return b.build();
      }

      @Configuration(proxyBeanMethods = false)
      @ConditionalOnClass(RedisTemplate.class)
      @ConditionalOnProperty(prefix = "acme.ratelimit", name = "backend",
                             havingValue = "redis")
      static class RedisBackend {
          @Bean
          @ConditionalOnMissingBean(RateLimitStore.class)
          @ConditionalOnBean(RedisConnectionFactory.class)
          RateLimitStore redisStore(RedisConnectionFactory f,
                                    RateLimitProperties p) {
              return new RedisStore(f, p.window());
          }
      }

      @Bean
      @ConditionalOnBean(MeterRegistry.class)
      RateLimitMetrics rateLimitMetrics(RateLimiter rl, MeterRegistry r) {
          return new RateLimitMetrics(rl, r);
      }
  }

  // 3. REGISTRATION
  //  src/main/resources/META-INF/spring/
  //    org.springframework.boot.autoconfigure.AutoConfiguration.imports
  com.acme.ratelimit.RateLimitAutoConfiguration

  // 4. FAILURE ANALYZER -- the piece almost every library omits
  public class RateLimitBackendFailureAnalyzer
          extends AbstractFailureAnalyzer<MissingRateLimitStoreException> {
      @Override
      protected FailureAnalysis analyze(Throwable root,
                                        MissingRateLimitStoreException cause) {
          return new FailureAnalysis(
            "acme.ratelimit.backend is set to 'redis' but no "
              + "RedisConnectionFactory bean is available.",
            "Either add spring-boot-starter-data-redis and configure "
              + "spring.data.redis.*, or set acme.ratelimit.backend=memory. "
              + "Note that the memory backend is per-instance and will not "
              + "enforce a shared limit across replicas.",
            cause);
      }
  }

  //  src/main/resources/META-INF/spring.factories
  //  (failure analyzers still use spring.factories -- only
  //   auto-configuration registration moved to the .imports file)
  org.springframework.boot.diagnostics.FailureAnalyzer=\
    com.acme.ratelimit.RateLimitBackendFailureAnalyzer
DecisionReason
Three override levelsProperties for tuning, RateLimitCustomizer for adjusting, @ConditionalOnMissingBean for replacing. Most teams want the middle one, which libraries usually forget to provide.
@AutoConfiguration(after = RedisAutoConfiguration.class)@ConditionalOnBean(RedisConnectionFactory.class) is order-sensitive. Without this it can be false purely because of processing order, and it will differ between machines.
Redis backend in a nested static classThe nested @ConditionalOnClass means the outer class loads fine when Redis is absent — referencing RedisTemplate at the top level would throw NoClassDefFoundError.
ObjectProvider with a fallback for the storeFalls back to in-memory without requiring a second conditional bean, and lets a consumer supply their own store implementation.
Metrics only when Micrometer existsOptional integration: useful when the consumer has monitoring, invisible otherwise.
Failure analyzerFor 30 consuming teams this is worth more than documentation, because it appears exactly when it is needed. Note the action text warns that the memory backend is per-instance — that is the mistake this library will actually cause.

What I would deliberately not do: @ComponentScan from the auto-configuration, which would scan the consumer's classpath from my package; a @Profile anywhere, since I do not know what profiles 30 services use; or a default of backend: redis — the safe default is the one that works with no infrastructure, with the limitation documented rather than hidden.

The honest limitation to document loudly: the in-memory backend does not enforce a shared limit across replicas, so a service running 6 pods with a limit of 100 actually permits 600. That is the single most likely way this library gets misused, and it should be in the failure analyzer, the Javadoc and the release notes — not discovered in production.

🎯 Key Takeaways

  • @SpringBootApplication = @Configuration + @ComponentScan + @EnableAutoConfiguration.
  • Component scanning starts at the main class's package — put it in the root package, or nothing beneath a sibling package is found.
  • Auto-configuration is a text file of class names plus conditions, discovered from META-INF/spring/…AutoConfiguration.imports in every JAR.
  • Auto-configuration is processed last, after your own configuration. That ordering guarantee is the only reason @ConditionalOnMissingBean works as an override.
  • @ConditionalOnMissingBean between two of your own configs is a race — there is no ordering guarantee among user configurations.
  • @ConditionalOnBean is order-sensitive and needs @AutoConfiguration(after = ...), or it fails differently on different machines.
  • A starter is a POM with no code; an auto-configuration is the code. They are independent — the auto-config fires on the classpath, not on the starter.
  • Starters exist for version alignment, which is what prevents runtime NoSuchMethodError from mismatched transitive versions.
  • --debug prints the condition evaluation report, and /actuator/conditions gives the same data at runtime. This answers both "why does this bean exist?" and "why doesn't it?" directly.
  • Condition evaluation was 2.9 s of a 6.1 s startup in one measured service — about half of startup spent deciding what not to create.
  • Removing an unused dependency beats excluding its auto-configuration — same startup saving, fewer classes, less CVE surface, no list to maintain.
  • Override in increasing bluntness: property → customizer → your own bean → exclude. Take the smallest step that works.
  • Defining your own bean discards everything Boot's builder did, including modules and every related spring.* property — silently.
  • Every bean in a library needs @ConditionalOnMissingBean, or the library is a cage.
  • Provide a Customizer interface — adjusting one setting is what most consumers actually want, and without it they must reimplement the whole bean.
  • Never @ComponentScan from an auto-configuration — it scans the consumer's classpath from your package.
  • spring.factories no longer registers auto-configurations (removed in 3.0), though failure analyzers still use it.
  • A FailureAnalyzer is worth more than documentation for a shared library, because it appears exactly when it is needed.
