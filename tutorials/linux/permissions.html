Users, Groups & Permissions Foundations

What you'll master: that a user is an integer and a username is a lookup convenience, the exact three-way check the kernel performs (and why it stops at the first match rather than accumulating permissions), what the permission bits mean on directories as opposed to files, the three special bits that cause most "why can't it write there" incidents, how setuid actually elevates privilege and why root is increasingly the wrong tool, and where the traditional model runs out — ACLs, capabilities, and the ambient authority that containers inherit. Prerequisites: Files, Inodes & Links.

Part 1 — A User Is a Number

The kernel has no concept of the name "alice". Every permission decision is made on integers: a user ID and a set of group IDs. Names exist purely so humans can read output, and the translation happens in userspace, not in the kernel.

$ id
uid=1000(alice) gid=1000(alice) groups=1000(alice),27(sudo),128(docker)

$ id -u
1000                          # this is what the kernel actually stores

The mapping lives in /etc/passwd, which despite its name has not stored passwords in decades — those moved to /etc/shadow, readable only by root, precisely because /etc/passwd must be world-readable for name lookups to work.

$ getent passwd alice
alice:x:1000:1000:Alice Smith:/home/alice:/bin/bash
  │    │  │    │       │           │          └── login shell
  │    │  │    │       │           └── home directory
  │    │  │    │       └── GECOS (real name, historical field)
  │    │  │    └── primary GID
  │    │  └── UID
  │    └── 'x' = password is in /etc/shadow
  └── username

Because the kernel stores only the number, the name is a display detail — and that has a consequence people meet constantly with containers and NFS:

# On the host
$ ls -ln /srv/data/file            # -n shows numbers instead of names
-rw-r--r-- 1 1000 1000 42 Aug  8 11:20 /srv/data/file

# Inside a container where UID 1000 is a different account
$ ls -l /data/file
-rw-r--r-- 1 nodejs nodejs 42 Aug  8 11:20 /data/file

Nothing changed on disk. The file's owner is 1000 in both views; the container simply has a different /etc/passwd mapping that number to a different name. File ownership travels as integers, which is why a volume mounted into a container can be unreadable despite looking correctly owned, and why ls -ln is the diagnostic that cuts through the confusion.

The UID ranges are conventions worth knowing, because they determine what tools do automatically:

UIDMeaningNotes
0rootThe kernel special-cases this number, and only this number
1–999System accountsDaemons; typically no login shell and no password
1000+Regular usersuseradd allocates from here by default
65534nobodyDeliberately unprivileged; NFS maps unknown users here
🔑 Root is a number, not a name. Any account with UID 0 is root, regardless of what it is called. A backdoor account named backup with uid=0 has complete control of the machine. Auditing for this is a one-liner worth running on any system you inherit: awk -F: '$3==0 {print $1}' /etc/passwd should print exactly root and nothing else.

Part 2 — The Three-Way Check, and Why It Stops Early

Every file has one owner UID, one group GID, and nine permission bits arranged in three sets. The algorithm the kernel uses is short, and its most important property is that it is a first-match test, not an accumulation.

Can this process access this file?

   1. Is the process UID 0 (root)?          → allow (almost everything)
   2. Does process UID == file owner UID?   → use the OWNER bits, and STOP
   3. Is file GID in the process's groups?  → use the GROUP bits, and STOP
   4. Otherwise                             → use the OTHER bits

Step 2 stopping is the counter-intuitive part. If you own a file, the group and other bits are irrelevant to you — even when they grant more access than your owner bits:

$ echo data > /tmp/odd.txt
$ chmod 077 /tmp/odd.txt            # owner: none, group: rwx, other: rwx
$ ls -l /tmp/odd.txt
----rwxrwx 1 alice alice 5 Aug  8 11:30 /tmp/odd.txt

$ cat /tmp/odd.txt                  # as alice, the owner
cat: /tmp/odd.txt: Permission denied

$ sudo -u bob cat /tmp/odd.txt      # as anyone else
data

The owner is the only user who cannot read it. This is not a bug — it is the first-match rule working exactly as specified, and it explains a whole class of confusing "but I'm in that group" incidents.

The nine bits in octal are worth being fluent in rather than looking up:

OctalSymbolicOn a fileOn a directory
4rRead contentsList names (needs x to be useful)
2wModify contentsCreate/delete/rename entries
1xExecute as a programTraverse (enter, and access known names)

The directory column is where most confusion lives, and the previous lesson already showed why: since names live in directories, deleting a file is a write to the directory. The file's own permissions have nothing to do with it.

ModeTypical useMeaning
644Ordinary fileOwner writes; everyone reads
600Secrets, SSH keysOwner only — SSH refuses looser modes

Part 3 — The Three Special Bits

Above the nine bits sit three more, and each solves a specific problem that the basic model cannot.

setuid (4000) — when an executable with this bit runs, the process takes the file owner's UID rather than the caller's. This is how an unprivileged user changes their own password:

$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 68208 Mar 23 14:02 /usr/bin/passwd
   ^
   's' instead of 'x' — setuid

$ stat -c '%a %n' /usr/bin/passwd
4755 /usr/bin/passwd

/etc/shadow is mode 000 and owned by root, so nobody can write it. Yet passwd must. The setuid bit makes the process run as root for its lifetime, and the program is responsible for behaving. That responsibility is the entire security problem: a bug in any setuid binary is a privilege escalation, which is why the modern trend is to eliminate them.

setgid (2000) — on an executable it does the same for the group. On a directory, it does something far more useful: new files inherit the directory's group rather than the creator's primary group. This is the correct way to build a shared team folder:

$ sudo mkdir /srv/team && sudo chgrp devs /srv/team
$ sudo chmod 2775 /srv/team
$ ls -ld /srv/team
drwxrwsr-x 2 root devs 4096 Aug  8 11:45 /srv/team
        ^
        's' in the group position

$ touch /srv/team/notes.txt && ls -l /srv/team/notes.txt
-rw-rw-r-- 1 alice devs 0 Aug  8 11:45 /srv/team/notes.txt
                   ^
                   group is 'devs', not alice's primary group

Without setgid, every file alice creates is owned by group alice, and her colleagues cannot write to it despite the directory being group-writable. This single bit is the difference between a shared directory that works and one that generates a permissions ticket every week.

sticky (1000) — on a directory, it restricts deletion to the file's owner (or the directory's owner, or root), overriding the normal rule that directory write permission is enough:

$ ls -ld /tmp
drwxrwxrwt 10 root root 4096 Aug  8 11:50 /tmp
         ^
         't' — sticky

$ sudo -u bob touch /tmp/bobs-file
$ rm /tmp/bobs-file                 # as alice
rm: cannot remove '/tmp/bobs-file': Operation not permitted

Without it, /tmp being world-writable would let any user delete every other user's temporary files — a trivial denial of service.

❌ chmod -R 777 /var/www to "fix" a permissions problem. It works, in the sense that the error stops. It also means any compromised process on the machine can rewrite your application code, and it strips setuid/setgid bits from anything recursed into. It converts a narrow problem into a systemic one.

✅ Identify which of the three checks is failing, then fix that. Use namei -l /var/www/app/file to see the permission of every path component, sudo -u www-data test -r /path && echo ok to test as the real user, and set ownership (chown -R app:www-data) plus 2775/644 rather than opening everything. The answer is almost always a missing execute bit on a parent directory or a wrong group.

Part 4 — umask: Why Your New Files Are 644

Programs request permissions when creating files — typically 0666 for files and 0777 for directories. The kernel then removes the bits set in the process's umask. It is a subtraction mask, not a default.

$ umask
0022

  Requested by the program:   666   (rw-rw-rw-)
  umask:                    - 022   (----w--w-)
  ─────────────────────────────────
  Actual file mode:           644   (rw-r--r--)

  For a directory:
  Requested:                  777   (rwxrwxrwx)
  umask:                    - 022
  ─────────────────────────────────
  Actual:                     755   (rwxr-xr-x)

Note that the execute bit is never added by umask — a plain file created by a program asking for 0666 can never come out executable, which is a deliberate safety property.

$ umask 077 && touch /tmp/private.txt && ls -l /tmp/private.txt
-rw------- 1 alice alice 0 Aug  8 12:00 /tmp/private.txt

$ umask 002 && touch /tmp/shared.txt && ls -l /tmp/shared.txt
-rw-rw-r-- 1 alice alice 0 Aug  8 12:00 /tmp/shared.txt

$ umask 022                          # restore the default
umaskFilesDirsWhen to use it
022644755Default; world-readable
002664775Collaborative systems with per-user groups
027640750Hardened servers — nothing readable by "other"
077600700Private by default; correct for secret-handling daemons

umask is per-process and inherited by children, which makes it a genuine source of "works interactively, breaks under systemd" bugs. Your login shell reads it from /etc/profile or PAM; a systemd service does not, and defaults to 0022 regardless of what the account's profile says. If a daemon must create private files, set it explicitly in the unit:

[Service]
UMask=0077

Part 5 — Becoming Another User, and Why root Is Losing Its Job

Traditional Unix has exactly two privilege levels: root and everyone else. That coarseness is the source of most of its security weaknesses, and the modern toolkit is a set of ways to avoid needing full root.

sudo is the standard front door, and its value is not that it grants root — it is that it grants specific commands with an audit trail:

# /etc/sudoers.d/deploy   (always edit with visudo — a syntax error can lock you out)
%deploy ALL=(ALL) NOPASSWD: /bin/systemctl restart myapp, /bin/systemctl status myapp

Members of deploy may restart one service, with no password, and nothing else. Every invocation is logged. Compare that to handing out the root password, which is unauditable and irrevocable without changing it for everyone.

Writing safe sudo rules is harder than it looks, because many commands can be turned into a shell:

RuleWhy it is dangerous
ALL=(ALL) /usr/bin/vim:!sh inside vim gives a root shell
ALL=(ALL) /bin/findfind . -exec sh \; — same result
ALL=(ALL) /bin/chmodchmod +s any binary, then walk in later
ALL=(ALL) /usr/bin/systemctlUnrestricted systemctl can start a unit you wrote
Any rule with a wildcard path/bin/cat /var/log/* matches /var/log/../../etc/shadow

The safer pattern is to grant a purpose-built script rather than a general tool, and to make the script take no arguments that influence which file it touches.

Capabilities split root's powers into ~40 independent privileges, so a process can have exactly the one it needs. The canonical example is binding to a low port:

# The old way: run the whole web server as root, then hope it drops privileges correctly
# The modern way:
$ sudo setcap 'cap_net_bind_service=+ep' /usr/local/bin/myserver
$ getcap /usr/local/bin/myserver
/usr/local/bin/myserver cap_net_bind_service=ep

$ ./myserver --port 80              # binds port 80 as an ordinary user

A compromise of that process yields the ability to bind low ports — and nothing else. No file access, no module loading, no ability to become root. Under systemd this is declarative and preferable:

[Service]
User=myapp
AmbientCapabilities=CAP_NET_BIND_SERVICE
NoNewPrivileges=true

NoNewPrivileges=true is worth calling out: it makes the process and all its children permanently unable to gain privilege through setuid binaries, which neutralises an entire escalation path. Hardening builds the full unit sandbox around these primitives.

Part 6 — Where the Traditional Model Runs Out

Nine bits express exactly one owner and one group. When you need "alice and bob can write, the auditors can read, nobody else sees it", you have run out of model. Three mechanisms extend it.

ACLs attach arbitrary per-user and per-group entries to a file:

$ setfacl -m u:bob:rw /srv/reports/q3.csv
$ setfacl -m g:auditors:r /srv/reports/q3.csv
$ getfacl /srv/reports/q3.csv
user::rw-
user:bob:rw-
group::r--
group:auditors:r--
mask::rw-
other::---

$ ls -l /srv/reports/q3.csv
-rw-rw----+ 1 alice finance 8412 Aug  8 12:20 /srv/reports/q3.csv
          ^
          the '+' is the only hint in ls output that ACLs exist

That + is easy to miss, and it is the reason a file can be accessible to someone the permission bits appear to exclude. Any audit that reads ls -l without checking for it is incomplete. Default ACLs on a directory propagate to new files, which is the more maintainable use:

$ setfacl -d -m g:auditors:r /srv/reports        # -d = default, applies to new entries

MAC systems (SELinux, AppArmor) apply a policy the file owner cannot override — the traditional bits become a floor rather than the whole story. A process can be denied access to a file it owns outright:

$ ls -Z /var/www/html/index.html
unconfined_u:object_r:httpd_sys_content_t:s0 /var/www/html/index.html

# The classic SELinux symptom: perfect permissions, still denied
$ sudo ausearch -m avc -ts recent | tail -3

If permissions look correct and access is still refused, checking getenforce and the audit log should be an early step rather than a last resort.

Namespaces change what the numbers mean. A user namespace maps UID 0 inside a container to an unprivileged UID outside it, so a process can be root in its own world while the kernel treats it as nobody:

$ cat /proc/self/uid_map
         0       1000          1        # UID 0 inside == UID 1000 outside

This is the foundation of rootless containers, and it is the cleanest answer to "how do I let this thing think it is root without it actually being root". Namespaces & cgroups covers the mechanism in full.

Interview Questions

Beginner: What do rwx mean on a directory, as opposed to a file?

They mean something quite different, because a directory is a table of name→inode entries rather than a stream of bytes.

  • read (r) — you may list the names in it. Without execute, that is nearly useless: you get names but cannot access anything.
  • write (w) — you may create, delete, and rename entries. This is why deleting a file depends on the directory's permissions, not the file's. You can delete a root-owned read-only file from a directory you own.
  • execute (x) — you may traverse it: enter it, and access entries whose names you already know.

Because read and execute are independent, chmod 711 gives a directory that can be passed through but not enumerated — the standard pattern for a home directory that serves ~/public_html. Conversely, a missing x on any parent directory blocks access to everything beneath it no matter how open those files are, which is the usual cause of a web server returning 403 on a file that looks perfectly readable.

Beginner: What is umask and why are new files 644 rather than 666?

umask is a per-process mask of permission bits to remove from newly created files. It is a subtraction, not a default.

Programs typically request 0666 for a file and 0777 for a directory. With the common umask of 022, the kernel clears the group-write and other-write bits, producing 644 and 755. With umask 077 you get 600 and 700 — private by default.

Two details worth knowing. umask never adds bits, so an ordinary file created via a 0666 request can never come out executable — a deliberate safety property. And umask is inherited by child processes, which is why it is a common source of "works in my shell, breaks as a service": systemd does not read login profiles and defaults to 0022, so a daemon that must create private files needs UMask=0077 in its unit file.

Mid: Explain the setuid bit. Why is /usr/bin/passwd setuid, and why is the mechanism considered dangerous?

When an executable has the setuid bit, running it produces a process with the file owner's effective UID instead of the caller's. For a root-owned binary, any user who runs it gets a root-privileged process.

passwd needs it because /etc/shadow is mode 000 owned by root — literally nobody can write it through normal permissions. Yet an ordinary user must be able to change their own password. setuid lets the program run with the authority to write that file, and the program is responsible for enforcing the policy that you may only change your own entry.

That last sentence is the danger: the security check moves from the kernel into the application. Any bug in a setuid binary — a buffer overflow, an unsanitised environment variable, a command injection, a race in how it opens files — becomes a full privilege escalation. The attack surface includes things the author may not think of as input, such as LD_PRELOAD, resource limits, or an unexpected umask inherited from the caller.

The modern direction is to eliminate them. File capabilities grant one specific privilege (cap_net_bind_service rather than all of root); systemd's User= plus AmbientCapabilities= does it declaratively; polkit handles authorisation for desktop actions. Auditing what remains is worthwhile — find / -perm -4000 -type f 2>/dev/null — and anything unexpected there deserves investigation, since planting a setuid shell is a classic persistence technique.

Mid: A user is in the docker group. What have you actually granted them?

Effectively unrestricted root on the host, with no audit trail. This is the most commonly underestimated group membership on Linux.

The Docker daemon runs as root, and the group grants access to its socket, which is an unauthenticated API to that daemon. Anyone who can talk to it can ask for a container that mounts the host's root filesystem:

$ docker run -v /:/host -it alpine chroot /host sh
# whoami
root

That is a root shell on the host, reached without sudo, without a password prompt, and without appearing in the sudo logs. Variations using --privileged, --pid=host or mounting /etc achieve the same thing. No Docker configuration prevents this — the ability to specify mounts is the point of the API.

The practical implications: treat docker group membership as equivalent to granting passwordless full sudo, and audit it the same way. Where that is unacceptable, the alternatives are rootless Docker or Podman, which run the daemon as the user and rely on user namespaces so container root maps to an unprivileged host UID; or brokering access through a narrow sudo rule that runs a specific vetted command rather than exposing the socket.

Senior: A web server returns 403 on a file whose permissions look correct. Walk through your diagnosis.

"The file's permissions look fine" only rules out the last of at least five layers. I'd check them in order of how often they are the cause.

1. The whole path, not the file. Reaching a file requires execute on every ancestor directory. namei -l shows all of them at once, which is faster than ls -ld on each:

$ namei -l /var/www/app/public/index.html
f: /var/www/app/public/index.html
 drwxr-xr-x root  root  /
 drwxr-xr-x root  root  var
 drwxr-xr-x root  root  www
 drwxr-x--- deploy deploy app          ← www-data is not deploy and not other-executable
 drwxr-xr-x deploy deploy public
 -rw-r--r-- deploy deploy index.html

That single line identifies it. This is the cause the majority of the time.

2. Test as the actual user rather than reasoning about it, since the service account is often not what people assume:

$ ps -o user:16,cmd -C nginx | head -2
$ sudo -u www-data test -r /var/www/app/public/index.html && echo READABLE || echo DENIED

3. ACLs. A + in ls -l means the bits are not the whole story — and ACLs can be more restrictive than they appear, because the mask entry caps every named entry. getfacl is definitive.

4. SELinux or AppArmor. The signature is permissions that are demonstrably correct with access still denied. Contexts matter as much as modes:

$ ls -Z /var/www/app/public/index.html
unconfined_u:object_r:user_home_t:s0 ...    ← wrong type; httpd cannot read it
$ sudo ausearch -m avc -ts recent
$ sudo restorecon -Rv /var/www/app          ← usual fix after moving files in

Files moved with mv keep their original context (unlike cp, which inherits the destination's), so "it worked before I moved it there" is a strong SELinux tell.

5. The application layer. If all of the above pass, the 403 is nginx's own deny rule, a missing index directive with autoindex off, or an upstream returning it. Checking the error log rather than the access log distinguishes these immediately.

The discipline is going outside-in — path, then identity, then extended attributes, then MAC, then the app — because each step is cheap and eliminates a whole category. Jumping to chmod 777 "to see if that fixes it" both destroys evidence and, if it works, tells you almost nothing about which of the five layers was responsible.

Senior: Design the permission model for a multi-tenant application server where several teams deploy independently.

The goal is that a compromise or mistake in one tenant cannot read or modify another, and that no deployment path requires full root. I would build it from four layers, each of which holds if the one above fails.

1. One service account per tenant, no shared accounts. Each app runs as its own system user with no login shell, so a compromised process starts with an identity that owns almost nothing:

$ sudo useradd -r -s /usr/sbin/nologin -d /srv/app-a app-a
$ sudo install -d -o app-a -g app-a -m 750 /srv/app-a

750 rather than 755 matters: with world-execute, any other tenant can traverse in and read anything world-readable inside.

2. Separate deploy identity from runtime identity. The account that writes code should not be the account that executes it. If the running process cannot modify its own code, a remote code execution cannot achieve persistence by rewriting the application:

# deploy-a owns the files; app-a only reads them
$ sudo chown -R deploy-a:app-a /srv/app-a/code
$ sudo chmod -R 640 /srv/app-a/code && sudo find /srv/app-a/code -type d -exec chmod 750 {} +
# writable state is separate and narrow
$ sudo install -d -o app-a -g app-a -m 700 /srv/app-a/state

3. Narrow, auditable privilege escalation. No team gets general sudo. Each gets exactly the restart of their own unit, via a purpose-built rule with no arguments they control:

%team-a ALL=(root) NOPASSWD: /bin/systemctl restart app-a, /bin/systemctl status app-a

Not systemctl *, which would let them start a unit file they wrote.

4. Kernel-enforced isolation, because permissions alone are a weak boundary. This is the layer that actually contains a compromise, and systemd expresses it declaratively:

[Service]
User=app-a
NoNewPrivileges=true          # setuid binaries cannot escalate, ever
ProtectSystem=strict          # entire filesystem read-only...
ReadWritePaths=/srv/app-a/state   # ...except this
PrivateTmp=true               # its own /tmp — no cross-tenant temp-file attacks
ProtectHome=true              # /home invisible
RestrictAddressFamilies=AF_INET AF_INET6
AmbientCapabilities=          # empty: no capabilities at all

What I would deliberately avoid. A shared deploy group with write access across tenants, which silently makes every tenant equivalent. World-readable config directories, since one leaked database password crosses every boundary above. And running anything as root "temporarily" — the temporary version outlives everyone's memory of why.

Verification is part of the design, not an afterthought: I would have a test that runs as tenant A and asserts it cannot read tenant B's state directory, because a model nobody checks drifts within a quarter. For genuinely hostile multi-tenancy, this whole scheme is still shared-kernel and I would move to per-tenant VMs or gVisor rather than trusting UID separation alone.

🏋️ Exercises

1 (easy): Prove the permission check is first-match by locking the owner out of their own file.
Solution 
$ echo "the data" > /tmp/paradox.txt
$ chmod 077 /tmp/paradox.txt
$ ls -l /tmp/paradox.txt
----rwxrwx 1 alice alice 9 Aug  8 12:40 /tmp/paradox.txt

$ whoami
alice
$ cat /tmp/paradox.txt
cat: /tmp/paradox.txt: Permission denied      # the owner cannot read it

$ sudo -u nobody cat /tmp/paradox.txt
the data                                      # but a stranger can

The kernel matched at step 2 — "are you the owner?" — found the owner bits set to ---, and stopped. It never looked at the group or other bits, even though both grant full access.

The same rule produces the more common real-world version, where being in the group does not help because you own the file:

$ chmod 470 /tmp/paradox.txt        # owner: r--, group: rwx
$ echo more >> /tmp/paradox.txt
bash: /tmp/paradox.txt: Permission denied     # alice is IN group alice, but owns it

Permissions are not cumulative. The first matching class wins outright, which is why "add them to the group" sometimes changes nothing at all.

2 (easy): Build a shared team directory that actually works, and show what breaks without setgid.
Solution

The broken version first, so the failure is concrete:

$ sudo groupadd devs
$ sudo usermod -aG devs alice && sudo usermod -aG devs bob
$ sudo mkdir /srv/broken && sudo chgrp devs /srv/broken && sudo chmod 775 /srv/broken

$ touch /srv/broken/alice-file.txt          # as alice (after re-login)
$ ls -l /srv/broken/
-rw-r--r-- 1 alice alice 0 Aug  8 12:50 alice-file.txt
                   ^^^^^ group is 'alice', not 'devs'

$ sudo -u bob sh -c 'echo x >> /srv/broken/alice-file.txt'
sh: /srv/broken/alice-file.txt: Permission denied

The directory is group-writable, but the file got alice's primary group, so bob falls through to the "other" bits, which are read-only.

The fixed version — setgid on the directory:

$ sudo mkdir /srv/team && sudo chgrp devs /srv/team && sudo chmod 2775 /srv/team
$ ls -ld /srv/team
drwxrwsr-x 2 root devs 4096 Aug  8 12:52 /srv/team
        ^ setgid

$ touch /srv/team/alice-file.txt
$ ls -l /srv/team/
-rw-r--r-- 1 alice devs 0 Aug  8 12:52 alice-file.txt
                   ^^^^ inherited from the directory

Still not writable by bob, because umask 022 stripped group-write from the file. Both halves are needed:

$ umask 002 && touch /srv/team/shared.txt && ls -l /srv/team/shared.txt
-rw-rw-r-- 1 alice devs 0 Aug  8 12:53 shared.txt

$ sudo -u bob sh -c 'echo works >> /srv/team/shared.txt' && cat /srv/team/shared.txt
works

The durable fix is a default ACL rather than relying on every user's umask, since you cannot control what umask each person's shell or cron job uses:

$ sudo setfacl -d -m g:devs:rwx /srv/team
$ umask 022 && touch /srv/team/acl-test.txt && ls -l /srv/team/acl-test.txt
-rw-rw-r--+ 1 alice devs 0 Aug  8 12:55 acl-test.txt     # group-write despite umask 022

/usr/bin/sudo
/usr/bin/umount
/usr/lib/openssh/ssh-keysign

Each exists because an unprivileged user must perform an action that touches root-owned state:

BinaryWhy it needs root
passwd, chsh, gpasswdWrite /etc/shadow or /etc/passwd, which are not user-writable
su, sudoChange process credentials — inherently a root operation
mount, umountModify the mount table (only for entries marked user in fstab)
newgrpChange the process's group set
ssh-keysignRead the host key for host-based authentication

Also check setgid, which is easy to forget:

$ find / -perm -2000 -type f 2>/dev/null | head -5
/usr/bin/wall
/usr/bin/write
/usr/bin/ssh-agent
/usr/bin/crontab

The security exercise is spotting what does not belong. A setuid binary outside standard system paths is a strong indicator of compromise, since planting one is a classic persistence technique:

$ find /home /tmp /var/tmp /srv -perm -4000 -type f 2>/dev/null
/tmp/.hidden/sh                            ← nothing legitimate looks like this

Establish a baseline and diff it, which turns this from a one-off into monitoring:

$ find / -perm -4000 -type f 2>/dev/null | sort > /var/lib/setuid.baseline
# later, from cron:
$ find / -perm -4000 -type f 2>/dev/null | sort | diff /var/lib/setuid.baseline -

Reducing the list is also legitimate work. Mounting filesystems nosuid where users can write, and replacing setuid binaries with capabilities where possible, both shrink the attack surface permanently.

4 (medium): Replace a root-running service with an unprivileged one that binds port 80 using capabilities.
Solution

Show the problem first — ports below 1024 require CAP_NET_BIND_SERVICE, which ordinary users lack:

$ python3 -m http.server 80
PermissionError: [Errno 13] Permission denied

The bad fix is running the whole thing as root, which grants every privilege to solve one narrow need. The good fix grants exactly that one privilege:

$ sudo cp /usr/bin/python3.11 /usr/local/bin/pyserve
$ sudo setcap 'cap_net_bind_service=+ep' /usr/local/bin/pyserve
$ getcap /usr/local/bin/pyserve
/usr/local/bin/pyserve cap_net_bind_service=ep

$ /usr/local/bin/pyserve -m http.server 80 &
$ ss -tlnp | grep ':80 '
LISTEN 0 5 0.0.0.0:80 0.0.0.0:* users:(("pyserve",pid=54120,fd=3))

$ ps -o user,pid,cmd -p 54120
USER   PID   CMD
alice 54120  /usr/local/bin/pyserve -m http.server 80    # not root

Confirm the privilege is genuinely narrow — the process can bind a low port and nothing else:

$ grep Cap /proc/54120/status
CapEff: 0000000000000400          # only cap_net_bind_service
$ cat /etc/shadow                  # still no file access
cat: /etc/shadow: Permission denied

In production, do it declaratively rather than with a setcap'd binary, which is fragile (package upgrades replace the file and silently drop the capability):

[Service]
User=webapp
ExecStart=/usr/bin/python3 -m http.server 80
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
NoNewPrivileges=true

CapabilityBoundingSet caps what the process could ever acquire, and NoNewPrivileges blocks escalation via setuid binaries. Verify with systemctl show -p AmbientCapabilities myapp.

The honest alternative: a reverse proxy on 80 forwarding to an unprivileged port above 1024 avoids the question entirely and is what most production stacks actually do. Capabilities matter more when there is no proxy in front.

5 (hard): Diagnose a 403 caused by a missing execute bit several directories up, using only systematic tools.
Solution

Construct the fault:

$ sudo mkdir -p /srv/site/releases/v3/public
$ echo "<h1>hello</h1>" | sudo tee /srv/site/releases/v3/public/index.html >/dev/null
$ sudo chown -R deploy:deploy /srv/site
$ sudo chmod -R 755 /srv/site
$ sudo chmod 750 /srv/site/releases          # the fault, three levels up

The file itself looks perfect, which is what makes this confusing:

$ ls -l /srv/site/releases/v3/public/index.html
-rwxr-xr-x 1 deploy deploy 15 Aug  8 13:10 index.html      # world-readable
$ sudo -u www-data cat /srv/site/releases/v3/public/index.html
cat: ...: Permission denied

Step 1 — inspect the entire path at once. This is the tool that makes the problem obvious, and checking each directory with ls -ld is the slow way to reach the same answer:

$ namei -l /srv/site/releases/v3/public/index.html
f: /srv/site/releases/v3/public/index.html
 drwxr-xr-x root   root   /
 drwxr-xr-x root   root   srv
 drwxr-xr-x deploy deploy site
 drwxr-x--- deploy deploy releases      ← no 'x' for other; www-data stops here
 drwxr-xr-x deploy deploy v3
 drwxr-xr-x deploy deploy public
 -rwxr-xr-x deploy deploy index.html

Step 2 — confirm as the real user, rather than trusting the reasoning:

$ sudo -u www-data test -x /srv/site/releases && echo TRAVERSABLE || echo BLOCKED
BLOCKED
$ sudo -u www-data test -x /srv/site && echo TRAVERSABLE || echo BLOCKED
TRAVERSABLE

Bisecting the path this way localises it in two commands even without namei.

Step 3 — fix narrowly, not broadly. The instinct is chmod -R 755 /srv/site, which also makes every file world-writable-adjacent and would strip any setgid bits. Grant only traversal on the one directory:

$ sudo chmod o+x /srv/site/releases            # traversal only — still not listable
$ sudo -u www-data cat /srv/site/releases/v3/public/index.html
<h1>hello</h1>

$ sudo -u www-data ls /srv/site/releases
ls: cannot open directory: Permission denied   # deliberately still opaque

The better structural fix is group-based rather than opening to "other", so the permission expresses the actual intent:

$ sudo chgrp -R www-data /srv/site/releases
$ sudo chmod 750 /srv/site/releases
$ sudo -u www-data test -r /srv/site/releases/v3/public/index.html && echo OK
OK

The generalisable lesson: a 403 is a statement about a path, not a file. Reading the whole chain first turns a guessing game into a two-command diagnosis.

6 (hard): Design and verify least-privilege access for a deployment user who must restart a service and read its logs — nothing more.
Solution

The requirement is narrow, so the grant should be too. Each decision below is chosen against a specific escape it prevents.

1. Dedicated account and group, no shell login needed for automation:

$ sudo groupadd deployers
$ sudo useradd -r -m -s /bin/bash -G deployers ci-deploy

2. Read logs via group membership, not sudo. Requiring sudo to read a log is a smell — journald already has a group for exactly this:

$ sudo usermod -aG systemd-journal ci-deploy
$ sudo -u ci-deploy journalctl -u myapp -n 5 --no-pager

3. Restart via a precisely scoped sudo rule. The wildcard version is the trap:

# /etc/sudoers.d/ci-deploy   (edit with: sudo visudo -f /etc/sudoers.d/ci-deploy)
Cmnd_Alias MYAPP_CTL = /bin/systemctl restart myapp, \
                       /bin/systemctl reload myapp, \
                       /bin/systemctl status myapp
%deployers ALL=(root) NOPASSWD: MYAPP_CTL
Defaults:%deployers !requiretty, log_output

Full paths are mandatory — a relative command name would let them place a fake systemctl earlier in PATH. No wildcard, because systemctl * permits systemctl link on a unit file they wrote, which is arbitrary root code execution.

4. Verify what is granted — and confirm what is refused. Testing only the happy path is how over-broad rules survive review:

$ sudo -u ci-deploy sudo -l
User ci-deploy may run the following commands:
    (root) NOPASSWD: /bin/systemctl restart myapp, /bin/systemctl reload myapp,
                     /bin/systemctl status myapp

$ sudo -u ci-deploy sudo systemctl restart myapp        # allowed
$ sudo -u ci-deploy sudo systemctl restart sshd
Sorry, user ci-deploy is not allowed to execute '/bin/systemctl restart sshd' as root.
$ sudo -u ci-deploy sudo systemctl stop myapp
Sorry, user ci-deploy is not allowed to execute '/bin/systemctl stop myapp' as root.
$ sudo -u ci-deploy sudo -i
Sorry, user ci-deploy is not allowed to execute '/bin/bash' as root.
$ sudo -u ci-deploy cat /etc/shadow
cat: /etc/shadow: Permission denied

5. Confirm the audit trail exists, since an unlogged grant is unreviewable:

$ sudo journalctl -t sudo -n 3 --no-pager
sudo[55201]: ci-deploy : TTY=pts/1 ; PWD=/ ; USER=root ;
             COMMAND=/bin/systemctl restart myapp

What I deliberately did not grant. No editor, no find, no cat with a path argument, no systemctl wildcard, no docker group — every one of those converts this narrow grant into full root. And no password-less ALL=(ALL) ALL "for now", which is how these always start.

The residual risk worth naming: systemctl restart re-reads the unit file, so anyone who can write /etc/systemd/system/myapp.service can execute arbitrary code as root at the next restart. The grant is only as narrow as the unit file's permissions, so that file must be root-owned and not writable by deployers — verify with ls -l, and treat it as part of this design rather than a separate concern.

🎯 Key Takeaways

  • The kernel decides on integers — a username is a userspace lookup, which is why the same UID means different names inside a container and why ls -ln cuts through the confusion.
  • Root is UID 0, not the name "root"; any account with UID 0 has full control, so audit /etc/passwd for extras.
  • The permission check is first-match: owner, then group, then other — it stops at the first applicable class, so owning a file with mode 077 locks you out while strangers get in.
  • On directories, read means list, write means create/delete/rename entries, and execute means traverse — which is why deleting depends on the directory, not the file.
  • A missing execute bit on any parent directory blocks everything beneath it; namei -l diagnoses this in one command.
  • setuid runs a binary as its owner, moving the security check from the kernel into the application — every bug becomes privilege escalation, so audit with find / -perm -4000.
  • setgid on a directory makes new files inherit its group — the difference between a shared team folder that works and a weekly permissions ticket.
  • The sticky bit lets a world-writable directory like /tmp exist without users deleting each other's files.
  • umask subtracts bits from what programs request; it is inherited, and systemd ignores login profiles, so daemons needing private files require UMask= in the unit.
  • Capabilities split root into ~40 privileges — CAP_NET_BIND_SERVICE beats running a whole web server as root, and NoNewPrivileges=true closes the setuid escalation path.
  • Membership of the docker group is equivalent to passwordless root with no audit trail.
  • The nine bits express one owner and one group; beyond that you need ACLs (watch for the + in ls -l), MAC systems like SELinux (ls -Z), or user namespaces.
