The Shell Executes a Line The Shell

What you'll master: the exact expansion order bash applies to every line you type, and why knowing it turns quoting from superstition into arithmetic — why $var unquoted is a bug waiting for a filename with a space, why word splitting happens after variable expansion but pathname expansion happens after that, what actually happens when you press Tab or Enter, how the shell finds a command and why hash -r exists, and the difference between a subshell and a child process that explains why cmd | while read loses its variables. Prerequisites: How Unix Is Put Together and Users, Groups & Permissions.

Part 1 — The Expansion Pipeline

When you press Enter, bash does not "run your command". It transforms the line through a fixed sequence of stages, and only at the end does anything execute. Nearly every shell surprise is a consequence of this ordering, so it is worth committing to memory.

     you type:  echo $files *.txt "$HOME/a b"
                   │
   1. TOKENIZE ────┤  split on unquoted metacharacters, note quoting
                   │
   2. BRACE     ───┤  {a,b} → a b        (before variables — cannot use $var!)
                   │
   3. TILDE     ───┤  ~ → /home/alice
                   │
   4. PARAMETER ───┤  $var, ${var:-x} → their values
      COMMAND SUB  │  $(cmd), `cmd`  → their output
      ARITHMETIC   │  $((1+2))       → 3
                   │
   5. WORD      ───┤  split UNQUOTED results on $IFS  ← the dangerous one
      SPLITTING    │
                   │
   6. PATHNAME  ───┤  *, ?, [] → matching filenames
      EXPANSION    │
                   │
   7. QUOTE     ───┤  remove the quotes themselves
      REMOVAL      │
                   │
   8. REDIRECT  ───┤  set up >, <, | before the program starts
                   ▼
              fork + execve

Two orderings in that list cause most real bugs.

Brace expansion happens first, before variables exist. This is why the obvious loop does not work:

$ n=3
$ echo {1..$n}
{1..3}                         # literal — brace expansion already ran
$ echo {1..3}
1 2 3

$ seq 1 "$n"                   # the correct approach
1
2
3
$ for i in $(seq 1 "$n"); do printf '%s ' "$i"; done; echo
1 2 3

Word splitting happens after variable expansion. The shell substitutes the value, then re-splits the result on whitespace — as if you had typed the value yourself:

$ file="report final.txt"
$ touch "$file"

$ ls $file                     # unquoted: becomes two arguments
ls: cannot access 'report': No such file or directory
ls: cannot access 'final.txt': No such file or directory

$ ls "$file"                   # quoted: one argument
'report final.txt'

The mental model that makes this predictable: an unquoted $var means "paste the value here and re-parse it". A quoted "$var" means "insert this value as exactly one word". The second is what you want approximately always.

🔑 The rule that eliminates a whole class of bug. Quote every variable expansion unless you have a specific reason not to. There are exactly two common legitimate exceptions: when you deliberately want a string split into multiple arguments, and inside [[ ]], where bash suppresses splitting anyway. Everything else — "$file", "$@", "$(cmd)" — takes quotes. shellcheck flags the violations automatically and is worth running on every script you write.

Part 2 — Quoting Is Three Different Things

Bash has three quoting mechanisms and they stop different stages of the pipeline. Choosing between them is a question of which expansions you want.

FormStopsStill allowsUse for
'single'EverythingNothing — literal, including \Regexes, awk programs, literal $
"double"Word splitting, globbing$var, $(cmd), \Almost all variable use
\cThe next character onlyn/aOne special char inline
$'...'ExpansionsEscape sequences (\n, \t)Literal newlines/tabs in arguments
$ name="Alice"
$ echo 'Hello $name'
Hello $name                    # single: literal
$ echo "Hello $name"
Hello Alice                    # double: expands
$ echo "Cost: \$5"
Cost: $5                       # backslash escapes inside double quotes
$ printf '%s' $'line1\nline2'; echo
line1
line2                          # $'' interprets escapes

Single quotes cannot contain a single quote, not even escaped — this trips up everyone once. The workaround is to close, insert, and reopen:

$ echo 'it'\''s here'
it's here
#     ^^^^ close ' , escaped ' , reopen '

The single most important quoted form is "$@", which is special-cased by bash to expand to one word per argument, preserving those containing spaces:

$ cat > /tmp/args.sh <<'EOF'
#!/usr/bin/env bash
echo "--- \$* (joined) ---";   for a in $*;   do echo "[$a]"; done
echo "--- \$@ unquoted ---";   for a in $@;   do echo "[$a]"; done
echo "--- \"\$@\" quoted ---"; for a in "$@"; do echo "[$a]"; done
EOF
$ chmod +x /tmp/args.sh
$ /tmp/args.sh one "two three" four
--- $* (joined) ---
[one]
[two]
[three]
[four]
--- $@ unquoted ---
[one]
[two]
[three]
[four]
--- "$@" quoted ---
[one]
[two three]                    # correct — argument boundaries preserved
[four]

"$@" is the only form that passes arguments through unchanged. A wrapper script that uses $* or unquoted $@ silently corrupts any argument containing a space, which is why every serious wrapper ends with exec realcmd "$@".

❌ for f in $(ls *.txt); do rm $f; done — three bugs stacked: ls output is parsed, the unquoted $(...) is word-split on spaces, and the unquoted $f is split and glob-expanded again. A file called report final.txt becomes two nonexistent names; a file called * .txt is a genuine disaster.

✅ for f in *.txt; do rm -- "$f"; done — the glob produces exact filenames with no parsing step, the quotes prevent re-splitting, and -- stops a filename beginning with a dash being read as an option. For recursion, use find . -name '*.txt' -exec rm -- {} +, covered in find & xargs.

Part 3 — How the Shell Finds a Command

Given a command word, bash resolves it in a strict order. Knowing the order explains why an alias sometimes wins over a function, and why a freshly installed binary is sometimes "not found" when it demonstrably exists.

1. Alias            (only for interactive shells, only the first word)
2. Function
3. Builtin          (cd, echo, test, export...)
4. Hash table       (cached path from a previous lookup)
5. $PATH search     (left to right, first match wins — then cached)

$ type -a echo
echo is a shell builtin
echo is /usr/bin/echo          # both exist; the builtin wins

$ type -a ls
ls is aliased to `ls --color=auto'
ls is /usr/bin/ls

type -a is the tool that answers "what will actually run?", and it is the first thing to reach for when a command behaves unexpectedly. To bypass the earlier stages deliberately:

FormEffect
\ls or 'ls'Skip alias lookup
command lsSkip alias and function
builtin cdForce the builtin over a function
/usr/bin/lsSkip everything — exact binary
env lsSkip everything shell-level

Step 4 — the hash table — is the source of a genuinely confusing failure. Bash caches the resolved path of every command it runs, so moving or replacing a binary leaves a stale entry:

$ which mytool
/usr/local/bin/mytool
$ mytool --version
v1.0

$ sudo mv /usr/local/bin/mytool /opt/bin/mytool     # relocated, PATH updated elsewhere
$ mytool --version
bash: /usr/local/bin/mytool: No such file or directory
#     ^ bash is still using the cached path

$ hash -r                                            # clear the cache
$ mytool --version
v2.0

Note the error message names the old path, which is the giveaway. hash -r after installing or moving binaries costs nothing and saves confusion.

PATH order matters and is a security boundary. The first match wins, so a writable directory early in PATH lets anyone who can write there hijack a command:

$ echo "$PATH" | tr ':' '\n' | head -5
/home/alice/.local/bin
/usr/local/bin
/usr/bin
/bin

# The classic mistake — never do this:
$ export PATH=".:$PATH"        # '.' first means running any command in an
                               # untrusted directory can execute a planted binary

A ls script planted in a shared directory, with . on PATH, runs the moment someone cds there and types ls. This is why . is not on the default PATH and why you must type ./script explicitly.

Part 4 — Subshells, Child Processes, and Lost Variables

The most-reported "bash is broken" behaviour is a variable that refuses to persist:

$ count=0
$ find /etc -name '*.conf' 2>/dev/null | while read -r f; do
>     count=$((count + 1))
> done
$ echo "$count"
0                              # ...but it definitely counted files

Nothing is broken. Each stage of a pipeline runs in its own subshell, which is a fork of the current shell. The while loop incremented count in a child process; when that child exited, its memory went with it. The parent's count was never touched — and could not be, because processes do not share memory.

ConstructRuns in a subshell?Variables persist?
cmd1 | cmd2Yes — every stageNo
( commands )Yes, explicitlyNo
$(command)YesNo (output is captured)
cmd &YesNo
{ commands; }No — same shellYes
while ...; do ...; done < fileNoYes
source script.shNoYes

Three fixes, in order of preference:

# 1. Redirect instead of piping — no subshell at all (best when possible)
$ count=0
$ while read -r f; do count=$((count + 1)); done < <(find /etc -name '*.conf' 2>/dev/null)
$ echo "$count"
84

# 2. Restructure so the pipeline's output is captured
$ count=$(find /etc -name '*.conf' 2>/dev/null | wc -l)

# 3. lastpipe (bash 4.2+, requires job control off — scripts only)
$ shopt -s lastpipe; set +m
$ find /etc -name '*.conf' 2>/dev/null | while read -r f; do count=$((count+1)); done
$ echo "$count"
84

Option 1 uses process substitution — <(cmd) makes a command's output appear as a filename, so the loop reads from a redirect and stays in the current shell:

$ echo <(echo hi)
/dev/fd/63                     # it is literally a file descriptor path
$ diff <(sort a.txt) <(sort b.txt)     # compare without temp files

The related question of when a subshell is a full child process versus a cheaper construct also explains export. Variables are per-process; export marks one to be copied into the environment of children at execve time:

$ myvar="hello"
$ bash -c 'echo "child sees: $myvar"'
child sees:                    # not exported — child has no such variable

$ export myvar
$ bash -c 'echo "child sees: $myvar"'
child sees: hello

$ bash -c 'myvar="changed"'    # a child cannot affect the parent
$ echo "$myvar"
hello

The environment flows strictly downward, one copy at a time. There is no mechanism for a child to modify its parent's variables — which is exactly why cd must be a builtin, as Lesson 1 established.

Part 5 — Exit Status and Chaining

Every command produces an integer exit status: 0 for success, non-zero for failure. The shell's control flow is built entirely on it, and the inversion (0 is true) confuses newcomers because it is backwards from most languages.

$ ls /etc >/dev/null; echo "status=$?"
status=0
$ ls /nonexistent 2>/dev/null; echo "status=$?"
status=2
StatusMeaning
0Success
1General error
2Misuse of builtin / bad arguments
126Found but not executable (permission, or it is a directory)
127Command not found — usually a PATH or typo issue
128+NKilled by signal N (137 = 128+9 = SIGKILL, often the OOM killer)

That last row is worth internalising: a container exiting with 137 was killed with SIGKILL, and the usual cause is the OOM killer or a memory limit, not application logic. See Memory and Signals.

$ cmd1 && cmd2         # run cmd2 only if cmd1 succeeded
$ cmd1 || cmd2         # run cmd2 only if cmd1 failed
$ cmd1 ; cmd2          # run cmd2 regardless
$ cmd1 & cmd2          # run cmd1 in background, cmd2 immediately

A pipeline's status is that of its last command by default, which silently hides failures in earlier stages — the single most common cause of a script "succeeding" while doing nothing:

$ false | true; echo $?
0                              # the failure vanished

$ set -o pipefail
$ false | true; echo $?
1                              # now the pipeline reports the failure

$ false | true
$ echo "${PIPESTATUS[@]}"      # per-stage statuses
1 0

This is why the standard script preamble includes pipefail:

set -euo pipefail
#  │││ └─ pipefail: a pipeline fails if ANY stage fails
#  ││└─── nounset:  using an undefined variable is an error
#  │└──── errexit:  exit immediately on any unhandled failure
#  └───── (combined short form)

set -e has genuine sharp edges worth knowing — it does not trigger inside a condition, in a command followed by ||, or (in many cases) inside a function called in a conditional context. It is a useful safety net rather than a correctness guarantee, and Shell Scripting That Survives covers where it lets you down.

Part 6 — What Happens Between Keystroke and Execution

Putting the whole chain together, an interactive command traverses considerably more machinery than the expansion pipeline alone:

  keystroke
     │
     ├─ terminal driver (line discipline) buffers the line,
     │  handles backspace, and interprets Ctrl-C as a signal
     │
     ├─ readline: history, Tab completion, Ctrl-R search, editing keys
     │
  [Enter] → the line is delivered to bash
     │
     ├─ history is recorded
     ├─ the expansion pipeline (Part 1) runs
     ├─ command lookup (Part 3) resolves the first word
     │
     ├─ builtin?  → run in this process, done
     └─ external? → fork()
                     └─ child: apply redirections, then execve()
                        parent: waitpid() unless backgrounded
     │
  exit status → $?  → the prompt is redrawn

Two parts of that chain are not bash at all. The terminal line discipline is kernel code: it is what makes backspace work before bash sees anything, and what turns Ctrl-C into a signal delivered to the foreground process group. That is why Ctrl-C interrupts a running program that has no idea what a keyboard is:

$ stty -a | head -2
speed 38400 baud; rows 40; columns 160; line = 0;
intr = ^C; quit = ^\; erase = ^?; kill = ^U; eof = ^D;
     ^^^^^^^^ the kernel's mapping of keys to signals

readline is a library, not a shell feature, which is why the same editing keys work in python, psql, and gdb. The handful worth knowing pay for themselves immediately:

KeyAction
Ctrl-RSearch history backwards — the highest-value shortcut on this list
Ctrl-A / Ctrl-EStart / end of line
Ctrl-W / Ctrl-UDelete previous word / to start of line
Alt-.Insert last argument of the previous command
Ctrl-LClear screen (keeps the current line)
Ctrl-DEOF — exits the shell on an empty line
🔑 Ctrl-C and Ctrl-Z are not sent to your program by bash. The terminal driver sends SIGINT/SIGTSTP to the entire foreground process group, which is why Ctrl-C kills a whole pipeline rather than just the last stage. This also explains why a program that ignores SIGINT cannot be stopped that way, and why a background job that tries to read from the terminal gets stopped with SIGTTIN. Signals & Job Control builds on all of this.

Interview Questions

Beginner: What is the difference between single and double quotes?

They stop different stages of bash's expansion pipeline.

Single quotes suppress everything — the content is completely literal, including $, backticks, and backslashes. Use them for regexes, awk programs, and anything containing a literal dollar sign.

Double quotes suppress word splitting and pathname expansion (globbing), but still allow parameter expansion ($var), command substitution ($(cmd)), and arithmetic. This is what you want for almost all variable use: the value is inserted as exactly one word regardless of spaces in it.

$ f="my file.txt"
$ echo '$f'    → $f
$ echo "$f"    → my file.txt        (one word)
$ echo $f      → my file.txt        (two words — a bug)

A detail worth knowing: single quotes cannot contain a single quote at all, even escaped. You close, add an escaped quote, and reopen: 'it'\''s'. And $'...' is a fourth form that interprets escape sequences like \n and \t.

Beginner: Why does echo {1..$n} not work?

Because brace expansion is the second stage of the expansion pipeline and parameter expansion is the fourth. When bash processes the braces, $n has not been substituted yet — it is still the literal text $n, which is not a valid number, so bash gives up and leaves the whole construct as a literal string {1..$n}.

The ordering is deliberate and not a bug, but it makes brace expansion useless for anything dynamic. The alternatives:

$ seq 1 "$n"                         # external command, portable
$ for ((i=1; i<=n; i++)); do ...     # arithmetic context, no forking
$ eval "echo {1..$n}"                # works, but avoid — eval on
                                     # untrusted input is a code-injection hole

The general lesson is more valuable than the specific fix: when something expands "too early" or "too late", the expansion order is the explanation. Knowing that word splitting comes after parameter expansion, and globbing after that, predicts nearly every quoting surprise.

Mid: Why does a variable set inside cmd | while read lose its value?

Because every stage of a pipeline runs in its own subshell — a forked copy of the shell. The while loop is the last stage, so it executes in a child process. It sets the variable in that process's memory, and when the child exits, its memory is gone. The parent's copy was never modified, and could not be: processes do not share memory.

This is the same reason cd must be a builtin and why a child cannot alter its parent's environment. Variables flow downward at execve time and never back up.

The fixes, best first:

# 1. Avoid the pipe — process substitution keeps the loop in this shell
while read -r line; do count=$((count+1)); done < <(some_command)

# 2. Restructure so you capture output rather than looping
count=$(some_command | wc -l)

# 3. shopt -s lastpipe — runs the LAST stage in the current shell.
#    Requires job control disabled, so it works in scripts but not
#    interactively by default.

Worth knowing which constructs do not subshell: { ...; } grouping, a while loop with a plain < file redirect, and source. Compare with ( ... ), which subshells deliberately — useful when you want isolation, such as (cd /tmp && do_work) leaving your directory unchanged.

Mid: What does set -euo pipefail do, and where does it fall short?

Three separate safety options:

  • -e (errexit) — exit immediately if a command fails without its status being checked.
  • -u (nounset) — referencing an undefined variable is an error rather than silently expanding to empty. This is what prevents the notorious rm -rf "$PREFIX/" deleting / when PREFIX is unset.
  • -o pipefail — a pipeline's status is the first non-zero status among its stages, not just the last. Without it, failing_cmd | tee log reports success.

Where -e falls short, and this matters because people over-trust it:

set -e
false || true            # not triggered — failure is "handled" by ||
if false; then :; fi     # not triggered — inside a condition
f() { false; echo "still here"; }
f && echo ok             # -e is suppressed inside a function called this way
count=$(grep -c x file)  # assignment masks the status of the command

The last one is subtle and common: in local x=$(cmd), the exit status is that of local, not cmd, so failures vanish. Declare and assign on separate lines.

My practice is to use all three as a baseline safety net while still checking status explicitly at the points that matter, and to run shellcheck, which catches most of these statically. Treat -e as a seatbelt, not as error handling.

Senior: A deployment script works when run manually but fails under cron. Diagnose it systematically.

This is nearly always an environment difference, not a logic bug, and there are four usual causes. I would first capture the actual failure, since cron discards output unless you redirect it:

* * * * * /path/deploy.sh >/tmp/deploy.log 2>&1

1. PATH. Cron's PATH is typically just /usr/bin:/bin — no /usr/local/bin, no language version manager shims. A command found interactively is simply absent. The symptom is exit status 127. Fix by using absolute paths in the script or setting PATH= explicitly at the top; do not rely on the crontab's PATH= line alone, because the script may be run other ways too.

2. Non-interactive, non-login shell. Cron does not read .bashrc or .profile, so aliases, functions, and every variable set there are missing. Anything the script needs must be set by the script or sourced explicitly. This is also why nvm/rbenv/conda workflows break under cron so reliably.

3. No TTY. Programs that detect a terminal behave differently or fail outright — ssh asking for a passphrase, sudo demanding a tty, progress bars writing control codes, or a tool that buffers differently when stdout is not a terminal. Reproduce it faithfully with ssh's -n or by testing under setsid/< /dev/null.

4. Working directory and umask. Cron starts in $HOME, so every relative path resolves differently. And the umask is not your login umask, so created files may have unexpected permissions — the failure often appears one step later, as another process being unable to read what was written.

The reproduction that settles it rather than guessing:

$ env -i /bin/sh -c '/path/deploy.sh'        # empty environment, closest to cron

The durable fix is to make the script independent of its invocation environment: set -euo pipefail, an explicit PATH, absolute paths or a SCRIPT_DIR anchor as in The Filesystem, explicit umask, and no reliance on interactive shell configuration. In practice I would move scheduled work to a systemd timer instead, where the environment is declared in the unit file and the logs go to the journal automatically — see systemd.

Senior: Explain the security implications of the shell's expansion pipeline for a script that handles untrusted input.

The pipeline is a repeated-evaluation engine, and every stage where attacker-controlled text gets re-parsed is an injection point. The core danger is that an unquoted expansion means "paste this and re-parse it", which is textually equivalent to eval on a subset of the input.

1. Word splitting and globbing on untrusted values. A filename is attacker-controlled in any system that accepts uploads:

file="$1"                  # user-supplied: "x -rf /important"
rm $file                   # word-split → rm x -rf /important

Quoting fixes the splitting; -- is also required, or a filename beginning with a dash is read as an option: rm -- "$file".

2. eval and any construct that re-parses. eval, bash -c "$var", unquoted arithmetic contexts, and source on a user-controlled path are all direct code execution. $(( )) is genuinely surprising here: in bash, $((x)) where x="a[$(id)]" executes the substitution.

3. The argument boundary is the real defence. Passing data as a distinct argv element means no shell parses it. This is why the right answer for calling out to another program is usually to avoid a shell entirely — in Python, subprocess.run([...]) without shell=True; in shell, find -exec cmd {} + rather than building a command string with xargs and hoping.

4. Environment as an attack surface. A caller controls the environment of anything it spawns. IFS can be redefined so word splitting occurs on unexpected characters; PATH can be pointed at attacker binaries; BASH_ENV is sourced by non-interactive bash. A setuid shell script is unfixable for exactly these reasons, which is why Linux ignores the setuid bit on scripts.

What I actually do: quote every expansion and let shellcheck enforce it in CI; use -- before any user-derived path; use arrays for command construction (cmd=(rsync -a -- "$src" "$dst"); "${cmd[@]}") rather than string concatenation; validate inputs against an allowlist pattern rather than trying to escape them; and set PATH and IFS explicitly at the top of any script that matters. Above a certain complexity I stop writing shell — a language with real argument vectors and no re-parsing stage removes the entire class of bug rather than defending against it.

1 (easy): Demonstrate each stage of the expansion pipeline running in order.
Solution

Use set -x, which prints the command after all expansion — showing exactly what bash produced:

$ mkdir -p /tmp/exp && cd /tmp/exp && touch a.txt b.txt
$ files="a.txt b.txt"
$ n=2

$ set -x
$ echo ~/x {1,2} $files *.txt $((n*3)) "$files"
+ echo /home/alice/x 1 2 a.txt b.txt a.txt b.txt 6 'a.txt b.txt'
$ set +x

Reading the trace stage by stage:

{1,2}1 22 — brace
$filesa.txt b.txt (2 words)4 then 5 — expanded, then split

2 (easy): Show that "$@" is the only faithful way to forward arguments.
Solution 
$ cat > /tmp/show.sh <<'EOF'
#!/usr/bin/env bash
printf 'received %d args:\n' "$#"
i=1; for a in "$@"; do printf '  %d: [%s]\n' "$i" "$a"; i=$((i+1)); done
EOF
$ chmod +x /tmp/show.sh

$ cat > /tmp/wrap.sh <<'EOF'
#!/usr/bin/env bash
echo "=== \$* ===";     /tmp/show.sh $*
echo "=== \$@ ===";     /tmp/show.sh $@
echo "=== \"\$*\" ===";  /tmp/show.sh "$*"
echo "=== \"\$@\" ===";  /tmp/show.sh "$@"
EOF
$ chmod +x /tmp/wrap.sh

$ /tmp/wrap.sh alpha "two words" 'three  spaces'

=== $* ===
received 5 args:            ← boundaries destroyed
  1: [alpha]
  2: [two]
  3: [words]
  4: [three]
  5: [spaces]
=== $@ ===
received 5 args:            ← unquoted $@ is no better
  ...
=== "$*" ===
received 1 args:            ← everything joined into one string
  1: [alpha two words three  spaces]
=== "$@" ===
received 3 args:            ← correct
  1: [alpha]
  2: [two words]
  3: [three  spaces]        ← even internal double-space preserved

Only "$@" reproduces the original argument vector exactly. Bash special-cases it: inside double quotes it expands to one word per argument rather than a single joined string, which is unique in the language.

This is why every correct wrapper script ends with exec realcmd "$@". Using $* means any argument containing a space is silently corrupted — a bug that hides until someone uses a path with a space in it.

3 (medium): Prove the pipeline-subshell behaviour and fix a counter three different ways.
Solution

Show the variable is lost, and prove it is a separate process:

$ count=0
$ printf 'a\nb\nc\n' | while read -r x; do
>   count=$((count+1))
>   echo "  inside: count=$count  shell PID=$BASHPID  parent=$$"
> done
  inside: count=1  shell PID=56102  parent=55890
  inside: count=2  shell PID=56102  parent=55890
  inside: count=3  shell PID=56102  parent=55890
$ echo "outside: count=$count  shell PID=$BASHPID"
outside: count=0  shell PID=55890

$BASHPID differs from $$ inside the loop — conclusive proof it ran in a forked child. The count reached 3 in PID 56102, which then exited.

Fix 1 — process substitution (preferred):

$ count=0
$ while read -r x; do count=$((count+1)); done < <(printf 'a\nb\nc\n')
$ echo "$count"
3

Fix 2 — capture the output instead of looping:

$ count=$(printf 'a\nb\nc\n' | wc -l)
$ echo "$count"
3

Fix 3 — lastpipe (bash 4.2+; needs job control off, so scripts only):

$ cat > /tmp/lp.sh <<'EOF'
#!/usr/bin/env bash
shopt -s lastpipe
count=0
printf 'a\nb\nc\n' | while read -r x; do count=$((count+1)); done
echo "count=$count"
EOF
$ bash /tmp/lp.sh
count=3

Confirm which constructs avoid the subshell:

$ v=outer; { v=changed; }; echo "$v"
changed                      # brace grouping: same shell
$ v=outer; ( v=changed ); echo "$v"
outer                        # parens: subshell, discarded

The parenthesised form is useful deliberately — (cd /tmp && work) guarantees your directory is unchanged afterwards regardless of what happens inside.

4 (medium): Show how a pipeline hides failures and fix it three ways.
Solution 
$ cat /nonexistent | wc -l
cat: /nonexistent: No such file or directory
0
$ echo $?
0                            # SUCCESS — despite cat failing

This is why a backup script can "succeed" every night while producing empty archives. The status reported is wc's, and wc was perfectly happy counting zero lines.

Fix 1 — pipefail:

$ set -o pipefail
$ cat /nonexistent | wc -l 2>/dev/null; echo "status=$?"
status=1

Fix 2 — inspect every stage with PIPESTATUS, which is the diagnostic tool when you need to know which stage failed:

$ set +o pipefail
$ cat /nonexistent 2>/dev/null | sort | wc -l >/dev/null
$ echo "${PIPESTATUS[@]}"
1 0 0                        # stage 1 failed, 2 and 3 fine

It must be captured immediately — the next command overwrites it:

$ cat /nonexistent 2>/dev/null | wc -l >/dev/null
$ status=("${PIPESTATUS[@]}")     # save it first
$ echo "${status[0]}"
1

Fix 3 — restructure to remove the pipe, which is often the cleanest answer:

$ if ! data=$(cat /nonexistent 2>/dev/null); then
>   echo "read failed" >&2; exit 1
> fi
> echo "$data" | wc -l
read failed

The realistic case worth remembering — a failure in the middle of a long pipeline:

$ set -o pipefail
$ echo hi | grep nomatch | tee /tmp/out.txt; echo "status=$?"
status=1                     # grep's "no match" status now surfaces

Note the trade-off: pipefail makes grep finding nothing (status 1) into a pipeline failure, which under set -e aborts the script. That is often correct but sometimes not — cmd | grep -q pattern || true is the usual way to opt out for a specific stage.

5 (hard): Build a wrapper script that is transparent to the program it wraps — arguments, exit status, signals, and stdin all preserved.
Solution

Each requirement rules out a naive approach, so build it up:

$ cat > /tmp/wrapper.sh <<'EOF'
#!/usr/bin/env bash
set -uo pipefail            # deliberately NOT -e: we handle the status ourselves

log() { printf '[wrapper] %s\n' "$*" >&2; }

log "invoking: $*"
start=$SECONDS

# exec replaces this process: the child inherits the PID, so signals sent to
# the wrapper reach the real program, and no extra process sits in the tree.
exec "$@"
EOF
$ chmod +x /tmp/wrapper.sh

Verify each property. Arguments with spaces survive:

$ /tmp/wrapper.sh /tmp/show.sh alpha "two words"
[wrapper] invoking: /tmp/show.sh alpha two words
received 2 args:
  1: [alpha]
  2: [two words]              # boundary preserved

Exit status passes through, because exec means there is no wrapper left to return a different one:

$ /tmp/wrapper.sh sh -c 'exit 42'; echo "status=$?"
[wrapper] invoking: sh -c exit 42
status=42

Stdin flows through untouched:

$ printf 'x\ny\n' | /tmp/wrapper.sh wc -l
[wrapper] invoking: wc -l
2

Signals reach the real program, because exec keeps the same PID:

$ /tmp/wrapper.sh sleep 60 &
$ pid=$!; ps -o pid,cmd -p "$pid"
    PID CMD
  56430 sleep 60              # the wrapper is gone; sleep owns the PID
$ kill -TERM "$pid"; wait "$pid"; echo "status=$?"
status=143                    # 128 + 15 (SIGTERM) — correctly reported

If you need work after the child finishes, you cannot use exec, and must then handle signals and status manually — this is the version that gets written wrong:

$ cat > /tmp/wrapper2.sh <<'EOF'
#!/usr/bin/env bash
set -uo pipefail
child=0
# Forward signals to the child rather than dying and orphaning it
trap 'if [ "$child" -ne 0 ]; then kill -TERM "$child" 2>/dev/null; fi' TERM INT

"$@" &
child=$!
wait "$child"; status=$?
# wait returns 128+N when the child was signalled — preserve that faithfully
printf '[wrapper] finished with status %d\n' "$status" >&2
exit "$status"
EOF
$ chmod +x /tmp/wrapper2.sh
$ /tmp/wrapper2.sh sh -c 'exit 7'; echo "final=$?"
[wrapper] finished with status 7
final=7

The four mistakes this avoids: using $* instead of "$@" (corrupts arguments with spaces); forgetting exit "$status" (the wrapper returns the status of its own last command, usually the log line); not trapping signals in the non-exec version (Ctrl-C kills the wrapper and orphans the child); and using set -e, which would make the wrapper exit before it could report or clean up after a failing child.

6 (hard): Audit a script for injection vulnerabilities introduced by the expansion pipeline, and harden it.
Solution

The vulnerable original — a plausible-looking backup helper:

#!/bin/bash
# BAD: every line below has a defect
name=$1
dir=$2
tar czf /backups/$name.tar.gz $dir
eval "echo Backed up $name at $(date)" >> /var/log/backup.log
find /backups -name $name*.tar.gz -mtime +7 -delete

The defects, and how each is exploited:

LineDefectExploit
$name, $dir unquotedWord splitting + globbing./b.sh "x" "/etc /home" archives unintended paths
No -- before pathsA value starting with - is read as an optiondir="--exclude=* /" changes tar's behaviour
evalDirect code executionname='x; rm -rf /tmp/*;' runs as the script's user
-name $name*Glob expands against the cwd before find runsDeletes the wrong set, or errors unpredictably
No input validationname may contain / or ..name="../../etc/cron.d/evil" writes outside /backups
No set -uMissing arguments expand to emptyRunning with no args produces /backups/.tar.gz of the cwd

The hardened version:

#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'                          # remove space from IFS: safer splitting
PATH=/usr/bin:/bin; export PATH      # don't inherit a hostile PATH

usage() { printf 'usage: %s NAME DIR\n' "${0##*/}" >&2; exit 2; }
[ $# -eq 2 ] || usage

name=$1
dir=$2

# Validate against an ALLOWLIST — never try to escape or blocklist
[[ $name =~ ^[A-Za-z0-9_-]+$ ]] || { echo "invalid name: $name" >&2; exit 2; }
[ -d "$dir" ] || { echo "not a directory: $dir" >&2; exit 2; }

# Canonicalise and confine the source to an expected root
dir=$(readlink -f -- "$dir")
case $dir in
  /srv/*|/home/*) ;;
  *) echo "refusing to back up: $dir" >&2; exit 2 ;;
esac

archive="/backups/${name}.tar.gz"

# Build the command as an ARRAY — no string re-parsing anywhere
tar_cmd=(tar czf "$archive" -C "$(dirname -- "$dir")" -- "$(basename -- "$dir")")
"${tar_cmd[@]}"

# printf, never eval; %q would quote safely if the value were ever reused
printf 'Backed up %s at %s\n' "$name" "$(date -Is)" >> /var/log/backup.log

# Quote the pattern so FIND does the matching, not the shell
find /backups -maxdepth 1 -name "${name}-*.tar.gz" -mtime +7 -delete

Verify the hardening actually holds — testing only the happy path is how these ship broken:

$ ./backup.sh 'x; rm -rf /tmp/junk;' /srv/data
invalid name: x; rm -rf /tmp/junk;
$ ./backup.sh ../../etc/evil /srv/data
invalid name: ../../etc/evil
$ ./backup.sh good /etc
refusing to back up: /etc
$ ./backup.sh good /srv/data          # only the intended case works

The principles worth carrying: validate against an allowlist rather than escaping a blocklist; use arrays for command construction so no string is ever re-parsed; quote every expansion and add -- before user-derived paths; never eval; canonicalise paths with readlink -f and then confine them to an expected root; and set PATH and IFS explicitly so the caller's environment cannot redirect your behaviour. Run shellcheck in CI — it flags most of the original's defects automatically.

🎯 Key Takeaways

  • Bash transforms every line through a fixed pipeline: brace → tilde → parameter/command/arithmetic → word splitting → pathname → quote removal → redirection, then fork+exec.
  • Brace expansion runs before variables exist, which is why {1..$n} stays literal — use seq or a C-style loop.
  • Word splitting happens after parameter expansion, so an unquoted $var means "paste this value and re-parse it" — quote every expansion.
  • Single quotes stop everything, double quotes stop splitting and globbing while allowing $, and $'...' interprets escapes.
  • "$@" is special-cased to produce one word per argument and is the only faithful way to forward arguments; $* silently corrupts anything containing a space.
  • Command lookup is alias → function → builtin → hash cache → PATH; type -a tells you what will actually run, and hash -r fixes stale cached paths.
  • Every pipeline stage runs in a subshell, so variables set inside cmd | while read die with the child — use < <(cmd) instead.
  • { ...; }, while ... < file, and source stay in the current shell; ( ... ) deliberately does not.
  • A pipeline reports only its last stage's status by default — set -o pipefail or ${PIPESTATUS[@]} surfaces earlier failures.
  • Exit status 127 means not found, 126 means found but not executable, and 128+N means killed by signal N (137 = SIGKILL, usually the OOM killer).
  • set -euo pipefail is a seatbelt, not error handling — -e is suppressed inside conditions, after ||, and by command substitution in assignments.
  • Ctrl-C is the kernel's terminal driver signalling the whole foreground process group, not bash killing a program — which is why it stops an entire pipeline.
  • Every unquoted expansion of untrusted input is an injection point; use arrays for command construction, validate with allowlists, and never eval.
