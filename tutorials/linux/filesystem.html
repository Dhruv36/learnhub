The Filesystem & Paths Foundations

What you'll master: why Linux has one tree instead of drive letters and what that buys you, what each top-level directory is genuinely for (and which ones are historical accidents nobody will admit to), how the kernel resolves a path one component at a time and why that algorithm explains symlink surprises, the difference between a path that exists and a path you can reach, where configuration and state are supposed to live under the FHS, and how mount points make the single tree a lie in the most useful possible way. Prerequisites: How Unix Is Put Together.

Part 1 — One Tree, No Drive Letters

Windows gives each storage device its own namespace root: C:\, D:\, \\server\share. Unix made the opposite choice. There is exactly one tree, rooted at /, and every storage device is grafted onto a directory somewhere inside it.

                        /
        ┌───────┬───────┼───────┬────────┬────────┐
       bin     etc     home    var     proc     mnt
                        │       │       │        │
                     ┌──┴──┐   log   (kernel)  data
                    alice  bob                   │
                                          [second disk grafted here]

The consequence is that a path never tells you which device holds the data. That sounds like lost information; it is actually the whole point. An application writing to /var/lib/app/data does not need rewriting when you move that directory to a bigger disk, a RAID array, or a network filesystem. You change the mount, not the code.

$ df -h /var/log /home /
Filesystem      Size  Used Avail Use% Mounted on
/dev/nvme0n1p3   50G   31G   17G  65% /
/dev/nvme0n1p4  100G   22G   73G  24% /home
tmpfs           7.8G  1.2M  7.8G   1% /var/log        # this one is RAM

Three different devices, one tree, and nothing in the paths hints at the boundary. df with a path argument is the tool that answers "which device is this actually on?" — a question worth asking before you assume a disk-full error names the disk you expect.

A mount hides whatever was underneath it, which is a genuine source of production confusion:

$ ls /mnt/data              # before mounting: files placed here earlier
placeholder.txt

$ sudo mount /dev/sdb1 /mnt/data
$ ls /mnt/data              # the old contents are not gone — just shadowed
lost+found  actual-data/

$ sudo umount /mnt/data
$ ls /mnt/data
placeholder.txt             # back again
🔑 The classic disk-full mystery. A service writes to /var/lib/app before its dedicated volume is mounted, filling the root filesystem. Then the mount happens at boot, hiding those files. du now reports the directory as nearly empty while df insists the root disk is full, and the space cannot be reclaimed because nothing can see the files. The fix is to bind-mount the root filesystem elsewhere and look underneath: mount --bind / /mnt/root, then inspect /mnt/root/var/lib/app. Storage & Filesystems covers this in full.

Part 2 — What the Directories Actually Mean

The Filesystem Hierarchy Standard defines these, and most of it is genuinely logical once you learn the organising question: is this data static or variable, and is it shareable across machines or specific to this one?

The /bin versus /usr/bin split is the historical accident. In 1970s Unix, the root disk filled up, so the developers moved some binaries onto the /usr disk. That emergency became forty years of doctrine about "essential" binaries. Modern distributions have quietly undone it:

$ ls -ld /bin /sbin /lib
lrwxrwxrwx 1 root root 7 Apr 18 09:12 /bin -> usr/bin
lrwxrwxrwx 1 root root 8 Apr 18 09:12 /sbin -> usr/sbin
lrwxrwxrwx 1 root root 7 Apr 18 09:12 /lib -> usr/lib

The three distinctions that do still matter operationally:

What must I back up?/etc, /home, /var/lib, /srvEverything else is reinstallable from packages
What fills the disk?/var/log, /var/lib/docker, /var/cacheGive /var its own volume in production
Where do my builds go?/usr/local or /optNever /usr/bin — package upgrades will fight you

Part 3 — How the Kernel Resolves a Path

Path resolution is not string manipulation. The kernel walks the path one component at a time, and understanding that loop explains almost every path-related surprise.

To resolve /home/alice/notes.txt:

1. Start at the root directory inode (or at cwd, if the path is relative)
2. Check execute (search) permission on it              → else EACCES
3. Look up "home" in it                                 → else ENOENT
4. Is the result a mount point? If so, switch to the mounted filesystem's root
5. Is the result a symlink? If so, resolve it and restart from the target
6. Repeat from step 2 with the next component ("alice", then "notes.txt")

Several important facts fall directly out of this loop:

You need execute permission on every directory in the path. Not read — execute. On a directory, the execute bit means "may traverse", and read means "may list". They are independent:

$ mkdir -p /tmp/vault/secret && echo hi > /tmp/vault/secret/file
$ chmod 711 /tmp/vault          # rwx for owner, --x for everyone else

$ ls /tmp/vault                 # as another user: cannot list
ls: cannot open directory '/tmp/vault': Permission denied

$ cat /tmp/vault/secret/file    # but CAN traverse, if you know the name
hi

This is a real access-control pattern — chmod 711 on a home directory lets a web server reach ~/public_html without being able to enumerate the user's files. It also means "they can't list it" is not the same as "they can't read it". Users, Groups & Permissions goes deeper.

Resolution is relative to cwd, which is per-process kernel state — not a shell variable:

$ ls -l /proc/self/cwd
lrwxrwxrwx 1 you you 0 Aug  7 11:02 /proc/self/cwd -> /home/alice

# A deleted cwd still "works" until you use a relative path
$ mkdir /tmp/gone && cd /tmp/gone && rmdir /tmp/gone
$ pwd
/tmp/gone
$ ls .
ls: cannot open directory '.': No such file or directory

Symlinks restart resolution, which is why they can loop. The kernel caps the chain at roughly 40 links and then gives up:

$ ln -s b /tmp/a && ln -s a /tmp/b
$ cat /tmp/a
cat: /tmp/a: Too many levels of symbolic links       # ELOOP
🔑 Why .. is not what you think. The shell often resolves .. textually before the kernel ever sees it, but the kernel resolves it against the real directory tree. With symlinks in play, these disagree — and that disagreement is a genuine source of scripts deleting the wrong directory. Compare cd /link/../x (bash's logical view) with cd -P (physical). Use realpath or readlink -f whenever a script must know where it truly is.

Part 4 — Absolute, Relative, and Canonical

Three different notions of "where", and confusing them causes real bugs.

KindExampleResolved againstStable?
Absolute/var/log/syslogThe root directoryYes, unless mounts change
Relative../log/syslogThe process's cwdNo — depends on who runs it
Canonical/var/log/syslog with all symlinks resolvedRoot, fully dereferencedYes — this is the true identity
$ cd /tmp && ln -sfn /var/log loglink
$ cd /tmp/loglink && pwd
/tmp/loglink                      # bash's logical cwd — keeps the symlink
$ pwd -P
/var/log                          # physical: the truth
$ realpath .
/var/log

The practical rule for scripts: a script must never assume the caller's cwd. Cron runs it from $HOME, systemd from /, a colleague from wherever they happened to be. Establish your own footing explicitly:

#!/usr/bin/env bash
set -euo pipefail

# Resolve the directory this script lives in, following symlinks
SCRIPT_DIR=$(cd -- "$(dirname -- "$(readlink -f -- "${BASH_SOURCE[0]}")")" && pwd)

# Now every path is anchored, regardless of who invoked us or from where
source "$SCRIPT_DIR/lib/common.sh"
config="$SCRIPT_DIR/../etc/app.conf"

That SCRIPT_DIR incantation is worth memorising; it appears in nearly every serious shell script. readlink -f handles the case where the script itself was invoked through a symlink in /usr/local/bin, which is extremely common.

❌ cd $(dirname $0) — breaks when the path contains spaces, when $0 is a symlink, and when the script is sourced rather than executed. It also silently leaves you in the wrong directory if the cd fails.

✅ cd -- "$(dirname -- "$(readlink -f -- "${BASH_SOURCE[0]}")")" — quoted against spaces, -- guards against filenames starting with a dash, readlink -f canonicalises symlinks, and BASH_SOURCE is correct when sourced. Combined with set -e, a failed cd aborts rather than continuing blindly.

Part 5 — Hidden Files, Globbing, and Who Expands What

A "hidden" file is nothing more than a filename beginning with a dot. There is no hidden attribute in the filesystem. The convention exists entirely because ls chooses to skip such names, and that choice was itself an accident: an early ls was written to skip . and .., and the implementation skipped anything starting with a dot.

The critical thing to internalise is that globbing is done by the shell, not by the program — and the shell's glob also skips dotfiles:

$ ls -a /tmp/demo
.  ..  .hidden  visible.txt

$ echo /tmp/demo/*
/tmp/demo/visible.txt             # .hidden not matched

$ echo /tmp/demo/.*
/tmp/demo/. /tmp/demo/.. /tmp/demo/.hidden      # and now . and .. are included!

That second result is a genuine footgun: rm -rf .* historically matched .. and walked up out of the directory. Modern GNU rm refuses . and .. explicitly, but the general lesson stands. Use dotglob or find instead:

$ shopt -s dotglob && echo /tmp/demo/*
/tmp/demo/.hidden /tmp/demo/visible.txt
$ shopt -u dotglob

# Or sidestep the whole question
$ find /tmp/demo -mindepth 1 -delete

Because the shell expands globs before the program runs, a program never sees the *. This explains a frequent confusion:

$ ls *.txt
# The program receives: ls report.txt notes.txt
# It never sees the asterisk at all

$ find . -name *.log            # BROKEN if any .log file is in the cwd
$ find . -name '*.log'          # correct — quoting sends the * to find

In the broken form, the shell expands *.log first, so find receives -name app.log error.log and errors out or silently searches for the wrong thing. Quoting is not stylistic here; it changes which program does the matching. find & xargs depends on this distinction throughout.

Glob patterns worth knowing beyond *:

PatternMatchesNote
*Any string, including empty; never /Does not cross directory boundaries
?Exactly one character
[abc], [a-z]One character from a set or rangeRanges are locale-dependent — use [[:lower:]]
{a,b}Brace expansion — not a glob at allExpands even if nothing matches
**Recursive, with shopt -s globstarOff by default in bash

Brace expansion catches people out because it happens earlier and does not check the filesystem:

$ echo file{1,2,3}.txt
file1.txt file2.txt file3.txt        # produced whether or not they exist

$ echo nonexistent*.txt
nonexistent*.txt                     # glob with no match: bash passes it through literally

That last behaviour — an unmatched glob being passed through as a literal string — causes scripts to operate on a file literally named nonexistent*.txt. shopt -s nullglob makes it expand to nothing instead, and failglob makes it an error.

Part 6 — Mount Points and the Tree as a Composition

The single tree is assembled at boot from many sources, and reading that assembly is a core operational skill.

$ findmnt -t ext4,xfs,tmpfs -o TARGET,SOURCE,FSTYPE,OPTIONS
TARGET       SOURCE           FSTYPE OPTIONS
/            /dev/nvme0n1p3   ext4   rw,relatime
├─/boot      /dev/nvme0n1p1   ext4   rw,relatime
├─/home      /dev/nvme0n1p4   ext4   rw,relatime,nodev,nosuid
├─/tmp       tmpfs            tmpfs  rw,nosuid,nodev,noexec,size=8G
└─/var/log   /dev/nvme0n1p5   ext4   rw,relatime,nodev,nosuid,noexec

The OPTIONS column is a security control surface that is easy to overlook:

OptionEffectWhy you would set it
noexecNo binary on this filesystem may be executedOn /tmp and upload directories — blocks a common exploit step
nosuidsetuid/setgid bits are ignoredAnywhere untrusted users can write files
nodevDevice nodes here are not honouredPrevents a crafted /dev/sda bypassing permissions
roRead-onlyImmutable infrastructure; forces config into a mounted volume
relatimeOnly update access time occasionallyDefault; noatime saves more writes on busy filesystems

A bind mount makes the same data appear at two places in the tree, without copying:

$ sudo mkdir -p /srv/www/shared
$ sudo mount --bind /var/data/assets /srv/www/shared
$ findmnt /srv/www/shared
TARGET            SOURCE                       FSTYPE OPTIONS
/srv/www/shared   /dev/nvme0n1p3[/var/data/assets] ext4 rw,relatime

This is the mechanism behind Docker's -v volumes and behind systemd's directory sandboxing — the same kernel feature, exposed with friendlier names. Namespaces & cgroups shows how a container gets an entirely different root via pivot_root, which is the logical extreme of everything in this lesson: the tree is not a fact about the machine, it is a per-process view.

Interview Questions

Beginner: Why does Linux use one directory tree instead of drive letters?

Because it decouples the logical location of data from the physical device holding it. Every device is mounted onto a directory inside the single tree rooted at /.

The practical benefit is that applications never encode storage decisions. A service writing to /var/lib/app keeps working when that directory is moved to a larger disk, an SSD, or a network filesystem — you change the mount, not the application. With drive letters, the path itself names the device, so moving data means editing configuration everywhere it is referenced.

The trade-off is that you cannot tell from a path which device it lives on, so you need df -h /path or findmnt -T /path to answer that. It also creates the shadowing problem: files written to a directory before its volume is mounted become invisible and unreclaimable once it is.

Beginner: What is the difference between /etc, /var, and /usr?

The FHS organises them by two questions: does the content change during normal operation, and is it specific to this host?

  • /usr — static and shareable. Installed software and its data. It can be mounted read-only, and in principle shared across identical machines. Owned by the package manager.
  • /etc — static but host-specific. Configuration for this machine. Small, text-based, and the single most important thing to back up and version-control.
  • /var — variable. Logs, caches, spools, databases, container images. It grows without bound, which is why giving it a separate volume in production stops a runaway log from taking down the root filesystem.

The practical takeaway: to rebuild a machine you need /etc, /home, and /var/lib. Everything under /usr comes back from packages.

Mid: Walk through exactly how the kernel resolves /home/alice/notes.txt.

Component by component, not as a string:

  1. The path starts with /, so begin at the root inode. (A relative path would begin at the process's cwd, which is kernel state visible at /proc/PID/cwd.)
  2. Check execute permission on the current directory — execute means "may traverse". Without it, EACCES, regardless of permissions further down.
  3. Look up the name home in that directory's entries. Not found → ENOENT.
  4. If the result is a mount point, switch to the mounted filesystem's root inode.
  5. If the result is a symlink, resolve the target and restart resolution from there — capped near 40 links, then ELOOP.
  6. Repeat for alice, then notes.txt.

Three consequences follow directly. You need execute on every directory in the path, which makes chmod 711 a real pattern — traversable but not listable. The mount check at each step is why a path cannot tell you its device. And because symlinks restart the walk against the real tree, .. after a symlink does not go where textual manipulation suggests, which is why scripts should use realpath rather than string surgery.

Mid: Why does find . -name *.log sometimes work and sometimes fail bizarrely?

Because the shell expands globs before find ever runs, so the behaviour depends entirely on what is in the current directory.

If no .log file is in the cwd, bash finds no match and (by default) passes the literal string *.log through — find receives the pattern and works correctly. This is the "sometimes works" case, and it is working by accident.

If exactly one matches, say app.log, find receives -name app.log and silently searches for only that name — wrong results, no error.

If two or more match, find receives -name app.log error.log and fails with "paths must precede expression".

The fix is to quote: find . -name '*.log' sends the asterisk to find, which does its own matching against every file it walks. The general principle is knowing which program performs an expansion — the same question explains why grep 'a b' needs quotes and why echo * prints filenames rather than an asterisk.

Senior: df says the root filesystem is 100% full but du -sh / accounts for far less. Diagnose it.

Three causes account for nearly every instance, and they are distinguishable.

1. Deleted files still held open. The most common by far. Unlinking a file removes the directory entry, but the inode and its blocks survive while any process holds it open — typically a log rotated without signalling the writer. du walks directory entries and cannot see it; df asks the filesystem and does.

$ lsof +L1 2>/dev/null | head -3
COMMAND  PID USER   FD   TYPE DEVICE   SIZE/OFF NLINK NODE NAME
nginx   2210 www    5w   REG  259,3  8421990400     0  512 /var/log/nginx/access.log (deleted)

NLINK 0 is the signature. The fix is to signal the process to reopen its logs (kill -USR1 for nginx) or restart it — never kill -9, which loses buffered data. Truncating via : > /proc/PID/fd/5 reclaims space immediately if a restart is unacceptable.

2. Files hidden under a mount point. Data was written before a volume was mounted over that directory. Nothing can see it while the mount is active:

$ sudo mount --bind / /mnt/root
$ du -sh /mnt/root/var/lib/app        # now visible underneath
14G     /mnt/root/var/lib/app
$ sudo umount /mnt/root

3. Inode exhaustion rather than block exhaustion. Millions of tiny files can exhaust inodes while blocks remain free; the error is still ENOSPC, which misleads:

$ df -i /
Filesystem       Inodes  IUsed IFree IUse% Mounted on
/dev/nvme0n1p3  3276800 3276800     0  100% /

Also worth checking: reserved blocks. ext4 reserves 5% for root by default, so a filesystem can be "full" for ordinary users with gigabytes remaining — tune2fs -m 1 reclaims most of it on a large data volume where the reservation serves no purpose.

My order of operations is df -i first (instant, rules out inodes), then lsof +L1 (usually the answer), then the bind-mount check.

Senior: How would you use mount options to harden a server that accepts file uploads?

The goal is to make the uploaded bytes unable to become executing code, using filesystem-level controls that hold even if the application is compromised.

Separate the volume. Uploads go to a dedicated filesystem, not a directory on root. That gives you independent mount options and a hard capacity boundary so filling it cannot take down the system.

Mount it noexec,nosuid,nodev. noexec means the kernel refuses to execute anything there, defeating the classic "upload a shell, then run it" chain. nosuid ensures a setuid binary written there gains no privilege. nodev prevents a crafted device node from being used to read raw disk and bypass file permissions entirely.

/dev/sdb1  /srv/uploads  ext4  rw,noexec,nosuid,nodev,relatime  0 2

Apply the same to /tmp and /dev/shm, since an attacker blocked from /srv/uploads will simply write there instead. A partial hardening that leaves an obvious alternative is not hardening.

Know the honest limits. noexec stops ./payload; it does not stop bash /srv/uploads/payload.sh or python payload.py, because the interpreter is executing, not the file. It is a meaningful layer, not a boundary. Real defence also needs the application to validate content types, store files with non-executable names outside any web root, and run as a user with no write access anywhere else — plus systemd sandboxing (ProtectSystem=strict, ReadWritePaths=), covered in Hardening.

Verify rather than assume, since a mount option in fstab that was never applied is worse than none — it produces false confidence:

$ findmnt -o TARGET,OPTIONS /srv/uploads
$ cp /bin/true /srv/uploads/t && /srv/uploads/t
bash: /srv/uploads/t: Permission denied      # confirmed

🏋️ Exercises

1 (easy): Determine which physical device holds four different paths, and identify which are not on disk at all.
Solution 
$ for p in / /tmp /proc/cpuinfo /var/log; do
>   printf '%-16s ' "$p"; findmnt -n -o SOURCE,FSTYPE -T "$p"
> done
/                /dev/nvme0n1p3 ext4
/tmp             tmpfs          tmpfs
/proc/cpuinfo    proc           proc
/var/log         /dev/nvme0n1p3 ext4

-T is the key flag: it takes a path and reports the filesystem containing it, rather than requiring an exact mount point. Note that /var/log here is not a separate volume — it is part of root, so a log flood will fill the root filesystem and can prevent the machine from booting. That is a finding worth acting on.

Two of the four are not on disk: tmpfs lives in RAM (and swap), and proc is generated by the kernel on read. Confirm the RAM claim:

$ df -h /tmp | tail -1
tmpfs           7.8G  1.2M  7.8G   1% /tmp
$ free -h | head -2
               total        used        free
Mem:            15Gi       4.2Gi       412Mi

Writing 8 GB to /tmp on this machine would consume all memory — a real incident pattern when a job assumes /tmp is disk-backed.

2 (easy): Demonstrate that directory execute and read permissions are independent.
Solution 
$ sudo mkdir -p /tmp/lab/inner
$ echo secret > /tmp/lab/inner/data.txt
$ sudo chmod 711 /tmp/lab          # rwx owner, --x others
$ sudo chmod 755 /tmp/lab/inner
$ sudo chmod 644 /tmp/lab/inner/data.txt
$ sudo chown -R root:root /tmp/lab

# As a normal user:
$ ls /tmp/lab
ls: cannot open directory '/tmp/lab': Permission denied     # no read = no listing

$ cat /tmp/lab/inner/data.txt
secret                                                       # but --x allows traversal

The directory is traversable but not enumerable. You can reach anything inside it if you already know the name, but you cannot discover names.

Now remove execute and observe the opposite failure:

$ sudo chmod 644 /tmp/lab          # rw-, no execute for anyone
$ ls /tmp/lab
ls: cannot access '/tmp/lab/inner': Permission denied
inner                                # the NAME is listed (read works)...
$ cat /tmp/lab/inner/data.txt
cat: /tmp/lab/inner/data.txt: Permission denied     # ...but traversal fails

Read gives you names; execute gives you the ability to go through. This is why "chmod 755 the whole path" is the standard fix when a web server reports 403 on a file whose own permissions look fine — the failure is on a parent directory. namei -l /tmp/lab/inner/data.txt shows the permission of every component at once and is the fastest diagnostic.

3 (medium): Show three ways an unquoted glob changes a command's meaning, and state which program does the matching in each case.
Solution 
$ mkdir -p /tmp/g && cd /tmp/g && touch app.log error.log notes.txt

Case 1 — multiple matches, hard failure:

$ find . -name *.log
find: paths must precede expression: `error.log'

The shell expanded to find . -name app.log error.log. Find never saw a pattern.

Case 2 — single match, silent wrong answer (the dangerous one):

$ rm error.log
$ find . -name *.log
./app.log                          # looks right...
$ touch sub/deep.log 2>/dev/null || (mkdir sub && touch sub/deep.log)
$ find . -name *.log
./app.log                          # deep.log missing! Shell matched only cwd
$ find . -name '*.log'
./app.log
./sub/deep.log                     # correct: find matched at every level

This is the case that gets into production: no error, plausible output, incomplete results.

Case 3 — no match, accidental success:

$ cd /tmp && find /tmp/g -name *.log
/tmp/g/app.log
/tmp/g/sub/deep.log                # works — because cwd had no .log to expand

Identical command, correct result, purely because of the current directory. Code that works by accident is the hardest kind to debug later.

Who matches what: unquoted, bash matches against the cwd only and passes filenames. Quoted, find matches against each basename it encounters during the walk. Same syntax, different engine, different scope. The rule: quote any pattern intended for a program that does its own matching — find -name, grep, rsync --exclude.

4 (medium): Write a script that works correctly no matter which directory it is invoked from or whether it is reached through a symlink.
Solution 
$ mkdir -p /tmp/proj/{bin,etc,lib}
$ cat > /tmp/proj/bin/run.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail

SCRIPT_DIR=$(cd -- "$(dirname -- "$(readlink -f -- "${BASH_SOURCE[0]}")")" && pwd)
PROJ_ROOT=$(cd -- "$SCRIPT_DIR/.." && pwd)

echo "invoked from : $PWD"
echo "script dir   : $SCRIPT_DIR"
echo "project root : $PROJ_ROOT"
echo "config       : $PROJ_ROOT/etc/app.conf"
EOF
$ chmod +x /tmp/proj/bin/run.sh
$ echo 'key=value' > /tmp/proj/etc/app.conf

Test from an unrelated directory, and through a symlink on PATH:

$ cd / && /tmp/proj/bin/run.sh
invoked from : /
script dir   : /tmp/proj/bin
project root : /tmp/proj
config       : /tmp/proj/etc/app.conf

$ sudo ln -sf /tmp/proj/bin/run.sh /usr/local/bin/myapp
$ cd /home && myapp
invoked from : /home
script dir   : /tmp/proj/bin            # readlink -f followed the symlink
project root : /tmp/proj
config       : /tmp/proj/etc/app.conf

Without readlink -f, the symlinked invocation would report /usr/local/bin as the script dir and look for config in /usr/local/etc — the classic "works when I run it directly, breaks when installed" bug.

Each piece earns its place: readlink -f canonicalises symlinks; BASH_SOURCE[0] is correct even when sourced (unlike $0); -- protects against paths starting with a dash; the quotes handle spaces; and set -e means a failed cd aborts instead of silently continuing in the wrong directory.

5 (hard): Reproduce the "files hidden under a mount point" incident end to end, then recover the space.
Solution

Build it with a loop device so no real disk is needed:

$ sudo mkdir -p /mnt/appdata
$ sudo dd if=/dev/zero of=/tmp/disk.img bs=1M count=100 2>/dev/null
$ sudo mkfs.ext4 -q /tmp/disk.img

# Simulate the mistake: the service writes BEFORE the volume is mounted
$ sudo dd if=/dev/zero of=/mnt/appdata/orphan.bin bs=1M count=60 2>/dev/null
$ du -sh /mnt/appdata
60M     /mnt/appdata

# Now the volume mounts at boot, on top of the existing data
$ sudo mount -o loop /tmp/disk.img /mnt/appdata
$ du -sh /mnt/appdata
20K     /mnt/appdata            # the 60M has vanished from view
$ ls /mnt/appdata
lost+found                      # orphan.bin is unreachable

The symptom in production: df reports the root filesystem consuming 60 MB more than anything under it accounts for, and no amount of searching finds the files — because path resolution stops at the mount point and switches filesystems, so nothing can traverse underneath.

Recovery — bind-mount the parent filesystem elsewhere. A bind mount of / exposes the underlying tree without the child mounts layered on it:

$ sudo mkdir -p /mnt/rootview
$ sudo mount --bind / /mnt/rootview
$ du -sh /mnt/rootview/mnt/appdata
60M     /mnt/rootview/mnt/appdata          # there it is
$ ls -la /mnt/rootview/mnt/appdata
-rw-r--r-- 1 root root 62914560 Aug  7 11:40 orphan.bin

$ sudo rm /mnt/rootview/mnt/appdata/orphan.bin
$ sudo umount /mnt/rootview && sudo rmdir /mnt/rootview

Prevention. Make the service refuse to start when its volume is absent, rather than silently writing to the mount point. In systemd this is declarative:

[Unit]
RequiresMountsFor=/mnt/appdata

[Service]
ExecStartPre=/usr/bin/mountpoint -q /mnt/appdata

mountpoint -q exits non-zero if the path is not a mount, so ExecStartPre aborts the start. RequiresMountsFor= additionally orders the unit after the mount. systemd covers both.

Cleanup: sudo umount /mnt/appdata && sudo rm /tmp/disk.img.

6 (hard): Design the partition and mount-option layout for a production web server, justifying each decision by the failure it prevents.
Solution

Every separation should be defensible by naming a specific incident it stops. Separating everything is as wrong as separating nothing — it creates volumes that fill independently while space sits idle next door.

# /etc/fstab
/dev/nvme0n1p1  /boot        ext4  ro,nodev,nosuid,noexec                  0 2
/dev/nvme0n1p2  /            ext4  rw,relatime                             0 1
/dev/nvme0n1p3  /var         ext4  rw,relatime,nodev,nosuid                0 2
/dev/nvme0n1p4  /var/log     ext4  rw,relatime,nodev,nosuid,noexec         0 2
/dev/nvme0n1p5  /srv/uploads ext4  rw,relatime,nodev,nosuid,noexec         0 2
/dev/nvme0n1p6  /home        ext4  rw,relatime,nodev,nosuid                0 2
tmpfs           /tmp         tmpfs rw,nodev,nosuid,noexec,size=2G,mode=1777 0 0
DecisionFailure it prevents
/var/log separateA logging loop or debug-level flag fills a bounded volume instead of the root filesystem — the single most common cause of "the server won't boot"
/var separate from /Container images, package caches and spools grow unbounded; root stays writable so you can still log in and fix it
/srv/uploads separate + noexecUntrusted bytes cannot become an executable, and a flood of uploads cannot exhaust system space
/tmp as sized tmpfsCleared on reboot by construction; the size= cap stops a runaway job from consuming all RAM — the failure mode of an unbounded tmpfs
/boot read-onlyAccidental or malicious kernel/bootloader modification; remount rw deliberately for upgrades
nodev everywhere but /A crafted device node on a writable volume reading raw disk and bypassing file permissions entirely
mode=1777 on /tmpThe sticky bit — world-writable, but users can only delete their own files

What I deliberately did not do. No separate /usr: it complicates upgrades and initramfs for no modern benefit. No separate /opt or /srv beyond uploads: unnecessary volumes fragment free space. And I would use LVM or thin-provisioned volumes in practice, because the real risk of this layout is guessing sizes wrong at install time and being unable to grow /var when it fills — the option that preserves the ability to change your mind is worth more than a perfect initial guess.

Verify after provisioning, since an fstab entry that failed to apply gives false confidence:

$ findmnt -o TARGET,SOURCE,OPTIONS
$ cp /bin/true /srv/uploads/x && /srv/uploads/x
bash: /srv/uploads/x: Permission denied     # noexec confirmed live

🎯 Key Takeaways

  • Linux has one tree; devices are grafted onto directories, so a path never reveals which device holds the data — ask findmnt -T or df.
  • Mounting over a non-empty directory hides its contents and makes that space unreclaimable until you bind-mount the parent and look underneath.
  • The FHS organises by two questions: static or variable, host-specific or shareable. To rebuild a machine you need /etc, /home, and /var/lib.
  • Path resolution is component-by-component, checking execute permission and testing for mount points and symlinks at every step.
  • Directory execute means "may traverse", read means "may list" — they are independent, which makes chmod 711 a real access-control pattern.
  • Symlinks restart resolution against the real tree, so .. after a symlink does not match textual expectations; use realpath or pwd -P.
  • Globbing is done by the shell before the program runs — find -name '*.log' must be quoted or find never sees a pattern.
  • An unmatched glob is passed through literally by default; nullglob or an existence test prevents operating on a file named *.txt.
  • Scripts must never assume the caller's cwd — anchor with readlink -f "${BASH_SOURCE[0]}", not $0.
  • Mount options are a real security surface: noexec,nosuid,nodev on untrusted volumes stops several standard exploitation steps, though noexec does not stop interpreters.
  • Bind mounts make the same data appear at two paths without copying — the mechanism behind container volumes and systemd sandboxing.
  • Separate a volume only when you can name the failure it prevents; the usual justified ones are /var/log, /var, and untrusted upload directories.
