systemd & Service Management The Running System

What you'll master: what PID 1 is actually responsible for and why systemd replaced shell init scripts, how to write a unit file that restarts correctly instead of crash-looping, the difference between Type=simple, forking and notify that determines whether dependencies start too early, why After= and Requires= are unrelated directives that everyone conflates, the sandboxing options that harden a service in one line each, and timers as a strictly better cron. Prerequisites: Processes, fork & exec and Signals & Job Control.

Part 1 — PID 1 and What It Owes the System

The kernel starts exactly one process directly: PID 1. Everything else descends from it by fork and exec. PID 1 has two obligations that nothing else can fulfil.

$ ps -p 1 -o pid,comm,args
  PID COMMAND  COMMAND
    1 systemd  /sbin/init splash

$ pstree -p 1 | head -5
systemd(1)─┬─NetworkManager(842)─┬─{NetworkManager}(861)
           ├─sshd(901)───sshd(64100)───bash(64102)
           ├─nginx(1204)─┬─nginx(1205)
ObligationWhat happens if it fails
Reap orphans — wait() on adopted childrenZombie processes accumulate until the PID table is exhausted
Start and supervise servicesNothing else boots
Default signal handling is specialPID 1 ignores signals it has no handler for — the kernel refuses to kill it, since that would panic
🔑 This is why docker run myapp can leak zombies. Your application becomes PID 1 inside the container and almost certainly never calls wait(). Any process it spawns that outlives its parent gets reparented to it and stays a zombie forever. It is also why Ctrl-C often does nothing in a container: PID 1 ignores SIGINT unless the program installs a handler. docker run --init inserts a minimal reaper for exactly these two reasons.

systemd replaced SysV init because shell scripts could not express the things a supervisor actually needs: parallel startup with real dependencies, restart-on-failure, per-service resource limits and sandboxing, structured logging, and socket activation.

Unit typeManagesExample
.serviceA processnginx.service
.socketA listening socket, started on demanddocker.socket
.timerScheduled activationfstrim.timer
.mountA mountpoint (generated from fstab)var-log.mount
.targetA grouping/synchronisation pointmulti-user.target
.sliceA cgroup for resource controlsystem.slice

Part 2 — A Unit File, Line by Line

Custom units live in /etc/systemd/system/. Packages install to /lib/systemd/system/, and anything in /etc overrides it — which is the rule that decides where your file belongs.

# /etc/systemd/system/myapp.service
[Unit]
Description=My Application API
Documentation=https://internal.example.com/runbook/myapp
After=network-online.target postgresql.service
Wants=network-online.target
Requires=postgresql.service

[Service]
Type=notify
User=myapp
Group=myapp
WorkingDirectory=/opt/myapp
Environment="NODE_ENV=production"
EnvironmentFile=-/etc/myapp/env          # leading '-' = ignore if missing
ExecStart=/opt/myapp/bin/server
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5s
TimeoutStopSec=30s
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target

$ sudo systemctl daemon-reload            # REQUIRED after any unit file change
$ sudo systemctl enable --now myapp
$ systemctl status myapp

The three sections divide cleanly: [Unit] is metadata and ordering, [Service] is how to run the process, [Install] is what enable should do — and a unit with no [Install] section cannot be enabled at all, which is a common first surprise.

DirectiveEffectNote
ExecStart=The command to runAbsolute path required; no shell, so no pipes or globs
Restart=no, on-failure, always, on-abnormalon-failure is the right default
RestartSec=Delay before restartingWithout it, a crash loop burns CPU
TimeoutStopSec=Grace period before SIGKILLMust exceed your longest in-flight request
User=/Group=Drop privilegesNever run a service as root without a reason
EnvironmentFile=Load KEY=VALUE from a filePrefix - to tolerate absence

Never edit a packaged unit in place — the next package update overwrites it. Use a drop-in, which layers on top and survives upgrades:

$ sudo systemctl edit nginx              # creates /etc/systemd/system/nginx.service.d/override.conf
[Service]
LimitNOFILE=65535
Restart=on-failure

$ systemctl cat nginx                    # shows the base unit plus every drop-in, in order
$ systemd-delta                          # lists everything overridden system-wide

Part 3 — Type= Decides When "Started" Means Started

Type= tells systemd how to know the service is up. Getting it wrong does not usually break the service — it breaks everything ordered after it, which is a far more confusing failure.

TypeConsidered started whenUse for
simple (default)Immediately after fork/execForeground processes — but dependents may start too early
execAfter execve succeedsBetter default than simple; catches a bad binary path
forkingThe parent exitsClassic daemons; needs PIDFile=
notifyThe process calls sd_notify(READY=1)Best — the service says when it is genuinely ready
oneshotThe process exitsSetup tasks; pair with RemainAfterExit=yes
idleLike simple, but delayed until other jobs finishCosmetic — keeps boot output tidy
# Type=notify — the service reports readiness itself
[Service]
Type=notify
NotifyAccess=main
ExecStart=/opt/myapp/server

# in the application, after listeners are bound and migrations are done:
import systemd.daemon
systemd.daemon.notify('READY=1')
systemd.daemon.notify('STATUS=Serving on :8080')     # shows in systemctl status

❌ Using Type=simple and adding After=myapp.service to whatever depends on it. With simple, systemd marks the service started the instant it forks — before the port is bound, before migrations run. The dependent service starts against a socket that is not listening yet and fails on the first connection, intermittently, usually only under the timing of a real boot.

✅ Use Type=notify and send READY=1 once the service can actually serve. If the code cannot be changed, Type=exec at least confirms the binary executed, and a socket unit removes the race entirely — systemd holds the listening socket, so clients connect and block instead of failing.

Part 4 — Ordering Is Not Dependency

This is the single most misunderstood part of systemd. After= controls order. Requires= controls whether. They are independent, and using one when you meant both produces races that only appear at boot.

DirectiveMeansIf the other unit fails
After=bStart me after b — only if b is starting at allNothing; I still start
Requires=bStart b too; if b fails, stop meI am stopped
Wants=bStart b too, but tolerate its failureI continue
BindsTo=bLike Requires, plus stop me if b stops laterI am stopped, even mid-run
Conflicts=bStop b when I start—
# WRONG — declares a requirement with no ordering
[Unit]
Requires=postgresql.service     # postgres will start... possibly at the same time as me

# RIGHT — both directives, they do different jobs
[Unit]
Requires=postgresql.service     # pull it in, fail with it
After=postgresql.service        # and wait for it

network-online.target is the classic trap. network.target means only "the networking stack is being configured", not that an address exists. A service that binds to a specific IP needs the online target, and that target only does anything if a waiting service is enabled:

[Unit]
Wants=network-online.target
After=network-online.target

$ systemctl is-enabled systemd-networkd-wait-online.service     # or NetworkManager-wait-online
enabled

Inspect what systemd actually computed rather than trusting the file:

$ systemctl list-dependencies myapp --all
$ systemctl list-dependencies --before myapp
$ systemd-analyze verify /etc/systemd/system/myapp.service      # catches typos before you apply
$ systemd-analyze critical-chain myapp.service
myapp.service +2.481s
└─postgresql.service @4.212s +1.903s
  └─network-online.target @4.198s

Part 5 — Logs, Restarts, and Failure Handling

Anything a service writes to stdout or stderr goes to the journal automatically, tagged with the unit, PID, UID and boot ID. That removes the entire category of "the daemon writes its own log file and rotates it badly".

$ journalctl -u myapp -f                       # follow
$ journalctl -u myapp --since '10 min ago' -p err
$ journalctl -u myapp -b -1                    # previous boot
$ journalctl -u myapp -o json-pretty | head -20
$ journalctl -u myapp --grep 'timeout' -n 50
$ journalctl -u myapp -o cat                   # message text only
FlagPurpose
-u UNITOne unit
-f / -n NFollow / last N lines
-b / -b -1This boot / previous boot
-p errPriority: emerg, alert, crit, err, warning, notice, info, debug
--since/--untilTime window; accepts "2 hours ago", "09:00"
-kKernel messages (equivalent to dmesg)
--disk-usage / --vacuum-size=1GInspect and trim the journal

Restart policy is where a well-meant setting causes an outage. Restart=always with no rate limit produces a crash loop that burns CPU and fills the journal:

[Service]
Restart=on-failure
RestartSec=5s
StartLimitIntervalSec=300      # over a 5-minute window...
StartLimitBurst=5              # ...allow 5 starts, then give up and stay failed

$ systemctl status myapp
   Active: failed (Result: start-limit-hit)
$ sudo systemctl reset-failed myapp        # clears the counter so it can start again

Reaching the start limit is a feature: a service that has failed five times in five minutes will not fix itself on the sixth, and a permanently failed unit is a clear alert, whereas an endless loop is noise.

Graceful shutdown depends on the application honouring SIGTERM — see Signals & Job Control. systemd sends SIGTERM, waits TimeoutStopSec, then SIGKILL:

[Service]
KillSignal=SIGTERM
TimeoutStopSec=45s             # longer than the longest in-flight request
KillMode=mixed                 # SIGTERM to the main process, SIGKILL to leftovers

Part 6 — Hardening, Resource Limits, and Timers

Each sandboxing directive is one line and removes a whole class of compromise. They are the cheapest security available on a Linux host, and they are built on the same namespaces and cgroups that containers use.

[Service]
# Filesystem
ProtectSystem=strict           # entire filesystem read-only...
ReadWritePaths=/var/lib/myapp  # ...except this
ProtectHome=yes                # /home, /root, /run/user inaccessible
PrivateTmp=yes                 # private /tmp — no symlink attacks, auto-cleaned

# Privilege
NoNewPrivileges=yes            # setuid binaries cannot escalate
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
PrivateDevices=yes             # no raw device access

# Kernel
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictSUIDSGID=yes
SystemCallFilter=@system-service
SystemCallArchitectures=native

# Resource limits (cgroup v2)
MemoryMax=2G
MemoryHigh=1.5G
CPUQuota=200%                  # 2 cores' worth
TasksMax=512
IOWeight=50

$ systemd-analyze security myapp.service
  NoNewPrivileges=                 ✓
  PrivateTmp=                      ✓
  ProtectSystem=strict             ✓
  RestrictAddressFamilies=         ✗ 0.3  (no restrictions)
→ Overall exposure level: 2.8 OK 🙂

That command grades a unit out of 10 and lists exactly which directive would improve it — the fastest hardening feedback loop available.

Timers replace cron, and the reasons are concrete rather than stylistic:

# /etc/systemd/system/backup.timer
[Unit]
Description=Nightly backup

[Timer]
OnCalendar=daily
RandomizedDelaySec=30m         # spread load across a fleet
Persistent=true                # run on boot if the machine was off at the scheduled time
AccuracySec=1m

[Install]
WantedBy=timers.target

Missed run while powered offSkippedPersistent=true catches up
Overlapping runsPossible — a slow job stacks upPrevented; a unit runs once at a time

Dry run / next fire timeManual reasoningsystemd-analyze calendar, systemctl list-timers

Interview Questions

Beginner: What is PID 1 and why does it matter?

PID 1 is the first userspace process the kernel starts; every other process descends from it via fork. On most modern distributions it is systemd.

It has two responsibilities nothing else can take over. First, reaping orphans: when a parent dies before its child, the child is reparented to PID 1, which must call wait() to collect the exit status. Without that, entries accumulate as zombies until the PID table is exhausted. Second, starting and supervising services — the entire boot.

PID 1 is also special to the kernel: it ignores signals for which it has no handler, and it cannot be killed, because that would panic the system.

Both facts explain container behaviour. In docker run myapp your application is PID 1. It probably never calls wait(), so any subprocess it spawns can become a permanent zombie; and it ignores SIGTERM/SIGINT unless it explicitly installs a handler, which is why Ctrl-C sometimes does nothing and docker stop takes the full ten seconds before SIGKILL. docker run --init inserts a tiny reaper as PID 1 to fix both.

Beginner: Walk through the sections of a unit file.

Three sections, each answering a different question:

[Unit]                       # metadata and relationships
Description=My API
After=network-online.target postgresql.service
Requires=postgresql.service

[Service]                    # how to run the process
Type=notify
User=myapp
ExecStart=/opt/myapp/bin/server
Restart=on-failure
RestartSec=5s

[Install]                    # what `systemctl enable` should do
WantedBy=multi-user.target

[Unit] is ordering and dependencies. [Service] is execution: the command, the user, the environment, restart behaviour, resource limits. [Install] is only consulted by enable/disable — WantedBy=multi-user.target creates the symlink that makes the service start at boot. A unit with no [Install] section cannot be enabled, only started manually, which surprises people the first time.

Two operational rules go with it. Custom units belong in /etc/systemd/system/, which overrides the packaged copies in /lib/systemd/system/ — editing the packaged file directly means losing the change on the next update, so systemctl edit and a drop-in is the correct mechanism. And systemctl daemon-reload is mandatory after any change, or systemd keeps using the cached version and your edit appears to have no effect.

Mid: What is the difference between After=, Requires=, and Wants=?

They answer two entirely separate questions, and conflating them is the most common systemd bug.

After= is ordering only. "If b is also being started, start me after it finishes starting." It does not cause b to start, and if b fails, I still start.

Requires= is dependency only. "Pull b in, and if b fails or is stopped, stop me." It says nothing about order — without After=, both can start simultaneously.

Wants= is a weak dependency. "Try to start b, but carry on if it fails."

So the correct form for a service that needs a database is both directives:

[Unit]
Requires=postgresql.service    # pull it in and fail with it
After=postgresql.service       # and wait for it to be up

Requires= alone is a race that usually passes on a warm restart and fails at boot, which is the worst possible failure signature.

BindsTo= is the stronger form: like Requires, but it also stops my unit if b stops later, not just during startup — appropriate for a service tied to a device or a mount.

One caveat worth adding: even correct ordering only guarantees systemd's notion of "started", which depends on Type=. With Type=simple, postgres counts as started the instant it forks — so After= is satisfied before it accepts connections. The genuinely robust combination is Requires= + After= + Type=notify on the dependency, plus retry logic in the client.

Mid: A service crash-loops. Walk through diagnosing it.

I would work from systemd's own record before touching the application, because the exit reason usually names the cause.

1. Read the status — the exit code and result are the first clue:

$ systemctl status myapp
   Active: activating (auto-restart) (Result: exit-code)
  Process: 65100 ExecStart=/opt/myapp/bin/server (code=exited, status=203/EXEC)

systemd's exit codes are specific: 203/EXEC means the binary could not be executed — wrong path or not executable; 200/CHDIR is a bad WorkingDirectory; 217/USER means the User= does not exist; signal=KILL with Result: oom-kill is the OOM killer.

2. Read the journal for this unit, including previous attempts:

$ journalctl -u myapp -n 100 --no-pager
$ journalctl -u myapp --since '10 min ago' -p err

3. Stop the loop first. Restarting continuously makes everything harder to read and burns CPU:

$ sudo systemctl stop myapp

4. Run the exact command manually as the service user — this catches the majority of cases, because the service environment differs from a login shell in specific ways:

$ sudo -u myapp /opt/myapp/bin/server

The usual findings: a PATH that is minimal under systemd, environment variables set in .bashrc that never load for a service, a relative path that worked from the developer's directory, or file permissions that the service user does not have.

5. Check the sandboxing directives, which cause failures that look like application bugs. ProtectSystem=strict without a matching ReadWritePaths= produces "permission denied" on a path that is world-writable in ls:

$ systemctl cat myapp | grep -E 'Protect|Private|ReadWrite|Capability'
$ sudo systemd-run --uid=myapp -p ProtectSystem=strict -t /opt/myapp/bin/server   # reproduce

6. Fix the restart configuration regardless of the cause. A crash loop should stop itself:

[Service]
Restart=on-failure
RestartSec=5s
StartLimitIntervalSec=300
StartLimitBurst=5

Hitting the start limit leaves the unit cleanly failed, which alerts and stops the CPU burn. systemctl reset-failed clears it once fixed. I would treat Restart=always with no delay as a bug in its own right — it converts a visible failure into an expensive invisible one.

Senior: Design a production-grade unit file for a critical web service.

I would aim for four properties: correct readiness signalling, safe restart behaviour, least privilege, and bounded resource use.

[Unit]
Description=Payments API
Documentation=https://internal/runbook/payments
Requires=postgresql.service
After=postgresql.service network-online.target
Wants=network-online.target
StartLimitIntervalSec=300
StartLimitBurst=5

[Service]
Type=notify                      # the app sends READY=1 when it can serve
NotifyAccess=main
User=payments
Group=payments
WorkingDirectory=/opt/payments
EnvironmentFile=-/etc/payments/env
ExecStartPre=/opt/payments/bin/migrate --check
ExecStart=/opt/payments/bin/server
ExecReload=/bin/kill -HUP $MAINPID

Restart=on-failure
RestartSec=5s
TimeoutStartSec=60s
TimeoutStopSec=45s               # longer than the longest request
KillMode=mixed

# Least privilege
NoNewPrivileges=yes
ProtectSystem=strict
ReadWritePaths=/var/lib/payments /var/log/payments
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
SystemCallFilter=@system-service
CapabilityBoundingSet=

# Resources
MemoryHigh=1.5G
MemoryMax=2G
CPUQuota=200%
TasksMax=512
LimitNOFILE=65535
OOMScoreAdjust=-500

[Install]
WantedBy=multi-user.target

The reasoning behind the choices that are not obvious:

  • Type=notify because simple would mark it started before migrations finish, letting the load balancer route to a service that cannot serve.
  • TimeoutStopSec=45s deliberately exceeds the longest request. A shorter value SIGKILLs mid-request and drops in-flight work — for a payments service that is a correctness issue, not a tidiness one.
  • Restart=on-failure rather than always, so a clean exit stays exited; plus start limits so a persistent failure ends in a clear failed state rather than an endless loop.
  • CapabilityBoundingSet= empty because the service binds a high port. If it needed port 80 I would add CAP_NET_BIND_SERVICE rather than run as root.
  • MemoryHigh below MemoryMax gives a throttling warning band before the OOM kill, and OOMScoreAdjust=-500 makes the host's OOM killer prefer other victims.

Then verify rather than assume:

$ systemd-analyze verify /etc/systemd/system/payments.service
$ systemd-analyze security payments.service        # grades exposure and names the gaps
$ systemctl show payments -p MemoryMax,Restart,TimeoutStopSec

I would also test the failure modes explicitly in staging — kill the database and confirm the dependency behaves as intended, send SIGTERM mid-request and confirm draining works, and drive it past MemoryMax to confirm the kill is clean and observable.

Senior: The system takes 90 seconds to boot. How do you find and fix the cause?

systemd instruments the boot in detail, so this is a measurement problem rather than a guessing one.

1. Split the total into phases — that alone narrows it to a layer:

$ systemd-analyze
Startup finished in 4.1s (firmware) + 3.2s (loader) + 2.8s (kernel) + 78.4s (userspace) = 88.5s

78 seconds in userspace means services, not hardware or the kernel.

2. Rank the slowest units:

$ systemd-analyze blame | head -8
     45.012s NetworkManager-wait-online.service
     18.443s postgresql.service
      6.201s snapd.service

3. But blame is misleading on its own — units run in parallel, so the slowest unit is not necessarily on the critical path. The chain is what actually determines boot time:

$ systemd-analyze critical-chain
graphical.target @78.401s
└─multi-user.target @78.398s
  └─myapp.service @77.102s +1.294s
    └─network-online.target @76.998s
      └─NetworkManager-wait-online.service @31.981s +45.012s

The diagnosis is now specific: 45 seconds waiting for the network to be "online", and everything else waits behind it.

4. Understand why the wait is timing out. Usually an interface is configured with DHCP but not present or not connected — a second NIC, a bridge, or a VPN interface. The wait service blocks until every managed interface is up or it hits its timeout:

$ nmcli device status
$ journalctl -u NetworkManager-wait-online.service -b

5. Fix the cause, and only then consider the timeout. Marking the unused interface unmanaged, or setting may-fail=yes on the IPv6 configuration of an IPv4-only network, removes the wait rather than hiding it. If a service genuinely does not need an address, dropping network-online.target for plain network.target is correct and immediate.

6. Look for other structural wins once the critical path is clear:

$ systemd-analyze plot > boot.svg        # visual timeline; parallelism gaps are obvious
$ systemctl list-unit-files --state=enabled | wc -l
$ systemctl disable snapd.service        # things not needed on a server

Socket activation is the structural answer for services that only need to exist when used: systemd holds the listening socket from early boot and starts the service on the first connection, so it contributes nothing to boot time and clients never see a connection refused.

The general principle worth stating: I would optimise the critical chain, not the blame list. Shaving time off a unit that runs in parallel with a 45-second blocker changes the boot time by zero.

🏋️ Exercises

1 (easy): Write, enable, and inspect a minimal service.
Solution 
$ sudo tee /etc/systemd/system/heartbeat.service <<'EOF'
[Unit]
Description=Heartbeat demo service

[Service]
Type=simple
ExecStart=/bin/sh -c 'while true; do echo "beat $(date +%T)"; sleep 5; done'
Restart=on-failure
RestartSec=3s

[Install]
WantedBy=multi-user.target
EOF
$ sudo systemctl daemon-reload
$ sudo systemctl start heartbeat

Inspect what systemd knows about it:

$ systemctl status heartbeat
● heartbeat.service - Heartbeat demo service
     Loaded: loaded (/etc/systemd/system/heartbeat.service; disabled)
     Active: active (running) since Sun 2026-08-10 09:41:02 UTC; 12s ago
   Main PID: 65200 (sh)
      Tasks: 2 (limit: 18823)
     Memory: 512.0K
     CGroup: /system.slice/heartbeat.service
             ├─65200 /bin/sh -c while true; do echo ...
             └─65214 sleep 5

Note the CGroup section — systemd tracks every descendant, which is how it can reliably stop a service that forks.

The output went to the journal automatically:

$ journalctl -u heartbeat -n 3
Aug 10 09:41:07 host sh[65200]: beat 09:41:07
Aug 10 09:41:12 host sh[65200]: beat 09:41:12

Prove that daemon-reload is mandatory:

$ sudo sed -i 's/sleep 5/sleep 2/' /etc/systemd/system/heartbeat.service
$ sudo systemctl restart heartbeat
$ journalctl -u heartbeat -n 3 --no-pager     # still 5s apart — the edit was ignored
$ sudo systemctl daemon-reload && sudo systemctl restart heartbeat
$ journalctl -u heartbeat -n 3 --no-pager     # now 2s apart

Enable it and see what that actually does:

$ sudo systemctl enable heartbeat
Created symlink /etc/systemd/system/multi-user.target.wants/heartbeat.service → /etc/systemd/system/heartbeat.service

"Enable" is literally a symlink into the target's .wants directory — which is exactly why a unit without an [Install] section cannot be enabled.

Cleanup: sudo systemctl disable --now heartbeat; sudo rm /etc/systemd/system/heartbeat.service; sudo systemctl daemon-reload.

2 (easy): Query the journal in the ways you actually need during an incident.
Solution 
$ journalctl -u ssh -n 20 --no-pager           # last 20 lines for one unit
$ journalctl -u ssh --since '1 hour ago' -p warning
$ journalctl -b                                # this boot
$ journalctl -b -1 -p err                      # errors from the PREVIOUS boot
$ journalctl --list-boots | tail -3

That third command is the one that matters after an unexplained reboot — the evidence is in the boot that ended, not the current one.

Find failures across the whole system:

$ systemctl --failed
$ journalctl -p err -b --no-pager | tail -20
$ journalctl -k -b -p warning                  # kernel: OOM kills, disk errors, link flaps

Search and structure:

$ journalctl -u nginx --grep 'upstream timed out' -n 20
$ journalctl -u nginx -o json-pretty -n 1
{
    "_PID" : "1204",
    "_UID" : "33",
    "_SYSTEMD_UNIT" : "nginx.service",
    "PRIORITY" : "3",
    "MESSAGE" : "connect() failed (111: Connection refused)"
}

Every field is indexed and filterable directly — journalctl _PID=1204 or journalctl _UID=33 works without grep.

Correlate two services during an incident, which grep across separate log files cannot do:

$ journalctl -u nginx -u myapp --since '09:40' --until '09:45' -o short-precise

Manage journal size before it manages you:

$ journalctl --disk-usage
Archived and active journals take up 3.8G in the file system.
$ sudo journalctl --vacuum-time=14d
$ sudo journalctl --vacuum-size=1G
# permanent, in /etc/systemd/journald.conf:  SystemMaxUse=1G

Confirm persistence across reboots — the default on some distributions is volatile, and that is discovered at the worst moment:

$ ls -d /var/log/journal 2>/dev/null || echo "journal is VOLATILE — lost on reboot"
$ sudo mkdir -p /var/log/journal && sudo systemd-tmpfiles --create --prefix /var/log/journal
3 (medium): Demonstrate that Requires= without After= is a race.
Solution

Build a slow "database" and a client that depends on it:

$ sudo tee /etc/systemd/system/slowdb.service <<'EOF'
[Unit]
Description=Slow starting database
[Service]
Type=simple
ExecStart=/bin/sh -c 'echo "db: starting"; sleep 8; echo "db: READY"; sleep 300'
EOF

$ sudo tee /etc/systemd/system/dbclient.service <<'EOF'
[Unit]
Description=Client that needs the database
Requires=slowdb.service
# NOTE: no After= — this is the bug
[Service]
Type=oneshot
ExecStart=/bin/sh -c 'echo "client: connecting at $(date +%T)"'
EOF
$ sudo systemctl daemon-reload

Start the client and watch the ordering:

$ sudo systemctl start dbclient
$ journalctl -u slowdb -u dbclient --since '1 min ago' -o short-precise --no-pager
09:52:01.104 sh[65300]: db: starting
09:52:01.118 sh[65302]: client: connecting at 09:52:01     # BEFORE the db is ready
09:52:09.121 sh[65300]: db: READY

The client ran 8 seconds before the database was usable. Requires= pulled the dependency in but imposed no ordering whatsoever.

Add the missing directive:

$ sudo systemctl edit dbclient --full     # add:  After=slowdb.service
$ sudo systemctl daemon-reload
$ sudo systemctl stop slowdb; sudo systemctl start dbclient
$ journalctl -u slowdb -u dbclient --since '30 s ago' -o short-precise --no-pager
09:54:10.201 sh[65400]: db: starting
09:54:10.203 systemd[1]: Starting Client that needs the database...   # waits
09:54:18.208 sh[65402]: client: connecting at 09:54:18                # correct order

Now show the remaining subtlety — even with After=, Type=simple means "started" only signifies "forked". The client ran at 09:54:18 because slowdb is Type=simple and systemd considered it started immediately; the 8 second wait here came from the oneshot scheduling, not from readiness. Make readiness explicit:

$ sudo systemctl edit slowdb --full
# [Service]
# Type=notify
# ExecStart=/bin/sh -c 'echo "db: starting"; sleep 8; systemd-notify --ready; echo "db: READY"; sleep 300'
# NotifyAccess=all
$ sudo systemctl daemon-reload
$ sudo systemctl stop slowdb; time sudo systemctl start slowdb
real  0m8.1s                    # `start` itself now blocks until READY=1

The rule this establishes: Requires= answers "must it exist", and After= answers "must it be first" — you almost always need both, and Type=notify is what makes "first" mean "actually ready".

Cleanup: sudo systemctl stop slowdb dbclient; sudo rm /etc/systemd/system/{slowdb,dbclient}.service; sudo rm -rf /etc/systemd/system/dbclient.service.d; sudo systemctl daemon-reload.

4 (medium): Harden a service and measure the improvement.
Solution

Start from a deliberately unhardened unit:

$ sudo tee /etc/systemd/system/weak.service <<'EOF'
[Unit]
Description=Unhardened demo
[Service]
Type=simple
ExecStart=/bin/sh -c 'sleep 300'
EOF
$ sudo systemctl daemon-reload && sudo systemctl start weak
$ systemd-analyze security weak.service | tail -3
→ Overall exposure level for weak.service: 9.6 UNSAFE 😨

Prove the exposure is real — it runs as root with full filesystem access:

$ sudo systemd-run --uid=0 -p Description=probe -t /bin/sh -c 'id; ls /root >/dev/null && echo "can read /root"; touch /etc/probe && echo "can write /etc"'
uid=0(root) gid=0(root)
can read /root
can write /etc
$ sudo rm -f /etc/probe

Apply hardening one concern at a time:

$ sudo systemctl edit weak
[Service]
DynamicUser=yes                  # ephemeral unprivileged user, no account to manage
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
NoNewPrivileges=yes
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
RestrictSUIDSGID=yes
RestrictAddressFamilies=AF_UNIX
SystemCallFilter=@system-service
SystemCallArchitectures=native
CapabilityBoundingSet=
MemoryMax=128M
TasksMax=16
$ sudo systemctl daemon-reload && sudo systemctl restart weak

Measure the change:

$ systemd-analyze security weak.service | tail -3
→ Overall exposure level for weak.service: 1.6 OK 🙂

From 9.6 UNSAFE to 1.6 OK, with no application changes at all.

Verify the restrictions actually bite:

$ sudo systemd-run --uid=0 -p ProtectSystem=strict -p ProtectHome=yes -p PrivateTmp=yes -t \
>   /bin/sh -c 'touch /etc/probe 2>&1; ls /root 2>&1 | head -1; ls /tmp | wc -l'
touch: cannot touch '/etc/probe': Read-only file system
ls: cannot open directory '/root': Permission denied
0                                       # a completely private, empty /tmp

Confirm the resource limits are enforced by the cgroup:

$ systemctl show weak -p MemoryMax -p TasksMax -p User
MemoryMax=134217728
TasksMax=16
$ cat /sys/fs/cgroup/system.slice/weak.service/memory.max
134217728

The trade-off to be aware of: ProtectSystem=strict makes the entire filesystem read-only, so any real service needs ReadWritePaths= for its data and log directories, and SystemCallFilter can break a runtime that uses an unusual syscall. Both fail loudly at startup rather than silently, and journalctl -u names the blocked call — which makes iterating safe.

Cleanup: sudo systemctl stop weak; sudo rm -rf /etc/systemd/system/weak.service*; sudo systemctl daemon-reload.

5 (hard): Replace a cron job with a timer and demonstrate what cron cannot do.
Solution

1. The service half — a job that occasionally runs long:

$ sudo tee /etc/systemd/system/report.service <<'EOF'
[Unit]
Description=Generate report
[Service]
Type=oneshot
ExecStart=/bin/sh -c 'echo "start $(date +%T)"; sleep 20; echo "done $(date +%T)"'
MemoryMax=256M
PrivateTmp=yes
EOF

2. The timer half:

$ sudo tee /etc/systemd/system/report.timer <<'EOF'
[Unit]
Description=Run report every 30 seconds (demo)
[Timer]
OnBootSec=10s
OnUnitActiveSec=30s
AccuracySec=1s
Persistent=true
RandomizedDelaySec=0
[Install]
WantedBy=timers.target
EOF
$ sudo systemctl daemon-reload && sudo systemctl enable --now report.timer

3. Inspect the schedule without waiting for it:

$ systemctl list-timers report.timer
NEXT                        LEFT LAST                        PASSED UNIT
Sun 2026-08-10 10:02:41 UTC 22s  Sun 2026-08-10 10:02:11 UTC 8s ago report.timer
$ systemd-analyze calendar 'Mon *-*-* 04:30:00'
  Next elapse: Mon 2026-08-12 04:30:00 UTC
      From now: 1 day 18h left

Being able to ask "when will this next fire" is already something crontab cannot answer.

4. Output is in the journal, per unit, with no configuration:

$ journalctl -u report.service -n 6 --no-pager
Aug 10 10:02:11 host sh[65500]: start 10:02:11
Aug 10 10:02:31 host sh[65500]: done 10:02:31
Aug 10 10:02:41 host systemd[1]: Starting Generate report...

With cron this output would have gone to mail — which on most servers means nowhere.

5. Prove overlap is prevented. The job takes 20s and the timer fires every 30s; shorten the interval so they would collide:

$ sudo systemctl edit report.timer     # OnUnitActiveSec=5s
$ sudo systemctl daemon-reload && sudo systemctl restart report.timer
$ sleep 40; journalctl -u report.service --since '40 s ago' -o short-precise --no-pager | grep -c start
2                                       # NOT 8 — a unit runs once at a time

With cron, eight overlapping copies would be running, each doing the same work — the classic cause of a job that "sometimes corrupts the report".

6. Prove Persistent=true catches up missed runs:

$ sudo systemctl stop report.timer
$ sleep 60                              # simulate the machine being off
$ sudo systemctl start report.timer
$ journalctl -u report.service -n 2 --no-pager
Aug 10 10:06:02 host sh[65600]: start 10:06:02      # ran immediately on start

A cron job scheduled for 03:00 on a machine that was off at 03:00 simply does not run, and nothing records that it did not.

6 (hard): Build a zero-downtime restart using socket activation.
Solution

Socket activation makes systemd own the listening socket, so the service can restart while clients connect and wait rather than being refused.

1. The socket unit — systemd binds the port, not the application:

$ sudo tee /etc/systemd/system/echo.socket <<'EOF'
[Unit]
Description=Echo service socket
[Socket]
ListenStream=9400
Accept=no                        # one instance handles all connections
Backlog=256
[Install]
WantedBy=sockets.target
EOF

2. The service, which inherits the socket as fd 3:

$ sudo tee /etc/systemd/system/echo.service <<'EOF'
[Unit]
Description=Echo service
Requires=echo.socket
After=echo.socket
[Service]
Type=notify
ExecStart=/usr/local/bin/echo_server.py
NotifyAccess=main
EOF

$ sudo tee /usr/local/bin/echo_server.py <<'EOF'
#!/usr/bin/env python3
import socket, os, sys, time
SD_LISTEN_FDS_START = 3
n = int(os.environ.get('LISTEN_FDS', 0))
if n:
    sock = socket.socket(fileno=SD_LISTEN_FDS_START)   # inherited from systemd
    print(f"inherited socket from systemd (LISTEN_FDS={n})", flush=True)
else:
    sock = socket.socket(); sock.bind(('0.0.0.0', 9400)); sock.listen(256)
    print("bound my own socket", flush=True)
time.sleep(3)                                          # simulate slow startup
import socket as s
try:
    s.socket(s.AF_UNIX, s.SOCK_DGRAM).sendto(b"READY=1", os.environ["NOTIFY_SOCKET"])
except KeyError: pass
print(f"ready, pid {os.getpid()}", flush=True)
while True:
    conn, _ = sock.accept()
    conn.sendall(f"served by pid {os.getpid()}\n".encode()); conn.close()
EOF
$ sudo chmod +x /usr/local/bin/echo_server.py
$ sudo systemctl daemon-reload && sudo systemctl enable --now echo.socket

3. The service is not running yet — the socket is:

$ systemctl is-active echo.service echo.socket
inactive
active
$ ss -tlnp | grep 9400
LISTEN 0 256 0.0.0.0:9400 users:(("systemd",pid=1,fd=42))     # systemd holds it

4. The first connection starts the service on demand:

$ time nc 127.0.0.1 9400
served by pid 65700
real  0m3.1s                     # the client WAITED through startup, was not refused
$ journalctl -u echo.service -n 3 --no-pager
echo_server.py[65700]: inherited socket from systemd (LISTEN_FDS=1)
echo_server.py[65700]: ready, pid 65700

5. The payoff — restart while a client is connecting:

$ (for i in $(seq 1 30); do nc -w2 127.0.0.1 9400 || echo "FAILED at $i"; sleep 0.3; done) &
$ sleep 2 && sudo systemctl restart echo.service
$ wait
served by pid 65700
served by pid 65700
served by pid 65812        # new process, mid-stream
served by pid 65812
                           # note: no "FAILED" lines at all

Compare with a conventional service, where the same test produces connection-refused for the whole restart window:

$ sudo systemctl stop echo.socket echo.service
$ nc -w2 127.0.0.1 9400 || echo "refused — nothing is holding the socket"
refused — nothing is holding the socket

Why it works: the listening socket's lifetime is decoupled from the process's. Connections queue in the kernel's accept queue while the new process starts and calls accept() on the inherited descriptor. This is the same mechanism behind docker.socket and cups.socket, and it also removes startup ordering races entirely — a dependent service can connect at any time and simply blocks until the backend is ready.

The limits worth stating: in-flight requests on the old process are still cut off unless it drains on SIGTERM, so TimeoutStopSec and signal handling still matter; and the first request after activation pays the startup cost, which is fine for admin tools and wrong for a latency-critical path.

Cleanup: sudo systemctl disable --now echo.socket echo.service; sudo rm /etc/systemd/system/echo.{socket,service} /usr/local/bin/echo_server.py; sudo systemctl daemon-reload.

🎯 Key Takeaways

  • PID 1 must reap orphans and supervise services; a container whose PID 1 does neither leaks zombies and ignores SIGTERM — which is what --init fixes.
  • Custom units go in /etc/systemd/system/ and override /lib/systemd/system/; never edit a packaged unit, use systemctl edit drop-ins.
  • systemctl daemon-reload is mandatory after any unit change — without it systemd keeps running the cached version.
  • Type= defines when a service counts as started: simple means "forked", notify means "the app said it is ready" — and dependents race whenever it is wrong.
  • After= is ordering, Requires= is dependency; they are independent and you almost always need both.
  • network.target only means networking is being configured; a service that binds an address needs network-online.target with a matching Wants=.
  • Everything on stdout/stderr goes to the journal with unit, PID and boot metadata — query with journalctl -u, and -b -1 for the boot that crashed.
  • Restart=on-failure plus RestartSec plus start limits turns a crash loop into a clean failed state that alerts instead of burning CPU.
  • TimeoutStopSec must exceed the longest in-flight request, or SIGKILL drops work mid-flight.
  • Sandboxing is one line per class of risk — ProtectSystem=strict, NoNewPrivileges, PrivateTmp, CapabilityBoundingSet= — and systemd-analyze security grades the result.
  • MemoryMax, CPUQuota and TasksMax apply cgroup limits per service, the same mechanism containers use.
  • Timers beat cron: journal output, no overlapping runs, Persistent=true for missed schedules, resource limits, and a testable service half.
  • Optimise boot time along systemd-analyze critical-chain, not blame — units run in parallel, so the slowest unit is often not on the critical path.
  • Socket activation decouples the listening socket from the process, giving on-demand start and restarts that queue connections instead of refusing them.
