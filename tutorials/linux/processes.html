Processes, fork & exec Processes & The Kernel

What you'll master: the process lifecycle as a state machine you can read off ps output — including why D state cannot be killed and what that tells you about storage — how fork returns twice and what copy-on-write actually copies, why zombies exist and why they are the parent's fault, how orphans get re-parented and what changes inside a container, the difference between PID/PPID/PGID/SID that makes signals and job control comprehensible, and how to read /proc/PID to answer almost any question about a running process. Prerequisites: How Unix Is Put Together and The Shell Executes a Line.

Part 1 — The Process State Machine

A process is always in exactly one state, and the letter in ps's STAT column tells you what it is waiting for. Reading it correctly redirects an investigation in seconds.

                    ┌─────────────┐
        fork() ───→ │  R  runnable │ ←──────────────┐
                    │  (or running)│                │
                    └──────┬───────┘                │
                           │                        │
          waits for I/O,   │                   event occurs,
          lock, or timer   │                   scheduler picks it
                           ▼                        │
              ┌────────────────────────┐            │
              │  S  interruptible sleep │───────────┤
              │     (can be signalled)  │            │
              └────────────────────────┘            │
              ┌────────────────────────┐            │
              │  D  UNinterruptible     │───────────┘
              │     (cannot be killed)  │
              └────────────────────────┘
                           │ exit()
                           ▼
                    ┌─────────────┐    parent calls wait()
                    │  Z  zombie   │ ──────────────────→ gone
                    │ (exit status │
                    │   retained)  │
                    └─────────────┘
StateMeaningWhat it tells you
RRunning or runnableUsing CPU, or queued for it. High counts = CPU contention
SInterruptible sleepNormal waiting — network, timer, lock. Signals work
DUninterruptible sleepBlock I/O or NFS. Cannot be killed, not even with -9
ZZombieDead; parent has not reaped it. Holds only a PID
TStoppedSIGSTOP/SIGTSTP, or under a debugger
IIdle kernel threadIgnore — does not count toward load

Suffixes add detail: < high priority, N low priority, s session leader, + foreground process group, l multi-threaded.

$ ps -eo pid,stat,wchan:20,cmd --sort=-stat | head -6
    PID STAT WCHAN                CMD
   2210 Ss   ep_poll              /usr/sbin/nginx: master process
  48901 S    inet_csk_accept      ./api-server
  51022 D    io_schedule          /usr/bin/rsync -a /data /backup
  51190 Z    -                    [worker] <defunct>

WCHAN names the kernel function the process is parked in, which is far more specific than the state letter alone. ep_poll means waiting on epoll (idle server, healthy), inet_csk_accept means waiting for a TCP connection, io_schedule means waiting on a block device, and futex_wait means blocked on a userspace lock — often a deadlock.

🔑 Why D state ignores SIGKILL. An uninterruptible sleep means the process is inside a kernel operation that cannot safely be abandoned — typically mid-way through a block device request where unwinding would corrupt kernel state. Signals are only delivered when a process transitions back to userspace, and a D-state process never gets there until the I/O completes. So a pile of unkillable D processes is not an application problem: it is a storage problem, or a hung NFS server. Fix the device, or the processes never leave.

Part 2 — fork() Returns Twice

fork is the only system call that returns twice — once in each of two now-independent processes. This is genuinely strange the first time you see it, and it is the foundation of everything else in this lesson.

pid_t pid = fork();

if (pid == 0) {
    // We are the CHILD. fork() returned 0 here.
} else if (pid > 0) {
    // We are the PARENT. fork() returned the child's PID.
} else {
    // fork failed (-1): out of memory, or hit RLIMIT_NPROC
}

The child is a near-exact duplicate: same code, same variables, same open file descriptors, same current directory. The differences are few and specific:

Inherited by the childDifferent in the child
Memory contents (copy-on-write)PID and PPID
Open file descriptors (shared offsets)Pending signals are cleared
Environment, cwd, umaskCPU time counters reset to zero
Signal handlers, resource limitsFile locks are not inherited
Real/effective UID and GIDTimers are not inherited

That "shared offsets" detail matters more than it looks. Parent and child share the same open file description, so they share a read/write position:

$ cat > /tmp/shared.sh <<'EOF'
#!/usr/bin/env bash
exec 3< /tmp/data.txt
( read -r line <&3; echo "child read: $line" ) &
wait
read -r line <&3
echo "parent read: $line"
EOF
$ printf 'first\nsecond\n' > /tmp/data.txt
$ bash /tmp/shared.sh
child read: first
parent read: second        # the parent continued from where the child left off

This is exactly why two processes appending to the same log file with >> do not overwrite each other — they share the offset — while two processes that each opened the file separately do clobber one another.

Copy-on-write makes fork cheap. The child does not get a physical copy of the parent's memory; both processes share the same physical pages, marked read-only. A page is only duplicated when one of them writes to it:

$ python3 -c "
import os, time
data = bytearray(500 * 1024 * 1024)      # 500 MB
pid = os.fork()
if pid == 0:
    time.sleep(3); os._exit(0)
time.sleep(1)
print(open('/proc/%d/status' % pid).read().split('VmRSS:')[1].split(chr(10))[0])
os.wait()
"
	 12345 kB                # the child's RSS is tiny, not 500 MB

The consequence people meet in production: a large process forking is fast, but if the child then writes across its inherited memory, pages get copied and memory use spikes. This is why a memory-heavy service forking workers can OOM under load despite each worker "sharing" memory — and why vfork and posix_spawn exist for the common fork-then-exec case where the copy is pure waste.

Part 3 — Zombies and Orphans

These two are opposites and are constantly confused. Both arise from the parent/child relationship outliving one party.

A zombie is a process that has exited but whose parent has not yet collected its exit status. The kernel must keep the status somewhere until someone asks, so it retains a minimal entry — no memory, no descriptors, just a PID and the status.

$ cat > /tmp/zombie.sh <<'EOF'
#!/usr/bin/env bash
sleep 1 &                        # child exits after 1s
sleep 30                         # parent ignores it for 30s
EOF
$ bash /tmp/zombie.sh &
$ sleep 3; ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'
  52301  52300 Z    [sleep] <defunct>

Zombies are always the parent's bug. The fix is for the parent to call wait(). You cannot kill a zombie — it is already dead; signals have no effect. Killing the parent works, because the zombie is then re-parented to init, which reaps it immediately.

A handful of zombies is harmless. Thousands exhaust the PID space and prevent new processes from starting, which presents as a system that cannot fork — often reported as "everything is broken".

$ ps -eo stat | grep -c '^Z'
2847
$ cat /proc/sys/kernel/pid_max
4194304

An orphan is the reverse: the parent died first. The kernel immediately re-parents the child, traditionally to PID 1:

$ (sleep 300 & echo "child PID: $!"; exit)
child PID: 52890
$ ps -o pid,ppid,cmd -p 52890
    PID    PPID CMD
  52890       1 sleep 300        # PPID became 1

Modern Linux allows a process to declare itself a subreaper (PR_SET_CHILD_SUBREAPER), so orphans are re-parented to the nearest subreaper ancestor rather than PID 1. systemd uses this so a service's orphaned children stay within its unit and are cleaned up with it.

❌ Running an application directly as PID 1 in a container. PID 1 has special semantics: it does not get default signal handlers, so a process that has not explicitly installed a SIGTERM handler ignores it — docker stop then waits ten seconds and SIGKILLs. It is also responsible for reaping every orphan in the container, which most applications never do, so zombies accumulate.

✅ Use an init that handles both — docker run --init, or tini/dumb-init as the entrypoint. It forwards signals to your application and reaps orphans. The symptoms it prevents — containers that take exactly ten seconds to stop, and slowly accumulating <defunct> entries — are both extremely common and both look like application bugs.

Part 4 — PID, PPID, PGID, SID

Four identifiers, each answering a different question. Confusing them is why job control and signal delivery feel arbitrary.

IDWhat it identifiesUsed for
PIDThis processSignalling one process
PPIDIts parentReaping; orphan detection
PGIDIts process group — usually one pipelineSignalling a whole job at once
SIDIts session — usually one terminal loginTerminal ownership; SIGHUP on disconnect
$ sleep 100 | cat &
$ ps -eo pid,ppid,pgid,sid,cmd | grep -E 'sleep 100|PID'
    PID    PPID    PGID     SID CMD
  53201   53100   53201   53100 sleep 100
  53202   53100   53201   53100 cat
                  ^^^^^^ same PGID — one job, two processes

Both stages of the pipeline share a PGID. That is why Ctrl-C stops the entire pipeline rather than one stage: the terminal driver sends SIGINT to the whole foreground process group. You can do the same manually with a negative PID:

$ kill -TERM -53201          # note the minus: signal the GROUP

This is the reliable way to kill a process and everything it spawned. Killing only the parent leaves children running as orphans — a common cause of "I stopped the service but the port is still in use".

Sessions explain SIGHUP. When a terminal closes, the kernel sends SIGHUP to the foreground process group of that session, and the default action is to terminate. That is why closing an SSH window kills your jobs, and why the tools to prevent it work the way they do:

ToolMechanism
nohup cmdIgnores SIGHUP; redirects output to nohup.out
setsid cmdNew session with no controlling terminal — cannot receive terminal signals
disown -h %1Tells bash not to send SIGHUP to that job
tmux / screenThe session persists on the server; you detach rather than disconnect
systemd-run --userRuns it under systemd, fully detached from your session

For anything that must survive genuinely, a systemd unit is the right answer — nohup is a convenience for interactive work, not a supervision strategy. See systemd & Service Management.

Part 5 — Reading /proc/PID

/proc/PID is the definitive interface for inspecting a running process. Every tool — ps, top, htop — is a parser over these files, so knowing them directly means never being blocked by a missing tool.

PathContains
/proc/PID/statusHuman-readable summary: state, memory, UIDs, threads, capabilities
/proc/PID/cmdlineFull argv, NUL-separated
/proc/PID/environEnvironment at exec time, NUL-separated
/proc/PID/fd/Symlinks to every open file, pipe, socket
/proc/PID/cwdSymlink to the working directory
/proc/PID/exeSymlink to the binary — resolves even if deleted
/proc/PID/mapsMemory map: libraries, heap, stack
/proc/PID/limitsSoft and hard resource limits
/proc/PID/wchanThe kernel function it is sleeping in
/proc/PID/task/One directory per thread
$ pid=$(pgrep -n nginx)
$ tr '\0' ' ' < /proc/$pid/cmdline; echo
nginx: master process /usr/sbin/nginx -g daemon on; master_process on;

$ grep -E '^(State|Threads|VmRSS|FDSize)' /proc/$pid/status
State:  S (sleeping)
Threads:        1
VmRSS:      8412 kB
FDSize:     128

/proc/PID/exe resolving even for a deleted binary is genuinely useful — it identifies processes still running code that has been replaced by an upgrade:

$ ls -l /proc/*/exe 2>/dev/null | grep deleted
lrwxrwxrwx 1 root root 0 Aug  9 10:12 /proc/2210/exe -> /usr/sbin/nginx (deleted)

Those processes are still running the old code and must be restarted for a security patch to take effect — an entire class of "we patched it but the CVE scanner still flags us".

/proc/PID/environ is worth a security note: it is readable only by the process owner and root, because environments routinely hold secrets. That is precisely why passing credentials via environment variables is weaker than it looks — any process running as the same user can read them, and they are inherited by every child.

Part 6 — Finding and Signalling Processes

The tooling divides into finding processes and acting on them, and the modern options are considerably safer than the traditional ones.

$ pgrep -a nginx                  # -a shows the full command line
2210 nginx: master process /usr/sbin/nginx
2211 nginx: worker process

$ pgrep -u www-data -f 'worker'   # by user, matching the full command
$ pgrep -P 2210                   # children of a given PID
$ pkill -TERM -u baduser          # signal every process of a user

pgrep -f matches against the whole command line rather than just the process name, which is essential for anything run through an interpreter — python worker.py has a process name of python, so a name-only match finds every Python process on the box.

The classic mistake is ps aux | grep name, which matches its own grep process and is fragile:

$ ps aux | grep nginx
www-data  2210  ... nginx: master process
alice    54012  ... grep --color=auto nginx      # matched itself

$ pgrep -a nginx                                  # no such problem

For process trees, pstree shows relationships that a flat list hides:

$ pstree -ps $(pgrep -n nginx)
systemd(1)───nginx(2210)─┬─nginx(2211)
                         └─nginx(2212)

Signalling escalates in a specific order, and skipping steps causes data loss:

StepSignalEffect
1SIGTERM (15)Polite request to exit. Catchable — lets the process flush and clean up
2WaitGive it time. Databases may need tens of seconds to flush
3SIGKILL (9)Immediate, uncatchable. Buffered data is lost
$ kill 2210                       # SIGTERM by default
$ sleep 10
$ kill -0 2210 2>/dev/null && kill -9 2210     # -0 tests existence without signalling

kill -9 as a first resort is one of the most common bad habits in operations. It skips the process's own shutdown path: unflushed writes are lost, lock files remain, and — as Files, Inodes & Links showed — deleted-but-open files never release their disk space because no orderly close happens.

Interview Questions

Beginner: What is a zombie process and how do you get rid of one?

A zombie is a process that has already exited but whose parent has not yet collected its exit status. The kernel keeps a minimal entry — just the PID and the status — because the parent might still ask for it via wait(). It holds no memory and no file descriptors.

You cannot kill a zombie. It is already dead; signals have no meaning for it. kill -9 does nothing.

The fix is always in the parent, because a zombie is a parent bug: the parent must call wait() or waitpid() to reap its children. If you cannot fix the code, killing or restarting the parent works — the zombie is then re-parented to init (PID 1), which reaps it immediately.

A few zombies are harmless. Thousands are a real problem because each holds a PID, and exhausting the PID space means nothing on the system can fork — which presents as a machine where every command fails. This is a common container symptom when an application runs as PID 1 without reaping orphans; docker run --init or tini solves it.

Beginner: What does D state mean in ps, and why can't you kill it?

D is uninterruptible sleep. The process is blocked inside a kernel operation that cannot safely be abandoned partway — almost always a block device request, or a network filesystem like NFS waiting on an unresponsive server.

Signals are only delivered when a process transitions from kernel mode back to userspace. A D-state process never makes that transition until the underlying operation completes, so the signal sits pending. Even SIGKILL, which cannot be caught or ignored, cannot be delivered.

The diagnostic value is high: a pile of D-state processes is a storage problem, not an application problem. Restarting the application will not help, and the processes are not "stuck" in the sense of being buggy. I would check /proc/PID/wchan for the specific function (io_schedule for block I/O), then iostat -x 1 for device saturation or errors, then dmesg for device or NFS timeouts.

The practical resolutions are fixing the device, recovering the NFS server, or — for NFS specifically — mounting with soft and a timeout so operations fail rather than hanging forever, though that trades hangs for potential data errors and is a deliberate choice.

Mid: Explain copy-on-write and its practical consequences.

When a process forks, the child does not receive a physical copy of the parent's memory. Both processes' page tables point at the same physical pages, marked read-only. When either one writes to a page, the CPU raises a fault, and the kernel then copies just that page and lets the write proceed.

This makes fork cheap and nearly independent of the parent's size — forking a 500 MB process does not copy 500 MB, and the child's initial RSS is a few megabytes.

The consequences that matter in production:

  • Memory can spike unexpectedly later. If the child writes across its inherited memory, pages get copied one at a time. A forking web server can OOM under load even though fork itself was cheap — the cost is deferred, not avoided.
  • Reported memory is misleading. Summing RSS across forked workers double-counts shared pages. PSS (proportional set size, in /proc/PID/smaps) divides shared pages among users and is the honest number.
  • Garbage collectors defeat it. A GC that touches object headers across the heap dirties nearly every page, so a forked Python or Ruby worker gradually stops sharing anything. This is why gc.freeze() exists in Python before forking.
  • Redis's background save relies on it — it forks and writes the snapshot from the child's frozen view. If the parent then receives heavy writes, memory use can approach double, which is why Redis hosts need headroom.

For the common fork-immediately-exec case, all of this copying machinery is pure waste, which is why posix_spawn and vfork exist and why they measurably help large processes that spawn frequently.

Mid: Why does Ctrl-C kill an entire pipeline rather than just one command?

Because the signal goes to a process group, not a process.

When bash builds a pipeline, it puts every stage into a single new process group, and makes that group the terminal's foreground group. The terminal line discipline — kernel code, not bash — maps Ctrl-C to SIGINT and delivers it to every process in the foreground group.

$ sleep 100 | cat &
$ ps -eo pid,pgid,cmd | grep -E 'sleep 100|cat'
  53201   53201 sleep 100
  53202   53201 cat            # same PGID

You can do this manually with a negative PID: kill -TERM -53201 signals the whole group. That is the reliable way to stop a process and everything it spawned, and it is the fix for the common situation where killing a parent leaves orphaned children holding a port open.

Sessions are the level above: a session usually corresponds to one terminal login and contains multiple process groups (one per job). When the terminal disconnects, the kernel sends SIGHUP to the foreground group of that session — which is why closing an SSH window kills your jobs, and why nohup, disown, setsid, and tmux each break that chain at a different point.

Senior: A service will not stop cleanly — systemctl stop hangs for 90 seconds then reports failure. Diagnose it.

The 90 seconds is a strong clue on its own: it is systemd's default TimeoutStopSec. So SIGTERM was sent, nothing exited, and systemd eventually escalated to SIGKILL. The question is why the process ignored SIGTERM.

1. Confirm what systemd is waiting for.

$ systemctl status myapp
$ journalctl -u myapp -n 50
$ systemctl show myapp -p TimeoutStopUSec,KillMode,KillSignal,ExecStop

KillMode= matters here: the default control-group signals every process in the unit, but KillMode=process signals only the main PID, leaving children running and the unit "still active".

2. Determine the process state, because the three cases need different fixes:

$ ps -o pid,stat,wchan:25,cmd -p $(systemctl show -p MainPID --value myapp)
  • D state — it is blocked on I/O and cannot receive the signal. This is a storage problem; no amount of signalling helps.
  • S state — it received SIGTERM and is either ignoring it or doing slow cleanup.
  • T state — it is stopped, perhaps by a debugger, and will never process anything.

3. Check whether the signal is masked or handled. This is the case people miss:

$ grep -E 'SigBlk|SigIgn|SigCgt' /proc/$PID/status
SigIgn: 0000000000001000      # bit 15 set = SIGTERM is being IGNORED
SigCgt: 0000000180004a03

Decoding is straightforward: SIGTERM is signal 15, so bit 15 (value 0x4000 counting from 1). A process that inherited an ignored SIGTERM — common when a poorly written wrapper script spawned it — will never respond. Applications running as PID 1 in a container have the same symptom for a different reason: PID 1 gets no default handlers, so an unhandled SIGTERM is simply discarded.

4. Watch what it is actually doing rather than assuming it is stuck:

$ sudo strace -p $PID -f -e trace=none -e signal=all
$ sudo cat /proc/$PID/stack           # kernel-side, if it is in D state

A process legitimately flushing a large write buffer looks identical to a hung one for the first thirty seconds. Distinguishing them matters — killing a database mid-flush is how you get a corrupt recovery.

The fixes, matched to the cause: install a real SIGTERM handler that begins graceful shutdown; raise TimeoutStopSec= if shutdown legitimately takes longer than 90s; add ExecStop= for services that need a specific drain command; set KillMode=mixed so the main process gets SIGTERM and stragglers get SIGKILL; and in containers, run an init that forwards signals. I would treat "hangs then gets killed" as a real bug rather than cosmetic — every stop is an unclean shutdown, and the data-loss risk is only visible after it bites.

Senior: Design a supervisor that manages worker processes correctly. What must it get right?

The requirements sound simple and the failure modes are all in the details. I would build around five obligations.

1. Reap every child, unconditionally. Missing this is what produces zombie accumulation and eventual PID exhaustion. The subtlety is that SIGCHLD is not queued — several children exiting close together produce one signal, so the handler must loop:

while ((pid = waitpid(-1, &status, WNOHANG)) > 0) {
    handle_exit(pid, status);        // loop until no more, not just once
}

A handler that reaps a single child per signal leaks zombies under load and works perfectly in testing.

2. Distinguish exit causes. The exit status encodes how the process died, and restarting blindly is wrong for at least two of them: a clean exit 0, a nonzero failure, a signal death (WIFSIGNALED, reported as 128+N by shells), and specifically SIGKILL from the OOM killer — which means restarting immediately will just OOM again.

3. Shut down in the right order, with escalation. Signal the process group so grandchildren are included, wait a bounded time, then escalate:

kill(-pgid, SIGTERM);
if (!all_exited_within(timeout)) kill(-pgid, SIGKILL);

Signalling only the main PID is the standard bug — children are re-parented and keep holding ports and locks, so the restart fails with "address already in use".

4. Back off on restarts. A worker that crashes on startup will otherwise spin at thousands of forks per second, which is indistinguishable from a fork bomb. Exponential backoff with jitter, plus a circuit breaker that stops trying after N failures in a window, is the minimum. systemd expresses this as RestartSec=, StartLimitBurst= and StartLimitIntervalSec=.

5. Handle the PID-reuse race. PIDs wrap. A supervisor that records a PID and later signals it can, in principle, kill an unrelated process that inherited that number. Signalling the process group narrows the window; on modern Linux, pidfd_open() eliminates it entirely by giving a stable handle to a specific process. Cgroup membership is the other robust identity — which is exactly what systemd uses.

What I would actually do: not write this. systemd already implements all five correctly, plus dependency ordering, socket activation, resource limits, and journal integration. The legitimate reasons to write a supervisor are a language-specific worker pool inside one service (gunicorn, puma) or a platform that has no init — and in the container case the answer is tini, which is roughly 200 lines because that is genuinely all a correct minimal init needs to be.

2 (easy): Demonstrate that fork returns twice and that copy-on-write defers the memory cost.
Solution 
$ python3 <<'EOF'
import os
print("before fork, pid =", os.getpid())
pid = os.fork()
if pid == 0:
    print("  CHILD : fork() returned", pid, "my pid is", os.getpid())
    os._exit(0)
else:
    print("  PARENT: fork() returned", pid, "my pid is", os.getpid())
    os.wait()
EOF
before fork, pid = 54100
  PARENT: fork() returned 54101 my pid is 54100
  CHILD : fork() returned 0 my pid is 54101

One fork() call, two returns, two different values — 0 in the child, the child's PID in the parent. The line before the fork printed once; everything after printed twice.

Now measure copy-on-write:

$ python3 <<'EOF'
import os, time

def rss(pid):
    for line in open('/proc/%d/status' % pid):
        if line.startswith('VmRSS'): return line.split()[1] + ' kB'

data = bytearray(400 * 1024 * 1024)          # 400 MB, touched
print("parent RSS before fork:", rss(os.getpid()))

pid = os.fork()
if pid == 0:
    time.sleep(2)
    print("  child RSS (no writes):", rss(os.getpid()))
    for i in range(0, len(data), 4096):       # now dirty every page
        data[i] = 1
    print("  child RSS (after writing):", rss(os.getpid()))
    os._exit(0)
time.sleep(4); os.wait()
EOF
parent RSS before fork: 410892 kB
  child RSS (no writes): 8244 kB              ← shares the parent's pages
  child RSS (after writing): 412108 kB        ← every page now copied

The child started at 8 MB despite "inheriting" 400 MB, then grew to the full size once it wrote across it. The copy was deferred, not avoided — which is exactly why a forking service can OOM later under write pressure while the fork itself looked free.

3 (medium): Create a zombie and an orphan, and fix each correctly.
Solution

The zombie — a parent that does not reap:

$ cat > /tmp/zparent.sh <<'EOF'
#!/usr/bin/env bash
sleep 0.5 &                 # child exits quickly
echo "parent $$ ignoring child $!"
sleep 60                    # never calls wait
EOF
$ bash /tmp/zparent.sh & sleep 2
parent 54300 ignoring child 54301

$ ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'
  54301   54300 Z    [sleep] <defunct>

Confirm it cannot be killed, because it is already dead:

$ kill -9 54301; sleep 1; ps -o pid,stat -p 54301
    PID STAT
  54301 Z                    # unchanged

Fix — remove the parent, so init reaps it:

$ kill 54300; sleep 1; ps -o pid= -p 54301 || echo "zombie gone"
zombie gone

The real fix in code is for the parent to wait:

$ cat > /tmp/good.sh <<'EOF'
#!/usr/bin/env bash
sleep 0.5 &
wait                        # reap it
sleep 5
EOF
$ bash /tmp/good.sh & sleep 2; ps -eo stat,cmd | grep -c defunct
0                           # no zombies

The orphan — the opposite case:

$ bash -c 'sleep 60 & echo "child=$!"; echo "parent=$$"; exit'
child=54500
parent=54499
$ ps -o pid,ppid,cmd -p 54500
    PID    PPID CMD
  54500       1 sleep 60     # re-parented to init

The orphan is not a problem — it keeps running normally, and init will reap it when it exits. The distinction is the point: a zombie is dead and un-reaped (parent's bug); an orphan is alive with a dead parent (handled automatically by the kernel).

Where it goes wrong at scale is a container whose PID 1 is an ordinary application: it inherits every orphan but never calls wait(), so zombies accumulate until PIDs run out. docker run --init inserts a minimal init that reaps them.

4 (medium): Use process groups to kill a whole job tree, and show why killing the parent alone fails.
Solution 
$ cat > /tmp/tree.sh <<'EOF'
#!/usr/bin/env bash
sleep 300 &
sleep 300 &
sleep 300 &
echo "parent=$$ pgid=$(ps -o pgid= -p $$ | tr -d ' ')"
wait
EOF
$ bash /tmp/tree.sh & sleep 1
parent=54700 pgid=54700

$ ps -eo pid,ppid,pgid,cmd | grep -E 'tree.sh|sleep 300' | grep -v grep
  54700   54600   54700 bash /tmp/tree.sh
  54701   54700   54700 sleep 300
  54702   54700   54700 sleep 300
  54703   54700   54700 sleep 300

All four share PGID 54700 — one job.

Killing the parent alone leaves the children:

$ kill 54700; sleep 1
$ ps -eo pid,ppid,cmd | grep 'sleep 300' | grep -v grep
  54701       1 sleep 300
  54702       1 sleep 300
  54703       1 sleep 300      # orphaned, re-parented to init, still running

This is exactly the "I stopped the service but the port is still in use" situation.

Killing the group gets everything:

$ kill -TERM -54700 2>/dev/null      # already reaped above; restart to demo
$ bash /tmp/tree.sh & sleep 1
parent=54800 pgid=54800
$ kill -TERM -54800; sleep 1
$ ps -eo pid,cmd | grep -c 'sleep 300'
0                              # all gone

The negative PID is the whole trick — kill -TERM -PGID. Getting the PGID reliably:

$ pgid=$(ps -o pgid= -p "$pid" | tr -d ' ')
$ kill -TERM -"$pgid"

For a tree that spans process groups, use pkill -P recursively, or start the job in its own session with setsid so the whole tree is isolated and killable as one unit. systemd solves this properly with cgroups: KillMode=control-group signals every process in the unit's cgroup regardless of PGID or re-parenting, which is why it is the default and why it is more reliable than anything achievable with PIDs alone.

5 (hard): Investigate an unknown process entirely through /proc, without ps or lsof.
Solution

Start a target with a distinctive setup:

$ (cd /var/tmp && exec 7< /etc/hostname; SECRET=hunter2 sleep 400) &
$ pid=$!

1. What is it, and what state?

$ grep -E '^(Name|State|Pid|PPid|Threads|VmRSS)' /proc/$pid/status
Name:   sleep
State:  S (sleeping)
Pid:    55010
PPid:   55009
Threads:        1
VmRSS:       716 kB

2. The exact command line — NUL-separated, so translate:

$ tr '\0' ' ' < /proc/$pid/cmdline; echo
sleep 400

3. Where is it running, and what binary?

$ ls -l /proc/$pid/cwd /proc/$pid/exe
lrwxrwxrwx ... /proc/55010/cwd -> /var/tmp
lrwxrwxrwx ... /proc/55010/exe -> /usr/bin/sleep

4. What does it have open? This replaces lsof:

$ ls -l /proc/$pid/fd
lrwx------ ... 0 -> /dev/pts/3
lrwx------ ... 1 -> /dev/pts/3
lrwx------ ... 2 -> /dev/pts/3
lr-x------ ... 7 -> /etc/hostname        ← the inherited descriptor

5. Its environment — note this is why env vars are poor secret storage:

$ tr '\0' '\n' < /proc/$pid/environ | grep SECRET
SECRET=hunter2

6. What is it blocked on, and what are its limits?

$ cat /proc/$pid/wchan; echo
hrtimer_nanosleep                        # sleeping on a timer, as expected
$ grep -E 'open files|processes' /proc/$pid/limits
Max processes             31404    31404    processes
Max open files            1024     524288   files

7. Which signals are handled, blocked or ignored — the field people forget exists:

$ grep -E 'Sig(Blk|Ign|Cgt)' /proc/$pid/status
SigBlk: 0000000000000000
SigIgn: 0000000000000000
SigCgt: 0000000000000000                 # handles nothing: default actions apply

8. Memory map, to see what libraries it loaded:

$ awk '{print $NF}' /proc/$pid/maps | sort -u | grep -v '^\[' | head -3
/usr/bin/sleep
/usr/lib/x86_64-linux-gnu/libc.so.6
/usr/lib/x86_64-linux-gnu/ld-linux-x86-64.so.2

Why this matters: every one of ps, top, lsof and htop is a parser over these files. On a stripped container image or a compromised host where you cannot trust the binaries, /proc is still there and still tells the truth. The SigIgn field in particular answers "why is this ignoring SIGTERM?", which no standard tool surfaces.

Cleanup: kill $pid.

6 (hard): Build a correct graceful-shutdown handler and prove it beats kill -9.
Solution

Write a worker that must flush state before exiting — the realistic case where an abrupt kill loses data:

$ cat > /tmp/worker.py <<'EOF'
import signal, sys, time, os

buffer, running = [], True

def shutdown(signum, frame):
    global running
    print(f"[{os.getpid()}] got {signal.Signals(signum).name}, draining", flush=True)
    running = False

signal.signal(signal.SIGTERM, shutdown)
signal.signal(signal.SIGINT,  shutdown)

n = 0
while running:
    n += 1
    buffer.append(f"record-{n}")
    if len(buffer) >= 5:                       # flush periodically
        with open('/tmp/worker.out','a') as f:
            f.write('\n'.join(buffer) + '\n')
        buffer.clear()
    time.sleep(0.1)

with open('/tmp/worker.out','a') as f:          # FINAL flush on shutdown
    if buffer: f.write('\n'.join(buffer) + '\n')
    f.write(f"CLEAN-EXIT after {n} records\n")
print("exited cleanly", flush=True)
EOF

SIGTERM — the handler runs and nothing is lost:

$ rm -f /tmp/worker.out; python3 /tmp/worker.py & pid=$!
$ sleep 2; kill -TERM $pid; wait $pid; echo "status=$?"
[55200] got SIGTERM, draining
exited cleanly
status=0
$ tail -2 /tmp/worker.out
record-20
CLEAN-EXIT after 20 records

SIGKILL — the same run, abruptly terminated:

$ rm -f /tmp/worker.out; python3 /tmp/worker.py & pid=$!
$ sleep 2; kill -9 $pid; wait $pid 2>/dev/null; echo "status=$?"
status=137
$ tail -2 /tmp/worker.out
record-19
record-20                     # no CLEAN-EXIT; unflushed buffer lost

Status 137 = 128+9 confirms SIGKILL. The records held in the buffer at that instant are gone permanently, and there is no marker indicating the file is incomplete.

Prove the handler is registered via /proc:

$ python3 /tmp/worker.py & pid=$!; sleep 1
$ grep SigCgt /proc/$pid/status
SigCgt: 0000000000004002      # bit 2 (SIGINT) and bit 15 (SIGTERM) caught
$ kill -TERM $pid

The production-grade additions this simple version omits:

ConcernHandling
Shutdown could hangThe supervisor must escalate — systemd's TimeoutStopSec, then SIGKILL
Second signal while drainingTreat a repeated SIGTERM as "exit now"; users press Ctrl-C twice
Handler doing too muchSignal handlers should set a flag, not perform I/O — async-signal-safety
Children still runningForward the signal to the process group, not just self
In-flight requestsStop accepting new work first, then drain, then exit

The systemd counterpart makes the escalation explicit rather than implicit:

[Service]
KillSignal=SIGTERM
TimeoutStopSec=30
KillMode=mixed          # SIGTERM to main process, SIGKILL to stragglers

The general principle: kill -9 is not a stronger version of kill — it is a different operation that skips the program's own correctness logic. Reserve it for processes that have demonstrably failed to respond, never as the first attempt.

🎯 Key Takeaways

  • The STAT letter tells you what a process is waiting for; WCHAN names the exact kernel function and is far more specific.
  • D state cannot receive any signal, including SIGKILL, because signals are only delivered on return to userspace — a pile of them is a storage problem, not an application one.
  • fork() returns twice: 0 in the child, the child's PID in the parent.
  • Parent and child share open file descriptions, so they share read/write offsets — which is why concurrent appends to one log do not clobber each other.
  • Copy-on-write makes fork cheap but defers the cost; a child that writes widely materialises the full copy later, which is how forking services OOM under load.
  • A zombie is dead and un-reaped — always the parent's bug, unkillable, fixed by making the parent wait() or by killing the parent.
  • An orphan is alive with a dead parent; the kernel re-parents it to init or the nearest subreaper, and it is not a problem.
  • Running an app as PID 1 in a container breaks signals (no default handlers) and leaks zombies — use --init or tini.
  • PGID groups a pipeline into one job, which is why Ctrl-C stops every stage; kill -TERM -PGID is how you stop a process and its children.
  • SIGHUP on terminal disconnect is a session-level mechanism — nohup, setsid, disown and tmux each break that chain differently.
  • /proc/PID answers nearly everything: fd/ replaces lsof, exe reveals processes running deleted binaries after an upgrade, and SigIgn/SigCgt explain why a signal is being ignored.
  • Secrets in environment variables are readable from /proc/PID/environ by the same user and inherited by every child.
  • Always SIGTERM, wait, then SIGKILL — kill -9 skips the program's own flush and cleanup, losing buffered data and leaving disk space unreleased.
