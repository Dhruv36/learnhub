How Unix Is Put Together Foundations

What you'll master: the handful of design decisions that explain almost every Linux behaviour you will ever meet — why "everything is a file" is a statement about a uniform API rather than about files, where the boundary between kernel and userspace actually sits and what crossing it costs, why the shell is an ordinary program with no special powers, how a process is constructed out of exactly three mechanisms, and why a system built from small composable programs ended up outliving every integrated competitor. This is the lesson that makes the other nineteen feel obvious instead of arbitrary. No prerequisites — but everything after this assumes it.

Part 1 — The Kernel/Userspace Split

The single most important line in the system is not in any source file. It is the boundary between kernel mode and user mode, a distinction enforced by the CPU itself. In kernel mode, code may execute any instruction and touch any memory address. In user mode, whole classes of instruction are forbidden and memory access is filtered through page tables the kernel controls. Your program runs in user mode. Always.

This has a consequence that surprises people: your program cannot read a file. It genuinely cannot. It has no instruction available to it that talks to a disk. What it can do is ask the kernel to read a file on its behalf, by executing a special instruction that deliberately traps into kernel mode at a fixed, kernel-chosen entry point. That request is a system call, and it is the only door in the wall.

     ┌──────────────────────────────────────────────┐
     │  USER MODE                                   │
     │                                              │
     │   bash    nginx    python    your program    │
     │     │       │        │           │           │
     │     └───────┴────────┴───────────┘           │
     │                  │                           │
     │        the C library (glibc/musl)            │
     │                  │                           │
     └──────────────────┼───────────────────────────┘
                        │  system call boundary
     ┌──────────────────┼───────────────────────────┐
     │  KERNEL MODE     ▼                           │
     │                                              │
     │  scheduler   VFS   network stack   memory    │
     │      │        │         │            │       │
     │      └────────┴─────────┴────────────┘       │
     │                  │                           │
     │            device drivers                    │
     └──────────────────┼───────────────────────────┘
                        ▼
                    hardware

Count the layers a trivial cat file.txt traverses and the cost model of the whole system falls out. cat calls read() in the C library; the library executes a syscall instruction; the CPU switches privilege level and jumps to the kernel's handler; the kernel's virtual filesystem layer routes to the right filesystem driver; that driver may find the data already in the page cache, or may queue a request to a block device driver and put the process to sleep until the disk answers.

Each of those transitions costs something, and the numbers matter more than the names:

OperationRough costWhat that implies
Ordinary function call~1 nsFree. Never optimise these first.
System call (cached, no I/O)~50–500 nsHundreds of times a function call. Batch them.
Read from page cache~1–10 µsFast because no device is touched at all.
Read from NVMe SSD~100 µs~1000× RAM. This is why caching dominates.
Context switch to another process~1–5 µsPlus cache pollution you cannot see in the number.
🔑 The reason this matters practically. When a program is slow and the CPU is not busy, it is almost always blocked in a system call waiting for something. That single observation is the root of the debugging method in Performance Debugging: don't guess which line is slow, ask the kernel which call the process is sitting in. strace and /proc answer that directly.

Notice too what the diagram does not show: any privileged position for the shell, or for init, or for any particular program. Every box in the user-mode half is the same kind of thing. The shell has no capability that your own program lacks. This is not an accident of implementation — it is the design, and Part 3 shows exactly why it produces such a flexible system.

Part 2 — "Everything Is a File" Is About the API

The slogan is repeated so often that its actual content gets lost. It does not mean everything is stored on disk. It means: the kernel exposes wildly different things behind one small, uniform interface, so that a program written against that interface works with all of them without knowing which it has.

The interface is roughly five calls: open, read, write, close, and the catch-all ioctl. Consider what hides behind them:

What it isExample pathWhat read() actually does
A regular file/etc/hostnameFetches bytes from disk or page cache
A directory/homeReturns name→inode entries (via getdents)
A terminal/dev/pts/3Returns keystrokes from a line discipline
A pipe(no path)Takes bytes from a kernel ring buffer, blocking if empty
A network socket(no path)Pulls bytes off the TCP receive queue
Kernel state/proc/meminfoRuns kernel code that generates text on the spot
A block device/dev/sdaReads raw sectors, bypassing any filesystem
Randomness/dev/urandomReturns bytes from the kernel CSPRNG

The payoff is compositional and it is enormous. Because grep only knows how to read from a file descriptor, it works unchanged on a file, on the output of another program, on a serial port, and on a network connection. Nobody had to write a network-aware grep. The uniformity is what makes the pipeline in Redirection & Pipes possible at all.

/proc is the most striking case, because those files do not exist. There is no meminfo stored anywhere. When you read it, kernel code runs and formats a string into your buffer:

$ cat /proc/self/status | head -4
Name:   cat
Umask:  0022
State:  R (running)
Tgid:   48213

$ ls -l /proc/meminfo
-r--r--r-- 1 root root 0 Aug  7 10:22 /proc/meminfo     # size 0 — nothing is stored

The reported size is zero because there is no content until you ask. This is why you cannot usefully tail -f a proc file, and why tools like free and top are thin wrappers: they open a file, read text, and parse it. You can trivially write your own.

🔑 Where the abstraction leaks, and it leaks by design. Not everything fits five calls, which is why ioctl exists — a deliberate escape hatch meaning "do something device-specific I could not express". Setting a terminal's window size, ejecting a CD, configuring a network interface: all ioctl. It is the honest admission that the uniform-interface idea is 95% right, not 100%. Newer subsystems (like io_uring) are the modern acknowledgement that the classic API is also not always fast enough.

Part 3 — The Shell Is Just a Program

Beginners assume the shell is part of the operating system. It is not. bash is a user-mode program like any other, and everything it does is available to you. Demonstrating that collapses a huge amount of apparent magic.

When you type ls -l /tmp, bash performs a sequence you could write yourself:

1. Read the line              (read() from the terminal)
2. Expand it                  (globs, $VARIABLES, $(subshells), ~)
3. Split into words           → ["ls", "-l", "/tmp"]
4. Search $PATH for "ls"      → /usr/bin/ls
5. fork()                     → a duplicate of bash exists
6. In the child: execve("/usr/bin/ls", ["ls","-l","/tmp"], environ)
7. In the parent: waitpid()   → sleep until the child exits
8. Print the prompt again

Step 6 is the surprising one. execve does not create a process. It replaces the contents of the one that is already running: same process ID, same open file descriptors, but the entire memory image is discarded and replaced with /usr/bin/ls. The child that was a copy of bash a microsecond ago is now ls, and it never returns to being bash.

That separation of "make a new process" (fork) from "run a different program" (execve) is one of Unix's cleverest decisions, because it creates a window between the two where the child is still running the parent's code and can rearrange its own environment. Everything the shell offers lives in that window:

Shell featureWhat happens in the window between fork and exec
ls > out.txtChild opens out.txt, dup2()s it onto fd 1, then execs
ls | wc -lParent makes a pipe; each child wires one end to fd 0 or 1
FOO=bar lsChild sets FOO in its own environment, then execs
nice lsChild lowers its scheduling priority, then execs
sudo ls(setuid binary) changes credentials, then execs

ls is entirely ignorant of all of it. It writes to file descriptor 1 exactly as it always does; the shell already arranged what fd 1 points at. Redirection is not a feature of the programs being redirected. That is why it works with every program ever written, including ones written before the feature existed.

A few commands genuinely cannot be separate programs, and knowing which reveals the boundary:

$ type cd ls echo
cd is a shell builtin
ls is /usr/bin/ls
echo is a shell builtin

$ ls /usr/bin/cd
ls: cannot access '/usr/bin/cd': No such file or directory

cd must be a builtin. A child process changing its own working directory would accomplish nothing — the child exits and the parent shell is unaffected. The same reasoning explains export, ulimit, and exec. If a command needs to modify the shell's own state, it cannot be a child. This is the general rule, and it also explains why a script must be sourced rather than executed if it is meant to set variables in your session.

❌ "The shell runs my program." It suggests the shell supervises execution, which leads to confusion about why a program can outlive its shell, why & works, and why killing a terminal sometimes kills jobs and sometimes does not.

✅ "The shell copies itself, and the copy becomes my program." The relationship is parent/child, and after execve the shell's only remaining involvement is waiting for an exit status. Everything in Signals & Job Control follows from taking this literally.

Part 4 — A Process Is Three Things

Strip away the vocabulary and a Unix process is exactly three components. Every tool in this track inspects, modifies, or isolates one of them.

ComponentWhat it containsWhere you see it
An address spaceCode, heap, stack, mapped files — a private virtual memory map/proc/PID/maps, pmap
A file descriptor tableSmall integers → open files, pipes, sockets, devices/proc/PID/fd/, lsof
Kernel bookkeepingPID, parent, credentials, cwd, signal handlers, limits, cgroup/proc/PID/status, ps
$ ls -l /proc/self/fd
lrwx------ 1 you you 64 Aug  7 10:30 0 -> /dev/pts/2
lrwx------ 1 you you 64 Aug  7 10:30 1 -> /dev/pts/2
lrwx------ 1 you you 64 Aug  7 10:30 2 -> /dev/pts/2
lr-x------ 1 you you 64 Aug  7 10:30 3 -> /proc/48901/fd

$ ls -l /proc/self/fd > /tmp/fds.txt ; head -3 /tmp/fds.txt
lrwx------ 1 you you 64 Aug  7 10:30 0 -> /dev/pts/2
l-wx------ 1 you you 64 Aug  7 10:30 1 -> /tmp/fds.txt      # fd 1 moved
lrwx------ 1 you you 64 Aug  7 10:30 2 -> /dev/pts/2

The second run makes redirection concrete: fd 0 and 2 still point at the terminal, fd 1 now points at the file, and nothing about the program changed. Those three descriptors are conventions, not laws — 0 is standard input, 1 standard output, 2 standard error, purely because every program agrees to it. The kernel merely hands out the lowest unused integer.

Two of the three components explain most container behaviour, which is why Namespaces & cgroups is a natural end to this track: a container is a process whose view of the system (namespaces) and whose resource allowance (cgroups) have been restricted. It is not a lightweight virtual machine. It is one of these three-part processes with different bookkeeping.

Part 5 — Why Small Composable Programs Won

The Unix philosophy is usually recited as slogans. It is more useful as an engineering argument with a cost you can name.

The claim: build small programs that do one thing, communicate in text over a uniform interface, and make no assumptions about who is at the other end. The payoff is that N programs give you roughly N² useful combinations, none of which anyone had to anticipate.

# Nobody designed this. It was assembled at a prompt in ten seconds.
$ grep -h ' 500 ' /var/log/nginx/access.log* \
    | awk '{print $7}' \
    | sort \
    | uniq -c \
    | sort -rn \
    | head -10

Five programs, written decades apart by different people, none aware of the others, answering "which URLs are producing the most 500s?" without a single line of new code. An integrated log-analysis tool would answer this question only if its author had thought of it.

The cost is equally real and worth stating honestly, because pretending otherwise makes the philosophy sound like religion:

BenefitThe price you actually pay
Anything composes with anythingText parsing is fragile — a filename with a space breaks a pipeline
Each tool stays small and testableNo type safety across the boundary; errors surface as garbled output
Tools are independently replaceableSerialising to text and re-parsing is genuinely slow at volume
Works over any byte streamStructured data (JSON) needs new tools like jq bolted on

PowerShell's response was to pipe structured objects instead of text, which eliminates the parsing fragility and imposes a common runtime. That is a legitimate trade, not an obvious improvement. The Unix bet — that a universal lowest common denominator beats a richer format requiring agreement — is what let a 1975 tool interoperate with a 2025 one. Text Processing and find & xargs teach you to get the benefit while defusing the fragility, and the defusing is mostly one habit: -print0 and -0.

Part 6 — Reading the System Instead of Guessing

The practical skill this track builds is the habit of asking the machine rather than recalling folklore. Four questions cover most situations, and each has a direct answer:

QuestionCommandWhat you learn
What is this command?type -a cmdBuiltin, alias, function, or which binary
What is it doing right now?strace -p PIDThe exact syscall it is blocked in
What does it have open?ls -l /proc/PID/fdFiles, sockets, pipes, and leaks
What is the machine doing?vmstat 1, /proc/*Whether it is CPU-bound, I/O-bound, or idle
# A hung process: don't guess, look.
$ cat /proc/48901/wchan ; echo
inet_csk_accept                    # blocked waiting for a TCP connection

$ cat /proc/48901/stack 2>/dev/null | head -3    # kernel stack (needs privileges)
$ ps -o pid,stat,wchan:25,cmd -p 48901
    PID STAT WCHAN                     CMD
  48901 S    inet_csk_accept           ./server

State S means interruptible sleep — the process is waiting, not stuck. The distinction between that and D (uninterruptible sleep, almost always disk or NFS) is one of the highest-value diagnostic facts on the platform, and Processes covers the full state machine.

🔑 The habit that separates competent operators from confident ones. Every claim in this track is verifiable in under a minute at a prompt. When you meet a surprising behaviour, the productive move is not to search for someone's blog post — it is to ask strace, /proc, or type. The system is unusually willing to explain itself, and every lesson here ends with exercises that make you do exactly that.

Interview Questions

Beginner: What is a system call, and why can't a program just read the disk directly?

A system call is a controlled request from a user-mode program to the kernel, executed via a special CPU instruction that switches privilege level and jumps to a fixed, kernel-controlled entry point.

A program cannot touch the disk directly because the CPU enforces the restriction. In user mode, the instructions that talk to hardware are unavailable, and memory access goes through page tables the kernel controls, so a process cannot even see the device registers. This is what makes multi-user systems possible: if any program could read any sector, file permissions would be advisory at best.

Practically, the important consequence is cost. A system call is roughly 50–500 ns against ~1 ns for a function call, so a program that reads one byte at a time can be a hundred times slower than one that reads 64KB at a time, doing the identical work.

Beginner: What does "everything is a file" actually mean?

It means the kernel exposes many different kinds of object — regular files, directories, terminals, pipes, sockets, devices, and live kernel state — behind one small interface: open, read, write, close.

It does not mean everything is stored on disk. /proc/meminfo reports a size of zero because nothing is stored; reading it runs kernel code that formats text on demand.

The payoff is composition. Because grep only knows how to read a file descriptor, it works on a file, a pipe, a serial port, or a network socket without modification. The uniformity is what makes shell pipelines possible, and it is why tools written decades apart still interoperate.

The honest caveat: the abstraction leaks, and ioctl is the leak made official — a catch-all for device-specific operations that don't fit read/write.

Mid: Why does Unix separate fork() from exec() instead of having one "spawn" call?

Because the gap between them is where all the configurability lives. After fork, the child is still running the parent's code and can modify its own environment before being replaced.

In that window the child can: open a file and dup2 it onto fd 1 (redirection); wire up a pipe (pipelines); set environment variables; change working directory; drop privileges; lower scheduling priority; set resource limits; join a cgroup or namespace.

The elegance is that the program being executed needs to know nothing about any of it. ls writes to fd 1 as always; the shell already decided what fd 1 points at. A single spawn() call would need a parameter for every one of those behaviours, and would need extending every time a new one was invented — which is exactly what happened to posix_spawn.

The cost is real: fork must duplicate the parent's address space, which copy-on-write makes cheap but not free — a large process forking frequently pays measurably, which is why posix_spawn and vfork exist for that case.

Mid: Why must cd be a shell builtin, and what else must be for the same reason?

Because the working directory is per-process state. If cd were an external program, the shell would fork a child, the child would change its own working directory, and then exit — leaving the parent shell exactly where it was. The command would be a no-op with extra steps.

The general rule: any command that must modify the shell's own state cannot be a child process. That covers cd, export, ulimit, umask, set, exec, and source.

The same reasoning explains a common frustration: a script that sets environment variables has no effect when executed, because it ran in a child. You must source it, which makes the current shell read the file itself rather than forking.

Note that some builtins exist purely for speed rather than necessity — echo and test both have /usr/bin equivalents, but forking for them would be absurd in a loop. type -a echo shows both.

Senior: A service is consuming no CPU but is unresponsive. Walk through your diagnosis from first principles.

No CPU with no progress means the process is blocked in the kernel. The question is which call, and waiting on what. I'd work outward from the process itself rather than starting with the application.

1. Process state. ps -o pid,stat,wchan:30,cmd -p PID. S is interruptible sleep — a normal wait on I/O, a lock, or a network peer. D is uninterruptible sleep, which in practice means block I/O or a hung network filesystem; a process in D cannot even be killed with SIGKILL, and a pile of them signals a storage problem, not an application one. Z is a zombie — already dead, the parent has not reaped it.

2. The exact call. cat /proc/PID/wchan names the kernel function it is parked in — inet_csk_accept (waiting for a connection) reads very differently from futex_wait (a userspace lock) or io_schedule (disk).

3. Confirm dynamically. strace -p PID. Silence confirms it is blocked rather than spinning; a repeating EAGAIN loop tells a different story. For threads, -f matters — the blocked one may not be the main thread.

4. What it is waiting on. ls -l /proc/PID/fd plus ss -tanp to see socket states. A full receive queue on the peer, or a connection stuck in SYN_SENT, localises the fault to the network or the dependency.

5. Rule out the environment. Descriptor limit reached (/proc/PID/limits versus the count in fd/) presents exactly like a hang, as does a cgroup memory limit causing thrashing rather than an OOM kill. Both are covered in Memory.

The discipline is that each step is an observation, not a hypothesis. I have never found "restart it and see" to be faster than four commands that name the cause.

Senior: The Unix philosophy of small text-based tools is often praised. Argue the other side.

The strongest criticism is that text is an untyped interface, so every pipeline is an undeclared parsing contract that no one checks. A filename containing a space silently breaks a for loop; a log line with an embedded newline corrupts a count; a locale change alters sort order and quietly produces different results. These failures are silent, which is the worst property a failure can have.

Second, it is slow at volume. Serialising structured data to text and re-parsing it at every stage is real CPU work. A pipeline of six tools over gigabytes of logs can be an order of magnitude off what a single program doing the same work would cost.

Third, composability is often overstated in practice. Real pipelines accumulate awk field indices and cut -d delimiters that encode assumptions about upstream formats. Change nginx's log format and a dozen scripts break with no compile-time warning.

PowerShell's object pipeline is the serious counter-design: passing structured objects eliminates parsing entirely and gives you discoverable properties. The cost is that every participant must share a runtime and a type system.

My actual position: the Unix bet was on the lowest common denominator, and it won on longevity — interoperability with tools not yet written, in languages not yet invented, is worth a great deal. But the healthy modern practice is a hybrid. Use structured formats where structure exists (jq, --json flags on modern tools), use -print0 and -0 to make the text path robust, and write a real program when a pipeline exceeds about four stages or needs error handling. Treating the philosophy as doctrine rather than a trade-off is how people end up with unmaintainable 200-character one-liners.

🏋️ Exercises

1 (easy): Prove that a system call is expensive by measuring the same work done in different-sized chunks.
Solution

Create a file and read it with different block sizes, counting syscalls:

$ dd if=/dev/zero of=/tmp/test.bin bs=1M count=64 2>/dev/null

# One byte at a time — 67 million read() calls
$ time dd if=/tmp/test.bin of=/dev/null bs=1 2>/dev/null
real    0m24.8s

# 64KB at a time — 1024 read() calls
$ time dd if=/tmp/test.bin of=/dev/null bs=64K 2>/dev/null
real    0m0.02s

Roughly a thousandfold difference for identical work. Confirm the cause is syscall count rather than disk by counting them directly — the file is in page cache for both runs, so no disk I/O is involved:

$ strace -c -e trace=read dd if=/tmp/test.bin of=/dev/null bs=1 count=100000 2>&1 | tail -4
% time     seconds  usecs/call     calls    errors syscall
100.00    0.041318           0    100000           read

$ strace -c -e trace=read dd if=/tmp/test.bin of=/dev/null bs=64K count=100 2>&1 | tail -4
100.00    0.000212           2       100           read

The lesson generalises: this is exactly why language runtimes buffer I/O, and why a program that writes to a log with an unbuffered stream can be dramatically slower than one that buffers.

2 (easy): Demonstrate that /proc files are generated on demand rather than stored.
Solution 
$ ls -l /proc/meminfo
-r--r--r-- 1 root root 0 Aug  7 10:22 /proc/meminfo      # size 0

$ wc -c /proc/meminfo
1543 /proc/meminfo                                        # but 1543 bytes come out

$ cat /proc/uptime ; sleep 2 ; cat /proc/uptime
4821.33 18234.11
4823.36 18242.07                                          # different every read

A stored file cannot report size 0 and then yield 1543 bytes, and cannot change between two reads with no writer. The kernel formats the text when you call read.

Confirm the filesystem type, which is the real explanation — procfs is a virtual filesystem with no backing store:

$ stat -f -c %T /proc
proc
$ mount | grep ' /proc '
proc on /proc type proc (rw,nosuid,nodev,noexec,relatime)

Practical consequence: tail -f /proc/meminfo does not work as you would hope, and tools like free and top are just parsers over these files. You can replace them with awk whenever you want.

3 (medium): Observe the fork/exec pair directly, and identify where redirection is set up.
Solution 
$ strace -f -e trace=clone,execve,openat,dup2 \
      bash -c 'ls /tmp > /tmp/out.txt' 2>&1 | grep -v ENOENT
execve("/bin/bash", ["bash", "-c", "ls /tmp > /tmp/out.txt"], 0x...) = 0
clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|SIGCHLD) = 51023
[pid 51023] openat(AT_FDCWD, "/tmp/out.txt", O_WRONLY|O_CREAT|O_TRUNC, 0666) = 3
[pid 51023] dup2(3, 1)                  = 1
[pid 51023] execve("/bin/ls", ["ls", "/tmp"], 0x...) = 0

Read the order carefully, because it contains the whole lesson:

  1. clone (the syscall behind fork) creates child PID 51023.
  2. The child — still running bash's code — opens the output file, getting fd 3.
  3. dup2(3, 1) makes fd 1 a copy of fd 3. Standard output now is the file.
  4. Only then does execve replace the child with ls.

ls starts life with fd 1 already pointing at the file and never learns that anything unusual happened. This is precisely why redirection works with every program ever written, including ones predating the feature — the redirected program is not involved.

4 (medium): Write a replacement for free using only /proc, and explain why the "available" figure is the one that matters.
Solution 
$ awk '/^MemTotal|^MemAvailable|^MemFree|^Cached/ {printf "%-14s %8.1f MB\n", $1, $2/1024}' /proc/meminfo
MemTotal:        15845.2 MB
MemFree:           412.7 MB
MemAvailable:    11203.8 MB
Cached:          10982.4 MB

The striking pair is MemFree at 412 MB against MemAvailable at 11.2 GB. Nearly all "used" memory is page cache — file data the kernel keeps because there was no reason not to. It is instantly reclaimable when a process needs memory.

This is why low free memory on Linux is normal and not a problem. Unused RAM is wasted RAM. Monitoring alerts written against MemFree fire constantly and mean nothing; alerts against MemAvailable mean something. That single distinction is one of the most common false alarms in production monitoring.

A closer clone of free's arithmetic:

$ awk '/^MemTotal/{t=$2} /^MemAvailable/{a=$2} END {
    printf "total %.1fG   available %.1fG   really used %.1fG (%.0f%%)\n",
           t/1048576, a/1048576, (t-a)/1048576, 100*(t-a)/t }' /proc/meminfo
total 15.5G   available 10.9G   really used 4.5G (29%)

Memory covers why this matters when the OOM killer gets involved.

5 (hard): A colleague reports that their script "randomly deletes the wrong files". Reproduce the bug from first principles and fix it.
Solution

The near-certain cause is word splitting on filenames containing spaces. Reproduce it deliberately:

$ mkdir -p /tmp/demo && cd /tmp/demo
$ touch "report final.txt" "important.txt"
$ ls
important.txt  report final.txt

$ for f in $(ls *.txt); do echo "would delete: [$f]"; done
would delete: [important.txt]
would delete: [report]
would delete: [final.txt]

Three "files" from two. The shell split ls output on whitespace, so report final.txt became two words. A rm $f here deletes neither — it reports two missing files — but the identical bug with a file named a *.txt or with rm -f in a directory containing a matching name deletes real data.

Fix 1 — use a glob, which never splits:

$ for f in *.txt; do echo "would delete: [$f]"; done
would delete: [important.txt]
would delete: [report final.txt]

Fix 2 — for recursion, use the null separator: NUL is the only byte that cannot appear in a filename, which is precisely why -print0 exists:

$ find . -name '*.txt' -print0 | xargs -0 -I{} echo "would delete: [{}]"
would delete: [./important.txt]
would delete: [./report final.txt]

Fix 3 — let find do it, avoiding the pipeline entirely:

$ find . -name '*.txt' -exec rm -- {} +

Three habits prevent the entire class of bug: never parse ls; always quote "$var"; use -- before filename arguments so a file named -rf is not read as a flag. Shell Scripting That Survives makes these systematic, and find & xargs covers the NUL-separated pipeline in depth.

6 (hard): Design a diagnostic runbook for "the application is slow", using only the concepts in this lesson. State what each step rules out.
Solution

The goal is to bisect the stack, eliminating whole layers rather than guessing at code. Each step must produce a decision, not just a number.

Step 1 — is the machine busy at all?

$ vmstat 1 5
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa
 1  3      0 412700  88320 1098240    0    0  4212     8 1820 3410  4  3 41 52

Read three columns. r (runnable) high with us high means CPU-bound — a code problem. b (blocked) high with wa high, as here, means I/O-bound — stop looking at the application's CPU profile entirely. si/so non-zero means swapping, which makes every other number meaningless until fixed.

Here wa is 52% and b is 3: this is I/O. That single line has eliminated the application logic as the primary suspect.

Step 2 — which processes are blocked, and on what?

$ ps -eo pid,stat,wchan:25,cmd | awk '$2 ~ /^D/'
  51230 D    io_schedule               /usr/bin/postgres: writer

D state confirms uninterruptible disk sleep. This is not an application that needs restarting — it is storage that cannot keep up, or a device with errors.

Step 3 — is it the device or the volume of requests?

$ iostat -x 1 3 | awk '/^Device|nvme0n1/'
Device   r/s     w/s   rkB/s   wkB/s  %util  aqu-sz  r_await  w_await
nvme0n1  1240.0  88.0  49600   3520   99.2    14.8    11.20     8.40

%util at 99 with queue depth 14.8 means the device is saturated. High r/s with modest rkB/s means many small random reads — the signature of cache misses, which points back at memory sizing rather than the disk being faulty.

Step 4 — confirm the memory hypothesis.

$ awk '/MemAvailable|^Cached/ {print}' /proc/meminfo
MemAvailable:    1203848 kB
Cached:          1098240 kB

Only 1.2 GB available against a working set clearly larger — the page cache is being thrashed, so reads that should be memory hits are becoming disk reads. The chain is now complete and evidenced: insufficient RAM → cache misses → random read storm → device saturation → D-state processes → application latency.

What each step ruled out: step 1 eliminated CPU and the application's own code; step 2 eliminated a hung process needing a restart; step 3 eliminated a failing device; step 4 identified the actual cause. The fix is more memory or a smaller working set — restarting the application would have "worked" briefly and taught nothing.

The general principle: never start at the layer you are most familiar with. Start at the top with a whole-machine view and bisect downward. Performance Debugging formalises this as the USE method.

🎯 Key Takeaways

  • The CPU enforces a kernel/user split; your program cannot touch hardware and must ask via system calls — the only door in the wall.
  • A syscall costs 100–1000× a function call, which is why buffering exists and why byte-at-a-time I/O is catastrophically slow.
  • "Everything is a file" is a claim about a uniform five-call API, not about disk storage — /proc files report size 0 and are generated on read.
  • ioctl is the official admission that the file abstraction is 95% right, not 100%.
  • The shell is an ordinary user-mode program; it has no capability you lack, and you can replace it.
  • fork then exec are separate on purpose — the gap between them is where redirection, pipes, env vars and privilege drops happen.
  • Redirection is a property of the file descriptor table, not of the program being redirected, which is why it works with every program ever written.
  • Any command that must change the shell's own state (cd, export, ulimit) must be a builtin, because a child's changes die with it.
  • A process is exactly three things: an address space, a file descriptor table, and kernel bookkeeping — containers restrict the latter two rather than virtualising anything.
  • Small composable tools buy you N² unanticipated combinations; the price is untyped text parsing, and -print0/-0 is how you pay less of it.
  • When something is slow with no CPU use, it is blocked in a syscall — ask /proc/PID/wchan and strace rather than guessing.
  • Low MemFree is normal and healthy; MemAvailable is the number worth alerting on.
