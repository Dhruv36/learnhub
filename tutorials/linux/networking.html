Networking From the Socket Up The Running System

What you'll master: what a socket actually is as a file descriptor, how to find which process owns a port and why netstat is the wrong tool now, the connection lifecycle including the two backlog queues that silently drop traffic, why TIME_WAIT sockets pile up and when that genuinely matters, how DNS resolution really happens on Linux (not via /etc/resolv.conf alone), and a layered method for debugging "it can't connect" that reaches an answer instead of guessing. Prerequisites: Processes, fork & exec and System Calls & strace.

Part 1 — A Socket Is a File Descriptor

Unix's central abstraction holds here too: a network connection is a file descriptor. The same read, write, and close calls work on it, which is why redirection and pipes compose with network tools at all.

$ ls -l /proc/$(pgrep -o nginx)/fd/ | head -6
lrwx------ 1 root root 64 Aug 10 09:14 0 -> /dev/null
lrwx------ 1 root root 64 Aug 10 09:14 3 -> 'socket:[482913]'    # listening socket
lrwx------ 1 root root 64 Aug 10 09:14 8 -> 'socket:[483204]'    # a client connection

The number in brackets is the socket's inode, and it is the join key between "which process" and "which connection" — exactly how ss -p attributes a connection to a PID.

Creating a TCP server is four syscalls, and knowing them makes the failure modes obvious:

socket()   → create an unbound endpoint, get an fd
bind()     → claim an address:port          ← fails with EADDRINUSE
listen()   → mark it passive, create the queues
accept()   → pull one completed connection off the queue, get a NEW fd
Socket familyAddress looks likeUsed for
AF_INET / AF_INET610.0.1.5:8080TCP/UDP over the network
AF_UNIX/run/docker.sockLocal IPC — faster, and filesystem permissions apply
AF_NETLINKKernel subsystem idTalking to the kernel (ss, ip use this)
AF_PACKETRaw framestcpdump, needs CAP_NET_RAW
🔑 Unix sockets are the right default for local communication. They skip the entire TCP/IP stack — no checksums, no loopback routing, no port exhaustion — and they are protected by ordinary file permissions rather than by hoping nothing else on the host connects. A database on the same machine reached over 127.0.0.1:5432 is measurably slower and less secure than the same database reached over /var/run/postgresql/.s.PGSQL.5432.

Part 2 — Seeing What Is Connected

ss replaced netstat because it reads socket state from netlink rather than parsing /proc/net/tcp line by line — on a box with 100,000 connections that is the difference between instant and unusable.

$ ss -tlnp
State  Recv-Q Send-Q  Local Address:Port  Peer Address:Port  Process
LISTEN 0      511           0.0.0.0:80         0.0.0.0:*      users:(("nginx",pid=1204,fd=6))
LISTEN 0      4096        127.0.0.1:5432       0.0.0.0:*      users:(("postgres",pid=980,fd=5))
LISTEN 0      128             [::1]:631            [::]:*      users:(("cupsd",pid=742,fd=8))
FlagMeaning
-t / -u / -xTCP / UDP / Unix sockets
-lListening only
-nNumeric — do not resolve names (much faster, and honest)
-pShow the owning process (needs root for others' sockets)
-sSummary counts by state
-iInternal TCP info: cwnd, rtt, retransmits

The bind address is a security boundary, and the most commonly misread field here. 0.0.0.0:80 means every interface — reachable from the network. 127.0.0.1:5432 means loopback only — unreachable from outside the host regardless of firewall rules:

$ ss -tlnp | awk '$4 ~ /^0\.0\.0\.0|^\[::\]/ {print "EXPOSED:", $4, $6}'
EXPOSED: 0.0.0.0:80 users:(("nginx",pid=1204,fd=6))
EXPOSED: 0.0.0.0:9200 users:(("java",pid=3310,fd=112))     # Elasticsearch on the public interface

That second line is how unauthenticated databases end up on the internet. Auditing bind addresses is a one-line check that finds a class of serious mistakes.

ss's filter language answers real questions directly:

$ ss -tn state established '( dport = :443 or sport = :443 )' | head
$ ss -tn state time-wait | wc -l                      # how many TIME_WAIT
$ ss -tn '( sport = :80 )' dst 10.0.0.0/8             # who from the internal network
$ ss -tni dst 10.0.1.7 | grep -oE 'rtt:[0-9.]+/[0-9.]+|retrans:[0-9/]+'
rtt:0.412/0.108  retrans:0/3

Part 3 — The Connection Lifecycle and Its Queues

TCP's state machine is where most production networking bugs live. Two states matter far more than the rest, and two queues sit behind listen() that most people never learn about until they drop traffic.

  Client                          Server
  ------                          ------
  SYN         ────────────────►   (goes into the SYN queue)
              ◄──────────────── SYN-ACK
  ACK         ────────────────►   (moves to the ACCEPT queue)
                                  accept() pulls it off  →  ESTABLISHED
  ...data...
  FIN         ────────────────►
              ◄──────────────── ACK
              ◄──────────────── FIN
  ACK         ────────────────►   the side that closed FIRST enters TIME_WAIT (60s)
QueueHoldsSized byOverflow symptom
SYN queueHalf-open connections awaiting the final ACKnet.ipv4.tcp_max_syn_backlogSYNs dropped; clients see timeouts
Accept queueCompleted connections waiting for accept()min(listen() backlog, net.core.somaxconn)Connections dropped or reset after the handshake

The accept queue is the one that catches people out: the handshake completed, so the client believes it is connected, and then the request hangs or resets. The application never saw it, because the application was too slow to call accept().

$ ss -tln
State  Recv-Q Send-Q  Local Address:Port
LISTEN 129    128           0.0.0.0:8080
       ^^^    ^^^
   queued     max         Recv-Q at the limit = overflowing right now

$ nstat -az | grep -E 'ListenOverflows|ListenDrops'
TcpExtListenOverflows           4821    0.0        # every one of these is a dropped connection
TcpExtListenDrops               4821    0.0

Fixing it requires both the kernel ceiling and the application's own argument — raising only somaxconn does nothing if the app passes listen(fd, 128):

$ sudo sysctl -w net.core.somaxconn=4096
$ sudo sysctl -w net.ipv4.tcp_max_syn_backlog=8192
# and in the app: listen(fd, 4096) / nginx: listen 80 backlog=4096; / gunicorn: --backlog 4096

❌ "We're dropping connections under load, let's raise the backlog." A deeper queue does not make the application faster — it makes the wait longer before the same failure. Clients that would have been refused immediately now time out after 30 seconds, which is worse for them and hides the signal from you.

✅ Treat a full accept queue as a symptom of slow accepting. The queue exists to absorb bursts, not sustained overload. If Recv-Q sits at the limit continuously, the fix is more workers, faster request handling, or shedding load at the edge. Raise the backlog to survive a spike; raise capacity to survive traffic.

Part 4 — TIME_WAIT and Port Exhaustion

Thousands of TIME_WAIT sockets look alarming and are usually harmless. Knowing when they are not harmless is the actual skill.

$ ss -s
Total: 8214
TCP:   7801 (estab 412, closed 7102, orphaned 3, timewait 7098)

TIME_WAIT lasts 2×MSL (60 seconds on Linux) and exists for two real reasons: to absorb delayed duplicate packets so they cannot be delivered to a new connection reusing the same four-tuple, and to ensure the final ACK can be retransmitted if lost.

Where TIME_WAIT sitsConsumesActually a problem?
Server side (server closes first)Memory only — the port stays listeningRarely — a few hundred KB for thousands
Client side (outbound connections)An ephemeral port per socketYes — this is what exhausts ports

Port exhaustion is specific: outbound connections to the same destination draw from the ephemeral range, and the four-tuple must be unique. About 28,000 ports at 60 seconds each caps you near 470 new connections per second to a single destination.

$ cat /proc/sys/net/ipv4/ip_local_port_range
32768   60999                                  # 28,231 ports

$ ss -tn state time-wait dst 10.0.1.50 | wc -l
27904                                          # nearly exhausted against ONE host
$ dmesg | tail -2
TCP: request_sock_TCP: Possible SYN flooding
net_ratelimit: 82 callbacks suppressed
FixWhat it doesCaveat
Connection pooling / keep-aliveReuses connections instead of creating themThe real fix — everything else is mitigation
net.ipv4.tcp_tw_reuse=1Reuse TIME_WAIT sockets for new outbound connectionsSafe with timestamps on; client-side only
Widen ip_local_port_rangeMore ephemeral portsBuys ~2×, delays the wall
SO_REUSEADDRLets a server rebind a port in TIME_WAITSolves restart EADDRINUSE, not exhaustion
tcp_tw_recycle—Removed in 4.12; broke NAT badly. Never use

The reason SO_REUSEADDR exists is worth knowing separately: it is why a restarted server can bind immediately instead of waiting 60 seconds for its old connections to leave TIME_WAIT — the classic "Address already in use" on redeploy.

Part 5 — DNS Resolution Is Not Just resolv.conf

"DNS is broken" is frequently misdiagnosed because dig and the application resolve names through completely different paths. dig talks to a DNS server directly; applications go through the C library's Name Service Switch.

$ cat /etc/nsswitch.conf | grep hosts
hosts:  files mdns4_minimal [NOTFOUND=return] dns myhostname
        ^^^^^                                  ^^^
     /etc/hosts first                    only then DNS

$ getent hosts api.internal        # follows nsswitch — what the application sees
10.0.1.50       api.internal
$ dig +short api.internal          # queries DNS directly — bypasses /etc/hosts
                                   # (empty — the answer came from /etc/hosts)
🔑 Use getent hosts, not dig, to reproduce what an application sees. dig ignores /etc/hosts, ignores nsswitch ordering, ignores systemd-resolved's per-link routing, and ignores the search domains that turn api into api.svc.cluster.local. The number of hours lost to "dig works but the app can't resolve it" is enormous, and the cause is almost always one of those four.

On systemd hosts /etc/resolv.conf is usually a symlink to a stub that points at 127.0.0.53, and the real configuration lives elsewhere:

$ ls -l /etc/resolv.conf
lrwxrwxrwx 1 root root 39 → ../run/systemd/resolve/stub-resolv.conf
$ resolvectl status | grep -A3 'Link 2'
Link 2 (eth0)
      Current Scopes: DNS
       DNS Servers: 10.0.0.2 10.0.0.3
        DNS Domain: internal.example.com
$ resolvectl query api.internal            # includes cache state and which link answered

Search domains multiply queries, and the ndots setting decides when. In Kubernetes the default ndots:5 means any name with fewer than five dots is tried against every search domain first — so api.example.com generates four failing lookups before the correct one:

$ cat /etc/resolv.conf
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

# api.example.com (2 dots < 5) is tried as:
#   api.example.com.default.svc.cluster.local   NXDOMAIN
#   api.example.com.svc.cluster.local           NXDOMAIN
#   api.example.com.cluster.local               NXDOMAIN
#   api.example.com                             ✓

The fix is a trailing dot — api.example.com. is fully qualified and skips the search list entirely — or lowering ndots for that pod.

Part 6 — Debugging "It Can't Connect", Layer by Layer

The productive approach is to walk the layers in order and stop at the first failure, rather than guessing from symptoms. Each step has one command and one unambiguous answer.

1. Does the name resolve?        getent hosts api.internal
2. Is there a route?             ip route get 10.0.1.50
3. Is the host reachable?        ping -c2 10.0.1.50   (ICMP may be blocked — not proof)
4. Is the port open?             nc -zv 10.0.1.50 8080  /  timeout 2 bash -c '</dev/tcp/10.0.1.50/8080'
5. Is anything listening there?  ss -tlnp | grep 8080          (on the server)
6. Is it bound to the right IP?  127.0.0.1 vs 0.0.0.0
7. Is a firewall dropping it?    sudo nft list ruleset / iptables -L -n -v
8. What does the wire say?       sudo tcpdump -ni any port 8080
SymptomAlmost always means
Connection refused (instant)Reached the host; nothing is listening on that port — RST returned
Connection timed outPackets dropped silently — firewall, security group, or wrong route
No route to hostRouting table has no path, or ARP failed on the local segment
Name or service not knownDNS/nsswitch — never reached the network at all
Connection reset by peerConnected, then the other side sent RST — app crash, protocol mismatch, or accept-queue overflow

The refused-versus-timeout distinction alone eliminates half the search space: refused proves packets reached the host and came back, so DNS, routing, and firewall are all fine, and the problem is the service. Timeout proves nothing came back, so the problem is between you and the process.

$ sudo tcpdump -ni any 'tcp port 8080 and tcp[tcpflags] & (tcp-syn|tcp-rst) != 0' -c 6
09:41:02 IP 10.0.2.11.51234 > 10.0.1.50.8080: Flags [S], seq 918273
09:41:03 IP 10.0.2.11.51234 > 10.0.1.50.8080: Flags [S], seq 918273    # retry, no answer
09:41:05 IP 10.0.2.11.51234 > 10.0.1.50.8080: Flags [S], seq 918273    # dropped, not refused

SYNs going out with nothing coming back is a silent drop — a firewall or security group, never a stopped service, because a stopped service produces an immediate RST.

Interview Questions

Beginner: How do you find which process is using port 8080?

ss with process attribution:

$ sudo ss -tlnp | grep :8080
LISTEN 0 511 0.0.0.0:8080 0.0.0.0:* users:(("java",pid=3310,fd=112))

-t TCP, -l listening, -n numeric (skips DNS lookups, much faster), -p process. Root is needed to see processes you do not own. sudo lsof -i :8080 gives the same answer from the file-descriptor side.

Read the local address, not just the port. 0.0.0.0:8080 is bound to every interface and reachable from the network; 127.0.0.1:8080 is loopback-only and cannot be reached from another host no matter what the firewall says. That distinction is the cause of both "why can't I connect from outside" and, more seriously, accidentally exposed internal services.

netstat does the same job but parses /proc/net/tcp line by line, so on a host with many connections it takes minutes where ss takes milliseconds — ss reads the same data over netlink.

Beginner: What is the difference between "connection refused" and "connection timed out"?

They fail at different layers, and the distinction narrows the search immediately.

Connection refused is instant. Your SYN reached the host, and the host's kernel replied with a RST because nothing was listening on that port. That single fact proves DNS resolved, routing works, the host is up, and no firewall is dropping traffic — the problem is that the service is not running or is bound to a different address.

Connection timed out takes seconds. Your SYN went out and nothing came back at all. The packet is being dropped silently, which is what firewalls, security groups, and network ACLs do by design — a REJECT rule would produce "refused" instead.

$ nc -zv host 8080
nc: connect to host port 8080 (tcp) failed: Connection refused    # service problem

$ nc -zv host 8080
nc: connect to host port 8080 (tcp) failed: Connection timed out  # network problem

Confirming on the wire removes any doubt: repeated SYNs with no response is a drop, whereas an immediate Flags [R.] coming back is a refusal:

$ sudo tcpdump -ni any 'port 8080'

The related third case is "connection reset by peer" mid-stream, which means the connection was established and then torn down — an application crash, a protocol mismatch, or an accept-queue overflow.

Mid: A server has 30,000 sockets in TIME_WAIT. Is that a problem?

It depends entirely on which side is closing the connection, and that is the first thing I would determine.

TIME_WAIT is entered by whichever side closes first, and lasts 60 seconds on Linux. It exists so that delayed duplicate packets from the old connection cannot be delivered to a new one reusing the same four-tuple, and so the final ACK can be retransmitted.

Server-side TIME_WAIT is almost always harmless. The listening port is unaffected; each socket costs a small amount of memory. 30,000 of them is a few megabytes and a sign of high throughput, not a fault.

Client-side TIME_WAIT is the real concern, because each one holds an ephemeral port:

$ ss -tn state time-wait dst 10.0.1.50 | wc -l
27904
$ cat /proc/sys/net/ipv4/ip_local_port_range
32768   60999                # only 28,231 available — nearly exhausted

Since the four-tuple must be unique, roughly 28,000 ports over a 60-second window caps you near 470 new connections per second to a single destination. Beyond that, connections fail with EADDRNOTAVAIL.

The fix is connection reuse, not tuning. HTTP keep-alive or a connection pool eliminates the churn entirely and is the only change that addresses the cause. tcp_tw_reuse=1 is a safe mitigation for outbound connections when timestamps are enabled; widening the port range buys perhaps 2×. tcp_tw_recycle is not an option — it broke clients behind NAT and was removed in kernel 4.12.

I would also check whether the server should be closing first at all. For HTTP, letting the client close moves the TIME_WAIT burden to the many clients rather than the one server.

Mid: What are the SYN queue and the accept queue, and what happens when they overflow?

listen() creates two distinct queues, and connections move through both.

The SYN queue holds half-open connections: a SYN arrived, SYN-ACK was sent, the final ACK has not come back. Sized by net.ipv4.tcp_max_syn_backlog. Overflow means SYNs are dropped and clients see timeouts — this is also what a SYN flood attacks, which is why SYN cookies exist as a fallback.

The accept queue holds fully established connections waiting for the application to call accept(). Sized by min(backlog argument, net.core.somaxconn).

Accept-queue overflow is the nastier failure because the handshake already completed — the client believes it is connected, then the request hangs or is reset. The application logs show nothing, because the application never received the connection:

$ ss -tln
State  Recv-Q Send-Q Local Address:Port
LISTEN 129    128          0.0.0.0:8080     # Recv-Q at Send-Q = overflowing

$ nstat -az | grep ListenOverflows
TcpExtListenOverflows    4821    0.0        # each one is a dropped connection

Both limits must be raised together — somaxconn is only a ceiling, and the application's own listen(fd, backlog) argument still applies:

$ sudo sysctl -w net.core.somaxconn=4096
# nginx: listen 80 backlog=4096;   gunicorn: --backlog 4096

But I would treat sustained overflow as a capacity problem rather than a tuning one. The queue absorbs bursts; if it is permanently full, the application is not accepting fast enough, and a deeper queue only converts fast failures into slow ones — which is worse for clients and hides the signal.

Senior: An application intermittently fails to resolve a hostname, but dig always works. Diagnose it.

The premise contains the answer: dig and the application resolve through different code paths, so "dig works" tells you almost nothing about what the application does.

1. Reproduce what the application actually sees. dig queries a DNS server directly; the application uses glibc's resolver, which follows /etc/nsswitch.conf:

$ getent hosts api.internal          # honours /etc/hosts, nsswitch, search domains
$ grep hosts /etc/nsswitch.conf
hosts: files mdns4_minimal [NOTFOUND=return] dns myhostname

Note [NOTFOUND=return]: if mDNS returns NOTFOUND, resolution stops and DNS is never consulted. That alone produces intermittent failures that dig can never reproduce.

2. Check for a stub resolver in between. On systemd hosts /etc/resolv.conf usually points at 127.0.0.53, so the real per-link configuration and cache live in systemd-resolved:

$ resolvectl status
$ resolvectl query api.internal      # shows cache hits and which link answered
$ resolvectl statistics              # cache hit rate, failed transactions

3. Consider search domains and ndots. With Kubernetes' default ndots:5, a name with fewer than five dots is tried against every search domain first. That is four extra queries per lookup, quadrupling DNS load and creating timeouts under pressure — while dig api.example.com (absolute) does exactly one.

4. Look for the intermittency's cause specifically. Intermittent means a rate or timing effect:

  • UDP DNS responses over 512 bytes truncating, forcing a TCP retry that a firewall blocks
  • Two nameservers where one is unhealthy — glibc tries them in order with a 5-second timeout by default
  • Conntrack table full on the DNS path, dropping UDP replies
  • The classic Linux DNS race: parallel A and AAAA queries over one socket, where one response can be dropped by conntrack (options single-request-reopen is the historical workaround)

5. Capture the evidence rather than inferring it:

$ sudo tcpdump -ni any port 53 -c 40
$ strace -f -e trace=network,openat -p $(pgrep -o myapp) 2>&1 | grep -E 'resolv|53'

The strace is decisive: it shows exactly which files the resolver opened and which servers it contacted, which settles the question of whether the application is even reading the config you think it is. Cached negative results and a container's own /etc/resolv.conf differing from the host's are both common findings at this step.

6. Fix at the right level. Timeouts and retries (options timeout:1 attempts:2) reduce the blast radius; a local caching resolver such as NodeLocal DNSCache removes most of the load; and applications that cache DNS themselves need their TTL handling checked, since a JVM caching forever is its own separate outage.

Senior: A service handles 5,000 req/s fine but collapses at 8,000. Walk through diagnosing the network layer.

A cliff rather than a gradual slope means a limit was hit, not that everything got proportionally slower. I would find the limit rather than tune broadly.

1. Check the accept queue first — it produces exactly this shape, because it absorbs bursts until it cannot:

$ ss -tln | grep :8080
LISTEN 511 511 0.0.0.0:8080          # Recv-Q pinned at the maximum
$ nstat -az | grep -E 'ListenOverflows|ListenDrops|TCPBacklogDrop'
TcpExtListenOverflows    18402

A rising counter means connections are being dropped after a successful handshake — the client sees a hang or reset while the application logs nothing at all.

2. Check file descriptor limits, the other classic hard cliff:

$ cat /proc/$(pgrep -o myapp)/limits | grep 'open files'
Max open files            1024      4096
$ ls /proc/$(pgrep -o myapp)/fd | wc -l
1021                                        # at the limit
$ dmesg | grep -i 'too many open files'

EMFILE on accept() is particularly nasty: the connection stays in the queue, so the server spins retrying and burns CPU while serving nothing.

3. Check conntrack, which silently drops packets when full and is invisible unless you look:

$ sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max
net.netfilter.nf_conntrack_count = 262144
net.netfilter.nf_conntrack_max = 262144
$ dmesg | grep -i 'conntrack table full'

4. Check ephemeral ports on the outbound side. If this service calls a database or an upstream API, it is a client too, and 8,000 req/s without pooling exhausts ports against a single destination:

$ ss -tn state time-wait | wc -l
28104
$ nstat -az | grep -E 'TcpExtTCPTimeWaitOverflow|CurrEstab'

5. Check retransmits and the softirq path to rule out the network itself and single-CPU packet processing:

$ nstat -az | grep -E 'RetransSegs|OutSegs'
$ mpstat -P ALL 1 3 | awk '$NF != "idle" && $6 > 20'      # %soft high on one core?
$ ethtool -S eth0 | grep -iE 'drop|miss|error'

A single core at 100% %soft while others idle means interrupts are not being spread — RSS or RPS configuration, and a genuine ceiling regardless of application speed.

6. Form the conclusion from which counter moved. Each of these produces the same user-visible symptom and has a completely different fix: backlog overflow means capacity or worker count, EMFILE means raising LimitNOFILE, conntrack means raising the table or bypassing it with NOTRACK, port exhaustion means connection pooling, and softirq saturation means NIC tuning. Tuning all five because the symptom looked like "the network" is how people end up with a host full of sysctls nobody can justify.

I would then verify by load-testing back past 8,000 with the one identified fix applied, confirming the specific counter stops rising — a fix that is not tied to a moving counter is a guess.

2 (easy): Build a TCP server with nc and observe the connection lifecycle from both sides.
Solution 
$ nc -l 9000 &
[1] 64200
$ ss -tlnp | grep 9000
LISTEN 0 1 0.0.0.0:9000 0.0.0.0:* users:(("nc",pid=64200,fd=3))

Note Send-Q 1 — nc requests a backlog of exactly one connection.

Connect and watch the state change:

$ exec 3<>/dev/tcp/127.0.0.1/9000        # bash opens a TCP socket as fd 3

ESTAB 0 0 127.0.0.1:52418 127.0.0.1:9000 users:(("bash",pid=64310,fd=3))
ESTAB 0 0 127.0.0.1:9000  127.0.0.1:52418 users:(("nc",pid=64200,fd=4))

Two entries — one per endpoint. Note nc's connection is fd 4: accept() returned a new descriptor while fd 3 keeps listening.

Send data through the file descriptor:

$ echo "hello over TCP" >&3
# the nc terminal prints: hello over TCP

$ exec 3<&-                              # close the client side
$ ss -tan | grep 9000
TIME-WAIT 0 0 127.0.0.1:52418 127.0.0.1:9000
$ sleep 60; ss -tan | grep 9000          # gone after 2*MSL

$ strace -f -e trace=socket,bind,listen,accept4,read,write nc -l 9001 2>&1 | head -8
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP) = 3
bind(3, {sa_family=AF_INET, sin_port=htons(9001), ...}, 16) = 0
listen(3, 1)                            = 0
accept4(3, ...)                         = 4        # a new fd for the connection
read(4, "hi\n", 8192)                   = 3        # ordinary read(), on a socket

read and write — the same calls that work on files — which is precisely why shell redirection works with network endpoints.

3 (medium): Overflow an accept queue deliberately and observe the dropped connections.
Solution

Write a server that listens with a tiny backlog and never accepts:

$ cat > /tmp/slow_server.py <<'EOF'
import socket, time
s = socket.socket()
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(('127.0.0.1', 9100))
s.listen(2)                       # backlog of only 2
print("listening, not accepting", flush=True)
time.sleep(120)                   # deliberately never call accept()
EOF
$ python3 /tmp/slow_server.py &

Record the baseline counter, then flood it:

$ nstat -az TcpExtListenOverflows
TcpExtListenOverflows           12      0.0
$ for i in $(seq 1 40); do (timeout 3 bash -c 'exec 3<>/dev/tcp/127.0.0.1/9100; sleep 3' &) ; done
$ sleep 2

The queue is visibly full:

$ ss -tln | grep 9100
LISTEN 3 2 127.0.0.1:9100 0.0.0.0:*
       ^ ^
    queued(3) exceeds max(2)

And connections are being dropped:

$ nstat -az | grep -E 'ListenOverflows|ListenDrops'
TcpExtListenOverflows          47      0.0        # 35 new drops
TcpExtListenDrops              47      0.0

The critical observation — the clients think they connected:

$ ss -tn dst 127.0.0.1:9100 | head -4
ESTAB 0 0 127.0.0.1:41208 127.0.0.1:9100
ESTAB 0 0 127.0.0.1:41210 127.0.0.1:9100

The handshake completed from the client's point of view, but the server's application never saw these. They hang until timeout or get reset. This is why the failure is so hard to diagnose from application logs — there is nothing to log.

Compare with a properly-sized listener:

$ sed -i 's/s.listen(2)/s.listen(128)/' /tmp/slow_server.py
$ kill %1; python3 /tmp/slow_server.py &
$ for i in $(seq 1 40); do (timeout 3 bash -c 'exec 3<>/dev/tcp/127.0.0.1/9100; sleep 3' &) ; done
$ sleep 2; ss -tln | grep 9100
LISTEN 40 128 127.0.0.1:9100          # queued but within limits, nothing dropped
$ nstat -az TcpExtListenOverflows      # counter unchanged

The lesson to carry: Recv-Q on a LISTEN socket is the depth of the accept queue, and ListenOverflows incrementing is proof of dropped connections that no application log will ever mention.

Cleanup: kill %1; rm /tmp/slow_server.py.

4 (medium): Trace exactly how a hostname is resolved and prove dig and the application differ.
Solution

1. Add a hosts entry that DNS does not know about:

$ echo "203.0.113.99  test.example.invalid" | sudo tee -a /etc/hosts

2. The two tools disagree immediately:

$ getent hosts test.example.invalid
203.0.113.99    test.example.invalid          # what the application sees

$ dig +short test.example.invalid
                                              # nothing — dig skips /etc/hosts
$ dig test.example.invalid | grep -E 'status:'
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN

This one difference accounts for an enormous amount of wasted debugging time.

3. Prove it by watching the syscalls — the resolver's file access is visible:

$ strace -f -e trace=openat,connect getent hosts test.example.invalid 2>&1 | grep -E 'hosts|nsswitch|resolv|connect'
openat(AT_FDCWD, "/etc/nsswitch.conf", O_RDONLY|O_CLOEXEC) = 3
openat(AT_FDCWD, "/etc/hosts", O_RDONLY|O_CLOEXEC) = 3
                                              # no connect() at all — never touched the network

Compare with a name only DNS knows:

$ strace -f -e trace=openat,connect,sendto getent hosts example.com 2>&1 | grep -E 'resolv|connect|sendto' | head -4
openat(AT_FDCWD, "/etc/resolv.conf", O_RDONLY|O_CLOEXEC) = 4
connect(4, {sa_family=AF_INET, sin_port=htons(53), sin_addr=inet_addr("127.0.0.53")}, 16) = 0
sendto(4, "\x8a\x1f\x01\x00\x00\x01...", 40, MSG_NOSIGNAL, NULL, 0) = 40

Now it reads resolv.conf and sends UDP to port 53.

4. Inspect the nsswitch order that governs all of this:

$ grep '^hosts' /etc/nsswitch.conf
hosts: files mdns4_minimal [NOTFOUND=return] dns myhostname

[NOTFOUND=return] means that if mDNS answers NOTFOUND, resolution stops and DNS is never tried — a real source of intermittent failures that dig can never reproduce.

5. Watch the search-domain expansion that ndots controls:

$ sudo tcpdump -ni any port 53 -c 6 &
$ getent hosts api 2>/dev/null
IP 10.0.2.11.42311 > 10.0.0.2.53: A? api.internal.example.com. (42)
IP 10.0.2.11.42311 > 10.0.0.2.53: A? api. (22)

Two queries for one name. In Kubernetes with ndots:5 this becomes four or five, which is why a trailing dot (api.example.com.) is a genuine optimisation — it marks the name fully qualified and skips the search list.

Cleanup: sudo sed -i '/test.example.invalid/d' /etc/hosts.

5 (hard): Exhaust ephemeral ports and demonstrate that connection pooling fixes it.
Solution

1. Shrink the ephemeral range so exhaustion happens in seconds:

$ cat /proc/sys/net/ipv4/ip_local_port_range
32768   60999
$ sudo sysctl -w net.ipv4.ip_local_port_range="60000 60100"    # only 101 ports
$ python3 -m http.server 9200 --bind 127.0.0.1 &>/dev/null &

2. Churn connections — a new one per request, no reuse:

$ python3 - <<'EOF'
import socket, time
ok = fail = 0
t0 = time.time()
for i in range(400):
    try:
        s = socket.create_connection(('127.0.0.1', 9200), timeout=1)
        s.sendall(b'GET / HTTP/1.0\r\n\r\n'); s.recv(100)
        s.close()                       # client closes first → TIME_WAIT here
        ok += 1
    except OSError as e:
        fail += 1
        if fail == 1: print("first failure at request", i, "->", e)
print(f"ok={ok} fail={fail} in {time.time()-t0:.1f}s")
EOF
first failure at request 103 -> [Errno 99] Cannot assign requested address
ok=103 fail=297 in 2.4s

EADDRNOTAVAIL — no ephemeral port is free, because all 101 are in TIME_WAIT.

3. Confirm the cause:

$ ss -tn state time-wait dst 127.0.0.1:9200 | wc -l
101
$ ss -tan sport ge :60000 sport le :60100 | awk 'NR>1{print $1}' | sort | uniq -c
    101 TIME-WAIT

4. Now reuse a single connection — the actual fix:

$ python3 - <<'EOF'
import http.client, time
t0 = time.time()
conn = http.client.HTTPConnection('127.0.0.1', 9200)   # ONE connection, kept alive
ok = 0
for i in range(400):
    conn.request('GET', '/'); conn.getresponse().read(); ok += 1
print(f"ok={ok} in {time.time()-t0:.1f}s, ports used: 1")
EOF
ok=400 in 0.6s, ports used: 1

400 requests, one port, and four times faster — because every connection avoided a handshake as well as a port.

5. Compare the mitigations honestly:

$ sudo sysctl -w net.ipv4.tcp_tw_reuse=1        # reuse TIME_WAIT for new outbound
# re-run the churning version: gets further, still hits a wall under sustained load
ApproachPorts for 400 requestsVerdict
New connection each time400 (fails at 101)The bug
Widen port range400Delays the wall ~2×
tcp_tw_reuse=1400, recycled fasterUseful mitigation, outbound only
Keep-alive / pooling1The fix

Restore: sudo sysctl -w net.ipv4.ip_local_port_range="32768 60999"; kill %1.

6 (hard): Debug an unreachable service methodically, layer by layer.
Solution

Set up a service that is reachable only from loopback — the single most common real cause:

$ python3 -m http.server 9300 --bind 127.0.0.1 &>/dev/null &
$ HOSTIP=$(ip -4 route get 1.1.1.1 | awk '{print $7; exit}')
$ echo "host IP: $HOSTIP"
host IP: 192.168.1.42

Layer 1 — name resolution:

$ getent hosts localhost
127.0.0.1       localhost                       # ✓ resolves

Layer 2 — routing:

$ ip route get $HOSTIP
local 192.168.1.42 dev lo src 192.168.1.42 uid 1000    # ✓ route exists

Layer 3/4 — the port, from two different addresses:

$ timeout 2 bash -c "exec 3<>/dev/tcp/127.0.0.1/9300" && echo "loopback: OK"
loopback: OK
$ timeout 2 bash -c "exec 3<>/dev/tcp/$HOSTIP/9300" || echo "host IP: FAILED"
bash: connect: Connection refused
host IP: FAILED

"Refused", not "timeout" — that is the diagnosis right there. The RST proves packets reached the host and were answered, so DNS, routing and firewall are all fine. Only the bind address can explain it.

Layer 5 — confirm the bind:

$ ss -tlnp | grep 9300
LISTEN 0 5 127.0.0.1:9300 0.0.0.0:* users:(("python3",pid=64900,fd=3))
                ^^^^^^^^^
          loopback only — not 0.0.0.0

Confirm on the wire:

$ sudo tcpdump -ni any "port 9300 and host $HOSTIP" -c 4 &
$ timeout 2 bash -c "exec 3<>/dev/tcp/$HOSTIP/9300"
IP 192.168.1.42.55120 > 192.168.1.42.9300: Flags [S], seq 41203
IP 192.168.1.42.9300 > 192.168.1.42.55120: Flags [R.], seq 1, ack 41204
                                                  ^^^^ immediate RST = refused

The fix, and proof it worked:

$ kill %1; python3 -m http.server 9300 --bind 0.0.0.0 &>/dev/null &
$ ss -tlnp | grep 9300
LISTEN 0 5 0.0.0.0:9300 0.0.0.0:*
$ timeout 2 bash -c "exec 3<>/dev/tcp/$HOSTIP/9300" && echo "host IP: OK"
host IP: OK

Now contrast with a genuine firewall drop, so the two signatures are unmistakable:

$ sudo iptables -I INPUT -p tcp --dport 9300 -j DROP
$ time timeout 5 bash -c "exec 3<>/dev/tcp/$HOSTIP/9300"
real  0m5.001s                                  # hangs until timeout, no answer
$ sudo tcpdump -ni any "port 9300" -c 3
IP ...55210 > ...9300: Flags [S]                # SYN
IP ...55210 > ...9300: Flags [S]                # retry
IP ...55210 > ...9300: Flags [S]                # retry — silence

With REJECT instead of DROP it looks like the service being down again:

$ sudo iptables -R INPUT 1 -p tcp --dport 9300 -j REJECT --reject-with tcp-reset
$ timeout 5 bash -c "exec 3<>/dev/tcp/$HOSTIP/9300"
bash: connect: Connection refused               # instant — indistinguishable from no listener
ObservationConclusion
Instant refused, ss shows no listenerService down
Instant refused, ss shows 127.0.0.1Wrong bind address
Instant refused, ss shows 0.0.0.0A REJECT firewall rule
Timeout, repeated SYNs, no replyDROP rule, security group, or wrong route

Cleanup: sudo iptables -D INPUT 1; kill %1.

🎯 Key Takeaways

  • A socket is a file descriptor — read/write/close work on it, which is why shell redirection composes with the network.
  • Unix domain sockets beat loopback TCP for local IPC: no protocol stack, no port exhaustion, and filesystem permissions as the access control.
  • ss replaced netstat because it reads netlink instead of parsing /proc; ss -tlnp is the everyday command.
  • The bind address is a security boundary — 0.0.0.0 is network-reachable, 127.0.0.1 is not, and auditing that one field finds exposed services.
  • listen() creates two queues; accept-queue overflow drops connections after a successful handshake, so nothing appears in application logs.
  • ss -tln's Recv-Q/Send-Q on a LISTEN socket show queue depth against the limit, and nstat ListenOverflows counts the drops.
  • Raising somaxconn alone is useless — the application's listen() backlog argument must rise too, and sustained overflow is a capacity problem.
  • Server-side TIME_WAIT costs only memory; client-side TIME_WAIT consumes ephemeral ports and caps outbound rate to a single destination near 470/s.
  • Connection pooling is the fix for port exhaustion; tcp_tw_reuse mitigates, and tcp_tw_recycle was removed for breaking NAT.
  • Applications resolve names via nsswitch, not DNS directly — use getent hosts, never dig, to reproduce what an application sees.
  • ndots:5 in Kubernetes makes every short name generate several failed lookups; a trailing dot makes a name absolute and skips them.
  • "Refused" means packets reached the host and were answered — the service is the problem; "timeout" means silent drops — the network is.
  • Debug connectivity by layer in order (name → route → reachability → port → listener → bind address → firewall → packet capture) and stop at the first failure.
