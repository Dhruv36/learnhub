Memory: Virtual Memory & the OOM Killer Processes & The Kernel

What you'll master: why "free memory is nearly zero" is healthy and which number to alert on instead, the difference between virtual and resident memory that makes VSZ almost meaningless, why overcommit means malloc succeeding tells you nothing, how the OOM killer chooses its victim and how to influence that choice, why a container gets killed at a limit the host never noticed, and how to tell a genuine leak from cache growth from fragmentation. Prerequisites: Processes, fork & exec and System Calls & strace.

Part 1 — Free Memory Is Supposed to Be Low

The single most common Linux monitoring mistake is alerting on free memory. Unused RAM does nothing; the kernel fills it with page cache — file data kept around in case it is needed again — and reclaims it instantly when a process needs memory.

$ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi       4.1Gi       391Mi       128Mi        11Gi        10Gi
                                       ^^^^^                              ^^^^^
                              looks alarming                    the number that matters

391 MB free and 10 GB available. The 11 GB in buff/cache is doing useful work — it is why your files open instantly the second time — and it evaporates the moment something needs it.

FieldMeaningAlert on it?
freeGenuinely untouched RAMNo — near-zero is normal and healthy
buff/cachePage cache and kernel buffersNo — this is memory working for you
availableWhat a new process could get without swappingYes — this is the real headroom
usedtotal − free − buff/cacheOnly alongside available

Prove the cache is reclaimable rather than trusting the label:

$ awk '/^(MemFree|MemAvailable|Cached)/' /proc/meminfo
MemFree:          400512 kB
MemAvailable:   10982400 kB
Cached:         11204096 kB

$ head -c 4G /dev/zero | tail -c 1 >/dev/null      # demand 4 GB
$ awk '/^(MemFree|Cached)/' /proc/meminfo
MemFree:         4102336 kB                        # cache shrank to supply it
Cached:          7301248 kB
🔑 The alerting rule. Alert on MemAvailable as a fraction of MemTotal, never on MemFree. A threshold on free memory fires constantly on a healthy machine and teaches everyone to ignore memory alerts — which means the real one gets ignored too. The other genuinely useful signal is pressure stall information (/proc/pressure/memory), which reports the percentage of time tasks were stalled waiting for memory, and catches thrashing before an OOM kill happens.

Part 2 — Virtual vs Resident

Every process has its own virtual address space, mapped to physical pages by the MMU. The two numbers reported everywhere mean very different things, and confusing them produces false alarms daily.

MetricMeansUseful?
VSZ / VmSizeTotal address space reservedRarely — includes unbacked reservations
RSS / VmRSSPhysical pages currently residentYes, but double-counts shared pages
PSSRSS with shared pages divided among usersBest for "how much is this really using"
USSPrivate only — freed if the process diesBest for "what would I get back"
$ ps -o pid,vsz,rss,comm -C java
    PID    VSZ   RSS COMMAND
  60100 8412304 512384 java          # 8.4 GB virtual, 512 MB actually resident

The JVM reserves a large heap up front but touches only part of it. The 8.4 GB costs nothing physical — it is bookkeeping. Alerting on VSZ here would page someone for a healthy process.

PSS is the honest number when processes share memory, which forked workers always do:

$ sudo awk '/^Pss:/ {sum += $2} END {printf "PSS: %.1f MB\n", sum/1024}' /proc/60100/smaps
PSS: 486.2 MB

# Summing RSS across forked workers double-counts shared libraries and COW pages
$ ps -o rss= -C nginx | awk '{s+=$1} END {printf "RSS sum: %.1f MB\n", s/1024}'
RSS sum: 184.0 MB
$ sudo awk '/^Pss:/ {s+=$2} END {printf "PSS sum: %.1f MB\n", s/1024}' /proc/*/smaps 2>/dev/null

/proc/PID/smaps_rollup gives the same totals without parsing thousands of lines:

$ sudo grep -E '^(Rss|Pss|Private_|Swap):' /proc/60100/smaps_rollup
Rss:              512384 kB
Pss:              497821 kB
Private_Clean:      2048 kB
Private_Dirty:    481920 kB       # this is what a leak grows
Swap:                  0 kB

Private_Dirty is the number to watch for leaks: it is memory this process alone has modified, which cannot be shared, reclaimed, or dropped.

Part 3 — Overcommit: Why malloc Always Succeeds

Linux hands out address space it cannot necessarily back with physical memory. A successful malloc is a promise, not a delivery — the pages are allocated lazily on first touch.

$ free -h | awk 'NR==2 {print "total:", $2}'
total: 15Gi

$ python3 -c "
import ctypes
buf = ctypes.create_string_buffer(30 * 1024**3)   # ask for 30 GB
print('allocation succeeded')
"
allocation succeeded                               # on a 15 GB machine

Nothing failed because nothing was touched. The kernel recorded a mapping; physical pages arrive only when written to, one page fault at a time.

vm.overcommit_memoryBehaviour
0 (default)Heuristic — refuses only obviously absurd requests
1Always allow. Used for workloads that reserve huge sparse regions (Redis)
2Strict — never exceed swap + overcommit_ratio% of RAM

The consequence is architectural: because allocation cannot fail meaningfully, the failure is deferred to first touch — and at that point there is no error to return. The kernel cannot fail a page fault, so instead it kills something. That is the OOM killer, and it exists precisely because overcommit exists.

This is also why the classic defensive check is useless on Linux:

void *p = malloc(size);
if (!p) { /* almost never taken — the kill comes later, elsewhere */ }

Part 4 — The OOM Killer

When memory is genuinely exhausted and nothing can be reclaimed, the kernel picks a process and kills it. The choice is scored, not random.

oom_score  ≈  (RSS + swap + page tables) as a proportion of available memory
              adjusted by oom_score_adj  (-1000 … +1000)

$ for p in $(pgrep -d' ' -f 'java|nginx|postgres'); do
>   printf '%-8s %-12s score=%-5s adj=%s\n' "$p" "$(comm=$(ps -o comm= -p $p); echo $comm)" \
>     "$(cat /proc/$p/oom_score)" "$(cat /proc/$p/oom_score_adj)"
> done
60100    java         score=412   adj=0
60210    nginx        score=8     adj=0
60300    postgres     score=95    adj=-500

The biggest user is usually the victim, which is often the most important process on the box — the database, or the application itself. Protect it explicitly:

$ echo -500 | sudo tee /proc/60300/oom_score_adj     # less likely to be chosen
$ echo 1000 | sudo tee /proc/60400/oom_score_adj     # sacrifice this one first
oom_score_adjEffect
-1000Never kill (effectively immune)
-500Strongly protected — databases, critical daemons
0Default
+1000Kill first — batch jobs, caches, anything restartable

In systemd this is declarative rather than a manual poke that vanishes on restart:

[Service]
OOMScoreAdjust=-500
MemoryMax=2G                # cgroup limit: killed at 2G regardless of host memory
MemoryHigh=1.5G             # throttle and reclaim aggressively before that

Recognising an OOM kill matters because the application logs show nothing — SIGKILL cannot be caught, so the process simply vanishes:

$ sudo dmesg -T | grep -i 'killed process'
[Sat Aug  9 03:14:22 2026] Out of memory: Killed process 60100 (java)
    total-vm:8412304kB, anon-rss:7981204kB, file-rss:0kB, shmem-rss:0kB,
    UID:1000 pgtables:15804kB oom_score_adj:0

$ journalctl -k --since '1 hour ago' | grep -i oom
$ systemctl status myapp | grep -E 'Main PID|Result'
   Main PID: 60100 (code=killed, signal=KILL)
     Result: oom-kill

Exit status 137 (128+9) from a container or a shell is the same signal reported differently — as The Shell Executes a Line noted, that number almost always means the OOM killer or a memory limit, not application logic.

❌ "The container keeps restarting, let's add restart: always." If the cause is an OOM kill at a cgroup limit, restarting produces a crash loop: the process grows, gets killed at the same threshold, and restarts — burning CPU and generating alerts while the actual problem (limit too low, or a leak) is untouched.

✅ Confirm the cause first. kubectl describe pod showing OOMKilled, or exit 137, or memory.events in the cgroup, distinguishes a memory limit from an application crash. Then decide: raise MemoryMax if the limit was wrong, or fix the growth if it is a leak. Restarting is a mitigation, never a diagnosis.

Part 5 — Containers and cgroup Limits

A container hitting its memory limit is killed by the cgroup OOM killer while the host has plenty of free memory. The host never noticed, which is why host-level monitoring misses these entirely.

# cgroup v2 — per-container accounting
$ cat /sys/fs/cgroup/memory.max
2147483648                      # 2 GB limit
$ cat /sys/fs/cgroup/memory.current
2041823232                      # 1.9 GB used — very close

$ cat /sys/fs/cgroup/memory.events
low 0
high 4821                       # times it was throttled at MemoryHigh
max 12                          # times it hit the hard limit
oom 3
oom_kill 3                      # three processes killed

memory.events is the definitive record. A non-zero oom_kill proves the container was killed by its limit rather than crashing on its own — and a high high count with zero kills means it is being throttled constantly, which presents as unexplained slowness.

Two container-specific traps are worth stating plainly:

TrapConsequence
Page cache counts toward the cgroup limitA container doing heavy file I/O gets OOM-killed for cache it did not "use"
The JVM/runtime sees the host's memoryOld JVMs size their heap from host RAM and instantly exceed a small container limit

The second is why -XX:+UseContainerSupport (default since JDK 10) and MaxRAMPercentage exist, and why Node needs --max-old-space-size set relative to the container limit rather than left to guess.

Part 6 — Leak, Cache, or Fragmentation?

"Memory keeps growing" has three quite different causes with three different fixes. Distinguishing them is the actual diagnostic skill.

CauseSignatureFix
LeakPrivate_Dirty climbs monotonically, never fallsFix the code — raising limits only delays it
Cache growthRSS grows then plateaus; falls under pressureNothing — this is correct behaviour
FragmentationRSS high, allocator reports most of it freeTune the allocator, or restart periodically
Thread stacksVSZ grows in 8 MB steps with thread countBound the thread pool
# Sample over time — the shape of the curve is the diagnosis
$ while sleep 60; do
>   printf '%s %s\n' "$(date +%T)" \
>     "$(awk '/^Private_Dirty/ {s+=$2} END {print s}' /proc/$PID/smaps)"
> done
10:00:00 481920
10:01:00 502144      # +20 MB
10:02:00 523392      # +21 MB — linear growth, never plateauing = leak

Fragmentation is the one people misdiagnose as a leak. glibc's allocator can hold freed memory in arenas without returning it to the kernel, so RSS stays high while the application believes it freed everything:

$ MALLOC_ARENA_MAX=2 ./myapp        # fewer arenas, less fragmentation

The classic case is a multi-threaded C or Python service whose RSS grows to a plateau far above its live-object size and never falls. malloc_trim() or jemalloc usually fixes it, and it is not a bug in the application's logic.

Finally, swap. Its role is widely misunderstood: a small amount of swap lets the kernel evict genuinely cold anonymous pages, which is useful. What is harmful is thrashing — continuous swap-in/swap-out — which makes a machine unresponsive without ever triggering an OOM kill:

$ vmstat 1 5
procs -----------memory---------- ---swap-- -----io----  ---system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs  us sy id wa
 2  8 4194300  40112  1024 102400 8412 9203  2104  9812 4821 9302   3  8  2 87
                                   ^^^^ ^^^^                                ^^
                          continuous swap traffic                    87% iowait

Non-zero si/so sustained over time is thrashing. vm.swappiness tunes how eagerly the kernel swaps anonymous pages (default 60; 10 is common for databases), but the real fix is fitting the working set in RAM. Kubernetes disables swap entirely by default so that hitting the limit produces a clean, observable OOM kill rather than an ambiguous slow degradation.

Interview Questions

Beginner: Your server shows almost no free memory. Is that a problem?

Almost certainly not. Linux deliberately uses otherwise-idle RAM for the page cache — copies of file data kept in case they are read again. Unused memory does nothing useful, so the kernel fills it, and reclaims it instantly when a process needs memory.

The number that matters is MemAvailable, which the kernel calculates as roughly "what a new process could get without swapping" — free memory plus reclaimable cache:

$ free -h
               total        used        free      buff/cache   available
Mem:            15Gi       4.1Gi       391Mi            11Gi        10Gi

391 MB free looks alarming; 10 GB available is the truth. You can demonstrate it by allocating several gigabytes and watching Cached shrink to supply it.

The practical consequence is a monitoring rule: alert on MemAvailable as a fraction of total, never on MemFree. A free-memory alert fires constantly on healthy machines, which trains everyone to ignore memory alerts — so the one that matters gets ignored too. /proc/pressure/memory is the other good signal, since it catches thrashing before anything is killed.

Beginner: What is the difference between VSZ and RSS?

VSZ (virtual size) is the total address space the process has reserved. RSS (resident set size) is how much physical RAM it is actually using right now.

They diverge because Linux allocates lazily. A process can reserve a large region and touch very little of it; the untouched part costs no physical memory at all:

$ ps -o pid,vsz,rss,comm -C java
    PID     VSZ    RSS COMMAND
  60100 8412304 512384 java        # 8.4 GB reserved, 512 MB resident

A JVM reserving its maximum heap up front is the classic example, and alerting on VSZ would page someone for a perfectly healthy process.

RSS has its own flaw: it counts shared pages fully in every process that maps them, so summing RSS across forked workers double-counts shared libraries and copy-on-write pages. PSS (proportional set size) divides shared pages among their users and is the honest number for "how much is this really costing", available from /proc/PID/smaps_rollup.

For leak-hunting specifically, Private_Dirty is the field to watch — memory this process alone has modified, which cannot be shared or dropped.

Mid: What is memory overcommit, and why does it mean malloc checking is useless?

Linux hands out virtual address space it cannot necessarily back with physical memory. Physical pages are only allocated when a page is first touched, via a page fault.

So malloc succeeding means the kernel recorded a mapping — not that the memory exists. You can allocate 30 GB on a 15 GB machine and it will report success, because nothing was written.

The architectural consequence: the failure is deferred to first touch, and at that point there is no way to report an error. The kernel cannot fail a page fault the way it can fail a syscall — so instead it kills a process. The OOM killer exists precisely because overcommit exists.

This makes the traditional defensive pattern nearly useless:

void *p = malloc(size);
if (!p) { /* almost never taken on Linux */ }

The process dies later, elsewhere, by SIGKILL, with no opportunity to handle anything.

vm.overcommit_memory=2 enforces strict accounting so allocation genuinely fails instead — but most workloads break under it, because sparse reservations (JVM heaps, Redis fork-for-snapshot, thread stacks) are normal and useful. The practical answer is cgroup limits plus monitoring growth, not allocation checks.

Mid: How does the OOM killer choose a victim, and how do you influence it?

The kernel scores every process roughly by its proportion of available memory — RSS plus swap plus page tables — then adjusts by that process's oom_score_adj, and kills the highest scorer.

$ cat /proc/60100/oom_score        # the computed score
412
$ cat /proc/60100/oom_score_adj    # the tunable bias, -1000..+1000
0

The heuristic is "kill the biggest user", which is reasonable for recovering the most memory quickly and frequently wrong operationally — the biggest user is often the database or the main application, while the disposable batch job survives.

Influence it explicitly: -1000 makes a process effectively immune, -500 strongly protects a database, +1000 marks a cache or batch worker as the preferred sacrifice. In systemd this belongs in the unit as OOMScoreAdjust=, since a manual write to /proc is lost on restart.

Recognising a kill matters as much as preventing one. SIGKILL cannot be caught, so application logs show nothing — the process simply vanishes. The evidence is in dmesg -T | grep -i 'killed process', journalctl -k, systemctl status showing Result: oom-kill, or exit status 137 (128+9) from a container.

In containers the far more common case is the cgroup OOM killer firing at memory.max while the host has gigabytes free — which host-level monitoring misses entirely, and memory.events records definitively.

Senior: A service's memory grows steadily until it is OOM-killed every few days. Diagnose it.

"Steadily until killed" fits three quite different causes, and I would identify which before touching anything, because the fixes are unrelated.

1. Establish the shape of the growth. The curve is the diagnosis:

$ while sleep 300; do
>   printf '%s rss=%s pss=%s priv_dirty=%s\n' "$(date +%T)" \
>     "$(awk '/^Rss:/{print $2}'  /proc/$PID/smaps_rollup)" \
>     "$(awk '/^Pss:/{print $2}'  /proc/$PID/smaps_rollup)" \
>     "$(awk '/^Private_Dirty/{print $2}' /proc/$PID/smaps_rollup)"
> done
  • Linear, never plateaus, Private_Dirty tracks it → genuine leak.
  • Grows then plateaus, falls under pressure → cache. Working as intended.
  • Plateaus far above live-object size, allocator says memory is free → fragmentation.

2. Confirm it is not the runtime's own cache. Many services have unbounded internal caches that look exactly like leaks — a connection pool with no maximum, a memoisation dict, an in-memory session store. Application metrics distinguish this in one step, and it is far commoner than a true allocator leak.

3. Localise the allocation. Where the memory lives narrows the cause quickly:

$ sudo awk '/^Size:/{s=$2} /^Private_Dirty:/{if ($2 > 10240) print $2" kB", region}
            /^[0-9a-f]+-/{region=$NF}' /proc/$PID/smaps | sort -rn | head -5

Growth in [heap] points at the allocator; many similar anonymous mappings suggest thread stacks (8 MB each) and an unbounded thread pool; growth in a mapped file is a different problem entirely.

4. Use the right profiler for the runtime rather than guessing: tracemalloc or objgraph for Python, a heap dump plus MAT for the JVM, pprof for Go, valgrind --leak-check or heaptrack for native code. This is where the actual fix comes from; everything before it is triage.

5. Mitigate honestly while fixing. A cgroup MemoryMax with Restart=on-failure turns an unpredictable 3am kill into a controlled restart, and MemoryHigh below it applies reclaim pressure first. I would state clearly that this is a mitigation, not a fix — the distinction matters, because "we added a restart" has a way of becoming the permanent solution and the leak then grows until restarts are hourly.

Senior: How would you size memory limits for a containerised service?

The tension is real: too low and you get OOM kills under normal peaks; too high and you waste capacity and lose the early warning a limit provides. I would measure rather than guess, then leave deliberate headroom.

1. Measure the true working set under realistic load, for long enough to include periodic work — nightly jobs and cache warm-up are what catch people out:

$ cat /sys/fs/cgroup/memory.current      # actual usage
$ cat /sys/fs/cgroup/memory.peak         # high-water mark (v2)
$ awk '/^Pss:/{print $2}' /proc/$PID/smaps_rollup

2. Set two limits, not one. This is the part most people miss:

[Service]
MemoryHigh=1.5G      # soft: throttle and reclaim aggressively
MemoryMax=2G         # hard: OOM kill

MemoryHigh gives you a visible warning band — memory.events shows high incrementing — before anything is killed. A service that is throttling constantly is under-provisioned, and you learn that from a metric rather than from an outage.

3. Account for page cache. In cgroup v2, page cache counts toward the limit. An I/O-heavy container can be OOM-killed for cache it never "used", so file-serving and log-writing workloads need extra headroom or explicit cache limits.

4. Make the runtime aware of the limit. Older JVMs and Node read the host's memory and size their heap from it, then immediately exceed a small container limit. Set -XX:MaxRAMPercentage=75 or --max-old-space-size explicitly, and leave room for the non-heap portion — thread stacks, metaspace, native buffers — which is routinely 25–30% more than the heap setting.

5. Decide requests versus limits deliberately under Kubernetes. Setting requests == limits gives the Guaranteed QoS class and predictable behaviour; setting requests lower allows overcommitting the node but makes the pod evictable under node pressure. For a latency-sensitive service I want Guaranteed; for batch work, Burstable is fine and cheaper.

6. Verify the failure mode, do not assume it. I would deliberately drive the service past its limit in staging and confirm three things: it is killed cleanly rather than thrashing (which is why Kubernetes disables swap), the restart is fast and safe, and the event is visible in metrics and alerts. A limit whose behaviour at the boundary has never been observed is a guess, and the first observation should not be in production at 3am.

🏋️ Exercises

1 (easy): Prove that page cache is reclaimable and that free memory is the wrong metric.
Solution 
$ awk '/^(MemTotal|MemFree|MemAvailable|Cached)/' /proc/meminfo
MemTotal:       16318464 kB
MemFree:          412008 kB
MemAvailable:   11203848 kB
Cached:         10982400 kB

400 MB free but 11 GB available. Fill the cache further by reading a large file:

$ dd if=/dev/urandom of=/tmp/big.bin bs=1M count=3000 2>/dev/null
$ cat /tmp/big.bin > /dev/null                    # pull it into cache
$ awk '/^(MemFree|Cached)/' /proc/meminfo
MemFree:          208112 kB                        # free dropped further
Cached:         13891200 kB                        # cache grew

Now demand memory and watch the cache give it back:

$ python3 -c "
b = bytearray(4 * 1024**3)      # touch 4 GB
for i in range(0, len(b), 4096): b[i] = 1
import subprocess; subprocess.run(['awk','/^(MemFree|Cached)/','/proc/meminfo'])
"
MemFree:          198432 kB
Cached:          9412096 kB                        # cache shrank by ~4.4 GB

The cache was reclaimed automatically, with no swapping and no OOM. This is exactly why MemFree is a useless alert threshold.

Confirm the pressure metric stayed healthy — the signal that actually distinguishes "using memory well" from "in trouble":

$ cat /proc/pressure/memory
some avg10=0.00 avg60=0.00 avg300=0.00 total=1420
full avg10=0.00 avg60=0.00 avg300=0.00 total=0

Zero stall time — no task waited for memory. Under genuine pressure these rise well before an OOM kill, which makes PSI the best early-warning signal available.

Cleanup: rm /tmp/big.bin.

2 (easy): Demonstrate overcommit by allocating more than the machine has.
Solution 
$ free -h | awk 'NR==2{print "RAM:", $2}'
RAM: 15Gi
$ cat /proc/sys/vm/overcommit_memory
0                                   # heuristic mode (default)

Reserve far more than exists — and succeed:

$ python3 -c "
import mmap, os
m = mmap.mmap(-1, 40 * 1024**3)       # 40 GB on a 15 GB box
print('reserved 40 GB successfully')
print('RSS now:', open('/proc/self/status').read().split('VmRSS:')[1].split()[0], 'kB')
print('VSZ now:', open('/proc/self/status').read().split('VmSize:')[1].split()[0], 'kB')
"
reserved 40 GB successfully
RSS now: 9284 kB                      # nothing physical consumed
VSZ now: 41952324 kB                  # 40 GB of address space

VSZ is 40 GB, RSS is 9 MB. The reservation is pure bookkeeping.

Now touch it and watch physical memory arrive one page at a time:

$ python3 -c "
import mmap
m = mmap.mmap(-1, 2 * 1024**3)
def rss(): return int(open('/proc/self/status').read().split('VmRSS:')[1].split()[0])
print('after reserve :', rss(), 'kB')
for i in range(0, 512*1024**2, 4096): m[i] = 1     # touch 512 MB
print('after touching:', rss(), 'kB')
"
after reserve : 9412 kB
after touching: 533284 kB             # only the touched pages materialised

Confirm strict mode changes the behaviour — the allocation genuinely fails:

$ echo 2 | sudo tee /proc/sys/vm/overcommit_memory
$ python3 -c "
import mmap
try:
    m = mmap.mmap(-1, 40 * 1024**3); print('succeeded')
except OSError as e: print('FAILED:', e)
"
FAILED: [Errno 12] Cannot allocate memory
$ echo 0 | sudo tee /proc/sys/vm/overcommit_memory     # restore

Strict mode makes malloc checks meaningful again — but breaks any workload that reserves sparse regions, which is why it is rarely used.

3 (medium): Trigger the OOM killer in a controlled cgroup and read the evidence.
Solution

Use a scoped cgroup so only the test process is at risk — never trigger a host-wide OOM deliberately:

$ sudo systemd-run --scope -p MemoryMax=256M --unit=oomtest \
>   python3 -c "
b = bytearray()
while True:
    b.extend(b'x' * 10_000_000)      # grow 10 MB at a time
    print(len(b)//1_000_000, 'MB', flush=True)
"
Running scope as unit: oomtest.scope
10 MB
...
240 MB
Killed

The evidence, in three places:

$ sudo dmesg -T | grep -i 'killed process' | tail -2
[Sat Aug  9 11:22:14 2026] Memory cgroup out of memory: Killed process 61200 (python3)
    total-vm:512304kB, anon-rss:249812kB, file-rss:2048kB, oom_score_adj:0

$ journalctl -k --since '2 min ago' | grep -i 'memory cgroup'
$ systemctl status oomtest.scope 2>/dev/null | grep -E 'Result|Main PID'

Note it says "Memory cgroup out of memory", not plain "Out of memory" — the host was nowhere near exhausted. This is the container case, and host-level memory monitoring would show nothing at all.

The definitive per-cgroup record:

$ sudo systemd-run --scope -p MemoryMax=256M -p MemoryHigh=200M --unit=oom2 \
>   bash -c 'python3 -c "
b=bytearray()
while len(b) < 300_000_000: b.extend(b\"x\"*5_000_000)
" ; cat /sys/fs/cgroup/system.slice/oom2.scope/memory.events'
low 0
high 41                    # throttled 41 times at MemoryHigh first
max 8
oom 1
oom_kill 1                 # then killed once at MemoryMax

The high counter rising before oom_kill is exactly the early-warning band that makes a two-limit configuration worth having.

Show that protection works:

$ sudo systemd-run --scope -p MemoryMax=256M -p OOMScoreAdjust=-900 --unit=oom3 \
>   python3 -c "..."          # same allocation
# The cgroup limit still applies — oom_score_adj biases WHICH process is chosen
# within a cgroup, it does not exempt you from the cgroup's hard limit.

That last point is the subtlety worth internalising: oom_score_adj influences victim selection under system-wide pressure, but a cgroup hard limit is enforced regardless.

4 (medium): Distinguish RSS from PSS on a process with shared memory.
Solution

Fork several children that share a large read-only allocation:

$ python3 <<'EOF' &
import os, time
data = bytearray(400 * 1024 * 1024)          # 400 MB, touched by the parent
for i in range(0, len(data), 4096): data[i] = 1
for _ in range(3):
    if os.fork() == 0:
        time.sleep(60); os._exit(0)          # children only READ it
time.sleep(60)
EOF
$ sleep 2; pids=$(pgrep -f 'python3 -$|python3$' | head -4)

Summing RSS massively overstates the total:

$ for p in $pids; do
>   printf 'pid %-7s rss=%-8s pss=%-8s priv=%s\n' "$p" \
>     "$(awk '/^Rss:/{print $2}' /proc/$p/smaps_rollup)" \
>     "$(awk '/^Pss:/{print $2}' /proc/$p/smaps_rollup)" \
>     "$(awk '/^Private_Dirty:/{print $2}' /proc/$p/smaps_rollup)"
> done
pid 61400   rss=412308  pss=105204  priv=2048
pid 61401   rss=409112  pss=103892  priv=1024
pid 61402   rss=409112  pss=103892  priv=1024
pid 61403   rss=409112  pss=103892  priv=1024

$ echo "RSS sum: $(( (412308+409112*3) / 1024 )) MB"
RSS sum: 1601 MB                    # implies 1.6 GB used
$ echo "PSS sum: $(( (105204+103892*3) / 1024 )) MB"
PSS sum: 407 MB                     # the truth — one 400 MB allocation

RSS counts the same physical pages four times. PSS divides each shared page by the number of processes mapping it, so the total matches reality.

Verify against the system view:

$ free -m | awk 'NR==2{print "used:", $3, "MB"}'

Now make a child write, and watch copy-on-write turn shared pages into private ones:

$ python3 <<'EOF'
import os, time
data = bytearray(200 * 1024 * 1024)
for i in range(0, len(data), 4096): data[i] = 1
pid = os.fork()
if pid == 0:
    def priv(): return open('/proc/self/smaps_rollup').read().split('Private_Dirty:')[1].split()[0]
    print('child private before writes:', priv(), 'kB')
    for i in range(0, len(data), 4096): data[i] = 2      # dirty every page
    print('child private after writes :', priv(), 'kB')
    os._exit(0)
os.wait()
EOF
child private before writes: 1284 kB
child private after writes : 205892 kB

This is the practical rule: use PSS for capacity planning, and Private_Dirty for leak detection — the latter is the memory that is genuinely this process's own and cannot be shared away.

5 (hard): Tell a leak, cache growth, and fragmentation apart from their growth curves.
Solution

Build all three and sample them identically:

$ cat > /tmp/mem3.py <<'EOF'
import sys, time, os

def priv():
    return int(open('/proc/self/smaps_rollup').read().split('Private_Dirty:')[1].split()[0])

mode = sys.argv[1]
store, cache = [], {}

for tick in range(12):
    if mode == 'leak':
        store.append(bytearray(20 * 1024 * 1024))          # never released
    elif mode == 'cache':
        cache[tick % 5] = bytearray(20 * 1024 * 1024)      # bounded to 5 entries
    elif mode == 'frag':
        tmp = [bytearray(1024) for _ in range(200_000)]    # many small allocs
        del tmp[::2]                                        # free every other one
    print(f"{tick*5:3d}s private_dirty={priv()//1024} MB", flush=True)
    time.sleep(0.3)
EOF

Leak — linear, never plateaus:

$ python3 /tmp/mem3.py leak
  0s private_dirty=22 MB
 25s private_dirty=122 MB
 55s private_dirty=242 MB           # perfectly linear, no ceiling

Cache — grows then plateaus:

$ python3 /tmp/mem3.py cache
  0s private_dirty=22 MB
 20s private_dirty=102 MB
 30s private_dirty=104 MB
 55s private_dirty=104 MB           # flat once the bound is reached

Fragmentation — high RSS despite the objects being freed:

$ python3 /tmp/mem3.py frag
  0s private_dirty=118 MB
 30s private_dirty=214 MB
 55s private_dirty=221 MB           # plateaus HIGH, far above live data

The third case is the one misdiagnosed as a leak: the application freed half the objects, but the allocator kept the arenas rather than returning pages to the kernel.

Confirm fragmentation specifically by comparing what the allocator thinks it holds against RSS:

$ MALLOC_ARENA_MAX=2 python3 /tmp/mem3.py frag | tail -1
 55s private_dirty=147 MB           # fewer arenas → much less waste
CurveDiagnosisFix
Linear, unboundedLeakFix the code — a limit only delays the kill
Rises then flatCache / poolNothing, or bound it explicitly
Flat but far above live setFragmentationMALLOC_ARENA_MAX, jemalloc, malloc_trim
Steps of ~8 MBThread stacksBound the thread pool

The operational point: a single memory reading tells you nothing. Sampling over time and looking at the shape is what distinguishes three problems that present identically as "memory keeps growing".

6 (hard): Size and verify memory limits for a containerised service.
Solution

1. Measure the real working set under load rather than guessing from a single sample:

$ cat > /tmp/svc.py <<'EOF'
import time, os, sys
cache = {}
print("pid", os.getpid(), flush=True)
for i in range(200):
    cache[i % 40] = bytearray(3 * 1024 * 1024)     # bounded working set ~120 MB
    if i % 20 == 0:
        rss = open('/proc/self/status').read().split('VmRSS:')[1].split()[0]
        print(f"i={i} rss={int(rss)//1024}MB", flush=True)
    time.sleep(0.05)
EOF
$ sudo systemd-run --scope --unit=sizing python3 /tmp/svc.py
i=0 rss=12MB
i=100 rss=131MB
i=180 rss=133MB                       # plateau ≈ 133 MB
$ cat /sys/fs/cgroup/system.slice/sizing.scope/memory.peak 2>/dev/null
142606336                             # 136 MB high-water mark

2. Set two limits with deliberate headroom — soft for warning, hard for enforcement:

# working set 136 MB → MemoryHigh 1.5x, MemoryMax 2x
$ sudo systemd-run --scope -p MemoryHigh=200M -p MemoryMax=272M \
>   -p OOMScoreAdjust=-500 --unit=sized python3 /tmp/svc.py

3. Verify behaviour at the boundary — the step almost everyone skips, which means the first observation happens in production:

$ cat /sys/fs/cgroup/system.slice/sized.scope/memory.events
low 0
high 0
max 0
oom 0
oom_kill 0                            # never approached the limits: correctly sized

Now deliberately under-size it to confirm the failure is clean and observable:

$ sudo systemd-run --scope -p MemoryHigh=60M -p MemoryMax=80M --unit=toosmall \
>   python3 /tmp/svc.py
i=0 rss=12MB
Killed
$ cat /sys/fs/cgroup/system.slice/toosmall.scope/memory.events 2>/dev/null
high 892                              # throttled heavily FIRST
max 14
oom_kill 1

The high counter climbing to 892 before the kill is the early warning — a service being throttled that hard is visibly degraded long before it dies, and that is precisely the signal to alert on.

4. Account for the runtime's own view. A JVM or Node process must be told the limit, or it sizes its heap from host RAM:

# JVM: heap as a percentage of the CONTAINER limit, leaving room for non-heap
java -XX:MaxRAMPercentage=70 -jar app.jar
# Node:
node --max-old-space-size=$((LIMIT_MB * 70 / 100)) app.js

The 30% reserve is not padding — thread stacks, metaspace, JIT code cache, and native buffers live outside the heap and routinely account for that much.

5. Remember page cache counts. For an I/O-heavy service, files it reads occupy the cgroup's allowance. A container that passes a synthetic CPU test can still be OOM-killed in production purely from serving files, so I/O-heavy workloads need extra headroom above the measured anonymous working set.

Cleanup: sudo systemctl stop sized.scope sizing.scope 2>/dev/null.

🎯 Key Takeaways

  • Low free memory is healthy — the kernel fills idle RAM with reclaimable page cache. Alert on MemAvailable and /proc/pressure/memory, never MemFree.
  • VSZ is reserved address space and is nearly meaningless; RSS is resident but double-counts shared pages; PSS is the honest per-process number.
  • Private_Dirty from smaps_rollup is the field to watch for leaks — memory only this process has modified.
  • Overcommit means malloc succeeds without backing memory; pages arrive on first touch, so checking for NULL is nearly useless on Linux.
  • The OOM killer exists because of overcommit — a page fault cannot return an error, so the kernel kills instead.
  • Victim selection scores processes by proportional memory use; oom_score_adj (or systemd's OOMScoreAdjust=) biases the choice.
  • An OOM kill leaves nothing in application logs because SIGKILL is uncatchable — look in dmesg, journalctl -k, or exit status 137.
  • Containers are usually killed by the cgroup OOM killer at memory.max while the host has memory free; memory.events is the definitive record.
  • Page cache counts toward a cgroup limit, so I/O-heavy containers get killed for cache they did not consider "theirs".
  • Set two limits: MemoryHigh for a visible throttling warning band, MemoryMax for the hard stop.
  • Runtimes must be told the container limit — MaxRAMPercentage, --max-old-space-size — and need ~30% beyond the heap for stacks, metaspace and native buffers.
  • Growth has three shapes: linear and unbounded is a leak, rise-then-plateau is cache, and a high plateau above the live set is allocator fragmentation.
  • Swap converts a clean OOM kill into slow thrashing; sustained si/so in vmstat with high iowait is the signature, and Kubernetes disables swap for exactly this reason.
