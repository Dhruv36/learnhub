Storage, Filesystems & Mounts The Running System

What you'll master: the block-device stack from partition to mounted directory, why df and du disagree and which one is lying, the two separate ways a disk fills up (bytes and inodes) and why only one of them is obvious, what mount options actually change at runtime, how the page cache and fsync decide whether your data survives a power cut, and how to read I/O latency well enough to tell a slow disk from a busy one. Prerequisites: The Filesystem & Paths and Files, Inodes & Links.

Part 1 — The Storage Stack, Bottom to Top

A path like /var/lib/postgresql/data sits at the top of a stack of layers, each one presenting a block device to the layer above. Debugging storage means knowing which layer you are actually looking at.

  /var/lib/postgresql/data     ← path in the directory tree
        │  mount
  filesystem   (ext4, xfs, btrfs)    ← inodes, journaling, allocation
        │
  logical volume  (LVM: /dev/vg0/data)   ← resizable, snapshottable
        │
  partition   (/dev/nvme0n1p3)      ← a byte range of the disk
        │
  block device  (/dev/nvme0n1)      ← the physical device

Every layer is optional except the top and bottom. A cloud VM often has no LVM; a container may mount a filesystem directly from a network device. lsblk renders the whole stack in one command:

$ lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT,MODEL
NAME          SIZE FSTYPE      MOUNTPOINT   MODEL
nvme0n1       477G                          Samsung SSD 980
├─nvme0n1p1     1G vfat        /boot/efi
├─nvme0n1p2     2G ext4        /boot
└─nvme0n1p3   474G LVM2_member
  ├─vg0-root   50G ext4        /
  ├─vg0-swap    8G swap        [SWAP]
  └─vg0-data  416G xfs         /var/lib/postgresql
CommandShowsLayer
lsblkDevice tree, sizes, mountpointsBlock + filesystem
blkidUUIDs and filesystem typesFilesystem
findmntMount tree with options and sourceMount
df -hSpace per mounted filesystemFilesystem
lvs / vgs / pvsLVM volumes, groups, physical volumesLVM
🔑 Devices are files, but not ordinary ones. /dev/nvme0n1 is a block special file — reading it gives you raw bytes off the disk, bypassing the filesystem entirely. That is why dd if=/dev/sda of=/dev/sdb clones a disk regardless of what filesystem is on it, and why writing to the wrong device destroys everything with no confirmation prompt. The filesystem is an interpretation layered on top of a flat array of blocks; nothing about the device enforces it.

Part 2 — Mounting: Grafting a Filesystem Onto the Tree

Unix has no drive letters. A filesystem becomes reachable by being mounted at a directory, and from that moment the directory's previous contents are hidden — not deleted, just shadowed.

$ sudo mkdir -p /mnt/data
$ echo "written before mount" | sudo tee /mnt/data/hidden.txt
$ sudo mount /dev/vg0-data /mnt/data
$ ls /mnt/data
lost+found                        # hidden.txt is invisible — but not gone
$ sudo umount /mnt/data
$ ls /mnt/data
hidden.txt                        # it was there the whole time

This is a genuine production trap: a service writes to /mnt/data before the disk mounts at boot, the mount then happens, and the data vanishes from view while quietly consuming space on the root filesystem.

Mount options change behaviour, not just access. They are the cheapest performance and security lever on a filesystem:

OptionEffectWhen to use
noatimeStop updating access time on every readAlmost always — read turns into a write otherwise
relatimeUpdate atime at most once a day (default)Sensible default; noatime is faster
nodev,nosuid,noexecIgnore device files, setuid bits, execution/tmp, /home, any user-writable mount
roRead-onlyForensics, immutable images, recovery
discardIssue TRIM inline on deleteSSDs — though a weekly fstrim.timer is usually better
nofailBoot continues if the device is missingAny non-essential mount in fstab
$ findmnt /
TARGET SOURCE            FSTYPE OPTIONS
/      /dev/mapper/vg0-root ext4 rw,relatime,errors=remount-ro

$ sudo mount -o remount,noatime /var/lib/postgresql     # change without unmounting

Persistence lives in /etc/fstab, and the one rule that matters is: never identify a device by its kernel name. /dev/sdb is assigned in probe order and can change between boots, silently mounting the wrong disk.

# /etc/fstab
# <device>                                  <mount>   <type>  <options>                <dump> <pass>
UUID=8f3a1c22-4b7e-4a01-9c2f-1d55e0a7b311   /         ext4    defaults,errors=remount-ro  0     1
UUID=b21c9f04-7a3e-42d1-8e5c-9a0f3c1d7e42   /var/log  xfs     defaults,noatime,nofail     0     2
tmpfs                                        /tmp      tmpfs   nosuid,nodev,noexec,size=2G 0     0

❌ Editing /etc/fstab and rebooting to test it. A typo or a wrong UUID drops the machine into emergency mode at boot — and on a cloud VM with no console, that is an unrecoverable instance.

✅ Test before you trust it: sudo mount -a applies every fstab entry that is not already mounted and reports errors immediately, while you still have a shell. systemd-analyze verify catches unit-level problems too. Add nofail to anything non-essential so a missing disk degrades the boot instead of stopping it.

Part 3 — Full Disks: Two Different Ways to Run Out

A filesystem has two finite resources: data blocks and inodes. Exhausting either produces ENOSPC — "No space left on device" — but only one of them shows up in df -h, which is why the second one causes so much confusion.

$ df -h /var
Filesystem      Size  Used Avail Use% Mounted on
/dev/vg0-var     50G   18G   30G  38% /var          # plenty of space...

$ df -i /var
Filesystem       Inodes   IUsed  IFree IUse% Mounted on
/dev/vg0-var    3276800 3276800      0  100% /var   # ...and zero inodes

Thirty gigabytes free and you cannot create a single file. The cause is always the same shape: millions of tiny files — a session directory, a mail queue, a cache that never expires.

# Find the directory hoarding inodes
$ sudo find /var -xdev -type d -printf '%h\n' 2>/dev/null | sort | uniq -c | sort -rn | head -5
1842203 /var/lib/php/sessions
   4021 /var/log/nginx

The other classic is a deleted file that is still open. Unlinking a file removes the directory entry, but the space is only reclaimed when the last file descriptor closes — so du (which walks directory entries) and df (which asks the filesystem) disagree:

$ df -h /var/log
Filesystem      Size  Used Avail Use% Mounted on
/dev/vg0-var     50G   49G  600M  99% /var/log
$ sudo du -sh /var/log
2.1G    /var/log                    # 47 GB unaccounted for

$ sudo lsof -nP +L1 /var/log        # +L1 = link count below 1, i.e. deleted
COMMAND   PID USER   FD   TYPE DEVICE   SIZE/OFF NLINK    NODE NAME
java    60100 app    31w   REG  253,2 47982103552     0  262147 /var/log/app.log (deleted)

Someone ran rm app.log instead of truncating it. The application still holds the descriptor and keeps appending at the same offset. The fixes, in order of preference:

$ : > /var/log/app.log                       # truncate in place — correct, no restart
$ > /proc/60100/fd/31                        # truncate via the still-open descriptor
$ sudo systemctl restart myapp               # last resort: closes the fd, frees the space
SymptomReal causeDiagnosis
Disk full, du shows littleDeleted-but-open filelsof +L1
Disk full, df shows space freeInode exhaustiondf -i
Disk full, du shows little, no open fdsFiles hidden under a mountpointUnmount and look, or du -x
Only root can write when "full"5% reserved blockstune2fs -m 1 to reduce

That last row surprises people: ext4 reserves 5% of the filesystem for root by default, so a "full" disk still lets root and daemons write. On a 4 TB data volume that reserve is 200 GB of wasted space — tune2fs -m 1 is the standard fix for non-root filesystems.

Part 4 — The Page Cache and Durability

A successful write() does not mean the data is on disk. It means the data is in the kernel's page cache, marked dirty, and will be written back later. Understanding this boundary is the difference between a database that survives a power cut and one that does not.

write()  →  page cache (dirty)  →  writeback (30s, or pressure)  →  device cache  →  platters/NAND
                    ↑                                                      ↑
              fsync() forces from here                        FUA/flush forces from here

$ grep -E 'Dirty|Writeback' /proc/meminfo
Dirty:            184320 kB          # written by apps, not yet on disk
Writeback:          8192 kB          # currently in flight to the device

fsync(fd) blocks until that file's data is durable. It is expensive — a fraction of a millisecond on NVMe, several milliseconds on spinning disks — which is exactly why databases batch commits, and why turning fsync off makes a benchmark look brilliant and makes the data worthless.

$ dd if=/dev/zero of=/tmp/t bs=1M count=1000                 # no fsync
1048576000 bytes (1.0 GB) copied, 0.31 s, 3.4 GB/s           # lying: it is in RAM

$ dd if=/dev/zero of=/tmp/t bs=1M count=1000 conv=fsync      # honest
1048576000 bytes (1.0 GB) copied, 2.9 s, 362 MB/s            # the real device speed
🔑 Renaming is the atomic-write primitive. There is no atomic "overwrite this file" syscall, but rename() within a filesystem is atomic: a reader sees either the old file or the new one, never a half-written mix. The safe-save recipe is write to a temp file → fsync the temp file → rename over the target → fsync the directory. Skipping that last step is the subtle bug: the rename itself can be lost in a crash even though the file contents were durable.

Journaling protects filesystem metadata consistency, not your file contents. After a crash the filesystem will be structurally sound, but recently written data may simply be missing:

ext4 journal modeJournalsTrade-off
data=ordered (default)Metadata, with data written firstGood balance — no stale-block exposure
data=writebackMetadata onlyFaster; a crash can expose stale block contents
data=journalMetadata and dataSafest, roughly half the write throughput

Part 5 — Reading I/O Performance

"The disk is slow" is a conclusion, not an observation. Three numbers separate a genuinely slow device from one that is merely saturated by a badly behaved workload.

$ iostat -xz 1 3
Device  r/s     w/s   rkB/s   wkB/s  r_await w_await  aqu-sz  %util
nvme0n1 142.0  891.0  2184.0 108320.0    0.31    8.42   7.84   99.2
                                          ^^^^    ^^^^   ^^^^   ^^^^
                                     fast reads  slow writes  deep queue  saturated
MetricMeansReading it
r_await/w_awaitAverage latency including queue timeThe number users feel. NVMe <1 ms, SSD 1–3 ms, HDD 10–20 ms
aqu-szAverage queue depthHigh + high await = queueing, not device slowness
%utilTime with at least one request in flightMisleading on SSDs — they serve many requests in parallel, so 100% ≠ saturated
rkB/s/wkB/sThroughputCompare against the device's rated speed

Once you know the device is busy, find out who is making it busy:

$ sudo iotop -oPa                          # only processes doing I/O, accumulated
$ sudo pidstat -d 1                        # per-process kB/s read and written
$ sudo biolatency 10 1                     # bcc/eBPF: latency histogram

The distinction that matters most in practice is random versus sequential. A device rated at 3 GB/s sequential may deliver 40 MB/s on 4 KB random I/O — the same hardware, two orders of magnitude apart. A query plan that switched from a sequential scan to random index lookups can look exactly like a failing disk.

Part 6 — LVM, Growing Filesystems, and Repair

LVM decouples the filesystem's size from the partition's. Growing a volume online is routine; shrinking is not, and the order of operations is the part people get wrong.

$ sudo lvextend -L +50G /dev/vg0/data       # grow the logical volume
$ sudo resize2fs /dev/vg0/data              # then grow the ext4 filesystem
$ sudo xfs_growfs /var/lib/postgresql       # xfs: grow by MOUNTPOINT, and only ever grows
Operationext4xfs
Grow onlineresize2fs — yesxfs_growfs — yes
ShrinkOffline only, unmount firstNot supported at all
Check/repairfsck.ext4 -fxfs_repair
Defaults suitGeneral purpose, small filesLarge files, high parallelism

Snapshots make backups consistent. An LVM snapshot is a copy-on-write view frozen at an instant, so you can back up a live database without a long lock:

$ sudo lvcreate -L 10G -s -n data_snap /dev/vg0/data
$ sudo mount -o ro,nouuid /dev/vg0/data_snap /mnt/snap
$ tar -C /mnt/snap -czf /backup/data.tar.gz .
$ sudo umount /mnt/snap && sudo lvremove -f /dev/vg0/data_snap

The snapshot has a fixed size for changed blocks; if writes exceed it, the snapshot is dropped and the backup fails. Size it for the write volume during the backup window, not for the volume's size.

Repair only ever runs on an unmounted filesystem. Running fsck on a mounted one corrupts it — the tool and the kernel would be modifying the same structures simultaneously:

$ sudo umount /dev/vg0/data
$ sudo fsck.ext4 -f -y /dev/vg0/data       # -f force, -y auto-answer
$ sudo smartctl -a /dev/nvme0n1 | grep -Ei 'reallocated|pending|percentage used|media errors'

If SMART reports reallocated sectors climbing or media errors, the correct response is replacement, not repair — fsck fixes the filesystem's bookkeeping, never the hardware underneath it.

Interview Questions

Beginner: What does it mean to "mount" a filesystem?

Unix presents a single directory tree with no drive letters. Mounting attaches a filesystem — living on some block device — to a directory in that tree, called the mountpoint. From that moment, paths under the mountpoint are served by the new filesystem.

$ sudo mount /dev/vg0-data /mnt/data
$ findmnt /mnt/data
TARGET     SOURCE               FSTYPE OPTIONS
/mnt/data  /dev/mapper/vg0-data xfs    rw,relatime

The important consequence is that anything already in the mountpoint directory is hidden, not deleted. Unmount, and it reappears. This causes a real production bug: a service starts before its data disk mounts, writes to the plain directory, the mount then happens, and the data disappears from view while still consuming space on the root filesystem.

Mounts persist across reboots via /etc/fstab, and entries there should identify the device by UUID= rather than /dev/sdb, because kernel device names depend on probe order and can change between boots.

Beginner: df says the disk is full but du only accounts for a fraction. Why?

The two tools ask different questions. du walks the directory tree and adds up the files it can see; df asks the filesystem how many blocks are allocated. When they disagree, something is consuming blocks that has no directory entry.

The overwhelmingly common cause is a deleted file that a process still has open. Unlinking removes the name, but the inode and its blocks survive until the last descriptor closes:

$ sudo lsof -nP +L1 /var/log
COMMAND   PID USER  FD   TYPE  SIZE/OFF NLINK   NAME
java    60100 app   31w   REG 47982103552   0   /var/log/app.log (deleted)

NLINK 0 is the proof. Someone ran rm on a log the application had open; it keeps writing at the same offset into a file with no name.

The fix is to truncate rather than restart: : > /var/log/app.log, or write to /proc/60100/fd/31. Restarting the service also works but is heavier than necessary.

Two other causes worth checking: files hidden underneath a mountpoint (compare with the filesystem unmounted, or use du -x), and ext4's 5% root-reserved blocks, which make a filesystem refuse ordinary writes while root can still write.

Mid: A disk reports "No space left on device" but df -h shows 30 GB free. What is happening?

Almost certainly inode exhaustion. A filesystem allocates a fixed number of inodes at format time; each file, directory, and symlink consumes one. Run out and you cannot create anything, regardless of free bytes:

$ df -i /var
Filesystem       Inodes   IUsed  IFree IUse% Mounted on
/dev/vg0-var    3276800 3276800      0  100% /var

The cause is always millions of small files — PHP session files, an unrotated mail queue, a cache with no eviction. Find the directory holding them:

$ sudo find /var -xdev -type f -printf '%h\n' | sort | uniq -c | sort -rn | head

The immediate fix is deletion, and it needs care: rm * in a directory with two million entries fails on argument-list length, so find ... -delete or find ... -print0 | xargs -0 rm is the correct tool.

The real fix is upstream — expiry on the cache, rotation on the queue. Increasing the inode count requires reformatting (mkfs.ext4 -i 8192), which is a migration, not a tweak. XFS allocates inodes dynamically and mostly sidesteps the problem, which is one reason it is preferred for workloads with unpredictable file counts.

I would also add df -i to monitoring at that point — the alert that would have caught this early is almost never configured.

Mid: What guarantees do you get from write() succeeding? How do you make data durable?

Very few. A successful write() means the bytes are in the kernel's page cache, marked dirty. They will reach the device within about 30 seconds, or sooner under memory pressure. A power cut before then loses them, and the application was told the write succeeded.

$ grep -E 'Dirty|Writeback' /proc/meminfo
Dirty:            184320 kB          # acknowledged to apps, not on disk

fsync(fd) blocks until that file's data and metadata are durable, including flushing the device's own write cache. fdatasync is a cheaper variant that skips metadata not needed for retrieval.

The cost is real, which is why it gets disabled and why disabling it is usually indefensible:

$ dd if=/dev/zero of=/tmp/t bs=1M count=1000               # 3.4 GB/s — page cache
$ dd if=/dev/zero of=/tmp/t bs=1M count=1000 conv=fsync    # 362 MB/s — the truth

The atomic-update recipe matters as much as fsync itself, because there is no atomic overwrite syscall — but rename() within a filesystem is atomic:

  1. Write the new content to file.tmp
  2. fsync(file.tmp)
  3. rename("file.tmp", "file")
  4. fsync the containing directory

Step 4 is the one everyone omits. Without it the rename can be lost in a crash even though the data was durable, leaving the old file intact — usually survivable, but not what the code claimed to guarantee.

Finally, journaling does not help here: ext4's journal protects metadata consistency so the filesystem mounts cleanly, not your file contents. A crash leaves a structurally sound filesystem that is missing your last few seconds of data.

Senior: Users report the application is slow. iostat shows 100% %util. Is the disk the bottleneck?

Not necessarily, and %util is the weakest evidence in that output. It measures the fraction of time at least one request was in flight — meaningful for a spinning disk that serves one request at a time, misleading for NVMe, which serves dozens in parallel. An NVMe device can sit at 100% util at 5% of its capability.

The numbers I would actually read:

$ iostat -xz 1 5
Device  r/s     w/s   rkB/s    wkB/s  r_await w_await  aqu-sz  %util
nvme0n1 142.0  891.0  2184.0 108320.0    0.31    8.42    7.84   99.2
  • w_await 8.4 ms on NVMe is roughly 20× the expected latency — something is genuinely wrong.
  • aqu-sz 7.8 means requests are queueing. High await with a deep queue points at an overwhelming workload; high await with a queue near 1 points at a failing device.
  • 108 MB/s of writes at 891 IOPS implies ~120 KB per write — large, sequential-ish. If it were 4 KB random, the same device could be at its genuine limit.

Then identify the source rather than assuming:

$ sudo iotop -oPa
$ sudo pidstat -d 1
$ sudo biolatency 10 1        # is the distribution bimodal? that suggests the device

The alternative explanations I would rule out before blaming hardware: a workload change from sequential to random access (a lost index turns 3 GB/s into 40 MB/s on identical hardware); memory pressure causing swap traffic that appears as disk I/O; a noisy neighbour on shared cloud storage; and throughput throttling — cloud volumes have IOPS credits, and exhausting a burst balance looks exactly like a dying disk.

Confirm the hardware separately with smartctl -a for reallocated sectors and media errors, and by benchmarking the device directly with fio --direct=1 during a quiet window. That distinguishes "this disk is slow" from "this workload is too much for this disk" — and the two have completely different fixes.

Senior: Design the storage layout for a database server that must survive disk failure and grow over time.

I would separate concerns by access pattern and failure impact, then make growth a routine operation rather than an outage.

1. Separate filesystems, not one big root. Data, WAL/journal, and logs have different I/O patterns and different consequences when full:

/                 50G   ext4   root, packages
/var/lib/pgsql   400G   xfs    data      (noatime, large files, high parallelism)
/var/lib/pgwal    50G   xfs    WAL       (separate device — sequential, latency-critical)
/var/log          20G   ext4   logs      (nofail, rotated)

The reason is blast radius: logs filling up must never stop the database from committing. A single filesystem couples them.

2. Redundancy below the filesystem. RAID 10 for the data volume — mirroring plus striping gives both failure tolerance and write performance, where RAID 5/6 pays a read-modify-write penalty that hurts database workloads badly. On cloud, that responsibility moves to the provider's replicated volume, and the equivalent decision is provisioned IOPS and multi-AZ.

3. LVM for growth. Logical volumes let me extend online:

$ sudo lvextend -L +100G /dev/vg0/data && sudo xfs_growfs /var/lib/pgsql

I would deliberately leave free space in the volume group rather than allocating everything up front — unallocated space is the option to grow whichever volume turns out to need it, and XFS can never shrink, so over-allocating is irreversible.

4. Durability settings that match the promise. fsync on, write barriers enabled, and — critically — verify that the storage controller's write cache is either battery-backed or disabled. A RAID controller with a volatile cache and no BBU silently converts every fsync into a lie, and that is only discovered after a power event.

5. Backups that are tested, not just taken. LVM snapshots give a consistent point-in-time source without a long lock; the snapshot must be sized for the write volume during the backup window or it is dropped mid-run. Backups go off-host — a snapshot on the same failing disk is not a backup — and I would schedule an actual restore drill, because an untested backup is a hypothesis.

6. Monitoring that covers both exhaustion modes. Free bytes, free inodes, await latency, and SMART reallocated-sector counts, with alerts at a level that leaves time to act — 80% is a ticket, 90% is a page. Filling a database's data volume completely tends to require manual recovery, so the alert exists to prevent a state that is expensive to leave.

🏋️ Exercises

1 (easy): Map your machine's entire storage stack from device to mountpoint.
Solution 
$ lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT
NAME          SIZE TYPE FSTYPE      MOUNTPOINT
nvme0n1       477G disk
├─nvme0n1p1     1G part vfat        /boot/efi
├─nvme0n1p2     2G part ext4        /boot
└─nvme0n1p3   474G part LVM2_member
  ├─vg0-root   50G lvm  ext4        /
  └─vg0-home  424G lvm  ext4        /home

Confirm the identifiers that fstab should use:

$ sudo blkid
/dev/nvme0n1p2: UUID="a1b2c3d4-..." TYPE="ext4"
/dev/mapper/vg0-root: UUID="8f3a1c22-..." TYPE="ext4"

$ findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS /
TARGET SOURCE               FSTYPE OPTIONS
/      /dev/mapper/vg0-root ext4   rw,relatime,errors=remount-ro

Check both exhaustion dimensions at once:

$ df -h --output=source,size,used,avail,pcent,target -x tmpfs -x devtmpfs
$ df -i --output=source,itotal,iused,ipcent,target -x tmpfs -x devtmpfs

The two df invocations are the habit worth forming — a disk can be at 30% bytes and 100% inodes, and only the second command reveals it.

2 (easy): Create a filesystem in a file, mount it, and prove that mounting hides the directory's contents.
Solution

A loop-mounted file behaves exactly like a real disk and is safe to experiment on:

$ dd if=/dev/zero of=/tmp/disk.img bs=1M count=100
$ mkfs.ext4 -q /tmp/disk.img
$ sudo mkdir -p /mnt/test
$ echo "I existed before the mount" | sudo tee /mnt/test/before.txt

Mount, and watch the file disappear:

$ sudo mount -o loop /tmp/disk.img /mnt/test
$ ls /mnt/test
lost+found                          # before.txt is gone from view
$ findmnt /mnt/test
TARGET     SOURCE     FSTYPE OPTIONS
/mnt/test  /dev/loop0 ext4   rw,relatime

Unmount, and it returns:

$ sudo umount /mnt/test
$ cat /mnt/test/before.txt
I existed before the mount

Demonstrate the production consequence — the shadowed file still occupies space on the parent filesystem, invisible while the mount is active:

$ sudo dd if=/dev/zero of=/mnt/test/hidden.bin bs=1M count=50
$ df -h / | awk 'NR==2{print "root used:", $3}'
$ sudo mount -o loop /tmp/disk.img /mnt/test
$ du -sh /mnt/test                  # 20K — looks empty
$ df -h / | awk 'NR==2{print "root used:", $3}'   # unchanged: 50 MB still consumed

This is exactly the bug where a service writes before its disk mounts: the data is invisible and the root filesystem fills up for no apparent reason. The guard is mountpoint -q /mnt/test || exit 1 before writing.

Cleanup: sudo umount /mnt/test; sudo rm -rf /mnt/test /tmp/disk.img.

3 (medium): Reproduce the "disk full but du shows nothing" situation and fix it without restarting the process.
Solution

Create a small filesystem so it can actually be filled:

$ dd if=/dev/zero of=/tmp/small.img bs=1M count=200
$ mkfs.ext4 -q /tmp/small.img
$ sudo mkdir -p /mnt/small && sudo mount -o loop /tmp/small.img /mnt/small
$ sudo chmod 777 /mnt/small

Start a writer, then delete the file out from under it:

$ (while true; do dd if=/dev/zero bs=1M count=1 2>/dev/null; sleep 0.2; done) \
>   > /mnt/small/growing.log &
[1] 62100
$ sleep 5
$ rm /mnt/small/growing.log         # the writer still holds the fd

Observe the disagreement:

$ df -h /mnt/small | awk 'NR==2{print "df says used:", $3}'
df says used: 38M
$ du -sh /mnt/small
20K     /mnt/small                  # du sees almost nothing

Find the culprit:

$ sudo lsof -nP +L1 /mnt/small
COMMAND   PID USER  FD  TYPE DEVICE SIZE/OFF NLINK   NODE NAME
dd      62100 dhruv  1w  REG    7,0 39845888     0     12 /mnt/small/growing.log (deleted)

NLINK 0 confirms it: no directory entry, but the inode and its blocks are alive.

Reclaim the space without killing the process by truncating through the open descriptor:

$ sudo truncate -s 0 /proc/62100/fd/1
$ df -h /mnt/small | awk 'NR==2{print "df says used:", $3}'
df says used: 1.1M                  # reclaimed, process still running

The correct habit in the first place — never rm a live log:

$ : > /mnt/small/growing.log        # truncate in place, keeps the inode and the fd valid

This is also precisely what logrotate's copytruncate does, and why the alternative mode requires sending the daemon a signal to reopen its log file.

Cleanup: kill %1; sudo umount /mnt/small; sudo rm -rf /mnt/small /tmp/small.img.

4 (medium): Exhaust inodes on a filesystem that still has plenty of free bytes.
Solution

Format with deliberately few inodes to make the effect quick:

$ dd if=/dev/zero of=/tmp/inodes.img bs=1M count=100
$ mkfs.ext4 -q -N 512 /tmp/inodes.img          # only 512 inodes
$ sudo mkdir -p /mnt/ino && sudo mount -o loop /tmp/inodes.img /mnt/ino
$ sudo chmod 777 /mnt/ino
$ df -i /mnt/ino
Filesystem     Inodes IUsed IFree IUse% Mounted on
/dev/loop1        512    11   501    3% /mnt/ino

Create empty files until it breaks:

$ for i in $(seq 1 600); do touch /mnt/ino/f$i 2>/dev/null || { echo "failed at $i"; break; }; done
failed at 502
$ touch /mnt/ino/onemore
touch: cannot touch '/mnt/ino/onemore': No space left on device

The two views tell opposite stories:

$ df -h /mnt/ino
Filesystem      Size  Used Avail Use% Mounted on
/dev/loop1       93M  1.6M   85M   2% /mnt/ino      # 85 MB free!
$ df -i /mnt/ino
Filesystem     Inodes IUsed IFree IUse% Mounted on
/dev/loop1        512   512     0  100% /mnt/ino    # zero inodes

Locate the offending directory the way you would in production:

$ sudo find /mnt/ino -xdev -type f -printf '%h\n' | sort | uniq -c | sort -rn | head -3
    501 /mnt/ino

Delete safely — rm * would fail on argument-list length with a real million-file directory:

$ sudo find /mnt/ino -xdev -type f -name 'f*' -delete
$ df -i /mnt/ino | awk 'NR==2{print "inodes used:", $3}'
inodes used: 11

The permanent fix is not "add inodes" — that requires reformatting (mkfs.ext4 -i 8192), which is a migration. The real fixes are expiry on whatever generates the files, and adding df -i to monitoring. XFS allocates inodes dynamically and largely avoids the failure mode, which is a legitimate reason to choose it for unpredictable workloads.

Cleanup: sudo umount /mnt/ino; sudo rm -rf /mnt/ino /tmp/inodes.img.

5 (hard): Measure the true cost of durability and prove the atomic-write pattern works.
Solution

1. Show the page cache inflating throughput:

$ sync; echo 3 | sudo tee /proc/sys/vm/drop_caches >/dev/null
$ dd if=/dev/zero of=/tmp/bench bs=1M count=500 2>&1 | tail -1
524288000 bytes (524 MB) copied, 0.16 s, 3.3 GB/s

$ dd if=/dev/zero of=/tmp/bench bs=1M count=500 conv=fsync 2>&1 | tail -1
524288000 bytes (524 MB) copied, 1.42 s, 369 MB/s

Nearly 9× apart on the same hardware. The first number measures memcpy speed.

2. Watch dirty pages accumulate and drain:

$ dd if=/dev/zero of=/tmp/bench2 bs=1M count=800 2>/dev/null &
$ for i in 1 2 3 4 5; do grep -E '^(Dirty|Writeback):' /proc/meminfo | tr '\n' ' '; echo; sleep 1; done
Dirty:  412160 kB Writeback:   32768 kB
Dirty:  688128 kB Writeback:   65536 kB
Dirty:  204800 kB Writeback:  131072 kB     # writeback kicking in
Dirty:       0 kB Writeback:       0 kB     # drained

Between the first and last line, that data existed only in RAM while the application believed it was written.

3. Measure per-operation fsync latency — the number that bounds a database's commit rate:

$ python3 - <<'EOF'
import os, time
fd = os.open('/tmp/fsynctest', os.O_CREAT | os.O_WRONLY, 0o644)
lat = []
for _ in range(200):
    os.write(fd, b'x' * 4096)
    t0 = time.perf_counter(); os.fsync(fd); lat.append((time.perf_counter()-t0)*1000)
os.close(fd); lat.sort()
print(f"p50={lat[100]:.3f} ms  p99={lat[198]:.3f} ms")
EOF
p50=0.412 ms  p99=1.883 ms

At 0.41 ms per fsync, a naive one-commit-per-fsync design caps at roughly 2400 commits/sec — which is exactly why databases group-commit.

4. Prove rename is atomic while a reader hammers the file:

$ printf 'OLD\n' > /tmp/atomic.txt
$ (for i in $(seq 1 20000); do cat /tmp/atomic.txt; done | sort -u > /tmp/seen.txt) &
$ for i in $(seq 1 50); do
>   printf 'NEW\n' > /tmp/atomic.tmp
>   mv /tmp/atomic.tmp /tmp/atomic.txt        # atomic within the same filesystem
>   printf 'OLD\n' > /tmp/atomic.tmp
>   mv /tmp/atomic.tmp /tmp/atomic.txt
> done
$ wait; cat /tmp/seen.txt
NEW
OLD

Only complete values were ever observed — no empty reads, no partial lines. Compare with the naive approach:

$ # printf 'NEW\n' > /tmp/atomic.txt   truncates first — a reader CAN see an empty file

5. The complete safe-save, including the step everyone forgets:

$ python3 - <<'EOF'
import os
path, tmp = '/tmp/safe.json', '/tmp/safe.json.tmp'
with open(tmp, 'w') as f:
    f.write('{"state": "committed"}')
    f.flush(); os.fsync(f.fileno())        # 1. data durable
os.rename(tmp, path)                        # 2. atomic swap
dfd = os.open(os.path.dirname(path), os.O_RDONLY)
os.fsync(dfd); os.close(dfd)                # 3. THE RENAME itself durable
print(open(path).read())
EOF
{"state": "committed"}

Without step 3 the file contents survive a crash but the rename may not, leaving the old file in place. That is usually recoverable, but it is not the guarantee the code appears to make.

6 (hard): Diagnose an I/O problem end to end and decide whether the device or the workload is at fault.
Solution

1. Generate two workloads with identical throughput requirements but opposite access patterns:

$ fio --name=seq --rw=write --bs=1M --size=1G --direct=1 --filename=/tmp/fio.dat \
>     --runtime=15 --time_based --output-format=terse | cut -d';' -f7,8,49
# bandwidth, IOPS, p99 latency
1048576;1024;892

$ fio --name=rand --rw=randwrite --bs=4k --size=1G --direct=1 --filename=/tmp/fio.dat \
>     --runtime=15 --time_based --iodepth=32 --ioengine=libaio --output-format=terse | cut -d';' -f7,8,49
40960;10240;4210

Same device: 1 GB/s sequential versus 40 MB/s random. A workload change alone can produce a 25× drop that looks exactly like failing hardware.

2. Read the live picture while it runs:

$ iostat -xz 1 3
Device  r/s    w/s   rkB/s   wkB/s r_await w_await aqu-sz %util
nvme0n1 0.0 10240.0     0.0 40960.0    0.00    3.12  31.94  100.0
                                                     ^^^^^  ^^^^^
                                          queue depth 32    "saturated"

%util is 100% but the device is doing 10k IOPS — it is busy, not slow. The queue depth of 32 exactly matches what fio was told to submit, which is the giveaway that the queueing is self-inflicted by the workload, not a device limitation.

3. Attribute the I/O to a process:

$ sudo pidstat -d 1 3
UID  PID   kB_rd/s   kB_wr/s  Command
1000 63200      0.00  40912.00  fio

4. Distinguish "device is slow" from "workload is heavy" — the decisive test is latency at low queue depth, where queueing cannot be the explanation:

$ fio --name=probe --rw=randread --bs=4k --iodepth=1 --direct=1 --runtime=10 \
>     --time_based --filename=/tmp/fio.dat --output-format=normal | grep -E 'lat.*avg|IOPS'
   read: IOPS=12.1k, BW=47.3MiB/s
    clat (usec): min=48, avg=79.21, max=1204

79 µs average at queue depth 1 is a healthy NVMe. Conclusion: the device is fine; the earlier 3.12 ms was queueing delay from a deep-queue random workload. If this probe had shown 8 ms, the device itself would be the problem.

5. Check the hardware's own opinion:

$ sudo smartctl -a /dev/nvme0n1 | grep -Ei 'percentage used|media errors|unsafe shutdowns|critical'
Critical Warning:                   0x00
Percentage Used:                    7%
Media and Data Integrity Errors:    0
Unsafe Shutdowns:                   14

6. The decision table this produces:

ObservationConclusionAction
High await, deep queue, low await at qd=1Workload exceeds deviceReduce IOPS, add caching, faster/more devices
High await even at qd=1Device is genuinely slow or failingSMART check, replace, or check cloud IOPS credits
Throughput fine, latency spikyCache flush or GC on the SSDOver-provision, check discard/fstrim
Sudden change with no deployAccess pattern changedCheck query plans, lost index, cache miss rate

The habit worth keeping is the qd=1 probe: it separates the device's intrinsic latency from queueing delay in a single measurement, and that distinction decides whether you buy hardware or fix code.

Cleanup: rm -f /tmp/fio.dat.

🎯 Key Takeaways

  • Storage is a stack — device → partition → LVM → filesystem → mountpoint — and debugging means knowing which layer you are looking at; lsblk shows all of it at once.
  • Mounting grafts a filesystem onto a directory and hides whatever was there; writing to a mountpoint before it mounts silently fills the parent filesystem.
  • Always identify devices by UUID= in /etc/fstab, test with mount -a before rebooting, and add nofail to non-essential mounts.
  • A filesystem can exhaust bytes or inodes independently — df -h only shows the first, so df -i belongs in every full-disk investigation and in monitoring.
  • df and du disagree when a deleted file is still open; lsof +L1 finds it and truncating (: > file) reclaims the space without a restart.
  • ext4 reserves 5% of blocks for root, which is why a "full" disk still accepts root's writes and why tune2fs -m 1 matters on large data volumes.
  • A successful write() only reaches the page cache; fsync is what makes data durable, and it costs 0.1–10 ms depending on the device.
  • Atomic update = write temp → fsync temp → rename → fsync the directory; the last step is the one usually omitted.
  • Journaling protects metadata consistency, not your data — after a crash the filesystem mounts cleanly but recent writes can be gone.
  • %util is misleading on SSDs and NVMe; await and queue depth are the real signals, and latency at queue depth 1 separates a slow device from a heavy workload.
  • Random versus sequential access can change effective throughput by 25× on identical hardware — a lost index looks like a dying disk.
  • LVM allows online growth (lvextend then resize2fs/xfs_growfs); XFS can never shrink, so size decisions are one-way.
  • fsck must only run on an unmounted filesystem, and it repairs bookkeeping — never failing hardware, which SMART will tell you about.
