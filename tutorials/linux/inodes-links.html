Files, Inodes & Links Foundations

What you'll master: the fact that a file has no name — names live in directories and the file itself is an anonymous numbered object — and how that single inversion explains deleting a file you lack write permission on, why df and du disagree, why a rotated log keeps consuming disk, what hard and symbolic links really are and when each breaks, why mv is instant within a filesystem and slow across one, and the atomic-rename pattern that every serious program uses to write a file safely. Prerequisites: The Filesystem & Paths.

Part 1 — A File Has No Name

The mental model most people carry is that a file is a named thing containing bytes. In Unix that is wrong in a way that matters, and correcting it explains a surprising amount of behaviour.

A file is an inode: a numbered record holding the metadata and pointers to the data blocks. It contains everything about the file except its name.

  A DIRECTORY is just a table of (name → inode number)

  /home/alice/               inode 8412 ──┐
  ┌──────────────┬────────┐               │  the actual file:
  │ name         │ inode  │               ├─ size, owner, group
  ├──────────────┼────────┤               ├─ permissions
  │ .            │  4102  │               ├─ timestamps
  │ ..           │  2048  │               ├─ link count
  │ notes.txt    │  8412  │───────────────┤
  │ backup.txt   │  8412  │───────────────┘  ← SAME file, second name
  │ photo.jpg    │  9930  │
  └──────────────┴────────┘

Look up the inode number with ls -i and the whole model becomes visible:

$ cd /tmp && echo "hello" > notes.txt
$ ln notes.txt backup.txt              # a hard link: a second NAME
$ ls -li notes.txt backup.txt
8412 -rw-r--r-- 2 alice alice 6 Aug  8 09:14 backup.txt
8412 -rw-r--r-- 2 alice alice 6 Aug  8 09:14 notes.txt
     ^                        ^
     same inode               link count is 2

Both names refer to one file. Neither is "the original" — the filesystem has no concept of which name came first. Modifying through one name changes the other, because there is only one file:

$ echo "world" >> backup.txt
$ cat notes.txt
hello
world

The stat command shows the full inode contents, and it is worth reading carefully because every field explains a behaviour elsewhere in this track:

$ stat notes.txt
  File: notes.txt
  Size: 12         Blocks: 8          IO Block: 4096   regular file
Device: 259,3      Inode: 8412        Links: 2
Access: (0644/-rw-r--r--)  Uid: ( 1000/  alice)   Gid: ( 1000/  alice)
Access: 2026-08-08 09:14:22.100000000 +0000
Modify: 2026-08-08 09:15:03.480000000 +0000
Change: 2026-08-08 09:15:03.480000000 +0000
 Birth: 2026-08-08 09:14:22.100000000 +0000

Note what is absent: the name. The inode does not know it. That is not an implementation detail — it is the design, and Part 2 shows what it costs and buys.

🔑 The consequence that catches everyone. Because the name lives in the directory, deleting a file is a directory operation, not a file operation. You need write permission on the directory, and the file's own permissions are irrelevant. This is why you can delete a root-owned, read-only file from a directory you own — and why /tmp needs the sticky bit to stop users deleting each other's files.

Part 2 — Link Counts and What Delete Really Means

There is no delete system call. The call is unlink, and its name is precise: it removes a name→inode entry from a directory and decrements the inode's link count.

unlink("notes.txt"):
   1. Remove the entry "notes.txt" from the directory
   2. Decrement the inode's link count
   3. IF link count == 0 AND no process has it open:
         free the data blocks and the inode
      ELSE:
         do nothing — the file survives

Two independent conditions must both be false for the data to be freed. Watch the count fall:

$ ls -li notes.txt backup.txt
8412 -rw-r--r-- 2 alice alice 12 Aug  8 09:15 backup.txt
8412 -rw-r--r-- 2 alice alice 12 Aug  8 09:15 notes.txt

$ rm notes.txt
$ ls -li backup.txt
8412 -rw-r--r-- 1 alice alice 12 Aug  8 09:15 backup.txt    # count now 1
$ cat backup.txt
hello
world                                                        # data intact

The second condition — an open file descriptor — is the one that produces production incidents. A process holding the file open keeps the data alive even at link count zero:

$ python3 -c "
import time
f = open('/tmp/big.log', 'w')
f.write('x' * 100_000_000)
f.flush()
import os; os.unlink('/tmp/big.log')     # unlinked while still open
print('unlinked, sleeping'); time.sleep(300)
" &

$ ls -l /tmp/big.log
ls: cannot access '/tmp/big.log': No such file or directory   # gone from the directory

$ df -h /tmp | tail -1
tmpfs    7.8G  1.3G  6.5G  17% /tmp                            # but space still used

$ lsof +L1 /tmp 2>/dev/null
COMMAND   PID  USER FD TYPE DEVICE SIZE/OFF NLINK NODE NAME
python3 52104 alice  3w  REG  0,26 100000000     0 4521 /tmp/big.log (deleted)
                                                  ^
                                          NLINK 0 — the signature

This is exactly the df/du disagreement from the previous lesson. du walks directory entries, so it cannot see a file with no name. df asks the filesystem how many blocks are allocated, so it can. The file is unreachable but not freed.

SituationLink countOpen FDsData freed?
Normal file10Not until unlinked
Hard-linked twice, one removed10No — the other name holds it
Rotated log, writer not signalled01No — the classic leak
Writer restarted / signalled00Yes, immediately
Deliberate temp file pattern01On process exit — guaranteed cleanup

That last row is a genuinely useful technique rather than a bug. Create a file, unlink it immediately, and keep the descriptor: you now have private scratch space with no name, invisible to other processes, automatically reclaimed when your process exits even if it crashes. No cleanup handler can fail to run. Modern kernels expose this directly as O_TMPFILE.

Part 3 — Hard Links vs Symbolic Links

These are often taught as two flavours of the same thing. They are structurally different objects and the differences are all predictable from Part 1.

A hard link is another directory entry pointing at the same inode. It is not a reference to a file — it is the file, equally. A symbolic link is a separate inode of its own whose data is a path string, resolved at every access.

HARD LINK                          SYMBOLIC LINK

  "a.txt" ──┐                        "link" (inode 9001)
            ├──→ inode 8412              data = "/tmp/a.txt"
  "b.txt" ──┘    [the data]                     │
                                                └──→ resolved on each access
  Both are the file.                                 → inode 8412
  No indirection.                    An extra hop, and a path that may not exist.

$ echo data > /tmp/a.txt
$ ln    /tmp/a.txt /tmp/hard.txt
$ ln -s /tmp/a.txt /tmp/soft.txt
$ ls -li /tmp/a.txt /tmp/hard.txt /tmp/soft.txt
8412 -rw-r--r-- 2 alice alice  5 Aug  8 09:30 /tmp/a.txt
8412 -rw-r--r-- 2 alice alice  5 Aug  8 09:30 /tmp/hard.txt
9001 lrwxrwxrwx 1 alice alice 10 Aug  8 09:30 /tmp/soft.txt -> /tmp/a.txt
^                                                             ^
different inode, type 'l', size 10 = length of the path string

The symlink's size is 10 bytes — precisely the length of /tmp/a.txt. That is all it contains. Now delete the original and watch them diverge:

$ rm /tmp/a.txt
$ cat /tmp/hard.txt
data                                    # fine — it IS the file
$ cat /tmp/soft.txt
cat: /tmp/soft.txt: No such file or directory     # dangling: path no longer resolves
PropertyHard linkSymbolic link
What it isA directory entry → the same inodeA separate inode containing a path
Survives deleting the "original"Yes — there is no originalNo — becomes dangling
Can cross filesystemsNo — inode numbers are per-filesystemYes — it is just text
Can link a directoryNo (except ./.., made by the kernel)Yes
Extra resolution costNoneAn extra lookup per access
Can point at nothingImpossibleYes — dangling is legal
Own permissionsN/A — shares the inode'sAlways lrwxrwxrwx; the target's apply
Shows in du twice?No — counted onceNo — only the tiny link

The cross-filesystem restriction is not arbitrary. A directory entry stores an inode number, and that number is only meaningful within one filesystem. Inode 8412 exists on nearly every filesystem on the machine, referring to something different on each:

$ ln /tmp/x /home/alice/x
ln: failed to create hard link '/home/alice/x' => '/tmp/x': Invalid cross-device link

That error — EXDEV — is the same one that makes mv behave differently depending on where you move things, which is Part 4.

❌ ln -s app-v2 current then later ln -s app-v3 current — the second command fails with "File exists", or worse, if current is already a symlink to a directory, it creates current/app-v3 inside the target. Deploy scripts have broken production this way.

✅ ln -sfn app-v3 current — -f replaces an existing link and -n treats an existing symlink-to-directory as a file rather than descending into it. For true atomicity, create a new link and mv -T it over: the rename is atomic, so no observer ever sees a missing current.

Part 4 — Why mv Is Sometimes Instant and Sometimes Slow

Renaming a 40 GB file within one filesystem is instantaneous. Moving it to another filesystem takes minutes. Part 1 already explains why, but it is worth making explicit because it drives real design decisions.

mv /var/data/big.bin /var/backup/big.bin       # SAME filesystem
   → rename(): delete one directory entry, create another
   → the inode and every data block are untouched
   → atomic, instant, no data copied

mv /var/data/big.bin /mnt/other/big.bin        # DIFFERENT filesystem
   → rename() fails with EXDEV
   → mv falls back to: open source, open dest, copy all bytes, unlink source
   → slow, NOT atomic, and interruptible halfway

$ dd if=/dev/zero of=/tmp/big.bin bs=1M count=2000 2>/dev/null

$ time mv /tmp/big.bin /tmp/renamed.bin            # within tmpfs
real    0m0.001s

$ time mv /tmp/renamed.bin /home/alice/big.bin     # across filesystems
real    0m2.140s

The operational consequences are significant:

ConsequenceWhy it follows
Same-filesystem mv is atomic; cross-filesystem is notOne is a single rename(); the other is copy-then-delete with a window in between
A cross-filesystem mv interrupted leaves a partial destinationThe copy is not transactional; the source is only removed at the end
You need free space on the destination for the full fileBoth copies exist simultaneously during the transfer
Cross-filesystem moves may lose metadataHard links between moved files are broken; xattrs may not transfer
Docker "moving" between layers is slowEach layer is effectively a different filesystem — this is a real container performance trap

Because same-filesystem rename() is atomic, it is the foundation of the most important pattern in this lesson.

Part 5 — The Atomic Write Pattern

Writing a configuration file the obvious way is unsafe:

$ generate_config > /etc/app/config.json          # DON'T

The shell truncates the file to zero the instant it opens it, before a single byte is written. If the generator fails, the machine loses power, or the disk fills, the file is left empty or half-written — and any process reading it concurrently may see a truncated file that parses as valid but means something different.

The correct approach uses rename()'s atomicity: write to a temporary file in the same directory, then rename over the target. There is no instant at which an observer sees anything other than the complete old file or the complete new one.

#!/usr/bin/env bash
set -euo pipefail

target=/etc/app/config.json
# Same directory is essential — a different filesystem means no atomic rename
tmp=$(mktemp "$(dirname "$target")/.config.XXXXXX")

# Clean up the temp file if anything below fails
trap 'rm -f "$tmp"' EXIT

generate_config > "$tmp"
chmod 644 "$tmp"                    # mktemp creates 0600
sync                                # optional: force data to disk before renaming
mv -f "$tmp" "$target"              # atomic rename; trap now has nothing to remove
trap - EXIT

The three details that are easy to get wrong:

DetailWhy it matters
Temp file in the same directory/tmp is usually a different filesystem, so the rename becomes a non-atomic copy
chmod before the renamemktemp creates mode 0600; fixing permissions after the rename leaves a window where the file is unreadable
sync/fsync before renamingRename is atomic with respect to other processes, but a power loss can still leave the new name pointing at unwritten data

This is not an exotic technique — it is what every editor, package manager, and database does. strace on vim saving a file shows exactly this dance. When you see a directory containing .#config.json.swp or config.json.tmpXXXX, you are watching it happen.

🔑 Atomic against crashes, not against readers-mid-read. A process that already has the old file open keeps reading the old inode — the rename does not affect open descriptors. That is usually what you want (readers see a consistent old version rather than a changing file), but it means a long-running process will not notice the new config until it reopens the path. That is precisely why daemons need a SIGHUP handler, covered in Signals & Job Control.

Part 6 — Timestamps, and the Fourth One Nobody Knows

stat reports four times, and confusing them costs people hours during investigations.

FieldNameUpdated whenCan a user forge it?
atimeAccessFile contents are readYes — touch -a
mtimeModifyFile contents changeYes — touch -m
ctimeChangeThe inode changes: contents, permissions, owner, or link countNo
btimeBirthFile creation (not on all filesystems)No, but often unavailable

ctime is the forensically interesting one because it cannot be set by any user-facing call. An attacker who backdates a modified file with touch resets mtime but necessarily bumps ctime in doing so:

$ echo original > /tmp/f.txt && sleep 1
$ echo tampered > /tmp/f.txt
$ touch -d '2020-01-01 00:00' /tmp/f.txt        # backdate it

$ stat -c 'mtime=%y%nctime=%z' /tmp/f.txt
mtime=2020-01-01 00:00:00.000000000 +0000       # looks old
ctime=2026-08-08 09:52:11.334000000 +0000       # but the inode changed just now

An mtime far older than its ctime is a red flag worth investigating. find -newerct searches by ctime specifically, which is the right tool during an incident:

$ find /usr/bin -newerct '2026-08-01' -type f -ls    # binaries whose inode changed recently

The other practical timestamp fact is that atime updates are a write. Reading a file causing a disk write is absurd on a busy server, so Linux defaults to relatime, which only updates atime if it was older than mtime or more than a day stale. On write-heavy filesystems, noatime removes the cost entirely — a genuinely free performance win discussed in Storage & Filesystems.

Interview Questions

Beginner: What is an inode, and what is not stored in it?

An inode is the filesystem's record of a file: its size, owner, group, permissions, timestamps, link count, and pointers to the data blocks. Every file has exactly one, identified by a number unique within its filesystem.

What is not in it is the filename. Names live in directories, which are tables mapping names to inode numbers. The file itself has no idea what it is called, and may be called several things at once.

Two consequences follow immediately. Deleting a file requires write permission on the directory, not the file — which is why you can delete a root-owned read-only file from your own directory. And a file can have multiple equal names (hard links) with no notion of which is original.

Inodes are also a finite resource allocated at filesystem creation, so a filesystem can run out of inodes while blocks remain free — df -i catches it, and the error is a confusing "No space left on device".

Beginner: What is the difference between a hard link and a symbolic link?

A hard link is an additional directory entry pointing at the same inode. It is not a reference to the file — it is the file, exactly as much as any other name. A symbolic link is a separate file of its own whose contents are a path string, resolved anew at every access.

The differences all follow from that. Delete the "original" and the hard link still works, because there was never an original — only a link count that dropped from 2 to 1. Delete a symlink's target and the symlink dangles, because the path it stores no longer resolves.

A hard link cannot cross filesystems, because a directory entry stores an inode number and those numbers are only meaningful within one filesystem. A symlink can point anywhere, including at nothing, because it is just text.

Practically: use symlinks for convenience and version switching (current → app-v3); use hard links when you need two names to genuinely be one file, as deduplicating backup tools like rsync --link-dest do.

Mid: A log was rotated hours ago but disk space was never reclaimed. Explain and fix it.

The rotation removed the directory entry while the writing process still had the file open. Freeing data requires both a link count of zero and no open descriptors; only the first condition was met, so the inode and all its blocks survive with no name.

This is exactly why du and df disagree here: du walks directory entries and cannot see a nameless file, while df asks the filesystem about allocated blocks and can.

Confirm it:

$ lsof +L1 2>/dev/null | awk 'NR==1 || $NLINK==0'
COMMAND  PID USER FD TYPE DEVICE  SIZE/OFF NLINK NODE NAME
nginx   2210 www   5w REG  259,3 8421990400    0  512 /var/log/nginx/access.log (deleted)

The NLINK 0 plus (deleted) is the signature.

Fix, in order of preference: signal the daemon to reopen its logs — kill -USR1 2210 for nginx, or systemctl reload. That closes the old descriptor and the space is reclaimed instantly. If a reopen is not supported, truncating through /proc works without stopping the process: : > /proc/2210/fd/5. Restarting the service works too. Never kill -9 — it discards buffered writes.

Prevent it properly: logrotate's postrotate stanza should signal the writer. When a daemon genuinely cannot reopen, copytruncate is the fallback — it copies then truncates in place so the descriptor stays valid, at the cost of a small window where lines can be lost.

Mid: Why is mv instant within a filesystem and slow across one?

Within one filesystem, mv is a single rename() syscall: it removes one name→inode entry and creates another. The inode and every data block are untouched, so the cost is independent of file size — renaming a 40 GB file is as fast as renaming an empty one.

Across filesystems, rename() fails with EXDEV (invalid cross-device link), because a directory entry can only reference inode numbers within its own filesystem. mv then falls back to copying every byte to a new inode on the destination and unlinking the source.

The important operational differences: the same-filesystem case is atomic, so no observer ever sees a partial state, while the cross-filesystem case has a long window where both or neither exist and an interruption leaves a partial destination. The cross case also needs free space for a second full copy, and breaks any hard links the file participated in.

This is why the atomic-write pattern insists the temporary file be created in the same directory as the target — putting it in /tmp silently downgrades an atomic rename to a non-atomic copy, defeating the entire purpose.

Senior: Design a safe procedure for updating a config file that a running service reads, with no window of inconsistency.

There are two distinct problems: making the file's content change atomically, and making the service notice the change. Solving only the first is the common half-measure.

Atomic content change — write, sync, rename.

tmp=$(mktemp /etc/app/.config.XXXXXX)   # same directory: required for atomic rename
trap 'rm -f "$tmp"' EXIT
generate_config > "$tmp"
validate_config "$tmp" || exit 1        # validate BEFORE it can be seen
chown app:app "$tmp" && chmod 640 "$tmp"
sync                                     # data durable before the name points at it
mv -f "$tmp" /etc/app/config.json        # atomic
trap - EXIT

Every line is load-bearing. Same directory, or the rename is a copy. Validate before the rename, so a broken config never becomes visible. Set ownership and mode before, or there is a window where the service cannot read it. sync before, or a power cut can leave the name pointing at unwritten blocks — atomic against processes is not the same as durable against crashes.

Making the service notice. The rename does not affect already-open descriptors, so a process holding the file open continues reading the old inode indefinitely. That is a feature — it guarantees a consistent view — but it means you must trigger a reopen. In order of robustness: systemctl reload if the unit defines ExecReload=; a direct SIGHUP if the daemon documents it; inotify-based auto-reload if the application supports it, though this is racy against partial writes unless the app watches for the rename specifically rather than for writes.

What I would add in production. Reload rather than restart, so in-flight requests survive. Keep the previous version (config.json.prev) so rollback is another rename rather than a re-generation. Check the service's health after reload and roll back automatically if it degrades — the rename being atomic does not mean the new config is correct. And verify the reload actually happened: ls -l /proc/PID/fd showing the config still marked (deleted) means the service is running on the old file and your deploy silently did nothing.

Senior: How would you build a space-efficient daily backup system using only links, and what are its limits?

The technique is hard-link deduplication: each daily snapshot is a full directory tree, but unchanged files are hard links to the previous day's inode, so identical content is stored once.

rsync -a --delete \
      --link-dest=/backups/2026-08-07 \
      /srv/data/ /backups/2026-08-08/

--link-dest compares each source file against the reference tree; if unchanged, it creates a hard link instead of copying. The result is that every snapshot looks like a complete independent copy — you can restore any day by copying one directory, with no chain of incrementals to replay — while consuming space proportional to the changes.

Why it works: because a hard link is not a reference to a file, deleting yesterday's snapshot is safe. It just decrements link counts; blocks are only freed when the last snapshot referencing them is removed. Retention pruning is a plain rm -rf of a dated directory, with no special logic.

The limits, which are real:

  • Modifying a file in place corrupts every snapshot, because they are all the same inode. This only works because rsync replaces changed files (write-temp-then-rename) rather than editing them. A tool that edits in place, or an admin who edits a file inside a snapshot, silently rewrites history.
  • Inode exhaustion. Every snapshot needs its own directory entries; millions of small files across hundreds of snapshots can exhaust inodes while blocks stay free — df -i, not df -h, is the metric to alarm on.
  • Single filesystem only. Hard links cannot cross devices, so the entire backup set must live on one filesystem — which is also a single point of failure. This is a snapshot system, not an offsite backup, and it protects against accidental deletion, not against the disk dying or ransomware that walks the tree.
  • No block-level deduplication. A one-byte change to a 10 GB file stores another 10 GB. Tools like restic or borg deduplicate at chunk level and handle this far better.

I would use this for fast local point-in-time recovery, paired with a genuinely offsite, content-addressed backup for disaster recovery. Or, on ZFS/btrfs, use native snapshots instead — they are copy-on-write at block level and avoid every limitation above.

🏋️ Exercises

1 (easy): Prove that a file's name is not part of the file.
Solution 
$ cd /tmp && echo "content" > one.txt
$ ln one.txt two.txt && ln one.txt three.txt
$ ls -li *.txt
8801 -rw-r--r-- 3 alice alice 8 Aug  8 10:12 one.txt
8801 -rw-r--r-- 3 alice alice 8 Aug  8 10:12 three.txt
8801 -rw-r--r-- 3 alice alice 8 Aug  8 10:12 two.txt

One inode (8801), three names, link count 3. Now delete the "original" and show nothing was lost:

$ rm one.txt
$ cat two.txt
content
$ stat -c 'inode=%i links=%h' two.txt
inode=8801 links=2

Modify through one name and read through another — there is only one file:

$ echo "appended" >> three.txt
$ cat two.txt
content
appended

The filesystem has no record of which name came first. one.txt was not special; it was one of three equal entries pointing at the same numbered object.

2 (easy): Show that deleting a file depends on directory permissions, not file permissions.
Solution 
$ mkdir /tmp/mydir
$ sudo sh -c 'echo secret > /tmp/mydir/root-owned.txt'
$ sudo chmod 400 /tmp/mydir/root-owned.txt          # read-only, root-owned
$ ls -l /tmp/mydir/
-r-------- 1 root root 7 Aug  8 10:20 root-owned.txt

$ cat /tmp/mydir/root-owned.txt
cat: /tmp/mydir/root-owned.txt: Permission denied    # cannot READ it

$ rm /tmp/mydir/root-owned.txt
rm: remove write-protected regular file '/tmp/mydir/root-owned.txt'? y
$ ls /tmp/mydir/
                                                     # deleted it anyway

You cannot read a single byte of the file, but you can destroy it — because deletion modifies the directory, which you own. rm's prompt is a courtesy from rm, not a kernel restriction; rm -f skips it silently.

The reverse confirms it. Remove your write permission on the directory and deletion becomes impossible even for a file you own outright:

$ echo mine > /tmp/mydir/mine.txt
$ chmod 555 /tmp/mydir                              # r-x: no write on the directory
$ rm /tmp/mydir/mine.txt
rm: cannot remove '/tmp/mydir/mine.txt': Permission denied

This is exactly why /tmp needs the sticky bit (mode 1777). It is world-writable so anyone can create files, but the sticky bit adds the rule that you may only remove entries you own — otherwise any user could delete every other user's temp files.

3 (medium): Reproduce the "deleted file still consuming space" incident and reclaim the space without restarting the process.
Solution 
# Start a writer that holds the file open
$ python3 -u -c "
import time
f = open('/tmp/leak.log','w')
for i in range(500):
    f.write('x'*200000 + chr(10)); f.flush(); time.sleep(0.5)
" &
[1] 53880

$ sleep 5 && ls -lh /tmp/leak.log
-rw-r--r-- 1 alice alice 2.0M Aug  8 10:31 /tmp/leak.log

# "Rotate" it the wrong way — remove the name, don't tell the writer
$ rm /tmp/leak.log
$ ls /tmp/leak.log
ls: cannot access '/tmp/leak.log': No such file or directory

The name is gone, but the writer keeps writing and the space keeps growing:

$ du -sh /tmp 2>/dev/null
1.1M    /tmp                       # du sees nothing
$ df -h /tmp | tail -1
tmpfs  7.8G  6.2M  7.8G   1% /tmp  # df sees it, and it climbs

$ lsof +L1 /tmp 2>/dev/null
COMMAND    PID  USER  FD TYPE DEVICE SIZE/OFF NLINK NODE NAME
python3  53880 alice   3w REG  0,26  6400000     0 4901 /tmp/leak.log (deleted)

NLINK 0 confirms the diagnosis. Reclaim without killing the process by truncating through its own file descriptor in /proc:

$ ls -l /proc/53880/fd/3
l-wx------ 1 alice alice 64 Aug  8 10:32 /proc/53880/fd/3 -> '/tmp/leak.log (deleted)'

$ : > /proc/53880/fd/3              # truncate to zero
$ lsof +L1 /tmp 2>/dev/null | awk 'NR>1 {print $7, $9}'
0 /tmp/leak.log

Space is reclaimed instantly and the process is unaffected — it keeps writing at its current offset, so the file will show as sparse until it catches up. This is the emergency technique when a disk is full at 3am and restarting the service is not acceptable.

The proper fix is signalling: kill -USR1 for daemons that reopen logs, configured in logrotate's postrotate. Cleanup: kill %1.

4 (medium): Demonstrate why the atomic-write temp file must be in the same directory as the target.
Solution

First establish that /tmp and the target are different filesystems, which is the whole issue:

$ findmnt -n -o SOURCE,FSTYPE -T /tmp
tmpfs tmpfs
$ findmnt -n -o SOURCE,FSTYPE -T /home/alice
/dev/nvme0n1p4 ext4

The wrong version — temp in /tmp. Trace what mv actually does:

$ dd if=/dev/zero of=/tmp/staging.dat bs=1M count=500 2>/dev/null
$ strace -e trace=rename,renameat2,openat,read,write -c \
      mv /tmp/staging.dat /home/alice/config.dat 2>&1 | tail -6
% time     seconds  usecs/call     calls    errors syscall
 52.10    0.121043          15      8192           read
 47.20    0.109655          13      8192           write
  0.02    0.000041          41         1         1 renameat2

renameat2 was attempted once and failed (EXDEV), then 8192 read/write pairs copied the data. There is a multi-second window where the destination exists but is incomplete — any reader during it sees a truncated file.

The right version — temp in the same directory:

$ dd if=/dev/zero of=/home/alice/.staging.dat bs=1M count=500 2>/dev/null
$ strace -e trace=rename,renameat2,read,write -c \
      mv /home/alice/.staging.dat /home/alice/config.dat 2>&1 | tail -4
% time     seconds  usecs/call     calls    errors syscall
100.00    0.000032          32         1           renameat2

One syscall, no reads, no writes, no error. The operation is instantaneous and atomic regardless of file size.

Prove the atomicity matters by having a reader poll during each version. With the cross-filesystem move, a concurrent cat can catch a partial file; with the rename, every read returns either the complete old file or the complete new one, never anything in between. That is the entire justification for the pattern.

5 (hard): Detect tampering using ctime, and explain why an attacker cannot hide it with touch.
Solution 
$ echo "legitimate content" > /tmp/app.conf
$ touch -d '2026-01-15 09:00' /tmp/app.conf         # establish a plausible history
$ stat -c 'mtime=%y  ctime=%z' /tmp/app.conf
mtime=2026-01-15 09:00:00.000000000 +0000  ctime=2026-08-08 10:45:02.118000000 +0000

Note that even this setup leaves ctime at "now" — touch changed the inode, and the inode change time cannot be suppressed.

Simulate the attack: modify the file, then backdate it to cover the tracks:

$ sleep 2
$ echo "malicious addition" >> /tmp/app.conf
$ touch -d '2026-01-15 09:00' /tmp/app.conf         # attacker restores the old mtime

$ stat -c 'mtime=%y%nctime=%z' /tmp/app.conf
mtime=2026-01-15 09:00:00.000000000 +0000           # looks untouched since January
ctime=2026-08-08 10:45:12.902000000 +0000           # but the inode changed 10s ago

Why it cannot be hidden: utimensat() — the syscall behind touch — sets atime and mtime only. There is deliberately no interface to set ctime, because ctime is "when this inode last changed", and setting it would itself be a change. The only ways around it are writing to the raw block device (requires root and unmounting, and leaves other traces) or recreating the whole filesystem.

Hunt for it across a directory tree — files whose ctime is far newer than their mtime are the anomaly:

$ find /etc -type f -printf '%C@ %T@ %p\n' 2>/dev/null \
  | awk '$1 - $2 > 86400 { printf "ctime %d days newer: %s\n", ($1-$2)/86400, $3 }' \
  | head
ctime 205 days newer: /etc/app.conf

A legitimate edit updates both together, so a large gap needs an explanation. Benign causes exist — chmod, chown, and package manager restores all bump ctime alone — so this is a triage filter, not proof.

The limitation worth stating: ctime is only useful if you have a baseline or the attacker was careless. A file created by an attacker has consistent, freshly-set timestamps and shows no anomaly at all. Real integrity monitoring (AIDE, Tripwire) stores cryptographic hashes off-host, because timestamps are a heuristic and hashes are evidence.

6 (hard): Build the hard-link snapshot backup system, verify the space saving, and demonstrate the failure mode that breaks it.
Solution 
$ mkdir -p /tmp/src && cd /tmp/src
$ dd if=/dev/urandom of=big1.dat bs=1M count=50 2>/dev/null
$ dd if=/dev/urandom of=big2.dat bs=1M count=50 2>/dev/null
$ echo "v1" > small.txt

$ mkdir -p /tmp/backups
$ rsync -a /tmp/src/ /tmp/backups/day1/           # first snapshot: full copy
$ du -sh /tmp/backups
101M    /tmp/backups

Change one small file, then take a second snapshot linked against the first:

$ echo "v2" > /tmp/src/small.txt
$ rsync -a --delete --link-dest=/tmp/backups/day1 /tmp/src/ /tmp/backups/day2/

$ du -sh /tmp/backups/day1 /tmp/backups/day2
101M    /tmp/backups/day1
4.0K    /tmp/backups/day2               # only the changed file is new
$ du -sh /tmp/backups
101M    /tmp/backups                    # total barely moved

Yet day2 is a complete, independently restorable tree:

$ ls /tmp/backups/day2
big1.dat  big2.dat  small.txt
$ ls -li /tmp/backups/day1/big1.dat /tmp/backups/day2/big1.dat
9112 -rw-r--r-- 2 alice alice 52428800 Aug  8 11:02 /tmp/backups/day1/big1.dat
9112 -rw-r--r-- 2 alice alice 52428800 Aug  8 11:02 /tmp/backups/day2/big1.dat
                ^ same inode, link count 2 — stored once, visible twice

$ ls -li /tmp/backups/day1/small.txt /tmp/backups/day2/small.txt
9120 -rw-r--r-- 1 alice alice 3 ... /tmp/backups/day1/small.txt
9131 -rw-r--r-- 1 alice alice 3 ... /tmp/backups/day2/small.txt
                ^ different inodes — the changed file was genuinely copied

Pruning is safe precisely because a hard link is not a reference:

$ rm -rf /tmp/backups/day1
$ cat /tmp/backups/day2/small.txt && ls -lh /tmp/backups/day2/big1.dat | awk '{print $5}'
v2
50M                                     # day2 is still complete

Now the failure mode. Because snapshots share inodes, editing a file in place rewrites every snapshot at once:

$ rsync -a --link-dest=/tmp/backups/day2 /tmp/src/ /tmp/backups/day3/
$ echo "CORRUPTED" >> /tmp/backups/day3/big2.dat    # in-place edit inside a snapshot
$ tail -c 10 /tmp/backups/day2/big2.dat
CORRUPTED                                            # day2 changed too!

The whole scheme depends on every writer replacing files rather than editing them — which is exactly what rsync does (write temp, then rename), and exactly what a careless admin with an editor does not. Any tool that opens a file inside a snapshot for writing silently rewrites history across every snapshot sharing that inode.

Guard against it by making snapshots read-only after creation (chmod -R a-w, or mounting the backup filesystem read-only between runs), and monitor df -i rather than df -h — inode exhaustion, not block exhaustion, is what actually kills these systems. For anything beyond local point-in-time recovery, use a content-addressed tool (restic, borg) or filesystem-native snapshots (ZFS, btrfs), which deduplicate at block level and are immune to the in-place-edit problem entirely.

🎯 Key Takeaways

  • A file is an inode — a numbered record of metadata and block pointers. The name is not in it; names live in directories as name→inode entries.
  • Deleting requires write permission on the directory, not the file, which is why /tmp needs the sticky bit.
  • There is no delete syscall — unlink() removes a name and decrements the link count; data is freed only when the count hits zero and no process has it open.
  • A deleted-but-open file is the classic disk-full mystery: du can't see it, df can. Find it with lsof +L1 and the NLINK 0 signature.
  • Reclaim that space without a restart by truncating through /proc/PID/fd/N; fix it properly by signalling the writer to reopen.
  • A hard link is another name for the same inode — equal, indistinguishable, confined to one filesystem. A symlink is a separate file holding a path, resolved fresh on every access.
  • Symlinks can dangle and cross filesystems; hard links can do neither, because inode numbers are only meaningful within one filesystem.
  • mv within a filesystem is one atomic rename(), independent of file size; across filesystems it degrades to copy-then-delete, which is slow and non-atomic.
  • The atomic-write pattern is write-temp → validate → chmod → sync → rename, with the temp file in the same directory or the atomicity is lost.
  • Rename is atomic for new readers but does not affect already-open descriptors — daemons need a reload signal to pick up a new config.
  • Of the four timestamps, ctime is the only one users cannot forge, making an mtime far older than its ctime a tampering red flag.
  • Hard-link snapshots give near-free full backups, but break if anything edits files in place, and fail on inode exhaustion rather than disk space.
