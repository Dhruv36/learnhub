Signals & Job Control Processes & The Kernel

What you'll master: signals as asynchronous interrupts with a delivery model that explains every surprising behaviour — why standard signals are not queued and identical ones collapse, why only two are truly uncatchable, what "async-signal-safe" means and why a handler that calls printf can deadlock, how trap works in shell scripts and why cleanup handlers so often fail to run, the terminal's role in Ctrl-C and Ctrl-Z, and the exact signal sequence systemd and Docker use to stop a service. Prerequisites: Processes, fork & exec.

Part 1 — What a Signal Is

A signal is the kernel's mechanism for interrupting a process asynchronously. It carries no data beyond its number — it is a doorbell, not a message. When one arrives, the kernel suspends the process at whatever instruction it was executing, runs the handler, and resumes.

Signal№Default actionTypical cause
SIGHUP1TerminateTerminal closed; by convention, "reload config"
SIGINT2TerminateCtrl-C
SIGQUIT3Terminate + coreCtrl-\
SIGKILL9Terminate — uncatchableForced kill; OOM killer
SIGSEGV11Terminate + coreInvalid memory access
SIGPIPE13TerminateWrote to a pipe with no reader
SIGTERM15TerminatePolite shutdown request — the default of kill
SIGCHLD17IgnoredA child exited or stopped
SIGSTOP19Stop — uncatchableForced suspend
SIGTSTP20StopCtrl-Z
SIGCONT18Continuefg / bg
SIGUSR1/210/12TerminateApplication-defined — often "reopen logs"

A process has four possible responses to each signal, and /proc/PID/status reports which apply:

  1. Default action    — terminate, stop, ignore, or dump core
  2. Ignore it         — signal(SIGTERM, SIG_IGN)
  3. Catch it          — run a handler function
  4. Block it          — defer delivery until unblocked (stays pending)

$ grep -E 'Sig(Blk|Ign|Cgt)' /proc/self/status
SigBlk: 0000000000000000        # blocked (deferred)
SigIgn: 0000000000381000        # ignored
SigCgt: 000000004b817efb        # caught by a handler

These are bitmasks where bit N-1 corresponds to signal N. SIGTERM is 15, so bit 15 has value 0x4000. Reading them answers "why is this process ignoring my signal?", which no standard tool surfaces directly.

Exactly two signals cannot be caught, blocked, or ignored: SIGKILL (9) and SIGSTOP (19). They are handled entirely by the kernel, which is why they always work — and why they are also the two you should reach for last, since the process gets no opportunity to clean up.

🔑 Standard signals are not queued. If SIGTERM arrives three times while the process has it blocked, it is delivered once. The pending set is a bitmask, not a counter, so identical signals collapse. This is the reason a SIGCHLD handler must loop over waitpid(WNOHANG) until it returns zero — three children exiting simultaneously produce one signal, and a handler that reaps one child per signal leaks zombies under load while working perfectly in testing. Real-time signals (SIGRTMIN..SIGRTMAX) are queued, which is precisely why they exist.

Part 2 — Sending Signals

$ kill 1234                  # SIGTERM (15) by default
$ kill -TERM 1234            # explicit, and clearer in scripts
$ kill -9 1234               # SIGKILL
$ kill -0 1234               # send NOTHING — just test existence and permission
$ kill -TERM -1234           # negative PID: the whole process GROUP
$ kill -l                    # list all signal names

kill -0 is the idiomatic liveness check. It performs the permission and existence checks without delivering anything:

if kill -0 "$pid" 2>/dev/null; then
    echo "still running"
fi

By name rather than PID, pkill takes the same arguments as pgrep — which means you should always run the pgrep first to see what you are about to hit:

$ pgrep -a -f 'python worker.py'      # LOOK first
55201 python worker.py --queue=high
$ pkill -TERM -f 'python worker.py'   # then act

Permission to signal is not arbitrary: you may signal a process if you are root, or if your real or effective UID matches the target's real or saved UID. This is why you cannot Ctrl-C a root daemon from your own shell.

Part 3 — Handlers, and Why Most Are Written Wrong

A handler interrupts the process at an arbitrary instruction — possibly in the middle of malloc, or mid-way through updating a data structure. Only a specific list of functions are async-signal-safe (safe to call from a handler), and printf, malloc, and most of the standard library are not on it.

/* WRONG — printf() takes an internal lock. If the signal arrived while the
   main program held that same lock, the handler deadlocks the process. */
void handler(int sig) {
    printf("caught %d\n", sig);        /* not async-signal-safe */
    cleanup_database_connection();     /* definitely not */
}

/* CORRECT — set a flag; do the real work in the main loop. */
volatile sig_atomic_t got_signal = 0;
void handler(int sig) { got_signal = sig; }

while (running) {
    if (got_signal) { graceful_shutdown(); break; }
    do_work();
}

The deadlock is intermittent and load-dependent, which makes it one of the hardest bugs to reproduce. The rule — handlers set flags, main loops do work — costs nothing and eliminates the entire class.

The modern alternative avoids handlers entirely: block the signals and read them synchronously from a file descriptor, which composes with epoll and has no safety restrictions at all:

sigprocmask(SIG_BLOCK, &mask, NULL);
int fd = signalfd(-1, &mask, 0);       /* now select/poll/epoll on fd */

In shell scripts, trap is the equivalent, and it has its own well-known failure modes:

#!/usr/bin/env bash
set -euo pipefail

tmpdir=$(mktemp -d)
cleanup() {
    local status=$?
    rm -rf "$tmpdir"
    exit "$status"
}
trap cleanup EXIT INT TERM

# ... work using "$tmpdir" ...
trap targetFires when
EXITThe script exits for any reason — the one to use for cleanup
ERRA command fails (with set -e semantics)
INT TERMThose specific signals
DEBUGBefore every command — for tracing
trap - EXITRemoves the trap

Three things regularly break shell traps:

# 1. Single quotes defer expansion — usually what you want
trap "rm -f $tmpfile" EXIT      # expands NOW; wrong if tmpfile changes later
trap 'rm -f "$tmpfile"' EXIT    # expands at trap time — correct

# 2. Traps are NOT inherited by subshells or functions by default
( trap 'echo inner' EXIT; true )   # only fires for the subshell

# 3. While waiting on a foreground child, bash defers the trap
sleep 300                        # Ctrl-C here goes to sleep, not the trap
sleep 300 & wait $!              # correct: bash can run the trap

That third point matters for any script that supervises a long-running child. Running it in the background and using wait is what allows the trap to fire promptly.

❌ trap 'rm -rf $WORKDIR' EXIT — double quotes would expand $WORKDIR immediately, and even single-quoted, if WORKDIR is unset or empty at trap time this becomes rm -rf with no argument, or worse, rm -rf / if it was set to something ending in a slash.

✅ Set the variable before installing the trap, quote it inside, and guard it: trap 'test -n "${WORKDIR:-}" && rm -rf -- "$WORKDIR"' EXIT. Better still, use mktemp -d so the value is always a fresh directory you own, and add set -u so an unset variable aborts rather than expanding to nothing.

Part 4 — The Terminal's Role

Ctrl-C is not bash killing a program. The terminal line discipline — kernel code between the keyboard and any process — maps certain keystrokes to signals and delivers them to the terminal's foreground process group.

$ stty -a | tr ';' '\n' | grep -E 'intr|susp|quit|eof'
 intr = ^C
 quit = ^\
 susp = ^Z
 eof = ^D
KeySignalSent to
Ctrl-CSIGINTForeground process group
Ctrl-ZSIGTSTPForeground process group
Ctrl-\SIGQUITForeground process group (dumps core)
Ctrl-DnoneNot a signal — signals EOF on the input stream

Two consequences follow from "process group" rather than "process". Ctrl-C stops an entire pipeline, because bash puts all its stages in one group. And a program can genuinely ignore Ctrl-C by catching SIGINT — which is why vim and less are unaffected by it.

Ctrl-D is worth separating out because it is constantly misunderstood: it sends no signal at all. It causes a pending read() to return zero bytes, which programs interpret as end of input. That is why it exits a shell (no more commands) and why it terminates cat with no file argument.

Background processes get special treatment. If one tries to read from the terminal, the kernel stops it with SIGTTIN, because two processes reading the same keyboard would be chaos:

$ cat &
[1] 55400
$ jobs
[1]+  Stopped                 cat        # SIGTTIN — it tried to read
$ fg
cat

Part 5 — Job Control

Job control is bash managing process groups on your behalf. The commands map directly onto signals and terminal ownership.

CommandEffect
cmd &Start in the background (own process group, not foreground)
Ctrl-ZSIGTSTP — suspend the foreground job
bg %1SIGCONT — resume in the background
fg %1SIGCONT + give it the terminal
jobs -lList jobs with PIDs
wait %1Block until that job finishes
disown -h %1Do not send SIGHUP to it when the shell exits
kill %1Signal by job spec rather than PID
$ sleep 300 &
[1] 55500
$ sleep 400 &
[2] 55501
$ jobs -l
[1]-  55500 Running                 sleep 300 &
[2]+  55501 Running                 sleep 400 &
      ^ '+' is the default job for fg/bg; '-' is the previous one

Job specs (%1, %+, %string) are per-shell — another shell cannot see your jobs, because they exist only in that bash process's bookkeeping.

The practical case is escaping a job you started in the foreground without losing it:

$ ./long-running-import.sh          # oops, should have backgrounded this
^Z
[1]+  Stopped                 ./long-running-import.sh
$ bg
[1]+ ./long-running-import.sh &
$ disown -h %1                      # survive the terminal closing

That disown -h only prevents SIGHUP from bash. It does not detach the process from the terminal, so if it later writes output it may still receive SIGTTOU. For work that genuinely must survive, tmux or a systemd unit is the right tool — see systemd & Service Management.

Part 6 — Shutdown Sequences in Practice

Both systemd and Docker implement the same pattern — polite request, grace period, forced kill — and knowing the exact sequence explains most "why did my container take ten seconds to stop?" questions.

systemctl stop myapp
   │
   ├─ ExecStop=  (if defined) runs first
   ├─ SIGTERM to the unit's processes (per KillMode)
   ├─ wait up to TimeoutStopSec (default 90s)
   ├─ SIGKILL to anything still alive
   └─ unit reported as stopped (or 'failed' if it timed out)

docker stop mycontainer
   │
   ├─ SIGTERM to PID 1 in the container
   ├─ wait 10s (default; --time to change)
   └─ SIGKILL
systemd settingEffect
KillSignal=SIGTERMWhich signal is sent first
KillMode=control-groupDefault — signals every process in the cgroup
KillMode=mixedSIGTERM to the main process, SIGKILL to the rest
KillMode=processOnly the main PID — children are left running
TimeoutStopSec=30Grace period before SIGKILL
ExecReload=What systemctl reload runs (often kill -HUP $MAINPID)

The cgroup-based approach is why systemd is more reliable than PID-based supervision: it signals everything in the unit's control group regardless of re-parenting or process-group changes, so a daemon cannot escape by double-forking. This is the same mechanism covered in Namespaces & cgroups.

Two container-specific traps are worth stating plainly. First, ENTRYPOINT cmd in shell form runs your program under /bin/sh -c, so the shell is PID 1 and does not forward SIGTERM — the exec form ENTRYPOINT ["cmd"] makes your program PID 1 directly. Second, as Processes covered, PID 1 has no default signal handlers, so an application that never installs a SIGTERM handler ignores it entirely and always takes the full grace period.

SIGHUP deserves a final note because its meaning is purely conventional. Its origin is "the modem hung up", but daemons adopted it to mean "reload configuration", since a daemon with no terminal would never receive it otherwise. That is why nginx -s reload, kill -HUP, and systemctl reload often do the same thing — and why logrotate's postrotate stanza signals the writer, which is what actually releases the deleted-but-open file from Files, Inodes & Links.

Interview Questions

Beginner: What is the difference between SIGTERM and SIGKILL?

SIGTERM (15) is a polite request to terminate. The process can catch it and run a handler — flushing buffers, closing connections, removing lock files, finishing in-flight requests — and then exit on its own terms. It is what kill sends by default.

SIGKILL (9) cannot be caught, blocked, or ignored. The kernel destroys the process immediately, and it gets no opportunity to do anything.

The practical consequences of skipping straight to -9: unflushed writes are lost; lock files and PID files remain, so the next start may refuse; database connections are left open on the server side until timeout; and files the process had deleted-but-open never release their disk space, because no orderly close happens.

The correct sequence is SIGTERM, wait a reasonable period, and escalate to SIGKILL only if the process has demonstrably not responded. That is exactly what systemd does with TimeoutStopSec and what docker stop does with its 10-second default.

SIGSTOP (19) is the only other uncatchable signal — it suspends rather than terminates, and SIGCONT resumes.

Beginner: What actually happens when you press Ctrl-C?

The terminal's line discipline — kernel code, not bash — maps Ctrl-C to SIGINT and sends it to the terminal's foreground process group.

Three things follow from that. It reaches every process in the group, which is why Ctrl-C stops an entire pipeline rather than only the last stage. It does not involve bash at all, which is why it works on programs that know nothing about shells. And because SIGINT is catchable, a program can legitimately ignore it — which is why Ctrl-C does not close vim or less.

You can see the mapping and change it:

$ stty -a | grep intr
intr = ^C

Worth distinguishing from its neighbours: Ctrl-Z sends SIGTSTP (suspend), Ctrl-\ sends SIGQUIT (which dumps core), and Ctrl-D sends no signal at all — it causes a pending read() to return zero bytes, which programs interpret as end of input.

Mid: Why must a SIGCHLD handler loop, and what happens if it does not?

Because standard signals are not queued. The kernel tracks pending signals in a bitmask, not a counter, so if three children exit while SIGCHLD is blocked or being handled, the bit is simply set three times and the handler runs once.

A handler that reaps a single child therefore leaves the other two as zombies:

/* WRONG — reaps one child per signal */
void handler(int sig) { waitpid(-1, NULL, WNOHANG); }

/* CORRECT — drain everything that has exited */
void handler(int sig) {
    while (waitpid(-1, NULL, WNOHANG) > 0)
        ;
}

WNOHANG is essential: it makes waitpid return 0 immediately when no more children have exited, rather than blocking inside the handler.

Why this bug is nasty: it works perfectly in testing, where children exit one at a time, and only leaks under concurrency. Zombies accumulate slowly until PIDs are exhausted, at which point nothing on the system can fork and the failure looks unrelated to the service that caused it.

The same non-queuing property is why POSIX real-time signals (SIGRTMIN..SIGRTMAX) exist — they are queued and can carry a small payload. And it is why signalfd is preferable in modern code: signals become readable events on a descriptor that integrates with epoll, with no async-signal-safety restrictions at all.

Mid: Why is calling printf in a signal handler dangerous?

Because a handler can interrupt the process at any instruction — including one inside printf itself. printf takes an internal lock on the stdio buffer. If the signal arrives while the main program already holds that lock, the handler tries to acquire it, waits for a lock that only the interrupted code can release, and the process deadlocks permanently.

The same reasoning applies to malloc (heap lock), most of the standard library, and any function that touches shared state. POSIX defines a short list of async-signal-safe functions that are guaranteed re-entrant — write, _exit, signal, kill among them. Notably write(2) is safe while printf(3) is not, so emergency logging from a handler uses raw write.

The rule: handlers set a flag, main loops do the work.

volatile sig_atomic_t shutdown_requested = 0;
void handler(int sig) { shutdown_requested = 1; }   /* nothing else */

volatile sig_atomic_t is the specific type guaranteed to be written atomically and not cached in a register by the optimiser.

This bug is intermittent and load-dependent, so it survives testing and appears in production as an unexplained hang. The modern way to avoid the whole category is signalfd or a self-pipe, turning asynchronous signals into ordinary readable events handled in the normal event loop.

Senior: A container takes exactly 10 seconds to stop every time. Diagnose it.

"Exactly 10 seconds, every time" is the diagnosis nearly on its own — that is docker stop's default grace period. SIGTERM was sent, nothing exited, and Docker escalated to SIGKILL on schedule. Every stop is an unclean shutdown.

There are three usual causes, and they are distinguishable.

1. Shell-form ENTRYPOINT. The most common by far:

ENTRYPOINT node server.js          # → /bin/sh -c "node server.js"

sh becomes PID 1, and it does not forward signals to its child. SIGTERM kills the shell's intent but node never hears it. Confirm inside the container:

$ docker exec mycontainer ps -eo pid,cmd
  PID CMD
    1 /bin/sh -c node server.js
    7 node server.js               ← the real process is not PID 1

The fix is exec form: ENTRYPOINT ["node", "server.js"], which makes node PID 1 directly.

2. PID 1 semantics. Even with exec form, PID 1 gets no default signal handlers. A process that has not explicitly installed a SIGTERM handler ignores it entirely — behaviour that differs from the same binary run as any other PID. Check what it handles:

$ docker exec mycontainer grep SigCgt /proc/1/status
SigCgt: 0000000000000000          ← catches nothing; SIGTERM is discarded

Fix by installing a handler in the application, or running an init that forwards signals: docker run --init, or tini as the entrypoint.

3. A handler exists but shutdown genuinely takes too long. Here SigCgt shows SIGTERM caught, and the process is doing real work — draining connections, flushing a write buffer. Confirm with strace rather than assuming, then raise the grace period (docker stop -t 30, or terminationGracePeriodSeconds in Kubernetes) to something above the real drain time.

Why it matters beyond the ten seconds: every deploy, scale-down, and node drain becomes a hard kill. In-flight requests fail, buffered writes are lost, and connections are left for the peer to time out. Under Kubernetes this is the difference between a rolling update that is invisible to users and one that returns 502s on every pod replacement.

Senior: Design a signal-handling strategy for a long-running service. What must it cover?

I would treat signals as the service's control interface and define the contract explicitly, because the defaults are almost always wrong for a server.

The signal contract:

SignalBehaviour
SIGTERMGraceful shutdown: stop accepting new work, drain in-flight, flush, exit 0
SIGINTSame as SIGTERM (interactive use)
SIGHUPReload configuration without dropping connections
SIGUSR1Reopen log files (for logrotate's postrotate)
SIGUSR2Dump diagnostics — goroutine/thread stacks, metrics
Second SIGTERMEscalate: abandon draining and exit now

The implementation rules:

  • Handlers set flags only. No I/O, no allocation — async-signal-safety. Better, use signalfd or a self-pipe so signals arrive as ordinary events in the main event loop and none of the restrictions apply.
  • Drain in the right order: stop accepting, close listeners, let in-flight requests finish with a bounded deadline, flush persistent state, then exit. Closing listeners first is what lets a load balancer stop routing to you.
  • Bound the drain. An unbounded graceful shutdown is a hang. Pick a deadline below the supervisor's TimeoutStopSec so you control the outcome rather than being SIGKILLed mid-flush.
  • Handle the repeated signal. Operators press Ctrl-C twice; the second one should mean "I meant it".
  • Propagate to children. Signal the process group, or rely on systemd's KillMode=control-group, so workers do not survive as orphans holding ports.
  • Make reload safe. Validate the new configuration before applying it, and keep serving the old one if it fails — a reload that takes the service down is worse than no reload.

The systemd side of the contract must match, or the application's care is wasted:

[Service]
KillSignal=SIGTERM
KillMode=mixed
TimeoutStopSec=45            # > the application's own drain deadline
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure

And I would test it, because untested shutdown paths are always broken: send SIGTERM under load and assert that in-flight requests complete, the exit status is 0, and no data is lost. Kubernetes makes this concrete — a preStop hook plus a readiness probe that fails immediately on SIGTERM gives the load balancer time to stop routing before the process stops accepting.

🏋️ Exercises

1 (easy): Show which signals a process catches, ignores, or blocks by reading /proc.
Solution 
$ cat > /tmp/sig.py <<'EOF'
import signal, time, os
signal.signal(signal.SIGTERM, lambda s,f: None)   # catch 15
signal.signal(signal.SIGHUP,  signal.SIG_IGN)     # ignore 1
print("pid", os.getpid(), flush=True)
time.sleep(300)
EOF
$ python3 /tmp/sig.py & sleep 1; pid=$(pgrep -f sig.py)

$ grep -E 'Sig(Blk|Ign|Cgt)' /proc/$pid/status
SigBlk: 0000000000000000
SigIgn: 0000000000000001          # bit 1 = SIGHUP
SigCgt: 0000000000004002          # bit 2 (SIGINT via python) + bit 15 (SIGTERM)

Decode a mask by checking bit N-1 for signal N:

$ python3 -c "
m = int('0000000000004002', 16)
import signal
print([signal.Signals(i+1).name for i in range(31) if m >> i & 1])
"
['SIGINT', 'SIGTERM']

Verify the behaviour matches the mask:

$ kill -HUP $pid; sleep 1; kill -0 $pid && echo "survived SIGHUP (ignored)"
survived SIGHUP (ignored)
$ kill -TERM $pid; sleep 1; kill -0 $pid && echo "survived SIGTERM (handler did nothing)"
survived SIGTERM (handler did nothing)
$ kill -9 $pid; sleep 1; kill -0 $pid 2>/dev/null || echo "SIGKILL always wins"
SIGKILL always wins

This is the fastest answer to "why is this process ignoring my signal?" — no other tool exposes SigIgn, and a process that inherited an ignored SIGTERM from a careless wrapper script will never respond to it.

2 (easy): Demonstrate that Ctrl-C signals a process group, not a process.
Solution 
$ cat > /tmp/catcher.sh <<'EOF'
#!/usr/bin/env bash
trap 'echo "  [$$] caught SIGINT"; exit 0' INT
echo "started $$ pgid=$(ps -o pgid= -p $$ | tr -d ' ')"
sleep 300 & wait $!
EOF
$ chmod +x /tmp/catcher.sh

Run two stages in a pipeline so they share a group:

$ /tmp/catcher.sh | cat
started 56100 pgid=56100
^C
  [56100] caught SIGINT

Confirm both stages were in one group before the interrupt:

$ /tmp/catcher.sh | cat &
$ sleep 1; ps -eo pid,pgid,cmd | grep -E 'catcher|sleep 300' | grep -v grep
  56200   56200 /bin/bash /tmp/catcher.sh
  56201   56200 sleep 300
  56202   56200 cat                        # all three share PGID 56200

Signal the group manually — the negative PID:

$ kill -INT -56200
  [56200] caught SIGINT

Compare with signalling only the leader:

$ /tmp/catcher.sh & sleep 1; pid=$!
$ kill -INT $pid; sleep 1
  [56300] caught SIGINT
$ pgrep -f 'sleep 300' && echo "orphaned child survives"
56301
orphaned child survives

The script exited but its sleep child kept running, re-parented to init. This is exactly the "service stopped but the port is still bound" scenario — and why kill -TERM -PGID, or systemd's cgroup-based killing, is the reliable way to stop a job tree.

3 (medium): Prove that signals collapse, and fix a leaky SIGCHLD handler.
Solution

The broken version — reaps one child per signal:

$ cat > /tmp/leaky.py <<'EOF'
import os, signal, time
def handler(signum, frame):
    try: os.waitpid(-1, os.WNOHANG)      # ONE child only
    except ChildProcessError: pass
signal.signal(signal.SIGCHLD, handler)

for _ in range(20):                       # spawn 20 quick children at once
    if os.fork() == 0: os._exit(0)
time.sleep(3)
print("zombies:", os.popen("ps -eo stat,ppid | awk '$1 ~ /^Z/ && $2==%d' | wc -l" % os.getpid()).read().strip())
time.sleep(5)
EOF
$ python3 /tmp/leaky.py
zombies: 14

Fourteen of twenty children leaked. They exited nearly simultaneously, so most SIGCHLDs collapsed into a handful of deliveries — the pending set is a bitmask, not a counter.

The correct version — drain in a loop:

$ sed 's/try: os.waitpid(-1, os.WNOHANG).*/try:\n        while os.waitpid(-1, os.WNOHANG)[0] > 0: pass/' \
      /tmp/leaky.py > /tmp/fixed.py
$ cat > /tmp/fixed.py <<'EOF'
import os, signal, time
def handler(signum, frame):
    while True:
        try:
            pid, _ = os.waitpid(-1, os.WNOHANG)
            if pid == 0: break            # no more exited children
        except ChildProcessError: break   # no children at all
signal.signal(signal.SIGCHLD, handler)

for _ in range(20):
    if os.fork() == 0: os._exit(0)
time.sleep(3)
print("zombies:", os.popen("ps -eo stat,ppid | awk '$1 ~ /^Z/ && $2==%d' | wc -l" % os.getpid()).read().strip())
EOF
$ python3 /tmp/fixed.py
zombies: 0

Why the bug survives testing: spawn children one at a time, with gaps, and the broken version works flawlessly:

$ python3 -c "
import os, signal, time
def h(s,f):
    try: os.waitpid(-1, os.WNOHANG)
    except ChildProcessError: pass
signal.signal(signal.SIGCHLD, h)
for _ in range(5):
    if os.fork() == 0: os._exit(0)
    time.sleep(0.5)                       # spaced out — no collapsing
time.sleep(1)
print('zombies:', os.popen(\"ps -eo stat,ppid | awk '\\$1 ~ /^Z/ && \\$2==%d'|wc -l\" % os.getpid()).read().strip())
"
zombies: 0

Correct under low load, leaking under concurrency — which is why the symptom appears in production months after the code shipped, as PID exhaustion that looks unrelated to the service causing it.

4 (medium): Write a shell trap that reliably cleans up, and show three ways naive traps fail.
Solution

Failure 1 — double quotes expand too early:

$ cat > /tmp/t1.sh <<'EOF'
#!/usr/bin/env bash
tmp=/tmp/first.txt
trap "rm -f $tmp" EXIT       # expands NOW → 'rm -f /tmp/first.txt'
tmp=/tmp/second.txt          # the trap still targets the OLD path
touch /tmp/first.txt /tmp/second.txt
EOF
$ bash /tmp/t1.sh; ls /tmp/second.txt
/tmp/second.txt              # leaked — trap deleted the wrong file
$ rm -f /tmp/second.txt

Failure 2 — the trap does not fire during a foreground child:

$ cat > /tmp/t2.sh <<'EOF'
#!/usr/bin/env bash
trap 'echo "CLEANUP RAN"; exit 130' INT
sleep 30                     # foreground: bash defers the trap
EOF
$ bash /tmp/t2.sh
^C                           # trap output appears only after sleep dies

The fix is to background the child and wait, which lets bash service the trap promptly:

$ cat > /tmp/t3.sh <<'EOF'
#!/usr/bin/env bash
trap 'echo "CLEANUP RAN"; kill $child 2>/dev/null; exit 130' INT
sleep 30 & child=$!
wait $child
EOF
$ bash /tmp/t3.sh
^CCLEANUP RAN                # immediate

Failure 3 — an unset variable makes cleanup dangerous:

$ cat > /tmp/t4.sh <<'EOF'
#!/usr/bin/env bash
trap 'rm -rf "$WORKDIR"/' EXIT     # if WORKDIR is empty → rm -rf /
echo "would have run: rm -rf ${WORKDIR:-}/"

$ bash /tmp/t4.sh
would have run: rm -rf /

The version that gets all three right:

$ cat > /tmp/safe.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail

workdir=$(mktemp -d)                    # always a real, fresh directory
child=0

cleanup() {
    local status=$?
    [ "$child" -ne 0 ] && kill -TERM "$child" 2>/dev/null || true
    [ -n "${workdir:-}" ] && [ -d "$workdir" ] && rm -rf -- "$workdir"
    exit "$status"
}
trap cleanup EXIT INT TERM

echo "working in $workdir"
sleep 30 & child=$!
wait "$child"
EOF
$ bash /tmp/safe.sh & sleep 1; kill -INT %1; sleep 1
working in /tmp/tmp.9xKq2p
$ ls -d /tmp/tmp.9xKq2p 2>/dev/null || echo "cleaned up"
cleaned up

Each element earns its place: mktemp -d guarantees a valid path, single quotes defer expansion, the guards prevent operating on an empty value, EXIT covers every exit path including errors under set -e, backgrounding plus wait makes the trap responsive, and preserving $? keeps the real exit status.

5 (hard): Reproduce the Docker "10 seconds to stop" problem and fix it three ways.
Solution

Simulate PID 1 semantics without Docker using an unshared PID namespace:

$ cat > /tmp/app.sh <<'EOF'
#!/usr/bin/env bash
echo "app running as PID $$"
while :; do sleep 1; done
EOF
$ chmod +x /tmp/app.sh

Case 1 — shell-form entrypoint: the shell is PID 1 and does not forward signals.

$ sudo unshare --pid --fork --mount-proc sh -c '/tmp/app.sh' &
$ sleep 1; sudo ps -eo pid,cmd --ppid 1 2>/dev/null | head
# In a real container:
$ docker run -d --name t1 --entrypoint sh alpine -c 'while :; do sleep 1; done'
$ time docker stop t1
t1
real    0m10.3s              ← the full grace period, every time

Confirm the shape of the problem inside the container:

$ docker run -d --name t2 --entrypoint sh alpine -c 'sleep 300'
$ docker exec t2 ps -eo pid,cmd
PID   CMD
    1 sh -c sleep 300        ← sh is PID 1
    7 sleep 300              ← the real work is not PID 1

Fix A — exec form, so the application is PID 1 directly:

$ docker run -d --name t3 alpine sleep 300
$ docker exec t3 ps -eo pid,cmd
PID   CMD
    1 sleep 300
$ time docker stop t3
real    0m0.4s               ← sleep has no handler, but as a non-shell PID 1
                                the default action still applies for SIGTERM

Fix B — exec inside the shell script, replacing the shell rather than forking under it:

$ cat > /tmp/entry.sh <<'EOF'
#!/bin/sh
# setup work here...
exec "$@"                    # replace the shell; the app becomes PID 1
EOF

Fix C — an init that forwards signals and reaps orphans:

$ docker run -d --init --name t4 --entrypoint sh alpine -c 'while :; do sleep 1; done'
$ docker exec t4 ps -eo pid,cmd | head -3
PID   CMD
    1 /sbin/docker-init -- sh -c while :; do sleep 1; done
    7 sh -c while :; do sleep 1; done
$ time docker stop t4
real    0m0.5s

The PID 1 subtlety worth confirming — an application that catches nothing behaves differently as PID 1 than anywhere else:

$ docker run -d --name t5 python:alpine python -c "import time; time.sleep(300)"
$ docker exec t5 grep SigCgt /proc/1/status
SigCgt: 0000000000000000     ← catches nothing
$ time docker stop t5
real    0m10.2s              ← SIGTERM discarded; killed after the grace period

The same Python process run as PID 50 would terminate immediately on SIGTERM, because the kernel applies default actions. PID 1 gets none, so an unhandled signal is silently dropped — this is the single most common cause of slow container shutdowns.

Cleanup: docker rm -f t1 t2 t3 t4 t5 2>/dev/null.

6 (hard): Implement a service with a full signal contract and verify each signal.
Solution 
$ cat > /tmp/service.py <<'EOF'
import signal, sys, os, time, threading

state = {"running": True, "draining": False, "config": "v1", "logfile": None, "served": 0}

def open_log():
    if state["logfile"]: state["logfile"].close()
    state["logfile"] = open('/tmp/service.log', 'a')
    state["logfile"].write(f"log opened at {time.time()}\n"); state["logfile"].flush()

def on_term(signum, frame):
    if state["draining"]:                     # second signal = escalate
        print("second signal — exiting immediately", flush=True); os._exit(1)
    state["draining"] = True; state["running"] = False
    print(f"got {signal.Signals(signum).name} — draining", flush=True)

def on_hup(signum, frame):
    state["config"] = "v2"                    # reload without dropping work
    print("SIGHUP — config reloaded", flush=True)

def on_usr1(signum, frame):
    open_log(); print("SIGUSR1 — logs reopened", flush=True)

def on_usr2(signum, frame):
    print(f"SIGUSR2 — diagnostics: served={state['served']} "
          f"threads={threading.active_count()} config={state['config']}", flush=True)

signal.signal(signal.SIGTERM, on_term); signal.signal(signal.SIGINT, on_term)
signal.signal(signal.SIGHUP,  on_hup);  signal.signal(signal.SIGUSR1, on_usr1)
signal.signal(signal.SIGUSR2, on_usr2)

open_log()
print(f"service up, pid {os.getpid()}", flush=True)
while state["running"]:
    state["served"] += 1; time.sleep(0.2)

print("draining in-flight work...", flush=True)
time.sleep(1)                                  # bounded drain
state["logfile"].write(f"clean shutdown after {state['served']} units\n")
state["logfile"].close()
print("exited cleanly", flush=True)
sys.exit(0)
EOF
$ rm -f /tmp/service.log; python3 /tmp/service.py & pid=$!
service up, pid 57100

Verify each signal in turn:

$ kill -HUP  $pid; sleep 0.3
SIGHUP — config reloaded
$ kill -USR1 $pid; sleep 0.3
SIGUSR1 — logs reopened
$ kill -USR2 $pid; sleep 0.3
SIGUSR2 — diagnostics: served=31 threads=1 config=v2
$ kill -TERM $pid; wait $pid; echo "status=$?"
got SIGTERM — draining
draining in-flight work...
exited cleanly
status=0
$ cat /tmp/service.log
log opened at 1786...
log opened at 1786...
clean shutdown after 43 units

Confirm the handlers are registered before testing behaviour:

$ python3 /tmp/service.py & pid=$!; sleep 0.5
$ python3 -c "
m = int(open('/proc/$pid/status').read().split('SigCgt:')[1].split()[0], 16)
import signal
print(sorted(signal.Signals(i+1).name for i in range(31) if m >> i & 1))
"
['SIGHUP', 'SIGINT', 'SIGTERM', 'SIGUSR1', 'SIGUSR2']

Test the escalation path — two rapid SIGTERMs:

$ kill -TERM $pid; kill -TERM $pid; wait $pid; echo "status=$?"
got SIGTERM — draining
second signal — exiting immediately
status=1

The matching systemd unit, so the contract is honoured on both sides:

[Service]
ExecStart=/usr/bin/python3 /opt/service.py
KillSignal=SIGTERM
KillMode=mixed
TimeoutStopSec=45              # comfortably above the app's own drain time
ExecReload=/bin/kill -HUP $MAINPID
Restart=on-failure
RestartSec=5s

What this deliberately gets right: handlers do minimal work; the drain is bounded so the app controls its own exit rather than being SIGKILLed mid-flush; a repeated signal escalates because operators press Ctrl-C twice; SIGUSR1 exists specifically for logrotate's postrotate, which is what actually releases a deleted-but-open log file; and TimeoutStopSec exceeds the internal deadline so the two layers do not fight.

🎯 Key Takeaways

  • A signal is an asynchronous interrupt carrying no data beyond its number — a doorbell, not a message.
  • Only SIGKILL (9) and SIGSTOP (19) cannot be caught, blocked, or ignored, which is why they always work and why they skip all cleanup.
  • Standard signals are not queued: pending signals are a bitmask, so identical ones collapse — which is why SIGCHLD handlers must loop over waitpid(WNOHANG).
  • /proc/PID/status's SigBlk/SigIgn/SigCgt masks answer "why is this ignoring my signal?" — bit N-1 corresponds to signal N.
  • Handlers must only set flags: printf and malloc are not async-signal-safe and can deadlock intermittently. Prefer signalfd or a self-pipe.
  • Ctrl-C is the terminal line discipline sending SIGINT to the foreground process group — which is why it stops a whole pipeline and why programs can ignore it.
  • Ctrl-D sends no signal at all; it makes read() return zero bytes, signalling EOF.
  • Shell traps fail in three predictable ways: double quotes expand too early, traps are deferred while a foreground child runs, and unset variables make cleanup dangerous.
  • Use trap ... EXIT for cleanup, run long children with cmd & wait $!, and guard paths with mktemp -d plus set -u.
  • systemd and Docker both do SIGTERM → grace period → SIGKILL; a container that always takes exactly 10 seconds to stop is being force-killed every time.
  • PID 1 has no default signal handlers, so an app that never installs one ignores SIGTERM entirely — use exec-form ENTRYPOINT plus --init or tini.
  • systemd's KillMode=control-group signals every process in the cgroup, which is why it is more reliable than PID- or PGID-based killing.
  • SIGHUP's "reload config" meaning is pure convention, and SIGUSR1's "reopen logs" is what makes logrotate release deleted-but-open files.
