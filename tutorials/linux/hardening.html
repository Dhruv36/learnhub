Hardening & The Production Checklist Production Skills

What you'll master: how to reduce a host's attack surface in the order that actually matters, why SSH key-only access plus no root login eliminates the majority of real intrusions, what setuid binaries and file capabilities let you audit in one command, how to write firewall rules that fail closed instead of locking you out, why unattended security updates beat a quarterly patch window, what to collect before you reboot a possibly-compromised host, and a checklist you can actually run before a server takes traffic. This is the capstone — it draws on every earlier lesson in the track. Prerequisites: Users, Groups & Permissions, systemd & Service Management, and Networking From the Socket Up.

Part 1 — Attack Surface, in Priority Order

Hardening guides fail because they list two hundred items of equal weight. In practice a small number of controls account for nearly all real-world compromise, and they should be done first.

#ControlPreventsEffort
1SSH keys only, no root loginCredential brute-force — the most common intrusion by farMinutes
2Automatic security updatesExploitation of known CVEs — the second most commonMinutes
3Close unnecessary listening portsWhole services being reachable at allMinutes
4Services run unprivilegedA service compromise becoming a host compromiseHours
5systemd sandboxing per serviceLateral movement after a compromiseHours
6Centralised logs and alertingNot the breach — the silence after itDays
7MAC (SELinux/AppArmor) enforcingExploits that survive everything aboveDays

The first three take under an hour combined and remove most of the realistic risk. A host with an enforcing SELinux policy and password-based root SSH is not secure; the ordering matters more than the total count.

# What is actually exposed right now — the single highest-value audit
$ sudo ss -tlnp | awk 'NR>1 && ($4 ~ /^0\.0\.0\.0:/ || $4 ~ /^\[::\]:/) {print $4, $NF}'
0.0.0.0:22    users:(("sshd",pid=901,fd=3))
0.0.0.0:80    users:(("nginx",pid=1204,fd=6))
0.0.0.0:5432  users:(("postgres",pid=980,fd=5))     ← should be 127.0.0.1
0.0.0.0:9200  users:(("java",pid=3310,fd=112))      ← Elasticsearch, unauthenticated
🔑 The bind address is the cheapest security control there is. A database listening on 127.0.0.1 is unreachable from the network regardless of firewall misconfiguration, security-group drift, or a VPN change. Every service that does not need remote access should bind loopback or a Unix socket — as Networking covers, this is a one-line change that removes an entire category of exposure, and it defends in depth rather than relying on a single perimeter rule.

Part 2 — SSH: The Front Door

SSH is the service most exposed and most attacked. Six settings do nearly all the work:

# /etc/ssh/sshd_config.d/99-hardening.conf     (a drop-in survives package updates)
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AuthenticationMethods publickey
AllowGroups ssh-users                  # explicit allowlist, not everyone with an account
MaxAuthTries 3
LoginGraceTime 20
X11Forwarding no
ClientAliveInterval 300
ClientAliveCountMax 2

$ sudo sshd -t                          # ALWAYS validate before reloading
$ sudo systemctl reload ssh

❌ Editing sshd_config, restarting, and discovering you are locked out. A typo in AllowGroups, a key that was never actually installed, or PasswordAuthentication no before adding a key — and on a cloud VM with no console that is an unrecoverable instance.

✅ Keep the existing session open and test in a second terminal. Run sshd -t to catch syntax errors, reload (never restart — reload does not drop existing connections), then open a new connection to verify before closing the first. For extra safety sudo systemd-run --on-active=5m systemctl restart ssh schedules a revert if you lose access.

Key hygiene matters as much as the config. Ed25519 keys, passphrase-protected, and audit what is actually authorised:

$ ssh-keygen -t ed25519 -C "dhruv@laptop-2026"
$ for f in /home/*/.ssh/authorized_keys /root/.ssh/authorized_keys; do
>   [[ -f $f ]] || continue
>   echo "== $f"; ssh-keygen -lf "$f"
> done
== /home/dhruv/.ssh/authorized_keys
256 SHA256:kL2f... dhruv@laptop-2026 (ED25519)
3072 SHA256:9xQm... old-ci-server (RSA)          ← still authorised, decommissioned 2024

That second key is the finding: orphaned authorised keys outlive the people and machines they belonged to, and nothing expires them. fail2ban is worth adding for noise reduction, but note that with passwords disabled it is defence against log spam rather than against compromise.

Part 3 — Users, setuid, and Privilege

Every setuid binary is a program that runs as root regardless of who invokes it. Each one is a potential escalation, and most systems carry several that nobody needs:

$ sudo find / -xdev -perm -4000 -type f -exec ls -l {} + 2>/dev/null
-rwsr-xr-x 1 root root  85064 /usr/bin/sudo
-rwsr-xr-x 1 root root  55528 /usr/bin/mount
-rwsr-xr-x 1 root root  44784 /usr/bin/newgrp
-rwsr-xr-x 1 root root  68208 /usr/bin/passwd
-rwsr-xr-x 1 root root  14328 /usr/bin/pkexec           ← CVE-2021-4034 (PwnKit)

$ sudo chmod u-s /usr/bin/pkexec           # remove setuid if the system does not need it
$ sudo getcap -r / 2>/dev/null             # file capabilities: the modern, finer-grained form
/usr/bin/ping cap_net_raw=ep

File capabilities are strictly better than setuid — ping needs only CAP_NET_RAW, not all of root — and a binary with capabilities should be treated with the same suspicion as a setuid one during an audit.

Audit accounts and sudo rules, since these accumulate quietly:

$ awk -F: '$3 == 0 {print "UID 0:", $1}' /etc/passwd        # should be root ONLY
$ awk -F: '$2 == "" {print "NO PASSWORD:", $1}' /etc/shadow
$ awk -F: '$3 >= 1000 && $7 !~ /nologin|false/ {print $1, $7}' /etc/passwd
$ getent group sudo wheel docker 2>/dev/null
docker:x:998:dhruv,jenkins                  ← docker group membership == root
$ sudo grep -rE 'NOPASSWD|ALL=\(ALL\)' /etc/sudoers /etc/sudoers.d/

Docker group membership deserves the callout: a member can start a privileged container mounting the host filesystem, which is unrestricted root. It is not a lesser privilege than sudo — it is sudo without the audit trail.

PrincipleIn practice
Least privilegePer-service system accounts; DynamicUser=yes where possible
No shared accountsNamed accounts + sudo, so the audit log names a person
Scoped sudo%deploy ALL=(app) NOPASSWD: /usr/bin/systemctl restart app
No interactive logins for servicesuseradd -r -s /usr/sbin/nologin
Remove, do not disableDeprovision leavers; disabled accounts get re-enabled

Part 4 — Network Exposure and Firewalls

A firewall is the second line; the first is not listening. Once you do write rules, the ordering trap is what locks people out.

# nftables — the modern replacement for iptables
$ sudo nft list ruleset
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;      # default deny
    ct state established,related accept
    iif lo accept
    tcp dport 22 ct state new limit rate 10/minute accept
    tcp dport { 80, 443 } accept
    ip protocol icmp icmp type echo-request limit rate 5/second accept
  }
}

# ufw — simpler, correct for most single hosts
$ sudo ufw default deny incoming
$ sudo ufw default allow outgoing
$ sudo ufw allow from 10.0.0.0/8 to any port 22 proto tcp
$ sudo ufw limit 22/tcp
$ sudo ufw allow 80,443/tcp
$ sudo ufw --force enable
$ sudo ufw status verbose

Set the SSH rule before the default-deny policy, and verify from a second session. The classic lockout is enabling policy drop with no accept rule for the port you are connected on — existing connections survive on the established rule, so it looks fine until you reconnect.

Egress filtering is skipped almost everywhere and is what limits damage after a compromise. Malware needs to reach a C2 server, and a stolen database needs somewhere to go:

$ sudo ufw default deny outgoing
$ sudo ufw allow out 53                    # DNS
$ sudo ufw allow out to 10.0.0.0/8         # internal services
$ sudo ufw allow out 443                   # package repos, APIs (or allowlist by host)

Kernel network hardening via sysctl, applied persistently:

# /etc/sysctl.d/99-hardening.conf
net.ipv4.conf.all.rp_filter = 1                    # reverse-path filtering (anti-spoofing)
net.ipv4.conf.all.accept_redirects = 0
net.ipv4.conf.all.send_redirects = 0
net.ipv4.conf.all.accept_source_route = 0
net.ipv4.tcp_syncookies = 1                        # SYN-flood resistance
net.ipv4.icmp_echo_ignore_broadcasts = 1
net.ipv4.conf.all.log_martians = 1
kernel.kptr_restrict = 2                           # hide kernel pointers from /proc
kernel.dmesg_restrict = 1                          # non-root cannot read dmesg
kernel.yama.ptrace_scope = 1                       # restrict ptrace to descendants
fs.protected_hardlinks = 1
fs.protected_symlinks = 1
fs.suid_dumpable = 0
$ sudo sysctl --system

Part 5 — Patching, Integrity, and Detection

Unpatched known CVEs cause more compromise than novel exploits. Automatic security updates beat a quarterly window because the window is where the exposure lives:

$ sudo apt install unattended-upgrades
$ sudo dpkg-reconfigure -plow unattended-upgrades
$ cat /etc/apt/apt.conf.d/50unattended-upgrades | grep -A3 'Allowed-Origins'
Unattended-Upgrade::Allowed-Origins {
    "${distro_id}:${distro_codename}-security";
};
Unattended-Upgrade::Automatic-Reboot "false";       # decide reboots deliberately
$ sudo unattended-upgrade --dry-run --debug | tail -5

# Kernel patches need a reboot — know when one is pending
$ [[ -f /var/run/reboot-required ]] && cat /var/run/reboot-required.pkgs
$ sudo needrestart -b                    # which services are running old libraries
NEEDRESTART-SVC: nginx.service
NEEDRESTART-SVC: postgresql@16-main.service

That second command catches the case everyone misses: apt upgrade replaced OpenSSL on disk, but every running process still has the vulnerable version mapped until it restarts.

Mandatory access control confines a service even after it is compromised. Do not disable it because a service misbehaves — write the policy:

$ getenforce                             # SELinux
Enforcing
$ sudo ausearch -m avc -ts recent | audit2why | head
$ sudo aa-status | head -4               # AppArmor
$ sudo aa-complain /etc/apparmor.d/usr.sbin.myapp   # log-only while developing a profile

Detection matters more than prevention past a point, because prevention eventually fails and the average intrusion goes unnoticed for weeks:

$ sudo auditctl -w /etc/passwd -p wa -k identity
$ sudo auditctl -w /etc/sudoers.d/ -p wa -k sudoers
$ sudo auditctl -a always,exit -F arch=b64 -S execve -F euid=0 -k rootcmd
$ sudo ausearch -k identity -ts today | tail
$ sudo aide --check                      # file integrity baseline

Ship all of it off-host — as Logs, Journals & Time notes, editing local logs is an intruder's first move, so logs that only exist locally are not evidence.

Part 6 — The Production Checklist

Run this before a host takes traffic. It is deliberately short enough to actually be used:

# ── Access ────────────────────────────────────────────────
□ SSH: keys only, PermitRootLogin no, AllowGroups set, `sshd -t` clean
□ authorized_keys audited — no orphaned or unknown keys
□ No UID-0 accounts other than root; no empty passwords
□ sudo rules scoped; docker group membership justified
□ Service accounts have nologin shells

# ── Network ───────────────────────────────────────────────
□ `ss -tlnp` reviewed: every 0.0.0.0 bind is intentional
□ Firewall default-deny inbound, SSH rule added BEFORE enabling
□ Egress restricted where feasible
□ sysctl hardening applied via /etc/sysctl.d/ and verified

# ── Services ──────────────────────────────────────────────
□ Nothing runs as root without a documented reason
□ systemd sandboxing applied; `systemd-analyze security` reviewed
□ Resource limits set (MemoryMax, CPUQuota, TasksMax, LimitNOFILE)
□ Restart=on-failure + RestartSec + start limits
□ TimeoutStopSec exceeds the longest in-flight request

# ── Data & Storage ────────────────────────────────────────
□ Separate filesystems for /var/log and data; nosuid,nodev,noexec on /tmp
□ Disk AND inode monitoring (`df -h` and `df -i`)
□ Backups tested by an actual restore, stored off-host
□ Secrets not in images, env files world-readable, or git history

# ── Observability ─────────────────────────────────────────
□ Journal persistent (/var/log/journal exists)
□ Logs shipped off-host with a disk-backed queue
□ NTP synchronised; offset alerted on; servers in UTC
□ Alerts on saturation (PSI) and latency percentiles, not CPU%
□ Someone receives the alerts and knows what to do

# ── Maintenance ───────────────────────────────────────────
□ Unattended security upgrades enabled and verified
□ Reboot-required and needrestart checked in a routine
□ MAC (SELinux/AppArmor) enforcing, not permissive
□ auditd rules for identity and privileged commands

If a host is compromised, collect before you reboot. A reboot destroys the memory-resident evidence, which is often the only place the intrusion lives:

1. Isolate      — firewall it off; do NOT power off (memory is evidence)
2. Capture      — ps auxf, ss -tanp, lsof -n, /proc/*/exe, dmesg, journal, memory image
3. Preserve     — copy logs and artefacts OFF the host, hash them
4. Investigate  — last, lastb, auth logs, new users, cron jobs, authorized_keys, setuid files
5. Rebuild      — from a known-good image, NOT by cleaning the compromised host
6. Rotate       — every credential the host could touch: keys, tokens, DB passwords

Point 5 is the one people resist. You cannot verify the absence of a rootkit on a host you no longer trust; rebuilding is the only defensible outcome, and it is why infrastructure-as-code pays for itself here.

Interview Questions

Beginner: What are the first things you would do to harden a new Linux server?

Three things, in this order, because they take under an hour and remove most of the realistic risk:

1. SSH. Keys only, no root login, and an explicit allowlist of who may connect:

PermitRootLogin no
PasswordAuthentication no
AllowGroups ssh-users
MaxAuthTries 3
$ sudo sshd -t && sudo systemctl reload ssh

Credential brute-force is the single most common intrusion route, and disabling passwords eliminates it.

2. Automatic security updates, because unpatched known CVEs cause more compromise than novel exploits:

$ sudo apt install unattended-upgrades
$ sudo dpkg-reconfigure -plow unattended-upgrades

3. Close what is listening. Audit the bind addresses before writing a single firewall rule:

$ sudo ss -tlnp | awk '$4 ~ /0\.0\.0\.0/ {print $4, $NF}'

Anything that does not need remote access should bind 127.0.0.1 — that is unreachable from the network regardless of firewall drift, which makes it stronger than a rule.

Then a default-deny firewall with SSH allowed, and services running as non-root users. Those five steps cover the large majority of what matters. SELinux policies and audit rules come after, not before — a host with enforcing SELinux and password-based root SSH is not secure.

And always test SSH changes in a second terminal before closing the first, since a typo on a cloud VM with no console is unrecoverable.

Beginner: What is a setuid binary and why does it matter for security?

A file with the setuid bit set runs with the owner's privileges rather than the caller's. When the owner is root, any user who executes it gets a root process:

$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 68208 /usr/bin/passwd
   ^
   's' instead of 'x' — setuid

It exists for a real reason: passwd must write /etc/shadow, which only root can do, but any user must be able to change their own password.

The risk is that every setuid binary is a potential privilege escalation. A bug in one — a buffer overflow, an argument-parsing flaw, an environment variable it trusts — gives root to any local user. pkexec's CVE-2021-4034 (PwnKit) was exactly this, and it had been present for over a decade.

Audit them:

$ sudo find / -xdev -perm -4000 -type f -exec ls -l {} + 2>/dev/null
$ sudo chmod u-s /usr/bin/pkexec           # remove if unused

File capabilities are the modern, finer-grained alternative:

$ sudo getcap -r / 2>/dev/null
/usr/bin/ping cap_net_raw=ep

ping needs only CAP_NET_RAW, not all of root — so a bug in it yields far less. Capabilities should be audited with the same suspicion as setuid bits, and a new setuid binary appearing on a host is a strong compromise indicator worth alerting on.

Mid: How do you harden a systemd service without changing the application?

systemd's sandboxing directives apply namespaces, capability bounding, and seccomp filters to any service — no code changes, one line per class of risk:

[Service]
User=myapp
DynamicUser=yes                  # ephemeral unprivileged user, no account to manage

# Filesystem
ProtectSystem=strict             # entire filesystem read-only...
ReadWritePaths=/var/lib/myapp    # ...except this
ProtectHome=yes
PrivateTmp=yes

# Privilege
NoNewPrivileges=yes              # setuid binaries cannot escalate
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
PrivateDevices=yes

# Kernel
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
SystemCallFilter=@system-service
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX

# Resources
MemoryMax=2G
TasksMax=512

Measure the result rather than guessing at it — systemd grades the unit and names the gaps:

$ systemd-analyze security myapp.service
  NoNewPrivileges=       ✓
  RestrictAddressFamilies= ✗ 0.3
→ Overall exposure level: 1.6 OK 🙂

Going from 9.6 UNSAFE to under 2.0 typically takes fifteen minutes.

The practical caveats: ProtectSystem=strict means every writable path must be declared explicitly, and SystemCallFilter can break a runtime that uses an unusual syscall. Both fail loudly at startup and journalctl -u names the blocked path or call, so iterating is safe — I would apply them in staging first and read the journal rather than guessing.

The same mechanisms underlie containers, as Namespaces, cgroups & Containers covers, which is worth saying explicitly: you do not need a container runtime to get namespace isolation for a service.

Mid: Walk through securing SSH access for a team of 20 engineers.

The requirements are that access is individually attributable, revocable in one place, and does not depend on anyone copying files around.

1. Baseline server config:

PermitRootLogin no
PasswordAuthentication no
AuthenticationMethods publickey
AllowGroups ssh-users
MaxAuthTries 3
LoginGraceTime 20
ClientAliveInterval 300

2. Named accounts, never a shared one. A shared deploy account means the audit log cannot tell you who did anything, and offboarding one person means rotating for everyone.

3. At 20 people, use SSH certificates rather than authorized_keys. This is the decision that scales:

# Server trusts one CA
TrustedUserCAKeys /etc/ssh/ca.pub

# Each engineer gets a short-lived certificate
$ ssh-keygen -s ca_key -I dhruv@example.com -n dhruv -V +8h user_key.pub

Why certificates win: no key distribution to every host, revocation is central and immediate, certificates expire on their own (so an unnoticed leak has an 8-hour blast radius rather than an indefinite one), and principals encode which roles a person may assume. Managing authorized_keys across N hosts × 20 people by configuration management works but leaves orphaned keys behind — I have never audited a fleet that did not have some.

4. A bastion host, so production is not directly reachable:

# ~/.ssh/config
Host prod-*
  ProxyJump bastion.example.com
  User %r

One audited entry point, one place to log sessions, and production security groups that only accept SSH from the bastion.

5. Session recording and alerting on the bastion — logs shipped off-host, alerts on out-of-hours access and on any successful root login.

6. Offboarding as a single, tested action. With certificates it is revoking the principal; with authorized_keys it is a config-management run plus verification. I would test offboarding deliberately, because it is the control most often assumed to work and never exercised.

For the emergency path I would keep a documented break-glass account with a sealed credential and an alert on its use — not password SSH "just in case", which is the exposure we removed in step 1.

Senior: You suspect a production host is compromised. Walk through your response.

The goal is to preserve evidence, limit damage, and end with a host you can trust — which almost always means rebuilding rather than cleaning.

1. Isolate without destroying evidence. Firewall it off or move it to a quarantine security group. Do not power off — memory holds injected code, decrypted keys, and network state that disappear on reboot. Do not log in more than necessary, since every action overwrites evidence.

2. Capture volatile state first, in order of volatility:

$ ps auxf > /evidence/ps.txt
$ ss -tanp > /evidence/sockets.txt
$ sudo lsof -n > /evidence/lsof.txt
$ sudo ls -l /proc/*/exe 2>/dev/null > /evidence/exes.txt     # catches deleted binaries
$ sudo cat /proc/*/maps > /evidence/maps.txt
$ dmesg -T > /evidence/dmesg.txt
$ sudo journalctl -b --no-pager > /evidence/journal.txt

/proc/*/exe is particularly valuable: a process whose binary shows (deleted) is running something removed from disk, which is a strong indicator.

3. Copy evidence off the host and hash it, because anything left locally is under the intruder's control.

4. Investigate the standard persistence locations:

$ last -20; sudo lastb -20                  # logins and failures
$ sudo grep -Ei 'accepted|session opened' /var/log/auth.log | tail -40
$ awk -F: '$3==0' /etc/passwd               # new UID-0 accounts
$ sudo find /home /root -name authorized_keys -newermt '-30 days' -exec ls -l {} +
$ sudo crontab -l; ls -la /etc/cron.*/ /var/spool/cron/crontabs/
$ systemctl list-unit-files --state=enabled | grep -vE '^(systemd|dbus)'
$ sudo find / -xdev -perm -4000 -newermt '-30 days' 2>/dev/null
$ sudo aide --check                         # if a baseline exists

5. Determine scope before deciding the response. What credentials did this host hold — SSH keys, cloud IAM roles, database passwords, API tokens? What could it reach? Egress logs and connection history answer "did data leave", which is the question that drives notification obligations. Cloud instance metadata credentials are a standard pivot and must be assumed used.

6. Rebuild, do not clean. This is the part people resist and it is not negotiable: you cannot prove the absence of a rootkit or a kernel module on a host you no longer trust. Rebuild from a known-good image, restore data from a backup predating the compromise, and verify the entry point is closed before returning it to service.

7. Rotate everything the host could touch — SSH keys, service credentials, API tokens, database passwords, cloud keys — on the assumption they are known.

8. Close the loop. Identify the entry vector, fix it fleet-wide rather than on the one host, and add detection for the technique. The genuinely useful output of an incident is not the clean host; it is the detection that would have caught it on day one instead of week six.

Senior: Design a security baseline for a fleet of 200 hosts running mixed workloads.

At 200 hosts the problem changes from "harden a server" to "prove every server is hardened and know within minutes when one drifts". Manual hardening does not scale and cannot be audited.

1. Immutable, versioned base images. One golden image built in CI with the baseline applied — SSH config, sysctls, auditd rules, logging agent, no extra packages. Hosts are replaced rather than patched in place, which makes configuration drift structurally impossible and makes rebuilding after an incident routine instead of a project.

2. Configuration as code, enforced continuously. Ansible/Puppet/Chef running on a schedule in enforcing mode, not just at provision time. A host that drifts is corrected and the correction is alerted on — silent remediation hides a signal.

3. Tiered baselines, because "mixed workloads" is the actual constraint:

TierAdditional controls
Base (all hosts)SSH certs, auto-updates, default-deny inbound, auditd, log shipping, MAC enforcing
Internet-facingEgress allowlist, WAF, stricter rate limits, no internal credentials
Data-handlingEncryption at rest, restricted access, extended audit, DLP on egress
Untrusted codeSeparate node pool, gVisor/Firecracker, no IAM role, no metadata access

4. Centralised identity and short-lived credentials. SSH certificates from a CA with 8-hour validity, tied to the identity provider, so offboarding is one action and a leaked credential expires on its own. No long-lived static keys anywhere, including CI.

5. Continuous verification, not an annual audit. Automated CIS-benchmark scanning, vulnerability scanning against an SBOM, and drift detection — with the results as a dashboard and a trend, since the number that matters is "how long does a finding survive", not "how many findings do we have".

6. Detection with someone on the other end. Centralised logs with a disk-backed queue, alerts on new UID-0 accounts, new setuid binaries, unexpected egress, failed-auth spikes, and out-of-hours access. Every alert needs an owner and a documented response — alerts nobody reads are worse than no alerts, because they create the appearance of coverage.

7. Practise the incident response. A tested rebuild path, tested backup restores, and a credential-rotation runbook that has actually been run. The first time you rebuild a compromised host should not be during the compromise.

The measures I would track: percentage of hosts on the current image, mean time from CVE publication to fleet patched, number of hosts with drift, and time to detect a simulated intrusion. Those four say more about the fleet's security than any checklist completion percentage.

1 (easy): Audit a host's exposed attack surface in one pass.
Solution

1. What is listening, and on which address:

$ sudo ss -tulnp | awk 'NR>1 {print $1, $5, $NF}'
tcp 0.0.0.0:22    users:(("sshd",pid=901,fd=3))
tcp 127.0.0.1:631 users:(("cupsd",pid=742,fd=8))
tcp 0.0.0.0:5432  users:(("postgres",pid=980,fd=5))
udp 0.0.0.0:68    users:(("dhclient",pid=680,fd=6))

Filter to just the exposed ones:

$ sudo ss -tlnp | awk 'NR>1 && ($4 ~ /^0\.0\.0\.0:/ || $4 ~ /^\[::\]:/) {print "EXPOSED:", $4, $NF}'
EXPOSED: 0.0.0.0:22 users:(("sshd",pid=901,fd=3))
EXPOSED: 0.0.0.0:5432 users:(("postgres",pid=980,fd=5))     ← finding

Postgres on all interfaces is the finding. Fix in postgresql.conf: listen_addresses = 'localhost' — or better, a Unix socket.

dhruv /bin/bash

$ sudo getcap -r / 2>/dev/null

Save that list as a baseline — a new setuid binary appearing later is a strong compromise indicator.

4. SSH configuration and authorised keys:

$ sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication|pubkeyauthentication|maxauthtries)'
permitrootlogin without-password         ← finding: should be 'no'
passwordauthentication yes               ← finding: should be 'no'
pubkeyauthentication yes
maxauthtries 6
$ for f in /home/*/.ssh/authorized_keys /root/.ssh/authorized_keys; do
>   [[ -f $f ]] && { echo "== $f"; ssh-keygen -lf "$f"; }
> done

sshd -T is the right tool here: it prints the effective configuration including defaults and drop-ins, not just what is written in the main file.

5. Patch state:

$ apt list --upgradable 2>/dev/null | grep -ci security
14
$ [[ -f /var/run/reboot-required ]] && echo "REBOOT REQUIRED: $(cat /var/run/reboot-required.pkgs | tr '\n' ' ')"
REBOOT REQUIRED: linux-image-6.8.0-45-generic
$ sudo needrestart -b 2>/dev/null | grep NEEDRESTART-SVC

Summary of findings from this one pass: Postgres exposed, root SSH permitted, password auth enabled, 14 pending security updates, a pending kernel reboot, and jenkins in the docker group. Every one is a five-minute fix, and together they represent most of the host's realistic risk.

2 (easy): Harden SSH safely, without locking yourself out.
Solution

1. Make sure key access works BEFORE changing anything:

$ ssh-keygen -t ed25519 -C "dhruv@laptop-2026"
$ ssh-copy-id -i ~/.ssh/id_ed25519.pub dhruv@server
$ ssh -i ~/.ssh/id_ed25519 -o PasswordAuthentication=no dhruv@server 'echo KEY AUTH OK'
KEY AUTH OK

Never proceed past this step until it prints OK.

2. Write a drop-in rather than editing the main file — it survives package updates:

$ sudo tee /etc/ssh/sshd_config.d/99-hardening.conf <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
AuthenticationMethods publickey
AllowGroups ssh-users
MaxAuthTries 3
LoginGraceTime 20
X11Forwarding no
ClientAliveInterval 300
ClientAliveCountMax 2
EOF
$ sudo groupadd -f ssh-users && sudo usermod -aG ssh-users dhruv

3. Validate the syntax and the effective config:

$ sudo sshd -t && echo "syntax OK"
syntax OK
$ sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication|allowgroups|maxauthtries)'
permitrootlogin no
passwordauthentication no
allowgroups ssh-users
maxauthtries 3

4. Set a safety net before reloading — if you lose access, this reverts it:

$ sudo systemd-run --on-active=5m --unit=ssh-revert \
>   /bin/sh -c 'rm -f /etc/ssh/sshd_config.d/99-hardening.conf; systemctl reload ssh'

5. Reload — not restart — and verify from a SECOND terminal:

$ sudo systemctl reload ssh          # reload does not drop existing connections

# in a NEW terminal, keeping the first one open:
$ ssh dhruv@server 'echo STILL WORKS'
STILL WORKS
$ ssh root@server 2>&1 | head -1
root@server: Permission denied (publickey).      # root correctly refused

6. Only now cancel the safety net:

$ sudo systemctl stop ssh-revert.timer 2>/dev/null; sudo systemctl reset-failed ssh-revert 2>/dev/null

7. Confirm password attempts are actually rejected:

$ ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password dhruv@server 2>&1 | head -1
Permission denied (publickey).
$ sudo journalctl -u ssh --since '5 min ago' | grep -i 'accepted\|denied' | tail -3

The pattern to internalise: verify the new access path works before removing the old one, reload rather than restart, and test in a second session while the first stays open.

3 (medium): Configure a default-deny firewall without locking yourself out.
Solution

1. Record the current state and your own connection:

$ sudo ufw status
Status: inactive
$ echo "connected from: ${SSH_CLIENT%% *}"
connected from: 10.0.2.11

2. Add the SSH rule FIRST — before any policy change:

$ sudo ufw allow from 10.0.0.0/8 to any port 22 proto tcp comment 'ssh from internal'
$ sudo ufw limit 22/tcp comment 'rate-limit ssh'
$ sudo ufw show added
ufw allow from 10.0.0.0/8 to any port 22 proto tcp
ufw limit 22/tcp

show added lets you review rules before they are active.

3. Add the service rules, then the default policy:

$ sudo ufw allow 80,443/tcp comment 'web'
$ sudo ufw default deny incoming
$ sudo ufw default allow outgoing

4. Set a revert timer before enabling — the step that makes this safe:

$ sudo systemd-run --on-active=3m --unit=fw-revert ufw --force disable
Running as unit: fw-revert.service

5. Enable and immediately verify from a new session:

$ sudo ufw --force enable
Firewall is active and enabled on system startup
$ sudo ufw status verbose
Status: active
Default: deny (incoming), allow (outgoing)
To                Action      From
22/tcp            ALLOW IN    10.0.0.0/8
22/tcp            LIMIT IN    Anywhere
80,443/tcp        ALLOW IN    Anywhere

# from another machine / new terminal:
$ ssh dhruv@server 'echo SSH STILL WORKS'
SSH STILL WORKS
$ nc -zv server 80 && echo "web reachable"
$ nc -zv -w3 server 5432 2>&1 | tail -1
nc: connect to server port 5432 (tcp) timed out     # correctly blocked (DROP, not REJECT)

The timeout rather than "refused" confirms it is a DROP rule doing the work.

6. Cancel the revert only after verifying:

$ sudo systemctl stop fw-revert.timer 2>/dev/null; sudo systemctl reset-failed fw-revert 2>/dev/null

7. Add egress filtering — the part almost everyone skips:

$ sudo ufw default deny outgoing
$ sudo ufw allow out 53 comment 'dns'
$ sudo ufw allow out to 10.0.0.0/8 comment 'internal'
$ sudo ufw allow out 443/tcp comment 'https: repos and apis'
$ sudo ufw allow out 123/udp comment 'ntp'
$ curl -sf -m5 https://example.com >/dev/null && echo "https OK"
$ nc -zv -w3 1.2.3.4 4444 2>&1 | tail -1
nc: connect to 1.2.3.4 port 4444 (tcp) timed out     # C2-style egress blocked

Egress rules are what limit damage after a compromise — malware needs to reach its C2 server and exfiltrated data needs somewhere to go.

8. Verify persistence across reboot:

$ systemctl is-enabled ufw
enabled
$ sudo nft list ruleset | head -5           # what ufw actually generated
4 (medium): Sandbox a service and measure the improvement.
Solution

1. A deliberately unhardened service:

$ sudo tee /usr/local/bin/demoapp.sh >/dev/null <<'EOF'
#!/bin/sh
mkdir -p /var/lib/demoapp
while true; do date >> /var/lib/demoapp/heartbeat.log; sleep 5; done

4. Measure:

→ Overall exposure level for demoapp.service: 1.4 OK 🙂

9.6 → 1.4 with no change to the application.

CapEff:	0000000000000000                # no capabilities at all
$ sudo nsenter -t $PID -m sh -c 'touch /etc/probe 2>&1; ls /root 2>&1 | head -1; ls /tmp | wc -l'

5 (hard): Build a detection baseline and trigger it.
Solution

1. Audit rules for the things that matter:

$ sudo tee /etc/audit/rules.d/99-baseline.rules >/dev/null <<'EOF'
-w /etc/passwd -p wa -k identity
-w /etc/shadow -p wa -k identity
-w /etc/sudoers -p wa -k sudoers
-w /etc/sudoers.d/ -p wa -k sudoers
-w /etc/ssh/sshd_config -p wa -k sshd_config
-w /root/.ssh/ -p wa -k ssh_keys
-a always,exit -F arch=b64 -S execve -F euid=0 -F auid>=1000 -F auid!=4294967295 -k rootcmd
-a always,exit -F arch=b64 -S chmod,fchmod,fchmodat -F a1&04000 -k setuid_set
EOF
$ sudo augenrules --load && sudo auditctl -l | head -5

2. Baseline the filesystem state you care about:

$ sudo find / -xdev -perm -4000 -type f 2>/dev/null | sort | sudo tee /var/lib/baseline-suid.txt | wc -l
17
$ sudo getcap -r / 2>/dev/null | sort | sudo tee /var/lib/baseline-caps.txt
$ awk -F: '{print $1":"$3}' /etc/passwd | sort | sudo tee /var/lib/baseline-users.txt >/dev/null
$ sudo sha256sum /etc/passwd /etc/shadow /etc/sudoers | sudo tee /var/lib/baseline-hashes.txt

3. Trigger each detection and confirm it fires.

New user account:

$ sudo useradd -m -s /bin/bash suspicious
$ sudo ausearch -k identity -ts recent 2>/dev/null | grep -c 'type=SYSCALL'
4
$ comm -13 /var/lib/baseline-users.txt <(awk -F: '{print $1":"$3}' /etc/passwd | sort)
suspicious:1001                          ← detected

New UID-0 account — the high-severity case:

$ sudo usermod -u 0 -o suspicious
$ awk -F: '$3==0 {print $1}' /etc/passwd
root
suspicious                               ← CRITICAL finding

New setuid binary:

$ sudo cp /bin/bash /usr/local/bin/.hidden-sh && sudo chmod u+s /usr/local/bin/.hidden-sh
$ comm -13 /var/lib/baseline-suid.txt \
>   <(sudo find / -xdev -perm -4000 -type f 2>/dev/null | sort)
/usr/local/bin/.hidden-sh                ← detected
$ sudo ausearch -k setuid_set -ts recent 2>/dev/null | tail -3

Modified sudoers:

$ echo 'suspicious ALL=(ALL) NOPASSWD: ALL' | sudo tee /etc/sudoers.d/99-backdoor
$ sudo ausearch -k sudoers -ts recent 2>/dev/null | grep -oE 'name="[^"]+"' | tail -1
name="/etc/sudoers.d/99-backdoor"        ← detected
$ sudo sha256sum -c /var/lib/baseline-hashes.txt 2>&1 | grep -v OK

New authorized_keys entry:

$ sudo mkdir -p /root/.ssh && echo "ssh-ed25519 AAAAC3Nz... attacker@host" | sudo tee -a /root/.ssh/authorized_keys
$ sudo ausearch -k ssh_keys -ts recent 2>/dev/null | grep -c type=PATH
2                                        ← detected

4. A single check script suitable for a timer:

$ sudo tee /usr/local/bin/security-check.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
f=0
chk() { if [[ -n "$2" ]]; then echo "ALERT: $1"; echo "$2"; f=1; fi; }
chk "unexpected UID-0 account(s)" "$(awk -F: '$3==0 && $1!="root"{print $1}' /etc/passwd)"
chk "new setuid binaries" "$(comm -13 /var/lib/baseline-suid.txt \
      <(find / -xdev -perm -4000 -type f 2>/dev/null | sort))"
chk "new file capabilities" "$(comm -13 /var/lib/baseline-caps.txt \
      <(getcap -r / 2>/dev/null | sort))"
chk "modified critical files" "$(sha256sum -c /var/lib/baseline-hashes.txt 2>&1 | grep -v ': OK')"
chk "empty passwords" "$(awk -F: '$2==""{print $1}' /etc/shadow)"
[[ $f -eq 0 ]] && echo "baseline clean"
exit $f
EOF
$ sudo chmod +x /usr/local/bin/security-check.sh
$ sudo /usr/local/bin/security-check.sh
ALERT: unexpected UID-0 account(s)
suspicious
ALERT: new setuid binaries
/usr/local/bin/.hidden-sh
ALERT: modified critical files
/etc/passwd: FAILED

All three planted artefacts detected.

5. Schedule it, so the check runs without anyone remembering:

$ sudo systemd-run --on-calendar='hourly' --unit=security-check /usr/local/bin/security-check.sh
$ systemctl list-timers security-check --no-pager

Cleanup — remove every planted artefact:

$ sudo userdel -r suspicious 2>/dev/null
$ sudo rm -f /usr/local/bin/.hidden-sh /etc/sudoers.d/99-backdoor
$ sudo sed -i '/attacker@host/d' /root/.ssh/authorized_keys
$ sudo /usr/local/bin/security-check.sh
baseline clean

The value here is not the script — it is having a baseline. Detection is comparison against a known-good state, and without one recorded in advance, "is this setuid binary supposed to be here?" has no answer.

6 (hard): Run the full production checklist against a host and produce a report.
Solution 
$ sudo tee /usr/local/bin/prodcheck.sh >/dev/null <<'BASH'
#!/usr/bin/env bash
pass=0; fail=0; warn=0
ok()   { printf '  \033[32m[PASS]\033[0m %s\n' "$1"; pass=$((pass+1)); }
bad()  { printf '  \033[31m[FAIL]\033[0m %s\n' "$1"; fail=$((fail+1)); }
warn() { printf '  \033[33m[WARN]\033[0m %s\n' "$1"; warn=$((warn+1)); }
sec()  { printf '\n\033[1m== %s ==\033[0m\n' "$1"; }

sec "Access"
[[ "$(sshd -T 2>/dev/null | awk '/^permitrootlogin/{print $2}')" == "no" ]] \
  && ok "root SSH login disabled" || bad "PermitRootLogin is not 'no'"
[[ "$(sshd -T 2>/dev/null | awk '/^passwordauthentication/{print $2}')" == "no" ]] \
  && ok "password auth disabled" || bad "PasswordAuthentication is enabled"
n=$(awk -F: '$3==0 && $1!="root"' /etc/passwd | wc -l)
[[ $n -eq 0 ]] && ok "only root has UID 0" || bad "$n extra UID-0 account(s)"
n=$(awk -F: '$2==""' /etc/shadow 2>/dev/null | wc -l)
[[ $n -eq 0 ]] && ok "no empty passwords" || bad "$n account(s) with no password"
n=$(getent group docker 2>/dev/null | cut -d: -f4 | tr ',' '\n' | grep -c .)
[[ $n -eq 0 ]] && ok "docker group empty" || warn "$n user(s) in docker group (== root)"

sec "Network"
n=$(ss -tlnH | awk '$4 ~ /^0\.0\.0\.0:|^\[::\]:/' | wc -l)
[[ $n -le 3 ]] && ok "$n service(s) on all interfaces" || warn "$n services exposed — review"
if command -v ufw >/dev/null && ufw status 2>/dev/null | grep -q '^Status: active'; then
  ok "firewall active"
elif nft list ruleset 2>/dev/null | grep -q 'policy drop'; then
  ok "nftables default-deny active"
else bad "no default-deny firewall"; fi
[[ "$(sysctl -n net.ipv4.tcp_syncookies 2>/dev/null)" == "1" ]] \
  && ok "SYN cookies enabled" || warn "SYN cookies disabled"
[[ "$(sysctl -n kernel.dmesg_restrict 2>/dev/null)" == "1" ]] \
  && ok "dmesg restricted" || warn "dmesg readable by non-root"

sec "Services"
n=$(ps -eo user:20,comm --no-headers | awk '$1=="root"' | wc -l)
warn "$n process(es) running as root — review each"
if command -v systemd-analyze >/dev/null; then
  n=$(systemd-analyze security --no-pager 2>/dev/null | awk '$3=="UNSAFE"' | wc -l)
  [[ $n -eq 0 ]] && ok "no UNSAFE-rated units" || warn "$n unit(s) rated UNSAFE"
fi

sec "Storage"
while read -r pct mnt; do
  [[ ${pct%\%} -ge 85 ]] && bad "disk ${pct} on $mnt" || ok "disk ${pct} on $mnt"
done < <(df -hP -x tmpfs -x devtmpfs --output=pcent,target | tail -n +2)
while read -r pct mnt; do
  [[ ${pct%\%} -ge 85 ]] && bad "inodes ${pct} on $mnt" || ok "inodes ${pct} on $mnt"
done < <(df -iP -x tmpfs -x devtmpfs --output=ipcent,target | tail -n +2 | grep -v '^ *-')

sec "Observability"
[[ -d /var/log/journal ]] && ok "journal is persistent" || bad "journal is VOLATILE — lost on reboot"
timedatectl show -p NTPSynchronized --value 2>/dev/null | grep -q yes \
  && ok "clock synchronised" || bad "clock NOT synchronised"
[[ "$(timedatectl show -p Timezone --value 2>/dev/null)" == "UTC" ]] \
  && ok "timezone is UTC" || warn "timezone is not UTC"

sec "Maintenance"
if [[ -f /etc/apt/apt.conf.d/20auto-upgrades ]] \
   && grep -q '"1"' /etc/apt/apt.conf.d/20auto-upgrades 2>/dev/null; then
  ok "unattended upgrades enabled"
else bad "automatic security updates not enabled"; fi
[[ -f /var/run/reboot-required ]] && bad "REBOOT REQUIRED (kernel/libc update pending)" \
  || ok "no pending reboot"
if command -v getenforce >/dev/null; then
  [[ "$(getenforce)" == "Enforcing" ]] && ok "SELinux enforcing" || warn "SELinux $(getenforce)"
elif command -v aa-status >/dev/null; then
  aa-status --enabled 2>/dev/null && ok "AppArmor enabled" || warn "AppArmor not enabled"
else warn "no MAC system detected"; fi

printf '\n\033[1m== SUMMARY ==\033[0m\n  pass=%d  warn=%d  fail=%d\n' "$pass" "$warn" "$fail"
[[ $fail -eq 0 ]] || exit 1
BASH

🎯 Key Takeaways

  • Hardening has an order: SSH keys only, automatic security updates, and closing exposed ports remove most realistic risk in under an hour — before any SELinux policy.
  • Binding a service to 127.0.0.1 or a Unix socket is stronger than a firewall rule, because it survives perimeter misconfiguration.
  • Always sshd -t, reload rather than restart, and verify in a second session — with a scheduled revert as a safety net.
  • Audit authorized_keys across the fleet: orphaned keys outlive the people and machines they belonged to, and nothing expires them.
  • At team scale, SSH certificates beat authorized_keys — central revocation, automatic expiry, no per-host distribution.
  • Every setuid binary is a potential escalation; audit them, record a baseline, and prefer file capabilities which grant one privilege instead of all of root.
  • Docker group membership is unrestricted host root with no audit trail — treat it exactly like sudo.
  • Add firewall rules before enabling default-deny, and remember existing connections survive the change so it looks fine until you reconnect.
  • Egress filtering is what limits damage after a compromise, and it is the control almost everyone skips.
  • Automatic security updates beat quarterly windows; needrestart catches services still running the old, vulnerable library after an upgrade.
  • Never disable SELinux/AppArmor to fix a service — use permissive mode, read the AVCs, and write the policy.
  • Detection is comparison against a recorded baseline; without one, "should this setuid binary be here?" has no answer.
  • On suspected compromise: isolate but do not power off, capture volatile state, copy evidence off-host, then rebuild rather than clean and rotate every credential.
  • A checklist that runs on a timer and exits non-zero is worth more than a thorough one-time audit — security is a property of the current state, not of a past review.
