Logs, Journals & Time The Running System

What you'll master: where logs actually live on a modern system and why there are two parallel systems, how logrotate can silently break a daemon and the one directive that prevents it, why writing to stdout is the correct choice for a service, how clock skew corrupts an investigation and how NTP fixes it without ever stepping the clock backwards, why monotonic and wall-clock time are different and which one a timeout must use, and how to trace a request across services when every host disagrees about what time it is. Prerequisites: systemd & Service Management and Redirection, Pipes & File Descriptors.

Part 1 — Two Logging Systems, Side by Side

A modern Linux host runs both the systemd journal and, usually, a syslog daemon. They are not alternatives so much as layers, and knowing which one holds what saves an enormous amount of searching.

   application stdout/stderr ──┐
   sd_journal_send()           ├──►  systemd-journald  ──► /run/log/journal (volatile)
   syslog(3) / /dev/log        ─┘         │                /var/log/journal (persistent)
   kernel ring buffer (/dev/kmsg) ────────┘
                                          │  forwards
                                          ▼
                                   rsyslog / syslog-ng  ──► /var/log/syslog, auth.log, ...
                                                         ──► remote log server
SourceRead withNotes
Service stdout/stderrjournalctl -u UNITCaptured automatically, no config needed
Kernel messagesjournalctl -k or dmesg -TOOM kills, disk errors, link state
Authenticationjournalctl -t sshd, /var/log/auth.logDuplicated in both on most distros
Application's own filetail -F /var/log/app/*.logNeeds its own rotation — the source of most log bugs
Audit subsystemausearch, /var/log/audit/Separate daemon, separate format

The journal is a structured binary store, not a text file. Every entry carries indexed fields — unit, PID, UID, boot ID, executable path — which is why it can answer questions grep cannot:

$ journalctl -o json-pretty -n 1 -u ssh
{
    "__REALTIME_TIMESTAMP" : "1786455662104213",
    "_BOOT_ID" : "9c1e77a4f0b24c1a8e33d0b7c2145aa9",
    "_SYSTEMD_UNIT" : "ssh.service",
    "_PID" : "901",
    "_UID" : "0",
    "PRIORITY" : "6",
    "MESSAGE" : "Accepted publickey for dhruv from 10.0.2.11 port 51422"
}

$ journalctl _PID=901 --since today          # query by any field, no grep
$ journalctl _UID=1000 -p err
$ journalctl _SYSTEMD_UNIT=nginx.service _PID=1204
🔑 Check that the journal is persistent before you need it. If /var/log/journal/ does not exist, journald writes to /run/log/journal — tmpfs — and every log is lost at reboot. That is the default on several distributions and on most container images, and it is invariably discovered right after the crash you needed to investigate: ls -d /var/log/journal || sudo mkdir -p /var/log/journal && sudo systemctl restart systemd-journald.

Part 2 — Priorities, Facilities, and Rate Limiting

Syslog's severity scale is inherited by the journal and by nearly every logging library, so the numbers are worth knowing — -p err means "err and worse", not "err only".

#NameMeansShould it page someone?
0emergSystem unusableYes
1alertImmediate action requiredYes
2critCritical conditionYes
3errError — something failedTicket, or page if sustained
4warningSomething is off but handledNo — dashboard
5noticeNormal but significantNo
6infoRoutine operationNo
7debugDiagnostic detailOff in production
$ journalctl -p err -b --no-pager | tail -20        # errors and worse, this boot
$ journalctl -p warning..err --since '1 hour ago'   # a range
$ logger -p local0.warning "cache warm-up skipped"  # write to the journal from a script
$ logger -t deploy -p user.notice "release v2.4.1 started"

journald rate-limits by default, and a service that suddenly logs thousands of lines a second will have entries silently dropped — with one line saying so, which is easy to miss:

$ journalctl | grep -i 'suppressed'
Aug 10 09:22:14 host systemd-journald[412]: Suppressed 4821 messages from myapp.service

# /etc/systemd/journald.conf
RateLimitIntervalSec=30s
RateLimitBurst=10000
SystemMaxUse=2G
MaxRetentionSec=30day

The per-unit override is usually the better tool, because raising the global limit lets one noisy service drown out everything else:

[Service]
LogRateLimitIntervalSec=0        # exempt this unit entirely
LogLevelMax=info                 # or drop debug at the source

Part 3 — Rotation, and How It Breaks Daemons

An application that writes its own log file must have it rotated, or the disk fills. The mechanism is simple; the failure mode is not obvious and it is extremely common.

# /etc/logrotate.d/myapp
/var/log/myapp/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    create 0640 myapp adm
    sharedscripts
    postrotate
        systemctl reload myapp >/dev/null 2>&1 || true
    endscript
}

Here is the failure. logrotate renames app.log to app.log.1. But the daemon holds an open file descriptor to the inode, not the name — as Files, Inodes & Links explains — so it keeps writing to the renamed file forever. The new app.log stays empty, and disk space is never reclaimed because the old file is still open:

$ ls -l /var/log/myapp/
-rw-r----- 1 myapp adm         0 Aug 10 00:00 app.log        # empty, and staying empty
-rw-r----- 1 myapp adm 8412034221 Aug 10 09:41 app.log.1     # still growing

$ sudo lsof -nP /var/log/myapp/ | grep -v app.log$
COMMAND   PID  USER  FD  TYPE  SIZE/OFF   NODE NAME
java    65100 myapp  31w  REG 8412034221 262149 /var/log/myapp/app.log.1
ApproachHow it worksTrade-off
postrotate + reload/HUPDaemon reopens its log file by nameCorrect — requires the app to handle the signal
copytruncateCopy the file, then truncate the original in placeNo signal needed, but loses lines written during the copy
Log to stdout + journaldNo files, no rotation at allBest — the problem stops existing

This is the strongest practical argument for the twelve-factor rule: a service should write to stdout and let the supervisor handle the rest. No rotation config, no reopen signal, no permissions on a log directory, no descriptor to leak — and the journal adds unit, PID and boot metadata for free.

$ sudo logrotate -d /etc/logrotate.d/myapp      # dry run — shows what WOULD happen
$ sudo logrotate -f /etc/logrotate.d/myapp      # force a rotation now, to test it
$ cat /var/lib/logrotate/status | grep myapp    # when it last ran

❌ Adding copytruncate because the daemon "doesn't support reload". Between the copy finishing and the truncate landing, every line the application writes is destroyed. On a busy service that is thousands of lines a day, gone silently — and they are disproportionately likely to be the ones you need, since rotation happens during the quiet window that follows a busy one.

✅ Prefer reopening. Almost every daemon reopens its logs on SIGHUP or on systemctl reload; postrotate is one line. If the application genuinely cannot, the right fix is to make it log to stdout and let journald take it — copytruncate is a last resort that trades correctness for convenience.

Part 4 — Clocks: Wall, Monotonic, and Skew

Linux exposes several clocks, and choosing the wrong one is a real bug class. Wall-clock time can jump backwards; monotonic time cannot.

ClockMeasuresCan jump?Use for
CLOCK_REALTIMEWall-clock time since the epochYes — NTP steps, manual set, DST is separateTimestamps, logs, "when did this happen"
CLOCK_MONOTONICTime since bootNo, only pauses in suspendTimeouts, intervals, latency
CLOCK_BOOTTIMESince boot, including suspendNoTimers that must fire after a laptop wakes
CLOCK_PROCESS_CPUTIME_IDCPU time consumedNoProfiling, CPU accounting
$ python3 -c "
import time
print('realtime :', time.time())                 # can go backwards
print('monotonic:', time.monotonic())            # never does
"
realtime : 1786455662.104
monotonic: 184203.51

The bug this prevents is concrete: a timeout computed as end = time.time() + 30 and then compared against time.time() will hang for hours if NTP steps the clock backwards by an hour mid-wait, and will fire instantly if it steps forwards.

# WRONG — a clock step breaks the timeout
deadline = time.time() + 30
while time.time() < deadline: ...

# RIGHT — immune to clock adjustments
deadline = time.monotonic() + 30
while time.monotonic() < deadline: ...

Two hardware clocks exist, and confusing them causes an offset that appears at boot:

$ timedatectl
               Local time: Sun 2026-08-10 09:41:02 IST
           Universal time: Sun 2026-08-10 04:11:02 UTC
                 RTC time: Sun 2026-08-10 04:11:01
                Time zone: Asia/Kolkata (IST, +0530)
System clock synchronized: yes
              NTP service: active
             RTC in local TZ: no                  # keep it 'no' — UTC in hardware

The system clock is maintained by the kernel; the RTC is battery-backed hardware read at boot. Store UTC in the RTC. "RTC in local TZ: yes" — the Windows convention — produces a wrong clock at every DST transition on a dual-boot machine.

Part 5 — NTP, and Why It Slews Instead of Stepping

Time synchronisation does not simply set the clock. A correct NTP implementation slews — it speeds up or slows down the clock's tick rate until the offset is gone — because a backwards jump breaks any code holding a wall-clock deadline, corrupts log ordering, and can violate a database's assumptions.

$ timedatectl timesync-status
       Server: 91.189.91.157 (ntp.ubuntu.com)
Poll interval: 34min 8s (min: 32s; max 34min 8s)
       Offset: +2.481ms
        Delay: 12.903ms
       Jitter: 1.204ms

$ chronyc tracking                   # if using chrony instead
Reference ID    : C0248F97 (ntp1.example.com)
Stratum         : 3
System time     : 0.000241 seconds slow of NTP time
Frequency       : 12.481 ppm slow
Skew            : 0.412 ppm
Root dispersion : 0.001204 seconds
FieldMeaningHealthy value
OffsetDifference from true time< 10 ms on a LAN, < 100 ms over WAN
StratumHops from a reference clock2–4; 16 means unsynchronised
FrequencyHow fast the local oscillator driftsStable value; large swings mean thermal issues or a bad VM host
Jitter / Root dispersionMeasurement uncertaintyLow and stable
$ timedatectl set-ntp true                       # enable synchronisation
$ sudo chronyc makestep                          # force an immediate STEP — use with care
$ journalctl -u systemd-timesyncd --since today | tail -3

A step is occasionally the right answer — at boot, or when the offset is so large that slewing would take days — but it should be deliberate. chrony's makestep 1.0 3 configuration says exactly that: step only in the first three updates, slew forever after.

Leap seconds are the historical hazard here: inserting a 61st second has crashed real systems. The modern practice is leap smearing — spreading the extra second over hours so no clock ever repeats or reverses. Google and AWS time sources do this; mixing a smearing and a non-smearing source in one fleet is a subtle way to create disagreement.

Part 6 — Correlating Logs Across Machines

An investigation spanning services is only as good as the timestamps, and three problems have to be solved before the logs are usable: agreeing on a timezone, agreeing on the actual time, and being able to follow one request.

1. Log in UTC, always. Local time in logs makes cross-region correlation guesswork and creates one ambiguous hour every year when DST ends:

$ journalctl -u myapp --utc -o short-precise
Aug 10 04:11:02.104821 host myapp[65100]: request started
$ sudo timedatectl set-timezone UTC          # standard practice for servers

2. Verify the hosts agree before trusting an ordering conclusion:

$ for h in web1 web2 db1; do
>   printf '%-6s %s  offset=%s\n' "$h" \
>     "$(ssh $h date -u +%FT%T.%3NZ)" \
>     "$(ssh $h 'chronyc tracking 2>/dev/null | awk "/System time/{print \$4, \$6}"')"
> done
web1   2026-08-10T04:11:02.104Z  offset=0.000241 slow
web2   2026-08-10T04:11:02.108Z  offset=0.000512 slow
db1    2026-08-10T04:11:04.902Z  offset=2.801423 slow      ← 2.8s adrift

A host 2.8 seconds adrift makes cause and effect appear reversed. Any conclusion of the form "the database error happened before the request" is worthless until that is fixed.

3. Carry a request ID, because even perfectly synchronised clocks cannot tell you which of 500 concurrent requests a log line belongs to:

$ journalctl --since '04:11:00' --until '04:11:10' -o short-precise \
>   -u frontend -u api -u worker | grep 'req=7f3a91'
04:11:02.104 frontend[65100]: req=7f3a91 POST /orders
04:11:02.118 api[65200]:      req=7f3a91 validating payload
04:11:02.402 worker[65300]:   req=7f3a91 charge failed: upstream timeout
04:11:02.411 api[65200]:      req=7f3a91 returning 502

The correlation ID is what turns a pile of logs into a trace, and it is the single highest-value thing to add to a logging setup. Structured output makes it queryable rather than greppable:

$ journalctl -u api -o json --since '1 hour ago' \
>   | jq -r 'select(.PRIORITY <= "3") | "\(.__REALTIME_TIMESTAMP) \(.MESSAGE)"' | head

Finally, ship logs off the host. A machine that has crashed, been terminated by an autoscaler, or been compromised takes its local logs with it — and in the compromise case, the attacker's first move is usually to edit them:

# /etc/rsyslog.d/50-remote.conf
*.* @@logserver.internal:6514        # @@ = TCP; @ = UDP and loses messages under load
$ sudo systemctl restart rsyslog

Interview Questions

Beginner: Where do you look for logs on a modern Linux system?

Two places, and which one depends on the source.

The journal holds everything from systemd-managed services, plus the kernel:

$ journalctl -u nginx -n 50          # a specific unit
$ journalctl -k -b                   # kernel messages, this boot
$ journalctl -p err -b               # errors and worse
$ journalctl -b -1                   # the PREVIOUS boot — after an unexplained reboot

Anything a service writes to stdout or stderr lands there automatically, tagged with the unit, PID, UID and boot ID.

Files under /var/log/ hold what rsyslog wrote and what applications wrote themselves — /var/log/syslog, auth.log, nginx/access.log. Most distributions duplicate journal content into these, so the same message often appears in both.

Two practical notes I would add. First, check the journal is persistent: if /var/log/journal/ does not exist, journald writes to tmpfs and everything is lost at reboot — the default in many container images. Second, journalctl -b -1 is the command that matters after a crash, because the evidence is in the boot that ended, not the current one.

Beginner: What is log rotation and why does it exist?

Log files grow without bound. Rotation caps that by periodically renaming the current file, starting a fresh one, compressing the old ones and deleting the oldest.

/var/log/myapp/*.log {
    daily
    rotate 14          # keep two weeks
    compress
    missingok
    notifempty
    create 0640 myapp adm
    postrotate
        systemctl reload myapp
    endscript
}

logrotate runs from a systemd timer, typically daily.

The part that matters is the postrotate block. Renaming a file does not affect a process that already has it open — the descriptor points at the inode, not the name. Without telling the daemon to reopen, it keeps writing to app.log.1 forever, the new app.log stays empty, and the disk fills with a file that du can still see but nobody is reading.

copytruncate is the alternative for daemons that cannot reopen, but it loses any line written between the copy and the truncate.

The cleanest answer is to avoid the problem: a service that logs to stdout needs no rotation at all, because journald manages retention itself.

Mid: A service is running but its log file has been empty since midnight. What happened?

Midnight is when logrotate runs, so the rotation almost certainly succeeded while the reopen did not.

The mechanism: logrotate renamed app.log to app.log.1. The daemon holds a file descriptor to the inode, and renaming does not change the inode, so it carries on writing into the renamed file. A new empty app.log was created and nothing writes to it.

Confirm it in one command:

$ sudo lsof -nP /var/log/myapp/
COMMAND   PID  USER FD TYPE   SIZE/OFF   NODE NAME
java    65100 myapp 31w REG 8412034221 262149 /var/log/myapp/app.log.1
$ ls -l /var/log/myapp/
-rw-r----- 1 myapp adm          0 Aug 10 00:00 app.log
-rw-r----- 1 myapp adm 8412034221 Aug 10 09:41 app.log.1     # still growing

The process holds .1, which is still growing — conclusive.

Immediate recovery: systemctl reload myapp, or kill -HUP, makes the daemon reopen by name and start writing to app.log again.

Permanent fix: add a postrotate block that does exactly that. Test it without waiting a day using logrotate -d for a dry run and logrotate -f to force one.

The related failure worth mentioning is the same bug's cousin: if the file had been rm'd rather than renamed, the space would not be reclaimed either — df would show a full disk while du showed nothing, and lsof +L1 would find it.

Long term I would move the service to logging on stdout, which removes this entire class of problem.

Mid: Why should a timeout use monotonic time rather than wall-clock time?

Because wall-clock time can move — forwards or backwards — while the timeout is being measured, and a duration measured with a clock that jumps is not a duration.

CLOCK_REALTIME is adjusted by NTP, by an administrator, and at boot from the RTC. CLOCK_MONOTONIC counts from an arbitrary point (usually boot) and only ever moves forwards.

# WRONG
deadline = time.time() + 30
while time.time() < deadline: poll()

# RIGHT
deadline = time.monotonic() + 30
while time.monotonic() < deadline: poll()

The failure is asymmetric and both directions are bad. If the clock steps backwards an hour during the wait, the first version blocks for an hour instead of 30 seconds — a hung request, a held lock, a stuck deployment. If it steps forwards, the timeout fires immediately and the operation is abandoned when nothing was wrong.

This is precisely why NTP daemons slew rather than step under normal operation: they adjust the tick rate so the clock converges without ever repeating or reversing a timestamp. A step is reserved for boot or an offset too large to slew away in reasonable time.

Related distinctions worth knowing: CLOCK_BOOTTIME behaves like monotonic but keeps counting through suspend, which is what a timer on a laptop needs; and CLOCK_MONOTONIC is the correct basis for latency measurement and rate limiting for the same reason it is correct for timeouts.

Senior: Design a logging strategy for a fleet of 50 services across 200 hosts.

The goal is that an engineer can answer "what happened to this request" in minutes, without SSH-ing to any host. That shapes every decision.

1. Services log structured JSON to stdout. No files, no rotation, no log directory permissions, no reopen signals — the supervisor captures it:

{"ts":"2026-08-10T04:11:02.104Z","level":"error","svc":"api","req_id":"7f3a91",
 "trace_id":"4bf92f...","msg":"charge failed","upstream":"payments","dur_ms":2401}

Structured means queryable. level, svc and req_id become index fields rather than substrings someone has to grep for.

2. Correlation IDs are mandatory and propagated. A request ID generated at the edge and passed through every hop is what turns 50 services' logs into one story. I would enforce it in the shared HTTP middleware rather than trusting each team, and adopt W3C traceparent so the same identifier links logs to traces.

3. UTC everywhere, with verified synchronisation. Servers set to UTC, chrony on every host pointing at a small set of internal NTP servers, and an alert on offset exceeding 100 ms. Without this, ordering across hosts is fiction — and I would monitor it, because a single VM with a drifting clock produces investigations that reach the wrong conclusion confidently.

4. Ship off-host, immediately. A local agent (Vector, Fluent Bit) tails the journal and forwards over TCP with local disk buffering for collector outages. Logs must survive the host — autoscaler termination, a crash, or a compromise where editing local logs is the attacker's first step.

5. Tiered retention, because cost is the real constraint. Hot searchable storage for 7–14 days covers nearly every investigation; cheap object storage for 90+ days covers audit and forensics. Sampling high-volume success paths while keeping 100% of errors preserves signal at a fraction of the cost.

6. Log levels adjustable at runtime. Debug logging that requires a redeploy is debug logging that never gets used during an incident. An endpoint or signal handler that raises the level for one service, with an automatic revert, is worth building.

7. Be explicit about what logs are not. Logs answer "what happened to this specific request"; metrics answer "how is the system behaving"; traces answer "where did the time go". Using logs to compute rates is expensive and slow, and teams that skip metrics end up doing exactly that.

Finally, redaction at the source — tokens, card numbers, personal data — because once a secret is in the log pipeline it is in backups, in the search index, and on someone's laptop, and removing it is a project rather than a fix.

Senior: Timestamps across services appear inconsistent — a response is logged before its request. Diagnose it.

Effect preceding cause means one of three things: the clocks disagree, the timestamps are being generated somewhere other than where I assume, or the precision is too coarse to order events that are genuinely close together. I would rule them out in that order.

1. Measure the skew between the hosts involved:

$ for h in frontend1 api2; do
>   printf '%-10s %s  ' "$h" "$(ssh $h date -u +%FT%T.%6NZ)"
>   ssh $h 'chronyc tracking | awk "/System time/{print \$4,\$5,\$6}"'
> done
frontend1  2026-08-10T04:11:02.104213Z  0.000241 seconds slow
api2       2026-08-10T04:11:04.902871Z  2.801423 seconds slow

2.8 seconds is more than enough to invert an ordering. I would confirm the cause on that host — chronyd not running, blocked UDP 123, a stratum-16 unsynchronised state, or a VM whose clock drifts badly after live migration:

$ ssh api2 'timedatectl; chronyc sources -v; systemctl is-active chrony'

2. Check where the timestamp is actually produced. This catches the cases that survive perfect NTP:

  • A log line timestamped when it was written rather than when the event occurred — after a 2-second operation, that is a 2-second lie.
  • Buffered logging flushed in batches, so ordering within a file reflects flush order.
  • The collector applying its own ingestion timestamp, which reorders anything delayed in transit.
  • A container with a different /etc/localtime than the host, producing an offset that is exactly a whole number of hours — a strong tell.

3. Check precision. Second-granularity timestamps cannot order events 10 ms apart, and the apparent inversion may be a stable sort artefact:

$ journalctl -u api -o short-precise -n 5     # microsecond precision

4. Stop relying on timestamps for causality. This is the durable fix. Wall clocks are not a synchronisation primitive; distributed systems establish ordering with explicit causal information — a correlation ID plus span parent/child relationships, or a logical clock. With a trace_id and parent spans, the ordering is recorded rather than inferred, and it stays correct even with skew:

$ journalctl -u frontend -u api -o json --since '04:11:00' \
>   | jq -r 'select(.MESSAGE | test("7f3a91")) | .MESSAGE'

5. Prevent recurrence: alert on NTP offset per host, alert on stratum 16, ensure UDP 123 is permitted to the internal time servers, and use one consistent time source across the fleet — mixing leap-smearing and non-smearing sources reintroduces sub-second disagreement that is genuinely hard to spot.

🏋️ Exercises

1 (easy): Query the journal by field rather than by grep.
Solution 
$ logger -t exercise -p user.notice "hello from the exercise"
$ journalctl -t exercise -n 1 -o short-precise
Aug 10 09:41:02.104821 host exercise[65900]: hello from the exercise

See every indexed field on that entry:

$ journalctl -t exercise -n 1 -o json-pretty
{
    "__REALTIME_TIMESTAMP" : "1786455662104821",
    "_BOOT_ID" : "9c1e77a4f0b24c1a8e33d0b7c2145aa9",
    "_UID" : "1000",
    "_PID" : "65900",
    "SYSLOG_IDENTIFIER" : "exercise",
    "PRIORITY" : "5",
    "MESSAGE" : "hello from the exercise"
}

Query by any of them directly — no grep, and no false matches from message text:

$ journalctl _UID=1000 --since '5 min ago' -o cat
$ journalctl PRIORITY=5 -t exercise
$ journalctl _BOOT_ID=$(cat /proc/sys/kernel/random/boot_id | tr -d -) -t exercise

Discover which values exist for a field:

$ journalctl -F _SYSTEMD_UNIT | head -8
ssh.service
nginx.service
systemd-journald.service
$ journalctl -F PRIORITY

Write structured fields yourself, which is what a well-instrumented service does:

$ echo "MESSAGE=order failed
PRIORITY=3
REQ_ID=7f3a91
ORDER_ID=44120" | systemd-cat
$ journalctl REQ_ID=7f3a91 -o json-pretty | grep -E 'MESSAGE|ORDER_ID'
    "ORDER_ID" : "44120",
    "MESSAGE" : "order failed"

That last capability is the real argument for structured logging: journalctl REQ_ID=7f3a91 finds every line of one request across every service, with no pattern matching at all.

2 (easy): Check whether your journal survives a reboot, and bound its size.
Solution 
$ ls -d /var/log/journal 2>/dev/null && echo "PERSISTENT" || echo "VOLATILE — lost on reboot"
VOLATILE — lost on reboot
$ journalctl --list-boots | wc -l
1                                    # only the current boot: confirmation

Make it persistent:

$ sudo mkdir -p /var/log/journal
$ sudo systemd-tmpfiles --create --prefix /var/log/journal
$ sudo systemctl restart systemd-journald
$ journalctl --disk-usage
Archived and active journals take up 24.0M in the file system.

Bound the size before it bounds you:

$ sudo tee /etc/systemd/journald.conf.d/limits.conf <<'EOF'
[Journal]
Storage=persistent
SystemMaxUse=1G
SystemKeepFree=2G
MaxRetentionSec=30day
MaxFileSec=1day
EOF
$ sudo systemctl restart systemd-journald
$ journalctl --header | grep -E 'File Path|Entries' | head -4

Trim an already-oversized journal:

$ journalctl --disk-usage
Archived and active journals take up 3.8G in the file system.
$ sudo journalctl --vacuum-size=500M
Deleted archived journal /var/log/journal/.../system@...journal (128.0M).
Vacuuming done, freed 3.3G of archived journals.
$ sudo journalctl --vacuum-time=7d

Check for rate-limit drops, which are easy to miss and mean missing evidence:

$ journalctl -b | grep -i 'suppressed' | tail -3
systemd-journald[412]: Suppressed 4821 messages from myapp.service
$ systemctl show myapp -p LogRateLimitIntervalSec -p LogRateLimitBurst

If a service is legitimately verbose, exempt that unit rather than raising the global limit — otherwise one noisy service can push everything else out of the journal.

3 (medium): Reproduce the rotation bug, then fix it both ways.
Solution

1. A writer that holds its log open, exactly like a daemon:

$ mkdir -p /tmp/logdemo
$ python3 - <<'EOF' &
import time
f = open('/tmp/logdemo/app.log', 'a')     # opened ONCE, held forever
for i in range(1000):
    f.write(f"line {i} at {time.strftime('%T')}\n"); f.flush()
    time.sleep(0.5)
EOF
$ sleep 3; wc -l /tmp/logdemo/app.log
6 /tmp/logdemo/app.log

2. Rotate it the way logrotate does — by renaming:

$ mv /tmp/logdemo/app.log /tmp/logdemo/app.log.1
$ touch /tmp/logdemo/app.log
$ sleep 3
$ wc -l /tmp/logdemo/app.log /tmp/logdemo/app.log.1
  0 /tmp/logdemo/app.log          # the NEW file: empty and staying empty
 12 /tmp/logdemo/app.log.1        # the old one: still growing

3. Prove the descriptor is the cause:

$ PID=$(pgrep -f 'python3 -$' | head -1)
$ ls -l /proc/$PID/fd/ | grep logdemo
l-wx------ 1 dhruv dhruv 64 Aug 10 09:44 3 -> /tmp/logdemo/app.log.1
$ stat -c '%i %n' /tmp/logdemo/app.log*
262151 /tmp/logdemo/app.log        # new inode
262149 /tmp/logdemo/app.log.1      # the inode the process holds

Different inodes. The process never knew the name changed, because it never uses the name again.

4. Fix A — copytruncate, which keeps the inode and works without cooperation:

$ cp /tmp/logdemo/app.log.1 /tmp/logdemo/app.log.2 && : > /tmp/logdemo/app.log.1
$ sleep 2; wc -l /tmp/logdemo/app.log.1
4 /tmp/logdemo/app.log.1           # writing resumed into the same (now truncated) inode

It works — but any line written between the cp and the :> is gone with no trace. On a busy service that is a real, silent loss.

5. Fix B — reopen on signal, the correct approach:

$ kill %1
$ python3 - <<'EOF' &
import time, signal
path = '/tmp/logdemo/app.log'
f = open(path, 'a')
def reopen(sig, frm):
    global f
    f.close(); f = open(path, 'a')       # reopen BY NAME
    f.write("--- log reopened ---\n"); f.flush()
signal.signal(signal.SIGHUP, reopen)
for i in range(1000):
    f.write(f"line {i}\n"); f.flush(); time.sleep(0.5)
EOF
$ sleep 2
$ mv /tmp/logdemo/app.log /tmp/logdemo/app.log.old && touch /tmp/logdemo/app.log
$ kill -HUP $(pgrep -f 'python3 -$' | head -1)         # the postrotate step
$ sleep 2; head -2 /tmp/logdemo/app.log
--- log reopened ---
line 8

Writing resumed into the new file, with nothing lost.

6. Fix C — do not write files at all:

$ sudo systemd-run --unit=logdemo -p StandardOutput=journal \
>   /bin/sh -c 'i=0; while :; do echo "line $i"; i=$((i+1)); sleep 0.5; done'
$ journalctl -u logdemo -n 3 --no-pager

No file, no rotation, no signal, no descriptor to lose — and journald enforces retention itself. This is why the twelve-factor rule exists.

Cleanup: kill %1 2>/dev/null; sudo systemctl stop logdemo; rm -rf /tmp/logdemo.

4 (medium): Demonstrate why a timeout must not use wall-clock time.
Solution

1. Show the two clocks moving independently:

$ python3 -c "
import time
print(f'realtime : {time.time():.3f}')
print(f'monotonic: {time.monotonic():.3f}')
print(f'boottime : {time.clock_gettime(time.CLOCK_BOOTTIME):.3f}')
"
realtime : 1786455662.104
monotonic: 184203.512
boottime : 184203.512

2. Break a wall-clock timeout by stepping the clock backwards. Do this in a VM or container — never on a machine anything depends on:

$ sudo timedatectl set-ntp false
$ python3 - <<'EOF' &
import time
start_wall = time.time()
deadline   = start_wall + 10          # WRONG: wall-clock deadline
print("waiting up to 10s (wall clock)...", flush=True)
while time.time() < deadline:
    time.sleep(0.2)
print(f"finished after {time.monotonic() - mono_start:.1f}s of real elapsed time"
      if False else f"finished at {time.strftime('%T')}", flush=True)
EOF
$ sleep 2
$ sudo date -s '-5 minutes'           # NTP-style backwards step
$ # the loop now waits 5 minutes 10 seconds instead of 10 seconds

3. The monotonic version is unaffected:

$ python3 - <<'EOF' &
import time
deadline = time.monotonic() + 10      # RIGHT
t0 = time.monotonic()
while time.monotonic() < deadline:
    time.sleep(0.2)
print(f"finished after {time.monotonic()-t0:.1f}s", flush=True)
EOF
$ sleep 2; sudo date -s '-5 minutes'
$ wait
finished after 10.0s                  # exactly as intended

4. Show the forwards case too, which fails in the opposite direction:

$ python3 -c "
import time, subprocess
deadline = time.time() + 300          # a 5-minute wall-clock timeout
subprocess.run(['sudo','date','-s','+10 minutes'], capture_output=True)
print('expired immediately:', time.time() > deadline)
subprocess.run(['sudo','date','-s','-10 minutes'], capture_output=True)
"
expired immediately: True

5. Restore correct time:

$ sudo timedatectl set-ntp true
$ sleep 5; timedatectl | grep -E 'System clock|NTP'
System clock synchronized: yes
              NTP service: active

6. Confirm NTP slews rather than steps in normal operation, which is why this hazard is rare but not absent:

$ chronyc tracking | grep -E 'System time|Frequency|Skew'
System time     : 0.000241 seconds slow of NTP time
Frequency       : 12.481 ppm slow

The correction is applied as a frequency adjustment — the clock ticks slightly fast until it converges, so no timestamp is ever repeated or reversed. Steps are reserved for boot and for offsets too large to slew away, which is exactly what makestep 1.0 3 configures.

5 (hard): Correlate one request across three services with skewed clocks.
Solution

1. Emit interleaved logs from three "services" with a shared request ID:

$ for svc in frontend api worker; do
>   systemd-cat -t $svc sh -c '
>     for i in 1 2 3; do
>       echo "req=7f3a91 '"$svc"' step $i at $(date -u +%T.%3N)"
>       echo "req=aa1122 '"$svc"' unrelated traffic"
>       sleep 0.3
>     done' &
> done; wait

2. Timestamp ordering alone is not enough — the interleaving is unreadable:

$ journalctl -t frontend -t api -t worker --since '1 min ago' -o short-precise --no-pager | tail -8
09:52:01.104 host frontend[66000]: req=7f3a91 frontend step 1 at 04:22:01.104
09:52:01.106 host api[66001]:      req=aa1122 api unrelated traffic
09:52:01.108 host worker[66002]:   req=7f3a91 worker step 1 at 04:22:01.108

3. The correlation ID makes it a trace:

$ journalctl -t frontend -t api -t worker --since '1 min ago' -o short-precise --no-pager \
>   | grep 'req=7f3a91'
09:52:01.104 frontend[66000]: req=7f3a91 frontend step 1
09:52:01.108 api[66001]:      req=7f3a91 api step 1
09:52:01.112 worker[66002]:   req=7f3a91 worker step 1
09:52:01.408 frontend[66000]: req=7f3a91 frontend step 2

4. Now introduce skew and watch the ordering lie. Simulate a host 3 seconds ahead:

$ systemd-cat -t api sh -c 'echo "req=bb3344 api RESPONSE sent at $(date -u -d "+3 seconds" +%T.%3N)"'
$ systemd-cat -t frontend sh -c 'echo "req=bb3344 frontend REQUEST sent at $(date -u +%T.%3N)"'
$ journalctl -t api -t frontend --since '30 s ago' -o cat --no-pager | grep bb3344
req=bb3344 api RESPONSE sent at 04:22:07.401
req=bb3344 frontend REQUEST sent at 04:22:04.398

The response is timestamped three seconds before the request. Any conclusion drawn from this ordering is wrong.

5. Detect the skew rather than being fooled by it:

$ timedatectl | grep -E 'synchronized|NTP'
System clock synchronized: yes
$ chronyc tracking | awk '/System time/{print "offset:", $4, $6}'
offset: 0.000241 slow
$ chronyc sources -v | tail -3

In a real fleet this becomes a loop over hosts, and any host beyond ~100 ms is untrustworthy for ordering.

6. Record ordering explicitly instead of inferring it — the durable fix, since it works regardless of skew:

$ echo "MESSAGE=charge failed
PRIORITY=3
REQ_ID=7f3a91
SPAN_ID=3
PARENT_SPAN=2
SVC=worker" | systemd-cat
$ journalctl REQ_ID=7f3a91 -o json --no-pager \
>   | jq -r 'select(.SPAN_ID) | "\(.PARENT_SPAN)->\(.SPAN_ID) \(.SVC): \(.MESSAGE)"'
2->3 worker: charge failed

Parent/child span relationships encode causality directly. That is exactly what distributed tracing formalises, and it is the reason mature systems do not use wall-clock timestamps to establish what happened first.

The three rules this exercise establishes: log in UTC with sub-second precision, carry a correlation ID through every hop, and monitor clock offset per host so you know when ordering can be trusted at all.

6 (hard): Build a complete logging setup for a service: structured output, retention, and a hard size bound.
Solution

1. The service writes structured JSON to stdout — no files:

$ sudo tee /usr/local/bin/orders.py >/dev/null <<'EOF'
#!/usr/bin/env python3
import json, sys, time, random, os
def log(level, msg, **kw):
    print(json.dumps({"ts": time.strftime('%Y-%m-%dT%H:%M:%S', time.gmtime()) +
                            f".{int(time.time()%1*1000):03d}Z",
                      "level": level, "svc": "orders", "pid": os.getpid(),
                      "msg": msg, **kw}), flush=True)
log("info", "service starting", version="2.4.1")
for i in range(10000):
    rid = f"{random.getrandbits(24):06x}"
    log("info", "request received", req_id=rid, path="/orders")
    if random.random() < 0.15:
        log("error", "charge failed", req_id=rid, upstream="payments", dur_ms=2401)
    time.sleep(0.4)
EOF
$ sudo chmod +x /usr/local/bin/orders.py

2. The unit — logging config, rate limits and resource bounds together:

$ sudo tee /etc/systemd/system/orders.service >/dev/null <<'EOF'
[Unit]
Description=Orders service
After=network-online.target

[Service]
Type=simple
DynamicUser=yes
ExecStart=/usr/local/bin/orders.py
StandardOutput=journal
StandardError=journal
SyslogIdentifier=orders
LogRateLimitIntervalSec=30s
LogRateLimitBurst=20000
LogLevelMax=info
Restart=on-failure
RestartSec=5s
MemoryMax=128M

[Install]
WantedBy=multi-user.target
EOF
$ sudo systemctl daemon-reload && sudo systemctl start orders

3. Query it as structured data, not text:

$ journalctl -u orders -n 2 -o cat
{"ts":"2026-08-10T04:31:02.104Z","level":"info","svc":"orders","pid":66200,"msg":"request received","req_id":"3a91f2","path":"/orders"}

$ journalctl -u orders -o cat --since '2 min ago' | jq -r 'select(.level=="error") | "\(.ts) \(.req_id) \(.upstream) \(.dur_ms)ms"' | head -3
2026-08-10T04:31:04.912Z 8c2201 payments 2401ms
2026-08-10T04:31:09.401Z 41ba09 payments 2401ms

$ journalctl -u orders -o cat --since '5 min ago' | jq -r 'select(.level=="error") | .upstream' | sort | uniq -c
     14 payments

4. Trace one request end to end:

$ RID=$(journalctl -u orders -o cat -n 200 | jq -r 'select(.level=="error") | .req_id' | head -1)
$ journalctl -u orders -o cat --since '10 min ago' | jq -c "select(.req_id==\"$RID\")"
{"ts":"...","level":"info","msg":"request received","req_id":"8c2201","path":"/orders"}
{"ts":"...","level":"error","msg":"charge failed","req_id":"8c2201","upstream":"payments"}

5. Bound the journal so this service can never fill the disk:

$ sudo tee /etc/systemd/journald.conf.d/limits.conf >/dev/null <<'EOF'
[Journal]
Storage=persistent
SystemMaxUse=1G
SystemKeepFree=2G
MaxRetentionSec=30day
EOF
$ sudo systemctl restart systemd-journald
$ journalctl --disk-usage
Archived and active journals take up 96.0M in the file system.

6. Verify the rate limit does not silently drop entries:

$ journalctl -u orders -b | grep -ci suppressed
0
$ systemctl show orders -p LogRateLimitBurst -p LogRateLimitIntervalSec
LogRateLimitBurst=20000
LogRateLimitIntervalSec=30000000

7. Forward off-host, because everything above is still local:

$ sudo tee /etc/rsyslog.d/50-remote.conf >/dev/null <<'EOF'
module(load="imjournal" StateFile="imjournal.state")
*.* action(type="omfwd" target="logserver.internal" port="6514" protocol="tcp"
           queue.type="linkedlist" queue.filename="fwdq" queue.saveonshutdown="on"
           action.resumeRetryCount="-1")
EOF
$ sudo systemctl restart rsyslog          # disk-backed queue survives collector outages

What this setup achieves: no log files to rotate, structured fields that are queryable with jq or any collector, a correlation ID linking every line of a request, a hard bound on disk usage, explicit confirmation that nothing is being dropped, and durability beyond the host. The only remaining work is redaction of sensitive fields at emit time — which must happen in log(), before the data ever leaves the process.

Cleanup: sudo systemctl stop orders; sudo rm /etc/systemd/system/orders.service /usr/local/bin/orders.py /etc/rsyslog.d/50-remote.conf; sudo systemctl daemon-reload.

🎯 Key Takeaways

  • The journal captures service stdout/stderr, syslog and kernel messages automatically, with indexed fields — query with journalctl _PID=, _UID=, -u, not grep.
  • Without /var/log/journal/ the journal is tmpfs and every log dies at reboot; check this before you need it.
  • journalctl -b -1 is the command that matters after an unexplained reboot — the evidence is in the previous boot.
  • Syslog priorities run 0 (emerg) to 7 (debug), and -p err means "err and worse".
  • journald rate-limits by default and reports drops as one "Suppressed N messages" line — exempt a noisy unit rather than raising the global limit.
  • Renaming a log file does not affect an open descriptor, so rotation without a reopen leaves the daemon writing to app.log.1 forever.
  • postrotate + reload is the correct rotation fix; copytruncate silently loses lines written during the copy.
  • Logging to stdout removes rotation, permissions and reopen signals as a category of problem — the strongest practical reason for the twelve-factor rule.
  • CLOCK_REALTIME can jump; CLOCK_MONOTONIC cannot — every timeout, interval and latency measurement must use monotonic time.
  • NTP slews rather than steps precisely so wall-clock time never reverses; steps are reserved for boot or very large offsets.
  • Keep the RTC in UTC and set servers to UTC; local time in logs makes cross-region correlation guesswork and repeats an hour every DST change.
  • Verify clock offset per host before trusting cross-host ordering — a few seconds of skew makes effects appear before causes.
  • A correlation ID propagated through every service is what turns logs into a trace; parent/child spans record causality that timestamps can only infer.
  • Ship logs off-host with a disk-backed queue — a crashed, autoscaled-away, or compromised host takes its local logs with it.
