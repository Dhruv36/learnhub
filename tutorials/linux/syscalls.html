System Calls & strace Processes & The Kernel

What you'll master: strace as the tool that ends arguments — it shows what a program actually did rather than what anyone believes it does — including how to read its output fluently, why -c summaries point at the problem faster than full traces, the difference between a program being slow and being blocked, how to trace a program you cannot restart, why strace makes things 10–100× slower and when to reach for ltrace, perf, or eBPF instead, and the handful of syscall patterns that identify a bug on sight. Prerequisites: How Unix Is Put Together and Processes, fork & exec.

Part 1 — The Syscall Boundary, Concretely

As Lesson 1 established, a userspace program cannot touch hardware. Every interaction with the outside world — files, network, memory, other processes, time — goes through a system call. That makes the syscall stream a complete record of everything a program did that mattered.

This is why strace is uniquely powerful: it does not depend on the program's own logging, honesty, or source availability. A closed-source binary, a stripped container image, a program whose logs say "connecting..." and nothing else — all reveal themselves identically.

$ strace -e trace=openat,read,close cat /etc/hostname
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
read(3, "\177ELF\2\1\1\3\0\0\0\0\0\0\0\0\3\0>\0\1\0\0\0P\237\2\0\0\0\0\0"..., 832) = 832
close(3)                                = 0
openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3
read(3, "workstation\n", 131072)        = 12
read(3, "", 131072)                     = 0
close(3)                                = 0

Every line has the same shape, and reading it fluently is most of the skill:

    openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3
    └─┬──┘ └────────────┬───────────────────┘   └┬┘
     name           arguments                  return value
                                        (fd 3, or -1 with an errno)

    read(3, "workstation\n", 131072)    = 12
         │        │            │          └── bytes actually read
         │        │            └── buffer size requested
         │        └── the data (truncated to 32 bytes by default)
         └── the fd from the openat above

Two details make output readable immediately. A return of -1 is always followed by the errno name and message, and read returning 0 means EOF — not an error:

openat(AT_FDCWD, "/nope", O_RDONLY)     = -1 ENOENT (No such file or directory)
connect(3, {sa_family=AF_INET, sin_port=htons(443), ...}) = -1 ECONNREFUSED (Connection refused)
🔑 The errnos worth recognising on sight. ENOENT — file not found, the single most common answer to "why won't it start". EACCES — permission denied, usually a missing execute bit on a parent directory. ECONNREFUSED — nothing is listening. ETIMEDOUT — a firewall silently dropping packets rather than rejecting. EAGAIN on a non-blocking socket is normal, not a bug. EMFILE — descriptor limit reached. ENOSPC — disk full, or inodes exhausted.

Start with -c, always. A full trace of a busy process is tens of thousands of lines; the summary is twenty and usually identifies the problem outright:

$ strace -c -f ./slow-app
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 71.02    4.812043          48    100000           stat
 18.31    1.240118          12    100000           openat
  8.44    0.571902           5    100000     99998 access
  1.90    0.128744        6437        20           connect
------ ----------- ----------- --------- --------- ----------------
100.00    6.772807                 300020     99998 total

Two things jump out without reading a single trace line. 100,000 stat calls for what should be a handful of files means a cache is missing or a loop is re-checking. And 99,998 errors out of 100,000 access calls means the program is searching a long path list and failing almost every time — the classic symptom of a misconfigured library or plugin search path.

-y is an underrated quality-of-life flag, because correlating fd numbers back to paths by hand is the tedious part of reading traces:

$ strace -y -e trace=read,write ./app
read(3</etc/app/config.yaml>, "server:\n  port: 8080\n", 4096) = 21
write(1</dev/pts/2>, "starting\n", 9)   = 9
write(7<socket:[482913]>, "GET /health HTTP/1.1\r\n", 22) = 22

Part 3 — Slow vs Blocked

This distinction redirects an investigation more than any other, and strace answers it in seconds.

Symptom in straceMeaningWhere to look next
Output stops on one callBlocked — waiting on something externalThe peer, the disk, the lock
Thousands of fast calls scrollingBusy — doing too much workThe loop issuing them
No syscalls at all, high CPUPure userspace computationperf, not strace
Repeating EAGAIN loopNon-blocking poll — usually normalCheck the event loop's timeout
$ strace -p 58200
strace: Process 58200 attached
futex(0x7f8e4c0d1a40, FUTEX_WAIT_PRIVATE, 2, NULL
                                                    ← silence. Blocked here.

That silence is the finding. futex_wait means the process is waiting on a userspace lock — often a deadlock or heavy lock contention, not slow I/O. Compare with the alternatives:

Blocked in…Waiting for
futexA userspace mutex — contention or deadlock
read on a socketThe peer to send data
connectTCP handshake — firewall or dead host if it hangs
epoll_wait/pollNothing — an idle server, healthy
flock/fcntlAnother process holding a file lock
io_schedule (via read)Block device — see D state

-T attributes time to individual calls, which separates "one slow call" from "a million fast ones":

$ strace -T -e trace=network ./api-client
connect(3, {sa_family=AF_INET, sin_port=htons(443), sin_addr="93.184.216.34"}, 16) = 0 <0.041>
sendto(3, "GET /api/data HTTP/1.1\r\n"..., 128, 0, NULL, 0) = 128 <0.000034>
recvfrom(3, "HTTP/1.1 200 OK\r\n"..., 8192, 0, NULL, NULL) = 4096 <2.847291>
                                                                  ^^^^^^^^^^
                                                          2.8s waiting on the server

That single number moves the investigation off your machine entirely — the client is fine, the server is slow.

Part 4 — Patterns That Identify Bugs on Sight

A handful of syscall shapes are diagnostic. Recognising them turns strace from exploratory to decisive.

1. The failed-search pattern — many ENOENTs before success means a path list is misconfigured:

openat(AT_FDCWD, "/opt/lib/libfoo.so", O_RDONLY) = -1 ENOENT
openat(AT_FDCWD, "/usr/local/lib/libfoo.so", O_RDONLY) = -1 ENOENT
openat(AT_FDCWD, "/usr/lib/libfoo.so", O_RDONLY) = 3      ← found on the third try

Harmless once. Repeated a hundred thousand times inside a loop, it is the whole performance problem.

2. Tiny reads — unbuffered I/O, often a 100× slowdown:

read(3, "a", 1)  = 1
read(3, "b", 1)  = 1
read(3, "c", 1)  = 1                    ← one syscall per byte

3. The retry loop — an operation failing repeatedly with no backoff:

connect(3, {...}) = -1 ECONNREFUSED
connect(4, {...}) = -1 ECONNREFUSED
connect(5, {...}) = -1 ECONNREFUSED     ← and note the fd climbing: also a leak

The climbing descriptor number is a second bug hiding inside the first — failed connections are not being closed, so this will hit EMFILE eventually.

4. Descriptor exhaustion:

openat(AT_FDCWD, "/var/data/x", O_RDONLY) = -1 EMFILE (Too many open files)

5. Config read from an unexpected path — the fastest way to end a "but I edited the config" argument:

$ strace -f -e trace=openat -o /tmp/t.log ./app; grep -E '\.(conf|ya?ml|json|ini)"' /tmp/t.log
openat(AT_FDCWD, "/etc/app/config.yaml", O_RDONLY) = -1 ENOENT
openat(AT_FDCWD, "/opt/app/config.yaml", O_RDONLY) = 3      ← it reads THIS one

Part 5 — Attaching Safely, and the Cost

strace works by ptrace, which stops the target twice per syscall — once on entry, once on return. That is why it is expensive:

WorkloadTypical slowdown
Syscall-heavy (I/O loops)10–100×
Mixed2–10×
CPU-bound (few syscalls)Nearly none — and strace shows nothing useful

The practical implications on a production system are real. Attaching to a busy process can push it past timeouts and trigger the very failure you are investigating, and detaching mid-syscall can deliver EINTR to a program that handles it badly. Always filter to reduce overhead:

# Bad on production: traces everything
$ strace -f -p 2210

# Better: only what you need, time-bounded, to a file
$ timeout 10 strace -f -c -e trace=network -p 2210 -o /tmp/trace.txt

Attaching may require privileges. Many distributions set ptrace_scope=1, which restricts tracing to direct children:

$ cat /proc/sys/kernel/yama/ptrace_scope
1
$ sudo strace -p 2210               # sudo works

In containers, tracing needs CAP_SYS_PTRACE:

$ docker run --cap-add=SYS_PTRACE --security-opt seccomp=unconfined ...
$ kubectl debug -it pod/mypod --image=nicolaka/netshoot --target=app

For a process that fails at startup and exits too fast to attach to, trace it from the beginning instead — and remember -f, since the real work is often in a forked child:

$ strace -f -o /tmp/startup.log ./app --config /etc/app.conf
$ tail -30 /tmp/startup.log          # the last calls before exit tell you why

Part 6 — When strace Is the Wrong Tool

strace only sees the kernel boundary. A program that is slow purely in userspace makes no syscalls to observe, and strace will show an empty trace while the CPU sits at 100%.

QuestionTool
Which syscalls, with what arguments and errors?strace
Which library functions? (malloc, getenv)ltrace
Which userspace functions are burning CPU?perf top, perf record
System-wide, low overhead, in productionbpftrace / eBPF
What is it doing right now, zero overhead?/proc/PID/wchan, stack
Network specificstcpdump, ss

perf samples rather than intercepting, so its overhead is a few percent instead of 10–100×:

$ sudo perf top -p 2210               # live view of hot functions
$ sudo perf record -F 99 -g -p 2210 -- sleep 10 && sudo perf report

eBPF is the modern production answer — it runs a verified program inside the kernel and reports aggregates, with overhead low enough to leave running:

# Which processes are opening which files, system-wide
$ sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat {
      printf("%s -> %s\n", comm, str(args->filename)); }'

# Histogram of read() latency for one process
$ sudo bpftrace -e 'tracepoint:syscalls:sys_exit_read /pid == 2210/ {
      @bytes = hist(args->ret); }'

And for the fastest possible answer with literally zero overhead, /proc is already there — as Processes covered, wchan names the blocking function without attaching anything at all.

❌ strace -f -p $(pgrep nginx | head -1) on a production web server at peak. Every request now traps twice per syscall; latency multiplies, health checks time out, and the load balancer removes the node — you have caused an outage while investigating one.

✅ Bound and filter it, or don't use strace at all. Start with /proc/PID/wchan and -c summaries on a canary instance. If you must attach in production, use timeout 5 strace -c -e trace=network -p PID. For sustained observation, eBPF is the right tool — it was built precisely because strace is unsafe at this scale.

Interview Questions

Beginner: What does strace show you, and why is that useful?

strace intercepts and prints every system call a process makes — the arguments, the return value, and the errno on failure.

It is uniquely useful because every interaction a program has with the outside world must go through a system call. Reading a file, opening a socket, allocating memory, checking the time — all of it crosses the kernel boundary. So the syscall stream is a complete record of everything the program actually did that mattered.

That means strace works regardless of language, without source code, without debug symbols, and without cooperation from the program's own logging. A closed-source binary that logs nothing reveals exactly as much as one you wrote yourself.

The questions it answers directly: which config file did it really read, what host did it connect to, why did it fail to start (usually an ENOENT or EACCES), and is it blocked or busy. Those cover a large share of "it doesn't work and the logs don't say why".

The limitation is the same as the strength: it only sees the kernel boundary. A program burning CPU in a userspace loop makes no syscalls, so strace shows nothing while the process is pinned at 100% — that is perf's job.

Beginner: How do you find out which config file a program is actually reading?

Trace the file-opening syscalls and look at the paths:

$ strace -f -e trace=openat -o /tmp/t.log ./myapp
$ grep -E '\.(conf|ya?ml|json|ini)' /tmp/t.log
openat(AT_FDCWD, "/etc/myapp/config.yaml", O_RDONLY) = -1 ENOENT
openat(AT_FDCWD, "/opt/myapp/config.yaml", O_RDONLY) = 3

The ENOENT shows where it looked and failed; the = 3 shows what it actually opened. This is the fastest way to settle "but I edited the config file" — very often the program is reading a different copy entirely, or the packaged default rather than your edit.

Two flags make it more reliable: -f because config loading often happens in a forked child or a worker thread, and -s 200 because the default 32-byte string limit truncates long paths right where the interesting part is.

For a running process that you cannot restart, ls -l /proc/PID/fd shows what it currently has open, though that misses files it read and closed at startup. lsof -p PID gives the same information with nicer formatting.

Mid: How do you tell whether a process is slow or blocked, and why does it matter?

Attach with strace and watch the output.

Blocked looks like silence — the trace stops on a single incomplete call and nothing further appears:

$ strace -p 58200
recvfrom(7, <unfinished ...>              ← waiting on a peer

Slow but working looks like thousands of completed calls scrolling past. The process is doing too much, not waiting.

Neither — an empty trace with high CPU — means the work is entirely in userspace, and strace is the wrong tool.

The distinction matters because it redirects the investigation to a completely different place. If blocked, the fault is external: which fd, and what is on the other end? futex means lock contention or deadlock; recvfrom means a slow upstream service; io_schedule means storage. If busy, the fault is internal: strace -c shows which call dominates and whether it is a missing cache or unbuffered I/O.

The zero-overhead first step is cat /proc/PID/wchan, which names the kernel function the process is parked in without attaching anything at all. On a production system I would always check that before reaching for strace.

Mid: Why does strace slow a program down so much, and what do you use instead?

strace uses ptrace, which stops the traced process twice per system call — once on entry so strace can read the arguments, once on return for the result. Each stop is a context switch to strace, a read of the target's memory, and a switch back.

So the overhead scales with syscall rate: 10–100× for I/O-heavy programs, and essentially nothing for CPU-bound ones (where strace also shows nothing useful).

The production risk is real — attaching to a busy service can push it past health-check timeouts and cause the outage you were investigating.

The alternatives, by what you need:

  • /proc/PID/wchan — zero overhead, instantly answers "what is it blocked on". Always my first step.
  • perf — samples at a fixed frequency rather than intercepting, so overhead is a few percent. This is the tool for CPU-bound problems and userspace hot spots.
  • eBPF (bpftrace) — runs verified code in the kernel and returns aggregates rather than a line per event. Low enough overhead to leave running in production, and it can trace system-wide rather than per-process.
  • ltrace — library calls rather than syscalls, when the question is about malloc or getenv.

When I do use strace in production, I bound it: timeout 5 strace -c -e trace=network -p PID gives a summary, limits the blast radius, and filters to the subsystem in question.

Senior: An application takes 30 seconds to start, then runs fine. Diagnose it with strace.

Slow startup then normal operation points at something done once — a lookup, a lock, a scan, or a connection with a timeout. I would work from the summary inward rather than reading a 200,000-line trace.

1. Summary first, with timing:

$ strace -f -c -o /tmp/sum.txt ./app --start && head -12 /tmp/sum.txt
% time     seconds  usecs/call     calls    errors syscall
 89.21   26.740000    26740000         1           connect
  4.10    1.229000          12    102400           stat
  3.02    0.905000           8    113000    112800  openat

One connect taking 26 seconds is the answer immediately — that is a TCP connect timeout, meaning packets are being dropped rather than refused. A firewall silently discarding SYNs produces exactly this; a closed port would return ECONNREFUSED in milliseconds.

2. Confirm the target:

$ strace -f -T -e trace=connect,socket -o /tmp/net.log ./app --start
$ grep -B1 'connect' /tmp/net.log | head -4
connect(5, {sa_family=AF_INET, sin_port=htons(8125),
            sin_addr=inet_addr("10.4.2.19")}, 16) = -1 ETIMEDOUT <26.001>

Port 8125 is statsd. The application blocks on a metrics endpoint at startup, and the host is unreachable — a dependency that should have been optional and asynchronous.

3. Note the second finding. 112,800 failed openat calls out of 113,000 is a separate bug: a search path with many wrong entries, typically PYTHONPATH, NODE_PATH, or a plugin directory list. It costs about a second here but would dominate on a slower filesystem or over NFS.

4. Verify with timestamps where the wall-clock time actually goes, since the summary aggregates rather than orders:

$ strace -f -tt -o /tmp/t.log ./app --start
$ awk '{print $1}' /tmp/t.log | uniq -c | sort -rn | head -3

The fixes and their priority: make the metrics connection non-blocking with a short timeout and a background retry — a monitoring dependency must never gate startup; fix or trim the search path; and add a startup-duration metric so the regression is visible next time rather than being noticed by a human. If this ran under systemd I would also check TimeoutStartSec, because a 30-second startup is close to defaults that would eventually mark the unit failed.

Senior: How would you investigate an intermittent production issue where strace is too expensive?

The constraint is that the problem is rare, so I need sustained observation, and strace's 10–100× overhead makes sustained observation impossible on a busy service. I would layer techniques by cost.

1. Zero-cost sampling first. Poll /proc on an interval — no tracing, no overhead, and it catches the state at the moment of failure:

while sleep 5; do
  printf '%s %s %s\n' "$(date -Is)" "$(cat /proc/$PID/wchan)" \
                      "$(ls /proc/$PID/fd | wc -l)"
done >> /var/log/probe.log

A wchan that changes to futex_wait during incidents, or an fd count that climbs monotonically, identifies the class of problem without touching the process.

2. eBPF for continuous, low-overhead tracing. This is what it was built for — the kernel aggregates and only reports what matches, so a rare event costs nothing until it happens:

# Only report syscalls slower than 100ms
$ sudo bpftrace -e '
  tracepoint:syscalls:sys_enter_* /pid == '"$PID"'/ { @start[tid] = nsecs; }
  tracepoint:syscalls:sys_exit_*  /@start[tid]/ {
      $d = nsecs - @start[tid];
      if ($d > 100000000) { printf("%s %d ms\n", probe, $d/1000000); }
      delete(@start[tid]); }'

3. Conditional capture — trigger the expensive tool only when the condition appears. This is the key trick for intermittent problems:

while sleep 1; do
  if [ "$(cat /proc/$PID/wchan)" = "futex_wait" ]; then
      timeout 3 strace -f -tt -p "$PID" -o "/tmp/caught-$(date +%s).log"
      cat /proc/$PID/stack > "/tmp/stack-$(date +%s).txt"
      break
  fi
done

4. Reduce the blast radius rather than the tool cost. Route a small percentage of traffic to one canary instance and trace that heavily. Accepting 100× overhead on 1% of traffic is usually acceptable where 100× on everything is not.

5. Correlate rather than trace where possible: application metrics, ss -ti for TCP retransmits, /proc/PID/status for descriptor and thread counts, and the journal. Often the pattern — always at the top of the hour, always after N hours uptime, always on one host — identifies the cause without any tracing at all.

What I would avoid: attaching strace to all instances "just to see", and leaving it running. Both convert an intermittent degradation into a reliable outage, and the trace of the outage you caused is not the trace you needed.

🏋️ Exercises

1 (easy): Trace a simple command and account for every syscall.
Solution 
$ echo "hello world" > /tmp/greet.txt
$ strace -o /tmp/trace.log cat /tmp/greet.txt
hello world
$ wc -l /tmp/trace.log
28 /tmp/trace.log

Twenty-eight syscalls to print one line. Group them by phase:

$ awk -F'(' '{print $1}' /tmp/trace.log | sort | uniq -c | sort -rn
      6 mmap
      4 close
      3 openat
      3 fstat
      2 read
      ...

Startup — the dynamic linker:

$ grep -n 'ld.so\|libc' /tmp/trace.log | head -3
2:openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
5:openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3

Most of the trace is loading libc, not doing the work. Confirm with a static binary:

$ strace -c /bin/true 2>&1 | tail -3
$ strace -o /tmp/t2.log busybox true 2>/dev/null; wc -l /tmp/t2.log

The actual work is three calls:

$ grep -A2 'greet.txt' /tmp/trace.log
openat(AT_FDCWD, "/tmp/greet.txt", O_RDONLY) = 3
fstat(3, {st_mode=S_IFREG|0644, st_size=12, ...}) = 0
read(3, "hello world\n", 131072)        = 12

The fstat is how cat picks its buffer size — it asks the file how big it is, then reads it in one call rather than byte by byte. Note the second read returning 0: that is EOF, not an error.

2 (easy): Use strace to find why a program fails to start.
Solution 
$ cat > /tmp/needy.sh <<'EOF'
#!/usr/bin/env bash
config=$(cat /etc/needy/config.ini) || { echo "startup failed" >&2; exit 1; }
echo "running with $config"
EOF
$ chmod +x /tmp/needy.sh
$ /tmp/needy.sh
cat: /etc/needy/config.ini: No such file or directory
startup failed

Here the error is clear, but many programs report only "startup failed". Trace it to find the real cause regardless:

$ strace -f -e trace=openat -o /tmp/fail.log /tmp/needy.sh 2>/dev/null
$ grep -v ENOENT /tmp/fail.log | grep -c openat     # successful opens
14
$ grep 'needy' /tmp/fail.log
openat(AT_FDCWD, "/etc/needy/config.ini", O_RDONLY) = -1 ENOENT (No such file or directory)

The permission variant is the other common case, and it produces a different errno:

$ sudo mkdir -p /etc/needy && echo "mode=prod" | sudo tee /etc/needy/config.ini >/dev/null
$ sudo chmod 000 /etc/needy/config.ini
$ strace -e trace=openat /tmp/needy.sh 2>&1 | grep needy
openat(AT_FDCWD, "/etc/needy/config.ini", O_RDONLY) = -1 EACCES (Permission denied)

ENOENT versus EACCES distinguishes "wrong path" from "wrong permissions" instantly — and note that EACCES can also mean a missing execute bit on a parent directory, as Permissions covered, which is why namei -l is the follow-up.

$ sudo chmod 644 /etc/needy/config.ini && /tmp/needy.sh
running with mode=prod
3 (medium): Use strace -c to find a performance problem without reading the trace.
Solution

Write two versions of the same task — one unbuffered, one buffered:

$ python3 -c "open('/tmp/big.txt','w').write('x'*5000000)"

$ cat > /tmp/slow.py <<'EOF'
f = open('/tmp/big.txt', 'rb', buffering=0)      # unbuffered
n = 0
while f.read(1): n += 1
print(n)
EOF
$ cat > /tmp/fast.py <<'EOF'
f = open('/tmp/big.txt', 'rb')                    # default buffering
n = 0
while chunk := f.read(65536): n += len(chunk)
print(n)
EOF

Compare the summaries — no trace reading required:

$ strace -c -o /tmp/slow.sum python3 /tmp/slow.py >/dev/null; head -6 /tmp/slow.sum
% time     seconds  usecs/call     calls    errors syscall
 98.71   12.402113           2   5000001           read
  0.42    0.052900          12      4210           mmap

$ strace -c -o /tmp/fast.sum python3 /tmp/fast.py >/dev/null; head -6 /tmp/fast.sum
% time     seconds  usecs/call     calls    errors syscall
 41.20    0.014820         194        77           read

Five million read calls versus 77, for identical work. The summary alone identifies the bug: one syscall per byte.

Confirm the wall-clock impact:

$ time python3 /tmp/slow.py; time python3 /tmp/fast.py
5000000
real    0m3.812s
5000000
real    0m0.021s

The general reading of a -c table:

Signal in the summaryLikely cause
Huge calls for one syscallUnbuffered I/O or a missing cache
High errors countA search path failing repeatedly
Large usecs/call, few callsBlocking on something external
Many futex callsLock contention between threads
Many brk/mmapAllocation churn

This is why -c is always the first command: it turns a 5-million-line trace into six lines that name the problem.

4 (medium): Distinguish a blocked process from a busy one on a live system.
Solution

Create one of each:

# Blocked: waiting on a socket that never sends
$ nc -l 9999 >/dev/null &
$ (exec 3<>/dev/tcp/127.0.0.1/9999; read -r x <&3) & blocked=$!

# Busy: spinning on syscalls
$ (while :; do : > /tmp/spin.tmp; done) & busy=$!

Zero-overhead check first:

$ cat /proc/$blocked/wchan; echo
sk_wait_data                       # waiting on a socket
$ cat /proc/$busy/wchan; echo
0                                  # not blocked at all — it is running
$ ps -o pid,stat,cmd -p $blocked,$busy
    PID STAT CMD
  59100 S    bash
  59110 R    bash

Now confirm with strace:

$ timeout 3 strace -p $blocked 2>&1 | tail -3
strace: Process 59100 attached
read(3, <unfinished ...>
                                   # silence for 3 seconds — BLOCKED

$ timeout 1 strace -c -p $busy 2>&1 | tail -6
% time     seconds  usecs/call     calls    errors syscall
 52.10    0.140212           3     46703           openat
 47.90    0.128901           2     46703           close
                                   # ~93,000 calls in one second — BUSY

The third case — busy in userspace with no syscalls, where strace is useless:

$ (python3 -c "
while True: sum(i*i for i in range(10000))
") & cpu=$!
$ timeout 2 strace -c -p $cpu 2>&1 | tail -4
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
100.00    0.000042          21         2
$ top -bn1 -p $cpu | tail -2
  PID USER  PR NI  %CPU  COMMAND
59200 alice 20  0  99.7  python3

Two syscalls in two seconds while consuming a full core. strace has nothing to show — this needs perf top -p $cpu to find the hot function.

Cleanup: kill $blocked $busy $cpu %1 2>/dev/null; rm -f /tmp/spin.tmp.

5 (hard): Diagnose a file descriptor leak using strace and /proc.
Solution 
$ cat > /tmp/leaker.py <<'EOF'
import time, os
print("pid", os.getpid(), flush=True)
handles = []
while True:
    f = open('/etc/hostname')          # never closed
    handles.append(f)                  # kept referenced so GC cannot save us
    time.sleep(0.05)
EOF
$ ulimit -n 256; python3 /tmp/leaker.py & pid=$(pgrep -f leaker.py)
pid 59300

1. Confirm the leak by sampling the count — a monotonic climb, not a plateau:

$ for i in 1 2 3 4; do
>   printf '%s fds=%d\n' "$(date +%T)" "$(ls /proc/$pid/fd | wc -l)"; sleep 2
> done
10:14:02 fds=45
10:14:04 fds=85
10:14:06 fds=125
10:14:08 fds=165

2. Identify what is leaking:

$ ls -l /proc/$pid/fd | awk '{print $NF}' | sort | uniq -c | sort -rn | head -3
    198 /etc/hostname
      1 /dev/pts/3

198 handles on one file — unambiguous.

3. Confirm with strace that opens have no matching closes:

$ timeout 4 strace -e trace=openat,close -p $pid 2>&1 | grep -c openat
78
$ timeout 4 strace -e trace=openat,close -p $pid 2>&1 | grep -c '^close'
0                                  # opens with zero closes

4. Watch it hit the limit:

$ sleep 5; timeout 2 strace -e trace=openat -p $pid 2>&1 | tail -2
openat(AT_FDCWD, "/etc/hostname", O_RDONLY|O_CLOEXEC) = -1 EMFILE (Too many open files)
$ grep 'Max open files' /proc/$pid/limits
Max open files            256      256      files

5. Find the responsible code path — this is what makes it actionable rather than just observed:

$ sudo timeout 2 strace -k -e trace=openat -p $pid 2>&1 | grep -A6 hostname | head -8
openat(AT_FDCWD, "/etc/hostname", O_RDONLY|O_CLOEXEC) = -1 EMFILE
 > /usr/lib/libc.so.6(open64+0x5b)
 > /usr/lib/libpython3.11.so(_io_open+0x2f1)
 > /tmp/leaker.py(<module>+0x18)

The distinction that determines the fix: a count that climbs monotonically is a leak and the fix is in the code — use scoping (with, defer, try-with-resources) so descriptors close on every path including exceptions. A count that plateaus just under the limit under load is under-provisioning, and the fix is LimitNOFILE= in the systemd unit. Raising the limit on a genuine leak only delays the failure.

Also worth checking with sockets: ss -tan state close-wait | wc -l. CLOSE_WAIT means the peer closed and the application never called close() — unambiguously an application bug.

Cleanup: kill $pid.

6 (hard): Build a low-overhead production diagnostic that captures an intermittent problem.
Solution

The requirement: catch a rare stall without leaving strace attached to a busy process.

Layer 1 — zero-overhead continuous sampling. Poll /proc; nothing is attached, so this can run indefinitely:

$ cat > /tmp/probe.sh <<'EOF'
#!/usr/bin/env bash
pid=$1; out=${2:-/tmp/probe.log}
while kill -0 "$pid" 2>/dev/null; do
    printf '%s\t%s\t%s\t%s\t%s\n' \
        "$(date -Is)" \
        "$(awk '/^State/{print $2}' /proc/$pid/status)" \
        "$(cat /proc/$pid/wchan 2>/dev/null || echo -)" \
        "$(ls /proc/$pid/fd 2>/dev/null | wc -l)" \
        "$(awk '/^Threads/{print $2}' /proc/$pid/status)"
    sleep 2
done >> "$out"
EOF
$ chmod +x /tmp/probe.sh

Layer 2 — conditional capture. Only pay strace's cost when the anomaly appears:

$ cat > /tmp/watch.sh <<'EOF'
#!/usr/bin/env bash
pid=$1
threshold_fds=1000
while kill -0 "$pid" 2>/dev/null; do
    w=$(cat /proc/$pid/wchan 2>/dev/null)
    n=$(ls /proc/$pid/fd 2>/dev/null | wc -l)
    if [[ $w == futex_wait || $w == *lock* || $n -gt $threshold_fds ]]; then
        ts=$(date +%s)
        echo "ANOMALY at $ts: wchan=$w fds=$n" >&2
        # bounded, filtered capture — never open-ended
        timeout 5 strace -f -tt -T -p "$pid" -o "/tmp/capture-$ts.log" 2>/dev/null
        cat /proc/$pid/stack   > "/tmp/kstack-$ts.txt" 2>/dev/null
        ls -l /proc/$pid/fd    > "/tmp/fds-$ts.txt"    2>/dev/null
        cat /proc/$pid/status  > "/tmp/status-$ts.txt"
        break
    fi
    sleep 1
done
EOF
$ chmod +x /tmp/watch.sh

Test it against a process that stalls after a delay:

$ cat > /tmp/staller.py <<'EOF'
import threading, time, os
print("pid", os.getpid(), flush=True)
lock = threading.Lock()
def holder(): lock.acquire(); time.sleep(300)
time.sleep(5)                        # normal for 5s
threading.Thread(target=holder, daemon=True).start()
time.sleep(0.5)
lock.acquire()                       # deadlock
EOF
$ python3 /tmp/staller.py & sleep 1; pid=$(pgrep -f staller.py)
$ /tmp/watch.sh "$pid"
ANOMALY at 1786312455: wchan=futex_wait fds=4
$ head -3 /tmp/capture-1786312455.log
10:31:02.114 futex(0x7f2c8c0016d0, FUTEX_WAIT_PRIVATE, 0, NULL <unfinished ...>

The capture triggered exactly at the stall, ran for five bounded seconds, and produced the evidence — futex_wait with no progress, which is a lock problem, not I/O.

Layer 3 — eBPF for continuous low-overhead tracing where even conditional strace is too risky:

$ sudo bpftrace -e '
  tracepoint:syscalls:sys_enter_futex /pid == '"$pid"'/ { @waits = count(); }
  interval:s:10 { print(@waits); clear(@waits); }'

The design principles: never attach anything continuously to a busy process; make the cheap check the always-on layer and the expensive one conditional; always bound the expensive capture with timeout; capture context (fds, stack, status) alongside the trace, since the trace alone often lacks the deciding detail; and prefer reducing blast radius — trace one canary instance heavily rather than every instance lightly.

Cleanup: kill $pid; rm -f /tmp/capture-* /tmp/kstack-* /tmp/fds-* /tmp/status-*.

🎯 Key Takeaways

  • Every interaction with the outside world crosses the syscall boundary, so the syscall stream is a complete record of what a program actually did — no source, symbols, or cooperative logging required.
  • Read a trace line as name(args) = return; -1 is always followed by the errno, and read() = 0 is EOF, not an error.
  • ENOENT, EACCES, ECONNREFUSED, ETIMEDOUT, and EMFILE cover most startup and connectivity failures.
  • Always start with strace -c -f — the summary turns a million-line trace into twenty lines that name the problem.
  • -f is near-mandatory, because the interesting work is usually in a forked child or another thread.
  • Silence in a trace means blocked; scrolling output means busy; an empty trace with high CPU means the work is in userspace and strace is the wrong tool.
  • The blocking call names the culprit: futex = lock contention, recvfrom = slow peer, io_schedule = storage, epoll_wait = healthy idle.
  • Diagnostic patterns: many ENOENTs = misconfigured search path; one-byte reads = unbuffered I/O; climbing fd numbers with failures = a leak inside a retry loop.
  • strace costs 10–100× on syscall-heavy programs because ptrace stops the process twice per call — filter with -e and bound with timeout in production.
  • Tracing needs privileges: ptrace_scope on hosts, CAP_SYS_PTRACE in containers.
  • -y annotates fds with their paths and removes most of the tedium of reading traces.
  • Choose the tool by the question: /proc/PID/wchan for zero-cost "what is it waiting on", perf for userspace CPU, ltrace for library calls, eBPF for sustained production tracing.
  • For intermittent problems, make the cheap probe always-on and trigger the expensive capture conditionally — never leave strace attached to a busy service.
