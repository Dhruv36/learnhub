Finding Files: find & xargs The Shell

What you'll master: find as an expression evaluator rather than a search command — once you see that every argument is a test returning true or false, the ordering rules and the -print surprises become obvious — why -name must be quoted, the difference between -exec \; and -exec + that changes a command from thousands of forks to one, why NUL separation is the only safe way to pass filenames between programs, how to prune whole directory trees efficiently, and when xargs -P turns a serial job into a parallel one safely. Prerequisites: Text Processing and Users, Groups & Permissions.

Part 1 — find Is an Expression Evaluator

Most people learn find as a collection of magic flags. It is actually much simpler than that: find walks a directory tree and, for each file, evaluates a boolean expression you supply. Every argument after the starting path is either a test (returns true/false), an action (does something, and also returns true/false), or an operator joining them.

      find  /var/log   -type f  -name '*.log'  -mtime +7   -delete
            └────┬───┘ └───────────────┬──────────────┘   └──┬──┘
              where            tests (ANDed implicitly)     action

Adjacent tests are joined with an implicit AND, and evaluation short-circuits left to right exactly like && in a shell. That single fact has a real performance consequence: put the cheap tests first.

# Slow: runs a stat() for size on every file, then filters by name
$ find /data -size +100M -name '*.log'

# Fast: the name test is a string comparison; only survivors get stat()ed
$ find /data -name '*.log' -size +100M

The operators are worth knowing because they let you express real conditions:

OperatorMeaningNote
expr1 expr2AND (implicit)The default when you list tests
-aAND (explicit)Rarely needed
-oORNeeds parentheses — see below
! or -notNOTEscape as \! in some shells
\( ... \)GroupingParentheses must be escaped from the shell

The precedence trap with -o is the most common find bug, and it is silent:

# WRONG: AND binds tighter than OR, so this reads as
#   (-name '*.log' -mtime +7) OR (-name '*.tmp')
# ...which deletes every .tmp file regardless of age
$ find /data -name '*.log' -o -name '*.tmp' -mtime +7 -delete

# CORRECT: group the alternatives
$ find /data \( -name '*.log' -o -name '*.tmp' \) -mtime +7 -delete

Because actions also return values, this composes further than expected — -print returns true, which is why you can chain conditional actions:

# Print small files, delete large ones, in a single pass
$ find /data -type f \( -size -1M -print -o -size +1G -delete \)
🔑 The -print surprise. find adds an implicit -print only if you supply no action of your own. The moment you use -delete, -exec, or an explicit -print, the implicit one disappears. Combined with -o, this produces the classic confusion where half your results vanish: find . -name a -o -name b prints only the b matches, because the implicit -print attaches to the last term only. Write find . \( -name a -o -name b \) -print and the ambiguity disappears.

Part 3 — -exec \; vs -exec +

Two terminators for -exec, and the difference is enormous.

      -exec cmd {} \;      → run cmd ONCE PER FILE
      -exec cmd {} +       → batch as many files as fit per invocation

$ mkdir -p /tmp/many && cd /tmp/many && touch file{1..5000}.txt

$ time find . -name '*.txt' -exec echo {} \; >/dev/null
real    0m4.812s              # 5000 forks + execs

$ time find . -name '*.txt' -exec echo {} + >/dev/null
real    0m0.031s              # 2 invocations

Over 150× faster, doing identical work. The + form builds an argument list up to the system limit (ARG_MAX, typically ~2 MB) and then invokes the command, repeating as needed.

Use + whenUse \; when
The command accepts multiple file argumentsThe command takes exactly one file
rm, grep, chmod, tarAnything using {} more than once
Performance matters (it usually does)You need per-file shell logic
{} is the last argument{} must appear mid-command

+ requires {} to be the final argument, so commands like mv that need a trailing destination cannot use it directly — -exec mv {} /dest \; works, or better, xargs -0 -I{} mv {} /dest or GNU mv -t:

$ find . -name '*.log' -exec mv -t /archive/ {} +      # -t puts the target first

When you genuinely need shell logic per file, invoke a shell explicitly — and pass the filenames as arguments, never by interpolating them into the command string:

# WRONG: filename is substituted into shell source — injection and space bugs
$ find . -name '*.txt' -exec sh -c 'echo "processing {}"' \;

# CORRECT: filenames arrive as "$@", parsed by nothing
$ find . -name '*.txt' -exec sh -c '
    for f do
      printf "processing %s\n" "$f"
    done' sh {} +

The trailing sh sets $0 so the first real filename lands in $1. This is the safe idiom for per-file shell work at scale.

Part 4 — Why NUL Separation Exists

Filenames on Linux may contain any byte except / and NUL. That includes spaces, newlines, quotes, and leading dashes. Every text-based pipeline that separates filenames by whitespace is therefore broken for some input — usually input an attacker or a careless user controls.

$ mkdir -p /tmp/nasty && cd /tmp/nasty
$ touch 'normal.txt' 'with space.txt' && touch $'with\nnewline.txt'

$ find . -name '*.txt' | wc -l
4                              # WRONG: 3 files, but one contains a newline

$ find . -name '*.txt' -print0 | tr -dc '\0' | wc -c
3                              # correct count

NUL is the only byte guaranteed never to appear in a filename, which is exactly why it is the safe separator. The paired flags are -print0 on the producer and -0 on the consumer:

$ find . -name '*.txt' -print0 | xargs -0 ls -l
ToolNUL flag
find-print0
xargs-0
grep-z (input), -Z (filenames out)
sort-z
read (bash)-d ''
sed-z

The bash loop that reads NUL-separated names safely is worth memorising, since it is the correct replacement for for f in $(find ...):

while IFS= read -r -d '' file; do
    printf 'processing: %s\n' "$file"
done < <(find . -name '*.txt' -print0)

Each piece matters: IFS= stops leading/trailing whitespace being stripped, -r stops backslash interpretation, -d '' sets NUL as the delimiter, and < <(...) avoids the subshell that a pipe would create — the lost-variable problem from The Shell Executes a Line.

❌ for f in $(find . -name '*.txt'); do rm $f; done — the command substitution is word-split on whitespace, so with space.txt becomes two nonexistent names; the unquoted $f is then glob-expanded again; and a file named -rf becomes an option to rm. Three independent failures in one line.

✅ find . -name '*.txt' -exec rm -- {} + — no shell parsing of filenames at any point, batched for speed, and -- guards against leading dashes. If you need a loop, use the read -d '' form above.

Part 5 — xargs: Batching, Placement and Parallelism

xargs reads items from stdin and builds command lines from them. Its default behaviour is dangerous and its useful behaviour is one flag away.

$ printf 'a\nb\nc\n' | xargs echo
a b c                          # all three as arguments to ONE echo
FlagEffect
-0NUL-separated input — use this always with filenames
-n NAt most N arguments per invocation
-I {}Replace {} with the item; implies -n 1
-P NRun up to N invocations in parallel
-rDo not run at all if input is empty (GNU)
-tPrint each command before running it
-pPrompt before each command

-r prevents a genuinely nasty failure mode. Without it, empty input still runs the command once with no arguments:

$ printf '' | xargs ls
                               # ran 'ls' with no args — listed the CURRENT directory!
$ printf '' | xargs -r ls
                               # nothing, correctly

With rm or chmod in place of ls, that difference is the gap between "nothing happened" and an incident. GNU find's -exec + does not have this problem — it simply does not run when there are no matches.

-I {} lets you place the argument anywhere, which -exec + cannot do:

$ find . -name '*.log' -print0 | xargs -0 -I{} mv {} /archive/
$ find . -name '*.conf' -print0 | xargs -0 -I{} cp {} {}.bak

Note that -I forces one invocation per item, losing the batching speedup. When both matter, use -P to recover throughput through concurrency instead.

Parallelism is xargs's most underused feature. For CPU- or network-bound per-file work, -P turns a serial loop into a pool:

# Serial: one image at a time
$ find . -name '*.png' -print0 | xargs -0 -I{} optipng {}

# Parallel across all cores
$ find . -name '*.png' -print0 | xargs -0 -P "$(nproc)" -I{} optipng {}

The caveat is output interleaving: parallel processes writing to the same stdout can produce mixed lines. Writes under PIPE_BUF (4096 bytes) are atomic, as Redirection & Pipes established, so short lines survive — but anything longer can interleave. For jobs with substantial output, write to per-job files, or use GNU parallel, which buffers each job's output and emits it whole.

Part 6 — Pruning, and Not Walking What You Don't Need

On a large tree, most of find's time goes into directories you never wanted. -prune stops descent, and the idiom is worth learning exactly because the obvious formulation is wrong.

# Skip .git and node_modules entirely — never descend into them
$ find . \( -name .git -o -name node_modules \) -prune -o -type f -name '*.js' -print

Read it as an expression: if the name matches, -prune returns true and short-circuits the AND, so find does not descend and (crucially) the -print after -o is never reached for that directory. Otherwise the right-hand side runs. The trailing explicit -print is mandatory — without it, the implicit print would apply to the pruned directories too.

The performance difference on a real repository is not subtle:

$ time find . -type f -name '*.js' | wc -l
44219
real    0m8.921s

$ time find . -name node_modules -prune -o -type f -name '*.js' -print | wc -l
812
real    0m0.214s

Other ways to limit the walk:

OptionEffect
-maxdepth 1Current directory only — must appear before other tests
-mindepth 1Exclude the starting directory itself
-xdevDo not cross filesystem boundaries — essential when /proc or NFS is below
-quitStop after the first match

-xdev deserves emphasis. A find / without it will descend into /proc, /sys, network mounts, and container overlay filesystems — producing spurious results, enormous runtimes, and occasionally hanging on an unresponsive NFS server:

$ find / -xdev -type f -size +1G 2>/dev/null      # only the root filesystem

For plain name lookups on a system with mlocate installed, the indexed database answers in milliseconds what find takes minutes to do — at the cost of being as stale as the last updatedb run:

$ locate -b '\config.yaml'

Interview Questions

Beginner: Why must you quote the pattern in find . -name '*.log'?

Because globbing is done by the shell, not by find. Unquoted, bash expands *.log against the current directory before find is ever invoked.

What happens then depends on what is in the cwd, which makes the bug intermittent:

  • No match — bash passes the literal *.log through, and find works correctly by accident.
  • One match, say app.log — find receives -name app.log and silently searches for only that name, missing everything in subdirectories. No error.
  • Two or more matches — find receives extra arguments and fails with "paths must precede expression".

The middle case is the dangerous one: plausible output, incomplete results, no warning. Quoting sends the asterisk to find, which then matches it against every basename it encounters during the walk.

The same principle applies to any tool that does its own matching — grep, rsync --exclude, tar --wildcards. The question to ask is always "which program should perform this expansion?"

Beginner: What is the difference between -exec cmd {} \; and -exec cmd {} +?

\; runs the command once per file. + batches as many filenames as fit into each command line and runs it far fewer times.

The performance difference is dramatic because each invocation is a fork plus an exec. On 5000 files, \; takes seconds while + takes milliseconds — roughly 150× in a simple measurement.

Use + whenever the command accepts multiple file arguments — rm, grep, chmod, chown, tar. That is most of the time.

Use \; when the command takes exactly one file, when {} must appear somewhere other than the end, or when you need per-file logic. + requires {} to be the last argument, which is why -exec mv {} /dest + is invalid — use GNU mv -t /dest {} + instead.

One more difference worth knowing: with no matches, -exec + does not run the command at all, whereas a bare xargs without -r would run it once with no arguments — which is how people accidentally operate on their current directory.

Mid: Why is -print0/-0 necessary, and when does it actually matter?

Because a Linux filename may contain any byte except / and NUL — including spaces, newlines, tabs, and quotes. Any pipeline that separates filenames by whitespace or newlines is therefore ambiguous for some inputs.

$ touch $'weird\nname.txt'
$ find . -name '*.txt' | wc -l
2                          # one file, counted as two lines

NUL is the only byte that cannot appear in a filename, which makes it the unambiguous separator. -print0 emits it; xargs -0, grep -z, sort -z and bash's read -d '' consume it.

When it matters in practice: anywhere filenames come from users or external systems — upload directories, media libraries, anything synced from macOS or Windows where spaces are the norm. The classic failure is a cleanup script that appears to work for months and then deletes the wrong thing, or fails silently, when a file with a space appears.

The most robust answer is usually to avoid the text pipeline altogether: -exec cmd {} + passes filenames directly as arguments with no serialisation step, so there is nothing to mis-parse. Reach for -print0 | xargs -0 when you need xargs-specific features like -P for parallelism or -I{} for argument placement.

Mid: Explain the -prune idiom and why the trailing -print is required.

-prune tells find not to descend into a directory. It is an action that returns true, so it composes with the boolean operators like anything else.

$ find . -name node_modules -prune -o -type f -name '*.js' -print

Read it as an expression: for each entry, if the name is node_modules, then -prune runs (returning true), the AND is satisfied, and evaluation short-circuits — find does not descend, and the right-hand side of -o is never evaluated. Otherwise the left side is false, so -o evaluates the right side, which tests and prints.

The trailing -print is required because find only supplies an implicit -print when you give it no action of your own — and -prune is an action. If you leave it out, find falls back to printing everything the whole expression matched, which now includes the pruned directory names themselves. You would see ./node_modules in your results, which is exactly what you were trying to exclude.

The payoff is large. On a JavaScript project, pruning node_modules took a search from 8.9 seconds to 0.2 seconds in my measurement, because find was no longer walking tens of thousands of irrelevant files. The related option is -xdev, which stops find crossing into other filesystems — essential for find / so it does not wander into /proc or hang on an unresponsive NFS mount.

Senior: Design a safe log-cleanup job. What could go wrong and how do you prevent it?

Cleanup jobs are dangerous because they run unattended, have no undo, and the failure is usually silent until someone needs the deleted data. I'd design against each failure mode explicitly.

The naive version, and everything wrong with it:

find $LOGDIR -name "*.log" -mtime +30 -delete
  • $LOGDIR unquoted and possibly unset — under set -u it aborts, but without it, an empty value makes this find -name ... -delete starting from the current directory.
  • No -type f, so it can delete directories and symlinks.
  • No -xdev, so it crosses into other mounts.
  • No check that the target directory exists — a typo'd path silently matches nothing, and the job reports success forever while disk fills.
  • Follows symlinks out of the intended tree in some configurations.

The version I would actually deploy:

#!/usr/bin/env bash
set -euo pipefail

LOGDIR=/var/log/myapp
RETAIN_DAYS=30
MIN_EXPECTED=1          # sanity floor: refuse to run on an empty/wrong tree

[[ -d $LOGDIR ]] || { echo "missing: $LOGDIR" >&2; exit 1; }
mountpoint -q /var/log || true    # informational

# Count first — never delete blind
count=$(find "$LOGDIR" -xdev -type f -name '*.log' \
             -mtime "+$RETAIN_DAYS" -print | wc -l)

if (( count == 0 )); then
    echo "nothing to clean"; exit 0
fi
if (( count > 10000 )); then
    echo "refusing: $count files exceeds safety limit" >&2; exit 1
fi

echo "deleting $count files older than $RETAIN_DAYS days"
find "$LOGDIR" -xdev -type f -name '*.log' -mtime "+$RETAIN_DAYS" -delete

The specific defences: quoting and set -u stop an unset path expanding to nothing; -type f confines it to regular files; -xdev stops it crossing mounts; the existence check catches typos; and the upper bound turns "my expression is wrong" from a disaster into a failed job. That last one is the most valuable — a cleanup job that suddenly matches 200,000 files is a bug, not a busy week.

What I would prefer over all of it: logrotate or systemd's journald retention settings. Both already handle rotation, compression, retention by size and age, and signalling the writing process to reopen its files — which a find -delete does not, leaving the classic deleted-but-open situation from Files, Inodes & Links where space is never reclaimed. Writing a custom cleanup job is usually a sign that the platform's own mechanism was not configured.

Senior: How would you parallelise a per-file operation across a large tree, and what are the risks?

xargs -P is the low-ceremony answer, and it works well when the operation is independent per file:

$ find . -name '*.png' -print0 | xargs -0 -P "$(nproc)" -n 20 optipng

-P sets concurrency, -n controls batch size per invocation. Both matter: -I{} would force one file per process, so for cheap operations the fork overhead dominates and parallelism buys nothing.

Choosing the degree of parallelism depends on what the work is bound by. For CPU-bound work, nproc is right and going higher just adds context switching. For I/O-bound work on spinning disks, high concurrency makes it slower by converting sequential reads into random seeks. For network-bound work, concurrency far above core count is fine and usually necessary.

The risks, in the order they bite:

  • Output interleaving. Parallel writers to one stdout produce mixed lines. Writes under 4096 bytes are atomic so short lines survive, but anything longer corrupts. Write per-job output files, or use GNU parallel, which buffers each job and emits it whole.
  • Partial failure is invisible. xargs returns 123 if any invocation failed but does not tell you which. For anything important, have each job log its own status and reconcile afterwards.
  • Resource exhaustion. N concurrent processes multiply memory and file descriptors. A job that uses 500 MB is fine serially and an OOM kill at 32× concurrency.
  • Shared-state races. If the operation writes to a common output file or database, parallelism introduces corruption that does not exist serially. This is the one that produces genuinely confusing bugs.
  • Non-idempotency. An interrupted parallel run leaves a partially-processed tree. The operation should be safe to re-run.

My practice: start serial, confirm correctness, then add -P and measure — parallelism that is not measured is often slower. For anything beyond a one-off, GNU parallel earns its keep with --joblog (resumable, tells you exactly what failed), --retries, and clean output handling. And for very large trees I would question the shape entirely: if this runs regularly, the right fix is usually to process files as they arrive rather than rescanning millions of them on a schedule.

🏋️ Exercises

1 (easy): Demonstrate the -o precedence trap safely.
Solution 
$ mkdir -p /tmp/prec && cd /tmp/prec
$ touch old.log new.log old.tmp new.tmp
$ touch -d '30 days ago' old.log old.tmp        # make two of them old

The wrong expression — use -print instead of -delete to see what it would have done:

$ find . -name '*.log' -o -name '*.tmp' -mtime +7 -print
./old.tmp

Only one result, and not the one you wanted. It parsed as (-name '*.log') OR (-name '*.tmp' AND -mtime +7 AND -print): the .log branch matched but had no action attached, so nothing printed for it, while the .tmp branch printed only the old one.

Had this been -delete, the behaviour would differ again — worth seeing why this is genuinely dangerous rather than merely confusing.

The correct expression:

$ find . \( -name '*.log' -o -name '*.tmp' \) -mtime +7 -print
./old.log
./old.tmp

Both old files, neither new one. The parentheses group the alternatives so the age test and the action apply to both.

Confirm the implicit-print rule that caused the first surprise:

$ find . -name '*.log' -o -name '*.tmp'
./old.log
./new.log
./old.tmp
./new.tmp                     # no action given → implicit -print applies to everything

$ find . -name '*.log' -o -name '*.tmp' -print
./old.tmp
./new.tmp                     # explicit -print attaches to the LAST term only

The rule: the moment you supply any action, the implicit -print disappears. Always group with \( \) and add an explicit -print when using -o.

3 (medium): Show how whitespace in filenames breaks naive pipelines, and fix it three ways.
Solution 
$ mkdir -p /tmp/ws && cd /tmp/ws
$ touch 'normal.txt' 'with space.txt' 'two  spaces.txt' $'new\nline.txt' -- '-dash.txt'
$ ls -b
-dash.txt  new\nline.txt  normal.txt  two\ \ spaces.txt  with\ space.txt

The naive loop fails in three distinct ways:

$ for f in $(find . -name '*.txt'); do echo "[$f]"; done
[./normal.txt]
[./with]                       # split on the space
[space.txt]
[./two]                        # split, and the double space collapsed
[spaces.txt]
[./new]                        # split on the newline
[line.txt]
[./-dash.txt]

Five files became seven items, and none of the multi-word ones exist under those names.

Fix 1 — -exec +, no serialisation at all:

$ find . -name '*.txt' -exec ls -b -- {} +
-dash.txt  new\nline.txt  normal.txt  two\ \ spaces.txt  with\ space.txt

Fix 2 — NUL-separated pipeline:

$ find . -name '*.txt' -print0 | xargs -0 -I{} sh -c 'printf "[%s]\n" "$1"' sh {}
[./normal.txt]
[./with space.txt]
[./two  spaces.txt]
[./new
line.txt]
[./-dash.txt]                  # five items, correctly

Fix 3 — a bash loop reading NUL, when you need shell state:

$ count=0
$ while IFS= read -r -d '' f; do
>     count=$((count + 1))
>     printf '%d: [%s]\n' "$count" "$f"
> done < <(find . -name '*.txt' -print0)
1: [./normal.txt]
2: [./with space.txt]
3: [./two  spaces.txt]
4: [./new
line.txt]
5: [./-dash.txt]
$ echo "total=$count"
total=5                        # variable survived: no subshell

Every element of that loop earns its place: IFS= preserves leading/trailing whitespace, -r stops backslash mangling, -d '' reads to NUL, and < <(...) avoids the pipeline subshell that would discard count.

4 (medium): Use -prune to speed up a search, and measure it.
Solution

Build a tree resembling a real project:

$ mkdir -p /tmp/proj/{src,test,.git/objects,node_modules/pkg{1..50}/dist}
$ for i in $(seq 1 200); do touch "/tmp/proj/src/mod$i.js"; done
$ for d in /tmp/proj/node_modules/pkg*/dist; do
>     for i in $(seq 1 200); do touch "$d/bundle$i.js"; done
> done
$ find /tmp/proj -type f -name '*.js' | wc -l
20200

Without pruning — walks everything:

$ time find /tmp/proj -type f -name '*.js' -not -path '*/node_modules/*' | wc -l
200
real    0m0.412s

Note this gives the right answer but is slow: -not -path filters results after descending into every directory. find still stat'ed 20,000 files.

With pruning — never descends:

$ time find /tmp/proj \( -name node_modules -o -name .git \) -prune \
>      -o -type f -name '*.js' -print | wc -l
200
real    0m0.019s

Same answer, ~20× faster, and the gap widens with tree size because the work avoided is proportional to what was pruned.

Prove it is not descending by counting directories visited:

$ find /tmp/proj -type d | wc -l
104
$ find /tmp/proj -name node_modules -prune -o -type d -print | wc -l
5                              # only src, test, .git and its child, plus the root

The trailing -print is mandatory. Omitting it produces the pruned directories in the output, which is the opposite of the intent:

$ find /tmp/proj -name node_modules -prune -o -type f -name '*.js' | head -2
/tmp/proj/node_modules         # the pruned directory itself got printed
/tmp/proj/src/mod1.js

Cleanup: rm -rf /tmp/proj.

5 (hard): Parallelise a per-file operation with xargs -P and handle the failure modes.
Solution

Create work with a deliberate failure in it:

$ mkdir -p /tmp/par && cd /tmp/par
$ for i in $(seq 1 40); do echo "data $i" > "file$i.txt"; done
$ chmod 000 file17.txt                     # will fail to read

$ cat > /tmp/process.sh <<'EOF'
#!/usr/bin/env bash
f=$1
sleep 0.2                                   # simulate work
if ! content=$(cat -- "$f" 2>/dev/null); then
    printf 'FAIL %s\n' "$f" >&2
    exit 1
fi
printf 'OK %s (%d bytes)\n' "$f" "${#content}"
EOF
$ chmod +x /tmp/process.sh

Serial baseline:

$ time find . -name '*.txt' -print0 | xargs -0 -n1 /tmp/process.sh >/tmp/out.log 2>/tmp/err.log
real    0m8.214s
$ echo "status=$?"; wc -l < /tmp/err.log
status=123
1

Exit 123 is xargs's signal that at least one invocation failed — but it does not say which, which is why per-job logging matters.

Parallel:

$ time find . -name '*.txt' -print0 \
>   | xargs -0 -P 8 -n1 /tmp/process.sh >/tmp/out.log 2>/tmp/err.log
real    0m1.093s               # ~8x, as expected for sleep-bound work
$ grep -c '^OK' /tmp/out.log; cat /tmp/err.log
39
FAIL ./file17.txt

Demonstrate the output-interleaving risk — the failure mode people miss:

$ cat > /tmp/noisy.sh <<'EOF'
#!/usr/bin/env bash
# Emit a long line in pieces — simulates a program with unbuffered chunked output
printf '%s' "START-$1-"; sleep 0.01; printf '%s\n' "$(head -c 5000 /dev/zero | tr '\0' 'x')END"
EOF
$ chmod +x /tmp/noisy.sh
$ find . -name '*.txt' -print0 | xargs -0 -P 8 -n1 /tmp/noisy.sh > /tmp/noisy.log
$ grep -c 'START.*END' /tmp/noisy.log
31                             # not 40 — nine lines were corrupted by interleaving

Writes above PIPE_BUF (4096 bytes) are not atomic, so concurrent writers split each other's lines.

The robust version — per-job output files, then reconcile:

$ cat > /tmp/safe.sh <<'EOF'
#!/usr/bin/env bash
f=$1; out=/tmp/par-results/$(echo "$f" | md5sum | cut -c1-8)
{ if content=$(cat -- "$f" 2>/dev/null)
  then printf 'OK\t%s\t%d\n' "$f" "${#content}"
  else printf 'FAIL\t%s\t-\n' "$f"
  fi
} > "$out"
EOF
$ chmod +x /tmp/safe.sh && mkdir -p /tmp/par-results
$ find . -name '*.txt' -print0 | xargs -0 -P 8 -n1 /tmp/safe.sh
$ cat /tmp/par-results/* | sort | awk -F'\t' '{c[$1]++} END {for (s in c) print s, c[s]}'
FAIL 1
OK 39

No interleaving is possible, and every job's outcome is individually recoverable. GNU parallel --joblog does this for you and additionally supports resuming a partial run — worth the dependency for anything recurring.

Choosing -P: this workload was sleep-bound, so 8× concurrency gave 8× throughput. CPU-bound work should use nproc; disk-bound work on spinning media is often slower in parallel because sequential reads become random seeks. Measure rather than assume.

Cleanup: chmod 644 file17.txt; rm -rf /tmp/par /tmp/par-results.

6 (hard): Build a disk-usage investigation toolkit for a full filesystem.
Solution

The scenario: a filesystem is at 95% and you need to find why, fast, without hanging on network mounts or wandering into /proc.

1. Establish which filesystem, and rule out inode exhaustion first — it is instant and presents identically to a full disk:

$ df -h / /var /home
$ df -i / /var /home
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/nvme0n1p3 3276800 412093 2864707   13% /

2. Largest files on this filesystem only — -xdev is what makes this safe and fast:

$ find / -xdev -type f -size +500M -printf '%s\t%p\n' 2>/dev/null \
>   | sort -rn | head -10 | awk -F'\t' '{printf "%8.1f GB  %s\n", $1/1073741824, $2}'
    12.4 GB  /var/lib/docker/overlay2/a3f.../diff/data.bin
     8.1 GB  /var/log/app/debug.log

-printf '%s\t%p\n' avoids a second stat pass that -exec du would cost.

3. Largest directories, when the problem is many small files rather than a few big ones:

$ du -xh --max-depth=2 / 2>/dev/null | sort -rh | head -15

-x is du's equivalent of -xdev. Without it you measure network mounts and container layers.

4. Recently grown files — this is what identifies the cause rather than merely the largest historical file:

$ find / -xdev -type f -newermt '24 hours ago' -size +100M \
>      -printf '%TY-%Tm-%Td %TH:%TM  %10s  %p\n' 2>/dev/null | sort -rn -k3 | head
2026-08-09 03:14   4294967296  /var/log/app/debug.log

A 4 GB file written in the last day is almost certainly the reason the disk filled today.

5. The invisible cases that du cannot see. This is where most "df and du disagree" incidents live, and both were covered in Files, Inodes & Links:

# Deleted but still held open — space is allocated with no directory entry
$ sudo lsof +L1 2>/dev/null | awk 'NR==1 || $5=="REG"' | head
COMMAND  PID USER FD TYPE DEVICE SIZE/OFF NLINK NODE NAME
app     2210 www   5w  REG  259,3 8421990400   0  512 /var/log/app/old.log (deleted)

# Files hidden underneath a mount point
$ sudo mount --bind / /mnt/rootview
$ du -xsh /mnt/rootview/var/lib/app
14G     /mnt/rootview/var/lib/app
$ sudo umount /mnt/rootview

6. Count files per directory when inodes rather than blocks are exhausted:

$ find / -xdev -type d -printf '%p\0' 2>/dev/null \
>   | xargs -0 -P 4 -I{} sh -c 'printf "%d %s\n" "$(ls -A "$1" 2>/dev/null | wc -l)" "$1"' sh {} \
>   | sort -rn | head -5
482193 /var/spool/postfix/maildrop

Half a million files in a mail spool is an inode problem and a stuck-queue problem, not a disk-space problem — and du -h would have reported it as almost nothing.

The ordering is the actual skill. Each step is cheap and eliminates a category: inodes vs blocks, then big files vs many files, then historical vs recent growth, then the two invisible cases. Starting with du -sh /* — the instinct — is the slowest possible opening move, since it walks every filesystem including network mounts and can take an hour.

🎯 Key Takeaways

  • find evaluates a boolean expression per file; adjacent tests are implicitly ANDed and short-circuit left to right, so cheap tests belong first.
  • AND binds tighter than -o — always group alternatives with \( ... \) or your action applies to only one branch.
  • The implicit -print disappears the moment you supply any action, which is why -o expressions need an explicit trailing -print.
  • -name patterns must be quoted, or bash expands them against the current directory and find silently searches for the wrong thing.
  • -mtime +7 means 8 days or more because of whole-day truncation; use -newermt '7 days ago' when precision matters.
  • -exec cmd {} + batches filenames into few invocations and is often 100× faster than \;, which forks once per file.
  • + requires {} to be last, so use mv -t dest {} + or xargs -I{} when the target must trail.
  • Filenames may contain spaces and newlines, so NUL is the only safe separator — pair -print0 with xargs -0 or bash's read -r -d ''.
  • Never interpolate {} into sh -c; pass filenames as arguments with sh -c '...' sh {} +.
  • xargs without -r runs the command once even on empty input — with rm that is an incident.
  • -prune stops descent entirely and is far faster than filtering results with -not -path, which still walks everything.
  • -xdev keeps find on one filesystem, avoiding /proc, container layers, and hangs on unresponsive NFS mounts.
  • xargs -P parallelises cheaply, but output above 4096 bytes interleaves and partial failures are invisible — log per job, and measure before assuming concurrency helps.
  • Always run a destructive expression with -print first; find -delete has no undo and does not signal processes holding deleted files open.
