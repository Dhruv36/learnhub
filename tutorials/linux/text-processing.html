Text Processing: grep, sed & awk The Shell

What you'll master: which of the three tools to reach for and why the answer is usually decided in seconds — grep selects lines, sed edits streams, awk understands fields — plus the regex distinctions that silently change behaviour (BRE vs ERE vs PCRE), why greedy matching ruins your first attempt at parsing, awk's pattern/action model and associative arrays that replace most sort | uniq -c pipelines, why sed -i is not really in-place, and where text processing stops being the right answer entirely. Prerequisites: The Shell Executes a Line and Redirection, Pipes & File Descriptors.

Part 1 — Choosing the Tool in Five Seconds

These three overlap enough that people pick by habit rather than fit, and end up writing an awk program inside a sed command. The decision is nearly always mechanical:

If you need to…UseBecause
Find lines matching a patterngrepIt only selects; fastest and clearest
Substitute text, delete or insert linessedLine-oriented stream editing
Work with columns, sum, count, or groupawkAutomatic field splitting + real variables
Extract a fixed column from clean datacutSimpler and faster than awk for the trivial case
Anything needing state across many linesawk or a real languagesed's hold space is possible but unreadable
Parse JSON, XML, CSV with quoted commasjq, xmlstarlet, PythonThese formats are not line-oriented — see Part 6

A useful rule of thumb: if your sed command contains more than one ;, you probably wanted awk. If your awk program is longer than ten lines, you probably wanted Python.

# Same task, three ways — count HTTP 500s per URL
$ grep ' 500 ' access.log | awk '{print $7}' | sort | uniq -c | sort -rn   # idiomatic
$ awk '$9 == 500 {count[$7]++} END {for (u in count) print count[u], u}' access.log | sort -rn

The second does it in one pass with no sorting of the raw data, and it is more correct: it matches field 9 exactly rather than the string " 500 " anywhere in the line, which would also match a byte count of 500 or a URL containing it. Precision usually comes from knowing which field you mean.

Part 2 — Regex: Three Dialects, Silently Different

The most common source of "this regex works in one tool but not another" is that Unix has three regex dialects and the tools default to different ones.

DialectTools+ ? | ( ) { }
BRE (Basic)grep, sed (default)Literal — must escape as \+ \? \| \( \)
ERE (Extended)grep -E, sed -E, awkSpecial — work as expected
PCREgrep -PSpecial, plus \d, \s, lookarounds, non-greedy
$ echo "aaa" | grep    'a\+'      # BRE: backslash makes + special
aaa
$ echo "aaa" | grep -E 'a+'       # ERE: + is special already
aaa
$ echo "aaa" | grep    'a+'       # BRE: matches a LITERAL plus sign
$                                 # no output — correct, and surprising

Use grep -E and sed -E by default. The escaping rules of BRE are a historical artefact that buys nothing, and mixing them up produces silent wrong matches rather than errors — the worst failure mode.

The character classes worth using are the POSIX bracket forms, because they are locale-correct where [a-z] is not:

ClassMatchesNote
[[:digit:]]0–9\d only in PCRE
[[:alpha:]]LettersLocale-aware, unlike [a-zA-Z]
[[:space:]]Space, tab, newline\s only in PCRE
[[:alnum:]]Letters and digits
\bWord boundaryGNU extension; works in grep/sed

The other reliable trap is greedy matching. Regex quantifiers take the longest possible match, which almost never matches intent on the first attempt:

$ echo '<b>bold</b> and <i>italic</i>' | sed -E 's/<.*>//'
                                  # everything vanished: .* matched the whole line

$ echo '<b>bold</b> and <i>italic</i>' | sed -E 's/<[^>]*>//g'
bold and italic                   # [^>]* cannot cross a '>', so each tag matches alone

The negated-character-class trick — [^X]* instead of .* — is the single most useful regex habit. It expresses "up to the next delimiter" directly, works in every dialect, and is faster than the PCRE non-greedy .*? because there is no backtracking.

🔑 Anchors and quoting are where most one-liners break. Always single-quote a regex so the shell cannot expand $, *, or backslashes before the tool sees it — as the shell lesson showed, an unquoted pattern is matched by bash against the current directory instead. And anchor when you mean it: grep '^error' is a very different query from grep error, which matches terrorized.

Part 3 — grep: Selection, and the Flags That Matter

grep answers one question — which lines match — and its value is in a handful of flags that turn it from a search tool into a precise filter.

FlagEffectWhen it matters
-FFixed string, no regexSearching for literal text with dots/slashes; much faster
-wWhole wordAvoids cat matching concatenate
-cCount matching linesNot occurrences — a line with 3 matches counts once
-oPrint only the matchExtraction; combine with -P for groups
-vInvertExclusion filters
-rRecurseUse -r not -R to avoid symlink loops
-l / -LFiles with / without matchesFeeding a list into another command
-A/-B/-C nContext linesReading a stack trace around an error
-qQuiet; exit status onlyConditionals — exits at the first match
-m nStop after n matchesHuge files where you need one example
# Count lines vs count occurrences — a classic off-by-many
$ printf 'a a a\nb\n' | grep -c a
1                                  # one LINE contains 'a'
$ printf 'a a a\nb\n' | grep -o a | wc -l
3                                  # three occurrences

grep -q in a conditional is the idiomatic existence test, and it is faster than it looks because grep exits as soon as it finds one match rather than reading the rest of the file:

$ if grep -q '^ERROR' /var/log/app.log; then
>   echo "errors present"
> fi

Exit status is part of grep's interface: 0 means matched, 1 means no match, 2 means an actual error. The distinction between 1 and 2 matters under set -e, where a legitimate "no match" aborts the script — grep -q x file || true is the usual opt-out.

For extraction, -o with -P gives you lookarounds, which pull a value out without the surrounding text:

$ echo 'user=alice id=42 role=admin' | grep -oP 'id=\K\d+'
42                                 # \K discards everything matched before it

$ echo 'user=alice id=42' | grep -oP '(?<=user=)\w+'
alice                              # lookbehind: match preceded by 'user='

Part 4 — sed: Stream Editing

sed applies commands to each line as it streams past. Ninety percent of real use is the substitute command, whose full form is worth knowing exactly:

      s/pattern/replacement/flags
      │ │        │            │
      │ │        │            └── g (all), i (case-insens), p (print), 3 (3rd match only)
      │ │        └── & = whole match; \1 \2 = capture groups
      │ └── the regex (BRE unless -E)
      └── substitute

$ echo "hello world" | sed 's/o/0/'
hell0 world                        # first occurrence per line only
$ echo "hello world" | sed 's/o/0/g'
hell0 w0rld                        # g = every occurrence

$ echo "2026-08-08" | sed -E 's/([0-9]{4})-([0-9]{2})-([0-9]{2})/\3\/\2\/\1/'
08/08/2026                         # capture groups reordered

$ echo "important" | sed 's/.*/[&]/'
[important]                        # & is the entire match

Any character can be the delimiter, which removes the need to escape slashes in paths — a real readability win:

$ echo "/usr/local/bin" | sed 's/\/usr\/local/\/opt/'     # unreadable
/opt/bin
$ echo "/usr/local/bin" | sed 's|/usr/local|/opt|'        # same thing, clear
/opt/bin

Line addressing restricts where a command applies, which is what makes sed more than a substitute engine:

AddressApplies to
sed '3s/a/b/'Line 3 only
sed '2,5d'Delete lines 2–5
sed '/START/,/END/d'Delete from a matching line to another
sed '$d'Last line
sed '/^#/d'Delete comment lines
sed -n '/x/p'-n suppresses auto-print; p prints matches (≈ grep)
sed '5q'Quit after line 5 — stops reading, unlike head on a pipe

sed -i is not in-place. It writes a temporary file and renames it over the original, which has consequences people hit in production:

$ ls -i /tmp/conf.txt
9401 /tmp/conf.txt
$ sed -i 's/old/new/' /tmp/conf.txt
$ ls -i /tmp/conf.txt
9412 /tmp/conf.txt                 # DIFFERENT inode — it is a new file

So sed -i breaks hard links, replaces symlinks with regular files (unless --follow-symlinks), changes ownership to the running user, and needs write permission on the directory, not just the file — all of which follow directly from Files, Inodes & Links. Always take a backup on anything that matters:

$ sed -i.bak 's/old/new/' /etc/app.conf     # leaves /etc/app.conf.bak

Part 5 — awk: Fields, Patterns and Arrays

awk is a small programming language whose defining feature is that it splits every line into fields automatically. That one behaviour eliminates most of the pipeline plumbing people write around cut and sort.

      awk 'PATTERN { ACTION }' file

      no PATTERN → run ACTION on every line
      no ACTION  → print the line (default)

      $0 = whole line     $1, $2… = fields
      NF  = number of fields          NR = record (line) number
      FS  = input separator           OFS = output separator

$ echo "alice 30 engineer" | awk '{print $3, $1}'
engineer alice

$ awk '$3 > 100' data.txt              # pattern only: print lines where field 3 > 100
$ awk 'NF == 0' file.txt               # blank lines
$ awk '$NF ~ /error/' log.txt          # last field matches a regex
$ awk 'NR % 2 == 0' file.txt           # every second line

Field splitting defaults to runs of whitespace, which handles ragged alignment automatically — the reason awk beats cut on real command output:

$ ps aux | awk '$3 > 5.0 {print $2, $11}'     # PIDs using >5% CPU
$ df -h | awk 'NR>1 && $5+0 > 80 {print $6, $5}'   # filesystems over 80%

cut -d' ' fails on both of those because consecutive spaces create empty fields. awk's default splitter collapses them.

BEGIN and END blocks run before and after all input, which is what turns awk into an aggregator:

$ awk '{sum += $2} END {print "total:", sum, "avg:", sum/NR}' data.txt
total: 4821 avg: 96.42

Associative arrays are the feature that replaces whole pipelines. Any string can be a key, and counting is a single expression:

# The classic pipeline:
$ awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -5

# The awk version — one pass, no sorting of the raw data:
$ awk '{count[$1]++} END {for (ip in count) print count[ip], ip}' access.log \
    | sort -rn | head -5

On a large log the difference is substantial, because the pipeline sorts every line while awk only sorts the distinct keys. Grouping by two fields is just as easy:

# Bytes transferred per status code
$ awk '{bytes[$9] += $10; hits[$9]++} END {
    for (s in bytes) printf "%s: %d hits, %.1f MB\n", s, hits[s], bytes[s]/1048576
  }' access.log
200: 48213 hits, 1420.3 MB
404: 1902 hits, 3.1 MB
500: 87 hits, 0.4 MB

A few practical details that come up constantly:

TaskIdiom
Custom separatorawk -F: '{print $1}' /etc/passwd
Multiple separatorsawk -F'[:,]' ... (FS is a regex when longer than one char)
Output separatorawk -v OFS='\t' '{print $1,$2}'
Pass a shell variable inawk -v threshold="$n" '$2 > threshold'
Force numeric comparison$5+0 > 80 — strips a trailing %
Deduplicate, preserving orderawk '!seen[$0]++'
Print a range between markersawk '/START/,/END/'

awk '!seen[$0]++' deserves a moment: it deduplicates a file without sorting it. The expression is true the first time a line is seen (seen[$0] is 0, negated to true) and false afterwards, and the bare pattern prints matching lines. It is the fastest way to remove duplicate lines while keeping original order.

Never interpolate shell variables directly into an awk program — use -v, or you have created a code-injection hole exactly as described in the shell lesson:

$ awk "\$2 > $userinput"           # WRONG: userinput is executed as awk code
$ awk -v t="$userinput" '$2 > t'   # correct: passed as data

❌ cat file | grep x | awk '{print $2}' — three processes and two pipes for one job. The cat is pure waste (grep reads files directly), and awk can do the matching itself.

✅ awk '/x/ {print $2}' file — one process, one pass. The "useless use of cat" is a running joke, but the real cost is that each pipeline stage adds a fork, a buffer, and a copy; on a multi-gigabyte log the single-process version is measurably faster and simpler to read.

Part 6 — Where Text Processing Stops Being Right

These tools assume input is line-oriented records of delimited fields. When that assumption breaks, line-based tools produce plausible wrong answers rather than errors — the most dangerous failure mode there is.

FormatWhy line tools failUse instead
JSONNested, and whitespace/order are not significantjq
CSV with quoted fields"Smith, John" contains the delimitercsvkit, Python csv, miller
XML/HTMLNesting cannot be expressed by a regexxmlstarlet, a parser
Multi-line recordsStack traces span linesawk with RS="", or a real parser
BinaryNo line concept; NUL bytes truncatexxd, a language with byte strings
# Fragile — breaks the moment a value contains a comma or the field order changes
$ grep '"status"' response.json | sed 's/.*: *"\(.*\)".*/\1/'

# Correct — a parser that understands the format
$ jq -r '.status' response.json

The CSV case is the one that quietly corrupts data:

$ printf 'name,city\n"Smith, John",Berlin\n' | awk -F, '{print $1}'
name
"Smith                             # split inside a quoted field

awk can be taught this with a complex FS regex, but the honest answer is that CSV is not a delimiter-separated format — it is a format with quoting and escaping rules, and it needs a parser.

awk does handle multi-line records natively when they are blank-line separated, which covers many config and record formats:

$ awk 'BEGIN {RS=""; FS="\n"} /Name:/ {print $1, $2}' records.txt
🔑 The rule I actually apply. Text tools are excellent for exploration at a prompt, where a wrong answer is immediately visible and costs nothing. For anything committed — a cron job, a deploy script, a monitoring check — if the input format has quoting, nesting, or escaping rules, use a parser. A pipeline that is 95% correct on production data is a bug that surfaces at 3am with a customer's name in it.

Interview Questions

Beginner: When would you use grep, sed, and awk?

They divide cleanly by what they operate on:

  • grep selects lines matching a pattern. It only filters — it does not modify. Reach for it whenever the question is "which lines contain this?"
  • sed is a stream editor: substitute text, delete lines, insert. Reach for it for find-and-replace across a stream or file.
  • awk splits each line into fields automatically and is a real programming language with variables and arrays. Reach for it whenever columns, arithmetic, or grouping are involved.

The practical heuristic: if you find yourself piping cut | sort | uniq -c, awk usually does the whole thing in one pass. If a sed command has grown several semicolons, it wanted to be awk. If an awk program has passed ten lines, it wanted to be Python.

They also overlap deliberately — awk '/pattern/' is grep, and sed -n '/x/p' is grep. Choosing the narrowest tool that fits keeps the intent obvious to whoever reads it next.

Beginner: Why does grep 'a+' not match "aaa"?

Because grep defaults to Basic Regular Expressions (BRE), where + is a literal plus sign, not a quantifier. The pattern is asking for a letter 'a' followed by an actual '+' character.

Unix has three regex dialects and the tools default differently:

$ echo aaa | grep    'a\+'    # BRE: escape to make + special
$ echo aaa | grep -E 'a+'     # ERE: + is special by default
$ echo aaa | grep -P 'a+'     # PCRE: also supports \d, \s, lookarounds

BRE requires escaping + ? | ( ) { } to make them special — the reverse of every modern regex flavour. It is a historical artefact, and the dangerous part is that a BRE pattern using ERE syntax usually fails silently by matching nothing (or matching a literal) rather than raising an error.

My practice is to use -E on grep and sed unconditionally. awk already uses ERE, so that also makes the three tools consistent with each other.

Mid: Explain greedy matching and how to avoid it.

Regex quantifiers (*, +) are greedy: they match the longest string that still allows the overall pattern to succeed. This almost never matches intent when a delimiter is involved.

$ echo '<b>bold</b> and <i>x</i>' | sed -E 's/<.*>//'
                      # empty — .* matched from the first < to the LAST >

Three fixes, in order of preference:

  • Negated character class — <[^>]*>. This says "up to the next >" directly. It works in every dialect and is fastest, because it cannot backtrack past a delimiter.
  • Non-greedy quantifier — <.*?>, but only in PCRE (grep -P, Perl, Python). Not available in sed or awk.
  • Don't use regex — if the data has fields, awk's field splitting sidesteps the question entirely.

The negated class is the habit worth building. It also has a performance dimension: catastrophic backtracking (ReDoS) comes from nested greedy quantifiers over ambiguous input, and constraining what each part can match is the general defence.

Mid: Why is sed -i not really in-place, and what breaks because of it?

Because sed writes a temporary file and renames it over the original. The name survives, but the inode does not — you can watch the inode number change across the command.

Everything that breaks follows from that, and each traces back to how inodes and links work:

  • Hard links break. The other names still point at the old inode with the old content, so a file that appeared in two places is now two different files.
  • Symlinks are replaced by regular files unless you pass --follow-symlinks — a real problem for config directories built from symlinked templates.
  • Ownership and permissions can change to the running user's, since a new file is created.
  • You need write permission on the directory, not just the file, because the operation is fundamentally a rename.
  • A process holding the file open keeps reading the old content, exactly as with any rename — which is why a daemon needs a reload signal after you edit its config.

The upside is that the rename is atomic, so no reader ever sees a half-edited file — sed is implementing the atomic-write pattern for you. In practice I always use sed -i.bak on anything that matters, and for config management I would use a tool that manages the whole file (Ansible, a template) rather than mutating it with regexes, because a sed expression that matches nothing fails silently.

Senior: You need the top 10 URLs by total bytes from a 50 GB access log. Design the most efficient approach.

The dominant cost is I/O, so the goal is one pass, no sorting of raw data, and bounded memory.

The naive pipeline is the wrong shape:

$ awk '{print $7, $10}' access.log | sort | ...

That sorts 50 GB — spilling to disk, writing temp files roughly the size of the input, and taking many minutes. The sort is doing work that is not needed.

Aggregate first, sort only the distinct keys:

$ awk '{bytes[$7] += $10} END {for (u in bytes) print bytes[u], u}' access.log \
    | sort -rn | head -10

One pass, and the sort input is the number of distinct URLs — likely tens of thousands, not hundreds of millions. This is usually 10–50× faster and is the single most valuable awk idiom.

Then check the assumption that could break it. Memory is proportional to distinct keys, so if URLs carry unique query strings or session IDs, the array can grow unbounded. Normalise the key as part of the same pass:

$ awk '{u=$7; sub(/\?.*/, "", u); bytes[u] += $10} END {...}' access.log

Further optimisations, in the order I would apply them:

  • LC_ALL=C in front — byte-wise comparison instead of locale collation, often a significant speedup for both awk and sort.
  • mawk instead of gawk if available; it is typically 2–3× faster for simple field work.
  • If the file is compressed, keep it that way — zcat plus awk usually beats reading uncompressed data from disk, because decompression is cheaper than the extra I/O.
  • Parallelise across files rather than within one, if logs are already rotated: run per-file aggregations concurrently and merge the small results.

The honest limit: if this runs daily, the right answer is not a better one-liner — it is to stop scanning 50 GB repeatedly. Load into a columnar store or query it where it already lives. Text tools are excellent for a one-off investigation and a poor foundation for a recurring report.

Senior: When is text processing the wrong tool, and how do you decide?

These tools rest on one assumption: input is line-oriented records of delimited fields. When that holds, they are unbeatable for their size. When it does not, they produce plausible wrong answers instead of errors, which is far worse than failing.

The four cases where the assumption breaks:

  • Nested formats (JSON, XML, YAML). A regex cannot express arbitrary nesting. grep '"status"' | sed 's/.*"\(.*\)".*/\1/' works until a value contains a quote, the key appears twice at different depths, or the file is pretty-printed differently.
  • Quoted delimiters (CSV). "Smith, John" contains the separator, so field 1 splits mid-value. This corrupts data silently and usually first shows up with a customer's real name.
  • Multi-line records (stack traces, MIME). awk's RS="" handles the blank-line-separated case; anything else needs real state.
  • Meaningful whitespace or encoding — UTF-8 multi-byte characters, embedded NULs, CRLF line endings that leave an invisible \r on every field.

My decision rule is about blast radius rather than difficulty. At an interactive prompt, I use whatever is fastest to type, because a wrong answer is visible immediately and costs nothing. For anything that gets committed — a cron job, a deploy step, a monitoring check, an alert threshold — if the format has quoting, escaping, or nesting rules, I use a parser: jq for JSON, Python's csv module, miller for tabular data.

The second signal is length. Past roughly ten lines of awk, I have re-implemented parts of a language that already has dictionaries, error handling, and tests. Rewriting it in Python takes twenty minutes and is maintainable by whoever inherits it — a 200-character one-liner is write-only code, and the cleverness is a liability rather than an achievement.

🏋️ Exercises

1 (easy): Demonstrate the difference between BRE, ERE, and PCRE on the same pattern.
Solution 
$ printf 'aaa\na+b\nabc123\n' > /tmp/re.txt

# The + quantifier
$ grep 'a\+' /tmp/re.txt          # BRE: escaped + is a quantifier
aaa
a+b
abc123
$ grep -E 'a+' /tmp/re.txt        # ERE: same result, natural syntax
aaa
a+b
abc123
$ grep 'a+' /tmp/re.txt           # BRE: literal plus sign
a+b

The last one is the trap: it did not error, it just answered a different question.

Grouping and alternation differ the same way:

$ echo "abcabc" | grep -E '(abc){2}'
abcabc
$ echo "abcabc" | grep '\(abc\)\{2\}'     # BRE needs everything escaped
abcabc
$ echo "cat" | grep -E 'cat|dog'
cat
$ echo "cat" | grep 'cat\|dog'            # BRE
cat

PCRE adds what neither has:

$ echo "abc123" | grep -oP '\d+'
123                               # \d is PCRE-only
$ echo "id=42 x" | grep -oP 'id=\K\d+'
42                                # \K resets the match start
$ echo "<a><b>" | grep -oP '<.*?>'
<a>
<b>                               # non-greedy, unavailable in BRE/ERE

The portable equivalent of that last one works everywhere and is faster:

$ echo "<a><b>" | grep -oE '<[^>]*>'
<a>
<b>
2 (easy): Show why grep -c does not count occurrences.
Solution 
$ printf 'error error error\nok\nerror\n' > /tmp/log.txt

$ grep -c error /tmp/log.txt
2                                  # two LINES contain 'error'

$ grep -o error /tmp/log.txt | wc -l
4                                  # four occurrences

-c counts matching lines, which is what you want for "how many requests failed?" but wrong for "how many times does this appear?". Getting this backwards silently under-reports.

A realistic case where it matters — counting how many times an IP appears versus how many log lines mention it:

$ printf '10.0.0.1 -> 10.0.0.1\n10.0.0.2 -> 10.0.0.1\n' > /tmp/conn.txt
$ grep -c '10.0.0.1' /tmp/conn.txt
2                                  # 2 lines
$ grep -o '10\.0\.0\.1' /tmp/conn.txt | wc -l
3                                  # 3 appearances

Note the escaped dots in the second: unescaped, . matches any character, so 10.0.0.1 would also match 10x0y0z1. Use grep -F when the pattern is a literal string:

$ grep -oF '10.0.0.1' /tmp/conn.txt | wc -l
3

-F is also meaningfully faster on large files, since no regex engine is involved.

3 (medium): Replace a four-stage pipeline with a single awk program and measure the difference.
Solution

Generate a realistic log:

$ python3 -c "
import random
ips = ['10.0.0.%d' % i for i in range(1, 60)]
urls = ['/api/v%d/items' % i for i in range(1, 25)]
with open('/tmp/access.log','w') as f:
    for _ in range(2_000_000):
        f.write('%s - - [08/Aug/2026] \"GET %s\" %d %d\n' % (
            random.choice(ips), random.choice(urls),
            random.choice([200,200,200,404,500]), random.randint(200, 90000)))
"
$ ls -lh /tmp/access.log
-rw-r--r-- 1 alice alice 143M Aug  8 16:20 /tmp/access.log

The pipeline version — sorts all two million lines:

$ time (awk '{print $1}' /tmp/access.log | sort | uniq -c | sort -rn | head -5)
  34012 10.0.0.23
  33987 10.0.0.7
  ...
real    0m11.42s

The single-pass version — sorts only the 59 distinct keys:

$ time (awk '{c[$1]++} END {for (i in c) print c[i], i}' /tmp/access.log | sort -rn | head -5)
  34012 10.0.0.23
  33987 10.0.0.7
  ...
real    0m1.86s

Roughly 6× faster, and the gap widens with input size because the pipeline's sort is O(n log n) on every line while awk's hash insert is O(1) per line.

Aggregate several things in the same pass — the pipeline would need a separate run for each:

$ awk '{
    hits[$1]++
    bytes[$1] += $NF
    if ($(NF-1) == 500) errors[$1]++
  } END {
    printf "%-12s %8s %10s %7s\n", "IP", "HITS", "MB", "5xx"
    for (i in hits) printf "%-12s %8d %10.1f %7d\n", i, hits[i], bytes[i]/1048576, errors[i]
  }' /tmp/access.log | sort -k2 -rn | head -5
IP               HITS         MB     5xx
10.0.0.23       34012      1462.8    6821
10.0.0.7        33987      1459.1    6790

Three aggregations, one read of 143 MB. The pipeline approach would read the file three times and sort it three times.

Cleanup: rm /tmp/access.log.

4 (medium): Prove that sed -i creates a new file, and show what that breaks.
Solution 
$ echo "value=old" > /tmp/conf.txt
$ ln /tmp/conf.txt /tmp/conf-hardlink.txt        # a second name for the same inode
$ ln -s /tmp/conf.txt /tmp/conf-symlink.txt
$ ls -li /tmp/conf.txt /tmp/conf-hardlink.txt
9401 -rw-r--r-- 2 alice alice 10 Aug  8 16:30 /tmp/conf-hardlink.txt
9401 -rw-r--r-- 2 alice alice 10 Aug  8 16:30 /tmp/conf.txt

Now edit and observe the inode change:

$ sed -i 's/old/new/' /tmp/conf.txt
$ ls -li /tmp/conf.txt /tmp/conf-hardlink.txt
9455 -rw-r--r-- 1 alice alice 10 Aug  8 16:31 /tmp/conf.txt          ← new inode
9401 -rw-r--r-- 1 alice alice 10 Aug  8 16:30 /tmp/conf-hardlink.txt ← old inode

$ cat /tmp/conf.txt
value=new
$ cat /tmp/conf-hardlink.txt
value=old                          # the hard link kept the ORIGINAL content

The link count dropped from 2 to 1 on each — they are now two independent files. Anything relying on them being one file is silently broken.

The symlink case is worse, because it destroys the link itself:

$ ls -l /tmp/conf-symlink.txt
lrwxrwxrwx 1 alice alice 14 Aug  8 16:30 /tmp/conf-symlink.txt -> /tmp/conf.txt
$ sed -i 's/new/newer/' /tmp/conf-symlink.txt
$ ls -l /tmp/conf-symlink.txt
-rw-r--r-- 1 alice alice 12 Aug  8 16:33 /tmp/conf-symlink.txt      ← now a regular file!

The symlink was replaced by a regular file containing the edited content, and the real target was never modified. In a config directory built from symlinked templates, this is a genuinely confusing production incident.

The fixes:

$ sed -i --follow-symlinks 's/x/y/' /tmp/link.txt    # edits the target, keeps the link
$ sed -i.bak 's/x/y/' /etc/app.conf                  # always keep a backup

And confirm ownership can change, which matters when editing as root:

$ sudo sh -c 'echo x > /tmp/owned.txt; chown nobody /tmp/owned.txt'
$ sudo sed -i 's/x/y/' /tmp/owned.txt
$ ls -l /tmp/owned.txt
-rw-r--r-- 1 nobody nogroup 2 ...    # GNU sed preserves it, but not all implementations do
5 (hard): Show how parsing structured data with line tools silently corrupts results, then fix it.
Solution

The CSV case — quoted fields containing the delimiter:

$ cat > /tmp/people.csv <<'EOF'
name,city,amount
"Smith, John",Berlin,100
"O'Brien, Mary",Paris,250
Simple Name,London,75
EOF

$ awk -F, '{print $1}' /tmp/people.csv
name
"Smith                             ← split inside the quoted field
"O'Brien
Simple Name

$ awk -F, '{sum += $3} END {print sum}' /tmp/people.csv
75                                 ← WRONG: should be 425

The sum is not an error — it is a plausible number that is simply wrong, because field 3 is Berlin for the first two rows. Nothing warns you.

The fix — a real CSV parser:

$ python3 -c "
import csv, sys
with open('/tmp/people.csv') as f:
    rows = list(csv.DictReader(f))
print('names:', [r['name'] for r in rows])
print('total:', sum(int(r['amount']) for r in rows))
"
names: ['Smith, John', \"O'Brien, Mary\", 'Simple Name']
total: 425

The JSON case is the same lesson:

$ cat > /tmp/resp.json <<'EOF'
{"status": "ok", "user": {"status": "suspended", "name": "alice"}, "count": 3}
EOF

$ grep -o '"status": "[^"]*"' /tmp/resp.json
"status": "ok"
"status": "suspended"              ← which one did you want? Both matched.

$ jq -r '.status' /tmp/resp.json
ok                                 ← unambiguous: the top-level key
$ jq -r '.user.status' /tmp/resp.json
suspended

The grep version also breaks entirely if the JSON is pretty-printed across lines, if the key order changes, or if a value contains an escaped quote — none of which are errors in JSON, and all of which are invisible until they happen.

Where awk is still right: when the format genuinely is delimited with no quoting, awk is the correct and fastest tool. /etc/passwd is a good example — colon-separated, no escaping, guaranteed structure:

$ awk -F: '$3 >= 1000 {print $1, $6}' /etc/passwd
alice /home/alice

The distinction is whether the format has rules beyond "split on a character". If it does, you need something that implements those rules.

6 (hard): Build a log analysis report in one awk pass, handling malformed lines safely.
Solution

Real logs contain truncated lines, wrong field counts, and non-numeric values where numbers belong. A report that silently mis-counts them is worse than one that refuses.

$ cat > /tmp/report.awk <<'EOF'
# Usage: awk -f report.awk -v threshold=1000 access.log
BEGIN {
    OFS = "\t"
    if (threshold == "") threshold = 500
}

# Reject lines that do not have the expected shape, and count them.
NF != 10 { malformed++; next }
$(NF-1) !~ /^[0-9]{3}$/ { malformed++; next }

{
    status = $(NF-1)
    bytes  = $NF + 0                 # +0 forces numeric; non-numeric becomes 0
    url    = $7
    sub(/\?.*/, "", url)             # normalise: drop query strings

    total++
    total_bytes += bytes
    hits[url]++
    vol[url] += bytes
    codes[status]++
    if (status ~ /^5/) server_errors++
    if (bytes > max_bytes) { max_bytes = bytes; max_url = url }
}

END {
    if (total == 0) { print "no valid records" > "/dev/stderr"; exit 1 }

    printf "Records: %d valid, %d malformed (%.2f%%)\n", \
           total, malformed, 100 * malformed / (total + malformed)
    printf "Traffic: %.2f GB   5xx rate: %.3f%%\n", \
           total_bytes / 1073741824, 100 * server_errors / total
    printf "Largest single response: %.1f MB (%s)\n\n", max_bytes / 1048576, max_url

    print "Status codes:"
    for (c in codes) printf "  %s  %8d  %6.2f%%\n", c, codes[c], 100 * codes[c] / total
    print ""

    printf "URLs over %d hits, by volume:\n", threshold
    for (u in hits)
        if (hits[u] > threshold)
            printf "  %-24s %8d hits %10.1f MB %8.1f KB avg\n", \
                   u, hits[u], vol[u] / 1048576, vol[u] / hits[u] / 1024
}
EOF

Run it against data that includes deliberate corruption:

$ printf '%s\n' \
  '10.0.0.1 - - [08/Aug/2026] "GET /api/items" 200 4096' \
  '10.0.0.2 - - [08/Aug/2026] "GET /api/items?q=x" 500 128' \
  'TRUNCATED LINE' \
  '10.0.0.3 - - [08/Aug/2026] "GET /health" 200 abc' \
  > /tmp/mixed.log
$ awk -f /tmp/report.awk -v threshold=0 /tmp/mixed.log
Records: 3 valid, 1 malformed (25.00%)
Traffic: 0.00 GB   5xx rate: 33.333%
Largest single response: 0.0 MB (/api/items)

Status codes:
  200      2   66.67%
  500      1   33.33%

URLs over 0 hits, by volume:
  /api/items                      2        0.0 MB      2.0 KB avg
  /health                         1        0.0 MB      0.0 KB avg

The defensive choices, and why each is there:

TechniquePrevents
NF != 10 { malformed++; next }Truncated lines producing garbage fields
Regex-validating the status fieldA shifted line silently counting as a status code
$NF + 0Non-numeric bytes (abc, -) breaking sums
Reporting the malformed rateSilent data loss — 25% rejection should alarm you
sub(/\?.*/, "", url)Unbounded array growth from unique query strings
-v threshold=Shell injection from interpolating a variable into the program
Exit 1 on zero recordsAn empty report reading as success in a cron job

The limit worth stating: this handles space-delimited logs with a stable field count. The moment a user-agent string with spaces or an escaped quote appears in a field, the NF == 10 assumption fails and lines get rejected as malformed — which is at least visible rather than silently wrong. If that rate climbs, the correct response is to move to a parser for the actual log format, not to loosen the validation.

🎯 Key Takeaways

  • grep selects lines, sed edits streams, awk understands fields — if a sed command has several semicolons it wanted awk, and past ten lines of awk you wanted Python.
  • Unix has three regex dialects: BRE (grep/sed default, where + ? | are literal), ERE (-E, and awk), and PCRE (grep -P). Use -E by default.
  • A BRE pattern using ERE syntax fails silently by matching the wrong thing rather than erroring.
  • Quantifiers are greedy; [^X]* is the portable, faster way to say "up to the next delimiter" and is the most useful regex habit to build.
  • Always single-quote regexes so bash cannot expand them before the tool sees them.
  • grep -c counts matching lines, not occurrences — use grep -o | wc -l for the latter.
  • grep's exit status is part of its interface: 0 matched, 1 no match, 2 error — and a "no match" aborts scripts under set -e.
  • sed -i writes a new file and renames it, so it breaks hard links, replaces symlinks with regular files, and needs directory write permission.
  • awk splits fields automatically and collapses runs of whitespace, which is why it beats cut on real command output.
  • Associative arrays let awk aggregate in one pass — sorting only the distinct keys instead of every line is often 6× or more faster on large logs.
  • Pass shell values with awk -v; interpolating them into the program text is code injection.
  • Force numeric comparison with $5+0 when a field carries units like 85%.
  • These tools assume line-oriented delimited records — JSON, quoted CSV, and XML need real parsers, because line tools produce plausible wrong answers rather than errors.
