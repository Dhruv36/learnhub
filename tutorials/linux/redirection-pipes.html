Redirection, Pipes & File Descriptors The Shell

What you'll master: why 2>&1 before a redirect does nothing and after it works — the ordering rule that makes redirection finally click — what a pipe physically is and why a full one blocks the writer, why cmd | grep shows nothing when cmd writes to stderr, the buffering behaviour that makes piped output appear in bursts and how to defeat it, and how to open, duplicate and close descriptors deliberately rather than by copying incantations. Prerequisites: The Shell Executes a Line and How Unix Is Put Together.

Part 1 — Three Descriptors, and Nothing Special About Them

Every process starts with three open file descriptors by convention. They are ordinary integers with no kernel-level significance beyond the fact that every program agrees on their meaning.

FDNameDefaultPurpose
0stdinTerminalInput
1stdoutTerminalData — the program's actual output
2stderrTerminalDiagnostics — errors, progress, warnings

The split between 1 and 2 is a design decision worth appreciating: it lets you redirect a program's data without losing its error messages, and it means diagnostics do not contaminate a pipeline. A well-behaved program puts only results on stdout.

$ ls -l /proc/self/fd
lrwx------ 1 alice alice 64 Aug  8 14:02 0 -> /dev/pts/2
lrwx------ 1 alice alice 64 Aug  8 14:02 1 -> /dev/pts/2
lrwx------ 1 alice alice 64 Aug  8 14:02 2 -> /dev/pts/2
lr-x------ 1 alice alice 64 Aug  8 14:02 3 -> /proc/57201/fd

All three point at the same terminal device, which is why output and errors interleave on screen. Now redirect one and watch the table change — the program is unaware:

$ ls -l /proc/self/fd > /tmp/fds.txt; cat /tmp/fds.txt
lrwx------ 1 alice alice 64 Aug  8 14:03 0 -> /dev/pts/2
l-wx------ 1 alice alice 64 Aug  8 14:03 1 -> /tmp/fds.txt      ← moved
lrwx------ 1 alice alice 64 Aug  8 14:03 2 -> /dev/pts/2

As Lesson 1 established, the shell arranges this in the window between fork and execve. The program writes to fd 1 exactly as always.

OperatorEffect
> filestdout to file, truncating it
>> filestdout to file, appending
2> filestderr to file
< filestdin from file
&> fileboth stdout and stderr (bash shorthand)
2>&1make fd 2 a copy of wherever fd 1 currently points
> /dev/nulldiscard
<<< "text"here-string: feed a literal string as stdin
🔑 Truncation happens at open time, before the command runs. The shell opens the target with O_TRUNC during redirection setup — stage 8 of the expansion pipeline — which is before execve. This is why sort file > file produces an empty file: the redirect truncates it to zero, then sort opens it and finds nothing. Use sort file -o file (which handles it internally) or write to a temp file and rename, as in Files, Inodes & Links.

Part 2 — The Ordering Rule That Makes 2>&1 Make Sense

This is the single most misunderstood piece of shell syntax, and it becomes obvious once you read 2>&1 correctly: "make fd 2 point at whatever fd 1 points at right now". It is a copy of a current value, not a permanent link.

Redirections are processed strictly left to right, so order changes the meaning entirely:

$ cmd > file 2>&1               # CORRECT: both go to file

  step 1:  > file    →  fd 1 = file
  step 2:  2>&1      →  fd 2 = copy of fd 1 = file
  result:  1→file, 2→file  ✓


$ cmd 2>&1 > file               # WRONG: stderr still goes to the terminal

  step 1:  2>&1      →  fd 2 = copy of fd 1 = TERMINAL (fd 1 not moved yet)
  step 2:  > file    →  fd 1 = file
  result:  1→file, 2→terminal  ✗

Demonstrate it rather than trusting the diagram:

$ mkerr() { echo "this is stdout"; echo "this is stderr" >&2; }

$ mkerr > /tmp/out.txt 2>&1
$ cat /tmp/out.txt
this is stdout
this is stderr                  # both captured

$ mkerr 2>&1 > /tmp/out.txt
this is stderr                  # leaked to the terminal
$ cat /tmp/out.txt
this is stdout                  # only stdout captured

That second form is not useless — it is precisely how you send stderr to the terminal while piping stdout elsewhere, which is occasionally exactly what you want.

The same rule explains the common pipeline idiom. A pipe connects stdout only, so to pipe stderr you must merge it first:

$ mkerr | grep -c .
this is stderr                  # bypassed the pipe entirely
1                               # grep only saw stdout

$ mkerr 2>&1 | grep -c .
2                               # both lines reached grep

$ mkerr |& grep -c .            # bash shorthand for 2>&1 |
2

This resolves the classic complaint that "grep isn't finding the error message". The error was never in the pipe. Compiler errors, curl progress, and most warnings go to stderr by design.

❌ cmd 2>&1 > logfile — written by people expecting "redirect both". It sends stderr to the terminal and only stdout to the file, so errors are lost from the log and clutter the console. Under cron, where there is no terminal, they may vanish entirely.

✅ cmd > logfile 2>&1 — redirect fd 1 first, then point fd 2 at the same place. Bash's &> logfile is equivalent and harder to get wrong; use it when portability to POSIX sh is not required.

Part 3 — What a Pipe Physically Is

A pipe is not a file and touches no disk. It is a fixed-size kernel ring buffer — 64KB by default on Linux — with a read end and a write end, exposed as two file descriptors.

$ ls -l /proc/self/fd | grep pipe
lr-x------ 1 alice alice 64 Aug  8 14:20 3 -> 'pipe:[184203]'
                                                    ^ an inode number, no path

$ cat /proc/sys/fs/pipe-max-size
1048576

The buffer being finite is the important part, because it creates flow control for free. When a pipe fills, the writer blocks in write() until the reader consumes something:

$ yes | head -3
y
y
y

yes would produce infinite output, but it never runs away. It fills the 64KB buffer, blocks, and when head exits the kernel sends it SIGPIPE and it dies. The whole pipeline is self-limiting with no coordination between the two programs — neither knows the other exists.

Watch the blocking directly:

$ (dd if=/dev/zero bs=1M count=10 2>/dev/null | (sleep 5; wc -c)) &
$ sleep 1; ps -o pid,stat,wchan:20,cmd -C dd
    PID STAT WCHAN                CMD
  58120 S    pipe_write           dd if=/dev/zero bs=1M count=10
                ^^^^^^^^^^ blocked writing to a full pipe

Two consequences follow that people meet in production:

BehaviourWhyPractical effect
A slow reader throttles a fast writerThe buffer fills and write() blocksBackpressure for free; a pipeline runs at its slowest stage
Writer gets SIGPIPE when the reader closesNothing can consume the datahead terminates a producer; exit status 141 (128+13)
Reader gets EOF when all writers closeThe write end's reference count hits zeroA held-open write fd makes the reader hang forever
Writes under PIPE_BUF (4096) are atomicKernel guaranteeMultiple writers can share a pipe without interleaving short lines

The SIGPIPE case is worth recognising because the exit status is distinctive:

$ yes | head -1 >/dev/null; echo "${PIPESTATUS[@]}"
141 0
#  ^ 128 + 13 (SIGPIPE) — 'yes' was killed, which is normal and expected here

Under set -o pipefail this makes a pipeline "fail" when it was working correctly, which is a real friction point in scripts that use head to limit output.

A named pipe (FIFO) is the same object with a name in the filesystem, which lets unrelated processes connect:

$ mkfifo /tmp/mypipe
$ ls -l /tmp/mypipe
prw-r--r-- 1 alice alice 0 Aug  8 14:30 /tmp/mypipe
^ 'p' for pipe; size is always 0 — nothing is stored on disk

# Terminal A (blocks until a reader appears):
$ echo "hello" > /tmp/mypipe

# Terminal B:
$ cat /tmp/mypipe
hello

Opening a FIFO for writing blocks until someone opens it for reading, and vice versa. That rendezvous behaviour is the source of most FIFO confusion — and is also why they are useful as a synchronisation primitive.

Part 4 — Buffering: Why Piped Output Arrives in Bursts

You pipe a long-running program into grep and nothing appears for thirty seconds, then everything at once. The program is not slow. The C library changed its buffering strategy because stdout is no longer a terminal.

stdout is…BufferingFlushes when
A terminalLine-bufferedEvery newline
A pipe or fileFully buffered (4–8KB)The buffer fills, or the program exits
stderr (always)UnbufferedImmediately

The switch is done by the library, not the program, using isatty(). It is a sensible default — flushing every line to a file would be needlessly slow — but it makes live monitoring useless:

$ ping -c 100 example.com | grep 'time=' | head -3
        # ...long silence, then a burst

$ stdbuf -oL ping -c 100 example.com | grep 'time=' | head -3
64 bytes from 93.184.216.34: icmp_seq=1 ttl=56 time=11.2 ms
        # appears immediately

Three ways to force line buffering, depending on what you control:

ToolUseLimitation
stdbuf -oL cmdGeneric; works on most C programsFails if the program sets its own buffering
unbuffer cmd (expect)Allocates a pty so the program thinks it is a terminalExtra dependency; also enables colour output
Program's own flaggrep --line-buffered, awk fflush(), python -u, sed -uMost reliable when available

In a multi-stage pipeline, every stage buffers, so one unbuffered stage is not enough:

$ tail -f /var/log/app.log | grep ERROR | cut -d' ' -f3
        # grep buffers its output to cut — still bursty

$ tail -f /var/log/app.log | grep --line-buffered ERROR | cut -d' ' -f3
        # now live

This also explains a debugging classic: a Python script's print output vanishing when the program crashes. The buffer was never flushed. python -u, or PYTHONUNBUFFERED=1 in a container, is the standard fix — and is why nearly every Docker image for a Python service sets it.

Part 5 — Opening, Duplicating and Closing Descriptors

Descriptors above 2 are yours to use. The shell can open, copy and close them, which enables patterns that are otherwise impossible.

$ exec 3> /tmp/log.txt          # open fd 3 for writing
$ echo "first" >&3             # write to it
$ echo "second" >&3
$ exec 3>&-                    # close it
$ cat /tmp/log.txt
first
second

The value over >> file on each line is that the file is opened once. For a loop writing thousands of lines, that is thousands of avoided open/close pairs — and it keeps writing to the same inode even if the path is later renamed.

The most useful pattern is saving and restoring a descriptor, which lets you redirect temporarily:

$ exec 3>&1                    # fd 3 = a copy of the original stdout
$ exec 1> /tmp/captured.txt     # stdout now goes to a file
$ echo "this is captured"
$ exec 1>&3 3>&-               # restore stdout, close the spare
$ echo "this is on screen"
this is on screen
$ cat /tmp/captured.txt
this is captured

A frequent real use is capturing a command's output while still letting it write to the terminal — the "tee to a variable" problem:

# Capture stdout AND display it, preserving the command's exit status
$ exec 3>&1
$ output=$(mycommand 2>&1 | tee /dev/fd/3); status=${PIPESTATUS[0]}
$ exec 3>&-

Descriptors are inherited across fork and survive execve unless marked close-on-exec. That inheritance is what makes redirection work at all, but it also means a leaked descriptor is passed to every child — a real problem for daemons:

$ exec 4< /etc/passwd
$ bash -c 'ls -l /proc/self/fd/4'
lr-x------ 1 alice alice 64 Aug  8 14:50 /proc/self/fd/4 -> /etc/passwd
                                          ^ the child inherited it

A long-running service that leaks descriptors eventually hits its limit and fails with EMFILE — "too many open files". The diagnosis is counting them:

$ ls /proc/$PID/fd | wc -l
1021
$ cat /proc/$PID/limits | grep 'open files'
Max open files            1024                 4096

Steadily climbing counts mean a leak; a flat count near the limit means the limit is simply too low for the workload. Performance Debugging treats this as a standard check.

Part 6 — Here-Documents and Process Substitution

Two constructs that supply input from something other than a file, and both are worth using deliberately.

A here-document feeds literal text as stdin. Whether the delimiter is quoted decides if expansion happens — a distinction that causes real bugs:

$ name="Alice"
$ cat <<EOF
Hello $name, today is $(date +%A)
EOF
Hello Alice, today is Friday             # unquoted: expanded

$ cat <<'EOF'
Hello $name, the cost is $5
EOF
Hello $name, the cost is $5              # quoted: fully literal

Always quote the delimiter when writing a script or config file, or the outer shell will substitute variables meant for the inner one — the single most common here-doc bug:

$ cat > /tmp/gen.sh <<'EOF'
#!/bin/bash
echo "PATH is $PATH"          # stays literal — evaluated when gen.sh runs
EOF

<<- strips leading tabs (not spaces) so the delimiter can be indented inside a function. And <<< is a here-string, ideal for feeding one value to a command that only reads stdin:

$ grep -c 'o' <<< "hello world"
1
$ read -r a b <<< "first second"; echo "$b"
second

Process substitution makes a command's output appear as a filename, which lets tools that require file arguments consume streams:

$ diff <(sort a.txt) <(sort b.txt)              # no temp files
$ comm -13 <(sort old.txt) <(sort new.txt)      # lines added
$ paste <(cut -f1 data.tsv) <(cut -f3 data.tsv)

$ echo <(true)
/dev/fd/63                                       # it is literally an fd path

It also works in the output direction, which is less known and occasionally exactly right:

# Send one stream to two different processing chains
$ generate_data | tee >(gzip > archive.gz) >(wc -l > count.txt) | head -5

And as the previous lesson showed, < <(cmd) is the standard way to feed a loop without the subshell that a pipe would create — the fix for the vanishing-variable problem.

Interview Questions

Beginner: What is the difference between stdout and stderr, and why are there two?

They are file descriptors 1 and 2, both connected to the terminal by default, but they carry different kinds of output. stdout is for the program's actual results — the data. stderr is for diagnostics: errors, warnings, and progress messages.

The separation exists so that redirecting a program's data does not silently swallow its errors. If there were only one stream, find / -name x > results.txt would mix permission-denied messages into your results file, corrupting it.

It matters most in pipelines, because a pipe connects stdout only:

$ make | grep -i error      # finds nothing — compiler errors are on stderr
$ make 2>&1 | grep -i error # now they reach grep

One more practical difference: stderr is unbuffered by convention, so its messages appear immediately even when stdout is fully buffered into a pipe. That is why error output sometimes appears "out of order" relative to normal output when both go to the terminal.

Beginner: Why does cmd > file 2>&1 work but cmd 2>&1 > file not?

Because 2>&1 means "make fd 2 point at whatever fd 1 points at at this moment" — it copies a current value, it does not create a permanent link. Redirections are processed left to right.

In cmd > file 2>&1: first fd 1 is pointed at the file, then fd 2 is made a copy of fd 1, which is now the file. Both end up in the file.

In cmd 2>&1 > file: first fd 2 is made a copy of fd 1, which is still the terminal. Then fd 1 is moved to the file. The result is stdout in the file and stderr on the terminal — fd 2 kept pointing at the terminal because it copied the old value.

The second form is not useless: it is exactly how you pipe stdout somewhere while letting errors appear on screen. In bash, &> file is unambiguous shorthand for the correct version and is harder to get backwards, though > file 2>&1 is the portable POSIX form.

Mid: What is a pipe, physically, and what happens when it fills up?

A pipe is a fixed-size kernel ring buffer — 64KB by default on Linux — with a read end and a write end exposed as file descriptors. It touches no disk and has no filename; in /proc/PID/fd it shows as pipe:[inode].

When the buffer fills, the writer blocks in write() until the reader consumes data. You can observe it: a blocked writer sits in the pipe_write kernel function, visible in /proc/PID/wchan.

This gives flow control for free. yes | head -3 does not produce infinite output because yes fills the buffer and blocks; a pipeline naturally runs at the speed of its slowest stage, with no coordination between programs that know nothing about each other.

Two related behaviours complete the picture. When the reader closes, the writer receives SIGPIPE and dies — this is how head terminates its producer, and it shows as exit status 141 (128+13). When all writers close, the reader gets EOF; a descriptor held open by a forgotten process means the reader hangs forever, which is a classic FIFO bug.

Finally, writes smaller than PIPE_BUF (4096 bytes) are atomic, so multiple processes can write short lines to one pipe without interleaving — the property that makes simple concurrent logging to a pipe safe.

Mid: Why does piped output appear in bursts instead of live, and how do you fix it?

The C library changes its buffering strategy based on what stdout is connected to. When it is a terminal, output is line-buffered and flushes on every newline. When it is a pipe or file, it becomes fully buffered — typically 4–8KB — and only flushes when the buffer fills or the program exits.

The program did not change; isatty() returned false and libc switched modes. It is a sensible default (flushing every line to a file would be slow) that happens to defeat live monitoring.

Fixes, in order of reliability:

  • The program's own flag: grep --line-buffered, sed -u, python -u, awk with explicit fflush().
  • stdbuf -oL cmd — overrides libc's default via LD_PRELOAD. Works for most C programs but not for ones that call setvbuf themselves, and not for statically linked binaries.
  • unbuffer cmd (from expect) — allocates a pseudo-terminal so the program believes it is interactive. Most robust, but pulls in a dependency and also turns colour output back on.

The trap in multi-stage pipelines is that every stage buffers, so fixing only the first does nothing: tail -f log | grep --line-buffered ERROR | cut -d' ' -f3 needs the flag on grep, the stage whose output feeds the next pipe.

This is also why a crashed Python service loses its last log lines, and why nearly every Python Dockerfile sets PYTHONUNBUFFERED=1.

Senior: A service intermittently fails with "too many open files". Diagnose and fix it.

EMFILE means the process hit its descriptor limit. The first question is whether this is a leak or an under-sized limit, and the two look identical at the moment of failure but need opposite fixes.

1. Establish the count against the limit:

$ ls /proc/$PID/fd | wc -l
1021
$ grep 'open files' /proc/$PID/limits
Max open files            1024                 4096

2. Distinguish leak from under-provisioning by sampling over time. A count that climbs monotonically and never falls is a leak; a count that plateaus just under the limit under load is a sizing problem:

$ while sleep 10; do printf '%s %s\n' "$(date +%T)" "$(ls /proc/$PID/fd | wc -l)"; done

3. Identify what is being leaked, which points straight at the code path:

$ ls -l /proc/$PID/fd | awk '{print $NF}' | sed 's/[0-9]*$//' | sort | uniq -c | sort -rn
    812 socket:[
    103 /var/log/app/session-
     44 pipe:[

812 sockets says connections are not being closed — usually a missing close() in an error path, or an HTTP client created per-request instead of being reused. Sockets stuck in CLOSE_WAIT confirm it: ss -tan state close-wait | wc -l. CLOSE_WAIT means the peer closed and the application never called close() — that is unambiguously an application bug, not a network one.

4. Fix appropriately. For a genuine leak, the fix is in the code — use language-level scoping (with, defer, try-with-resources) so descriptors close on every path including exceptions. Raising the limit only delays the failure. For legitimate high concurrency, raise it properly in the unit file rather than via ulimit in a wrapper, since systemd services do not inherit shell limits:

[Service]
LimitNOFILE=65536

5. Prevent recurrence. Alert on descriptor count as a fraction of the limit rather than waiting for EMFILE, and remember inherited descriptors: a leaked fd is passed to every child at fork, so a daemon that spawns workers multiplies the problem. Marking descriptors close-on-exec (O_CLOEXEC) is the correct default in any program that forks.

Senior: Design a robust logging setup for a script that must capture everything, show progress, and preserve exit status.

Four requirements that pull against each other: capture stdout and stderr to a file, keep them distinguishable, show live progress on the terminal, and report the real exit status rather than tee's. A naive cmd &> log satisfies only the first.

The core structure — redirect the whole script once, through a process substitution so buffering does not defeat live output:

#!/usr/bin/env bash
set -euo pipefail

LOG=/var/log/deploy/$(date +%Y%m%d-%H%M%S).log
mkdir -p "$(dirname "$LOG")"

# Save the real terminal so we can still write to it deliberately
exec 3>&1 4>&2

# Everything from here goes to the log AND the terminal, timestamped
exec 1> >(stdbuf -oL ts '[%Y-%m-%d %H:%M:%S]' | tee -a "$LOG" >&3)
exec 2> >(stdbuf -oL ts '[%Y-%m-%d %H:%M:%S] [ERR]' | tee -a "$LOG" >&4)

echo "deployment starting"
echo "a warning" >&2

Redirecting the script's own fd 1 and 2 once, rather than appending | tee to every command, means every subsequent command and every child process is captured automatically — including output from programs you did not anticipate.

Preserving exit status is where most implementations fail. Any cmd | tee log reports tee's status:

run() {
  local status
  "$@"; status=$?                       # status of the real command
  if [ "$status" -ne 0 ]; then
    printf 'FAILED (%d): %s\n' "$status" "$*" >&2
  fi
  return "$status"
}
run ./migrate.sh || exit $?

Where a pipeline is unavoidable, set -o pipefail plus ${PIPESTATUS[0]} gets the true status.

Flush before exiting. Process substitution writers are asynchronous, so a script can exit before tee has written the last lines — losing exactly the error you most want. Close the descriptors and wait:

cleanup() {
  local status=$?
  exec 1>&3 2>&4 3>&- 4>&-           # restore, closing the substitutions
  wait                                  # let tee finish writing
  exit "$status"
}
trap cleanup EXIT

What I would do instead in production. All of the above is a reimplementation of what the platform already provides. Under systemd, a service's stdout and stderr go to the journal automatically, tagged, timestamped, rotated, and queryable by unit and priority — journalctl -u deploy -p err beats any of this. I would use this pattern for a standalone script run by hand, and a systemd unit or timer for anything scheduled, so the logging is the platform's problem. See systemd and Logs, Journals & Time.

🏋️ Exercises

1 (easy): Prove that redirection order determines where stderr goes.
Solution 
$ both() { echo "OUT: data"; echo "ERR: problem" >&2; }

# Correct order
$ both > /tmp/a.txt 2>&1
$ cat /tmp/a.txt
OUT: data
ERR: problem

# Reversed order — stderr escapes to the terminal
$ both 2>&1 > /tmp/b.txt
ERR: problem
$ cat /tmp/b.txt
OUT: data

Confirm what the process actually sees by inspecting its descriptor table in each case:

$ sh -c 'ls -l /proc/self/fd' > /tmp/c.txt 2>&1; grep -E ' [12] ->' /tmp/c.txt
l-wx------ 1 alice alice 64 ... 1 -> /tmp/c.txt
l-wx------ 1 alice alice 64 ... 2 -> /tmp/c.txt        # both to the file

$ sh -c 'ls -l /proc/self/fd' 2>&1 > /tmp/d.txt; grep -E ' [12] ->' /tmp/d.txt
l-wx------ 1 alice alice 64 ... 1 -> /tmp/d.txt
lrwx------ 1 alice alice 64 ... 2 -> /dev/pts/2        # fd 2 kept the terminal

The descriptor table is the ground truth: 2>&1 copied fd 1's then-current value. Reading it as "make 2 follow 1" is the misunderstanding; it is "make 2 a copy of 1, now".

The bash shorthand avoids the ordering question entirely:

$ both &> /tmp/e.txt && cat /tmp/e.txt
OUT: data
ERR: problem
2 (easy): Show that a pipe is a fixed-size buffer that blocks its writer.
Solution

Start a writer with a deliberately slow reader and inspect its kernel state:

$ (dd if=/dev/zero bs=1M count=100 2>/tmp/dd.err | (sleep 30; cat >/dev/null)) &
$ sleep 2
$ pid=$(pgrep -f 'dd if=/dev/zero')
$ ps -o pid,stat,wchan:20,cmd -p "$pid"
    PID STAT WCHAN                CMD
  59310 S    pipe_write           dd if=/dev/zero bs=1M count=100

pipe_write in WCHAN is the proof: dd is asleep inside the kernel's pipe write path, not consuming CPU, waiting for the reader. It wrote 64KB and stopped.

Measure the buffer size directly:

$ cat /proc/sys/fs/pipe-max-size
1048576
# Default per-pipe capacity is 64KB (16 pages):
$ python3 -c "
import os, fcntl
r, w = os.pipe()
print('capacity:', fcntl.fcntl(w, 1032))       # F_GETPIPE_SZ
"
capacity: 65536

Now show the SIGPIPE half — what happens when the reader disappears:

$ kill %1 2>/dev/null
$ yes | head -2
y
y
$ echo "${PIPESTATUS[@]}"
141 0

yes exited 141 = 128+13 (SIGPIPE). It did not "finish"; the kernel killed it when head closed the read end. This is the mechanism that stops infinite producers, and it is why set -o pipefail can make a perfectly correct producer | head pipeline report failure.

3 (medium): Defeat output buffering in a multi-stage pipeline.
Solution

Build a slow producer and observe the buffering:

$ cat > /tmp/emit.sh <<'EOF'
#!/usr/bin/env bash
for i in $(seq 1 60); do echo "line $i STATUS=ok"; sleep 0.5; done
EOF
$ chmod +x /tmp/emit.sh

# Direct to terminal: line-buffered, appears immediately
$ timeout 3 /tmp/emit.sh
line 1 STATUS=ok
line 2 STATUS=ok
...

# Through grep: silence
$ timeout 5 /tmp/emit.sh | grep STATUS
                          # nothing for the full 5 seconds

grep saw the data but held its own output in a 4KB buffer. Fix the stage whose output feeds the next pipe:

$ timeout 5 /tmp/emit.sh | grep --line-buffered STATUS
line 1 STATUS=ok
line 2 STATUS=ok          # live

Three stages — every one buffers. Fixing only grep is not enough:

$ timeout 5 /tmp/emit.sh | grep --line-buffered STATUS | cut -d' ' -f2 | cat
                          # still nothing: cut is buffering now

$ timeout 5 /tmp/emit.sh | grep --line-buffered STATUS | stdbuf -oL cut -d' ' -f2 | cat
1
2                         # live

The generic hammer when a tool has no flag of its own:

$ timeout 5 stdbuf -oL /tmp/emit.sh | stdbuf -oL awk '{print $2}' | cat
1
2

Note the exception worth knowing: stdbuf works by LD_PRELOADing a library that changes libc's defaults, so it has no effect on programs that call setvbuf() explicitly (like tee) or on statically linked/Go binaries. When it fails, allocating a pty with unbuffer is the fallback that always works, because the program's own isatty() check then returns true.

4 (medium): Use custom file descriptors to capture output while still displaying it, preserving the real exit status.
Solution

The naive attempt loses the status:

$ output=$(sh -c 'echo hello; exit 3' | tee /dev/tty); echo "status=$?"
hello
status=0                  # tee's status, not the command's

Correct version — save the terminal on fd 3 and read PIPESTATUS:

$ exec 3>&1
$ output=$(sh -c 'echo hello; echo oops >&2; exit 3' 2>&1 | tee /dev/fd/3)
$ status=${PIPESTATUS[0]}
$ exec 3>&-
hello
oops
$ echo "captured=[$output] status=$status"
captured=[hello
oops] status=3

Both displayed live and captured, with the real status. Using /dev/fd/3 rather than /dev/tty matters because it still works under cron or in a container where no controlling terminal exists.

Keeping the streams separate while capturing both — the harder variant:

$ exec 3>&1 4>&2
$ out=$(sh -c 'echo to-stdout; echo to-stderr >&2; exit 5' \
        2> >(tee /tmp/err.log >&4) | tee /tmp/out.log)
$ status=${PIPESTATUS[0]}
$ exec 3>&- 4>&-
to-stderr
to-stdout
$ echo "status=$status"; echo "err file: $(cat /tmp/err.log)"
status=5
err file: to-stderr

The subtlety worth knowing: process substitution writers are asynchronous, so the script can exit before tee flushes. In a real script, add wait after closing the descriptors — otherwise the last few lines, often the error you care about, are silently lost.

5 (hard): Build a two-way communication channel between processes using named pipes, and explain the deadlock risk.
Solution 
$ mkfifo /tmp/req /tmp/resp
$ ls -l /tmp/req /tmp/resp
prw-r--r-- 1 alice alice 0 Aug  8 15:30 /tmp/req
prw-r--r-- 1 alice alice 0 Aug  8 15:30 /tmp/resp

A server that reads requests and writes responses:

$ cat > /tmp/server.sh <<'EOF'
#!/usr/bin/env bash
# Hold the write end open ourselves so the FIFO never sees "all writers closed"
exec 3> /tmp/resp
while read -r line < /tmp/req; do
  [ "$line" = "QUIT" ] && break
  printf 'processed: %s\n' "${line^^}" >&3
done
exec 3>&-
EOF
$ chmod +x /tmp/server.sh && /tmp/server.sh &

$ echo "hello" > /tmp/req
$ read -r reply < /tmp/resp; echo "$reply"
processed: HELLO
$ echo "world" > /tmp/req
$ read -r reply < /tmp/resp; echo "$reply"
processed: WORLD
$ echo "QUIT" > /tmp/req

The rendezvous behaviour that causes most FIFO confusion — opening blocks until the other end appears:

$ timeout 2 sh -c 'echo test > /tmp/req'; echo "exit=$?"
exit=124                  # timed out: blocked in open(), no reader present

A FIFO stores nothing. It is a rendezvous point, not a queue, which is why its size is always 0.

The deadlock. Two processes each writing before reading will hang forever, because both block in open() waiting for the other to open the opposite end:

# Process A:  exec 3> /tmp/req   ; exec 4< /tmp/resp
# Process B:  exec 3> /tmp/resp  ; exec 4< /tmp/req
#             ^ both block on their write-open; neither reaches its read-open

Confirm a hung process is stuck exactly there:

$ cat /proc/$PID/wchan; echo
pipe_wait

Three ways to avoid it: enforce a strict, opposite open order on the two sides (A opens read-then-write, B opens write-then-read); open with O_NONBLOCK so open() returns immediately; or use a socketpair/Unix socket instead, which is bidirectional in one object and has none of this ordering hazard.

The honest assessment: FIFOs are a poor fit for request/response. There is no message framing (a partial line can interleave), no way to tell which client sent what, and the reader gets EOF whenever the last writer closes — which is why the server above must hold its own write descriptor open. A Unix domain socket solves all three and is what any real implementation should use. FIFOs earn their place for simple one-way streaming and as a synchronisation barrier.

Cleanup: rm -f /tmp/req /tmp/resp.

6 (hard): Diagnose a pipeline that hangs, and identify which stage is responsible.
Solution

Construct a realistic hang — a reader that never gets EOF because a descriptor is held open:

$ mkfifo /tmp/hang
$ exec 5> /tmp/hang           # this shell holds the write end open
$ cat /tmp/hang &
[1] 60210
$ sleep 1; ps -o pid,stat,wchan:20,cmd -p 60210
    PID STAT WCHAN                CMD
  60210 S    pipe_read            cat /tmp/hang

cat waits forever: data may still arrive because a writer exists. It will only see EOF when every write descriptor closes.

The systematic diagnosis for any hung pipeline:

1. Find which stage is blocked and on what.

$ ps -o pid,stat,wchan:20,cmd --ppid $$ | grep -v grep
    PID STAT WCHAN                CMD
  60210 S    pipe_read            cat /tmp/hang

pipe_read = waiting for input. pipe_write = blocked because the buffer is full and nobody is reading. Those two states point in opposite directions and immediately halve the search.

2. Confirm with strace — silence means genuinely blocked, not spinning:

$ timeout 3 strace -p 60210
strace: Process 60210 attached
read(3, <unfinished ...>

3. Identify who else holds the descriptor, which is the actual root cause here:

$ ls -l /proc/60210/fd/3
lr-x------ 1 alice alice 64 Aug  8 15:45 /proc/60210/fd/3 -> /tmp/hang
$ fuser -v /tmp/hang 2>&1
                     USER   PID ACCESS COMMAND
/tmp/hang:           alice 59880 F....  bash        ← the shell holds the write end
                     alice 60210 f....  cat

That identifies the culprit precisely: our own shell, via fd 5.

$ exec 5>&-              # release it
[1]+  Done                    cat /tmp/hang

The three hang patterns worth recognising:

WCHANMeaningUsual cause
pipe_readWaiting for inputA writer never closes, or the producer is itself blocked upstream
pipe_writeBuffer full, blockedThe consumer is slow, dead, or never reads
pipe_waitBlocked in open() on a FIFOThe other end has not opened — the rendezvous deadlock

The most common real-world instance of this is a background daemon that inherited the write end of a pipe it does not use. Since descriptors survive fork, an unrelated child keeps the pipe alive and the reader hangs indefinitely. Marking descriptors O_CLOEXEC — or explicitly closing them before spawning children — prevents the entire class of bug.

Cleanup: rm -f /tmp/hang.

🎯 Key Takeaways

  • fds 0/1/2 are conventions, not kernel magic; stdout carries data and stderr carries diagnostics so redirecting results never swallows errors.
  • 2>&1 means "copy fd 1's current target into fd 2" — redirections apply left to right, which is why > file 2>&1 works and the reverse does not.
  • The shell truncates a redirect target before the command runs, so sort file > file empties it — write to a temp file and rename.
  • A pipe carries stdout only, so cmd | grep error misses stderr; use 2>&1 | or |&.
  • A pipe is a 64KB kernel ring buffer with no disk backing; when it fills the writer blocks in pipe_write, giving backpressure for free.
  • When the reader closes, the writer gets SIGPIPE and exits 141 — this is how head stops an infinite producer, and it can trip pipefail.
  • Writes under 4096 bytes are atomic, so several processes can safely append short lines to one pipe.
  • libc switches stdout from line-buffered to fully buffered when it is not a terminal, which is why piped output arrives in bursts — fix with stdbuf -oL, --line-buffered, or python -u.
  • Every stage of a pipeline buffers independently; fixing only one stage does not restore live output.
  • exec 3>file opens a descriptor once for many writes, and exec 3>&1 saves stdout so it can be restored later.
  • Descriptors are inherited across fork and survive exec unless marked close-on-exec — leaks accumulate until EMFILE, and a leaked write end makes a reader hang forever.
  • Quote the here-doc delimiter (<<'EOF') when generating scripts, or the outer shell expands variables meant for the inner one.
  • Process substitution <(cmd) gives a stream a filename — the basis of diff <(...) <(...) and of feeding a loop without a subshell.
