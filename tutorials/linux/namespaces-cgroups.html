Namespaces, cgroups & Containers Production Skills

What you'll master: that a container is not a thing the kernel knows about but a process with restricted views, what each of the seven namespaces isolates and what it deliberately does not, how cgroup v2 enforces memory and CPU limits and why CPU throttling causes latency spikes at 30% average utilisation, why user namespaces are the difference between root-in-a-container and root, how overlay filesystems make images cheap, and how to build a container from scratch with nothing but shell commands. Prerequisites: Processes, fork & exec and Users, Groups & Permissions.

Part 1 — There Is No Such Thing as a Container

The kernel has no container object, no container syscall, and no container ID. A container is a normal process that was started with three kinds of restriction applied at once.

MechanismControlsAnswers
NamespacesWhat the process can see"Which processes, mounts, network interfaces exist?"
cgroupsWhat the process can use"How much CPU, memory, I/O?"
Capabilities, seccomp, LSMWhat the process can do"Which privileged operations are permitted?"
$ docker run -d --name web nginx
$ docker inspect -f '{{.State.Pid}}' web
69200
$ ps -p 69200 -o pid,ppid,comm            # just a process on the host
  PID  PPID COMMAND
69200 69180 nginx
$ sudo ls -l /proc/69200/ns/
lrwxrwxrwx 1 root root 0 cgroup -> 'cgroup:[4026532501]'
lrwxrwxrwx 1 root root 0 ipc    -> 'ipc:[4026532442]'
lrwxrwxrwx 1 root root 0 mnt    -> 'mnt:[4026532440]'
lrwxrwxrwx 1 root root 0 net    -> 'net:[4026532445]'
lrwxrwxrwx 1 root root 0 pid    -> 'pid:[4026532443]'
lrwxrwxrwx 1 root root 0 user   -> 'user:[4026531837]'      # SAME as the host's
lrwxrwxrwx 1 root root 0 uts    -> 'uts:[4026532441]'

Those inode numbers are the namespaces. Two processes sharing a number share that namespace. Note the user namespace matches the host's — the default for Docker, and the reason root inside the container is genuinely root on the host if it ever escapes.

🔑 Containers do not contain, in the way a VM does. A VM has a separate kernel; a container shares yours. Every container on the host runs against the same kernel, the same scheduler, the same page cache, and the same syscall surface — so a kernel privilege-escalation bug is a container escape. That is the fundamental security difference, and it is why untrusted multi-tenant workloads use VMs, gVisor, or Firecracker rather than plain containers.

Part 2 — The Seven Namespaces

NamespaceIsolatesConsequence
pidProcess IDsYour process is PID 1; you cannot see or signal host processes
mntMount tableA private filesystem view — this is what a container image is
netInterfaces, routes, ports, firewallOwn lo, own port space — two containers can both bind :80
utsHostname, domain namehostname differs from the host's
ipcSysV IPC, POSIX message queuesShared memory segments are private
userUID/GID mappingsRoot inside maps to unprivileged outside
cgroupThe cgroup root as seen in /procHides the host's cgroup hierarchy

unshare creates them directly — no container runtime required:

$ sudo unshare --pid --fork --mount-proc bash
# ps aux
USER  PID %CPU %MEM COMMAND
root    1  0.0  0.0 bash                    # PID 1 in the new namespace
root    9  0.0  0.0 ps aux
# echo $$
1
# exit
$ ps aux | wc -l
312                                          # the host still has everything

--mount-proc matters: without a fresh /proc mount, ps reads the host's /proc and shows host processes even though signalling them would fail. It is the clearest demonstration that namespaces isolate views, and that a stale view is confusing rather than secure.

$ sudo unshare --uts bash -c 'hostname container-01; hostname'
container-01
$ hostname
laptop                                       # host unaffected

$ sudo unshare --net bash -c 'ip link show'
1: lo: <LOOPBACK> mtu 65536 state DOWN       # only loopback, and it is down

Joining an existing namespace is how you debug a container that has no shell or no tools of its own — nsenter runs a host binary inside the container's view:

$ PID=$(docker inspect -f '{{.State.Pid}}' web)
$ sudo nsenter -t $PID -n ss -tlnp          # host's ss, container's network
LISTEN 0 511 0.0.0.0:80 users:(("nginx",pid=69200,fd=6))
$ sudo nsenter -t $PID -n -p -m /bin/bash   # network + pid + mount

Part 3 — cgroup v2: Limits That Actually Bind

cgroups are a filesystem tree at /sys/fs/cgroup. A process belongs to exactly one cgroup per hierarchy, and limits apply to the whole subtree — including anything it forks.

$ cat /proc/self/cgroup
0::/user.slice/user-1000.slice/session-3.scope

$ ls /sys/fs/cgroup/system.slice/nginx.service/
cgroup.procs  cpu.max  cpu.stat  io.max  memory.current  memory.events  memory.max  pids.max
Controller filePurpose
memory.max / memory.highHard limit (OOM kill) / soft limit (throttle and reclaim)
memory.current / memory.peakCurrent usage / high-water mark
memory.eventsCounters: high, max, oom, oom_kill
cpu.maxQUOTA PERIOD in microseconds — "200000 100000" = 2 cores
cpu.statnr_throttled, throttled_usec — the critical metrics
io.maxPer-device IOPS and bandwidth caps
pids.maxProcess count limit — fork-bomb protection
*.pressurePer-cgroup PSI, as in Performance Debugging
$ sudo mkdir /sys/fs/cgroup/demo
$ echo "100000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max      # exactly 1 CPU
$ echo "256M"          | sudo tee /sys/fs/cgroup/demo/memory.max
$ echo $$              | sudo tee /sys/fs/cgroup/demo/cgroup.procs # move this shell in

CPU throttling is the subtlest production problem in this lesson. cpu.max is enforced per 100 ms period, not smoothed over time. A service that uses 30% CPU on average but bursts across several threads will exhaust its quota early in a period and then be frozen until the next one — producing latency spikes with idle-looking average utilisation:

$ cat /sys/fs/cgroup/system.slice/myapp.service/cpu.stat
usage_usec 412033921
nr_periods 184203
nr_throttled 41208            # throttled in 22% of all periods
throttled_usec 8241033        # 8.2 seconds of frozen time

nr_throttled rising is a real finding even at low average CPU. The fixes: raise the quota, reduce thread-pool concurrency so the burst is smaller, or use cpu.weight (relative shares, never throttled) instead of a hard quota for latency-sensitive services.

❌ Setting a CPU limit of 0.5 cores because the service averages 20%. Average utilisation says nothing about burst shape. A request that briefly needs four threads exhausts a 50 ms quota in 12 ms and then waits 88 ms for the next period — a p99 latency cliff that appears nowhere in the CPU graph.

✅ Check cpu.stat's nr_throttled before and after setting a limit. For latency-sensitive services prefer cpu.weight (Kubernetes CPU requests) which guarantees a share under contention without ever freezing the process, and reserve hard quotas (limits) for batch work where throughput matters more than tail latency.

Part 4 — User Namespaces and the Root Problem

By default, root in a container is UID 0 on the host. Namespaces restrict what that root can see, and capabilities restrict what it can do, but the moment either is bypassed you have a host root process.

$ docker run --rm -it -v /:/host alpine sh
/ # id
uid=0(root) gid=0(root)
/ # cat /host/etc/shadow | head -1        # host's shadow file, because UID 0 is UID 0
root:$6$xyz...

User namespaces break that equivalence. They map a UID range so root inside is an unprivileged UID outside:

$ unshare --user --map-root-user bash        # no sudo needed!
# id
uid=0(root) gid=0(root)                      # root INSIDE
# cat /proc/self/uid_map
         0       1000          1             # container 0 → host 1000
# cat /etc/shadow
cat: /etc/shadow: Permission denied          # because on the host you are 1000

$ ps -o uid,comm -p $(pgrep -f 'unshare --user')
  UID COMMAND
 1000 bash                                   # the host sees an ordinary user
ConfigurationContainer root maps toEscape means
Docker defaultHost UID 0Full host root
--userns-remapAn unprivileged host UIDAn unprivileged host user
Rootless PodmanYour own UIDYour own account, nothing more
--privilegedHost UID 0, all capabilities, all devicesNot a boundary at all

Capabilities split root's powers into ~40 separable pieces, so a process can bind port 80 without being able to load kernel modules — see Users, Groups & Permissions:

$ docker run --rm --cap-drop=ALL --cap-add=NET_BIND_SERVICE nginx
$ grep CapEff /proc/69200/status
CapEff:	00000000a80425fb
$ capsh --decode=00000000a80425fb | tr ',' '\n' | head -5
cap_chown
cap_dac_override
cap_net_bind_service

The escape vectors worth knowing, because each is a real misconfiguration seen in the wild:

MisconfigurationWhy it is an escape
-v /var/run/docker.sock:/...Can launch a privileged container — equivalent to host root
--privilegedAll capabilities and all host devices; trivially escapable
--pid=hostCan see and signal host processes, read their /proc
--cap-add=SYS_ADMINMount filesystems; several documented escape paths
-v /:/hostThe entire host filesystem, writable
Running as UID 0 with no user namespaceAny kernel bug becomes host root

Part 5 — Images, Overlays, and the Container Filesystem

A container image is a stack of read-only layers plus one writable layer, combined by overlayfs into a single view. This is why pulling the tenth image based on the same base is nearly free.

   merged (what the container sees)
       ▲
   upper  ← writable layer: all changes land here
       │
   lower3 ← app layer      (read-only, shared)
   lower2 ← dependencies   (read-only, shared)
   lower1 ← base image     (read-only, shared by every container using it)

$ mkdir -p /tmp/ovl/{lower,upper,work,merged}
$ echo "from the base image" > /tmp/ovl/lower/config.txt
$ sudo mount -t overlay overlay \
>   -o lowerdir=/tmp/ovl/lower,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work \
>   /tmp/ovl/merged
$ cat /tmp/ovl/merged/config.txt
from the base image
$ echo "modified" > /tmp/ovl/merged/config.txt        # copy-up happens here
$ cat /tmp/ovl/lower/config.txt
from the base image                                    # lower layer untouched
$ cat /tmp/ovl/upper/config.txt
modified                                               # the change lives in upper

Copy-up is the performance consequence: modifying one byte of a 2 GB file in a lower layer copies the whole file to the upper layer first. Databases and other write-heavy workloads must use a volume — a real filesystem bind-mounted in — rather than the overlay:

$ docker run -v pgdata:/var/lib/postgresql/data postgres     # named volume, no overlay

Deleting a file from a lower layer cannot actually delete it — overlayfs writes a "whiteout" marker in the upper layer instead. That is why RUN rm secrets.txt in a Dockerfile does not remove the secret: the earlier layer still contains it, and anyone with the image can read it:

$ docker history --no-trunc myimage | head
$ docker save myimage | tar -x -O --wildcards '*/layer.tar' | tar -tv | grep secret

Part 6 — Building a Container by Hand

Assembling one from primitives makes the abstraction concrete — this is genuinely all a runtime does:

# 1. A root filesystem
$ mkdir -p /tmp/box/rootfs
$ docker export $(docker create alpine) | tar -x -C /tmp/box/rootfs

# 2. A cgroup with limits
$ sudo mkdir -p /sys/fs/cgroup/box
$ echo "100000 100000" | sudo tee /sys/fs/cgroup/box/cpu.max
$ echo "128M"          | sudo tee /sys/fs/cgroup/box/memory.max
$ echo "64"            | sudo tee /sys/fs/cgroup/box/pids.max

# 3. Namespaces + chroot, with the process placed in the cgroup
$ sudo unshare --pid --mount --uts --ipc --net --fork --mount-proc \
>   sh -c 'echo $$ > /sys/fs/cgroup/box/cgroup.procs;
>          hostname box-01;
>          exec chroot /tmp/box/rootfs /bin/sh'
/ # hostname
box-01
/ # ps aux
PID   USER     COMMAND
    1 root     /bin/sh                       # PID 1
/ # ip link
1: lo: <LOOPBACK> mtu 65536 state DOWN       # isolated network

That is a container: a chroot for the filesystem, namespaces for the views, a cgroup for the limits. Docker adds image management, networking (a veth pair into a bridge), a supervisor, and a friendlier CLI — but the isolation is exactly these three kernel features.

Note chroot is not a security boundary. A root process can escape it in a dozen lines of C; real runtimes use pivot_root, which detaches the old root entirely. And the network above is unusable — connecting it means creating a veth pair, moving one end into the namespace, and adding NAT rules, which is precisely what a container network driver does.

Interview Questions

Beginner: What is a container, at the kernel level?

A normal Linux process with three kinds of restriction applied. The kernel has no container object at all — no container syscall, no container ID.

  • Namespaces control what it can see: its own process list, mount table, network interfaces, hostname.
  • cgroups control what it can use: CPU, memory, I/O, process count.
  • Capabilities and seccomp control what it can do: which privileged operations and which syscalls are permitted.
$ docker inspect -f '{{.State.Pid}}' web
69200
$ ps -p 69200 -o pid,comm            # an ordinary host process
$ sudo ls /proc/69200/ns/            # with its own namespaces
cgroup ipc mnt net pid user uts

The consequence that matters is the shared kernel. A VM runs its own kernel, so the hypervisor boundary is narrow and hardware-enforced. Every container on a host shares one kernel and one syscall surface, so a kernel privilege-escalation bug is a container escape. That is why untrusted multi-tenant workloads use VMs, gVisor, or Firecracker rather than plain containers.

You can build one by hand with unshare, chroot, and a cgroup directory — Docker adds image management, networking and tooling on top, not isolation of a different kind.

Beginner: Name the namespaces and what each isolates.

Seven, each isolating one kind of global resource:

NamespaceIsolates
pidProcess IDs — your process is PID 1 and cannot see host processes
mntThe mount table — this is what makes an image a filesystem
netInterfaces, routes, ports, firewall rules — own port space
utsHostname and domain name
ipcSysV IPC and POSIX message queues
userUID/GID mappings — root inside can be unprivileged outside
cgroupThe cgroup root visible in /proc
$ sudo unshare --pid --fork --mount-proc bash
# ps aux
root  1  bash              # PID 1 in the new namespace

The user namespace is the security-critical one, and it is the one Docker does not enable by default — which is why container root is host UID 0 in a standard setup.

Two practical notes. Namespaces are composable: you can use just one, and tools do (--net=host shares the host's network while isolating everything else). And joining an existing namespace with nsenter -t PID -n is how you debug a container that has no shell or no tools of its own.

Mid: A container is being OOM-killed but the host has plenty of free memory. Explain.

The kill is coming from the cgroup OOM killer at memory.max, not the system-wide one. The container exceeded its own limit while the host was nowhere near exhausted — which is exactly why host-level memory monitoring misses these entirely.

$ cat /sys/fs/cgroup/system.slice/myapp.service/memory.events
low 0
high 4821          # throttled at memory.high this many times
max 12
oom 3
oom_kill 3         # three processes killed by the cgroup limit
$ dmesg -T | grep -i 'memory cgroup out of memory'

memory.events is the definitive record, and the dmesg wording differs — "Memory cgroup out of memory", not plain "Out of memory".

The three causes I would check, in order:

1. The runtime does not know the limit. Older JVMs and Node read the host's RAM and size their heap from it, instantly exceeding a small container limit. Fix with -XX:MaxRAMPercentage=70 or --max-old-space-size, leaving ~30% beyond the heap for thread stacks, metaspace and native buffers.

2. Page cache counts toward the limit. In cgroup v2 file cache is charged to the cgroup, so a container doing heavy file I/O can be killed for cache it never considered "its" memory. I/O-heavy workloads need explicit headroom.

3. A genuine leak or an under-sized limit — distinguished by whether memory.current grows monotonically or plateaus, as Memory covers.

The configuration fix regardless of cause is two limits, not one: MemoryHigh below MemoryMax gives a throttling warning band — a rising high counter with zero kills means the container is being reclaimed constantly and presents as unexplained slowness, which is a much better signal than a sudden death.

Mid: Why is running as root inside a container dangerous, and how do user namespaces help?

Because without a user namespace, UID 0 inside is UID 0 on the host. Namespaces restrict what that root can see and capabilities restrict what it can do, but the identity is the same — so any escape, kernel bug, or misconfigured mount gives full host root.

$ docker run --rm -v /:/host alpine cat /host/etc/shadow | head -1
root:$6$xyz...                            # host's shadow file

That is not an exploit; it is the default behaviour of a bind mount plus UID 0.

User namespaces remap the range, so root inside corresponds to an unprivileged UID outside:

$ unshare --user --map-root-user bash     # note: no sudo required
# id
uid=0(root) gid=0(root)                   # root INSIDE
# cat /proc/self/uid_map
         0       1000          1          # inside 0 → outside 1000
# cat /etc/shadow
cat: /etc/shadow: Permission denied       # on the host you are just user 1000

Now an escape yields an ordinary user account, not the machine.

In practice there are three ways to get this: Docker's --userns-remap, rootless Podman (where the whole daemon runs as your user), or simply not running as root — USER 1000 in the Dockerfile, which is the cheapest and most portable step.

Layer capabilities on top, since even non-root processes can hold privileges: --cap-drop=ALL --cap-add=NET_BIND_SERVICE grants only the ability to bind a low port, and --security-opt=no-new-privileges prevents setuid binaries escalating.

The limitation worth stating: user namespaces complicate volume permissions, because file ownership on the host is in the outer UID range. That friction is the main reason the default is still to run as root, and it is worth paying anyway.

Senior: A containerised service has p99 spikes but averages only 30% CPU. Diagnose it.

Average utilisation and tail latency are almost unrelated, and this specific pattern — low average, bad p99, in a container — has a prime suspect: CFS quota throttling.

1. Check cpu.stat first, because it settles it in one command:

$ cat /sys/fs/cgroup/system.slice/myapp.service/cpu.stat
usage_usec 412033921
nr_periods 184203
nr_throttled 41208            # throttled in 22% of periods
throttled_usec 8241033        # 8.2 seconds frozen

The mechanism: cpu.max is enforced per 100 ms period, not smoothed. With a limit of 0.5 CPU the container gets 50 ms of CPU time per period. A request that briefly uses four threads consumes that in ~12 ms and is then frozen for the remaining 88 ms. Average utilisation is 30%; individual requests take an extra 88 ms.

2. Confirm the burst shape rather than assuming it:

$ cat /sys/fs/cgroup/system.slice/myapp.service/cpu.pressure
some avg10=34.20 avg60=28.11
$ nproc                                  # the runtime may size pools from HOST cores
$ pidstat -t -u -p $(pgrep -o myapp) 1 5 | awk '$8>50'

A runtime that sized its thread pool or GC threads from nproc — which reports host cores, not the quota — will burst far wider than the quota allows. That is a very common contributor.

3. The fixes, in order of preference:

  • Use cpu.weight instead of a quota for latency-sensitive services (Kubernetes CPU requests without limits). Weight guarantees a share under contention but never freezes the process.
  • Raise the quota to cover the burst, accepting lower density.
  • Reduce concurrency inside so the burst fits: bound the thread pool, set GC threads explicitly, tell the runtime the real CPU count.

4. Rule out the alternatives before committing, since the same symptom has other causes: GC pauses (check the runtime's own GC log), lock contention (off-CPU profiling, as in Performance Debugging), memory high throttling (memory.events), noisy neighbours (%steal), and I/O queueing.

5. Verify by prediction: if throttling is the cause, removing the limit should drop p99 and take nr_throttled to zero together. If p99 does not move, the hypothesis was wrong and I would revert rather than leave a capacity change in place on a guess.

Senior: Design container isolation for running untrusted user-submitted code.

I would start by stating the honest constraint: standard containers are not a sufficient boundary for untrusted code, because the kernel is shared and a single privilege-escalation bug is a full escape. So the design is defence in depth, with a stronger boundary underneath.

1. Choose the outer boundary first. For genuinely untrusted code that means a VM-backed sandbox — Firecracker microVMs (a separate kernel, ~125 ms boot), gVisor (a userspace kernel intercepting syscalls, roughly 10–30% overhead), or Kata Containers. Everything below is hardening inside that, not a substitute for it.

2. Then apply every container restriction:

docker run \
  --user 65534:65534 \                    # never root
  --userns=host --security-opt=userns=remap \
  --read-only --tmpfs /tmp:size=64m,noexec \
  --cap-drop=ALL \
  --security-opt=no-new-privileges \
  --security-opt seccomp=strict.json \    # allowlist, not denylist
  --network=none \                        # no network at all if possible
  --pids-limit=64 \
  --memory=256m --memory-swap=256m \      # no swap: a clean OOM kill
  --cpus=0.5 \
  --ulimit nofile=64:64 --ulimit fsize=10000000 \
  sandbox-image

3. Bound everything that can be exhausted. Untrusted code will fork-bomb, allocate, spin, and fill disks — deliberately or accidentally. pids.max stops fork bombs, memory.max without swap gives a clean kill rather than host-wide thrashing, and ulimit fsize caps file creation. A hard wall-clock timeout enforced from outside is essential, because code that never returns is the common case.

4. Seccomp as an allowlist. The default Docker profile blocks ~44 syscalls; for untrusted code I want the inverse — permit the ~50 syscalls the workload actually needs and deny the rest. Most kernel CVEs live in syscalls no normal program calls.

5. Network isolation by default. --network=none where the workload permits it. If egress is required, an explicit allowlist through a proxy, never open internet — otherwise the sandbox is a free crypto miner and an SSRF pivot into the internal network.

6. Assume compromise and design the blast radius. One container per submission, never reused; a dedicated node pool with no cloud credentials and no metadata service access (that endpoint is a standard escalation path); short-lived nodes; and monitoring for the signatures — sustained CPU, unexpected egress, syscall denials.

7. Keep the kernel patched, since that is the actual attack surface, and consider reducing it further with a minimal host distribution.

The summary I would give: containers provide resource control and operational convenience; the security boundary for untrusted code has to come from a separate kernel. Anyone claiming plain Docker is sufficient for arbitrary user code has not read the escape CVE history.

3 (medium): Enforce cgroup limits by hand and watch them bind.
Solution

1. Create a cgroup with three limits:

$ sudo mkdir -p /sys/fs/cgroup/demo
$ echo "50000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max     # 0.5 CPU
$ echo "128M"         | sudo tee /sys/fs/cgroup/demo/memory.max
$ echo "20"           | sudo tee /sys/fs/cgroup/demo/pids.max

2. CPU limit — a busy loop gets exactly half a core:

$ (while :; do :; done) &
$ echo $! | sudo tee /sys/fs/cgroup/demo/cgroup.procs
$ top -b -n 2 -p $! | tail -1
  PID USER  %CPU  COMMAND
69400 dhruv 49.8  bash              # capped at ~50%
$ cat /sys/fs/cgroup/demo/cpu.stat | grep -E 'nr_throttled|throttled_usec'
nr_throttled 184
throttled_usec 9204812              # throttling is visible and countable
$ kill %1

3. Memory limit — the OOM kill is scoped to the cgroup:

$ sudo systemd-run --scope -p MemoryMax=128M --unit=memtest \
>   python3 -c "
b = bytearray()
while True:
    b.extend(b'x' * 10_000_000)
    print(len(b)//1_000_000, 'MB', flush=True)
"
10 MB
...
120 MB
Killed
$ dmesg -T | tail -2 | head -1
[...] Memory cgroup out of memory: Killed process 69500 (python3)

Note the wording: "Memory cgroup out of memory", not plain "Out of memory" — the host was never short.

4. PID limit — fork-bomb protection:

$ sudo systemd-run --scope -p TasksMax=20 --unit=pidtest \
>   bash -c 'for i in $(seq 1 50); do sleep 30 & done; wait' 2>&1 | head -3
bash: fork: retry: Resource temporarily unavailable
bash: fork: Resource temporarily unavailable

Without this, a fork bomb inside a container takes down the host.

5. Demonstrate the burst-throttling problem — the subtle one:

$ sudo mkdir -p /sys/fs/cgroup/bursty
$ echo "50000 100000" | sudo tee /sys/fs/cgroup/bursty/cpu.max    # 0.5 CPU
$ cat > /tmp/bursty.py <<'EOF'
import threading, time
def burn(ms):
    t = time.monotonic()
    while time.monotonic() - t < ms/1000: pass
lat = []
for i in range(30):
    t0 = time.monotonic()
    ts = [threading.Thread(target=burn, args=(20,)) for _ in range(4)]   # 4-way burst
    [t.start() for t in ts]; [t.join() for t in ts]
    lat.append((time.monotonic()-t0)*1000)
    time.sleep(0.2)
lat.sort()
print(f"p50={lat[15]:.0f}ms p99={lat[29]:.0f}ms")
EOF
$ sudo sh -c 'echo $$ > /sys/fs/cgroup/bursty/cgroup.procs; exec python3 /tmp/bursty.py'
p50=182ms p99=241ms
$ cat /sys/fs/cgroup/bursty/cpu.stat | grep nr_throttled
nr_throttled 84

Without the limit:

$ python3 /tmp/bursty.py
p50=21ms p99=28ms

8× worse latency at an average CPU usage well under the 0.5-core limit. The work fits in the quota on average; the burst does not fit in a single 100 ms period.

Cleanup: sudo rmdir /sys/fs/cgroup/demo /sys/fs/cgroup/bursty; rm /tmp/bursty.py.

4 (medium): Build an overlay filesystem and observe copy-up and whiteouts.
Solution 
$ mkdir -p /tmp/ovl/{lower1,lower2,upper,work,merged}
$ echo "base config"    > /tmp/ovl/lower1/app.conf
$ echo "base readme"    > /tmp/ovl/lower1/README
$ dd if=/dev/zero of=/tmp/ovl/lower1/big.dat bs=1M count=100 2>/dev/null
$ echo "dependency lib" > /tmp/ovl/lower2/lib.so

Stack them — later lowerdirs are lower in the stack:

$ sudo mount -t overlay overlay \
>   -o lowerdir=/tmp/ovl/lower2:/tmp/ovl/lower1,upperdir=/tmp/ovl/upper,workdir=/tmp/ovl/work \
>   /tmp/ovl/merged
$ ls /tmp/ovl/merged
README  app.conf  big.dat  lib.so       # all layers, one view
$ du -sh /tmp/ovl/upper
0       /tmp/ovl/upper                  # writable layer is empty

Copy-up — modifying one byte copies the whole file:

$ echo "x" >> /tmp/ovl/merged/big.dat
$ du -sh /tmp/ovl/upper /tmp/ovl/lower1
101M    /tmp/ovl/upper                  # the ENTIRE 100 MB file was copied
100M    /tmp/ovl/lower1                 # original untouched
$ stat -c '%i %n' /tmp/ovl/lower1/big.dat /tmp/ovl/upper/big.dat
262149 /tmp/ovl/lower1/big.dat
262203 /tmp/ovl/upper/big.dat           # different inodes

This is why databases must use volumes: every write to a large file in a lower layer duplicates it first.

Whiteouts — deletion cannot really delete:

$ rm /tmp/ovl/merged/README
$ ls /tmp/ovl/merged
app.conf  big.dat  lib.so               # gone from the merged view
$ ls /tmp/ovl/lower1
README  app.conf  big.dat               # STILL THERE in the lower layer
$ ls -l /tmp/ovl/upper/README
c--------- 2 root root 0, 0 Aug 10 10:14 /tmp/ovl/upper/README
  ^                    ^^^^
  character device     0,0 = the whiteout marker

The security consequence: RUN rm secrets.txt in a Dockerfile does not remove the secret — the earlier layer still contains it and anyone with the image can extract it:

$ docker history --no-trunc myimage | grep -i secret
$ docker save myimage -o /tmp/img.tar && tar -tf /tmp/img.tar | head

The correct fixes are multi-stage builds (the secret never enters the final stage) or BuildKit secret mounts (--mount=type=secret), which are never written to a layer at all.

Sharing — the reason images are cheap:

$ mkdir -p /tmp/ovl/{upper2,work2,merged2}
$ sudo mount -t overlay overlay \
>   -o lowerdir=/tmp/ovl/lower2:/tmp/ovl/lower1,upperdir=/tmp/ovl/upper2,workdir=/tmp/ovl/work2 \
>   /tmp/ovl/merged2
$ du -sh /tmp/ovl/merged2 /tmp/ovl/upper2
101M    /tmp/ovl/merged2                # a full 101 MB view...
0       /tmp/ovl/upper2                 # ...costing zero extra bytes

Cleanup: sudo umount /tmp/ovl/merged /tmp/ovl/merged2; sudo rm -rf /tmp/ovl /tmp/img.tar.

5. Now demonstrate that chroot is not a security boundary. A root process inside can escape it — this is why real runtimes use pivot_root:

$ cat > /tmp/escape.c <<'EOF'
#include <sys/stat.h>
#include <unistd.h>
#include <stdio.h>
int main(void) {
    mkdir("/.esc", 0755);
    chroot("/.esc");                       // now cwd is OUTSIDE the new root
    for (int i = 0; i < 1000; i++) chdir("..");   // walk up to the real /
    chroot(".");                           // make the real root our root
    execl("/bin/sh", "sh", NULL);
    return 0;
}
EOF
$ gcc -static -o /tmp/box/rootfs/escape /tmp/escape.c
$ sudo chroot /tmp/box/rootfs /escape
# ls /etc/hostname && cat /etc/os-release | head -1
NAME="Ubuntu"                            # the HOST filesystem — escaped
# exit

Why it works: chroot changes the root directory but leaves the process's working directory pointing outside it. A second chroot while the cwd is outside makes the escape trivial. It requires root, which is exactly why running as root inside a container matters.

All capabilitiesDrop all but a fewNo module loading, no raw sockets, no mounting
All syscallsseccomp profile~44 syscalls blocked by default
Isolated but dead networkveth pair into a bridge, NATActually usable

6 (hard): Harden a container and verify each restriction actually applies.
Solution

1. The baseline — an unhardened container, and what it can reach:

$ docker run --rm -v /:/host:ro alpine sh -c 'id; head -1 /host/etc/shadow; ls /host/root'
uid=0(root) gid=0(root)
root:$6$xyz...                           # host's shadow file
.bashrc .ssh

Root inside is root outside — the bind mount is not the flaw, the UID mapping is.

2. Check its capabilities:

$ docker run --rm alpine sh -c 'grep CapEff /proc/self/status'
CapEff:	00000000a80425fb
$ capsh --decode=00000000a80425fb | tr ',' '\n' | wc -l
14                                       # 14 capabilities by default

3. Apply hardening one layer at a time, verifying each:

# Non-root
$ docker run --rm --user 65534:65534 alpine id
uid=65534(nobody) gid=65534(nobody)

# Drop all capabilities
$ docker run --rm --user 65534 --cap-drop=ALL alpine sh -c 'grep CapEff /proc/self/status'
CapEff:	0000000000000000                 # zero

# Read-only root filesystem
$ docker run --rm --read-only alpine sh -c 'touch /f' 2>&1
touch: /f: Read-only file system
$ docker run --rm --read-only --tmpfs /tmp:size=16m alpine sh -c 'touch /tmp/f && echo "tmp writable"'
tmp writable

# No privilege escalation via setuid
$ docker run --rm --security-opt=no-new-privileges --user 65534 alpine \
>   sh -c 'ls -l /bin/su; su root 2>&1 | head -1'
-rwsr-xr-x  1 root root  /bin/su
su: must be suid to work properly

# Fork-bomb and resource protection
$ docker run --rm --pids-limit=16 alpine sh -c \
>   'for i in $(seq 1 40); do sleep 5 & done' 2>&1 | tail -1
sh: can't fork

# No network
$ docker run --rm --network=none alpine sh -c 'ip -br link; wget -T2 -q -O- http://1.1.1.1' 2>&1 | head -2
lo    DOWN    00:00:00:00:00:00
wget: bad address '1.1.1.1'

4. Everything together:

$ docker run --rm \
>   --user 65534:65534 \
>   --cap-drop=ALL \
>   --security-opt=no-new-privileges \
>   --read-only --tmpfs /tmp:size=16m,noexec \
>   --pids-limit=32 \
>   --memory=128m --memory-swap=128m \
>   --cpus=0.5 \
>   --network=none \
>   alpine sh -c 'id; grep CapEff /proc/self/status; touch /f 2>&1; nproc'
uid=65534(nobody) gid=65534(nobody)
CapEff:	0000000000000000
touch: /f: Read-only file system
8

Note the last line: nproc still reports 8 despite --cpus=0.5. The container sees host CPU count, which is exactly why runtimes size thread pools wrongly and then get throttled. It must be told explicitly.

5. Verify the resource limits actually bind:

$ docker run --rm --memory=128m alpine sh -c \
>   'cat /sys/fs/cgroup/memory.max; dd if=/dev/zero of=/dev/null bs=200M count=1 2>&1 | tail -1'

$ docker run -d --name limited --memory=64m --cpus=0.5 alpine sleep 300

$ docker rm -f limited

🎯 Key Takeaways

  • There is no container object in the kernel — a container is a process with namespaces (what it sees), cgroups (what it uses), and capabilities/seccomp (what it may do).
  • Containers share the host kernel, so a kernel privilege-escalation bug is an escape; VMs, gVisor or Firecracker are the boundary for untrusted code.
  • Seven namespaces — pid, mnt, net, uts, ipc, user, cgroup — and they compose independently; unshare creates them without any runtime.
  • Without a user namespace, container root is host UID 0; unshare --user --map-root-user makes root inside an unprivileged UID outside.
  • nsenter -t PID -n runs host tools inside a container's namespaces — the way to debug an image with no shell.
  • cgroup v2 limits live in a filesystem tree: memory.max, cpu.max, pids.max, with memory.events and cpu.stat as the evidence.
  • CPU quota is enforced per 100 ms period, so a bursty service is throttled at low average utilisation — nr_throttled is the signal, and cpu.weight the fix for latency-sensitive work.
  • Page cache counts toward memory.max, and runtimes read host CPU/RAM unless told otherwise — both cause kills and throttling that look inexplicable.
  • pids.max is what stops a fork bomb in a container from taking down the host.
  • Overlayfs stacks read-only layers under one writable layer, which is why images are cheap to share.
  • Copy-up duplicates an entire file on first write, so write-heavy workloads need a volume rather than the overlay.
  • Deleting a file writes a whiteout — RUN rm secret leaves the secret in an earlier layer; use multi-stage builds or BuildKit secret mounts.
  • chroot is not a security boundary — a root process escapes it in a dozen lines; runtimes use pivot_root.
  • --privileged, a mounted docker.sock, --pid=host, and -v /:/host each remove the boundary entirely.
  • Harden in layers: non-root user, drop all capabilities, read-only root, no-new-privileges, seccomp allowlist, pids/memory/CPU limits, and no network unless required.
