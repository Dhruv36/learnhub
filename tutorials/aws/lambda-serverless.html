Lambda & API Gateway Compute

What you'll master: the execution-environment lifecycle, and the single fact that explains most Lambda behaviour — code outside the handler runs once per environment, code inside runs once per invocation, which is both the connection-reuse optimisation everyone wants and the state leak that serves one user's data to another; concurrency as in-flight invocations rather than requests per second, sized by Little's Law, where reserved concurrency is simultaneously a floor and a ceiling and one runaway function can throttle every other function in the account; the three invocation models and how each one loses your data differently — asynchronous events silently dropped after two retries, and a single poison-pill record blocking an entire stream shard for 24 hours; Lambda in a VPC, where the old cold-start penalty is gone but 1,000 concurrent functions open 1,000 database connections; API Gateway's payload format versions and the 29-second timeout that returns a 504 while your function keeps running and keeps billing; and reading the REPORT line as the cheapest performance tool you have. Prerequisites: ECS, EKS & Fargate, VPCs, Subnets & Security Groups and Cost: Pricing Models & Data Transfer.

Part 1 — The Execution Environment, Not "A Container"

THE LIFECYCLE — three phases, and only one of them runs per request:

  INIT      (once per environment)
    ├─ download the code / image
    ├─ start the runtime
    └─ run everything OUTSIDE your handler          ← imports, clients, connections

  INVOKE    (once per request)
    └─ run the handler function                     ← this is all that repeats

  SHUTDOWN  (when the environment is reclaimed)
    └─ ~2 minutes' notice, no guarantee your code runs

WHICH MAKES THIS THE MOST IMPORTANT PATTERN IN LAMBDA:

  import boto3
  s3 = boto3.client("s3")          # ← INIT. Once per environment. Reused forever.
  pool = make_db_pool()            # ← INIT. Connections survive between invocations.

  def handler(event, context):
      return s3.get_object(...)    # ← INVOKE. Every request.

$ # the same client, constructed inside the handler instead:
  Duration: 412 ms   (client construction: ~340 ms, EVERY invocation)
$ # constructed at init:
  Duration:  71 ms   Init Duration: 349 ms   ← paid once, then never again
🔑 Move every client, connection pool, config parse and model load outside the handler. It is the highest-leverage change in most Lambda functions, often 3–5× on warm invocations, and it costs nothing. The rule for what belongs where: anything that is request-independent goes in INIT; anything derived from event goes in the handler.
AND THE BUG THAT COMES WITH IT — global state is SHARED between invocations:

  ❌ user_context = {}                              # module scope

  def handler(event, context):
      user_context["user"] = event["user"]          # invocation 1: alice
      enrich(user_context)                          # invocation 2: bob — SAME dict
      return render(user_context)                   # bob may see alice's data

$ # reproduce it deterministically:
$ for u in alice bob carol; do
    aws lambda invoke --function-name profile --payload "{\"user\":\"$u\"}" \
      --cli-binary-format raw-in-base64-out /dev/stdout | jq -r .rendered_for
  done
alice
alice                                              ← ⚠️ bob got alice's context
alice

COLD START ANATOMY — visible in every REPORT line:

REPORT RequestId: 9f2a...  Duration: 71.42 ms  Billed Duration: 72 ms
       Memory Size: 1024 MB  Max Memory Used: 187 MB  Init Duration: 349.11 ms
                    │                        │                     │
                    │                        │                     └─ COLD START cost;
                    │                        │                        absent when warm
                    │                        └─ right-sizing signal: 187 of 1024 MB
                    └─ what you configured
💡 Max Memory Used is the free right-sizing metric — but do not reflexively shrink to fit it. Lambda allocates CPU proportionally to memory, so cutting a function from 1024 MB to 256 MB because it only uses 187 MB usually makes it slower and more expensive (see the U-shaped curve in Cost). Memory is a CPU dial with a memory floor; Max Memory Used tells you the floor, not the optimum.

Part 2 — Concurrency Is Not Requests Per Second

LITTLE'S LAW, and it is the whole capacity model:

    concurrency  =  requests per second  ×  average duration in seconds

    100 rps × 0.05 s  =    5 concurrent   ← a fast function barely uses capacity
    100 rps × 2.00 s  =  200 concurrent
    500 rps × 2.00 s  = 1000 concurrent   ← the DEFAULT ACCOUNT LIMIT, in one function
ControlWhat it doesCostWatch out
Account concurrency1,000 per Region by default, shared by every function—Soft limit; raise it before you need it
Reserved concurrencyBoth a guarantee and a capFreeSetting it to 0 disables the function
Provisioned concurrencyPre-initialised environments — no cold startsBilled while idleChanges the cost model entirely
Burst rate+1,000 concurrent per 10 s, per function—A true spike still throttles at the edge
RESERVED CONCURRENCY IS TWO THINGS AT ONCE, which is what surprises people:

$ aws lambda put-function-concurrency --function-name checkout --reserved-concurrent-executions 200
   → checkout is GUARANTEED 200        (no other function can take them)
   → checkout is LIMITED to 200        (it can never exceed them)
   → the account's unreserved pool drops from 1000 to 800 for everyone else

$ aws lambda get-account-settings \
    --query 'AccountLimit.[ConcurrentExecutions,UnreservedConcurrentExecutions]' --output text
1000    800

THE NOISY NEIGHBOUR — one function eats the account and everything else 429s:

$ aws cloudwatch get-metric-statistics --namespace AWS/Lambda --metric-name Throttles \
    --dimensions Name=FunctionName,Value=checkout --period 300 --statistics Sum \
    --start-time $(date -u -d '1 hour ago' +%FT%TZ) --end-time $(date -u +%FT%TZ) \
    --query 'sum(Datapoints[].Sum)' --output text
18402.0                                            ← checkout is throttled

$ aws cloudwatch get-metric-statistics --namespace AWS/Lambda --metric-name ConcurrentExecutions \
    --period 300 --statistics Maximum ... --query 'max(Datapoints[].Maximum)' --output text
1000.0                                             ← the ACCOUNT is at its ceiling

$ # who is holding it? Per-function concurrency, sorted:
  image-thumbnailer   947                          ← a retry loop, 8-second duration
  checkout             41
  everything else      12
   → a batch function starved the customer-facing one. The blast radius is the ACCOUNT.
🔑 Reserved concurrency is the bulkhead pattern for Lambda. Give customer-facing functions a reservation so batch work cannot starve them, and cap batch functions so they cannot consume the account. The default of "everything shares one pool" means any function's bug is every function's outage — and the failure is invisible until you look at account-level ConcurrentExecutions rather than at the throttled function.

✅ AN ON-FAILURE DESTINATION captures the event AND the error context:
$ aws lambda put-function-event-invoke-config --function-name process-upload \
    --destination-config '{"OnFailure":{"Destination":"arn:aws:sqs:us-east-1:1111:upload-dlq"},
                           "OnSuccess":{"Destination":"arn:aws:sns:us-east-1:1111:upload-done"}}'

$ aws sqs receive-message --queue-url https://sqs.us-east-1.amazonaws.com/1111/upload-dlq \
    --query 'Messages[0].Body' --output text | jq '{reason:.requestContext.condition, err:.responsePayload.errorMessage, payload:.requestPayload.Records[0].s3.object.key}'
{ "reason": "RetriesExhausted",
  "err": "KeyError: 'contentType'",
  "payload": "uploads/2026-08-20/invoice-4821.pdf" }   ← the ORIGINAL event, replayable
⚠️ Destinations are better than the older DeadLetterConfig because they carry the error context and the response payload, not just the input event — so the DLQ message tells you why it failed, not only that it did. A DLQ with no consumer and no alarm is still data loss on a delay, so alarm on queue depth and build the replay path before you need it.
STREAMS — the poison pill that blocks everything behind it:

  a Kinesis shard delivers batches IN ORDER. If the batch fails, the poller
  RETRIES THE SAME BATCH. One bad record blocks the shard until the records expire.

   → a rising IteratorAge is THE stream health metric. Linear growth = fully stalled.

✅ THE FOUR SETTINGS THAT UNBLOCK A SHARD:
$ aws lambda update-event-source-mapping --uuid 0a1b2c3d \
    --maximum-retry-attempts 3 \
    --maximum-record-age-in-seconds 3600 \
    --bisect-batch-on-function-error \
    --destination-config '{"OnFailure":{"Destination":"arn:aws:sqs:us-east-1:1111:stream-dlq"}}'

  bisect-batch-on-function-error: split the failing batch in half and retry each half,
                                  recursively — ISOLATES the one bad record instead of
                                  discarding 99 good ones with it.
  maximum-retry-attempts:         stop retrying forever.
  maximum-record-age:             stop reprocessing stale data.
  OnFailure destination:          the bad record is captured, not dropped.

SQS — use partial batch responses, or one bad message re-delivers the whole batch:
$ aws lambda update-event-source-mapping --uuid 0f3c9a1e \
    --function-response-types ReportBatchItemFailures

  def handler(event, context):
      failures = []
      for record in event["Records"]:
          try:    process(record)
          except Exception:
              failures.append({"itemIdentifier": record["messageId"]})
      return {"batchItemFailures": failures}       # ← ONLY these are re-delivered

Part 4 — Lambda in a VPC, and the Connection Storm

Attaching a Lambda function to a VPC used to add seconds to every cold start. That has not been true since AWS moved to shared Hyperplane ENIs in 2019 — the ENI is created once per function/subnet/security-group combination, not per environment. The real problems are different.

In a VPC, Lambda…Consequence
Has no internet route by defaultPublic API calls hang until timeout — needs a NAT Gateway or endpoints
Cannot have a public IPA NAT Gateway is the only outbound path (see Cost)
Consumes VPC addressesHyperplane ENIs are shared, but subnet capacity still matters
Reaches AWS services privatelyInterface endpoints avoid NAT charges entirely
Opens one DB connection per environmentThe storm below
THE CONNECTION STORM — Lambda's scaling model versus a database's connection limit:

$ aws rds describe-db-instances --db-instance-identifier orders-db \
    --query 'DBInstances[0].DBInstanceClass' --output text
db.t3.medium                                       ← max_connections ≈ 90

  400 concurrent Lambda environments × 1 connection each = 400 attempts

$ aws logs tail /aws/lambda/checkout --since 5m | grep -c 'too many connections'
2841
  FATAL: remaining connection slots are reserved for non-replication superuser connections
🔑 This is a structural mismatch, not a tuning problem. Lambda scales by creating more processes, and each one wants its own connection; a relational database scales by serving more queries over few connections. They are opposite models. Raising max_connections trades one failure for another — each connection costs memory on the database, so you convert connection refusals into swapping and a slower database for everyone.
✅ RDS PROXY — one pool, shared by every environment:
$ aws rds create-db-proxy --db-proxy-name orders-proxy --engine-family POSTGRESQL \
    --auth '[{"AuthScheme":"SECRETS","SecretArn":"arn:aws:secretsmanager:...:db-creds",
              "IAMAuth":"REQUIRED"}]' \
    --role-arn arn:aws:iam::111122223333:role/rds-proxy-role \
    --vpc-subnet-ids subnet-0a subnet-0b subnet-0c

  # point the function at the proxy endpoint instead of the database:
  DB_HOST = orders-proxy.proxy-abc123.us-east-1.rds.amazonaws.com

$ # after:
  400 concurrent Lambdas → proxy → 22 pooled DB connections
$ aws cloudwatch get-metric-statistics --namespace AWS/RDS --metric-name DatabaseConnections \
    --dimensions Name=DBInstanceIdentifier,Value=orders-db --period 300 --statistics Maximum \
    ... --query 'max(Datapoints[].Maximum)' --output text
22.0                                               ← was pinned at 90 and failing

If you are attaching Lambda to a relational database at all, the proxy is close to mandatory.

THE 29-SECOND WALL — API Gateway and Lambda do not agree on how long is too long:

  API Gateway integration timeout:   29 seconds (default maximum)
  Lambda maximum timeout:            15 minutes

  at t=29s   API Gateway gives up and returns 504 to the client
  at t=29s   YOUR FUNCTION KEEPS RUNNING — and keeps billing — for up to 15 minutes
  at t=6m    it finishes successfully, writes to the database, and nobody is listening

$ aws logs tail /aws/lambda/report --since 10m --format short | grep REPORT
REPORT ... Duration: 362104.22 ms  Billed Duration: 362105 ms   ← 6 minutes, billed
$ # and the client saw:
{"message": "Endpoint request timed out"}          ← 504 at 29 seconds
⚠️ The dangerous part is not the 504 — it is that the work completed. A client that retries after the timeout runs the job a second time, so a non-idempotent operation (charge a card, send an email, increment a counter) happens twice, and the logs show two successful executions and one angry customer. Set the Lambda timeout below the API Gateway timeout for synchronous APIs, so the function fails when the caller stops listening, and make anything that mutates state idempotent.
✅ FOR WORK THAT GENUINELY TAKES MINUTES — return immediately, process asynchronously:

  POST /reports  →  Lambda validates, enqueues, returns 202 with a job id  (80 ms)
                 →  SQS → worker Lambda (15-minute timeout) → writes result to S3
  GET  /reports/{id}  →  returns status, or a presigned URL when done

$ curl -sD- -o /dev/null -X POST https://api.acme.com/reports
HTTP/2 202
location: /reports/9f2a-4b2c
   → the client polls or subscribes. No timeout to lose the race against.

AUTHORIZERS — and the cache that decides whether they cost anything:
$ aws apigateway create-authorizer --rest-api-id a1b2c3 --name jwt-auth --type REQUEST \
    --authorizer-uri arn:aws:apigateway:us-east-1:lambda:path/.../invocations \
    --identity-source 'method.request.header.Authorization' \
    --authorizer-result-ttl-in-seconds 300
   → WITHOUT the TTL, the authorizer Lambda runs on EVERY request: double the
     invocations, double the cold starts, and it is in the latency path of all of them.
   → identity-source is the CACHE KEY. Omit it and caching silently does nothing.

Part 6 — Reading the REPORT Line

Every invocation ends with one line that answers most performance questions:

REPORT RequestId: 9f2a-4b2c  Duration: 1204.18 ms  Billed Duration: 1205 ms
       Memory Size: 1024 MB  Max Memory Used: 891 MB  Init Duration: 2841.02 ms

  Duration          wall clock in the handler
  Billed Duration   rounded up to the next millisecond
  Max Memory Used   the right-sizing FLOOR (not the optimum — CPU scales with memory)
  Init Duration     the cold start. Present only on cold invocations.

$ aws logs start-query --log-group-name /aws/lambda/checkout \
    --start-time $(date -d '24 hours ago' +%s) --end-time $(date +%s) --query-string '
  filter @type = "REPORT"
  | stats count() as invocations,
          pct(@duration, 50) as p50, pct(@duration, 99) as p99,
          max(@maxMemoryUsed)/1024/1024 as peak_mb,
          count(@initDuration) as cold_starts,
          pct(@initDuration, 50) as p50_init'

  1,284,002    41.2   2,841.0  891      1,204        2,610.4
   → 0.09% cold starts, but they are 63× the warm p50 and they ARE the p99.

⚠️ SnapStart restores every environment from one snapshot taken after INIT, which means anything generated during initialisation is identical in every environment: random seeds, UUIDs, and cached credentials or connections captured at snapshot time. Re-seed randomness and re-establish connections in an afterRestore runtime hook, or you get duplicate identifiers and connections to a database that closed them hours ago. This is the one genuinely surprising thing about SnapStart and it is a correctness issue, not a performance one.

❌ Clients constructed inside the handler, request context in module scope, no reserved concurrency anywhere, asynchronous invocations with no destination, a stream with default retry settings, four hundred concurrent functions connecting directly to a db.t3.medium, a REST API kept for no reason, and a Lambda timeout longer than API Gateway's. Every invocation rebuilds an SDK client it could have reused, so warm requests cost three times what they should. A module-level dictionary holds the current user, so a warm environment serves one customer's data to the next. All functions share one concurrency pool, so a thumbnailer stuck in a retry loop consumed the account limit and threw 429s at checkout. Asynchronous S3 events fail twice and vanish with no record that they existed. A single malformed record blocks a Kinesis shard, and IteratorAge climbs linearly for ninety minutes before anyone notices. Four hundred environments each open a database connection to an instance that allows ninety. The API is a REST API paying 3.5× for features nobody uses. And the function's timeout is fifteen minutes while API Gateway gives up at twenty-nine seconds, so clients see 504s, retry, and charge the card twice.

✅ Initialise once, keep request state local, bulkhead the concurrency, capture every failure, bisect poison pills, pool the connections, use HTTP APIs, and make the function give up before the caller does. Construct clients and pools outside the handler and keep everything derived from event inside it — the first is the biggest free performance win in Lambda and the second prevents a data leak. Give customer-facing functions reserved concurrency so batch work cannot starve them, and cap batch functions so they cannot consume the account; watch account-level ConcurrentExecutions, not just per-function throttles. Configure on-failure destinations on every asynchronous function, because the default is two retries and silence. On streams, set BisectBatchOnFunctionError, a maximum retry count, a maximum record age and a destination, then alarm on IteratorAge — linear growth means fully stalled. Put RDS Proxy in front of any relational database, which also removes credentials from the function and survives failover. Use HTTP APIs unless you specifically need usage plans, request validation or private endpoints — and if you migrate, fix the v1/v2 payload differences first. Finally, set the Lambda timeout below API Gateway's so the function stops when the caller stops listening, make state-changing operations idempotent, and move genuinely long work behind a 202 and a queue.

Interview Questions

Beginner: What is a Lambda cold start, and what actually happens during one?

A cold start is the INIT phase: AWS creates a new execution environment, downloads your code or image, starts the runtime, and runs everything outside your handler — imports, SDK client construction, connection setup. Only then does it run the handler. It appears in the REPORT line as Init Duration, and is absent on warm invocations because the environment is reused.

The practical consequence is the pattern: anything request-independent belongs outside the handler, where it runs once per environment instead of once per request. Moving client construction out took a measured function from 412 ms to 71 ms warm.

Cold starts are usually a small share of invocations — 0.09% in the example above — but they are your p99, because they cost tens of times the warm duration. So they matter for latency percentiles far more than the raw percentage suggests, and that is the framing to give.

Beginner: How does Lambda concurrency work, and what happens when you hit the limit?

Concurrency is the number of invocations in flight at once, not requests per second. Little's Law gives it: concurrency = rps × duration. So 100 rps of a 50 ms function is 5 concurrent, while 100 rps of a 2-second function is 200.

The default account limit is 1,000 concurrent executions per Region, shared by every function in the account. Beyond it, synchronous callers receive TooManyRequestsException (429), asynchronous invocations are retried and eventually dropped, and stream pollers simply fall behind.

ControlEffect
Reserved concurrencyGuarantees and caps — and removes that amount from the shared pool
Provisioned concurrencyPre-initialised environments; no cold starts, but billed while idle
Account limit increaseA support request — do it before you need it

The point worth making unprompted: because the pool is shared, any function's bug is every function's outage. Reserved concurrency is the bulkhead that prevents it.

Mid: S3 events are triggering a Lambda and some uploads are never processed, with no errors reported anywhere. Explain.

S3 invokes Lambda asynchronously. On failure, Lambda retries twice with backoff and then discards the event. S3 is not told, no dead letter exists by default, and the only trace is the Errors metric — so an intermittent bug silently loses a fraction of uploads.

$ aws lambda get-function-event-invoke-config --function-name process-upload
{ "MaximumRetryAttempts": 2, "MaximumEventAge": 21600 }   ← and no DestinationConfig

The fix is an on-failure destination, which is better than the legacy DeadLetterConfig because it captures the error and the response payload alongside the original event — so the queued message tells you why, not just that:

$ aws lambda put-function-event-invoke-config --function-name process-upload \
    --destination-config '{"OnFailure":{"Destination":"arn:aws:sqs:...:upload-dlq"}}'

Then close the loop, because a DLQ nobody watches is delayed data loss: alarm on queue depth, build and test the replay path, and alarm on the Errors metric so failures are visible before they exhaust retries. Worth adding: if ordering or guaranteed delivery matter, put SQS between S3 and Lambda deliberately rather than relying on asynchronous invocation, which gives you visibility timeouts, retries you control, and a real queue depth to monitor.

Mid: A Kinesis-triggered function has an IteratorAge climbing steadily for an hour. What is happening and how do you fix it?

A poison pill is blocking the shard. Stream event sources deliver batches in order and retry the same batch on failure — by default until the records expire, up to 24 hours. One malformed record therefore stalls every record behind it on that shard, and IteratorAge grows linearly because nothing is being consumed at all.

Linear growth is the diagnostic. A function that is merely slow shows a sawtooth or a plateau; a stalled shard shows a straight line, because age increases exactly with wall-clock time.

SettingWhat it prevents
BisectBatchOnFunctionErrorSplits the failing batch recursively to isolate the one bad record instead of discarding 99 good ones
MaximumRetryAttemptsRetrying forever
MaximumRecordAgeInSecondsReprocessing data too stale to matter
OnFailure destinationLosing the bad record when you stop retrying

For the immediate incident, applying those settings to the event source mapping unblocks the shard within minutes. Longer term, the handler should be defensive: a record that cannot be parsed is a business event to route to a quarantine queue, not an exception to propagate. And note that increasing parallelisation does not help — the block is per shard, and more concurrency per shard still retries the same failing batch.

Senior: Design a serverless API that must handle a 50× traffic spike, stay under 200 ms at p99, and talk to a relational database.

Three requirements that each break a different part of the naive design, so take them one at a time.

The spike breaks concurrency. Compute the target: at 5,000 rps and 100 ms that is 500 concurrent, so the default 1,000 account limit is one bad day away — raise it in advance and give this function reserved concurrency so nothing else in the account can starve it. Lambda's burst rate adds 1,000 concurrent per 10 seconds, which is fine for a ramp and not for an instantaneous 50×, so shed load deliberately at the edge with API Gateway throttling and usage plans rather than letting the spike become 429s scattered across unrelated functions.

The p99 breaks on cold starts. At 0.09% cold with a 2.6-second INIT, the cold starts are the p99. Move all client construction into INIT, keep the package small, use SnapStart if the runtime supports it, and buy provisioned concurrency sized to the steady-state baseline — with an application-autoscaling schedule ahead of the known spike, since provisioned concurrency is billed while idle and there is no point paying for it overnight.

The database breaks on connections. Five hundred environments versus a connection limit in the low hundreds is a structural mismatch, so RDS Proxy is mandatory, not optional — it multiplexes onto a small pool, removes credentials from the function, and survives failover. Cap reserved concurrency at a number the database can actually support, so the throttle happens at Lambda where it is visible and cheap rather than at the database where it is an outage. Read-heavy paths go to read replicas or a cache; if the data model permits, DynamoDB removes the problem entirely because it has no connections.

What I would flag as the real risk: a 50× spike against a relational database is a database capacity question wearing a Lambda costume. Lambda will scale; the database will not. So the honest design either bounds concurrency to protect it, or moves the hot path off it. Deciding which before the spike is the whole job.

Senior: Customers report a checkout endpoint timing out, and some of them are charged twice. Walk through it.

The two symptoms together identify the mechanism. A timeout and a duplicate side effect means work completed after the caller stopped listening — which on API Gateway plus Lambda is almost always the 29-second integration timeout against a longer function timeout.

$ aws lambda get-function-configuration --function-name checkout --query Timeout
300                                                ← 5 minutes
$ aws logs tail /aws/lambda/checkout --since 30m --format short | grep REPORT | tail -2
REPORT ... Duration: 41204.11 ms  Billed Duration: 41205 ms      ← 41 s: SUCCEEDED
REPORT ... Duration: 39880.02 ms  Billed Duration: 39881 ms      ← the retry. Also succeeded.

API Gateway returned 504 at 29 seconds. The function kept running, charged the card, and completed successfully at 41 seconds. The client — a browser or a mobile app with its own retry — resubmitted, and the second invocation charged the card again. Both executions are "successful" in every metric, which is why this does not look like an incident from the dashboards.

FixWhy
Lambda timeout below 29 sThe function stops when the caller stops listening — no orphaned work
Idempotency keysThe retry is recognised and returns the first result. The one that actually protects the customer.
Fix the 40-second latencyA checkout taking 41 s is the underlying bug — find it in X-Ray
202 + async for long workRemoves the race for anything genuinely slow

Order matters here. Idempotency first, because it stops the customer harm immediately and protects against every other cause of duplicate submission — a double-clicked button, a flaky network, a client-side retry — not just this one. Then the timeout alignment, then the root-cause latency work. And the monitoring lesson worth stating: this was invisible because both invocations succeeded. Alarm on API Gateway's 5XXError and IntegrationLatency, not only on Lambda's Errors, or the gateway giving up will never show up as a failure anywhere.

🎯 Key Takeaways

  • Code outside the handler runs once per environment; code inside runs once per invocation. Moving client construction to INIT measured 412 ms → 71 ms warm.
  • The same reuse causes the worst Lambda bug: request state in module scope leaks between users. Anything derived from event stays in the handler.
  • Test for it by invoking twice with different inputs in one environment — unit tests never catch it, because each test gets a fresh module.
  • Max Memory Used is a right-sizing floor, not an optimum — CPU scales with memory, so shrinking to fit usually costs more.
  • Concurrency = rps × duration, not requests per second. 500 rps of a 2-second function is the entire default account limit.
  • Halving duration halves required concurrency — usually easier than a limit increase, and cheaper too.
  • Reserved concurrency is a floor and a ceiling, and it removes capacity from the shared pool. Setting it to 0 disables the function.
  • All functions share one account pool, so any function's bug is every function's outage — a thumbnailer holding 947 of 1,000 threw 429s at checkout. Reserved concurrency is the bulkhead.
  • Watch account-level ConcurrentExecutions, not just the throttled function's metrics, or the culprit stays invisible.
  • Asynchronous invocations retry twice and then silently drop the event — measured at ~2,996 uploads lost in a week with no record of which.
  • On-failure destinations beat the legacy DLQ because they carry the error, the attempt count and the response payload — why, not just that.
  • One bad record blocks an entire stream shard, retrying for up to 24 hours; IteratorAge growing linearly is the unmistakable signature.
  • BisectBatchOnFunctionError isolated one poison record in 15 splits and let all 100 good ones through; more shards or parallelisation do not help.
  • On SQS, use ReportBatchItemFailures or one bad message re-delivers the whole batch.
  • VPC Lambda has had no cold-start penalty since Hyperplane ENIs in 2019 — the real issues are NAT costs and connections.
  • Lambda and relational databases scale in opposite ways: 387 environments wanted 387 connections against a limit of 90. RDS Proxy took it to 22.
  • Raising max_connections is not a fix — it traded refusals for 8.4-second queries and 40 MB of free memory, degrading every other client.
  • RDS Proxy also removes credentials from the function (IAM auth) and survives failover, which is why it is close to mandatory for Lambda + RDS.
  • HTTP APIs cost 3.5× less than REST APIs — but migrating changes the payload format: v2 uses requestContext.http.method and rawPath.
  • API Gateway gives up at 29 seconds while the function keeps running and billing — the danger is not the 504, it is that the work completed, so retries duplicate side effects (47 customers charged twice).
  • Fix that in order: idempotency keys first (they cover every cause of duplicate submission), then timeout alignment, then the underlying latency, then 202-plus-queue for genuinely long work.
  • Alarm on API Gateway's 5XXError and IntegrationLatency — when both invocations succeed, Lambda's metrics show nothing at all.
  • Set an explicit timeout on every outbound call: a client with no timeout waits longer than the function, turning a slow third party into your outage.
  • SnapStart restores every environment from one snapshot, so random seeds, UUIDs and cached connections are identical everywhere — re-seed and reconnect in an afterRestore hook.
