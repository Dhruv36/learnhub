Observability: CloudWatch & X-Ray Operations

What you'll master: which question each tool answers, and the defaults that quietly answer none of them — CloudTrail does not log S3 object reads, CloudWatch cannot see memory, and X-Ray samples about 5% of your traffic; why Average is the statistic that hides outages, demonstrated with a fleet at 12% average error rate showing a flat green line; alarms that never fire because the metric stopped being emitted, and the TreatMissingData setting that decides whether silence means healthy or broken; the custom-metric cost explosion, where one high-cardinality dimension became $37,000 a month, and the Embedded Metric Format that gives you the same dimensions for a fraction of it; CloudWatch Logs, where ingestion at $0.50/GB routinely exceeds the compute producing it and retention does not help; X-Ray's annotations versus metadata — the distinction between a trace you can query and one you can only read; and the incident workflow that turns four disconnected tools into one investigation. Prerequisites: EC2, Lambda and Cost.

Part 1 — Four Tools, Four Questions

ToolAnswersGranularityThe default that surprises people
CloudWatch Metrics"What is happening, in aggregate?"1 s – 1 h, auto-aggregatedNo memory, no disk-space metric without the agent
CloudWatch Logs"What did the code say?"Every lineIngestion costs $0.50/GB; retention is infinite unless set
X-Ray"Where did the time go?"Per request, sampled~1 req/s + 5% is sampled, not everything
CloudTrail"Who did what to AWS?"Every API callData events are OFF — no S3 object reads, no DynamoDB items
THE CLOUDTRAIL DISTINCTION THAT MATTERS IN EVERY SECURITY REVIEW:

  MANAGEMENT events (on by default, free for the first copy)
      CreateBucket, PutBucketPolicy, RunInstances, AssumeRole, CreateUser
      → "who changed the infrastructure"

  DATA events (OFF by default, $0.10 per 100,000)
      s3:GetObject, s3:PutObject, dynamodb:GetItem, lambda:Invoke
      → "who read the data"

$ aws cloudtrail get-event-selectors --trail-name org-trail \
    --query 'EventSelectors[].{mgmt:IncludeManagementEvents,data:DataResources}' --output json
[ { "mgmt": true, "data": [] } ]
   ⚠️ "Did anyone download the customer export?" is UNANSWERABLE with this trail.
⚠️ This is the single most common gap found during an incident. The trail exists, management events are recorded, everyone believes S3 access is audited — and it is not. Enabling data events for a high-traffic bucket is genuinely expensive, so the practical answer is to enable them selectively: on the buckets holding sensitive data, with an advanced event selector that excludes noisy prefixes. Decide that before you need the answer, because CloudTrail cannot record the past.
$ aws cloudtrail put-event-selectors --trail-name org-trail --advanced-event-selectors '[
    {"Name":"management","FieldSelectors":[{"Field":"eventCategory","Equals":["Management"]}]},
    {"Name":"sensitive-s3","FieldSelectors":[
       {"Field":"eventCategory","Equals":["Data"]},
       {"Field":"resources.type","Equals":["AWS::S3::Object"]},
       {"Field":"resources.ARN","StartsWith":["arn:aws:s3:::acme-customer-exports/"]}]}]'
   → data events for ONE bucket, not for every object read in the account.

Part 2 — Metrics, and the Statistic That Lies

THE PROBLEM WITH AVERAGE — a 20-instance fleet, 3 of them completely broken:

  17 instances × 0% errors        = 0
   3 instances × 80% errors       = 240
  ────────────────────────────────────
  average across the fleet        = 12%

$ aws cloudwatch get-metric-statistics --namespace AWS/ApplicationELB \
    --metric-name TargetResponseTime --dimensions Name=LoadBalancer,Value=app/shop/ab \
    --period 300 --statistics Average \
    --start-time $(date -u -d '1 hour ago' +%FT%TZ) --end-time $(date -u +%FT%TZ) \
    --query 'max(Datapoints[].Average)' --output text
0.184                                              ← 184 ms. Looks fine.

$ aws cloudwatch get-metric-statistics ... --extended-statistics p99 \
    --query 'max(Datapoints[].ExtendedStatistics.p99)' --output text
8.412                                              ← 8.4 SECONDS at p99
StatisticAnswersUse for
AverageThe typical case, with outliers erasedCapacity trends — almost never alerting
SumTotal volumeCounts: requests, errors, invocations
MaximumThe single worstSaturation: queue depth, credit balance
p90/p99/p99.9What the unlucky user experiencedLatency alerting
SampleCountHow many data pointsDetecting that a metric stopped
🔑 Average is the wrong statistic for anything a user experiences. It is the arithmetic that makes three broken hosts out of twenty look like a rounding error, and it is the default in most consoles. Alert on percentiles for latency and on Sum for errors; keep Average for capacity planning, where "the typical case" is genuinely what you want.
CUSTOM METRICS COST PER DIMENSION COMBINATION — this is the trap:

  $0.30 per metric per month, and EVERY unique combination is a separate metric.

  aws cloudwatch put-metric-data --metric-name RequestLatency \
      --dimensions Service=checkout,Region=us-east-1,InstanceId=i-0a1b,CustomerId=42

  services   ×  instances  ×  customers   =   metrics
      12     ×     40      ×    260,000   =   124,800,000
                                              × $0.30 = $37,440,000 / month

✅ EMBEDDED METRIC FORMAT — emit metrics inside structured logs instead:
  print(json.dumps({
    "_aws": {"Timestamp": int(time.time()*1000),
             "CloudWatchMetrics": [{
               "Namespace": "Acme/Checkout",
               "Dimensions": [["Service"], ["Service","Operation"]],   ← LOW cardinality
               "Metrics": [{"Name":"LatencyMs","Unit":"Milliseconds"}]}]},
    "Service": "checkout", "Operation": "submit",
    "LatencyMs": 184,
    "customerId": "42",          ← HIGH cardinality: a log FIELD, not a dimension
    "requestId": "9f2a-4b2c"}))

  → CloudWatch creates metrics only for the declared Dimensions sets (12 × 8 = 96
    metrics = $28.80/month), while customerId and requestId remain queryable in
    Logs Insights.
💡 The rule: dimensions are for things you alert on, log fields are for things you investigate with. Anything unbounded — customer id, request id, instance id on an autoscaling fleet, URL path with ids in it — must never be a metric dimension. EMF gives you both without choosing: cheap aggregate metrics for alarms, and full-cardinality fields for the investigation that follows the alarm.
METRIC RESOLUTION AND RETENTION — metrics are aggregated as they age:
  1-second   kept for  3 hours
  1-minute   kept for 15 days
  5-minute   kept for 63 days
  1-hour     kept for 15 months
   ⚠️ so an alarm on a 1-minute period cannot be back-tested beyond 15 days,
     and a dashboard of last quarter is hourly whether you like it or not.

Part 3 — Alarms That Actually Fire

THREE STATES, and the third is where alarms go to die:
    OK                  the metric is within the threshold
    ALARM               it breached
    INSUFFICIENT_DATA   ⚠️ NO DATA ARRIVED — and by default this is NOT an alarm

$ aws cloudwatch describe-alarms --alarm-names checkout-errors \
    --query 'MetricAlarms[0].[StateValue,TreatMissingData,EvaluationPeriods,DatapointsToAlarm]' --output text
INSUFFICIENT_DATA   missing   3   3
   → the checkout service crashed, stopped emitting metrics entirely,
     and the alarm went quiet instead of firing.
TreatMissingDataMissing data meansUse for
missing (default)Ignore it; keep the current stateRarely correct
breachingTreat as a breach"This must always be emitting" — heartbeats, health
notBreachingTreat as healthyGenuinely sparse metrics — errors on a low-traffic queue
ignoreDo not evaluate at allBatch jobs with long gaps
$ aws cloudwatch put-metric-alarm --alarm-name checkout-errors \
    --namespace AWS/ApplicationELB --metric-name HTTPCode_Target_5XX_Count \
    --dimensions Name=LoadBalancer,Value=app/shop/ab \
    --statistic Sum --period 60 --evaluation-periods 5 --datapoints-to-alarm 3 \
    --threshold 10 --comparison-operator GreaterThanThreshold \
    --treat-missing-data breaching \
    --alarm-actions arn:aws:sns:us-east-1:111122223333:pager
                        │                    │
                        │                    └─ 3 OF 5: tolerates one bad minute,
                        │                       catches a sustained problem
                        └─ Sum, not Average — errors are counted, not averaged
🔑 Alert on symptoms, not causes. "CPU > 80%" pages someone for a condition that may be perfectly fine; "users are getting 5xx" pages for something that is definitely not. The discipline that removes most alert fatigue is to page only on things a user would notice — error rate, latency percentile, queue age, failed jobs — and to leave everything else as a dashboard or a ticket. Every cause-based page is a promise that you know all the causes.
COMPOSITE ALARMS — one page instead of forty:
$ aws cloudwatch put-composite-alarm --alarm-name checkout-degraded \
    --alarm-rule "ALARM(checkout-5xx) OR ALARM(checkout-latency-p99) OR ALARM(checkout-queue-age)" \
    --alarm-actions arn:aws:sns:us-east-1:111122223333:pager

  and SUPPRESSION, so a dependency's outage does not page four teams:
$ aws cloudwatch put-composite-alarm --alarm-name checkout-degraded \
    --alarm-rule "ALARM(checkout-5xx) OR ALARM(checkout-latency-p99)" \
    --actions-suppressor database-down \
    --actions-suppressor-wait-period 60 \
    --alarm-actions arn:aws:sns:us-east-1:111122223333:pager
   → if the database alarm is already firing, checkout does not page. One incident,
     one page, at the layer that can act on it.

Part 4 — Logs: The Bill and the Query

$ aws logs describe-log-groups --query \
    'reverse(sort_by(logGroups,&storedBytes))[:5].[logGroupName,storedBytes,retentionInDays]' \
    --output text
/aws/lambda/checkout          412048829440   None      ← NEVER EXPIRES
/ecs/api                      288104882944   None
/aws/rds/instance/orders      104882944000   7
/vpc/flowlogs                  88293180160   None
/aws/lambda/thumbnailer         4188293180   14

$ aws logs put-retention-policy --log-group-name /aws/lambda/checkout --retention-in-days 14
⚠️ Retention caps storage at $0.03/GB-month. Ingestion is $0.50/GB and is unaffected. A service logging 200 GB a day costs $3,000/month to ingest and $180/month to store — so setting retention addresses the smaller number and people are surprised the bill barely moves. The only fix for ingestion is to log less: raise the level, sample debug output, drop health-check lines at the agent, and stop logging entire request and response bodies.
STRUCTURED LOGGING IS WHAT MAKES LOGS QUERYABLE:

  ❌ log.info(f"processed order {oid} for {cid} in {ms}ms")
     → Logs Insights must regex it out, and the format drifts per developer

  ✅ log.info(json.dumps({"event":"order_processed","orderId":oid,
                          "customerId":cid,"durationMs":ms,
                          "requestId":ctx.aws_request_id,"traceId":trace_id}))
     → every field is queryable, typed, and joins across services

$ aws logs start-query --log-group-names /aws/lambda/checkout /ecs/api \
    --start-time $(date -d '2 hours ago' +%s) --end-time $(date +%s) --query-string '
  fields @timestamp, service, durationMs, orderId
  | filter durationMs > 1000
  | stats count() as slow, avg(durationMs) as avg_ms, pct(durationMs, 99) as p99
          by service, bin(5m)
  | sort slow desc'

METRIC FILTERS — turn a log pattern into a metric you can alarm on:
$ aws logs put-metric-filter --log-group-name /ecs/api \
    --filter-name payment-declines --filter-pattern '{ $.event = "payment_declined" }' \
    --metric-transformations \
      metricName=PaymentDeclines,metricNamespace=Acme/Payments,metricValue=1,defaultValue=0
   ⚠️ defaultValue=0 matters: without it the metric is SPARSE, and an alarm on it
     sits in INSUFFICIENT_DATA whenever there are no declines.

SUBSCRIPTION FILTERS — stream logs out in real time:
$ aws logs put-subscription-filter --log-group-name /ecs/api \
    --filter-name to-firehose --filter-pattern '' \
    --destination-arn arn:aws:firehose:us-east-1:1111:deliverystream/logs-to-s3 \
    --role-arn arn:aws:iam::111122223333:role/CWLtoFirehose
   → to S3 (cheap long-term), OpenSearch (search), or a third-party SIEM.

Part 5 — X-Ray: Where Did the Time Go?

A TRACE is a tree of SEGMENTS (one per service) and SUBSEGMENTS (one per call):

  trace 1-68a5f3c2-9f2a4b2c        total 2,410 ms
    ├─ api-gateway                        12 ms
    └─ checkout (Lambda)               2,398 ms
         ├─ DynamoDB GetItem              8 ms
         ├─ fraud-api (HTTP)          2,301 ms      ← there it is
         └─ SQS SendMessage              14 ms

SAMPLING — X-Ray does NOT trace everything, and the default is modest:
$ aws xray get-sampling-rules --query \
    'SamplingRuleRecords[].SamplingRule.{name:RuleName,fixed:ReservoirSize,rate:FixedRate}' --output json
[ { "name": "Default", "fixed": 1, "rate": 0.05 } ]
   → 1 request per second, plus 5% of everything above that.
     A rare error at 0.1% of traffic will almost never appear in a trace.

$ aws xray create-sampling-rule --sampling-rule '{
    "RuleName":"checkout-errors","Priority":100,"ReservoirSize":10,"FixedRate":1.0,
    "ServiceName":"checkout","ServiceType":"*","Host":"*","HTTPMethod":"POST",
    "URLPath":"/checkout*","Version":1}'
   → 100% of checkout POSTs, up to 10/s. Sample the paths you care about heavily
     and everything else lightly.
AnnotationsMetadata
Indexed✅ — filterable in queries❌
Limit50 per traceEffectively unlimited
TypesString, number, booleanAny JSON
Use forAnything you will search by: customerId, tier, region, versionPayloads, debug context, full objects
  from aws_xray_sdk.core import xray_recorder

  seg = xray_recorder.current_segment()
  seg.put_annotation("customerId", cid)         # ✅ searchable
  seg.put_annotation("tier", "premium")         # ✅ searchable
  seg.put_annotation("deployVersion", "a3f91c2")# ✅ searchable
  seg.put_metadata("requestBody", body)         # ❌ visible, NOT searchable

$ aws xray get-trace-summaries --start-time $(date -d '1 hour ago' +%s) --end-time $(date +%s) \
    --filter-expression 'annotation.tier = "premium" AND duration > 2' \
    --query 'TraceSummaries[].[Id,Duration]' --output text
1-68a5f3c2-9f2a4b2c   2.41
1-68a5f3d1-8e1b3a2d   3.02
   → impossible if `tier` had been metadata.
🔑 The annotation/metadata choice is what determines whether a trace is queryable or merely readable. A trace you can only open one at a time answers "why was this request slow"; annotations let you ask "which tier, which version, which customer segment is slow", which is the question that actually finds a regression. Add annotations for every dimension you might slice by — deploy version above all, since it turns "when did this start" into a filter.

Part 6 — One Investigation, Four Tools

THE THREAD THAT TIES THEM TOGETHER IS A CORRELATION ID:

  API Gateway   → requestId
  X-Ray         → traceId (X-Amzn-Trace-Id header, propagated automatically)
  your logs     → BOTH, in every structured line
  downstream    → the same traceId, forwarded

  → then one query joins everything:

1. THE ALARM (symptom-level)
   checkout-degraded → ALARM: p99 latency > 2 s for 3 of 5 minutes

2. WHICH LAYER? Response headers or the 5xx decoder from the load balancer lesson.
$ aws cloudwatch get-metric-statistics --namespace AWS/ApplicationELB \
    --metric-name TargetResponseTime ... --extended-statistics p99 \
    --query 'max(Datapoints[].ExtendedStatistics.p99)' --output text
2.84                                               ← the TARGET is slow, not the ALB

3. WHERE IN THE REQUEST? X-Ray, filtered to the slow ones.
$ aws xray get-trace-summaries --start-time $(date -d '30 min ago' +%s) --end-time $(date +%s) \
    --filter-expression 'service("checkout") AND duration > 2' \
    --query 'TraceSummaries[0].[Id,ServiceIds[].Name]' --output text
1-68a5f3c2-9f2a4b2c   checkout  orders-db  fraud-api

4. WHAT HAPPENED? Logs Insights, joined by traceId.
$ aws logs start-query --log-group-names /ecs/checkout /ecs/fraud --query-string '
  fields @timestamp, service, event, durationMs, error
  | filter traceId = "1-68a5f3c2-9f2a4b2c"
  | sort @timestamp asc'
  12:04:11  checkout  call_fraud_api   —      —
  12:04:11  fraud     upstream_retry   —      "connection reset"
  12:04:41  fraud     upstream_retry   —      "connection reset"
  12:06:12  fraud     responded      2301   —

5. WHO CHANGED SOMETHING? CloudTrail.
$ aws cloudtrail lookup-events --start-time 2026-08-20T11:00:00Z \
    --query 'Events[?contains(EventName, `Update`) || contains(EventName, `Modify`)].[EventTime,EventName,Username]' \
    --output text
2026-08-20T11:52:04Z   ModifyDBInstance      deploy-role
2026-08-20T11:58:31Z   UpdateFunctionConfiguration   deploy-role

❌ Alarms on Average, alarms with the default TreatMissingData, CPU-threshold pages, unbounded metric dimensions, log groups with no retention, unstructured log lines, X-Ray at the default sampling rate with everything as metadata, and CloudTrail with no data events. The latency alarm watches Average, so three broken instances out of twenty read as 184 ms while the p99 is 8.4 seconds and customers are timing out. When the service crashes entirely and stops emitting, the alarm goes to INSUFFICIENT_DATA and quietly stays there, so a total outage produces silence rather than a page. Meanwhile pages fire constantly for CPU above 80% on instances that are working perfectly, and everyone has learned to ignore them. Someone added customerId as a metric dimension and the custom-metrics line reached tens of thousands of dollars. Log groups were created by the console with no retention, so four hundred gigabytes of Lambda logs will be stored forever, and the far larger ingestion charge is untouched because nobody logs less. Log lines are formatted strings, so every Logs Insights query starts with a regex that breaks whenever a developer rephrases a message. X-Ray traces 5% of requests, which never includes the rare failure anyone wants to see, and everything useful was attached as metadata so no trace can be searched by customer, tier or deploy version. And when the security team asks who downloaded the customer export, the trail has management events only and the answer does not exist.

✅ Alarm on percentiles and sums, treat missing data as breaching for anything that must always emit, page only on user-visible symptoms, keep dimensions low-cardinality and put the detail in EMF fields, set retention on every log group and reduce ingestion at the source, log structured JSON with a correlation id, sample the paths that matter at 100%, annotate what you will search by, and enable CloudTrail data events selectively on sensitive buckets. Use percentiles for latency and Sum for errors, with M-of-N evaluation so one bad minute does not page and a sustained problem does. Set --treat-missing-data breaching on every heartbeat-style alarm, because silence from a health metric is the loudest signal there is. Move cause-based thresholds to dashboards and keep pages for error rate, latency and queue age — every cause-based page assumes you already know every cause. Declare only low-cardinality dimension sets and emit customer and request identifiers as EMF log fields, so alarms stay cheap and investigations stay possible. Put a retention policy on every log group at creation and attack ingestion by logging less, since retention only caps the smaller number. Emit structured JSON carrying both requestId and traceId so one query joins services. Create X-Ray sampling rules that capture 100% of the critical paths, and make everything you might filter by — customer, tier, deploy version — an annotation, because metadata cannot be searched. And enable data events on the buckets that hold sensitive data before an incident asks, since CloudTrail cannot record the past.

Interview Questions

Beginner: What is the difference between CloudWatch Logs, Metrics, X-Ray and CloudTrail?
ToolQuestion it answersShape of the data
Metrics"What is happening, in aggregate?"Numeric time series
Logs"What did the code say?"Text or JSON events
X-Ray"Where did the time go in this request?"A tree of timed spans
CloudTrail"Who called which AWS API?"An audit record per call

In practice they are used in sequence: a metric alarm tells you something is wrong, a trace tells you which hop is slow, logs tell you what that hop actually did, and CloudTrail tells you whether a human or a deploy changed something just before it started.

The detail worth adding unprompted: CloudTrail records calls to the AWS API — management events by default. It does not record your application's own behaviour, and it does not record S3 object reads or DynamoDB item access unless data events are explicitly enabled.

Beginner: Why is Average a poor statistic for alerting on latency?

Because it averages away exactly the users who are having a bad time. If seventeen instances in a fleet of twenty respond in 50 ms and three take 8 seconds, the average is a few hundred milliseconds and the alarm stays green — while 15% of requests are effectively failing.

  Average of TargetResponseTime : 0.184 s          ← green
  p99     of TargetResponseTime : 8.412 s          ← customers timing out

Use percentiles for anything a user experiences — p99 for the tail, p50 alongside it to distinguish "everything is slow" from "some requests are catastrophic". Use Sum for counted things like errors and invocations, and Maximum for saturation metrics like queue depth or credit balance, where the worst value is the one that matters.

Average has one good use: capacity planning, where "the typical case" is genuinely the question. It is the default in most consoles, which is why this is worth checking on every alarm you inherit.

Mid: A service went completely down and no alarm fired. How is that possible?

The metric stopped being emitted, and the alarm's TreatMissingData is at its default. CloudWatch alarms have three states, and the third — INSUFFICIENT_DATA — is not an alarm state. With the default of missing, CloudWatch simply retains the previous state, so an alarm that was OK stays OK forever once the data stops.

That is the perverse case: a partial failure fires the alarm, and a total failure silences it, because a service that has crashed emits no error metric at all.

SettingMissing data treated asRight for
missing (default)Keep current stateRarely anything
breachingA breachAnything that must always emit
notBreachingHealthyGenuinely sparse metrics
ignoreNot evaluatedBatch jobs with long gaps

Two complements worth mentioning. Alarm on a metric that exists when the service is healthy and is absent when it is not — request count with --treat-missing-data breaching is a better outage detector than error count. And add a synthetic canary hitting the endpoint from outside, because it is the only check that keeps producing data when everything inside has stopped.

Mid: Your CloudWatch bill is dominated by custom metrics. What happened and how do you fix it?

A high-cardinality dimension. CloudWatch charges $0.30 per metric per month, and every unique combination of dimension values is a separate metric. So adding customerId or requestId as a dimension multiplies the metric count by the cardinality of that field.

  12 services × 40 instances × 260,000 customers = 124,800,000 metrics
                                                 × $0.30 = $37,440,000 / month

The fix is the Embedded Metric Format, which separates the two concerns: declare only low-cardinality dimension sets (things you alarm on), and emit high-cardinality identifiers as ordinary log fields that stay queryable in Logs Insights.

  "Dimensions": [["Service"], ["Service","Operation"]]   ← 96 metrics, $28.80/month
  "customerId": "42", "requestId": "9f2a"                ← log fields, fully queryable

The general rule: dimensions are for alerting, log fields are for investigating. Anything unbounded — customer, request, instance on an autoscaling fleet, a URL path containing ids — must never be a dimension. To find existing offenders, list metrics per namespace and look for ones with an enormous number of dimension combinations; and note that deleting the offending PutMetricData call stops the charge immediately, since unused metrics simply stop being billed.

Senior: Design the observability strategy for a 40-service platform. What do you standardise, and what do you page on?

Standardise three things and let teams decide the rest, because a standard that covers everything will not be adopted.

1. A correlation id in every log line. Structured JSON carrying traceId and requestId, propagated across every hop, emitted by a shared library so no team has to get it right individually. This is the single highest-value standard: without it, forty services are forty separate investigations.

2. A common metric contract. Every service emits the same handful of names — request count, error count, duration percentiles, saturation — via EMF, with low-cardinality dimensions (Service, Operation) and everything else as log fields. That makes one dashboard template and one alarm template work for all forty, which is what makes the standard survive.

3. Sampling and retention defaults set centrally: X-Ray at 100% for critical paths and low elsewhere, log retention set at log-group creation (enforced with a Config rule, since nobody sets it voluntarily), and data events on sensitive buckets only.

SignalPage?Why
SLO error-budget burn rateYesThe user-visible symptom, normalised across services

DLQ depth > 0Yes (ticket, or page if it is money)Data is being quarantined

On paging specifically: page only on symptoms, and prefer error-budget burn rate to raw thresholds — a fast burn pages immediately, a slow burn opens a ticket. That one change removes most alert fatigue, because it distinguishes "this is on fire" from "this is slightly worse than target".

What I would explicitly avoid: a central team that owns all dashboards and alarms (it becomes a bottleneck and the owning team stops looking), and a mandate to adopt a tracing SDK without a shared library that makes it a one-line change. Standardise the contract, ship the library, and let teams own their own dashboards.

Senior: Latency regressed for some users after a deploy, but the dashboards look normal. How do you find it?

"Some users" plus "dashboards normal" means the aggregate is hiding a segment — which tells you immediately that the investigation is about slicing, not about thresholds.

Check the aggregate is really normal. If the dashboard shows Average, it proves nothing; look at p99 and p99.9. A regression affecting 5% of traffic moves p99 substantially and moves Average almost not at all.

Then slice, which is what X-Ray annotations exist for:

$ aws xray get-trace-summaries --start-time $(date -d '2 hours ago' +%s) --end-time $(date +%s) \
    --filter-expression 'annotation.deployVersion = "a3f91c2" AND duration > 2'
$ aws xray get-trace-summaries ... \
    --filter-expression 'annotation.tier = "premium" AND duration > 2'

If deployVersion and tier are annotations, this is two queries. If they were attached as metadata, they are not indexed and this line of investigation is closed — which is the practical argument for the annotation/metadata distinction.

In parallel, slice the logs, since EMF log fields carry the high-cardinality dimensions the metrics deliberately do not:

  fields @timestamp, durationMs, tier, region, deployVersion
  | filter durationMs > 1000
  | stats count() as slow, pct(durationMs,99) as p99 by tier, region, deployVersion

And confirm the deploy is the cause rather than the coincidence: CloudTrail for what changed and when, and compare the two versions over the same window — a canary or weighted rollout makes this a direct comparison rather than a before-and-after guess.

The prevention is what I would push hardest: this class of regression is invisible to any dashboard that aggregates across segments, so annotate the deploy version on every trace, keep per-segment percentiles for the dimensions that matter (tier, region, client version), and roll out with weighted target groups so both versions run concurrently and the comparison is like-for-like rather than time-shifted.

🔑 Default X-Ray gives you a trace viewer; annotations and sampling rules give you a query engine. The difference is between answering "why was this one request slow" — which you can often work out from logs anyway — and answering "which segment, which version, which payment method", which is the question that actually finds a regression. Both changes are configuration rather than architecture: a sampling rule per critical path, and an annotation for every dimension you might slice by, with deployVersion the most valuable of all because it turns "when did this start?" into a filter.

🎯 Key Takeaways

  • Four tools, four questions: Metrics (what, in aggregate), Logs (what the code said), X-Ray (where the time went), CloudTrail (who called which AWS API).
  • CloudTrail data events are OFF by default — "who downloaded the customer export?" is unanswerable, and CloudTrail cannot record the past. Scope them to sensitive buckets: measured $0.04/month versus $200.
  • Average is the statistic that hides outages: 3 broken hosts of 20 read as 1,243 ms while p99 was 8,103 ms and 15% of users were failing.
  • Alarm on percentiles for latency and Sum for errors; keep Average for capacity planning.
  • p99 and p50 together distinguish "everything is slow" from "a subset is failing" — two completely different investigations, told apart before opening a trace.
  • INSUFFICIENT_DATA is not an alarm state. A crashed service stops emitting and the alarm goes silent — a partial failure fires it, a total failure silences it.
  • Set --treat-missing-data breaching on anything that must always emit, and prefer alarming on a metric that exists when healthy (request count) over one that only exists when broken (errors).
  • Add a synthetic canary: it is the only check outside every failure domain it watches, and the only one that catches DNS and certificate failures.
  • Metric filters need defaultValue=0, or the metric is sparse and the alarm sits in INSUFFICIENT_DATA.
  • Page on symptoms, not causes. Every cause-based page assumes you already know all the causes; move CPU and memory thresholds to dashboards.
  • Use composite alarms with --actions-suppressor so a dependency's outage produces one page at the layer that can act, not forty across four teams.
  • Every unique dimension combination is a separate metric at $0.30 — one high-cardinality dimension computed to $37 M/month.
  • EMF gives cheap low-cardinality metrics for alarms and full-cardinality log fields for investigation: 108 metrics at $32.40 with per-customer latency still queryable.
  • The rule is mechanical: dimensions are for alerting, log fields are for investigating; anything unbounded is never a dimension.
  • Retention caps storage at $0.03/GB; ingestion is $0.50/GB and unaffected — so setting retention barely moves a log bill. Log less at the source.
  • Set retention on every log group at creation — the default is to keep logs forever.
  • Log structured JSON with both requestId and traceId; formatted strings turn every query into a regex that breaks on rephrasing.
  • X-Ray samples ~1 req/s + 5% by default — measured at 0.20% of traffic, so a 0.1% failure produced 2 traces. Write sampling rules: 100% for the money path, 0% for health checks.
  • Annotations are indexed and filterable; metadata is not. That distinction is what makes a trace queryable rather than merely readable.
  • Annotate deployVersion above all — it turns "when did this start?" into a filter, and isolated a regression to one version in one query.
  • Metrics aggregate as they age (1-minute data kept 15 days), so alarms cannot be back-tested indefinitely.
  • An investigation is only as good as instrumentation decided months earlier — the six-step trace here depended on p99 alarms, EMF fields, X-Ray annotations and a correlation id that were all already in place.
