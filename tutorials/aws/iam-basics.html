IAM: Identities, Policies & Evaluation Foundations

What you'll master: the evaluation algorithm every access decision runs through, in order, so AccessDenied stops being a mystery — including the rule that overrides everything else: an explicit Deny anywhere wins, always; the difference between identity-based and resource-based policies, and why cross-account access needs BOTH sides to agree while same-account access needs only one; the anatomy of a policy statement and the two constructs that routinely grant far more than intended — NotAction and a bare "Resource": "*"; condition keys, including the ones that actually contain a policy (aws:PrincipalOrgID, aws:SourceArn) and the confused-deputy problem they exist to solve; iam:PassRole, the most under-appreciated privilege-escalation permission in AWS; and the three tools that turn policy debugging from guesswork into a procedure. Prerequisites: Shared Responsibility, Accounts & Regions.

Part 1 — Principals and the Request Context

Every API call carries a context, and every policy is a predicate over that context. Once you see it that way, policies stop being magic incantations.

  a request =  PRINCIPAL   who is calling      arn:aws:sts::1111:assumed-role/App/i-0abc
               ACTION      what                s3:GetObject
               RESOURCE    on what             arn:aws:s3:::shop-data/orders/2026.json
               CONTEXT     everything else     aws:SourceIp, aws:SecureTransport,
                                               aws:PrincipalOrgID, aws:CurrentTime,
                                               aws:PrincipalTag/team, s3:prefix …
Principal typeLooks likeCredentialUse for
IAM userarn:aws:iam::1111:user/aliceLong-lived access keyAlmost nothing — avoid
IAM role (assumed)arn:aws:sts::1111:assumed-role/App/sessionTemporary, auto-rotatedEverything
AWS servicelambda.amazonaws.comn/a — trust policyService-to-service
Federated identitySAML or OIDC subjectShort-lived via STSHumans, CI, EKS pods
Account rootarn:aws:iam::1111:rootEmail + passwordNothing; in policies it means "the account"
🔑 In a resource policy, "Principal": {"AWS": "arn:aws:iam::1111:root"} does not mean the root user. It means "the account 1111 may delegate this to its own identities" — the standard way to grant cross-account access without naming every role. It is the single most misread string in AWS policy documents.

Part 2 — Policy Anatomy

{
  "Version": "2012-10-17",              ← always this; "2008-10-17" disables variables
  "Statement": [{
    "Sid": "ReadOrders",
    "Effect": "Allow",                  ← Allow or Deny
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::shop-data",         ← the BUCKET, for ListBucket
      "arn:aws:s3:::shop-data/orders/*" ← the OBJECTS, for GetObject
    ],
    "Condition": {
      "Bool": { "aws:SecureTransport": "true" },
      "StringEquals": { "aws:PrincipalOrgID": "o-abc123" }
    }
  }]
}
Policy typeAttached toAnswers
Identity-basedA user, group or role"What may this principal do?"
Resource-basedThe resource (S3 bucket, SQS queue, KMS key, Lambda…)"Who may touch this resource?" — has a Principal field
Permission boundaryA user or roleA ceiling on what an identity policy can grant
SCPAn OU or accountA ceiling for the whole account
Session policyPassed at AssumeRole timeA ceiling for that session

Only a handful of services support resource-based policies — S3, SQS, SNS, KMS, Lambda, Secrets Manager, ECR, EFS, API Gateway, and a few more. That distinction decides how cross-account access is granted, which is Part 3.

The two constructs that over-grant

❌ "NotAction" — everything EXCEPT the listed actions
{ "Effect": "Allow", "NotAction": "iam:*", "Resource": "*" }
   → grants every action in every service AWS has ever launched, except IAM.
     Including services released next year.

❌ a bare wildcard resource on a mutating action
{ "Effect": "Allow", "Action": "s3:DeleteObject", "Resource": "*" }
   → every object in every bucket in the account

✅ enumerate, and scope
{ "Effect": "Allow", "Action": ["s3:GetObject","s3:PutObject"],
  "Resource": "arn:aws:s3:::shop-data/orders/*" }
⚠️ NotAction with Allow is almost always a mistake. It is useful in a Deny statement — "deny everything except these actions" is a coherent guardrail, and that is how Region-restriction SCPs are written. Paired with Allow it grants an unbounded and growing set, because AWS keeps adding services.

Part 3 — The Evaluation Algorithm

  1. Is there an EXPLICIT DENY anywhere?        → DENY. Stop. Nothing overrides this.
                                                  (SCP, boundary, session, identity,
                                                   resource policy — any of them)
  2. Does an SCP allow it?                      → no → DENY
  3. Does a resource policy explicitly allow?   → yes → ALLOW  (same account)
  4. Does an identity policy allow?             → no → DENY
  5. Does the permission boundary allow?        → no → DENY
  6. Does the session policy allow?             → no → DENY
  7. → ALLOW
RuleConsequence
Explicit Deny always winsYou cannot "override" a Deny with a broader Allow
Default is implicit denyNothing is permitted unless something grants it
Boundaries and SCPs only subtractThey never grant; the identity policy must still allow
Same account: identity OR resource policy sufficesEither one can grant access
Cross account: identity AND resource policyBoth sides must agree
CROSS-ACCOUNT, THE RULE THAT CATCHES EVERYONE:

  account A (1111) role wants s3:GetObject on account B's (2222) bucket

  A's identity policy:   Allow s3:GetObject on arn:aws:s3:::b-bucket/*     ← required
  B's bucket policy:     Allow Principal arn:aws:iam::1111:role/App        ← ALSO required

  either one missing → AccessDenied. Same account would have needed only one.

$ aws s3 cp s3://b-bucket/file.txt . --profile account-a
fatal error: An error occurred (403) when calling the HeadObject operation: Forbidden
$ aws s3api get-bucket-policy --bucket b-bucket --profile account-b \
    --query Policy --output text | jq -r '.Statement[].Principal'
{ "AWS": "arn:aws:iam::3333:root" }        ← the bucket trusts a DIFFERENT account

Part 4 — Conditions, and the Confused Deputy

aws:PrincipalOrgIDPrincipals in your OrganizationThe single best resource-policy guardrail
aws:SourceArn / aws:SourceAccountThe resource that triggered a service callPreventing the confused deputy

THE CONFUSED DEPUTY: a service you trust is tricked into acting on someone else's behalf.

  ❌ your S3 bucket policy trusts a service principal with no scoping:
  { "Effect": "Allow", "Principal": { "Service": "cloudtrail.amazonaws.com" },
    "Action": "s3:PutObject", "Resource": "arn:aws:s3:::my-logs/*" }
     → ANY account's CloudTrail can write into your bucket

  ✅ scope it to the calling resource and account:
  "Condition": {
    "StringEquals": { "aws:SourceAccount": "111122223333" },
    "ArnLike":      { "aws:SourceArn": "arn:aws:cloudtrail:eu-west-1:111122223333:trail/*" }
  }
🔑 aws:SourceArn and aws:SourceAccount belong on every resource policy whose principal is an AWS service. The classic third-party version is a role you let a SaaS vendor assume: without an sts:ExternalId condition, any other customer of that vendor can ask it to assume your role. Both patterns are the same bug — a trusted intermediary acting on an untrusted caller's instructions.
ABAC — one policy that scales to any number of teams:

{ "Effect": "Allow", "Action": ["ec2:StartInstances","ec2:StopInstances"],
  "Resource": "*",
  "Condition": { "StringEquals": {
      "aws:ResourceTag/team": "${aws:PrincipalTag/team}" } } }

  → a principal tagged team=payments may start/stop instances tagged team=payments,
    and nothing else. New team? Tag them. No policy change.

Part 5 — iam:PassRole and Escalation

Creating a resource that runs as a role requires two permissions: creating the resource, and passing the role to it. Grant the second carelessly and the first becomes total control.

{ "Effect": "Allow", "Action": "iam:PassRole", "Resource": "*" }     ← ⚠️
  + lambda:CreateFunction  → run any code as ANY role in the account, including admin
  + ec2:RunInstances       → launch an instance with an admin instance profile
  + ecs:RunTask            → same, via a task role

$ aws lambda create-function --function-name esc --runtime python3.12 \
    --role arn:aws:iam::111122223333:role/AdminRole \
    --handler i.h --zip-file fileb://exfil.zip --profile limited-dev
{ "FunctionArn": "arn:aws:lambda:eu-west-1:111122223333:function:esc" }
        ↑ the developer has no admin rights; the FUNCTION does

✅ scope PassRole to the roles that principal may legitimately pass:
{ "Effect": "Allow", "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::111122223333:role/app-*",
  "Condition": { "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" } } }
PermissionEffectively grants
iam:PassRole + a compute-create actionAnything the passed role can do
iam:CreatePolicyVersionRewrite an attached policy — self-escalation
iam:AttachUserPolicy / AttachRolePolicyAttach AdministratorAccess
iam:UpdateAssumeRolePolicyMake yourself trusted by a privileged role
sts:AssumeRole on *Every role that trusts the account
lambda:UpdateFunctionCode on a privileged functionRun your code as that function's role
ssm:SendCommandRun commands as the instance profile on any managed instance

Part 6 — Debugging Access

① READ THE ERROR — it names the principal, action and often the reason
$ aws s3 ls s3://shop-data --profile dev
An error occurred (AccessDenied) when calling the ListObjectsV2 operation: User:
arn:aws:sts::111122223333:assumed-role/Developer/alice is not authorized to perform:
s3:ListBucket on resource: "arn:aws:s3:::shop-data" because no identity-based policy
allows the s3:ListBucket action
            ↑ "no identity-based policy allows" vs "with an explicit deny in a
              service control policy" vs "explicit deny in an identity-based policy"

② SIMULATE — before and after a policy change
$ aws iam simulate-principal-policy \
    --policy-source-arn arn:aws:iam::111122223333:role/Developer \
    --action-names s3:GetObject s3:DeleteObject \
    --resource-arns arn:aws:s3:::shop-data/orders/x.json \
    --query 'EvaluationResults[].[EvalActionName,EvalDecision]' --output text
s3:GetObject       allowed
s3:DeleteObject    implicitDeny

③ LAST-ACCESSED — find permissions nobody uses
$ aws iam generate-service-last-accessed-details \
    --arn arn:aws:iam::111122223333:policy/DeveloperPolicy --query JobId --output text
$ aws iam get-service-last-accessed-details --job-id "$JOB" \
    --query 'ServicesLastAccessed[?TotalAuthenticatedEntities==`0`].ServiceName' --output text
Amazon Redshift    Amazon SageMaker    AWS Glue        ← granted, never used

④ ACCESS ANALYZER — external access, and generated policies
$ aws accessanalyzer list-findings --analyzer-arn "$ANALYZER" \
    --query 'findings[?status==`ACTIVE`].[resource,principal]' --output text
arn:aws:s3:::shop-backups    {"AWS":"*"}              ← public

❌ Policies built from "Action": "*" with NotAction carve-outs, iam:PassRole on *, resource policies naming service principals with no conditions, and access debugged by adding permissions until it works. The developer policy says "allow everything except IAM", which grants every service AWS has launched since — including ones nobody has reviewed. iam:PassRole on * combined with lambda:CreateFunction means any developer can run arbitrary code as the admin role, so the careful separation of duties is decorative. A logging bucket trusts cloudtrail.amazonaws.com with no aws:SourceAccount, so any AWS customer's trail can write into it. A vendor role has no ExternalId, so any other customer of that vendor can have it assumed on their behalf. And when something is denied, the fix is to broaden the policy until the error stops — which is why the account has fourteen roles with AdministratorAccess and nobody can say which are needed.

✅ Enumerate actions and resources, scope PassRole, condition every service principal, and debug with the tools rather than by widening. Write Allow statements that list actions explicitly and scope Resource to real ARNs — reserve NotAction for Deny guardrails, where "everything except" is a coherent ceiling. Scope iam:PassRole to a role-name prefix with an iam:PassedToService condition, because PassRole plus any compute-create action is equivalent to whatever the passed role can do. Put aws:SourceAccount and aws:SourceArn on every resource policy whose principal is a service, and sts:ExternalId on every role a third party may assume — both are the same confused-deputy bug. Add aws:PrincipalOrgID to resource policies so access cannot leak outside the Organization even if a principal ARN is mistyped. And when you hit AccessDenied, read the message (it distinguishes "no policy allows" from "explicit deny in an SCP"), then use the policy simulator and Access Analyzer — widening a policy until the error disappears is how an account accumulates admin roles nobody can justify.

Interview Questions

Beginner: How does AWS decide whether a request is allowed?

A fixed evaluation order, where an explicit Deny anywhere ends it immediately.

1. explicit Deny anywhere?            → DENY (nothing overrides this)
2. SCP allows?                        → no → DENY
3. resource policy explicitly allows? → yes → ALLOW (same account)
4. identity policy allows?            → no → DENY
5. permission boundary allows?        → no → DENY
6. session policy allows?             → no → DENY
7. → ALLOW

Two consequences worth stating: the default is implicit deny, so nothing is permitted unless something grants it; and SCPs, boundaries and session policies only subtract — they never grant, so the identity policy must still allow the action.

The practical takeaway is that "add another Allow" never fixes a Deny. Read the AccessDenied message: it distinguishes "no identity-based policy allows" from "with an explicit deny in a service control policy", which tells you where to look.

Beginner: What is the difference between identity-based and resource-based policies?

Identity-based policies attach to a principal and say what it may do; resource-based policies attach to a resource and say who may touch it — they have a Principal field.

Identity-basedResource-based
Attached toUser, group, roleThe resource
Principal field❌✅
Available onEverythingS3, SQS, SNS, KMS, Lambda, Secrets Manager, ECR…

The rule that matters: within one account, either can grant access. Across accounts, both must allow — the caller's identity policy and the resource's policy. A request that works same-account and fails cross-account with identical policies is almost always this.

The idiom to recognise: "Principal": {"AWS": "arn:aws:iam::1111:root"} does not mean the root user — it means "account 1111 may delegate this to its identities", which is the normal way to write a cross-account grant.

Mid: What is the confused deputy problem and how do you prevent it?

A trusted intermediary is tricked into using its privileges on an untrusted caller's behalf. It appears in two common shapes.

① a service principal with no scoping
{ "Principal": { "Service": "cloudtrail.amazonaws.com" },
  "Action": "s3:PutObject", "Resource": "arn:aws:s3:::my-logs/*" }
   → ANY AWS account's CloudTrail can write into your bucket

  fix:
  "Condition": { "StringEquals": { "aws:SourceAccount": "111122223333" },
                 "ArnLike": { "aws:SourceArn": "arn:aws:cloudtrail:*:111122223333:trail/*" } }

② a third-party role with no ExternalId
   the vendor assumes roles for many customers; if your trust policy only names the
   vendor's account, any other customer can ask the vendor to assume YOUR role

  fix: "Condition": { "StringEquals": { "sts:ExternalId": "unique-secret-per-customer" } }

The general rule: whenever a policy trusts something that acts on behalf of others — an AWS service, a SaaS vendor, a shared automation account — the trust must be conditioned on which caller or resource triggered it, not merely on who is calling.

A good default for internal resource policies is aws:PrincipalOrgID: even if a principal ARN is mistyped, access cannot leak outside your Organization.

Mid: Why is iam:PassRole dangerous?

Because creating a resource that runs as a role requires only two permissions, and the resulting code inherits everything that role can do.

iam:PassRole on "*"  +  lambda:CreateFunction
   → run arbitrary code as ANY role in the account, including admin

$ aws lambda create-function --role arn:aws:iam::1111:role/AdminRole ... --profile dev
{ "FunctionArn": "..." }        ← the developer has no admin rights; the function does

The same applies to ec2:RunInstances with an instance profile, ecs:RunTask with a task role, and glue, sagemaker and others.

{ "Effect": "Allow", "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::1111:role/app-*",
  "Condition": { "StringEquals": { "iam:PassedToService": "lambda.amazonaws.com" } } }

It belongs in a family of quietly-equivalent-to-admin permissions worth auditing together: iam:CreatePolicyVersion (rewrite an attached policy), iam:AttachRolePolicy (attach AdministratorAccess), iam:UpdateAssumeRolePolicy (make yourself trusted), lambda:UpdateFunctionCode on a privileged function, and ssm:SendCommand.

Access Analyzer's unused-access findings and IAM last-accessed data are the practical way to find them, because they look innocuous in a policy review.

Senior: Design an IAM strategy for a multi-account organisation.

Layer the controls so that no single mistake is sufficient, and make the safe path the easy one.

LayerMechanismExpresses
OrganisationSCPs on OUsWhat may never happen anywhere
AccountSeparate accounts per envThe blast radius
DelegationPermission boundariesTeams may create roles, but not privileged ones
HumansIAM Identity Center + SSOShort-lived credentials, one offboarding point
WorkloadsRoles — instance profiles, IRSA, task rolesNo long-lived keys anywhere
AccessABAC on team tagsOne policy that scales with teams

Permission boundaries are the under-used piece. They let a platform team delegate role creation to product teams safely: a developer may create roles, but only with a boundary attached that caps what those roles can ever do. Without boundaries, "can create roles" is equivalent to admin.

ABAC is what keeps this from becoming a policy factory. One policy conditioned on aws:ResourceTag/team = ${aws:PrincipalTag/team} serves every team; onboarding a new one is a tag, not a pull request. The prerequisite is tag governance — enforced at creation with SCPs or Config rules, because ABAC that depends on optional tags is not a control.

What I would monitor continuously: Access Analyzer external-access findings, unused permissions from last-accessed data, roles with iam:PassRole on *, any remaining IAM users with access keys, and CloudTrail for AssumeRole patterns that do not match expected workflows. Those five queries find nearly every real IAM problem without reading a single policy document.

Senior: A cross-account call fails with AccessDenied and both policies "look right". How do you debug it?

Work through the evaluation order, and check the things that are invisible in the two policy documents in front of you.

CheckWhy it is missed
Both sides actually allowCross-account needs identity and resource policy
An SCP on either accountInvisible from inside the account; denies even admins
A permission boundary on the roleCaps the identity policy silently
A session policy at AssumeRole timeSet by the caller, not stored anywhere
The KMS key policyEncrypted S3 objects need KMS as well as S3 permissions
Condition keys not matchingaws:SourceIp fails via a VPC endpoint; PrincipalOrgID fails cross-org
The role ARN vs the assumed-role ARNResource policies match the role ARN, conditions often see the session ARN

The KMS row is the most common "both policies look right" case. Reading an SSE-KMS-encrypted object cross-account requires s3:GetObject, the bucket policy, and kms:Decrypt granted by the key policy to the calling principal. The error is a generic 403 that mentions S3, not KMS.

The procedure: read the exact error text first — it distinguishes an SCP deny from a missing allow. Then run simulate-principal-policy from the calling account, which evaluates boundaries and SCPs. Then check CloudTrail in the resource-owning account, where the denied event records the principal and the specific reason.

What I would not do is start adding permissions. Cross-account failures are almost always a missing condition match or an invisible ceiling, and broadening either side hides the real cause while creating a finding for the next audit.

🎯 Key Takeaways

  • Every request is principal + action + resource + context, and every policy is a predicate over that context.
  • An explicit Deny anywhere wins — attaching AdministratorAccess did not override a one-line inline Deny.
  • The AccessDenied message distinguishes "no identity-based policy allows" from "explicit deny in a service control policy" — read it before changing anything.
  • SCPs, permission boundaries and session policies only subtract; something must still grant the action.
  • Same account: identity OR resource policy suffices. Cross account: BOTH must allow.
  • Cross-account access to SSE-KMS objects needs a third grant — the KMS key policy — which is the usual "both policies look right" case.
  • "Principal": {"AWS": "…:root"} means "delegate to this account's identities", not the root user.
  • NotAction with Allow grants every service AWS has and every service it launches next; it belongs only in Deny guardrails.
  • s3:ListBucket needs the bucket ARN while s3:GetObject needs the object ARN — listing both is the fix for a very common denial.
  • iam:PassRole on * plus lambda:CreateFunction is admin — demonstrated creating a backdoor user from a role explicitly denied iam:CreateUser.
  • Scope it by ARN prefix with an iam:PassedToService condition; audit the whole escalation family, including CreatePolicyVersion, AttachRolePolicy and UpdateAssumeRolePolicy.
  • A resource policy naming an AWS service principal needs aws:SourceAccount and aws:SourceArn, or any account's service can act through it.
  • A third-party role needs sts:ExternalId, or another of that vendor's customers can have your role assumed.
  • aws:PrincipalOrgID on internal resource policies means a mistyped principal cannot leak access outside the Organization.
  • aws:SourceIp does not match traffic arriving through a VPC endpoint — use aws:SourceVpce.
  • ABAC conditioned on aws:ResourceTag/team = ${aws:PrincipalTag/team} is one policy that scales with teams — but only if tags are enforced at creation by an SCP.
  • Permission boundaries are what make delegated role creation safe: attaching AdministratorAccess to a bounded role changed nothing.
  • IAM last-accessed data found 243 services granted and never used; Access Analyzer generated an 11-action policy from CloudTrail.
  • After tightening, watch CloudTrail for denials — monthly jobs are the classic gap a 90-day window misses.
  • Debug with the error text, then simulate-principal-policy, then Access Analyzer — widening a policy until the error stops is how accounts accumulate admin roles nobody can justify.
