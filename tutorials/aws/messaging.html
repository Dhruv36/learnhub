SQS, SNS, EventBridge & Kinesis Data

What you'll master: the one question that picks the service — is this work to be done once, an announcement to be heard by many, or a log to be replayed? — and why "we need a queue" is usually three different requirements; SQS's visibility timeout, the single most common source of duplicate processing in production, reproduced and measured; long polling, which costs 240× fewer requests than the default and lowers latency at the same time; SNS filter policies that stop four subscribers being woken for messages they discard; dead-letter queues and the redrive that most teams never build until they need it at 3am; FIFO queues, where the message group ID is simultaneously your ordering guarantee and your parallelism limit — one group measured at 300 messages/second, sixty groups at 18,000; EventBridge's content-based routing and its archive and replay, which recovers a bad deploy's lost events; Kinesis shards, ordering, and the fact that the real distinction from SQS is replay and independent consumers, not throughput; and the conclusion that ties them together — every one of these is at-least-once, so exactly-once is a property of your consumer. Prerequisites: Lambda & API Gateway and DynamoDB.

Part 1 — Queue, Topic, Bus, or Stream?

  SQS          a QUEUE    → work to be done ONCE, by one of N workers
  SNS          a TOPIC    → an announcement, pushed to many subscribers, now
  EventBridge  a BUS      → routing by CONTENT, to many targets, with replay
  Kinesis      a STREAM   → an ordered LOG, replayable, read independently
SQSSNSEventBridgeKinesis
Consumers per messageOneManyManyMany, independent
RetentionUp to 14 daysNoneNone (archive optional)24 h – 365 days
Replay❌❌✅ archive + replay✅ by sequence number
OrderingFIFO queues onlyFIFO topics only❌ nonePer shard
Routing—By subscription + filterBy event contentBy partition key
Consumer pacePullPushPushPull, own position
Backpressure✅ natural❌ pushes regardless❌✅
🔑 The backpressure row decides more architectures than any other. A queue absorbs a spike and lets consumers work at their own rate; a topic pushes at whatever rate producers write, so a slow subscriber becomes a failing subscriber. That is why SNS → SQS fan-out is the most common real pattern: SNS does the distribution, and each subscriber gets its own queue with its own retention, retry and dead-letter behaviour. Subscribing Lambda directly to SNS gives you neither buffering nor a durable retry story.
THE FAN-OUT PATTERN, which is worth learning as a unit:

   producer → SNS topic ──┬──→ SQS queue → billing workers      (own retries, own DLQ)
                          ├──→ SQS queue → analytics workers    (can be down for an hour)
                          └──→ SQS queue → email workers        (slow, and that is fine)

  each consumer:  its own backlog, its own failure isolation, its own replay-from-DLQ.
  without the queues: one slow subscriber, and the message is simply gone.

Part 2 — SQS: Visibility Timeout Is the Whole Story

  1. a consumer calls ReceiveMessage
  2. the message becomes INVISIBLE to other consumers for the visibility timeout
  3. the consumer processes it
  4. the consumer calls DeleteMessage      ← THIS is what removes it

  if step 4 does not happen before the timeout expires, the message becomes
  visible again and ANOTHER consumer processes it. The first one is still working.

$ aws sqs get-queue-attributes --queue-url $Q --attribute-names All \
    --query 'Attributes.{vis:VisibilityTimeout,retention:MessageRetentionPeriod,
             wait:ReceiveMessageWaitTimeSeconds,maxsize:MaximumMessageSize}' --output json
{ "vis": "30", "retention": "345600", "wait": "0", "maxsize": "262144" }
     │                                      └─ 0 = SHORT POLLING (the default)
     └─ 30 seconds. If your job takes 45, every message is processed TWICE.
⚠️ A visibility timeout shorter than processing time is the most common SQS bug in production, and it presents as "duplicate emails" or "double charges" rather than as an error — nothing fails, the work simply happens twice. Set the timeout to at least 6× the p99 processing time, and for variable workloads extend it while working with ChangeMessageVisibility. The real fix is idempotent consumers, because at-least-once delivery means duplicates are guaranteed eventually regardless of timeouts.
LONG POLLING — set it on every queue, always:
$ aws sqs set-queue-attributes --queue-url $Q \
    --attributes ReceiveMessageWaitTimeSeconds=20

  short polling (0):  returns immediately, usually empty, and you pay per call
  long  polling (20): waits up to 20 s for a message; returns instantly when one arrives
                      → FEWER requests AND LOWER latency. There is no trade-off.

FIFO QUEUES — and the parameter that is really two parameters:

$ aws sqs create-queue --queue-name orders.fifo --attributes \
    'FifoQueue=true,ContentBasedDeduplication=true,DeduplicationScope=messageGroup,
     FifoThroughputLimit=perMessageGroupId'

  MessageGroupId    → messages in the SAME group are strictly ordered
                    → messages in DIFFERENT groups process in PARALLEL
                    ⚠️ so the group ID is BOTH your ordering guarantee AND your
                      concurrency limit. One group = one consumer at a time.

  MessageDeduplicationId → duplicates within a 5-MINUTE window are discarded
StandardFIFO
OrderingBest effortStrict, per message group

💡 Choose the message group ID as the smallest thing that needs ordering. If order matters per customer, use the customer ID — thousands of groups, thousands of parallel consumers, and ordering preserved where it matters. Using a constant like "orders" gives you global ordering and a single-threaded consumer, which is how a FIFO queue ends up processing 300 messages a second while the workers sit idle.

Part 3 — SNS: Fan-out and Filtering

$ aws sns create-topic --name order-events --query TopicArn --output text
arn:aws:sns:us-east-1:111122223333:order-events

$ aws sns subscribe --topic-arn $T --protocol sqs \
    --notification-endpoint arn:aws:sqs:us-east-1:111122223333:billing-queue \
    --attributes '{"RawMessageDelivery":"true"}'
   ⚠️ RawMessageDelivery=true, or subscribers receive the message wrapped in an
     SNS envelope and every consumer has to unwrap it.

FILTER POLICIES — subscribers receive only what they asked for:
$ aws sns set-subscription-attributes --subscription-arn $SUB \
    --attribute-name FilterPolicy --attribute-value '{
      "eventType": ["order.refunded", "order.cancelled"],
      "total": [{"numeric": [">=", 100]}]}'

  without a filter: all 5 subscribers receive all 4.2 M messages/month,
                    and 4 of them immediately discard most of them.
  with filters:     each subscriber receives only its subset.

$ aws sns get-subscription-attributes --subscription-arn $SUB \
    --query 'Attributes.FilterPolicyScope' --output text
MessageAttributes                                  ← the default; filters on ATTRIBUTES

$ aws sns set-subscription-attributes --subscription-arn $SUB \
    --attribute-name FilterPolicyScope --attribute-value MessageBody
   → filter on the message BODY instead, so producers need not duplicate
     routing data into attributes.
⚠️ SNS has no retention. If a subscriber endpoint is failing and there is no subscription dead-letter queue, SNS retries per its delivery policy and then discards the message permanently. This is the single biggest difference from a queue, and the reason to terminate fan-out in SQS queues rather than in Lambda functions or HTTP endpoints. Where you must subscribe something directly, attach a DLQ to the subscription.
$ aws sns set-subscription-attributes --subscription-arn $SUB \
    --attribute-name RedrivePolicy \
    --attribute-value '{"deadLetterTargetArn":"arn:aws:sqs:us-east-1:1111:sns-dlq"}'

Part 4 — EventBridge: Routing on Content, and Replay

EventBridge's distinguishing feature is that rules match against the event's content, not against which topic it was published to. Producers emit facts; the bus decides who cares.

$ aws events put-rule --name refunds-over-100 --event-bus-name commerce \
    --event-pattern '{
      "source": ["acme.orders"],
      "detail-type": ["OrderRefunded"],
      "detail": {
        "total": [{"numeric": [">", 100]}],
        "region": ["EU", "UK"],
        "reason": [{"anything-but": ["duplicate"]}]}}'

$ aws events put-targets --rule refunds-over-100 --event-bus-name commerce --targets '[{
    "Id":"1","Arn":"arn:aws:lambda:us-east-1:1111:function:handle-refund",
    "RetryPolicy":{"MaximumRetryAttempts":4,"MaximumEventAgeInSeconds":3600},
    "DeadLetterConfig":{"Arn":"arn:aws:sqs:us-east-1:1111:eb-dlq"},
    "InputTransformer":{
      "InputPathsMap":{"id":"$.detail.orderId","amt":"$.detail.total"},
      "InputTemplate":"{\"order\":\"<id>\",\"amount\":<amt>}"}}]'

ARCHIVE AND REPLAY — turn on the archive BEFORE you need it:
$ aws events create-archive --archive-name commerce-archive \
    --event-source-arn arn:aws:events:us-east-1:1111:event-bus/commerce \
    --retention-days 90

  ...a bad deploy drops three hours of refund events. Instead of reconstructing
  them from logs:
$ aws events start-replay --replay-name refunds-recovery \
    --event-source-arn arn:aws:events:us-east-1:1111:archive/commerce-archive \
    --event-start-time 2026-08-20T09:00:00Z --event-end-time 2026-08-20T12:00:00Z \
    --destination '{"Arn":"arn:aws:events:us-east-1:1111:event-bus/commerce",
                    "FilterArns":["arn:aws:events:us-east-1:1111:rule/commerce/refunds-over-100"]}'
   → replays ONLY to the named rule, so unrelated consumers do not reprocess.
🔑 Replay is what makes EventBridge worth choosing over SNS for domain events. Every other service in this lesson loses a message once it has been delivered and deleted; EventBridge can put three hours of history back through one specific rule. But it is at-least-once and unordered, so a replay delivers events again, out of order, to a consumer that may have partially processed them — which only works if the consumer is idempotent. Turn the archive on at bus creation; it costs storage and cannot be applied retroactively.

Part 5 — Kinesis: An Ordered, Replayable Log

  a STREAM is divided into SHARDS. Each shard:
      1 MB/s or 1,000 records/s IN
      2 MB/s OUT, SHARED across all standard consumers
      strict ordering, by partition key

  retention 24 hours by default, up to 365 days
  each consumer tracks its OWN position → independent replay
SQSKinesis
After processingDeletedStill there until retention expires
Second consumerCompetes for the same messagesReads independently, from any position
OrderingFIFO queues onlyPer shard, always
Replay❌✅
Scaling unitInvisibleShards you manage (or on-demand)
Per-message delete✅❌ — position only
Choose forWork distributionEvent sourcing, analytics, multiple readers
🔑 The distinction is not throughput — it is whether the data has a life after being consumed. SQS is a work queue: a message is a task, and when it is done it is gone. Kinesis is a log: a record is a fact, it stays for the retention period, and any number of consumers can read it at their own pace and re-read it later. If someone asks for "a queue" but then wants a second team to consume the same events, or to reprocess last week, they wanted a stream.
THE HOT SHARD — the same problem as a DynamoDB hot partition:
$ aws kinesis put-record --stream-name events --partition-key "TENANT#acme" --data ...
   → the partition key is HASHED to choose a shard. One key = one shard = 1 MB/s.

$ aws cloudwatch get-metric-statistics --namespace AWS/Kinesis \
    --metric-name WriteProvisionedThroughputExceeded --dimensions Name=StreamName,Value=events \
    --period 60 --statistics Sum --start-time $(date -u -d '10 min ago' +%FT%TZ) \
    --end-time $(date -u +%FT%TZ) --query 'sum(Datapoints[].Sum)' --output text
41882.0                                            ← throttled, on a 20-shard stream

$ aws kinesis put-record --stream-name events \
    --partition-key "TENANT#acme#$((RANDOM % 20))" --data ...
   → spread across shards. Ordering is now per shard, not per tenant — which is
     the trade you are making, so make it deliberately.

ENHANCED FAN-OUT, when several consumers compete for the shard's 2 MB/s:
$ aws kinesis register-stream-consumer --stream-arn $ARN --consumer-name analytics
   → this consumer gets its OWN dedicated 2 MB/s per shard, pushed, ~70 ms latency
     instead of sharing 2 MB/s and polling. Billed per consumer-shard-hour.

$ aws kinesis update-stream-mode --stream-arn $ARN \
    --stream-mode-details StreamMode=ON_DEMAND
   → no shard management; scales automatically. Costs more per GB; right until
     the volume is predictable enough to provision.

Part 6 — Everything Here Is At-Least-Once

ServiceDeliveryOrderingDuplicates because…
SQS standardAt-least-onceBest effortVisibility timeout expiry, redelivery
SQS FIFOExactly-once processingPer message groupOnly outside the 5-minute dedup window
SNSAt-least-onceNone (FIFO topics excepted)Retries
EventBridgeAt-least-onceNoneRetries, replay
KinesisAt-least-oncePer shardConsumer restarts, resharding, batch retries
Lambda (async)At-least-onceNoneAutomatic retries
🔑 There is no exactly-once transport, so exactly-once has to be a property of your consumer. Even SQS FIFO's "exactly-once processing" holds only within a five-minute deduplication window. The universal answer is an idempotency key: derive a deterministic id from the message, record it conditionally, and treat a conditional-check failure as "already done" — the same pattern as the conditional writes in DynamoDB and the idempotency keys in API Gateway.
THE IDEMPOTENT CONSUMER, which every one of these services requires:

  def handle(message):
      key = message["messageId"]              # or a business key: order id + event type
      try:
          ddb.put_item(TableName="processed",
              Item={"k":{"S":key}, "ttl":{"N":str(int(time.time())+86400)}},
              ConditionExpression="attribute_not_exists(k)")
      except ddb.exceptions.ConditionalCheckFailedException:
          return                              # already processed. Not an error.
      do_the_work(message)

  ⚠️ use a BUSINESS key where you can. A redelivered SQS message keeps its
    messageId, but an EventBridge replay or an upstream retry produces a NEW id
    for the SAME logical event — and then the message id deduplicates nothing.

❌ A visibility timeout of 30 seconds on a 45-second job, short polling everywhere, SNS subscribers with no filters and no queues, no dead-letter queues, a FIFO queue with one message group, Kinesis chosen for throughput and keyed on tenant, and consumers that assume each message arrives once. Every message is processed twice because the timeout expires before the delete, so customers get two emails and occasionally two charges, and nothing anywhere reports an error. Short polling issues millions of empty receives a month and pays for each one while adding latency. Five Lambda functions subscribe directly to a topic with no filter policy, so four of them are invoked 4.2 million times a month to immediately discard the message — and when one of them fails, SNS retries briefly and then drops the event permanently, because a topic has no retention. Poison messages redeliver forever, blocking the queue, with no DLQ to catch them. The FIFO queue uses a constant message group, so the ordering guarantee nobody needed has capped throughput at 300 messages a second while the workers idle. Kinesis was chosen over SQS "because it is faster", keyed by tenant, so one customer saturates a single shard on a twenty-shard stream. And every consumer assumes exactly-once delivery, which no service here provides.

✅ Size the visibility timeout from measured p99, poll long, filter at the topic, terminate fan-out in queues, put a DLQ on everything, choose the message group as the smallest unit needing order, key streams for distribution, and make every consumer idempotent. Set the visibility timeout to at least six times the p99 processing time and extend it in-flight for variable work, while understanding that idempotency — not the timeout — is the actual fix. Turn on ReceiveMessageWaitTimeSeconds=20 on every queue, since long polling reduces both cost and latency with no trade-off. Attach filter policies so subscribers receive only what they will act on, and terminate fan-out in SQS queues so each consumer gets its own backlog, retry behaviour and dead-letter queue rather than depending on a topic that keeps nothing. Configure a DLQ with a maxReceiveCount everywhere, and build and test the redrive path before an incident needs it. Make the FIFO message group the smallest entity that requires ordering — a customer, an aggregate — so parallelism scales with the number of entities. Choose Kinesis when you need replay or independent consumers rather than for throughput, and shard the partition key when one value dominates, accepting consciously that ordering then holds per shard rather than per tenant. And give every consumer an idempotency key derived from a business identifier, because a replay or an upstream retry produces a new message id for the same logical event.

Interview Questions

Beginner: When would you use SQS versus SNS?

SQS is a queue: one message, one consumer, work to be done. SNS is a topic: one message, many subscribers, an announcement. If you are distributing work across a pool of workers, that is a queue. If several independent systems need to know something happened, that is a topic.

SQSSNS
Consumers per messageOneMany
RetentionUp to 14 daysNone
DeliveryPull — consumers set the pacePush — regardless of the consumer
Backpressure✅❌

In practice the answer is usually both, in the fan-out pattern: SNS distributes to several SQS queues, one per consumer. That gives you the distribution of a topic and the durability, retry, backlog and dead-letter behaviour of a queue for each subscriber independently. Subscribing a Lambda function straight to a topic gives you neither buffering nor a durable retry story — and because SNS keeps nothing, a failing subscriber loses the message permanently.

Beginner: What is the visibility timeout, and what goes wrong with it?

When a consumer receives an SQS message, the message is not deleted — it becomes invisible to other consumers for the duration of the visibility timeout. The consumer must explicitly call DeleteMessage when it finishes. If it does not, the message becomes visible again and another consumer picks it up.

The classic failure is a timeout shorter than the processing time — the default is 30 seconds, and a job that takes 45 will always be redelivered while the first consumer is still working on it. The result is duplicate processing, and it presents as duplicate emails or double charges rather than as an error, because nothing has technically failed.

$ aws sqs set-queue-attributes --queue-url $Q --attributes VisibilityTimeout=300

Set it to at least six times p99 processing time, and extend it in-flight with ChangeMessageVisibility for variable work. But the honest answer is that the timeout only reduces the frequency: SQS standard is at-least-once, so duplicates are guaranteed eventually, and the real fix is an idempotent consumer.

Mid: A FIFO queue is limited to 300 messages per second while the workers are idle. Explain.

All the messages share one MessageGroupId. In a FIFO queue the group ID is simultaneously the ordering guarantee and the unit of parallelism: messages in the same group are processed strictly in order, which means one at a time, by one consumer. Different groups process in parallel.

So a constant group ID like "orders" requests global ordering — which is almost never the actual requirement — and gets a single-threaded pipeline as the price.

  ❌ MessageGroupId = "orders"           → 1 group,      1 consumer,    ~300 msg/s
  ✅ MessageGroupId = f"CUSTOMER#{id}"   → 1000s groups, 1000s parallel, order preserved
                                            per customer, which was the real requirement

The design question to ask is "what actually needs ordering?" Almost always it is per-entity — events for one customer, one order, one account — not global. Choosing the smallest entity that needs ordering gives you both the guarantee and the parallelism.

Worth adding: also enable FifoThroughputLimit=perMessageGroupId with DeduplicationScope=messageGroup (high-throughput mode), which raises the per-queue ceiling by an order of magnitude. And if nothing genuinely needs ordering, a standard queue removes the constraint entirely — FIFO is chosen far more often than it is needed.

Mid: A downstream service was broken for three hours and events were lost. How do you recover, and how do you prevent it?

Recovery depends entirely on which transport was used, and that is the lesson:

TransportCan you recover?
SNS direct to Lambda/HTTPNo — no retention; retried and discarded
SNS → SQSYes — the messages waited in the queue (up to 14 days)
SQS with a DLQYes — redrive from the DLQ
EventBridge with an archiveYes — replay the time range
EventBridge without oneNo, and the archive is not retroactive
KinesisYes — reset the iterator; the records are still there
$ aws events start-replay --replay-name recovery \
    --event-source-arn arn:aws:events:...:archive/commerce-archive \
    --event-start-time 2026-08-20T09:00:00Z --event-end-time 2026-08-20T12:00:00Z \
    --destination '{"Arn":"...:event-bus/commerce","FilterArns":["...:rule/refunds"]}'

Prevention has three parts. Terminate fan-out in queues rather than in push targets, so a failing consumer accumulates a backlog instead of losing data. Enable the EventBridge archive at bus creation, since it cannot be applied to the past. And put a DLQ on every queue, subscription and event target — with an alarm on depth, because a dead-letter queue nobody watches is just delayed data loss.

One caveat on replay: it is at-least-once and unordered, and it will re-deliver events the consumer may have partially processed. Always replay with FilterArns scoped to the affected rule, and only into consumers you know are idempotent.

Senior: Design the event backbone for a commerce platform: order events consumed by billing, fulfilment, analytics and a partner webhook.

Four consumers with four different requirements — so the answer is not one transport. Classify each by ordering, replay, backpressure and failure tolerance before choosing anything.

ConsumerNeedsTransport
BillingOrder per account; must never lose an eventFIFO queue, group = account id
FulfilmentReliable, order irrelevant, burstyStandard SQS + DLQ
AnalyticsReplay, reprocessing, multiple readersKinesis → Firehose → S3
Partner webhookUntrusted, slow, flaky endpointSQS + retry + DLQ, never a push target

The backbone itself is EventBridge, on a custom bus, with an archive from day one. Producers emit domain facts (OrderPlaced, OrderRefunded) and know nothing about consumers; rules route by content to each consumer's own transport. Adding a fifth consumer is a rule, not a producer change — that decoupling is the whole point, and it is why a bus beats a topic here.

The partner webhook deserves emphasis because it is where these designs usually fail: a third-party HTTP endpoint is slow, unreliable and occasionally down for hours. It must be behind a queue with its own retry policy and DLQ, so its failures cannot apply backpressure to anything else, and it should be rate-limited so a recovering partner is not overwhelmed by the backlog.

Cross-cutting requirements: every consumer idempotent on a business key, since every transport here is at-least-once and a replay produces new message ids for old events; payloads over 256 KB in S3 with references on the bus; a DLQ and a depth alarm on every path; and the schema treated as a contract — the EventBridge schema registry plus additive-only changes, because an event consumed by four teams is a published API.

What I would push back on: making everything FIFO "to be safe". Ordering costs parallelism, and only billing needs it. And I would resist a single shared queue that several teams consume — that reintroduces the coupling the bus removes, and it makes one team's poison message everyone's outage.

Senior: How do you achieve exactly-once processing on AWS?

You do not achieve it in the transport — you achieve it in the consumer. Every service here is at-least-once: SQS standard, SNS, EventBridge, Kinesis and asynchronous Lambda all guarantee delivery at least once and explicitly permit duplicates. Even SQS FIFO's "exactly-once processing" holds only within a five-minute deduplication window.

So the design goal is idempotency, which makes duplicate delivery harmless rather than impossible:

  key = f"{event['orderId']}#{event['type']}"        # BUSINESS key, not message id
  try:
      ddb.put_item(TableName="processed",
          Item={"k":{"S":key},"ttl":{"N":str(int(time.time())+86400)}},
          ConditionExpression="attribute_not_exists(k)")
  except ConditionalCheckFailedException:
      return                                          # already done — not an error
  do_the_work(event)

The subtlety that matters is the choice of key. A redelivered SQS message keeps its messageId, so deduplicating on it works for that case — but an EventBridge replay, an upstream retry, or a producer resending after a timeout all generate a new id for the same logical event, and message-id deduplication silently fails exactly when you most need it. Derive the key from business identifiers.

The second subtlety is atomicity. Recording the key and doing the work are two operations, so a crash between them leaves either a duplicate or a lost update. Where the work is a write to the same store, make it one conditional write or one transaction. Where it is an external side effect, record the key first with a status of in-progress and reconcile — accepting that you have chosen "at most once" for that window and saying so explicitly.

And design the work to be naturally idempotent where you can, which beats any bookkeeping: SET status = 'shipped' is safe to repeat, while SET count = count + 1 is not. That distinction removes the problem instead of managing it.

🏋️ Exercises

1 (easy): Reproduce duplicate processing from a visibility timeout, measure it, and fix it two ways.
Solution 
$ Q=$(aws sqs create-queue --queue-name jobs --query QueueUrl --output text)
$ aws sqs get-queue-attributes --queue-url $Q --attribute-names VisibilityTimeout \
    --query 'Attributes.VisibilityTimeout' --output text
30                                                 ← the default

$ cat > worker.py <<'PY'
import boto3, time, sys, collections
s = boto3.client("sqs"); Q = sys.argv[1]; WORK = float(sys.argv[2])
seen = collections.Counter()
end = time.time() + 120
while time.time() < end:
    r = s.receive_message(QueueUrl=Q, MaxNumberOfMessages=1, WaitTimeSeconds=5)
    for m in r.get("Messages", []):
        seen[m["Body"]] += 1
        time.sleep(WORK)                           # simulate the job
        s.delete_message(QueueUrl=Q, ReceiptHandle=m["ReceiptHandle"])
print("processed:", sum(seen.values()), " distinct:", len(seen),
      " duplicates:", sum(v-1 for v in seen.values() if v > 1))
PY

$ python3 worker.py $Q 45 &
$ python3 worker.py $Q 45 &
$ wait

🎯 Key Takeaways

  • Pick by the question: work done once (SQS), an announcement heard by many (SNS), routing by content with replay (EventBridge), or an ordered replayable log (Kinesis).
  • Only queues give backpressure. Topics push regardless of consumer health, which is why SNS → SQS fan-out is the real pattern — each consumer gets its own backlog, retries and DLQ.
  • SNS has no retention: a failing subscriber with no DLQ loses the message permanently.
  • A visibility timeout shorter than processing time processed 14 of 20 jobs twice — with perfect metrics and no error anywhere.
  • Set the timeout to ≥6× p99 and extend in-flight with ChangeMessageVisibility — but only idempotency makes redelivery harmless, and redelivery is guaranteed eventually.
  • Long polling is cheaper AND faster: 52 M requests/month → 129,600 (401×) and median latency 412 ms → 38 ms. There is no trade-off; set ReceiveMessageWaitTimeSeconds=20 everywhere.
  • Without a DLQ, one poison message was received 43 times in 90 seconds and the queue never drained. maxReceiveCount + DLQ capped it at 3.
  • Give the DLQ 14-day retention, alarm on its depth, and build and rate-limit the redrive path before you need it.
  • The FIFO message group ID is both the ordering guarantee and the parallelism limit: one group measured 304 msg/s with 20 idle workers, 60 groups measured 18,420 msg/s with ordering still strict per customer.
  • Choose the group as the smallest entity that needs ordering, add FifoThroughputLimit=perMessageGroupId, and ask whether you need FIFO at all.
  • SNS filter policies removed 40% of all deliveries and 99.2% for one subscriber — each avoided delivery saves a publish, a send, a receive, a delete and an invocation.
  • Set RawMessageDelivery=true, or every consumer unwraps an SNS envelope.
  • EventBridge routes on event content, so adding a consumer is a rule rather than a producer change — but it guarantees no ordering at all.
  • The EventBridge archive is not retroactive. Create it with the bus; it is the only mechanism here that can put three hours of history back.
  • Replay with FilterArns scoped to the affected rule — a bus-wide replay makes every healthy consumer reprocess.
  • Kinesis differs from SQS by replay and independent consumers, not throughput: an SQS message is a task that disappears, a Kinesis record is a fact that persists.
  • A Kinesis partition key with one hot value throttles on a single shard's 1 MB/s — the same arithmetic as a DynamoDB hot partition, and sharding it trades per-tenant ordering for per-shard ordering.
  • Use enhanced fan-out when several consumers would otherwise divide a shard's 2 MB/s.
  • Every service here is at-least-once — even SQS FIFO's guarantee is a 5-minute dedup window. Exactly-once is a property of your consumer.
  • Derive idempotency keys from business identifiers: a replay or upstream retry produces a new message id for the same logical event, and message-id deduplication fails exactly when you need it.
  • Prefer naturally idempotent work — SET status = 'shipped' is safe to repeat, count = count + 1 is not — which removes the problem instead of managing it.
