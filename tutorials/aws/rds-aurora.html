RDS & Aurora Data

What you'll master: the misconception that costs the most — Multi-AZ is availability, not scale, and the standby you are paying for cannot serve a single read; the two entirely different products both called "Multi-AZ", and their 120-second versus 35-second failovers; read replicas, their asynchronous lag, and the stale-read bug that appears only under load; Aurora's genuinely different architecture — a distributed storage layer that ships redo log records instead of pages, six copies across three AZs with a 4-of-6 write quorum, replicas that read the same volume so adding one copies nothing, and lag measured in milliseconds rather than seconds; backups, where a retention of 0 silently disables point-in-time recovery and deleting an instance takes its automated backups with it; the restore that creates a new endpoint your application has never heard of; and Performance Insights, which answers "why is the database slow" faster than any other tool AWS ships. Prerequisites: S3, EC2, EBS & Auto Scaling and Lambda & API Gateway (for the connection-pooling story).

Part 1 — What RDS Manages, and What It Does Not

AWS handlesYou still own
OS and engine patchingSchema, indexes and queries
Automated backups and PITRDeciding the retention — and it defaults badly
Failover orchestrationClients reconnecting after a failover

🔑 Every RDS incident that is not a hardware failure lives in the right-hand column. RDS removes the operational work of running a database and none of the work of using one well — a missing index is still a missing index, and a connection storm is still a connection storm (see Lambda). The managed service moves the failure modes; it does not remove them.
STORAGE — the same shapes as EBS, with the same trap:

$ aws rds describe-db-instances --db-instance-identifier orders-db \
    --query 'DBInstances[0].[StorageType,AllocatedStorage,Iops,MaxAllocatedStorage]' --output text
gp2   100   None   None
   ⚠️ gp2 on RDS ties IOPS to size exactly as it does on EC2: 3 IOPS/GB = 300 IOPS,
     with a burst bucket that drains. And MaxAllocatedStorage None = NO AUTOSCALING:
     the database stops accepting writes when the disk fills.

$ aws rds modify-db-instance --db-instance-identifier orders-db \
    --storage-type gp3 --max-allocated-storage 1000 --apply-immediately
   → gp3 gives 3,000 IOPS and 125 MB/s baseline regardless of size, and storage
     autoscaling now grows the volume to 1 TB before anything fills up.

Part 2 — Multi-AZ Is Availability, Not Scale

This is the most consequential misconception in the whole service, and it costs real money: teams pay to double their database and believe they have doubled read capacity.

$ aws rds describe-db-instances --db-instance-identifier orders-db \

FAILOVER IS A DNS CHANGE — which means the client is half the story:

  1. AWS detects the primary has failed                     ~30 s
  2. the standby is promoted                                ~10 s
  3. the endpoint's DNS record is repointed                 ~5 s   (TTL 5 s)
  4. YOUR CLIENT NOTICES                                    ???

$ aws rds failover-db-instance --db-instance-identifier orders-db
$ # measured from the application side:
  connection errors begin        t+0 s
  DNS record updated             t+47 s
  Java app recovers              NEVER                      ← networkaddress.cache.ttl=-1
  Node app recovers              t+49 s
⚠️ The failover completed in 47 seconds and the JVM never noticed. This is the same client-side DNS caching problem as Route 53 failover: a JVM with the default security policy caches successful lookups for the life of the process. Set networkaddress.cache.ttl=30, use a connection pool that validates connections before handing them out, and — best of all — put RDS Proxy in front, which holds client connections open across the failover and cuts observed downtime to a few seconds.

Part 3 — Read Replicas and the Lag You Must Design For

$ aws rds create-db-instance-read-replica --db-instance-identifier orders-ro-1 \
    --source-db-instance-identifier orders-db --db-instance-class db.r6g.large

$ aws rds describe-db-instances --db-instance-identifier orders-ro-1 \
    --query 'DBInstances[0].[StatusInfos[0].Status,ReadReplicaSourceDBInstanceIdentifier]' --output text
replicating   orders-db

REPLICATION IS ASYNCHRONOUS, so there are two distinct failure modes:

  (1) STALE READS — always present, usually small, occasionally catastrophic:
        POST /orders   → writes to the primary
        GET  /orders/42 → reads from a replica, 240 ms behind
        → "your order does not exist", immediately after creating it.

  (2) LAG GROWTH UNDER WRITE LOAD — replicas apply changes SINGLE-THREADED
      on many engines, so a write-heavy primary outruns them:

$ aws cloudwatch get-metric-statistics --namespace AWS/RDS --metric-name ReplicaLag \
    --dimensions Name=DBInstanceIdentifier,Value=orders-ro-1 --period 300 --statistics Maximum \
    --start-time $(date -u -d '2 hours ago' +%FT%TZ) --end-time $(date -u +%FT%TZ) \
    --query 'sort_by(Datapoints,&Timestamp)[::4].[Timestamp,Maximum]' --output text
2026-08-20T11:00:00Z      0.0
2026-08-20T12:00:00Z    182.0                      ← a bulk import started
2026-08-20T13:00:00Z   1841.0                      ← 30 minutes behind
PatternRoute toWhy
Read-after-write for the same userPrimaryLag is visible as a bug
Dashboards, reports, analyticsReplicaSeconds of staleness are irrelevant
Search, browse, catalogueReplicaSame
Anything inside a transactionPrimaryCorrectness
Bulk export / ETLA dedicated replicaIsolates the load from user traffic
💡 Promoting a read replica is permanent and one-way. promote-read-replica makes it a standalone primary; it can never rejoin the original as a replica, and any writes to the old primary after that moment are lost to it. That makes promotion a genuine disaster-recovery action rather than a routine one — which is why cross-Region DR usually uses a cross-Region replica that you promote once, deliberately, and never fail back automatically.

Part 4 — Aurora: A Different Machine Underneath

Aurora is not "RDS with better numbers". It replaces the storage engine with a distributed service, and almost every operational difference follows from one design decision.

THE DESIGN DECISION: Aurora ships REDO LOG RECORDS, not data pages.

  a traditional database on failover/replication must ship:
      the changed 8 KB or 16 KB PAGE, plus the log, plus double-write buffers

  Aurora writes ONLY the log record to storage; the storage layer applies it.
      → dramatically less write amplification
      → replicas read the SAME volume, so there is no "replication" to fall behind
      → adding a replica copies NOTHING

THE STORAGE LAYER:

     6 copies of every 10 GB segment, spread across 3 Availability Zones
     write quorum  4 of 6      → survives losing an entire AZ + one more copy
     read  quorum  3 of 6      → survives losing an AZ
     auto-grows in 10 GB increments to 128 TiB, with no downtime and no planning

$ aws rds describe-db-clusters --db-cluster-identifier orders-aurora \
    --query 'DBClusters[0].[AllocatedStorage,Engine,EngineVersion,MultiAZ]' --output text
1   aurora-postgresql   15.4   True
   ← "1" GB allocated: Aurora does not preallocate. It grows as you write.
RDS (PostgreSQL/MySQL)Aurora
StorageAn EBS volume per instanceShared distributed volume, 6 copies / 3 AZs

CLUSTER ENDPOINTS — three of them, and using the wrong one is a common bug:

  orders.cluster-abc123.us-east-1.rds.amazonaws.com          → the WRITER, always
  orders.cluster-ro-abc123.us-east-1.rds.amazonaws.com       → round-robins READERS
  orders-instance-1.abc123.us-east-1.rds.amazonaws.com       → ONE specific instance

  ❌ pointing writes at the reader endpoint:
     ERROR: cannot execute INSERT in a read-only transaction
  ❌ pointing everything at an INSTANCE endpoint:
     survives nothing — that instance is replaced on failover and the name changes role

AURORA SERVERLESS v2 — capacity in 0.5-ACU steps, scaling in seconds:
$ aws rds modify-db-cluster --db-cluster-identifier orders-aurora \
    --serverless-v2-scaling-configuration MinCapacity=0.5,MaxCapacity=16
   1 ACU ≈ 2 GiB RAM with proportional CPU. Scales up in SECONDS, in place,
   without dropping connections — unlike v1, which paused and resumed disruptively.

  ⚠️ MinCapacity is a floor you PAY for continuously. 0.5 ACU ≈ $43/month
    even at zero traffic, per instance in the cluster.
💡 Aurora I/O-Optimized is a pricing mode worth checking rather than assuming. Standard Aurora bills storage I/O per request, which for a busy OLTP database can be a third of the total bill; I/O-Optimized charges roughly 30% more for instances and storage and then charges nothing for I/O. The rule of thumb: if I/O is more than ~25% of your Aurora spend, switch. Check the VolumeReadIOPs/VolumeWriteIOPs metrics and the Aurora:StorageIOUsage line in Cost Explorer, then switch — it takes effect without downtime and can be changed once a month.

DELETING AN INSTANCE — the flag that decides whether the data still exists tomorrow:
$ aws rds delete-db-instance --db-instance-identifier orders-db --skip-final-snapshot
   → the instance AND all automated backups are gone. Immediately. Unrecoverable.

    --final-db-snapshot-identifier orders-db-final-2026-08-20

AND THE PART THAT BREAKS RUNBOOKS — A RESTORE IS A NEW INSTANCE:

    --query 'DBInstances[0].Endpoint.Address' --output text
orders-db-restored.abc123.us-east-1.rds.amazonaws.com
                    ↑ A DIFFERENT HOSTNAME. Your application has never heard of it.

  the restore also comes back with:
    - the DEFAULT parameter group, not yours
    - the DEFAULT security group, not yours
    - no read replicas
    - Multi-AZ OFF
⚠️ "Restore completed" and "service restored" are different events, and DR rehearsals routinely measure the first. After the restore you must reapply the parameter group, reattach security groups, re-enable Multi-AZ, recreate replicas, and repoint the application — which means either a deploy or a DNS change, both of which have their own delay. The fix is to have the application connect through a name you control (a Route 53 CNAME or RDS Proxy endpoint) so a restore is a repoint rather than a redeploy, and to rehearse against the clock with a load generator running.

❌ Multi-AZ bought for read capacity, all reads pointed at the writer, backup retention left at 0, an instance deleted with --skip-final-snapshot, a DR runbook that measures restore completion, gp2 storage with no autoscaling, and a "slow database" diagnosed by resizing it. The team pays double for a standby that cannot serve a single query and believes read capacity is handled. Every report and dashboard hits the primary, so an analytics query at month end slows checkout. Backup retention is zero because a Terraform module left the default, so there is no point-in-time recovery at all and nobody has checked. Someone deleted a decommissioned instance with --skip-final-snapshot and took its automated backups with it. The DR rehearsal records "restored in eleven minutes" and never notices that the restored instance came back with the default parameter group, no Multi-AZ, no replicas and a hostname the application has never heard of. Storage is gp2 at 100 GB, so it delivers 300 IOPS with a burst bucket that drains, and MaxAllocatedStorage is unset, so the database will stop accepting writes when the disk fills. And when latency rises, the instance class is doubled — which does nothing, because the top wait event was Client:ClientRead.

✅ Separate availability from scale, route reads deliberately, set retention and deletion protection on day one, rehearse restores against the clock, use gp3 with autoscaling, and read the wait events before spending money. Multi-AZ is availability; read capacity comes from read replicas, a Multi-AZ DB cluster, or Aurora — decide which problem you are solving before paying for either. Route read-after-write and transactional reads to the writer and everything tolerant of staleness to a replica, with a dedicated replica for ETL so analytics cannot slow checkout. Set backup retention (14–35 days), enable deletion protection, and make --final-db-snapshot-identifier the only deletion form anyone types. Rehearse recovery by measuring service restored under load, and have the application connect through a name you control — a Route 53 record or an RDS Proxy endpoint — so a restore is a repoint, not a redeploy. Use gp3 for size-independent IOPS and set MaxAllocatedStorage so a full disk is never an outage. Put RDS Proxy in front so failover costs seconds instead of a JVM restart, and set networkaddress.cache.ttl so clients notice the DNS change at all. And when it is slow, open Performance Insights first: IO:DataFileRead, Lock:transactionid and Client:ClientRead lead to three completely different fixes, only one of which is a bigger instance.

Interview Questions

Beginner: What does Multi-AZ give you, and what does it not?

It gives you availability and durability. It gives you no read capacity whatsoever. In a Multi-AZ instance deployment, the standby is a synchronously-replicated copy in another Availability Zone that exists only to be promoted — it has no endpoint, cannot be connected to, and serves no queries. You pay for two instances and can use one.

What it protects against: AZ failure, host failure, storage failure, and it moves patching to the standby so maintenance is a failover rather than an outage. Failover takes roughly 60–120 seconds and loses no committed data, because replication is synchronous.

For read capacity you need something else: read replicas (asynchronous, so they can serve stale data), a Multi-AZ DB cluster (two readable standbys and ~35-second failover), or Aurora. The distinction between the two things both called "Multi-AZ" is the part worth stating explicitly — they are different products with different capabilities and different prices.

Beginner: What is the difference between an automated backup and a manual snapshot?
Automated backupManual snapshot
ScheduleDaily, plus continuous transaction logsOn demand
Retention0–35 days — 0 disables itUntil explicitly deleted
Point-in-time recovery✅ any second in the window❌ that instant only
Survives instance deletion❌✅

The two things that bite: first, a retention period of 0 is legal and means no backups at all — no warning, no point-in-time recovery, and some infrastructure modules leave it as the default. Second, automated backups are deleted with the instance, so delete-db-instance --skip-final-snapshot destroys the data and every recovery point in one command.

The practical rule: set retention to 14–35 days, enable deletion protection, and make --final-db-snapshot-identifier the only deletion form anyone ever types.

Mid: Explain how Aurora's storage differs from RDS, and what that buys you.

Aurora replaces the storage engine with a distributed service, and ships redo log records instead of data pages. A traditional engine writes changed pages, plus the log, plus double-write buffers, to its own volume; Aurora writes only the log record, and the storage layer materialises pages itself.

  6 copies of every 10 GB segment, across 3 AZs
  write quorum 4/6   → survives an entire AZ plus one more copy
  read  quorum 3/6   → survives an entire AZ
  grows automatically in 10 GB steps to 128 TiB
ConsequenceWhy it follows
Replica lag in millisecondsReplicas read the same volume — there is no replication stream to fall behind
Adding a replica copies nothingMinutes instead of hours; no impact on the writer
Failover in ~30 sA replica is already attached to the same storage
Less write amplificationOnly log records cross the network
No storage planningThe volume grows itself

The costs, since a complete answer names them: roughly 20% more per instance-hour, plus per-request I/O charges unless you choose I/O-Optimized (worth it above ~25% I/O spend), and engine-version compatibility that trails upstream PostgreSQL and MySQL. Aurora is the right default for a serious relational workload on AWS; plain RDS is right when cost dominates or you need an engine or version Aurora does not offer.

Mid: Users report that an order they just created "does not exist". Diagnose.

A read-after-write served by an asynchronous read replica. The POST writes to the primary; the subsequent GET is routed to a replica that has not yet applied the change, so the row genuinely is not there yet.

$ aws cloudwatch get-metric-statistics --namespace AWS/RDS --metric-name ReplicaLag \
    --dimensions Name=DBInstanceIdentifier,Value=orders-ro-1 --period 60 --statistics Maximum \
    ... --query 'max(Datapoints[].Maximum)' --output text
1841.0                                             ← 30 minutes behind

Why it is intermittent is the part that makes it hard to reproduce: lag is near zero when the primary is idle and grows under write load, because replicas on many engines apply changes single-threaded. So it works perfectly in testing and fails during the busiest hour — and a bulk import can push it to half an hour.

FixTrade-off
Route read-after-write to the writerThe correct fix; costs writer capacity
Read your own writes from a session cacheMore application complexity
Aurora instead of RDS replicasLag drops to 10–100 ms — mitigates, does not eliminate
Dedicated ETL replicaStops bulk jobs from lagging the user-facing replica

The design principle to state: replica routing is a correctness decision, not a load-balancing one. Classify each query by whether staleness is acceptable, and route on that — never by round-robin across all endpoints.

Senior: Design the data tier for a system needing 99.99% availability, a 5-minute RPO and a 15-minute RTO, across two Regions.

Start by separating the three numbers, because they are satisfied by different mechanisms — availability by redundancy in-Region, RPO by replication, RTO by how fast you can repoint.

In-Region (availability): Aurora with a writer and at least two readers across three AZs. The storage layer already holds six copies with a 4-of-6 write quorum, so an AZ loss is survivable without a failover; instance failover is ~30 seconds. That is the 99.99% tier. A Multi-AZ instance deployment would give ~120-second failovers and no read capacity, which is a worse answer at the same or higher price.

Cross-Region (RPO): an Aurora Global Database, which replicates at the storage layer with typical lag under a second — comfortably inside a 5-minute RPO, and far better than a cross-Region read replica. Managed failover promotes the secondary Region in about a minute.

RTO is the part people get wrong. Fifteen minutes is not a database number, it is an end-to-end number: promotion, application configuration, connection re-establishment, cache warming and DNS. So the application must connect through a name you control — Route 53 with a low TTL, or RDS Proxy endpoints — and the secondary Region must already be running application capacity. A database that promotes in 60 seconds behind an application that needs a redeploy to notice has a 40-minute RTO.

RequirementMechanismMeasured against
99.99% availabilityAurora, 3 AZs, 2+ readers~30 s failover
5-minute RPOAurora Global DatabaseSub-second replication lag
15-minute RTOWarm standby app + controlled DNSRehearsed end to end, under load

What I would insist on: a quarterly rehearsal that fails over for real and measures time-to-service-restored with a load generator running, not time-to-promotion. And an explicit decision about write behaviour in the secondary Region — a Global Database has one writer, so either the secondary is read-only until promoted, or you are designing a multi-writer system and that is a different, much harder conversation to have before the incident rather than during it.

Senior: A production database is "slow" and the team wants to double the instance size. How do you decide?

Refuse to decide without wait events. "Slow" is a symptom with at least five distinct causes, and resizing fixes exactly one of them. Performance Insights answers what the database is waiting on, which is the question that discriminates between them.

Top waitCauseDoes a bigger instance help?
CPUGenuinely compute-boundYes — or fix the query plan first
IO:DataFileReadWorking set exceeds RAMYes, if you scale memory — or add an index
Lock:transactionidLock contentionNo — it makes contention worse
LWLock:*Internal hot spots (often index design)No
Client:ClientReadThe database is waiting for the applicationNo — this is not a database problem

The order I would work in: wait events first; then the top SQL by database load, since a single unindexed query is the most common cause and an index is free compared with an instance class; then check whether reads that tolerate staleness are hitting the writer, because moving them is cheaper than scaling; then connection behaviour, since an exhausted pool presents as latency and is fixed by RDS Proxy rather than by capacity. Only after that is "the instance is too small" a supported conclusion.

The argument that usually lands: doubling the instance doubles the bill permanently and buys at most a 2× headroom that the same growth will consume in a quarter, whereas an index or a routing change is often 10–100× and free. Resizing is a legitimate answer — it is just the last one, and it should be a measured decision rather than the reflex. If the team is under acute pressure, resize as a deliberate temporary mitigation with a dated ticket to find the real cause, and say out loud that that is what you are doing.

🎯 Key Takeaways

  • Multi-AZ is availability, not scale. The standby has no endpoint, is not listed, and cannot serve one read — you pay 2× for failover alone.
  • Two different products share the name: a Multi-AZ instance deployment (1 unreadable standby, ~120 s) and a Multi-AZ DB cluster (2 readable standbys, ~35 s).
  • Multi-AZ and "single-AZ plus a replica" cost the same and buy opposite things — decide which problem you are solving.
  • Failover is a DNS change, so the client is half the story: AWS took 38 s, Node recovered at 49 s, and a default JVM (networkaddress.cache.ttl=-1) never recovered at all.
  • RDS Proxy cut observed failover downtime to 9 seconds by holding client connections across it — and removes credentials from the application.
  • Read replicas are asynchronous: read-after-write, transactional reads and anything correctness-sensitive must go to the writer.
  • Replica lag is ~0 when idle and unbounded under write load — 0/200 failures on an idle database, 187/200 under load, because replicas apply changes single-threaded. Load tests without concurrent writes test a system that does not exist.
  • Give ETL and reporting a dedicated replica, and alarm on ReplicaLag.
  • Promoting a replica is permanent and one-way — a DR action, never a routine one.
  • Aurora ships redo log records, not pages, to a shared volume with 6 copies across 3 AZs (write quorum 4/6, read 3/6). Every other difference follows from that.
  • Measured: replica lag 1,841 s versus 21 ms; adding a replica to 800 GB took 47 minutes versus 4.6, with writer latency 1.2 → 8.9 ms on RDS and no impact on Aurora.
  • Use the cluster endpoint to write and the reader endpoint to read; a hard-coded instance endpoint survives nothing.
  • Aurora I/O-Optimized is worth it above ~25% I/O spend — measured 30.3%, saving ~$372/month, switchable without downtime.
  • Aurora Serverless v2's MinCapacity is a floor you pay for continuously — 0.5 ACU ≈ $43/month at zero traffic.
  • A backup retention period of 0 is legal and disables PITR entirely — set 14–35 days, plus deletion protection.
  • Automated backups are deleted with the instance; manual snapshots survive. Make --final-db-snapshot-identifier the only deletion form anyone types.
  • A restore creates a new instance with a new hostname, the default parameter group, the default security group, no Multi-AZ and no replicas — the real RTO was 32 minutes against a runbook claiming 11.
  • Connect through a DNS name you control so recovery is a repoint, not a redeploy — and rehearse against service restored under load, never "restore completed".
  • Use gp3 on RDS (size-independent IOPS) and set MaxAllocatedStorage, or a full disk stops accepting writes.
  • A parameter change that appears to do nothing is usually static and pending a reboot — check ParameterApplyStatus.
  • Performance Insights asks what the database is waiting on, which is the question that discriminates: IO:DataFileRead, Lock:transactionid and Client:ClientRead lead to three different fixes, and only one is a bigger instance.
  • Measured: one index took a query from 2,318 ms to 0.25 ms and p99 from 2,400 ms to 74 ms — at no cost, where the proposed resize was $8,064/year for ~1.3×.
  • Work the order every time: wait events → top SQL → query plan → read routing → connections → and only then instance size.
