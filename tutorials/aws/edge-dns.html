Route 53, Load Balancers & CloudFront Networking

What you'll master: the four hops every external request takes — DNS → CDN → load balancer → target — and how to tell which one broke, because all four can return a five-hundred; alias records, which solve the apex-CNAME problem that no other DNS provider can; routing policies, and why DNS failover is bounded by TTL plus a client cache you do not control — measured at 11 minutes on a 60-second TTL, and forever on a default JVM; health checks that report healthy while the application is down, because they check the load balancer that is checking the targets; ALB versus NLB, including client-IP preservation rules that differ by target type, and cross-zone load balancing that is free and always on for ALB but off and billable for NLB; the keepalive mismatch that produces sporadic 502s no deploy can explain; CloudFront's cache key, where one header turned a 94% hit ratio into 0.3% and omitting another served one customer's page to another; and a decoder table that turns 502/503/504 into a diagnosis instead of a guess. Prerequisites: VPCs, Subnets & Security Groups and Connecting VPCs, PrivateLink & On-Prem.

Part 1 — Route 53, and the Record Type Only AWS Has

Route 53 is three products sharing a name: a domain registrar, an authoritative DNS service, and a health checking service. The DNS service is the interesting one, and it has one record type that does not exist anywhere else.

THE APEX PROBLEM, which every DNS provider has and only AWS solves cleanly:

  RFC 1034 forbids a CNAME coexisting with any other record at the same name.
  A zone apex (acme.com) MUST have SOA and NS records.
  → therefore acme.com can NEVER be a CNAME.

  But an ALB's address is a hostname, not an IP:
$ dig +short shop-alb-1234.us-east-1.elb.amazonaws.com
54.211.14.9
44.202.8.117                                       ← and these CHANGE without notice

✅ THE ALIAS RECORD — resolved inside Route 53, so no CNAME is ever sent to the client:

$ aws route53 change-resource-record-sets --hosted-zone-id Z1234567890ABC \
    --change-batch '{"Changes":[{"Action":"UPSERT","ResourceRecordSet":{
      "Name":"acme.com","Type":"A",
      "AliasTarget":{"HostedZoneId":"Z35SXDOTRQ7X7K",
                     "DNSName":"shop-alb-1234.us-east-1.elb.amazonaws.com",
                     "EvaluateTargetHealth":true}}}]}'

$ dig +short acme.com
54.211.14.9                                        ← an A record. At the apex. Tracking the ALB.
44.202.8.117
CNAMEAlias
Allowed at the zone apex❌ Never✅
Query costChargedFree to AWS targets
Extra lookup for the clientYes — an extra round tripNo — resolved server-side
Tracks the target's changing IPsYesYes
Can targetAny hostnameALB/NLB, CloudFront, S3 website, API Gateway, another record in the zone
Can health-check the target❌✅ EvaluateTargetHealth
🔑 Use an alias record for every AWS target, apex or not. It is free, saves the client a round trip, and — the part people miss — EvaluateTargetHealth: true makes the record disappear from responses when the target is unhealthy, without configuring a separate health check. That is the cheapest failover mechanism in AWS and it costs nothing.
TTL is the only lever you have over how fast a change propagates, and it is a
BEFORE-THE-FACT decision — lowering it during an incident does nothing for
resolvers that already cached the old value:

$ dig acme.com | grep -A1 'ANSWER SECTION'
;; ANSWER SECTION:
acme.com.       300     IN      A       54.211.14.9      ← 300s: minimum 5 min to move traffic

  Lower the TTL to 60 the DAY BEFORE a migration, not during it.
  Alias records to AWS targets inherit the target's TTL (60s for ELB) — you cannot set it.

⚠️ DNS is a coarse traffic-splitting tool. The unit of granularity is a resolver's cache entry, not a request, so weighted routing gives you approximately the ratio only across many independent resolvers. For a real canary — 5% of requests, shifted instantly, with per-request metrics — split at the load balancer with weighted target groups, not at DNS. Use weighted DNS for coarse, slow moves such as a Region migration, where "roughly 10%, over an hour" is the actual requirement.

Part 3 — Health Checks, and Failover That Does Not Fail Over

$ aws route53 create-health-check --caller-reference hc-$(date +%s) \
    --health-check-config '{"Type":"HTTPS","FullyQualifiedDomainName":"api.acme.com",
      "ResourcePath":"/health","Port":443,"RequestInterval":10,"FailureThreshold":2}' \
    --query 'HealthCheck.Id' --output text
a1b2c3d4-5e6f

  checked from 15+ locations worldwide; unhealthy when >18% of checkers fail
  RequestInterval 10s + FailureThreshold 2  →  ~20-30s to DETECT

NOW THE ACTUAL FAILOVER TIME, measured end to end:

  detection            (10s interval × 2 failures)          ~ 20-30 s
  Route 53 propagation                                      ~  5-10 s
  TTL expiry at recursive resolvers (TTL=60)                    0-60 s
  client-side caching  (browser ~60s, JVM DEFAULT: FOREVER)     ???
                                                            ─────────
  realistic                                                 90 s - 11 min
  worst case (a JVM with networkaddress.cache.ttl=-1)        NEVER
🔑 DNS failover is a minutes-scale mechanism, and for some clients it is an infinite-scale mechanism. A JVM with the default security policy caches successful DNS lookups for the lifetime of the process — set networkaddress.cache.ttl=30 or those hosts never move. Anything needing seconds-scale failover must fail over below DNS: multiple targets behind one load balancer, or a global accelerator with anycast addresses that never change.
THE HEALTH CHECK THAT LIES — checking the thing that is already checking:

  Route 53 → health-checks → ALB /health → ALB returns 200 (the ALB itself is fine)
                                          → but every TARGET is failing
  the ALB is up, so the health check passes, so Route 53 never fails over,
  and users get 503s from a "healthy" endpoint.

$ curl -s -o /dev/null -w '%{http_code}\n' https://api.acme.com/health
200                                                ← the ALB answering for itself
$ curl -s -o /dev/null -w '%{http_code}\n' https://api.acme.com/orders/42
503                                                ← what users actually see

✅ make the health check exercise the DEPENDENCY CHAIN, not the front door:

  GET /health/deep  →  200 only if: the app is up
                                    AND the database answers a real query
                                    AND the critical downstream is reachable

$ curl -s https://api.acme.com/health/deep | jq
{ "status": "degraded", "db": "ok", "inventory": "timeout", "cache": "ok" }
$ curl -s -o /dev/null -w '%{http_code}\n' https://api.acme.com/health/deep
503                                                ← NOW Route 53 fails over

The counter-argument matters too, and senior interviews probe it: a deep health check makes a shared dependency a correlated failure. If every Region's health check queries the same global database, one database blip marks all Regions unhealthy and Route 53 fails over to nothing. Check dependencies that are local to the failover unit, and treat shared global dependencies as something to alarm on rather than to route on.

CLIENT IP PRESERVATION on NLB is NOT one rule — it depends on the target type:

  instance targets                     → preserved (default ON, cannot disable)
  IP targets, UDP / TCP_UDP            → preserved (default ON)
  IP targets, TCP / TLS                → NOT preserved by default    ← the surprise
  ALB, always                          → never preserved; read X-Forwarded-For

$ aws elbv2 describe-target-group-attributes --target-group-arn arn:...:targetgroup/api/ab12 \
    --query 'Attributes[?Key==`preserve_client_ip.enabled`].Value' --output text
false                                              ← your rate limiter is seeing the NLB
⚠️ This is how IP allow-lists and rate limiters silently stop working. With preservation off, every connection appears to come from the NLB's own address, so a per-IP rate limit throttles everyone at once and an allow-list either admits everyone or nobody. Enable preserve_client_ip.enabled — but know the cost: with preservation on, targets cannot be addressed by the load balancer's own IP, and traffic from a target back through the same NLB (hairpin) breaks. That is why it is off by default for TCP IP-targets.
CROSS-ZONE LOAD BALANCING — different defaults, and one of them costs money:

  ALB: always enabled, and the cross-AZ transfer is FREE.
  NLB: DISABLED by default. Each AZ's node sends only to targets IN THAT AZ.

$ aws elbv2 describe-target-health --target-group-arn arn:...:targetgroup/api/ab12 \
    --query 'TargetHealthDescriptions[].[Target.Id,Target.AvailabilityZone,TargetHealth.State]' --output text
i-0aaa   us-east-1a   healthy
i-0bbb   us-east-1b   healthy
i-0ccc   us-east-1b   healthy
i-0ddd   us-east-1b   healthy
   → with cross-zone OFF, us-east-1a's single instance receives 50% of all traffic
     while each 1b instance receives 16.7%. Uneven by design.

$ aws elbv2 modify-target-group-attributes --target-group-arn arn:...:targetgroup/api/ab12 \
    --attributes Key=load_balancing.cross_zone.enabled,Value=true
   ⚠️ now billable: NLB cross-zone traffic is charged at standard cross-AZ rates.

THE SPORADIC 502 — a keepalive race that no deploy explains:

  ALB idle timeout        60 s  (default)
  backend keepalive       5 s   (nginx default), or 5 s (Node.js default)

  t=0     ALB opens a connection, uses it
  t=5s    the BACKEND closes it (its keepalive expired)
  t=7s    the ALB reuses the connection it still believes is open
          → the FIN arrives, the ALB gets nothing usable
          → HTTP 502, with no error in the application log at all

$ aws elbv2 describe-load-balancer-attributes --load-balancer-arn arn:...:loadbalancer/app/shop/ab \
    --query 'Attributes[?Key==`idle_timeout.timeout_seconds`].Value' --output text
60

✅ THE RULE: the backend's keepalive must be LONGER than the ALB's idle timeout.

    # nginx
    keepalive_timeout 75s;                         ← 75 > 60 ✅

    // Node.js — the default of 5s is the single most common cause of this
    server.keepAliveTimeout = 65000;               // 65s
    server.headersTimeout   = 66000;               // must exceed keepAliveTimeout

$ aws logs start-query --log-group-name /aws/alb/shop --query-string \
  'fields elb_status_code, target_status_code | filter elb_status_code = 502
   | stats count() by target_status_code'
  target_status_code  count
  "-"                 4,182                        ← NO target status: the target never replied.
                                                     Not an application bug. A connection race.

Part 5 — CloudFront and the Cache Key

CloudFront is worth understanding as three things at once: a cache, a TLS terminator at 600+ edge locations, and — often the biggest line item saved — a cheaper egress path, since fetching from an AWS origin is free and edge egress is below the raw internet rate. But everything depends on one concept.

THE CACHE KEY is what CloudFront hashes to decide "is this the same object?"

  BY DEFAULT it contains ONLY:  the distribution + the path
  NOT:  query strings, headers, cookies

  → two consequences, and they are opposite disasters:

  (a) key TOO NARROW:  /profile ignores the Authorization header
                       → user A's profile page is served to user B.
  (b) key TOO WIDE:    include a per-user cookie or User-Agent
                       → every request is unique, hit ratio ≈ 0, and the
                         origin now serves MORE traffic than before CloudFront.

$ aws cloudfront create-cache-policy --cache-policy-config '{
    "Name":"static-assets","DefaultTTL":86400,"MaxTTL":31536000,"MinTTL":1,
    "ParametersInCacheKeyAndForwardedToOrigin":{
      "EnableAcceptEncodingGzip":true,"EnableAcceptEncodingBrotli":true,
      "HeadersConfig":{"HeaderBehavior":"none"},
      "CookiesConfig":{"CookieBehavior":"none"},
      "QueryStringsConfig":{"QueryStringBehavior":"whitelist",
        "QueryStrings":{"Quantity":1,"Items":["v"]}}}}'
   → the key is path + "v". Nothing else varies it.
Cache policyOrigin request policy
ControlsWhat is in the cache keyWhat is forwarded to the origin
Adding a fieldFragments the cacheCosts nothing in hit ratio
Use forThings that genuinely change the responseThings the origin needs but that do not change the response — logging, geo headers
🔑 These two policies are the single most misunderstood pair in CloudFront. If the origin needs to see a header — for analytics, for geo, for a request ID — put it in the origin request policy, where it is forwarded but does not fragment the cache. Only put it in the cache policy if two requests differing in that header must receive genuinely different bytes. Almost every catastrophic hit ratio is a header that belonged in the second policy and was put in the first.
TTL PRECEDENCE — the origin usually wins, which surprises people:

  origin sends Cache-Control: max-age=3600   and  MinTTL=0, MaxTTL=31536000
    → CloudFront caches for 3600 s. The ORIGIN decided.

  origin sends NOTHING                       and  DefaultTTL=86400
    → CloudFront caches for 86400 s.

  origin sends Cache-Control: max-age=60     and  MinTTL=3600
    → CloudFront caches for 3600 s. MinTTL OVERRIDES a shorter origin value.

  origin sends Cache-Control: no-store       → never cached, regardless of TTLs.

INVALIDATION IS NOT A DEPLOYMENT STRATEGY:

$ aws cloudfront create-invalidation --distribution-id E1A2B3C4D5 --paths '/*'
   first 1,000 paths per month free, then $0.005 per path.
   AND it takes minutes to complete, AND '/*' throws away the entire cache,
   so the origin takes the full load while it refills.

✅ versioned filenames instead — new name, new cache entry, zero invalidations:
   /static/app.a3f91c2.js         (immutable, Cache-Control: max-age=31536000, immutable)
   /static/app.b7e40d9.js         ← the deploy just changes the reference in the HTML
   and the HTML itself: Cache-Control: no-cache (revalidate every time, cheap)

LOCK THE ORIGIN so nobody bypasses the CDN — Origin Access Control for S3:

$ OAC=$(aws cloudfront create-origin-access-control --origin-access-control-config \
    '{"Name":"s3-oac","OriginAccessControlOriginType":"s3",
      "SigningBehavior":"always","SigningProtocol":"sigv4"}' \
    --query 'OriginAccessControl.Id' --output text)

  then the bucket policy allows ONLY that distribution:
  { "Effect":"Allow","Principal":{"Service":"cloudfront.amazonaws.com"},
    "Action":"s3:GetObject","Resource":"arn:aws:s3:::acme-assets/*",
    "Condition":{"StringEquals":{"AWS:SourceArn":
      "arn:aws:cloudfront::111122223333:distribution/E1A2B3C4D5"}}}

  ← note this is the aws:SourceArn confused-deputy pattern from the IAM lesson,
    applied to a service principal. Without it, any distribution could read the bucket.

Part 6 — Which Layer Broke?

Four hops, and each can return a five-hundred. The response headers tell you which one answered, and that is almost always faster than reading logs.

  503   -            2,048   0.000                 ← no target at all
  504   i-0ccc         311   60.001                ← ONE target, timing out at exactly 60s
  502   i-0aaa         184   0.002                 ← instant: connection race, not slowness
💡 target_processing_time is the fastest triage field in the whole log. Exactly at the idle timeout means the target hung — look at the application. Near zero on a 502 means the connection failed before any work happened — look at keepalive and target health. -1 means the ALB never successfully sent the request. Three different causes, one status code, distinguished by one number.

❌ A CNAME attempted at the apex, a 300-second TTL lowered during the incident, health checks pointed at the load balancer, NLB cross-zone left at its default, a Node backend with a five-second keepalive behind a sixty-second ALB, and a CloudFront cache policy that forwards every header. The apex CNAME is rejected outright, so someone hardcodes the ALB's current IP addresses in an A record and it breaks silently the next time the ALB scales. The TTL was 300 seconds and was only lowered once traffic needed moving, which changes nothing for resolvers that already cached the old answer, and a fleet of JVMs never picks up the change at all. The Route 53 health check asks the ALB for /health, the ALB answers 200 for itself while every target is failing, so failover never triggers and users receive 503s from an endpoint monitoring calls healthy. The NLB has cross-zone disabled by default, so the single instance in one AZ takes half the traffic while three instances in another share the rest. Sporadic 502s appear with no application error and no correlated deploy, because the backend closes idle connections before the load balancer stops reusing them. And the cache policy includes User-Agent, so every browser version is a distinct cache entry, the hit ratio collapses, and the origin serves more traffic than it did before the CDN existed.

✅ Alias records everywhere, TTLs lowered in advance, deep health checks scoped to the failover unit, cross-zone understood as a per-load-balancer decision, keepalive ordered correctly, and a cache key containing only what changes the bytes. Use alias records for every AWS target — free, one less round trip, valid at the apex, and EvaluateTargetHealth gives failover with no separate health check. Lower TTLs the day before a migration, and remember that DNS failover is a minutes-scale mechanism that is infinite-scale for a default JVM; if you need seconds, fail over below DNS. Point health checks at an endpoint that exercises the dependencies local to that failover unit, so a real outage trips it and a shared global dependency does not mark every Region unhealthy at once. Know that ALB cross-zone is always on and free while NLB's is off and billable, and choose deliberately. Set the backend keepalive above the ALB idle timeout — 75s against 60s — because the reverse produces 502s that appear in no application log. Put fields the origin merely needs to see in the origin request policy and only genuinely response-varying fields in the cache policy. And ship versioned filenames instead of invalidating, so a deploy never throws away a warm cache.

Interview Questions

Beginner: Why can't you use a CNAME at a zone apex, and what does AWS do about it?

RFC 1034 forbids a CNAME from coexisting with any other record at the same name, and a zone apex must hold SOA and NS records. So acme.com can never be a CNAME, while www.acme.com can. This matters because AWS load balancers and CloudFront distributions are addressed by hostname — their IP addresses change without notice — so the obvious "point acme.com at the ALB" is exactly the forbidden thing.

Route 53's alias record solves it: it is an A or AAAA record whose value Route 53 resolves internally at query time, so the client receives real addresses and no CNAME is ever involved. It is valid at the apex, free for AWS targets, saves the client a round trip, and supports EvaluateTargetHealth so the record disappears when the target is unhealthy. The wrong answer people give is hardcoding the load balancer's current IPs in an A record, which works until the ALB scales.

Beginner: ALB or NLB — how do you choose?
Choose ALB whenChoose NLB when
The traffic is HTTP/HTTPS/gRPCIt is raw TCP or UDP
You need host-, path- or header-based routingYou need a static IP or an Elastic IP
You want WAF, OIDC auth, or weighted target groupsYou need extreme throughput or microsecond latency
You want cross-zone balancing for freeYou are fronting a PrivateLink endpoint service (which requires an NLB)

The default is ALB for anything HTTP, because the layer-7 features are why load balancers are useful. Reach for NLB when something forces layer 4: a static IP for a partner's firewall allow-list, a non-HTTP protocol, PrivateLink, or latency budgets where milliseconds matter. A common production pattern is NLB in front of ALB — static IPs from the NLB, path routing from the ALB. And remember the two differ on cross-zone defaults, which is a real behavioural difference and not trivia.

Mid: Users report intermittent 502s. Application logs show nothing wrong. Diagnose.

"No application log entry" is the diagnosis, not an obstacle. A 502 from an ALB means the target closed the connection or returned something unparseable — so if the application never logged a request, the failure happened before any application code ran.

fields elb_status_code, target_status_code, target_processing_time
| filter elb_status_code = 502
| stats count() by target_status_code, target_processing_time

  "-"   0.001   4,182                             ← no target status, near-zero time

That signature — target_status_code = "-" with a processing time near zero — is a connection-level race, and the overwhelmingly common cause is a keepalive mismatch: the ALB's idle timeout defaults to 60 seconds, while nginx and Node.js default to 5. The backend closes an idle connection the ALB still believes is usable, the ALB sends a request into it, and the FIN arrives instead of a response.

The fix is ordering: the backend keepalive must exceed the ALB idle timeout — 75s against 60s. In Node, set both server.keepAliveTimeout = 65000 and server.headersTimeout = 66000, since headersTimeout must be the larger of the two or you reintroduce the same race.

Rule the others out quickly: a processing time at exactly the idle timeout is a 504, not this; response headers exceeding the ALB limit produce 502 with a target status; and a target crashing mid-request would show up in target health. If the server: response header says CloudFront rather than awselb/2.0, you are debugging the wrong hop entirely.

Mid: CloudFront was deployed and the origin's load went up. Explain how that is possible.

The cache key is fragmented, so almost nothing is a hit — and CloudFront then adds its own request volume on top of the original traffic, since every miss becomes an origin fetch plus the edge's own connection overhead.

The usual culprits, all in the cache policy where they do not belong:

Field in the cache keyDistinct valuesEffect
User-AgentThousandsNear-total fragmentation
A session cookieOne per userHit ratio ≈ 0
Accept-Encoding rawMany variantsUse the Gzip/Brotli normalisation flags instead
All query stringsUnbounded — trackers, UTM tagsWhitelist the ones that matter

Measure before guessing: the CacheHitRate CloudWatch metric, and x-cache: Hit from cloudfront versus Miss on individual requests. Then split the policies: anything the origin merely needs to see goes in the origin request policy, which forwards it without touching the key; only fields that genuinely change the response bytes belong in the cache policy.

The mirror-image failure is worse, and worth raising unprompted: a key that is too narrow — omitting Authorization on authenticated content — caches one user's response and serves it to the next. Fragmentation costs money; over-collapsing is a data breach. Do not cache authenticated responses unless the identity is part of the key.

Senior: Design multi-Region active-active for a global application. Where does traffic get steered, and what actually fails over?

Steer at the edge, not at DNS, for anything needing fast failover. DNS latency-based routing is the cheap answer and it is genuinely useful for coarse steering, but its failover is bounded by detection plus propagation plus TTL plus client caching — minutes at best, and never for a JVM with the default DNS cache. State that trade-off explicitly, because it is the heart of the question.

AnycastGlobal Accelerator — two static IPs, unchanged on failover~30 s, client cache irrelevant
CDNCloudFront origin groupsPer request, on origin error
RegionalALB across AZsSeconds

The layered answer: CloudFront in front for static and cacheable content, with an origin group so a failing origin is retried against the other Region per request. Global Accelerator for the dynamic API path, because its anycast addresses never change — the client's cached DNS answer stays valid and failover happens in the AWS network in about thirty seconds. Route 53 latency records underneath for coarse steering and as the mechanism of last resort.

What actually fails over is the hard part, and it is data, not traffic. Active-active is a data problem: either partition writes by key so each Region owns its records (the approach that actually scales), or accept last-writer-wins with DynamoDB global tables and design the application to tolerate it, or keep writes in one Region and serve reads globally. Say which you are choosing and why. Routing users to a second Region that cannot accept their writes is worse than an outage, because it corrupts data instead of stopping.

And health checks must be local. If both Regions' checks query the same global database, one blip marks both unhealthy and there is nowhere to send traffic. Check what the Region can independently serve; alarm on shared dependencies rather than routing on them.

Senior: A deploy caused a partial outage. Users on some networks see errors, others do not, and it started 40 minutes after the deploy. Walk me through it.

Two clues point the same way before any log is read. "Some networks" means the population is split by resolver, not by user or request — the signature of DNS. "Forty minutes after" rules out the deploy as a direct cause and implicates something with a cache expiry: a TTL, a CDN object, or a connection pool.

Establish which layer answers, per affected network:

$ curl -sS -D- -o /dev/null https://shop.acme.com/ --resolve shop.acme.com:443:<each_ip>
   server: awselb/2.0        → reached the ALB
   server: CloudFront + x-cache: Error from cloudfront  → never reached the origin
$ dig +short shop.acme.com @8.8.8.8
$ dig +short shop.acme.com @1.1.1.1
   → if these differ, a weighted or failover record is splitting the population

The most likely mechanisms, in order: a weighted record left at a partial weight so only the resolvers that re-queried after their TTL expired moved onto the broken version — which explains both the split and the delay exactly; a Route 53 failover triggered by a health check that only started failing once a dependency degraded; or a CDN cache expiry at 40 minutes exposing a broken origin that a warm cache had been masking.

Mitigate before diagnosing further. If it is a weighted record, set the bad target's weight to zero — but note the recovery is also TTL-bound, so it will not be instant and you must say so rather than watching and assuming it failed. If it is CDN-related, an invalidation is faster than a redeploy. Only then find the root cause.

The prevention that matters is the lesson people take away too narrowly: this class of incident is invisible to synthetic monitoring from one location and to any dashboard that averages across users. Monitor from multiple resolvers and Regions, and — the real fix — do not use DNS weighting for deployment canaries at all. Split at the load balancer with weighted target groups, where the shift is per-request, instant to reverse, and observable in one metric.

const server = http.createServer((req, res) => res.end('ok'));

server.headersTimeout   = 66000;                   // MUST exceed keepAliveTimeout
server.listen(8080);
JS
$ node server.js &

THE SAME BUG IN OTHER STACKS — check yours:
  nginx     keepalive_timeout 75s;                 (default 75s — already safe)
  Node.js   server.keepAliveTimeout = 65000        (default 5000  ← DANGEROUS)
  Go        srv.IdleTimeout = 65 * time.Second     (default: falls back to ReadTimeout)
  Java/Tomcat  connectionTimeout="65000"           (default 60000 — borderline)
  Python/gunicorn  --keep-alive 65                 (default 2     ← DANGEROUS)
⚠️ headersTimeout must be greater than keepAliveTimeout in Node, or you reintroduce the same race in a subtler form — the socket survives the idle period and then the header timer fires mid-request. Setting only keepAliveTimeout is the most common half-fix, and it reduces the 502 rate enough to look successful for a week. The alternative direction — lowering the ALB idle timeout below the backend's keepalive — also works, and is the right choice when you do not control the backend.

🔑 Every layer told the truth, and each one's error code named its own view rather than the cause. CloudFront said "I could not get a response", the ALB said "I have no healthy targets", the target said "the database refused me", and the database said "I am full". Debugging downward through the layers — asking who answered, then bypassing that layer — reaches the cause in four commands and without changing anything. The alternative, restarting things at whichever layer you happen to suspect, is how a connection-pool exhaustion becomes a two-hour incident. Note also the real fix is not "raise max_connections": add a proxy such as RDS Proxy to multiplex the pools, or cap the ASG at a size the database can actually support — the autoscaler is currently able to take down its own dependency.

🎯 Key Takeaways

  • Every external request takes four hops — DNS → CloudFront → load balancer → target — and all four can return a 5xx. The server: response header names which one answered.
  • A CNAME can never sit at a zone apex (RFC 1034), which is why AWS invented the alias record: valid at the apex, free for AWS targets, one fewer round trip, and health-aware via EvaluateTargetHealth.
  • Never hardcode a load balancer's IP addresses — they change without notice, and the failure is silent and delayed.
  • Lower TTLs the day before a migration; lowering during an incident does nothing for resolvers that already cached the old answer.
  • Weighted DNS splits resolver answers, not requests — a 5% weight measured 3.4% one day and 17% another, because one corporate resolver decided for thousands of users.
  • For a real canary, use weighted target groups at the ALB: exactly 5%, per request, and instantly reversible — the roll-back speed is what matters at 3am.
  • DNS failover is minutes, not seconds: detection + propagation + TTL + client cache measured 47 s at best, and a JVM with networkaddress.cache.ttl=-1 never moves at all.
  • If you need seconds-scale failover, do it below DNS — Global Accelerator's anycast addresses never change, so a stale cache cannot hurt you.
  • A health check pointed at the load balancer will report healthy while every target fails — failover never triggers, and monitoring says everything is fine.
  • Deep health checks must be scoped to the failover unit: checking a shared global dependency marks every Region unhealthy at once and turns a partial outage into a total one.
  • ALB is layer 7 with host/path routing; NLB is layer 4 with static IPs, microsecond latency, and it is what PrivateLink requires.
  • NLB client-IP preservation depends on the target type — off by default for IP targets over TCP/TLS, which silently breaks rate limiters and allow-lists.
  • ALB cross-zone is always on and free; NLB's is off by default and billable — leave it off and one instance in a thin AZ takes 50% of the traffic.
  • The backend keepalive must exceed the ALB idle timeout (75s > 60s). Node's 5s default produces sporadic 502s with no application log entry — and headersTimeout must exceed keepAliveTimeout.
  • Decode ALB 5xx by field: 503 = no healthy targets, 504 = target exceeded the idle timeout, 502 with target_status_code = "-" and near-zero processing time = a connection race.
  • CloudFront's cache key is the whole game: too wide (a per-request header) drops the hit ratio to 0.3% and the origin serves more than before the CDN; too narrow (omitting Authorization) serves one user's page to another.
  • Fields the origin merely needs to see belong in the origin request policy; only response-varying fields belong in the cache policy. Fixing that took 0.3% → 94.1% and cut origin requests 94%.
  • The origin's Cache-Control usually wins over CloudFront's DefaultTTL, but MinTTL overrides a shorter origin value.
  • Invalidation is not a deployment strategy — $0.005 per path past 1,000/month, minutes of latency, and a cold-cache stampede. Use versioned filenames with immutable caching.
  • Lock the origin with Origin Access Control plus an AWS:SourceArn condition, or anyone can bypass the CDN and you pay raw egress.
  • Debug downward: ask who answered, bypass that layer, repeat. Every layer reports its own view honestly — a user's 502 was a database connection ceiling four layers below.
