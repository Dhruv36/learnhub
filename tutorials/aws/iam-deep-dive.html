IAM Advanced: STS, Roles & Trust Foundations

What you'll master: what actually happens when a role is assumed, and why every role carries two policies — a trust policy answering "who may become this" and a permissions policy answering "what may it then do"; session durations, and the hard one-hour cap that applies the moment you chain roles; instance profiles and IMDS, where IMDSv1 turns any SSRF bug into stolen AWS credentials and IMDSv2 does not; OIDC federation that removes long-lived keys from CI and Kubernetes entirely — along with the sub-claim mistake that lets any repository on GitHub assume your role; session policies and permission boundaries as ceilings; how to actually revoke credentials that cannot be deleted; and the credential resolution order that explains why the CLI is using an identity you did not expect. Prerequisites: IAM: Identities, Policies & Evaluation.

Part 1 — What AssumeRole Really Does

  caller (some identity)
      │  sts:AssumeRole(RoleArn, RoleSessionName, [ExternalId, Policy, DurationSeconds])
      ▼
  STS evaluates the ROLE'S TRUST POLICY   ← "may this principal become me?"
      │  and the caller's identity policy ← "is this principal allowed to try?"
      ▼
  returns a TEMPORARY CREDENTIAL TRIPLE
      AccessKeyId      ASIA...            ← "ASIA" prefix = temporary
      SecretAccessKey  ...
      SessionToken     ...                ← required; AKIA keys have none
      Expiration       2026-08-20T10:14:00Z

$ aws sts assume-role \
    --role-arn arn:aws:iam::111122223333:role/DeployRole \
    --role-session-name alice-deploy-4821 \
    --duration-seconds 3600 \
    --query 'AssumedRoleUser.Arn' --output text
arn:aws:sts::111122223333:assumed-role/DeployRole/alice-deploy-4821
                                                    ↑ the SESSION NAME appears in
                                                      every CloudTrail event
FieldMatters because
RoleSessionNameIt is your only attribution — put the human or job ID in it
ExternalIdPrevents the third-party confused deputy
Policy / PolicyArnsA session policy — a ceiling for this session only
DurationSecondsUp to the role's MaxSessionDuration (default 1 h, max 12 h)
TagsSession tags — the basis of ABAC via aws:PrincipalTag
🔑 The assumed-role ARN is not the role ARN. Resource policies and trust policies match on arn:aws:iam::1111:role/DeployRole; conditions and CloudTrail see arn:aws:sts::1111:assumed-role/DeployRole/session-name. Writing the STS form into a Principal field silently matches nothing — a denial that looks impossible until you notice the service prefix.

ROLE CHAINING — and the cap that surprises people:

  role A ──AssumeRole──► role B ──AssumeRole──► role C
                                  └── this second hop is CHAINING

$ aws sts assume-role --role-arn ...RoleB --role-session-name s --duration-seconds 14400
{ "Credentials": { "Expiration": "2026-08-20T14:14:00Z" } }      ← 4 hours, fine

$ AWS_PROFILE=roleB aws sts assume-role --role-arn ...RoleC \
    --role-session-name s --duration-seconds 14400
An error occurred (ValidationError) when calling the AssumeRole operation: The
requested DurationSeconds exceeds the 1 hour session limit for roles assumed by
role chaining.
⚠️ Chained sessions are capped at one hour, regardless of MaxSessionDuration. Long-running jobs that chain roles must refresh credentials, not request a longer session — which is exactly what the SDKs do automatically if you configure the profile with role_arn and source_profile rather than exporting static environment variables. Hand-rolled scripts that export the triple once break at the sixty-minute mark.

Part 3 — Instance Profiles and IMDS

An EC2 instance gets credentials from the Instance Metadata Service — a link-local HTTP endpoint at 169.254.169.254. How that endpoint is protected is the difference between a minor bug and a breach.

IMDSv1 — a plain GET, no authentication of the caller:
$ curl http://169.254.169.254/latest/meta-data/iam/security-credentials/AppRole
{ "AccessKeyId": "ASIA...", "SecretAccessKey": "...", "Token": "..." }

  ⚠️ ANY code that can make an HTTP request from the instance can read this:
      · an SSRF bug in your application
      · a compromised dependency
      · a misconfigured proxy that follows user-supplied URLs

IMDSv2 — session-oriented, PUT-then-GET with a token:
$ TOKEN=$(curl -sX PUT http://169.254.169.254/latest/api/token \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
$ curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/iam/security-credentials/AppRole
IMDSv2 propertyBlocks
Requires a PUT to obtain a tokenSSRF, which can almost always only issue GETs
Token must be sent in a headerURL-only injection
X-Forwarded-For requests are rejectedOpen proxies relaying the request
Default hop limit of 1Containers on the host reaching it — raise to 2 for Docker/ECS bridge networking
$ aws ec2 modify-instance-metadata-options --instance-id i-0a1b2c3d \
    --http-tokens required --http-put-response-hop-limit 2 --http-endpoint enabled

$ aws ec2 describe-instances --filters "Name=metadata-options.http-tokens,Values=optional" \
    --query 'Reservations[].Instances[].InstanceId' --output text | wc -w
14                                    ← 14 instances still accepting IMDSv1

The best option, where the workload does not need metadata at all, is --http-endpoint disabled. The second best is enforcing IMDSv2 organisation-wide with an SCP denying ec2:RunInstances unless ec2:MetadataHttpTokens is required.

Part 4 — OIDC Federation: No Keys at All

GitHub Actions, without a single stored secret:

  1. GitHub mints a short-lived OIDC token describing the workflow
  2. the job calls sts:AssumeRoleWithWebIdentity with that token
  3. STS validates it against your OIDC provider and the role's trust policy
  4. the job receives temporary AWS credentials

$ aws iam create-open-id-connect-provider \
    --url https://token.actions.githubusercontent.com \
    --client-id-list sts.amazonaws.com \
    --thumbprint-list 6938fd4d98bab03faadb97b34396831e3780aea1

❌ THE MISTAKE THAT MATTERS:
{ "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::1111:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": { "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" } } }
     → the ONLY condition is the audience, which is identical for every GitHub user.
       ANY repository on GitHub can assume this role.

✅ scope to the repository AND the ref:
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:acme/shop:ref:refs/heads/main" } }

⚠️ and beware StringLike with a loose wildcard:
      "sub": "repo:acme/*"        → any repo in the acme org, any branch, any PR
      "sub": "repo:acme/shop:*"   → including pull_request from forks
🔑 The sub claim is the whole security boundary. Omitting it is equivalent to publishing an access key; wildcarding it loosely means an untrusted pull request can assume a deployment role. Scope to exact repository and ref, use ref:refs/heads/main or an environment (environment:production) for anything that touches production, and never match pull_request for a role with write access.

The same mechanism underlies EKS IRSA, where the OIDC provider is the cluster and the sub is system:serviceaccount:namespace:name — which is why, as noted in Kubernetes RBAC, a trust policy that pins only the cluster issuer and not the namespace and ServiceAccount is a cluster-wide grant.

Part 5 — Ceilings, and Revoking What Cannot Be Deleted

CeilingSet byApplies toCan it grant?
SCPThe OrganizationEvery principal in the account❌
Permission boundaryAttached to the role/userThat identity, always❌

$ aws sts assume-role --role-arn arn:aws:iam::1111:role/AdminRole \
    --role-session-name readonly-investigation \
    --policy '{"Version":"2012-10-17","Statement":[{"Effect":"Allow",
               "Action":["s3:Get*","s3:List*","logs:*"],"Resource":"*"}]}'
   → an ADMIN role, downscoped to read-only for this session.
     Useful for break-glass access that is auditable and self-limiting.

REVOCATION — temporary credentials cannot be deleted, only outlived or denied:

$ cat > revoke.json <<'EOF'
{ "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Deny", "Action": "*", "Resource": "*",
    "Condition": { "DateLessThan": { "aws:TokenIssueTime": "2026-08-20T10:30:00Z" } }
  }] }
EOF
$ aws iam put-role-policy --role-name CompromisedRole \
    --policy-name AWSRevokeOlderSessions --policy-document file://revoke.json
   → every session issued BEFORE that timestamp is denied everything, immediately.
     New sessions still work, so the workload recovers on its next refresh.
CompromiseResponse
Leaked long-lived access keyDeactivate, then delete the key; rotate anything it touched
Leaked temporary credentialsDeny by aws:TokenIssueTime — they cannot be deleted
Compromised roleRevoke sessions, then tighten the trust policy
Compromised OIDC trustFix the sub condition; revoke sessions

Part 6 — The Credential Resolution Chain

  the SDK/CLI tries, IN ORDER, and stops at the first that yields credentials:

  1. explicit parameters in code
  2. environment variables       AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY / AWS_SESSION_TOKEN
  3. the CLI --profile / AWS_PROFILE, from ~/.aws/credentials and ~/.aws/config
  4. web identity token          AWS_WEB_IDENTITY_TOKEN_FILE  (EKS IRSA, GitHub OIDC)
  5. ECS/EKS container credentials  AWS_CONTAINER_CREDENTIALS_RELATIVE_URI
  6. EC2 instance profile        via IMDS

$ aws sts get-caller-identity
{ "Arn": "arn:aws:iam::111122223333:user/legacy-ci" }
        ↑ NOT the role you configured — a stale AWS_ACCESS_KEY_ID in the environment
          shadowed the profile entirely

$ env | grep -c AWS_ACCESS_KEY_ID
1
$ unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN
$ aws sts get-caller-identity --query Arn --output text
arn:aws:sts::111122223333:assumed-role/DeployRole/botocore-session-1755598931

The profile form that refreshes automatically — use this rather than exporting a triple:

# ~/.aws/config
[profile deploy]
role_arn       = arn:aws:iam::111122223333:role/DeployRole
source_profile = sso-user
role_session_name = alice-deploy
duration_seconds  = 3600
external_id    = cust-7f3c9a1e

❌ Long-lived access keys in CI, IMDSv1 left enabled, a GitHub OIDC trust policy conditioned only on the audience, credentials exported as environment variables in a long job, and no plan for revoking a leak. The CI system holds a static key pair with deployment permissions, so a compromised build or a leaked repository secret is a permanent credential until someone notices. The application has an SSRF bug, and because IMDSv1 is enabled a single crafted URL returns the instance role's credentials — the classic shape of several very public breaches. The GitHub trust policy checks only aud: sts.amazonaws.com, which is identical for every GitHub user on earth, so any repository anywhere can assume the deployment role. A four-hour data job exports the credential triple once and fails at exactly sixty minutes because it chained roles. And when a token does leak, nobody can revoke it — temporary credentials cannot be deleted, and the team waits out the expiry while the attacker uses them.

✅ Federate instead of storing keys, enforce IMDSv2, pin the OIDC subject, let the SDK refresh, and know the revocation move in advance. Replace CI keys with OIDC federation so no AWS credential exists to leak, and scope the trust policy on sub — exact repository and ref, or a GitHub environment for production — because the audience claim alone is a grant to the entire internet. Enforce --http-tokens required everywhere, with an SCP denying instance launches that do not, and set the hop limit to 2 only where containers genuinely need metadata; disable the endpoint entirely where nothing does. Configure profiles with role_arn and source_profile so the SDK refreshes automatically, rather than exporting a triple that dies at the one-hour chaining cap. Put a meaningful RoleSessionName on every assumption, since it is the only attribution CloudTrail will have. Use session policies to downscope break-glass access so an admin role is read-only for an investigation. And keep the aws:TokenIssueTime deny policy in the runbook — it is the only way to revoke temporary credentials, and improvising it during an incident wastes the minutes that matter.

Interview Questions

Beginner: What happens when a role is assumed?

STS checks the role's trust policy, then returns temporary credentials.

sts:AssumeRole → trust policy says "may this principal become me?"
               → caller's identity policy says "may this principal try?"
               → returns AccessKeyId (ASIA…), SecretAccessKey, SessionToken, Expiration

Every role has two policies, and confusing them is the most common beginner error: the trust policy controls who may assume it; the permissions policy controls what it can do afterwards. An AccessDenied on AssumeRole is a trust-policy problem; an AccessDenied afterwards is a permissions problem.

Two details worth adding: temporary keys start with ASIA and require the session token, whereas long-lived keys start with AKIA and have none. And the resulting identity is arn:aws:sts::…:assumed-role/RoleName/SessionName — so the session name you choose is the only attribution CloudTrail will record.

Beginner: What is an instance profile, and why does IMDSv2 matter?

An instance profile is the container that delivers a role's credentials to an EC2 instance, served over the link-local metadata endpoint at 169.254.169.254.

IMDSv1:  curl http://169.254.169.254/latest/meta-data/iam/security-credentials/AppRole
         → returns credentials to ANY code that can make a GET from the instance

IMDSv2:  PUT to obtain a token, then GET with the token in a header
IMDSv2 requirementBlocks
A PUT to get a tokenSSRF, which can usually only issue GETs
Token in a headerURL-only injection
Rejects X-Forwarded-ForOpen proxies relaying the request
Hop limit 1 by defaultContainers on the host — raise to 2 if they need it

This is the shape of several well-known breaches: an SSRF bug in a web application, one request to the metadata endpoint, and the attacker holds the instance role's credentials with whatever permissions it had. Enforce --http-tokens required, and disable the endpoint entirely on instances that never call AWS APIs.

Mid: How do you give GitHub Actions access to AWS without storing keys?

OIDC federation: GitHub mints a short-lived token describing the workflow, and STS exchanges it for AWS credentials. No secret is stored anywhere.

{ "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::1111:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": { "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "repo:acme/shop:ref:refs/heads/main" } } }

The sub claim is the entire security boundary. Conditioning only on aud is not a partial control — the audience is identical for every GitHub user, so any repository on GitHub could assume the role. That has happened in the wild.

sub patternWho can assume
AbsentAny GitHub repository
repo:acme/*Any repo in the org, any branch, forked PRs included
repo:acme/shop:ref:refs/heads/mainThat repo, that branch
repo:acme/shop:environment:productionThat repo, gated by GitHub environment approval

The same mechanism is EKS IRSA, where the issuer is the cluster and the subject is system:serviceaccount:ns:name — with the identical failure mode if the trust policy pins only the issuer.

Mid: A long-running job fails after exactly one hour. Why?

Role chaining caps sessions at one hour, regardless of the role's MaxSessionDuration.

$ AWS_PROFILE=roleB aws sts assume-role --role-arn ...RoleC --duration-seconds 14400
An error occurred (ValidationError): The requested DurationSeconds exceeds the 1 hour
session limit for roles assumed by role chaining.

Even where the request succeeds, exporting the triple as environment variables freezes it: the SDK has nothing to refresh from, so the job dies at expiry.

# ~/.aws/config — the SDK refreshes automatically
[profile deploy]
role_arn       = arn:aws:iam::1111:role/DeployRole
source_profile = sso-user
duration_seconds = 3600

The general fix is to give the SDK the ability to re-authenticate rather than a frozen credential: a profile with role_arn and source_profile, an instance or task role, or a web-identity token file. All of them refresh transparently.

The related design point: if a job genuinely needs many hours of access, prefer running it under a role it holds directly (task role, instance profile) rather than a chained assumption — the cap exists precisely to bound delegated credentials.

Senior: Credentials have leaked. Walk through the response.

First establish which kind, because the remediation differs entirely.

CredentialPrefixRevocation
Long-lived access keyAKIADeactivate, then delete
Temporary sessionASIACannot be deleted — deny by aws:TokenIssueTime
$ aws iam put-role-policy --role-name CompromisedRole \
    --policy-name AWSRevokeOlderSessions --policy-document '{
  "Version":"2012-10-17","Statement":[{"Effect":"Deny","Action":"*","Resource":"*",
  "Condition":{"DateLessThan":{"aws:TokenIssueTime":"2026-08-20T10:30:00Z"}}}]}'
   → every session issued before that instant is denied everything, immediately;
     new sessions still work, so the workload recovers on its next refresh

Then the investigation: CloudTrail filtered by the access key ID gives every action taken, and the RoleSessionName tells you which job or human it was — which is why generic session names are a real operational cost. GuardDuty's credential-exfiltration findings often detect the use before anyone reports the leak.

Then the root cause, which is nearly always one of three: a key committed to a repository, IMDSv1 plus an SSRF bug, or an over-broad OIDC trust policy. Each has a structural fix — federation so no key exists, IMDSv2 enforced by SCP, and a pinned sub claim.

What I would change afterwards is detection rather than response: a budget alarm and GuardDuty catch abuse quickly, and Access Analyzer plus IAM last-accessed data shrink what a future leak would be worth. The revocation policy itself belongs in the runbook, pre-written — improvising the condition syntax during an incident wastes the minutes that matter.

Senior: Design credential management for CI, workloads and humans.

Nobody and nothing holds a long-lived AWS credential. Every identity federates.

ConsumerMechanismLifetime
HumansIAM Identity Center + SSOSession-bound
CI (GitHub, GitLab)OIDC federation, sub pinned to repo and refMinutes
EC2Instance profile, IMDSv2 enforcedAuto-rotated
ECS/FargateTask roleAuto-rotated
EKS podsIRSA or Pod Identity, namespace + SA pinnedAuto-rotated
Third partiesCross-account role + ExternalIdPer assumption
Break-glassRole + session policy downscope, MFA requiredTime-boxed, alerting

The controls that make it stick are organisational rather than clever: an SCP denying iam:CreateAccessKey outside a break-glass OU, so nobody can quietly reintroduce static keys; an SCP requiring ec2:MetadataHttpTokens = required on launch; and secret scanning in CI as a backstop.

What I would monitor: any remaining AKIA keys and their age, instances still accepting IMDSv1, OIDC trust policies whose sub condition is missing or wildcarded, and AssumeRole events whose session names do not match expected patterns. Those four queries find essentially every credential-management weakness without reading policies by hand.

The trade-off I would name honestly: federation adds a dependency on the identity provider. If GitHub or the IdP is unavailable, deployments stop — which is acceptable, and worth planning a documented break-glass path around, rather than keeping a static key "just in case", because that key is exactly the thing that eventually leaks.

from flask import Flask, request
import urllib.request
app = Flask(__name__)
@app.route("/fetch")
def fetch():                                   # takes a user-supplied URL
    return urllib.request.urlopen(request.args["url"]).read()
EOF
