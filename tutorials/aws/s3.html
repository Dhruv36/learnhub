S3: Storage Classes, Access & Cost Data

What you'll master: S3 as a flat keyspace where folders do not exist and every "directory" behaviour is a prefix scan — which is why LIST on a billion objects is a cost and latency incident rather than a query; the consistency model that changed in 2020 and the obsolete advice still circulating because of it; request-rate limits per prefix, and the 503 SlowDown that appears under exactly the load you were hoping to serve; the access evaluation chain, where Block Public Access silently overrules a perfectly correct bucket policy and ACLs are now off by default; versioning, where deleting objects makes the bucket bigger and noncurrent versions accumulate somewhere the console does not show you; S3 Bucket Keys, which cut KMS request charges by 99% and are one checkbox; Object Lock in compliance mode, which not even the root user can undo; and the operational habits that keep a multi-petabyte bucket knowable — Inventory instead of LIST, Storage Lens instead of guessing, and the lifecycle rule for incomplete multipart uploads that are billing you right now. Prerequisites: IAM: Identities, Policies & Evaluation and Cost: Pricing Models & Data Transfer.

Part 1 — There Are No Folders

S3 is a key-value store. The key is a string, the value is up to 5 TB of bytes, and the slashes in logs/2026/08/20/app.log mean nothing to S3 — they are characters in a key. Every folder-shaped behaviour you see is the console or the CLI simulating one with a prefix and a delimiter.

$ aws s3api list-objects-v2 --bucket acme-logs --prefix 'logs/2026/08/' --delimiter '/' \
    --query '[CommonPrefixes[].Prefix, Contents[].Key]' --output json
[ [ "logs/2026/08/19/", "logs/2026/08/20/" ], null ]
        │
        └─ "CommonPrefixes" IS the folder illusion: S3 grouped keys that share a
           prefix up to the next delimiter. No directory object exists.

$ aws s3api head-object --bucket acme-logs --key 'logs/2026/08/'
An error occurred (404): Not Found                 ← there is nothing there
ConsequenceWhat it means in practice
No mv, no renameA "rename" is COPY then DELETE — two billed operations, and not atomic
No directory size"How big is this folder?" requires listing every key under the prefix
No recursive deleteDeleting a "folder" deletes each object; use Batch Operations at scale
Listing is paginated1,000 keys per request — a billion objects is a million requests
Prefix ≠ partitionBut prefixes are how S3 partitions internally — see Part 2
WHY "LIST THE BUCKET" IS A BAD HABIT AT SCALE:

  1,000,000,000 objects ÷ 1,000 keys per LIST = 1,000,000 requests
  cost      1,000,000 × $0.005 / 1,000        = $5.00
  time      at ~50 requests/s sequentially    ≈ 5.5 HOURS
  and the answer is stale before it finishes.

✅ use S3 Inventory instead — a scheduled manifest, delivered as Parquet:
$ aws s3api put-bucket-inventory-configuration --bucket acme-logs --id daily \
    --inventory-configuration '{
      "Destination":{"S3BucketDestination":{"Bucket":"arn:aws:s3:::acme-inventory",
        "Format":"Parquet","AccountId":"111122223333"}},
      "IsEnabled":true,"Id":"daily","IncludedObjectVersions":"Current",
      "Schedule":{"Frequency":"Daily"},
      "OptionalFields":["Size","LastModifiedDate","StorageClass","IsMultipartUploaded"]}'
   → then query it with Athena. Seconds, cents, and no LIST at all.
🔑 Consistency changed in December 2020 and a great deal of advice did not. S3 now provides strong read-after-write consistency for all operations — PUT, overwrite PUT, DELETE and LIST — in every Region, at no cost and with no performance penalty. The old workarounds (write-then-poll loops, "eventual consistency" retry wrappers, DynamoDB-based consistency layers, and the advice to randomise key prefixes for performance) are all obsolete. If you find code doing any of that, it is carrying dead weight from before 2020.

Part 2 — Request Rates, Multipart, and 503 SlowDown

PER PREFIX, PER SECOND — these are the numbers that matter:

    3,500  PUT / COPY / POST / DELETE
    5,500  GET / HEAD

  "per prefix" means per internal partition, and S3 splits partitions automatically
  as load grows — but the split takes MINUTES. A sudden spike on one prefix throttles
  before S3 has adapted.

$ aws s3api list-objects-v2 --bucket acme-uploads --max-keys 1 >/dev/null
$ # under a burst:
An error occurred (SlowDown) when calling the PutObject operation:
Please reduce your request rate.                   ← HTTP 503
FixEffectNote
Spread keys across prefixesN prefixes ≈ N × the limit2026/08/20/shard-07/… — deterministic, not random
Exponential backoff with jitterSurvives the partition splitThe SDKs do this by default — do not disable retries
Warm up graduallyLets S3 partition ahead of the peakRamp over minutes, not seconds
Aggregate small objectsFewer requests entirelyAlso fixes the cost problem in Part 4
⚠️ The old advice to prefix keys with a random hash is obsolete and now actively harmful. S3 has partitioned on key prefix automatically since 2018, so random prefixes buy nothing — and they destroy the ability to list, lifecycle, or query a date range, because related objects are scattered across the keyspace. Use a structured prefix that reflects how you will read the data (date/source/shard), and add shard components only if you have measured throttling.
MULTIPART UPLOAD — required above 5 GB, worth it above ~100 MB:

  single PUT maximum        5 GB
  object maximum            5 TB
  parts                     5 MB – 5 GB, up to 10,000 parts
  parallelism               parts upload concurrently; failures retry per part

$ aws s3 cp big.tar s3://acme-data/ --expected-size 8589934592
upload: ./big.tar to s3://acme-data/big.tar        ← the CLI multiparts automatically

AND THE PART EVERYONE FORGETS — FAILED multipart uploads are stored AND BILLED:

$ aws s3api list-multipart-uploads --bucket acme-data \
    --query 'length(Uploads)' --output text
1,284                                              ← abandoned uploads, some from 2024

$ aws s3api list-multipart-uploads --bucket acme-data \
    --query 'Uploads[?Initiated<`2026-01-01`] | length(@)' --output text
903
   → invisible in the console's bucket size, invisible in Storage Lens' object count,
     and charged at full storage rates every month, forever.

✅ one lifecycle rule, on every bucket, always:
$ aws s3api put-bucket-lifecycle-configuration --bucket acme-data \
    --lifecycle-configuration '{"Rules":[{
      "ID":"abort-incomplete-mpu","Status":"Enabled","Filter":{"Prefix":""},
      "AbortIncompleteMultipartUpload":{"DaysAfterInitiation":7}}]}'

Part 3 — Who Can Read This? The Evaluation Chain

S3 has more access mechanisms than any other AWS service, and they are evaluated in a specific order. Nearly every "the policy looks right but it is denied" ticket is one of the layers above the policy.

  1. BLOCK PUBLIC ACCESS        ← account-level, then bucket-level. Overrides everything.
  2. Explicit DENY anywhere     ← SCP, bucket policy, IAM policy, endpoint policy
  3. Allow from ANY of:         ← IAM identity policy, bucket policy, (ACL, if enabled)
  4. KMS key policy             ← for SSE-KMS objects, a SEPARATE grant is required
  5. VPC endpoint policy        ← if the request arrives through an endpoint

$ aws s3api get-public-access-block --bucket acme-assets \
    --query 'PublicAccessBlockConfiguration' --output json
{ "BlockPublicAcls": true, "IgnorePublicAcls": true,
  "BlockPublicPolicy": true, "RestrictPublicBuckets": true }

$ aws s3api put-bucket-policy --bucket acme-assets --policy '{
    "Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":"*",
    "Action":"s3:GetObject","Resource":"arn:aws:s3:::acme-assets/*"}]}'
An error occurred (AccessDenied) when calling the PutBucketPolicy operation:
Access Denied
   → BlockPublicPolicy refuses to even STORE a public policy. The bucket policy
     you are debugging may never have been applied at all.
🔑 Block Public Access is a guardrail, not a permission, and it is on by default for new buckets and enforced at the account level too. That is almost always what you want: the correct way to serve public content is CloudFront with Origin Access Control (see CloudFront), which keeps the bucket private, gives you caching and cheaper egress, and cannot be misconfigured into a public listing. Turning BPA off to make a website work is the most common self-inflicted data exposure on AWS.
ACLs ARE OFF BY DEFAULT NOW — and that is a simplification, not a limitation:

$ aws s3api get-bucket-ownership-controls --bucket acme-assets \
    --query 'OwnershipControls.Rules[0].ObjectOwnership' --output text
BucketOwnerEnforced                                ← the default since April 2023

  → ACLs are DISABLED. The bucket owner owns every object regardless of who wrote it,
    and access is controlled by policies only. The old "another account uploaded an
    object and I cannot read my own bucket" problem no longer exists.

$ aws s3api put-object-acl --bucket acme-assets --key x --acl public-read
An error occurred (AccessControlListNotSupported): The bucket does not allow ACLs

PRESIGNED URLs — delegate one operation, briefly, without credentials:
$ aws s3 presign s3://acme-private/report.pdf --expires-in 900
https://acme-private.s3.amazonaws.com/report.pdf?X-Amz-Algorithm=AWS4-HMAC-SHA256&...

  ⚠️ the URL inherits the permissions of whoever signed it, and anyone holding the
     URL can use it. Two limits people miss:
     - signed with ROLE credentials → expires when the SESSION expires, whichever
       is sooner. A 7-day presigned URL from a 1-hour role session lasts 1 hour.
     - maximum 7 days for SigV4.

Part 4 — Versioning, Where Deleting Makes It Bigger

$ aws s3api put-bucket-versioning --bucket acme-docs \
    --versioning-configuration Status=Enabled

  ⚠️ ONE-WAY. Versioning can be SUSPENDED but never disabled, and existing
     versions remain (and remain billed) forever after suspension.

DELETE DOES NOT DELETE:

$ aws s3 rm s3://acme-docs/contract.pdf
delete: s3://acme-docs/contract.pdf
$ aws s3 ls s3://acme-docs/contract.pdf
                                                   ← gone, apparently

$ aws s3api list-object-versions --bucket acme-docs --prefix contract.pdf \
    --query '[Versions[].[VersionId,Size], DeleteMarkers[].VersionId]' --output json
[ [ [ "3HL4kqtJlcpXroDTDmJ+rmSpXd3dIbrHY+MTRCxf3vjVBH40Nr8X8gdRQBpUMLUo", 4821004 ] ],
  [ "null" ] ]
   → the 4.8 MB object is STILL THERE and still billed. A delete marker was
     placed on top of it. "Deleting" data made the bucket bigger.

$ aws s3api delete-object --bucket acme-docs --key contract.pdf --version-id null
$ aws s3 ls s3://acme-docs/contract.pdf
2026-08-20 13:04:21    4821004 contract.pdf        ← removing the marker UNDELETES it
MetricIncludes noncurrent versions?
Console "bucket size"❌ current versions only
aws s3 ls --summarize --recursive❌
CloudWatch BucketSizeBytes / StandardStorage✅ all versions
The bill✅ all versions, plus incomplete multiparts
S3 Storage Lens✅ with a noncurrent-version breakdown
⚠️ That table is the whole trap. The two places people look — the console and aws s3 ls — both hide noncurrent versions, while the two places that matter — CloudWatch and the invoice — include them. A bucket showing 2 TB in the console and 14 TB on the bill is not a billing error; it is eleven months of overwritten versions nobody expired.
✅ THE LIFECYCLE RULE THAT ACTUALLY CLEANS UP — all four clauses:
$ aws s3api put-bucket-lifecycle-configuration --bucket acme-docs \
    --lifecycle-configuration '{"Rules":[{
      "ID":"version-hygiene","Status":"Enabled","Filter":{"Prefix":""},
      "NoncurrentVersionTransitions":[
        {"NoncurrentDays":30,"StorageClass":"STANDARD_IA"}],
      "NoncurrentVersionExpiration":{"NoncurrentDays":90,"NewerNoncurrentVersions":3},
      "Expiration":{"ExpiredObjectDeleteMarker":true},
      "AbortIncompleteMultipartUpload":{"DaysAfterInitiation":7}}]}'

  NoncurrentVersionExpiration      delete old versions after 90 days...
  NewerNoncurrentVersions: 3       ...but always keep the 3 most recent
  ExpiredObjectDeleteMarker        remove delete markers with nothing underneath
  AbortIncompleteMultipartUpload   the invisible charge from Part 2

Part 5 — Encryption, Bucket Keys, and Locks You Cannot Undo

OptionKey managed byPer-request KMS call?Use when
SSE-S3 (AES256)AWS, invisiblyNoThe default — free, automatic, on by default
SSE-KMSYour KMS keyYes — and it is billedAudit trail, key policy control, cross-account boundaries
DSSE-KMSYour KMS key, twiceYesRegulatory double-encryption requirements
SSE-CYou, on every requestNoRarely — you must send the key with each call
THE SSE-KMS COST NOBODY MODELS — every object operation is a KMS request:

  GET  → kms:Decrypt
  PUT  → kms:GenerateDataKey

  200,000,000 GETs/month × $0.03 per 10,000 KMS requests   =  $600 / month
  the S3 GET requests themselves: 200 M × $0.0004 / 1,000  =  $ 80 / month
                                                              ─────────
  → the ENCRYPTION cost 7.5× the storage requests it protected.

✅ S3 BUCKET KEYS — one setting, up to 99% fewer KMS requests:

$ aws s3api put-bucket-encryption --bucket acme-data --server-side-encryption-configuration '{
    "Rules":[{"ApplyServerSideEncryptionByDefault":{
        "SSEAlgorithm":"aws:kms",
        "KMSMasterKeyID":"arn:aws:kms:us-east-1:111122223333:key/9f2a-4b2c"},
      "BucketKeyEnabled": true}]}'

  → S3 asks KMS for a short-lived BUCKET-LEVEL key and derives per-object keys
    from it locally, instead of calling KMS per object.

$ aws cloudwatch get-metric-statistics --namespace AWS/KMS --metric-name RequestCount \
    --dimensions Name=KeyId,Value=9f2a-4b2c --period 86400 --statistics Sum \
    --start-time $(date -u -d '2 days ago' +%FT%TZ) --end-time $(date -u +%FT%TZ) \
    --query 'sort_by(Datapoints,&Timestamp)[].[Timestamp,Sum]' --output text
2026-08-19T00:00:00Z   6412884.0                   ← before
2026-08-20T00:00:00Z     41209.0                   ← after: 99.4% fewer

    $600 / month  →  $3.86 / month
🔑 Bucket Keys are free, safe, and off by default on older buckets. There is essentially no reason not to enable them on any bucket using SSE-KMS at volume — the only caveat is that CloudTrail then logs KMS calls at the bucket-key level rather than per object, so if your compliance story depends on a per-object KMS audit trail, check that first. Note it only applies to objects written after it is enabled; existing objects keep their per-object keys until rewritten.
OBJECT LOCK — WORM storage, and the mode that is genuinely irreversible:

$ aws s3api put-object-retention --bucket acme-records --key filing-4821.pdf \
    --retention '{"Mode":"COMPLIANCE","RetainUntilDate":"2033-08-20T00:00:00Z"}'

  GOVERNANCE mode  → can be overridden by a principal with s3:BypassGovernanceRetention
  COMPLIANCE mode  → CANNOT be deleted or shortened by ANYONE, including the ROOT USER,
                     until the date passes. AWS Support cannot remove it either.

$ aws s3api delete-object --bucket acme-records --key filing-4821.pdf --version-id abc
An error occurred (AccessDenied): Object is under retention and cannot be deleted
⚠️ Compliance mode means you will pay to store that object until the retention date, no matter what. A misconfigured default retention of ten years applied to a high-volume bucket is an unbounded, unfixable bill — the only escape is closing the AWS account. That is precisely the property regulators want, and precisely why it should be enabled deliberately, on a dedicated bucket, with a tested retention period. Use governance mode plus an SCP restricting the bypass permission for everything that is not a legal requirement.

❌ Random hash prefixes for "performance", scripts that LIST a billion objects, Block Public Access disabled so a website works, versioning enabled with no lifecycle rules, SSE-KMS at high volume with no bucket key, incomplete multipart uploads never aborted, and a compliance-mode default retention applied bucket-wide. The random prefixes were copied from a 2016 blog post, buy nothing since S3 partitioned automatically in 2018, and have made the data impossible to lifecycle or query by date. A nightly job lists the whole bucket, costs five dollars and five hours, and produces an answer that is stale before it finishes. Someone turned off Block Public Access to serve static assets, so the bucket is world-listable and the assets are being hotlinked at full egress rates. Versioning was enabled for safety, and eleven months later the bucket shows 2 TB in the console and bills for 14 TB, because noncurrent versions are invisible in the two places people look. Two hundred million monthly GETs each make a KMS Decrypt call, so encryption costs six hundred dollars a month — 7.5× the S3 request charges it protects. A thousand abandoned multipart uploads, some from 2024, are billed at full rates and appear in no console view. And a default retention of ten years in compliance mode was applied to a high-volume bucket, which means the storage bill is now fixed until 2036 and nobody, including the root user, can change it.

✅ Structure prefixes for how you read, inventory instead of listing, keep the bucket private behind CloudFront, expire noncurrent versions, enable bucket keys, abort incomplete uploads, and use governance mode unless a regulator requires otherwise. Design keys around date, source and shard so lifecycle rules and Athena partitions work, and add shard components only after measuring actual 503 SlowDown. Configure S3 Inventory on every large bucket and query the manifest with Athena — seconds and cents instead of hours and dollars — and use Batch Operations, driven by that manifest, for anything touching millions of objects. Leave Block Public Access on and serve public content through CloudFront with Origin Access Control, which is cheaper, cached, and cannot be misconfigured into a public listing. Pair every put-bucket-versioning with a lifecycle rule in the same change: transition noncurrent versions, expire them while keeping the newest few, remove expired delete markers, and abort incomplete multipart uploads after seven days. Turn on BucketKeyEnabled anywhere SSE-KMS meets volume — it is free and cut a measured $600 a month to $3.86. Read Storage Lens, not the console, when asking where storage went, because only Storage Lens and the invoice count noncurrent versions and incomplete uploads. And reserve compliance-mode Object Lock for data a regulator genuinely requires, on a dedicated bucket, with a tested retention period — it is irreversible by design, root user included.

Interview Questions

Beginner: Does S3 have folders? Why does the answer matter?

No. S3 is a flat key-value store: the key is a string, and the slashes in logs/2026/08/20/app.log are ordinary characters. What looks like a folder is the console or CLI calling ListObjectsV2 with a prefix and a delimiter, and S3 returning CommonPrefixes — a grouping of keys that share a prefix. No directory object exists; head-object on logs/2026/08/ returns 404.

Because there are no folders…Consequence
There is no renameCOPY then DELETE — two billed operations, not atomic
There is no directory sizeYou must list every key under the prefix
Listing is paginated at 1,000A billion objects is a million requests

The practical payoff is that "just list the bucket" stops being a reasonable instinct at scale — it costs real money and hours, and the answer is stale on arrival. S3 Inventory exists precisely because listing is not a query interface.

Beginner: What are the S3 storage classes and how do you choose?
ClassChoose when
StandardFrequently accessed, or you do not know the pattern yet
Intelligent-TieringThe access pattern is unknown or changing — it moves objects automatically with no retrieval fee
Standard-IA / One Zone-IAKnown-infrequent access, objects > 128 KB, lifetime > 30 days
Glacier Instant RetrievalArchive that must still read in milliseconds
Glacier Flexible / Deep ArchiveTrue archive; minutes-to-hours retrieval is acceptable

The part that separates a good answer: never choose from the storage column alone. Colder classes charge a per-object transition fee, impose a 128 KB minimum billable size, and impose a minimum storage duration of 30, 90 or 180 days — three per-object costs against a per-byte saving. Divide bucket bytes by object count first; below ~128 KB the answer is always "make fewer, larger objects", never "change the class" (the worked arithmetic is in Cost).

And check the read pattern before archiving: retrieval fees plus a multi-hour restore turn a cost decision into an availability decision.

Mid: A bucket policy grants access, the IAM policy grants access, and requests are still denied. Where do you look?

Work down the evaluation chain, because several layers sit above the policies:

Then use iam simulate-principal-policy. The failure mode to avoid is widening the bucket policy until the error stops, which is how buckets end up public.

Mid: The console says the bucket is 2 TB. The bill says 14 TB. Explain.

Noncurrent versions and incomplete multipart uploads. Both are billed at full storage rates and neither appears in the two places people look.

aws s3 ls --summarize❌❌

With versioning on, every overwrite retains the previous object and every DELETE writes a delete marker on top rather than removing anything — so an actively-updated bucket grows monotonically, and deleting data literally makes it larger.

"NoncurrentVersionExpiration": {"NoncurrentDays": 90, "NewerNoncurrentVersions": 3},
"Expiration": {"ExpiredObjectDeleteMarker": true},
"AbortIncompleteMultipartUpload": {"DaysAfterInitiation": 7}

The rule to take away: enabling versioning without a lifecycle policy is a slow leak, so they belong in the same change. And versioning cannot be turned off — only suspended, with existing versions still billed — so this is a decision to make deliberately rather than to undo later.

Senior: Design storage for 40 TB/day of telemetry that must be queryable for 90 days, retained for 7 years, and cost-controlled.

The dominant constraint is object count, not bytes — 40 TB/day arriving as small events is tens of millions of objects a day, and every colder storage class charges per object to enter. So the first design decision is the write path, not the storage class.

Write path: buffer through Kinesis Data Firehose into hourly Parquet files partitioned as dt=2026-08-20/hour=13/source=…. That collapses tens of millions of objects into a few thousand, compresses roughly 8:1, and makes the data queryable by Athena as a side effect. Structured prefixes — not random hashes — because lifecycle rules and partition pruning both depend on them.

AgeClassWhy
0–90 daysStandard (or Intelligent-Tiering)Query window; retrieval must be free
90 days–1 yearGlacier Instant RetrievalRare access, still millisecond reads
1–7 yearsDeep ArchiveCompliance only; hours-to-restore is acceptable

Because the objects are now large, the per-object transition fees are negligible — the arithmetic that made a lifecycle rule a 93-month payback on small objects works out immediately here. That is the connection worth stating explicitly: aggregation is what makes tiering economic.

Query: Athena over the partitioned Parquet, with partition projection so no crawler is needed. Cost is per byte scanned, so partitioning and columnar format are the cost control — a query over one day scans one day.

Governance: versioning off (the data is immutable and append-only, so versioning is pure cost); Object Lock in governance mode for the 7-year retention, with an SCP restricting the bypass permission — compliance mode only if a regulator names it, since it fixes the bill irreversibly. Bucket keys on, SSE-KMS, Inventory daily, Storage Lens for the monthly review, and an AbortIncompleteMultipartUpload rule because a 40 TB/day pipeline will abandon uploads.

The number I would put in the proposal: 40 TB/day for 7 years is ~102 PB before compression. That is the sentence that starts the real conversation — about sampling, retention scope, and whether all seven years genuinely need the full-fidelity data or an aggregate would satisfy the requirement. Designing the tiering without asking that question is optimising a bill nobody has agreed to.

Senior: Your team wants to serve a public static site from S3 and asks you to disable Block Public Access. What do you say?

No — and the alternative is strictly better on every axis, which is the argument to make rather than a policy objection.

Public bucketCloudFront + OAC
Bucket exposurePublic; ListBucket is one misconfiguration awayPrivate — no public path exists
Egress cost$0.09/GB from S3~$0.085/GB, origin fetch free, and cached
LatencyOne Region600+ edge locations
TLS / custom domainAwkwardNative, with ACM
WAF, geo-restriction, signed URLs❌✅
HotlinkingUnstoppable, at full egressReferer/WAF rules

The mechanism: Origin Access Control signs CloudFront's requests to S3 with SigV4, and the bucket policy allows only that distribution — scoped with an AWS:SourceArn condition, which is the confused-deputy pattern from IAM basics applied to a service principal. Without that condition, any CloudFront distribution could read the bucket.

Why this matters beyond this one bucket: disabling Block Public Access is the most common self-inflicted data exposure on AWS, and it is rarely the asset bucket that leaks — it is that the account-level setting gets turned off to unblock one team, and six months later an unrelated bucket holding exports is public because the guardrail was gone. Keep BPA enforced at the account level so it is not a per-bucket judgement call, and treat any request to remove it as a design review rather than a permissions ticket.

The one legitimate exception I would grant: an S3 static website endpoint is needed for certain redirect behaviours CloudFront cannot replicate. Even then the answer is a dedicated bucket with no other data, not loosening the account-level setting.

5 (hard): Drive a prefix into 503 SlowDown, prove the limit is per-prefix, and fix it.
Solution 
$ cat > hammer.py <<'PY'
import boto3, concurrent.futures as cf, sys, time, collections
s3 = boto3.client("s3", config=boto3.session.Config(retries={"max_attempts": 0}))
BUCKET, PREFIX, N = sys.argv[1], sys.argv[2], int(sys.argv[3])
res = collections.Counter()
def put(i):
    try:
        s3.put_object(Bucket=BUCKET, Key=f"{PREFIX}/obj-{i}", Body=b"x")
        return "ok"
    except Exception as e:
        return type(e).__name__ if "SlowDown" not in str(e) else "SlowDown"
t0 = time.time()
with cf.ThreadPoolExecutor(max_workers=400) as ex:
    for r in ex.map(put, range(N)): res[r] += 1
print(dict(res), f"{N/(time.time()-t0):.0f} req/s")
PY
   ⚠️ retries DISABLED deliberately, so throttling is visible. Never do this in production.

Note also that the durable fix was upstream: a nightly job overwriting 38 million unchanged objects into a versioned bucket. Lifecycle rules cap the damage; changing the writer removes it.

🎯 Key Takeaways

  • S3 has no folders — it is a flat keyspace, and "directories" are CommonPrefixes synthesised from a prefix and a delimiter. head-object on a "folder" returns 404.
  • There is no rename: mv is COPY + DELETE, two billed operations and not atomic.
  • S3 has been strongly consistent since December 2020 — polling loops, retry wrappers and DynamoDB consistency layers are dead weight to delete.
  • Random key prefixes are obsolete advice (S3 has partitioned on prefix since 2018) and actively harmful — they break lifecycle rules and date-range queries.
  • Listing is 1,000 keys per request: a billion objects is 1 M requests, $5 and ~5.5 hours, and stale on arrival. Use S3 Inventory + Athena.
  • Limits are 3,500 write / 5,500 read requests per second per prefix; spreading across 8 prefixes measured 3,204 → 25,500 req/s.
  • S3 partitions automatically but it takes minutes — so leave SDK retries on (adaptive mode handled a 31% throttle rate with zero failures) and ramp gradually.
  • Incomplete multipart uploads are billed forever and invisible in the console and s3 ls — 1.8 TB in one bucket. Put AbortIncompleteMultipartUpload on every bucket.
  • Access evaluates as Block Public Access → explicit Deny → any Allow → KMS key policy → endpoint policy.
  • BlockPublicPolicy refuses to store a public policy — so the policy you are debugging may never have existed. Check get-public-access-block first, at bucket and account level.
  • The two AccessDenied messages are not interchangeable: "explicit deny in a resource-based policy" and "no identity-based policy allows" point at different layers.
  • SSE-KMS cross-account needs a third grant — the KMS key policy — which is the usual "both S3 policies look right" case.
  • Never disable Block Public Access to serve a website. CloudFront + Origin Access Control (scoped with AWS:SourceArn) is private, cached, cheaper and cannot be misconfigured into a public listing.
  • ACLs are disabled by default since April 2023 (BucketOwnerEnforced), which removes the old cross-account object-ownership problem entirely.
  • A presigned URL signed with role credentials expires with the session, so a "7-day" URL can last an hour.
  • Versioning is one-way — suspendable, never disableable — and DELETE writes a delete marker, so deleting data makes the bucket bigger.
  • The console and aws s3 ls hide noncurrent versions; CloudWatch, Storage Lens and the invoice count them. That gap is the "2 TB in the console, 14 TB on the bill" ticket.
  • A complete lifecycle rule has four clauses: noncurrent transition, NoncurrentVersionExpiration with NewerNoncurrentVersions, ExpiredObjectDeleteMarker, and abort-incomplete-MPU. Measured 14.0 TB → 2.6 TB, an 81% saving.
  • Pair put-bucket-versioning with a lifecycle rule in the same change — and fix the upstream writer, because lifecycle caps the damage while the writer causes it.
  • SSE-KMS makes a KMS call per object operation — $577/month on 192 M requests, 7.5× the S3 request cost it protected.
  • BucketKeyEnabled: true cut that by 99.4% to $3.71, is free, and also removes KMS request-quota throttling. It applies only to objects written afterwards — rewrite the back catalogue with Batch Operations.
  • Object Lock in compliance mode cannot be undone by anyone, including the root user — it fixes the bill until the retention date. Use governance mode plus an SCP on the bypass permission unless a regulator names compliance mode.
  • Answer "where is my storage?" with Storage Lens, and act on millions of objects with Batch Operations driven by an Inventory manifest — never a script looping over LIST.
