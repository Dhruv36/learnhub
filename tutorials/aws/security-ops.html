Encryption, Secrets & Audit Operations

What you'll master: KMS as the thing everything else is built on — envelope encryption, and the rule that surprises people every time: the key policy is authoritative, so an IAM policy granting kms:Decrypt can grant nothing at all; what "encrypted at rest" actually costs you operationally, including the fact that an unencrypted RDS instance cannot be encrypted in place — the only path is snapshot, copy, restore, cut over; secrets that live in Secrets Manager or Parameter Store instead of in environment variables, images and Terraform state, and rotation that the application actually picks up; the detective services — GuardDuty, Security Hub, Config, Inspector, Macie, Access Analyzer — and the uncomfortable truth that a finding nobody routes to a human is not a control; the incident-response moves specific to AWS, where revoking a leaked temporary credential is a deny on aws:TokenIssueTime and forensics means snapshotting before terminating; and the account baseline that should exist on day one, shipped as StackSets. Prerequisites: IAM, IAM Advanced, S3 and Infrastructure as Code.

Part 1 — KMS: Envelope Encryption and an Authoritative Key Policy

KMS NEVER ENCRYPTS YOUR DATA. It encrypts the key that encrypts your data:

  1. GenerateDataKey        → returns { Plaintext: K, CiphertextBlob: E(K) }
  2. encrypt the object locally with K, using AES-256
  3. throw away K; store E(K) alongside the ciphertext
  4. to read: send E(K) to KMS → Decrypt → K → decrypt locally

  → your 5 GB file never crosses the network to KMS. Only a 32-byte key does.
    (KMS's own Encrypt API is limited to 4 KB, which is why this pattern exists.)

$ aws kms generate-data-key --key-id alias/acme-data --key-spec AES_256 \
    --query '[length(Plaintext),length(CiphertextBlob)]' --output text
44   200                                           ← base64: a 32-byte key, and its wrapped form

$ aws kms decrypt --ciphertext-blob fileb://encrypted-key.bin \
    --encryption-context 'purpose=customer-export,tenant=acme' \
    --query Plaintext --output text | head -c 20
   ⚠️ the ENCRYPTION CONTEXT is authenticated additional data: decrypt fails unless
     it matches exactly, and it is recorded in CloudTrail — so the audit log shows
     WHAT was decrypted, not merely that a key was used.
🔑 The key policy is authoritative, not the IAM policy. Unlike almost everything else in AWS, a KMS key's resource policy must either grant the principal directly or explicitly delegate to IAM (the default policy does the latter with a kms:CallerAccount condition). If someone replaces that default policy with a narrow one, an identity policy granting kms:Decrypt on * grants nothing — which is the root of most "the IAM policy is clearly correct and it is still denied" tickets, and of the cross-account SSE-KMS failures from the IAM lesson.

SCOPE A KEY TO A SERVICE — so a stolen credential cannot use it directly:
  { "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111122223333:role/AppRole" },
    "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
    "Resource": "*",
    "Condition": {
      "StringEquals": {
        "kms:ViaService": "s3.us-east-1.amazonaws.com",
        "kms:EncryptionContext:tenant": "acme" } } }
   → AppRole can decrypt ONLY through S3, and ONLY for tenant acme.
     A leaked credential cannot call kms:Decrypt directly on arbitrary ciphertext.

ROTATION AND DELETION — both behave differently from how people assume:
$ aws kms enable-key-rotation --key-id 9f2a-4b2c
   → new backing material each year. OLD MATERIAL IS RETAINED, so ciphertext
     encrypted years ago still decrypts. Rotation does NOT re-encrypt anything.

$ aws kms schedule-key-deletion --key-id 9f2a-4b2c --pending-window-in-days 30
{ "DeletionDate": "2026-09-19T00:00:00Z", "KeyState": "PendingDeletion" }
   ⚠️ 7–30 days, and it is the ONLY destructive action in AWS with a mandatory
     waiting period — because deleting a key destroys every ciphertext it protects,
     permanently and unrecoverably. Alarm on ScheduleKeyDeletion.

Part 2 — Encryption in Practice, and the One You Cannot Retrofit

ServiceDefaultRetrofit an existing resource?
S3SSE-S3 on, automatically✅ re-copy objects (Batch Operations)
EBSOff unless the Region default is set❌ not in place — snapshot → copy encrypted → new volume
RDS / AuroraOff unless specified❌ not in place — snapshot → copy encrypted → restore → cut over
DynamoDBAlways encrypted✅ switch to a CMK any time
EFS / FSxOff unless specified❌ create new, copy data
Secrets Manager / SSM SecureStringAlways—
⚠️ "Encrypt the database" is a migration, not a setting. RDS encryption is fixed at creation, so retrofitting means snapshot, copy the snapshot with a KMS key, restore the copy, and cut the application over — which involves a new endpoint and a maintenance window (see the restore caveats in RDS & Aurora). Turn on the account-level EBS default and create every database encrypted from the start; the retrofit is the expensive path and it is entirely avoidable.
SET THE DEFAULTS ONCE PER REGION, so nobody has to remember:
$ aws ec2 enable-ebs-encryption-by-default
$ aws ec2 modify-ebs-default-kms-key-id --kms-key-id alias/acme-ebs
$ aws ec2 get-ebs-encryption-by-default --query EbsEncryptionByDefault --output text
true
   ⚠️ per-Region. A new Region starts unencrypted again.

ENFORCE TLS IN TRANSIT — a bucket policy, not a hope:
  { "Sid": "DenyInsecureTransport",
    "Effect": "Deny", "Principal": "*", "Action": "s3:*",
    "Resource": ["arn:aws:s3:::acme-data", "arn:aws:s3:::acme-data/*"],
    "Condition": { "Bool": { "aws:SecureTransport": "false" } } }

$ aws s3api get-object --bucket acme-data --key x /tmp/x --endpoint-url http://s3.amazonaws.com
An error occurred (AccessDenied): ... explicit deny in a resource-based policy

  and the same idea as an SCP, so it applies everywhere at once:
  { "Effect": "Deny", "Action": "s3:*", "Resource": "*",
    "Condition": { "Bool": { "aws:SecureTransport": "false" } } }

WHERE SECRETS SHOULD NEVER BE — and all of these are common:

  ❌ git                          searchable forever, even after the commit is "removed"
  ❌ a container image layer      `docker history` shows it; the registry keeps it
  ❌ an AMI                       anyone who can launch it can read it
  ❌ Terraform state              PLAINTEXT, regardless of `sensitive`
  ❌ CloudFormation parameters    stored in the stack's template history
  ⚠️ Lambda environment variables  encrypted at rest, but readable by ANYONE with
                                   lambda:GetFunctionConfiguration
💡 Lambda environment variables are the nuanced case, so state the nuance. They are encrypted at rest, and for low-sensitivity values they are fine. But the value is returned in plaintext by GetFunctionConfiguration, which is granted by ReadOnlyAccess — so "read-only" access to the account reveals every secret stored that way. For anything that matters, fetch from Secrets Manager at runtime and cache it in the INIT phase (see Lambda), or use the Parameters and Secrets extension, which caches for you.
ROTATION — and the half of it teams forget:
$ aws secretsmanager rotate-secret --secret-id prod/db \
    --rotation-lambda-arn arn:aws:lambda:us-east-1:1111:function:SecretsManagerRDSRotation \
    --rotation-rules AutomaticallyAfterDays=30

  the four-step rotation the Lambda implements:
    createSecret  → generate a new password as AWSPENDING
    setSecret     → set it on the database
    testSecret    → connect using AWSPENDING and verify
    finishSecret  → move the AWSCURRENT label to the new version

  ⚠️ ROTATION IS ONLY HALF THE JOB. If the application read the secret once at
    startup and cached it forever, rotation BREAKS IT at the finish step.

✅ the application side — cache with a TTL, and retry once on an auth failure:
  _cache = {"value": None, "at": 0}
  def get_secret(name, ttl=300):
      now = time.time()
      if _cache["value"] is None or now - _cache["at"] > ttl:
          _cache.update(value=sm.get_secret_value(SecretId=name)["SecretString"], at=now)
      return _cache["value"]

  def connect():
      try:
          return db.connect(get_secret("prod/db"))
      except AuthError:
          _cache["at"] = 0                # force a refresh — the secret just rotated
          return db.connect(get_secret("prod/db"))

Part 5 — Incident Response, the AWS-Specific Moves

THE ORDER MATTERS: PRESERVE → CONTAIN → INVESTIGATE → ERADICATE → RECOVER.
Terminating the instance first destroys the evidence you need.

Leaked long-lived access keyupdate-access-key --status Inactive, then deleteDeactivate first — reversible if you are wrong
Leaked temporary credentialsDeny on aws:TokenIssueTimeThey cannot be deleted, only outlived or denied
Compromised instanceSnapshot, then swap to a quarantine SGPreserve memory/disk before isolating or stopping
Compromised roleRevoke sessions, then fix the trust policyFixing trust alone leaves live sessions working

THE TEMPORARY-CREDENTIAL REVOCATION, which is the one people improvise badly:
$ cat > revoke.json <<'EOF'
{ "Version": "2012-10-17",
  "Statement": [{ "Effect": "Deny", "Action": "*", "Resource": "*",
    "Condition": { "DateLessThan": { "aws:TokenIssueTime": "2026-08-20T14:06:00Z" } } }] }
EOF
$ aws iam put-role-policy --role-name CompromisedRole \
    --policy-name AWSRevokeOlderSessions --policy-document file://revoke.json
   → every session issued BEFORE that timestamp is denied everything, instantly.
     Workloads that refresh from IMDS or a task role recover on their next refresh.

FORENSICS BEFORE ISOLATION — snapshot, then quarantine, and never terminate:
$ VOL=$(aws ec2 describe-instances --instance-ids i-0compromised \
    --query 'Reservations[0].Instances[0].BlockDeviceMappings[0].Ebs.VolumeId' --output text)
$ aws ec2 create-snapshot --volume-id $VOL \
    --description "forensic i-0compromised 2026-08-20" \
    --tag-specifications 'ResourceType=snapshot,Tags=[{Key=Incident,Value=INC-4821}]'

$ aws ec2 modify-instance-attribute --instance-id i-0compromised --groups sg-0quarantine
   (sg-0quarantine: no ingress, egress only to the forensics collector)
$ aws ec2 modify-instance-metadata-options --instance-id i-0compromised --http-endpoint disabled
   → cuts the instance off from new credentials while leaving it running for analysis.
🔑 A leaked access key posted publicly triggers an AWS response of its own. AWS scans public sources and, on detecting an exposed key, attaches a quarantine policy (AWSCompromisedKeyQuarantine…) that denies the operations most used for abuse, and opens a support case. That is a safety net, not a plan — it fires after exposure, covers only some actions, and finding it attached to one of your users means the key was public. Treat its appearance as a confirmed incident.

❌ An IAM policy granting kms:Decrypt against a key whose policy never delegated to IAM, databases created unencrypted "to fix later", secrets in Lambda environment variables and Terraform state, rotation configured without the application reloading, GuardDuty enabled and never read, and an incident response that starts by terminating the instance. The identity policy is obviously correct and access is still denied, because the key policy is authoritative and nobody looks there. The databases were created without encryption because it was quicker, and retrofitting now means snapshot, copy, restore and a cutover window nobody has scheduled for eighteen months. Secrets sit in Lambda environment variables where anyone with ReadOnlyAccess can read them, and in a Terraform state file that half the engineering team can download. Rotation runs every thirty days and breaks the service every thirty days, because the application read the password once at startup. GuardDuty produces four hundred findings into a dashboard someone opened during onboarding, so the crypto-mining finding from Tuesday is still unread. And when a role is compromised, the first action is to terminate the instance, destroying the disk and memory that would have explained how, while the attacker's temporary credentials keep working from somewhere else entirely.

✅ Read the key policy first, encrypt at creation, keep secrets in a secrets store and reload them, route findings to humans and automation, and preserve before you contain. When a KMS denial makes no sense, check whether the key policy delegates to IAM at all — and scope keys with kms:ViaService and encryption context so a stolen credential cannot decrypt arbitrary ciphertext. Turn on account-level EBS default encryption and create every database encrypted, because RDS and EBS cannot be encrypted in place and the retrofit is a migration with a cutover. Put credentials in Secrets Manager, fetch them in the INIT phase, cache with a TTL, and retry once on an authentication failure so rotation is invisible rather than an outage — and never let a secret reach git, an image layer, an AMI, a CloudFormation parameter or a state file. Route high-severity findings to a pager, medium to a ticket queue, and a narrow set of unambiguous ones to automatic remediation, because a dashboard is not a control. Use Access Analyzer's unused-access findings to drive least-privilege from evidence. And run incidents in the order preserve, contain, investigate, eradicate, recover: snapshot the volume, swap to a quarantine security group, disable IMDS, deny sessions by aws:TokenIssueTime — and keep that policy document in the runbook, because improvising it during an incident wastes the minutes that matter.

Interview Questions

Beginner: What is envelope encryption and why does KMS use it?

KMS encrypts a key, and that key encrypts your data. The service calls GenerateDataKey, which returns a plaintext data key and an encrypted copy of it. Your data is encrypted locally with the plaintext key, the plaintext key is discarded, and the encrypted key is stored alongside the ciphertext. To read, you send the encrypted key back to KMS, get the plaintext key, and decrypt locally.

ReasonDetail
SizeKMS's Encrypt API caps at 4 KB — a 5 GB file could never go through it
PerformanceOnly 32 bytes cross the network; bulk encryption happens locally at line rate
Blast radiusA data key protects one object; the KMS key never leaves the service
AuditabilityEvery use of the KMS key is a CloudTrail event

The practical consequence worth adding is S3 Bucket Keys: without them, every object operation is a KMS request, which the S3 lesson measured at $577 a month — Bucket Keys derive per-object keys from a short-lived bucket-level key and cut that by 99%.

The deciding question is rotation. If the value is a credential that should rotate — a database password, an API key — Secrets Manager, because rotation with staging labels (AWSPENDING → AWSCURRENT) is the whole feature you are paying for. For configuration, feature flags, ARNs and endpoints, Parameter Store's standard tier is free and perfectly good, and SecureString parameters are KMS-encrypted too.

Most real systems use both: Parameter Store for configuration, Secrets Manager for the handful of things that rotate. And the point that matters more than either: fetch at runtime and cache with a TTL, so a rotation is invisible rather than an outage.

Mid: An IAM policy grants kms:Decrypt on the key, and the call is still denied. Why?

Because KMS key policies are authoritative in a way other resource policies are not. For most services, an identity policy or a resource policy suffices within one account. For KMS, the key policy must either name the principal directly, or explicitly delegate to IAM — which the default key policy does with a kms:CallerAccount condition. If someone replaced that default with a narrow policy, no identity policy in the account can grant access.

$ aws kms get-key-policy --key-id 9f2a-4b2c --policy-name default \
    --query Policy --output text | jq '.Statement[].Principal'
{ "AWS": "arn:aws:iam::111122223333:role/DataTeam" }
   → only DataTeam. No delegation to IAM. Every other identity policy is inert.
Also checkSymptom
A kms:ViaService conditionWorks through S3, denied when called directly
An encryption-context conditionDenied unless the context matches exactly
Cross-account useNeeds the key policy and the caller's identity policy
GrantsAccess can come from a grant rather than a policy — check list-grants

The habit worth forming: on any KMS denial, read the key policy before touching the identity policy. It is also the explanation for the classic cross-account SSE-KMS failure, where the bucket policy and the role policy are both correct and the missing grant is on the key.

Mid: Secrets rotation is enabled and the application breaks every 30 days. Explain.

The application reads the secret once at startup and caches it for the process lifetime. Rotation's final step moves the AWSCURRENT label to the new version and the old password stops working — so every long-lived process is holding a credential that has just been invalidated.

Rotation is two halves, and teams implement only the first:

  createSecret → setSecret → testSecret → finishSecret     ← Secrets Manager's half
  the application must NOTICE                              ← the half that is missing
FixEffect
TTL cache (5 minutes)Picks up the new value within the TTL
Retry once on auth failureInvalidate the cache and refetch — closes the window entirely
Parameters and Secrets Lambda extensionCaching handled outside your code
RDS Proxy with IAM authThe application never holds a password at all

The strongest answer is the last row: with RDS Proxy holding the credentials and IAM authentication from the application, rotation stops being an application concern — there is no cached password to invalidate. Failing that, the TTL-plus-retry pattern is a few lines and makes rotation a non-event. And a rotation that has never been tested is not a control: rotate on demand in staging and confirm the service does not blink.

Senior: An access key has been leaked publicly. Walk through your response.

Order matters: preserve, contain, investigate, eradicate, recover. The instinct to delete everything immediately destroys the evidence needed to answer the only question that matters — what did they do.

1. Contain, reversibly. Deactivate the key rather than deleting it, so the identifier remains resolvable in CloudTrail. If the compromised identity is a role, add the aws:TokenIssueTime deny policy as well, because any temporary credentials already issued cannot be deleted and would otherwise keep working:

$ aws iam update-access-key --user-name ci-user --access-key-id AKIA… --status Inactive
$ aws iam put-role-policy --role-name AssumedByCI --policy-name AWSRevokeOlderSessions \
    --policy-document file://revoke.json      # Deny * where aws:TokenIssueTime < now

2. Determine the blast radius. What could the key do, and what did it do? Access Analyzer or the attached policies answer the first; CloudTrail answers the second — every call, from which IP, at what time. Look specifically for persistence: new users, new keys, new roles, changed trust policies, and anything in Regions you do not normally use, which is where crypto-mining appears.

3. Eradicate. Delete the key, remove anything the attacker created, and rotate every secret the identity could read — assume anything reachable was read.

4. Fix the cause, which is never "someone leaked a key". It is that a long-lived key existed at all. Replace it with OIDC federation for CI (see IAM Advanced), so there is no credential to leak; add secret scanning in CI and on the repository; and use permission boundaries so the next leaked identity cannot escalate.

Two things worth raising unprompted. If AWS attached a AWSCompromisedKeyQuarantine… policy, the key was publicly indexed — treat that as confirmation, not as the remediation, since it covers only some actions and fires after exposure. And check GuardDuty for the finding types that accompany this (UnauthorizedAccess:IAMUser/…, CryptoCurrency:EC2/…) — if it was enabled and nobody read it, the detection gap is a second, separate finding for the postmortem.

Senior: Design the security baseline for a new AWS Organization.

Structure first, because the account boundary is the only control that cannot be edited away. Separate accounts per environment and per domain, an OU hierarchy that matches how you will apply policy, and dedicated accounts for logging, security tooling and shared services — with the log archive account restricted so that even administrators of the workload accounts cannot alter its contents.

Delivery matters as much as content. Ship the baseline as StackSets with auto-deployment so accounts created next year inherit it automatically — a baseline applied by hand drifts within a quarter and never reaches new accounts. Then verify it with a scheduled check that can fail, because a control nobody tests is an assumption.

The distinction I would emphasise to a regulator or an auditor is between controls a team could disable and controls they cannot. Anything that matters belongs in an SCP at the Organization level, not in an account-level setting a workload team owns. That single distinction is what makes the baseline an architecture rather than a checklist.

What I would deliberately not do: enable every detective service at maximum verbosity on day one. Four hundred unread findings train people to ignore the console, and the cost is real. Start with GuardDuty and AWS Foundational Security Best Practices, route them properly, and add Macie and Inspector once there is a workflow that acts on what they produce.

✅ THE FIX — TTL cache plus one retry on an authentication failure:
$ cat > app_good.py <<'PY'
import boto3, json, time, psycopg2
sm = boto3.client("secretsmanager")
_c = {"v": None, "at": 0.0}

def secret(ttl=300, force=False):
    now = time.time()
    if force or _c["v"] is None or now - _c["at"] > ttl:
        _c["v"] = json.loads(sm.get_secret_value(SecretId="prod/db")["SecretString"])
        _c["at"] = now
    return _c["v"]

def connect(force=False):
    s = secret(force=force)
    return psycopg2.connect(host=HOST, user=s["username"], password=s["password"])

conn = connect()
while True:
    try:
        conn.cursor().execute("SELECT 1"); print("ok", flush=True)
    except psycopg2.OperationalError as e:
        if "authentication failed" in str(e):
            print("auth failed - refreshing secret", flush=True)
            conn = connect(force=True)                 # ← the important line
        else:
            conn = connect()
    time.sleep(10)
PY

THE CONTAINMENT FUNCTION — preserve BEFORE isolating:
$ cat > auto_contain.py <<'PY'
import boto3, os
ec2 = boto3.client("ec2")
QUARANTINE_SG = os.environ["QUARANTINE_SG"]
CONTAIN_TYPES = ("CryptoCurrency:EC2/", "Backdoor:EC2/", "UnauthorizedAccess:EC2/")

def handler(event, context):
    d = event["detail"]
    if not d["type"].startswith(CONTAIN_TYPES):
        return {"action": "notified_only", "type": d["type"]}
    iid = d["resource"]["instanceDetails"]["instanceId"]

    # 1. PRESERVE — snapshot every volume before touching anything
    inst = ec2.describe_instances(InstanceIds=[iid])["Reservations"][0]["Instances"][0]
    for bdm in inst["BlockDeviceMappings"]:
        ec2.create_snapshot(VolumeId=bdm["Ebs"]["VolumeId"],
            Description=f"forensic {iid} {d['id']}",
            TagSpecifications=[{"ResourceType":"snapshot",
                "Tags":[{"Key":"Incident","Value":d["id"]},
                        {"Key":"Instance","Value":iid}]}])

    # 2. CONTAIN — isolate, and cut off new credentials
    ec2.modify_instance_attribute(InstanceId=iid, Groups=[QUARANTINE_SG])
    ec2.modify_instance_metadata_options(InstanceId=iid, HttpEndpoint="disabled")

    # 3. MARK — do NOT terminate; the evidence is in memory
    ec2.create_tags(Resources=[iid],
        Tags=[{"Key":"Quarantined","Value":d["id"]},{"Key":"DoNotTerminate","Value":"true"}])
    return {"action": "contained", "instance": iid}
PY

Auditors and regulators care about controls a team cannot disable — so anything that genuinely matters belongs in an SCP, not in an account setting. 🎯 Key Takeaways

  • KMS encrypts a key, not your data — envelope encryption exists because the Encrypt API caps at 4 KB and because only 32 bytes should cross the network.
  • The KMS key policy is authoritative. Proven: AdministratorAccess plus kms:* was still denied, with the error explicitly saying "no resource-based policy allows".
  • Scope keys with kms:ViaService and encryption-context conditions so a stolen credential cannot decrypt arbitrary ciphertext directly.
  • The encryption context is authenticated data recorded in CloudTrail — it makes the audit log show what was decrypted, not just that a key was used.
  • Key rotation adds new material and retains the old; it re-encrypts nothing. Key deletion has a mandatory 7–30 day window because it destroys every ciphertext permanently.
  • RDS and EBS cannot be encrypted in place. The measured path was snapshot → copy with a key → restore → cut over: ~80 minutes plus a real cutover window, with default parameter groups and no backups on the restored instance.
  • Set account-level EBS default encryption per Region, and deny unencrypted creation with an SCP so the decision never arises.
  • Lambda environment variables are readable by anyone with ReadOnlyAccess via GetFunctionConfiguration — encrypted at rest is not the same as private.
  • Never let secrets reach git, an image layer, an AMI, a CloudFormation parameter, or Terraform state (plaintext regardless of sensitive).
  • Rotation is two halves and teams ship one. Read-once-at-startup fails on every rotation; a TTL cache plus one retry on auth failure reduced it to a single failed request.
  • The strongest version removes the password entirely: ManageMasterUserPassword plus RDS Proxy with IAM auth means zero failures per rotation.
  • Test rotation with --rotate-immediately under load — an unexercised rotation schedule is a scheduled outage.
  • Detective services are not controls until findings reach someone. Three high-severity GuardDuty findings sat unread for six days while crypto-mining ran.
  • Route by severity: page, ticket, or narrow auto-remediation — and automate only where the correct action is never ambiguous.
  • Preserve before you contain. Snapshot volumes, swap to a quarantine SG, disable IMDS, tag DoNotTerminate — terminating destroys the evidence and does not stop the attacker's other credentials.
  • Leaked temporary credentials cannot be deleted — deny by aws:TokenIssueTime, and keep that policy document in the runbook.
  • Deactivate a leaked key rather than deleting it: reversible, and the key ID stays resolvable in CloudTrail while you scope the incident.
  • Hunt persistence after containment: new users, new keys, changed trust policies, and running instances in Regions you never use.
  • The cause of a leaked key is never "someone leaked a key" — it is that a long-lived credential existed. Replace CI keys with OIDC federation so there is nothing to leak.
  • An AWSCompromisedKeyQuarantine… policy appearing means the key was publicly indexed; treat it as confirmation of an incident, never as the fix.
  • Ship the account baseline as StackSets with auto-deployment so future accounts inherit it, and put anything that genuinely matters in an SCP — the only layer a workload team cannot disable.
  • Write a baseline check that can fail, run it daily, and break it deliberately once: an assertion you have never seen fail is not a control.
