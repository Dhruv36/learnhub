VPCs, Subnets & Security Groups Networking

What you'll master: that a VPC is a routing domain, not a device, and that nothing in it is "public" — a subnet is public only because a route table entry says so, which is the single fact that explains most surprise exposures and most mysterious timeouts; CIDR decisions you cannot take back, and why AWS silently removes five addresses from every subnet; security groups as stateful, allow-only, unioned filters that can reference other security groups — the idiom that makes rules survive autoscaling — along with the connection-tracking behaviour that means removing a rule does not drop an established connection; NACLs as stateless, ordered, subnet-level blunt instruments, and the ephemeral-port trap that makes a "correct" NACL break every reply; address exhaustion, where an EKS cluster hands a VPC IP to every pod and a /24 node subnet dies at 29 pods per node; and a layered debugging order that finds any connectivity failure in five checks instead of five hours. Prerequisites: Shared Responsibility, Accounts & Regions.

Part 1 — A VPC Is a Routing Domain

There is no box. A VPC is a set of address ranges, a distributed routing table, and a policy engine that AWS enforces inside its own network fabric. Nothing is plugged into anything. Once you stop imagining a switch, the rules stop being arbitrary: everything is either an address, a route, or a filter.

ObjectScopeWhat it really isChangeable later?

🔑 A subnet lives in exactly one Availability Zone, and that is the whole reason subnets exist. They are not security boundaries and not organisational units — they are the mechanism by which you place things in failure domains. "Three private subnets" almost always means "one per AZ", and a workload with subnets in only one AZ has no multi-AZ story regardless of how many replicas it runs. This is also why cross-AZ traffic costs money (see Cost) — the subnet you chose determined the bill.
CIDR SIZING — the decision you cannot undo:

$ aws ec2 create-vpc --cidr-block 10.42.0.0/16 --query 'Vpc.VpcId' --output text
vpc-0ab1c2d3e4f56789a

  /16  = 65,536 addresses   ← default choice; costs nothing to be generous
  /20  =  4,096
  /24  =    256             ← per-subnet, a common and often regrettable size
  /28  =     16             ← the smallest AWS allows

  You may ADD secondary CIDRs later. You may NOT shrink, renumber, or change
  a subnet's CIDR — the only fix is to build a new subnet and migrate.

The choice that hurts most is not size but overlap. Every VPC-to-VPC mechanism — peering, Transit Gateway, VPN, Direct Connect — requires non-overlapping ranges, and there is no NAT to rescue you. Three teams that each picked 10.0.0.0/16 because it was the console default can never connect their environments without renumbering.

❌ every account defaulting to 10.0.0.0/16
     prod  10.0.0.0/16   staging  10.0.0.0/16   data  10.0.0.0/16
     → peering prod↔data is IMPOSSIBLE. Not hard. Impossible.

✅ allocate from a plan, per account and Region, before anyone builds:
     prod    us-east-1   10.  0.0.0/16      staging us-east-1   10. 20.0.0/16
     prod    eu-west-1   10.  1.0.0/16      data    us-east-1   10. 40.0.0/16
     sandbox any         10.200.0.0/16      on-prem             172.16.0.0/12
   → use IPAM to enforce it:

$ aws ec2 allocate-ipam-pool-cidr --ipam-pool-id ipam-pool-0a1b --netmask-length 16
{ "IpamPoolAllocation": { "Cidr": "10.40.0.0/16" } }

Part 2 — "Public" Is a Route, Not a Property

There is no public: true anywhere in a VPC. A subnet is public if — and only if — its route table contains a route to an Internet Gateway. Everything else people call "making it public" is downstream of that one entry.

$ aws ec2 describe-route-tables --route-table-ids rtb-public \
    --query 'RouteTables[0].Routes[].[DestinationCidrBlock,GatewayId]' --output text
10.42.0.0/16   local                               ← implicit, cannot be removed or overridden
0.0.0.0/0      igw-0f3c9a1e                        ← THIS is what "public" means

$ aws ec2 describe-route-tables --route-table-ids rtb-private \
    --query 'RouteTables[0].Routes[].[DestinationCidrBlock,NatGatewayId]' --output text
10.42.0.0/16   None
0.0.0.0/0      nat-04c8e1f2                        ← outbound only; nothing can initiate inbound
To reach the internet from an instance, you need ALL ofMiss it and you get
A route to an IGW (public) or NAT (private)Timeout
A public IP or Elastic IP on the ENI (public subnets only)Timeout — a public subnet without a public IP is just a private subnet
Security group egress allowing itTimeout
NACL allowing outbound and the return on ephemeral portsTimeout
For inbound: SG ingress + NACL inbound + something listeningTimeout or connection refused
⚠️ Every one of those failures presents as an identical timeout. That is why guessing is so expensive here and why Part 6 gives an order to check them in. The one failure that looks different is connection refused, which means packets arrived and nothing was listening — so the entire network path is fine and the problem is the application.
THE MAIN ROUTE TABLE TRAP — a new subnet is associated with the MAIN route table implicitly:

$ aws ec2 create-subnet --vpc-id vpc-0ab1 --cidr-block 10.42.9.0/24 \
    --availability-zone us-east-1a --query 'Subnet.SubnetId' --output text
subnet-0new123

$ aws ec2 describe-route-tables --filters Name=association.subnet-id,Values=subnet-0new123 \
    --query 'RouteTables[].RouteTableId' --output text
                                                   ← EMPTY. No explicit association.
$ aws ec2 describe-route-tables --filters Name=vpc-id,Values=vpc-0ab1 \
    Name=association.main,Values=true --query 'RouteTables[0].Routes[].GatewayId' --output text
local   igw-0f3c9a1e
   → the main route table has an IGW route, so this "private" subnet is PUBLIC.
     Nobody wrote that down. It was inherited.

The two failure modes are mirror images, and both are common: if the main route table has an IGW route, every subnet anyone forgets to associate is accidentally internet-facing; if it does not, every such subnet is a black hole and someone spends an afternoon on it. Fix it structurally — leave the main route table with only the local route, and associate every subnet explicitly.

$ aws ec2 associate-route-table --subnet-id subnet-0new123 --route-table-id rtb-private
{ "AssociationId": "rtbassoc-0d2e4f", "AssociationState": { "State": "associated" } }

Route selection is LONGEST PREFIX MATCH, and `local` always wins for the VPC range:

  0.0.0.0/0        nat-04c8e1f2       ← default
  10.99.0.0/16     pcx-0a1b2c3d       ← more specific: peering wins for that range
  10.42.0.0/16     local              ← cannot be overridden, cannot be deleted
  pl-63a5400a      vpce-0f3c9a1e      ← prefix list (S3), beats the default route

PropertySecurity GroupWhy it matters

THE IDIOM — reference the group, not the addresses:

❌ what people write first:
$ aws ec2 authorize-security-group-ingress --group-id sg-db \
    --protocol tcp --port 5432 --cidr 10.42.1.14/32
$ aws ec2 authorize-security-group-ingress --group-id sg-db \
    --protocol tcp --port 5432 --cidr 10.42.2.31/32
   ...one rule per app server. The ASG scales at 3am. The new instance is denied.

✅ what survives:
$ aws ec2 authorize-security-group-ingress --group-id sg-db --ip-permissions \
   'IpProtocol=tcp,FromPort=5432,ToPort=5432,UserIdGroupPairs=[{GroupId=sg-app,Description="app tier"}]'
   → "any ENI carrying sg-app may reach 5432", forever, at any scale,
     in any subnet, at any address. Zero maintenance.

$ aws ec2 describe-security-groups --group-ids sg-db \
    --query 'SecurityGroups[0].IpPermissions[0].UserIdGroupPairs[].GroupId' --output text
sg-app
🔑 Security-group references turn network rules into role rules. "The app tier may reach the database tier" is a statement about roles that stays true through scaling, replacement, re-IPing and AZ changes. CIDR rules are a statement about a moment in time. Almost every tangle of 60 hand-maintained /32 rules is a group reference that was never written — and note the 60-rule-per-group quota exists precisely because that list is not supposed to grow.
QUOTAS worth knowing before you design around them:

  rules per security group          60 inbound + 60 outbound (adjustable)
  security groups per ENI            5 (adjustable to 16)
  rules per ENI                      ≤ 1000  (groups × rules — the REAL ceiling)

$ aws ec2 describe-security-groups --group-ids sg-legacy \
    --query 'length(SecurityGroups[0].IpPermissions)'
58                                                 ← two rules from a 3am incident

Now the behaviour that surprises people during an incident: security groups are stateful because AWS tracks connections. Removing a rule does not tear down flows already established under it.

$ aws ec2 revoke-security-group-ingress --group-id sg-web \
    --protocol tcp --port 22 --cidr 203.0.113.77/32
   → the attacker's EXISTING ssh session stays up. Tracked connections survive
     rule removal; only NEW connections are refused.

To actually cut it: kill the process, detach/replace the SG on the ENI, stop the
instance, or add a NACL deny (stateless, so it drops packets immediately):

$ aws ec2 create-network-acl-entry --network-acl-id acl-0a1b --rule-number 10 \
    --protocol -1 --rule-action deny --cidr-block 203.0.113.77/32 --ingress
   → the session dies on the next packet.
⚠️ There is an exception that cuts the other way. A flow becomes untracked when the rules allow all traffic in both directions (0.0.0.0/0, all protocols, both ingress and egress). Untracked flows are not stateful — they are interrupted the instant a rule changes. So the wide-open group behaves differently under a rule change than the tight one, which is exactly backwards from what anyone expects during an incident. This is one of the few genuinely obscure VPC behaviours that shows up in senior interviews.

Part 4 — NACLs: Stateless, Ordered, and Usually the Wrong Tool

Security GroupNetwork ACL

THE EPHEMERAL PORT TRAP — the single most common NACL bug:

  A "correct-looking" NACL for a web tier:
    inbound   100  allow tcp 443  0.0.0.0/0
    inbound   *    deny  all
    outbound  100  allow tcp 443  0.0.0.0/0
    outbound  *    deny  all

  → EVERY REQUEST HANGS.

  Because NACLs are STATELESS, the reply is a separate decision. The client
  connected FROM a random high port, so the response goes TO that port:

    client 203.0.113.5:54233  →  server 10.42.1.20:443     (inbound 443 ✅)
    server 10.42.1.20:443     →  client 203.0.113.5:54233  (outbound 54233 ❌ DENIED)

✅ the fix — allow the ephemeral range in the RETURN direction:
    outbound  110  allow tcp 1024-65535  0.0.0.0/0

  and symmetrically, a subnet making outbound calls needs:
    inbound   110  allow tcp 1024-65535  0.0.0.0/0

  ranges differ by client OS: Linux 32768–60999, Windows 49152–65535,
  NAT Gateway 1024–65535, ELB 1024–65535.  Use 1024–65535 and stop guessing.

$ aws ec2 create-network-acl-entry --network-acl-id acl-0a1b --rule-number 110 \
    --protocol tcp --port-range From=1024,To=65535 --rule-action allow \
    --cidr-block 0.0.0.0/0 --egress
🔑 Use security groups for everything; reach for NACLs only for a blunt, subnet-wide deny that must apply regardless of any security group. The legitimate cases are narrow: blocking a specific hostile CIDR during an incident, an organisational rule that a subnet may never talk to the internet at all, or a compliance control that must be independent of application-team-managed groups. Everything else is a security group, because the NACL will eventually break something on an ephemeral port and the person debugging it will not be you.

Part 5 — Running Out of Addresses

IP exhaustion is a scheduled outage you set in motion months earlier, and it always arrives during growth — which is to say, at the worst time. Four consumers eat addresses faster than people plan for.

ConsumerAddresses usedSurprise factor
AWS reservation5 per subnetA /28 gives 11 usable
ALB / NLB8 free per subnet, more while scalingLoad balancer creation simply fails
EKS VPC-CNIOne VPC IP per pod, pre-warmed per ENIThe big one — see below
Fargate / Lambda-in-VPCOne ENI eachScales with concurrency, not with instances
Interface endpointsOne ENI per AZ per endpointTwenty endpoints × 3 AZs = 60 addresses
EKS, where every pod holds a real VPC address:

$ kubectl get pods -A --field-selector status.phase=Pending -o wide | head -3
kube-system   coredns-7f9c-4h2k    0/1  Pending  0  4m  <none>  <none>
shop          checkout-6d4f9-x2k   0/1  Pending  0  4m  <none>  <none>

$ kubectl describe pod checkout-6d4f9-x2k | tail -3
  Warning  FailedCreatePodSandBox  ... failed to assign an IP address to container

$ aws ec2 describe-subnets --subnet-ids subnet-0node-a subnet-0node-b subnet-0node-c \
    --query 'Subnets[].[SubnetId,CidrBlock,AvailableIpAddressCount]' --output text
subnet-0node-a   10.42.10.0/24   0
subnet-0node-b   10.42.11.0/24   2
subnet-0node-c   10.42.12.0/24   0
                                                   ← the cluster is out of addresses

THE ARITHMETIC nobody does in advance:

  max pods per node = (ENIs × IPs-per-ENI) − 1        [VPC-CNI, no prefix delegation]
    m5.large   :  3 ENIs × 10 IPs − 1  =  29 pods
    m5.2xlarge :  4 ENIs × 15 IPs − 1  =  59 pods

  a /24 node subnet = 251 usable IPs
    ≈ 8 m5.large nodes at full pod density, per AZ.  That is a small cluster.
  and the CNI PRE-WARMS a whole ENI's worth of IPs per node, so consumption
  outruns actual pod count.

THREE FIXES, in order of how much they change:

(1) PREFIX DELEGATION — /28 prefixes instead of single IPs. Same subnet, more pods:
$ kubectl set env ds/aws-node -n kube-system ENABLE_PREFIX_DELEGATION=true
$ kubectl get node ip-10-42-10-31 -o jsonpath='{.status.allocatable.pods}'
110                                                ← was 29, now the kubelet cap

(2) A SECONDARY CIDR from carrier-grade NAT space, dedicated to pods:
$ aws ec2 associate-vpc-cidr-block --vpc-id vpc-0ab1 --cidr-block 100.64.0.0/16
   → 65,536 pod addresses that do not consume your routable 10.x plan.
     (100.64.0.0/10 is RFC 6598 — not internet-routable, and not RFC 1918,
      so it will not collide with on-prem or a partner VPC.)

(3) Bigger node subnets from the start — /20 per AZ costs nothing in a /16 VPC.
💡 The general principle: be extravagant with private address space and stingy with nothing else. Addresses in RFC 1918 are free, and a /20 subnet costs exactly what a /24 does. The only real constraint is your organisation-wide allocation plan, which is why Part 1 insists on writing one before the first VPC exists. Every hour spent renumbering later would have been a minute spent planning.

Part 6 — Debugging a Timeout, in Order

Five different misconfigurations produce a byte-identical timeout. Guessing means changing things until it works, which is how security groups end up at 0.0.0.0/0. Check in this order — it goes from cheapest and most likely to most expensive and least likely.

    --query 'NetworkInsightsAnalyses[0].Explanations[0].SecurityGroup.Id' --output text

And Flow Logs answer "did the packet arrive at all?", which splits the search space in half:

$ aws ec2 create-flow-logs --resource-type NetworkInterface --resource-ids eni-0server \
    --traffic-type ALL --log-destination-type cloud-watch-logs \
    --log-group-name /vpc/flowlogs --deliver-logs-permission-arn arn:aws:iam::1111:role/FlowLogs

fields srcaddr, dstaddr, dstport, action
| filter dstaddr = "10.42.2.31" and dstport = 5432
| stats count() by srcaddr, action

  10.42.1.14   REJECT   4,192                      ← arriving and being dropped: SG or NACL
  10.42.1.15   ACCEPT      881
⚠️ REJECT vs nothing at all is the key distinction. A REJECT record means the packet reached the ENI and a filter dropped it — check groups and NACLs. No record at all means it never arrived — check routing, or the wrong destination entirely. But know what flow logs never record, or you will chase ghosts: traffic to 169.254.169.254 (instance metadata) and 169.254.169.253, DHCP, requests to the Amazon DNS server at VPC-base+2, Windows license activation, and traffic between an ENI and a Network Load Balancer's ENI. "There's nothing in the flow logs" is not proof that nothing happened.

❌ Every VPC on 10.0.0.0/16, subnets inheriting the main route table, database rules written as a list of instance /32s, a NACL added for "defence in depth", /24 subnets under an EKS cluster, and a timeout debugged by widening security groups until it works. Three environments picked the console default CIDR, so peering prod to the data account is permanently impossible without renumbering. New subnets were never explicitly associated with a route table, so some are accidentally internet-facing and others are black holes, and no document records which. The database security group has fifty-eight /32 rules, two of which were added at 3am, and the autoscaling group's newest instance is denied. A NACL was added with matching inbound and outbound rules on port 443, and every request now hangs because the replies go to ephemeral ports nobody allowed. The EKS node subnets are /24s, so at twenty-nine pods per node the cluster stops scheduling with an error that names neither IP addresses nor subnets in a way anyone recognises. And when something times out, the fix is to widen the security group to 0.0.0.0/0, which works, ships, and is never revisited.

✅ Allocate address space centrally, associate every subnet explicitly, reference groups instead of addresses, skip the NACL, size for pods, and debug in a fixed order. Publish a CIDR plan per account and Region before the first VPC exists and enforce it with IPAM, because overlap has no remedy but renumbering. Leave the main route table with only the local route so a forgotten association fails visibly instead of silently exposing a subnet. Write database rules as "any ENI carrying sg-app", which stays correct through every scaling event and never needs maintenance. Do not add NACLs for their own sake — they are stateless, and the ephemeral-port bug they cause is subtle and intermittent; reserve them for a blunt subnet-wide deny that must survive any application-team security group. Give EKS node subnets a /20, or a secondary 100.64.0.0/16 CIDR for pods, and turn on prefix delegation to lift a node from 29 pods to 110. And when something times out, check the error text first — refused means the network is fine — then run Reachability Analyzer, which names the offending group in thirty seconds and costs nothing, rather than widening rules until the symptom disappears.

Interview Questions

Beginner: What makes a subnet "public"?

A route in its route table to an Internet Gateway. That is the entire definition — there is no public flag, no setting, no checkbox that means anything else. A subnet whose route table sends 0.0.0.0/0 to an igw- is public; one that sends it to a nat- is private with outbound access; one with neither is isolated.

The follow-up worth pre-empting: an instance in a public subnet still cannot reach the internet without a public IP or Elastic IP on its ENI, because the Internet Gateway performs a 1:1 NAT between the private address and the public one and has nothing to translate otherwise. A public subnet with no public IPs behaves exactly like a private subnet with no NAT — a total black hole — and that combination is a very common "but it's in the public subnet!" ticket.

Beginner: Security group versus NACL — name the differences that change how you use them.
Security groupNACL

The two that actually change your behaviour: statefulness, because a NACL needs an explicit rule for ephemeral return ports and forgetting it hangs every request; and group references, because they let you express "the app tier may reach the database tier" as a rule that survives every scaling event. Default to security groups for everything and use NACLs only for a blunt subnet-wide deny.

Mid: An instance cannot reach a database in the same VPC. Walk me through the diagnosis without guessing.

Step 0 — read the error. Connection refused means packets arrived and nothing was listening: the whole network path is fine, and you should be looking at the process and its bind address. Timeout means a filter or a route. This one question eliminates half the search space and people skip it constantly.

Then, in order:

CheckWhy here
1. Route table of the source subnetSame-VPC traffic uses the un-removable local route, so this is usually fine — but it catches the case where the "database" is actually in a peered VPC
2. Egress on the source SGDefault is allow-all, so this is only a suspect in hardened environments — but it is one line to check
3. Ingress on the destination SGThe most common single cause. Check the port and that the source is the app's group or CIDR
4. NACLs on both subnets, both directionsStateless — look for the missing 1024–65535 return rule
5. ss -tlnp on the database hostBound to 127.0.0.1 rather than 0.0.0.0 is unreachable from anywhere else

The shortcut I would actually run first: Reachability Analyzer does checks 1–4 statically in about thirty seconds and returns an explanation code naming the exact resource — no packets, no access to either host required. Flow logs then answer "did it arrive?": a REJECT record means a filter dropped it, no record at all means it never got there.

Mid: Your EKS cluster stops scheduling pods with "failed to assign an IP address". What happened, and what are the options?

The AWS VPC CNI gives every pod a real VPC address from the node's subnet, and pre-warms a whole ENI's worth per node. So pod density is capped by instance type — an m5.large gets 3 ENIs × 10 IPs − 1 = 29 pods — and the subnet drains far faster than pod count suggests. A /24 node subnet holds 251 usable addresses, roughly eight fully-packed m5.larges.

FixEffectCost
Prefix delegation (ENABLE_PREFIX_DELEGATION=true)/28 prefixes per ENI: 29 → 110 pods per nodeA DaemonSet env var; nodes must be Nitro
Secondary CIDR 100.64.0.0/16 for pod subnets65k pod addresses that do not consume the routable planCNI config; RFC 6598 space is not routable off-VPC
Larger node subnets (/20)Straightforward headroomRequires new subnets — CIDRs are immutable
Fewer, larger nodesFewer pre-warm poolsCoarser failure domains, worse bin-packing

The one to say out loud: prefix delegation first, because it is a single environment variable, needs no renumbering, and nearly quadruples density on existing subnets. Then plan the secondary CIDR, because the underlying cause is that someone sized node subnets like application subnets, and that will recur as the cluster grows.

Senior: Design the VPC layout for a regulated platform: three environments, forty teams, some workloads needing on-prem connectivity, and an audit requirement to prove isolation.

Start with accounts, not VPCs. The account is the blast radius, the quota boundary and the attribution boundary (see Foundations and Cost), and it is the only isolation an auditor can verify without reading configuration. One account per environment per domain; VPCs inside them are a routing detail. Trying to isolate forty teams with subnets and security groups inside one shared VPC is the design people regret, because every control is then a policy someone can edit.

Address plan before anything is built. A published allocation per account and Region, enforced by IPAM, with room reserved for growth and for a non-RFC-1918 100.64.0.0/10 range for pod networks. Overlap is unfixable, so this is the one decision that must be made centrally on day one.

Hub-and-spoke with Transit Gateway, not a peering mesh. Peering does not transit — n VPCs need n(n−1)/2 connections and every one is a manual route entry. A TGW with separate route tables per environment gives you both connectivity and the isolation proof: prod's route table simply has no route to dev, which is a configuration an auditor can read in one screen. On-prem attaches once to the hub rather than once per VPC.

Inside each VPC, three tiers per AZ: public (load balancers only), private (application), isolated (databases, no NAT route at all). Security groups reference each other by role — LB group → app group → data group — so the rules are readable as an architecture diagram and survive scaling. Gateway endpoints for S3 and DynamoDB in every VPC from creation, because they are free and their absence is a pure NAT tax.

For the audit specifically: flow logs to a central account's S3 bucket, queried with Athena; Reachability Analyzer runs as evidence that a path does not exist; Config rules for "no security group allows 0.0.0.0/0 on 22 or 3389" and "no isolated subnet has an IGW route"; and SCPs that prevent deleting flow logs or attaching an IGW in the data accounts at all. The distinction that matters to an auditor is between controls a team could change and controls they cannot — put the isolation guarantees in the second category, at the Organization level.

What I would explicitly not do: a shared services VPC that every team's traffic traverses, because it becomes a single point of failure with forty owners; and NACLs as a per-team control, because they are stateless, cap out at 20 rules per direction, and their failures are intermittent and blamed on the application for weeks.

Senior: A security group rule was revoked during an active incident and the attacker's session stayed up. Explain, and give the correct incident response.

Security groups are stateful because AWS tracks connections in the fabric. A revoked rule stops new connections from being established; it does not tear down flows already in the tracking table. An established SSH or database session therefore survives the revocation indefinitely — which is precisely the behaviour you do not want at the moment you need it.

What actually cuts an established flow:

ActionSpeedBlast radius
NACL deny for the source CIDRImmediate — stateless, drops the next packetThe whole subnet, but scoped to that CIDR
Replace the SGs on the ENI with an empty groupImmediate for new, and drops tracked flows because the rule set no longer permits themThat ENI only
Stop or isolate the instanceImmediateLoses volatile forensic state — snapshot first
Kill the process / revoke the credentialImmediatePrecise, but only if you know what to kill

The obscure counterpart, worth knowing because it is the same mechanism inverted: when a group allows all traffic in both directions, flows become untracked and are interrupted instantly by a rule change. So the wide-open configuration reacts faster to remediation than the carefully-scoped one. Do not let that become an argument for wide-open groups — let it be the reason your runbook says "NACL deny", not "revoke the rule".

And the wider lesson for the runbook: pair this with credential revocation from IAM Advanced. Cutting the network while the attacker still holds valid temporary credentials only moves them to a different source address; cutting the credentials while the network path stays open leaves the next stolen key usable. Incident response has to do both, in that order, and the time to work out the commands is not during the incident.

🎯 Key Takeaways

  • A VPC is a routing domain, not a device — everything in it is an address, a route, or a filter.
  • A subnet lives in exactly one AZ, and that is why subnets exist: they place things in failure domains, and they determine your cross-AZ bill.
  • CIDRs are immutable — you may add secondary ranges but never shrink or renumber; overlap between accounts makes peering permanently impossible.
  • Publish an address plan per account and Region before the first VPC exists, and enforce it with IPAM. Private space is free; be extravagant.
  • AWS reserves 5 addresses per subnet — a /28 yields 11 usable, not 16. Read AvailableIpAddressCount, never arithmetic.
  • "Public" is a route to an Internet Gateway — there is no flag — and the ENI needs a public IP, or the IGW has nothing to translate.
  • A subnet with no explicit route-table association silently inherits the main table: accidentally internet-facing, or a black hole. Leave the main table with local only.
  • Routing is longest-prefix-match, and the local route can never be overridden or removed.
  • Security groups are stateful, allow-only, attached to ENIs, and unioned — adding a group can only widen access.
  • Reference other security groups instead of CIDRs. "Any ENI carrying sg-app" survives every scaling event, works cross-VPC and cross-account, and cannot go stale the way a /32 does.
  • Revoking a rule does not drop established connections — tracked flows survive; use a NACL deny or replace the ENI's groups to cut one immediately.
  • Flows allowed all traffic both ways become untracked and are cut instantly by a rule change — the opposite of what everyone expects.
  • NACLs are stateless, numbered, first-match-wins, subnet-level; the ephemeral-port trap (allow 1024–65535 in the return direction) hangs every request.
  • Use NACLs only for a blunt deny that must apply regardless of any security group. "Defence in depth" alone is not a reason.
  • EKS gives every pod a real VPC address and pre-warms a whole ENI's worth per node — an m5.large caps at 29 pods and a /24 holds ~8 packed nodes.
  • FailedCreatePodSandBox: failed to assign an IP is a scheduling success — never add nodes; that consumes more addresses.
  • Prefix delegation took a node from 29 to 110 pods with one environment variable and no renumbering; a 100.64.0.0/16 secondary CIDR fixes it structurally.
  • ALBs and NLBs need 8 free addresses per subnet, and creation fails outright without them.
  • Five misconfigurations produce an identical timeout — but "connection refused" means the network is fine. Read the error before touching anything.
  • Debug in order: error text → Reachability Analyzer (names the resource in ~30s) → flow logs → ss -tlnp. A REJECT record means a filter dropped it; no record means it never arrived.
  • Flow logs never record IMDS, DHCP, Amazon DNS, or ENI↔NLB traffic — "nothing in the logs" is not proof that nothing happened.
