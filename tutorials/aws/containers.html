ECS, EKS & Fargate Compute

What you'll master: the framing that makes the whole area click — ECS and EKS are orchestrators, Fargate is a capacity provider, so "ECS or Fargate?" is a malformed question; ECS task definitions, and the execution role versus task role distinction that produces two completely different errors when you swap them; awsvpc networking, where every task takes a real VPC address and an ENI slot, so an m5.large runs three tasks and then stops regardless of free CPU; Fargate's fixed CPU/memory menu, its 20 GB of ephemeral storage, and the utilisation crossover where it becomes cheaper than EC2 rather than more expensive — measured at 61%; EKS as AWS glue around Kubernetes — IRSA, the VPC CNI, the Load Balancer Controller, and the access-entry model that replaced the aws-auth ConfigMap you could lock yourself out with; ECR lifecycle policies, pull-through caching and the Docker Hub rate limit that breaks deploys at the worst moment; and a decoder for STOPPED tasks, where exit code 137 and a two-word reason are the whole diagnosis. Prerequisites: EC2, EBS & Auto Scaling, VPCs, Subnets & Security Groups and IAM Advanced: STS, Roles & Trust. For Kubernetes itself — objects, scheduling, probes, RBAC — see the Kubernetes track; this lesson covers the AWS layer around it.

Part 1 — Orchestrator and Capacity Are Different Questions

Almost every confusing container discussion on AWS comes from collapsing two independent choices into one. Separate them and the options stop overlapping.

  QUESTION 1: what SCHEDULES my containers?      → ECS   or   EKS
  QUESTION 2: what RUNS them?                    → EC2   or   Fargate

  the four combinations are all real, and all in production somewhere:

     ECS on EC2      cheapest at high utilisation; you patch the nodes
     ECS on Fargate  simplest thing that works; no nodes at all
     EKS on EC2      full Kubernetes; DaemonSets, GPUs, custom kernels
     EKS on Fargate  Kubernetes API, no nodes — with real restrictions
ECSEKS
Control plane costFree$0.10/hr ≈ $73/month per cluster
APIAWS-proprietaryKubernetes — portable, huge ecosystem
Learning curveDaysMonths
IAM integrationNative (task roles)IRSA / Pod Identity — good, but a layer to configure
EcosystemAWS services onlyHelm, operators, service meshes, everything
Choose whenYou are all-in on AWS and want the smallest thing that worksYou need the ecosystem, portability, or already have Kubernetes skills
🔑 "Should we use Fargate instead of ECS?" is a malformed question, and hearing it is a reliable sign the model has not landed. Fargate is not an orchestrator — it does not schedule anything, has no API of its own, and cannot run a container without ECS or EKS telling it to. It replaces the EC2 instances, not the orchestrator. The correct question is "ECS or EKS?" and then, separately, "EC2 or Fargate?"
EC2 capacityFargate capacity
You manageAMIs, patching, scaling, bin-packingNothing
Billing unitThe instance, whether packed or notvCPU-seconds and GB-seconds you requested
StartupSeconds (node already warm)~30–60 s per task
DaemonSets / node agents✅❌ — sidecars only
Privileged, GPUs, instance store✅❌

🔑 The two errors tell you which role is wrong, precisely. If the task never reaches RUNNING and the stopped reason mentions pulling an image, reading a secret, or creating a log stream, it is the execution role. If the task is happily running and your code logs AccessDenied, it is the task role. People swap them, put the application's S3 permissions on the execution role, and then cannot understand why a policy that clearly grants s3:GetObject has no effect — the container is not using that role at all.
NETWORK MODE decides addressing, security groups, and density:

  awsvpc   each task gets its OWN ENI and VPC IP   ← the default and the right answer
           → per-task security groups, real IPs, works with ALB IP targets
           → BUT each task consumes an ENI slot on the instance (see Part 3)
  bridge   Docker bridge, dynamic host ports
           → dense, but security groups are per-INSTANCE, not per-task
  host     the container uses the host's network namespace
           → fastest, no port flexibility, one task per port per instance
  none     no external networking

$ aws ecs create-service --cluster shop --service-name checkout \
    --task-definition checkout:17 --desired-count 6 --launch-type FARGATE \
    --network-configuration 'awsvpcConfiguration={subnets=[subnet-0a,subnet-0b,subnet-0c],
        securityGroups=[sg-0checkout],assignPublicIp=DISABLED}' \
    --load-balancers 'targetGroupArn=arn:...:targetgroup/checkout/ab12,
        containerName=app,containerPort=8080' \
    --health-check-grace-period-seconds 120 \
    --deployment-configuration 'deploymentCircuitBreaker={enable=true,rollback=true},
        maximumPercent=200,minimumHealthyPercent=100'
💡 deploymentCircuitBreaker with rollback=true is the setting that turns a bad deploy into a non-event: ECS watches how many tasks fail to reach a steady state and, past a threshold, stops the deployment and rolls back to the previous task definition automatically. Without it a broken image will retry forever, slowly replacing every healthy task with a crash-looping one. It is off by default, and it costs nothing.

Part 3 — Fargate: The Menu, the Limits, and the Crossover

CPU AND MEMORY ARE A FIXED MENU, not arbitrary numbers:

$ aws ecs register-task-definition --cpu 1024 --memory 3000 ...
An error occurred (ClientException): No Fargate configuration exists for given values.

  0.25 vCPU →  0.5, 1, 2 GB
  0.5  vCPU →  1–4 GB      (1 GB steps)
  1    vCPU →  2–8 GB
  2    vCPU →  4–16 GB
  4    vCPU →  8–30 GB
  8    vCPU →  16–60 GB    (4 GB steps)
  16   vCPU →  32–120 GB   (8 GB steps)

  → you cannot ask for 1 vCPU and 12 GB. Memory drags vCPU up with it,
    which is exactly where Fargate gets expensive for memory-heavy work.
Fargate cannotWhy it matters
Run DaemonSets / per-node agentsLog and metric agents must be sidecars in every task — more cost, more config

    --ephemeral-storage sizeInGiB=100
   → 21–200 GiB. Billed at ~$0.000111 per GB-hour above the free 20 GB.

THE COST CROSSOVER — Fargate is not "more expensive", it is priced differently:

  Fargate     $0.04048 per vCPU-hour  +  $0.004445 per GB-hour
  m6i.large   $0.096/hr for 2 vCPU + 8 GB

  the same 2 vCPU + 8 GB on Fargate:
      2 × $0.04048  +  8 × $0.004445  =  $0.11652 / hour     ← 21% MORE, at 100% packing

  but nobody packs an instance to 100%. At real utilisation:

      utilisation   EC2 effective $/task-hour   Fargate $/task-hour   cheaper
        100%              $0.0960                   $0.1165            EC2
         80%              $0.1200                   $0.1165          Fargate
         61%              $0.1574                   $0.1165          Fargate
         40%              $0.2400                   $0.1165          Fargate  (by 2×)
🔑 The crossover in this example is 61% utilisation — and typical ECS clusters run well below that. The comparison people make ("Fargate costs 21% more per vCPU") assumes perfect bin-packing, no headroom for the largest task, no reserved capacity for scale-out, and no partially-empty node. Add the real numbers — plus the engineering time spent on AMIs, patching, draining and cluster autoscaling — and Fargate usually wins below large scale. It stops winning when utilisation is genuinely high and sustained, which is where Savings Plans and Spot on EC2 pull ahead (see Cost; Compute Savings Plans cover Fargate too).
FARGATE SPOT — up to 70% off, with a 2-minute SIGTERM, for interruptible work:
$ aws ecs put-cluster-capacity-providers --cluster shop \
    --capacity-providers FARGATE FARGATE_SPOT \
    --default-capacity-provider-strategy \
      capacityProvider=FARGATE,base=4,weight=1 \
      capacityProvider=FARGATE_SPOT,weight=4
   → a guaranteed on-demand base of 4 tasks, then 80% Spot above it.
     Handle SIGTERM and set stopTimeout, or interruptions become errors.

EKS runs the Kubernetes control plane for you. Everything interesting is in how it joins Kubernetes concepts to AWS ones — and each join is a place things break. For Kubernetes itself, see the Kubernetes track.

$ kubectl annotate serviceaccount checkout -n shop \
    eks.amazonaws.com/role-arn=arn:aws:iam::111122223333:role/checkoutRole
💡 EKS Pod Identity is the newer, simpler alternative — an association between a ServiceAccount and a role made through the EKS API, with no OIDC provider, no trust-policy editing and no per-cluster IAM plumbing. It does not work across accounts the way IRSA does, so IRSA remains the answer for cross-account access, but for the ordinary case Pod Identity removes the exact trust-policy mistake shown above by making it impossible to write.

NAME                        READY   STATUS    RESTARTS   AGE
checkout-6d4f9-x2k          1/1     Running   0          4h            ✅

Why this replaced the aws-auth ConfigMap: the old model stored the mapping inside the cluster, so a bad edit removed your own access and the only way to fix it was to authenticate as the cluster creator — an identity that is often a long-departed engineer's role or a CI principal nobody can assume. Access entries live in the EKS API, are IAM-controlled, and are auditable in CloudTrail. Migrate to API mode; keep API_AND_CONFIG_MAP only while migrating.

Part 5 — Images: ECR, Lifecycle, and the Rate Limit

UNTAGGED IMAGES ACCUMULATE FOREVER AND NOBODY LOOKS:

$ aws ecr describe-repositories --query 'repositories[].repositoryName' --output text | wc -w
64
$ aws ecr describe-images --repository-name checkout \
    --query 'length(imageDetails[?imageTags==null])'
2841                                               ← untagged layers from every CI build
$ aws ecr describe-repositories --repository-name checkout \
    --query 'repositories[0].repositoryUri' --output text >/dev/null
$ aws cloudwatch get-metric-statistics --namespace AWS/ECR --metric-name RepositoryPullCount ...
  storage across 64 repos: 4.2 TB × $0.10/GB-month  =  $430 / month of dead layers

✅ a lifecycle policy — write it once per repository, at creation:
$ aws ecr put-lifecycle-policy --repository-name checkout --lifecycle-policy-text '{
  "rules": [
    {"rulePriority":1,"description":"keep 10 tagged releases",
     "selection":{"tagStatus":"tagged","tagPrefixList":["v"],
                  "countType":"imageCountMoreThan","countNumber":10},
     "action":{"type":"expire"}},
    {"rulePriority":2,"description":"expire untagged after 7 days",
     "selection":{"tagStatus":"untagged","countType":"sinceImagePushed",
                  "countUnit":"days","countNumber":7},
     "action":{"type":"expire"}}]}'

$ aws ecr put-image-tag-mutability --repository-name checkout --image-tag-mutability IMMUTABLE
   → an existing tag can never be overwritten. "checkout:v2.1" means one thing, always.
⚠️ The Docker Hub rate limit breaks deploys at exactly the wrong time. Anonymous pulls are limited per IP address, and every task on a NAT Gateway shares one address — so a cluster scaling out during a traffic spike hits toomanyrequests: You have reached your pull rate limit and tasks fail to start while you are trying to add capacity. Use an ECR pull-through cache rule so upstream images are mirrored into ECR on first pull and served from there afterwards.
$ aws ecr create-pull-through-cache-rule --ecr-repository-prefix docker-hub \
    --upstream-registry-url registry-1.docker.io \
    --credential-arn arn:aws:secretsmanager:us-east-1:1111:secret:ecr-pullthroughcache/dockerhub

  then reference images through ECR instead of Docker Hub:
    image: 111122223333.dkr.ecr.us-east-1.amazonaws.com/docker-hub/library/nginx:1.27
   → first pull fetches upstream and caches; every later pull is ECR, in-Region,
     over a gateway endpoint, with no rate limit and no data transfer cost.

GET INSIDE A RUNNING TASK — no SSH, no bastion, and it works on Fargate:

$ aws ecs update-service --cluster shop --service checkout --enable-execute-command
$ aws ecs execute-command --cluster shop --task 9f2a --container app \
    --interactive --command "/bin/sh"
Starting session with SessionId: ecs-execute-command-0a1b
/app # cat /proc/meminfo | head -2
MemTotal:        2097152 kB
MemAvailable:      48120 kB                        ← 2 GB task, 48 MB left. There it is.
/app # java -XX:+PrintFlagsFinal -version | grep MaxHeapSize
   size_t MaxHeapSize   = 2147483648                ← a 2 GB heap in a 2 GB container.
🔑 That last pair of lines is the most common exit-137 in production containers: a JVM (or any runtime that sizes itself from the host) reading the container limit as its heap budget and leaving nothing for the JVM's own non-heap memory, the OS, or the sidecar. Set -XX:MaxRAMPercentage=75 rather than a fixed heap, and remember that ECS Exec needs three things: enableExecuteCommand on the service, ssmmessages:* permissions on the task role, and SSM connectivity — an interface endpoint if the task has no NAT route.

❌ Application permissions on the execution role, awsvpc tasks in a /24 with no density arithmetic, a Fargate decision made on the per-vCPU sticker price, an IRSA trust policy pinned only to the cluster issuer, images pulled from Docker Hub through a NAT Gateway, no ECR lifecycle policy, no deployment circuit breaker, and tasks that die with exit 137 and no explanation. The S3 policy is attached to ecsTaskExecutionRole, so the container that actually needs it is not using that role at all and a policy that plainly grants access has no effect. Tasks each take a VPC address and an ENI slot, so the cluster stops scheduling at three tasks per m5.large with the CPU nearly idle, and the error mentions network namespaces rather than addresses. Someone compared $0.11652 against $0.096 and concluded Fargate costs 21% more, without noticing the cluster runs at 40% utilisation where it is half the price. The IRSA trust policy checks only the cluster issuer, so every ServiceAccount in every namespace can assume a role scoped to one service. Deploys pull upstream images through a shared NAT address and fail with toomanyrequests precisely when scaling out under load. Untagged layers accumulate to 4.2 TB and $430 a month that nobody has ever looked at. A broken image rolls forward indefinitely because the circuit breaker is off by default. And exit code 137 gets logged as "the task crashed" when it means the kernel killed it for memory.

✅ Split the roles by who uses them, do the density arithmetic, compare Fargate at your real utilisation, pin the IRSA subject, cache upstream images in ECR, expire what you do not keep, turn the circuit breaker on, and learn the decoder table. The execution role belongs to the ECS agent and needs only ECR, logs and secrets access; the task role belongs to your code and should be least-privilege per service — the two failures look completely different, and knowing which you have is the diagnosis. Size subnets for awsvpc tasks the way you would for pods, since each one holds a real address (see VPCs). Compute the Fargate crossover from measured utilisation rather than from list prices, and remember Compute Savings Plans cover Fargate. Pin the IRSA sub claim to system:serviceaccount:namespace:name, or move to EKS Pod Identity where the mistake cannot be written. Create an ECR pull-through cache rule so a deploy never depends on Docker Hub's rate limit. Attach a lifecycle policy at repository creation and make tags immutable. Enable deploymentCircuitBreaker with rollback, which is free and turns a bad image into a non-event. And treat stoppedReason plus the exit code as structured data: 137 is OOM, 139 is a segfault, and a JVM sizing its heap to the whole container limit is the usual cause of the first.

Interview Questions

Beginner: What is the difference between ECS, EKS and Fargate?

ECS and EKS are orchestrators; Fargate is a capacity provider. ECS is AWS's own container scheduler with a proprietary API and a free control plane. EKS is managed Kubernetes, costing about $73 a month per cluster and bringing the whole Kubernetes ecosystem with it. Fargate is neither — it is a way of running tasks or pods without managing EC2 instances, and it works underneath both.

So the choices are independent. You pick ECS or EKS based on whether you want the Kubernetes ecosystem and portability or the simplest thing that works on AWS. Then, separately, you pick EC2 or Fargate based on whether you want to manage nodes — and all four combinations are used in production.

The tell that someone has the model wrong is the phrase "we migrated from ECS to Fargate", which describes a change of capacity provider, not of orchestrator.

Beginner: Explain the ECS task role versus the execution role.
Execution roleTask role
Assumed byThe ECS agent, before your container runsYour application code, at runtime
Typical permissionsECR pull, CloudWatch Logs, Secrets Manager / SSMS3, DynamoDB, SQS — whatever the app calls
ScopeUsually one shared role per accountOne per service, least-privilege

The practical value is diagnostic: the failure tells you which role to look at. A task stuck before RUNNING, with a stopped reason about pulling an image or reading a secret, is the execution role. A healthy task logging AccessDenied is the task role. The classic confusion is putting the application's S3 permissions on the execution role and then being unable to explain why an obviously correct policy does nothing — the container is not using that role.

Mid: An ECS service will not scale past a few tasks per instance even though CPU and memory are nearly idle. Why?

awsvpc network mode gives every task its own ENI, and ENIs per instance are a hard limit of the instance type — nothing to do with CPU or memory.

$ aws ec2 describe-instance-types --instance-types m5.large \
    --query 'InstanceTypes[0].NetworkInfo.[MaximumNetworkInterfaces,Ipv4AddressesPerInterface]' --output text
3   10
   → 3 ENIs, one used by the host → 2 tasks. (3 with ENI trunking off/on varies by type.)

$ aws ecs describe-tasks ... --query 'tasks[0].stoppedReason'
"ResourceInitializationError: unable to create new network namespace"
FixEffectCost
ENI trunking (awsvpcTrunking account setting)Many more task ENIs per instance — e.g. m5.large 2 → 10Requires supported instance types; opt-in per account
Larger instancesMore ENIs per nodeCoarser failure domains, worse bin-packing
bridge network modeNo per-task ENI at allLoses per-task security groups
FargateDensity stops being your problemPer-task pricing

The general lesson, and it is the same one as EKS pod density: on AWS, container density is usually an addressing limit before it is a resource limit. Check ENI and subnet capacity before adding nodes — adding nodes consumes more addresses and can make it worse.

Mid: Is Fargate more expensive than EC2? Answer properly.

Per unit of provisioned capacity, yes — about 21% more. Per unit of useful capacity, usually no. The list-price comparison assumes you pack instances perfectly, which nobody does.

  2 vCPU + 8 GB:  m6i.large $0.0960/hr   vs   Fargate $0.11652/hr

  but EC2 bills the whole instance regardless of packing:
     utilisation   EC2 $/task-hour   Fargate $/task-hour
        100%          $0.0960            $0.1165          ← EC2 wins
         61%          $0.1574            $0.1165          ← crossover
         40%          $0.2400            $0.1165          ← Fargate half the price

And the EC2 column is optimistic, because it ignores headroom reserved for the largest task, capacity kept free for scale-out, partially-drained nodes during deploys, and the engineering time spent on AMIs, patching and cluster autoscaling.

Where EC2 genuinely wins: sustained high utilisation, large scale, GPUs, DaemonSet-heavy observability stacks, and workloads that benefit from Spot at up to 90% off. Note that Compute Savings Plans cover Fargate too, so committing does not force you back onto EC2 — and Fargate Spot exists at roughly 70% off for interruptible work. The honest answer is "measure your utilisation, then compute the crossover", and the number is usually lower than people expect.

Senior: A team of forty is choosing between ECS and EKS for a new platform. How do you run that decision?

The decision is about the organisation, not the technology — both will run containers reliably, and arguing about features misses what actually determines the outcome.

Choose ECS whenChoose EKS when
The team is small or has no Kubernetes experienceYou already have Kubernetes skills, or will hire for them
You are committed to AWS and value simplicityPortability or multi-cloud is a genuine requirement
The workload is plain services behind load balancersYou need operators, Helm charts, a service mesh, or GPU scheduling
You want the smallest operational surfaceYou will invest in a platform team

The question I would actually ask: is there going to be a platform team? EKS without one distributes Kubernetes' operational burden across forty application engineers who each learn a quarter of it — upgrades, CNI behaviour, admission controllers, RBAC — and that is where the cost appears, not in the $73 a month. ECS with no platform team is genuinely fine; EKS with no platform team is a slow accumulation of things nobody owns.

What I would push back on: "portability" as a stated reason, unless someone can name the second target and the date. Kubernetes manifests are portable; the load balancer controller, storage classes, IRSA, and every IAM integration are not. Teams pay the Kubernetes complexity tax for a portability they never exercise — that is the most common version of this decision going wrong.

What I would insist on either way: capacity decided separately (start on Fargate, move hot services to EC2 when utilisation justifies it), one image registry with lifecycle policies and immutable tags, per-service least-privilege roles from day one, and a deployment mechanism with automatic rollback. Those matter more to the platform's success than which orchestrator won.

Senior: Tasks are being killed with exit code 137 in production but never in staging. Walk through it.

137 is 128 + 9: SIGKILL. Nothing in the container chose to exit — the kernel's OOM killer or the container runtime terminated it for exceeding its memory limit. So the question is not "what crashed" but "what used more memory here than there".

Confirm the mechanism first, since 137 can occasionally come from other forced kills:

$ aws ecs describe-tasks --cluster shop --tasks 9f2a \
    --query 'tasks[0].containers[0].[exitCode,reason]' --output text
137   OutOfMemoryError: Container killed due to memory usage

Then look for the difference, which is almost always one of four things: production has more concurrent requests and therefore more live objects; the task definition's memory differs between environments; a runtime is sizing itself from the container limit; or a sidecar is consuming part of the budget that the application assumes it owns.

$ aws ecs execute-command --cluster shop --task 9f2a --container app \
    --interactive --command "java -XX:+PrintFlagsFinal -version" | grep MaxHeapSize
   size_t MaxHeapSize = 2147483648                 ← a 2 GB heap in a 2 GB task

That is the usual answer, and it is a footgun rather than a bug: the JVM reads the cgroup limit and claims it all for the heap, leaving nothing for metaspace, thread stacks, native buffers, the JVM itself, or the log sidecar. It survives staging because staging never fills the heap. Fix it with -XX:MaxRAMPercentage=75 rather than a fixed -Xmx, so it scales with the task size instead of needing to be re-tuned every time.

Then close the observability gap, because the real problem is that this was discovered by tasks dying. ECS container-level memory utilisation is in Container Insights, not in the default metrics; alarm on it approaching the limit rather than on task restarts. And make staging representative in the dimension that matters — same task memory, same sidecars, and a load test with production-like concurrency. A staging environment that differs in memory shape cannot catch memory bugs, which is worth saying out loud since "it works in staging" was the evidence that delayed this.

🔑 The absence of an OutOfMemoryError in the application log is evidence, not a dead end. A JVM that exhausts its heap logs loudly and often produces a heap dump; a JVM killed by the kernel for exceeding a cgroup limit logs nothing at all, because the process is terminated with SIGKILL and never runs another instruction. 🎯 Key Takeaways

  • ECS and EKS are orchestrators; Fargate is a capacity provider. "ECS or Fargate?" is a category error — the questions are orchestrator, then capacity, and all four combinations are real.
  • ECS has a free control plane and an AWS-native API; EKS costs ~$73/month per cluster and brings the Kubernetes ecosystem, portability, and a much larger operational surface.
  • Execution role = the ECS agent (pull image, write logs, read secrets); task role = your code. The container credential endpoint serves only the task role, which is why app permissions on the execution role can never work.
  • The two roles fail differently, and that is the diagnosis: never reaching RUNNING is the execution role; running and logging AccessDenied is the task role.
  • awsvpc gives every task an ENI — an m5.large ran 2 tasks with 45% of its CPU idle, failing with insufficient ENI capacity.
  • ENI trunking took density from 2 to 10 tasks per instance for free — but it applies only to newly-registered instances, and then the subnet becomes the next ceiling.
  • On AWS, container density is an addressing limit before it is a resource limit — the same arithmetic as EKS pod density, and adding nodes consumes more addresses.
  • Fargate's CPU/memory pairs are a fixed menu; 12 GB forces 2 vCPU, so memory-heavy CPU-light workloads waste ~$30/month per task and belong on r-family EC2.
  • Fargate's "21% more expensive" assumes perfect bin-packing. The crossover is around 61% utilisation, and a real cluster measured at 17% used made Fargate 55% cheaper.
  • Right-size task reservations before choosing a platform — tasks reserving 7,168 CPU units and using 2,842 is the highest-leverage fix, and it may reverse the decision.
  • Fargate cannot run DaemonSets, privileged containers, GPUs or instance store, defaults to 20 GB ephemeral storage, and takes ~30–60 s per task launch.
  • Compute Savings Plans cover Fargate, and Fargate Spot is ~70% off — committing does not force you back to EC2.
  • An IRSA trust policy pinned only to the cluster issuer lets every ServiceAccount in every namespace assume the role — pin sub, or use EKS Pod Identity where the mistake cannot be written.
  • EKS access entries replaced the aws-auth ConfigMap: IAM-controlled, CloudTrail-audited, and they cannot lock you out the way a YAML typo could.
  • When migrating to authenticationMode=API, recreate the node group's role as an EC2_LINUX access entry first — the switch is one-way and otherwise every node goes NotReady.
  • Authentication and authorisation fail differently in EKS: kubectl auth whoami showing a valid ARN with only system:authenticated means EKS knows you and Kubernetes does not.
  • A Service stuck at <pending> is usually untagged subnets — kubernetes.io/role/elb and /internal-elb — with the reason only in the controller's logs.
  • Docker Hub's per-IP rate limit fails deploys exactly when scaling out, because tasks share a NAT address. Use ECR pull-through cache rules.
  • Without a lifecycle policy, untagged layers reach thousands of images and hundreds of dollars a month; set one at repository creation and make tags immutable.
  • deploymentCircuitBreaker with rollback=true is free and off by default — without it a broken image replaces every healthy task, forever.
  • Exit 137 is SIGKILL for memory, and the absence of an OutOfMemoryError in the log is the signature: a JVM sizing its heap to the whole container limit is the usual cause. Use -XX:MaxRAMPercentage=75.
  • ECS Exec works on Fargate and needs three things: enableExecuteCommand, ssmmessages:* on the task role, and SSM connectivity.
