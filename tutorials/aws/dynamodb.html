DynamoDB Data

What you'll master: the inversion that makes DynamoDB work — you design the table around the queries, not the entities, and getting that backwards produces a system that scans; capacity arithmetic in RCUs and WCUs, and the on-demand break-even at ~14% utilisation; the failure mode that defines the service — a table provisioned at 40,000 WCU throttling while consuming 4% of it, because per-partition limits are 1,000 WCU and one key is hot; why FilterExpression on a Scan saves you nothing — you pay for every item read and then discarded; LSIs versus GSIs, including the trap where a throttled GSI throttles writes to the base table; single-table design, what it is actually for, and when it is the wrong answer; conditional writes as the only defence against the lost update that concurrency will find; and the operational layer — Streams, TTL, global tables and DAX. Prerequisites: RDS & Aurora, Cost and Lambda.

Part 1 — A Partitioned, Sorted Table

DynamoDB is often described as a key-value store, which undersells it and leads people to model it badly. It is a partitioned, sorted table: the partition key decides which machine, and the sort key decides the order within that machine. Every capability and every limit falls out of those two sentences.

    PK = "CUSTOMER#42"          ← hashed → chooses a partition (a physical shard)
    SK = "ORDER#2026-08-20#001" ← sorted within that partition

    a Query says: "give me the items in ONE partition, in sort-key order,
                   optionally a range of them"
    → which is why Query is fast and cheap, and why it REQUIRES the partition key.
ConceptRealityConsequence
Partition keyHashed to choose a shardNo key = no Query. You can only Scan.
Sort keyOrdered within a partitionRanges, prefixes, "most recent N" are cheap
ItemMax 400 KBLarge blobs go in S3 with a pointer here
SchemaOnly the key attributes are fixedDifferent item types can share a table
Partition~10 GB, 3,000 RCU, 1,000 WCUThe limit that causes most incidents — Part 3
🔑 Relational modelling starts from entities and discovers queries later; DynamoDB modelling starts from the queries and derives the keys. Write down every access pattern first — "get a customer's 20 most recent orders", "find all orders in status X for today" — and then choose keys that answer each one with a single Query. If you find yourself writing a Scan in normal operation, the model is wrong, not the query.
$ aws dynamodb create-table --table-name Orders \
    --attribute-definitions AttributeName=PK,AttributeType=S AttributeName=SK,AttributeType=S \
    --key-schema AttributeName=PK,KeyType=HASH AttributeName=SK,KeyType=RANGE \
    --billing-mode PAY_PER_REQUEST

$ aws dynamodb query --table-name Orders \
    --key-condition-expression 'PK = :c AND begins_with(SK, :p)' \
    --expression-attribute-values '{":c":{"S":"CUSTOMER#42"},":p":{"S":"ORDER#2026-08"}}' \
    --scan-index-forward false --limit 20 \
    --return-consumed-capacity TOTAL \
    --query '[Count,ConsumedCapacity.CapacityUnits]' --output text
20   2.5                                           ← 20 items, 2.5 RCU. One partition.

Part 2 — Capacity Arithmetic

  1 WCU  = one write per second of up to 1 KB      (round UP)
  1 RCU  = one STRONGLY consistent read per second of up to 4 KB
         = two EVENTUALLY consistent reads per second of up to 4 KB
  transactional operations cost DOUBLE.

  a 6.5 KB item:
      write   ceil(6.5 / 1) = 7 WCU
      read    ceil(6.5 / 4) = 2 RCU strong,  1 RCU eventual
      transactional write   = 14 WCU

NEVER GUESS — ask the API what it charged you:
$ aws dynamodb put-item --table-name Orders --item file://item.json \
    --return-consumed-capacity TOTAL --query 'ConsumedCapacity.CapacityUnits' --output text
7.0

$ aws dynamodb get-item --table-name Orders \
    --key '{"PK":{"S":"CUSTOMER#42"},"SK":{"S":"ORDER#001"}}' \
    --consistent-read --return-consumed-capacity TOTAL \
    --query 'ConsumedCapacity.CapacityUnits' --output text
2.0
$ aws dynamodb get-item --table-name Orders \
    --key '{"PK":{"S":"CUSTOMER#42"},"SK":{"S":"ORDER#001"}}' \
    --return-consumed-capacity TOTAL --query 'ConsumedCapacity.CapacityUnits' --output text

Part 3 — Hot Partitions: The Failure Mode That Defines DynamoDB

Table-level capacity is spread across partitions. A single item, or a single partition key, can only ever get one partition's worth of throughput — and that is the number people never plan for.

    PER PARTITION, HARD:      3,000 RCU     1,000 WCU     ~10 GB

    a table provisioned at 40,000 WCU spread over 40 partitions gives 1,000 WCU each.
    if 95% of writes go to ONE partition key:

$ aws cloudwatch get-metric-statistics --namespace AWS/DynamoDB \
    --metric-name ConsumedWriteCapacityUnits --dimensions Name=TableName,Value=Events \
    --period 60 --statistics Sum --start-time $(date -u -d '10 min ago' +%FT%TZ) \
    --end-time $(date -u +%FT%TZ) --query 'max(Datapoints[].Sum)' --output text
96420.0                                            ← 1,607 WCU/s of 40,000 = 4%

$ aws cloudwatch get-metric-statistics --namespace AWS/DynamoDB \
    --metric-name ThrottledRequests --dimensions Name=TableName,Value=Events \
    --period 60 --statistics Sum ... --query 'sum(Datapoints[].Sum)' --output text
184022.0                                           ← 184,022 throttles
⚠️ 4% consumed and throttling hard is the signature of a hot partition, and it is genuinely confusing the first time: every table-level metric says there is spare capacity, because there is — just not where the traffic is going. Adding capacity does not help; it adds partitions the traffic will not use. The fix is always the key.
FIND THE HOT KEY — CloudWatch Contributor Insights, not guesswork:
$ aws dynamodb update-contributor-insights --table-name Events \
    --contributor-insights-action ENABLE
$ aws cloudwatch get-insight-rule-report \
    --rule-name 'DynamoDBContributorInsights-PKC-Events' \
    --start-time $(date -u -d '1 hour ago' +%FT%TZ) --end-time $(date -u +%FT%TZ) \
    --period 3600 --max-contributor-count 3 \
    --query 'Contributors[].[Keys[0],ApproximateAggregateValue]' --output text
TENANT#acme      8412004                           ← 95% of writes, one key
TENANT#globex     201884
TENANT#initech    188402

✅ WRITE SHARDING — spread one logical key across N physical partitions:

  ❌ PK = "TENANT#acme"                     → one partition, 1,000 WCU ceiling
  ✅ PK = "TENANT#acme#" + str(random(0,19)) → 20 partitions, 20,000 WCU ceiling

  writing:
      shard = random.randint(0, 19)
      put_item(PK=f"TENANT#acme#{shard}", SK=f"EVT#{ts}#{uuid}")

  reading "all events for acme" now needs 20 queries, run in parallel:
      results = await gather(*[query(PK=f"TENANT#acme#{s}") for s in range(20)])
Sharding strategyRead costUse when
Random suffix (0–N)N queries, merged client-sideWrites dominate; reads are rare or batched
Calculated suffix (hash(id) % N)1 query if you know the idYou can derive the shard at read time — preferred
Time-based suffix (#2026-08-20-13)1 query per time bucketTime-series data
Better natural key1 queryAlways try this first
💡 Adaptive capacity mitigates this but does not remove it. DynamoDB automatically shifts unused table capacity toward a hot partition, and does so within seconds — which is why moderate skew often never surfaces. But it can never exceed the hard per-partition ceiling of 1,000 WCU / 3,000 RCU, so a genuinely hot key still throttles. Treat adaptive capacity as headroom for imperfect distribution, not as a licence to design a hot key.

Part 4 — Query, Scan, and the Indexes

THE MOST EXPENSIVE MISCONCEPTION IN DYNAMODB:

  FilterExpression is applied AFTER the items are read.
  You pay full capacity for every item examined and then discarded.

$ aws dynamodb scan --table-name Orders \
    --filter-expression '#s = :st' \
    --expression-attribute-names '{"#s":"status"}' \
    --expression-attribute-values '{":st":{"S":"REFUNDED"}}' \
    --return-consumed-capacity TOTAL \
    --query '[Count,ScannedCount,ConsumedCapacity.CapacityUnits]' --output text
12   482104   60263.0
     │  │        └─ 60,263 RCU consumed
     │  └─ 482,104 items READ
     └─ 12 items returned
   → you paid to read half a million items to return twelve.
QueryScan
RequiresThe partition keyNothing
ReadsOnly the matching partitionThe entire table
CostProportional to resultsProportional to table size
Scales as data grows✅ constant❌ linearly worse forever
Acceptable forEverythingMigrations, one-off exports, tiny tables
INDEXES — the two kinds, and they are not interchangeable:

  LSI  Local Secondary Index
       SAME partition key, DIFFERENT sort key
       ⚠️ can ONLY be created WITH the table — never added later
       ✅ supports strongly consistent reads
       ⚠️ 10 GB limit per partition key value, for the table + all its LSIs

  GSI  Global Secondary Index
       ANY partition key and sort key
       ✅ can be added or removed at any time
       ⚠️ EVENTUALLY consistent only
       ⚠️ its OWN capacity — and see the trap below

$ aws dynamodb update-table --table-name Orders \
    --attribute-definitions AttributeName=status,AttributeType=S \
                            AttributeName=createdAt,AttributeType=S \
    --global-secondary-index-updates '[{"Create":{
        "IndexName":"status-createdAt-index",
        "KeySchema":[{"AttributeName":"status","KeyType":"HASH"},
                     {"AttributeName":"createdAt","KeyType":"RANGE"}],
        "Projection":{"ProjectionType":"INCLUDE",
                      "NonKeyAttributes":["customerId","total"]}}}]'

$ aws dynamodb query --table-name Orders --index-name status-createdAt-index \
    --key-condition-expression '#s = :st AND #c > :d' \
    --expression-attribute-names '{"#s":"status","#c":"createdAt"}' \
    --expression-attribute-values '{":st":{"S":"REFUNDED"},":d":{"S":"2026-08-01"}}' \
    --return-consumed-capacity TOTAL \
    --query '[Count,ScannedCount,ConsumedCapacity.CapacityUnits]' --output text
12   12   1.5                                      ← 60,263 RCU → 1.5 RCU
⚠️ A throttled GSI throttles writes to the base table. Every write to the table must also be written to each GSI whose keys it contains; if the GSI has insufficient capacity, the write cannot complete and DynamoDB rejects it at the table. So an under-provisioned index — often one nobody reads any more — takes down writes to the table itself. Provision GSIs for the write rate of the base table, not for how often you query them, and delete indexes you have stopped using.
Projection typeStoresCostNote
KEYS_ONLYKeys onlyCheapestRequires a second read to fetch attributes
INCLUDEKeys + named attributesMiddleUsually correct — project what the query returns
ALLEverythingDoubles storage and write costConvenient, and the default people regret
SPARSE INDEXES — a GSI only contains items that HAVE its key attributes:

  items with  needsReview = "Y"   → appear in the index
  items without that attribute    → do NOT appear at all

  → an index over 400 pending items on a 500 M-item table, costing almost nothing.
    Delete the attribute when the work is done and the item leaves the index.

Part 5 — Modelling, and Writing Safely

SINGLE-TABLE DESIGN — one table, many item types, keys overloaded:

  PK                SK                        type      attributes
  CUSTOMER#42       PROFILE                   customer  name, email
  CUSTOMER#42       ORDER#2026-08-20#001      order     total, status
  CUSTOMER#42       ORDER#2026-08-19#004      order     total, status
  CUSTOMER#42       ADDRESS#home              address   line1, city
  ORDER#001         ITEM#sku-9f2a             lineitem  qty, price

  Query(PK="CUSTOMER#42")                        → the customer AND everything about them,
                                                   in ONE request, ONE partition
  Query(PK="CUSTOMER#42", SK begins_with "ORDER#") → just the orders, newest first
🔑 Single-table design is a technique for known access patterns at scale, not a universal best practice. It exists because a Query against one partition is the cheapest, fastest operation DynamoDB offers, and co-locating related items lets one request replace several. It costs you readability, ad-hoc queryability, and the ability to change access patterns cheaply. Use it when the patterns are stable and the scale is real; use separate tables when you are still discovering the domain, because a wrong single-table model is far more expensive to change than a wrong set of tables.
CONDITIONAL WRITES — the only defence against a lost update:

  ❌ read-modify-write, two clients, no condition:
     A: GET stock → 10        B: GET stock → 10
     A: PUT stock = 9         B: PUT stock = 9
     → two items sold, stock decremented once. Money lost, silently.

  ✅ atomic, server-side:
$ aws dynamodb update-item --table-name Inventory \
    --key '{"PK":{"S":"SKU#9f2a"}}' \
    --update-expression 'SET stock = stock - :one' \
    --condition-expression 'stock >= :one' \
    --expression-attribute-values '{":one":{"N":"1"}}'
An error occurred (ConditionalCheckFailedException)   ← when stock is 0. Correct.

OPTIMISTIC CONCURRENCY with a version attribute:
$ aws dynamodb update-item --table-name Orders \
    --key '{"PK":{"S":"ORDER#001"},"SK":{"S":"META"}}' \
    --update-expression 'SET #s = :new, version = :v1' \
    --condition-expression 'version = :v0' \
    --expression-attribute-names '{"#s":"status"}' \
    --expression-attribute-values '{":new":{"S":"SHIPPED"},":v0":{"N":"7"},":v1":{"N":"8"}}'
   → the write succeeds only if nobody else changed the item since you read it.
     On ConditionalCheckFailedException: re-read and retry.

TRANSACTIONS — for the cases a condition cannot cover:
$ aws dynamodb transact-write-items --transact-items '[
    {"Update":{"TableName":"Inventory","Key":{"PK":{"S":"SKU#9f2a"}},
      "UpdateExpression":"SET stock = stock - :one",
      "ConditionExpression":"stock >= :one",
      "ExpressionAttributeValues":{":one":{"N":"1"}}}},
    {"Put":{"TableName":"Orders","Item":{"PK":{"S":"ORDER#002"},"SK":{"S":"META"}},
      "ConditionExpression":"attribute_not_exists(PK)"}}]'
   ⚠️ all-or-nothing across up to 100 items, and it costs DOUBLE the capacity.
     Use a single conditional write where one suffices; transactions are for
     genuinely multi-item invariants.

TTL — the free delete, and the trap:
$ aws dynamodb update-time-to-live --table-name Sessions \
    --time-to-live-specification 'Enabled=true,AttributeName=expiresAt'
   the attribute must be a NUMBER, in epoch SECONDS. A millisecond timestamp
   means the item expires in the year 57000, silently.

  ⚠️ deletion happens within ~48 hours, not at the instant. So:
$ aws dynamodb query --table-name Sessions \
    --key-condition-expression 'PK = :u' \
    --filter-expression 'expiresAt > :now' \
    --expression-attribute-values '{":u":{"S":"USER#42"},":now":{"N":"1755700000"}}'
   → always filter on expiry in the read path too. TTL is a cost optimisation,
     not a correctness mechanism.

EXPORT TO S3 instead of scanning for analytics:
$ aws dynamodb export-table-to-point-in-time \
    --table-arn arn:aws:dynamodb:us-east-1:111122223333:table/Orders \
    --s3-bucket acme-exports --export-format DYNAMODB_JSON
   → 500 M items exported, ZERO read capacity consumed, no impact on production.
     Then query it in Athena. A full Scan would have cost 60,000+ RCU and hours.

❌ A table modelled from entities, Scans with filters in the request path, one tenant as a partition key, a GSI projecting ALL with a fraction of the base table's write capacity, read-modify-write with no condition, TTL trusted for correctness, and a nightly Scan for reporting. The table was designed like a relational schema, so the common access patterns have no matching key and every one is a Scan with a FilterExpression — reading 482,104 items to return 12 and consuming 60,263 RCU each time. The biggest customer is a single partition key, so the table throttles 184,000 requests while consuming 4% of its provisioned capacity, and someone keeps raising the capacity because every table-level metric shows headroom. A GSI projects every attribute and is provisioned for how often it is queried rather than how often the base table is written, so it throttles and takes the table's writes down with it. Inventory is decremented by reading, subtracting and writing, so under concurrency two orders sell the same unit and the discrepancy is discovered at stock-take. Sessions are read without checking expiry because TTL "deletes them", and expired sessions remain valid for up to two days. And the reporting job Scans the whole table every night, doubling the capacity bill to answer questions Athena could answer for free.

✅ Model from the access patterns, Query never Scan, distribute the partition key, provision GSIs for the write rate, make every mutation conditional, filter on expiry anyway, and export instead of scanning. Write the access patterns down before the schema and choose keys so each one is a single Query; a Scan in the request path means the model is wrong, not the query. Find hot keys with Contributor Insights rather than guessing, and shard them — a calculated suffix if you can derive it at read time, a random one if writes dominate — remembering that adaptive capacity smooths imperfect distribution but can never exceed 1,000 WCU on one partition. Project INCLUDE with the attributes the query returns rather than ALL, provision each GSI for the base table's write rate, and delete indexes nobody reads, because an unused index can still stop your writes. Replace every read-modify-write with a condition-expression or an atomic SET x = x - :n, and use transactions only for genuine multi-item invariants since they cost double. Treat TTL as a cost optimisation and filter expired items in the read path. And export to S3 for analytics — full table exports consume no capacity at all and leave production untouched.

Interview Questions

Beginner: What is the difference between a Query and a Scan?

A Query reads one partition; a Scan reads the entire table. A Query requires the partition key, optionally narrows by a sort-key condition, and costs in proportion to what it returns. A Scan requires nothing, reads every item, and costs in proportion to the table's size — so it gets worse forever as the data grows.

The point most people miss is that FilterExpression does not make a Scan cheap. Filters are applied after items are read, so you pay full capacity for everything examined and then discarded:

Count: 12    ScannedCount: 482,104    ConsumedCapacity: 60,263 RCU

Twelve results, half a million items paid for. The fix is a GSI whose partition key is the attribute you were filtering on, which turned that same query into 1.5 RCU. Scans are legitimate for migrations, one-off exports and genuinely tiny tables; a Scan in the request path means the data model does not support the access pattern.

Beginner: How do you choose between on-demand and provisioned capacity?

By sustained utilisation, and the break-even is about 14%.

  1 WCU for a month = 2,628,000 writes
  provisioned  $0.00065 × 730          = $0.4745
  on-demand    2.628 M × $1.25 / M     = $3.2850      → 6.92× more
  → on-demand wins below ~14% utilisation; provisioned is up to 7× cheaper above it
Choose on-demandChoose provisioned
New table, unknown patternSteady, predictable baseline
Spiky or unpredictable trafficSustained above ~14% utilisation
Development and testProduction at scale

The answer for most production workloads is both: provisioned at the floor with auto scaling for the peaks. Start on-demand until you have a month of data — committing before measuring is how tables end up either throttling or paying seven times over. And note that neither choice protects you from a hot partition: capacity mode is about cost, not about distribution.

Mid: A table is throttling while CloudWatch shows it consuming 4% of provisioned capacity. Explain.

A hot partition. Table capacity is spread across partitions, and each partition has a hard ceiling of 1,000 WCU and 3,000 RCU regardless of what the table is provisioned for. If most traffic targets one partition key, that key hits its ceiling while the other partitions sit idle — so the table-level metrics honestly report spare capacity that the traffic cannot reach.

Adding capacity makes it worse, not better: it creates more partitions the traffic will not use, and increases the bill. This is the moment to stop scaling and start looking at keys.

$ aws cloudwatch get-insight-rule-report --rule-name 'DynamoDBContributorInsights-PKC-Events' ...

On adaptive capacity: DynamoDB does shift unused capacity toward hot partitions within seconds, which is why mild skew rarely surfaces — but it cannot exceed the per-partition ceiling. It buys tolerance for imperfect distribution, not permission to design a hot key.

Mid: Writes to a table start failing after you add a GSI. Why?

Because every write to the base table must also be written to each GSI whose key attributes it contains — and if the GSI cannot accept the write, DynamoDB rejects it at the table. An under-provisioned index therefore takes down writes to the table itself, which is counter-intuitive because the index is usually thought of as a read-side concern.

CauseFix
GSI provisioned for query rate, not write rateProvision it for the base table's write rate
GSI partition key is hot (e.g. status)The same hot-partition problem, one level down — pick a distributed key
Projection ALL on large itemsINCLUDE only what the query returns

Two things worth adding. A GSI with a low-cardinality partition key — status with five values, say — concentrates all writes onto five partitions and will throttle no matter how much capacity it has. And an index nobody reads still costs every write and can still throttle you, so deleting unused indexes is a real availability improvement, not just a cost one.

Senior: When is single-table design the right choice, and when is it not?

It is a technique for known access patterns at scale, not a default. The reason it exists is that a Query against one partition is the cheapest and fastest operation DynamoDB offers, so co-locating related items under one partition key lets a single request replace what would otherwise be several — a customer, their orders and their addresses in one round trip, one partition, a few RCU.

Use it whenDo not when
Access patterns are known and stableYou are still discovering the domain
You need related items in one requestEntities are genuinely independent
Scale makes the round trips matterScale is modest and clarity matters more
The team understands the patternThe team will maintain it without that context
Analytics happens elsewhere (S3/Athena)You need ad-hoc queries against live data

The costs are real and usually understated: the table is unreadable without the access pattern documentation, every new pattern may need a new GSI or a migration, ad-hoc investigation is painful, and onboarding is slow. Most importantly, a wrong single-table model is far more expensive to change than a wrong set of tables, because the keys encode the access patterns and changing keys means rewriting every item.

What I would actually advise: start with separate tables while the domain is uncertain — DynamoDB tables are free when idle and on-demand billing makes many small tables cheap — and consolidate deliberately when patterns stabilise and round trips are measurably hurting. Treat single-table design as an optimisation you earn the right to, not a purity test. And whichever you choose, write the access patterns down as documentation that lives with the code; that artefact is what makes either model maintainable.

Senior: Design the data model for a multi-tenant SaaS event store: 50k writes/sec, per-tenant queries by time range, and a 90-day retention policy.

Three requirements, and each one pins a different part of the key design.

The write rate forces sharding. 50,000 writes/sec against a 1,000 WCU per-partition ceiling means at least 50 partitions actively receiving writes, and tenants are never evenly sized — one large customer will be most of the traffic. So the partition key must combine tenant, a time bucket, and a shard:

  PK = TENANT#<id>#<yyyy-mm-dd-hh>#<shard 0..N>
  SK = <timestamp>#<event-id>

  N sized per tenant: large tenants get 32 shards, small ones get 1.
  Store N per tenant in a config item so readers know how many to fan out to.

The query pattern is satisfied by the time bucket in the key. "Events for tenant X between two times" becomes a bounded fan-out: one Query per (hour × shard) in range, run in parallel, merged client-side. That is a known, bounded cost rather than a Scan. The sort key gives ordering within each partition for free.

Retention is where the design earns its keep. TTL is the obvious answer, and it is the wrong primary one at this volume: TTL deletes are free but arrive up to 48 hours late, and at 50k/sec the deletion backlog itself becomes significant. The better pattern is a table per time period — a monthly or weekly table — because dropping a table is instant, free and consumes no capacity, whereas expiring billions of items individually does not. Keep TTL as a secondary safety net for stragglers.

What I would flag explicitly: shard counts must be adjustable per tenant without a migration, because tenant sizes change and today's small customer is next year's hot partition. Storing the count as data rather than a constant is the difference between a config change and a rewrite. And analytics must go to S3 via Streams from day one — the moment someone Scans this table for a report, the production workload suffers and the capacity bill doubles.

✅ FIX 1 — ATOMIC UPDATE WITH A CONDITION. No read at all:
$ cat > atomic.py <<'PY'
import boto3, concurrent.futures as cf
d = boto3.client("dynamodb")
def sell(_):
    try:
        d.update_item(TableName="Inventory", Key={"PK":{"S":"SKU#9f2a"}},
            UpdateExpression="SET stock = stock - :one",
            ConditionExpression="stock >= :one",
            ExpressionAttributeValues={":one":{"N":"1"}})
        return "sold"
    except d.exceptions.ConditionalCheckFailedException:
        return "out"
with cf.ThreadPoolExecutor(max_workers=100) as ex:
    r = [x for x in ex.map(sell, range(1500))]
final = int(d.get_item(TableName="Inventory", Key={"PK":{"S":"SKU#9f2a"}},
                       ConsistentRead=True)["Item"]["stock"]["N"])
print(f"sold={r.count('sold')}  refused={r.count('out')}  stock_now={final}")

✅ FIX 2 — OPTIMISTIC CONCURRENCY, when the update is not a simple arithmetic step:
$ cat > occ.py <<'PY'
import boto3, concurrent.futures as cf, collections
d = boto3.client("dynamodb"); stats = collections.Counter()
def update_status(_):
    for attempt in range(5):
        it = d.get_item(TableName="Orders",
              Key={"PK":{"S":"ORDER#001"},"SK":{"S":"META"}}, ConsistentRead=True)["Item"]
        v = int(it["version"]["N"])
        try:
            d.update_item(TableName="Orders",
                Key={"PK":{"S":"ORDER#001"},"SK":{"S":"META"}},
                UpdateExpression="SET #s = :new, version = :v1",
                ConditionExpression="version = :v0",
                ExpressionAttributeNames={"#s":"status"},
                ExpressionAttributeValues={":new":{"S":"SHIPPED"},
                                           ":v0":{"N":str(v)}, ":v1":{"N":str(v+1)}})
            stats[f"ok_attempt_{attempt+1}"] += 1
            return
        except d.exceptions.ConditionalCheckFailedException:
            continue
    stats["gave_up"] += 1
with cf.ThreadPoolExecutor(max_workers=50) as ex:
    list(ex.map(update_status, range(50)))
print(dict(stats))

🎯 Key Takeaways

  • DynamoDB is a partitioned, sorted table: the partition key chooses a shard, the sort key orders within it. Every capability and limit follows from that.
  • Model from access patterns, not entities. Write the queries down first and derive keys that answer each with one Query; a Scan in the request path means the model is wrong.
  • Capacity: 1 WCU = 1 KB write, 1 RCU = 4 KB strong read or 8 KB eventual, transactions double. Verify with --return-consumed-capacity rather than estimating.
  • ProjectionExpression saves bandwidth, never capacity — the whole item is read regardless.
  • On-demand versus provisioned breaks even at ~14% sustained utilisation; above it provisioned is up to 7× cheaper. Provisioned at the floor plus auto scaling is usually right.
  • Per-partition limits are 1,000 WCU and 3,000 RCU, hard — so a table provisioned at 40,000 WCU throttled 69% of writes while consuming 2.5%.
  • Raising capacity to fix a hot partition changes nothing and doubles the bill — proven. Fix the key.
  • Find hot keys with Contributor Insights, not guesswork; sharding took throughput from 1,002/s to 21,840/s with zero throttles.
  • Prefer a calculated shard (derivable at read time, 1 Query) over a random one (N-way fan-out); store shard counts as config so growth is not a migration.
  • Adaptive capacity smooths imperfect distribution but cannot exceed the per-partition ceiling — it is headroom, not permission.
  • FilterExpression is applied after the read: 482,104 items read and 60,263 RCU to return 12. A GSI made the same query 1.5 RCU.
  • ScannedCount versus Count is the fastest diagnostic in DynamoDB — a large ratio means you are paying for data you discard.
  • LSIs can only be created with the table and share its partition key; GSIs can be added any time, are eventually consistent, and have their own capacity.
  • A throttled GSI throttles writes to the base table — measured 92% of writes rejected while the table sat at 1% utilisation. Provision GSIs for the base table's write rate.
  • A low-cardinality GSI partition key (like status) throttles at any capacity; use a sparse index over the rare values instead.
  • An index nobody reads still costs every write and can stop your writes — deleting unused GSIs is an availability improvement.
  • Project INCLUDE with exactly what the query returns; ALL doubles storage and write cost per index.
  • Single-table design is for known access patterns at scale, not a default — and a wrong single-table model is far harder to change than a wrong set of tables.
  • Read-modify-write loses updates silently: 1,000 sold, 947 still in stock, no error anywhere. Atomic SET x = x - :n with a condition is correct and cheaper, needing no read.
  • Use a version attribute plus ConditionExpression for complex updates, and transactions only for genuine multi-item invariants since they cost double.
  • TTL deletes are free but up to 48 hours late — filter on expiry in the read path too, and store epoch seconds or items expire in the year 57000.
  • Export to S3 consumes zero capacity — use it for analytics instead of a Scan that doubles the bill and competes with production.
  • Global tables resolve conflicts by last-writer-wins: concurrent writes to one item silently lose one. Partition writes by Region or design for it.
