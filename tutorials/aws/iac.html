Infrastructure as Code Operations

What you'll master: what infrastructure as code is actually for — review and reproducibility, not automation — and why state is the hard part that distinguishes every tool; reading a plan or change set as the artefact that matters, where a one-word edit shows Replacement: True and would silently destroy a production database; DeletionPolicy and its overlooked twin UpdateReplacePolicy, the two lines that decide whether a mistake is recoverable; Terraform state locking, and what two concurrent applies do to a state file without it; CDK as a synthesiser, where renaming a construct replaces the resource because logical IDs derive from the code's structure; drift, why plan is a prediction rather than a promise, and the SCP that stops drift being possible; and the operational realities nobody writes in the tutorial — importing existing resources without downtime, refactoring without destroying, and recovering from UPDATE_ROLLBACK_FAILED. Prerequisites: IAM, EC2 and Observability.

Part 1 — The Point Is Review, and State Is the Hard Part

The usual argument for IaC is automation, which is the least interesting benefit — a shell script automates too. The real value is that every infrastructure change becomes a reviewable diff with an author, a reason and a history, and that the same input reproduces the same environment. Everything else follows from that.

ToolLanguageWho holds stateBest for
CloudFormationYAML / JSONAWS, in the stackAWS-only, no state to manage, StackSets across accounts
CDKTypeScript, Python, Java, GoAWS (it synthesises CloudFormation)Complex logic, reusable constructs, application teams
TerraformHCLYou, in a state fileMulti-cloud, huge provider ecosystem, mature tooling
SAMYAMLAWS (CloudFormation)Serverless applications specifically
PulumiGeneral-purpose languagesYou, or their serviceTeams wanting CDK ergonomics off AWS
🔑 The "who holds state" column explains almost every operational difference. CloudFormation keeps state inside AWS, so there is nothing to lose, lock or corrupt — but you are bound to its update semantics and its rollback behaviour. Terraform keeps state in a file you own, which gives you import, state mv and surgical fixes — and also gives you a file that can be lost, corrupted or written by two people at once. Neither is better; they fail differently, and knowing which failure you have signed up for is the point.
THE THREE THINGS ANY IaC TOOL IS DOING:

  1. DESIRED state    what your code says should exist
  2. ACTUAL state     what is really in AWS right now
  3. RECORDED state   what the tool believes it created

  drift            = ACTUAL ≠ RECORDED   (someone used the console)
  a plan/change set = RECORDED → DESIRED  (a prediction, not a promise)

Part 2 — CloudFormation: Change Sets, and the Two Policies

NEVER `deploy` BLIND. Create a change set and read it:
$ aws cloudformation create-change-set --stack-name prod-db \
    --template-body file://db.yaml --change-set-name review-$(date +%s) \
    --capabilities CAPABILITY_NAMED_IAM
$ aws cloudformation describe-change-set --stack-name prod-db --change-set-name review-1755701842 \
    --query 'Changes[].ResourceChange.{action:Action,type:ResourceType,
             id:LogicalResourceId,replace:Replacement,props:Details[].Target.Name}' --output table
|  Modify  |  AWS::RDS::DBInstance  |  Database  |  True   |  DBSubnetGroupName  |
                                                    ────
                                    ⚠️ Replacement: True — CloudFormation will
                                       CREATE a new database and DELETE this one.
Property changeEffect
Replacement: FalseUpdated in place — safe
Replacement: ConditionalDepends on values AWS cannot evaluate yet — treat as True
Replacement: TrueNew resource created, old one deleted — new endpoint, empty data
THE TWO POLICIES, and almost everyone sets only the first:

  DeletionPolicy:       what happens when the RESOURCE IS REMOVED or the STACK IS DELETED
  UpdateReplacePolicy:  what happens when an update REPLACES the resource
                        ⚠️ DeletionPolicy does NOT cover this case

  Resources:
    Database:
      Type: AWS::RDS::DBInstance
      DeletionPolicy: Snapshot
      UpdateReplacePolicy: Snapshot          ← without this, a replacement destroys it
      Properties:
        DeletionProtection: true
⚠️ DeletionPolicy: Retain alone does not protect you from a replacement. If an update changes an immutable property, CloudFormation creates the new resource and deletes the old one — and that deletion is governed by UpdateReplacePolicy, which defaults to Delete. Set both, on every stateful resource, every time. This single omission is the most common way production data is lost through IaC.
THE STATE YOU CAN GET STUCK IN:
$ aws cloudformation describe-stacks --stack-name prod-api \
    --query 'Stacks[0].[StackStatus,StackStatusReason]' --output text
UPDATE_ROLLBACK_FAILED   The following resource(s) failed to update: [WorkerQueue]
   → the update failed, AND the rollback failed. The stack accepts no further
     updates until this is resolved.

$ aws cloudformation continue-update-rollback --stack-name prod-api \
    --resources-to-skip WorkerQueue
   → skip the resource that cannot roll back, returning the stack to
     UPDATE_ROLLBACK_COMPLETE. That resource is now DRIFTED — reconcile it manually.

STACKSETS — one template, many accounts and Regions:
$ aws cloudformation create-stack-set --stack-set-name org-baseline \
    --template-body file://baseline.yaml --permission-model SERVICE_MANAGED \
    --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false \
    --capabilities CAPABILITY_NAMED_IAM
$ aws cloudformation create-stack-instances --stack-set-name org-baseline \
    --deployment-targets OrganizationalUnitIds=ou-abc1-1a2b3c4d \
    --regions us-east-1 eu-west-1 \
    --operation-preferences FailureTolerancePercentage=10,MaxConcurrentPercentage=25
   → and `auto-deployment` applies it to accounts created LATER, which is what makes
     a baseline actually hold.

Part 3 — Terraform: The State File Is the Product

❌ LOCAL STATE — fine for a tutorial, a disaster for a team:
$ terraform init
$ ls
main.tf  terraform.tfstate  terraform.tfstate.backup
   → on one laptop, not backed up, not locked, and containing SECRETS in plaintext.

✅ REMOTE STATE WITH LOCKING:
  terraform {
    backend "s3" {
      bucket         = "acme-tfstate"
      key            = "prod/network/terraform.tfstate"
      region         = "us-east-1"
      encrypt        = true
      kms_key_id     = "arn:aws:kms:us-east-1:111122223333:key/9f2a-4b2c"
      dynamodb_table = "acme-tflock"        # or use_lockfile = true on modern versions
    }
  }
⚠️ Terraform state contains every attribute of every resource — including secrets. Database passwords, generated keys and any sensitive value passed to a resource are stored in plaintext in the state file, regardless of whether the variable was marked sensitive. Encrypt the bucket with KMS, restrict read access as tightly as you would to the secrets themselves, enable versioning for recovery, and never commit state to git. "It is only infrastructure metadata" is wrong.
THE PLAN IS THE REVIEW ARTEFACT — and only a SAVED plan is a guarantee:
$ terraform plan -out=tfplan
Plan: 2 to add, 1 to change, 1 to destroy.

  # aws_db_instance.orders must be replaced
  -/+ resource "aws_db_instance" "orders" {
      ~ engine_version = "15.4" -> "16.2"   # forces replacement
      ~ endpoint       = "orders.abc.rds.amazonaws.com" -> (known after apply)
    }

$ terraform apply tfplan
   → applies EXACTLY what you reviewed. `terraform apply` without a saved plan
     re-plans against whatever the world looks like now, which may differ.
CommandDoesDanger
terraform importAdds an existing resource to stateConfig must match, or the next plan destroys it
terraform state rmForgets a resource without destroying itIt becomes unmanaged and invisible
terraform state mvRenames within stateSuperseded by moved blocks
moved blockRefactor without destroy/recreateNone — this is the safe way
-targetApplies part of the graphLeaves state inconsistent — emergencies only
-replaceForces one resource to be recreatedReplaces the old taint
REFACTORING WITHOUT DESTROYING — the `moved` block:
  # renamed aws_instance.web  →  aws_instance.frontend
  moved {
    from = aws_instance.web
    to   = aws_instance.frontend
  }
$ terraform plan
Plan: 0 to add, 0 to change, 0 to destroy.         ← a pure rename. Nothing rebuilt.
   (without it: 1 to add, 1 to destroy — a new instance and an outage)

Part 4 — CDK: A Synthesiser, and Logical IDs

CDK IS NOT A RUNTIME. It generates CloudFormation and hands it over:
$ cdk synth > template.yaml
$ cdk diff                                         ← this IS a change set, read it
$ cdk deploy

  Construct levels:
    L1  CfnBucket           1:1 with CloudFormation. Everything is available.
    L2  s3.Bucket           sensible defaults, helper methods, IAM grants
    L3  patterns            whole architectures (ApplicationLoadBalancedFargateService)

⚠️ LOGICAL IDs ARE DERIVED FROM THE CONSTRUCT PATH. Renaming a variable
   renames the resource, and CloudFormation reads that as delete-and-create:

  const bucket = new s3.Bucket(this, 'DataBucket');     → logical id DataBucket1A2B3C4D
  const bucket = new s3.Bucket(this, 'AssetBucket');    → logical id AssetBucket9F2A4B2C

$ cdk diff
Resources
[-] AWS::S3::Bucket DataBucket1A2B3C4D destroy
[+] AWS::S3::Bucket AssetBucket9F2A4B2C
   ⚠️ A COSMETIC RENAME DELETES THE BUCKET AND ITS CONTENTS.

✅ pin the logical ID when renaming for readability:
  const bucket = new s3.Bucket(this, 'AssetBucket');
  (bucket.node.defaultChild as s3.CfnBucket).overrideLogicalId('DataBucket1A2B3C4D');
$ cdk diff
There were no differences                          ✅ same resource, better name
💡 The same trap applies to moving a construct between stacks or nesting it inside another construct — both change the construct path, and therefore the logical ID. Always read cdk diff before deploying, and look for [-] … destroy lines specifically. CDK's ergonomics make infrastructure feel like application code, where renaming a variable is free; in CloudFormation it is a resource replacement.
THE ESCAPE HATCH — when the L2 construct does not expose what you need:
  const cfnBucket = bucket.node.defaultChild as s3.CfnBucket;
  cfnBucket.addPropertyOverride('ReplicationConfiguration.Rules.0.Priority', 1);
  cfnBucket.addOverride('UpdateReplacePolicy', 'Retain');
  cfnBucket.addOverride('DeletionPolicy', 'Retain');
   → you are never blocked by the abstraction; L1 is always underneath.

SECRETS — never in a template, never in state:
  ❌ MasterUserPassword: !Ref DbPassword          # a parameter: ends up in state/history
  ✅ MasterUserPassword: '{{resolve:secretsmanager:prod/db:SecretString:password}}'
     → resolved by CloudFormation at deploy time; the value never enters the template.

  ✅ better still — let AWS generate it and never see it:
     ManageMasterUserPassword: true               # RDS creates and rotates it in
                                                  # Secrets Manager; nothing to leak

STACK SPLITTING — by change frequency, because that is what determines blast radius:

    network-stack     changes yearly     VPC, subnets, TGW attachments
    data-stack        changes rarely     RDS, DynamoDB, S3 buckets
    platform-stack    changes monthly    clusters, load balancers, roles
    app-stack         changes daily      services, task definitions, alarms

  → the daily deploy cannot touch the database. That is the whole point.
  ⚠️ and the coupling between them should be one-way: use SSM parameters or
    exported outputs, but remember an EXPORTED output cannot be changed while
    another stack imports it — which can wedge you. Prefer SSM parameter lookups.

PREVENTING DRIFT STRUCTURALLY — an SCP, not a policy document nobody reads:
  { "Effect": "Deny",
    "Action": ["ec2:*", "rds:*", "elasticloadbalancing:*"],
    "Resource": "*",
    "Condition": {
      "StringNotLike": { "aws:PrincipalArn": [
         "arn:aws:iam::*:role/DeployRole",
         "arn:aws:iam::*:role/BreakGlassRole" ] },
      "Bool": { "aws:ViaAWSService": "false" } } }
   → the console cannot mutate infrastructure at all. Drift becomes impossible
     rather than discouraged, and break-glass access is auditable.

Part 6 — Drift, Imports, and Broken Deploys

DETECT DRIFT — and note it is a point-in-time scan, not continuous:
$ ID=$(aws cloudformation detect-stack-drift --stack-name prod-api \
    --query StackDriftDetectionId --output text)
$ aws cloudformation describe-stack-drift-detection-status --stack-drift-detection-id $ID \
    --query '[DetectionStatus,StackDriftStatus,DriftedStackResourceCount]' --output text
DETECTION_COMPLETE   DRIFTED   3

$ aws cloudformation describe-stack-resource-drifts --stack-name prod-api \
    --stack-resource-drift-status-filters MODIFIED \
    --query 'StackResourceDrifts[].{id:LogicalResourceId,
             diff:PropertyDifferences[].{p:PropertyPath,exp:ExpectedValue,act:ActualValue}}' --output json
[ { "id": "ApiSecurityGroup",
    "diff": [ { "p": "/SecurityGroupIngress/2", "exp": null, "act": "0.0.0.0/0:22" } ] } ]
   ⚠️ someone opened SSH to the world in the console during an incident,
     and it has been there ever since.

IMPORTING WHAT ALREADY EXISTS — the common real-world starting point:

  CloudFormation:
$ aws cloudformation create-change-set --stack-name legacy-import \
    --change-set-type IMPORT --template-body file://imported.yaml \
    --resources-to-import '[{"ResourceType":"AWS::S3::Bucket",
        "LogicalResourceId":"DataBucket",
        "ResourceIdentifier":{"BucketName":"acme-legacy-data"}}]'
   ⚠️ every imported resource needs DeletionPolicy: Retain in the template,
     or CloudFormation refuses the import.

  Terraform (modern form — declarative, and it appears in the plan):
  import {
    to = aws_s3_bucket.data
    id = "acme-legacy-data"
  }
$ terraform plan
  # aws_s3_bucket.data will be imported
Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.
   ✅ "0 to change" is the goal. Anything else means your config does not match
     reality, and applying would MODIFY a production resource.
🔑 The import workflow is: write config, plan, and iterate until the plan says zero changes. Only then apply. An import that shows "1 to change" is telling you the code and reality disagree, and applying it will mutate a live resource in ways nobody reviewed. This is slow and tedious, and it is the entire safety mechanism — resist the temptation to accept a "small" diff.

❌ Deploying without reading a plan, DeletionPolicy without UpdateReplacePolicy, local Terraform state, secrets as template parameters, one stack for the whole environment, environments separated by a variable, drift addressed by asking people nicely, and a CDK rename shipped because the code diff looked cosmetic. Someone changes a subnet group to tidy up a template; the change set said Replacement: True but nobody read it, so CloudFormation builds a new database, deletes the old one, and the endpoint the application uses no longer exists. The stateful resources have DeletionPolicy: Retain, which does not apply to replacements, so the data is gone anyway. Terraform state lives on one engineer's laptop, is not backed up, is not locked, and contains the database password in plaintext. Secrets are template parameters, so they are in CloudFormation's history and in every state file. A single stack holds the VPC, the database and the application, so a daily deploy can and eventually does touch the network. Environments differ by a variable inside one account, so a mistyped workspace applies staging's plan to production. Drift is managed by a wiki page asking people not to use the console, and an emergency SSH rule opened months ago is still there. And a CDK construct was renamed for readability, which changed its logical ID and deleted the bucket it referred to.

✅ Make the plan the reviewed artefact, set both policies, put state in S3 with locking and KMS, resolve secrets at deploy time, split stacks by change frequency, separate environments by account, deny console mutation with an SCP, and read cdk diff for destroy lines. Generate a change set or a saved plan, review it in the pull request, and apply that file — the code diff hides replacements, and only the plan shows them. Put DeletionPolicy and UpdateReplacePolicy on every stateful resource, since the second governs the case that actually destroys data. Move Terraform state to an encrypted, versioned S3 bucket with locking, and treat read access to it as equivalent to read access to your secrets. Never pass secrets as parameters or variables: use {{resolve:secretsmanager:…}}, or let RDS generate and rotate a password nobody ever sees. Split stacks so the daily deploy cannot reach the database, and prefer SSM parameter lookups to exported outputs, which can wedge a stack that another imports. Give each environment its own account, because an account boundary cannot be bypassed by a mistyped variable. Deny mutating actions outside the deploy role with an SCP so drift is impossible rather than discouraged, and keep an audited break-glass role for the genuine emergency. And with CDK, read the diff for [-] … destroy before every deploy, pinning logical IDs with overrideLogicalId when a rename is purely cosmetic.

Interview Questions

Beginner: What is the actual benefit of infrastructure as code?

Review and reproducibility — not automation. A shell script automates; what IaC adds is that every infrastructure change becomes a diff with an author, a reason, a reviewer and a history, and that the same input reproduces the same environment in a new account or Region.

BenefitWhy it matters
Reviewable changeSomeone other than the author sees it before production does
Reproducible environmentsStaging genuinely resembles production; DR is a deploy
Audit history"Who opened this port, and why" is a git log
RollbackRevert the commit, redeploy
Drift detectionA declared desired state means deviation is detectable at all

The follow-up worth pre-empting: the benefit only materialises if the plan is what gets reviewed. A pull request showing a one-line YAML change can correspond to a change set that replaces a database — so a team that reviews code diffs but deploys without reading change sets has the paperwork of IaC and none of the safety.

Beginner: CloudFormation, CDK or Terraform — how do you choose?
ChooseWhen
CloudFormationAWS-only, you want no state to manage, and you need StackSets across an Organization
CDKYou want loops, conditionals and reusable constructs, and the team is comfortable in a programming language
TerraformMulti-cloud or many SaaS providers, or the team already knows it

The distinction that actually drives operations is who holds state. CloudFormation and CDK (which synthesises to CloudFormation) keep it inside AWS — nothing to lose or corrupt, but you inherit its update and rollback semantics, including UPDATE_ROLLBACK_FAILED. Terraform keeps it in a file you own, which enables import, moved and surgical repair — and creates a file that can be lost, leaked or written concurrently.

The honest answer to "which is best" is that the team's existing familiarity usually outweighs the technical differences, and the worst outcome is using two of them on the same resources. What matters far more than the choice is the discipline around it: reviewed plans, both deletion policies, remote locked state, and separate accounts per environment.

Mid: A colleague changes one property and the database is replaced. How could that have been prevented?

Three independent controls, each of which would have stopped it on its own.

1. Read the change set. CloudFormation states the outcome explicitly before anything happens:

|  Modify  |  AWS::RDS::DBInstance  |  Database  |  Replacement: True  |

The code diff was one line; the change set said a new database would be created and this one deleted. Reviewing the plan rather than the code is the difference.

2. Set both policies. Most people set DeletionPolicy and believe they are covered — but a replacement is governed by UpdateReplacePolicy, which defaults to Delete:

DeletionPolicy: Snapshot
UpdateReplacePolicy: Snapshot         ← the one that applies here

3. Split the stacks. If the database lived in a rarely-changed data stack rather than alongside the application, a routine application change could not have reached it at all.

And structurally: require change-set review in CI — fail the pipeline if any change shows Replacement: True on a stateful resource without an explicit override label on the pull request. That turns a discipline into a control, which is what you want when the failure mode is "someone was in a hurry".

Mid: Two engineers run terraform apply at the same time. What happens, and how do you prevent it?

Without locking, both read the same state, both plan against it, and both write it back — so the second write silently overwrites the first. The result is a state file that does not describe reality: resources created by the first apply exist in AWS but are absent from state, which makes them unmanaged, and a subsequent plan may propose creating duplicates or destroying things it no longer recognises.

The prevention is state locking, which is a property of the backend:

  terraform {
    backend "s3" {
      bucket         = "acme-tfstate"
      key            = "prod/network/terraform.tfstate"
      encrypt        = true
      kms_key_id     = "arn:aws:kms:..."
      dynamodb_table = "acme-tflock"      # or use_lockfile = true on modern versions
    }
  }

With a lock, the second run fails immediately with Error acquiring the state lock and names the holder, which is the correct behaviour.

Two things worth adding. Enable versioning on the state bucket, since it is the only way back from a corrupted state file. And the organisational fix is that humans should not be running apply against production at all — a pipeline holds the credentials, applies a reviewed saved plan, and serialises deploys by construction. Locking prevents the collision; a pipeline prevents the situation.

Senior: Design the IaC strategy for 40 teams across many AWS accounts.

Separate the layers by who owns them and how often they change, because that is what determines both blast radius and review burden.

LayerOwnerCadenceMechanism
Organization: accounts, OUs, SCPsPlatformRarelyStackSets with auto-deployment
Account baseline: logging, guardrails, rolesPlatformRarelyStackSets — applies to future accounts too
Shared network: VPCs, TGW, DNSPlatformYearlyIts own pipeline
Application infrastructureThe teamDailyTheir repo, their pipeline

Environments are separate accounts, not workspaces or variables — the account is the only boundary that cannot be bypassed by a mistyped flag, and it is simultaneously the blast radius, the quota boundary and the cost-attribution boundary.

Give teams paved-road modules rather than freedom or a ticket queue. A published construct or module library — "a service", "a queue with a DLQ and an alarm", "a bucket that is private and lifecycled" — encodes the standards so that the compliant thing is also the easy thing. A central team that reviews every change becomes a bottleneck; a central team that ships good modules scales.

Guardrails as code, enforced in CI and at the Organization: cfn-guard or checkov in every pipeline, SCPs denying infrastructure mutation outside the deploy role so drift is impossible, and Config rules as the detective backstop.

The two things I would insist on regardless of tool: the pipeline applies a saved plan that a human reviewed, and stateful resources carry both DeletionPolicy and UpdateReplacePolicy. Almost every catastrophic IaC incident I have seen reduces to one of those two being absent.

What I would avoid: a single monorepo state for everything (one lock, one blast radius, one bottleneck), and mixing tools on the same resources — Terraform managing a resource inside a CloudFormation stack is a reliable source of destroyed production infrastructure.

Senior: You inherit an account built entirely by hand. How do you get it under IaC without an outage?

Do not start by writing templates. Start by stopping the bleeding and by deciding what is worth importing.

1. Freeze manual change for the resources you are about to import — an SCP restricting mutation to a break-glass role. Importing while people are still editing by hand guarantees the config you write never matches reality.

2. Inventory and triage. Config or Resource Explorer gives the full picture. Then classify honestly: some resources should be imported, some should be recreated under IaC and cut over, and some should simply be deleted because nobody can explain them. Importing everything is a common and expensive mistake — an unused legacy instance does not become valuable by being in a template.

3. Import in dependency order, outside-in: network first, then data stores, then compute, then application resources. Each import follows the same loop — write config, plan, iterate until the plan reports zero changes, then apply.

  import { to = aws_s3_bucket.data, id = "acme-legacy-data" }
$ terraform plan
Plan: 1 to import, 0 to add, 0 to change, 0 to destroy.     ← the ONLY acceptable result

"0 to change" is non-negotiable. Any other number means the code and reality disagree, and applying would modify a production resource in a way nobody reviewed. It is slow and tedious, and that tedium is the safety mechanism.

4. Protect before you proceed: DeletionPolicy and UpdateReplacePolicy (CloudFormation actually requires the former for imports), prevent_destroy lifecycle rules in Terraform, and deletion protection on databases — so that a mistake during the migration is recoverable.

5. Then the greenfield lever: once the critical path is under code, build the next environment entirely from it. That is the real test of the work, and it converts the effort into something reusable — a DR account, a new Region, a per-team sandbox — rather than a one-off tidy-up.

Expectation to set with stakeholders: this takes months and produces no visible feature. The way to keep it funded is to sequence it so each phase pays for itself — the freeze prevents incidents immediately, the data-layer import makes DR possible, and the paved-road modules speed up every team afterwards.

🏋️ Exercises

1 (easy): Make a change that looks harmless in the code diff and destroys a database in the change set. Prove the code diff cannot tell you.
Solution 
$ git diff db.yaml
-        DBSubnetGroupName: !Ref OldSubnetGroup
+        DBSubnetGroupName: !Ref NewSubnetGroup
   → one line. A reviewer approves it in seconds.

NOW ASK CLOUDFORMATION WHAT IT WILL ACTUALLY DO:
$ aws cloudformation create-change-set --stack-name prod-db \
    --template-body file://db.yaml --change-set-name review-$(date +%s) \
    --capabilities CAPABILITY_NAMED_IAM
$ aws cloudformation wait change-set-create-complete --stack-name prod-db \
    --change-set-name review-1755701842
$ aws cloudformation describe-change-set --stack-name prod-db \
    --change-set-name review-1755701842 \
    --query 'Changes[].ResourceChange.{action:Action,id:LogicalResourceId,
             type:ResourceType,replace:Replacement,
             scope:Scope,cause:Details[].ChangeSource}' --output table
|  Modify  |  Database  |  AWS::RDS::DBInstance  |  True  |  Properties  |  DirectModification  |
                                                    ────
   ⚠️ Replacement: True. A NEW database, then DELETE the old one.
     New endpoint. Empty data. The code diff said none of this.

CONFIRM WHAT WOULD BE LOST:
$ aws cloudformation describe-stack-resources --stack-name prod-db \

Use prevent_destroy and ignore_changes for passwords while you work, keep the freeze in place until the layer is done, and prove the result by building a second environment from the same code.

🎯 Key Takeaways

  • IaC is for review and reproducibility, not automation — the value is that every change is a diff with an author, a reviewer and a history.
  • Who holds state explains every operational difference: CloudFormation keeps it in AWS (nothing to lose, its rollback semantics), Terraform in a file you own (surgical repair, and a file that can be lost or corrupted).
  • Reviewing the code is not reviewing the change. A one-line diff produced Replacement: True on a production database — only the change set or plan shows that.
  • Treat Replacement: Conditional as True, and fail CI on replacements of stateful resources.
  • DeletionPolicy does not cover replacements — UpdateReplacePolicy does, and it defaults to Delete. Proven: Retain was set and the database was destroyed anyway.
  • Layer the protections: both policies, DeletionProtection, stack termination protection, and an SCP — because every template-level control is bypassed by editing the template.
  • Terraform state contains every attribute in plaintext, including passwords, regardless of sensitive. Encrypt it, version it, and restrict it like a secret.
  • Two concurrent applies without locking orphaned a real resource and wedged the next plan; locking refuses the second apply and names the holder.
  • Only a saved plan is a guarantee — plan -out=tfplan then apply tfplan, or you apply something nobody reviewed.
  • Use moved blocks to refactor: a rename went from "1 to add, 1 to destroy" to "0 to add, 0 to destroy".
  • CDK logical IDs derive from the construct path, so renaming a construct, nesting it, or moving it between stacks all read as destroy and create.
  • Pin with overrideLogicalId for cosmetic renames, and gate CI on [-] … destroy lines in cdk diff.
  • Never put secrets in templates, parameters or variables — use {{resolve:secretsmanager:…}}, or let RDS generate and rotate a password nobody ever sees.
  • Split stacks by change frequency and ownership so the daily deploy cannot reach the database; prefer SSM parameter lookups to exported outputs, which wedge while imported.
  • Separate environments by account, not by workspace or variable — an account boundary cannot be mistyped.
  • Drift is not automatically wrong: triage each one as revert-it or adopt-it-into-code, using CloudTrail to learn who changed it and why.
  • Detection is a point-in-time scan; an SCP denying mutation outside the deploy role makes drift impossible rather than merely visible.
  • Recover UPDATE_ROLLBACK_FAILED with continue-update-rollback --resources-to-skip, then reconcile the resource you skipped.
  • Import is an iterate-until-clean loop: "0 to change" is the only acceptable plan, and accepting a small diff modifies production.
  • When adopting a hand-built account: freeze manual change first, triage what is worth importing at all, import outside-in, and prove it by building the next environment from the code.
  • -target and state rm leave state inconsistent — emergencies only, never as a way to make a confusing plan go away.
