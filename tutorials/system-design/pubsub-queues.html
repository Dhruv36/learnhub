Pub/Sub vs Message Queues Fundamentals

What you'll master: the competing-consumers vs broadcast distinction and why Kafka is both, why true exactly-once delivery is impossible and what "effectively-once" actually requires in code, how partition keys buy ordering and what they cost you, the outbox pattern that fixes the dual-write problem, and how to run a queue in production — backpressure, DLQs, poison messages and consumer lag.

Prerequisites: CAP Theorem, Replication & Failover. Feeds Microservices, Data Platforms and Design a Notification System.

1. Why Asynchronous Messaging Changes The System

The value isn't "messages" — it's decoupling in three independent dimensions, and naming all three is what makes an interview answer sound experienced:

DecouplingWhat it buys
TemporalThe consumer doesn't have to be up when the producer sends. Deploy, restart, or crash a consumer without losing work.
LoadThe queue absorbs bursts. A 10× traffic spike becomes a deeper queue and delayed processing, not dropped requests or a melted database.
LogicalThe producer doesn't know who consumes. Adding a fourth consumer of "order placed" requires no change to the order service.

Compare the synchronous version of the same flow, because the contrast is the argument:

❌ Synchronous chain 
POST /order
  → charge payment    (300 ms)
  → reserve inventory (150 ms)
  → send email        (800 ms)
  → update analytics  (200 ms)
  → return 201        (1,450 ms)

Availability = product of ALL four:
  0.999⁴ ≈ 99.6%

The email provider being slow makes
CHECKOUT slow. Its outage makes
checkout FAIL — for a side effect
the customer doesn't even see.
✅ Async after the critical path 
POST /order
  → charge payment    (300 ms)
  → reserve inventory (150 ms)
  → publish OrderPlaced
  → return 201        (455 ms)

email / analytics / recommendations
consume OrderPlaced independently.

Checkout availability now depends
on payment + inventory only.
Email provider down → emails queue
up and send later. Nobody notices.
💡 The design rule this yields: keep in the synchronous path only what the user's response correctness depends on. Payment and inventory must succeed before you promise an order; email, analytics, search indexing and recommendations must not. Every dependency you move off the critical path is one that can no longer take down the request — the same any-of-N vs all-of-N arithmetic from replication.

2. Queue vs Pub/Sub: Competing Consumers vs Broadcast

MESSAGE QUEUE — each message goes to exactly ONE consumer
                (they COMPETE; this is how you parallelise work)

  Producer → [ m1 m2 m3 m4 m5 ] → Worker A takes m1  (m1 now invisible/removed)
                                → Worker B takes m2
                                → Worker C takes m3
  Add workers → throughput rises. Each job done once.
  Examples: SQS, RabbitMQ queues, Celery.


PUB/SUB — every subscriber gets EVERY message (they BROADCAST)

  Publisher → TOPIC ─┬→ Subscriber A gets m1, m2, m3   (own copy, own cursor)
                     ├→ Subscriber B gets m1, m2, m3
                     └→ Subscriber C gets m1, m2, m3
  Add subscribers → same throughput, more reactions. Each event seen by all.
  Examples: SNS, Google Pub/Sub, Redis pub/sub, Kafka consumer groups.
Queue (competing consumers)Pub/Sub (broadcast)
Use forWork distribution — resize an image, send one email, process one paymentEvent notification — "order placed" fans out to inventory, email, analytics, fraud
Scaling consumersMore workers = more throughputMore subscribers = more reactions, same throughput
CouplingProducer knows a job needs doingProducer knows only that something happened
Message namingCommands: ResizeImage, SendEmailEvents (past tense): OrderPlaced, UserRegistered

The command/event naming distinction is a real signal. A command names an action the producer wants performed and implies exactly one handler; an event names a fact that already happened and implies any number of interested parties. Teams that blur this end up with "events" like SendWelcomeEmail published to a topic — which is a command wearing an event's costume, and it recouples the producer to the consumer's job.

3. Kafka Is Both — And That's The Interesting Part

Kafka isn't "a queue" or "a pub/sub system"; it's a partitioned, replayable log, and the two models fall out of how you assign consumer groups.

TOPIC "orders", 4 partitions. Records are appended and RETAINED
(not deleted on read) — consumers track their own OFFSET.

  P0: [o1][o5][o9] ...
  P1: [o2][o6]     ...
  P2: [o3][o7]     ...
  P3: [o4][o8]     ...

Consumer group "email-service"     (2 consumers)
   C1 ← P0, P1        C2 ← P2, P3          ← partitions SPLIT within a group
   → queue-like: each record handled once by the group

Consumer group "analytics"          (1 consumer)
   C1 ← P0, P1, P2, P3
   → gets EVERY record independently, own offsets

Consumer group "fraud-detection"    (4 consumers)
   C1←P0  C2←P1  C3←P2  C4←P3
   → also gets every record; maximum parallelism

→ ACROSS groups: pub/sub (each group sees everything).
→ WITHIN a group: queue (partitions divided, each record once).

Two consequences that matter in design discussions:

Partition count caps consumer parallelism within a group. With 4 partitions, a 5th consumer in that group sits idle — there's nothing left to assign. Partition count is therefore a capacity decision made at topic-creation time, and increasing it later reshuffles key→partition mapping (breaking ordering for in-flight keys), so teams deliberately over-partition up front.

Retention enables replay. Because records aren't deleted on consumption, a new consumer group can start from offset 0 and rebuild its entire state from history — the property that makes event sourcing and "add a new service that needs the last 6 months of events" possible. A traditional queue deletes on ack, so that history simply doesn't exist.

Log-based (Kafka, Pulsar, Kinesis)Broker queue (SQS, RabbitMQ)
Message lifetimeRetained by time/size policy; replayableDeleted on acknowledgement
OrderingPer-partition, strictSQS Standard: none. FIFO: per message-group
Consumer modelPull, with offsets the consumer ownsPush/pull with per-message ack and visibility timeout
Redelivery granularityRewind the offset — replays everything after itPer-message; one failed message doesn't affect others
StrengthThroughput, replay, multiple independent consumers, event sourcingPer-message retry/DLQ semantics, simple ops, no partition sizing
WeaknessA poison message blocks its partition; per-message retry is awkwardNo replay; limited ordering; fan-out needs a separate topic (SNS→SQS)
🎯 Staff-level framing: the deepest difference isn't the delivery model, it's who owns the cursor. In a broker queue the broker tracks per-message state (delivered? acked? retried 3 times?), which gives beautiful per-message retry and DLQ behaviour but makes the broker stateful and harder to scale. In a log the consumer owns one integer offset per partition, which makes the broker nearly stateless and enormously fast — but per-message retry becomes the consumer's problem, and a single poison record can stall an entire partition. Most "should we use Kafka or SQS?" debates are really about that trade.

4. Delivery Guarantees: Why Exactly-Once Doesn't Exist

GuaranteeMechanismFailure mode
At-most-onceAck before processing (or fire-and-forget)Loss. Crash after ack, before work → message gone. Acceptable only for pure telemetry.
At-least-onceAck after successful processing; redeliver if no ackDuplicates. Crash after work, before ack → redelivered and reprocessed. The default everywhere.
Exactly-onceNot achievable end-to-end across a networkSee below — the honest answer is "effectively-once".

Why it's impossible, stated concretely — the ack itself can be lost:

Consumer processes message m, then sends ACK. The ACK is lost in the network.

The broker cannot distinguish:
   (a) consumer processed m, ack lost        → redelivering DUPLICATES
   (b) consumer died before processing m     → NOT redelivering LOSES it

Both look identical from the broker's side. It must choose:
   redeliver → at-least-once (duplicates)
   don't     → at-most-once  (loss)

There is no third option. This is the Two Generals' Problem: no finite
protocol over a lossy channel achieves certain mutual agreement.
Adding another ack just moves the uncertainty to that ack.

What "exactly-once" products actually mean. Kafka's exactly-once semantics are real but narrower than the name suggests: idempotent producers (sequence numbers deduplicate retried produces) plus transactions that atomically commit consumer offsets together with output records — giving exactly-once for Kafka-to-Kafka processing. The moment your consumer's side effect leaves Kafka (charging a card, sending an email, writing to Postgres), that atomicity is gone and you are back to at-least-once plus your own idempotency.

5. Deep Dive: Building Effectively-Once In Practice

Since at-least-once is what you get, idempotent consumers are not optional. Three techniques, in increasing robustness:

① NATURAL IDEMPOTENCY — restructure so repeats are harmless.
   Bad:  balance = balance + 10        (repeat → wrong balance)
   Good: SET status = 'shipped'        (repeat → same result)
   Prefer SET over INCREMENT, absolute over relative, wherever possible.
   Cheapest and most robust: no extra state to maintain.

② DEDUPLICATION TABLE — record processed IDs, check before acting.
   Must be in the SAME TRANSACTION as the side effect, or the gap
   between "act" and "record" reintroduces the duplicate.

     BEGIN;
       INSERT INTO processed(msg_id) VALUES ($1);  -- PK violation if dup
       UPDATE orders SET status='paid' WHERE id=$2;
     COMMIT;
   The unique constraint does the work: a duplicate throws, you catch
   it, ack the message, and move on. Atomic by construction.

③ CONDITIONAL / VERSIONED WRITES — compare-and-set on a version.
     UPDATE orders SET status='paid', version=version+1
      WHERE id=$1 AND version=$2;
   0 rows updated → someone already applied it → safe to ack.
   Works without a separate dedup table; needs a version column.

Where teams get this wrong: putting the dedup check outside the transaction.

❌ Check, then act 
if seen(msg_id):        # check
    return
charge_card()           # act
mark_seen(msg_id)       # record

Crash between charge and mark
→ redelivery charges AGAIN.

Two consumers concurrently:
both see "not seen", both charge.
The check bought nothing.
✅ Atomic insert-or-fail 
BEGIN;
  INSERT INTO processed(msg_id)
    VALUES ($1);   -- dup → error
  apply_side_effect();
COMMIT;

The unique constraint IS the
mutual exclusion. No window,
no race, no second consumer.

For external calls, pass an
idempotency key so the PROVIDER
dedupes (Stripe works this way).

For external side effects you can't wrap in your transaction — charging a card, sending an email — the answer is to push idempotency to the provider: send a stable idempotency key derived from the message ID, and let the provider guarantee one charge per key. That's precisely the fencing-token principle again: put the safety check at the resource, not in the caller.

6. Deep Dive: Ordering, Partition Keys, And What They Cost

Global total ordering across a distributed topic would require a single serialisation point — which is exactly the bottleneck partitioning exists to remove. So systems offer ordering within a partition and let you choose what shares a partition.

partition = hash(key) % partition_count

key = user_id  →  all of one user's events land in one partition,
                  so they are consumed IN ORDER relative to each other.
                  Different users may interleave arbitrarily — which is
                  usually fine, because they're causally unrelated.
SystemOrdering guaranteeNotes
KafkaStrict per partitionSame key → same partition → ordered. Requires max.in.flight ≤ 5 with idempotence, or retries can reorder.
SQS StandardNoneBest-effort only; assume arbitrary order. Very high throughput.
SQS FIFOPer MessageGroupIdOrdered within a group, and a blocked group stalls only itself. Throughput capped (~3,000 msg/s with batching).
RabbitMQPer queue, single consumerAdding a second consumer to a queue breaks ordering — parallelism and ordering are directly opposed.

The three costs of ordering, which is what senior interviews probe:

1. Parallelism collapses to the key. Ordering per user means one consumer thread per user at a time. Fine when users are numerous and independent; fatal if you key by something coarse like region — you've built a single-threaded pipeline with extra steps.

2. Hot partitions. Keying by tenant_id in a system with one enormous tenant puts a disproportionate share of traffic on one partition — the balanced-keys-but-not-balanced-load problem, and adding partitions doesn't help because that key still hashes to one place.

3. Head-of-line blocking. In a log, one un-processable record blocks every later record in its partition. Ordering is precisely the guarantee that forbids skipping ahead — so you must decide explicitly: stall the partition (preserve order, halt progress) or divert the bad record to a DLQ (make progress, break ordering for that key). There's no option that keeps both.

⚠️ Question the requirement before paying for it. "Process events in order" is often over-specified. Alternatives that avoid ordering entirely: make handlers commutative so order doesn't matter; include a version or timestamp in each event and have the consumer reject anything older than what it has applied (last-write-wins at the consumer, which tolerates arbitrary arrival order); or send state snapshots instead of deltas, since a full-state message is self-contained and the newest one always wins. Each of these buys back full parallelism.

7. Deep Dive: The Dual-Write Problem And The Outbox Pattern

This is the most common correctness bug in event-driven systems, and it's invisible until it isn't.

❌ THE DUAL WRITE — two systems, no shared transaction:

   BEGIN; UPDATE orders SET status='paid'; COMMIT;   ← database
   kafka.publish(OrderPaid)                          ← broker

   Crash between them → the DB says paid, no event was ever published.
   Inventory never reserved, no email sent, analytics wrong. FOREVER —
   there is no retry that fixes it, because nothing recorded the intent.

   Reverse the order and it's just as broken: publish then crash before
   commit → consumers react to an order that doesn't exist.

The outbox pattern fixes it by making the event part of the same transaction as the state change:

✅ TRANSACTIONAL OUTBOX

   BEGIN;
     UPDATE orders SET status='paid' WHERE id=42;
     INSERT INTO outbox(id, topic, payload)
       VALUES (uuid, 'orders', '{"type":"OrderPaid","id":42}');
   COMMIT;                    ← ONE atomic commit. Both or neither.

   A separate relay process then:
     SELECT * FROM outbox WHERE published=false ORDER BY id;
     publish each to Kafka;
     mark published=true;

   The relay can crash and retry freely — it may publish a message
   TWICE (at-least-once), which is exactly what idempotent consumers
   from section 5 already handle. What it can never do is LOSE an
   event, because the event is committed with the data.

The relay is usually CDC tailing the database log (Debezium), which needs no polling and no extra table scan. Note how this composes with earlier lessons: the same CDC stream that reliably publishes events also drives cache invalidation — one mechanism, because both need "the truth about what committed."

The inverse pattern, listen-to-yourself: publish the event first, then have your own service consume it to update its database. The event log becomes the source of truth and there's no dual write at all. Costs you read-your-own-writes (your own DB is now eventually consistent with the event you just published), so it suits systems that are already event-sourced.

8. Running It In Production: Backpressure, DLQs, Lag

Backpressure. The queue is a shock absorber, not infinite storage. When producers outpace consumers, depth grows — and you must decide, in advance, what happens at the limit:

StrategyBehaviourUse when
Buffer (default)Queue grows; latency risesBursts are temporary and consumers will catch up
Autoscale consumersAdd workers based on depth or lagThe real fix for sustained growth — scale on queue depth, not CPU
Shed load at the producerReject new work with a 429Latency-sensitive work where a stale result is worthless
Drop by prioritySeparate queues; starve the low-priority oneMixed criticality — never let bulk backfills delay user-facing work

A growing queue is a leading indicator. Alert on depth and its derivative: depth rising steadily means consumers are permanently under-provisioned, and the queue is buying you time, not fixing anything. Also alert on oldest-message age — depth alone hides a stuck partition.

Dead-letter queues and poison messages. A message that will never succeed — malformed JSON, a reference to a deleted row, a bug — must not be retried forever:

Retry with exponential backoff + JITTER (see the caching lesson: never
let retries synchronise), up to N attempts. Then → DLQ.

Without a DLQ, the two outcomes are both bad:
   infinite retry  → the poison message blocks the queue (or burns
                     capacity forever) and, in a log, stalls its
                     whole partition
   silent drop     → data loss with no record that it happened

The DLQ is where you INSPECT and REPLAY after fixing the bug. Treat a
non-empty DLQ as an alert, not a dumping ground — an unmonitored DLQ is
just a slower silent drop.

Consumer lag is the single most important metric for log-based systems: how many records behind the head is each consumer group, per partition? Per-partition matters because aggregate lag hides the case where one partition is stalled and the rest are healthy — which is exactly what head-of-line blocking looks like.

Interview Questions

🟢 Beginner — When would you choose a queue over pub/sub, and vice versa?

Queue — when work must be done once and you want to parallelise it across a fleet. Image resizing, sending a specific email, processing a payment. Consumers compete: each message goes to exactly one worker, so adding workers increases throughput. The producer is effectively saying "this job needs doing".

Pub/Sub — when several independent systems must react to the same fact. "Order placed" needs to reach inventory, email, analytics and fraud detection, each doing something different, each with its own copy of the event. Adding a fifth subscriber requires no change to the publisher — that logical decoupling is the whole point.

A useful tell is the message name. Commands (ResizeImage) imply one handler → queue. Events in the past tense (OrderPlaced) imply any number of interested parties → pub/sub. If you find yourself publishing SendWelcomeEmail to a topic, you've written a command as an event and recoupled the producer to what the consumer does.

In practice you often use both: pub/sub to fan an event out, with each subscriber feeding its own work queue.

🟢 Beginner — What are the three delivery guarantees, and which do real systems use?

At-most-once: the message arrives zero or one times. Achieved by acknowledging before processing — so a crash mid-work loses it. Only acceptable for data where loss is cheap, like high-volume metrics.

At-least-once: one or more times. Achieved by acknowledging only after successful processing; if no ack arrives, the broker redelivers. The risk is duplicates. This is what essentially every production system uses.

Exactly-once: the ideal, and not achievable end-to-end across a network. When a consumer processes a message and its ack is lost, the broker cannot distinguish that from a consumer that died before processing — so it must either redeliver (duplicates) or not (loss). There is no third choice; this is the Two Generals' Problem.

So real systems build effectively-once: at-least-once delivery plus idempotent consumers, so processing a duplicate has no additional effect. The practical implication is that idempotency isn't an optimisation you add later — it's a requirement of every consumer you write.

🟡 Mid — Your consumer charges credit cards. How do you prevent double charges on redelivery?

Redelivery is guaranteed to happen eventually (at-least-once), so the consumer must be idempotent. The key point is that a naive "check if processed, then charge" is not idempotent — it has a race and a crash window:

❌ if not seen(msg_id): charge(); mark_seen(msg_id)
   - crash between charge and mark → redelivery charges again
   - two concurrent consumers both pass the check → two charges

The fix has two layers, and I'd use both:

1. Atomic local dedup. Insert the message ID and record the charge in the same transaction, letting a unique constraint provide mutual exclusion:

BEGIN;
  INSERT INTO processed_messages(msg_id) VALUES ($1);  -- PK error if dup
  INSERT INTO payments(order_id, amount, status) VALUES (...);
COMMIT;
-- On unique violation: already handled → just ack the message.

2. Push idempotency to the payment provider — this is the layer that actually protects the money, because the charge is an external side effect I cannot enroll in my transaction. Send a stable idempotency key derived from the message or order ID; Stripe and similar providers guarantee one charge per key even if I send the request twice. Now even a crash during the HTTP call is safe: retrying with the same key returns the original charge rather than creating a second.

Why both: the provider key prevents the double charge; the local table lets me answer "did I already handle this?" without an API round trip, and keeps my own records consistent. And the ordering matters — write the intent locally before calling the provider, so a crash leaves a record I can reconcile rather than a mystery charge.

I'd also make the whole thing observable: a metric on duplicate-detection hits. A sudden spike means something upstream is redelivering aggressively and is worth investigating.

🟡 Mid — How do you guarantee a user's events are processed in order, and what does it cost?

Mechanism: use the user ID as the partition key. partition = hash(user_id) % partition_count sends all of one user's events to the same partition, and partitions are strictly ordered, so that user's events are consumed in the order they were produced. Different users interleave arbitrarily, which is fine because their events are causally unrelated.

In Kafka that's the message key; in SQS FIFO it's MessageGroupId; in RabbitMQ you'd need one queue per key with a single consumer, which is why RabbitMQ scales poorly for this.

Three costs:

1. Parallelism is capped by the key. One user's events are processed serially. That's acceptable with millions of users, but if you keyed by something coarse — region, or a single tenant — you've built a serial pipeline. Choose the finest-grained key whose ordering you actually need.

2. Hot partitions. One very active user or tenant sends far more events than others, and they all land on one partition. Adding partitions doesn't help, because that key still hashes to one place — the same limitation as hot keys on a hash ring.

3. Head-of-line blocking. A record that can't be processed blocks every later record in its partition, because ordering is exactly the guarantee that forbids skipping ahead. You must choose explicitly: stall the partition to preserve order, or divert to a DLQ and accept an ordering gap for that key. Nothing preserves both.

Also worth stating: with Kafka, retries can reorder within a partition unless you enable idempotent production and bound max.in.flight.requests — so "same key" alone isn't sufficient; the producer config has to cooperate.

And I'd question the requirement first. Often ordering isn't needed: version each event and have the consumer ignore anything older than its current state, or send full state snapshots rather than deltas so the newest message always wins. Both tolerate arbitrary arrival order and restore full parallelism — usually a better trade than paying ordering's three costs.

🔴 Senior — Your service updates its database and publishes an event. Occasionally consumers never see the event despite the DB showing the change. Diagnose and fix.

This is the dual-write problem, and it's a design flaw rather than a bug — the two writes go to different systems with no shared transaction:

BEGIN; UPDATE orders SET status='paid'; COMMIT;   ← succeeded
kafka.publish(OrderPaid)                          ← process crashed here
→ DB is updated, event never published, and nothing recorded the intent
  to publish. No retry can recover it. Permanent inconsistency.

Reversing the order doesn't help — publishing first and then crashing before commit means consumers react to an order that doesn't exist. Wrapping them in a "transaction" across both systems isn't available either, and 2PC across a database and a broker is exactly the availability-multiplying trap discussed in CAP.

The fix — transactional outbox:

BEGIN;
  UPDATE orders SET status='paid' WHERE id=42;
  INSERT INTO outbox(id, topic, payload) VALUES (uuid, 'orders', {...});
COMMIT;                          -- one atomic commit: both or neither

Relay process: read unpublished outbox rows → publish → mark published.

The relay may publish a message twice if it crashes after publishing but before marking — that's at-least-once, which idempotent consumers already handle. What it can never do is lose an event, because the event was committed alongside the data.

Implementation choices for the relay: polling the outbox table is simple and works anywhere, but adds query load and latency. CDC (Debezium tailing the WAL/binlog) is better at scale — no polling, low latency, and it cannot be bypassed by application code. Note that CDC can even publish from the orders table directly, skipping the outbox; the outbox is still preferable when you want to control the event's shape rather than leaking your table schema to consumers.

Operational details I'd add: the outbox table needs pruning (delete published rows on a schedule, or it grows forever and slows the relay); ordering should be preserved by relaying in primary-key order per aggregate; and monitor unpublished-row age — a stalled relay is silent, since the application keeps succeeding while consumers fall behind.

The alternative worth mentioning: listen-to-yourself — publish the event first and let your own service consume it to update its database. Then there's only one write and no dual-write problem at all. The cost is losing read-your-own-writes on your own data, so it fits systems already built on event sourcing.

🔴 Senior — Design the messaging architecture for an e-commerce checkout: payment, inventory, email, analytics, recommendations, fraud.

Step 1 — split the flow by whether the user's response depends on it. This is the decision that shapes everything else:

SYNCHRONOUS (must succeed before returning 201):
   - payment authorisation   → the order is meaningless without money
   - inventory reservation   → overselling is a real business cost
   Availability = payment × inventory only.

ASYNCHRONOUS (must not block or fail checkout):
   - email confirmation, analytics, recommendations, fraud scoring,
     warehouse notification, loyalty points
   A slow email provider must never slow checkout; its outage must
   never fail checkout.

Step 2 — publish one event, fan out with pub/sub. On success, publish OrderPlaced to a topic. Each downstream service is its own consumer group, so each gets every event independently and a failure in one doesn't affect the others. Adding "SMS notifications" later means adding a subscriber, with no change to checkout.

Step 3 — outbox for the publish, because this is exactly the dual-write hazard: the order row and the outbox row commit in one transaction, and CDC/relay publishes. Losing an OrderPlaced event would mean a paid order that never ships — the worst failure in the system, and it's silent.

Step 4 — per-consumer design decisions:

ConsumerDesignReasoning
EmailQueue per consumer group, bounded retries → DLQ. Idempotency key = order_id + templateA duplicate email is embarrassing but survivable; a lost one is a support ticket. Retry generously.
Inventory (post-reservation fulfilment)Ordered by sku as partition key; atomic dedup on event IDStock movements per SKU must not reorder or double-apply. Keying by SKU (not order) is what makes ordering meaningful here.
AnalyticsKafka with long retention, at-least-once, dedup at query timeWants replay — a new metric needs last quarter's events. This is why a log beats a queue for this consumer.
RecommendationsSame log, separate group, may lag freelyLoss-tolerant and latency-insensitive; must never apply backpressure to anything else.
FraudConsumes the event, but can also act synchronously pre-auth with a strict timeout and fail-open defaultThe one case where async might be too late — so split it: a fast inline check with a deadline, plus deeper async scoring that can reverse an order afterwards.

Step 5 — the multi-step consistency problem. Payment succeeded but inventory reservation later fails (a race, or the reservation expires). There's no distributed transaction, so use a saga with compensating actions: refund the payment, publish OrderCancelled, and notify the customer. Every step needs an idempotency key because every step will be retried. Model the order as an explicit state machine (pending → paid → reserved → shipped, with cancelling/refunded branches) so a crash at any point leaves a state you can resume from rather than an ambiguous one.

Step 6 — operations. Alert on consumer lag per partition (aggregate lag hides one stalled partition), on DLQ depth for every consumer, and on outbox unpublished-row age. Separate queues by priority so a bulk analytics backfill can never delay confirmation emails.

The framing I'd close on: the architecture's real achievement is that checkout's availability no longer depends on six services — only on payment and inventory. Everything else degrades to "delayed" instead of "failed", and that conversion of hard failures into latency is the entire reason to introduce a broker.

Exercise 1 (Easy): For each, choose queue or pub/sub: (a) resize uploaded images, (b) notify 4 services that a user signed up, (c) send one password-reset email, (d) stream page views to analytics and the recommendation engine.
Solution

(a) Resize images → queue. Each image needs resizing exactly once; workers compete, and adding workers increases throughput. A command, not an event.

(b) Notify 4 services of a signup → pub/sub. One event (UserRegistered), four independent reactions, each with its own copy. Adding a fifth consumer shouldn't touch the signup service.

(c) Password-reset email → queue. Exactly one email should be sent, by one worker. Note this is a command — and it's worth flagging that if you'd published PasswordResetRequested as an event with one subscriber, that also works and is more extensible; the distinction is whether the producer is dictating the action or reporting a fact.

(d) Page views to analytics + recommendations → pub/sub, specifically a log (Kafka/ Kinesis). Two independent consumers need every event, and both benefit from replay — a new metric or retrained model needs history. High volume plus multiple independent readers plus replay is precisely the log-based use case.

Exercise 2 (Easy): A consumer acks a message, then crashes before finishing the work. What guarantee did the system provide, and what would you change?
Solution

Acking before completing the work provides at-most-once delivery: the broker considers the message handled and will never redeliver it, so the work is silently lost. Worse, nothing records that it happened — no error, no DLQ entry, no metric. You discover it from a customer complaint.

The change: ack only after the work is durably committed. That converts the system to at-least-once — on a crash the broker redelivers, and the work gets done.

❌ msg.ack(); process(msg)        # at-most-once: loss on crash
✅ process(msg); msg.ack()        # at-least-once: duplicate on crash

The consequence to state explicitly: you've traded loss for duplicates, so the consumer now must be idempotent. That's the correct trade — duplicates are detectable and preventable with a dedup table or idempotency key, whereas silent loss is neither.

Practical detail: the broker needs a visibility timeout (SQS) or max poll interval (Kafka) longer than your worst-case processing time, or the broker will redeliver while the first consumer is still working — producing duplicates from slowness rather than failure.

Exercise 3 (Medium): Write an idempotent consumer for "apply a $10 account credit". Show why the obvious version is wrong.
Solution 
❌ WRONG — not idempotent, and not fixable by checking first:
def handle(msg):
    if db.query("SELECT 1 FROM processed WHERE msg_id=?", msg.id):
        return
    db.execute("UPDATE accounts SET balance = balance + 10 WHERE id=?",
               msg.account_id)
    db.execute("INSERT INTO processed(msg_id) VALUES (?)", msg.id)

Two failures:
 1. Crash between the UPDATE and the INSERT → redelivery credits AGAIN.
 2. Two consumers process the same message concurrently → both SELECT
    "not processed", both credit. The check bought nothing because it
    isn't atomic with the write.
Also: `balance + 10` is a RELATIVE update, so every duplicate compounds.
✅ CORRECT — one transaction, unique constraint as mutual exclusion:
def handle(msg):
    try:
        with db.transaction():
            # PK violation if this msg_id was already applied
            db.execute("INSERT INTO processed(msg_id) VALUES (?)", msg.id)
            db.execute("UPDATE accounts SET balance = balance + 10 "
                       "WHERE id=?", msg.account_id)
        msg.ack()
    except UniqueViolation:
        msg.ack()          # already applied — safe to ack, not an error

Why this works: the insert and the update commit atomically, so there is no window between "recorded" and "applied". Concurrency is handled by the database's unique constraint rather than by application logic — one transaction wins, the other gets a violation and acks. No distributed lock needed.

Points worth making:

• The dedup key should be the message ID, not the account ID — the same account legitimately receives many credits.
• processed needs a retention policy (delete rows older than the maximum possible redelivery window, e.g. 7 days) or it grows forever.
• A relative update (balance + 10) is inherently duplicate-sensitive, which is why the dedup table is mandatory here. Where the domain allows it, prefer an absolute write (SET status='paid') — naturally idempotent with no extra state, per section 5.
• Best of all for money: model it as an immutable ledger — INSERT INTO entries(msg_id UNIQUE, account_id, amount) and derive the balance as a sum. The unique constraint on the ledger entry is the dedup, so there's no separate table and a full audit trail comes free.

Exercise 4 (Medium): Your Kafka consumer group has 3 consumers on a 3-partition topic. One partition's records are un-processable due to a bug. What happens, and what are your options?
Solution

What happens: that partition's consumer retries the bad record and cannot advance its offset, because a log consumer commits a single position per partition — it can't ack record 500 while leaving 499 unhandled. So:

P0: consumer A — healthy, lag 0
P1: consumer B — STUCK on the poison record, lag growing without bound
P2: consumer C — healthy, lag 0

~1/3 of traffic stops being processed. Aggregate lag looks "elevated"
rather than critical, which is why per-partition lag alerting matters —
an average across three partitions hides a fully stalled one.

Options, with trade-offs:

1. Fix the bug and redeploy. Correct but slow; lag grows the whole time. Fine if the fix is minutes away and the data isn't time-sensitive.

2. Divert to a DLQ and commit past it. Catch the exception, produce the record to a dead-letter topic, commit the offset, continue. Restores progress immediately. Cost: ordering for that key is now broken — later records for the same entity are processed while an earlier one sits in the DLQ. Whether that's acceptable is a domain question: for a state machine that would apply transitions out of order, it may be worse than stalling.

3. Skip the offset manually. Fast but silently discards data with no record. Only for genuinely worthless records, and I'd log the payload first.

4. Pause the partition, keep the others running. Explicitly accept a stalled partition while you fix the bug, rather than burning capacity on a retry loop. Preserves ordering; the lag is a known, bounded debt.

5. Retry topic with delay. Produce failures to a retries topic consumed on a delay, commit the main offset. Good middle ground for transient failures (a dependency is down), bad for genuine poison, which will just cycle.

What I'd actually do: distinguish transient from permanent failure in the consumer. Transient (timeout, 503 downstream) → bounded retry with jittered backoff, then a retry topic. Permanent (deserialisation error, schema violation, missing referenced entity) → straight to DLQ, because retrying is guaranteed to fail. Then decide the ordering question deliberately: if out-of-order application is unsafe for this data, stall the partition and page someone; if it's safe, DLQ and keep moving.

This is the structural weakness of log-based systems that broker queues don't have: SQS acks per-message, so one poison message never blocks its neighbours. Worth naming as the trade for the log's throughput and replay.

Exercise 5 (Hard): Design the notification pipeline for a social app: 50M users, a viral post can trigger 10M notifications in minutes, users have per-channel preferences (push/email/none), and notifications must not arrive twice.
Solution

Estimate first, because it determines the whole shape:

Viral event: 10M notifications in ~5 min = 300 s
   → 33,000 notifications/s sustained during the spike
Steady state: maybe 2,000/s
→ Peak is ~16× steady state. Provisioning for peak is wasteful;
  provisioning for steady state without a buffer drops notifications.
  This asymmetry is exactly what a queue is for.

Pipeline stages, each a separate queue so they scale and fail independently:

1. FAN-OUT SERVICE
   Consumes PostCreated. Looks up followers. Does NOT emit 10M
   messages one by one — it emits BATCHES:
      {post_id, follower_ids[1000], ...}
   → 10M/1000 = 10,000 batch messages instead of 10M individual ones.
   Batching here is the difference between a manageable topic and a
   40× throughput problem.

2. PREFERENCE FILTER
   Expands batches, joins each user's channel preferences (cached —
   this is a hot read path, ~33K lookups/s).
   Drops "none", routes the rest per channel.
   Filtering EARLY means downstream queues only carry real work.

3. PER-CHANNEL QUEUES  (separate, different characteristics)
   push  → high volume, low latency, cheap        → large worker pool
   email → lower volume, higher latency tolerance → rate-limited by
                                                    provider quotas
   sms   → expensive, strict rate limits          → small pool, priority

4. DELIVERY WORKERS
   Idempotent send + per-provider retry/DLQ.

No duplicates — the explicit requirement. At-least-once delivery is unavoidable, so dedupe at the point of send:

notification_id = hash(user_id, post_id, channel)   -- DETERMINISTIC
                                                    -- so a retry
                                                    -- computes the same id
BEGIN;
  INSERT INTO sent(notification_id) VALUES ($1);   -- unique → dup fails
  -- then call the provider with idempotency_key = notification_id
COMMIT;

The deterministic ID is the crux: derived from stable inputs, not generated per attempt, so a redelivered batch produces identical IDs and the unique constraint catches it. Pass the same value as the push/email provider's idempotency key so the provider dedupes too — belt and braces, since the provider call can't join my transaction.

Handling the 16× spike:

• Autoscale on queue depth, not CPU — workers waiting on provider APIs have low CPU while the queue explodes.
• Priority separation: a viral post's "someone you follow posted" notifications are low-priority; "your payment failed" is high. Separate queues, so bulk fan-out can never delay transactional messages. Without this, one viral post delays everyone's password resets.
• Accept latency, not loss: during a spike, notifications arriving over 10 minutes instead of 30 seconds is fine. That's the queue doing its job — converting a capacity problem into a latency one.
• Time-based relevance: drop notifications older than, say, 1 hour rather than delivering stale ones — a "trending now" push from two hours ago is worse than nothing. Encode a TTL in the message.

Ordering: mostly unnecessary here, and that's worth stating as a deliberate choice — notifications from different posts are independent, so I keep full parallelism. The exception is coalescing: 50 likes on one post should become "50 people liked your post", not 50 pushes. Do that with a short windowed aggregation keyed by (user, post) before the delivery stage — which also cuts the delivery volume dramatically for exactly the viral case that stresses the system.

Failure modes to design for: the push provider being down (retry with backoff, DLQ, and crucially don't let email delivery stall behind it — separate queues already handle this); the preference cache going cold at 33K lookups/s (pre-warm, and fail open to "send push only" rather than blocking the pipeline); and the fan-out service dying mid-batch (batches are idempotent by deterministic ID, so simply reprocess).

Exercise 6 (Hard): A team wants "exactly-once processing" for a pipeline that reads from Kafka, calls a third-party API, and writes to Postgres. Explain what's achievable and design the best available solution.
Solution

What's achievable: not exactly-once. The pipeline has three participants that cannot share a transaction, and there are two unavoidable uncertainty windows:

Kafka offset commit ──?── third-party API call ──?── Postgres write

Window 1: API call succeeds, process crashes before recording it
          → on restart, was the API called? UNKNOWABLE locally.
Window 2: Postgres write commits, offset commit fails
          → the record is reprocessed.

Kafka's "exactly-once semantics" does NOT cover this: it makes
Kafka→Kafka atomic (transactional offsets + output records). The moment
a side effect leaves Kafka — an HTTP call, a Postgres write — that
atomicity ends.

What to build instead — effectively-once, with the uncertainty pushed to places that can resolve it:

1. Make the third-party call idempotent via a provider-side key. This is the only way to resolve Window 1, because it's the only participant that knows whether it already acted:

idempotency_key = f"{topic}:{partition}:{offset}"   -- or a business key
                                                    -- stable across retries
POST /charge  Idempotency-Key: orders:3:558123
→ a retry returns the ORIGINAL result rather than acting again.

If the provider doesn't support idempotency keys, that's a hard limitation to surface explicitly — you then need a local "attempted" record written before the call plus a reconciliation process that queries the provider afterwards to determine what actually happened. Say this out loud rather than pretending the problem is solved.

2. Collapse the offset commit into the Postgres transaction. This eliminates Window 2 entirely — store the consumed offset in Postgres rather than in Kafka:

BEGIN;
  INSERT INTO processed(topic, partition, offset) VALUES (...);  -- unique
  INSERT INTO results(...) VALUES (...);          -- the actual output
COMMIT;

On startup, seek() each partition to the offset stored in Postgres.
Now "work done" and "offset advanced" are ONE atomic fact, and Kafka's
own offset store is bypassed. A duplicate delivery hits the unique
constraint and is skipped.

3. Order the steps so failures are recoverable rather than ambiguous.

read record
  → BEGIN; insert intent(offset, state='pending'); COMMIT;
  → call API with idempotency key (retry safely — provider dedupes)
  → BEGIN; update intent state='done'; insert results; COMMIT;

A crash anywhere leaves a 'pending' row naming exactly what was in
flight. On restart: re-drive it. The API call is safe to repeat, so
re-driving converges. No state is ever unknown — only unfinished.

4. Reconciliation as the backstop. A periodic job compares 'pending' rows older than N minutes against the provider's records and resolves them. This is what makes the system genuinely trustworthy: not that failures can't happen mid-flight, but that every mid-flight state is detectable and resolvable.

What I'd tell the team: reframe the goal. "Exactly-once" is not a property you can buy at the transport layer, and chasing it there wastes effort. The achievable and equally valuable property is "every message is processed at least once, and processing is idempotent, so the observable outcome is as if exactly once." That requires: a deterministic idempotency key, provider-side deduplication, offsets committed atomically with output, and reconciliation for the residue. Each piece is simple; the discipline is refusing to skip any of them.

🎯 Key Takeaways

  • Async messaging decouples in three ways — temporal, load and logical. Keep only correctness-critical work synchronous, so downstream outages become latency instead of failure.
  • Queue = competing consumers (each message once, scale throughput). Pub/sub = broadcast (every subscriber gets everything, scale reactions).
  • Kafka is both: across consumer groups it's pub/sub, within a group it's a queue. Partition count caps in-group parallelism, and retention is what makes replay possible.
  • The real log-vs-broker difference is who owns the cursor — a stateless broker with consumer-held offsets buys throughput and replay but makes per-message retry the consumer's problem.
  • Exactly-once delivery is impossible. A lost ack is indistinguishable from a dead consumer, so the broker must choose duplicates or loss.
  • At-least-once + idempotent consumers = effectively-once. Idempotency is a requirement of every consumer, not an optimisation.
  • Dedup must be atomic with the side effect. "Check then act" has both a crash window and a concurrency race — let a unique constraint enforce it inside one transaction.
  • Push idempotency to the resource (provider idempotency keys) for side effects you can't enroll in your transaction.
  • The dual-write problem loses events silently. Use a transactional outbox or CDC so the event commits atomically with the state change.
  • Ordering is per-partition and costs you three things: parallelism capped by the key, hot partitions, and head-of-line blocking. Question whether you need it — versioned events or state snapshots often make order irrelevant.
  • Bounded retries with jittered backoff, then a DLQ — and alert on DLQ depth, or it's just a slower silent drop.
  • Autoscale on queue depth or consumer lag, never CPU, and alert per-partition, since aggregate lag hides one stalled partition.
