Data Platforms (CDC, Event Sourcing) Senior / Staff

What you'll master: how to keep derived stores — caches, search indexes, analytics warehouses — in sync with a source of truth without the dual-write problem, the operational realities of CDC that tutorials omit, when event sourcing genuinely pays for itself and when it's a costly mistake, and why "exactly-once" stream processing means something narrower than it sounds.

Prerequisites: Pub/Sub (dual writes, the outbox pattern), Caching (invalidation), Replication (WAL). Referenced throughout the case studies wherever a derived store needed updating.

🎯 What this topic is really testing. Whether you recognise that "keep the search index in sync" is the dual-write problem in disguise, and that the robust answer removes the second write entirely rather than making it more reliable. The secondary signal is restraint: event sourcing is genuinely powerful and genuinely expensive, and proposing it for a CRUD domain is a common way to make a system permanently harder to work on.

1. The Problem: Derived Data Goes Stale

A single logical change must reach several stores:

   user updates their profile
      → primary database    (source of truth)
      → search index        (so they're findable)
      → cache               (so reads are fast)
      → analytics warehouse (so reporting is current)
      → recommendation features

THE NAIVE APPROACH — the application writes to each:

   db.update(user)
   search.index(user)      ← what if this fails?
   cache.invalidate(user)  ← or this?
   analytics.send(user)    ← or the process crashes here?

Any partial failure leaves stores permanently inconsistent, with NO
automatic recovery. This is the DUAL-WRITE PROBLEM, and it does not
get better with retries — a crash between two writes leaves no record
of the intent to perform the second.

The insight that resolves it: don't write twice — write once and derive the rest. Both CDC and event sourcing are ways of doing that, differing in what the single write goes to.

2. Change Data Capture: Derive Events From the Database

Every database already records every write in its own log for crash
recovery — Postgres's WAL, MySQL's binlog, MongoDB's oplog. CDC tails
that log and publishes each change as an event.

   app → INSERT/UPDATE/DELETE → database
                                   │
                                   ├─ (already writes to the WAL for
                                   │   its own durability)
                                   │
                              Debezium tails the WAL
                                   │
                                   ▼
                                 Kafka
                          ┌────────┼────────┐
                          ▼        ▼        ▼
                     search    cache    warehouse

THE KEY PROPERTY: there is only ONE write — to the database. The
event stream is DERIVED from what the database actually committed,
so it cannot diverge from it. Application code is unchanged, and
cannot forget to publish.
CDCApplication publishes events
Dual-write riskNone — one write, events derivedReal — a crash between write and publish loses the event
Code changesNoneEvery write site must publish
Event shapeMirrors table structure — leaks your schema to consumersYou control it — domain events, not rows
Semantics"This row changed" — what, not why"OrderCancelled by customer" — carries intent
OpsReplication slots, connector lag, schema driftSimpler infrastructure, harder correctness

The transactional outbox sits between them and is often the best answer: the application writes its domain event to an outbox table in the same transaction as the state change, and CDC publishes from that table. You get atomicity from the database and meaningful domain events rather than raw row diffs — see Pub/Sub for the mechanics.

3. Deep Dive: CDC's Operational Realities

The concept is simple; running it is where the difficulty lives, and these are the things tutorials omit:

ConcernReality
Replication slots pin WALIn Postgres, an inactive slot prevents WAL cleanup — so a stopped connector fills the primary's disk and takes the database down. This is the classic CDC outage, and it requires alerting on slot lag as a first-class metric.
Initial snapshotA new connector must first read the entire table, then switch to streaming. On a large table this takes hours and adds significant load, and the handover must not lose or duplicate changes.
Schema changesAn ALTER TABLE changes the event shape mid-stream. Consumers must tolerate it, which is why a schema registry with compatibility rules matters.
DeletesA delete event carries only the primary key by default — the old values are gone unless the table has REPLICA IDENTITY FULL, which costs write throughput.
OrderingGuaranteed per table/partition, not globally. Two related rows in different tables can arrive out of order.
At-least-onceConnector restarts replay from the last committed offset, so consumers will see duplicates and must be idempotent.
⚠️ The failure mode worth memorising: a CDC connector that stops consuming doesn't just fall behind — in Postgres it actively endangers the primary database, because the replication slot prevents WAL segments from being recycled until they're consumed. A connector down for a weekend can fill the disk and take down the source system it was only supposed to observe. Alert on replication slot lag, and configure max_slot_wal_keep_size so the database protects itself by dropping the slot rather than dying.

4. Event Sourcing: The Log Is the Source of Truth

TRADITIONAL:  store current state; history is lost
   accounts: { id: 5, balance: 150 }
   → you know the balance. You do NOT know how it got there.

EVENT SOURCED: store the events; state is DERIVED
   events: [ Deposited(100), Deposited(75), Withdrew(25) ]
   balance = fold(events) = 150

   The audit trail is not a feature you added — it IS the data.
BenefitCost
Complete audit trail, inherentlyReading current state means replaying history — needs snapshots
Point-in-time reconstruction ("what did this look like on 3 March?")Events are immutable and permanent, so GDPR erasure is genuinely hard
New read models by replaying history — you never lost the informationSchema evolution is permanent: you must read every version of every event, forever
Natural fit for domains that are inherently event-shaped (ledgers, orders)Significantly higher conceptual load; queries are indirect
Debugging: you can see exactly what happenedFixing bad data means compensating events, not UPDATE statements

The GDPR point deserves emphasis because it's often discovered too late: an append-only, immutable event log conflicts directly with a right to erasure. The practical resolution is crypto-shredding — encrypt personal data within events using a per-subject key, and delete the key to render it unreadable, as covered in Security. Retrofitting that onto an existing event store is painful, so it's a design-time decision.

Snapshots make reads tractable: periodically persist the folded state at a known version, and replay only the events after it. Snapshots are a cache — always recomputable from the log — so a corrupt snapshot is never a loss of truth.

5. Deep Dive: When Event Sourcing Is Wrong

❌ Event sourcing everything 
UserProfileUpdated,
UserAvatarChanged,
UserTimezoneSet, ...

For a CRUD domain this buys
almost nothing and costs a lot:

- every read replays or hits a
  snapshot
- every schema change is forever
- new engineers face a much
  steeper model
- "just update the row" becomes
  a compensating event
✅ Event source selectively 
Ledger / payments  → yes.
   audit is a legal requirement,
   the domain IS a sequence of
   events, and correction by
   compensating entry is how
   accounting already works.

User profiles      → no.
   a CRUD table with an audit
   log column is simpler and
   sufficient.

Use it where the DOMAIN is
event-shaped, not everywhere.

The test: would a domain expert describe this as a sequence of things that happened, or as a current state that changes? An accountant thinks in transactions; a user thinks of their profile as a thing with a current value. Match the model to the domain, not to the architecture you find interesting.

CQRS pairs naturally with event sourcing — writes append events, reads are served from denormalised projections built by consuming them. Note it's independent though: you can have CQRS without event sourcing (read replicas with different schemas), and it carries its own cost, since read models are eventually consistent with writes and users notice "I saved it but don't see it".

6. Deep Dive: Batch, Streaming, and "Exactly-Once"

BatchStreaming
LatencyMinutes to hoursSub-second to seconds
EfficiencyHigher — amortises overhead over large chunksLower per event
ReprocessingNatural — just run it againRequires replaying the stream
CorrectnessEasier — the full dataset is availableHarder — late and out-of-order events
Use forReports, model training, large aggregations, correctionsFraud detection, live dashboards, cache invalidation, feature updates

The hard part of streaming is time. Batch sees a complete dataset; streaming must decide when a window is "done" despite events arriving late:

EVENT TIME  — when it actually happened
PROCESSING TIME — when your system saw it

A mobile client offline for an hour uploads events with timestamps
from an hour ago. Your 10:00-11:00 window "closed" at 11:00, and
now an 10:30 event arrives at 11:45.

WATERMARKS: an assertion that "no events older than T will arrive".
   Emit results when the watermark passes the window's end.
   ALLOWED LATENESS: keep the window open a little longer.
   Beyond that → route to a side output for later correction, or drop.

This is why batch remains valuable: it can reprocess with complete
data and correct what streaming approximated — the "fast-approximate
now, precise-later" pattern, the same shape as the offline/online
split in recommendations.

"Exactly-once" in stream processing means something narrower than it sounds. As established in Pub/Sub, exactly-once delivery is impossible. What Flink and Kafka Streams provide is exactly-once state updates: consumer offsets and processing state are committed atomically, so a failure and restart doesn't double-count within the pipeline. The moment the pipeline produces an external side effect — an HTTP call, a write to another system — you are back to at-least-once and need idempotency.

Interview Questions

🟢 Beginner — How do you keep a search index in sync with the database?

With Change Data Capture — tail the database's own write-ahead log and publish each change as an event that the indexer consumes.

app → INSERT/UPDATE → database → WAL (already written, for durability)
                                    ↓
                              Debezium tails it
                                    ↓
                                  Kafka → search indexer

Why not have the application update both? That's the dual-write problem:

db.update(user)
search.index(user)     ← if this fails, or the process crashes here,
                          the index is permanently stale and nothing
                          knows to fix it.

Retries don't solve it, because a crash between the two writes leaves no record that the second was intended. The index silently diverges, and you discover it when a user complains they can't be found.

CDC eliminates the problem structurally: there is only one write — to the database — and the event stream is derived from what actually committed. Application code can't forget to publish, because it isn't publishing.

Two things to add: consumers must be idempotent, because connector restarts replay from the last committed offset and duplicates are guaranteed. And the index is eventually consistent — typically milliseconds to seconds behind — so anything requiring read-your-own-writes must query the primary, not the index.

If you want domain events rather than raw row changes, use the transactional outbox: write the event to an outbox table in the same transaction as the state change, and have CDC publish from there. Atomicity from the database, meaningful events for consumers.

🟢 Beginner — What is event sourcing, and what does it cost?

Event sourcing stores the sequence of events as the source of truth and derives current state by folding them, rather than storing current state and losing the history.

Traditional:    accounts { id: 5, balance: 150 }
                → you know the balance, not how it got there.

Event sourced:  [ Deposited(100), Deposited(75), Withdrew(25) ]
                balance = fold(events) = 150
                → the audit trail IS the data, not a feature bolted on.

The benefits: a complete audit trail inherently; point-in-time reconstruction ("what did this look like on 3 March?"); and the ability to build new read models later by replaying history, because you never discarded the information.

The costs, which are substantial:

• Reads require replay, so you need periodic snapshots to keep them tractable.
• Schema evolution is permanent — you must be able to read every version of every event you ever wrote, forever.
• Deletion is genuinely hard. An immutable log conflicts with the right to erasure; the practical answer is crypto-shredding, and retrofitting it is painful.
• Fixing bad data means compensating events, not UPDATE statements.
• Higher conceptual load for everyone who joins the team.

So use it selectively. The test is whether a domain expert would describe the thing as a sequence of events or as a current state — an accountant thinks in transactions, a user thinks of their profile as a thing with a current value. Ledgers and orders are event-shaped; user profiles are not.

🟡 Mid — Your CDC connector has been down for two days. What's the impact?

The consumers being stale is the obvious problem. The dangerous one is the source database.

1. Derived stores are two days behind — the search index, cache and warehouse reflect two-day-old data. Bad, but recoverable: when the connector restarts it resumes from its last committed offset and catches up.

2. The replication slot is pinning WAL — this is the real emergency. In Postgres, an inactive replication slot prevents WAL segments from being recycled, because the database must retain everything the slot hasn't consumed:

Two days of WAL at, say, 50 GB/day = 100 GB of retained WAL that
cannot be cleaned up.

If the disk fills → the primary database STOPS ACCEPTING WRITES.

An observability component has taken down the system it was only
meant to observe.

3. Catch-up is a load spike. Restarting means processing two days of changes as fast as possible, which floods Kafka and the consumers, and can overwhelm the search cluster.

What to do now: check disk headroom on the primary first — that's the outage risk. If it's critical, drop the slot to save the database and accept re-snapshotting later; a slow rebuild is far better than a write outage. Otherwise restart the connector and throttle its catch-up rate.

What should have prevented it:

• Alert on replication slot lag as a first-class metric, not connector uptime.
• Set max_slot_wal_keep_size so the database invalidates a slot rather than filling its disk — it fails the CDC pipeline instead of the primary, which is the correct priority.
• Alert on consumer lag in Kafka as well.

The general lesson: a component that observes your database can become a dependency of it. CDC looks read-only and isn't — that's the non-obvious operational fact about it.

🟡 Mid — CDC or application-published events? When would you choose each?
CDCApp-published
Dual-write riskNoneReal — crash between write and publish
Code changesNoneEvery write site
Event semantics"Row changed" — what"OrderCancelled by customer" — why
CouplingLeaks table schema to consumersYou control the contract

CDC when you can't change the application (a legacy system, a third-party product), when you need guaranteed completeness (no code path can bypass it), or when adding consumers to an existing system without touching it.

App-published events when consumers need intent rather than row diffs. A row changing from active to cancelled doesn't tell you whether the customer cancelled, a fraud check triggered, or payment failed — and downstream consumers often need exactly that distinction.

The synthesis is usually right: the transactional outbox. Write the domain event to an outbox table in the same transaction as the state change, and let CDC publish from that table.

BEGIN;
  UPDATE orders SET status='cancelled' WHERE id=42;
  INSERT INTO outbox(topic, payload)
    VALUES ('orders', '{"type":"OrderCancelled","reason":"customer"}');
COMMIT;                 ← atomic: both or neither

CDC publishes from `outbox` → consumers get DOMAIN events with no
dual-write risk.

Why this is the best of both: atomicity comes from the database (so nothing can be lost), and the event shape is yours (so you can refactor tables without breaking consumers). The cost is an extra table and a pruning job for published rows.

The wider principle: don't leak your internal schema as a public contract. Raw CDC events couple every consumer to your table structure — which is the same expand/contract hazard as API versioning, just less visible.

🔴 Senior — When is event sourcing genuinely worth it, and when is it a mistake?

Worth it when the domain is inherently event-shaped and history has independent value:

• Financial ledgers. Accounting already works this way — you never edit a posted entry, you post a correcting one. Event sourcing matches how domain experts already think, and the audit trail is a legal requirement rather than a nice extra.
• Order lifecycles. An order genuinely is a sequence of events (placed, paid, picked, shipped, delivered, returned), and disputes require knowing exactly what happened when.
• Regulated domains where "who changed what, when, and why" must be provable.
• Systems needing temporal queries — "what was our exposure at market close on 3 March?" — which are painful without stored history.

A mistake when the domain is CRUD. User profiles, settings, product catalogues: a user thinks of their profile as a thing with a current value, not a stream of changes. You pay every cost — replay, snapshots, permanent schema compatibility, harder deletion, steeper onboarding — for an audit log you could have achieved with a history table.

The costs that bite hardest in practice:

1. Schema evolution is forever. Version 1 of an event written in 2020 must still be readable in 2030, because it's still in the log and still needed to rebuild projections. Every event type accumulates versions and upcasting logic.

2. GDPR conflicts fundamentally with an immutable log. Crypto-shredding works — encrypt personal fields per subject, delete the key — but retrofitting it is very painful, so it must be a design-time decision.

3. Corrections require compensating events, which means every bug fix is a domain-modelling exercise rather than an UPDATE.

4. Team velocity. New engineers take much longer to become productive, and that cost is permanent and rarely counted.

The pragmatic middle ground I'd usually recommend: a normal CRUD model, plus an append-only audit/history table, plus CDC to publish domain events. You get the audit trail and the event stream without making every read a replay — capturing most of the value at a fraction of the cost. Reserve full event sourcing for the bounded contexts that genuinely need it, rather than applying it system-wide.

🔴 Senior — What does "exactly-once" mean in stream processing, and what doesn't it cover?

It means exactly-once state updates within the processing framework — not exactly-once delivery, which is impossible.

What it does cover: Flink and Kafka Streams commit consumer offsets atomically with their internal processing state (and, for Kafka-to-Kafka, with output records). So if a job fails and restarts, it resumes from a consistent checkpoint — no double-counting in an aggregation, no lost updates in a windowed computation.

read offset 100 → update state → write output → commit offset 101
   all in ONE atomic transaction

A crash before the commit means the whole step is retried from
offset 100 with the previous state — so the aggregate is correct.

What it does not cover — the moment a side effect leaves the system:

• An HTTP call to a third party. Charging a card, sending an email, calling an external API — none of these can join the framework's transaction. A crash after the call but before the commit means the call is repeated on restart.
• A write to an external database that isn't participating in the checkpoint protocol.
• Anything observed by a human — a notification sent twice is sent twice.

Why this is fundamentally so: exactly-once delivery would require an atomic commit across systems that cannot share a transaction. As established in Pub/Sub, a lost acknowledgement is indistinguishable from a dead consumer, so the choice is always duplicates or loss.

What to do at the boundary: idempotency keys derived deterministically from the input (offset, or a business key), passed to the external system so it deduplicates — the same push-safety-to-the-resource principle as fencing tokens and payment idempotency. Plus a transactional sink where the target supports it (some databases can participate in a two-phase commit with Flink).

The framing I'd give a team: "exactly-once" is a marketing-adjacent term for a real but narrow guarantee. Read it as "the pipeline's internal state is correct across failures", and treat every external effect as at-least-once requiring idempotency. Teams that read it as an end-to-end guarantee ship double-charges.

🏋️ Graded Exercises

Exercise 1 (Easy): Why is "write to the DB, then publish an event" unsafe? Name the failure and the fix.
Solution

The failure is the dual-write problem:

BEGIN; UPDATE orders SET status='paid'; COMMIT;   ← succeeded
kafka.publish(OrderPaid)                          ← process crashes here

The database says paid. No event was published. Downstream systems —
inventory, notifications, analytics — never learn.

And nothing can fix it: no record exists of the INTENT to publish, so
no retry mechanism has anything to retry.

Reversing the order doesn't help either — publishing first and then crashing before the commit means consumers react to an order that doesn't exist.

The fix is to eliminate the second write. Two options:

1. CDC — tail the database's WAL and derive events from what actually committed. One write, events derived, no divergence possible. Best when you can't change the application, or want guaranteed completeness.

2. Transactional outbox — write the event into an outbox table in the same transaction as the state change, and have a relay (usually CDC) publish from it:

BEGIN;
  UPDATE orders SET status='paid' WHERE id=42;
  INSERT INTO outbox(topic, payload) VALUES ('orders', {...});
COMMIT;                     ← atomic: both or neither

The relay may publish twice if it crashes after publishing but before marking the row — that's at-least-once, which idempotent consumers already handle. What it can never do is lose the event.

Why not 2PC across the database and Kafka? It couples their availability (all-of-N), holds locks across the network, and is operationally painful — the same trap as distributed transactions in microservices.

Exercise 2 (Easy): An event-sourced account has 10 million events. How do you read the balance quickly?
Solution

Snapshots. Periodically persist the folded state at a known version, then replay only the events after it.

WITHOUT snapshots:
   balance = fold(all 10,000,000 events)
   → seconds per read, growing forever. Unusable.

WITH snapshots every 1,000 events:
   snapshot { version: 9,999,000, balance: 45,231 }
   balance = snapshot.balance + fold(events after 9,999,000)
   → fold at most 1,000 events. Milliseconds, and BOUNDED
     regardless of history length.

The key property: a snapshot is a cache, not a source of truth. It's always recomputable from the log, so a corrupted or lost snapshot costs performance, never correctness. That means you can regenerate them freely, and a bug in snapshot logic is recoverable — which is not true of a system that stores state directly.

Choosing the interval trades storage against read latency: every 100 events means fast reads and more snapshots; every 10,000 means fewer snapshots and slower reads. Snapshot on a count threshold rather than time, so busy aggregates get them more often.

The versioning trap: a snapshot is a serialisation of your state model, so when that model changes, old snapshots may be unreadable. The safe approach is to version snapshots and discard incompatible ones — you can always rebuild from the log, which is exactly why treating them as a cache matters.

For very large aggregates, consider whether the aggregate boundary is right — 10 million events on one account may indicate it should be split (per-year sub-accounts, say), the same bounded-partition instinct as bucketing in chat.

Exercise 3 (Medium): Design the pipeline keeping a search index in sync. Handle failures.
Solution 
Postgres → (WAL) → Debezium → Kafka topic (partitioned by entity id)
                                    ↓
                              indexer consumers
                                    ↓
                              Elasticsearch

Design decisions:

1. Partition by entity ID so all changes to one document go to the same partition and are processed in order. Without this, an update and a delete for the same entity can be applied out of order — resurrecting deleted documents.

2. Idempotent indexing. CDC is at-least-once, so duplicates are guaranteed. Use the entity's ID as the document ID and index with a version (the WAL position or a row version), so Elasticsearch rejects out-of-order or repeated writes:

PUT /index/_doc/{id}?version={lsn}&version_type=external
   → an older version is rejected, so replays and reordering are safe

3. Handle failures per type:

Transient (ES unavailable, 429)
   → retry with jittered backoff; consumer lag grows but nothing is lost
Permanent (malformed document, mapping conflict)
   → DLQ + alert. Do NOT block the partition indefinitely on one
     poison document, and do not silently skip it either.
Consumer crash
   → restart from the last committed offset; idempotency makes the
     replay safe

4. Monitoring: replication slot lag (the database-endangering one), Kafka consumer lag, DLQ depth, and — most usefully — an end-to-end freshness probe that writes a row and measures how long until it's searchable.

5. Rebuild capability. You will eventually need to reindex from scratch — a mapping change, a bug, a corrupted index. Build it into the design: snapshot the table into a new index, switch an alias atomically, delete the old one. Systems without a tested rebuild path discover they need one at the worst time.

The consistency to state plainly: the index is eventually consistent, typically milliseconds to seconds behind. Anything needing read-your-own-writes must query the primary.

Exercise 4 (Medium): A stream job computes hourly aggregates. Events arrive up to 30 minutes late. Design the windowing.
Solution

Use event time, not processing time — otherwise a late event lands in the wrong hour and both hours are wrong.

EVENT TIME:      when it actually happened (in the payload)
PROCESSING TIME: when your job saw it

A mobile client offline for 40 minutes uploads events timestamped
10:15. If you bucket by arrival, they count toward the 11:00 hour —
corrupting two windows at once.

Watermarks and allowed lateness:

WATERMARK: an assertion that "no events with event time < T will
   arrive". With observed lateness up to 30 minutes:
      watermark = max_event_time_seen − 30 minutes

The 10:00-11:00 window is triggered when the watermark passes 11:00 —
i.e. once we've seen events timestamped ~11:30.

ALLOWED LATENESS (say a further 15 min): keep window state and EMIT
   AN UPDATED RESULT if a straggler arrives. Downstream consumers
   must handle updates, so the sink should be idempotent/upsert.

BEYOND that: route to a SIDE OUTPUT rather than dropping silently —
   you want to know how much you're missing, and it can feed a batch
   correction.

The trade-off to state explicitly: a longer watermark delay means more complete results and higher latency. Waiting 30 minutes to close an hourly window is a real product cost — so consider emitting a provisional result at the hour boundary and a corrected one later, which is the fast-approximate-then-precise pattern that recurs throughout this track.

Watch window state size: keeping windows open for 45 minutes means holding state for several concurrent windows. With high cardinality (per-user aggregates) that can be substantial, and it's the usual cause of stream-job memory problems.

And keep a batch correction pass that reprocesses the day's complete data. Streaming gives speed; batch gives correctness with full information. Using both deliberately is the point of hybrid architectures.

Exercise 5 (Hard): You need to add a new projection over 3 years of events without stopping the live system. Design the migration.
Solution

This is where event sourcing genuinely pays off — the information you need is already there, which would be impossible in a state-only system.

PHASE 1 — Build offline against a snapshot
   1. Note the current stream position, P.
   2. Replay events from the beginning to P, building the new
      projection in a SEPARATE store. Hours or days; no impact on
      live traffic since it reads the immutable log.
   3. Throttle the replay so it doesn't starve live consumers.

PHASE 2 — Catch up
   4. Start a consumer from position P and let it process forward
      until its lag approaches zero. It is now live-but-hidden.

PHASE 3 — Verify before switching
   5. Run BOTH projections in parallel and compare outputs on real
      traffic. This is the step that makes the migration safe, and
      the one most often skipped.
   6. Investigate discrepancies — they usually reveal a bug in the
      new projection logic, occasionally in the old one.

PHASE 4 — Switch
   7. Route reads to the new projection behind a feature flag,
      ramping 1% → 10% → 100%.
   8. Keep the old projection running for a rollback window, then
      decommission.

Complications to handle:

• Event schema evolution. Three years of events include old versions. The new projection must handle every historical shape — upcasting old events to current form, which is a real cost of event sourcing and precisely why schema versioning must be disciplined from the start.
• Replay throughput. Three years may be billions of events. Parallelise by partition, and consider replaying from an archived copy rather than the live cluster.
• Non-deterministic logic. If the projection calls external services or uses wall-clock time, replay produces different results than the original processing. Projections should be pure functions of the event stream — a design constraint that must be enforced from the outset.
• Ordering. Replay must preserve per-entity ordering, so parallelism must partition on the same key as the live stream.

The point worth making: "add a new read model over historical data" is trivial here and effectively impossible in a state-only system, where the historical information simply doesn't exist. This is the strongest argument for event sourcing — and it's worth weighing honestly against its costs rather than treating it as a general-purpose default.

Exercise 6 (Hard): A regulator requires deletion of a user's personal data. Your event log is immutable. Resolve this.
Solution

This is the fundamental tension in event sourcing: an append-only immutable log versus a legal right to erasure. It cannot be resolved by deleting events, because projections and downstream consumers depend on the log's integrity — and in practice the events also exist in backups, replicas and archives you cannot practically rewrite.

The standard resolution: crypto-shredding.

Encrypt personal data WITHIN events using a per-subject key:

   { type: "UserRegistered",
     user_id: 4821,                       ← pseudonymous, retained
     encrypted_pii: "a8f3c2...",          ← name, email, address
     key_id: "user-4821-key" }

The key lives in a separate key store, NOT in the log.

TO DELETE: destroy the key.
   → every copy of that event — in the log, in backups, in replicas,
     in archives — becomes permanently unreadable.
   → the event STRUCTURE remains, so projections and ordering are
     intact and the log is not rewritten.

Why this satisfies the requirement: regulators generally accept that data rendered permanently irrecoverable is erased. It's the same mechanism used for GDPR compliance across immutable backup estates, as covered in Security.

What you must design in advance:

• Separate personal from non-personal fields at event-design time. Encrypting the whole event breaks projections that need non-personal fields (amounts, timestamps, state transitions).
• Key management with stronger durability than the data — losing a key is unrecoverable data loss, so the key store needs its own backups and a tested restore.
• Handle existing projections: derived read models may contain decrypted personal data and must be purged separately. Crypto-shredding the log doesn't clean the projections.
• Audit the deletion — record that the key was destroyed, when, and under what request.

The alternatives, and why they're worse: rewriting the log (breaks immutability, invalidates snapshots and downstream offsets, and is infeasible across backups); tombstone events that "mark as deleted" (the data is still readable — this does not satisfy erasure); or never storing personal data in events at all, keeping it in a mutable side table referenced by ID (clean, and a legitimate design, though it means events alone can't reconstruct full state).

The honest framing: this must be a design-time decision. Retrofitting crypto-shredding onto a mature event store is a large, risky project — which is one of the strongest practical arguments for not event-sourcing domains containing personal data unless you've planned for it from the start.

🎯 Key Takeaways

  • Dual writes cannot be made safe by retrying — a crash between two writes leaves no record of the intent. Remove the second write instead.
  • CDC derives events from the database's own log, so events can never diverge from what actually committed, and no code path can forget to publish.
  • A stopped CDC connector can take down the primary database by pinning WAL — alert on replication slot lag and cap WAL retention.
  • The transactional outbox is usually the best of both: atomicity from the database, domain events rather than leaked row schemas.
  • CDC is at-least-once with per-table ordering — consumers must be idempotent and tolerate cross-table reordering.
  • Event sourcing makes the audit trail the data, and enables new read models by replaying history.
  • Its costs are permanent: replay needs snapshots, schema versions live forever, corrections are compensating events, and deletion conflicts with immutability.
  • Event-source where the domain is event-shaped (ledgers, orders), not where it's CRUD. Ask how a domain expert describes it.
  • Crypto-shredding resolves GDPR erasure — encrypt per subject, delete the key — but it must be designed in from the start.
  • Snapshots are a cache, always recomputable, so corruption costs performance not correctness.
  • Streaming needs event-time windowing with watermarks; batch remains valuable for correcting with complete data.
  • "Exactly-once" covers internal state, not external side effects — the boundary always needs idempotency.
