REST, API Contracts, Serverless Fundamentals

What you'll master: how to choose an API style from the caller rather than from fashion, why every schema change is an expand/contract migration, the exact mechanics of an idempotent endpoint (including the concurrency window most implementations get wrong), pagination that doesn't break under writes, and how to reason about serverless economics with real arithmetic instead of vibes.

Prerequisites: Back-of-Envelope Estimation, Caching Strategies, Pub/Sub vs Message Queues (idempotency at the consumer; this lesson covers it at the API edge). Feeds Microservices and Design a Rate Limiter.

1. REST vs gRPC vs GraphQL: Choose By Caller

StyleModelWire costBest forReal weakness
RESTResources + HTTP verbsJSON over HTTP/1.1 or 2Public APIs, CRUD, anything needing broad tooling and HTTP cachingOver/under-fetching; nested data means N+1 round trips
gRPCTyped remote procedure callsProtobuf over HTTP/2 — roughly 3–10× smaller than JSON, and faster to parseInternal service-to-service, high throughput, streamingNeeds codegen; not directly callable from a browser (needs grpc-web + a proxy); opaque to curl
GraphQLClient declares exactly the fields it wantsJSON, single round trip for nested dataMany heterogeneous clients (web/iOS/Android) with different data needsResolver N+1s; HTTP caching largely unavailable; a malicious deep query is a DoS vector
🎯 The framing that answers the question properly: match the style to the caller, not to your preference. Third parties you don't control → REST, because universal tooling and cacheability matter more than efficiency. Your own services, both ends deployed together → gRPC, because codegen is free and you want the wire savings. Mobile clients over a slow network with varying screens → GraphQL, because one round trip that fetches exactly the needed fields beats six REST calls. Large systems use all three: gRPC internally, REST at the public edge, GraphQL for the mobile BFF. "Which is best" is the wrong question.

The N+1 problem, since it's the failure mode in two of the three styles:

REST — under-fetching forces the client to loop:
   GET /orders            → 50 orders
   GET /users/{id}   ×50  → 50 more round trips
   → 51 requests. At 50 ms each over mobile: 2.5 s.
   Fixes: an expansion parameter (?include=user), a purpose-built
   aggregate endpoint, or a BFF that composes server-side.

GraphQL — the client asks once, but the SERVER loops:
   { orders { id user { name } } }
   → naive resolvers issue 1 query for orders + 50 for users.
   The N+1 moved from the network to your database.
   Fix: DataLoader-style batching — collect the IDs requested within
   one tick and issue a single  WHERE id IN (...)  query.

GraphQL doesn't remove N+1; it relocates it to where you can
actually fix it. That's the honest way to describe the benefit.

2. Deep Dive: API Contracts And The Expand/Contract Discipline

Once anyone else depends on your API, every change is a migration. The core asymmetry:

SAFE (backward-compatible) — old clients keep working:
   ✓ ADD an optional field to a response
   ✓ ADD an optional request parameter with a default
   ✓ ADD a new endpoint
   ✓ ADD a new enum value  ...if clients tolerate unknown values

BREAKING — someone's code stops working:
   ✗ REMOVE or RENAME a field
   ✗ CHANGE a type ("123" → 123, or scalar → array)
   ✗ ADD a required request field
   ✗ TIGHTEN validation (a previously-accepted value now 400s)
   ✗ CHANGE the meaning of an existing field   ← the worst, because
     it passes every schema check and silently corrupts behaviour

The expand/contract pattern — identical in shape to a database migration, which is why learning it once pays twice:

Goal: rename  "name"  →  "full_name"

EXPAND    Add full_name. Write BOTH fields on every response.
          Accept BOTH on every request. Nothing breaks; nothing removed.
MIGRATE   Ship clients that read/write full_name. Instrument the OLD
          field — log every request that still uses `name`, with the
          caller's identity. This telemetry is the whole point: it turns
          "has everyone migrated?" from a guess into a number.
CONTRACT  When usage of `name` hits zero (and stays there through a
          full business cycle — monthly batch jobs exist), remove it.

Never skip the instrumentation step. "We announced the deprecation"
is not evidence that anyone read it.
Versioning approachExampleTrade-off
URL path/v2/ordersMost common and most visible; trivially cacheable and routable. Tends toward whole-API version bumps for one endpoint's change.
HeaderAccept: application/vnd.api.v2+jsonKeeps URLs stable (purist REST). Invisible in logs and browsers, easy to forget, harder to debug.
Date-basedAPI-Version: 2026-07-30Stripe's model. Each client pins the date it integrated; the server maintains transformation layers between versions. Excellent for clients, significant sustained cost for you.
No version, evolve additively—Often the best choice. If you only ever make backward-compatible changes, you never need a v2. Versioning is what you do when you've failed to be additive.

Consumer-driven contract testing is what makes this safe in practice: each consumer publishes the subset of the response it actually depends on, and your CI fails if a change violates any consumer's expectations. That converts "I hope nobody used that field" into a test failure at build time — far cheaper than discovering it from a customer.

3. Deep Dive: Idempotency At The API Edge

Pub/sub covered idempotent consumers. The API edge has an extra requirement: you must return the same response to a retry, not merely avoid repeating the side effect.

First, what HTTP already gives you:

MethodIdempotent by spec?Note
GET, HEADYes (and safe — no side effects)Freely retried and cached by proxies, browsers, CDNs.
PUTYes"Set the resource to this state." Repeating it lands on the same state — which is why absolute writes beat relative ones.
DELETEYesSecond delete returns 404 or 204; the state is unchanged either way.
POSTNo"Create a new thing." Two POSTs mean two things. This is the one you must make idempotent yourself.
PATCHNot necessarily{"op":"increment","by":1} is not idempotent; {"status":"paid"} is. Depends entirely on your payload semantics.

The full mechanism, with the concurrency case that trips up most implementations:

POST /charges
Idempotency-Key: 4f3c-a91e-...        ← client generates ONCE, reuses on retry
{ "amount": 5000, "currency": "usd" }

Server logic:
 1. Look up the key.
    - Found + COMPLETED  → return the STORED response, status and body,
                           with  Idempotent-Replay: true
    - Found + IN_PROGRESS → return 409 Conflict (a retry arrived while the
                           original is still running — do NOT start a second)
    - Not found          → claim it and proceed
 2. Claim atomically:
       INSERT INTO idempotency(key, state, request_hash)
         VALUES ($1, 'IN_PROGRESS', $2);     -- unique key → race resolved
    A concurrent duplicate hits the constraint and takes the 409 path.
 3. Do the work. Persist the response body + status WITH the key,
    in the same transaction as the side effect where possible.
 4. Mark COMPLETED.

Three details that separate a correct implementation from a plausible one:

Store the response, not just a flag. The retry must receive the original 201 and the original charge ID. Returning "already processed" with no body forces the client to guess what happened — and clients guess wrong.

Hash the request body and compare it. If the same key arrives with a different body, that's a client bug (key reuse), and silently returning the old response hides it. Return 422 and name the problem.

Scope keys per API consumer and give them a TTL (24h is typical). Global keys let one tenant collide with another; keys kept forever grow unboundedly.

⚠️ The window that remains, and how to close it: if the client never receives your response — connection dropped after commit — it doesn't know whether the charge happened. The idempotency key makes the retry safe, which resolves it. But if the client also lost the key (process died before persisting it), the state is genuinely unknown to it. That's why serious APIs also offer a lookup by client reference ("GET /charges?client_ref=order-42") — so a client can always ask "did this happen?" rather than guessing. Idempotency handles retries; a query endpoint handles amnesia. Payment systems need both.

4. Deep Dive: Pagination, And Why Offset Breaks

Nearly every list endpoint gets this wrong at first, and the bug only appears under concurrent writes.

❌ Offset pagination 
GET /posts?limit=20&offset=40
SELECT ... LIMIT 20 OFFSET 40

Problem 1 — SKIPPED/DUPLICATED rows:
a new post is inserted at the top
between page 1 and page 2
→ everything shifts down one
→ the last item of page 1 becomes
  the first item of page 2.
The user sees a duplicate and
never sees one real row.

Problem 2 — O(offset) cost:
OFFSET 1000000 makes the database
count and discard a million rows
on EVERY request.
✅ Cursor (keyset) pagination 
GET /posts?limit=20
  &after=eyJpZCI6MTIzfQ

SELECT ... WHERE (created_at, id)
  < ($cursor_ts, $cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 20

- Stable under inserts: the cursor
  names a POSITION, not a count.
- O(log n) via the index — the same
  cost on page 1 and page 50,000.
- Requires a stable, unique sort
  key (hence the id tiebreaker).

Cost: no random access. You can't
jump to "page 500", only next/prev.

Two subtleties worth stating: the sort key must be unique, or rows sharing a timestamp get skipped at page boundaries — hence the composite (created_at, id). And the cursor should be opaque (base64-encoded) so clients can't construct one, which keeps you free to change its internals later. Encode enough to reconstruct the full sort position, not just the ID.

Offset pagination remains fine for small, bounded, mostly-static lists — an admin table of 200 categories doesn't need a cursor. As always, the point is knowing which failure you're accepting.

5. Status Codes And Error Contracts

Getting these right is cheap and immediately signals experience, because clients build retry logic on them:

CodeMeansShould the client retry?
400 Bad RequestMalformed syntaxNo — deterministic failure
401 / 403Not authenticated / not permittedNo (401 after refreshing a token, yes)
404Not foundNo
409 ConflictState conflict — version mismatch, or an idempotent request in flightSometimes — after re-reading state
422Syntactically valid, semantically wrongNo
429 Too Many RequestsRate limitedYes — after Retry-After
500Server bugCautiously — it may be deterministic
502 / 503 / 504Transient: bad gateway, overloaded, timeoutYes — with exponential backoff and jitter

The distinction that matters operationally: 4xx means "don't retry, the request is wrong"; 5xx means "the request may be fine, try again." Returning 500 for a validation error causes clients to hammer you with a request that can never succeed — a self-inflicted load amplifier during an incident.

Error bodies should be machine-readable, with a stable code the client can branch on:

{ "error": { "code": "insufficient_funds",     ← stable, safe to branch on
             "message": "Card was declined.",  ← human-readable, may change
             "request_id": "req_8f2a..." ,     ← for support correlation
             "retryable": false } }

Never make clients parse the message string. Message text is UI copy;
the code is the contract.

6. Serverless: The Economics, With Arithmetic

"Serverless is cheaper" and "serverless is expensive" are both true at different volumes. Compute the crossover rather than arguing about it:

Lambda-style pricing (order of magnitude):
   $0.20 per 1M requests  +  $0.0000166667 per GB-second

Workload: 100 ms average duration, 512 MB memory.
   GB-seconds per request = 0.5 GB × 0.1 s = 0.05
   Cost per request ≈ (0.20/1M) + (0.05 × 0.0000166667)
                    ≈ 0.0000002 + 0.00000083  ≈ $0.00000103

At 1M requests/month:      ~$1        vs a $30/mo container → SERVERLESS WINS
At 100M requests/month:    ~$103      vs $30/mo container    → container wins
At 1B requests/month:      ~$1,030    plus you'd need several containers,
                                       say $300 → CONTAINER WINS ~3×

Crossover is roughly 20–50M requests/month for this shape. Below it,
serverless is dramatically cheaper AND less work. Above it, you're
paying a large premium for elasticity you no longer need.
Serverless strengthCorresponding cost
Scales to zero — pay nothing when idleCold starts: 100 ms–1 s+ (worse for JVM/.NET, worse again inside a VPC). Provisioned concurrency removes it but also removes scale-to-zero, which was the point.
Scales out automatically and fastIt scales into your dependencies: 1,000 concurrent functions opening 1,000 database connections exhausts the pool. Needs a connection proxy (RDS Proxy) or a serverless-friendly datastore.
No servers to patch or capacity-planExecution limits (~15 min), payload limits, no local disk to speak of, and no long-lived state — no in-process cache, no warm connection pool you can rely on.
Per-request billing suits bursty trafficSustained high volume costs multiples of a provisioned container. Also: a runaway loop bills you rather than simply saturating a fixed server.
Event-source integrations are trivialVendor coupling in the event contracts; local testing and step-through debugging are genuinely harder.

Where serverless is clearly right: event-driven glue (an upload triggers thumbnailing), webhook receivers, cron jobs, low-and-spiky internal tools, and anything whose traffic is unpredictable enough that capacity planning is guesswork.

Where it's clearly wrong: sustained high-QPS services, latency-critical paths where a cold start blows the SLO, long-running or stateful work (WebSocket servers, big batch jobs), and anything needing a warm in-process cache — the L1 cache trick simply doesn't work when your process may not exist between requests.

🎯 Staff-level insight: the significant cost of serverless usually isn't the invocation bill, it's the architectural constraints leaking outward. No warm connection pool pushes you to a connection proxy. No in-process cache pushes more load onto Redis. A 15-minute ceiling pushes you to split jobs and orchestrate them. Each is manageable, but together they mean serverless isn't "the same app without servers" — it's a different design. Choose it for the elasticity, not to avoid thinking about infrastructure.

Interview Questions

🟢 Beginner — When would you choose gRPC over REST?

For internal service-to-service calls where you control both ends. Three reasons:

1. Wire efficiency. Protobuf is binary and schema-driven, typically 3–10× smaller than equivalent JSON and much cheaper to parse. At high internal call volumes that's real CPU and bandwidth.
2. Generated, typed clients. The .proto file is the contract, and codegen means a field rename is a compile error rather than a runtime undefined.
3. HTTP/2 features — multiplexing over one connection, and first-class bidirectional streaming, which REST handles awkwardly.

I'd stay with REST when the caller is a third party or a browser: universal tooling, debuggable with curl, cacheable by CDNs and proxies, and no codegen step for consumers. Browsers can't speak gRPC directly — you need grpc-web plus a translating proxy, which is friction you shouldn't impose on external developers.

The summary I'd give: gRPC optimises for machines that know each other; REST optimises for reach and debuggability. Most large systems use gRPC inside and REST at the edge.

🟢 Beginner — Which HTTP methods are idempotent, and why does it matter?

GET, HEAD, PUT and DELETE are idempotent per the HTTP spec; POST is not, and PATCH depends on your payload.

Idempotent means making the request N times leaves the same server state as making it once. PUT is idempotent because it sets a resource to a given state — applying that twice lands on the same state. DELETE is idempotent in terms of state: the second call may return 404, but the resource is equally gone. POST means "create a new thing", so two POSTs create two things.

Why it matters: networks fail in a way that hides the outcome. If a client sends a request and the connection drops before the response arrives, it cannot tell whether the server acted. Its only options are to retry (risking duplication) or not (risking loss) — the same dilemma as message delivery. For idempotent methods, retrying is always safe, so clients, proxies and load balancers retry them automatically.

Because POST isn't idempotent, any POST with real consequences — charging a card, placing an order — needs an explicit idempotency key so retries are safe. Note also that safe (GET, HEAD — no side effects at all) is a stronger property than idempotent, which is why a GET that mutates state breaks caches and prefetchers in surprising ways.

🟡 Mid — Design an idempotent POST /payments endpoint. Handle the concurrent-retry case.

The client generates an Idempotency-Key once per logical operation and resends it with every retry. The server must guarantee one side effect and return the same response each time.

POST /payments
Idempotency-Key: 4f3c-a91e-...
{ "amount": 5000, "order_id": 42 }

Server flow:

1. Atomically CLAIM the key — this is what resolves concurrency:
     INSERT INTO idempotency(key, consumer_id, request_hash, state)
       VALUES ($1, $2, $3, 'IN_PROGRESS');
   Unique constraint on (consumer_id, key).

   - Insert SUCCEEDS  → we own it, proceed to step 2.
   - UNIQUE VIOLATION → someone already claimed it. Read the row:
       state = COMPLETED   → return the STORED status + body,
                             plus  Idempotent-Replay: true
       state = IN_PROGRESS → 409 Conflict + Retry-After. Do NOT wait
                             and do NOT start a second payment.
       request_hash differs → 422: same key, different body = client bug.

2. Perform the charge. Persist the response body and status code into
   the idempotency row in the SAME transaction as the payment record:
     BEGIN;
       INSERT INTO payments(...);
       UPDATE idempotency SET state='COMPLETED', response_status=201,
              response_body=$1 WHERE key=$2;
     COMMIT;

3. Return 201 with the body.

Why the atomic claim is the crux: a "SELECT then INSERT" check has a window where two concurrent retries both see "not found" and both charge. Letting the unique constraint arbitrate means the database provides mutual exclusion — no distributed lock, no race.

Why 409 rather than blocking: if I made the second request wait for the first, a slow payment would hold a connection and the client's own timeout might fire anyway, producing a third request. Returning 409 immediately with Retry-After tells the client exactly what's happening.

Details I'd include: scope keys per consumer (so tenants can't collide) with a 24-hour TTL and a cleanup job; store the response so replays are exact; and if the external payment provider is involved, pass the same key onward as its idempotency key, since that's the only participant that can guarantee one charge. Finally, offer GET /payments?order_id=42 so a client that lost its key can still ask what happened — idempotency fixes retries, a lookup endpoint fixes amnesia.

🟡 Mid — Your /posts?offset=N endpoint shows users duplicate items. Diagnose and fix.

Diagnosis: offset pagination is unstable under concurrent writes. Offset means "skip N rows of the current result set". If a new post is inserted at the top between the user fetching page 1 and page 2, every row shifts down by one — so the item that was last on page 1 is now first on page 2. The user sees a duplicate, and symmetrically, a deletion causes a row to be skipped entirely, which is the same bug and much harder to notice.

There's a second, unrelated problem worth flagging: OFFSET 1000000 forces the database to count and discard a million rows on every request, so deep pages get progressively slower.

Fix — cursor (keyset) pagination:

GET /posts?limit=20&after=<opaque_cursor>

SELECT * FROM posts
 WHERE (created_at, id) < ($cursor_created_at, $cursor_id)
 ORDER BY created_at DESC, id DESC
 LIMIT 20;

The cursor names a position in the sort order rather than a count, so inserts and deletes elsewhere don't shift it. And with an index on (created_at, id) it's O(log n) — page 50,000 costs the same as page 1.

Two details that matter: the sort key must be unique, hence the id tiebreaker — paginating on created_at alone silently skips rows sharing a timestamp at page boundaries. And the cursor should be opaque (base64 the composite value) so clients can't hand-construct one, leaving you free to change its internals later.

The trade-off to state: cursors give up random access — no "jump to page 500", only next/previous. If the product genuinely needs numbered pages, options are to keep offset for shallow pages only, or precompute page boundaries for a static snapshot. And offset is perfectly fine for small bounded lists like an admin table of 200 categories; the bug only bites on large, actively-written collections.

🔴 Senior — You must rename a field used by 200 third-party integrations. Walk me through it.

A rename is a breaking change, so the only safe path is expand/contract — and with 200 external consumers I cannot rely on them acting on an announcement.

Phase 1 — Expand (ship immediately, breaks nothing). Add full_name alongside name. Every response includes both, populated identically. Every request accepts either; if both arrive, define and document a precedence rule (new field wins) and reject conflicting values rather than silently picking one.

Phase 2 — Instrument, which is the step that makes this decidable. Log every request that reads or writes the old field, tagged with API key, consumer name, endpoint and timestamp. This converts "has everyone migrated?" from a hope into a dashboard. Without it, the rest of the plan is guesswork.

Phase 3 — Communicate with specifics. Deprecation notice in the docs, a Deprecation and Sunset header on responses that used the old field (machine readable, so diligent clients can alert themselves), changelog, and — because I have usage data — targeted emails to the specific integrations still using it, naming the endpoints they call. Generic broadcasts get ignored; "your integration called /orders 40,000 times last week using a field we're removing on 1 March" does not.

Phase 4 — Wait a full business cycle, then some. For third parties, 6–12 months is normal. Critically, wait long enough to catch infrequent consumers: a quarterly reconciliation job appears in your logs four times a year, and a consumer that's silent for two months may not be migrated — just idle.

Phase 5 — Contract, carefully. When usage is zero and has been for a full cycle: remove it behind a kill switch first — disable the old field for a small percentage of traffic or for specific consenting consumers, watch error rates, then proceed. Being able to re-enable within minutes is worth more than confidence.

What I'd actually recommend instead, though: question whether the rename is worth it. The benefit is cosmetic clarity; the cost is 200 integrations of coordination risk plus months of dual maintenance. Keeping name forever as a documented alias, and using full_name in all new endpoints, is often the better engineering trade. If it's part of a larger versioned redesign, do it there — one breaking change bundling many improvements is far cheaper for consumers than a series of individual ones.

And for the future: consumer-driven contract tests, so each integration's expectations run in your CI and a breaking change fails at build time rather than in production.

🔴 Senior — When would you choose serverless over containers, and when is it a mistake?

I'd decide on three axes: traffic shape, latency budget, and state requirements — and run the cost arithmetic rather than asserting.

Serverless is right when:

• Traffic is spiky or unpredictable. Scale-to-zero means an internal tool used twice a day costs cents rather than a permanently-running container. Capacity planning for unknown load is guesswork you get to skip.
• The work is event-driven glue. Upload triggers thumbnailing, webhook receivers, cron jobs. The platform integrations do real work for you here.
• Volume is below the crossover. At 100 ms and 512 MB, roughly:

1M req/month   ≈ $1     vs $30 container → serverless wins ~30×
100M req/month ≈ $103   vs $30 container → container wins ~3×
1B req/month   ≈ $1,030 vs ~$300         → container wins ~3×
Crossover ≈ 20–50M requests/month for this shape.

It's a mistake when:

• Sustained high QPS — you pay a large premium for elasticity you no longer need.
• Tight latency SLOs. Cold starts of 100 ms–1 s+ (worse for JVM/.NET, worse in a VPC) blow a 50 ms p99. Provisioned concurrency fixes it but removes scale-to-zero, i.e. the reason you chose serverless.
• Long-running or stateful work — the ~15-minute ceiling, no durable local disk, and no WebSocket-style long-lived connections.
• You need warm in-process state. The L1 cache that solves hot keys, and a warm connection pool, both assume a long-lived process.

The deeper point, which is what I'd emphasise: the dominant cost usually isn't the invocation bill — it's that serverless constraints leak into the rest of the architecture. No connection pool means adding a connection proxy. No in-process cache means more load on Redis. The 15-minute limit means splitting jobs and adding an orchestrator. 1,000 concurrent invocations will happily exhaust a database connection pool that a fixed fleet of 10 containers never threatened — so serverless scales into your dependencies, and the bottleneck moves rather than disappearing.

So: serverless is a different architecture, not "the same app without servers". Choose it deliberately for elasticity and operational simplicity at modest or unpredictable volume; choose containers when load is steady, latency is tight, or the app wants to hold state. Hybrid is common and correct — containers for the steady core API, functions for bursty event handling around it.

🏋️ Graded Exercises

Exercise 1 (Easy): Classify each as breaking or non-breaking: (a) add an optional response field, (b) rename a request parameter, (c) add a required request field, (d) change an ID from string to integer, (e) add a new endpoint.
Solution

(a) Add optional response field → NON-BREAKING. Existing clients ignore unknown fields. The one caveat: clients using strict schema validation that rejects unknown properties will break — rare, but it's why "additive is safe" assumes tolerant readers.

(b) Rename a request parameter → BREAKING. Old clients send the old name, which the server now ignores, so the value silently reverts to a default. Worse than an error, because it fails quietly.

(c) Add a required request field → BREAKING. Every existing client omits it and now gets a 400. To do this safely, add it as optional with a sensible default, migrate clients, then tighten.

(d) Change ID from string to integer → BREAKING and particularly nasty: statically-typed clients fail to deserialise, and JavaScript clients may silently lose precision on large integers past 2⁵³. Type changes are never safe — add a new field instead.

(e) Add a new endpoint → NON-BREAKING. Nothing existing changes.

The pattern: additive is safe, mutative is not. If you only ever add, you never need a v2 — versioning is the tool you reach for after failing to be additive.

Exercise 2 (Easy): A client's POST times out and it retries. What are the possible states, and how does an idempotency key resolve them?
Solution

Three possible states, indistinguishable to the client:

1. Request never reached the server        → no side effect
2. Server processed it, response was lost → side effect DID happen
3. Server is still processing it          → side effect in flight

This is the fundamental problem: a timeout tells you nothing about the server's state. Without idempotency the client must choose between retrying (double-charge in case 2) and not retrying (lost order in case 1) — and both are wrong some of the time.

How the key resolves each:

• Case 1 — the key is unknown to the server, so it processes the retry normally. Correct: one side effect.
• Case 2 — the key is found in COMPLETED state, so the server returns the stored original response (same status, same body, same charge ID). The client learns the true outcome and no second charge occurs.
• Case 3 — the key is found IN_PROGRESS, so the server returns 409 with Retry-After rather than starting a second operation. The client waits and retries.

The essential detail is that case 2 must return the original response body, not just "already done" — otherwise the client still doesn't know the charge ID and has to go looking for it.

Exercise 3 (Medium): Design cursor pagination for a feed sorted by score DESC, where scores change constantly. What breaks, and what do you do?
Solution

What breaks: the sort key is mutable. Cursor pagination assumes the cursor names a stable position. If scores change between page fetches, an item you already saw can drop below the cursor (you'll see it again) or a new item can rise above it (you'll never see it). Worse, an item whose score changes can appear on page 1 and page 5.

Keyset pagination fundamentally requires a sort key that is stable and unique, and a live score is neither. So the honest answer is that you cannot cursor-paginate a continuously re-ranked list correctly — you have to change the problem.

Option 1 — snapshot the ranking (best for correctness). Materialise the ordering when pagination begins and paginate that:

On first request: compute the ranked ID list, store it in Redis
   feed:{user}:{session}  →  [id_9, id_4, id_77, ...]   TTL 10 min
Cursor = an INDEX into that frozen list.
→ Stable, no duplicates, no misses. Pages are consistent with each other.
Cost: memory per active paginating session, and results go stale — which
      is usually fine, since a user scrolling for 30 s expects a
      consistent list rather than a live-updating one.

Option 2 — paginate on an immutable key, rank within the page. Use (created_at, id) as the cursor (immutable) and sort each returned page by current score. Stable pagination, but the global ordering isn't score-ordered — acceptable for "recent and interesting", wrong for "top of all time".

Option 3 — composite cursor with a tiebreaker and accept the drift. Cursor on (score, id), acknowledging that items whose scores change may be duplicated or skipped. Cheap, no extra state; suitable when small inconsistencies are invisible to users (an infinite social feed) and unacceptable for anything auditable.

Option 4 — exclusion list. Send back the IDs already seen (or a compact Bloom filter of them) and have the server filter them out. Prevents duplicates but not misses, and the payload grows as the user scrolls.

What I'd choose: snapshot (option 1) for anything where users notice or correctness matters — leaderboards, search results, paginated reports — because "the list doesn't shuffle under me" is what users actually expect. For an endless social feed, option 3 with a (score, id) composite is pragmatic and cheap. Either way, the decision to state is which inconsistency you're accepting.

Exercise 4 (Medium): An endpoint receives 1M req/day with 200 ms of work, and its traffic is flat. Serverless or container? Show the arithmetic and name the deciding factor.
Solution 
1M req/day = ~30M req/month.  200 ms at 512 MB:
  GB-seconds/req = 0.5 × 0.2 = 0.1
  Per request ≈ (0.20/1M) + (0.1 × 0.0000166667) ≈ $0.0000019
  Monthly ≈ 30M × $0.0000019  ≈ $57

Container sizing: 30M/month ≈ 12 req/s average.
  At 200 ms each, concurrency ≈ 12 × 0.2 = 2.4 in-flight requests.
  Two small containers (with headroom + HA) ≈ $30–60/month.

→ Roughly a WASH on cost. So cost is NOT the deciding factor.

The deciding factor is that traffic is flat. Serverless earns its premium through elasticity — scale-to-zero and absorbing spikes. A steady 12 req/s uses none of that, so you'd be paying for an option you never exercise while inheriting the constraints: cold starts on the tail, no warm connection pool, a 15-minute ceiling, no in-process cache.

So: containers. At equal cost, take the option with fewer constraints and the ability to hold warm state (connection pool, L1 cache) — and note that L1 caching could plausibly cut the 200 ms work substantially, an optimisation that's unavailable in a process that may not exist between requests.

What would flip my answer:

• Spiky traffic — the same 30M/month arriving in two hours a day would need containers provisioned for peak and idle the rest of the time; serverless wins clearly.
• No ops capacity — if there's no team to patch and monitor containers, the operational saving can outweigh a modest cost premium.
• Much lower volume — at 1M/month serverless is ~$2 versus $30, a 15× win.
• Much higher volume — at 500M/month serverless is ~$950 versus a few hundred, so containers win decisively.

The transferable habit: compute the crossover, then check whether you're actually using the thing you're paying extra for.

Exercise 5 (Hard): Design the public API contract for a payments service: create a payment, check status, list payments, handle webhooks. Specify idempotency, versioning, errors and pagination.
Solution

Endpoints:

POST /v1/payments          create (idempotent via header)
GET  /v1/payments/{id}     fetch one
GET  /v1/payments          list (cursor paginated, filterable)
POST /v1/payments/{id}/refunds   refund (also idempotent)
GET  /v1/payments?client_ref=X   ← recovery lookup, see below

1. Create, with idempotency:

POST /v1/payments
Idempotency-Key: 4f3c-a91e-...        (client-generated, required)
{ "amount": 5000, "currency": "usd",
  "client_ref": "order-42",           ← the caller's own identifier
  "payment_method": "pm_abc" }

201 → { "id": "pay_9x", "status": "succeeded", "amount": 5000,
        "client_ref": "order-42", "created_at": "..." }

Keys scoped per API consumer, 24-hour TTL, stored with the response body so replays return the original 201 and ID plus Idempotent-Replay: true. Same key with a different body → 422. Key claimed but still in flight → 409 with Retry-After.

The client_ref field is the piece people forget, and it's essential for a payments API: if a client loses its idempotency key (crashed before persisting it), it can still ask GET /v1/payments?client_ref=order-42 to discover whether the payment exists. Idempotency makes retries safe; this makes amnesia recoverable. Without it, a client's only option after a crash is to guess or reconcile manually.

2. Status semantics. Use an explicit state machine and never overload HTTP status to convey business outcome:

status: pending | processing | succeeded | failed | refunded
A DECLINED card is a successful API call (200/201) with
status="failed" and a decline reason — NOT an HTTP 402.
HTTP status describes the API interaction; the body describes the
business outcome. Conflating them means clients can't distinguish
"your request was malformed" from "the bank said no".

3. Errors — stable machine-readable codes:

{ "error": { "code": "card_declined",
             "message": "The card was declined.",
             "decline_code": "insufficient_funds",
             "request_id": "req_8f2a",
             "retryable": false } }

400 malformed · 401 bad key · 403 not permitted
409 idempotent request in flight, or state conflict
422 valid syntax, semantically rejected (bad currency, key reuse)
429 rate limited + Retry-After
5xx transient → retry with exponential backoff and jitter

Clients branch on code, never on message, and request_id is echoed in every response for support correlation.

4. Pagination — cursor, not offset:

GET /v1/payments?limit=50&after=<opaque>&created_after=2026-01-01
200 → { "data": [...],
        "has_more": true,
        "next_cursor": "eyJjIjoiMjAyNi0..." }

Sort key (created_at, id) — immutable and unique, so pages are stable
even as payments are created continuously. Offset would duplicate and
skip records, which for a financial API means a reconciliation script
silently missing transactions. That's the failure mode that makes
cursors non-negotiable here.

5. Webhooks — the mirror image, where I'm the unreliable caller:

POST to the customer's endpoint:
  Webhook-Id: evt_123           ← stable; retries reuse it so the
                                   RECEIVER can dedupe
  Webhook-Signature: t=...,v1=HMAC_SHA256(secret, timestamp + body)
  { "type": "payment.succeeded", "data": {...},
    "created_at": "...", "api_version": "2026-07-30" }

- SIGN the payload (HMAC with a per-customer secret) and include a
  timestamp, so receivers can verify authenticity and reject replays.
- At-least-once delivery with exponential backoff over ~24h, then a
  DLQ plus an email alert. Document that receivers MUST be idempotent
  on Webhook-Id — same contract as any
  message consumer.
- Order is NOT guaranteed. Include a sequence number or timestamp so
  receivers can ignore stale events, per the ordering discussion in
  the pub/sub lesson.
- Provide a REPLAY endpoint and an event log, so a customer whose
  endpoint was down for a day can catch up without contacting support.

6. Versioning — date-based pinning. Each account pins the API version in force when it integrated (API-Version: 2026-07-30), overridable per request. Internally, one current model plus transformation layers down to older versions. This is Stripe's approach and it's the right trade for payments: consumers are numerous, external, and cannot be asked to migrate on your schedule. It costs real sustained effort to maintain those transformations, which is the honest downside.

Cross-cutting: only additive changes within a version; every response carries request_id; rate limits communicated via X-RateLimit-* headers plus 429; and all money as integer minor units (5000 = $50.00) — never floats, because binary floating point cannot represent 0.10 exactly and financial rounding errors are unforgivable.

Exercise 6 (Hard): A team moved a 200-QPS API from containers to Lambda. Latency p99 went from 80 ms to 2.5 s and the database started failing with "too many connections". Diagnose fully.
Solution

Two independent failures, both predictable consequences of the execution model rather than bugs.

Failure 1 — p99 latency: cold starts.

200 QPS with, say, 100 ms of work → ~20 concurrent executions steady state.
But concurrency fluctuates, and every scale-up event initialises a NEW
sandbox: download code, start the runtime, run module-level init,
establish connections.

Cold start budget:
  runtime boot            50–500 ms  (JVM/.NET at the high end)
  VPC-attached ENI setup  +100 ms–1 s (historically much worse)
  module init / DI graph  100 ms–1 s
  first DB connection     10–50 ms
  → 2.5 s is entirely consistent with a VPC-attached function with a
    heavy init path.

Why it hits p99 specifically: only a small fraction of requests land on
a cold sandbox, so the MEAN looks fine (which is why this shipped) while
the tail is catastrophic. Averages hide it — the exact trap from the
estimation lesson.

Failure 2 — database connections: the concurrency model inverted.

Containers: 10 containers × a pooled 20 connections = 200 connections,
            REUSED across thousands of requests. Bounded by design.

Lambda:     each concurrent execution is an isolated process with its
            OWN connection. No shared pool exists — pooling assumes a
            long-lived process.
            200 QPS × spikes → hundreds of concurrent sandboxes →
            hundreds of connections, and each one costs the database
            ~5–10 MB of memory plus fork/auth overhead.
            Postgres default max_connections is ~100. It refused.

Worse: sandboxes are recycled, so connections churn constantly, and
Postgres connection establishment is expensive — adding latency to the
very requests already paying a cold start.

Fixes for the connection problem, in order:

1. Connection proxy (RDS Proxy, PgBouncer in transaction mode) — the proper fix. It maintains a small warm pool to the database and multiplexes many short-lived client connections onto it, restoring the bounded behaviour containers had.
2. Initialise the client outside the handler so a warm sandbox reuses its connection across invocations instead of reconnecting per request — a one-line change that's frequently missed.
3. Cap reserved concurrency so the function cannot scale past what the database tolerates. Note the trade: requests then queue or throttle, which is a deliberate choice of shedding load over killing the database — the same reasoning as protecting the DB during a cache avalanche.
4. Use an HTTP-based data API (Data API / serverless-native datastore) that doesn't hold persistent connections at all.

Fixes for cold starts:

1. Provisioned concurrency for a baseline — keeps N sandboxes warm, eliminating cold starts up to that level. But it bills continuously, which removes scale-to-zero: at that point you are paying for always-on capacity with extra steps.
2. Remove the VPC attachment if the function doesn't need private resources — historically the single largest contributor.
3. Slim the init path: lazy-load dependencies, trim the deployment package, avoid heavy DI containers. Consider a lighter runtime, or native AOT compilation for JVM/.NET.
4. Increase memory — CPU scales with memory allocation, so a larger size can reduce both init and execution time enough to be cost-neutral.

The verdict I'd give the team: at a flat 200 QPS this workload should probably go back to containers. 200 QPS is steady, meaningful traffic — it uses none of serverless's elasticity while paying all of its constraints, and the remedies above (provisioned concurrency + a connection proxy) amount to reconstructing always-on servers with more moving parts and a higher bill. If they keep Lambda, they need provisioned concurrency, no VPC attachment, a connection proxy, and reserved-concurrency caps — and they should verify against p99, not the mean, because the mean is what made this look fine before launch.

🎯 Key Takeaways

  • Choose an API style by the caller: REST at the public edge, gRPC between your own services, GraphQL for heterogeneous clients. Large systems use all three.
  • GraphQL relocates N+1 rather than removing it — from the network into your resolvers, where DataLoader-style batching can fix it.
  • Additive changes are safe; mutative ones aren't. If you only ever add, you never need a v2.
  • Changing a field's meaning is the worst breaking change — it passes every schema check and corrupts behaviour silently.
  • Expand → migrate → contract, and instrument the old field. Usage telemetry is what turns "has everyone migrated?" into a number; announcements are not evidence.
  • POST is not idempotent — everything with real consequences needs an idempotency key, claimed atomically via a unique constraint so concurrent retries can't both act.
  • Store and replay the original response, not a bare "already processed" — and offer a lookup-by-client-reference endpoint so a client that lost its key can still recover.
  • Offset pagination duplicates and skips rows under writes and costs O(offset). Use cursors on a unique, immutable composite key.
  • Cursors need a stable sort key — for a live-scored feed, snapshot the ranking instead, and state which inconsistency you're accepting.
  • 4xx means don't retry, 5xx means retry. Returning 500 for validation errors makes clients hammer a request that can never succeed.
  • HTTP status describes the API call; the body describes the business outcome. A declined card is a successful request with status: "failed".
  • Serverless crossover is roughly 20–50M requests/month. Below it, a large win; above it, a large premium for elasticity you aren't using.
  • Serverless scales into your dependencies: no connection pool, no in-process cache, ~15-minute ceiling. It's a different architecture, not the same app without servers.
