Concurrent Programming & Deadlocks Deep Dive

What you'll master: why counter++ loses updates and why visibility is a separate problem from atomicity (the part most engineers never learn), the four conditions deadlock requires and which one you actually break in practice, how to distinguish deadlock from livelock and starvation, how to size a thread pool from a formula rather than a guess, why blocking a thread is expensive and what async models do instead, and how to make concurrency bugs reproducible.

Prerequisites: Concurrency Control (the same problems at database scope). Feeds Microservices (bulkheads are semaphores) and Realtime Apps (event loops).

1. Two Problems, Not One: Atomicity and Visibility

Almost every treatment of concurrency covers atomicity and stops. Visibility is the other half, and it produces bugs that are far harder to diagnose.

PROBLEM 1 — ATOMICITY.  counter++ is three operations:

   Thread A: READ counter (5)
   Thread B: READ counter (5)      ← both read before either writes
   Thread A: ADD 1 → WRITE 6
   Thread B: ADD 1 → WRITE 6       ← overwrites A's increment

   Expected 7, got 6. One increment lost.


PROBLEM 2 — VISIBILITY.  Even a single, genuinely atomic write may
never become visible to another thread:

   // Thread A
   data = compute();          // 1
   ready = true;              // 2

   // Thread B
   while (!ready) { }         // may spin FOREVER
   use(data);                 // may see a STALE or half-built value

   Why: the compiler may reorder 1 and 2 (they look independent), the
   CPU may reorder the stores, and B may read `ready` from its core's
   cache indefinitely — never re-reading main memory.

   Nothing here is a race in the "lost update" sense. It is a MEMORY
   MODEL problem, and no amount of "make it atomic" fixes it.
⚠️ The consequence that surprises people: a variable can be written atomically and still never be seen. Fixing visibility requires a memory barrier — which is what volatile (Java/C#), std::atomic (C++), or simply using a lock provides. Locks give you both properties at once: mutual exclusion and a happens-before relationship that forces changes to become visible. This is the real reason "just remove the lock, it's only one variable" is usually wrong.

2. Locks, and Their True Cost

lock.acquire();
counter++;              // critical section: exactly one thread here
lock.release();         // also publishes all prior writes to other threads
CostDetail
Uncontended acquisition~20–50 ns. Cheap — modern runtimes use a fast path that avoids the OS entirely.
Contended acquisition~1–10 µs. The thread parks, the OS context-switches, and the cache is likely cold on resume. 100× the uncontended cost.
SerialisationThe critical section runs one thread at a time — this is the real ceiling, and it's what Amdahl's law bites on.
Cache-line bouncingA lock and its data ping-pong between cores' caches. Two threads on different sockets updating one counter can be slower than one thread alone.
ConvoyingA thread descheduled while holding a lock stalls everyone behind it, regardless of their priority.

The rule that follows: hold locks for the shortest possible time, and never across anything slow. A lock held during a network call, a disk read, or a log write serialises your whole system on that operation's latency.

❌ Slow work inside the lock 
lock.acquire();
var user = db.query(id);   // 5 ms!
user.count++;
api.notify(user);          // 50 ms!!
lock.release();

regardless of core count.

the network call.
✅ Lock only the shared state

concurrency, not the lock.

Lock-free alternatives use hardware compare-and-swap instead of blocking:

// CAS loop — the primitive underneath every lock-free structure
do {
    old = counter.get();
    next = old + 1;
} while (!counter.compareAndSet(old, next));   // retry if someone else won

Pros: no blocking, no deadlock, no convoying — a stalled thread never
      blocks others (lock-freedom guarantees SYSTEM-wide progress).
Cons: under heavy contention the retry loop burns CPU and can perform
      WORSE than a lock; correctness is far harder to reason about;
      the ABA problem (value returns to A after B, so CAS wrongly
      succeeds) needs versioned pointers or hazard pointers.

Use the library's atomic types. Do not hand-write lock-free data
structures — this is one of the few areas where "don't roll your own"
is as strong as it is for cryptography.

3. Deadlock: Four Conditions, One Practical Fix

Thread A: holds Lock 1, wants Lock 2
Thread B: holds Lock 2, wants Lock 1
→ neither proceeds, ever.

Deadlock requires ALL FOUR simultaneously (Coffman conditions):
  1. MUTUAL EXCLUSION — the resource can't be shared
  2. HOLD AND WAIT    — holding one while requesting another
  3. NO PREEMPTION    — can't forcibly take a lock away
  4. CIRCULAR WAIT    — a cycle in the wait-for graph

Break any ONE and deadlock becomes impossible.
StrategyBreaksPracticality
Consistent global lock orderingCircular waitThe answer in practice. Free at runtime, enforceable by convention and lint. Always lock accounts in ascending ID order, and no cycle can form.
Lock timeouts (tryLock)Hold and waitGood safety net, but converts deadlock into livelock if everyone retries identically — needs jittered backoff.
Acquire all locks at once, or noneHold and waitWorks when you know the full set upfront; often you don't.
Lock-free structuresMutual exclusionEliminates deadlock entirely, at a significant complexity cost.
Preemption / victim abortNo preemptionWhat databases do — detect a cycle and abort a transaction. Needs a rollback mechanism, which application threads generally lack.
Lock ordering, concretely — the bank transfer case:

  ❌ transfer(from, to):  lock(from); lock(to);
     transfer(A,B) and transfer(B,A) concurrently → guaranteed deadlock

  ✅ transfer(from, to):
        first, second = (from.id < to.id) ? (from, to) : (to, from);
        lock(first); lock(second);
     Both directions now acquire in the SAME order. Cycle impossible.

4. Deadlock's Cousins: Livelock and Starvation

FailureSymptomCauseFix
DeadlockThreads blocked forever; CPU idleCircular waitLock ordering
LivelockThreads active, CPU busy, no progressThreads repeatedly react to each other — e.g. both release and retry in lockstepRandomised backoff. Same fix as retry storms.
StarvationOne thread never gets the resource while others proceedUnfair scheduling; a writer waiting behind a continuous stream of readersFair locks (FIFO queue), or writer-preference read-write locks
Priority inversionA high-priority thread waits on a low-priority oneThe low-priority holder is preempted by medium-priority workPriority inheritance — the holder temporarily inherits the waiter's priority

Livelock is the one people misdiagnose, because the system looks busy rather than hung. Classic instance: two threads each hold one lock, both detect a potential deadlock, both release and immediately retry — and land in exactly the same state. CPU is at 100%, throughput is zero. The cure is the same jitter used for retry storms: randomise the backoff so the symmetry breaks.

Priority inversion is worth knowing because of its famous failure: the 1997 Mars Pathfinder rover repeatedly reset on Mars when a high-priority bus-management task blocked on a mutex held by a low-priority meteorological task, which was itself preempted by medium-priority communications work. The fix uploaded to the spacecraft was to enable priority inheritance on that mutex.

5. Deep Dive: Sizing a Thread Pool

"How many threads?" has an actual formula, and getting it wrong is one of the most common performance bugs in server code.

threads = cores × target_utilisation × (1 + wait_time / service_time)

CPU-BOUND work (wait ≈ 0):
   8 cores × 1.0 × (1 + 0)      = 8 threads
   More threads only add context-switching overhead — there is no
   spare CPU for them to use.

I/O-BOUND work (e.g. 100 ms waiting, 5 ms computing):
   8 cores × 1.0 × (1 + 100/5)  = 8 × 21 = 168 threads
   Threads spend most of their life blocked, so you need many to keep
   the cores busy.

MIXED: measure the actual ratio. Guessing here is how systems end up
       with a 200-thread pool on 4 cores, thrashing on context
       switches, or an 8-thread pool serialising on database calls.
SymptomLikely cause
High CPU, low throughputToo many threads — context-switch thrashing, cache pollution
Low CPU, low throughput, growing queueToo few threads for an I/O-bound workload, or a blocking call inside a lock
Throughput collapses under loadUnbounded queue absorbing work faster than it drains, then memory pressure
Intermittent total stallsPool exhaustion — every thread blocked on the same slow dependency

Two rules that prevent most thread-pool incidents:

1. Bound the queue. An unbounded work queue converts overload into unbounded latency and eventually an out-of-memory crash. A bounded queue with a rejection policy gives you back-pressure — failing fast is a feature, and it's the same load-shedding principle as elsewhere in the track.
2. Use separate pools per dependency. This is the bulkhead pattern in-process: if one slow downstream service exhausts a shared pool, requests that never touch it fail too. Separate pools contain the damage.

6. Deep Dive: Why Blocking Is Expensive, and What Async Does

A blocked OS thread costs:
   ~1 MB of stack (reserved virtual memory, partially committed)
   a kernel scheduler entry
   ~1–5 µs per context switch, plus cache disturbance

10,000 concurrent connections × 1 thread each
   = 10 GB of stack, and a scheduler managing 10,000 runnable entities.
   This is the "C10K problem" — and it's why the one-thread-per-request
   model stops working at scale.
ModelMechanismTrade-off
Thread per requestOS thread blocks on I/OSimplest to write and debug — a real stack trace, ordinary control flow. Memory-bound at high concurrency.
Event loop (Node.js, nginx, Redis)Single thread + non-blocking I/O + callbacksEnormous concurrency on one thread. Any blocking or CPU-heavy call stalls everything. Doesn't use multiple cores without multiple processes.
async/awaitCompiler transforms functions into state machines; awaiting frees the threadEvent-loop efficiency with sequential-looking code. Risk: one accidental blocking call in an async path stalls the loop, and stack traces get harder to read.
Virtual/green threads (Go, Java 21+)Runtime-scheduled lightweight threads; blocking parks the virtual thread, not the OS threadThe best of both — write straightforward blocking code, get async scaling. ~2–4 KB per virtual thread instead of ~1 MB.
🎯 The insight worth carrying: async doesn't make anything faster — it makes waiting cheaper. If work is CPU-bound, async provides nothing (you still need the cycles) and adds complexity. Async wins exactly when threads would otherwise sit blocked on I/O. That's why virtual threads are so attractive: they remove the trade entirely, letting you keep simple sequential code while paying async-level costs for blocking.

7. Making Concurrency Bugs Findable

Concurrency bugs are timing-dependent, so they pass tests, survive review, and appear only in production under load. Deliberate technique matters more here than care:

TechniqueWhat it catches
ImmutabilityEverything — an object that never changes cannot race. The single highest-leverage design choice.
ConfinementDon't share state; give each thread its own, or pass ownership via a queue. "Share memory by communicating."
Race detectors (Go -race, TSan, Java Flight Recorder)Actual unsynchronised access at runtime — finds bugs that haven't yet manifested. Run them in CI.
Stress + interleaving testsRun the operation from many threads thousands of times, asserting the invariant. Add random sleeps to widen windows.
Deterministic simulationControl the scheduler so an interleaving is reproducible — the technique behind FoundationDB's reliability.
Static analysis / lock-order checkingCycles in lock acquisition order, before they deadlock in production.

The strongest advice is architectural: most concurrency bugs come from shared mutable state, so the winning move is not to have any. Immutable data, single-threaded ownership with message passing, or pushing coordination into a database transaction all eliminate the class of bug rather than managing it — the same "remove the contention" instinct as in concurrency control.

Interview Questions

🟢 Beginner — Why isn't counter++ thread-safe?

Because it isn't one operation — it compiles to three: read the current value, add one, write it back. Two threads can interleave between those steps:

Thread A: reads 5
Thread B: reads 5          ← both read before either writes
Thread A: writes 6
Thread B: writes 6         ← overwrites A's increment
Expected 7, got 6 — a lost update.

The result depends on unpredictable thread timing, which is what makes it a race condition: the code is correct in isolation and wrong under concurrency, and it will usually pass tests.

Fixes: an atomic type (AtomicInteger.incrementAndGet()), which uses a hardware compare-and-swap so the read-modify-write is indivisible; or a lock around the increment, which is slower but also covers larger critical sections.

Worth adding, because it's the deeper point: even if the increment were atomic, another thread might never see the new value — compilers and CPUs reorder operations, and each core has its own cache. Atomicity and visibility are separate problems, and a proper atomic or a lock gives you both.

🟢 Beginner — What are the four conditions for deadlock, and which do you break in practice?

Deadlock requires all four Coffman conditions simultaneously:

1. Mutual exclusion — the resource can't be shared.
2. Hold and wait — a thread holds one resource while requesting another.
3. No preemption — a resource can't be forcibly taken.
4. Circular wait — a cycle where each thread waits on the next.

Breaking any single one makes deadlock impossible, which is what makes this framing useful rather than academic.

In practice you break circular wait, with consistent global lock ordering. If every code path acquires locks in the same order — say, ascending account ID — a cycle cannot form:

transfer(from, to):
    first, second = (from.id < to.id) ? (from, to) : (to, from)
    lock(first); lock(second)
// transfer(A,B) and transfer(B,A) now acquire in the SAME order.

Why this one: it's free at runtime, requires no detection machinery, and is enforceable by convention, code review or a lint rule. The others are worse in application code: you usually can't share a resource (1), you often don't know the full lock set upfront (2), and preemption (3) requires rollback machinery that threads — unlike database transactions — don't have.

Lock timeouts are a reasonable safety net, but they convert deadlock into livelock if everyone retries in lockstep, so they need jittered backoff.

🟡 Mid — How many threads should a pool have? Walk through the reasoning.

There's a formula, and the key input is how much time a task spends waiting versus computing:

threads = cores × target_utilisation × (1 + wait_time / service_time)

CPU-bound work (wait ≈ 0): 8 cores × 1.0 × 1 = 8 threads. More threads can't help — there's no spare CPU for them, so extra threads only add context-switching overhead and cache pollution.

I/O-bound work (100 ms waiting on a database, 5 ms computing): 8 × (1 + 100/5) = 8 × 21 = ~168 threads. Threads spend 95% of their life blocked, so you need many to keep the cores busy.

Diagnosing a wrong size: high CPU with low throughput means too many threads (thrashing); low CPU with a growing queue means too few for an I/O-bound workload — or a blocking call inside a lock, which serialises everything regardless of pool size.

Two things I'd insist on beyond the number:

1. Bound the queue. An unbounded queue turns overload into unbounded latency and eventually an OOM crash. A bounded queue with a rejection policy gives back-pressure — rejecting work you cannot complete is a feature.
2. Separate pools per dependency. The in-process bulkhead: if one slow downstream service exhausts a shared pool, requests that never touch it fail too. This is the single most common cause of "one slow dependency took down the whole service".

And if the platform offers virtual threads (Go, Java 21+), much of this tuning disappears — blocking parks a cheap virtual thread rather than an OS thread, so the pool-sizing trade largely goes away.

🟡 Mid — Distinguish deadlock, livelock and starvation. How do you tell them apart in production?
DeadlockLivelockStarvation
ProgressNoneNoneSome threads progress, one never does
CPUIdle — threads are blockedBusy — threads are runningNormal
CauseCircular waitThreads repeatedly reacting to each otherUnfair scheduling
FixLock orderingRandomised backoffFair (FIFO) locks; writer preference

Telling them apart in production starts with one observation: is the CPU busy?

Deadlock: throughput drops to zero and CPU goes idle. A thread dump shows threads blocked on monitors in a cycle — A waiting on a lock held by B, B waiting on one held by A. Most JVM thread dumps detect and print this explicitly. It's the easiest to confirm.

Livelock: throughput is zero but CPU is pegged, which typically gets misdiagnosed as "a performance problem". Successive thread dumps show threads running, but cycling through the same few states — acquire, detect conflict, release, retry. The classic cause is deadlock-avoidance logic without jitter, where both threads back off identically and collide again.

Starvation: aggregate throughput looks fine, so dashboards look healthy — but tail latency is terrible and specific operations time out. The usual culprit is a read-write lock under a continuous read stream, where a writer waits indefinitely. Look at per-operation latency percentiles rather than averages; the average hides it completely.

The one I'd flag as most dangerous is starvation, precisely because the system appears healthy. Deadlock announces itself; starvation just makes a subset of users unhappy in a way that aggregate metrics don't show.

🔴 Senior — Explain memory visibility. Why can a correctly-locked-looking program still be wrong?

Visibility is separate from atomicity. Atomicity concerns whether an operation is indivisible; visibility concerns whether one thread's writes are ever observed by another. A program can be free of lost updates and still broken.

// Thread A
data = compute();     // 1
ready = true;         // 2

// Thread B
while (!ready) { }    // may spin forever
use(data);            // may see stale or partially-constructed data

Three independent mechanisms cause this:

1. Compiler reordering. Statements 1 and 2 look independent, so the optimiser may swap them — making ready true before data is written.
2. CPU reordering. Store buffers and out-of-order execution mean writes can reach memory in a different order than issued.
3. Cache coherence timing. B may read ready from its core's cache indefinitely. Worse, the compiler may hoist the read out of the loop entirely, producing a genuinely infinite spin.

The fix is a memory barrier, which establishes a happens-before relationship: volatile in Java/C#, std::atomic with appropriate ordering in C++, or simply taking a lock. Note that locks provide both properties — mutual exclusion and the barrier — which is why "it's just one variable, we don't need the lock" is so often wrong.

Double-checked locking is the canonical example of getting this wrong: checking a field, taking a lock, checking again, then constructing. Without volatile on the field, another thread can observe a non-null but partially constructed object, because the reference assignment may become visible before the constructor's writes. The bug is undetectable in testing and depends on processor architecture — it appears on ARM far more readily than on x86, since x86 has a stronger memory model. A system that works in development and fails on different hardware is often exactly this.

The practical takeaway: reason in terms of the language's memory model and its happens-before guarantees, not in terms of what the source code appears to say sequentially. And prefer immutability, which sidesteps visibility entirely — a value that never changes after construction (and is safely published) can't be seen in an inconsistent state.

🔴 Senior — A service intermittently stops responding under load. Threads are alive, CPU is low. Diagnose.

Alive threads plus low CPU means everything is blocked waiting — the work isn't being done, and nothing is spinning. I'd work through five candidates:

1. Thread-pool exhaustion on a slow dependency (most likely). One downstream service degrades from 50 ms to 5 s; every pool thread ends up parked on it; requests that never touch that dependency now queue behind them. This is the classic cascading failure and it matches the symptoms exactly. Check: a thread dump showing most threads in the same stack frame — a socket read on one dependency. Fix: per-dependency bulkhead pools, aggressive timeouts derived from the dependency's p99, and a circuit breaker.

2. Connection pool exhaustion. Same shape, different resource: threads blocked acquiring a database connection, often because a code path leaks connections (missing close() on an error branch) or holds them across slow work. Check: pool metrics — active vs idle vs waiting.

3. Deadlock (partial). If a subset of threads is deadlocked, the pool bleeds capacity over time — intermittent at first, then total. Check: thread dumps; the JVM detects lock cycles automatically. Intermittency plus gradual worsening is a strong tell.

4. Blocking work on an event loop. In an async runtime, one synchronous call — a file read, a DNS lookup, a CPU-heavy JSON parse — stalls every in-flight operation on that loop. Check: event-loop lag metrics.

5. Lock convoy or a lock held across I/O. A single lock held during a network call serialises everything, so throughput collapses to 1/latency while CPU stays near idle. Check: thread dump showing many threads blocked on one monitor.

Diagnostic method: take three thread dumps ~10 s apart. If threads are in the same stack frame across all three, they're genuinely stuck rather than slow — and the shared frame names the resource. Combine with connection-pool and event-loop-lag metrics.

The structural fix beyond the immediate cause: every blocking call needs a timeout (no timeout is an infinite timeout), separate pools per dependency so exhaustion is contained, and circuit breakers so a known-bad dependency fails fast instead of consuming a thread for its full timeout. The goal is that a slow dependency degrades one feature rather than the whole service.

🏋️ Graded Exercises

Exercise 1 (Easy): Two threads run transfer(A, B) and transfer(B, A) concurrently, each locking source then destination. What happens, and what's the fix?
Solution 
Thread 1: lock(A) ✓ ... wants lock(B) — held by Thread 2 → waits
Thread 2: lock(B) ✓ ... wants lock(A) — held by Thread 1 → waits
→ DEADLOCK. Circular wait; neither ever proceeds; CPU goes idle.

Fix — consistent global lock ordering, which breaks the circular-wait condition:

def transfer(src, dst, amount):
    first, second = (src, dst) if src.id < dst.id else (dst, src)
    with first.lock:
        with second.lock:
            src.balance -= amount
            dst.balance += amount

Now both calls acquire A before B regardless of transfer direction, so no cycle can form. This costs nothing at runtime and is enforceable as a code-review or lint rule.

Two details worth noting: use a stable, total ordering key — object IDs, not memory addresses, which vary per run. And handle the src.id == dst.id case (a self-transfer), which would otherwise try to acquire the same non-reentrant lock twice and deadlock against itself.

Exercise 2 (Easy): A pool of 200 threads on an 8-core machine performs CPU-heavy work. Throughput is worse than with 8 threads. Explain.
Solution

For CPU-bound work the formula gives cores × 1.0 × (1 + 0/service) = 8 threads. Only 8 can genuinely execute at once; the other 192 are runnable but waiting for a core, and they impose real costs:

1. Context switching — the scheduler rotates 200 threads across 8 cores, each switch costing ~1–5 µs of pure overhead that does no useful work.
2. Cache pollution — this is usually the bigger effect. Each thread's working set evicts the others', so a thread resuming finds cold caches and stalls on memory. Eight threads can keep their hot data resident; 200 cannot.
3. Memory pressure — 200 × ~1 MB of stack is 200 MB of extra footprint.
4. Scheduler overhead and increased lock contention, since more threads contend for any shared state.

Fix: size the pool to roughly the core count for CPU-bound work (cores or cores + 1).

The generalisable point: threads don't create parallelism — cores do. Threads only help when they'd otherwise be blocked, which is why the formula keys on the wait-to-service ratio. Adding threads to a CPU-bound workload adds overhead with no upside.

Exercise 3 (Medium): Implement a thread-safe counter three ways (lock, atomic, sharded) and say when each wins.
Solution 
import threading
from concurrent.futures import ThreadPoolExecutor

# 1. LOCK — simplest, covers compound operations
class LockedCounter:
    def __init__(self):
        self._n = 0
        self._lock = threading.Lock()
    def inc(self):
        with self._lock:          # ~20-50 ns uncontended, ~1-10 us contended
            self._n += 1
    def value(self):
        with self._lock:
            return self._n

# 2. ATOMIC / CAS — lock-free (Java AtomicLong, C++ std::atomic,
#    Python: itertools.count() is atomic via the GIL)
class AtomicCounter:
    def __init__(self):
        self._it = __import__('itertools').count()
        self._read = 0
    def inc(self):
        next(self._it)            # single bytecode -> atomic under the GIL

# 3. SHARDED — removes contention entirely (LongAdder's approach)
class ShardedCounter:
    def __init__(self, shards=64):
        self._shards = [0] * shards
        self._locks  = [threading.Lock() for _ in range(shards)]
    def inc(self):
        i = threading.get_ident() % len(self._shards)   # thread -> own shard
        with self._locks[i]:
            self._shards[i] += 1
    def value(self):              # reads are now O(shards), writes contend rarely
        return sum(self._shards)


def demo():
    c = ShardedCounter()
    with ThreadPoolExecutor(max_workers=16) as ex:
        for _ in range(16):
            ex.submit(lambda: [c.inc() for _ in range(1000)])
    assert c.value() == 16000, c.value()
    print("ok — sharded counter:", c.value())

if __name__ == "__main__":
    demo()
ApproachWins when
LockLow contention, or the critical section is compound (update several fields consistently). Simplest to reason about.
Atomic/CASModerate contention on a single value. No blocking, no deadlock. Degrades under heavy contention because CAS retries burn CPU.
ShardedHeavy contention — many threads incrementing one counter. Each thread touches its own cache line, so contention nearly disappears. Cost: reads must sum all shards, and memory grows with shard count.

The sharded version is what Java's LongAdder does, and it typically beats AtomicLong by an order of magnitude under write-heavy contention. It's the same "remove the contention rather than manage it" move as sharding a hot database row — and note the trade it accepts: reads become more expensive and are only approximate while writes are in flight.

Exercise 4 (Medium): A service has a 50-thread pool. One downstream dependency slows from 50 ms to 5 s. Trace the failure and design the fix.
Solution 
Normal: 50 ms per call, 50 threads → ~1,000 req/s capacity.

Dependency degrades to 5 s:
  t=0    threads begin blocking on it (100x longer than before)
  t~1s   all 50 threads are parked on that one dependency
  t~1s+  the queue grows; requests that DON'T touch this dependency
         also queue, because there is no free thread to run them
  t~5s   client timeouts fire; clients retry, adding load
  t~10s  health checks (which need a thread) time out → the instance
         is pulled from the load balancer → its traffic shifts to
         other instances → they exhaust too → CASCADE.

Capacity collapsed from 1,000 req/s to 50/5 = 10 req/s, and the
failure spread to unrelated functionality.

The fix, in layers:

1. Bulkhead — separate pools per dependency (the key structural fix). Give this dependency its own pool of, say, 10 threads. When it degrades, those 10 block and the other 40 keep serving everything else. The feature that depends on it fails; the service does not.

2. Timeouts derived from the dependency's p99, not a round number. A 200–500 ms timeout here means a thread is tied up for 0.5 s rather than 5 s — a 10× improvement in effective capacity during the incident. No timeout is an infinite timeout.

3. Circuit breaker — after N failures, fail fast without consuming a thread at all. This converts a slow failure into an instant one, which is precisely what protects the pool.

4. Bounded queue with rejection. An unbounded queue converts overload into unbounded latency and eventually OOM. Rejecting fast gives clients an honest signal.

5. Fallback — cached data, a default, or a degraded response omitting that dependency's contribution, decided in advance.

6. Isolate health checks so they never queue behind application work — otherwise a busy instance gets killed for being busy, which is what turns a local problem into a cascade.

The principle: a slow dependency is worse than a dead one, because slowness consumes the resource everyone shares. Bulkheads convert total failure into partial failure, which is the whole goal.

Exercise 5 (Hard): A cache uses double-checked locking for lazy initialisation. It works in testing and occasionally returns a partially-initialised object in production. Explain and fix.
Solution 
❌ BROKEN — the classic double-checked locking bug:

private static Config instance;             // NOT volatile

public static Config get() {
    if (instance == null) {                 // 1. unsynchronised read
        synchronized (lock) {
            if (instance == null) {
                instance = new Config();    // 2. THE PROBLEM
            }
        }
    }
    return instance;
}

Why it breaks. Line 2 is not one operation. It is roughly: allocate memory, run the constructor, then assign the reference. The compiler and CPU are permitted to reorder the assignment before the constructor completes, because within a single thread the difference is unobservable.

Thread A: allocates memory
Thread A: assigns `instance` = that memory   ← reordered to happen FIRST
Thread B: reads instance != null at line 1   ← sees a NON-NULL reference
Thread B: returns and USES a partially-constructed object
Thread A: finally runs the constructor

Thread B never takes the lock, so nothing forces it to see A's constructor writes. There's no lost update and no missing lock — it's purely a memory visibility and ordering failure.

Why it passes tests: the window is nanoseconds and requires exact interleaving. It also almost never reproduces on x86, whose memory model prohibits most store reordering, but appears readily on ARM (Apple silicon, Graviton, mobile). "Works in dev, fails in production" is frequently this exact architectural difference.

✅ FIX 1 — volatile (Java 5+ semantics guarantee the ordering):
private static volatile Config instance;

✅ FIX 2 — holder idiom (best in Java; the JVM guarantees class-init
   safety, and it is lazy with no synchronisation on the read path):
private static class Holder { static final Config INSTANCE = new Config(); }
public static Config get() { return Holder.INSTANCE; }

✅ FIX 3 — just use a lock, or eager initialisation. Double-checked
   locking is an optimisation for a problem most systems don't have;
   an uncontended lock is ~20-50 ns.

The transferable lesson: reason from the language's memory model and its happens-before guarantees, not from the apparent sequential order of source code. And treat double-checked locking as a code smell — it's a micro-optimisation that has produced this bug repeatedly across many codebases, and simpler alternatives are almost always fast enough.

Exercise 6 (Hard): Design a rate limiter shared by 64 threads, allowing 10,000 requests/s. Optimise for throughput and explain your concurrency choices.
Solution

The naive design is a single lock around a token bucket — and it becomes the bottleneck, because every one of the 64 threads must serialise through it on every request. At 10,000 req/s with a ~1 µs contended acquisition, the lock alone can consume a core and cause severe cache-line bouncing between threads.

Design 1 — sharded buckets (the main answer):

Split the global limit across N shards:
   64 threads, 16 shards → each shard permits 10,000/16 = 625 req/s
   Thread affinity: shard = thread_id % 16

Each shard is an independent token bucket with its own lock (or atomic).
Contention drops ~16x, and each shard's state sits on its own cache line
(pad to 64 bytes to avoid FALSE SHARING — otherwise adjacent shards
share a cache line and you keep the bouncing you tried to remove).

Trade-off: the limit becomes approximate. One shard can exhaust while
another has spare tokens, so effective throughput is slightly below
10,000. Mitigate with work stealing — a thread whose shard is empty
may try one other shard before rejecting.

Design 2 — atomic token bucket, lock-free:

Encode (tokens, last_refill_time) in a single 64-bit value and CAS it:

  do {
      old = state.get();
      refilled = refill(old, now());
      if (refilled.tokens < 1) return REJECT;
      next = refilled.withTokens(refilled.tokens - 1);
  } while (!state.compareAndSet(old, next));
  return ALLOW;

No blocking and no deadlock, but under 64-thread contention the CAS
retry loop burns CPU — often WORSE than a sharded lock at this level
of contention. Best when contention is moderate.

Design 3 — batched local permits (highest throughput):

Each thread acquires a BATCH of 100 permits from the shared bucket,
then serves 100 requests with zero shared-state access.

Shared-state operations drop 100x: 10,000/s becomes 100/s.
Trade-off: a thread holding unused permits when traffic shifts wastes
part of the budget, and burstiness increases. Return unused permits
on a timer, and keep batches small relative to the total.

What I'd choose: sharded buckets with cache-line padding, plus small batches per thread. That combination removes essentially all contention while keeping the limit close to accurate. I'd measure first, though — if the limiter is not actually hot, a single lock is simpler and fine.

The design point to state explicitly: a rate limit is inherently approximate. Insisting on an exact global count forces a single serialisation point, which caps throughput at exactly the moment you need throughput most. Accepting ±2% accuracy buys an order of magnitude in performance — and no product requirement meaningfully distinguishes 9,800 from 10,000 requests per second. Recognising that the requirement can flex is what unlocks the design, which is the same move as the approximate leaderboard rank in CAP.

For a distributed rate limiter across many instances, the same reasoning applies at a larger scale — see Design a Rate Limiter.

🎯 Key Takeaways

  • Atomicity and visibility are separate problems. An atomic write can still never be seen by another thread — that needs a memory barrier.
  • Locks provide both mutual exclusion and a happens-before relationship, which is why removing "an unnecessary lock" often introduces a visibility bug.
  • Contended locks cost ~100× uncontended ones. Never hold a lock across I/O — it serialises the system on that latency.
  • Break circular wait with consistent global lock ordering — free at runtime and enforceable by convention.
  • Livelock looks like a performance problem (busy CPU, no progress) and is fixed with randomised backoff; starvation is worse because aggregate metrics look healthy.
  • Size thread pools with cores × utilisation × (1 + wait/service) — threads don't create parallelism, cores do.
  • Bound your queues and use separate pools per dependency, or one slow downstream exhausts everything.
  • A slow dependency is worse than a dead one — it consumes the resource everyone shares.
  • Async makes waiting cheaper, not work faster. Virtual threads remove the trade entirely.
  • Never hand-write lock-free structures — ABA and memory ordering make this expert territory; use the standard library.
  • Double-checked locking without volatile is broken, and passes tests on x86 while failing on ARM.
  • The best fix is architectural: immutability and confinement eliminate the bug class rather than managing it.
