Realtime Apps (WebSockets, Push) Deep Dive

What you'll master: choosing a transport from the actual communication pattern rather than defaulting to WebSockets, why stateful connections break normal horizontal scaling and how a backplane fixes it, sizing a connection tier with real memory arithmetic, the three fan-out strategies and when each collapses, why reconnection is the failure mode that takes these systems down, and how to get delivery guarantees on top of a transport that offers none.

Prerequisites: Pub/Sub vs Message Queues (the backplane is a pub/sub problem), Heartbeat & Gossip (reconnection storms and jitter). Feeds Design a Chat System and Design a Notification System.

1. Choosing a Transport

TransportDirectionCostChoose when
PollingClient pulls on a timerWasteful — most requests return nothing; latency = poll intervalUpdates are rare and latency tolerance is tens of seconds. Genuinely fine more often than people admit.
Long pollingClient requests; server holds it open until data or timeoutOne connection per waiting client, plus reconnect overhead per messageFallback for restrictive networks. Largely legacy now.
SSE (Server-Sent Events)Server → client only, over plain HTTPOne connection; text onlyUnderused and often correct. Live scores, dashboards, notification streams, LLM token streaming. Auto-reconnect and event IDs are built into the protocol.
WebSocketFull duplex, persistentStateful connection; needs its own scaling storyGenuinely bidirectional, low-latency: chat, collaborative editing, multiplayer, trading.
Push notifications (APNs/FCM)Server → device, app closedThird-party dependency, no delivery guarantee, OS throttlingReaching users who aren't in your app. Complements the others — never replaces them.
WebRTC data channelsPeer to peerNAT traversal, TURN relay costsUltra-low latency or media where server relay is too slow or too expensive.
💡 The mistake is defaulting to WebSockets. Ask what the traffic actually looks like. If the client only receives, SSE is simpler: it runs over ordinary HTTP (so proxies, CDNs and HTTP/2 multiplexing all work), it reconnects automatically, and Last-Event-ID gives you resumption for free — a feature you would otherwise hand-build on WebSockets. If updates are rare and a few seconds of latency is fine, plain polling has no connection state to scale, which removes this entire lesson's hardest problem. Choose the weakest transport that meets the requirement.

2. Why Stateful Connections Break Normal Scaling

Stateless HTTP: any instance can serve any request. Add servers → done.

WebSockets: a connection is PINNED to one instance for its lifetime.

   Client A ══════ Server 1        Client B ══════ Server 2

Server 1 processes "A sends B a message" — but B's socket lives in
Server 2's memory. Server 1 has NO WAY to write to it.

This is the core problem. Every realtime architecture is a solution
to it.

The fix is a backplane — a pub/sub layer every instance subscribes to:

Server 1 (holds A)              Server 2 (holds B)
     │  publish to channel            │  subscribed to channel
     │      user:B                    │      user:B
     └──────────▶  REDIS PUB/SUB  ────┘
                                      │
                                      └─▶ writes to B's local socket

Business logic no longer needs to know WHERE a connection lives.
It publishes to a logical channel; whichever instance owns that
socket delivers it.
BackplaneStrengthsWeaknesses
Redis Pub/SubSimple, very low latency, ubiquitousFire-and-forget — a message published while an instance is briefly disconnected is lost forever. No persistence, no replay.
Redis StreamsPersistent, replayable, consumer groupsMore complex; needs trimming to bound memory
KafkaDurable, replayable, high throughputHigher latency than Redis; heavier to operate. Partition-per-user doesn't scale — you'd fan out differently.
Direct instance routingNo broker hop — lowest possible latencyNeeds a connection registry, and every instance must be able to reach every other. Used at very large scale where the broker becomes the bottleneck.

With direct routing you keep a registry mapping user → instance:

SET  conn:user123  "ws-node-7"  EX 60      -- refreshed by heartbeat
GET  conn:user123  →  "ws-node-7"          -- then POST directly to that node

Registry entries MUST expire. If a node dies without cleaning up, stale
entries route messages into a void — and the client, having reconnected
elsewhere, silently receives nothing. A TTL refreshed by heartbeat makes
staleness self-correcting.

3. Deep Dive: Sizing the Connection Tier

Connections are cheap individually and expensive in aggregate, and the arithmetic decides your architecture:

Per idle WebSocket connection:
   kernel socket buffers      ~4–16 KB   (tunable, and the dominant term)
   application object/state   ~2–10 KB   (user ID, subscriptions, buffers)
   TLS session state          ~1–4 KB
   ─────────────────────────────────────
   realistic total            ~10–40 KB

1,000,000 concurrent connections at 20 KB  =  20 GB of RAM
   → ~10 nodes at 64 GB, comfortably. NOT a memory wall.

The real limits you hit first:
   • File descriptors — default ulimit is often 1024. Raise to 1M+.
   • Ephemeral ports on any intermediary (~65K per source IP/dest pair)
   • The LOAD BALANCER's own connection table
   • Per-connection CPU for TLS handshakes during reconnect storms
   • Bandwidth: 1M clients × 1 msg/s × 200 B = 200 MB/s = 1.6 Gbps

A well-tuned event-loop server holds 100K–500K idle connections per node. The constraint is rarely steady-state memory — it's the churn: TLS handshakes, authentication and state rehydration during mass reconnection (section 5), which is a CPU problem, not a memory one.

⚠️ Deploys are the recurring operational pain nobody anticipates. Restarting a node drops every connection it holds, and those clients reconnect simultaneously. With 10 nodes and 1M connections, a rolling restart means 100K clients reconnecting per step — each requiring a TLS handshake, auth, and subscription rehydration. Mitigate by draining slowly (stop accepting new connections, then close existing ones gradually over minutes), and by having clients reconnect with jittered backoff. A naive rolling deploy of a large WebSocket tier is a self-inflicted outage.

4. Deep Dive: Fan-out Strategies

Realtime systems are fundamentally fan-out problems, and the right strategy depends entirely on the shape of the audience:

PatternMechanismBreaks when
Direct (1:1)Look up the recipient's instance; deliverRarely — this is the easy case
Room / topic (1:N, small N)Each instance holds local subscriber lists; the backplane publishes once per room and each instance fans out locallyFine to thousands per room. Note the key optimisation: the broker sends one message per instance, not per subscriber.
Broadcast (1:everyone)Publish once; every instance writes to all local socketsBandwidth-bound: 1M clients × 1 KB = 1 GB per broadcast. Batch and rate-limit.
Celebrity fan-outOne publisher, millions of subscribersThe hard case. A naive per-subscriber write is O(N) on one path. Needs a hierarchical or pull-based approach.
THE CELEBRITY PROBLEM — the same shape as the feed fan-out in the
estimation lesson:

  One message → 10,000,000 subscribers.
  Per-recipient delivery = 10M writes for ONE event.

Mitigations:
  1. HIERARCHICAL fan-out — publish to a small number of relay nodes,
     each of which fans out to its own subscriber shard. Turns one
     O(N) path into a tree of O(log N) depth.
  2. PULL for the long tail — the most-active subscribers get pushed;
     everyone else polls a cached "latest" value. A live view counter
     doesn't need per-user push.
  3. COALESCE — 50 updates in one second become one update carrying
     the latest state. This is the single biggest win for high-frequency
     data (presence, cursors, counters, prices).
  4. SAMPLE — at 100K chat messages/s in one stream, no human reads
     them all; deliver a representative subset.

Coalescing deserves emphasis because it's cheap and enormously effective. For any state update (a price, a cursor position, an online indicator, a progress bar), only the latest value matters. Buffer for 100–250 ms and send one message with the current state instead of twenty. This cuts bandwidth and client CPU by an order of magnitude while being imperceptible to users — and it works precisely because the data is state, not events.

5. Deep Dive: Reconnection — The Real Failure Mode

Realtime systems rarely fail under steady load. They fail when many clients reconnect at once, and the mechanism is a feedback loop:

A node crashes holding 100,000 connections.

  t=0    100K clients detect the drop
  t=1s   ALL of them reconnect simultaneously (no jitter)
         → surviving nodes take 100K TLS handshakes at once
         → CPU saturates; auth backend receives 100K requests
         → some reconnections time out
         → those clients retry, adding load
         → another node becomes overloaded and drops ITS connections
         → 200K clients now reconnecting... cascade.

This is the retry storm from the heartbeat lesson, with an expensive
per-connection setup cost that makes it far worse.

Defences, all of which must be client-side and server-side:

DefenceDetail
Jittered exponential backoffMandatory. random(0, min(cap, base·2ⁿ)) — full jitter, so 100K clients spread over the window rather than arriving together.
Connection rate limitingCap new connections per second per node. Rejecting quickly is far better than accepting and collapsing — the load-shedding principle again.
Resumable sessionsA session token that lets a reconnect skip full authentication and rehydrate subscriptions in one step. Cuts reconnect cost dramatically.
Stagger deploysDrain connections gradually over minutes; never restart multiple nodes at once.
Separate the auth pathDon't let a reconnect storm take down the auth service that everything else needs. Bulkhead it.
Heartbeat/ping tuningDetect dead connections without false positives. Too aggressive and you cause the disconnects you're detecting; too slow and you leak connections and route to the void.

Also note the silent-failure problem: TCP connections can be dead without either side noticing — a NAT timeout, a mobile network handover, or a proxy idle-timeout can drop a connection while both endpoints still believe it's open. The server thinks the client is connected and writes into the void; the client waits for messages that never come. Application-level ping/pong (WebSocket ping frames) at 20–60 second intervals is the only reliable detection, and it also keeps intermediaries from closing an idle connection.

6. Delivery Guarantees On A Transport That Has None

A WebSocket gives you ordered delivery while connected and nothing at all across a disconnect. If the socket drops, messages sent during the gap are simply gone. So durability must be built above the transport:

THE PATTERN — persist first, then push:

  1. Write the message to durable storage, assigning a monotonic
     sequence number per conversation/channel.
  2. Publish to the backplane for live delivery (best effort).
  3. Client tracks the last sequence number it has seen.
  4. On reconnect: GET /messages?after=<last_seq>  → the gap is filled.

The live socket is an OPTIMISATION for latency. Correctness comes from
the persisted log plus the catch-up query. Designing it the other way
round — treating the socket as the source of truth — is the mistake
that produces "messages sometimes vanish" bugs nobody can reproduce.

Match the guarantee to the data, because persistence isn't always warranted:

DataGuarantee neededApproach
Chat messageMust not be lost; order mattersPersist + sequence + catch-up on reconnect
Typing indicator, cursor positionNone — stale is worthlessFire and forget; coalesce aggressively
Presence (online/offline)Eventually correctPeriodic reconciliation; a TTL so a crashed client eventually appears offline
Price tick, live scoreLatest value onlyCoalesce; on reconnect fetch the current value rather than replaying history
Notification of a durable eventMust reach the user eventuallyPersist; push if connected, fall back to APNs/FCM or email
🎯 Staff-level insight: a great many "realtime" requirements are actually latency requirements with a durability requirement hiding inside them. Separating the two is the key design move: persist for correctness, push for speed. That separation also makes the system far easier to reason about during incidents — if the push tier is entirely down, users still get their data on the next poll or reconnect, degraded but not broken.

Interview Questions

🟢 Beginner — WebSocket or SSE for a live sports-score feed?

SSE, because the communication is one-directional: the server pushes scores and the client never needs to send anything back over the same channel. Choosing the weaker, simpler transport is the right instinct.

Concrete advantages here:

• It's ordinary HTTP, so existing proxies, load balancers, CDNs and HTTP/2 multiplexing all work without special configuration. WebSocket upgrades are blocked by some corporate proxies.
• Automatic reconnection is in the protocol — browsers reconnect on their own, and Last-Event-ID lets the server resume from where the client left off. On WebSockets you would hand-build both.
• Simpler server model — it's just a long-lived HTTP response writing text.

The limitations to acknowledge: SSE is text-only (binary needs encoding), and over HTTP/1.1 browsers cap connections per domain (~6), which matters if you open several streams — HTTP/2 removes that via multiplexing.

I'd switch to WebSockets if the product added genuinely bidirectional low-latency features — live chat alongside the scores, or in-play betting where client→server latency matters. And worth stating: if scores only update every 30 seconds, plain polling is entirely reasonable and has no connection state to scale at all.

🟢 Beginner — Why can't you scale WebSockets by just adding servers behind a load balancer?

Because a WebSocket connection is stateful and pinned. Once established, that socket lives in one specific instance's memory for its entire lifetime — unlike stateless HTTP, where any instance can serve any request.

So the problem isn't accepting connections (a load balancer distributes those fine) — it's reaching them:

Client A ══ Server 1        Client B ══ Server 2

Server 1 handles "A sends a message to B", but B's socket is in
Server 2's memory. Server 1 cannot write to it. There is no shared
place where connections live.

The fix is a backplane: every instance subscribes to a shared pub/sub layer (Redis Pub/Sub, Redis Streams, Kafka). Server 1 publishes to a logical channel like user:B; Server 2 is subscribed, receives it, and writes to B's local socket. Business logic then never needs to know where a connection lives.

The alternative at very large scale is a connection registry — Redis maps user:B → ws-node-7, and senders POST directly to that node, skipping the broker hop for lower latency. That requires registry entries with a TTL refreshed by heartbeat; otherwise a crashed node leaves stale entries and messages route into a void.

🟡 Mid — Design the connection tier for 1M concurrent WebSocket users. Size it. 
Memory per idle connection:
   socket buffers      ~4–16 KB
   app state           ~2–10 KB   (user, subscriptions, write buffer)
   TLS state           ~1–4 KB
   → ~20 KB realistic

1M × 20 KB = 20 GB total
   → 10 nodes × 64 GB, holding ~100K connections each,
     using ~2 GB for connections and leaving ample headroom.

Bandwidth: 1M × 1 msg/s × 200 B = 200 MB/s ≈ 1.6 Gbps aggregate
   → ~160 Mbps per node. Comfortable.

The limits you actually hit first — memory is not the constraint:

• File descriptors: default ulimit is often 1024. Raise to 1M+ and tune net.core.somaxconn and the ephemeral port range.
• Load balancer connection tables — a million long-lived connections is a very different profile from a million short requests, and many LBs are priced or capped on concurrent connections.
• CPU during reconnect storms — TLS handshakes, not steady-state traffic, are what saturate these nodes.

Architecture: stateless-ish connection nodes (holding only sockets and subscriptions) behind an L4 load balancer; a Redis backplane for message routing; a connection registry with heartbeat TTLs; and business logic in separate services that publish to the backplane. Separating the connection tier from application logic matters — it lets you deploy business changes without dropping a million connections.

Capacity planning for failure: size for N−1 or N−2 nodes. Losing one node means 100K clients reconnect at once, and the survivors must absorb them — so run at ~60–70% and enforce per-node connection rate limits so a reconnect surge is shed rather than cascading.

The operational detail I'd raise unprompted: deploys. Restarting a node drops 100K connections. Drain gradually — stop accepting new connections, then close existing ones over several minutes — and require jittered client backoff, or a routine rolling deploy becomes an outage.

🟡 Mid — A user is offline when a message is sent. How do you guarantee they receive it?

You don't get this from the transport — a WebSocket delivers only while connected, and anything sent during a disconnect is gone. Durability has to be built above it.

The pattern: persist first, push second.

1. Write the message to durable storage with a monotonic sequence
   number per conversation.
2. Publish to the backplane for live delivery (best effort).
3. The client tracks the highest sequence number it has seen.
4. On reconnect: GET /messages?after=<last_seq> to fill the gap.

The live socket becomes a latency optimisation; correctness comes from the persisted log plus the catch-up query. Building it the other way round — treating the socket as the source of truth — is what produces "messages occasionally vanish" bugs that nobody can reproduce, because they only occur during disconnects.

Sequence numbers rather than timestamps: clocks skew across servers, and two messages can share a millisecond. A per-conversation monotonic counter gives an unambiguous "everything after X", which is exactly the query the client needs.

For a user offline for a long time, layer on:

• Push notifications (APNs/FCM) so they learn something happened while the app is closed — necessary because mobile OSes kill background sockets.
• A bounded catch-up. Don't replay 10,000 messages on reconnect; return the most recent N plus a cursor, and let the client page backwards. Otherwise a long-absent user triggers an enormous payload at exactly the moment the connection is fragile.
• Deduplication by message ID, since at-least-once delivery means the client may receive a message live and in the catch-up.

Finally, match the guarantee to the data: a chat message needs all of this; a typing indicator needs none of it, and persisting ephemeral state is wasted work.

🔴 Senior — A node holding 200K connections crashes. Trace what happens and design to contain it.

What happens without protection:

t=0     Node dies. 200K clients see the socket close.
t=0–1s  Client libraries reconnect — most default to an IMMEDIATE
        retry, so ~200K connection attempts hit the LB at once.
t=1s    Surviving nodes must perform 200K TLS handshakes plus auth.
        TLS is CPU-expensive; the tier saturates.
t=2–5s  Auth service receives 200K requests — it was sized for
        steady-state login, not this.
        Some reconnects time out → clients retry → more load.
t=5s+   A second node's event loop stalls under handshake load,
        health checks fail, it is pulled from rotation, dropping
        ITS connections → 400K clients reconnecting → cascade.

The crash was survivable; the RECONNECTION was not.

Containment, layered:

1. Jittered backoff on the client — the single most important control. random(0, min(30s, 1s·2ⁿ)) spreads 200K reconnects over tens of seconds instead of one. Since this lives in client code, it must be right before you need it — you cannot deploy a fix to disconnected clients, which makes it a genuinely critical design decision rather than an implementation detail.

2. Per-node connection rate limiting — accept, say, 2K new connections/s per node and reject the rest quickly with a retry hint. Fast rejection is vastly better than slow acceptance; this is load shedding applied to connection establishment.

3. Resumable sessions — a signed session token lets a reconnect skip full authentication and rehydrate subscriptions in one round trip. This cuts the per-reconnect cost, which is what makes the storm survivable rather than merely slower.

4. Bulkhead the auth path so a reconnect surge can't take down authentication for the rest of the platform.

5. Capacity headroom — run at 60–70% so N−1 nodes can absorb the load. Sizing to 100% guarantees the cascade.

6. Faster failure detection with stale-registry cleanup — TTL'd registry entries mean senders stop routing to the dead node within seconds instead of writing into the void.

The general principle: in stateful connection systems the expensive event is establishment, not steady state. So capacity planning must be driven by the reconnection scenario, and the correctness of the client's retry logic is part of your server architecture — an unusual property worth calling out, because it means shipping a bad client backoff is a production risk you can't hotfix.

🔴 Senior — Design realtime updates for a collaborative document editor with 50 concurrent editors per document.

The hard part isn't transport — it's concurrent conflicting edits. Fifty people typing in one document means concurrent operations on shared state with no lock, so the core question is how edits converge.

Convergence strategy:

ApproachTrade-off
OT (Operational Transformation)What Google Docs uses. Transforms each operation against concurrent ones. Requires a central server to establish order, and the transform functions are notoriously subtle to get right.
CRDT (e.g. RGA, Yjs, Automerge)Converges by construction with no central authority; supports offline editing naturally. Costs metadata per character (tombstones), so document size grows with edit history.
Locking / sectionsSimple but a poor experience — users blocked from editing the same paragraph.

I'd choose a CRDT (a mature library, not a hand-rolled one) for a new build: it tolerates offline editing and network partitions without a central sequencer, which is a large practical advantage. OT is defensible if there's an existing server-authoritative architecture.

Transport and topology: WebSockets, genuinely bidirectional here. Documents are the natural sharding unit — route all editors of one document to the same node via consistent hashing on document_id. That's the key architectural move: it makes fan-out in-process (50 local sockets, no broker hop per keystroke) and gives a single place to hold document state. The backplane is then only needed for cross-node concerns and failover.

Message design — this is where naive implementations fall over:

Keystrokes at 5/s × 50 editors = 250 ops/s per document,
each fanning out to 49 peers = ~12,000 messages/s per document.

Fixes:
  - BATCH: buffer 50–100 ms and send accumulated ops in one frame.
    Sub-100 ms feels instantaneous, and this cuts messages ~10x.
  - COALESCE presence/cursor updates hard — they are pure state,
    so only the latest matters. Cursors at 20 Hz become 5 Hz.
  - SEND DELTAS, never whole documents.

Persistence and correctness: the socket is not the source of truth. Persist the operation log (or CRDT updates) with sequence numbers; clients reconnect with their last-seen sequence and receive the delta. Periodically write a snapshot plus trimmed log so opening a document doesn't mean replaying a year of operations — the same checkpoint pattern as the ledger in concurrency control.

Failure handling: if the owning node dies, editors reconnect and consistent hashing routes them to a new node, which rehydrates from the snapshot plus log. Because CRDT state converges, clients can replay their unacknowledged local operations safely — offline edits merge on reconnect without conflict, which is precisely why CRDTs were worth their metadata overhead here.

And the thing I'd flag as most often missed: undo. In a collaborative context, undo must be per user — undoing your own last edit, not the document's last edit, which may belong to someone else. That constrains the operation model from the start and is far harder to retrofit than to design in.

🏋️ Graded Exercises

Exercise 1 (Easy): For each, choose a transport: (a) stock ticker, (b) multiplayer game, (c) "your order shipped" alert to a closed mobile app, (d) a dashboard refreshing every 30 s.
Solution

(a) Stock ticker → SSE. One-directional server push. Works over plain HTTP with automatic reconnection and Last-Event-ID resumption built in. Coalesce aggressively — only the latest price matters, so buffer and send the current value rather than every tick.

(b) Multiplayer game → WebSocket (or WebRTC/UDP for fast-paced action). Genuinely bidirectional and latency-critical: clients send input continuously and receive state continuously. For twitch games, WebRTC data channels with unreliable delivery beat TCP-based WebSockets, because a retransmitted stale position is worse than a dropped one.

(c) Order-shipped alert to a closed app → push notification (APNs/FCM). This is the only option — mobile operating systems terminate background sockets, so no persistent connection exists to deliver over. Persist the notification too, so it appears in-app when opened.

(d) Dashboard refreshing every 30 s → polling. No connection state, trivially scalable, cacheable at the CDN, and 30 seconds of latency tolerance means realtime infrastructure buys nothing. This is the option people skip past, and it's frequently correct.

The pattern: match the transport to the actual communication direction and latency requirement, and choose the weakest one that satisfies them.

Exercise 2 (Easy): Why does a chat backend need Redis (or similar) even when all servers share a database?
Solution

Because a database solves storage, not notification. Server 1 can write A's message to the shared database perfectly well — but B's WebSocket lives in Server 2's memory, and Server 2 has no idea a new row appeared.

Without a pub/sub layer the only option is for every server to poll the database for new messages for every connected user — which reintroduces polling latency, and at 100K connected users becomes a crushing query load for something that is almost always "nothing new".

Redis Pub/Sub (or Streams) provides the push signal: Server 1 publishes to user:B, Server 2 is subscribed, receives it immediately, and writes to B's local socket. It's the notification channel between server instances, complementing rather than replacing the database.

The important caveat: Redis Pub/Sub is fire-and-forget. If Server 2 is briefly disconnected from Redis, that message is lost with no replay. That's acceptable precisely because the database holds the durable copy — the client reconnects and catches up via ?after=<last_seq>. Pub/Sub delivers speed; the database delivers correctness. Using Pub/Sub as the only path is the design error.

Exercise 3 (Medium): Implement client reconnection logic correctly. What must it handle beyond retrying?
Solution 
class RealtimeClient {
  constructor(url) {
    this.url = url; this.attempt = 0;
    this.lastSeq = 0;              // for gap recovery
    this.intentionalClose = false;
    this.pingTimer = null;
  }

  connect() {
    this.ws = new WebSocket(`${this.url}?after=${this.lastSeq}`);

    this.ws.onopen = () => {
      this.attempt = 0;            // reset backoff ONLY on success
      this.startHeartbeat();
      this.resubscribe();          // re-establish server-side state
    };

    this.ws.onmessage = (e) => {
      const msg = JSON.parse(e.data);
      if (msg.type === 'pong') { this.pongSeen = true; return; }
      if (msg.seq <= this.lastSeq) return;   // dedupe: live + catch-up overlap
      this.lastSeq = msg.seq;
      this.handle(msg);
    };

    this.ws.onclose = () => {
      this.stopHeartbeat();
      if (this.intentionalClose) return;
      // FULL JITTER — never a fixed delay
      const cap = 30000;
      const delay = Math.random() * Math.min(cap, 1000 * 2 ** this.attempt);
      this.attempt++;
      setTimeout(() => this.connect(), delay);
    };
  }

  startHeartbeat() {               // detect SILENTLY dead connections
    this.pingTimer = setInterval(() => {
      if (!this.pongSeen) { this.ws.close(); return; }  // no reply → dead
      this.pongSeen = false;
      this.ws.send(JSON.stringify({ type: 'ping' }));
    }, 30000);
  }
}

What it must handle beyond retrying:

1. Full jitter — random(0, min(cap, base·2ⁿ)). Without it, every client that dropped together reconnects together. This is the one thing that cannot be fixed server-side later.
2. Gap recovery — track lastSeq and request everything after it on reconnect, or messages sent during the outage are silently lost.
3. Deduplication — the catch-up query and the live stream overlap, so the same message arrives twice. Drop anything at or below lastSeq.
4. Application-level heartbeat — TCP connections die silently through NAT and proxy timeouts. Without ping/pong the client waits forever on a dead socket, believing it's connected.
5. Resubscription — server-side subscription state died with the old connection.
6. Reset backoff only on a successful connection, not on the attempt, or a connect-then-immediately-drop loop hammers the server at full rate.
7. Distinguish intentional closes so logging out doesn't trigger reconnection.

Worth adding in production: stop reconnecting when the browser reports offline and reconnect promptly on the online event, and pause or slow reconnection when the tab is hidden.

Exercise 4 (Medium): A live-streaming chat has 500K viewers in one room sending 1,000 messages/s. Compute the fan-out and make it feasible.
Solution 
Naive: every message to every viewer
   1,000 msg/s × 500,000 viewers = 500,000,000 deliveries/s
   at 100 bytes each = 50 GB/s = 400 Gbps

Completely infeasible — and no amount of horizontal scaling fixes it,
because the product of messages and recipients is the problem.

The requirement itself has to change, and the justification is that no human reads 1,000 messages per second — the chat is ambient texture, not a transcript. That observation is what unlocks the design.

1. Sample. Deliver ~10–20 messages/s rather than 1,000, chosen to include moderator and creator messages plus a random sample of the rest. Instantly a 50–100× reduction, and the experience is subjectively unchanged. This is what large streaming platforms actually do.

2. Batch. Group the sampled messages into one frame every 200 ms instead of sending each individually. Cuts message overhead ~4× and dramatically reduces client-side render churn.

After sampling + batching:
   20 msg/s → 5 batched frames/s × 500K viewers = 2.5M sends/s
   at ~500 B per batch = 1.25 GB/s ≈ 10 Gbps
   → spread over 20 nodes = 500 Mbps each. Feasible.

3. Fan out hierarchically. Publish once to the backplane per batch; each connection node fans out to its own local sockets. The broker handles ~20 messages per batch (one per node), not 500,000 — this is the difference between a working design and a broker meltdown.

4. Shard viewers across nodes by consistent hashing, so each holds ~25K of the room's connections.

5. Rate-limit senders (e.g. one message per few seconds per user, slow mode) — this caps the input side, and it's also the primary spam control.

The transferable lesson: when fan-out arithmetic returns an impossible number, the answer is almost never "scale harder" — it's to question whether the literal requirement is what users actually need. Sampling a 1,000 msg/s chat loses nothing a viewer could have perceived.

Exercise 5 (Hard): Your realtime tier is healthy but users report messages arriving minutes late, or not at all, then appearing on refresh. Diagnose.
Solution

"Appears on refresh" is the decisive clue: the data is persisted correctly and the push path is failing. That splits the problem cleanly — this is a delivery bug, not a storage bug.

Candidate causes, in the order I'd check them:

1. Silently dead connections (most likely). A NAT timeout, mobile handover, or proxy idle-timeout dropped the TCP connection without either side noticing. The server believes the client is connected and writes into a void; the client waits for messages that never arrive. On refresh, a fresh connection plus catch-up query shows everything.
Check: compare server-side "connected users" against genuinely active clients — a large discrepancy confirms it. Fix: application-level ping/pong every 20–60 s, closing the socket when a pong is missed.

2. Stale connection registry. A node crashed and left entries pointing at it, so senders route messages to a node that no longer holds the socket. Fix with a short TTL refreshed by heartbeat.

3. Backplane message loss. If it's Redis Pub/Sub, any subscriber briefly disconnected loses messages permanently — there's no replay. This produces exactly "some messages never arrive" with no errors anywhere. Fix by moving to Redis Streams/Kafka, or by relying on the persisted log plus catch-up (which is the correct architecture regardless).

4. Slow-consumer backpressure. If a client can't drain fast enough, the server's write buffer grows. Some servers block, some buffer unboundedly (memory leak), some drop. Minutes of delay strongly suggests a growing buffer. Check: per-connection write-buffer sizes. Fix: bound the buffer and disconnect slow consumers, letting them reconnect and catch up — better than degrading everyone.

5. Event-loop blocking. A synchronous operation on the connection node stalls all its sockets simultaneously. Check: event-loop lag metrics; symptoms cluster by node.

Diagnostic approach: instrument the pipeline end to end — persisted → published to backplane → received by node → written to socket → acknowledged by client. Timestamp each stage. Whichever hop shows the gap identifies the layer, and this instrumentation is worth having permanently, because "messages sometimes don't arrive" is otherwise nearly impossible to reproduce.

The architectural point: a system where the socket is the only delivery path will always produce this class of bug. Persist-plus-catch-up makes push a best-effort optimisation, so silent connection death degrades latency instead of losing data.

Exercise 6 (Hard): Design presence ("who's online") for 10M users with friend lists averaging 200. Name what makes it expensive.
Solution

What makes it expensive is fan-out on state change, not storage:

Storage is trivial: 10M users × ~20 B = 200 MB in Redis.

The cost is NOTIFICATION:
  a user going online/offline notifies ~200 friends.
  With 10M users and (say) 5 status changes per user per hour:
     10M × 5 = 50M changes/hour = ~14,000/s
     × 200 friends = 2,800,000 notifications/s

Mobile makes it far worse: connectivity flaps constantly, so naive
presence generates enormous churn from users who never actually
went away.

Design:

1. TTL-based state, not explicit online/offline. Clients heartbeat every ~30 s; SET presence:user123 online EX 60. Online means "the key exists". This self-heals when a client crashes without sending a disconnect — the single most important design choice here, because explicit offline signals are exactly what unreliable networks fail to deliver.

2. Debounce transitions. Don't broadcast offline the instant a heartbeat is missed; wait 60–90 s. Most mobile disconnections are brief handovers, and debouncing eliminates the majority of churn — the largest single reduction available.

3. Pull, don't push, for the long tail. This is the key move:

Push presence changes ONLY to friends who are currently:
   - online, AND
   - actually viewing a surface that displays presence
     (a chat list, a friends panel)

Everyone else PULLS when they open such a view:
   MGET presence:friend1 presence:friend2 ... (200 keys, one round trip)

Nobody needs realtime presence for friends whose status they aren't
looking at. This collapses 2.8M notifications/s to a small fraction.

4. Coalesce and batch whatever push remains: buffer 5–10 s and send one presence-delta message rather than individual events.

5. Accept approximate correctness. Presence is inherently stale — a user can walk into a tunnel a millisecond after the check. Users understand and tolerate this, so paying for strict accuracy is wasted money. Design to "correct within a minute", and prefer showing "active recently" over a binary indicator, which is both cheaper and more honest.

The celebrity case: a user with 100,000 followers changing status would notify 100K people. Cap push fan-out above a threshold and make those users pull-only — the same hybrid push/pull split as the feed fan-out in estimation.

The framing that matters: presence looks like a storage problem and is actually a fan-out problem, and the winning move is reducing who needs to know rather than making notification faster.

🎯 Key Takeaways

  • Choose the weakest transport that meets the requirement. SSE for server→client only; polling when latency tolerance is tens of seconds — it has no connection state to scale.
  • WebSocket connections are pinned to one instance, so another instance cannot write to them. Every realtime architecture is a solution to that.
  • A backplane (pub/sub) decouples business logic from connection location — publish to a logical channel, and whichever node owns the socket delivers.
  • Redis Pub/Sub is fire-and-forget. It's fine as a speed layer over a durable log, and wrong as the only delivery path.
  • Persist first, push second. The socket is a latency optimisation; correctness comes from a sequenced log plus catch-up on reconnect.
  • Memory isn't the connection-tier limit — 1M connections is ~20 GB. File descriptors, LB connection tables, and reconnect-time CPU are.
  • Reconnection is the real failure mode. Mass simultaneous reconnects cause TLS-handshake storms that cascade across nodes.
  • Client backoff with full jitter is part of your server architecture — and you can't hotfix it, because the affected clients are disconnected.
  • Drain deploys slowly. Restarting a WebSocket tier quickly is a self-inflicted outage.
  • Application-level ping/pong is mandatory — TCP connections die silently through NAT and proxy timeouts, and the server writes into the void.
  • Fan out once per node, not once per subscriber, and coalesce state updates into 100–250 ms windows.
  • When fan-out arithmetic returns an impossible number, question the requirement — sampling, batching and pull-for-the-long-tail beat scaling harder.
