Authentication (JWT, OAuth2, OIDC) Deep Dive

What you'll master: why sessions-vs-tokens is a state placement decision rather than a security one, the revocation problem and the honest ways to solve it, the OAuth 2.1 authorization code flow with PKCE (and why the implicit flow is now forbidden), the difference between authentication and authorization that OIDC exists to fix, the JWT vulnerabilities that have produced real CVEs, and how to design auth across services without creating a system where any internal caller can impersonate anyone.

Prerequisites: REST & API Contracts, Caching Strategies (the authorization-caching trap). Pairs with Security Deep Dive and Microservices.

⚠️ Terminology first, because interviews probe it: Authentication (AuthN) = who are you. Authorization (AuthZ) = what may you do. OAuth 2.0 is an authorization framework — using it alone to prove identity is the mistake OIDC was created to fix. Getting these two words right, consistently, is a small thing that reads as professional competence.

1. Sessions vs Tokens: A State Placement Decision

Server-side sessionsSelf-contained tokens (JWT)
Where state livesServer (Redis / database)In the token, held by the client
Per-request costA lookup (~0.5–1 ms to Redis)Signature verification (~0.01–0.1 ms, local)
RevocationInstant — delete the sessionHard — valid until expiry, by design
Horizontal scalingNeeds shared session storageAny instance validates independently
Size on the wire~32-byte opaque IDHundreds of bytes to several KB, on every request
Claim freshnessAlways current — you read it liveFrozen at issue time. A revoked role stays effective until expiry
Failure modeSession store down → nobody can authenticateSigning key compromised → attacker mints valid tokens

The honest assessment, because JWTs are widely over-recommended: a Redis session lookup costs well under a millisecond, and you almost certainly already run Redis. For a single first-party application, sessions are usually the better default — instant revocation, live claims, and small cookies. JWTs earn their complexity when you have genuinely distributed verification: multiple services or organisations that must validate independently, third-party API access, or federation across trust boundaries.

The "stateless scaling" argument, examined honestly:

  Claim:   "JWTs scale better — no shared session store."
  Reality: you will add a shared store anyway, for token revocation,
           refresh-token rotation and reuse detection. You end up with
           BOTH a token layer AND server state — the worst of both —
           unless you genuinely never need to revoke.

  Redis session lookup: ~0.5 ms, and it scales to ~100K ops/s per node.
  That is not the bottleneck anyone claims it is.

Choose JWTs for DISTRIBUTED VERIFICATION, not for performance.

2. Deep Dive: The Revocation Problem

A signed token is valid until it expires. Nothing the server does changes that, because verification is purely local — the server never consults anything. So "log this user out everywhere, now" has no direct answer, and this is the most-tested nuance in the topic.

Why the naive answer is wrong: "the client deletes the token" only helps an honest client. An attacker who stole the token keeps using it, and that's exactly the scenario revocation exists for.

ApproachHowHonest assessment
Short expiry + refresh tokensAccess token lives 5–15 min; a long-lived refresh token is exchanged for new ones and is revocable server-sideThe standard answer. Bounds exposure to the access-token lifetime. Note it doesn't achieve instant revocation — it bounds it.
Denylist of revoked JTIsCheck each token's ID against a shared blocklistInstant, but reintroduces a lookup on every request — you've rebuilt sessions with extra steps. Denylist entries only need to live until the token's natural expiry, so it stays small.
Per-user token version / epochEmbed tv:5; bump the user's version to invalidate all their tokens at onceElegant for "log out everywhere" and password changes — one write invalidates every token for that user. Still needs a lookup, but a tiny, highly cacheable one.
Rotate the signing keyInvalidate every token system-wideThe break-glass option for a suspected key compromise. Logs out every user simultaneously — appropriate for an incident, never for routine revocation.

Refresh token rotation with reuse detection is the pattern worth knowing in detail, because it turns a stolen refresh token from a permanent compromise into a detectable event:

Each refresh consumes the old token and issues a NEW one, with the
family tracked server-side:

   RT1 → (refresh) → RT2, and RT1 is marked USED
   RT2 → (refresh) → RT3, and RT2 is marked USED

If RT1 is EVER presented again, one of two things is true: an attacker
stole it, or the legitimate client is replaying. Either way you cannot
tell which — so REVOKE THE ENTIRE FAMILY and force re-authentication.

Result: a stolen refresh token grants at most ONE refresh before the
theft is detected and the whole chain dies. Without rotation, a stolen
refresh token is indefinite access.
🎯 The framing that answers "how do you revoke a JWT?" well: "You can't — not directly, and that's the deliberate trade for stateless verification. What you do is bound the window: short-lived access tokens plus revocable, rotating refresh tokens with reuse detection. If the requirement is genuinely instant revocation — a banking session, an admin console — then either check a denylist on every request or use server-side sessions, and accept that you've chosen state over statelessness. Pretending JWTs give you both is the wrong answer."

3. OAuth 2.0: Delegated Authorization

The problem OAuth solves: "let this app read my Google Calendar without giving it my Google password." Four roles:

Resource Owner       the user who owns the data
Client               the application requesting access
Authorization Server issues tokens (Google's login/consent)
Resource Server      hosts the API the token unlocks (Calendar API)

The Authorization Code flow with PKCE — the only flow you should propose for new work:

1. Client → browser → Authorization Server
      Sends: client_id, redirect_uri, scope, state,
             code_challenge = SHA256(code_verifier)   ← PKCE
      (code_verifier is a high-entropy random string the client keeps.)

2. User authenticates AT the Authorization Server and approves the scope.
      The client never sees the password. That is the whole point.

3. Authorization Server → browser → redirect_uri?code=XYZ&state=...
      Client MUST verify `state` matches what it sent  → CSRF protection.

4. Client → Authorization Server  (back channel, server-to-server)
      Sends: code=XYZ, code_verifier, client_id (+ client_secret if
             it is a confidential client)
      Server checks SHA256(code_verifier) == the stored code_challenge.

5. Authorization Server → Client:  access_token (+ refresh_token,
                                    + id_token if OIDC)

6. Client → Resource Server:  Authorization: Bearer <access_token>

Why PKCE exists, concretely. The authorization code travels through the browser — a URL redirect — where a malicious app registered for the same custom URI scheme, browser history, or a proxy log could capture it. Without PKCE, whoever holds the code can exchange it for a token. PKCE binds the code to the specific client instance that started the flow: the attacker has the code but not the code_verifier, so the exchange fails.

PKCE was originally designed for mobile apps, which cannot keep a client secret (anyone can decompile the binary). OAuth 2.1 requires PKCE for all clients, including confidential server-side ones, because it defends against code interception regardless of client type.

FlowStatusNotes
Authorization Code + PKCE✅ Use thisThe answer for web apps, SPAs and mobile alike.
Client Credentials✅ Machine-to-machineNo user involved — a service authenticating as itself.
Implicit❌ Removed in OAuth 2.1Returned the access token directly in the URL fragment — exposed in browser history, referrer headers and logs, with no way to authenticate the client. Superseded by Authorization Code + PKCE.
Resource Owner Password Credentials❌ Removed in OAuth 2.1The app collects the user's password directly — defeating OAuth's entire purpose, and incompatible with MFA and federated login.
Device Authorization✅ For input-constrained devicesTVs and CLIs: show a code, user authorises on their phone.

4. OIDC: The Identity Layer OAuth Lacks

OAuth 2.0 tokens answer "may this client access this resource?" They are deliberately opaque to the client and carry no standard, verifiable statement of who the user is.

THE CONFUSED DEPUTY PROBLEM — why "log in with OAuth" alone is broken:

Attacker obtains an access token for THEIR OWN account at Provider P
(trivial — they just authorise their own account in some app they control).
They present that token to YourApp's "log in with P" endpoint.
YourApp calls P's userinfo API with the token, gets a valid response,
and logs the attacker in...

...as whoever that token belongs to. Since YourApp never verified the
token was ISSUED FOR YourApp, a token minted for a completely different
application is accepted. This is a real historical vulnerability class.

OIDC fixes it with the ID TOKEN — a JWT whose `aud` (audience) claim
names YOUR client_id, and whose signature you verify against the
provider's published keys. A token issued for another app fails the
audience check.

ID token vs access token — the distinction that matters:

ID token (OIDC)Access token (OAuth 2.0)
AnswersWho is the user? (authentication)What may the bearer do? (authorization)
Audience (aud)Your client_id — you must verify thisThe resource server
FormatAlways a JWT with defined claimsOpaque to the client — do not parse it
Consumed byThe client, once, at loginThe resource server, on every API call

Claims you must validate on an ID token, in order — skipping any of these is a real vulnerability, not a style issue:

1. SIGNATURE  against the provider's JWKS (fetched from the discovery
              document, cached, keyed by the token's `kid`)
2. iss        matches the expected issuer exactly
3. aud        contains YOUR client_id            ← blocks confused deputy
4. exp / nbf  not expired, not before valid time
5. nonce      matches the nonce you sent          ← blocks replay
6. azp        if present, matches your client_id

5. Deep Dive: JWT Vulnerabilities That Produced Real CVEs

These are not theoretical. Each has shipped in widely-used libraries.

❌ alg: none 
{"alg":"none","typ":"JWT"}

Some libraries honoured the header
and skipped verification entirely.
An attacker edits the payload,
strips the signature, sets
alg:none — and it validates.

The bug: TRUSTING the token's own
header to decide how to verify it.
The token is attacker-controlled
input; its header is not a
trustworthy instruction.
✅ Pin the algorithm 
jwt.verify(token, publicKey, {
  algorithms: ['RS256'],   // explicit
  issuer:   'https://...',
  audience: 'my-client-id'
});

The VERIFIER decides the algorithm,
never the token. Also pin issuer
and audience — a signature check
alone proves the token is genuine,
not that it was meant for you.

Algorithm confusion (RS256 → HS256) is the subtler sibling, and worth understanding because the mechanism is instructive:

Your server verifies RS256 (asymmetric): sign with the PRIVATE key,
verify with the PUBLIC key. The public key is, by definition, public.

Attacker changes the header to HS256 (symmetric HMAC) and signs the
forged token using YOUR PUBLIC KEY AS THE HMAC SECRET.

A naive library does: verify(token, key) — reading `alg` from the token
to pick the routine. It runs HMAC-SHA256 with the public key as the
secret... which is exactly what the attacker did. It validates.

Fix: pin `algorithms: ['RS256']` so an HS256 token is rejected before
any key material is used. This is why "just call verify(token, key)"
is insufficient — the algorithm must be an argument, not an inference.

⚠️ The single most misunderstood fact about JWTs: the payload is base64url-encoded, not encrypted. Anyone holding the token can read every claim — paste it into jwt.io and it's plain text. The signature guarantees integrity (it hasn't been altered), never confidentiality. Never put PII you wouldn't log, internal IDs you don't want exposed, or anything secret into a JWT.

6. Token Storage In Browsers: Choosing Which Attack To Prevent

There's no option immune to everything, so the decision is which threat dominates:

StorageXSS exposureCSRF exposureVerdict
localStorageFully exposed — any injected script reads itNot automatically sent, so no CSRFCommon and weak. One XSS means total account compromise, and tokens can be exfiltrated silently.
JS-readable cookieFully exposedVulnerable (sent automatically)Worst of both. Avoid.
HttpOnly; Secure; SameSite cookieNot readable by JSMitigated by SameSite=Lax/Strict + CSRF tokens for state-changing requestsBest default. XSS can still use the cookie by making requests from the page, but cannot exfiltrate the token itself.
In-memory only (JS variable)Exposed while running, but gone on refreshNo CSRFGood for short-lived access tokens, paired with an HttpOnly refresh cookie. Requires a silent-refresh path on page load.

The pattern used by well-built SPAs: refresh token in an HttpOnly, Secure, SameSite=Strict cookie scoped to the token endpoint; access token held in memory only, refreshed silently on load. This limits XSS damage to the current page session rather than yielding a durable, exfiltratable credential — and it accepts a small UX cost (a refresh call on every page load) for a real security gain.

7. Deep Dive: Auth Across Services (And Its Central Hazard)

Client → API Gateway
            ├─ validate the external token ONCE (signature, iss, aud, exp)
            ├─ authenticate the CALLER (mTLS / service identity)
            └─ mint an INTERNAL token with verified claims
                 ↓
         Internal services validate the INTERNAL token

The hazard, and it's the thing most designs get wrong: if the gateway simply forwards X-User-Id: 123 as a plain header and services trust it, then any caller that can reach a service internally can impersonate any user. One SSRF vulnerability, one compromised pod, or one misconfigured network policy becomes total account takeover. Perimeter-only security assumes the internal network is trustworthy, which it isn't.

ApproachSecurityCost
Plain header (X-User-Id)Weak — trivially spoofed by any internal callerFree. Acceptable only with genuinely enforced network isolation and mTLS between every hop.
Forward the original tokenGood — services verify independentlyEvery service needs IdP/JWKS connectivity; the token's audience wasn't meant for them.
Gateway-minted internal tokenStrong — short-lived, signed, audience-scoped per serviceThe gateway becomes a signing authority; key management required. The usual right answer.
mTLS + service identity (SPIFFE)Strong for service identityProves which service is calling, not which user — combine with a user token, don't substitute.

Cache the JWKS, don't fetch per request. Fetching the provider's keys on every validation adds a network hop to every request and makes the IdP a hard dependency on your hot path. Cache by kid with a TTL (hours), refresh on an unknown kid (with rate limiting so an attacker can't force unbounded fetches), and keep serving the cached key if the fetch fails.

And do not cache the authorization decision — cache the inputs and re-evaluate. As covered in Caching Strategies, a cached "user X may do Y" means a revoked permission remains effective for the TTL: a security hole with a countdown.

Interview Questions

🟢 Beginner — Sessions or JWTs? What's the actual trade-off?

It's fundamentally a decision about where the state lives, and the real trade is revocation against distributed verification.

Server-side sessions: the server stores the session and gives the client an opaque ID. Every request does a lookup. You get instant revocation (delete the session), always-current claims (a role change takes effect immediately), and a tiny cookie. The cost is shared session storage across instances.

JWTs: the token carries signed claims, so any instance verifies locally with no lookup. The cost is that revocation is hard by design — verification consults nothing, so a valid signature is accepted until expiry — and claims are frozen at issue time.

What I'd push back on is the usual justification. "JWTs scale better" overstates it: a Redis session lookup is well under a millisecond and handles ~100K ops/s per node, so it's rarely the bottleneck. And in practice you add shared state anyway for refresh-token rotation and revocation, ending up with both a token layer and server state.

So: sessions are a good default for a single first-party application. JWTs earn their complexity when verification must be genuinely distributed — many services or organisations validating independently, third-party API access, or federation across trust boundaries. A common hybrid is sessions for your own web app and JWTs for your public API.

🟢 Beginner — What problem does OAuth 2.0 solve, and how is OIDC different?

OAuth 2.0 solves delegated authorization: letting an application access a subset of your data on another service without giving it your password. You authenticate at the provider, approve a specific scope, and the app receives a scoped, independently revocable token. Before OAuth, apps asked for your actual password — which gave unlimited access with no way to revoke it short of a password change.

OIDC adds authentication on top. OAuth's access tokens answer "may this client access this resource?" and are deliberately opaque to the client — they carry no standardised, verifiable statement of who the user is. Using them to log someone in is unsafe: an attacker can present a token issued for a different application, and if you just call a userinfo endpoint with it, you'll happily log them in as its owner. That's the confused deputy problem.

OIDC introduces the ID token — a JWT with defined claims whose aud (audience) names your client_id, signed by the provider. You verify the signature against their published keys and check the audience, so a token minted for another app is rejected.

The rule: OAuth 2.0 for delegated access, OIDC for authentication. "Sign in with Google" is OIDC.

🟡 Mid — A user's account is compromised. How do you log them out everywhere immediately with JWTs?

Directly, you can't — and saying so plainly is the correct start. JWT verification is local: the server checks a signature and consults nothing else, so a valid token is accepted until it expires. Telling the client to delete it helps only an honest client; the attacker who stole the token keeps using it, which is exactly the case that matters.

What actually works, in the order I'd deploy it:

1. Bump a per-user token version. Store token_version on the user and embed it as a claim. Validation compares the claim against the current value; incrementing it invalidates every token for that user at once. This requires a lookup, but a tiny, highly cacheable one — and it's the cleanest mechanism for "log out everywhere", password change, and account compromise.

2. Revoke the refresh token family. The attacker can no longer obtain new access tokens, so their access dies at the current token's expiry.

3. Deny-list the specific JTIs if you need to kill in-flight access tokens instantly. Entries only need to live until each token's natural expiry, so the list stays small.

4. Break-glass: rotate the signing key — invalidates every token for every user. Correct for a suspected key compromise, wrong for a single account.

The design lesson: short access-token lifetimes (5–15 min) are what make this tractable — they bound worst-case exposure without a per-request lookup. And note the honest conclusion: if the requirement is genuinely instant revocation on every request, you need a lookup, which means you've chosen server-side state. Sessions may simply be the better design for that system.

I'd also add refresh token rotation with reuse detection going forward: each refresh invalidates the previous token, so replaying an old one signals theft and revokes the whole family automatically — turning a silent compromise into a detected one.

🟡 Mid — Walk through the OAuth authorization code flow with PKCE. Why is PKCE needed? 
1. Client generates a random code_verifier, computes
   code_challenge = SHA256(verifier), and redirects the user to the
   authorization server with client_id, redirect_uri, scope, state,
   code_challenge.

2. User authenticates AT the authorization server and approves the
   scope. The client never sees the credentials.

3. Authorization server redirects back with ?code=XYZ&state=...
   The client verifies `state` matches what it sent (CSRF protection).

4. Client exchanges the code on the BACK CHANNEL (server-to-server),
   sending code + code_verifier. The server checks
   SHA256(code_verifier) == the code_challenge it stored.

5. Server returns access_token (+ refresh_token, + id_token for OIDC).

6. Client calls the API with  Authorization: Bearer <access_token>.

Why PKCE is needed: the authorization code travels through the browser as a URL redirect, where it can leak — a malicious app registered for the same custom URI scheme on mobile, browser history, a referrer header, or a logging proxy. Without PKCE, whoever obtains that code can exchange it for a token.

PKCE binds the code to the client instance that began the flow. The attacker has the code but not the code_verifier (which never left the client), so the exchange fails. The challenge is sent first and the verifier only at redemption, so intercepting the initial request doesn't help either.

Two points that show current knowledge: PKCE originated for mobile and native apps because they cannot keep a client secret — anyone can decompile the binary — but OAuth 2.1 requires PKCE for all clients, including confidential server-side ones, since code interception is a risk regardless. And the implicit flow is removed in OAuth 2.1: it returned the access token directly in the URL fragment, exposing it to history and referrers with no client authentication. Proposing implicit for a SPA is a dated answer; Authorization Code + PKCE is correct for every client type.

🔴 Senior — What JWT implementation mistakes have caused real vulnerabilities?

Four that have produced CVEs in widely-used libraries:

1. alg: none. The JWT header declares its own algorithm, and some libraries honoured "alg":"none" by skipping verification entirely. An attacker edits the payload, drops the signature, and it validates. The underlying bug is architectural: trusting attacker-controlled input to decide how to verify that input.

2. Algorithm confusion (RS256 → HS256). Subtler and more instructive. Your server verifies RS256 using a public key. An attacker changes the header to HS256 and signs a forged token using that public key as the HMAC secret. A library that reads alg from the token to select the routine will run HMAC-SHA256 with the public key — exactly what the attacker did — and accept it. The public key is public, so this needs no secret at all.

Both are fixed the same way: pin the algorithm at the verifier, algorithms: ['RS256']. The verifier decides; the token never does.

3. Missing audience and issuer validation. A signature check proves a token is genuine, not that it was meant for you. Without an aud check, a valid token minted for a different service is accepted — the confused deputy problem, and the reason OIDC mandates audience validation.

4. Treating kid as trusted input. The key-ID header has been used for path traversal (kid: "../../dev/null", yielding an empty key the attacker can HMAC with) and SQL injection where implementations looked keys up by concatenation. Treat kid as an opaque index into a known JWKS, never as a path or query fragment.

And the pervasive misunderstanding: the JWT payload is base64url, not encrypted. Anyone with the token reads every claim. The signature provides integrity, never confidentiality — so no PII, internal identifiers, or secrets belong in a JWT.

The meta-lesson I'd state: every one of these comes from the same root — a self-describing credential that tells the verifier how to check it. The defence is to make the verifier's expectations explicit and fixed: pinned algorithm, expected issuer, expected audience, enforced expiry, and a small allowed clock skew.

🔴 Senior — Design authentication for a platform with a web app, mobile apps, third-party API access, and 30 internal services.

Four distinct client types with genuinely different constraints, so I'd use one identity provider and different flows per client — not one uniform mechanism.

Central identity provider issuing OIDC tokens, publishing a JWKS endpoint, and owning credentials, MFA and session lifecycle.

ClientMechanismReasoning
Web app (first-party)Authorization Code + PKCE, then a server-side session in an HttpOnly/Secure/SameSite cookieInstant revocation, live claims, tiny cookie, no token in JS. There's no distributed-verification requirement for your own web app, so a JWT would add complexity for nothing.

The internal design is where this is won or lost. The tempting approach — the gateway forwards X-User-Id: 123 and services trust it — means any internal caller can impersonate any user. One SSRF, one compromised pod, or one missing network policy becomes total account takeover, because perimeter-only security assumes an internal network that can be trusted.

Instead: the gateway validates the external token once (signature, iss, aud, exp), then mints a signed internal token carrying the verified user claims, scoped to the specific downstream service and living only a few minutes. Each service validates it — cheap, local, no IdP dependency. Layer mTLS so services also prove which service is calling; that's service identity, complementary to user identity, not a substitute.

Operational details: cache JWKS by kid with a TTL and refresh on unknown kid (rate-limited), keeping the last good keys if a fetch fails, so the IdP isn't a hot-path dependency. Support key rotation with an overlap window — publish the new key before signing with it, and retire the old one only after every outstanding token has expired. And cache authorization inputs (roles, ACLs), never the decision, so a revoked permission takes effect immediately.

Revocation strategy across all of this: a per-user token version claim gives "log out everywhere" with one write; refresh-token families are revocable per device (letting a user sign out one lost phone); third-party consent is revocable per integration. Access tokens stay at 5–15 minutes so the worst-case exposure window is bounded without a per-request lookup.

The trade I'd state explicitly: the internal token adds a signing step at the gateway and key management to operate. That's worth it because the alternative — trusted headers — has a catastrophic and very common failure mode. Security at the boundary between services should not assume the network is safe.

🏋️ Graded Exercises

Exercise 1 (Easy): A JWT's payload contains {"user_id": 42, "ssn": "123-45-6789"}. What's wrong?
Solution

The SSN is effectively public. A JWT payload is base64url-encoded, not encrypted — anyone holding the token can decode and read every claim. Paste it into jwt.io and it's plain text.

The signature provides integrity (proof the claims weren't altered), never confidentiality. Since the token travels in headers, is often stored in browser storage, and frequently appears in logs, proxies and error reports, that SSN is now scattered across your infrastructure — and likely in violation of data-protection obligations.

Fix: keep claims minimal and non-sensitive — a user ID, roles, expiry, issuer, audience. Anything confidential is fetched server-side using the identity the token establishes. If you genuinely need encrypted claims there's JWE (JSON Web Encryption), but that's rare; the normal answer is simply not to put secrets in tokens.

Worth noting a second, smaller issue: even non-secret claims should be minimal, because the token is sent on every request. A bloated JWT with dozens of claims adds bandwidth to each call and can exceed header size limits.

Exercise 2 (Easy): Why is the OAuth implicit flow deprecated, and what replaces it?
Solution

The implicit flow returned the access token directly in the URL fragment of the redirect — it existed because early browsers lacked CORS, so SPAs couldn't make the back-channel token exchange.

Why it's unsafe:

• The token lands in the URL, so it enters browser history, can leak via Referer headers, and is captured by any logging proxy or analytics script reading the location.
• There's no client authentication step, so nothing binds the token to the app that requested it.
• No refresh tokens are issued, pushing implementations toward long-lived access tokens — precisely the wrong trade.

Replacement: Authorization Code + PKCE, which OAuth 2.1 mandates for all client types. The browser only ever receives a short-lived authorization code, which is useless without the code_verifier the client kept privately. CORS is now universally available, so SPAs can perform the token exchange directly and the original justification for implicit no longer exists.

Proposing implicit for a SPA in an interview is a clear signal of dated knowledge — the guidance changed several years ago.

Exercise 3 (Medium): Implement JWT validation correctly. List every check and explain what attack each prevents.
Solution 
import jwt   # PyJWT
from jwt import PyJWKClient

# Cache the JWKS client — do NOT fetch keys per request.
jwks = PyJWKClient("https://idp.example.com/.well-known/jwks.json",
                   cache_keys=True, lifespan=3600)

def validate(token: str) -> dict:
    # Resolve the signing key by `kid` from a KNOWN JWKS.
    # kid is used only as an opaque lookup key — never as a path
    # or SQL fragment.
    signing_key = jwks.get_signing_key_from_jwt(token).key

    return jwt.decode(
        token,
        signing_key,
        algorithms=["RS256"],              # 1. PINNED by the verifier
        issuer="https://idp.example.com",  # 2. expected issuer
        audience="my-service-api",         # 3. expected audience
        leeway=30,                         # 4. bounded clock skew
        options={
            "require": ["exp", "iat", "iss", "aud", "sub"],
            "verify_signature": True,
            "verify_exp": True,
            "verify_aud": True,
            "verify_iss": True,
        },
    )
CheckPrevents
Pinned algorithmsalg:none forgery and RS256→HS256 algorithm confusion. The verifier decides the algorithm; the attacker-controlled header never does.
Signature verificationPayload tampering — changing role to admin.
issTokens from a different (possibly attacker-run) issuer.
audConfused deputy: a valid token minted for another service being replayed against yours.
exp + small leewayIndefinite reuse of stolen tokens. Leeway must be small (≤60 s) or it materially extends the exposure window.
require claims presentTokens omitting exp or aud entirely, which some libraries would otherwise accept silently.
kid as opaque lookupPath traversal and injection through the key-ID header.
JWKS cachingNot an attack, but it keeps the IdP off your hot path; refresh on unknown kid, rate-limited so an attacker can't force unbounded fetches.

Application-level checks that must follow — these are not the library's job: verify the token version claim against the user's current value (for "log out everywhere"), consult a denylist if the path requires instant revocation, and re-evaluate authorization from current roles rather than trusting a cached decision.

Exercise 4 (Medium): Design token storage for a SPA. Compare localStorage against HttpOnly cookies for the XSS and CSRF threats.
Solution
localStorageHttpOnly cookie
XSSTotal loss. localStorage.getItem('token') is readable by any injected script, which can exfiltrate the token to an attacker's server. The credential outlives the page — usable later, elsewhere.Not readable by JS. XSS can still make requests from the page using the cookie, but cannot steal the token itself, so damage is confined to the compromised session.
CSRFNot vulnerable — not sent automatically; the app attaches it explicitly.Vulnerable in principle (browsers send cookies automatically), mitigated by SameSite=Lax/Strict plus CSRF tokens on state-changing requests.

The decisive asymmetry: XSS with localStorage yields a durable, exfiltratable credential the attacker uses at leisure from their own machine. XSS with an HttpOnly cookie yields only the ability to act within that page while it's open. Both are bad; one is much worse. And CSRF has robust, well-understood mitigations (SameSite, CSRF tokens) whereas token exfiltration has none.

Design I'd implement:

Refresh token → HttpOnly; Secure; SameSite=Strict cookie,
                Path=/auth/refresh   (scoped so it's sent ONLY to the
                token endpoint, never to your API surface)
Access token  → held in a JS variable, IN MEMORY ONLY.
                Lost on refresh → silently re-obtained on page load
                via the refresh cookie.

Why this is strong: the long-lived credential is unreadable by JS and only transmitted to one narrow path; the access token is short-lived and never persisted, so XSS gets at most a few minutes of in-page access and nothing durable. The cost is a refresh round trip on page load, and slightly more code — a good trade.

The essential caveat: none of this fixes XSS, it only limits the blast radius. A strict Content-Security-Policy, output encoding, and dependency auditing are the actual defence. Storage choice is damage control, not prevention — worth saying plainly, because it's the part candidates often miss.

Exercise 5 (Hard): Your API gateway validates JWTs and forwards X-User-Id to 30 internal services. A pentest finds an SSRF in one service. Assess the impact and redesign.
Solution

Impact: total authentication bypass across the platform. The SSRF lets an attacker make arbitrary HTTP requests from inside the trusted network. Since internal services accept X-User-Id on faith, the attacker simply sets it:

SSRF payload:
   POST http://payments-svc.internal/transfers
   X-User-Id: 1                       ← any user they choose
   {"to": "attacker", "amount": 999999}

The payments service has no way to distinguish this from a legitimate
gateway-forwarded request. The header is just a string.

Reachable: every one of the 30 services, as ANY user, including
admin accounts. The gateway — the only component that ever verified
anything — has been bypassed entirely.

The root cause is perimeter-only security: authentication happens once at the edge, and everything inside assumes the network is trustworthy. Any SSRF, compromised pod, misconfigured network policy, or malicious insider collapses the whole model. It's also completely silent — the requests look legitimate in every log.

Redesign — gateway-minted internal tokens:

Gateway:
  1. validates the external token (signature, iss, aud, exp)
  2. mints an INTERNAL JWT:
       { sub: 42, roles: [...], aud: "payments-svc",
         iss: "gateway", exp: now + 120s, jti: ... }
     signed with a gateway key whose public half services know
  3. forwards it as Authorization: Bearer <internal token>

Each service:
  - verifies signature, issuer=gateway, aud=ITS OWN NAME, exp
  - rejects anything else

Now the SSRF is largely neutralised: the attacker can still reach internal endpoints, but cannot forge a signed token. The audience scoping adds a second property — a token minted for search-svc can't be replayed against payments-svc, so one leaked token doesn't unlock the platform. The ~2-minute expiry bounds replay.

Layer additional defences, since no single control should be load-bearing:

• mTLS between services — proves which service is calling, complementing user identity. An SSRF from a service without a client certificate for that path is rejected at the transport layer.
• Network policy — default-deny egress, so a compromised service can only reach the specific dependencies it legitimately needs. The payments service probably has no business receiving calls from the service with the SSRF at all.
• Re-authorise at the service. The gateway proves identity; the service should still check "may this user perform this action on this resource?" against current state — defence in depth, and it catches privilege escalation the gateway couldn't know about.
• And fix the SSRF: allowlist outbound destinations, block link-local and internal ranges, disable redirect following. Architecture limits the blast radius; the vulnerability itself still needs patching.

Migration path, since 30 services can't switch at once: have the gateway send both the signed token and the legacy header; update services incrementally to require the token; log any request still relying on the header to track progress; then remove header trust once usage is provably zero — the same expand/contract discipline as an API migration.

Exercise 6 (Hard): Design authentication for a healthcare system: clinicians, patients, third-party apps, emergency "break-glass" access, and a full audit trail.
Solution

Regulatory context (HIPAA-style) makes auditability and least privilege primary design drivers rather than afterthoughts, and it changes several defaults.

ActorMechanismReasoning
CliniciansOIDC + mandatory MFA; server-side sessions with short idle timeout (10–15 min); smart-card/SSO where availableSessions, not JWTs — instant revocation matters when someone is terminated or a role changes. Shared workstations make idle timeout essential.
PatientsOIDC + optional MFA; sessions; strict scoping to their own record (and dependants where legally established)Different risk profile and a lower-friction bar, but the authorization model must handle proxy access (a parent viewing a child's record) explicitly rather than by ad-hoc exception.
Third-party appsOAuth 2.0 + PKCE, fine-grained scopes, per-integration consent that the patient can revokeThe genuine JWT/distributed-verification case. Scopes must be granular (read:labs, not read:everything), and consent revocable independently per app.
Internal servicesGateway-minted short-lived tokens, audience-scoped, over mTLSNever trusted headers — the failure mode is a mass PHI breach.

Break-glass emergency access is the interesting requirement, because it is a deliberate controlled bypass of normal authorization:

A clinician needs immediate access to a record they are not normally
authorised for (unconscious patient, another department's chart).
Blocking it can cost a life; leaving it open destroys least privilege.

Design:
  1. Access is GRANTED — never make a clinician wait for approval in
     an emergency. Deny-by-default would be actively dangerous here.
  2. It requires an EXPLICIT, deliberate action: a distinct
     "emergency access" button plus a typed justification. No
     accidental invocation.
  3. It is TIME-BOXED — e.g. 4 hours, scoped to that one patient,
     expiring automatically.
  4. It generates a HIGH-PRIORITY audit event, flagged for mandatory
     review by compliance, and (typically) notifies the patient.
  5. Every access under break-glass is separately logged.

The control is DETECTIVE, not preventive: you cannot safely prevent it,
so you make it impossible to use unnoticed. Retrospective review plus
certain visibility is the deterrent.

Audit trail — the compliance backbone:

Log EVERY access to PHI, not merely writes:
   who (user + role + on whose behalf), what (patient, record type,
   fields), when, from where (IP/device), why (normal duty vs
   break-glass + justification), and the authorization basis
   (treatment relationship, consent, emergency).

Properties required:
   - APPEND-ONLY and tamper-evident (hash chain, or a WORM store),
     because an attacker who can edit the audit log defeats the
     entire control
   - retained per regulation (often 6+ years)
   - separate from application storage, with a distinct access path
   - queryable: "who viewed this patient's record?" is a question
     patients have a legal right to ask

Authorization model: RBAC alone is insufficient — "is a doctor" doesn't imply "may view this patient". Use ABAC/relationship-based rules: a treatment relationship, an active care-team membership, an explicit consent grant, or a break-glass authorisation. Evaluate this per request against current data and — per the caching lesson — cache the inputs, never the decision, since a revoked care-team membership must take effect immediately.

Two design points I'd emphasise: (1) prefer sessions over JWTs for clinicians and patients despite the "JWTs are modern" instinct — in a regulated environment, instant revocation and live claims outweigh stateless verification, and the scale doesn't demand it; (2) the hardest requirement isn't authentication at all, it's authorization granularity plus provable auditability. Interviews focused on login mechanics miss that the real work is modelling who may see what, and proving afterwards who did.

🎯 Key Takeaways

  • AuthN is who you are; AuthZ is what you may do. OAuth 2.0 is an authorization framework — using it alone to prove identity is the bug OIDC fixes.
  • Sessions vs JWTs is a state-placement decision. Sessions give instant revocation and live claims; JWTs give distributed verification. Choose JWTs for that, not for performance.
  • JWTs cannot be revoked directly — verification is local. Bound the window with short access tokens plus revocable, rotating refresh tokens.
  • Refresh token rotation with reuse detection turns a stolen refresh token from indefinite access into a detected, family-wide revocation.
  • Authorization Code + PKCE for every client type. Implicit and password flows are removed in OAuth 2.1.
  • Always validate signature, issuer, audience and expiry — a valid signature proves authenticity, not that the token was meant for you.
  • Pin the algorithm at the verifier. alg:none and RS256→HS256 confusion both come from trusting the token to describe how it should be checked.
  • A JWT payload is base64, not encrypted. Never put PII or secrets in it.
  • HttpOnly cookies over localStorage: XSS with localStorage yields a durable, exfiltratable credential; with HttpOnly it's limited to in-page actions.
  • Never trust plain internal headers like X-User-Id — one SSRF becomes platform-wide impersonation. Mint signed, audience-scoped internal tokens.
  • Cache JWKS by kid, and cache authorization inputs — never the decision.
  • Some access can't be prevented, only audited. Break-glass access should be granted, time-boxed, justified, and impossible to use unnoticed.
