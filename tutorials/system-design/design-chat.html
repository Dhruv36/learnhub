Design Real-Time Chat Case Study

What you'll master: designing WhatsApp/Slack-scale messaging — why persist-then-deliver is non-negotiable, how to get ordering without a global sequencer, the storage schema that makes "load recent messages" a single partition read, multi-device sync (the part most answers ignore), when fan-out-on-write collapses, and what end-to-end encryption actually costs you architecturally.

Prerequisites: Realtime Apps (connection scaling, backplane), Pub/Sub (delivery guarantees, idempotency), CAP (causal ordering). Pairs with Notification System.

🎯 What this problem is really testing. Two things beyond the obvious WebSocket plumbing: whether you make the durable log the source of truth rather than the socket, and whether you notice that "messages must arrive in order" is a per-conversation requirement, not a global one — because global ordering would need a single sequencer and cap the whole system's throughput. The candidates who struggle here are the ones who design the delivery path first and bolt storage on afterwards.

2. Estimation

Assume 50M DAU, 40 messages sent per user per day.

MESSAGES
   50M × 40 = 2B messages/day
   2 × 10⁹ / 10⁵ s = 20,000 messages/s   (peak ×3 ≈ 60,000/s)
   → CONSEQUENCE: 60K writes/s far exceeds one primary (~5K/s).
     This REQUIRES sharding — unlike TinyURL, where writes were trivial.

STORAGE
   message ≈ 100 B text + 100 B metadata (ids, timestamps, status) = 200 B
   2B/day × 200 B = 400 GB/day  →  ~146 TB/year
   → CONSEQUENCE: history retention dominates everything. Tiering old
     messages to cheap storage is not optional at this scale.

CONNECTIONS
   assume 10% of DAU concurrently online = 5M connections
   at ~20 KB per connection = 100 GB RAM
   → ~20-50 connection nodes. Memory is fine; the constraint is
     reconnect storms (see the realtime lesson).

FAN-OUT
   most messages are 1:1 → 1 delivery each
   group messages (say 20% of traffic, avg 50 members):
      0.2 × 20,000 × 50 = 200,000 deliveries/s
   → CONSEQUENCE: fan-out multiplies delivery volume 10x over send
     volume. The delivery path, not the send path, is the bottleneck.

4. The Core Design Decision: Persist Before Deliver

❌ Deliver, then persist 
1. push over the socket
2. write to the database

Crash between 1 and 2:
the recipient saw the message,
but it is absent from history.
On their next sync it VANISHES.

Worse, it's unreproducible —
it only happens on crashes, so
it passes every test and shows
up as "messages sometimes
disappear" tickets.
✅ Persist, then deliver 
1. assign seq, write durably
2. ACK the sender ("sent")
3. publish for live delivery
4. offline? → push notification

A crash after step 1 loses
nothing: the recipient's next
catch-up query returns it.

The socket becomes a LATENCY
OPTIMISATION. Correctness lives
in the log.

This single decision determines whether the system is correct. A WebSocket guarantees ordered delivery while connected and nothing across a disconnect — so anything sent during a drop is simply gone. Durability has to come from the store, with the socket as a fast path over it. Get this backwards and you have a system that works in demos and loses messages in production.

5. Deep Dive: Ordering Without a Global Sequencer

"Messages must arrive in order" needs unpacking, because the naive reading is expensive:

GLOBAL ordering (every message in the system totally ordered)
   → requires ONE sequencer → a throughput ceiling and a SPOF
   → and nobody needs it: messages in different conversations are
     causally unrelated.

PER-CONVERSATION ordering  ← what the product actually requires
   → a monotonic counter per conversation
   → conversations are independent, so this shards perfectly

Timestamps are the wrong mechanism and this is a common error: server clocks skew, two messages can share a millisecond, and a client clock is entirely untrustworthy. Use a per-conversation sequence number, assigned server-side at persist time:

seq = atomic_increment(conversation:{id}:seq)     -- Redis INCR, or
                                                  -- a DB sequence per
                                                  -- conversation partition

Client tracks the highest seq it has seen per conversation:
   - detects GAPS (received 5, 7 → 6 is missing → request it)
   - reorders arrivals that came out of order
   - resumes after reconnect:  GET /messages?after=<last_seq>

The remaining subtlety: two users sending simultaneously in the same conversation get sequence numbers in whatever order the server processes them, which may not match "real" wall-clock order. That's unavoidable without coordination between the senders, and it's fine — both users see a consistent order, and disagreement about which of two simultaneous messages came first is invisible in practice. Consistency of order matters; matching physical time does not.

6. Deep Dive: The Storage Schema

The schema decision follows from the dominant query: "load the most recent N messages in this conversation, then page backwards." That's a time-ordered scan within a single partition — a wide-column store's ideal access pattern.

CREATE TABLE messages (
    conversation_id  uuid,
    bucket           int,        -- see below
    seq              bigint,
    message_id       uuid,
    sender_id        uuid,
    body             text,
    created_at       timestamp,
    PRIMARY KEY ((conversation_id, bucket), seq)
) WITH CLUSTERING ORDER BY (seq DESC);

PARTITION KEY  (conversation_id, bucket) → all of a conversation's
   recent messages live together on one node
CLUSTERING KEY seq DESC → "most recent N" is a single sequential read
   from the start of the partition. No sorting, no scatter-gather.
DecisionReasoning
Partition by conversationMatches the query exactly — one partition read serves a chat window. Also spreads load naturally, since conversations are numerous and independent.
Bucket in the partition keyEssential. Without it, a busy group's partition grows without bound — wide partitions cause slow reads, compaction problems and eventually node instability. Bucket by month (or by fixed message count) so each partition stays bounded.
Clustering by seq DESCNewest first is how chat is read. Descending order means no reversal at query time.
Cassandra-style storeWrite-optimised (60K writes/s), linear scalability, and the access pattern needs no joins. A relational DB would need sharding anyway and offers nothing here.

The wide-partition trap is worth emphasising because it's the schema mistake that reliably appears in production rather than in review: a group chat active for three years accumulates millions of rows in one partition, and that partition becomes a hotspot that no amount of cluster scaling fixes. The bucket component is what bounds it.

7. Deep Dive: Group Fan-Out and Multi-Device

Fan-out on writeFan-out on read
MechanismCopy the message into each recipient's inbox at send timeStore once per conversation; recipients query it
Write costO(group size)O(1)
Read costO(1) — inbox is prebuiltO(conversations) — merge across conversations
Breaks whenVery large groups — a 100,000-member broadcast means 100,000 writes for one messageRarely, for chat — a user's conversation list is small

For chat, fan-out on read is usually right — the opposite of the social-feed answer, and worth saying explicitly. A user has tens of conversations, not thousands of followees, so merging is cheap; and storing one copy per message rather than N copies saves enormously at 2B messages/day. Use fan-out on write only for the delivery notification (a small pointer per recipient), not for the message body.

Hybrid, which is what production systems do:
   message body      → stored ONCE per conversation  (fan-out on read)
   delivery signal   → published per online recipient (fan-out on write)
   offline recipients→ push notification, no inbox copy

A 100,000-member broadcast channel then costs one write plus
publishing to however many members are currently online — and for
those, sample or batch rather than pushing every message.

Multi-device is the part most answers omit, and it changes the model: "delivered" is no longer a single boolean, because a user has a phone, a laptop and a tablet.

Model per-DEVICE cursors, not per-user:
   device_state(user_id, device_id, conversation_id, last_seq_synced)

- Each device syncs independently from its own cursor.
- A message is "delivered" when ANY device acks; "read" when the user
  reads it on ANY device — then that read state must propagate to the
  OTHER devices so the unread badge clears everywhere.
- A new device performs an initial sync (bounded — recent history,
  paged backwards on demand).

The read-state propagation is the fiddly part: it's a second class of
message flowing back through the same delivery machinery, and
forgetting it produces the "I read it on my phone but my laptop still
shows unread" bug.

8. Deep Dive: End-to-End Encryption's Real Cost

E2E encryption is frequently proposed casually. It's the right choice for a privacy-focused product, but you should be able to state what it removes:

CapabilityEffect under E2E
Server-side searchGone. The server holds ciphertext. Search must be client-side over locally-stored messages.
Server-side spam/abuse detectionGone for content. You're limited to metadata signals (rate, graph shape, reports).
Multi-deviceMuch harder — each device needs its own key pair, and messages must be encrypted separately per device, or you need a key-sharing scheme.
New-device historyNot available from the server. Either the history doesn't transfer, or you build encrypted backups keyed by something the user controls (which becomes a recovery problem).
Link previews, media transcodingMust move to the client, changing bandwidth and battery characteristics.
Group membership changesRequires re-keying so a departing member cannot read future messages.

The honest summary: E2E moves work and state to the client and makes the server a dumb relay. That's the correct trade for WhatsApp or Signal, and the wrong one for Slack, where organisations need search, compliance retention and eDiscovery. "Which product is this?" is the question that decides it — and framing it that way is stronger than asserting either position.

Interview Questions

🟢 Beginner — Why must you persist a message before delivering it?

Because a WebSocket provides no durability. If you push over the socket first and crash before writing to the database, the message is gone from history — the recipient may have seen it on screen, but their next sync won't return it, and the sender believes it was delivered.

That bug is especially nasty because it's unreproducible: it only occurs on a crash in a millisecond window, so it passes every test and arrives as "messages sometimes disappear" support tickets that nobody can trace.

The correct order:

1. Validate, assign a per-conversation sequence number, WRITE durably
2. ACK the sender — the message is now "sent" and cannot be lost
3. Publish for live delivery (best effort)
4. If the recipient is offline, send a push notification

This makes the durable log the source of truth and the socket a latency optimisation. If live delivery fails for any reason — disconnect, node crash, backplane hiccup — the recipient's catch-up query on reconnect fills the gap, because the message was committed before anyone was told it existed.

The general principle applies well beyond chat: never acknowledge something you haven't made durable, and never let an ephemeral transport be the only copy of data you promised to keep.

🟢 Beginner — How do you guarantee message ordering?

With a monotonic sequence number per conversation, assigned server-side when the message is persisted.

Not timestamps — this is the common wrong answer. Server clocks skew across machines, two messages can land in the same millisecond, and client-supplied timestamps are entirely untrustworthy (a user with a wrong clock, or a malicious client, could place messages anywhere in history).

seq = INCR conversation:{id}:seq        -- atomic, per conversation

The client tracks the highest seq seen per conversation, which gives it:
  - gap detection      (saw 5 then 7 → request 6)
  - reordering         (buffer 7 until 6 arrives)
  - resumption         (GET /messages?after=<last_seq> on reconnect)

Why per-conversation and not global: global ordering would require a single sequencer for the entire system — a throughput ceiling and a single point of failure — to provide a guarantee nobody needs. Messages in different conversations are causally unrelated; nobody can observe their relative order. Per-conversation counters shard perfectly because conversations are independent.

The residual subtlety: two people sending simultaneously in one conversation get sequence numbers in whatever order the server happens to process them, which may not match true wall-clock order. That's unavoidable without coordinating the senders, and it's fine — everyone sees the same order, which is what matters. Consistency of ordering is the requirement; matching physical time is not.

🟡 Mid — Design the message storage schema and justify the partition key.

Start from the dominant query: "load the most recent 50 messages in this conversation, then page backwards." That's a time-ordered scan within one conversation — which points directly at a wide-column store partitioned by conversation.

CREATE TABLE messages (
    conversation_id  uuid,
    bucket           int,            -- e.g. months since epoch
    seq              bigint,
    message_id       uuid,           -- client-generated, for idempotency
    sender_id        uuid,
    body             text,
    created_at       timestamp,
    PRIMARY KEY ((conversation_id, bucket), seq)
) WITH CLUSTERING ORDER BY (seq DESC);

Partition key (conversation_id, bucket): conversation_id co-locates a conversation's messages so a chat window is served by a single partition read — no scatter-gather, no cross-node coordination. It also distributes load well, since conversations are numerous and independent.

The bucket component is the part people miss, and it's essential. Without it, a group chat active for three years accumulates millions of rows in one partition. Wide partitions cause slow reads, expensive compaction, memory pressure during repair, and eventually node instability — and no amount of cluster scaling fixes it, because the partition stays whole. Bucketing by month (or by fixed message count) bounds partition size permanently.

Clustering by seq DESC means "most recent N" is a sequential read from the start of the partition, with no sorting at query time.

Why Cassandra-style rather than relational: 60,000 writes/s needs sharding regardless, and a relational database would give us joins and transactions we don't use here. An LSM-based store handles the write volume natively and scales linearly.

Reading across buckets: the client usually needs only the current bucket; paging further back queries the previous one. Storing a small per-conversation index of active buckets avoids probing empty ones.

🟡 Mid — A user has a phone and a laptop. How does sync work?

The core change is that cursors are per-device, not per-user — a single "last read" pointer per user cannot represent two devices at different positions.

device_state(user_id, device_id, conversation_id, last_seq_synced)

Each device syncs independently:
   GET /conversations/{id}/messages?after={its own last_seq_synced}

Delivery and read state need redefining:

• Delivered = at least one device acknowledged. The sender doesn't care which.
• Read = the user read it on any device — and crucially, that state must propagate to their other devices so the unread badge clears everywhere. Forgetting this produces the classic "I read it on my phone but my laptop still shows unread" bug.

Read-state propagation is a second class of message flowing through the same delivery machinery: when device A marks messages up to seq 42 as read, that fact is published to the user's other devices exactly like a chat message.

New device onboarding: an initial sync must be bounded — fetch recent history (say the last 30 days or N messages per conversation) plus the conversation list, then page backwards on demand. Downloading years of history on first launch is slow, expensive, and happens at the worst moment.

Two operational details: devices go stale (a phone replaced a year ago) so expire device records after a period of inactivity to bound the state; and each device needs its own push token, since "notify the user" means "notify their active devices", with suppression once one device acknowledges.

If the product is end-to-end encrypted, this gets substantially harder — each device needs its own key pair and messages must be encrypted per device, which is why E2E multi-device took years to ship in real products.

🔴 Senior — Design for a 100,000-member broadcast channel.

Fan-out on write collapses at this size, and the arithmetic shows why immediately:

One message → 100,000 inbox writes.
At even 10 messages/s in that channel: 1,000,000 writes/s
for a single channel. Infeasible, and it would starve every other
conversation on the cluster.

1. Store the message once (fan-out on read). The body is written a single time to the conversation's partition. Members read from that shared log when they open the channel. Write cost is O(1) regardless of membership — this alone resolves the storage problem.

2. Fan out only the delivery signal, and only to online members. Of 100,000 members perhaps 5,000 are connected. Publish a lightweight notification (channel ID + new seq) to those, not the message body. Offline members discover it on next open or via a batched push.

3. Batch and coalesce. In a busy channel, send one "N new messages, latest seq X" update every few hundred milliseconds rather than one per message. This cuts delivery volume by an order of magnitude and — importantly — improves the client experience, since a UI re-rendering on every message is unusable anyway.

4. Suppress per-message push notifications entirely. Nobody wants 500 pushes from one channel. Digest them, or default broadcast channels to muted with an opt-in for mentions only.

5. Handle read receipts by not computing them. "Read by 100,000 people" is meaningless to display and enormously expensive to track per member. Either disable receipts in large channels or show an approximate count — a HyperLogLog-style estimate rather than exact per-member state.

6. Bound the partition. A high-traffic channel fills its partition quickly, so bucket by time and message count, and consider dedicated capacity for the largest channels so they can't degrade neighbours.

The framing: a broadcast channel is a fundamentally different product from a group chat even though the UI looks similar — it's closer to a feed. The design should treat it as such rather than trying to make the group-chat path scale, and recognising that is what the question is checking. Note the mirror image in Instagram Feed, where fan-out-on-write is correct for normal users and collapses for celebrities — same trade, opposite default.

🔴 Senior — What does end-to-end encryption cost you architecturally?

E2E makes the server a dumb relay that cannot read the payload. That's the point, and it removes a substantial amount of functionality:

1. Server-side search is gone. The server holds ciphertext, so search must run client-side over locally stored messages. That means every device needs a full local copy and its own index — which constrains history size on mobile and makes "search all my messages from 2019" a local-storage problem.

2. Content-based abuse detection is gone. No spam filtering, no malware scanning, no automated moderation. You're limited to metadata: send rates, graph patterns, and user reports. This is the trade societies argue about, and it's worth naming as a real cost rather than glossing over.

3. Multi-device becomes genuinely hard. Each device needs its own key pair, so a message must be encrypted separately for every recipient device, or you need a key-sharing scheme (sender keys for groups). This is why E2E multi-device support took years to appear in real products.

4. History on a new device isn't available from the server. Either it doesn't transfer, or you build encrypted backups keyed by a user-held secret — which creates a recovery problem, since losing that key means losing everything, permanently.

5. Group membership changes require re-keying so a departing member can't read future messages.

6. Server-side features move to the client — link previews, media transcoding, translation — changing bandwidth and battery characteristics.

And what it does NOT hide: metadata. Who talks to whom, how often, message sizes and timing are all still visible to the server. For many threat models that metadata is more revealing than the content, so claiming E2E makes a system "private" without qualification is overstating it.

The decision framing: E2E is right for a privacy-focused consumer product (Signal, WhatsApp) and wrong for enterprise messaging (Slack, Teams), where organisations require search, compliance retention and eDiscovery as contractual obligations. "Which product is this?" is the question that settles it — and answering that way is stronger than advocating for either position in the abstract.

🏋️ Graded Exercises

Exercise 1 (Easy): 50M DAU sending 40 messages/day. Compute messages/s and annual storage, and say what each number forces.
Solution 
MESSAGES
   50M × 40 = 2,000,000,000 messages/day
   2 × 10⁹ / 10⁵ s = 20,000 messages/s average
   peak ×3          ≈ 60,000 messages/s

STORAGE
   ~200 B per message (100 B text + 100 B metadata)
   2B × 200 B = 400 GB/day
   × 365      ≈ 146 TB/year   (before replication ×3 ≈ 438 TB)

What 60,000 writes/s forces: sharding. A single primary handles ~5,000 writes/s, so this is 12× over — replication cannot help (it scales reads, not writes), so the data must be partitioned. conversation_id is the natural key because conversations are independent and it matches the read pattern.

What 146 TB/year forces: tiered storage. Keeping years of history on SSD is expensive and unnecessary — the overwhelming majority of reads target recent messages. Recent months on fast storage, older data compressed to object storage, retrieved on demand.

The contrast worth drawing: in TinyURL, writes were 33/s and the correct headline was "this is a caching problem". Here writes are 60,000/s and the headline is "this is a write-scaling and storage problem". Same estimation method, opposite conclusion — which is exactly why you estimate before designing rather than reaching for a familiar architecture.

Exercise 2 (Easy): Why not order messages by created_at timestamp?
Solution

Three independent reasons, any one of which is disqualifying:

1. Server clock skew. Messages are handled by different servers whose clocks differ by milliseconds even with NTP. Two messages sent seconds apart can receive timestamps in the wrong order if they land on differently-skewed machines.

2. Collisions. At 60,000 messages/s, many share a millisecond. Timestamps alone don't provide a total order, so you'd need a tiebreaker — and any deterministic tiebreaker is really just a sequence number with extra steps.

3. Client timestamps are untrustworthy. If the client supplies the time, a device with a wrong clock scrambles the conversation, and a malicious client can place a message anywhere in history — including before messages that already exist.

The fix — a per-conversation sequence number assigned server-side at persist time. It's monotonic by construction, has no ties, and gives the client three capabilities timestamps can't: gap detection ("I have 5 and 7, fetch 6"), deterministic reordering, and resumption after reconnect (?after=42).

Still store created_at — users need to see when a message was sent, and it's useful for analytics and retention. Just don't order by it. The display timestamp and the ordering key are different concerns, and conflating them is the actual mistake.

Exercise 3 (Medium): Design the reconnect sync protocol. A user was offline for two hours across 20 conversations.
Solution 
CLIENT STATE (persisted locally):
   { conversation_id → last_seq_synced }  for each conversation
   plus a global cursor for NEW conversations created while offline

RECONNECT SEQUENCE:
1. Establish the WebSocket, authenticate, resume the session if possible.

2. Send a batched sync request — NOT 20 separate calls:
      POST /sync
      { "cursors": { "conv_1": 340, "conv_2": 12, ... },
        "since": "2026-07-30T08:00:00Z" }   // for new conversations

3. Server responds with, per conversation:
      - up to N (say 50) messages after the cursor
      - has_more flag + a cursor for paging
      - the new high-water seq, so the client knows the true gap size
   Plus: conversations created while offline, and read-state updates
   from the user's OTHER devices.

4. Client applies updates, then resumes live delivery from the socket.

5. Deduplicate: a message may arrive BOTH in the sync response and live
   over the socket. Drop anything with seq <= last applied.

The critical design choices:

Bound the response. Never return "everything since the cursor" unbounded. A user offline for a month across 20 busy conversations could otherwise trigger a multi-megabyte payload at exactly the moment the connection is most fragile. Cap per conversation and let the client page.

Batch the request. Twenty separate HTTP calls on a mobile network means twenty round trips and twenty chances to fail. One request, one response.

Return the high-water mark even when truncating, so the client can display "142 new messages" accurately without having fetched them all.

Deduplicate explicitly. The overlap between catch-up and live delivery is guaranteed, not exceptional — the socket may deliver a message that the sync response also contained.

Include other devices' read state, or the user reconnects to stale unread badges they already cleared elsewhere.

Prioritise: sync active conversations first so the UI is usable immediately, and fetch the rest in the background — perceived latency matters more than total sync time.

Exercise 4 (Medium): A user sends a message, the network drops before the ack, and the client retries. Prevent duplicates.
Solution

The client cannot distinguish "the server never received it" from "the server received it and the ack was lost" — the classic at-least-once situation from pub/sub. It must retry (otherwise messages are silently lost), so the server must make retries safe.

CLIENT: generate a UUID per message, at composition time.
   Retries reuse the SAME id — this is the whole mechanism.

   { "client_message_id": "a3f2-...", "conversation_id": ...,
     "body": "hello" }

SERVER: dedupe atomically on insert.

   INSERT INTO messages (conversation_id, bucket, seq, message_id, ...)
   VALUES (...)
   IF NOT EXISTS;                  -- or a UNIQUE index on
                                   -- (conversation_id, client_message_id)

   - insert succeeds        → new message, assign seq, deliver
   - uniqueness violation   → already processed; return the ORIGINAL
                              seq and ack. Do NOT create a second row.

Why the ID must be client-generated: a server-generated ID is created after the request arrives, so a retry produces a different one and the duplicate is undetectable. Generating it at composition time means the identity of the message is fixed before it ever leaves the device.

Why the check must be atomic with the insert: a "SELECT then INSERT" has a race — two retries arriving concurrently both find nothing and both insert. The unique constraint does the mutual exclusion, exactly as with custom aliases in TinyURL.

Return the original sequence number on the duplicate path. The retry is the client asking "did this happen?", so answering with the original result lets it reconcile its local state rather than guessing.

Client-side benefits too: the client can render the message optimistically with its own ID and a "sending" state, then reconcile when the ack arrives — so the UI is instant and correct without waiting for the round trip.

Bound the dedupe window: keep client_message_id indexed for a period longer than any plausible retry (say 24 hours) rather than forever, so the index doesn't grow without limit.

Exercise 5 (Hard): Typing indicators generate more traffic than messages. Design them so they don't dominate the system.
Solution 
Naive: send an event on every keystroke.
   40 wpm ≈ 200 chars/min ≈ 3.3 events/s per typing user.
   With 500,000 users typing at any moment:
      1,650,000 events/s — nearly 30x the MESSAGE volume of 60,000/s,
   for data that is worthless within two seconds.

Design principles, in order of impact:

1. Never persist them. Typing state has no value after a few seconds, so it should never touch the message store. This alone removes the storage and write-amplification problem entirely.

2. Throttle at the client — the biggest win. Send "started typing" once, then at most one refresh every 3–5 seconds while typing continues, and a "stopped" event on send or after a pause.

3.3 events/s → ~0.25 events/s per typing user: a ~13x reduction,
achieved entirely on the client with no server changes.

3. Use TTL rather than explicit "stopped" events. Set the indicator with a 5-second expiry; if the user keeps typing, refreshes extend it. If their connection drops mid-typing, the indicator clears itself — no stuck "Alice is typing…" forever, which is the bug the explicit-stop design produces. This is the same self-healing pattern as presence in the realtime lesson.

4. Route through the backplane only, never through persistence: publish to typing:{conversation_id}; connection nodes deliver to their local sockets for members currently viewing that conversation.

5. Only deliver to members with the conversation open. Someone with the app backgrounded gains nothing from a typing indicator, so filter by view state — a large reduction in large groups.

6. Suppress in large groups. "17 people are typing" is noise. Cap at a few names, or disable above a member threshold.

7. Shed under load. Because typing indicators are pure ephemera, they should be the first thing dropped when the system is stressed — a separate, lower-priority path from message delivery, so protecting them never costs message throughput.

The general lesson: classify data by its value over time. Messages are durable facts; typing state is a hint that expires in seconds. Building both on the same delivery guarantees means paying message-grade costs for data that should be cheap and disposable.

Exercise 6 (Hard): Users report messages arriving out of order in one busy group. Sequence numbers are assigned correctly. Diagnose.
Solution

Correct sequence numbers mean the storage order is right, so the problem is in delivery or on the client. Candidates, in order:

1. The client renders on arrival rather than by sequence (most likely). Messages travel through the backplane, possibly via different nodes, with retries — so arrival order is not send order. If the UI appends whatever arrives, users see reordering. Fix: the client must buffer by sequence and render in order, holding out-of-order arrivals briefly and requesting any gap it detects. The sequence number exists precisely so the client can do this; assigning it and then ignoring it is the actual bug.

2. Parallel delivery paths. If publishes are spread across partitions or nodes without a consistent key, two messages from the same conversation can take different routes and race. Fix: key the backplane publish by conversation_id, so one conversation's messages traverse a single ordered partition — the standard ordering-via-partition-key technique from pub/sub.

3. Sequence assignment isn't atomic with the publish. If the server assigns seq, then does other work, then publishes, two concurrent messages can be published in the opposite order to their sequence numbers. Fix: publish immediately after assignment, and rely on client-side ordering regardless.

4. Retry reordering. A failed delivery retried after a backoff arrives after later messages. Unavoidable in an at-least-once system — which is another reason client-side ordering is mandatory rather than optional.

5. Multi-device or mixed paths. A message delivered live over the socket and another fetched via catch-up can interleave incorrectly if the client merges them naively by arrival.

Why only this group: high traffic widens every race window. Concurrent sends make near-simultaneous sequence assignment common, and higher volume means more retries. The bug likely exists everywhere and is only observable where volume makes it frequent — so fixing it should be global, not scoped to this group.

The architectural conclusion: ordering cannot be guaranteed by the delivery path in a distributed at-least-once system. The server's job is to assign a correct, meaningful order; the client's job is to render that order. Any design relying on messages arriving in order will eventually produce this bug.

🎯 Key Takeaways

  • Persist before delivering. The durable log is the source of truth; the socket is a latency optimisation.
  • Order per conversation, not globally — global ordering needs a single sequencer for a guarantee nobody can observe.
  • Sequence numbers, never timestamps — clocks skew, milliseconds collide, and client clocks are untrustworthy.
  • The client must render by sequence, because arrival order in an at-least-once system is never guaranteed.
  • Partition by (conversation_id, bucket) — the bucket is what stops long-lived groups growing unbounded partitions.
  • Chat is fan-out on READ for message bodies (unlike social feeds), with fan-out on write only for delivery signals.
  • Cursors are per-device, not per-user, and read state must propagate between a user's devices.
  • Bound every catch-up query — a long-absent user must not trigger an unbounded payload on a fragile connection.
  • Client-generated message IDs with an atomic uniqueness check make retries safe; server-generated IDs cannot.
  • Classify data by its value over time: typing indicators are never persisted, throttled at the client, TTL-based, and the first thing shed under load.
  • Broadcast channels are a different product from group chat — treat them as feeds, not conversations.
  • E2E encryption makes the server a dumb relay — no server-side search, no content moderation, much harder multi-device. Right for Signal, wrong for Slack.
