How to Scale a System Fundamentals

What you'll master: the eight-stage scaling ladder every system climbs, and — far more importantly — the specific number that forces each step. By the end you'll be able to look at a QPS figure and a data size and say which stage a system belongs at, what problem the next stage solves, and what new problem it introduces. This is the map for the rest of the track.

No prerequisites — this is the starting point. Every stage below links to the lesson that covers it in depth.

🎯 The single most important idea in this lesson: each stage is not an upgrade, it's a response to a specific bottleneck, and each one introduces new problems. Adding a cache creates invalidation and stampedes. Adding replicas creates lag. Sharding breaks joins and transactions. Scaling is not "make it bigger" — it's a sequence of deliberate trades. Candidates who recite the stages sound mid-level; candidates who name the forcing problem and the cost accepted sound senior.

Stage 0 → 1: One Box → Split the Tiers

Stage 0:  [Client] → [Web server + DB on one machine]
Stage 1:  [Client] → [Web server] → [DB server]

Forcing problem: the app and the database compete for the same CPU, RAM and disk. A slow query starves request handling; a traffic spike starves the database's buffer pool.

What it buys: the two tiers scale and fail independently, and you can size each for its actual workload (databases want RAM and fast disks; app servers want CPU).

The number that triggers it: honestly, mostly not a number — it's the first time a deploy or a heavy query causes a user-visible problem. A single modern box handles a surprising amount; don't leave stage 0 out of principle.

Stage 2: Horizontal Scaling + Load Balancer

[Client] → [Load Balancer] → [Web 1 .. Web N]  (stateless)  → [DB]

Forcing problem: one web server saturates — roughly 1,000–5,000 QPS for a typical app server, or a latency SLO that degrades past ~70% utilisation.

The prerequisite that matters: servers must be stateless. Session data moves to a shared store (Redis) so any server can serve any request. Without that, losing a server logs those users out, and you can't autoscale.

Horizontal vs vertical: a bigger machine is simpler and often the right first move — but it has a hard ceiling, costs superlinearly at the top end, and gives you no fault tolerance. One machine is one outage. Horizontal scaling buys redundancy as a side effect, which is usually worth more than the throughput.

Stage 3: Read Replicas

              ┌→ [Replica 1]  reads
[Primary] ────┼→ [Replica 2]  reads
  writes      └→ [Replica 3]  reads

Forcing problem: the database is the bottleneck and the workload is read-heavy — commonly 100:1 reads to writes for consumer products.

What it buys: read capacity scales with replica count, and replicas double as failover targets.

New problem introduced: replication lag. A user writes, then reads from a lagging replica and doesn't see their own change — the vanishing-comment bug. → Replication & Failover covers the fixes, and CAP Theorem covers why you must choose a consistency model per operation.

The limit: replicas do nothing for write throughput. Every write still goes through one primary. Confusing these two axes is the most common mistake in this whole topic.

Stage 4: Caching + CDN

[Client] → [CDN: static assets, cacheable responses]
         → [LB] → [Web] → [Redis: hot data] → [DB]

Forcing problem: replicas keep recomputing the same expensive queries, and read volume grows faster than you can add replicas.

What it buys — the biggest single win available: a memory read is ~1,000× faster than a disk-backed query, and the payoff is non-linear:

600,000 reads/s against a DB that handles 30,000 QPS:
   90% hit rate →  60,000 QPS to DB  ✗ still 2× over
   99% hit rate →   6,000 QPS to DB  ✓ comfortable
Going from 90% to 99% removes 90% of the REMAINING load.

New problems introduced: invalidation, stampedes when a hot key expires, and — the one people miss — the cache becomes load-bearing capacity. At a 99% hit rate your database is sized for 1% of traffic, so losing the cache is a 100× spike. → Caching Strategies.

Stage 5: Async Processing

[Web] → respond to user immediately
      → [Queue] → [Workers] → email / encoding / reports / analytics

Forcing problem: slow or unreliable work sits in the request path. Sending an email takes 800 ms and can fail — and it makes checkout both slower and less available.

What it buys: latency drops to the critical path only, and availability stops multiplying:

Synchronous chain of 4 services at 99.9% each → 0.999⁴ ≈ 99.6% (~35 h/yr down)
Move 2 off the critical path            → 0.999² ≈ 99.8% (~17 h/yr)
The queue also absorbs bursts: a 10× spike becomes a deeper queue,
not dropped requests.

New problems introduced: eventual consistency, duplicate delivery (at-least-once is what you get), and the dual-write problem. → Pub/Sub vs Message Queues.

Stage 6: Sharding

hash(user_id) → Shard 0 | Shard 1 | Shard 2 | Shard 3
Each shard is its own primary + replicas.

Forcing problem: write volume or dataset size exceeds a single primary — typically above ~5,000 writes/s, or a working set that no longer fits in one machine's RAM.

What it buys: write throughput and storage scale with shard count.

The costs you accept, and they're steep: cross-shard joins and transactions become hard or impossible; resharding is a major operation (→ Consistent Hashing makes it survivable); and a badly chosen shard key produces hot partitions that adding shards won't fix.

Shard key selection is the decision that matters. High cardinality, even distribution, and — critically — chosen so that your most common queries hit a single shard. A key that forces every query to scatter-gather across all shards has multiplied your work rather than divided it.

Stage 7: Multi-Region

Forcing problem: users on another continent see 150 ms+ of latency on every round trip; or you need to survive losing an entire region; or data-residency law requires it.

What it buys: local latency, regional fault tolerance, compliance.

Why it's last: it brings the hardest problems in the field — cross-region replication lag measured in seconds, conflict resolution if you accept writes in more than one region, and the full weight of the CAP trade-offs. → Multi-Region & DR.

The trick that makes it tractable: partition users by home region so each record is only ever written in one place. Then you get active-active globally with no write conflicts, because the write sets are disjoint.

Interview Questions

🟢 Beginner — Walk me through scaling a web app from one server to a million users.

I'd go stage by stage, naming what forces each step:

1. Split the tiers. App and database on one box compete for CPU and RAM. Separate them so each can be sized and scaled for its own workload.

2. Horizontal scaling behind a load balancer, once one app server saturates around 1,000–5,000 QPS. The prerequisite is making servers stateless — sessions move to Redis, so any server can serve any request and losing one doesn't log users out.

3. Read replicas, because consumer workloads are typically ~100:1 read-heavy. Reads spread across replicas, which also serve as failover targets. This introduces replication lag, so I'd need read-your-own-writes handling for anything a user just changed.

4. Caching and a CDN. Redis for hot data, CDN for static assets and cacheable responses. This is usually the largest single win — memory is ~1,000× faster than a disk-backed query.

5. Async processing for anything not needed in the response: emails, image processing, analytics. Cuts latency and stops those dependencies from affecting availability.

At one million users — roughly 2,000 QPS and maybe 100 GB — I'd stop here. That's comfortably handled by stages 2–5 with a single unsharded primary. I'd explicitly say I'm not sharding, because writes still fit one primary and sharding costs you joins and transactions permanently. Sharding and multi-region come later, when write volume or data size actually forces them.

🟢 Beginner — What's the difference between vertical and horizontal scaling?

Vertical means a bigger machine — more CPU, RAM, faster disks. Horizontal means more machines working together.

Vertical is simpler and often the right first move: no code changes, no distributed systems problems, no coordination. Its limits are that machines have a hard ceiling, cost grows superlinearly at the high end, and — most importantly — one machine gives no fault tolerance. It's a single point of failure and requires downtime to upgrade.

Horizontal scales further and buys redundancy, which is usually worth more than the throughput itself. The costs: servers must be stateless, you need a load balancer, and you've entered distributed-systems territory — partial failures, consistency questions, distributed debugging.

In practice you do both: vertical first because it's cheap and easy, horizontal once you need availability or hit the ceiling. And note they apply differently by tier — stateless app servers scale horizontally trivially, while databases scale vertically much further before you're forced into sharding, which is why "scale the database up, scale the app out" is such a common shape.

🟡 Mid — At what point do you shard, and what do you give up?

When to shard: when a single primary can no longer handle the write volume (roughly above 5,000 writes/s for a relational database) or when the dataset exceeds what one machine can store or keep in RAM. Those are the only two forcing conditions — everything else has cheaper answers.

What to try first, because sharding is close to irreversible: vertical scaling (modern machines go a long way), read replicas if reads are the problem, caching, archiving cold data, and moving large blobs to object storage. Many "we need to shard" situations are actually "we're storing 1 MB images in Postgres".

What you give up:

• Cross-shard joins — a query spanning shards means fetching from each and joining in application code, or denormalising so it doesn't have to.
• Cross-shard transactions — no ACID across shards. You're into sagas and compensating actions.
• Simple resharding — changing shard count moves data. Consistent hashing reduces it from "almost everything" to ~1/N, which is the difference between feasible and not.
• Uniform performance — a hot shard becomes your ceiling, and adding shards doesn't fix a single hot key.

The shard key is the decision that determines everything. It needs high cardinality, even distribution, and — the part people miss — it should be chosen so your most common queries hit a single shard. Sharding users by user_id works beautifully if queries are per-user, and terribly if your main query is "all orders in a date range", which would scatter-gather across every shard. Getting this wrong is expensive to correct, so it deserves more discussion time than the mechanics.

🟡 Mid — Your app is slow. Walk me through diagnosing where to scale.

I'd resist adding infrastructure until I know which resource is saturated — the common failure is scaling the wrong tier and concluding "scaling doesn't help".

1. Where is the time going? Distributed tracing or request-level timing to break latency into app time, database time, cache time, and external-call time. Look at p99, not the mean — averages hide the problem, and users experience the tail.

2. Is it load-dependent? If latency is flat regardless of traffic, it's an algorithmic or query problem (a missing index, an N+1) and no amount of hardware fixes it. If latency rises with load, something is saturating.

3. Which resource?

App servers at high CPU, DB fine     → scale out the app tier (stage 2)
DB CPU high, mostly SELECTs         → replicas + caching (stages 3–4)
DB CPU high, mostly writes          → sharding (stage 6); replicas won't help
Everything idle but latency high    → waiting: locks, external calls,
                                      connection pool exhaustion, or a
                                      slow dependency consuming threads
One endpoint slow, others fine      → application/query problem, not capacity

4. Check the cheap fixes first, because they're usually the real answer: a missing index can be a 1000× improvement; an N+1 query pattern turns one request into 50; a connection pool that's too small serialises everything regardless of how many servers you add.

5. Then scale the identified bottleneck — and re-measure, because bottlenecks move. Fixing the database frequently reveals that the app tier is now the constraint.

The overall discipline: measure, identify the saturated resource, fix that one thing, re-measure. Adding machines to a system bottlenecked on a lock, an index, or a pool size just costs money without changing anything.

🔴 Senior — What problems does adding machines NOT solve?

Several important ones, and recognising them prevents a lot of wasted effort:

1. Hot keys. One celebrity account taking 5% of all reads hashes to exactly one node. Adding nodes doesn't move it — the key still maps to one place. The fix is replicating the key: split it into key#0..9 and read a random copy, or put it in an in-process L1 cache. This is the most common "we scaled out and nothing improved" story.

2. Single-writer bottlenecks. Anything requiring global ordering — a strict sequence, a global counter, linearizable state — needs one serialisation point by definition. More machines add coordination, not throughput. The fix is to change the requirement: partition so ordering is only needed within a partition, or use commutative operations that don't need ordering at all.

3. Coordination overhead. Consensus gets slower with more participants — a 7-node Raft cluster has higher write latency than a 3-node one. Adding voters reduces performance while increasing durability. Keep quorums small and scale reads through non-voting replicas.

4. Cross-region latency. Light takes ~70 ms to cross the Atlantic and back, and no amount of hardware changes that. You can only move data or computation closer, or hide the latency behind async UX.

5. Tail latency under fan-out. A request touching 100 services hits someone's p99 nearly every time, so the composite p99 is far worse than any individual service's. More replicas of each service doesn't fix it — fewer dependencies, hedged requests, and graceful degradation do.

6. Data gravity and correctness. Getting the same answer from more places is a consistency problem, not a capacity one — that's CAP territory.

7. Team coordination — the original reason for microservices, and not a machine problem at all.

The unifying observation: horizontal scaling solves throughput problems for work that parallelises. Anything requiring a single point of agreement, anything bound by physics, and anything bound by a single hot element resists it — and needs the problem restructured rather than resourced.

🔴 Senior — A startup asks whether to build for 100M users from day one. Advise them.

No — and the reasoning matters more than the answer.

1. The architecture would be wrong anyway. Designing for 100M users requires knowing the access patterns, read/write ratio, and which entities are hot. A pre-launch startup knows none of these, so they'd be optimising against guesses. Shard keys chosen before you understand your query patterns are usually wrong, and a wrong shard key is one of the most expensive mistakes to correct.

2. The cost is paid in the currency they can least afford: speed. Sharding, eventual consistency, sagas and distributed tracing all make every feature slower to build. A startup's actual risk is building the wrong product, and this architecture directly worsens their iteration speed — the one thing that mitigates that risk.

3. The operational burden needs a team they don't have. Kafka, a service mesh, sharded databases and multi-region replication need people to run them. At 8 engineers, that's most of the team not building product.

4. A single well-tuned server goes remarkably far. A modern box handles thousands of QPS and a database with hundreds of gigabytes. Stack Overflow served enormous traffic on a famously small number of servers. Most companies never reach the scale that forces stage 6.

What I'd actually recommend:

• Build stages 1–2: separate tiers, stateless app servers behind a load balancer. Cheap, and it preserves the option to scale out.
• Keep the data model shardable even though you don't shard: avoid queries that inherently span all users, keep a natural partition key (tenant or user ID) on your main tables, and don't rely on cross-entity transactions you couldn't later split. This is the highest-leverage thing they can do — it's nearly free now and enormously expensive to retrofit.
• Instrument from day one. Metrics, structured logs, tracing. You cannot scale what you can't measure, and this is genuinely hard to add later.
• Modular monolith with clear internal boundaries, so extraction later is a refactor rather than a rewrite.

The framing I'd leave them with: scaling problems are good problems — they mean the product worked. Premature scaling is a bet that you'll succeed, paid for with the resources that determine whether you succeed. Design so you're not blocked from scaling, then scale when a real number forces it. The mature version of "build for scale" is "don't build in anything that prevents scaling later" — which is a much cheaper commitment.

🏋️ Graded Exercises

Exercise 1 (Easy): A system does 50,000 reads/s and 500 writes/s on 200 GB of data. Which stages does it need?
Solution 
Writes: 500/s   → far below a single primary's ~5,000/s ceiling
                 → NO SHARDING NEEDED
Data:   200 GB  → fits comfortably on one machine
                 → NO SHARDING NEEDED
Reads:  50,000/s → far beyond one DB, and the dominant problem (100:1 ratio)

Stages needed: 1–4. Separate tiers, load-balanced stateless app servers, read replicas, and — most importantly — caching. At a 95% hit rate the database sees only 2,500 reads/s, which a primary plus a couple of replicas handles easily.

The point of the exercise is recognising that a big-sounding number (50,000 QPS) is a caching problem, not a sharding one. Proposing shards here would give up joins and transactions to solve a problem that doesn't exist. Always separate the read axis from the write axis before choosing a stage.

Exercise 2 (Easy): Why must servers be stateless before you can scale horizontally?
Solution

Because a load balancer sends each request to whichever server is available. If a user's session lives in one server's memory, then:

• A request routed elsewhere doesn't find the session — the user appears logged out.
• Losing a server logs out every user on it.
• Autoscaling breaks — you can't remove a server without discarding its users' state.
• Deploys become disruptive for the same reason.

The workaround, sticky sessions (pinning users to a server), technically functions but reintroduces every problem: uneven load distribution, users still lost when a server dies, and no ability to scale in.

The fix: move state to a shared store — sessions in Redis, files in object storage, no local disk dependencies. Then any server can serve any request, servers become interchangeable, and scaling in or out is safe.

The broader principle: state is what makes scaling hard. Stateless tiers scale trivially, which is exactly why so much architectural effort goes into isolating state into the few components designed to handle it (databases, caches, object stores).

Exercise 3 (Medium): Your database is at 90% CPU. Reads are 80% of the load. List three options in order and justify the ordering.
Solution

1. Query optimisation and indexing (do this first — hours of work, potentially 10–1000×). Find the slow queries: a missing index turns a full table scan into a lookup; an N+1 pattern turns one request into fifty. This is free of architectural cost, has no ongoing operational burden, and frequently resolves the problem entirely. Skipping it means scaling to accommodate waste.

2. Caching (days of work, removes most read load). With 80% reads and typical access skew, a cache can absorb 90–99% of them. At a 95% hit rate the database's read load drops 20×. Cost: invalidation complexity, staleness, and — importantly — the cache becomes load-bearing, so it needs HA.

3. Read replicas (days, scales reads linearly). Spread reads across replicas. Cost: replication lag and the read-your-own-writes problem, plus infrastructure. I put this after caching because caching removes work entirely whereas replicas redistribute it — and replicas cost more per unit of relief.

Explicitly not sharding. Writes are only 20% of the load, so the write path isn't the bottleneck. Sharding would give up joins and transactions permanently to solve a read problem that caching and replicas address far more cheaply.

The ordering principle: cheapest and most reversible first, and remove work before redistributing it. Each step also buys time to see whether the next is still necessary.

Exercise 4 (Medium): Pick a shard key for a multi-tenant SaaS where 90% of queries are scoped to one tenant, but one tenant is 40% of all data.
Solution

The tension: tenant_id is the natural key because 90% of queries are tenant-scoped, so it keeps them single-shard. But one tenant holding 40% of the data creates a massively hot shard, and no number of additional shards fixes it — that tenant still hashes to one place.

The answer is a composite key with special handling for large tenants:

Small/medium tenants:  shard on hash(tenant_id)
                       → all their queries hit ONE shard. Ideal.

Large tenants:         shard on hash(tenant_id, sub_key)
                       where sub_key is user_id, region, or date bucket
                       → that tenant SPREADS across many shards.
                       Their queries scatter-gather, which is acceptable
                       because they're a small number of customers with
                       (usually) a commercial relationship that justifies
                       the extra engineering.

Maintain a routing/directory table: tenant_id → sharding strategy,
so the application knows which mode applies. This also lets you
PROMOTE a tenant from simple to composite sharding as they grow,
without changing anything for everyone else.

The alternative worth naming: dedicated shards for the largest tenants. Give the 40% tenant its own database entirely. This is common in real SaaS and has real advantages — noisy-neighbour isolation, per-tenant backup and restore, easier compliance, and the ability to offer it as a premium feature. The cost is operational heterogeneity: you now run two kinds of infrastructure.

What I'd avoid: sharding on something like user_id globally. It distributes data beautifully and destroys the 90% case, because every tenant-scoped query would scatter-gather across all shards. Even distribution is worthless if it breaks your dominant query pattern — that's the core lesson of shard key selection.

Exercise 5 (Hard): Design the scaling path for a live-streaming platform going from 10K to 10M concurrent viewers. Name what breaks at each stage.
Solution

Estimate first, since video changes everything:

10K viewers × 3 Mbps  =    30 Gbps
10M viewers × 3 Mbps  = 30,000 Gbps = 30 Tbps

A 10 Gbps NIC serves ~3,300 viewers. 10M viewers would need ~3,000
saturated NICs of pure egress. Bandwidth — not CPU, not the database —
is the entire problem.

10K viewers (30 Gbps): origin servers plus a CDN. Already CDN-dependent at this size, because 30 Gbps is beyond a small origin fleet. Chat and metadata are trivial at this scale.
What breaks next: origin egress, and transcoding cost as you add quality variants.

100K viewers (300 Gbps): multi-CDN, adaptive bitrate (transcode each stream to 4–5 renditions once, serve the appropriate one), and edge caching of HLS/DASH segments. Segments are immutable and identical for all viewers — the ideal cacheable object, so CDN hit rates approach 100%.
What breaks next: chat. 100K viewers in one chat room is a fan-out problem — one message multiplied by 100K deliveries.

1M viewers (3 Tbps): hierarchical distribution — origin → regional shields → edge — so the origin serves each segment a handful of times rather than once per edge. Chat moves to sharded pub/sub with rate limiting, and at this size you sample chat for display rather than delivering every message to everyone.
What breaks next: the thundering herd at segment boundaries, and origin egress during cache misses.

10M viewers (30 Tbps): multi-CDN with active traffic steering, possibly P2P assist for the long tail, and per-region origin shields. At this volume you negotiate bespoke CDN contracts or build edge PoPs — list-price egress would be tens of millions per month.

The failure modes specific to live streaming, which is what this exercise is really testing:

• Synchronised segment requests. Every viewer requests the same 2-second segment at nearly the same moment — a thundering herd every 2 seconds, by design. Mitigate with jittered client request timing and edge request coalescing.
• Cache misses are catastrophic here. A missed segment at the edge means an origin fetch multiplied by every edge — hence shield layers.
• Latency vs scale trade: low-latency streaming (LL-HLS, WebRTC) means smaller segments and less effective caching. Broadcast-style delay of 10–30 s caches far better. This is a product decision driven by infrastructure economics.
• Startup spikes: when a scheduled event begins, viewers arrive within seconds rather than gradually — so autoscaling can't react in time and you must pre-warm capacity.

The through-line: the database barely features in this design. Metadata is small and the viewer count is an approximate counter. The entire architecture is dictated by one number — egress bandwidth — which is exactly why estimating first matters: it tells you which problem you're actually solving.

Exercise 6 (Hard): A system was designed for 100× its current traffic. What are the concrete costs, and how would you argue for simplifying it?
Solution

Concrete costs of premature scaling:

1. Development velocity — the largest and least visible cost. Every feature crossing a service boundary needs versioned API changes, multi-repo deploys and coordination. Every write spanning shards needs a saga rather than a transaction. Work that would take a day takes a week, permanently.

2. Operational burden. Kafka, a service mesh, sharded databases and multi-region replication each need monitoring, upgrades, on-call expertise and incident runbooks. This is often a person or two of permanent capacity from a team that could be building product.

3. Debugging difficulty. A bug spanning eight services with eventual consistency is qualitatively harder than a stack trace. Mean time to resolution goes up, and every engineer pays that tax on every incident.

4. Infrastructure cost — usually the smallest item, which is worth pointing out because it's the one people cite. Twenty mostly-idle services still cost far less than the engineering time above.

5. Correctness risk. Eventual consistency and sagas introduce bug classes — duplicate processing, partial failures, ordering issues — that a single ACID database simply doesn't have. You've adopted a harder correctness model for load you don't serve.

How I'd argue for simplification — with evidence, not aesthetics:

Measure first. Actual QPS and data size against each component's capacity; how many services are deployed less than monthly (a sign they needn't be separate); how much time incidents consume; how long a typical cross-service feature takes versus a within-service one. Turn the argument into numbers before proposing anything.

Then propose targeted consolidation, not a rewrite:

- Services that ALWAYS deploy together → merge them (they're one
  service wearing two costumes)
- Sharded DB well under one primary's capacity → consolidate to one
  primary + replicas, recovering joins and transactions
- Queues where synchronous calls would do → simplify, if the work is
  fast and correctness-critical anyway
- Multi-region with no users in the second region → collapse to one,
  keeping cross-region BACKUP for DR

Sequence it by risk: start with the lowest-risk, highest-annoyance consolidation to build confidence and demonstrate value. Keep each step reversible.

The framing that wins the argument: avoid "this is over-engineered", which reads as criticism of colleagues and triggers defensiveness. Use "we're carrying complexity for load we don't have; here's what it costs us per feature, and here's what we'd get back". Complexity that was reasonable to add can be reasonable to remove once the uncertainty it hedged against has resolved.

The honest caveat: some of it may be load-bearing for reasons that aren't obvious — compliance boundaries, a genuine scaling need in one component, or an imminent contract. Ask before removing, and keep the pieces that earn their keep. The goal is complexity that's justified, not minimal complexity for its own sake.

🎯 Key Takeaways

  • Each stage is a response to a specific bottleneck, not an upgrade. Name the forcing problem and the new problem it creates.
  • State the scale before drawing anything. Jumping to the final architecture for a system doing 100 QPS is how strong candidates lose points.
  • Replication scales reads; sharding scales writes. Confusing the two axes is the most common mistake in this topic.
  • Stateless servers are the prerequisite for horizontal scaling — externalise sessions before adding machines.
  • Caching is the biggest single win and the payoff is non-linear: 90% → 99% removes 90% of the remaining database load.
  • At a high hit rate the cache is load-bearing capacity, not an optimisation — losing it is a 100× spike.
  • Async processing stops availability multiplying — moving two of four dependencies off the critical path halves your downtime.
  • Shard last and choose the key carefully: high cardinality, even distribution, and common queries hitting a single shard. Even distribution is worthless if it breaks your dominant query.
  • Some things don't scale with machines: hot keys, single-writer bottlenecks, coordination overhead, cross-region latency, tail latency under fan-out. These need the problem restructured, not resourced.
  • Measure before scaling. A missing index or an N+1 query is often a 1000× win that no amount of hardware would have delivered.
  • Don't build for 100× today's traffic — but don't build in anything that prevents scaling later. Keeping the data model shardable is nearly free now and expensive to retrofit.
