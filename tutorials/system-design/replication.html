Replication & Failover Fundamentals

What you'll master: why replication and sharding solve different problems (and why candidates conflate them), the real cost of synchronous vs asynchronous replication expressed as a durability budget, how replication lag produces user-visible bugs, the four steps of failover and how each one fails, why split brain is the hardest correctness problem in the lesson, and how fencing tokens fix it when heartbeats can't.

Prerequisites: CAP Theorem, Consistent Hashing. Leads into Distributed Consensus, Heartbeat & Gossip and Multi-Region & DR.

1. Two Problems, Two Solutions (Don't Confuse Them)

A single database instance has two independent limitations, and mixing them up is the most common muddle in this topic:

ReplicationSharding (partitioning)
SolvesAvailability + read throughputWrite throughput + dataset size
MechanismSame data on N nodesDifferent data on N nodes
Does NOT solveWrite throughput — every write still goes through one leaderAvailability — losing a shard loses that slice of data
CostN× storage; consistency lagCross-shard queries and transactions get hard

They are orthogonal and production systems use both: shard for write capacity, then replicate each shard for availability. A 12-node cluster is typically 4 shards × 3 replicas.

Common interview error:
  "We have 50,000 writes/s, so I'll add read replicas."
   → Read replicas do NOTHING for write load. Every write still
     funnels through the single leader. You need SHARDING.

  "We need high availability, so I'll shard the data."
   → Sharding without replication makes availability WORSE:
     now any one of N nodes dying loses data. More nodes = more
     failures = lower availability, not higher.
💡 Say the number: replication multiplies read capacity by roughly the replica count but leaves write capacity flat. If your estimate from back-of-envelope shows 6,000 writes/s against a ~5,000 writes/s ceiling, no number of replicas helps — that's a sharding conversation. Diagnosing which axis you're bounded on, before choosing a topology, is the whole skill.

2. Leader–Follower: The Default Topology

                    ┌──────────┐
   ALL WRITES  ───→  │  LEADER  │
                    └────┬─────┘
                repl.    │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
    ┌──────────┐   ┌──────────┐   ┌──────────┐
    │FOLLOWER 1│   │FOLLOWER 2│   │FOLLOWER 3│
    └──────────┘   └──────────┘   └──────────┘
          ▲              ▲              ▲
          └──────── READS can go to any node ───────┘

The single-writer constraint is a feature, not a limitation: one leader means all writes are ordered by one node, so write conflicts cannot occur. Everything about multi-leader replication (section 7) is harder precisely because it gives that up.

What actually travels over the wire matters more than diagrams suggest, and it's a frequent follow-up:

Replication methodShipsTrade-off
Statement-basedThe literal SQLCompact, but breaks on nondeterminism — NOW(), RAND(), auto-increment races produce different data on replicas. Largely abandoned for this reason.
Write-ahead log (WAL) shippingPhysical disk-block changesExact and fast, but couples replicas to the leader's storage format — so you can't run mixed versions, which blocks zero-downtime upgrades.
Logical (row-based)Row-level before/after imagesThe modern default (MySQL ROW, Postgres logical). Version-tolerant, and consumable by other systems — this is exactly what CDC taps for cache invalidation and search indexing.
Trigger-basedApplication-level change recordsFlexible and selective; significant write overhead. Used for bespoke partial replication.

3. Synchronous vs Asynchronous: A Durability Budget

The choice looks binary but is really a spectrum, and the correct framing is "how much data am I willing to lose, and what latency will I pay to lose less?"

SynchronousAsynchronousSemi-synchronous
Leader acks afterAll followers confirmLocal write onlyOne follower confirms
Write latency+1 network round trip, and paced by the slowest followerNo penalty+1 round trip to the fastest follower
Data loss if leader diesNoneEverything not yet shipped (the lag window)None — one replica provably has it
Availability riskAny slow/dead follower blocks all writesNoneBlocks only if every sync candidate is unreachable
Use forRarely — the availability coupling is usually unacceptableRead replicas, analytics copies, cross-regionThe right default for important data

Why fully-synchronous replication is usually a trap:

Leader + 3 synchronous followers. Each has 99.9% availability.
A write needs ALL of them. Effective write availability:

   0.999⁴ ≈ 99.6%   →  ~35 hours of write downtime per year,
                       WORSE than the single node you started with (~9 h).

You added redundancy and reduced availability. That's the coupling trap:
requiring N components makes you LESS available, not more. Redundancy
only helps when you need ANY of N, not ALL of N.

Semi-sync (any 1 of 3 confirms) inverts it:
   P(all 3 unavailable) = 0.001³ = 0.000000001  → essentially never blocks
   AND zero data loss, because someone always has the write.
🎯 Staff-level insight: that arithmetic generalises far beyond replication. Any design requiring all of N components multiplies failure probability; designs requiring any of N multiply reliability. When you see a synchronous fan-out to every replica, a 2PC across every service, or a request that fails if any dependency is slow, you're looking at the same bug in different clothing. Quorums (R+W>N) exist to sit in the middle: strong enough to be safe, loose enough to tolerate failure.

4. Replication Lag: The Bugs Users Actually Report

Async replication means followers trail the leader by anywhere from a millisecond to (during trouble) minutes. Every classic "ghost data" bug traces back to one of three violated guarantees:

① READ-YOUR-OWN-WRITES violated
   User posts a comment → refresh → comment GONE → refresh → it's BACK.
   The write hit the leader; the read hit a lagging follower.
   → Fix: version token, or pin post-write reads to the leader briefly.

② MONOTONIC READS violated
   User sees a comment, refreshes, and it DISAPPEARS — because request 1
   hit a caught-up follower and request 2 hit a further-behind one.
   Time appears to run backwards.
   → Fix: sticky routing (a session always reads the same replica).

③ CAUSAL / CONSISTENT-PREFIX violated
   Observer sees the ANSWER before the QUESTION, because two shards
   replicated at different speeds and the conversation spans both.
   → Fix: causal tracking, or keep causally-related data on one shard.

Each fix is covered in depth in CAP Theorem & Consistency Models; the key insight for this lesson is that these are replication-topology bugs, not application bugs — no amount of frontend retry logic fixes them, and they're invisible in testing because lag is ~0 on an idle system.

When lag explodes — the operational reality worth knowing:

CauseWhyMitigation
Single-threaded replica applyThe leader writes with 64 concurrent connections; a replica replays serially and simply can't keep upParallel apply (MySQL multi-threaded replication, based on independent transaction groups)
Long-running query on the replicaAn analytics query blocks WAL application to avoid reading rows it's about to loseSeparate analytics replicas from serving replicas; allow controlled lag there
Bulk write / migration on the leaderA backfill generates far more WAL than the replica link can carryThrottle backfills; batch with pauses; watch lag as a gate on the job
Cross-region link150 ms RTT plus bandwidth limitsExpect seconds of lag; never serve read-your-own-writes from another continent

Alert on lag in bytes/seconds, not just "replica is up". A replica 10 minutes behind is usually worse than a replica that's down: it's still in the load balancer, silently serving stale reads. A health check that only pings the process will happily route traffic to it.

5. Failover: Four Steps, Each With A Failure Mode

1. DETECT     the leader is gone   (missed heartbeats)
2. ELECT      a new leader         (most up-to-date follower, or consensus)
3. RECONFIGURE clients/proxies     (point writes at the new leader)
4. REINTEGRATE the old leader      (it must rejoin as a FOLLOWER)

Walk through what goes wrong at each step — this structure is exactly what senior interviewers probe.

Step 1, Detect — the timeout dilemma. You cannot distinguish a dead leader from a slow one. That's not an engineering gap; it's a theoretical impossibility in an asynchronous network.

Timeout too SHORT → a GC pause or brief network blip triggers a needless
                    failover. Failovers aren't free: they drop connections,
                    abort in-flight transactions, and risk data loss.
                    Flapping is worse than the original problem.
Timeout too LONG  → real outages last longer than they should.

Typical: 10–30 s for databases. And crucially, whoever declares death
must be a MAJORITY — one node's opinion is never enough, or a node that's
merely isolated will declare a perfectly healthy leader dead.

Step 2, Elect — choosing wrong loses data. With async replication, followers are at different positions in the log. Promote the furthest-behind follower and you discard every write the others had. So elect the most up-to-date replica — which is precisely what Raft enforces by refusing to elect a candidate whose log is behind a majority's.

Step 3, Reconfigure — and this is where split brain lives (section 6). Clients, proxies and DNS caches must all learn the new leader. Any that don't keep writing to the old one.

Step 4, Reintegrate — the discarded-writes problem. The old leader had writes it never replicated. It comes back believing they're committed. They aren't — the new leader never saw them.

Old leader had: writes 1..100
Replicated:     writes 1..97
New leader starts from 97, accepts NEW writes 98', 99', 100'

Old leader returns holding 98, 99, 100 — which CONFLICT with 98', 99', 100'.
Those writes must be DISCARDED. They were acknowledged to clients and are
now gone: real, silent data loss.

Worse in practice: if IDs are auto-increment, 98/99/100 and 98'/99'/100'
are DIFFERENT ROWS WITH THE SAME PRIMARY KEYS. Naive reintegration
corrupts data rather than merely losing it — which is why tools refuse
to auto-rejoin and demand a rebuild from the new leader instead.

6. Deep Dive: Split Brain, And Why Heartbeats Can't Fix It

Split brain is two nodes simultaneously believing they are the leader, both accepting writes. It's the most serious failure in this lesson because it's a correctness violation, not an availability one — and the damage is discovered later, in inconsistent data, not in an alert.

Network partitions the leader from its followers, but the leader is
ALIVE and still reachable by some clients:

  Clients (group A) ──→ OLD LEADER  ✕✕✕  FOLLOWERS ←── Clients (group B)
                        still accepting        promoted a NEW leader
                        writes!                also accepting writes

Both are "the leader". Both take writes. The data diverges with no
correct merge — the same account is debited twice from two ledgers.

Why a majority quorum is necessary but not sufficient. Requiring a majority to elect prevents the minority side from electing a new leader — good. But it does not stop the old leader, which was already elected, from continuing to serve writes. It doesn't know it lost the election.

Three mechanisms, layered:

MechanismHow it worksLimitation
Leader leaseLeadership expires after N seconds unless renewed by a majority. A leader that can't reach a majority must voluntarily step down when its lease lapses.Relies on bounded clock drift and on the leader actually executing its own step-down code — a process frozen in GC does neither. Wall-clock jumps break it outright.
Fencing tokensEach new leader gets a monotonically increasing number. Every write carries it. Storage rejects any write with a token lower than the highest it has seen.Requires the storage/resource layer to participate. This is the robust answer — it doesn't care about clocks, pauses, or what the old leader believes.
STONITH ("shoot the other node in the head")Forcibly power off or network-isolate the old leader before promoting.Needs out-of-band control (IPMI, cloud API) and can itself partition. Brutal but final; standard in HA clusters.

Fencing tokens deserve the detail, because they're the mechanism that actually holds:

Leader A acquires leadership with token 33.
A pauses (GC, VM migration) for 40 s. Its lease expires.
Followers elect B, which gets token 34.
B writes with token 34. Storage records "highest seen = 34".

A wakes up, still believing it is the leader, and writes with token 33.
Storage compares 33 < 34  →  REJECTS the write.

A learns it is deposed from the rejection itself, not from a heartbeat.
No clock assumption. No cooperation from A required. This is why it works
where leases alone don't.
⚠️ The subtlety that separates senior answers: a paused process cannot be trusted to police itself. Any protocol relying on the old leader noticing it should stop — lease expiry, "check if I'm still leader before writing" — has a window between the check and the write in which the process can be suspended for arbitrarily long. The only robust defence puts the check at the resource being protected: the storage layer rejects the stale token. Push safety to the resource, never to the actor. The same reasoning applies to distributed locks (see Concurrency Control) — a lock without a fencing token is advisory, not safe.

7. Deep Dive: Multi-Leader and Leaderless

Single-leader replication is the default because it avoids write conflicts. Two alternatives give that up deliberately, in exchange for something specific:

TopologyBuys youCosts you
Multi-leader (active-active)Local write latency in every region; a region survives losing the WAN link; write availability during partitionsWrite conflicts are now unavoidable and need resolution (LWW, CRDTs, app merge — see CAP). Auto-increment IDs break; use UUIDs or Snowflake.
Leaderless (Dynamo-style)No failover step at all — any node takes writes, so there's no election to get wrong and no split brain to preventQuorum tuning becomes the app's problem; needs read repair, anti-entropy and hinted handoff to converge.

The honest guidance for interviews: propose multi-leader only when you can name the conflict resolution strategy and show the conflicts are rare or mergeable. "Active-active across three regions" sounds impressive and is a trap — if two regions can edit the same record, you've signed up for a distributed-systems research problem. It works beautifully when writes are naturally partitioned by geography (each user's home region owns their data, so conflicts are almost impossible), which is the design used in practice.

Leaderless is genuinely different in one respect worth stating: by eliminating the leader it eliminates this entire lesson's hardest section. No leader means no detection dilemma, no election, no split brain, no reintegration. The complexity doesn't vanish — it moves into quorums and convergence — but if an interviewer pushes on failover complexity, "or we avoid leader election entirely with a Dynamo-style quorum system, trading strong ordering for it" is a strong pivot.

Interview Questions

🟢 Beginner — What does replication solve, and what does it not solve?

It solves two things: availability (if one node dies, others hold the same data and one can be promoted) and read throughput (reads can be served by any replica, so read capacity scales roughly with replica count).

It does not solve write throughput. In leader–follower replication every write goes through the single leader, so adding replicas leaves write capacity flat — and actually adds a little load, since the leader must now ship changes to more followers. If writes are the bottleneck you need sharding, which puts different data on different nodes so writes spread across leaders.

It also doesn't replace backups: replication copies mistakes faithfully. An accidental DELETE without a WHERE clause reaches every replica in milliseconds. You need point-in-time backups for that, which is a different concern from availability.

In production you use both: shard for capacity, replicate each shard for availability — e.g. 4 shards × 3 replicas = 12 nodes.

🟢 Beginner — Explain replication lag with a user-visible example.

With asynchronous replication, the leader acknowledges a write before followers have applied it, so followers trail by anywhere from a millisecond to minutes under load. Lag is the size of that gap.

The classic user-visible bug: a user posts a comment. The write goes to the leader and succeeds. The page refreshes, that read is load-balanced to a follower that hasn't applied the write yet, and the comment isn't there. The user refreshes again, hits a caught-up replica, and it reappears. From the user's point of view the site randomly lost and recovered their data — the most common "ghost data" bug report in web applications.

This is a violation of read-your-own-writes consistency. It's a topology problem, not an application bug: no frontend retry fixes it, and it's invisible in testing because lag is effectively zero on an idle system. Fixes include routing a user's reads to the leader briefly after they write, or having the write return a version token the read then requires the replica to have reached.

🟡 Mid — Sync or async replication for a payments system? Justify with numbers.

Semi-synchronous — at least one synchronous replica, the rest async. Here's the reasoning:

Pure async is unacceptable because if the leader dies, every write not yet shipped is lost. For payments that means captured money with no record — an unreconcilable financial discrepancy, not just a bug.

Fully synchronous to all replicas is also wrong, and this is the part that needs numbers. With a leader and 3 sync followers at 99.9% each, a write needs all four: 0.999⁴ ≈ 99.6% availability, roughly 35 hours of write downtime a year — worse than the single node you started with (~9 h). You added redundancy and became less available, because any one slow or dead follower blocks every write.

Semi-sync inverts the arithmetic: the write needs any one of the 3 followers to confirm. P(all three unavailable) = 0.001³ = 10⁻⁹, so it essentially never blocks — while still guaranteeing at least one replica provably holds every acknowledged write, so failover loses nothing. You get async-like availability and sync-like durability.

Details I'd add for payments specifically: put the synchronous replica in a different availability zone (same-AZ sync doesn't survive an AZ loss) but not a different continent (150 ms per write is too slow) — so a different AZ in the same region, roughly 1–2 ms. And make the write path idempotent with an idempotency key, because during failover clients will retry writes whose outcome they don't know, and at-least-once delivery plus idempotency is how you get effectively-once behaviour.

🟡 Mid — Walk me through automatic failover and what breaks at each step.

1. Detect. Followers miss heartbeats from the leader and declare it dead. What breaks: you fundamentally cannot distinguish a dead leader from a slow one — a GC pause looks identical to a crash. Too short a timeout causes needless failovers (which drop connections and abort transactions, so flapping is worse than the slowdown); too long extends real outages. Typically 10–30 s, and a majority must agree, otherwise a node that is itself isolated will declare a healthy leader dead.

2. Elect. Choose a new leader. What breaks: with async replication, followers sit at different log positions. Promoting a behind replica silently discards every acknowledged write the others had. So you must promote the most up-to-date replica — which is exactly what Raft enforces by refusing to elect a candidate whose log trails a majority's.

3. Reconfigure. Point clients, proxies and DNS at the new leader. What breaks: anything that doesn't get the message keeps writing to the old leader — this is where split brain occurs. Caches, connection pools with long-lived connections, and DNS TTLs all lag. A proxy layer (ProxySQL, PgBouncer) or a coordination service is far more reliable than DNS.

4. Reintegrate. The old leader must rejoin as a follower. What breaks: it holds writes it never replicated and believes them committed. They must be discarded — silent loss of acknowledged data. Worse, with auto-increment primary keys, its writes 98/99/100 and the new leader's 98'/99'/100' are different rows sharing primary keys, so naive rejoining corrupts rather than merely loses. That's why production tooling refuses to auto-rejoin and instead rebuilds the old leader from the new one.

Given all four, many teams deliberately choose manual or approval-gated failover for their most critical databases: the mean time to recovery is worse, but you avoid automated systems making an unrecoverable decision at 3am.

🔴 Senior — What is split brain, and why don't heartbeats and leases fully prevent it?

Split brain is two nodes simultaneously acting as leader, both accepting writes. It's the worst failure in replication because it's a correctness violation — data diverges with no correct merge — and it surfaces later as inconsistency rather than immediately as an alert.

It arises when a partition isolates the leader from its followers while the leader is still alive and reachable by some clients. Followers promote a new leader; the old one never learns it was deposed. Now both take writes.

Why a majority quorum isn't enough: requiring a majority to elect stops the minority side from promoting anyone. It does nothing about the old leader, which was legitimately elected earlier and simply keeps going.

Why leases aren't enough: a lease says "leadership expires in 10 s unless renewed by a majority", requiring the leader to step down voluntarily. Two problems. First, it assumes bounded clock drift — a wall-clock jump (NTP correction, VM migration) breaks the reasoning. Second and more fundamentally, a paused process cannot police itself: a leader can check "is my lease still valid?", get "yes", then be suspended by GC or a VM freeze for 40 seconds, and issue the write when it wakes. There is always a window between the check and the write, and no amount of checking closes it.

What actually works — fencing tokens. Each leadership term gets a monotonically increasing number. Every write carries it. The storage layer tracks the highest token seen and rejects anything lower:

A leads with token 33 → pauses 40 s → B elected with token 34
B writes (34) → storage records highest = 34
A wakes, writes with token 33 → 33 < 34 → REJECTED

No clock assumptions, no cooperation from A, no vulnerable window. A discovers it's deposed from the rejection itself.

The general principle, which is what's really being tested: push the safety check to the resource being protected, never to the actor. This is also why a distributed lock without a fencing token is advisory rather than safe — the same flaw, and the reason Redis-based locking schemes are debated. Layer STONITH on top where you have out-of-band control, since forcibly powering off the old leader removes all doubt.

🔴 Senior — Design replication for a global SaaS: 10M users across US, EU and APAC, with GDPR data-residency requirements.

The residency requirement is the design driver, and it turns out to make the distributed-systems problem easier, not harder — recognising that is the senior insight here.

1. Partition by user home region — writes are single-leader within a region. Each user's record has a home region (eu-west, us-east, ap-south), and all writes for that user go to that region's leader. Because a user's data is only ever written in one place, there are no cross-region write conflicts — I get active-active behaviour at the global level without any conflict resolution, because the write sets are disjoint. Avoid true multi-leader on the same records: concurrent edits have no correct merge and I'd be inventing a research problem.

2. Within a region: semi-synchronous across AZs. Leader plus one sync replica in a different AZ (~1–2 ms, so cheap) and two async replicas for read scaling. Survives an AZ failure with zero data loss and no write-availability coupling.

3. GDPR forces the shape of cross-region replication. EU personal data must stay in the EU, so I cannot globally replicate the user table. Instead:

Per-region (never replicated out): PII, messages, documents, activity
Globally replicated (async, eventually consistent):
   - user_id → home_region  DIRECTORY (routing metadata, not personal data)
   - non-personal reference data: plans, feature flags, pricing, config
   - aggregated/anonymised analytics (k-anonymity thresholds applied)

The routing directory is the keystone: small, rarely changing, safe to replicate everywhere, and it lets any edge accept a request and forward it to the right region. It needs care — a stale directory entry sends a user to the wrong region — so version it and treat a miss as "look up authoritatively" rather than "guess".

4. Latency for non-home users. A EU user travelling in APAC gets ~150 ms writes because their writes must return to the EU leader. Mitigate with an edge/CDN layer for reads and optimistic UI for writes; accept it for the genuinely rare case. Do not "solve" it by replicating their data to APAC — that's a compliance breach, and this is where the residency constraint prevents an engineering mistake.

5. Cross-region DR. Residency generally permits an in-jurisdiction DR replica, so EU data replicates to a second EU region, not to the US. State the RPO/RTO explicitly: async cross-region means RPO measured in seconds (some data loss on a hard region failure) and RTO in minutes if promotion is gated on human approval. See Multi-Region & DR.

6. Right to erasure. Deletion must propagate to replicas, backups and derived stores (search indexes, caches, warehouses). This is where most designs quietly fail an audit: a backup taken before deletion still contains the data. Practical answer — crypto-shredding: encrypt each user's data with a per-user key and delete the key, rendering every copy including backups unrecoverable without touching them.

The framing to close on: the compliance constraint eliminated the hardest technical problem. Because data must be region-partitioned, I never face concurrent multi-region writes to one record — the requirement that looked like a burden removed the need for conflict resolution entirely. Constraints that partition your write set are gifts.

🏋️ Graded Exercises

Exercise 1 (Easy): Your system does 40,000 reads/s and 8,000 writes/s. One node handles 10,000 reads/s or 5,000 writes/s. What topology do you need?
Solution 
Writes: 8,000 needed / 5,000 per node  → exceeds ONE leader
        → replication does not help → must SHARD (≥2 shards)
Reads:  40,000 / 10,000 per node       → need ≥4 read-capable nodes

Topology: 2 shards × 3 replicas = 6 nodes
  Write capacity: 2 leaders × 5,000  = 10,000/s ✓ (8,000 needed)
  Read capacity:  6 nodes × 10,000   = 60,000/s ✓ (40,000 needed)
  Availability:   any single node can fail ✓

The trap is answering "add 4 read replicas" — that satisfies reads but leaves writes at a 5,000/s ceiling against 8,000/s of demand. Always check both axes, and note they need different solutions: sharding for writes, replication for reads.

With headroom for peak (2×) and failure, you'd realistically run 3 shards × 3 replicas.

Exercise 2 (Easy): A leader and 4 followers each have 99.9% availability. Compute write availability under fully-synchronous vs semi-synchronous replication.
Solution 
FULLY SYNCHRONOUS — needs leader AND all 4 followers:
   0.999⁵ = 0.99501  →  99.5%  ≈ 44 hours downtime/year
   (a single node alone would be 99.9% ≈ 9 hours — you made it 5× WORSE)

SEMI-SYNCHRONOUS — needs leader AND any 1 of 4 followers:
   P(all 4 followers down) = 0.001⁴ = 10⁻¹²  (negligible)
   Write availability ≈ P(leader up) = 0.999 → 99.9%, and with
   automatic failover the leader itself becomes replaceable.

The lesson: requiring ALL of N multiplies failure; requiring ANY of N multiplies reliability. Redundancy only helps when it's an OR, not an AND. Semi-sync gets sync's durability guarantee (someone provably has the write) with async's availability profile — which is why it's the right default for important data.

Exercise 3 (Medium): Users intermittently report data disappearing then reappearing. Replication lag averages 200 ms. Explain the mechanism and give three fixes with trade-offs.
Solution

Mechanism: read-your-own-writes violation. The write commits on the leader; the subsequent read is load-balanced to a follower still 200 ms behind, which doesn't have it yet. The next request hits a caught-up replica and the data "returns". Note that the average lag is a red herring — what matters is the p99, which under load can be seconds.

Two related symptoms to distinguish: if data appears and disappears repeatedly across refreshes, that's also a monotonic reads violation — successive reads landing on replicas at different positions.

Fix 1 — pin post-write reads to the leader for ~N seconds per user.
Pro: trivial, ships today. Con: adds read load to the leader (the node you least want loaded), and N is a guess — if p99 lag exceeds it, the bug returns.

Fix 2 — session-sticky replicas. Route a session consistently to one replica.
Pro: also gives monotonic reads; no leader load. Con: uneven load distribution; breaks when that replica dies or is de-pooled; doesn't help if the sticky replica is the lagging one.

Fix 3 — write-version token (the correct fix). The write returns its log position (GTID/LSN); the client sends it with subsequent reads; a replica behind that position waits briefly or forwards to the leader.
Pro: precisely correct, scoped to only the requests that need freshness, no guessing. Con: clients must carry the token, and it needs replica support and API changes.

What I'd actually do: ship fix 1 immediately, implement fix 3 properly, and — regardless — alert on replication lag and de-pool replicas exceeding a threshold. A replica 10 minutes behind is worse than one that's down, because it stays in rotation serving stale data.

Exercise 4 (Medium): Your leader fails. Follower A is 50 writes behind, B is 200 behind, C is 5 behind. Which do you promote, what's lost, and how do you reduce future loss?
Solution

Promote C — the most up-to-date replica, 5 writes behind. Any other choice discards more acknowledged data.

What's lost: the 5 writes the leader acknowledged but never shipped to C. Those clients received success responses for data that no longer exists — silent, unrecoverable loss (the leader's disk may still hold them, but as section 5 shows, merging them back conflicts with new writes and can corrupt data with reused primary keys).

Then handle A and B: A is 50 behind and C is 5 behind, so A and B are missing writes C has, but they may also hold writes C doesn't (if the leader shipped to them in a different order). They must be reset to C's log position and re-replicate forward from there — not left to diverge.

Reducing future loss:

• Semi-synchronous replication — the real fix. Requiring one replica to confirm before acking means a promotable replica always has every acknowledged write: RPO becomes zero instead of "however far behind we happened to be".
• Investigate why B is 200 behind — that's a symptom, usually single-threaded apply, a long analytics query blocking WAL replay, or an undersized replica. Lag is a leading indicator of data loss.
• Alert on lag with de-pooling, so lagging replicas neither serve reads nor become promotion candidates.
• Idempotent client retries — clients can't know whether their in-flight write survived, so make retries safe with idempotency keys. This converts data loss into a retry for anything still in-flight.

Worth stating plainly: async replication means your RPO equals your replication lag. If you can't tolerate losing the last N seconds of writes, you cannot use pure async — that's a requirements decision, not a tuning exercise.

Exercise 5 (Hard): Your monitoring shows two nodes both accepting writes as leader for 90 seconds. Explain how it happened, how to remediate now, and how to prevent recurrence.
Solution

How it happened — the likely sequence:

1. Leader L experiences a 60 s stall (GC pause, VM migration, disk I/O
   hang) or is partitioned from followers but NOT from some clients.
2. Followers miss heartbeats, declare L dead, elect N (majority agrees).
3. Clients/proxies partially reconfigure — some now write to N.
4. L resumes (or the partition heals asymmetrically). L never learned it
   was deposed, so it keeps serving the clients still connected to it.
5. For 90 s, both L and N accept writes. Data diverges.

Remediate now — order matters, and speed matters because divergence grows:

1. Stop the bleeding first: forcibly isolate L — revoke its network access or power it off via the cloud API/IPMI (STONITH). Don't try to reason with it; every second adds divergent writes.
2. Freeze writes briefly if the data is financial. A short outage is cheaper than more divergence.
3. Quantify the damage: diff L's and N's logs over the 90 s window. Identify which rows were written on both sides — those are the true conflicts; writes touching disjoint rows can often be replayed.
4. Reconcile with domain logic, not automation. There is no generically correct merge. Duplicate financial transactions need business rules and probably human review. Do not let a tool pick by timestamp — that silently chooses one customer's reality over another's.
5. Rebuild L from N from scratch. Never rejoin a divergent node.
6. Reconcile downstream: anything derived from those writes — caches, search indexes, analytics, emails already sent, payments already captured — also saw divergent data.

Prevent recurrence:

• Fencing tokens (the essential fix). Every leadership term gets an increasing number; storage rejects writes carrying a stale one. L's post-recovery writes would have been rejected immediately at step 4, capping the incident at zero divergent writes. Note this requires the storage layer to participate — it cannot be bolted on at the application tier alone.
• STONITH before promotion, so the old leader is provably dead before a new one starts.
• Route through a proxy (ProxySQL/PgBouncer) rather than DNS or client-side config, so reconfiguration is atomic instead of gradual — step 3's "partial" reconfiguration is what let both nodes have clients.
• Require majority agreement to declare death, and have the leader itself step down if it can't reach a majority (a lease) — necessary but, as section 6 shows, not sufficient alone.
• Fix the root cause of the stall: tune GC, check for disk I/O saturation, and consider whether a 60 s pause indicates an undersized or misconfigured node.
• Alert on "two leaders" explicitly — a monitoring check that counts nodes claiming leadership. Detecting this in 5 s instead of 90 s is a 20× reduction in blast radius.

Exercise 6 (Hard): Design replication for a multiplayer game: player inventory (must never duplicate items), chat (high volume, loss-tolerant), and match results (must be durable). One region, 50K concurrent players.
Solution

Three data classes with genuinely different requirements — the exercise is about resisting one uniform answer.

DataTopologyReasoning
Player inventorySingle leader + semi-sync replica, sharded by player_id. All writes for a player go to one leader, wrapped in a transaction."Never duplicate items" is a linearizability requirement — item duplication bugs are how game economies get destroyed. Sharding by player keeps every inventory operation single-shard, so a plain local transaction suffices; no distributed transaction needed. Semi-sync gives RPO=0: a lost trade means lost items and a support ticket.
ChatAsync replication, or don't persist at all — in-memory pub/sub with a short Redis-backed scrollback buffer.High volume, ephemeral value, loss-tolerant. Paying for durable replication of chat is wasted money; a dropped message during a crash is unnoticeable. Persist only what moderation/compliance requires, async, to a cheap write-optimised store.
Match resultsSemi-sync, append-only, then async-replicate to analytics.Immutable once written, which makes replication trivially conflict-free. Ranked results affect player standing and possibly prize money, so durability matters — but they're written once per match (low volume), so synchronous cost is irrelevant.

Sizing. 50K concurrent players is modest — worth stating so as not to over-engineer:

Inventory writes: trades/loot ≈ 1 per player per 30 s → ~1,700 writes/s
                  → ONE leader handles this. Shard for isolation and
                    future growth, not because capacity demands it (yet).
Chat:             ~1 msg/player/10 s → 5,000 msg/s → trivially in-memory.
Match results:    50K players / 10 per match / 300 s ≈ 17 matches/s → nothing.

The genuinely hard part — item trading between two players, which is the question behind the question. A trade touches two inventories, and if they're on different shards you have a cross-shard transaction. Options:

1. Escrow / saga (preferred): remove item from A into an escrow record, then add to B, with a compensating action if step 2 fails. Each step is a single-shard transaction. State transitions are idempotent so retries are safe.
2. Co-locate trading partners — impractical, since anyone can trade with anyone.
3. Route all trades through a single "trade service" shard that owns the ledger of in-flight trades. Serialises trades but keeps correctness simple; at 17 matches/s-scale traffic this is easily fast enough.

The duplication bug to name explicitly: the classic exploit is a client retrying a trade whose response was lost, and the server processing it twice — producing two copies of the item. This is not a replication problem; it's an idempotency problem, and semi-sync replication wouldn't prevent it. Every mutating operation needs a client-supplied idempotency key checked inside the same transaction that applies the change. Recognising that the headline requirement ("never duplicate items") is solved by idempotency rather than by replication topology is the real insight here.

🎯 Key Takeaways

  • Replication ≠ sharding. Replication buys availability and read throughput; sharding buys write throughput and dataset size. Diagnose which axis binds you before choosing.
  • Requiring ALL of N multiplies failure; requiring ANY of N multiplies reliability. Fully-synchronous replication to 3 followers is less available than one node.
  • Semi-synchronous is the right default for important data: zero data loss with no availability coupling.
  • Your RPO equals your replication lag under async replication. If you can't lose the last N seconds, you can't use pure async.
  • Replication lag causes user-visible bugs — vanishing comments, time running backwards — that are topology problems, not application bugs, and are invisible on an idle test system.
  • Alert on lag, not liveness. A replica 10 minutes behind is worse than one that's down, because it stays in rotation.
  • Failover has four steps and each fails distinctly: you can't distinguish slow from dead, promoting a behind replica discards writes, partial reconfiguration causes split brain, and rejoining a divergent old leader can corrupt data with reused primary keys.
  • Split brain is a correctness failure, and leases can't prevent it — a paused process can't police itself, and there's always a window between the check and the write.
  • Fencing tokens are the real fix: push the safety check to the resource being protected, not the actor. The same principle makes distributed locks safe.
  • Replication is not a backup. It faithfully copies your DROP TABLE everywhere in milliseconds.
  • Multi-leader only with a named conflict strategy — and best of all, partition writes so conflicts are impossible rather than resolved.
