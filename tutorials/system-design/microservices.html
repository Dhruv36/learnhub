Microservices Architecture Fundamentals

What you'll master: why microservices are an organisational solution before a technical one, how to draw boundaries that don't produce a distributed monolith, the availability arithmetic that makes synchronous chains dangerous, sagas with compensating actions (and why compensation isn't rollback), the four resilience patterns and how they compose, and how to argue the case against microservices — which is the answer interviewers most often reward.

Prerequisites: CAP Theorem, Pub/Sub vs Message Queues (outbox, idempotency), REST & API Contracts. Feeds Observability, Data Platforms and Migration Strategies.

1. The Actual Reason Microservices Exist

The technical benefits usually cited — independent scaling, technology choice, fault isolation — are real but secondary. The primary driver is letting many teams ship without coordinating.

ONE codebase, 5 engineers:
   merge conflicts rare · one deploy pipeline · one test run
   coordination cost ≈ 0. A monolith is strictly better here.

ONE codebase, 200 engineers across 20 teams:
   every deploy is a negotiation · one team's failing test blocks
   everyone · release trains form · "we deploy on Thursdays"
   → the CODEBASE has become the bottleneck, not the machines.

Splitting into 20 services each owned end-to-end by one team removes
that coordination. THAT is what you're buying. Everything else is a
side effect.
⚠️ The interview trap is "microservices are better". They're not better; they trade operational simplicity for team independence. A 5-person startup adopting them on day one pays the entire distributed-systems tax — network partial failure, eventual consistency, distributed tracing, service discovery — to solve a coordination problem it does not have. The mature answer is "start with a modular monolith and split when the coordination pain is real and measurable", and being able to say which pain (deploy frequency blocked by other teams, one module needing radically different scaling, a compliance boundary) is what makes it credible.
MonolithMicroservices
DeploymentOne unit — all or nothingPer service, independent
Team scalingCoordination cost grows with team countTeams own services end to end
Refactoring across boundariesEasy — compiler finds every caller, one atomic commitHard — a cross-service change is a multi-repo, multi-deploy, versioned migration
TransactionsACID across the whole app, for freeNone across services — sagas and eventual consistency
DebuggingOne stack trace, one log streamDistributed tracing required or you're blind
Failure isolationOne memory leak takes down everythingIsolated if you build circuit breakers, timeouts, bulkheads
ScalingScale the whole app for its hungriest partScale each service to its own demand

Note the third row — it's the cost people underestimate most. In a monolith, moving a field between two modules is a rename the compiler verifies. Across services it becomes: add the field to service B, deploy, dual-write from A, migrate consumers, verify, remove from A, deploy. Weeks instead of minutes. Put boundaries where you expect changes not to cross.

2. Drawing Boundaries: The Decision That Determines Everything

Bad boundaries produce a distributed monolith — services that must be deployed together anyway, but now with network latency, partial failure and no transactions. Strictly worse than the monolith you left.

Heuristics that actually help when the domain isn't obvious:

SignalWhat it suggests
Two areas change together in most PRsSame service. Change coupling is the strongest evidence available — read your git history rather than theorising.
Different scaling profilesPossible split. Image processing (CPU-heavy, bursty) vs the order API (steady, I/O-bound) genuinely benefit from separate scaling.

The database rule is absolute: one service, one database, no sharing. Two services reading the same tables recreates tight coupling invisibly — service B's query now depends on service A's schema, so A can't migrate without breaking B, and you have all the coupling of a monolith with none of the compiler support. If B needs A's data, it calls A's API or subscribes to A's events. This is the rule teams break first and regret most.

3. Deep Dive: The Availability Arithmetic Of Synchronous Chains

The same any-of-N vs all-of-N reasoning from replication applies, and it's the strongest argument for asynchronous communication:

A request that synchronously calls 5 services, each 99.9% available:
   0.999⁵ ≈ 99.50%   →  ~44 hours of downtime per year

Same 5 services, each 99.99%:
   0.9999⁵ ≈ 99.95%  →  ~4.4 hours/year

Availability MULTIPLIES down a synchronous chain. To make a
composite service highly available, every dependency must be
MORE available than your target — an escalating requirement.

Latency composes just as badly, and worse in the tail:

5 sequential calls, each p99 = 20 ms → 100 ms p99 at best.

Tail amplification: with 5 independent calls, the probability that
at LEAST ONE hits its p99 is 1 − 0.99⁵ ≈ 5%.
→ your p95 is dominated by other services' p99s.

Parallelise independent calls: latency becomes max(20 ms) not sum.
Always check whether sequencing is a real data dependency or just
how the code was written — it's usually the latter.
Communication styleAvailability impactUse for
Synchronous (REST/gRPC)Multiplies — caller is down when callee is downQueries needing an immediate answer; steps whose result changes the response
Asynchronous (events)Isolates — callee can be down for hours; work queues upEverything that isn't required for the response's correctness
Cached / replicated dataIsolates — you own a local copyReference data read constantly and changed rarely (product catalogue, feature flags)
🎯 The design principle worth stating in any microservices interview: every synchronous call is a shared fate decision. Before adding one, ask "should my service be down when theirs is?" For payment authorisation during checkout the answer is genuinely yes. For fetching a display name it's no — cache it, or accept its absence. Most cascading-failure incidents trace back to a synchronous call that nobody consciously decided to make.

4. Deep Dive: Sagas — Distributed Transactions Without Distributed Transactions

Cross-service ACID doesn't exist, and 2PC is the wrong answer (it multiplies availability, holds locks across the network, and can't include third parties). A saga is a sequence of local transactions, each with a compensating action:

Happy path:
  1. Order Service    → create order (PENDING)
  2. Payment Service  → charge card
  3. Inventory        → reserve stock
  4. Order Service    → mark CONFIRMED

Step 3 fails → run compensations in REVERSE:
  2'. Payment Service → REFUND the charge
  1'. Order Service   → mark order CANCELLED

Compensation is not rollback, and the difference matters:

ROLLBACK      erases history. Nobody ever saw the intermediate state.
COMPENSATION  adds a new fact that offsets the old one. The charge
              HAPPENED and the refund HAPPENED — both appear on the
              customer's statement.

Consequences you must design for:
 • Side effects that ESCAPED cannot be compensated. If step 2 sent a
   "payment received" email, no compensating action unsends it. Order
   steps so irreversible effects come LAST, or make them conditional.
 • Other transactions can observe intermediate state — the order was
   briefly PENDING with a charge and no stock. Model those states
   explicitly rather than pretending they don't exist.
 • Compensations can THEMSELVES fail. The refund API is down. You need
   retries, a DLQ, and ultimately a human — so make every compensation
   idempotent and durably queued.
ChoreographyOrchestration
HowEach service listens for events and reacts; no central brainA coordinator explicitly directs each step and handles failures
ProNo single point of failure; services stay decoupled; easy to add a participantThe whole flow is readable in one place; failure handling and timeouts are explicit; easy to query saga state
ConNobody knows the whole flow. Understanding "what happens on checkout" means reading 6 services. Cyclic event chains are easy to create accidentallyThe coordinator is a new component to build, scale and keep available; risks becoming a god service holding all business logic
Use when2–3 participants, simple flows4+ participants, real compensation logic, or when you need to answer "where is order 42 stuck?"

For anything with money in it, prefer orchestration. When a customer calls support asking why their order is stuck, "let me query the saga state" beats "let me correlate logs across six services". Model the saga as an explicit state machine with a durable record per instance, so a crash mid-saga leaves a resumable state rather than an ambiguous one.

And the saga must be built on the primitives from pub/sub: every step idempotent (they will be retried), every event published via the outbox pattern (or a crash between the local commit and the event publish strands the saga forever).

5. Deep Dive: Resilience Patterns And How They Compose

PatternPreventsKey parameter
TimeoutA slow dependency consuming your threads indefinitelySet from the dependency's p99, not a round number. No timeout = infinite timeout.
Retry + backoff + jitterTransient blips causing user-visible errorsBounded attempts (2–3). Jitter is mandatory — synchronised retries are a self-inflicted DDoS.
Circuit breakerHammering a known-dead dependency and waiting on every callOpens after N failures → fails fast → half-open probe → closes. Converts slow failures into instant ones.
BulkheadOne slow dependency exhausting the shared pool and starving unrelated workSeparate thread/connection pools per dependency.
FallbackA failed dependency becoming a failed requestCached value, default, or degraded response — decided in advance.
Load sheddingAccepting more work than you can serve, and dyingReject early with 429 when queues are deep. Partial service beats none.

How they compose — the order matters:

request
  → BULKHEAD        (is there capacity in THIS dependency's pool?)
    → CIRCUIT BREAKER (is it currently known-bad? fail fast if so)
      → TIMEOUT       (bound this attempt)
        → CALL
      ← retry with jittered backoff on transient failure (bounded)
  ← FALLBACK        (breaker open or retries exhausted → degrade)

The subtle interaction people miss: retries and circuit breakers fight each other if tuned naively. Retrying 3× against a struggling service triples its load exactly when it's failing — turning a partial outage into a total one. The circuit breaker must count attempts including retries, and ideally you use a retry budget (e.g. retries capped at 10% of requests) so a broad outage can't produce a retry storm. This is the mechanism behind most "the service recovered, then immediately died again" incidents.

Timeout budgets must decrease down the call chain, or they're meaningless:

❌ Gateway 30 s → Service A 30 s → Service B 30 s
   A waits the full 30 s for B even though the client gave up at 30 s
   overall. Work continues for a caller who has vanished.

✅ Gateway 3 s → A 2.5 s → B 2 s → DB 1.5 s
   Each layer leaves room for its own error handling and fallback.
   Propagate the REMAINING budget in a header so B knows it has 2 s,
   not "its configured default".

6. The Operational Tax (Budget For It Honestly)

Microservices move complexity from the codebase into the platform. That platform is not free, and pretending otherwise is why so many migrations stall:

NeedWhy it becomes mandatory
Distributed tracingA single request spans 8 services. Without trace IDs propagated everywhere, debugging is archaeology. Non-optional — see Observability.
Centralised logging + correlation IDsLogs in 20 places with no shared key are useless.
Service discoveryServices move, scale and restart; hardcoded addresses don't survive.
CI/CD per service20 services × manual deploys is untenable; independent deployability is the whole point.
Contract testingIntegration tests across 20 services are slow and flaky. Consumer-driven contracts catch breakage at build time.
Schema/versioning disciplineEvery inter-service call is now a versioned public API — see expand/contract.
On-call structureWho is paged when service 14 fails at 3am? Team ownership must be explicit and staffed.
Local dev storyEngineers can't run 20 services on a laptop. You need mocks, shared dev environments, or ephemeral per-PR environments.

Rough rule: the platform investment is worth it somewhere around 4+ teams. Below that you are funding a platform team's worth of work to solve a coordination problem you could solve with a well-modularised monolith and a code-owners file.

Interview Questions

🟢 Beginner — What problem do microservices actually solve?

Primarily an organisational one: they let many teams build, deploy and scale their part of a system without coordinating with everyone else.

With 200 engineers in one codebase, the codebase becomes the bottleneck — merge conflicts, one team's failing test blocking everyone's deploy, release trains, "we ship on Thursdays". Splitting into services each owned end-to-end by one team removes that coordination cost. That's the purchase.

The technical benefits are real but secondary: independent scaling (scale image processing without scaling the order API), fault isolation (with resilience patterns), independent technology choices, and smaller compliance scope.

The critical point is that it's a trade, not an upgrade. You give up ACID transactions across services, cheap cross-boundary refactoring, and simple debugging, and you take on a platform burden — tracing, service discovery, contract testing, per-service CI/CD. For a small team that trade is clearly negative, which is why "start with a modular monolith and split when coordination pain is real" is the better default.

🟢 Beginner — Why shouldn't two services share a database?

Because it recreates the tight coupling microservices exist to remove, but invisibly.

If service B reads service A's tables, then A's schema is now B's public API — except nothing declares or enforces that. A can't rename a column, change a type, or restructure without breaking B, and no compiler or contract test will warn anyone. You discover it in production.

It also destroys the ownership model: nobody can reason about who writes what, so data integrity rules live in two codebases and drift apart. And you can no longer deploy independently, which was the entire point — so you've kept every cost of distribution and lost its only benefit.

Instead: each service owns its database exclusively. If B needs A's data, it either calls A's API (synchronous, current data, couples availability) or subscribes to A's events and keeps its own local copy (asynchronous, eventually consistent, no availability coupling). The second is often better for read-heavy cases — B keeps exactly the projection it needs and stays up when A is down.

Worth noting the pragmatic exception: during a monolith-to-services migration you may temporarily share a database while splitting the code. That's acceptable as a transitional state with a deadline, not as a destination.

🟡 Mid — A checkout calls payment, inventory, shipping and notification synchronously. What's wrong?

Two problems: availability multiplies and latency sums.

4 dependencies at 99.9% each → 0.999⁴ ≈ 99.6% ≈ 35 hours/year down.
Checkout — the revenue path — is now less reliable than any single
dependency, and the notification service can take down purchasing.

Latency likewise: four sequential calls at 200 ms each is 800 ms before your own work, and tail amplification means ~4% of requests hit somebody's p99.

The fix is to classify each call by whether the response's correctness depends on it:

Must be synchronous: payment authorisation (you cannot confirm an order you can't charge for) and inventory reservation (overselling has real cost). Checkout's availability legitimately depends on these two.

Must not be synchronous: shipping and notification. Neither changes whether the order is valid. Publish an OrderPlaced event and let them consume it — if the notification service is down for an hour, emails queue and send later, and no customer notices.

0.999² ≈ 99.8% (~17 h/year) instead of 99.6% (~35 h)
Latency: 400 ms instead of 800 ms — and shipping/notification
         no longer contribute at all.

Further improvements: parallelise payment and inventory if they're independent, taking latency to max() rather than sum. Add per-dependency timeouts with a decreasing budget, circuit breakers so a dead dependency fails fast, and publish the event via the outbox pattern so a crash can't lose it. And handle the partial-failure case explicitly: payment succeeded but inventory reservation failed needs a compensating refund — that's a saga.

🟡 Mid — Explain the saga pattern and why compensation isn't rollback.

A saga implements a business transaction spanning services as a sequence of local transactions, each with a compensating action. Each service commits its own ACID transaction locally; if a later step fails, earlier steps' compensations run in reverse.

1. create order (PENDING)  → compensate: cancel order
2. charge card             → compensate: refund
3. reserve stock           → compensate: release stock
Step 3 fails → run 2' then 1'.

Why not 2PC: it multiplies availability (all participants must be up), holds locks across the network so a dead coordinator blocks everyone, and can't enrol third parties like Stripe.

Compensation vs rollback — three practical consequences:

1. History is preserved, not erased. A rollback means nobody ever saw the intermediate state. A compensation adds an offsetting fact: the charge happened and the refund happened, and both appear on the customer's statement. That's a product and support consideration, not just a technical one.

2. Escaped side effects can't be undone. If step 2 triggered a "payment received" email or fired a webhook to a partner, no compensating action retracts it. So order the steps to put irreversible effects last, or make them conditional on the saga completing.

3. Intermediate states are observable. Between steps 2 and 3 the order exists with a charge and no stock. Other queries can see it. You must model those states explicitly (PENDING, AWAITING_STOCK, CANCELLING) rather than pretending the transaction is atomic.

And compensations themselves fail. The refund API can be down, so compensations need durable queuing, bounded retries and idempotency — and ultimately an alert for human intervention, since a failed compensation is money in the wrong place.

For coordination I'd use orchestration for anything financial: a central coordinator makes the flow readable in one place and lets support answer "where is order 42 stuck?" with a query instead of a log correlation exercise.

🔴 Senior — One slow service is causing cascading failures across your platform. Diagnose and fix.

The mechanism — slowness propagates worse than outright failure, which is the counter-intuitive part:

Service D degrades: 50 ms → 5 s (not down, just slow).
Service C calls D with no timeout (or a 30 s one).
C's threads block waiting. At 200 QPS × 5 s, C needs 1,000 concurrent
threads. Its pool is 200 → the pool exhausts.
Now C can't serve requests that DON'T touch D either — total failure.
B calls C, blocks, exhausts. A calls B... the failure climbs the stack.

A hard failure would have been better: fast errors free threads.
Slow failures consume the one resource everyone shares.

Immediate mitigation: open the circuit breaker to D manually (or shed its traffic) so calls fail fast and threads drain; scale D if it's a capacity problem; disable the feature that calls D if there's a flag.

Structural fixes, in order of impact:

1. Timeouts everywhere, derived from the dependency's p99, not round numbers, with a decreasing budget down the chain (gateway 3 s → C 2.5 s → D 2 s) propagated in a header. No timeout is an infinite timeout, and equal timeouts mean inner services keep working for callers who already gave up.

2. Bulkheads — the fix that specifically stops this cascade. Give each dependency its own thread/connection pool. Then D exhausting its pool degrades only D-dependent requests; everything else in C keeps serving. This converts total failure into partial failure, which is the whole game.

3. Circuit breakers so a known-bad dependency fails instantly rather than consuming a timeout's worth of thread time per call.

4. Retry budgets. Check whether retries amplified this — 3× retries against a struggling D triples its load precisely when it's failing. Cap retries at a small fraction of traffic and ensure the breaker counts attempts including retries. Many "it recovered then died again" incidents are retry storms.

5. Load shedding at D. D should reject excess with 429 rather than accepting work it can't complete — a queue that grows without bound converts overload into unbounded latency, which is exactly what poisoned its callers.

6. Question the dependency. Does C genuinely need D synchronously? If it's enriching a response with non-essential data, cache it, make it async, or degrade gracefully.

Then verify with load testing: inject latency into D and confirm the platform degrades partially instead of collapsing. Untested resilience configuration is usually wrong — and this class of incident is why chaos/failure-injection testing exists.

🔴 Senior — A startup with 8 engineers wants to move from a monolith to microservices. Advise them.

I'd start by asking what problem they're solving, because at 8 engineers the answer is usually not one microservices fix.

Reasons that don't justify it: "it's best practice", "we want to scale", "the monolith is messy". A messy monolith becomes messy microservices with network calls between the mess — you export your coupling into the network layer where it's harder to see and impossible for a compiler to check. And "scale" is nearly always solvable with horizontal replicas of the monolith long before 8 engineers hit a real ceiling.

Reasons that would justify it, even at this size: one component with a genuinely different scaling profile (GPU inference, video transcoding) that's expensive to scale as part of the whole; a compliance boundary where isolating card data shrinks PCI scope dramatically; or a component needing a different runtime entirely.

The cost at 8 engineers is severe. They need distributed tracing, centralised logging, service discovery, per-service CI/CD, contract testing, and a local dev story — roughly a platform team's worth of work, from a team that has no platform team. Meanwhile every cross-service refactor becomes a multi-repo versioned migration, and they lose ACID transactions across boundaries. At 8 engineers, coordination cost in one codebase is near zero; they'd be paying the entire tax to solve a problem they don't have.

What I'd recommend instead — a modular monolith:

One deployable, but with enforced internal boundaries:
  - modules by business capability (orders/, inventory/, payments/)
  - each owns its tables; NO cross-module table access
  - modules talk through explicit interfaces, not shared internals
  - enforce it in the build (module boundaries, import linting,
    ArchUnit-style tests) so violations FAIL CI rather than
    accumulating quietly
  - in-process events for cross-module reactions

This gets most of the benefit — clear ownership, decoupled domains, a real path to extraction later — with none of the distribution cost. Crucially, they keep transactions and cheap refactoring at exactly the stage where the domain model is still changing weekly. Boundaries drawn at 8 engineers are usually wrong, and moving a boundary inside a monolith is a refactor while moving one between services is a project.

The trigger to revisit: when teams block each other on deploys, when one module truly needs separate scaling, or around 4+ teams. Then extract the one service that hurts most — strangler-fig style, keeping the monolith as the core — rather than a big-bang decomposition. See Migration Strategies.

And I'd point out that the modular monolith isn't a compromise or a stepping stone you're embarrassed by — for many companies it's the correct final architecture. Shopify and Stack Overflow run enormous monoliths deliberately.

🏋️ Graded Exercises

Exercise 1 (Easy): A request synchronously calls 4 services, each 99.95% available. What's the composite availability, and what would you change?
Solution 
0.9995⁴ = 0.998  →  99.8%  ≈ 17.5 hours of downtime per year

Each dependency alone: 99.95% ≈ 4.4 hours/year.
The composite is 4× worse than any individual part.

What to change: classify each call by whether the response's correctness depends on it. Typically only one or two genuinely do. Moving two of the four to asynchronous events gives 0.9995² = 99.9% (~8.8 h/year), halving the downtime — and the async consumers can be down for hours without any user impact, since work simply queues.

Also worth stating: for the calls that must stay synchronous, add timeouts, circuit breakers and fallbacks so a dependency's slowness doesn't consume your threads. And parallelise them if they're independent, which cuts latency without changing availability.

The general principle: every synchronous call is a decision to share fate. Make it deliberately, not by default.

Exercise 2 (Easy): A team proposes user-api, user-logic, and user-data services. What's wrong, and what would you propose?
Solution

This is splitting by technical layer — the classic distributed monolith. Adding a single field to a user profile requires changes to all three services, three PRs, three deploys, and a coordinated release. Every feature crosses every boundary, so they can never deploy independently — the one benefit microservices offer.

They've taken a monolith's layers, put a network between them, and inherited network latency, partial failure, no transactions, and distributed debugging. Strictly worse than the monolith.

Propose instead: split by business capability, with each service owning its full vertical slice (API → logic → data):

user-profile     (names, avatars, preferences)
authentication   (credentials, sessions, MFA)
notifications    (channels, delivery preferences)

Now a profile change touches one service. Authentication has different security and availability requirements, so isolating it is genuinely valuable and shrinks its audit scope.

The test to apply: look at the last 50 pull requests. If a typical change touches several proposed services, the boundary is wrong. Change coupling in git history is far better evidence than architectural theory — and it's available before you commit to anything.

Exercise 3 (Medium): Design a saga for booking a trip: reserve flight, reserve hotel, charge card. Handle the case where the hotel reservation fails.
Solution 
ORCHESTRATED saga (a Trip Booking coordinator), state machine per trip:

  1. reserve flight   → compensate: cancel flight reservation
  2. reserve hotel    → compensate: cancel hotel reservation
  3. charge card      → compensate: refund
  4. confirm trip, send itinerary

Hotel fails at step 2:
  → run 1' : cancel the flight reservation
  → mark trip FAILED, notify the user with the reason
  (No charge occurred — charging LAST is a deliberate ordering choice.)

Key design decisions and why:

1. Charge last. Money is the hardest thing to compensate — refunds take days to appear, cost fees, and generate support tickets. Ordering the reservations first means the common failure (nothing available) never touches the customer's card. Put irreversible or expensive-to-compensate steps at the end.

2. Use expiring holds, not permanent reservations. Reserve with a 15-minute TTL so that if the coordinator crashes and never compensates, the reservation releases itself. This is the safety net for the case your saga logic can't cover — a crash between steps with no record. Relying solely on compensation means a coordinator failure strands inventory indefinitely.

3. Orchestration over choreography. Three participants with real compensation and a customer who will phone support. A central coordinator makes "where is booking 42?" a database query.

4. Every step idempotent, keyed by saga ID. Steps will be retried after timeouts, and a duplicate "reserve hotel" must not book two rooms. Use the saga ID as the idempotency key at each participant.

5. Persist state before each call. Write "attempting step 2" durably, then call. A crash leaves a resumable state naming exactly what was in flight, rather than an ambiguous one.

The hard cases to name:

• Compensation fails (flight cancellation API down): retry with backoff, then DLQ, then alert a human. Never silently drop — that's a real reservation nobody is using and a customer potentially charged.
• Timeout ambiguity: the hotel call times out but may have succeeded. Don't assume failure — query the hotel by idempotency key to find out, or compensate defensively (cancellation must itself be idempotent and safe when nothing exists).
• Step 3 succeeds but confirmation fails: the customer is charged with no itinerary. The saga must be resumable forward, not just backward — retry the confirmation rather than refunding a valid booking.

Exercise 4 (Medium): Service A calls B with a 30 s timeout, 3 retries, no circuit breaker. B starts failing. Describe what happens over the next 5 minutes.
Solution 
t=0    B degrades. Calls now take 30 s (timeout) instead of 50 ms.

t=0–30s  A's threads block. Each request now occupies a thread 30 s
         instead of 50 ms — a 600× increase in thread-seconds per request.
         At 100 QPS, A needs 3,000 concurrent threads. Its pool is 200.
         → THREAD POOL EXHAUSTED within seconds.

t=30s    Retries begin. Each failed call retries 3× → 4 total attempts
         × 30 s = 120 s per request, AND B now receives 4× its normal
         request rate precisely while it's failing.
         → the retries actively prevent B from recovering.

t=1min   A is fully unresponsive — including for requests that never
         touch B, because the shared thread pool is exhausted. A's
         health checks start failing.

t=2min   A's callers begin timing out and exhausting THEIR pools.
         The failure climbs the dependency graph.

t=3–5min Load balancers pull A out of rotation for failing health checks.
         If B briefly recovers, the backlog of queued retries hits it
         instantly and knocks it over again — the recover-then-die cycle.

Every setting here is wrong:

30 s timeout — should be derived from B's p99, likely 200–500 ms. A 30 s timeout means you'll exhaust your thread pool long before you ever return an error.
3 retries with no budget — quadruples load on a struggling dependency. Cap at 1–2 with jittered backoff and a retry budget (e.g. ≤10% of requests).
No circuit breaker — after N failures, A should fail fast instead of paying 30 s per call. This alone would have contained it.
No bulkhead — this is why A failed entirely rather than just for B-dependent requests. A separate pool for B would have kept the rest of A alive.
No fallback — decide in advance whether to serve a cached value, a default, or a partial response.

Corrected configuration:

timeout: 500 ms (B's p99 + margin)
retries: 1, exponential backoff + jitter, retry budget 10%
breaker: open after 50% failures over a 10 s window, half-open probe at 30 s
bulkhead: dedicated pool of 50 for B
fallback: cached/last-known value, else degraded response omitting B's data

With these, B's failure produces slightly degraded responses from A within 500 ms — and A stays healthy for everything else. Same outage, contained blast radius.

Exercise 5 (Hard): A 40-engineer company has a monolith where deploys take 2 hours and one team's bug blocks everyone. Design the decomposition strategy.
Solution

At 40 engineers with deploy coordination as the stated pain, this is a legitimate case — but the strategy matters more than the destination.

Step 0 — check the cheap fixes first. A 2-hour deploy is often fixable without any decomposition: parallelise the test suite, cut flaky tests, add incremental builds, adopt blue-green/canary deploys. If deploys go from 2 hours to 10 minutes, much of the pain evaporates and they may not need to split at all. I'd insist on this before committing to a multi-year architecture programme — it's weeks of work versus years.

Step 1 — find boundaries from evidence, not theory. Analyse 6–12 months of git history: which directories change together in the same PR? Clusters of change-coupled code are candidate services; code that changes independently is a candidate boundary. Cross-reference with team ownership and with which modules cause the most cross-team blocking.

Step 2 — modularise inside the monolith first. Before extracting anything, enforce module boundaries in the existing codebase: no cross-module table access, communication via explicit interfaces, violations failing CI. This is where you discover your boundaries are wrong — and fixing a boundary inside a monolith is a refactor, whereas fixing it between services is a project. Most of the value arrives here.

Step 3 — strangler fig, one service at a time. Extract the module with the highest pain-to-risk ratio first — typically one that's well-isolated, has its own scaling profile, and blocks a team frequently:

1. Put a facade/routing layer in front of the module's entry points.
2. Build the new service; DUAL WRITE to old and new stores.
3. Shadow traffic: send reads to both, compare results, fix
   discrepancies while the monolith remains authoritative.
4. Flip reads to the new service behind a flag, percentage by percentage.
5. Flip writes. Monolith module becomes a thin proxy.
6. Delete the module. Remove the proxy.

Every step is reversible with a flag, which is what makes this survivable.

Step 4 — build the platform in parallel, and treat it as a real project. Distributed tracing, centralised logging with correlation IDs, service discovery, per-service CI/CD templates, contract testing, and a local dev story. Extracting services without this makes debugging dramatically worse. I'd staff a small platform team explicitly — the most common failure mode is expecting product teams to build this in their spare time.

Sequencing and expectations: extract 3–5 services over the first year, not 20. Keep the monolith as the core indefinitely — "monolith plus a few services" is a perfectly good steady state, and far better than a half-finished decomposition. Set the success metric on the actual pain: deploy frequency per team and cross-team blocking incidents, not service count.

Failure modes to guard against: a big-bang rewrite (never finishes); extracting the easy service instead of the painful one (no benefit, all cost); leaving a shared database behind (all coupling retained); and stopping halfway with two systems to maintain and no clear owner. Write down what "done" means for each extraction before starting it.

Exercise 6 (Hard): Design service boundaries for a food-delivery platform: ordering, restaurants, couriers, payments, tracking, notifications, ratings. Justify each boundary and name what you deliberately keep together.
Solution
ServiceOwnsWhy it's its own boundary
OrderingCart, order lifecycle, order state machineThe transactional core. Changes with menu/pricing rules but has its own team and its own consistency requirements.
Restaurant catalogueRestaurants, menus, hours, availabilityRead-heavy by orders of magnitude (browsing ≫ ordering), rarely written, cacheable at the edge. A completely different scaling profile — the clearest split of all.

PaymentsCharges, refunds, payouts, ledgerCompliance boundary — isolating card handling shrinks PCI scope dramatically. Highest correctness bar; deserves its own release cadence and audit trail.
TrackingLive courier location, ETAEnormous write volume (GPS pings every few seconds), ephemeral data, loss-tolerant. Would otherwise pollute the ordering database with traffic that has completely different durability needs.
NotificationsPush/SMS/email delivery, preferencesPure consumer of events from everyone; no upstream dependencies. Easy, high-value extraction — and it must never be in a synchronous path.
RatingsReviews of restaurants and couriersCompletely independent lifecycle, written long after the order, read on the catalogue path. Low risk, no transactional coupling.

What I'd deliberately keep together — usually the more revealing half of the answer:

• Cart and order in one service. A cart is a pre-order; they share the same data and change together constantly. Splitting them creates a transaction boundary in the middle of checkout for no benefit.
• Pricing, promotions and fees inside Ordering (initially). They're computed at order time from order contents and change together with order rules. A separate pricing service creates a synchronous dependency on the revenue path. Extract later only if a dedicated pricing team emerges.
• Courier assignment stays with dispatch, not in Ordering — but the assignment result is an event Ordering consumes. Don't split the matching algorithm from the courier state it operates on.

Communication design:

SYNCHRONOUS (correctness-critical only):
   Ordering → Payments (authorise)      — can't confirm an unpaid order
   Ordering → Catalogue (validate items/prices at checkout)

ASYNCHRONOUS (events):
   OrderPlaced    → dispatch, notifications, analytics
   OrderDelivered → payments (capture/payout), ratings (invite), analytics
   CourierMoved   → tracking only (high volume, never fans out broadly)

LOCALLY REPLICATED:
   Catalogue data cached by Ordering (menu snapshot ON the order, so a
   menu change never rewrites order history — orders must be immutable
   records of what was actually bought)

Three design points worth calling out:

1. Snapshot menu data onto the order. An order must record the item name and price at purchase time. Referencing the live catalogue means a price change silently rewrites history and breaks reconciliation. This is a general rule for anything financial: store the facts, don't join to mutable state.

2. Tracking is deliberately separate because its data is high-volume, ephemeral and loss-tolerant — losing 30 seconds of GPS pings costs nothing, while losing an order is unacceptable. Mixing those durability requirements in one datastore forces the cheap data onto the expensive infrastructure.

3. The order → delivery flow is a saga (payment authorised → restaurant accepts → courier assigned → delivered → payment captured), orchestrated from Ordering, with compensations for restaurant rejection and courier unavailability. Authorise early, capture late — so a cancellation before delivery voids an authorisation rather than issuing a refund.

🎯 Key Takeaways

  • Microservices solve an organisational problem — team independence — before a technical one. Below ~4 teams the tax exceeds the benefit.
  • Split by business capability, never by technical layer. api/logic/data services make every feature cross every boundary: a distributed monolith.
  • One service, one database. Sharing tables recreates tight coupling with no compiler to catch it.
  • Needing a distributed transaction across a boundary is evidence the boundary is wrong.
  • Use change coupling from git history to find boundaries — what changes together belongs together, and that's real evidence rather than theory.
  • Availability multiplies down synchronous chains: five 99.9% dependencies give 99.5%. Every synchronous call is a decision to share fate.
  • Slow dependencies are worse than dead ones — they consume the thread pool everyone shares. Bulkheads convert total failure into partial failure.
  • Timeout budgets must decrease down the chain and be propagated, or inner services keep working for callers who already gave up.
  • Retries without a budget or breaker cause retry storms that prevent the struggling dependency from recovering.
  • Compensation is not rollback: history is preserved, escaped side effects can't be undone, intermediate states are observable, and compensations can themselves fail.
  • Orchestrate sagas with money or 4+ participants — you need to answer "where is order 42 stuck?" with a query. Use expiring holds so a crashed coordinator can't strand resources.
  • Order saga steps so irreversible ones come last, and prefer authorise-early/capture-late for payments.
  • A modular monolith is a legitimate final architecture, not just a stepping stone — and boundaries drawn too early are usually wrong.
