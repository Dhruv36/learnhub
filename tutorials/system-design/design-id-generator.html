Design Unique ID Generator Case Study

What you'll master: why uniqueness through structure beats uniqueness through coordination, how to derive Snowflake's bit allocation from stated requirements rather than reciting 64 = 41+10+12, why random UUIDs hurt database write throughput (with the B-tree mechanism explained), how to handle clock regression correctly, and what a sequential ID leaks about your business.

Prerequisites: Concurrent Programming, Heartbeat & Gossip (clock assumptions), TinyURL (which leads here). Pairs with Distributed Consensus.

🎯 What this problem is really testing. Whether you understand that coordination is the cost to be eliminated. Any answer involving a central authority handing out numbers has missed the point — the interesting move is partitioning the ID space in advance so no runtime coordination is ever needed. The follow-up (clock skew) then tests whether you know that wall clocks are not monotonic, which is the assumption most implementations get wrong.

1. Requirements

FunctionalNon-functional
Globally unique across all serversNo single point of failure or bottleneck
Roughly time-ordered (sortable by creation)High throughput — 10,000+ IDs/s per node
Fits in 64 bits (a standard integer)Low latency — ID generation must be local, not a network call

The question that decides the design: "does ordering need to be exact, or roughly time-sortable?" Exact global ordering requires a single serialisation point — the very bottleneck we're avoiding. Assume roughly ordered: IDs generated a second apart sort correctly, IDs generated in the same millisecond on different machines may not. That's sufficient for pagination, index locality and "newest first" queries, and it's what makes a coordination-free design possible.

2. Why the Obvious Answers Fail

ApproachWhy it fails here
Database auto-incrementEvery ID request serialises through one database — a throughput ceiling and a single point of failure. If that database is down, nothing in the system can create anything.
UUID v4 (random)Solves uniqueness with zero coordination, but: 128 bits (2× storage on every row and every index and foreign key), and not ordered — which harms write throughput badly (see below).
Central ID serviceJust relocates the bottleneck, and adds a network round trip to every entity creation. Only sensible when combined with range allocation.

Why random UUIDs hurt write throughput — this is the mechanism people cite without being able to explain, and it's worth being precise about:

Databases store rows in a B-tree ordered by primary key.

SEQUENTIAL IDs (auto-increment, Snowflake):
   every insert lands at the RIGHT EDGE of the tree
   → that page is in the buffer pool (it was just used)
   → writes are effectively append-only, page splits are rare
   → high cache hit rate, low write amplification

RANDOM IDs (UUID v4):
   inserts scatter uniformly across the entire index
   → each insert touches a DIFFERENT page, likely not cached
   → a random read from disk BEFORE the write can happen
   → frequent mid-page splits, index fragmentation, more WAL

The gap is largest when the index exceeds RAM — which is exactly
when you have enough data to care. Reported slowdowns of several
times are common on large tables.

WORSE with a clustered index (MySQL InnoDB, SQL Server): the primary
key determines PHYSICAL row order, so random PKs scatter the actual
table data too, not just the index.

3. The Core Idea: Structure Instead of Coordination

Snowflake's insight is that if you partition the ID space up front, two machines can generate IDs simultaneously and forever without ever communicating — because their outputs are structurally incapable of colliding.

64-bit Snowflake ID layout:

 ┌─┬──────────────────────────┬────────────┬──────────────┐
 │0│    41-bit timestamp      │ 10-bit     │  12-bit      │
 │ │   (ms since custom epoch)│ machine ID │  sequence    │
 └─┴──────────────────────────┴────────────┴──────────────┘
  1            41                   10           12         = 64 bits

Two IDs collide only if timestamp AND machine AND sequence all match.
Since machine IDs are unique, and the sequence is a per-machine local
counter within a millisecond, collisions are impossible BY CONSTRUCTION.
No locks, no consensus, no network calls.

Derive the bit allocation rather than memorising it — this is what the question is actually asking:

TIMESTAMP: how many bits for how long?
   2⁴¹ ms = 2.2 × 10¹² ms ≈ 69.7 YEARS
   → 41 bits is chosen to give a working lifetime from a CUSTOM epoch
     (the service's launch date, not 1970 — using the Unix epoch would
     have burned decades of range before the system existed).

MACHINE ID: how many concurrent generators?
   2¹⁰ = 1,024 machines
   → enough for a large fleet; 10 bits is a deliberate trade against
     the sequence bits.

SEQUENCE: how many IDs per millisecond per machine?
   2¹² = 4,096 per ms per machine
   → 4,096 × 1,000 = 4.1 MILLION IDs/second PER MACHINE
   → × 1,024 machines = 4.2 BILLION IDs/second cluster-wide

The allocation is a THREE-WAY TRADE within a fixed 64 bits:
   more timestamp bits → longer lifetime, fewer machines or lower rate
   more machine bits   → bigger fleet, lower per-machine rate
   more sequence bits  → higher burst rate, smaller fleet
Instagram, for example, uses 41/13/10 — more shards, lower per-shard
rate — because their partitioning needs differed.

4. Implementation, With the Parts That Matter

class Snowflake:
    EPOCH        = 1735689600000      # custom epoch (2025-01-01), NOT 1970
    MACHINE_BITS = 10
    SEQ_BITS     = 12
    MAX_MACHINE  = (1 << MACHINE_BITS) - 1     # 1023
    MAX_SEQ      = (1 << SEQ_BITS) - 1         # 4095

    def __init__(self, machine_id):
        if not 0 <= machine_id <= self.MAX_MACHINE:
            raise ValueError("machine_id out of range")
        self.machine_id = machine_id
        self.last_ts    = -1
        self.seq        = 0
        self.lock       = threading.Lock()

    def _now(self):
        return int(time.time() * 1000)

    def next_id(self):
        with self.lock:                       # generation must be atomic
            ts = self._now()

            if ts < self.last_ts:             # CLOCK WENT BACKWARDS
                drift = self.last_ts - ts
                if drift <= 5:                # tiny drift: wait it out
                    time.sleep(drift / 1000.0)
                    ts = self._now()
                else:                         # large regression: REFUSE
                    raise ClockRegression(
                        f"clock moved back {drift}ms; refusing to generate")

            if ts == self.last_ts:            # same millisecond
                self.seq = (self.seq + 1) & self.MAX_SEQ
                if self.seq == 0:             # sequence exhausted
                    ts = self._wait_next_ms(self.last_ts)
            else:
                self.seq = 0                  # new ms: reset

            self.last_ts = ts
            return (((ts - self.EPOCH) << (self.MACHINE_BITS + self.SEQ_BITS))
                    | (self.machine_id << self.SEQ_BITS)
                    | self.seq)

    def _wait_next_ms(self, last):
        ts = self._now()
        while ts <= last:
            ts = self._now()
        return ts
DetailWhy it matters
Custom epochStarting from the service's launch date rather than 1970 recovers decades of the 69-year budget that would otherwise already be spent.
The locknext_id is a read-modify-write on last_ts and seq. Without synchronisation, two threads can produce identical IDs — the exact race from the concurrency lesson.
Sequence exhaustion → waitBusy-waiting for the next millisecond is correct: it preserves uniqueness rather than wrapping and colliding. It only triggers above 4,096 IDs/ms, which is a very high rate.
Refusing on large regressionAvailability is sacrificed for correctness — see below.

5. Deep Dive: Clock Skew, The Real Problem

The entire design rests on time moving forward. It doesn't, reliably:

Wall clocks move BACKWARD in normal operation:
   • NTP correction after drift accumulates
   • VM migration or a snapshot restore
   • leap second handling (some systems step back)
   • an operator setting the clock manually
   • hardware clock instability

If the clock jumps back 100 ms and we keep generating, we reuse
timestamps we have ALREADY USED — with the same machine ID and a
sequence counter that has since reset. That is a COLLISION, not just
a broken sort order. Two different entities get the same ID.
StrategyBehaviourTrade-off
Refuse to generateThrow until the clock catches upCorrect. Chooses a brief outage over duplicate IDs — the right call, since duplicates corrupt data permanently while an outage is recoverable.
Wait it out (small drift)Sleep until the clock passes last_tsFine for a few milliseconds; unusable for a large jump.
Monotonic-only clockTrack your own counter, never letting it decreaseGuarantees uniqueness even under regression. IDs drift from true wall-clock time, but they stay ordered — often the best engineering answer.
Extra bits on regressionBump a generation counter within the IDCosts bits from another field; adds complexity.

Prefer a monotonic internal clock: keep last_ts and never emit a timestamp below it — if the wall clock regresses, hold the previous value and let the sequence absorb requests until real time catches up. That preserves both uniqueness and ordering with no downtime, and it degrades gracefully. Use CLOCK_MONOTONIC for measuring elapsed time and only consult the wall clock for the base offset.

⚠️ The operational rule that follows: never run NTP with large step adjustments on ID-generating nodes — configure slewing (gradually speeding or slowing the clock) rather than stepping. This is a real production requirement, and the kind of infrastructure detail that distinguishes someone who has operated such a system from someone who has read about it.

6. Deep Dive: Assigning Machine IDs

The whole uniqueness guarantee collapses if two machines share a machine ID — so how they're assigned is load-bearing, not an implementation detail:

MethodAssessment
Static config / env varSimple, and fragile: a copy-paste error or a cloned VM image silently duplicates an ID and produces collisions that surface much later as mysterious duplicate-key errors.
ZooKeeper/etcd ephemeral sequential nodeThe robust answer. Each instance claims a unique ID at startup and holds it via a session; the ID is released automatically on death. Coordination happens once at startup, never on the ID path.
Derived from the environmentKubernetes StatefulSet ordinal, or a hash of the pod IP. Convenient, but hash collisions in 10 bits are plausible with a large fleet (birthday bound: ~38 machines for a 50% chance in 1,024 slots), so verify uniqueness.
Database-assigned leaseA row per machine with a heartbeat-renewed lease. Works without a separate coordination service; reclaim IDs whose lease expires.

The subtlety worth raising: reusing a machine ID too quickly after a node dies is dangerous. If the replacement starts with a clock behind the dead node's last-used timestamp, it can regenerate IDs the dead node already issued. Guard by persisting the last-used timestamp per machine ID, or by imposing a cooldown longer than any plausible clock difference before reissuing an ID.

UUID v7 deserves emphasis because the landscape genuinely changed: it puts a millisecond timestamp in the high bits followed by random bits, giving Snowflake's index locality with UUID's zero-coordination property. No machine IDs to assign, no clock-skew collision risk (the random bits absorb it), and native support in Postgres 18, modern MySQL and most languages. If you don't specifically need 64 bits, UUID v7 is usually the better engineering choice today — and saying so demonstrates current knowledge rather than reciting a 2010 design.

8. Deep Dive: What Your IDs Leak

Sequential and time-ordered IDs are information disclosure, which candidates rarely raise unprompted:

1. ENUMERATION. Sequential IDs let anyone walk your data:
      /api/orders/1001, /api/orders/1002, ...
   Combined with a missing authorisation check (IDOR — the most common
   API vulnerability), this is a full data breach.

2. BUSINESS INTELLIGENCE. The "German tank problem": sign up twice a
   month apart, note the two user IDs, and their difference is your
   growth rate. Competitors and journalists have used exactly this to
   publish companies' order volumes.

3. TIMING. A Snowflake ID contains its creation timestamp in plaintext —
   anyone can decode precisely when a record was created, even if your
   API deliberately hides that field.

Mitigations: use Snowflake IDs internally (for index locality and joins) while exposing an opaque external identifier — a UUID v4, or the internal ID encrypted with a format-preserving cipher. That gets you both properties. And regardless: never rely on unguessable IDs as an authorisation mechanism — every endpoint must verify the caller is entitled to the object, because ID obscurity is a defence-in-depth measure, not access control.

Interview Questions

🟢 Beginner — Why not just use a database auto-increment?

Because it forces every ID request through a single point of coordination, which is both a throughput ceiling and a single point of failure.

Throughput: every entity creation across the entire system serialises through one sequence. That caps you at whatever one database can sustain, and you cannot scale past it by adding application servers — they all queue at the same place.

Availability: if that database is unavailable, nothing in the system can create anything. You've coupled every write path in the platform to one component's uptime.

Latency: generating an ID becomes a network round trip, so creating an entity costs at minimum one extra hop before any real work happens.

Sharding makes it worse: with a sharded database there is no single sequence to increment, so you'd need cross-shard coordination for something as basic as a primary key.

The alternatives trade differently: UUID v4 removes coordination entirely but isn't ordered and costs 128 bits; Snowflake keeps 64 bits and rough ordering by partitioning the ID space so each machine generates independently. Range allocation is the middle ground — a server claims 10,000 IDs at a time, so coordination happens once per 10,000 creations rather than once per creation, which is often enough to make an auto-increment-style design viable.

🟢 Beginner — Explain Snowflake's 64-bit layout and why each field is that size. 
1 bit sign (unused) | 41 bits timestamp | 10 bits machine | 12 bits sequence

41-bit timestamp (milliseconds): 2⁴¹ ms ≈ 69.7 years. Measured from a custom epoch — the service's launch date rather than 1970, so none of that budget is spent before the system existed. This field is first so that IDs sort chronologically as plain integers.

10-bit machine ID: 1,024 distinct generators. This is what makes coordination unnecessary — two machines cannot produce the same ID because this segment differs, even if they never communicate.

12-bit sequence: 4,096 IDs per millisecond per machine, for bursts within a single clock tick. It resets when the millisecond advances.

Total capacity: 4,096 × 1,000 = ~4.1 million IDs/second per machine, and ~4.2 billion/s across 1,024 machines.

The key point is that these are a three-way trade within a fixed 64 bits: more machine bits means fewer sequence bits, so a bigger fleet costs per-machine burst rate. Instagram used 41/13/10 — more shards, lower per-shard rate — because their sharding needs differed. Being able to rederive the split from requirements, rather than reciting 41/10/12, is what the question is checking.

The leading bit is unused so the ID stays positive when interpreted as a signed 64-bit integer, which matters in languages (like Java) that lack unsigned types.

🟡 Mid — What happens if the clock moves backwards, and how do you handle it?

It can cause genuine ID collisions, not merely broken ordering — which is why this is the standard follow-up.

Machine generated IDs at t=1000 with sequence 0..500.
NTP corrects the clock back to t=950.
The machine now generates at t=950, sequence starting at 0 —
timestamps it has ALREADY USED, same machine ID, same sequence values.
→ duplicate IDs for different entities.

Clocks move backwards routinely: NTP corrections, VM migration or snapshot restore, leap-second handling, manual changes, and unstable hardware clocks. Treating wall-clock time as monotonic is the core mistake.

Handling, from simplest to best:

1. Refuse to generate until the clock catches up. Correct, and the right instinct — choosing a brief outage over permanent data corruption. But it's an availability hit, and a large jump means a long outage.

2. Wait it out for small drift (a few milliseconds). Fine at that scale, unusable for a large regression.

3. Use a monotonic internal clock — my preferred answer. Track last_ts and never emit a timestamp below it; if the wall clock regresses, keep issuing at last_ts and let the sequence counter absorb requests until real time catches up. Uniqueness and ordering are both preserved with no downtime; the only cost is that IDs briefly drift from true wall-clock time, which is acceptable since we only promised rough ordering.

The operational half of the answer: configure NTP to slew (gradually adjust clock rate) rather than step on ID-generating nodes, so regressions don't happen in the first place. And alert on detected regressions — repeated occurrences indicate a hardware or virtualisation problem worth fixing at the source.

Worth noting: UUID v7 sidesteps this entirely, because its random low bits make a collision vanishingly unlikely even if two IDs share a millisecond after a clock jump.

🟡 Mid — Why do random UUIDs hurt database write performance?

Because databases store rows in a B-tree ordered by primary key, and random keys destroy the locality that makes inserts cheap.

SEQUENTIAL keys: every insert lands at the RIGHT EDGE of the tree.
   → that page was just used, so it's in the buffer pool
   → effectively append-only; page splits are rare
   → high cache hit rate, minimal write amplification

RANDOM keys: inserts scatter uniformly across the whole index.
   → each insert targets a different page, probably not cached
   → the DB must READ that page from disk before writing it
   → frequent mid-page splits → fragmentation → more WAL/redo

The effect scales with data size. While the index fits in RAM, random inserts are only mildly worse. Once it exceeds memory, every insert risks a random disk read, and throughput can drop several-fold — precisely when you have enough data to care.

It's worse with a clustered index (MySQL InnoDB, SQL Server), where the primary key determines the physical row order — so random PKs scatter the table data itself, not just an index. Secondary indexes in InnoDB also store the PK as their pointer, so a 128-bit random key inflates every secondary index too.

Fixes: a time-ordered ID (Snowflake, or UUID v7, which is the same idea standardised at 128 bits). If you're stuck with UUID v4 as an external identifier, keep an internal auto-increment or Snowflake column as the clustered key and put a unique index on the UUID — you get ordered physical storage and an unguessable public ID.

The general principle: write patterns matter as much as read patterns. Choosing a primary key is choosing a physical storage layout.

🔴 Senior — Would you use Snowflake today, or something else?

For most new systems I'd reach for UUID v7 rather than Snowflake, and the reasoning is about operational cost rather than the algorithm.

Snowflake's real cost isn't the algorithm — it's machine-ID management. You need a mechanism to assign 1,024 unique IDs, guarantee no duplicates across deploys and cloned images, reclaim them when nodes die, and avoid reissuing one to a node whose clock is behind. That's a coordination service (ZooKeeper/etcd) plus operational vigilance, and duplicate machine IDs fail silently, surfacing much later as inexplicable duplicate-key errors.

UUID v7 (RFC 9562) puts a millisecond timestamp in the high bits followed by random bits. That gives:

• Time-ordering and therefore index locality — the property that made Snowflake worth having.
• Zero coordination — no machine IDs at all, so an entire class of operational failure disappears.
• Clock-skew tolerance — the random bits make collisions vanishingly unlikely even if two generators share a millisecond.
• Standardisation and native support in Postgres 18, modern MySQL and most languages.

The cost is 128 bits versus 64. That's 8 extra bytes per row, plus every index and every foreign key referencing it. At billions of rows it's real, but it's a storage cost — and storage is usually cheaper than the engineering time to operate machine-ID assignment correctly.

I'd still choose Snowflake when: the ID must fit in 64 bits (a legacy schema, or an extremely large table where 8 bytes per row genuinely matters); throughput is enormous and the compact representation matters for network and memory; or the machine-ID infrastructure already exists and is proven.

The general point: Snowflake was designed in 2010, when there was no standardised time-ordered UUID. UUID v7 exists now specifically to solve this problem without the coordination burden. Recommending the older design without acknowledging that reads as dated — the interesting answer is knowing why the landscape changed.

🔴 Senior — What do your ID choices leak, and how would you design around it?

Ordered IDs are information disclosure, and this is rarely raised unprompted — which makes it a strong differentiator.

1. Enumeration. Sequential IDs let anyone walk your data: /api/orders/1001, 1002, and so on. Combined with a missing authorisation check — IDOR, consistently among the most common API vulnerabilities — this is a complete data breach. The IDs make it trivial rather than merely possible.

2. Business intelligence (the German tank problem). Sign up, note your user ID, sign up again a month later, and the difference is the company's growth rate. The same trick on order IDs reveals transaction volume. This has been used publicly to report companies' revenue figures from nothing but two receipts.

3. Timing metadata. A Snowflake ID contains its creation timestamp in plaintext. Anyone can decode exactly when a record was created — even if your API deliberately omits that field, and even for records they can't otherwise read.

Design around it — use different IDs for different purposes:

INTERNAL:  Snowflake / UUID v7 — ordered, compact, great index
           locality, used for the primary key, joins and sorting.
EXTERNAL:  an opaque identifier exposed in APIs and URLs — either a
           UUID v4 (unguessable, stored in a unique-indexed column) or
           the internal ID encrypted with a format-preserving cipher
           (no extra storage; decryptable back to the internal ID).

You keep write performance AND leak nothing.

The essential caveat: unguessable IDs are defence in depth, never authorisation. Every endpoint must verify the caller is entitled to the object regardless of how obscure the identifier is. Systems that rely on ID obscurity fail the moment one ID leaks — in a log, a referrer header, a shared screenshot, or a support ticket.

Where I'd accept sequential public IDs: when the count is genuinely non-sensitive (a public blog's post IDs) or when ordering is a product feature (invoice numbers, which are often required by law to be sequential). The decision should be explicit rather than accidental — and worth noting that "invoice numbers must be sequential" is exactly the kind of regulatory constraint that overrides the security preference.

Exercise 2 (Easy): Two servers accidentally get the same machine ID. What happens, and how would you detect it?
Solution

What happens: duplicate IDs — the entire uniqueness guarantee is void. Two servers with the same machine ID, generating in the same millisecond, with independently-reset sequence counters, will produce identical IDs.

Server A (machine 5): ts=1000, seq=0 → ID X
Server B (machine 5): ts=1000, seq=0 → ID X   ← same ID, different entity

Why it's insidious: collisions only occur when both servers generate within the same millisecond and their sequences align — so at low traffic it may not happen for days. It surfaces later as sporadic duplicate-key errors, or worse, as silent data corruption where one record overwrites another. The cause is rarely obvious from the symptom, and the damage is already in your data.

Common causes: a cloned VM image or container carrying a baked-in ID; a copy-pasted config; a deployment that scaled beyond the assigned range; or an ID reused too soon after a node died.

Detection:

• Prevent it at the source — assign machine IDs from a coordination service using ephemeral nodes, so a live claim is required and duplicates are impossible by construction.
• Register at startup — each instance writes machine_id → hostname, pid, started_at to a shared store and refuses to start if the ID is already held by a live instance. This is the single most valuable check.
• Monitor distinct hostnames per machine ID; alert on more than one.
• Watch for duplicate-key errors on ID columns — treat any occurrence as a potential machine-ID collision rather than an application bug.

The principle: a silent failure mode with delayed, hard-to-attribute symptoms deserves an explicit startup check, not a runbook entry.

Exercise 3 (Medium): Implement Snowflake with correct handling for sequence exhaustion and clock regression.
Solution 
import threading, time

class ClockRegression(Exception): pass

class Snowflake:
    EPOCH = 1735689600000                  # 2025-01-01, custom epoch
    MACHINE_BITS, SEQ_BITS = 10, 12
    MAX_MACHINE = (1 << MACHINE_BITS) - 1
    MAX_SEQ     = (1 << SEQ_BITS) - 1
    MAX_DRIFT_MS = 5                       # tolerate tiny drift by waiting

    def __init__(self, machine_id):
        assert 0 <= machine_id <= self.MAX_MACHINE
        self.machine_id = machine_id
        self.last_ts = -1
        self.seq = 0
        self.lock = threading.Lock()       # generation is read-modify-write

    def _now(self): return int(time.time() * 1000)

    def next_id(self):
        with self.lock:
            ts = self._now()

            # --- CLOCK REGRESSION ---
            if ts < self.last_ts:
                drift = self.last_ts - ts
                if drift <= self.MAX_DRIFT_MS:
                    while ts < self.last_ts:        # wait it out
                        ts = self._now()
                else:
                    # Monotonic fallback: never emit a smaller timestamp.
                    # Uniqueness preserved; IDs briefly lead wall-clock time.
                    ts = self.last_ts

            # --- SEQUENCE ---
            if ts == self.last_ts:
                self.seq = (self.seq + 1) & self.MAX_SEQ
                if self.seq == 0:                   # EXHAUSTED this ms
                    while ts <= self.last_ts:       # spin to the next ms
                        ts = self._now()
            else:
                self.seq = 0

            self.last_ts = ts
            return (((ts - self.EPOCH) << (self.MACHINE_BITS + self.SEQ_BITS))
                    | (self.machine_id << self.SEQ_BITS)
                    | self.seq)


def demo():
    gen = Snowflake(machine_id=1)
    # Uniqueness under concurrency is the invariant that matters.
    ids, lock = [], threading.Lock()
    def worker():
        local = [gen.next_id() for _ in range(2000)]
        with lock: ids.extend(local)
    threads = [threading.Thread(target=worker) for _ in range(8)]
    [t.start() for t in threads]; [t.join() for t in threads]

    assert len(ids) == len(set(ids)), "DUPLICATE IDS GENERATED"
    assert all(i > 0 for i in ids), "IDs must be positive"
    print(f"ok — {len(ids)} unique IDs, monotonic within thread")

if __name__ == "__main__":
    demo()

The three correctness points:

1. The lock is mandatory. next_id reads and writes last_ts and seq — without synchronisation, two threads interleave and emit identical IDs. The demo() asserts exactly this invariant, because it's the one that silently breaks.

2. Sequence exhaustion spins rather than wraps. Wrapping past 4,095 within the same millisecond would reuse sequence values and collide. Blocking until the next millisecond is correct, and only occurs above 4.1M IDs/s per machine.

3. Clock regression uses the monotonic fallback for large jumps rather than throwing: holding last_ts preserves uniqueness and ordering with no downtime. For small drift, waiting is simpler and keeps IDs aligned with wall-clock time.

In production I'd also register the machine ID at startup against a coordination service, and emit a metric whenever regression is detected — repeated occurrences point at an infrastructure problem worth fixing at the source.

Exercise 4 (Medium): You need 100,000 IDs/second on a 5-machine fleet, and IDs must fit in 64 bits. Allocate the bits and justify it.
Solution 
Requirement: 100,000 IDs/s total, 5 machines
   → 20,000 IDs/s per machine = 20 per millisecond per machine
   With headroom for uneven distribution and bursts, target ~256/ms.

Bit allocation (63 usable bits after the sign bit):
   SEQUENCE: 2⁸ = 256 IDs/ms per machine → 256,000/s per machine
             comfortably above the 20,000/s requirement
   MACHINE:  2⁴ = 16 machines → 3x headroom over 5. Or 2⁵ = 32 for
             more room to grow the fleet.
   TIMESTAMP: 63 - 8 - 5 = 50 bits
             2⁵⁰ ms ≈ 35,700 YEARS — absurdly generous.

REBALANCE — spend the surplus timestamp budget usefully:
   TIMESTAMP 41 bits (69.7 years — still ample)
   MACHINE   10 bits (1,024 machines — room for 200x fleet growth)
   SEQUENCE  12 bits (4,096/ms = 4.1M/s per machine)

...which is standard Snowflake. The requirement is met with enormous
headroom, so there is no reason to deviate.

The lesson from doing the arithmetic: 100,000 IDs/s sounds substantial but is ~0.002% of standard Snowflake's capacity. The bit allocation is not the constraint at this scale, so I'd use the standard layout rather than a bespoke one — a custom split saves nothing and costs interoperability with existing tooling and libraries.

When you would deviate: if the fleet needed more than 1,024 generators (take bits from the sequence, as Instagram did with 13 machine bits), or if a single machine needed more than 4,096 IDs/ms (take bits from the machine field). The 64 bits are a budget, and you spend them against the dimension that's actually binding.

And I'd question the premise: if the 64-bit constraint is inherited from a legacy schema rather than a real requirement, UUID v7 removes machine-ID management entirely for 8 extra bytes per row — likely a better trade at only 5 machines, where the operational overhead of coordination infrastructure is proportionally largest.

Exercise 5 (Hard): Your ID generator is embedded in application servers that autoscale from 10 to 500 instances. Design machine-ID assignment.
Solution

Autoscaling breaks static assignment — instances appear and disappear continuously, so IDs must be claimed and released dynamically without ever being held by two live instances.

Design: ephemeral nodes in a coordination service.

On startup:
  1. Connect to ZooKeeper/etcd and create an EPHEMERAL SEQUENTIAL node
     under /snowflake/machines/ → receives a unique index, e.g. 0..1023
  2. Derive machine_id from that index.
  3. Maintain the session with heartbeats.

On death (crash, scale-in, network partition):
  the session expires and the node is DELETED AUTOMATICALLY —
  the ID returns to the pool with no cleanup code to get wrong.

Key property: coordination happens ONCE at startup, never on the
ID-generation path. Generation stays purely local.

The dangerous edge case — ID reuse after death:

Instance A holds machine_id 7, generates IDs up to ts=5000, then dies.
Instance B starts, claims the now-free machine_id 7.
If B's clock reads 4900 (skew of 100 ms), it generates IDs with
timestamps A ALREADY USED → collisions.

Mitigations, in order:

1. Persist the last-used timestamp per machine ID (written periodically to the coordination service). A claiming instance reads it and refuses to start until its own clock exceeds that value. This is the correct fix, and it's cheap — a write every few seconds.
2. Cooldown before reissue — hold a released ID for longer than any plausible clock difference (say 30 s). Simpler, weaker.
3. Session timeout longer than the maximum clock skew, so an ID cannot be reclaimed faster than skew could matter.

Failure handling: if the coordination service is unavailable at startup, the instance must refuse to start rather than guessing an ID — a duplicate machine ID corrupts data permanently, whereas a failed startup is visible and recoverable. If the session drops while running, stop generating IDs and attempt to re-acquire; continuing risks another instance having claimed your ID.

Scale check: 500 instances against 1,024 slots is tight — churn means released IDs must be reclaimed promptly. I'd rebalance to 13 machine bits (8,192 slots, 512 sequence per ms) for headroom.

The honest alternative: at this level of churn, machine-ID management is most of the complexity in the system. UUID v7 eliminates it entirely — no coordination service, no reuse hazard, no startup dependency. Unless 64 bits is a hard constraint, that's the better answer for an autoscaling fleet, and saying so is stronger than building elaborate machinery to preserve a design choice that no longer pays for itself.

Exercise 6 (Hard): Your public API exposes sequential order IDs. A competitor is tracking your order volume. Fix it without breaking existing integrations.
Solution

The attack (the German tank problem): place two orders a month apart, note the IDs, and the difference is your monthly order volume. It requires no access beyond being a customer, and it has been used publicly to estimate companies' revenue.

The constraint that shapes the answer: existing integrations depend on current IDs, so the fix must be additive — this is an expand/contract migration.

Phase 1 — introduce an opaque public ID alongside the existing one.

orders: id BIGINT PK,                    -- internal, unchanged, ordered
        public_id VARCHAR(24) UNIQUE,     -- new, opaque

Two options for public_id:
  a) Random (UUID v4 / 22-char base62) — unguessable, needs storage
     and an index.
  b) Format-preserving encryption of the internal ID — no extra
     storage, deterministic, and reversible with the key, so
     support tooling can map back easily.

I'd choose (b) for a numeric-looking ID, or (a) for simplicity.
Backfill all existing rows.

Phase 2 — return both. Responses include id (existing) and public_id; API endpoints accept either form. Nothing breaks.

Phase 3 — migrate consumers. Document the new field, instrument which integrations still send the sequential ID, and contact those specific customers with usage data. Per the API lesson, instrumentation is what makes the migration decidable rather than a guess.

Phase 4 — contract. When sequential-ID usage reaches zero and stays there through a full business cycle, stop returning it — behind a kill switch, rolled out gradually.

Important caveats:

• Other fields leak too. If the API exposes created_at alongside a sequential ID, or any other monotonic counter (invoice numbers, ticket numbers), the same inference works. Audit the whole response, not just the ID.
• This isn't authorisation. Opaque IDs make enumeration impractical, but every endpoint must still verify entitlement — otherwise you've swapped an easy attack for a slightly harder one.
• Keep the internal ID sequential. It's the clustered primary key and provides the index locality discussed earlier; only the exposed identifier needs to be opaque. That separation is the whole point.
• Check for regulatory constraints — invoice numbers are often legally required to be sequential, so the mitigation there is different (expose the opaque order ID, keep the invoice number for accounting documents only).

🎯 Key Takeaways

  • Uniqueness through structure, not coordination — partition the ID space up front so machines never need to communicate.
  • Derive the bit allocation from requirements: 41 bits ≈ 69 years, 10 bits = 1,024 machines, 12 bits = 4,096 IDs/ms. It's a three-way trade within a fixed 64 bits.
  • Use a custom epoch at the service's launch date — the Unix epoch wastes decades of the timestamp budget.
  • Random UUIDs hurt writes because inserts scatter across the B-tree, causing page splits and cache misses — worst once the index exceeds RAM.
  • Clocks move backwards routinely. A regression causes real collisions, not just bad ordering. Use a monotonic internal clock, and configure NTP to slew rather than step.
  • Machine-ID assignment is the operational cost of Snowflake — use ephemeral coordination nodes, and never reissue an ID without checking the last-used timestamp.
  • UUID v7 is often the better modern default: time-ordered like Snowflake, zero coordination like UUID v4, standardised — for 8 extra bytes per row.
  • Ordered IDs leak information — enumeration, growth rates, and creation timestamps. Use ordered IDs internally and opaque identifiers externally.
  • Unguessable IDs are never authorisation. Verify entitlement on every request regardless.
  • Don't shard by a time-ordered ID — the property that gives index locality also concentrates every new write on one shard.
