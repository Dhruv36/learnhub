Design Key-Value Store (Dynamo) Case Study

What you'll master: the synthesis case study — how consistent hashing, quorums, vector clocks, anti-entropy and LSM storage compose into one coherent system. You'll be able to derive the N/W/R trade-off rather than quoting it, explain why sloppy quorums break the R+W>N guarantee people assume, trace a vector-clock conflict to its resolution, and justify an LSM tree over a B-tree from the write pattern.

Prerequisites: Consistent Hashing, CAP Theorem, Replication, Bloom Filters & Merkle Trees. This lesson assumes all four.

🎯 What this problem is really testing. Whether the fundamentals compose in your head. Every component here is covered elsewhere in the track; the signal is whether you can assemble them, justify each choice against the stated requirement (always writable), and identify where the standard answers have subtleties — particularly that a sloppy quorum does not give you the consistency that R+W>N implies.

1. Requirements

The requirement that drives everything is "always writable." Rejecting an add-to-cart because a replica is unreachable costs a sale, whereas briefly showing a slightly stale cart costs nothing. That's an explicit AP choice from CAP, and every subsequent decision — leaderless writes, quorums, vector clocks, hinted handoff — follows from it. If the requirement were "never oversell inventory", the correct design would be entirely different.

3. Partitioning and Replica Placement

Consistent hashing with virtual nodes, exactly as in that lesson — but the replica placement detail is where designs go wrong:

A key's PREFERENCE LIST = walk clockwise from hash(key), collecting
the first N nodes.

THE BUG: with virtual nodes, consecutive ring positions often belong
to the SAME physical node. Naively taking "the next 3 vnodes" can give
you 3 copies on 1 machine — you believe you have RF=3 and you have 1.
It is invisible until that machine dies.

CORRECT: skip vnodes whose physical node is already in the list.
BETTER:  also skip nodes in a failure domain already represented, so
         the 3 replicas land in 3 different racks/AZs. Three copies in
         one rack all die together in one power event.

Virtual nodes also matter for recovery: without them, a dead node's entire range lands on one successor, which may then also fall over. With ~150 vnodes per node, the load scatters across the whole cluster, and a replacement node rebuilds by streaming from many peers in parallel rather than serially from one.

4. The Core Design Decision: Quorums (N, W, R)

N = replication factor        (copies of each key)
W = write quorum              (acks required before a write succeeds)
R = read quorum               (replicas consulted on a read)

If R + W > N, the read and write sets MUST overlap on at least one
node — so a read is guaranteed to see the most recent acknowledged
write.
Config (N=3)PropertyUse for
W=2, R=2R+W=4>3 — overlap guaranteed; tolerates 1 node down for both reads and writesThe balanced default
W=1, R=1Fastest and most available; reads may be staleShopping cart adds, view counters, session data — "always writable" wins
W=3, R=1Fast reads, slow writes; writes fail if any replica is downRead-heavy, rarely-written config — but note the availability trap
W=1, R=3Fast writes, slow readsWrite-heavy ingestion where reads are rare
⚠️ The subtlety that most answers miss: R+W>N gives you recency, not linearizability. Quorum overlap guarantees a read touches a replica holding the latest acknowledged write. It does not order two concurrent writes — with no leader, two clients writing simultaneously both succeed, and you get siblings (or, under last-write-wins, silent data loss). It also doesn't make a partial write atomic: a write acked by 2 of 3 that then fails leaves a value some later read may or may not see, and there is no rollback. Quorums give recency; consensus gives ordering — and if you need the latter, you need Paxos/Raft and roughly 4× the latency.

5. Deep Dive: Sloppy Quorums and Hinted Handoff

Strict quorums would violate "always writable" — if 2 of a key's 3 replicas are unreachable, a W=2 write fails. Dynamo's answer changes the guarantee in a way worth understanding precisely:

SLOPPY QUORUM: if a preference-list node is unreachable, write to the
next healthy node on the ring instead, tagged with a HINT naming the
intended recipient.

   Key's preference list: [A, B, C].  B is down.
   Write goes to A, C, and D — where D stores it with
   "hint: this belongs to B".
   When B recovers, D hands the data off and deletes its copy.

   → the write SUCCEEDS during the failure. Always writable. ✓

What it costs, and this is the part to state: during a sloppy write, the data is not on the nodes a reader will consult. A subsequent R=2 read of [A, B, C] may reach A and C — fine here — but in a worse case reads the two nodes that never received it. So R+W>N no longer guarantees overlap. The guarantee degrades from "reads see the latest write" to "reads see it eventually, once handoff completes." Sloppy quorums buy availability by weakening exactly the property strict quorums provide, and many candidates cite R+W>N without realising their design has already forfeited it.

Hinted handoff's failure mode: if the node holding hints dies before delivering them, those writes are lost from the intended replica until anti-entropy repairs them from another copy. Hints are a fast path, not a durability guarantee — which is why anti-entropy remains necessary rather than optional.

6. Deep Dive: Vector Clocks and Conflict Resolution

With no leader, two clients can write the same key concurrently on different replicas. Someone must decide what happened — and the first job is detecting whether there's a genuine conflict at all.

A vector clock is a set of (node, counter) pairs recording which
replicas have seen which versions.

   put("cart") on A     → v1: [milk]            vc {A:1}
   put on A (+bread)    → v2: [milk, bread]     vc {A:2}
                          {A:2} DESCENDS from {A:1} → v2 supersedes v1.
                          No conflict; discard v1.

   PARTITION: client 1 writes via A, client 2 via B, both from v1.
   A: [milk, bread]   vc {A:2}
   B: [milk, butter]  vc {A:1, B:1}

   Compare: is {A:2} ≥ {A:1,B:1} in every position?  A:2≥1 ✓ but B:0<1 ✗
            is {A:1,B:1} ≥ {A:2}?                    A:1<2 ✗
   NEITHER descends from the other → GENUINE CONCURRENT WRITE.
   → return BOTH siblings to the client.

   Client merges (a cart is a set — union is the natural semantic):
   [milk, bread, butter]  vc {A:2, B:1}   ← descends from both
Resolution strategyBehaviourCost
Last-write-winsHighest timestamp survivesTrivial, and silently discards a concurrent write. Also depends on synchronised clocks — skew can make an older write win permanently. Cassandra's default.
Vector clocks + app mergeDetect true concurrency; hand siblings to the applicationNo silent loss, but the app must know how to merge. Vector clocks also grow with the number of writing nodes (Dynamo truncates the oldest entries, which can produce false conflicts).
CRDTsData types that merge deterministically by constructionNo conflict handling needed at all — but only for operations fitting the algebra, and they carry metadata (tombstones).

Why a shopping cart is the canonical example: its merge is a set union, which is commutative, associative and idempotent — so merging is unambiguous. The famous consequence is that a deleted item can reappear, because an "add" from one replica merges with a "remove" from another and the add wins. Amazon accepted that deliberately: a resurrected item is an annoyance, a lost sale is revenue. Naming that trade — and that it was a business decision, not a technical accident — is the strongest thing you can say about this design.

7. Deep Dive: The Storage Engine (LSM vs B-tree)

Each node needs local storage, and the choice follows directly from the write pattern:

B-tree (traditional RDBMS) 
Writes update pages IN PLACE.
→ random I/O per write
→ page splits, fragmentation
→ read: O(log n), usually
  one seek — EXCELLENT

Good when reads dominate and
writes are moderate.
LSM tree (Dynamo, Cassandra) 
Writes go to an in-memory
memtable + append-only WAL.
Flushed to immutable SSTables;
merged by compaction.

→ writes are SEQUENTIAL — very
  fast, no random I/O
→ reads may check several
  SSTables — slower

Good when writes dominate.
Why LSM here: the design accepts writes even during failures ("always
writable"), so write throughput is the priority. Sequential appends
also suit both SSDs and spinning disks far better than random updates.

The read cost is mitigated by exactly the structures from the
fundamentals:
   BLOOM FILTER per SSTable → "definitely not in this file", skipping
      disk seeks for files that can't contain the key. A false positive
      costs one wasted seek; a false NEGATIVE would return wrong data,
      which is why the guarantee direction matters.
   Sparse index + block cache for the files that remain.

The real cost of LSM is COMPACTION: background merging of SSTables
consumes I/O and CPU, and competes with live traffic. "Compaction
storms" are the classic Cassandra operational problem, and the reason
these systems need I/O headroom rather than running near capacity.

8. Failure Handling: The Full Picture

Membership changesGossipO(log n) propagation with no coordinator — see Heartbeat & Gossip

The tombstone trap, which is the operational hazard specific to this architecture: deletes are stored as tombstones (a delete has to be replicated like any other write, or a replica that missed it would resurrect the row). Tombstones are garbage-collected after a grace period — and if anti-entropy hasn't run within that window, a replica that never saw the delete still holds the row, sees the other replicas lacking it, and "repairs" by copying the deleted data back. That's why repair frequency must be tied to the tombstone grace period as a hard operational rule, not a recommendation.

Interview Questions

🟢 Beginner — Explain N, W and R, and what R+W>N buys you.

N is the replication factor — how many copies of each key exist. W is the write quorum — how many replicas must acknowledge before a write is considered successful. R is the read quorum — how many replicas are consulted on a read.

R+W>N guarantees the read and write sets overlap on at least one node. With N=3, W=2, R=2: a write is on at least 2 nodes and a read consults 2 of 3, so by pigeonhole at least one node in the read set holds the latest write. Version numbers then identify which returned value is newest.

N=3, W=2, R=2 → 4 > 3 → overlap; tolerates one node down. The default.
N=3, W=1, R=1 → 2 ≤ 3 → no overlap; fastest and most available,
                        reads may be stale.
N=3, W=3, R=1 → overlap, but the write fails if ANY replica is down.

The important caveat is that this gives recency, not linearizability. Overlap ensures a read observes the most recent acknowledged write; it says nothing about ordering two writes that happen concurrently, and it doesn't make a partially-completed write atomic. For genuine ordering you need consensus, at roughly 4× the latency.

Note also that W=N is usually a mistake: requiring every replica makes writes less available than a single node, because any one failure blocks them.

🟢 Beginner — Why does this design use consistent hashing rather than hash(key) % N?

Because the requirement is incremental scalability — adding or removing one node at a time — and modulo hashing makes that catastrophic.

With hash(key) % N, changing N changes the mapping for essentially every key: going from 10 nodes to 11 remaps ~90% of the keyspace. In a storage system that means physically moving 90% of the data while serving traffic — effectively impossible.

Consistent hashing remaps only ~1/N of keys, and crucially those keys all come from a single neighbour on the ring, so exactly one node streams data to the joining node while the rest of the cluster is untouched.

Virtual nodes matter for two further reasons here. First, random placement of a few physical nodes produces very uneven ring arcs — one node could own 40% of the keyspace. With ~150 vnodes each, distribution smooths to within a few percent. Second, and more important for a storage system, when a node dies its ranges scatter across all surviving nodes rather than dumping entirely on one successor — so recovery load is shared, and a replacement rebuilds by streaming from many peers in parallel.

The ring also gives replica placement naturally: the preference list is simply the next N distinct physical nodes clockwise, so replication falls out of the partitioning scheme rather than needing separate machinery.

🟡 Mid — What is a sloppy quorum, and what does it cost?

A strict quorum requires W acknowledgements from the key's actual preference list. If enough of those nodes are unreachable, the write fails — which directly contradicts the "always writable" requirement.

A sloppy quorum instead accepts acknowledgements from the first W healthy nodes on the ring, even if they aren't the designated replicas. The substitute stores the data with a hint naming the intended owner and hands it off when that node recovers.

Preference list [A, B, C]; B is down.
Write goes to A, C and D, where D holds it tagged "belongs to B".
The write SUCCEEDS. Availability preserved. ✓

The cost is that R+W>N no longer guarantees overlap. The data now lives partly on a node that no reader will consult, so a subsequent read of the preference list can miss it entirely. The guarantee degrades from "a read sees the latest acknowledged write" to "a read sees it eventually, once handoff completes."

That's the subtlety worth naming: many designs cite R+W>N as their consistency argument while also enabling sloppy quorums, without noticing the two are in tension. It's a deliberate trade — availability now, consistency shortly — but it should be stated rather than assumed away.

A second failure mode: hinted handoff is not durable. If D dies before delivering its hints, those writes never reach B and are recoverable only from A or C via anti-entropy. Hints are a fast path, which is exactly why background repair remains necessary.

🟡 Mid — Trace a vector clock conflict and explain how it's resolved. 
Start: put("cart") via node A → v1: [milk], vc {A:1}

Network partition. Two clients write concurrently from v1:
  via A:  [milk, bread]    vc {A:2}
  via B:  [milk, butter]   vc {A:1, B:1}

Partition heals. Compare the clocks:
  Does {A:2} dominate {A:1,B:1}?   A: 2≥1 ✓   B: 0≥1 ✗   → no
  Does {A:1,B:1} dominate {A:2}?   A: 1≥2 ✗              → no
  Neither descends from the other → GENUINE CONCURRENT WRITE.

Detection is the vector clock's job; resolution is not. The store returns both siblings to the client, because only the application knows the semantics of the data.

For a shopping cart the merge is a set union: [milk, bread, butter] with clock {A:2, B:1}, which now descends from both siblings so the conflict is closed. Union works because it's commutative, associative and idempotent — order of merging doesn't matter.

The famous consequence: an item deleted on one replica can reappear, because the "add" sibling merges with the "remove" sibling and the add wins. Amazon accepted that deliberately — a resurrected item is an annoyance a customer can fix, while a lost item is a lost sale. That it was a business decision, not an oversight, is the point of the example.

Contrast with last-write-wins: LWW would keep whichever write had the later timestamp and silently discard the other, so one customer's addition simply vanishes. It's one line of code versus sibling handling, and it also depends on synchronised clocks — skew can make an older write win permanently.

The practical caveat: vector clocks grow with the number of nodes that write a key. Dynamo truncates the oldest entries, which can produce false conflicts (siblings reported for writes that were actually ordered) — safe, since a false conflict causes an unnecessary merge rather than data loss.

🔴 Senior — Justify the storage engine choice, and name its operational cost.

An LSM tree, because the design is write-optimised by requirement — it accepts writes even during failures, so write throughput is the priority.

The mechanism: writes go to an in-memory memtable plus an append-only write-ahead log — sequential I/O, no seeks. The memtable is periodically flushed to an immutable SSTable, and background compaction merges SSTables to reclaim space and bound read cost.

B-tree:  in-place page updates → RANDOM I/O per write, page splits,
         fragmentation. Reads are excellent (one seek, O(log n)).
LSM:     append-only → SEQUENTIAL writes, far higher throughput.
         Reads may consult several SSTables → slower.

Read cost is mitigated by a Bloom filter per SSTable answering "definitely not here", which eliminates disk seeks for files that cannot contain the key — plus a sparse index and block cache for those that remain. Note the guarantee direction matters: a false positive costs one wasted seek, whereas a false negative would return wrong data.

The operational cost is compaction, and it's the thing that actually bites in production:

• It consumes I/O and CPU continuously, competing with live traffic — so you must provision headroom and throttle it, rather than running near capacity.
• Write amplification: a value may be rewritten several times as it moves through compaction levels, so the disk sees multiples of your logical write volume.
• "Compaction storms" — a burst of compaction saturating I/O and spiking read latency — are the classic Cassandra incident.
• Strategy matters: size-tiered compaction favours writes but leaves more SSTables to read; levelled compaction favours reads at higher write amplification. That choice should follow the workload, and getting it wrong is a common source of unexplained latency.

The framing: LSM trades predictable background work for much higher write throughput. That's the right trade when writes dominate and you can afford I/O headroom — and the wrong one for a read-dominated workload on constrained hardware, where a B-tree's simplicity wins.

🔴 Senior — When is this architecture the wrong choice?

It's a specialised design that buys availability at real cost, so it's wrong whenever those costs aren't worth paying:

1. When you need transactions across keys. There are none. An operation touching two keys atomically — transferring money, decrementing inventory while creating an order — cannot be expressed. You would need sagas and compensation, which is far more application complexity than a relational database transaction.

2. When queries aren't key lookups. No joins, no range scans, no ad-hoc filtering. "Find all orders over £100 last week" requires either a full scan or a separately maintained index. If the access patterns aren't known up front and stable, this is the wrong model.

3. When correctness beats availability. The AP choice means accepting stale reads and concurrent-write conflicts. For inventory decrements, account balances or uniqueness constraints, that's unacceptable — you want linearizability, which means consensus.

4. When the application can't merge conflicts. The design pushes resolution to the application. A shopping cart merges naturally by union; a bank balance does not — "£100 and £150 concurrently" has no sensible merge. If your data lacks a natural merge semantic, you're choosing between silent LWW loss and unresolvable siblings.

5. When the scale doesn't justify it. This is genuinely the most common case. A single Postgres instance with replicas handles workloads far larger than most people assume, and it gives you transactions, joins, indexes and strong consistency for free. Adopting a Dynamo-style store at moderate scale means paying all the operational cost — compaction tuning, repair scheduling, tombstone management, conflict resolution — for capacity you don't need.

What I'd say in an interview: this architecture is right for high-volume, key-addressable, availability-critical workloads where the application can tolerate eventual consistency and resolve conflicts meaningfully — session stores, shopping carts, user preferences, activity feeds, time-series ingestion. Reaching for it by default is over-engineering, and recognising that is more valuable than reciting the design.

🏋️ Graded Exercises

Exercise 1 (Easy): With N=5, list every (W,R) pair satisfying R+W>N, and pick one for a write-heavy log and one for a read-heavy config store.
Solution 
R+W > 5 requires R+W ≥ 6:
   W=1,R=5   W=2,R=4   W=3,R=3   W=4,R=2   W=5,R=1
   (and any larger combination)

Write-heavy log → W=1, R=5. Writes ack from a single replica, so ingestion is fast and stays available while up to 4 nodes are down. The rare read pays the cost. In practice a log might drop the overlap requirement entirely (W=1, R=1), since stale reads of log data are usually harmless.

Read-heavy config store → W=4, R=2. Config changes are rare, so expensive writes are acceptable; reads happen constantly and must be fast.

Why not W=5, R=1 — the tempting answer? Requiring all five replicas means any single node being down blocks all writes. That's the coupling trap from the replication lesson: requiring all of N multiplies failure probability, so W=N makes writes less available than a single node. W=4 keeps fast reads while tolerating one failure.

The general rule: put the cost on the rarer operation, then check the failure tolerance you've implicitly chosen. Every quorum choice is simultaneously a latency decision and an availability decision.

Exercise 2 (Easy): A key's preference list is computed by taking the next 3 vnodes clockwise. Why is that a bug?
Solution

Because consecutive vnodes frequently belong to the same physical node. With 10 machines × 150 vnodes each, the next three positions on the ring are quite likely to include two or three vnodes from one machine.

Intended: RF=3 → three copies on three machines.
Reality:  three vnodes might map to  [node-7, node-7, node-3]
          → only TWO physical copies
          or worse: [node-7, node-7, node-7] → ONE copy.

You believe you can survive two failures. You cannot survive one.
And it is completely invisible until that machine dies.

The fix is to walk clockwise while skipping vnodes whose physical node is already in the preference list — the "preference list" construction from the Dynamo paper — so you collect N distinct machines rather than N ring positions.

The stronger fix extends this to failure domains: skip nodes in a rack or availability zone already represented, so the three replicas land in three independent failure domains. Three copies in one rack all die together in a single power or switch failure, which is the correlated-failure problem from estimation — independent-failure maths gives beautiful availability numbers that reality doesn't honour.

This also constrains your replication factor: RF=3 across only 2 AZs is unsatisfiable if you require one replica per AZ, so topology and RF have to be chosen together.

Exercise 3 (Medium): Implement vector clock comparison — returning BEFORE, AFTER, EQUAL or CONCURRENT.
Solution 
def compare(vc1, vc2):
    """Compare two vector clocks: dicts of {node_id: counter}.
    Returns 'BEFORE', 'AFTER', 'EQUAL', or 'CONCURRENT'."""
    # A dominates B if A[n] >= B[n] for EVERY node n present in either.
    nodes = set(vc1) | set(vc2)
    vc1_greater = False        # vc1 exceeds vc2 somewhere
    vc2_greater = False        # vc2 exceeds vc1 somewhere

    for n in nodes:
        a, b = vc1.get(n, 0), vc2.get(n, 0)
        if a > b: vc1_greater = True
        if b > a: vc2_greater = True

    if vc1_greater and vc2_greater: return 'CONCURRENT'   # genuine conflict
    if vc1_greater:                 return 'AFTER'        # vc1 descends
    if vc2_greater:                 return 'BEFORE'       # vc2 descends
    return 'EQUAL'


def merge(vc1, vc2):
    """Clock for a value merged from both: element-wise maximum."""
    return {n: max(vc1.get(n, 0), vc2.get(n, 0)) for n in set(vc1) | set(vc2)}


def demo():
    assert compare({'A': 2}, {'A': 1}) == 'AFTER'
    assert compare({'A': 1}, {'A': 2}) == 'BEFORE'
    assert compare({'A': 1}, {'A': 1}) == 'EQUAL'
    # The case that matters: neither dominates → true concurrency
    assert compare({'A': 2}, {'A': 1, 'B': 1}) == 'CONCURRENT'
    # A missing node counts as 0, not as "unknown"
    assert compare({'A': 1, 'B': 1}, {'A': 1}) == 'AFTER'
    assert merge({'A': 2}, {'A': 1, 'B': 1}) == {'A': 2, 'B': 1}
    print("ok — vector clock comparison")

if __name__ == "__main__":
    demo()

The key insight in the algorithm: track both directions of dominance in one pass. If each clock exceeds the other at some node, neither descends from the other — that is the definition of concurrency, and it's exactly the case that must produce siblings rather than a silent overwrite.

Treating a missing node as 0 is deliberate: a node absent from a clock has simply never written that key, which is equivalent to counter 0. Getting this wrong (treating absence as "unknown" and bailing out) makes the comparison report false conflicts everywhere.

The merge is element-wise maximum, producing a clock that dominates both inputs — so once the application merges the values, the resulting version supersedes both siblings and the conflict is resolved rather than perpetuated.

In production you'd also bound clock size: Dynamo truncates the oldest (node, counter) entries past a limit, accepting occasional false conflicts — safe, because a false conflict causes an unnecessary merge rather than data loss.

Exercise 4 (Medium): A node is down for 3 hours. Trace exactly how it catches up when it returns.
Solution

Three mechanisms operate at different timescales, and they're complementary rather than redundant:

1. Hinted handoff — the fast path (seconds to minutes). While the node was down, writes destined for it went to substitute nodes tagged with hints. On recovery, gossip propagates that the node is back, and hint-holders replay the stored writes to it. This recovers the majority of missed data quickly and cheaply.

Limitation: hints are usually capped by time and volume — after several hours, hint-holders stop accumulating them (otherwise a long outage would exhaust their disks). At 3 hours, some hints may already have been dropped, which is precisely why the next mechanism exists.

2. Read repair — opportunistic (immediate, for hot data). As reads arrive, a quorum read that returns mismatched versions triggers a write-back of the newest value to the stale replica. Keys that are actually being read get repaired essentially for free, on the hot path — so the data users care about converges first.

Limitation: it only fixes keys that happen to be read. Cold data stays stale indefinitely.

3. Anti-entropy — the backstop (scheduled, hours). Merkle-tree comparison per token range finds every remaining difference in O(log n) hash exchanges and streams only the differing blocks. This is the mechanism that guarantees eventual convergence for data nobody reads.

Exchange root hashes per token range → equal? done (O(1)).
Differ → descend, pruning matching subtrees → transfer only the
differing blocks. Full repair is expensive (it reads all data),
so it runs on a rolling, throttled schedule.

The critical operational constraint: repair must complete within the tombstone grace period. If the returning node missed a DELETE and the tombstone is garbage-collected elsewhere before repair runs, anti-entropy sees the row present on one replica and absent on others — and "repairs" by copying the deleted data back into existence. Deleted records resurrect. This is why Cassandra ties repair frequency to gc_grace_seconds as a hard rule rather than a recommendation.

One more consideration: if the node was down long enough to have diverged nearly everywhere, a Merkle diff visits almost every node and costs more than simply bootstrapping it from scratch. The operational decision rule is repair when differences are few, rebuild when they're many.

Exercise 5 (Hard): Design the shopping cart on top of this store. Handle the "deleted item reappears" problem.
Solution

The naive model causes the problem. If the cart is stored as a set of items and merged by union, then a remove on one replica concurrent with any write on another loses to the union — the removed item comes back.

Replica A: cart = {milk, eggs}      user removes eggs → {milk}
Replica B: cart = {milk, eggs}      user adds bread     → {milk, eggs, bread}
Merge (union):                      {milk, eggs, bread}
→ "eggs" is back. The removal was silently undone.

Fix: model the cart as an OR-Set (observed-remove set) — store adds and removes as separate facts with unique tags, rather than storing a set of current members:

adds:    {(milk, tag1), (eggs, tag2), (bread, tag4)}
removes: {tag2}                       ← removes reference the TAG it observed

current = adds whose tags are not in removes = {milk, bread}   ✓

Now the merge is a union of both sets, which is still commutative and associative, but a remove persists because it names the specific add it cancelled. Eggs stays removed.

The residual case, stated honestly: if a user removes eggs on one device while adding eggs on another concurrently, the new add has a different tag that no remove references — so eggs remains in the cart. That's arguably correct (the user did add it), and it's the OR-Set's documented bias: concurrent add wins over remove. Every CRDT has such a bias, and knowing yours is part of choosing it.

Quantity, which the set model ignores: for "2 × milk", use a PN-Counter per item (a per-replica pair of increment and decrement counters, merged by taking the max of each) rather than a single number, since a plain integer has no meaningful merge.

Practical additions:

• Garbage-collect tombstones — removed tags accumulate forever otherwise. Prune them once all replicas have observed the remove (or at checkout, when the cart is emptied anyway).
• Set N=3, W=1, R=2 — "always writable" is the requirement, so an add must never be rejected; reads consult two replicas to catch most divergence.
• Validate at checkout, not in the cart. Stock availability and pricing are checked when the order is placed, against a linearizable store. The cart can be eventually consistent precisely because it is not the system of record — that separation is what makes the whole AP design acceptable.

Exercise 6 (Hard): Your cluster reports 99.9% availability, but one customer's writes fail regularly. Diagnose.
Solution

Aggregate availability hiding a localised failure — the cluster average is dominated by customers whose keys are healthy, so a subset failing entirely barely moves the number. The clue is that it's one customer, meaning their keys share something.

Candidate causes, in order:

1. Their keys map to a degraded preference list. If two of the three nodes owning their key range are down or overloaded, a W=2 write fails for those keys only. Everyone else is fine. Check: compute the preference list for the failing keys and inspect the health of exactly those nodes. This is the most likely cause and the easiest to miss, because node-level dashboards look mostly green.

2. A hot partition. If this customer is large and their data concentrates on one partition — a wide partition, or a key with a low-cardinality prefix — that node saturates and times out under load while the rest of the cluster idles. Check: per-node request rates and partition sizes. Fix: add a bucketing component to the key so their data spreads.

3. Wide partitions causing timeouts. One partition holding millions of values makes reads and compactions on it slow enough to breach timeouts. This is a schema problem, not a capacity problem — adding nodes won't help, because the partition stays whole.

4. Correlated placement. If their replicas landed in one rack or AZ (the preference-list bug from Exercise 2), a single domain failure takes out all copies of their data while cluster-wide availability barely registers it.

5. Their quorum settings differ — a stricter W for this tenant, or a client library configured with W=N, which fails whenever any replica is down.

The measurement lesson, which is the real point: cluster-wide availability is the wrong SLI. Per the observability lesson, aggregate metrics average away localised failure. You need availability measured per tenant and per token range, because "99.9% overall" and "one customer at 60%" are simultaneously true — and only the second one generates support tickets. I'd add per-tenant success-rate alerting as the durable fix, independent of whichever cause turns out to be responsible today.

🎯 Key Takeaways

  • "Always writable" is the requirement that drives everything — the AP choice makes leaderless writes, quorums, vector clocks and hinted handoff all follow.
  • R+W>N gives recency, not linearizability. Concurrent writes remain unordered and partial writes have no rollback.
  • Sloppy quorums break the R+W>N guarantee by placing data outside the preference list — available now, consistent after handoff.
  • Replica placement must skip duplicate physical nodes and failure domains, or "RF=3" silently becomes one copy on one machine.
  • Vector clocks detect concurrency; they don't resolve it. Resolution belongs to the application, because only it knows the merge semantics.
  • Last-write-wins silently discards data and trusts synchronised clocks — acceptable only where losing a concurrent write is genuinely fine.
  • The reappearing-item trade was a business decision: a resurrected item costs less than a lost sale. Name the bias of whatever CRDT you choose.
  • LSM trees suit write-heavy stores (sequential appends), with Bloom filters mitigating the read cost — and compaction as the ongoing operational tax.
  • Hinted handoff is a fast path, not durability. Anti-entropy is the guarantee.
  • Repair must run inside the tombstone grace period, or deleted data is resurrected by the repair process itself.
  • Aggregate availability hides per-tenant failure — measure per tenant and per token range.
  • This is the wrong store for transactions, joins, or correctness-critical data — and usually over-engineering below very large scale.
