Distributed Consensus (Raft, Quorums) Senior / Staff

What you'll master: why majority quorums prevent split brain (the overlap argument, which is the single most reusable idea here), how Raft elects leaders and commits entries, the safety properties that make it correct, why reads are surprisingly harder than writes, how membership changes avoid creating two disjoint majorities, and — most importantly — when consensus is the wrong tool.

Prerequisites: Replication & Failover (split brain, fencing), CAP (quorums give recency, consensus gives ordering), Heartbeat & Gossip (failure detection). Referenced by Key-Value Store and ID Generator.

🎯 What this topic is really testing. Two things. First, whether you understand why majority — not that Raft uses it, but that any two majorities of the same set must share a node, which is what makes split brain impossible. Second, whether you know consensus is expensive and know when to avoid it: every write costs a round trip to a majority, and adding nodes makes it slower. Candidates who propose Raft for everything have learned the mechanism without the cost.

1. The Problem, and Why It's Genuinely Hard

CONSENSUS: get N unreliable machines, on an unreliable network, to
agree on ONE value — and to keep agreeing as machines fail and
recover.

Why it's hard: you cannot distinguish "slow" from "dead" (the
failure-detection limit from the heartbeat lesson). So a node that
looks dead may be alive and still acting.

THE FLP IMPOSSIBILITY RESULT (1985):
   In a fully asynchronous network with even ONE faulty process,
   no deterministic algorithm can GUARANTEE consensus in bounded
   time.

Real systems sidestep this with PARTIAL SYNCHRONY: assume messages
usually arrive within some bound. Under that assumption Raft always
maintains SAFETY (never wrong) and usually maintains LIVENESS (makes
progress) — sacrificing progress, never correctness, when the network
misbehaves.

The safety/liveness distinction is the key framing: Raft never returns a wrong answer, but it may return no answer during a partition. That's the CP choice from CAP, made explicit — a minority partition halts rather than risking divergence.

2. Why Majority: The Overlap Argument

This is the most reusable idea in the lesson, and it's worth being able to state precisely:

A quorum is any set of more than N/2 nodes.

THE PROPERTY: any two majorities of the same N MUST share at least
one node.

   N = 5, majority = 3
   Quorum A = {1, 2, 3}
   Quorum B = {3, 4, 5}
                ↑ they overlap at node 3 — and they always must.

WHY, by pigeonhole: two disjoint sets of size 3 would need 6 distinct
nodes, but only 5 exist. Two majorities cannot be disjoint.

WHAT IT BUYS: two different groups can never both believe they hold a
valid majority, because the shared node can only vote once per term.
That single fact is what makes split brain impossible in the
ELECTION path.
Cluster sizeMajorityFailures tolerated

220 — same as one node, at double the cost
321
431 — same as three, at higher latency
532
743

Always use odd numbers. Even sizes buy nothing: a 4-node cluster tolerates one failure exactly like a 3-node one, while requiring an extra acknowledgement on every write. And a 2-node cluster is the worst case — it tolerates zero failures for writes, exactly like a single node, but adds a partition mode a single node doesn't have.

💡 The same overlap principle, three places in this track. Raft's majority quorums overlap so two leaders can't be elected. Dynamo's R+W>N makes read and write sets overlap so a read sees the latest write. And a Raft leader elected by a majority is guaranteed to have every committed entry, because the committing majority and the electing majority must share a node. One mathematical idea, reapplied — and recognising it as one idea rather than three techniques is exactly the connection staff interviews look for.

3. Raft: Leader Election

Three roles: LEADER (handles all writes), FOLLOWER (replicates,
votes), CANDIDATE (a follower seeking election).

Time is divided into TERMS — a logical clock, incremented on each
election. Each term has at most one leader.

ELECTION:
   1. A follower's election timeout expires (no heartbeat received).
   2. It increments its term, becomes a CANDIDATE, votes for itself,
      and requests votes from all peers.
   3. Each node grants at most ONE vote per term, and only to a
      candidate whose log is at least as up to date as its own.
   4. A majority of votes → the candidate becomes leader and starts
      sending heartbeats, which suppress further elections.

SPLIT VOTES: if several nodes become candidates simultaneously, none
may win. Raft fixes this with RANDOMISED election timeouts (e.g.
150-300 ms) so one node reliably times out first — the same jitter
principle that solves thundering herds elsewhere in this track.

The "log at least as up to date" rule is a safety property, not an optimisation. It guarantees a node missing committed entries can never win an election — which combined with the overlap argument means every new leader already contains every committed entry. That's how Raft avoids needing to reconcile divergent logs after a failover.

4. Raft: Log Replication and Commitment

1. Client sends a write to the leader.
2. Leader APPENDS it to its own log (uncommitted).
3. Leader sends AppendEntries to all followers, in parallel.
4. When a MAJORITY have persisted the entry, it is COMMITTED.
5. Leader applies it to its state machine and responds to the client.
6. Followers learn of the commit on the next AppendEntries and apply
   it to their own state machines.

   term:   1   1   2   2   2
   index:  1   2   3   4   5
   leader [a] [b] [c] [d] [e]     ← committed through index 4
   f1     [a] [b] [c] [d]
   f2     [a] [b] [c] [d] [e]
   f3     [a] [b]                 ← lagging, will be caught up
   f4     [a] [b] [x]             ← CONFLICTING entry from an old term

Index 4 is committed: leader + f1 + f2 = 3 of 5 = majority.
f4's [x] will be OVERWRITTEN — the leader's log is authoritative,
and consistency is restored by the leader forcing followers to match.
Safety propertyGuarantee
Election safetyAt most one leader per term — enforced by one-vote-per-node and majority
Leader append-onlyA leader never overwrites or deletes its own entries
Log matchingIf two logs share an entry at the same index and term, all preceding entries are identical
Leader completenessA new leader contains every committed entry — the property that makes failover safe
State machine safetyNo two nodes ever apply different commands at the same log index

5. Deep Dive: Why Reads Are Harder Than Writes

This is the subtlety most people miss, and it's a strong senior discriminator:

❌ "Just read from the leader" 
The leader may not KNOW it has
been deposed.

A network partition isolates it;
the majority elects a new leader
and commits new entries. The old
leader has received no message
telling it otherwise — it still
believes it leads.

It serves a STALE read, with
full confidence. Linearizability
is violated.
✅ Confirm leadership first 
Options:

1. QUORUM READ — contact a
   majority to confirm you are
   still leader. Correct, but
   costs a round trip per read.

2. LEASE — the leader holds a
   time-bounded lease renewed by
   heartbeats; within it, local
   reads are safe. Fast, but
   assumes bounded clock drift.

3. READ INDEX — confirm the
   commit index with a majority
   once, then serve several
   reads. Amortises the cost.

The general point: in a consensus system, writes are safe by construction because they require a majority. Reads from a single node are not, because that node's belief about its own role may be stale. Any system offering "linearizable reads" is doing one of the three things above, and knowing which tells you its latency and clock assumptions.

Follower reads are cheaper still but only give you stale reads — acceptable for many workloads, and a deliberate choice worth offering per query rather than per system, exactly as with tunable consistency.

6. Deep Dive: Membership Changes

Changing the cluster's node set is the operation most likely to break a consensus system, because it can momentarily create two disjoint majorities:

❌ NAIVE: switch every node from config {A,B,C} to {A,B,C,D,E} at once.
   Nodes switch at different times, so briefly:
      A, B still believe the cluster is {A,B,C} → majority = 2
      C, D, E believe it is {A,B,C,D,E}        → majority = 3

   {A,B} can elect a leader under the old config.
   {C,D,E} can elect a leader under the new config.
   TWO LEADERS, both legitimately believing they hold a majority.
   The overlap guarantee is broken because they are majorities of
   DIFFERENT SETS.

✅ JOINT CONSENSUS (Raft's solution):
   transition through a combined configuration C_old,new in which
   decisions require a majority of BOTH the old AND new sets.
   No decision can be made by either set alone, so no two disjoint
   majorities can exist at any instant.

✅ SINGLE-SERVER CHANGES (simpler, used in practice):
   add or remove ONE node at a time. With one change, old and new
   majorities always overlap, so joint consensus isn't needed.

The operational rule: never change more than one member at a time unless the implementation explicitly supports joint consensus. "Replace three nodes" means three sequential single-node changes, each allowed to complete — and this is a genuinely common source of production incidents in etcd and similar systems.

7. Deep Dive: When NOT to Use Consensus

Consensus is expensive, and its cost profile is unusual — it gets worse as you add nodes:

CostDetail
Latency per writeA round trip to a majority. Same-DC ~1–2 ms; cross-region 100 ms+
Throughput ceilingAll writes go through one leader — typically low tens of thousands/s. Does not scale horizontally
Scaling backwardsMore voters means slower commits. 7 nodes is slower than 3, and beyond 7 the durability gain rarely justifies the latency
AvailabilityA minority partition halts entirely — correct, but it is downtime
USE CONSENSUS FOR:
   leader election · cluster membership · configuration
   distributed locks with fencing tokens · shard assignment
   → small, slow-changing, correctness-critical metadata

DO NOT USE IT FOR:
   bulk data storage (use replication with quorum reads instead)
   high-throughput writes (partition; run consensus PER SHARD)
   anything tolerating eventual consistency

THE STANDARD ARCHITECTURE:
   a small Raft group (3-5 nodes) holds the AUTHORITATIVE metadata,
   while the data plane scales independently with cheaper replication.
   Kubernetes does exactly this — etcd is a small Raft cluster; the
   pods are not.

And for per-shard scaling: systems like CockroachDB and Spanner run an independent Raft group per shard, so consensus latency is paid per shard rather than globally, and total write throughput scales with shard count. That's how consensus-backed systems achieve horizontal scale despite consensus itself not scaling.

Interview Questions

🟢 Beginner — Why does consensus require a majority rather than any two nodes?

Because any two majorities of the same set must overlap, and that overlap is what makes split brain impossible.

N = 5, majority = 3
   Quorum A = {1,2,3}    Quorum B = {3,4,5}
   They share node 3 — and they always must.

By pigeonhole: two disjoint 3-node sets would need 6 nodes, and only
5 exist. Two majorities cannot be disjoint.

What that buys: two different groups can never both believe they hold a valid majority, because the shared node votes only once per term. So two leaders cannot be elected simultaneously.

Why "any two nodes" fails: with N=5, {1,2} and {3,4} are both size two and completely disjoint. Both could elect a leader, both could accept writes, and the cluster diverges with no way to reconcile.

The same overlap property also guarantees leader completeness: an entry committed by one majority, and a leader elected by another majority, must share a node — so the new leader necessarily has that entry. That's why failover in Raft doesn't require merging divergent logs.

Practical corollary: always use odd cluster sizes. Four nodes tolerate one failure exactly like three, while requiring an extra acknowledgement on every write — strictly worse.

🟢 Beginner — Walk through Raft leader election.

Raft divides time into terms, a logical clock incremented at each election, with at most one leader per term. Nodes are leader, follower, or candidate.

1. A follower stops receiving heartbeats and its election timeout
   expires.
2. It increments its term, becomes a CANDIDATE, votes for itself,
   and sends RequestVote to all peers.
3. Each peer grants at most ONE vote per term, and only if the
   candidate's log is at least as up to date as its own.
4. A majority of votes → leader. It immediately sends heartbeats,
   which suppress other elections.
5. If no one wins (a split vote), the term ends and a new election
   begins.

Randomised election timeouts (typically 150–300 ms) are what prevent repeated split votes: if every node used the same timeout, they'd all become candidates simultaneously, split the vote, and repeat indefinitely. Randomising means one node reliably times out first — the same jitter principle that solves retry storms and cache stampedes elsewhere in this track.

The log-completeness check in step 3 is a safety property, not an optimisation. A node missing committed entries can never win, so combined with quorum overlap, every new leader is guaranteed to already contain every committed entry. That's why Raft never needs to reconcile divergent logs after a failover — a nice property that Paxos variants achieve with more difficulty.

🟡 Mid — A 5-node cluster partitions 3–2. What happens on each side? 
MAJORITY SIDE (3 nodes)
   3 > 5/2, so it holds a quorum.
   - if it has the leader, that leader continues normally
   - if not, it elects a new one within an election timeout
   → FULLY OPERATIONAL: accepts writes, commits with 3 of 3 locally
     (still a majority of 5)

MINORITY SIDE (2 nodes)
   2 is not a majority of 5.
   - cannot elect a leader (never reaches 3 votes)
   - if it CONTAINS the old leader, that leader cannot commit
     anything, because it can't reach a majority
   → HALTS for writes. Correct behaviour: refusing beats diverging.

The subtlety worth raising: if the old leader is on the minority side, it doesn't immediately know it's deposed. Until its own lease or election timeout expires, it may still believe it leads — and if it serves reads locally, those reads are stale. It cannot commit writes (no majority), so safety holds for writes, but linearizable reads require confirming leadership with a quorum or holding a valid lease.

When the partition heals: the old leader sees a higher term number from the new leader, immediately steps down to follower, and any uncommitted entries in its log are overwritten by the authoritative leader's log. No manual reconciliation.

The CAP framing: this is the CP choice made concrete. Raft sacrifices availability on the minority side to guarantee it never diverges. Clients connected to the minority experience an outage — which is correct for a coordination system, and exactly why you wouldn't use consensus for a shopping cart.

🟡 Mid — Why can't you just read from the Raft leader?

Because the leader may not know it has been deposed. If a partition isolates it, the majority elects a new leader and commits new entries — and the old leader receives no message telling it so. It will happily serve reads from its now-stale state with full confidence.

Writes are safe by construction (they require a majority acknowledgement, which the isolated leader can't get). Reads have no such natural check, which is why they're the harder case.

Three solutions, with different trade-offs:

1. Quorum read. Contact a majority to confirm you're still leader before serving. Correct, and costs a round trip on every read — expensive for a read-heavy workload.

2. Leader lease. The leader holds a time-bounded lease renewed by heartbeats; within it, local reads are safe because no other leader can have been elected. Fast, but it assumes bounded clock drift — a wall-clock jump or a long pause breaks the guarantee, which is the same weakness as leases in split-brain prevention.

3. Read index. Confirm the current commit index with a majority once, then serve multiple reads against it. Amortises the round trip across many reads — the usual production choice.

And the cheap option worth offering: follower reads serve from any replica with no coordination at all, giving stale but fast results. Whether that's acceptable is a per-query decision, not a per-system one — the same tunable-consistency thinking as R+W>N.

The general lesson: in consensus systems, safety is asymmetric between reads and writes, and any product claiming "linearizable reads" is doing one of the above — knowing which tells you its latency profile and clock assumptions.

🔴 Senior — Why are membership changes dangerous, and how does Raft handle them?

Because a naive change can create two disjoint majorities — breaking the one property the entire protocol depends on.

Changing {A,B,C} → {A,B,C,D,E} all at once. Nodes adopt the new
config at different moments, so there is an instant where:

   A, B still think the cluster is {A,B,C}   → majority = 2
   C, D, E think it is {A,B,C,D,E}           → majority = 3

   {A,B} elects a leader under the OLD config.
   {C,D,E} elects a leader under the NEW config.

Two leaders, each holding a legitimate majority — of DIFFERENT SETS.
The overlap guarantee never applied across different configurations.

Raft's solution — joint consensus. Transition through an intermediate configuration C_old,new in which any decision requires a majority of both the old and new member sets. Since neither set can decide alone, no two disjoint majorities can exist at any instant. Once the joint configuration is committed, the cluster moves to C_new.

The simpler approach used in practice: single-server changes. Add or remove exactly one node at a time. With a change of one, the old and new majorities are guaranteed to overlap (e.g. going 3→4, old majority is 2 and new is 3, and any 2-subset and 3-subset of 4 nodes must share a member), so joint consensus isn't needed.

The operational rule, and a real source of incidents: never change more than one member at a time. "Replace all three nodes" means three sequential single-node changes, each allowed to fully complete. Operators doing bulk replacements — during a migration or a cloud instance-type change — is a recognised way to break etcd clusters.

A related hazard: removing a node that is currently the leader. Best practice is to transfer leadership first, then remove, so the cluster doesn't have to run an election while simultaneously processing a configuration change.

🔴 Senior — When would you deliberately avoid consensus?

Whenever the cost isn't justified — and the cost is substantial, with an unusual shape: consensus gets slower as you add nodes.

The costs:

• Latency: every write requires a round trip to a majority — 1–2 ms same-DC, 100 ms+ across regions.
• Throughput: all writes funnel through one leader, typically capping at low tens of thousands per second. It does not scale horizontally.
• Negative scaling: a 7-node group commits more slowly than a 3-node one, because more acknowledgements are required. You add nodes for durability and pay in latency.
• Availability: a minority partition halts entirely — correct, but it is downtime.

So use it only for small, slow-changing, correctness-critical state: leader election, cluster membership, configuration, shard assignment, distributed locks with fencing tokens.

Avoid it for:

• Bulk data storage — use replication with quorum reads instead, which gives recency without full ordering.
• High-throughput writes — partition the data and run an independent consensus group per shard, which is how CockroachDB and Spanner scale.
• Anything tolerating eventual consistency — a shopping cart, a feed, a session store. The AP designs in this track exist precisely because consensus would be the wrong trade.

The standard architecture separates the two: a small Raft group (3–5 nodes) holds authoritative metadata, while the data plane scales independently with cheaper replication. Kubernetes is the canonical example — etcd is a small Raft cluster; the workloads it coordinates are not.

The framing I'd give: consensus buys you agreement, which is expensive. Most systems need it for a tiny fraction of their state, and treating it as a general-purpose storage layer is the most common way to build something needlessly slow.

🏋️ Graded Exercises

Exercise 1 (Easy): How many failures can clusters of 3, 4, 5 and 6 nodes tolerate? What does that tell you?
Solution 
N    majority   failures tolerated
3       2              1
4       3              1     ← same as 3, but slower
5       3              2
6       4              2     ← same as 5, but slower

Failures tolerated = floor((N-1)/2)

What it tells you: always use odd numbers. An even-sized cluster tolerates exactly as many failures as the odd size below it, while requiring an additional acknowledgement on every write — so it's strictly worse on latency for identical fault tolerance.

The worst case is N=2: majority is 2, so it tolerates zero failures for writes — identical to a single node — while costing twice as much and introducing a partition mode a single node doesn't have. It is the one configuration that is unambiguously a mistake.

Choosing between 3, 5 and 7: 3 is the common default (tolerates one failure, lowest latency). 5 is worth it when you need to survive two simultaneous failures — for instance, tolerating one planned maintenance and one unplanned failure. Beyond 7, the extra acknowledgements cost more latency than the marginal durability is worth.

The deployment corollary: spread the nodes across failure domains. Three nodes in one rack tolerate one node failure but zero rack failures.

Exercise 2 (Easy): Why does Raft randomise election timeouts?
Solution

To prevent repeated split votes. Without randomisation, all followers would detect the leader's absence at nearly the same moment, all become candidates simultaneously, and all request votes at once.

With identical timeouts:
   t=0    leader dies
   t=150  ALL followers time out together → all become candidates
          → each votes for itself, nobody reaches a majority
   t=300  all time out again → same outcome
   → the cluster can fail to elect a leader for many rounds,
     remaining unavailable the whole time.

With randomised timeouts (150-300 ms):
   one node reliably times out first, requests votes while others are
   still followers, and wins immediately.

Why a vote split doesn't resolve itself: each node votes at most once per term, and votes for itself as a candidate. With all nodes as candidates, no votes are available for anyone else. The term ends with no leader and the process repeats.

The general principle, which recurs throughout this track: whenever independent actors share a schedule, randomise it. The same fix applies to retry storms after an outage, cache TTLs expiring together, reconnection storms in WebSocket tiers, and quiet-hour notification releases. Synchronisation among independent actors is almost always a bug, and jitter is almost always the cure.

Exercise 3 (Medium): A client sends a write; the leader commits it to a majority then crashes before responding. What should the client do?
Solution

The write succeeded, but the client doesn't know that — the classic ambiguous outcome. It must retry, and the system must make retrying safe.

What actually happened:
   - the entry was committed (a majority persisted it)
   - the new leader, by leader completeness, HAS that entry
   - the write is durable and will be applied

What the client saw: a timeout. Indistinguishable from
   - the leader crashing BEFORE committing, or
   - the request never arriving at all.

The client must retry, because not retrying risks losing a write that never happened. But a blind retry risks applying the operation twice.

The fix is idempotency, and it belongs in the protocol:

Each client attaches a unique request ID, stable across retries.
The state machine records applied request IDs.
On retry:
   ID already applied → return the ORIGINAL result, don't re-apply
   ID not seen        → apply normally

Note this must live in the REPLICATED STATE MACHINE, not in the
leader's memory — otherwise a new leader wouldn't know the request
was already applied.

That last point is the design insight: the deduplication state must itself be replicated through the consensus log, or it doesn't survive the very failure it exists to handle.

Bound the dedup table with a session or time window, since retaining every request ID forever is unbounded growth — the same trade as idempotency-key expiry in API design.

The generalisation: distributed systems cannot avoid ambiguous outcomes; they can only make retrying safe. This is exactly the at-least-once-plus-idempotency pattern from message delivery, appearing again at the consensus layer.

Exercise 4 (Medium): Compare Raft's majority quorum with Dynamo's R+W>N. Same idea or different?
Solution

The same mathematical idea — overlapping sets — applied to different architectures with different guarantees.

Raft (majority)Dynamo (R+W>N)
Overlap betweenAny two majorities (elections, commits)The read set and the write set
GuaranteesOne leader per term; a new leader has every committed entryA read observes the most recent acknowledged write
ProvidesTotal ordering — a single replicated logRecency only — no ordering of concurrent writes
Concurrent writesImpossible — one leader serialises everythingBoth succeed; produces siblings or LWW loss
CostA majority round trip per write, single-leader throughputTunable per operation; no leader bottleneck

The shared insight: if any two sets you care about must intersect, then at least one node witnesses both operations — so information cannot be lost between them. Raft applies it across elections and commits; Dynamo applies it across reads and writes.

The crucial difference: Raft gives ordering; Dynamo does not. Quorum overlap guarantees a Dynamo read sees a recent write, but says nothing about ordering two writes that happen concurrently — which is why Dynamo needs vector clocks or last-write-wins, and Raft needs neither. As stated in the CAP lesson: quorums give recency, consensus gives ordering, and you pay for ordering.

Which to choose: Raft when you need a single authoritative sequence (leader election, config, ordered logs). Dynamo-style quorums when you need availability and horizontal write scale, and can resolve conflicts at the application level.

Exercise 5 (Hard): You need 500,000 writes/s with strong consistency. Raft caps around 20,000. Design around it.
Solution

A single Raft group cannot do this, and adding nodes makes it worse — more voters means more acknowledgements per commit, so a 7-node group is slower than a 3-node one. Consensus does not scale vertically or by adding replicas.

The answer: partition, and run an independent consensus group per shard.

500,000 writes/s ÷ 20,000 per group = 25 groups minimum
   with headroom for skew and growth: 50-100 shards

Each shard = its own Raft group of 3-5 nodes, with its own leader,
its own log, and its own commit path. They never coordinate.

   shard 1: Raft group {A,B,C}   leader A
   shard 2: Raft group {B,C,D}   leader B     ← leaders spread
   shard 3: Raft group {C,D,E}   leader C        across nodes
   ...

Total write throughput now scales LINEARLY with shard count, while
each individual write still gets full consensus guarantees.

This is exactly how CockroachDB and Spanner work — Spanner calls the units "Paxos groups", CockroachDB calls them "ranges", and both place multiple groups per physical node so leadership is balanced.

What you give up, and it's significant:

• Cross-shard transactions now require two-phase commit across Raft groups — slower, and it reintroduces the availability coupling that all-of-N creates.
• Strong consistency is per shard, not global. Reading from two shards gives you two consistent snapshots taken at different instants, unless you add a global timestamp mechanism (Spanner's TrueTime) at real cost.
• Shard key choice becomes critical — a hot shard caps at 20,000/s regardless of how many other shards are idle.

The question I'd ask first, though: does all of this data need strong consistency? 500,000 writes/s of strongly-consistent data is unusual. Often the honest answer is that a small fraction needs it (balances, inventory) and the rest tolerates eventual consistency — in which case a small Raft group for the critical state plus a cheaper replicated store for the bulk is simpler and faster than 100 consensus groups. Questioning the requirement is frequently better value than engineering to meet it.

Exercise 6 (Hard): Design a distributed lock with consensus. Why isn't the lock alone sufficient?
Solution

The lock service itself is straightforward — a Raft-backed key-value store with compare-and-set and TTLs:

ACQUIRE:  CAS(lock_key, expected=empty, new={owner, expiry})
             success → you hold it
             failure → someone else does
RENEW:    while working, extend the expiry via CAS
RELEASE:  CAS(lock_key, expected={you}, new=empty)
TTL:      if the holder dies, the lock expires automatically —
          essential, or a crash strands it forever.

Why that isn't sufficient — the pause problem:

1. Client A acquires the lock.
2. A is paused (GC, VM migration) for 40 s.
3. A's lease expires. Client B legitimately acquires the lock.
4. B does its work.
5. A WAKES UP, still believing it holds the lock, and writes.

A never did anything wrong — it checked, and it held the lock when it
checked. But there is an unavoidable window between "verify I hold
the lock" and "perform the write", and a process can be suspended for
arbitrarily long inside it.

No amount of checking closes this. A paused process cannot police
itself.

The fix is fencing tokens — the same mechanism as in split-brain prevention:

Each successful acquisition returns a MONOTONICALLY INCREASING token:
   A acquires → token 33
   B acquires → token 34

Every write to the protected resource carries its token, and the
RESOURCE rejects any token lower than the highest it has seen:

   B writes with 34 → accepted, resource records highest = 34
   A wakes, writes with 33 → 33 < 34 → REJECTED

A learns it is deposed from the rejection itself. No clock
assumptions, no cooperation from A required.

The critical requirement: the resource must participate. A lock service alone cannot make this safe — the storage layer, filesystem or API being protected must check the token. This is why distributed locks are frequently described as "advisory": without resource-side fencing they express intent, not exclusion.

The general principle, which appears repeatedly in this track: push the safety check to the resource being protected, never to the actor. The same reasoning gives us fencing tokens for leaders, idempotency keys at payment providers, and audience validation in JWTs.

🎯 Key Takeaways

  • Majority quorums work because any two majorities must overlap — that single fact makes split brain impossible in elections.
  • Always odd cluster sizes. 4 tolerates the same failures as 3 at higher latency; 2 tolerates none at all.
  • Raft's log-completeness rule means every new leader already has every committed entry, so failover never requires reconciling divergent logs.
  • Randomised election timeouts prevent split votes — the same jitter principle as retry storms and cache TTLs.
  • Reads are harder than writes: a partitioned leader doesn't know it's deposed. Use quorum reads, leases, or read-index.
  • Membership changes can create two disjoint majorities — change one node at a time, or use joint consensus.
  • Consensus scales backwards — more voters means slower commits. Adding nodes buys durability, not throughput.
  • Partition and run consensus per shard to scale horizontally, at the cost of cross-shard transactions.
  • Quorums give recency; consensus gives ordering — and you pay for ordering.
  • Use consensus for small, critical metadata (leader election, config, membership) and cheaper replication for bulk data.
  • Ambiguous outcomes are unavoidable — make retrying safe with request IDs deduplicated inside the replicated state machine.
  • A distributed lock isn't safe without fencing tokens, because a paused process cannot police itself.
