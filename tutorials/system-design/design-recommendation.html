Design Recommendation System Case Study

What you'll master: the offline/online split that lets an arbitrarily expensive model serve a 50 ms request, the retrieval-then-ranking funnel and why it's the only way to score millions of items, approximate nearest-neighbour search as the mechanism that makes retrieval possible, training-serving skew (the bug that silently destroys model quality), and why offline metrics are a filter rather than a verdict.

Prerequisites: Caching, Pub/Sub (streaming features), Data Platforms (batch vs streaming). Pairs with Search Engine, which uses the same funnel.

🎯 What this problem is really testing. Not machine learning — it's a pipeline architecture question. The signal is whether you separate the expensive work (training, embedding, precomputation) from the latency-critical work (serving), and whether you recognise that scoring 10 million items per request is impossible so the problem must be split into cheap-and-broad retrieval followed by expensive-and-narrow ranking. Candidates who dive into matrix factorisation details usually never get to the architecture, which is what's actually being assessed.

1. Requirements

FunctionalNon-functional
Given a user, return a ranked list of itemsp99 < 100 ms — it renders inline with the page

The last point matters and is easy to miss: recommendations are never worth failing a page load. Whatever the design, it must have a fallback (trending items, a cached list) so a recommendation outage degrades the page rather than breaking it.

2. Estimation: Why Live Scoring Is Impossible

Assume 100M users, 10M items, 50K recommendation requests/s at peak.

NAIVE APPROACH — score every item for every request:
   50,000 req/s × 10,000,000 items = 5 × 10¹¹ scores/second
   At even 100 ns per score, that is 50,000 CPU-seconds per second
   → ~50,000 cores, continuously, for recommendations alone.
   → CONSEQUENCE: impossible. This single calculation is what forces
     the entire architecture.

WITH THE FUNNEL:
   retrieval: ~500 candidates from 10M   (approximate, cheap, indexed)
   ranking:   score 500 with a heavy model
   50,000 req/s × 500 = 25M scores/s — a few hundred cores. Feasible.
   → 20,000x less work for a near-identical result, because the
     items ranked 500th and 5,000,000th are both "not shown".

PRECOMPUTED STORAGE
   100M users × 500 candidates × 8 B = 400 GB
   → fits a sharded key-value store; a lookup is ~1 ms.

INTERACTION DATA
   100M users × 50 events/day = 5B events/day
   × 100 B = 500 GB/day → streaming pipeline + data lake.

The 5 × 10¹¹ figure is the number to lead with — it demonstrates immediately that the naive design is not merely slow but impossible by orders of magnitude, which is what justifies everything that follows.

3. The Core Architecture: Offline / Nearline / Online

OFFLINE (hours-days) — arbitrarily expensive, never on the request path
   ├─ train the embedding model on historical interactions
   ├─ compute user and item EMBEDDINGS (dense vectors, e.g. 128-dim)
   ├─ build the ANN index over item embeddings
   └─ precompute candidate sets for active users

NEARLINE (seconds-minutes) — keeps recommendations responsive
   ├─ stream interaction events (Kafka)
   ├─ update "recent activity" features per user
   └─ invalidate/refresh candidates for users with new signals

ONLINE (tens of ms) — the request path, must be fast and safe
   ├─ fetch precomputed candidates (KV lookup, ~1 ms)
   ├─ fetch fresh features (recent views, current context)
   ├─ RANK ~500 candidates with the serving model (~20-40 ms)
   ├─ apply business rules (dedupe, diversity, already-purchased)
   └─ fall back to trending if ANYTHING above fails

The three-tier split is the answer to the question. The offline tier can take six hours and nobody notices; the online tier has a 100 ms budget. Putting the nearline tier between them is what stops recommendations feeling stale — a user who just watched five cooking videos should see cooking content within minutes, not tomorrow, and that requires updating features without retraining the model.

4. Deep Dive: Retrieval — How You Get 500 From 10 Million

Retrieval must be fast and approximate; precision is the ranker's job. Real systems blend several sources:

SourceMechanismStrength / weakness
Collaborative filtering"Users like you liked these" — from the interaction matrixFinds genuinely surprising items. Fails completely for new items with no interactions.
Content-based (embeddings)Nearest neighbours to items the user engaged with, in embedding spaceWorks for new items (metadata gives an embedding). Tends toward sameness — the filter-bubble risk.
Trending / popularGlobal or segment-level top itemsThe universal fallback. Works with zero personal data.
Rule-based"Continue watching", "from creators you follow"High precision, narrow coverage — cheap and worth including.

Approximate nearest neighbour (ANN) search is what makes embedding retrieval tractable, and it's the mechanism most candidates can't explain:

Exact nearest neighbour over 10M item embeddings = 10M dot products
per query. Far too slow.

ANN trades a little recall for orders of magnitude of speed:
   HNSW      — a navigable small-world graph; ~1 ms for 10M vectors
               at ~95% recall. The common default.
   IVF-PQ    — cluster the space, search only nearby clusters, and
               COMPRESS vectors (product quantisation) so the index
               fits in RAM.
   ScaNN/FAISS/Vespa — production implementations.

The trade is explicitly acceptable here: missing the 47th-best
candidate is invisible, because the ranker will reorder the top 500
anyway and only ~20 are shown.
💡 Why approximation is obviously correct at this stage: retrieval's job is to avoid missing anything the ranker would have placed in the top 20. Getting 95% of the truly-relevant candidates costs you almost nothing in final quality, while exact search costs 100× the latency. Contrast this with inventory or payments, where approximation is unacceptable — knowing which parts of a system tolerate error is a recurring senior judgement, and here it's the difference between feasible and impossible.

5. Deep Dive: The Feature Store and Training-Serving Skew

This is the failure mode that silently destroys recommendation quality, and it's rarely mentioned in interviews:

❌ Two implementations 
Training (Python, batch):
  avg_watch = total / count
  over the last 30 days

Serving (Java, online):
  avg_watch = total / count
  over the last 28 days
  ...and it excludes videos
  under 10 seconds

Subtly different features.
The model was trained on one
distribution and serves on
another. Quality degrades and
nothing errors.
✅ One definition, two paths 
A FEATURE STORE computes each
feature ONCE from a single
definition, and materialises it
to both:

  offline store (for training)
  online store  (for serving)

Same code, same semantics,
guaranteed consistent —
and point-in-time correct
for training.

Point-in-time correctness is the subtler half. When building training data you must use feature values as they were at the time of the interaction, not as they are now. Using today's "total watch count" to train on a click from last month leaks future information — the model learns from data it won't have at serving time, scores brilliantly offline, and fails in production. That's label leakage, and it's the most common reason a model that looked excellent in evaluation disappoints on launch.

6. Deep Dive: Cold Start and the Exploration Problem

CaseStrategy
New userTrending items, optionally segmented by whatever you know (country, device, referrer). Ask 2–3 onboarding preference questions — cheap and effective. Personalise rapidly: the first few interactions are worth far more than later ones.
New itemContent-based embedding from metadata (title, category, creator, text). Collaborative signals are unavailable until it accumulates interactions — so deliberately give it some impressions to gather them.
New user AND new itemPure content/popularity. This is the hardest quadrant, and honest fallbacks matter more than clever models.

The exploration/exploitation trade is the deeper issue. A system that only shows what it's confident about never learns anything new:

Pure exploitation: show the highest predicted-score items.
   → the model's existing beliefs are reinforced; new items never
     get impressions, so they never accumulate data, so they are
     never recommended. A FEEDBACK LOOP that ossifies the catalogue.

Exploration: deliberately show some uncertain items.
   → epsilon-greedy: ~5-10% of slots go to exploration
   → or Thompson sampling / UCB: explore in proportion to uncertainty

Cost: a small amount of short-term engagement.
Benefit: the catalogue stays alive, new items get discovered, and
the model keeps learning. Without it the system slowly degrades in
a way offline metrics will not reveal.

The same mechanism addresses filter bubbles: injecting diversity into the candidate set — by category, creator, or embedding distance — prevents the "watched one video about X, now everything is X" failure that users experience as the system being broken rather than personalised.

7. Deep Dive: Evaluation — Offline Metrics Are Not the Verdict

MethodMeasuresLimitation
Offline metrics (precision@k, recall, NDCG)Does the model rank held-out interactions well?Only measures what users saw. It cannot tell you whether an item the user never had the chance to click would have been better — a fundamental bias, not a fixable one.
A/B testReal business metrics on real trafficThe verdict. Slow (days–weeks), and needs enough traffic for significance.
InterleavingBlend two rankers' results in one list and compare click positionsFar more sensitive than A/B for ranking changes — needs a fraction of the traffic and time.
Counterfactual / off-policyEstimate a new policy's performance from logged dataCheaper than A/B, and dependent on assumptions that often don't hold.

Choosing the metric is where recommendation systems go morally and commercially wrong. Optimising raw click-through teaches the model to promote clickbait; optimising watch time promotes outrage and autoplay traps. Better targets combine engagement with satisfaction signals — completion rate, returns the next day, explicit feedback, and negative signals like "not interested" and unfollows. Long-term retention is the honest objective, and it's the hardest to measure, which is exactly why systems drift toward the easy proxy.

Offline metrics remain useful as a filter — they cheaply reject bad candidates before you spend traffic on them. They just aren't evidence that a model is better, and treating them as such is the common error.

Interview Questions

🟢 Beginner — Why can't you compute recommendations at request time?

Because the work is impossible within the latency budget, by several orders of magnitude:

10,000,000 items × 50,000 requests/s = 5 × 10¹¹ scores per second.
At 100 ns per score that's ~50,000 CPU-seconds every second — around
50,000 cores, continuously, for recommendations alone.

And that's just scoring. Training the model takes hours.

The request budget is tens of milliseconds; a single page fetches recommendations alongside everything else it needs.

The fix is separating expensive work from latency-critical work:

Offline (hours to days) does the heavy lifting — training, computing embeddings, building the search index, precomputing candidates per user. It can take six hours and nobody notices.

Online (tens of ms) does a key-value lookup for precomputed candidates, then lightly re-ranks a few hundred of them with fresh context.

This decouples how sophisticated the model can be from how fast the response must be — you can run an arbitrarily expensive offline job without it ever touching request latency.

In practice there's a third tier: a nearline streaming layer, seconds to minutes, that updates recent-activity features so a user who just watched five cooking videos sees cooking content promptly. It updates features without retraining the model, which is what makes freshness affordable.

🟢 Beginner — What is the cold-start problem, and how do you handle it?

Recommendations are built from interaction history, so a user or item with no history can't be handled by the main mechanism. There are two distinct cases:

New user: no signals about their preferences. Fall back to trending or popular items, ideally segmented by whatever you do know — country, device, how they arrived. Two or three onboarding preference questions are cheap and surprisingly effective. Then personalise fast: the first handful of interactions carry far more information than later ones.

New item: no interactions, so collaborative filtering ("users like you liked this") cannot surface it. Use content-based retrieval instead — derive an embedding from metadata (title, category, creator, description) and find users who engaged with similar items.

The part that's easy to miss: new items need deliberate impressions. If you only show items with high predicted scores, a new item with no data never gets shown, never accumulates interactions, and therefore never becomes recommendable — a self-reinforcing loop that quietly ossifies the catalogue. Reserving an exploration budget (5–10% of slots) breaks it.

The hardest quadrant is new user and new item together, where only popularity and content signals exist. Honest fallbacks matter more than clever modelling here — and having any fallback is essential, because the alternative is an empty section on the page.

🟡 Mid — Explain the retrieval-then-ranking funnel. Why two stages?

Because scale and precision have opposite costs, and no single stage can provide both.

RETRIEVAL: 10,000,000 items → ~500 candidates
   Must be FAST and can be APPROXIMATE.
   Mechanisms: ANN search over embeddings, collaborative filtering
   lookups, trending lists, rule-based sources — blended.
   ~1-5 ms.

RANKING: 500 candidates → ordered top 20
   Now the set is small, so an expensive model is affordable:
   hundreds of features, deep networks, full personalisation context.
   ~20-40 ms.

Why the split works: the items ranked 500th and 5,000,000th are both "not shown", so retrieval only has to avoid missing things the ranker would have placed in the top 20. That's a much weaker requirement than ranking correctly, and it's why approximation is acceptable there.

The arithmetic: 50,000 req/s × 500 candidates = 25M scores/s, versus 5 × 10¹¹ for scoring everything — a 20,000× reduction for a near-identical result.

Retrieval blends multiple sources rather than using one, because each has different blind spots: collaborative filtering finds surprising items but fails for new ones; content-based works for new items but tends toward sameness; trending covers cold start. Union them, dedupe, and let the ranker sort it out.

The pattern generalises — the same broad-and-cheap then narrow-and-precise funnel appears in search (retrieve by inverted index, then rank with BM25 and ML), in geospatial matching (cell query, then routing), and in fraud detection (cheap rules, then an expensive model). Whenever you need both scale and precision, the answer is usually a funnel rather than a single clever stage.

🟡 Mid — Recommendations feel stale after a user's behaviour changes. Diagnose and fix.

The candidates were precomputed by a batch job that runs daily, so a user who just watched five cooking videos still sees yesterday's recommendations. The system is working as designed — the design is the problem.

The fix is a nearline tier between the offline and online stages:

Interaction events → Kafka → streaming processor
   ├─ update RECENT ACTIVITY features per user (last N items viewed,
   │  categories engaged with in the last hour) → online feature store
   └─ trigger candidate refresh for users with significant new signals

The online ranker then uses fresh features even though the MODEL and
the base candidate set are from the last batch run.

The key distinction: you don't need to retrain the model to be responsive — you need fresh features. Retraining takes hours; updating "categories viewed in the last hour" takes seconds. Most of the perceived staleness comes from stale features, not a stale model.

Layered fixes, cheapest first:

• Session-context re-ranking — boost candidates matching what the user is doing right now, using signals available in the request itself. No infrastructure needed, immediate effect.
• Nearline feature updates — seconds of latency, moderate cost.
• Event-driven candidate refresh — regenerate candidates when a user's behaviour shifts significantly, rather than on a fixed schedule. Most users are inactive on any given day, so refreshing everyone nightly is largely wasted work.
• More frequent batch runs — the blunt option; expensive and it only reduces the staleness window rather than eliminating it.

The trade to state: perfect freshness would mean live inference over the full catalogue, which the estimation rules out. The design goal is "responsive enough that users don't notice", and nearline features achieve that at a fraction of the cost.

🔴 Senior — What is training-serving skew and how do you prevent it?

Training-serving skew is when the features a model sees in production differ from those it was trained on. It degrades quality silently — nothing errors, no alert fires, and the model just performs worse than evaluation predicted.

How it arises, and it's almost always the same way: features are implemented twice. Training runs in Python over a data warehouse; serving runs in Java or Go against a live store. Two implementations of "average watch time over the last 30 days" will eventually diverge — a different window, a different null handling, a filter one side applies and the other doesn't. Neither is wrong; they're just different, and the model was fitted to one of them.

The fix is a feature store: define each feature once, and materialise it to both an offline store (for training) and an online store (for serving) from that single definition. Same computation, same semantics, guaranteed consistent.

The subtler half is point-in-time correctness. When constructing training data you must use feature values as they were at the moment of the interaction:

❌ Training row for a click from 3 weeks ago, joined against TODAY's
   "total video views" → the model learns from a value that already
   reflects the outcome. It scores brilliantly offline and fails live.
   This is LABEL LEAKAGE.

✅ Retrieve the feature value as of the interaction timestamp.
   Feature stores support this explicitly, because doing it correctly
   by hand is difficult and easy to get subtly wrong.

Detection, since prevention is never complete: log the actual feature vectors used at serving time and compare their distributions against the training set. A drift alert on feature distributions is one of the highest-value monitors in an ML system — it catches skew, upstream data changes, and genuine population shift, all of which look identical from the model's perspective.

Worth stating plainly: this is the most common reason a model that looked excellent in evaluation disappoints on launch, and it's an engineering problem rather than a modelling one — which is exactly why it belongs in a systems design discussion.

🔴 Senior — How do you know a new recommendation model is actually better?

Offline metrics are a filter, not a verdict — and understanding why is the substance of the answer.

Why offline evaluation is fundamentally biased: it measures how well the model ranks items users actually saw and interacted with. But the items they saw were chosen by the current model. You cannot observe whether an item the old model never showed would have been clicked — the counterfactual is unavailable. So offline metrics systematically favour models that agree with the incumbent, which is precisely backwards when you're trying to find something better.

What I'd actually do, in order:

1. Offline metrics as a cheap filter. NDCG, precision@k against held-out data — good for rejecting clearly-bad candidates before spending traffic on them. Never treat an improvement here as evidence of a real improvement.

2. Interleaving for ranking changes. Blend both rankers' results into one list and observe which source's items get clicked. Far more sensitive than an A/B test because each user compares both rankers directly, so it needs a fraction of the traffic and time. This is underused and the strongest practical tool for ranking work.

3. A/B test as the verdict. Real traffic, real business metrics, run long enough for significance and to see beyond novelty effects.

Choosing the metric is where this gets genuinely hard, and it's the part worth emphasising: optimising raw click-through rate teaches the model to promote clickbait; optimising watch time promotes autoplay traps and outrage. Both will show "improvements" in an A/B test while making the product worse.

Better: combine engagement with satisfaction signals — completion rate, next-day return, explicit feedback — and weight negative signals heavily ("not interested", unfollows, hides). The honest objective is long-term retention, which is the hardest thing to measure and the reason systems drift toward easy proxies.

And measure what an A/B test won't show you: catalogue coverage (is the model collapsing onto a narrow set of items?) and diversity per user. A model can win on engagement while quietly creating a filter bubble that costs you months later — an effect no two-week experiment will surface.

🏋️ Graded Exercises

Exercise 1 (Easy): 10M items, 50K requests/s. Compute the cost of scoring everything versus the funnel.
Solution 
SCORE EVERYTHING
   50,000 req/s × 10,000,000 items = 5 × 10¹¹ scores/s
   at 100 ns each = 50,000 CPU-seconds per second
   → ~50,000 cores continuously. Impossible.

FUNNEL (retrieve 500, then rank)
   retrieval: ANN lookup, ~1 ms per request
   ranking:   50,000 × 500 = 2.5 × 10⁷ scores/s
              at 100 ns each = 2.5 CPU-seconds per second
   → a few hundred cores with overhead. Feasible.

REDUCTION: 20,000x

Why the quality loss is negligible: only ~20 items are shown. The items ranked 500th and 5,000,000th are equally invisible, so retrieval only has to avoid missing something that belonged in the top 20. Getting 95% of those is worth 20,000× less compute.

What the calculation forces: it's not an optimisation, it's the reason the architecture exists. Any design that scores the full catalogue per request is wrong by four orders of magnitude — and doing this arithmetic first is what stops you designing one.

The same reasoning justifies approximation within retrieval: exact nearest-neighbour over 10M vectors is 10M dot products per query, while ANN gets ~95% recall at roughly 1% of the cost.

Exercise 2 (Easy): Why must a recommendation service never block page rendering?
Solution

Because recommendations are optional content on a page whose core purpose is something else. A product page must show the product; a video page must play the video. "You might also like" is additive.

If the recommendation service is a hard dependency, its availability multiplies into the page's:

Page availability = product service × recommendation service
                  = 0.999 × 0.99 = 0.989

A 99% recommendation service has just cost you nearly 1% of ALL page
loads — on the revenue path — for a section users may not even scroll to.

The design:

• Strict timeout (say 50 ms). If recommendations aren't ready, render without them.
• Cached fallback — a generic trending list, refreshed periodically, that can always be served. Better than an empty section.
• Circuit breaker so a degraded service fails fast rather than consuming the timeout on every request.
• Async loading — render the page, fetch recommendations separately. The user sees the product immediately and recommendations appear when ready.

This is the general principle from microservices: every synchronous call is a decision to share fate. For an optional feature that decision should always be "no" — and this is one of the clearest cases where the right answer is obvious once you compute the availability product.

Exercise 3 (Medium): Design the retrieval stage. Which sources, and how do you combine them?
Solution

Blend multiple sources, because each has a different blind spot and the union is far more robust than any single one:

1. COLLABORATIVE (ANN over user embedding) → ~200 candidates
      "users with similar taste engaged with these"
      Strength: finds genuinely surprising items.
      Blind spot: new items with no interactions.

2. CONTENT-BASED (ANN over item embeddings)  → ~150 candidates
      "similar to things you engaged with recently"
      Strength: works for brand-new items via metadata.
      Blind spot: tends toward sameness (filter bubble).

3. TRENDING / POPULAR (precomputed list)     → ~50 candidates
      Segmented by region/demographic where useful.
      Strength: always available, covers cold start.

4. RULE-BASED                                → ~50 candidates
      "continue watching", "new from creators you follow"
      Strength: high precision, cheap.

5. EXPLORATION                               → ~50 candidates
      Deliberately uncertain items, so new content gets impressions.

UNION → dedupe → filter → ~500 to the ranker

Filters applied before ranking (cheap, and they prevent embarrassing output): already purchased or watched, out of stock, region-unavailable, age-restricted, explicitly hidden by the user, and blocked creators. Doing this at retrieval avoids wasting ranking compute on items that can never be shown.

Why union rather than picking the best source: the ranker is much better at judging relative quality than any retrieval heuristic. Retrieval's job is recall — make sure the good items are in the set — while precision is delegated. Over-filtering at retrieval permanently removes options the ranker never gets to consider.

Source allocation should be tunable and measured: track which source produced each shown item and its downstream engagement. That tells you where to spend the candidate budget, and it's the data that justifies keeping (or cutting) the exploration allocation.

Exercise 4 (Medium): A new item gets no impressions because the model has no data on it. Break the loop.
Solution

The loop: no interaction data → low predicted score → never shown → no interaction data. It's self-reinforcing, and it means the catalogue slowly ossifies around items that happened to get early traction. Offline metrics won't reveal it, because they only measure items that were shown.

1. Content-based retrieval (immediate coverage). Derive an embedding from metadata — title, category, creator, description text — so the item is retrievable from day one on similarity to items users already like, with no interaction data at all.

2. An explicit exploration budget (the real fix). Reserve 5–10% of slots for items the model is uncertain about, rather than items it scores highly. Two standard approaches:

epsilon-greedy    : with probability ε, show a random/new item
Thompson sampling : sample from the posterior over each item's
                    quality, so uncertain items get shown in
                    proportion to how uncertain they are — more
                    principled, and it self-corrects as data arrives

3. A cold-start boost with decay. Give new items a temporary score bonus that decays as impressions accumulate. Enough to gather signal; not enough to flood the product with untested content.

4. Targeted exploration. Show a new item to users most likely to appreciate it based on content similarity, rather than to random users. You gather informative signal faster and degrade fewer users' experience — noticeably more efficient than uniform exploration.

The cost, stated honestly: exploration reduces short-term engagement, because you're deliberately showing items with lower expected value. That's an investment in long-term catalogue health and model quality — and it will look like a regression in any short A/B test, which is exactly why it needs to be a deliberate policy decision rather than something an experiment decides.

Monitor catalogue coverage — what fraction of items received impressions this week — as a first-class metric alongside engagement. A system optimising engagement alone will quietly drive that number down, and you'll only notice when creators leave.

Exercise 5 (Hard): Your model performs excellently offline and poorly in the A/B test. List the likely causes.
Solution

A gap between offline and online performance has a small number of usual causes, and they're worth working through in order of likelihood:

1. Training-serving skew (most common). Features are computed differently in training and serving — a different time window, different null handling, an extra filter on one side. The model serves on a distribution it never learned. Check: log actual serving feature vectors and compare their distributions to training.

2. Label leakage / point-in-time errors. Training data was built using feature values as they are now rather than as they were at the interaction. The model learned from information unavailable at serving time, which inflates offline scores specifically. Check: any feature whose importance is suspiciously high, especially aggregates that could include the outcome.

3. Offline evaluation bias. Held-out data only contains items the old model chose to show. A new model that recommends different items is penalised for having no observed labels on them — so offline metrics structurally favour agreement with the incumbent.

4. The offline metric doesn't match the business metric. Higher NDCG on historical clicks doesn't imply higher conversion or retention. Optimising the proxy improved the proxy.

5. Position and presentation bias. Historical clicks are heavily influenced by where items appeared. A model trained on raw clicks learns "position 1 gets clicked" rather than "this item is good", and that signal doesn't transfer.

6. Feedback-loop effects. The training data was generated by the old model, so the new model is fitted to a distribution the old model created — and once deployed, it changes that distribution.

7. Non-model causes worth ruling out early: the new model is slower and pushes p99 past a timeout, so some requests fall back to trending; the A/B split is contaminated; or the test period coincides with a seasonal effect.

What I'd do: check latency and fallback rates first (cheap, and a surprisingly common culprit), then compare serving feature distributions to training, then audit for leakage. And I'd treat the outcome as informative rather than a failure: it's evidence that the offline evaluation methodology needs fixing, which is more valuable than this one model — interleaving would have caught the discrepancy days earlier and far more cheaply.

Exercise 6 (Hard): Design for the filter bubble: users who watch one video about a topic see only that topic afterwards.
Solution

This is a feedback loop, not a bug. The model correctly learned "this user engaged with X", and optimising engagement produces more X. Each impression reinforces the signal, so the loop tightens over time — and users experience it as the product being broken rather than personalised.

1. Diversity constraints at ranking time. The most direct fix — a hard rule rather than a model change:

Cap items per category/creator in a result set:
   at most 3 of 20 from any one category
   at most 2 from any one creator

Or use MMR (maximal marginal relevance): score each candidate by
   λ × relevance − (1−λ) × similarity to items already selected
so each addition must bring something new.

2. Diversity in retrieval, not just ranking. If every candidate is from one topic, no ranking rule can create diversity. Allocate retrieval slots across categories, and include exploration candidates.

3. Optimise for the session and beyond, not the click. Single-click optimisation is what creates the bubble. Train on session-level or next-day-return outcomes, where variety demonstrably performs better — a user shown ten near-identical videos watches fewer of them overall.

4. Weight negative signals heavily. "Not interested", hides, and unfollows are strong, under-used evidence. A user who hides three items from a category is telling you something no engagement metric captures.

5. Give the user controls. "Show me less of this", topic preferences, an explicit "explore" mode. Transparency helps too — "because you watched X" lets users understand and correct the system's model of them.

6. Measure it. Track per-user diversity (distinct categories in the last N impressions) and catalogue coverage as first-class metrics. What isn't measured drifts, and engagement metrics alone will actively drive both down.

The honest tension to state: diversity typically reduces short-term engagement, so it will lose most A/B tests. That means it has to be a deliberate product decision informed by long-term retention and user satisfaction, not something an experiment framework decides. Framing it that way — as a case where the metric you can measure conflicts with the outcome you want — is the senior answer, and it's the same class of judgement as accepting a small oversell rate or approximate leaderboard ranks elsewhere in this track.

🎯 Key Takeaways

  • Scoring every item per request is impossible — 5 × 10¹¹ scores/s. That calculation forces the entire architecture.
  • Split offline / nearline / online: expensive training and precomputation offline, feature freshness nearline, lookups and light ranking online.
  • The retrieval-then-ranking funnel reduces work 20,000× — retrieval needs recall, ranking provides precision.
  • Approximate nearest neighbour is obviously correct here — 95% recall at 1% of the cost, and the loss is invisible after ranking.
  • Blend retrieval sources — collaborative, content-based, trending, rules, exploration — because each has a different blind spot.
  • Training-serving skew silently destroys quality. One feature definition, materialised to both paths, with point-in-time correctness.
  • Label leakage from using current feature values in training data is the top reason a great offline model disappoints live.
  • Cold start needs deliberate exploration, not just fallbacks — otherwise new items never get the impressions they need to become recommendable.
  • Offline metrics are a filter, not a verdict — they only measure items the current model already showed.
  • Interleaving beats A/B for ranking changes — far more sensitive, needing a fraction of the traffic.
  • Optimising raw CTR or watch time produces clickbait. Combine engagement with satisfaction and negative signals; aim at retention.
  • Recommendations must never block page rendering — strict timeout, cached trending fallback.
