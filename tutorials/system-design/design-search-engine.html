Design Search Engine Case Study

What you'll master: the three-stage pipeline (crawl → index → serve) and why each stage has a different bottleneck, document- versus term-partitioning and why almost everyone picks the one that touches every shard, the query latency budget that dictates the ranking funnel, posting-list compression (the difference between an index that fits in RAM and one that doesn't), and crawler politeness — the part that gets your IP blocked if you get it wrong.

Prerequisites: Inverted Index (the core structure), Estimation, Recommendation (same retrieval/ranking funnel). Pairs with Data Platforms.

🎯 What this problem is really testing. Whether you can hold three different systems in your head at once. Crawling is a politeness and coverage problem, indexing is a batch throughput problem, and serving is a latency problem — and they connect only through the index. Candidates who spend the whole interview on ranking algorithms miss that the hard engineering is in the pipeline, and that document-partitioning (scatter-gather to every shard) is chosen despite being the obviously "wasteful" option.

1. Requirements

FunctionalNon-functional
Crawl and discover pagesIndex billions of documents
Index content with positions and metadataQuery p99 < 200 ms
Keyword and phrase queries, ranked by relevanceFreshness: news within minutes, general pages within days
Handle typos, synonyms, stemmingBe a polite crawler — don't get blocked

Scoping question worth asking: web-scale search (billions of pages, adversarial SEO, a crawler) is a very different problem from site search (millions of documents, trusted content, no crawling). I'll design web-scale and note where site search is far simpler — because for most real systems the answer is "use Elasticsearch", and knowing when not to build this is part of the judgement.

2. Estimation

Assume 10B documents, 100K queries/s.

INDEX SIZE
   10B docs × ~1,000 unique terms each = 10¹³ postings
   naive (4 B docId + 4 B position + 2 B tf) = 100 TB
   with delta encoding + variable-byte compression (~1-2 B/posting):
      ≈ 10-20 TB
   → CONSEQUENCE: compression is not optional. It's the difference
     between an index that fits in cluster RAM and one that doesn't —
     and RAM residency is what makes 200 ms achievable.

SHARDING
   20 TB / 64 GB per node ≈ 300 shards minimum
   with replication ×3 for availability and read throughput:
      ~900 nodes
   → CONSEQUENCE: a query fanning out to 300 shards means the
     response is bounded by the SLOWEST shard — tail latency
     dominates (see §6).

QUERY LOAD
   100,000 queries/s × 300 shards = 30,000,000 shard queries/s
   → CONSEQUENCE: each shard query must be sub-millisecond. This is
     what forces in-memory posting lists and skip lists.

CRAWL RATE
   10B pages re-crawled monthly on average:
      10¹⁰ / (30 × 10⁵ s) ≈ 3,300 pages/s sustained
   at ~100 KB/page = 330 MB/s of ingest, continuously
   → CONSEQUENCE: crawling is a bandwidth and politeness problem
     long before it is a compute problem.

3. Stage 1: Crawling

       ┌─────────────┐
       │ URL FRONTIER │ ← priority queue, politeness-aware
       └──────┬──────┘
              ▼
       ┌─────────────┐    robots.txt cache
       │  FETCHERS   │◄───────────────────
       └──────┬──────┘
              ▼
     ┌────────────────┐
     │ CONTENT STORE  │ → dedupe → parse → extract links → back to frontier
     └────────────────┘
ConcernHandling
PolitenessHonour robots.txt (cached per host), and rate-limit per host — typically one request every 1–2 s. This is the constraint that shapes the frontier: you cannot simply pull the highest-priority URL, because it may be from a host you just hit.
Frontier designTwo-level: priority queues by importance, then per-host FIFO queues with a next-allowed-time. A worker takes from a host whose timer has expired.
DeduplicationURL-level (canonicalise, strip tracking params) and content-level. Near-duplicates are rampant — use SimHash to detect them, since exact hashing misses pages differing by a timestamp.
FreshnessConditional GETs with ETag/If-Modified-Since — a 304 costs almost nothing. Re-crawl frequency should adapt to observed change rate: news hourly, archives monthly.
Crawler trapsInfinite calendars, session IDs generating unbounded URLs, deliberately generated link mazes. Defend with depth limits, per-host page caps, and URL-pattern detection.
⚠️ Politeness is a hard constraint, not a nicety. An impolite crawler gets IP-banned, blocked by Cloudflare, and reported — after which you cannot crawl that content at all. It also means the crawl is host-limited rather than bandwidth-limited: crawling 3,300 pages/s at one request per host per second requires touching at least 3,300 distinct hosts concurrently. That's why the frontier is organised by host, and why a naive priority queue doesn't work.

4. Stage 2: Indexing at Scale

Parsed documents → tokenise → normalise → build postings → merge → serve

TOKENISATION AND NORMALISATION
   lowercase · strip punctuation · stemming ("running" → "run")
   language detection (CJK has no spaces — needs segmentation)
   Keep STOP WORDS indexed: dropping "the" makes the phrase
   "to be or not to be" unsearchable.

BUILDING AT SCALE — MapReduce-shaped:
   Map:    document → (term, docId, position, tf) tuples
   Reduce: group by term → sorted posting list → compressed segment

INCREMENTAL UPDATES — you cannot rebuild 10B documents to add one:
   new documents → small in-memory segment
   periodically flush to an immutable on-disk segment
   background MERGE of small segments into larger ones
   deletes are TOMBSTONES, applied at merge time
   → this is an LSM tree, the same structure as the key-value store,
     for the same reason: writes are appends, reads check several
     segments, and compaction bounds the read cost.

Posting list compression is what makes the index fit in memory, and the mechanism is worth knowing:

Posting list for "database": [17, 145, 892, 1043, 1099, ...]

DELTA ENCODING — store gaps, not absolute IDs:
   [17, 128, 747, 151, 56, ...]
   Gaps are much smaller numbers than the IDs themselves.

VARIABLE-BYTE / PFOR — small numbers use fewer bytes:
   a gap of 56 costs 1 byte instead of 4.

Result: ~1-2 bytes per posting instead of 8-10.
   100 TB → 10-20 TB. That is the difference between fitting in
   cluster RAM and not, and RAM residency is what makes the latency
   budget achievable.

SKIP LISTS over long posting lists let intersection JUMP AHEAD
instead of scanning every entry — essential when one query term is
common and the other is rare.

5. The Core Decision: How to Shard the Index

Document-partitionedTerm-partitioned
LayoutEach shard indexes a subset of documents, holding all terms for themEach shard owns a subset of terms, holding their full posting lists
QueryFan out to every shard; each returns its local top-k; mergeContact only the shards holding the query's terms
IntersectionLocal — each shard intersects its own listsAcross the network — posting lists must be shipped between shards to intersect
Load balanceEven — documents distribute uniformlyTerrible — the shard owning "the" is a permanent hotspot
FailureLosing a shard loses some documents — recall degrades gracefullyLosing a shard makes certain terms unsearchable entirely
Used byEffectively everyone — Elasticsearch, Lucene, GoogleRare

Document-partitioning wins despite touching every shard, and the reason is the row that matters most: intersection stays local. A two-term query on a term-partitioned index requires shipping one term's posting list — potentially gigabytes for a common word — across the network to intersect with the other. Document-partitioning does the expensive work where the data already is, and each shard returns only its small top-k.

The generalisable rule: partition so the expensive operation stays local, even if that means contacting more nodes. Fanning out to 300 shards sounds worse than contacting 2, but 300 cheap local intersections beat 2 with a gigabyte network transfer between them.

6. Deep Dive: The Query Path and Its Latency Budget

200 ms total budget:

   parse + rewrite query (spelling, synonyms, stemming)   ~5 ms
   fan out to 300 shards, each:
       posting list lookup + intersection                 ~5 ms
       local BM25 scoring, return local top-100           ~5 ms
   merge 300 × 100 results, take global top-1000          ~10 ms
   RE-RANK top ~100 with the expensive ML model           ~50 ms
   fetch snippets/titles for the top 10                   ~20 ms
   ─────────────────────────────────────────────────────
   plus network hops and serialisation                    ~50 ms
   TOTAL                                                 ~145 ms ✓

Tail latency is the dominant risk, and this is where the fan-out design bites:

With 300 shards, the response waits for the SLOWEST one.
If each shard has a p99 of 50 ms, the probability that at least one
of 300 is slow is  1 − 0.99³⁰⁰ ≈ 95%.

→ Almost EVERY query hits some shard's p99. The system's p50 is
  determined by the shards' p99.

Mitigations:
   HEDGED REQUESTS — after p95 elapses, send a duplicate to a replica
      and take the first response. A few percent extra load for a
      dramatic tail improvement.
   PARTIAL RESULTS — return after 95% of shards respond. Missing 1%
      of documents is invisible to the user; a 2-second wait is not.
   Fewer, larger shards where memory allows.

Ranking is the same funnel as recommendations: cheap BM25 scoring across all candidates in each shard, then an expensive ML re-rank of only the top ~100. You never run the heavy model over the full candidate set, for exactly the reason the estimation showed.

SignalPurpose
BM25 (TF-IDF's successor)Term frequency × inverse document frequency, with saturation and length normalisation — cheap, computed per shard
PageRank-style link authorityDocument importance from the link graph — computed offline over the whole web graph, stored as a per-document score
FreshnessRecency boost, weighted by query intent (news queries need it; recipe queries don't)
Click signalsHistorical engagement per (query, document) — powerful, and a feedback loop that needs exploration, exactly as in recommendations
Spam / qualityAdversarial: SEO actively games ranking, so this is a permanent arms race unique to web search

Interview Questions

🟢 Beginner — Walk through the three stages of a search engine.

1. Crawling. Bots fetch pages, extract links, and feed newly discovered URLs back into a frontier queue. The constraints here are politeness (honour robots.txt, rate-limit per host) and efficiency (use conditional GETs so unchanged pages cost almost nothing). It's a bandwidth and courtesy problem more than a compute one.

2. Indexing. Parse each page, tokenise and normalise the text (lowercase, stem, detect language), then build the inverted index — term → list of documents containing it, with positions for phrase search and term frequency for ranking. At billions of documents this is a distributed batch job, and the index is sharded across hundreds of machines.

3. Query serving. Parse the query, look up each term's posting list, intersect them, score the candidates, and return the top results. This is the latency-critical stage with a budget of roughly 200 ms.

The connection worth noting: the three stages are almost entirely decoupled — they communicate only through the index. Crawling can be hours or days behind, indexing runs as a batch pipeline, and serving reads a mostly-immutable structure. That decoupling is what lets each stage be optimised for a completely different property: coverage, throughput, and latency respectively.

🟢 Beginner — Why store positions in the inverted index?

Because without them you can only ask "do both words appear somewhere in this document?", which produces obviously wrong results for phrase queries.

Query: "New York"

Without positions:
   documents containing "new" ∩ documents containing "york"
   → matches "a new dress shop in York" — both words present,
     completely wrong result.

With positions:
   "new"  → (doc7, [12, 45])
   "york" → (doc7, [13])
   13 == 12 + 1 → genuinely adjacent → a real phrase match.

Positions also enable proximity scoring beyond exact phrases: documents where query terms appear near each other are usually more relevant than those where they're paragraphs apart, even without exact adjacency. That's a meaningful ranking signal.

The cost is index size — you're storing an entry per term occurrence rather than per document, which is why compression matters so much. Delta encoding helps here too, since positions within a document are naturally close together and their gaps are small.

Some systems keep a separate unstemmed positional field for phrase matching, because stemming can break exact phrases — if "learning" stems to "learn" at index time, the phrase "machine learning" must be queried consistently or it silently fails.

🟡 Mid — Document-partitioned or term-partitioned? Justify it.

Document-partitioned, despite the apparent inefficiency of every query touching every shard.

The decisive reason is where intersection happens. With term-partitioning, a query for "database systems" has "database" on one shard and "systems" on another — so intersecting requires shipping an entire posting list across the network. For a common term that can be gigabytes, per query. Document-partitioning keeps intersection local: each shard intersects its own lists and returns only its top-k, which is kilobytes.

Document-partitionedTerm-partitioned
IntersectionLocal to each shardAcross the network
Load balanceEven — documents distribute uniformlyThe shard owning "the" is a permanent hotspot
Shard lossRecall degrades slightlyCertain terms become unsearchable

Load balance is the second reason. Term frequency is Zipfian, so term-partitioning produces wildly uneven shards — one holding "the" and "of" would be enormous and constantly hot, while others idle. Documents distribute evenly by construction.

Graceful degradation is the third: losing a document shard means missing some results, which users won't notice. Losing a term shard means queries containing that word return nothing — a visible, total failure for those queries.

The cost you accept is fan-out: every query hits every shard, so tail latency dominates (with 300 shards, ~95% of queries encounter some shard's p99). That's mitigated with hedged requests and partial results — and it's a much better problem to have than gigabyte network transfers.

The generalisable rule: partition so the expensive operation stays local, even if that means contacting more nodes.

🟡 Mid — Your index doesn't fit in memory. What do you do before adding machines?

Compress the postings — typically a 5–10× reduction, which is usually enough on its own:

Posting list: [17, 145, 892, 1043, 1099, ...]

1. DELTA ENCODING — store gaps rather than absolute IDs:
      [17, 128, 747, 151, 56, ...]
   Gaps are far smaller numbers, especially in dense lists.

2. VARIABLE-BYTE or PFOR encoding — small numbers use fewer bytes.
      a gap of 56 costs 1 byte, not 4.

Together: ~8-10 bytes per posting → ~1-2 bytes.
100 TB → 10-20 TB.

Then reduce what you store:

• Drop positions for fields that never need phrase search. Positions are often the majority of the index.
• Prune low-value postings — a term appearing once in a very long document contributes almost nothing to ranking and can be omitted.
• Tier by access frequency: hot shards in RAM, rarely-queried ones on SSD. Query distribution is Zipfian, so a small fraction of the index serves most traffic.
• Separate the fresh index — a small, frequently-updated index in memory merged with a larger, colder one.

Why this matters more than adding machines: RAM residency is what makes the sub-millisecond shard queries possible, and 30 million shard queries/s cannot be served from disk. Compression isn't an optimisation here — it's the difference between meeting the latency budget and not. Adding machines without compressing means paying for RAM you didn't need.

Also add skip lists over long posting lists so intersection can jump ahead rather than scanning — a large win when one query term is common and another is rare.

🔴 Senior — With 300 shards, why is tail latency your dominant problem?

Because a fan-out query completes only when the slowest shard responds, so you sample the tail of the latency distribution 300 times per query.

Each shard has p99 = 50 ms (99% of its responses are faster).

P(at least one of 300 shards is in its slow 1%)
   = 1 − 0.99³⁰⁰
   ≈ 95%

So roughly 95% of queries wait on some shard's p99. The SYSTEM's
median latency is governed by the SHARDS' p99 — the aggregate is far
worse than any individual component, and looking at per-shard
dashboards makes everything appear healthy.

Mitigations, in order of effectiveness:

1. Hedged requests. After the p95 elapses without a response, send a duplicate to a replica and use whichever returns first. Costs a few percent extra load and dramatically compresses the tail — the standard technique for exactly this problem.

2. Partial results. Return once 95% of shards have responded. Missing 1% of the corpus is invisible to users; a two-second wait is not. This requires accepting that results are approximate, which for search is entirely acceptable — nobody can verify they got every match.

3. Fewer, larger shards where memory allows — 100 shards instead of 300 reduces the exposure substantially (1 − 0.99¹⁰⁰ ≈ 63%).

4. Attack the per-shard p99 itself: the tail usually comes from GC pauses, disk reads on cache misses, and compaction competing for I/O. Fixing those helps every query rather than papering over the symptom.

The general lesson, which recurs throughout distributed systems: fan-out amplifies tails. Any request touching N services or shards is exposed to N chances of hitting a slow path, so the more you parallelise, the more the tail dominates — and mean-based capacity planning systematically under-provisions such systems.

🔴 Senior — How do you keep the index fresh when reindexing 10B documents takes days?

You never reindex everything — you use an LSM-style segmented index with tiered freshness.

The segmented structure:

New/updated documents → small in-memory segment (seconds)
   ↓ flush periodically
Small immutable on-disk segments (minutes)
   ↓ background merge
Larger segments (hours)
   ↓ background merge
The main index (days)

Deletes and updates are TOMBSTONES — an update is a delete plus an
insert, resolved at merge time. Queries consult all segments and
apply tombstones, so a document updated one second ago returns the
new version immediately.

This is precisely the LSM tree from the key-value store, for the same reason: writes become cheap appends, reads pay a bounded cost across several segments, and background compaction keeps that number small.

Tiered freshness by content type, because "fresh" means different things:

News / social      → a separate small "fresh index", rebuilt every few
                     minutes, merged into results at query time.
                     Small enough that full rebuilds are cheap.
Frequently-updated → re-crawled hourly to daily; incremental segments
Static archives    → monthly. Most of the corpus lives here.

Crawl scheduling drives freshness more than indexing does. Adapt re-crawl frequency to each page's observed change rate — a news homepage changes hourly, a 2015 blog post never will. Conditional GETs (ETag/If-Modified-Since) make checking nearly free, so you can check often and only pay to re-index when something actually changed.

The trade to state: more segments means slower queries (each must be consulted), while more aggressive merging means more background I/O competing with serving. That's the same compaction tuning problem as any LSM system, and it's why these engines need I/O headroom rather than running near capacity.

🏋️ Graded Exercises

Exercise 1 (Easy): 10B documents averaging 1,000 unique terms. Estimate the index size raw and compressed.
Solution 
POSTINGS
   10 × 10⁹ docs × 1,000 terms = 10¹³ postings

RAW
   docId 4 B + position 4 B + term frequency 2 B ≈ 10 B
   10¹³ × 10 B = 10¹⁴ B = 100 TB

COMPRESSED (delta encoding + variable-byte)
   ~1-2 B per posting
   10¹³ × 1.5 B ≈ 15 TB

REDUCTION: roughly 7x

Why the compression is decisive: at 64 GB per node, 100 TB needs ~1,600 nodes just to hold the index in RAM, while 15 TB needs ~240. Since 100,000 queries/s × 300 shards = 30M shard queries/s cannot be served from disk, RAM residency isn't optional — so compression directly determines whether the latency target is achievable at a sane cost.

Why delta encoding works so well here: posting lists are sorted document IDs, so gaps are small — and for common terms the lists are dense, making gaps smaller still. Variable-byte encoding then stores a gap of 56 in one byte instead of four. The compression is better exactly where the lists are longest, which is the ideal property.

Note this is a lower bound: real indexes also store field information, document metadata and auxiliary structures, so plan for meaningfully more than the posting-list figure alone.

Exercise 2 (Easy): Why is intersecting posting lists cheaper if you start with the rarest term?
Solution

Because the result of an intersection can never be larger than the smallest input, so starting small bounds all subsequent work.

Query: "the" AND "chlorofluorocarbon"

   "the"                 → 8,000,000,000 documents
   "chlorofluorocarbon"  →         4,000 documents

Start with "the":
   scan 8 billion entries, checking each against the other list.

Start with "chlorofluorocarbon":
   take 4,000 candidates, check each against "the" — and with skip
   lists you jump directly to the relevant region rather than
   scanning.

Roughly 2,000,000x less work for an identical result.

Skip lists make this even more effective: they let the intersection jump ahead within the long list rather than walking it, so checking 4,000 candidates against an 8-billion-entry list costs 4,000 × O(log n) rather than a linear scan.

The generalisable principle: in any multi-way intersection, order by selectivity — most selective first. It's the same instinct as a query planner choosing the most restrictive index first, and it applies to filtering pipelines generally: eliminate as much as possible as early as possible.

This is also why term rarity is worth storing: knowing each term's document frequency lets the query planner order the intersection without inspecting the lists.

Exercise 3 (Medium): Design the crawler frontier. How do you crawl 3,300 pages/s while staying polite?
Solution

The constraint drives the design: politeness means roughly one request per host per 1–2 seconds. So crawling 3,300 pages/s requires touching at least 3,300 distinct hosts concurrently — the bottleneck is host diversity, not bandwidth.

TWO-LEVEL FRONTIER:

  Front queues (priority):     F1 (high) ... Fn (low)
     URLs assigned by importance — PageRank, change rate, depth

  Back queues (politeness):    one FIFO queue PER HOST
     plus a heap of (next_allowed_time, host)

  A worker:
     1. pops the host with the earliest next_allowed_time
     2. if that time is in the future, waits
     3. takes the next URL from that host's queue
     4. sets next_allowed_time = now + delay(host)
     5. fetches

Why two levels: a single priority queue would repeatedly hand workers URLs from the same high-value host, which politeness then forces them to wait on — so throughput collapses while the crawler idles. Separating what to crawl next from which host may be contacted now is what makes both constraints satisfiable simultaneously.

Additional requirements:

• Cache robots.txt per host (with its own TTL) — fetching it per URL would double your request volume and be its own politeness violation.
• Honour Crawl-delay where specified, and back off on 429 or 5xx responses.
• Deduplicate URLs before enqueueing — canonicalise, strip tracking parameters, and use a Bloom filter of seen URLs (a false positive skips one page, which is harmless; false negatives don't occur, which is the guarantee direction you need).
• Defend against traps — depth limits, per-host page caps, and detection of URL patterns that generate infinitely (calendars, session IDs).
• Distribute by host hash so all URLs for one host are handled by one crawler node, which makes per-host rate limiting a purely local decision requiring no coordination.

That last point is the scaling insight: partitioning by host makes politeness enforceable without any distributed state.

Exercise 4 (Medium): Implement phrase search for "machine learning" given a positional index.
Solution 
def phrase_search(index, terms):
    """Find documents containing the terms as an adjacent phrase."""
    if not terms:
        return []

    # 1. Order by selectivity — start from the RAREST term.
    postings = sorted((index.postings(t) for t in terms),
                      key=len)
    # But we need the ORIGINAL order for adjacency, so keep both.
    lists = [index.postings(t) for t in terms]
    rarest = min(range(len(lists)), key=lambda i: len(lists[i]))

    # 2. Intersect on document ID (sorted lists → linear merge).
    candidates = set(d for d, _ in lists[rarest])
    for i, pl in enumerate(lists):
        if i == rarest:
            continue
        candidates &= set(d for d, _ in pl)
        if not candidates:
            return []

    # 3. For surviving candidates, check POSITION ADJACENCY.
    results = []
    for doc in candidates:
        pos_lists = [set(positions_for(pl, doc)) for pl in lists]
        # term i must appear at p+i for some starting position p
        for p in pos_lists[0]:
            if all((p + i) in pos_lists[i] for i in range(1, len(terms))):
                results.append(doc)
                break
    return results


def demo():
    # doc7: "... machine[12] learning[13] ..."   → phrase match
    # doc9: "machine[3] ... learning[80]"        → both present, NOT a phrase
    index = {
        "machine":  [(7, [12]), (9, [3])],
        "learning": [(7, [13]), (9, [80])],
    }
    def positions_for(pl, doc):
        return next(p for d, p in pl if d == doc)

    globals()['positions_for'] = positions_for
    class Idx:
        def postings(self, t): return index[t]
    out = phrase_search(Idx(), ["machine", "learning"])
    assert out == [7], out          # doc9 must be excluded
    print("ok — phrase search excludes non-adjacent co-occurrence")

if __name__ == "__main__":
    demo()

The three stages matter in order: intersect on document ID first (cheap, eliminates most), then check positions only for survivors (expensive, but on a small set). Reversing that would check positions across every document containing either term.

The demo asserts the property that matters: doc9 contains both words but 77 positions apart, so it must be excluded. That's exactly the case a position-less index gets wrong, and it's why "New York" would otherwise match "a new dress shop in York".

Production refinements: a bigram index ("machine learning" as a single term) for known-common phrases avoids the adjacency check entirely — one lookup, much faster, at the cost of index size. And stemming must be consistent between index and query time, or exact phrases silently fail; many engines keep a separate unstemmed field for phrase matching.

Exercise 5 (Hard): A query fans out to 300 shards, each with p99 = 50 ms. Compute the system's tail behaviour and fix it.
Solution 
P(a given shard responds within its p99) = 0.99
P(ALL 300 shards respond within p99)     = 0.99³⁰⁰ ≈ 0.049
P(at least one is slower)                ≈ 95%

So ~95% of queries wait on at least one shard's slow path. The
system's typical latency is set by the shards' p99, not their median —
and every per-shard dashboard looks healthy while user-facing latency
is terrible.

Fix 1 — hedged requests (the standard answer). After p95 elapses without a response, send a duplicate request to a replica of that shard and take whichever returns first.

Extra load: only requests exceeding p95 are duplicated → ~5% more
            shard queries.
Effect:     the tail now reflects min(two independent samples),
            which compresses it dramatically.

Fix 2 — partial results. Return once 95% of shards have replied, marking the result as approximate. Missing ~1% of the corpus is imperceptible to users; a two-second page load is not. Search is unusually suited to this because nobody can verify they received every match — the same "approximate is fine" judgement as HyperLogLog counts and approximate leaderboard ranks.

Fix 3 — reduce the fan-out. 100 larger shards instead of 300 gives 1 − 0.99¹⁰⁰ ≈ 63% exposure rather than 95%. Constrained by per-node memory.

Fix 4 — attack the per-shard p99 directly, which helps every query rather than masking the symptom. The usual causes are GC pauses (tune or use a low-pause collector), disk reads on cache misses (more RAM, better compression), and compaction competing for I/O (throttle it).

What I'd do: hedged requests plus partial results immediately — both are cheap and effective — while investigating the per-shard p99 as the durable fix. And I'd make sure monitoring shows end-to-end query latency prominently, since the per-shard view is exactly the misleading aggregate the observability lesson warns about.

Exercise 6 (Hard): Should you build this, or use Elasticsearch? Give the decision criteria.
Solution

Use Elasticsearch (or OpenSearch, Solr, Vespa) unless you have a specific reason not to. Building a search engine is a multi-year effort, and the existing ones implement everything discussed here — inverted indexes, document sharding, BM25, compression, incremental segments — well and reliably.

Use an existing engine when:

• The corpus is bounded and trusted (site search, product catalogue, logs, documents) — no crawler needed, no adversarial SEO.
• Scale is up to hundreds of millions of documents, which Elasticsearch handles comfortably.
• Standard relevance (BM25 plus some custom boosting) is good enough.
• You need it working in weeks rather than years.

Consider building — or heavily customising — when:

• Web scale with an adversarial environment. Crawling the open web means SEO spam, cloaking and link farms actively gaming your ranking. That arms race is unique to web search and isn't something a general engine addresses.
• Ranking is your core product differentiator and requires deep ML integration in the serving path — Vespa exists precisely for this middle ground.
• Extreme scale (tens of billions of documents) where per-node efficiency directly determines feasibility and cost.
• Unusual query semantics that don't map onto an inverted index — vector-only search, for instance, is better served by a purpose-built vector database.

The honest cost of building: not just the index, but crawling, deduplication, spam detection, relevance tuning, incremental updates, sharding and rebalancing, and years of operational learning. Google's search quality comes largely from decades of ranking refinement, not from the inverted index — which is the commodity part.

The middle path is usually right: use an existing engine for retrieval, and build your own re-ranking layer on top. That's where domain-specific value lives, and it's a fraction of the effort. This mirrors the recommendation-system funnel: standard retrieval, custom ranking.

Being willing to say "don't build this" is a strong signal in an interview — it shows you're evaluating engineering cost against benefit rather than demonstrating that you can design one.

🎯 Key Takeaways

  • Three decoupled stages — crawling (politeness/coverage), indexing (batch throughput), serving (latency) — connected only through the index.
  • Document-partition the index, not term-partition: intersection stays local, load is even, and shard loss degrades recall gracefully.
  • Partition so the expensive operation stays local, even if that means contacting more nodes.
  • Compression is not optional — delta encoding plus variable-byte turns 100 TB into 15 TB, which is what makes RAM residency and the latency budget possible.
  • Start intersections from the rarest term, and use skip lists to jump ahead — often a millionfold reduction in work.
  • Positions enable phrase search; without them "New York" matches "new dress in York".
  • Fan-out amplifies tails: with 300 shards at p99=50 ms, ~95% of queries hit some shard's slow path. Hedged requests and partial results are the fixes.
  • Ranking is a funnel — cheap BM25 across candidates, expensive ML re-rank on the top ~100. The same shape as recommendations.
  • Never rebuild the whole index — LSM-style segments with background merges and tombstoned deletes, plus a small fresh index for recent content.
  • Politeness is a hard constraint: crawl more hosts concurrently rather than hitting any host harder, and partition crawlers by host so rate limiting needs no coordination.
  • Deduplicate at both URL and content level — SimHash catches near-duplicates that exact hashing misses.
  • Usually, don't build this. Use an existing engine for retrieval and build your own re-ranking layer, where the domain value actually is.
