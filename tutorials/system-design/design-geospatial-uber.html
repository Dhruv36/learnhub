Design Geo-Spatial Apps / Uber Case Study

What you'll master: why B-tree indexes cannot answer proximity queries, how geohashing reduces 2D space to a sortable 1D key and where that reduction leaks, choosing between geohash, quadtree and S2/H3, sizing a write path that takes hundreds of thousands of location updates per second, and the atomic claim that stops two riders being matched to one driver.

Prerequisites: Estimation, Caching (location data is ephemeral), Concurrency Control (the matching race), Consistent Hashing (regional sharding).

🎯 What this problem is really testing. Whether you recognise that proximity is not a range query. Two points close in 2D space are not necessarily close in either latitude or longitude ordering, so no combination of ordinary indexes answers "what's near me" efficiently. The second signal is noticing this system has two completely different workloads sharing a datastore — a firehose of ephemeral location writes, and a small number of latency-critical, correctness- critical matching operations. Designs that treat them the same fail on one or the other.

Questions worth asking:

"How fresh must driver locations be?"  → ~5 s is fine; a car moving
   at 50 km/h travels 70 m in 5 s, which barely affects matching.
"Do we need historical GPS trails?"    → Yes, for billing/disputes,
   but on a SEPARATE async path — never in the matching hot path.
"Matching radius?"                     → Adaptive: 500 m in a city,
   several km rurally. A fixed radius fails at both extremes.
"Is this global or per-city?"          → Rides are LOCAL. That single
   fact makes the whole system shardable by geography.

2. Estimation: Two Very Different Workloads

Assume 5M active drivers, 1M rides/hour at peak.

LOCATION WRITES — the firehose
   5M drivers × 1 ping / 4 s = 1,250,000 writes/s
   → CONSEQUENCE: this is enormous. It immediately rules out a
     durable, indexed database on the hot path — 1.25M/s of indexed
     writes is far beyond any relational primary, and the data is
     worthless within seconds anyway.
   → Points to an IN-MEMORY store with TTLs.

Storage IF we persisted every ping:
   1.25M/s × 100 B × 86,400 = ~10 TB/day
   → CONSEQUENCE: persist to cheap object storage via an async
     stream for billing/analytics; never into the matching index.

MATCHING QUERIES — small but critical
   1M rides/hour = ~280/s  (peak ×3 ≈ 850/s)
   → CONSEQUENCE: three ORDERS OF MAGNITUDE fewer than location
     writes. So optimise the write path for throughput and the
     query path for latency and correctness — they are not the
     same system.

WORKING SET
   5M drivers × ~100 B (id, lat, lon, status, updated_at) = 500 MB
   → CONSEQUENCE: the entire live index fits in memory comfortably.
     This is a THROUGHPUT problem, not a storage problem.

The 1,250,000 : 850 ratio is the number to say out loud — it's what justifies treating location updates as disposable, in-memory, best-effort data while treating matching as a careful, transactional operation.

3. Why Ordinary Indexes Fail

❌ SELECT * FROM drivers
   WHERE lat BETWEEN 37.76 AND 37.79
     AND lon BETWEEN -122.43 AND -122.40;

With a B-tree on lat and another on lon, the database must:
   - scan every driver in a 3 km-tall horizontal BAND of the planet
   - scan every driver in a 3 km-wide vertical BAND of the planet
   - intersect two enormous result sets

A composite index (lat, lon) is no better: it sorts by lat first, so
all longitudes at a given latitude are adjacent — points 10,000 km
apart sit next to each other in the index.

THE ROOT ISSUE: proximity in 2D does not correspond to adjacency in
any 1D sort order. That is what spatial indexes exist to fix.

4. The Core Design Decision: The Spatial Index

StructureHow it worksTrade-off
GeohashInterleave latitude and longitude bits, base32-encode → a string where a shared prefix means geographic proximitySimplest — works with any string index, sortable, human-inspectable. Fixed grid, so it adapts poorly to density; boundary problems (below).
QuadtreeRecursively split space into 4 quadrants, subdividing further only where point density is highAdapts to density — fine cells in Manhattan, coarse cells in Wyoming. Costs a dedicated in-memory structure that must be rebalanced as drivers move.
S2 (Google)Projects the sphere onto a cube, then uses a Hilbert curve for the 1D orderingBetter locality than geohash (the Hilbert curve preserves proximity more faithfully), and cells have more uniform area. More complex.
H3 (Uber)Hexagonal gridHexagons have uniform neighbour distance — all 6 neighbours are equidistant, unlike a square's 4 edge- and 4 corner-neighbours. Genuinely better for radius queries, which is why Uber built it.

Geohash precision, so the choice of length isn't arbitrary:

length   cell size (approx, at the equator)
   4      ~39 km × 20 km      — a metro area
   5      ~5 km × 5 km        — a district
   6      ~1.2 km × 0.6 km    — a neighbourhood  ← typical for matching
   7      ~150 m × 150 m      — a block
   8      ~38 m × 19 m        — a building

Pick the length so a cell is roughly your search radius: too coarse
and you scan thousands of irrelevant drivers; too fine and you must
query many cells to cover the radius.
⚠️ The boundary problem, which is the classic follow-up. Two drivers 10 metres apart on opposite sides of a cell boundary have completely different geohash prefixes — the 1D projection tears at grid lines. A naive prefix query misses them. The fix is to query the target cell plus all 8 neighbours, then filter by true distance. Any answer that relies on prefix matching alone is wrong, and interviewers ask precisely because it's the non-obvious failure of an otherwise elegant trick.

5. The Location Write Path

Driver app ──every 4s──► Location Ingest ──► Redis (in-memory index)
                              │
                              └──► Kafka ──► object storage
                                            (trails for billing,
                                             analytics, disputes)

Using Redis GEO commands (which use geohashing internally):
   GEOADD drivers:sf  -122.4194 37.7749  driver:8821
   EXPIRE handled per-driver via a separate key, or by sweeping
   stale entries — a driver that stops pinging must disappear.

Why in-memory and not a database:
   - 1.25M writes/s of indexed data is beyond a durable store
   - only the LATEST position matters; history has a separate path
   - a lost ping is harmless — another arrives in 4 seconds
   → this is exactly the "ephemeral, loss-tolerant" data class from
     the realtime lesson, and treating it as precious is the most
     expensive mistake available here.

Reduce the write volume rather than scaling to absorb it — the highest-leverage optimisations are on the client:

• Adaptive ping rate: a stationary driver waiting at a rank doesn't need 4-second updates. Ping on significant movement, or back off to 30 seconds when idle. This alone can cut volume several-fold.
• Batch a few positions per request on poor networks.
• Only index available drivers. A driver mid-trip cannot be matched, so they don't belong in the matching index at all — keep their location on the trip-tracking path instead.

6. Deep Dive: Matching, and the Race That Breaks It

1. Rider requests a ride at (lat, lon).
2. Compute the geohash cell + its 8 neighbours.
3. Query available drivers in those cells (Redis GEORADIUS or a
   prefix scan).
4. Filter: vehicle type, rating, driver preferences.
5. RANK by estimated pickup TIME, not straight-line distance —
   a driver 200 m away across a river is further than one 1 km away
   on the same road. This needs a routing service.
6. Offer to the best candidate; on decline or timeout (~15 s), offer
   to the next.
7. On acceptance, CLAIM the driver atomically.

Step 7 is where correctness lives. Two riders searching simultaneously will see the same nearby driver, and both may offer to them:

❌ Check then assign 
if driver.status == 'available':
    driver.status = 'assigned'
    create_trip(rider, driver)

Two requests both read 'available',
both write 'assigned', both create
a trip.

One driver, two riders. The driver
sees two trips; one rider is
stranded with a phantom booking.
✅ Atomic conditional claim 
UPDATE drivers
   SET status='assigned',
       trip_id=$new_trip
 WHERE driver_id=$id
   AND status='available';

-- 0 rows → someone got there
--          first → offer the
--          next candidate

Or Redis: SET driver:{id}:claim
$trip NX EX 30

This is the check-then-act race from concurrency control, and the fix is the same: fold the check into the write so the database arbitrates. The claim should also carry a short TTL — if the trip creation fails after claiming, the driver must be released automatically rather than being stuck as "assigned" forever.

7. Deep Dive: Density Variance and Adaptive Radius

A FIXED radius fails at both extremes:

   Manhattan, 1 km radius   → 800 drivers returned. Wasteful to rank,
                              and unnecessary — the nearest is 100 m away.
   Rural, 1 km radius       → 0 drivers. The rider gets "no cars
                              available" when one is 8 km away and
                              perfectly willing.

ADAPTIVE SEARCH — expand until you have enough candidates:
   radius = 500 m
   while candidates < 10 and radius <= 15 km:
       query(radius); radius *= 2

Cheap in dense areas (one query), and degrades gracefully in sparse
ones. Cap the radius so you don't offer a rider a driver 40 minutes
away.

The structural alternative is a quadtree or H3, where cell size adapts to density automatically — dense areas subdivide further, so a single cell contains a workable number of drivers everywhere. That's precisely why Uber built H3: with hexagons, all six neighbours are equidistant, so expanding a search ring is uniform in every direction, unlike a square grid where diagonal neighbours are 1.41× further than edge neighbours.

8. Bottlenecks and Scaling

What breaksFix
1.25M location writes/sShard by geography — rides are local, so a city maps to a shard and no query ever crosses shards. This is the property that makes the system scale linearly
Hot shard in a dense citySub-shard by geohash prefix within the city; the busiest metros get their own clusters
Airport / stadium surgeA hot cell — thousands of drivers in one geohash. Use finer cells there, or a quadtree/H3 that subdivides by density automatically
Ranking cost (routing per candidate)Pre-filter by straight-line distance, then call routing for only the top ~10 candidates. Cache route estimates per cell pair
Stale drivers in the indexTTL every entry; a driver who loses signal must vanish rather than being offered rides they can't see
Cross-border / cross-shard ridesRare but real — query neighbouring shards when the search radius crosses a boundary

Geographic sharding is the strongest property of this design. Unlike most systems, where sharding forces cross-shard queries somewhere, here the business domain is inherently local: nobody in London is matched with a driver in Tokyo. That means shards are genuinely independent, a regional outage affects only that region, and capacity can be provisioned per city against local demand patterns.

Interview Questions

🟢 Beginner — Why can't you use a normal database index for "find nearby drivers"?

Because proximity in two dimensions doesn't correspond to adjacency in any one-dimensional sort order, and B-tree indexes are one-dimensional.

SELECT * FROM drivers
 WHERE lat BETWEEN 37.76 AND 37.79
   AND lon BETWEEN -122.43 AND -122.40;

With separate indexes on lat and lon, the database scans everyone in
a 3 km-tall band spanning the whole planet, everyone in a 3 km-wide
band spanning the whole planet, and intersects two huge sets.

A composite index on (lat, lon) doesn't help either: it sorts by latitude first, so all longitudes at a given latitude are adjacent — two points 10,000 km apart end up next to each other in the index, while two points 10 m apart on either side of a latitude value can be far apart.

The fix is a spatial index that maps 2D proximity into 1D adjacency. Geohashing does this by interleaving the bits of latitude and longitude, so nearby points share a prefix and "find nearby" becomes "find keys with this prefix" — which ordinary indexes handle well.

The interesting part is that this reduction is lossy: you cannot perfectly flatten a plane onto a line, so the mapping tears at cell boundaries. Two adjacent points can land in different cells with unrelated prefixes, which is why real implementations query the surrounding cells too.

🟢 Beginner — What is geohashing, and what's its main weakness?

Geohashing encodes a (latitude, longitude) pair into a single string by recursively halving the world — each bit says "east or west half", "north or south half" — interleaving the two dimensions and base32-encoding the result.

(37.7749, -122.4194) → "9q8yyk8yu"     San Francisco

KEY PROPERTY: nearby points share a prefix.
   "9q8yy" and "9q8yz" are geographically close.
Precision is set by length:
   5 chars ≈ 5 km cell · 6 ≈ 1.2 km · 7 ≈ 150 m

The main weakness is the boundary problem. Two drivers 10 metres apart, sitting on opposite sides of a cell boundary, can have completely different prefixes — the 1D projection tears along grid lines. A prefix-only query would report no nearby driver while one is across the street.

The fix: query the target cell and all 8 neighbouring cells, then compute true distances and filter. Neighbour computation is a standard geohash operation.

A second weakness: the grid is fixed, so cells contain wildly different numbers of drivers — hundreds in Manhattan, zero in the countryside. That's what motivates density-adaptive structures like quadtrees, or Uber's H3 hexagonal grid where all six neighbours are equidistant (unlike a square grid, where diagonal neighbours are 1.41× further than edge neighbours).

🟡 Mid — 5M drivers ping every 4 seconds. Design the write path. 
5,000,000 / 4 s = 1,250,000 location writes/s

What that number rules out: any durable, indexed database. 1.25M indexed writes/s is far beyond a relational primary, and it would be an absurd amount of infrastructure for data that is worthless within seconds.

What the data's properties allow instead: only the latest position matters, and a lost ping is harmless because another arrives in four seconds. That's ephemeral, loss-tolerant data — so:

Driver app → Location Ingest (stateless, horizontally scaled)
                 ├──► REDIS: GEOADD drivers:{region} lon lat driver_id
                 │           with a TTL so silent drivers disappear
                 └──► KAFKA → object storage (trails for billing,
                              disputes, analytics — NOT the hot path)

Shard by geography. Rides are local, so a city or region maps to a shard and no proximity query ever crosses shards. This is what makes the write path scale linearly — and it's unusual, since most sharded systems have some cross-shard access pattern.

Reduce the volume rather than just absorbing it — the highest-leverage changes are on the client:

• Adaptive ping rate: a stationary driver at a taxi rank needs 30-second updates, not 4-second ones. Ping on meaningful movement. This can cut total volume several-fold for free.
• Only index available drivers: someone mid-trip can't be matched, so they don't belong in the matching index.
• Batch positions on poor mobile networks.

TTL every entry. A driver who loses signal must vanish from the index automatically — the self-healing pattern from presence, and much more reliable than expecting an explicit "going offline" message that a dying connection won't deliver.

🟡 Mid — Two riders request a ride simultaneously and the nearest driver is the same. What happens?

Without care, both get assigned the same driver — the check-then-act race:

Rider A: read driver 42 → status 'available'
Rider B: read driver 42 → status 'available'     ← both read before
Rider A: write status='assigned', create trip A     either writes
Rider B: write status='assigned', create trip B

One driver, two trips. The driver's app shows two pickups; one rider
waits for a car that will never come.

The fix is an atomic conditional claim — fold the check into the write so the database arbitrates:

UPDATE drivers
   SET status='assigned', trip_id=$trip, claimed_at=now()
 WHERE driver_id=$id AND status='available';

rows affected = 1 → we won; confirm the trip
rows affected = 0 → someone else claimed them; offer the next candidate

Or in Redis, SET driver:42:claim $trip NX EX 30 — NX makes it succeed only if unset, which is the same mutual exclusion.

The claim must expire. If trip creation fails after the claim — a crash, a timeout — an un-TTL'd claim leaves the driver permanently "assigned" and invisible to all matching, which is a slow leak of supply. A 30-second TTL that's extended on successful trip creation handles it.

The wider design point: matching should be an offer-based flow rather than an assignment. The system offers a ride, and the driver accepts within a timeout; the claim is taken at acceptance, not at offer time. That naturally handles decline, timeout and the concurrent-request case — the loser simply moves to the next candidate, and the rider never sees the churn.

🔴 Senior — Manhattan has 800 drivers per square km; rural Montana has one per 50 km². Design for both.

A fixed radius and a fixed cell size fail at both extremes, in opposite directions:

1 km radius in Manhattan → 800 candidates. Wasteful to rank (each
   needs a routing call), and pointless — the nearest is 100 m away.
1 km radius in Montana   → zero candidates. The rider is told "no cars
   available" while a willing driver sits 8 km away.

Solution 1 — adaptive expanding search (simple, works with geohash):

radius = 500 m
while len(candidates) < 10 and radius <= 15 km:
    candidates = query(cell_and_neighbours(radius))
    radius *= 2

One query in dense areas; a few in sparse ones. Cap the maximum radius so you never offer a rider a driver 40 minutes away — beyond some distance, "no cars available" is the honest answer.

Solution 2 — a density-adaptive structure (better). A quadtree subdivides only where density is high, so a leaf cell holds a workable number of drivers everywhere — fine cells in Manhattan, one enormous cell covering rural Montana. The cost is maintaining a mutable tree as millions of drivers move, and rebalancing as density shifts through the day.

Solution 3 — H3 hexagons at variable resolution. This is what Uber actually built. Hexagons matter because all six neighbours are equidistant, whereas a square cell has 4 edge neighbours and 4 corner neighbours that are 1.41× further — so expanding a search ring on a square grid covers an uneven area, while on hexagons it's uniform. Uber assigns different H3 resolutions per region based on observed density.

Beyond the index — the operational differences matter too: matching parameters should be per-market, not global. Acceptable pickup time in Manhattan is 3 minutes; in rural Montana, 15 minutes is normal and the product should communicate that rather than failing. Surge pricing, driver repositioning incentives and even the ping rate can differ per market. Density isn't just a technical parameter, it's a product one — and recognising that the same code with per-market configuration beats either a global compromise or separate implementations is the senior framing.

🔴 Senior — Design the sharding strategy. What breaks at a city boundary?

Shard by geography — and this system has an unusually favourable property: the business domain is inherently local. Nobody in London is matched with a driver in Tokyo, so shards are genuinely independent and no query needs to cross them in the common case.

Shard key: a coarse geohash prefix (or an H3 cell at low resolution)
   shard "9q8" → San Francisco Bay Area
   shard "dr5" → New York metro

Each shard holds: the driver location index, available-driver state,
and active trips for that region. A city can be its own cluster,
sized against its own demand curve.

Benefits beyond throughput: a regional outage is contained to that region; capacity is provisioned per city against local peak patterns (Friday night in one city isn't Friday night in another); and data residency requirements are naturally satisfied because a market's data stays in its region.

What breaks at boundaries — three distinct cases:

1. A rider near the edge of a shard. Their search radius extends into the neighbouring shard, where genuinely closer drivers may be. Fix: detect when the radius crosses a boundary and query the adjacent shard(s) too, merging results. Rare enough that the extra latency is acceptable, and you can make boundaries follow low-density areas so it's rarer still.

2. A trip that crosses shards — pickup in one region, drop-off in another. The trip must have a single owner: assign it to the pickup shard for its whole lifetime, and let the driver's location updates route there even after they've crossed the boundary. Splitting ownership mid-trip is where consistency bugs live.

3. A driver crossing a boundary mid-shift. They must be removed from one index and added to the other — and the handover window is where a driver can be briefly invisible or briefly present in both. Better to make it idempotent: the driver's location update writes to whichever shard their current cell belongs to, with a TTL removing them from the old one automatically. Don't build an explicit handover protocol when expiry does it for free.

What I'd avoid: sharding by driver ID or a hash. It distributes load beautifully and destroys locality — every proximity query would become a scatter-gather across every shard, which is the one thing geographic sharding exists to prevent. This is the same lesson as shard-key selection in the scaling ladder: even distribution is worthless if it breaks the dominant query.

Exercise 2 (Easy): Two drivers are 50 m apart but their geohashes are 9q8yy and 9q8yz — actually they're 9q8yy and dr5ru. Explain.
Solution

They're on opposite sides of a major grid boundary. Geohash divides the world recursively, and at each level of division there's a line where the encoding changes completely rather than incrementally. Two points straddling such a line share no prefix at all, despite being metres apart.

9q8yy → western US
dr5ru → eastern US

These prefixes differ from the FIRST character, so the points fall on
opposite sides of a top-level division. The 1D projection of 2D space
tears along these lines: adjacency in space is not preserved.

Why it happens: you cannot map a plane onto a line while preserving all proximity relationships — some neighbours must become distant in the 1D ordering. Geohash's bit-interleaving keeps most nearby points close in the encoding, but the tears are unavoidable, and they're worst at high-level boundaries (the equator, the prime meridian, and major grid lines).

The fix: never rely on prefix matching alone. Compute the target cell's 8 neighbours using geohash neighbour arithmetic, query all nine cells, then filter by true great-circle distance. The neighbour computation handles the tears explicitly rather than hoping the encoding preserves adjacency.

Why alternatives are better here: S2 uses a Hilbert curve, which preserves locality more faithfully than geohash's simple bit-interleaving (fewer and less severe tears), and H3's hexagons give uniform neighbour distances in all six directions. Both still require neighbour queries — the problem is fundamental to dimensional reduction — but they make the failure less pronounced.

Exercise 3 (Medium): Implement the nearby-driver query including neighbour cells and distance filtering.
Solution 
import math

def haversine_m(lat1, lon1, lat2, lon2):
    """Great-circle distance in metres."""
    R = 6_371_000
    p1, p2 = math.radians(lat1), math.radians(lat2)
    dp = math.radians(lat2 - lat1)
    dl = math.radians(lon2 - lon1)
    a = (math.sin(dp/2)**2
         + math.cos(p1) * math.cos(p2) * math.sin(dl/2)**2)
    return 2 * R * math.asin(math.sqrt(a))


def find_nearby(redis, geohash_lib, lat, lon, radius_m=500,
                min_results=10, max_radius_m=15_000):
    """Adaptive expanding search over a cell + its 8 neighbours."""
    while True:
        precision = precision_for_radius(radius_m)   # 6 -> ~1.2km cells
        centre = geohash_lib.encode(lat, lon, precision)

        # THE CRITICAL PART: the centre cell alone misses drivers just
        # across a boundary. Query all 9 cells.
        cells = [centre] + geohash_lib.neighbours(centre)

        candidates = []
        for cell in cells:
            for driver_id, dlat, dlon in redis.members(f"geo:{cell}"):
                d = haversine_m(lat, lon, dlat, dlon)
                if d <= radius_m:                    # true distance filter
                    candidates.append((driver_id, d))

        if len(candidates) >= min_results or radius_m >= max_radius_m:
            candidates.sort(key=lambda c: c[1])
            return candidates[:50]                   # cap before ranking

        radius_m *= 2                                # expand and retry


def demo():
    # Points on opposite sides of a cell boundary must both be found.
    # Two coordinates ~50m apart chosen to straddle a boundary:
    a = (37.77490, -122.41940)
    b = (37.77535, -122.41940)
    assert haversine_m(*a, *b) < 60, "test points should be ~50m apart"
    # Distance filtering must reject a point outside the radius.
    far = (37.80000, -122.41940)
    assert haversine_m(*a, *far) > 2000
    print("ok — haversine + boundary-straddling test points")

if __name__ == "__main__":
    demo()

The three things this gets right:

1. Nine cells, not one. Querying only the centre cell misses drivers just across a boundary — the single most common bug in naive implementations.

2. True distance filtering after the cell query. A geohash cell is rectangular and the search area is circular, so cell membership over-selects at the corners. Haversine gives the actual great-circle distance.

3. Adaptive radius with a cap. Handles Manhattan and Montana with the same code, while refusing to offer a driver 40 minutes away.

What comes next: these candidates are ranked by straight-line distance, which is only a pre-filter. The top ~10 should then be scored by estimated pickup time from a routing service — a driver 200 m away across a river is much further in practice. Routing calls are expensive, which is exactly why you cap the candidate list first.

In production, Redis GEOSEARCH does the cell arithmetic and distance filtering natively; the manual version above is what you'd sketch in an interview to show you understand the mechanics.

Exercise 4 (Medium): A driver loses network signal mid-shift. What should happen, and how?
Solution

They must disappear from the matching index promptly — otherwise riders are matched to a driver who can't receive the request, and the ride fails after a 15-second timeout while the rider waits.

The mechanism: TTL, not explicit offline signals.

Every location update refreshes a per-driver expiry:
   SET driver:{id}:alive 1 EX 15      -- refreshed every ping (~4 s)

Missing pings → the key expires → the driver drops out of the
available set automatically.

Why not an explicit "going offline" message: a driver losing signal cannot send one. Exactly the case you need to handle is the case where the signal is unavailable. This is the same self-healing reasoning as presence in realtime apps — TTLs handle silent failure, explicit messages handle only graceful exit.

Choosing the TTL is a trade:

Too short (8 s)  → a brief tunnel or lift drops them from the index,
                   costing the driver rides and the platform supply.
Too long (60 s)  → riders are matched to unreachable drivers, and the
                   ride fails 15 s later.
~15-20 s (3-5 missed pings) is the usual balance.

Different handling if a trip is in progress, which is the important distinction: a driver mid-trip who loses signal must not have the trip cancelled — they're driving through a tunnel and will reappear. Keep the trip active, show the rider "reconnecting", and buffer location updates on the device for upload when signal returns (so the trip's GPS trail and fare stay accurate). Only escalate after a much longer silence, with a support path rather than automatic cancellation.

And on reconnect: the driver's app should re-register and upload buffered positions. Since only the latest position matters for matching, but the full trail matters for billing, those go down the two different paths — the same split as the main write-path design.

Exercise 5 (Hard): A stadium empties: 5,000 riders request within 2 minutes in one geohash cell. Trace the failure and fix it.
Solution 
5,000 requests / 120 s ≈ 42 matching requests/s in ONE cell,
against a normal city-wide rate of a few hundred per second.

What breaks, in order:

1. A hot cell. Every request queries the same geohash cell, so one shard — one Redis node — takes all of it. Adding shards doesn't help, because the cell maps to one place. This is the hot-key problem again.

2. Claim contention. Thousands of riders compete for hundreds of drivers, so most atomic claims fail and retry against the next candidate. Wasted routing calls, and rising latency.

3. Routing service overload. Ranking by pickup time means a routing call per candidate. 5,000 riders × 10 candidates = 50,000 routing calls in two minutes.

4. Genuine supply shortage. Even perfectly implemented, there may be 300 drivers for 5,000 riders — an inherent mismatch that no technical fix resolves.

Fixes, technical first:

• Sub-shard the hot cell — split it into finer cells (higher geohash precision) so load spreads across nodes, or replicate the cell's driver set across several Redis replicas for reads.
• Batch the matching. Instead of 5,000 independent greedy searches, run matching in short windows (say every 2 s) and solve the assignment for the whole batch — a global assignment produces better pairings and eliminates the claim contention entirely, because each driver is assigned once by the batch rather than raced over.
• Cache routing estimates per (cell, cell) pair — during a stadium exit, thousands of riders are at effectively the same origin, so the ETA to a given driver cell is reusable.
• Pre-scale. Stadium schedules are known in advance; pre-warm capacity and pre-position supply incentives.

Then the product fixes, which matter more: surge pricing to attract drivers and moderate demand; designated pickup zones so riders are batched to a few points rather than scattered (this also makes routing cacheable and the pickups faster); queueing with honest wait estimates rather than failures; and suggesting alternatives (walk 5 minutes to a quieter zone, or use transit).

The framing: a stadium exit is a demand-supply imbalance, not primarily an engineering failure. The system should degrade honestly — queue with accurate ETAs — rather than time out or report "no cars available" while thousands of people are standing there. Recognising that the best fix is batched assignment plus product measures, rather than scaling the greedy path harder, is the senior answer.

Exercise 6 (Hard): Should driver locations be strongly or eventually consistent? Justify with the failure modes of each.
Solution

Eventually consistent — emphatically — and the reasoning is that the data is stale by physics before consistency ever becomes the limiting factor.

A car at 50 km/h travels ~14 m per second.
Even with PERFECTLY consistent reads, a location is:
   - 0-4 s old (ping interval)      → up to 56 m stale
   - plus network latency
   - plus GPS accuracy of 5-20 m

So the position is already tens of metres wrong. Adding strong
consistency to a value that is inherently approximate buys nothing
and costs latency and availability on 1.25M writes/s.

Failure modes of strong consistency here: every location write would need quorum acknowledgement, multiplying the cost of the highest-volume operation in the system; writes would fail during partitions, so drivers would vanish from the index precisely when the network is unhealthy; and latency would rise on a path where 1.25M/s makes every millisecond expensive. You'd pay heavily for precision the GPS itself doesn't provide.

Failure modes of eventual consistency — and why they're acceptable: a rider might see a driver's position a few seconds out of date (invisible, since the map updates continuously), or briefly see a driver who has just gone offline (handled by TTLs and by the claim failing). Both are self-correcting within seconds.

But the matching decision must be strongly consistent, and this is the distinction that makes the answer complete:

Driver LOCATION       → eventually consistent, in-memory, TTL'd,
                        loss-tolerant. Best effort.
Driver AVAILABILITY   → LINEARIZABLE. The claim
   ("is this driver assigned?")   must be atomic, or two riders get
                        the same driver.
TRIP state            → strongly consistent, durable. Money and
                        safety depend on it.

This is per-operation consistency from CAP: the same system legitimately uses different guarantees for different data based on the cost of being wrong. A stale location costs nothing; a double-assigned driver costs a failed ride and a support ticket; a lost trip record costs money and potentially safety.

Choosing one global consistency level — the classic mid-level mistake — would mean either paying quorum costs on 1.25M writes/s of disposable data, or racing on the one operation that genuinely can't tolerate it.

🎯 Key Takeaways

  • Proximity isn't a range query. 2D closeness doesn't map to adjacency in any 1D sort, which is why B-tree indexes on lat/lon fail.
  • Geohashing interleaves lat/lon bits so nearby points share a prefix — turning proximity into prefix matching.
  • Always query the cell plus its 8 neighbours, then filter by true distance. The 1D projection tears at boundaries.
  • Pick geohash precision to match your search radius — length 6 (~1.2 km) is typical for matching.
  • Two workloads, three orders of magnitude apart: 1.25M location writes/s versus ~850 matching queries/s. Optimise them separately.
  • Location data is ephemeral and loss-tolerant — in-memory with TTLs, never a durable indexed store. Trails go down a separate async path.
  • Reduce writes at the client with adaptive ping rates; it's the cheapest large reduction available.
  • The driver claim must be an atomic conditional update with a TTL, or two riders get the same driver and a failure leaves them stuck.
  • Rank by estimated pickup time, not straight-line distance — and cap the candidate list first, because routing calls are expensive.
  • Adaptive radius or a density-adaptive structure (quadtree, H3) — a fixed radius returns 800 candidates in Manhattan and zero in Montana.
  • Shard by geography. The domain is inherently local, so shards are genuinely independent — unusually favourable, and destroyed by hash-based sharding.
  • Consistency per operation: locations eventually consistent, availability linearizable, trips durable.
