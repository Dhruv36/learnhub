Migration Strategies at Scale Senior / Staff

What you'll master: moving a live system without downtime or data loss — the six-phase database migration and why each phase is independently reversible, shadow reads as the highest-leverage risk reduction available, backfilling billions of rows without destroying production, the dual-write consistency problem that makes naive migrations silently wrong, and the organisational failure modes that kill more migrations than technical ones.

Prerequisites: Expand/contract, CDC, Idempotency, Microservices (strangler fig). Pairs with Trade-off Driven Design.

🎯 What this topic is really testing. Whether you think in reversible steps. Almost every real system change is a migration, and the difference between a senior and a mid-level engineer here is that the senior never enters a state they can't back out of. The second signal is verification: shadow reads on real production traffic catch the class of bug that no amount of testing on synthetic data will, and skipping that step is the most common cause of migration incidents.

1. Why Migrations Are Their Own Discipline

Designing from scratch:  you control everything, nothing is live.
Migrating:               there is real traffic, real data, real
                         money, and no maintenance window.

The constraints that make it hard:
   - the system must work at EVERY intermediate step
   - the data must never be lost or silently corrupted
   - you must be able to REVERSE at any point
   - it takes weeks or months, so it must survive team changes,
     deploys, incidents and shifting priorities
   - the old and new systems must coexist and agree

Interviews ask "design X". Staff engineers mostly do "move X while
it is running", which is strictly harder.

2. The Six-Phase Database Migration

1. EXPAND      deploy the new store; start DUAL-WRITING to both.
                 Old remains the source of truth. Reversible: stop
                 writing to new.

2. BACKFILL    copy historical data old → new, in batches, throttled.
                 Reversible: truncate new; nothing user-facing changed.

3. VERIFY      SHADOW READS — read from both, compare, serve the OLD
                 answer. Log every discrepancy. Reversible: it's
                 read-only observation.

4. CUTOVER     switch reads to new, gradually (1% → 10% → 50% → 100%)
                 behind a flag. Writes still go to BOTH.
                 Reversible: flip the flag back, instantly.

5. SOAK        run on new for a defined period while still
                 dual-writing. Reversible: the old store is current.

6. CONTRACT    stop dual-writing; decommission old after a grace
                 period. THE FIRST IRREVERSIBLE STEP — so it comes
                 last, and only after evidence.

The property that makes this safe is that steps 1–5 are all reversible. You can abandon the migration at any point up to contraction with no user impact. That's what lets you take it slowly and stop if something looks wrong — as opposed to a big-bang cutover, where the only options are forward or a painful restore.

3. Deep Dive: Shadow Reads — The Highest-Leverage Step

❌ Backfill then cut over 
Tests pass on synthetic data.
The backfill completed.
Cut over to the new store.

Then production reveals:
- a timezone difference in one
  aggregation
- NULL handled differently
- a rounding discrepancy on
  money
- an ordering difference in
  paginated results

Users hit all of it at once,
and you're debugging live.
✅ Shadow read first 
for each read:
    old_result = old.query(q)
    new_result = new.query(q)
    if old != new:
        log_discrepancy(q, old, new)
    return old_result   ← users still
                          get the old
                          answer

Real queries, real data, real
distributions — zero user risk.
Fix discrepancies before anyone
depends on the new answer.

Why it catches what tests don't: production data contains shapes nobody writes tests for — rows created by code that no longer exists, encoding oddities, records at the boundaries of every assumption. Shadow reads exercise the new system against the actual distribution rather than an imagined one.

PRACTICAL DETAILS:

   - sample if the cost is high (1-10% of reads is usually enough
     to surface systematic issues)
   - compare SEMANTICALLY, not byte-for-byte: field ordering,
     floating-point representation and whitespace will differ
     harmlessly and drown the signal
   - run shadow reads ASYNCHRONOUSLY so the new store's latency
     never affects the user
   - CATEGORISE discrepancies — a systematic 3% difference in one
     aggregation is a bug; a handful of races on rows written
     mid-comparison is expected
   - set an exit criterion IN ADVANCE: "discrepancy rate below
     0.01%, sustained for a week, with every category explained"

4. Deep Dive: Backfilling Billions of Rows

The naive approach kills production:

   INSERT INTO new_table SELECT * FROM old_table;

   → a single enormous transaction
   → table locks, replication lag spikes into minutes
   → the transaction log fills
   → live traffic degrades or fails

BATCHED, THROTTLED, RESUMABLE:

   last_id = load_checkpoint()             # RESUMABLE
   while True:
       rows = old.query(
           "SELECT * FROM t WHERE id > ? ORDER BY id LIMIT 1000",
           last_id)
       if not rows: break
       new.bulk_upsert(rows)               # IDEMPOTENT — upsert,
       last_id = rows[-1].id               #   not insert
       save_checkpoint(last_id)
       sleep(throttle_delay)               # THROTTLED

       if replication_lag() > 5:           # ADAPTIVE
           sleep(30)                       # back off when the
                                           # database is stressed
PropertyWhy it's required
BatchedBounded transaction size; no long locks; replication keeps up
ResumableA job running for days will be interrupted by a deploy or an incident. Checkpoints mean restarting costs minutes, not days
IdempotentRestarts reprocess the last batch. Upsert, so re-running is harmless
Throttled and adaptiveThe backfill must yield to live traffic — watch replication lag and error rates, and back off automatically
Ordered by a stable keyPaginating by id > last is stable under concurrent inserts; OFFSET is not (the pagination problem)

The race that catches people: rows modified during the backfill. A row copied at 10:00 and updated at 10:05 is stale in the new store. Dual-writing solves it — the update goes to both — but only if dual-writing started before the backfill. That's why expand comes first: get writes flowing to both stores, then copy history underneath.

5. Deep Dive: The Dual-Write Consistency Problem

Dual-writing sounds simple and contains a real hazard — it's the dual-write problem again, inside your migration:

try:
    old_db.write(record)      # succeeds
    new_db.write(record)      # FAILS — network blip
except:
    ???

Now the stores disagree, and the migration's verification will show
discrepancies that aren't real bugs — which erodes trust in the
signal exactly when you need it.

OPTIONS:

A. OLD IS AUTHORITATIVE; new-store failures are logged, not raised.
      ✓ user requests never fail because of the migration
      ✗ the new store drifts; needs periodic reconciliation
      → the usual choice during EXPAND

B. BOTH MUST SUCCEED (2PC or compensations)
      ✓ they stay in sync
      ✗ availability now depends on BOTH — the all-of-N trap; your
        migration has made the system less reliable

C. WRITE TO OLD ONLY; use CDC to propagate to new
      ✓ NO dual write at all — one write, derived replication
      ✓ ordering and completeness guaranteed by the log
      ✗ requires CDC infrastructure; new store is eventually
        consistent
      → often the BEST option, and underused

Option C is worth reaching for. Rather than making the application write twice, let CDC tail the old database and populate the new one. The application changes not at all, no write can be missed, and ordering is preserved — you've eliminated the dual write instead of managing it.

Whichever you choose, run continuous reconciliation: a job comparing row counts and checksums between stores, alerting on drift. Without it you discover divergence at cutover, which is the worst moment.

6. The Strangler Fig: Migrating a System, Not a Database

Named for a vine that gradually envelops a host tree until the tree
is gone and the vine stands alone.

1. Put a routing layer (proxy/gateway) in front of the monolith.
   Changes nothing yet, and this is the enabling step.
2. Build ONE new service replicating ONE capability.
3. Route THAT traffic to the new service; everything else still
   goes to the monolith.
4. Verify with shadow traffic before flipping.
5. Repeat, capability by capability.
6. When the monolith serves nothing, decommission it.

At every step the system is FULLY FUNCTIONAL. There is never a
half-migrated broken state.

Choose the first extraction carefully. Not the easiest (proves nothing) and not the hardest (risks failing before you've built confidence). Ideally something well-isolated, painful enough that success is visible, and with clear boundaries. Getting the first one right is what earns the runway for the rest.

And accept that you may stop partway. "Monolith plus a few extracted services" is a perfectly good steady state. Many migrations are declared failures because they didn't reach a total rewrite, when in fact they captured most of the value — the strangler fig's virtue is that stopping is always a valid outcome.

Interview Questions

🟢 Beginner — Walk through migrating to a new database with no downtime.

Six phases, and the important property is that the first five are all reversible:

1. EXPAND    deploy the new store; start dual-writing to both.
             Old is still the source of truth.
2. BACKFILL  copy historical data old → new in throttled, resumable
             batches. Note this comes AFTER dual-writing, so rows
             changing during the copy are already being written to
             both.
3. VERIFY    shadow reads — query both, compare, serve the OLD
             answer. Log discrepancies. Zero user risk.
4. CUTOVER   switch reads to the new store gradually behind a flag:
             1% → 10% → 50% → 100%. Writes still go to both.
5. SOAK      run on the new store for a defined period while still
             dual-writing, so the old store stays current.
6. CONTRACT  stop dual-writing; decommission old after a grace
             period. The FIRST irreversible step, deliberately last.

Why the ordering matters: dual-writing before backfilling means no row can be missed — anything modified during the copy is written to both stores anyway. Reversing those steps leaves a window where updates land only in the old store and the new one is silently stale.

The step people skip is verification, and it's the highest-value one. Shadow reads compare real production queries against real data with no user exposure, catching the timezone, rounding and null-handling differences that synthetic tests never surface.

Throughout: writes must be idempotent, because retries during dual-writing would otherwise double-apply on one side and cause divergence.

🟢 Beginner — What is a shadow read and why does it matter so much?

A shadow read queries both the old and new systems on real production traffic, compares the results, and serves the old answer to the user. The new system's output is logged, not used.

old_result = old.query(q)
new_result = new.query(q)      # asynchronously, off the critical path
if not equivalent(old_result, new_result):
    log_discrepancy(q, old_result, new_result)
return old_result               # user is unaffected

Why it's the highest-leverage step in a migration: it exercises the new system against real queries and real data distributions with zero user risk. Production data contains shapes nobody writes tests for — rows created by code that no longer exists, unusual encodings, records at the boundary of every assumption you've made.

The bugs it typically catches are exactly the ones tests miss: a timezone difference in a date aggregation, NULLs handled differently, floating-point rounding on money, a different sort order for ties in paginated results. Each is subtle, none would fail a unit test on synthetic data, and all are user-visible.

Practical requirements: compare semantically rather than byte-for-byte, or field ordering and formatting differences will drown the real signal; run the shadow query asynchronously so the new system's latency never affects users; sample if the cost is high; and set an exit criterion in advance — "discrepancy rate below 0.01% for a week with every category explained" — so the decision to cut over is evidence-based rather than a judgement call under pressure.

🟡 Mid — Design the backfill for 5 billion rows without impacting production.

Never as one statement — INSERT INTO new SELECT * FROM old creates an enormous transaction that locks tables, spikes replication lag into minutes and can fill the transaction log, degrading or failing live traffic.

last_id = load_checkpoint()                  # RESUMABLE
while True:
    rows = old.query(
        "SELECT * FROM t WHERE id > ? ORDER BY id LIMIT 1000",
        last_id)                             # KEYSET pagination
    if not rows:
        break
    new.bulk_upsert(rows)                    # IDEMPOTENT
    last_id = rows[-1].id
    save_checkpoint(last_id)
    sleep(throttle)                          # THROTTLED

    if replication_lag() > 5 or error_rate_elevated():
        sleep(30)                            # ADAPTIVE backoff

Each property is load-bearing:

• Batched — bounded transactions, no long locks, replication keeps up.
• Resumable — a job running for days will be interrupted by a deploy or an incident. Checkpointing means restarting costs minutes rather than days.
• Idempotent (upsert) — restarts reprocess the last batch, and that must be harmless.
• Keyset pagination — OFFSET is unstable under concurrent inserts and gets slower with depth, so rows would be skipped or duplicated.
• Adaptive throttling — the backfill must yield to live traffic automatically, not require a human to notice.

Sizing: at 1,000 rows per batch and 10 batches/second, 5 billion rows takes ~140 hours — about six days. That's fine if the job is resumable and throttled, and it's why "how long will this take" should be computed before starting rather than discovered.

The race to handle: rows updated during the copy. Dual-writing (started before the backfill) covers it — the update goes to both stores. Then run a reconciliation pass afterwards comparing checksums to confirm.

🟡 Mid — Dual-writing: what if the write to the new store fails?

This is the dual-write problem appearing inside your migration, and there are three answers with different trade-offs:

Option A — old is authoritative, log new-store failures. The user's request succeeds if the old store accepted it; failures against the new store are recorded but not raised.

✓ The migration can never cause a user-facing failure — important, because a migration that degrades reliability will be stopped.
✗ The new store drifts, so you need reconciliation to repair it.
→ This is the usual choice during the expand phase.

Option B — both must succeed. ✓ The stores stay in sync. ✗ Availability now depends on both systems — the all-of-N trap from replication. Your migration has made the system less reliable than before it started, which is the wrong direction.

Option C — write to old only; use CDC to populate new. ✓ There is no dual write at all: one write, and the new store is derived from the old database's log. No write can be missed, ordering is preserved, and the application doesn't change. ✗ Requires CDC infrastructure, and the new store is eventually consistent.

Option C is often the best and is underused. Rather than managing the dual-write problem, it eliminates it — the same reasoning that makes CDC preferable to application-published events in data platforms.

Whichever you choose, run continuous reconciliation: compare row counts and checksums between stores on a schedule and alert on drift. Without it, divergence is discovered at cutover, which is precisely when you least want surprises — and it also erodes trust in your shadow-read signal, since real drift and real bugs become indistinguishable.

🔴 Senior — You're at 50% cutover and error rates rise. Walk me through your response.

1. Roll back first, diagnose second. Flip the feature flag to 0% immediately. This is precisely why flags rather than deploys control a migration — rollback takes seconds and requires no deployment pipeline. Do not spend ten minutes investigating while users are affected; the new system's behaviour will still be reproducible afterwards.

2. Confirm the rollback worked. Error rates should return to baseline. If they don't, the problem isn't the new read path — perhaps dual-writing is degrading the old store, or the issue is coincidental. That distinction matters and is easy to assume wrongly.

3. Characterise before re-attempting.

- Which errors? timeouts (capacity/latency) vs 500s (correctness)
  vs 404s (data missing from the new store)?
- Which queries? a specific pattern, or uniform?
- Which users? a segment with unusual data shapes is a strong clue
- Did it appear at 50% specifically, or was it present at 10% and
  simply below the alerting threshold?

4. The last question is the most important one. If the errors existed at 10% and nobody noticed, your rollout gates were too coarse — you should be comparing error rates between the two paths at each step, not just watching for a global alert. That's a process finding worth more than the individual bug.

5. Common causes at partial cutover: the new store lacks capacity for 50% of production load (it was fine at 10%); a cold cache on the new path; missing data from an incomplete backfill affecting a subset of queries; or a query pattern that only appears at higher volume.

6. Resume with better instrumentation: ramp more slowly, compare error and latency per path rather than in aggregate, and define abort criteria in advance ("if new-path error rate exceeds old-path by 0.1%, roll back automatically").

What I'd resist: pushing forward to 100% on the theory that it's a transient issue. Migrations are one of the few situations where the reversible option is always available — spending it is the whole point of the design.

🔴 Senior — Why do most migrations stall at 80%, and how do you prevent it?

Because the remaining 20% is where all the difficulty concentrates, and by then the momentum is gone.

Why it happens:

• The easy parts were done first — reasonably, to build confidence. What remains is the gnarly legacy nobody understands: undocumented behaviour, obscure integrations, the batch job that runs quarterly.
• Diminishing visible value. The first 80% delivered obvious wins; the last 20% delivers "we can finally turn off the old thing", which is harder to prioritise against new features.
• Sponsors and teams change. A migration spanning quarters outlives reorgs and shifting priorities.
• It works well enough. Both systems run, nothing is on fire, and urgency evaporates.

Why stalling is the worst outcome — worse than either endpoint: you now operate two systems, pay for both, onboard every new engineer onto both, and implement every change twice. You've taken all the cost of the migration and captured only part of the benefit, permanently.

Prevention:

1. Define success as decommissioning, not cutover. The migration is not finished until the old system is switched off — say so at the outset, and track it as the metric.

2. Plan the endgame first. Identify the hardest remaining piece before starting, and confirm there's a viable approach. Migrations stall because nobody checked whether the last 20% was possible.

3. Tackle one genuinely hard thing early — after the first easy win, to prove the approach and surface unknowns while sponsorship is strong.

4. Make the old system progressively unattractive: stop adding features to it, mark it deprecated in code, add friction to new integrations. Each step makes finishing easier than not finishing.

5. Track and publish remaining usage — "12 endpoints still on the legacy path, down from 340". A visible countdown sustains attention far better than a status update.

6. Timebox and be willing to stop deliberately. If the last 20% genuinely isn't worth it, decide that explicitly, document the permanent split, and stop paying attention costs. A conscious partial migration is respectable; an accidental one is the failure mode.

🏋️ Graded Exercises

Exercise 1 (Easy): Why does dual-writing come before the backfill, not after?
Solution

Because rows change during the backfill, and without dual-writing already running, those changes are lost.

BACKFILL FIRST (wrong):
   10:00  copy row 42 (balance = 100) → new store
   10:05  user updates row 42 (balance = 150) → OLD STORE ONLY
   10:30  backfill completes
   → the new store has balance = 100. Permanently stale, and
     nothing will correct it.

DUAL-WRITE FIRST (right):
   09:00  dual-writing begins — all NEW writes go to both stores
   10:00  backfill copies row 42 (balance = 100)
   10:05  user updates row 42 → BOTH stores get balance = 150
   → correct, regardless of copy timing.

The general principle: establish the mechanism that keeps the stores in sync before copying history. Then the backfill only needs to handle data that existed before it started — a fixed, bounded set — rather than chasing a moving target.

The subtlety worth adding: the backfill must use upsert rather than insert. If a row is updated at 10:05 by the dual-write path and then the backfill copies its old value at 10:10, an insert would fail on the key conflict, but a naive "insert or overwrite" would overwrite the newer value with the older one. Upsert with a version or timestamp check — only write if the incoming version is newer — resolves it. That ordering hazard is easy to miss and produces silent, hard-to-trace corruption.

Exercise 2 (Easy): Why use feature flags rather than deploys to control a migration rollout?
Solution

Because rollback speed is the property that matters most, and flags make it instant.

Feature flagDeploy-based
Rollback timeSecondsMinutes to tens of minutes
GranularityPer user, per percentage, per segmentPer deployment unit
Under stressOne toggleA full pipeline run, while users are affected
TargetingInternal users first, then a cohort, then everyoneAll or nothing per instance

The scenario that decides it: at 50% cutover, error rates climb. With a flag you're at 0% within seconds and can then investigate calmly. With deploys you're waiting for a pipeline while users experience errors — and rollback deploys are themselves risky when done under pressure.

Flags also enable targeting that deploys can't: route internal employees to the new path first, then a small cohort of low-risk users, then ramp. And you can hold a percentage steady for a soak period rather than being forced to complete the rollout.

The cost to acknowledge: flags add branching to the code, and they must be removed after the migration completes. Long-lived migration flags accumulate into a maze of dead conditionals, so treat flag cleanup as part of the contract phase rather than optional tidying.

Exercise 3 (Medium): Design the shadow-read comparison. What counts as a discrepancy?
Solution 
async def shadow_compare(query, old_result):
    """Runs OFF the critical path — never affects user latency."""
    try:
        new_result = await new_store.query(query, timeout=5)
    except Exception as e:
        record("shadow_error", query=query, error=e)
        return

    diff = semantic_diff(old_result, new_result)
    if diff:
        record("discrepancy", query=query, diff=diff,
               category=classify(diff))

What is NOT a discrepancy — and filtering these out is essential, or real signal drowns:

• Field ordering in JSON or result sets.
• Floating-point representation — 1.0 vs 1.00.
• Timestamp precision — milliseconds vs microseconds.
• Ties ordered differently in a sort where the comparator isn't total.
• Rows written between the two reads — a genuine race, expected at low rates.

What IS a discrepancy:

• Different values for the same field — the clearest signal.
• Different row counts — missing or extra data, usually an incomplete backfill or a filtering difference.
• Different aggregations — often timezone or NULL handling.
• Monetary rounding differences, which matter at any magnitude.
• Systematic ordering differences in paginated results, which cause users to see duplicates or skipped records.

Categorise rather than counting. "0.5% discrepancy rate" is uninformative; "0.4% are write races, 0.1% are a timezone bug in monthly aggregation" is actionable. Every category must be explained before cutover, not merely small.

Set the exit criterion in advance: for example, "unexplained discrepancy rate below 0.01% sustained for a week, with every category root-caused". Deciding the bar beforehand prevents the pressure to rationalise remaining differences when the migration is running late.

Exercise 4 (Medium): Migrate a monolith's user service to a new microservice. Sequence it.
Solution 
1. ROUTING LAYER
   Put a proxy/gateway in front of the monolith. Changes nothing
   functionally; this is the enabling step and should be boring.

2. BUILD THE SERVICE
   Implement the user capability in the new service, reading from
   the SAME database as the monolith initially. This decouples the
   code migration from the data migration — do one at a time.

3. SHADOW TRAFFIC
   Route a copy of user requests to the new service. Compare
   responses; serve the monolith's. Fix discrepancies.

4. GRADUAL CUTOVER (reads)
   Flag-controlled: 1% → 10% → 50% → 100% of read traffic to the
   new service. Monitor error and latency per path.

5. CUTOVER (writes)
   Only after reads are stable. Writes are riskier because they
   are not idempotent by default and mistakes persist.

6. SPLIT THE DATABASE (separate migration)
   Now do the six-phase data migration so the service owns its
   own store — with the code migration already proven.

7. REMOVE the monolith's user code and its database access.
   Only now is this capability actually migrated.

The key sequencing decision is step 2: the new service initially shares the monolith's database. That separates two risky changes — new code and new data store — so a problem has one obvious cause. Doing both at once means any discrepancy could come from either, and diagnosis becomes guesswork.

Reads before writes because reads are reversible: a wrong read shows stale or incorrect data momentarily, whereas a wrong write persists and may need repair.

What to watch for: the monolith probably reaches into user tables from places that aren't "the user service" — reports, admin tools, batch jobs, joins in unrelated queries. Finding those is the hard part of step 7, and it's where extraction usually stalls. Grep for table references early, before committing to a timeline.

Exercise 5 (Hard): Migrate a payments database with zero data loss. What's different about money?
Solution

The six-phase structure is the same; what changes is that every tolerance goes to zero and verification becomes far more rigorous.

1. Zero acceptable discrepancy. For most migrations "0.01% differences, all explained" is a reasonable exit criterion. For money it is not — every discrepancy must be root-caused and resolved. A penny difference indicates a systematic bug that will recur at scale.

2. Reconciliation is continuous and total. Compare not just row counts but balances: sum every account in both stores and require exact agreement. Run it constantly during the migration, not just at the end. If the domain is a ledger, the invariant that entries sum to zero must hold in both stores independently.

3. Idempotency is mandatory, not advisable. Every write during dual-writing carries an idempotency key. A retry that double-applies a payment is unacceptable rather than merely untidy.

4. Prefer CDC over application dual-writes. Eliminating the dual write removes the entire class of "wrote to one store but not the other" failures — worth the infrastructure cost when the data is money.

5. Cut over far more slowly, and consider partitioning by account rather than by percentage of traffic — so a given account is consistently served by one store, and any problem affects a bounded, identifiable set of customers you can reconcile individually.

6. Keep the old system longer. Financial bugs surface on monthly and quarterly cycles — statement generation, reconciliation runs, tax reporting. A two-week soak is insufficient; keep the old store queryable through at least one full reporting cycle.

7. Involve finance and compliance. There may be regulatory requirements about audit trails, data retention and change control that constrain the approach — and discovering those after cutover is much worse than before.

The framing: for most systems a migration bug means a bad user experience. For payments it means money in the wrong place, a regulatory issue, and a loss of trust that is not recoverable by fixing the bug. That justifies spending several times more effort on verification than the same migration would warrant elsewhere — and knowing when to spend disproportionately is the judgement being tested.

Exercise 6 (Hard): Your migration has been at 80% for six months. What do you do?
Solution

First, name the cost honestly, because the organisation is probably treating this as "mostly done" when it's the worst possible state:

Running both systems means:
   - paying for both
   - onboarding every new engineer onto both
   - implementing every change twice, or choosing which system
     gets it (and creating divergence)
   - reasoning about which is authoritative for each capability
   - carrying the operational and security burden of the legacy one

This is strictly worse than EITHER endpoint. "80% migrated" is not
80% of the value.

Then diagnose why it stalled — the remedy differs:

• The remaining 20% is genuinely hard — undocumented behaviour, an obscure integration, a quarterly batch job.
• Nobody owns it — the sponsor moved on, the team was reassigned.
• It's not visibly painful enough — both systems work, so urgency evaporated.
• The last piece was never actually feasible and nobody checked at the outset.

Then make an explicit decision, which is the real answer:

Option A — finish it. Requires re-establishing sponsorship by quantifying the ongoing cost (engineering hours per month spent on dual maintenance, infrastructure spend, incident load). Set a hard deadline, assign clear ownership, and publish a countdown of remaining usage. Make the old system progressively unattractive — freeze features on it, add friction to new integrations.

Option B — stop deliberately. If the last 20% genuinely isn't worth it, decide that, document the permanent split, define the boundary clearly, and stop treating it as an unfinished migration. Remove the half-built scaffolding and dual-write machinery so nobody maintains code for a migration that isn't happening.

Option C — revert the 80%. Rare, but worth considering if the new system is worse in practice. Sunk cost is not a reason to continue.

What I'd push hardest on: the decision must be made, not drifted into. The failure mode isn't choosing wrongly — it's the absence of a choice, where everyone assumes it'll be finished "eventually" while the cost accrues indefinitely. Forcing an explicit decision, with the ongoing cost quantified, is the highest-value thing a senior engineer can do here.

🎯 Key Takeaways

  • Think in reversible steps — expand, backfill, verify, cutover and soak are all reversible; only contraction isn't, so it comes last.
  • Dual-write before backfilling, or rows changed during the copy are silently stale.
  • Shadow reads are the highest-leverage step — real queries, real data, zero user risk, and they catch what synthetic tests never will.
  • Compare semantically and categorise discrepancies, with an exit criterion set in advance.
  • Backfills must be batched, throttled, resumable, idempotent, and paginated by keyset rather than OFFSET.
  • Never make dual-writes require both stores to succeed — that makes the system less available than before the migration.
  • CDC can eliminate the dual write entirely, which is often the best option and is underused.
  • Run continuous reconciliation so drift is found during the migration, not at cutover.
  • Use feature flags, not deploys — rollback in seconds is the property that matters.
  • Strangler fig keeps the system functional at every step, and stopping partway is a valid outcome if it's chosen deliberately.
  • Define success as decommissioning the old system, not as cutover — otherwise you stall at 80% and pay for both forever.
  • For money, every tolerance goes to zero — exact reconciliation, mandatory idempotency, and a soak spanning a full reporting cycle.
