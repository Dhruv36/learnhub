Caching Strategies Fundamentals

What you'll master: the four read/write patterns and when each is correct, why cache-aside must delete rather than update (with the exact interleaving that proves it), how to pick a TTL from business tolerance instead of guessing, the three failure modes that take down production — stampede, penetration, avalanche — and how to reason about a cache as a capacity dependency rather than an optimisation.

Prerequisites: Back-of-Envelope Estimation, CAP Theorem, Consistent Hashing (how keys map to cache nodes). Feeds into Design TinyURL and Design Instagram Feed.

1. Why Caching Is The Highest-Leverage Tool (And The Most Dangerous)

Recall the latency ratios from estimation: memory ≈ 100 ns, SSD ≈ 150 µs, a disk-backed DB query with parsing and planning ≈ 1–10 ms. A cache hit is routinely 1,000–10,000× faster than the query it replaces. Nothing else in system design offers that multiplier for so little code.

Here's the leverage, in the arithmetic that matters:

600,000 reads/s against a database that handles 30,000 QPS.

  hit rate    QPS reaching DB      verdict
  ────────────────────────────────────────────────────
     0%          600,000           dead (20× over)
    50%          300,000           dead (10× over)
    90%           60,000           dead (2× over)
    95%           30,000           exactly at limit — no headroom
    99%            6,000           comfortable ✓
    99.9%            600           luxurious

Notice the shape: the payoff is NON-LINEAR and all the value is at the
end. Going 90% → 99% removes 90% of the remaining DB load. This is why
teams obsess over the last few percent of hit rate.
⚠️ Read that table backwards and you have the danger: a system at 99% hit rate has provisioned its database for 6,000 QPS. If the cache tier dies, the database instantly receives 600,000 — 100× its capacity. The cache is not making a working system faster; it is the capacity. That reframing changes everything: cache HA, warming, and stampede protection stop being nice-to-haves and become the same tier of requirement as database backups.

2. The Four Patterns

Two dimensions: who populates the cache on a read, and how writes propagate. Most systems use cache-aside; know all four so you can justify the choice.

PatternRead pathWrite pathChoose when
Cache-aside
(lazy loading)		App checks cache → miss → app reads DB → app fills cacheApp writes DB → app deletes the keyThe default. Cache failure degrades to slow, not broken. Only requested data is cached. Cost: app owns the logic, and a brief staleness window.
Read-throughApp asks cache; cache itself loads from DB on missUsually paired with write-throughYou want the loader logic in one place (a library or the cache layer). Cleaner app code; the cache becomes a hard dependency on the read path.
Write-throughSame as read-throughWrite to cache and DB synchronously before ackingCache must never be stale and reads dominate. Cost: every write pays both latencies, and you cache data nobody reads.

(write-behind)		From cacheWrite to cache, ack immediately, flush to DB async in batchesWrite-heavy, burst-absorbing workloads (counters, metrics, view counts). Fastest writes and it coalesces updates. Cost: data loss if the cache dies before flushing.

The write-back trade-off is worth making concrete, because it's the one people either over- or under-use:

View counter, 50,000 increments/s on popular videos.

Write-through: 50,000 DB writes/s. Needs a sharded write-optimised store.
               Expensive, and the DB is doing pointless work — nobody
               reads the count between increments.

Write-back:    INCR in Redis (100K+ ops/s on one node), flush to the DB
               every 10 seconds. 50,000 increments coalesce into ONE row
               update per video per 10s. DB write load drops ~1000×.
               Risk: a Redis crash loses ≤10s of counts.

For a view counter, losing 10 seconds of counts is invisible.
For an account balance, it's fraud. Same pattern, opposite verdict —
the data's tolerance for loss decides, not the traffic shape.

3. Deep Dive: Why Cache-Aside Must DELETE, Not Update

This is the single most common caching interview trap, and the reasoning is worth internalising because it generalises to every read-modify-write race.

Suppose on write you update the cache instead of deleting it. Two concurrent writers:

❌ Update the cache 
Writer A: sets value = 1
Writer B: sets value = 2

  T1  A writes DB: value=1
  T2  B writes DB: value=2
  T3  B updates cache: value=2
  T4  A updates cache: value=1   ← A was slow

DB says 2. Cache says 1.
STALE FOREVER — no TTL, no fix,
until someone notices.
The two operations (write DB, write cache) aren't atomic, so their orderings can interleave independently.
✅ Delete the cache 
  T1  A writes DB: value=1
  T2  B writes DB: value=2
  T3  B deletes cache key
  T4  A deletes cache key

Cache is empty. Next read fetches
the truth from the DB: value=2. ✓

Deletes are IDEMPOTENT and
order-independent — that's the
whole trick.
Worst case you pay one extra cache miss. Correctness doesn't depend on timing.

Now the harder question interviewers escalate to: delete before or after the DB write? Both have a race, and knowing that both do is the real answer:

DELETE FIRST, then write DB:
  T1  Writer deletes cache
  T2  Reader misses, reads DB (OLD value), starts to fill cache
  T3  Writer writes DB (NEW value)
  T4  Reader fills cache with the OLD value it read at T2
  → stale cache again, and this window is WIDE (a whole DB write)

WRITE DB FIRST, then delete cache:
  T1  Writer writes DB (NEW value)
  T2  Reader misses, reads DB → gets NEW value ✓
  T3  Writer deletes cache
  → the only bad window is if a reader read the OLD value BEFORE T1
    and fills the cache AFTER T3 — requires the reader's DB read to
    straddle the entire write. Far narrower.

→ WRITE DB FIRST, THEN DELETE. Smaller race window.

To close the remaining window you need one of: delayed double-delete (delete again after ~500 ms to catch late fills), versioned writes (the fill is rejected if its version is older than what's cached), or CDC-driven invalidation (see Data Platforms — tail the DB's replication log and invalidate from there, which makes the cache eventually correct by construction).

💡 The pragmatic answer, and the one to give: "Write DB, then delete the key, and always set a TTL as a backstop. The residual race is rare and the TTL bounds its damage. If the data can't tolerate even that, I'd invalidate from the database's change log rather than from application code, because application-side invalidation can always be skipped by a crash between the two steps." That last point matters — an app that dies between "write DB" and "delete cache" leaves stale data forever, and no amount of ordering fixes it. Only a TTL or CDC does.

4. TTL: Deriving It Instead of Guessing

"What's your TTL?" is a question about product tolerance, not infrastructure. The wrong answer is a round number; the right answer names the business constraint.

DataTTLWhy that number
Immutable, content-addressed asset (app.a3f9c1.js)1 yearThe URL changes when the content changes, so it can never be wrong. Always pair long TTLs with content hashing.
User profile / avatar1–24 hRarely edited, and an hour of staleness on someone's display name is harmless. Invalidate explicitly on edit; the TTL is just the backstop.
Rendered feed10–60 sUsers can't distinguish a 30-second-old feed, but a 10-minute-old one feels broken. Ties directly to perceived freshness.
Product priceseconds, or never cacheShowing a stale price you won't honour is a legal and trust problem. Either very short, or cache the quote as a durable fact instead.
Inventory countDon't cache the decisionCache the display ("in stock") loosely; the decrement must be linearizable. Never let a cache decide whether a sale is allowed.
Negative result (key not found)30 s – 5 minShort, so a newly created record appears promptly, but long enough to blunt penetration attacks (section 5).
Session token= session lifetimeThe TTL is the business rule here — expiry is a feature, not a cache detail.

Always set a TTL, even when you invalidate explicitly. Explicit invalidation fails in ways you won't notice: a deploy skips the delete, a message is dropped, a process crashes between the DB write and the delete, a new code path forgets. The TTL converts "stale forever" into "stale for at most N" — an unbounded bug into a bounded one.

5. Deep Dive: The Three Failure Modes

5a. Stampede (thundering herd)

One hot key — the homepage feed — expires at T=0.
10,000 in-flight requests all miss simultaneously.
All 10,000 issue the same expensive DB query.
The DB, sized for ~100 of these, collapses.
Requests time out → clients retry → MORE load → cascading failure.

Note the cruelty: this happens BECAUSE the key was popular.
The hotter the key, the worse the stampede.

Three fixes, usually combined:

FixMechanismTrade-off
Per-key lock (request coalescing)First miss acquires a short-lived lock (SET key:lock NX EX 5) and rebuilds; others wait briefly and re-read, or serve staleOne DB query instead of 10,000. Must handle lock-holder death via the lock's own TTL, or everyone waits forever.
Stale-while-revalidateServe the expired value immediately while one background task refreshes itZero latency spike and no DB burst — the best user experience. Requires storing a soft-expiry alongside a longer hard-expiry.
TTL jitterttl = base + random(0, base × 0.1)One line of code. Prevents synchronised expiry of a million keys populated in the same batch — which is the mass version of this failure.

Why jitter matters more than people expect: if you warm 1M keys at deploy time with a fixed 1-hour TTL, all 1M expire in the same second, one hour later. Your cache goes from 99% to 0% instantly — you've built a scheduled outage that fires every hour.

5b. Penetration

Requests for keys that DON'T EXIST always miss, by definition,
so every one reaches the database.

  GET /user/999999999   → cache miss → DB miss → nothing to cache
  Repeat 100,000×/s with random IDs → the cache is bypassed entirely
  and your DB takes the full load. Often deliberate (an attack), or
  a buggy client looping over an ID range.

Fix 1 — cache the negative result. Store a tombstone with a short TTL: SET user:999999999 "__NULL__" EX 60. Now repeat requests hit the cache. The short TTL ensures a genuinely-new record still appears within a minute.

Fix 2 — Bloom filter in front. Keep a Bloom filter of all existing IDs; if it says "definitely not present", reject without touching cache or DB. Bloom filters have no false negatives, so a "not present" answer is trustworthy — exactly the guarantee you need here. Costs ~1.2 GB per billion keys at 1% false-positive rate, and a false positive merely means one wasted DB lookup.

Fix 3 — validate before querying. The cheapest fix, and the one people skip: if IDs are Snowflake-shaped or UUIDs, a malformed ID can be rejected at the edge for free.

5c. Avalanche

The entire cache tier restarts (deploy, OOM, AZ failure, cluster upgrade).
Hit rate: 99% → 0% instantly. DB receives 100× normal load and dies.
Then: DB is down → cache can't be refilled → nothing recovers on its own.
This is the incident that keeps people up at night, because it does not
self-heal.

Defences, in the order you should build them:

• Never let the whole tier restart at once. Rolling restarts, one node at a time; with consistent hashing that costs only 1/N of the keys per step.
• Persistence / replicas. Redis AOF or RDB plus replicas means a restarting node reloads warm rather than empty.
• Warming before traffic. A new node preloads the top-N hot keys and only then enters the load balancer's rotation.
• Load shedding at the DB. A concurrency limiter in front of the database that rejects excess requests fast. A database serving 30K QPS and shedding the rest keeps some of the site up; a database that accepts 600K QPS and dies keeps none of it. This is the difference between degradation and an outage, and it's the answer senior interviewers are listening for.
• Circuit breaker + serve stale. When the DB is unhealthy, keep serving expired cache entries rather than failing. Stale data during an incident beats an error page.

🎯 Staff-level insight: notice all three failure modes share one shape — the cache stops absorbing load and the database inherits traffic it was never sized for. So the durable fix isn't three separate tricks, it's a single principle: the database must be protected from the cache's absence. Rate-limit it, shed load, serve stale, degrade features. A team that has done this survives a cache outage with elevated latency; a team that hasn't takes a full outage. Say this and you're answering the question behind the question.

6. Where Caches Live: The Layers

Browser cache        (0 ms, per-user, Cache-Control)
   ↓ miss
CDN / edge           (10–50 ms, shared globally, static + cacheable API)
   ↓ miss
API gateway cache    (same-region, full-response caching)
   ↓ miss
App-local / L1       (~0 ms, per-process, tiny, seconds-long TTL)
   ↓ miss
Distributed cache    (0.5–2 ms, shared, Redis/Memcached)  ← "the cache"
   ↓ miss
DB buffer pool       (in-DB memory, hides disk from repeated queries)
   ↓ miss
Disk

Each layer trades freshness for latency and blast radius. Two layers deserve specific attention:

App-local (L1) is the most underused. A tiny in-process cache with a 1–5 second TTL absorbs hot keys entirely — no network hop at all — and it's the correct answer to the hot-key problem from consistent hashing, because a single hot key cannot be spread across the ring but can be replicated into every app process. Cost: N copies means N independent staleness windows, and you cannot invalidate it reliably. Keep the TTL short and only cache what tolerates it.

The CDN is where the largest wins hide, because it removes traffic from your infrastructure entirely rather than moving it around inside. Cacheable API responses at the edge (product pages, public profiles) with a short TTL and stale-while-revalidate can cut origin traffic by an order of magnitude.

Sizing the tier — apply the estimation method:

Requirements: 600,000 reads/s, hot set = 12 GB (from the estimation lesson).

Throughput:  600,000 / 100,000 ops/s per node   = 6 nodes
Memory:      12 GB hot set × 1.3 (overhead)     ≈ 16 GB → trivial per node
Replication: ×2 for HA                          = 12 nodes total
Headroom:    run at ~70%                        ≈ 14–16 nodes

→ THROUGHPUT and FAILURE TOLERANCE size this cluster, not data volume.
  The 12 GB working set would fit on one machine — but one machine means
  a total cache wipe on failure, i.e. the avalanche scenario by design.

Two eviction subtleties worth knowing: LFU beats LRU when popularity is stable (LRU evicts a genuinely-hot key after one burst of scanning cold keys — a full-table scan can flush your entire working set), and noeviction turns a full cache into write errors, which is occasionally what you want for a queue but is a self-inflicted outage for a cache.

8. Deep Dive: Invalidation Across Services

One service owning one cache is easy. The hard version: five services cache data derived from a table that a sixth service owns. Application-side invalidation now requires every writer to know every reader's cache keys — coupling that decays the moment someone adds a service.

❌ Point-to-point: the writer calls each cache to invalidate.
   N×M coupling, and a missed call means permanent staleness.

✅ Event-driven: the writer publishes "user:123 changed" to a topic;
   each service invalidates its own derived keys.
   Writer knows nothing about readers. Add a service, subscribe, done.

✅✅ CDC (change data capture): tail the DB's replication log
   (Debezium/binlog) and emit change events automatically.
   Cannot be skipped by application code, because it's derived from the
   commit itself — a crash between "write DB" and "publish event" is
   impossible when the log IS the event source.

CDC is the strongest option precisely because it removes the failure mode that ordering tricks can't: an app crashing between its DB write and its invalidation. See Data Platforms for the mechanics. The cost is real infrastructure and eventual (not immediate) invalidation — which is exactly why you still set TTLs.

Interview Questions

🟢 Beginner — Explain cache-aside, and why you delete rather than update the key on a write.

Cache-aside means the application manages the cache explicitly. On a read: check the cache; on a miss, read the database, store the result, return it. On a write: write the database, then delete the cache key so the next read repopulates from the truth.

It's the default pattern because the cache is advisory — if it's down, reads still work, just slower. Compare read-through, where the cache sits on the read path and its failure is an outage.

Why delete, not update: the DB write and the cache write aren't atomic, so two concurrent writers can interleave. If A writes value=1 and B writes value=2, the DB may commit in the order 1, 2 while the cache updates arrive 2, 1 — leaving the cache holding 1 while the DB says 2, with no mechanism to ever correct it. Deleting avoids this entirely because deletes are idempotent and order-independent: whichever arrives last, the key ends up absent and the next read fetches the truth. The cost is one extra cache miss, which is trivially cheaper than permanent staleness.

🟢 Beginner — What TTL would you set for a user's avatar URL, a product price, and a hashed JS bundle? Why?

Each answer comes from business tolerance for staleness, not from a default:

Avatar URL → 1–24 hours. Rarely changes, and an hour of showing the previous avatar harms nothing. I'd invalidate explicitly when the user uploads a new one and treat the TTL purely as a backstop for missed invalidations.

Product price → seconds, or don't cache the value at all. Displaying a stale price you won't honour is a trust and potentially legal problem. Better design: cache the product page briefly but treat the price as a durable quote — generate a priced quote with its own expiry and honour it — which converts a consistency problem into a business fact.

Hashed JS bundle (app.a3f9c1.js) → 1 year, immutable. The filename contains a content hash, so the content at that URL can never change; a new build produces a new URL. This is the ideal case — make the key change when the content changes and caching becomes free of invalidation entirely. Whenever you can restructure data to be content-addressed, do it.

🟡 Mid — Your homepage feed key expires and the database falls over. Diagnose and fix.

That's a cache stampede (thundering herd). The key was hot, so at the instant it expired every in-flight request missed simultaneously — potentially thousands — and each issued the same expensive query. The database was sized for the steady-state miss rate, not for every concurrent request arriving at once. Then timeouts triggered client retries, amplifying the load further.

The irony worth naming: the failure is caused by popularity. The hotter the key, the bigger the herd.

Fixes, and I'd deploy more than one:

1. Request coalescing / per-key lock. The first request to miss takes a short lock (SET feed:lock NX EX 5) and rebuilds; the rest wait briefly and re-read, or serve stale. 10,000 requests become one query. Critical detail: the lock must have its own TTL, or a crashed lock-holder blocks everyone indefinitely.
2. Stale-while-revalidate (best UX). Keep a soft expiry and a longer hard expiry. Past the soft expiry, serve the stale value immediately and kick off one background refresh. No latency spike, no DB burst.
3. TTL jitter so this can't become synchronised across many keys.
4. Precompute hot keys. For something as predictable as the homepage feed, don't rely on lazy fill at all — refresh it on a schedule so it never expires under load.

I'd also add a concurrency limiter at the DB so that any future herd degrades latency instead of taking the database down — treating the symptom class, not just this one key.

🟡 Mid — How do you invalidate a cache when five different services read data one service owns?

Point-to-point invalidation (the writer calls each reader's cache) creates N×M coupling: the writer must know every consumer's key naming, and a single missed call means permanent staleness. It also breaks the moment someone adds a sixth service, which is guaranteed.

Event-driven invalidation is the standard fix. The owning service publishes a domain event — "user:123 updated" — to a topic; each consuming service subscribes and invalidates its own derived keys. The writer knows nothing about readers, and adding a service means adding a subscriber.

CDC is strictly better where you can afford it. Tail the database's replication log (Debezium on the binlog/WAL) and emit change events automatically. The decisive advantage: application code cannot skip it. With app-published events there's always a window where the process writes the DB, then crashes before publishing — leaving stale caches with no recovery path. When the commit log is the event source, that window doesn't exist.

Two caveats I'd state: invalidation is now eventual (milliseconds to seconds of lag), so TTLs remain necessary as a backstop; and events must carry enough identity for each consumer to map them to its own derived keys — a service caching "top 10 products by category" needs to know which category a changed product belongs to, which often means the event carries before/after state.

🔴 Senior — Your Redis cluster fails entirely at peak. Walk me through what happens and how the system should be designed to survive it.

What happens without preparation: hit rate goes 99% → 0%. If the DB was sized for 6,000 QPS (1% of 600K), it now receives 600,000 — 100× capacity. Connection pools exhaust, queries queue, latency crosses client timeouts, clients retry, effective load exceeds even 600K. The database becomes unresponsive, so the cache cannot be refilled even after Redis returns. This does not self-heal — that's the defining property of an avalanche, and it's why recovery often requires taking traffic off entirely.

Designing to survive it, in layers:

1. Prevent total loss. Cluster mode with replicas so a node failure loses 1/N, not everything. AOF/RDB persistence so restarts reload warm. Rolling restarts only — with consistent hashing, one node at a time costs 1/N of keys. Multi-AZ so one zone's failure isn't the tier's failure.

2. Protect the database — the crucial layer. A concurrency limiter or token bucket in front of the DB that rejects excess immediately. This is counterintuitive but correct: a DB serving 30K QPS and shedding the rest keeps part of the site alive; a DB accepting 600K dies and keeps none. Pair with a circuit breaker that trips on rising latency and, while open, serves stale cache entries or a degraded response.

3. Degrade features deliberately. Decide in advance what to turn off: recommendations, "people also viewed", activity feeds. Serving a bare product page beats serving nothing. This is a product decision that must be made before the incident, not during it.

4. Recover deliberately. Don't return full traffic to a cold cache — that just re-triggers the avalanche. Warm the top-N keys first, then ramp traffic gradually (1%, 10%, 50%), watching DB load.

5. Add L1. A small in-process cache with a few seconds' TTL keeps the hottest keys served even with the entire distributed tier gone. Cheap insurance that turns a catastrophic dependency into a degraded one.

The framing I'd close on: at high hit rates the cache isn't an optimisation, it's load-bearing capacity. Any component the system cannot survive losing needs HA, graceful degradation, and a tested recovery runbook — the same bar as the primary database.

🔴 Senior — When should you NOT cache?

Caching has real costs — staleness, memory, operational complexity, and a whole class of correctness bugs — so it needs justification. Cases where it's wrong:

1. Authorisation decisions. Cache the user's data, never "user X may do Y". A revoked permission or a fired employee's access remains valid for the TTL — a security hole with a countdown. If you must, cache the inputs and re-evaluate the decision each time.

2. Anything where staleness is a correctness violation. Inventory decrements, account balances, seat assignments, uniqueness checks. Cache the display ("in stock") but never let a cache decide whether a sale is permitted — that path needs linearizability.

3. Low hit rate. If the access pattern has no locality — random access across a huge key space, or an analytics query that's different every time — you're adding a network hop, memory cost, and a failure mode for nothing. Measure before assuming; a 10% hit rate is usually a net negative once you count the miss penalty.

4. Write-heavy data with few reads. Caching data that's rewritten more often than it's read means the invalidation traffic exceeds the value delivered. Event logs and telemetry ingestion are typical.

5. When the query is already fast. A well-indexed primary-key lookup on a warm buffer pool is sub-millisecond. Adding Redis to save 0.3 ms while introducing staleness and a new dependency is a bad trade. Cache expensive things: joins, aggregations, fan-outs, external API calls.

6. When you can restructure instead. The best cache is often no cache: content-address immutable assets so they're cacheable forever with no invalidation, denormalise so the expensive join doesn't exist, or precompute into a materialised view the DB maintains. Those eliminate the problem rather than layering state on top of it.

The general test: what's the cost of serving stale data here, and what's the actual latency I'm saving? If the first is high or the second is small, don't cache.

🏋️ Graded Exercises

Exercise 1 (Easy): A service does 200,000 reads/s. The database handles 20,000 QPS. What minimum cache hit rate keeps the DB inside its limit, and what hit rate would you actually target?
Solution 
DB must receive ≤ 20,000 of 200,000  → miss rate ≤ 10%
                                     → hit rate ≥ 90%  (minimum)

But 90% leaves zero headroom — the DB is exactly at its ceiling, so any hit-rate dip, traffic spike, or single node loss causes an incident. Target 99%, which sends 2,000 QPS to the DB, giving 10× headroom.

The point of the exercise: the "minimum required" hit rate is a trap answer. Provision the cache so that a degraded cache still fits inside the DB's capacity, because hit rates fall exactly when you're already having a bad day. And state the corollary — at 99%, the DB is sized for 1% of traffic, so cache HA is now mandatory.

Exercise 2 (Easy): You warm 500,000 keys at deploy time with EX 3600. What happens one hour later, and what's the one-line fix?
Solution

All 500,000 keys expire within the same second, because they were all created within the same second. Hit rate drops from ~99% to ~0% instantly and the database takes the full read load — a self-inflicted avalanche that recurs every hour for as long as the warming job runs on a schedule.

Fix — jitter the TTL:
   ttl = 3600 + random.randint(0, 360)     # ±10%

Now expiry is spread over 6 minutes instead of 1 second.
At 500K keys / 360 s ≈ 1,400 refills/s — an easy trickle
instead of a cliff.

Worth adding: jitter is the general cure for any synchronised behaviour in distributed systems — retry backoff, health check intervals, cron jobs, and metric flush timers all cause thundering herds when perfectly aligned. Whenever many actors share a schedule, randomise it.

Exercise 3 (Medium): Write pseudocode for a cache-aside read with stampede protection via per-key locking. Handle the case where the lock holder crashes.
Solution 
def get(key):
    v = cache.get(key)
    if v is not None:
        return None if v == NULL_SENTINEL else v      # negative caching

    # Miss. Try to become the single rebuilder.
    got_lock = cache.set(f"{key}:lock", me, nx=True, ex=5)   # 5s lock TTL
    if got_lock:
        try:
            v = db.read(key)
            # cache negatives too, or nonexistent keys penetrate forever
            cache.set(key, v if v is not None else NULL_SENTINEL,
                      ex=jitter(300) if v is not None else 60)
            return v
        finally:
            cache.delete(f"{key}:lock")     # always release
    else:
        # Someone else is rebuilding. Wait briefly and re-read.
        for _ in range(10):                 # bounded: never wait forever
            sleep(0.05)
            v = cache.get(key)
            if v is not None:
                return None if v == NULL_SENTINEL else v
        # Rebuilder died or is slow: fall back to the DB rather than
        # failing the request. Some herd is better than an error.
        return db.read(key)

Crash handling is the point of the exercise. Three defences are present: the lock has its own ex=5 TTL so a dead holder's lock evaporates; the release is in a finally so exceptions don't leak it; and waiters are bounded — after ~500 ms they query the DB themselves rather than waiting indefinitely. Without that bound, a crashed rebuilder converts a stampede into a total stall, which is worse.

Production refinement: prefer stale-while-revalidate over locking where you can. Have waiters serve the previous value instead of sleeping, which removes the latency spike entirely. Also store the lock owner and check it before deleting, so a slow holder can't release a lock that has since expired and been acquired by someone else.

Exercise 4 (Medium): An attacker requests random nonexistent user IDs at 50,000 req/s. Your cache is useless against this. Design a defence with a cost estimate.
Solution

This is cache penetration: misses on nonexistent keys reach the DB by definition, so the cache provides no protection. Layered defence, cheapest first:

Layer 1 — validate the ID format (free). If IDs are UUIDs or Snowflake-shaped, most random garbage fails a syntactic check at the edge with zero lookups. Often removes the bulk of unsophisticated attacks.

Layer 2 — negative caching (cheap). SET user:{id} "__NULL__" EX 60. Repeat requests for the same bad ID now hit the cache. Against random IDs this helps less, and it introduces a new risk: 50,000 tombstones/s could evict your real working set. Bound it with a dedicated small cache or a separate Redis DB for negatives.

Layer 3 — Bloom filter (the real fix). Keep a Bloom filter of all existing user IDs. "Definitely not present" is trustworthy (no false negatives), so reject without touching cache or DB.

Cost for 100M existing users at 1% false-positive rate:
   ≈ 9.6 bits/key × 100M  ≈ 120 MB   — trivially fits in memory
   1% false positives → 500 of 50,000 req/s reach the DB. Survivable.

At 0.1% FP: ≈ 14.4 bits/key ≈ 180 MB, 50 req/s reach the DB.

Layer 4 — rate limit per client (IP, API key). 50,000 req/s from few sources is trivially throttled; distributed across a botnet it isn't, which is why the Bloom filter carries the real load.

Operational caveat to mention: a standard Bloom filter can't delete, so a deleted user stays "present" — acceptable, since a false positive is just one wasted lookup. Rebuild periodically, or use a counting / cuckoo filter if deletions are frequent. See Bloom Filters & Merkle Trees.

Cross-cutting decisions worth stating:

• Different data, different patterns, one system. The insight this exercise tests is that "how do you cache?" has four different answers inside one product, chosen by read/write ratio, shareability and loss tolerance.
• Breaking-news traffic spike is the failure scenario to design for: one article goes from 0 to 500K req/s. The CDN absorbs it (same URL for everyone), but the view counter becomes a hot key — split it into views:{id}#0..9 and sum on read.
• Editorial correction must be instant. A libellous sentence can't sit in a CDN for 5 minutes, so explicit purge is required — the TTL alone is insufficient. This is a case where the business demands invalidation, not expiry.
• Degradation plan: if Redis dies, articles still serve from the CDN, view counts stop updating (invisible), and recommendations fall back to a generic "most popular" list. The site stays up with reduced personalisation — decided in advance, not during the incident.

Exercise 6 (Hard): A team caches permission checks (can_user_edit(user, doc)) with a 15-minute TTL to reduce load. Explain what's wrong, then design something that's both fast and correct.
Solution

What's wrong: they've cached a decision rather than data, which makes revocation take effect up to 15 minutes late. Concretely: an employee is fired and retains edit access for 15 minutes; a document is unshared and the removed collaborator keeps writing; a compromised account's access survives the lockout. This is a security vulnerability with a timer, and it will be found in an audit rather than by monitoring — worse, shortening the TTL only reduces the window, it never closes it.

A second, subtler problem: the cache key must capture everything the decision depends on. If permission derives from group membership, document ACL, org policy and sharing link state, then a (user, doc) key is invalidated by changes to any of four different entities — and the team almost certainly isn't tracking all four.

Design that's fast and correct:

1. Cache the inputs, evaluate the decision. Cache the user's group memberships and the document's ACL — both cheap, both stable — then run the (in-memory, microsecond) policy evaluation on every request. You keep almost all the performance win because the expensive part was the I/O, not the boolean logic. This alone resolves most of the problem.

2. Make revocation push-based, not expiry-based. On any permission change, publish an event that invalidates the affected keys immediately — ideally via CDC so an application crash can't skip it. Now correctness comes from invalidation and the TTL is only a safety net.

3. Add a revocation epoch for instant global kill. Keep a per-user permissions_version counter; include it in every cache key. Bumping it invalidates that user's entire cached authorisation state atomically with one write — no key enumeration required. This is how you handle "revoke everything for this account right now" during a security incident.

key = f"perm:{user_id}:v{user_epoch}:{doc_id}"
# Bump user_epoch → every old key is unreachable instantly.

4. Keep TTLs short where a decision is cached at all (seconds, not minutes), and fail closed — if the cache and the permission service are both unreachable, deny rather than allow. A cache miss must never be interpreted as permission granted.

5. Asymmetric caching. Cache denials longer than grants. A stale denial is an annoyance ("refresh the page"); a stale grant is a breach. Making the TTL depend on the direction of the answer is a nice senior touch.

The transferable principle: cache facts, not verdicts. Facts have owners and change events; verdicts are derived from several facts at once and go stale in ways no single invalidation catches.

🎯 Key Takeaways

  • Hit-rate payoff is non-linear — 90% → 99% removes 90% of the remaining database load. The last few percent carry most of the value.
  • At a high hit rate the cache IS your capacity, not an optimisation. At 99%, losing it is a 100× spike, so it needs HA, warming and rolling restarts.
  • Cache-aside is the default because cache failure degrades to slow rather than broken.
  • Delete, don't update — deletes are idempotent and order-independent. And write the DB first, then delete, for the narrower race window.
  • Always set a TTL, even with explicit invalidation: it converts unbounded staleness into bounded staleness when invalidation is skipped by a crash or a dropped message.
  • Derive TTLs from business tolerance, not round numbers. Best of all: content-address immutable data so the key changes when the content does.
  • Three failure modes, one shape — stampede, penetration and avalanche all end with the DB inheriting traffic it wasn't sized for. Protect the DB directly: rate-limit, shed load, serve stale, degrade features.
  • Jitter every TTL. Keys created together expire together, which is a scheduled outage.
  • Write-back trades durability for throughput — correct for view counters, fraud for balances. The data's loss tolerance decides, not the traffic shape.
  • Cache facts, not verdicts. Caching authorisation decisions is a security hole with a timer; cache the inputs and re-evaluate.
  • Invalidate via events or CDC across services. App-side invalidation can always be skipped by a crash between the write and the delete; a commit log can't be.
