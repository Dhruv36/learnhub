Consistent Hashing Fundamentals

What you'll master: why hash(key) % N is catastrophic when N changes, how the hash ring fixes it with arithmetic you can do on a whiteboard, why virtual nodes are mandatory rather than optional, the crucial distinction between balancing keys and balancing load, and when to reach for rendezvous or jump hashing instead of a ring at all.

Prerequisites: Back-of-Envelope Estimation, CAP Theorem. This is the partitioning mechanism behind Caching Strategies, Design a Key-Value Store and Replication & Failover.

1. The Problem: Why Modulo Hashing Breaks

You have 4 cache servers and route keys with hash(key) % 4. It's uniform, it's O(1), it works. Then one server dies and you're down to 3. Watch what happens to the mapping:

key       hash(key)   % 4        % 3        moved?
────────────────────────────────────────────────────────
user:1        100      0          1          ✗ MOVED
user:2        101      1          2          ✗ MOVED
user:3        102      2          0          ✗ MOVED
user:4        103      3          1          ✗ MOVED
user:5        104      0          2          ✗ MOVED
user:6        105      1          0          ✗ MOVED
user:7        106      2          1          ✗ MOVED
user:8        107      3          2          ✗ MOVED

Every single key moved. That isn't bad luck — it's the arithmetic. Changing the divisor changes the remainder for essentially every input. The general result:

Fraction of keys that remap when N → N−1 under modulo hashing:
   ≈ (N−1)/N     →  4 servers: 75%     10 servers: 90%     100 servers: 99%

Fraction under consistent hashing:
   ≈ 1/N         →  4 servers: 25%     10 servers: 10%     100 servers: 1%

Why is that a production emergency rather than an inconvenience? Estimate it, using the method from the previous lesson:

Cache tier: 10 nodes, 90% hit rate, backing DB sized for the 10% miss traffic.
Normal:  600,000 reads/s × 10% miss  =  60,000 QPS to the DB  ✓ survivable

One node dies under MODULO hashing → 90% of keys remap → near-total cache miss:
         600,000 reads/s × ~100%     = 600,000 QPS to the DB  ✗ 10× over capacity
         → DB saturates → timeouts → retries → cascading failure

Same failure under CONSISTENT hashing → ~10% of keys remap:
         600,000 × (10% miss + 10% remapped) ≈ 120,000 QPS   ✓ 2× spike, absorbable
💡 This is the whole point, and it's worth saying in exactly these terms: consistent hashing isn't about elegance — it converts a node failure from a total cache flush that takes down your database into a bounded, survivable traffic spike. The blast radius is the feature.

2. The Ring, Built Step by Step

Take the hash output space — say 32-bit, so 0 to 2³²−1 — and bend it into a circle so the largest value wraps around to 0. Hash servers onto the same circle you hash keys onto. That single idea is the trick: servers and keys share one address space.

Step 1 — place servers by hashing their IDs onto the ring (0 … 2³²−1,
         shown here scaled to 0–360 for readability):

                        0/360
                          │
              A (50) ●    │
                     ╲    │
                      ╲   │
        C (280) ●──────  ring  ──────● B (160)
                          │
                          │

Step 2 — place a key by hashing it the same way.
Step 3 — walk CLOCKWISE from the key's position; the first
         server you meet owns that key.

  key "user:1"  → hash 30   → clockwise → A (50)     ✓
  key "user:2"  → hash 100  → clockwise → B (160)    ✓
  key "user:3"  → hash 200  → clockwise → C (280)    ✓
  key "user:4"  → hash 300  → clockwise → wraps past 360 → A (50)  ✓

Now the operations that used to be catastrophic:

ADD server D at position 120:

  Before:  keys in (50, 160]  → B
  After:   keys in (50, 120]  → D      ← only these move
           keys in (120, 160] → B      ← untouched

  Only the range between D and its PREDECESSOR moves, and it all comes
  from exactly ONE server (D's successor, B). Every other server is
  completely unaffected — it doesn't even need to be told.

REMOVE server B (at 160):

  keys in (120, 160] → C     ← B's range passes to its successor
  Everything else untouched.

The property that makes it work: adding or removing a node only ever disturbs the arc between that node and its neighbour. Nothing else on the ring is recomputed, so no other server's keys move.

3. Implementation (Small Enough To Write In An Interview)

Interviewers sometimes ask you to code this. It's about 20 lines, and the only real insight is "sorted array + binary search".

class ConsistentHash:
    def __init__(self, nodes=(), vnodes=150):
        self.vnodes = vnodes
        self.ring = {}          # position -> node
        self._sorted = []       # sorted positions, for binary search
        for n in nodes:
            self.add(n)

    def _hash(self, key):
        # MD5 is fine here: we need uniform distribution, NOT security.
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def add(self, node):
        for i in range(self.vnodes):                  # 150 positions per node
            pos = self._hash(f"{node}#{i}")
            self.ring[pos] = node
        self._sorted = sorted(self.ring)              # rebuild index

    def remove(self, node):
        for i in range(self.vnodes):
            del self.ring[self._hash(f"{node}#{i}")]
        self._sorted = sorted(self.ring)

    def get(self, key):
        if not self.ring:
            return None
        h = self._hash(key)
        # first position >= h, wrapping to index 0 -- this IS the clockwise walk
        i = bisect.bisect_left(self._sorted, h) % len(self._sorted)
        return self.ring[self._sorted[i]]

Complexity, which is the standard follow-up:

OperationCostNote
Lookup get(key)O(log V)V = total vnodes = nodes × vnodes-per-node. Binary search over sorted positions.
Add / remove nodeO(V log V)Dominated by re-sorting. Use a balanced BST / skip list for O(log V) inserts if churn is high.
MemoryO(V)10 nodes × 150 vnodes = 1,500 entries. Trivial.
Keys remapped on changeO(K/N)K keys, N nodes — the whole reason we're here.
💡 Two details that signal experience: (1) use a fast non-cryptographic hash — MurmurHash3 or xxHash — in production; MD5 is ~10× slower and you need uniformity, not collision resistance. (2) Every client must use the identical hash function and vnode count, or they'll disagree about ownership. That's why Ketama is a specified algorithm rather than "just use a ring" — the spec is the interop contract.

4. Virtual Nodes: Why They're Mandatory, Not An Optimisation

Hash 3 servers onto a ring and you will not get 33% each. Random placement is lumpy — this is the same reason random points on a line leave uneven gaps.

3 servers hashed onto the ring, one plausible outcome:

  A at 50, B at 160, C at 280
  A owns (280 → 50]  =  130/360  = 36%
  B owns (50 → 160]  =  110/360  = 31%
  C owns (160 → 280] =  120/360  = 33%     ← got lucky

Another, equally likely:
  A at 10, B at 30, C at 300
  A owns (300 → 10]  =  70/360   = 19%
  B owns (10 → 30]   =  20/360   =  6%     ← owns almost nothing
  C owns (30 → 300]  = 270/360   = 75%     ← owns three quarters!

C now takes 4× its share of traffic and will fall over first,
while B sits idle. The ring is "correct" and the cluster is broken.

Fix: place each physical server at many positions on the ring, using hash(server_id + "#" + i) for i in 0..149. With many small arcs per server, the law of large numbers smooths the distribution:

Vnodes per serverTypical load spread (std dev)Verdict
1±30–40%Unusable — a random server owns 3× its share
10±10%Still lumpy enough to cause hot nodes
100±3%Good
150±2.5%The industry default (Ketama, Cassandra's old default)
1000±1%Diminishing returns; lookup and memory costs grow

Vnodes buy three more things that are easy to forget in an interview:

1. Weighted capacity. A machine with twice the RAM gets 300 vnodes instead of 150 and organically receives twice the keys. Heterogeneous clusters become trivial.
2. Spread recovery load. When a node dies without vnodes, its entire range lands on one successor — which may then also fall over (cascading failure). With 150 vnodes, the dead node's ranges are distributed across many surviving nodes, each absorbing ~1/N of the load.
3. Faster rebuilds. A recovering node streams data from many peers in parallel rather than from a single successor.

5. Deep Dive: Consistent Hashing Balances Keys, Not Load

This is the most important limitation, and the thing that separates people who've read about the technique from people who've operated it.

The ring guarantees each node owns roughly the same number of keys. It guarantees nothing about how often those keys are accessed. Real traffic is Zipfian: a small fraction of keys take a huge fraction of requests.

10 nodes, 150 vnodes each, perfectly balanced: 10% of keys per node. ✓

But: one celebrity's profile is 5% of ALL read traffic, and it is
     ONE key, hashing to ONE vnode, on ONE node.

  Node holding it:  10% of keys  +  5% of total traffic on a single key
  → that node is hot, and adding nodes does NOT help:
    the hot key still maps to exactly one node no matter how big the ring.

Scaling out is powerless against a hot key. This is why "just add
more cache servers" fails, and why every large system has a
separate story for hot keys.

Four real mitigations, in rough order of how often they're used:

TechniqueMechanismCost
Key splittingStore the hot key as celebrity:1#0 … #9, write to all copies, read from a random one. 10 copies → 10 nodes share the load.Writes amplify 10×; reads need a fan-in for anything needing all shards. Best for read-heavy hot keys.
Client-side / L1 cacheCache the hottest keys in the application process for a few seconds. A 5%-of-traffic key gets ~100% local hit rate.Staleness bounded by TTL; memory per app instance. Extremely effective — usually the first thing to try.
Dedicated hot tierDetect hot keys (streaming top-K, e.g. count-min sketch) and promote them to a replicated tier that every node can serve.Extra infrastructure plus a detection pipeline.
Bounded-load consistent hashingCap each node at ⌈average × c⌉ (c ≈ 1.25). If the target node is at capacity, walk clockwise to the next one with room.Lookups may need multiple hops and nodes must share load state. Used at Google and Vimeo; solves skew generally, not single-key heat.
🎯 Staff-level insight: notice that key splitting and bounded-load solve different problems. Bounded-load fixes many moderately warm keys landing together. Neither the ring nor bounded-load can fix one key receiving 5% of traffic — that requires replication of the key itself (splitting, or a local cache). Diagnose which flavour of hotness you have before choosing a cure; teams routinely deploy the wrong one and see no improvement.

6. Deep Dive: Data Movement When a Node Joins

The ring tells you the new mapping instantly. Moving the actual bytes is the hard part, and during the move there's a window where the mapping and the data disagree.

Node D joins, claiming range (50, 120] from node B.

Naive: flip the mapping immediately.
  → reads for those keys now go to D, which has NO DATA
  → 100% miss for that range; for a cache, a stampede to the DB;
    for a database, wrong answers (missing rows). Unacceptable.

Correct sequence:
  1. D joins as a "pending" owner of (50, 120] — mapping not yet live.
  2. B STREAMS the range to D in the background (bulk transfer).
  3. Writes during the transfer go to BOTH B and D (dual write),
     or B keeps a log of mutations to replay onto D at the end.
  4. When D has caught up, atomically flip the mapping — usually via
     a coordination service (etcd/ZooKeeper) so all clients switch together.
  5. B drops the range (after a grace period, in case of rollback).

Dynamo-style AP systems can be looser about this because quorum reads paper over the gap: while ownership is in flux, a read that consults R replicas still finds the data on one of the old owners, and hinted handoff plus read repair (see Replication & Failover) converge the state afterwards. CP systems must complete the handoff properly before flipping, because a missing row is a wrong answer rather than a cache miss.

For a pure cache the calculus changes entirely: don't move data at all. Let the ~1/N remapped keys miss and refill naturally — that's cheaper than building a transfer protocol, and it's precisely why the 1/N bound matters so much for caches.

7. Deep Dive: Alternatives, And When They're Better

A ring is not always the right answer. Knowing the alternatives is a strong senior signal because it shows you're choosing rather than reciting.

AlgorithmHow it worksUse when / avoid when
Ring (Ketama)Sorted vnode positions, binary search clockwiseThe default. Handles arbitrary add/remove, weighting, and range ownership (needed for replication). Costs memory for vnodes and O(log V) lookups.
Rendezvous / HRWFor a key, compute hash(key, node) for every node; highest score winsSimpler and better distributed — no vnodes, no ring state, perfect 1/N balance, trivially weighted. But O(N) per lookup, so ideal for small N (say < 100 nodes) — very common for shard selection inside a service.
Jump hashClever O(1)-memory, O(log N)-time function mapping a key to bucket 0..N−1 with optimal balanceBeautiful and fast, but buckets are only addressable by index — you can only add/remove the last bucket. Great for a fixed shard count you scale by appending; useless when arbitrary nodes die.
MaglevBuilds a fixed-size lookup table with near-perfect balance and minimal disruptionGoogle's load balancer hashing. O(1) lookups, excellent balance; table build is expensive, so best when membership changes are infrequent relative to lookup volume.
Bounded-load ringRing plus a per-node capacity cap, overflow walks clockwiseWhen key balance is fine but load skews. Needs shared load state and adds lookup hops.
💡 The interview-winning comparison: "For a 20-node shard router I'd actually use rendezvous hashing rather than a ring — O(20) per lookup is nothing, it needs no vnode bookkeeping, and it gives better balance than 150 vnodes would. I'd reach for the ring specifically when I need range ownership — because replication ('the next 3 nodes clockwise hold the replicas') falls out of the ring naturally, and HRW gives you an ordering per key but no shared notion of adjacency."

Interview Questions

🟢 Beginner — What problem does consistent hashing solve, in one sentence with a number?

It reduces the fraction of keys that must be remapped when the server count changes from ~(N−1)/N under modulo hashing to ~1/N. With 10 servers, losing one remaps 90% of keys with modulo versus 10% with consistent hashing.

Why that matters concretely: for a cache tier, remapping means missing. A 90% remap turns a 90% hit rate into a near-total miss, and the database that was comfortably serving 10% of read traffic suddenly receives all of it — typically 10× its provisioned capacity, which cascades into a full outage. Consistent hashing turns the same node failure into a bounded ~2× spike the database can absorb. The technique exists to contain blast radius.

🟢 Beginner — Explain how a key finds its server on the ring, and what happens when a node is added.

Both servers and keys are hashed into the same circular space (0 to 2³²−1, wrapping at the top). To find a key's owner you hash the key, then walk clockwise until you hit the first server position; that server owns the key. In code this is a binary search for the first server position ≥ the key's hash, wrapping to index 0 if you run off the end — O(log V).

When you add a node, it lands somewhere on the ring and claims only the arc between itself and its predecessor. Those keys previously belonged to its clockwise successor, so exactly one existing server hands over exactly one contiguous range. Every other server's keys are untouched and no other server even needs to be notified. Removal is the mirror image: the departing node's range passes to its successor, nothing else moves.

🟡 Mid — Why are virtual nodes necessary? What breaks without them?

Because hashing a handful of servers onto a ring produces uneven arcs. Random points on a circle don't divide it evenly — with 3 servers you might get a 19% / 6% / 75% split, meaning one node takes 4× its share of traffic and falls over while another idles. The ring is functioning correctly and the cluster is still broken.

Virtual nodes fix this by placing each physical server at ~150 positions via hash(server_id + "#" + i). Averaging over many small arcs brings the spread to roughly ±2.5%.

Three additional benefits I'd mention:

• Weighted capacity — a machine with double the resources gets 300 vnodes instead of 150 and naturally receives double the keys, making heterogeneous clusters easy.
• Spread failure load — this is the big one. Without vnodes, a dead node's entire range lands on its single successor, doubling that node's load and risking a cascade. With vnodes, the dead node's many small ranges scatter across all survivors, each absorbing ~1/N.
• Parallel rebuild — a replacement node streams from many peers at once instead of serially from one successor.

The cost is modest: O(V) memory (10 nodes × 150 = 1,500 entries) and O(log V) lookups, which is why 150 became the default rather than 10 or 10,000.

🟡 Mid — A node joins the ring. Who moves the data, and what does a client read during the move?

The successor moves it. The joining node claims the arc between itself and its predecessor; all of those keys currently live on its clockwise successor, so that one node streams the range over. Only two nodes participate.

The danger is the window where the mapping and the data disagree. If you flip the mapping first, reads hit a node with no data: for a cache that's a stampede to the database for that whole range, and for a database it's wrong answers — missing rows. So the correct sequence is:

1. New node joins as pending owner; mapping not yet live.
2. Successor bulk-streams the range in the background.
3. Concurrent writes go to both nodes (dual write), or the successor logs mutations to replay at cutover.
4. Once caught up, flip the mapping atomically — via etcd/ZooKeeper so all clients switch together, since clients disagreeing about ownership is its own bug.
5. Old owner drops the range after a grace period, so you can roll back.

AP systems can be looser: quorum reads still find the data on old owners, and hinted handoff plus read repair converge things afterwards. And for a pure cache, don't move data at all — let the ~1/N remapped keys miss and refill. Building a transfer protocol for data you can cheaply recompute is wasted work; that's exactly why the 1/N bound is what makes caches viable.

🔴 Senior — Your ring is perfectly balanced by key count but one node is at 90% CPU while others sit at 30%. Diagnose.

Consistent hashing balances keys, not load. Perfect key distribution says nothing about access frequency, and real traffic is Zipfian. I'd work through three distinct causes, because they need different fixes and deploying the wrong one produces no improvement:

1. A single hot key. One celebrity profile or one viral item taking 5% of all reads hashes to exactly one vnode on one node. Critically, adding nodes does not help — the key still maps to one place. Diagnose with per-key metrics or a count-min sketch top-K. Fix by replicating the key: split it into key#0..#9 and read a random replica, or (usually best first move) add a short-TTL in-process L1 cache so the hottest keys never leave the app server.

2. Many moderately warm keys colliding. Ring randomness put several warm ranges on one node. Here bounded-load consistent hashing is the right tool: cap each node at ⌈average × 1.25⌉ and let overflow walk clockwise. Also worth increasing vnode count.

3. Not hashing at all — heterogeneous hardware or a noisy neighbour. Always rule this out before redesigning the hash: an older instance type, a co-tenant, or a background repair/compaction job on that node explains the symptom with no ring involvement. Check whether the node's request rate is actually elevated or just its CPU. If request rate is even, the ring is innocent.

Diagnostic order: compare request rate per node → if even, it's hardware/local work; if skewed, get top-K keys → one dominant key means replicate it, a spread of warm keys means bounded-load.

🔴 Senior — When would you NOT use ring-based consistent hashing?

Four situations, each with a better tool:

1. Small, fixed node count → rendezvous (HRW) hashing. For a 20-node shard router, computing hash(key, node) for all 20 and taking the max is O(20) — nothing — and gives perfect 1/N balance with no vnode bookkeeping, no ring state, and trivial weighting. Simpler and better; the ring's advantage only appears at large N.

2. Append-only scaling → jump hash. O(1) memory, optimal balance, but buckets are addressable only by index, so you can only add/remove the last one. Perfect for a shard count you grow by appending; useless when arbitrary nodes fail.

3. Stable membership with extreme lookup volume → Maglev. A precomputed table gives O(1) lookups and near-perfect balance; the expensive table rebuild is amortised when membership rarely changes. This is why it's in Google's load balancer.

4. When the data has a natural partition key → don't hash at all. This is the one people miss. Multi-tenant systems often partition by tenant_id range so a tenant's data is co-located (enabling local joins and transactions), and geo-partitioned systems shard by region for data-residency law and latency. Hashing deliberately destroys locality — sometimes locality is the requirement, and a directory/lookup service beats any hash function.

The one thing that keeps me on a ring: range ownership. Replication ("the next RF−1 nodes clockwise hold the copies") falls out of ring adjacency for free. HRW gives a per-key node ordering but no shared notion of adjacency, so if I need coordinated replica placement, streaming ranges, and Merkle-tree repair between neighbours, the ring earns its complexity.

🏋️ Graded Exercises

Exercise 1 (Easy): You have 5 cache servers using hash(key) % 5 and add a 6th. Roughly what fraction of keys remap, and what does that do to your database?
Solution 
Modulo: changing the divisor from 5 to 6 remaps keys whose
        hash % 5 ≠ hash % 6 — approximately 5/6 ≈ 83% of keys.

Consistent hashing: ~1/6 ≈ 17%.

Consequence: with an 85% hit rate before the change, an 83% remap means the cache is effectively cold — the database briefly receives close to 100% of read traffic instead of 15%, roughly a 6× spike. If the DB was provisioned with less than 6× headroom (it was), you get timeouts, client retries amplifying load further, and an outage caused by adding capacity. That irony — scaling up taking you down — is the classic war story this technique prevents.

Exercise 2 (Easy): Servers hash to positions A=100, B=200, C=300 on a 0–399 ring. Which server owns keys hashing to 50, 150, 250, 350?
Solution 
Rule: first server clockwise (next position ≥ key hash, wrapping).

  key 50   → next ≥ 50  is 100  → A
  key 150  → next ≥ 150 is 200  → B
  key 250  → next ≥ 250 is 300  → C
  key 350  → nothing ≥ 350 → WRAPS to lowest position 100 → A

The wrap case is what interviewers check — it's the off-by-one bug in every first implementation. In code it's bisect_left(positions, h) % len(positions); the modulo is the wrap.

Note the ownership split here: A owns (300→100] = 200/400 = 50% of the ring, B and C own 25% each. Three servers, and one has double the load — exactly the imbalance virtual nodes exist to fix.

Exercise 3 (Medium): Implement get(key) for a ring given a sorted list of vnode positions, then state its complexity and the one edge case.
Solution 
def get(self, key):
    if not self._sorted:              # edge case 0: empty ring
        return None
    h = self._hash(key)
    i = bisect.bisect_left(self._sorted, h)
    if i == len(self._sorted):        # THE edge case: past the last position
        i = 0                         # wrap to the first (equivalently: % len)
    return self.ring[self._sorted[i]]

Complexity: O(log V) time via binary search, where V = nodes × vnodes-per-node (e.g. 10 × 150 = 1,500). O(V) memory. Note it's log of vnode count, not node count — one reason not to set vnodes to 10,000.

The edge case is a key hashing above every vnode position, which must wrap to index 0. Forgetting it throws IndexError for the fraction of keys above your highest vnode — a bug that only appears in production, intermittently, for a small slice of keys. Also handle the empty ring separately, or % 0 raises.

bisect_left versus bisect_right only matters when a key hashes exactly onto a vnode position — pick one and use it in every client, since a mismatch means clients disagree about ownership for those keys.

Exercise 4 (Medium): A 10-node Redis cluster has 150 vnodes each and is perfectly balanced, but p99 latency is terrible on one node. Metrics show its request rate is 4× the others. Walk through diagnosis and fix.
Solution

Elevated request rate (not just CPU) rules out hardware and background jobs, so this is genuine traffic skew — the ring is balancing keys while load is Zipfian.

Diagnose: get the top-K keys by request count on that node — redis-cli --hotkeys, MONITOR sampling, or a count-min sketch in the client. The shape of the answer decides the fix:

Case A — one key dominates (e.g. trending:homepage at 5% of all traffic). Adding nodes cannot help; that key maps to one node forever. Fixes, in the order I'd actually deploy them:

1. In-process L1 cache, 1–5s TTL.  A key taking 5% of traffic gets a
   ~100% local hit rate — the request never reaches Redis. Cheapest,
   fastest, biggest win. Cost: up to TTL staleness.
2. Key splitting: write trending:homepage#0..#9, read a random suffix.
   Spreads load across 10 nodes. Cost: 10× write amplification.
3. Replicate to all nodes and read locally, if the value is small and
   changes rarely.

Case B — many warm keys collided on that node. Then increase vnode count (150 → 500) to smooth placement, or adopt bounded-load consistent hashing (cap ⌈avg × 1.25⌉, overflow walks clockwise).

Verify before and after with per-node request rate, not CPU — and confirm the hot key didn't simply move to a different node, which is what happens if you reshuffle the ring instead of replicating the key.

Exercise 5 (Hard): Design the migration from hash(key) % 8 to consistent hashing for a live 8-node cache serving 500K QPS, with no cold-cache incident.
Solution

The trap: flipping the algorithm in one deploy remaps ~87% of keys at once — precisely the cold-cache stampede we're trying to prevent forever. So the migration must never have a moment where a large key range has no warm home.

Approach — dual-read with a gradual cutover:

Phase 1. Ship the ring alongside modulo. Config flag, ring NOT authoritative.
         Both mappings computable in the client; no behaviour change yet.

Phase 2. DUAL READ:
           v = ring_get(key)          # new mapping
           if v is None:
               v = modulo_get(key)    # fall back to old mapping
               if v: ring_set(key, v) # populate the new home (warm it)
         → Miss on the new ring silently repairs from the old one.
           No DB traffic increase: fallback finds the data warm.
           Writes go to BOTH during this phase, so neither map goes stale.

Phase 3. Watch ring hit rate climb (minutes to hours, per your TTLs).
         Wait for ring hit rate ≈ old hit rate. This is the gate.

Phase 4. Stop dual-writing and drop the modulo fallback. Ring authoritative.

Phase 5. Remove the modulo code path.

Why this works: at no point is a key range served by an empty node — every new-ring miss is backstopped by the old mapping, and the backstop is warm. The database never sees the spike. Cost is a temporary 2× memory footprint (each key cached in both its old and new home) and doubled writes, both of which are acceptable and, crucially, both temporary.

Details that make it a senior answer: (1) Roll out the client change progressively — 1% of app instances, then 10%, then 100% — since a bug in the ring implementation is then a 1% problem. (2) All clients must share the identical hash function and vnode count; ship that as versioned config, not a code constant, so a partial deploy can't split the cluster's view of ownership. (3) Verify the 2× memory actually fits before starting, or Phase 2 triggers evictions and causes the very incident you're avoiding. (4) Have a kill switch: the flag must flip back to modulo-only instantly. (5) If memory headroom is tight, migrate one key prefix at a time instead of all keys at once.

Exercise 6 (Hard): Your ring maps keys to nodes and you now need 3 replicas of each key. Design replica placement, and identify the failure mode of the obvious approach.
Solution

The obvious approach: a key's replicas are the next 3 vnode positions clockwise from its hash. This is what Dynamo describes and it's the natural extension of the ring.

The failure mode: with virtual nodes, consecutive vnode positions frequently belong to the same physical node. With 10 nodes × 150 vnodes, the chance that the next two vnodes are both a different physical machine is far from certain — so "3 replicas" can silently become 2 or even 1 physical copy. One machine dies and you've lost data you believed was triple-replicated. Worse, it's invisible until the failure.

Fix: walk clockwise SKIPPING vnodes whose physical node is already
     in the replica set — the "preference list" from the Dynamo paper.

  def replicas(self, key, rf=3):
      out = []
      i = bisect.bisect_left(self._sorted, self._hash(key))
      for _ in range(len(self._sorted)):          # bounded scan
          node = self.ring[self._sorted[i % len(self._sorted)]]
          if node not in out:                     # skip duplicate physical nodes
              out.append(node)
              if len(out) == rf:
                  break
          i += 1
      return out

Then extend it to failure domains, which is the real production requirement: three copies on three machines in the same rack or AZ all die together in one power or network event. So the preference list should skip nodes sharing a failure domain, giving one replica per AZ. Cassandra calls this NetworkTopologyStrategy.

Consequences to state: (1) Cross-AZ replication costs write latency (~1–2 ms per hop) and inter-AZ bandwidth charges — a real line on the bill. (2) You must be able to place RF replicas in distinct domains at all: RF=3 across 2 AZs is unsatisfiable, so topology constrains your replication factor. (3) Combined with quorum (R+W>N), one-replica-per-AZ and W=2 means a whole AZ can fail with writes still succeeding — which is the actual goal, and it's only reachable because replica placement was made topology-aware rather than purely ring-adjacent.

🎯 Key Takeaways

  • Modulo hashing remaps ~(N−1)/N of keys when N changes; consistent hashing remaps ~1/N. That's the difference between a cache flush that kills your database and a survivable spike.
  • The ring: hash servers and keys into one circular space; a key belongs to the first server clockwise. Adding or removing a node only disturbs one arc.
  • Lookup is O(log V) — binary search over sorted vnode positions. The wrap-around at the top of the ring is the edge case everyone's first implementation gets wrong.
  • Virtual nodes are mandatory, not an optimisation: without them one node can own 3–4× its share, and a dead node dumps its entire range on a single successor. Use ~150.
  • Consistent hashing balances keys, not load. One hot key saturates one node no matter how many you add — that needs replication of the key (splitting, L1 cache), not a better ring.
  • Never flip ownership before data has moved: stream, dual-write, then cut over atomically. For pure caches, skip the transfer and let 1/N miss.
  • Every client must use the identical hash and vnode count — ship it as versioned config, because disagreement about ownership is a silent, brutal bug.
  • The ring isn't always right: rendezvous (HRW) is simpler and better-balanced for small N; jump hash for append-only shards; Maglev for stable membership; a directory service when data locality matters more than uniformity.
  • Replica placement must skip duplicate physical nodes and failure domains, or "3 replicas" quietly becomes 1 copy on 1 machine in 1 rack.
