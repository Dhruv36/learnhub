Back-of-Envelope Estimation Fundamentals

What you'll master: how to turn a vague prompt ("design Twitter") into a handful of numbers that force architectural decisions — and how to say those numbers out loud in an interview without a calculator. By the end you'll be able to derive QPS, storage, bandwidth, memory and server count from first principles, know which numbers actually change a design, and recognise the three estimation mistakes that make an otherwise strong candidate look junior.

Prerequisites: How to Scale a System. This lesson feeds directly into CAP Theorem and every case study in section 3 — most of them open with the estimate you're about to learn how to build.

1. Why Estimate At All? (The Mental Model)

Beginners think estimation is a maths quiz the interviewer uses to check your arithmetic. It isn't. Estimation is how you earn the right to make a design decision. Every architectural claim you make later — "we need a cache", "we can't put this in Postgres", "one region is fine" — is either backed by a number or it's an opinion. Interviewers are listening for the number.

Consider two candidates answering "design an image host":

❌ Unbacked 
"I'll use S3 for the images
and put a CDN in front,
and Cassandra for metadata."
Correct-sounding, but indistinguishable from someone reciting a blog post. Nothing here proves you'd notice if the requirements changed by 100×.
✅ Backed 
"30M uploads/day × 1 MB = 30 TB/day.
That's ~11 PB/year, so this can't
live in a database — object storage
+ CDN. Metadata is only 30M × 500 B
= 15 GB/day, which any DB handles."
Same conclusion, but now it's derived. The interviewer knows you'd have chosen differently at 30 GB/day.
💡 The rule that makes estimation worth doing: if a number doesn't change your design, you estimated the wrong thing. Don't compute "total users in 5 years" because it sounds thorough — compute the number that decides between two architectures you're actually weighing.

2. The Only Numbers Worth Memorising

You need latency figures to reason about what's cheap and what's expensive. Learn the orders of magnitude and the ratios between them, not the digits.

OperationLatencyRelativeWhat it tells you
L1 cache reference~0.5 ns1×Memory access is effectively free. Never optimise CPU-local work in a design interview.
Branch mispredict~5 ns10×
Main memory reference~100 ns200×
Read 1 MB sequentially from memory~250 µs500,000×Bulk memory work is measured in microseconds — fine inside one request.
SSD random read~150 µs300,000×SSD is ~1000× slower than RAM but ~100× faster than spinning disk seek. This gap is why caches exist.
Read 1 MB from SSD~1 ms2,000,000×
Round trip, same datacenter~0.5 ms1,000,000×One network hop costs more than 5,000 memory reads. Chatty service calls are the #1 real-world latency bug.
Round trip, US ↔ Europe~150 ms300,000,000×Cross-region is 300× same-DC. This single number justifies read replicas, edge caching, and multi-region write locality.

Three ratios carry almost all the weight. Commit these instead of the table:

Memory : SSD : Network(local) : Network(cross-region)
   1   :  1000 :      5000       :     1,500,000

Read as: "SSD is a thousand times slower than RAM.
          A local network hop is worse than an SSD read.
          Crossing an ocean is 300× a local hop."

3. Cheat-Sheet Conversions (The Arithmetic Shortcuts)

The whole trick to doing this in your head is rounding a day to 105 seconds. It's 86,400, so you're 16% high — irrelevant when you're deciding between "a cache" and "no cache".

TIME
1 day  ≈ 86,400 s ≈ 10⁵ s        ← the single most useful approximation in system design
1 month ≈ 2.5 × 10⁶ s
1 year  ≈ 3 × 10⁷ s

QPS SHORTCUTS (all follow from 1 day ≈ 10⁵ s)
1 million requests/day  ≈  10 req/s
1 billion requests/day  ≈  10,000 req/s
100M daily users × 10 actions = 1B actions/day ≈ 10K QPS

POWERS OF TWO → DECIMAL
2¹⁰ ≈ 10³  (1 KB)      2²⁰ ≈ 10⁶  (1 MB)
2³⁰ ≈ 10⁹  (1 GB)      2⁴⁰ ≈ 10¹² (1 TB)      2⁵⁰ ≈ 10¹⁵ (1 PB)

TYPICAL OBJECT SIZES
char 1 B · int 4 B · long/timestamp 8 B · UUID 16 B
tweet/comment ≈ 200 B · URL record ≈ 500 B · user profile row ≈ 1 KB
thumbnail ≈ 20 KB · web page ≈ 100 KB · photo ≈ 300 KB–1 MB
minute of 1080p video ≈ 50 MB

THROUGHPUT CEILINGS PER COMMODITY BOX (know these to convert QPS → servers)
Simple app server        ≈ 1,000–5,000 QPS
Postgres/MySQL writes    ≈ 1,000–5,000 QPS (single primary)
Redis                    ≈ 100,000 ops/s
NIC (10 Gbps)            ≈ 1.25 GB/s
💡 Why round to 105 and not 86,400? Because estimation exists to pick an order of magnitude, and 105 lets you do every division by moving a decimal point while talking. A candidate who pulls out long division has stopped communicating and started calculating — that's the failure mode. Precision you can't compute out loud is worthless here.

4. The 5-Step Method, Applied Step by Step

Let's build a full estimate for Twitter, narrating exactly what you'd say. Watch how each step's output becomes the next step's input, and how every result triggers a design consequence.

Step 1 — Clarify scale, then state assumptions out loud

Never invent numbers silently. Ask for DAU; if the interviewer deflects ("you tell me"), propose a figure and get it confirmed. This turns your guesses into agreed premises you can't be blamed for later.

"Let me state my assumptions and you can correct me:
   300M monthly active users
   50% are daily active            → 150M DAU
   each DAU posts 2 tweets/day
   10% of tweets carry media, ~1 MB each
   read:write ratio of 100:1       (people scroll far more than they post)
   peak traffic = 2× average"

Step 2 — Write QPS first (it's always the smaller, easier number)

Writes/day = 150M DAU × 2 tweets     = 300M tweets/day
Write QPS  = 300M / 10⁵ s            = 3,000 tweets/s
Peak write = 3,000 × 2               = 6,000 tweets/s

→ CONSEQUENCE: 6,000 writes/s exceeds a single Postgres primary (~1–5K).
  So: shard by user_id, or accept a write-optimised store (Cassandra).
  This is a real fork in the design, decided by one number.

Step 3 — Derive read QPS from a stated ratio

Read QPS  = 3,000 × 100              = 300,000 reads/s
Peak read = 600,000 reads/s

→ CONSEQUENCE: 600K QPS is ~6 Redis boxes at 100K ops/s, versus
  hundreds of DB replicas. Caching isn't an optimisation here,
  it's the only affordable architecture. Also: at a 95% hit rate
  the DB still sees 30K QPS — so the cache doesn't remove sharding,
  it just makes the shard count sane.

Step 4 — Storage: per-item size × volume × retention

Text:  300M tweets × 200 B           = 60 GB/day    → 22 TB/year
Media: 30M (10%) × 1 MB              = 30 TB/day    → 11 PB/year
5-year media total                   ≈ 55 PB

→ CONSEQUENCE: the 500× gap between text and media is the whole story.
  Text (22 TB/yr) fits a sharded cluster comfortably.
  Media (11 PB/yr) must be object storage + CDN — putting 1 MB blobs
  in the DB would be the single worst decision available.
  55 PB also forces a lifecycle conversation: tiering cold media to
  glacier-class storage, transcoding to cheaper formats.

Step 5 — Bandwidth and memory (the steps candidates skip)

Egress: media reads dominate. If 20% of feed views load an image:
        600K reads/s × 0.2 × 300 KB   ≈ 36 GB/s of egress
→ CONSEQUENCE: 36 GB/s = ~290 Gbps. No origin serves this;
  it is a CDN problem by definition. It's also the biggest line
  on the cloud bill — egress pricing, not compute, dominates cost.

Cache memory: cache the hot 20% of a day's tweets (80/20 rule):
        300M tweets × 200 B × 0.2     ≈ 12 GB
→ CONSEQUENCE: 12 GB is astonishingly cheap — it fits in ONE machine's
  RAM. Working-set size, not total data size, sets your cache tier cost.
  This is why "just cache it" is usually right for text and never for video.
🎯 Staff-level insight: notice that not one of those five numbers was interesting on its own — each was interesting because it eliminated an option. 6,000 writes/s killed the single primary. 11 PB/year killed blobs-in-DB. 12 GB made the cache a no-brainer. Strong candidates don't present estimates as a table at the start and then forget them; they reach back for a number every time they make a choice. That's the behaviour being scored.

5. Deep Dive: Converting QPS Into Servers (And Why Peak ≠ Average)

"How many machines?" is the follow-up that separates people who've run systems from people who've read about them. The naive answer divides QPS by per-box throughput. Three corrections make it real:

CorrectionEffectReasoning
Design for peak, not average×2 to ×10Average load sizes a system that falls over daily at lunchtime. Social apps peak 2–3×; ticket sales and live sport spike 10–50×.
Headroom for failure÷0.7 or ÷N-1Run at ~70% utilisation. If one of three AZs dies, the survivors absorb its traffic — so any single AZ must be able to fail without the rest saturating.
Latency, not just throughputoften ×2+A box that does 5,000 QPS at 800 ms p99 fails a 100 ms SLO. Queueing theory bites hard past ~70% utilisation; you buy machines to keep latency down long before you need them for raw capacity.
Worked: 6,000 peak write QPS, app server does 2,000 QPS at acceptable p99
Raw:              6,000 / 2,000              = 3 servers
70% utilisation:  3 / 0.7                    ≈ 5 servers
Survive 1 AZ of 3 failing: need full capacity on 2/3 of fleet
                  5 / (2/3)                  ≈ 8 servers
→ "About 8, spread across 3 AZs." That answer shows three levels of thinking.

6. Deep Dive: When Estimation Changes the Answer Completely

The best use of an estimate is discovering the obvious design is wrong. Two classics:

Twitter's celebrity fan-out. Fan-out-on-write (push each tweet into every follower's precomputed feed) makes reads trivially cheap. Estimate it for a user with 100M followers:

1 tweet × 100M followers = 100M feed writes for ONE post.
At 6,000 tweets/s average that model is fine — but a single celebrity
tweet creates a 100M-row write storm and minutes of feed lag.

→ Neither pure model works. The real answer is HYBRID: fan-out-on-write
  for normal users, fan-out-on-read (fetch-and-merge at query time) for
  accounts above a follower threshold. You cannot discover that hybrid
  without doing the arithmetic — which is exactly why interviewers ask.

The rate limiter that doesn't need a database. A million users × one counter each, at 20 bytes per counter, is 20 MB. That fits in RAM on one node, which means the entire "where do we store rate-limit state" debate evaporates — Redis, or even local memory with approximate sync. An estimate that removes a component from your diagram is worth more than one that adds one.

Interview Questions

🟢 Beginner — Roughly how many requests per second is 1 million requests per day?

About 12 req/s, and in an interview you'd say "roughly 10 per second".

Derivation: a day is 86,400 s, which we round to 105. So 106 / 105 = 10 req/s. The exact figure is 11.6, and the rounding error is deliberate — at this scale the useful conclusion ("this is tiny, a single box handles it comfortably") is identical either way.

🟢 Beginner — Why do we estimate storage and QPS separately?

Because they constrain different tiers and can point in opposite directions.

QPS sizes your compute and caching tier; storage sizes your persistence tier and cost model. A system can be enormous in one and trivial in the other: a data warehouse holds petabytes at 10 QPS (storage problem, no caching needed), while a rate limiter does a million QPS against 20 MB of state (throughput problem, no storage concern). Conflating them produces the classic wrong answer — "it's big data, use Hadoop" — for what is actually a small-state, high-throughput problem.

🟡 Mid — You estimate 6,000 peak writes/s. Walk me from that number to a storage decision.

First, compare against the known ceiling: a single relational primary sustains roughly 1,000–5,000 writes/s, so 6,000 exceeds one node. That rules out the simplest option and forces a choice between three paths:

1. Shard the relational DB by a high-cardinality key (user_id). Keeps SQL, joins and transactions within a shard; costs you cross-shard queries and operational complexity.
2. Use a write-optimised store (Cassandra, DynamoDB) whose LSM-tree design absorbs writes far better; costs you joins, and you inherit eventual consistency.
3. Buffer the writes — put a queue (Kafka) in front and consume at a sustainable rate. Great for absorbing spikes, but only works if the write path tolerates async application.

Then pick using the access pattern, not preference: if reads are simple key lookups, option 2 is the least work. If the product needs transactions across entities, option 1. Say the number, name the ceiling it breaks, list the options, choose on a stated criterion — that's the full answer shape.

🟡 Mid — Your design needs 600K reads/s. How much do you cache, and how much DB traffic remains?

Start from the working set, not the total. With an 80/20 access distribution, caching the hot 20% of a day's data typically yields an 80–95% hit rate for social/feed workloads.

At 95%: 600K × 0.05 = 30K QPS still reaches the DB. That's the number that matters, and it's the one candidates forget — the cache didn't eliminate the database problem, it reduced it by 20×. 30K QPS of reads still needs read replicas or sharding.

Capacity-wise: 600K ops/s ÷ 100K per Redis node ≈ 6 nodes for throughput, and the hot text set is only ~12 GB so memory isn't the constraint — throughput and failure tolerance size this cluster, not data volume. Also state what happens on a cold cache: if the cache tier restarts, the DB instantly takes 600K QPS and dies. That's the thundering-herd risk, mitigated by request coalescing, staggered TTLs, and warming.

🔴 Senior — When is back-of-envelope estimation actively misleading?

Whenever the average hides the distribution. Four cases worth naming:

1. Skewed keys. "100M users ÷ 100 shards = 1M each" is false when one celebrity or one tenant is 30% of traffic. Averages assume uniformity; real workloads are Zipfian. The hot-shard problem is invisible to an average-based estimate and is the most common real production failure.

2. Tail latency. Estimating mean latency tells you nothing about p99, and p99 is what users experience. Worse, a request that fans out to 100 services hits someone's p99 almost every time — mean-based capacity plans systematically under-provision.

3. Correlated failure. Independent-failure maths gives beautiful availability numbers (three 99.9% AZs → 99.9999%). Reality correlates: shared control planes, a bad config pushed everywhere, one DNS provider. The estimate is arithmetically right and operationally fantasy.

4. Queueing non-linearity. Utilisation and latency aren't linear. A system at 70% is fine; at 95% latency explodes. "We have 30% headroom" is not 30% more traffic available.

The senior move is to estimate the number, then state the distribution assumption you just made and what breaks if it's wrong. "3,000 writes/s average, but if it's Zipfian by user I have a hot shard, so I'd shard on a composite key" is the answer that gets a senior offer.

🔴 Senior — Estimate the cost of the Twitter media path and use it to change the design.

Take the numbers derived above: 30 TB/day ingest and ~36 GB/s egress. Rough public cloud rates (order of magnitude only): object storage ~$0.02/GB/month, CDN egress ~$0.05/GB, origin egress ~$0.09/GB.

Storage, year 1:  11 PB × ~$0.02/GB/mo, averaged over ramp
                  ≈ 11M GB × $0.02 × ~6 mo effective   ≈ $1.3M/yr and CLIMBING
                  (year 3 storage alone ≈ $6M/yr — it accumulates)

Egress:  36 GB/s × 2.6M s/month  ≈ 94 PB/month (!)
         at $0.05/GB CDN          ≈ $4.7M/month  ≈ $56M/yr

Egress is ~40× the storage cost, and that inverts the usual instinct to optimise storage. Design consequences that follow directly from the money:

• Aggressive transcoding. Serving 300 KB WebP instead of 1 MB JPEG cuts egress ~3× — a ~$35M/yr line item. Compute spent on transcoding is trivially worth it.
• Thumbnail-first feeds. Feeds load 20 KB thumbnails, full images only on tap. This is a product decision justified purely by an infrastructure estimate.
• Lifecycle tiering. Media access is heavily recency-biased; move anything older than 30 days to infrequent-access/archive tiers for ~5× storage savings.
• Negotiate or self-host CDN at this scale. At 94 PB/month, list price is not the price, and building edge PoPs becomes defensible — which is precisely why the large social companies all run their own.

The lesson: at scale, the cost estimate is a design document. A candidate who reaches cost-per-byte and lets it drive transcoding and tiering decisions is thinking like an owner, not a whiteboard architect.

🏋️ Graded Exercises

Do these on paper, out loud, without a calculator — that's the skill being trained. Each solution shows the reasoning chain, not just the figure.

Exercise 1 (Easy): A service has 10M daily active users, each making 20 requests/day. What is the average QPS, and the peak at 3×?
Solution 
Requests/day = 10M × 20 = 200M
Average QPS  = 200M / 10⁵ = 2,000 QPS
Peak (3×)    = 6,000 QPS

Consequence to state: 6,000 QPS is a handful of app servers (~5–8 with headroom), but it's past a single relational primary's write ceiling if these are writes. The same number means "trivial" or "needs sharding" depending entirely on the read/write mix — so always ask which it is.

Exercise 2 (Easy): A chat app stores 500M messages/day at 100 bytes each. How much storage per day, per year, and over 5 years?
Solution 
Per day  = 500M × 100 B = 50 GB/day
Per year = 50 GB × 365   ≈ 18 TB/year
5 years  ≈ 90 TB (plus replication ×3 ≈ 270 TB)

Don't forget the replication factor — candidates routinely quote raw logical size and get corrected. 90 TB logical is comfortable for a sharded cluster; the interesting follow-up is retention policy, since most chat products can archive or delete beyond a window and cut this dramatically.

Exercise 3 (Medium): A video platform serves 1M concurrent viewers at 5 Mbps each. Compute egress bandwidth and explain what it rules out.
Solution 
1M × 5 Mbps = 5,000,000 Mbps = 5 Tbps  ≈ 625 GB/s

5 Tbps is far beyond any single origin — a 10 Gbps NIC does 0.01 Tbps, so you'd need ~500 saturated NICs just for the bits. This rules out origin-serving entirely: the only viable architecture is a CDN with deep edge caching, and for live content, hierarchical/tree-based distribution or P2P assist. It also rules out any design where video bytes traverse your application layer. Note how one number collapses the entire solution space — that's estimation doing real work.

Exercise 4 (Medium): You must cache user sessions for 50M DAU. Each session is 1 KB, TTL 24 hours. Size the cache, then decide if it fits one machine.
Solution 
50M sessions × 1 KB = 50 GB
Plus Redis overhead (~30% for key metadata/pointers) ≈ 65 GB
Plus replication for HA (×2)                          ≈ 130 GB

50 GB technically fits one large modern instance (memory-optimised boxes reach 768 GB+), but you should not run it as one: a single node means a total session wipe on failure, logging out every user simultaneously. The right answer is a small sharded, replicated cluster — sized by failure domain, not capacity. This is a recurring theme: once state matters, availability sizes the cluster long before memory does.

Exercise 5 (Hard): Design-size a "who viewed my profile" feature for a 500M-user professional network. 20% of users view 10 profiles/day. Decide the storage architecture.
Solution 
Viewers/day  = 500M × 0.2        = 100M active viewers
Views/day    = 100M × 10         = 1B view events/day
Write QPS    = 1B / 10⁵          = 10,000 writes/s  (peak 20–30K)
Event size   ≈ 50 B (viewer_id, viewee_id, timestamp)
Storage      = 1B × 50 B         = 50 GB/day → 18 TB/year

The decision: 10–30K writes/s of small immutable events, read back as "recent viewers of X, newest first". That access pattern is a time-ordered append log per user, which points at a wide-column store (Cassandra) partitioned by viewee_id and clustered by timestamp descending — writes are appends, reads are a single partition scan, no joins.

Then question the requirement, which is the senior move: nobody scrolls a year of profile views. Cap retention at 90 days (or keep only the last N per user) and 18 TB/year becomes ~4.5 TB steady-state. Better still, if the product only shows a count plus a handful of recent viewers, you don't need every event — a HyperLogLog counter plus a capped list is orders of magnitude cheaper. The estimate's real output was discovering the requirement was overspecified.

Exercise 6 (Hard): An interviewer says "we get 50,000 QPS with a p99 latency target of 50 ms." Your service calls 4 downstream services sequentially, each with p99 of 20 ms. Show why the design fails and fix it.
Solution 
Sequential: 4 × 20 ms = 80 ms best case at p99  →  MISSES the 50 ms SLO

Worse — tail amplification: with 4 independent calls, the chance that
at least one hits its p99 is  1 − 0.99⁴ ≈ 4%.
So ~4% of requests see ≥20 ms from one straggler alone, and your
service's p99 is dominated by the SLOWEST downstream, not the average.

Fixes, in order of preference:

1. Parallelise the independent calls: latency becomes max(20 ms) ≈ 20 ms rather than the sum. Immediately inside SLO. Always check whether sequencing is a real data dependency or just how the code was written — it's usually the latter.
2. Cut the fan-out. Four network hops for one request is a design smell; consider denormalising the data so one store answers the query.
3. Hedged requests — after p95 elapses, send a duplicate to another replica and take the first response. Costs a few percent extra load, dramatically cuts the tail.
4. Degrade gracefully: set a 15 ms timeout per call and return a partial response (e.g. omit the recommendations block) rather than blowing the SLO. Explicitly deciding what is optional is a senior instinct.

The transferable lesson: latency composes by addition and tails compose by amplification. Any design with sequential fan-out needs this arithmetic done before you commit to it.

🎯 Key Takeaways

  • An estimate exists to eliminate an option. If the number doesn't change your design, you computed the wrong number.
  • 1 day ≈ 105 seconds is the one conversion that makes mental arithmetic possible. Round hard and keep talking.
  • Learn ratios, not digits: memory 1 : SSD 1,000 : local network 5,000 : cross-region 1,500,000.
  • Follow the 5 steps in order — assumptions → write QPS → read QPS → storage → bandwidth/memory — and state a design consequence after each.
  • Always design for peak (2–3× typical, 10×+ for spiky products), then add failure headroom (~70% utilisation, survive an AZ loss).
  • Working set sizes the cache; total data sizes the database. Confusing the two produces absurd numbers.
  • Egress often dominates cost in media systems — sometimes 40× storage — which makes transcoding and CDN strategy an architectural concern, not an afterthought.
  • Averages lie about skew, tails, correlated failure and queueing. Name the distribution assumption you're making and what breaks if it's wrong.
