Design TinyURL Case Study

What you'll master: the classic warm-up question, done properly. You'll be able to derive the short-code length from the required key space, compare the three generation strategies and justify one, explain why this is fundamentally a read-heavy caching problem rather than a storage one, handle custom aliases and expiry without race conditions, and add analytics without slowing the redirect.

Prerequisites: Estimation, Caching Strategies, Consistent Hashing, Unique ID Generator (the follow-up this question always leads to).

🎯 What this problem is really testing. Nobody cares whether you can build a URL shortener — it's a hash map with a web server. The signal is: do you derive the code length from a key-space calculation rather than guessing "7 characters"; do you recognise a 100:1 read/write ratio and design the read path accordingly; and do you pick a generation strategy for a stated reason rather than reciting one. Candidates who treat it as trivial usually miss all three.

    → Assume NO. Separate codes allow per-link analytics and expiry.
      (Deduplicating would save storage but breaks both.)
"Are links permanent?"      → Assume default 5-year retention, optional TTL.
"Do we need to prevent abuse (malware/phishing links)?"
    → Yes in reality; I'll note where it fits but keep it out of scope.
"Read/write ratio?"         → Assume 100:1. This is the number that
                              shapes the entire design.

2. Estimation

Assume 100M new URLs/month.

WRITES
   100M / (30 × 10⁵ s) ≈ 33 writes/s      (peak ×3 ≈ 100/s)
   → CONSEQUENCE: trivial. A single primary handles this comfortably.
     Sharding is NOT required for write throughput.

READS
   100:1 ratio → ~3,300 reads/s           (peak ×3 ≈ 10,000/s)
   → CONSEQUENCE: 10K QPS against a DB doing simple key lookups is
     achievable but wasteful. This is where caching earns its place.

STORAGE
   record ≈ short_code(7B) + long_url(~200B) + metadata(~100B) ≈ 500 B
   100M/month × 12 × 5 years = 6B records
   6 × 10⁹ × 500 B ≈ 3 TB over five years
   → CONSEQUENCE: 3 TB is large for one node but not extreme. One
     well-provisioned primary + replicas works; shard for headroom
     and operational comfort, not because throughput demands it.

CACHE WORKING SET
   Link popularity is heavily Zipfian — a small fraction of links take
   most traffic, and links decay fast (most clicks occur within days
   of creation).
   Cache the hot 20% of a month's links: 100M × 0.2 × 500 B = 10 GB
   → CONSEQUENCE: 10 GB fits in RAM easily. A very high hit rate is
     achievable cheaply, which is the single most important fact here.

The shape this reveals: writes are negligible, storage is moderate, and reads dominate by two orders of magnitude — with a working set that fits comfortably in memory. So the interesting engineering is entirely on the read path, and the correct headline is "this is a caching problem, not a storage problem."

3. Key Space: Deriving the Code Length

Don't assert "7 characters" — derive it, since this is the calculation the question is built around:

Base62 alphabet: a–z, A–Z, 0–9 = 62 characters
(Why base62? URL-safe without encoding. Base64 adds '+' and '/',
 which need escaping in URLs.)

   62⁵ ≈ 916 million
   62⁶ ≈ 56.8 billion
   62⁷ ≈ 3.5 trillion
   62⁸ ≈ 218 trillion

We need 6 billion codes over 5 years:
   62⁶ = 56.8B  → sufficient (~10× headroom)
   62⁷ = 3.5T   → 580× headroom

→ CHOOSE 7 characters. Six would technically fit, but as the key space
  fills, random generation collides more often, and 6 characters is
  more enumerable by an attacker. Seven costs one extra byte per URL
  and buys three orders of magnitude of headroom.

4. The Core Design Decision: Generating Short Codes

ApproachHowTrade-off
Hash the URL
(MD5/SHA, take 7 chars)		base62(md5(url))[0:7]Deterministic, so the same URL always maps to the same code — free deduplication, but you cannot issue two codes for one URL (breaks per-link analytics and expiry). Collisions are possible, so every write needs a read-then-check-then-retry, adding a round trip and a race.
Base62-encode a counterbase62(auto_increment_id)No collisions by construction — the standard answer. But: codes are sequential and enumerable (scrape every link by counting up), and a single counter is a distributed bottleneck.
Random generation + uniqueness checkGenerate 7 random base62 chars; insert with a unique constraint; retry on violationNon-enumerable. With 3.5T space and 6B used, collision probability is ~0.2% — so retries are rare. Needs a unique index (which you want anyway).
Pre-generated key poolA background service pre-generates unused codes; the write path claims oneFastest write path (no generation or collision check inline). Costs extra infrastructure and needs careful handling so two servers never claim the same key.
💡 The choice, and the reasoning that matters: the textbook answer is counter + base62, and it's defensible — no collisions, no retries. But sequential codes are enumerable, which for a URL shortener is a genuine privacy problem: anyone can walk the key space and harvest every link, including unlisted documents people assumed were private. I'd choose random generation with a unique constraint: at 0.2% collision probability, retries are negligible, and the codes are unguessable. If a counter is required for other reasons, at minimum obfuscate it (e.g. multiply by a large coprime modulo 62⁷, or encrypt with a format-preserving cipher) so the sequence isn't visible. Naming the enumeration risk unprompted is the strongest signal you can give on this question.

Distributed counter, if you go that route — a single auto-increment is a bottleneck and a single point of failure. The standard fix is range allocation: each application server claims a block of 10,000 IDs from a coordination service and serves from it locally, returning for a new block when exhausted. That's one coordination call per 10,000 URLs instead of per URL. Gaps appear when a server dies holding a block — harmless here, since we don't need contiguity. See Unique ID Generator for the full treatment.

        → LB → API → CACHE lookup

6. Deep Dive: The Redirect Path

This is where the real decisions are, because it's 99% of the traffic.

301 vs 302 — a genuine trade with an analytics consequence:

301 Permanent302 Found (temporary)
Browser behaviourCaches the redirect, often indefinitelyRe-requests every time
Server loadMuch lower — repeat visits never reach youEvery click hits your servers
AnalyticsBroken — you never see repeat clicksComplete
Changing the target laterEffectively impossible — cached in browsers you can't reachWorks immediately

Choose 302 for a URL shortener: analytics is a core feature, and the ability to update or disable a link (for malware takedowns, expiry, or user edits) is essential. The extra load is exactly what the cache exists to absorb. Choose 301 only if you have no analytics requirement and want the traffic reduction.

Cache design, applying the caching lesson:

Pattern:   cache-aside (cache failure = slower, not broken)
Key:       url:{code}          Value: the long URL + expires_at
TTL:       24h, JITTERED — a million links created in a batch must not
           expire in the same second
Eviction:  allkeys-lru — recency matches this workload well, since link
           popularity decays sharply after creation

NEGATIVE CACHING IS ESSENTIAL HERE:
   Requests for nonexistent codes (typos, scanners, expired links)
   miss the cache by definition and hit the DB every time — textbook
   cache penetration. Cache a tombstone:
       SET url:{code} "__404__" EX 300
   For a large key space, add a Bloom filter of existing codes so
   "definitely not present" is answered without touching the DB.

Should the CDN handle redirects? Tempting — a 302 at the edge would be ~10 ms instead of ~50 ms and remove the load entirely. But it requires caching the redirect at the edge, which reintroduces the 301 problems: you lose per-click analytics and can't revoke a link promptly. A reasonable middle ground is a short edge TTL (30–60 s) for the hottest links, accepting slightly undercounted analytics and a bounded revocation delay. Worth raising as an option with its cost stated.

7. Deep Dive: Custom Aliases, Expiry, and Analytics

Custom aliases introduce the one real concurrency hazard in this design:

❌ Check-then-insert 
if not exists(alias):
    insert(alias, url)

Two requests for the same alias
both pass the check, then both
insert. One silently overwrites
the other — a user's link now
points somewhere unexpected.

No isolation level below
SERIALIZABLE prevents this.
✅ Unique constraint 
INSERT INTO urls(code, url)
VALUES ($1, $2);
-- unique index on code
-- → second insert raises a
--   constraint violation

Catch it and return 409 Conflict.
The database enforces uniqueness
atomically; no race exists.

Also: keep custom aliases in a separate key space or reserve a prefix, so a user cannot claim an alias that a future generated code would produce. And maintain a blocklist for reserved words (admin, api, login) and offensive terms.

Expiry — prefer the storage layer's own TTL (DynamoDB TTL, Redis EXPIRE) over a cleanup job: it removes an operational burden and a class of bugs. If the database lacks TTL, run a batched background purge on an expires_at index, and — importantly — check expiry on read as well, so a link is never served after expiry just because the purge job is behind.

Analytics without slowing the redirect:

❌ Synchronous:  INSERT INTO clicks(...) before returning the 302
   → adds a database write to every redirect, converting a
     10,000/s read workload into a 10,000/s WRITE workload.
     This is the single worst mistake available on this question.

✅ Asynchronous:  publish {code, timestamp, referrer, geo, ua} to a
   queue and return the 302 immediately. Workers aggregate offline
   into per-link counters and time series.

At 10,000 clicks/s, don't store 10,000 rows/s forever:
   - aggregate into hourly/daily buckets per link
   - use approximate counters (HyperLogLog) for unique visitors —
     ~12 KB per link for a ±2% estimate of uniques
   - retain raw events briefly (days), aggregates for years

Interview Questions

🟢 Beginner — How long should the short code be, and why base62?

Seven characters, in base62 — and the reasoning is a key-space calculation rather than a convention.

Base62 (a–z, A–Z, 0–9) because those are the characters that are safe in a URL without percent-encoding. Base64 adds + and /, which must be escaped and would make the "short" URL longer and uglier. Some services drop visually ambiguous characters (0/O, 1/l/I) for human-transcribable codes, at a small cost in key space.

62⁶ ≈ 56.8 billion
62⁷ ≈ 3.5 trillion

Requirement: 100M URLs/month × 12 × 5 years = 6 billion codes.

62⁶ = 56.8B would technically fit (~10× headroom)
62⁷ = 3.5T gives ~580× headroom

I'd choose 7, for two reasons beyond raw capacity. First, if you generate codes randomly, collision probability rises as the key space fills — at 6B used out of 56.8B (10%) collisions become common enough to need frequent retries, whereas at 6B out of 3.5T it's ~0.2%. Second, a 6-character space is meaningfully more enumerable by an attacker scanning for valid links.

The cost of the extra character is one byte per record — trivial against the benefit. And note the general habit: derive the length from the required key space and the generation strategy, rather than quoting a number you remember.

🟢 Beginner — Walk through the read path for a redirect. 
GET https://tiny.co/aB3xK9z

1. DNS → load balancer → an API server
2. Extract the code: "aB3xK9z"
3. CACHE lookup (Redis): GET url:aB3xK9z
     HIT  (~99% of requests, ~1 ms) → go to step 5
     MISS → step 4
4. DATABASE lookup by primary key (~5-10 ms)
     found     → populate the cache with a jittered TTL
     not found → cache a "__404__" tombstone (short TTL), return 404
5. Check expiry; if expired, return 410 Gone
6. PUBLISH a click event to the queue (fire and forget — never awaited)
7. Return  302 Found  with  Location: <long URL>

The two decisions that matter here:

Step 6 is asynchronous. Writing analytics synchronously would add a database write to every one of ~10,000 redirects per second, converting a read-heavy system into a write-heavy one and adding latency to the hot path.

Step 7 uses 302, not 301. A 301 is cached by browsers indefinitely, so repeat clicks never reach you — which kills analytics and makes it impossible to revoke or update a link. The extra traffic 302 creates is precisely what the cache absorbs.

The whole path is a single key lookup with no joins, which is why a simple key-value access pattern and a high cache hit rate make this cheap despite the volume.

🟡 Mid — Compare the code-generation strategies. Which would you pick?

Hashing the URL (base62(md5(url))[0:7]) is deterministic, so the same URL always yields the same code — free deduplication. Two problems: truncated hashes collide, so every write needs a read-check-retry (an extra round trip and a race window); and determinism means you cannot issue two codes for one URL, which breaks per-link analytics and per-link expiry.

Counter + base62 is the textbook answer: no collisions by construction, no retries, and codes stay short as the counter grows. Two problems: a single auto-increment counter is a distributed bottleneck (fixable with range allocation — each server claims 10,000 IDs at a time), and more seriously, codes are sequential and therefore enumerable.

Random + unique constraint generates 7 random base62 characters and relies on a unique index to reject duplicates. With 3.5 trillion possible codes and 6 billion used, collision probability is ~0.2%, so retries are negligible.

I'd pick random generation, primarily for the security property. Enumerable codes let anyone walk the key space and harvest every link in the system — including unlisted documents, private shares, and password-reset style URLs that users assumed were unguessable. That's a real privacy failure, and it has happened to real shorteners.

If a counter were required for other reasons (guaranteed no retries, or ordered IDs), I'd obfuscate it — multiply by a large coprime modulo 62⁷, or use a format-preserving cipher — so the underlying sequence isn't visible. And I'd mention the pre-generated key pool as the option that optimises the write path hardest, since claiming a pre-made key removes generation and collision checking from the request entirely.

🟡 Mid — How do you add click analytics without slowing redirects?

Never write analytics synchronously. At ~10,000 redirects/s, a synchronous insert per click turns a read-dominated system into a write-dominated one — 10,000 writes/s exceeds a single primary and adds latency to the one path that must stay fast.

The design:

1. On redirect, publish an event to a queue (Kafka/Kinesis) and return
   the 302 immediately. Fire-and-forget: if the publish fails, we lose
   an analytics event, not a redirect. That trade is correct here.
2. Workers consume and AGGREGATE rather than storing raw events forever:
      per-link counters in hourly/daily buckets
      dimensional breakdowns (referrer, country, device)
3. Retention: raw events for days; aggregates for years.

Why aggregation matters: 10,000 events/s is 864M rows/day. Storing every click indefinitely is expensive and nobody queries individual clicks — they query "how many clicks did this link get last week, by country". Pre-aggregating turns an unbounded storage problem into a bounded one.

Unique visitors deserve a specific mention: counting distinct visitors exactly means storing every visitor identifier per link. A HyperLogLog gives a ±2% estimate in ~12 KB per link regardless of traffic — an enormous saving, and a case where approximation is obviously correct because nobody makes decisions on the difference between 1,000,000 and 1,020,000 unique visitors.

The subtlety worth raising: this only works with 302 redirects. With 301, browsers cache the redirect and repeat clicks never reach your servers at all, so analytics silently undercount by an unknowable margin. The analytics requirement and the redirect-status choice are coupled.

🔴 Senior — One link goes viral and takes 30% of all traffic. What breaks and how do you fix it?

This is a hot-key problem, and the crucial insight is that horizontal scaling does not help. That one code hashes to one cache node and one database shard, so adding nodes leaves it exactly where it was — the traffic simply concentrates on one machine that saturates while the rest of the fleet idles.

What breaks, in order: the single cache node holding that key saturates on CPU and network; if it evicts or expires the key, every request stampedes to one database shard simultaneously; and the analytics pipeline develops a hot partition if it's keyed by link ID.

Fixes, in the order I'd deploy them:

1. In-process L1 cache — the cheapest and most effective. Cache the hottest codes in each API server's memory with a 1–5 second TTL. A key taking 30% of traffic achieves a ~100% local hit rate, so those requests never leave the application server. Bounded staleness of a few seconds is irrelevant for a URL mapping that essentially never changes.

2. Key splitting if L1 isn't enough — store the entry under url:{code}#0..9 and read a random replica, spreading load across ten cache nodes. Adds write amplification on update, which is negligible here since these records are effectively immutable.

3. Stampede protection — request coalescing (one rebuild, others wait) plus stale-while-revalidate, so expiry of this key can't produce a synchronised rush to the database.

4. CDN edge caching for this specific link — a short edge TTL removes the traffic from your infrastructure entirely. The trade is undercounted analytics during the TTL window and delayed revocation, which for a viral link is usually acceptable and worth stating explicitly.

5. Fix the analytics hot partition — shard the counter for this link (clicks:{code}#0..9, summed on read), the same technique as the cache.

The general lesson is one worth stating plainly: a hot key cannot be solved by distributing it, only by replicating it. Sharding spreads distinct keys; it does nothing for a single key. Recognising which of the two you have is what determines whether your fix works.

🔴 Senior — Design this to survive a full regional outage with sub-second global latency.

Two requirements that pull in different directions, but this workload has a property that makes it unusually tractable: URL mappings are effectively immutable after creation. That means aggressive replication carries almost no consistency cost.

1. Multi-region active-active reads. Deploy the read path (cache + replica) in every region and route users to the nearest via GeoDNS or anycast. Because a mapping never changes, a stale replica returns the right answer — there is no read-your-own-writes problem for redirects.

2. Writes: home region with global async replication. Creating a link is 33/s globally — negligible — so I'd accept a single write region (or region-partitioned writes with globally unique codes) and replicate asynchronously. The one visible artifact: a link created in Europe may take a second or two to resolve in Asia. Mitigate by having the creating region serve that link immediately and letting propagation catch up.

3. Making codes globally unique without coordination — this is the design detail that makes multi-region writes work. Embed a region identifier in the code (or partition the key space per region), so two regions can never generate the same code without talking to each other. Cross-region coordination per write would defeat the entire design.

4. Regional failure behaviour. Health-checked GeoDNS or anycast withdrawal shifts traffic to the next region. Reads continue uninterrupted because every region has a full replica. Writes fail over to a secondary write region — and since writes are rare and links are immutable, a brief write outage is far less serious than a read outage. Stating that asymmetry, and designing for it, is the point.

5. Edge acceleration. With immutable mappings, a CDN with a moderate TTL is genuinely attractive — sub-100 ms globally and most traffic never reaching origin. The cost is the analytics and revocation trade discussed earlier, so I'd apply it selectively: edge-cache high-traffic links, and keep low-traffic and sensitive links origin-served.

6. What I'd deliberately not do: synchronous cross-region replication. It would add 150 ms+ to every write for a system where write durability at that granularity isn't critical — and per the replication lesson, requiring all regions to acknowledge would make write availability worse than a single region.

The framing: identify the property that makes the problem easy — immutability — and let it drive the architecture, rather than applying a generic multi-region template.

🏋️ Graded Exercises

Exercise 1 (Easy): How many URLs can 6 base62 characters encode? Is that enough for 100M URLs/month over 10 years?
Solution 
62⁶ = 56,800,235,584 ≈ 56.8 billion

Requirement: 100M/month × 12 × 10 years = 12 billion codes.

12B / 56.8B ≈ 21% of the key space consumed.

It technically fits, but I wouldn't choose it. Two reasons:

1. Collision rate under random generation. At 21% occupancy, a randomly generated code collides ~21% of the time, so roughly one in five writes needs a retry — and it worsens as the space fills. With 7 characters (3.5T), 12B used is 0.34% occupancy and collisions are negligible.

2. Enumerability. A smaller key space is meaningfully cheaper to scan for valid links.

If you use a counter rather than random generation, collisions don't occur and 6 characters is viable on capacity grounds — but you inherit the enumeration problem more severely, since sequential codes are trivially walkable.

Choose 7 characters. One extra byte per record buys 62× the key space, near-zero collision probability, and much better resistance to scanning. This is the shape of a good engineering trade: a negligible cost against a meaningful reduction in risk.

Exercise 2 (Easy): Why is caching so effective here? Compute the DB load at a 99% hit rate.
Solution 
Peak reads ≈ 10,000/s
At 99% cache hit rate:
   DB receives 10,000 × 0.01 = 100 reads/s

100 reads/s of primary-key lookups is trivial — a single modest
database instance handles it with enormous headroom.

Why such a high hit rate is achievable here, which is the real question:

1. The values are tiny. ~500 bytes per record means the hot 20% of a month's links is only ~10 GB — it fits in one machine's RAM, so you're not forced to choose what to cache.

2. The access pattern is strongly Zipfian. A small number of links receive most clicks, which is exactly the distribution caches exploit.

3. Links decay fast. Most clicks happen within days of creation, so an LRU policy keeps precisely the right working set without tuning.

4. The data is effectively immutable. A code→URL mapping never changes, so there's no invalidation problem at all — the hardest part of caching simply doesn't arise.

That last point is worth emphasising: this workload is close to the ideal case for caching, which is why the correct headline for the whole design is "read-heavy caching problem, not a storage problem".

Exercise 3 (Medium): Two users request the custom alias /summer-sale simultaneously. Write the code that handles this correctly.
Solution 
-- Schema: the constraint does the work
CREATE TABLE urls (
  code       VARCHAR(32) PRIMARY KEY,      -- unique by definition
  long_url   TEXT NOT NULL,
  owner_id   BIGINT,
  is_custom  BOOLEAN DEFAULT FALSE,
  expires_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT now()
);
def create_custom(code, url, owner):
    if code.lower() in RESERVED:              # admin, api, login, ...
        raise BadRequest("reserved alias")
    if not VALID_PATTERN.match(code):         # charset/length rules
        raise BadRequest("invalid alias")
    try:
        db.execute(
            "INSERT INTO urls(code, long_url, owner_id, is_custom) "
            "VALUES (%s, %s, %s, TRUE)", (code, url, owner))
        return {"short": f"https://tiny.co/{code}"}
    except UniqueViolation:
        # Someone won the race. This is the ONLY correct place to detect it.
        raise Conflict(409, "alias already taken")

Why check-then-insert fails:

T1: SELECT ... WHERE code='summer-sale'  → not found
T2: SELECT ... WHERE code='summer-sale'  → not found
T1: INSERT  ✓
T2: INSERT  → overwrites, or errors unpredictably

Both passed the check because neither had committed. This is the
write-skew / check-then-act race from the concurrency lesson, and no
isolation level below SERIALIZABLE prevents it.

The unique constraint is the fix — the database enforces uniqueness atomically as part of the insert, so there is no window between checking and acting. Catch the violation and translate it to a 409.

Two additional requirements: validate against a reserved-word list (admin, api, login, settings) so aliases can't shadow real routes; and keep custom aliases in a separate key space from generated codes — for example, require custom aliases to be ≥8 characters while generated codes are exactly 7 — so a user can never claim a string that the generator would later produce.

Exercise 4 (Medium): Your cache restarts and the hit rate drops to 0%. Trace what happens and design the protection.
Solution 
Steady state: 10,000 reads/s, 99% hit → 100 reads/s to the DB.
The database is provisioned for ~100 reads/s plus headroom.

Cache restarts, hit rate = 0%:
   the DB instantly receives 10,000 reads/s — 100x its provisioned load
   → connection pool exhausts, queries queue, latency crosses timeouts
   → clients retry, adding more load
   → the DB becomes unresponsive, so the cache CANNOT be refilled
   → the system does not self-heal. This is a cache AVALANCHE.

Protection, in layers:

1. Don't lose the whole cache at once. Run Redis in cluster mode with replicas, so a single node failure loses 1/N of the keys, and use consistent hashing so that's all that remaps. Rolling restarts, one node at a time — never restart the tier together.

2. Persistence. Redis AOF/RDB means a restarting node reloads warm rather than empty, which removes most of this scenario.

3. Rate-limit at the database — the most important control. A concurrency limiter that rejects excess fast means the DB serves 500 reads/s successfully instead of accepting 10,000 and dying. Partial service beats none, and it keeps the database available to refill the cache.

4. Request coalescing. When 10,000 requests miss the same key, one queries the database and the rest wait for that result. Turns a stampede into a single query.

5. Warm before serving. A restarted node preloads the top-N hottest codes and only then enters the load balancer rotation.

6. Ramp traffic on recovery. Don't return 100% of traffic to a cold cache — that re-triggers the avalanche. Go 1% → 10% → 50%, watching database load.

The framing to state: at a 99% hit rate the cache is not an optimisation, it is load-bearing capacity — the database is deliberately provisioned for 1% of traffic. Any component the system can't survive losing needs HA, warming, and a tested recovery procedure, at the same bar as the database itself.

Exercise 5 (Hard): Add per-link expiry. Design it so an expired link never resolves, without a nightly job being on the critical path.
Solution

The requirement has two halves that need different mechanisms: correctness (an expired link must never resolve) and storage reclamation (expired rows shouldn't accumulate forever). Conflating them is the mistake — a cleanup job alone gives you neither promptly.

1. Check expiry on read — this provides correctness.

row = cache.get(code) or db.get(code)
if row and row.expires_at and row.expires_at <= now():
    cache.delete(code)          # purge the stale entry
    return 410 Gone
return 302 → row.long_url

Correctness now depends on the read path, not on a job. Even if cleanup is a week behind, an expired link never resolves. Return 410 Gone rather than 404 — it correctly signals that the resource existed and was intentionally removed.

2. Align the cache TTL with the link's expiry so the cache can't outlive the record:

ttl = min(DEFAULT_TTL, seconds_until(row.expires_at))
cache.set(code, row, ex=jitter(ttl))

Without this, a link cached for 24 hours keeps resolving after it expires — the read-path check catches it only if the cached value carries expires_at, so cache the expiry alongside the URL, not just the URL string.

3. Reclaim storage in the background, now purely an optimisation:

• Best: native TTL. DynamoDB TTL or Redis EXPIRE deletes expired items automatically with no job to operate, monitor or page on.
• Otherwise: batched deletes on an index over expires_at, in small chunks with pauses, so the purge never competes with live traffic. Deleting millions of rows in one transaction causes lock contention and replication lag.

4. Consider soft deletion — mark expired and purge after a grace period, so an accidental expiry (a bug, a bad bulk update) is recoverable. Hard-deleting user data immediately is rarely worth the irreversibility.

The transferable principle: never let correctness depend on a background job running on time. Enforce the invariant on the read path, where it's cheap and always current, and let the job handle only space reclamation — where being late costs storage rather than correctness.

Exercise 6 (Hard): The product team wants "how many unique visitors clicked this link?" at 10K clicks/s. Design it, and justify any approximation.
Solution

Exact counting is the expensive path, so first establish what it would cost:

Exact unique visitors requires remembering every visitor identifier
per link, forever:
   10,000 clicks/s × 86,400 = 864M events/day
   a set of visitor IDs per link — for a viral link with 50M unique
   visitors, that's 50M × 16 B = 800 MB FOR ONE LINK.

Across millions of links this is completely impractical, and the
cardinality of the data far exceeds the value of the answer.

Design — HyperLogLog per link per time bucket:

On each click (asynchronously, off the redirect path):
   PFADD hll:{code}:2026-07-30  {visitor_id}

Query:
   PFCOUNT hll:{code}:2026-07-30              → uniques that day
   PFCOUNT hll:{code}:07-28 hll:{code}:07-29  → uniques over a RANGE
                                                (HLLs merge losslessly —
                                                 the key property)

Cost: ~12 KB per link per bucket, REGARDLESS of visitor count.
Accuracy: ~±0.81% standard error.
   50M uniques → 800 MB exact  vs  12 KB approximate. ~65,000x smaller.

Why the approximation is obviously correct here: no product decision changes between "1,000,000" and "1,008,000" unique visitors. The number informs marketing judgement, not billing or compliance. Paying 65,000× more storage for a precision nobody acts on would be a straightforwardly bad trade — and being able to say why the approximation is acceptable is the point of the exercise.

The mergeability property is what makes it a design win rather than just a compression trick: because HLLs union losslessly, you store per-day sketches and answer any date range without pre-computing every possible range, and without double-counting a visitor who appeared on multiple days. Exact sets would require either storing every range or re-scanning raw events.

Defining "unique visitor" is the part that actually determines accuracy, and it's worth raising: a cookie ID is precise but lost when cleared and absent in privacy-preserving browsers; hashed IP+user-agent avoids storing identifiers but merges everyone behind one NAT. I'd use a hashed, salted, rotating identifier — better privacy posture, and the measurement error it introduces is larger than HLL's ±0.81% anyway, which reinforces that chasing exactness in the counter is the wrong place to spend effort.

Where I would not approximate: total click counts (a simple incrementing counter is exact and cheap) and anything billable. Use sketches for high-cardinality distinct counts; use exact counters for sums.

🎯 Key Takeaways

  • Derive the code length from the key space: 62⁷ ≈ 3.5T against a 6B requirement. Don't quote "7 characters" as a convention.
  • This is a read-heavy caching problem, not a storage problem — 33 writes/s versus 10,000 reads/s, with a 10 GB working set that fits in RAM.
  • Sequential counter codes are enumerable, letting anyone harvest every link. Random codes with a unique constraint, or an obfuscated counter.
  • Use 302, not 301. Browser-cached 301s destroy analytics and make revocation impossible.
  • Never write analytics synchronously — it converts a read-heavy system into a write-heavy one on the hot path.
  • Custom aliases need a unique constraint, not check-then-insert, and a separate key space from generated codes.
  • Cache negative lookups — typos and scanners bypass the cache by definition.
  • Enforce expiry on read, not via a cleanup job. Correctness must never depend on a background job running on time.
  • A viral link is a hot key — sharding cannot help, because one key maps to one node. Replicate it instead (L1 cache, key splitting).
  • Approximate where nobody acts on the precision: HyperLogLog gives unique-visitor counts at ~12 KB per link instead of hundreds of megabytes.
  • Immutable mappings make multi-region easy — replicate reads everywhere, since a stale replica still returns the right answer.
