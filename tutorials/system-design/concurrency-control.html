Concurrency Control (ACID, Isolation) Deep Dive

What you'll master: what each ACID letter actually promises (and which one isn't the database's job), the four anomalies each isolation level prevents — including write skew, the one most engineers have never heard of and which breaks real financial systems — how MVCC gives you snapshot isolation without read locks, why "Repeatable Read" means different things in Postgres and MySQL, and how to choose between pessimistic and optimistic control from a contention estimate.

Prerequisites: CAP Theorem (linearizability vs isolation are different axes), Replication. Feeds Design Amazon and Concurrent Programming.

1. ACID, Precisely (And The Letter That's Lying To You)

PropertyGuaranteeWho provides it
AtomicityAll operations commit or none do — no partial application, even on crashThe database (via the write-ahead log)
ConsistencyThe transaction moves the DB from one valid state to anotherYou. The database only enforces the constraints you declare. "Consistency" here means your invariants, and it's the odd one out — arguably in the acronym because ACID is easier to say than AID.
IsolationConcurrent transactions appear to run serially — to a configurable degreeThe database, at the level you select
DurabilityOnce committed, it survives a crashThe database (fsync to WAL) — but see below
💡 Two clarifications that come up in senior interviews. First, the C in ACID is not the C in CAP — CAP's consistency means linearizability (a distributed reads-see-latest-writes property), while ACID's means "your invariants hold". They're unrelated axes, and conflating them is a common tell. Second, durability is a spectrum: fsync-on-commit is genuinely durable but slow; many systems buffer, so a power loss can lose the last few milliseconds. And durability on one node says nothing about surviving that node's disk failing — that's replication's job.

2. The Four Anomalies (Including The One Nobody Teaches)

① DIRTY READ — reading uncommitted data
   T1: UPDATE accounts SET balance=500 WHERE id=1   (not committed)
   T2: SELECT balance FROM accounts WHERE id=1      → reads 500
   T1: ROLLBACK
   → T2 acted on a value that never existed.

② NON-REPEATABLE READ — the same ROW changes under you
   T1: SELECT balance WHERE id=1  → 100
   T2: UPDATE balance=200 WHERE id=1; COMMIT
   T1: SELECT balance WHERE id=1  → 200   (same query, different answer)

③ PHANTOM READ — the same SET of rows changes under you
   T1: SELECT COUNT(*) WHERE status='pending'  → 5
   T2: INSERT a new pending row; COMMIT
   T1: SELECT COUNT(*) WHERE status='pending'  → 6
   → Not one row changing value; a row APPEARING in the result set.

④ WRITE SKEW — the one that breaks real systems
   Invariant: "at least one doctor must remain on call."
   Currently Alice and Bob are both on call.

   T1 (Alice): SELECT COUNT(*) on_call → 2. "Fine, I can go off call."
   T2 (Bob):   SELECT COUNT(*) on_call → 2. "Fine, I can go off call."
   T1: UPDATE alice SET on_call=false; COMMIT
   T2: UPDATE bob   SET on_call=false; COMMIT

   → ZERO doctors on call. Each transaction read a state that its
     own commit invalidated, and they wrote to DIFFERENT rows, so
     no row-level conflict was ever detected.

Write skew is the important one because it survives Snapshot Isolation — the level most people think of as "basically serializable". Both transactions read a consistent snapshot, neither modified the same row, so nothing conflicts. The invariant spans multiple rows, and row-level conflict detection cannot see it. This is the class of bug behind double-booked meeting rooms, overdrawn accounts under concurrent withdrawals, and duplicate usernames that pass a check-then-insert.

3. The Isolation Levels, And What Each Actually Prevents

LevelDirty readNon-repeatablePhantomWrite skew
Read UncommittedPossiblePossiblePossiblePossible
Read Committed (default in Postgres, Oracle, SQL Server)PreventedPossiblePossiblePossible
Repeatable Read / Snapshot Isolation (default in MySQL InnoDB)PreventedPreventedPossible per the standard — but see belowPossible
SerializablePreventedPreventedPreventedPrevented

The naming is genuinely inconsistent across databases, and knowing this is a strong signal:

PostgreSQL "REPEATABLE READ"  = Snapshot Isolation.
   Prevents phantoms (snapshot-based) but NOT write skew.
MySQL InnoDB "REPEATABLE READ" = snapshot reads + NEXT-KEY LOCKING,
   which blocks most phantoms — stronger than the standard requires.
PostgreSQL "SERIALIZABLE"      = SSI (true serializability, aborts on
   dangerous read/write dependency cycles).
Oracle "SERIALIZABLE"          = actually Snapshot Isolation.
   It does NOT prevent write skew, despite the name.

→ "What isolation level?" is an incomplete question. "Which anomalies
  does THIS database prevent at that level?" is the real one.

4. Deep Dive: MVCC — How Readers Stop Blocking Writers

Naive isolation uses read locks, so a long-running report blocks every writer. Multi-Version Concurrency Control instead keeps multiple versions of each row, so readers never block writers and writers never block readers.

Every row carries version metadata:
   (id=1, balance=100, xmin=50, xmax=null)   ← created by txn 50, still live

An UPDATE does not overwrite. It writes a NEW version and marks the old
one as ending:
   (id=1, balance=100, xmin=50, xmax=73)     ← old version, valid before 73
   (id=1, balance=200, xmin=73, xmax=null)   ← new version, valid from 73

A transaction reads with a SNAPSHOT (a transaction ID + the set of
in-flight txns). For each row it takes the version visible to that
snapshot:
   txn 60 reading → sees balance=100  (73 hadn't committed at its start)
   txn 80 reading → sees balance=200

Consequences:
  ✓ readers never block writers, writers never block readers
  ✓ a long report sees a consistent snapshot without freezing the system
  ✗ old versions accumulate → VACUUM / purge must reclaim them
  ✗ a long-running transaction pins old versions, causing BLOAT — the
    classic Postgres operational problem
⚠️ The operational consequence worth knowing: in MVCC databases, a forgotten open transaction is genuinely dangerous. It prevents vacuum from reclaiming any version newer than its snapshot, so table and index bloat grows until disk fills or performance collapses. "An idle-in-transaction connection took down the database" is a real and common incident. Always set idle_in_transaction_session_timeout and monitor the oldest running transaction.

5. Pessimistic vs Optimistic: Choose By Contention

Pessimistic (locking)Optimistic (version check)
MechanismSELECT ... FOR UPDATE — lock first, others blockRead a version, then UPDATE ... WHERE version = $read; 0 rows means someone beat you
Cost when there's no conflictLock acquisition and holding, even though nothing contendedNearly zero
Cost when there IS a conflictWaiting (bounded, fair-ish)Wasted work — the whole transaction is redone
Failure modeDeadlocks, lock convoys, blocked connectionsRetry storms under high contention — livelock
Use whenContention is high, or the work is expensive to redoContention is low (<10% conflicts), or you can't hold a transaction open (stateless HTTP, user think-time)
Estimate the crossover rather than guessing:

  conflict probability ≈ (concurrent writers to the same row) × (txn duration)
                         ────────────────────────────────────────────────
                                    time between writes to that row

  1,000 writes/s spread over 1M rows, 10 ms transactions
     → any given row is written 0.001 times/s → conflicts ~never
     → OPTIMISTIC. Locking would be pure overhead.

  1,000 writes/s onto ONE hot counter row, 10 ms transactions
     → every transaction conflicts → optimistic retries forever
     → PESSIMISTIC (or restructure: shard the counter, or make it an
       append-only ledger you sum, so writes never contend at all)

The third option is usually the best one: remove the contention rather than managing it. A hot counter becomes N sharded counters summed on read. A balance becomes an append-only ledger of entries — inserts never conflict with each other, so concurrency control stops mattering. Restructuring to avoid contention beats both locking strategies, and proposing it is a strong senior signal.

6. Deep Dive: Two-Phase Locking And Deadlock

2PL discipline:
   GROWING phase   — acquire locks, release none
   SHRINKING phase — release locks, acquire none
(Strict 2PL, used in practice, holds ALL locks until commit/abort.)

This guarantees serializability. It also makes deadlock inevitable:

   T1: LOCK row A ──────────── wants row B ──┐
                                             │  cycle → DEADLOCK
   T2: LOCK row B ──────────── wants row A ──┘

Detection: the DB maintains a WAIT-FOR graph and looks for cycles.
On a cycle it picks a VICTIM (usually the transaction with the least
work done) and aborts it with a serialization error.

→ Your application MUST handle deadlock/serialization errors by
  RETRYING. Code that treats them as fatal will randomly fail in
  production under load and pass every test.

Preventing deadlocks is mostly about ordering:

• Acquire locks in a consistent global order. If every transaction locks accounts in ascending ID order, the cycle above is impossible — T2 would lock A before B too. This one rule eliminates most application-level deadlocks.
• Keep transactions short. Never hold a transaction open across a network call, a user's think-time, or an external API. Lock duration is the dominant factor in conflict probability.
• Touch fewer rows, and take the most-contended lock last.
• Set lock_timeout so a pathological case fails fast rather than blocking a connection indefinitely.

7. Deep Dive: Preventing Write Skew Specifically

Since Snapshot Isolation permits write skew, and SI is what most people are actually running, you need a deliberate strategy for multi-row invariants:

TechniqueHowTrade-off
SERIALIZABLE (SSI)Postgres tracks read/write dependencies and aborts transactions forming a dangerous cycleCorrect and general. Costs tracking overhead and produces serialization failures you must retry. The right default for genuinely critical invariants.
Materialise the conflictCreate a row representing the invariant (a shift row) and lock it with SELECT ... FOR UPDATE, forcing an artificial row-level conflictWorks at any isolation level. Requires you to identify the invariant and add a row for it — manual but very effective.
Explicit lockingSELECT ... FOR UPDATE on all rows the invariant reads, not just the ones you writeSimple, works everywhere. Locks more than strictly necessary; easy to forget a row.
Database constraintPush the invariant into the schema: unique index, exclusion constraint, or a checkBest when it fits. The DB enforces it atomically regardless of isolation level or application bugs. Postgres exclusion constraints handle "no overlapping bookings" natively.
Single-writer serialisationRoute all writes touching the invariant through one partition/queueEliminates concurrency entirely for that invariant; caps throughput at one writer.

The constraint approach deserves emphasis because engineers reach for it last and should reach for it first. "Two users can register the same username" is not an isolation problem to solve with SERIALIZABLE — it's a UNIQUE index. The database enforces it atomically, at any isolation level, and no application bug can bypass it. Whenever an invariant can be expressed declaratively, that beats any transactional strategy.

Interview Questions

🟢 Beginner — What's a dirty read, and which isolation level prevents it?

A dirty read is reading data another transaction has written but not yet committed. If that transaction then rolls back, you acted on a value that never truly existed.

T1: UPDATE accounts SET balance = 500 WHERE id = 1   -- not committed
T2: SELECT balance WHERE id = 1                     -- reads 500
T1: ROLLBACK                                        -- balance is really 100
    → T2 made a decision based on a phantom value.

Read Committed and above prevent it — only Read Uncommitted allows it. In practice almost nobody runs Read Uncommitted; Read Committed is the default in Postgres, Oracle and SQL Server, and MVCC databases prevent dirty reads essentially for free because readers see the last committed version rather than in-flight changes.

Worth adding: dirty reads are the easiest anomaly to prevent and get the most textbook attention, while the anomalies that actually cause production bugs — phantoms and especially write skew — survive at much higher isolation levels.

🟢 Beginner — Explain optimistic vs pessimistic concurrency control.

Pessimistic assumes conflicts are likely, so it locks first: SELECT ... FOR UPDATE takes a row lock, and other transactions block until you commit. No wasted work — but waiting, and the risk of deadlock.

Optimistic assumes conflicts are rare, so it doesn't lock. You read a version number, do your work, and check at write time that nothing changed:

UPDATE orders SET status='shipped', version = version + 1
 WHERE id = 5 AND version = 3;
-- 0 rows updated → someone else changed it → abort and retry

Choose by contention. With 1,000 writes/s spread across a million rows, conflicts are essentially never — locking would be pure overhead, so optimistic wins. With 1,000 writes/s onto one hot counter row, every transaction conflicts and optimistic retries forever, so pessimistic wins.

One practical factor that often decides it: optimistic control doesn't require holding a transaction open. In a stateless HTTP flow where a user loads a form, thinks for two minutes, and submits, you cannot hold a database lock for that. A version number in the form is the standard solution — and it's why optimistic concurrency dominates web applications.

The best answer is often neither: restructure to remove the contention. A hot counter becomes N sharded counters; a balance becomes an append-only ledger where inserts never conflict.

🟡 Mid — Two users book the last seat simultaneously. Walk through what happens at each isolation level and how you'd fix it.

The dangerous pattern is check-then-act:

T1: SELECT available FROM seats WHERE id=5   → true
T2: SELECT available FROM seats WHERE id=5   → true
T1: UPDATE seats SET available=false WHERE id=5; COMMIT
T2: UPDATE seats SET available=false WHERE id=5; COMMIT
→ both users are told they booked seat 5.

By level:

• Read Committed — both reads see true, both updates succeed. Double booking.
• Repeatable Read / Snapshot Isolation — in Postgres, both read from their snapshots; the second update hits a concurrent-update conflict and gets a serialization error (so it fails safely, provided you retry). In MySQL InnoDB, the second UPDATE blocks on the row lock, then re-reads and sees available=false. Both are saved by the fact that this contends on the same row.
• Serializable — safe.

How I'd actually fix it, best first:

1. Conditional update — make the check part of the write. No isolation level needed:

UPDATE seats SET available=false, booked_by=$user
 WHERE id=5 AND available=true;
-- 0 rows → someone got it first. Atomic, no locks, no retries.

2. Pessimistic lock — SELECT ... FOR UPDATE on the seat row before checking, if there's more logic between the read and the write.

3. A database constraint if the model allows it: a unique index on (seat_id) in a bookings table makes double booking structurally impossible.

The important caveat: this specific case is easy because both transactions touch the same row, so row-level conflict detection catches it. Change the requirement to "a party of 4 needs any 4 adjacent seats" and it becomes a multi-row invariant — write skew territory, where snapshot isolation provides no protection and you need SERIALIZABLE, a lock on the whole seat range, or an exclusion constraint.

🟡 Mid — Your app randomly throws "deadlock detected" under load. Diagnose and fix.

Deadlock means two transactions each hold a lock the other needs, forming a cycle in the database's wait-for graph. The database detects the cycle and aborts a victim — which is correct behaviour, not a database bug.

First, the immediate fix: retry. Deadlock and serialization errors are expected under concurrency. Application code must catch them and retry with bounded attempts and jittered backoff. Code that treats them as fatal will fail randomly in production while passing every test, because tests rarely run concurrent transactions.

Then find the cycle. Postgres logs both statements involved; MySQL has SHOW ENGINE INNODB STATUS. You're looking for two code paths that acquire the same locks in opposite orders.

Transfer A→B:  lock account A, then account B
Transfer B→A:  lock account B, then account A
→ guaranteed deadlock when they run concurrently.

Structural fixes, in order:

1. Consistent lock ordering — the highest-leverage fix. Always lock in ascending primary key order:

first, second = sorted([from_account, to_account])
lock(first); lock(second)
-- now BOTH transfer directions lock in the same order. Cycle impossible.

2. Shorten transactions. Lock duration drives conflict probability directly. Never hold a transaction across an HTTP call, a queue publish, or user think-time. Move non-database work outside the transaction.

3. Touch fewer rows, and acquire the most contended lock last so it's held briefly.

4. Consider optimistic control if conflicts are actually rare — no locks means no deadlocks, at the cost of retries when they do collide.

5. Set lock_timeout so pathological waits fail fast instead of tying up connections.

I'd also check whether deadlock frequency is rising with load in a way that suggests a hot row — if so, the real fix is removing the contention (sharded counters, append-only inserts) rather than tuning lock behaviour.

🔴 Senior — Explain write skew and why Snapshot Isolation doesn't prevent it.

Write skew occurs when two transactions read an overlapping data set, each makes a decision based on what it read, and each writes to different rows — such that the combined result violates an invariant that neither transaction individually broke.

Invariant: at least one doctor on call. Alice and Bob are both on call.

T1 (Alice): SELECT COUNT(*) WHERE on_call → 2. Safe to go off.
T2 (Bob):   SELECT COUNT(*) WHERE on_call → 2. Safe to go off.
T1: UPDATE doctors SET on_call=false WHERE name='alice'; COMMIT
T2: UPDATE doctors SET on_call=false WHERE name='bob';   COMMIT
→ zero doctors on call.

Why Snapshot Isolation misses it: SI guarantees each transaction reads a consistent snapshot and detects write-write conflicts on the same row. Here neither guarantee is violated — both snapshots were valid at their start times, and the two transactions wrote to different rows, so there is no write-write conflict to detect. The invariant spans multiple rows, and row-level conflict detection is structurally blind to it.

Put precisely: each transaction's write invalidated the premise the other transaction read. That's a read-write dependency, and SI doesn't track read sets.

Real-world instances: double-booking a meeting room (checking for overlaps, then inserting), overdrawing an account when two withdrawals each check the same balance, duplicate usernames from check-then-insert, and violating "at most N of X" constraints of any kind.

Fixes:

• SERIALIZABLE with SSI (Postgres) — tracks read/write dependencies and aborts transactions that form a dangerous cycle. Correct and general; costs tracking overhead and produces serialization failures you must retry.
• Materialise the conflict — create a row representing the invariant (e.g. a shift row) and SELECT ... FOR UPDATE it, converting an invisible multi-row invariant into a detectable single-row conflict. Works at any isolation level.
• Lock the read set explicitly — FOR UPDATE on the rows your decision reads, not just those you write.
• Database constraint — best where it fits. Postgres exclusion constraints enforce "no overlapping bookings" declaratively and atomically, immune to isolation level and application bugs.

The point I'd emphasise: Oracle's "SERIALIZABLE" is actually Snapshot Isolation and does not prevent write skew, and Postgres's REPEATABLE READ is SI too. So "we use a high isolation level" is not evidence of safety — you have to know which anomalies your specific database prevents at that specific level.

🔴 Senior — Design concurrency control for an inventory system: 10K SKUs, 5K orders/s, must never oversell.

Estimate the contention first, because it determines the strategy:

5,000 orders/s across 10,000 SKUs → 0.5 writes/s per SKU on average
→ contention looks negligible... but demand is Zipfian. A flash-sale
  SKU might absorb 2,000 orders/s ALONE.
→ So I need TWO strategies: one for the long tail, one for hot SKUs.

Baseline for normal SKUs — conditional update, no locks:

UPDATE inventory SET available = available - $qty
 WHERE sku = $sku AND available >= $qty;
-- 0 rows → insufficient stock. Atomic; the check and the decrement are
-- ONE statement, so no check-then-act race exists at any isolation level.

This is correct under Read Committed and needs no explicit locking, because a single UPDATE takes its own row lock and re-evaluates the predicate against the current version.

For hot SKUs — remove the contention rather than manage it:

Split each hot SKU's stock into N buckets:
   inventory_bucket(sku, bucket_id, available)
   100 units → 10 buckets × 10 units

An order picks a RANDOM bucket and decrements it.
→ 2,000 orders/s spread over 10 rows instead of hammering one.
Fallback: if the chosen bucket is empty, try others before declaring
sold out (otherwise you report sold-out with stock remaining).
Periodically rebalance buckets.

This is the same hot-key remedy as in consistent hashing — the single row is the bottleneck, and no locking strategy fixes a single row; only splitting it does.

Reservation model, since checkout isn't instantaneous:

1. RESERVE at add-to-cart/checkout-start: decrement stock, insert a
   reservation row with expires_at = now + 15 min.
2. CONFIRM on payment success: mark the reservation consumed.
3. EXPIRE via a background job: return stock from unconfirmed
   reservations past expires_at.

Reservations must be IDEMPOTENT (keyed by cart/order ID) so retries
don't double-decrement — and they WILL be retried.

The expiring hold is important: it means a crashed checkout flow returns stock automatically rather than stranding it, which no transactional mechanism would handle.

What I would not do:

• SERIALIZABLE globally — enormous overhead at 5K orders/s for a problem a conditional update already solves.
• SELECT ... FOR UPDATE then a separate UPDATE — holds the lock longer than necessary and serialises hot SKUs completely.
• Cache the stock count for the decision — caching the display is fine, but the decrement must hit the source of truth. A cache must never decide whether a sale is allowed.

The honest trade to state: "never oversell" and "5,000 orders/s on one hot SKU" are in tension, because a single row is a serialisation point. Bucketing resolves it, at the cost of slightly imprecise sold-out reporting at the boundary. Many retailers deliberately accept a small oversell rate and handle it with cancellations, because the revenue from higher throughput exceeds the cost — worth raising, since recognising that this is a business trade rather than purely a technical one is the senior move.

🏋️ Graded Exercises

Exercise 1 (Easy): Name the anomaly: a transaction runs SELECT COUNT(*) WHERE status='pending' twice and gets 5 then 6.
Solution

A phantom read. The count changed because another transaction inserted (or committed) a row matching the predicate between the two queries.

The distinction from a non-repeatable read is what's being tested: a non-repeatable read is the same row returning a different value; a phantom is the set of rows changing membership. That difference matters because they need different mechanisms — protecting a specific row is a row lock, while protecting a predicate requires locking a range (MySQL's next-key locking) or snapshot isolation.

Prevented by: Serializable in the SQL standard. In practice, Postgres's REPEATABLE READ (snapshot isolation) also prevents it, since the snapshot is fixed at transaction start; MySQL InnoDB's REPEATABLE READ prevents it via next-key locks. Another instance of level names not implying identical guarantees.

Exercise 2 (Easy): Why does `SELECT balance; if balance >= 100 then UPDATE balance = balance - 100` fail under concurrency, and what's the one-line fix?
Solution

It's check-then-act: two transactions can both read a balance of 100, both pass the check, and both subtract — leaving −100. The gap between the read and the write is where the race lives, and at Read Committed nothing prevents it.

Fix — make the check part of the write, atomically:

UPDATE accounts SET balance = balance - 100
 WHERE id = $1 AND balance >= 100;
-- 0 rows affected → insufficient funds

This works because a single UPDATE statement takes a row lock and evaluates its predicate against the current committed version. The second transaction blocks briefly, re-evaluates balance >= 100 against the new value of 0, matches nothing, and safely reports insufficient funds.

The generalisable lesson: whenever you see read → decide → write on the same data, look for a way to express it as one conditional statement. This is the same reasoning behind compare-and-set, optimistic version checks, and conditional writes in NoSQL stores — collapsing the window rather than guarding it.

A stronger option for money: model it as an append-only ledger and enforce non-negativity with a constraint or a periodic check, so writes never contend at all.

Exercise 3 (Medium): Implement optimistic locking for a document editor where users load, edit for minutes, then save. Handle the conflict case.
Solution

Pessimistic locking is impossible here — you cannot hold a database transaction open while a user thinks for five minutes. Optimistic version checking is the standard answer.

-- schema
documents(id, content, version INT NOT NULL, updated_at, updated_by)

-- 1. LOAD: return the version to the client
SELECT id, content, version FROM documents WHERE id = $1;
   → {id: 7, content: "...", version: 3}

-- 2. SAVE: the client sends back the version it loaded
UPDATE documents
   SET content = $new, version = version + 1,
       updated_at = now(), updated_by = $user
 WHERE id = $1 AND version = $client_version;

-- rows affected = 1 → success
-- rows affected = 0 → someone saved first. CONFLICT.
def save(doc_id, new_content, client_version, user):
    rows = db.execute(
        "UPDATE documents SET content=%s, version=version+1, "
        "updated_by=%s WHERE id=%s AND version=%s",
        (new_content, user, doc_id, client_version))
    if rows == 1:
        return {"ok": True, "version": client_version + 1}

    # Conflict: fetch current state so the user can decide.
    current = db.query_one(
        "SELECT content, version, updated_by FROM documents WHERE id=%s",
        (doc_id,))
    return {"ok": False, "conflict": True,
            "their_content": current.content,
            "their_version": current.version,
            "their_author":  current.updated_by,
            "your_content":  new_content}

Handling the conflict is the real design question, and the answer is a product decision:

• Last-write-wins with a warning — simplest, and silently loses work. Acceptable only for low-stakes data.
• Show a diff and let the user merge — the standard for documents. Requires returning both versions, which is why the conflict response above includes them.
• Auto-merge non-overlapping edits — three-way merge against the common ancestor. Needs the base version stored, and works well for structured content.
• Operational transformation / CRDTs — what Google Docs uses for real-time collaboration. Merges concurrent edits automatically without conflicts, at substantially higher complexity (see CAP).

Details worth including: return who made the conflicting change (users resolve conflicts far better with that context); autosave drafts locally so a rejected save never loses the user's work; and consider a soft "Bob is editing" advisory lock to prevent most conflicts socially rather than technically — advisory because it must never block a save if Bob's browser crashed.

Exercise 4 (Medium): A meeting-room booking system checks for overlaps then inserts. Two users book the same slot concurrently and both succeed. Explain and fix three ways.
Solution

This is write skew. Both transactions query for overlapping bookings, both see none, and both insert — to different rows. There's no write-write conflict on any single row, so snapshot isolation detects nothing. The invariant ("no two bookings overlap for one room") spans rows, which row-level conflict detection cannot see.

T1: SELECT * FROM bookings
     WHERE room=5 AND tstart < '11:00' AND tend > '10:00'  → none
T2: same query                                              → none
T1: INSERT booking(room=5, 10:00–11:00)  COMMIT
T2: INSERT booking(room=5, 10:00–11:00)  COMMIT
→ double booked.

Fix 1 — exclusion constraint (best where supported). Postgres enforces it declaratively:

CREATE EXTENSION btree_gist;
ALTER TABLE bookings ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (
    room_id WITH =,
    tstsrange(tstart, tend) WITH &&      -- && = "overlaps"
  );

The database rejects the second insert atomically, at any isolation level, and no application bug can bypass it. This is the strongest option: the invariant lives in the schema rather than in every code path that touches bookings.

Fix 2 — SERIALIZABLE (SSI). Postgres tracks the read/write dependency and aborts one transaction with a serialization failure, which the application retries. General-purpose and requires no schema change, but costs tracking overhead and demands retry logic everywhere.

Fix 3 — materialise the conflict. Create a row representing the resource-time slot and lock it, turning the invisible multi-row invariant into a detectable single-row conflict:

-- one row per room per time bucket
SELECT * FROM room_slots
 WHERE room_id=5 AND slot='2026-07-30 10:00' FOR UPDATE;
-- now T2 blocks here until T1 commits, then sees the booking

Works at any isolation level and in databases without exclusion constraints. The cost is maintaining slot rows and choosing a bucket granularity.

What I'd choose: the exclusion constraint on Postgres — declarative, unbypassable, and it documents the invariant in the schema. Fix 3 for MySQL, which lacks exclusion constraints. Fix 2 as a general safety net for other multi-row invariants in the same system.

Exercise 5 (Hard): Your Postgres database has grown to 400 GB but holds only 80 GB of live data, and queries have slowed dramatically. Diagnose.
Solution

Table and index bloat from MVCC. Postgres never overwrites a row — an UPDATE writes a new version and marks the old one dead. Dead tuples are reclaimed by VACUUM, but only if no transaction might still need to see them. 5× bloat means vacuum has been unable to reclaim for a long time.

The usual cause: a long-running or idle-in-transaction connection. Vacuum cannot remove any tuple version newer than the oldest running transaction's snapshot — so one forgotten BEGIN in a connection pool blocks reclamation database-wide, indefinitely.

-- find the culprit
SELECT pid, state, age(clock_timestamp(), xact_start) AS txn_age, query
  FROM pg_stat_activity
 WHERE state IN ('idle in transaction','active')
 ORDER BY xact_start;

-- confirm bloat and last successful vacuum
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
  FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;

Why queries slowed: sequential scans read dead tuples too, so a table 5× its necessary size takes ~5× the I/O. Indexes bloat identically, so index scans traverse more pages. Worse, the buffer cache now holds mostly dead data, collapsing the cache hit rate — which is why the slowdown is disproportionate rather than merely 5×.

Other contributing causes to check: autovacuum too slow or throttled for the write rate (tune autovacuum_vacuum_cost_limit, autovacuum_max_workers, and the scale factor on large tables); very high update churn on a table; long-running replication slots or prepared transactions holding old snapshots (an abandoned replication slot has exactly the same effect and is easily missed); and bulk delete jobs generating dead tuples faster than vacuum reclaims them.

Remediation:

1. Terminate the offending transaction and set idle_in_transaction_session_timeout so it can't recur.
2. Reclaim the space: VACUUM FULL rewrites the table compactly but takes an exclusive lock — unacceptable on a live system. Use pg_repack instead, which does the same online. REINDEX CONCURRENTLY for bloated indexes.
3. Tune autovacuum to keep up going forward, more aggressively on high-churn tables.
4. Monitor oldest transaction age, dead tuple counts, and table-size-to-live-data ratio — all three should be alerting metrics, since this failure is slow, silent, and eventually catastrophic (transaction ID wraparound forces an emergency shutdown).

The general lesson: MVCC's gift — readers never block writers — is paid for with garbage collection, and that garbage collection has a prerequisite: transactions must end. Long transactions are not merely a locking concern in MVCC databases; they're a storage and performance concern too.

Exercise 6 (Hard): Design the transaction strategy for a ledger that must never lose or duplicate money, at 20K transfers/s, with a full audit trail.
Solution

Core decision: an append-only double-entry ledger, not mutable balance rows. This choice resolves most of the concurrency problem before it starts.

entries(
  id            BIGSERIAL,
  transfer_id   UUID NOT NULL,        -- groups the two legs
  account_id    BIGINT NOT NULL,
  amount        BIGINT NOT NULL,      -- minor units; +credit / -debit
  created_at    TIMESTAMPTZ,
  idempotency_key TEXT,
  UNIQUE (idempotency_key)            -- dedup enforced by the DB
);
-- INVARIANT: sum(amount) per transfer_id = 0  (double-entry)
-- Balance = SUM(amount) for an account, not a stored mutable field.

Why append-only wins here: inserts never conflict with each other, so 20K/s of transfers produces no row contention at all — unlike UPDATE balance, where two transfers touching the same account serialise. It also gives the audit trail for free: every movement is an immutable record, and history can never be rewritten.

Never lose money — atomicity + durability:

BEGIN;
  INSERT INTO entries(transfer_id, account_id, amount, idempotency_key)
    VALUES ($t, $from, -$amt, $key),        -- both legs
           ($t, $to,   +$amt, $key || ':2');
COMMIT;                                     -- atomic: both or neither

Both legs in one transaction means a crash can never leave money debited but not credited. Pair with semi-synchronous replication (replication lesson) so an acknowledged commit provably exists on a second node — RPO zero. Async replication would mean a leader failure loses committed transfers, which is unacceptable for money.

Never duplicate money — idempotency: the UNIQUE(idempotency_key) constraint does the work. A retried request (which will happen — clients time out without knowing the outcome) hits the constraint, and the handler catches the violation and returns the original result. The database enforces it, so no application bug can bypass it.

The balance problem, and how to keep it fast: summing all history per query gets slower forever. Use periodic checkpoints:

balance_snapshots(account_id, as_of_entry_id, balance)

current balance = snapshot.balance
                + SUM(amount) FROM entries
                   WHERE account_id=$1 AND id > snapshot.as_of_entry_id

Snapshot nightly (or every N entries). Reads stay O(recent entries).
Snapshots are a derived CACHE — always recomputable from the ledger,
so a corrupt snapshot is never a loss of truth.

Enforcing "no overdraft" — this is the write-skew case. Checking a balance then inserting a debit is exactly the anomaly from section 2: two concurrent withdrawals each read a sufficient balance and both insert. Options:

• SELECT ... FOR UPDATE on the account row (a small accounts row existing purely as a lock target) — materialising the conflict. Serialises per account, which is acceptable because contention is per-account rather than global.
• SERIALIZABLE for withdrawal transactions specifically, with retry on serialization failure.
• Accept and reconcile — permit the overdraft, detect it asynchronously, and charge a fee or reverse it. This is genuinely what many banks do, and it's worth naming: for accounts that cannot realistically go negative (internal system accounts), skipping the check entirely maximises throughput.

Scaling to 20K/s: shard by account_id. A transfer between accounts on different shards becomes a cross-shard transaction, so use a saga: debit leg, then credit leg, with a compensating reversal — every step idempotent and durably queued. Alternatively route all transfers through a partitioned single-writer per account range, which preserves ordering per account.

Reconciliation as the safety net: a continuous job asserting that SUM(amount) = 0 across every transfer_id, and that account snapshots match recomputed sums. In financial systems the test isn't "can it fail?" but "will we detect it within minutes?" — and an append-only ledger makes that detection straightforward, which is ultimately the strongest argument for the design.

🎯 Key Takeaways

  • ACID's C is your job, not the database's — it only enforces constraints you declare. And it's unrelated to CAP's C (linearizability).
  • Four anomalies, not three: dirty read, non-repeatable read, phantom, and write skew — the one that survives snapshot isolation and breaks real systems.
  • Write skew happens when transactions read overlapping data and write different rows, so no row-level conflict is ever detected.
  • Isolation level names lie across databases. Oracle's SERIALIZABLE is snapshot isolation; MySQL's REPEATABLE READ blocks phantoms while Postgres's doesn't. Ask which anomalies are prevented.
  • MVCC means readers never block writers — paid for with garbage collection, so a long-running or idle-in-transaction connection causes unbounded bloat.
  • Choose optimistic vs pessimistic from an estimated conflict rate, and prefer optimistic when you can't hold a transaction open (stateless HTTP, user think-time).
  • Best of all: remove the contention. Sharded counters and append-only ledgers make concurrency control largely moot.
  • Collapse check-then-act into one conditional statement — UPDATE ... WHERE balance >= 100 is atomic and needs no isolation level.
  • Lock in a consistent global order (ascending key) to make deadlock cycles impossible, and keep transactions short.
  • Serialization and deadlock errors are expected — application code must retry them, or it will fail randomly in production while passing every test.
  • Push invariants into schema constraints where possible — unique indexes and exclusion constraints are enforced atomically at any isolation level and can't be bypassed by application bugs.
