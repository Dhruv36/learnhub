Design Gmail Case Study

What you'll master: why store-and-forward makes email uniquely durable, separating hot metadata from cold content (and the deduplication that saves most of your storage bill), per-user search indexes and why they're far easier than web search, spam filtering as an inline pipeline stage with an asymmetric cost function, and the threading model that turns a flat message list into a conversation.

Prerequisites: Inverted Index, Search Engine (this is search scoped per user), Pub/Sub (delivery guarantees), Caching. Pairs with Design Chat.

🎯 What this problem is really testing. Durability discipline, and recognising that email is a federated system you don't control. Unlike chat, where you own both endpoints, email must interoperate with thousands of independently-operated servers over a protocol from 1982 — so the design centres on never acknowledging what you haven't stored, and never silently dropping anything. The second signal is storage: attachments dominate the bill, and deduplication is the single highest-leverage decision.

1. Requirements

FunctionalNon-functional
Send and receive email over SMTPNever lose an email — the hard requirement
Labels/folders, threading into conversationsSearch a mailbox of millions of messages in <500 ms
Full-text search over entire historyHandle 25 MB attachments efficiently
AttachmentsSpam filtering with very low false positives
Spam filteringStorage cost must be sustainable at petabyte scale

The requirement that shapes everything: "never lose an email" is stronger than it sounds. Not "rarely", not "with 99.99% probability" — a lost email is a business contract missed, a job offer never seen. That drives durable store-and-forward at every hop, and it means acknowledge only after committing is a rule with no exceptions.

2. Estimation

Assume 1B users, 100 emails received per user per day.

VOLUME
   1B × 100 = 100B emails/day
   10¹¹ / 10⁵ s = 1,000,000 emails/s
   → CONSEQUENCE: enormous ingest. But note most is SPAM (typically
     50-80% of raw inbound), so filtering early saves storage and
     indexing work on the majority of traffic.

STORAGE — where the real cost is
   average email ~75 KB (text is tiny; attachments dominate)
   100B/day × 75 KB = 7.5 PB/day (!)
   → CONSEQUENCE: unsustainable if taken naively. Two facts save it:
       1. spam is discarded or short-retained → cuts most of it
       2. attachments DEDUPLICATE heavily — one company-wide memo
          with a 5 MB PDF sent to 10,000 employees is ONE blob,
          not 10,000 copies.

METADATA vs CONTENT
   metadata per email ≈ 1 KB (headers, labels, flags, refs)
   100B/day × 1 KB = 100 TB/day of metadata
   → small enough to live in an indexed store; content goes to object
     storage. This split is the core storage decision.

SEARCH
   a heavy user has ~1M emails; an index over one mailbox is ~100 MB
   → CONSEQUENCE: search is PER USER, so a query touches ONE shard —
     dramatically easier than web search's 300-way fan-out.

The 7.5 PB/day figure is the one to state, because it immediately makes deduplication and spam filtering architectural concerns rather than optimisations.

3. Architecture

INBOUND
  Internet → MX servers (SMTP) → accept, durably queue
      → spam/virus pipeline → classify
      → store: metadata DB + content in object storage
      → index for search → deliver to mailbox → notify clients

OUTBOUND
  Client → compose → durable outbox queue
      → (undo-send delay window)
      → MX lookup → SMTP delivery → retry on failure → bounce if permanent

STORAGE SPLIT
  METADATA (hot, structured, queried constantly)
     from, to, subject, labels, flags, thread_id, blob_ref
     → sharded relational or wide-column store, sharded BY USER
  CONTENT (cold, large, write-once)
     body, attachments
     → object storage, content-addressed for deduplication

Shard by user. Every meaningful query — list my inbox, search my mail, apply a label — is scoped to one user, so user-sharding means no query ever crosses shards. That's the same favourable property as geographic sharding in Uber, and it's why email scales more gracefully than its volume suggests.

4. The Core Decision: Durability Through Store-and-Forward

SMTP's defining property: every hop DURABLY STORES the message before
acknowledging it to the previous hop.

  Sender → MTA-1: "250 OK" only AFTER writing to disk
  MTA-1 → MTA-2:  same
  MTA-2 → mailbox: same

If MTA-2 is unreachable, MTA-1 does NOT lose the message — it retries
from its own durable queue for days, then bounces with a clear error.

THE RULE, with no exceptions:
   never send "250 OK" before the message is committed to durable
   storage. An ack is a PROMISE that you now own this message.
❌ Ack then store 
1. receive message
2. send "250 OK"
3. write to storage

Crash between 2 and 3:
the sender believes delivery
succeeded and will never retry.
The message is GONE, silently,
with no error anywhere.

Nobody discovers it until a
human asks "did you get my
email?"
✅ Store then ack 
1. receive message
2. write durably (replicated)
3. send "250 OK"

Crash between 1 and 2:
no ack was sent, so the sender
RETRIES. At-least-once.

Duplicates are possible, which
is why Message-ID exists —
dedupe on it at ingest.

This is the same persist-before-acknowledge discipline as chat, but here it's enforced by protocol across organisational boundaries — which is precisely why email is more reliable than most modern systems built on it.

Retry and bounce semantics are part of the durability story:

4xx (temporary: mailbox full, server busy)
   → retry with exponential backoff for up to ~5 days
   → send the sender a "delayed" notice after a few hours
5xx (permanent: no such user, domain doesn't exist)
   → stop immediately, send a BOUNCE

Never retry a 5xx — it wastes resources and looks like abuse.
Never silently drop a 4xx — that's the loss the design exists to
prevent.

5. Deep Dive: Storage — Separation and Deduplication

MetadataContent
Size~1 KB~75 KB average, up to 25 MB
AccessRead on every list view, search, label operationRead only when a message is opened
MutabilityChanges often (read/unread, labels, stars)Write-once
StoreSharded indexed databaseObject storage, content-addressed

Never put attachments in the database. A 25 MB blob in a row bloats every page the query planner touches, slows scans that don't even reference it, inflates backups, and makes replication painful. Keep a reference and let object storage do what it's good at.

Deduplication is the highest-leverage storage decision, and it falls out of content-addressing:

blob_key = SHA-256(content)

One company memo with a 5 MB PDF sent to 10,000 employees:
   naive:      10,000 × 5 MB = 50 GB
   dedup:      1 × 5 MB = 5 MB, plus 10,000 small references
   → 10,000x reduction for that message.

Mailing lists, newsletters and forwarded attachments make this
enormously effective in practice — a large fraction of total bytes.

Reference counting is required so deleting one recipient's copy
doesn't destroy everyone else's. Or use a garbage collector that
sweeps unreferenced blobs, which is simpler to get right.
⚠️ The privacy consideration worth raising: cross-user deduplication means the system can tell that two users hold identical content, and a naive implementation can leak that ("upload this file, see if it deduplicates" reveals whether someone else already has it). Within one provider's trust boundary this is usually acceptable, but it's the reason end-to-end encrypted services cannot deduplicate across users — their content is encrypted per user, so identical files produce different ciphertext. Same trade as in the backup-sync design.

6. Deep Dive: Per-User Search

This reuses the inverted index, and the crucial difference makes it far easier:

WEB SEARCH: any query may match any document in the corpus
   → the index must be sharded by document, so every query fans out
     to all 300 shards. Tail latency dominates.

EMAIL SEARCH: a query only ever searches ONE user's mail
   → shard the index BY USER. A query touches exactly one shard.
   → no fan-out, no tail amplification, no cross-shard merge.

An individual mailbox index is ~100 MB even for a heavy user, so it
fits comfortably in memory on one node.

Incremental indexing: each arriving email is added to that user's index immediately rather than triggering any rebuild. Deletions are tombstoned and cleaned up during periodic merges — the same LSM-segment approach as the search engine, but at a scale where a full per-user rebuild is actually feasible as a repair mechanism.

What email search needs that web search doesn't: structured filters combined with full-text. from:alice has:attachment after:2026/01/01 "quarterly report" mixes metadata predicates with text search, so the query planner should apply the selective metadata filters first (usually cheap indexed lookups) and run text matching over the much smaller surviving set — the same "most selective first" principle as posting-list intersection.

7. Deep Dive: Spam Filtering and Its Asymmetric Costs

The cost function is deeply asymmetric, and it dictates the design:

   FALSE POSITIVE (legitimate mail marked spam)
      → the user misses a job offer, an invoice, a medical result.
      → catastrophic and often invisible — they don't know to look.
   FALSE NEGATIVE (spam reaches the inbox)
      → mildly annoying; the user deletes it.

→ Tune HEAVILY toward avoiding false positives, and NEVER delete:
  route to a Spam folder that the user can inspect. Silently dropping
  mail is the one thing an email system must not do.
SignalDetail
Sender authenticationSPF (is this IP allowed to send for this domain?), DKIM (cryptographic signature), DMARC (policy tying them together). Cheap, and strong evidence.
IP/domain reputationHistorical behaviour per sending IP and domain — the strongest single signal in practice.
Content featuresML over text, links, images, and structure. Adversarial: spammers actively test against filters.
User feedback"Mark as spam" / "not spam" — both a training signal and a per-user personalisation input.
Rate and graph patternsOne sender to a million recipients in a minute is structurally suspicious regardless of content.

Architecturally it's the offline/online split again: the model trains offline on historical data and user feedback, while classification runs inline at delivery time within a tight latency budget. Reputation lookups are cached aggressively because they're on the hot path for every one of a million messages per second.

Filter early. Classifying before storage and indexing means you never pay to store, index or replicate the majority of inbound traffic — which, given that spam is most of it, is a substantial fraction of the entire system's cost.

8. Deep Dive: Threading

Turning a flat stream of messages into conversations is a subtle problem interviewers like, because the obvious approach is wrong:

❌ Group by subject line
   - "Re: Re: FW: lunch?" vs "lunch?" — needs normalisation
   - two unrelated threads both titled "Question" merge together
   - a subject change mid-thread splits it incorrectly

✅ Use RFC 5322 headers, which exist for exactly this:
   Message-ID:  unique identifier for this message
   In-Reply-To: the Message-ID this replies to
   References:  the full ancestor chain

Build a thread by following References/In-Reply-To into a tree, then
flatten for display. Fall back to normalised-subject + participants +
time-window heuristics ONLY when headers are missing (some clients
omit them).

The interesting design choice is that threading is per user: your view of a thread contains only the messages you received, which may be a subset of the true conversation. Storing thread_id on each user's metadata row — rather than globally — keeps this correct and keeps the query "show me this conversation" a single-shard operation.

Interview Questions

🟢 Beginner — What is store-and-forward, and why does it make email reliable?

Store-and-forward means every hop in the delivery chain durably writes the message to disk before acknowledging receipt to the previous hop, and only then attempts to forward it.

Sender → MTA-1 → MTA-2 → recipient mailbox

Each arrow: write durably, THEN reply "250 OK".

Why it makes email reliable: if MTA-2 is down, MTA-1 doesn't fail the message — it holds it in its own durable queue and retries for days, sending a "delayed" notice to the sender after a few hours and a bounce only if it ultimately fails. The recipient's server can be offline for a day and no mail is lost.

Compare a synchronous HTTP request, which simply fails if the destination is unavailable. Email's asynchrony is exactly what buys the durability.

The rule with no exceptions: never send 250 OK before the message is committed to durable storage. That acknowledgement is a promise that you now own the message and the sender may forget about it. Acking first and storing second means a crash in between loses the message permanently and silently — the sender believes it succeeded and will never retry.

The consequence is at-least-once delivery, so duplicates are possible — which is why every message carries a Message-ID that receivers deduplicate on.

🟢 Beginner — Why separate email metadata from content?

Because they have completely different access patterns, and forcing them into one store makes both worse.

MetadataContent
Size~1 KB~75 KB, up to 25 MB
ReadEvery inbox view, search, label changeOnly when a message is opened
MutabilityFrequently (read/unread, labels, stars)Write-once

Metadata is small, hot, structured and queried constantly — it belongs in an indexed database where filtering and sorting are fast.

Content is large, cold and immutable — it belongs in object storage, which is far cheaper per byte and built for exactly this.

What goes wrong if you combine them: a 25 MB attachment in a database row means every query touching that table reads pages full of blob data, even queries that never reference the attachment. Backups balloon, replication slows, and the buffer cache fills with bytes nobody is querying.

The bonus that makes the split really pay: once content lives in object storage keyed by its hash, you get deduplication for free. One memo with a 5 MB attachment sent to 10,000 employees stores one blob and 10,000 small references instead of 50 GB — and given that attachments dominate the storage bill, that's an enormous saving.

🟡 Mid — 100B emails/day at 75 KB average is 7.5 PB/day. How do you make that sustainable?

Three reductions, in order of impact:

1. Filter spam before storing it. Typically 50–80% of raw inbound is spam. Classifying early in the pipeline means you never pay to store, index or replicate the majority of traffic. Spam that is stored gets short retention (30 days) rather than forever.

2. Content-addressed deduplication — the biggest single win on the remainder:

blob_key = SHA-256(content)

A newsletter with a 2 MB image to 1M subscribers:
   naive  → 2 TB
   dedup  → 2 MB + 1M small references
Mailing lists, forwards and company-wide attachments make this
extremely effective — a large share of total bytes.

3. Tier by age. Access is heavily recency-biased — the vast majority of reads target recent mail. Keep the last months on fast storage and move older content to infrequent-access or archival tiers, at roughly 5× lower cost, retrieved on demand.

Plus: compress bodies (text compresses ~5×; already-compressed attachments don't), and store metadata separately so the hot, frequently-queried part stays small.

The operational detail that matters: deduplication requires reference counting or a garbage collector, because deleting one user's copy must not destroy everyone else's. Getting that wrong is data loss, so many systems prefer a sweeping GC over refcounts — simpler to reason about and safer under partial failure.

🟡 Mid — Why is email search easier than web search?

Because a query only ever searches one user's mailbox, which changes the sharding strategy and eliminates the hardest problem in web search.

WEB SEARCH
   any query may match any document
   → shard by document → every query fans out to ~300 shards
   → the response waits on the SLOWEST shard
   → with p99=50ms per shard, ~95% of queries hit some shard's tail

EMAIL SEARCH
   a query searches exactly one mailbox
   → shard the index BY USER → one query, ONE shard
   → no fan-out, no merge, no tail amplification

Scale is also far smaller per query. Even a heavy user with a million emails has an index of roughly 100 MB, which fits comfortably in memory on a single node. Web search indexes tens of terabytes across hundreds of machines.

And relevance is much simpler. Web search must rank against an adversarial corpus where SEO actively games the algorithm. Email results are usually best sorted by date, or with light relevance scoring — there's no spam-ranking arms race because the user already trusts their own mailbox.

What email search needs that web search doesn't: combining structured filters with full-text, as in from:alice has:attachment after:2026/01/01 "quarterly report". The planner should apply the selective metadata predicates first — usually cheap indexed lookups — then run text matching over the small surviving set. Same "most selective first" principle as posting-list intersection.

🔴 Senior — Design spam filtering. What's the cost function, and what does it imply?

The cost function is deeply asymmetric, and that asymmetry dictates the entire design:

FALSE POSITIVE — legitimate mail classified as spam
   the user misses a job offer, an invoice, a medical result.
   Worse: it is INVISIBLE. They don't know to go looking.

FALSE NEGATIVE — spam reaches the inbox
   mildly annoying. The user deletes it in two seconds.

So the system should be tuned heavily toward letting spam through rather than risking blocking real mail — and it should never delete. Route to a Spam folder the user can inspect and recover from. Silently dropping mail is the one thing an email system must not do, and it's a rule worth stating explicitly.

Signals, cheapest and strongest first:

• SPF / DKIM / DMARC — is this IP authorised to send for this domain, is the message cryptographically signed, and what policy does the domain declare? Cheap and strong.
• IP and domain reputation — historical behaviour is the single most predictive signal in practice.
• Content ML over text, links and structure. Powerful but adversarial — spammers test against filters continuously, so the model needs constant retraining.
• User feedback — "mark as spam" is both a global training signal and per-user personalisation.
• Rate and graph patterns — one sender to a million recipients in a minute is suspicious regardless of content.

Architecture: the offline/online split again — train the model offline on historical data and feedback, classify inline at delivery within a tight latency budget. Order the checks so cheap signals resolve the clear cases and the expensive model only runs on the ambiguous middle. Cache reputation lookups aggressively, since they're on the hot path for a million messages per second.

Filter before storage and indexing, so you never pay to persist the majority of inbound traffic — a substantial fraction of total system cost, not merely an optimisation.

The outbound side is equally important and often forgotten: if a compromised account sends spam from your infrastructure, your IPs get blocklisted and all your users' outbound mail stops. Rate-limit per sender, detect compromise, and monitor blocklist status as a first-class operational metric.

🔴 Senior — Implement "undo send". What's actually happening?

Nothing is undone — the send is simply delayed. Once a message leaves for another provider's server it is irretrievable; SMTP has no recall mechanism, and any claim otherwise is wrong.

1. User clicks Send.
2. The message is written durably to an OUTBOUND QUEUE with
   send_after = now + 10s. The UI shows "Sent" with an Undo option.
3a. User clicks Undo within the window
       → mark the queued message cancelled, move it back to Drafts.
       → nothing ever left the building.
3b. Window expires
       → a worker picks it up, does the MX lookup, and delivers.

Why this is the only correct implementation: the alternative — sending immediately and attempting recall — cannot work across providers. Recall exists only inside closed systems like Exchange where the server controls both mailboxes, and even there it typically fails if the message was already read.

Design details that matter:

• The queue must be durable. A crash during the delay window must not lose the message — it's already been acknowledged to the user as sent.
• Cancellation must be atomic with respect to the sending worker. Use a conditional update (UPDATE ... SET state='cancelled' WHERE state='pending') so a message can't be both cancelled and delivered — the same check-then-act discipline as everywhere else.
• Same-provider recipients could technically be delivered instantly and retracted, but behaving inconsistently would confuse users. Apply the same delay uniformly.
• Keep the window short (5–30 s). Longer delays mean users notice their mail arriving late, and the value of undo drops sharply after a few seconds.

The honest framing for an interview: "undo send" is a product feature implemented as a deliberate delay, not a technical capability to retract sent mail. Recognising which requirements are genuinely impossible and reframing them into something achievable is a more valuable skill than engineering toward an impossible spec — and this is a clean example of it.

🏋️ Graded Exercises

Exercise 1 (Easy): A 5 MB attachment is sent to 10,000 employees. How much storage, with and without deduplication?
Solution 
WITHOUT DEDUPLICATION
   10,000 recipients × 5 MB = 50 GB

WITH CONTENT-ADDRESSED DEDUPLICATION
   blob_key = SHA-256(content)
   1 × 5 MB = 5 MB of content
   + 10,000 metadata rows, each holding a reference (~100 B)
   = 5 MB + 1 MB ≈ 6 MB

REDUCTION: ~8,300x for this message

Why this matters at scale: attachments dominate email storage, and duplication is pervasive — company-wide memos, newsletters, mailing lists, and forwarded threads all send identical bytes to many mailboxes. Deduplication typically removes a large fraction of total storage, which at 7.5 PB/day of raw ingest is the difference between sustainable and not.

What it requires: reference counting so deleting one recipient's copy doesn't destroy everyone else's, or — often preferable — a garbage collector that periodically sweeps blobs with no remaining references. GC is simpler to make correct under partial failure, since a miscounted reference is silent data loss.

The trade to note: cross-user deduplication means the provider can observe that two users hold identical content. Within one trust boundary that's normally fine, but it's exactly why end-to-end encrypted mail cannot deduplicate — per-user encryption makes identical files produce different ciphertext.

Exercise 2 (Easy): Why must an SMTP server never ack before writing to disk?
Solution

Because 250 OK is a promise of ownership. The sending server takes it as "this message is now your responsibility", removes it from its own queue, and will never retry.

❌ receive → ack → store
   Crash between ack and store:
     - the sender believes delivery succeeded
     - the sender has discarded its copy
     - no error is raised anywhere
   → the message is GONE, silently and permanently.

✅ receive → store durably → ack
   Crash before the ack:
     - the sender receives no 250 OK
     - the sender RETRIES from its durable queue
   → at-least-once delivery. Nothing is lost.

Silence is what makes this failure so bad. There's no error, no bounce, no log entry suggesting a problem — it surfaces days later as a human asking "did you get my email?", by which time the cause is untraceable.

"Durably" means replicated, not merely written to one local disk. If that machine's disk fails after acking, the outcome is the same. Write to replicated storage before acknowledging.

The consequence to accept: at-least-once delivery means duplicates are possible when an ack is lost after a successful store. That's why every message carries a Message-ID and receivers deduplicate on it — the same at-least-once-plus-idempotency pattern as message queues.

Exercise 3 (Medium): Design the email threading algorithm. Why not group by subject?
Solution

Subject-based grouping fails in three distinct ways:

1. Prefix noise: "Re: Re: FW: lunch?" vs "lunch?" — needs
   normalisation, and the prefixes are locale-specific ("AW:", "SV:").
2. Collisions: two unrelated conversations both titled "Question" or
   "Hello" merge into one thread.
3. Subject changes: someone edits the subject mid-conversation and the
   thread splits, or a reply keeps an old subject and joins the wrong one.

Use the RFC 5322 headers designed for this:

Message-ID:  <abc123@example.com>    unique to this message
In-Reply-To: <xyz789@example.com>    the message this replies to
References:  <m1@..> <m2@..> <xyz789@..>   full ancestor chain

ALGORITHM
   1. For each message, look up In-Reply-To (then References,
      walking backwards) to find its parent.
   2. Parent found → attach to that parent's thread.
      No parent found → start a new thread rooted here.
   3. If a later message reveals two existing threads share an
      ancestor, MERGE them (out-of-order arrival is common).
   4. Flatten the tree by date for display.

   5. FALLBACK only when headers are missing (some clients omit
      them): normalised subject + overlapping participants +
      a bounded time window.

The design choice worth highlighting: threading is per user. Your view of a conversation contains only the messages you received — you may have been added to a thread halfway through, or BCC'd on one message. Storing thread_id on each user's metadata row rather than globally keeps this correct and keeps "show me this conversation" a single-shard query.

Practical robustness: some clients set References incorrectly or truncate it, so cap how far back you walk and treat the headers as strong hints rather than guarantees. And handle the out-of-order case explicitly — a reply can arrive before the message it replies to.

Exercise 4 (Medium): A user has 2 million emails and searches for from:alice has:attachment "budget". Design the query execution.
Solution

Order the predicates by selectivity — cheapest and most restrictive first, exactly like posting-list intersection:

Estimated selectivity for this mailbox of 2M messages:
   from:alice        → maybe 500 messages     (very selective)
   has:attachment    → maybe 100,000          (moderately selective)
   "budget" in text  → maybe 2,000            (selective, but the
                                               most EXPENSIVE to
                                               evaluate)

EXECUTION PLAN
   1. Metadata index lookup on (user_id, from) → ~500 candidates.
      Cheap B-tree lookup, massive reduction.
   2. Filter that set by has_attachment flag → ~200 remaining.
      In-memory filter over 500 rows — trivial.
   3. Full-text match "budget" over those ~200 documents only.
   4. Sort by date, return the top 50.

Total work: one index lookup plus text matching on 200 documents,
rather than a text search over 2 million.

The key insight: metadata predicates are cheap indexed lookups; full-text matching is expensive. So resolve the structured filters first and run text search over the small surviving set — which is why the metadata store and the text index need to cooperate rather than being queried independently and intersected afterwards.

Statistics make this possible. The planner needs cardinality estimates to know that from:alice is more selective than has:attachment. Maintain per-user counts for common fields; without them the planner guesses and can pick catastrophically wrong orders.

Why this is single-shard: everything is scoped to one user, so the whole query executes on one node with no fan-out, no merge and no tail amplification — the structural advantage email search has over web search.

Indexes required: (user_id, from, date), (user_id, thread_id), (user_id, label, date), plus the per-user text index. Note every one is prefixed by user_id, which is what keeps queries confined to a single shard.

Exercise 5 (Hard): The recipient's mail server is down for 3 days. Trace exactly what happens to a message sent on day 1.
Solution 
Day 1, 09:00 — user sends. Our MTA stores it durably and acks the
   client. The message is now OUR responsibility.

09:00 — MX lookup for the recipient domain; connection attempt fails
   (timeout / connection refused). This is a TEMPORARY failure, so we
   do NOT bounce.

Retry schedule with exponential backoff and jitter:
   +15 min, +30 min, +1 h, +2 h, +4 h, +8 h, then every ~8 h
   (jitter matters — thousands of queued messages for one domain must
    not all retry simultaneously when it recovers)

Day 1, ~13:00 (after ~4 h) — send the sender a DELAY NOTIFICATION:
   "Your message has not yet been delivered; we are still trying."
   Informative, not a failure — the sender should not resend.

Days 1-3 — retries continue from durable storage. Our queue grows with
   every message for that domain; monitor per-destination queue depth.

Day 4, ~09:00 — the recipient server recovers. The next retry connects,
   the message is delivered, and we receive 250 OK. We delete our copy.
   The recipient sees it with its ORIGINAL Date header — sent day 1,
   received day 4.

IF it had NOT recovered within the retry window (~5 days is typical):
   send a permanent BOUNCE to the sender containing the failure reason
   and the original message, then delete our copy.

What this demonstrates about the design:

1. Durability across days, not seconds. The message survives in our queue through restarts and deploys, which is only possible because it was written to replicated storage before we acked the sender.

2. Temporary versus permanent failures are treated completely differently. A 4xx or a connection failure means retry; a 5xx ("no such user") means bounce immediately. Retrying a permanent failure wastes resources and looks like abuse to the receiving server.

3. The sender is kept informed — a delay notice after a few hours, a bounce only at the end. Silence would leave them unsure whether to resend.

4. Jitter on retries is essential. When a large domain recovers, every queued message for it would otherwise retry at once — a thundering herd against a server that has just come back up, likely knocking it over again.

Operationally: alert on per-destination queue depth and age. A single domain accumulating messages for days is a signal worth investigating — it may be their outage, or it may be that you've been blocklisted.

Exercise 6 (Hard): Your outbound IPs get added to a spam blocklist. Diagnose and fix.
Solution

This is an outage, not an inconvenience — being blocklisted means receiving servers reject your mail, so every user's outbound email starts failing, regardless of content.

Diagnosis — what caused it, in order of likelihood:

1. Compromised accounts (most common). Attackers obtain credentials via phishing or credential stuffing and send spam from legitimate accounts. Your infrastructure is doing exactly what it was asked to — which is why volume-based detection is required rather than content filtering alone. Check: per-account send rates, sudden spikes, unusual recipient patterns, logins from new locations.

2. A misconfigured or abused relay allowing unauthenticated sending.

3. A legitimate bulk campaign that looked like spam — a marketing send to a stale list with many dead addresses generates bounces and complaints, which is precisely what reputation systems penalise.

4. Poor list hygiene — repeatedly sending to addresses that hard-bounce, which signals you're not processing bounce feedback.

Immediate response:

1. Stop the source — suspend the offending accounts and pause the campaign. Delisting before fixing the cause guarantees immediate relisting.
2. Route around it — shift outbound to unaffected IP pools so most users' mail keeps flowing while you remediate.
3. Request delisting from each blocklist, with a clear description of the cause and the remediation. Some are automatic after the abuse stops; others require manual review.

Preventing recurrence — this is the part that matters:

• Per-account outbound rate limits, with much tighter limits for new accounts. This alone prevents most incidents.
• Anomaly detection on send patterns — a user who normally sends 20 emails a day suddenly sending 5,000 should be throttled automatically and reviewed.
• Process bounce feedback and suppress hard-bounced addresses permanently. Continuing to mail dead addresses is a strong negative reputation signal.
• Honour feedback loops from major providers, which report spam complaints back to you.
• Segment your IP pools by traffic type — transactional, bulk, and per-tenant for large customers — so one bad sender cannot poison the reputation everyone depends on. This is the bulkhead pattern applied to reputation.
• Enforce SPF, DKIM and DMARC on your own outbound so receivers can verify you.
• Monitor blocklist status continuously as a first-class operational metric — you want to discover this from a dashboard, not from users reporting that their mail bounces.

The framing: outbound reputation is a shared resource among all your users, and one compromised account can destroy it for everyone. That makes abuse prevention an availability requirement rather than a policy nicety.

🎯 Key Takeaways

  • Store before you acknowledge. A 250 OK is a promise of ownership — acking first means silent, permanent loss on a crash.
  • Store-and-forward makes email uniquely durable — every hop retries from its own durable queue for days.
  • Distinguish 4xx from 5xx: retry temporary failures with jittered backoff, bounce permanent ones immediately.
  • Separate hot metadata from cold content — attachments never belong in the database.
  • Content-addressed deduplication is the biggest storage win — one memo to 10,000 people is one blob, not 10,000.
  • Shard by user. Every query is user-scoped, so search touches exactly one shard — no fan-out, no tail amplification.
  • Email search is far easier than web search for that reason, and needs structured filters combined with text — apply the selective ones first.
  • Spam filtering has an asymmetric cost function: a false positive is catastrophic and invisible, a false negative is trivial. Never delete — quarantine.
  • Filter spam before storing and indexing, since most inbound traffic is spam.
  • Thread with Message-ID/In-Reply-To/References, not subject lines — and thread per user, since each sees a different subset.
  • "Undo send" is a delayed send, not a retraction. Recognising impossible requirements and reframing them is the real skill.
  • Outbound reputation is a shared resource — one compromised account can blocklist everyone. Rate-limit, detect anomalies, and segment IP pools.
