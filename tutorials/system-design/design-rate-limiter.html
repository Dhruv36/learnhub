Design API Rate Limiter Case Study

What you'll master: the four algorithms and the specific flaw each one has, why check-then-decrement is a race condition and how a Lua script fixes it atomically, the latency budget that decides your architecture, the fail-open vs fail-closed decision (a product question, not a technical one), and how to rate-limit accurately across 50 stateless servers without making the limiter itself the bottleneck.

Prerequisites: Caching Strategies, Concurrent Programming (the atomicity problem), Estimation. Pairs with Heartbeat & Retry (what clients do when you return 429).

🎯 What this problem is really testing. Three things: can you compare algorithms on their actual trade-offs rather than listing them; do you notice that "check tokens, then decrement" is two network round trips and therefore a race; and do you recognise that a component on every single request's hot path has a latency budget measured in single-digit milliseconds. Candidates who describe token bucket correctly but add a 20 ms Redis round trip to every request have missed the point.

1. Requirements

FunctionalNon-functional
Limit each client to N requests per windowLow latency — it sits on every request; budget <5 ms
Return 429 with Retry-After when exceededHighly available — the limiter must not become the outage
Different limits per tier / endpoint / methodAccurate under concurrency across many servers
Limit by user, API key, or IPMemory-efficient for millions of clients

Clarifying questions worth asking:

"How accurate must it be?"  → THE key question. Exact enforcement
   forces a single serialisation point; ±5% allows far cheaper designs.
   Assume approximate is fine — no product cares about 100 vs 103 req/min.
"Fail open or fail closed if the limiter is unavailable?"
   → A business decision. Assume FAIL OPEN for a public API (availability
     over protection), but note where the opposite is right.
"Per-user, per-IP, or both?" → Both, at different granularities.
"Is this for abuse prevention or cost control?"
   → Changes the answer: abuse prevention needs to be harder to evade.

2. Estimation: The Number That Shapes Everything

Assume 1M active clients, 10,000 requests/s at peak.

STATE SIZE
   token bucket per client ≈ {tokens: float, last_refill: int} ≈ 20 B
   1,000,000 clients × 20 B = 20 MB
   → CONSEQUENCE: the ENTIRE state fits in RAM on one machine, trivially.
     This is a THROUGHPUT problem, not a storage problem — which rules
     out any design involving a database.

THROUGHPUT
   10,000 checks/s (one per request, plus internal service calls)
   → CONSEQUENCE: one Redis node handles ~100K ops/s, so a single node
     covers this with 10x headroom. Sharding is for availability, not
     capacity.

LATENCY BUDGET
   A same-DC Redis round trip is ~0.5-1 ms.
   If the API's own p99 is 100 ms, spending 1 ms on rate limiting is 1%.
   → ACCEPTABLE. But if this were an internal service with a 5 ms p99,
     1 ms would be 20% — and you'd need the local-token design (§6).

The 20 MB figure is the one to say out loud: it immediately eliminates a whole family of over-engineered answers involving persistent storage, and reframes the problem as "how do I make a small amount of shared state fast and consistent".

3. The Core Design Decision: Which Algorithm

AlgorithmMechanismMemory/clientThe specific flaw
Fixed window counterINCR a key per window; reset each period~8 BBoundary burst: 100 requests at 12:00:59 plus 100 at 12:01:00 is 200 in one second under a "100/min" limit — 2× the intended rate
Sliding window logStore a timestamp per request; count those within the window~8 B × NExact, but memory scales with the limit. A 10,000/hour limit means 10,000 timestamps per client — 80 KB × 1M clients = 80 GB
Sliding window counterWeighted blend of the current and previous fixed window~16 BAn approximation (assumes uniform distribution within the previous window), typically within ~1% of exact. Excellent memory/accuracy trade
Token bucketBucket of capacity C refilling at rate R; each request consumes one token~20 BNo significant flaw. Allows bursts up to C — which is usually a feature
Leaky bucketRequests queue and drain at a fixed rate~queue sizeSmooths output completely (no bursts), but queues requests, adding latency — better for shaping outbound traffic than for admitting inbound

The boundary-burst flaw made concrete, since it's the one candidates most often miss:

Fixed window, limit 100/minute:

  12:00:00 ─────────── window A ─────────── 12:01:00 ── window B ──
                          ▲                    ▲
                 100 requests at 12:00:59   100 requests at 12:01:00

  Both windows are individually within limit. But the client sent
  200 requests in a ~1 second span — DOUBLE the intended rate, at
  exactly the moment a burst is most damaging.

Token bucket cannot do this: the bucket holds at most C tokens, so
the burst is bounded by C regardless of when it arrives.
💡 Choose token bucket, and be able to say why "allows bursts" is different from the fixed-window flaw. Token bucket's burst is bounded and intentional — capacity C caps the instantaneous burst while refill rate R caps the sustained rate, and those are two independently tunable knobs. That models real traffic well: a client idle for a minute can legitimately send a short burst, but cannot sustain more than R. The fixed-window boundary burst, by contrast, is an unintended 2× breach of the stated limit that no configuration prevents. Same word, opposite meaning — and articulating that distinction is the strongest signal on this question.

4. Token Bucket, Correctly Implemented

The naive implementation contains the race this problem is built around:

❌ Check then decrement 
tokens = redis.get(key)      # RTT 1
if tokens >= 1:
    redis.decr(key)          # RTT 2
    return ALLOW
return REJECT

Two concurrent requests both
read "1 token left", both pass
the check, both decrement.
→ 2 requests admitted on 1 token,
  and the counter goes negative.

The gap between the two round
trips is the race window.
✅ Atomic Lua script 
redis.eval(SCRIPT, key, now,
          rate, capacity)   # 1 RTT

Redis executes Lua scripts
atomically — single-threaded,
no interleaving possible.

Refill, check and decrement
happen as ONE indivisible
operation, and it's also
one round trip instead of two.

Correctness AND lower latency.
-- Atomic token bucket. KEYS[1] = bucket key
-- ARGV: now_ms, refill_per_sec, capacity, requested
local key      = KEYS[1]
local now      = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local capacity = tonumber(ARGV[3])
local want     = tonumber(ARGV[4])

local b        = redis.call('HMGET', key, 'tokens', 'ts')
local tokens   = tonumber(b[1])
local last     = tonumber(b[2])

if tokens == nil then                    -- first request from this client
  tokens = capacity
  last   = now
end

-- Refill based on elapsed time, capped at capacity
local delta = math.max(0, now - last) / 1000.0
tokens = math.min(capacity, tokens + delta * rate)

local allowed = 0
if tokens >= want then
  tokens  = tokens - want
  allowed = 1
end

redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
-- Expire idle buckets so memory is reclaimed automatically
redis.call('EXPIRE', key, math.ceil(capacity / rate) * 2)

-- Return enough for the client's response headers
return { allowed, math.floor(tokens), math.ceil((want - tokens) / rate) }

Three details in that script worth noting. The lazy refill computes tokens from elapsed time on read, so there's no background job ticking a million buckets. The EXPIRE reclaims memory for idle clients automatically — without it, state grows forever as clients come and go. And it returns the remaining tokens and retry-after, so the caller can populate response headers without a second query.

Pass the timestamp in from the caller rather than using Redis's clock inside the script: it keeps the script deterministic (a requirement for safe replication in older Redis versions) and makes the behaviour testable.

5. The Response Contract

A rate limiter's API surface is part of its design, because clients build retry behaviour on it:

HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 30            ← seconds until tokens are available
Retry-After: 30                ← the standard header clients honour

{ "error": { "code": "rate_limit_exceeded",
             "message": "Rate limit exceeded. Retry in 30s.",
             "retry_after": 30 } }

Return the limit headers on successful responses too, so well-behaved clients can self-throttle before hitting the wall rather than discovering it by being rejected. And per the API lesson, 429 is explicitly retryable — which makes Retry-After essential: without it, clients guess, and their guesses synchronise into exactly the retry storm the limiter is meant to prevent.

6. Deep Dive: Distributing Without Becoming the Bottleneck

Local per-server counters are useless — 50 servers each allowing 100/min means a client gets 5,000/min. So state must be shared. The question is how much you pay for that.

ApproachAccuracyLatency addedUse when
Centralised RedisExact~0.5–1 ms per requestThe default. Fine when the API's own latency is tens of milliseconds
Local buckets, divided limitPoor — uneven load means some servers reject while others have spare capacity0 msRarely. Breaks badly with unbalanced routing
Local token batchesApproximate (±batch size)~0 ms amortisedWhen latency is critical. Each server claims 100 tokens at a time from Redis, then serves locally
Sharded by client keyExact per client~0.5–1 msScaling beyond one Redis node — a client's key always maps to one shard, so no cross-shard coordination is ever needed

Local token batching is the design that removes the round trip from the hot path:

Instead of 1 Redis call per request:
   server claims 100 tokens from the shared bucket in ONE call,
   then serves 100 requests from local memory with zero network cost.

   → Redis load drops 100x: 10,000/s becomes 100/s.
   → Latency contribution drops to ~0 for 99% of requests.

Trade-offs to state:
   - a server holding unused tokens when traffic shifts wastes part of
     the budget → return unclaimed tokens on a timer, keep batches small
   - accuracy becomes ±(batch × servers) in the worst case
   - a crashed server's claimed tokens are lost until they expire

This is the same "batch to amortise the coordination cost" move as
range-allocating IDs in the ID generator case study.

Sharding by client key is what makes this scale horizontally: because each client's bucket lives on exactly one shard, there is never cross-shard coordination. That's a rare property — most sharded systems need scatter-gather somewhere — and it's why rate limiting scales so cleanly.

7. Deep Dive: Failure Behaviour and Evasion

What happens when Redis is unavailable? This is a product decision, and the interviewer wants you to recognise that rather than pick a default:

Fail open (allow)Fail closed (reject)
RiskUnprotected during the outage — abuse and overload get throughThe limiter's outage becomes your API's outage
Right forPublic APIs where availability matters most; the limiter must never be the single point of failureProtecting a fragile downstream that genuinely cannot survive unlimited traffic, or metered/billable operations

Usually fail open — a rate limiter exists to protect the system, and it would be perverse for it to cause the outage it prevents. But fail open with a local fallback: each server applies a conservative in-memory limit while Redis is down, so you degrade from precise global limiting to approximate local limiting rather than to none at all. That's a much better answer than picking either extreme.

Choosing the key determines how evadable the limit is:

KeyStrengthWeakness
API key / user IDPrecise, tied to an account, survives IP changesOnly works for authenticated traffic — useless for login and signup endpoints
IP addressWorks pre-authenticationBoth over- and under-blocks: a corporate NAT or mobile carrier shares one IP across thousands of users, while an attacker with a botnet or IPv6 range has effectively unlimited IPs
IP subnet (/24, /64)Blunts trivial IPv6 rotation, since a single host often gets a whole /64Still over-blocks shared networks
Composite (IP + device + account)Much harder to evadeMore state, more complexity, some privacy considerations

The unauthenticated case is the genuinely hard one — and login endpoints are exactly where rate limiting matters most, because that's where credential stuffing happens. The practical answer is layered: a per-IP limit, plus a per-account limit on failed logins (so distributing across IPs doesn't help an attacker targeting one account), plus progressive friction (CAPTCHA, delays) rather than a hard block, since a hard block on an account is itself a denial-of-service vector against that user.

Interview Questions

🟢 Beginner — Explain the fixed-window boundary burst problem.

A fixed-window counter divides time into aligned windows (say, each calendar minute) and counts requests in the current one, resetting at the boundary. The flaw is that a client can concentrate its allowance at the end of one window and the start of the next:

Limit: 100 requests/minute.

  12:00:59  → 100 requests   (window 12:00-12:01, now full)
  12:01:00  → 100 requests   (window 12:01-12:02, fresh allowance)

Both windows are individually compliant, but the client sent
200 requests in roughly one second — twice the intended rate.

That matters because the point of a rate limiter is usually protecting a downstream from instantaneous load, and this flaw permits a 2× spike at exactly the wrong moment. No configuration prevents it; it's inherent to aligned windows.

Fixes: a sliding window counter (blend the current and previous window by how far into the current one you are — approximate but close, at ~16 bytes per client), or token bucket, where the bucket holds at most C tokens so any burst is bounded by C regardless of when it arrives.

Fixed window's advantages are real — it's the simplest to implement (INCR plus EXPIRE) and the cheapest in memory — so it's a reasonable choice when the limit is coarse and a 2× boundary spike is harmless. Knowing when the flaw doesn't matter is part of the answer.

🟢 Beginner — Where should the rate limiter live, and why not in each service?

At the API gateway or edge, before requests reach application servers.

Three reasons:

1. Rejecting early saves the most resources. A request blocked at the edge consumes one cheap check; one blocked inside a service has already consumed a connection, a thread, authentication work, and possibly a database query. Under the abusive traffic the limiter exists to stop, that difference is exactly what keeps you up.

2. One place to configure and audit. Limits per tier, per endpoint and per customer live in a single config rather than being reimplemented — slightly differently, and with slightly different bugs — in each of N services.

3. Consistency. One implementation means one set of semantics for headers, error formats, and key derivation.

Why not purely per-service: beyond duplication, each service would need its own view of shared state, and a client's total consumption across services would be invisible — so "100 requests per minute" would silently become "100 per minute per service".

The nuance worth adding: the edge limiter doesn't remove the need for service-level protection. Internal callers bypass the gateway, and individual services may need their own limits for expensive endpoints. So: coarse global limiting at the edge, plus targeted limits on specific expensive operations — defence in depth rather than either/or. And note that wherever enforcement happens, it still needs shared state.

🟡 Mid — Why is check-then-decrement a bug, and how do you fix it?

Because it's two separate network round trips with a gap between them, and concurrent requests interleave in that gap:

Bucket has 1 token.

Request A: GET tokens → 1     ┐ both read before either writes
Request B: GET tokens → 1     ┘
Request A: DECR → 0   → ALLOW
Request B: DECR → -1  → ALLOW

Two requests admitted on one token, and the counter is now negative.
Under real concurrency this over-admits substantially — and it gets
worse as traffic rises, which is exactly when the limit matters.

This is the same read-modify-write race as counter++ in the concurrency lesson, distributed across the network.

The fix is a Lua script. Redis executes scripts atomically — it's single-threaded, and a script runs to completion without interleaving — so refill, check and decrement become one indivisible operation:

-- refill from elapsed time, then check-and-consume, atomically
tokens = math.min(capacity, tokens + elapsed * rate)
if tokens >= 1 then
  tokens = tokens - 1
  allowed = 1
end
redis.call('HMSET', key, 'tokens', tokens, 'ts', now)

This also halves the latency, since it's one round trip instead of two — correctness and performance in the same change, which is unusual and worth pointing out.

Alternatives: Redis transactions with WATCH (optimistic — retries on conflict, which under contention is worse than a script); or a single atomic primitive like INCR with EXPIRE for a fixed-window counter, where the whole operation is naturally one command. Token bucket needs the script because refill depends on elapsed time, so it can't be expressed as one built-in command.

Two implementation details I'd mention: pass now in as an argument rather than reading the clock inside the script, keeping it deterministic and testable; and set an EXPIRE so idle buckets are reclaimed automatically.

🟡 Mid — Redis goes down. What should happen, and what would you actually build?

This is a product decision before it's a technical one, and recognising that is the point of the question.

Fail closed (reject everything) means the limiter's outage becomes your API's outage — a component added to protect availability has become the thing destroying it. That's usually perverse, though it's right when the downstream genuinely cannot survive unlimited traffic, or when the operations are billable and admitting unmetered usage costs real money.

Fail open (allow everything) keeps the API up but removes all protection precisely when the system may already be stressed — and if Redis went down because of a traffic surge, failing open pours fuel on it.

What I'd actually build: fail open with a local fallback.

if redis_available:
    decision = redis_token_bucket(key)          # precise, global
else:
    decision = local_in_memory_limit(key)       # conservative, per-server
    # e.g. global_limit / server_count, applied locally

Degrades from precise global limiting to approximate local limiting,
rather than to no limiting at all. Requests keep flowing; abuse is
still bounded.

Supporting details: a circuit breaker on the Redis client so a slow Redis fails fast rather than adding its timeout to every request (slow is worse than down here — it consumes the thread pool, per the bulkhead discussion); a short timeout on the check, maybe 5–10 ms, since blocking a request on a struggling limiter is the wrong trade; and an alert, because a rate limiter silently failing open is exactly the kind of degradation nobody notices until abuse arrives.

I'd also make the behaviour configurable per endpoint: fail open for read APIs, fail closed for expensive or billable operations. The right answer genuinely differs by endpoint, and encoding that is better than one global policy.

🔴 Senior — Your limiter adds 1 ms to every request, and the service's p99 budget is 5 ms. Redesign.

1 ms on a 5 ms budget is a 20% regression — unacceptable, and a case where the standard centralised-Redis answer is simply wrong. The fix is to remove the network round trip from the hot path.

Design: local token batching.

Instead of one Redis call per request, each server CLAIMS a batch:

   1. Server asks Redis for 100 tokens (one round trip)
   2. Serves the next 100 requests from LOCAL memory — ~50 ns each
   3. Claims another batch when its local pool runs low
      (refill asynchronously at ~20% remaining, so the claim's latency
       is never on a request's critical path)

Effect:
   Redis calls drop 100x — 10,000/s becomes 100/s
   Per-request added latency ≈ 0 for 99% of requests
   The remaining 1% don't block either, because refill is async

The trade-offs I'd state:

• Accuracy becomes approximate, bounded by (batch size × server count) in the worst case. With 100-token batches on 20 servers, transient over-admission is up to ~2,000 — so tune the batch size against the limit, using smaller batches for tighter limits.
• Unused tokens are stranded when traffic shifts away from a server. Return unclaimed tokens on a timer, and keep batches small relative to the total budget.
• A crashed server's tokens are lost until they expire — acceptable, and a reason to keep batch sizes modest.

Alternatives worth naming: sampling — check the shared limiter on 1 in N requests and extrapolate, which is cheaper but much less precise; or moving the limiter out of the request path entirely by having a sidecar/agent maintain the local bucket and sync in the background, which is essentially the batching design with better ergonomics (and how service meshes implement it).

The underlying principle, and the reason this generalises: amortise coordination across many operations instead of paying it per operation. It's the same move as range-allocating IDs in the ID generator, or batching messages in realtime fan-out. Whenever a per-request coordination cost is unacceptable, the answer is usually to buy in bulk.

🔴 Senior — Design rate limiting for a login endpoint facing credential stuffing from a botnet.

This breaks the standard design, and understanding why is the substance of the answer. Two properties make it hard:

1. Traffic is unauthenticated, so there's no API key or user ID to key on — the identity is precisely what's being attacked.
2. A botnet has many IPs, so a per-IP limit is trivially evaded: 10,000 hosts each making 5 attempts per minute stays under any reasonable per-IP threshold while producing 50,000 attempts/min.

Meanwhile, per-IP limits over-block legitimate users behind corporate NATs and mobile carrier gateways, where thousands of real users share one address.

Layered design — no single key works, so use several:

1. PER-ACCOUNT failed-login limit  ← the key insight
   Key on the TARGETED USERNAME, not the source.
   "5 failed attempts per account per 15 min" holds regardless of how
   many IPs the attacker uses. Distributing the attack does not help
   them, because the target is the constant.

2. PER-IP limit, generous
   Catches unsophisticated attacks without punishing shared NATs.
   Key on /64 for IPv6, since one host often controls a whole /64.

3. GLOBAL anomaly detection
   Total failed-login rate across the platform. A botnet shows up as
   an aggregate spike even when every individual key looks innocent —
   this is what actually detects a distributed attack.

4. PROGRESSIVE FRICTION, not hard blocks
   1-2 failures  → normal
   3-5 failures  → CAPTCHA / proof-of-work
   6+            → exponential delay, then require email verification

Why friction rather than blocking: a hard per-account block is itself a denial-of-service vector — an attacker can lock any user out by deliberately failing their login. Friction degrades the attacker's economics (CAPTCHA and proof-of-work cost them money per attempt) while a legitimate user who mistyped their password can still get in.

Additional measures that matter more than the limiter: check credentials against known breach corpora and block reuse (credential stuffing only works because passwords are reused — this addresses the root cause); make responses constant-time and identical for "no such user" and "wrong password", so the endpoint can't be used to enumerate accounts; and alert on a spike in successful logins from new devices, since that's what a successful stuffing attack looks like.

The framing: rate limiting here is one layer of an anti-abuse system, not the solution. The design move that carries the most weight is keying on the target rather than the source — because the attacker controls the source and cannot change the target.

🏋️ Graded Exercises

Exercise 1 (Easy): A token bucket has capacity 10 and refills at 1 token/second. A client idle for 30 seconds sends 15 requests instantly. What happens?
Solution 
Idle 30 s at 1 token/s would add 30 tokens, but the bucket CAPS at
capacity: tokens = min(10, 0 + 30) = 10.

15 instant requests:
   requests 1-10  → ALLOWED  (consume the 10 available tokens)
   requests 11-15 → REJECTED (429) — the bucket is empty and refill
                    is only 1/second

After rejection, the client can send 1 request per second thereafter.

The two properties this demonstrates:

Capacity caps the burst. No matter how long a client idles, it can never accumulate more than 10 tokens — so the instantaneous burst is bounded by design. This is exactly what fixed-window counters fail to guarantee.

Refill rate caps the sustained rate. Over any long period, throughput converges to 1 request/second regardless of the burst.

Those are two independently tunable knobs, which is the main reason token bucket is preferred: you can allow a generous burst (good UX for a client that batches work) while keeping the long-run rate strict. A single "requests per minute" number cannot express that distinction.

Exercise 2 (Easy): Compute the memory for 1M clients under sliding window log (limit 1,000/hour) versus token bucket.
Solution 
SLIDING WINDOW LOG — stores a timestamp per request in the window
   worst case 1,000 timestamps × 8 B = 8 KB per client
   1,000,000 clients × 8 KB = 8 GB
   (plus per-entry overhead in a real Redis sorted set — realistically
    2-3x that, so ~16-24 GB)

TOKEN BUCKET — stores {tokens, last_refill}
   ~20 B per client
   1,000,000 × 20 B = 20 MB

→ Token bucket is roughly 400x smaller (and ~1000x with overhead).

The critical property: sliding window log memory scales with the limit, not just the client count. Raise the limit to 10,000/hour and it becomes 80 GB — so the design gets more expensive precisely as you become more permissive, which is a bad scaling characteristic.

Token bucket is O(1) per client regardless of the limit, because it stores a token count rather than a history.

When the log is still worth it: when you need exactness and an audit trail — "show me every request this client made in the window" — for a small number of high-value clients. It's the only algorithm here that's precise and inspectable. For general-purpose limiting at scale it's the wrong tool, and the sliding window counter (~16 B) gets you within ~1% of its accuracy at token bucket's memory cost.

Exercise 3 (Medium): Implement a sliding window counter and explain its approximation.
Solution 
def sliding_window_counter(redis, key, limit, window_sec, now):
    """Blend the current and previous fixed windows by how far we are
    into the current one. ~16 bytes/client, within ~1% of exact."""
    cur_start  = (now // window_sec) * window_sec
    elapsed    = (now - cur_start) / window_sec        # 0.0 .. 1.0
    cur_key    = f"{key}:{cur_start}"
    prev_key   = f"{key}:{cur_start - window_sec}"

    pipe = redis.pipeline()
    pipe.get(prev_key)
    pipe.incr(cur_key)
    pipe.expire(cur_key, window_sec * 2)     # reclaim automatically
    prev, cur, _ = pipe.execute()
    prev = int(prev or 0)

    # Weight the previous window by the fraction NOT yet elapsed.
    estimate = prev * (1 - elapsed) + cur
    return estimate <= limit, estimate


def demo():
    # Boundary behaviour: the previous window still counts, so a client
    # cannot double its rate by straddling the edge.
    class FakeRedis(dict):
        def pipeline(self): return self
        def get(self, k): self._q = self.get_val(k); return self
        def get_val(self, k): return dict.get(self, k, 0)
        def incr(self, k): self[k] = dict.get(self, k, 0) + 1; return self
        def expire(self, k, s): return self
        def execute(self): return [self._prev, self._cur, None]
    # (illustrative — the assertion below is the property that matters)

    # With prev=100, limit=100, at 10% into the new window:
    #   estimate = 100*0.9 + cur  → already 90 before ANY new request
    prev, limit = 100, 100
    for elapsed, expect_allowed in [(0.1, False), (0.95, True)]:
        est = prev * (1 - elapsed) + 1
        assert (est <= limit) == expect_allowed, (elapsed, est)
    print("ok — boundary burst is blocked early in the window")

if __name__ == "__main__":
    demo()

The approximation: it assumes requests in the previous window were spread uniformly. If a client actually sent all 100 requests in the last second of the previous window, the weighted estimate under-counts them early in the new window (it assumes only a fraction fall inside the true sliding window).

Why that's acceptable: Cloudflare reported the error is under ~1% for real traffic, and the memory cost is two counters (~16 B) instead of a full timestamp log. Crucially, it does fix the boundary burst — as the demo shows, immediately after a window rolls over the previous window's count still dominates the estimate, so a client cannot get a fresh allowance by waiting for the edge.

This is the right default when you want fixed-window's cheapness without its 2× flaw and don't need token bucket's separate burst/rate knobs.

Exercise 4 (Medium): Design tiered limits: free 100/hour, pro 10,000/hour, enterprise custom. Where does the tier lookup happen, and what could go wrong?
Solution 
Bucket parameters become per-client rather than global:

   free:       capacity 100,    refill 100/3600  ≈ 0.028/s
   pro:        capacity 10,000, refill 10000/3600 ≈ 2.8/s
   enterprise: from the account record

Key: rate:{client_id}   → the limit PARAMETERS come from the client's
                          plan, looked up at request time.

Where the lookup happens is the design question, because it's on every request:

Don't query the account database per request — that adds a second dependency and a second round trip to the hot path, and it makes the limiter fail whenever the account service is degraded.

Instead:

1. Cache plan data aggressively in the gateway (a few minutes' TTL). Plans change rarely — this is close to a perfect caching workload.
2. Better: put the tier in the API key itself or in a signed token claim, so the limit parameters arrive with the request and need no lookup at all. This is the cleanest option and removes the dependency entirely.
3. Store the limits alongside the bucket in Redis, refreshed by a background job on plan changes.

What could go wrong:

• Stale tier data — a customer upgrades and is still limited to the free tier for the cache TTL. Fix by invalidating on plan change (an event from billing), not just waiting for expiry. This is a support-ticket generator if ignored.
• Downgrades leave a large bucket — a pro customer dropping to free may hold 10,000 tokens. Reset or clamp the bucket on plan change.
• Enterprise custom limits need somewhere to live; a config service with a cached fallback avoids a per-request lookup.
• Burst capacity vs rate should be tuned separately per tier — enterprise customers often need a large burst for batch jobs even when their sustained rate is similar.
• Fail-open behaviour must be tier-aware: if plan data is unavailable, default to the free tier limits rather than unlimited, so a lookup failure can't be exploited for unlimited access.

Exercise 5 (Hard): One enterprise customer sends 40% of all API traffic through a single API key. Your limiter's Redis shard for that key saturates. Fix it.
Solution

This is a hot key, and — as with the viral link in TinyURL — the crucial point is that adding shards does not help. That API key hashes to one shard, so all 40% of traffic lands on one node no matter how many nodes you add.

Fix 1 — shard the bucket itself (the direct solution):

Split this client's limit across N sub-buckets:
   rate:{key}#0 .. rate:{key}#9,  each with limit/10

Each request picks a sub-bucket at random (or by hashing the request
ID) → load spreads across 10 shards.

Cost: accuracy degrades at the margins — one sub-bucket can be
exhausted while others have tokens, so the client may see rejections
slightly before their true limit. Mitigate by trying a second
sub-bucket before rejecting.

Fix 2 — local token batching for this client (usually better here). Since they're high-volume, batching amortises beautifully: each gateway claims 1,000 tokens at a time, cutting Redis operations by 1,000× for the client causing the problem. High volume is exactly the condition that makes batching efficient, so the worst offender becomes the cheapest to serve.

Fix 3 — a dedicated limiter instance for very large customers. Isolating them protects every other customer from their traffic (a bulkhead), and it's operationally simpler to reason about. This is common in practice for the largest accounts.

What I'd actually do: local token batching first — it's the least invasive, needs no accuracy compromise on the shared path, and gets better the more traffic the client sends. Add a dedicated instance if they grow enough to warrant operational isolation.

Two things worth raising beyond the immediate fix: monitor per-key traffic share so this is detected before saturation rather than after; and treat it as a commercial signal — a customer at 40% of platform traffic likely warrants a conversation about a dedicated tier, and possibly infrastructure they pay for. Recognising when a scaling problem is really an account-management problem is a senior instinct.

Exercise 6 (Hard): Design rate limiting that works across 3 regions with clients routed by GeoDNS, without cross-region latency on every request.
Solution

The tension: a global limit implies global state, but a cross-region round trip is 100–150 ms — utterly unacceptable on every request when the limiter's budget is single-digit milliseconds.

The resolution starts by questioning the requirement: does the limit genuinely need to be global? Most clients are routed to one region by GeoDNS and stay there, so a per-region limit is usually equivalent in practice. Establishing that changes the whole design.

Design: regional limiters with budget allocation.

1. Each region runs an INDEPENDENT limiter (local Redis, ~0.5 ms).
   No cross-region call on the request path. Ever.

2. Each region is allocated a SHARE of the global budget, based on
   observed traffic distribution:
      us-east 50%, eu-west 30%, ap-south 20%

3. A background reconciliation process (every 5-10 s) reports regional
   consumption to a coordinator and REBALANCES the shares — a region
   running hot borrows unused budget from an idle one.
   This is off the hot path, so its latency is irrelevant.

4. Enforce a hard per-region ceiling so a coordinator failure cannot
   allow unbounded consumption anywhere.

The accuracy trade, stated honestly: a client that somehow hits all three regions could briefly consume up to the sum of the regional allocations before rebalancing catches up. For a limit of 10,000/hour, transient over-admission of a few percent is irrelevant. If exactness were genuinely required, you'd need synchronous global coordination — and you'd be paying 150 ms per request for it, which is almost never worth it.

Handling client migration between regions (travel, DNS changes, regional failover): the reconciliation process carries per-client consumption, so a client moving from EU to US brings their consumption with them within one reconciliation interval. Between intervals they get a small extra allowance — bounded and acceptable.

Regional failure: if a region goes down, its traffic shifts to the others, whose allocations are now too small. The reconciliation loop should detect the missing region and redistribute its share promptly — otherwise a failover triggers spurious 429s at exactly the wrong moment, which is a subtle failure mode worth designing for explicitly.

The general principle: for a constraint that is inherently approximate, replace global coordination with local decisions plus periodic reconciliation. This is the same structure as local token batching in §6, applied at regional granularity — and the same reasoning as sharded counters and approximate leaderboard rank elsewhere in the track: accept bounded imprecision to remove a serialisation point.

🎯 Key Takeaways

  • State is tiny (~20 MB for 1M clients) — this is a throughput and latency problem, not a storage one, which rules out database-backed designs immediately.
  • Fixed window's boundary burst allows 2× the stated limit across a window edge, and no configuration prevents it.
  • Token bucket's burst is bounded and intentional — capacity caps the burst, refill rate caps the sustained rate, two independently tunable knobs.
  • Sliding window log memory scales with the limit, not just the client count — 80 GB at a 10,000/hour limit.
  • Check-then-decrement is a race across two round trips. A Lua script makes it atomic and halves the latency.
  • Always EXPIRE buckets, or state grows forever as clients churn.
  • Return Retry-After and RateLimit-* headers — including on success, so clients self-throttle instead of discovering the wall.
  • Fail open with a conservative local fallback. A limiter that causes the outage it exists to prevent is a failed design.
  • Local token batching removes the round trip from the hot path by amortising coordination 100:1 — the fix when latency budgets are tight.
  • Sharding by client key needs no cross-shard coordination, which is why this scales unusually cleanly.
  • For login abuse, key on the target (account), not the source (IP) — the attacker controls the source and cannot change the target.
  • Insisting on exact global accuracy forces a serialisation point exactly when throughput matters most. Accept ±2%.
