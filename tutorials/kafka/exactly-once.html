Idempotence & Transactions Delivery & Durability

What you'll master: the three gaps the idempotent producer leaves open, and how transactions close them; the transaction protocol — the coordinator, __transaction_state, and the commit markers written into every partition; the consume-transform-produce loop, and the missing seek() after an abort that silently skips records; zombie fencing with transactional.id and epochs; why downstream consumers see aborted data by default; the hanging transaction that freezes every read_committed reader of a partition, and how to find and abort it; and an honest account of what exactly-once costs and where it stops. Prerequisites: Offsets & Commit Strategies and the idempotence section of Producers.

Part 1 — What Idempotence Leaves Open

The idempotent producer (default since Kafka 3.0) stops the producer's own retries from writing duplicates: each batch carries a producer id, epoch and sequence number, and the broker discards a batch it has already written. That solves one problem precisely, and leaves three others.

GapExampleWhy idempotence cannot help
RestartsThe app crashes after sending, restarts, and resends records it is unsure aboutThe new producer has a new producer id; the broker cannot relate the two
Atomic writes to several partitionsAn order event to orders and a stock event to inventory must both appear or neitherIdempotence is per partition; one write can succeed while the other fails
Read-process-writeConsume from payments, write an enriched record to payments.enriched, commit the input offsetThe output write and the offset commit are two separate operations; a crash between them duplicates or loses
consume offset 500 ─► produce enriched record ─► commit offset 501
                                              ▲
                          crash HERE: the output exists, the commit does not
                          restart → reprocess 500 → the enriched record is written TWICE

transactions make "produce outputs" and "commit input offsets" ONE atomic step

Transactions extend the same producer id and epoch mechanism across restarts (by giving the producer a stable identity) and across partitions (by committing or aborting a group of writes, including offset commits, together).

Part 2 — The Transaction Protocol

A transactional producer is configured with a transactional.id, a name that stays the same across restarts of the same logical producer. A broker acting as the transaction coordinator — chosen, like the group coordinator, by hashing the id onto a partition of the internal __transaction_state topic — records each transaction's state.

producer                          transaction coordinator              data partitions
────────                          ───────────────────────              ───────────────
initTransactions()   ────────────► assign producer id, BUMP epoch
                                   (fences any older instance)
beginTransaction()   (local only)
send(orders-2, …)    ────────────► AddPartitionsToTxn(orders-2) ──►   records written, marked
send(inventory-5, …)                AddPartitionsToTxn(inventory-5)    "transactional", NOT yet visible
sendOffsetsToTransaction(…) ─────► adds the group's offsets as part of the transaction
commitTransaction()  ────────────► state = PrepareCommit (durable in __transaction_state)
                                   write COMMIT MARKERS ───────────►  a control record in orders-2,
                                                                      inventory-5, __consumer_offsets
                                   state = CompleteCommit

The markers are the mechanism. A transaction's records are written to their partitions as they are sent, and a commit or abort control record is appended to each partition at the end. A read_committed consumer delivers a transaction's records only once it sees the commit marker, and skips them if it sees an abort marker. Brokers keep an aborted-transaction index (.txnindex, next to each segment) so consumers can filter aborted records efficiently.

SettingDefaultMeaning
transactional.id (producer)noneStable identity; enables transactions and fencing
transaction.timeout.ms (producer)60 sThe coordinator aborts a transaction open longer than this
transaction.max.timeout.ms (broker)15 minUpper limit for the producer's timeout
transaction.state.log.replication.factor / min.isr3 / 2Durability of transaction state; single-broker dev setups lower these
transactional.id.expiration.ms (broker)7 daysAn unused id's state is removed after this
isolation.level (consumer)read_uncommittedWhether a consumer hides open and aborted transactions

Markers take offsets. Each commit or abort writes one control record per partition in the transaction, and those records are never delivered to your code, so transactional topics always have gaps in the offsets your consumers see — expected, and one reason offsets are not a record count.

Part 3 — The Consume-Transform-Produce Loop

The main use of transactions is a service that reads from Kafka, transforms, and writes back to Kafka. The input offsets are committed inside the transaction, so outputs and progress are atomic.

Properties pp = new Properties();
pp.put("transactional.id", "enricher-" + instanceId);      // stable per instance, see Part 4
pp.put("enable.idempotence", "true");                       // required, and implied
KafkaProducer<String, String> producer = new KafkaProducer<>(pp, ...);
producer.initTransactions();                               // fences older instances with this id

Properties cp = new Properties();
cp.put("group.id", "enricher");
cp.put("enable.auto.commit", "false");                      // offsets go through the producer
cp.put("isolation.level", "read_committed");                // do not read other apps' aborted data
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(cp, ...);
consumer.subscribe(List.of("payments"));

while (running) {
    ConsumerRecords<String, String> batch = consumer.poll(Duration.ofMillis(200));
    if (batch.isEmpty()) continue;
    producer.beginTransaction();
    try {
        for (var r : batch) producer.send(new ProducerRecord<>("payments.enriched", r.key(), enrich(r.value())));
        producer.sendOffsetsToTransaction(nextOffsets(batch), consumer.groupMetadata());
        producer.commitTransaction();
    } catch (ProducerFencedException | OutOfOrderSequenceException | AuthorizationException fatal) {
        producer.close();                                   // this instance is finished
        throw fatal;
    } catch (KafkaException abortable) {
        producer.abortTransaction();
        rewindToCommitted(consumer);                        // ◄── the step people forget
    }
}

❌ Aborting and carrying on with the next poll(). After abortTransaction() the outputs are discarded and the offsets were never committed — but the consumer's in-memory position has already moved past the batch. The next poll() returns the records after it, and the aborted batch is never processed. Nothing errors; the records are simply skipped.

✅ Seek back to the committed offsets after every abort. For each assigned partition, read consumer.committed(...) and seek() to it (or to the beginning, if nothing is committed), so the aborted batch is fetched and processed again. Exercise 3 reproduces the skip.

void rewindToCommitted(KafkaConsumer<?, ?> c) {
    Map<TopicPartition, OffsetAndMetadata> committed = c.committed(c.assignment());
    for (TopicPartition tp : c.assignment()) {
        OffsetAndMetadata om = committed.get(tp);
        if (om != null) c.seek(tp, om.offset());
        else c.seekToBeginning(List.of(tp));        // or apply your auto.offset.reset policy
    }
}

sendOffsetsToTransaction(offsets, consumer.groupMetadata()) passes the consumer group's generation along with the offsets (KIP-447, Kafka 2.5). The coordinator uses it to reject offset commits from a consumer that has lost its partitions in a rebalance. Before 2.5, safe fencing needed one transactional producer per input partition; with it, one producer per application instance is enough.

Part 4 — Zombie Fencing

A zombie is an instance that the rest of the system considers dead but that is still running — paused by garbage collection, cut off by a network partition — and that may wake up and write. Transactions fence zombies with epochs.

instance A: transactional.id = enricher-7, epoch 4      running normally
instance A pauses for 2 minutes (a long GC pause, a frozen VM)
orchestrator starts instance B with transactional.id = enricher-7
instance B: initTransactions() → coordinator BUMPS the epoch to 5, aborts A's open transaction
instance A wakes up, tries to send or commit with epoch 4
   → ProducerFencedException: A can never write under this id again
What is fencedByResult for the zombie
Its data writesProducer epoch per transactional.idProducerFencedException; must close
Its offset commitsConsumer group generation (KIP-447)Commit rejected; its transaction aborts
Its open transactionThe new instance's initTransactions()Aborted, so its partial output is never visible

Fencing only works if the id is stable and unique per logical instance. Two common mistakes break it in opposite directions:

Choice of transactional.idProblem
A random UUID per startA restarted instance never fences its previous self; a zombie can still commit
The same id for every instanceEach instance fences the others on start-up; only one can run
Stable per slot (e.g., the StatefulSet pod ordinal: enricher-0, enricher-1)Correct: a replacement for slot 1 fences the old slot 1 and nothing else
🔑 Fencing stops zombie writes to Kafka, not to anything else. If the zombie also writes to a database or calls an API, those effects go through: the epoch check happens only on Kafka brokers. A consume-transform-produce loop is protected end to end only when all of its outputs are Kafka topics. Anything else needs its own fencing — a version check in the database, or an idempotency key at the API.

Part 5 — Readers: read_committed, the LSO and Hanging Transactions

Transactions affect readers in two ways, and both surprise people.

1. The default consumer reads everything. isolation.level defaults to read_uncommitted, which delivers transactional records as soon as they are written — including records from transactions that later abort. A downstream team that consumes your transactional topic with default settings sees data your service threw away.

producer: begin → send A, B → ABORT          (A and B must never be seen)
          begin → send C     → COMMIT

read_uncommitted consumer (DEFAULT) receives:  A, B, C     ◄── aborted records delivered
read_committed consumer receives:              C

2. read_committed readers wait for the oldest open transaction. They read only up to the last stable offset (LSO): the offset of the first record belonging to a transaction that is still open. Everything after it — including committed records from other producers — waits.

partition payments.enriched-2
offsets:  100  101  102  103  104  105  106  107
          c    c    T1   c    c    T1   c    c         T1 = open transaction from producer X
                    ▲
                    LSO = 102: read_committed consumers stop here, although 103, 104, 106, 107
                    are committed records from other producers

So end-to-end latency for read_committed consumers includes the producer's transaction duration. A producer committing every 5 seconds adds up to 5 seconds of latency for every reader of those partitions. And a transaction that never finishes — a hanging transaction — stops readers of its partitions until it times out.

Kafka 4.0 strengthened the broker-side defences against hanging transactions (KIP-890), which rely on up-to-date clients; the tooling above remains the way to find and clear one when it happens.

Interview Questions

Beginner: What problem do Kafka transactions solve that the idempotent producer does not?

The idempotent producer prevents duplicates caused by the producer's own retries: each batch is numbered, and the broker ignores a batch it has already written. But it only works within one producer session and one partition at a time.

Transactions add three things. Atomic writes across partitions and topics: a group of records to several partitions either all become visible or none do. Atomic read-process-write: the input offsets are committed as part of the same transaction as the output records, so a crash can never leave outputs written without the offsets committed, or the reverse. Continuity across restarts: a stable transactional.id lets a restarted producer fence off its previous incarnation, so an old instance cannot keep writing.

The typical use is a service that consumes from one topic, transforms, and produces to another. With transactions and read_committed consumers downstream, each input record's output appears exactly once in the output topic, even across crashes and rebalances.

The limit is that all of this happens inside Kafka. As soon as a step writes to a database or calls an API, that step needs its own idempotency.

Beginner: What does isolation.level=read_committed do, and why is it not the default?

It makes a consumer deliver transactional records only after their transaction commits, and never deliver records from transactions that abort. Non-transactional records are delivered as usual.

It works using markers and the last stable offset. A transaction's records are written to the log as they are produced; a commit or abort marker follows at the end. A read_committed consumer reads only up to the first record of any still-open transaction, and uses the broker's aborted-transaction index to drop records from aborted ones.

It is not the default because it costs latency and most topics are not transactional. A read_committed consumer waits for open transactions, including other producers' — so its end-to-end latency includes their commit intervals, and a stuck transaction stalls it. For non-transactional topics it makes no difference.

The practical consequence is that the producer's team has to tell every consumer of a transactional topic to set it. Otherwise downstream services quietly read records that the producer aborted, and the transactions protect nothing for them.

Mid: Walk through the consume-transform-produce loop and the failure cases it must handle.

The producer has a stable transactional.id and calls initTransactions() once, which registers it and fences any previous instance with the same id. The consumer has auto-commit off and isolation.level=read_committed. For each batch: beginTransaction(); send the output records; sendOffsetsToTransaction() with the next offsets and the consumer's group metadata; commitTransaction().

Fatal errors — ProducerFencedException, an out-of-order sequence, or an authorization failure — mean this producer can never continue. Another instance has taken over its id, or something is misconfigured. The producer must be closed; retrying is pointless.

Abortable errors — a timeout, a record too large, a transient broker problem — mean this transaction failed but the producer can continue. Call abortTransaction(), which discards the batch's outputs, and then — the step most often missed — seek the consumer back to the committed offsets. Its position has already advanced past the batch, so without the seek the batch is skipped. Then process it again in a new transaction.

Rebalances are covered by passing the consumer's group metadata with the offsets: if the consumer has lost its partitions, the coordinator rejects the offset commit and the transaction aborts, so a zombie cannot commit progress on partitions it no longer owns.

Finally, commit per batch or per time interval, not per record, and make sure every downstream consumer reads with read_committed. In practice I would reach for Kafka Streams with exactly_once_v2, which implements exactly this loop and its error handling.

Mid: How should you choose transactional.id values?

The id is what the coordinator uses to recognise "the same producer, restarted". Choosing it means deciding what counts as the same logical producer.

It must be stable across restarts of one instance, so that a replacement fences its predecessor. A random UUID per start fails this: the old instance, if it is a zombie, keeps its own id and epoch and nothing stops it. It must also be unique between instances that run at the same time. If every replica uses the same id, each new one fences the others, and the service can only run one instance.

The usual answer is one id per instance slot: the service name plus a stable ordinal, such as the pod ordinal in a Kubernetes StatefulSet (enricher-0, enricher-1). When pod 1 is replaced, the new pod 1 fences the old one, and pods 0 and 2 are unaffected.

Since Kafka 2.5, input-partition zombies are also fenced through the consumer group generation passed in sendOffsetsToTransaction, so ids no longer need to be tied to input partitions — one per instance is enough. Older designs used one id per input partition, which is where much of the confusing advice online comes from.

Senior: Downstream read_committed consumers of a topic stopped progressing, while read_uncommitted consumers of the same topic are fine. Diagnose it.

That contrast is diagnostic in itself: the data is being written, but it is not becoming stable. read_committed consumers read only up to the last stable offset — the first record of the oldest still-open transaction on each partition — so an open transaction that does not finish holds back everything after it.

Step 1: find the partitions and the open transaction. Lag per partition shows which partitions are stuck. kafka-transactions.sh describe-producers on one of them lists producer ids with a CurrentTransactionStartOffset; the one matching the stuck position is the culprit.

Step 2: is it merely slow or truly hanging? If the producer is alive and commits eventually — for example, it commits every 30 seconds, or holds transactions open while calling a slow service — this is a design problem: shorten the transactions. If the producer crashed, the coordinator should abort the transaction after transaction.timeout.ms; a stall ending after about that long is this case, and a very large configured timeout makes it long.

Step 3: a transaction the coordinator does not know about. Rarely — historically through client or broker bugs — a partition can hold an open transaction that the coordinator has no record of, so no timeout ever aborts it. kafka-transactions.sh find-hanging identifies these, and abort writes the abort marker directly for that partition, which releases the LSO.

Recommendation: abort the hanging transaction to unblock readers, then fix the cause — keep transaction.timeout.ms near its default, keep clients and brokers current (Kafka 4.0 added stronger protection against hanging transactions), and add monitoring that compares read_committed progress with the partition's high watermark, so a stuck LSO alerts within minutes rather than when a downstream team notices.

Senior: A team wants "exactly-once" for a pipeline: Postgres → Kafka → enrichment service → Kafka → data warehouse. Design it.

I would design each boundary separately, because Kafka transactions cover only one of the four hops, and the pipeline is only as strong as its weakest one.

Postgres → Kafka: transactional outbox. The application writes each business change and an outbox row in the same database transaction; Debezium captures the outbox table and publishes it. This is at-least-once — CDC can republish after a restart — so every event carries a stable id (the outbox row id) that later stages can deduplicate on.

Kafka → enrichment → Kafka: exactly-once with transactions, preferably Kafka Streams with exactly_once_v2. Duplicates arriving from the outbox are handled here if needed, by keying on the event id and keeping a deduplication store (a Streams state store with a retention window). The output topic is consumed with read_committed.

Kafka → warehouse: this sink is outside Kafka, so it needs its own mechanism. For a warehouse, idempotent loading is usual: write batches into a staging table and MERGE on the event id, so reprocessing a batch after a rebalance changes nothing. If the warehouse supports transactions, storing the consumer offsets in the same transaction as each load is the alternative.

Costs to state: end-to-end latency includes the enrichment commit interval (100 ms by default in Streams); deduplication state has to be sized for the window in which duplicates can arrive; and every consumer of the enriched topic must use read_committed.

Recommendation: outbox with stable event ids at the source, Kafka Streams EOS in the middle, idempotent MERGE at the warehouse — and describe it to stakeholders as "each event's effect is applied exactly once", defined by the event id, rather than as a property of Kafka alone. Then test it by killing each component mid-flow and reconciling counts against the source.

6 (hard): Decide, for each stage of a fraud-scoring pipeline, which delivery guarantee it gets and how.
Solution 
payments (Kafka)  ─►  scorer  ─►  scores (Kafka)  ─►  alerting  ─►  PagerDuty / email
                          │
                          └──►  feature store (Redis) update per payment
StageGuaranteeMechanism
payments → scoresExactly-onceTransactional loop (or Streams exactly_once_v2); read_committed readers of scores
Feature store update inside the scorerAt-least-onceTransactions do not cover Redis: make the update idempotent (SET a value computed from the event, not INCR), keyed by payment id
scores → alertingAt-least-onceCommit after sending; each alert carries the payment id
Alert → PagerDutyEffectively oncePagerDuty's deduplication key set to the payment id, so a resend updates the same incident

Two points decide the design. First, the Redis update is a side effect inside the transactional service, and it will run again whenever a transaction aborts and the batch is reprocessed — which is exactly the normal recovery path. An increment there would drift upward over time; a value derived from the event does not. Second, the alerting stage talks to external systems, so the end-to-end "once" comes from a deduplication key at the receiver, not from Kafka.

The summary for stakeholders: "each payment is scored exactly once into the scores topic; alerts may be sent more than once but are deduplicated by payment id at PagerDuty; feature updates are idempotent". That sentence is accurate, and "the pipeline is exactly-once" is not.

🎯 Key Takeaways

  • Idempotence stops retry duplicates within one producer session; transactions cover restarts, multiple partitions and read-process-write.
  • A transaction's records are written immediately and made visible by commit markers appended to every partition involved.
  • Markers use offsets, so transactional topics always show gaps in consumer offsets.
  • sendOffsetsToTransaction commits input offsets atomically with the outputs, and with group metadata (KIP-447) fences rebalanced-away consumers.
  • After abortTransaction(), seek back to the committed offsets, or the aborted batch is silently skipped.
  • Fatal errors such as ProducerFencedException end the producer; abortable errors mean abort, rewind and retry.
  • initTransactions() bumps the epoch and fences older instances with the same transactional.id.
  • Use a stable id per instance slot: random ids never fence, a shared id fences every other instance.
  • Fencing protects Kafka writes only; zombie writes to databases and APIs need their own guard.
  • Consumers default to read_uncommitted and see aborted records; every reader of a transactional topic must opt in.
  • read_committed readers stop at the last stable offset, so reader latency includes the producer's commit interval.
  • A hanging transaction stalls read_committed readers of its partition; find it with kafka-transactions.sh and abort it.
  • Keep transactions short and transaction.timeout.ms near its 60 s default.
  • Commit per batch or interval, never per record, to keep coordinator overhead small.
  • Kafka Streams with exactly_once_v2 implements the whole loop and is usually the better choice than hand-written code.
  • Exactly-once ends at Kafka's edge; state the guarantee per boundary and use idempotent writes or sink-side offsets beyond it.
