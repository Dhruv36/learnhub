Serialization & Schema Evolution Data Design

What you'll master: why Kafka's indifference to your bytes makes the schema your real contract; JSON, Avro, Protobuf and JSON Schema compared on the properties that matter in a log; how a schema registry works, down to the five bytes it prepends to every record; the compatibility modes and the deployment order each one forces; exactly which changes are safe in Avro and Protobuf; why a topic's retention window demands transitive compatibility; the producer that writes plain JSON into an Avro topic and blocks a partition; and how to ship a genuinely breaking change without stopping every consumer. Prerequisites: Rebalancing & Group Membership; the Spring Boot Messaging lesson introduces events as contracts.

Part 1 — Kafka Stores Bytes; the Contract Lives Elsewhere

A Kafka record's key and value are byte arrays. The broker never parses them, validates them or checks that one record looks like the next. Everything that gives those bytes meaning — field names, types, which fields are required — lives in the producer's serializer and the consumer's deserializer.

producer: Order object ──serializer──► bytes ──► broker (stores bytes, no idea what they mean)
consumer: bytes ──deserializer──► Order object          ◄── if this fails, the record is a POISON PILL

Consequences:
  • nothing stops a producer from writing a different shape tomorrow
  • a record that cannot be deserialized fails in the consumer's poll loop, not at the producer
  • the log keeps OLD shapes for the whole retention period — consumers must read all of them

That last point is what makes Kafka different from an API. An HTTP endpoint only has to accept today's requests. A consumer that starts from the beginning of a topic, or replays last week, must read every version of the data still in the log — records written by producers that were retired months ago on a compacted topic. The schema is a contract with the past as well as the present.

🔑 A record that cannot be deserialized blocks its partition. The consumer throws inside poll(), before your code ever sees the record, so a naive loop retries the same record forever while everything behind it waits. Handle deserialization failures explicitly — catch the exception, skip or dead-letter the record by seeking past it (Spring's ErrorHandlingDeserializer does this) — and, better, prevent bad records reaching the topic in the first place with a registry and producer controls.

Avro   0c 6f 2d 31 30 34 32  9e 1f  06 45 55 52                          13 bytes: values only, in schema order
       ◄──── "o-1042" ────►  1999   ◄─ "EUR" ─►                          (unreadable without the WRITER's schema)
Proto  0a 06 6f 2d 31 30 34 32  10 cf 0f  1a 03 45 55 52                  16 bytes: tag + value per field

Avro's reader needs the writer's schema. Because an Avro record is just values in the order the writer's schema declared them, a reader cannot decode it without knowing exactly which schema wrote it. Avro then resolves the writer's schema against the reader's own: fields the reader does not know are skipped, fields the writer did not have are filled from the reader's defaults. That resolution is what makes evolution work — and why every record must identify its writer schema, which is the registry's job.

The size difference matters at Kafka volumes: at 100,000 records per second, 40 bytes of repeated field names is 4 MB/s — about 10 TB a month before replication — though compression recovers part of it, since repeated names compress well within a batch.

Part 3 — How a Schema Registry Works

A schema registry (Confluent Schema Registry, Apicurio, AWS Glue Schema Registry and others) stores versioned schemas and checks new versions against compatibility rules. The serializers integrate with it: the producer's serializer looks up (or registers) the schema and writes its id into every record; the consumer's deserializer uses the id to fetch the writer's schema.

Confluent wire format (used by Confluent and compatible registries)

byte 0       magic byte   0x00
bytes 1-4    schema id    big-endian int32, e.g. 00 00 00 2a = schema 42
bytes 5..    payload      Avro binary (Protobuf adds message-index varints first)

producer: schema not yet cached → POST it to the registry → id 42 → cache it → write 00 00000002a + payload
consumer: sees id 42 → GET /schemas/ids/42 once → cache it → decode with writer schema 42 + reader schema
ConceptMeaningDefault / note
SubjectThe name a sequence of schema versions is registered underTopicNameStrategy: <topic>-value and <topic>-key
RecordNameStrategySubject = the record's fully qualified nameSeveral event types per topic, each evolving separately
TopicRecordNameStrategySubject = topic + record nameSeveral types per topic, scoped to that topic
Compatibility levelRule a new version must satisfyConfluent's default is BACKWARD
auto.register.schemasSerializer registers unknown schemas itselftrue by default — usually wrong in production

Turn off auto-registration in production. With the default, any producer build carrying a changed class registers a new schema version the first time it runs. The compatibility check still applies, but the change was never reviewed, and a change that passes the check can still be wrong for consumers (a field that became meaningless, a unit that changed). Register schemas from CI after review, and set auto.register.schemas=false — with use.latest.version=true where producers should write the latest registered version.

The registry is on the critical path, but only briefly. Clients cache schemas by id, so a registry outage does not affect records whose schemas are already cached. It does block a producer starting up with an uncached schema and a consumer meeting a schema id it has not seen — so run the registry replicated, and include it in capacity and failure testing.

Part 4 — Compatibility Modes and the Order of Deployment

Each compatibility mode answers one question: which side can be upgraded first without breaking the other?

ModeGuaranteeUpgrade firstAllowed (Avro)
BACKWARD (default)New schema can read data written with the previous oneConsumersDelete fields; add fields with defaults
FORWARDPrevious schema can read data written with the new oneProducersAdd fields; delete fields that had defaults
FULLBoth directionsEitherAdd or delete fields that have defaults
*_TRANSITIVEThe same, checked against all previous versionsAs aboveAs above, across the whole history
NONENo checksCoordinate by handAnything, including breaking changes
BACKWARD: v2 deletes field "coupon" (no default)
  deploy consumers with v2 first → they read old v1 records (coupon ignored)  ✔
  then producers write v2        → consumers on v2 read them                 ✔
  WRONG ORDER: producers first   → consumers still on v1 read v2 records with no "coupon"
                                   and v1 has no default for it → DESERIALIZATION FAILS  ✘

❌ Assuming "the registry accepted it" means "any deployment order is safe". Under BACKWARD, the registry guarantees only that new consumers can read old data. A team that ships the producer first — the natural order, because the producer "owns" the topic — breaks every consumer still on the old schema, with a change the registry approved.

✅ Derive the deployment order from the mode, and write it down. BACKWARD: consumers first. FORWARD: producers first. If you cannot control consumer deployments — many teams, external consumers — use FULL_TRANSITIVE and restrict changes to adding or removing fields with defaults, so the order stops mattering.

Why transitive matters in Kafka. Non-transitive modes compare a new version only with the latest one. But a consumer may read any version still in the log. Three pairwise-compatible steps can add up to an incompatible whole:

v1: { id }
v2: { id, region = "eu" }       add a field WITH a default     → BACKWARD-compatible with v1 ✔
v3: { id, region }              remove the default from region  → BACKWARD-compatible with v2 ✔
                                                                 (v2 data always has region)
a v3 consumer replays last week's v1 records: no region, and v3 has no default → FAILS ✘

BACKWARD            accepts v3 (checks v3 against v2 only)
BACKWARD_TRANSITIVE rejects v3 (checks v3 against v1 and v2)

For topics with long retention, compaction or replay requirements, choose a transitive mode. The cost is small — some changes that look harmless get rejected — and the protection covers exactly the case Kafka makes common.

Remove a field without a default✔✘Old readers cannot decode new data

Widen a type (int → long, float → double)✔✘Readers may promote the writer's type, not narrow it

Make a field nullable (union with null)✔✘Old readers cannot decode a null

Protobuf's contract is the field number. Names can change freely; numbers cannot.

message Order {
  string order_id = 1;
  int64  amount   = 2;
  reserved 3;                    // was "coupon": its NUMBER can never be reused
  reserved "coupon";
  string currency = 4;
  optional string region = 5;    // proto3 "optional": readers can tell "unset" from ""
}

safe:    add a field with a new number; rename; remove a field and RESERVE its number
unsafe:  reuse a number (old data is decoded as the wrong field); change a field's type incompatibly;
         proto2 "required" fields (can never be removed safely)

Proto3 defaults hide absence. Without optional, a proto3 scalar field that is not set reads as its zero value — 0, "", false. A consumer cannot tell "the amount is zero" from "this producer is too old to send an amount". For fields where absence means something, declare them optional (proto3.15+) or use wrapper types.

JSON Schema compatibility is less intuitive. Whether adding a property is compatible depends on whether the schema is open (allows unknown properties) or closed (additionalProperties: false). Under a closed model, adding an optional property is not backward compatible in the way it is in Avro. Teams using JSON Schema should test their intended changes against the registry's checker rather than reasoning from Avro rules.

Part 6 — Shipping Changes Safely, Including Breaking Ones

Schema changes should go through the same pipeline as code: reviewed, checked automatically, and deployed in a known order.

pull request changes order.avsc
  CI: POST /compatibility/subjects/orders-value/versions/latest   {"schema": "..."}
      → {"is_compatible": false, "messages": ["READER_FIELD_MISSING_DEFAULT_VALUE ... region"]}
      → build fails; the reviewer sees exactly which rule was broken
  merge → CI registers the new version → deploy in the order the compatibility mode requires

A genuinely breaking change — a rename without aliases, a type change, restructuring an event — cannot pass a compatibility check, and should not be forced through with NONE. Two patterns handle it:

PatternHowCost
Expand and contract within one schemaAdd the new field (with a default) alongside the old; producers fill both; consumers move to the new field; finally remove the old oneSeveral releases; both fields meanwhile
New topic versionCreate orders.v2; producers write both topics during migration; consumers switch one by one; retire ordersDouble writes; every consumer migrates; replay spans two topics
expand and contract: renaming customerId → accountId

release 1  schema: customerId, accountId (default null)   producer writes BOTH
release 2  consumers read accountId, fall back to customerId if null
release 3  (after retention has aged out records without accountId) make accountId required,
           remove customerId — both steps checked by the registry

❌ Setting a subject's compatibility to NONE "just for this release". The breaking schema is registered, the producer deploys, and every consumer still on the old schema fails — along with any consumer that later replays records written before the change. The setting is often left at NONE afterwards, removing the protection for every later change.

✅ Treat a breaking change as a migration, not a registration. Expand and contract where possible; a new topic version where not. Both keep every record in the log readable by the consumers expected to read it, and the compatibility level never has to be lowered.

Interview Questions

Beginner: Why do Kafka teams use a schema registry?

Because Kafka itself treats every record as bytes. It does not know or check what the bytes contain, so nothing in Kafka prevents a producer from changing the shape of its data and breaking every consumer. A schema registry adds the missing contract.

It does three things. It stores versioned schemas for each subject (usually one per topic key and value). It checks new versions against compatibility rules before accepting them, so a change that would break readers is rejected at registration rather than discovered in production. And it lets records be compact: instead of carrying field names, each record carries a small schema id, and consumers fetch and cache the schema it refers to.

For Avro in particular the registry is close to essential, because Avro binary data cannot be decoded without the exact schema that wrote it; the schema id in each record is how a consumer finds that schema.

What it does not do is decide deployment order or catch semantic changes — a field whose meaning changed but whose type did not passes every check. Those still need review.

Beginner: What is the difference between backward and forward compatibility?

Backward compatible means the new schema can read data written with the old schema. That lets you upgrade consumers first: new consumers can still read everything already in the topic and everything old producers keep writing. Deleting a field, or adding one that has a default, is backward compatible.

Forward compatible means the old schema can read data written with the new schema. That lets you upgrade producers first: consumers still on the old schema can read what new producers write. Adding a field is forward compatible, because old readers ignore it; so is deleting a field that had a default.

Full compatibility means both, and allows only adding or removing fields that have defaults — changes that are safe in any deployment order.

In Kafka there is also the transitive dimension: whether the check covers only the previous version or all of them. Because consumers can replay old records from the log, the transitive variants are usually the right choice for topics with long retention.

Mid: A schema change passed the registry's check, yet consumers started failing after the release. How?

Several explanations are consistent with that, and I would check them in this order.

Deployment order. The most common: the subject uses BACKWARD compatibility, which only guarantees that new readers can read old data. The producer was deployed first, and consumers still on the old schema cannot read the new records — for example, a field they require without a default was removed. The registry did its job; the rollout order was wrong for the mode.

Non-transitive checking. The new version is compatible with the previous version but not with older ones still in the log. A consumer that replays or starts from the beginning reaches records written with an old version and fails.

A subject mismatch. With a naming strategy different from what consumers expect, the check may have run against a different subject than the one consumers read — or auto-registration created a new subject with no history, so there was nothing to be incompatible with.

Semantics. The schema is compatible but the meaning changed — amounts moved from euros to cents, a timestamp from seconds to milliseconds — and consumers computed wrong results or failed validation. No compatibility checker catches that.

The fixes are process: document the deployment order per mode, use a transitive mode for replayable topics, register from CI with auto-registration off, and review semantic changes as breaking changes that need a migration.

Mid: Compare Avro and Protobuf for Kafka events.

Both are compact binary formats with defined evolution rules, so either is a reasonable choice; the differences are in how they identify fields and how the ecosystem supports them.

Avro writes only values, in schema order. A reader must have the writer's schema, and Avro resolves it against the reader's schema: unknown fields are skipped, missing fields take the reader's defaults. Defaults are therefore central to evolution. Avro has the deepest Kafka ecosystem support — Kafka Connect, CDC tools like Debezium and Kafka Streams serdes all default to or strongly support it — and it works well with dynamic, schema-driven tooling.

Protobuf writes a tag (field number) with each value. Readers can skip unknown fields without the writer's schema, and names can change freely because the number is the contract. Its risks are reusing a field number and proto3's zero-value defaults, which hide whether a field was set. It is the natural choice where services already use gRPC and Protobuf definitions are the organisation's shared language.

I would choose Avro for data-platform-centred pipelines — CDC, Connect, analytics — and Protobuf where the same messages flow through gRPC services. In either case the registry and compatibility discipline matter more than the format.

Senior: You own a topic read by twelve teams. How do you run schema evolution for it?

With twelve consumer teams I cannot coordinate deployments, so the design has to make deployment order irrelevant and make breaking changes rare and deliberate.

Compatibility: FULL_TRANSITIVE. Every change must be readable by old and new consumers and against every version still in the log, which restricts routine changes to adding and removing fields with defaults. That is limiting, and that is the point: any team can deploy in any order, and replays always work.

Process: the schema lives in a repository with the producer, changes arrive as pull requests, CI runs the registry's compatibility check and a set of consumer contract tests (sample records for each version, decoded with each consumer team's current schema), and CI — not the producer at runtime — registers the new version. Auto-registration is off. Field documentation is part of the schema, including units and semantics.

Breaking changes go through expand and contract, with announced timelines: add the new field, produce both, give consumers a deadline to migrate, and only remove the old field after the retention period has aged out records without the new one. For restructurings that cannot be expressed that way, a new topic version with a dual-write period.

Operations: a replicated registry, consumers that dead-letter undecodable records rather than block, and ACLs so only the owning service can produce to the topic.

Recommendation: FULL_TRANSITIVE, schema changes reviewed and registered by CI, contract tests against consumers' schemas, and a written deprecation policy for breaking changes. The registry enforces the syntax; the process has to protect the semantics.

Senior: Consumers of an Avro topic suddenly fail with "Unknown magic byte!". Diagnose and prevent it.

The message means a record does not start with the registry wire format's magic byte (0), so the deserializer cannot even find a schema id. The record was not written by the registry-aware serializer.

Diagnose: find the failing partition and offset from the consumer error, and read the raw bytes of that record with a plain consumer. Usually the first byte is { (0x7b): someone produced JSON — a test script, a console producer used for a quick fix, a new service configured with a string serializer, or a Connect connector with the wrong converter. Headers or the client id in broker logs can identify the producer.

Recover: the consumers are stuck on that record, because deserialization fails before application code can decide anything. Skip it: move the group past it with kafka-consumer-groups.sh --reset-offsets --to-offset for that partition (after checking there are no other bad records), or deploy an error-handling deserializer that routes it to a dead-letter topic. If the bad records carried real data, re-produce them correctly.

Prevent: restrict who can write with ACLs — only the owning service's principal should have write access to the topic. Configure every consumer to dead-letter undecodable records instead of blocking. Some platforms offer broker-side schema validation, which rejects records whose schema id is missing or unknown at produce time; where available, it moves the failure from the consumers to the offending producer, which is where it belongs.

Recommendation: ACLs so only the owner produces, error-handling deserializers with a dead-letter topic on every consumer, and broker-side validation if your platform supports it. The incident is small; the systemic weakness is that anyone could write anything to a topic that twelve teams depend on.

6 (hard): Plan the rename of customerId to accountId on a FULL_TRANSITIVE topic with 30-day retention.
Solution

A rename is incompatible in both directions, so it becomes a sequence of compatible releases:

release 1 (schema v5): add accountId: ["null","string"] default null     FULL-compatible ✔
          producer writes customerId AND accountId (same value)
release 2: consumers read accountId, falling back to customerId when accountId is null
           (null only for records written before release 1)
wait:      30 days of retention, so no record without accountId remains in the log
           (on a COMPACTED topic, "waiting" is not enough: every key must have been rewritten —
            republish the latest value for each key, or keep the fallback forever)
release 3 (schema v6): customerId given a default, if it lacked one      FULL-compatible ✔
release 4 (schema v7): remove customerId                                  FULL-compatible ✔
          consumers remove the fallback
ReleaseRegistry checkWho must have deployed first
1: add accountIdPassesNo one (FULL)
2: consumers switchNo schema changeRelease 1 producer
3–4: retire customerIdPassesAll consumers off customerId; retention elapsed

Two details make it work. The new field is nullable with a default, so every intermediate schema is compatible with every older one. And the removal waits for the log, not just for the consumers: a consumer replaying 30-day-old records still needs customerId until those records have expired. Publish the timeline to consumer teams at release 1, because releases 3 and 4 depend on all of them.

🎯 Key Takeaways

  • Kafka stores bytes and never checks them; the schema is the real contract between producers and consumers.
  • The log holds every version written during retention, so consumers must read the past as well as the present.
  • An undecodable record fails inside poll() and blocks its partition unless you dead-letter it and seek past it.
  • Avro binary carries no field names; a reader needs the writer's schema, which the record's schema id identifies.
  • The registry wire format is a zero byte, a 4-byte schema id, then the payload.
  • Clients cache schemas by id, so a registry outage mainly affects new producers and unseen schema ids.
  • Turn off auto.register.schemas in production and register reviewed schemas from CI.
  • BACKWARD means new readers can read old data: deploy consumers first.
  • FORWARD means old readers can read new data: deploy producers first.
  • FULL allows only adding or removing fields with defaults, which makes deployment order irrelevant.
  • Use transitive modes on replayable topics; pairwise compatibility can add up to an incompatible history.
  • In Avro, every new field needs a default; renames need aliases or a migration.
  • In Protobuf, the field number is the contract: never reuse one, reserve removed numbers.
  • Proto3 zero values hide absence; use optional where "unset" means something.
  • Ship breaking changes as expand-and-contract or a new topic version, never by lowering compatibility to NONE.
  • Only the owning service should be able to produce to a shared topic; ACLs prevent the "Unknown magic byte!" incident.
