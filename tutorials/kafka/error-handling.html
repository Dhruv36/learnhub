Errors, Retries & Dead Letter Topics Processing & Integration

What you'll master: the classification that decides every other choice — bad data or bad dependency — and why treating one as the other causes the worst outages; head-of-line blocking, and the arithmetic of what one poison record costs; in-place retries and the sleep that exceeds max.poll.interval.ms and triggers a rebalance; retry topics, the delay mechanics behind them, and the ordering they trade away; what a dead-letter record must carry to be replayable, and why the payload should be raw bytes; the downstream outage that fills the DLQ with perfectly good records, and pausing instead; and the replay path that makes a DLQ worth having. Prerequisites: Kafka Connect & CDC; the Spring Boot Messaging lesson shows one framework's implementation.

Part 1 — Classify the Failure First

Every error-handling decision follows from one question: will retrying this record ever succeed? If the record is malformed, no number of retries helps, and retrying blocks everything behind it. If a database is down, the record is fine and dead-lettering it throws away valid work.

FailureClassRetry helps?Correct response
Deserialization failure, schema mismatchBad dataNeverDead-letter immediately; alert
Validation failure (missing field, impossible value)Bad dataNeverDead-letter; often a producer bug
Business rejection (unknown account)AmbiguousSometimes — the account may arrive laterBounded retry, then dead-letter
Database timeout, connection refusedBad dependencyYesRetry with backoff; pause if it persists
HTTP 429 / rate limitedBad dependencyYes, after waitingBackoff and pause; never dead-letter
HTTP 500 from a downstream serviceBad dependencyUsuallyRetry; circuit-break if widespread
Out of memory, disk full in the consumerBad consumerNoFail the instance; let it restart
🔑 The two classes need opposite responses, and the failure is symmetrical. Dead-lettering a bad dependency means valid records pile into the DLQ while the real problem is a database restart. Retrying bad data forever means one record blocks its partition indefinitely. A consumer that treats every exception the same way will do one of these, and usually finds out during an incident.

Deserialization failures are special because they happen inside poll(), before your code sees the record. A naive loop cannot even catch them usefully: the consumer throws, the loop restarts, and the same record fails again. Modern clients raise RecordDeserializationException carrying the partition and offset precisely so the loop can log the record, publish its raw bytes to a DLQ and seek past it.

Part 2 — Head-of-Line Blocking, Quantified

topic "payments", 12 partitions, 6,000 records/s, one consumer per partition

one poison record on partition 7, retried forever:
  partition 7 stops:      500 records/s never processed
  capacity lost:          1/12 = 8.3%    — and lag on partition 7 grows at 500/s
  after 1 hour:           1.8 M records behind on that partition alone
  other partitions:       perfectly healthy, which is why dashboards look fine

the group's TOTAL lag looks like a modest rise; the per-partition view shows a cliff

This is the argument for per-partition lag alerting from the consumers lesson: a stuck partition is invisible in aggregate metrics until it is very large. It is also the argument for bounding every retry: "retry until it works" is indistinguishable from "stop processing this partition" when the record can never succeed.

Part 3 — Retrying Without Breaking the Poll Loop

The obvious implementation of "retry with backoff" is a sleep inside the processing loop. It works in testing and fails in production, because the consumer must call poll() within max.poll.interval.ms or it is removed from the group.

for (var record : records) {
    for (int attempt = 1; attempt <= 5; attempt++) {
        try { handle(record); break; }
        catch (TransientException e) { Thread.sleep(attempt * 10_000L); }   // 10+20+30+40 = 100 s
    }
}
// 500 records × up to 100 s ... the next poll() is far beyond max.poll.interval.ms (5 min)
// → the consumer is kicked out, its partitions move, the batch is reprocessed elsewhere,
//   and the commit fails with CommitFailedException

The correct in-place pattern is pause, poll, resume. Pausing stops fetching for those partitions while the loop keeps calling poll() — which returns nothing but keeps the consumer in the group and its liveness intact.

if (needsBackoff) {
    consumer.pause(consumer.assignment());
    retryAt = System.currentTimeMillis() + backoffMs;
}
while (running) {
    var records = consumer.poll(Duration.ofMillis(200));     // still polling: the group stays healthy
    if (consumer.paused().size() > 0 && System.currentTimeMillis() >= retryAt) {
        consumer.resume(consumer.paused());
        consumer.seek(tp, failedOffset);                     // reprocess from the failed record
    }
    ...
}
Backoff approachKeeps the consumer alive?Use for
Thread.sleep in the loopOnly if total time stays well inside the poll intervalVery short retries (milliseconds)
Pause + poll + resumeYes, indefinitelyWaiting out a dependency; ordering preserved
Retry topicsYes: the record leaves the main flowPer-record retries where ordering can be given up

Retry topics move the failed record to another topic and let the main flow continue. A tiered arrangement gives increasing delays:

payments ──fail──► payments.retry.5s ──fail──► payments.retry.1m ──fail──► payments.retry.10m ──► payments.DLT

each retry topic has its own consumer, which works out the delay itself:
  read a record → if (now − record.timestamp) < delay → PAUSE the partition and seek back,
                  sleep-by-polling until due, then resume and process
(Kafka has no delayed delivery; every "delay topic" implementation is this pattern underneath)

❌ Adding retry topics to an order-lifecycle consumer. OrderPaid fails once and goes to the 5-second retry topic; OrderShipped, right behind it in the same partition, succeeds immediately. The two events are now processed in the wrong order, and the order's state machine ends up in "shipped" then "paid" — a bug that appears only under transient failures and is nearly impossible to reproduce.

✅ Retry topics are for independent records. When per-key ordering matters, retry in place with pause and backoff, so the partition waits with the record rather than overtaking it. If throughput cannot tolerate that wait, the fix is to make the failure less likely — timeouts, capacity, idempotent downstream calls — not to reorder the business events.

Part 4 — What a Dead-Letter Record Must Carry

A dead-letter topic is only useful if its records can be understood and replayed. That requires the original bytes and the circumstances, and it requires the DLQ write itself never to fail.

DLT record
  key    = the ORIGINAL key bytes          (so a replay keeps the same partition and ordering)
  value  = the ORIGINAL value bytes        ◄── raw, NOT re-serialized: the record may be undeserializable
  headers:
    dlt.original.topic      payments
    dlt.original.partition  7
    dlt.original.offset     918273
    dlt.original.timestamp  1789200000042
    dlt.exception.class     com.acme.ValidationException
    dlt.exception.message   currency "EURO" is not an ISO 4217 code
    dlt.exception.stack     (truncated)
    dlt.attempts            4
    dlt.consumer.group      billing
    dlt.failed.at           2026-09-17T09:14:22Z
ChoiceWhy
Raw bytes as the valueThe record may have failed because it cannot be deserialized; re-serializing it would fail too
Original key preservedA replay lands in the same partition, so per-key ordering survives the round trip
Metadata in headersThe payload stays byte-identical to the original
Original topic, partition and offsetThe record can be found and re-read from the source if the DLQ ages out

A DLQ nobody reads is data loss with extra steps. The pattern that works is: alert on the DLT's record rate (any sustained non-zero rate is an incident), give every DLT an owner, and build the replay path before you need it — a small tool that reads the DLT, filters by exception class or time range, and re-produces the original bytes to the original topic once the bug is fixed.

Part 5 — Downstream Outages: Pause, Don't Dead-Letter

The worst DLQ failure mode is systemic. When a downstream dependency fails, every record fails, and a consumer that dead-letters after N retries will move the entire stream into the DLQ at full speed.

payments consumer, 6,000 records/s, 3 retries then DLT
database fails over (takes 4 minutes)

with per-record dead-lettering:
  4 min × 6,000/s = 1.44 M VALID records in the DLT
  replaying them = a second incident: ordering lost, duplicates, and a manual operation

with circuit breaking:
  error ratio over a 30 s window > 50% → pause ALL assigned partitions
  keep polling (stay in the group), probe the dependency every 10 s
  database returns → resume; the 1.44 M records are simply processed, in order, a few minutes late
  DLT records: ZERO
SignalInterpretationAction
A few failures, scattered keysBad dataBounded retry, then dead-letter
Nearly every record failingBad dependencyPause and probe; do not dead-letter
Failures on one partition onlyA poison record, or a hot keyDead-letter that record; check the key
Failures rising with loadCapacity or rate limitsBackoff and pause; reduce concurrency

Retries multiply load on a struggling dependency. Three retries per record against a database that is failing turns 6,000 requests per second into 24,000 — the retry storm from the Spring Boot microservices lesson. Pausing removes the load entirely, which is usually what a recovering dependency needs most.

Side effects make retries non-neutral. At-least-once delivery means every retry repeats whatever the handler already did before failing — a charge, an email, a partial database write. Split the handler so the effects are idempotent (keyed upserts, idempotency keys on API calls) or ordered so the retryable part comes first, as the offsets lesson describes for transactional sinks.

Rehearse the failure. Produce a deliberately malformed record into a staging topic and watch what happens: does the consumer dead-letter it and continue, or does the partition stall? Does the DLT record contain enough to explain itself? Does an alert fire? Teams that have run this drill respond to the real thing in minutes; teams that have not discover during an incident that the DLT is missing headers and nobody owns it.

Keep the policy in one place. Error handling scattered across handlers drifts: one swallows exceptions, another retries forever, a third dead-letters silently. A single shared component — classify, retry with backoff, pause on systemic failure, dead-letter with full context, count everything — makes the behaviour uniform and reviewable, and is what frameworks such as Spring Kafka provide out of the box.

Interview Questions

Beginner: What is a poison pill, and why is it worse in Kafka than in a queue?

A poison pill is a record a consumer can never process successfully — malformed bytes, a schema the consumer cannot read, or data that fails validation every time.

In a traditional queue, the broker tracks each message: a message that fails repeatedly can be moved to a dead-letter queue automatically while the others keep flowing. Kafka has no per-message state; a consumer group tracks one offset per partition. So the consumer cannot acknowledge the records after the bad one without acknowledging the bad one too. If it keeps retrying, the partition stops: every record behind it waits, and the lag grows at the full production rate.

The impact is partial, which makes it easy to miss. With twelve partitions, one stuck partition is about 8% of capacity, and the group's total lag rises only gradually — so per-partition lag is the alert that catches it.

Handling it means deciding what to do with a record that cannot be processed: publish it to a dead-letter topic with enough context to investigate, and move the offset past it so the partition continues. The important half is that someone must look at the dead-letter topic, or the record is simply lost.

Beginner: What belongs in a dead-letter record?

Enough to explain the failure and to replay the record later. In practice that is the original key and the original value as raw bytes, plus metadata in headers.

The bytes must be the originals, not a re-serialized object, because a common reason for dead-lettering is that the record could not be deserialized in the first place — re-serializing would fail the same way. Keeping the original key matters too: a replay then lands in the same partition, so per-key ordering survives.

The headers should carry the original topic, partition, offset and timestamp; the exception class and message; how many attempts were made; the consumer group; and when it failed. That is what turns a dead-letter topic from a pile of bytes into something an engineer can triage — and what lets a replay tool filter, for example, "everything that failed with ValidationException between 09:00 and 10:00".

Two operational details complete it: retention long enough that the evidence outlives the investigation — weeks rather than the default week — and one dead-letter topic per consumer group, since two groups reading the same topic fail on different records for different reasons.

Mid: How do you implement retries with backoff without being kicked out of the consumer group?

The constraint is that the consumer must call poll() within max.poll.interval.ms — five minutes by default. Sleeping inside the processing loop eats that budget, and a batch of 500 records with a few seconds of backoff each blows through it: the consumer is removed, its partitions are reassigned, the commit fails and the batch is reprocessed elsewhere.

The in-place pattern is pause, poll, resume. When a record needs a backoff, pause the assigned partitions and record the time to retry. Keep calling poll() in the loop — with everything paused it returns no records, but it maintains the consumer's membership and liveness. When the backoff expires, resume the partitions and seek() back to the failed record. Ordering is preserved, because the partition waits rather than skipping ahead.

The alternative is retry topics: publish the failed record to a separate topic with its own consumer and delay, and let the main flow continue. That keeps throughput up but reorders records for a key, so it suits independent records — notifications, enrichment — and not lifecycle events.

Either way the retries must be bounded, with jitter on the backoff so a fleet of consumers does not synchronise its retries into a spike, and with a terminal dead-letter step so nothing retries forever.

Mid: Your consumer dead-lettered 1.4 million records during a database failover. What went wrong, and what is the fix?

The consumer treated a dependency failure as bad data. Every record failed because the database was unavailable, the retry budget was exhausted within seconds, and each perfectly valid record was routed to the dead-letter topic at full production rate.

The damage is worse than the outage itself. Replaying 1.4 million records means reordering them relative to everything processed since, re-running side effects for any that partly succeeded, and doing it as a manual operation under pressure.

The fix is to distinguish systemic failures from per-record ones. Track the error ratio over a short window: when nearly every record in a window fails, this is not bad data. At that point the consumer should stop consuming rather than dead-lettering — pause all assigned partitions, keep polling to stay in the group, and probe the dependency periodically. When it recovers, resume; the backlog is then simply processed, in order, a few minutes late, and the dead-letter topic stays empty.

Two supporting changes: only exceptions classified as permanent should reach the dead-letter path at all, and pausing also protects the dependency, since retrying 6,000 records per second into a database that is recovering is the retry storm that prevents recovery.

Recovery now: replay the dead-lettered records with a tool that preserves the original keys, after confirming the handler is idempotent, and reconcile against the source system.

Senior: Design error handling for a payments consumer with strict ordering per account.

Ordering per account rules out retry topics for anything that changes account state, so the design centres on retrying in place and on being precise about which failures are terminal.

Classification, decided up front and encoded in one component: deserialization and validation failures are terminal — dead-letter immediately, because they will never succeed and a payments producer sending malformed data is itself an incident. Downstream timeouts, connection failures and 5xx responses are transient. Business rejections are terminal after a bounded wait, because the referenced account may still be in flight.

Transient handling: pause the partition, keep polling, retry with exponential backoff and jitter up to a few minutes. Above a 50% error ratio over 30 seconds, treat it as systemic: pause all partitions and probe, so the dead-letter topic never fills with valid payments and the dependency is not hammered while recovering.

Terminal handling: dead-letter with the original key and bytes plus full context headers, into a per-group DLT with a month's retention, and alert on any record appearing in it — for payments, one abandoned record deserves a page, not a dashboard.

Side effects: every handler idempotent on the payment id, with the ledger write and the offset in one database transaction, so retries cannot double-apply. Non-idempotent external calls carry an idempotency key.

Recommendation: in-place retry with pause, a circuit breaker on error ratio, terminal dead-lettering only for permanent failures, idempotent effects, per-partition lag and DLT alerts, and a rehearsed replay tool. And a stated SLO — "no payment unprocessed for more than 15 minutes" — so the team knows when pausing has stopped being the safe choice and must be escalated.

Senior: A bug caused a consumer to dead-letter 40,000 records over two days. The bug is fixed. Plan the replay.

A replay is a production operation, so I would plan it like a deployment rather than running a script against the DLT.

1. Scope it. Read the DLT and group the records by exception class and time: confirm that all 40,000 failed for the reason that was fixed, and not that two bugs are mixed together. The context headers make this a filter rather than an investigation.

2. Check what the handler will do now. Some of these records may have partly succeeded before failing — a row written, an email sent. Reprocessing repeats whatever was not idempotent, so I would verify the handler is idempotent on the business key, and check downstream state for a sample.

3. Decide the destination. Re-producing to the original topic keeps keys and ordering relative to each other, and every consumer group of that topic sees the records again — which may be wrong for groups that processed them fine. If only this group needs them, a dedicated replay topic consumed by this group alone is safer.

4. Control the rate. 40,000 records injected at full speed can starve live traffic or overwhelm the downstream that just recovered. Replay at a bounded rate, outside peak hours, with the consumer's lag watched.

5. Track and verify. Mark replayed records — a header, or a separate topic — count what was replayed against what was in the DLT, and reconcile the business outcome afterwards. Records that fail again go to the DLT with a new attempt count, and the loop is not repeated blindly.

Recommendation: a replay tool built alongside the DLQ, run at a controlled rate, into a replay topic where possible, with idempotency confirmed first and reconciliation afterwards. The two-day gap between the failure and the fix is itself worth a look: the alert on DLT rate should have made that hours, not days.

🎯 Key Takeaways

  • Classify first: bad data or bad dependency. The two need opposite responses.
  • Retrying bad data blocks a partition forever; dead-lettering a bad dependency abandons valid records.
  • One poison record costs a full partition of capacity and is invisible in aggregate lag.
  • Deserialization failures happen inside poll() — catch RecordDeserializationException, dead-letter the raw bytes, seek past exactly one record.
  • Sleeping for backoff blows the max.poll.interval.ms budget and gets the consumer removed from the group.
  • Pause, keep polling, resume is how to wait for any length of time while staying in the group.
  • Retry topics keep throughput but reorder records for a key, so they suit independent records only.
  • Kafka has no delayed delivery; every delay topic is pause-and-seek underneath.
  • Dead-letter records must carry the original key and raw bytes, because the record may be undeserializable.
  • Context headers — topic, partition, offset, exception, attempts — are what make a DLT triageable.
  • One DLT per consumer group, with retention measured in weeks.
  • A systemic failure means pause, not dead-letter: a 4-minute outage can otherwise abandon over a million valid records.
  • Retries multiply load on a failing dependency; pausing is what helps it recover.
  • Every retry repeats side effects, so handlers need idempotency keys or transactional sinks.
  • Build the replay tool with the DLQ, and rehearse a poison record in staging — a DLQ nobody reads or replays is data loss with extra steps.
