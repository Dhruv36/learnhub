Producers: Batching, Keys & Partitioners Foundations

What you'll master: what really happens between send() and the broker's acknowledgement — serializer, partitioner, the per-partition accumulator and the background sender thread; why send() can block your request thread for 60 seconds even though it returns a future; how batch.size and linger.ms form batches, and why a topic with many partitions and modest traffic barely batches at all; compression codecs and what they cost; the timeout hierarchy that bounds every send; the configuration that silently switches idempotence off; why a slow callback stalls every send in the process; and a shutdown that does not drop buffered records. Prerequisites: Topics, Partitions & the Log.

Part 1 — The Journey of a Record Through send()

A producer is two halves: the part that runs on your thread when you call send(), and a background I/O thread (the sender) that does the network work. Knowing which half does what explains nearly every production issue with producers.

🔑 send() is asynchronous only once metadata is known and the buffer has room. The first send to a topic, a send while the cluster is unreachable, or a send while the buffer is full all block the calling thread — for up to a minute with the defaults. If that thread is serving an HTTP request, the request hangs for a minute too. Lower max.block.ms for latency-sensitive callers, and warm the metadata at startup with partitionsFor(topic) so the first real request does not pay for it.
// Java: one producer, created once and shared — it is thread-safe
Properties p = new Properties();
p.put("bootstrap.servers", "kafka-1:9092,kafka-2:9092,kafka-3:9092");
p.put("key.serializer",   "org.apache.kafka.common.serialization.StringSerializer");
p.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");
p.put("max.block.ms", "2000");                       // fail fast instead of hanging a request
KafkaProducer<String, String> producer = new KafkaProducer<>(p);
producer.partitionsFor("orders");                    // fetch metadata at startup

producer.send(new ProducerRecord<>("orders", orderId, json), (meta, err) -> {
    if (err != null) log.error("send failed for {}", orderId, err);   // ALWAYS handle
});

Create one producer and share it. A KafkaProducer is thread-safe, holds connections to the brokers, a metadata cache and the batching buffer. A producer created per request pays for connections and metadata every time, never batches anything, and leaks resources if it is not closed. One per application — or one per distinct configuration — is the rule.

Part 2 — How Batches Form

The accumulator keeps one open batch per partition. The sender ships a batch when either of two things happens first:

batch for orders-4:  [r1][r2][r3][r4] ...          ship when:
                     ◄──── batch.size ────►         (a) the batch reaches batch.size (16 KB), or
                                                     (b) the oldest record has waited linger.ms
                                                         (5 ms by default since Kafka 4.0; 0 before)

linger.ms = 0  →  ship as soon as the sender is free: at low traffic, often ONE record per batch
linger.ms = 20 →  wait up to 20 ms to fill the batch: fewer, fuller, better-compressed requests

Batching happens per partition, so the per-partition rate is what matters. A producer sending 10,000 keyed records per second sounds busy. Spread across 200 partitions, that is 50 records per second per partition, or one record every 20 ms. With a 5 ms linger, most batches hold a single record.

10,000 records/s ÷ 200 partitions = 50 records/s per partition
linger.ms = 5    → expected records per batch ≈ 50 × 0.005 = 0.25 → mostly 1-record batches
linger.ms = 50   → ≈ 2.5 records per batch
linger.ms = 200  → ≈ 10 records per batch, at up to 200 ms of added latency

Unkeyed records avoid this: the sticky partitioner fills one partition's batch at a time.
SettingDefaultRaise it whenCost
linger.ms5 ms (4.0+), 0 beforeThroughput matters more than a few ms of latencyAdds up to that much latency per record
batch.size16,384 bytesHigh per-partition rates; batches are filling before linger endsMore memory per partition in the accumulator
buffer.memory32 MBMany partitions, or bursts while brokers are slowMemory; and more data lost if the process is killed
max.block.ms60 s(Usually lower it)Lower means failing fast when the buffer is full

❌ Calling producer.send(record).get() for every record. Each record waits for its own acknowledgement before the next is sent, so there is never more than one record in a batch and never more than one request in flight. Throughput falls to roughly one record per network round trip plus replication — a few hundred per second instead of tens of thousands.

✅ Send asynchronously and handle the result in a callback. If the caller truly needs confirmation (an API that must not respond until the event is durable), send the batch of records first and wait on all of their futures together, or wait once with flush(). Exercise 2 measures the difference.

Part 3 — Compression

Compression is applied per batch by the producer, stored unchanged by the broker (when the topic's compression.type is producer, the default) and undone by the consumer. It reduces network traffic, disk and page-cache use at the cost of producer and consumer CPU.

CodecRatioCPUTypical choice
none (default)1×NonePayloads that are already compressed (images, encrypted data)
lz4GoodVery lowA safe general default for high throughput
snappyGoodLowSimilar to lz4; common in older setups
zstdBestModerate, tunableNetwork- or storage-bound clusters; cross-region links
gzipHighHighRarely the best choice today; zstd usually beats it

The ratio depends on batch size more than codec. Compression works by finding repetition, and a batch of one JSON record has little to find; a batch of 200 similar records repeats every field name 200 times. Turning compression on while batches hold one record each is mostly wasted CPU — fix batching first. Since Kafka 3.8 each codec's level is configurable (compression.zstd.level and similar), which lets you trade more CPU for a better ratio on expensive links.

producer-metrics to read before and after a change:
  batch-size-avg          average bytes per batch       ◄── tiny? fix linger/keys first
  records-per-request-avg records per produce request
  compression-rate-avg    compressed ÷ uncompressed     ◄── 0.25 means 4× smaller
  record-queue-time-avg   ms a record waited in the accumulator (≈ added latency)
  request-latency-avg     broker round trip, incl. replication for acks=all

Part 4 — Delivery: acks, Retries, Timeouts and Idempotence

Once a batch leaves, the producer keeps retrying retriable errors until the batch succeeds or its time runs out. Since Kafka 3.0 the defaults are safe: acks=all, effectively unlimited retries, and enable.idempotence=true.

acksLeader acknowledges whenRisk
0Never waits — fire and forgetAny failure loses data silently; no retries possible
1The leader has written itLeader dies before followers copy it → acknowledged data lost
all (default)Every in-sync replica has itSafe if min.insync.replicas ≥ 2; see the replication lesson

The timeout hierarchy. Several timeouts nest, and only one of them is the promise to your code:

delivery.timeout.ms  (120 s)  ─ total time from send() to callback, including every retry
  ├─ linger.ms        (5 ms)   ─ time spent waiting for the batch to fill
  ├─ request.timeout.ms (30 s) ─ time to wait for ONE produce request's response
  └─ retry.backoff.ms (100 ms, growing to retry.backoff.max.ms = 1 s) ─ pause between attempts

The producer refuses to start if delivery.timeout.ms < linger.ms + request.timeout.ms.
When delivery.timeout.ms expires, the callback receives a TimeoutException and the record is DROPPED.

How idempotence works. The producer gets a producer id from the broker and numbers each batch per partition. The broker remembers the last five sequence numbers per producer and partition, so a retried batch that was already written is recognised and acknowledged again instead of written twice. The same numbering keeps batches in order even with up to five requests in flight.

without idempotence, max.in.flight = 5, retries on:
  batch A (seq 10) ──► fails (leader moved)                     ┐
  batch B (seq 11) ──► succeeds, written at offset 500          ├─ log order: B, A   ◄── REORDERED
  batch A retried  ──► succeeds, written at offset 501          ┘

with idempotence:
  broker sees seq 11 while expecting 10 → rejects B as out of order; producer retries in order
  and a duplicate retry of A (seq 10 already written) is acknowledged without a second write
🔑 Idempotence is on by default, but conflicting settings switch it off without an error. If you set acks=1, retries=0, or max.in.flight.requests.per.connection above 5 and do not set enable.idempotence yourself, the producer quietly disables idempotence to honour your setting. If you set enable.idempotence=true explicitly alongside a conflicting value, it refuses to start instead. So state it explicitly: enable.idempotence=true turns a silent downgrade into a startup error.

What idempotence does not cover: it removes duplicates caused by the producer's own retries within one producer session. If your application crashes and a new producer resends records it is not sure about, those are new sends with a new producer id, and they are duplicates. Surviving restarts takes transactions with a stable transactional.id, or deduplication on the consumer side — covered in the idempotence and transactions lesson.

Part 5 — Errors and Callbacks

Producer errors come out in two places, and code has to handle both:

WhereExamplesHandle by
Thrown from send()SerializationException; TimeoutException from metadata or a full buffer; producer already closedtry/catch around the call; the record never entered the buffer
Callback / future, retriableNotLeaderOrFollowerException, network errors, NotEnoughReplicasExceptionRetried automatically; you only see them if delivery.timeout.ms runs out
Callback / future, not retriableRecordTooLargeException, authorization failures, TimeoutException after the delivery timeoutYour code decides: log, dead-letter, fail the request, alert

Fire-and-forget is the most common producer bug. producer.send(record) with no callback and no one reading the returned future means every failure after the record left your thread disappears. There is no exception and no log line from your code; the only trace is the producer's record-error-rate metric, if anyone graphs it.

// WRONG: failures vanish
producer.send(new ProducerRecord<>("audit", userId, event));

// RIGHT: every outcome is observed
producer.send(new ProducerRecord<>("audit", userId, event), (meta, err) -> {
    if (err != null) {
        failures.increment();
        deadLetter.offer(event);          // hand off; do NOT block here
    }
});

Callbacks run on the sender thread. That thread is the only one moving data for this producer. A callback that makes a database call, takes a contended lock, or sends to another blocking system holds up every batch for every partition until it returns. Keep callbacks to counting, logging and handing work to a queue that another thread drains.

❌ Writing to a database inside the producer callback. It works in testing. Under load the database slows to 50 ms per call, the sender thread spends its time waiting on it, batches stop moving, the accumulator fills, and send() starts blocking every application thread for up to max.block.ms — a database slowdown has become a Kafka outage in your service.

✅ Keep the callback trivial. Record the outcome into a concurrent queue or counter, and let a separate worker do the slow follow-up. Exercise 4 shows the stall and the fix.

Part 6 — Lifecycle, Shutdown and What You Can Lose

Records in the accumulator exist only in your process's memory. Anything that ends the process before those batches are acknowledged loses them, and nothing on the broker side knows they existed.

send() returned  ─►  record in accumulator (RAM)  ─►  sent  ─►  acknowledged
                     ▲
                     SIGKILL, OOM kill, or a container stopped before close() finishes
                     = records gone, and the callbacks never run
CallWhat it doesUse it
flush()Sends everything buffered and blocks until each record completes (success or failure)Before committing input offsets, at a checkpoint, or before responding
close()Flushes, then releases resources; without an argument it waits indefinitelyAt shutdown
close(Duration)Waits at most that long, then abandons what is left (those records fail)At shutdown with a deadline shorter than your platform's kill timeout

Match the shutdown deadline to the platform. Kubernetes sends SIGTERM and kills the container after terminationGracePeriodSeconds (30 s by default). If the brokers are unreachable, close() would wait far longer than that, and the kill arrives first. Call close(Duration.ofSeconds(20)) in the shutdown hook, so any records that cannot be delivered fail through their callbacks, where your code can log or persist them, instead of vanishing when the kill arrives.

If a record must never be lost, do not rely on the producer's buffer alone. A service that writes to its database and then sends to Kafka can crash between the two. The durable pattern is the transactional outbox: write the event to an outbox table in the same database transaction as the business change, and relay the table to Kafka separately. The System Design queues lesson covers it.

Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    stopAcceptingRequests();                     // 1. no new sends
    producer.close(Duration.ofSeconds(20));      // 2. flush with a deadline under the kill timeout
}));

Interview Questions

Beginner: What happens when you call producer.send()?

On the calling thread, the producer makes sure it has metadata for the topic, serializes the key and value, picks a partition, and appends the record to an in-memory batch for that partition in the record accumulator. It then returns a Future — the record has been buffered, not delivered.

A separate sender thread takes batches that are ready — full at batch.size or older than linger.ms — groups them by the broker leading each partition, and sends one produce request per broker. It retries retriable errors until delivery.timeout.ms expires, and when a batch finally succeeds or fails it completes the futures and runs the callbacks, on the sender thread.

Two points follow. First, a successful return from send() tells you nothing about delivery; you learn the outcome from the callback or the future. Second, send() is not always non-blocking: waiting for metadata and waiting for buffer space both happen on your thread, for up to max.block.ms, which is 60 seconds by default.

That split — your thread fills the buffer, one I/O thread empties it — is also why the producer is thread-safe and meant to be shared: many application threads can feed one producer, and its batching gets better the more records it sees.

Beginner: What do batch.size and linger.ms control?

They decide when a batch leaves the producer. Each partition has an open batch; it is sent when it reaches batch.size bytes (16 KB by default) or when its oldest record has waited linger.ms (5 ms by default since Kafka 4.0, 0 in earlier versions), whichever comes first.

Bigger batches mean fewer requests, less per-request overhead on the brokers and much better compression. The cost is latency: with linger.ms=20, a record can wait up to 20 ms before it is even sent.

The point that is easy to miss is that batching happens per partition. A producer sending 10,000 records per second across 200 partitions sends only 50 per second to each, so a 5 ms linger collects well under one record per batch on average. For keyed traffic spread over many partitions, a longer linger is often the only way to get real batches. Unkeyed traffic batches better because the sticky partitioner fills one partition at a time.

I would tune them by looking at batch-size-avg and record-queue-time-avg: small batches with a short queue time mean linger could be raised; batches at the size limit mean batch.size is the constraint.

Mid: A web service calls producer.send() in its request handler, and during a Kafka outage every request hangs for a minute. Why, and how do you fix it?

Because send() blocks in two situations, and an outage triggers both. If the producer does not have current metadata for the topic's partitions, it waits for it. And once the brokers stop accepting data, the sender cannot drain the accumulator, so after a few seconds buffer.memory fills and every new send() waits for space. Both waits are bounded by max.block.ms, which defaults to 60 seconds — on the request thread.

The fix starts with deciding what the service should do when Kafka is down, because that is a product decision. If the event is optional (analytics), the request should succeed without it: set max.block.ms low (a few hundred milliseconds), catch the TimeoutException, count the drop and move on. If the event is required (an order placed), the request should fail quickly with a clear error rather than hang — again a low max.block.ms, but returning an error.

If the event must not be lost and the request must not fail, the design needs a durable buffer that is not Kafka: write the event to an outbox table in the same transaction as the business data, and relay it to Kafka asynchronously. The request then depends only on the database.

Two supporting changes: fetch metadata at startup with partitionsFor() so the first request after a deploy does not block, and alert on the producer's buffer-available-bytes and record-error-rate, which show trouble before users do.

Mid: How does the idempotent producer prevent duplicates, and when does it not?

When idempotence is enabled — the default since Kafka 3.0 — the producer obtains a producer id and epoch from the broker, and numbers every batch it sends to each partition with a sequence number. The partition leader remembers the recent sequence numbers for each producer. If a batch arrives with a sequence number already written, the broker acknowledges it without writing it again; if one arrives out of order, the broker rejects it so the producer retries in order.

That solves the classic retry duplicate: the produce request succeeded but its response was lost, the producer retried, and without idempotence the record would be written twice. It also keeps ordering intact with up to five requests in flight, where a non-idempotent producer with retries could reorder batches.

It does not help in three situations. Across producer sessions: if the application restarts and resends records it is unsure about, the new producer has a new id and the broker cannot relate the two. Application-level resends: code that catches a failure and calls send() again creates a new record, which idempotence treats as new. When it has been silently disabled: setting acks=1 or more than five in-flight requests without explicitly enabling idempotence turns it off with no error.

So I would set enable.idempotence=true explicitly, so conflicting settings fail at startup, and handle cross-session duplicates with transactions or idempotent consumers.

Senior: A producer's throughput is far below what the brokers can handle. How do you find the bottleneck?

I would locate it by stage, using the producer's own metrics, before changing any setting.

1. Is the application actually calling send() fast enough? If record-send-rate matches what the application produces and the buffer is nearly empty (buffer-available-bytes close to buffer.memory), the producer is not the limit — the code feeding it is. A common cause is send().get() per record, which caps throughput at one round trip per record.

2. Are batches small? A low batch-size-avg and records-per-request-avg mean many small requests: keyed records spread over many partitions with a short linger. Raising linger.ms to 10–50 ms, if the latency budget allows, usually gives the biggest single improvement, and makes compression effective.

3. Is the producer waiting on the brokers? A high request-latency-avg with full buffers points to the brokers or to replication: acks=all waits for the slowest in-sync follower, so one struggling follower slows every produce request to its partitions. Broker-side request metrics show whether time goes to the leader's disk, to waiting for followers, or to the network.

4. Is the sender thread busy doing something else? If callbacks do real work, the one I/O thread spends its time there instead of sending. Profiling the sender thread, or timing callbacks, shows it.

5. Is the producer CPU-bound? Compression, serialization and TLS all cost CPU; gzip in particular. Switching to lz4 or zstd at a low level, or adding producer instances, helps here.

Recommendation: measure with kafka-producer-perf-test.sh against the same topic to establish what the cluster can accept, then compare the application's metrics against it. In my experience the answer is usually batching (linger and keys) or a blocking pattern in application code, and rarely the brokers.

Senior: Design how a service publishes "order placed" events so that no committed order is ever missing from Kafka.

The problem is that the order lives in a database and the event goes to Kafka, and no single operation writes both. Every ordering of the two writes has a crash window: commit then send, and a crash between them loses the event; send then commit, and a crash between them publishes an order that does not exist. Producer settings cannot fix this, because the gap is between two systems.

The design I would use is the transactional outbox. In the same database transaction that inserts the order, insert a row into an outbox table containing the event. Now the event exists if and only if the order does. A separate relay reads the outbox — by polling, or better by change data capture of the outbox table with Debezium — sends each event to Kafka, and marks it sent only after the producer's callback reports success.

The relay's producer is configured for safety: acks=all, enable.idempotence=true stated explicitly, default retries and delivery.timeout.ms, and a callback that records failures without blocking. The topic has replication factor 3 and min.insync.replicas=2, so an acknowledged event survives a broker loss.

Duplicates are still possible — the relay can send an event and crash before marking the row sent, then send it again after restart. So each event carries a stable id (the outbox row id or the order id plus event type), and consumers deduplicate on it. Keying by order id keeps all of one order's events in order within a partition.

Recommendation: outbox plus CDC relay, safe producer defaults stated explicitly, RF 3 with min.insync.replicas=2, stable event ids, and idempotent consumers. The request path then depends only on the database, a Kafka outage delays events rather than losing them, and "never missing" is a property of the design rather than of hoping the process is not killed at the wrong moment.

2 (easy): Compare a synchronous send loop with asynchronous sends.
Solution 
long t0 = System.nanoTime();
for (int i = 0; i < 5_000; i++) {
    producer.send(new ProducerRecord<>("perf", "k" + i, "v" + i)).get();   // waits every time
}
System.out.printf("sync:  %.0f rec/s%n", 5_000 / ((System.nanoTime() - t0) / 1e9));

t0 = System.nanoTime();
List<Future<RecordMetadata>> fs = new ArrayList<>();
for (int i = 0; i < 5_000; i++) {
    fs.add(producer.send(new ProducerRecord<>("perf", "k" + i, "v" + i)));
}
for (Future<RecordMetadata> f : fs) f.get();                               // wait once, at the end
System.out.printf("async: %.0f rec/s%n", 5_000 / ((System.nanoTime() - t0) / 1e9));

sync:  612 rec/s
async: 48210 rec/s

The synchronous loop is bounded by one full round trip per record — the network plus, with acks=all, the time for followers to replicate. Every batch holds one record. The asynchronous version fills batches and keeps up to five requests in flight per broker.

Both versions confirm every record; the second just waits for all of them together. That is the pattern for a caller that needs confirmation: send everything first, then wait on the futures (or call flush()), rather than waiting between records.

4 (medium): Show that a slow callback stalls every send in the producer, then fix it.
Solution 
AtomicLong done = new AtomicLong();
Callback slow = (meta, err) -> {
    try { Thread.sleep(20); } catch (InterruptedException e) { }   // "write the audit row"
    done.incrementAndGet();
};
long t0 = System.nanoTime();
for (int i = 0; i < 2_000; i++) producer.send(new ProducerRecord<>("perf", "k" + i, "v"), slow);
producer.flush();
System.out.printf("slow callback: %.1f s%n", (System.nanoTime() - t0) / 1e9);

slow callback: 40.3 s          ◄── 2,000 × 20 ms, run one after another on the sender thread

All callbacks run on the single sender thread, so their durations add up, and while the thread runs them it is not sending anything. Under sustained load, the accumulator fills and send() starts blocking the application's threads. Move the work off that thread:

ExecutorService followUp = Executors.newFixedThreadPool(8);
Callback fast = (meta, err) -> followUp.submit(() -> writeAuditRow(meta, err));
...
fast callback: 0.4 s           ◄── sends finish at network speed; follow-up work runs elsewhere

Bound the executor's queue in real code, and decide what happens when it is full — otherwise the unbounded queue becomes the next memory problem. The rule stays simple: a callback records the outcome and returns.

5 (hard): A service shows occasional duplicate events after network blips, although "idempotence is on by default". Find out why.
Solution

The producer logs its effective configuration at startup. Search it:

$ grep -A200 'ProducerConfig values' app.log | grep -E 'acks|enable.idempotence|max.in.flight|retries'
	acks = 1

Someone set acks=1 for latency. Because enable.idempotence was not set explicitly, the producer resolved the conflict by disabling idempotence — no error, one log line among hundreds. From then on, a produce request whose response was lost during a network blip was retried and written twice.

Prove it by making the conflict explicit:

p.put("acks", "1");
p.put("enable.idempotence", "true");
→ org.apache.kafka.common.config.ConfigException: Must set acks to all in order to use the idempotent producer.

6 (hard): A Kubernetes deployment loses a few hundred events on every rollout. Diagnose it and design a shutdown that does not.
Solution 
# what the pod does today
main():
    producer = new KafkaProducer(...)          # linger.ms=100 for throughput
    serveHttp()                                # no shutdown hook

# what Kubernetes does on rollout
SIGTERM → (JVM exits: no hook, producer never closed) → buffered batches gone

Without a shutdown hook, SIGTERM ends the JVM while up to 100 ms of records — at this service's rate, a few hundred — sit in the accumulator. Their callbacks never run, so nothing is logged. The fix has three steps, and the order matters:

Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    http.stopAcceptingNewRequests();                 // 1. stop creating new events
    http.awaitInFlightRequests(Duration.ofSeconds(5)); // 2. let requests that already sent finish
    producer.close(Duration.ofSeconds(15));          // 3. flush, bounded under the kill timeout
}));

# deployment.yaml
terminationGracePeriodSeconds: 30                    # 5 + 15 + margin, under 30
StepPrevents
Stop accepting requests firstNew records arriving after the flush has begun
close(Duration) under the grace periodSIGKILL arriving mid-flush; records that cannot be sent fail through callbacks, which log them
A readiness probe that fails on SIGTERMThe load balancer sending new traffic to a stopping pod

This fixes rollouts. It does not fix crashes or OOM kills, which skip the hook entirely. If losing those events is also unacceptable, move the durability boundary into the database with a transactional outbox, so the producer's buffer is never the only copy.

🎯 Key Takeaways

  • send() buffers; it does not deliver. The callback or future is the only report of the outcome.
  • send() blocks for metadata and for buffer space, for up to max.block.ms (60 s) — lower it on request paths.
  • Serialization errors are thrown from send(); network and broker errors arrive later in the callback.
  • Use one shared producer per application; it is thread-safe and batches better the more it sees.
  • A batch ships at batch.size or after linger.ms, whichever comes first; the linger default became 5 ms in Kafka 4.0.
  • Batching is per partition, so keyed traffic over many partitions barely batches without a longer linger.
  • send().get() per record collapses throughput to one round trip per record; wait on futures together instead.
  • Compression ratio depends on batch size; fix batching before choosing a codec, and prefer lz4 or zstd.
  • delivery.timeout.ms is the promise: the total time from send to callback, including retries, after which the record is dropped.
  • Idempotence is the default since 3.0 and prevents duplicates from the producer's own retries, keeping order with up to 5 requests in flight.
  • acks=1 or more than 5 in-flight requests silently disable idempotence unless enable.idempotence=true is set explicitly.
  • Idempotence does not span producer restarts; use transactions or consumer-side deduplication for that.
  • Callbacks run on the single sender thread; slow callbacks stall every send in the process.
  • Buffered records die with the process, so close with a deadline shorter than the platform's kill timeout.
  • Events that must never be lost need an outbox, because no producer setting closes the gap between a database commit and a send.
