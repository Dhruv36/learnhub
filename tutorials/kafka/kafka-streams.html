Kafka Streams: KStream, KTable & State Processing & Integration

What you'll master: what Kafka Streams actually is — a library whose parallelism is your input partitions, not a cluster you operate; the difference between a KStream, a KTable and a GlobalKTable, and why choosing wrongly changes your results rather than your performance; state stores, their compacted changelog topics, and the restore time that decides how long a failover takes; the operations that silently create a repartition topic, and co-partitioning for joins; record caches and commit intervals, which control how many intermediate results downstream sees; the unnamed operator whose auto-generated store name changes when you add a step, resetting state on deploy; and RocksDB memory living outside the JVM heap. Prerequisites: Retention & Log Compaction and Idempotence & Transactions.

Part 1 — A Library, Not a Cluster

Kafka Streams is a Java library. There is no processing cluster, no job manager and no separate deployment model: you write a main method, and you scale by running more copies of your application. Everything it needs — coordination, state, fault tolerance — it gets from Kafka itself.

Streams is the right tool when the input and output are both Kafka. It gives you exactly-once processing (processing.guarantee=exactly_once_v2) over the consume-transform-produce loop from the transactions lesson, plus joins, aggregations and windows that would otherwise be hand-written state management. When the output is a database or an API, a plain consumer — or Kafka Connect — is usually simpler.

Properties p = new Properties();
p.put(StreamsConfig.APPLICATION_ID_CONFIG, "order-enricher");     // group id AND internal topic prefix
p.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
p.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);

StreamsBuilder b = new StreamsBuilder();
KStream<String, Order> orders = b.stream("orders", Consumed.with(Serdes.String(), orderSerde));
orders.filter((k, o) -> o.total() > 10_000)
      .mapValues(Order::toAlert)                                   // mapValues: no repartition
      .to("large-orders", Produced.with(Serdes.String(), alertSerde));

KafkaStreams streams = new KafkaStreams(b.build(), p);
streams.start();
Runtime.getRuntime().addShutdownHook(new Thread(streams::close));   // close() commits and leaves the group

Part 2 — KStream, KTable and GlobalKTable

The same topic can be read three ways, and they mean different things. This is the distinction that decides whether your results are right.

KStreamKTableGlobalKTable
A record meansAn event happenedThe latest value for this key (an upsert)The same, but fully replicated
A null value meansAn ordinary record with no valueDelete this key (tombstone)Delete this key
Each instance holdsIts assigned partitionsIts assigned partitions' keysEvery partition, on every instance
Joins need co-partitioningYesYesNo — any key can be looked up locally
Typical sourceEvent topic (delete policy)State topic (compact)Small reference data: currencies, feature flags
input topic "clicks":  (u1, 1)  (u1, 1)  (u1, 1)

as a KStream, counted:    u1 → 3        "three click events happened"
as a KTable,  counted:    u1 → 1        "u1's current value was set three times; there is ONE u1"

input topic "profiles":  (u1, {…})  (u1, null)
as a KTable: u1 is DELETED by the null; a KStream would pass the null through as a record
🔑 Read events as a KStream and state as a KTable. A KTable's semantics — latest value per key, null deletes — match a compacted topic exactly, which is why state topics are compacted. Reading an event topic as a KTable silently collapses events that happen to share a key; reading a state topic as a KStream turns tombstones into records your code must special-case. The Event Design lesson makes the same split at the topic level.

GlobalKTable trades memory for freedom from co-partitioning. Every instance reads every partition of the topic into local state, so a stream can be joined against it by any field, not just by the stream's key, and no repartition is needed. The costs are real: each instance stores the whole table, and each instance must load it fully at start-up before processing begins. It suits small, slowly changing reference data — a few thousand currencies or feature flags — and not a 40-million-row catalogue.

Part 3 — State Stores, Changelogs and Restore Time

Stateful operations — count, aggregate, reduce, joins, windows — keep their state in a local store, RocksDB by default, on the instance's disk. That state is backed up to a changelog topic in Kafka: a compacted topic written to on every update.

task 0_5 processes partition 5 of "orders"
   local store: /tmp/kafka-streams/order-enricher/0_5/rocksdb/orders-by-customer/
   changelog:   order-enricher-orders-by-customer-changelog, partition 5 (compacted)

instance dies → the task moves to another instance → that instance REBUILDS the store
   by reading the changelog partition from the beginning
   restore rate is bounded by network and RocksDB write speed

restore arithmetic
  store size 100 GB, restore at ~50 MB/s → 100,000 MB / 50 = 2,000 s ≈ 33 minutes
  during which that task processes NOTHING — its partitions' lag grows

num.standby.replicas = 1
  a second instance keeps a warm copy of the store, following the changelog continuously
  failover becomes seconds instead of half an hour, at the cost of a second copy of the state
SettingDefaultEffect
num.standby.replicas0Warm copies of each store; the single biggest lever on failover time
acceptable.recovery.lag10,000 recordsHow close a warm copy must be before a task is moved to it

Persistent volumes matter as much as standbys. The default state directory lives under the system temp directory; in a container that means the store is lost on every restart and rebuilt from the changelog. A StatefulSet with a persistent volume, plus static membership from the rebalancing lesson, turns a routine deploy from "restore everything" into "resume from where the local store stopped".

Part 4 — Repartitioning and Co-Partitioning

Any operation that may change a record's key marks the stream for repartitioning: Streams writes the records to an internal topic keyed by the new key, then reads them back, so that the downstream operation's state is correctly partitioned.

OperationRepartitions?Use instead
mapValues, filter, flatMapValues, peekNo — the key cannot change—
map, flatMap, selectKey, transformYes, if a stateful step followsmapValues when only the value changes
groupByYes — it selects a new keygroupByKey when the key is already right
join between two KStreams / KTablesRequires co-partitioning; repartitions if neededMatch partition counts, or use a GlobalKTable
orders.map((k, v) -> KeyValue.pair(v.customerId(), v))     // key CHANGED → repartition topic
      .groupByKey().count();                               // every record: written to Kafka and read back

orders.mapValues(Order::enrich)                            // key untouched → no extra topic
      .groupByKey().count();

A repartition costs a full round trip through Kafka for every record: produce, replicate, fetch. On a high-volume stream that can double or triple the topic traffic the application generates, and it adds latency. It is often necessary — grouping by a different field genuinely requires it — but an accidental one, caused by using map where mapValues would do, is pure waste.

Co-partitioning is the requirement for KStream-KStream and KStream-KTable joins: both sides must have the same number of partitions and be keyed the same way with the same partitioner, so that matching keys land on the same task. Streams checks partition counts and fails at start-up if they differ; it cannot check that both sides used the same partitioner, which is where the librdkafka mismatch from the partitions lesson resurfaces as a join that silently matches nothing.

Part 5 — Caches, Commits and What Downstream Sees

Streams does not emit every intermediate result. A record cache in front of each state store deduplicates updates for the same key, and the cache is flushed when it fills or when the application commits.

1,000 updates to key "u1" within one commit interval

statestore.cache.max.bytes = 10 MB (default), commit.interval.ms = 30 s (at_least_once)
   downstream receives: ONE record for u1 per flush — not 1,000

statestore.cache.max.bytes = 0
   downstream receives: 1,000 records, every intermediate count
SettingDefaultRaising itLowering it
commit.interval.ms30 s (100 ms under exactly-once)Fewer commits, more reprocessing after a crashFresher output, more coordinator traffic
statestore.cache.max.bytes10 MBFewer downstream updates, more memoryEvery update emitted: useful when debugging, expensive in production
processing.guaranteeat_least_onceexactly_once_v2: atomic output + offsets, 100 ms commits—

The cache changes what consumers see, not what is correct. Final values are always emitted eventually; caching only suppresses intermediate ones. Code downstream must therefore treat a KTable's output as a sequence of states — the "latest value wins" rule again — and never assume it receives one output record per input record.

❌ Testing a topology with the cache disabled and deploying with it enabled. The test asserts one output record per input record and passes. In production the cache collapses updates, a downstream service that counted records sees far fewer, and an alert based on "output rate ≈ input rate" fires constantly.

✅ Treat the cache as part of the contract. Test with production settings for anything that depends on output cadence, and design downstream consumers to be idempotent and state-based. If a step genuinely needs every intermediate value, that is a KStream operation, not a KTable one.

Part 6 — Operating Streams Applications

Name your operators. Without explicit names, Streams generates them by position — KSTREAM-AGGREGATE-STATE-STORE-0000000002 — and the store's name becomes part of its changelog topic's name. Insert one new operator earlier in the topology and every later number shifts: new store names, new changelog topics, and an application that starts with empty state while the old changelogs sit unused.

release 1   .groupByKey().count()                            store KSTREAM-AGGREGATE-STATE-STORE-0000000002
release 2   .filter(...).groupByKey().count()                store KSTREAM-AGGREGATE-STATE-STORE-0000000003
            → different changelog topic → counts restart from ZERO after the deploy

fix, from day one:
   .groupByKey().count(Materialized.as("orders-per-customer"))    // stable name, stable changelog
   .filter(..., Named.as("drop-internal"))

RocksDB memory is not JVM heap. Each store's block cache, memtables and index blocks are native allocations, so a container sized from -Xmx alone is killed by the kernel with no Java error — the exit-137 case from the Docker track. With many partitions the effect multiplies: 64 tasks, each with a store, each with its own buffers. Bound it with a RocksDBConfigSetter that shares one block cache and one write-buffer manager across stores, and size the container for heap plus that budget plus overhead.

memory budget for one instance
  JVM heap                      2 GB
  RocksDB shared block cache    1 GB      ← set explicitly in a RocksDBConfigSetter
  write buffers (shared)      512 MB
  JVM non-heap, threads, other ~512 MB
  container limit               4.5–5 GB  (not 2 GB + a little)

Interview Questions

Beginner: What is Kafka Streams, and how does it scale?

It is a Java library for processing Kafka topics: you build a topology of sources, processors and sinks inside your own application, and run it wherever you run that application. There is no separate processing cluster — coordination, fault tolerance and state backup all use Kafka.

It scales by tasks. Streams creates one task per partition of the input, and distributes tasks across the threads of all running instances, using a consumer group named after the application.id. Adding an instance moves some tasks to it; the maximum useful parallelism is the input topic's partition count, exactly as for a plain consumer group.

Its value over a plain consumer is the stateful work it handles for you: aggregations, joins and windows, with local state stores backed by compacted changelog topics so a failed instance's state can be rebuilt elsewhere. It also supports exactly-once processing across the read-process-write cycle.

Its limit is that both ends should be Kafka. If the destination is a database or an API, a plain consumer or Kafka Connect is usually the better fit.

Beginner: What is the difference between a KStream and a KTable?

A KStream is a stream of independent records: every record is an event that happened, and two records with the same key are two separate facts. A KTable is a changelog: each record is the latest value for its key, replacing any previous one, and a record with a null value deletes the key.

The difference shows up immediately in results. Counting a KStream of three clicks by u1 gives three. Counting the same topic read as a KTable gives one, because the three records are read as three updates to the same entity.

The rule I follow is that event topics — clicks, orders, payments — are KStreams, and compacted state topics — profiles, prices, configuration — are KTables. That matches the topic's cleanup policy: KTable semantics and log compaction are the same idea, one in the application and one in the broker.

There is also a GlobalKTable, which is a KTable replicated in full to every instance. It removes the co-partitioning requirement for joins and lets you look up any key locally, at the cost of every instance holding and loading the whole table — so it is for small reference data.

Mid: A Streams application takes 30 minutes to recover after an instance dies. Why, and what would you change?

Almost certainly state restoration. When a task moves to another instance, its state store must be rebuilt by reading that task's changelog topic from the beginning. A large store — tens or hundreds of gigabytes — restores at the speed the network and RocksDB allow, and the task processes nothing until it finishes.

The main fix is standby replicas. With num.standby.replicas=1, another instance continuously follows each changelog and keeps a warm copy, so failover becomes seconds. The cost is a second copy of the state and the traffic to keep it current.

Persistent local state helps for the common case, which is a restart rather than a hardware loss: if state.dir is on a persistent volume, a restarting instance reuses its store and only catches up the tail of the changelog. Combined with static membership, an ordinary deploy stops triggering restores at all.

Smaller state also helps: more partitions means smaller per-task stores and faster parallel restores; shorter retention on windowed state reduces size; and storing only what the application needs rather than whole records.

I would measure first — the restore progress is reported per task — and start with standbys plus persistent volumes, since those address both failure and deploys.

Mid: What is a repartition topic, and how do you avoid unnecessary ones?

When an operation may change a record's key and a stateful operation follows, Streams must move records so that all records for a key end up on the same task. It does this by writing them to an internal -repartition topic keyed by the new key and reading them back.

That is a full round trip through Kafka for every record — produce, replicate, fetch — so it adds latency and can double the traffic an application generates. It is necessary when you genuinely group by a different field, and wasteful when it is triggered by accident.

The accidental cases are easy to spot: using map when only the value changes (use mapValues), using flatMap instead of flatMapValues, or calling groupBy with a key selector that returns the existing key instead of groupByKey. Streams marks a stream for repartitioning as soon as a key-changing operation is used, even if the key is not actually modified, because it cannot inspect the lambda.

I check by printing topology.describe() and looking for repartition sinks and sub-topology boundaries — and I keep that output in a test, so a change that introduces a new repartition shows up in code review rather than in the traffic graphs.

Senior: After a routine deploy, a Streams application's aggregates reset to zero. What happened?

The state stores changed identity, so Streams created new, empty ones. Two causes produce this.

Auto-generated operator names. If stateful operators are not named, Streams names them by position — KSTREAM-AGGREGATE-STATE-STORE-0000000002 — and the store name becomes part of the changelog topic name. Adding or removing any operator earlier in the topology shifts every later number, so after the deploy the application looks for changelogs that do not exist, creates them, and starts from empty state while the old changelogs remain, unused, holding the real data.

A changed application.id. It prefixes every internal topic and is the consumer group, so changing it is a complete restart under a new identity.

Recovery depends on the aggregate. If it can be rebuilt from the input topic and the input is still retained, reset the application (the reset tool plus deleting local state) and reprocess from the beginning, with output consumers able to tolerate the replay. If not — for example the input has aged out — the old changelog topic still holds the state, and it can be copied into the new changelog topic's name, which is delicate and needs the application stopped.

Prevention: name every stateful operator explicitly with Materialized.as and Named.as from day one; assert the output of topology.describe() in a test so any change to names or sub-topology boundaries fails the build; and treat topology changes as migrations that are reviewed, not as ordinary code changes.

Senior: When would you choose Kafka Streams over a plain consumer, or over Flink?

Against a plain consumer: Streams earns its place when the work is stateful — joins, aggregations, windows, deduplication — or when exactly-once processing between Kafka topics is required. Writing that by hand means managing local state, its backup, its restoration after a failover, and the transactional loop; Streams does all of it. For stateless work, or when the sink is a database, a plain consumer is simpler to reason about and to operate, and Kafka Connect may remove the code entirely.

Against Flink: the trade is operational model against capability. Streams is a library: no cluster, deployed like any other service, scaled like any other service, and limited to Kafka on both ends. Flink is a distributed runtime with its own cluster and job lifecycle, richer windowing and event-time handling, checkpointed state that can be very large, savepoints for versioned upgrades, SQL, and many connectors beyond Kafka.

I would choose Streams when a team already runs JVM services on Kubernetes, the pipelines are Kafka-to-Kafka, and state per instance is modest. I would choose Flink when the processing is the product — complex event-time logic, very large state, multiple sources and sinks — and a platform team can own the cluster.

Recommendation: start with a plain consumer for stateless transformations, Streams for stateful Kafka-to-Kafka work, and move to Flink when the requirements — state size, event-time semantics, non-Kafka sources — outgrow what a library inside your service can reasonably do. Migrating later is real work, so the honest question at the start is how stateful and how big this will become.

6 (hard): A Streams pod is OOM-killed with no Java exception. Budget its memory.
Solution 
symptoms: exit code 137, no OutOfMemoryError in the log, heap graphs look fine at 1.2/2 GB
container limit 2.5 GB, -Xmx2g, 24 tasks on this instance, each with a state store

RocksDB allocates outside the heap: a block cache, memtables (write buffers) and index/filter blocks per store. With 24 stores at default settings, that is easily a gigabyte or more that the JVM never reports. Bound it explicitly so the total is predictable:

public class BoundedRocksDBConfig implements RocksDBConfigSetter {
    private static final Cache CACHE = new LRUCache(512 * 1024 * 1024);            // shared: 512 MB
    private static final WriteBufferManager WBM = new WriteBufferManager(256L * 1024 * 1024, CACHE);
    public void setConfig(String storeName, Options options, Map<String, Object> configs) {
        BlockBasedTableConfig t = (BlockBasedTableConfig) options.tableFormatConfig();
        t.setBlockCache(CACHE);
        t.setCacheIndexAndFilterBlocks(true);        // count index/filter memory against the cache
        options.setTableFormatConfig(t);
        options.setWriteBufferManager(WBM);          // shared write-buffer budget across stores
        options.setMaxWriteBufferNumber(2);
    }
    public void close(String storeName, Options options) { }
}
props.put(StreamsConfig.ROCKSDB_CONFIG_SETTER_CLASS_CONFIG, BoundedRocksDBConfig.class);

Verify with a soak test at full task count rather than in a single-partition development run: the memory that kills the pod scales with the number of stores on the instance, which is why it appears only after a rebalance concentrates tasks on fewer instances.

🎯 Key Takeaways

  • Kafka Streams is a library, not a cluster; you scale it by running more instances of your application.
  • Parallelism is bounded by input partitions, one task per partition, spread across instances and threads.
  • application.id is the consumer group and the prefix of every internal topic; changing it starts over.
  • A KStream is events; a KTable is the latest value per key, where a null value deletes.
  • Counting the same topic as a stream or a table gives different, both-plausible answers.
  • GlobalKTable removes co-partitioning at the cost of every instance holding and loading the whole table.
  • State stores are local and backed by compacted changelog topics, which is how a task recovers elsewhere.
  • Restore time is proportional to state size — roughly 33 minutes for 100 GB at 50 MB/s — and standby replicas turn it into seconds.
  • Put state.dir on a persistent volume, or every restart is a full restore.
  • Key-changing operators create repartition topics; mapValues and groupByKey avoid the needless ones.
  • Joins require co-partitioning, and a partitioner mismatch makes joins match nothing without error.
  • Record caches collapse intermediate updates, so downstream must expect a sequence of states, not one output per input.
  • Unnamed operators get positional store names; adding a step renames them and resets state on deploy.
  • Name every store and operator, and assert topology.describe() in a test.
  • RocksDB memory is native, not heap; bound it with a config setter and size containers for it.
