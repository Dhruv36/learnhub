Time, Windows & Joins Processing & Integration

What you'll master: the three clocks in a streaming system, and why Kafka Streams runs on stream time — the largest record timestamp seen, never the wall clock, so a quiet topic never closes a window; tumbling, hopping, sliding and session windows, and what each costs in state; grace periods, late records and the metric that tells you data is being dropped; suppress() for final results, and why it can emit nothing at all; the four join types, their co-partitioning rules and their windowed state; the stream-table join that enriches with tomorrow's data when a table update overtakes an event; and the arithmetic that says when a join window is too large to hold. Prerequisites: Kafka Streams: KStream, KTable & State.

Part 1 — Three Clocks, and the One Streams Uses

ClockSet byUsed forProblem
Event timeThe producer, or your payloadWhat actually happened, and whenProducer clocks skew; events arrive out of order
Ingestion timeThe broker (LogAppendTime)A reliable, monotonic-ish stampNot when the event happened; a delayed batch looks recent
Processing timeThe consumer's wall clockTrivially availableReprocessing gives different results every run

Kafka Streams is event-time by default and drives everything from the record timestamp — which the partitions lesson showed is either the producer's or the broker's, depending on message.timestamp.type. A timestamp extractor decides where that value comes from:

FailOnInvalidTimestamp              (default) use the record timestamp; throw if it is negative
LogAndSkipOnInvalidTimestamp        skip records with invalid timestamps
UsePartitionTimeOnInvalidTimestamp  fall back to the partition's current time
WallclockTimestampExtractor         ignore the record; use now()  ◄── makes results non-reproducible
custom                              read it out of the payload: occurredAt, as the event design lesson advises

Stream time is the engine's clock, and it only moves when records arrive. Each task tracks the highest timestamp it has seen (never going backwards). Windows close, grace periods expire and suppress() emits only when stream time passes the relevant point.

task stream time = max(record timestamps seen so far)

09:00:00  records flowing, stream time ≈ 09:00        windows closing normally
09:05:00  the source goes quiet (a nightly lull, an upstream outage, a weekend)
          NO records → stream time STAYS at 09:05
          → the 09:00–09:05 window never closes
          → suppress(untilWindowCloses) emits NOTHING, indefinitely
12:00:00  one record arrives, timestamped 12:00
          → stream time jumps to 12:00; every window in between closes at once, in a burst
🔑 "My aggregation stopped producing output" is almost always stream time. Nothing is broken: the application is waiting for evidence that the window is over, and only a record with a later timestamp is evidence. Low-traffic topics, per-tenant topics that idle overnight and test environments all hit this. The fixes are a heartbeat record on the input, a wall-clock punctuator in the Processor API that flushes results, or accepting continuous (non-final) output instead of suppression.

Part 2 — Window Types and What They Cost

WindowShapeA record belongs toState per key
TumblingFixed size, no overlap (every 5 min)Exactly one windowOne entry per retained window
HoppingFixed size, fixed advance (5 min every 1 min)size ÷ advance windows — 5 hereMultiplied by the same factor
SlidingWindows defined by the records themselves, within a time differenceOnly windows that actually contain recordsMuch smaller than hopping for the same resolution
SessionActivity separated by an inactivity gapOne session, which grows and mergesOne entry per open session; merges rewrite them
hopping windows are the expensive ones

TimeWindows.ofSizeAndGrace(Duration.ofMinutes(5), Duration.ofMinutes(1)).advanceBy(Duration.ofMinutes(1))
  every record is written into 5 overlapping windows
  1 M keys × 5 windows × 200 bytes ≈ 1 GB of state for a 5-minute view
  the same "updated every minute" result from SlidingWindows costs a fraction of it

// tumbling count, explicit grace (the 3.0+ API makes grace a required decision)
orders.groupByKey()
      .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofMinutes(5), Duration.ofSeconds(30)))
      .count(Materialized.as("orders-5min"))
      .toStream()
      .to("orders-per-5min", Produced.with(windowedSerde, Serdes.Long()));

// session windows: activity with a 30-minute inactivity gap
clicks.groupByKey()
      .windowedBy(SessionWindows.ofInactivityGapAndGrace(Duration.ofMinutes(30), Duration.ofMinutes(5)))
      .count(Materialized.as("sessions"));

Session windows merge. Two sessions separated by less than the gap become one session when a record arrives between them — the old session records are deleted and a merged one is written. That is correct, and it means a single late record can change results that were already emitted, which downstream consumers must handle as updates rather than as new facts.

Part 3 — Grace Periods and Late Records

Out-of-order records are normal: producers retry, partitions are consumed at different speeds, mobile clients upload hours later. The grace period is how long after a window's end Streams keeps accepting records that belong to it.

window 09:00–09:05, grace 30 s

record with timestamp 09:04:50 arriving while stream time is 09:04:59   → included
record with timestamp 09:04:50 arriving while stream time is 09:05:20   → included (within grace)
record with timestamp 09:04:50 arriving while stream time is 09:06:00   → TOO LATE: dropped silently,
                                                                          counted in dropped-records-total
SettingEffectTrade-off
Grace periodHow long a window accepts late recordsLonger: more correct, more state, later final results
Window retentionHow long the window store keeps a window (at least size + grace)Longer: queryable history, more disk
dropped-records-total metricRecords discarded for being too lateAlert on it: silent data loss otherwise

Choose grace from measured lateness, not from intuition. Publish the difference between a record's event time and the stream time when it arrives — Streams also reports end-to-end latency metrics per processor node — and set the grace period to cover the bulk of the distribution. A long tail of very late records is usually better handled by a separate correction path than by making every window wait.

Part 4 — Emitting Results: Continuous Updates or Final Values

By default a windowed aggregation emits an updated result as records arrive (subject to the record cache from the previous lesson). Downstream sees a stream of revisions for the same window, ending with the final value.

window 09:00–09:05 for key "u1", continuous output
  → (u1@09:00-09:05, 1) (…, 2) (…, 5) (…, 9)      each an UPDATE, not a new fact

with suppression, only the final value
  .suppress(Suppressed.untilWindowCloses(Suppressed.BufferConfig.unbounded()))
  → (u1@09:00-09:05, 9)                            emitted when stream time passes 09:05 + grace
ModeDownstream seesLatencyRisk
Continuous (default)Every intermediate valueImmediateConsumers must treat results as updates
Record cache onlyFewer intermediate valuesUp to the commit intervalSame, with fewer messages
suppress(untilWindowCloses)One final value per windowWindow size + grace, and stream time must advanceEmits nothing while the input is idle
suppress(untilTimeLimit)Rate-limited updatesThe configured limitNot final values

❌ Adding suppress(untilWindowCloses) to get "clean" output, then losing the last window of every day. Traffic stops at 23:00, so stream time freezes there. The 22:55–23:00 window never closes; its result is buffered in memory and emitted the next morning when traffic resumes — or lost entirely if the buffer is bounded with a shutdown policy, or the application restarts.

✅ Decide deliberately how the window gets closed. Either accept continuous updates and let consumers take the latest value per window, or guarantee that stream time advances: a heartbeat record per partition, or a Processor API punctuator on wall-clock time that flushes and forwards. And give suppress a bounded buffer with a policy you have thought about, since unbounded() means the buffer grows with the number of open windows.

Part 5 — The Four Joins

JoinSemanticsWindowed?Co-partitioning
KStream–KStreamTwo events near each other in timeYes — both sides buffered in window storesRequired
KStream–KTableEnrich an event with the table's current valueNoRequired
KStream–GlobalKTableEnrich by any field, not just the keyNoNot required
KTable–KTableTwo tables joined into a third, updated by either sideNoRequired (foreign-key joins relax this)
// stream-stream: payments and orders within 10 minutes of each other
orders.join(payments,
        (order, payment) -> enrich(order, payment),
        JoinWindows.ofTimeDifferenceAndGrace(Duration.ofMinutes(10), Duration.ofMinutes(1)),
        StreamJoined.with(Serdes.String(), orderSerde, paymentSerde));

// stream-table: enrich each order with the customer's current tier
orders.join(customers,                       // customers is a KTable
        (order, customer) -> enrich(order, customer),
        Joined.with(Serdes.String(), orderSerde, customerSerde));

A stream-stream join buffers both sides for the whole window. Each side's window store holds every record within the time difference (plus grace), because a match may still arrive. That is the arithmetic that decides whether a join is feasible:

join window 10 minutes, grace 1 minute, 5,000 orders/s and 5,000 payments/s at 500 bytes
  buffered per side ≈ 5,000 × 660 s × 500 B ≈ 1.65 GB
  both sides ≈ 3.3 GB of state, spread over the tasks — and its changelog traffic

join window 48 HOURS with the same rates
  ≈ 475 GB per side. Not a join: model it as a KTable of open orders plus a punctuator
  that expires them, so state is bounded by OPEN orders rather than by all traffic in 48 h.

Outer and left joins emit non-matches when the window closes, which again depends on stream time advancing. Modern Streams versions emit these correctly rather than eagerly producing a null-side result that a later record contradicts; the practical consequence is that "no match" results arrive one window (plus grace) after the event, not immediately.

❌ A stream-table join enriching with the wrong version of the table. The order stream is a few minutes behind while the customer table is caught up. Streams looks up the table's current value, so an order from 09:00 is enriched with a tier the customer only reached at 09:20 — and reprocessing the same input later produces different output, because the table has moved on again.

✅ Use versioned state stores for temporally correct lookups where it matters, so the join uses the table value as of the event's timestamp. Where that is not available, keep the two sides close in time (monitor the lag difference), or carry the needed attributes in the event itself — the event-carried state approach from the Event Design lesson, which removes the join entirely.

Foreign-key KTable joins (joining on a field of the value rather than the key) exist and are genuinely useful, but they are expensive: Streams maintains subscription topics behind the scenes to propagate updates from both sides. Reach for them when the data model demands it, and expect extra internal topics and state.

Part 6 — Operating Windowed Applications

Bursts of window results after a quiet periodStream time jumped; all pending windows closed at once
Window store size growing steadilyRetention longer than needed, or hopping windows multiplying entries
End-to-end latency metrics per nodeWhere time is spent between event time and emission

Reprocessing is where event time proves itself. A pipeline built on processing time gives different answers every run, so a bug fix cannot be applied to history. With event time, grace periods and idempotent output, replaying last month's data produces the same windows it produced then — which is what makes "reset the application and reprocess" a safe operation rather than a gamble.

Windowed keys carry their window. A windowed aggregation's output key is a Windowed<K> — the key plus the window's start and end — serialized by a windowed serde. Consumers written in other languages must parse that format, which is a common source of confusion; an alternative is to map the result back to a plain key and put the window boundaries in the value, where every consumer can read them.

Interview Questions

Beginner: What is the difference between event time and processing time?

Event time is when something happened, carried in the record — set by the producer, or read from a field in the payload. Processing time is when the application happens to handle the record, read from its own clock. There is also ingestion time, the moment the broker appended the record, which the broker can stamp itself.

The difference matters whenever results are grouped by time. A purchase made at 23:59 that reaches the pipeline at 00:03 belongs to yesterday in event time and to today in processing time. With event time the daily total is correct and stays correct; with processing time it depends on delays, retries and how far behind the consumer was.

Event time also makes reprocessing meaningful: replaying last month's records produces the same windows it produced originally, because the timestamps come from the data rather than from the clock at replay. That is what makes "fix the bug and reprocess" a safe operation.

The cost is that event-time systems must handle out-of-order and late data, which is what grace periods are for. Kafka Streams uses event time by default, taken from the record's timestamp or a custom extractor.

Beginner: What are the window types in Kafka Streams?

Tumbling windows are fixed-size and non-overlapping — every five minutes, say — so each record belongs to exactly one. They are the usual choice for periodic aggregates.

Hopping windows are fixed-size but advance by less than their size, so they overlap: a five-minute window advancing every minute gives a moving five-minute view updated each minute. Each record is written into size ÷ advance windows, so state and output multiply — five times in that example.

Sliding windows also express "within this time difference", but windows are created around the records themselves, so only windows that actually contain data exist. For the same resolution they cost far less state than hopping windows.

Session windows group activity separated by a gap of inactivity: a user's clicks with a 30-minute gap ending the session. Sessions grow as records arrive and can merge when a record arrives between two existing sessions, which means previously emitted results can change.

All of them are event-time based, all accept a grace period for late records, and all keep state per key per window — which is what makes the choice a cost decision as well as a semantic one.

Mid: A windowed aggregation stopped emitting results overnight, but no errors appear. Explain.

Almost certainly stream time. Kafka Streams closes windows when stream time — the highest record timestamp the task has seen — passes the window's end plus its grace period. Stream time advances only when records arrive. When traffic stops overnight, stream time stops with it, so the final windows of the evening never close.

With continuous output you would still have seen the intermediate results; the symptom of complete silence points at suppress(untilWindowCloses), which holds each window's value until it closes. The results are sitting in the suppression buffer, and they will be emitted in a burst when the first record of the morning arrives and jumps stream time forward.

I would confirm it by checking whether the input partitions are genuinely idle, and whether output resumes with a burst when traffic returns. It is also worth checking whether only some partitions are idle: a task whose partition is quiet holds back its own windows even while other tasks process normally.

The fixes, in order of preference: emit continuous updates and let consumers take the latest value per window; or send a heartbeat record per partition every minute so stream time advances; or use the Processor API with a wall-clock punctuator that flushes completed windows. And bound the suppression buffer, so an idle period cannot grow it without limit.

Mid: How do you choose a grace period?

From measurement, not intuition. The grace period should cover the lateness that actually occurs in your data: the gap between a record's event time and the stream time when it arrives.

I would instrument the pipeline to publish that difference, or use the end-to-end latency metrics Streams reports per processor node, and look at the distribution. Typical sources of lateness are producer retries (milliseconds to seconds), consumer lag on the source topic (seconds to minutes), and genuinely delayed producers such as mobile clients uploading after being offline (hours).

Then it is a trade-off. A longer grace period includes more records and keeps windows correct, at the cost of holding state longer and emitting final results later — the final result of a five-minute window with a one-hour grace arrives an hour and five minutes after the window starts. A shorter one gives prompt results and drops the stragglers, which shows up in dropped-records-total.

My usual approach is to set grace to cover the bulk of the distribution — enough that dropped records are rare — and handle the long tail separately, with a correction job that reprocesses late data into the same output keyed by window, rather than making every window wait for the slowest possible record. And I alert on the dropped-records metric, because otherwise late data disappears silently.

Senior: Design a join between orders and shipments that can be up to 48 hours apart.

A 48-hour stream-stream join is usually the wrong shape, and the arithmetic shows why. Both sides must be buffered for the whole window: at 5,000 records per second and 500 bytes, each side holds about 475 GB for 48 hours, plus a changelog topic carrying all of it. That is not a join; it is a database with a very inconvenient interface.

The design I would use is a KTable of open orders. Orders are materialised into a state store keyed by order id, holding only orders that are still awaiting shipment. The shipments stream is joined against that table — a stream-table join, no windowing, state proportional to open orders rather than to all traffic in 48 hours. That is typically a few hours' worth, orders of magnitude smaller.

Expiry needs a punctuator. An order that is never shipped must eventually leave the store, or state grows forever. In the Processor API, a punctuator scans for orders older than the business deadline, emits an "unshipped" event and deletes them. Wall-clock punctuation is appropriate here, since this is an operational timeout rather than an event-time computation — with the caveat that it makes that particular output dependent on real time.

The ordering caveat: a shipment can arrive before its order if the two topics are consumed at different speeds. The handler must tolerate a miss and retry — for example by writing the unmatched shipment into a small pending store, checked when orders arrive — rather than treating it as an error.

Recommendation: KTable of open orders plus a stream-table join and a punctuated expiry, not a 48-hour windowed join. I would reserve stream-stream joins for genuinely near-in-time correlations, minutes rather than days, where the buffered state is bounded and affordable.

Senior: Your nightly totals disagree with the source system by a fraction of a percent, every night. How do you find the cause?

A small, consistent discrepancy in a windowed aggregation usually comes from one of four places, and each leaves a different trace.

1. Late records dropped. Records arriving after the grace period are discarded and counted in dropped-records-total. A steady trickle produces exactly this symptom. The check is the metric; the fix is a longer grace period or a correction path for late data.

2. Window boundaries and time zones. Kafka Streams windows are UTC-aligned from the epoch. A business day that ends at midnight local time does not align with them, so a "daily" total built from 24-hour tumbling windows covers the wrong hours — and differs from the source system by whatever happened in the offset, including during daylight-saving changes.

3. The wrong timestamp. If the extractor uses the broker's append time, or a payload field that is populated late, records land in neighbouring windows. Comparing a sample of records' event times against the window they were counted in shows this quickly.

4. The comparison itself. The source system may count cancellations, refunds or test orders differently, or take its snapshot at a different moment. This is worth ruling out early, because it is common and cheap to check.

Recommendation: instrument first — dropped records, the lateness distribution, and a reconciliation job that recomputes one day's total directly from the topic and compares. Then fix the cause: daily aggregations in a business time zone are better computed from explicit day keys derived from the event's local date than from 24-hour tumbling windows, which is a modelling change rather than a tuning one.

🎯 Key Takeaways

  • Event time is what happened; processing time is when you looked. Only event time makes reprocessing reproducible.
  • Stream time is the largest record timestamp a task has seen, and it advances only when records arrive.
  • An idle input freezes windows, so a quiet topic emits nothing until traffic resumes — then emits a burst.
  • Timestamp extractors decide the clock; the wall-clock extractor makes results non-reproducible.
  • Hopping windows write each record into size ÷ advance windows; sliding windows give the same resolution for far less state.
  • Session windows merge when a record bridges two sessions, so earlier results are revised and must be applied as upserts and deletes.
  • The grace period decides how late a record may be; set it from the measured lateness distribution.
  • Records past the grace period are dropped silently — alert on dropped-records-total.
  • suppress(untilWindowCloses) needs stream time to advance and can emit nothing at all while the input is idle.
  • Stream-stream joins buffer both sides for the whole window; do the arithmetic before choosing one.
  • A wide join window is really a database: model it as a KTable with punctuated expiry instead.
  • Stream-table joins use the table's current value, so a lagging stream is enriched with later data unless stores are versioned.
  • Joins need co-partitioning; GlobalKTable avoids it at the cost of a full copy per instance.
  • Windowed output keys carry their window, which consumers in other languages must parse — or map it into the value.
  • Business-day aggregates are better keyed by the local date than built from UTC-aligned 24-hour windows.
