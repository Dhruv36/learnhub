Retention & Log Compaction Data Design

What you'll master: the three cleanup policies and when each is right; how the log cleaner actually compacts a partition — the clean tail, the dirty head and the in-memory offset map that caps how many keys one pass can handle; why compaction "isn't working" on most new topics (the active segment and the dirty ratio); tombstones, delete.retention.ms, and the consumer that was away too long and never learns a record was deleted; exactly what compaction guarantees and what it does not; sizing a compacted topic; and the log cleaner thread that can die silently and let a compacted topic grow until the disk fills. Prerequisites: Event Design and the segment material in Topics, Partitions & the Log.

Part 1 — Three Cleanup Policies

Every topic has a cleanup.policy that decides how old data leaves the log. The choice follows from what the topic means: a history of events, or the current state of a set of entities.

The internal topics show both at work: __consumer_offsets and __transaction_state are compacted, because they hold the latest value per key (per group partition, per transactional id). Kafka Streams state stores are backed by compacted changelog topics for the same reason.

Retention on a delete topic was covered in the partitions lesson: it works on closed segments, is checked every log.retention.check.interval.ms (5 minutes), uses the segment's largest timestamp, and retention.bytes applies per partition. The rest of this lesson is about compaction, where most of the surprises are.

Part 2 — How the Log Cleaner Compacts a Partition

Compaction is done by background log cleaner threads on each broker (log.cleaner.threads, 1 by default). A compacted partition is divided into a part that has already been cleaned and a part that has not:

compacted partition
┌─────────────── CLEAN TAIL ───────────────┬──────── DIRTY HEAD ────────┬─ ACTIVE SEGMENT ─┐
│ at most one record per key (as of the    │ written since the last     │ never cleaned     │
│ last clean); offsets have gaps           │ clean; duplicates per key  │                   │
└──────────────────────────────────────────┴────────────────────────────┴───────────────────┘

one cleaning pass on this partition:
1. scan the DIRTY head; build an OFFSET MAP: hash(key) → latest offset seen for that key
2. rewrite every segment (tail AND head) into new segments, keeping a record only if
   it is the latest for its key (offset ≥ the map's offset for that key, or key not in the map)
3. swap the new segments in; the cleaned point moves to the end of the old dirty head

The offset map is the cleaner's working memory, and it is bounded. Each entry takes 24 bytes (a 16-byte hash of the key and an 8-byte offset). The broker's log.cleaner.dedupe.buffer.size (128 MB by default, shared among cleaner threads) therefore holds roughly 5 million keys at the default load factor. If a partition's dirty head contains more distinct keys than that, one pass can only deduplicate part of it, and the partition needs several passes to be fully compacted.

128 MB × 0.9 load factor ÷ 24 bytes per entry ≈ 5.0 million keys per pass (one cleaner thread)

compacted topic, 40 M keys over 24 partitions → ~1.7 M keys per partition   ✔ one pass each
compacted topic, 40 M keys over 2 partitions  → ~20 M keys per partition    ✘ ~4 passes each
SettingDefaultWhat it controls
log.cleaner.threads1Parallel cleaning across partitions
log.cleaner.dedupe.buffer.size128 MBOffset-map memory, shared by all cleaner threads
min.cleanable.dirty.ratio0.5Clean a partition only when the dirty head is at least this share of the log
min.compaction.lag.ms0A record is left alone until it is at least this old
max.compaction.lag.msUnlimitedA record becomes eligible for compaction after at most this long, whatever the ratio
delete.retention.ms24 hoursHow long tombstones survive after their segment is cleaned
🔑 Compaction is eventual, and "eventual" can be a long time. A partition is cleaned only when its dirty share reaches min.cleanable.dirty.ratio, only closed segments are eligible, and cleaner threads work through partitions one at a time. A consumer reading a compacted topic will routinely see several records for the same key. Compaction is a storage optimisation that bounds the topic's size — never a promise that a key appears once.

Part 3 — Why Compaction "Isn't Working"

The most common report about a new compacted topic is that it still holds every record. Usually nothing is broken; the defaults simply mean compaction has not been allowed to start.

new compacted topic, 20 MB of updates per day, defaults everywhere

active segment: rolls at 1 GiB OR 7 days (segment.ms)  → 20 MB/day never reaches 1 GiB
                → the segment rolls after 7 days
                → until then EVERYTHING is in the active segment, which is never cleaned
day 7:          first segment closes; dirty ratio 100% ≥ 0.5 → cleaned
                → the new active segment again holds 7 days of duplicates

A consumer reading from the start sees 7 days of repeated updates for every key.
SymptomCauseSetting to change
Nothing compacted on a low-volume topicThe active segment has not rolledLower segment.ms (e.g. 1 hour)
Compaction runs rarely on a large topicDirty share stays below 50%Lower min.cleanable.dirty.ratio (e.g. 0.1–0.2)
A deleted key must disappear within a deadlineNo bound on when a record is compactedSet max.compaction.lag.ms
Consumers need to see every update for a whileCompaction removes intermediate values quicklySet min.compaction.lag.ms
Very many keys per partitionThe offset map cannot hold one pass's keysLarger dedupe buffer, or more partitions

Lower ratios and shorter segments cost I/O. Each cleaning pass rewrites the whole partition's log, clean tail included. A ratio of 0.1 on a large topic means rewriting it every time 10% of it is new data. Choose the values from what consumers need — how many duplicates they can tolerate when reading from the beginning, and any deadline for deletions — rather than making compaction as aggressive as possible.

Part 4 — Tombstones and delete.retention.ms

To delete a key from a compacted topic, produce a tombstone: a record with that key and a null value. Compaction then removes every earlier record for the key. The tombstone itself is kept for delete.retention.ms (24 hours) after the segment containing it has been cleaned, so that consumers get a chance to see the deletion; after that it is removed too.

t0        produce (c3, null)                        tombstone written
t0 + x    cleaner compacts: c3's older values gone  tombstone KEPT
t0 + x + 24h (delete.retention.ms)                 tombstone removed: c3 no longer appears at all

consumer A, reading continuously       sees the tombstone → deletes c3 from its local copy ✔
consumer B, reading from the beginning after the tombstone is removed
                                        never sees c3 at all → correct: c3 does not exist ✔
consumer C, offline for 3 days with c3 in its LOCAL STATE, resumes from its old offset
                                        c3's tombstone was removed while C was away
                                        → C never learns c3 was deleted → keeps it FOREVER ✘

❌ A service that caches a compacted topic locally, and is sometimes stopped for days. Each record it has seen lives in its local store; tombstones are how it learns about deletions. After an outage longer than delete.retention.ms, it resumes from its committed offset past where the tombstones used to be. Deleted customers, revoked permissions or withdrawn prices stay in its cache with no error — and the one-day default makes this a realistic outcome of a long weekend.

✅ Make delete.retention.ms longer than any consumer's plausible downtime, and give stateful consumers a rule: if they have been away longer than that, rebuild local state from the beginning of the topic instead of resuming. Kafka Streams applications restoring from changelogs follow the same logic. Exercise 3 reproduces the stale entry.

Compacted topics require keys. A record with a null key has no identity to compact on, and the broker rejects it with an error that the compacted topic cannot accept a message without a key. Producers writing to compacted topics must always set one.

Part 5 — What Compaction Guarantees, and Sizing a Compacted Topic

GuaranteedNot guaranteed
A consumer reading from the start sees at least the latest value of every key that has not been deletedThat it sees only the latest value — the dirty head and active segment hold duplicates
Records keep their original offsets and orderThat offsets are consecutive
A tombstone is visible for at least delete.retention.ms after cleaningThat a deleted key disappears by any particular time (unless max.compaction.lag.ms is set)
Any consumer that keeps up sees every updateThat a consumer far behind sees intermediate updates — they may have been compacted away

Compacted consumers must be built for "latest value wins". Because intermediate values can vanish, a consumer of a compacted topic must not depend on seeing every change — it sees a sequence of states, some skipped. That suits snapshots of state and does not suit events that must each be acted on (a payment, a notification). The event design lesson's rule applies directly: compacted topics carry state, not deltas.

Sizing depends on the number of keys, not on the write rate:

live data     = distinct keys × average record size
worst case    ≈ live data ÷ (1 − min.cleanable.dirty.ratio)   (dirty head grows until cleaned)
              + the active segment + tombstones within delete.retention.ms

40 M products × 2 KB = 80 GB live
with ratio 0.5: up to ~160 GB before a clean, per replica set
× replication factor 3 = up to ~480 GB of disk

compact,delete adds a time bound: records older than retention.ms are removed even if they are the latest for their key. It suits state that is only relevant while active — sessions, device heartbeats, carts — where an entity untouched for a month should simply disappear. It does not suit a product catalogue, where a product that has not changed for a year must still be present.

Tiered storage does not help here. Moving old segments to object storage (KIP-405) is supported for delete topics; compacted topics stay entirely on local broker disks, so their size has to fit the brokers.

Part 6 — Operating Compaction: The Cleaner That Dies Silently

The log cleaner is a background thread, and if it hits an error it cannot handle, it can stop cleaning — historically by dying, and in newer versions by marking the problem partition as uncleanable and skipping it. Either way, producers and consumers carry on normally, and the compacted topic simply starts to grow without limit.

server log:   ERROR [kafka-log-cleaner-thread-0]: Error due to ...   (or: marking partition uncleanable)
effect:       compacted topics (including __consumer_offsets!) stop being cleaned
              disk use on the affected brokers climbs steadily; nothing else looks wrong
days later:   disk full → the broker stops → partitions offline
MetricHealthyMeaning when unhealthy
max-dirty-percent (LogCleanerManager)Stays around the dirty ratioClimbing past it: cleaning is falling behind or stopped
time-since-last-run-ms (LogCleaner)SmallGrowing: the cleaner thread is not running
uncleanable-partitions-count0Partitions the cleaner has given up on
max-clean-time-secsStableRising: partitions too large, or too many keys per pass
Disk use of compacted topicsRoughly flatLinear growth: the cleaner is not keeping up

Because __consumer_offsets is a compacted topic, a stopped cleaner eventually affects every consumer group: the offsets topic grows, and coordinator failover — which loads a group's offsets by reading its partition of that topic — gets slower. Alert on the cleaner's health on every cluster, not only those where you have created compacted topics yourself.

❌ Monitoring broker disk only as a percentage threshold. A stopped cleaner produces a slow, steady climb that crosses 80% days after the cause, when the log line explaining it has long since scrolled away. The team adds disk, the climb continues, and the cause is found only when someone reads the cleaner metrics.

✅ Alert on the cause, not the consequence: time-since-last-run-ms growing, uncleanable-partitions-count above zero, or max-dirty-percent far above the dirty ratio. Exercise 5 walks through finding and fixing an uncleanable partition.

Interview Questions

Beginner: What is log compaction, and when would you use it?

Log compaction is a cleanup policy that keeps at least the most recent record for each key and removes older records for that key, instead of deleting data by age. A compacted topic therefore behaves like a table of current values: read it from the beginning and you end up with the latest value of every key.

It is the right choice when a topic represents state rather than a history: the current profile of each customer, the current price of each product, configuration values, or the changelog of a Kafka Streams state store. Kafka uses it for its own internal state, including committed consumer offsets.

It is the wrong choice for events that each matter — orders, payments, clicks — because compaction discards all but the latest record for a key, so intermediate events would disappear.

Two properties are worth stating: records keep their original offsets, so compacted topics have gaps; and compaction is eventual, so consumers still see several records for the same key and must treat the latest one as the truth.

Beginner: How do you delete a key from a compacted topic?

Produce a tombstone: a record with the key and a null value. When the log cleaner next compacts that part of the log, it removes every earlier record for the key. The tombstone itself is kept for delete.retention.ms — 24 hours by default — so consumers reading the topic see that the key was deleted, and then it is removed as well.

The retention period matters for consumers that keep local copies. A consumer that is reading continuously sees the tombstone and deletes the key locally. But a consumer that was stopped for longer than delete.retention.ms resumes after the tombstone has gone, never learns about the deletion, and keeps the stale value.

So the practical rules are: set delete.retention.ms longer than any consumer's plausible downtime, and have stateful consumers rebuild from the start of the topic if they have been away longer than that.

Also note that deletion is not immediate: the key disappears only after compaction runs, which depends on the dirty ratio and segment rolling. If there is a deadline, max.compaction.lag.ms bounds it.

Mid: A new compacted topic still contains every update after several days. Why?

Usually because compaction has not been allowed to start, not because it is broken.

The log cleaner never touches the active segment. A segment only closes at segment.bytes (1 GiB) or after segment.ms (7 days). A topic receiving a few megabytes a day keeps everything in its active segment for a week, so for that week nothing can be compacted.

Second, a partition is only cleaned when the dirty portion — data written since the last clean — reaches min.cleanable.dirty.ratio of the log, 50% by default. On a large topic receiving a modest share of updates, that can take a long time.

Third, less often, the cleaner may be unable to keep up or may have stopped: I would check time-since-last-run-ms, max-dirty-percent and uncleanable-partitions-count, and the broker logs for cleaner errors.

For the first two, the fixes are a shorter segment.ms (an hour, for example) and a lower dirty ratio, chosen from how many duplicates readers can tolerate when replaying, and max.compaction.lag.ms if there is a deadline. Each makes the cleaner rewrite logs more often, so the cost is extra disk I/O.

Mid: What is the offset map in the log cleaner, and why does it matter?

When the cleaner compacts a partition, it first scans the dirty part of the log and builds an in-memory map from each key's hash to the latest offset where that key appears. It then rewrites the log, keeping a record only if it is the latest for its key according to the map.

The map's memory is fixed by log.cleaner.dedupe.buffer.size, 128 MB by default and shared among the cleaner threads. Each entry takes 24 bytes, so the default buffer holds roughly 5 million keys. If a partition's dirty section contains more distinct keys than that, one pass covers only part of them, and the partition needs several passes to be fully compacted.

This matters for topics with very many keys in few partitions: a compacted topic with 40 million keys in two partitions has 20 million keys per partition and compacts slowly, while the same data over 24 partitions fits in one pass per partition. The fixes are more partitions, a larger dedupe buffer (which uses broker heap), or more cleaner threads (which divide the same buffer unless it is also increased).

It is a good example of a Kafka limit that is invisible until a topic grows past it: compaction slows, max-clean-time-secs rises, and disk use creeps up without any error.

Senior: Design a compacted topic that distributes a 40-million-product catalogue to many services.

Model: a products topic with cleanup.policy=compact, keyed by the immutable product id, each record carrying the full current product state and a version. Deleted products are tombstones. Services build a local copy by reading from the beginning and then follow updates.

Partitions and sizing: 40 million keys at about 2 KB is 80 GB of live data. With the default dirty ratio the log can reach roughly twice that before a clean, and with replication factor 3 that is up to about 480 GB of disk — which must fit on local broker disks, because tiered storage does not cover compacted topics. I would use 24 or more partitions, which keeps each partition to well under the offset map's capacity per pass, and lets consuming services bootstrap in parallel.

Cleaner settings: segment.ms of an hour or so, so compaction is not delayed by the active segment; a dirty ratio around 0.3 so bootstrapping consumers read fewer duplicates; and delete.retention.ms of several days — longer than any service could plausibly be down — so deletions are never missed.

Consumers: each applies records by version ("latest value wins"), handles tombstones by deleting locally, and rebuilds from scratch if it has been offline longer than delete.retention.ms. Bootstrapping 80 GB takes time, so services should persist their local copy and resume rather than rebuild on every restart.

Operations: alerts on cleaner health and on the topic's disk growth, and producers keyed consistently with full-state records.

Recommendation: a compacted, well-partitioned topic with shortened segments, a long tombstone retention, versioned full-state records and cleaner monitoring. And I would consider whether every service needs all 40 million products: if most need a subset, a filtered derived topic per use case keeps bootstrap times and local storage down.

Senior: Disk use on three brokers has been growing steadily for a week. The topics on them have not changed. Investigate.

Steady growth without a change in traffic suggests something that normally removes data has stopped. I would look at both removal mechanisms.

Compaction first. The log cleaner may have stopped or given up on partitions. The metrics show it: time-since-last-run-ms growing, uncleanable-partitions-count above zero, max-dirty-percent well above the configured ratio. The broker logs will have an error from the cleaner thread. Because __consumer_offsets is compacted, this can happen on a cluster with no user-created compacted topics at all. kafka-log-dirs.sh --describe shows which partitions are growing.

Retention second. For delete topics, the causes of stalled deletion from the partitions lesson apply: a record with a far-future timestamp pinning old segments, a quiet topic whose segments never close, or a retention.bytes that is per partition and therefore much larger in total than intended. The oldest segment's timestamps and the log start offsets show whether deletion has stopped moving.

Also check the unusual ones: a partition reassignment that left extra replicas behind, or a topic whose configuration was changed at the topic level to override the broker defaults.

Remediation depends on the cause — restarting the cleaner and fixing or removing the record it cannot process; deleting records up to an offset for a pinned segment. Prevention is monitoring the mechanisms rather than the disk: cleaner metrics, the age of the oldest segment per partition, and disk growth rate as a trend rather than a threshold.

🎯 Key Takeaways

  • delete is for histories, compact for state, and compact,delete for state that should expire when inactive.
  • Compaction keeps at least the latest record per key and leaves offsets unchanged, with gaps.
  • The cleaner builds an offset map of the dirty head, 24 bytes per key: about 5 million keys per pass with the default 128 MB buffer.
  • Too many keys per partition means several passes; add partitions or buffer.
  • The active segment is never compacted, so low-volume topics need a shorter segment.ms.
  • A partition is cleaned only when its dirty share reaches min.cleanable.dirty.ratio (0.5 by default).
  • Compaction is eventual; consumers always see some duplicates and must apply "latest value wins".
  • max.compaction.lag.ms is the only bound on when a record is compacted.
  • A tombstone is a null value; an empty string deletes nothing.
  • Tombstones survive for delete.retention.ms after cleaning (24 h by default), then vanish.
  • A stateful consumer away longer than delete.retention.ms never sees deletions; rebuild from the beginning in that case.
  • Compacted topics require keys and must carry full state, never deltas.
  • Size compacted topics by keys × record size ÷ (1 − dirty ratio) × replication factor.
  • Tiered storage does not apply to compacted topics; they must fit on broker disks.
  • A stopped or blocked cleaner lets compacted topics — including __consumer_offsets — grow until disks fill; alert on cleaner metrics.
