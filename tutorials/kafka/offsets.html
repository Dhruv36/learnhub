Offsets & Commit Strategies Delivery & Durability

What you'll master: where committed offsets actually live — the compacted __consumer_offsets topic — and how a group finds its coordinator; the commit contract (you commit the next offset to read) and the off-by-one bugs it invites; exactly when auto-commit is at-least-once and the one design change that makes it lose records; synchronous, asynchronous and per-partition commit strategies and their duplicate windows; the commitAsync retry that rewinds a group; committing correctly around rebalances; storing offsets in your own database, in the same transaction as the results, for an exactly-once effect; and resetting offsets safely when you need to replay. Prerequisites: Replication, ISR & acks.

Part 1 — Where Committed Offsets Live

A consumer group's progress is stored in Kafka itself, in an internal topic called __consumer_offsets. A commit is simply a produce request to that topic: a record whose key is (group, topic, partition) and whose value is the offset plus some metadata.

__consumer_offsets   50 partitions (offsets.topic.num.partitions), RF 3, cleanup.policy=compact

a commit for group "billing", orders-3, offset 88120433 is a record:
   key   = (billing, orders, 3)
   value = { offset: 88120433, leaderEpoch: 7, metadata: "", commitTimestamp: ... }

compaction keeps only the LATEST value per key → the table of current positions stays small

How a group finds its coordinator. Every group is mapped to one partition of __consumer_offsets, and the broker leading that partition is the group's coordinator:

coordinator partition = abs(hash(group.id)) % 50
coordinator broker    = the current leader of that __consumer_offsets partition

consequence: all of a group's commits and membership traffic go to ONE broker.
A very busy group (thousands of members, commits every few ms) loads that broker;
many small groups spread naturally across the 50 partitions.
Setting (broker)DefaultWhy it matters
offsets.topic.num.partitions50Fixed once the topic exists; spreads coordinator load
offsets.topic.replication.factor3Must be achievable, or the topic cannot be created on first use
offsets.retention.minutes10,080 (7 days)How long offsets survive after a group becomes empty
offsets.commit.timeout.ms5 sHow long a commit waits for replication before failing
🔑 Committed offsets are only as durable as __consumer_offsets. A development cluster started with one broker creates it with replication factor 1 (the default of 3 cannot be met, so single-broker setups lower it). If that setting is carried into production, losing one broker loses the positions of every group whose coordinator partition lived there — and those groups restart from auto.offset.reset. Check it with kafka-topics.sh --describe --topic __consumer_offsets on every cluster.

Part 2 — The Commit Contract

A committed offset means "the next record this group should read is this offset". It is not "the last record processed". Getting this wrong by one is one of the most common bugs in hand-written commit code.

processed records at offsets 100, 101, 102 of orders-3

CORRECT:  commit 103   → a restart resumes at 103: nothing skipped, nothing repeated
WRONG:    commit 102   → a restart resumes at 102: record 102 is processed AGAIN, every restart
WRONG:    commit 104   → a restart resumes at 104: record 103 is SKIPPED, never processed

// per-partition commit after processing a batch — note the + 1
Map<TopicPartition, OffsetAndMetadata> toCommit = new HashMap<>();
for (TopicPartition tp : batch.partitions()) {
    List<ConsumerRecord<String, String>> recs = batch.records(tp);
    long last = recs.get(recs.size() - 1).offset();
    toCommit.put(tp, new OffsetAndMetadata(last + 1));
}
consumer.commitSync(toCommit);

The no-argument forms, commitSync() and commitAsync(), commit the consumer's current position for every assigned partition — the offset after the last record returned by poll(). That is correct only if every record returned has been processed. If your code processes part of a batch and then calls commitSync(), it commits the unprocessed remainder too.

CallCommitsSafe when
commitSync()Current position of every assigned partitionThe whole batch from the last poll() has been processed
commitSync(map)Exactly the offsets you passYou pass last processed + 1, per partition
commitAsync()Current positions, without waitingAs commitSync(), and you tolerate a lost commit
Auto-commitPositions at the time of a later poll()Processing finishes inside the poll loop (Part 3)

Committed offsets carry the leader epoch. Since Kafka 2.1 (KIP-320), a commit includes the leader epoch of the last record consumed. If the partition's log was later truncated — after an unclean leader election, for example — a consumer resuming from that offset can detect that the log it read no longer matches, instead of silently continuing from a position that now points to different records.

Part 3 — Auto-Commit, Precisely

With enable.auto.commit=true (the default when a group.id is set), the consumer commits every auto.commit.interval.ms (5 s). The detail that decides everything is when: the commit happens inside poll(), and it commits the positions reached by the previous poll().

poll #1 → records 0..499        your loop processes 0..499
poll #2 → (auto-commit 500)     commits 500 — records 0..499 are DONE, so this is correct
          → records 500..999    your loop processes them
crash during processing of 700
restart → resumes at 500        records 500..699 processed again: AT-LEAST-ONCE ✔

So auto-commit is at-least-once as long as every record is fully processed before the next poll(). Also, close() performs a final auto-commit, so a clean shutdown commits exactly what was processed. The guarantee breaks the moment processing leaves the poll loop:

poll #1 → records 0..499 → handed to a thread pool / queue; loop returns immediately
poll #2 → auto-commit 500 → but the pool has only finished 0..120
          ...crash...
restart → resumes at 500  → records 121..499 were NEVER processed: LOST, silently

❌ Adding an executor to "speed up" an auto-committing consumer. The code change looks harmless — executor.submit(() -> handle(record)) instead of handle(record) — and throughput improves. But the next poll() now auto-commits records that are still waiting in the executor's queue, and any crash or redeploy loses them. Nothing errors; the records are simply never processed.

✅ Once processing is asynchronous, commit manually. Turn auto-commit off and commit only offsets whose records have finished — for keyed worker pools, the lowest offset still in flight per partition, as the consumers lesson describes. The Spring Boot Messaging lesson shows the same failure through a framework's listener container.

Processing modelAuto-commit gives
Synchronous, inside the poll loopAt-least-once; up to ~5 s (or one batch) reprocessed after a crash
Handed to another thread or queueRecords can be lost on crash — effectively at-most-once for in-flight work
Batch buffered across several polls before writingLost on crash: commits run ahead of the buffered writes

Part 4 — Manual Commit Strategies

With enable.auto.commit=false, your code decides when progress is recorded. The choice is a trade between commit overhead and how much work is repeated after a crash.

StrategyDuplicates after a crashCost
commitSync after every recordAt most 1 recordA blocking round trip per record — throughput collapses
commitSync after every batchAt most one batchOne blocking round trip per poll; the common default
commitAsync per batch, commitSync on shutdown and revocationAt most a few batchesCheap; a failed async commit is simply superseded
Every N records or T secondsUp to N records or T seconds of workTunable; right for very high rates
Offsets stored with the results (Part 6)None, for the results' storeYour storage must be transactional

The async retry trap. commitAsync does not retry by itself, for a good reason. If your callback retries a failed commit, it may land after a later commit has already succeeded, and move the group backwards:

t1  commitAsync(offset 2000)  ─┐  fails (coordinator moving)
t2  commitAsync(offset 3000)   │─ succeeds → committed = 3000
t3  callback retries 2000     ─┘  succeeds → committed = 2000   ◄── REWOUND by 1,000 records
restart → records 2000..2999 processed again

// if you retry async commits, only retry the newest one
AtomicLong seq = new AtomicLong();
long mySeq = seq.incrementAndGet();
consumer.commitAsync(offsets, (committed, err) -> {
    if (err != null && mySeq == seq.get()) {
        // still the latest attempt: safe to retry (from the poll thread, not here — the consumer
        // is not thread-safe; set a flag and let the loop retry)
        retryLatest = offsets;
    }
});

In practice the simplest robust pattern is: commitAsync() after each batch without retries, and commitSync() at the points that matter — when partitions are revoked and on shutdown — where blocking is acceptable and the final position must be recorded.

try {
    while (running) {
        var batch = consumer.poll(Duration.ofMillis(500));
        process(batch);
        consumer.commitAsync();              // fast path; a failure is fixed by the next one
    }
} finally {
    try { consumer.commitSync(); }           // final, blocking, retried internally
    finally { consumer.close(); }
}

Part 5 — Commits and Rebalances

A rebalance can take a partition away from a consumer at any poll(). If the consumer has processed records from that partition but not committed them, the new owner starts from the old committed offset and processes them again. A rebalance listener closes that window:

consumer.subscribe(List.of("orders"), new ConsumerRebalanceListener() {
    public void onPartitionsRevoked(Collection<TopicPartition> parts) {
        consumer.commitSync(processedOffsetsFor(parts));   // record progress BEFORE giving them up
    }
    public void onPartitionsAssigned(Collection<TopicPartition> parts) { }
    public void onPartitionsLost(Collection<TopicPartition> parts) {
        // already reassigned elsewhere: DO NOT commit — clean up local state only
    }
});
CallbackWhenCommit here?
onPartitionsRevokedBefore partitions are taken away in an orderly rebalanceYes — synchronously, only processed offsets
onPartitionsAssignedAfter new partitions are givenNo; seek here if you store offsets yourself
onPartitionsLostThe consumer lost them without an orderly revoke (session expired, poll timeout)No — another member may already own them

A commit after losing ownership fails. If a consumer exceeds max.poll.interval.ms, it leaves the group, and its next commit throws CommitFailedException: the coordinator rejects commits from a member that no longer owns the partitions, which is what stops a zombie consumer from overwriting the new owner's progress. Treat the exception as "these records will be reprocessed by someone else", not as an error to retry.

Cooperative rebalancing changes when the listener runs. With the cooperative sticky assignor, onPartitionsRevoked is called only for partitions actually moving away, and the rest keep being consumed during the rebalance. Code that assumed "revoked means everything" — flushing all state, committing all partitions — needs adjusting when switching assignors. The rebalancing lesson covers this.

Part 6 — Offsets Outside Kafka, and Resetting Them

When the results of processing go into a transactional database, you can store the consumer's offsets in that database, in the same transaction as the results. Then the results and the progress marker can never disagree: either both commit or neither does.

table consumer_offsets(group_id, topic, partition, next_offset, PRIMARY KEY(group_id, topic, partition))

per batch, ONE database transaction:
  BEGIN;
    INSERT/UPSERT the results for records 1000..1499;
    UPDATE consumer_offsets SET next_offset = 1500 WHERE group_id='ledger' AND topic='payments' AND partition=3;
  COMMIT;

on assignment (onPartitionsAssigned):
  next = SELECT next_offset FROM consumer_offsets WHERE ...;
  consumer.seek(partition, next);      ◄── Kafka's committed offsets are not used at all

A crash before COMMIT rolls back both the results and the offset, and the records are fetched again; a crash after it finds the new offset already stored. The database sees each record's effect exactly once, without needing idempotent writes — this is the "exactly-once effect" for a database sink. Many teams still commit to Kafka as well, for monitoring: lag tools read Kafka's committed offsets.

ApproachGuarantee for the sinkRequires
Commit to Kafka after writingAt-least-once; duplicates possibleIdempotent writes (upserts by key)
Offsets in the DB, same transactionExactly-once effectA transactional sink; seek on assignment
Kafka transactions (Kafka → Kafka)Exactly-once within KafkaOutput is a Kafka topic; see the transactions lesson

Resetting offsets is how you replay after a bug or skip a poisoned range. The tool acts on one group at a time, so other groups reading the same topic are unaffected — and it refuses to run while the group has active members, which prevents the running consumers from immediately overwriting the reset with their own commits.

$ kafka-consumer-groups.sh --bootstrap-server kafka:9092 --group ledger --topic payments \
    --reset-offsets --to-datetime 2026-09-14T09:00:00.000 --dry-run     # default: shows, changes nothing
$ kafka-consumer-groups.sh ... --reset-offsets --to-datetime 2026-09-14T09:00:00.000 --execute

other targets:  --to-earliest  --to-latest  --to-offset N  --shift-by -500
                --by-duration PT2H   --to-current   --from-file plan.csv
scope:          --topic payments:3,4   (only those partitions)   or   --all-topics
🔑 Replaying data replays its side effects. Resetting a group re-runs everything its consumers do: database writes, but also emails, webhooks and charges. Before a replay, list what the consumer does per record and check each effect is idempotent — or run the replay through a separate code path that performs only the safe effects. Save the current offsets first (--reset-offsets --to-current --export > before.csv) so the reset itself can be undone.

Interview Questions

Beginner: What does committing an offset mean, and where is it stored?

Committing records a consumer group's progress on a partition, so that after a restart or rebalance the group resumes from there. The committed value is the offset of the next record to read — after processing offsets 100 to 102, the group commits 103.

It is stored in Kafka, in the internal topic __consumer_offsets. A commit is a record keyed by group, topic and partition, and the topic is compacted so only the latest value per key is kept. Each group is mapped by a hash of its group id to one partition of that topic, and the leader of that partition acts as the group's coordinator, handling its membership and commits.

A few consequences are worth knowing. Commits are only as durable as that topic's replication factor. Committed offsets expire after a group has been empty for offsets.retention.minutes, 7 days by default. And committing is separate from reading: the consumer's position advances as it polls, but only a commit survives a restart.

The commit point decides the delivery guarantee: commit after processing and you get at-least-once, with duplicates after a crash; commit before processing and you get at-most-once, with possible loss.

Beginner: Is auto-commit safe?

It depends on where processing happens, and the precise answer is more useful than "never use it".

Auto-commit runs inside poll() and commits the positions reached by the previous poll. If your loop fully processes each batch before calling poll() again, every committed offset covers only finished records, so auto-commit gives at-least-once delivery. A crash reprocesses at most the records since the last commit — around five seconds' worth by default. A clean close() also commits one last time.

It becomes unsafe as soon as records leave the loop before they are finished: handed to a thread pool, put on an in-memory queue, or buffered to be written later in bulk. Then the next poll() commits records that have not been processed, and a crash loses them without any error.

So I use auto-commit for simple consumers that process synchronously and can tolerate a few seconds of duplicates. For anything that processes asynchronously, batches across polls, or needs exact control over duplicates, I turn it off and commit manually after the work is done.

Mid: Compare commitSync and commitAsync. Which do you use, and when?

commitSync blocks until the coordinator confirms the commit, retrying retriable errors internally. It is reliable, and it costs a round trip each time the loop commits. commitAsync sends the commit and returns immediately, reporting the result to an optional callback. It does not retry, deliberately.

The reason it does not retry is ordering. If an async commit of offset 2000 fails and a later async commit of 3000 succeeds, retrying the first would move the group back to 2000. So a failed async commit is normally just left alone — the next commit, which includes later offsets, supersedes it. If you do retry in a callback, only retry when no newer commit has been sent, which can be tracked with a sequence number.

The pattern I use combines them: commitAsync after each batch in the normal loop, so commits do not slow processing, and commitSync in the two places where the final position must be recorded — in onPartitionsRevoked before partitions move to another consumer, and in the shutdown path before close().

Commit frequency is a separate decision from the method. Committing after every batch bounds duplicates to one batch; committing every few seconds reduces load on the coordinator for very high-rate consumers at the cost of more reprocessing after a crash.

Mid: A consumer writes to Postgres and must never apply a record twice. How do you achieve that?

There are two approaches, and the choice depends on whether the writes can be made naturally idempotent.

If they can, use at-least-once delivery with idempotent writes. Each record has a stable identity — a business key or an event id — and the write is an upsert or an insert that ignores conflicts on that key. Duplicates still arrive after crashes and rebalances, but applying one twice changes nothing. Offsets are committed to Kafka after the database commit. This is simple and works well for state updates ("set order 42 to shipped").

If they cannot — incrementing a balance, appending to a ledger — store the consumer offsets in Postgres, in the same transaction as the results. Each batch becomes one transaction that writes the results and updates a row holding the next offset for that partition. On assignment, the consumer reads that row and seeks to it, ignoring Kafka's committed offsets. A crash either rolls back both results and offset, or finds both committed, so each record's effect is applied exactly once.

The second approach has costs: every assignment must seek correctly, the offsets table becomes part of the schema, and lag monitoring needs either a parallel commit to Kafka or a custom exporter.

I would use idempotent upserts wherever the data allows it, and reserve database-stored offsets for genuinely non-idempotent effects such as balances. Either way I would test by killing the consumer mid-batch repeatedly and checking the totals.

Senior: A bug in a consumer corrupted data for two hours. Plan the replay.

A replay is a production change with side effects, so I would plan it like one rather than just resetting offsets.

1. Establish the window and the scope. From deploy logs and the data, find when the bad version started and stopped processing, per partition if possible. Identify which consumer group was affected; other groups reading the same topic are independent and must not be touched.

2. Check that the input still exists. The topic's retention must still cover the start of the window. If the data is compacted, the replay sees only the latest value per key, which may or may not be what the consumer needs.

3. Audit side effects. List everything the consumer does per record. Database upserts are usually safe to repeat. Emails, payments, webhooks and increments are not. Either make those paths idempotent first (for example, skip emails whose event id was already sent), or run the replay with those effects disabled.

4. Undo the damage if needed. Replaying may simply overwrite bad rows with correct ones, or the bad rows may need deleting first — for appends, replaying without cleanup creates duplicates.

5. Execute safely. Deploy the fixed version with the group stopped; export the current offsets with --to-current --export as the rollback; reset with --to-datetime and --dry-run first, checking the new offsets per partition; then --execute and start the consumers. Watch lag drain and verify the data.

Recommendation: make replay a routine, rehearsed capability rather than an emergency procedure — idempotent effects by design, a documented list of each consumer's side effects, and retention long enough to cover the time it takes to detect a bug. The worst replays are the ones where the team discovers mid-incident that the consumer also sends emails.

Senior: Why does Kafka reject commits from a consumer that was removed from the group, and what does that protect?

Because of zombies. When a consumer stalls longer than max.poll.interval.ms or loses its session, the group reassigns its partitions to another member, which starts processing from the last committed offset. The old consumer may not know it has been removed — it may be in the middle of a long batch — and when it finishes, it tries to commit.

If that commit were accepted, it could move the committed offset to a position that no longer reflects the new owner's progress. Usually it would be behind (causing extra reprocessing), but in some patterns it could be ahead of records the new owner has not processed, causing them to be skipped. The coordinator prevents this by checking the member id and the group's generation: a commit from a member of an old generation is rejected with CommitFailedException.

It protects the committed offset only. It does not stop the zombie's side effects — the zombie may already have written the batch's results to a database while the new owner writes the same records again. That is why at-least-once consumers need idempotent writes even when commits are correct, and why the strongest designs fence zombies at the sink too: storing offsets in the database transaction, or using Kafka transactions, where the producer epoch fences an old instance's writes.

Operationally, a CommitFailedException should be logged and counted, and treated as a sign of a poll-loop problem — batches too slow for the poll interval — rather than retried.

3 (medium): Reproduce an async commit retry rewinding a group, then fix the retry logic.
Solution

Simulate the race deterministically by recording callbacks and replaying the failed one late:

List<Map<TopicPartition, OffsetAndMetadata>> failed = new ArrayList<>();
OffsetCommitCallback naiveRetry = (offsets, err) -> { if (err != null) failed.add(offsets); };

consumer.commitAsync(Map.of(tp, new OffsetAndMetadata(2000)), naiveRetry);  // pretend it failed:
failed.add(Map.of(tp, new OffsetAndMetadata(2000)));
consumer.commitSync(Map.of(tp, new OffsetAndMetadata(3000)));               // a later commit succeeds
for (var o : failed) consumer.commitSync(o);                                 // the naive "retry"
System.out.println(consumer.committed(Set.of(tp)).get(tp).offset());

2000        ◄── the group moved BACKWARDS; 1,000 records will be reprocessed

Two correct designs:

DesignHow
Do not retry async commitsThe next commitAsync supersedes a failed one; commitSync on revoke and shutdown
Retry only the newestKeep a sequence number; in the callback, retry only if no newer commit was sent, and do the retry from the poll thread

A third safeguard is to never commit an offset lower than the one you last committed successfully for that partition — a simple check in your commit helper that makes rewinding impossible by accident.

5 (hard): Build a consumer that applies each payment to an account balance exactly once, by storing offsets in Postgres.
Solution 
CREATE TABLE balances (account text PRIMARY KEY, cents bigint NOT NULL);
CREATE TABLE kafka_offsets (grp text, topic text, part int, next_offset bigint,
                            PRIMARY KEY (grp, topic, part));

consumer.subscribe(List.of("payments"), new ConsumerRebalanceListener() {
    public void onPartitionsAssigned(Collection<TopicPartition> parts) {
        for (TopicPartition tp : parts) {
            Long next = db.queryNextOffset("ledger", tp.topic(), tp.partition());
            if (next != null) consumer.seek(tp, next);          // the DB is the source of truth
        }
    }
    public void onPartitionsRevoked(Collection<TopicPartition> parts) { }  // nothing to commit: DB has it
});

while (running) {
    var batch = consumer.poll(Duration.ofMillis(500));
    for (TopicPartition tp : batch.partitions()) {
        var recs = batch.records(tp);
        db.inTransaction(tx -> {
            for (var r : recs) tx.update("UPDATE balances SET cents = cents + ? WHERE account = ?",
                                         amount(r), account(r));
            tx.upsert("kafka_offsets", "ledger", tp.topic(), tp.partition(),
                      recs.get(recs.size() - 1).offset() + 1);
        });
    }
    consumer.commitAsync();      // optional: only so lag dashboards stay accurate
}

Test it the way it will fail: produce 100,000 payments of known total, kill the consumer with kill -9 at random moments twenty times, and compare the final sum of balances with the expected total.

expected total change: 48,213,904 cents
auto-commit version:   48,391,117   (over by 177,213: payments applied twice)
DB-offset version:     48,213,904   (exact, on every run)

Note the per-partition transaction: offsets are per partition, so each transaction covers one partition's records and its own offset row. Also make sure only one instance can hold a partition at a time — a zombie that lost its partition could still commit a transaction, so the offset upsert should be conditional on the expected previous value.

The records after the skipped range will be processed again as the group catches up. For a notifier that sends emails, that matters: check that the consumer deduplicates by event id before resending, or the replay emails everyone twice for the records that were not skipped.

If only the skipped range should be processed — not everything after it — reset to the start of the range, let the consumer run until it reaches the end of the range, and handle the rest with deduplication, since the tool has no "stop at" option; or write a small one-off consumer using assign() and seek() that reads exactly the range and exits.

🎯 Key Takeaways

  • Committed offsets live in the compacted __consumer_offsets topic, and a commit is a produce request to it.
  • Each group has one coordinator, the leader of partition hash(group.id) % 50 of that topic.
  • __consumer_offsets needs replication factor 3; RF 1 carried from a dev setup loses every group's position with one broker.
  • A committed offset is the next record to read — commit last processed + 1.
  • The no-argument commits use the current position, so they commit the whole last batch whether processed or not.
  • Auto-commit commits the previous poll's positions inside poll(), which is at-least-once only if processing finishes in the loop.
  • Handing records to a thread pool under auto-commit loses them on crash, silently.
  • commitAsync does not retry, because a late retry can rewind the group; the next commit supersedes a failed one.
  • Use commitAsync in the loop and commitSync on revocation and shutdown.
  • Commit processed offsets in onPartitionsRevoked; never commit in onPartitionsLost.
  • CommitFailedException means you no longer own the partitions; accept reprocessing and fix the slow loop.
  • Commit fencing protects the offset, not the side effects; writes still need idempotency or a transactional sink.
  • Storing offsets in the same DB transaction as the results gives an exactly-once effect for that database.
  • Resetting offsets affects one group and requires it to be stopped; dry-run first and export the current offsets.
  • A replay re-runs every side effect, so audit what each consumer does per record before resetting.
