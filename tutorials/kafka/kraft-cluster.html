Cluster Architecture & KRaft Operations

What you'll master: what the controller actually owns, and why Kafka 4.0 removed ZooKeeper entirely; metadata as a replicated log — the __cluster_metadata topic, the Raft quorum that writes it, and brokers as observers applying deltas; dedicated versus combined mode, and how many controllers to run; forming a cluster, cluster ids, and the mismatch error that stops a broker dead; what still works when the controller quorum is lost, which is more than people expect and less than they need; broker fencing and session timeouts; rolling upgrades and the metadata.version feature flag that is not freely reversible; and what migrating from ZooKeeper demanded. Prerequisites: Replication, ISR & acks.

Part 1 — What the Controller Owns

A Kafka cluster needs one component that decides things: which brokers exist, who leads each partition, which replicas are in sync, what topics and configurations exist, and which ACLs apply. That is the controller, and every cluster has exactly one active at a time.

The controller decidesConsequence when it cannot
Partition leadershipA failed broker's partitions stay leaderless — offline
ISR membership changesDurability state freezes; acks=all behaviour drifts from reality
Broker registration and fencingNew brokers cannot join; dead ones are not replaced
Topic and partition creation, deletion, reassignmentAdministrative operations hang or fail
Dynamic configuration and ACLsChanges do not take effect

Before KRaft, this state lived in ZooKeeper, and one broker acted as controller by winning a ZooKeeper election. The arrangement worked for a decade, but it had structural problems: two distributed systems to operate and secure, controller failover that meant reloading all metadata from ZooKeeper (slow on large clusters), and metadata propagated to brokers as full snapshots in RPCs, which limited how many partitions a cluster could manage.

KRaft (Kafka Raft) replaced it. Metadata became a Kafka log, replicated by a Raft quorum of controller nodes. KRaft was production-ready in 3.3, and Kafka 4.0 removed ZooKeeper support completely — a 4.x cluster is KRaft or nothing.

Part 2 — Metadata as a Replicated Log

controllers (a Raft quorum of 3)                 brokers (observers)
┌───────────────────────────────┐
│ controller-1  ACTIVE (leader) │◄── writes metadata records
│ controller-2  follower        │     to __cluster_metadata
│ controller-3  follower        │
└───────────────┬───────────────┘
                │ brokers FETCH the metadata log, like consumers
     ┌──────────┼──────────┐
     ▼          ▼          ▼
  broker-1   broker-2   broker-3      each applies records in order into its in-memory metadata cache
                                      each periodically writes a SNAPSHOT so replay is bounded

Metadata changes are now events: "broker 4 registered", "partition orders-7 has leader 2, ISR 2,3", "topic payments created". Brokers replay them in order, which means every broker converges on the same view and a lagging broker is visibly behind — a measurable quantity rather than a mystery.

Part 3 — How Many Controllers, and Where

The quorum needs a majority to commit metadata, so the count determines the failure tolerance, and the placement determines which failures are survivable.

VotersMajorityToleratesUse
11NothingDevelopment only
321 controller lossThe standard production choice
532 controller lossesLarge or highly critical clusters; more replication work per write
Even numbers—No better than the odd number belowNever
3 zones, 3 controllers, one per zone
  zone lost → 2 of 3 remain → majority holds → leader elections and topic changes continue ✔

3 controllers, 2 in zone A and 1 in zone B
  zone A lost → 1 of 3 → NO majority → metadata frozen ✘
Deploymentprocess.rolesWhen
Dedicated controllerscontroller on 3 nodes, broker on the restProduction: controllers isolated from broker load and restarts
Combinedbroker,controller on the same nodesDevelopment, tests, small clusters; a broker's load can disturb the quorum

Dedicated controllers are small but not unimportant. They hold the metadata log, so they need a fast, reliable disk and low-latency links to each other, but little CPU or RAM compared with brokers. Putting them on the same machines as busy brokers means a broker's garbage collection pause or disk saturation becomes a metadata-availability problem.

Voter membership. Classic KRaft lists the voters statically in controller.quorum.voters, so changing the set means a coordinated restart. Kafka 4.0 supports dynamic quorums (KIP-853), where voters are added and removed at runtime and clients use controller.quorum.bootstrap.servers — check what your version and tooling support before planning a controller replacement.

Part 4 — Forming a Cluster and Keeping It Consistent

Every node's storage is stamped with the cluster id at format time. That is what prevents a broker from joining the wrong cluster — and what produces one of the most common first-run errors.

$ kafka-storage.sh random-uuid
4L6g3nShT-eMCtK--X86sw

# on EVERY node, with the SAME cluster id
$ kafka-storage.sh format --cluster-id 4L6g3nShT-eMCtK--X86sw --config /etc/kafka/server.properties
Formatting /var/lib/kafka/data with metadata.version 4.0-IV3.

# controller node
process.roles=controller
node.id=1
controller.quorum.voters=1@c1:9093,2@c2:9093,3@c3:9093
listeners=CONTROLLER://:9093
controller.listener.names=CONTROLLER

# broker node
process.roles=broker
node.id=101
controller.quorum.voters=1@c1:9093,2@c2:9093,3@c3:9093      # brokers must know the quorum
listeners=PLAINTEXT://:9092
advertised.listeners=PLAINTEXT://broker-1.internal:9092     # the address clients must reach
broker.rack=eu-west-1a

❌ Formatting each node with its own generated cluster id. Every node starts, and then brokers refuse to join with InconsistentClusterIdException, or the cluster appears to come up with a quorum that no broker recognises. It is the usual outcome of copying a runbook that ends at kafka-storage.sh random-uuid without saying to reuse the output.

✅ Generate the cluster id once and format every node with it. Keep it in the deployment configuration, not in someone's terminal history — and when a node is rebuilt, format it with the cluster's existing id, which kafka-metadata-quorum.sh describe --status will tell you.

SettingDefaultEffect
broker.heartbeat.interval.ms2 sHow often a broker tells the controller it is alive
broker.session.timeout.ms9 sSilence for this long and the broker is fenced: its partitions move
controlled.shutdown.enabletrueA clean stop hands leadership over before exiting
metadata.log.dirThe first log dirPut the metadata log on a fast, reliable disk

Fencing is the mechanism behind "my broker left the cluster". A broker that stops heartbeating — a long GC pause, a saturated disk, a network problem — is fenced by the controller: it stops being a leader, its partitions move, and it must re-register and catch up before serving again. That is correct behaviour, and it means broker pause times matter as much here as they did for the ISR.

Part 5 — What Breaks When the Quorum Breaks

Losing the controller quorum is less catastrophic than it sounds and more dangerous than it looks, because the cluster keeps serving traffic while being unable to react to anything.

quorum LOST (2 of 3 controllers down)

still works:                                  does NOT work:
  produce and consume on existing leaders       leader election for a failing broker
  replication between existing replicas         broker registration (no new/restarted brokers)
  consumer group coordination on live brokers   topic creation, deletion, partition changes
                                                config and ACL changes
                                                ISR changes being recorded

so: the cluster looks healthy — until anything else fails, and then those partitions stay offline
SymptomLikely causeFirst check
Admin operations hang; produce/consume fineQuorum lost or unstablekafka-metadata-quorum.sh describe --status
One controller's lag growingSlow disk or network on that nodedescribe --replication; the node's disk latency

Alert on the quorum itself — the number of current voters, the active controller's identity changing frequently, and each voter's lag — rather than inferring cluster health from producer metrics. The failure mode that hurts is exactly the one where producers are fine.

Part 6 — Upgrades, Feature Flags and the ZooKeeper Migration

A KRaft cluster carries a metadata.version feature flag that gates which metadata record types are in use. Upgrading Kafka is therefore two steps: roll the software, then raise the feature version once every node is running the new release.

$ kafka-features.sh --bootstrap-server kafka:9092 describe
Feature: metadata.version  SupportedMinVersion: 3.3-IV3  SupportedMaxVersion: 4.0-IV3  FinalizedVersionLevel: 3.9-IV0

# only AFTER every controller and broker runs the new release
$ kafka-features.sh --bootstrap-server kafka:9092 upgrade --metadata 4.0
StepRule
Roll the softwareOne node at a time, in the order the release notes specify; wait for zero under-replicated partitions between brokers
Raise metadata.versionOnly when every node supports it — a node that does not cannot join afterwards
DowngradesLimited and version-dependent; treat a finalized metadata version as a one-way door unless the notes say otherwise
Client compatibilityOlder clients keep working; 4.0 removed support for very old client protocol versions, so check the oldest client in the estate

The ZooKeeper migration mattered to anyone still on 3.x: a ZooKeeper-based cluster had to be migrated to KRaft on a 3.x release — 3.9 being the last bridge — before it could run 4.x. The process registered KRaft controllers alongside ZooKeeper, ran a dual-write phase while metadata was copied and verified, then cut brokers over to KRaft mode. Clusters that skipped it found that 4.0 simply would not start.

What changed operationally is worth knowing even on a cluster that was always KRaft, because most material online predates it: there is no zookeeper-shell and no --zookeeper flag, every tool takes --bootstrap-server (or --bootstrap-controller for quorum tools), ACLs and dynamic configs live in metadata rather than ZooKeeper znodes, and controller failover no longer involves reloading everything.

Interview Questions

Beginner: What is KRaft, and why did Kafka move away from ZooKeeper?

KRaft is Kafka's built-in consensus mechanism for cluster metadata. Instead of storing metadata in a separate ZooKeeper ensemble, a small quorum of controller nodes maintains it as a Kafka log — __cluster_metadata — replicated with the Raft protocol. Brokers follow that log like consumers and apply the changes to their own view of the cluster.

The move solved several problems at once. Operationally, a Kafka cluster needed two distributed systems, each with its own configuration, security model, monitoring and upgrade cycle. Technically, controller failover meant loading all metadata out of ZooKeeper, which was slow on large clusters, and metadata was pushed to brokers as full state, which limited how many partitions a cluster could handle.

With KRaft, a controller failover is fast because the other voters already have the log; metadata reaches brokers as incremental records with periodic snapshots; and there is one system to run.

The practical consequence today is that Kafka 4.0 removed ZooKeeper support entirely. A cluster still on ZooKeeper had to be migrated to KRaft on a 3.x release before upgrading, and a great deal of documentation and tutorials online still describe the old world.

Beginner: How many controllers should a cluster have, and where should they run?

Three for most production clusters, five for large or especially critical ones. The quorum needs a majority to commit a metadata change, so three voters tolerate losing one and five tolerate losing two. Even numbers are pointless: four voters need three for a majority, the same as five, while adding replication work.

Placement matters as much as the count. With three availability zones, one controller per zone means losing a zone leaves two of three — a majority — so leader elections and administrative changes continue. Putting two of three controllers in the same zone means losing that zone freezes metadata.

In production I would run dedicated controller nodes: process.roles=controller on small machines with fast disks, separate from the brokers. Combined mode, where a node is both broker and controller, is convenient for development and small clusters, but a broker's garbage collection pause or disk saturation then becomes a metadata problem.

Controllers need little CPU or memory compared with brokers, but they do need low-latency storage and network, because every metadata change is a Raft write that a majority must acknowledge.

Mid: What happens if the controller quorum loses its majority?

The cluster keeps serving existing traffic and loses the ability to change anything — which is a dangerous combination, because it looks healthy.

Still working: producers and consumers on partitions whose leaders are alive, replication between existing replicas, and consumer group coordination handled by live brokers. Clients notice nothing.

Not working: anything requiring a metadata write. No new partition leaders can be elected, so if a broker fails while the quorum is down, its partitions simply go offline and stay there. No broker can register, so a restarted broker cannot rejoin. Topic creation, partition reassignment, configuration and ACL changes all fail or hang. ISR changes cannot be recorded.

So the risk is a second failure. The cluster is running without its ability to heal, and the first broker problem becomes an outage of those partitions.

I would detect it by alerting on the quorum directly — current voters, voter lag, and how often the active controller changes — because producer-side metrics stay green. Recovery is to restore controller nodes; since they hold the metadata log, a returning voter catches up from the leader and the majority is restored.

Mid: Walk through upgrading a KRaft cluster.

It is two phases: roll the software, then raise the metadata feature version. Mixing them is where upgrades go wrong.

Preparation: read the release notes for the specific hop, because the order of controllers and brokers and any removed configuration or protocol support differ between releases. Check the oldest client in the estate against the version's supported protocol range — 4.0 removed support for very old clients. Confirm the cluster is healthy first: zero under-replicated partitions, a stable quorum.

Rolling: one node at a time. Stop cleanly with SIGTERM so controlled shutdown moves leadership, start the new version, and wait for zero under-replicated partitions before the next broker — the rule from the replication lesson. For controllers, verify the quorum is complete and lag is zero before moving on.

Finalizing: once every node runs the new release, raise metadata.version with kafka-features.sh upgrade --metadata. Doing it earlier means nodes still on the old release can no longer participate. Treat it as a one-way door: downgrade paths for metadata versions are limited and version-specific, so I would rehearse the whole sequence in staging, including a rollback of the software before finalizing.

Afterwards: watch for clients failing on removed protocol versions, check the quorum and under-replicated partitions, and leave the cluster a release behind the very latest unless a specific feature is needed — upgrades are risk, and there is no prize for being first.

Senior: Design the cluster topology for a platform serving 40 teams across three availability zones.

Controllers: three dedicated nodes, one per zone, on small instances with fast local disks. Five only if the cluster becomes very large; three tolerates a zone loss, which is the failure I am designing for.

Brokers: a multiple of three, spread evenly across zones with broker.rack set, sized so the cluster runs comfortably on two-thirds of its capacity — when a zone goes, its traffic and leadership move to the remaining two. Topic defaults of replication factor 3 and min.insync.replicas=2, with auto-creation disabled.

One cluster or several? With 40 teams I would start with one well-run cluster and split only for specific reasons: hard isolation for regulated data, wildly different SLAs (a batch-analytics workload next to payments), or geography. Each additional cluster multiplies the operational work — upgrades, monitoring, ACLs, client configuration — and cross-cluster data then needs replication tooling. Multi-tenancy inside one cluster is handled with quotas and ACLs rather than with separate clusters.

Multi-tenancy controls: per-principal produce, consume and request-rate quotas so one team cannot starve the rest; ACLs per topic prefix per team; a naming convention that encodes ownership; and partition-count governance, since partitions are a shared cluster resource.

Operability: automated rolling restarts that wait for zero under-replicated partitions, quorum alerting, per-broker and per-partition metrics, capacity headroom reviewed quarterly, and a tested zone-failure game day.

Recommendation: three dedicated controllers across three zones, brokers in multiples of three with rack awareness and 50–60% peak utilisation, one cluster with quotas and ACLs for tenancy, and a second cluster only when a concrete isolation requirement appears — documented, so the decision is revisited deliberately rather than by accretion.

Senior: Admin commands hang while producers and consumers are fine. Diagnose it.

That split — data plane healthy, control plane stuck — points at the controller quorum, and I would check it before anything else.

1. Quorum status. kafka-metadata-quorum.sh describe --status shows the current voters, the leader and the high watermark. If fewer than a majority are present, no metadata can be committed, which is exactly "admin operations hang while traffic flows". describe --replication shows each voter's lag: a single voter far behind suggests a slow disk or a network problem on that node rather than a lost majority.

2. Controller stability. Frequent changes of active controller — visible in the leader epoch climbing and in controller logs — indicate an unstable quorum: voters timing out because of disk latency, garbage collection or packet loss. The symptom is the same, because each election interrupts metadata writes.

3. Connectivity. Brokers reach controllers on the controller listener; a firewall or security-group change affecting port 9093 leaves brokers serving data from their cached metadata while being unable to participate in changes.

4. The controller nodes themselves: disk full on the metadata log directory, or a node that failed to start after a restart.

Recovery is to restore a majority — usually restarting a failed controller, which catches up from the log. Prevention: alert on voter count, voter lag and active-controller changes; keep the metadata log on fast, dedicated disks; and run controllers on nodes that are not also busy brokers, so a broker's bad day cannot take the control plane with it.

The decision rule I would write down: split when there is a concrete isolation requirement — regulation, a blast-radius limit for a critical workload, or a hardware profile that does not fit — and not for organisational tidiness. Everything else is multi-tenancy: quotas so one tenant cannot starve another, ACLs per topic prefix, a naming convention encoding ownership, and partition-count governance.

Revisit it yearly with data: per-tenant volume, quota throttling events, and incidents where one tenant affected another. Those numbers say whether the shared cluster is still the right call far better than the instinct that separate clusters feel safer.

🎯 Key Takeaways

  • The controller owns leadership, ISR changes, registration, topics, configs and ACLs; without it the cluster cannot change.
  • KRaft stores metadata as a replicated Kafka log written by a Raft quorum of controllers.
  • Kafka 4.0 removed ZooKeeper entirely; ZooKeeper clusters had to migrate on a 3.x release first.
  • Brokers are observers of the metadata log, applying incremental records instead of receiving full state.
  • Three controllers tolerate one loss, five tolerate two; even numbers add nothing.
  • One controller per availability zone, or losing a zone loses the majority.
  • Use dedicated controller nodes in production so broker load cannot destabilise the quorum.
  • Every node is formatted with the same cluster id; a mismatch stops a broker with InconsistentClusterIdException.
  • Never reformat a broker that holds replicas to clear a start-up error.
  • Brokers are fenced after broker.session.timeout.ms (9 s) of silence, so pauses move partitions.
  • A lost quorum still serves traffic but cannot elect leaders, register brokers or change anything — a latent outage.
  • Alert on the quorum itself — voter count, voter lag, active-controller changes — not on producer health.
  • Upgrades are two phases: roll the software, then raise metadata.version once every node supports it.
  • Treat a finalized metadata version as one-way; soak before finalizing, while software rollback is still simple.
  • Split clusters for concrete isolation requirements, not tidiness: every extra cluster multiplies operational cost.
