Topics, Partitions & the Log Foundations

What you'll master: what a partition physically is on a broker's disk — segments and their sparse indexes — and how a fetch at any offset is found without scanning; the record batch, which is the real unit Kafka stores, compresses and replicates; the difference between the log end offset and the high watermark, and why a consumer cannot see a record the leader already holds; exactly how a key becomes a partition, why a Python or Go producer can send the same key to a different partition than a Java one, and why adding partitions breaks per-key ordering; hot partitions; choosing a partition count with arithmetic; and the future-dated timestamp that stops retention from deleting anything. Prerequisites: What Kafka Actually Is.

Part 1 — A Partition Is a Directory of Segments

On a broker, every partition replica is a directory named <topic>-<partition> inside one of the configured log.dirs. The log is not one ever-growing file: it is split into segments, and each segment is named after the first offset it contains.

/var/lib/kafka/data/orders-3/
  00000000000000000000.log         segment 1: offsets 0 .. 1,843,001        (closed)
  00000000000000000000.index       sparse offset → byte position
  00000000000000000000.timeindex   sparse timestamp → offset
  00000000000001843002.log         segment 2: offsets 1,843,002 .. 3,702,414 (closed)
  00000000000001843002.index
  00000000000001843002.timeindex
  00000000000003702415.log         ACTIVE segment — every write goes here
  00000000000003702415.index
  00000000000003702415.timeindex
  00000000000003702415.snapshot    producer-state snapshot (idempotence bookkeeping)
  leader-epoch-checkpoint          which leader epoch began at which offset
  partition.metadata               the topic's id
SettingDefaultEffect
segment.bytes (topic) / log.segment.bytes1 GiBRoll to a new segment when the active one reaches this size
segment.ms / log.roll.hours7 daysRoll even if the size was never reached
index.interval.bytes4,096Add one offset-index entry roughly every 4 KB of log
segment.index.bytes10 MBMaximum index file size; a full index also rolls the segment

Why segments exist: deletion and compaction work on whole files. Retention deletes a closed segment in one unlink instead of rewriting a huge file, and the active segment is never touched by either. This is why segment size quietly controls how precisely retention works — a topic with 1 GiB segments and little traffic may keep data days past retention.ms, because the old records sit in a segment that has not closed yet.

Finding offset 3,702,900 without scanning:

1. Pick the segment:  base offsets [0, 1843002, 3702415] kept in memory, sorted
                      → 3,702,900 lives in segment 3702415
2. Search the index:  00000000000003702415.index is memory-mapped
                      entries are (relative offset, byte position), 8 bytes each
                      binary search → largest entry ≤ 485 (= 3,702,900 − 3,702,415)
                      → (480, position 1,961,234)
3. Scan the .log:     read forward from byte 1,961,234 until offset 3,702,900
                      at most ~4 KB of scanning, because an entry exists every ~4 KB
🔑 The index is sparse on purpose. Indexing every record would make the index as big as a large part of the log. One entry per ~4 KB keeps each index small enough to stay in memory, and the cost is a short sequential scan — which is cheap. The .timeindex works the same way for timestamps (12-byte entries: an 8-byte timestamp and a 4-byte relative offset), and it is what makes "reset this group to 09:00 yesterday" a fast lookup.

Part 2 — The Record Batch: the Real Unit of Storage

Producers do not send records one by one, and brokers do not store them that way. The unit on the wire, on disk and in replication is the record batch (message format v2, introduced in Kafka 0.11 and the only format Kafka 4.0 still supports).

RECORD BATCH (header = 61 bytes)
  baseOffset            int64    offset of the first record — assigned by the BROKER
  batchLength           int32
  partitionLeaderEpoch  int32
  magic                 int8     = 2
  crc                   uint32   covers everything after this field
  attributes            int16    compression codec, timestamp type, transactional?, control batch?
  lastOffsetDelta       int32
  baseTimestamp         int64
  maxTimestamp          int64
  producerId            int64  ┐
  producerEpoch         int16  ├ idempotence and transactions live HERE, once per batch
  baseSequence          int32  ┘
  recordCount           int32
  records[] ─┐   (compressed together as ONE block when compression is on)
             ▼
RECORD
  length varint · attributes int8 · timestampDelta varlong · offsetDelta varint
  key (varint length + bytes) · value (varint length + bytes) · headers[]

Three consequences follow from that layout:

Design choiceConsequence
Offsets and timestamps stored as deltas from the batch baseThe broker assigns offsets by writing one baseOffset, without recompressing the records
Compression applies to the whole batchLarger batches compress better; a batch of one record barely compresses at all
Producer id, epoch and sequence are per batchIdempotence costs a few bytes per batch, not per record
Size limits apply to the batchOne record bigger than max.request.size (1 MB) or the broker's message.max.bytes (about 1 MB) is rejected outright

Message size limits must agree along the whole path. Raising the broker's message.max.bytes is not enough: the producer's max.request.size, the topic's max.message.bytes and the consumer's fetch limits have to allow it too, and replication must be able to fetch it. A record larger than 1 MB is usually a sign that the payload belongs in object storage, with Kafka carrying a reference to it.

Part 3 — Log End Offset, High Watermark, and What a Consumer Can See

Every replica has a log end offset (LEO): the offset the next record will get. The leader also tracks the high watermark (HW): the highest offset that every in-sync replica has copied. Consumers can read only below the high watermark.

                offsets:  ...  96   97   98   99  100  101
leader    (broker 1)           ■    ■    ■    ■    ■    ■     LEO = 102
follower  (broker 2)           ■    ■    ■    ■                LEO = 100
follower  (broker 3)           ■    ■    ■    ■    ■           LEO = 101

HIGH WATERMARK = min LEO across the ISR = 100
consumers can read offsets ≤ 99. Offsets 100 and 101 exist on the leader but are INVISIBLE,
because a leader failure right now could elect broker 2, which does not have them.

The high watermark is how Kafka stops consumers from reading records that could vanish in a leader failover. If a consumer could read offset 101 and broker 2 then became leader, the consumer would have processed a record that no longer exists — and the new leader would later assign offset 101 to a different record.

OffsetMeaningWho uses it
Log start offsetOldest offset still retainedearliest resets; retention
High watermarkReplicated to the whole ISR; readableDefault consumers; the "end" in lag
Last stable offset (LSO)Below any still-open transactionread_committed consumers
Log end offsetNext offset to be written on this replicaReplication; not visible to consumers

Offsets are not a record count. Offsets always increase, but they are not always consecutive for data records. Transactional producers write control records (commit and abort markers) that take offsets of their own and are never delivered to your code, and compaction removes records while leaving the survivors at their original offsets. So "end offset minus start offset" is an upper bound on the number of records, not a count, and code that expects offset + 1 to be the next record it receives will be surprised.

  offset 44  key=c        ◄── 42, 43: a commit marker and a compacted-away record
  offset 45  key=a

Part 4 — From Key to Partition

The producer, not the broker, decides which partition a record goes to. With the Java client's default behaviour:

key present:   partition = toPositive(murmur2(serializedKeyBytes)) % numPartitions
key null:      "sticky" — fill a batch for one partition, then move on (KIP-480, Kafka 2.4)
               since 3.3 (KIP-794) it switches after about batch.size bytes, and sends
               fewer records to partitions whose brokers are responding slowly
explicit:      new ProducerRecord<>(topic, partition, key, value) overrides everything

The hash is taken over the serialized bytes of the key, which has a practical consequence: the same logical key serialized differently — a number sent as a string by one service and as a 4-byte integer by another — lands on different partitions, and per-key ordering silently disappears.

❌ A Java service and a Python service produce to the same topic with the same keys, and per-customer ordering breaks. The Java client uses murmur2. Clients built on librdkafka — confluent-kafka for Python, Go and .NET, among others — default to consistent_random, which hashes keys with CRC32. The same key goes to different partitions depending on which service wrote it, so one customer's events are split across two partitions with no order between them.

✅ Make every producer on a topic use the same partitioner. Set partitioner=murmur2_random on librdkafka clients so they match the Java client, and write a test that produces a known key from each language and asserts the partition. Exercise 2 shows the mismatch.

Adding partitions remaps keys. Because the partition is the hash modulo the partition count, changing the count changes where most keys go. Going from 6 to 8 partitions, a key keeps its partition only when h % 6 == h % 8, which holds for 6 of every 24 hash values:

6 → 8 partitions:   25% of keys stay put, 75% move to a different partition
6 → 12 partitions:  50% stay (h % 12 is either h % 6 or h % 6 + 6)

During the change, customer 42's OLD events sit in partition 1 and NEW ones go to partition 7.
A consumer of partition 7 can process "order shipped" before another consumer has finished
"order paid" in partition 1. Per-key order is broken exactly at the moment of the change.
SituationCan you add partitions?Safer approach
Unkeyed events (logs, metrics)Yes — nothing depends on placementAdd freely
Keyed, order matters, can pause producersYes, with a drainStop producers, let consumers catch up, add, restart
Keyed, order matters, no pause possibleRiskyCreate a new topic with more partitions and migrate consumers deliberately
Compacted "current state" topicNoA key's older value stays in the old partition and is never compacted away

Hot partitions come from skewed keys. If one tenant produces 40% of traffic and the key is the tenant id, one partition carries 40% of the load no matter how many partitions exist, and the one consumer assigned to it falls behind while the others sit idle. The usual fix is a composite key — tenant-42#3, spreading a large tenant across a few buckets — which keeps ordering within each bucket but gives up ordering across the whole tenant. Decide which ordering the business actually needs before choosing the key.

Part 5 — Choosing a Partition Count

You cannot reduce a topic's partition count, and increasing it has the costs above, so the number deserves some arithmetic at creation time. Size for the slower of the two sides:

target throughput                     T = 120 MB/s at peak, growing 50%/year
per-partition PRODUCE rate (measured) P = 20 MB/s
per-partition CONSUME rate (measured) C = 5 MB/s   ◄── consumers do real work; usually the limit

partitions ≥ max(T / P, T / C) = max(6, 24) = 24
headroom for 2 years of growth (×2.25) → 54, round to 60 (divisible by many consumer counts)

The consume side usually decides it, because each consumer does real work per record — a database write, an API call — and a partition can only be processed as fast as one consumer handles it. Measure C with your real handler, not with a benchmark consumer that discards records.

More partitions buyMore partitions cost
More consumer parallelismMore open files and memory on every broker
Spreading load over more brokersMore replication traffic and more leaders to move in a failover
Headroom without remapping keys laterSmaller batches per partition in producers, so worse compression and more requests
Longer rebalances for consumer groups
🔑 Partitions are cheap individually and expensive in bulk. KRaft raised the number of partitions a cluster can manage well, but each partition is still a set of files, a replication stream and a producer batch. A producer writing to 2,000 partitions spreads its buffer.memory (32 MB by default) across 2,000 batches, so each batch is small, compression is poor and requests multiply. Prefer a sensible count per topic over "1,000 just in case".

Placement matters as much as count. Set broker.rack on each broker (to its availability zone, for example) so that Kafka spreads a partition's replicas across racks. Without it, all three replicas of a partition can land in one zone, and losing the zone loses the partition despite a replication factor of 3.

Part 6 — Timestamps, and the Record That Blocks Retention

Every record carries a timestamp, and the topic's message.timestamp.type decides whose clock it comes from.

TypeSet byGood forRisk
CreateTime (default)The producer, or your code explicitlyEvent time: when the thing happenedWrong producer clocks, or code passing bad values
LogAppendTimeThe broker, on appendRetention and time lookups that must be reliableLoses the original event time (put it in the payload instead)

Time-based retention uses the largest timestamp in a segment. A segment becomes eligible for deletion only when its newest record is older than retention.ms. So one record stamped in the future — a device with a clock set to 2036, or a bug that writes milliseconds where seconds were expected — keeps its whole segment, and in practice every later segment's deletion is blocked behind it, since segments are deleted oldest first.

segment 0   max timestamp = 2026-09-01          ► deletable after 7 days
segment 1   max timestamp = 2036-01-01  (!)     ► NOT deletable for ten years
segment 2   max timestamp = 2026-09-12          ► blocked: retention deletes from the oldest end
            ... disk use grows without limit, and nothing reports an error

Kafka 3.6 added broker-side limits on how far a record's timestamp may sit before or after the broker's clock (log.message.timestamp.before.max.ms and after.max.ms, KIP-937), so records with absurd timestamps can be rejected at write time. Check the defaults in the version you run; for topics fed by devices or third parties, set a strict limit or use LogAppendTime. Exercise 5 recovers a partition from exactly this state.

❌ Trusting producer timestamps on a topic whose disk usage "just keeps growing". The team raises disk alerts, adds brokers and shortens retention.ms, and nothing is ever deleted, because the problem is one record stamped years ahead that pins its segment.

✅ Check the timestamps before changing retention. kafka-dump-log.sh prints each batch's largest timestamp (as CreateTime: on the batch line); the .timeindex of the oldest segment shows the largest time in it. Delete up to a known offset with kafka-delete-records.sh, then stop it recurring with a timestamp limit or LogAppendTime.

Interview Questions

Beginner: How is a partition stored on disk?

As a directory per partition replica, containing a series of segment files. Each segment is a .log file of record batches plus two small indexes, and it is named after the first offset it holds — 00000000000001843002.log starts at offset 1,843,002. Only the newest segment, the active one, receives writes; it rolls to a new segment at 1 GiB or after 7 days by default.

The indexes are what make random access fast. The .index maps offsets to byte positions, but sparsely — about one entry per 4 KB of log — so it stays small and memory-mapped. To fetch an offset, the broker picks the segment by base offset, binary-searches the index for the nearest entry below the target, and scans forward a few kilobytes. The .timeindex does the same for timestamps.

Splitting the log into segments is also what makes retention cheap: deleting old data means removing whole closed files, never rewriting a large one. The trade-off is that retention can only be as precise as the segment size allows, because the active segment is never deleted.

Beginner: How does a producer choose a partition, and what does that mean for ordering?

With the Java client, a record with a key goes to murmur2(keyBytes) % numPartitions, so every record with the same key lands in the same partition and stays in order. A record without a key is placed by the sticky partitioner: the producer fills a batch for one partition, then moves to another, which gives good batching while spreading load. Code can also name a partition explicitly.

For ordering, that means: same key, same partition, strict order; different keys, no defined order between them. So the key has to be the thing whose events must stay in order — the order id or customer id, for example.

Two things break this quietly. Adding partitions changes the modulus, so most keys move to a new partition, and old and new events for a key can be processed out of order. And producers written in different languages may not use the same hash: librdkafka-based clients default to a CRC32-based partitioner, so a Python producer and a Java producer can send the same key to different partitions unless the librdkafka client is set to murmur2_random.

The key is also a load decision. A key with a very skewed distribution makes one hot partition, whatever the partition count.

Mid: What is the high watermark, and why can't a consumer read a record the leader already has?

Each replica has a log end offset, the next offset it will write. The high watermark is the highest offset that every in-sync replica has copied — effectively the minimum log end offset across the ISR. Consumers can only read records below it.

The reason is failover safety. A record the leader has but some in-sync follower does not could disappear: if the leader fails, that follower may become leader, and the record was never on it. If a consumer had already read and acted on it, the consumer would have processed a record that no longer exists — and the new leader would eventually give the same offset to a different record. Hiding everything above the high watermark means a consumer only ever sees records that survive a leader change.

There is a second boundary for transactions: the last stable offset. A read_committed consumer reads only below the first still-open transaction, so an open transaction holds back everything after it, including records from other producers. A transaction that is left open for a long time shows up as consumer lag that no amount of consumer scaling fixes.

In practice this is also why acks=all latency and consumer end-to-end latency are linked: a slow follower in the ISR delays the high watermark, which delays what consumers can see, even though the leader wrote the record immediately.

Mid: A topic's disk usage grows without limit even though retention.ms is 3 days. What do you check?

Retention is not running the way it appears to, and I would work through the causes that stop segments from becoming deletable.

1. The cleanup policy. If cleanup.policy is compact only, time-based retention never deletes anything — compaction keeps the latest record per key forever. Check with kafka-configs.sh --describe --entity-type topics.

2. Future timestamps. Retention compares retention.ms against the largest timestamp in a segment. One record stamped years ahead pins its segment, and because segments are deleted from the oldest end, everything after it is blocked too. kafka-dump-log.sh on the oldest segment prints each batch's largest timestamp; this is the cause I would expect when producers set timestamps themselves.

3. Segments that never close. With low traffic and large segments, the active segment holds days of data and is never deleted while active. segment.ms bounds this.

4. Size versus time. retention.bytes is per partition, not per topic, so the total can be many times the configured number. Also confirm the broker-level setting is not being overridden differently than expected at the topic level.

The fix follows the cause: correct the policy, delete up to a known offset with kafka-delete-records.sh and add timestamp limits or LogAppendTime, or lower segment.ms. What I would not do first is shorten retention further — if segments are not deletable, a shorter retention changes nothing.

Senior: A keyed topic has 12 partitions and needs to handle four times the traffic. How do you increase capacity without breaking ordering?

First I would confirm what "capacity" is short of. If the consumers are the bottleneck because each record needs slow work, more partitions help. If the brokers are the bottleneck, more brokers or better batching might be enough without changing the partition count at all. And if a few hot keys carry most of the traffic, adding partitions does nothing for them — the hot key still hashes to one partition.

If more partitions are genuinely needed, the problem is that changing the count remaps most keys: 12 → 48 keeps a key's partition only for a quarter of hash values. During the change, a key's older records sit in its old partition and new records go to a new one, so a consumer can process a later event before an earlier one. There are three ways to handle it.

1. Drain and switch in place. Pause the producers, wait until every consumer group has zero lag, add the partitions, resume. Simple and correct, but it needs a producer pause, and every consumer group must be caught up, including slow batch ones.

2. Migrate to a new topic. Create orders.v2 with 48 partitions. Point producers at it; let consumers finish the old topic, then switch them to the new one. No producer pause, and the old topic stays available for replay, but consumers must handle the switch-over, and every consumer group has to migrate.

3. Parallelise inside the consumer. Keep 12 partitions and process each partition's records concurrently by key inside the consumer — a pool of workers where records for the same key always go to the same worker, committing offsets only up to the lowest fully processed record. Libraries such as Confluent's parallel consumer do this. Ordering per key is kept and nothing is repartitioned, at the cost of more complex offset handling.

Recommendation: if the constraint is consumer work per record, I would try option 3 first, since it avoids touching the topic at all. If partitions must grow, a new topic is the safer path for anything order-sensitive; I would reserve the in-place change for topics where a short producer pause is acceptable. And whichever is chosen, I would size the new count for several years of growth so it is not repeated.

Senior: Walk through how you would choose the partition count and key for a new "payments" topic.

Start with the key, because it decides ordering and load. Payments go through state changes — authorised, captured, refunded — that must be processed in order for one payment, so the key has to be at least the payment id. If downstream consumers maintain per-account balances, ordering per account matters too, and the account id is the better key. I would check the distribution: a marketplace with one merchant doing 30% of volume would make a merchant-id key a hot partition, which rules it out.

Then size the count from measured rates. Say peak is 3,000 payments per second at about 2 KB each — 6 MB/s — which any single partition can accept. The real limit is the consumer: if the ledger consumer needs 8 ms per payment because it writes to a database, one partition handles about 125 per second, so 3,000 per second needs 24 partitions just for today's peak. With room for three years of growth at 40% a year, that is about 66; I would choose 72, which divides evenly among many consumer counts.

Then durability and placement: replication factor 3, min.insync.replicas=2, broker.rack set so replicas span three zones, acks=all and idempotence on every producer, and topic auto-creation off so the topic exists only with these settings.

Then retention: long enough to cover the longest plausible consumer outage plus reconciliation needs — for payments, weeks rather than days — with the disk arithmetic done explicitly, and LogAppendTime or a timestamp limit so a bad client clock cannot pin segments.

Recommendation: key by account id if balance consumers need account-level ordering (otherwise by payment id), 72 partitions sized from the consumer's measured throughput, RF 3 across three zones with min.insync.replicas=2, and every producer using the same partitioner. I would write the arithmetic into the topic's design note so the next person to change it can see why.

    --max-messages 20000 --property print.key=true | cut -f1 | sort | uniq -c | sort -rn | head -3
  14211 merchant-8812
    402 merchant-1170
    388 merchant-3001

One merchant is 71% of the partition. Choices, in order of preference: key by something finer if per-merchant ordering is not actually required (payment id); spread the large merchant across buckets (merchant-8812#0..7) if ordering within a payment is enough; or give that merchant its own topic with more partitions. Each gives up some ordering; choose the one the business can live with.

5 (hard): A producer with a wrong clock stamped records ten years ahead. Show that retention stops working, then recover.
Solution 
// Java: the timestamp argument is used as-is under CreateTime
long tenYears = 10L * 365 * 24 * 3600 * 1000;
producer.send(new ProducerRecord<>("clock", 0, System.currentTimeMillis() + tenYears, "k", "future"));

$ kt --create --topic clock --partitions 1 --replication-factor 1 \
    --config retention.ms=60000 --config segment.ms=10000
# produce normal records, then the future one, then more normal records, for a few minutes

$ docker exec kafka /opt/kafka/bin/kafka-dump-log.sh \
    --files /tmp/kraft-combined-logs/clock-0/00000000000000000000.log | grep -o 'CreateTime: [0-9]*' | sort -u | tail -2
CreateTime: 1789286400000          ◄── 2026-09-13
CreateTime: 2104646400000          ◄── 2036-09-10: ten years ahead

$ kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic clock --time -2
clock:0:0                           ◄── nothing deleted, though retention is 1 minute

The segment containing the future record cannot expire for ten years, and the segments after it wait behind it. Recover by deleting everything below a chosen offset, then prevent recurrence:

$ echo '{"version":1,"partitions":[{"topic":"clock","partition":0,"offset":480}]}' > del.json
$ kafka-delete-records.sh --bootstrap-server localhost:9092 --offset-json-file del.json
partition: clock-0  low_watermark: 480

$ kafka-configs.sh --bootstrap-server localhost:9092 --alter --entity-type topics \
    --entity-name clock --add-config message.timestamp.type=LogAppendTime

kafka-delete-records.sh moves the log start offset forward; the segments below it are then removed. Choosing the offset is a data decision — records below it are gone for every consumer — so check with the teams that read the topic. With LogAppendTime the broker stamps records itself; if the event time matters to consumers, carry it in the payload.

6 (hard): Design the partitioning for a clickstream topic: 400,000 events per second at peak, 600 bytes each, consumed by a sessionization job that needs all of one user's events in order and handles 4,000 events per second per partition.
Solution 
volume         400,000 ev/s × 600 B = 240 MB/s at peak (compression reduces the stored bytes)
key            user id       — sessionization needs one user's events in order
consumer limit 400,000 / 4,000 = 100 partitions for today's peak
growth         +50%/yr, sized for 2 years → 100 × 2.25 = 225 → choose 240

producer side  240 MB/s over 240 partitions = 1 MB/s per partition — trivial for brokers
retention      3 days × 240 MB/s ≈ 62 TB before compression; × RF 3 ≈ 187 TB

Check the key distribution before trusting the number. Clickstreams contain bots and crawlers that generate far more events than any person; if one "user" produces 2% of traffic, its partition runs at about five times the average. Filtering or routing bot traffic to a separate topic protects the job.

DecisionChoiceReason

The number that drives everything is the consumer's per-partition rate, which is why it has to be measured with the real job. If the job later gets faster, the extra partitions cost little; if it gets slower, there is headroom before a repartition is needed.

🎯 Key Takeaways

  • A partition is a directory of segments, each named after its first offset; only the active segment is written.
  • The offset index is sparse — about one entry per 4 KB — so it stays in memory and a lookup is a binary search plus a short scan.
  • Retention and compaction work on whole, closed segments, so segment size limits how precisely retention acts.
  • The record batch is the real unit of storage, compression and replication; bigger batches compress better.
  • Size limits apply along the whole path; raising only the broker's limit does not let large records through.
  • Consumers read only below the high watermark, so they never see records a leader failover could erase.
  • read_committed consumers stop at the last stable offset, so one long-open transaction holds back the whole partition.
  • Offsets always increase but are not consecutive on transactional or compacted topics, so they are not a record count.
  • The Java client partitions keyed records by murmur2(key) % partitions; null keys use the sticky partitioner.
  • librdkafka clients hash keys differently by default; set partitioner=murmur2_random when they share a topic with Java producers.
  • Adding partitions moves most keys — 75% when going from 6 to 8 — and breaks per-key order during the change.
  • Hot partitions come from skewed keys, and no number of partitions or consumers fixes them.
  • Size partition count from the slower side, which is usually the consumer doing real work per record.
  • Set broker.rack or replicas can share one zone despite RF 3.
  • Time retention uses a segment's largest timestamp, so one future-dated record can stop all deletion.
  • Use LogAppendTime or timestamp limits for topics fed by clocks you do not control.
