Kafka Connect & CDC Processing & Integration

What you'll master: what Connect is and when writing a producer yourself is the wrong choice; workers, tasks and the three internal topics that hold a cluster's entire state; converters, the single most common Connect failure, and why the sink's converter must match what the producer wrote; source offsets keyed by connector name, so that renaming a connector re-ingests everything; sink error handling and dead-letter queues; SMTs and where they stop; log-based change data capture with Debezium — the snapshot, the envelope, deletes as tombstones — and the replication slot that fills a database's disk while the connector is down; and why raw table CDC should not be your public contract. Prerequisites: Time, Windows & Joins; the System Design data platforms lesson covers CDC at the architecture level.

Part 1 — Connect: Workers, Tasks and Configuration as Data

Kafka Connect is a framework and a worker cluster for moving data between Kafka and other systems without writing producer or consumer code. Source connectors read from a system into Kafka; sink connectors read from Kafka into a system. You configure connectors over a REST API; the workers run them.

Connect cluster (distributed mode): 3 workers, each a JVM

  POST /connectors  {name, connector.class, tasks.max, topics, converters, …}
        │
        ▼
  worker A ── task 0 ── task 3        internal topics (ALL COMPACTED):
  worker B ── task 1 ── task 4          connect-configs   connector and task configs
  worker C ── task 2                    connect-offsets   SOURCE connector offsets
                                        connect-status    connector/task state

a worker dying moves its tasks to the others — the cluster's state is in Kafka, not on disk
ConceptMeaningDetail that bites
WorkerA JVM running connector tasksWorkers with the same group.id form one cluster
TaskThe unit of parallelism (tasks.max)The connector decides how many it can use: a JDBC source cannot exceed its table count; a sink cannot exceed the topic's partitions
ConverterTurns Connect's internal records into bytes and backSet per worker and overridable per connector; a mismatch is the classic failure

Standalone modeOne process, offsets in a local fileFine for demos; no fault tolerance — do not use in production

Use Connect when a well-maintained connector exists for the system at hand — databases, S3, Elasticsearch, JDBC sinks, cloud queues. You get offset management, restarts, scaling, dead-letter handling and monitoring without writing them. Write your own producer or consumer when the integration is genuinely custom, needs business logic per record, or when the only available connector is unmaintained: operating a bad connector is worse than owning fifty lines of code.

Part 2 — Converters: the Most Common Connect Failure

Connect has its own internal record format. A converter translates between that format and the bytes on the topic. The producer's serializer and the sink's converter must agree, and nothing checks this until data flows.

producer wrote Avro with a schema id (magic byte 0 + id), as in the schemas lesson
sink connector configured with value.converter=org.apache.kafka.connect.json.JsonConverter

   org.apache.kafka.connect.errors.DataException: Converting byte[] to Kafka Connect data failed
   due to serialization error: ... JsonParseException: Unrecognized token 'Ãµ'

the task FAILS (errors.tolerance defaults to none) and stays failed until restarted
ConverterWire formatCarries a schema?
StringConverterPlain textNo
ByteArrayConverterRaw bytes, untouchedNo
JsonConverter, schemas.enable=falsePlain JSONNo
JsonConverter, schemas.enable=trueJSON with a schema/payload envelopeYes, inline — and it bloats every record
AvroConverter / ProtobufConverter / JsonSchemaConverterRegistry wire formatYes, by schema id

❌ Assuming the key uses the same format as the value. A sink is configured with value.converter=AvroConverter, which is right, while key.converter is left at the worker default of JsonConverter — and the topic's keys are plain strings. Every record fails on the key, with an error that talks about the value's converter classes and sends people looking in the wrong place.

✅ Set both converters explicitly on every connector, matching what the producers actually write: key.converter=StringConverter with value.converter=AvroConverter is a very common and correct pairing. Verify by consuming the topic with the same converters before deploying the connector.

Schemas matter for sinks that need types. A JDBC sink must know whether a field is an integer or a string to create and populate columns, so it needs a schema — Avro, Protobuf, JSON Schema, or JSON with schemas.enable=true. Schemaless JSON into a JDBC sink fails with a message about requiring a schema; that is the connector telling you the format choice was made too early.

Part 3 — Offsets, Restarts and Renames

Source and sink connectors track progress in completely different places, and the difference explains several surprising behaviours.

Source connectorsSink connectors
Progress stored inThe connect-offsets topic__consumer_offsets, like any consumer
Keyed byConnector name + the connector's own partition (a table, a file)The consumer group connect-<connector-name>
DeliveryAt-least-once (exactly-once support exists for source connectors on recent versions)At-least-once; the sink must be idempotent
Lag visible viaConnector-specific metricskafka-consumer-groups.sh, like any group
renaming a source connector re-ingests everything

connector "pg-orders"      offsets keyed by "pg-orders" → LSN 0/4A2B1938
delete it; create "pg-orders-v2" with identical configuration
   → no offsets exist for "pg-orders-v2"
   → the connector takes a FULL SNAPSHOT of every table, republishing millions of rows

the same applies to a fresh Connect cluster whose connect-offsets topic was not migrated

To rename safely, copy the offsets first: read the connect-offsets record for the old name and produce the same value under the new name's key (recent Connect versions expose a REST endpoint for reading and writing a connector's offsets, which is safer than hand-producing). Then create the new connector while the old one is stopped.

Sink connectors are ordinary consumer groups, which is convenient: lag is visible with the standard tooling, a sink can be reset with kafka-consumer-groups.sh --reset-offsets on group connect-<name> while the connector is stopped, and everything from the consumers lesson about rebalances and poll intervals applies.

Part 4 — Errors, Dead-Letter Queues and SMTs

By default a single bad record fails the task, and the connector stops. That is safe and rarely what you want in production — one malformed record should not stop a pipeline for hours.

# sink connector error handling (dead-letter queues are SINK-only)
errors.tolerance=all
errors.deadletterqueue.topic.name=dlq.es-sink
errors.deadletterqueue.topic.replication.factor=3
errors.deadletterqueue.context.headers.enable=true     # WHY it failed, in the record's headers
errors.log.enable=true
errors.retry.timeout=300000                            # keep retrying transient failures for 5 min

With context.headers.enable, each dead-lettered record carries headers naming the original topic, partition, offset, the connector, the stage that failed and the exception — everything needed to reprocess or to explain it. Without them, a DLQ is a topic of bytes with no story.

Single Message Transforms modify records as they pass, in a chain, without any processing framework:

transforms=route,addTs,dropInternal
transforms.route.type=org.apache.kafka.connect.transforms.RegexRouter
transforms.route.regex=(.*)\\.(.*)\\.(.*)
transforms.route.replacement=$3                        # db.schema.table → table
transforms.addTs.type=org.apache.kafka.connect.transforms.InsertField$Value
transforms.addTs.timestamp.field=ingested_at
transforms.dropInternal.type=org.apache.kafka.connect.transforms.Filter
transforms.dropInternal.predicate=isInternal
transforms.dropInternal.negate=false
SMTs are good atSMTs cannot
Renaming, routing, masking, casting, inserting fieldsJoin two streams, or look anything up
Dropping or filtering records (with predicates)Aggregate, window, or see more than one record
Flattening nested structures, extracting a field as the keyCall an external service safely (they run inline, per record)

When a transformation needs more than one record or an external lookup, that is Kafka Streams or a stream-processing job, not an SMT chain. A long chain of transforms is also a readability problem: it is configuration in a properties file, without tests or a type checker.

Part 5 — Change Data Capture with Debezium

CDC turns a database's changes into events. There are two ways to do it, and only one of them is correct in general.

Query-based (JDBC source)Log-based (Debezium)
MechanismPolls SELECT … WHERE updated_at > ?Reads the database's write-ahead log / binlog
DeletesMissed entirelyCaptured
Intermediate updates between pollsMissed; only the latest value is seenEvery change, in commit order
Load on the databaseRepeated queries, often full scans without the right indexReads the log; no query load
Rows committed out of orderCan be skipped by a timestamp cursorNot an issue: the log is the order
SetupSimple: a JDBC URLReplication user, slot or binlog access, more operational care

Debezium's shape: an initial snapshot of the tables, then continuous streaming from the log. Each change becomes an event with a standard envelope:

{
  "op": "u",                       // c=create, u=update, d=delete, r=read (snapshot)
  "before": { "id": 42, "status": "PENDING",  ... },
  "after":  { "id": 42, "status": "SHIPPED",  ... },
  "source": { "db": "shop", "table": "orders", "lsn": 123456789, "ts_ms": 1789200000000, "snapshot": "false" },
  "ts_ms":  1789200000042
}

a DELETE produces the delete event AND a tombstone (key, null) so the topic compacts correctly
ExtractNewRecordState (an SMT) unwraps the envelope to just "after", for consumers that want the row
🔑 The replication slot is the part that takes a database down. In Postgres, a logical replication slot makes the server retain WAL until the consumer has confirmed it. If the Debezium connector stops — a failed task, a Connect outage, a forgotten connector deleted in Kafka but not in the database — WAL accumulates at the database's full write rate. Disk fills, and the database stops. Monitor pg_replication_slots for slot lag, set max_slot_wal_keep_size so the server sacrifices the slot instead of itself, and delete slots for connectors you retire.

Part 6 — What to Publish: Tables or Events?

CDC makes it easy to publish a topic per table. That is the right answer for a data warehouse and the wrong answer for service-to-service integration.

raw table CDC as a public contract
  consumers depend on: column names, types, nullability, join keys, soft-delete flags
  a routine migration — renaming a column, splitting a table, adding NOT NULL — breaks every consumer
  and the owning team learns this only when someone else's service fails

outbox instead
  the service writes an EVENT ROW in the same transaction as the business change
  Debezium captures the OUTBOX table; the EventRouter SMT routes rows to topics by aggregate type
  the published contract is the event schema, which the owning team designs and versions
ApproachContractGood for
CDC of business tablesThe database schemaAnalytics, warehouses, search indexes owned by the same team
CDC of an outbox tableDesigned eventsService-to-service integration, public domain events
Direct producer in the serviceDesigned eventsSame, when the dual-write gap is handled another way

The outbox also solves the dual-write problem from the producers lesson: the event row and the business change commit together, so an event exists exactly when the change does, and the relay publishes it afterwards. Delivery is still at-least-once, so events carry a stable id and consumers deduplicate — the event design rules apply unchanged.

Interview Questions

Beginner: What is Kafka Connect, and when would you use it instead of writing a producer?

Connect is a framework and a cluster of workers for moving data between Kafka and other systems using configuration rather than code. Source connectors bring data in; sink connectors write it out. You submit a connector's configuration over a REST API, and the workers run its tasks, handling offsets, restarts, scaling and error handling.

I would use it whenever a well-maintained connector exists for the system involved — a database, S3, Elasticsearch, a cloud queue. Reimplementing that in application code means rewriting offset management, retries, dead-letter handling, schema conversion and metrics, and doing it worse.

I would write my own producer or consumer when the integration needs real business logic per record, when the data must be shaped in ways that Connect's single-message transforms cannot express, or when the only available connector is unmaintained — operating someone's abandoned connector is worse than owning a small amount of code.

The important operational detail is that a Connect cluster keeps its entire state — connector configs, source offsets and status — in three compacted Kafka topics, so workers are stateless and tasks move between them when one dies.

Beginner: What is change data capture, and why is log-based CDC preferred?

CDC turns changes in a database into a stream of events. The query-based approach polls the database for rows whose timestamp or id has increased since the last poll. The log-based approach reads the database's own write-ahead log or binlog — the same stream the database uses for replication.

Log-based is preferred because query-based misses things. Deletes leave no row to select, so they are invisible unless the application only soft-deletes. Intermediate updates between two polls are lost: if a row changes three times, the poller sees only the final value. And a timestamp cursor can skip rows committed out of order by concurrent transactions.

Log-based CDC also puts far less load on the database — it reads a log rather than running repeated queries — and it captures changes in commit order, which is what makes the resulting stream usable for replicating state.

The cost is operational: a replication user, a replication slot or binlog access, an initial snapshot of existing data, and monitoring — particularly of the replication slot, which makes the database retain log files until the connector consumes them.

Mid: A sink connector fails immediately with a DataException. How do you diagnose it?

That exception almost always means a converter mismatch: the connector is decoding the topic's bytes with a different format from the one the producer used.

I would first read the connector's status (GET /connectors/<name>/status) for the full stack trace, then check both converters in its configuration — not just the value converter. A common case is a correct value.converter with the key left on the worker's default, while the topic's keys are plain strings; the error message names converter classes and sends people to the wrong side.

Then I would confirm what is actually on the topic: consume a few records with kafka-console-consumer.sh using the deserializers I believe are right. Avro and the other registry formats start with a zero byte and a schema id, which is visible in a hex dump — the byte-level check from the schemas lesson.

Once the format is known, fix the connector's converters to match, and consider whether the pipeline should tolerate such records rather than stopping: errors.tolerance=all with a dead-letter queue and context headers turns "the connector is down" into "some records are in the DLQ with an explanation". I would not set that blindly, though: for a sink where every record matters, failing fast is the correct behaviour.

Mid: A source connector was renamed and suddenly republished millions of rows. Explain.

Source connector offsets are stored in the connect-offsets topic, keyed by the connector name together with the connector's own notion of a partition — a table, a file, a replication slot position. The new name has no offsets, so the connector starts from the beginning: for a CDC connector, a fresh snapshot of every captured table; for a JDBC source, every row.

The same thing happens when a Connect cluster is rebuilt without migrating its internal topics, or when the connect-offsets topic is recreated — which is also why those topics must be compacted and replicated like production data.

Renaming safely means moving the offsets: stop the old connector, read its offset record and write the same value under the new connector's key — recent Connect versions expose REST endpoints to read and alter a connector's offsets, which is much safer than producing to the internal topic by hand — then create the connector under the new name.

Recovering from the accidental republish depends on the consumers: if events carry stable ids and consumers are idempotent, the duplicates are absorbed, which is the argument for designing them that way. If not, the options are unpleasant — resetting downstream state, or filtering the republished range by timestamp.

Senior: A Postgres database ran out of disk. The cause was a Debezium connector. Explain the mechanism and the prevention.

Debezium reads Postgres's write-ahead log through a logical replication slot. A slot is a promise: the server keeps every WAL segment from the slot's confirmed position onwards until the consumer confirms it has processed them. That is what makes the stream lossless.

If the consumer stops — a failed task, a Connect cluster outage, a connector deleted in Kafka while its slot was left behind in the database — the slot's position stops advancing and WAL accumulates at the database's full write rate. Nothing throttles it; the write volume has nothing to do with the captured tables, because WAL covers the whole cluster. Eventually pg_wal fills the volume and Postgres stops accepting writes.

Prevention has three parts. Monitor slot lag from pg_replication_slots and alert on it long before the disk matters — this is the signal that catches every variant. Set max_slot_wal_keep_size so the server invalidates the slot rather than filling the disk: the connector then needs a new snapshot, which is a bad day, but a bad day beats an outage of the primary database. And treat slots as resources with owners: deleting a connector must include dropping its slot, and a periodic audit should list slots with no corresponding connector.

Also worth configuring is Debezium's heartbeat, which periodically emits an event and advances the slot even when the captured tables are quiet — otherwise a database whose activity is mostly in non-captured tables shows exactly this growth during a quiet weekend.

Recommendation: slot-lag alerting, max_slot_wal_keep_size as the backstop, heartbeats for low-traffic captures, and a documented connector-retirement procedure that drops the slot. The same reasoning applies to MySQL in reverse: binlog retention must exceed any plausible connector outage, or recovery means a new snapshot.

Senior: Your team wants to publish order data to four other teams. Compare CDC of the orders table with an outbox.

Both put data on Kafka reliably; they differ in what becomes the contract.

CDC of the orders table is quick to set up and needs no application changes. The contract becomes the database schema: consumers depend on column names, types, nullability and the meaning of status codes. Every migration — renaming a column, splitting a table, changing a soft-delete flag — is a breaking change to four teams, discovered when their services fail. It also exposes internals that were never meant to be public, and it publishes changes rather than business events: consumers must reconstruct "the order was paid" from a status column transition, each in their own way.

An outbox means the service writes a designed event into an outbox table in the same transaction as the business change, and Debezium captures that table, routing rows to topics with the EventRouter transform. The contract is the event schema, versioned in the registry with compatibility rules, owned by the producing team and independent of the database schema. It also solves the dual-write problem: the event exists exactly when the change does.

The costs are real: application changes, an outbox table with its own growth and cleanup, and the same CDC operational work — slot monitoring, snapshots.

Recommendation: outbox for these four teams, because the data is crossing a team boundary and the schema must be able to evolve on both sides independently. I would keep direct table CDC for same-team analytical uses — the warehouse, a search index — where the consumer can be changed in the same pull request as the migration, and say so explicitly in the topic's documentation, so nobody treats the warehouse feed as a public API.

6 (hard): Implement the outbox pattern with Debezium for order events.
Solution 
CREATE TABLE outbox (
  id            uuid PRIMARY KEY,              -- becomes the event id
  aggregatetype text NOT NULL,                 -- "orders"  → topic

One detail worth testing: the outbox table's own growth and vacuum behaviour. High-volume services insert and delete constantly, which produces significant table bloat in Postgres unless autovacuum is tuned for it. The event pipeline works long before that becomes visible, so it is worth checking at design time rather than after the first alert.

🎯 Key Takeaways

  • Connect moves data by configuration, not code, and keeps its whole state in three compacted Kafka topics.
  • Use it when a maintained connector exists; write your own client when the integration needs real logic.
  • Converter mismatches are the most common Connect failure — set key and value converters explicitly on every connector.
  • Typed sinks such as JDBC need a schema, so schemaless JSON cannot feed them.
  • Source offsets are keyed by connector name; renaming a connector re-ingests everything.
  • Sink connectors are ordinary consumer groups named connect-<name>, so standard lag and reset tooling applies.
  • The default is to fail the task on a bad record; a DLQ with context headers is a deliberate choice.
  • A dead-letter queue nobody monitors is silent data loss — alert on its rate.
  • SMTs shape single records; joins, lookups and aggregations belong in Kafka Streams.
  • Query-based CDC misses deletes and intermediate updates and can skip rows committed out of order.
  • Log-based CDC reads the WAL or binlog — snapshot first, then stream, with a before/after/op envelope.
  • A Postgres replication slot makes the server retain WAL until the connector confirms it: a stopped connector fills the disk.
  • Alert on slot lag, set max_slot_wal_keep_size, and drop slots for retired connectors.
  • Use heartbeats when captured tables are quiet, or the slot never advances on a busy database.
  • Raw table CDC makes your database schema the public contract; publish an outbox of designed events instead.
