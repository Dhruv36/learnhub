Event Design: Keys, Ordering & Payloads Data Design

What you'll master: the difference between events, commands and state, and why it decides how a topic behaves; choosing a key as the unit of ordering — and why a key built from a mutable field silently splits an entity across partitions; one topic per aggregate versus one topic per event type, and the reordering that the second choice causes; full-state versus delta payloads, and why deltas turn every duplicate into data corruption; the metadata envelope every event needs, and what belongs in headers; making consumers correct under duplicates and out-of-order arrival with version checks; and the anti-patterns — god topics, events as RPC, personal data retained forever. Prerequisites: Serialization & Schema Evolution; the System Design queues lesson covers ordering at the architecture level.

Part 1 — Events, Commands and State

Records on a topic can mean very different things, and mixing them up leads to designs that fight Kafka's model.

KindExampleMeaningConsumers
Event (a fact)OrderPlaced, PaymentCapturedSomething happened; it cannot be refusedAny number, each deciding what to do
Command (a request)ChargeCard, SendEmailPlease do this; it may fail or be refusedExactly one intended handler
State (a snapshot)Customer with every current fieldThis is the current value of an entityAnyone needing the latest value; compaction fits

Kafka is built for events and state. Facts published once and read by many, and compacted snapshots of current values, use exactly what the log is good at: fan-out, replay and ordering per key. Commands fit less well: they have one intended recipient, need a response, and often need per-message retry — queue features (see What Kafka Actually Is).

Name events in the past tense, from the domain. OrderPlaced, OrderCancelled, AddressChanged say what happened. OrderUpdated says only that a row changed; every consumer must diff the payload to find out what the business event was, and each will reconstruct it slightly differently.

event notification          "OrderPlaced {orderId}"                 consumers call back for details
event-carried state         "OrderPlaced {orderId, items, total…}"  consumers need nothing else
state snapshot (compacted)  "Order {every current field}"           latest value per key; history not kept
event sourcing              the events ARE the source of truth; state is rebuilt by replaying them

Part 2 — The Key Is the Unit of Ordering

A record's key decides its partition, and Kafka orders records only within a partition. So the key is not a label: it defines which records are guaranteed to be processed in order relative to each other. Choose it from the question "which events must never be seen out of order?"

KeyOrdered togetherRisk
Order idAll events for one orderNone for per-order logic; nothing ordered across a customer's orders
Customer idEverything a customer doesLarge customers make hot partitions
Account id (payments)Every movement on one balanceWhat balance consumers need; skew if a few accounts dominate
No keyNothingOnly for truly independent events (logs, metrics)
Random or per-request idNothing usefulLooks like ordering; guarantees none

A key must never change for the life of the entity. If the key is derived from a field that can change — an email address, a region, a status — then the entity's events move to a different partition when the field changes, and its old and new events are no longer ordered relative to each other.

key = customer email
  CustomerRegistered   key alice@old.com  → partition 3
  EmailChanged         key alice@new.com  → partition 7     ◄── the SAME customer, a different partition
  AddressChanged       key alice@new.com  → partition 7

a consumer of partition 7 can process EmailChanged before the consumer of partition 3
has processed CustomerRegistered: "email changed for a customer who does not exist yet"

on a COMPACTED topic it is worse: partition 3 keeps alice@old.com's record FOREVER,
because no later record with that key ever arrives to replace it
🔑 Key by identity, never by attribute. Use the stable, immutable id of the entity whose events must stay ordered — the order id, the account id — and put everything else in the value. If the natural id is composite, build the key the same way everywhere, from the same fields, with the same serializer; the partitions lesson shows how differently serialized keys land on different partitions.

Part 3 — One Topic per Aggregate, or per Event Type?

Should OrderPlaced, OrderPaid and OrderShipped each get their own topic, or share one orders topic? The answer follows from ordering: Kafka orders records only within one partition of one topic.

separate topics: order-placed, order-paid, order-shipped (each keyed by orderId)

  consumer reads all three topics:
    order-paid     p2: OrderPaid(o-42)        ◄── fetched first: that topic's consumer was ahead
    order-placed   p2: OrderPlaced(o-42)      ◄── arrives later
  "payment for an order that does not exist" — there is NO ordering across topics

one topic: orders (keyed by orderId), three event types in it
    orders p2: OrderPlaced(o-42), OrderPaid(o-42), OrderShipped(o-42)   ◄── always in this order
Topic per aggregate (orders)Topic per event type
Ordering across an entity's eventsYes, per keyNo
Consumer wanting one event typeReads and discards the othersReads only what it needs
SchemasSeveral types per subject: a union, or RecordNameStrategyOne schema per topic; simplest
Retention and access controlOne policy for all the aggregate's eventsPer type
Good forState machines: lifecycle events of one entityIndependent facts consumed separately

The usual answer is one topic per aggregate for events that describe one entity's lifecycle, because nearly every consumer of such events needs them in order. Separate topics are fine for facts that are genuinely independent of each other. The schema side needs care: with several event types in one topic, register them under RecordNameStrategy or TopicRecordNameStrategy, or as a union in one schema, so each type can evolve.

❌ One "events" topic for the whole company. Forty event types, three partitions, keyed inconsistently. Every consumer reads everything and discards most of it; one team's burst of events delays everyone's; retention must suit the most demanding type; access control is all or nothing; and the partition count, set for the first use case, caps every consumer's parallelism.

✅ Topics per aggregate or bounded context, each owned by one team. orders, payments, shipments — each with a key chosen for its own ordering needs, its own partition count, retention and ACLs. Exercise 6 migrates a god topic.

Part 4 — Payloads: Full State, Deltas and Notifications

The payload shape decides what consumers can do with a single event, and how they cope with duplicates and gaps.

ShapeExampleDuplicate deliveredEvent missed or out of order
DeltaBalanceChanged {account, +50}Applied twice: wrong balanceWrong forever
Full stateBalanceChanged {account, balance: 1250, version: 88}Harmless: same value written againNext event corrects it; version rejects stale ones
NotificationOrderChanged {orderId}Harmless: one extra lookupHarmless, but every consumer calls the source
Business event + stateItemAdded {orderId, item, orderTotal, version}Detectable by versionDetectable by version gap

Deltas make every at-least-once duplicate a correctness bug. Kafka delivers at least once, so duplicates are normal — after rebalances, restarts and replays. A consumer that adds deltas to a balance adds some of them twice, and there is nothing in the data to detect it unless each event carries an id that the consumer deduplicates on.

deltas:      +50, +20, (+20 again after a rebalance), -10     → consumer balance 80, true balance 60
full state:  balance=50 v1, balance=70 v2, (balance=70 v2 again), balance=60 v3 → consumer balance 60 ✔

The practical rule: publish the business event plus the resulting state and a version. Consumers that care about what happened read the event type and details; consumers that only need the current value take the state; everyone can use the version to ignore duplicates and stale records. The Spring Boot Messaging lesson shows the cost of thin notifications at scale: every consumer calling the source service back for each event.

Size limits apply. A topic accepts records up to about 1 MB by default, and large records slow every consumer that must fetch them. Full state for an order with 3,000 line items, or an event carrying a PDF, does not belong in the record: store the large part in object storage and put a reference and a checksum in the event.

Part 5 — The Envelope, Headers, and Ordering You Can Check

Every event needs the same few metadata fields, whatever its business content. Without them, consumers cannot deduplicate, order, trace or debug.

FieldPurposePayload or header?
eventId (UUID)Deduplication; idempotency keys downstreamPayload — consumers depend on it
eventTypeWhich schema and handler applyPayload (or record name); may be copied to a header for routing
occurredAtEvent time, when it happened in the businessPayload — distinct from the Kafka timestamp
aggregateId, versionEntity identity and a per-entity sequence numberPayload — correctness depends on them
correlationId, causationIdLinking an event to the request and event that caused itHeader or payload
Trace context (traceparent)Distributed tracing across servicesHeader
producer, schema versionDebugging; the registry already carries the schema idHeader

Headers are for infrastructure, payloads for meaning. Record headers (since Kafka 0.11) are key/value byte arrays outside the key and value. The schema registry does not describe or validate them, some tools and connectors drop them, and a consumer that only deserializes the value never sees them. Put anything a business decision depends on in the payload, where its schema is enforced; use headers for tracing, routing and diagnostics. (The CloudEvents specification defines a standard mapping of such metadata to Kafka headers, if you want a common convention.)

Consumers should check ordering rather than assume it. Per-key ordering in one partition covers most cases, but real systems also see replays, events for one entity arriving through two paths, and reprocessing after bugs. A per-entity version turns those into something the consumer can detect:

UPDATE orders_view
   SET status = :status, total = :total, version = :version
 WHERE order_id = :orderId AND version < :version;        -- stale or duplicate: 0 rows, ignored

INSERT INTO processed_events(event_id) VALUES (:eventId)
    ON CONFLICT DO NOTHING;                               -- for effects that are not state (emails, charges)

Note that occurredAt is not a substitute for a version. Clocks on different producers disagree, and two events in the same millisecond cannot be ordered by time at all. A version assigned by the single writer of the entity — incremented with each change, in the same transaction — is the reliable order.

Part 6 — Anti-Patterns, Including Personal Data That Never Expires

Anti-patternWhy it hurtsInstead
Events as RPC (request topic + reply topic)Correlation ids, timeouts and retries rebuilt by hand; latency of pollingHTTP or gRPC for request/response; events for the facts that result
Raw CDC of internal tables as the public contractEvery schema change in the service's database breaks consumersAn outbox of designed domain events; CDC of the outbox (see the Connect lesson)
EntityUpdated with the whole row and no reasonConsumers diff payloads to guess what happenedNamed business events carrying the resulting state
Money as floating pointRounding errors in totalsInteger minor units, or a decimal type (Avro decimal)
Timestamps without a time zone or unitSeconds read as milliseconds; local times across zonesUTC, with the unit in the schema (Avro timestamp-millis)
Personal data in long-retention or compacted topicsA deletion request cannot be honoured in an immutable logKeep personal data out, or encrypt it per person (below)

Personal data and an immutable log. Privacy law gives people the right to have their data erased, and a Kafka topic with long retention — or a compacted topic, which keeps the latest record per key forever — is designed never to forget. Three approaches exist:

1. keep it out:     events carry a customerId; personal fields live in one service's database
                    → erase there; events contain nothing personal
2. compaction:      a "customers" state topic keyed by customerId; to erase, write a TOMBSTONE
                    (key, null value) → compaction removes older values for that key
                    → but copies in OTHER topics, consumer databases and backups remain
3. crypto-shredding: personal fields encrypted with a per-customer key held in a key store;
                    events keep the ciphertext; to erase, DELETE THE KEY
                    → every copy everywhere becomes unreadable, including old events and backups

Keeping personal data out of events is the simplest and should be the default. Crypto-shredding is the answer when events genuinely must carry personal fields and are retained for a long time; its cost is a key lookup per event on both sides and a key service that becomes critical infrastructure. Tombstones alone remove data only from the one compacted topic they are written to.

Interview Questions

Beginner: How do you choose the key for a Kafka topic?

Start from ordering: the key decides the partition, and Kafka only orders records within a partition. So the key should be the identity of whatever must be processed in order — usually the entity the events are about. For order lifecycle events that is the order id; for balance movements, the account id.

Two properties matter besides ordering. The key must be stable: derived from an id that never changes, not from an attribute like an email address or a status, or the entity's events move to a new partition when the attribute changes and lose their ordering. And the key's values should be well distributed, because a key that is very common — one huge customer — makes one hot partition that no amount of scaling fixes.

There are also practical rules: every producer must build and serialize the key the same way, since the partition comes from a hash of the key's bytes; and on compacted topics the key is the identity that compaction keeps the latest value for, so it must be exactly the entity id.

If nothing needs ordering — logs, metrics — leaving the key empty spreads load most evenly.

Beginner: What should an event contain besides its business data?

A small, consistent envelope. An event id, generated once when the event is created, so consumers can detect duplicates. An event type, so consumers know which schema and handler apply. The time it occurred in business terms, which differs from when Kafka received it. The entity id and a version — a per-entity sequence number — so consumers can ignore stale and duplicate events.

Then tracing and diagnostics: a correlation id linking the event to the request that caused it, a causation id linking it to a preceding event, trace context for distributed tracing, and the producing service's name.

Where they go matters. Anything a consumer's logic depends on — the event id, type, version, occurred-at time — belongs in the payload, where the schema enforces it. Tracing and routing metadata can go in record headers, which are outside the schema and ignored by consumers that do not look for them.

A consistent envelope across all of an organisation's events is worth agreeing early; it makes generic tooling — deduplication libraries, dead-letter inspection, tracing — work for every topic.

Mid: Should each event type have its own topic?

It depends on whether consumers need those events in order with each other, because Kafka provides no ordering across topics.

For the lifecycle events of one entity — an order being placed, paid, shipped, cancelled — consumers almost always need them in order. If they were in separate topics, a consumer reading all of them could see a payment before the order exists or a cancellation before the shipment. Putting them in one topic, keyed by the order id, guarantees their order. That is the "topic per aggregate" design, and it is the right default for events about one entity.

The costs are manageable: consumers interested in only one type read and skip the others, and the schema must accommodate several types — either a union in one schema or a subject naming strategy that registers each type separately.

Separate topics per type make sense for facts that are independent, consumed by different teams, or needing different retention or access control. What I would avoid at the other extreme is one topic for all events across domains, which shares partition counts, retention and access among unrelated teams.

Mid: Why are delta events dangerous in Kafka, and what do you publish instead?

Because Kafka's normal delivery guarantee is at-least-once. Consumers see duplicates after rebalances, crashes and replays as a matter of course. A delta event — "add 50 to the balance" — is only correct if it is applied exactly once, so every duplicate becomes a wrong balance, and nothing in the resulting data reveals it.

Deltas also make gaps permanent. If an event is skipped or lost, the consumer's state is wrong from then on, with no later event to correct it.

The alternative is to publish the resulting state along with the event: "item added; order total is now 1,250; version 88". Applying a full-state event twice writes the same value twice, which is harmless. Missing one is corrected by the next. And the version lets the consumer reject anything older than what it already has, so replays and out-of-order arrivals are ignored safely.

If a consumer truly needs deltas — an analytics job summing sales — each event must carry a unique id, and the consumer must deduplicate on it, ideally in the same transaction as its own writes. So I would publish business events that carry the resulting state and a version, and treat pure deltas as a special case that requires deduplication.

Senior: Design the events for an e-commerce order domain consumed by payments, fulfilment, notifications and analytics.

Topics: one orders topic for the order aggregate, keyed by order id, carrying its lifecycle events — OrderPlaced, OrderPaid, OrderCancelled, OrderShipped — so every consumer sees one order's events in order. Payments and shipments are separate aggregates owned by other services, with their own topics. Partition count is sized from the slowest consumer's per-partition throughput with growth headroom.

Payloads: each event names what happened and carries the resulting order state that consumers need — status, line items, totals, shipping address reference — plus an envelope: event id, occurred-at, order id and a version incremented on every change. Money is in integer minor units with a currency code; timestamps are UTC with explicit units. Personal data is minimised: the shipping address is referenced by id, not embedded, because notifications and fulfilment can look it up and the event topic should not carry personal data for its whole retention.

Production: the order service writes events through a transactional outbox in the same transaction as the order row, so events exist exactly when the order change does, and the version is assigned in that transaction.

Consumption: payments and fulfilment update their own state with version checks, so duplicates and replays are ignored; notifications deduplicate on event id before sending; analytics reads the full history and can replay from the beginning. Schemas are Avro, registered from CI with FULL_TRANSITIVE compatibility, because four teams deploy independently.

Recommendation: one topic per aggregate keyed by its id, business events carrying resulting state and a version, an outbox for production, idempotent consumers by version or event id, and personal data kept out of events. That set of choices makes ordering, duplicates, replay and erasure each somebody's design decision rather than an incident.

Senior: A regulator requires that a customer's personal data can be erased on request. Your events are retained for a year. What do you do?

An immutable log with year-long retention cannot have individual records edited or removed, so the design has to make erasure possible without rewriting history.

First, reduce what is in the log. Most events do not need personal data: they can refer to a customer id and let consumers look up details from the customer service, which can erase them in one place. I would audit every event schema and remove names, emails, addresses and phone numbers wherever a reference would do. This is the cheapest and most robust measure.

Second, for data that must travel in events, crypto-shredding. Encrypt personal fields with a key specific to each customer, held in a key management service. Consumers that are allowed to see the data decrypt it. To erase a customer, delete their key: every copy of their data — in every topic, every consumer's database that stored ciphertext, and every backup — becomes unreadable. The costs are key lookups (cached) on both sides, and the key service becoming critical infrastructure that must be highly available and itself backed up with care.

Third, compacted state topics can use tombstones to remove a customer's current record, but that affects only that topic; copies consumers made elsewhere are untouched.

And the consumers matter as much as the log. Every service that stored personal data from events needs its own erasure path, triggered by a CustomerErased event.

Recommendation: keep personal data out of events by default; crypto-shred the fields that must be included; publish an erasure event that every consumer handles; and document which topics may contain personal data at all. Retention settings alone cannot satisfy the requirement.

1 (easy): Compare three candidate keys for an order-events topic.
Solution 
events per order: OrderPlaced → OrderPaid → OrderShipped (sometimes OrderCancelled)
traffic: 2M orders/day; the largest customer (a reseller) places 18% of all orders
consumers: fulfilment (per-order state machine), loyalty (points per customer, applied as deltas)
KeyOrderingDistributionVerdict
customerIdAll of a customer's orders, in orderOne partition carries 18% of trafficHot partition; fulfilment gains nothing
orderIdEach order's events, in orderEvenChoose this

Loyalty seems to want customer ordering, but look at what it does: it adds points per order. If each event carries an event id and the loyalty service deduplicates on it, the order in which different orders' points arrive does not matter — addition is commutative. The design need is per-order ordering (for fulfilment) plus idempotency (for loyalty), not per-customer ordering.

That is the general move: before accepting a hot key for "ordering", check whether the consumer actually needs order or only needs each event applied once.

Solution 
order-placed  (12 partitions, consumer group lagging 40 s during a busy hour)

6 (hard): Migrate a company-wide events topic (40 event types, 3 partitions, keyed by whatever each producer chose) to owned topics without downtime.
Solution 
inventory: list every event type, its producer, its consumers, its key, its volume
            (a consumer reading raw bytes and counting types by schema id gives the real picture)

target:     orders (key orderId, 24 partitions)   payments (key accountId, 12)
            shipments (key shipmentId, 12)        customers (key customerId, compacted, 6) ...

phase 1  a small router (Kafka Streams) reads "events" and writes each type to its new topic,
         re-keyed correctly                      → new topics exist immediately, with history if needed
phase 2  consumers move one at a time to the new topics (they see the same events, correctly keyed)
phase 3  producers move one at a time to writing their new topic directly;
         the router ignores types whose producer has moved (a per-type switch)
phase 4  when "events" has no producers and no consumers, stop the router; let retention empty it
RiskMitigation
Ordering during the switch of a producerMove a producer only when the router has caught up; for keyed types, a brief producer pause guarantees order across the cut-over
Duplicates during the overlapConsumers deduplicate on event id (add one in the router if producers lacked it)

Schema subjectsNew topics get their own subjects; register each type from CI

The router is what makes it incremental: consumers and producers move independently, each at their own pace, and the old topic stays authoritative until the last producer has moved. Keying correctly in the router means consumers get per-entity ordering on the new topics from the first day, before any producer has changed.

🎯 Key Takeaways

  • Events are facts, commands are requests, state is a snapshot; Kafka suits events and state far better than commands.
  • Name events in the past tense from the domain; OrderUpdated forces consumers to guess what happened.
  • The key defines what is ordered together: choose it from which events must never be seen out of order.
  • Key by immutable identity, never by a mutable attribute, or an entity's events split across partitions.
  • Kafka provides no ordering across topics, so one entity's lifecycle events belong in one topic keyed by its id.
  • A company-wide events topic shares partitions, retention and access among unrelated teams; use topics per aggregate or context.
  • Several event types in one topic need a union schema or a record-based subject strategy.
  • Delta payloads turn every duplicate into corruption; publish the resulting state and a version.
  • Full state fixes duplicates; a version also fixes stale and replayed events.
  • Every event needs an id, a type, an occurred-at time, and an entity version.
  • Headers are for tracing and routing; anything business logic depends on belongs in the schema-checked payload.
  • Order by a version from the single writer, not by timestamps, which skew and tie.
  • Large payloads belong in object storage, with a reference and checksum in the event.
  • Before accepting a hot key for ordering, check whether the consumer needs order or only idempotency.
  • Keep personal data out of events; crypto-shred what must be included, and publish an erasure event.
