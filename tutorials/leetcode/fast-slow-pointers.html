Fast & Slow Pointers Core Pattern

What you'll master: why two pointers moving at different speeds must meet inside a cycle, and the modular-arithmetic proof that makes it more than a trick; Floyd's algorithm including the non-obvious second phase that finds the cycle's entrance; the middle-of-list template and the one-line difference between the two middles; how to apply the pattern to problems with no linked list at all — Happy Number, Find the Duplicate Number — by recognising an implicit successor function; and when Brent's algorithm or a hash set is the better choice. Prerequisites: Two Pointers, Hashing.

Part 1 — Why Different Speeds Detect a Cycle

Two pointers traverse the same sequence, one moving one step per iteration and the other two. If the sequence ends, the fast pointer reaches the end. If it loops, the fast pointer must eventually lap the slow one.

        entrance
   1 → 2 → 3 → 4
           ↑     ↓
           7 ← 6 ← 5          slow: 1,2,3,4,5,6,7,3...
                              fast: 1,3,5,7,4,6,3...   → they meet

The proof is a one-liner once you see it. Once both pointers are inside the cycle, look at the gap between them measured along the cycle:

each iteration:  slow advances 1, fast advances 2
                 ⟹ the gap CLOSES by exactly 1 per step

the gap is at most (cycle length − 1) and strictly decreases
⟹ it must reach 0 in at most (cycle length) steps
⟹ they meet
🔑 Speeds 1 and 2 are the only pair guaranteed to work without further argument. With speeds 1 and 3, the gap closes by 2 per step — so it can jump from 1 to −1 and skip zero entirely, meaning the pointers may pass without ever landing on the same node. They still meet eventually for most cycle lengths, but not for all, and the clean "closes by exactly 1" argument is lost. Use 1 and 2 unless you have a specific reason not to.
SituationWhat happens
No cyclefast or fast.next becomes null → terminate
Cycle existsGap closes by 1 per step → guaranteed meeting
Meeting pointSomewhere inside the cycle — not necessarily the entrance
function hasCycle(head) {                       // LC 141
  let slow = head, fast = head;
  while (fast && fast.next) {                   // ← check BOTH, in this order
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) return true;
  }
  return false;
}
// O(n) time, O(1) space

The loop condition must test fast before fast.next, and both are needed: a list of even length ends with fast === null, and an odd-length list ends with fast.next === null. Testing only one crashes on the other case.

Part 2 — Finding the Cycle Entrance

Detecting a cycle is easy; finding where it starts is the part with real mathematics behind it. Floyd's algorithm does it with a second phase that looks like magic and is not.

        F              C = cycle length
   ├─────────┤   ┌──────────────┐
   head ... entrance ......... meeting point
                 └──── a ──────┘

When they meet:
  slow has travelled   F + a
  fast has travelled   F + a + kC          (k full laps, k ≥ 1)

fast moved exactly twice as far:
  2(F + a) = F + a + kC
  ⟹  F + a = kC
  ⟹  F = kC − a

So walking F steps from the head, and F steps from the meeting point,
both land on the entrance — because kC − a steps forward from the
meeting point is exactly the entrance.

function detectCycle(head) {                    // LC 142
  let slow = head, fast = head;
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) {                        // phase 1: find a meeting point
      let p = head;
      while (p !== slow) { p = p.next; slow = slow.next; }   // phase 2: same speed
      return p;                                  // the entrance
    }
  }
  return null;
}

Phase 2 moves both pointers at the same speed — one from the head, one from the meeting point. That is the detail people misremember; using speed 2 again in phase 2 does not work.

Cycle length falls out of the same meeting point, by walking a lap:

let len = 1, p = slow.next;
while (p !== slow) { p = p.next; len++; }        // back to the meeting point

Part 3 — Finding the Middle

When fast reaches the end, slow is at the halfway point — one pass, no length count, O(1) space.

function middleNode(head) {                     // LC 876
  let slow = head, fast = head;
  while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }
  return slow;                                   // SECOND middle when length is even
}

1 → 2 → 3 → 4 → 5           1 → 2 → 3 → 4
        ↑ slow (3)                  ↑ slow (3, the SECOND middle)

for the FIRST middle on even lengths, start fast one ahead:
  let slow = head, fast = head.next;   →  slow lands on 2
InitialisationEven-length resultUse for
slow = head, fast = headSecond middleSplitting for merge sort's right half
slow = head, fast = head.nextFirst middlePalindrome check, splitting into equal halves

The first-middle variant is what you want when splitting a list, because it leaves slow as the last node of the left half — so slow.next = null cleanly severs it:

function split(head) {
  let slow = head, fast = head.next;
  while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }
  const right = slow.next;
  slow.next = null;                              // cut
  return [head, right];
}

Palindrome checking composes this with in-place reversal:

function isPalindrome(head) {                   // LC 234
  let slow = head, fast = head;
  while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }

  let prev = null;                               // reverse the second half
  while (slow) { const nxt = slow.next; slow.next = prev; prev = slow; slow = nxt; }

  let a = head, b = prev;                        // compare halves
  while (b) { if (a.val !== b.val) return false; a = a.next; b = b.next; }
  return true;
}
// O(n) time, O(1) space

Compare while b is non-null, not a — on odd lengths the two halves differ in length by one, and the reversed half is the shorter one.

Part 4 — Implicit Sequences

The pattern's real power is that it needs no linked list — only a function that maps each state to exactly one successor. Any such function defines a "linked list" you can traverse.

next(x) = some deterministic function of x

finite state space + deterministic successor
⟹ the sequence MUST eventually repeat
⟹ it is a "rho" shape: a tail leading into a cycle

Happy Number (LC 202) — the successor is the sum of squared digits:

function isHappy(n) {
  const next = x => {
    let s = 0;
    while (x > 0) { const d = x % 10; s += d * d; x = Math.floor(x / 10); }
    return s;
  };
  let slow = n, fast = n;
  do {
    slow = next(slow);
    fast = next(next(fast));
  } while (slow !== fast);
  return slow === 1;                             // met at 1 → happy; else stuck in a loop
}
// O(log n) space-free cycle detection instead of a hash set

Find the Duplicate Number (LC 287) is the cleverest instance: an array of n+1 integers in the range [1, n] is read as a function next(i) = nums[i], and the duplicate value is exactly the cycle entrance.

function findDuplicate(nums) {
  let slow = nums[0], fast = nums[0];
  do { slow = nums[slow]; fast = nums[nums[fast]]; } while (slow !== fast);

  slow = nums[0];                                // phase 2: find the entrance
  while (slow !== fast) { slow = nums[slow]; fast = nums[fast]; }
  return slow;
}
// O(n) time, O(1) space — and it does NOT modify the array

nums = [1, 3, 4, 2, 2]      index: 0  1  2  3  4

0 → 1 → 3 → 2 → 4 → 2 → 4 ...
             └────┬────┘
             the cycle; its ENTRANCE is 2 = the duplicate

Why the entrance is the duplicate: two different indices hold the same value, so two arrows point at that value — and a node with two incoming arrows is exactly where a rho-shaped path closes into a cycle.

Part 5 — Alternatives and Their Trade-offs

ApproachTimeSpaceNotes
Hash set of visited nodesO(n)O(n)Simplest; finds the entrance directly
Floyd (tortoise and hare)O(n)O(1)The expected interview answer
Brent's algorithmO(n)O(1)Fewer next calls; finds length first
Marking visited nodesO(n)O(1)Mutates the input — usually disallowed

The hash-set version is worth mentioning before you write Floyd's, because it is the honest baseline and takes fifteen seconds:

function detectCycleHash(head) {
  const seen = new Set();
  for (let p = head; p; p = p.next) {
    if (seen.has(p)) return p;                   // first repeat IS the entrance
    seen.add(p);
  }
  return null;
}

Brent's algorithm uses a different idea — keep the slow pointer still and move the fast one in powers-of-two bursts:

function brent(head) {
  let power = 1, lam = 1;
  let tortoise = head, hare = head?.next;
  while (hare && hare !== tortoise) {
    if (power === lam) { tortoise = hare; power *= 2; lam = 0; }   // teleport, don't walk
    hare = hare.next;
    lam++;
  }
  return hare ? lam : null;                      // lam = cycle length
}

It makes fewer successor calls than Floyd's (useful when next() is expensive) and yields the cycle length directly. Floyd's remains the interview default because the entrance-finding phase is simpler.

❌ Memorising "reset one pointer to the head and walk both at speed 1" without knowing why. The second phase of Floyd's looks arbitrary, so it gets stored as a magic incantation — and then the interviewer asks "why does that find the entrance?", or the problem varies slightly (the sequence starts at nums[0] rather than a head node), and the candidate cannot adapt because they never had the derivation.

✅ Derive it from F = kC − a once and it stops being magic. When they meet, slow has walked F + a and fast has walked twice that, so the extra distance is whole laps: F + a = kC, hence F = kC − a. Walking F steps from the head and F steps from the meeting point therefore both terminate at the entrance. Two lines of algebra, and it survives every variant of the problem.

The n-th-from-the-end variant is a fixed gap rather than different speeds, and it is worth having as a template:

function removeNthFromEnd(head, n) {            // LC 19
  const dummy = { next: head };                  // ← handles removing the head
  let fast = dummy, slow = dummy;
  for (let i = 0; i <= n; i++) fast = fast.next; // open a gap of n+1
  while (fast) { fast = fast.next; slow = slow.next; }
  slow.next = slow.next.next;
  return dummy.next;
}

The dummy node removes the special case where the node to delete is the head — without it, that case needs its own branch, which is where the bugs go.

Interview Questions

Beginner: Detect whether a linked list has a cycle, and prove the two pointers must meet. 
function hasCycle(head) {
  let slow = head, fast = head;
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) return true;
  }
  return false;
}
// O(n) time, O(1) space

The proof: if there is no cycle, fast reaches the end and the loop terminates. If there is a cycle, both pointers eventually enter it — fast first, then slow. Once both are inside, consider the gap from fast to slow measured forward along the cycle:

per iteration: slow advances 1, fast advances 2
             ⟹ the gap shrinks by exactly 1 each step

the gap is at most C−1 (C = cycle length) and strictly decreases
⟹ it reaches 0 within C steps  ⟹  they land on the same node

"Shrinks by exactly 1" is why speeds 1 and 2 are used. With speeds 1 and 3 the gap shrinks by 2, so it can go from 1 to −1 — stepping over zero without the pointers ever coinciding.

The loop condition must be fast && fast.next in that order, because evaluating fast.next when fast is null throws. Both checks are needed: an even-length list terminates with fast === null, an odd-length one with fast.next === null.

The alternative is a hash set of visited nodes — O(n) time, O(n) space, and it returns the cycle entrance directly. Floyd's wins on space, which is what the problem is testing.

Beginner: Find the middle node of a linked list in one pass.

Advance slow by one and fast by two; when fast reaches the end, slow is halfway.

function middleNode(head) {
  let slow = head, fast = head;
  while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }
  return slow;
}
// O(n) time, O(1) space, ONE pass

Why it lands in the middle: fast covers exactly twice the distance of slow, so when fast has covered n nodes, slow has covered n/2.

odd  1→2→3→4→5 :  slow ends at 3   (the unique middle)
even 1→2→3→4   :  slow ends at 3   (the SECOND middle)

Even-length lists have two middles, and which one you get is decided by one character:

InitEven resultUse when
fast = headSecond middleYou want the start of the right half
fast = head.nextFirst middleYou want the END of the left half — for splitting

The splitting case is the practical one:

let slow = head, fast = head.next;
while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }
const right = slow.next;
slow.next = null;              // clean cut into two halves

With fast = head, slow would already be in the right half and severing there produces unequal halves — a real bug in merge-sort-on-a-linked-list implementations.

The two-pass alternative — count the length, then walk half — is also O(n) and equally correct; the one-pass version is preferred because it works on a stream where you cannot revisit.

Mid: Find the node where a cycle begins, and explain why the second phase works. 
function detectCycle(head) {
  let slow = head, fast = head;
  while (fast && fast.next) {
    slow = slow.next;
    fast = fast.next.next;
    if (slow === fast) {
      let p = head;
      while (p !== slow) { p = p.next; slow = slow.next; }   // SAME speed
      return p;
    }
  }
  return null;
}

The derivation. Let F be the distance from the head to the entrance, C the cycle length, and a the distance from the entrance to the meeting point:

at the meeting:
  slow travelled  F + a
  fast travelled  F + a + kC        (k ≥ 1 complete laps)

fast went exactly twice as far:
  2(F + a) = F + a + kC
       F + a = kC
           F = kC − a

Read the last line as a statement about walking. From the meeting point, walking kC − a steps means completing the current lap's remaining C − a steps and then k−1 further laps — landing exactly on the entrance. And kC − a equals F, the distance from the head to the entrance.

So both pointers, moving one step at a time, arrive at the entrance simultaneously.

head ──F──▶ entrance ──a──▶ meeting
              ▲                │
              └───── C−a ──────┘

p  from head:    F steps      → entrance
slow from meet:  F = kC−a     → entrance

Equal speeds in phase 2 is essential — the algebra gives a distance equality, not a ratio, so doubling one pointer's speed breaks it.

Cycle length comes free from the meeting point: walk forward counting until you return to it.

The hash-set alternative finds the entrance with no derivation at all — the first node seen twice is the entrance — at O(n) space. Mentioning it first, then giving Floyd's for O(1) space, is the strongest way to present this.

Mid: Determine whether a number is "happy" without using extra space.

Recognise the hidden linked list. Repeatedly summing squared digits is a deterministic function on a finite state space, so the sequence must eventually repeat — it is a rho shape, exactly like a linked list with a cycle.

function isHappy(n) {
  const next = x => {
    let s = 0;
    while (x > 0) { const d = x % 10; s += d * d; x = Math.floor(x / 10); }
    return s;
  };

  let slow = n, fast = n;
  do {
    slow = next(slow);
    fast = next(next(fast));
  } while (slow !== fast);

  return slow === 1;
}
// O(log n) time per step, O(1) space

The do…while is required, not stylistic: both pointers start at n, so a plain while (slow !== fast) would never execute its body.

n = 19:  19 → 82 → 68 → 100 → 1 → 1 → 1 ...     cycle {1}      → happy
n =  2:   2 →  4 → 16 →  37 → 58 → 89 → 145 → 42 → 20 → 4 ...  → not happy
                            └──────── cycle ────────┘

Why the state space is finite is worth stating, because it is what guarantees termination: for any number below 1000, the next value is at most 9² × 4 = 324. So the sequence is permanently trapped below 1000 after at most a couple of steps, and with finitely many states a deterministic sequence must repeat.

The obvious alternative is a hash set of seen values — simpler, O(1) time per step, but O(log n) space. Floyd's makes it O(1) space, which is the point of the question.

The recognition cue to generalise: any problem that repeatedly applies a deterministic transformation to a value in a finite space is a cycle-detection problem, whether or not a linked list is mentioned anywhere.

Senior: Find the duplicate in an array of n+1 integers in [1,n], without modifying it and in O(1) space.

Read the array as a function: next(i) = nums[i]. Starting from index 0 and following that function produces a sequence that must cycle, because there are n+1 slots holding values in a range of size n — so two indices share a value, giving a node with two incoming arrows, which is precisely a cycle entrance.

function findDuplicate(nums) {
  let slow = nums[0], fast = nums[0];
  do {
    slow = nums[slow];
    fast = nums[nums[fast]];
  } while (slow !== fast);

  slow = nums[0];
  while (slow !== fast) { slow = nums[slow]; fast = nums[fast]; }
  return slow;
}
// O(n) time, O(1) space, input unmodified

nums = [1, 3, 4, 2, 2]
index:  0  1  2  3  4

sequence from index 0:  1 → 3 → 2 → 4 → 2 → 4 → 2 ...
                                  └────┬────┘
                            cycle entrance = 2 = the duplicate  ✓

Why the entrance is the duplicate: the value v appears at two distinct indices i and j, so both next(i) and next(j) equal v. Two arrows into v is exactly the structure that closes a rho into a cycle, and Floyd's phase 2 finds it.

The constraints are what force this solution, and each rules out an alternative:

AlternativeRuled out by
Hash setO(1) space requirement
Sorting"Do not modify the array"
Marking nums[nums[i]] negativeAlso modifies the array
Binary search on the value range (counting ≤ mid)Valid! O(n log n) — worth mentioning

The binary-search alternative is genuinely good and worth offering: count how many values are ≤ mid; if that count exceeds mid, the duplicate lies in the lower half. O(n log n) time, O(1) space, no cleverness required — and mentioning it shows you did not just memorise the Floyd trick.

Values must be in [1, n], not [0, n], for this to work: a zero would make index 0 point to itself, creating a self-loop at the start and breaking the traversal before it reaches the real duplicate.

Senior: Compare Floyd's algorithm with the alternatives. When would you not use it?

Floyd's optimises for space at the cost of a second phase and a non-obvious proof. Whether that trade is right depends on the constraints.

ApproachTimeSpacenext() callsNotes
Hash setO(n)O(n)nSimplest; entrance found directly
FloydO(n)O(1)~3nInterview default
BrentO(n)O(1)~1.5nFewer calls; gives cycle length first
Mark visitedO(n)O(1)nDestroys the input

I would not use Floyd's when:

1. next() is expensive. Floyd's evaluates the successor roughly three times per step (once for slow, twice for fast). If each call is a network request or a costly hash, Brent's algorithm — which teleports the slow pointer instead of walking it — makes about half as many calls:

function brent(f, x0) {
  let power = 1, lam = 1, tortoise = x0, hare = f(x0);
  while (tortoise !== hare) {
    if (power === lam) { tortoise = hare; power *= 2; lam = 0; }  // teleport
    hare = f(hare);
    lam++;
  }
  return lam;                     // cycle length, obtained directly
}

2. Space is not constrained and clarity matters. In production code, a hash set is obviously correct and needs no comment explaining modular arithmetic. Floyd's O(1) space is only worth its subtlety when memory is genuinely the constraint.

3. The structure is not a function. Floyd's requires exactly one successor per state. A general graph — where a node has several outgoing edges — needs DFS with a visited set or three-colour marking; Floyd's cannot express the branching.

4. You need all cycles, not one. Floyd's finds a single cycle reachable from the start. Enumerating every cycle in a graph is a different problem entirely.

What I would actually say in an interview: "A hash set solves this in O(n) time and O(n) space, and the first repeated node is the entrance. If we need O(1) space, Floyd's gets there — detect a meeting point, then reset one pointer to the head and advance both by one, which works because F = kC − a." Leading with the simple solution and then justifying the clever one is stronger than producing Floyd's cold.

2 (easy): Verify the meeting-point mathematics empirically.
Solution

Instrument Floyd's to record F, a, C and the number of steps, then check F = kC − a across many random shapes:

function analyse(tailLen, cycleLen) {
  const total = tailLen + cycleLen;
  const nodes = Array.from({length: total}, (_, i) => ({ id: i, next: null }));
  for (let i = 0; i < total - 1; i++) nodes[i].next = nodes[i+1];
  nodes[total-1].next = nodes[tailLen];            // close the cycle
  const head = nodes[0];

  let slow = head, fast = head, steps = 0;
  do { slow = slow.next; fast = fast.next.next; steps++; } while (slow !== fast);

  const F = tailLen, C = cycleLen;
  const a = (slow.id - tailLen + C) % C;           // distance entrance → meeting
  const k = (F + a) / C;

  return { F, C, a, k, steps, integerK: Number.isInteger(k) };
}

for (const [t, c] of [[0,1],[0,5],[3,4],[5,3],[7,7],[10,3],[1,12]]) {
  const r = analyse(t, c);
  console.log(`F=${r.F} C=${r.C} a=${r.a} k=${r.k} steps=${r.steps}`,
              r.integerK && r.F === r.k * r.C - r.a ? "✓ F = kC - a" : "✗");
}

3 (medium): Solve Happy Number and Find the Duplicate with the same machinery.
Solution

Write cycle detection once, parameterised by the successor function, then apply it to both problems:

function floyd(next, start) {
  let slow = start, fast = start;
  do { slow = next(slow); fast = next(next(fast)); } while (slow !== fast);
  // phase 2: entrance
  slow = start;
  while (slow !== fast) { slow = next(slow); fast = next(fast); }
  return slow;
}

// Happy Number — we only need the cycle's contents, not its entrance
function isHappy(n) {
  const next = x => {
    let s = 0;
    while (x > 0) { const d = x % 10; s += d*d; x = Math.floor(x/10); }
    return s;
  };
  let slow = n, fast = n;
  do { slow = next(slow); fast = next(next(fast)); } while (slow !== fast);
  return slow === 1;
}

4 (medium): Check a linked-list palindrome in O(1) space.
Solution

Three phases: find the middle, reverse the second half, compare — all in place.

function isPalindrome(head) {
  if (!head || !head.next) return true;

  // 1. middle
  let slow = head, fast = head;
  while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }

  // 2. reverse from slow
  let prev = null, cur = slow;
  while (cur) { const nxt = cur.next; cur.next = prev; prev = cur; cur = nxt; }

  // 3. compare
  let a = head, b = prev;
  let ok = true;
  while (b) { if (a.val !== b.val) { ok = false; break; } a = a.next; b = b.next; }
  return ok;
}

const build = vs => { const n = vs.map(v => ({val:v, next:null}));
  for (let i=0;i<n.length-1;i++) n[i].next = n[i+1]; return n[0] ?? null; };

for (const vs of [[1,2,2,1],[1,2,3,2,1],[1,2],[1],[1,2,3],[],[1,1]]) {
  console.log(JSON.stringify(vs), isPalindrome(build(vs)));
}

The critical detail is looping on b, not a. On odd lengths the two halves are unequal:

[1,2,3,2,1]:  slow lands on 3
  reversed second half: 1 → 2 → 3   (length 3)
  first half from head: 1 → 2 → 3 → 2 → 1   (still the full list!)

looping on `b` compares exactly 3 pairs: (1,1), (2,2), (3,3)  ✓
looping on `a` would run past the end of `b` → null dereference  ✗

Note that the first half is not truncated — after reversal, head still walks into the middle. That is fine because b is the shorter list and controls the loop, but it is why the comparison must be driven by b.

A production version would restore the list, since mutating the caller's data is a real side effect:

function isPalindromeRestoring(head) {
  if (!head || !head.next) return true;
  let slow = head, fast = head;
  while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }

  const reverse = node => {
    let prev = null, cur = node;
    while (cur) { const n = cur.next; cur.next = prev; prev = cur; cur = n; }
    return prev;
  };

  const secondHalf = reverse(slow);
  let a = head, b = secondHalf, ok = true;
  while (b) { if (a.val !== b.val) { ok = false; break; } a = a.next; b = b.next; }
  reverse(secondHalf);                                  // ← put it back
  return ok;
}

5 (hard): Implement Brent's algorithm and compare call counts with Floyd's.
Solution

Both find cycles in O(1) space; they differ in how many times they invoke the successor function, which matters when that call is expensive.

function floydCount(f, x0) {
  let calls = 0;
  const next = x => { calls++; return f(x); };

  let slow = next(x0), fast = next(next(x0));
  while (slow !== fast) { slow = next(slow); fast = next(next(fast)); }

  let mu = 0;                                    // tail length
  slow = x0;
  while (slow !== fast) { slow = next(slow); fast = next(fast); mu++; }

  let lam = 1, p = next(slow);                   // cycle length
  while (p !== slow) { p = next(p); lam++; }

  return { mu, lam, calls };
}

function brentCount(f, x0) {
  let calls = 0;
  const next = x => { calls++; return f(x); };

  let power = 1, lam = 1;
  let tortoise = x0, hare = next(x0);
  while (tortoise !== hare) {
    if (power === lam) { tortoise = hare; power *= 2; lam = 0; }   // teleport
    hare = next(hare);
    lam++;
  }

  tortoise = x0; hare = x0;
  for (let i = 0; i < lam; i++) hare = next(hare);     // open a gap of lam
  let mu = 0;
  while (tortoise !== hare) { tortoise = next(tortoise); hare = next(hare); mu++; }

  return { mu, lam, calls };
}

6 (hard): Solve Circular Array Loop, where the cycle must satisfy extra conditions.
Solution

The problem (LC 457): in a circular array, nums[i] is a jump offset. Find whether a cycle exists that (a) has length greater than 1 and (b) moves in a single direction — all positive or all negative.

Plain Floyd's is insufficient because it finds any cycle; the extra conditions must be enforced during traversal.

function circularArrayLoop(nums) {
  const n = nums.length;
  const next = i => (((i + nums[i]) % n) + n) % n;      // wrap in both directions

  for (let start = 0; start < n; start++) {
    if (nums[start] === 0) continue;

    let slow = start, fast = start;
    const dir = nums[start] > 0;

    // advance only while the direction stays consistent
    while (true) {
      slow = next(slow);
      if ((nums[slow] > 0) !== dir) break;              // direction changed → invalid

      fast = next(fast);
      if ((nums[fast] > 0) !== dir) break;
      fast = next(fast);
      if ((nums[fast] > 0) !== dir) break;

      if (slow === fast) {
        if (slow === next(slow)) break;                 // length-1 cycle → invalid
        return true;
      }
    }

    // mark this whole path as dead so we never rescan it
    let p = start;
    const d = nums[start];
    while (nums[p] !== 0 && (nums[p] > 0) === (d > 0)) {
      const nxt = next(p);
      nums[p] = 0;
      p = nxt;
    }
  }
  return false;
}

console.log(circularArrayLoop([2,-1,1,2,2]));    // true
console.log(circularArrayLoop([-1,-2,-3,-4,-5])); // true
console.log(circularArrayLoop([-1,2]));           // false  (direction changes)
console.log(circularArrayLoop([-2,1,-1,-2,-2]));  // false
console.log(circularArrayLoop([1,1,1,1,1]));      // true
console.log(circularArrayLoop([1]));              // false  (length-1 cycle)
console.log(circularArrayLoop([2,2,2,2]));        // true

Three things go beyond textbook Floyd's:

RequirementHandling
Cycle length > 1slow === next(slow) detects a self-loop → reject
Single directionCheck the sign at every step; break on a change
Every start must be triedOuter loop, plus marking to keep it O(n)

The marking pass is what keeps it linear. Without it, trying every start index re-walks the same paths and the algorithm becomes O(n²). Zeroing out a failed path means each element is visited a constant number of times overall — the same amortised argument as the sliding window.

The modulo must be normalised — ((i + nums[i]) % n + n) % n — because negative offsets produce negative remainders in JavaScript, exactly as in subarrays divisible by k.

The transferable lesson: Floyd's detects that a cycle exists. When the problem constrains which cycles count, those constraints have to be checked during traversal — and each check needs its own break condition, because a cycle that violates a constraint must not be reported even though the pointers genuinely met.

🎯 Key Takeaways

  • Two pointers at speeds 1 and 2 must meet inside a cycle, because the gap between them closes by exactly 1 each step.
  • Speeds 1 and 3 close the gap by 2, which can skip zero — use 1 and 2 unless you have a reason not to.
  • Always write while (fast && fast.next) in that order; both checks are needed for even and odd lengths.
  • The meeting point is somewhere inside the cycle, not its entrance — finding the entrance needs a second phase.
  • Floyd's phase 2 works because F = kC − a: walking F steps from the head and F from the meeting point both land on the entrance.
  • Phase 2 moves both pointers at equal speed — the algebra is a distance equality, not a ratio.
  • When fast reaches the end, slow is at the middle; fast = head.next gives the first middle, fast = head the second.
  • Use the first-middle variant when splitting a list, or the halves come out unequal.
  • Palindrome checking is middle + reverse + compare in O(1) space, and the comparison loop must be driven by the reversed (shorter) half.
  • The pattern needs no linked list — only a deterministic successor function on a finite state space, which always produces a rho shape.
  • Happy Number and Find the Duplicate are cycle detection in disguise; the latter's cycle entrance is the duplicated value.
  • Find the Duplicate requires values in [1, n]; a zero creates a self-loop at index 0 and breaks the traversal.
  • Use do…while for implicit sequences, since both pointers start equal and a plain while never runs.
  • A hash set solves all of these in O(n) space with no derivation, and finds the entrance directly — mention it as the baseline before giving Floyd's.
  • Brent's algorithm makes roughly half as many successor calls and yields the cycle length first; prefer it when next() is expensive.
  • Floyd's requires exactly one successor per state — a graph with branching needs DFS with a visited set instead.
  • Use a dummy node for "remove the n-th from the end", with a gap of n+1, so deleting the head needs no special case.
  • When a problem constrains which cycles count, those conditions must be checked during traversal, not after the pointers meet.
