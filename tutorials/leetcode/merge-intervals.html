Merge Intervals Core Pattern

What you'll master: why sorting by start makes merging a single linear sweep, and the proof that no earlier interval can ever reappear; the overlap test and its off-by-one variants for closed versus half-open intervals; the sweep-line technique that answers "maximum concurrent" problems by separating endpoints into events; why a min-heap of end times solves Meeting Rooms II and when sorting by end instead of start is the correct greedy choice; and how insert, erase and interval-intersection problems reduce to the same three-case skeleton. Prerequisites: Two Pointers, Big-O.

Part 1 — Sort by Start, Then Sweep

Interval problems are almost always "sort, then make one pass". The sort is what converts a pairwise-comparison problem into a linear one.

unsorted:  [1,3] [8,10] [2,6] [15,18]
                → any pair might overlap: O(n²) comparisons

sorted by start:  [1,3] [2,6] [8,10] [15,18]
                → only ADJACENT intervals can merge: O(n) sweep

function merge(intervals) {                        // LC 56
  if (!intervals.length) return [];
  intervals.sort((a, b) => a[0] - b[0]);           // by START

  const out = [intervals[0].slice()];
  for (let i = 1; i < intervals.length; i++) {
    const last = out[out.length - 1], cur = intervals[i];
    if (cur[0] <= last[1]) {                       // overlap → absorb
      last[1] = Math.max(last[1], cur[1]);         // ← MAX, not cur[1]
    } else {
      out.push(cur.slice());                       // disjoint → start a new run
    }
  }
  return out;
}
// O(n log n) time (the sort), O(n) output
🔑 Why sorting by start is sufficient, stated as a proof: after sorting, every later interval has a start ≥ the current one. So if the next interval does not overlap the merged block we are building, no interval after it can either — its start is even larger. That means the merged block is final and can be emitted, which is exactly what licenses a single pass with no backtracking. Being able to say this is what separates "I remember the code" from "I understand the pattern".

Math.max on the end is the bug people write. A fully-contained interval must not shrink the block:

[1, 10] then [2, 3]

with max:  end stays 10       → [1,10]   ✓
without:   end becomes 3      → [1,3]    ✗ silently loses coverage
RelationshipExampleAction
Disjoint[1,3] and [5,8]Emit the first, start a new block
Touching[1,3] and [3,8]Merge if intervals are closed
Partial overlap[1,5] and [3,8]Merge → [1,8]
Contained[1,10] and [3,5]Merge → [1,10] (keep the max end)

Part 2 — The Overlap Test

Two intervals overlap when each starts before the other ends. The exact comparison depends on whether the endpoints are inclusive.

overlap(a, b)  ⟺  a.start <= b.end  AND  b.start <= a.end        [closed]
overlap(a, b)  ⟺  a.start <  b.end  AND  b.start <  a.end        [half-open)

intersection = [max(a.start, b.start), min(a.end, b.end)]
             valid only if start <= end

a: ├────────┤
b:      ├────────┤
        └───┘  intersection = [max(starts), min(ends)]

The closed/half-open distinction decides whether touching counts:

DomainConventionDo [1,3] and [3,5] overlap?
Merging number rangesClosed [a, b]Yes — merge to [1,5]
Meeting rooms, time slotsHalf-open [a, b)No — one ends as the other starts
Array index rangesHalf-openNo

Ask which convention applies before writing the comparison. "Does a meeting ending at 3 conflict with one starting at 3?" takes five seconds and decides between < and <= in three places.

Part 3 — Sweep Line and Event Counting

When the question is "how many are active at once", stop thinking about intervals and start thinking about events: separate every interval into a start (+1) and an end (−1), sort all events by time, and sweep.

meetings: [0,30] [5,10] [15,20]

events:  (0,+1) (5,+1) (10,-1) (15,+1) (20,-1) (30,-1)
running:    1      2      1       2       1       0
                   ↑                ↑
                 peak concurrency = 2

function minMeetingRooms(intervals) {              // LC 253
  const starts = intervals.map(i => i[0]).sort((a,b) => a-b);
  const ends   = intervals.map(i => i[1]).sort((a,b) => a-b);

  let rooms = 0, best = 0, e = 0;
  for (let s = 0; s < starts.length; s++) {
    while (e < ends.length && ends[e] <= starts[s]) { rooms--; e++; }  // free rooms first
    rooms++;
    best = Math.max(best, rooms);
  }
  return best;
}
// O(n log n) time, O(n) space

Process ends before starts at the same timestamp. With half-open intervals, a meeting ending at 10 frees its room for one starting at 10 — the <= in the inner while is what encodes that, and changing it to < over-counts rooms.

The heap formulation is equivalent and often easier to reason about:

function minMeetingRoomsHeap(intervals) {
  intervals.sort((a, b) => a[0] - b[0]);
  const heap = new MinHeap();                      // holds END times of active meetings
  for (const [s, e] of intervals) {
    if (heap.size() && heap.peek() <= s) heap.pop();  // the earliest-ending room is free
    heap.push(e);
  }
  return heap.size();                              // rooms in use at the peak
}

The heap holds end times, and its size is the room count. Only the earliest-ending meeting can possibly have finished, so checking the minimum is sufficient — see Heaps.

Part 4 — Sort by End: The Greedy Exception

One family of interval problems requires sorting by end, and using start there gives wrong answers.

function eraseOverlapIntervals(intervals) {        // LC 435
  if (!intervals.length) return 0;
  intervals.sort((a, b) => a[1] - b[1]);           // by END

  let kept = 1, lastEnd = intervals[0][1];
  for (let i = 1; i < intervals.length; i++) {
    if (intervals[i][0] >= lastEnd) {              // no overlap → keep it
      kept++;
      lastEnd = intervals[i][1];
    }
  }
  return intervals.length - kept;
}

The exchange argument: to fit as many non-overlapping intervals as possible, always take the one that finishes earliest — it leaves the most room for everything after it. Any optimal solution can have its first interval swapped for the earliest-ending one without reducing the count, so the greedy choice is safe.

[1,100] [2,3] [3,4]

sort by START: take [1,100] first → blocks everything → 1 interval    ✗
sort by END:   take [2,3], then [3,4]                 → 2 intervals   ✓
Sort byUse forWhy
StartMerging, inserting, counting overlapsAdjacent-only merging; a single sweep suffices
EndMaximum non-overlapping set, minimum removals, arrow shotsFinishing earliest leaves maximum room

Minimum Number of Arrows (LC 452) is the same greedy with the sign of the comparison flipped — shoot at the earliest end, which pops every balloon that started before it.

Part 5 — Insert, Intersect and Erase

Inserting into an already-sorted list is a three-phase sweep, and writing it as three explicit loops keeps it correct:

function insert(intervals, newInterval) {          // LC 57
  const out = [];
  let i = 0, n = intervals.length;
  const [ns, ne] = [newInterval[0], newInterval[1]];
  let s = ns, e = ne;

  while (i < n && intervals[i][1] < s) out.push(intervals[i++]);   // 1. entirely before

  while (i < n && intervals[i][0] <= e) {                          // 2. overlapping
    s = Math.min(s, intervals[i][0]);
    e = Math.max(e, intervals[i][1]);
    i++;
  }
  out.push([s, e]);

  while (i < n) out.push(intervals[i++]);                          // 3. entirely after
  return out;
}
// O(n) — no sort needed, the input is already sorted

Interval intersection of two sorted lists is a two-pointer merge — see Two Pointers:

function intervalIntersection(A, B) {              // LC 986
  const out = [];
  let i = 0, j = 0;
  while (i < A.length && j < B.length) {
    const lo = Math.max(A[i][0], B[j][0]);
    const hi = Math.min(A[i][1], B[j][1]);
    if (lo <= hi) out.push([lo, hi]);              // non-empty intersection

    if (A[i][1] < B[j][1]) i++;                    // advance whichever ENDS first
    else j++;
  }
  return out;
}
// O(n + m)

Advance the interval that ends first, because it cannot intersect anything further along the other list — the same discard argument as converging two pointers.

Part 6 — Recognition and Pitfalls

"maximum number of non-overlapping…"Sort by end, greedy

Many range updates, read onceDifference array

The difference-array connection is worth making explicit. "Car Pooling" and "Corporate Flight Bookings" are interval problems whose answer is an array rather than a merged list — and there, difference arrays beat sorting because each update is O(1).

❌ Sorting by start for every interval problem. It is the right choice for merging, inserting and counting overlaps, so it becomes automatic — and then a problem asks for the maximum number of non-overlapping intervals, the candidate sorts by start, greedily takes the first, and a single wide interval like [1,100] swallows the whole answer. The code looks right, the sample passes, and the result is off by an arbitrary amount on any input containing one long interval.

✅ Decide from what is being optimised. Building merged blocks or scanning in time order means sort by start. Selecting the largest set of mutually non-overlapping intervals means sort by end, because finishing earliest leaves the most room for everything after — and that exchange argument is exactly what the interviewer wants to hear you state.

Interview Questions

Beginner: Merge all overlapping intervals. Why is sorting by start enough? 
function merge(intervals) {
  if (!intervals.length) return [];
  intervals.sort((a, b) => a[0] - b[0]);
  const out = [intervals[0].slice()];
  for (let i = 1; i < intervals.length; i++) {
    const last = out[out.length - 1], cur = intervals[i];
    if (cur[0] <= last[1]) last[1] = Math.max(last[1], cur[1]);
    else out.push(cur.slice());
  }
  return out;
}
// O(n log n) time — dominated by the sort

Why one pass suffices: after sorting, every remaining interval has a start greater than or equal to the current one. So if the next interval does not overlap the block being built, nothing after it can either — later starts are even larger. The block is therefore final and can be emitted with no possibility of a later interval reopening it.

[1,3] [2,6] [8,10] [15,18]

block [1,3];  2 ≤ 3  → merge → [1,6]
block [1,6];  8 > 6  → emit [1,6], start [8,10]
block [8,10]; 15 > 10 → emit [8,10], start [15,18]
→ [[1,6],[8,10],[15,18]]

Math.max is not optional:

[1,10] then [2,3]
  with max: end stays 10 → [1,10]  ✓
  without:  end becomes 3 → [1,3]  ✗ coverage silently lost

The <= assumes closed intervals, so [1,3] and [3,5] merge into [1,5]. If the intervals were half-open — meeting times, for instance — the test would be < and they would stay separate. Asking which convention applies is a fifteen-second question worth asking.

.slice() avoids mutating the caller's arrays, which matters because the merge writes into last[1] in place.

Beginner: How do you test whether two intervals overlap, and what is their intersection?

Two intervals overlap when each begins before the other ends:

overlap(a, b)  ⟺  a[0] <= b[1]  &&  b[0] <= a[1]        [closed]

It is easier to reason about the negation: they do not overlap only when one finishes entirely before the other starts — a[1] < b[0] || b[1] < a[0]. Negating that gives the test above, which is why the two-condition form is correct rather than arbitrary.

a: ├────────┤
b:      ├────────┤
        └───┘   intersection

intersection = [max(a[0], b[0]), min(a[1], b[1])]
valid iff  max(starts) <= min(ends)

function intersect(a, b) {
  const lo = Math.max(a[0], b[0]);
  const hi = Math.min(a[1], b[1]);
  return lo <= hi ? [lo, hi] : null;
}
console.log(intersect([1,5], [3,8]));    // [3,5]
console.log(intersect([1,3], [3,8]));    // [3,3]  — touching, closed
console.log(intersect([1,2], [5,8]));    // null
console.log(intersect([1,10], [3,4]));   // [3,4]  — containment

The strictness depends on the convention:

ConventionTest[1,3] vs [3,5]
Closed [a, b]<=Overlap at the point 3
Half-open [a, b)<No overlap

Meeting-room problems are almost always half-open — a meeting from 9 to 10 does not conflict with one from 10 to 11 — while numeric range merging is usually closed. Getting this backwards produces off-by-one answers that look almost right.

Mid: Find the minimum number of meeting rooms required.

The answer is the maximum number of meetings active simultaneously. Two equivalent formulations:

1. Sweep line — separate the endpoints into events:

function minMeetingRooms(intervals) {
  const starts = intervals.map(i => i[0]).sort((a,b) => a-b);
  const ends   = intervals.map(i => i[1]).sort((a,b) => a-b);
  let rooms = 0, best = 0, e = 0;
  for (let s = 0; s < starts.length; s++) {
    while (e < ends.length && ends[e] <= starts[s]) { rooms--; e++; }
    rooms++;
    best = Math.max(best, rooms);
  }
  return best;
}

Sorting starts and ends independently is the key move, and it looks wrong at first — the pairing between them is destroyed. It is valid because we only ever ask "how many have started by time t" and "how many have finished by time t"; which specific meeting occupies which room never matters.

2. Min-heap of end times:

function minMeetingRoomsHeap(intervals) {
  intervals.sort((a,b) => a[0] - b[0]);
  const heap = new MinHeap();
  for (const [s, e] of intervals) {
    if (heap.size() && heap.peek() <= s) heap.pop();   // reuse the freed room
    heap.push(e);
  }
  return heap.size();
}

The heap holds the end times of currently-occupied rooms, so its size is the room count. Only the earliest-ending meeting can possibly be free, which is why a min-heap — checking just the minimum — is sufficient and a scan of all rooms is unnecessary.

[[0,30],[5,10],[15,20]]

[0,30]:  heap empty      → push 30   → heap [30],     rooms 1
[5,10]:  peek 30 > 5     → push 10   → heap [10,30],  rooms 2
[15,20]: peek 10 ≤ 15    → pop, push 20 → heap [20,30], rooms 2
answer 2  ✓

The <= encodes half-open intervals — a meeting ending at 10 frees the room for one starting at 10. With closed intervals it would be <, and the answer would differ by one on touching meetings.

Both are O(n log n); the heap version generalises better when you need to know which room each meeting used.

Mid: Find the minimum number of intervals to remove so the rest are non-overlapping.

Equivalently: keep the maximum number of non-overlapping intervals, then subtract. This is the classic activity-selection greedy, and it requires sorting by end.

function eraseOverlapIntervals(intervals) {
  if (!intervals.length) return 0;
  intervals.sort((a, b) => a[1] - b[1]);          // by END
  let kept = 1, lastEnd = intervals[0][1];
  for (let i = 1; i < intervals.length; i++) {
    if (intervals[i][0] >= lastEnd) { kept++; lastEnd = intervals[i][1]; }
  }
  return intervals.length - kept;
}
// O(n log n)

The exchange argument, which is what makes it provably optimal: let the greedy pick interval g (the earliest-ending) and suppose some optimal solution starts with a different interval o. Since g ends no later than o, replacing o with g cannot conflict with anything the optimal solution chose afterwards. So there is an optimal solution containing g, and the argument repeats on the remainder.

Sorting by start fails, and the counterexample is one line:

[[1,100], [2,3], [3,4]]

by START: take [1,100] → nothing else fits → kept 1 → remove 2   ✗
by END:   take [2,3], then [3,4]           → kept 2 → remove 1   ✓

The greedy by start is seduced by an interval that happens to begin early and runs forever; the greedy by end never is, because "finishes soonest" is exactly the property that preserves future options.

The same greedy in different clothing:

ProblemVariation
Non-overlapping Intervals (435)Count removals
Minimum Arrows to Burst Balloons (452)Shoot at each chosen end; use > not >= (touching balloons pop together)
Maximum Length of Pair Chain (646)Same greedy, count kept instead

The arrows variant flips one comparison because balloons that merely touch are burst by the same arrow — a good example of how the closed/half-open question changes the code without changing the algorithm.

Senior: Insert an interval into a sorted, non-overlapping list and merge as needed.

The input is already sorted, so re-sorting would waste O(n log n). A three-phase sweep is O(n) and, more importantly, is easier to get right than a single loop with branching.

function insert(intervals, newInterval) {
  const out = [];
  let i = 0;
  const n = intervals.length;
  let [s, e] = newInterval;

  // 1. everything entirely BEFORE the new interval
  while (i < n && intervals[i][1] < s) out.push(intervals[i++]);

  // 2. everything OVERLAPPING — absorb into [s, e]
  while (i < n && intervals[i][0] <= e) {
    s = Math.min(s, intervals[i][0]);
    e = Math.max(e, intervals[i][1]);
    i++;
  }
  out.push([s, e]);

  // 3. everything entirely AFTER
  while (i < n) out.push(intervals[i++]);

  return out;
}
// O(n) time, O(n) output

Why three loops rather than one: a single loop needs a branch for each of the three cases plus state tracking whether the new interval has been emitted yet, and that state is where the bugs live. Three sequential loops make each phase's condition explicit, and the phases cannot interleave because the input is sorted.

intervals = [[1,3],[6,9]], new = [2,5]

phase 1: [1,3][1] = 3, not < 2 → nothing emitted
phase 2: [1,3] overlaps → s=1, e=5
         [6,9]: 6 > 5 → stop
         push [1,5]
phase 3: push [6,9]
→ [[1,5],[6,9]]  ✓

Edge cases the structure handles automatically:

CaseResult
New interval before everythingPhase 1 empty, phase 2 empty, push, then phase 3
New interval after everythingPhase 1 consumes all, push at the end
Empty inputAll loops skip; output is just the new interval
New interval swallows everythingPhase 2 absorbs them all

The comparison in phase 1 is intervals[i][1] < s — strictly less, so an interval ending exactly at s falls into phase 2 and merges. With half-open intervals it would be <= and it would stay separate.

If insertions were repeated — thousands of inserts into the same structure — I would switch to a balanced BST or an interval tree keyed by start, giving O(log n) per insert rather than O(n). The array sweep is right for a single insertion, which is what the problem asks.

Senior: Design a system to find the busiest period across millions of time ranges.

The core algorithm is a sweep line; the engineering is in how the data arrives and whether it fits in memory.

1. In-memory baseline — events, sorted:

function busiestPeriod(intervals) {
  const events = [];
  for (const [s, e] of intervals) { events.push([s, 1]); events.push([e, -1]); }
  events.sort((a, b) => a[0] - b[0] || a[1] - b[1]);   // ← -1 before +1 at equal times

  let cur = 0, best = 0, bestStart = null;
  for (const [t, delta] of events) {
    cur += delta;
    if (cur > best) { best = cur; bestStart = t; }
  }
  return { peak: best, at: bestStart };
}
// O(n log n) time, O(n) space

The tie-break a[1] - b[1] puts −1 before +1 at identical timestamps, which encodes half-open intervals: something ending at t frees capacity for something starting at t. Reversing it counts a spurious extra unit of concurrency, and it is the single most common bug in sweep-line code.

2. When timestamps are bounded integers — a difference array beats sorting:

function busiestBounded(intervals, maxT) {
  const diff = new Int32Array(maxT + 2);
  for (const [s, e] of intervals) { diff[s]++; diff[e]--; }   // O(1) per interval
  let cur = 0, best = 0, at = 0;
  for (let t = 0; t <= maxT; t++) {
    cur += diff[t];
    if (cur > best) { best = cur; at = t; }
  }
  return { peak: best, at };
}
// O(n + maxT) — no sort at all

For timestamps in seconds over a day (86,400 slots) this is dramatically faster than sorting millions of events, and it is the same difference-array technique.

3. Scaling beyond memory:

ConstraintApproach
Data exceeds RAMExternal sort of events, then a streaming sweep (O(1) memory)
Distributed inputPartition by time bucket; each worker sweeps locally; combine with the boundary carry-in
Streaming, live answerDifference array over a fixed time grid + running maximum
Queries over arbitrary windowsPrefix sums of the difference array, or a segment tree

The partitioning detail worth stating: an interval spanning two buckets must contribute to both, so each worker needs the count of intervals already active at its bucket's start. That carry-in is one number per boundary, computed by a cheap first pass, and forgetting it is what makes naive parallel sweeps wrong.

What I would build first: the bounded difference array, since real timestamps are almost always quantised to seconds or minutes and the sort is pure overhead. I would only move to event-sorting if timestamps were genuinely continuous or the range were unbounded.

function coveredPoints(intervals) {
  const set = new Set();

function mergeA(iv) {

// (b)
function eraseB(iv) {
  iv.sort((a,b) => a[0] - b[0]);
  let kept = 1, end = iv[0][1];
  for (let i = 1; i < iv.length; i++)
    if (iv[i][0] >= end) { kept++; end = iv[i][1]; }
  return iv.length - kept;
}

// (c)
function roomsC(iv) {
  const st = iv.map(x=>x[0]).sort((a,b)=>a-b);
  const en = iv.map(x=>x[1]).sort((a,b)=>a-b);
  let rooms = 0, best = 0, e = 0;

    while (e < en.length && en[e] < st[s]) { rooms--; e++; }
    rooms++; best = Math.max(best, rooms);

// (d)

3 (medium): Compare sweep line and min-heap for meeting rooms.
Solution 
class MinHeap {
  constructor() { this.a = []; }
  size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(v) {
    this.a.push(v);
    let i = this.a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.a[p] <= this.a[i]) break;
      [this.a[p], this.a[i]] = [this.a[i], this.a[p]]; i = p;
    }
  }
  pop() {
    const top = this.a[0], last = this.a.pop();
    if (this.a.length) {
      this.a[0] = last;
      let i = 0;
      for (;;) {
        const l = 2*i+1, r = 2*i+2; let m = i;
        if (l < this.a.length && this.a[l] < this.a[m]) m = l;
        if (r < this.a.length && this.a[r] < this.a[m]) m = r;
        if (m === i) break;
        [this.a[m], this.a[i]] = [this.a[i], this.a[m]]; i = m;
      }
    }
    return top;
  }
}

function roomsSweep(iv) {
  const st = iv.map(x=>x[0]).sort((a,b)=>a-b);
  const en = iv.map(x=>x[1]).sort((a,b)=>a-b);
  let rooms = 0, best = 0, e = 0;
  for (let s = 0; s < st.length; s++) {
    while (e < en.length && en[e] <= st[s]) { rooms--; e++; }
    rooms++; best = Math.max(best, rooms);
  }
  return best;
}

function roomsHeap(iv) {
  const s = iv.map(x=>x.slice()).sort((a,b)=>a[0]-b[0]);
  const h = new MinHeap();
  for (const [start, end] of s) {
    if (h.size() && h.peek() <= start) h.pop();
    h.push(end);
  }
  return h.size();
}

function roomsBrute(iv) {                       // check every timestamp
  let best = 0;
  const times = [...new Set(iv.flat())];
  for (const t of times) {
    let c = 0;
    for (const [a,b] of iv) if (a <= t && t < b) c++;   // half-open
    best = Math.max(best, c);
  }
  return best;
}

4 (medium): Prove that sorting by end is required for the greedy.
Solution

Implement both greedies plus an exhaustive reference, then measure how often sorting by start is wrong:

function maxNonOverlapByEnd(iv) {
  if (!iv.length) return 0;
  const s = iv.map(x=>x.slice()).sort((a,b) => a[1]-b[1]);
  let kept = 1, end = s[0][1];
  for (let i = 1; i < s.length; i++)
    if (s[i][0] >= end) { kept++; end = s[i][1]; }
  return kept;
}

function maxNonOverlapByStart(iv) {
  if (!iv.length) return 0;
  const s = iv.map(x=>x.slice()).sort((a,b) => a[0]-b[0]);
  let kept = 1, end = s[0][1];
  for (let i = 1; i < s.length; i++)
    if (s[i][0] >= end) { kept++; end = s[i][1]; }
  return kept;
}

function maxNonOverlapBrute(iv) {               // try every subset
  const n = iv.length;
  let best = 0;
  for (let mask = 0; mask < (1 << n); mask++) {
    const pick = [];
    for (let i = 0; i < n; i++) if (mask & (1 << i)) pick.push(iv[i]);
    pick.sort((a,b) => a[0]-b[0]);
    let ok = true;
    for (let i = 1; i < pick.length; i++) if (pick[i][0] < pick[i-1][1]) { ok = false; break; }
    if (ok) best = Math.max(best, pick.length);
  }
  return best;
}

5 (hard): Build a sweep-line engine that answers several interval questions.
Solution

One event stream, several answers — the sweep is the same and only the accumulator changes:

function sweep(intervals) {
  const events = [];
  for (const [s, e] of intervals) { events.push([s, +1]); events.push([e, -1]); }
  events.sort((a, b) => a[0] - b[0] || a[1] - b[1]);   // -1 before +1 at ties

  let cur = 0, peak = 0, peakAt = null;
  let coveredLength = 0, lastT = null, gaps = [];
  const merged = [];
  let blockStart = null;

  for (const [t, d] of events) {
    if (cur > 0 && lastT !== null) coveredLength += t - lastT;    // time spent covered
    if (cur === 0 && d === +1) blockStart = t;                    // a merged block opens

    cur += d;

    if (cur > peak) { peak = cur; peakAt = t; }
    if (cur === 0) {                                              // block closes
      merged.push([blockStart, t]);
      gaps.push(t);                                               // gap starts here
    }
    lastT = t;
  }
  return { peak, peakAt, coveredLength, merged };
}

function peakSweep(intervals) {
  const ev = [];

  ev.sort((a,b) => a[0]-b[0] || a[1]-b[1]);

}

function peakDiff(intervals, maxT) {
  const diff = new Int32Array(maxT + 2);

  return best;
}

🎯 Key Takeaways

  • Sorting by start turns an O(n²) pairwise problem into a single O(n) sweep, because only adjacent intervals can merge.
  • The proof: after sorting, if the next interval does not overlap the current block, nothing later can either — later starts are larger.
  • Always merge with Math.max(last.end, cur.end), or a fully-contained interval silently shrinks the block.
  • Two intervals overlap iff a.start ≤ b.end && b.start ≤ a.end; the intersection is [max(starts), min(ends)].
  • Closed intervals merge when touching; half-open ones do not — ask which convention applies before choosing < or <=.
  • "Maximum concurrent" is a sweep-line problem: split into +1/−1 events, sort, and track the running count.
  • At equal timestamps, process ends before starts — otherwise touching intervals inflate the peak by one.
  • Sorting starts and ends independently is valid for room counting, because only the counts matter, never the pairing.
  • A min-heap of end times is the equivalent formulation, and its size is the room count — only the earliest-ending meeting can be free.
  • Sort by end for maximum non-overlapping selection, minimum removals, and arrow shots; sorting by start there is wrong ~20% of the time.
  • The exchange argument justifies it: finishing earliest leaves the most room for everything after.
  • Inserting into a sorted list is a three-phase sweep (before, overlapping, after) in O(n) — no re-sort needed.
  • Interval intersection of two sorted lists is a two-pointer merge; advance whichever interval ends first.
  • When timestamps are bounded integers, a difference array beats sorting outright — over 100× faster in realistic scheduling data.
  • When the range is huge or continuous, the sweep line wins because its space is independent of the timeline.
  • Copy intervals with .slice() before mutating merged ends, or the caller's data changes underneath them.
