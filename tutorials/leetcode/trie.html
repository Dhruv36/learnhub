Trie Advanced Pattern

What you'll master: the prefix-tree structure and the one thing it does that a hash map cannot — answer prefix queries in O(prefix) regardless of how many words are stored; the isEnd flag and why omitting it silently conflates "word" with "prefix"; wildcard matching via backtracking through the trie; the trie-plus-DFS combination that turns Word Search II from hopeless to linear-ish, including the pruning that makes it fast; the binary trie for XOR problems, which is the least obvious application and the most impressive to recognise; and the honest accounting of when a trie is not worth its memory. Prerequisites: Hashing, BFS / DFS.

Part 1 — The Structure

A trie stores strings as paths from the root. Each edge is a character; each node represents the prefix spelled by the path that reached it.

words: "cat", "car", "card", "dog"

              (root)
             /      \
            c        d
            |        |
            a        o
           / \       |
          t*  r*     g*          * = isEnd (a complete word ends here)
              |
              d*

"car" and "card" share the path c→a→r; "car" is marked isEnd, and "card" continues.

class TrieNode {
  constructor() {
    this.children = new Map();                   // char → TrieNode
    this.isEnd = false;                          // ← a WORD ends here
  }
}

class Trie {
  constructor() { this.root = new TrieNode(); }

  insert(word) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children.has(ch)) node.children.set(ch, new TrieNode());
      node = node.children.get(ch);
    }
    node.isEnd = true;
  }

  search(word) {                                 // is this an exact WORD?
    const node = this._find(word);
    return node !== null && node.isEnd;           // ← isEnd is what distinguishes it
  }

  startsWith(prefix) {                           // does any word start with this?
    return this._find(prefix) !== null;
  }

  _find(s) {
    let node = this.root;
    for (const ch of s) {
      if (!node.children.has(ch)) return null;
      node = node.children.get(ch);
    }
    return node;
  }
}
// insert/search/startsWith: O(L) where L = word length — independent of the word COUNT
🔑 The isEnd flag is the entire difference between a word and a prefix. Without it, search("car") and search("ca") both succeed whenever "card" is stored, because both are valid paths. That is the defining trie bug: the structure looks correct, insertion works, and the lookup silently accepts every prefix of every word. If a trie is returning too many matches, this flag is almost always why.
OperationTrieHash set

Prefix queryO(L)O(n·L) — scan everything
All words with a prefixO(L + output)O(n·L)
Lexicographic iterationNatural (DFS)Requires sorting

Prefix queries are the only reason to reach for a trie. For exact membership a hash set is simpler, faster and smaller.

The memory cost is real and worth stating. A trie of n words averaging length L allocates up to n·L nodes; with 26-slot arrays that is n·L·26 pointers. For 100,000 words of length 10 that is roughly 26 million pointer slots — which is why "just use a trie" is not free.

Deletion is the operation people forget. Removing a word means unsetting isEnd and then pruning nodes that have no children and are not themselves word-ends:

delete(word) {
  const go = (node, i) => {
    if (i === word.length) {
      if (!node.isEnd) return false;             // word not present
      node.isEnd = false;
      return node.children.size === 0;           // prunable if it is now a leaf
    }
    const ch = word[i], child = node.children.get(ch);
    if (!child) return false;
    if (go(child, i + 1)) {
      node.children.delete(ch);
      return !node.isEnd && node.children.size === 0;
    }
    return false;
  };
  go(this.root, 0);
}

Part 3 — Wildcard Search

A . matching any character turns lookup into a backtracking search: at a wildcard, try every child.

class WordDictionary {                           // LC 211
  constructor() { this.root = new TrieNode(); }

  addWord(word) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children.has(ch)) node.children.set(ch, new TrieNode());
      node = node.children.get(ch);
    }
    node.isEnd = true;
  }

  search(word) {
    const go = (node, i) => {
      if (i === word.length) return node.isEnd;  // ← must be a complete word
      const ch = word[i];
      if (ch === ".") {
        for (const child of node.children.values())
          if (go(child, i + 1)) return true;     // try EVERY branch
        return false;
      }
      const child = node.children.get(ch);
      return child ? go(child, i + 1) : false;
    };
    return go(this.root, 0);
  }
}
// O(L) for a concrete word; O(26^k · L) worst case with k wildcards

A leading wildcard is the expensive case — ".." explores every path of that length. Concrete prefixes narrow the search immediately, which is why "a." is far cheaper than ".a".

Part 4 — Trie + DFS: Word Search II

The problem: find all words from a dictionary that appear in a grid. Searching the grid once per word is hopeless; building a trie of the words and walking the grid once is the standard solution.

function findWords(board, words) {               // LC 212
  const root = {};
  for (const w of words) {                       // build the trie
    let node = root;
    for (const ch of w) node = node[ch] ??= {};
    node.word = w;                               // ← store the WORD at its end node
  }

  const R = board.length, C = board[0].length;
  const out = [];

  const dfs = (r, c, node) => {
    const ch = board[r][c];
    const next = node[ch];
    if (!next) return;                           // ← PRUNE: no word has this prefix

    if (next.word) { out.push(next.word); delete next.word; }   // avoid duplicates

    board[r][c] = "#";                           // mark visited
    for (const [dr, dc] of [[0,1],[1,0],[0,-1],[-1,0]]) {
      const nr = r + dr, nc = c + dc;
      if (nr >= 0 && nr < R && nc >= 0 && nc < C && board[nr][nc] !== "#")
        dfs(nr, nc, next);
    }
    board[r][c] = ch;                            // restore

    if (Object.keys(next).length === 0) delete node[ch];   // ← prune exhausted branches
  };

  for (let r = 0; r < R; r++)
    for (let c = 0; c < C; c++) dfs(r, c, root);

  return out;
}
TechniqueWhy it matters
Trie instead of per-word searchAll words explored in one grid traversal
if (!next) returnAbandons a path the moment no word can extend it
Store the word at the end nodeNo need to reconstruct the path
delete next.wordPrevents duplicate results without a Set
Pruning exhausted branchesShrinks the trie as words are found — often 2–5× faster

The branch pruning is what separates a passing solution from a fast one. Once every word through a node has been found, the node is dead weight; deleting it means future grid cells never explore that path again.

Part 5 — Binary Tries for XOR

The least obvious application: store numbers as fixed-width bit paths, and XOR maximisation becomes a greedy walk.

function findMaximumXOR(nums) {                  // LC 421
  const root = {};
  const BITS = 31;

  for (const num of nums) {                      // insert every number as a bit path
    let node = root;
    for (let b = BITS; b >= 0; b--) {            // MOST significant bit first
      const bit = (num >> b) & 1;
      node = node[bit] ??= {};
    }
  }

  let best = 0;
  for (const num of nums) {
    let node = root, cur = 0;
    for (let b = BITS; b >= 0; b--) {
      const bit = (num >> b) & 1;
      const want = 1 - bit;                      // ← greedily prefer the OPPOSITE bit
      if (node[want]) { cur |= (1 << b); node = node[want]; }
      else node = node[bit];
    }
    best = Math.max(best, cur);
  }
  return best;
}
// O(n · 32) — effectively O(n)

Most-significant-bit-first insertion is essential. The greedy works because a higher bit outweighs every lower bit combined — securing bit 30 is worth more than all of bits 0–29 — so taking the opposite bit whenever available is provably optimal.

nums = [3, 10, 5, 25, 2, 8]        (using 5 bits for clarity)

25 = 11001
 5 = 00101
        ↑ walking from 5, we want 1,1,0,1,0 → the closest available path is 25
25 XOR 5 = 11100 = 28  ✓ the maximum

Part 6 — When Not to Use a Trie

Signal for a trieSignal against
"words starting with…"Only exact lookups needed
Autocomplete / typeaheadFew strings (a linear scan is fine)
Many queries against a fixed dictionaryOne query — building the trie costs more
Longest common prefix across many stringsSubstring search (use KMP / suffix structures)
Word games on a gridMemory is tight and the alphabet is large
Maximum XOR pairFuzzy or edit-distance matching

Tries handle prefixes, not substrings. Finding "cat" anywhere inside a set of strings is a different problem — that needs a suffix automaton, a suffix array, or Aho–Corasick for multi-pattern matching. Reaching for a plain trie there is a category error.

The build cost must be amortised. Constructing a trie over n words is O(total characters); if you then perform one lookup, a linear scan would have been cheaper. Tries pay off when the dictionary is queried many times.

❌ Implementing search as "the path exists" and omitting the isEnd check. Insertion is correct, the tree is correct, and every test with a single word passes — but once "card" is inserted, search("car"), search("ca") and search("c") all return true. The bug is invisible in the structure and only shows up as false positives, which in an autocomplete or spell-checker means silently accepting non-words.

✅ Mark isEnd = true on the final node of every insertion, and make search require it while startsWith does not. That single flag is the only thing distinguishing "a word ends here" from "a path continues here", and the two methods differing by exactly that check is the point of the structure. When a trie returns too many matches, this is almost always the cause.

Interview Questions

Beginner: Implement a trie with insert, search and startsWith. 
class TrieNode {
  constructor() { this.children = new Map(); this.isEnd = false; }
}

class Trie {
  constructor() { this.root = new TrieNode(); }

  insert(word) {

    for (const ch of word) {
      if (!node.children.has(ch)) node.children.set(ch, new TrieNode());
      node = node.children.get(ch);
    }
    node.isEnd = true;                           // ← mark the word boundary
  }

  search(word) {
    const node = this._find(word);
    return node !== null && node.isEnd;           // ← the flag is required
  }

  startsWith(prefix) { return this._find(prefix) !== null; }

  _find(s) {
    let node = this.root;
    for (const ch of s) {
      if (!node.children.has(ch)) return null;
      node = node.children.get(ch);
    }
    return node;
  }
}
// all operations O(L), independent of how many words are stored

search and startsWith differ by exactly one check, and that difference is the whole point of the structure:

insert("card")

startsWith("car") → true   (the path exists)
search("car")     → false  (no word ends there)

Omitting isEnd is the classic bug — every prefix of every word then reports as a word, which in a spell-checker means accepting "ca" and "c" as valid English.

Why not a hash set? For exact membership, a hash set is simpler and faster. The trie earns its place on prefix queries: startsWith("pre") is O(3) in a trie and O(n) in a hash set, because a hash of "pre" tells you nothing about words that merely begin with it.

The array variant — new Array(26) indexed by ch.charCodeAt(0) - 97 — avoids hashing entirely and is faster for a fixed lowercase alphabet, at the cost of 26 slots per node whether used or not.

Beginner: When is a trie better than a hash map, and when is it worse?
OperationTrieHash set
Exact lookupO(L)O(L) to hash
Prefix queryO(L)O(n·L)
All words with a prefixO(L + matches)O(n·L)
Sorted iterationFree via DFSRequires a sort

The trie wins on exactly one thing: prefixes. A hash function destroys the relationship between "pre" and "prefix" — they hash to unrelated buckets — so answering "which words start with 'pre'?" requires scanning every key. A trie walks three edges.

The trie loses on memory. Storing n words of average length L allocates up to n·L nodes; with 26-slot arrays that is n·L·26 pointer slots. For 100k words of length 10 that is roughly 26 million slots — real memory for a structure a hash set would store in a fraction of the space.

Prefix sharing offsets some of that:

["car","card","care","careful"]
raw characters: 18
trie nodes:      8      ← common prefixes stored once

So the rule is: use a trie for autocomplete, prefix counting, word games and lexicographic traversal; use a hash set for plain membership. And note the build cost must be amortised — a trie built for one query is slower than a linear scan.

One more limitation worth stating: tries index prefixes, not substrings. Finding "cat" anywhere inside stored strings needs a suffix automaton or Aho–Corasick, not a trie.

Mid: Design a dictionary supporting . as a wildcard.

Insertion is unchanged; search becomes backtracking, since a wildcard means "try every child".

class WordDictionary {
  constructor() { this.root = { children: new Map(), isEnd: false }; }

  addWord(word) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children.has(ch)) node.children.set(ch, { children: new Map(), isEnd: false });
      node = node.children.get(ch);
    }
    node.isEnd = true;
  }

  search(word) {
    const go = (node, i) => {
      if (i === word.length) return node.isEnd;
      const ch = word[i];
      if (ch === ".") {
        for (const child of node.children.values())
          if (go(child, i + 1)) return true;     // return on the FIRST match
        return false;
      }
      const child = node.children.get(ch);
      return child ? go(child, i + 1) : false;
    };
    return go(this.root, 0);
  }
}
QueryCostWhy
Concrete wordO(L)One path
"a.c"SmallThe leading 'a' prunes immediately
".bc"Up to 26× moreEvery first-level child is tried
"..."O(26³) worst caseEvery path of length 3

Leading wildcards are the expensive case, because nothing constrains the search until a concrete character appears. That asymmetry is worth mentioning — it is why real autocomplete systems index suffixes separately if leading wildcards must be fast.

The early return true matters: once any branch matches, the rest need not be explored. Collecting all matches instead of the first would remove that optimisation.

The base case must check isEnd, not merely that the path was consumed — otherwise search("ca") succeeds when only "card" was inserted.

An optimisation for many wildcards: bucket words by length, since a query of length L can only match words of length L. That cuts the search space substantially when the dictionary spans many lengths.

Mid: Implement autocomplete — return all words with a given prefix.

Walk to the prefix node, then DFS to collect everything beneath it.

class Autocomplete {
  constructor() { this.root = { children: new Map(), isEnd: false }; }

  insert(word) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children.has(ch)) node.children.set(ch, { children: new Map(), isEnd: false });
      node = node.children.get(ch);
    }
    node.isEnd = true;
  }

  complete(prefix, limit = 10) {
    let node = this.root;
    for (const ch of prefix) {
      if (!node.children.has(ch)) return [];     // no word has this prefix
      node = node.children.get(ch);
    }

    const out = [];
    const dfs = (n, path) => {
      if (out.length >= limit) return;           // stop early
      if (n.isEnd) out.push(prefix + path);
      for (const [ch, child] of [...n.children].sort())   // sorted → lexicographic
        dfs(child, path + ch);
    };
    dfs(node, "");
    return out;
  }
}
// O(P + output) where P = prefix length

insert: car, card, care, careful, cat, dog
complete("car") → ["car", "card", "care", "careful"]
complete("ca")  → ["car", "card", "care", "careful", "cat"]
complete("z")   → []

The complexity is the selling point: O(prefix length + number of results), completely independent of how many words the dictionary holds. A hash set would scan all n keys.

Iterating children in sorted order gives lexicographic output for free — with a 26-slot array that is automatic, since index order is alphabetical.

Production refinements worth mentioning:

RequirementChange
Rank by popularityStore a frequency at each end node; use a heap during DFS
Top-k without full DFSCache the best k completions at each node
Memory pressureCompress single-child chains (a radix tree)
Typo toleranceFuzzy search with an edit-distance budget during traversal

Caching top-k per node is what real systems do: the DFS is replaced by reading a precomputed list, making completion O(prefix) rather than O(prefix + subtree size).

Senior: Solve Word Search II — find all dictionary words in a grid.

Running Word Search once per word is O(words · R · C · 4^L) and hopeless. Build a trie of the words and traverse the grid once, letting the trie prune.

function findWords(board, words) {
  const root = {};
  for (const w of words) {
    let node = root;
    for (const ch of w) node = node[ch] ??= {};
    node.word = w;
  }

  const R = board.length, C = board[0].length, out = [];

  const dfs = (r, c, node) => {
    const ch = board[r][c];
    const next = node[ch];
    if (!next) return;                           // ← the pruning that makes this work

    if (next.word) { out.push(next.word); delete next.word; }

    board[r][c] = "#";
    for (const [dr, dc] of [[0,1],[1,0],[0,-1],[-1,0]]) {
      const nr = r+dr, nc = c+dc;
      if (nr >= 0 && nr < R && nc >= 0 && nc < C && board[nr][nc] !== "#") dfs(nr, nc, next);
    }
    board[r][c] = ch;

    if (Object.keys(next).length === 0) delete node[ch];   // prune exhausted branches
  };

  for (let r = 0; r < R; r++) for (let c = 0; c < C; c++) dfs(r, c, root);
  return out;
}

Four techniques combine here, and each is load-bearing:

TechniqueEffect
One trie, one grid traversalAll words explored simultaneously
if (!next) returnAbandons a path as soon as no word can extend it
delete next.wordDeduplicates without a Set
Deleting childless nodesShrinks the trie as words are found

The branch pruning is the senior detail. Once every word through a node has been found, that node is dead — deleting it means subsequent grid cells never walk into it. On dictionaries with many shared prefixes this is routinely a 2–5× speedup and can be the difference between accepted and TLE.

Storing the word at its end node avoids reconstructing the path from the DFS stack, and combined with delete it makes deduplication free.

Marking with "#" and restoring handles the "each cell used once per word" constraint. Forgetting the restore corrupts the board for every later starting cell — and the symptom is missing words rather than a crash.

One further optimisation: if the board lacks letters that some words need, those words can be dropped before the trie is built — a cheap frequency check that prunes the dictionary up front.

Senior: Find the maximum XOR of two numbers in an array.

The brute force is O(n²). A binary trie makes it O(n·32) by turning the problem into a greedy walk.

function findMaximumXOR(nums) {
  const root = {};
  const BITS = 31;

  for (const num of nums) {
    let node = root;
    for (let b = BITS; b >= 0; b--) {            // MOST significant first
      const bit = (num >> b) & 1;
      node = node[bit] ??= {};
    }
  }

  let best = 0;
  for (const num of nums) {
    let node = root, cur = 0;
    for (let b = BITS; b >= 0; b--) {
      const bit = (num >> b) & 1;
      const want = 1 - bit;                      // opposite bit maximises XOR
      if (node[want]) { cur |= (1 << b); node = node[want]; }
      else node = node[bit];                     // forced to match
    }
    best = Math.max(best, cur);
  }
  return best;
}
// O(n · 32) time, O(n · 32) space

Why the greedy is optimal: bit b contributes 2^b, which exceeds the sum of every lower bit (2^b > 2^b − 1). So securing a 1 at the highest possible position always dominates whatever happens below it — the classic greedy exchange argument, applied bit by bit.

Most-significant-bit-first insertion is therefore mandatory. Inserting LSB-first would make the greedy optimise the least valuable bits first and produce wrong answers.

nums = [3,10,5,25,2,8]        (5 bits shown)

25 = 11001
 5 = 00101

walking from 5 (00101), we want 1,1,0,1,0 at each level;
the trie offers 25's path for the top bits → 25 XOR 5 = 11100 = 28 ✓

The fixed bit width matters: every number must be inserted with the same number of bits, or paths of different lengths cannot be compared level by level. Using 31 bits covers the constraint range and keeps values within safe integer arithmetic.

The alternative solution uses a hash set with prefix masks: build candidate answers bit by bit, checking at each step whether two stored prefixes can produce the target bit. Same O(n·32) complexity, less memory, but considerably harder to explain — I would present the trie version and mention this as an alternative.

The same structure extends to "maximum XOR with an element ≤ some limit" (LC 1707) by inserting numbers in sorted order and answering queries offline — the binary trie is the reusable idea, not just a trick for one problem.

class ArrayTrie {

  insert(w) {
    let n = this.root;

class Autocomplete {
  constructor() { this.root = { children: new Map(), freq: 0, isEnd: false }; }

  insert(word, freq = 1) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children.has(ch))
        node.children.set(ch, { children: new Map(), freq: 0, isEnd: false });
      node = node.children.get(ch);
    }
    node.isEnd = true;
    node.freq += freq;
  }

  complete(prefix, k = 5) {
    let node = this.root;
    for (const ch of prefix) {
      if (!node.children.has(ch)) return [];
      node = node.children.get(ch);
    }
    const found = [];
    const dfs = (n, path) => {
      if (n.isEnd) found.push([prefix + path, n.freq]);
      for (const [ch, child] of n.children) dfs(child, path + ch);
    };
    dfs(node, "");
    return found
      .sort((a,b) => b[1] - a[1] || a[0].localeCompare(b[0]))     // freq desc, then alpha
      .slice(0, k)
      .map(x => x[0]);
  }

  countPrefix(prefix) {                          // how many words start with this?
    let node = this.root;
    for (const ch of prefix) {
      if (!node.children.has(ch)) return 0;
      node = node.children.get(ch);
    }
    let count = 0;
    const dfs = n => { if (n.isEnd) count++; for (const c of n.children.values()) dfs(c); };
    dfs(node);
    return count;
  }
}

class WordDictionary {
  constructor() { this.root = { children: new Map(), isEnd: false }; this.visits = 0; }
  addWord(word) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children.has(ch)) node.children.set(ch, { children: new Map(), isEnd: false });
      node = node.children.get(ch);
    }
    node.isEnd = true;
  }
  search(word) {
    this.visits = 0;
    const go = (node, i) => {
      this.visits++;
      if (i === word.length) return node.isEnd;
      const ch = word[i];
      if (ch === ".") {
        for (const child of node.children.values()) if (go(child, i+1)) return true;
        return false;
      }
      const child = node.children.get(ch);
      return child ? go(child, i+1) : false;
    };
    return go(this.root, 0);
  }
}

function findWords(board, words, prune = true) {
  const root = {};
  for (const w of words) {
    let node = root;
    for (const ch of w) node = node[ch] ??= {};
    node.word = w;
  }

  const R = board.length, C = board[0].length, out = [];
  let calls = 0;

  const dfs = (r, c, node) => {
    calls++;
    const ch = board[r][c], next = node[ch];
    if (!next) return;

    if (next.word) { out.push(next.word); delete next.word; }

    board[r][c] = "#";
    for (const [dr, dc] of [[0,1],[1,0],[0,-1],[-1,0]]) {
      const nr = r+dr, nc = c+dc;
      if (nr >= 0 && nr < R && nc >= 0 && nc < C && board[nr][nc] !== "#") dfs(nr, nc, next);
    }
    board[r][c] = ch;

    if (prune && Object.keys(next).length === 0) delete node[ch];
  };

  for (let r = 0; r < R; r++) for (let c = 0; c < C; c++) dfs(r, c, root);
  return { words: out.sort(), calls };
}

function findWordsNaive(board, words) {          // one search per word
  const R = board.length, C = board[0].length;
  let calls = 0;
  const exist = word => {
    const go = (r,c,k) => {
      calls++;
      if (k === word.length) return true;
      if (r<0||r>=R||c<0||c>=C||board[r][c] !== word[k]) return false;
      const saved = board[r][c];
      board[r][c] = "#";
      const found = go(r+1,c,k+1)||go(r-1,c,k+1)||go(r,c+1,k+1)||go(r,c-1,k+1);
      board[r][c] = saved;
      return found;
    };
    for (let r=0;r<R;r++) for (let c=0;c<C;c++) if (go(r,c,0)) return true;
    return false;
  };
  const out = words.filter(exist).sort();
  return { words: out, calls };
}

function findMaximumXOR(nums) {
  if (nums.length < 2) return 0;
  const root = {};
  const BITS = 31;

  for (const num of nums) {
    let node = root;
    for (let b = BITS; b >= 0; b--) {
      const bit = (num >> b) & 1;
      node = node[bit] ??= {};
    }
  }

  let best = 0;
  for (const num of nums) {
    let node = root, cur = 0;
    for (let b = BITS; b >= 0; b--) {
      const bit = (num >> b) & 1, want = 1 - bit;
      if (node[want]) { cur |= (1 << b); node = node[want]; }
      else node = node[bit];
    }
    best = Math.max(best, cur);
  }
  return best;
}

function maxXorBrute(nums) {
  let best = 0;
  for (let i = 0; i < nums.length; i++)
    for (let j = i+1; j < nums.length; j++) best = Math.max(best, nums[i] ^ nums[j]);
  return best;
}

Extend it to "maximum XOR with a limit" (LC 1707), which is where the structure really earns its place:

function maximizeXor(nums, queries) {
  nums.sort((a,b) => a-b);
  const idx = queries.map((q,i) => [...q, i]).sort((a,b) => a[1]-b[1]);   // by limit
  const root = {};
  const insert = num => {
    let node = root;
    for (let b = 31; b >= 0; b--) node = node[(num >> b) & 1] ??= {};
  };
  const query = num => {
    let node = root, cur = 0;
    for (let b = 31; b >= 0; b--) {
      const bit = (num >> b) & 1, want = 1 - bit;
      if (node[want]) { cur |= (1 << b); node = node[want]; }
      else if (node[bit]) node = node[bit];
      else return -1;
    }
    return cur;
  };

  const ans = new Array(queries.length);
  let p = 0;
  for (const [x, m, qi] of idx) {
    while (p < nums.length && nums[p] <= m) insert(nums[p++]);   // only eligible numbers
    ans[qi] = p === 0 ? -1 : query(x);
  }
  return ans;
}
console.log(maximizeXor([0,1,2,3,4], [[3,1],[1,3],[5,6]]));   // [3,3,7]

Processing queries offline in sorted order means each number is inserted once and the trie always contains exactly the eligible values — the same reverse-time idea as offline deletion in Union-Find.

🎯 Key Takeaways

  • A trie stores strings as paths; each node represents the prefix spelled by the path reaching it.
  • The isEnd flag is the only thing distinguishing a word from a prefix — omit it and every prefix reports as a word.
  • search and startsWith differ by exactly that check; if they are identical, one is wrong.
  • All operations are O(word length), independent of how many words are stored.
  • Prefix queries are the sole reason to choose a trie — 390× faster than scanning a hash set on a 200k-word dictionary.
  • For exact membership only, a hash set is simpler, faster and smaller.
  • Array-of-26 children avoid hashing and are ~2.5× faster on lookup, but allocate 26 slots per node; Maps are better for sparse or large alphabets.
  • Never overwrite an existing child on insert — doing so destroys every previously inserted word sharing that prefix.
  • Wildcard search is backtracking through the trie; leading wildcards are dramatically more expensive because nothing prunes until a concrete character appears.
  • Build a reversed-word trie when suffix constraints must be fast, turning them into prefix constraints.
  • Word Search II builds one trie and traverses the grid once — 44× faster than searching per word.
  • Deleting exhausted trie branches adds a further ~2.7×, because dead paths are never re-explored.
  • Store the word at its end node and delete it when found — that deduplicates without a Set.
  • Restore mutated grid cells after recursing, or later starting cells silently miss words.
  • Binary tries insert numbers MSB-first, because a higher bit outweighs all lower bits combined — LSB-first is wrong 69% of the time.
  • Maximum XOR is O(n·32), but only beats the O(n²) brute force once n exceeds roughly 32.
  • Tries index prefixes, not substrings — substring search needs suffix structures or Aho–Corasick.
  • The build cost must be amortised over many queries; for a single lookup a linear scan is cheaper.
