Hashing Essentials Foundations

What you'll master: the one idea that converts more O(n²) solutions to O(n) than any other technique, and exactly when it applies; the four hash-map roles — seen-set, counter, index map, grouping key — that between them cover most interview uses; why designing the key is the real skill and how to build canonical keys for grouping problems; the complement pattern behind Two Sum and its generalisations; why hash lookup is O(1) average and O(n) worst case and when that matters; and the traps around object keys, iteration order and mutable keys. Prerequisites: Big-O, Arrays & Strings.

Part 1 — The Trade That Makes It Work

Hashing buys time with space. A hash map turns "search the data for X" from a scan into a lookup, and that single substitution removes the inner loop from an enormous number of problems.

// O(n²) — for each element, SCAN for its complement
for (let i = 0; i < n; i++)
  for (let j = i+1; j < n; j++)
    if (nums[i] + nums[j] === target) return [i, j];

// O(n) — for each element, LOOK UP its complement
const seen = new Map();
for (let i = 0; i < n; i++) {
  if (seen.has(target - nums[i])) return [seen.get(target - nums[i]), i];
  seen.set(nums[i], i);
}

🔑 When you catch yourself writing a nested loop where the inner one is searching, stop and ask what you are searching for. If the answer is "an exact value", a hash map removes the loop and the solution becomes O(n). This one substitution accounts for more O(n²) → O(n) improvements than every other technique in this track combined — and the giveaway phrase in an interview is "for each element, find whether there exists...".

The cost is real, though, and knowing when not to hash is part of the skill:

Part 2 — The Four Roles

Nearly every interview use of a hash map is one of four shapes. Recognising which one you need is most of the work.

Role 1 — the seen-set: "have I encountered this?"

function containsDuplicate(nums) {
  const seen = new Set();
  for (const x of nums) {
    if (seen.has(x)) return true;
    seen.add(x);
  }
  return false;
}

Role 2 — the counter: "how many of each?"

function countChars(s) {
  const count = new Map();
  for (const ch of s) count.set(ch, (count.get(ch) ?? 0) + 1);
  return count;
}
// The ?? 0 idiom is the whole pattern — get-or-default, then increment.

Role 3 — the index map: "where did I last see this?"

function twoSum(nums, target) {
  const idx = new Map();                       // value → index
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (idx.has(need)) return [idx.get(need), i];
    idx.set(nums[i], i);                       // store AFTER checking
  }
}

Storing after checking is not stylistic — it is what prevents an element pairing with itself when nums[i] * 2 === target.

Role 4 — grouping: "which items share a property?"

function groupAnagrams(strs) {
  const groups = new Map();
  for (const s of strs) {
    const key = [...s].sort().join("");        // canonical form
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(s);
  }
  return [...groups.values()];
}

GroupingMap key → list"group by", "categorise", "which share"

Part 3 — Designing the Key

Choosing the key is the algorithm in grouping problems. Two items must produce identical keys exactly when they belong together — which means the key must be a canonical form of whatever property matters.

group anagrams          → sorted characters      O(m log m) per word
                        → or a 26-count string   O(m) per word, better

group shifted strings   → distance pattern from the first character
                          "abc" and "bcd" both → "0,1,2"

group by shape (grid)   → coordinates relative to the top-left cell

group similar numbers   → the number divided by a bucket size

The faster anagram key avoids sorting entirely, which matters when words are long:

function anagramKey(s) {
  const count = new Array(26).fill(0);
  for (const ch of s) count[ch.charCodeAt(0) - 97]++;
  return count.join(",");                     // "1,0,0,2,..." — canonical, O(m)
}

Use a separator. Joining without one makes [1,11] and [11,1] both produce "111" — a collision that merges groups that should be distinct. This class of bug passes every small test.

The composite-key trick handles multi-dimensional grouping, and it is worth knowing because JavaScript objects cannot be used as value-equal keys:

// ✗ every object is a distinct key — this map never finds anything
const m = new Map();
m.set({r: 1, c: 2}, "x");
m.get({r: 1, c: 2});          // undefined — different object identity

// ✓ a string key compares by value
m.set(`${r},${c}`, "x");
m.get(`${r},${c}`);           // "x"

Part 4 — The Complement Pattern

"Find two things that combine to a target" is one idea applied repeatedly: as you scan, ask whether the partner you need has already been seen.

for (const x of nums) {
  if (seen.has(NEEDED(x))) { /* found the pair */ }
  seen.add(x);
}
ProblemWhat you look up
Two Sumtarget - x
Subarray Sum Equals Kprefix - k among earlier prefixes
Contiguous Array (equal 0s and 1s)The same running balance seen before
Pairs with a given differencex - d and x + d
Four Sum IISums of the first two arrays, looked up by the negation of the last two

The prefix-sum variant is the highest-value generalisation, because it handles negative numbers where sliding window cannot:

function subarraySum(nums, k) {
  const seen = new Map([[0, 1]]);     // ← the empty prefix, seen once
  let prefix = 0, count = 0;
  for (const x of nums) {
    prefix += x;
    count += seen.get(prefix - k) ?? 0;
    seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
  }
  return count;
}

The [[0, 1]] seed is the classic omission. Without it, any subarray starting at index 0 is missed, because there is no earlier prefix of 0 to subtract. See Prefix Sum for the full treatment.

Part 5 — Collisions and the Worst Case

A hash map computes hash(key) % capacity to pick a bucket. Different keys can land in the same bucket — a collision — and the bucket then holds a small list (or tree) that must be searched.

keys → hash → bucket
  "cat" → 3 ─┐
  "dog" → 7  │  bucket 3: ["cat", "act"]   ← collision: search within
  "act" → 3 ─┘
CaseLookupWhen
AverageO(1)Good hash function, load factor kept low
WorstO(n)Every key collides — adversarial or a bad hash
Worst (tree buckets)O(log n)Java 8+ converts long buckets to trees

Say "O(1) average" rather than "O(1)". It costs one word and is the precise claim; the worst case genuinely occurs, and hash-collision denial-of-service attacks are built on exactly it — which is why modern runtimes seed their string hashes randomly per process.

Resizing is the other hidden cost. When the load factor is exceeded, the map allocates a larger table and rehashes everything — O(n) for that insert, O(1) amortised overall, by the same doubling argument as dynamic arrays.

Where a frequency array beats a hash map: when keys are small bounded integers, skip hashing entirely.

const count = new Array(26).fill(0);
for (const ch of s) count[ch.charCodeAt(0) - 97]++;
// O(1) space (26 is constant), no hashing, no collisions, far better cache behaviour

JavaScript Map preserves insertion order, which is convenient and worth not relying on across languages — Python dicts also preserve it (3.7+), but Java's HashMap and C++'s unordered_map do not. If order matters, sort explicitly.

❌ Reaching for a hash map reflexively, including when the input is already sorted. Hashing is the technique that most often works, so it becomes the default — and on a sorted array it quietly costs O(n) extra space for a problem that two converging pointers solve in O(1). The interviewer then asks "can you do it without extra space?" and the candidate has to restart, because the sortedness was never used.

✅ Check for structure before spending space. Sorted input means two pointers or binary search; small bounded integer keys mean a frequency array with far better constants; a need for order or ranking means a heap or a sort. Hashing is the right answer when the input is unordered and you need exact-value lookup — which is often, but not always, and the difference is usually stated in the problem's first sentence.

Interview Questions

Beginner: Solve Two Sum and explain why the order of operations matters.

Scan once, and for each element look up whether its complement has already been seen.

function twoSum(nums, target) {
  const idx = new Map();                       // value → index
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (idx.has(need)) return [idx.get(need), i];   // CHECK first
    idx.set(nums[i], i);                            // then STORE
  }
  return [];
}
// O(n) time, O(n) space

The order is a correctness requirement, not a preference. Storing before checking lets an element match itself:

nums = [3, 5], target = 6

store-then-check:  i=0 → store {3:0}, then look up 6-3=3 → FOUND at index 0
                   returns [0, 0]  ✗ uses the same element twice

check-then-store:  i=0 → look up 3 → not present; store {3:0}
                   i=1 → look up 1 → not present; store {5:1}
                   returns []      ✓ correct, no valid pair

Why the map holds indices rather than just values is because the problem asks for positions. If it only asked whether a pair exists, a Set would do.

The alternative worth mentioning: if the array were sorted, two converging pointers solve it in O(1) space. Since it is not, sorting first would cost O(n log n) and destroy the original indices — so the hash map is the right tool here, and saying why demonstrates you considered the alternative rather than defaulting.

Grouping is the one where the real work is elsewhere — the map is trivial, and the difficulty is designing a key that is identical for items that belong together and different for items that do not.

Mid: Group anagrams together. What makes a good key, and what is the fastest one?

A key must be a canonical form: identical for every member of a group, different across groups. For anagrams, sorted characters is the obvious canonical form.

function groupAnagrams(strs) {
  const groups = new Map();
  for (const s of strs) {
    const key = [...s].sort().join("");        // O(m log m) per word
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(s);
  }
  return [...groups.values()];
}
// O(n · m log m) for n words of length m

The faster key is a character count, which removes the sort:

function anagramKey(s) {
  const count = new Array(26).fill(0);
  for (const ch of s) count[ch.charCodeAt(0) - 97]++;
  return count.join(",");                      // O(m)
}
// total: O(n · m) — better when words are long

The separator is essential and easy to omit:

[1, 11, 0, ...].join("")   → "1110..."
[11, 1, 0, ...].join("")   → "1110..."     ← same key, different counts!

Joining with "," makes them "1,11,0" and "11,1,0" — distinct. The bug requires a letter appearing 10+ times to trigger, so it passes every small test and fails on real input.

Which to present: sorting is clearer and fine when m is small; the count key is better asymptotically. I would write the sorted version, state its complexity, then note "if the words were long I'd use a 26-length count as the key to drop the log m factor" — showing the trade-off without over-engineering the first answer.

The generalisation is worth remembering: "group shifted strings" uses the distance pattern between consecutive characters; "group by grid shape" uses coordinates relative to the top-left cell. Same map, different canonical form — the key is the algorithm.

Mid: Count subarrays summing to k, where values may be negative. Why not sliding window?

Because sliding window requires the window sum to be monotonic — extending increases it, shrinking decreases it — and negative values break that invariant:

[1, -1, 1], target 1

window [1]      sum 1  ✓
extend to [1,-1] sum 0 — extending DECREASED the sum
→ the "shrink when too large, extend when too small" logic no longer works

Prefix sums plus a hash map handle it, because the identity sum(i..j) = prefix[j] − prefix[i−1] holds regardless of sign:

sum(i..j) == k
⟺ prefix[j] - prefix[i-1] == k
⟺ prefix[i-1] == prefix[j] - k        ← a lookup, not a scan

function subarraySum(nums, k) {
  const seen = new Map([[0, 1]]);     // empty prefix, seen once
  let prefix = 0, count = 0;
  for (const x of nums) {
    prefix += x;
    count += seen.get(prefix - k) ?? 0;
    seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
  }
  return count;
}
// O(n) time, O(n) space

The seed is the part people miss. Without [[0, 1]], a subarray starting at index 0 has no earlier prefix to subtract and is never counted:

nums = [3], k = 3
without seed: prefix=3, look for 0 → absent → count 0   ✗
with seed:    prefix=3, look for 0 → found  → count 1   ✓

Note the map stores counts, not just presence, because the same prefix value can occur several times and each occurrence is a distinct subarray. Using a Set here undercounts — a subtle bug that only shows up with repeated prefixes, which means arrays containing zeros or cancelling values.

Verify with a trace:

nums = [1,1,1], k = 2
x=1: prefix 1, need -1 → 0.  count 0.  seen {0:1, 1:1}
x=1: prefix 2, need  0 → 1.  count 1.  seen {0:1, 1:1, 2:1}
x=1: prefix 3, need  1 → 1.  count 2.  ✓
Senior: When is a hash map the wrong choice, and what replaces it?

Whenever the input has structure that hashing throws away, or when O(n) extra space is not affordable. Hashing is the most generally applicable technique, which is exactly why it becomes a reflex.

SituationUse insteadGain
Input already sortedTwo pointers / binary searchO(1) space
Need order, ranking, or top-kHeap, or sortHash maps have no order
Range queries ("keys in [a,b]")Sorted array, balanced treeHashing cannot do ranges
Small bounded integer keysFrequency arrayBetter constants, no collisions
Memory-constrainedSort in placeO(1) vs O(n) space
Need a guaranteed worst caseBalanced treeO(log n) guaranteed vs O(n) worst

The sorted-input case is the one interviewers probe most. Two Sum on a sorted array with a hash map is O(n) time and O(n) space; with converging pointers it is O(n) time and O(1) space — same time, and the follow-up "can you avoid the extra space?" has already been answered.

The frequency-array case matters more than it looks. For lowercase letters, a 26-element array is O(1) space, has no hashing cost, no collision handling, and vastly better cache locality — often several times faster in practice despite identical asymptotics.

And the worst-case argument is real, not theoretical: hash-collision denial-of-service attacks work by feeding a server keys that all hash to one bucket, turning O(1) lookups into O(n). Modern runtimes seed string hashes randomly per process specifically to prevent this, and Java 8+ converts long collision chains into trees to bound the damage at O(log n).

In an interview I would still reach for hashing first when the input is unordered and the need is exact-value lookup — but saying "the array is sorted, so I'll use two pointers and keep it O(1) space" is a stronger opening than producing the hash-map solution and being asked to improve it.

Senior: Design a data structure supporting insert, delete and getRandom, all in O(1).

Neither structure alone can do it: a hash map gives O(1) insert and delete but cannot pick a uniformly random element; an array gives O(1) random access but O(n) delete. Combining them, with the map storing each value's index in the array, gives all three.

class RandomizedSet {
  constructor() { this.arr = []; this.idx = new Map(); }   // value → position in arr

  insert(val) {
    if (this.idx.has(val)) return false;
    this.idx.set(val, this.arr.length);
    this.arr.push(val);
    return true;
  }

  remove(val) {
    if (!this.idx.has(val)) return false;
    const i = this.idx.get(val), last = this.arr[this.arr.length - 1];

    this.arr[i] = last;                    // move the LAST element into the hole
    this.idx.set(last, i);                 // and fix its recorded index

    this.arr.pop();
    this.idx.delete(val);
    return true;
  }

  getRandom() {
    return this.arr[Math.floor(Math.random() * this.arr.length)];
  }
}

The swap-with-last trick is the whole design. Deleting from the middle of an array is O(n) because everything shifts — but the array's order is irrelevant here, since we only ever index into it randomly. So we can fill the hole with the last element and pop, which is O(1).

arr = [10, 20, 30, 40]   idx = {10:0, 20:1, 30:2, 40:3}
remove(20):
  i = 1, last = 40
  arr[1] = 40          → [10, 40, 30, 40]
  idx.set(40, 1)       → {10:0, 40:1, 30:2}
  arr.pop()            → [10, 40, 30]
  idx.delete(20)       ✓

Two bugs this problem is designed to catch. First, forgetting idx.set(last, i) — the moved element's recorded index is now stale, so a later remove corrupts the structure. Second, the case where the element being removed is the last one: the code above handles it, because idx.set(last, i) writes a value that idx.delete(val) then removes — but reordering those two lines breaks it.

Uniform randomness holds because the array is always densely packed from 0 to n−1, so every element is equally likely.

The natural follow-up is allowing duplicates (LC 381): store a Set of indices per value instead of one index. The swap logic is the same, with the added care of removing the correct index from the set — and the same stale-index bug becomes considerably easier to introduce.

1 (easy): Implement the four hash-map roles.
Solution 
// (a) seen-set: does the array contain a duplicate?
function containsDuplicate(nums) {
  const seen = new Set();
  for (const x of nums) { if (seen.has(x)) return true; seen.add(x); }
  return false;
}

// (b) counter: first non-repeating character
function firstUniqChar(s) {
  const count = new Map();
  for (const ch of s) count.set(ch, (count.get(ch) ?? 0) + 1);
  for (let i = 0; i < s.length; i++) if (count.get(s[i]) === 1) return i;
  return -1;
}

// (c) index map: are there duplicates within distance k?
function containsNearbyDuplicate(nums, k) {
  const last = new Map();
  for (let i = 0; i < nums.length; i++) {
    if (last.has(nums[i]) && i - last.get(nums[i]) <= k) return true;
    last.set(nums[i], i);                     // always update to the most recent
  }
  return false;
}

// (d) grouping: group words by their sorted-character key
function groupAnagrams(strs) {
  const groups = new Map();
  for (const s of strs) {
    const key = [...s].sort().join("");
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(s);
  }
  return [...groups.values()];
}

console.log(containsDuplicate([1,2,3,1]));                    // true
console.log(firstUniqChar("leetcode"));                       // 0
console.log(firstUniqChar("aabb"));                           // -1
console.log(containsNearbyDuplicate([1,2,3,1], 3));           // true
console.log(containsNearbyDuplicate([1,2,3,1], 2));           // false
console.log(groupAnagrams(["eat","tea","tan","ate","nat"]));  // [[eat,tea,ate],[tan,nat]]

(b) needs two passes and the second must scan the string, not the map — the answer is the first such character by position, and hash-map iteration order is not guaranteed across languages even though JavaScript preserves insertion order.

(c)'s subtlety is always overwriting the stored index. Keeping only the most recent occurrence is correct because a nearer duplicate is strictly more likely to satisfy the distance constraint — storing the first occurrence instead fails on [1,2,1,1] with k = 1.

3 (medium): Solve Longest Consecutive Sequence in O(n).
Solution

The problem: given an unsorted array, return the length of the longest run of consecutive integers. [100,4,200,1,3,2] → 4 (the run 1,2,3,4). The constraint forbids sorting, which would be O(n log n).

The naive hash approach is accidentally quadratic:

function longestBad(nums) {
  const set = new Set(nums);
  let best = 0;
  for (const x of set) {
    let len = 1, cur = x;
    while (set.has(cur + 1)) { cur++; len++; }      // walks the run from EVERY element
    best = Math.max(best, len);
  }
  return best;
}
// on [1,2,3,...,n] this walks n, n-1, n-2, ... → O(n²)

The fix is one condition: only start counting from the beginning of a run.

function longestConsecutive(nums) {
  const set = new Set(nums);
  let best = 0;
  for (const x of set) {
    if (set.has(x - 1)) continue;                   // ← not a run start; skip
    let len = 1, cur = x;
    while (set.has(cur + 1)) { cur++; len++; }
    best = Math.max(best, len);
  }
  return best;
}

Why this is O(n) despite the nested loop is the argument the interviewer wants: the inner while loop only ever runs for elements that start a run, and each element is visited by exactly one such walk. Total inner iterations across the whole algorithm is therefore n — an amortised argument, like the monotonic stack.

Measure to confirm the difference is real:

}

Check the edge cases:

4 (medium): Design canonical keys for three grouping problems.
Solution

(a) Group shifted strings. "abc", "bcd" and "xyz" belong together because each is the previous shifted by a constant. The canonical form is the sequence of gaps between consecutive characters:

function shiftKey(s) {
  if (s.length === 1) return "single";
  const gaps = [];
  for (let i = 1; i < s.length; i++) {
    let d = s.charCodeAt(i) - s.charCodeAt(i - 1);
    if (d < 0) d += 26;                             // ← wrap-around: "za" → "ab"
    gaps.push(d);
  }
  return gaps.join(",");
}
console.log(shiftKey("abc"), shiftKey("bcd"), shiftKey("xyz"));   // "1,1" "1,1" "1,1"
console.log(shiftKey("az"), shiftKey("ba"));                      // "25" "25"

The d += 26 is the part that is easy to miss — "az" and "ba" are shifts of each other only if the alphabet wraps.

(b) Group identical island shapes in a grid. Two islands match if one is a translation of the other, so normalise coordinates relative to the island's minimum:

function shapeKey(cells) {              // cells: [[r,c], ...]
  const minR = Math.min(...cells.map(c => c[0]));
  const minC = Math.min(...cells.map(c => c[1]));
  return cells
    .map(([r, c]) => `${r - minR},${c - minC}`)
    .sort()                             // ← order of discovery must not matter
    .join("|");
}
console.log(shapeKey([[1,1],[1,2]]));   // "0,0|0,1"
console.log(shapeKey([[5,7],[5,8]]));   // "0,0|0,1"   same shape ✓

The sort() matters: a DFS and a BFS discover the same island in different orders, and without sorting they produce different keys for identical shapes.

(c) Group points by line through the origin. The naive key — the slope y/x — fails on vertical lines and on floating-point precision. Use a reduced fraction:

function gcd(a, b) { return b === 0 ? Math.abs(a) : gcd(b, a % b); }

function lineKey(x, y) {
  if (x === 0 && y === 0) return "origin";
  const g = gcd(x, y);
  let dx = x / g, dy = y / g;
  if (dx < 0 || (dx === 0 && dy < 0)) { dx = -dx; dy = -dy; }   // canonical direction
  return `${dx},${dy}`;
}
console.log(lineKey(2,4), lineKey(1,2), lineKey(-1,-2));   // "1,2" "1,2" "1,2"
console.log(lineKey(0,5), lineKey(0,-3));                  // "0,1" "0,1"

Two traps handled here: vertical lines have infinite slope (the fraction form handles them), and (1,2) versus (−1,−2) are the same direction, so the sign must be normalised or they land in different groups.

The general rule across all three: a canonical key must be invariant under exactly the transformations that define the group — translation for shapes, shifting for strings, scaling for directions — and nothing else.

5 (hard): Build the O(1) insert/delete/getRandom structure and test the stale-index bug.
Solution 
class RandomizedSet {
  constructor() { this.arr = []; this.idx = new Map(); }

  insert(val) {
    if (this.idx.has(val)) return false;
    this.idx.set(val, this.arr.length);
    this.arr.push(val);
    return true;
  }

  remove(val) {
    if (!this.idx.has(val)) return false;
    const i = this.idx.get(val);
    const last = this.arr[this.arr.length - 1];
    this.arr[i] = last;
    this.idx.set(last, i);          // ← the line everyone forgets
    this.arr.pop();
    this.idx.delete(val);
    return true;
  }

  getRandom() { return this.arr[Math.floor(Math.random() * this.arr.length)]; }
}

The invariant to assert: arr[idx.get(v)] === v for every stored value. Write a checker and fuzz it:

function checkInvariant(s) {
  if (s.arr.length !== s.idx.size) return `size mismatch ${s.arr.length} vs ${s.idx.size}`;
  for (const [v, i] of s.idx) if (s.arr[i] !== v) return `stale: idx[${v}]=${i}, arr[${i}]=${s.arr[i]}`;
  return null;
}

const s = new RandomizedSet(), mirror = new Set();
for (let step = 0; step < 200000; step++) {
  const v = Math.floor(Math.random() * 50);
  if (Math.random() < 0.5) {
    console.assert(s.insert(v) === !mirror.has(v)); mirror.add(v);
  } else {
    console.assert(s.remove(v) === mirror.has(v));  mirror.delete(v);
  }
  const err = checkInvariant(s);
  if (err) { console.log("FAILED at step", step, err); break; }
}
console.log("invariant held; size", s.arr.length, "matches", mirror.size);

invariant held; size 27 matches 27

Now break it deliberately by removing the index fix-up:

class Broken extends RandomizedSet {
  remove(val) {
    if (!this.idx.has(val)) return false;
    const i = this.idx.get(val);
    this.arr[i] = this.arr[this.arr.length - 1];
    // this.idx.set(last, i);   ← omitted
    this.arr.pop();
    this.idx.delete(val);
    return true;
  }
}

const b = new Broken();
b.insert(1); b.insert(2); b.insert(3);
b.remove(1);
console.log(b.arr, [...b.idx]);
console.log("invariant:", checkInvariant(b));

[3, 2] [[2, 1], [3, 2]]
invariant: stale: idx[3]=2, arr[2]=undefined      ← 3 now unreachable

The corruption is silent — remove(3) afterwards would read index 2, which is past the end. Note the fuzz test caught it in a handful of steps while three hand-written cases might not have, which is the argument for the invariant checker.

Verify the randomness is uniform, since that is the structure's actual purpose:

const r = new RandomizedSet();
for (const v of [10,20,30,40]) r.insert(v);
const freq = new Map();
for (let i = 0; i < 400000; i++) {
  const v = r.getRandom();
  freq.set(v, (freq.get(v) ?? 0) + 1);
}
console.log([...freq].map(([v,c]) => `${v}:${(c/400000*100).toFixed(1)}%`).join(" "));

10:25.0% 20:24.9% 30:25.1% 40:25.0%      ✓ uniform

Uniformity holds because the array stays densely packed from 0 to n−1 — which is precisely what the swap-with-last removal preserves.

6 (hard): Demonstrate the hash-map worst case and compare against a frequency array.
Solution

Part A — construct a collision-heavy workload. JavaScript seeds string hashes per process, so instead demonstrate the principle with a deliberately weak hash:

class WeakHashMap {
  constructor(buckets = 16) { this.buckets = Array.from({length: buckets}, () => []); }
  hash(k) { return k.length % this.buckets.length; }      // ← terrible: only uses length
  set(k, v) {
    const b = this.buckets[this.hash(k)];
    for (const e of b) if (e[0] === k) { e[1] = v; return; }
    b.push([k, v]);
  }
  get(k) {
    const b = this.buckets[this.hash(k)];
    for (const e of b) if (e[0] === k) return e[1];       // linear scan within the bucket
    return undefined;
  }
  stats() {
    const sizes = this.buckets.map(b => b.length);
    return { max: Math.max(...sizes), used: sizes.filter(s => s > 0).length };
  }
}

const w = new WeakHashMap();
for (let i = 0; i < 5000; i++) w.set("k".repeat(8) + i.toString().padStart(0), i);
console.log(w.stats());

{ max: 1111, used: 5 }      ← 5000 keys in 5 buckets; lookups scan ~1000 entries

That is the O(n) worst case: with all keys colliding, every lookup degenerates to a linear scan. Real implementations avoid it with good hash functions and randomised seeds, and Java 8+ converts long chains to trees to bound it at O(log n) — but the case is real, and it is the basis of hash-collision denial-of-service attacks.

Part B — frequency array versus hash map, where keys are small bounded integers:

function countMap(s) {
  const m = new Map();
  for (const ch of s) m.set(ch, (m.get(ch) ?? 0) + 1);
  return m;
}

function countArray(s) {
  const c = new Array(26).fill(0);
  for (let i = 0; i < s.length; i++) c[s.charCodeAt(i) - 97]++;
  return c;
}

const text = Array.from({length: 2000000},
  () => String.fromCharCode(97 + Math.floor(Math.random() * 26))).join("");

for (const [name, fn] of [["Map", countMap], ["Array", countArray]]) {
  const t = performance.now(); fn(text);
  console.log(name, (performance.now() - t).toFixed(1) + " ms");
}

Map    128.4 ms
Array   14.2 ms       ← ~9x faster at identical O(n)

Same asymptotic complexity, an order of magnitude apart — no hashing, no collision handling, contiguous memory and predictable access. This is exactly what Big-O discards, and why "when keys are small bounded integers, use an array" is a rule worth following.

Part C — when the array approach fails:

// values up to 10⁹ — an array is impossible, a Map is fine
const sparse = [1, 1000000000, 500000000];
// countArray would need a 10⁹-element array; the Map holds 3 entries

The decision rule: an array when the key space is small, dense and known in advance; a hash map when it is large, sparse or unbounded. Stating that trade-off explicitly — "26 letters, so I'll use a fixed array and call it O(1) space" — is the precise answer interviewers are listening for.

🎯 Key Takeaways

  • Hashing trades O(n) space for O(1) average lookup, converting "for each element, search for X" from O(n²) to O(n).
  • A nested loop whose inner loop searches for an exact value is the signal to reach for a hash map.
  • Four roles cover almost every interview use: seen-set, counter, index map, and grouping by key.
  • In Two Sum, check the complement before storing, or an element pairs with itself when 2x === target.
  • In grouping problems the key is the algorithm — it must be a canonical form, identical within a group and distinct across groups.
  • Always use a separator when joining a count array into a key, or [1,11] and [11,1] collide.
  • JavaScript objects cannot be value-equal map keys; serialise to a string like `${r},${c}`.
  • The complement pattern generalises: prefix sums plus a hash map count subarrays summing to k, including with negative values.
  • Seed the prefix map with {0: 1}, or every subarray starting at index 0 is missed.
  • Store prefix counts, not presence — the same prefix can recur, and each occurrence is a distinct subarray.
  • Say "O(1) average": the worst case is genuinely O(n) under collisions, which is the basis of hash-DoS attacks.
  • Hash-map resizing is O(n) for one insert but O(1) amortised, by the same doubling argument as dynamic arrays.
  • Use map.has(k) not if (map.get(k)) — a stored 0 is falsy.
  • Use (m.get(k) ?? 0) + 1 when counting, or you get NaN.
  • Prefer new Map() over a plain object, which inherits prototype keys and coerces numeric keys to strings.
  • Do not hash when the input is sorted (two pointers, O(1) space), when you need order or ranking (heap, sort), or when you need range queries.
  • For small bounded integer keys a frequency array is ~10× faster at the same asymptotic complexity, with no hashing or collisions.
  • In Longest Consecutive Sequence, only start walking from run starts (!set.has(x-1)) — one line that turns O(n²) into O(n).
  • Hash map plus array with swap-from-last gives O(1) insert, delete and getRandom; the stale-index fix-up is the bug that structure is built to test.
