Sliding Window Core Pattern

What you'll master: the fixed-size and variable-size window templates, and why the variable one is O(n) despite containing a nested loop; the monotonicity invariant that the entire pattern depends on, and how to test whether a problem has it before you commit; the longest-versus-shortest distinction that decides where your answer update goes; the counting trick that turns "at most k" into "exactly k"; and the specific conditions — negative numbers, non-contiguous requirements — under which sliding window silently produces wrong answers. Prerequisites: Two Pointers, Hashing.

Part 1 — The Idea and Its Precondition

A window is a contiguous range [left, right]. Instead of recomputing each range from scratch, you update incrementally: extend on the right, shrink on the left, and maintain a running summary.

recompute every window:            slide the window:
  for each start i                   right++ → add one element
    for each end j                   left++  → remove one element
      sum arr[i..j]     O(n²)                          O(n) total

The entire pattern rests on one property, and problems that lack it produce wrong answers with no error:

MONOTONICITY INVARIANT

  extending the window (right++)  makes the quantity move one way
  shrinking the window (left++)   makes it move the other way

e.g. positive numbers, sum:   extend → sum grows;  shrink → sum falls   ✓ valid
     with negatives, sum:     extend → sum may FALL                     ✗ invalid
🔑 Before writing a window, test the invariant on a two-element example. If extending the window can make the quantity you are tracking move in the "wrong" direction, then shrinking is no longer a reliable way to fix a violated condition — and the window will happily skip the correct answer. This single check is what separates a correct sliding-window solution from one that passes the sample and fails on hidden tests. When the invariant fails, the usual replacement is prefix sums plus a hash map.

Part 2 — Fixed-Size Windows

When the window size is given, there is no shrinking decision — add the incoming element, remove the outgoing one.

function maxSumFixed(nums, k) {
  let sum = 0;
  for (let i = 0; i < k; i++) sum += nums[i];      // first window
  let best = sum;

  for (let i = k; i < nums.length; i++) {
    sum += nums[i] - nums[i - k];                   // add new, drop old
    best = Math.max(best, sum);
  }
  return best;
}
// O(n) time, O(1) space

[2, 1, 5, 1, 3, 2], k = 3

first: 2+1+5 = 8            best 8
i=3:   8 + 1 - 2 = 7        best 8
i=4:   7 + 3 - 1 = 9        best 9
i=5:   9 + 2 - 5 = 6        best 9   ✓

Fixed windows work with negative numbers — this is the important exception. There is no shrink decision to make, so no monotonicity is required; you are simply evaluating every window of size k efficiently.

The same skeleton with a hash-map state handles character-based problems:

function findAnagrams(s, p) {                      // LC 438
  const need = new Array(26).fill(0), win = new Array(26).fill(0);
  for (const ch of p) need[ch.charCodeAt(0) - 97]++;
  const res = [];

  for (let i = 0; i < s.length; i++) {
    win[s.charCodeAt(i) - 97]++;                            // add
    if (i >= p.length) win[s.charCodeAt(i - p.length) - 97]--;  // remove
    if (i >= p.length - 1 && need.every((c, j) => c === win[j])) {
      res.push(i - p.length + 1);
    }
  }
  return res;
}

Comparing 26 counters per position is O(26n) = O(n) — a constant factor, not a log. A "matched counters" counter can avoid the rescan entirely, which Part 4 covers.

Part 3 — Variable-Size Windows

Most window problems have no fixed size: you extend until a condition breaks, then shrink until it holds again.

let left = 0;
for (let right = 0; right < n; right++) {
  add(arr[right]);                          // 1. extend

  while (windowIsInvalid()) {               // 2. shrink until valid
    remove(arr[left]);
    left++;
  }

  best = Math.max(best, right - left + 1);  // 3. record (for LONGEST)
}

Why this is O(n) despite the nested loop is the question interviewers ask, and the answer is an amortised argument: left only ever increases, and it can advance at most n times in total across the whole run. Each element is added exactly once and removed at most once — so the total work is 2n, not n².

function lengthOfLongestSubstring(s) {              // LC 3
  const lastSeen = new Map();
  let left = 0, best = 0;

  for (let right = 0; right < s.length; right++) {
    const ch = s[right];
    if (lastSeen.has(ch) && lastSeen.get(ch) >= left) {
      left = lastSeen.get(ch) + 1;                  // jump past the duplicate
    }
    lastSeen.set(ch, right);
    best = Math.max(best, right - left + 1);
  }
  return best;
}

The lastSeen.get(ch) >= left guard is essential. Without it, a character last seen before the current window drags left backwards, which both breaks the amortised argument and produces wrong answers:

s = "abba"

right=0 'a': left=0, best=1
right=1 'b': left=0, best=2
right=2 'b': last 'b' at 1 ≥ left → left=2, best=2
right=3 'a': last 'a' at 0 — BEFORE left=2, so IGNORE it
             without the guard: left = 0+1 = 1 ← moves BACKWARDS, window "bba" has a dup
             with the guard:    left stays 2, window "ba", best=2  ✓

Part 4 — Longest vs Shortest

Where you record the answer depends on which you are asked for, and getting this backwards is a common structural error.

LONGEST valid window                     SHORTEST valid window
────────────────────                     ─────────────────────
for right:                               for right:
  add(right)                               add(right)
  while (INVALID) shrink()                 while (VALID) {
  best = max(best, size)                     best = min(best, size)   ← record INSIDE
                                             shrink()
  ↑ record AFTER restoring validity        }
                                           ↑ shrink while it STAYS valid
LongestShortest
While-loop conditionWindow is invalidWindow is valid
Record the answerAfter the while loopInside the while loop
ExampleLongest substring without repeatsMinimum window substring
function minSubArrayLen(target, nums) {             // LC 209 — SHORTEST
  let left = 0, sum = 0, best = Infinity;
  for (let right = 0; right < nums.length; right++) {
    sum += nums[right];
    while (sum >= target) {                          // while VALID
      best = Math.min(best, right - left + 1);       // record inside
      sum -= nums[left++];                           // then shrink
    }
  }
  return best === Infinity ? 0 : best;
}

Minimum Window Substring is the hardest standard window problem, and the trick that makes it clean is tracking how many characters are fully satisfied rather than re-comparing maps:

function minWindow(s, t) {                          // LC 76
  if (t.length > s.length) return "";
  const need = new Map();
  for (const ch of t) need.set(ch, (need.get(ch) ?? 0) + 1);

  let required = need.size, formed = 0;             // ← distinct chars fully satisfied
  const win = new Map();
  let left = 0, bestLen = Infinity, bestStart = 0;

  for (let right = 0; right < s.length; right++) {
    const c = s[right];
    win.set(c, (win.get(c) ?? 0) + 1);
    if (need.has(c) && win.get(c) === need.get(c)) formed++;   // exactly equal → newly satisfied

    while (formed === required) {                    // while VALID
      if (right - left + 1 < bestLen) { bestLen = right - left + 1; bestStart = left; }
      const d = s[left++];
      win.set(d, win.get(d) - 1);
      if (need.has(d) && win.get(d) < need.get(d)) formed--;  // dropped below → no longer satisfied
    }
  }
  return bestLen === Infinity ? "" : s.substr(bestStart, bestLen);
}
// O(|s| + |t|) time

Use === when incrementing formed and < when decrementing. Using >= on the way up would count the same character repeatedly when the window holds surplus copies, and the answer silently becomes wrong.

Part 5 — The "At Most K" Counting Trick

Counting subarrays rather than finding one is a different job, and a neat identity handles it:

exactly(k) = atMost(k) - atMost(k - 1)

Sliding window naturally computes "at most k", because the window can always be shrunk until the condition holds. "Exactly k" is not directly windowable — so compute the easier quantity twice.

function subarraysWithKDistinct(nums, k) {          // LC 992
  return atMostK(nums, k) - atMostK(nums, k - 1);
}

function atMostK(nums, k) {
  const count = new Map();
  let left = 0, total = 0;
  for (let right = 0; right < nums.length; right++) {
    count.set(nums[right], (count.get(nums[right]) ?? 0) + 1);
    while (count.size > k) {
      const v = nums[left++];
      count.set(v, count.get(v) - 1);
      if (count.get(v) === 0) count.delete(v);
    }
    total += right - left + 1;                       // ← all subarrays ENDING at right
  }
  return total;
}

total += right - left + 1 is the counting insight. Every subarray ending at right and starting anywhere in [left, right] is valid, and there are exactly right - left + 1 of them — so you count a whole family in O(1) rather than enumerating.

Binary subarrays with sum exactly katMostSum(k) − atMostSum(k−1)
Count of nice subarrays (k odd numbers)Same identity, counting odds
Subarrays with product < kDirectly "at most" — no subtraction needed

Part 6 — When Sliding Window Is Wrong

The pattern fails in two specific ways, and both produce plausible wrong answers rather than errors.

Failure 1: negative numbers break monotonicity.

"longest subarray with sum ≤ target", values may be negative

[5, -10, 5], target 0

window [5]        sum 5  > 0 → shrink? but shrinking makes it EMPTY
extend to [5,-10] sum -5 ≤ 0  ← extending FIXED the violation

Shrinking is supposed to be the way to repair a violated condition. With negatives, extending can repair it too — so the window logic has no reliable direction, and it skips valid answers. The replacement is prefix sums with a hash map (or a monotonic deque for the "shortest subarray with sum ≥ k" variant).

Failure 2: the problem is not about contiguous ranges.

WordingContiguous?Pattern
"subarray", "substring"YesSliding window
"subsequence"No — order kept, gaps allowedDP, or greedy
"subset"No — any selectionSubset DP, backtracking

Read that word carefully. "Longest contiguous subarray summing to k" and "longest subsequence summing to k" differ by one word and are different problems with different complexities.

❌ Applying the window template because the problem says "subarray", without checking the invariant. The recognition cue is real and usually right, so it becomes automatic — and then a problem allows negative values, extending the window reduces the sum, and the shrink logic quietly skips the correct answer. The code passes the sample input, passes the obvious hand-written tests, and fails on hidden cases where a negative number sits in the middle of the optimal range.

✅ Test the invariant on two elements before writing the loop. "If I extend this window, does my tracked quantity always move one way? If I shrink it, does it always move the other?" With all positive values and a sum, yes. With negatives, no — and the answer is prefix sums plus a hash map, which does not need monotonicity at all. Ten seconds of checking prevents the class of bug that is hardest to find by testing.

Interview Questions

Beginner: Find the maximum sum of a contiguous subarray of size k.

A fixed-size window: compute the first window, then slide by adding the incoming element and subtracting the outgoing one.

function maxSumFixed(nums, k) {
  if (nums.length < k) return null;
  let sum = 0;
  for (let i = 0; i < k; i++) sum += nums[i];
  let best = sum;
  for (let i = k; i < nums.length; i++) {
    sum += nums[i] - nums[i - k];         // add new, drop old — O(1) per step
    best = Math.max(best, sum);
  }
  return best;
}
// O(n) time, O(1) space

The naive version recomputes each window, which is O(n·k):

for (let i = 0; i + k <= n; i++) {
  let s = 0;
  for (let j = i; j < i + k; j++) s += nums[j];   // rescans the overlap every time
  best = Math.max(best, s);
}

Consecutive windows share k−1 elements, so recomputing them is pure waste — that observation is the entire pattern.

[2,1,5,1,3,2], k=3
2+1+5 = 8
8 + 1 - 2 = 7
7 + 3 - 1 = 9      ← best
9 + 2 - 5 = 6

Worth stating: this works with negative numbers. Fixed-size windows need no monotonicity because there is no shrink decision — you are just evaluating every size-k window efficiently. It is the variable-size version that requires all-positive values.

Edge cases: nums.length < k, and k === nums.length (one window, the loop never runs).

Beginner: Find the length of the longest substring without repeating characters.

A variable window that extends on the right and jumps left past any duplicate.

function lengthOfLongestSubstring(s) {
  const lastSeen = new Map();
  let left = 0, best = 0;
  for (let right = 0; right < s.length; right++) {
    const ch = s[right];
    if (lastSeen.has(ch) && lastSeen.get(ch) >= left) {
      left = lastSeen.get(ch) + 1;         // jump past the previous occurrence
    }
    lastSeen.set(ch, right);
    best = Math.max(best, right - left + 1);
  }
  return best;
}
// O(n) time, O(min(n, alphabet)) space

The >= left guard is the part that gets missed, and it matters:

s = "abba"
right=3, character 'a', last seen at index 0
  but left is already 2 — that 'a' is OUTSIDE the window

without the guard: left = 0 + 1 = 1   ← moves BACKWARDS
                   window becomes "bba", which contains a duplicate  ✗
with the guard:    left stays 2, window "ba"                          ✓

Beyond correctness, moving left backwards would break the O(n) argument — the amortised bound depends on left only ever increasing.

The alternative formulation uses a Set and shrinks one step at a time:

const set = new Set();
let left = 0, best = 0;
for (let right = 0; right < s.length; right++) {
  while (set.has(s[right])) set.delete(s[left++]);   // shrink until the dup is gone
  set.add(s[right]);
  best = Math.max(best, right - left + 1);
}

Both are O(n). The jump version does fewer operations; the set version is closer to the generic template and slightly easier to get right under pressure.

Mid: Why is the variable-size window O(n) when it contains a nested loop?

Because the inner loop's total work across the entire run is bounded by n, not by n per outer iteration. This is an amortised argument, and interviewers ask for it specifically.

for (let right = 0; right < n; right++) {
  add(arr[right]);
  while (invalid()) { remove(arr[left]); left++; }    // ← looks like it could be O(n)
  best = Math.max(best, right - left + 1);
}

The argument:

- `right` advances exactly n times.
- `left` only ever INCREASES, and it can never exceed `right`.
- So `left` advances at most n times in TOTAL, across all iterations combined.
- Each element is added exactly once and removed at most once.

⟹ total operations ≤ 2n  ⟹  O(n)

The intuition to state: the inner while loop may run many times in one iteration and zero times in the next, but the sum of its iterations over the whole algorithm is at most n. Averaged out, each outer step does O(1) work.

This is the same shape of argument as amortised push on a dynamic array, monotonic stacks (each index pushed and popped once), and Longest Consecutive Sequence in Hashing.

The condition that breaks it is moving left backwards. If any code path does left = something_smaller, the bound collapses and the algorithm can genuinely become O(n²) — which is exactly why the lastSeen ≥ left guard is a performance requirement as well as a correctness one.

Mid: Solve Minimum Window Substring. What makes it harder than the longest-window problems?

Three things: it asks for the shortest valid window (so the answer is recorded inside the shrink loop), the validity check involves character counts rather than presence, and naively re-comparing two maps on every step would make it O(n · alphabet).

function minWindow(s, t) {
  if (t.length > s.length) return "";
  const need = new Map();
  for (const ch of t) need.set(ch, (need.get(ch) ?? 0) + 1);

  let required = need.size, formed = 0;
  const win = new Map();
  let left = 0, bestLen = Infinity, bestStart = 0;

  for (let right = 0; right < s.length; right++) {
    const c = s[right];
    win.set(c, (win.get(c) ?? 0) + 1);
    if (need.has(c) && win.get(c) === need.get(c)) formed++;

    while (formed === required) {                 // VALID → try to shrink
      if (right - left + 1 < bestLen) { bestLen = right - left + 1; bestStart = left; }
      const d = s[left++];
      win.set(d, win.get(d) - 1);
      if (need.has(d) && win.get(d) < need.get(d)) formed--;
    }
  }
  return bestLen === Infinity ? "" : s.substr(bestStart, bestLen);
}
// O(|s| + |t|)

The formed counter is the key optimisation: it tracks how many distinct required characters currently have enough copies in the window, so validity is a single integer comparison instead of a map walk.

The comparison operators are exact, and both are easy to get wrong:

incrementing:  win.get(c) === need.get(c)     ✓ fires exactly once, when it becomes satisfied
               win.get(c) >= need.get(c)      ✗ fires again for every surplus copy → formed too high

decrementing:  win.get(d) < need.get(d)       ✓ fires only when it drops below
               win.get(d) <= need.get(d)      ✗ fires while still satisfied → formed too low

The structural difference from "longest" is worth stating explicitly, since it is the thing candidates invert:

LongestShortest
Shrink whileInvalidValid
RecordAfter the while loopInside, before shrinking

Edge cases: t longer than s; t with repeated characters (which is why counts, not a set, are needed); and no valid window at all, which must return the empty string rather than a garbage substring.

Senior: Count subarrays with exactly k distinct integers. Why can't a window do this directly?

Because "exactly k" is not a shrinkable condition. A sliding window works by maintaining an invariant it can always restore by shrinking — but for a fixed right, the subarrays with exactly k distinct values form a contiguous range of start positions, not a single boundary, so there is no unique window to maintain.

The identity that solves it:

exactly(k) = atMost(k) - atMost(k-1)

"At most k" is shrinkable: whenever the window has too many distinct values, shrink from the left until it does not.

function subarraysWithKDistinct(nums, k) {
  return atMostK(nums, k) - atMostK(nums, k - 1);
}

function atMostK(nums, k) {
  const count = new Map();
  let left = 0, total = 0;
  for (let right = 0; right < nums.length; right++) {
    count.set(nums[right], (count.get(nums[right]) ?? 0) + 1);
    while (count.size > k) {
      const v = nums[left++];
      count.set(v, count.get(v) - 1);
      if (count.get(v) === 0) count.delete(v);      // ← or size is wrong
    }
    total += right - left + 1;
  }
  return total;
}
// O(n) — two passes

total += right - left + 1 counts a whole family at once: every subarray ending at right whose start lies in [left, right] is valid, and there are exactly that many. Enumerating them individually would make the solution O(n²).

nums = [1,2,1,2,3], k = 2

atMost(2) = 12    atMost(1) = 5    → exactly(2) = 7
verify by hand: [1,2] [2,1] [1,2] [2,3] [1,2,1] [2,1,2] [1,2,1,2]  = 7  ✓

Deleting zero-count keys is a real bug source — Map.size counts keys, not non-zero values, so leaving a key at count 0 makes the window think it holds a character it does not.

The identity generalises to any "exactly k" over a monotone-in-k property: binary subarrays with sum exactly k, subarrays with exactly k odd numbers, and so on. Recognising that "exactly" should become a difference of two "at most" computations is the transferable insight.

Senior: When does sliding window silently produce wrong answers, and what replaces it?

When the monotonicity invariant does not hold. The window's logic assumes that extending moves the tracked quantity one way and shrinking moves it the other — and when that assumption fails, the algorithm still runs, still returns a number, and that number is wrong.

The canonical failure is negative values:

"longest subarray with sum ≤ target",  nums = [5, -10, 5],  target = 0

window [5]:        sum 5 > 0 → invalid → shrink → window empty
extend to [5,-10]: sum -5 ≤ 0 → VALID, length 2

Extending REPAIRED the violation. The shrink logic assumed only shrinking could,
so it discarded the start of the optimal window before ever reaching it.
SituationWhy the window failsUse instead
Sum with negative valuesExtending can decrease the sumPrefix sum + hash map
Shortest subarray with sum ≥ k, negatives allowedSamePrefix sums + monotonic deque
"Subsequence" rather than "subarray"Not contiguousDP or greedy
"Subset"No ordering or contiguity at allSubset-sum DP, backtracking
Product with zeros or values < 1Extending can decrease the productHandle zeros separately, or prefix products

The test I would apply before committing: take a two-element example and ask whether extending can move the quantity in the "wrong" direction. For sums with all-positive values, no — the window is safe. For sums with negatives, yes — it is not.

Prefix sums are the general replacement because they need no monotonicity at all: the identity sum(i..j) = prefix[j] − prefix[i−1] holds regardless of sign, which turns the problem into a lookup rather than a boundary search.

The subtlety worth flagging: fixed-size windows remain valid with negative numbers, because there is no shrink decision to make. So "does this problem allow negatives?" only disqualifies the variable-size template — which is a distinction that saves you from over-correcting.

    while (count.size > k) {
      const v = nums[left++];
      count.set(v, count.get(v) - 1);
    }
    total += r - left + 1;
  }
  return total;
}

// (d) window size
function countWindows(nums, k) {
  let left = 0, c = 0;
  for (let r = 0; r < nums.length; r++) {
    if (r - left > k) left++;
    c++;
  }
  return c;
}

// (e) max sum of size k
function maxSum(nums, k) {
  let sum = 0, best = -Infinity;
  for (let i = 0; i < nums.length; i++) {
    sum += nums[i];
    if (i >= k) sum -= nums[i-k];
    best = Math.max(best, sum);
  }
  return best;
}

3 (medium): Solve Minimum Window Substring and verify against brute force.
Solution 
function minWindow(s, t) {
  if (!s || !t || t.length > s.length) return "";
  const need = new Map();
  for (const ch of t) need.set(ch, (need.get(ch) ?? 0) + 1);

  let required = need.size, formed = 0;
  const win = new Map();
  let left = 0, bestLen = Infinity, bestStart = 0;

  for (let right = 0; right < s.length; right++) {
    const c = s[right];
    win.set(c, (win.get(c) ?? 0) + 1);
    if (need.has(c) && win.get(c) === need.get(c)) formed++;

    while (formed === required) {
      if (right - left + 1 < bestLen) { bestLen = right - left + 1; bestStart = left; }
      const d = s[left++];
      win.set(d, win.get(d) - 1);
      if (need.has(d) && win.get(d) < need.get(d)) formed--;
    }
  }
  return bestLen === Infinity ? "" : s.substr(bestStart, bestLen);
}

4 (medium): Prove that sliding window fails with negative numbers.
Solution

Implement the window version and a correct prefix-sum version of "longest subarray with sum ≤ target", then find the inputs where they disagree:

// window version — assumes monotonicity
function longestWindow(nums, target) {
  let left = 0, sum = 0, best = 0;
  for (let right = 0; right < nums.length; right++) {
    sum += nums[right];
    while (sum > target && left <= right) sum -= nums[left++];
    best = Math.max(best, right - left + 1);
  }
  return best;
}

// brute-force reference
function longestBrute(nums, target) {
  let best = 0;
  for (let i = 0; i < nums.length; i++) {
    let s = 0;
    for (let j = i; j < nums.length; j++) {
      s += nums[j];
      if (s <= target) best = Math.max(best, j - i + 1);
    }
  }
  return best;
}

nums = [5, -6, 4], target = 3
true answer: the WHOLE array sums to 3 ≤ 3 → length 3

The window discarded the 5 because it looked too big — but the −6 that follows would have repaired the violation. Shrinking is not the only way to restore validity when negatives exist, so the window's core assumption is false.

5 (hard): Implement the "exactly k" counting identity and verify it.
Solution 
function atMostK(nums, k) {
  if (k < 0) return 0;
  const count = new Map();
  let left = 0, total = 0;
  for (let right = 0; right < nums.length; right++) {
    count.set(nums[right], (count.get(nums[right]) ?? 0) + 1);
    while (count.size > k) {
      const v = nums[left++];
      count.set(v, count.get(v) - 1);
      if (count.get(v) === 0) count.delete(v);
    }
    total += right - left + 1;
  }
  return total;
}

Extend the identity to a different property to show it generalises:

// count subarrays with exactly k odd numbers (LC 1248)
function atMostOdd(nums, k) {
  let left = 0, odds = 0, total = 0;
  for (let right = 0; right < nums.length; right++) {
    if (nums[right] % 2) odds++;
    while (odds > k) { if (nums[left++] % 2) odds--; }
    total += right - left + 1;
  }
  return total;
}

6 (hard): Solve Sliding Window Maximum with a monotonic deque.
Solution

The problem: return the maximum of every window of size k. The naive approach rescans each window for O(n·k); a heap gives O(n log k); a monotonic deque gives O(n).

function maxSlidingWindow(nums, k) {
  const dq = [];            // holds INDICES; their values are strictly decreasing
  const out = [];
  for (let i = 0; i < nums.length; i++) {
    if (dq.length && dq[0] <= i - k) dq.shift();              // front expired
    while (dq.length && nums[dq[dq.length-1]] <= nums[i]) dq.pop();  // dominated
    dq.push(i);
    if (i >= k - 1) out.push(nums[dq[0]]);                    // front is the max
  }
  return out;
}

The domination argument is the insight: if nums[i] is at least as large as an earlier element and arrives later, that earlier element can never be the maximum of any future window — it is both smaller and expires sooner. So it can be discarded permanently.

Why it is O(n) despite the inner while loop: each index is pushed exactly once and popped at most once, so total deque operations are bounded by 2n. Same amortised argument as the window itself.

One production caveat: dq.shift() is O(n) on a JavaScript array (see Arrays & Strings). It is fine here because it happens at most once per iteration, but for a true deque a head index or linked structure is safer — and pointing that out is a good senior signal.

🎯 Key Takeaways

  • A sliding window updates a contiguous range incrementally instead of recomputing it, turning O(n²) into O(n).
  • The pattern depends on a monotonicity invariant: extending must move the tracked quantity one way and shrinking the other.
  • Test that invariant on a two-element example before writing the loop — when it fails, the window returns wrong answers with no error.
  • Fixed-size windows need no monotonicity, so they remain valid with negative numbers; only the variable-size template is disqualified.
  • The variable template is O(n) because left only increases and advances at most n times in total — an amortised argument interviewers ask for.
  • Never move left backwards; it breaks both correctness and the O(n) bound (the lastSeen ≥ left guard).
  • For longest: shrink while invalid, record after the loop. For shortest: shrink while valid, record inside the loop.
  • Inverting that structure is the most common structural error, and it produces plausible off-by-one answers.
  • Track a formed counter for multi-character conditions instead of comparing maps — === when incrementing, < when decrementing.
  • Delete zero-count keys from the window map, or map.size counts values the window no longer holds.
  • "Exactly k" is not directly windowable; use atMost(k) − atMost(k−1).
  • total += right − left + 1 counts every subarray ending at right in O(1) — the trick that keeps counting problems linear.
  • Negative values break the sum invariant because extending can repair a violation that shrinking was supposed to fix — use prefix sums instead.
  • "Subsequence" and "subset" are not windows; only "subarray" and "substring" guarantee contiguity.
  • Sliding Window Maximum needs a monotonic deque: an element smaller than a later arrival is dominated and can be discarded permanently.
  • Window size is right − left + 1 — trace a single-element window to catch the off-by-one.
