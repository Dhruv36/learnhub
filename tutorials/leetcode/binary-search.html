Binary Search & Variants Core Pattern

What you'll master: why the classic three-branch template produces off-by-one bugs and how the predicate formulation eliminates them entirely; the boundary-search template that answers lower-bound, upper-bound, first-true and last-true with one piece of code; binary search on the answer — the technique behind Koko Eating Bananas, Split Array Largest Sum and capacity problems — and how to spot it; rotated-array search and why its invariant is "one half is always sorted"; and the loop-invariant discipline that makes termination provable rather than hopeful. Prerequisites: Big-O, Arrays & Strings.

Part 1 — Why the Classic Template Causes Bugs

Everyone learns this version first, and it is correct for exact-match search:

function search(nums, target) {                  // LC 704
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (nums[mid] === target) return mid;
    if (nums[mid] < target) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}

The trouble starts the moment the question is not "is it present". "First element ≥ target", "last element < target", "insert position" — each needs different treatment of the three branches, and there are four independent decisions to get right:

DecisionOptionsGetting it wrong causes
Bound typehi = n-1 or hi = nMissing the insert-at-end case
Loop conditionlo <= hi or lo < hiInfinite loop or a skipped element
Updatehi = mid - 1 or hi = midInfinite loop or overshooting
Returnlo, hi, or lo - 1Off by one

That is 2×2×2×3 combinations and only a few are correct, which is why binary search has a reputation for being deceptively hard. The fix is to stop enumerating cases and adopt a single formulation.

🔑 Reframe every binary search as finding a boundary in a monotone predicate. If you can write a function f(i) that is false, false, …, false, true, true, …, true — never flipping back — then binary search finds the first true in one template, with one loop condition and one update rule. Exact match becomes a special case. This single change eliminates the entire category of off-by-one bugs, because there are no longer any variants to remember.

Part 2 — The Boundary Template

      index:   0  1  2  3  4  5  6
      f(i):    F  F  F  T  T  T  T
                       ↑
                  first true — the answer

function firstTrue(lo, hi, f) {                  // hi is EXCLUSIVE
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (f(mid)) hi = mid;                        // mid might be the answer — KEEP it
    else lo = mid + 1;                           // mid is definitely not — discard it
  }
  return lo;                                     // == hi; may be the original hi (no true)
}

Three properties make this template safe:

PropertyWhy it holds
TerminatesThe range shrinks every iteration: hi = mid < hi or lo = mid+1 > lo
No infinite loopmid rounds down, so hi = mid strictly decreases hi
Correct on exitInvariant: everything < lo is false, everything ≥ hi is true

Every standard variant is now a choice of predicate:

lower_bound (first ≥ target):   firstTrue(0, n, i => nums[i] >= target)
upper_bound (first > target):   firstTrue(0, n, i => nums[i] >  target)
last < target:                  firstTrue(0, n, i => nums[i] >= target) - 1
count of target:                upper_bound - lower_bound
insert position:                lower_bound
exact match:                    const i = lower_bound; nums[i] === target ? i : -1

function searchRange(nums, target) {             // LC 34
  const lo = firstTrue(0, nums.length, i => nums[i] >= target);
  if (lo === nums.length || nums[lo] !== target) return [-1, -1];
  const hi = firstTrue(0, nums.length, i => nums[i] > target) - 1;
  return [lo, hi];
}

mid = lo + ((hi - lo) >> 1) rather than (lo + hi) / 2 avoids integer overflow in languages with fixed-width ints. JavaScript numbers do not overflow at these sizes, but the habit costs nothing and transfers to Java, C++ and Go — where it is a real, famous bug that sat in the JDK for years.

Part 3 — Binary Search on the Answer

The most valuable variant searches a range of possible answers rather than an array. It applies whenever a candidate answer can be checked for feasibility, and feasibility is monotone.

"minimum X such that condition(X) holds"

     X:          1  2  3  4  5  6  7  8
  feasible:      F  F  F  T  T  T  T  T
                          ↑ binary search for this

function minEatingSpeed(piles, h) {              // LC 875
  const canFinish = k => {
    let hours = 0;
    for (const p of piles) hours += Math.ceil(p / k);
    return hours <= h;                           // MONOTONE: faster is never worse
  };
  return firstTrue(1, Math.max(...piles) + 1, canFinish);
}
// O(n log(max)) — the log is over the ANSWER range, not the array

The recognition signals are consistent across every problem in this family:

SignalExample
"minimum X such that…" / "maximum X such that…"Koko, Ship Packages, Split Array
Checking a specific X is easy; finding the best X is notAny capacity/rate problem
Feasibility is monotone in XMore capacity never hurts
"Minimise the maximum" / "maximise the minimum"Split Array Largest Sum, Magnetic Force

Split Array Largest Sum (LC 410) is the same shape with a greedy feasibility check:

function splitArray(nums, k) {
  const canSplit = cap => {
    let parts = 1, sum = 0;
    for (const x of nums) {
      if (sum + x > cap) { parts++; sum = x; }    // greedy: cut as late as possible
      else sum += x;
    }
    return parts <= k;
  };
  const lo = Math.max(...nums);                  // a part must hold the largest element
  const hi = nums.reduce((a,b) => a+b, 0);       // one part holds everything
  return firstTrue(lo, hi + 1, canSplit);
}

Choosing the bounds is half the work, and both must be justified: the answer can never be below the largest single element (it cannot be split), and never above the total sum. Setting lo = 0 still works but wastes iterations; setting it too high skips the answer entirely.

Part 4 — Rotated and Unsorted-Looking Arrays

Binary search needs a monotone property, not a fully sorted array. A rotated sorted array has one: at least one half is always sorted.

[4,5,6,7,0,1,2]        mid = 7
 └─ sorted ─┘

nums[lo] <= nums[mid]  ⟹  the LEFT half is sorted
otherwise              ⟹  the RIGHT half is sorted

function searchRotated(nums, target) {           // LC 33
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (nums[mid] === target) return mid;

    if (nums[lo] <= nums[mid]) {                 // left half sorted
      if (nums[lo] <= target && target < nums[mid]) hi = mid - 1;
      else lo = mid + 1;
    } else {                                     // right half sorted
      if (nums[mid] < target && target <= nums[hi]) lo = mid + 1;
      else hi = mid - 1;
    }
  }
  return -1;
}

Finding the rotation point is cleaner as a boundary search, and it is the version worth memorising:

function findMin(nums) {                         // LC 153
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (nums[mid] > nums[hi]) lo = mid + 1;      // minimum is strictly right
    else hi = mid;                               // mid could BE the minimum
  }
  return nums[lo];
}

Compare against nums[hi], not nums[lo]. Comparing with nums[lo] fails on a non-rotated array — [1,2,3] has nums[mid] > nums[lo], which would send the search right, away from the true minimum at index 0.

Duplicates break the guarantee (LC 154): when nums[lo] === nums[mid] === nums[hi], neither half is provably sorted, and the only correct response is to shrink by one — degrading the worst case to O(n):

if (nums[mid] === nums[hi]) hi--;                // cannot decide; give up one element

Part 5 — Loop Invariants and Termination

Rather than testing templates until the samples pass, state the invariant and the code follows from it.

INVARIANT for firstTrue:
    every index <  lo   →  f is FALSE
    every index >= hi   →  f is TRUE
    the answer is in [lo, hi]

initially: lo = 0, hi = n   → vacuously true
each step: preserved by construction
at exit:   lo === hi        → the answer is exactly lo
SymptomCauseFix
Infinite looplo = mid when mid can equal loUse lo = mid + 1, or bias mid upward
Off by one at the endExclusive/inclusive hi mismatchPick exclusive hi = n and keep it
Misses the last elementhi = n - 1 with lo < hiUse hi = n
Wrong on empty inputAccessing nums[0] unguardedThe template handles it — lo === hi === 0

The one case that needs lo = mid is a "last true" search, and it requires biasing the midpoint upward or it loops forever:

function lastTrue(lo, hi, f) {                   // hi INCLUSIVE here
  while (lo < hi) {
    const mid = lo + ((hi - lo + 1) >> 1);       // ← +1 rounds UP
    if (f(mid)) lo = mid;
    else hi = mid - 1;
  }
  return lo;
}

Without the +1, lo = mid with lo = 3, hi = 4 computes mid = 3 and never advances. Rounding up guarantees progress. Simpler still: express "last true" as firstTrue(…) - 1 with the negated predicate and never write this variant.

❌ Adjusting < versus <= and mid versus mid ± 1 until the sample tests pass. There are a dozen plausible combinations, two or three of which are correct for the specific case being tested, and the rest fail on an empty array, a single element, a target beyond the end, or duplicates. The code passes the visible tests and breaks on the hidden ones, and no amount of staring reveals which combination is right because the choice was never grounded in anything.

✅ Write the predicate first, then use the one template unchanged. Decide what f(i) means, confirm it is monotone (false…false, true…true), and call firstTrue(0, n, f). The loop condition is always lo < hi, the updates are always hi = mid / lo = mid + 1, and the answer is always lo. The only per-problem thinking is the predicate and the bounds — which is exactly where the thinking belongs.

Find Peak Element (LC 162) is the case people find surprising — an unsorted array, yet binary search applies:

function findPeakElement(nums) {
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (nums[mid] < nums[mid + 1]) lo = mid + 1;  // uphill to the right
    else hi = mid;                               // mid could be the peak
  }
  return lo;
}

It works because moving uphill guarantees a peak in that direction: with boundaries treated as −∞, an ascending step means the right side must eventually turn down, so a peak exists there.

Interview Questions

Beginner: Implement binary search and explain why it is O(log n). 
function search(nums, target) {
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (nums[mid] === target) return mid;
    if (nums[mid] < target) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}

The complexity: each iteration discards half the remaining range, so after k iterations the range has size n/2ᵏ. The loop ends when that reaches 1, giving n/2ᵏ = 1 ⟹ k = log₂n.

n = 1,000,000  →  20 iterations
n = 1,000,000,000  →  30 iterations

lo + ((hi - lo) >> 1) rather than (lo + hi) / 2 avoids overflow when both indices are large. In JavaScript numbers are doubles so it cannot overflow at realistic sizes, but the same code in Java or C++ breaks — this was a real bug in the JDK's Arrays.binarySearch for nine years.

The requirement is a sorted array, or more precisely a monotone property. If the array is unsorted, sorting first costs O(n log n) — which is only worth it for repeated searches; a single lookup is better served by a linear scan.

I would note that this template only answers "is it present". For "first occurrence", "insert position" or "count of target", I would switch to the boundary formulation — find the first index where a monotone predicate becomes true — which handles all of those with one template instead of several variants.

Beginner: Find the first and last position of a target in a sorted array.

Two boundary searches: the first index with nums[i] >= target, and the first with nums[i] > target minus one.

function firstTrue(lo, hi, f) {                  // hi exclusive
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (f(mid)) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}

function searchRange(nums, target) {
  const n = nums.length;
  const lo = firstTrue(0, n, i => nums[i] >= target);
  if (lo === n || nums[lo] !== target) return [-1, -1];
  const hi = firstTrue(0, n, i => nums[i] > target) - 1;
  return [lo, hi];
}
// O(log n), two passes

nums = [5,7,7,8,8,10], target = 8

predicate nums[i] >= 8 :  F F F T T T   → first true at 3
predicate nums[i] >  8 :  F F F F F T   → first true at 5, minus 1 = 4
→ [3, 4]  ✓

The check lo === n || nums[lo] !== target is required, because the lower-bound search returns an insert position, not a match. For a target absent from the array it returns where the target would go, and the value there is a different number.

Both predicates are monotone, which is what licenses binary search: nums[i] >= 8 is false for a prefix and true for the rest, never flipping back, because the array is sorted.

The same two searches give the count — upper_bound − lower_bound — which is why this template is worth internalising over memorising a separate "find first occurrence" variant.

Mid: Search a rotated sorted array in O(log n).

The array is not sorted, but it retains a usable invariant: splitting at any midpoint leaves at least one half sorted. Identify which, then decide whether the target lies in it.

function search(nums, target) {
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (nums[mid] === target) return mid;

    if (nums[lo] <= nums[mid]) {                 // LEFT half is sorted
      if (nums[lo] <= target && target < nums[mid]) hi = mid - 1;
      else lo = mid + 1;
    } else {                                     // RIGHT half is sorted
      if (nums[mid] < target && target <= nums[hi]) lo = mid + 1;
      else hi = mid - 1;
    }
  }
  return -1;
}

[4,5,6,7,0,1,2], target = 0

lo=0 hi=6 mid=3 (7):  nums[0]=4 <= 7 → left sorted [4..7]
                      is 0 in [4,7)? no → search right, lo=4
lo=4 hi=6 mid=5 (1):  nums[4]=0 <= 1 → left sorted [0..1]
                      is 0 in [0,1)? YES → hi=4
lo=4 hi=4 mid=4 (0):  found → 4  ✓

The <= in nums[lo] <= nums[mid] matters for the two-element case: with lo === mid, the left half is trivially sorted and strict < would misclassify it.

The range checks use asymmetric strictness — nums[lo] <= target < nums[mid] — because nums[mid] was already tested for equality and excluded.

Duplicates break the invariant (LC 81): if nums[lo] === nums[mid] === nums[hi], as in [1,1,1,0,1], neither half is provably sorted. The only correct move is hi--, which degrades the worst case to O(n) — and that degradation is unavoidable, since an array of all-equal values with one different element requires a linear scan to find it.

An alternative worth mentioning: find the rotation index first (a clean boundary search), then do an ordinary binary search on the appropriate segment. Two simple searches instead of one intricate one, at the same complexity — and easier to get right under pressure.

Mid: Koko eats bananas — find the minimum eating speed. Why is this binary search?

Because the answer space is monotone: if Koko finishes in time at speed k, she also finishes at any speed greater than k. So feasibility as a function of speed is false…false, true…true, and binary search finds the boundary.

function minEatingSpeed(piles, h) {
  const canFinish = k => {
    let hours = 0;
    for (const p of piles) hours += Math.ceil(p / k);
    return hours <= h;
  };
  return firstTrue(1, Math.max(...piles) + 1, canFinish);
}
// O(n log(max pile))

piles = [3,6,7,11], h = 8

speed:      1   2   3   4   5   6   7   8
hours:     27  15  10   8   7   6   5   4
feasible:   F   F   F   T   T   T   T   T
                        ↑ answer = 4

The bounds must be justified: speed 1 is the slowest meaningful rate, and max(piles) is the fastest useful one — beyond it, each pile still takes exactly one hour, so nothing improves. Using a larger upper bound is harmless but wasteful; a smaller one can exclude the answer.

Note that each pile takes ceil(p/k) hours, not p/k — Koko does not move to the next pile within an hour. Getting that wrong produces a feasibility function that is subtly too optimistic and an answer that is too small.

The general recognition rule: when checking one candidate answer is easy but finding the best is not, and feasibility is monotone, binary search the answer range. The whole family shares this shape:

ProblemSearch overFeasibility check
Koko (875)Eating speedTotal hours ≤ h
Ship Packages (1011)Ship capacityDays needed ≤ D
Split Array (410)Largest subarray sumParts needed ≤ k
Magnetic Force (1552)Minimum gapBalls placeable ≥ m

The complexity is O(n log(range)), and the log is over the answer range rather than the input size — which is why it stays fast even when the range is 10⁹.

Senior: Split an array into k subarrays minimising the largest subarray sum.

"Minimise the maximum" is the signature of binary search on the answer. Rather than searching over partitions — exponentially many — search over the answer value and test feasibility greedily.

function splitArray(nums, k) {
  const canSplit = cap => {
    let parts = 1, sum = 0;
    for (const x of nums) {
      if (sum + x > cap) { parts++; sum = x; }    // greedy: extend until it overflows
      else sum += x;
    }
    return parts <= k;
  };

  const lo = Math.max(...nums);                  // no part can be smaller than this
  const hi = nums.reduce((a, b) => a + b, 0);    // one part holding everything
  return firstTrue(lo, hi + 1, canSplit);
}
// O(n log(sum))

Two claims carry the solution, and both need stating:

1. Feasibility is monotone. If a cap of C admits a split into ≤ k parts, so does any larger cap — a larger allowance never forces more cuts. So the feasible set is an upward-closed interval, and its lower endpoint is the answer.

2. The greedy check is exact. Given a cap, filling each part as much as possible before cutting minimises the number of parts. Cutting earlier can never reduce the part count, so if greedy needs more than k parts, no strategy fits within the cap.

The bounds are derived, not guessed:

lo = max(nums)      a single element must fit in some part
hi = sum(nums)      k=1 puts everything in one part

nums = [7,2,5,10,8], k = 2      lo = 10, hi = 32

cap=10:  [7,2] [5] [10] [8]      → 4 parts > 2   F
cap=18:  [7,2,5] [10,8]          → 2 parts ≤ 2   T
cap=21:  [7,2,5] [10,8]          → 2 parts       T

F at 10..17, T from 18 → answer 18  ✓

The alternative is dynamic programming — dp[i][j] = best split of the first i elements into j parts — at O(n²k) time and O(nk) space. Binary search on the answer is O(n log(sum)), which for n = 1000 and sum = 10⁹ is roughly 30,000 operations against 10⁹. The DP generalises better to variants with per-part costs; the binary search wins decisively here.

The transferable idea: when the search space of solutions is exponential but the space of answer values is a small monotone range, invert the problem — search the answers and verify each, rather than constructing the optimum directly.

Senior: Find the median of two sorted arrays in O(log(min(m,n))).

This is binary search over a partition point rather than a value, and it is the hardest common binary-search problem. The insight: a median is defined by a split where everything on the left is ≤ everything on the right, and the left holds exactly half the elements.

function findMedianSortedArrays(A, B) {
  if (A.length > B.length) [A, B] = [B, A];      // binary search the SHORTER array
  const m = A.length, n = B.length;
  const half = (m + n + 1) >> 1;

  let lo = 0, hi = m;
  while (lo <= hi) {
    const i = (lo + hi) >> 1;                    // take i from A
    const j = half - i;                          // take j from B

    const Aleft  = i > 0 ? A[i-1] : -Infinity;
    const Aright = i < m ? A[i]   :  Infinity;
    const Bleft  = j > 0 ? B[j-1] : -Infinity;
    const Bright = j < n ? B[j]   :  Infinity;

    if (Aleft <= Bright && Bleft <= Aright) {    // correct partition
      if ((m + n) % 2) return Math.max(Aleft, Bleft);
      return (Math.max(Aleft, Bleft) + Math.min(Aright, Bright)) / 2;
    }
    if (Aleft > Bright) hi = i - 1;              // took too many from A
    else lo = i + 1;                             // took too few
  }
  throw new Error("inputs not sorted");
}

A = [1,3], B = [2]      half = 2

i=1: Aleft=1  Aright=3        left:  {1, 2}
     j=1: Bleft=2 Bright=∞    right: {3}
     1 ≤ ∞ ✓ and 2 ≤ 3 ✓  → correct partition
     odd total → max(1,2) = 2  ✓

Three details make it work:

1. Search the shorter array so j = half - i is always in range, and the complexity is O(log(min(m,n))) rather than O(log(max)).

2. The ±∞ sentinels remove every boundary special case. Without them, i = 0 or i = m needs its own branch, and that is where implementations break.

3. half = (m+n+1) >> 1 with the +1 puts the extra element on the left for odd totals, so the odd case reads the median directly from max(Aleft, Bleft).

The correctness condition is the partition property: Aleft ≤ Bright and Bleft ≤ Aright together mean every element on the left is ≤ every element on the right — which is exactly what defines the median split, without ever merging the arrays.

The O(m+n) merge alternative is far easier to write and correct; I would state it first, then offer this when logarithmic time is required. In a real system I would also ask whether the arrays are large enough for the difference to matter — for a few thousand elements, the merge is simpler and its constant factor smaller.

3 (medium): Solve the binary-search-on-answer family with one helper.
Solution 
// Koko Eating Bananas (875)
function minEatingSpeed(piles, h) {
  const ok = k => piles.reduce((s, p) => s + Math.ceil(p / k), 0) <= h;
  return firstTrue(1, Math.max(...piles) + 1, ok);
}

// Capacity to Ship Packages in D Days (1011)
function shipWithinDays(weights, days) {
  const ok = cap => {
    let d = 1, cur = 0;
    for (const w of weights) {
      if (cur + w > cap) { d++; cur = w; } else cur += w;
    }
    return d <= days;
  };
  return firstTrue(Math.max(...weights),
                   weights.reduce((a,b)=>a+b,0) + 1, ok);
}

// Split Array Largest Sum (410) — identical to shipWithinDays
function splitArray(nums, k) { return shipWithinDays(nums, k); }

// Magnetic Force Between Two Balls (1552) — MAXIMISE the minimum
function maxDistance(position, m) {
  position.sort((a,b) => a-b);
  const ok = gap => {                            // can we place m balls this far apart?
    let count = 1, last = position[0];
    for (const p of position) if (p - last >= gap) { count++; last = p; }
    return count >= m;
  };
  // find the LAST feasible gap = firstTrue(infeasible) - 1
  const hi = position[position.length-1] - position[0] + 2;
  return firstTrue(1, hi, g => !ok(g)) - 1;
}

function assertMonotone(ok, lo, hi, label) {
  let seenTrue = false, bad = null;
  for (let x = lo; x < hi; x++) {
    const v = ok(x);
    if (v) seenTrue = true;
    else if (seenTrue) { bad = x; break; }       // true then false again → NOT monotone
  }
  console.log(`${label}: ${bad === null ? "monotone ✓" : "NOT monotone at " + bad}`);
}

4 (medium): Handle rotated arrays, with and without duplicates.
Solution 
function findMin(nums) {                         // LC 153, distinct
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (nums[mid] > nums[hi]) lo = mid + 1;
    else hi = mid;
  }
  return nums[lo];
}

function findMinDup(nums) {                      // LC 154, duplicates allowed
  let lo = 0, hi = nums.length - 1;
  while (lo < hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (nums[mid] > nums[hi]) lo = mid + 1;
    else if (nums[mid] < nums[hi]) hi = mid;
    else hi--;                                   // tie: cannot decide, shrink by one
  }
  return nums[lo];
}

function searchRotated(nums, target) {           // LC 33
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = lo + ((hi - lo) >> 1);
    if (nums[mid] === target) return mid;
    if (nums[lo] <= nums[mid]) {
      if (nums[lo] <= target && target < nums[mid]) hi = mid - 1; else lo = mid + 1;
    } else {
      if (nums[mid] < target && target <= nums[hi]) lo = mid + 1; else hi = mid - 1;
    }
  }
  return -1;
}

5 (hard): Binary search a sorted matrix, three ways.
Solution 
// A. Fully sorted (each row sorted, first of row > last of previous) — LC 74
function searchMatrixFlat(matrix, target) {
  const m = matrix.length, n = matrix[0].length;
  const i = firstTrue(0, m * n, k => matrix[(k / n) | 0][k % n] >= target);
  return i < m * n && matrix[(i / n) | 0][i % n] === target;
}

// B. Rows and columns sorted independently — LC 240 — staircase from a corner
function searchMatrixStaircase(matrix, target) {
  let r = 0, c = matrix[0].length - 1;           // start top-RIGHT
  while (r < matrix.length && c >= 0) {
    if (matrix[r][c] === target) return true;
    if (matrix[r][c] > target) c--;              // whole column below is larger
    else r++;                                    // whole row left is smaller
  }
  return false;
}

// C. Kth smallest in a sorted matrix — LC 378 — binary search on the VALUE
function kthSmallest(matrix, k) {
  const n = matrix.length;
  const countLE = x => {                         // staircase count, O(n)
    let count = 0, r = n - 1, c = 0;
    while (r >= 0 && c < n) {
      if (matrix[r][c] <= x) { count += r + 1; c++; }
      else r--;
    }
    return count;
  };
  let lo = matrix[0][0], hi = matrix[n-1][n-1];
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (countLE(mid) >= k) hi = mid; else lo = mid + 1;
  }
  return lo;
}

The staircase is not a binary search at all — it eliminates a full row or column per step. Starting from the top-right (or bottom-left) is essential: from a corner, one comparison always rules out an entire line. Starting top-left gives no such elimination, since both directions increase.

Variant C is binary search on the answer applied to a matrix, and it is the one that generalises: countLE(x) is monotone in x, so the smallest x with countLE(x) >= k is the kth smallest value — and the returned value is guaranteed present in the matrix, because the boundary only moves to values that exist.

6 (hard): Build a monotonicity checker and a fuzz harness for predicates.
Solution

Binary search silently returns nonsense on a non-monotone predicate. This harness catches that before it reaches a submission:

function checkMonotone(f, lo, hi) {
  const vals = [];
  for (let x = lo; x < hi; x++) vals.push(f(x) ? 1 : 0);
  // valid shapes: all 0, all 1, or 0...01...1
  let transitions = 0;
  for (let i = 1; i < vals.length; i++) if (vals[i] !== vals[i-1]) transitions++;
  const ok = transitions <= 1 && (transitions === 0 || vals[0] === 0);
  return { ok, transitions, pattern: vals.join("") };
}

function bruteFirstTrue(f, lo, hi) {
  for (let x = lo; x < hi; x++) if (f(x)) return x;
  return hi;
}

function verify(f, lo, hi, label) {
  const m = checkMonotone(f, lo, hi);
  const fast = firstTrue(lo, hi, f);
  const slow = bruteFirstTrue(f, lo, hi);
  console.log(`${label.padEnd(22)} monotone=${m.ok ? "✓" : "✗"} ` +
              `binary=${fast} brute=${slow} ${fast === slow ? "match" : "MISMATCH"}` +
              (m.ok ? "" : `  pattern=${m.pattern}`));
}

The reusable discipline for any binary-search-on-answer problem: write the feasibility check, run checkMonotone over a small range, confirm the pattern is 0…01…1, and only then reach for firstTrue. On a real contest problem this takes a minute and eliminates the most common source of wrong answers.

🎯 Key Takeaways

  • The classic three-branch template answers only "is it present"; every other question invites off-by-one bugs across four independent choices.
  • Reframe every binary search as finding the first true in a monotone predicate — one template, no variants to remember.
  • The template is while (lo < hi), f(mid) ? hi = mid : lo = mid + 1, return lo, with hi exclusive.
  • It terminates because mid rounds down, so hi = mid strictly decreases the range.
  • lower_bound, upper_bound, count, insert position and exact match are all just different predicates over the same code.
  • lower_bound returns an insert position — always verify nums[i] === target before claiming a match.
  • Use lo + ((hi - lo) >> 1) to avoid overflow; it is a real bug in fixed-width-integer languages.
  • Binary search on the answer applies when checking one candidate is easy and feasibility is monotone — "minimum X such that…", "minimise the maximum".
  • Both answer bounds must be justified: too narrow excludes the answer, too wide wastes iterations.
  • Koko, Ship Packages, Split Array and Magnetic Force are the same problem with different feasibility checks.
  • A rotated sorted array always has at least one sorted half — that is the invariant the search exploits.
  • In findMin, compare with nums[hi], never nums[lo], which fails on non-rotated input.
  • Duplicates destroy the rotated-array guarantee; hi-- on a tie, and accept O(n) worst case.
  • Find Peak Element works on unsorted data because moving uphill guarantees a peak in that direction.
  • "Last true" needs mid rounded up to avoid an infinite loop — or express it as firstTrue(negated) - 1 and skip the variant.
  • A non-monotone predicate makes binary search silently wrong on ~20% of inputs while appearing to work on the rest — check the F…FT…T shape explicitly.
  • Sorted matrices admit three approaches: flatten, staircase from a corner, or binary search on the value with a monotone count.
  • State the loop invariant — everything below lo is false, everything at or above hi is true — and correctness follows rather than being tested into existence.
