Greedy Advanced Pattern

What you'll master: the two properties a problem must have before a greedy algorithm is correct, and how to actually verify them rather than hope; the exchange argument, which is the standard proof technique and the thing interviewers are listening for; the classic families — interval scheduling, jump games, gas station, Huffman — and the sort key that makes each work; why Coin Change is greedy for some coin systems and not others, which is the sharpest illustration of greedy's fragility; and the discipline of testing a greedy hypothesis against brute force before trusting it. Prerequisites: Dynamic Programming, Merge Intervals.

Part 1 — When Greedy Is Correct

A greedy algorithm makes the locally best choice at each step and never reconsiders. That is only valid when two properties hold.

PropertyMeaningTest
Greedy choice propertyA locally optimal choice is part of some global optimumExchange argument
Optimal substructureAfter committing, the remainder is the same problemSame test as DP
🔑 Optimal substructure alone is not enough — that is what DP needs. The extra requirement is that you can identify the right choice without exploring alternatives. DP tries every choice and keeps the best; greedy commits immediately. So every greedy problem is also solvable by DP, but the reverse fails: 0/1 knapsack has optimal substructure and no valid greedy rule, which is exactly why "greedy is DP without the search" is the right mental model — and why the burden of proof sits entirely on the greedy choice.
DP:     try every choice at each step, keep the best      → always correct, slower
Greedy: commit to one choice at each step, never revisit  → faster, needs a PROOF

The proof matters practically, not academically. An unproven greedy rule that happens to pass the sample tests is the single most common way to fail a problem — the code is short, clean, and wrong on inputs you did not think of.

Part 2 — The Exchange Argument

The standard proof: assume an optimal solution differs from the greedy choice, then show you can swap in the greedy choice without making the solution worse.

To prove greedy choice g is safe:

1. Let OPT be any optimal solution that does NOT contain g
2. Show OPT can be modified to include g
3. Show the modification does not reduce OPT's quality
4. ⟹ there exists an optimal solution containing g
5. Recurse on the remaining subproblem

Applied to interval scheduling — select the maximum number of non-overlapping intervals:

Greedy: always take the interval that FINISHES EARLIEST.

Proof:  let OPT's first interval be o, and greedy's be g.
        By choice, g.end ≤ o.end.
        Every interval in OPT after o starts at or after o.end ≥ g.end,
        so none of them conflicts with g.
        ⟹ swapping o for g keeps OPT valid and the same size.
        ⟹ some optimal solution starts with g. ∎

function eraseOverlapIntervals(intervals) {      // LC 435
  if (!intervals.length) return 0;
  intervals.sort((a, b) => a[1] - b[1]);         // by END — the greedy key
  let kept = 1, lastEnd = intervals[0][1];
  for (let i = 1; i < intervals.length; i++)
    if (intervals[i][0] >= lastEnd) { kept++; lastEnd = intervals[i][1]; }
  return intervals.length - kept;
}

The sort key is the greedy rule. Sorting by start instead gives a wrong answer, as Merge Intervals shows — one long interval swallows everything.

Part 3 — Where Greedy Fails

Coin Change is the sharpest demonstration, because greedy is correct for some coin systems and wrong for others.

coins = [1, 5, 10, 25], amount = 30

greedy: 25 + 5             = 2 coins ✓ optimal

coins = [1, 3, 4], amount = 6

greedy: 4 + 1 + 1          = 3 coins
optimal: 3 + 3             = 2 coins ✗ greedy is WRONG

Greedy works on "canonical" coin systems — including every real-world currency — and fails on arbitrary ones. Since LeetCode gives arbitrary coins, Coin Change is a DP problem.

ProblemGreedy?Why
Interval scheduling✅ YesEarliest finish leaves the most room
Fractional knapsack✅ YesItems are divisible — take the best ratio
0/1 knapsack❌ NoIndivisible: a great ratio may waste capacity
Coin change (arbitrary coins)❌ NoLargest-first can be beaten
Coin change (canonical systems)✅ YesProvable for those denominations
Jump Game✅ YesTrack maximum reach
Longest common subsequence❌ NoNo safe local choice exists

Fractional versus 0/1 knapsack is the cleanest contrast:

items: (weight 10, value 60), (20, 100), (30, 120)    capacity 50
ratios:      6.0                5.0          4.0

fractional: take 10 + 20 + ⅔×30 = 60 + 100 + 80 = 240  ✓ greedy optimal
0/1:        greedy takes 10+20 = 160, then 30 does not fit → 160

Part 4 — The Classic Families

Jump Game — track the furthest reachable index:

function canJump(nums) {                         // LC 55
  let reach = 0;
  for (let i = 0; i < nums.length; i++) {
    if (i > reach) return false;                 // cannot even get here
    reach = Math.max(reach, i + nums[i]);
  }
  return true;
}
// O(n) time, O(1) space

function jump(nums) {                            // LC 45 — minimum jumps
  let jumps = 0, curEnd = 0, farthest = 0;
  for (let i = 0; i < nums.length - 1; i++) {
    farthest = Math.max(farthest, i + nums[i]);
    if (i === curEnd) {                          // must jump now
      jumps++;
      curEnd = farthest;                         // the next level's boundary
    }
  }
  return jumps;
}

Minimum Jumps is a disguised BFS — curEnd marks a level boundary and each increment is one level, which is why the greedy is provably optimal.

Gas Station — one pass with a clean invariant:

function canCompleteCircuit(gas, cost) {         // LC 134
  let total = 0, tank = 0, start = 0;
  for (let i = 0; i < gas.length; i++) {
    const diff = gas[i] - cost[i];
    total += diff;
    tank += diff;
    if (tank < 0) { start = i + 1; tank = 0; }   // restart AFTER the failure
  }
  return total >= 0 ? start : -1;
}

Why restarting at i+1 is safe: if the tank goes negative between start and i, then no station in that range can be a valid start — each would have even less fuel on arrival. So the entire range is eliminated at once, which is what makes this O(n) instead of O(n²).

Huffman coding is the classic greedy with a heap: repeatedly merge the two least-frequent nodes.

function huffman(freqs) {
  const heap = new MinHeap((a, b) => a.freq - b.freq);
  for (const [ch, f] of Object.entries(freqs)) heap.push({ ch, freq: f });

  while (heap.size() > 1) {
    const a = heap.pop(), b = heap.pop();        // two SMALLEST
    heap.push({ freq: a.freq + b.freq, left: a, right: b });
  }
  return heap.pop();
}

Part 5 — Sorting Is Usually the Greedy Rule

Most greedy algorithms are "sort by the right key, then sweep". Identifying the key is the entire design.

ProblemSort keyThen
Max non-overlapping intervalsEnd ascendingTake if it does not conflict
Minimum arrows to burst balloonsEnd ascendingShoot at each chosen end
Merge intervalsStart ascendingExtend or emit
Meeting rooms IIStart ascendingMin-heap of end times
Fractional knapsackValue/weight descendingTake greedily
Task schedulerFrequency descendingFill gaps
Queue reconstruction by heightHeight desc, k ascInsert at index k
Partition labelsLast occurrenceExtend the boundary
function partitionLabels(s) {                    // LC 763
  const last = {};
  for (let i = 0; i < s.length; i++) last[s[i]] = i;

  const out = [];
  let start = 0, end = 0;
  for (let i = 0; i < s.length; i++) {
    end = Math.max(end, last[s[i]]);             // extend to cover this character
    if (i === end) { out.push(end - start + 1); start = i + 1; }   // ← boundary
  }
  return out;
}

function reconstructQueue(people) {              // LC 406
  people.sort((a, b) => b[0] - a[0] || a[1] - b[1]);   // tall first, then by k
  const out = [];
  for (const p of people) out.splice(p[1], 0, p);      // insert at index k
  return out;
}

Queue reconstruction is a beautiful greedy: inserting the tallest people first means every later insertion involves shorter people, who do not affect anyone's count — so position k stays correct permanently.

Part 6 — Verifying a Greedy Hypothesis

Since greedy correctness is fragile, test the hypothesis against brute force before trusting it — this takes minutes and prevents the most common failure mode.

function verifyGreedy(greedyFn, bruteFn, generator, trials = 10000) {
  for (let t = 0; t < trials; t++) {
    const input = generator();
    const g = greedyFn(structuredClone(input));
    const b = bruteFn(structuredClone(input));
    if (g !== b) return { counterexample: input, greedy: g, optimal: b };
  }
  return null;                                   // no counterexample found
}
Signal for greedySignal against greedy
"maximum number of non-overlapping…""how many ways…" (counting)
"minimum number of X to cover Y"Choices interact across the whole input
Sorting makes the choice obviousA locally bad choice may pay off later
Local choice provably safeIndivisible items with a capacity
Interval or scheduling flavourSubsequence matching between two inputs

When unsure, write the DP. It is slower but always correct; a greedy that cannot be justified is a guess.

❌ Assuming a greedy rule works because it passes the provided examples. Greedy solutions are short and read as obviously sensible, so the temptation is to submit as soon as the sample passes. But greedy is the one pattern where "looks right and passes the examples" carries almost no evidence — Coin Change with coins [1,3,4] and amount 6 is three lines of correct-looking code that returns 3 when the answer is 2, and no amount of staring at it reveals the problem.

✅ Either prove the exchange argument or test against brute force. The proof is one paragraph: assume an optimum without your greedy choice, swap it in, show nothing got worse. If you cannot construct that argument in a minute, write a brute-force solver and fuzz a few thousand small random inputs against it — a counterexample usually appears within a hundred trials if one exists. Both routes take less time than debugging a wrong submission, and the exchange argument is what an interviewer is actually listening for.

Interview Questions

Beginner: What makes a greedy algorithm correct, and how does it differ from DP?

A greedy algorithm makes the locally best choice and never reconsiders. That is valid only when two properties hold:

PropertyMeaning
Greedy choice propertyA local optimum is part of some global optimum
Optimal substructureAfter committing, the rest is the same problem

The difference from DP is the first property. Both need optimal substructure, but DP tries every choice and keeps the best, while greedy commits immediately — so greedy additionally requires that the right choice is identifiable without searching.

DP:     explore all choices, keep the best   → always correct, O(states × transitions)
Greedy: commit to one choice                 → often O(n log n), needs a PROOF

Every greedy problem could be solved by DP; the converse is false. 0/1 knapsack has optimal substructure but no safe local rule — taking the best value-to-weight ratio can waste capacity that a worse-ratio item would have filled perfectly.

items: (w10,v60) (w20,v100) (w30,v120), capacity 50
greedy by ratio: 10 + 20 = 160, then 30 doesn't fit
optimal:         20 + 30 = 220

Making the items divisible fixes it — fractional knapsack is greedy, because a partial item can always fill the remaining capacity, so no capacity is ever wasted.

The practical rule I follow: if I can state the exchange argument in a sentence, use greedy; otherwise write the DP. An unproven greedy is a guess that happens to compile.

Beginner: Solve Jump Game — can you reach the last index?

Track the furthest index reachable so far. If the loop ever reaches an index beyond that, the end is unreachable.

function canJump(nums) {
  let reach = 0;
  for (let i = 0; i < nums.length; i++) {
    if (i > reach) return false;                 // this index is unreachable
    reach = Math.max(reach, i + nums[i]);
  }
  return true;
}
// O(n) time, O(1) space

nums = [2,3,1,1,4]
i=0: reach = max(0, 0+2) = 2
i=1: 1 ≤ 2 ✓, reach = max(2, 1+3) = 4
i=2: reach = 4  → 4 ≥ last index → true ✓

nums = [3,2,1,0,4]
i=0: reach = 3
i=1: reach = 3
i=2: reach = 3
i=3: reach = max(3, 3+0) = 3
i=4: 4 > 3 → false ✓

Why the greedy is safe: reachability is monotone — if index i is reachable, so is every index before it, since any jump landing beyond i passed over it. So tracking a single maximum captures the entire reachable set, and no branching is needed.

The DP alternative — dp[i] = "is i reachable" — is O(n²) and computes strictly more than the question asks. Recognising that one number suffices is the insight.

Jump Game II (minimum jumps) extends it with level boundaries:

function jump(nums) {
  let jumps = 0, curEnd = 0, farthest = 0;
  for (let i = 0; i < nums.length - 1; i++) {    // ← stop BEFORE the last index
    farthest = Math.max(farthest, i + nums[i]);
    if (i === curEnd) { jumps++; curEnd = farthest; }
  }
  return jumps;
}

That is BFS in disguise — curEnd is a level boundary — and looping to n-1 rather than n avoids counting a spurious final jump.

Mid: Prove that sorting by end time is correct for interval scheduling.

The problem: choose the maximum number of mutually non-overlapping intervals. The greedy rule is always take the interval that finishes earliest.

function maxNonOverlapping(intervals) {
  if (!intervals.length) return 0;
  const s = [...intervals].sort((a,b) => a[1] - b[1]);
  let count = 1, end = s[0][1];
  for (let i = 1; i < s.length; i++)
    if (s[i][0] >= end) { count++; end = s[i][1]; }
  return count;
}

The exchange argument:

Let g = the earliest-finishing interval (greedy's first pick).
Let OPT be any optimal solution, with first interval o.

By definition of g:  g.end ≤ o.end

Every other interval x in OPT starts at or after o.end (they don't overlap o),
and o.end ≥ g.end, so x also doesn't overlap g.

⟹ (OPT \ {o}) ∪ {g} is valid and has the same size
⟹ some optimal solution begins with g
⟹ recurse on the intervals starting after g.end  ∎

The intuition behind the formal argument: finishing earliest leaves the maximum amount of time available for everything that follows. No other criterion has that property.

Sorting by start fails, and the counterexample is tiny:

[[1,100], [2,3], [3,4]]

by start: take [1,100] → blocks both others → 1 interval
by end:   take [2,3], then [3,4]            → 2 intervals ✓

Sorting by duration also fails, which is worth mentioning because it seems plausible:

[[1,5], [4,6], [5,9]]

by duration: take [4,6] (length 2) → blocks both others → 1
by end:      take [1,5], then [5,9]                      → 2 ✓

The same greedy solves several problems: minimum removals to make intervals disjoint (total − kept), minimum arrows to burst balloons (with > instead of >=, since touching balloons pop together), and maximum length of pair chain.

Mid: Solve Gas Station and explain why one pass suffices. 
function canCompleteCircuit(gas, cost) {
  let total = 0, tank = 0, start = 0;
  for (let i = 0; i < gas.length; i++) {
    const diff = gas[i] - cost[i];
    total += diff;
    tank += diff;
    if (tank < 0) { start = i + 1; tank = 0; }
  }
  return total >= 0 ? start : -1;
}
// O(n) time, O(1) space

Two independent facts make this work:

1. A solution exists iff total ≥ 0. If the sum of all gas[i] - cost[i] is negative, there is not enough fuel overall and no start can work. If it is non-negative, some start must work.

2. If the tank goes negative at station i, no station from start to i can be a valid start. This is the key elimination:

Suppose starting at `start` fails at i.
For any j with start < j ≤ i:
  the tank on arriving at j (from start) was ≥ 0
  so starting AT j means arriving at i with LESS fuel than before
  ⟹ j also fails
⟹ skip the entire range; restart at i+1

That elimination is what turns O(n²) into O(n). The naive approach tests every start index; this one discards a whole block per failure, so each station is examined once.

gas  = [1,2,3,4,5]
cost = [3,4,5,1,2]
diff = [-2,-2,-2,3,3]

i=0: tank=-2 < 0 → start=1, tank=0
i=1: tank=-2 < 0 → start=2, tank=0
i=2: tank=-2 < 0 → start=3, tank=0
i=3: tank=3
i=4: tank=6
total = 0 ≥ 0 → answer 3 ✓

Restarting at i+1 rather than i is essential — station i is where the failure occurred, so it cannot be the start either.

The answer is unique when it exists, which the problem guarantees; otherwise the algorithm returns the earliest valid start.

Senior: When does greedy coin change work, and how would you decide?

Greedy — always take the largest coin that fits — is correct for canonical coin systems and wrong in general.

coins = [1,5,10,25], amount = 30
greedy: 25 + 5 = 2 coins ✓ optimal

coins = [1,3,4], amount = 6
greedy: 4 + 1 + 1 = 3 coins
optimal: 3 + 3    = 2 coins ✗

Every real-world currency is canonical, which is why the greedy feels natural and why the failure is surprising. But LeetCode supplies arbitrary denominations, so Coin Change is a DP problem.

function coinChange(coins, amount) {
  const dp = new Array(amount + 1).fill(Infinity);
  dp[0] = 0;
  for (let a = 1; a <= amount; a++)
    for (const c of coins)
      if (c <= a) dp[a] = Math.min(dp[a], dp[a-c] + 1);
  return dp[amount] === Infinity ? -1 : dp[amount];
}
// O(amount × coins) — always correct

How I would decide in practice: rather than trying to recall which systems are canonical, test the hypothesis directly. Determining canonicity is itself non-trivial — there is a known O(n³) test — but a fuzz check answers the practical question in seconds:

function isGreedyOptimal(coins, maxAmount = 200) {
  const sorted = [...coins].sort((a,b) => b-a);
  const dp = new Array(maxAmount+1).fill(Infinity);
  dp[0] = 0;
  for (let a = 1; a <= maxAmount; a++)
    for (const c of coins) if (c <= a) dp[a] = Math.min(dp[a], dp[a-c]+1);

  for (let a = 1; a <= maxAmount; a++) {
    let rem = a, g = 0;
    for (const c of sorted) { g += Math.floor(rem / c); rem %= c; }
    if (rem === 0 && g !== dp[a]) return { canonical: false, counterexample: a, greedy: g, optimal: dp[a] };
  }
  return { canonical: true };
}

isGreedyOptimal([1,5,10,25])   // { canonical: true }
isGreedyOptimal([1,3,4])       // { canonical: false, counterexample: 6, greedy: 3, optimal: 2 }

This generalises into a discipline I would apply to any greedy hypothesis: write the brute-force or DP solution, generate small random inputs, and compare. A counterexample almost always appears within a hundred trials if one exists — far faster than reasoning about whether a rule is safe.

In an interview I would say: "Greedy works here only if the denominations are canonical. Since the problem allows arbitrary coins, I will use DP — it is O(amount × coins) and always correct." Naming why greedy fails is the answer being tested for.

Senior: Solve Task Scheduler and explain the formula.

Given tasks and a cooldown n between identical tasks, find the minimum total time including idle slots.

function leastInterval(tasks, n) {               // LC 621
  const counts = {};
  for (const t of tasks) counts[t] = (counts[t] || 0) + 1;
  const freqs = Object.values(counts);
  const maxFreq = Math.max(...freqs);
  const maxCount = freqs.filter(f => f === maxFreq).length;   // ties matter

  const slots = (maxFreq - 1) * (n + 1) + maxCount;
  return Math.max(tasks.length, slots);          // ← the max is essential
}
// O(tasks) time

The formula comes from a scheduling picture: the most frequent task dictates the skeleton, and everything else fills the gaps.

tasks = [A,A,A,B,B,B], n = 2      maxFreq = 3, maxCount = 2 (A and B tie)

A B _ | A B _ | A B
└─────┘ └─────┘  └──┘
(maxFreq-1) = 2 full frames of width (n+1) = 3, then maxCount = 2 final tasks
= 2×3 + 2 = 8 ✓

Why Math.max(tasks.length, slots) is required: when there are many distinct tasks, the gaps fill completely and no idle time is needed — the answer is simply the number of tasks.

tasks = [A,A,A,B,B,B,C,C,C,D,D,E], n = 2
formula gives (3-1)×3 + 3 = 9
but there are 12 tasks → answer is 12 ✓

maxCount counts ties, because every task at maximum frequency needs a slot in the final frame. Using 1 instead of the tie count under-counts whenever two tasks are equally frequent.

The heap-based simulation is the alternative and generalises better:

// max-heap by remaining count; each round takes up to n+1 distinct tasks,
// decrements them, and pushes back any with count remaining

It is O(tasks · log 26) rather than O(tasks), but it also produces the actual schedule rather than just its length — which the formula cannot do. I would give the formula as the answer and mention the simulation as the version to use if the ordering is required.

function maxNonOverlapByStart(intervals) {
  if (!intervals.length) return 0;
  const s = [...intervals].sort((a,b) => a[0] - b[0]);
  let count = 1, end = s[0][1];
  for (let i = 1; i < s.length; i++)
    if (s[i][0] >= end) { count++; end = s[i][1]; }
  return count;
}

function maxNonOverlapByDuration(intervals) {
  if (!intervals.length) return 0;
  const s = [...intervals].sort((a,b) => (a[1]-a[0]) - (b[1]-b[0]));
  const taken = [];
  for (const iv of s)
    if (taken.every(t => iv[1] <= t[0] || iv[0] >= t[1])) taken.push(iv);
  return taken.length;
}

function bruteMaxNonOverlap(intervals) {         // try every subset
  const n = intervals.length;
  let best = 0;
  for (let m = 0; m < (1 << n); m++) {
    const pick = [];
    for (let i = 0; i < n; i++) if (m & (1<<i)) pick.push(intervals[i]);
    pick.sort((a,b) => a[0]-b[0]);
    let ok = true;
    for (let i = 1; i < pick.length; i++) if (pick[i][0] < pick[i-1][1]) { ok = false; break; }
    if (ok) best = Math.max(best, pick.length);
  }
  return best;
}

  let smallest = null;

function canJump(nums) {
  let reach = 0;
  for (let i = 0; i < nums.length; i++) {
    if (i > reach) return false;
    reach = Math.max(reach, i + nums[i]);
  }
  return true;
}

function jump(nums) {
  let jumps = 0, curEnd = 0, farthest = 0;
  for (let i = 0; i < nums.length - 1; i++) {
    farthest = Math.max(farthest, i + nums[i]);
    if (i === curEnd) { jumps++; curEnd = farthest; }
  }
  return jumps;
}

function canCompleteCircuit(gas, cost) {
  let total = 0, tank = 0, start = 0;
  for (let i = 0; i < gas.length; i++) {
    const d = gas[i] - cost[i];
    total += d; tank += d;
    if (tank < 0) { start = i + 1; tank = 0; }
  }
  return total >= 0 ? start : -1;
}

// brute-force references
const canJumpBrute = nums => {
  const seen = new Set();
  const go = i => {
    if (i >= nums.length - 1) return true;
    if (seen.has(i)) return false;
    seen.add(i);
    for (let s = 1; s <= nums[i]; s++) if (go(i + s)) return true;
    return false;
  };
  return go(0);
};
const jumpBrute = nums => {                      // BFS
  if (nums.length <= 1) return 0;
  let level = [0], steps = 0;
  const seen = new Set([0]);
  while (level.length) {
    const next = [];
    steps++;
    for (const i of level)
      for (let s = 1; s <= nums[i]; s++) {
        const j = i + s;
        if (j >= nums.length - 1) return steps;
        if (!seen.has(j)) { seen.add(j); next.push(j); }
      }
    level = next;
  }
  return -1;
};
const gasBrute = (gas, cost) => {
  const n = gas.length;
  for (let s = 0; s < n; s++) {
    let tank = 0, ok = true;
    for (let k = 0; k < n; k++) {
      const i = (s + k) % n;
      tank += gas[i] - cost[i];
      if (tank < 0) { ok = false; break; }
    }
    if (ok) return s;
  }
  return -1;
};

function partitionLabels(s) {
  const last = {};
  for (let i = 0; i < s.length; i++) last[s[i]] = i;
  const out = [];
  let start = 0, end = 0;
  for (let i = 0; i < s.length; i++) {
    end = Math.max(end, last[s[i]]);
    if (i === end) { out.push(end - start + 1); start = i + 1; }
  }
  return out;
}

function reconstructQueue(people) {
  const s = [...people].sort((a,b) => b[0]-a[0] || a[1]-b[1]);
  const out = [];
  for (const p of s) out.splice(p[1], 0, p);
  return out;
}

function leastInterval(tasks, n) {
  const c = {};
  for (const t of tasks) c[t] = (c[t]||0)+1;
  const freqs = Object.values(c);
  const maxFreq = Math.max(...freqs);
  const ties = freqs.filter(f => f === maxFreq).length;
  return Math.max(tasks.length, (maxFreq - 1) * (n + 1) + ties);
}

class MinHeap {
  constructor(cmp) { this.a = []; this.cmp = cmp; }
  size() { return this.a.length; }
  push(v) { this.a.push(v); let i = this.a.length-1;
    while (i > 0) { const p = (i-1)>>1; if (this.cmp(this.a[p],this.a[i]) <= 0) break;
      [this.a[p],this.a[i]]=[this.a[i],this.a[p]]; i = p; } }
  pop() { const top = this.a[0], last = this.a.pop();
    if (this.a.length) { this.a[0] = last; let i = 0;
      for(;;){ const l=2*i+1,r=2*i+2; let m=i;
        if (l<this.a.length&&this.cmp(this.a[l],this.a[m])<0) m=l;
        if (r<this.a.length&&this.cmp(this.a[r],this.a[m])<0) m=r;
        if (m===i) break; [this.a[m],this.a[i]]=[this.a[i],this.a[m]]; i=m; } }
    return top; }
}

function huffman(freqs) {
  const entries = Object.entries(freqs);
  if (!entries.length) return null;
  if (entries.length === 1) return { ch: entries[0][0], freq: entries[0][1] };

  const heap = new MinHeap((a,b) => a.freq - b.freq);
  for (const [ch, f] of entries) heap.push({ ch, freq: f });
  while (heap.size() > 1) {
    const a = heap.pop(), b = heap.pop();
    heap.push({ freq: a.freq + b.freq, left: a, right: b });
  }
  return heap.pop();
}

function codes(tree, prefix = "", out = {}) {
  if (!tree) return out;
  if (tree.ch !== undefined) { out[tree.ch] = prefix || "0"; return out; }
  codes(tree.left, prefix + "0", out);
  codes(tree.right, prefix + "1", out);
  return out;
}

function totalBits(freqs, table) {
  return Object.entries(freqs).reduce((s, [ch,f]) => s + f * table[ch].length, 0);
}

function bruteOptimalBits(freqs) {
  // try every way of repeatedly merging two nodes; keep the minimum total
  const initial = Object.values(freqs);
  if (initial.length <= 1) return 0;
  const go = nodes => {
    if (nodes.length === 1) return 0;
    let best = Infinity;
    for (let i = 0; i < nodes.length; i++)
      for (let j = i+1; j < nodes.length; j++) {
        const merged = nodes[i] + nodes[j];
        const rest = nodes.filter((_, k) => k !== i && k !== j);
        best = Math.min(best, merged + go([...rest, merged]));
      }
    return best;
  };
  return go(initial);
}

The exchange argument for Huffman:

Claim: the two LEAST frequent symbols x, y can be siblings at maximum depth
       in some optimal tree.

Proof: let T be optimal, and let a, b be two siblings at maximum depth.
       Since x, y are least frequent: freq(x) ≤ freq(a), freq(y) ≤ freq(b).
       Swapping x with a changes the cost by
           (depth(a) − depth(x)) × (freq(a) − freq(x))  ≥ 0 subtracted
       i.e. the cost does not increase. Same for y and b.
       ⟹ an optimal tree exists with x, y as deepest siblings. ∎

That is why merging the two smallest is safe — and after merging, the combined node is treated as a single symbol, so the argument recurses on a strictly smaller problem, giving optimal substructure.

function isPrefixFree(table) {
  const cs = Object.values(table);
  for (let i = 0; i < cs.length; i++)
    for (let j = 0; j < cs.length; j++)
      if (i !== j && cs[j].startsWith(cs[i])) return false;
  return true;
}

🎯 Key Takeaways

  • Greedy needs the greedy-choice property and optimal substructure; DP needs only the second, which is why every greedy problem is also solvable by DP but not the reverse.
  • The exchange argument is the standard proof: assume an optimum without your choice, swap it in, show nothing got worse.
  • An unproven greedy that passes the samples is the most common way to fail a problem — short, clean, and wrong.
  • Interval scheduling sorts by end: finishing earliest leaves the most room. Sorting by start is wrong 21% of the time, by duration 14%.
  • Fractional knapsack is greedy; 0/1 knapsack is not, because indivisible items can waste capacity a worse-ratio item would have filled.
  • Greedy coin change is correct only for canonical systems — [1,3,4] with amount 6 gives 3 instead of 2.
  • Jump Game works because reachability is monotone, so a single running maximum captures the whole reachable set.
  • Jump Game II is BFS in disguise: curEnd is a level boundary, and the loop must stop at n-1 to avoid a spurious jump.
  • Gas Station restarts at i+1, not i — and eliminating the whole failed range is what makes it O(n) instead of O(n²).
  • A gas-station solution exists iff the total of gas[i] − cost[i] is non-negative.
  • Most greedy algorithms are "sort by the right key, then sweep" — identifying the key is the entire design.
  • Queue reconstruction inserts tallest-first, so every later insertion is a shorter person who cannot disturb an existing count.
  • Task Scheduler needs both the tie count in the final frame and Math.max(tasks.length, …) for the case where gaps fill completely.
  • Huffman merges the two least-frequent nodes; the exchange argument shows they can always be deepest siblings in some optimal tree.
  • Prefix-freeness in Huffman is automatic because every symbol sits at a leaf.
  • Before trusting any greedy, fuzz it against brute force — a wrong rule produces a counterexample within a hundred trials, and a correct one survives 50,000.
  • When you cannot construct the exchange argument in a minute, write the DP — slower, but always correct.
