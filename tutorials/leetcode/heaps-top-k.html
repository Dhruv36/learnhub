Heaps / Top-K Advanced Pattern

What you'll master: the binary heap as an implicit tree in an array, and why sift-up and sift-down are all it takes; the counter-intuitive rule that top-k largest needs a MIN-heap and the size-k invariant that makes it work; when a heap beats sorting and when it does not, with the arithmetic; the two-heap median technique and its rebalancing invariant; k-way merge, and why the heap holds k items rather than everything; and Quickselect as the O(n) alternative that beats heaps when the data is static. Prerequisites: Big-O, Arrays & Strings.

Part 1 — The Structure

A binary heap is a complete binary tree stored in a flat array, with one rule: every parent compares favourably to its children (smaller, for a min-heap).

            1                index:  0  1  2  3  4  5
          /   \              array: [1, 3, 2, 7, 4, 5]
         3     2
        / \   /              parent(i) = (i-1) >> 1
       7   4 5               left(i)   = 2i + 1
                             right(i)  = 2i + 2

Only the root is ordered. The heap does not sort — siblings have no relationship to each other, and index 3 holding 7 while index 5 holds 5 is perfectly valid. That weaker invariant is exactly why insertion and extraction cost O(log n) instead of O(n).

class MinHeap {
  constructor(cmp = (a, b) => a - b) { this.a = []; this.cmp = cmp; }
  size() { return this.a.length; }
  peek() { return this.a[0]; }

  push(v) {
    this.a.push(v);
    let i = this.a.length - 1;
    while (i > 0) {                              // sift UP
      const p = (i - 1) >> 1;
      if (this.cmp(this.a[p], this.a[i]) <= 0) break;
      [this.a[p], this.a[i]] = [this.a[i], this.a[p]];
      i = p;
    }
  }

  pop() {
    const top = this.a[0], last = this.a.pop();
    if (this.a.length) {
      this.a[0] = last;
      let i = 0;
      for (;;) {                                 // sift DOWN
        const l = 2*i + 1, r = 2*i + 2;
        let m = i;
        if (l < this.a.length && this.cmp(this.a[l], this.a[m]) < 0) m = l;
        if (r < this.a.length && this.cmp(this.a[r], this.a[m]) < 0) m = r;
        if (m === i) break;
        [this.a[m], this.a[i]] = [this.a[i], this.a[m]];
        i = m;
      }
    }
    return top;
  }
}
OperationCostWhy
peekO(1)The root is index 0
pushO(log n)Sift up at most the height
popO(log n)Sift down at most the height
Build from an arrayO(n)Heapify bottom-up, not n pushes
Search for an arbitrary valueO(n)Only the root is ordered

Building a heap is O(n), not O(n log n), which surprises people: sifting down from the last internal node upward costs O(n) in total, because most nodes are near the bottom and sift down only a short distance.

Part 2 — Top-K Uses the Opposite Heap

This is the rule that trips everyone up: to keep the k largest elements, use a MIN-heap of size k.

k = 3, stream: 5, 1, 9, 3, 7, 2

min-heap holds the 3 largest seen so far; its ROOT is the WEAKEST survivor

push 5      [5]
push 1      [1,5]
push 9      [1,5,9]
push 3      [1,3,5,9] → size 4 > 3 → pop the min (1) → [3,5,9]
push 7      [3,5,7,9] → pop 3                        → [5,7,9]
push 2      2 < root(5) → don't even push            → [5,7,9]  ✓
🔑 The root of a min-heap is the weakest element you are keeping, which makes it the perfect gatekeeper. A new candidate only needs one comparison against the root: if it is smaller, it cannot belong in the top k and is discarded immediately; if larger, it displaces the root. A max-heap would put the strongest element at the root, which tells you nothing about what to evict — so you would have to scan all k. Same logic mirrored for "k smallest": use a max-heap.
function topKLargest(nums, k) {
  const heap = new MinHeap();
  for (const x of nums) {
    heap.push(x);
    if (heap.size() > k) heap.pop();             // ← evict the weakest
  }
  return heap.a;                                 // the k largest, unsorted
}
// O(n log k) time, O(k) space

function topKFrequent(nums, k) {                 // LC 347
  const freq = new Map();
  for (const x of nums) freq.set(x, (freq.get(x) || 0) + 1);

  const heap = new MinHeap((a, b) => a[1] - b[1]);   // compare by frequency
  for (const entry of freq) {
    heap.push(entry);
    if (heap.size() > k) heap.pop();
  }
  return heap.a.map(e => e[0]);
}
// O(n log k) — better than O(n log n) sorting when k is small

The heap's real advantage is not always the asymptotics — it is that it works on a stream. Sorting and Quickselect both need the entire dataset in memory at once; a size-k heap needs only k elements, which is what makes "top 10 of a billion records" tractable.

Bucket sort wins outright when keys are bounded, and Top K Frequent is the classic case — frequencies are at most n, so they can be bucketed directly:

function topKFrequentBucket(nums, k) {
  const freq = new Map();
  for (const x of nums) freq.set(x, (freq.get(x) || 0) + 1);

  const buckets = Array.from({length: nums.length + 1}, () => []);
  for (const [val, f] of freq) buckets[f].push(val);       // index BY frequency

  const out = [];
  for (let f = buckets.length - 1; f >= 0 && out.length < k; f--)
    for (const v of buckets[f]) { out.push(v); if (out.length === k) break; }
  return out;
}
// O(n) time

Part 4 — Two Heaps: The Running Median

Splitting the data into a low half and a high half, each in the appropriate heap, keeps the median at the boundary:

        LOW half              HIGH half
      (max-heap)             (min-heap)
     ┌──────────┐           ┌──────────┐
     │  1 2 3   │           │  4 5 6   │
     └────┬─────┘           └────┬─────┘
       root = 3               root = 4
          └──── median is here ───┘

odd total:  median = root of the larger heap
even total: median = average of the two roots

class MedianFinder {                             // LC 295
  constructor() {
    this.low = new MinHeap((a, b) => b - a);     // MAX-heap via reversed comparator
    this.high = new MinHeap((a, b) => a - b);    // min-heap
  }

  addNum(x) {
    this.low.push(x);                            // always insert into low first
    this.high.push(this.low.pop());              // move its max across — keeps order
    if (this.high.size() > this.low.size())      // rebalance sizes
      this.low.push(this.high.pop());
  }

  findMedian() {
    if (this.low.size() > this.high.size()) return this.low.peek();
    return (this.low.peek() + this.high.peek()) / 2;
  }
}
// addNum O(log n), findMedian O(1)

The push-then-transfer dance is what guarantees correctness. Inserting directly into whichever heap is smaller can violate the ordering — a small number placed into the high half breaks the invariant. Routing everything through low and then moving its maximum across guarantees the element lands on the correct side regardless of its value.

Part 5 — K-Way Merge and Scheduling

When merging k sorted sequences, the heap holds one element per list, not all elements:

function mergeKLists(lists) {                    // LC 23
  const heap = new MinHeap((a, b) => a.val - b.val);
  for (const node of lists) if (node) heap.push(node);

  const dummy = { next: null };
  let tail = dummy;
  while (heap.size()) {
    const node = heap.pop();
    tail.next = node;
    tail = node;
    if (node.next) heap.push(node.next);         // ← refill from the same list
  }
  return dummy.next;
}
// O(N log k) where N = total nodes, k = number of lists

The heap size stays at k, which is the whole point — pushing everything would be O(N log N) and defeat the purpose. Each pop is immediately followed by a push from the same source, so the heap always holds the current front of every list.

function kSmallestPairs(nums1, nums2, k) {       // LC 373
  const heap = new MinHeap((a, b) => (nums1[a[0]] + nums2[a[1]]) - (nums1[b[0]] + nums2[b[1]]));
  const seen = new Set();
  const push = (i, j) => {
    if (i < nums1.length && j < nums2.length && !seen.has(i + "," + j)) {
      seen.add(i + "," + j);
      heap.push([i, j]);
    }
  };
  push(0, 0);
  const out = [];
  while (out.length < k && heap.size()) {
    const [i, j] = heap.pop();
    out.push([nums1[i], nums2[j]]);
    push(i + 1, j);                              // expand in both directions
    push(i, j + 1);
  }
  return out;
}

Task Scheduler and interval problems use heaps for a different reason — to always know which resource frees up first, which is the same reasoning as Meeting Rooms II.

Part 6 — Quickselect and Recognition

When the data is static and only the kth element is needed, Quickselect is O(n) average:

function quickselect(nums, k) {                  // kth SMALLEST, 1-indexed
  const a = [...nums];
  let lo = 0, hi = a.length - 1, target = k - 1;
  while (lo < hi) {
    const p = partition(a, lo, hi);
    if (p === target) return a[p];
    if (p < target) lo = p + 1;                  // ← recurse into ONE side only
    else hi = p - 1;
  }
  return a[lo];
}

function partition(a, lo, hi) {
  const r = lo + Math.floor(Math.random() * (hi - lo + 1));   // random pivot
  [a[r], a[hi]] = [a[hi], a[r]];
  const pivot = a[hi];
  let i = lo;
  for (let j = lo; j < hi; j++) if (a[j] < pivot) { [a[i], a[j]] = [a[j], a[i]]; i++; }
  [a[i], a[hi]] = [a[hi], a[i]];
  return i;
}
// O(n) average, O(n²) worst — randomised pivot makes the worst case vanishingly unlikely

It is O(n) because it recurses into only one partition: n + n/2 + n/4 + … = 2n. Quicksort recurses into both, which is where its extra log factor comes from.

❌ Using a max-heap to find the k largest elements. It reads correctly — "I want the biggest, so I want a max-heap" — and it even produces the right answer if you push everything and pop k times. But that heap holds all n elements, costing O(n) space and O(n log n) time, which is worse than simply sorting. On a stream of a billion records it is not merely slow, it does not fit in memory.

✅ Use a min-heap capped at size k. Its root is the weakest element currently in the top k, so a new candidate needs exactly one comparison: smaller than the root means it cannot qualify; larger means it displaces the root. The heap never exceeds k elements, giving O(n log k) time and O(k) space, and it works on data too large to hold. The mirror rule applies to "k smallest" — use a max-heap.

Interview Questions

Beginner: What is a binary heap and what are its operations?

A complete binary tree stored in a flat array, maintaining one invariant: every parent compares favourably to its children. In a min-heap, every parent is ≤ both children.

            1              array: [1, 3, 2, 7, 4, 5]
          /   \
         3     2           parent(i) = (i-1) >> 1
        / \   /            left(i)   = 2i + 1
       7   4 5             right(i)  = 2i + 2
OperationCost
peekO(1)
push (sift up)O(log n)
pop (sift down)O(log n)
Build from arrayO(n)
Find arbitrary elementO(n)

Crucially, a heap is not sorted. Only the root is guaranteed to be the extreme; siblings have no relationship. That weaker guarantee is exactly why operations are O(log n) rather than O(n) — maintaining full order on every insert would be far more expensive.

The array representation needs no pointers, because a complete tree's structure is implied by the indices. That makes heaps cache-friendly and memory-efficient compared with a pointer-based tree.

Building in O(n) surprises people. Sifting down from the last internal node backwards costs O(n) total rather than O(n log n), because half the nodes are leaves that never sift at all, and only the root can sift the full height.

The typical uses are priority queues, top-k selection, k-way merge, running medians, and Dijkstra's algorithm.

Beginner: Find the k largest elements. Which heap type do you use, and why?

A min-heap of size k — which is the opposite of most people's first instinct.

function topKLargest(nums, k) {
  const heap = new MinHeap();
  for (const x of nums) {
    heap.push(x);
    if (heap.size() > k) heap.pop();             // evict the smallest
  }
  return heap.a;
}
// O(n log k) time, O(k) space

The reasoning: the heap holds the k largest elements seen so far, so its root is the weakest of the survivors. That makes the root the perfect gatekeeper — a new element needs one comparison to decide its fate.

k = 3, stream: 5, 1, 9, 3, 7, 2

[5] → [1,5] → [1,5,9] → push 3, size 4, pop 1 → [3,5,9]
                      → push 7, pop 3         → [5,7,9]
                      → 2 < root 5, skip      → [5,7,9] ✓

A max-heap would put the largest element at the root, which tells you nothing about which element to evict — you would have to scan all k to find the weakest. So the max-heap approach degenerates into holding all n elements and popping k times: O(n) space and O(n log n) time, which is worse than sorting.

ApproachTimeSpaceStreams?
Sort, take kO(n log n)O(n)No
Min-heap size kO(n log k)O(k)Yes
QuickselectO(n) avgO(1)No

The mirror rule: k smallest uses a max-heap of size k. The general statement is "use the heap whose root is the element you would evict."

The streaming property is the real differentiator — with a billion records, sorting and Quickselect both require the data in memory, while a size-k heap needs only k.

Mid: Find the k most frequent elements, and compare approaches. 
function topKFrequent(nums, k) {
  const freq = new Map();
  for (const x of nums) freq.set(x, (freq.get(x) || 0) + 1);

  const heap = new MinHeap((a, b) => a[1] - b[1]);   // by count

// O(n log k)

But bucket sort is strictly better here, and recognising why is the point of the question: frequencies are bounded by n, so they can index an array directly.

}
// O(n) time, O(n) space

The general lesson is that a heap is not automatically the answer to a top-k question. When the sort key is a bounded integer — a frequency, a small score, an age — bucketing beats the logarithmic factor entirely.

I would still mention the heap version, because it is the one that generalises to a stream where the counts are unbounded or the data does not fit in memory.

Mid: Design a data structure that returns the median of a stream.

Two heaps split the data at the median: a max-heap for the lower half and a min-heap for the upper half, so both medians sit at the roots.

class MedianFinder {
  constructor() {
    this.low = new MinHeap((a,b) => b - a);      // MAX-heap
    this.high = new MinHeap((a,b) => a - b);     // min-heap
  }
  addNum(x) {
    this.low.push(x);
    this.high.push(this.low.pop());              // move low's max into high
    if (this.high.size() > this.low.size()) this.low.push(this.high.pop());
  }
  findMedian() {
    return this.low.size() > this.high.size()
      ? this.low.peek()
      : (this.low.peek() + this.high.peek()) / 2;
  }
}
// addNum O(log n), findMedian O(1)

The push-then-transfer sequence is the subtle part. Inserting directly into whichever heap is smaller can break the ordering — a value of 1 pushed into the high half when the low half contains 5 would leave the structure invalid. Routing every insertion through low and then moving its maximum to high guarantees correct placement regardless of the value.

add 1: low=[1]        high=[]        → transfer → low=[] high=[1] → rebalance → low=[1] high=[]
add 2: low=[2,1]      high=[]        → transfer → low=[1] high=[2]
       median = (1+2)/2 = 1.5 ✓
add 3: low=[3,1] → pop 3 → high=[2,3], rebalance → low=[2,1] high=[3]
       median = 2 ✓

The size invariant is low.size ∈ {high.size, high.size + 1} — low may hold one extra element, which is what makes the odd case read directly from low.peek().

Follow-ups worth anticipating:

ConstraintBetter structure
All numbers in [0, 100]A counting array — O(1) insert, O(100) median
99% of numbers in a small rangeCounting array plus overflow heaps
Need arbitrary percentilesOrder-statistic tree, or t-digest for approximations
Sliding window medianTwo heaps with lazy deletion, or a multiset

Sliding-window median is the genuinely hard variant, because heaps cannot remove an arbitrary element — the standard answer is lazy deletion with a "to remove" hash map, popping stale entries when they surface at a root.

Senior: Merge k sorted linked lists efficiently.

A min-heap holding one node from each list — never more — gives O(N log k).

function mergeKLists(lists) {
  const heap = new MinHeap((a, b) => a.val - b.val);
  for (const node of lists) if (node) heap.push(node);

  const dummy = { next: null };
  let tail = dummy;
  while (heap.size()) {
    const node = heap.pop();
    tail.next = node;
    tail = node;
    if (node.next) heap.push(node.next);         // refill from the SAME list
  }
  tail.next = null;
  return dummy.next;
}
// O(N log k) time, O(k) space

The heap size stays at k, because every pop is followed by at most one push from the same list. Pushing all N nodes up front would be O(N log N) — no better than concatenating and sorting.

ApproachTimeSpace
Concatenate and sortO(N log N)O(N)
Merge one at a timeO(N·k)O(1)
HeapO(N log k)O(k)
Divide and conquerO(N log k)O(log k) stack

Divide and conquer matches the heap's complexity and is often faster in practice because merging two sorted lists is a tight pointer loop with no comparator indirection:

function mergeKListsDC(lists) {
  if (!lists.length) return null;
  while (lists.length > 1) {
    const merged = [];
    for (let i = 0; i < lists.length; i += 2)
      merged.push(mergeTwo(lists[i], lists[i+1] ?? null));
    lists = merged;
  }
  return lists[0];
}

Why both are O(N log k): the heap does N pops at O(log k) each; divide-and-conquer does log k rounds, each touching all N nodes.

I would choose the heap when lists arrive as a stream or when k is large and unknown up front, and divide-and-conquer when all lists are available and constant factors matter. Merging one at a time — O(N·k) — is the trap: it looks natural and is quadratic in k.

Senior: Find the kth largest element. When would you use Quickselect over a heap?

Both solve it; the choice depends on whether the data is static and whether O(n) worst-case matters.

function findKthLargest(nums, k) {               // Quickselect
  const a = [...nums];
  let lo = 0, hi = a.length - 1;
  const target = a.length - k;                   // kth largest = (n-k)th smallest
  while (lo < hi) {
    const p = partition(a, lo, hi);
    if (p === target) return a[p];
    if (p < target) lo = p + 1; else hi = p - 1;
  }
  return a[lo];
}

function partition(a, lo, hi) {
  const r = lo + Math.floor(Math.random() * (hi - lo + 1));   // RANDOM pivot
  [a[r], a[hi]] = [a[hi], a[r]];
  const pivot = a[hi];
  let i = lo;
  for (let j = lo; j < hi; j++) if (a[j] < pivot) { [a[i], a[j]] = [a[j], a[i]]; i++; }
  [a[i], a[hi]] = [a[hi], a[i]];
  return i;
}
// O(n) average, O(n²) worst

Why Quickselect is O(n): it recurses into only one partition, so the work is n + n/2 + n/4 + … = 2n. Quicksort recurses into both halves, which is where its log factor originates.

HeapQuickselect
TimeO(n log k)O(n) average
Worst caseO(n log k)O(n²)
SpaceO(k)O(1)
Mutates inputNoYes (or needs a copy)
StreamingYesNo
Returns all kYesOnly the kth (though the partition gives them)

I would use Quickselect for a one-off query on a static in-memory array where only the kth value is needed — it is genuinely linear and uses no extra space.

I would use a heap when the data streams, when the input must not be mutated, when all k elements are wanted, or when worst-case guarantees matter — a randomised pivot makes O(n²) astronomically unlikely but not impossible.

The randomised pivot is not optional. With a fixed pivot (first or last element), already-sorted input produces maximally unbalanced partitions and the algorithm degrades to O(n²) — on exactly the input that occurs most often in practice.

Median-of-medians guarantees O(n) worst case, but its constant factor is large enough that randomised Quickselect is faster in practice; it is worth mentioning as the theoretical answer.

Solution 
class MinHeap {
  constructor(cmp = (a,b) => a - b) { this.a = []; this.cmp = cmp; }
  size() { return this.a.length; }
  peek() { return this.a[0]; }
  push(v) {
    this.a.push(v);
    let i = this.a.length - 1;
    while (i > 0) {
      const p = (i-1) >> 1;
      if (this.cmp(this.a[p], this.a[i]) <= 0) break;
      [this.a[p], this.a[i]] = [this.a[i], this.a[p]];
      i = p;
    }
  }
  pop() {
    const top = this.a[0], last = this.a.pop();
    if (this.a.length) {
      this.a[0] = last;
      let i = 0;
      for (;;) {
        const l = 2*i+1, r = 2*i+2;
        let m = i;
        if (l < this.a.length && this.cmp(this.a[l], this.a[m]) < 0) m = l;
        if (r < this.a.length && this.cmp(this.a[r], this.a[m]) < 0) m = r;
        if (m === i) break;
        [this.a[m], this.a[i]] = [this.a[i], this.a[m]];
        i = m;
      }
    }
    return top;
  }
}

function checkHeapInvariant(h) {
  for (let i = 1; i < h.a.length; i++) {
    const p = (i-1) >> 1;
    if (h.cmp(h.a[p], h.a[i]) > 0) return false;

function heapify(arr, cmp = (a,b) => a-b) {
  const h = new MinHeap(cmp);
  h.a = [...arr];
  for (let i = (h.a.length >> 1) - 1; i >= 0; i--) {   // last internal node → root
    let j = i;
    for (;;) {
      const l = 2*j+1, r = 2*j+2;
      let m = j;
      if (l < h.a.length && cmp(h.a[l], h.a[m]) < 0) m = l;
      if (r < h.a.length && cmp(h.a[r], h.a[m]) < 0) m = r;
      if (m === j) break;
      [h.a[m], h.a[j]] = [h.a[j], h.a[m]];
      j = m;
    }
  }
  return h;
}

function topKFrequentHeap(nums, k) {
  const freq = new Map();
  for (const x of nums) freq.set(x, (freq.get(x)||0)+1);
  const heap = new MinHeap((a,b) => a[1]-b[1]);
  for (const e of freq) { heap.push(e); if (heap.size() > k) heap.pop(); }
  return heap.a.map(e => e[0]).sort((a,b) => freq.get(b)-freq.get(a));
}

function topKFrequentSort(nums, k) {
  const freq = new Map();
  for (const x of nums) freq.set(x, (freq.get(x)||0)+1);
  return [...freq.entries()].sort((a,b) => b[1]-a[1]).slice(0,k).map(e => e[0]);
}

function topKFrequentBucket(nums, k) {
  const freq = new Map();
  for (const x of nums) freq.set(x, (freq.get(x)||0)+1);
  const buckets = Array.from({length: nums.length+1}, () => []);
  for (const [v,f] of freq) buckets[f].push(v);
  const out = [];
  for (let f = buckets.length-1; f >= 0 && out.length < k; f--)
    for (const v of buckets[f]) { out.push(v); if (out.length === k) break; }
  return out;
}

function kClosestPoints(points, k) {             // LC 973
  const heap = new MinHeap((a,b) => (b[0]*b[0]+b[1]*b[1]) - (a[0]*a[0]+a[1]*a[1]));  // MAX by distance
  for (const p of points) { heap.push(p); if (heap.size() > k) heap.pop(); }
  return heap.a;
}

4 (medium): Build the running-median structure.
Solution 
class MedianFinder {
  constructor() {
    this.low = new MinHeap((a,b) => b - a);      // max-heap
    this.high = new MinHeap((a,b) => a - b);     // min-heap
  }
  addNum(x) {
    this.low.push(x);
    this.high.push(this.low.pop());
    if (this.high.size() > this.low.size()) this.low.push(this.high.pop());
  }
  findMedian() {
    return this.low.size() > this.high.size()
      ? this.low.peek()
      : (this.low.peek() + this.high.peek()) / 2;
  }
}

function referenceMedian(arr) {
  const s = [...arr].sort((a,b) => a-b);
  const n = s.length;
  return n % 2 ? s[(n-1)/2] : (s[n/2 - 1] + s[n/2]) / 2;
}

function mergeKListsHeap(lists) {
  const heap = new MinHeap((a,b) => a.val - b.val);
  for (const node of lists) if (node) heap.push(node);
  const dummy = { next: null };
  let tail = dummy;
  while (heap.size()) {
    const node = heap.pop();
    tail.next = node; tail = node;
    if (node.next) heap.push(node.next);
  }
  tail.next = null;

function mergeTwo(a, b) {
  const dummy = { next: null };
  let tail = dummy;
  while (a && b) {
    if (a.val <= b.val) { tail.next = a; a = a.next; }
    else { tail.next = b; b = b.next; }
    tail = tail.next;
  }
  tail.next = a || b;
  return dummy.next;
}

function mergeKListsDC(lists) {
  let cur = lists.filter(Boolean);

      next.push(mergeTwo(cur[i], i+1 < cur.length ? cur[i+1] : null));
    cur = next;

  return cur[0];
}

function partition(a, lo, hi) {
  const r = lo + Math.floor(Math.random() * (hi - lo + 1));
  [a[r], a[hi]] = [a[hi], a[r]];
  const pivot = a[hi];
  let i = lo;
  for (let j = lo; j < hi; j++) if (a[j] < pivot) { [a[i],a[j]]=[a[j],a[i]]; i++; }
  [a[i], a[hi]] = [a[hi], a[i]];
  return i;
}

function quickselectKthLargest(nums, k) {
  const a = [...nums];
  let lo = 0, hi = a.length - 1;
  const target = a.length - k;
  while (lo < hi) {
    const p = partition(a, lo, hi);
    if (p === target) return a[p];
    if (p < target) lo = p + 1; else hi = p - 1;
  }
  return a[lo];
}

🎯 Key Takeaways

  • A binary heap is a complete tree in a flat array: parent(i) = (i-1)>>1, children = 2i+1, 2i+2.
  • Only the root is ordered — a heap is not sorted, and reading heap.a[k-1] as the kth smallest is wrong.
  • Building from an existing array is O(n) via bottom-up heapify, not O(n log n) via n pushes — roughly 3.5× faster in practice.
  • Top-k largest uses a MIN-heap of size k, because its root is the weakest survivor and therefore the right thing to evict.
  • Mirror rule: k smallest uses a max-heap; k closest uses a max-heap on distance.
  • Push first, then pop if the size exceeds k — popping first evicts a valid element.
  • The heap's decisive advantage is streaming: O(k) space works on data that cannot fit in memory.
  • When the sort key is a bounded integer — a frequency, a small score — bucket sort beats the heap at O(n).
  • Running median uses two heaps, and every insertion must go through low then transfer, or values land on the wrong side.
  • The median invariant is low.size ∈ {high.size, high.size+1}, with both medians at the roots.
  • K-way merge keeps exactly k elements in the heap, refilling from the same list after each pop — pushing everything is O(N log N) and pointless.
  • Merging k lists one at a time is O(N·k) and 120× slower at k=500; divide-and-conquer matches the heap's O(N log k) and is often faster.
  • Quickselect is O(n) average because it recurses into only one partition: n + n/2 + n/4 + … = 2n.
  • Quickselect's pivot must be randomised — a fixed pivot is O(n²) on sorted input, which is 3600× slower on 100k elements.
  • Quickselect is flat in k while the heap degrades as log k grows; use Quickselect for static arrays, the heap for streams and immutability.
  • Searching a heap for an arbitrary value is O(n) — pair it with a hash map if you need lookups or deletions.
