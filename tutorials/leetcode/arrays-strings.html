Arrays & Strings Essentials Foundations

What you'll master: the read/write pointer template that solves an entire family of in-place problems with O(1) space; why string concatenation in a loop is the most common accidental O(n²) in interview code, and what to do instead; prefix and suffix precomputation, which turns "for each position, look at everything else" into two linear passes; the array operations that hide loops and silently change your complexity; cyclic and reversal tricks for in-place rearrangement; and the character encoding traps that break "reverse a string" on real input. Prerequisite: Big-O & Complexity Analysis. Every later pattern is written in this vocabulary.

Part 1 — The Read/Write Pointer

A large family of problems reduces to one template: scan with a read pointer, and advance a separate write pointer only for elements you keep. It gives O(n) time and O(1) space, and it is the answer to almost every question containing the words "in place".

function removeDuplicates(nums) {          // sorted array
  if (nums.length === 0) return 0;
  let write = 1;                           // next slot for a kept value
  for (let read = 1; read < nums.length; read++) {
    if (nums[read] !== nums[write - 1]) {  // keep it?
      nums[write++] = nums[read];
    }
  }
  return write;                            // new logical length
}

[1,1,2,2,3]
 r=1: 1 == nums[0]  skip                  write=1  [1,1,2,2,3]
 r=2: 2 != nums[0]  keep → nums[1]=2      write=2  [1,2,2,2,3]
 r=3: 2 == nums[1]  skip                  write=2
 r=4: 3 != nums[1]  keep → nums[2]=3      write=3  [1,2,3,2,3]
                                                    └─ valid ─┘  return 3

The invariant is what makes it correct: everything before write is a finished, correct answer, and everything from read onward is unprocessed. Since write ≤ read always, you never overwrite an element you have not yet examined.

ProblemKeep condition
Remove Duplicates from Sorted Arraynums[read] !== nums[write-1]
Remove Element (value v)nums[read] !== v
Move Zeroesnums[read] !== 0, then zero-fill the tail
Remove Duplicates, at most twicewrite < 2 || nums[read] !== nums[write-2]
Partition by predicatepred(nums[read])
🔑 One template, five problems, and the only thing that changes is the keep condition. This is what "learn patterns, not problems" means concretely — a candidate who has memorised Move Zeroes solves Move Zeroes; a candidate who knows the read/write template solves all five and adapts to the sixth they have never seen. When a problem says "in place" and "return the new length", write the skeleton first and then think about the condition.

The at-most-twice variant is worth reading closely, because comparing against nums[write-2] rather than nums[read-1] is the whole trick:

function removeDuplicatesII(nums) {
  let write = 0;
  for (const x of nums) {
    if (write < 2 || x !== nums[write - 2]) nums[write++] = x;
  }
  return write;
}
// Comparing to the WRITTEN output (not the input) generalises to "at most k"
// by changing 2 to k — the input may have runs of any length.

Part 2 — String Immutability

In JavaScript, Python, Java and C#, strings are immutable: every "modification" allocates a new string and copies the old contents.

let s = "";
for (let i = 0; i < n; i++) s += chars[i];    // O(n²) — LOOKS linear

// iteration 1: copy 0 chars   iteration 2: copy 1   ...   iteration n: copy n-1
// total = 0 + 1 + ... + (n-1) = n(n-1)/2 = O(n²)

const buf = [];
for (let i = 0; i < n; i++) buf.push(chars[i]);
const s = buf.join("");                        // O(n) — one allocation at the end
LanguageWrongRight
JavaScripts += c in a looparr.push(c) then join("")
Pythons += c"".join(parts)
Javas += cStringBuilder.append
C#s += cStringBuilder.Append
Go, Rust—strings.Builder, String::push_str

This is the single most common accidental O(n²) in interview code, and it is dangerous precisely because the code reads as linear. Interviewers watch for it; saying "I'll build into an array and join at the end, since string concatenation in a loop would be quadratic" as you write it is a free signal.

When a string must be modified in place, convert to an array first:

function reverseWords(s) {
  const a = s.split("");                    // now mutable
  reverse(a, 0, a.length - 1);              // reverse the whole thing
  let start = 0;                            // then reverse each word back
  for (let i = 0; i <= a.length; i++) {
    if (i === a.length || a[i] === " ") { reverse(a, start, i - 1); start = i + 1; }
  }
  return a.join("");
}
function reverse(a, l, r) { while (l < r) { [a[l], a[r]] = [a[r], a[l]]; l++; r--; } }

Reverse-all-then-reverse-each-part is a reusable trick: it also rotates an array by k in O(1) space, which Part 5 covers.

Part 3 — Prefix and Suffix Precomputation

When a problem asks "for each position, something about everything before or after it", the naive answer is a nested loop. Two linear passes replace it.

// Product of Array Except Self — no division, O(n) time, O(1) extra space
function productExceptSelf(nums) {
  const n = nums.length, res = new Array(n).fill(1);

  let prefix = 1;
  for (let i = 0; i < n; i++) { res[i] = prefix; prefix *= nums[i]; }   // ← left pass

  let suffix = 1;
  for (let i = n - 1; i >= 0; i--) { res[i] *= suffix; suffix *= nums[i]; }  // ← right pass

  return res;
}

nums   = [1, 2, 3, 4]
after left pass  res = [1, 1, 2,  6]      product of everything to the LEFT
suffix values      =  [24, 12, 4, 1]      product of everything to the RIGHT
after right pass res = [24, 12, 8, 6]     ✓

Writing the prefix into the result array before multiplying by the suffix is what keeps it O(1) extra space — the output does not count, so no auxiliary arrays are needed.

Note the trap the problem is built around: dividing the total product by nums[i] is obvious, faster to write, and wrong — it breaks on any zero. Interviewers ask this one specifically to see whether you check that edge case.

ProblemPrefix holdsSuffix holds
Product Except SelfProduct of the leftProduct of the right
Trapping Rain WaterMax height to the leftMax height to the right
Candy (min sweets)Left-to-right constraintRight-to-left constraint
Best Time to Buy/Sell IIMin price so farMax price ahead

From Big-O: the most common wrong analysis is counting visible loops. Array and string methods are where the invisible ones live.

Three of these turn a correct algorithm into a slow one without changing its output, so they are worth recognising on sight:

// ✗ O(n²) — shift() reindexes on every pop
while (queue.length) { const node = queue.shift(); ... }
// ✓ O(n)
let head = 0;
while (head < queue.length) { const node = queue[head++]; ... }

// ✗ O(n·k) — slice allocates a k-length copy each iteration
for (let i = 0; i + k <= n; i++) process(arr.slice(i, i + k));
// ✓ O(n) — slide the window instead
let sum = 0;
for (let i = 0; i < n; i++) { sum += arr[i]; if (i >= k) sum -= arr[i-k]; }

// ✗ O(n²) — includes scans
for (const x of arr) if (!out.includes(x)) out.push(x);
// ✓ O(n)
const seen = new Set();
for (const x of arr) if (!seen.has(x)) { seen.add(x); out.push(x); }

Part 5 — In-Place Rearrangement

Rotation by k is the canonical O(1)-space rearrangement, and the reversal trick is the one to memorise:

function rotate(nums, k) {
  const n = nums.length;
  k %= n;                                  // ← k can exceed n
  reverse(nums, 0, n - 1);                 // reverse everything
  reverse(nums, 0, k - 1);                 // reverse the first k
  reverse(nums, k, n - 1);                 // reverse the rest
}

[1,2,3,4,5,6,7], k = 3

reverse all      → [7,6,5,4,3,2,1]
reverse first 3  → [5,6,7,4,3,2,1]
reverse rest     → [5,6,7,1,2,3,4]   ✓

Why it works: rotating right by k means the last k elements move to the front while both groups keep their internal order. Reversing everything puts the groups in the right place with their order flipped; reversing each group restores it.

Cyclic replacement is the other approach, and it exists mainly as a lesson about a subtle failure:

function rotateCyclic(nums, k) {
  const n = nums.length; k %= n;
  let count = 0;
  for (let start = 0; count < n; start++) {      // ← may need several cycles
    let current = start, prev = nums[start];
    do {
      const next = (current + k) % n;
      [nums[next], prev] = [prev, nums[next]];
      current = next;
      count++;
    } while (start !== current);
  }
}

The count < n outer loop is not decoration. When gcd(n, k) > 1 the cycle returns to its start before visiting every element, so a single pass moves only some of them — with n = 6, k = 2 there are two disjoint cycles. Candidates who write one cycle get a plausible wrong answer on exactly those inputs.

Two-pass counting is the other reusable in-place idea — useful whenever the value range is small and known:

// Sort Colors (Dutch national flag) — one pass, O(1) space
function sortColors(nums) {
  let low = 0, mid = 0, high = nums.length - 1;
  while (mid <= high) {
    if (nums[mid] === 0)      { [nums[low], nums[mid]] = [nums[mid], nums[low]]; low++; mid++; }
    else if (nums[mid] === 2) { [nums[mid], nums[high]] = [nums[high], nums[mid]]; high--; }
    else mid++;                      // 1: already in place
  }
}

Do not advance mid after swapping with high — the value that arrived from the back is unexamined. Advancing it is the standard bug in this problem.

Part 6 — Character and Encoding Traps

Interview problems say "string" and mean "sequence of characters", but real strings are sequences of code units, and the difference produces bugs that pass every ASCII test.

"héllo".length              // 5
"👋".length                 // 2  ← one emoji, two UTF-16 code units
[..."👋"].length            // 1  ← spread iterates by code POINT

"👋".split("").reverse().join("")   // broken — splits the surrogate pair
[..."👋a"].reverse().join("")       // "a👋"  ✓
TaskSafe approach
Iterate charactersfor (const ch of str) or [...str]
Reverse a string[...str].reverse().join("")
Compare case-insensitivelya.toLowerCase() === b.toLowerCase()
Check alphanumeric/[a-z0-9]/i.test(ch)
Character to index (a–z)ch.charCodeAt(0) - 97

The 26-slot frequency array is worth knowing because it appears in dozens of problems and beats a hash map on constant factors:

function isAnagram(s, t) {
  if (s.length !== t.length) return false;
  const count = new Array(26).fill(0);
  for (let i = 0; i < s.length; i++) {
    count[s.charCodeAt(i) - 97]++;
    count[t.charCodeAt(i) - 97]--;         // one pass, both strings
  }
  return count.every(c => c === 0);
}
// O(n) time, O(1) space — 26 is a constant

Say "O(1) space because the alphabet is fixed at 26" out loud. It is the kind of precise claim interviewers probe, and the follow-up — "what if it were Unicode?" — has the answer "then it is O(k) for alphabet size k, and I'd use a hash map".

❌ Reaching for extra arrays whenever a problem involves rearranging. Building a result array, filtering into a new list, or slicing sub-arrays inside a loop is the instinct, and it produces O(n) space where O(1) was asked for — or worse, O(n²) time when the slicing happens per iteration. The code is correct, so tests pass, and the follow-up "can you do it in place?" arrives with no plan.

✅ Reach for two indices before reaching for a second array. Read/write pointers handle filtering and deduplication; converging pointers handle reversal, rotation and partitioning; prefix and suffix passes handle "everything except me". All are O(1) extra space, all are the expected answer when a problem says "in place", and all are one template each — the cost of learning them is far lower than the cost of not having them when the follow-up comes.

Interview Questions

Beginner: Remove all instances of a value from an array in place and return the new length.

This is the read/write pointer template with the keep condition nums[read] !== val.

function removeElement(nums, val) {
  let write = 0;
  for (let read = 0; read < nums.length; read++) {
    if (nums[read] !== val) nums[write++] = nums[read];
  }
  return write;
}
// O(n) time, O(1) space

The invariant: everything before write is final and correct; everything from read onward is unprocessed. Because write ≤ read always, we never overwrite an element we have not read.

nums = [3,2,2,3], val = 3
r=0: 3 == 3  skip                write=0
r=1: 2 != 3  nums[0]=2           write=1
r=2: 2 != 3  nums[1]=2           write=2
r=3: 3 == 3  skip                write=2   → [2,2,_,_], return 2  ✓

The variant worth knowing is when order does not matter and removals are rare — swap from the end instead, which minimises writes:

function removeElement(nums, val) {
  let n = nums.length, i = 0;
  while (i < n) {
    if (nums[i] === val) nums[i] = nums[--n];   // pull from the back, don't advance i
    else i++;
  }
  return n;
}

Not advancing i after the swap is essential — the value pulled from the back has not been examined and might also equal val. That is the same bug as advancing mid in Sort Colors.

Beginner: Why is building a string with += in a loop O(n²), and what should you do?

Because strings are immutable in JavaScript, Python, Java and C#. s += c does not append — it allocates a new string and copies the entire existing content.

iteration 1: copy 0 chars
iteration 2: copy 1
iteration 3: copy 2
...
iteration n: copy n-1
             ─────────
total = n(n-1)/2 = O(n²)

It is dangerous because the code looks linear — one loop, one operation per iteration. Nothing signals that the operation's cost grows with what has already been built.

The fix is a mutable buffer:

const parts = [];
for (let i = 0; i < n; i++) parts.push(chars[i]);
const s = parts.join("");            // O(n) — one allocation
LanguageUse
JavaScriptArray + join("")
Python"".join(parts)
Java / C#StringBuilder

The measurement is stark — at n = 100,000, concatenation takes seconds while array-and-join is milliseconds.

Worth noting for precision: some engines optimise simple concatenation patterns with ropes or in-place extension when the intermediate is not referenced elsewhere, so you may not always see quadratic behaviour in practice. But it is not guaranteed by any specification, it varies by engine, and in an interview the array-and-join answer is the one that is correct by construction.

Mid: Solve Product of Array Except Self without division, in O(1) extra space.

Two passes: one accumulating products from the left, one from the right, both writing into the output array.

function productExceptSelf(nums) {
  const n = nums.length, res = new Array(n).fill(1);

  let prefix = 1;
  for (let i = 0; i < n; i++) { res[i] = prefix; prefix *= nums[i]; }

  let suffix = 1;
  for (let i = n - 1; i >= 0; i--) { res[i] *= suffix; suffix *= nums[i]; }

  return res;
}

The key ordering detail: in each pass, write the accumulator before updating it with the current element. That is what excludes nums[i] from its own product.

nums = [1, 2, 3, 4]

left pass:   res = [1, 1, 2, 6]        (product of everything to the left)
right pass:  suffix = 24, 12, 4, 1
             res = [1*24, 1*12, 2*4, 6*1] = [24, 12, 8, 6]   ✓

Why not division? Because total / nums[i] breaks on zeros:

[1, 0, 3]  total = 0
  res[0] = 0/1 = 0     ✓ by luck
  res[1] = 0/0 = NaN   ✗

Handling zeros with division means counting them and special-casing one zero versus two — messier than the two-pass solution, and the problem forbids division precisely to steer you here.

On the space claim: this is O(1) extra space because the output array is not counted as auxiliary — a convention worth stating explicitly rather than assuming the interviewer shares it.

Mid: Rotate an array right by k in O(1) space. Why does the reversal trick work?

Three reversals: the whole array, then the first k, then the remaining n − k.

function rotate(nums, k) {
  const n = nums.length;
  k %= n;                                  // k may exceed n
  reverse(nums, 0, n - 1);
  reverse(nums, 0, k - 1);
  reverse(nums, k, n - 1);
}
function reverse(a, l, r) { while (l < r) { [a[l], a[r]] = [a[r], a[l]]; l++; r--; } }

[1,2,3,4,5,6,7], k = 3
reverse all     → [7,6,5,4,3,2,1]
reverse [0..2]  → [5,6,7,4,3,2,1]
reverse [3..6]  → [5,6,7,1,2,3,4]   ✓

Why it works: a right rotation by k means the array becomes [B, A] where A is the first n−k elements and B the last k, with both keeping their internal order. Reversing the whole array produces [reverse(B), reverse(A)] — the blocks are now in the right places with their contents flipped, so reversing each block restores it.

k %= n is not optional — k = 10 on a 7-element array must behave as k = 3, and without it reverse(nums, 0, 9) runs past the end.

The alternative, cyclic replacement, is O(n) with one pass but has a trap:

n = 6, k = 2:  0 → 2 → 4 → 0   (cycle closes after 3 of 6 elements)
               1 → 3 → 5 → 1   (a second, disjoint cycle)

When gcd(n, k) > 1 there are multiple disjoint cycles, so a single pass leaves half the array unmoved. The loop must continue until count === n. I would present the reversal version in an interview — same complexity, far harder to get wrong.

Senior: Sort an array of 0s, 1s and 2s in a single pass with O(1) space.

The Dutch national flag partition — three pointers maintaining four regions.

function sortColors(nums) {
  let low = 0, mid = 0, high = nums.length - 1;
  while (mid <= high) {
    if (nums[mid] === 0) {
      [nums[low], nums[mid]] = [nums[mid], nums[low]];
      low++; mid++;
    } else if (nums[mid] === 2) {
      [nums[mid], nums[high]] = [nums[high], nums[mid]];
      high--;                                  // ← do NOT advance mid
    } else {
      mid++;
    }
  }
}

The invariant is the whole solution:

[0 ... low-1]   all 0s        (settled)
[low ... mid-1] all 1s        (settled)
[mid ... high]  UNKNOWN       (shrinking)
[high+1 ... n-1] all 2s       (settled)

Why mid advances on a 0-swap but not on a 2-swap: swapping with low brings back a value from the settled 1s region, which is known to be a 1 — safe to move past. Swapping with high brings back a value from the unknown region, which has never been examined. Advancing there is the standard bug:

[2, 0, 1] with the buggy version (mid++ after the high swap):
  mid=0: nums[0]=2, swap with high → [1,0,2], high=1, mid=1  ← bug: skipped the 1
  mid=1: nums[1]=0, swap with low  → [0,1,2], low=1, mid=2
  mid=2 > high=1, stop → [0,1,2]  ✓ by luck here, but fails on other inputs

The termination condition is mid ≤ high, not mid < high, because the element at mid === high is still unclassified.

The generalisation worth mentioning: this is three-way partitioning, the same routine that makes quicksort robust against arrays with many duplicate keys — which is a nice connection to draw if the interviewer asks where else it appears.

Senior: What can go wrong with "reverse a string" on real-world input?

The naive solution is correct for ASCII and wrong for most other text, because a JavaScript string is a sequence of UTF-16 code units, not characters.

"hello".split("").reverse().join("")   // "olleh"  ✓
"👋a".split("").reverse().join("")     // broken — the emoji is 2 code units,
                                       //   reversing them produces an invalid pair

Three layers of the problem, each needing a different fix:

LayerIssueFix
Code unitsEmoji and CJK extensions are surrogate pairs[...str] iterates code points
Combining marks"é" may be e + U+0301Normalise (NFC) first
Grapheme clustersFlags and skin-tone emoji are several code pointsIntl.Segmenter
// handles surrogate pairs
const reversed = [...str].reverse().join("");

// handles combining marks too
const reversed = [...str.normalize("NFC")].reverse().join("");

// handles grapheme clusters (flags, ZWJ sequences, skin tones)
const seg = new Intl.Segmenter("en", { granularity: "grapheme" });
const reversed = [...seg.segment(str)].map(s => s.segment).reverse().join("");

What I would say in an interview: "For the ASCII case, two pointers swapping in place is O(n) with O(1) space. If the input can contain Unicode, I'd iterate by code point with spread — and if it can contain emoji with ZWJ sequences or combining marks, correct reversal needs grapheme segmentation. Which should I assume?"

That question is the point. The interviewer almost always says "assume ASCII", and the answer takes fifteen seconds — but it demonstrates awareness of a class of bug that reaches production constantly, and it distinguishes a candidate who has shipped text handling from one who has only solved puzzles.

1 (easy): Implement the read/write template for four different keep conditions.
Solution

One skeleton, four problems — only the condition changes:

// (a) Move Zeroes — keep non-zeros, then zero-fill the tail
function moveZeroes(nums) {
  let write = 0;
  for (const x of nums) if (x !== 0) nums[write++] = x;
  while (write < nums.length) nums[write++] = 0;
}

// (b) Remove Duplicates (sorted)
function removeDuplicates(nums) {
  if (!nums.length) return 0;
  let write = 1;
  for (let read = 1; read < nums.length; read++)
    if (nums[read] !== nums[write - 1]) nums[write++] = nums[read];
  return write;
}

// (c) Remove Duplicates, at most twice
function removeDuplicatesII(nums) {
  let write = 0;
  for (const x of nums)
    if (write < 2 || x !== nums[write - 2]) nums[write++] = x;
  return write;
}

// (d) Partition: evens before odds
function partitionEvens(nums) {
  let write = 0;
  for (let read = 0; read < nums.length; read++)
    if (nums[read] % 2 === 0) { [nums[write], nums[read]] = [nums[read], nums[write]]; write++; }
  return write;
}

Test them:

let a = [0,1,0,3,12];        moveZeroes(a);              console.log(a);
let b = [1,1,2,2,3];         console.log(removeDuplicates(b),   b.slice(0,3));
let c = [1,1,1,2,2,3];       console.log(removeDuplicatesII(c), c.slice(0,5));
let d = [3,1,2,4];           console.log(partitionEvens(d),     d);

[1,3,12,0,0]
3 [1,2,3]
5 [1,1,2,2,3]
2 [2,4,1,3]

Note the difference between (a)/(b) and (d). The first two overwrite, which is safe because write ≤ read and overwritten values are already processed. (d) swaps, which is required when the displaced element must be preserved rather than discarded. Choosing wrongly is a silent correctness bug: swapping in (a) would preserve zeros in the wrong places, and overwriting in (d) would destroy the odd numbers.

(c) is the subtle one: comparing against nums[write-2] looks at the output being built, not the input. Comparing nums[read-1] instead fails on [1,1,1,1], where the input has a run longer than the allowed count.

// building a run-length encoding
function encodeBad(s) {
  let out = "";
  let i = 0;
  while (i < s.length) {
    let j = i;
    while (j < s.length && s[j] === s[i]) j++;
    out += s[i] + (j - i);            // ← quadratic
    i = j;
  }
  return out;
}

function encodeGood(s) {
  const out = [];
  let i = 0;
  while (i < s.length) {
    let j = i;
    while (j < s.length && s[j] === s[i]) j++;
    out.push(s[i], j - i);            // ← linear
    i = j;
  }
  return out.join("");
}

The algorithm is O(n); the string building made it O(n²). This is why the habit is to reach for an array buffer automatically rather than deciding case by case.

3 (medium): Solve Trapping Rain Water three ways and compare space.
Solution

Water above bar i is min(maxLeft, maxRight) − height[i]. Three implementations of that same insight:

// (a) brute force — O(n²) time, O(1) space
function trapBrute(h) {
  let total = 0;
  for (let i = 0; i < h.length; i++) {
    let l = 0, r = 0;
    for (let j = 0; j <= i; j++) l = Math.max(l, h[j]);
    for (let j = i; j < h.length; j++) r = Math.max(r, h[j]);
    total += Math.min(l, r) - h[i];
  }
  return total;
}

// (b) prefix/suffix arrays — O(n) time, O(n) space
function trapPrefix(h) {
  const n = h.length;
  if (!n) return 0;
  const left = new Array(n), right = new Array(n);
  left[0] = h[0];
  for (let i = 1; i < n; i++) left[i] = Math.max(left[i-1], h[i]);
  right[n-1] = h[n-1];
  for (let i = n-2; i >= 0; i--) right[i] = Math.max(right[i+1], h[i]);

  let total = 0;
  for (let i = 0; i < n; i++) total += Math.min(left[i], right[i]) - h[i];
  return total;
}

// (c) two pointers — O(n) time, O(1) space
function trapTwoPtr(h) {
  let l = 0, r = h.length - 1, leftMax = 0, rightMax = 0, total = 0;
  while (l < r) {
    if (h[l] < h[r]) {                    // the SMALLER side bounds the water
      leftMax = Math.max(leftMax, h[l]);
      total += leftMax - h[l];
      l++;
    } else {
      rightMax = Math.max(rightMax, h[r]);
      total += rightMax - h[r];
      r--;
    }
  }
  return total;
}

Why (c) is correct is the interview question. When h[l] < h[r], we know there exists some bar on the right at least as tall as h[r], so the right bound is at least h[r] > h[l]. Therefore min(leftMax, rightMax) = leftMax for position l — we can compute its water without knowing the actual right maximum.

Verify all three agree, then time them:

const h = [0,1,0,2,1,0,1,3,2,1,2,1];

  const t = performance.now(); const v = f(big);
  console.log(n, v, (performance.now()-t).toFixed(1) + " ms");
}

4 (medium): Implement rotation both ways and find the cyclic bug.
Solution 
function reverse(a, l, r) { while (l < r) { [a[l], a[r]] = [a[r], a[l]]; l++; r--; } }

function rotateReversal(nums, k) {
  const n = nums.length;
  k %= n;
  reverse(nums, 0, n - 1);
  reverse(nums, 0, k - 1);
  reverse(nums, k, n - 1);
}

// deliberately buggy: only one cycle
function rotateCyclicBuggy(nums, k) {
  const n = nums.length; k %= n;
  let current = 0, prev = nums[0];
  do {
    const next = (current + k) % n;
    [nums[next], prev] = [prev, nums[next]];
    current = next;
  } while (current !== 0);
}

Find the input where the buggy version fails:

  const a = Array.from({length:n}, (_, i) => i);
  const b = [...a];
  rotateReversal(a, k);
  rotateCyclicBuggy(b, k);
  console.log(`n=${n} k=${k} gcd=${gcd(n,k)}`, JSON.stringify(a),
              JSON.stringify(b), a.join() === b.join() ? "ok" : "MISMATCH");
}

The pattern is exact: it fails precisely when gcd(n, k) > 1. The permutation decomposes into gcd(n, k) disjoint cycles, and a single pass traverses only one of them:

n=6, k=2:  cycle A: 0 → 2 → 4 → 0
           cycle B: 1 → 3 → 5 → 1     ← never visited

The fix is an outer loop counting moved elements:

function rotateCyclic(nums, k) {
  const n = nums.length; k %= n;
  let count = 0;
  for (let start = 0; count < n; start++) {
    let current = start, prev = nums[start];
    do {
      const next = (current + k) % n;
      [nums[next], prev] = [prev, nums[next]];
      current = next;
      count++;
    } while (start !== current);
  }
}

Verify it now matches everywhere, then note the practical conclusion: both are O(n) time and O(1) space, but the reversal version has no cycle structure to reason about and cannot fail this way. In an interview, present the reversal solution — equal complexity, far lower risk, and it is explainable in three lines.

5 (hard): Implement string compression in place with O(1) space.
Solution

The problem (LC 443): given an array of characters, compress runs in place — ["a","a","b","b","c","c","c"] becomes ["a","2","b","2","c","3"] and returns 6. Runs of length 1 keep no count. Counts of 10 or more occupy several slots.

The read/write template, with the complication that the digits of a count must be written individually:

function compress(chars) {
  let write = 0, read = 0;

  while (read < chars.length) {
    const ch = chars[read];
    let count = 0;
    while (read < chars.length && chars[read] === ch) { read++; count++; }

    chars[write++] = ch;                       // always write the character
    if (count > 1) {                           // counts of 1 are omitted
      for (const d of String(count)) chars[write++] = d;
    }
  }
  return write;
}

Why it is safe to write while reading is the invariant worth stating: a run of length L is replaced by 1 + digits(L) slots, and 1 + digits(L) ≤ L for every L ≥ 1. So write never overtakes read:

L = 1  → 1 slot  ≤ 1   ✓
L = 2  → 2 slots ≤ 2   ✓   (the tight case)
L = 9  → 2 slots ≤ 9   ✓
L = 12 → 3 slots ≤ 12  ✓

L = 2 is the tight case, where output length equals input length — proving it is where the O(1)-space claim comes from, and it is the argument an interviewer wants to hear.

Test the cases that break naive versions:

  [Array(100).fill("x"),           4, "x100"],        // three digits

The two bugs this problem is designed to catch: writing "12" as a single array element rather than the characters "1" and "2", and emitting "1" after a run of length one. Both produce plausible output on the sample input and fail on the test cases above — which is why enumerating edge cases before coding matters more here than the algorithm does.

function reverseAscii(chars) {          // in place, O(n) time, O(1) space
  let l = 0, r = chars.length - 1;
  while (l < r) { [chars[l], chars[r]] = [chars[r], chars[l]]; l++; r--; }
  return chars;
}

🎯 Key Takeaways

  • The read/write pointer template solves an entire family of in-place problems — only the keep condition changes between them.
  • Its invariant: everything before write is final, everything from read on is unprocessed, and write ≤ read guarantees you never clobber unread data.
  • Overwrite when displaced values can be discarded; swap when they must be preserved — choosing wrongly is a silent correctness bug.
  • For "at most k duplicates", compare against the written output (nums[write-k]), not the input.
  • Strings are immutable in JS, Python, Java and C#, so += in a loop is O(n²) — the most common accidental quadratic in interview code.
  • Build strings in an array and join once; the code that looks linear is the one that is not.
  • Prefix and suffix passes replace "for each position, look at everything else" with two linear scans.
  • Product Except Self writes the prefix into the output before applying the suffix, giving O(1) extra space — and division breaks on zeros.
  • shift(), slice() in a loop, and includes() hide loops that silently change your complexity.
  • Use a head index instead of shift() for queues, or BFS becomes O(V² + E).
  • Rotation by k: k %= n, then reverse all, reverse the first k, reverse the rest.
  • Cyclic rotation needs an outer loop — when gcd(n, k) > 1 the permutation splits into disjoint cycles and one pass misses most elements.
  • Dutch national flag sorts 0s/1s/2s in one pass; do not advance mid after swapping with high, because that value is unexamined.
  • A 26-slot frequency array beats a hash map for lowercase-letter problems, and it is O(1) space because the alphabet is fixed.
  • str.length counts UTF-16 code units, so split("").reverse() corrupts emoji.
  • Unicode correctness has three layers: code points ([...str]), normalisation (combining marks), and graphemes (Intl.Segmenter).
  • Asking "should I assume ASCII?" costs fifteen seconds and demonstrates awareness of a real production bug class.
  • In-place string compression is safe because 1 + digits(L) ≤ L for every run length — that inequality is the O(1)-space proof.
