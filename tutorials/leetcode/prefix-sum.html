Prefix Sum Core Pattern

What you'll master: the identity that turns any range sum into a subtraction, and the off-by-one convention that makes it painless; why prefix sums succeed exactly where sliding window fails, because they need no monotonicity; the prefix-plus-hash-map combination that counts subarrays with a target sum in O(n); the running-balance trick that converts "equal counts of two things" into "the same prefix seen twice"; prefix XOR, prefix products, and the 2-D extension; and the difference-array technique for applying many range updates in O(1) each. Prerequisites: Hashing, Sliding Window.

Part 1 — The Identity

A prefix sum array stores the running total, so every range sum becomes the difference of two prefixes.

nums    = [ 2,  4,  1,  5,  3 ]
prefix  = [0, 2,  6,  7, 12, 15 ]        ← length n+1, prefix[0] = 0
            ↑
        the empty prefix

sum(i..j) = prefix[j+1] - prefix[i]

sum(1..3) = prefix[4] - prefix[1] = 12 - 2 = 10    (4 + 1 + 5)  ✓

Use the length-(n+1) convention with prefix[0] = 0. It removes every special case for ranges that start at index 0, and it is the single biggest source of off-by-one bugs when omitted:

// ✓ n+1 convention — no special cases
const prefix = new Array(nums.length + 1).fill(0);
for (let i = 0; i < nums.length; i++) prefix[i + 1] = prefix[i] + nums[i];
const rangeSum = (i, j) => prefix[j + 1] - prefix[i];      // inclusive [i..j]

// ✗ n-length version needs a branch every time
const p = [nums[0]];
for (let i = 1; i < nums.length; i++) p[i] = p[i-1] + nums[i];
const rangeSumBad = (i, j) => i === 0 ? p[j] : p[j] - p[i-1];   // ← the branch
BuildQuery a rangeUpdate an element
Plain array—O(n)O(1)
Prefix sumO(n)O(1)O(n) — must rebuild
Fenwick / segment treeO(n)O(log n)O(log n)

Prefix sums are for static data. If elements change between queries, the rebuild cost dominates and you need a Fenwick tree instead — that trade-off is what "Range Sum Query — Mutable" (LC 307) is testing.

Part 2 — Where Sliding Window Fails

Sliding window requires monotonicity: extending must increase the sum, shrinking must decrease it. Negative values break that, and prefix sums do not care.

"count subarrays summing to k",  nums may contain negatives

window:  extending can DECREASE the sum → shrink logic is unreliable   ✗
prefix:  sum(i..j) = prefix[j+1] - prefix[i]  holds for ANY values     ✓

The rearrangement is the whole trick — it converts a search into a lookup:

sum(i..j) == k
⟺  prefix[j+1] - prefix[i] == k
⟺  prefix[i] == prefix[j+1] - k        ← "have I seen this prefix before?"

function subarraySum(nums, k) {                    // LC 560
  const seen = new Map([[0, 1]]);                  // the empty prefix, seen once
  let prefix = 0, count = 0;
  for (const x of nums) {
    prefix += x;
    count += seen.get(prefix - k) ?? 0;            // every earlier match is a subarray
    seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
  }
  return count;
}
// O(n) time, O(n) space
🔑 The [[0, 1]] seed is the most commonly omitted line in this pattern. It represents the empty prefix — the subarray that starts at index 0 has no earlier prefix to subtract, so without the seed every such subarray is missed. With nums = [3] and k = 3: prefix becomes 3, we look for 3 − 3 = 0, and only the seed makes that lookup succeed. Test with a single-element array whose value equals k and the bug appears immediately.

Store counts, not presence. The same prefix value can occur several times, and each occurrence is a distinct subarray:

nums = [1, -1, 1, -1],  k = 0

prefix values: 0(seed), 1, 0, 1, 0
              → prefix 0 occurs 3 times, prefix 1 twice
              → pairs: C(3,2) + C(2,2) = 3 + 1 = 4 subarrays  ✓

using a Set instead of a Map would count each prefix once → wrong answer

Part 3 — The Running Balance Trick

"Equal numbers of two things" becomes a prefix-sum problem by mapping one thing to +1 and the other to −1. A balanced range is then one where the running balance is the same at both ends.

function findMaxLength(nums) {                     // LC 525 — equal 0s and 1s
  const firstSeen = new Map([[0, -1]]);            // balance 0 at index -1
  let balance = 0, best = 0;
  for (let i = 0; i < nums.length; i++) {
    balance += nums[i] === 1 ? 1 : -1;
    if (firstSeen.has(balance)) {
      best = Math.max(best, i - firstSeen.get(balance));   // same balance → equal counts
    } else {
      firstSeen.set(balance, i);                   // keep the EARLIEST index only
    }
  }
  return best;
}

nums    = [0, 1, 0, 0, 1, 1, 0]
balance = [-1, 0, -1, -2, -1, 0, -1]
              ↑                 ↑
        balance 0 at index 1 and index 5 → range (1..5] has equal 0s and 1s, length 4 ✓

For "longest" you must store the earliest index and never overwrite it — the farther apart the two equal balances, the longer the subarray. This is the opposite of the counting version, which stores every occurrence.

ProblemMappingMap stores
Count subarrays summing to kThe values themselvesCount of each prefix
Longest with equal 0s and 1s0 → −1, 1 → +1Earliest index per balance
Longest subarray summing to kThe values themselvesEarliest index per prefix
Subarray sum divisible by kValues, then prefix mod kCount per remainder
Contiguous with equal a's and b'sa → +1, b → −1, others → 0Earliest index per balance

The divisibility variant needs one extra care in JavaScript, because % returns negative results for negative operands:

function subarraysDivByK(nums, k) {                // LC 974
  const count = new Map([[0, 1]]);
  let prefix = 0, total = 0;
  for (const x of nums) {
    prefix += x;
    const r = ((prefix % k) + k) % k;              // ← normalise to [0, k)
    total += count.get(r) ?? 0;
    count.set(r, (count.get(r) ?? 0) + 1);
  }
  return total;
}

Two prefixes with the same remainder mod k differ by a multiple of k — so their enclosed range is divisible by k. Without normalisation, -1 % 5 is -1 rather than 4, and matching remainders are never found.

Part 4 — Other Prefix Aggregates

The technique works for any operation with an inverse (or its own inverse).

AggregateRange formulaCaveat
SumP[j+1] − P[i]Watch overflow in fixed-width languages
XORP[j+1] ^ P[i]XOR is its own inverse — no subtraction needed
ProductP[j+1] / P[i]Breaks on zeros — use prefix/suffix passes instead
Count of a propertyP[j+1] − P[i]Map the property to 0/1 first
Min / max—No inverse — needs a sparse table or segment tree

Prefix XOR is elegant because XOR undoes itself:

function subarrayXor(nums, k) {
  const seen = new Map([[0, 1]]);
  let px = 0, count = 0;
  for (const x of nums) {
    px ^= x;
    count += seen.get(px ^ k) ?? 0;          // px ^ prefix_i == k  ⟺  prefix_i == px ^ k
    seen.set(px, (seen.get(px) ?? 0) + 1);
  }
  return count;
}

Min and max have no inverse, which is why "range minimum query" is a different problem requiring a sparse table (O(n log n) build, O(1) query) or a segment tree. Attempting a prefix-min array gives you the minimum of every prefix, not of an arbitrary range.

The 2-D extension uses inclusion–exclusion:

// P[r][c] = sum of the rectangle from (0,0) to (r-1, c-1)
function build2D(mat) {
  const R = mat.length, C = mat[0].length;
  const P = Array.from({length: R+1}, () => new Array(C+1).fill(0));
  for (let r = 0; r < R; r++)
    for (let c = 0; c < C; c++)
      P[r+1][c+1] = mat[r][c] + P[r][c+1] + P[r+1][c] - P[r][c];   // ← subtract the overlap
  return P;
}

const rectSum = (P, r1, c1, r2, c2) =>
  P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1];           // ← add it back

        c1      c2
   ┌────┬───────┬───┐
r1 │ A  │   B   │   │      target = TOTAL - (A+B) - (A+C) + A
   ├────┼───────┤   │              = P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1]
r2 │ C  │ TARGET│   │
   └────┴───────┴───┘      A is subtracted twice, so it is added back once

Part 5 — Difference Arrays (Prefix Sums in Reverse)

When you must apply many range updates and only read the result at the end, invert the technique: record deltas at the boundaries, then take a prefix sum once.

// naive: each update touches the whole range → O(updates × n)
for (const [l, r, v] of updates)
  for (let i = l; i <= r; i++) arr[i] += v;

// difference array: each update is O(1), one final pass
function applyUpdates(n, updates) {
  const diff = new Array(n + 1).fill(0);
  for (const [l, r, v] of updates) {
    diff[l] += v;
    diff[r + 1] -= v;                      // ← cancel just past the end
  }
  const out = new Array(n);
  let running = 0;
  for (let i = 0; i < n; i++) { running += diff[i]; out[i] = running; }
  return out;
}
// O(updates + n)

n = 5, updates = [[1,3,2],[2,4,3]]

diff:  [0, 2, 3, 0, -2, -3]        (+2 at 1, -2 at 4;  +3 at 2, -3 at 5)
prefix: 0, 2, 5, 5,  3
result: [0, 2, 5, 5, 3]   ✓

The n + 1 length matters — an update ending at the last index writes its cancellation at diff[n], which must exist.

This is the standard approach for interval-counting problems such as Car Pooling and Corporate Flight Bookings, where the naive per-range loop is O(updates × n) and times out.

Part 6 — Choosing Between the Techniques

Problem shapeTechniqueWhy
Contiguous, all positive, longest/shortestSliding windowO(1) space, monotonicity holds
Contiguous, negatives allowedPrefix sum + hash mapNo monotonicity needed
Count subarrays with an exact sumPrefix sum + hash mapCounting, not boundary-finding
Many range-sum queries, static dataPrefix arrayO(1) per query
Queries interleaved with updatesFenwick / segment treePrefix rebuild is O(n)
Many range updates, read at the endDifference arrayO(1) per update
Range min/maxSparse table, segment treeMin has no inverse

The deciding question between window and prefix sum is whether the values are all positive and whether you need a boundary or a count. Positive plus "longest/shortest" means window (and O(1) space); negatives or "how many" means prefix sum.

❌ Building a prefix array when a running variable would do. Many problems — counting subarrays with sum k, longest balanced subarray, subarrays divisible by k — never index into the prefix array at all; they only ever compare the current running total against previously seen ones. Allocating an n-element array for that is O(n) space spent on data you immediately throw away, and it makes the code longer than the single accumulator version.

✅ Materialise the array only when you need random access to arbitrary ranges. If the problem answers repeated range queries — "sum between i and j", 2-D rectangle sums — build it. If it scans once and asks about ranges ending at the current position, keep a single prefix variable and a hash map. The hash map is still O(n), but the code is shorter and the intent is clearer.

Interview Questions

Beginner: Build a prefix sum array and answer range-sum queries in O(1).

Store running totals in an array of length n+1, with prefix[0] = 0 representing the empty prefix.

class RangeSum {
  constructor(nums) {
    this.p = new Array(nums.length + 1).fill(0);
    for (let i = 0; i < nums.length; i++) this.p[i + 1] = this.p[i] + nums[i];
  }
  query(i, j) { return this.p[j + 1] - this.p[i]; }    // inclusive [i..j]
}
// build O(n), each query O(1), space O(n)

nums   = [ 2,  4,  1,  5,  3 ]
p      = [0, 2,  6,  7, 12, 15]

query(1,3) = p[4] - p[1] = 12 - 2 = 10   (4+1+5)  ✓
query(0,4) = p[5] - p[0] = 15 - 0 = 15   ✓
query(2,2) = p[3] - p[2] =  7 - 6 = 1    ✓ single element

Why the n+1 convention matters: with an n-length array you need a branch for i === 0 in every query, and that branch is where the off-by-one bugs live. The extra slot costs one integer and removes the special case entirely.

The trade-off to state: queries become O(1), but any element update invalidates every later prefix, so updates are O(n). That is fine for static data and wrong for mutable data — if the problem interleaves updates and queries, the answer is a Fenwick tree with O(log n) for both.

Edge cases: the empty array (prefix is just [0]), and a query where i === j, which should return the single element.

Beginner: Count subarrays summing to k. Why is the {0: 1} seed necessary?

Rearrange the range identity so that finding a subarray becomes a hash lookup.

sum(i..j) == k
⟺  prefix[j+1] - prefix[i] == k
⟺  prefix[i] == prefix[j+1] - k

function subarraySum(nums, k) {
  const seen = new Map([[0, 1]]);
  let prefix = 0, count = 0;
  for (const x of nums) {
    prefix += x;
    count += seen.get(prefix - k) ?? 0;
    seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
  }
  return count;
}
// O(n) time, O(n) space

The seed represents the empty prefix. A subarray starting at index 0 spans [0..j], so the prefix to subtract is the one before index 0 — which is 0, and it must already be in the map for the lookup to succeed:

nums = [3], k = 3
  prefix = 3, look for 3 - 3 = 0

  without the seed: 0 is absent → count 0   ✗
  with the seed:    0 found once → count 1  ✓

Storing counts rather than presence is the second requirement, because the same prefix value can recur and each occurrence begins a distinct valid subarray:

nums = [1,-1,1,-1], k = 0
prefixes: 0(seed), 1, 0, 1, 0

prefix 0 appears 3 times, prefix 1 appears twice
→ C(3,2) + C(2,2) = 3 + 1 = 4 subarrays  ✓

with a Set: each prefix counted once → 2  ✗

Why not a sliding window? Because the values may be negative, so extending the window can decrease the sum — the monotonicity that window shrinking depends on does not hold. The prefix identity holds for any values, which is exactly why this is the fallback.

Mid: Find the longest subarray with equal numbers of 0s and 1s.

Map 0 to −1 and 1 to +1. A subarray is balanced exactly when its values sum to zero — which, in prefix terms, means the running balance is the same at both ends.

function findMaxLength(nums) {
  const firstSeen = new Map([[0, -1]]);        // balance 0 before the array starts
  let balance = 0, best = 0;
  for (let i = 0; i < nums.length; i++) {
    balance += nums[i] === 1 ? 1 : -1;
    if (firstSeen.has(balance)) {
      best = Math.max(best, i - firstSeen.get(balance));
    } else {
      firstSeen.set(balance, i);               // EARLIEST index only
    }
  }
  return best;
}
// O(n) time, O(n) space

nums    = [0,  1,  0,  0,  1,  1,  0]
balance = [-1, 0, -1, -2, -1,  0, -1]

balance 0 at index 1 and index 5  → subarray (1..5], length 4  ✓
balance -1 at index 0 and index 6 → length 6  ✓ ← the answer

Two details decide correctness. First, the seed [[0, -1]]: index −1 is the position "before the array", so a balanced prefix starting at index 0 gets the right length (i − (−1) = i + 1).

Second, never overwrite an existing entry. For "longest", the earlier the first occurrence, the longer the resulting subarray:

if overwritten with the latest index:
  balance -1 recorded at index 6 instead of 0
  → the length-6 subarray is never found  ✗

This contrasts directly with the counting version, which stores how many times each prefix occurred rather than where it first occurred. The map's contents follow from the question: "how many" needs counts, "how long" needs earliest indices.

The generalisation: any "equal numbers of A and B" becomes +1/−1, and any "contiguous range where property P balances out" becomes a prefix-equality search.

Mid: Count subarrays whose sum is divisible by k.

Two prefixes with the same remainder modulo k enclose a range whose sum is divisible by k — because their difference is a multiple of k.

function subarraysDivByK(nums, k) {
  const count = new Map([[0, 1]]);
  let prefix = 0, total = 0;
  for (const x of nums) {
    prefix += x;
    const r = ((prefix % k) + k) % k;          // normalise into [0, k)
    total += count.get(r) ?? 0;
    count.set(r, (count.get(r) ?? 0) + 1);
  }
  return total;
}
// O(n) time, O(k) space — at most k distinct remainders

The normalisation is essential in JavaScript, Java and C++, where % takes the sign of the dividend:

-1 % 5   →  -1      (not 4)
((-1 % 5) + 5) % 5  →  4   ✓

Without it, a prefix of −1 and a prefix of 4 have remainders -1 and 4 — they never match, even though their difference is 5 and the enclosed range is divisible by k.

nums = [4,5,0,-2,-3,1], k = 5

prefixes:    4, 9, 9, 7, 4, 5
remainders:  4, 4, 4, 2, 4, 0
counts:      {0:1(seed)} → 4 appears 4 times, 0 appears twice

pairs: C(4,2) + C(2,2) = 6 + 1 = 7  ✓

Space is O(k), not O(n), because there are only k possible remainders — worth mentioning, since it is better than the general prefix-sum bound and shows you understand what the map is holding.

Python is the exception: its % already returns a non-negative result for a positive modulus, so the normalisation is unnecessary there. Knowing which languages need it is the kind of detail that separates a careful answer from a memorised one.

Senior: Design a structure for range-sum queries on data that also changes.

A prefix array is the wrong tool the moment updates appear: queries are O(1) but a single element change invalidates every later prefix, making updates O(n). A Fenwick tree (binary indexed tree) balances both at O(log n).

StructureQueryUpdateBuildWhen
Prefix arrayO(1)O(n)O(n)Static data
Fenwick treeO(log n)O(log n)O(n)Point update, range sum
Segment treeO(log n)O(log n)O(n)Also min/max/gcd; range updates with lazy propagation
Difference arrayO(n) final passO(1)O(n)Many range updates, read once at the end
class Fenwick {
  constructor(n) { this.n = n; this.t = new Array(n + 1).fill(0); }

  update(i, delta) {                            // add delta at index i (0-based)
    for (let x = i + 1; x <= this.n; x += x & -x) this.t[x] += delta;
  }

  prefix(i) {                                   // sum of [0..i]
    let s = 0;
    for (let x = i + 1; x > 0; x -= x & -x) s += this.t[x];
    return s;
  }

  range(i, j) { return this.prefix(j) - (i > 0 ? this.prefix(i - 1) : 0); }
}

x & -x isolates the lowest set bit, which is how the tree walks its implicit structure — each node covers a range whose length is that bit value, so both loops take O(log n) steps.

How I would choose in an interview:

queries only, no updates          → prefix array (simplest, O(1) queries)
point updates + range sums        → Fenwick (shortest code of the log-time options)
range updates + range queries     → segment tree with lazy propagation
range updates, ONE read at the end → difference array (O(1) per update)
min/max instead of sum            → segment tree or sparse table (no inverse for min)

The last row is the conceptual point: prefix sums and Fenwick trees both rely on subtraction to isolate a range. Minimum has no inverse — knowing min(0..j) and min(0..i) tells you nothing about min(i..j) — so those structures do not apply and a segment tree, which stores per-range answers explicitly, is required.

I would start with the prefix array and only escalate when the problem states that updates occur, since the simplest structure that satisfies the requirements is the right answer.

Senior: You must apply 10⁵ range updates to an array of 10⁵ elements, then read it once. How?

A difference array — prefix sums run backwards. Each update becomes two O(1) writes, and one final pass reconstructs the array.

naive: 10⁵ updates × up to 10⁵ elements = 10¹⁰ operations   ✗ far too slow
diff:  10⁵ updates × O(1)  +  one O(n) pass = 2×10⁵         ✓

function applyUpdates(n, updates) {
  const diff = new Array(n + 1).fill(0);       // n+1: the cancel may land at index n
  for (const [l, r, v] of updates) {
    diff[l] += v;
    diff[r + 1] -= v;
  }
  const out = new Array(n);
  let running = 0;
  for (let i = 0; i < n; i++) { running += diff[i]; out[i] = running; }
  return out;
}
// O(updates + n)

Why it works: adding v at l makes every prefix from l onward include it; subtracting v at r+1 cancels it from r+1 onward. The running sum therefore contains v exactly on [l, r].

n = 5, updates = [[1,3,2], [2,4,3]]

diff:   [0, +2, +3, 0, -2, -3]
             ↑   ↑      ↑   ↑
            l=1 l=2   r+1=4 r+1=5

running: 0, 2, 5, 5, 3
result:  [0, 2, 5, 5, 3]   ✓

The n + 1 allocation is not optional — an update ending at the last index writes its cancellation at diff[n], and a length-n array would throw or silently corrupt neighbouring data depending on the language.

Where this pattern appears: Corporate Flight Bookings, Car Pooling, "range addition", and most interval-counting problems. The recognition cue is "many range updates, and the answer is only needed after all of them" — if reads are interleaved with writes, a difference array does not work and a segment tree with lazy propagation does.

The 2-D version extends the same idea with four corner writes per rectangle update, followed by a 2-D prefix pass — useful for problems like counting overlapping rectangles on a grid.

// (b) same, with a Set
function countB(nums, k) {
  const seen = new Set([0]);
  let prefix = 0, count = 0;
  for (const x of nums) {
    prefix += x;
    if (seen.has(prefix - k)) count++;
    seen.add(prefix);
  }
  return count;
}

// (c) longest subarray with equal 0s and 1s
function longestC(nums) {
  const seen = new Map([[0, -1]]);
  let bal = 0, best = 0;
  for (let i = 0; i < nums.length; i++) {
    bal += nums[i] === 1 ? 1 : -1;
    if (seen.has(bal)) best = Math.max(best, i - seen.get(bal));
    seen.set(bal, i);
  }
  return best;
}

// (d) subarrays divisible by k
function divD(nums, k) {
  const c = new Map([[0,1]]);
  let p = 0, total = 0;
  for (const x of nums) {
    p += x;
    const r = p % k;
    total += c.get(r) ?? 0;
    c.set(r, (c.get(r) ?? 0) + 1);
  }
  return total;
}

// (e) difference array
function applyE(n, updates) {
  const diff = new Array(n).fill(0);
  for (const [l, r, v] of updates) { diff[l] += v; diff[r+1] -= v; }
  const out = []; let run = 0;
  for (let i = 0; i < n; i++) { run += diff[i]; out.push(run); }
  return out;
}

function countSubarrays(nums, k) {

  let p = 0, count = 0;
  for (const x of nums) {
    p += x;
    count += seen.get(p - k) ?? 0;
    seen.set(p, (seen.get(p) ?? 0) + 1);
  }
  return count;
}

// (b) LONGEST subarray summing to k → map stores EARLIEST INDEX
function longestSubarray(nums, k) {
  const first = new Map([[0, -1]]);
  let p = 0, best = 0;
  for (let i = 0; i < nums.length; i++) {
    p += nums[i];
    if (first.has(p - k)) best = Math.max(best, i - first.get(p - k));
    if (!first.has(p)) first.set(p, i);            // earliest only
  }
  return best;
}

// (c) longest with equal 0s and 1s → +1/-1 mapping
function findMaxLength(nums) {
  const first = new Map([[0, -1]]);
  let bal = 0, best = 0;
  for (let i = 0; i < nums.length; i++) {
    bal += nums[i] === 1 ? 1 : -1;
    if (first.has(bal)) best = Math.max(best, i - first.get(bal));
    else first.set(bal, i);
  }
  return best;
}

// (d) count subarrays divisible by k → map stores COUNTS of REMAINDERS
function divByK(nums, k) {
  const c = new Map([[0, 1]]);

  for (const x of nums) {

    const r = ((p % k) + k) % k;
    total += c.get(r) ?? 0;
    c.set(r, (c.get(r) ?? 0) + 1);
  }
  return total;
}

5 (hard): Build 2-D prefix sums and solve a rectangle-sum problem.
Solution 
function build2D(mat) {
  const R = mat.length, C = mat[0].length;
  const P = Array.from({length: R+1}, () => new Array(C+1).fill(0));
  for (let r = 0; r < R; r++)
    for (let c = 0; c < C; c++)
      P[r+1][c+1] = mat[r][c] + P[r][c+1] + P[r+1][c] - P[r][c];
  return P;
}

const rectSum = (P, r1, c1, r2, c2) =>
  P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1];

  return s;
}

Now the harder application — count submatrices summing to target (LC 1074), which combines 2-D prefix sums with the 1-D hash-map technique:

function numSubmatrixSumTarget(matrix, target) {
  const R = matrix.length, C = matrix[0].length;

  // row-wise prefix sums: rp[r][c] = sum of row r up to column c-1
  const rp = Array.from({length:R}, () => new Array(C+1).fill(0));
  for (let r = 0; r < R; r++)
    for (let c = 0; c < C; c++) rp[r][c+1] = rp[r][c] + matrix[r][c];

  let count = 0;
  for (let c1 = 0; c1 < C; c1++) {              // fix the LEFT column
    for (let c2 = c1; c2 < C; c2++) {           // fix the RIGHT column
      // now each row collapses to a single number → 1-D subarray-sum problem
      const seen = new Map([[0, 1]]);
      let prefix = 0;
      for (let r = 0; r < R; r++) {
        prefix += rp[r][c2+1] - rp[r][c1];
        count += seen.get(prefix - target) ?? 0;
        seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
      }
    }
  }
  return count;
}
// O(R · C²) time

console.log(numSubmatrixSumTarget([[0,1,0],[1,1,1],[0,1,0]], 0));   // 4
console.log(numSubmatrixSumTarget([[1,-1],[-1,1]], 0));             // 5
console.log(numSubmatrixSumTarget([[904]], 0));                     // 0

The reduction is the insight worth stating: fixing a pair of columns collapses each row to a single value, turning a 2-D problem into the 1-D "count subarrays summing to target" problem from Part 2 — which we already know how to solve in O(R) with a hash map.

Complexity: C²/2 column pairs × O(R) per pair = O(R·C²). For a 100×100 matrix that is 5×10⁵ — comfortable, whereas enumerating all submatrices would be O(R²C²) = 10⁸.

6 (hard): Compare prefix sum, Fenwick tree, and difference array on the same workload.
Solution 
class Fenwick {
  constructor(n) { this.n = n; this.t = new Array(n + 1).fill(0); }
  update(i, d) { for (let x = i + 1; x <= this.n; x += x & -x) this.t[x] += d; }
  prefix(i) { let s = 0; for (let x = i + 1; x > 0; x -= x & -x) s += this.t[x]; return s; }
  range(i, j) { return this.prefix(j) - (i > 0 ? this.prefix(i - 1) : 0); }
}

class PrefixArray {
  constructor(nums) { this.nums = [...nums]; this.rebuild(); }
  rebuild() {
    this.p = new Array(this.nums.length + 1).fill(0);
    for (let i = 0; i < this.nums.length; i++) this.p[i+1] = this.p[i] + this.nums[i];
  }
  update(i, d) { this.nums[i] += d; this.rebuild(); }      // ← O(n)
  range(i, j) { return this.p[j+1] - this.p[i]; }
}

🎯 Key Takeaways

  • The identity sum(i..j) = prefix[j+1] − prefix[i] turns any range sum into a subtraction.
  • Use a length-(n+1) prefix array with prefix[0] = 0 — it removes the special case for ranges starting at index 0, where the off-by-one bugs live.
  • Prefix sums work where sliding window fails, because the identity needs no monotonicity and holds for negative values.
  • Rearranging to prefix[i] == prefix[j+1] − k converts a search into a hash lookup — that is the whole prefix-plus-map technique.
  • Seed the map with {0: 1} (counting) or {0: -1} (longest), or every subarray starting at index 0 is missed.
  • Store counts for "how many" and the earliest index for "how long" — swapping them is the classic error.
  • Never overwrite an existing entry when finding the longest subarray; the earliest occurrence gives the longest range.
  • Map 0 → −1 and 1 → +1 to turn "equal counts" into "the same running balance seen twice".
  • Two prefixes with the same remainder mod k enclose a range divisible by k — normalise with ((x % k) + k) % k in JS, Java and C++.
  • XOR is its own inverse, so prefix XOR works with P[j+1] ^ P[i].
  • Prefix products break on zeros; min and max have no inverse at all and need a sparse table or segment tree.
  • 2-D prefix sums use inclusion–exclusion: subtract the two overlapping strips, then add back the doubly-subtracted corner.
  • Fixing a pair of columns collapses a 2-D submatrix-sum problem into the 1-D subarray-sum problem.
  • Difference arrays invert the technique: record deltas at range boundaries for O(1) updates, then one prefix pass at the end.
  • Allocate n + 1 for a difference array — an update ending at the last index cancels at diff[n].
  • Prefix arrays are for static data; if updates interleave with queries, the rebuild is O(n) and a Fenwick tree is the right structure.
  • Keep a single running variable instead of materialising the array unless you need random access to arbitrary ranges.
  • "Better complexity" is workload-dependent: a Fenwick tree is 20× slower than a prefix array for pure queries and vastly faster when updates are frequent.
