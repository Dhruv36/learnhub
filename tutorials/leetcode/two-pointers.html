Two Pointers Core Pattern

What you'll master: the three distinct two-pointer shapes — converging, same-direction, and across two sequences — and which problems each one solves; the correctness argument that makes converging pointers valid, which is what interviewers actually probe; how to handle duplicates in 3Sum without producing repeated triplets; the non-obvious proof behind Container With Most Water and Trapping Rain Water, where the pointer movement rule is the whole insight; and when two pointers beats hashing and when it cannot be used at all. Prerequisites: Arrays & Strings, Hashing.

Part 1 — Three Shapes, One Idea

Two indices walk through the data, and every step discards possibilities that can no longer be answers. That is the whole pattern; the three shapes differ only in how the pointers move.

CONVERGING                    SAME DIRECTION                 TWO SEQUENCES
──────────                    ──────────────                 ─────────────
l →         ← r               slow → fast →                  i →   (array A)
[ . . . . . . . ]             [ . . . . . . . ]              j →   (array B)
shrink toward each other      one leads, one follows         advance the smaller

sorted pair sums              in-place filtering             merging sorted data
palindromes                   window boundaries              intersection of sets
container/area                dedup, partition               subsequence matching

The converging shape is what most people mean by "two pointers", and it is the one with a real correctness argument to make:

let l = 0, r = arr.length - 1;
while (l < r) {
  const current = evaluate(arr[l], arr[r]);
  if (current === target) return answer;
  if (current < target) l++;      // need MORE → give up the smallest
  else r--;                       // need LESS → give up the largest
}
🔑 Why converging pointers are correct, stated precisely: in a sorted array, if arr[l] + arr[r] < target, then arr[l] paired with anything remaining is also too small — because arr[r] is the largest value left. So no pair involving arr[l] can work, and discarding it loses nothing. That sentence is the answer to "how do you know you don't miss a pair?", and it is asked almost every time this pattern appears.

Sortedness is the precondition, and it is what the problem statement is telling you when it says "sorted". Without it, moving a pointer discards nothing reliably — which is why unsorted Two Sum needs a hash map instead.

Part 2 — Converging: Pair Sums

function twoSumSorted(nums, target) {          // LC 167
  let l = 0, r = nums.length - 1;
  while (l < r) {
    const sum = nums[l] + nums[r];
    if (sum === target) return [l + 1, r + 1];  // 1-indexed
    if (sum < target) l++;
    else r--;
  }
  return [];
}
// O(n) time, O(1) space

nums = [2, 7, 11, 15], target = 18

l=0 r=3:  2 + 15 = 17 < 18  → l++     (2 can never reach 18, even with the largest)
l=1 r=3:  7 + 15 = 22 > 18  → r--     (15 is too big for anything remaining)
l=1 r=2:  7 + 11 = 18       ✓

Compare the two approaches to Two Sum, because choosing correctly is the point:

Hash mapTwo pointers
Input requirementAny orderMust be sorted
TimeO(n)O(n), or O(n log n) if you must sort
SpaceO(n)O(1)
Preserves original indicesYesNo, if you sort

Sorting to enable two pointers is usually wrong when indices are required — sorting destroys them, and recovering them costs the space you were trying to save.

Part 3 — 3Sum and the Duplicate Problem

3Sum is Two Sum with an outer loop, and the difficulty is not the algorithm — it is returning each triplet exactly once.

function threeSum(nums) {                      // LC 15
  nums.sort((a, b) => a - b);
  const res = [];

  for (let i = 0; i < nums.length - 2; i++) {
    if (nums[i] > 0) break;                          // sorted: no zero sum possible
    if (i > 0 && nums[i] === nums[i - 1]) continue;  // skip duplicate ANCHORS

    let l = i + 1, r = nums.length - 1;
    while (l < r) {
      const sum = nums[i] + nums[l] + nums[r];
      if (sum === 0) {
        res.push([nums[i], nums[l], nums[r]]);
        while (l < r && nums[l] === nums[l + 1]) l++;   // skip duplicate LEFTS
        while (l < r && nums[r] === nums[r - 1]) r--;   // skip duplicate RIGHTS
        l++; r--;
      } else if (sum < 0) l++;
      else r--;
    }
  }
  return res;
}
// O(n²) time, O(1) extra space (excluding the output and the sort)

Three duplicate skips, each for a different reason:

SkipPreventsWhy i > 0 / l < r guard matters
Anchor: nums[i] === nums[i-1]The same first element producing the same tripletsi > 0 avoids reading index −1
Left: after a match[-1,-1,2] found twicel < r prevents running past the right pointer
Right: after a matchSame, from the other sideSame guard

The anchor skip must compare backwards, not forwards. Writing nums[i] === nums[i+1] skips the first occurrence of a repeated value, which loses triplets like [-1,-1,2] that legitimately use the value twice:

nums = [-1,-1,0,1,2]

backwards (correct):  i=0 uses -1 → finds [-1,-1,2] and [-1,0,1]
                      i=1 skipped (same as i=0's value)   ✓

forwards (wrong):     i=0 skipped (nums[0] === nums[1])
                      i=1 uses -1 → finds [-1,0,1] but the pair -1,-1 is gone  ✗

if (nums[i] > 0) break is a genuine optimisation, not just a shortcut: once the smallest of three sorted values is positive, their sum cannot be zero, and everything after is also positive.

Part 4 — The Movement Rule Is the Insight

In two problems, deciding which pointer to move is the entire difficulty, and the justification is what an interviewer is listening for.

Container With Most Water (LC 11): area is min(h[l], h[r]) × (r − l). Always move the shorter side.

function maxArea(height) {
  let l = 0, r = height.length - 1, best = 0;
  while (l < r) {
    best = Math.max(best, Math.min(height[l], height[r]) * (r - l));
    if (height[l] < height[r]) l++;      // move the SHORTER side
    else r--;
  }
  return best;
}

Why moving the shorter side loses nothing: the width shrinks with every step, no matter which pointer moves. Keeping the shorter bar and moving the taller one gives a container whose height is still capped by that same short bar and whose width is smaller — strictly worse. So every pair involving the short bar is already dominated by the pair we just measured, and discarding it is safe.

Trapping Rain Water (LC 42): water above bar i is min(maxLeft, maxRight) − h[i], and the pointers let you know the binding side without computing both maxima.

function trap(height) {
  let l = 0, r = height.length - 1;
  let leftMax = 0, rightMax = 0, water = 0;
  while (l < r) {
    if (height[l] < height[r]) {         // ← the left side is the binding constraint
      leftMax = Math.max(leftMax, height[l]);
      water += leftMax - height[l];
      l++;
    } else {
      rightMax = Math.max(rightMax, height[r]);
      water += rightMax - height[r];
      r--;
    }
  }
  return water;
}

The argument: when height[l] < height[r], there is some bar at position r of height at least height[r] > height[l], so the right maximum is guaranteed to exceed the left maximum. Therefore min(leftMax, rightMax) = leftMax, and the water at position l can be computed from leftMax alone — without ever knowing the true right maximum.

This is the O(1)-space version of the prefix/suffix approach in Arrays & Strings; both are O(n) time.

Part 5 — Two Sequences

When the input is two sorted sequences, advance whichever pointer is behind.

function intersection(a, b) {              // both sorted
  const res = [];
  let i = 0, j = 0;
  while (i < a.length && j < b.length) {
    if (a[i] === b[j]) { res.push(a[i]); i++; j++; }
    else if (a[i] < b[j]) i++;             // a is behind
    else j++;                               // b is behind
  }
  return res;
}
// O(n + m) time, O(1) extra space

Merging in place from the back is the variant worth memorising, because writing forward would overwrite unread data:

function merge(nums1, m, nums2, n) {       // LC 88 — nums1 has space for both
  let i = m - 1, j = n - 1, write = m + n - 1;
  while (j >= 0) {                          // only nums2 must be exhausted
    if (i >= 0 && nums1[i] > nums2[j]) nums1[write--] = nums1[i--];
    else nums1[write--] = nums2[j--];
  }
}

The loop condition is j >= 0, not both: if nums1 runs out first, the remaining nums2 values must still be copied; if nums2 runs out first, the remaining nums1 values are already in place.

Subsequence matching is the same shape with an asymmetry:

function isSubsequence(s, t) {             // is s a subsequence of t?
  let i = 0;
  for (const ch of t) if (i < s.length && ch === s[i]) i++;
  return i === s.length;
}
// O(|t|) — greedy matching is correct: taking the earliest match is never worse

The test to apply before using converging pointers: if I move this pointer, can I prove that every pair I am discarding is already impossible or already dominated? If yes, the pattern is valid. If you cannot state that argument, the pattern is probably wrong for the problem — and the interviewer will ask for exactly that argument.

❌ Sorting the input so two pointers becomes available, without checking what the sort destroys. The instinct is right — sorted input unlocks an O(1)-space linear scan — but Two Sum asks for indices, and sorting scrambles them. The candidate produces a correct-looking O(n log n) solution that returns the wrong positions, or bolts on an index-tracking array that costs the O(n) space the sort was meant to avoid.

✅ Ask what the problem returns before deciding to sort. Values or a count: sorting is free, and two pointers gives O(1) space. Original indices: use a hash map instead, accept O(n) space, and say why — "sorting would give O(1) space but destroys the indices the problem asks for, so I'll trade space for that". Naming the trade-off out loud is worth more than either solution alone.

Interview Questions

Beginner: Check whether a string is a palindrome, ignoring non-alphanumeric characters and case.

Converging pointers from both ends, skipping characters that do not count.

function isPalindrome(s) {                     // LC 125
  const ok = c => /[a-z0-9]/i.test(c);
  let l = 0, r = s.length - 1;
  while (l < r) {
    while (l < r && !ok(s[l])) l++;            // skip junk from the left
    while (l < r && !ok(s[r])) r--;            // skip junk from the right
    if (s[l].toLowerCase() !== s[r].toLowerCase()) return false;
    l++; r--;
  }
  return true;
}
// O(n) time, O(1) space

The l < r guard inside the skip loops is essential. Without it, a string of only punctuation runs the pointers past each other and indexes out of range:

s = ",."     l=0 r=1
  skip left:  ',' not ok → l=1;  now l === r, guard stops it  ✓
  without the guard: l keeps advancing past r → s[l] is undefined → crash

Why not preprocess with a regex and compare to the reverse?

const clean = s.toLowerCase().replace(/[^a-z0-9]/g, "");
return clean === [...clean].reverse().join("");

It is correct and shorter, but it allocates two extra strings — O(n) space where the pointer version is O(1). The interviewer is asking this problem specifically to see the in-place version, and the follow-up is always "can you do it without extra space?"

Edge cases worth stating: the empty string is a palindrome, a single character is a palindrome, and a string of only punctuation is too — all handled because the loop simply never finds a mismatch.

Beginner: Why do converging pointers work on a sorted array, and how do you know no pair is missed?

Because each move discards only pairs that are provably impossible.

let l = 0, r = n - 1;
while (l < r) {
  const sum = arr[l] + arr[r];
  if (sum === target) return [l, r];
  if (sum < target) l++;
  else r--;
}

The argument, stated as an interviewer wants to hear it:

Suppose arr[l] + arr[r] < target.

arr[r] is the LARGEST value in the remaining range [l..r].
So for any j in that range, arr[l] + arr[j] ≤ arr[l] + arr[r] < target.

⟹ NO pair involving arr[l] can reach the target.
⟹ discarding arr[l] (by l++) loses no possible answer.

The symmetric argument applies when the sum exceeds the target: arr[l] is the smallest remaining value, so no pair involving arr[r] can be small enough.

Sortedness is what makes "largest remaining" and "smallest remaining" true, and it is precisely what the pattern depends on. On unsorted data, arr[r] is just some value — moving a pointer discards pairs that might have been answers.

The loop is l < r, not l <= r, because a pair requires two distinct elements. With <=, an element at l === r pairs with itself and [3] with target 6 wrongly returns a match.

Complexity is O(n): each iteration moves exactly one pointer, and they start n apart, so there are at most n iterations. O(1) space.

Mid: Solve 3Sum. How do you avoid duplicate triplets?

Sort, fix each element as an anchor, then run converging pointers on the remainder — with three separate duplicate skips.

function threeSum(nums) {
  nums.sort((a, b) => a - b);
  const res = [];
  for (let i = 0; i < nums.length - 2; i++) {
    if (nums[i] > 0) break;
    if (i > 0 && nums[i] === nums[i - 1]) continue;      // 1. duplicate anchors

    let l = i + 1, r = nums.length - 1;
    while (l < r) {
      const sum = nums[i] + nums[l] + nums[r];
      if (sum === 0) {
        res.push([nums[i], nums[l], nums[r]]);
        while (l < r && nums[l] === nums[l + 1]) l++;    // 2. duplicate lefts
        while (l < r && nums[r] === nums[r - 1]) r--;    // 3. duplicate rights
        l++; r--;
      } else if (sum < 0) l++;
      else r--;
    }
  }
  return res;
}
// O(n²) time — O(n log n) sort + n iterations of an O(n) scan

The anchor skip must look backwards. Comparing to nums[i+1] instead loses legitimate triplets that use a repeated value twice:

nums = [-1,-1,0,1,2]

backwards ✓:  i=0 (-1) → finds [-1,-1,2] and [-1,0,1]
              i=1 skipped, since nums[1] === nums[0]

forwards  ✗:  i=0 skipped, since nums[0] === nums[1]
              i=1 (-1) → finds [-1,0,1] only — [-1,-1,2] is lost

Why sorting first is worth the O(n log n): it enables the two-pointer inner scan (turning the natural O(n³) into O(n²)) and it makes duplicates adjacent, which is what allows the skips to work at all. A hash-based approach would need a set of canonical triplets to deduplicate, costing extra space.

The nums[i] > 0 break is a real pruning step: with a sorted array, if the smallest of the three is positive, the sum is positive, and so is every anchor after it.

Edge cases: fewer than three elements returns empty; all zeros returns exactly one [0,0,0]; no solution returns an empty array.

Mid: In Container With Most Water, why do you move the shorter side?

Because every pair involving the shorter bar is already dominated by the pair just measured, so discarding it loses nothing.

area(l, r) = min(height[l], height[r]) × (r - l)

The argument: suppose height[l] < height[r] and we keep l while moving r inward to some r'. Then:

width shrinks:   (r' - l) < (r - l)                    always
height cannot grow: min(height[l], height[r']) ≤ height[l]   because height[l] is already the smaller

⟹ area(l, r') ≤ height[l] × (r' - l) < height[l] × (r - l) = area(l, r)
⟹ every container using l is worse than the one we just measured
⟹ discarding l is safe

The reverse move is what loses answers. Moving the taller side keeps the short bar as the cap while shrinking the width — guaranteed worse — and gives up the chance of finding a taller partner for the tall bar.

function maxArea(height) {
  let l = 0, r = height.length - 1, best = 0;
  while (l < r) {
    best = Math.max(best, Math.min(height[l], height[r]) * (r - l));
    if (height[l] < height[r]) l++; else r--;
  }
  return best;
}
// O(n) time, O(1) space

When the heights are equal, either move works — both bars are simultaneously the cap, so both are dominated by the current measurement.

The contrast with Trapping Rain Water is worth drawing, since they look similar and are not: Container measures the water between exactly two chosen bars, so the answer is a single maximum. Trapping measures water above every bar, bounded by the running maxima on both sides, so the answer is a sum. Same pointer mechanics, different quantity.

Senior: Explain the two-pointer solution to Trapping Rain Water and why it needs no second pass.

Water above bar i is min(maxLeft[i], maxRight[i]) − height[i]. The prefix/suffix solution computes both arrays in two passes and O(n) space; the two-pointer version gets O(1) space by recognising that you only ever need the smaller of the two maxima — and you can always know which side that is.

function trap(height) {
  let l = 0, r = height.length - 1;
  let leftMax = 0, rightMax = 0, water = 0;
  while (l < r) {
    if (height[l] < height[r]) {
      leftMax = Math.max(leftMax, height[l]);
      water += leftMax - height[l];
      l++;
    } else {
      rightMax = Math.max(rightMax, height[r]);
      water += rightMax - height[r];
      r--;
    }
  }
  return water;
}

The key deduction: when height[l] < height[r], there exists a bar at position r with height greater than height[l]. Therefore the true right maximum for position l is at least height[r] > height[l] , and since leftMax ≥ height[l] is what we have accumulated:

rightMax(true, for position l) ≥ height[r] > height[l]

so min(leftMax, rightMax_true) = leftMax   whenever leftMax ≤ height[r]
⟹ water at l = leftMax - height[l], computable WITHOUT knowing rightMax_true

That is why no second pass is needed — the comparison height[l] < height[r] is a certificate that the left side is the binding constraint, so the running leftMax is sufficient.

ApproachTimeSpace
Brute force (scan both sides per bar)O(n²)O(1)
Prefix/suffix maxima arraysO(n)O(n)
Two pointersO(n)O(1)
Monotonic stackO(n)O(n)

The monotonic stack solution is worth mentioning because it computes the water in horizontal layers rather than vertical columns — same answer, different decomposition, and it generalises to problems where you need the bounding bars themselves rather than just the total.

How I would present this in an interview: brute force first with its complexity, then the prefix/suffix insight, then eliminate the arrays. Arriving directly at the two-pointer version without that progression usually reads as memorisation, and the interviewer will probe the correctness argument to find out.

Senior: How do you extend the pattern to k-Sum, and where does it stop being the right tool?

Recursively: sort once, then peel off one fixed element per level until two remain, where converging pointers take over.

function kSum(nums, target, k, start = 0) {
  const res = [];
  if (start === nums.length) return res;

  if (k === 2) {                                  // base case: two pointers
    let l = start, r = nums.length - 1;
    while (l < r) {
      const sum = nums[l] + nums[r];
      if (sum === target) {
        res.push([nums[l], nums[r]]);
        while (l < r && nums[l] === nums[l+1]) l++;
        while (l < r && nums[r] === nums[r-1]) r--;
        l++; r--;
      } else if (sum < target) l++;
      else r--;
    }
    return res;
  }

  for (let i = start; i < nums.length - k + 1; i++) {
    if (i > start && nums[i] === nums[i-1]) continue;      // duplicate anchors
    for (const sub of kSum(nums, target - nums[i], k - 1, i + 1)) {
      res.push([nums[i], ...sub]);
    }
  }
  return res;
}
// O(n^(k-1)) time — 3Sum O(n²), 4Sum O(n³)

Pruning matters more as k grows, and these two checks cut enormous amounts of work:

if (nums[i] * k > target) break;                       // smallest possible sum too big
if (nums[nums.length-1] * k < target) continue;        // largest possible sum too small

Where it stops being right: the complexity is O(n^(k−1)), so by k = 5 or 6 on a nontrivial n it is hopeless. Two alternatives take over:

Problem shapeBetter approachComplexity
Four Sum II — four separate arrays, count onlyHash the pairwise sums of A+B, look up −(C+D)O(n²)
Large k, values boundedSubset-sum DPO(n·target)
Need only existence, not the tuplesMeet in the middleO(n^(k/2))

Four Sum II is the instructive case because it looks like 4Sum and is a completely different problem: the four arrays are separate (so no deduplication is needed) and only the count is required (so the tuples never have to be materialised). Hashing all n² sums of A+B and looking up the negation of each C+D sum gives O(n²) instead of O(n³) — a reminder that the right pattern depends on what is asked, not on what the problem superficially resembles.

1 (easy): Implement all three two-pointer shapes.
Solution 
// (a) converging — reverse an array in place
function reverse(a) {
  let l = 0, r = a.length - 1;
  while (l < r) { [a[l], a[r]] = [a[r], a[l]]; l++; r--; }
  return a;
}

// (b) same direction — squares of a sorted array, sorted
function sortedSquares(nums) {
  const n = nums.length, res = new Array(n);
  let l = 0, r = n - 1;
  for (let w = n - 1; w >= 0; w--) {          // fill from the BACK: largest first
    if (Math.abs(nums[l]) > Math.abs(nums[r])) res[w] = nums[l] * nums[l++];
    else res[w] = nums[r] * nums[r--];
  }
  return res;
}

// (c) two sequences — merge two sorted arrays
function mergeTwo(a, b) {
  const res = [];
  let i = 0, j = 0;
  while (i < a.length && j < b.length) res.push(a[i] <= b[j] ? a[i++] : b[j++]);
  while (i < a.length) res.push(a[i++]);
  while (j < b.length) res.push(b[j++]);
  return res;
}

console.log(reverse([1,2,3,4,5]));            // [5,4,3,2,1]
console.log(sortedSquares([-4,-1,0,3,10]));   // [0,1,9,16,100]
console.log(mergeTwo([1,3,5],[2,4,6]));       // [1,2,3,4,5,6]

(b) is the interesting one. The largest square comes from whichever end has the largest absolute value, since negatives square to positives. Filling the result from the back avoids a sort:

[-4,-1,0,3,10]
|−4| = 4, |10| = 10 → 10 wins → res[4] = 100, r--
|−4| = 4, |3| = 3   → −4 wins → res[3] = 16,  l++
|−1| = 1, |3| = 3   → 3 wins  → res[2] = 9,   r--
|−1| = 1, |0| = 0   → −1 wins → res[1] = 1,   l++
                    → res[0] = 0
→ [0,1,9,16,100]  ✓

The naive solution — square everything then sort — is O(n log n); this is O(n) because the input's sortedness means the extremes are at the ends.

(c)'s two trailing loops handle whichever array is exhausted first; forgetting them silently truncates the result.

3 (medium): Implement 3Sum and verify the deduplication exhaustively.
Solution 
function threeSum(nums) {
  nums.sort((a, b) => a - b);
  const res = [];
  for (let i = 0; i < nums.length - 2; i++) {
    if (nums[i] > 0) break;
    if (i > 0 && nums[i] === nums[i - 1]) continue;
    let l = i + 1, r = nums.length - 1;
    while (l < r) {
      const sum = nums[i] + nums[l] + nums[r];
      if (sum === 0) {
        res.push([nums[i], nums[l], nums[r]]);
        while (l < r && nums[l] === nums[l + 1]) l++;
        while (l < r && nums[r] === nums[r - 1]) r--;
        l++; r--;
      } else if (sum < 0) l++;
      else r--;
    }
  }
  return res;
}

5 (hard): Solve Trapping Rain Water four ways and compare.
Solution 
// (a) brute force — O(n²) time, O(1) space
function trapBrute(h) {
  let total = 0;
  for (let i = 0; i < h.length; i++) {
    let L = 0, R = 0;
    for (let j = 0; j <= i; j++) L = Math.max(L, h[j]);
    for (let j = i; j < h.length; j++) R = Math.max(R, h[j]);
    total += Math.min(L, R) - h[i];
  }
  return total;
}

// (b) prefix/suffix arrays — O(n) time, O(n) space
function trapArrays(h) {
  const n = h.length; if (!n) return 0;
  const L = new Array(n), R = new Array(n);
  L[0] = h[0];       for (let i=1; i<n; i++)  L[i] = Math.max(L[i-1], h[i]);
  R[n-1] = h[n-1];   for (let i=n-2; i>=0; i--) R[i] = Math.max(R[i+1], h[i]);
  let t = 0; for (let i=0;i<n;i++) t += Math.min(L[i],R[i]) - h[i];
  return t;
}

// (c) two pointers — O(n) time, O(1) space
function trapTwoPtr(h) {
  let l = 0, r = h.length-1, lm = 0, rm = 0, t = 0;
  while (l < r) {
    if (h[l] < h[r]) { lm = Math.max(lm, h[l]); t += lm - h[l]; l++; }
    else             { rm = Math.max(rm, h[r]); t += rm - h[r]; r--; }
  }
  return t;
}

// (d) monotonic stack — O(n) time, O(n) space — fills HORIZONTAL layers
function trapStack(h) {
  const st = [];                    // indices, heights decreasing
  let total = 0;
  for (let i = 0; i < h.length; i++) {
    while (st.length && h[i] > h[st[st.length-1]]) {
      const bottom = st.pop();
      if (!st.length) break;                       // no left wall
      const left = st[st.length-1];
      const width = i - left - 1;
      const depth = Math.min(h[left], h[i]) - h[bottom];
      total += width * depth;
    }
    st.push(i);
  }
  return total;
}

6 (hard): Build a generic k-Sum and find where the pattern breaks down.
Solution 
function kSum(nums, target, k) {
  nums.sort((a, b) => a - b);
  return helper(nums, target, k, 0);
}

function helper(nums, target, k, start) {
  const res = [];
  const n = nums.length;
  if (start >= n) return res;

  // pruning: if even the k smallest are too big, or the k largest too small, stop
  if (nums[start] * k > target) return res;
  if (nums[n-1] * k < target) return res;

  if (k === 2) {
    let l = start, r = n - 1;
    while (l < r) {
      const s = nums[l] + nums[r];
      if (s === target) {
        res.push([nums[l], nums[r]]);
        while (l < r && nums[l] === nums[l+1]) l++;
        while (l < r && nums[r] === nums[r-1]) r--;
        l++; r--;
      } else if (s < target) l++;
      else r--;
    }
    return res;
  }

  for (let i = start; i <= n - k; i++) {
    if (i > start && nums[i] === nums[i-1]) continue;
    for (const sub of helper(nums, target - nums[i], k - 1, i + 1)) {
      res.push([nums[i], ...sub]);
    }
  }
  return res;
}

The alternative for Four Sum II, which looks like 4Sum and is a different problem — four separate arrays, count only, no deduplication:

function fourSumCount(A, B, C, D) {
  const sums = new Map();
  for (const a of A) for (const b of B)
    sums.set(a+b, (sums.get(a+b) ?? 0) + 1);       // O(n²)
  let count = 0;
  for (const c of C) for (const d of D)
    count += sums.get(-(c+d)) ?? 0;                 // O(n²)
  return count;
}

The lesson is that the right pattern depends on what is asked, not on what the problem resembles. Four Sum II needs only a count from separate arrays, so hashing pairwise sums halves the exponent — and recognising that distinction is worth more than knowing the k-Sum recursion.

🎯 Key Takeaways

  • Three shapes: converging (sorted pair sums, palindromes, areas), same-direction (in-place filtering), and two-sequence (merging, intersection).
  • Converging pointers are correct because, in a sorted array, the discarded element cannot pair with anything remaining — that argument is what interviewers probe.
  • Sortedness is the precondition; without it, moving a pointer discards nothing reliably and you need hashing instead.
  • Use while (l < r), never <=, or an element pairs with itself.
  • Two pointers beats hashing on space (O(1) vs O(n)) but requires sorted input and destroys original indices if you sort.
  • Ask what the problem returns before sorting: values or counts make sorting free; indices make it wrong.
  • 3Sum needs three duplicate skips — anchors, lefts, and rights — each preventing a different repetition.
  • Skip duplicate anchors backwards (nums[i] === nums[i-1] with i > 0); comparing forwards loses valid triplets like [-1,-1,2].
  • Guard inner skip loops with l < r, or the pointers cross and read out of range.
  • In Container With Most Water, always move the shorter side: keeping it caps the height while width shrinks, so those pairs are already dominated.
  • In Trapping Rain Water, height[l] < height[r] certifies that the left side is binding, so leftMax alone determines the water — that is why one pass suffices.
  • Trapping Rain Water has four solutions; the interview-strong answer is the progression brute force → prefix/suffix → two pointers, each step justified.
  • Merge sorted arrays in place from the back, looping while j >= 0, or you overwrite unread data or drop a tail.
  • Squares of a sorted array is O(n) by filling from the back — the extremes hold the largest absolute values.
  • k-Sum generalises recursively to O(n^(k−1)), and becomes unusable by around k = 5 or 6.
  • Four Sum II is not 4Sum: separate arrays and a count-only answer make hashing pairwise sums O(n²) instead of O(n³).
  • Before using converging pointers, state the discard argument — if you cannot, the pattern is probably wrong for the problem.
