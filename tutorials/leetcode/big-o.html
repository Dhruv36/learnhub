Big-O & Complexity Analysis Foundations

What you'll master: what Big-O actually claims and the three things it deliberately ignores; how to read complexity off code including the loops that look linear and are not; the recurrence shortcuts that give you divide-and-conquer complexity in seconds; amortised analysis and why push() is O(1) despite occasionally copying the whole array; space complexity including recursion's hidden call stack; and the constraint-to-complexity inference that tells you which pattern to use before you write a line. Prerequisite: Overview & Study Plan. Everything after this lesson assumes you can name a target complexity from a constraint.

Part 1 — What Big-O Actually Says

Big-O describes how cost grows with input size. It is a statement about the shape of a curve, not about runtime in seconds.

f(n) is O(g(n))  ⟺  beyond some n₀, f(n) ≤ c · g(n) for a constant c

in practice: "ignore constants, keep the dominant term"

3n² + 500n + 9000   →  O(n²)
n + n log n         →  O(n log n)
2ⁿ + n¹⁰⁰           →  O(2ⁿ)      ← exponential eventually beats any polynomial

Three things it deliberately discards, and knowing them is what stops you misapplying it:

DiscardedConsequenceWhen it bites
Constant factorsO(n) with a 100× constant loses to O(n log n)Small n, or cache-hostile algorithms
Lower-order termsn² + n is just n²Rarely — this one is usually safe
Input size below n₀Asymptotics say nothing about n = 10Why insertion sort beats quicksort on tiny arrays

Big-O is an upper bound, which is why the precise vocabulary occasionally matters in an interview:

NotationMeansExample
O(g)Grows no faster than g — an upper boundBinary search is O(log n)
Ω(g)Grows at least as fast as g — a lower boundComparison sorting is Ω(n log n)
Θ(g)Both — a tight boundMerge sort is Θ(n log n)

Technically every O(n) algorithm is also O(n²) — the bound is still valid, just loose. In interviews "O(...)" is used to mean the tight bound, and saying "it's O(n²)" about a linear algorithm will get you corrected even though it is not false.

Best, average and worst case are a separate axis from O/Ω/Θ, and conflating them is a common stumble:

quicksort:  best Θ(n log n)   average Θ(n log n)   worst Θ(n²)     ← already-sorted input, bad pivot
hash lookup: best Θ(1)        average Θ(1)         worst Θ(n)      ← all keys collide

Interviews mean worst case unless you say otherwise. Claiming "hash map lookup is O(1)" is accepted shorthand, but the precise answer — "O(1) average, O(n) worst case with adversarial collisions" — is a senior signal that costs four extra words.

Candidates lose more points to missing the second direction than the first, because designing an exponential solution feels like giving up.

Part 3 — Reading Complexity Off Code

for (let i = 0; i < n; i++) { ... }                  // O(n)

for (let i = 0; i < n; i++)                          // O(n²) — nested over the same n
  for (let j = 0; j < n; j++) { ... }

for (let i = 1; i < n; i *= 2) { ... }               // O(log n) — i DOUBLES

for (let i = 0; i < n; i++)                          // O(n log n)
  for (let j = 1; j < n; j *= 2) { ... }

for (let i = 0; i < n; i++)                          // O(n²) NOT O(n) — triangular:
  for (let j = i; j < n; j++) { ... }                //   n + (n-1) + ... = n(n+1)/2

The rule is multiply when nested, add when sequential — and then keep only the dominant term:

sort(arr);                       // O(n log n)
for (const x of arr) { ... }     // O(n)
                                 // total: O(n log n) + O(n) = O(n log n)

The trap that catches most people is a hidden loop inside a loop. Library calls are not free, and the ones that scan are the difference between passing and timing out:

// looks O(n) — is actually O(n²)
for (const x of arr) {
  if (seen.includes(x)) return true;    // ← .includes() is O(n) on an array
  seen.push(x);
}

// genuinely O(n)
const seen = new Set();
for (const x of arr) {
  if (seen.has(x)) return true;         // ← O(1) average
  seen.add(x);
}
OperationComplexityNote
arr.includes(x), indexOfO(n)Scans — the classic hidden cost
set.has(x), map.get(k)O(1) averageO(n) worst case with collisions
arr.push/popO(1) amortisedOccasional resize
arr.shift/unshiftO(n)Reindexes everything — use a deque
arr.slice(a, b)O(b − a)Copies; inside a loop this is quadratic
str + str in a loopO(n²)Strings are immutable — collect and join
arr.sort()O(n log n)Frequently the dominant term

shift() deserves emphasis because it silently turns a correct BFS into a quadratic one:

// O(n²) — every shift() reindexes the whole queue
while (queue.length) { const node = queue.shift(); ... }

// O(n) — move a head pointer instead
let head = 0;
while (head < queue.length) { const node = queue[head++]; ... }

Part 4 — Recursion, Recurrences and Amortised Cost

For recursive algorithms, count the work per call and multiply by the number of calls. Two shortcuts cover nearly every interview case:

T(n) = 2·T(n/2) + O(n)     → O(n log n)     merge sort: halve, linear merge
T(n) = T(n/2)  + O(1)      → O(log n)       binary search: halve, constant work
T(n) = 2·T(n-1) + O(1)     → O(2ⁿ)          naive fib: branch twice, shrink by 1
T(n) = n·T(n-1) + O(n)     → O(n!)          permutations

The intuition that makes these memorable: dividing by 2 gives a log-depth tree; adding branches multiplies the width. Merge sort has log n levels each doing O(n) work. Naive Fibonacci has depth n and branches twice, so 2ⁿ nodes.

function fib(n) {                      // O(2ⁿ) — the same subproblems recomputed
  return n <= 1 ? n : fib(n-1) + fib(n-2);
}

function fib(n, memo = new Map()) {    // O(n) — each n computed once
  if (n <= 1) return n;
  if (memo.has(n)) return memo.get(n);
  memo.set(n, fib(n-1, memo) + fib(n-2, memo));
  return memo.get(n);
}

That single change from O(2ⁿ) to O(n) is the whole idea behind dynamic programming — memoisation turns an exponential recursion into a linear one whenever subproblems repeat.

Amortised analysis explains costs that are usually cheap and occasionally expensive. A dynamic array doubles when full, so a single push can cost O(n) — yet n pushes cost O(n) total:

copies when growing to n:  1 + 2 + 4 + 8 + ... + n/2 + n  <  2n

total for n pushes = O(n)  →  O(1) AMORTISED per push

Because the expensive resizes happen exponentially less often, their total cost is linear. The precise interview answer is "O(1) amortised" — saying plain O(1) invites the follow-up "but what about resizing?", and saying O(n) is wrong in the way that matters.

TermMeaningExample
AmortisedAverage over a sequence, worst-case guaranteedpush is O(1) amortised
Average caseExpected over random inputsQuicksort is O(n log n) average
Worst caseThe guarantee for any inputQuicksort is O(n²) worst case

Amortised is a stronger claim than average case: it holds for every sequence of operations, not merely typical ones. That distinction is a genuine senior signal.

Part 5 — Space Complexity

Space is scored too, and it is where recursion's cost hides.

function sumRec(arr, i = 0) {                  // O(n) TIME and O(n) SPACE
  if (i === arr.length) return 0;              // ← n stack frames, even with no
  return arr[i] + sumRec(arr, i + 1);          //   extra data structures
}

function sumIter(arr) {                        // O(n) time, O(1) space
  let total = 0;
  for (const x of arr) total += x;
  return total;
}

"Can you do it in O(1) space?" is the most common follow-up in the entire interview format, and it almost always means one of three things: convert recursion to iteration, replace an auxiliary array with two pointers, or reuse the input array itself.

StructureSpaceNote
Recursion on a listO(n)Stack depth — often overlooked
Recursion on a balanced treeO(log n)Depth, not node count
Recursion on a skewed treeO(n)Degenerates to a list
Hash map of all elementsO(n)The usual time/space trade
Two pointersO(1)Why it beats hashing when input is sorted
SortingO(1)–O(n)Heapsort O(1); merge sort O(n); JS sort is not specified

Output space is conventionally excluded. A function returning n results is "O(1) extra space" if it allocates nothing else — say "O(1) auxiliary space, excluding the output" and the ambiguity disappears.

Part 6 — From Constraints to Pattern

This is the payoff, and the reason this lesson comes first.

1. Read the constraint            n ≤ 10⁵
2. Infer target complexity        O(n log n) or better
3. Eliminate patterns             no backtracking, no O(n²) DP, no nested scan
4. Choose from what remains       sort / heap / two pointers / window / hashing
5. Check your plan against (2)    if it does not fit, the plan is wrong

Step 5 catches the expensive mistakes. Building an O(n²) solution for n = 10⁵ is not a near-miss — it is a failure the constraints announced before you started.

ConstraintTargetPatterns that fit
n ≤ 20O(2ⁿ)Subsets, bitmask DP, backtracking
n ≤ 5,000O(n²)2-D DP, pairwise scan
n ≤ 10⁵O(n log n)Sort, heap, two pointers, window, hashing
n ≤ 10⁹, small answer rangeO(log n)Binary search on the answer
Huge n, streamingO(n), O(1) spaceTwo pointers, running aggregates

❌ Declaring a complexity by counting visible loops. "One loop, so it's O(n)" is the most common wrong analysis in interviews, and it is wrong because the expensive work is usually inside a library call: includes scans, slice copies, shift reindexes, string concatenation reallocates. The candidate states O(n), the interviewer asks about the includes, and the answer turns out to be O(n²).

✅ Account for every operation inside the loop, then state the reasoning aloud. "The outer loop runs n times; set.has is O(1) average, so the total is O(n) — using O(n) extra space for the set." That sentence names the loop count, the per-iteration cost, the total, and the space trade. It is also exactly what the interviewer is scoring, and it takes ten seconds.

Interview Questions

Beginner: What is the time complexity of this function, and why? 
function hasDuplicate(arr) {
  for (let i = 0; i < arr.length; i++) {
    for (let j = i + 1; j < arr.length; j++) {
      if (arr[i] === arr[j]) return true;
    }
  }
  return false;
}

O(n²) time, O(1) space. The inner loop starting at i + 1 makes people guess it is better than quadratic, but summing the iterations settles it:

i=0 → n-1 iterations
i=1 → n-2
...
total = (n-1) + (n-2) + ... + 1 = n(n-1)/2 ≈ n²/2  →  O(n²)

Halving the work removes a constant factor, and constants are exactly what Big-O discards.

The linear alternative trades space for time:

function hasDuplicate(arr) {
  const seen = new Set();
  for (const x of arr) {
    if (seen.has(x)) return true;    // O(1) average
    seen.add(x);
  }
  return false;
}
// O(n) time, O(n) space

And there is a third point on the trade-off curve worth mentioning, because it shows you are thinking about space as well as time: sort first, then check adjacent pairs — O(n log n) time and O(1) extra space if sorting in place. Which is best depends on whether the constraint pressures time or memory.

Beginner: Why is a dynamic array's push() called "O(1) amortised" rather than O(1) or O(n)?

Because a single push is usually O(1) and occasionally O(n), and averaged over any sequence of pushes the cost per operation is constant.

What happens: the array has a capacity. When it fills, a push allocates a larger buffer (typically double) and copies everything across — that push is O(n). Every other push is O(1).

Why the average is constant is the part to be able to show:

growing to capacity n, the copies performed are
  1 + 2 + 4 + 8 + ... + n/2 + n   <   2n

so n pushes cost O(n) TOTAL  →  O(1) per push, amortised

Doubling means expensive resizes happen exponentially less often, so their total cost stays linear. If the array grew by a fixed amount instead — say 10 slots each time — there would be n/10 resizes copying an average of n/2 elements, giving O(n²) total and O(n) amortised. The doubling is what makes the guarantee work.

The distinction from "average case" matters: amortised is a worst-case guarantee over a sequence — no adversarial input makes n pushes cost more than O(n). Average case is an expectation over random inputs, and an adversary can defeat it. Quicksort is O(n log n) average but O(n²) worst case; push is O(1) amortised with no bad case at all.

Mid: Given n ≤ 10⁵ and a solution you believe is O(n²), what do you do?

Recognise it will not pass, say so out loud, and use the gap to find the intended approach — the constraint is telling me the answer's shape.

First, the arithmetic that justifies the claim:

O(n²) at n = 10⁵  →  10¹⁰ operations  ≈ 100 seconds   ✗
target O(n log n) →  1.7 × 10⁶        ≈ 0.02 seconds  ✓

So I need to remove a factor of roughly n. There are only a few ways to do that, and running through them is usually faster than staring at the problem:

TechniqueRemoves the inner loop byCost
Hash mapReplacing a scan with a lookupO(n) space
Sorting firstMaking order exploitableO(n log n), sometimes destroys indices
Two pointersDiscarding half the pairs per stepNeeds sorted input
Sliding windowReusing the previous window's workNeeds contiguity and monotonicity
Prefix sumsTurning range queries into subtractionO(n) space
Monotonic stackAmortising "next greater" queriesO(n) space

Concretely: if the O(n²) is "for each element, scan for a complement", a hash map makes it O(n). If it is "for each element, scan forward for the next larger", a monotonic stack makes it O(n). If it is "for each window, sum it", sliding window makes it O(n).

What I would say in the room: "The brute force is O(n²) which is 10¹⁰ operations here — too slow. The inner loop is searching for a complement, so a hash map should get it to O(n) with O(n) space. Shall I code that?" This states the baseline, proves I read the constraints, names the fix, and invites correction — all in about fifteen seconds.

And if I cannot find the improvement, I code the O(n²) anyway while saying why it is insufficient. A working suboptimal solution scores; twenty minutes of silence does not.

// (b)
for (let i = 1; i <= n; i *= 2)
  for (let j = 0; j < i; j++) work();

// (c)
function f(node) { if (!node) return; f(node.left); f(node.right); }

// (d)

ComplexityWhy it is tricky
(a)O(n²)Looks like less than nested; triangular sum is n(n+1)/2
(b)O(n)Looks like O(n log n) — but it is a geometric series
(c)O(n) time, O(h) spaceSpace is tree height, not node count
(d)O(n²)Immutable strings reallocate on every concatenation

(b) is the one that catches people, and it is worth working out:

outer i = 1, 2, 4, 8, ..., n     (log n iterations)
inner work = i each time

total = 1 + 2 + 4 + ... + n = 2n - 1  →  O(n)

A geometric series is dominated by its largest term, so log n iterations doing exponentially growing work sum to linear — not O(n log n). Contrast it with the genuine O(n log n) shape, where the outer loop is linear and the inner is logarithmic.

(c)'s space is the standard follow-up: O(log n) for a balanced tree, O(n) for a skewed one. Answering "O(h) where h is the height, which is O(n) worst case" pre-empts it.

(d)'s fix is to collect and join:

const parts = [];
for (let i = 0; i < n; i++) parts.push("x");
const s = parts.join("");        // O(n)
Senior: When is an asymptotically worse algorithm the right choice?

Whenever the discarded factors dominate at the actual input size — which is more often than the notation suggests, because Big-O deliberately throws away constants, lower-order terms and all behaviour below n₀.

1. Small n, where constants win. This is why real sort implementations switch to insertion sort for small subarrays:

insertion sort  O(n²)     but ~1 operation per comparison, cache-friendly, no recursion
merge sort      O(n log n) but allocation, recursion, and poor locality

n ≤ ~16 → insertion sort is measurably faster
→ every production sort (Timsort, introsort) does exactly this

2. Memory hierarchy effects that the model ignores. Big-O counts operations as equal, but a cache miss costs ~100× a cache hit. A linear scan of a contiguous array frequently beats an asymptotically superior structure with pointer chasing, which is why B-trees beat binary search trees on disk despite the same O(log n).

3. Worst case versus typical case. Quicksort is O(n²) worst case and beats merge sort in practice through better locality and no allocation — with randomised pivots making the bad case vanishingly unlikely.

4. Simplicity, when n is bounded by the problem. If the input is capped at 100 by the domain, an O(n²) solution that is obviously correct beats an O(n log n) one with subtle invariants that someone must maintain at 3am.

SituationPrefer
n bounded and smallThe simpler algorithm
Cache locality mattersContiguous over pointer-based
Worst case must be boundedMerge sort / heapsort over quicksort
n large and unboundedThe better asymptotic

In an interview I would still lead with the asymptotically better solution, since that is what is being scored — but noting "at these constraints the constant factor probably dominates, so I would benchmark before optimising further" is a strong senior signal. It shows the notation is a tool I use rather than a rule I follow.

Senior: How would you analyse the complexity of an algorithm whose cost depends on more than one input?

By naming every dimension explicitly and refusing to collapse them into a single n, because collapsing is where the analysis silently becomes wrong.

Graphs are the standard case:

BFS/DFS over a graph:  O(V + E)     NOT O(n)

dense graph:   E ≈ V²  →  O(V²)
sparse graph:  E ≈ V   →  O(V)

Writing O(n) hides that the same algorithm is linear or quadratic depending on the graph's shape — and the constraint usually tells you which. "V ≤ 10⁵, E ≤ 2×10⁵" is explicitly a sparse graph.

String problems are the other common case:

comparing n strings of length m:
  sorting them:      O(n·m log n)     ← each comparison costs O(m), not O(1)
  hashing them:      O(n·m)           ← must read every character
  building a trie:   O(n·m)

Treating a string comparison as O(1) is a frequent and consequential error — it is the difference between O(n log n) and O(n·m log n).

ProblemCorrect formCommon error
Graph traversalO(V + E)O(n) — which n?
Grid BFSO(rows × cols)O(n) without saying what n is
k-way mergeO(n log k)O(n log n) — the heap holds k, not n
0/1 knapsack DPO(n·W)"Polynomial" — it is pseudo-polynomial in W

The knapsack row is worth understanding properly, because it is a genuine subtlety. O(n·W) looks polynomial, but W is a value in the input, not a size — its encoding takes log W bits, so the algorithm is exponential in the input length. That is why knapsack is NP-hard despite the DP, and being able to explain it is a strong signal.

The practical habit: state which quantity each symbol refers to before giving the complexity — "O(V + E), where V is nodes and E is edges" — because half the value of the analysis is demonstrating you know precisely what you are counting.

2 (easy): Find the hidden complexity in code that looks linear.
Solution

Each of these appears O(n). Identify the real cost:

// (a)
function unique(arr) {
  const out = [];
  for (const x of arr) if (!out.includes(x)) out.push(x);
  return out;
}

// (b)
function bfs(start, graph) {
  const queue = [start], seen = new Set([start]);
  while (queue.length) {
    const node = queue.shift();
    for (const nb of graph[node]) if (!seen.has(nb)) { seen.add(nb); queue.push(nb); }
  }
}

// (c)
function build(n) {
  let s = "";
  for (let i = 0; i < n; i++) s += i + ",";
  return s;
}

// (d)
function firstK(arr, k) {
  const out = [];
  for (let i = 0; i < k; i++) out.push(arr.slice(i, i + 10));
  return out;
}
ActualCauseFix
(a)O(n²)includes scans outTrack membership in a Set
(b)O(V² + E)shift() reindexes the queueHead index, or a deque
(c)O(n²)Immutable strings reallocateArray + join
(d)O(k)Not a problem — slice length is constantNone needed

(d) is the control case: slice is O(b − a), and here that is always 10, so the total is O(10k) = O(k). The lesson is to check what the operation costs in this call rather than pattern-matching on the method name.

The corrected (a) and (b):

function unique(arr) {
  const seen = new Set(), out = [];
  for (const x of arr) if (!seen.has(x)) { seen.add(x); out.push(x); }
  return out;                                  // O(n) time, O(n) space
}

function bfs(start, graph) {
  const queue = [start], seen = new Set([start]);
  let head = 0;                                // ← the whole fix
  while (head < queue.length) {
    const node = queue[head++];
    for (const nb of graph[node]) if (!seen.has(nb)) { seen.add(nb); queue.push(nb); }
  }
}                                              // O(V + E)

(b) is the most consequential of the four, because the algorithm is correct and the complexity is silently wrong — a BFS that should be linear becomes quadratic on large graphs, and it only shows up as a timeout.

The reasoning for (a), which generalises: the recursion tree has log n levels and each level does O(n) total work (the halves sum back to n), giving n · log n.

(e) shows why the branching factor matters more than the division. Three branches on half-size inputs gives 3^(log₂ n) = n^(log₂ 3) leaves — Karatsuba beats schoolbook multiplication's O(n²) precisely by turning four subproblems into three.

Verify (c) empirically by counting calls:

let calls = 0;
function fib(n) { calls++; return n <= 1 ? n : fib(n-1) + fib(n-2); }

for (const n of [10, 20, 25, 30]) {
  calls = 0; fib(n);
  console.log(n, calls, (calls / Math.pow(2, n)).toFixed(3));
}

10      177   0.173
20   21891    0.021
25  242785    0.007
30 2692537    0.003

Calls grow by roughly 1.6× per increment of n — that is φ, the golden ratio, so the true bound is O(φⁿ) ≈ O(1.618ⁿ), tighter than the O(2ⁿ) upper bound. Both statements are correct; O(2ⁿ) is a valid but loose bound, and knowing the difference is exactly the O-versus-Θ distinction.

Then confirm memoisation collapses it:

calls = 0;
function fibMemo(n, memo = new Map()) {
  calls++;
  if (n <= 1) return n;
  if (memo.has(n)) return memo.get(n);
  memo.set(n, fibMemo(n-1, memo) + fibMemo(n-2, memo));
  return memo.get(n);
}
fibMemo(30);  console.log(calls);   // 59  — linear, versus 2,692,537
4 (medium): Measure amortised cost and prove the doubling argument.
Solution

Implement a dynamic array that counts element copies, then compare growth strategies:

class Growable {
  constructor(growth) { this.data = new Array(1); this.size = 0;
                        this.cap = 1; this.copies = 0; this.growth = growth; }
  push(x) {
    if (this.size === this.cap) {
      const newCap = this.growth(this.cap);
      const next = new Array(newCap);
      for (let i = 0; i < this.size; i++) { next[i] = this.data[i]; this.copies++; }
      this.data = next; this.cap = newCap;
    }
    this.data[this.size++] = x;
  }
}

for (const n of [1000, 10000, 100000]) {
  const dbl = new Growable(c => c * 2);
  const add = new Growable(c => c + 10);
  for (let i = 0; i < n; i++) { dbl.push(i); add.push(i); }
  console.log(n,
    "doubling:", dbl.copies, "(" + (dbl.copies/n).toFixed(2) + " per push)",
    "| +10:", add.copies, "(" + (add.copies/n).toFixed(1) + " per push)");
}

  1000 doubling:    1023 (1.02 per push) | +10:    49500 (49.5 per push)
 10000 doubling:   16383 (1.64 per push) | +10:  4995000 (499.5 per push)
100000 doubling:  131071 (1.31 per push) | +10: 499950000 (4999.5 per push)

Doubling holds copies-per-push under 2 regardless of n — that is O(1) amortised. Fixed growth's per-push cost grows linearly with n, which is O(n) amortised and O(n²) total.

The proof, which the numbers confirm:

doubling to capacity n copies  1 + 2 + 4 + ... + n/2  =  n - 1  <  n
  → total O(n) over n pushes → O(1) each

+k growth needs n/k resizes, copying ~n/2 on average
  → total O(n²/k) → O(n/k) each → O(n) amortised

Now show that a single push is genuinely not O(1), which is why the word "amortised" is load-bearing:

const a = new Growable(c => c * 2);
for (let i = 0; i < 100000; i++) {
  const before = a.copies;
  a.push(i);
  if (a.copies - before > 1000) console.log("push", i, "copied", a.copies - before);
}

push  1024 copied  1024
push  2048 copied  2048
push  4096 copied  4096
push 65536 copied 65536      ← a single O(n) push

Individual pushes at capacity boundaries cost O(n). The amortised claim is not that this never happens — it is that it happens rarely enough that the total stays linear, which is a worst-case guarantee over the sequence rather than an average over random inputs.

5 (hard): Derive the required pattern from constraints alone, then verify by measurement.
Solution

The problem: "Given an array of n integers and an integer k, return the number of distinct pairs (i, j) with i < j and nums[i] + nums[j] == k." Three constraint sets, three different correct answers.

ConstraintTargetApproach
n ≤ 1,000O(n²) fineNested loops — simplest correct code
n ≤ 10⁵O(n) or O(n log n)Hash map of counts, or sort + two pointers
n ≤ 10⁷, memory ≤ 64 MBO(n log n), O(1) spaceSort in place + two pointers — a hash map may not fit

The three implementations:

// n ≤ 1000 — O(n²), and this is the RIGHT answer at this constraint
function countPairsBrute(nums, k) {
  let c = 0;
  for (let i = 0; i < nums.length; i++)
    for (let j = i + 1; j < nums.length; j++)
      if (nums[i] + nums[j] === k) c++;
  return c;
}

// n ≤ 10⁵ — O(n) time, O(n) space
function countPairsHash(nums, k) {
  const seen = new Map();
  let c = 0;
  for (const x of nums) {
    c += seen.get(k - x) ?? 0;              // every earlier complement pairs with x
    seen.set(x, (seen.get(x) ?? 0) + 1);
  }
  return c;
}

// n ≤ 10⁷, tight memory — O(n log n) time, O(1) extra space
function countPairsTwoPtr(nums, k) {
  nums.sort((a, b) => a - b);               // in place
  let l = 0, r = nums.length - 1, c = 0;
  while (l < r) {
    const s = nums[l] + nums[r];
    if (s === k) { c++; l++; r--; }         // (counts pairs, not multiplicities)
    else if (s < k) l++;
    else r--;
  }
  return c;
}

Measure to confirm the constraint reasoning was right:

for (const n of [1000, 10000, 100000]) {
  const nums = Array.from({length: n}, () => Math.floor(Math.random() * 1000));
  for (const [name, fn] of [["brute", countPairsBrute], ["hash", countPairsHash]]) {
    if (name === "brute" && n > 20000) { console.log(n, name, "skipped"); continue; }
    const t = performance.now(); fn([...nums], 500);
    console.log(n, name, (performance.now() - t).toFixed(1) + " ms");
  }
}

  1000 brute    0.9 ms
  1000 hash     0.2 ms
 10000 brute   82.4 ms          ← 100x the input, ~90x the time: quadratic confirmed
 10000 hash     1.1 ms
100000 brute  skipped (would be ~8 s)
100000 hash    9.8 ms           ← linear

Brute force grew ~90× when n grew 10× — the signature of O(n²). The hash version grew ~9×, the signature of O(n).

The judgement worth stating: at n ≤ 1,000 the brute force takes under a millisecond and is the clearest code, so writing the hash version there optimises something that was never a problem. The constraint does not just forbid slow solutions — it also tells you when a simple one is sufficient.

6 (hard): Analyse a multi-input algorithm and expose a pseudo-polynomial trap.
Solution

Part A — graph traversal. Give the complexity of BFS on a graph, and explain why O(n) is not an acceptable answer:

function bfs(start, adj) {
  const seen = new Set([start]), queue = [start];
  let head = 0;
  while (head < queue.length) {
    const node = queue[head++];
    for (const nb of adj[node]) if (!seen.has(nb)) { seen.add(nb); queue.push(nb); }
  }
  return seen;
}

O(V + E) — every vertex is enqueued once and every edge examined once. Writing O(n) hides that the same code is linear or quadratic depending on density:

sparse (E ≈ V):   O(V)      e.g. a tree, or a grid
dense  (E ≈ V²):  O(V²)     e.g. a complete graph

The constraint tells you which: "V ≤ 10⁵, E ≤ 2×10⁵" is explicitly sparse, so BFS is comfortable. If E could be V², then V ≤ 10⁵ would mean 10¹⁰ edges — impossible, so the constraint is also telling you the graph is sparse.

Part B — the knapsack trap. This DP is often called polynomial. It is not:

function knapsack(weights, values, W) {
  const dp = new Array(W + 1).fill(0);
  for (let i = 0; i < weights.length; i++)
    for (let w = W; w >= weights[i]; w--)
      dp[w] = Math.max(dp[w], dp[w - weights[i]] + values[i]);
  return dp[W];
}

O(n·W) time, O(W) space — and W is a value from the input, not a size:

n = 100 items, W = 1,000        → 10⁵ operations     instant
n = 100 items, W = 1,000,000    → 10⁸ operations     ~1 second
n = 100 items, W = 10⁹          → 10¹¹ operations    intractable

the INPUT barely grew — W takes log₂(10⁹) ≈ 30 bits to write down

That is what pseudo-polynomial means: polynomial in the numeric value W, exponential in the number of bits needed to encode it. It is why 0/1 knapsack is NP-hard despite having a DP solution, and being able to explain it is a genuine senior signal.

Part C — verify empirically that W drives the cost:

for (const [n, W] of [[100, 1000], [100, 100000], [1000, 1000], [100, 1000000]]) {
  const w = Array.from({length: n}, () => 1 + Math.floor(Math.random() * 100));
  const v = Array.from({length: n}, () => Math.floor(Math.random() * 100));
  const t = performance.now(); knapsack(w, v, W);
  console.log(`n=${n} W=${W}`, (performance.now() - t).toFixed(1) + " ms");
}

n=100  W=1000        0.4 ms
n=100  W=100000     31.2 ms      ← 100x W  → ~80x time
n=1000 W=1000        3.9 ms      ← 10x n   → ~10x time
n=100  W=1000000   318.7 ms      ← W dominates entirely

Both dimensions scale the runtime linearly, exactly as O(n·W) predicts — and W, the one that costs almost nothing to write in the input, is the one that makes the problem intractable.

The habit this exercise is training: name what each symbol counts before stating a complexity. "O(V + E) where V is vertices and E is edges" and "O(n·W) where W is the capacity value, so this is pseudo-polynomial" are the answers that demonstrate you know what you are counting — which is half of what the analysis is for.

🎯 Key Takeaways

  • Big-O describes growth, not runtime — it deliberately discards constants, lower-order terms, and all behaviour below some n₀.
  • O is an upper bound, Ω a lower bound, Θ a tight one; interviews say "O" but mean tight, and mean worst case unless you say otherwise.
  • Best/average/worst case is a separate axis from O/Ω/Θ — quicksort is Θ(n log n) average and Θ(n²) worst.
  • Know the arithmetic: ~10⁸ operations per second, so O(n²) at n = 10⁵ is ~100 seconds and O(n log n) is 0.02.
  • Memorise the constraint ladder: n ≤ 20 → O(2ⁿ); n ≤ 5,000 → O(n²); n ≤ 10⁵ → O(n log n); n ≤ 10⁹ → O(log n).
  • Read constraints in both directions — small n means an exponential solution is intended, not a failure.
  • Multiply for nested loops, add for sequential ones, then keep the dominant term.
  • for (j = i; j < n; j++) is O(n²), not O(n) — the triangular sum is n(n+1)/2.
  • A doubling inner loop over a doubling outer loop is a geometric series: O(n), not O(n log n).
  • The commonest wrong analysis is counting visible loops — includes, slice, shift and string concatenation all hide loops.
  • shift() in a BFS queue turns O(V + E) into O(V² + E); use a head index instead.
  • Recurrence shortcuts: T(n)=2T(n/2)+O(n) → O(n log n); T(n)=T(n/2)+O(1) → O(log n); T(n)=2T(n−1)+O(1) → O(2ⁿ).
  • Memoisation collapses exponential recursion to linear whenever subproblems repeat — that is all dynamic programming is.
  • "O(1) amortised" is the precise answer for push: doubling makes total copies linear across n pushes.
  • Amortised is stronger than average case — it is a worst-case guarantee over any sequence of operations.
  • Recursion costs O(depth) space even with no data structures: O(log n) on a balanced tree, O(n) on a skewed one.
  • "Can you do it in O(1) space?" almost always means iterate instead of recursing, use two pointers, or reuse the input.
  • Name every dimension: O(V + E) for graphs, O(n·m) for n strings of length m — collapsing them to O(n) hides the real cost.
  • O(n·W) knapsack is pseudo-polynomial: polynomial in the value W, exponential in the bits used to encode it.
  • An asymptotically worse algorithm can be the right choice at small n, under cache pressure, or when a bounded worst case matters.
