Overview & Study Plan Start Here

What you'll master: why interviews test roughly twenty reusable patterns rather than three thousand problems, and how to recognise which one applies from the problem statement alone; the constraint-reading skill that tells you the target complexity before you write a line; the decision procedure that maps input shape to pattern; how to run the 45 minutes of an actual interview so that a partial solution still passes; what interviewers are really scoring, which is not whether your code compiles; and a study plan that produces recognition rather than memorised solutions. No prerequisites — this is the first lesson. It ends by pointing at Big-O & Complexity Analysis.

Part 1 — The Skill Being Tested

Candidates who have solved 400 problems routinely fail interviews that candidates who have solved 80 pass. The difference is not volume; it is whether the practice built recognition or recall.

RECALL (fails)                          RECOGNITION (passes)
──────────────                          ────────────────────
"I've seen this one... it was           "Sorted array, find a pair — the
 something with a hash map...            sorted-ness is the gift. Two pointers,
 I remember the answer was 2..."         O(n), and I can prove nothing is missed."

breaks on any variation                 adapts, because the REASON is understood

An interviewer is not checking whether you have memorised LC 15. They are checking whether, given an unfamiliar problem, you can identify its structure and derive a solution. That is why this track is organised by pattern rather than by problem.

🔑 The single highest-leverage habit: read the constraints before the problem statement. Constraints tell you the intended complexity, and complexity tells you the pattern — often before you have finished reading what the problem is asking. Candidates who skip the constraints spend ten minutes designing an O(n²) solution for an input of size 10⁵, then have to start over with twenty minutes left. This one habit converts more interview failures into passes than any amount of extra problem-solving.
Constraint on nTarget complexityWhat that implies
n ≤ 10O(n!) or O(2ⁿ)Permutations, subsets — backtracking
n ≤ 20O(2ⁿ)Subsets, bitmask DP over all states
n ≤ 500O(n³)Floyd-Warshall, interval DP
n ≤ 5,000O(n²)Two-dimensional DP, nested scan
n ≤ 10⁵–10⁶O(n log n) or O(n)The overwhelmingly common case — sort, heap, two pointers, sliding window, hashing

Work the arithmetic once and it stays with you. A modern judge does roughly 10⁸ simple operations per second. With n = 10⁵:

O(n²)      = 10¹⁰ operations  → ~100 seconds   ✗ time limit exceeded
O(n log n) = 1.7 × 10⁶        → ~0.02 seconds  ✓
O(n)       = 10⁵              → ~0.001 seconds ✓

So "n ≤ 10⁵" is the interviewer telling you the answer is O(n log n) or better. That eliminates most patterns immediately and is information you get for free, before any thinking about the problem itself.

Two cues are worth singling out because they are the most commonly missed.

"Minimise the maximum" means binary search on the answer, not a greedy or DP approach. The giveaway is that checking a candidate answer is easy even though finding the best one is not:

"Split the array into m subarrays; minimise the largest subarray sum."

hard:  find the optimal split
easy:  given a limit L, can we split into ≤ m parts each ≤ L?   ← greedy check, O(n)

and feasibility is MONOTONIC: if L works, every larger L works
→ binary search L over [max(nums), sum(nums)]

"Contiguous" is the word that separates Sliding Window from everything else. Remove it and the pattern changes completely — a contiguous subarray summing to k is a sliding window (positive values) or a prefix-sum hash map (with negatives); a subset summing to k is a subset-sum DP, an entirely different problem with entirely different complexity.

Part 3 — The Decision Procedure

When the phrase does not give it away, the input shape does. Work down this list:

1. What is the INPUT?
   array/string ──▶ sorted?  ──yes──▶ two pointers / binary search
                    │
                    └──no───▶ contiguous window asked for? ──▶ sliding window
                              range sums / negatives?       ──▶ prefix sum
                              need counts or lookups?       ──▶ hashing
   linked list  ──▶ cycle/middle?    ──▶ fast & slow
                    reorder/reverse? ──▶ in-place reversal
   tree         ──▶ level by level?  ──▶ BFS
                    path/subtree?    ──▶ DFS + recursion
   graph        ──▶ shortest (unweighted)? ──▶ BFS
                    dependencies?           ──▶ topological sort
                    connectivity/merging?   ──▶ union-find
   intervals    ──▶ sort by start, sweep

2. What is ASKED?
   "the best/k-th"  ──▶ heap, or binary search on the answer
   "how many ways"  ──▶ DP
   "all of them"    ──▶ backtracking
   "does it exist"  ──▶ hashing, or DFS/BFS

3. Does the CONSTRAINT agree with the complexity of what I just chose?
   If not, go back — the constraint is right and the plan is wrong.

Step 3 is the check most candidates skip. Choosing backtracking for n = 10⁵ is not a small error; it is a guaranteed failure that the constraints announced in advance.

Many problems are two patterns composed, and this is what separates medium from hard far more often than any single pattern's difficulty:

Part 4 — Running the 45 Minutes

Technical ability is necessary and not sufficient. A great deal of interview failure is process failure, and process is entirely learnable.

MinutesDo thisWhy it matters
0–3Restate the problem; ask about edge cases and constraintsCatches misunderstanding while it is still free
3–6Work one small example by handFrequently reveals the pattern; shows your thinking
6–10State the brute force and its complexity, then improve itGuarantees a baseline — never sit silent
10–13Name the pattern and the target complexity; get agreementAn interviewer will redirect you here if you are wrong — for free
13–33Code it, narrating as you goSilent coding is unscoreable
33–40Trace your code on the example, out loudFinds off-by-one errors before the interviewer does
40–45Discuss complexity, edge cases, and possible follow-upsShows senior awareness

Say the brute force out loud even when it is embarrassing. "The naive approach is to check every pair, which is O(n²); given n up to 10⁵ that is too slow, so I need something better" takes fifteen seconds and does three things: it establishes a working baseline, it demonstrates you read the constraints, and it invites a hint. Candidates who stay silent hunting for the optimal solution frequently produce nothing at all.

❌ Grinding problem count as the measure of progress. "I've done 300 problems" is a number that feels like readiness and often is not. Solving each problem once, reading the editorial when stuck, and moving on builds a memory of specific answers — which collapses the moment an interviewer varies the input, asks for a follow-up, or gives a problem the candidate happens not to have seen.

✅ Practise recognition and re-derivation, and measure yourself on those. After solving a problem, close it and write down which pattern it was and what phrase in the statement signalled it. Re-solve it three days later from the template rather than from memory. Explain the complexity out loud. Eighty problems handled this way beat three hundred handled the other way, and the difference shows up precisely on the unfamiliar problem an interview is built around.

Part 5 — What Is Actually Being Scored

Most interview rubrics score four things, and only one of them is the code.

DimensionWhat a strong signal looks like
Problem solvingReads constraints, states a baseline, improves it deliberately rather than by guessing
CodingClean, correct, sensible names; handles empty and single-element inputs
CommunicationNarrates the approach, responds to hints, asks clarifying questions
VerificationTraces the code on an example unprompted, finds their own bugs

A candidate who reaches a working O(n log n) solution while explaining their reasoning usually scores above one who silently produces the optimal O(n). This is not a consolation prize — the job involves working with other people on problems nobody has solved yet, and the interview is a proxy for that.

The most common avoidable failures are not exotic:

- silence for 10 minutes while thinking          → narrate instead
- coding before agreeing on the approach         → state it, get a nod, then code
- ignoring a hint because it breaks your plan    → hints are a signal you are off-track
- no edge cases: empty input, one element, all-equal, overflow
- claiming a complexity without justifying it    → say WHY it is O(n log n)

Interview Questions

Beginner: The constraint says 1 ≤ n ≤ 10⁵. What does that tell you before you have read the problem?

That the intended solution is O(n log n) or better, and that anything quadratic is out. This is the most useful free information in any problem statement.

The arithmetic, once: a judge performs roughly 10⁸ simple operations per second, so at n = 10⁵:

O(n²)      = 10¹⁰  → ~100 s     ✗
O(n log n) = 1.7×10⁶ → ~0.02 s  ✓
O(n)       = 10⁵   → ~0.001 s   ✓

So the search space of plausible patterns shrinks immediately to sorting, heaps, two pointers, sliding window, hashing, prefix sums, and single-pass graph traversal. Backtracking, subset enumeration and O(n²) DP are all eliminated without knowing what the problem asks.

nTargetTypical pattern
≤ 20O(2ⁿ)Subsets, bitmask DP
≤ 5,000O(n²)2-D DP
≤ 10⁵O(n log n)Sort, heap, two pointers, hashing
≤ 10⁹O(log n)Binary search on the answer

The reverse inference is just as useful. If n ≤ 20, an exponential solution is not merely acceptable — it is almost certainly what is intended, and searching for a clever polynomial algorithm is wasted interview time.

Beginner: Why does this track organise material by pattern rather than by problem?

Because interviews present unfamiliar problems, and only patterns transfer to problems you have not seen.

There are thousands of problems and roughly twenty structural ideas behind them. A candidate who has memorised solutions has a lookup table with no entry for the question actually asked; a candidate who knows patterns has a derivation procedure.

RECALL:      "I've seen this... something with a hash map... the answer was 2?"
             → breaks on any variation

RECOGNITION: "Sorted input, find a pair. Sortedness means moving the left
              pointer only increases the sum — so two pointers, O(n), and
              I can prove no pair is skipped."
             → adapts, because the reason is understood

It also explains the interview failure mode people find puzzling: a candidate who has done 400 problems failing where one who has done 80 passes. Volume without re-derivation builds recall; the 80-problem candidate practised recognition.

And patterns compose, which is what most "hard" problems actually are. Top K Frequent Elements is a hash map plus a heap; Word Search II is a trie plus DFS backtracking. Knowing the pieces means a hard problem is two familiar ideas rather than one unfamiliar one.

Mid: A problem asks you to minimise the largest sum among m subarray splits. How do you recognise the approach?

The phrase "minimise the maximum" is the cue, and it means binary search on the answer. The structural signal is that checking a candidate answer is much easier than finding the best one.

hard:  what is the smallest possible largest-subarray-sum?
easy:  given a limit L, can we split into ≤ m parts each summing ≤ L?

The feasibility check is a simple greedy sweep:

function canSplit(nums, m, limit) {
  let parts = 1, current = 0;
  for (const x of nums) {
    if (x > limit) return false;          // a single element exceeds the limit
    if (current + x > limit) { parts++; current = x; }   // start a new part
    else current += x;
  }
  return parts <= m;
}

The property that makes binary search valid is monotonicity: if a limit L is feasible, every larger limit is also feasible. That means the feasible values form a contiguous suffix, and the answer is its boundary — exactly what binary search finds.

lo = max(nums)        // cannot be smaller: one element must fit
hi = sum(nums)        // always feasible: one part containing everything

while (lo < hi) {
  const mid = lo + Math.floor((hi - lo) / 2);
  if (canSplit(nums, m, mid)) hi = mid;   // feasible → try smaller
  else lo = mid + 1;
}
return lo;

Complexity is O(n log(sum − max)) — n per feasibility check, logarithmically many checks. The generalisation worth remembering: whenever the answer is a number, and feasibility is monotonic in that number, binary search the answer rather than searching for it directly. "Minimum days to ship packages", "smallest divisor given a threshold" and "minimum eating speed" are all the same problem in different costumes.

Mid: Walk through how you decide which pattern a new problem needs.

I work three questions in order, and the third is a check that catches most errors.

1. What is the input shape?

InputThen askPattern
Array/stringSorted?Two pointers, binary search
Array/stringContiguous window asked for?Sliding window
ArrayRange sums, or negatives present?Prefix sum + hash map
Linked listCycle or middle?Fast & slow pointers
TreeLevel by level?BFS
GraphDependencies? Connectivity?Topological sort; union-find
IntervalsAlwaysSort by start, sweep

2. What is being asked? "The best or k-th" suggests a heap or binary search on the answer; "how many ways" suggests DP; "all of them" suggests backtracking; "does it exist" suggests hashing or a traversal.

3. Does the constraint agree with the complexity I just chose? This is the step that catches the expensive mistakes. Choosing backtracking when n ≤ 10⁵ is a guaranteed failure that the constraints announced before I started. If the complexity does not fit, the constraint is right and my plan is wrong.

Worked example: "Given an unsorted array of n ≤ 10⁵ integers, find the length of the longest contiguous subarray summing to k, where values may be negative."

input:      array, unsorted           → not two pointers, not binary search
asked:      contiguous subarray sum   → sliding window?
BUT:        negatives present         → window sum is not monotonic, so
                                        shrinking does not reliably reduce it
                                      → sliding window is INVALID here
therefore:  prefix sum + hash map of first-seen prefix index
constraint: O(n) ✓ agrees with n ≤ 10⁵

The negatives detail is the whole problem. Sliding window depends on the window sum increasing when you extend and decreasing when you shrink; negative numbers break that invariant, which is why the same question with "all positive" in the constraints is a different pattern entirely.

Senior: You are 20 minutes into a 45-minute interview with no working solution. What do you do?

I would stop optimising and secure a baseline, because at this point the largest risk is finishing with nothing to show.

1. Say the brute force out loud and start coding it, explicitly framed as a baseline:

"I don't have the optimal approach yet. Let me code the O(n²) version so we
 have something correct, then optimise it — I think the improvement is
 avoiding the rescan of the inner loop."

This converts a likely no-hire into a partial pass. A working brute force with a clear analysis of why it is too slow scores meaningfully; twenty-five more minutes of silent thinking scores nothing.

2. Invite the hint explicitly. Interviewers are usually willing to help and are waiting for an opening. "I'm considering a hash map to avoid the inner loop — does that seem like the right direction?" is a much better use of thirty seconds than continuing alone, and responding well to hints is itself a scored dimension.

3. Re-read the constraints. Being stuck often means I have anchored on the wrong complexity target. If n ≤ 5,000, an O(n²) solution may be the intended answer and I have been searching for an elegance that does not exist.

4. Work a concrete example by hand. Being stuck in the abstract is usually solved concretely — tracing a five-element input frequently exposes the structure, and the interviewer sees methodical debugging rather than paralysis.

What I would not do: stay silent, apologise repeatedly, or abandon a half-written approach to start a different one from scratch. Two half-solutions score far worse than one complete suboptimal solution.

The underlying judgement is that the interview measures how I work under uncertainty, not whether I happen to know this problem. A candidate who says "here is a correct approach, here is why it is too slow, here is where I think the improvement lives" has demonstrated exactly the reasoning the job requires — and has often talked their way to the optimal solution in the process.

Senior: How would you design a study plan for an engineer with six weeks and a full-time job?

I would optimise for recognition per hour rather than problems per week, because the binding constraint is time and the failure mode is memorising answers.

Weeks 1–4: patterns in dependency order, roughly 5 problems each. The ordering matters because the patterns build on one another:

WeekPatternsWhy here
1Big-O, hashing, two pointers, sliding windowHighest frequency in real interviews
2Binary search (incl. on the answer), prefix sum, intervalsSearch and sweep
3BFS/DFS, trees, topological sortTraversal underpins all graph problems
4Heaps, backtracking, DP fundamentalsSelection and exhaustive search

Weeks 5–6: mixed randomised practice only, plus two timed mock interviews per week. This is the non-negotiable half. Practising one pattern at a time never trains recognition, because the chapter heading already told you the answer — the skill only develops when problems arrive unlabelled.

The per-problem protocol matters more than the problem selection:

1. Read constraints → state the target complexity out loud
2. 25-30 minutes of genuine attempt before any editorial
3. After solving: write ONE line — which pattern, and what phrase signalled it
4. Re-solve from the template 3 days later, not from memory

Step 3 is the highest-value habit in the whole plan, and it takes ten seconds. The written record becomes a personal recognition table, and reviewing it before an interview is worth more than solving three more problems.

What I would cut given limited time: obscure patterns (segment trees, advanced graph algorithms) and hard DP. The distribution of real interview questions is heavily weighted toward arrays, strings, hashing, two pointers, sliding window, binary search and BFS/DFS — and being fluent in those beats being shaky across everything.

And I would insist on the timed mocks, because the most common failure in this population is process, not knowledge: coding before agreeing on an approach, going silent, and never verifying. Those are only visible under interview conditions, and they are the cheapest points on the board to recover.

3 (medium): Apply the full decision procedure to an unfamiliar problem.
Solution

The problem: "You are given an array of n integers (1 ≤ n ≤ 10⁵, values may be negative) and an integer k. Return the number of contiguous subarrays whose sum equals k."

Step 1 — constraints first. n ≤ 10⁵ means O(n) or O(n log n). O(n²) enumeration of all subarrays is 10¹⁰ operations — ruled out before any thinking about the approach.

Step 2 — input shape. An unsorted array. Not sorted, so two pointers and binary search are out. "Contiguous subarray" suggests sliding window — but the values may be negative.

Step 3 — test the sliding-window invariant, which is where this problem is decided:

sliding window requires: extending the window INCREASES the sum,
                         shrinking it DECREASES the sum

with negatives:  [1, -1, 1]  target 1
                 extending from [1] to [1,-1] DECREASES the sum
                 → shrinking is no longer a valid way to reduce it
                 → sliding window is INVALID

Step 4 — reach for prefix sums. Any contiguous range sum is a difference of two prefixes, and that identity does not care about signs:

sum(i..j) = prefix[j] - prefix[i-1]

so   sum(i..j) == k
⟺   prefix[j] - prefix[i-1] == k
⟺   prefix[i-1] == prefix[j] - k     ← a lookup, not a scan

The solution:

function subarraySum(nums, k) {
  const seen = new Map([[0, 1]]);      // empty prefix, seen once
  let prefix = 0, count = 0;
  for (const x of nums) {
    prefix += x;
    count += seen.get(prefix - k) ?? 0;   // how many earlier prefixes complete a k-sum
    seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
  }
  return count;
}

The [0, 1] seed is the subtle part — it represents the empty prefix, and without it any subarray starting at index 0 is missed. Verify with a trace:

nums = [1, 1, 1], k = 2

x=1: prefix=1, look for -1 → 0 found. count=0. seen={0:1, 1:1}
x=1: prefix=2, look for  0 → 1 found. count=1. seen={0:1, 1:1, 2:1}   ← [1,1]
x=1: prefix=3, look for  1 → 1 found. count=2. seen={...,3:1}          ← [1,1] at index 1

answer 2 ✓

Complexity O(n) time, O(n) space, which agrees with step 1 — the check that closes the procedure. And confirm the negative case the window could not handle:

nums = [1, -1, 0], k = 0  →  3   ([1,-1], [-1,0]... and [0])

Work one through end to end — Sliding Window Maximum: given an array and window size k, return the maximum of each window.

naive:      for each window, scan it → O(n·k)
constraint: n ≤ 10⁵, k ≤ n  → O(n·k) can be 10¹⁰   ✗ need O(n)

Pattern A gives the window; pattern B answers "maximum" in O(1) amortised. A monotonic decreasing deque of indices keeps the largest at the front:

function maxSlidingWindow(nums, k) {
  const dq = [], out = [];            // dq holds INDICES, values decreasing
  for (let i = 0; i < nums.length; i++) {
    if (dq.length && dq[0] <= i - k) dq.shift();        // front left the window
    while (dq.length && nums[dq[dq.length-1]] <= nums[i]) dq.pop();
    dq.push(i);                                          // now smaller elements are gone
    if (i >= k - 1) out.push(nums[dq[0]]);
  }
  return out;
}

Why popping smaller elements is safe is the insight worth being able to state: if nums[i] is larger than an earlier element and arrives later, that earlier element can never be the maximum of any future window — it is both smaller and expires sooner. It is dominated, so it can be discarded permanently.

nums = [1,3,-1,-3,5], k = 3

i=0: dq=[0]                      (1)
i=1: 3 > 1 → pop 0; dq=[1]       (3)
i=2: dq=[1,2]                    (3,-1)  → window max = 3 ✓
i=3: dq=[1,2,3]                  (3,-1,-3) → max = 3 ✓
i=4: front 1 expired → shift; 5 pops all; dq=[4] → max = 5 ✓

Each index is pushed once and popped once, so it is O(n) despite the inner while loop — the amortised argument that most candidates need to state explicitly, because at a glance the nested loop looks quadratic.

5 (hard): Run a full mock interview on yourself, timed.
Solution

The problem (45 minutes, narrate aloud, no editorial): "Given an array of n integers (1 ≤ n ≤ 10⁵) and an integer k, return the maximum sum of any contiguous subarray of length exactly k. Then extend it: return the maximum sum of any contiguous subarray of length at most k."

Minutes 0–3 — restate and clarify:

"So I need a contiguous run of exactly k elements with the largest sum.
 Questions: can values be negative? Is k guaranteed ≤ n? What should I
 return if the array is empty?"

Minutes 3–6 — a small example by hand:

nums = [2, 1, 5, 1, 3, 2], k = 3
windows: [2,1,5]=8  [1,5,1]=7  [5,1,3]=9  [1,3,2]=6   → 9

Minutes 6–10 — brute force, out loud: "For each start index, sum k elements: O(n·k). With n up to 10⁵ that could be 10¹⁰ — too slow, so I need to avoid recomputing the overlap."

Minutes 10–13 — name the pattern: "Fixed-size sliding window. Each step adds one element and removes one, so the sum updates in O(1) and the whole thing is O(n)."

Minutes 13–33 — code it, narrating:

function maxSumFixed(nums, k) {
  if (nums.length < k) return null;
  let sum = 0;
  for (let i = 0; i < k; i++) sum += nums[i];      // first window
  let best = sum;
  for (let i = k; i < nums.length; i++) {
    sum += nums[i] - nums[i - k];                   // slide: add new, drop old
    best = Math.max(best, sum);
  }
  return best;
}

Minutes 33–40 — trace it:

[2,1,5,1,3,2], k=3
first window: 2+1+5 = 8, best=8
i=3: 8 + 1 - 2 = 7,  best=8
i=4: 7 + 3 - 1 = 9,  best=9
i=5: 9 + 2 - 5 = 6,  best=9      → 9 ✓

The extension is the real test, and it is where the pattern changes. "At most k" breaks the fixed window, because with negative values a shorter window can beat a longer one:

[5, -10, 5], k = 3
best of length exactly 3: 0
best of length at most 3: 5      ← different answer

So it becomes a variable-size window — but only if all values are positive. With negatives, the honest answer is a Kadane-style DP with a length bound:

// max sum of a subarray of length at most k, values may be negative
function maxSumAtMost(nums, k) {
  const n = nums.length, prefix = [0];
  for (let i = 0; i < n; i++) prefix.push(prefix[i] + nums[i]);

  const dq = [];                 // indices of increasing prefix values
  let best = -Infinity;
  for (let j = 1; j <= n; j++) {
    if (dq.length && dq[0] < j - k) dq.shift();               // enforce length ≤ k
    while (dq.length && prefix[dq[dq.length-1]] >= prefix[j-1]) dq.pop();
    dq.push(j - 1);
    best = Math.max(best, prefix[j] - prefix[dq[0]]);         // smallest prefix in range
  }
  return best;
}

Minutes 40–45 — complexity and edge cases: O(n) time and O(n) space; each index enters and leaves the deque once. Edge cases: k > n, all-negative arrays (the answer is the largest single element), and k = 1.

Score yourself on process, not just the code: did you read the constraints first? State the brute force? Get agreement before coding? Trace unprompted? Notice that negatives break the naive extension? That last one is the actual discriminator — the follow-up exists specifically to see whether you check the invariant before reusing the pattern.

2. Test yourself blind. Take twenty problem statements you have not seen, read only the first two sentences and the constraints, and write down the pattern without solving anything:

target: ≥ 80% correct pattern identification in under 60 seconds each

scoring:
  correct pattern, correct reason      2 points
  correct pattern, wrong reason        1 point   ← memorised, not recognised
  wrong pattern                        0 points

The "correct pattern, wrong reason" case is the one to watch. It means you matched a surface feature rather than the structure, and it is exactly what collapses when a problem is phrased unusually.

3. Drill the confusion pairs your log reveals. The classics:

ConfusionThe distinguishing question

The measurable goal for the whole track is not a problem count. It is: given an unfamiliar statement and its constraints, name the pattern and the target complexity within sixty seconds, and justify both. That is the skill the interview tests, so it is the skill to practise directly.

🎯 Key Takeaways

  • Interviews test roughly twenty reusable patterns, not three thousand problems — recognition transfers to unfamiliar problems, memorised solutions do not.
  • Read the constraints before the problem statement: n ≤ 10⁵ means O(n log n) or better, and that eliminates most patterns for free.
  • Know the arithmetic — ~10⁸ operations per second, so O(n²) at n = 10⁵ is ~100 seconds while O(n log n) is 0.02.
  • Small constraints are equally informative: n ≤ 20 means an exponential solution is intended, and hunting for a polynomial one wastes time.
  • "Contiguous" selects sliding window; remove it and the problem becomes a completely different one.
  • "Minimise the maximum" or "maximise the minimum" means binary search on the answer, because feasibility is monotonic even when the optimum is hard to find.
  • Negative values break the sliding-window invariant — the fallback is prefix sums plus a hash map.
  • Use the decision procedure: input shape → what is asked → does the constraint agree with my complexity. Step three catches the expensive mistakes.
  • Most hard problems are two familiar patterns composed, not one unfamiliar pattern.
  • State the brute force out loud in fifteen seconds — it guarantees a baseline and invites a hint.
  • Get agreement on the approach before coding; twenty minutes spent coding the wrong plan is unrecoverable.
  • Narrate continuously — silent thinking is unscoreable, and communication is an explicitly scored dimension.
  • Treat every hint as a signal you are off-track, not an interruption to argue with.
  • Trace your code on an example unprompted; finding your own bug scores better than the interviewer finding it.
  • A working O(n log n) solution explained well usually outscores a silent optimal one.
  • Practise one pattern at a time to learn it, then mixed randomised practice to learn recognition — the chapter heading gives away the answer otherwise.
  • After each problem, log the pattern and the phrase that signalled it; after thirty problems that log is a personalised list of what to drill.
  • Re-derive from templates three days later rather than re-reading solutions — if you cannot re-derive it, you learned an answer, not a pattern.
  • The measurable goal: given an unfamiliar statement and its constraints, name the pattern and target complexity within sixty seconds, and justify both.
