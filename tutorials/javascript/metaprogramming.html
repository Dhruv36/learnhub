Metaprogramming: Proxy & Reflect Production JavaScript

What you'll master: intercepting the language's own fundamental operations — property reads, writes, deletions, function calls, new — with Proxy; performing those same operations correctly from inside your interceptors with Reflect; and the real systems built on this pair: Vue 3's reactivity, validation layers, and mocking libraries. Prerequisites: Objects Deep Dive (property descriptors, internal methods) and Prototypes — a Proxy intercepts exactly the internal operations those lessons described.

Part 1 — The Mental Model: Every Object Operation Is a Method Call

The spec defines objects by a set of internal methods: [[Get]], [[Set]], [[Delete]], [[Has]], [[OwnPropertyKeys]], and so on. When you write obj.x, the engine calls obj.[[Get]]("x"). Normally you can't touch these. A Proxy is an object whose internal methods are your functions — the traps.

const target = { greeting: "hello" };

const handler = {
  get(target, prop, receiver) {                // trap for [[Get]] — fires on EVERY property read
    console.log(`read: ${String(prop)}`);
    return Reflect.get(target, prop, receiver); // then do the default behavior
  }
};

const proxy = new Proxy(target, handler);
proxy.greeting;        // logs "read: greeting", returns "hello"
proxy.missing;         // logs "read: missing", returns undefined — traps fire even for absent keys

// The target is untouched — reads through `target` itself never hit the trap:
target.greeting;       // no log. Proxies wrap; they don't modify.
The one-sentence model: a Proxy is a transparent wrapper where each of the ~13 internal object operations can be replaced by a function of yours; any trap you don't define falls through to the target's default behavior. Metaprogramming = your code running when the language, not the programmer, invokes an operation.

// A validating "set" trap — the classic first real use:
function typed(target, types) {
  return new Proxy(target, {
    set(t, prop, value, receiver) {
      if (prop in types && typeof value !== types[prop]) {
        throw new TypeError(`${String(prop)} must be a ${types[prop]}, got ${typeof value}`);
      }
      return Reflect.set(t, prop, value, receiver);  // MUST return true on success
    }
  });
}

const user = typed({ name: "Ada", age: 36 }, { name: "string", age: "number" });
user.age = 37;        // fine
user.age = "old";     // TypeError: age must be a number, got string
Traps have contracts. set and deleteProperty must return a boolean (falsy = a TypeError in strict mode). ownKeys must return only strings/symbols. Violate an invariant — e.g. report a non-configurable property as absent — and the engine itself throws. You can lie to callers, but not about the target's non-configurable/non-extensible facts.

Part 3 — Reflect: the Default Behaviors as Functions

Reflect has one static method per internal operation, with the same signature as the corresponding trap. That symmetry is the whole point: inside a trap, Reflect.get(...arguments) is exactly "do what would have happened without me".

Reflect.get(obj, "x");             // like obj.x
Reflect.set(obj, "x", 1);          // like obj.x = 1, but returns false instead of throwing (strict) on failure
Reflect.has(obj, "x");             // like "x" in obj
Reflect.deleteProperty(obj, "x");  // like delete obj.x, returns boolean
Reflect.ownKeys(obj);              // ALL own keys: string + symbol, enumerable or not
Reflect.construct(Fn, args);       // like new Fn(...args)
Reflect.defineProperty(obj, k, d); // like Object.defineProperty, but returns false instead of throwing

Why not just target[prop] inside a get trap? The receiver. If a proxy sits in a prototype chain, a getter on the target should run with this = the original object the read started on. Only Reflect.get(target, prop, receiver) forwards that correctly:

const base = {
  _name: "base",
  get name() { return this._name; }        // `this` should be whoever the read started on
};
const proxy = new Proxy(base, {
  get(t, prop, receiver) {
    return Reflect.get(t, prop, receiver); // receiver-aware: correct
    // return t[prop];                     // WRONG: getter would always see this === base
  }
});
const child = Object.create(proxy);
child._name = "child";
child.name;   // "child" with Reflect.get — would be "base" with t[prop]

Part 4 — Build It: a Reactivity System (How Vue 3 Works)

Let's build the real thing, incrementally: a reactive() that tracks which function read which property, and re-runs that function when the property changes.

// Step 1 — track the currently running effect
let activeEffect = null;
function effect(fn) { activeEffect = fn; fn(); activeEffect = null; }

// Step 2 — a dependency map: target → prop → Set of effects
const deps = new WeakMap();
function track(target, prop) {
  if (!activeEffect) return;
  let propMap = deps.get(target) ?? deps.set(target, new Map()).get(target);
  let set = propMap.get(prop) ?? propMap.set(prop, new Set()).get(prop);
  set.add(activeEffect);
}
function trigger(target, prop) {
  deps.get(target)?.get(prop)?.forEach(fn => fn());
}

// Step 3 — the proxy: reads track, writes trigger
function reactive(target) {
  return new Proxy(target, {
    get(t, prop, receiver) {
      track(t, prop);                                   // "this effect depends on this prop"
      return Reflect.get(t, prop, receiver);
    },
    set(t, prop, value, receiver) {
      const ok = Reflect.set(t, prop, value, receiver);
      trigger(t, prop);                                 // "re-run everything that depended on it"
      return ok;
    }
  });
}

// Step 4 — use it
const state = reactive({ count: 0 });
effect(() => console.log("count is", state.count));  // logs "count is 0" and REGISTERS the dependency
state.count++;                                        // logs "count is 1" — automatically

Every read inside effect registers a dependency; every write replays the dependents. That's the entire core of Vue 3's reactive() — the production version adds nested-object wrapping, array/collection handling, and batching, but no new ideas. Note the WeakMap keyed by target: when the object is garbage-collected, its whole dependency tree goes with it (see Memory Management).

Part 5 — Other Production Patterns

// 1. Negative array indices (à la Python):
const arr = new Proxy([10, 20, 30], {
  get(t, prop, r) {
    const i = Number(prop);
    if (Number.isInteger(i) && i < 0) return t[t.length + i];
    return Reflect.get(t, prop, r);
  }
});
arr[-1];   // 30

// 2. Throw on missing properties — kill silent undefined bugs in config objects:
function strict(obj) {
  return new Proxy(obj, {
    get(t, prop, r) {
      if (!(prop in t)) throw new ReferenceError(`No such config key: ${String(prop)}`);
      return Reflect.get(t, prop, r);
    }
  });
}

// 3. Revocable proxies — hand out access you can cancel later:
const { proxy, revoke } = Proxy.revocable({ secret: 42 }, {});
proxy.secret;   // 42
revoke();
proxy.secret;   // TypeError: revoked — the target is now unreachable through it
// 4. Auto-mocking / method-missing (how test spies work):
const api = new Proxy({}, {
  get(t, prop) {
    return (...args) => console.log(`called ${String(prop)}(${args.join(", ")})`);
  }
});
api.anything(1, 2);      // "called anything(1, 2)" — no such method ever existed
When NOT to reach for Proxy: a getter/setter pair (Object.defineProperty) covers one known property with zero overhead and full engine optimization. Proxies defeat inline caches — every trapped operation is a function call, roughly 2–10× slower than a plain property access. Use a Proxy when the property names are unknown ahead of time or you must intercept structural operations (delete, enumeration, in). That's also why Vue 3 moved to Proxy: defineProperty (Vue 2) couldn't see added/deleted keys or array index writes.

Part 6 — Edge Cases & Gotchas (the Senior Layer)

// 1. Built-ins with internal slots break through naive proxies:
const p = new Proxy(new Map([["a", 1]]), {});
p.get("a");   // TypeError! Map.prototype.get reads the [[MapData]] internal slot,
              // and `this` is the proxy, which has no such slot.
// Fix: in the get trap, bind functions to the target:
const fixed = new Proxy(new Map([["a", 1]]), {
  get(t, prop, r) {
    const v = Reflect.get(t, prop, r);
    return typeof v === "function" ? v.bind(t) : v;
  }
});
fixed.get("a");   // 1  — same trick needed for Date, Set, and DOM nodes

// 2. Identity: proxy !== target. Using objects as Map/Set keys or in === checks
//    breaks if one side holds the proxy and the other the raw target.
//    (Vue exposes toRaw() precisely for this.)

// 3. this inside target methods is the proxy — method calls route reads/writes
//    through your traps again. Usually what you want (nested reactivity), but it
//    can cause infinite recursion if a trap itself touches the proxy.

// 4. JSON.stringify(proxy) works — it triggers ownKeys + get traps — but
//    structuredClone(proxy) and postMessage throw: proxies can't be cloned.

Interview Questions

Beginner: What is a Proxy, and what happens for operations you don't write a trap for?

A Proxy wraps a target object and lets you intercept the language's fundamental operations on it — property reads, writes, deletion, enumeration, in checks, function calls, construction — with handler functions called traps. The key mental model is that every object operation you thought was syntax is actually an internal method call, and a Proxy lets you replace those internal methods.

Any operation you do not write a trap for forwards transparently to the target. So new Proxy(obj, {}) — an empty handler — produces something that behaves identically to obj for every operation. That default is what makes proxies practical: you intercept the two or three operations you care about and inherit correct behaviour for everything else, rather than having to reimplement an object from scratch.

The one thing that is not transparent is identity. proxy !== target, always, and there is no trap that can change that — identity comparison is not a trappable operation. This is the source of the most confusing proxy bugs: a value stored in a Set or used as a Map key under one reference will not be found under the other, and === checks that "should" pass silently fail.

In practice you use proxies at boundaries — a reactive state store, a config object that warns on unknown keys, a test spy, an API client that turns property access into method calls — rather than in ordinary application objects, because every intercepted operation costs a function call.

Beginner: What is Reflect and why does it mirror the Proxy traps?

Reflect exposes each of the object internal operations as a plain static function, with exactly the same name and signature as the corresponding Proxy trap. Reflect.get(target, prop, receiver) matches the get trap's parameters; Reflect.set matches set, and so on through all thirteen.

That symmetry is deliberate and it is the whole point. Inside a trap, calling the matching Reflect method with the trap's own arguments performs precisely the default behaviour. So the standard shape of a trap is: observe or adjust, then delegate.

The alternative — writing target[prop] or target[prop] = value by hand — looks equivalent and is not. It hard-codes assumptions the language does not make: it loses the receiver, so inherited accessors get the wrong this, and for set it gives you no way to report failure, since assignment evaluates to the assigned value rather than to whether the write succeeded. Reflect.set returns a boolean, which is exactly what the trap is required to return.

Reflect is also useful outside proxies, for the same reason: it turns operations that were previously statements or that threw on failure into functions that return booleans. Reflect.has(obj, key) is in as a function, and Reflect.defineProperty returns false where Object.defineProperty throws.

Mid: Why must you pass receiver to Reflect.get/Reflect.set?

receiver is the object the operation originally started on, which is not necessarily the target. The two diverge when the proxy sits in a prototype chain: read a property on a child object, the lookup walks up to the proxied prototype, and the trap fires with target being the prototype but receiver being the child.

It matters when the property is an accessor. A getter's this is supposed to be the object the access started from, so that get fullName() { return this.first + " " + this.last; } reads the child's fields. Writing target[prop] inside the trap hard-codes this = target, so the getter reads the prototype's fields instead — usually undefined, and silently. Reflect.get(target, prop, receiver) preserves the correct binding.

The same applies to set, with a sharper failure. Without the receiver, a setter inherited through the proxy writes onto the target rather than onto the instance, so every instance that inherits from that prototype ends up sharing one value. That presents as "changing one object changed them all", which sends people looking for an aliasing bug that does not exist.

The general rule, and the one worth stating in an interview: forward every trap argument to the matching Reflect method, always. The arguments exist because the specification needs them. Dropping one produces behaviour that is correct in the flat, non-inherited case you tested and wrong in the prototype case you did not — which is why this bug tends to survive review and appear later.

Mid: Sketch how Vue-3-style reactivity uses Proxy.

State is wrapped in a Proxy with two meaningful traps. The get trap records a dependency: "the effect currently running depends on this (target, key)". The set trap looks up the effects registered for that key and re-runs them.

The bookkeeping is a WeakMap from target object to a Map from key to a Set of effects. WeakMap at the outer level matters: when a state object becomes garbage, its entire dependency table goes with it, so there is nothing to clean up manually and no leak from long-lived subscriptions to short-lived state.

Rendering is itself just an effect. So a component that reads state.count during render subscribes to that exact key as a side effect of reading it — no dependency array, no explicit subscription — and writing state.count re-runs precisely the components that read it. That is the entire mechanism, and the reason the API feels like it has no API.

The reason Vue 3 rewrote this on Proxy is the limitation of Vue 2's Object.defineProperty approach, which had to walk the object at creation time and install an accessor per known key. Adding a new property, deleting one, or writing to an array index by position were all undetectable, which is why Vue 2 shipped Vue.set and Vue.delete as workarounds. Proxy traps the operations structurally, so those special cases disappear. The costs are that proxies are not supported in IE at all, and that deep reactivity requires wrapping nested objects lazily on access rather than eagerly.

Senior: Why does new Proxy(new Map(), {}).get("k") throw, and how do you fix it?

Map.prototype.get reads the [[MapData]] internal slot of its this. Called through the proxy, this is the proxy object, and a proxy has no internal slots of its own. Crucially, internal-slot access is not a trappable operation — there is no handler you can write to forward it — so the method throws TypeError: Method Map.prototype.get called on incompatible receiver.

Note what this reveals about the "empty handler is transparent" rule: it is true for every operation the Proxy specification defines, and internal slots are outside that set. The transparency is real but bounded, and the boundary is exactly the built-ins implemented with hidden state.

The fix is to bind methods to the raw target in the get trap:

  const wrap = (map) => new Proxy(map, {
    get(target, prop, receiver) {
      const value = Reflect.get(target, prop, receiver);
      return typeof value === "function" ? value.bind(target) : value;
    },
  });

The same applies to Set, WeakMap, Date, typed arrays, promises and DOM nodes — anything holding internal state. Two consequences follow that are worth raising unprompted. Binding means the method now runs against the target, so any mutation it performs bypasses your traps entirely — a reactive Map needs the trap to return an instrumented wrapper for set and delete, not a bound original, which is precisely what Vue's collection handlers do. And value.bind(target) allocates a new function on every access, so caching the bound methods matters if the object is read in a loop.

Senior: What are proxy invariants, and why do they exist?

Invariants are consistency rules the engine enforces on trap results by checking them against the target's actual property descriptors. A has trap cannot report a non-configurable own property as absent. A get trap cannot return a value different from a non-configurable, non-writable own property's real value. An ownKeys trap cannot omit a non-configurable key, or invent extra keys on a non-extensible target. Violating any of them throws a TypeError at the point of the operation — not at proxy creation.

They exist so that the guarantees the language already makes remain guarantees in the presence of a proxy. Object.freeze promises that a property's value cannot change. If a proxy could report a different value on each read for a frozen property, that promise would hold only for objects you could prove were not proxied — and since a proxy is indistinguishable from its target by design, you could never prove it. Freezing would become meaningless, and so would every security or correctness argument built on it.

This is the same reasoning that makes proxy transparency safe in the first place. Code that receives an object it did not create can still rely on descriptor-level facts about it. Without invariants, a hostile or merely buggy proxy could make a frozen configuration object appear to change under a consumer that had checked it, and the consumer would have no defence.

The practical consequence is that a trap must respect the target's real descriptors rather than lying about them. If you need a trap to report something the target contradicts, the answer is to change the target — or to use a plain object as the target and manage the real data in a closure, which is why a proxy over an empty object with the state held separately is a common pattern. It also means invariant violations surface at runtime in whichever operation triggered them, so they are easy to miss in testing and worth a deliberate test when a trap does anything conditional.

1 (easy): Create a proxy that logs every property read on an object, then returns the real value.
Solution 
const logged = new Proxy(obj, {
  get(t, prop, r) { console.log("read", prop); return Reflect.get(t, prop, r); }
});
2 (easy): Make a proxy where reading any missing property returns the string "N/A" instead of undefined.
Solution 
const withDefault = new Proxy(obj, {
  get(t, prop, r) { return prop in t ? Reflect.get(t, prop, r) : "N/A"; }
});
// `prop in t` (not truthiness of the value!) so stored falsy values still come through.
3 (medium): Build readonly(obj): reads work, but any write or delete throws a descriptive TypeError.
Solution 
function readonly(obj) {
  return new Proxy(obj, {
    set(t, prop)            { throw new TypeError(`Cannot set "${String(prop)}": object is read-only`); },
    deleteProperty(t, prop) { throw new TypeError(`Cannot delete "${String(prop)}": object is read-only`); },
    defineProperty(t, prop) { throw new TypeError(`Cannot define "${String(prop)}": object is read-only`); }
  });
}
// Unlike Object.freeze, the original stays mutable for whoever holds the raw reference.
4 (medium): Create a case-insensitive object: o.NAME, o.Name, and o.name all reach the same property, for get, set, and in.
Solution 
function caseInsensitive(obj) {
  const norm = p => typeof p === "string" ? p.toLowerCase() : p;
  return new Proxy(obj, {
    get: (t, p, r)    => Reflect.get(t, norm(p), r),
    set: (t, p, v, r) => Reflect.set(t, norm(p), v, r),
    has: (t, p)       => Reflect.has(t, norm(p))
  });
}
5 (medium): Implement hideUnderscored(obj): properties starting with _ are invisible — absent from Object.keys, in, and reads return undefined.
Solution 
function hideUnderscored(obj) {
  const hidden = p => typeof p === "string" && p.startsWith("_");
  return new Proxy(obj, {
    get: (t, p, r) => hidden(p) ? undefined : Reflect.get(t, p, r),
    has: (t, p)    => hidden(p) ? false : Reflect.has(t, p),
    ownKeys: t     => Reflect.ownKeys(t).filter(p => !hidden(p))
  });
}
// Works because _props are configurable — hiding non-configurable keys would violate invariants.
6 (hard): Build tracked(fn) using the apply trap: the returned function works normally but records { args, result, ms } of every call in a .calls array.
Solution 
function tracked(fn) {
  const calls = [];
  const proxy = new Proxy(fn, {
    apply(t, thisArg, args) {
      const start = performance.now();
      const result = Reflect.apply(t, thisArg, args);
      calls.push({ args, result, ms: performance.now() - start });
      return result;
    },
    get(t, p, r) { return p === "calls" ? calls : Reflect.get(t, p, r); }
  });
  return proxy;
}
const add = tracked((a, b) => a + b);
add(2, 3); add(10, 5);
add.calls.length;   // 2 — this is the skeleton of every test-spy library.
7 (hard): Extend Part 4's reactive() so nested objects are reactive too: state.user.name = "x" must trigger effects that read state.user.name.
Solution 
const proxyCache = new WeakMap();
function reactive(target) {
  if (proxyCache.has(target)) return proxyCache.get(target);  // stable identity per target
  const proxy = new Proxy(target, {
    get(t, prop, receiver) {
      track(t, prop);
      const value = Reflect.get(t, prop, receiver);
      return typeof value === "object" && value !== null
        ? reactive(value)          // wrap lazily, on read — not eagerly on creation
        : value;
    },
    set(t, prop, value, receiver) {
      const ok = Reflect.set(t, prop, value, receiver);
      trigger(t, prop);
      return ok;
    }
  });
  proxyCache.set(target, proxy);
  return proxy;
}
// The cache is essential: without it, state.user !== state.user (new proxy per read),
// breaking === checks and dependency identity. This is exactly Vue 3's approach.
8 (hard): Why does this loop forever, and how do you fix it while keeping the logging? 
const p = new Proxy({ n: 1 }, {
  get(t, prop, r) { console.log("read", prop, "on", p.n); return Reflect.get(t, prop, r); }
});
Solution 
// p.n inside the trap goes THROUGH the proxy → fires the get trap again → reads p.n → …
// infinite recursion, stack overflow on the first read.
// Fix: read from the raw target inside the trap — t.n, not p.n:
const p = new Proxy({ n: 1 }, {
  get(t, prop, r) { console.log("read", prop, "on", t.n); return Reflect.get(t, prop, r); }
});
// General rule: trap bodies must only touch the target; touching the proxy re-enters the traps.

🎯 Key Takeaways

  • Every object operation is an internal method call, and a Proxy lets you replace those methods — the syntax was always a function call underneath.
  • Untrapped operations forward transparently, so new Proxy(obj, {}) behaves like obj — you intercept two operations and inherit correctness for the rest.
  • Identity is never transparent: proxy !== target always, and no trap can change it — the source of the most confusing Map/Set/=== bugs.
  • Delegate from every trap to the mirror-image Reflect method, passing all the trap's arguments.
  • receiver is the object the operation started on, which is not the target when the proxy sits in a prototype chain.
  • Dropping receiver breaks inherited accessors silently — getters read the prototype's fields, and setters write onto the prototype so every instance shares one value.
  • Reflect.set returns a boolean; plain assignment does not, which is exactly what the set trap must return.
  • set, deleteProperty and defineProperty traps must return booleans — returning nothing reads as failure in strict mode and throws.
  • Invariants are engine-enforced: a trap may not contradict the target's non-configurable or non-extensible facts, and violations throw at the operation, not at construction.
  • Invariants exist so Object.freeze keeps meaning through a proxy you cannot detect — without them, no descriptor-level guarantee would survive.
  • Reactivity is two traps and two maps: get tracks (effect ← key), set triggers, and rendering is just another effect.
  • Key the dependency table with a WeakMap so a discarded store takes its subscriptions with it.
  • Proxy replaced defineProperty in Vue 3 because added keys, deleted keys and index writes are undetectable with accessors — that is why Vue.set existed.
  • Built-ins with internal slots throw through a proxy — internal-slot access is not trappable, so Map, Set, Date and DOM nodes need methods bound to the raw target.
  • A bound method bypasses your traps, so a reactive collection needs instrumented wrappers for its mutating methods, not bound originals.
  • Trap bodies must touch the target, never the proxy, or you recurse infinitely.
  • Proxies cost a function call per operation — wrap boundaries such as stores, config and spies, never inner loops; for one known property a plain getter wins.
  • Proxy.revocable is how you withdraw a capability you handed to code you do not control.
