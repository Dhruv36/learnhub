Builds, Artifacts & Versioning Building & Testing

What you'll master: the guarantee that makes every other check meaningful — the bytes you tested must be the bytes you deploy, which means building once and promoting a digest, never a tag, after the incident where staging and production ran different glibc versions from an identical commit hash and cost three hours to explain; why latest and even v2.1.0 are mutable pointers and what to use instead; reproducible builds — the four things that break them (timestamps, file ordering, locale, network) and what byte-identical rebuilds actually buy you, demonstrated with a diffoscope run that found a 140-byte difference and a build that embedded the runner's hostname; how to version a service, where the commit is the version and semver is mostly a lie, versus a library where semver is a contract; the question every incident starts with — what exactly is running? — and the build-metadata plumbing that answers it in one HTTP call; artifact retention that does not delete the image production is running (measured: a cleanup job removed an image running in three regions); the strict separation of config from artifact, including the one legitimate exception; and the provenance you should record at build time so supply-chain work later is plumbing rather than archaeology. Prerequisites: Anatomy of a Pipeline and Pipelines as Code.

Part 1 — Build Once, Promote the Digest

Lesson 1 named immutability as one of the five guarantees. This is how it is implemented, and the mistake it prevents is the most expensive one in this lesson.

THE INCIDENT, WHICH LOOKS IMPOSSIBLE UNTIL YOU SEE THE PIPELINE

  09:12  a deploy of commit 4f2a91c to production
  09:14  production crashes on startup: symbol lookup error, libc
  09:15  "but staging is running 4f2a91c and it's fine"
  12:20  root cause found

  THE PIPELINE:
    job build-and-test   -> docker build ... (image A) -> tests pass
    job deploy-staging   -> docker build ... (image B) -> deployed
    job deploy-prod      -> docker build ... (image C) -> deployed

  three builds of the same commit, hours apart. Between B and C the
  base image `node:20-slim` published a new patch: glibc 2.36 -> 2.37.
  A native dependency compiled against the older one.

  Commit hash: IDENTICAL. Artifacts: DIFFERENT. This is why the first
  three hours were spent looking in the wrong place entirely.
ReferenceMutable?What it identifiesUse for
app:latestYes — constantlyWhatever was pushed most recentlyNothing in a pipeline. Local convenience only
app:v2.1.0Yes — a tag can be re-pushedWhatever that tag currently points atHuman-readable release naming

THE CORRECT SHAPE — ONE BUILD, ONE DIGEST, THREE PROMOTIONS

  jobs:
    build:
      outputs:
        digest: ${{ steps.push.outputs.digest }}
      steps:
        - id: push
          uses: docker/build-push-action@v6
          with:
            push: true
            tags: |
              registry/app:${{ github.sha }}
              registry/app:latest
            provenance: true
            sbom: true

    test:
      needs: [build]
      steps:
        - run: ./ci/test.sh "registry/app@${{ needs.build.outputs.digest }}"

    staging:
      needs: [build, test]
      steps:
        - run: ./ci/deploy.sh staging "registry/app@${{ needs.build.outputs.digest }}"

    production:
      needs: [staging]
      steps:
        - run: ./ci/deploy.sh production "registry/app@${{ needs.build.outputs.digest }}"

  the tags exist for HUMANS. Every machine reference is the digest.
🔑 "Promotion" means changing which environment points at a digest — never rebuilding. If your promotion step contains the word build, you do not have promotion; you have three independent releases that happen to share a commit message. The test for this is one command: compare the digest running in production with the digest the tests passed against. If your tooling cannot answer that, that is the finding.

1.1 What counts as "the artifact"

  THE ARTIFACT IS EVERYTHING THAT VARIES WITH THE COMMIT:

    ✅ the application image (by digest)
    ✅ database migrations         (they ship WITH the code that needs them)
    ✅ static assets and their content hashes
    ✅ the deployment manifest TEMPLATE (not its values)
    ✅ an SBOM and provenance attestation for that digest

  NOT THE ARTIFACT — these vary by ENVIRONMENT, not by commit:
    ❌ config values, endpoints, feature-flag defaults
    ❌ secrets (never, under any circumstances, baked in)
    ❌ replica counts, resource limits, scaling thresholds

  THE TEST: if changing it should NOT require a new build, it is config.
  If changing it MUST produce a new artifact, it is part of the artifact.

Part 2 — Reproducible Builds

A build is reproducible when the same source produces byte-identical output, on any machine, at any time. Most builds are not, and the reasons are mundane.

Breaks reproducibilityTypical formFix
TimestampsBuild time embedded in archives, file mtimes, image metadataSOURCE_DATE_EPOCH from the commit date; --rewrite-timestamp style flags
File orderingFilesystem iteration order differs across machinesSort inputs explicitly before archiving
Locale and environmentSorting, number formatting, hostname, username, pathsPin LC_ALL=C, TZ=UTC; strip build paths
Network resolutionAn unpinned dependency, a floating base image, a CDN downloadLockfiles; digest-pinned base images; vendored or cached deps
RandomnessGenerated IDs, nonces, ordering by hash seedSeed deterministically; sort outputs
ParallelismConcurrent compilation writing in nondeterministic orderDeterministic linkers/archivers; sort before combining
FINDING THE DIFFERENCE — diffoscope IS THE TOOL FOR THIS

$ git checkout 4f2a91c
$ docker build -t probe:a . && docker save probe:a > a.tar
$ # ... on a different machine, a day later ...
$ docker build -t probe:b . && docker save probe:b > b.tar
$ sha256sum a.tar b.tar
  9e1c4a…  a.tar
  41ab77…  b.tar                                 NOT reproducible

$ diffoscope a.tar b.tar | head -30
  --- a.tar
  +++ b.tar
  ├── layer.tar
  │ ├── ./app/build-info.json
  │ │ @@ -1,5 +1,5 @@
  │ │ -  "built_at": "2026-08-19T04:11:22Z",
  │ │ +  "built_at": "2026-08-21T09:02:41Z",
  │ │ -  "built_on": "runner-ip-10-2-3-44",
  │ │ +  "built_on": "runner-ip-10-2-7-91",
  │ ├── ./app/node_modules/.package-lock.json
  │ │ @@ -812,7 +812,7 @@
  │ │ -      "version": "2.2.1",
  │ │ +      "version": "2.2.3",            <-- an unpinned transitive dep
  Total difference: 140 bytes + one dependency version

  TWO SEPARATE PROBLEMS, TWO SEPARATE FIXES:
    the timestamps/hostname: cosmetic, but they defeat cache reuse and
      make verification impossible -> move them OUT of the artifact and
      into registry LABELS/annotations, or set SOURCE_DATE_EPOCH
    the dependency drift: a REAL correctness problem -> the lockfile was
      not being respected (npm install, not npm ci)

THE PRACTICAL RECIPE — 90% OF THE BENEFIT

  # Dockerfile
  FROM node:20-slim@sha256:cb1e5f3ac0…      # digest, not a tag
  ENV TZ=UTC LC_ALL=C
  COPY package.json package-lock.json ./
  RUN npm ci --ignore-scripts               # ci, NOT install: honours the lock
  COPY . .
  RUN npm run build

  # build with a fixed timestamp derived from the commit
  export SOURCE_DATE_EPOCH="$(git log -1 --pretty=%ct)"
  docker buildx build \
      --build-arg SOURCE_DATE_EPOCH \
      --output type=registry,rewrite-timestamp=true \
      -t registry/app:"$GIT_SHA" .

  and put the volatile metadata where it does NOT change the bytes:
  --label org.opencontainers.image.revision="$GIT_SHA" \
  --label org.opencontainers.image.created="$BUILD_TIME"
💡 You do not need perfect reproducibility to get most of the value. The point of chasing it is not a certificate; it is that investigating the differences finds real bugs — unpinned dependencies, floating base images, environment leakage. In the measured case, the exercise took a team from "we cannot explain why the artifact differs" to a pinned, lock-respecting build, and the 140 cosmetic bytes were the least valuable part of the finding.

FOR A SERVICE, THE COMMIT IS THE VERSION

   │      └────── 17 commits since the tag

  a service's "2.5.0" answers no question anyone actually asks.
  The questions that DO get asked, at 3am:

  feat!: remove deprecated send() overload  -> MAJOR
  (conventional commits + release-please / semantic-release)

  the value is not the automation; it is that the RULES are written
  down and applied consistently, instead of being re-argued per release.

RETENTION — AND THE CLEANUP THAT DELETED PRODUCTION'S IMAGE

  THE INCIDENT
    a retention policy: "delete untagged images older than 30 days"
    production deployed BY DIGEST, so its image had no tag once the
    commit-SHA tag was rotated by a separate cleanup rule
    the nightly job deleted it
    nothing broke — until a node was replaced 6 days later and could not
    pull. Then three regions could not scale, during peak.

  THE RULES THAT PREVENT IT
   1. NEVER delete a digest that is REFERENCED BY A RUNNING WORKLOAD.
      Build the in-use set from the clusters, not from tags:
        kubectl get pods -A -o jsonpath='{..image}' | tr ' ' '\n' | sort -u
   2. Keep the last N releases per environment regardless of age.
   3. Protect tags that matter (immutable tags where the registry
      supports it, so a tag can never be re-pointed).
   4. Dry-run first, and log what WOULD be deleted for a week before
      deleting anything.

  MEASURED COST OF GETTING RETENTION RIGHT (a 60-service estate)
    before: 41 TB of images, $940/month, oldest artifact 4 years
    after : 6.2 TB, $142/month
      policy: keep 10 most recent per service + anything in use +
              anything tagged as a release, delete the rest after 45 days

Part 5 — Config Is Not Part of the Artifact

The same artifact must run in every environment. If it cannot, then either you are building per environment (Part 1's incident) or configuration has leaked into the build.

  ❌ BAKED IN — a different image per environment, by construction
     ENV API_URL=https://api.staging.acme.com
     ENV FEATURE_NEW_CHECKOUT=true
     COPY config/production.yml /app/config.yml

  ✅ INJECTED AT RUNTIME
     env:
       - name: API_URL
         valueFrom: { configMapKeyRef: { name: api-config, key: url } }
       - name: DB_PASSWORD
         valueFrom: { secretKeyRef: { name: db, key: password } }

  AND VALIDATE CONFIG AT STARTUP, LOUDLY — a missing variable should
  crash the process immediately, not produce an empty string that
  reaches a database connection string:
     API_URL = must_get_env("API_URL")        # raises if unset/empty
CategoryWhere it livesRotates without a build?
Endpoints, timeouts, pool sizesConfigMap / environment / parameter storeYes
SecretsA secret manager, injected at runtimeYes — and it must
Feature-flag defaultsConfig; live values in the flag serviceYes
Replica counts, limits, autoscalingDeployment manifest values per environmentYes
MigrationsThe artifact — they belong to the codeNo
Compiled-in frontend valuesThe artifact — the legitimate exception belowNo
THE ONE LEGITIMATE EXCEPTION, AND HOW TO KEEP IT HONEST

  A browser bundle is compiled: environment values are inlined at build
  time and cannot be injected into a static file server later. So a
  per-environment build looks unavoidable.

  IT IS NOT. Two standard ways out:

  1. RUNTIME CONFIG FETCH — the bundle reads /config.json on startup:
       // index.html loads this before the app boots
       fetch('/config.json').then(r => r.json()).then(boot)
     one artifact; the file is served per environment.

  2. PLACEHOLDER SUBSTITUTION AT CONTAINER START — build with tokens,
     replace them in the entrypoint:
       RUN npm run build              # emits __API_URL__ in the bundle
       ENTRYPOINT ["/entrypoint.sh"]  # sed -i "s|__API_URL__|$API_URL|g"
     still one image; substitution happens at boot.

  If you genuinely must build per environment, then be explicit about
  what you have given up: the artifact tested is not the artifact shipped,
  and you must test EACH build. Most teams doing this have not noticed
  they made that trade.

Everything supply-chain security asks for later is cheap if the build recorded it and expensive if it did not. Two artifacts are worth generating on every build.

❌ Three separate builds of the same commit, deployment by latest, a version number bumped by hand in a release meeting, no build metadata at runtime, a retention job that deletes by tag, config baked into images, and no SBOM. Staging and production run different bytes from an identical commit hash, so when a base-image patch changes glibc between two builds the investigation spends three hours in the wrong place. Config is baked in, so a timeout change requires a rebuild and a full re-test, and the frontend has a separate image per environment that nobody realises is untested. And when a CVE lands in a common library, answering "which services ship it?" takes three days of grepping repositories.

Build once, push, and pass the digest through test, staging and production so promotion is a pointer change and never a rebuild — then verify by comparing the digest running in production with the digest the tests passed against. Compute the retention in-use set from the clusters rather than from tags, keep the last N releases per environment, and dry-run for a week before deleting anything — one estate went from 41 TB and $940/month to 6.2 TB and $142. Keep config out of the artifact, including the frontend, via a runtime /config.json or entrypoint substitution. And emit an SBOM and provenance attestation per digest, which turns the next CVE scramble from three days into six minutes.

Interview Questions

Beginner: What does "build once, deploy everywhere" mean and why does it matter?

It means the pipeline produces one artifact from a commit, tests that artifact, and then promotes the identical artifact through staging and production. Promotion changes which environment points at it; it never rebuilds.

It matters because it is the only way the test result applies to the thing you shipped. If each environment builds its own image, the tests validated bytes that no longer exist anywhere.

The concrete failure: one team built separately for test, staging and production. Between the staging and production builds, the node:20-slim base image published a patch that moved glibc from 2.36 to 2.37, and a native dependency crashed only in production. The commit hash was identical in both environments, which is exactly why it took three hours to find — everyone was looking for a code difference that did not exist.

The implementation detail that makes it real: promote by digest (app@sha256:…), not by tag. A tag is a mutable pointer; a digest is the bytes.

Beginner: How should you version a service, and is it different from versioning a library?

Yes, and conflating them causes a lot of pointless ceremony.

A library's version is a compatibility contract with consumers who upgrade on their own schedule. SemVer means something there: MAJOR signals a breaking change, MINOR an additive one, PATCH a fix. It is worth automating from conventional commits so the rules are applied consistently rather than re-argued each release.

A service's version is an identity: which code is this? Nobody consumes your service by version number — they call its API, which has its own versioning. So the useful version is the commit SHA, optionally dressed up with git describe --tags --always to give humans something like v2.4.0-17-g4f2a91c.

The test I would offer: a service version number is useful only if it answers a question someone actually asks. The real questions at 3am are "what code is running?", "is it what we tested?", "when was it deployed?" and "what changed since the last deploy?" — and all four are answered by a commit SHA, an image digest and deploy metadata, not by "2.5.0".

Mid: What makes a build non-reproducible, and why should you care?

Four common causes: timestamps baked into archives and image metadata, file ordering from filesystem iteration, environment leakage (locale, timezone, hostname, build paths), and network resolution — an unpinned dependency or floating base image resolving differently on different days. Randomness and nondeterministic parallel output add a long tail.

Why care: not for a certificate. Three practical reasons:

  • Investigating the differences finds real bugs. In the measured case, diffoscope showed 140 bytes of timestamp and hostname noise — and also a transitive dependency that had moved from 2.2.1 to 2.2.3 because CI ran npm install rather than npm ci. That second one is a correctness problem hiding behind a cosmetic one.
  • Verification. If a build is reproducible, you can rebuild a historical commit and confirm the artifact in production really came from it — which is the foundation of any supply-chain claim.
  • Caching. Non-deterministic outputs defeat layer and build caches, so builds are slower than they need to be.

The pragmatic recipe gets most of the way: pin base images by digest, use lockfile-respecting installs, set SOURCE_DATE_EPOCH from the commit date, pin TZ and LC_ALL, and move volatile metadata into OCI labels rather than into the bytes.

Mid: A cleanup job deleted an image that production was running. How do you design retention properly?

The root cause is that the policy reasoned about tags while production referenced a digest. Once the commit-SHA tag was rotated, the digest looked untagged and matched "delete untagged images older than 30 days". Nothing broke immediately — the running nodes had the image cached — so it was discovered days later when a node was replaced during peak and three regions could not pull.

RuleWhy
Never delete a digest referenced by a running workloadBuild the in-use set from the clusters (kubectl get pods -A -o jsonpath='{..image}'), not from registry metadata
Keep the last N releases per service per environment, regardless of ageRollback targets must exist; "old" is not the same as "unneeded"
Protect release tags, and use immutable tags where supportedPrevents both deletion and silent re-pointing
Dry-run and log for a week before deletingThe cheapest possible way to discover a rule like this one
Alert on deletions that touch anything referenced in the last 90 daysCatches the case where the in-use set is computed wrongly

Worth adding: retention is worth doing — the same estate went from 41 TB and $940/month to 6.2 TB and $142/month. The lesson is not "keep everything", it is that the keep-rules must be derived from what is running and what you might roll back to, not from tag age.

Senior: Your frontend team says they must build a separate bundle per environment. How do you respond?

I would start by agreeing with the constraint and disagreeing with the conclusion. It is true that a browser bundle is compiled and that environment values get inlined at build time. It does not follow that you need a build per environment — and the cost of that choice is usually unexamined.

What the per-environment build actually costs: the bundle tested in staging is not the bundle shipped to production. Every guarantee from the test stage evaporates, and any difference between the two builds — a dependency resolving differently, a base image patch — is invisible because the commit hash matches.

Two standard ways out, both single-artifact:

  • Runtime config fetch: the app loads /config.json before booting. One bundle everywhere; the JSON is served per environment. Costs one extra request, cacheable, and it also lets you change an endpoint without a release.
  • Placeholder substitution at container start: build with tokens like __API_URL__ and replace them in the entrypoint. One image; substitution happens at boot. Useful when you cannot add a startup request.

If they still need per-environment builds — genuinely happens with some static-hosting setups and strict CSP requirements — then I would insist on making the trade explicit: each build gets its own test run, the production build is smoke-tested before traffic reaches it, and both builds' digests are recorded so an incident can tell them apart. What I would not accept is quietly having two artifacts and one test result.

Senior: A critical CVE is announced in a widely used library. Walk through how you determine exposure across 60 services.

The answer depends entirely on what the builds recorded, which is why this question is really about work done months earlier.

With SBOMs and provenance per digest (the prepared case):

  1. Enumerate what is running — the digests actually deployed in each environment, from the clusters, not from a spreadsheet of services.
  2. Query each digest's SBOM for the package and version. This is a loop over cosign download sbom and jq. Measured: 6 minutes, and complete — including transitive and vendored dependencies, which is exactly what lockfile-grepping misses.
  3. Assess reachability: shipping a vulnerable version is not the same as being exploitable. Which services expose the affected code path, and are they internet-facing?
  4. Patch and roll out in exposure order, using the same build-once-promote path; confirm by re-querying SBOMs of the new digests.
  5. Prove it: the audit answer is "these digests contained it, these are the replacements, here is the query", not "we think we got them all".

Without SBOMs: rebuild or inspect 60 repositories' lockfiles, miss anything vendored or transitively bundled, and answer with a caveat. Measured on a real event: three days, and the answer was still hopeful rather than complete.

The organisational point I would make afterwards: the fix is not a better scanner, it is that every build emits an SBOM and a provenance attestation attached to the digest. That is two lines in a shared workflow (reusable workflows make it one change for all 60), and it converts the next event from an archaeology project into a query.

  echo "protected: $(wc -l < /tmp/protected.txt) digests"

  for repo in $(crane catalog registry.acme.io); do
    crane ls "registry.acme.io/$repo" --full-ref | while read -r ref; do
      digest=$(crane digest "$ref")

      fi
    done

🎯 Key Takeaways

  • Build once, promote the digest. Three builds of one commit let a base-image patch move glibc between staging and production — identical commit hash, different bytes, three hours to explain.
  • Tags are mutable pointers; digests are bytes. Deploy by @sha256:… and keep tags for humans; latest belongs nowhere in a pipeline.
  • If a promotion step contains the word build, you do not have promotion — you have independent releases that share a commit message.
  • The audit is one command: compare the digest running in production with the digest the tests passed against. If your tooling cannot answer it, that is the finding.
  • Migrations belong to the artifact; config does not. The test: if changing it should not require a new build, it is config.
  • Four things break reproducibility: timestamps, file ordering, environment leakage (locale, TZ, hostname, paths) and network resolution.
  • Chase reproducibility for what the investigation finds, not for a certificate — diffoscope surfaced 140 bytes of cosmetic noise and a transitive dependency drifting because CI ran npm install instead of npm ci.
  • The practical recipe: digest-pinned base images, lockfile-respecting installs, SOURCE_DATE_EPOCH, TZ=UTC/LC_ALL=C, and volatile metadata in OCI labels rather than in the bytes.
  • Run the reproducibility check as a nightly warning, not a gate — a hard gate here gets routed around within a quarter.
  • For a service, the commit is the version; semver is a compatibility contract and services have no consumers who upgrade on their own schedule. git describe --tags --always gives humans a readable form.
  • For libraries, semver is a real promise — automate it from conventional commits so the rules are applied rather than re-argued.
  • Expose /internal/buildinfo: commit, digest, build time, CI run URL. It answers the first question of every incident in one HTTP call.
  • Query pods, not the load balancer — during a rollout the service endpoint answers from whichever replica served the request, which is how "the fix is deployed" gets said too early.
  • Retention must be computed from what is running, not from tag age: a policy that deleted "untagged images older than 30 days" removed the digest production was running, discovered days later when a node was replaced during peak.
  • Protect the in-use set from every cluster including DR, the last N deploys per environment as rollback targets, and release-tagged digests — then dry-run for a week and diff the outputs before deleting anything.
  • Retention done right is worth real money: 41 TB and $940/month → 6.2 TB and $142/month, with zero incidents.
  • Config injected, never baked, and validated loudly at startup so a missing value crashes the process instead of becoming an empty string in a connection string.
  • The frontend exception is not real: a runtime /config.json fetch or entrypoint placeholder substitution keeps one artifact — and a per-environment bundle means the tested bundle is not the shipped one.
  • A secret baked into a layer is compromised — deleting the line later does not remove it from image history, registry copies or node caches. Rotate, then fix the build.
  • Emit an SBOM and provenance per digest, generated from the final image rather than the source tree: the next CVE exposure question takes 6 minutes and is complete instead of three days and hopeful.
