Pipeline Performance Pipeline Engineering

What you'll master: the measurement that makes every optimisation decision obvious — feedback time is queue + setup + critical path + upload, and teams routinely optimise the smallest term, with one measured pipeline reporting "38 minutes" of which 6m20s was waiting for a machine and 4m50s was uploading artifacts nobody downloaded; the four levers in the order that pays — don't run it, run it in parallel, make it start faster, make the work faster — because the first two are configuration and the last is engineering; caching that is honest about its own value, including the cache that took 71 seconds to restore and saved 48; sharding arithmetic, where splitting by file count left one shard carrying 42% of the runtime and duration-based splitting plus Amdahl's law give you the optimum shard count rather than a guess; queue time and capacity, the term that is invisible in every dashboard and was the largest single component in three of four pipelines audited; and how to keep a fast pipeline fast — a duration budget enforced in CI, so the regression that adds 90 seconds is caught in the PR that adds it rather than a year later. Prerequisites: Anatomy of a Pipeline, Test Strategy and Containers in CI.

Part 1 — Measure First: Feedback Time Is a Sum

"The pipeline takes 38 minutes" is not a measurement; it is four measurements added together, and they have completely different fixes.

DECOMPOSE BEFORE YOU OPTIMISE

  feedback time = QUEUE + SETUP + CRITICAL PATH + PUBLISH

  MEASURED, ONE PIPELINE, 400 RUNS

    term                          p50       p90     fix lives in
    ------------------------------------------------------------------
    queue (waiting for a runner)  6m20s   19m00s    capacity, concurrency
    setup (checkout, toolchain,
      cache restore)              4m10s    5m30s    images, caching
    critical path (the longest
      chain of actual work)      22m40s   31m00s    parallelism, the work
    publish (artifact upload,
      reports, notifications)     4m50s    7m10s    upload less
    ------------------------------------------------------------------
    TOTAL                        38m00s   62m40s

  WHAT THE TEAM HAD BEEN OPTIMISING: the test suite (part of the
  critical path). What they had never measured: 6m20s of queue and
  4m50s of publish — 29% of feedback time, in configuration.

Part 2 — The Four Levers, In Order

#LeverTypical gainEffortMechanism
1Don't run it30–80%HoursPath filters, concurrency cancellation, test-impact selection, skipping unchanged targets
2Run it in parallel2–4×DaysFan-out, matrix sharding, splitting the critical path
3Make it start faster10–30%DaysPrebuilt images, cache tuning, shallow clone, warm runner pools
4Make the work fasterVariesWeeksFix the slow tests, the slow build, the slow compiler settings
WHY THE ORDER MATTERS — THE SAME PIPELINE, LEVERS APPLIED IN SEQUENCE

  start:                                        38m00s
  L1  concurrency cancel + path filters         31m10s   (queue collapsed)
  L1  test-impact selection on PRs              19m20s
  L2  fan-out lint/typecheck/unit/integration   12m40s
  L2  shard integration 3 ways (by duration)     9m10s
  L3  prebuilt toolchain image, cache keys       7m30s
  L3  shallow clone + narrower artifact upload   6m05s
  L4  fix the two slowest integration tests      5m20s
  ------------------------------------------------------------------
  total effort: ~6 engineer-days, of which L4 was 3.

  DOING L4 FIRST would have taken 38m -> 36m40s, cost the same 3 days,
  and left everyone concluding that pipeline work does not pay.

2.1 Lever 1 in practice: the work you can simply not do

  # a) cancel superseded runs (never on main or deploys)
  concurrency:
    group: ${{ github.workflow }}-${{ github.ref }}
    cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}

  # b) skip what the diff cannot affect
  on:
    pull_request:
      paths-ignore: ['docs/**', '**/*.md', 'design/**']

  # c) skip unchanged targets in a monorepo
  - id: plan
    run: ./ci/affected.sh "origin/${GITHUB_BASE_REF}" | tee targets.json

  # d) run only the tests the change can break (test-impact selection),
  #    with the full suite post-merge — see <test strategy>

  MEASURED CONTRIBUTION OF EACH, ONE MONTH
    concurrency cancellation ... 41% of runs never finished (nobody
                                 wanted their results anyway)
    path filters ............... 29% of runs never started
    affected-target selection .. 34 services built -> 2.8 median
    test-impact selection ...... 1,100 tests -> 84 median

Part 3 — Caching That Earns Its Place

A cache is only a win if restore time + miss cost × miss rate is less than the work it replaces. Teams add caches without measuring either side, and some of them are net negative.

THE CACHE THAT LOST TIME

  step                                  duration
  ------------------------------------------------
  restore cache (412 MB)                  71 s
  npm ci (with a warm cache)              12 s
  ------------------------------------------------
  total with cache                        83 s
  npm ci from scratch (no cache at all)   60 s      <-- FASTER

  the cache was 412 MB because it included node_modules AND the npm
  download cache AND a stale build directory. Restoring it across the
  network cost more than re-downloading the packages.

  THE FIX: cache the DOWNLOAD cache only (~40 MB), not node_modules.
    restore ............ 6 s
    npm ci ............. 19 s
    total .............. 25 s     (vs 60 s uncached, 83 s before)
QuestionHow to answer itAction if the answer is bad
What is the hit rate?Log cache-hit per run; aggregate weeklyBelow ~70%: the key is too specific, or the cache is being evicted
How long does a restore take?The step durationIf restore ≥ the work it saves, delete the cache
How big is it?Registry/cache listingSplit it: cache downloads, not installed trees
What invalidates it?Read the key expressionKey on the lockfile + toolchain + OS, nothing else
Is it load-bearing?Weekly cold buildFix immediately — it is an artifact in disguise
KEYS: SPECIFIC ENOUGH TO BE CORRECT, LOOSE ENOUGH TO HIT

  ❌ key: deps-${{ github.sha }}
     100% miss rate. Every commit is a new key.

  ❌ key: deps
     100% hit rate, and it never updates. Stale forever.

  ✅ key: ${{ runner.os }}-node20-${{ hashFiles('**/package-lock.json') }}
     restore-keys: |
       ${{ runner.os }}-node20-
     exact hit when the lockfile is unchanged; a near-hit (last week's
     tree) when it changed, which npm ci then reconciles from the lock.

  MEASURED HIT RATES, ONE MONTH, AFTER FIXING KEYS
    npm download cache ..... 94%
    pip wheel cache ........ 91%
    Docker layer cache ..... 88%
    Gradle build cache ..... 76%   (invalidated by generated sources)
    Cypress binary ......... 99%   (pinned by version — never changes)

Part 4 — Sharding: The Arithmetic

STEP 1 — SPLIT BY DURATION, NOT BY FILE COUNT

  splitting 198 integration tests 3 ways by FILE COUNT:
    shard 1: 66 files ....  3m10s
    shard 2: 66 files ....  4m20s
    shard 3: 66 files .... 10m50s   <-- 42% of total runtime, alone
    pipeline = 10m50s (the slowest shard)

  splitting by RECORDED DURATION (timings from the last green run):
    shard 1 ..............  6m05s
    shard 2 ..............  6m10s
    shard 3 ..............  6m05s
    pipeline = 6m10s        (43% faster, same machines, same tests)

  most runners support this directly:
    pytest --splits 3 --group ${{ matrix.shard }} --durations-path .timings
    jest --shard=${{ matrix.shard }}/3
    go test -shuffle=on ./...    (with a partitioning wrapper)

STEP 2 — KNOW WHERE PARALLELISM STOPS PAYING (Amdahl, concretely)

  per-shard fixed overhead (runner start, checkout, restore) = 95 s
  serial work that cannot be split (the total test time)     = 18m24s

  shards   test time/shard   + overhead   wall clock   runner-minutes
  ----------------------------------------------------------------
    1        18m24s            1m35s       19m59s          20
    2         9m12s            1m35s       10m47s          22
    3         6m08s            1m35s        7m43s          23
    4         4m36s            1m35s        6m11s          25
    6         3m04s            1m35s        4m39s          28
    8         2m18s            1m35s        3m53s          31
   12         1m32s            1m35s        3m07s          37
   16         1m09s            1m35s        2m44s          44

  the curve flattens once test time per shard approaches the overhead.
  Past 8 shards you pay 40% more runner-minutes for 60 seconds.
  CHOOSE where the marginal minute stops being worth the marginal cost —
  usually 4-8 for a suite this size.
💡 Reduce the per-shard overhead and the whole curve improves. That 95 seconds is checkout, toolchain and cache restore — paid once per shard. A prebuilt toolchain image and a shallow clone took it to 28 s in the measured case, which made 8 shards cost what 4 had cost before. Fixing setup is what makes parallelism cheap.

4.1 Merging what the shards produce

  each shard writes its own report; a final job merges them, or you lose
  coverage totals and get N separate test summaries:

    - uses: actions/upload-artifact@v4
      with: { name: results-${{ matrix.shard }}, path: junit-*.xml }

    merge:
      needs: [test]
      steps:
        - uses: actions/download-artifact@v4
          with: { pattern: results-*, merge-multiple: true }
        - run: |
            junitparser merge junit-*.xml junit-all.xml
            coverage combine .coverage.*        # then report ONCE
            coverage xml
        - run: diff-cover coverage.xml --compare-branch=origin/main \
                 --fail-under=80

  and keep the timings for the NEXT split:
        - run: cp .timings .timings.new
        - uses: actions/upload-artifact@v4
          with: { name: timings, path: .timings.new }

Part 5 — Queue Time and Capacity

Queue time is the term nobody sees, because dashboards start the clock when a job begins. It was the largest single component in three of four pipelines audited.

MEASURING IT, AND WHAT DRIVES IT

$ gh run list --limit 500 --json createdAt,startedAt \
    --jq '.[] | (.startedAt|fromdate) - (.createdAt|fromdate)' \
  | sort -n | awk '{a[NR]=$1} END {
      printf "queue p50 %ds  p90 %ds  p99 %ds  max %ds\n",
      a[int(NR*.5)], a[int(NR*.9)], a[int(NR*.99)], a[NR]}'

THE ECONOMIC COMPARISON THAT SETTLES CAPACITY ARGUMENTS

  option A — stay as we are
    queue p50 6m20s x 118 runs/day x (30% of runs are waited on)
      = 3.7 engineer-hours/day = ~$7,800/month at $85/h

  option B — double the concurrency limit / runner pool
    additional runner cost .......... $310/month
    queue p50 measured after ......... 47s
    engineer time recovered .......... ~$7,400/month

  the ratio is not close, and it is the same ratio as in
  <lesson 1>: runner minutes are cheap, engineer minutes are not.
  Bring THIS table to the budget conversation, not a request for
  "more CI capacity".

Part 6 — Keeping It Fast

Pipelines rot. Every new check, artifact and dependency adds seconds, and nobody notices 30 seconds a month until the year is over.

A DURATION BUDGET, ENFORCED LIKE ANY OTHER CHECK

  # .github/workflows/ci.yml
  - name: Pipeline duration budget
    if: always()
    run: |
      set -euo pipefail
      ELAPSED=$(( $(date +%s) - START ))
      BUDGET=600                       # 10 minutes for the PR pipeline
      echo "pipeline: ${ELAPSED}s (budget ${BUDGET}s)"
      if [ "$ELAPSED" -gt "$BUDGET" ]; then
        echo "::warning::PR pipeline exceeded its ${BUDGET}s budget (${ELAPSED}s)"
        ./ci/post-slowest-steps.sh          # name the top 5 steps
      fi

  START AS A WARNING, NOT A GATE. A duration gate blocks the PR that
  discovers the problem rather than the PR that caused it, which is
  exactly the kind of gate people route around
  (<quality gates>). Escalate to a gate only for a repo where the
  duration is a product requirement.

WEEKLY REGRESSION REPORT — the thing that actually keeps it fast

  week   p50     p90    biggest step        change
  ---------------------------------------------------------------
  32     6m05s   9m10s  integration 3m20s   —
  33     6m12s   9m20s  integration 3m22s   +7s
  34     7m41s  11m30s  integration 4m50s   +89s  <-- investigate
         -> a new integration test suite added 41 tests without
            rebalancing the shards. Shard 2 now carries 61%.

⚠️ Watch the p90, not just the p50. The median hides queue spikes, cache misses and the lockfile-changed path — and those are exactly the runs people remember. A pipeline with a 6-minute median and a 20-minute p90 feels like a 20-minute pipeline, because the slow runs are the ones that interrupt someone's flow.

❌ A team optimising the test suite for three weeks while 6m20s of queue time, 4m50s of artifact upload, a 412 MB cache that loses time, and a 3m18s full-history checkout go unmeasured. The pipeline "takes 38 minutes" and nobody has decomposed that number, so the effort goes into the one term that is hardest to improve. The integration suite is sharded by file count, leaving one shard with 42% of the runtime, so three machines deliver the speed of one and a half. Sixteen shards were tried at one point because more parallelism seemed better, and the runner bill rose 40% for 60 seconds. The cache key includes the commit SHA, so it never hits; the artifacts uploaded on every run are downloaded by nobody; and the nightly job overlaps the afternoon peak so the queue is worst exactly when people are working. A year later the pipeline is nine minutes slower than it was and nobody can say which change did it.

✅ Decompose the number, then pull the four levers in order — don't run it, run it in parallel, make it start faster, make the work faster. Profile per step across forty runs and you will usually find a third of the time in checkout, cache restore and upload rather than in tests. Take the configuration wins first: cancel superseded runs, filter paths, select affected targets and impacted tests — 38m to 19m20s before anyone touches code. Then fan out and shard by recorded duration (10m50s → 6m10s on the same machines), and compute the shard count from the overhead curve instead of guessing, because past the point where per-shard test time approaches per-shard setup, you are buying minutes with money. Audit every cache against the only question that matters — does restore time plus miss cost beat doing the work? — and delete the ones that lose, cache download directories rather than installed trees, and key on lockfile plus toolchain plus OS. Measure queue time separately and bring the capacity table to the budget conversation: $310/month of runners recovered ~$7,400/month of waiting. Then defend it with a duration budget as a warning and a weekly p50/p90 regression report, so the 89 seconds added by an unbalanced shard is found in week 34 rather than next year.

Interview Questions

Beginner: A pipeline takes 30 minutes. What do you look at first?

I would refuse to optimise anything before decomposing the number, because "30 minutes" is four different measurements with four different fixes:

  • Queue — time between the run being created and a machine picking it up. Fixed with concurrency settings and capacity, not with code.
  • Setup — checkout, toolchain installation, cache restore. Fixed with prebuilt images and better cache keys.
  • Critical path — the longest chain of actual work. Fixed with parallelism first, then by making the work faster.
  • Publish — artifact uploads, reports, notifications. Often surprisingly large and trivially reducible.

In one measured pipeline that reported 38 minutes, 6m20s was queue and 4m50s was uploading artifacts nobody downloaded — 29% of feedback time in configuration, while the team had spent three weeks on the test suite.

Then within the critical path, I would profile per step across many runs rather than looking at one run, because a single run can be unrepresentative. The usual finding is that one or two steps dominate and everything else is noise.

Beginner: Why can adding more parallel shards stop helping?

Because each shard pays a fixed setup cost — runner start, checkout, toolchain, cache restore — and that cost does not shrink when you split the work further.

With 18m24s of test time and 95 s of per-shard overhead:

ShardsTest time eachWall clockRunner-minutes
118m24s19m59s20
44m36s6m11s25
82m18s3m53s31
161m09s2m44s44

Going from 8 to 16 shards buys 69 seconds and costs 42% more runner-minutes. The curve flattens once per-shard test time approaches the per-shard overhead — which is Amdahl's law with the serial part being setup.

The useful corollary: reducing setup improves the whole curve. Taking overhead from 95 s to 28 s with a prebuilt toolchain image and a shallow clone made 8 shards cost what 4 had cost before, so investing in setup is what makes parallelism affordable.

Mid: How do you decide whether a cache is worth having?

One inequality: restore time + (miss rate × miss cost) must be less than the work the cache replaces. Most teams measure neither side.

The measured counter-example: a 412 MB cache containing node_modules, the npm download cache and a stale build directory took 71 seconds to restore and made npm ci take 12 s instead of 60 s. Total with cache: 83 s. Total without: 60 s. The cache was costing 23 seconds per run and had been in place for a year.

The fix was to cache the download directory rather than the installed tree — 40 MB, 6 s restore, 19 s install, 25 s total.

The four numbers I would collect for every cache: hit rate (log cache-hit per run; under ~70% usually means the key is too specific), restore duration, size, and what invalidates it. And one qualitative check that overrides all of them — is it load-bearing? A weekly cold build must still pass. If it does not, the cache is not an optimisation, it is an artifact, and the pipeline's results depend on history.

Mid: Your test suite is sharded across three machines but the pipeline is barely faster. Why?

Almost certainly an unbalanced split. The pipeline is as slow as the slowest shard, so splitting by file count — the default in most setups — produces this:

shard 1: 66 files    3m10s
shard 2: 66 files    4m20s
shard 3: 66 files   10m50s      <-- 42% of the runtime, alone

Three machines, and the wall clock is 10m50s: barely better than the 18m24s serial run, for triple the runner cost.

Fix: split by recorded duration. Most runners support this directly (pytest --splits N --group M --durations-path, jest --shard with timing data), which gave 6m05s / 6m10s / 6m05s on the same machines — 43% faster with no other change.

Two follow-ups I would check. Is the timings file being refreshed? It must be regenerated from green runs, or the split degrades as the suite changes — that is exactly how a pipeline silently regressed 89 seconds in one measured week. And are the reports merged? Sharding without a merge job leaves N partial coverage reports and breaks any diff-coverage gate, which usually gets "fixed" by lowering the threshold.

Senior: You are asked to cut CI costs by 40%. How do you approach it without slowing everyone down?

I would start by pointing out that CI compute is almost never the expensive resource, and bring the comparison rather than arguing: in one measured organisation runners cost $610/month while queue time alone consumed roughly $7,800/month of engineer waiting. A 40% compute cut that adds five minutes to everyone's feedback loop is a large net loss — so the first deliverable is that number, in the finance team's units.

Then I would find the cuts that do not cost time, which usually reach 40% on their own:

LeverCompute savedEffect on feedback time
Cancel superseded runs~40% of runs never finishImproves it — queue drops
Path filters~29% of runs never startImproves it
Test-impact selection on PRsLargeImproves it
Right-size runnersBig machines only where measured to helpNeutral if measured per job
Stop uploading unread artifacts; shorten retentionStorage + minutesImproves it
Move nightly heavy jobs off peakNeutral compute, big queue winImproves it
Reduce shard count past the flat part of the curveDirectCosts a little — do this one last

What I would resist: cutting the runner pool (it converts money into queue time, which costs more), and removing checks to save minutes (that is a quality decision being made with a budget justification — if a check is not worth its time, delete it on the merits, per quality gates).

Finally I would instrument cost per pipeline per repository, because the distribution is always skewed — in most estates a handful of repositories generate the majority of the spend, and fixing three of them beats a policy applied to sixty.

Senior: How do you stop a fast pipeline from slowly getting slow again?

Treat duration as a tracked property with an owner, not as a project that finished.

  • A budget, enforced as a warning per run. Print elapsed time against the budget and, when it is exceeded, automatically post the five slowest steps. A warning rather than a gate, because a duration gate blocks the PR that discovers the regression rather than the one that caused it — a classic routed-around gate.
  • A weekly p50/p90 report with the biggest step named and week-over-week deltas. This is what catches the +89 s that an unbalanced shard introduced in the measured case; nobody notices it in a single run.
  • Track p90, not just the median — a 6-minute p50 with a 20-minute p90 feels like a 20-minute pipeline, and the p90 is where cache misses and queue spikes live.
  • Refresh the inputs the optimisations depend on: shard timings from green runs, the test-impact map, cache keys after toolchain upgrades. Optimisations decay silently when their data goes stale.
  • Cold-build and cold-cache checks weekly, so the recovery-time number is known and load-bearing caches are caught in days.
  • An owner. The pipeline is production for the engineering organisation; without a named team and an SLO, duration regressions are nobody's ticket — which is the same conclusion as lesson 1, and the one that actually determines whether any of this survives the quarter.

6 (hard): Build the regression defence: a duration budget, a weekly report, and refresh jobs for the derived data every optimisation depends on.
Solution 
COMPONENT 1 — PER-RUN BUDGET, AS A WARNING WITH DIAGNOSIS

  # first step of the pipeline
  - run: echo "PIPELINE_START=$(date +%s)" >> "$GITHUB_ENV"

  # last job, always()
  - name: Duration budget
    if: always()
    run: |
      set -euo pipefail
      ELAPSED=$(( $(date +%s) - PIPELINE_START ))
      BUDGET=600
      echo "pipeline ${ELAPSED}s / budget ${BUDGET}s"
      if [ "$ELAPSED" -gt "$BUDGET" ]; then
        echo "::warning title=Slow pipeline::${ELAPSED}s exceeds ${BUDGET}s"
        gh run view "$GITHUB_RUN_ID" --json jobs --jq '.jobs[] | .name as $j
          | .steps[] | [((.completedAt|fromdate)-(.startedAt|fromdate)),
              "\($j) / \(.name)"] | @tsv' | sort -rn | head -5 \
          | while IFS=$'\t' read -r d n; do echo "::warning::${d}s  ${n}"; done
      fi
      echo "$(date +%F),$GITHUB_RUN_ID,$ELAPSED" >> /tmp/durations.csv
      ./ci/push-metric.sh pipeline_duration_seconds "$ELAPSED"

The warning tells the author something changed; the weekly report is what actually catches gradual drift, because no single PR is responsible for it; and the refresh jobs stop your optimisations from quietly becoming decoration. 🎯 Key Takeaways

  • Feedback time = queue + setup + critical path + publish. One "38-minute" pipeline was 6m20s queue, 4m10s setup, 22m40s work and 4m50s publish — and the team had been optimising only the third term.
  • Profile per step across many runs, not one run: checkout, cache restore and artifact upload together were a third of the pipeline and none of them is a test.
  • Pull the four levers in order — don't run it, run it in parallel, make it start faster, make the work faster. Doing lever 4 first cost three days for 80 seconds.
  • Lever 1 is configuration and pays most: cancellation removed 41% of runs, path filters 29%, affected-target selection took 34 builds to 2.8, impact selection 1,100 tests to 84 — 38m → 19m20s with no code change.
  • A cache is only a win if restore + miss cost beats the work. A 412 MB node_modules cache took 71 s to restore and saved 48 — caching ~/.npm instead gave 25 s total against 60 s uncached.
  • Cache inputs, not results: download directories are small, portable and cannot silently skip a build step the way a cached dist/ can.
  • Key on lockfile + toolchain + OS with a loose restore-keys prefix; a SHA in the key means a 100% miss rate and pure upload cost.
  • Split shards by recorded duration, never by file count — a file-count split left one shard with 42% of the runtime, so three machines bought 1.7×; duration splitting gave 43% faster on the same machines.
  • Compute the shard curve from your own overhead. With 95 s per shard, 8→16 shards bought 69 s for 42% more runner-minutes. Stop where per-shard work approaches per-shard setup.
  • Reducing setup improves the whole parallelism curve — 95 s → 28 s made 8 shards cost what 4 had cost.
  • Sharding without a merge job leaves N partial coverage reports and breaks diff-coverage gates, which then get "fixed" by lowering the threshold.
  • Queue time is invisible and often the largest term. Measure startedAt − createdAt, and read its shape: activity-correlated means a concurrency ceiling, monotonic growth means too few runners, brief spikes mean autoscaler lag.
  • Never buy capacity before removing waste — the measured pipeline would have needed four times the concurrency to absorb runs that were superseded or irrelevant.
  • Bring the money table to capacity arguments: $310/month of runners recovered roughly $7,400/month of engineer waiting; the ratio is never close.
  • Publish time is the easiest unclaimed win: 86 GB of artifacts a week served 11 downloads. Upload on failure only, compress, shorten retention.
  • Shallow clone by default (fetch-depth: 1), deepening only where history is genuinely needed — full history cost 3m18s on a large repository.
  • Track p90, not just p50. A 6-minute median with a 20-minute p90 feels like a 20-minute pipeline, because the slow runs are the ones that break someone's flow.
  • Enforce a duration budget as a warning that names the five slowest steps — a hard gate blocks the PR that discovers the regression rather than the one that caused it.
  • Every optimisation depends on derived data that decays: shard timings, impact maps, toolchain images, cache keys. Refresh them on a schedule or they quietly become decoration — a stale timings file cost +87 s in one week.
  • The weekly p50/p90 report is what actually keeps a pipeline fast, because gradual drift belongs to no single pull request and will never be caught by looking at individual runs.
