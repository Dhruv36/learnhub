Environments & Promotion Deployment

What you'll master: the test that decides whether an environment should exist — what question does it answer that a cheaper environment cannot? — and what to do about the common answer, "none", after the audit where only 12 of 47 production incidents were reproducible in staging and 9 were caused by staging-only differences; parity and drift, where a three-way diff found 61 configuration differences between staging and production, 14 of them unintentional, including a connection-pool size that made staging incapable of showing the exhaustion bug that caused two outages; promotion done properly — promote an immutable digest, never a branch, with an auditable record of which artifact is approved for where; ephemeral per-PR environments that removed a shared-staging queue in which engineers waited a median of 47 minutes, and how to keep their cost from becoming a line item; the honest division of labour between staging and production testing, since some questions can only be answered in production; and approvals that mean something, given that the measured median approval on a 400-line deploy took 18 seconds. Prerequisites: Builds & Artifacts and Deployment Strategies.

🔑 An environment that causes more incidents than it catches is a liability, not a safety net. The response is not necessarily to delete staging — it is to make it answer a question it can actually answer. In the measured case that meant fixing data volume and config parity, after which staging's catch rate rose to 21 of the next 40 incidents; the alternative would have been to delete it and spend the $4,900 on better canary analysis, which is a legitimate choice.

Part 2 — Parity and Drift

Environments diverge continuously and silently. The difference that matters is not "staging is smaller" — it is the differences nobody chose.

PropertyMust match productionMay differ
Application artifactExactly — same digestNever
Schema versionYesOnly during a migration window
Dependency versions (DB, cache, broker)Major/minorPatch, briefly
Config shapeYes — the same keys existValues
Pool sizes, timeouts, limitsRatios, at leastAbsolute values, proportionally
Data volumeOrder of magnitudeActual rows, obviously
Instance count> 1, so multi-instance bugs appearThe exact number
Feature flag defaultsYes, unless deliberately testingPer-test overrides

⚠️ Config that exists in only one environment is the highest-risk category. A flag that is on in production and absent from staging means the code path that runs for your users has never run anywhere else. Enforce it structurally: generate every environment's config from one template with per-environment values, so a missing key is a build error rather than a discovery during an incident.

Part 3 — Promotion: Move Artifacts, Not Branches

  ❌ BRANCH-BASED PROMOTION (still extremely common)
     merge main -> staging branch   -> CI builds and deploys to staging
     merge staging -> production branch -> CI builds and deploys to prod

     problems, in order of severity:
       - each merge triggers a NEW BUILD: production runs bytes that
         were never tested (<builds and artifacts>)
       - the branches diverge; cherry-picks and merge conflicts appear
         in the DEPLOYMENT path, which is the worst place for them
       - "what is in staging?" requires reading git history
       - a hotfix to production must be back-merged, and sometimes isn't

  ✅ ARTIFACT PROMOTION
     one build -> one digest -> tested -> the SAME digest deployed to
     staging -> the SAME digest deployed to production

     "promotion" = changing which environment points at that digest.
     Branches stay for source control; deployment is a pointer change.
Promotion modelMechanismAudit trailGood for
Pipeline-driven (push)A job deploys the digest to the next environmentThe run log and deployment APISimple estates; fastest to build
GitOps (pull)A commit to an environment repo changes the digest; an agent reconcilesGit history is the recordMulti-cluster, compliance, drift correction
Metadata/registry promotionA record marks a digest "approved for production"The record storeDecoupling approval from deployment timing
WHAT A PROMOTION RECORD SHOULD CONTAIN (any model)

  {
    "artifact":    "registry/app@sha256:9e1c4a…",
    "commit":      "4f2a91c8d11e…",
    "from_env":    "staging",
    "to_env":      "production",
    "promoted_by": "r.okafor",
    "promoted_at": "2026-08-21T10:14:07Z",
    "evidence": {
      "ci_run":        "…/actions/runs/9481123",
      "tests_passed":  ["unit","integration","contract","e2e"],
      "staging_since": "2026-08-21T08:02:11Z",     // bake time
      "canary_result": "passed 4 gates at 1/5/25%"
    }
  }

  THIS RECORD IS THE THING AUDITORS ACTUALLY WANT, and it is
  incidentally what makes "which build is in production, and what
  proved it was ready?" a one-line query instead of an investigation.

3.1 GitOps in one paragraph

  the environment's desired state lives in a Git repository:

    envs/production/shop-api.yaml
      image: registry/app@sha256:9e1c4a…      # promotion = change this line

  an in-cluster agent continuously reconciles the cluster to that file.
  CONSEQUENCES:
    + the audit trail is git history, with review and revert built in
    + drift is corrected automatically (someone's kubectl edit is undone)
    + rollback is `git revert`
    − a second repository to keep in sync
    − "deployed" now means "reconciled", so your pipeline must WAIT for
      and VERIFY reconciliation, or it will report success before the
      change is live — a very common bug in first GitOps rollouts

Part 4 — Ephemeral Environments per Pull Request

THE PROBLEM THEY SOLVE — A SHARED STAGING QUEUE

  measured, one 40-engineer org, one shared staging:
    "who is on staging?" messages per day .......... 23
    median wait for a slot ......................... 47 min
    changes tested together and blamed on each other  frequent
    hours per week lost to coordination ............ ~19

THE REPLACEMENT

  on: pull_request
  jobs:
    preview:
      steps:
        - run: ./ci/deploy-preview.sh "pr-${{ github.event.number }}" \
                 "registry/app@${{ needs.build.outputs.digest }}"
        - run: gh pr comment ${{ github.event.number }} \
                 --body "🚀 Preview: https://pr-${{ github.event.number }}.preview.acme.dev"

    # and the part people forget:
  on:
    pull_request:
      types: [closed]
  jobs:
    teardown:
      steps:
        - run: ./ci/destroy-preview.sh "pr-${{ github.event.number }}"

  COST CONTROL, WHICH DECIDES WHETHER THIS SURVIVES CONTACT WITH FINANCE
    - TTL: destroy after 72 h of inactivity, whatever the PR state
    - scale to zero when idle (request-triggered wake-up)
    - share expensive dependencies: ONE database server, a schema per PR
    - no preview for docs-only PRs (path filters)
    measured: 60 concurrent previews for $310/month, against a $4,900
    shared staging that also had a queue.
Design decisionOptionsRecommended
DataEmpty, seeded fixture, anonymised production subsetSeeded fixture — deterministic, safe, fast; anonymised subsets need a strong pipeline and legal review
DependenciesReal neighbours, mocks, shared instanceShared instance of stable neighbours; contract tests for the rest
LifetimePR open, fixed TTL, manualPR closed and a TTL, because PRs go stale
Naming/URLPer PR number, per branchPer PR number — branch names contain characters URLs hate
SecretsReal, dedicated, noneDedicated non-production credentials, never production ones
💡 The teardown job is the whole cost model. The failure mode is predictable: previews accumulate because a PR was closed while the workflow was failing, or the teardown job itself broke and nobody noticed. Run a nightly reaper that destroys anything whose PR is closed or whose TTL has passed, and alert when the count of live previews exceeds a threshold — one estate discovered 214 orphaned environments this way, at $2,100/month.

Part 5 — What Staging Cannot Tell You

Some questions are answerable only where the users are. Pretending otherwise produces the 55% of incidents that were not reproducible before release.

QuestionAnswerable in staging?Where it is really answered
Does the code work?YesTests, then preview environments
Do the services still agree?YesContract tests; integration environment
Does the migration apply cleanly?Only with production-scale dataA restored production-sized copy — see migrations
Does the query plan hold at scale?Only with representative volumeProduction-sized data, or production itself
Does it survive real traffic patterns?NoCanary in production
Does the third party behave as documented?Partly (sandboxes lie)Production, with a flag and a small blast radius
Do real users understand the change?NoProduction experiments — progressive delivery
THE HONEST DIVISION OF LABOUR

  BEFORE PRODUCTION (cheap, deterministic)
    unit + integration + contract tests
    a preview environment for human review
    migration rehearsal against a production-sized restore
    a staging soak IF staging is realistic enough to mean something

  IN PRODUCTION (the only place some questions exist)
    canary with automated analysis          <- deployment strategies
    feature flags and gradual exposure      <- progressive delivery
    synthetic monitoring of critical journeys, continuously
    real-user monitoring and error tracking

  THE SHIFT THIS IMPLIES: money spent making staging "more real" has a
  ceiling; money spent on production detection does not. In the measured
  estate, halving staging spend and funding canary analysis moved
  mean-time-to-detect from 8 minutes to 90 seconds — which mattered more
  than the 8 incidents staging had been catching.

❌ A staging environment nobody trusts, branch-based promotion that rebuilds at every step, a shared staging queue with a 47-minute wait, 61 undocumented config differences, and two required approvals granted in 18 seconds. Staging causes more incidents than it catches — nine against eight — because it holds four config keys production does not have, its connection pool is a tenth the size, and its data is small enough that every query plan is different. Promotion means merging into a production branch, which triggers a fresh build, so the bytes users receive were never the bytes anyone tested, and answering "what is in staging?" requires reading git history. Engineers wait a median of 47 minutes for a staging slot and then test their change alongside two others, so failures are unattributable. Preview environments were introduced once and abandoned when 214 orphans appeared on the invoice. The two approvals are rubber stamps — the approver opened the diff 11% of the time and has never rejected one — while the deploy record consists of a Slack message saying "shipping".

✅ Make every environment answer a question, promote immutable digests with an evidence record, replace the shared queue with cheap ephemeral previews, and spend the difference on production detection. Audit which incidents staging actually catches, then either fix its parity — data volume within an order of magnitude, identical config keys, pool ratios, more than one instance — or accept that some questions belong to production and fund canary analysis instead. Generate every environment's config from one template so a missing key is a build error, and run a quarterly three-way diff, because drift is continuous and silent. Promote by changing which environment points at a digest — pipeline-driven or GitOps, but never by merging branches — and record artifact, commit, promoter, bake time and the evidence that justified it, which is both the audit trail and the answer to "what is running?". Give every PR a preview environment with a TTL, a nightly reaper and shared expensive dependencies: 60 concurrent previews for $310/month replaced a $4,900 queue. Then make approvals rare and therefore real — automated gates for "did the checks pass", human judgement reserved for schema changes and out-of-hours releases, and environment-scoped secrets so a staging workflow cannot obtain production credentials at all.

Interview Questions

Beginner: What environments would you set up for a web service, and what is each one for?

I would justify each by the question it answers, and drop any that cannot answer one:

EnvironmentQuestion
LocalDoes my change work at all?
Ephemeral preview (per PR)Does this change work in isolation, and can a reviewer see it?
StagingDoes the release behave with production-like config, schema and data volume?
ProductionDoes it work for users?

The two things I would emphasise. First, the same artifact moves through all of them — one build, promoted by digest — otherwise the testing does not transfer. Second, staging only earns its cost if it is realistic in the ways that matter: config keys, pool-size ratios, data volume within an order of magnitude, and more than one instance. In one measured estate staging caused nine incidents and caught eight, because it had drifted into being a different system that happened to run the same code.

I would also add preview environments early. They remove the shared-staging queue — measured at a 47-minute median wait and 23 coordination messages a day — and they make review concrete for people who do not read diffs.

Beginner: Why is promoting an artifact better than merging into a "production" branch?

Because a branch merge triggers a new build, and a new build is a different artifact. The thing deployed to production was never the thing that was tested — which is the immutability guarantee from builds and artifacts, and the reason a base-image patch between two builds once cost three hours of debugging against an identical commit hash.

Three further problems with branch promotion:

  • The branches diverge. Hotfixes applied to production must be back-merged, and eventually one is not — so production contains a commit that exists nowhere else.
  • "What is in staging?" becomes a git archaeology question rather than a lookup.
  • Merge conflicts appear in the deployment path, which is the worst possible place for them — usually during an incident.

Artifact promotion makes deployment a pointer change: the environment references registry/app@sha256:…, and promoting means updating that reference. Branches go back to doing what they are good at, which is source control.

Mid: Your staging environment keeps missing bugs that appear in production. What do you do?

Measure before changing anything, because the fix depends on why it misses them.

Step 1 — classify the last 40 incidents by whether staging could have caught them. The measured breakdown in one estate: 17% caught, 9% reproducible after the fact, 55% not reproducible at all, and 19% actually caused by staging-only differences.

Step 2 — split the 55%, because those categories have different answers:

CauseFix
Data volume (query plans, migrations)Restore a production-sized copy periodically — this is usually the single highest-value change
Config drift (pool sizes, missing keys)Generate all environments from one template; quarterly three-way diff
Real traffic and concurrencyNot fixable in staging — move the detection to a canary in production
Third-party behaviourSandboxes lie; test in production behind a flag with a small blast radius

Step 3 — decide honestly. Money spent making staging more realistic has a ceiling; money spent on production detection does not. In the measured case, fixing data volume and config parity raised staging's catch rate substantially, and reallocating the remaining spend to canary analysis took mean-time-to-detect from 8 minutes to 90 seconds — which was worth more than the incidents staging had been catching.

Mid: How do you implement ephemeral preview environments without the cost getting out of control?

The mechanism is easy; the lifecycle is what decides whether it survives.

ControlDetail
Destroy on PR closeA workflow on pull_request: [closed] — necessary but not sufficient, because that workflow can itself fail
TTLDestroy after ~72 h of inactivity regardless of PR state; PRs go stale far more often than they close
Nightly reaperEnumerate live previews, cross-check against open PRs, destroy orphans. One estate found 214 orphans at $2,100/month
Scale to zeroIdle previews cost nothing; a request wakes them
Share expensive dependenciesOne database server with a schema per PR, rather than a database per preview
Skip trivial PRsPath filters — no preview for docs-only changes
Alert on the countIf live previews exceed a threshold, something is leaking

Measured outcome with those controls: 60 concurrent previews for $310/month, replacing a $4,900/month shared staging that also had a 47-minute queue.

Two details worth stating: seed with a fixture dataset rather than production data (deterministic, fast, and no legal exposure), and give previews dedicated non-production credentials — a preview environment is reachable by anyone who can open a pull request.

Senior: Design promotion and approval for a regulated environment that requires evidence of what was deployed and why.

Auditors want provenance and evidence, not a person's name — and a system that produces those automatically is both cheaper and more credible than one that relies on humans remembering.

RequirementImplementation
What exactly is deployed?Immutable digest per environment; a /buildinfo endpoint reporting commit and digest at runtime
Where did it come from?Provenance attestation and SBOM attached to the digest at build time
What proved it was ready?A promotion record: tests passed, staging bake window, canary gate results, linked CI run
Who authorised it?Approval on the exceptional cases, recorded in the promotion record; routine releases are authorised by the policy itself
Could someone bypass it?Environment-scoped secrets, protected branches, and an audited break-glass path with automatic follow-up
Can you prove the history?GitOps: the environment repo's git history is the deployment record, signed and reviewable

The argument I would make to the auditor: approve the pipeline and its controls rather than each release. A control that runs identically 200 times a month with a machine-generated evidence record is stronger than a human signature granted in 18 seconds — which is what the current process actually produces, and which the referrer logs show involved opening the diff 11% of the time.

Where I would keep humans: destructive schema changes, anything with irreversible side effects, first-time enablement of a flag at 100%, and out-of-hours releases. Rarity is what makes an approval mean something.

Senior: Would you delete staging? Make the argument either way.

It depends entirely on what it answers, and the answer is measurable rather than philosophical.

The case for deleting it: in the audited estate it caught 8 incidents and caused 9, at $4,900/month plus two engineer-days a month of upkeep. 55% of incidents were not reproducible there at all, because they depended on data volume, real traffic, third-party behaviour or production-only config. Money spent making staging more realistic has a hard ceiling — you will never have production's traffic — whereas money spent on canary analysis, feature flags and synthetic monitoring keeps paying, and it took mean-time-to-detect from 8 minutes to 90 seconds.

The case for keeping it: some questions genuinely need a full environment that is not production — migration rehearsal against production-sized data, destructive testing, load testing, integration across many services during a large change, and training or demos. And in regulated contexts a pre-production soak may be contractual.

What I would actually do: keep it, and change what it is for. Fix the parity items that make it lie — data volume within an order of magnitude, identical config keys, proportional pool sizes, more than one instance — and stop expecting it to catch traffic-dependent and third-party bugs. Move those to canary and progressive delivery. Then re-run the incident audit in six months: if it still causes more than it catches, that is the evidence to delete it, and by then you will have built the production detection that replaces it.

The framing I would offer leadership: this is not "do we test before release?" — it is "which questions do we answer where, and what does each answer cost?"

  | DB_POOL_SIZE | 12 | 50 | proportional to instance count (2 vs 8) |
  | CACHE_TTL_S | 3600 | 3600 | (aligned 2026-08; was 60 — hid a
                                 cache-stampede bug) |
  | DEBUG_ENDPOINTS_ENABLED | true | false | debug UI; access-controlled |
Drift classRiskControl
Key present in one environment onlyHighest — a production code path never runs elsewhereRequired-key template; build fails on a missing key
Ratios wildly different (pools, limits)High — the environment cannot reproduce saturationEnforce a maximum ratio in the check
Undocumented value differencesMedium — nobody knows if they are deliberateA reviewed differences file
Bypass/debug flags in stagingHigh — they mask exactly the bugs you are testing forRemove, or replicate the production path with test credentials
⚠️ Bypass flags are the worst drift. A staging environment with RATE_LIMIT_BYPASS_TOKEN and LEGACY_AUTH_FALLBACK is not testing your application; it is testing a variant of it that no user will ever run — and it will pass every test about the code paths it disables.

THE PROMOTION RECORD

  #!/usr/bin/env bash
  # ci/record-promotion.sh ENV DIGEST
  set -euo pipefail
  ENV="$1"; DIGEST="$2"
  SINCE=$(./ci/deployed-since.sh staging "$DIGEST" || echo "n/a")
  jq -n \
    --arg artifact "registry/app@$DIGEST" \
    --arg commit "$GITHUB_SHA" \
    --arg to "$ENV" \
    --arg by "${GITHUB_ACTOR}" \
    --arg at "$(date -u +%FT%TZ)" \
    --arg run "${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}" \

    | tee "promotion-$ENV.json" \
    | gh api "/repos/$GITHUB_REPOSITORY/deployments" --input - > /dev/null

DESTROY — TWO MECHANISMS, BECAUSE ONE ALWAYS FAILS

  # 1. on PR close
  on: { pull_request: { types: [closed] } }
  jobs:
    teardown:
      steps:
        - run: |
            kubectl delete ns "pr-${{ github.event.number }}" --ignore-not-found
            ./ci/preview-db.sh drop "pr_${{ github.event.number }}"

  # 2. the nightly reaper — this is the one that actually saves you
  # .github/workflows/preview-reaper.yml   (cron: '0 2 * * *')
  jobs:
    reap:
      steps:
        - run: |
            set -euo pipefail
            OPEN=$(gh pr list --state open --json number --jq '.[].number' | sort -u)
            NOW=$(date -u +%s)
            kubectl get ns -l preview=true \
              -o jsonpath='{range .items[*]}{.metadata.name} {.metadata.labels.pr} {.metadata.labels.ttl}{"\n"}{end}' \
            | while read -r ns pr ttl; do
                REASON=""
                grep -qx "$pr" <<<"$OPEN" || REASON="PR closed"
                [ "$(date -u -d "${ttl//_/:}" +%s)" -lt "$NOW" ] && REASON="TTL expired"
                if [ -n "$REASON" ]; then
                  echo "destroying $ns ($REASON)"
                  kubectl delete ns "$ns"
                  ./ci/preview-db.sh drop "${ns//-/_}"
                fi
              done
        - run: |
            LIVE=$(kubectl get ns -l preview=true --no-headers | wc -l)
            echo "live previews: $LIVE"
            [ "$LIVE" -lt 80 ] || echo "::warning::$LIVE previews live — check for leaks"

5 (hard): Move a question from staging to production: replace a staging soak with a canary plus synthetic monitoring, and show the detection improved.
Solution

The question being moved: "does this release handle real traffic patterns without errors or latency regressions?" — which staging answers badly, because it has no real traffic.

BEFORE — THE 4-HOUR STAGING SOAK

  deploy to staging -> synthetic load (a recorded, 6-month-old traffic
  mix) for 4 hours -> a human looks at a dashboard -> promote

  measured over 12 months:
    releases delayed by the soak ............ every one, by 4h
    regressions caught by the soak .......... 3
    regressions that reached production
      anyway .................................. 11
    reason: the recorded traffic mix no longer resembled reality
      (mobile share 31% -> 62%; a new endpoint was 40% of calls and
       appeared nowhere in the recording)

AFTER — CANARY IN PRODUCTION + CONTINUOUS SYNTHETICS

  1. canary stages with automated gates (see <deployment strategies>)
       1% / 10m  ->  5% / 20m  ->  25% / 15m  ->  100%
       gates: error rate vs control, p50 latency, new exception
              signatures, saturation, checkout conversion

  2. synthetic journeys every 60 s against production, always:
       - search -> product -> add to cart -> checkout (no payment capture)
       - login -> order history
       alert on 2 consecutive failures; page on 4

  3. staging keeps the questions it can answer:
       - migration rehearsal against a production-sized restore
       - destructive/load testing
       - integration during multi-service changes

🎯 Key Takeaways

  • Every environment must answer a question a cheaper one cannot. If it cannot, it is cost and risk without benefit.
  • Audit staging against real incidents. Measured: 17% caught, 55% not reproducible there, and 19% caused by staging-only differences — nine caused against eight caught, at $75,120/year.
  • Split the misses by cause: data volume and config drift are fixable in staging; real traffic and third-party behaviour are not, and belong to production detection.
  • Config keys present in only one environment are the highest-risk drift — the production code path has then never run anywhere else. Generate all environments from one template so a missing key fails the build.
  • Keep pool sizes and limits proportional: a staging pool a tenth the size made two production outages impossible to reproduce.
  • Bypass and debug flags in staging test a variant nobody runs — they mask exactly the code paths you are trying to validate.
  • Run at least two instances everywhere below production, or multi-instance bugs (races, cache coherence, session affinity) are structurally invisible.
  • Promote artifacts, not branches. Branch promotion rebuilds — production runs untested bytes — and the branches diverge until a hotfix exists only in one of them.
  • Promotion is a pointer change: the environment references an immutable digest, and promoting means updating that reference.
  • Write a promotion record — artifact, commit, who, when, soak time, tests, canary result. It answers "what is running and what proved it?" and is most of what an auditor wants.
  • With GitOps the audit trail is git history and rollback is git revert — but the pipeline must wait for and verify reconciliation, or it reports success before the change is live.
  • A shared staging is a queue: 47-minute median wait, 23 coordination messages a day, and changes tested together so failures are unattributable.
  • Per-PR previews replaced it at $310/month against $4,900 — using a schema per PR on one shared database server, scale-to-zero, fixture seeding and path filters.
  • The teardown job is the cost model, and it will fail: pair it with a TTL, a nightly reaper and an alert on live-preview count. Without one, 214 orphans accumulated at $2,100/month.
  • Give previews dedicated non-production credentials and fixture data — a preview URL is reachable by anyone who can open a pull request.
  • Some questions can only be answered in production: real traffic patterns, third-party behaviour, and whether users understand the change.
  • Money spent making staging realistic has a ceiling; money spent on production detection does not — replacing a 4-hour soak with canary plus synthetics took detection from 8m40s to 1m34s and caught 14 regressions against 3.
  • Build the production detection before removing the staging control, and run both for a few weeks — otherwise "shift testing right" becomes "stop testing".
  • Routine deploy approvals are rubber stamps: 412 a month, 18-second median, diff opened 11% of the time, zero rejections ever.
  • Automate "did the checks pass", reserve humans for the exceptional — schema changes, out-of-hours, first flag at 100% — and scope secrets per environment so a staging workflow cannot obtain production credentials at all.
