Test Strategy in CI Building & Testing

What you'll master: the test pyramid as an economic model rather than a rule — the shape follows from cost per test, and the cost that dominates is not runtime but diagnosis time, measured at 4 minutes for a failing unit test and 71 minutes for a failing end-to-end test; the placement rule that replaces arguing about ratios — test at the cheapest level that can actually catch the failure; what each layer owes you and what it must stop trying to prove; how mocks drift from the systems they imitate, with the measured consequence that eight production bugs passed a fully-green suite because the mocked HTTP client accepted a payload the real API rejected, and the contract tests that close that gap; test data and isolation, including the shared-database race that appears only when CI runs jobs in parallel; how to decide what runs on the PR versus after merge versus nightly, and how test-impact selection took a suite from 41 minutes to a median of 6 without deleting a test; and why line coverage is a Goodhart's-law gate — one team hit 84% coverage while mutation testing showed only 47% of injected bugs were caught. Prerequisites: What CI/CD Actually Is and Anatomy of a Pipeline; the next lesson, flaky tests, deals with the failure mode that destroys all of this.

Part 1 — The Pyramid Is an Economic Model

The pyramid is usually taught as a prescription — "lots of unit tests, some integration, few end-to-end" — which invites an argument about whether the ratios are right. They are not the point. The shape falls out of arithmetic once you measure what each kind of test costs, and the largest cost is invisible in every CI dashboard.

MEASURED: COST PER TEST, ONE REAL SUITE (1,100 tests, 8 months of history)

  layer          count   runtime    write    maintain     DIAGNOSE
                         per test   (first)  (per year)   a failure
  --------------------------------------------------------------------
  unit             847     0.3 s    12 min     4 min        4 min
  integration      198     4.1 s    38 min    22 min       18 min
  end-to-end        55    90.0 s   2.5 h      3.1 h        71 min
  --------------------------------------------------------------------
  total runtime    unit 4m14s | integration 13m32s | e2e 82m30s

  THE COLUMN THAT DECIDES EVERYTHING IS THE LAST ONE.
  A failing unit test names the function. A failing end-to-end test says
  "checkout is broken" and the engineer must reproduce a browser session,
  find which of eleven services misbehaved, and separate the real defect
  from the test's own fragility.

  ANNUAL COST OF THE E2E LAYER (55 tests):
    maintenance   55 x 3.1 h                     = 171 h
    diagnosis     55 x 4.2 failures/yr x 71 min  = 273 h
    runtime       (82 min x 3,000 runs)          = 4,100 runner-hours
    ------------------------------------------------------------------
    444 engineer-hours a year for 55 tests, or 8 hours per test per year.
🔑 The pyramid is what you get when you minimise total cost subject to catching the bugs that matter. Nobody should defend a ratio; they should defend a placement decision for each behaviour. That is why the useful rule is not "80% unit tests" but "test at the cheapest level that can actually catch this failure" — cheapest measured by diagnosis time, not by runtime.

1.1 The inverted pyramid, and how to recognise you have one

  HEALTHY                          INVERTED ("ice cream cone")
      /\   e2e     55                  ______________
     /  \  integ  198                  \  e2e  310  /   ← most coverage
    /____\ unit   847                   \ integ 92 /       lives here
                                         \ unit 40/
  symptoms of the cone, all measurable:
    - suite duration dominated by one layer            (82 of 100 minutes)
    - first-attempt pass rate below ~90%               (e2e is fragile)
    - "it failed, just re-run it" is normal            (see flaky-tests)
    - a one-line change takes 40 minutes to validate
    - nobody can say WHICH behaviour a failing test protects
    - the e2e suite is owned by a separate QA team, and the developers
      who break it are not the people who fix it       ← the real cause

The cone is almost never a testing decision; it is an organisational one. When the people writing features do not own the tests, tests accumulate at the only layer that can be written without touching the code — through the UI, from the outside. Fixing the ratio without fixing the ownership produces a smaller cone.

THE PLACEMENT RULE, APPLIED TO ONE FEATURE

  FEATURE: "orders over £500 require manager approval, and approval
            requests expire after 48 hours"

  behaviour to protect                       cheapest level that catches it
  ---------------------------------------------------------------------
  £499.99 does not require approval          unit  (boundary arithmetic)
  £500.00 does require approval              unit
  currency conversion before the threshold   unit
  expiry exactly at 48h vs 48h + 1s          unit  (inject the clock)
  the approval row is persisted with the
    right constraints and the unique index
    actually prevents duplicates             INTEGRATION (real database:
                                             an in-memory fake would not
                                             enforce the index)
  the notification service accepts our
    approval-request payload                 CONTRACT (schema, both sides)
  a manager can approve from the email link
    and the order proceeds                   E2E — ONE test, the journey
  ---------------------------------------------------------------------
  Result: 11 unit tests, 3 integration, 1 contract, 1 e2e.
  The tempting alternative — 6 e2e tests covering the threshold cases —
  costs 6 x 8 h/year and diagnoses at 71 minutes instead of 4.
💡 Ask "what would have to be broken for this test to fail?" If the honest answer is a long list, the test is at the wrong level: it will fail for reasons unrelated to the behaviour it claims to protect, and every one of those failures costs the expensive diagnosis time. A good test has a short, specific answer to that question.

Part 3 — Doubles, Drift, and the Bugs That Pass a Green Suite

Every test that does not use the real dependency is trading fidelity for speed. That trade is often correct — and the moment nobody re-checks it, the suite starts certifying a world that no longer exists.

DoubleWhat it isGood forDrifts because
StubReturns canned valuesIsolating logic from slow or nondeterministic inputsThe real thing changes its response shape
MockAsserts on calls made to itVerifying an interaction that has no other observable effectIt encodes your belief about the API; beliefs go stale
FakeA working lightweight implementation (in-memory repository)Fast tests with realistic behaviourIt implements the happy path, not the constraints (see below)
Real, containerisedThe actual Postgres/Kafka/Redis, in a containerAnything where the dependency's semantics are the pointDoes not drift — costs seconds instead of milliseconds
Recorded (VCR/cassette)Replays a captured real interactionThird-party APIs you cannot runThe recording ages silently; re-record on a schedule
THE MEASURED FAILURE: A MOCK THAT WAS WRONG FOR FIVE MONTHS

  the test (green, 1,400 runs):
    mock_http.post.return_value = Response(201, {"id": "abc"})
    result = notifier.send(approval_request)
    assert result.id == "abc"
    mock_http.post.assert_called_once_with("/v2/notify", json=payload)

  the reality, discovered in production:
    - the API had required `idempotency_key` since March (400 without it)
    - it returned 202, not 201, for async delivery
    - `id` was renamed to `notification_id` in v2.1

  the mock asserted our BELIEF about the API and never checked it.
  8 production defects over 5 months passed a fully green suite.

  WHAT WOULD HAVE CAUGHT EACH ONE
    required field added     -> contract test against the published schema
    status code changed      -> contract test, or one integration test
                                against a real sandbox
    field renamed            -> contract test
    (a nightly recorded-cassette refresh would have caught all three,
     and is the cheapest option when the provider has a sandbox)

3.1 Fakes lie about constraints, specifically

  the in-memory repository fake:
      def save(self, order):  self._items[order.id] = order

  what it silently does NOT enforce, all of which the real database does:
    - UNIQUE (customer_id, idempotency_key)   -> duplicate orders in prod
    - CHECK (total_cents >= 0)                -> negative totals accepted
    - FOREIGN KEY to customers                -> orphan rows
    - NOT NULL on a column added last month   -> insert fails only in prod
    - transaction isolation and lock ordering -> the deadlock nobody saw
    - the ORM's ACTUAL generated SQL          -> N+1 queries, wrong joins

  RULE: business logic against a fake is fine. PERSISTENCE BEHAVIOUR must
  be tested against the real engine — same major version as production —
  because the value of a database is precisely the constraints a fake omits.
⚠️ Test containers made this argument obsolete. "A real database is too slow for CI" was true when it meant a shared, hand-maintained instance. A containerised Postgres starts in about 1.2 seconds, is per-run isolated, and can be reused across a whole job — measured at 4.1 seconds per integration test including setup, against 0.3 for a fake. For the tests where constraints and SQL are the behaviour under test, that is a bargain; see containers in CI for making it fast.

Part 4 — Test Data and Isolation

Isolation problems have a signature: everything passes locally and on a quiet CI runner, then fails once jobs run in parallel or the suite is sharded — which is exactly when you introduced them by trying to go faster.

StrategyHow it isolatesCostWhen it breaks
Transaction rollback per testEach test runs in a transaction, rolled back afterVery cheapCode under test commits, or uses a second connection
Truncate between testsWipe tables after each testCheap; slower than rollbackParallel workers on one database wipe each other's rows
Schema/database per workerEach parallel worker gets its ownSetup per workerRarely — this is the robust default for parallel suites
Container per jobWhole engine per CI job~1–3 s startupRarely; costs runner memory
Shared long-lived test databaseIt does notZero, apparentlyAlways, eventually — and the failures look like flakes
THE RACE THAT ONLY APPEARS WHEN YOU SHARD

  before sharding: 1 worker, 1 database, green for two years
  after sharding:  4 workers, 1 database, ~9% of runs red

  $ pytest -n 4
  FAILED tests/test_reports.py::test_monthly_totals
    assert 4 == 7        # another worker inserted three orders mid-test

  FIXES, IN ORDER OF PREFERENCE
   1. a database per worker (the runner's test framework usually
      exposes a worker id):
        DB_NAME="test_${PYTEST_XDIST_WORKER:-0}"
   2. every test creates its own data with unique keys — no reliance on
      "the database contains exactly these rows"
   3. transaction-per-test rollback, where the code under test allows it
   ANTI-FIX: pinning the ordering, adding sleeps, or marking the test
   serial. Those hide the coupling and it returns as a flake later.

4.1 Fixtures versus factories

  ❌ SHARED FIXTURE FILE (the "seed data" everyone depends on)
     fixtures/orders.json — 340 rows, added to for four years
     test_refund_window relies on order #17 being 29 days old
     ... which is only true because it was written in 2024 with a
     hardcoded date. It now fails once a year, for a day.

  ✅ FACTORY, EXPLICIT PER TEST
     order = OrderFactory(created_at=now - timedelta(days=29),
                          total_cents=50_00, status="paid")
     assert refund_window_open(order) is True

  the factory version states the ONE property the test depends on.
  A reader can see why the test passes; a shared fixture makes that
  invisible, which is why shared-fixture suites become unmaintainable
  faster than any other kind.

Part 5 — What Runs Where, and Test Selection

The blocking PR pipeline has a budget — under ten minutes, because past thirty people stop treating it as a gate. Everything else is a placement decision.

🔑 Selection is a bet that you can enumerate the dependency edges, so make the fallback loud and the always-run set explicit. The single escaped defect above came from a runtime-loaded config file — an edge no coverage-based mapping can see. Treat "I am not sure" as "run everything": the whole value is in the median case, and being conservative in the unusual case costs almost nothing.

Part 6 — Coverage, Goodhart's Law, and Mutation Testing

Line coverage measures which lines executed while the tests ran. It does not measure whether anything was asserted, which is why it is so easy to satisfy without improving anything.

  THIS FILE HAS 100% LINE COVERAGE

    def test_everything():
        calculate_price(100, "GBP", tier="gold")
        apply_discount(order, code="SUMMER")
        render_invoice(order)
        # no assertions whatsoever

  and the gate is green. Coverage answers "did this line run?", never
  "would a bug in this line be caught?"

  MUTATION TESTING ANSWERS THE SECOND QUESTION:
    it edits your code (> becomes >=, + becomes -, a condition is
    negated, a return value is replaced) and re-runs the tests.
    A mutant that survives is a change to your program that NO test
    noticed — a hole, precisely located.

  MEASURED ON THE SAME CODEBASE
    line coverage ............ 84%      (the gate everyone celebrated)
    mutation score ........... 47%      (53% of injected bugs survived)

    where the survivors clustered:
      error-handling branches      81% survived   (executed, never asserted)
      boundary comparisons         66% survived   (>= vs > unnoticed)
      logging/observability code   94% survived   (fine — do not chase these)
      pricing rules                12% survived   (this area was genuinely
                                                   well tested)
MetricAnswersGameable byUse it as
Line coverageWhich lines ranTests with no assertions; testing gettersA ratchet on new code — never an absolute target
Branch coverageWhich decisions were taken both waysSame, with more effortBetter than line; same caveats
Mutation scoreWould a real bug be caught?Very hard to gameA nightly diagnostic, targeted at critical modules
Escaped-defect rateWhat actually reached productionNot gameable — it is the outcomeThe metric that matters; the others are proxies for it

The practical policy: do not set an absolute coverage target (it is met by testing trivial code and destroys credibility for every later request). Instead, require that coverage on changed lines does not fall — a ratchet, which is honest and cheap — and run mutation testing nightly on the modules where bugs are expensive, using the survivor list as a to-do list rather than a score to defend. Mutation runs are slow, so scope them: the payments module, not the whole repository.

❌ 310 end-to-end tests, 40 unit tests, mocks asserting a five-year-old belief about a third-party API, one shared test database, a 340-row fixture file, the whole suite blocking every pull request for 41 minutes, and an 80% line-coverage gate. The suite costs 444 engineer-hours a year at the end-to-end layer alone, and each failure takes 71 minutes to diagnose because "checkout is broken" names no function. Eight production defects walked through it green, because the mocked HTTP client happily accepted a payload the real API had been rejecting since March. The fakes never enforced a unique index, so duplicate orders reached production, and the in-memory repository never showed the N+1 query that the ORM actually generates. Sharding the suite to go faster turned a two-year-green run into a 9% failure rate, because four workers share one database and one test asserts the row count. The fixture file contains an order whose age was hardcoded in 2024, so one test fails for a day each year. And the coverage gate reads 84% while mutation testing shows 53% of injected bugs survive — with 81% surviving in error handling, which is where the incidents come from.

✅ Placement decided per behaviour by diagnosis cost, real dependencies where semantics matter, contracts checked rather than believed, per-worker isolation, a ten-minute blocking budget, and coverage used as a ratchet with mutation testing as the real diagnostic. For each behaviour ask what would have to be broken for the test to fail, and put it at the cheapest level that can catch it — eleven unit tests, three integration, one contract and one journey, rather than six end-to-end tests of arithmetic. Use containerised Postgres for anything where constraints, transactions or generated SQL are the behaviour under test, because a fake omits exactly the value the database provides. Replace belief-based mocks with contract tests against the published schema, and refresh recorded cassettes on a schedule so drift surfaces nightly rather than in an incident. Give every parallel worker its own database and let every test create the data it depends on, so sharding makes the suite faster instead of flaky. Keep the blocking pipeline under ten minutes with test-impact selection — 41 minutes to a median of 6, with the full suite post-merge, an explicit always-run set for auth, money and migrations, and a loud fallback whenever the mapping is unsure. Then stop defending a coverage number: ratchet coverage on changed lines, run mutation testing nightly on the modules where bugs are expensive, and treat the survivors as a to-do list.

Interview Questions

Beginner: What is the test pyramid, and why is that shape recommended?

The pyramid describes a suite with many fast, narrow tests at the bottom (unit), fewer tests that exercise real boundaries in the middle (integration), and a small number of full-journey tests at the top (end-to-end).

The reason is economic, and the decisive cost is not runtime — it is diagnosis time. In one measured suite a failing unit test took about 4 minutes to diagnose because it names the function; a failing end-to-end test took about 71 minutes, because "checkout is broken" could mean any of eleven services, the test's own fragility, or the environment. Add maintenance and the 55 end-to-end tests cost roughly 444 engineer-hours a year — about 8 hours per test per year.

The better way to state the rule, which avoids arguing about ratios: test each behaviour at the cheapest level that can actually catch its failure. Business rules and boundaries go in unit tests; anything where a real database's constraints or a real HTTP layer is the point goes in integration; and end-to-end is reserved for a handful of critical journeys. The pyramid shape is the result of applying that rule, not a target to hit.

Beginner: When should you use a mock, and when should you use the real dependency?

Use a double when the dependency is slow, nondeterministic, expensive, or outside your control — and when the behaviour under test does not depend on that dependency's semantics. Use the real thing when the dependency's semantics are the behaviour under test.

Testing…UseBecause
Pricing rules that call a clockInjected fake clockDeterminism; the real clock adds nothing
That a unique constraint prevents duplicatesReal database (container)A fake dictionary enforces no constraints
That the ORM generates a sane queryReal databaseN+1s and bad joins are invisible to a fake
A third-party payment API's success pathRecorded interaction or their sandboxYou cannot run their system; but the recording must be refreshed
That you call the notifier exactly onceMockThe interaction has no other observable effect

The trap worth naming: a mock encodes your belief about the other system, and beliefs go stale. In one measured case, mocked HTTP tests stayed green for five months while the real API had added a required field, changed a status code and renamed a response field — eight production defects passed a fully green suite. Contract tests against the published schema, or a nightly refresh of recorded interactions, are what close that gap.

Mid: Your test suite takes 41 minutes and blocks every pull request. How do you get it under ten without deleting coverage?

In this order, because each step is cheaper and safer than the next:

StepTypical effect
Move what does not need to block — the full end-to-end suite, performance, long integration runs — to post-merge and nightlyUsually the single biggest win; the checks still run, just not in the blocking path
Shard by recorded duration across parallel workers, with per-worker isolationNear-linear until the setup cost dominates
Test-impact selection — run the tests that touch changed code, plus an always-run set41 min → 6 min median in the measured case, at 7.6% of the suite selected
Fix the slowest tests — usually a handful with sleeps or per-test container startsA long tail; do it after the structural wins
Reuse expensive setup — one container per job rather than per test; cache dependency installsRemoves fixed overhead from every shard

The safety conditions that make selection acceptable — and I would state them unprompted, because without them it is reckless: the full suite still runs post-merge and nightly, so an escape is caught in hours rather than in production; there is an explicit always-run set for auth, money, migrations and security; and the tool falls back to the full suite whenever it is unsure — a changed lockfile, changed CI config, or stale mapping data. In the measured month, one defect escaped selection: a config file read at runtime, an edge no coverage-based mapping can see. That is the residual risk, and it is why the post-merge full run is not optional.

Mid: The team wants an 80% coverage gate. What do you say?

I would push back on the gate and offer two things that measure what they actually want.

Why the gate fails: line coverage measures which lines executed, not whether anything was asserted. A test that calls three functions with no assertions produces 100% coverage of them. Measured on one codebase, line coverage was 84% while mutation testing showed only 47% of injected bugs were caught — 81% of mutants survived in error-handling branches, which is exactly where incidents come from. An absolute gate is also met by testing getters and configuration constants, which costs real time and buys nothing, and it burns credibility for the next quality request.

What I would propose instead:

  • A ratchet on changed lines: coverage of the diff must not fall below the file's current level. It is cheap, it is honest, and it applies pressure exactly where new risk enters.
  • Mutation testing nightly on the modules where bugs are expensive — payments, auth, pricing — with the surviving mutants as a ranked to-do list rather than a score to defend. Not repository-wide: mutation runs are slow and most survivors in logging code are harmless.
  • Track escaped defects — the outcome all of this is a proxy for. If that number is falling, the strategy is working regardless of the percentages.

If the organisation insists on a number for reporting, coverage-on-changed-lines is the one to give them: it is the version of the metric that cannot be satisfied by writing tests for trivial code that nobody was going to break.

Senior: You inherit a suite of 310 end-to-end tests with a 9% failure rate and no unit tests. What is your plan?

Do not start by deleting tests — they are the only executable description of the system's behaviour, however badly expressed. And do not start by writing unit tests either, because nothing will change until the suite becomes trustworthy.

PhaseActionWhy in this order
1. Make the signal honestQuarantine the flakiest tests (they are 9% of runs and are training everyone to retry); track first-attempt pass rateUntil red means broken, no other change can be evaluated
2. Measure what they coverCoverage from the e2e run, plus a list of journeys by business importanceTells you what you would lose by rebalancing, in specifics
3. Stop the bleedingNew behaviour gets unit and integration tests, written by the feature engineer; no new e2e without justificationThe inflow is why the cone exists
4. Replace, don't deleteFor each e2e test, write the cheaper tests that cover the same behaviour, then retire it — as a pair, in one PRCoverage never drops, so the change is defensible at any point
5. Move the survivors out of the blocking pathThe remaining journeys run post-merge and pre-release, not on every PRReturns the ten-minute feedback loop immediately
6. Fix the ownershipFeature teams own the tests for their features, including the journeysWithout this, the cone regrows within a year

The organisational point I would make to leadership: the cone is nearly always a structural symptom — a separate QA group writing tests from the outside because they cannot touch the code. Rebalancing the suite without changing who writes tests produces a smaller cone and the same trajectory. Expect the whole programme to take two to three quarters, and report it with the numbers that matter: first-attempt pass rate, blocking-pipeline duration, and escaped defects — not test counts, which will fall and look like regression.

Senior: How do you test the boundary between two services owned by different teams, without running both?

Contract testing, which replaces "we both ran the same integration environment" with "each side independently verifies the same agreed contract".

ApproachWhat it givesWhat it costs
Shared integration environmentHigh fidelitySlow, contended, flaky, and broken by whoever deployed last — the failure is never attributable
Consumer-driven contracts (e.g. Pact)The consumer publishes expectations; the provider verifies them in its own pipelineA broker to run; discipline about who publishes what
Schema-first (OpenAPI/protobuf) + compatibility checksBreaking changes caught at build time on the provider sideOnly catches shape, not semantics
Recorded interactions refreshed nightlyCheap drift detection against a real sandboxNot a contract — it detects change after the fact

The property that makes contracts worth the setup: failures are attributable and arrive at the right team. When a provider's pipeline fails its consumer-contract verification, the message is "this change breaks shop-api's expectation of field notification_id" — before deploy, in the provider's own build, with no shared environment involved. Compare that with the alternative, where the same problem surfaces days later as an intermittent failure in a shared staging environment that three teams are simultaneously deploying to.

What I would still keep: a very small number of true end-to-end journeys through the real system. Contracts verify that both sides agree on the messages; they do not prove that the overall journey works, and something should exercise the whole path before customers do. One or two tests, run post-merge — not thirty, run on every PR.

🎯 Key Takeaways

  • The pyramid is an economic model, not a rule. Measured cost per test per year: unit 0.07 h, integration 0.46 h, end-to-end 8.07 h — 4.6% of the tests consumed 74% of the cost.
  • Diagnosis time dominates, and no dashboard shows it: 4 minutes for a failing unit test, 18 for integration, 71 for end-to-end — and 44% of those e2e failures were the test's own fragility.
  • Replace ratio arguments with a placement rule: test each behaviour at the cheapest level that can actually catch its failure, and ask "what would have to be broken for this test to fail?"
  • The inverted pyramid is an ownership problem, not a testing one — when feature engineers do not own tests, tests accumulate at the only layer writable from outside the code.
  • Each layer has a contract: unit proves logic, integration proves the boundary with a real dependency, contracts prove two services still agree, e2e proves a handful of journeys, smoke proves the deployed thing is alive.
  • A mock encodes your belief about another system, and beliefs go stale. Eight production defects passed a green suite for five months while the real API had added a required field, changed a status code and renamed a response field.
  • Fakes omit exactly what a database is for: unique indexes, checks, foreign keys, isolation and the ORM's real SQL. Persistence behaviour needs the real engine, same major version as production.
  • A schema-validating double is the cheapest big win — it keeps a mock's speed while failing when your assumption is wrong.
  • Consumer-driven contracts make failures attributable: the provider's own pipeline fails, naming your service, before they deploy — unlike a shared staging environment where nothing is attributable.
  • Isolation failures appear the day you parallelise. One shared database plus four workers turned a two-year-green suite into a 9% failure rate that everyone called flakiness.
  • Fix isolation structurally — a database per worker, unique keys per test, no assertions on global state, rollback per test — and never with sleeps or pinned ordering, which hide the coupling until later.
  • Run the suite in parallel and in random order even if you do not need the speed, so latent coupling fails immediately instead of six months after it was written.
  • Factories over shared fixture files. A factory states the one property the test depends on; a 340-row fixture hides why the test passes and eventually fails for a day each year.
  • Keep the blocking pipeline under ten minutes by placement: unit plus affected integration on the PR, full integration and e2e post-merge, heavy suites nightly, smoke post-deploy.
  • Test-impact selection took a 41-minute suite to a 6-minute median at 7.6% of tests selected — but only with a full post-merge run, an explicit always-run set, and a loud fallback whenever the mapping is stale or a lockfile changed.
  • The one escape in 612 PRs came from a config file read at runtime — an edge no coverage-based mapping can see, which is why selection is a bet that needs a net.
  • Line coverage answers "did this line run?", never "would a bug be caught?" A test with no assertions gives 100% coverage.
  • Measured: 84% line coverage, 47% mutation score — 81% of survivors in error-handling branches, which is where incidents come from. Killing the ones that mattered moved coverage 2 points and mutation score 36.
  • Use coverage as a ratchet on changed lines, never as an absolute target; run mutation testing nightly on the modules where bugs cost money, and treat survivors as a ranked to-do list rather than a score.
  • Escaped-defect rate is the only ungameable metric — everything else in this lesson is a proxy for it, and should be justified by moving it.
