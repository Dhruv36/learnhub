What CI/CD Actually Is Foundations

What you'll master: the definition the tooling obscures — continuous integration is a practice about how often work is merged, not a product that runs tests on a pull request, and a team whose branches live nine days is not doing CI however green its checks are; the arithmetic that makes this concrete, where merge conflicts rose from 4% of PRs at one day old to 61% at fourteen days in a measured repository; why the pipeline's duration changes engineers' behaviour rather than merely their patience — a 34-minute pipeline cost 71 engineer-hours a week of waiting and, more expensively, produced batching, speculative merging and review-while-red; the difference between continuous delivery (always releasable) and continuous deployment (every green commit ships), and the batch-size argument that makes small deploys safer rather than riskier — change failure rate stays roughly constant per change, so a 20-commit deploy carries 20 changes' worth of risk and none of the attribution; the five guarantees a pipeline must provide before its green tick means anything; what a broken trunk actually costs (measured: 38 minutes red × 24 blocked engineers); and the reason CI/CD initiatives fail in real organisations, which is almost never the tool. No prerequisites beyond basic Git — this is the entry point to the track, and it sets up branching, pipeline anatomy and everything after them.

Part 1 — Continuous Integration Is About Merging, Not About Testing

Ask ten teams whether they do CI and ten will say yes, because they all have a file in .github/workflows/ that runs tests on a pull request. Ask how long a typical branch lives before it reaches main and the answers spread from four hours to three weeks. Only the first group is doing continuous integration; the rest have automated testing on isolated work, which is a good thing that is not the same thing.

What people mean by "we have CI"What continuous integration is
A pipeline existsEvery engineer merges to trunk at least daily
Tests run on a PRThe integrated result is verified, continuously
The build is greenThe trunk is releasable, and is kept releasable
A tool was purchasedA practice was adopted, with the tool as support

The distinction matters because integration risk does not accumulate linearly with time — it accelerates. Two branches that diverge for a day touch a small number of the same lines. The same two branches over two weeks touch refactors, renames, dependency bumps and each other's new files.

MEASURED: PR MERGE OUTCOMES BY BRANCH AGE (one repo, 1,847 PRs, 6 months)

  branch age at merge   PRs     conflicted   needed rework   mean review rounds
  ---------------------------------------------------------------------------
  under 1 day           612          4%            6%              1.2
  1-2 days              498          9%           11%              1.5
  3-5 days              371         21%           19%              2.1
  6-13 days             244         43%           34%              3.4
  14+ days              122         61%           52%              4.9
  ---------------------------------------------------------------------------
  The 122 oldest PRs (6.6% of the total) consumed 31% of all review comments
  and produced 44% of all post-merge reverts.
🔑 Branch age is the single most predictive number in this whole track. It drives conflict rate, review quality, revert rate and the size of the change a reviewer must hold in their head — and unlike test coverage or pipeline duration, it is entirely within a team's control today, with no tooling change required. If you measure one thing after this lesson, measure the age distribution of merged branches.

The counter-argument is always the same: "our changes are too big to merge daily". That is a statement about how work is decomposed, not about the domain. The techniques that make it possible — feature flags, branch by abstraction, expand/contract schema changes, shipping code that is dormant until enabled — are exactly the techniques that also make deployment safe, which is why teams that adopt them get two benefits from one investment.

Part 2 — The Feedback Loop Is the Product

A pipeline's duration is usually discussed as a comfort issue. It is not: past certain thresholds it changes what engineers do, and those behaviour changes cost far more than the waiting.

Pipeline durationWhat engineers doSecond-order cost
Under ~2 minWait, watching. Fix and re-push immediatelyNone — this is the goal
2–10 minSwitch to something small, come backMinor context switching
10–30 minStart another task; return later, or after lunchReal context loss; two changes in flight at once
30–60 minBatch several changes into one push to "save" runsBigger changes, harder bisect, weaker attribution
Over an hourMerge speculatively before it goes green; review while red; retry rather than read failuresThe signal is now advisory — the pipeline has stopped being a gate
THE DIRECT COST, AND THE ONE PEOPLE MISS

  pipeline duration            34 min (p50), 52 min (p90)
  runs per day                 118 (60 merges + PR pushes + main builds)
  engineers                    24

  DIRECT: waiting
    conservatively, an engineer waits for 30% of the runs they trigger
    118 x 0.30 x 34 min = 20 engineer-hours per DAY of active waiting
    ... measured differently (time between push and next commit by the
        same author) it was 71 engineer-hours per WEEK. Use whichever
        number your leadership finds harder to ignore.

  INDIRECT: what the 34 minutes caused
    - median PR size grew from 180 to 410 changed lines in 8 months
      (people batched to avoid paying the 34 minutes repeatedly)
    - 22% of merges happened before the pipeline finished ("it'll be fine")
    - the flaky-test retry button was pressed 340 times in a month,
      and nobody read the failures any more
    - deploys moved from daily to twice-weekly, so each one carried more

  COMPUTE COST of the same 118 runs: about $140/month. The pipeline was
  optimised for the $140 and not for the 71 hours, for four years.
⚠️ The point at which a pipeline stops being a gate is a behavioural threshold, not a technical one. Once people merge before it finishes or retry without reading, the tick is decoration — you are paying the full cost of the pipeline and receiving none of the guarantee. That is why pipeline performance and flakiness are correctness topics in this track, not comfort topics.

Part 3 — CI, Continuous Delivery, Continuous Deployment

PracticeThe claim it makesWhat it requires
Continuous IntegrationEveryone's work is merged and verified continuouslyShort-lived branches, a fast trustworthy build, a releasable trunk
Continuous DeliveryAny green commit could be released, at any time, by pressing a buttonAll of CI, plus automated deploys, environment parity, migrations that are safe, rollback that works
Continuous DeploymentEvery green commit is released, with no human stepAll of CD, plus production verification, progressive rollout, automated rollback, and organisational trust

The gap between the second and third is smaller technically and larger culturally than people expect. If your delivery is genuinely continuous — a button exists, and pressing it is boring — then removing the button is mostly a decision about whether you trust your production verification. If pressing the button is an event that requires a person who knows things, you do not have continuous delivery; you have automated deployment with a human safety net that is doing real work.

3.1 Why smaller, more frequent deploys are safer

This is counter-intuitive to anyone who has been through a bad release, and it is the argument the whole discipline rests on. The intuition says: deploying is risky, so deploy less. The data says the opposite, and the reason is arithmetic rather than ideology.

BATCH SIZE AND RISK

  Assume a per-change probability of causing an incident, p ≈ 1.5%
  (this is roughly stable for a given team and codebase; it is a property
  of how changes are made, not of how they are shipped)

  WEEKLY DEPLOY, 20 changes per release
    P(release contains at least one bad change) = 1 − (1 − 0.015)^20 = 26%
    when it breaks:
      - 20 candidate causes to bisect
      - rollback removes 19 good changes with the bad one
      - the author of the bad change made it up to 5 days ago
      - mean time to identify (measured):        47 min
      - mean time to restore (measured):         64 min

  DAILY DEPLOY, 4 changes per release
    P(release contains at least one bad change) = 1 − (1 − 0.015)^4 = 5.9%
    when it breaks:
      - 4 candidates, all recent, all with their authors present
      - mean time to identify (measured):        11 min
      - mean time to restore (measured):         19 min

  DEPLOY-ON-MERGE, 1 change per release
    P(bad) = 1.5%; the cause is known before you finish reading the alert
    mean time to restore (measured):              6 min (automated rollback)

  Total risk exposure per week is similar in aggregate — what changes
  enormously is ATTRIBUTION and RECOVERY. Small batches do not make
  failures rarer; they make failures cheap.
🔑 "Deploy less often to be safer" optimises the wrong variable. It reduces the number of deploy events while increasing the cost of each one, and it delays the feedback that would have prevented the next bad change. The honest version of the safety argument is about blast radius and recovery — which is what deployment strategies and progressive delivery exist to bound.

Part 4 — The Five Guarantees a Pipeline Must Provide

A green tick is a claim. These are the five properties that make the claim mean something; a pipeline missing any of them can be green while the software is broken.

GuaranteeWhat it meansHow it is violated in practice
1. ReproducibilityThe same commit produces the same result, on any runner, at any timeUnpinned dependencies, latest tags, tests that read the wall clock or the network
2. IsolationA run cannot be affected by a previous run or a concurrent oneSelf-hosted runners with leftover state, a shared test database, a fixed port
3. ImmutabilityThe artifact tested is bit-for-bit the artifact deployedRebuilding per environment — the classic "it passed in staging" cause
4. Honest signalGreen means it works; red means it is brokenFlaky tests, || true, a test suite that silently ran zero tests
5. SpeedFast enough that people wait for itCovered in Part 2 — beyond a threshold the other four stop being enforced
GUARANTEE 3 IS THE ONE PEOPLE BREAK MOST, AND IT LOOKS HARMLESS

  BAD                                    GOOD
  ------------------------------------   ------------------------------------
  build in CI, test it                   build ONCE, in CI
  build again for staging, deploy        test THAT artifact
  build again for prod, deploy           promote THAT artifact to staging
                                         promote THAT SAME artifact to prod
  three builds, three artifacts,
  one of which was never tested          one artifact, tested once, deployed
                                         everywhere — "build once, promote"

  the incident: a base image published a new patch between the staging
  build and the production build. Staging ran glibc 2.36, production ran
  2.37, and a native dependency crashed only in production. The commit
  hash was identical in both, which is why it took 3 hours to find.

Guarantee 4 deserves a specific warning, because it fails silently and often. A test suite that exits zero having run nothing looks exactly like a test suite that passed — same green tick, same duration if the suite was fast, no output anyone reads.

THE SILENT ZERO — THREE REAL VERSIONS

  1. a test-path glob stopped matching after a directory rename
       $ pytest tests/unit/
       collected 0 items ... exit code 5
       (CI treated any non-crash as success)  -> 8 WEEKS with no unit tests

  2. a shell step without pipefail
       $ set -e
       $ run-tests | tee results.txt      # exit code is tee's: 0. Always.

  3. a "temporary" skip
       @pytest.mark.skip(reason="fix in JIRA-4192")   # added 14 months ago
       141 of 1,100 tests were skipped; the count was in the log nobody read

  THE FIX, and it is three lines:
    - assert a MINIMUM test count in CI (fail if collected < 1000)
    - set -euo pipefail in every shell step
    - fail the build when skipped tests exceed a threshold, and report
      the skip list in the PR

Part 5 — Trunk Hygiene: What a Broken Main Costs

If the trunk must be releasable, then a red trunk is an incident — not a nuisance to be worked around. Teams under-react to it because the cost is distributed across everyone else's day and therefore appears on nobody's ticket.

MEASURED: MAIN BRANCH RED TIME, ONE QUARTER

  incidents of red main                       61
  median time to green                        38 min
  p90 time to green                         3h12m
  engineers blocked (cannot merge or must
    merge onto a broken base)                 24

  61 x 38 min x 24 engineers = 927 engineer-hours per quarter
    ... of which most is not idle time, it is people building on a
    broken base and inheriting failures they did not cause,
    which is worse than idle time because it destroys the signal.

  WHAT CHANGED IT (in order of effect)
   1. MERGE QUEUE: changes are tested against the post-merge state before
      landing. Red-main incidents 61 -> 7 in the following quarter.
   2. REVERT FIRST: the rule is revert, then diagnose at leisure.
      Median time to green 38 min -> 6 min.
   3. STOP THE LINE: while main is red, nobody merges anything else.
      This is unpopular for a week and then never controversial again.
💡 Revert-first is a cultural change disguised as a technical one. The instinct is to fix forward, because reverting feels like an admission and the fix "will only take ten minutes". It rarely does, and while it is being written, every other engineer is blocked. Make the revert a routine, blameless, one-click action — and make it the default in the incident runbook — and the median red time falls by an order of magnitude, which no amount of pipeline tuning achieves.

Part 6 — Why CI/CD Initiatives Actually Fail

Almost never the tool. In five years of watching these efforts, the causes cluster into four, and all four are visible before the migration starts.

CauseSignatureWhat actually fixes it
Nobody owns the pipelineIt is everyone's and no one's; the last person to touch it is the reluctant expert; no on-call, no SLOExplicit ownership, a build-time SLO, and pipeline failures triaged like production incidents
Gates people route aroundA required approval that is rubber-stamped; a coverage gate met by testing getters; [skip ci] in 15% of commitsMake the control preventive and invisible (see quality gates), or remove it and stop pretending
Flakiness eroding trustThe retry button is muscle memory; red is assumed to be noise until proven otherwiseQuarantine, measure and fix — a whole lesson, because it destroys the entire value proposition
The pipeline is unmonitored productionNobody knows the p50 duration, the queue time, or the success rate; capacity is discovered during a release freezeTreat it as a service: dashboards for duration, queue time, success rate and cost

Notice what is absent from that list: the choice between GitHub Actions, GitLab CI, Jenkins, Buildkite or CircleCI. The tool determines how pleasant the YAML is and how the runners are managed; it does not determine whether branches are short-lived, whether the trunk is protected, whether the signal is honest, or whether anyone owns the thing. Teams migrate tools hoping to buy the practice, and arrive with the same four problems expressed in a new syntax.

❌ A pipeline that runs tests on pull requests whose branches live for a week, takes 34 minutes, is retried until green, rebuilds the artifact separately for each environment, is owned by nobody, and is measured only by whether it is currently green. The branches are old enough that 43% of them conflict and 34% need rework after review, so the review itself is superficial — nobody reads a 400-line diff carefully at the fourth round. The 34 minutes taught everyone to batch, so PRs grew from 180 to 410 lines, which made the conflicts worse in a loop that nobody attributes to the pipeline. Because flaky tests are common, red is assumed to be noise, and the retry button was pressed 340 times in a month without anyone reading a failure — so the one real failure in that month was retried into production. Each environment gets its own build, so the artifact in production was never the artifact that was tested, and a base-image patch between two builds produced a crash that took three hours to explain against an identical commit hash. Meanwhile main was red for 927 engineer-hours a quarter, which appeared in no budget, and the "CI/CD improvement" on the roadmap is a migration to a different tool.

✅ Integration measured by branch age, a pipeline fast enough that people wait for it, an honest signal, one artifact promoted through environments, a protected trunk with a merge queue and a revert-first rule, and an owner with an SLO. Track the age distribution of merged branches and drive p90 under two days by decomposing work with feature flags and expand/contract migrations — the same techniques that make deployment safe. Treat pipeline duration as a correctness property, not a comfort one, because past ~30 minutes the gate stops being a gate. Enforce the five guarantees explicitly: pin dependencies, isolate runs, build once and promote, assert a minimum test count with set -euo pipefail, and quarantine flaky tests instead of retrying them. Protect main with a merge queue that tests the post-merge state (61 red-main incidents fell to 7), make revert the default response (38 minutes to 6), and stop the line while it is red. Deploy small and often so that failures are cheap rather than rare: 20-change releases fail 26% of the time with 20 suspects, and single-change deploys fail 1.5% of the time with the cause already named. Then give the pipeline a team, an SLO and a dashboard, because an unmonitored pipeline is unmonitored production.

Interview Questions

Beginner: What is the difference between continuous integration, continuous delivery and continuous deployment?

Continuous integration is the practice of everyone merging their work into the trunk frequently — at least daily — with the integrated result verified automatically each time. The emphasis is on the merging; the automation exists to make frequent merging safe.

Continuous delivery means every green commit on the trunk is releasable: the deployment is automated, environments are consistent, migrations are safe, and shipping is a button press rather than a project. The trunk is always in a shippable state.

Continuous deployment removes the button: every green commit goes to production automatically. It requires everything above plus production verification and automated rollback, which is why teams stop at delivery and that is a legitimate choice.

The addition that shows you have thought about it: many teams have automated testing on long-lived branches and call it CI. If branches live for a week, there is no continuous integration happening — the work is being isolated, which is the opposite. The diagnostic question is not "do you have a pipeline?" but "how old is a typical branch when it merges?"

Beginner: Why is a fast pipeline important? Is a 30-minute build really a problem?

Yes, and not mainly because of the waiting. Duration changes behaviour:

  • Under about two minutes, engineers wait and iterate — the ideal loop.
  • Between ten and thirty minutes, they context-switch and hold two changes in flight.
  • Past thirty minutes, they batch changes to avoid paying repeatedly, which makes each change bigger, harder to review and harder to bisect.
  • Past an hour, they merge speculatively before it goes green and retry failures rather than reading them — at which point the pipeline is no longer a gate at all.

The measured version: a 34-minute pipeline in a 24-engineer team accounted for roughly 71 engineer-hours a week of waiting, and its second-order effects were larger — median PR size grew from 180 to 410 lines, 22% of merges happened before the run finished, and deploy frequency halved. The runners for all of it cost about $140 a month, which is what the team had been optimising.

The practical target most teams can reach: under 10 minutes for the PR pipeline, and a longer, non-blocking suite for the slower checks — with the split decided by what must gate a merge versus what must gate a release.

Mid: A team deploys once a week and argues that deploying daily would be riskier. How do you respond?

Do not argue about culture; do the arithmetic. Per-change failure probability is roughly a property of how changes are made, not of how often they ship — call it 1.5%. Then:

Weekly, 20 changesDaily, 4 changesPer-merge, 1 change
P(release contains a bad change)26%5.9%1.5%
Suspects when it breaks2041
Rollback costRemoves 19 good changes tooRemoves 3Removes nothing else
Measured MTTR64 min19 min6 min

Small batches do not make failures rarer — aggregate risk over a week is similar. They make failures cheap: the cause is obvious, the author is present and has the context, and rollback does not sacrifice a week of other people's work.

Then acknowledge the legitimate part of their fear, because there usually is one. Weekly deploys are often protecting against a real deficiency: no automated rollback, migrations that cannot be reversed, no canary, no production verification, or a manual QA step that genuinely takes a day. Name that deficiency and fix it — that is the actual project. Increasing frequency without fixing it just increases the rate of bad releases, and then everyone concludes that frequency was the problem.

Mid: Your pipeline is green but production is broken. What are the ways a green pipeline can lie?

Work through the five guarantees, because each one has a characteristic lie:

Broken guaranteeThe lieDetection
Honest signalZero tests ran — a glob stopped matching, or a pipe swallowed the exit codeAssert a minimum test count; set -euo pipefail; alert on suite duration dropping
Honest signalTests are flaky and were retried until green, including a real failureTrack first-attempt pass rate separately from final pass rate
ImmutabilityProduction runs a different artifact than the one tested, because each environment builds its ownBuild once, promote; verify the digest deployed matches the digest tested
ReproducibilityAn unpinned dependency or :latest base image changed between build and deployLockfiles, digest-pinned images, and a rebuild-from-commit check
IsolationTests passed because of state left by a previous run on a self-hosted runnerEphemeral runners; run the suite in a random order and in parallel
Coverage of realityEverything passed, but nothing tested the integration point that broke — config, migrations, or a third partySmoke tests against the deployed environment; test config and migrations as artifacts too

The senior point to make: a green tick is a claim of limited scope, and most production incidents live outside that scope — config, data, capacity, dependencies and rollout. That is why progressive delivery and production verification exist: not because the tests are bad, but because no test suite covers production.

Senior: You join an organisation of 200 engineers where every team has its own pipeline, quality varies wildly, and leadership wants "CI/CD improved". Where do you start?

Start by measuring, not by choosing a tool — because the request is unfalsifiable as stated and the tool question will otherwise consume the first quarter.

WeekActionWhy first
1–2Instrument four numbers per team from data you already have: branch age at merge, pipeline duration (p50/p90), first-attempt pass rate, deploy frequencyAll four come from the Git host's API. They rank the estate and make the conversation concrete
3Publish the distribution, unattributed. Find the two teams at the good end and the two at the bad endThe good teams are your evidence and your future advocates; the bad ones are your pilot
4–8Pilot with ONE willing team at the bad end. Fix in this order: honest signal (flakiness, minimum test count), then duration, then branch age, then trunk protectionOrder matters: speeding up a dishonest pipeline just produces wrong answers faster
9–12Extract the pilot's result into a paved road — a reusable workflow, a golden pipeline template — and publish the before/after numbersAdoption follows evidence from a peer team far better than it follows a mandate
OngoingMake the paved road the easiest option, not a policy. Keep the escape hatch, and measure who uses it and whyA mandated standard with no escape hatch produces creative circumvention and no feedback

What I would resist: a big-bang tool migration (it converts a practice problem into a migration project), a central team that owns every pipeline (it becomes a queue and teams lose ownership), and mandated coverage thresholds (they are met by testing getters and destroy credibility for every later request).

What I would insist on: that someone owns the shared CI infrastructure with an SLO, because at 200 engineers the pipeline is production — when it is down or slow, the whole company is idle, and it should have the on-call, dashboards and capacity planning that implies.

Senior: How do you decide what belongs in the PR pipeline versus what runs after merge or before release?

The decision rule is what does this check protect, and what is the remedy if it fails? A check belongs on the PR only if a human must act on it before merging and it is fast and reliable enough to be waited for. Everything else runs elsewhere.

StageContainsBudgetFailure means
Pre-commit / localFormatting, lint, type check, fast unit testsSecondsFix before pushing; CI repeats it as the enforcement point
PR pipeline (blocking)Unit + fast integration tests, build, security checks with low false-positive ratesUnder 10 minutesDo not merge
Merge queueThe same suite against the post-merge stateSameDo not land; the trunk stays green
Post-merge / mainFull integration, contract tests, image build and publish, slower security scansTens of minutesRevert; alert the author
Pre-release / nightlyEnd-to-end, performance, load, chaos, full dependency auditHoursBlock the release, not the merge
Post-deploySmoke tests, canary analysis, error-budget checksMinutesAutomated rollback

Two rules keep this from rotting. First, every blocking check needs an owner and a false-positive budget — a check that fails spuriously more than about 1% of the time will be retried rather than read, and it should be moved out of the blocking path until it is fixed. Second, the split must be revisited as the suite grows: PR pipelines accumulate checks the way houses accumulate cables, and the 10-minute budget is what forces the conversation about whether a new check earns its place.

The point people miss: moving a check out of the PR pipeline is not weakening it. A slow end-to-end suite that runs reliably after merge and triggers an automated revert protects production better than the same suite blocking every PR, being flaky, and being retried until green.

1 (easy): Measure your own repository's branch age and PR size distribution, then correlate them with conflicts and reverts. You need no tooling beyond the Git host's API.
Solution

Branch age at merge is the number this lesson claims is most predictive, so measure it before believing it.

$ gh pr list --state merged --limit 300 \
    --json number,createdAt,mergedAt,additions,deletions,reviews \
    > prs.json

$ python - <<'PY'
import json, statistics as st
from datetime import datetime
f = lambda s: datetime.fromisoformat(s.replace("Z","+00:00"))
prs = json.load(open("prs.json"))
ages, sizes = [], []
for p in prs:
    hours = (f(p["mergedAt"]) - f(p["createdAt"])).total_seconds()/3600
    ages.append(hours); sizes.append(p["additions"] + p["deletions"])
ages.sort(); sizes.sort()
pct = lambda xs, q: xs[int(len(xs)*q)]
print(f"branch age  p50 {pct(ages,.5):6.1f}h  p90 {pct(ages,.9):7.1f}h  max {ages[-1]:.0f}h")
print(f"PR size     p50 {pct(sizes,.5):6.0f}   p90 {pct(sizes,.9):7.0f}   max {sizes[-1]}")
buckets = {"<1d":0, "1-2d":0, "3-5d":0, "6-13d":0, "14d+":0}
for a in ages:
    d = a/24
    k = "<1d" if d<1 else "1-2d" if d<3 else "3-5d" if d<6 else "6-13d" if d<14 else "14d+"
    buckets[k] += 1
for k,v in buckets.items(): print(f"  {k:>6}: {v:4d}  {'#'*(v*40//len(ages))}")

4 (medium): Prove your test suite is telling the truth. Add the four checks that catch a silently-green pipeline, and measure the first-attempt pass rate.
Solution

Green is a claim. These four checks make it a verifiable one, and together they are about twenty lines of configuration.

CHECK 1 — MINIMUM TEST COUNT (catches the silent zero)

  - name: Verify the suite is actually running
    run: |
      set -euo pipefail
      COUNT=$(pytest --collect-only -q | tail -1 | grep -oE '^[0-9]+')
      echo "collected $COUNT tests"
      if [ "$COUNT" -lt 1000 ]; then
        echo "::error::only $COUNT tests collected, expected at least 1000"
        exit 1
      fi

  (set the floor slightly below today's count and raise it with the suite;
   this is the check that would have caught 8 weeks of zero unit tests)

CHECK 2 — set -euo pipefail EVERYWHERE

  defaults:
    run:
      shell: bash -euo pipefail {0}     # one line, applies to every step

  without it:  run-tests | tee out.txt   -> exit code is tee's, always 0
  with it:     the pipeline fails as intended

CHECK 3 — SKIP BUDGET (catches the 14-month "temporary" skip)

  - name: Skip budget
    run: |
      set -euo pipefail
      SKIPPED=$(pytest -rs -q 2>&1 | grep -c '^SKIPPED' || true)
      echo "skipped: $SKIPPED"
      [ "$SKIPPED" -le 20 ] || { echo "::error::$SKIPPED skips, budget 20"; exit 1; }

CHECK 4 — FIRST-ATTEMPT PASS RATE (catches retry-until-green)

  record two numbers per run: did attempt 1 pass, and did the run
  eventually pass. Report them separately. They are different metrics and
  only the first one is a measure of your test suite's honesty.

MEASURED, BEFORE AND AFTER (one team, six weeks apart)

  metric                              before      after
  ---------------------------------------------------------
  final pass rate (what was reported)   94%        96%
  FIRST-ATTEMPT pass rate               61%        93%   <-- the real number
  manual retries per week               78          4
  tests collected                    1,043      1,102
  tests skipped                        141          9
  steps with a swallowed exit code       6          0
  ---------------------------------------------------------
  the 94% had been reported to leadership for a year. The 61% is the
  number that explains why nobody trusted the pipeline.
🔑 First-attempt pass rate is the honesty metric. A high final pass rate with a low first-attempt rate says: the suite is unreliable, people retry reflexively, and a genuine failure will be retried into production. Track it from day one — it is the number that makes the case for the flaky-test work nobody wants to fund.
5 (hard): Reduce trunk red time. Measure the current cost, introduce a merge queue plus a revert-first rule, and report the before/after with the objection you will get.
Solution

$ python - <<'PY'
# a red period runs from the first failure to the next success
from datetime import datetime
rows=[l.split("\t") for l in open("main.tsv")]

red_start=None; periods=[]

    if concl=="failure" and red_start is None: red_start=f(created)

        periods.append((f(updated)-red_start).total_seconds()/60); red_start=None
periods.sort()
print(f"incidents {len(periods)}  median {periods[len(periods)//2]:.0f} min  "
      f"p90 {periods[int(len(periods)*.9)]:.0f} min  total {sum(periods)/60:.0f} h")

  63 hours of red main x 24 engineers = 1,512 engineer-hours per quarter

  inherit failures they did not cause, which destroys the signal.)

STEP 2 — MERGE QUEUE (test the post-merge state, not the PR in isolation)

  the failure it prevents, which nothing else catches:
    PR A renames a function.        Tested against main: green.
    PR B adds a call to that name.  Tested against main: green.
    Both merge. main is now broken, and NEITHER PR was ever red.

  gh api repos/:owner/:repo/rulesets ... (or branch protection UI):
    - required status checks: the PR suite
    - merge queue: ON, batch size 5, "merge if the batch passes,
      bisect and evict the culprit if not"

STEP 3 — REVERT FIRST (a rule, plus making it one click)

  runbook, in this order:
    1. main is red -> the on-call revert-owner reverts the offending commit
       IMMEDIATELY. No discussion, no "I can fix it in ten minutes".
    2. main is green. Everyone is unblocked.
    3. The author re-lands with the fix, at their own pace, in daylight.
  make it blameless in writing, and make it a single command:
       gh pr revert <n> --admin    (or a one-click button in the tool)

🎯 Key Takeaways

  • Continuous integration is about how often work is merged, not about owning a pipeline. If branches live for a week, the work is being isolated — the opposite of integration.
  • Branch age is the most predictive number in the practice. Measured: 4% of PRs conflicted at under a day, 43% at 6–13 days, 61% at 14+; the oldest 6.6% of PRs produced 44% of post-merge reverts.
  • "Our changes are too big to merge daily" is a statement about decomposition, not the domain — feature flags, branch by abstraction and expand/contract migrations are the enablers, and they are the same techniques that make deployment safe.
  • Pipeline duration changes behaviour, not just patience. Past ~30 minutes people batch changes; past an hour they merge before green and retry without reading — at which point the gate is decoration.
  • A 34-minute pipeline cost 71 engineer-hours a week against $140/month of compute — an 18× ratio — and grew median PR size from 180 to 410 lines.
  • Continuous delivery = always releasable; continuous deployment = every green commit ships. The gap is smaller technically and larger culturally than teams expect: if pressing the button is an event, you do not have continuous delivery.
  • Small batches do not make failures rarer; they make failures cheap. At a 1.5% per-change failure rate, a 20-change release is bad 26% of the time with 20 suspects and a 64-minute restore; a single-change deploy is bad 1.5% of the time with a 6-minute restore.
  • Five guarantees make a green tick mean something: reproducibility, isolation, immutability, honest signal and speed. A pipeline missing any one can be green while the software is broken.
  • Build once and promote the same artifact. Rebuilding per environment means production runs bytes that were never tested — a base-image patch between two builds cost three hours against an identical commit hash.
  • A suite that runs zero tests looks exactly like a suite that passes. A stale path glob hid the absence of unit tests for eight weeks. Assert a minimum collected-test count, use set -euo pipefail, and budget skips.
  • First-attempt pass rate is the honesty metric. One team reported 94% final pass rate for a year while the first-attempt rate was 61% — which is why nobody trusted the pipeline.
  • A red trunk is an incident. Measured at 61 incidents, a 38-minute median and 63 hours a quarter across 24 engineers — a cost that appears in no budget.
  • Merge queues catch the failure nothing else does: two PRs that are each green against main and broken together. Incidents fell 61 → 7.
  • Revert first, diagnose later. Making revert the blameless default took median time-to-green from 38 minutes to 6 — a bigger win than any pipeline tuning.
  • Merge-queue latency is the standard objection, and it is really a pipeline-speed problem: a queue with a 4-minute suite is free, and one with a 34-minute suite hurts.
  • CI/CD initiatives fail for four reasons, none of them the tool: nobody owns the pipeline, gates people route around, flakiness eroding trust, and the pipeline being unmonitored production.
  • Migrating tools does not buy the practice — the same four problems arrive in new syntax, after a quarter spent moving.
  • Measure before choosing anything: branch age, pipeline duration p50/p90, first-attempt pass rate and deploy frequency all come from the Git host's API, and they rank the estate in an afternoon.
  • Put a check in the blocking path only if a human must act on it before merging and it is fast and reliable enough to wait for; everything else runs post-merge, pre-release or post-deploy.
  • Raising deploy frequency before fixing the blockers makes things worse — automate the regression pass, make migrations safe, build tested rollback and post-deploy verification first, and let the cadence follow.
