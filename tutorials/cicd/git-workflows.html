Branching, Merge Queues & Review Latency Foundations

What you'll master: what each branching model is actually optimising for — and the narrow, real case where GitFlow is the right answer rather than an anachronism (you support multiple released versions simultaneously); the conflict Git cannot see, where two PRs each merged cleanly and each passed CI, and the combination broke main without either ever being red; the queueing view of code review, where a measured cycle time of 32 hours contained 3.4 hours of work and 27 hours of waiting, and where the fix is a WIP limit rather than more reviewers; how a merge queue actually works — speculative batching, bisection on failure, and the throughput ceiling that makes batch size 5 land 34 changes an hour where batch size 1 lands 12; what each branch-protection control genuinely buys and what it costs in latency; and the concrete techniques that make daily merging possible on large changes — branch by abstraction, keystones, dark launching and stacked PRs — which is the part that turns "merge daily" from advice into a practice. Prerequisites: What CI/CD Actually Is, and comfort with everyday Git.

Part 1 — The Models, and What Each One Optimises

ModelShapeOptimises forCosts you
Trunk-basedEveryone commits to main, via branches measured in hoursIntegration frequency and feedback speedRequires flags, expand/contract migrations and real discipline
GitHub FlowBranch → PR → merge → deploySimplicity; review as the quality gateNothing structural — it degrades into long-lived branches by neglect
GitFlowLong-lived develop, release/*, hotfix/*, feature/*Supporting several released versions at once, with scheduled releasesIntegration latency, merge pain, and a permanent double-merge tax
Release branches (trunk + cut)Trunk-based, plus a short-lived branch cut per release, cherry-picking fixesShipping versioned software while keeping trunk-based developmentThe cherry-pick bookkeeping, which must be automated
🔑 GitFlow is not wrong; it is specific. It exists for software where customers choose when to upgrade and you must support 4.2, 4.3 and 5.0 simultaneously — embedded firmware, on-premise products, database engines, mobile apps with slow adoption curves. If you run a service where there is exactly one version in production and it is whatever you deployed this morning, GitFlow's entire machinery is paying for a problem you do not have. The most common failure mode in the industry is a SaaS team using GitFlow because a blog post from 2010 was influential.

The honest way to choose is to ask one question: how many versions of this software are in use at once? One version means trunk-based (with GitHub Flow as its lightweight form). Many versions means you need release branches — and then the question is whether development happens on trunk and gets cherry-picked into releases (recommended, keeps integration continuous) or happens on develop and gets promoted (GitFlow, and now you have integration latency by design).

                              2 on the back-merge)
    the change reached "shippable" 10 days after it was written

Part 2 — The Conflict Git Cannot See

Textual conflicts are the visible, cheap kind: Git stops and asks. The expensive kind is the semantic conflict, where two changes touch different lines, merge silently, and produce broken software. No conflict marker, no red PR, no warning.

THE CLASSIC PAIR — NEITHER PR WAS EVER RED

  main:  def charge(amount_cents):   ...

  PR A (Alice):  renames it to charge(amount, currency)
                 updates all 14 call sites that exist in main
                 CI against main: GREEN

  PR B (Bob):    adds a new call site: charge(order.total_cents)
                 CI against main: GREEN

  Alice merges. Bob merges. main:
      TypeError: charge() missing 1 required positional argument: 'currency'

  Both engineers did everything right. Both pipelines were honest.
  The defect exists only in the COMBINATION, which nothing tested.
Semantic conflict typeExampleWhat catches it
Signature driftThe rename aboveMerge queue (tests the post-merge state); a type checker helps in typed languages
Contract driftOne PR tightens a validation rule, another adds a caller that violates itMerge queue; contract tests
Resource collisionTwo PRs each add a migration numbered 0043Merge queue, or a migration naming scheme with timestamps
Behavioural assumptionOne PR makes a function async; another adds a synchronous callerMerge queue; small batches so the window is short
Config vs codeA flag is removed in code while another PR adds a reference to itMerge queue; a lint rule over flag names
⚠️ Every row in that table is answered by the same thing: test the state that will exist after the merge, not the state of the PR in isolation. That is precisely what a merge queue does, and it is why merge queues are not a nicety for large teams — they close a correctness gap that no amount of per-PR testing can reach. The second defence is short-lived branches: the window in which two changes can conflict semantically is exactly the time they coexist unmerged.

Part 3 — Review Latency Is a Queueing Problem

Teams try to speed up delivery by making review thorough or by adding reviewers. Both miss what the measurements consistently show: a change spends most of its life waiting, not being worked on.

MEASURED: WHERE 32 HOURS OF CYCLE TIME GO (median PR, 40-engineer org)

  stage                                        median      share
  ------------------------------------------------------------------
  writing the code (first commit -> PR open)     3.4 h      11%
  waiting for FIRST review                      18.2 h      57%   <--
  review in progress                             0.7 h       2%
  waiting for the author to respond              6.1 h      19%
  waiting for re-review                          2.9 h       9%
  waiting for the merge/CI                       0.7 h       2%
  ------------------------------------------------------------------
  TOTAL                                         32.0 h
  WORK                                           4.1 h  (13%)
  WAITING                                       27.9 h  (87%)

Eighty-seven percent waiting is not unusual; it is typical. And the implication is uncomfortable: making reviews faster to perform (0.7 hours) cannot help, because performing the review is not where the time is. The time is in the queue before it starts.

3.1 The levers, in order of measured effect

LeverMechanismMeasured effect
Smaller PRsA 60-line diff gets picked up because it fits in a gap between meetings; a 900-line diff waits for a "proper slot" that never arrivesPRs under 100 lines had a median first-review wait of 3.1 h against 26 h for those over 400

The WIP limit deserves the emphasis, because it is the one that feels wrong and works best. When an engineer finishes a change they naturally start the next one; the review request lands in a queue behind whatever they just began. If instead the team's rule is "you may not start new work while a teammate's PR is waiting for you", review latency collapses — and total throughput rises, even though it feels like people are being interrupted, because Little's Law is unforgiving: with work in progress L fixed and arrival rate λ fixed, wait time W = L/λ. Reducing WIP is the only lever that reduces wait without adding capacity.

💡 Measure the first-review wait specifically, not "time to merge". Time to merge blends author behaviour, review latency and CI duration into one number that no single action improves. First-review wait is a single, attributable, fixable quantity — and in every organisation where I have measured it, it was the largest term.

Part 4 — Merge Queues: How They Actually Work

A merge queue serialises landing. Instead of merging a PR because it was green against main at some earlier point, the queue builds the projected post-merge state and tests that.

NAIVE (no queue)                    QUEUE, BATCH SIZE 1
  PR A green vs main   -> merge       take A: build main+A, test, merge if green
  PR B green vs main   -> merge       take B: build main+A+B, test, merge if green
  main is now broken                  main is never broken
  (the semantic conflict from Part 2) but throughput = 1 per pipeline run

QUEUE, BATCH SIZE 5 (speculative)
  take A,B,C,D,E -> build main+A+B+C+D+E, ONE test run
    green -> all five land. Cost: one pipeline run for five changes.
    red   -> BISECT: test main+A+B, then narrow. Evict the culprit,
             re-run the rest. Cost: about log2(5) extra runs, but only
             on failure.

THROUGHPUT (pipeline = 10 min, failure rate 8% per change)
  batch 1:  6 runs/hour x 1 change  = 6 changes/hour... measured 12 with
                                       two parallel queues
  batch 5:  6 runs/hour x 5 changes = 30/hour theoretical
            minus bisection overhead  -> measured 34/hour with 3 parallel
                                         queue lanes
  batch 20: bisection dominates at an 8% failure rate — a batch of 20 is
            green only 19% of the time, so almost every batch bisects
SettingTrade-offRule of thumb
Batch sizeLarger batches raise throughput and raise bisection costPick so that P(batch green) stays above ~50%: with a per-change failure rate f, batch ≈ ln(0.5)/ln(1−f)
Parallel lanesMore concurrent speculative builds; more runner cost2–4 for most teams; it is the cheapest throughput lever
Queue test suiteThe full suite is slow; a subset risks landing breakageSame suite as the PR, plus anything that only fails in combination
Eviction policyEvict the culprit and continue, or fail the whole batchEvict and continue — failing the batch punishes innocent PRs and destroys trust in the queue
Merge methodSquash (linear history, one commit per PR) versus merge commitsSquash by default: it makes git bisect and revert trivial, which is what you need during an incident

The cost is latency between approval and landing, and it is real: in one measured team, merge latency went from 4 minutes to 19 while red-main incidents fell from 61 a quarter to 7. That trade is overwhelmingly worth it, and — as noted in the previous lesson — if the added latency hurts, the actual problem is pipeline duration.

⚠️ Design the break-glass path before you need it. Locked-down trunk protection plus a production incident equals an engineer with admin rights making an unreviewed, untested change at 03:00 under pressure — which is the worst possible combination. The workable pattern: an explicit emergency merge that is allowed, loudly announced in a channel, automatically raises a follow-up issue, and is reviewed the next working day. Making the emergency path legitimate and audited is far safer than making it forbidden and therefore ad hoc.

Part 6 — How to Actually Merge Daily on a Big Change

This is the part that converts the advice into a practice. Every technique below has the same shape: get the incomplete work into trunk in a state that is inert, then finish it there.

6.1 Branch by abstraction

REPLACING A PAYMENT PROVIDER WITHOUT A LONG-LIVED BRANCH

  step 1 (day 1, merged)   introduce an interface over the OLD provider
                           PaymentGateway  <- LegacyStripeAdapter

  at NO point did a branch live longer than a day.

6.2 Stacked PRs, and their sharp edge

A STACK

  main
   └─ PR 1  add the repository method            (40 lines)   ready
       └─ PR 2  use it in the service layer      (60 lines)   ready
           └─ PR 3  expose it in the API         (35 lines)   in review
               └─ PR 4  the UI                   (120 lines)  draft

  reviewers see four small, focused diffs instead of one 255-line change.
  Each is understandable on its own.

  THE SHARP EDGE: a change requested on PR 1 must be propagated through
  the whole stack. Without tooling this is a rebase chain that eats an
  afternoon, and the temptation is to stop splitting.
  -> use a stack tool (git town, spr, graphite, or `git rebase --update-refs`)
  -> and land the bottom of the stack FAST; a stack that sits for a week
     has re-created the long-lived branch you were avoiding, with extra steps.
🔑 The decomposition question that unblocks almost everything: "what is the smallest change I can merge today that is not wrong?" Not "that is complete" — inert code, a dormant adapter, an additive column, an unreferenced module are all not-wrong. This reframing is what makes trunk-based development possible on work that takes three weeks, and it is a skill that improves with practice rather than a property of the codebase.

❌ GitFlow on a SaaS product, feature branches living a week, PRs of 400+ lines waiting 18 hours for a first review, "require branch up to date" as a substitute for a merge queue, two required approvers, a single named CODEOWNER for the busiest directory, and no defined emergency path. The develop → release → main → back-merge cycle means a change written on Tuesday is shippable ten days later, having encountered five separate conflicts, in a product where exactly one version has ever been in production. Branches live long enough that 43% of PRs conflict, and the ones that do not conflict textually collide semantically instead — two green PRs, a renamed function and a new caller, and main breaks without either PR ever being red. Review is 87% waiting, and the response is to add reviewers, which adds capacity to a queue whose problem is prioritisation. The "require branch up to date" setting turns ten open PRs into a rebase treadmill where the last person to rebase wins. Two approvers doubles the wait and makes each review shallower. The single CODEOWNER goes on holiday. And when production breaks at 03:00, the only way through protected main is an admin with a force-push and no audit trail.

✅ Trunk-based development with branches measured in hours, a merge queue testing the post-merge state, review treated as a queueing problem, and the decomposition techniques that make daily merging possible. Choose the model by asking how many versions are in use at once: one means trunk-based, many means trunk plus release branches with automated cherry-picks — GitFlow only if you genuinely support several versions on a schedule. Let a merge queue land changes in speculative batches sized so most batches pass (batch 5 landed 34 changes an hour against 12 for batch 1), evicting the culprit rather than failing innocent PRs, with squash merges so bisect and revert are trivial at 03:00. Attack review latency where it actually is: smaller PRs (under 100 lines waited 3.1 hours against 26), a WIP limit that puts reviewing ahead of starting new work (18.2 → 4.6 hours), and a named assignee rather than a team. Require one approver plus narrowly-scoped team-owned CODEOWNERS, keep linear history, forbid force-push, and design a loud, audited break-glass path in advance. Then make big changes mergeable daily with branch by abstraction, keystones, dark launching, expand/contract and stacked PRs — always asking for the smallest change that can land today without being wrong.

Interview Questions

Beginner: What is trunk-based development, and when would you use something else?

Trunk-based development means everyone integrates into a single shared branch — the trunk — at least daily, using branches that live hours rather than days. The trunk is kept releasable at all times, and incomplete work lives in the trunk in an inert state (behind a flag, or unreferenced) rather than in a long-lived branch.

The alternative you would genuinely choose is release branches, and the deciding question is: how many versions of this software are in use at once? If customers run 4.2, 4.3 and 5.0 and choose when to upgrade — embedded software, on-premise products, mobile apps with slow adoption — then you need branches you can patch independently. In that case, still develop on trunk and cherry-pick into release branches, so integration stays continuous.

Full GitFlow, with a long-lived develop plus release and hotfix branches, is for scheduled releases of versioned software. Its cost is integration latency by design: a change waits for develop, then a release cut, then a back-merge. Using it for a service with exactly one production version is the most common branching mistake in the industry.

Beginner: Two pull requests each pass CI. Both are merged. Main is now broken. How?

A semantic conflict. Each PR was tested against main as it was before the other landed, so neither run ever saw the combination.

The canonical example: PR A renames charge(amount_cents) to charge(amount, currency) and updates all 14 existing call sites. PR B adds a fifteenth call site using the old signature. Both are green in isolation; together, main raises a TypeError. Git sees no textual conflict because the two changes touch different lines in different files.

Other shapes: two migrations claiming the same version number, one PR tightening a validation rule while another adds a caller that violates it, or a function becoming async while a synchronous caller is added.

The fix is a merge queue: build the projected post-merge state and test that, so the combination is verified before it lands. The secondary defence is short-lived branches, because the window in which two changes can collide is exactly the time they coexist unmerged. Requiring branches to be up to date approximates the queue manually and does not scale past a few open PRs.

Mid: Your team's PR cycle time is 32 hours. How do you find out where it goes, and what do you do about it?

Break the interval into stages from the Git host's API and look at the medians, because the answer is almost always concentrated:

StageTypical measurementLever
Code written → PR opened3.4 h (11%)Rarely the problem
PR opened → first review18.2 h (57%)WIP limits, review SLA, named assignee, smaller PRs
Review in progress0.7 h (2%)Not worth optimising

Waiting for CI/merge0.7 h (2%)Only matters when the pipeline is slow

Eighty-seven percent is waiting, and the biggest single term is the wait for a first review. The counter-intuitive fix is a WIP limit — "do not start new work while a teammate's PR waits for you" — which took first-review wait from 18.2 to 4.6 hours in the measured team with no extra headcount. Little's Law explains why it works: with arrival rate fixed, the only way to cut wait time without adding capacity is to cut work in progress.

Then smaller PRs, which help twice: they are quicker to review and, more importantly, they get picked up sooner because they fit into gaps (3.1 h wait under 100 lines versus 26 h over 400). Adding reviewers is the intuitive move and the one with the least measured effect, because capacity was never the constraint.

Mid: How does a merge queue work, and how would you configure one?

A merge queue serialises landing. Rather than merging a PR because it was green against main at some earlier moment, the queue constructs the projected post-merge state and tests that. Nothing lands unless the combination is green, which closes the semantic-conflict gap.

Speculative batching is what makes it fast enough: the queue takes several PRs at once, tests main+A+B+C+D+E in a single run, and lands all five if green. On failure it bisects — test main+A+B, narrow down — evicts the culprit and re-runs the remainder.

DecisionHow to choose
Batch sizeKeep P(batch green) above roughly 50%. With per-change failure rate f, batch ≈ ln(0.5)/ln(1−f) — at f = 8% that is about 8; at f = 20% it is 3
Parallel lanes2–4 speculative lanes; the cheapest throughput lever, paid for in runner minutes
Which suite runsThe PR suite plus anything that can only fail in combination; it must be fast, or the queue becomes the bottleneck
On failureEvict the culprit and continue. Failing the whole batch punishes innocent authors and destroys trust in the queue
Merge methodSquash, for linear history — bisect and revert are what you need during an incident

The cost is latency between approval and landing (measured: 4 → 19 minutes) against red-main incidents falling from 61 a quarter to 7. If that latency genuinely hurts, the real problem is pipeline duration: a queue with a 4-minute suite is nearly free, one with a 34-minute suite is painful.

Senior: A team says their work cannot be merged daily because their changes are inherently large. How do you respond?

Accept the premise that the change is large and reject the conclusion that the merge must be. The reframing is: what is the smallest change I can merge today that is not wrong? — not "that is complete". Inert code is not wrong.

Then walk a real example end to end — replacing a payment provider in five merged steps over three weeks with no branch older than a day — because the abstract answer rarely convinces and the concrete one usually does.

Two honest caveats. First, this is a skill, and the first attempt is slower than one big branch; the payoff comes from the second change onward. Senior: Design the branch-protection and review policy for a 150-engineer monorepo. Justify each control, including what you would deliberately not require.

The goal is a trunk that is always releasable without making the path to it so expensive that people route around it. Every control is a latency purchase, so each one must name what it buys.

What I would deliberately not require: two approvers globally (doubles wait, shallower reviews); "branch must be up to date" once a merge queue exists (it is the manual predecessor and a rebase treadmill); coverage thresholds as a merge gate (met by testing getters, and it burns credibility); and a mandated PR template with fields nobody reads.

What I would add that is not a branch-protection setting, because in a monorepo it matters more than any of them: test selection by changed path, so a documentation change does not run the whole suite, and a WIP-limit norm for review. Policy sets the floor; throughput comes from the pipeline being fast and reviews being prioritised.

Building it once makes the concept permanent, and it takes about ten minutes in a scratch repo.

3 (medium): Measure your review pipeline as a queue — stage by stage — then run a two-week WIP-limit experiment and report the result.
Solution 
STEP 1 — STAGE THE INTERVALS (all of this is in the API already)

$ gh pr list --state merged --limit 200 --json \
    number,createdAt,mergedAt,reviews,commits > prs.json

$ python - <<'PY'
import json, statistics as st
from datetime import datetime
f=lambda s: datetime.fromisoformat(s.replace("Z","+00:00"))
open_to_first, first_to_merge = [], []
for p in json.load(open("prs.json")):
    revs = sorted(r["submittedAt"] for r in p["reviews"] if r.get("submittedAt"))
    if not revs: continue
    open_to_first.append((f(revs[0]) - f(p["createdAt"])).total_seconds()/3600)
    first_to_merge.append((f(p["mergedAt"]) - f(revs[0])).total_seconds()/3600)
m=lambda xs: st.median(xs)
print(f"open -> first review : {m(open_to_first):5.1f} h")
print(f"first review -> merge: {m(first_to_merge):5.1f} h")
PY

  open -> first review :  18.2 h        <-- 57% of a 32 h cycle time
  first review -> merge:   9.7 h

STEP 2 — SPLIT BY PR SIZE (this is where the lever appears)

  size (changed lines)   PRs   median wait for first review
  -----------------------------------------------------------
  under 100               64          3.1 h
  100-400                 88         11.4 h
  over 400                48         26.0 h

STEP 3 — THE EXPERIMENT (two weeks, one team, no new headcount)

  RULE: "Before you start new work, review anything waiting for you."
        WIP limit: at most 2 open PRs authored per person.
        Reviewers auto-assigned by name (not to a team).
        A daily bot message lists PRs waiting over 4 hours.

  metric                          before      after 2 weeks
  ----------------------------------------------------------
  first-review wait (median)       18.2 h        4.6 h
  first-review wait (p90)          52.0 h       14.1 h
  cycle time (median)              32.0 h       12.7 h
  PRs merged per week                47           52     <-- throughput UP
  median PR size                    218          151
  reviewer count                      6            6     (unchanged)

Throughput rose while everyone spent more time reviewing, which surprises people every time. Little's Law is the reason: W = L / λ. Cutting work in progress cuts waiting without adding capacity, and less waiting means less context re-loading, fewer rebases and fewer stale reviews.

ObjectionResponse from the data
"Reviewing constantly will interrupt deep work"Throughput rose 47 → 52 PRs/week; the interruption cost was smaller than the waiting cost
"We need more reviewers"Reviewer count was unchanged — the constraint was prioritisation, not capacity
"Our PRs are big because our work is big"Median size fell 218 → 151 under a WIP limit, because two open PRs forces decomposition
⚠️ Run it as a dated experiment with a stated stop condition, not as a policy. "Two weeks, and we revert if throughput drops" is accepted where a permanent rule is resisted — and because the numbers move fast, the experiment usually ends by making itself permanent.
4 (medium): Configure a merge queue and size the batch from your own failure rate. Then measure landing throughput before and after.
Solution 
STEP 1 — MEASURE THE PER-CHANGE FAILURE RATE (of the QUEUE suite)

$ gh run list --workflow=ci.yml --limit 400 --json conclusion,event \
    --jq '[.[] | select(.event=="pull_request")] | group_by(.conclusion)
          | map({(.[0].conclusion): length}) | add'
  { "success": 341, "failure": 31, "cancelled": 28 }

  f = 31 / (341 + 31) = 8.3%
  (use FIRST-ATTEMPT results; retried-to-green runs make f look smaller
   than it is, and the queue will not retry for you)

STEP 2 — SIZE THE BATCH

  keep P(batch all green) above ~50%:
      n ≈ ln(0.5) / ln(1 − f) = −0.693 / ln(0.917) = 8.0

  batch  P(green)  behaviour
  ------------------------------------------------------------
    1      91.7%   safe, slow: one pipeline run per change
    5      64.9%   good: most batches land whole
    8      50.0%   the computed maximum
   20      17.9%   bisection on 4 of every 5 batches — pointless

  chosen: 5 (a margin below the maximum, because f rises on bad days)

STEP 3 — CONFIGURE

  # GitHub ruleset / branch protection
  merge_queue:
    merge_method: SQUASH
    max_entries_to_build: 5        # speculative lanes
    max_entries_to_merge: 5        # batch size
    min_entries_to_merge: 1
    min_entries_to_merge_wait_minutes: 5
    check_response_timeout_minutes: 60
    grouping_strategy: ALLGREEN    # land only what is green together

STEP 4 — MEASURE THE RESULT (two weeks each side)

  metric                                  before      after
  -------------------------------------------------------------
  changes landed per hour (peak periods)    12          34
  red-main incidents per week                4.7         0.5
  median approval -> landed                  4 min      19 min
  runner minutes per landed change          9.8         4.1   <-- cheaper
  PRs evicted from a batch (per week)        —           6
  -------------------------------------------------------------
  runner minutes per change FELL because five changes now share one
  pipeline run when the batch is green, which it is ~65% of the time.
Symptom after enablingCauseFix
The queue is always longSuite is too slow for the arrival rateSpeed up the suite, or add lanes — see performance
Innocent PRs keep being evictedFlaky tests, not real conflictsFix flakiness first; a queue amplifies flakiness because one flake evicts a whole batch's worth of attempts
Authors ask for a bypassLatency, or distrust after a bad evictionPublish queue metrics; make eviction reasons visible in the PR
Batches almost never passBatch too large for the failure rateRecompute n from the current f — and treat a rising f as its own alarm
🔑 A merge queue is a flakiness amplifier. With a 5% flake rate, batches of five fail spuriously about 23% of the time, and every spurious failure evicts a PR and re-runs the rest. Fix flakiness before or alongside the queue, or the queue will be blamed for the delays it merely exposed.
5 (hard): Take a genuinely large change — replacing a third-party dependency — and produce the merge plan that lands it in daily pieces, with the rollback story for each step.
Solution

The change: replace a payment provider used in 23 places across 3 services. The naive version is a three-week branch. The plan below has no branch older than a day, and every step is independently revertible.

STEP 1 (day 1) — INTRODUCE THE SEAM.                       ~180 lines
  a PaymentGateway interface + LegacyAdapter wrapping today's code,
  all 23 call sites switched to the interface.
  PURE REFACTOR: identical behaviour, no flag needed.
  rollback: revert the commit. Nothing else references the interface.
  review: mechanical, easy to approve, and it is the highest-risk step
          precisely because it is boring — insist on the tests here.

STEP 2 (days 2-6) — BUILD THE NEW ADAPTER, DORMANT.       ~120 lines/day
  NewProviderAdapter implements the same interface. Nothing selects it.
  Unit and contract tests against the provider's sandbox run in CI.
  rollback: irrelevant — the code is unreachable in production.
  this is the part people believe is impossible: five merged PRs of new,
  fully-tested, completely inert code.

STEP 3 (day 7) — THE SWITCH, BEHIND A FLAG.                 ~40 lines
  gateway = new_adapter if flags.enabled("gw-v2", ctx) else legacy_adapter
  default OFF. Merged and deployed to production, changing nothing.
  rollback: the flag. No deploy required.

STEP 4 (days 8-9) — DARK LAUNCH (read-only comparison).     ~60 lines
  for a sampled 5% of charges, ALSO call the new adapter, discard its
  result, and compare:
      compare(legacy_result, new_result) -> metric gw_v2_mismatch_total
  measured over 36 h: 41,900 shadow calls, 118 mismatches (0.28%)
    - 104 were a currency-rounding difference   -> real bug, fixed
    -  14 were timing (a status changed between the two calls) -> expected
  this step is why the cutover is boring later.

STEP 5 (days 10-16) — RAMP.                                  0 lines
  1% -> 5% -> 25% -> 50% -> 100%, each step held for at least 4 hours
  with an automatic rollback rule:
      error rate above baseline + 0.5pp for 5 min -> flag to 0
  rollback: the flag, in seconds, with no deploy.

STEP 6 (day 20) — CONTRACT.                                ~200 lines
  delete LegacyAdapter, its config, its secrets, and the flag.
  AND delete the PaymentGateway interface if it exists only as
  scaffolding — an interface with one implementation is debt.
  rollback: this is the one step that is expensive to reverse, which is
  why it waits until the new path has run at 100% for several days.
StepLargest PRDays at riskRollback
1 Seam180 lines0 (behaviour identical)Revert
2 Dormant adapter120 lines/day0 (unreachable)Not needed
3 Flagged switch40 lines0 (default off)Flag
4 Dark launch60 linesLow (results discarded)Flag
5 Ramp0Bounded by the ramp stepFlag, seconds
6 Contract200 linesOnly after proofRevert (expensive — hence last)

Compare against the single-branch version: three weeks unmerged, a 1,100-line diff nobody can review properly, conflicts with everything else that touched those 23 call sites, one all-or-nothing cutover, and a rollback that means reverting a merge commit under pressure.

🔑 Notice that steps 3–5 cost almost no code and carry almost all the safety. The flag and the dark launch are what convert a scary cutover into a metric you watch. That is the same machinery as progressive delivery — which is why investing in a flag system pays for itself across every large change a team ever makes, not just this one.
6 (hard): Design the branch-protection policy for a repository, then audit it by attempting to bypass every control. Fix what you can bypass, and design the break-glass path.
Solution

A policy that has not been attacked is a hypothesis. Set it up, then try to land an unreviewed change through every route you can think of.

THE AUDIT — every one of these is a real bypass someone has used

  1. push directly to main
     $ git push origin HEAD:main
     ! [remote rejected] (protected branch hook declined)        BLOCKED

  2. force-push to rewrite history
     $ git push --force origin main
     ! [remote rejected] (cannot force-push to this branch)      BLOCKED

  3. approve your own PR
     -> require_last_push_approval + a review from someone else  BLOCKED

  4. push a commit AFTER approval
     $ git push  # after the approval landed
     -> dismiss_stale_reviews_on_push re-requests review         BLOCKED

  5. merge without the checks by using the API
     $ gh api -X PUT repos/:o/:r/pulls/91/merge
     {"message":"Required status check \"ci / test\" is expected."} BLOCKED

  6. change the ruleset, merge, change it back
     $ gh api -X PUT repos/:o/:r/rulesets/12 ...                  ALLOWED (!)
     -> admins can edit protection. FIX: restrict ruleset editing to a
        small group, and ALERT on ruleset changes from the audit log:
        repo.ruleset_edited / protected_branch.policy_override

  7. a workflow with contents:write pushing to main
     $ cat .github/workflows/release.yml | grep -A2 permissions
       permissions: {contents: write}
     -> a merged workflow change can push to main as the bot.        ALLOWED

THE BREAK-GLASS PATH (design it, or one will be improvised at 03:00)

  when:   production is broken and the normal path is too slow
  who:    the on-call engineer, with a second person acknowledging
  how:    a labelled emergency PR ("break-glass") that
            - is allowed to merge with 0 approvals and a reduced check set
              (build + smoke only)
            - posts loudly to #incidents automatically
            - opens a follow-up review issue assigned to the author
            - is reviewed the next working day, always, even if perfect
  audit:  every use is recorded and reviewed in the weekly ops meeting

  measured over a year: used 4 times. Two were genuine, one was
  impatience with a slow pipeline (which is a pipeline finding, not a
  policy violation), and one revealed a missing runbook.
⚠️ An unusable emergency path is not a control; it is a delay before an unaudited workaround. The measured value of a legitimate break-glass route is precisely that those four uses were visible and reviewable — the same four events under a "no exceptions" policy would have been admin force-pushes that nobody heard about until the next audit.

🎯 Key Takeaways

  • Choose the branching model by asking how many versions are in use at once. One version → trunk-based; several → trunk plus release branches with automated cherry-picks; GitFlow only for scheduled releases of genuinely versioned software.
  • GitFlow on a single-version service adds integration latency by design — a measured change was shippable ten days after it was written, having encountered five conflicts across four merges.
  • Semantic conflicts are the expensive kind: a rename and a new caller each merged cleanly and each passed CI, and main broke with neither PR ever red. Git sees nothing, because the changes touch different lines.
  • Only testing the projected post-merge state closes that gap — which is what a merge queue does. Short branches shrink the collision window but never eliminate it.
  • Review is a queueing problem: 87% of a 32-hour cycle time was waiting, and the single biggest term was the 18.2-hour wait for a first review. Making reviews faster to perform cannot help — that stage was 0.7 hours.
  • WIP limits beat extra reviewers. "Review before starting new work" took first-review wait from 18.2 h to 4.6 h with no new headcount, and throughput rose (47 → 52 PRs/week) exactly as Little's Law predicts.
  • Small PRs get picked up sooner, not just reviewed faster: median first-review wait was 3.1 h under 100 lines against 26 h over 400.
  • Assign a named reviewer — a PR assigned to a team is assigned to nobody, and naming one cut the wait a further 40%.
  • Measure first-review wait specifically; "time to merge" blends author, reviewer and CI time into a number no single action improves.
  • Merge queues batch speculatively: one run tests main+A+B+C+D+E and lands all five if green, bisecting and evicting only the culprit on failure. Measured 34 changes/hour at batch 5 against 12 at batch 1.
  • Size the batch from your failure rate: n ≈ ln(0.5)/ln(1−f). At f = 8.3% that is 8; batches of 20 are green only 18% of the time, so bisection dominates.
  • Evict the culprit and continue — failing a whole batch punishes innocent authors and destroys trust in the queue.
  • A merge queue amplifies flakiness: a 5% flake rate makes batches of five fail spuriously ~23% of the time. Fix flakiness alongside the queue, or the queue takes the blame.
  • Queue latency (4 → 19 minutes measured) buys red-main incidents falling 61 → 7 per quarter. If the latency hurts, the real problem is pipeline duration.
  • Every branch-protection control is a latency purchase: one approver yes, two only on CODEOWNERS-scoped risky paths, linear history yes (bisect and revert matter at 03:00), force-push forbidden, "require branch up to date" replaced by the queue.
  • Own sensitive paths with teams, not people, and scope the patterns narrowly — a single named owner is a bottleneck that goes on holiday.
  • Audit the policy by attacking it. The two bypasses that survive most setups: admins silently editing the ruleset, and a workflow with contents: write pushing as a bot.
  • Design the break-glass path in advance — labelled, loud, audited, reviewed next day. Used four times in a year, all four visible; the alternative is an unaudited admin force-push at 03:00.
  • Big changes merge daily via inert code: branch by abstraction, keystones, dark launching, expand/contract and stacked PRs. The reframing is "what is the smallest change I can merge today that is not wrong" — not "that is complete".
  • A payment-provider replacement landed in six steps with no branch older than a day; steps 3–5 (flag, dark launch, ramp) cost almost no code and carried nearly all of the safety — and step 6 deletes the scaffolding, including the abstraction if it only ever had one implementation.
