Database Migrations in CD Deployment

What you'll master: the asymmetry that makes this the hardest part of continuous delivery — code rolls back in seconds and data does not roll back at all, so every schema change must be designed so that the previous release still works; expand/contract as six explicit phases rather than a slogan, including the one everybody skips and the rule that the destructive phase belongs in a later release, never the same one; the lock behaviour that turns a "one-line ALTER TABLE" into an outage — an ADD COLUMN … NOT NULL DEFAULT on a 40M-row table held an ACCESS EXCLUSIVE lock for 4m12s and queued 61,000 requests behind it — and the lock_timeout discipline that makes it safe; backfills as throttled, resumable jobs outside the migration, where a naive single UPDATE ran 38 minutes and pushed replica lag to 94 seconds; where migrations run in the pipeline and how to stop two runners applying them at once; rehearsal against a production-sized restore, which is the only honest way to know a migration's duration; and the compatibility matrix test that proves old code still works against the new schema before you deploy anything. Prerequisites: Deployment Strategies, Environments & Promotion, and the SQL track for the engine behaviour underneath.

Part 1 — Code Rolls Back; Data Does Not

THE SITUATION EVERY MIGRATION MUST SURVIVE

  10:00  deploy v2, which includes: ALTER TABLE orders DROP COLUMN status
  10:04  v2 turns out to be broken for an unrelated reason
  10:05  roll back to v1 — 30 seconds, as designed
  10:05  v1 starts: SELECT id, status, total FROM orders
         ERROR: column "status" does not exist
  -> the rollback completed successfully and the service is still down.

  THE RULE THAT PREVENTS IT
    A release may only contain schema changes that the PREVIOUS release
    can also run against. Every time. No exceptions for "small" changes.
ChangeOld code survives it?Safe in one release?
Add a nullable columnYes — it ignores itYes
Add a column with a defaultYesYes (but see the lock section)
Add an indexYesYes, if built concurrently
Add a tableYesYes
Drop a columnNoNo — later release, after nothing reads it
Rename a columnNoNo — it is a drop plus an add
Add NOT NULL to an existing columnNo — old code inserts nullsNo — backfill and enforce in stages

1.1 Expand / contract, as six phases

  GOAL: rename orders.status -> orders.state, with zero downtime and a
        working rollback at every point.

  PHASE 1 — EXPAND (release N)
    ALTER TABLE orders ADD COLUMN state text;        -- nullable, no default
    -- old code: unaffected. new code: not deployed yet.

  PHASE 2 — DUAL WRITE (release N, same or next deploy)
    application writes BOTH columns on every insert/update.
    reads still come from `status`.
    -- rollback safe: old code reads and writes `status`, which is current.

  PHASE 3 — BACKFILL (a job, NOT a migration — see Part 3)
    UPDATE orders SET state = status WHERE state IS NULL   -- in batches,
                                                            -- throttled
    verify: SELECT count(*) FROM orders WHERE state IS DISTINCT FROM status;
    -- must be 0 before proceeding.

  PHASE 4 — SWITCH READS (release N+1)
    application reads `state`, still writes both.
    -- rollback safe: N still reads `status`, which dual-write keeps current.

  PHASE 5 — STOP WRITING THE OLD COLUMN (release N+2)
    application writes only `state`.
    -- rollback to N+1 is safe (it reads `state`).
    -- rollback to N is NOT safe any more. That is why phases are releases
    --   apart: you keep a rollback window, not a rollback forever.

  PHASE 6 — CONTRACT (release N+3, after verifying nothing reads it)
    ALTER TABLE orders DROP COLUMN status;

  THE PHASE PEOPLE SKIP IS 5. They go from "reads switched" straight to
  DROP, while old code somewhere — a report, a worker, a lambda — is
  still writing `status`, and its writes silently stop being read.
🔑 Expand/contract is not one deployment with six steps; it is several releases with rollback windows between them. Compressing it into one release is the single most common cause of "we could not roll back". The cost is calendar time — typically two to four releases — and the benefit is that every intermediate state is one where both the current and previous version of the code work.

Part 2 — Locks: How a One-Line ALTER Becomes an Outage

MEASURED: THE SAME STATEMENT ON A 40M-ROW TABLE

  -- PostgreSQL 11+ (this is fast: metadata only)
  ALTER TABLE orders ADD COLUMN state text;                        0.4 s

  -- older engines, or a VOLATILE default: rewrites every row
  ALTER TABLE orders ADD COLUMN state text NOT NULL DEFAULT gen_random_uuid();
                                                                 4m 12s
  during which an ACCESS EXCLUSIVE lock is held:
    - every SELECT, INSERT, UPDATE on `orders` blocks
    - connections pile up: 61,000 requests queued in 4 minutes
    - the connection pool exhausts at t+38s
    - the service is DOWN for a "one-line, additive" migration.

THE LOCK QUEUE IS THE PART THAT SURPRISES PEOPLE

  a migration waiting for a lock BLOCKS EVERYTHING BEHIND IT:

    t+0    ALTER TABLE waits for a long-running SELECT to finish
    t+0    it now holds a place in the lock QUEUE
    t+0.1  every subsequent query on that table queues BEHIND the ALTER,
           even though the ALTER has not started
    t+90   the slow SELECT ends; the ALTER runs; everything unblocks

  so a migration that never actually acquired a lock still took the
  table down for 90 seconds. THIS is why lock_timeout matters more than
  statement_timeout.

THE FOUR-LINE PREAMBLE THAT MAKES MIGRATIONS SAFE

  SET lock_timeout = '3s';        -- do not queue behind a long query,
                                  -- and do not make others queue behind me
  SET statement_timeout = '30s';  -- a migration that runs long is a bug
  SET idle_in_transaction_session_timeout = '10s';

  -- and then, for anything that can be slow, retry the whole thing:
  --   attempt -> lock_timeout fires -> wait 5s -> attempt again
  -- rather than holding the queue open.

  WITH THESE, THE FAILURE MODE CHANGES:
    without: the migration takes the site down for 4 minutes
    with:    the migration FAILS in 3 seconds, the deploy stops, and
             you fix the approach instead of the incident.
⚠️ CREATE INDEX CONCURRENTLY cannot run inside a transaction, and most migration tools wrap each migration in one. The result is either an error or — worse, with some tools — a silent fallback to a blocking build. Mark such migrations as non-transactional explicitly (disable_ddl_transaction! in Rails, atomic = False in Django, -- +goose NO TRANSACTION in goose), and be aware that a concurrent build can leave an INVALID index behind if it fails, which must be dropped before retrying.

Part 3 — Backfills Are Jobs, Not Migrations

THE NAIVE VERSION, MEASURED ON 40M ROWS

  UPDATE orders SET state = status WHERE state IS NULL;

    duration ................... 38 min
    rows locked ................ all of them, progressively
    replica lag peak ........... 94 s      <-- read replicas served
                                               stale data for 90+ seconds
    WAL generated .............. 22 GB     <-- disk alerts on the primary
    deploy pipeline ............ blocked for 38 minutes
    if it fails at minute 37 ... the whole transaction rolls back

THE BATCHED, THROTTLED, RESUMABLE VERSION

  #!/usr/bin/env python3
  BATCH = 5_000
  while True:
      n = execute("""
          WITH batch AS (
            SELECT id FROM orders
            WHERE state IS NULL
            ORDER BY id
            LIMIT %s
            FOR UPDATE SKIP LOCKED
          )
          UPDATE orders o SET state = o.status
          FROM batch b WHERE o.id = b.id
      """, (BATCH,)).rowcount
      if n == 0:
          break
      # THROTTLE ON THE SIGNAL THAT ACTUALLY MATTERS
      lag = query("SELECT EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp()))")
      while lag > 5:
          sleep(2); lag = ...
      sleep(0.2)                       # be a polite background job
      log(f"backfilled {n}, remaining {remaining()}")

    duration ................... 51 min (slower on purpose)
    replica lag peak ........... 5.2 s  (throttled)
    longest single lock ........ 40 ms
    deploy pipeline ............ not blocked — it runs separately
    resumable .................. yes: re-run it, it continues
Backfill propertyWhy
BatchedShort locks, small transactions, bounded WAL
IdempotentRe-running after a failure must be safe and must continue, not restart

THE STANDARD SHAPE

  jobs:
    migrate:
      needs: [build, test]
      environment: production
      concurrency:
        group: migrate-production        # NEVER cancel-in-progress
      steps:
        - run: ./ci/assert-safe-migration.sh    # see below
        - run: |
            set -euo pipefail
            ./ci/with-advisory-lock.sh 4711 \
              migrate -path ./migrations -database "$DATABASE_URL" up
        - run: ./ci/verify-schema.sh            # expected version applied

    deploy:
      needs: [migrate]
      steps: [ ... deploy the digest ... ]

  # ci/with-advisory-lock.sh — one migrator at a time, even if two
  # pipelines somehow run together
  psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -c \
    "SELECT pg_advisory_lock($1)" && trap 'psql ... -c "SELECT pg_advisory_unlock($1)"' EXIT
  "${@:2}"

FAILURE HANDLING — WHAT "HALF-APPLIED" MEANS PER ENGINE

  PostgreSQL: DDL is TRANSACTIONAL. A failed migration inside a
    transaction rolls back cleanly — except CREATE INDEX CONCURRENTLY
    and a few others, which cannot be in a transaction and CAN leave
    an INVALID index behind:
      SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
      -- drop it before retrying

  MySQL: DDL is NOT transactional (before 8.0 atomic DDL, and even then
    only per statement). A migration with three ALTERs that fails on the
    second leaves the first applied. Therefore:
      - ONE logical change per migration file
      - make each file idempotent where possible
        (IF NOT EXISTS, or a guard query)
      - never assume "the migration failed" means "nothing happened"

  BOTH: record the version AFTER success, and make the recording part
  of the same transaction where the engine allows it.
💡 The migration job must be gated by a check, not by hope. A script that inspects the pending migrations for destructive statements, missing CONCURRENTLY, or missing timeouts turns a class of outage into a failed pipeline step. It is the highest-value twenty lines in this lesson — a linter for SQL, applied to the diff.

Part 5 — Rehearsal: The Only Honest Way to Know

WHY STAGING DOES NOT TELL YOU

  staging orders table ..........  180,000 rows
  production orders table ....... 41,300,000 rows

  ALTER TABLE ... (the same statement)
    staging ...... 0.3 s     "the migration is instant"
    production ... 4m 12s    with the table locked

  the ratio is not linear either — index builds, sort memory and
  checkpoint behaviour all change shape at scale.

REHEARSE AGAINST A RESTORED PRODUCTION-SIZED COPY

  # nightly, automatically
  jobs:
    rehearse:
      steps:
        - run: ./ci/restore-latest-snapshot.sh rehearsal-db     # ~14 min
        - run: |
            set -euo pipefail
            START=$(date +%s)
            ./ci/with-timeouts.sh migrate -path ./migrations \
                -database "$REHEARSAL_URL" up

      duration ................ 4m12s      ⚠ exceeds the 30s budget

5.1 The compatibility matrix test

  the question expand/contract exists to answer, tested mechanically:

    for schema in (before, after):
      for code in (previous_release, this_release):
        run the integration suite

    schema \ code      v1 (previous)     v2 (this release)
    ------------------------------------------------------
    before             ✅ (today)        ✅ must pass — v2 deploys
                                            before migration finishes
    after              ✅ MUST PASS      ✅ (the target state)
                       ^^^^^^^^^^^^^^
                       this is the cell that catches "we cannot roll back",
                       and it is the one nobody tests.

  # ci/compat-matrix.sh
  for schema in before after; do
    ./ci/restore-snapshot.sh "$schema"
    for ref in "$PREV_RELEASE_SHA" "$GITHUB_SHA"; do
      git checkout "$ref" -- app/
      pytest tests/integration -q || fail "schema=$schema code=$ref"
    done
  done

Part 6 — The Contract Phase: Dropping Things Safely

BEFORE DROPPING ANYTHING, PROVE NOTHING USES IT

  1. STATIC: search the whole organisation, not just this repository
     $ gh search code 'orders.status' --owner acme --limit 100
       -> found in: shop-api, reporting-etl, admin-portal,
                    a Metabase saved question, two Airflow DAGs

  2. RUNTIME: ask the database, which cannot lie
     -- PostgreSQL, with pg_stat_statements
     SELECT calls, query FROM pg_stat_statements
     WHERE query ILIKE '%status%' AND query ILIKE '%orders%'
     ORDER BY calls DESC LIMIT 10;

     -- or column-level: log a sample of queries for 24h and grep

  3. INSTRUMENT: make the code tell you
     def status(self):
         emit_metric("deprecated_field_read", field="orders.status")
         return self._status
     -> wait until the metric is ZERO for two weeks across ALL services,
        including monthly batch jobs. A month-end report that reads the
        column once every 30 days is the classic thing this catches.

  4. THEN drop it, in its own release, with nothing else in it.
Contract-phase ruleReason
At least N releases after the last writePreserves a rollback window; N ≥ 2 in practice
Zero deprecated-read telemetry for two weeksCatches weekly and monthly jobs that static search misses
Search across every repository and BI toolDashboards and ETL are code too, and nobody thinks of them
Drop in its own releaseIf it breaks something, the cause is unambiguous

🔑 The rename-before-drop trick is underused. Renaming a column is fast, reversible in one statement, and makes every remaining reader fail immediately and visibly rather than silently reading a column that is about to disappear. Leave it renamed for a release; if nothing breaks, drop it. If something does break, rename it back in seconds.

❌ A release containing ALTER TABLE orders DROP COLUMN status, an ADD COLUMN NOT NULL DEFAULT gen_random_uuid(), a 40-million-row UPDATE in the same migration file, run on application startup by every replica, with no timeouts and no rehearsal. The ALTER holds an ACCESS EXCLUSIVE lock for four minutes, queues 61,000 requests, exhausts the connection pool at 38 seconds and takes the service down — for a change described in review as "additive". The backfill runs 38 minutes inside the deploy, pushes replica lag to 94 seconds so every read replica serves stale data, and generates 22 GB of WAL that alerts the DBA. Because migrations run at startup, eight replicas race to apply them and two partially succeed against MySQL's non-transactional DDL, leaving a schema that matches no migration version. And when the release turns out to be broken for an unrelated reason, the thirty-second rollback completes perfectly and the service stays down, because v1 selects a column that no longer exists. Staging said the migration took 0.3 seconds, because staging has 180,000 rows.

✅ Expand/contract across releases, locks bounded by timeouts, backfills as throttled resumable jobs, one migrator holding an advisory lock, and rehearsal against a production-sized restore. Design every schema change so the previous release still runs against it, and spread the six phases over several releases so there is always a rollback window — the drop belongs two or more releases after the last write, in a release containing nothing else. Set lock_timeout to a few seconds so a migration that cannot get its lock fails fast instead of queueing the entire table behind it, use CREATE INDEX CONCURRENTLY outside a transaction, and prefer NOT VALID constraints validated separately. Move data changes out of migrations entirely: batched, idempotent, throttled on replica lag, observable and resumable — 51 minutes as a background job beats 38 minutes of blocked deploy and 94 seconds of lag. Run migrations in a dedicated pipeline job holding an advisory lock, gated by a linter that rejects destructive or unbounded statements, and verify the applied version afterwards. Rehearse nightly on a restored production-sized copy, publish duration and longest lock on the pull request, and run the compatibility matrix — old code against the new schema is the cell that proves rollback still works. Then, before dropping anything, prove nothing reads it with telemetry over a period long enough to include the month-end jobs.

Interview Questions

Beginner: Why can't you just rename a database column in the same release that renames it in the code?

Because two versions of the code run at the same time, and because rollback must keep working.

During any rolling deploy, some instances run the old code and some the new. If the migration renames status to state, every old instance immediately starts failing — column "status" does not exist — for the whole rollout.

And the worse case is rollback. If the release turns out to be broken for an unrelated reason, you roll the code back in thirty seconds, the rollback succeeds, and the service is still down, because the old code needs a column that no longer exists. Code rolls back; data does not.

The safe form is expand/contract: add the new column, write both, backfill, switch reads, stop writing the old one, and drop it several releases later. It takes longer in calendar time, and every intermediate state is one where both the current and previous release work.

Beginner: What is expand/contract and what are its phases?

A pattern for changing a schema without breaking either the running code or the ability to roll back. Six phases, spread over several releases:

  1. Expand — add the new structure (nullable column, new table). Old code ignores it.
  2. Dual write — the application writes both old and new, still reads the old.
  3. Backfill — copy existing data, as a batched background job, not as a migration.
  4. Switch reads — read from the new structure, keep writing both.
  5. Stop writing the old — this is the phase that ends the rollback window to the earliest release, which is why it is separate.
  6. Contract — drop the old structure, once telemetry proves nothing reads it.

The phase people skip is 5: they go from switching reads straight to dropping, while some service — a report, a worker, a dashboard — is still writing the old column, and its writes silently stop mattering.

The cost is calendar time: two to four releases for one rename. The benefit is that at no point does a rollback leave you with code that cannot run.

Mid: A migration adds a column with a default to a 40-million-row table and takes the site down. What went wrong and how do you fix it?

Two separate problems, and both need naming.

The rewrite: on older engines — or on any engine when the default is a function rather than a constant — ADD COLUMN … NOT NULL DEFAULT rewrites every row while holding an ACCESS EXCLUSIVE lock. Measured: 4m12s, during which every query on the table blocked, 61,000 requests queued and the connection pool exhausted at 38 seconds.

The lock queue: even a fast ALTER is dangerous if it has to wait for a lock. Once it is queued, every subsequent query on the table queues behind it — so a long-running SELECT plus a migration equals a table-wide outage for the duration of that select.

The fix, in order:

  • SET lock_timeout = '3s' so the migration fails fast instead of queueing everything behind it; retry with backoff rather than waiting.
  • Add the column nullable and without a default (metadata-only), then backfill in batches, then add the NOT NULL constraint via a validated CHECK.
  • Rehearse on a restored production-sized copy and publish the measured duration and longest lock on the pull request — staging said 0.3 seconds because staging has 180,000 rows.
  • Add a migration linter to CI that rejects this pattern before review.
Mid: How would you backfill 40 million rows without impacting production?

As a job, not a migration, with five properties:

PropertyImplementation
Batched5,000 rows per transaction, ordered by primary key, FOR UPDATE SKIP LOCKED
Idempotent and resumableFilter on WHERE state IS NULL; re-running continues rather than restarting
Throttled on the right signalMeasured replica lag, pausing above ~5 s — CPU and IO are proxies, lag is the actual user-visible harm
ObservableLog rows done, rows remaining and rate; someone must see progress
Outside the deploy pathA 51-minute deploy is broken; a 51-minute background job is normal

The comparison that makes the case: a single UPDATE took 38 minutes, drove replica lag to 94 seconds, generated 22 GB of WAL and blocked the pipeline — and a failure at minute 37 rolled back everything. The batched version took 51 minutes, held no lock longer than 40 ms, kept lag under 5.2 seconds, and could be stopped and resumed at any point.

Then verify before proceeding: a query proving zero remaining discrepancies is the gate for the next expand/contract phase, and it belongs in the pipeline, not in someone's memory.

Senior: Where should migrations run in a CD pipeline, and how do you prevent two runners applying them simultaneously?

A dedicated job between test and deploy, not on application startup and not by hand.

OptionVerdict
Dedicated pipeline job before deployPreferred — visible, orderable, lockable, and its failure stops the deploy
Init container / release commandWorkable, but every replica attempts it — requires a lock, and failures look like crash loops
Application on startupWorst at scale: races, partial application, slow starts, no visibility
Manual by a DBANot continuous delivery; the schema drifts from the code

Preventing concurrent application, in layers: a CI concurrency group for the migrate job (never cancel-in-progress — a cancelled migration is worse than a queued one), and a database advisory lock held for the duration, which protects against anything outside CI too. Most migration tools take such a lock themselves; verify it rather than assuming, because the ones that do not fail silently and interleave.

Failure handling depends on the engine, and the difference matters: PostgreSQL DDL is transactional, so a failed migration usually rolls back cleanly — except CREATE INDEX CONCURRENTLY, which cannot run in a transaction and can leave an INVALID index that must be dropped before retrying. MySQL DDL is not transactional, so a file with three ALTERs that fails on the second leaves the first applied. That is the argument for one logical change per migration file and for verifying schema state after any failure rather than assuming nothing happened.

Senior: How do you gain confidence in a risky migration before it runs against production?

Rehearsal on production-sized data, an automated safety review, and a test of the rollback path — none of which staging provides.

For genuinely dangerous changes I would add two operational precautions: take a snapshot immediately before, and consider renaming instead of dropping — a rename is fast, instantly reversible, and makes any remaining reader fail loudly rather than silently. Leave it renamed for a release; if nothing breaks, drop it.

And the organisational point: the pull request for a migration should carry its rehearsal output the way a code change carries test results. Without that, review of a schema change is people reading SQL and guessing how long it will take.

1 (easy): Take a "simple" rename and rewrite it as an expand/contract sequence, marking the rollback window at every phase.
Solution

The request: rename orders.status to orders.state. What arrives in review is usually one file:

  -- 0042_rename_status.sql        ❌ THE VERSION THAT BREAKS ROLLBACK
  ALTER TABLE orders RENAME COLUMN status TO state;

  what happens: during the rolling deploy, every old replica fails with
  `column "status" does not exist`; and rolling back the code leaves
  v1 running against a schema it cannot use.

THE SEQUENCE, WITH THE ROLLBACK WINDOW MARKED AT EACH STEP

  RELEASE N
    migration 0042: ALTER TABLE orders ADD COLUMN state text;

    code: reads `state`; still writes BOTH
    can roll back to N?    YES — N reads `status`, which is still written
    the rollback window is still open

    code: writes ONLY `state`
    can roll back to N+1?  YES  (N+1 reads `state`)

2 (easy): Add a migration linter to CI that rejects the dangerous patterns before review.
Solution 
  #!/usr/bin/env bash
  # ci/assert-safe-migration.sh — run on every PR touching migrations/
  set -euo pipefail
  BASE="${1:-origin/main}"
  FILES=$(git diff --name-only "$BASE...HEAD" -- 'migrations/*.sql')
  [ -z "$FILES" ] && { echo "no migrations changed"; exit 0; }
  FAIL=0
  note() { echo "::error file=$1::$2"; FAIL=1; }
  warn() { echo "::warning file=$1::$2"; }

  for f in $FILES; do
    SQL=$(tr 'a-z' 'A-Z' < "$f")

    # 1. destructive DDL must be explicitly acknowledged
    if grep -qE 'DROP (COLUMN|TABLE)|RENAME COLUMN' <<<"$SQL"; then
      grep -q 'expand-contract-phase: contract' "$f" \
        || note "$f" "destructive DDL without an 'expand-contract-phase: contract' marker"
      grep -q 'verified-unused-since:' "$f" \
        || note "$f" "destructive DDL without a 'verified-unused-since:' date"
    fi

    # 2. indexes must be concurrent, and therefore non-transactional
    if grep -q 'CREATE INDEX' <<<"$SQL" && ! grep -q 'CONCURRENTLY' <<<"$SQL"; then
      note "$f" "CREATE INDEX without CONCURRENTLY blocks writes"
    fi
    if grep -q 'CONCURRENTLY' <<<"$SQL" && ! grep -q 'no-transaction' "$f"; then
      note "$f" "CONCURRENTLY requires a 'no-transaction' marker for the runner"
    fi

    # 3. volatile defaults rewrite the table
    if grep -qE 'ADD COLUMN.*DEFAULT *(GEN_RANDOM_UUID|NOW|CURRENT_|UUID_)' <<<"$SQL"; then
      note "$f" "ADD COLUMN with a volatile DEFAULT rewrites every row under an exclusive lock"
    fi

    # 4. NOT NULL on an existing column
    if grep -qE 'ALTER COLUMN .* SET NOT NULL' <<<"$SQL"; then
      grep -q 'NOT VALID' <<<"$SQL" \
        || warn "$f" "SET NOT NULL scans the whole table; consider CHECK ... NOT VALID then VALIDATE"
    fi

    # 5. constraints that validate on creation
    if grep -qE 'ADD CONSTRAINT.*(FOREIGN KEY|CHECK)' <<<"$SQL" \
       && ! grep -q 'NOT VALID' <<<"$SQL"; then
      warn "$f" "constraint validates on creation and locks; consider NOT VALID + VALIDATE"
    fi

    # 6. data changes do not belong in migrations
    if grep -qE '^\s*(UPDATE|DELETE|INSERT)' <<<"$SQL"; then
      grep -q 'LIMIT' <<<"$SQL" \
        || note "$f" "unbounded DML in a migration — use a batched backfill job"
    fi

    # 7. timeouts must be set
    grep -q 'LOCK_TIMEOUT' <<<"$SQL" \
      || note "$f" "missing SET lock_timeout — a waiting migration queues the whole table"

    # 8. one logical change per file (MySQL non-transactional DDL)
    n=$(grep -cE '^\s*ALTER TABLE' <<<"$SQL" || true)
    [ "$n" -le 1 ] || warn "$f" "$n ALTER statements in one file; split them"
  done
  exit "$FAIL"

4 (medium): Write a backfill job that is batched, throttled, resumable and observable — then verify the data before advancing a phase.
Solution 
  #!/usr/bin/env python3
  """Backfill orders.state from orders.status. Safe to stop and re-run."""
  import os, sys, time, logging, psycopg
  BATCH        = int(os.environ.get("BATCH", 5000))
  MAX_LAG_S    = float(os.environ.get("MAX_LAG_S", 5))
  PAUSE_S      = float(os.environ.get("PAUSE_S", 0.2))
  log = logging.getLogger("backfill")

  SQL_BATCH = """
    WITH batch AS (
      SELECT id FROM orders
      WHERE state IS NULL
      ORDER BY id
      LIMIT %s
      FOR UPDATE SKIP LOCKED
    )
    UPDATE orders o SET state = o.status
    FROM batch b WHERE o.id = b.id
  """
  SQL_LAG = """
    SELECT COALESCE(EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp())), 0)
    FROM pg_stat_replication LIMIT 1
  """
  SQL_REMAINING = "SELECT count(*) FROM orders WHERE state IS NULL"

  def replica_lag(cur):
      cur.execute(SQL_LAG); row = cur.fetchone()
      return float(row[0]) if row else 0.0

  def main():
      done = 0
      t0 = time.time()
      with psycopg.connect(os.environ["DATABASE_URL"], autocommit=True) as conn:
          with conn.cursor() as cur:
              cur.execute("SET lock_timeout = '3s'")
              cur.execute("SET statement_timeout = '30s'")
              cur.execute(SQL_REMAINING); total = cur.fetchone()[0]
              log.info("starting: %s rows to backfill", f"{total:,}")
              while True:
                  try:
                      cur.execute(SQL_BATCH, (BATCH,))
                      n = cur.rowcount
                  except psycopg.errors.LockNotAvailable:
                      log.warning("lock timeout; backing off"); time.sleep(5); continue
                  if n == 0:
                      break
                  done += n
                  lag = replica_lag(cur)
                  while lag > MAX_LAG_S:                    # THROTTLE
                      log.warning("replica lag %.1fs > %.1fs — pausing", lag, MAX_LAG_S)
                      time.sleep(2); lag = replica_lag(cur)
                  rate = done / max(time.time() - t0, 1)
                  log.info("done=%s remaining≈%s rate=%.0f/s eta=%.0fmin lag=%.1fs",
                           f"{done:,}", f"{max(total-done,0):,}", rate,
                           max(total-done, 0) / max(rate, 1) / 60, lag)
                  time.sleep(PAUSE_S)                        # be polite
      log.info("complete: %s rows in %.1f min", f"{done:,}", (time.time()-t0)/60)

  if __name__ == "__main__":
      logging.basicConfig(level=logging.INFO, format="%(asctime)s %(message)s")
      sys.exit(main())

🎯 Key Takeaways

  • Code rolls back in seconds; data does not roll back at all. Every schema change must leave the previous release able to run — a successful rollback onto a dropped column still leaves the service down.
  • Expand/contract is several releases, not one deployment with six steps: expand, dual write, backfill, switch reads, stop writing the old, contract.
  • Phase 5 — stop writing the old column — is the one people skip, and it is where the rollback window to the earliest release deliberately closes.
  • Locks, not duration, are the risk. ADD COLUMN NOT NULL DEFAULT gen_random_uuid() held an exclusive lock for 4m12s on 41M rows, queued 61,000 requests and exhausted the pool at 38 seconds.
  • A migration waiting for a lock queues the whole table behind it — so a long-running SELECT plus a migration is a table-wide outage even before the migration starts.
  • SET lock_timeout changes the failure mode from "four-minute outage" to "the deploy stops in three seconds and you fix the approach".
  • Use CREATE INDEX CONCURRENTLY (outside a transaction — most tools wrap migrations in one), and NOT VALID constraints validated separately, which takes a weaker lock that lets reads and writes continue.
  • Backfills are jobs, not migrations: a single UPDATE ran 38 minutes, pushed replica lag to 94 s and generated 22 GB of WAL; the batched version took 51 minutes with a 40 ms longest lock.
  • A backfill must be batched, idempotent, resumable, throttled on measured replica lag, observable and outside the deploy path — and gated by a verification query before the next phase.
  • Run migrations in a dedicated pipeline job holding an advisory lock, never on application startup where every replica races.
  • Engine differences matter on failure: PostgreSQL DDL is transactional (except concurrent index builds, which can leave an INVALID index); MySQL DDL is not, so one file with three ALTERs can half-apply.
  • Staging cannot tell you a migration's duration — 0.3 s on 180k rows against 4m12s on 41.3M. Rehearse against a restored production-sized snapshot.
  • Publish duration, longest blocking lock, blocked queries and induced replica lag on the pull request, so review is a decision rather than people reading SQL and guessing.
  • The compatibility matrix — {old schema, new schema} × {previous release, this release} — is the rollback guarantee, and the old-code/new-schema cell is the one nobody tests.
  • A migration linter in CI catches destructive DDL without a phase marker, volatile defaults, non-concurrent indexes, unbounded DML and missing timeouts — before review.
  • Markers beat prohibitions: requiring expand-contract-phase and verified-unused-since forces the author to state which phase they are in.
  • Before dropping, prove nothing reads it with code search across every repository, a BI-tool inventory, pg_stat_statements, and application telemetry at zero.
  • Wait through a month boundary — the monthly reconciliation job that reads a column once every thirty days is invisible to a two-week window and catastrophic on the 1st.
  • Rename before dropping. A rename is fast, reversible in one statement, and makes any remaining reader fail loudly instead of silently — the cheapest backstop available.
  • Destructive changes ship alone, after a snapshot, so that if something breaks the cause is unambiguous.
