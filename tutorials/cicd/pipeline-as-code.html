Pipelines as Code: Reuse & Versioning Foundations

What you'll master: why an estate of copy-pasted pipelines is not a style problem but a change-cost problem — a one-line security fix took 61 pull requests and eleven weeks, and 23 repositories were still unpatched at the end; which reuse primitive fits which job (composite action, reusable workflow, container image, shared library) and the capability boundaries that decide for you, including the one people hit first — a composite action cannot set concurrency, use services, or run its steps on a different runner; how to version shared CI as the library it is, after the incident where a platform team pushed to main and broke 47 repositories in nine minutes, and why third-party actions get pinned by SHA rather than by tag; the config complexity clock, where YAML with enough conditionals becomes a programming language you are writing badly — and the escape valve; how to test CI code, since a reusable workflow used by 60 repositories is production software with no test suite in most organisations; and when a pipeline should be generated rather than written, with the debuggability cost that comes with it. Prerequisites: Anatomy of a Pipeline.

Part 1 — The Copy-Paste Estate

Every organisation starts the same way: a good pipeline exists in one repository, someone copies it to the next, and eighteen months later there are sixty variants of a file that were identical on the day they were created.

MEASURED: SIXTY REPOSITORIES, ONE ANCESTOR FILE

  repositories with a CI workflow ........................ 60
  distinct variants of the "same" workflow ............... 54
  Node versions in use across them ....... 14, 16, 18, 20, 22  (5)
  checkout action versions ................. v2, v3, v4        (3)
  repos still using the deprecated set-output syntax ..... 31
  repos with NO dependency caching at all ................ 22
  repos publishing images by mutable tag rather than digest 38
  median age of the copied file .......................... 14 months

  THE COST APPEARS WHEN SOMETHING MUST CHANGE:
    a token scope had to be narrowed after a security review
      -> 61 pull requests, 11 weeks, 4 people chasing reviews
      -> 23 repositories were STILL unpatched when the audit closed,
         because their teams had reorganised and nobody owned them
🔑 Copy-paste is not a style crime; it is a decision to make every future change cost N pull requests. The question to ask about any shared pipeline pattern is therefore not "is this DRY?" but "when the next mandatory change arrives — a token scope, a runner migration, a compromised action — how many pull requests and how many weeks?" That number is the whole argument, and it is measurable before anyone proposes a refactor.

The opposite failure is worth naming immediately, because the reaction to the table above is usually over-correction: a single mega-workflow that every repository must call, with forty inputs, that nobody can change without risking everything. That is the config complexity clock in Part 4, and it is how platform teams become a queue.

Part 2 — The Reuse Primitives, and What Each Can Actually Do

Composite actionA sequence of steps, inlined into the caller's job"Set up our toolchain", "authenticate", "publish test results"Runs on the caller's runner; no concurrency, no services, no job-level if, no matrix; secrets must be passed as inputs
Reusable workflowWhole jobs, called with inputs and secrets"The standard Node service CI", "the release pipeline"Nesting depth is capped (4 levels on GitHub); the caller cannot reach inside a job; limited outputs
Container imageThe environmentToolchains, linters, scanners — the most portable unit there isDoes not orchestrate anything; you still need YAML around it

THE DECISION, AS A SEQUENCE OF QUESTIONS

  Is it a few steps that always run inside someone else's job?
      -> COMPOSITE ACTION            (setup-toolchain, auth, upload-report)

  Is it one or more whole jobs, with its own runners, matrix or services?
      -> REUSABLE WORKFLOW           (node-service-ci, publish-release)

  Is it "the tools needed to run X"?
      -> CONTAINER IMAGE             (ghcr.io/acme/ci-node:20)

  Is it logic that should run identically on a laptop?
      -> SCRIPT in the repo          (ci/build.sh)

  Is it a policy that must apply whether or not teams cooperate?
      -> NOT a reuse primitive at all. That is branch protection, an
         org-level required workflow, or an admission policy — see
         platform rollout at the end of this track.

2.1 The capability boundary people hit first

  # This does NOT work. A composite action cannot do job-level things.
  # action.yml
  runs:
    using: composite
    steps:
      - uses: actions/checkout@v4
      - services:                    # ERROR: not valid in a composite action
          postgres: { image: postgres:16 }

      - if: github.event_name == 'push'   # (step-level `if` IS allowed)
        run: echo ok
        shell: bash                  # NOTE: `shell:` is REQUIRED in composites

  # .github/workflows/service-ci.yml
  on:
    workflow_call:
      inputs:
        node-version: { type: string, default: '20' }
        run-e2e:      { type: boolean, default: false }
      secrets:
        REGISTRY_TOKEN: { required: true }
      outputs:
        image-digest: { value: ${{ jobs.build.outputs.digest }} }
  jobs:
    test:
      runs-on: ubuntu-latest
      services: { postgres: { image: postgres:16 } }     # allowed here

💡 secrets: inherit is convenient and blunt. It passes every secret the caller can see into the called workflow, which is fine when both are yours and dangerous the moment the shared workflow lives in another repository with different reviewers. Declaring the two or three secrets a workflow actually needs is a five-line cost that keeps the blast radius of a compromised shared workflow small — see pipeline identity.

Part 3 — Version Shared CI Like the Library It Is

The moment a workflow is called by other repositories, it is a published dependency with an API. Teams that skip this step discover it in one specific way:

THE INCIDENT (a real shape, in one form or another, everywhere)

  09:02  platform team merges "small fix" to shared-workflows main
  09:04  47 repositories referencing @main pick it up on their next run
  09:07  every pipeline fails: the fix renamed an input
  09:11  first escalation
  09:26  revert merged
  09:33  most repositories green again
  total: 31 minutes of a 200-engineer organisation unable to merge anything

  ROOT CAUSE: not the rename. The rename was fine. The cause was that
  60 repositories referenced a MOVING BRANCH.
Reference styleBehaviourVerdict
@mainEvery consumer picks up every commit, immediatelyNever for anything with consumers outside the repo
@v3 (moving major tag)Consumers get bug fixes and additive changes; breaking changes require @v4The default for first-party shared workflows
@v3.2.1 (exact tag)Fully pinned; nothing changes until someone bumps itFor repositories that need maximum stability, at the cost of manual updates
@<40-char SHA>Immutable — a tag can be moved, a SHA cannotRequired for third-party actions (supply chain), plus a comment naming the version
THE CONVENTIONS THAT MAKE THIS WORK

  # first-party shared workflow: moving major tag
  uses: acme/shared-workflows/.github/workflows/service-ci.yml@v3

  # third-party action: SHA-pinned, with the human-readable version
  uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2

  # maintaining the moving tag on release (this is the whole trick)
  $ git tag -a v3.4.0 -m "add run-e2e input"
  $ git tag -fa v3 -m "v3 -> v3.4.0"        # force-move the major tag
  $ git push origin v3.4.0 && git push -f origin v3

  A BREAKING CHANGE IS A NEW MAJOR, NOT A DISCUSSION:
    - renaming or removing an input          -> v4
    - changing a default that alters behaviour -> v4
    - requiring a secret that was optional   -> v4
    - adding an OPTIONAL input with a safe default -> v3.5.0, no action needed
⚠️ Tags are mutable; that is exactly why third-party actions must be pinned by SHA. An attacker (or a well-meaning maintainer) who can move v4 can change what runs inside your pipeline — with your tokens — without any change in your repository. SHA pinning turns a supply-chain question into a code-review question, and dependency bots can still raise the update PRs for you. This is covered in depth in supply-chain security.

3.1 Deprecation, with a window

  RELEASING v4 WHEN 60 REPOSITORIES USE v3

  week 0   v4 released. CHANGELOG names every breaking change with a
           before/after snippet. v3 keeps working, untouched.
  week 0   v3 emits a warning, once per run, that is impossible to miss:
             echo "::warning::service-ci v3 is deprecated; migrate to v4
                   by 2026-11-01. See MIGRATION.md"
  week 1   automated migration PRs raised against the 12 simplest consumers
           (a script does the edit; humans review and merge)
  week 4   dashboard of consumers by version; personal nudges to stragglers

  MEASURED ADOPTION on this schedule: 60 -> 4 remaining at week 8,
  and the last 4 were repositories with no owner, which the exercise
  surfaced as its real finding.

Part 4 — The Config Complexity Clock

There is a predictable progression in every shared pipeline, and knowing it lets you stop one step before the wall.

  1. hardcoded            one repository, one workflow. Clear, duplicated.
  2. parameterised        inputs appear: node-version, run-e2e. Still clear.
  3. conditional          if: inputs.deploy == true && github.ref == ...
  4. computed             expressions building strings from other inputs
  5. templated            YAML generating YAML; anchors; nested includes
  6. "we wrote a DSL"     nobody can predict what a change does; the
                          platform team is now the only group who can edit it
  7. escape               someone writes a script — and it is readable again

  THE OBSERVATION: step 7 was available at step 3, and the four steps
  in between cost a year.
Smell in a shared workflowWhat it meansMove to
More than ~8 inputsIt is serving several use cases badlySplit it into two workflows, or accept a second variant
Boolean inputs that switch whole jobs on and offTwo workflows wearing one costumeTwo named workflows the caller chooses between
Nested ternaries in an expressionLogic in a language with no tests and no debuggerA script that takes env vars and prints its decision
YAML anchors and merge keys everywhereClever, and unreadable at 03:00Explicit repetition, or generation with a real language
An input named extra_argsThe abstraction has failed and is being bypassedFind what people are actually passing; make that a first-class input or let them own their workflow
THE ESCAPE VALVE, CONCRETELY

  ❌ 40 lines of expression:
     tag: ${{ github.ref == 'refs/heads/main' && 'latest'
              || startsWith(github.ref, 'refs/tags/')
                 && format('{0}', ...) || format('pr-{0}', ...) }}

  ✅ one line of YAML, plus a script that a human can read and a test
     can exercise:
     - id: meta
       run: ./ci/compute-tags.sh >> "$GITHUB_OUTPUT"
       env: { GIT_REF: ${{ github.ref }}, PR: ${{ github.event.number }} }

Part 5 — Testing CI Code

A reusable workflow used by 60 repositories is production software. In most organisations it has no tests, no staging and no rollback plan, which is why the incident in Part 3 is so common.

LayerToolCatchesCost

Script unit testsbats, or plain assertions in a scriptTag computation, version parsing, decision logicSmall, because the logic already lives in scripts
Self-testThe shared repo calls its own workflow on every PRDoes it actually run end to end? Do the inputs work?One workflow file

  jobs:
    lint:
      steps:
        - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
        - run: |
            bash <(curl -fsSL https://raw.githubusercontent.com/rhysd/actionlint/main/scripts/download-actionlint.bash)
            ./actionlint -color
        - run: shellcheck ci/*.sh

  # self-test: the repo consumes its own workflow
  # .github/workflows/selftest.yml
  jobs:
    call-service-ci:
      uses: ./.github/workflows/service-ci.yml
      with: { node-version: '20', run-e2e: true }
      secrets: { REGISTRY_TOKEN: ${{ secrets.TEST_REGISTRY_TOKEN }} }

  MEASURED VALUE: actionlint alone caught, in one repository's history,
  31 issues that had each previously been found by pushing and waiting —
  including 9 references to a context that does not exist in that trigger
  (an expression that silently evaluates to an empty string rather than
  failing, which is the worst possible behaviour).
🔑 An undefined expression evaluates to an empty string rather than an error. ${{ github.event.pull_request.number }} on a push event is not a failure; it is "". That is how you get an image tagged pr- or a deploy to an environment called "". A linter finds these statically; a runtime guard (: "${PR:?}" in the script) catches the rest — and both are cheaper than the incident.

Part 6 — When to Generate the Pipeline

Sometimes the graph genuinely depends on the repository's contents: a monorepo where only affected services should build, a matrix derived from a manifest, or a fan-out over a list that changes weekly. Static YAML expresses this badly; generation expresses it well and costs you debuggability.

GENERATING A MATRIX FROM A REAL DECISION

  jobs:
    plan:
      outputs: { targets: ${{ steps.plan.outputs.targets }} }
      steps:
        - uses: actions/checkout@... { with: { fetch-depth: 0 } }
        - id: plan
          run: |
            # which services are affected by this diff?
            ./ci/affected.sh "origin/${{ github.base_ref }}" > targets.json
            echo "targets=$(cat targets.json)" >> "$GITHUB_OUTPUT"
            cat targets.json          # ALWAYS log the plan

    build:
      needs: [plan]
      if: ${{ needs.plan.outputs.targets != '[]' }}
      strategy:
        matrix: { target: ${{ fromJSON(needs.plan.outputs.targets) }} }
      steps:
        - run: ./ci/build.sh "${{ matrix.target }}"

  MEASURED on a 34-service monorepo:
    builds per PR before ...... 34 services, 41 min
    builds per PR after ....... 2.8 services (median), 9 min
    runner minutes ............ −71%
    the cost: when it is WRONG, it is wrong invisibly — a missed
    dependency edge means a service that should have been rebuilt was not.
Generation is worth it when…Prefer static YAML when…
The set of jobs depends on the diff (monorepo affected targets)The graph is the same on every run
A matrix comes from a manifest that changes oftenThe matrix is three Node versions
Hundreds of similar jobs would otherwise be hand-writtenA reviewer should be able to read the pipeline in the diff
You can log the generated plan and it is reviewableDebuggability matters more than expressiveness

Two rules keep generated pipelines humane. Log the plan — print the generated JSON or YAML in the run, so a human can see what was decided and why. And make the generator runnable locally (./ci/affected.sh main), so "why did it build these three?" is a question answered on a laptop rather than by re-reading expressions in a log.

❌ Sixty copy-pasted workflows that have drifted into 54 variants, a shared workflow everyone references as @main, third-party actions pinned to floating tags, forty inputs and nested ternaries in the shared file, no linting, and no tests. A one-line token-scope fix becomes 61 pull requests over eleven weeks and still leaves 23 repositories unpatched. Meanwhile the shared workflow that is used is a moving target: a small fix merged at 09:02 broke 47 repositories by 09:04 and nobody could merge anything for half an hour. Third-party actions can change under you without a commit in your repository, because a tag is a pointer someone else controls. The shared file has climbed the complexity clock to the point where only the platform team dares edit it, and every change is a gamble because there is no lint, no self-test and no canary — so the first consumer of a new version is all sixty repositories at once. And an undefined expression quietly renders as an empty string, so an image gets tagged pr- and a deploy targets an environment named "".

✅ Shared workflows treated as a versioned library, the right primitive for each job, logic in scripts, and CI code that is linted, tested and rolled out in stages. Ask the change-cost question — "when the next mandatory change lands, how many PRs and how many weeks?" — and let the answer justify the refactor. Use composite actions for step sequences, reusable workflows for whole jobs with their own runners and services, container images for toolchains, and repo scripts for anything specific. Reference first-party shared workflows by a moving major tag (@v3) so a breaking change requires @v4, pin third-party actions by SHA with the version in a comment, and publish a changelog with a dated deprecation window — measured 60 → 4 consumers in eight weeks, the last four being repositories with no owner, which was the real finding. Stop at step 3 of the complexity clock: when an expression needs a nested ternary or the input list passes eight, move the decision into a script that prints what it chose. Then test the CI code like code — actionlint and shellcheck on every PR (31 issues caught statically in one repository, including nine empty-string expressions), unit tests for the scripts, a self-test that calls the workflow, two canary consumers on the pre-release tag, and only then move the major tag.

Interview Questions

Beginner: What is the difference between a composite action and a reusable workflow?

A composite action packages a sequence of steps that are inlined into the caller's job. It runs on the caller's runner, shares that job's filesystem, and is the right tool for "set up our toolchain", "authenticate to the registry" or "publish the test report".

A reusable workflow packages whole jobs. It brings its own runners, can declare a matrix, use service containers, set concurrency, and define its own job graph. It is the right tool for "the standard CI pipeline for a Node service".

The boundary is easiest to remember by what a composite action cannot do: no services, no concurrency, no matrix, no choice of runner, and no job-level if. The first time someone tries to add a Postgres service container to a composite action, they get Unexpected value 'services' and learn this boundary the hard way.

One practical detail worth mentioning: composite actions require shell: on every run step, and secrets are not automatically available — they must be passed in as inputs, which is a good prompt to think about what the action actually needs.

Beginner: Why should third-party actions be pinned to a commit SHA rather than a version tag?

Because a tag is a mutable pointer controlled by someone else. If you reference @v4, the maintainer — or anyone who compromises their account — can move that tag to different code, and your next pipeline run executes it with your tokens, your secrets and your registry access. Nothing changes in your repository, so nothing appears in your review process.

A 40-character commit SHA is immutable: the content is fixed by the reference. Updating it is a diff someone reviews, which turns a supply-chain exposure into an ordinary code review.

The convention that keeps it readable:

uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2

The comment tells a human which version it is; the SHA tells the runner exactly what to execute. Dependabot and Renovate both understand this pattern and will raise update PRs that bump the SHA and the comment together — so the ergonomics cost is close to zero.

The nuance for first-party workflows in your own organisation: a moving major tag (@v3) is usually correct there, because you control the repository and you want consumers to receive fixes. The rule is about who can move the pointer, not about tags being inherently bad.

Mid: You maintain a workflow used by 60 repositories and need to make a breaking change. Walk through it.

Treat it exactly as you would a breaking change in a published library, because that is what it is.

StepAction
1. Confirm it is breakingRenaming or removing an input, changing a default that alters behaviour, or making an optional secret required. Adding an optional input with a safe default is not breaking
2. Release the new majorTag v4.0.0 and move v4. Leave v3 completely untouched — no "small fixes" backported without care
3. Write the migration guideEvery breaking change with a before/after snippet. This is the artifact that determines whether adoption takes eight weeks or eight months
4. Warn in v3A ::warning:: annotation naming the deprecation date and linking the guide, visible on every run
5. Automate the easy migrationsA script that edits the caller's YAML, raising PRs against the simplest consumers. Humans review; the platform team does not merge for them
6. Measure adoptionA dashboard of consumers by version — code search across the org, refreshed daily
7. Remove on the published dateAnd fail with a message naming the migration guide, never a cryptic error

Two things I would say unprompted. First, the stragglers are usually unowned repositories — measured 60 → 4 in eight weeks, with the last four having no team — so the migration doubles as an ownership audit, which is valuable in itself. Second, never fix this by force-pushing the change into v3: that is precisely the "broke 47 repositories in two minutes" incident, and it destroys the trust that makes the next migration possible.

Mid: How do you test CI configuration before it reaches every consumer?

Five layers, cheapest first, and each catches things the previous cannot:

LayerCatches
actionlint / yamllintInvalid keys, bad expressions, and — most valuably — references to contexts that do not exist for that trigger, which otherwise silently render as empty strings
shellcheck on run: blocks and ci/*.shUnquoted variables, swallowed exit codes, missing pipefail
Unit tests for the scriptsTag computation, version parsing, environment selection — the logic that used to live in expressions
Self-test: the shared repo calls its own workflowWhether it actually runs end to end with realistic inputs
Canary consumers on a pre-release tagIntegration reality — permissions, secrets, and the ways real repositories differ

Then roll out by moving the tag, not by asking sixty teams to change a line: canaries green for a few days, then v3 moves to the new release. That gives you a rollback too — moving the tag back restores every consumer in one operation.

The measured argument for the cheap end: actionlint alone found 31 issues in one repository's history that had each previously been discovered by pushing and waiting, including nine empty-string expressions. At 34 minutes per push-and-wait iteration, that is not a style tool.

Senior: When would you generate a pipeline dynamically rather than write it statically, and what does that cost?

Generate when the job graph genuinely depends on the repository's contents, and not before. The clear cases: a monorepo where only services affected by the diff should build; a matrix derived from a manifest that changes weekly; hundreds of near-identical jobs that would otherwise be hand-maintained.

The benefit is real. On a measured 34-service monorepo, affected-target generation took a PR from building 34 services in 41 minutes to a median of 2.8 services in 9 minutes, cutting runner minutes by 71%.

The costs, which must be accepted deliberately:

  • Debuggability. "Why did it build those three?" is no longer visible in the diff. Mitigate by printing the generated plan in the run and making the generator runnable locally.
  • Silent wrongness. A missing dependency edge means a service that should have been rebuilt was not — and nothing fails. Mitigate with a periodic full build (nightly) that would catch the discrepancy, and by deriving the graph from the build system's real dependency data rather than from hand-written lists.
  • Review. The generator is now code that decides what gets tested, so it needs tests and ownership of its own.

The rule I would apply: prefer static YAML while a reviewer can read the pipeline in the diff. The moment the static version is a hundred near-identical blocks or a nest of conditionals, generation is the more honest representation — but it is a step up in operational seriousness, not a shortcut.

Senior: Design the shared-CI strategy for 60 repositories across 12 teams. What is centralised, what is not, and how do you avoid becoming a bottleneck?

The goal is one place to fix a problem for everyone, without the platform team becoming a queue that every repository waits in.

LayerOwnerContents
Reusable workflows (@v3)PlatformThe three or four standard shapes — service CI, library release, container publish — including security and provenance steps
Composite actionsPlatformAuth via OIDC, toolchain setup, test-report publishing
CI container imagesPlatformToolchains, pinned and scanned
Caller workflow (a dozen lines)The repo's teamWhich shared workflow, with which inputs
ci/*.shThe repo's teamEverything specific to that codebase
Org-level required workflowSecurity/platformOnly what must be non-optional — provenance, secret scanning

Anti-bottleneck mechanisms, which matter more than the layering:

  • An escape hatch, measured. Any team may write their own workflow. Track who does and why; high opt-out on one feature is feedback about the paved road, not disobedience. A standard that cannot be escaped gets circumvented invisibly.
  • Contributions welcome, with ownership. Teams can raise PRs against the shared workflows; the platform team reviews rather than writes. Otherwise every new requirement is a ticket in someone else's backlog.
  • Versioned releases with deprecation windows, so consumers upgrade on their own schedule and the platform team is never forced into a synchronised migration.
  • Published SLO and support model for the shared CI — it is production for 200 engineers, so it needs an owner, a dashboard and an on-call.

What I would avoid: bootstrapping by copying templates (the copies diverge instantly); a bot that force-syncs YAML across repositories (it fights local changes and erodes ownership); and putting business logic into shared actions, which makes the platform team the owner of everyone's build and guarantees the queue you were trying to avoid.

THE REPLACEMENT — ci/plan.sh, readable and testable

  #!/usr/bin/env bash
  set -euo pipefail

  : "${GIT_REF:?GIT_REF required}"
  FORCE_ENV="${FORCE_ENV:-}"
  DEPLOY_PREVIEW="${DEPLOY_PREVIEW:-false}"
  PR_NUMBER="${PR_NUMBER:-}"
  RUN_ATTEMPT="${RUN_ATTEMPT:-1}"

  case "$GIT_REF" in
    refs/heads/main)      TAG="latest";                ENV="production" ;;
    refs/tags/*-rc*)      TAG="rc-${GIT_REF#refs/tags/}"; ENV="staging" ;;
    refs/tags/v*)         TAG="${GIT_REF#refs/tags/}";  ENV="production" ;;
    *)                    : "${PR_NUMBER:?PR_NUMBER required off main}"
                          TAG="pr-${PR_NUMBER}-${RUN_ATTEMPT}"
                          ENV=$([ "$DEPLOY_PREVIEW" = true ] && echo preview || echo none) ;;
  esac
  [ -n "$FORCE_ENV" ] && ENV="$FORCE_ENV"        # explicit override, last

  echo "plan: ref=$GIT_REF tag=$TAG env=$ENV" >&2   # visible in the log
  printf 'tag=%s\nenvironment=%s\n' "$TAG" "$ENV"

  # ci/plan_test.sh — the tests the expression could never have
  set -euo pipefail
  t() { local want="$1"; shift; local got; got="$(env "$@" ./ci/plan.sh 2>/dev/null)"
        [ "$got" = "$want" ] || { echo "FAIL: $* -> $got"; exit 1; }; echo "ok: $*"; }

  t $'tag=latest\nenvironment=production'        GIT_REF=refs/heads/main
  t $'tag=v2.1.0\nenvironment=production'        GIT_REF=refs/tags/v2.1.0
  t $'tag=rc-v2.0.0-rc.1\nenvironment=staging'   GIT_REF=refs/tags/v2.0.0-rc.1
  t $'tag=pr-91-1\nenvironment=none'             GIT_REF=refs/heads/x PR_NUMBER=91
  t $'tag=pr-91-1\nenvironment=preview'          GIT_REF=refs/heads/x PR_NUMBER=91 DEPLOY_PREVIEW=true
  t $'tag=pr-91-2\nenvironment=hotfix'           GIT_REF=refs/heads/x PR_NUMBER=91 RUN_ATTEMPT=2 FORCE_ENV=hotfix
  # and the failure case the expression handled SILENTLY:
  ! GIT_REF=refs/heads/x ./ci/plan.sh 2>/dev/null && echo "ok: missing PR_NUMBER fails loudly"

WEEK 1 — AUTOMATE THE MECHANICAL MIGRATION

  #!/usr/bin/env bash
  # ci/migrate-v3-to-v4.sh — run against a checkout of a consumer repo
  set -euo pipefail
  f=".github/workflows/ci.yml"
  [ -f "$f" ] || { echo "no ci.yml"; exit 1; }
  python3 - "$f" <<'PY'
  import re, sys
  p = sys.argv[1]; s = open(p).read()
  s = s.replace("service-ci.yml@v3", "service-ci.yml@v4")
  m = re.search(r"deploy_env:\s*(\S+)", s)
  env = m.group(1) if m else None
  s = re.sub(r"\n\s*deploy:\s*(true|false)", "", s)
  s = re.sub(r"\n(\s*)deploy_env:\s*\S+",
             (lambda mm: f"\n{mm.group(1)}environment: {env}") if env else "", s)
  s = re.sub(r"\n\s*REGISTRY_TOKEN:.*", "", s)
  open(p, "w").write(s)
  PY
  gh pr create --title "ci: migrate service-ci v3 -> v4" \
    --body "Automated. See MIGRATION.md. Please review and merge."

🎯 Key Takeaways

  • Copy-paste is a decision to make every future change cost N pull requests. Measured: 60 repos, 54 variants, and a one-line security fix that took 61 PRs and 11 weeks while leaving 23 repositories unpatched.
  • Argue with the change-cost question — "when the next mandatory change arrives, how many PRs and how many weeks?" — not with duplication, which invites a debate about taste.
  • Composite action = steps in the caller's job; reusable workflow = whole jobs with their own runners. The boundary is what a composite cannot do: no services, no concurrency, no matrix, no runner choice, and shell: required on every step.
  • Container images are the most portable reuse unit (the environment), and repo scripts are the right home for anything codebase-specific.
  • secrets: inherit hands over every secret the caller can see — declare the two or three a workflow actually needs, especially when it lives in another repository.
  • A shared workflow is a published library. Referencing @main caused a "small fix" to break 47 repositories in two minutes and block a 200-engineer org for half an hour.
  • Reference first-party shared workflows by a moving major tag (@v3), automate the tag move on release, and treat rename/removal/newly-required-secret as a new major.
  • Pin third-party actions by 40-character SHA with the version in a comment — a tag is a pointer someone else controls, and moving it runs unreviewed code with your tokens.
  • Deprecate with a dated window: warning annotation → automated migration PRs → adoption dashboard → removal with a message naming the guide. Measured 60 → 4 consumers in eight weeks.
  • The stragglers are almost always unowned repositories, so every migration doubles as an ownership audit — which is often its most valuable output.
  • The config complexity clock: hardcoded → parameterised → conditional → computed → templated → "we wrote a DSL". Escape at step 3 by moving the decision into a script; the four steps in between cost a year.
  • Smells that mean you have climbed too far: more than ~8 inputs, boolean inputs that switch whole jobs, nested ternaries, YAML anchors everywhere, and an input called extra_args.
  • An undefined expression renders as an empty string, not an error — that is how images get tagged pr- and deploys target an environment named "". Lint statically and guard at runtime with : "${VAR:?}".
  • CI code is production software: test it. actionlint plus shellcheck caught 31 issues in one repository that had each previously been found by pushing and waiting.
  • Test in five layers — lint, script unit tests, a self-test that calls the workflow, canary consumers on a pre-release tag, then a staged tag move.
  • Canaries catch what self-tests structurally cannot: permissions and identity, because the shared repo's own tokens and OIDC subject are not the consumer's.
  • The moving tag is your rollback — moving v4 back to the previous release restores every consumer in about 90 seconds. Exercise it on a quiet afternoon.
  • Generate the pipeline only when the graph depends on the repository's contents — affected-target generation took a 34-service monorepo from 34 builds in 41 minutes to 2.8 in 9, cutting runner minutes 71%.
  • Generation costs debuggability and can be silently wrong (a missed dependency edge skips a build that should have run): log the plan, make the generator runnable locally, and keep a nightly full build as the backstop.
  • Raise migration PRs; do not merge them. Automation removes the tedium, review keeps the ownership — and ownership is what makes the next migration cheaper instead of identical.
