Containers in CI Pipeline Engineering

What you'll master: the distinction that resolves most container-CI confusion — containers as the build environment versus building container images, which are different problems with different failure modes; why every CI build starts with a cold layer cache on an ephemeral runner and how to fix that, measured at 8m52s down to 47s with a registry cache and correct instruction ordering; the Dockerfile properties that matter specifically in CI — dependency-layer separation, --mount=type=cache, a .dockerignore that stopped shipping 1.9 GB of context on every build, and the COPY . . placement that silently invalidates everything; multi-architecture builds, where QEMU emulation measured 14× slower than native runners and the manifest-merge pattern that avoids it; service containers versus Testcontainers, and how to make either start reliably rather than with a sleep; and the security properties of container CI — why a shared Docker daemon on a self-hosted runner means any job can read any other job's registry credentials and images, and what to use instead. Prerequisites: Anatomy of a Pipeline, Builds & Artifacts, and the Docker track for the image internals.

  jobs:
    test:
      runs-on: ubuntu-latest
      container:
        image: ghcr.io/acme/ci-node:20@sha256:cb1e5f...   # pinned by digest
        options: --user 1001                              # not root
      steps:

        - run: npm ci && npm test        # node/npm are ALREADY there

  WHAT THIS BUYS, MEASURED (a 24-job pipeline)
    per-job toolchain install before ....... 68 s  (setup-node, apt, pip)
    per-job toolchain install after ........  0 s
    saved across the pipeline .............. 27 minutes of runner time
    AND: the toolchain is identical on a laptop:
         docker run --rm -it ghcr.io/acme/ci-node:20 bash

  THE TWO GOTCHAS
    1. UID mismatch: files created inside the container are owned by its
       user; later steps on the host cannot write them.
       -> run as the runner's UID, or chown the workspace explicitly.
    2. The image must contain git, or checkout behaves oddly (it falls
       back to the REST API and you lose history — which breaks
       `git describe`, diff-scoped linting and test-impact selection).
🔑 A CI toolchain image is the most portable reuse primitive you have. It is the one piece of your pipeline that works identically in GitHub Actions, GitLab, Jenkins, Buildkite and on a laptop — which is why pipelines as code lists it alongside reusable workflows. Build it in a repository, version it, scan it, and pin consumers to a digest.

Part 2 — The Cold Cache Problem

On a developer's machine, the second docker build is fast because the layer cache is local. On CI, every job starts on a fresh machine with no layers at all — so the naive pipeline pays a full build every single time.

MEASURED: THE SAME DOCKERFILE, FOUR CACHE STRATEGIES

  strategy                                       cold     warm    notes
  ---------------------------------------------------------------------
  no cache (default on ephemeral runners)       8m52s    8m52s   every run
  --cache-from a registry tag                   9m10s    2m14s   pull cost
  registry cache, mode=max                      9m20s      47s   best
  GHA cache backend (type=gha)                  9m05s    1m02s   10 GB cap,
                                                                 evicts
  self-hosted runner with a persistent daemon   8m52s      31s   fastest,
                                                                 and the
                                                                 riskiest
                                                                 (Part 6)

  THE CONFIGURATION THAT PRODUCED THE 47s

  - uses: docker/setup-buildx-action@v3
  - uses: docker/build-push-action@v6
    with:
      push: true
      tags: registry/app:${{ github.sha }}
      cache-from: type=registry,ref=registry/app:buildcache
      cache-to:   type=registry,ref=registry/app:buildcache,mode=max
      # mode=max caches INTERMEDIATE stages too — essential for
      # multi-stage builds, where mode=min caches only the final stage

2.1 Instruction order decides everything

  ❌ CACHE-DESTROYING ORDER
     FROM node:20-slim
     WORKDIR /app
     COPY . .                    <-- ANY source change invalidates here
     RUN npm ci                  <-- so dependencies reinstall EVERY build
     RUN npm run build

     measured: 8m52s on every commit, because npm ci was never cached

  ✅ DEPENDENCIES BEFORE SOURCE
     FROM node:20-slim@sha256:cb1e5f...
     WORKDIR /app
     COPY package.json package-lock.json ./     # changes rarely
     RUN npm ci --ignore-scripts                # cached until the lock moves
     COPY . .                                   # changes constantly
     RUN npm run build

     measured: 47s when only source changed; 3m10s when the lockfile moved

  THE RULE: order layers from LEAST to MOST frequently changing.
  Everything below the first invalidated layer is rebuilt.

2.2 Cache mounts for package managers

  # syntax=docker/dockerfile:1.7
  FROM python:3.12-slim
  WORKDIR /app
  COPY requirements.txt .
  RUN --mount=type=cache,target=/root/.cache/pip \
      pip install -r requirements.txt

  # and the same idea for other ecosystems:
  RUN --mount=type=cache,target=/root/.npm        npm ci
  RUN --mount=type=cache,target=/go/pkg/mod       go build ./...
  RUN --mount=type=cache,target=/root/.gradle     ./gradlew build
  RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
      --mount=type=cache,target=/var/lib/apt,sharing=locked \
      apt-get update && apt-get install -y --no-install-recommends curl

  THE DIFFERENCE FROM LAYER CACHING:
    a layer cache reuses a WHOLE step's result, and is invalidated by any
    change to its inputs. A cache MOUNT persists a directory ACROSS
    builds even when the step re-runs — so a one-package change to
    requirements.txt re-runs pip, but pip downloads only that package.

  MEASURED on a 180-dependency Python service:
    lockfile changed, no cache mount .... 3m41s   (re-downloads everything)
    lockfile changed, with cache mount .. 0m22s   (downloads the delta)

  NOTE: cache mounts need a persistent BuildKit state. On ephemeral
  runners, pair them with cache-to/cache-from, or run a remote builder.
⚠️ The cache must never be load-bearing. Everything in lesson 3 applies here: a build that only succeeds because a previous build populated a cache is an artifact wearing a disguise. Prove it by running a weekly build with --no-cache and no cache-from; it must still be green, only slower.

  FROM deps AS build
  COPY . .
  RUN npm run build

  FROM deps AS test                      # a TARGET the test job can build
  COPY . .
  CMD ["npm", "test"]

  FROM gcr.io/distroless/nodejs20-debian12 AS runtime
  WORKDIR /app
  COPY --from=build /app/dist ./dist
  COPY --from=build /app/node_modules ./node_modules
  USER 10001
  CMD ["dist/server.js"]

  # CI can then build exactly the stage it needs:
  docker buildx build --target test  -t app:test .     # for the test job
  docker buildx build --target runtime --push ...      # the artifact

Part 4 — Multi-Architecture Builds

Once anyone runs arm64 — Apple Silicon laptops, Graviton instances — one image is not enough. There are two ways to produce both, and one of them is a trap.

MEASURED: THE SAME IMAGE, TWO STRATEGIES

  A) QEMU EMULATION on one amd64 runner
     - uses: docker/setup-qemu-action@v3
     - uses: docker/build-push-action@v6
       with: { platforms: linux/amd64,linux/arm64, push: true }

     amd64 portion .......  4m10s
     arm64 portion ....... 58m20s      <-- 14x slower, emulated
     total ............... 62m30s

  B) NATIVE RUNNERS + MANIFEST MERGE
     build:
       strategy:
         matrix:
           include:
             - { platform: linux/amd64, runner: ubuntu-latest }
             - { platform: linux/arm64, runner: ubuntu-24.04-arm }
       steps:
         - uses: docker/build-push-action@v6
           with:
             platforms: ${{ matrix.platform }}
             outputs: type=image,name=registry/app,push-by-digest=true
     merge:
       needs: [build]
       steps:
         - run: |
             docker buildx imagetools create \
               -t registry/app:${{ github.sha }} \
               registry/app@${AMD64_DIGEST} registry/app@${ARM64_DIGEST}

     amd64 .......  4m10s  ┐ in parallel
     arm64 .......  4m40s  ┘
     merge .......    12s
     total .......  4m52s          12.8x faster than emulation
Use QEMU when…Use native runners when…
The build is tiny (a static binary copy, a config-only image)The build compiles anything
You build rarely — a monthly release imageIt is on the critical path of every merge
Native runners for that architecture are unavailableYour provider offers them (most now do)
You are cross-compiling in the build stage anywayNative toolchains are simpler than cross-compilation
💡 Cross-compilation often beats both. For Go, Rust and similar toolchains, build once on amd64 with GOARCH=arm64 and copy the binary into a per-platform runtime stage — no emulation, no second runner, and BuildKit's --platform=$BUILDPLATFORM plus TARGETARCH make it a five-line Dockerfile change. Measured on one Go service: 62m30s emulated → 5m10s native runners → 2m20s cross-compiled.

SERVICE CONTAINER — DECLARE THE HEALTH CHECK, NEVER sleep

  jobs:
    test:
      services:
        postgres:
          image: postgres:16
          env: { POSTGRES_PASSWORD: test }
          ports: ['5432:5432']
          options: >-
            --health-cmd "pg_isready -U postgres"
            --health-interval 5s
            --health-timeout 3s
            --health-retries 12

        - run: ./ci/test.sh        # the platform will not start this

  WITHOUT the health check, the classic race from
  flaky tests: "connection refused" on

  # runs identically on a laptop; each xdist worker gets its own instance

Part 6 — Security: The Shared Daemon Is the Whole Problem

Building images in CI requires a container runtime, and the obvious ways to get one hand every job the keys to every other job.

WHAT MOUNTING THE HOST DOCKER SOCKET ACTUALLY GRANTS

  volumes:
    - /var/run/docker.sock:/var/run/docker.sock     # "just to build images"

  a job with that socket can:
    $ docker ps                       # see every other job's containers
    $ docker exec -it <other-job> sh  # get a shell inside them
    $ cat ~/.docker/config.json       # read the daemon's registry creds
    $ docker run -v /:/host -it alpine chroot /host   # ROOT ON THE HOST

  on a self-hosted runner shared between repositories, that is a
  cross-repository compromise from any PR that can run a workflow.

Rootless BuildKit / buildkitdGoodGoodThe sensible default for self-hosted

THE REST OF THE CHECKLIST, IN THE ORDER THAT MATTERS

  1. NEVER pass registry credentials as build args or ENV — they persist
     in image layers and history forever:
       ❌ RUN --build-arg NPM_TOKEN=...        (visible in `docker history`)
       ✅ RUN --mount=type=secret,id=npmrc \
              npm ci                            (leaves no layer)

  2. Pin base images by DIGEST, and update them deliberately with a bot.
     A floating tag means someone else can change what you build.

  3. Scan the image you will actually ship — the final digest, not the
     source tree — and fail only on NEW, fixable findings
     (see quality gates).

  4. Emit SBOM + provenance at build time
     (builds & artifacts).

  5. Run as a non-root user in the final stage, by DEFAULT in your base
     images rather than by a blocking check.

  6. Give the build job the narrowest registry credentials that work:
     push to one repository, no delete, short-lived via OIDC
     (pipeline identity).
⚠️ Fork pull requests must never reach a builder with push credentials. A contributor's PR can change the Dockerfile and the workflow in the same commit. Build fork PRs with no registry credentials and no secrets, publishing nothing — and run the credentialed build only after merge, or from a separate workflow that uses the base branch's configuration.

❌ A Dockerfile that copies the whole tree before installing dependencies, no .dockerignore, no cache configuration on ephemeral runners, QEMU multi-arch builds, a sleep 15 waiting for Postgres, the host Docker socket mounted into every job, and an NPM_TOKEN passed as a build arg. Every build reinstalls every dependency because COPY . . sits above npm ci, so 8m52s is paid on every commit and the layer cache never helps. 1.9 GB of context — including .git, node_modules and a .env file — is transferred to the builder each time, adding 37 seconds and putting secrets one over-broad COPY away from the image. The arm64 image is emulated, so releases take an hour. The database race fails one run in four and is blamed on infrastructure. And any job on the shared runner can read the daemon's registry credentials, shell into another repository's build, or chroot the host — while the npm token sits permanently in an image layer that has been pushed to a registry.

✅ Layers ordered least-to-most volatile, a registry cache, native multi-arch runners, health checks instead of sleeps, rootless builders, and secrets that leave no layer. Put the lockfile copy and dependency install above COPY . ., add --mount=type=cache for the package manager, and configure cache-to/cache-from with mode=max so intermediate stages survive between ephemeral runners — measured 8m52s → 47s, and a lockfile change 3m41s → 22s. Write a .dockerignore before anything else: 1.91 GB of context became 8.4 MB and 37 seconds became one. Build the two architectures on native runners in parallel and merge the manifest (62m30s → 4m52s), or cross-compile and skip both. Declare a health check on the service container, or use Testcontainers so the same dependency starts identically on a laptop and each parallel worker gets its own. Then close the security holes that container CI opens by default: no host socket, rootless BuildKit or a daemonless builder, base images pinned by digest, secrets via --mount=type=secret, scanning the final digest for new fixable findings, and no credentials at all in fork-PR builds.

Interview Questions

Beginner: Why is a Docker build slow in CI when it is fast on my laptop?

Because your laptop has a warm layer cache and the CI runner does not. Ephemeral runners are fresh machines: no images, no layers, no package-manager cache. Every build is a cold build unless you arrange otherwise.

Three things fix most of it:

  • An external layer cache — cache-from/cache-to pointing at a registry, with mode=max so intermediate stages of a multi-stage build are cached too. Measured: 8m52s → 47s.
  • Instruction order — copy the lockfile and install dependencies before copying the source. With COPY . . above npm ci, every source change reinstalls every dependency, and no cache can help.
  • A .dockerignore — sending 1.9 GB of context (including .git and node_modules) costs about 37 seconds before the build even starts.

The one caveat worth adding: the cache must be an optimisation, never a requirement. A build that fails with an empty cache is a build whose result depends on history — run a weekly --no-cache build to prove it does not.

Beginner: What is the difference between running a job inside a container and building a container image in a job?

They share a word and nothing else.

Running the job inside a container decides what tools the job has. You specify an image (container: ghcr.io/acme/ci-node:20) and your steps run inside it, with the toolchain already installed. The benefits are reproducibility and speed — one measured pipeline saved 27 minutes of runner time by removing per-job toolchain installs — and the same image runs on a laptop, which is the best debugging property you can have.

Building an image produces the deployable artifact. That requires a container runtime inside CI, which is where the interesting problems live: cold caches, multi-architecture builds, and the security question of how the builder is isolated.

The failure signatures are different too, which is a useful diagnostic: "command not found" or a permission error on the workspace means the environment container is wrong (often a UID mismatch, or an image without git); "cannot connect to the Docker daemon" means the builder is missing.

Mid: Your multi-arch build takes an hour. How do you fix it?

An hour is the signature of QEMU emulation. In one measurement the amd64 half took 4m10s and the emulated arm64 half took 58m20s — a 14× penalty, because every instruction of the build is being translated.

Option 1 — native runners plus a manifest merge (the general answer): a matrix job builds each platform on a runner of that architecture, pushing by digest and publishing nothing on its own; a final job runs docker buildx imagetools create to combine the digests into one multi-arch tag. Measured: 62m30s → 4m52s, because the two builds run in parallel and neither is emulated.

Option 2 — cross-compile (better still, where the toolchain allows): build on amd64 with GOARCH=arm64 (or the Rust/Zig equivalent) and copy the binary into a per-platform runtime stage. BuildKit's --platform=$BUILDPLATFORM and TARGETARCH make this a few lines. Measured on a Go service: 2m20s — faster than either native build, because you only compile once.

When emulation is still fine: a tiny image that only copies files, or a release image built monthly. The rule is that emulation is acceptable when the build does no compilation or is off the critical path — never for something that runs on every merge.

Mid: When would you use Testcontainers instead of the CI platform's service containers?

Service containers are declared in the pipeline YAML and live for the job; Testcontainers are declared in the test code and live as long as the code says. The trade is mostly about where the dependency is defined.

Choose service containers whenChoose Testcontainers when
One shared dependency, and the suite is not parallelisedEach parallel worker needs its own instance
You want the absolute fastest start (one container per job)You want the tests to run identically on a laptop
The job cannot have a Docker socketSeveral dependencies with ordering and wait conditions
The dependency is trivial (a Redis with no data)You need programmatic control: seed data, network config, restart mid-test

The measured trade-off on a 198-test integration suite: a shared service container with four workers ran in 241 s but produced 9% flaky failures from shared-state races; Testcontainers per worker ran in 268 s with zero flaky failures. The extra 27 seconds bought a suite that can be parallelised at all — which is why I would usually reach for Testcontainers when the suite is big enough to shard.

Whichever you choose, the same rule applies: declare a real readiness condition — a health check in YAML or a wait strategy in code — never a sleep. That race is the most common "infrastructure flake" there is.

Senior: A team mounts the host Docker socket into their CI jobs to build images. What are the risks and what do you propose?

Mounting /var/run/docker.sock grants the job full control of the host's Docker daemon, which is equivalent to root on the runner. Concretely, a job with that socket can list and exec into other jobs' containers, read the daemon's registry credentials, and mount the host filesystem into a new container and chroot into it.

On a self-hosted runner shared between repositories, that is a cross-repository compromise reachable from any workflow — including, if fork PRs are built there, from an external contributor.

AlternativeIsolationTrade
Ephemeral VM-per-job hosted runnersStrongCold caches — fix with a registry cache
Rootless BuildKitGoodSlight setup cost; the sensible self-hosted default
Kaniko / Buildah (daemonless)GoodSlower; natural fit for Kubernetes runners

What I would do: move image builds to rootless BuildKit or a daemonless builder, make runners ephemeral so no state survives a job, scope registry credentials to a single repository with no delete permission and issue them via OIDC rather than storing long-lived tokens, and ensure fork PRs build with no credentials and publish nothing. And I would check docker history on current images for secrets passed as build args, because that is nearly always present alongside this pattern — anything found there must be rotated, not just removed.

Senior: How would you make container builds fast across 60 repositories without giving each team a caching project?

Centralise the mechanism, not the Dockerfiles — the teams should get the speed by default, without becoming build engineers.

LayerWhat the platform providesEffect
A shared reusable workflow for "build and publish an image"Cache configuration, provenance/SBOM, scanning, digest outputs, multi-arch matrixOne change improves 60 pipelines; see pipelines as code
Curated base imagesPinned, non-root, slim, pre-scanned, with common toolchainsDeletes whole categories of finding, and warms the pull cache
A registry cache conventionref=<repo>:buildcache, mode=max, with retentionConsistent warm caches without per-team decisions
A pull-through cache / registry mirrorBase-image pulls served locallyRemoves the cold-pull tax and the upstream rate limit
Native arm64 runner poolA matrix label teams opt intoNobody rediscovers the QEMU penalty individually
A Dockerfile linter in the shared workflowWarns on COPY . . above installs, floating tags, root users, secrets in ARGsFixes the top causes at review time rather than after a slow build

How I would sequence it: measure first — pull the p50 build duration and context size per repository, which ranks the estate in an afternoon. Fix the shared workflow so the top five repositories get the cache and the linter, publish the before/after, and let adoption follow the evidence. Most of the total saving usually comes from three changes applied broadly: .dockerignore, dependency-layer ordering, and a registry cache — none of which needs a per-team project once the workflow does it for them.

The thing I would explicitly avoid: a mandated central build service that every team must migrate to. It becomes a queue, it breaks the "runs on a laptop" property, and it converts a caching problem into an organisational one.

  jobs:
    build:

    merge:
      needs: [build]

AUDIT 3 — WHAT CAN A FORK PR DO?

  build.yml:3:  pull_request_target:            <-- runs with WRITE token
  build.yml:28:   password: ${{ secrets.REGISTRY_TOKEN }}

  workflow runs with the base branch's config AND real secrets. A build

  THE SAFE SHAPE:

    jobs:
      build:

        steps:
          - uses: docker/build-push-action@v6

              push: false                  # build only; publish nothing
              outputs: type=cacheonly

    # workflow triggered after review.

⚠️ Rotate before you remediate. The instinct on finding a token in a layer is to fix the Dockerfile and move on, but the secret has been distributed to every machine that pulled the image and every registry that mirrored it. Rotation is the fix; the Dockerfile change only stops it happening again.

🎯 Key Takeaways

  • Two different problems share the word "Docker": running the job inside a container (what tools it has) and building an image (what artifact it produces). The failure signatures differ — "command not found" versus "cannot connect to the Docker daemon".
  • A pinned CI toolchain image removed 68 s of setup from every job — 27 minutes of runner time across one pipeline — and runs identically on a laptop.
  • Two gotchas with job containers: UID mismatch on the workspace, and an image without git, which silently breaks git describe, diff-scoped linting and test-impact selection.
  • Ephemeral runners start with a cold layer cache every time. A registry cache with mode=max took a build from 8m52s to 47s; mode=min misses the expensive intermediate stages.
  • Order layers least-to-most volatile. With COPY . . above npm ci, every source change reinstalls every dependency and no cache can help.
  • Cache mounts are not layer caches: --mount=type=cache persists a package-manager directory across builds, so a one-package lockfile change downloads only the delta — 3m41s → 22s.
  • Prove the cache is not load-bearing with a weekly --no-cache --pull build; one real failure exposed a generated file that had survived only in a cache layer for nine weeks.
  • Track the cold-build time as a budget — it is your real recovery time when the cache backend is unavailable, and warm numbers hide its growth (8m20s → 14m40s unnoticed).
  • Write the .dockerignore first: 1.91 GB of context became 8.4 MB, 37 s became 1 s, and .env/.git stopped being one broad COPY away from the image.
  • Multi-stage builds took an image from 1.41 GB to 96 MB, cold-node pull from 41 s to 4 s, and HIGH CVE findings from 37 to 4 — most were in packages never used at runtime.
  • A dedicated test stage lets CI run the suite in the same image the build produced, and lets an engineer reproduce a CI failure locally with one command.
  • QEMU emulation measured 14× slower (58m20s vs 4m10s). Use native runners with push-by-digest plus imagetools create (62m30s → 4m52s), or cross-compile (2m20s).
  • If matrix jobs push the same tag instead of pushing by digest, they overwrite each other and you ship a single-architecture image under a multi-arch name.
  • Never sleep for a service container — declare --health-cmd, which removed a 25% failure rate and made every run 15 s faster.
  • Service containers cannot isolate parallel workers; Testcontainers per worker cost 27 s of startup and turned a 9%-flaky parallel suite into a green one that also runs on a laptop.
  • Template databases (CREATE DATABASE … TEMPLATE) cut per-worker setup to ~200 ms, making the isolated version faster than the shared racy one.
  • Mounting the host Docker socket is root on the runner: any job can list and exec into other jobs' containers, read registry credentials, and chroot the host. Use rootless BuildKit, a daemonless builder, or ephemeral VM runners.
  • Secrets passed as build args live in layers forever — found in 38 published images in one audit. Use --mount=type=secret, and rotate before remediating.
  • Fork PRs must build with no credentials and publish nothing: a contributor can change the Dockerfile and the workflow in the same commit, and pull_request_target hands that build real secrets.
  • Scan and SBOM the final digest, not the source tree — base-image packages and post-install additions are invisible to a source scan.
