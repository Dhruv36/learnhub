Progressive Delivery & Feature Flags Deployment

What you'll master: the separation that makes everything else in this track possible — deploying code and releasing a feature become two independent decisions, which is what lets a half-finished feature merge to trunk daily and what turns a rollback into a flag flip that takes 200 milliseconds instead of a deploy; the four kinds of flag, which have different lifetimes, owners and cleanup rules, and what happens when they are treated as one kind; flag mechanics that decide whether your system stays up — local evaluation with a cached ruleset, because a flag service on the request path took an outage from "one vendor is down" to "our checkout is down for 41 minutes"; consistent bucketing, since a user who flickers between variants on every request sees a broken product and pollutes every experiment; ramping with guardrail metrics and automatic rollback, and when a flag ramp is the right tool versus a canary; flag debt, measured at 312 flags of which 71% were permanently on and 4 caused incidents, and the expiry policy that keeps it bounded; and the experiment discipline — sample size, guardrails and the peeking problem — that separates a real A/B test from a decision someone made on day two. Prerequisites: Deployment Strategies and Database Migrations.

Part 3 — Mechanics That Decide Whether You Stay Up

3.1 Evaluate locally; never put the flag service on the request path

THE INCIDENT

  09:14  the flag vendor's API begins timing out
  09:14  every request calls flags.is_enabled("new_checkout") synchronously
  09:14  each call blocks for the 3 s client timeout
  09:15  the connection pool exhausts; p99 goes 210 ms -> 3,200 ms
  09:16  checkout is effectively down
  09:55  vendor recovers. TOTAL: 41 minutes of self-inflicted outage,
         caused by a dependency that was supposed to REDUCE risk.

THE CORRECT ARCHITECTURE

  ┌── flag service ──┐   streaming/polling    ┌── your process ──┐
  │ rules, targeting │ ────────────────────▶  │ in-memory ruleset│
  └──────────────────┘   every 30-60 s        │ evaluate locally │
                                              │   (microseconds) │
                                              └──────────────────┘
   - evaluation NEVER makes a network call
   - the ruleset is cached on disk, so a cold start with the service
     down still gets the last known rules
   - if there is no ruleset at all, the code uses a HARDCODED DEFAULT
   - the flag SDK must fail open to that default, never throw

  def is_enabled(flag: str, ctx: Context, default: bool = False) -> bool:
      try:
          rules = RULESET.get(flag)          # in-memory, no I/O
          return evaluate(rules, ctx) if rules else default
      except Exception:
          log.warning("flag evaluation failed: %s", flag)
          return default                      # NEVER raise from a flag check

3.2 Consistent bucketing

  ❌ random.random() < 0.05
     a user gets the new checkout on one request and the old one on the
     next. Their cart is empty, their session breaks, and the experiment
     data is meaningless.

  ✅ DETERMINISTIC HASH OF A STABLE KEY
     bucket = crc32(f"{flag_key}:{user_id}") % 10000       # 0..9999
     enabled = bucket < rollout_percent * 100

     properties this gives you:
       - the same user always gets the same variant (until you change
         the percentage or the salt)
       - INCLUDING the flag key in the hash means a user who is in the
         first 5% for flag A is not automatically in the first 5% for
         flag B — otherwise the same unlucky cohort receives every
         experiment, which quietly biases all of them
       - ramping 5% -> 10% only ADDS users; nobody loses the feature

  CHOOSING THE KEY
     user_id       best for user-facing features
     account_id    when a whole team must see the same thing
     session_id    for anonymous traffic — but the user changes cohort
                   on a new session, so never for anything stateful
     request       only for stateless, idempotent behaviour (a new
                   algorithm producing identical output shapes)

3.3 Testing with flags without a combinatorial explosion

  n flags -> 2^n combinations. With 312 flags that is not a test plan.

  THE RULE THAT WORKS:
    - test the CURRENT default state of every flag (that is production)
    - test BOTH states of the flag(s) this change touches
    - test the specific combinations you know interact, and write down
      why they interact
    - never try to cover the matrix

  # pytest example
  @pytest.mark.parametrize("new_checkout", [False, True])
  def test_checkout_flow(new_checkout, flags):
      flags.override("new_checkout", new_checkout)     # this PR's flag
      ...                                               # everything else
                                                        # at its default

  AND IN CI: a job that asserts every flag referenced in code exists in
  the flag service, and every flag in the service is referenced in code.
  Drift between the two is how a typo'd key silently returns the default
  forever.

Part 4 — Ramping With Guardrails

A RAMP IS A CANARY WHOSE ROUTING IS IN YOUR CODE

  stage   exposure   duration   gates
  -------------------------------------------------------------------
  0       internal   1 day      staff accounts only; qualitative
  1       1%         2 hours    error rate, latency p50, new exceptions
  2       5%         4 hours    + conversion, support-ticket rate
  3       25%        1 day      + revenue per session, p99
  4       50%        1 day      + infrastructure cost per request
  5       100%       —          bake, then REMOVE THE FLAG

  GUARDRAIL METRICS ARE DIFFERENT FROM SUCCESS METRICS
    success:   "checkout conversion goes up"       (why you built it)
    guardrail: "error rate does not rise, p99 does not rise, support
                tickets do not rise, cost per request does not rise"
                (what must not break while you find out)
  a ramp stops on GUARDRAILS automatically; success metrics are read by
  humans at the end.
Deployment canaryFlag ramp
Unit of exposureRequests hitting new instancesUsers, accounts, regions — anything you can key on
GranularityWhatever the router supportsArbitrary targeting rules
RollbackShift weight, secondsFlip the flag, milliseconds

  AUTOMATED GUARDRAIL ENFORCEMENT

  # ci/ramp-watch.sh — runs continuously while a flag is ramping
  while true; do
    E_ON=$(promql "error_rate{flag_variant='on'}")
    E_OFF=$(promql "error_rate{flag_variant='off'}")
    L_ON=$(promql "latency_p50{flag_variant='on'}")
    L_OFF=$(promql "latency_p50{flag_variant='off'}")
    NEW_EX=$(promql "count(new_exception_signatures{flag_variant='on'})")

    if over(E_ON, E_OFF, 1.2) || over(L_ON, L_OFF, 1.15) || [ "$NEW_EX" -gt 0 ]; then
      flagctl set new_checkout --percent 0 --reason "guardrail breach"
      notify "#eng-alerts" "new_checkout rolled back automatically"
      exit 1
    fi
    sleep 60
  done

  THE CRITICAL DETAIL: emit an EXPOSURE EVENT whenever a flag decides,
  so every metric can be split by variant:
      metrics.increment("flag_exposure",
                        tags=[f"flag:{key}", f"variant:{on}"])
  without exposure logging you cannot compare on-vs-off at all, and the
  ramp is just a slow rollout with no information.

Part 5 — Flag Debt

WHAT STALE FLAGS COST — THE FOUR INCIDENTS FROM THAT ESTATE

  1. A release toggle at 100% for 14 months. Someone "cleaned up" the
     ON branch, assuming the flag was off. 100% of users hit the removed
     path. 22 minutes to restore.

  2. Two flags nobody knew interacted: `bulk_import_v2` ON and
     `strict_validation` ON together produced duplicate orders. Neither
     had been tested with the other, because there were 312 flags.

  3. A flag service outage revealed that 9 flags had DEFAULTS that did
     not match their production values — so "fail to default" meant
     "silently change behaviour for everyone".  ← test this deliberately

  4. A kill switch that had never been exercised did not work when it
     was needed; the code path it disabled had moved.

  THE COST WHEN NOTHING BREAKS, WHICH IS MOST OF THE TIME:
    - every stale flag is a branch a reader must reason about
    - test surface multiplies
    - a new engineer cannot tell which branches are live
PolicyMechanism
Declare the kind and an expiry at creationThe SDK call or a registry file requires kind, owner, expires
Release toggles expire in 60 daysA CI check fails the build when an expired release toggle is still referenced
Automated cleanup PRsA bot removes the branch and the flag call when a toggle has been at 100% for 30 days
Ops toggles are exempt but must be testedA quarterly game day exercises every kill switch; untested ones are reported
Reconcile code and serviceA CI job diffs flags-in-code against flags-in-service, both directions
Defaults must match productionA job compares each flag's hardcoded default with its live value and warns on mismatch
⚠️ The hardcoded default is what runs during a flag-service outage — so it must match reality. A flag that has been at 100% for a year with a hardcoded default of false means the vendor's next outage silently disables a feature everyone depends on. Audit defaults against live values continuously; it is a five-line job and it converts an invisible landmine into a warning.

Part 6 — Experiments Are a Different Discipline

AN A/B TEST IS A STATISTICAL CLAIM, NOT A FLAG AT 50%

  what you must fix BEFORE starting:
    - the metric ......... "checkout conversion", defined precisely
    - the effect size .... the smallest change worth acting on (say +2%)
    - the sample size .... computed from baseline, effect and power
    - the duration ....... at least one full weekly cycle, whatever the
                           sample size says
    - the guardrails ..... what must not get worse
    - the decision rule .. what you will do for each outcome

$ python - <<'PY'
from math import sqrt
p, mde, za, zb = 0.032, 0.02, 1.96, 0.84       # 3.2% baseline, +2% rel
p1 = p * (1 + mde)
n = ((za*sqrt(2*p*(1-p)) + zb*sqrt(p*(1-p)+p1*(1-p1)))**2) / (p1-p)**2
print(f"{n:,.0f} sessions per arm")
print(f"at 40,000 sessions/day, 50/50 split: {2*n/40000:.1f} days")

  -> so this experiment needs SIX DAYS. Reading it on day two is not

Interview Questions

Beginner: What is the difference between deploying and releasing, and why does it matter?

Deploying puts code on servers. Releasing makes a behaviour visible to users. A feature flag separates them: the code ships dark, and someone turns it on later.

Why it matters, in order of impact:

  • Trunk-based development becomes possible. Incomplete work can merge daily behind an off flag, so branch age stays short — the number that predicts conflicts, review quality and revert rate.
  • Rollback stops being a deploy. Turning a flag off is milliseconds; a drilled rollback is around 74 seconds and an undrilled one measured 7+ minutes.
  • Exposure becomes gradual and targeted — 1% of users, one region, internal staff first.
  • Release timing becomes a product decision rather than an engineering event at 09:00.

The cost is real and worth stating: every flag is a branch in the code, and flags accumulate. That is why the discipline around lifetime and cleanup — not the flag mechanism itself — is the hard part.

Beginner: What happens to your application if the feature-flag service goes down?

It should be a non-event, and it is only a non-event if you designed for it.

The failure mode to avoid: evaluating flags by calling the service on the request path. In one measured incident the vendor's API began timing out, every request blocked for the three-second client timeout, the connection pool exhausted, and checkout was down for 41 minutes — an outage caused entirely by the risk-reduction tool.

The correct design:

  • The SDK streams or polls the ruleset into memory; evaluation is a pure in-memory function taking microseconds and making no network call.
  • The ruleset is cached on disk, so a process starting while the service is down still gets the last known rules.
  • If there is no ruleset at all, evaluation returns a hardcoded default supplied at the call site.
  • Flag evaluation never throws — any error returns the default and logs once.

And the subtlety that catches people: those hardcoded defaults must match production reality. A flag that has been at 100% for a year with a default of false means the next outage silently turns the feature off for everyone. A CI job comparing defaults with live values catches it.

Mid: How do you roll out a risky feature to 1% of users and know whether it is safe?

Four things, and the last is the one usually missing.

  1. Deterministic bucketing. Hash the flag key together with a stable subject id (crc32("new_checkout:user_42") % 10000) so a user always gets the same variant, ramping only adds users, and different flags select different cohorts.
  2. Exposure logging. Emit an event every time the flag decides, tagged with the variant. Without it you cannot split any metric by on-versus-off, and the rollout carries no information at all.
  3. Guardrail metrics compared against the off variant — error rate, p50 latency, new exception signatures, and something business-shaped like conversion. Compare concurrent variants, never today against last week.
  4. Automatic rollback. A watcher that sets the flag to 0% on a guardrail breach and announces it. Manual watching means detection is however long until someone looks — measured at 11 minutes in hours and 40+ outside them.

Then ramp in stages with a bake at each — internal, 1%, 5%, 25%, 50%, 100% — and remember that 1% may be statistically incapable of detecting a small regression: the sample-size arithmetic from deployment strategies applies identically here. Early stages catch catastrophes and new exceptions; the later stages are where subtle regressions become visible.

Mid: Your codebase has 312 feature flags. What do you do?

Classify first, then automate the cleanup of exactly one category — because deleting flags blindly is how you remove entitlement logic or an untested kill switch.

And the safety rule for the cleanup itself: check the live rollout percentage before deleting a branch. One incident came from a "cleanup" that removed the ON path of a flag which had been at 100% for fourteen months — the author assumed it was off.

Senior: When would you use a feature flag rather than a canary deployment, and when both?

They solve overlapping problems at different granularities, and the choice follows from what you want to be able to turn off.

Canary deploymentFeature flag
Turns offThe whole releaseOne behaviour
Exposure unitRequests to new instancesUsers, accounts, regions, plans
RollbackShift weight — secondsFlip — milliseconds
DurationMinutes; you want the deploy finishedHours to weeks; it is a product decision
Best forInfrastructure, library upgrades, cross-cutting changes with no user-visible switchUser-visible features, anything you might want to keep off for some cohort

Use both, in this order: canary the deployment so infrastructure-level regressions are caught before all instances run the new build, then ramp the feature flag independently once the release is fully deployed. That gives you two separable controls — "is this build healthy?" and "is this feature good?" — and it means the answer to a problem is rarely "roll back the whole release".

The case for flags alone: when the change is a behaviour with a clear on/off, and especially when the rollout should be by user or account rather than by request — a canary cannot express "all users on the enterprise plan in the EU".

The case for canary alone: when there is no user-visible switch to flip — a runtime upgrade, a connection-pool change, a serialisation library swap. Wrapping those in flags creates branches that are hard to remove and hard to reason about.

Senior: How do you run an A/B test properly, and what usually goes wrong?

An experiment is a statistical claim, and most of the work happens before it starts.

Fix in advance: the metric with a precise definition; the minimum effect worth acting on; the sample size implied by those two plus your baseline; the duration (at least one full weekly cycle regardless of what the sample size says, because behaviour is seasonal); the guardrails that must not degrade; and the decision rule for each outcome — including "no significant difference", which is the most common result and the one nobody plans for.

Worked example: a 3.2% baseline conversion, wanting to detect a 2% relative improvement, needs about 118,000 sessions per arm — roughly six days at 40,000 sessions a day with a 50/50 split.

What usually goes wrong:

  • Peeking. Checking significance daily inflates the false-positive rate far above the nominal 5% — over a two-week test it can exceed 20%. Either fix the end date or use sequential methods designed for continuous monitoring.
  • Changing allocation mid-test, which invalidates the comparison. Ramps are for releases; experiments hold exposure fixed.
  • Shared bucketing salt, so the same cohort receives every experiment and results are correlated in ways nobody models.
  • No guardrails, so a variant that increases conversion and also increases errors or latency wins.
  • Stopping when it looks good, which is peeking with extra steps and is the single most common failure.

The governance point I would make: experiment flags need different handling from release toggles — product and data own them, exposure is fixed rather than ramped, and they end with a decision and a removal rather than with 100%.

3 (medium): Implement deterministic bucketing and prove its properties: stability, monotonic ramping, and independence between flags.
Solution 
THE IMPLEMENTATION

  import zlib

  BUCKETS = 10_000

  def bucket_of(flag_key: str, subject_id: str) -> int:
      """Stable 0..9999 bucket for (flag, subject)."""
      return zlib.crc32(f"{flag_key}:{subject_id}".encode()) % BUCKETS

  def is_enabled(flag_key: str, subject_id: str, percent: float) -> bool:
      return bucket_of(flag_key, subject_id) < percent * BUCKETS / 100

STEP 2 — THE GUARDRAIL WATCHER

  #!/usr/bin/env bash
  # ci/ramp-watch.sh FLAG [POLL_SECONDS]
  set -euo pipefail
  FLAG="${1:?flag key}"; POLL="${2:-60}"
  q() { promtool query instant "$PROM" "$1" | awk '{print $NF}'; }

  breach() {
    echo "::error::guardrail breach: $1"
    flagctl set "$FLAG" --percent 0 --reason "auto-rollback: $1"
    ./ci/notify.sh '#eng-alerts' \
      "🔻 $FLAG rolled back to 0% automatically — $1"
    exit 1
  }

  while true; do
    L="flag_${FLAG}"
    E_ON=$(q "sum(rate(http_requests_total{${L}='on',status=~'5..'}[5m]))
              / sum(rate(http_requests_total{${L}='on'}[5m]))")
    E_OFF=$(q "sum(rate(http_requests_total{${L}='off',status=~'5..'}[5m]))
               / sum(rate(http_requests_total{${L}='off'}[5m]))")
    P50_ON=$(q "histogram_quantile(0.5, sum by (le) (rate(
                http_request_duration_seconds_bucket{${L}='on'}[5m])))")
    P50_OFF=$(q "histogram_quantile(0.5, sum by (le) (rate(
                 http_request_duration_seconds_bucket{${L}='off'}[5m])))")
    NEW_EX=$(q "count(count by (exception) (app_exceptions_total{${L}='on'})
                unless count by (exception) (app_exceptions_total{${L}='off'}))")
    EXPOSED=$(q "sum(increase(flag_exposure{flag='${FLAG}',variant='on'}[5m]))")

    # only judge once there is enough traffic to judge on
    if awk "BEGIN{exit !($EXPOSED < 1000)}"; then
      echo "only $EXPOSED exposures in 5m — not enough to evaluate; waiting"
      sleep "$POLL"; continue
    fi
    awk "BEGIN{exit !($E_ON > $E_OFF * 1.2 && $E_ON > 0.001)}" \
      && breach "error rate ${E_ON} vs ${E_OFF} (off)"
    awk "BEGIN{exit !($P50_ON > $P50_OFF * 1.15)}" \
      && breach "p50 latency ${P50_ON}s vs ${P50_OFF}s (off)"
    [ "${NEW_EX:-0}" = "0" ] || breach "$NEW_EX new exception signature(s)"

    echo "$(date -Is) ok: err=${E_ON}/${E_OFF} p50=${P50_ON}/${P50_OFF} exposures=${EXPOSED}"
    sleep "$POLL"
  done

import random
from statistics import NormalDist
def run(peek_daily: bool, days=14, per_day=20_000, p=0.032, trials=2000):
    """A/A test: both arms IDENTICAL. How often do we 'find' significance?"""
    false_positives = 0
    for _ in range(trials):
        a = b = na = nb = 0
        for d in range(days):
            for _ in range(per_day):
                a += random.random() < p; na += 1
                b += random.random() < p; nb += 1
            if peek_daily or d == days-1:
                pa, pb = a/na, b/nb
                pooled = (a+b)/(na+nb)
                se = (pooled*(1-pooled)*(1/na+1/nb))**0.5
                z = abs(pa-pb)/se if se else 0
                if z > 1.96:
                    false_positives += 1
                    break
    return false_positives/trials
print(f"check ONCE at the end : false positive rate {run(False):.1%}")
print(f"check EVERY DAY       : false positive rate {run(True):.1%}")

🎯 Key Takeaways

  • Deploy and release become independent decisions. Code ships dark; a flag makes it visible — which is what allows daily merges of incomplete work and turns rollback into a 200 ms flip.
  • Flags are what make trunk-based development and expand/contract migrations practical: every risky transition becomes instantly reversible without a deploy.
  • Four kinds, four lifetimes: release toggles (days–weeks, must be removed), experiment flags (until the decision), ops toggles/kill switches (permanent, must be exercised), entitlements (permanent business logic).
  • Declare kind, owner and expiry in the commit that creates the flag — the only moment anyone knows the answers.
  • Never evaluate flags over the network on the request path. A vendor timeout took checkout down for 41 minutes; stream the ruleset into memory, cache it on disk, evaluate in microseconds.
  • Flag evaluation must never throw — catch everything and return the declared default.
  • Hardcoded defaults must match live values. Nine mismatches meant the next outage would silently disable features everyone used; a five-line CI job catches them.
  • Bucket deterministically on a stable key, and include the flag key in the hash — otherwise the same unlucky 5% receives every experiment and all results are correlated.
  • Deterministic bucketing makes ramping monotonic: 1% → 100% only ever adds users, so nobody loses a feature mid-flow.
  • Do not test the flag matrix — 2ⁿ combinations. Test the default state everywhere, both states of the flag this change touches, and the interactions you can name.
  • Exposure logging is the prerequisite for everything else: without an event at the decision point, no metric can be split by variant and the ramp yields no information.
  • Ramp against guardrails, not success metrics — error rate, p50 latency and new exception signatures versus the off variant, with a minimum exposure before judging and automatic return to 0% on breach.
  • Flag ramps and canaries are complementary: canary the build ("is this release healthy?"), ramp the flag ("is this feature good?"), so the answer to a problem is rarely "roll back everything".
  • Flag debt is measurable and large: 312 flags, 141 expired release toggles, 132 permanently on, 39 concluded experiments, and 27 of 31 kill switches never exercised.
  • Stale flags cause real incidents — a cleanup deleted the branch 100% of users were on; two untested flags interacted to produce duplicate orders.
  • Automate cleanup for release toggles only, guarded by a check that the live value really is 100% — and never let the bot touch entitlements or kill switches.
  • Exercise kill switches quarterly. In one game day, 2 of 5 were decorative: the code path had moved, or background jobs ignored read-only mode.
  • Reconcile flags-in-code with flags-in-service in both directions — a typo'd key silently returns the default forever.
  • An experiment is a statistical claim: pre-register the metric, effect size, sample size, duration, guardrails and the decision rule for every outcome. A 3.2% baseline and a +2% target needed ~118,000 sessions per arm — six days.
  • Peeking daily raised the false-positive rate from 4.9% to 22.4% on identical variants. Fix the end date or use sequential methods, and pre-register that "no difference" means revert and remove.
