Runners & Build Infrastructure Pipeline Engineering

What you'll master: when self-hosted runners are genuinely justified and when they are a cost-saving that costs more — a team that moved to save $4,100/month spent 31 engineer-days a year maintaining the pool, and the maintenance alone was $21,000; the single most important property of a runner, which is that it is ephemeral, demonstrated by the persistent pool where a build passed for six weeks only because a previous job had left a file behind; the security model that most organisations get wrong exactly once — a self-hosted runner executing a fork pull request is arbitrary code execution inside your network, with whatever that machine can reach, and the audit that found runners able to reach a production database; capacity and autoscaling, where scale-up lag turned a 12-second queue into 4m40s of waiting until a warm pool fixed it, plus the pool-sizing arithmetic that comes from Little's law rather than from guessing; the five failure modes that make runners flaky — disk exhaustion caused 61% of one quarter's infrastructure failures — and how to run the pool as a service with an SLO; and the supporting infrastructure that decides whether a fast pipeline is possible at all: pull-through caches, package proxies and egress costs. Prerequisites: Containers in CI and Pipeline Performance.

THE FIVE LEGITIMATE REASONS FOR SELF-HOSTED, IN ORDER OF HOW OFTEN
THEY ARE TRUE

  1. NETWORK ACCESS — the build must reach a private artifact repository,
     an internal package registry, a licence server, or a database in a
     VPC. No amount of tunnelling makes hosted runners a good fit.
  2. HARDWARE — GPUs, huge memory, specific CPU features, physical
     devices, macOS at volume.
  3. COMPLIANCE — data residency, or an auditor who requires that source
     never leaves your infrastructure.
  4. SCALE ECONOMICS — genuinely enormous CI volume where per-minute
     pricing dominates and you already run a platform team.
  5. WARM CACHES — the weakest reason, and usually solvable with a
     registry cache instead (see <pipeline performance>).

Part 2 — Ephemeral Is the Property That Matters

Whatever you choose, each job must start from a known state and leave nothing behind. Persistent runners break this quietly, and the resulting bugs are among the hardest in this entire track to diagnose.

WHAT A PERSISTENT RUNNER ACCUMULATES

  $ ls -la /home/runner/_work/                # eight repositories' checkouts
  $ docker images | wc -l                     # 412 images, 180 GB
  $ cat ~/.netrc ~/.docker/config.json        # credentials from other jobs
  $ ls /tmp | head                            # test fixtures, sockets, pid files
  $ env | grep -i token                       # exported by a previous step
  $ crontab -l                                # a "temporary" cleanup job
                                              # someone added in 2024

THE BUG THIS PRODUCES — SIX WEEKS OF A GREEN BUILD THAT WAS NOT

  a job in repo A ran `npm install -g @acme/cli` (a leftover debug step)
  a job in repo B invoked `acme-cli generate` in its build
  repo B's package.json did NOT declare the dependency

  on the persistent pool: green, for six weeks.
  the day repo B ran on a fresh runner: "acme-cli: command not found"
  the day repo A removed the debug step: repo B broke, and repo A got
    the blame in three separate incident channels.

  This is the <first-pipeline> isolation guarantee failing at the
  infrastructure layer instead of the test layer.

Part 3 — The Security Model

A self-hosted runner is a machine inside your network that executes code from your repositories. The question that decides your posture is: whose code?

THE SENTENCE TO INTERNALISE

  A SELF-HOSTED RUNNER THAT BUILDS FORK PULL REQUESTS IS AN
  UNAUTHENTICATED REMOTE CODE EXECUTION ENDPOINT, INSIDE YOUR NETWORK.

  a contributor opens a PR:
    -  .github/workflows/ci.yml  (their version, if the trigger allows)
    -  Makefile / package.json scripts / Dockerfile RUN lines
    -  a test file that runs on `pytest`
  any of these executes on your machine, with its network position,
  its cached credentials, and its disk.

Part 4 — Capacity and Autoscaling

POOL SIZING FROM LITTLE'S LAW, NOT FROM GUESSING

  L = λ × W        jobs in the system = arrival rate × time in system

  measured: 118 jobs/day, but arrivals are not uniform —
  peak hour (14:00-15:00) sees 31 jobs, mean duration 6.2 min

    λ_peak = 31 jobs/hour = 0.52 jobs/min
    W      = 6.2 min
    L      = 0.52 × 6.2 = 3.2 jobs running concurrently, on average

  ... but AVERAGE concurrency is not capacity. Jobs arrive in bursts
  (a merge queue batch, a nightly fan-out), so size for the p95 of
  concurrent demand:

$ ./ci/concurrent-jobs.sh --day 2026-08-20 --percentile 95
  p50 concurrent: 3   p95: 11   p99: 17   max: 20

  capacity 11 -> ~5% of jobs queue briefly
  capacity 17 -> ~1% queue
  capacity 20 -> essentially never queue, and idle most of the day
  => autoscale between 2 (warm) and 20 (burst).

SCALE-UP LAG IS THE NUMBER THAT SURPRISES PEOPLE

  MEASURED, EC2-based ephemeral runners, cold pool:
    autoscaler notices the queued job ......  30 s (polling interval)
    RunInstances -> instance running ........ 42 s
    boot + cloud-init + agent registration .. 98 s
    docker pull of the toolchain image ...... 90 s
    -------------------------------------------------
    total from queued to executing ......... 4m40s

  FIXES, IN ORDER OF EFFECT
    minRunners: 2-4 (a warm pool)          -> first jobs start in ~5 s
    bake the toolchain into the AMI/image   -> removes the 90 s pull
    pre-registered, paused runners          -> removes agent registration
    faster polling (10 s)                   -> removes 20 s
    Kubernetes pods instead of VMs          -> 4m40s becomes 8-20 s
  after: p50 queue 12 s, p95 47 s, with 2 warm runners costing $94/month

THE DISK PROBLEM IS THE WHOLE PROBLEM, AND IT IS FIXABLE

  ❌ a cron job running `docker system prune -af` every night
     - it runs at 03:00; the disk fills at 15:00
     - it deletes the layer cache everyone depends on, so the first
       builds after it are 8 minutes slower
     - it can delete an image a running job is using

  ✅ ephemeral runners: nothing accumulates, by construction
  ✅ if persistent: prune by WATERMARK, not by schedule
       docker system prune -af --filter "until=24h" \
         && [ "$(df --output=pcent / | tail -1 | tr -dc 0-9)" -lt 80 ]
     triggered when usage crosses 75%, targeting 60%
  ✅ alert on disk at 70% so the fix precedes the incident
  ✅ separate volumes: workspace, docker data, caches — so one filling
     up does not take down the others

💡 Classify infrastructure failures separately from test failures, in the data. Until you do, 186 disk-full and rate-limit incidents are indistinguishable from flaky tests, and two teams spend a quarter debugging each other's problem. Tag them by error signature at the point of failure, and report them against the pool's SLO rather than against the test suite's first-attempt pass rate (see flaky tests).

❌ A persistent self-hosted pool adopted to save $4,100 a year, building fork pull requests, with the Docker socket mounted, a nightly docker system prune -af, no disk alerting, no network segmentation, and cache storage in another region. The saving was never real: 31 engineer-days of maintenance cost $21,000 against a $600/month hosted bill. State leaks between jobs, so one repository's globally-installed CLI made another repository's build pass for six weeks and then break with no related change. Disk exhaustion causes 61% of the quarter's failures and every one is reported as a flaky test, while the nightly prune deletes the layer cache and makes the first builds of each morning eight minutes slower. Any workflow in any repository can target the pool by label, including the pool that holds production deploy credentials, and a fork PR runs a contributor's Makefile on a machine that can open a TCP connection to the production database and read the instance's IAM role from the metadata endpoint. Meanwhile every job pays 62 seconds and $180 a month to fetch its cache across an ocean.

✅ Ephemeral runners in their own network segment, hosted runners for anything untrusted, autoscaling driven by queue depth with a small warm pool, and the pool run as a service with an SLO. Decide self-hosting on capability — private network access, hardware, compliance — and put the engineer-days in the business case, because they dominate it. Make every runner ephemeral so there is no cleanup script to forget and no credential to leave behind; one job per machine, then destroy it. Never build fork PRs on a self-hosted runner: route them to hosted runners with no secrets and nothing to publish. Put runners in their own subnet with an egress allowlist, block or hop-limit the metadata endpoint, issue short-lived credentials via OIDC, and scope high-privilege pools with platform-level runner groups rather than labels, which are not a boundary. Scale on queued-job count, keep two warm runners (measured $94/month to take job start from 4m40s to 12 s), and bake the toolchain into the image so the pull is not on the critical path. Then treat the pool as production: alert on disk at 70%, prune by watermark rather than by cron, classify infrastructure failures separately from test failures so 186 incidents stop being mistaken for flakiness, and put the cache next to the runners — a bucket in the right region removed 62 seconds from every job in the estate.

Interview Questions

Beginner: What is the difference between hosted and self-hosted runners, and when would you choose each?

Hosted runners are provided by the CI platform: a fresh virtual machine per job, discarded afterwards, billed per minute, with no maintenance. Self-hosted runners are machines you own and operate, which the CI platform dispatches jobs to.

The legitimate reasons to self-host, in the order they are actually true:

  1. Network access — the build needs a private registry, licence server or database inside your network.
  2. Hardware — GPUs, very large machines, specific CPU features, macOS at volume.
  3. Compliance — data residency or a requirement that source stays on your infrastructure.
  4. Scale economics — genuinely huge CI volume, where you already run a platform team.

The reason people usually give — cost — is usually wrong. One measured migration claimed $4,100/year of savings and consumed 31 engineer-days of maintenance in its first year, which at any realistic day rate is several times the hosted bill. If a capability reason applies, self-hosting is correct and the maintenance is the price of that capability; if none does, hosted runners plus a registry cache usually beat it on both cost and reliability.

Beginner: Why should CI runners be ephemeral?

Two reasons, one about correctness and one about security.

Correctness: a persistent runner accumulates state — installed packages, cached files, environment variables, Docker images — and jobs start depending on it without anyone deciding to. The measured example: a job in one repository globally installed a CLI as a leftover debug step; a job in a different repository used that CLI without declaring it. The second build passed for six weeks, then failed the day it landed on a fresh machine — and the failure had no relationship to any change in that repository.

Security: whatever a job leaves behind is available to the next job, including registry credentials in ~/.docker/config.json, tokens in the environment, and cloned source from a private repository. On a pool shared between repositories that is a cross-repository data leak by default.

Ephemeral means one job per machine — a fresh pod or VM — destroyed afterwards. The cost is startup time, which is why you pair it with a warm pool and a prebuilt image; the alternative, a cleanup script, is a denylist that is always missing the thing that mattered.

Mid: Your self-hosted runners have a 4-minute queue at peak. How do you diagnose and fix it?

First separate the two things a "queue" can mean: no capacity (all runners busy) or capacity exists but is slow to arrive (scale-up lag). The shape of the data tells you which.

ObservationCauseFix
Queue tracks working hours and the pool is pinned at maxInsufficient capacityRemove waste first (cancellation, path filters), then raise the ceiling
Queue spikes for ~4 minutes and clears, pool not at maxScale-up lagWarm pool, prebaked images, faster polling, pods instead of VMs
Only large jobs queueScarce big machinesRight-size — most jobs do not need them
Fixed daily spikeScheduled jobs overlapping peakMove the cron or use a separate pool

For scale-up lag specifically, the measured breakdown was: 30 s of autoscaler polling, 42 s to launch the instance, 98 s of boot and agent registration, and 90 s pulling the toolchain image — 4m40s total. Two warm runners at $94/month took the p50 to 12 seconds; baking the toolchain into the image removed the 90-second pull; moving to Kubernetes pods would have taken the whole thing to under 20 seconds.

And the sizing question underneath: size for the p95 of concurrent demand, not the mean. Averages say three concurrent jobs; the p95 says eleven and the max says twenty — so autoscale between a small warm floor and the burst ceiling.

Mid: What are the security risks of self-hosted runners?

The core risk is stated in one sentence: a self-hosted runner executes code from your repositories on a machine inside your network. Everything follows from asking whose code and what that machine can reach.

RiskMechanismControl
Untrusted code executionA fork PR can change workflows, build scripts, Dockerfiles and testsNever build fork PRs on self-hosted runners; hosted, no secrets, nothing published
Lateral movementThe runner can reach internal services — one audit found a path to the production databaseDedicated subnet, egress allowlist, no route to production data
Cloud identity theftThe instance metadata endpoint yields the runner's IAM roleBlock metadata, or IMDSv2 with hop limit 1; scope the role minimally
Cross-job credential theftPersistent runners keep ~/.docker/config.json, tokens, sourceEphemeral runners; short-lived OIDC credentials
Host takeoverMounted Docker socket or privileged containersRootless/daemonless builders
Pool targetingLabels are not a boundary — any repo can request a labelRunner groups scoped to specific repositories, at the platform level

The one I would emphasise unprompted is the last: teams separate a "prod-deploy" pool by label and believe it is isolated, when any workflow in any repository with access to the pool can request that label. Several published incidents follow this exact path — a low-value repository schedules a job onto a high-value pool and inherits its credentials and network position.

Senior: Design a runner platform for 200 engineers across 60 repositories, with some builds needing private network access.

The requirement splits the estate cleanly, and the design should follow that split rather than standardising on one answer.

TierRunsImplementation
Public / untrustedFork PRs, open-source reposHosted runners, no secrets, publish nothing, approval required before first run
StandardMost internal CIHosted runners plus a registry cache and package proxy — no maintenance, ephemeral by construction
Private-networkBuilds needing internal registries, licence servers, databasesEphemeral Kubernetes runners in a dedicated subnet, egress allowlist, no route to production data
DeployJobs holding production credentialsA separate pool in a runner group scoped to the deployment repositories only; on-demand instances, never spot

Cross-cutting decisions: every runner ephemeral, one job per pod; autoscale on queued job count with a warm floor of two to four; toolchain baked into a weekly-refreshed image pinned by digest; a pull-through registry cache and package proxy co-located with the runners; credentials issued via OIDC with short lifetimes and per-repository scoping.

Run it as a service: published SLIs — job start latency p95 under 60 s, infrastructure failure rate under 0.5%, pool availability above 99.5% in working hours — with a named owning team and an on-call rotation. At 200 engineers the pool is production: when it is slow, the entire company is slow.

What I would avoid: one big shared pool for everything (it forces the security posture of the least-trusted workload onto everyone), persistent runners for cache warmth (buy that with a remote build cache instead), and letting teams add their own runners to shared groups without review — that is how a pool with production credentials acquires an unexpected member.

Senior: Developers complain about "flaky CI". You find most failures are infrastructure. How do you handle that?

First, separate the two populations in the data, because until you do, both teams are debugging the wrong thing. Classify every failure by error signature at the point of failure — disk-full, image pull, agent lost, DNS, OOM — and report infrastructure failures against the runner pool's SLO rather than against the test suite's first-attempt pass rate.

In one measured quarter that reclassification moved 186 incidents out of "flaky tests": 61% disk exhaustion, 15% registry rate limits and auth expiry, 11% lost agents, 7% DNS/egress, 6% OOM. Not one was a test, and the test team had been spending its time on them.

Then fix them as reliability work, in order of share:

  • Disk — the dominant cause. Ephemeral runners remove it entirely; if persistent, prune by watermark rather than by cron (a nightly prune -af both deletes the cache everyone needs and still fills up by afternoon), alert at 70%, and split workspace, image and cache volumes.
  • Registry limits — a pull-through cache took these from 28 incidents to zero.
  • Lost agents — retry infrastructure errors specifically, matched by signature, not by "the job failed" (which is the retry-by-default trap from flaky tests).
  • DNS/egress and OOM — resource requests per job, and monitoring the proxy as a dependency.

And close the loop with the developers: publish the classification weekly. The complaint "CI is flaky" is a single undifferentiated signal; showing that 61% of it was disk space on the build pool converts an argument about test quality into a reliability backlog with an owner — and it restores trust in the red/green signal, which is the thing that was actually being lost.

Solution 
STEP 1 — CONCURRENT DEMAND, NOT AVERAGE DEMAND

$ gh run list --limit 1000 --json startedAt,updatedAt \
    --jq '.[] | [(.startedAt|fromdate), (.updatedAt|fromdate)] | @tsv' > spans.tsv

$ python - <<'PY'
import collections
events = []
for line in open("spans.tsv"):
    a, b = line.split()
    events += [(int(a), 1), (int(b), -1)]
events.sort()
cur = peak = 0
hist = collections.Counter()
prev = events[0][0]
for t, d in events:
    hist[cur] += t - prev          # time spent at each concurrency level
    prev = t; cur += d; peak = max(peak, cur)
total = sum(hist.values())
run = 0
for level in sorted(hist):
    run += hist[level]
    print(f"{level:3d} concurrent  {100*run/total:5.1f}% of the time")
print("peak:", peak)

🎯 Key Takeaways

  • Self-host for capability, never for cost. A migration claiming $4,100/year of savings consumed 31 engineer-days ($21,000) in its first year against a $7,188 hosted bill.
  • The legitimate reasons, in order of how often they are true: private network access, special hardware, compliance, genuine scale economics — and warm caches, which a registry cache usually solves better.
  • The hybrid is usually right: a small private pool for the handful of repositories that need VPC access, hosted runners for everything else.
  • Ephemeral is the property that matters. A persistent pool let one repository's global npm install -g keep another repository's build green for six weeks.
  • Persistent runners also leak credentials: another job's registry push token sitting in ~/.docker/config.json is a cross-repository compromise, not an inconvenience.
  • Cleanup scripts are a denylist and are always missing something — destroy the machine instead; there is then nothing to clean.
  • A self-hosted runner building fork PRs is unauthenticated remote code execution inside your network. An audit found runners able to open a socket to the production database and read the instance IAM role.
  • Runner labels are not a security boundary — any workflow in any repository with pool access can request them. Use platform-level runner groups scoped to named repositories.
  • Block the instance metadata endpoint (or IMDSv2 with hop limit 1), give runners their own subnet with an egress allowlist, and prefer per-job OIDC credentials over an instance role.
  • Size the pool from the p95 of concurrent demand, not the mean — averages said 3 concurrent jobs where the p95 was 11 and the peak 20.
  • Scale-up lag makes the ceiling irrelevant: 30 s polling + 42 s launch + 98 s boot + 90 s image pull = 4m40s from queued to executing.
  • Fix it with a warm floor (2 runners, $94/month, p50 380 s → 12 s), a baked toolchain image, a queued-job scaling signal, and pods instead of VMs.
  • Scale on queued jobs, never on CPU — a queued job consumes no CPU, so the metric arrives after people are already waiting.
  • Spot instances are fine for retryable jobs and wrong for deploys or anything holding a lock.
  • Disk exhaustion caused 61% of one quarter's infrastructure failures, and a nightly prune -af made it worse by deleting the cache while still filling up by afternoon. Prune by watermark, alert at 70%, split the volumes.
  • Classify infrastructure failures separately from test failures — 186 of 299 failures were infrastructure and every one had been reported as a flaky test.
  • Classification also makes retries defensible: retry on an infrastructure signature, never on "the job failed".
  • Run the pool as a service with published SLIs: job start latency p95 under 60 s, infrastructure failure rate under 0.5%, availability above 99.5% in working hours, disk headroom above 25%.
  • Supporting infrastructure decides whether fast pipelines are possible: a pull-through registry cache (−38 s, 28 rate-limit incidents → 0), a package proxy (−39 s), a co-located cache bucket (−62 s and $180/month), and a remote build cache (8m52s → 47 s).
  • Together those make ephemeral runners affordable — they attack precisely the cold-start cost that is the usual argument against a fresh machine per job.
