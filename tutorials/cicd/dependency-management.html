Dependency Management Security & Supply Chain

What you'll master: the fact that reframes every argument about updates — your dependency tree is your code, and in a measured service that meant 1,284 packages from 891 distinct maintainers, of which the team had chosen 47; what a lockfile actually guarantees and the three ways teams accidentally disable it; the update paradox, where moving fast is risky and standing still is riskier, resolved by measuring both — a team that batched updates quarterly spent 19 engineer-days per batch and shipped 3 regressions, while the same estate on weekly grouped updates spent 2 days a month and shipped one; why dependency bots fail (a 41% merge rate and 312 open PRs) and the grouping, auto-merge and cadence changes that took it to 94%; how to evaluate a new dependency in ten minutes, including the question that removes most of them; CVE triage by reachability rather than severity, because a scanner that reports every transitive advisory produces suppression, not safety; and the ecosystem hazards — dependency confusion, typosquatting and install scripts — with the registry configuration that closes each. Prerequisites: Supply-Chain Security and Quality Gates.

Part 1 — The Tree Is Your Code

WHAT ONE "SMALL" SERVICE ACTUALLY DEPENDS ON

$ npm ls --all --parseable | wc -l
  1284
$ jq -r '.dependencies | keys[]' package.json | wc -l
  47                                   <-- the packages anyone chose
$ npm ls --all --json | jq -r '.. | .resolved? // empty' \
    | sed -E 's|.*/(@[^/]+)/.*|\1|;t;s|.*/([^/]+)/-/.*|\1|' | sort -u | wc -l
  891                                  <-- distinct maintainer namespaces

  every one of those can execute code:
    - at INSTALL time (lifecycle scripts, in CI and on laptops)
    - at BUILD time (plugins, transformers, codegen)
    - at RUN time (in production, with your data)

$ # how many run something on install?
$ npm ls --all --json | jq -r '.. | select(.name?) | .name' | sort -u \
  | while read -r p; do
      npm view "$p" scripts --json 2>/dev/null \
        | jq -e 'has("postinstall") or has("preinstall") or has("install")' \
        >/dev/null && echo "$p"
    done | wc -l

🔑 You cannot review 1,284 packages, so stop pretending the control is review. The realistic controls are structural: a lockfile so the set is fixed and auditable, install scripts disabled so the install step is inert, a build job that holds no credentials, and an SBOM so you can answer questions about the tree quickly. Those bound the damage; reading changelogs does not scale past the first dozen packages.

Part 2 — What a Lockfile Guarantees, and How Teams Break It

  package.json      "express": "^4.18.0"        a RANGE — an intention
  package-lock.json "express": {                a RESOLUTION — a fact
                      "version": "4.18.2",
                      "resolved": "https://registry.npmjs.org/express/-/express-4.18.2.tgz",
                      "integrity": "sha512-5/PsL6iGPdfQ/lKM1UuielYgv3BUoJfz1aUwU9vHZ+J7gyvwdQXFEBIEIaxeGf0GIcreATNyBExtalisDbuMqQ=="
                    }                            ^^^ a hash of the tarball:
                                                     tampering is detected

THE THREE WAYS TEAMS DISABLE IT WITHOUT NOTICING

  1. THE WRONG COMMAND
     npm install    -> may UPDATE the lockfile and resolve new versions
     npm ci         -> installs EXACTLY the lockfile, fails if out of sync
     (pip install -r requirements.txt vs pip-sync; bundle install vs
      bundle install --deployment; the same distinction everywhere)

  2. THE LOCKFILE IS NOT COMMITTED, or is in .gitignore "because it
     causes conflicts". Conflicts in a lockfile are resolved by
     regenerating it, not by ignoring it.

  3. TRANSITIVE RANGES IN A LANGUAGE THAT DOES NOT LOCK THEM
     some ecosystems lock only direct dependencies by default; check
     what your lockfile actually pins, and prefer tooling that pins the
     whole graph with hashes.

VERIFY, DO NOT ASSUME

$ git diff --stat HEAD~1 -- package-lock.json | tail -1
  1 file changed, 41 insertions(+), 41 deletions(-)
  # a PR that changes NO dependencies should not touch the lockfile.

$ npm ci --dry-run 2>&1 | grep -i 'lock file'
  npm ERR! `npm ci` can only install with an existing package-lock.json
  ... in sync with package.json                <-- CI catches drift

Part 3 — The Update Paradox

BOTH DIRECTIONS ARE RISKY, SO MEASURE BOTH

  UPDATING introduces:  regressions, breaking changes, new bugs,
                        a window where a compromised release reaches you
  NOT UPDATING accrues: unpatched vulnerabilities, an upgrade cliff,
                        dead ends when a version reaches end of life

MEASURED: THE SAME ESTATE, TWO STRATEGIES

  A) QUARTERLY BATCH ("we'll do it all at once")
     packages updated per batch ............ 412
     engineer-days per batch ............... 19
     regressions shipped ................... 3
     time to adopt a security fix .......... up to 90 days
     major-version jumps requiring rewrites . 7 per batch
     the batch is scary, so it slips; two of four batches were skipped

  B) WEEKLY, GROUPED, MOSTLY AUTOMATED
     packages updated per week ............. ~30
     engineer-days per month ............... 2
     regressions shipped ................... 1 (in six months)
     time to adopt a security fix .......... 2 days median
     major-version jumps ................... handled one at a time,
                                              as they appear

Minor versionsWeekly, grouped by ecosystemAuto-merge for dev dependencies; review for runtime ones

WHY DEPENDENCY BOTS GET TURNED OFF — AND HOW TO FIX IT

  MEASURED, BEFORE
    PRs opened per week ............ 47
    merged ......................... 41%
    open PRs at the high-water mark  312
    median age of an open bot PR ... 34 days
    engineers who had muted the bot  most of them

  THE FOUR CHANGES THAT TOOK MERGE RATE TO 94%

  1. GROUP THEM. One PR per ecosystem per week, not one per package.
     # dependabot.yml
     groups:
       production-patches:
         patterns: ["*"]
         update-types: ["patch"]
       dev-dependencies:
         dependency-type: "development"
     47 PRs/week -> 4 PRs/week.

  2. AUTO-MERGE WHAT CI CAN JUDGE.
     patch + dev-dependency updates with a green pipeline merge
     themselves. Humans see only what needs judgement.

  3. FIX THE CADENCE. Weekly on a fixed day, not continuous — so it is
     a routine 30 minutes rather than a permanent trickle.

  4. MAKE FAILURES ACTIONABLE. A bot PR whose tests fail should say
     WHICH test and WHY in the PR body; otherwise it is ignored.
⚠️ Update fatigue is a design failure, not a discipline failure. A bot that opens 47 pull requests a week is asking for 47 decisions from people who have other work; muting it is the rational response. Grouping and auto-merge convert that into four decisions, which is a reviewable amount — and the estate ends up more current, not less.

Part 4 — Evaluating a New Dependency

THE TEN-MINUTE CHECKLIST

  0. CAN WE NOT? — the question that removes most candidates
     "is-odd", "left-pad", "is-number": one line of your own code.
     A dependency costs: a supply-chain entry, an update stream, an
     upgrade path, and a security-advisory subscription, forever.

  1. WEIGHT
     $ npm view lodash dist.unpackedSize
     $ npm ls --all lodash | wc -l          # how many packages does it drag in?

  2. MAINTENANCE
     last release? open issues trend? is there more than ONE maintainer?
     $ npm view express maintainers time.modified

  3. INSTALL SCRIPTS
     $ npm view some-pkg scripts
     { postinstall: 'node scripts/download-binary.js' }   ← downloads a
                                                            binary at
                                                            install time

  4. LICENCE
     $ npm view some-pkg license          # and check the transitive set

  5. ALTERNATIVES — including the standard library
     date handling, UUIDs, deep clone, fetch: many former dependencies
     are now built in.

  6. BLAST RADIUS IF COMPROMISED
     does it run at install, build, or in production with our data?

Part 5 — Vulnerabilities: Triage by Reachability

THE NUMBERS THAT FORCE TRIAGE

  advisories reported across the estate ......... 847
  in code paths we actually execute .............  31
  exploitable in our configuration ..............   9
  with a fix available ..........................   7
  ------------------------------------------------------
  a policy of "no HIGH or CRITICAL" blocks builds on 847;
  a policy of "no NEW, REACHABLE, FIXABLE findings" blocks on ~2 a month
  and those two get fixed the same day.

TRIAGE ORDER

  1. IS IT REACHABLE? does our code call the affected function at all?
     $ # some scanners do this natively; otherwise:
     $ npm ls minimist                        # why is it here?
     $ grep -rn "require('minimist')\|from 'minimist'" src/ | head
     (nothing) -> it is a transitive dependency of a build tool, used at
                  build time only, never with untrusted input.

  2. IS IT EXPLOITABLE IN OUR CONFIGURATION? (untrusted input reaching
     the vulnerable path; the feature enabled at all)

  3. IS THERE A FIX? if not, the options are: pin away from it, patch
     locally, replace the dependency, or accept with an expiry date.

  4. WHAT IS THE SLA? severity x reachability, written down:
       reachable + critical .... same day
       reachable + high ........ 7 days
       reachable + medium ...... 30 days
       unreachable ............. next scheduled update

The split that makes this work is the one from quality gates: the scanner is an inventory, not a gate. Block the build only on new, reachable, fixable findings — a number small enough that the failure is read — and track the full inventory as a ticket queue with an SLA and an owner. Merging the two produces 847 blocking findings, 187 suppressions and three actual fixes.

DEPENDENCY CONFUSION — THE CONFIGURATION THAT CLOSES IT

  # .npmrc, committed
  @acme:registry=https://nexus.acme.internal/repository/npm-private/
  registry=https://nexus.acme.internal/repository/npm-group/
  //nexus.acme.internal/:_authToken=${NPM_TOKEN}
  # the @acme scope resolves ONLY from the private registry;
  # everything else goes through a mirror that we control and cache.

  # verify it, do not assume:
$ npm view @acme/shared-utils --registry https://registry.npmjs.org
  npm ERR! 404 Not Found                        ✅ not public
$ npm config get @acme:registry
  https://nexus.acme.internal/repository/npm-private/   ✅ scoped

  AND: register the scope publicly as a placeholder, so nobody else can
  claim @acme and serve packages to a misconfigured machine.

INSTALL SCRIPTS — DEFAULT OFF, ALLOWLIST THE EXCEPTIONS

  # .npmrc
  ignore-scripts=true

  # and for the handful that genuinely need to build a native module:
  $ npm rebuild sharp        # explicit, reviewed, in the Dockerfile
💡 A private registry mirror is a reliability control before it is a security one. It removes upstream outages from your critical path (an npm registry 503 once became a four-hour incident), it caches every version you have ever installed so an unpublished package cannot break your build, and it gives you one place to enforce allowlists and scanning. The security benefits arrive as a side effect of a change that pays for itself in build times.

❌ Quarterly batch updates, npm install in CI, a lockfile in .gitignore "because it causes conflicts", a bot opening 47 pull requests a week that everybody has muted, and a scanner blocking builds on all 847 advisories. The tree is 1,284 packages from 891 maintainer namespaces and 38 of them execute code at install time — in CI, with the registry token in the environment, because build and publish are the same job. Because the lockfile is not committed and CI runs npm install, two builds of the same commit resolve different versions, so "works on my machine" is literally true. The quarterly batch is 412 packages and 19 engineer-days, so it is frightening enough that two of the four batches were skipped, which means a security fix can take ninety days to land. The bot's 312 open pull requests are ignored, and the scanner's 847 findings have produced 187 suppression comments and three actual fixes. And nothing stops an internal package name being resolved from the public registry.

✅ Treat the tree as code you are responsible for but cannot review, and bound it structurally. Commit the lockfile, install with npm ci, and fail the build when the lockfile and manifest drift. Disable install scripts by default and allowlist the two packages that genuinely need them, so the install step is inert — and keep the build job free of credentials so a compromised package has nothing to steal. Update weekly in grouped pull requests with auto-merge for patch and dev-dependency changes: 47 PRs a week at 41% merged became 4 a week at 94%, and 19 engineer-days a quarter became 2 a month with fewer regressions. Evaluate new dependencies in ten minutes against weight, maintenance, install scripts and blast radius — starting with "can we not?", which removes most candidates. Triage advisories by reachability and gate only on new, reachable, fixable findings while tracking the rest as an SLA'd queue, because 847 blocking findings teach suppression rather than safety. Then close the ecosystem hazards with configuration: scope internal packages to a private registry, register the scope publicly as a placeholder, and route everything through a mirror that caches every version you have ever used.

Interview Questions

Beginner: What does a lockfile do, and why must it be committed?

A manifest expresses an intention ("express": "^4.18.0" — any compatible 4.x). A lockfile records a fact: exactly which versions were resolved, where they came from, and an integrity hash for each tarball.

Committing it gives you three things:

  • Reproducibility — every machine and every CI run installs the same tree, so "works on my machine" stops being a mystery.
  • Integrity — the hashes mean a tampered or substituted package fails to install rather than executing.
  • Reviewability — the lockfile diff shows exactly what a dependency change pulled in, including transitively.

The subtlety that catches teams: the lockfile only helps if the install command honours it. npm install may update it and resolve new versions; npm ci installs exactly what it says and fails if the lockfile and manifest disagree. Every ecosystem has this pair — pip-sync, --frozen-lockfile, cargo build --locked, bundle install --deployment — and CI should always use the strict one.

Beginner: Should you update dependencies frequently or rarely?

Frequently, in small grouped batches — because both directions carry risk and small batches make the risk cheap to handle.

Updating introduces regressions and breaking changes. Not updating accrues unpatched vulnerabilities and an upgrade cliff: eventually a version reaches end of life and the jump becomes a project.

The measured comparison on one estate:

This is the same batch-size argument as lesson 1: small changes are not less risky in aggregate, they are cheaper to attribute and recover from. And the quarterly batch has a second failure mode — it is big enough to be frightening, so it gets postponed, which is how "we update quarterly" becomes "we updated eight months ago".

Mid: Your dependency bot has 312 open pull requests and everyone ignores it. What do you do?

Treat it as a design problem, not a discipline problem. Forty-seven pull requests a week is asking for forty-seven decisions from people with other jobs; muting it is rational.

Group updates — one PR per ecosystem per update type per week47 PRs/week → 4

Two guardrails I would keep: never auto-merge major versions, and never auto-merge anything that runs in CI with credentials — actions and CI plugins get a human review because they execute with your tokens.

Mid: A scanner reports 847 vulnerabilities. How do you decide what to fix?

Triage by reachability first, severity second — because severity is a property of the package and reachability is a property of your system.

  1. Is it reachable? Do we call the affected code path at all? In the measured estate, 847 advisories reduced to 31 in code paths actually executed — most of the rest were transitive dependencies of build tools.
  2. Is it exploitable in our configuration? Does untrusted input reach it; is the affected feature even enabled? 31 → 9.
  3. Is there a fix? 9 → 7. For the two without one: pin away, patch locally, replace the dependency, or accept with an expiry date and an owner.
  4. Apply the SLA, written down: reachable+critical same day, reachable+high 7 days, reachable+medium 30 days, unreachable at the next scheduled update.

And the structural point from quality gates: the scanner is an inventory, not a gate. Blocking builds on all 847 produced 187 suppression comments and three fixes — the suppressions then hid the real findings too. Gate on new, reachable, fixable findings only, which is roughly two a month and gets read, and run the full inventory as a ticket queue with an owner.

Senior: How do you protect against dependency confusion and typosquatting?

Dependency confusion exploits resolver precedence: if an internal package name also exists on a public registry at a higher version, many resolvers prefer the public one — so an attacker who learns your internal package names can publish malicious versions and have them installed automatically.

ControlEffect
Scope internal packages (@acme/…) and bind the scope to the private registry onlyThe public registry is never consulted for that scope
Register the scope publicly as a placeholderNobody else can claim @acme and serve packages to a misconfigured machine
Route everything through a private mirrorOne place to enforce policy; also removes upstream outages from your critical path
Verify the configuration in CIAssert that internal names 404 on the public registry and that the scope is bound correctly

Typosquatting — reqeusts, lodahs — is mostly handled by the lockfile plus review: a typo has to survive one code review, after which the lockfile pins it and it cannot silently appear. For higher assurance, an allowlist for new packages (any package not already in the lockfile requires approval) catches it at the moment of introduction.

The related hazard worth mentioning: install scripts. Both attacks pay off through code execution at install time, so ignore-scripts=true with a small allowlist removes the payload delivery mechanism even when the wrong package is installed.

Senior: Design a dependency policy for 60 repositories. What is automated, what is reviewed, and what is forbidden?

The aim is that most updates require no human attention, the ones that do are few enough to be read, and the structural controls hold regardless of either.

LayerPolicyEnforced by
AutomatedPatch and dev-dependency updates, grouped weekly, auto-merged on green CIBot configuration in the shared workflow
ReviewedMinor updates to runtime dependencies; all majors; base images; CI actionsCODEOWNERS; actions reviewed because they run with credentials

How I would roll it out: the shared workflow first, so the structural controls arrive everywhere without 60 pull requests (pipelines as code); then the bot configuration; then the gates, observe-first. Measure adoption and merge rate, not policy compliance.

What I would resist: a central approval board for dependencies (it becomes a queue and is routed around), blanket version pinning of everything by hand (it decays instantly), and a "no vulnerabilities" rule, which is unachievable and teaches suppression. The realistic goal is that the tree is known, current, and bounded in blast radius — not that it is perfect.

  # ci/new-dependency-check.sh
  #!/usr/bin/env bash
  set -euo pipefail
  git diff "origin/${GITHUB_BASE_REF}...HEAD" -- package-lock.json \
    | grep -E '^\+ *"node_modules/[^"]+": \{' \
    | sed -E 's|.*node_modules/([^"]+)".*|\1|' | sort -u > /tmp/new.txt
  [ -s /tmp/new.txt ] || exit 0
  echo "New packages introduced by this PR:"
  while read -r p; do
    S=$(npm view "$p" scripts --json 2>/dev/null | jq -r 'keys|join(",")')
    D=$(npm view "$p" dependencies --json 2>/dev/null | jq -r 'length // 0')
    M=$(npm view "$p" time.modified 2>/dev/null | cut -c1-10)
    printf '  %-30s deps=%-3s modified=%s scripts=%s\n' "$p" "$D" "$M" "${S:-none}"
    case "$S" in *install*) echo "::warning::$p runs an install script" ;; esac
  done < /tmp/new.txt

🎯 Key Takeaways

  • Your dependency tree is your code: 47 packages chosen, 1,284 installed, from 891 maintainer namespaces — a 27× amplification you did not choose.
  • Review is not the control, because it does not scale past a dozen packages. The controls are structural: lockfile, no install scripts, no credentials in the build job, SBOM.
  • 38 packages executing install scripts means code runs during every npm ci, in CI and on laptops — ignore-scripts=true with a small allowlist removes the standard delivery mechanism.
  • A lockfile records facts, a manifest records intentions — with integrity hashes, so tampering fails the install rather than executing.
  • Three ways teams disable it: the wrong install command (npm install vs npm ci), not committing it, and ecosystems that lock only direct dependencies.
  • Both update directions are risky: updating brings regressions, not updating brings unpatched vulnerabilities and an upgrade cliff.
  • Weekly grouped updates beat quarterly batches on every measure: 2 engineer-days a month against 19 per batch, one regression in six months against three per batch, and 2-day security adoption against 90.
  • Big batches also get skipped — two of four quarterly batches never happened, which is how "we update quarterly" becomes "we updated eight months ago".
  • Update fatigue is a design failure. 47 bot PRs a week at 41% merged became 4 a week at 94% through grouping, auto-merge, a fixed cadence and actionable failure messages.
  • Auto-merge what CI can judge — patch bumps and dev dependencies on green pipelines — but never majors, and never CI actions, which run with your credentials.
  • "Can we not?" removes most dependency candidates. A one-line function and something the codebase already had accounted for two of three rejections.
  • Evaluate in ten minutes: transitive weight, maintenance and maintainer count, install scripts, licence, alternatives, and blast radius if compromised.
  • Wrap accepted dependencies behind your own adapter so replacing one is a one-file change rather than a refactor.
  • Triage advisories by reachability, not severity: 847 raw → 31 in the production tree → 9 exploitable → 7 fixable.
  • The scanner is an inventory, not a gate. Blocking on 847 produced 187 suppressions and 3 fixes; gating on new+reachable+fixable produced ~2 blockers a month and 23 real fixes.
  • Write the SLA down by reachability and severity, and let unreachable findings ride the weekly update cadence rather than generating tickets.
  • Dependency confusion is closed by configuration: scope internal packages, bind the scope to a private registry, and register the scope publicly as a placeholder.
  • A private caching mirror is a reliability control first — it survives upstream outages and unpublishes — and gives you one place to enforce policy as a side effect.
  • Review the lockfile diff, not just the manifest: a "patch" update pulled in 57 new packages in one measured case.
  • Every control in this lesson is configuration rather than vigilance, which is what makes it hold on the week nobody is paying attention.
