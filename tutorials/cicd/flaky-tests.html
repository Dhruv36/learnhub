Flaky Tests Building & Testing

What you'll master: the arithmetic that makes flakiness an emergency rather than an annoyance — a 0.1% per-test failure rate across 1,100 tests means only 33% of runs are green, and the team's rational response to that is to stop reading failures; the nine kinds of flakiness and their signatures, so diagnosis starts from evidence rather than from re-running; why sleep is never the fix and polling always is, with the measured version where replacing fixed waits cut suite time 31% and removed the flakes; how to detect flaky tests deliberately instead of waiting for them — random order, parallel, stress, and a flake score computed from runs you already have; the quarantine policy that works (automatic on detection, an owner, a deadline, deletion if the deadline passes) versus the retry-by-default policy that feels identical and is the opposite; and the finding that changes how seriously you take all of this — in one measured quarter 19 of 63 quarantined "flaky" tests were real product bugs, including two that had already caused customer incidents. Prerequisites: Test Strategy in CI and Anatomy of a Pipeline.

Part 1 — The Arithmetic of Distrust

A single test that fails 1 in 1,000 times sounds negligible. Suites do not experience per-test rates; they experience the product of them.

P(suite green) = (1 − p)^N        for N independent tests each failing p

  per-test rate    N = 200      N = 1,100     N = 5,000
  ------------------------------------------------------------
  0.01%            98.0%          89.6%         60.7%
  0.05%            90.5%          57.7%          8.2%
  0.1%             81.9%          33.0%          0.7%
  0.5%             36.7%           0.4%          ~0%
  ------------------------------------------------------------
  A 1,100-test suite where each test is 99.9% reliable is green
  ONE RUN IN THREE.

  MEASURED, THE SUITE FROM THE PREVIOUS LESSON, BEFORE ANY WORK:
    first-attempt pass rate ............. 61%
    final pass rate (after retries) ..... 94%     <-- the reported number
    manual retries per week ............. 78
    tests responsible for 80% of the
      flaky failures ....................  9      <-- of 1,100
🔑 Flakiness is concentrated, which is the good news. Nine tests caused 80% of the noise in a suite of 1,100. This is the reliable shape: a handful of tests are responsible for nearly all the damage, so the work is small once you can identify them — and the entire cost of not doing it is paid by everyone, every day, in the form of a signal nobody believes.

1.1 What distrust actually costs

  DIRECT
    78 retries/week x 34 min pipeline x 24 engineers affected
      -> ~44 engineer-hours/week of waiting on re-runs
    runner minutes for reruns: +31% of total CI spend

  INDIRECT, AND FAR WORSE
    - red stops meaning "broken", so failures are not read
    - a REAL failure gets retried into main. Measured: 3 incidents in

    - engineers stop adding tests to a suite they do not trust
    - the merge queue is disabled "because it keeps blocking on flakes",
      which removes the mechanism that kept main green
    - new joiners learn the retry button in week one; it is now culture

That third item is the one to bring to a manager who thinks this is a hygiene task. A retried genuine failure is an incident whose root cause is a policy, and it will happen again on a schedule set by your flake rate.

THE MOST COMMON ONE, IN ITS THREE DISGUISES

  ❌ time.sleep(2)                  # "usually enough"
  ❌ await page.wait_for_timeout(500)
  ❌ retry(3, test_fn)              # papering over it at the harness level

  ✅ POLL FOR THE CONDITION, WITH A DEADLINE AND A USEFUL MESSAGE

     def until(cond, timeout=10.0, interval=0.05, what="condition"):
         deadline = time.monotonic() + timeout
         last = None
         while time.monotonic() < deadline:
             try:
                 last = cond()
                 if last: return last
             except AssertionError as e:
                 last = e
             time.sleep(interval)
         raise AssertionError(f"timed out after {timeout}s waiting for {what};"
                              f" last result: {last!r}")

     until(lambda: db.query(Order).filter_by(id=oid).one().status == "paid",
           what="order to become paid")

  WHY POLLING IS BOTH FASTER AND MORE RELIABLE THAN sleep:
    sleep(2) always costs 2 s and still fails on a slow runner.
    Polling returns in ~40 ms on a fast runner and tolerates 10 s on a
    loaded one. Measured across one suite: 214 sleeps removed,
    suite time −31%, timing flakes −94%.
⚠️ A sleep encodes a guess about someone else's speed. It is simultaneously too long (on every fast run, forever) and too short (on the loaded run that matters). The polling helper above is fifteen lines, is written once per repository, and eliminates an entire category of flakiness — while making the suite measurably faster, which is the argument that gets it prioritised.

Part 3 — Detecting Flakes Deliberately

Waiting for flakes to appear means learning about them at the worst possible time, from the most expensive possible signal. All four detection methods below are cheap and can run tonight.

METHOD 1 — FLAKE SCORE FROM DATA YOU ALREADY HAVE
  A test that passed and failed AT THE SAME COMMIT is flaky by definition.

$ # collect JUnit XML from the last 300 runs, then:
$ python - <<'PY'
import glob, collections, xml.etree.ElementTree as ET
res = collections.defaultdict(lambda: collections.defaultdict(set))
for f in glob.glob("artifacts/*/junit.xml"):
    sha = f.split("/")[1]
    for tc in ET.parse(f).getroot().iter("testcase"):
        name = f"{tc.get('classname')}::{tc.get('name')}"
        res[name][sha].add("fail" if (tc.find("failure") is not None) else "pass")
rows = []
for name, shas in res.items():
    both = sum(1 for s in shas.values() if len(s) == 2)
    if both: rows.append((both, len(shas), name))
for both, n, name in sorted(rows, reverse=True)[:10]:
    print(f"{both:4d} flaky commits / {n:4d}  {name}")
PY

    31 flaky commits /  287  tests/e2e/test_checkout.py::test_apply_coupon
    24 flaky commits /  287  tests/e2e/test_checkout.py::test_guest_checkout
    19 flaky commits /  287  tests/api/test_webhooks.py::test_retry_delivery
    ...
    9 tests account for 80% of all flaky-commit observations.

METHOD 2 — RERUN UNTIL FAILURE (targeted, for a suspect)
$ pytest tests/api/test_webhooks.py::test_retry_delivery --count=500 -x -q
  ...FAILED at iteration 41: assert 2 == 3
  -> reproduces in ~40 s; now it is a normal debugging problem

METHOD 3 — RANDOM ORDER AND PARALLEL (finds kinds 2 and 3)
$ pytest --random-order -n 4          # do this in CI, permanently

METHOD 4 — STRESS (finds kinds 1, 6 and 9)
$ docker run --cpus 0.5 --memory 1g ... pytest tests/     # a slow runner
$ stress-ng --cpu 8 --timeout 600 & pytest tests/         # contention
  timing assumptions that hold on an idle laptop fail here, on purpose

Part 4 — Quarantine: The Policy That Works

Two policies look similar from a distance and have opposite outcomes. One removes noise from the blocking path while keeping the debt visible and dated. The other hides the noise and calls the problem solved.

Retry-by-default ❌Quarantine ✅
MechanismThe harness re-runs failures automatically; green if any attempt passesDetected flaky tests are moved out of the blocking suite into a non-blocking job
Blocking signalPolluted: a real failure can pass on attempt 3Clean: everything blocking is deterministic
VisibilityNone — the run is greenA list, with owners and deadlines, reported weekly
IncentiveZero: nothing hurts, so nothing gets fixedThe test disappears if nobody fixes it, which forces a decision
CoverageBelieved intact; actually unknownExplicitly reduced, deliberately, with an expiry date
THE POLICY, IN FULL — SIX RULES, WRITTEN DOWN

  1. DETECTION IS AUTOMATIC. A test that passes and fails at the same
     commit twice in 30 days is flagged by the nightly report.

  2. QUARANTINE IS AUTOMATIC AND IMMEDIATE. The flagged test is tagged
     @quarantined and excluded from the blocking suite by CI config —
     not deleted, not commented out, not skipped silently.

  3. IT STILL RUNS, in a non-blocking nightly job, so its behaviour is
     tracked and the fix can be verified.

  4. IT HAS AN OWNER, assigned by CODEOWNERS on the test's path, and a
     ticket opened by the automation.

  5. IT HAS A DEADLINE — 14 days. The ticket says so, and the weekly
     report shows the countdown.

  6. AT THE DEADLINE THE TEST IS DELETED, automatically, by a PR the
     automation raises. Deleting a test nobody will fix is honest: it
     was providing no signal and costing everyone attention.
     If it protects something important, rule 6 is what finally makes
     someone say so.

  GUARDRAILS
    - a hard cap: if more than 2% of tests are quarantined, the pipeline
      posts a warning and new quarantines require a human approval.
      Quarantine must never become a landfill.
    - tests covering auth, money or migrations CANNOT be auto-quarantined;
      they escalate to a human immediately.

MEASURED, ONE QUARTER, 1,100-TEST SUITE

  ---------------------------------------------------------
  first-attempt pass rate           61%          93%
  manual retries per week           78            4
  tests quarantined at peak          -           63  (5.7%)
  quarantined tests FIXED            -           38
  quarantined tests DELETED          -           25

🔑 Deletion at the deadline is the rule people resist and the one that makes the policy work. Without it, quarantine becomes an infinite parking lot, and after a year nobody knows what is in it or what it covered. With it, every quarantined test forces a real decision within two weeks: fix it, or admit it was not protecting anything worth two weeks of someone's attention.

Part 5 — Fixing the Big Three

5.1 Timing: poll, do not sleep

  ❌ def test_order_is_processed():
         submit_order(oid)
         time.sleep(3)                       # fails at 4 s under load
         assert get_order(oid).status == "processed"

  ✅ def test_order_is_processed():
         submit_order(oid)
         until(lambda: get_order(oid).status == "processed",
               timeout=15, what=f"order {oid} to be processed")

  BROWSER TESTS: the same rule, expressed by the framework
  ❌ page.wait_for_timeout(1000); page.click("#pay")
  ✅ page.get_by_role("button", name="Pay").click()   # auto-waits for
                                                     # visible + enabled
  ✅ expect(page.get_by_test_id("receipt")).to_be_visible(timeout=15_000)

  AND THE ANTI-PATTERN THAT SURVIVES REVIEW BECAUSE IT LOOKS RIGOROUS:
  ❌ for _ in range(10):
         if condition(): break
         time.sleep(1)
     # no failure if it never becomes true — the test passes on timeout
     # ALWAYS assert after the loop, or use a helper that raises.

5.2 Time: inject the clock

  ❌ def is_expired(self):
         return datetime.utcnow() > self.created_at + timedelta(hours=48)
     # untestable at the boundary without sleeping or faking the system clock

  ✅ def is_expired(self, now=None):
         now = now or self.clock.now()
         return now > self.created_at + timedelta(hours=48)

     def test_expiry_boundary():
         t0 = datetime(2026, 8, 21, 12, tzinfo=UTC)
         a = Approval(created_at=t0)
         assert not a.is_expired(now=t0 + timedelta(hours=48) - timedelta(seconds=1))
         assert     a.is_expired(now=t0 + timedelta(hours=48))

  THE ONCE-A-YEAR FAILURES THIS PREVENTS
    - a test that assumes the month has 31 days           (fails 5x/year)
    - a test that assumes "tomorrow" is a weekday         (fails ~2x/week)
    - DST transitions: a "24 hours later" that is 23 or 25
    - a fixture created "29 days ago" with a hardcoded 2024 date
    - tests that pass in UTC and fail in the runner's local timezone
      -> pin TZ in CI, and ALSO run one nightly job in a hostile
         timezone (Pacific/Auckland or America/Santiago) to catch the
         assumptions that pinning hides

5.3 Order and state: isolate, do not sequence

  DIAGNOSE FIRST — bisect the ordering to find the pair
$ pytest --random-order --random-order-seed=4211      # reproduces
$ pytest -p no:randomly tests/a.py tests/b.py         # minimal pair
$ pytest tests/b.py                                    # passes alone
  -> a.py leaves state that b.py depends on (or is broken by)

  COMMON CULPRITS, ALL FIXABLE IN MINUTES
    module-level caches populated by the first test
    monkeypatching without undo (use the framework's patch fixture)
    a singleton or connection pool shared across tests
    environment variables set and not restored
    a global registry (metrics, feature flags, DI container)
    class attributes mutated instead of instance attributes

  ✅ reset in a fixture that ALWAYS runs, including on failure:
     @pytest.fixture(autouse=True)
     def isolate(monkeypatch):
         cache.clear(); registry.reset(); flags.reset()
         yield
         cache.clear(); registry.reset(); flags.reset()

Part 6 — The Flakes That Are Real Bugs

The most important finding in this lesson is that a meaningful minority of "flaky tests" are correct tests reporting a genuine nondeterminism in the product. Retrying them is not tidying up; it is suppressing a bug report.

THE 19 REAL BUGS FROM THE QUARTER ABOVE, BY KIND

  8  race conditions in application code (two writers, no lock or
       constraint; the test caught a duplicate that also happened in
       production about once a week and was blamed on "users
       double-clicking")
  4  missing idempotency: a retried webhook created two records

  closed as "could not reproduce". The test had been reproducing them,
  intermittently, for months — and being retried.

Interview Questions

Beginner: What is a flaky test, and why does one matter so much?

A flaky test is one that produces different results — pass and fail — for the same code. The operational definition that makes it detectable: a test that has both passed and failed at the same commit.

One matters because suites multiply. If each of 1,100 tests fails independently 0.1% of the time, the probability that a run is green is 0.9991100 ≈ 33%. Two runs in three are red for no reason, and the team's rational response is to stop reading failures and press retry.

That is the real damage: the pipeline stops being a gate. Once red means "probably noise", a genuine failure gets retried through — measured at three production incidents in one year in the case study — and every other quality control you have built depends on a signal nobody believes any more.

The encouraging part is that flakiness is concentrated: in that suite, nine tests caused 80% of the flaky failures. Finding those nine is an afternoon's work with historical data, which is why this is usually a small job that has simply never been assigned to anyone.

Beginner: A test fails once and passes on re-run. What do you do?

The wrong answer — and the honest one for most teams — is "merge it, it's fine". Re-running until green is what turns a flake into culture.

What I would actually do, in order:

  1. Read the failure. Two minutes. The message usually tells you the kind: an element not found (timing), a count assertion (shared state), a connection error (infrastructure or external), a duplicate key (possibly a real race).
  2. Record it. Even if I move on, the failure must be captured — test name, commit, runner, message. Without this the nine worst tests can never be identified.
  3. Try to reproduce cheaply: run that test 200 times locally; run it in random order; run it under CPU constraints. Most flakes reproduce in minutes once you stop hoping they will not.
  4. Ask whether the product could actually do this. A duplicate, a lost update or an out-of-order result is a bug report, not a flake.
  5. If it is confirmed flaky, quarantine it — out of the blocking path, still running nightly, with an owner and a deadline — rather than retrying it in place.

The team-level answer matters more than the individual one: if this happens often enough that step 1 feels unreasonable, that is the signal to build the flake report and fix the top nine, rather than to normalise the retry.

Mid: Your team wants to enable automatic test retries. What do you say?

I would separate two things that get conflated: retries as a measurement tool are useful; retries as a policy are how you lose the signal.

The problem with retry-as-policy: the blocking pipeline goes green when any attempt passes, so a genuine intermittent failure — a real race, a missing idempotency key — is indistinguishable from noise and merges. In the measured case study, three production incidents in one year traced back to real failures that had been retried until green. It also removes all pressure to fix anything, because nothing hurts any more, and it hides the fact that coverage is effectively unknown.

What I would propose instead:

  • Retry once, but report both numbers. If the harness retries, it must record first-attempt and final results separately, and the number the team tracks is first-attempt pass rate. That converts retries from a cover-up into a detector.
  • Quarantine, not retry, for the known-flaky. Out of the blocking path, still running nightly, with an owner, a 14-day deadline and automatic deletion at expiry.
  • A cap and an exception list: no more than 2% of tests quarantined, and never automatically for auth, money or migrations.

And the compromise I would accept if the team is drowning: retries on infrastructure errors only — image pulls, runner loss, network setup — which are genuinely not test outcomes, matched by error signature rather than by "the test failed".

Senior: When is a flaky test actually a bug in the product, and how do you tell?

More often than people expect. In one measured quarter, 19 of 63 quarantined tests were real product defects: eight race conditions, four missing idempotency paths, three ordering assumptions, two resource leaks, a timezone bug and an unseeded random in production code.

STEP 2 — ONE HELPER, WRITTEN ONCE

  # tests/support/wait.py
  import time
  def until(cond, timeout=10.0, interval=0.05, what="condition"):
      """Poll cond() until truthy. Raise with context on timeout."""
      deadline = time.monotonic() + timeout
      last = None
      while time.monotonic() < deadline:
          try:
              last = cond()
              if last:
                  return last
          except AssertionError as e:
              last = e
          time.sleep(interval)
      raise AssertionError(
          f"timed out after {timeout}s waiting for {what}; last={last!r}")

  # and for the "eventually consistent, then stays true" case:
  def stays(cond, for_seconds=1.0, interval=0.05, what="condition"):
      until(cond, what=what)
      deadline = time.monotonic() + for_seconds
      while time.monotonic() < deadline:
          assert cond(), f"{what} became false again"
          time.sleep(interval)

🎯 Key Takeaways

  • Suites multiply per-test flakiness. At 0.1% per test across 1,100 tests, only 33% of runs are green — and distrust becomes the rational response.
  • Flakiness is concentrated: nine tests out of 1,100 caused 80% of flaky failures. The work is small once you can rank it.
  • Report first-attempt pass rate, not final. One team reported 94% for a year while the number engineers experienced was 61%.
  • The operational definition that makes detection possible: a test that has both passed and failed at the same commit — computable from JUnit artifacts you may already be discarding.
  • Nine kinds, each with a signature: async timing, order dependence, shared state, time/date, unseeded randomness, resource exhaustion, external dependencies, infrastructure, and a real race in the product.
  • sleep is never the fix. It is too long on every fast run and too short on the loaded run that matters; polling with a deadline made a suite 31% faster and cut timing flakes 94% simultaneously.
  • A retry loop with a break and no assertion after it passes when the condition never becomes true — always raise on timeout.
  • Use a stays() helper to assert a property holds for an interval; a sleep-then-assert cannot detect a duplicate that arrives a moment later — one such check found a real idempotency bug.
  • Inject the clock. Calling now() in the code under test makes boundaries untestable and produces failures at midnight, month end, DST and once a year.
  • Pin TZ in CI and run one nightly job in a hostile timezone, so the assumptions that pinning hides still surface.
  • Fix order dependence by isolation, never by sequencing. Pinned ordering, sleeps and "run this test last" hide the coupling until someone shards the suite.
  • Run random order and parallel permanently in CI, print the seed on failure, and bisect the ordering to find the offending pair — 90 seconds of halving beats hours of reading.
  • Quarantine, do not retry. Retry-by-default pollutes the blocking signal; three production incidents in one year came from genuine failures that passed on a later attempt.
  • The policy that works: automatic detection → automatic quarantine → still runs nightly → an owner from CODEOWNERS → a 14-day deadline → automatic deletion.
  • Deletion at the deadline is what makes it work, and a 2% cap is what stops quarantine becoming a landfill; auth, money and migration tests escalate to humans instead.
  • Keep the quarantine list in config rather than as markers in test files: no code churn, one reviewable diff, and its git history is the audit trail.
  • Run quarantined tests 20× nightly so "fixed" is a measured rate rather than a claim.
  • 19 of 63 quarantined tests were real product bugs — races, missing idempotency, ordering assumptions, a descriptor leak — and two matched customer tickets closed as "could not reproduce".
  • The decisive probe: with unlimited time, is the answer always right? If not, stop debugging the test and open a bug; if the rate rises under contention rather than slowness, suspect concurrency in the product.
  • A retry policy is a bug-report suppressor — the argument to take to leadership, because it names customer impact rather than developer inconvenience.
