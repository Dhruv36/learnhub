Pipeline Reliability & Debugging Pipeline Engineering

What you'll master: the reframing that makes all of this tractable — the pipeline is a production system whose users are engineers, so it gets SLIs, an error budget, an owner and an on-call rotation, and "CI is down" becomes an incident with a severity rather than a Slack complaint; the failure taxonomy that decides what may be retried, because retrying a deterministic failure is a slow way to fail and retrying a deploy step is a way to deploy twice; retries done properly — classified by error signature, bounded by a budget, with idempotent steps — against the measured alternative where blanket retries hid a 40-minute registry outage and turned it into a four-hour one; timeouts, where a missing one let a hung job burn six hours of runner time and block the merge queue for an afternoon, and the watchdog that detects a stuck step rather than a slow one; a debugging method built on structured logs, an environment preamble and correlation IDs across jobs, so the first question of any failure is answered from the log rather than by re-running; and how to run a CI incident — declaring it, degrading deliberately, and writing the postmortem that stops the same 40 minutes happening quarterly. Prerequisites: Flaky Tests, Runners & Build Infrastructure and Quality Gates.

Part 1 — The Pipeline Is Production

When CI is down or slow, every engineer is blocked. That is the same shape as a production outage, so it deserves the same instrumentation — and the absence of that instrumentation is why most CI problems are discovered by complaint rather than by alert.

🔑 Alert on the pipeline, not on individual runs. A single failed run is normal; a rate of infrastructure failures, a collapse in first-attempt pass rate, or a queue depth that will not drain are incidents. Page on those three and you will hear about CI problems from a monitor rather than from the fourth person to give up and post in a channel.

Part 2 — A Failure Taxonomy You Can Act On

Every decision in this lesson — retry or not, alert or not, page or not — depends on which of four categories a failure falls into. Guessing produces both retried real failures and unretried transients.

CategoryExamplesRetry?Alert?
1. Deterministic — the change is brokenTest assertion, compile error, lint violation, type errorNeverNo — this is the pipeline working
2. Nondeterministic in our code or testsRace, order dependence, timingNo — quarantine insteadTrack the rate (see flaky tests)
3. Transient infrastructureRunner lost, image pull timeout, DNS blip, 503 from a registryYes, by signature, boundedOn rate, not on instance
4. External dependency outagePackage index down, cloud API throttling, the CI provider itselfBounded retry, then degradePage if it blocks merges
CLASSIFYING AUTOMATICALLY — SIGNATURES, NOT GUESSES

  # ci/classify.sh — run on every failure, before anything else decides
  case "$(tail -300 "$LOG")" in
    *"no space left on device"*)                    C=infra_disk ;;
    *"toomanyrequests"*|*"pull rate limit"*)        C=infra_registry ;;
    *"received a shutdown signal"*|\
     *"lost communication with the server"*)        C=infra_runner_lost ;;
    *"Temporary failure in name resolution"*|\
     *"TLS handshake timeout"*)                     C=infra_network ;;
    *"429 Too Many Requests"*)                      C=external_throttle ;;
    *"ECONNREFUSED"*|*"connection refused"*)        C=maybe_readiness ;;
    *"AssertionError"*|*"FAILED tests/"*|\
     *"error TS"*|*"SyntaxError"*)                  C=deterministic ;;
    *)                                              C=unclassified ;;
  esac

  the `unclassified` bucket is the useful one: every week, read those
  logs and add a signature. It should trend toward zero.
  MEASURED: 31% unclassified in week 1 -> 4% by week 6.

2.1 Degrading deliberately when something external is down

  npm registry returns 503 for 40 minutes. Three possible postures:

  ❌ FAIL EVERYTHING
     every pipeline red; nobody can merge; 140 engineers blocked

  ❌ RETRY FOREVER
     jobs hang for the full 6-hour default timeout, the runner pool
     fills with waiting jobs, and the queue never drains. This is how
     a 40-minute outage became a 4-hour one, MEASURED.

  ✅ BOUNDED RETRY, THEN DEGRADE WITH A LOUD, HONEST STATUS
     - retry 3 times with backoff (covers most blips)
     - then fall back to the package proxy's cached copy if present
     - if that fails, FAIL FAST with a message naming the dependency:
         ::error::npm registry unavailable (503 after 3 attempts).
                  This is not your change. Status: status.npmjs.org
     - and post once to the engineering channel, not once per run
⚠️ A failure message that names the cause is a reliability feature. The difference between "npm ERR! code E503" buried at line 2,400 and an annotation saying "this is not your change" is roughly twenty minutes per affected engineer — and it is the difference between one person investigating and forty people investigating the same thing simultaneously.

Part 3 — Retries That Help Rather Than Hide

  THE THREE RULES

  1. RETRY BY SIGNATURE, NEVER BY OUTCOME.
     ❌ retry-on: failure                 # retries broken code too
     ✅ retry only when classify.sh says infra_* or external_*

  2. THE STEP MUST BE IDEMPOTENT.
     safe to retry:    checkout, dependency install, image pull,
                       read-only API calls, most test runs
     NOT safe:         `docker push` of a mutable tag, a deploy,
                       a database migration, sending a notification,
                       anything that creates a resource without a key

  3. BOUND IT — attempts, total time, AND a budget across the fleet.
     3 attempts, exponential backoff with jitter, 10-minute ceiling,
     and an alert if more than 5% of runs retried in an hour.
StepIdempotent?Retry policy
Checkout, restore cache, install dependenciesYes3 attempts, backoff
Image pullYes3 attempts; then try the mirror
Test jobYes, but see rule 1Retry only on infrastructure signatures
Push an immutable tag / digestYes (same content, same digest)3 attempts
Push a mutable tagAmbiguousPrefer digests; retry with care
DeployOnly if designed to beNever blind-retry; re-run through the pipeline with a lock
Database migrationOnly if written to beNever automatically — see migrations
Notifications, tickets, releasesNoIdempotency key, or do not retry
IMPLEMENTATION — A RETRY WRAPPER WITH BACKOFF AND JITTER

  # ci/retry.sh -- attempts backoff_base -- command...
  #!/usr/bin/env bash
  set -uo pipefail
  ATTEMPTS="${ATTEMPTS:-3}"; BASE="${BASE:-5}"; n=1
  until "$@"; do
    rc=$?
    ./ci/classify.sh /tmp/last.log > /tmp/class || true
    case "$(cat /tmp/class)" in
      infra_*|external_*) : ;;                    # retryable
      *) echo "::error::not a transient failure ($(cat /tmp/class)); not retrying"
         exit "$rc" ;;
    esac
    if [ "$n" -ge "$ATTEMPTS" ]; then
      echo "::error::failed after $n attempts: $*"; exit "$rc"
    fi
    sleep_for=$(( BASE * (2 ** (n - 1)) + RANDOM % BASE ))
    echo "::warning::attempt $n failed ($(cat /tmp/class)); retrying in ${sleep_for}s"
    sleep "$sleep_for"; n=$(( n + 1 ))
  done

  # and RECORD every retry, or you cannot see the outage forming:
  ./ci/push-metric.sh ci_retry_total "{class=\"$(cat /tmp/class)\"}" 1
💡 Retries must be visible or they become camouflage. The measured four-hour outage happened because blanket retries kept jobs "in progress" — no failure rate rose, no alert fired, and the actual 40-minute registry problem was invisible until the queue was hours deep. Emit a metric per retry and alert when the retry rate crosses a threshold: that is the signal that something external has broken, long before anyone reports it.

Part 4 — Timeouts, Hangs and Watchdogs

THE DEFAULT THAT COSTS A DAY

  no timeout specified -> the platform default (6 hours on GitHub
  Actions). One hung job then:
    - occupies a runner slot for 6 hours
    - holds the concurrency group, so the merge queue stalls behind it
    - reports nothing until it is killed
  MEASURED: one hung integration job blocked the merge queue for an
  afternoon; 14 PRs waited; nobody could tell whether it was "slow"
  or "stuck" because the log had been silent for hours.

SET THREE LAYERS OF TIMEOUT, DELIBERATELY

  jobs:
    test:
      timeout-minutes: 20             # JOB: ~2x the p95 duration
      steps:
        - run: ./ci/test.sh
          timeout-minutes: 12         # STEP: the one that can hang
        - run: timeout 60s ./ci/smoke.sh    # COMMAND: inside the step

  RULE OF THUMB: job timeout ≈ 2x p95. Tight enough to fail fast,
  loose enough that a legitimately slow run is not killed. Then ALERT
  on jobs that exceed 1.5x p95 rather than waiting for the timeout.
SymptomUsual causeFix
Silent log, then timeoutWaiting on a prompt, or a network call with no timeoutCI=true, --yes, explicit client timeouts
Hangs only on CI, never locallyA service that never became ready; no TTYReadiness waits with deadlines; run non-interactively locally too
Hangs after tests passNon-daemon threads, open connections, a child process not reapedClose pools in teardown; --forceExit as a last resort, after finding the leak
Hangs at the end of the jobArtifact upload of a huge directoryUpload less; compress; check the post-job steps
Intermittent 6-hour jobsDeadlock under contentionWatchdog + thread dump (below)
A WATCHDOG THAT TELLS YOU WHY IT WAS STUCK

  - name: Tests with a watchdog
    run: |
      set -euo pipefail
      ( ./ci/test.sh 2>&1 | tee /tmp/test.log ) &
      TEST_PID=$!
      ( while kill -0 "$TEST_PID" 2>/dev/null; do
          sleep 60
          if [ -z "$(find /tmp/test.log -newermt '-120 seconds')" ]; then
            echo "::warning::no output for 120s — dumping diagnostics"
            ps auxf | head -40
            jstack "$(pgrep -f java | head -1)" 2>/dev/null || true
            py-spy dump --pid "$(pgrep -f pytest | head -1)" 2>/dev/null || true
            ss -tanp | head -20
          fi
        done ) &
      WATCHDOG=$!
      wait "$TEST_PID"; RC=$?
      kill "$WATCHDOG" 2>/dev/null || true
      exit "$RC"

  a timeout tells you the job hung. This tells you WHERE — and it costs
  one background loop. In the measured case it revealed a test waiting
  on a connection pool that had been exhausted by a leaked session.

Part 5 — A Debugging Method That Does Not Start With "Re-run"

Lesson 3 gave the ladder — read the log, correlate across runs, reproduce in the runner's image, then a gated interactive session. This part is about making the first rung actually work, because most CI logs are unreadable by design.

THE PREAMBLE — PRINT WHAT THE NEXT PERSON WILL ASK FOR

  # ci/preamble.sh, sourced by every script
  set -euo pipefail
  trap 'echo "::error::failed at ${BASH_SOURCE[0]}:${LINENO}: ${BASH_COMMAND}"' ERR

  echo "::group::environment"
  echo "commit    $(git rev-parse HEAD)"
  echo "run       ${GITHUB_RUN_ID:-local} attempt ${GITHUB_RUN_ATTEMPT:-1}"
  echo "runner    $(uname -srm)  cpus=$(nproc)  mem=$(free -m | awk 'NR==2{print $2}')MB"
  echo "disk      $(df -h / | awk 'NR==2{print $4" free ("$5" used)"}')"
  node --version; python3 --version; docker --version
  printenv | grep -viE 'token|secret|password|key' | sort
  echo "::endgroup::"

  WHY EACH LINE EARNS ITS PLACE:
    commit + run + attempt  -> correlate with other jobs and reruns
    cpus/mem                -> "it only fails on the small runners"
    disk                    -> the 61% failure cause from <runners>
    tool versions           -> "works on my machine" in one line
    filtered env            -> the empty-variable class of bug
TechniqueWhat it buys
::group:: / ::endgroup::A collapsible log someone will actually read
::error file=…,line=…:: annotationsThe failure appears inline on the PR diff, not in a log
A correlation ID exported to every jobJoins the build, test and deploy jobs of one run in your log system
Uploading diagnostics on failure onlyScreenshots, server logs, thread dumps — without the publish cost on green runs
A job summary ($GITHUB_STEP_SUMMARY)The three facts a reviewer needs, without opening the log
Printing the decision a script made"selected 84 of 1,100 tests", "tag=pr-91", "shard 2 of 4"
  - name: Diagnostics on failure
    if: failure()
    run: |
      mkdir -p /tmp/diag
      cp /tmp/test.log /tmp/diag/ 2>/dev/null || true
      docker logs "$(docker ps -aqf name=postgres)" > /tmp/diag/postgres.log 2>&1 || true
      df -h > /tmp/diag/disk.txt; ps auxf > /tmp/diag/processes.txt
      env | grep -viE 'token|secret|password' > /tmp/diag/env.txt
  - uses: actions/upload-artifact@v4
    if: failure()
    with: { name: diagnostics-${{ github.run_id }}, path: /tmp/diag, retention-days: 7 }

  MEASURED EFFECT: median time-to-diagnose for infrastructure failures
  fell from 34 minutes to 6, because the second engineer no longer had
  to reproduce the failure to see the state it happened in.

Part 6 — Running a CI Incident

THE RUNBOOK — WRITE IT BEFORE YOU NEED IT

  DECLARE when any of these is true:
    - infrastructure failure rate > 10% for 10 minutes
    - queue depth rising for 15 minutes with no drain
    - the merge queue has been blocked for 20 minutes
    - a required check cannot pass for reasons unrelated to changes

  FIRST FIVE MINUTES
    1. POST ONCE, centrally: what is broken, what to do meanwhile,
       who is on it, next update time. One message, updated in place —
       not forty people discovering it separately.
    2. STOP THE BLEEDING: pause the merge queue rather than letting it
       evict PRs; disable the affected optional check; scale the pool.
    3. Decide on DEGRADATION: which checks may be skipped, by whom, and
       with what follow-up (this is the break-glass path from
       <quality gates>, already designed).

  DURING
    - keep a timeline; you will need it for the postmortem
    - prefer reverting the CI change over fixing forward — the same
      rule as trunk in <lesson 1>
    - resist "just merge with admin rights" as a general instruction:
      use the audited break-glass so the bypasses are countable

  AFTER
    - postmortem with the same template as a production incident
    - the action item that matters is usually DETECTION, not the fix
CI incidentImmediate mitigationDurable fix
Registry or package index downSwitch to the mirror/proxy; announcePull-through cache; bounded retries; fail fast with a named cause
Runner pool exhaustedRaise the ceiling; pause nightly jobsQueue-depth alerting; warm floor; cancel superseded runs

🔑 The most valuable postmortem action item is almost always about detection. In the four-hour registry incident the fix was trivial — point at the mirror — and the real finding was that nobody knew for 90 minutes, because retries hid the failure rate and no alert existed. Fixing the detection turns the next occurrence into 10 minutes; fixing only the cause leaves the next unrelated outage exactly as expensive.

❌ A pipeline with no owner, no SLIs and no alerts; blanket retries on every failure; the default six-hour timeout; logs that print nothing about the machine; and an incident process that consists of people complaining in a channel until someone notices. A 40-minute registry outage becomes four hours because retries keep every job "in progress", so no failure rate rises and nothing alerts — the queue simply fills until it is hours deep. Broken code gets retried three times and still fails, wasting runner minutes and confusing the author, while a genuinely transient runner loss is not retried at all because nothing distinguishes them. A hung job holds a concurrency group for six hours and blocks the merge queue all afternoon, and nobody can tell whether it is slow or stuck because the log has been silent since 13:02. When something does fail, the first engineer re-runs it, the second re-runs it, and the third finally reads a log that does not say which Node version, how much disk was free, or which of the four services was unreachable. There is no postmortem, so the same afternoon repeats next quarter.

✅ Treat the pipeline as production: SLIs, an owner, alerts on rates, classified failures, bounded and visible retries, layered timeouts, logs that answer the first question, and a real incident runbook. Publish availability, job start latency, duration, first-attempt pass rate, infrastructure failure rate and pipeline MTTR — and price an outage in blocked engineer-hours, which is what funds the owner. Classify every failure by signature before anything decides what to do with it, and shrink the unclassified bucket weekly (31% → 4% in six weeks). Retry only infra_* and external_* signatures, only on idempotent steps, with backoff, a cap and a metric per retry, so a rising retry rate becomes the early warning that something external has broken. Set job, step and command timeouts at roughly twice the p95, alert at 1.5×, and attach a watchdog that dumps stacks when output goes quiet — a timeout says it hung, a watchdog says where. Print an environment preamble, group the logs, annotate failures inline, and upload diagnostics on failure only: median time-to-diagnose fell from 34 minutes to 6. Then write the runbook — declare, announce once centrally, pause the merge queue, degrade through the audited break-glass path — and make the postmortem's first action item about detection.

Interview Questions

Beginner: Should CI automatically retry failed jobs?

Only for failures that are not about the change — and that means classifying before retrying.

CategoryRetry?
Deterministic (assertion, compile error, lint)Never — it will fail identically, slower
Nondeterministic in our testsNo — quarantine it; retrying hides a real signal
Transient infrastructure (runner lost, pull timeout, DNS)Yes — bounded, with backoff
External outage (registry 503, API throttling)Bounded retry, then fail fast with a named cause

Two conditions on top of that. The step must be idempotent — retrying a deploy, a migration or a notification can do the thing twice. And the retry must be visible: emit a metric per retry, because retries that are silent become camouflage. In one measured case, blanket retries kept jobs "in progress" during a 40-minute registry outage, so no failure rate rose, nothing alerted, and the incident lasted four hours.

The blanket retry-on: failure setting fails all three tests at once, which is why it is the default people regret.

Beginner: Why do CI jobs need timeouts, and how do you choose them?

Because the platform default is generous — six hours on GitHub Actions — and a hung job does more than waste that time. It occupies a runner slot, holds its concurrency group, and blocks anything queued behind it. One hung integration job blocked a merge queue for an entire afternoon while 14 PRs waited, and nobody could tell whether it was slow or stuck.

Set three layers:

  • Job timeout ≈ 2× the p95 duration — tight enough to fail fast, loose enough not to kill a legitimately slow run.
  • Step timeout on the step that can actually hang (the test run, the deploy wait).
  • Command timeout (timeout 60s …) around anything talking to the network.

And alert before the timeout — at about 1.5× p95 — because a timeout is a blunt instrument that tells you a job hung and nothing about why. Pair it with a watchdog that dumps process state and stacks when output goes quiet for a couple of minutes; that is what turns "it timed out again" into "it was waiting on an exhausted connection pool".

Mid: What SLIs would you define for a CI system, and what would you alert on?

Six, chosen so each one maps to something engineers actually experience:

Alert on rates and trends, never on individual runs. A single failure is normal; page on an infrastructure failure rate above 10% for ten minutes, a queue depth rising for fifteen minutes without draining, a collapse in first-attempt pass rate, and a retry rate spike — the last is usually the earliest signal that something external has broken.

The framing that gets this funded: price an outage in blocked engineer-hours. A 40-minute outage at 2pm cost roughly 51 engineer-hours (~$4,335) in one measured organisation — three times the quarter's customer-facing SLO breach, with no owner, no alert and no postmortem.

Mid: A job hangs intermittently and eventually times out. How do you find the cause?

A timeout tells you it hung; it never tells you where. So the first change is to make the next occurrence self-explanatory rather than trying to reproduce a hang.

  1. Add a watchdog: a background loop that, when the log has produced no output for ~120 seconds, dumps ps auxf, thread stacks (jstack, py-spy dump), and open sockets (ss -tanp). This costs one background process and usually identifies the cause on the very next occurrence.
  2. Check the usual suspects while waiting: a prompt waiting for input (fix with CI=true, --yes), a network call with no client timeout, a service that never became ready, non-daemon threads or unclosed pools keeping the process alive after tests pass, and slow post-job artifact uploads.
  3. Correlate: does it hang only on small runners, only under contention, only on a specific shard? That distinguishes a resource problem from a deadlock.
  4. Reproduce under constraint — the runner's image with --cpus 0.5 --memory 2g — which turns many rare hangs into reliable ones.
  5. Then fix the cause and lower the timeout, so the next unrelated hang is caught in minutes rather than hours.

In the measured case the watchdog showed every thread blocked on a connection pool that a leaked session had exhausted — a product bug, found on the first occurrence after adding twelve lines of diagnostics, having previously been "flaky CI" for weeks.

Senior: An upstream package registry is down for 40 minutes. What should your pipeline do?

The goal is that a 40-minute external outage costs 40 minutes, not four hours — which is what happened in the measured case, because retries hid it.

LayerBehaviour
Bounded retry3 attempts with exponential backoff and jitter — this alone absorbs most blips without anyone noticing
FallbackA package proxy in your own network serves cached copies of every version you have installed before; most builds proceed unaffected
Fail fast, honestlyIf both fail: stop immediately with an annotation naming the dependency and its status page — "this is not your change"
Announce onceA single central message with a next-update time, so forty engineers do not investigate the same thing
Degrade deliberatelyPause the merge queue rather than letting it evict PRs; decide which checks may be bypassed via the audited break-glass path
Detect it earlyAlert on the retry rate and on external_* classifications — the earliest available signal

What to avoid: unbounded retries (jobs hang to the six-hour default and the runner pool fills, converting a 40-minute problem into a queue that takes hours to drain), and silent retries (no failure rate rises, so nothing alerts and nobody knows for 90 minutes).

The durable fix is the package proxy and registry mirror from the runners lesson: after installing one, upstream outages stopped blocking CI entirely, and the same infrastructure removed 39 seconds from every job as a side effect.

Senior: How do you run a CI outage as an incident, and what does the postmortem look like?

Exactly like a production incident, because the users — every engineer in the company — are blocked the same way.

Declare on objective criteria, agreed in advance: infrastructure failure rate above 10% for ten minutes, queue depth rising for fifteen without draining, the merge queue blocked for twenty, or a required check that cannot pass for reasons unrelated to changes. Without criteria, the incident starts whenever someone loses patience, which is typically 40 minutes late.

In the first five minutes: post once, centrally, with what is broken, what to do meanwhile, who is on it and the next update time — updated in place, not a new thread. Stop the bleeding: pause the merge queue so it stops evicting PRs, disable an affected optional check, scale the pool. Then decide degradation explicitly, using the break-glass path that already exists rather than inventing "just use admin merge", which produces untracked bypasses that outlive the incident.

During: keep a timeline, and prefer reverting the CI change over fixing forward — the same rule as a red trunk.

The postmortem uses the production template, and its most valuable action item is almost always about detection rather than the cause. In the registry incident the fix was one config line pointing at a mirror; the finding worth acting on was that nobody knew for 90 minutes, because retries suppressed the failure rate and no alert existed. Fixing detection makes the next outage — which will have a different cause — ten minutes instead of four hours.

I would also record the cost in blocked engineer-hours. It is the number that turns "CI was flaky again" into a prioritised reliability backlog with an owner.

🏋️ Exercises

1 (easy): Build the CI reliability dashboard: six SLIs from data you already have, and price one outage in blocked engineer-hours.
Solution 
COLLECT — one script, run hourly, pushing to whatever you already use

  #!/usr/bin/env bash
  # ci/slis.sh
  set -euo pipefail
  W=7    # days

  runs=$(gh run list --workflow=ci.yml --limit 1000 \
      --json conclusion,createdAt,startedAt,updatedAt,attempt,event)

  # availability: runs that reached a conclusion at all
  echo "$runs" | jq -r --argjson w "$W" '
    [.[] | select(.conclusion != null)] | length as $done
    | length as $total
    | "availability \(100 * $done / $total | floor)%"'

  # job start latency
  echo "$runs" | jq -r '[.[] | (.startedAt|fromdate)-(.createdAt|fromdate)]
    | sort | .[(length*0.95|floor)] | "start_latency_p95 \(.)s"'

  # duration
  echo "$runs" | jq -r '[.[] | (.updatedAt|fromdate)-(.startedAt|fromdate)]
    | sort | "duration_p50 \(.[(length*0.5|floor)])s duration_p90 \(.[(length*0.9|floor)])s"'

  # first-attempt pass rate
  echo "$runs" | jq -r '[.[] | select(.attempt==1)] as $f
    | ([$f[] | select(.conclusion=="success")] | length) as $ok
    | "first_attempt_pass \(100 * $ok / ($f|length) | floor)%"'

🎯 Key Takeaways

  • The pipeline is a production system whose users are engineers — it needs SLIs, an owner, an on-call and an error budget, or its outages are found by complaint.
  • Six SLIs worth publishing: availability, job start latency p95, duration p50/p90, first-attempt pass rate, infrastructure failure rate, and pipeline MTTR.
  • Price outages in blocked engineer-hours. A 40-minute outage cost ~51 engineer-hours ($4,335); eleven of them cost $47,685 — eight times the same year's customer-facing SLO breaches, with no owner.
  • Alert on rates, never on individual runs: infra failure rate, first-attempt pass rate, queue depth that will not drain, and the retry rate.
  • Classify every failure by signature before deciding anything — deterministic, nondeterministic-in-our-tests, transient infrastructure, or external outage. Each has a different correct response.
  • Drive the unclassified bucket down weekly by reading those logs and adding signatures — 31% to 4% in six weeks — and treat a rising deterministic share as success.
  • Retry by signature, never by outcome. Blanket retries turn a broken commit into 12m30s of identical failures and hide real outages.
  • Retries must be visible. Silent retries kept jobs "in progress" during a 40-minute registry outage, so nothing alerted and the incident lasted four hours; a retry-rate alert caught the next one in six minutes.
  • Only retry idempotent steps. Deploys, migrations and notifications are not — route those through a lock and a fresh run instead.
  • Bound retries: three attempts, exponential backoff with jitter, a ceiling, and a fleet-wide alert threshold.
  • No timeout means six hours — one hung job held a concurrency group and blocked the merge queue all afternoon while 14 PRs waited.
  • Set three layers — job ≈ 2× p95, step, and command — and alert at 1.5× p95, before the timeout, so someone can attach to a live hung job instead of reading its corpse.
  • A watchdog tells you why it hung. Dumping ps, stacks and sockets after 120 s of log silence found an exhausted connection pool on the first occurrence, after three weeks of "flaky".
  • The environment preamble is the highest-value twelve lines in a pipeline: commit, attempt, runner, CPUs, memory, free disk, tool versions and filtered env — most "why here and not locally?" questions are answered before anything fails.
  • Group logs, annotate failures inline on the diff, export a correlation ID to every job, and write a job summary so the log usually does not need opening.
  • Upload diagnostics on failure only — container logs, disk, processes, sockets. Median time-to-diagnose fell from 34 minutes to 6, and re-runs as a first step fell from 3-in-5 to 1-in-12.
  • A failure message that names the cause — "this is not your change", with the dependency and its status page — is a reliability feature worth ~20 minutes per affected engineer.
  • Declare CI incidents on objective criteria, post once centrally with a next-update time, pause the merge queue early, and degrade through the pre-designed break-glass path rather than inventing admin merges.
  • Never raise retry counts during an outage — it fills the pool and hides recovery.
  • The best postmortem action item is about detection, because the next outage will have a different cause. A synthetic canary that installs a package and pulls an image every minute catches breakage you have not imagined yet.
