Anatomy of a Pipeline Foundations

What you'll master: the execution model every CI system shares once you look past the YAML — a job is a machine, a step is a shell command on that machine, and jobs share nothing except what you explicitly move between them, which is the single mental model that explains "why isn't my file there?", "why is my environment variable empty?" and "why did my cd not stick?"; the trigger semantics that decide what code runs with which permissions, including the distinction between an event that runs your config and one that runs a contributor's; concurrency groups, which cancelled 41% of runs as superseded and cut queue time from 6m20s to 47s; the job graph as a critical path rather than a list, where a fan-out/fan-in rewrite took a pipeline from 34 minutes to 11 with no faster tests; the real difference between artifacts and cache (one is a durable output, the other is a best-effort optimisation, and treating the cache as storage produced a build that passed only when a previous build had run); what is genuinely portable between GitHub Actions, GitLab CI, Jenkins and Buildkite, and the discipline — logic in scripts, YAML as orchestration — that keeps a pipeline runnable on a laptop; and how to debug a run without the 22-push "add echo, push, wait" loop. Prerequisites: What CI/CD Actually Is and branching; the examples use GitHub Actions with a translation table for other systems.

Part 1 — The Execution Model: Machines, Not Scripts

Every mainstream CI system is the same four layers with different words. Learn the layers and the YAML dialect becomes a detail.

  EVENT            something happened: a push, a PR, a schedule, a manual click
    │
    ▼
  WORKFLOW         a file that says "on this event, run these jobs"
    │
    ├── JOB A ──── a FRESH MACHINE (VM or container). Isolated. Ephemeral.
    │              ├── step 1   checkout          ─┐
    │              ├── step 2   setup language     │ same machine,
    │              ├── step 3   install deps       │ same filesystem,
    │              └── step 4   run tests         ─┘ same working dir
    │
    ├── JOB B ──── ANOTHER FRESH MACHINE. Knows nothing about Job A.
    │              No files, no env vars, no installed packages.
    │
    └── JOB C ──── runs only after A and B (needs: [a, b])
                   still a fresh machine — "after" is not "on the same box"
Question people askThe model's answer
"Why isn't the file my last job built here?"Different machine. Move it explicitly with an artifact.
"Why is my env var empty in the next step?"export FOO=1 dies with that step's shell. Write to the job's environment file instead.
"Why did my cd build/ not stick?"Each step is a new shell. Use a per-step working directory, or cd inside the same step.
"Why does it work locally?"Your laptop has state: tools, caches, credentials, a warm dependency directory. The runner has none of it.
"Why did it pass yesterday and fail today with no changes?"Something unpinned moved, or the previous run's cache was carrying the build. See Part 4.
THE THREE STEP-SCOPE MISTAKES, AND THEIR FIXES

  ❌ - run: export VERSION=1.4.2
     - run: echo "$VERSION"          # empty: new shell, new process

  ✅ - run: echo "VERSION=1.4.2" >> "$GITHUB_ENV"
     - run: echo "$VERSION"          # 1.4.2, for all later steps in THIS job

  ❌ - run: cd frontend
     - run: npm ci                   # runs in the repo root

  ✅ - run: npm ci
       working-directory: frontend

  ❌ job build:  produces dist/
     job deploy: needs: [build]; run: ls dist/     # No such file or directory

  ✅ job build:  upload-artifact  path: dist/
     job deploy: download-artifact                 # explicit, durable
🔑 "A job is a machine" is the whole model. Almost every confused hour spent on a pipeline comes from expecting continuity that does not exist — between steps (new shell), between jobs (new machine) or between runs (new everything). Once you internalise that nothing persists unless you transport it, the YAML stops being magical and becomes a description of which machines run what, in which order.

2.1 Path filters: do not run what cannot be affected

  on:
    pull_request:
      paths:
        - 'services/api/**'
        - 'libs/shared/**'
        - '.github/workflows/api.yml'

  MEASURED on a monorepo, one month:
    runs before path filters ......... 3,180
    runs after path filters .......... 1,412   (−56%)
    runner minutes .................. −52%
    median PR feedback time .......... 21 min -> 9 min

  THE TRAP: a REQUIRED status check that never runs because its paths did
  not match leaves the PR blocked forever, waiting for a check that will
  never report. Two ways out:
    - a "skip job" with the same check name that succeeds trivially, OR
    - use the platform's "required checks only when they run" semantics
  Test this deliberately: open a docs-only PR and confirm it can merge.

2.2 Concurrency: stop paying for runs nobody will read

  concurrency:
    group: ${{ github.workflow }}-${{ github.ref }}
    cancel-in-progress: true        # for PR branches

  what it does: a new push to the same branch CANCELS the in-flight run.
  Nobody was going to read the old result anyway.

  MEASURED, 4-week window, 40-engineer org:
    runs started ......................... 4,820
    cancelled as superseded .............. 1,976  (41%)
    runner minutes saved ................. 31,400  (~$250/month)
    p50 QUEUE time (waiting for a runner)  6m20s -> 47s   <-- the real win
    p50 feedback time .................... 38m -> 19m

  DO NOT cancel-in-progress on:
    - main-branch builds (you want every commit built)
    - deploys (cancelling mid-deploy leaves a half-deployed system)
    - anything holding a lock or a lease
  For deploys use a concurrency group WITHOUT cancellation, so they queue
  rather than overlap:
    concurrency: { group: deploy-production }      # cancel-in-progress: false
⚠️ Queue time is invisible in most dashboards and is often the largest term. The measured pipeline above "took 38 minutes" of which 6m20s was waiting for a free runner before anything started. Concurrency limits and superseded-run cancellation attack that directly, and they cost four lines of YAML — usually a bigger win than any test-level optimisation, which is why they come before performance work.

Part 3 — The Job Graph Is a Critical Path

A pipeline's duration is the longest chain through its graph, not the sum of its jobs. Teams routinely optimise the wrong node because the total runtime figure hides the shape.

BEFORE — everything in one job, because it grew that way (34 min)

  build ─ lint ─ unit ─ integration ─ e2e ─ docker ─ publish     34m
  (one machine, sequential steps, one cache, one long log)

AFTER — fan out, fan in (11 min)

              ┌── lint ............... 1m36s ──┐
  checkout ───┼── unit (4 shards) .... 4m10s ──┼── docker ─ publish
              ├── integration (3 sh).. 6m30s ──┤   3m20s    1m10s
              └── typecheck .......... 2m05s ──┘

  critical path = 6m30s (slowest parallel job) + 3m20s + 1m10s = 11m
  TOTAL COMPUTE went UP (more machines, each doing setup) — 41 to 58
  runner-minutes — and WALL-CLOCK went down 3x. That is usually the
  right trade: runner minutes are cheap, engineer minutes are not.
Graph patternWhat it is forCost
Fan-out (independent jobs, no needs)Run everything that does not depend on anything else, at onceRepeated setup per job — mitigate with caching and slim images
Fan-in (needs: [a, b, c])A gate that waits for several jobs — packaging, deploySlowest input dominates; find and shorten it
MatrixSame job across versions/platforms/shardsMultiplies runner usage; use fail-fast deliberately
ShardingSplit one slow suite across N machinesNeeds a way to split tests and merge reports
Conditional jobs (if:)Deploy only on main; heavy suites only on demandSkipped-but-required checks (see the trap above)
MATRIX AND SHARDING, THE TWO IDIOMS

  # matrix over versions — testing compatibility
  strategy:
    fail-fast: false            # do NOT cancel siblings; you want the full grid
    matrix:
      python: ["3.10", "3.11", "3.12"]
      os: [ubuntu-latest, macos-latest]
  # 6 jobs, and a red cell tells you WHICH combination is broken

  # matrix as sharding — splitting one suite for speed
  strategy:
    fail-fast: true             # a failure anywhere means the suite failed;
    matrix:                     # cancelling the rest saves minutes
      shard: [1, 2, 3, 4]
  steps:
    - run: pytest --splits 4 --group ${{ matrix.shard }}

  fail-fast is the setting people get backwards. Compatibility grid:
  false (you want the whole picture). Sharding: true (one red = red).

3.1 Passing values between jobs

  jobs:
    build:
      outputs:
        image: ${{ steps.meta.outputs.image }}     # declared output
      steps:
        - id: meta
          run: echo "image=registry/app@${DIGEST}" >> "$GITHUB_OUTPUT"

    deploy:
      needs: [build]
      steps:
        - run: deploy.sh "${{ needs.build.outputs.image }}"

  Outputs are for SMALL values: a digest, a version, a flag. Files go
  through artifacts. Secrets go through the secret store, never outputs —
  outputs are visible in logs and in the API.

Part 4 — Artifacts vs Cache: Durable Output vs Best-Effort Speed

These look similar — both move files between jobs and runs — and they have opposite contracts. Confusing them produces the worst class of pipeline bug: one that passes intermittently depending on history.

ArtifactCache
PurposeA result you produced and will use or shipAn optimisation — recreate the same thing faster
GuaranteeDurable for its retention period; a missing artifact is an errorBest effort. May be evicted, cold, or absent — and that must be fine
Correctness ruleThe build must fail if it is missingThe build must succeed with an empty cache, only slower
KeyingBy name, per runBy a content hash of the inputs (lockfile, toolchain, OS)
Typical contentsBinaries, images by digest, test reports, coverage, SBOMsDependency directories, compiler caches, Docker layers
Cross-runDownloadable from the run; usually not reused as inputExplicitly reused across runs — that is the point
THE BUG THIS DISTINCTION PREVENTS

  a team cached node_modules AND the compiled dist/ under one key.
  For nine weeks the pipeline was green. Then the cache was evicted
  (7-day idle eviction) and every build failed:

    Error: cannot find module './dist/server.js'

  The build step had been silently skipped for months by an
  `if: steps.cache.outputs.cache-hit != 'true'` guard, so nothing had
  actually compiled since the guard was added — and the artifact being
  deployed came from a cache, not from a build.

  RULES THAT PREVENT IT
   1. NEVER cache build OUTPUT. Cache only inputs and intermediates that
      a tool can regenerate deterministically (npm/pip/go module caches,
      ccache, Gradle caches, Docker layers).
   2. Run a scheduled "cold cache" build weekly with caching disabled.
      If it fails, your cache was load-bearing.
   3. Key caches on a hash of the manifest AND the toolchain AND the OS:
        key: ${{ runner.os }}-node20-${{ hashFiles('**/package-lock.json') }}
   4. Never restore a stale cache with a loose prefix for anything whose
      correctness depends on it — restore-keys are a speed feature and can
      silently give you last week's dependencies.
🔑 The test for whether you have this right: delete every cache and re-run. The pipeline must still be green, only slower. If deleting the cache makes it fail, then the cache was an artifact wearing a disguise, and your green ticks have been depending on the history of previous runs — which violates the reproducibility guarantee from lesson 1.

4.1 Build once, promote — implemented

  jobs:
    build:
      outputs: { digest: ${{ steps.push.outputs.digest }} }
      steps:
        - uses: docker/build-push-action@v6
          id: push
          with: { push: true, tags: registry/app:${{ github.sha }} }

    test:
      needs: [build]
      steps:
        - run: run-tests-against.sh "registry/app@${{ needs.build.outputs.digest }}"

    deploy-staging:
      needs: [build, test]
      steps:
        - run: deploy.sh staging "registry/app@${{ needs.build.outputs.digest }}"

    deploy-prod:
      needs: [deploy-staging]
      steps:
        - run: deploy.sh production "registry/app@${{ needs.build.outputs.digest }}"

  EVERY stage references the same immutable DIGEST — not a tag, which can
  be moved, and not a rebuild. This is the "build once, promote" guarantee
  expressed in about six lines.

THE DISCIPLINE THAT MAKES PORTABILITY REAL

  ❌ 140 lines of YAML containing the logic:
       - run: |
           VERSION=$(cat package.json | jq -r .version)
           if [ "$GITHUB_REF" = "refs/heads/main" ]; then TAG=latest; ...
           ... 60 more lines of shell, inside YAML, with ${{ }} interpolation
     you cannot run it locally, you cannot unit-test it, you cannot read
     it, and every ${{ }} is a lock-in point.

  ✅ YAML says WHAT and WHEN; a script says HOW:
       - run: ./ci/build.sh
       - run: ./ci/publish.sh
       - run: ./ci/deploy.sh staging

     ci/build.sh is ordinary shell (or Python, or Make, or a task runner):
       - runs on a laptop identically
       - is reviewable and testable
       - is portable to any CI system in an afternoon
       - takes inputs from ENV VARS, not from ${{ }} expressions

  MEASURED: a team that moved logic into ci/*.sh migrated from Jenkins to
  GitHub Actions in 6 days. The YAML they replaced was 900 lines; the new
  YAML was 210, and the scripts were unchanged.
💡 Lock-in is not the marketplace action you use for checkout; it is the business logic you wrote inside YAML expressions. Use the platform's actions freely for platform things — checkout, auth, caching, artifact upload — and keep everything that is your build in files that run without the platform. The side benefit is bigger than portability: engineers can run the pipeline's steps on their own machine, which removes most of the "push and pray" loop in Part 6.

Part 6 — Debugging a Pipeline Without 22 Pushes

THE LOOP EVERYONE STARTS WITH (and its cost)

  add echo -> commit -> push -> wait 34 min -> read log -> repeat
  measured on one real incident: 22 pushes, 6h40m elapsed, to find a
  missing environment variable.

THE LADDER, CHEAPEST FIRST

  1. RUN IT LOCALLY. If the logic lives in ci/*.sh (Part 5), this is
     just `./ci/build.sh`. This alone resolves most failures.

  2. REPRODUCE THE ENVIRONMENT, not just the command:
       docker run --rm -it -v "$PWD:/w" -w /w ubuntu:24.04 bash
       # then run the same script. Most "works locally" bugs are a tool
       # version or a missing package, and this finds them in minutes.

  3. RE-RUN WITH DEBUG LOGGING (no code change, no push):
       gh run rerun 9481123 --debug
       # or set ACTIONS_STEP_DEBUG / CI_DEBUG_TRACE

  4. INTERACTIVE SESSION ON THE RUNNER (when it is genuinely
     environment-specific): a debug/tmate step, gated so it never runs
     unattended:
       - uses: mxschmitt/action-tmate@v3
         if: ${{ failure() && github.actor == github.triggering_actor
                 && inputs.debug == true }}
         timeout-minutes: 15
     NEVER leave this ungated on a public repo — it is an interactive
     shell on a machine holding your tokens.

  5. BISECT THE PIPELINE, not the code: comment out jobs, or push a
     branch with a minimal workflow that runs only the failing step.

  MAKE FAILURES SELF-EXPLANATORY SO STEP 1 IS USUALLY ENOUGH
    set -euo pipefail                 # fail on the failing command
    trap 'echo "::error::failed at line $LINENO: $BASH_COMMAND"' ERR
    echo "::group::dependency versions"   # collapsible log sections
    node --version; npm --version; printenv | grep -v -i 'token\|secret'
    echo "::endgroup::"

❌ One 34-minute job with 140 lines of shell embedded in YAML, no concurrency group, no path filters, exports that vanish between steps, a cache holding the build output, and a debugging process of push-and-wait. Everything is sequential because it grew that way, so lint's 96 seconds and e2e's 6 minutes are in the same chain as the Docker build. Every push starts a new run without cancelling the superseded one, so 41% of the runner fleet is producing results nobody will read while real runs wait 6m20s in a queue. A docs-only PR runs the full suite. The logic lives inside ${{ }} expressions, so nobody can run it locally and the only debugging loop is add-echo-push-wait — 22 pushes and 6h40m for one missing variable. Meanwhile the cache contains dist/, so the deployed artifact has not actually been compiled for nine weeks, and the day the cache is evicted every build fails with a missing module. And the deploy job pulls registry/app:latest, which is a different image from the one the tests passed against.

✅ A graph whose critical path you know, cheap runs suppressed before they start, explicit data movement, and logic in scripts you can run on a laptop. Fan out the independent work and fan in at packaging — that took a measured pipeline from 34 to 11 minutes without a single test getting faster, at the cost of runner-minutes, which are the cheap resource. Add a concurrency group with cancel-in-progress for PR branches (41% of runs cancelled, queue time 6m20s → 47s) and a non-cancelling group for deploys. Filter by path, then deliberately open a docs-only PR to prove a required check cannot block it forever. Move values between steps with the job's environment file and between jobs with declared outputs; move files with artifacts, and keep the cache strictly for regenerable inputs — verified by a weekly cold-cache build, because a cache that is load-bearing is an artifact in disguise. Build once and promote the immutable digest through test, staging and production. Keep YAML to orchestration and put every real decision in ci/*.sh, which makes the first debugging step "run it locally" instead of the twenty-second push.

Interview Questions

Beginner: Walk through what happens between pushing a commit and a test result appearing.

Six stages, and naming them is what the question is really testing:

  1. Event. The push (or PR update) is recorded by the Git host and emitted as an event.
  2. Workflow selection. The CI system reads the workflow files at the relevant ref and decides which are triggered by this event, applying branch and path filters.
  3. Scheduling. Jobs with no unmet dependencies become runnable and wait for a runner. This queue time is invisible in most dashboards and is frequently the largest single term.
  4. Runner assignment and setup. A fresh VM or container is allocated, the repository is checked out, toolchains are installed, caches are restored.
  5. Steps. Each step is a command in a new shell on that same machine, sharing its filesystem and working directory but not its shell state.
  6. Reporting. Exit codes become the job's conclusion, logs and artifacts are uploaded, and the status check is posted back to the commit.

The two things worth adding unprompted: a job is a fresh machine, so anything you want in another job must be transported explicitly (artifacts for files, outputs for small values); and queue time is part of feedback time — a "10-minute pipeline" that waits six minutes for a runner is a 16-minute feedback loop.

Beginner: What is the difference between an artifact and a cache?

They move files, but their contracts are opposite.

An artifact is a result: a binary, an image reference, a test report, an SBOM. It is durable for its retention period, it is what you ship or inspect, and a missing artifact is an error — the pipeline should fail.

A cache is an optimisation: a dependency directory, a compiler cache, Docker layers. It is best-effort — it can be evicted, cold or absent — and the build must still succeed without it, only slower.

The failure this distinction prevents: a team cached their compiled dist/ along with node_modules and guarded the build step with "skip if cache hit". Nothing compiled for nine weeks; when the cache was evicted, every build failed with a missing module — and the deployed artifact had been coming from a cache, not from a build.

The test: delete every cache and re-run. If the pipeline still passes, only slower, the separation is correct. If it fails, the cache was an artifact in disguise and your green ticks depended on the history of previous runs.

Mid: A pipeline takes 34 minutes. How do you find out why, and what would you change first?

Measure the critical path, not the total. Jobs run in parallel, so the sum of job durations is irrelevant — the pipeline is as slow as its longest chain, including queue time.

StepWhat to look for
Break the run into per-job durationsUsually one or two jobs dominate; in the measured case integration tests were 18m24s of 34m
Separate queue time from run time6m20s of waiting for a runner needs a completely different fix from 18 minutes of testing
Look at the graph shapeA single sequential job means everything is on the critical path by construction
Check setup overhead per jobIf each job spends 90 seconds installing tools, caching or a prebuilt image pays back immediately

The order of changes: (1) a concurrency group with cancel-in-progress and path filters — minutes of work, and in the measured org they cut queue time from 6m20s to 47s and runs by 56%; (2) fan out the independent jobs so lint, typecheck and unit tests stop sitting in front of the build; (3) shard the dominant suite across several machines; (4) then caching and image slimming. Together those took 34 minutes to 11 without any individual test getting faster.

The trade to state explicitly: total runner-minutes went up (41 → 58) because each machine repeats setup. That is nearly always correct — runner minutes are cheap, and engineer waiting time was measured at 18× the compute cost in lesson 1.

Mid: Your pipeline passes on a re-run with no code changes. What are the possibilities and how do you distinguish them?
CauseSignatureHow to confirm

The senior framing: "passes on re-run" is not a resolution, it is a data point. Every re-run that goes green without diagnosis trains the team to retry rather than read, and one of those retries will eventually push a genuine failure through. Record the failure, quarantine the test if it is a test, and treat repeated infrastructure flakes as a reliability problem with an owner.

Senior: How do you structure pipelines across 60 repositories so they are consistent but not rigid?

The goal is one place to fix a problem for everyone, without a central team becoming a queue that every repository waits in.

LayerContentsOwned by
Reusable workflows (called, not copied)The standard shapes: "node service CI", "python library release" — including the security and provenance stepsThe platform team
Composite actionsSmall shared pieces: auth via OIDC, cache setup, test reportingThe platform team
Repo workflowA dozen lines: which reusable workflow, with which inputsThe repo's team
ci/*.sh in the repoAnything specific to that codebaseThe repo's team

Versioning is the part that decides whether this works. Repositories reference the reusable workflow by a tag (@v3), not by @main, so the platform team cannot break 60 repositories with one commit — and repositories can adopt v4 when they are ready. Publish a changelog and a deprecation window, exactly as you would for a library, because that is what it is.

Keep an escape hatch and measure it. Teams with unusual needs must be able to opt out and write their own; then track who does and why. High opt-out on one feature is feedback about the paved road, not disobedience — and a standard that cannot be escaped gets circumvented in ways you cannot see.

What I would avoid: copying a template into every repository at bootstrap (the copies diverge instantly and fixing anything means 60 PRs); a bot that force-syncs YAML across repositories (it fights local changes and erodes ownership); and putting business logic into the shared actions, which turns the platform team into the owner of everyone's build.

Senior: An engineer says "it works on my machine but fails in CI". How do you get to the answer systematically?

Network postureNo access to an internal registry; different DNS; no credentialsLog the resolved endpoints; fail fast with a clear message when a dependency is unreachable
Permissions and identityYour laptop has broad credentials; the pipeline has a scoped tokenPrint the effective identity (never the token) — see pipeline identity

The structural fix is the one from Part 5: if the logic lives in ci/*.sh and CI runs it inside the same container image an engineer can pull, the two environments converge by construction and this class of question mostly disappears. The remaining differences — cores, memory, network, identity — are then few enough to enumerate on one page and print at the top of every run.

Solution

name: model-probe
on: workflow_dispatch

jobs:
  step-scope:
    runs-on: ubuntu-latest
    steps:
      - run: |
          export GREETING=hello
          echo "same step: $GREETING"
          mkdir -p /tmp/proof && echo data > /tmp/proof/file.txt
          cd /tmp/proof && pwd
      - run: |
          echo "next step, env:  [$GREETING]"
          echo "next step, pwd:  $(pwd)"
          cat /tmp/proof/file.txt

  job-scope:
    needs: [step-scope]
    runs-on: ubuntu-latest
    steps:
      - run: cat /tmp/proof/file.txt || echo "NOT PRESENT in a new job"

OUTPUT

  step-scope / step 1
    same step: hello
    /tmp/proof
  step-scope / step 2
    next step, env:  []                <-- gone: new shell, new process
    next step, pwd:  /home/runner/work/repo/repo   <-- cd did not persist
    data                               <-- the FILE survived: same machine
  job-scope / step 1
    NOT PRESENT in a new job           <-- new machine, nothing survives

The middle result is the one that surprises people: files persist between steps, shell state does not. Same machine, different process.

THE CORRECT VERSIONS

  # value that must outlive the step -> the job environment file
  - run: echo "GREETING=hello" >> "$GITHUB_ENV"
  - run: echo "$GREETING"                       # hello

  # a directory for one step -> working-directory, not cd
  - run: pwd
    working-directory: services/api

  # a file that must reach ANOTHER job -> an artifact
  - uses: actions/upload-artifact@v4
    with: { name: proof, path: /tmp/proof/ }
  # ... in the other job:
  - uses: actions/download-artifact@v4
    with: { name: proof, path: /tmp/proof/ }

  # a small VALUE that must reach another job -> a declared output
  outputs: { version: ${{ steps.v.outputs.version }} }
  - id: v
    run: echo "version=1.4.2" >> "$GITHUB_OUTPUT"

Two refinements once the shape is right. Setup is now paid five times, so a prebuilt image containing the toolchain (or a warm dependency cache) removes 60–90 seconds from every parallel job at once. 4 (medium): Audit cache-versus-artifact usage in a real pipeline. Prove whether the cache is load-bearing, and fix it if it is.
Solution

One command answers the whole question: destroy the caches and re-run.

STEP 1 — THE COLD-CACHE TEST

$ gh cache list
ID       KEY                                              SIZE     ACCESSED
88213    Linux-node20-9f2c1a...                           412 MB   2 hours ago
88109    Linux-build-output-4f21b9...                     186 MB   2 hours ago   (!)
88044    Linux-pip-31ab77...                               94 MB   1 day ago

$ gh cache delete --all
$ gh workflow run ci.yml --ref main && gh run watch

  ✗ deploy: Error: cannot find module './dist/server.js'
  BUILD FAILED WITH AN EMPTY CACHE -> the cache was LOAD-BEARING.

STEP 2 — FIND THE GUARD THAT DID IT

$ grep -B3 -A6 'cache-hit' .github/workflows/ci.yml
  - uses: actions/cache@v4
    id: cache
    with:
      path: |
        node_modules
        dist            # <-- BUILD OUTPUT in a cache
      key: ${{ runner.os }}-build-${{ hashFiles('src/**') }}
  - name: Build
    if: steps.cache.outputs.cache-hit != 'true'    # <-- skipped on a hit
    run: npm run build

  Consequence: on any cache hit the build did not run, and the deployed
  dist/ came from a cache entry — not from this commit's source.
  git log shows the guard was added 9 weeks ago.

STEP 3 — THE FIX: SEPARATE THE TWO CONCERNS

  # CACHE — inputs only, always safe to miss, never guards a build step
  - uses: actions/cache@v4
    with:
      path: ~/.npm
      key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
      restore-keys: ${{ runner.os }}-npm-     # a stale hit is fine: npm ci
                                              # still resolves from the lockfile
  - run: npm ci
  - run: npm run build                        # ALWAYS runs. No condition.

  # ARTIFACT — the output, moved deliberately to the jobs that need it
  - uses: actions/upload-artifact@v4
    with: { name: dist, path: dist/, retention-days: 7 }

STEP 4 — MAKE IT STAY FIXED

  .github/workflows/cold-cache.yml
    on:
      schedule: [ { cron: '0 3 * * 1' } ]      # Monday 03:00
    jobs:
      cold:
        env: { SKIP_CACHE: 'true' }            # every cache step is gated on it
        steps: [ ... the normal pipeline ... ]

  a red cold-cache build now means "something is load-bearing again",
  which is exactly the alarm you want, a week after the mistake rather
  than nine weeks.
Cache entryLegitimate?Why
~/.npm, ~/.cache/pip, Go module cacheYesRegenerable inputs; a miss costs only download time
node_modulesBorderlineFaster, but it must be keyed exactly on the lockfile — a loose restore-key can install last week's tree
ccache / Gradle / Turbo cachesYesDeterministic intermediates keyed by content
Docker layer cacheYesProvided the final image is still built and pushed by digest
dist/, compiled binaries, generated migrationsNoOutputs. Use artifacts, or they become the deployed thing without ever being built
🔑 Restore-keys are a speed feature with a correctness edge. They let a near-miss reuse an older cache, which is excellent for a package download cache and dangerous for anything whose contents must match the current manifest. Use them where a stale hit is merely suboptimal, never where a stale hit changes what gets built.

🎯 Key Takeaways

  • A job is a machine; a step is a new shell on that machine. Files persist between steps, shell state does not, and nothing at all persists between jobs — this one model explains almost every confusing pipeline behaviour.
  • Move values between steps with the job environment file, between jobs with declared outputs, and files with artifacts; use working-directory rather than a bare cd.
  • Trigger choice decides whose code runs with which permissions. pull_request gives forks a read-only token and no secrets; pull_request_target runs the base config with write access against untrusted code and is a notorious footgun.
  • Path filters cut runs 56% and halved feedback time — but a required check that never runs blocks a PR forever, so test the docs-only case deliberately and provide a skip job with the same check name.
  • Concurrency groups are the cheapest win available: cancelling superseded PR runs cancelled 41% of runs, cut runner minutes 42%, and took queue time from 6m20s to 47s. Never enable cancellation for deploys — give them a non-cancelling group so they serialise.
  • Queue time is part of feedback time and is invisible in most dashboards; measure it separately from run time, because the fixes are completely different.
  • Duration is the critical path, not the sum of jobs. Fan-out plus fan-in took a measured pipeline from 34 minutes to 11 with no test made faster — at the cost of runner minutes rising 41%, which is the right trade.
  • fail-fast is usually set backwards: false for a compatibility matrix (you want the whole grid), true for sharding (one red shard means the suite failed).
  • Shard by recorded test duration, not by file count, or one unbalanced shard becomes the new critical path — and remember to merge the reports.
  • An artifact is a durable result; a cache is a best-effort optimisation. A missing artifact must fail the build; a missing cache must only make it slower.
  • Never cache build output. A cached dist/ plus an if: cache-hit guard meant nothing compiled for nine weeks, and the deployed artifact came from a cache — discovered only when eviction broke every build.
  • The test is: delete every cache and re-run. Still green, only slower, means the separation is right. Schedule a weekly cold-cache build so a load-bearing cache is caught in days rather than months.
  • Restore-keys are a speed feature with a correctness edge — fine for a download cache, dangerous anywhere a stale hit changes what gets built.
  • Build once, promote the digest. Every downstream job references the same immutable digest rather than a tag or a rebuild — six lines that implement the immutability guarantee.
  • The concepts port; the syntax does not. Workflow/pipeline, job, needs, matrix, artifact and cache exist in every system under different names.
  • Real lock-in is business logic inside YAML expressions, not the marketplace actions you use for checkout and auth. Keep YAML for orchestration and put decisions in ci/*.sh — one team's migration then took 6 days instead of a quarter, with the scripts unchanged.
  • Scripts taking environment variables are runnable on a laptop, unit-testable, and reviewable — which turns the first debugging step into "run it" instead of "push and wait".
  • Debug on a ladder, cheapest first: read the failing log, correlate across runs, reproduce in the runner's image with matching CPU/memory limits, re-run with debug logging, then a gated interactive session. Add-echo-and-push is the last rung — one real case cost 22 pushes and 6h40m.
  • Gate any interactive-debug step on the actor, an explicit input and a short timeout: an ungated one is a shell on a machine holding your tokens.
  • Make failures self-explanatory: set -euo pipefail, an ERR trap naming the line, grouped version output, and readiness waits with deadlines instead of sleep.
