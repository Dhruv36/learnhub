Routing & URL State State Management

What you'll master: what a client router actually does — three moves on the History API — and the browser behaviour you silently took over and now owe back: scroll restoration, focus, and announcing navigation to a screen reader; route ranking, so config order stops mattering; nested routes and Outlet; the URL as the most under-used state container, and why useSearchParams hands you a snapshot, so two updates in one handler eat each other; loaders and actions, which start requests at navigation time and delete the fetch-in-effect waterfall; defer and per-route Suspense; why an effect-based auth redirect flashes the protected page; and route-based code splitting. Prerequisites: State Architecture, Data Fetching. React Router 6.4+ / 7.

Part 1 — What the Browser Did, and What You Just Took Over

  A MULTI-PAGE APP ASKS THE SERVER FOR EVERY NAVIGATION. An SPA has ONE
  document, and "navigation" is three moves you perform yourself:

    1. INTERCEPT THE CLICK.  <Link> renders a real <a href> and calls
       e.preventDefault() so the browser does not unload the document.
    2. PUSH THE URL.         history.pushState(state, "", "/products/42")
       changes the address bar and adds a history entry. It issues NO
       network request. Nothing is fetched. Nothing is parsed.
    3. RE-RENDER.            The router holds the location in state, so
       pushing it triggers a render that swaps the matched element.

    Back and forward do not go through steps 1 or 2 — the browser handles
    them and fires a "popstate" event. The router subscribes and does step
    3 only. That is why back is instant, and also why back is where the
    bugs live: it is the one path your click handler never sees.

  THAT IS THE WHOLE TRICK. The URL becomes a state input — the most
  privileged one, because it is shareable, bookmarkable, refresh-proof and
  back-button-correct — and the router is a controlled component over it.

  WHAT YOU GAVE UP WITHOUT BEING ASKED:

    The browser implemented a pile of navigation behaviour for free. The
    moment you call preventDefault, all of it is yours. Nothing errors.
    The app "works". It is simply worse in ways that never show up in a
    component test and always show up in an accessibility audit.

    SCROLL POSITION. A real navigation scrolls to the top; a real BACK
    restores the exact pixel offset you left. pushState does neither. The
    default SPA experience is: click a product from halfway down a list,
    land on the product page already scrolled halfway down. Then press
    back and land at the top of the list you had been reading.

    FOCUS. A real navigation resets focus to the document. pushState
    leaves focus where it was — usually on a link that no longer exists,
    at which point focus falls back to <body> and the next Tab press
    starts again from the top of the page.

    ANNOUNCEMENT. A screen reader announces the new document title on a
    real navigation. After pushState it announces NOTHING. To a screen
    reader user, clicking that link did nothing at all.

    THE STATUS CODE. A server 404 is a real 404. A client-side "*" route
    renders your NotFound component with HTTP 200, so crawlers index it.

  THE SCROLL FIX IS A COMPONENT; THE OTHER TWO ARE NOT.

    <ScrollRestoration />   // data routers. Renders nothing. It sets
                            // history.scrollRestoration = "manual" and
                            // saves window.scrollY per history key into
                            // sessionStorage, restoring it on POP.

    Note WHY sessionStorage: the offsets must survive a reload of the same
    tab and must not leak into another tab. Note also that restore happens
    after layout — if your list renders 40 rows in a lazy second pass, the
    document is 200px tall at restore time and the offset clamps to the
    bottom. That is the most common "scroll restoration is broken" report,
    and the fix is reserving height, not the router.

  FOCUS AND ANNOUNCEMENT YOU WRITE ONCE, IN THE LAYOUT ROUTE:

    function Shell() {
      const { pathname } = useLocation();
      const heading = useRef(null);
      const [message, setMessage] = useState("");

      useEffect(() => {
        heading.current?.focus();                 // focus into the new page
        setMessage(document.title + " loaded");   // announce it
      }, [pathname]);

      return (
        <>
          <a href="#main" className="skip">Skip to content</a>
          <div aria-live="polite" className="sr-only">{message}</div>
          <main id="main">
            <h1 tabIndex={-1} ref={heading}>...</h1>
            <Outlet />
          </main>
        </>
      );
    }

    tabIndex={-1} makes the heading programmatically focusable without
    adding it to the Tab order. Depend on pathname, NOT on the location
    object — location is a fresh reference on every search-param change,
    so depending on it re-announces the page on every filter tweak.

Part 2 — Routes, Ranking, and Nesting

  A ROUTE CONFIG IS DATA. That matters more than it sounds. Because the
  routes are an array rather than JSX discovered during rendering, the
  router can read the whole tree BEFORE rendering anything: match the URL,
  find every matching route, and start their data loading. A v5-style
  <Switch> could not — it had to render in order to learn what matched,
  which is precisely why v5 had no loaders.

    const router = createBrowserRouter([
      {
        path: "/",
        element: <Shell />,            // LAYOUT ROUTE: chrome, no path of its own
        errorElement: <RouteError />,   // catches throws from anything below
        children: [
          { index: true, element: <Home /> },             // exactly "/"
          { path: "products", children: [
              { index: true, element: <ProductList /> },   // /products
              { path: ":id", element: <Product /> },       // /products/42
              { path: ":id/edit", element: <Edit /> },
          ]},
          { path: "docs/*", element: <Docs /> },           // splat
          { path: "*", element: <NotFound /> },
        ],
      },
    ]);

  ORDER DOES NOT MATTER. This is the largest behavioural change from v5,
  and people still write configs defensively as though it did. v6 RANKS
  every route that matches and picks the best:

    URL /products/new     against    /products/:id    and    /products/new

      SEGMENT KIND     STATIC   DYNAMIC   SPLAT
      score per seg      10        3       -2

      /products/:id  ->  10 + 3  = 13
      /products/new  ->  10 + 10 = 20    WINS, wherever it sits in the array

    The exact numbers are an implementation detail; the ORDERING they
    produce is the contract — static beats dynamic beats splat, and a
    longer match beats a shorter one. A splat scores NEGATIVE, which is
    why "*" can never steal a URL that another route can serve. The "put
    specific routes first" rule you learned in v5 is now dead weight.

  NESTING IS URL NESTING AND UI NESTING AT ONCE. A child path is relative
  to its parent, and the child element renders INTO the parent's Outlet:

    URL /products/42/edit matches THREE routes, and all three render,
    outermost first:

      Shell                  renders <Outlet/>, which contains...
        products layout      renders <Outlet/>, which contains...
          Edit

    THE CONSEQUENCE PEOPLE MISS: the Shell does NOT unmount when you move
    between its children. Its state survives — an open sidebar stays open,
    a scroll container keeps its offset, an audio player keeps playing. If
    you are lifting state into a context purely so it survives navigation,
    check first whether a layout route already gives you that for free.

  AN INDEX ROUTE IS NOT "THE DEFAULT CHILD". It is the child that renders
  when the URL is EXACTLY the parent's path. Without one, /products draws
  the layout around an EMPTY Outlet — chrome with a blank middle, which is
  roughly a third of all "my route renders nothing" reports.

  RELATIVE LINKS FOLLOW THE ROUTE TREE, NOT THE URL:

    <Link to="edit">    from /products/42  ->  /products/42/edit
    <Link to="..">      from /products/42  ->  /products
    <Link to="/edit">   from anywhere      ->  /edit   (leading slash = absolute)

    ".." pops one ROUTE segment, not one URL segment. Inside a layout
    route that owns no path of its own those two differ, and it is much
    cheaper to know that now than to debug it later. Pass relative="path"
    to opt back into plain URL semantics.

  NavLink GIVES YOU ACTIVE STATE without reading the location yourself:

    <NavLink to="/products" end
             className={({ isActive, isPending }) =>
               isActive ? "on" : isPending ? "loading" : ""}>

    "end" matters: without it, /products stays active while you are on
    /products/42, because a parent path is a prefix match. With it, only
    the exact URL is active. Breadcrumbs want the prefix behaviour; a tab
    bar almost always wants "end". isPending is true while a navigation to
    that link is in flight — the cheapest possible "this tab is loading".

Part 3 — The URL Is a State Container, and useSearchParams Is a Snapshot

  Most apps keep filters, sort order, pagination and open panels in
  useState. Every one of those is the WRONG container, and the test is
  three questions:

    CAN A USER SEND THIS VIEW TO A COLLEAGUE?
    DOES REFRESH HAVE TO PRESERVE IT?
    SHOULD THE BACK BUTTON UNDO IT?

  Any yes means the value belongs in the URL. useState fails all three:
  a link to "the failed builds from last week, sorted by duration" is
  just a link to the dashboard, and the recipient starts over.

    useState                        URL
    ---------------------------------------------------------------
    dies on refresh                 survives refresh
    unshareable                     shareable, bookmarkable
    invisible to back button        back button undoes it
    invisible to the server         readable during SSR
    invisible in a bug report       the bug report IS the URL

  WHAT DOES NOT BELONG IN THE URL: anything secret (it lands in browser
  history, server logs and Referer headers), anything huge (browsers cap
  URLs around 2000 characters in practice, and a serialised table state
  gets there faster than you expect), and genuinely transient UI state
  like whether a tooltip is showing.
  useSearchParams LOOKS like useState. It is not.

    const [searchParams, setSearchParams] = useSearchParams();

  searchParams is a URLSearchParams SNAPSHOT taken at render time. It is
  a value captured by this render's closure, exactly like a state value —
  and that is where the trap lives.

  BROKEN — two updates in one handler, and the first is lost:

    function onFilterChange(status, page) {
      setSearchParams(prev => {                 // fine
        prev.set("status", status);
        return prev;
      });
      setSearchParams(searchParams => ...);     // also fine
    }

  THE ACTUAL BREAKAGE is the non-functional form:

    setSearchParams({ status });                // replaces EVERYTHING
    setSearchParams({ page: 1 });               // status is now GONE

  Object form REPLACES the whole query string. It does not merge. And
  reading the closed-over snapshot has the same problem as stale state:

    setSearchParams(withKey(searchParams, "status", status));
    setSearchParams(withKey(searchParams, "page", "1"));
    // both built from the SAME snapshot; the second wins outright

  CORRECT — functional form, mutate the draft, return it:

    setSearchParams(prev => {
      prev.set("status", status);
      prev.set("page", "1");
      return prev;
    });

  ONE CAVEAT the docs are quiet about: the functional updater hands you a
  MUTABLE URLSearchParams and expects you to return it. This is unlike
  useState, where mutating the previous value is a bug. Here it is the
  documented path.

  DEBOUNCE, AND CHOOSE PUSH VERSUS REPLACE DELIBERATELY.

  A search box wired straight to setSearchParams pushes one history entry
  PER KEYSTROKE. Typing "postgres" leaves eight entries, and the back
  button becomes a backspace key. Users report this as "back is broken".

    const [q, setQ] = useState(searchParams.get("q") ?? "");

    // typing: replace, so no history entry accumulates
    useEffect(() => {
      const t = setTimeout(() => {
        setSearchParams(prev => {
          if (q) prev.set("q", q); else prev.delete("q");
          return prev;
        }, { replace: true });
      }, 300);
      return () => clearTimeout(t);
    }, [q]);

    // committing (Enter, or clicking a filter chip): push
    setSearchParams(next, { replace: false });

  THE RULE: REPLACE WHILE A VALUE IS STILL SETTLING, PUSH WHEN THE USER
  HAS COMMITTED TO IT. A filter chip click is a decision — push it. A
  keystroke is not — replace it.

  Note the local-state mirror above is deliberate: the input stays
  responsive at 60fps while the URL trails 300ms behind. This is the ONE
  legitimate reason to duplicate URL state into useState, and it is
  one-directional — the URL never writes back into q except on mount.

Part 4 — Loaders and Actions: Fetching Starts at Navigation, Not at Render

  THE WATERFALL YOU HAVE BEEN SHIPPING. With fetch-in-effect, nothing is
  requested until the component has mounted — and a nested route mounts
  its children only after the parent has rendered:

    t=0ms     click /projects/42
    t=0ms     router renders Project
    t=5ms     Project mounts, effect fires, GET /projects/42
    t=205ms   project arrives, Project re-renders, Tasks mounts
    t=210ms   Tasks effect fires, GET /projects/42/tasks
    t=410ms   tasks arrive
              ----------------------------------------
              410ms, and the two requests were INDEPENDENT

  The requests never needed to be sequential. They were serialised by
  component mounting order, which is an accident of your tree shape.

  WITH LOADERS, the router knows the full matched route set BEFORE it
  renders anything, so it calls every loader in PARALLEL:

    t=0ms     click /projects/42
    t=0ms     router matches [Root, Project, Tasks], fires 3 loaders AT ONCE
    t=200ms   all resolved, render once, fully populated
              ----------------------------------------
              200ms, and ZERO loading spinners in the tree

  This is a ~2x improvement that costs you no cleverness. It is the
  single strongest argument for a data router.
    const router = createBrowserRouter([
      {
        path: "projects/:id",
        element: <Project />,
        loader: async ({ params, request }) => {
          // request.signal is aborted if the user navigates away —
          // wire it up, or you keep paying for abandoned navigations
          const res = await fetch(`/api/projects/${params.id}`, {
            signal: request.signal,
          });
          if (res.status === 404) {
            throw new Response("Not Found", { status: 404 });
          }
          return res.json();
        },
        errorElement: <ProjectError />,
        children: [
          { path: "tasks", element: <Tasks />, loader: tasksLoader },
        ],
      },
    ]);

    function Project() {
      const project = useLoaderData();   // already here, never null
      return <h1>{project.name}</h1>;
    }

  THREE THINGS THAT DISAPPEAR FROM YOUR COMPONENT:

    - the isLoading branch      (data is present at first render)
    - the error branch          (a thrown Response hits errorElement)
    - the null-check on data    (useLoaderData is never undefined)

  THROWING IS THE CONTROL FLOW. throw new Response(...) routes to the
  nearest errorElement; throw redirect("/login") navigates. A loader that
  throws is not a crash, it is a jump.
  ACTIONS ARE THE WRITE HALF, and they close the loop automatically:

    { path: "projects/:id/edit",
      element: <Edit />,
      action: async ({ request, params }) => {
        const form = await request.formData();
        const res = await fetch(`/api/projects/${params.id}`, {
          method: "PUT",
          body: form,
        });
        if (!res.ok) return { error: "Save failed" };   // RETURN = stay
        return redirect(`/projects/${params.id}`);      // THROW/RETURN redirect = go
      },
    }

    <Form method="post">
      <input name="title" defaultValue={project.title} />
      <button>Save</button>
    </Form>

  AFTER AN ACTION RESOLVES, THE ROUTER REVALIDATES EVERY LOADER ON THE
  PAGE. You do not invalidate a cache key, because there is no cache key.
  This is the browser's own model — submit, then re-render the page —
  restored on top of client routing.

  useNavigation() gives you the pending state without any useState:

    const nav = useNavigation();
    nav.state === "submitting"   // action in flight
    nav.state === "loading"      // revalidating, or navigating
    nav.formData                 // what was submitted — optimistic UI, free

  useFetcher() runs a loader or action WITHOUT navigating: a "mark done"
  checkbox in a list, a newsletter signup in a footer. Same revalidation,
  no URL change. Multiple fetchers on one page each track their own state,
  which is what makes per-row spinners straightforward.

  refetch. They are complementary, and a large app commonly runs both —
  loader calls queryClient.ensureQueryData, so the fetch starts at
  navigation time AND the result is cached.

Part 5 — Streaming with defer, and Protected Routes That Do Not Flash

  A loader blocks the navigation until it resolves. That is correct for
  the record itself, and wrong for the slow sidebar nobody is waiting on:
  one 900ms analytics query holds the whole page at the old URL.

  defer() splits fast from slow:

    loader: async ({ params }) => {
      const project = await getProject(params.id);   // AWAITED — blocks
      const stats   = getStats(params.id);           // NOT awaited — promise
      return defer({ project, stats });
    }

    function Project() {
      const { project, stats } = useLoaderData();
      return (
        <>
          <h1>{project.name}</h1>               {/* instant */}
          <Suspense fallback={<StatsSkeleton />}>
            <Await resolve={stats} errorElement={<StatsError />}>
              {(value) => <Stats data={value} />}
            </Await>
          </Suspense>
        </>
      );
    }

  THE RULE: AWAIT WHAT THE PAGE IS ABOUT, DEFER EVERYTHING ELSE. If the
  user came for the project, blocking on the project is honest. Blocking
  on its analytics is not.

  Each deferred value needs its OWN Suspense boundary with its own
  errorElement, or one slow widget's failure takes the section with it.
  PROTECTED ROUTES. The effect version is the one everybody writes first,
  and it flashes the protected content:

    function Protected({ children }) {
      const user = useUser();
      const navigate = useNavigate();
      useEffect(() => {
        if (!user) navigate("/login");
      }, [user]);
      return children;               // RENDERED BEFORE THE EFFECT RUNS
    }

  Effects run AFTER paint. So the sequence is:

    render children -> browser paints the dashboard -> effect fires ->
    navigate to /login

  The user sees the protected page for one frame. On a slow device it is
  several frames, and screenshots of it end up in bug reports. It is not
  only cosmetic: the children mounted, so their own effects fired and
  their own requests went out with no valid session.

  RENDER A REDIRECT INSTEAD — decided during render, nothing mounts:

    function Protected({ children }) {
      const user = useUser();
      const location = useLocation();
      if (user === undefined) return <FullPageSpinner />;   // still checking
      if (user === null) {
        return <Navigate to="/login" state={{ from: location }} replace />;
      }
      return children;
    }

  THREE DETAILS THAT ARE ALL LOAD-BEARING:

    state={{ from: location }}  after login, send them where they meant
                                to go, not to a generic dashboard
    replace                     do NOT push; otherwise back returns to the
                                protected URL, bounces to /login, and the
                                back button is now a trap
    the undefined check         "not logged in" and "have not checked yet"
                                are DIFFERENT STATES. Collapsing them
                                redirects every user on every refresh.

  Then on the login side:

    const location = useLocation();
    const from = location.state?.from?.pathname || "/";
    // after successful auth:
    navigate(from, { replace: true });

  IN A DATA ROUTER, do it in the loader and skip the render pass entirely:

    loader: async ({ request }) => {
      const user = await getUser();
      if (!user) {
        const from = new URL(request.url).pathname;
        throw redirect(`/login?from=${encodeURIComponent(from)}`);
      }
      return null;
    }

  This is strictly better: the protected component never renders, so
  there is nothing to flash and no child effect to misfire.

Part 6 — Route-Based Splitting, and Choosing a Router

  ROUTE BOUNDARIES ARE THE HIGHEST-VALUE SPLIT POINTS IN ANY APP, because
  they match how people actually use it. A user who never opens the admin
  section should never download it.

    const Admin = lazy(() => import("./routes/Admin"));

    { path: "admin/*",
      element: (
        <Suspense fallback={<RouteSkeleton />}>
          <Admin />
        </Suspense>
      ) }

  A typical dashboard app:

    ONE BUNDLE            420KB   every user pays for the admin panel,
                                  the charting library, the PDF exporter
    SPLIT BY ROUTE        110KB   initial; admin (180KB) and reports
                                  (130KB) load on demand
                          ----------------------------------------
                          ~74% off the initial payload for most sessions

  Numbers vary enormously with what your heavy dependency is — a charting
  or rich-text library dominates. Measure before and after; the shape of
  the win is reliable, the magnitude is not.

  IN A DATA ROUTER USE lazy, NOT React.lazy, and the Suspense boundary
  disappears too — the module is fetched during navigation, in parallel
  with the loader:

    { path: "admin/*",
      lazy: () => import("./routes/Admin"),   // exports element + loader
    }

  PREFETCH ON INTENT to hide even that. React Router's Link does this
  natively:

    <Link to="/admin" prefetch="intent">Admin</Link>

  Hover fires roughly 200-300ms before the click lands — usually enough to
  have the chunk in cache before the user commits.

Interview Questions

Beginner: What does a client-side router actually do when a link is clicked?

Three things, in order. It intercepts the click on a real anchor element and calls preventDefault() so the browser does not unload the document. It calls history.pushState() to change the address bar without a request. Then it updates React state so the component tree re-renders with the components matching the new URL.

The important word is intercepts. <Link> renders a genuine <a href>, which is why middle-click, right-click "open in new tab", and copy-link-address all still work — those never fire a click handler, so the browser handles them normally. A <div onClick={navigate}> breaks all three and is invisible to screen readers, which is the most common accessibility regression in a hand-rolled router.

The router also subscribes to popstate so the back and forward buttons drive the same re-render. Without that, history moves but the UI does not.

Beginner: What is <Outlet /> and when do you need it?

Outlet is the placeholder where a parent route renders whichever child route matched. It is the nesting mechanism: a layout route renders its chrome — header, sidebar, breadcrumbs — and puts <Outlet /> where the page content goes.

The payoff is that the layout does not unmount as you navigate between siblings. Moving from /settings/profile to /settings/billing re-renders only the outlet's contents. The sidebar keeps its scroll position and its state, because it never unmounted. Rebuilding this with a wrapper component in each page instead gives you a fresh sidebar every navigation.

Forgetting Outlet in a layout route is a distinctive bug: the URL changes, the layout renders, and the page content is simply absent with no error.

Mid: Why is useSearchParams a snapshot, and what breaks because of it?

The searchParams value is a URLSearchParams object captured by the closure of the render that produced it. Like any state value it does not update mid-handler. Two updates derived from it in the same event therefore both read the same starting point, and the second overwrites the first.

There is a second, sharper trap: the object form of setSearchParams replaces the entire query string rather than merging. setSearchParams({ page: 2 }) silently discards the active filter and sort. Users report this as "changing pages resets my filters", and it looks like a state bug rather than a routing one.

Both are fixed by the functional form, which hands you a mutable draft: setSearchParams(prev => { prev.set("status", s); prev.set("page", "1"); return prev; }). Note that mutating prev is correct here, unlike useState — the router copies it for you. That inconsistency with the rest of React is exactly why the mistake is so common.

Mid: Why does an effect-based auth redirect flash the protected page?

Because effects run after commit and after paint. The component returns its children, React commits that tree, the browser paints it, and only then does the effect run and call navigate. There is at minimum one painted frame of protected content, and on a slow device several.

It is worse than a cosmetic flash. The children genuinely mounted, so their own effects ran — meaning data requests went out for a user who is not authenticated. Those either fail noisily in your logs or, if your API is lax, return data they should not.

The fix is to decide during render: if (user === null) return <Navigate to="/login" state={{ from: location }} replace />. Nothing mounts, so nothing paints and no child effect fires. In a data router, redirect from the loader instead — the component is never even created. And keep "still checking" distinct from "anonymous", or you will redirect every logged-in user on every refresh.

Senior: Make the case for and against migrating an app from fetch-in-effect to a data router.

The case for is the waterfall, and it is a structural fix rather than a tuning exercise. With effects, a nested route cannot start its request until its parent has rendered, so request order is dictated by tree shape. Three nested levels at 200ms each is 600ms of avoidable latency. A data router matches the full route set before rendering and fires every loader in parallel — one round trip. Alongside that, three categories of code leave your components: loading branches, error branches, and cache invalidation after writes, since actions revalidate every loader automatically.

The case against is real. It is an architectural migration, not an incremental one: you must adopt createBrowserRouter, move fetching out of components, and rework anything relying on component-level refetch. Loaders provide no cache, so if you already run TanStack Query you are adding a second data-lifecycle concept, not replacing one. And loaders live in route config, which suits page-level data and suits component-level data poorly — a widget that fetches on user interaction still needs useFetcher or a query.

My recommendation: migrate if your route tree is genuinely nested and you have measured waterfalls, and do it route by route — both models coexist. If your app is mostly flat, or you already have TanStack Query handling caching and deduplication well, the win shrinks to error and loading ergonomics, and that does not justify the churn. Measure the waterfall first; if it is under ~100ms, spend the time elsewhere.

Senior: How would you decide what belongs in the URL versus component state, and where does that rule break down?

My test is three questions: should this be shareable, should it survive refresh, and should the back button undo it? Any yes puts it in the URL. That captures filters, sort, pagination, the open record, wizard step, and open panels — which is most of what teams reflexively put in useState. The benefit compounds: shareable URLs make support and bug reports dramatically cheaper, because the reporter's URL is the reproduction.

It breaks down in four places. Secrets — URLs leak through history, server logs and Referer headers, so tokens and identifiers you would not paste into Slack stay out. Size — practical URL limits sit around 2000 characters, and serialised table state reaches that faster than expected; keep an id in the URL and the payload server-side. Frequency — per-keystroke or per-drag updates thrash history, so mirror into local state and sync the URL on a debounce with replace. And genuinely transient UI, where back-button-undoes-a-hover is nonsense.

The deeper trade-off is that URL state is a public API. Once people bookmark and share those links you cannot rename a param without breaking them, so the shape needs the same care as an endpoint. That argues for a schema and validation at the boundary — which is precisely the pitch for TanStack Router's typed search params, and the strongest reason I would pick it for a filter-heavy app. On an existing React Router app I would instead centralise parsing in one hook per route rather than migrate, and treat the parsed shape as the contract.

🏋️ Graded Exercises

1 (easy): This tab bar highlights the wrong tab. On /products/42, both "Products" and the parent "Shop" tab appear active. Fix it.

  <NavLink to="/shop" className={({isActive}) => isActive ? "on" : ""}>Shop</NavLink>
  <NavLink to="/shop/products" className={({isActive}) => isActive ? "on" : ""}>Products</NavLink>
Solution 
  <NavLink to="/shop" end className={...}>Shop</NavLink>
  <NavLink to="/shop/products" end className={...}>Products</NavLink>

NavLink matches by path prefix by default. /shop is a prefix of /shop/products/42, so it reports itself active on every descendant URL, and /shop/products is a prefix of /shop/products/42 too. The end prop restricts the match to the exact URL.

The default is not a mistake — breadcrumbs and section indicators want exactly this prefix behaviour, where "you are somewhere inside Shop" is the useful signal. A tab bar wants the opposite. Decide per component which question you are asking.

2 (easy): Changing the page number wipes the user's filters. Explain and fix.

  const [searchParams, setSearchParams] = useSearchParams();
  const goToPage = (page) => setSearchParams({ page: String(page) });
Solution 
  const goToPage = (page) =>
    setSearchParams(prev => {
      prev.set("page", String(page));
      return prev;
    });

The object form of setSearchParams does not merge — it replaces the whole query string with what you pass. ?status=failed&sort=duration&page=1 becomes ?page=2, and every other parameter is gone.

The functional form receives the current params as a mutable draft. Mutating it and returning it is the documented pattern here, which is genuinely inconsistent with useState — and that inconsistency is why this bug is so widespread. Users describe it as "paging resets my filters", which sounds like a state bug and sends people looking in entirely the wrong file.

3 (medium): Users report the back button is "broken" on the search page — one press barely changes anything. Diagnose and fix.

  const [searchParams, setSearchParams] = useSearchParams();
  <input
    value={searchParams.get("q") ?? ""}
    onChange={(e) => setSearchParams({ q: e.target.value })}
  />
Solution 
  const [searchParams, setSearchParams] = useSearchParams();
  const [q, setQ] = useState(searchParams.get("q") ?? "");

  useEffect(() => {
    const t = setTimeout(() => {
      setSearchParams(prev => {
        if (q) prev.set("q", q); else prev.delete("q");
        return prev;
      }, { replace: true });
    }, 300);
    return () => clearTimeout(t);
  }, [q]);

  <input value={q} onChange={(e) => setQ(e.target.value)} />

Every keystroke pushed a history entry. Typing "postgres" left eight of them, so back stepped through the letters one at a time — the back button had become a backspace key. It also replaced the query string on each keystroke, so any other filter was destroyed too.

Two changes fix it. replace: true updates the current entry instead of pushing, so an in-progress search occupies exactly one slot. The debounce plus local mirror keeps the input at full responsiveness while the URL trails 300ms behind — this is the one legitimate case for duplicating URL state into useState, and it must stay one-directional or the two fight each other.

4 (medium): Authenticated users are briefly shown the dashboard before being bounced to /login, and after logging in they land on / rather than where they were headed. Fix both.

  function Protected({ children }) {
    const user = useUser();               // null until the check resolves
    const navigate = useNavigate();
    useEffect(() => {
      if (!user) navigate("/login");
    }, [user]);
    return children;
  }
Solution 
  function Protected({ children }) {
    const user = useUser();               // undefined = checking, null = anon
    const location = useLocation();

    if (user === undefined) return <FullPageSpinner />;
    if (user === null) {
      return <Navigate to="/login" state={{ from: location }} replace />;
    }
    return children;
  }

  // on the login page, after a successful sign-in:
  const from = location.state?.from?.pathname || "/";
  navigate(from, { replace: true });

There are three separate bugs. The flash is because effects run after paint: children render, the browser paints the dashboard, then the effect navigates away. Returning <Navigate> during render means nothing mounts and nothing paints — and no child effect fires a request without a session.

The second bug is that useUser returns null both while checking and when anonymous, so !user is true during the async check and every authenticated user is bounced on refresh. Three distinct states are required: undefined for checking, null for anonymous, an object for authenticated.

The third is the missing replace. Pushing /login leaves the protected URL in history, so back returns to it, bounces to login again, and the user cannot escape. Carrying state={{ from: location }} then lets the login page return them where they meant to go.

5 (hard): Navigating to /projects/42 takes ~600ms before anything renders, and a fast-clicking user stacks up requests. The route has a project, its tasks, and a slow analytics panel. Restructure it.

  function Project() {
    const { id } = useParams();
    const [project, setProject] = useState(null);
    const [stats, setStats] = useState(null);
    useEffect(() => {
      fetch(`/api/projects/${id}`).then(r => r.json()).then(setProject);
    }, [id]);
    useEffect(() => {
      if (project) fetch(`/api/projects/${id}/stats`).then(r => r.json()).then(setStats);
    }, [project]);
    if (!project) return <Spinner />;
    return <><h1>{project.name}</h1><Stats data={stats} /><Tasks /></>;
  }
Solution 
  {
    path: "projects/:id",
    element: <Project />,
    errorElement: <ProjectError />,
    loader: async ({ params, request }) => {
      const project = await fetch(
        `/api/projects/${params.id}`, { signal: request.signal }
      ).then(r => {
        if (r.status === 404) throw new Response("Not Found", { status: 404 });
        return r.json();
      });
      const stats = fetch(
        `/api/projects/${params.id}/stats`, { signal: request.signal }
      ).then(r => r.json());          // NOT awaited
      return defer({ project, stats });
    },
    children: [{ path: "tasks", element: <Tasks />, loader: tasksLoader }],
  }

  function Project() {
    const { project, stats } = useLoaderData();
    return (
      <>
        <h1>{project.name}</h1>
        <Suspense fallback={<StatsSkeleton />}>
          <Await resolve={stats} errorElement={<StatsError />}>
            {(value) => <Stats data={value} />}
          </Await>
        </Suspense>
        <Outlet />
      </>
    );
  }

The original serialises three independent requests. Nothing starts until the component mounts; stats waits on project purely because of the effect dependency; and Tasks cannot begin until project is truthy and it finally mounts. Three round trips at ~200ms each is the 600ms.

Loaders fire for every matched route in parallel at navigation time, collapsing project and tasks into one round trip. defer then removes analytics from the critical path entirely: the navigation completes as soon as the project resolves, and the panel streams in behind its own boundary. Await what the page is about, defer the rest.

request.signal fixes the stacking. When the user navigates away, the router aborts the signal and the in-flight fetches cancel, so a fast-clicking user is not paying for four abandoned navigations at once. The errorElement plus throw new Response also deletes the error branch from the component, and giving Await its own errorElement means a failed analytics query degrades one panel instead of blanking the page.

6 (hard): An admin dashboard ships a 430KB initial bundle. Most users never open /admin or /reports, which pull in a charting library and a PDF exporter. Design the split, and say how you would verify it.

Solution 
  // data router: lazy fetches the module DURING navigation,
  // in parallel with the loader — no Suspense boundary needed
  const router = createBrowserRouter([
    { path: "/",        element: <Home /> },              // eager
    { path: "admin/*",  lazy: () => import("./routes/Admin") },
    { path: "reports/*",lazy: () => import("./routes/Reports") },
  ]);

  // ./routes/Admin.jsx exports what the route needs:
  export const loader = adminLoader;
  export const element = <AdminLayout />;

  // hide the fetch behind hover intent
  <Link to="/admin" prefetch="intent">Admin</Link>

Route boundaries are the right split points because they match real usage: a user who never opens the admin panel should never download the charting library. Splitting per component instead produces dozens of tiny chunks, more round trips, and worse compression, since gzip works better across one larger file than many small ones.

Use the data router's lazy rather than React.lazy where you can. React.lazy starts fetching the module when the component renders — after navigation has already begun — so you need a Suspense fallback and the user sees a spinner. Route lazy fetches during the navigation, alongside the loader, so the chunk and the data arrive together and there is nothing to fall back to. prefetch="intent" starts it on hover, typically 200-300ms before the click.

Verify with numbers, not vibes. Check the bundle analyzer output for the before and after; confirm in the Network panel that the admin chunk is absent on first load and appears on hover; and watch a real user metric, not just bundle size — Lighthouse or field LCP on the entry route, because a smaller bundle that adds a round trip on the critical path is not a win. The shape of this improvement is reliable; the magnitude depends entirely on how heavy your outlier dependency is, so measure yours.

🎯 Key Takeaways

  • A client router is three moves — intercept the click, pushState, re-render — and it takes over scroll, focus and screen-reader announcements that the browser used to handle.
  • <Link> must render a real <a href>, or middle-click, open-in-new-tab, copy-link and assistive technology all break at once.
  • Route order has not mattered since v6 — matches are ranked, static beats dynamic beats splat, and a splat scores negative so "*" can never steal a servable URL.
  • <Outlet /> keeps the layout mounted across sibling navigations, which is why the sidebar keeps its scroll position and state.
  • NavLink matches by prefix unless you pass end — tabs want end, breadcrumbs want the default.
  • If it should be shareable, survive refresh, or be undone by back, it belongs in the URL — filters, sort, page, open record, wizard step.
  • useSearchParams hands you a snapshot, so two updates derived from it in one handler overwrite each other.
  • The object form of setSearchParams replaces the entire query string; only the functional form merges, and mutating its draft is correct there.
  • Replace while a value is settling, push when the user commits — per-keystroke pushes turn the back button into a backspace key.
  • Never put secrets or bulk data in a URL — history, server logs and Referer headers all see it, and browsers cap length near 2000 characters.
  • Loaders fire for every matched route in parallel at navigation time, collapsing a nested fetch-in-effect waterfall into one round trip.
  • Throwing is the control flow in a loader — throw new Response reaches errorElement, throw redirect navigates, and both delete branches from your component.
  • Actions revalidate every loader on the page automatically, so there is no cache key to invalidate and no missed refetch.
  • Await what the page is about and defer everything else, giving each deferred value its own Suspense and errorElement.
  • Effect-based auth redirects flash the protected page because effects run after paint — and its children mount and fetch without a session; redirect during render or in the loader instead.
  • "Still checking" and "not logged in" are different states; collapsing them bounces every authenticated user on every refresh.
  • Route boundaries are the highest-value split points, and the data router's lazy beats React.lazy because it fetches during navigation rather than during render.
  • Loaders are not a cache — pair them with TanStack Query if revisits should not refetch.
