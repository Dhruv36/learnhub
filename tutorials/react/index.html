Components & JSX Foundations

What you'll master: React's core mental model — UI as a function of state — and the four distinct things beginners collapse into one word: a component is your function, an element is a plain object it returns, a fiber is React's stateful bookkeeping, and a DOM node is the browser's; why a capital letter is a compilation switch, not a style rule, and why the lowercase version fails silently with a blank screen and no error; why defining a component inside another component destroys its state on every keystroke — the single most-reported "React is broken" bug, and the reconciliation rule that explains it; why {items.length && <List/>} puts a literal 0 on screen; what actually happens between createRoot().render() and pixels, and why the render/commit split is the foundation every performance lesson later builds on; and how to decompose a screen the way it's done in review, including when not to extract. Prerequisites: the JavaScript track through Modules — React is 90% JavaScript fluency, and most "React questions" in interviews are closure, reference-identity or array-method questions wearing a costume.

Part 1 — The One Big Idea: UI = f(state)

Before React, UI code was imperative: "find the row, add a class, update the counter text, remember to also update the badge." The cost of that model is not verbosity — it's that the number of code paths grows with the number of transitions, not states, and a missed path leaves a stale screen that no test asserts on.

// IMPERATIVE (jQuery era): describe every TRANSITION
$("#count").text(count);
if (count > 9) $("#badge").addClass("hot");
else $("#badge").removeClass("hot");
if (count === 0) $("#clear-btn").hide(); else $("#clear-btn").show();

// Now add "clear resets the badge". Three call sites to remember.
// Miss one and the badge stays "hot" over a count of 0 — a bug with no
// exception, no failed request, and nothing in the console.

// DECLARATIVE (React): describe every STATE, once
function Counter({ count }) {
  return (
    <div>
      <span className={count > 9 ? "badge hot" : "badge"}>{count}</span>
      {count > 0 && <button>Clear</button>}
    </div>
  );
}
// There is no "clear" path to forget. count is 0, so the description
// says no button and a cold badge. The transition is derived, not written.
🔑 The mental model that survives every React version: your components are pure descriptions. Data changes → React calls your functions again → compares the new description to the old → patches only the real DOM that differs. You never "update the UI"; you update data and re-describe. The whole framework is machinery for making that affordable, and The Render Cycle makes it precise.

Part 2 — What a Component Actually Is

A component is a plain JavaScript function that (1) starts with a capital letter, (2) accepts one object argument (props), and (3) returns JSX or null. That is the entire contract — there is no base class to extend and no interface to implement.

function UserCard({ name, role }) {        // destructure props in the signature
  return (
    <article className="card">
      <h3>{name}</h3>
      <p>{role}</p>
    </article>
  );
}

// Used like a tag — but this is NOT HTML. It is a reference to the function:
<UserCard name="Ada Lovelace" role="Engineer" />
  WHY THE CAPITAL LETTER IS A COMPILATION SWITCH

  The compiler decides what to emit by looking at the first character:

    <div />        ->  _jsx("div", {})       a STRING type
                                              "a host element — DOM, you
                                               handle it"

    <UserCard />   ->  _jsx(UserCard, {})    an IDENTIFIER
                                              "call this function"

  So <userCard /> compiles to _jsx("userCard", {}) — React asks the DOM
  for an element named "usercard", the DOM happily creates an unknown
  element, and it renders NOTHING.

  THE FAILURE PROFILE IS WHAT MAKES THIS COSTLY:
    no exception, no console error, no failed network call.
    A blank area of the page, and everything else works.

  This is why the convention is enforced by tooling (the react/jsx-pascal-case
  lint rule) rather than left to taste.
  YOU RENDER COMPONENTS. YOU DO NOT CALL THEM.

    <UserCard name="Ada" />        ✅ React calls it, when it decides to
    {UserCard({ name: "Ada" })}    ❌ works on screen, breaks everything else

  Why the second one is not merely "unidiomatic":

    - HOOKS. Hook state lives on the FIBER React creates per rendered
      component. Call the function inline and its useState belongs to the
      PARENT's fiber, so the parent's hook order shifts whenever this
      appears conditionally -> "Rendered more hooks than during the
      previous render", thrown at the parent, pointing at innocent code.

    - RECONCILIATION. There is no element of type UserCard in the tree, so
      React has no boundary to compare, no place to store state, and no way
      to skip re-rendering it independently.

    - DEVTOOLS. It does not appear in the component tree, because as far as
      React is concerned it never existed.

  The rule: rendering an element hands React a DESCRIPTION it owns and
  tracks. Calling the function just splices the result into your own output.

Part 3 — JSX Is Just Function Calls

JSX is syntax sugar with no runtime of its own. A compiler — Babel, SWC or esbuild, wired up in Tooling — rewrites it before the browser ever sees it:

// You write:
const ui = (
  <section className="hero">
    <h1>Hello, {user.name}</h1>
    <UserCard name={user.name} role="admin" />
  </section>
);

// The compiler emits (modern automatic runtime):
import { jsx as _jsx, jsxs as _jsxs } from "react/jsx-runtime";
const ui = _jsxs("section", {
  className: "hero",
  children: [
    _jsx("h1", { children: ["Hello, ", user.name] }),
    _jsx(UserCard, { name: user.name, role: "admin" })
  ]
});

// Two consequences worth holding on to:
//   1. children is just another prop. Nothing about it is special except
//      the syntax that fills it.
//   2. The whole thing is an EXPRESSION, so it obeys JavaScript's rules —
//      assign it, put it in an array, pass it as a prop, return it.

The result of those calls is an element: a small, plain, immutable object describing what you want. Elements are cheap — creating thousands per render is normal and is not what makes an app slow. They are neither DOM nodes nor component instances, and keeping those four things apart is the single most useful distinction in React:

ThingWhat it isCreated byLifetime
ComponentYour function — the recipeYou, once, at module levelThe program
Element{type, props, key} — one descriptionJSX, on every renderUntil the next render; then garbage
FiberReact's mutable node per mounted component — where hooks actually liveReact, during reconciliationUntil unmounted
DOM nodeThe real browser object on screenReact DOM, during commitUntil removed
🔑 "Where does my state live?" has exactly one correct answer: the fiber. Not the component (a function has no memory between calls) and not the element (thrown away every render). That single fact explains why state survives a re-render, why it is destroyed when the element's type changes at a position, and why a key can deliberately destroy it. Every state-loss bug in this track is the same question: did the fiber survive?

Part 4 — The JSX Rules That Have Teeth

Most JSX rules are cosmetic and the compiler tells you immediately. Four are not — they fail silently, at runtime, in ways that look like a different bug:

RuleWhy it existsHow it fails when you get it wrong
One root element per returnA function returns one valueLoud — a syntax error. Wrap in a Fragment <>…</>, which groups children and renders no DOM node
className, htmlForProps are JavaScript identifiers, and class/for are reserved wordsQuiet — a console warning most people have stopped reading, and unstyled output
Braces take expressions, never statementsThe braces become an argument valueLoud — no if/for inside JSX. Use a ternary, &&, or compute above the return
style takes an objectIt is a prop, not an HTML attribute stringLoud-ish — a warning, and no styling. style={{ }}: outer braces are JSX, inner are the object
Everything self-closesJSX parses by XML rules, not lenient HTMLLoud — a syntax error on <input>

  THE 0 BUG, AND WHY IT SURVIVES REVIEW

    {items.length && <List items={items} />}

  When items is empty:
    items.length          -> 0
    0 && anything         -> 0        (&& returns the FALSY OPERAND,
                                        not a boolean)
    JSX renders 0         -> the character "0" on the page

  It survives review because the code reads correctly in English, it works
  perfectly in every state except empty, and the empty state is exactly the
  one nobody clicks through in a PR.

  WHAT IT LOOKS LIKE IN THE BUG REPORT:
    "there's a random 0 above the empty cart"

  FIXES, in order of preference:
    {items.length > 0 && <List items={items} />}    explicit boolean
    {items.length ? <List items={items} /> : null}   ternary, no coercion
    {!!items.length && <List items={items} />}       terse, but reads worse

  THE GENERAL RULE: only ever put a real boolean on the left of && in JSX.
  Strings have the same problem — "" renders nothing, but any non-empty
  string renders itself, so {name && <Greeting/>} silently prints the name.

Part 5 — Decomposing a Real Screen

The senior skill is not writing one component — it is slicing a design into a tree that survives change. Start with one lump; that is a legitimate first state, not a failure:

// Step 1 — one component. It works. Ship-able.
function ProductPage() {
  return (
    <div>
      <header><h1>Shop</h1><input placeholder="Search…" /></header>
      <ul>
        <li><img src="/cam.jpg" /><b>Camera</b><span>$999</span></li>
        <li><img src="/mic.jpg" /><b>Microphone</b><span>$149</span></li>
      </ul>
    </div>
  );
}
// Step 2 — extract by RESPONSIBILITY, not by line count.
function SearchHeader() {
  return <header><h1>Shop</h1><input placeholder="Search…" /></header>;
}

function ProductRow({ product }) {         // a repeated shape -> component + data
  return (
    <li>
      <img src={product.image} alt={product.name} />
      <b>{product.name}</b>
      <span>${product.price}</span>
    </li>
  );
}

// Step 3 — the page becomes structure + data.
const PRODUCTS = [
  { id: 1, name: "Camera",     price: 999, image: "/cam.jpg" },
  { id: 2, name: "Microphone", price: 149, image: "/mic.jpg" },
];

function ProductPage() {
  return (
    <div>
      <SearchHeader />
      <ul>
        {PRODUCTS.map(p => <ProductRow key={p.id} product={p} />)}
      </ul>
    </div>
  );
}
// key={p.id} is mandatory — the full why is in Lists, Keys & Conditional
// Rendering, and it is the same fiber-identity question as Part 3.
Extract when…Do NOT extract when…
The shape repeats — two rows become map over dataIt is used once and the parent still reads clearly. A 40-line component beats eight 5-line ones you chase across files
It has its own data requirements — it would fetch or own stateThe only motive is line count. "Components should be small" is not a reason; it is a preference with a cost
It has its own reason to change — a different team or ticket touches itSplitting would require threading five props through to reassemble what was one readable block
The parent has become hard to scanYou are extracting speculatively, for reuse that has not been asked for
You want a re-render boundary there (see The Re-render Model)The boundary would sit somewhere that makes prop drilling worse

Part 6 — What Actually Happens Between render() and Pixels

import { createRoot } from "react-dom/client";
import App from "./App";

createRoot(document.getElementById("root")).render(<App />);

  STEP BY STEP:

  1. <App /> evaluates FIRST, before render() is called. It creates ONE
     element object: { type: App, props: {} }. Nothing has rendered yet;
     you have merely described what you want.

  2. render() begins RECONCILIATION. React calls App(props) — your
     function body runs, right here, synchronously.

  3. Its returned elements are walked depth-first. Every component type
     encountered is called in turn, until the tree contains only host
     elements ("div", "h1", …). React builds a fiber for each.

  4. COMMIT. React DOM creates the real nodes and inserts them in one
     batch, then attaches ONE delegated listener per event type at the
     root container — not one per element.

  THE SPLIT THAT MATTERS FOREVER:

    RENDER   calling your functions, building elements, diffing.
             Pure. Cheap. Interruptible in concurrent React — a render
             may start, be abandoned, and start over.

    COMMIT   applying mutations to the DOM.
             Synchronous, batched, and the genuinely expensive part.

  "React is slow" almost always means "too much commit", or "render ran
  far more often than it needed to" — not "calling functions is slow".
⚠️ Purity is a requirement, not a style guide, and Strict Mode enforces it by being deliberately annoying. In development, Strict Mode calls your component function twice and runs effects twice on mount. This is not a bug and not something to work around: it is React surfacing impurity now rather than letting concurrent rendering surface it later, in production, as a double-counted analytics event or a duplicated request. If your component breaks under double invocation, it was already broken — the render body was doing something that belongs in an event handler or useEffect.

Interview Questions

Beginner: What does "declarative UI" mean, concretely, versus imperative?

Imperative code specifies transitions: "when this happens, find that node and change it." Declarative code specifies states: "given this data, the UI is this." React lets you write only the state description and derives the transitions itself.

The reason that matters is a counting argument. In the imperative model the code you must write grows with the number of transitions between states, which grows far faster than the states themselves — and every transition you forget is a screen that silently disagrees with the data. In the declarative model there is only one description per state, so a forgotten transition is not possible; there are no transitions to forget.

The trade is that you give up direct control of the DOM and take on a framework that decides when your functions run. That is a real cost — it is why "why did this re-render?" becomes a question you have to be able to answer — but it buys away an entire category of stale-UI bugs.

Beginner: Why must component names be capitalized?

Because the JSX compiler switches on the case of the first character to decide what to emit. A lowercase tag becomes a string type — _jsx("div", …) — which tells the renderer "this is a host element, create it in the DOM". A capitalized tag becomes an identifier reference — _jsx(UserCard, …) — which tells React "call this function".

So <userCard /> compiles to _jsx("usercard", {}), and React politely asks the DOM for an element called usercard. The DOM creates one, because HTML permits unknown elements, and it renders nothing.

The reason this is worth knowing rather than just obeying is the failure profile: no exception, no console error, no failed request — a blank region of the page while everything around it works. That is a hard bug to search for, which is exactly why the convention is enforced by a lint rule rather than left to taste.

Mid: What does JSX compile to, and what exactly is a React element?

Each JSX tag compiles to a function call — _jsx(type, props) with the modern automatic runtime, or React.createElement(type, props, ...children) with the classic one. The call returns an element: an immutable plain object, roughly { type, props, key }.

An element is a description, not a thing on screen. It is not a DOM node and not a component instance. It is created fresh on every render and thrown away after the diff — which is why creating thousands of them per render is normal and is not what makes an app slow.

Two practical consequences follow. First, children is just another prop; the nesting syntax is sugar for filling it, which is why you can pass elements as any prop you like. Second, because JSX is an expression producing a value, everything JavaScript can do to a value works on UI — store it in a variable, put it in an array, return it from map, pass it down. There is no template language, which is the design bet React made.

Mid: Why does defining a child component inside a parent's body cause bugs?

Because a function definition inside a function body creates a new function object on every call. React compares element types by reference, so at that position it sees a different type each render, and its rule is that a changed type at a position means the old subtree is unmounted and a new one mounted.

Unmounting destroys the fiber — which is where state and effects live — so the symptoms are that the child's state resets, its effects re-run their cleanup and setup, and any focused input loses focus. The characteristic bug report is "the search box loses focus after every character", because each keystroke re-renders the parent, which redefines the child, which remounts the input.

It is easy to miss in review because the code reads perfectly well and works on first paint — the damage only appears on the second render.

The fix is to define every component at module scope and pass data through props. If the inner component genuinely needs something from the parent's scope, that something is a prop. The same rule is why you should be suspicious of any component type computed at render time.

Senior: Distinguish component, element, fiber and DOM node — and say why the distinction earns its keep.

Component: your function, the reusable recipe, defined once at module level. Element: the plain immutable object one JSX expression produces on one render — a snapshot description, recreated and discarded every time. Fiber: React's internal mutable node for each mounted component, holding its hook state, effect list and links to parent, child and sibling; it persists across renders. DOM node: the browser object the renderer creates and patches during commit.

The flow is: render creates elements, reconciliation matches those elements to existing fibers, and commit syncs fibers to DOM.

The distinction earns its keep because it answers the question every confusing React bug reduces to: where does state live, and did it survive? State lives on the fiber. A function has no memory between calls, and elements are thrown away — so if the fiber survives, state survives.

That single rule explains a set of behaviours that otherwise look arbitrary. Re-rendering with new props keeps state, because the fiber is reused. Changing the element's type at a position destroys state, because React discards the fiber and builds a new one. Giving two branches different key values destroys state deliberately, because key participates in identity. And defining a component inline changes its type every render, which is the same destruction happening by accident.

It also explains why hooks must be called unconditionally and in the same order: they are stored positionally on the fiber, so a conditional hook shifts every subsequent slot.

Senior: Why does React insist component functions be pure, and how does it enforce the habit?

Because React reserves the right to call them at times you do not control. A parent re-render calls them. Strict Mode deliberately calls them twice in development. Concurrent rendering may start a render, pause it, throw the work away, and start again from the top.

So any side effect in the function body — mutating something outside, incrementing a counter, firing analytics, kicking off a request — runs an unpredictable number of times. The bug this produces is not a crash; it is a double-counted event or a duplicated POST, appearing under load or after an unrelated change, which is close to the worst debugging profile there is.

React enforces the habit with Strict Mode's double invocation. It is worth being explicit that this is intentional and should not be worked around: if a component breaks when called twice, it was already broken, and Strict Mode surfaced it in development instead of letting concurrent rendering surface it in production. The same reasoning applies to effects being mounted, unmounted and remounted on mount — it proves the cleanup actually works.

The practical boundary is simple: the render body computes a description from props and state and does nothing else. Anything that changes the world goes in an event handler if it is caused by a user, or in useEffect if it must synchronise with something outside React.

Worth adding that purity is what makes the rest of React's roadmap possible — interruptible rendering, reusable state, and the compiler's automatic memoization all depend on being able to call your function again without consequences.

🏋️ Graded Exercises

1 (easy): Write a Badge component taking text and color props, rendering a <span> with that background colour.
Solution 
function Badge({ text, color }) {
  return (
    <span style={{ backgroundColor: color, padding: "2px 8px", borderRadius: 999 }}>
      {text}
    </span>
  );
}

// <Badge text="NEW" color="crimson" />

The two things being checked here are that style takes an object rather than a string, and that the double braces are not special syntax — the outer pair is "a JavaScript expression goes here" and the inner pair is an object literal.

Note borderRadius: 999 has no unit. React appends px automatically for numeric values on properties that take a length. That is a convenience with one sharp edge: it does not apply to unitless properties, so lineHeight: 1.5 stays unitless and correct, while width: 50 silently means 50px, never 50%.

What I would change before shipping this: take a tone prop ("info" | "error") mapped to a CSS class instead of a raw colour. A free-text colour prop means the design system can be bypassed from any call site, and a year later the codebase has eleven shades of red that nobody can theme centrally.

  <input id="q" />
</div>

3 (medium): Without running it, what does this render when msgs = [], and why? <div>{msgs.length && <b>You have mail</b>}</div>
Solution 
It renders:  <div>0</div>

  msgs.length   ->  0
  0 && <b>…    ->  0     && returns the FALSY OPERAND, not false
  JSX renders 0 ->  "0"   only false/null/undefined render nothing

The precise mechanism is &&'s return value. It does not return a boolean — it returns the left operand if that operand is falsy, otherwise the right one. So the expression evaluates to the number 0, and React's rule is that false, null, undefined and booleans render nothing, while numbers and strings render themselves. Zero is a legitimate thing to display, so React displays it.

FixTrade-off
msgs.length > 0 && …Explicit and reads as the intent. The default choice
msgs.length ? … : nullNo coercion at all, and it extends naturally when an empty state is added later
!!msgs.length && …Shortest, but the double negation is noise a reviewer has to decode

The same trap with strings, which is less well known: {name && <Greeting/>} renders the user's name as loose text when name is non-empty and the component is somehow falsy-guarded elsewhere — and renders nothing when name is "". Any non-boolean on the left of && in JSX is a latent display bug.

Why this specific bug reaches production so often: the code is correct in every state except empty, and the empty state is the one nobody clicks through when reviewing a PR. It shows up as "there's a random 0 above the empty cart", usually reported by a customer.

4 (medium): Hand-compile this JSX to _jsx/_jsxs calls: <nav id="top"><Logo /><a href="/">Home</a></nav>
Solution 
_jsxs("nav", {
  id: "top",
  children: [
    _jsx(Logo, {}),                              // capitalized -> identifier

  ]
});
DetailWhy it is that way

Logo unquoted, "a" quotedThe whole capital-letter rule, visible in the output: one is a reference to your function, the other is a string the renderer maps to a DOM element

Why hand-compiling is worth doing once: it makes the rest of the model concrete. You can see that elements are just objects, that there is no template engine anywhere, and that key — when present — is extracted as a separate argument rather than living in props, which is why props.key is undefined and why React warns if you try to read it.

5 (medium): A teammate wrote function List(){ function Row(){…} return items.map(i => <Row … />) } and reports that rows "flicker and lose input focus" on every keystroke. Diagnose and fix.
Solution 
// THE DIAGNOSIS
// Row is defined inside List, so every List render creates a NEW function
// object. React compares component element types BY REFERENCE.
//
//   render 1:  element.type === Row#1
//   render 2:  element.type === Row#2      different type, same position
//
// A changed type at a position means: unmount the old subtree, mount a new
// one. So every keystroke destroys and rebuilds every row.

// THE FIX — module scope, data through props
function Row({ item }) { /* … */ }

function List({ items }) {
  return items.map(i => <Row key={i.id} item={i} />);
}
SymptomWhat causes it
Input loses focusThe DOM node holding focus is removed and a new one inserted. Focus is a property of a node, and that node no longer exists
State resetsUnmounting destroys the fiber, and hook state lives on the fiber
Visible flickerReal DOM removal and insertion, not a patch — the browser repaints the subtree
Effects re-run every keystrokeMount effects run on mount, and this remounts constantly. If one of them fetches, you now have a request per keystroke

Why it is easy to miss in review: the code is correct on first paint, and reads naturally — defining a helper where it is used is good practice nearly everywhere else in JavaScript. The damage only exists from the second render onwards.

The generalisation worth taking away: a component's type must be stable across renders. Anything that computes a type at render time has this bug — const C = cond ? A : B used as <C /> is the same defect wearing different clothes, and so is a higher-order component applied inside a render body rather than at module level.

If the inner function genuinely needs the parent's scope, that need is a prop. Passing item down is not a workaround for the fix; it is the design React expects.

6 (hard): Build a Stats dashboard header as a component tree: a title and three stat tiles (label + value) driven from an array, with no repeated JSX. Sketch the decomposition before coding.
Solution 
// DECOMPOSITION, before any code:
//   Stats     — owns the layout and the data
//   StatTile  — one repeated shape, no data of its own
//
// Two components, because there is exactly one repeated shape. Extracting
// a <Title/> too would be splitting for its own sake.

const METRICS = [
  { id: "users",  label: "Users",  value: "12.4k"  },
  { id: "uptime", label: "Uptime", value: "99.99%" },
  { id: "p95",    label: "p95",    value: "180ms"  },
];

function StatTile({ label, value }) {
  return (
    <div className="tile">
      <strong>{value}</strong>
      <small>{label}</small>
    </div>
  );
}

function Stats() {

7 (hard): Explain why {cond ? <Panel side="a"/> : <Panel side="b"/>} keeps the Panel's internal state when cond flips, but {cond ? <PanelA/> : <PanelB/>} does not — using the element/fiber model from this lesson.
Solution 
  Reconciliation matches an element to an existing fiber by
  POSITION + TYPE (+ key, when present).

  CASE 1 — same type, different props
    before:  position 0, type Panel, props {side:"a"}
    after:   position 0, type Panel, props {side:"b"}
    -> type matches, so React REUSES the fiber and just updates props.
    -> Hook state lives on the fiber, so state SURVIVES.

  CASE 2 — different type
    before:  position 0, type PanelA
    after:   position 0, type PanelB
    -> type differs, so React unmounts PanelA (destroying its fiber,
       its state, and running effect cleanups) and mounts PanelB fresh.
    -> State is GONE.

The rule underneath both cases is the same one: state lives on the fiber, so the only question that matters is whether the fiber survived. Nothing about props is involved in that decision — which is why case 1 keeps state even though every prop changed.

You want…Do thisWhy it works
State preserved across the flipSame component type, differing props (case 1)The fiber is reused
State reset on the flip, same component<Panel key={cond ? "a" : "b"} …/>key is part of identity, so a changed key forces unmount and remount deliberately
A form cleared when the selected record changes<Editor key={recordId} …/>The canonical use of key outside lists, and it replaces an entire class of resetting useEffect

The practical version of this is the "stale form" bug: an editor bound to selectedId keeps the previous record's unsaved edits when the user picks a different record, because the type and position never changed. Teams usually reach for an effect that resets state when the id changes — which works, but runs after a render in which the wrong data was already displayed. A key does it as part of reconciliation, so there is no intermediate frame.

The caution worth stating: because key destroys and rebuilds, it also discards scroll position, focus, animation state and any uncommitted work in that subtree, and it re-runs mount effects — including fetches. It is the right tool when "this is now a different thing", and the wrong one for "this thing changed".

🎯 Key Takeaways

  • UI = f(state). You describe states, React derives transitions — which removes the entire class of bugs where one code path forgot to update one part of the screen.
  • A capital letter is a compilation switch, not a convention: lowercase emits a string type (host element), capitalized emits your function's identity.
  • The lowercase mistake fails silently — an unknown DOM element, a blank region, no error anywhere.
  • Render components, never call them. Calling attaches their hooks to the parent's fiber, which breaks hook order and removes them from reconciliation and DevTools.
  • JSX compiles to _jsx(type, props) returning cheap immutable element objects; children is an ordinary prop.
  • Four distinct things: component (your function) → element (one render's description) → fiber (React's stateful node) → DOM node (the browser's object).
  • State lives on the fiber — so every state-loss bug reduces to one question: did the fiber survive?
  • Same type at a position keeps the fiber; a changed type destroys it, and key lets you destroy it on purpose.
  • Defining a component inside a component changes its type every render — inputs lose focus mid-keystroke, state resets, and mount effects re-run on every parent render.
  • {count && …} renders a literal 0, because && returns the falsy operand and numbers render themselves. Only booleans on the left.
  • Render is cheap and pure; commit is the expensive part. "React is slow" nearly always means too much commit, or far too many renders.
  • Strict Mode's double invocation is a feature — if double-calling breaks your component, the impurity was already there and would have surfaced in production instead.
  • Extract by repetition, data ownership and reason-to-change — never by line count, and never speculatively.
  • Component boundaries become re-render boundaries, so good decomposition now is free performance later.
