Events & Interactivity Foundations

What you'll master: the fact that explains every confusing event bug in React — there are two dispatch systems running at once, React's synthetic one along the component tree and the browser's native one along the DOM tree, so stopPropagation in one does nothing to the other; why a click inside a modal portalled into document.body still fires the card's handler three levels up the React tree; why React's onChange is the DOM's input event and there is no lazy change under that name; the outside-click menu that closes itself the instant it opens, and the two fixes — only one of which is robust; why <div onClick> is a feature keyboard users cannot reach at all, and the exact five-part checklist a real <button> gives you free; setPointerCapture, which replaces the entire document-mousemove drag dance; and the discipline for native listeners, where a missing cleanup is the classic per-mount memory leak. Prerequisites: State and JS Events — bubbling, capture and delegation transfer directly.

Part 1 — Synthetic Events: What React Actually Does

You never call addEventListener per element. React attaches its listeners once at the root container and dispatches to your handlers itself — the delegation pattern you built by hand in JS Events, provided as a framework service:

<button onClick={handleClick}>Save</button>

  WHAT REACT DOES:

  1. The ROOT CONTAINER has one real "click" listener. (React 17 moved this
     from `document` to the root — which is what allows two React versions,
     or React inside a non-React page, to coexist without stealing each
     other's events.)
  2. A click bubbles natively to that root. React reads the event target and
     finds which fiber it belongs to.
  3. React builds a SyntheticEvent: a cross-browser wrapper with the standard
     interface — e.target, e.preventDefault(), e.stopPropagation().
  4. It walks the FIBER tree: capture handlers (onClickCapture) downward,
     then bubble handlers (onClick) upward.

  THREE CONSEQUENCES THAT EXPLAIN REAL BUGS:

  • e.nativeEvent is the raw event, when you need something React did not
    normalise.

  • REACT'S BUBBLING FOLLOWS THE COMPONENT TREE, NOT THE DOM TREE.
    A modal portalled into document.body is still a React child of whatever
    rendered it, so its clicks bubble to that component's handlers even
    though the DOM nodes are nowhere near each other. This is deliberate —
    it keeps events and context consistent — and it surprises everyone once.

  • stopPropagation() ON A SYNTHETIC EVENT DOES NOT STOP A NATIVE LISTENER
    you attached to document. They are different dispatch systems, and by
    the time React dispatches synthetically, the native event has ALREADY
    reached document. This is Part 3, and it is the source of the
    "my menu closes itself" bug.
⚠️ A legacy answer that dates you in an interview: event pooling. React used to reuse a single event object and null out its fields after the handler returned, so reading e.target after an await gave you null and you needed e.persist(). That was removed in React 17. Knowing it is gone signals current knowledge; explaining the persist() workaround signals 2019. The underlying caution still applies for a different reason — see the async handler row in Common Mistakes.

Part 2 — Handler Patterns

function TodoRow({ todo, onToggle, onDelete }) {
  // 1. Passing arguments — an arrow wrapper. This is the idiom, not a hack.
  return (
    <li>
      <input type="checkbox" checked={todo.done}
             onChange={() => onToggle(todo.id)} />
      {todo.text}
      <button type="button" onClick={() => onDelete(todo.id)}>✕</button>
    </li>
  );
}

// 2. The event object is the handler's argument
function SearchBox({ onSearch }) {
  return <input onChange={e => onSearch(e.target.value)} />;
}

// 3. One handler for many controls — dispatch on a data attribute
function Toolbar({ onAction }) {
  const handle = e => {
    const action = e.target.closest("button")?.dataset.action;
    if (action) onAction(action);          // guard: clicks on the gaps
  };
  return (
    <div onClick={handle}>
      <button type="button" data-action="bold">B</button>
      <button type="button" data-action="italic">I</button>
    </div>
  );
}

  NOTE ON (3): inside React you almost never need manual delegation for
  PERFORMANCE — React already delegates, so 500 onClick props are 500
  entries in React's internal map, not 500 real DOM listeners. Use this
  pattern when it genuinely simplifies the code, not to "save listeners".

Part 3 — preventDefault and stopPropagation, Precisely

// preventDefault — cancel the BROWSER's built-in action; bubbling continues
function LinkTab({ href, onSelect }) {
  return <a href={href} onClick={e => { e.preventDefault(); onSelect(href); }}>…</a>;
  //   The href STAYS: middle-click, "open in new tab", crawlers and screen
  //   readers all need it. Removing it and handling onClick alone turns a
  //   link into a div that happens to navigate.
}

<form onSubmit={e => { e.preventDefault(); save(); }}>   // the form idiom

// stopPropagation — stop ANCESTOR handlers seeing it; the default action runs
function Card({ onOpen, onFavourite }) {
  return (
    <article onClick={onOpen}>
      <h3>Title</h3>
      <button type="button"
              onClick={e => { e.stopPropagation(); onFavourite(); }}>⭐</button>
      {/* without it, favouriting ALSO opens the card */}
    </article>
  );
}

  THE TWO-SYSTEMS TRAP, DRAWN OUT

    document  ← native listener you added in an effect
      │
      └ #root ← React's single real listener
          │
          └ <div> ← your component, with onClick

    A click inside your component:

      1. NATIVE bubbling carries it up: div -> ... -> #root -> document
         Your document listener FIRES HERE.
      2. React's root listener received it during step 1, and NOW
         dispatches synthetically down and up the fiber tree.
      3. Your onClick runs and calls e.stopPropagation().

    Step 3 cannot un-fire step 1. The native event already reached
    document before React dispatched anything.

  So "stopPropagation inside the popover" never prevents a document-level
  outside-click handler from closing it. The correct test is containment:

      if (rootRef.current.contains(e.target)) return;   // inside: ignore

Part 4 — Building It: an Accessible Dropdown

One component that exercises every event skill at once — clicks, outside-clicks, keyboard, focus and ARIA state:

function Dropdown({ label, options, onPick }) {
  const [open, setOpen]     = useState(false);
  const [active, setActive] = useState(0);
  const rootRef = useRef(null);

  // OUTSIDE CLICK — a native listener, because React handlers only cover
  // your own elements. This is the sanctioned escape hatch.
  useEffect(() => {
    if (!open) return;
    const onDocPointerDown = e => {
      if (!rootRef.current?.contains(e.target)) setOpen(false);
    };
    document.addEventListener("pointerdown", onDocPointerDown);
    return () => document.removeEventListener("pointerdown", onDocPointerDown);
  }, [open]);                                  // cleanup is NOT optional

  function onKeyDown(e) {
    switch (e.key) {                           // e.key, never e.keyCode
      case "ArrowDown":
        e.preventDefault();                    // stop the page scrolling
        setActive(a => Math.min(a + 1, options.length - 1));
        break;
      case "ArrowUp":
        e.preventDefault();
        setActive(a => Math.max(a - 1, 0));
        break;
      case "Enter":
      case " ":
        e.preventDefault();
        pick(options[active]);
        break;
      case "Escape":
        setOpen(false);
        break;
    }
  }

  function pick(opt) { onPick(opt); setOpen(false); }

  return (
    <div ref={rootRef} onKeyDown={onKeyDown}>
      <button type="button" aria-haspopup="listbox" aria-expanded={open}
              onClick={() => setOpen(o => !o)}>{label} ▾</button>
      {open && (
        <ul role="listbox">
          {options.map((opt, i) => (
            <li key={opt} role="option" aria-selected={i === active}
                className={i === active ? "active" : ""}
                onPointerEnter={() => setActive(i)}
                onClick={() => pick(opt)}>{opt}</li>
          ))}
        </ul>
      )}
    </div>
  );
}

  WHAT THIS DEMONSTRATES:
    - React events for everything inside the component
    - ONE native document listener, with cleanup, for outside clicks
    - pointerdown rather than click, for the reason in Exercise 4
    - every pointer interaction has a keyboard twin
    - ARIA attributes mirror component state rather than duplicating it

  WHAT IT STILL OWES to be production-grade: focus management. Opening
  should move focus into the list and closing should return it to the
  button, or a keyboard user is left with focus on a button whose menu
  they cannot reach. That is Refs & the DOM.

Interview Questions

Beginner: What is a SyntheticEvent and why does React use one?

It is a cross-browser wrapper around the native event exposing the standard interface — target, preventDefault, stopPropagation — with the raw event still available at e.nativeEvent.

React attaches one real listener per event type at the root container rather than one per element, then constructs a synthetic event and dispatches it through the component tree itself. That buys three things: consistent behaviour across browsers, delegation for free regardless of how many handlers you write, and events that follow the React tree.

That last point is the one with consequences. Because dispatch follows components rather than DOM nodes, a modal rendered through a portal into document.body still bubbles its clicks to the component that rendered it — which is either exactly what you want or a genuine surprise, depending on whether you knew.

Beginner: Difference between onClick={fn}, onClick={fn(id)} and onClick={() => fn(id)}?

The first passes the function itself; React calls it on click, with the event as its argument.

The second calls fn during render and passes its return value as the handler. That is a bug unless fn is specifically written to return a handler — and if it sets state, it is an infinite render loop.

The third creates a new function that calls fn(id) when clicked. It is the standard way to bind data to a handler.

The usual follow-up is whether the arrow's fresh identity per render is a problem. Only if the receiver is memoized or the function lands in a dependency array — for a plain DOM handler it costs an allocation and nothing else.

Mid: Why doesn't React's onChange behave like the DOM's change?

React deliberately mapped onChange onto the native input event, so it fires on every keystroke rather than on blur or commit.

The reason is controlled components. If the input's value comes from state, then state must update on every keystroke or the field will not show what the user typed — the DOM would reject each character as React re-renders with the old value. Lazy change semantics would make controlled inputs impossible.

The cost is a naming collision with the platform that catches everyone once, and there is no way to get native change semantics under that name. When you want commit-on-blur — validating an email only when the user leaves the field — use onBlur, or debounce the change handler.

Mid: How do you correctly implement close-on-outside-click?

React handlers only cover elements you render, and an outside click by definition happens somewhere else — so this needs a native listener on document, added in an effect while the popover is open and removed in the cleanup.

The check is containment: if (rootRef.current?.contains(e.target)) return; before closing. What you must not rely on is calling stopPropagation inside the popover, because the native event reaches document before React dispatches synthetically at all — stopping the synthetic chain cannot un-fire a native listener that already ran.

I would listen for pointerdown rather than click, for two reasons. It fires before focus moves, which matters if closing depends on focus. And it sidesteps the classic bug where the same click that opened the menu bubbles to document after the effect has attached the listener, closing it instantly.

Escape needs handling too, and — the part usually forgotten — focus should return to the trigger when the popover closes, or a keyboard user is stranded on a removed element.

Senior: A click inside a portalled modal triggers the parent card's onClick. Why, and what do you do?

Because synthetic events propagate along the React tree, not the DOM tree. The modal is a React child of the card even though its DOM lives in document.body, so React dispatches the click up through the card's handlers.

This is deliberate rather than a bug: portals exist so content can escape a DOM constraint like overflow: hidden without leaving the component hierarchy, and keeping events and context consistent with that hierarchy is the whole point.

The immediate fix is onClick={e => e.stopPropagation()} on the modal root, which works. The better fix is usually structural: the underlying problem is a giant clickable surface, and a card whose entire area is a click target will keep colliding with everything placed inside it — buttons, links, text selection, context menus.

I would give the card an explicit interactive element — a title link or an open button — rather than making the <article> clickable. That also fixes the accessibility problem the clickable card already has, since a clickable <article> is not focusable and is not announced as actionable.

Senior: When would you bypass React's event system, and what discipline applies?

Four situations, and they share the property that React's props cannot express them.

Global targets — window resize, document-level keyboard shortcuts, outside-click detection. There is no JSX element to hang a prop on.

Non-passive wheel and touch handlers, where you need preventDefault to stop scrolling. React registers some of these as passive, in which case preventDefault is silently ignored, so an explicit addEventListener(…, { passive: false }) is the only way.

APIs outside the event system — ResizeObserver, IntersectionObserver, media element events like timeupdate.

High-frequency streams you want to throttle before they touch React. A pointermove at 120 Hz that calls a setter is 120 renders a second; subscribing natively lets you coalesce to an animation frame, or write to a ref and read it only where needed.

The discipline is the same in every case: subscribe in useEffect, unsubscribe in its cleanup, and be deliberate about the dependency array — a handler that closes over state either needs to be in the deps, in which case you resubscribe on every change, or needs to read from a ref so it can stay subscribed. Forgetting the cleanup is the classic leak: one listener per mount, an app that degrades over a session, and whole component trees held alive by closures.

🏋️ Graded Exercises

1 (easy): A button that logs "clicked at (x, y)" from the event's clientX/clientY.
Solution 
<button type="button"
        onClick={e => console.log(`clicked at (${e.clientX}, ${e.clientY})`)}>
  Where?
</button>

The coordinates are on the synthetic event because React copies the standard properties across from the native one. Nothing here needs e.nativeEvent.

PropertyOrigin
clientX/YThe viewport — changes as the page scrolls
pageX/YThe document — includes scroll offset
offsetX/YThe target element's own box — what you want for "where in this element"

The one that catches people is that a keyboard activation also fires onClick on a real button, and its coordinates are 0, 0 — so positioning anything from click coordinates puts it in the top-left corner for keyboard users. Check e.detail === 0 to distinguish a keyboard activation from a real pointer click.

2 (easy): Wire a delete button inside a clickable list row so deleting never triggers the row's open handler.
Solution 
<li onClick={() => onOpen(item.id)}>
  {item.name}
  <button type="button"
          onClick={e => { e.stopPropagation(); onDelete(item.id); }}>
    ✕
  </button>
</li>

Why stopPropagation and not preventDefault: the problem is the ancestor's handler, not a browser default. preventDefault would cancel nothing here and the row would still open.

What this solution is really working around, and what I would say in review: a clickable <li> is not focusable, not keyboard-activatable and not announced as interactive, so the "open" action does not exist for keyboard users at all — and now there is a nested button inside a clickable region, which is invalid interactive nesting.

<li>
  <button type="button" className="row-open" onClick={() => onOpen(item.id)}>
    {item.name}
  </button>
  <button type="button" onClick={() => onDelete(item.id)} aria-label={`Delete ${item.name}`}>
    ✕
  </button>
</li>

Now no stopPropagation is needed at all, because the two actions are siblings rather than nested. That is the general shape of the fix: reaching for stopPropagation is usually a signal that two interactive things are nested when they should be adjacent.

3 (medium): A search input that calls onSearch(value) only on Enter, and clears itself on Escape.
Solution 
function SearchOnEnter({ onSearch }) {
  const [q, setQ] = useState("");

  function onKeyDown(e) {
    if (e.key === "Enter") {
      e.preventDefault();          // inside a form, Enter would submit it
      onSearch(q);
    }
    if (e.key === "Escape") {
      setQ("");
      onSearch("");                // clearing the box should clear results too
    }
  }

  return (
    <input type="search" value={q} aria-label="Search"
           onChange={e => setQ(e.target.value)}
           onKeyDown={onKeyDown} />
  );
}
DetailWhy
onKeyDown, not onKeyUpDown fires before the character is processed, so preventDefault can still stop a form submit. Up is too late
e.key stringskeyCode is deprecated and gives different numbers on different layouts
Escape also calls onSearch("")Otherwise the box is empty while stale results remain on screen — the state and the display disagree
type="search"Gives a native clear affordance and the right on-screen keyboard on mobile

The real-world caveat: Escape-to-clear collides with IME composition. A user typing Japanese or Chinese presses Escape to cancel a candidate selection, and this handler would wipe their whole query. Guarding with if (e.nativeEvent.isComposing) return; is the fix, and it is the kind of thing that only surfaces from users in those locales.

If search should be live rather than on Enter, the answer is not to move onSearch into onChange — that fires a request per keystroke. It is to debounce, which brings in cancellation and out-of-order responses; see Data Fetching.

4 (medium): Why does this menu close instantly after opening — a button with onClick={() => setOpen(true)}, plus a document-level native click listener added when open that closes on any click? Fix it two ways.
Solution 
  THE SEQUENCE

  1. You click the button.
  2. React's root listener receives the native click and dispatches
     synthetically -> your onClick runs -> setOpen(true).
  3. React re-renders and runs the effect, which attaches the document

  4. THE SAME NATIVE CLICK IS STILL BUBBLING. It reaches document.

  wrong in the code, because the two halves are in different files.

Why stopPropagation on the button is not on this list: it is the fix people reach for first and it does not work. The native click reaches document independently of React's synthetic dispatch — stopping the synthetic chain cannot retract a native event that has already bubbled.

The general lesson: when React state and a native listener interact, the ordering is native-bubble-then-synthetic-dispatch, and effects run after the render that the synthetic dispatch caused. Almost every "it closes itself" bug is that sequence.

6 (hard): Implement a draggable slider thumb with pointer events: drag updates a 0–100 value, keeps working when the pointer leaves the element, and stops on release.
Solution 
function Slider({ value, onChange, label = "Value" }) {
  const trackRef = useRef(null);

  function valueFrom(e) {
    const r = trackRef.current.getBoundingClientRect();
    const ratio = (e.clientX - r.left) / r.width;
    return Math.round(Math.min(Math.max(ratio, 0), 1) * 100);
  }

  function onPointerDown(e) {
    e.currentTarget.setPointerCapture(e.pointerId);   // THE trick
    onChange(valueFrom(e));
  }

  function onPointerMove(e) {
    if (e.buttons) onChange(valueFrom(e));            // only while pressed
  }

  function onKeyDown(e) {
    if (e.key === "ArrowRight") onChange(Math.min(value + 1, 100));
    if (e.key === "ArrowLeft")  onChange(Math.max(value - 1, 0));
    if (e.key === "Home")       onChange(0);
    if (e.key === "End")        onChange(100);
  }

  return (
    <div ref={trackRef} className="track"
         role="slider" tabIndex={0}
         aria-label={label} aria-valuenow={value}
         aria-valuemin={0} aria-valuemax={100}
         onPointerDown={onPointerDown}
         onPointerMove={onPointerMove}
         onKeyDown={onKeyDown}>
      <div className="thumb" style={{ left: `${value}%` }} />
    </div>
  );
}

setPointerCapture is what replaces the old dance. Before pointer events, a drag meant attaching mousemove and mouseup to document on mousedown and removing them on mouseup — with all the cleanup risk that implies. Capture redirects all subsequent pointer events for that pointer id to this element until release, so the drag keeps working outside the element's bounds and ends automatically.

DecisionWhy
e.currentTarget, not e.targettarget may be the thumb; capturing on the track is what you want, and the thumb might unmount mid-drag
if (e.buttons)pointermove fires on hover too. Without the guard, moving the mouse across the track changes the value
Clamping inside valueFromCapture means you receive coordinates outside the track, so the ratio goes negative or above 1
Keyboard handler and ARIAA pointer-only slider is unusable without a mouse — and role="slider" with the value attributes is what makes it announceable

What is still missing for production: touch-action. On a touch device a horizontal drag on this element will also scroll the page unless CSS sets touch-action: none on the track — and that must be CSS rather than preventDefault, because the browser decides scrolling before the event is dispatched.

And the honest recommendation: <input type="range"> gives all of this — pointer, touch, keyboard, ARIA, and the platform's own accessibility — for one element. Build this only when the design genuinely cannot be achieved by styling the native control.

Solution

// inline arrow, for the same reason.

A third option worth knowing when the parent needs the value but not on every frame: keep it in a ref and read it in the handler that actually consumes it. That removes rendering from the path entirely, at the cost of the value not being reactive — appropriate for something like "which row was last hovered" used only on click.

The principle behind all three: a high-frequency event must not fan out into a wide re-render. Either shrink what re-renders, or keep the value out of React's render path. Reaching for useMemo on the row list would not help at all here — the props genuinely changed, and the problem is how many components care.

🎯 Key Takeaways

  • React attaches one real listener at the root and dispatches SyntheticEvents along the component tree — e.nativeEvent is the raw escape hatch.
  • Dispatch follows the React tree, not the DOM tree, so a portalled modal's clicks still reach the component that rendered it.
  • There are two dispatch systems. A native event reaches document before React dispatches synthetically, so synthetic stopPropagation cannot stop a document listener.
  • Event pooling was removed in React 17 — e.persist() is a 2019 answer.
  • preventDefault cancels the browser's action; stopPropagation shields ancestors. Different jobs, frequently confused.
  • Reaching for stopPropagation usually signals nested interactive elements that should be siblings.
  • React's onChange is the DOM's input — per keystroke, because controlled inputs require it. Use onBlur for commit semantics.
  • onFocus and onBlur bubble in React unlike natively, so container-level focus handling works; e.relatedTarget says where focus went.
  • An outside-click handler must test containment, and listening on pointerdown avoids the same-click-closes-it race.
  • Native listeners belong in effects with guaranteed cleanup — a leaked listener per mount is the classic React memory leak, and it presents as "the app gets slower".
  • setPointerCapture replaces the document-mousemove drag dance, and pointer events cover mouse, touch and pen at once.
  • A clickable <div> reimplements five button behaviours by hand and still gets Space's keyup semantics wrong.
  • Every pointer interaction needs a keyboard twin, and hover-only affordances do not exist for touch or keyboard users.
  • High-frequency events must not fan out into wide re-renders — use CSS, shrink the blast radius, or keep the value in a ref.
