State & useState Foundations

What you'll master: the one idea every state bug reduces to — state is a snapshot per render, not a live variable, so count is a constant inside your function and calling setCount never changes it; why three setN(n + 1) calls add one, and why the functional form adds three; the stale-closure stopwatch that sticks at 1 forever and the two different fixes, only one of which you should ship; why mutating state produces no re-render at all — the bail-out mechanism, and why the symptom is "it works after I click something else"; which values belong in state and which must be derived, since every derived value stored in state is a second source of truth that will drift; how to structure state so contradictory states are unrepresentable rather than merely unlikely; and lazy initialisation, batching, and the bail-out rules that decide how many times your component actually runs. Prerequisites: Props and JS Closures — most state "gotchas" are closures wearing a React costume.

Part 1 — Why State Exists, and Where It Lives

Props come from the parent, but something has to remember across renders — the typed text, the open flag, the fetched list. A local variable cannot: every render calls your function fresh and recreates all of them. useState asks React to store a value outside your function, on the component's fiber, and hand it back on every render:

import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);   // [current value, updater], initial 0
  //     ^ THIS render's snapshot  ^ the only way to change it

  return <button onClick={() => setCount(count + 1)}>Clicked {count}×</button>;
}

// Click -> setCount(1) -> React re-renders Counter -> useState returns 1.
// Two <Counter/> on a page = two fibers = two independent counts, because
// state is stored per fiber, not per component function.
🔑 The snapshot model, in one sentence: count is a constant within one render. Calling setCount never changes it — it schedules a re-render in which useState will return the new value to a new count constant. State reads are photographs; setters order the next photograph. Almost every confusing useState behaviour is this sentence applied somewhere you did not expect.

Part 2 — The Snapshot Model, Proven

function Demo() {
  const [n, setN] = useState(0);

  function handleClick() {
    setN(n + 1);      // n is 0 -> schedules "set to 1"
    setN(n + 1);      // n is STILL 0 here -> schedules "set to 1"
    setN(n + 1);      // still 0 -> schedules "set to 1"
    console.log(n);   // logs 0. This render's photograph never changes.
  }
  // After the click: n === 1. Not 3. All three computed 0 + 1.
}

// FUNCTIONAL UPDATES receive the latest QUEUED value, not the snapshot:
setN(prev => prev + 1);   // 0 -> 1
setN(prev => prev + 1);   // 1 -> 2
setN(prev => prev + 1);   // 2 -> 3   ✅ updaters queue and chain
  THE SAME MODEL, ASYNC FLAVOUR — the interview classic

  function Timer() {
    const [sec, setSec] = useState(0);
    useEffect(() => {
      const id = setInterval(() => setSec(sec + 1), 1000);  // ❌
      return () => clearInterval(id);
    }, []);                                                  // runs once
  }

  WHAT YOU OBSERVE: the display goes 0 -> 1, and then stops. Forever.
  No error. The interval is definitely running.

  WHY: the effect ran once, so the interval callback is a closure over the
  FIRST render's `sec`, which is 0. Every tick computes 0 + 1 and sets 1.
  React sees the state is already 1, bails out, and does not even
  re-render. The callback is never recreated, so it reads 0 forever.

  FIX A — ask React for the current value instead of trusting the closure:
    setInterval(() => setSec(s => s + 1), 1000);

  FIX B — make the closure fresh by depending on sec:
    useEffect(…, [sec]);
  This works, and it tears down and recreates the interval every second,
  which drifts the timer and creates garbage. Ship A.
Use the functional form when…The plain form is fine when…
The next value is computed from the previous one — increments, toggles, appendingThe next value is independent — setOpen(true), setQuery(e.target.value)
Several updates may land in one eventThere is exactly one update, from fresh data
The call is inside an async callback — an interval, a promise, an event listenerThe call is in a handler that runs during the same render's lifetime
You are not certain which of the above applies—
⚠️ The last row is deliberate. The functional form is never wrong — it costs one arrow function and is immune to snapshots, batching and stale closures alike. The plain form is a small readability win that requires you to be right about the context. When reviewing, I treat setX(x + 1) as a question to answer rather than a bug, and setX(p => p + 1) as needing no thought at all.

Part 3 — Batching, Lazy Init and the Bail-Out

  1. BATCHING — several setters in one event produce ONE re-render

     function submit() {
       setSaving(true);
       setError(null);
       setAttempts(a => a + 1);
     }
     // one render, which sees all three new values.

     React 17 batched only inside React event handlers, so updates in a
     setTimeout, a promise callback or a native listener each caused
     their own render. React 18's createRoot batches EVERYWHERE.

     The escape hatch, for when you must read the DOM between updates:
       flushSync(() => setX(1));   // forces a synchronous render
     It is a performance foot-gun by design — reach for it only when
     measuring layout between two updates, which is rare.

  2. LAZY INITIALISATION

     useState(JSON.parse(localStorage.getItem("draft") ?? "{}"))
     ^ runs the parse on EVERY render, and throws the result away after
       the first. The argument is evaluated before useState is called;
       React cannot prevent that.

     useState(() => JSON.parse(localStorage.getItem("draft") ?? "{}"))
     ^ React calls the initializer only on mount.

     Note this is about the COST, not correctness — the value is the
     same either way. It matters when the work is real: parsing storage,
     building a Map, reading layout.

  3. THE BAIL-OUT — setting the same value skips the render

     setCount(0);         // if count is already 0, no re-render
     Comparison is Object.is, so for objects "same" means SAME REFERENCE:

     setUser({ ...user }); // re-renders — new reference, equal contents
     setUser(user);        // does NOT re-render — same reference

     That second line is the entire reason mutating state renders
     nothing, and it is Part 4.

Part 4 — Immutable Updates

React decides whether state changed with Object.is on the value. Mutate in place and the reference survives, so React bails out and never re-renders. Every update must produce a new object or array at each level along the path that changed:

const [form, setForm] = useState({ name: "", address: { city: "", zip: "" } });

// ✅ one field — copy the object, override one key
setForm({ ...form, name: "Ada" });

// ✅ NESTED — copy every level on the path to the change
setForm({ ...form, address: { ...form.address, city: "Pune" } });

// ❌ the classic silent failure
form.address.city = "Pune";   // mutates the object React is holding…
setForm(form);                // …same reference -> bail-out -> no render

// WHAT YOU OBSERVE: the value is correct if you log it, wrong on screen,
// and it "appears" the moment anything else triggers a render — so it
// looks intermittent, and gets closed as unreproducible.
OperationMutates (wrong)Immutable (right)
Add itemarr.push(x)[...arr, x]
Remove itemarr.splice(i, 1)arr.filter(a => a.id !== id)
Update one itemarr[i].done = truearr.map(a => a.id === id ? { ...a, done: true } : a)
Insert at indexarr.splice(i, 0, x)[...arr.slice(0, i), x, ...arr.slice(i)]
Sortarr.sort(f) — returns the same arrayarr.toSorted(f), or copy first
Reversearr.reverse()arr.toReversed()
Set a fieldobj.k = v{ ...obj, k: v }
🔑 Spread is shallow, and that is by design rather than a limitation. {...form} copies one level; nested objects stay shared by reference until you copy along the changed path. That is what makes updates cheap — unchanged branches keep their identity, so memoized children below them can skip re-rendering. The cost is that deep updates need a copy per level, and when that becomes painful the state shape is telling you something: flatten it, or move to useReducer, optionally with Immer so you can write mutations that produce immutable results.

Part 5 — What Belongs in State

  THE MOST COMMON STATE SMELL — storing what you can compute

    const [items, setItems]   = useState([]);
    const [total, setTotal]   = useState(0);       // ❌ derivable
    const [hasAny, setHasAny] = useState(false);   // ❌ derivable

  Now EVERY code path that changes items must also update two other
  pieces of state. Add one — a "clear all" button, an undo, a websocket
  push — and forget one line, and the cart shows three items with a
  total of £0.

  The bug is not that it is slower. It is that correctness now depends
  on every future author remembering.

    ✅ derive during render. Renders are cheap; sync bugs are not.
    const [items, setItems] = useState([]);
    const total  = items.reduce((s, i) => s + i.price, 0);
    const hasAny = items.length > 0;

  STRUCTURE: THREE HEURISTICS

  1. GROUP WHAT CHANGES TOGETHER
       const [pos, setPos] = useState({ x: 0, y: 0 });
     A pointer position is one fact. Two setters you must always call
     together is a rule nobody can enforce.

  2. SPLIT WHAT CHANGES INDEPENDENTLY
       const [form, setForm]       = useState({…});
       const [modalOpen, setModal] = useState(false);
     One mega-object means every keystroke produces a new object for
     everything, so memoized consumers of the modal flag re-render too.

  3. MAKE CONTRADICTIONS UNREPRESENTABLE
       ❌ isLoading, isError, data          -> loading AND error is legal
       ✅ status: "idle" | "loading" | "success" | "error"

     With booleans, "loading and error at once" is a state your UI can
     reach and nobody designed. With a union, it cannot be written down.
     In TypeScript the discriminated union goes further — the compiler
     will not let you read `data` in the error branch:

       type State =
         | { status: "idle" }
         | { status: "loading" }
         | { status: "success"; data: Item[] }
         | { status: "error";   error: Error };

Part 6 — Putting It Together: an Editable Todo List

function TodoApp() {
  const [todos, setTodos] = useState(() =>                   // lazy: parse once
    JSON.parse(localStorage.getItem("todos") ?? "[]"));
  const [filter, setFilter] = useState("all");               // independent -> separate

  // DERIVED — not state. Cannot drift, because there is nothing to sync.
  const visible = filter === "done" ? todos.filter(t => t.done)
                : filter === "open" ? todos.filter(t => !t.done)
                : todos;
  const openCount = todos.filter(t => !t.done).length;

  // ALL functional updates: correct even if two land in one batch.
  const add    = text => setTodos(ts => [...ts, { id: crypto.randomUUID(), text, done: false }]);
  const toggle = id   => setTodos(ts => ts.map(t => t.id === id ? { ...t, done: !t.done } : t));
  const remove = id   => setTodos(ts => ts.filter(t => t.id !== id));

  return (
    <>
      <AddForm onAdd={add} />
      <FilterBar value={filter} onChange={setFilter} />
      <ul>
        {visible.map(t => (
          <TodoRow key={t.id} todo={t} onToggle={toggle} onRemove={remove} />
        ))}
      </ul>
      <footer>{openCount} remaining</footer>
    </>
  );
}

  Every rule in this lesson is visible here:
    - one owner for todos; children are stateless (Props lesson)
    - visible and openCount derived, so a filter change cannot desync
    - functional updates everywhere, so batching is safe
    - lazy initialiser, so localStorage is parsed once rather than
      on every keystroke
    - crypto.randomUUID() for keys, not the array index

  Persisting back to localStorage belongs in an effect — the next
  section of the track.

Interview Questions

Beginner: Why doesn't count update immediately after setCount(count + 1)?

Because count is not a variable React writes to — it is a value useState returned to this render. The setter does not assign anything; it tells React "on the next render, this state should be 1", and schedules that render.

So within the current function body, count is a constant. Logging it after the setter shows the old value, and that is correct behaviour rather than a timing quirk — there is no moment at which this render's count becomes 1.

The reason it works this way is consistency: everything in one render — the JSX, the handlers it creates, the effects it schedules — sees one coherent set of values. If state could change mid-render, two halves of the same output could disagree.

Beginner: When must you use the functional update form?

Whenever the next value is computed from the previous one — increments, toggles, appending to a list — and especially in three situations: several updates in one event, updates from async callbacks such as intervals or promises, and anywhere a closure might be holding an old snapshot.

The mechanism is that setX(prev => …) queues a function. React applies the queue in order, passing each one the result of the last, so three increments produce +3 rather than three copies of the same +1.

The plain form is fine when the value is independent of the previous one — setOpen(true), setQuery(e.target.value). That said, the functional form is never wrong, so if I am not certain which case I am in, I use it and stop thinking about it.

Mid: What is automatic batching, and what changed in React 18?

Batching collapses several state updates into a single re-render. Without it, three setters in one click handler would render three times, and the user could see intermediate states.

React 17 batched only inside React's own event handlers. Updates in a setTimeout, a promise callback such as the .then after a fetch, or a native event listener each triggered their own render — which is why a fetch that set loading, data and error separately rendered three times.

React 18 with createRoot batches everywhere by default, which is why some apps saw fewer renders after upgrading with no code change.

The escape hatch is flushSync, which forces a synchronous render. The legitimate use is narrow: you need the DOM updated now because you are about to measure it or move focus into something that must already exist. It opts out of the batching that makes React fast, so it is deliberately awkward.

Mid: Why does mutating state break React, mechanically?

Because React decides whether to re-render by comparing the new state value with the old using Object.is. Mutating an object keeps the same reference, so when you pass it to the setter React concludes the state did not change and bails out without rendering at all.

It is worth being precise that this is not a partial failure. The component does not re-render, so nothing downstream even gets the chance to notice — memoized children, effect dependency arrays and context consumers all see nothing because none of them ran.

The observable symptom is what makes it expensive: the data is correct if you log it, the screen is wrong, and it corrects itself as soon as anything else causes a render. That intermittency is why these bugs get filed as "sometimes the total is wrong" and closed as unreproducible.

The methods that catch people are sort and reverse, because they return an array and therefore look pure — but it is the same array. toSorted and toReversed are the non-mutating versions, and a spread before sorting works everywhere.

Senior: You see const [fullName, setFullName] = useState(first + " " + last) alongside state for first and last. What is the review comment?

Two problems, and the second is worse than the first.

It is redundant state. fullName is derivable from two values that are already state, so there are now three sources of truth for two facts. Every code path that updates first must remember to update fullName, and that is a rule no test enforces.

It is also already broken. useState's argument is read only on mount, so fullName is frozen at whatever the names were on the first render. Typing in the first name field updates first and leaves fullName showing the original — it does not drift eventually, it is wrong immediately.

The fix is to delete the state and derive during render: const fullName = `${first} ${last}`. No useMemo — string concatenation is far cheaper than the comparison and cache-management useMemo would add.

The general principle I would state in the comment is that state should hold what cannot be computed. Every derived value stored in state converts a "cannot be wrong" into a "must be kept right".

Senior: How would you model fetch status so invalid states are unrepresentable?

Replace the independent booleans with a discriminated union. The usual shape — isLoading, isError, data, error — permits sixteen combinations, of which maybe four are meaningful, and the UI can reach the others: loading and error simultaneously, success with no data, an error object left over from a previous attempt while the new one succeeds.

type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: Item[] }
  | { status: "error";   error: Error };

Now there is one field to branch on and each arm carries exactly the data that arm has. In TypeScript the narrowing is enforced: you cannot read data in the error branch, because it does not exist there. That converts a class of runtime bug — reading stale data during an error state — into a compile error.

The practical benefit beyond correctness is that the rendering code stops being a pile of nested conditionals and becomes a switch on one value, which is both readable and exhaustively checkable.

This is also the doorway to useReducer. Once you have named the states, the next question is which transitions are legal — can you go from error straight to success, what happens if a second request starts while one is in flight — and the moment that question has a non-obvious answer, a reducer or a state machine is a better home for it than a set of setState calls scattered through handlers.

The one caveat: for genuine server data I would ask whether this should be hand-rolled at all. A caching library already models these states, plus staleness, refetching and deduplication — and those are the parts people get wrong after getting the union right.

🏋️ Graded Exercises

1 (easy): Build a show/hide toggle: a button flipping between "Show details" and "Hide details", conditionally rendering a paragraph.
Solution 
function Details() {
  const [open, setOpen] = useState(false);
  return (
    <>
      <button type="button" onClick={() => setOpen(o => !o)}
              aria-expanded={open}>
        {open ? "Hide" : "Show"} details
      </button>
      {open && <p>The fine print…</p>}
    </>
  );
}

Why setOpen(o => !o) rather than setOpen(!open): the new value is computed from the old one, which is exactly the case the functional form exists for. Both work here, but the plain form stops working the moment this is called twice in one event or from an async callback — and the functional form costs nothing.

aria-expanded is not optional here. The button controls whether content is visible, and without it a screen-reader user is told "Hide details, button" with no indication that anything appeared. It is one attribute and it is the difference between a working disclosure widget and a confusing one.

The trade-off worth knowing: {open && …} unmounts the paragraph, which destroys any state inside it. For a static paragraph that is ideal — nothing is rendered when nothing is needed. If the hidden content held a form the user had typed into, unmounting would discard it, and hiding with CSS would be the better choice.

2 (easy): What renders after one click, and why? onClick={() => { setN(n + 1); setN(n + 1); }} with n starting at 5.
Solution 
// It renders 6.
//
//   setN(n + 1)   n is 5 in this snapshot  -> queue "set to 6"
//   setN(n + 1)   n is STILL 5             -> queue "set to 6"
//
// Both calls captured the same snapshot. The queue is applied in order:
// set to 6, then set to 6. One render. Final value 6.

// With functional updates:
//   setN(p => p + 1)   5 -> 6
//   setN(p => p + 1)   6 -> 7      final value 7

The point is that batching is not what caused this. That is the usual wrong answer. Batching decided there would be one render rather than two; the value would be 6 either way, because both calls computed from the same constant. Disabling batching would not change the result.

What the queue actually holds: with the plain form, a value — "set to 6" — which overwrites whatever came before it. With the functional form, a function, which React applies to the result of the previous one. That is why one chains and the other does not.

Where this shows up for real: a "add 2 to cart" button that calls addItem() twice, and a quantity that goes up by one. The bug is invisible in a code review that reads each line in isolation, because each line is correct.

3 (medium): Fix this handler: const [user, setUser] = useState({name:"", tags:[]}); function addTag(t){ user.tags.push(t); setUser(user); }
Solution 
function addTag(t) {
  setUser(u => ({ ...u, tags: [...u.tags, t] }));
}
Defect in the originalConsequence
user.tags.push(t) mutates the array React is holdingThe array changes, but nothing is notified — and the mutation has already happened even if the set is later removed
setUser(user) passes the same referenceObject.is(old, new) is true, so React bails out and does not re-render at all
Reads user from the closureTwo addTag calls in one event both start from the same snapshot, so the second overwrites the first

Note the fix copies two levels: a new object and a new array. Copying only the object — { ...u } with the same tags array mutated — would re-render (the object reference is new) while still mutating shared data, which is the worse bug because it appears to work.

Why the functional form matters here specifically: adding two tags in one event. With setUser({...user, tags:[...user.tags, t]}) both calls read the same user, so the second tag replaces the first. With the updater, the second receives the result of the first.

The nesting is a hint. Two levels of spread is fine; if this grows to {...u, profile: {...u.profile, address: {...}}}, that is the state shape asking to be flattened or moved to a reducer with Immer.

4 (medium): A profile form has firstName, lastName and email. Implement it with one state object and a single change handler.
Solution 
function Profile() {
  const [form, setForm] = useState({ firstName: "", lastName: "", email: "" });

  const onChange = e =>
    setForm(f => ({ ...f, [e.target.name]: e.target.value }));  // computed key

  return (
    <form>
      <label>First name
        <input name="firstName" value={form.firstName} onChange={onChange} />
      </label>
      <label>Last name
        <input name="lastName" value={form.lastName} onChange={onChange} />
      </label>
      <label>Email
        <input name="email" type="email" value={form.email} onChange={onChange} />
      </label>
    </form>
  );
}

Why grouping is right here and not always: these three fields are one cohesive record, edited together and submitted together. That satisfies the "group what changes together" heuristic. A modal-open flag in the same object would not — it changes for unrelated reasons, and putting it there means every keystroke produces a new object for it too.

The name attribute is doing real work. It is both the form field name and the state key, which is what allows one handler for any number of fields. The risk is that it is a string with no compile-time check — a typo in name silently adds a new key to the object instead of updating the intended one, and nothing warns. In TypeScript, typing the handler's key as keyof typeof form closes that hole.

Each input is wrapped in a <label> rather than left bare. An input with no label is unusable with a screen reader and has a smaller click target — and wrapping avoids needing matching id/htmlFor pairs.

What comes next in a real form: validation state and submission state. Note that neither belongs in this object — validation errors are derived from the values, and submission is a status union. Keeping them separate is what stops this growing into an unmanageable blob.

5 (medium): A search box stores results, resultCount and hasResults in state. Refactor to minimal state and say what you deleted.
Solution 
function Search() {
  const [query, setQuery]     = useState("");     // real: what the user typed
  const [results, setResults] = useState([]);     // real: what the server returned

  const resultCount = results.length;             // derived
  const hasResults  = resultCount > 0;            // derived
  const isEmpty     = query !== "" && !hasResults; // derived
}
DeletedWhat it cost while it existed
resultCount state and its setterEvery path that set results had to set this too — and the "clear search" path did not
hasResults state and its setterSame, plus it could contradict resultCount: count 0 with hasResults true is representable
The sync code at every call siteThree lines instead of one at each of the places results change, all of which must stay in agreement forever

The test for "is this really state": could I compute it from something else I already hold? If yes, computing is free of an entire failure mode. Renders are cheap; results.length is not a performance concern at any realistic size, and reaching for useMemo here would add cache management to solve nothing.

The state that remains is exactly the two things nothing else can produce: what the user typed, and what the server said. That is a good sanity check on any component — the state should be the inputs to the system, and everything visible should be a function of them.

What I would question next: whether results should be local state at all. It is server data, so it has staleness, race conditions between overlapping requests, and caching questions that useState does not address — see Data Fetching for why the last-response-wins race is the bug this component almost certainly has.

6 (hard): Build an undoable counter: plus and minus buttons, and an Undo that steps back through history. Design the state shape first.
Solution 
function UndoCounter() {
  // ONE piece of state: the history. The current value is DERIVED.
  const [history, setHistory] = useState([0]);
  const value = history[history.length - 1];

  const apply = delta => setHistory(h => [...h, h[h.length - 1] + delta]);
  const undo  = ()    => setHistory(h => (h.length > 1 ? h.slice(0, -1) : h));

  return (
    <div>
      <button type="button" onClick={() => apply(-1)} aria-label="Decrease">−</button>
      <b>{value}</b>
      <button type="button" onClick={() => apply(1)} aria-label="Increase">+</button>
      <button type="button" onClick={undo} disabled={history.length === 1}>Undo</button>
    </div>
  );
}

The design decision is that the history is the state and the value is derived. Storing both value and history would be redundant state: undo would have to pop the stack and set the value, and any path that forgets one desyncs them permanently.

DetailWhy
useState([0]), not []An empty history has no current value. Seeding with the initial value means value is never undefined and there is no special case
h.length > 1 ? … : hReturning the same reference when there is nothing to undo triggers React's bail-out — no re-render for a no-op, for free

The honest limitation: the history grows forever. For a counter that is irrelevant; for a text editor it is a memory leak, and the standard fix is a bounded stack — [...h, next].slice(-50) — which trades unlimited undo for a fixed ceiling.

The extension worth noticing: adding redo means splitting into { past, present, future }, because undo must remember what it undid. At that point the transitions have rules — a new action clears the redo stack — and rules about transitions are what useReducer is for. This exercise sits exactly at the boundary where useState stops being the right tool.

7 (hard): Explain precisely why this stopwatch sticks at 1, then fix it two ways and say which you would ship: useEffect(() => { const id = setInterval(() => setSec(sec + 1), 1000); return () => clearInterval(id); }, []);
Solution 
  WHY IT STICKS

  1. The effect has [] deps, so it runs once, on mount.
  2. The interval callback it created is a CLOSURE over that render's
     `sec`, which is 0. That binding never changes.
  3. Tick 1: computes 0 + 1, sets 1. React re-renders.
  4. The re-render creates a new `sec` (1) and a new callback —
     but the effect does not re-run, so the INTERVAL still holds the
     old callback.
  5. Tick 2: computes 0 + 1 again, sets 1. React compares with
     Object.is, sees 1 === 1, and BAILS OUT — it does not even
     re-render.
  6. Forever.

  The display is not frozen because the timer stopped. The timer is
  running perfectly and setting the same value every second.

Ship A. B is not merely less tidy — it is less correct. Restarting the interval on every tick means the clock loses a few milliseconds each second, which is visible after a few minutes.

The general rule this teaches: when an effect needs a value only to compute the next one, do not put the value in the dependency array — restructure so the value is not needed. Functional updates are one form of that; a ref holding the latest value is another, for cases where you need to read rather than update.

What a real stopwatch does instead, and it is worth knowing why: counting ticks is inaccurate regardless of the fix, because intervals are throttled in background tabs and delayed under load. A correct stopwatch stores the start timestamp and computes Date.now() - startedAt on each tick, so a missed tick changes the update frequency but never the displayed time. This exercise fixes the React bug; the timing bug underneath it is a different lesson.

🎯 Key Takeaways

  • State is a per-render snapshot stored on the fiber. Setters never change the current render's value — they schedule the next render.
  • Three setN(n + 1) calls add one, because all three read the same constant. Three setN(p => p + 1) add three, because updaters chain.
  • Use the functional form whenever the next value depends on the previous — and when unsure, since it is never wrong.
  • A stale closure in an interval sets the same value forever, and React's bail-out means it does not even re-render — the timer is running, the value is not moving.
  • React 18 batches everywhere, not only in React event handlers; flushSync is the narrow escape hatch for measuring the DOM between updates.
  • Setting the same value bails out. For objects, "same" means the same reference — which is exactly why mutation renders nothing.
  • Immutable updates need a new reference at every level on the changed path; spread is shallow by design, and that is what keeps unchanged branches memoizable.
  • sort and reverse mutate while looking like pure expressions — toSorted/toReversed instead.
  • Do not store what you can derive. A derived value in state is a second source of truth that some future code path will forget to update.
  • Lazy-initialise expensive starting values with useState(() => …) — otherwise the work runs on every render and is discarded.
  • Group state that changes together; split state that changes independently. One mega-object makes every keystroke look like a change to everything.
  • Make contradictions unrepresentable — one status union rather than isLoading plus isError, ideally discriminated so the compiler enforces it.
  • Setting state during render is an infinite loop; setters belong in handlers and effects, and derived values just get computed.
  • Mutable values that should not redraw the UI belong in a ref, not state.
  • State lives on the fiber, so unmounting destroys it — which is the same identity rule that key exploits deliberately.
