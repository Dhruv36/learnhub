Server Components Full-Stack React

What you'll master: the one distinction the entire topic rests on — a Server Component runs only on the server and ships zero JavaScript, while SSR renders components to HTML and then hydrates those same components in the browser; what 'use client' actually marks — an entry point into the client bundle, not a label on a file — so everything it imports goes with it; the serialisation rules, including why you can pass a server component as children but never pass a function; async components and the fetch waterfall they dissolve; the payload format and streaming; server actions and the fact that each one is a public HTTP endpoint; caching; and an honest read on who should adopt this today. Prerequisites: Data Fetching — the waterfall this dissolves — and Architecture for Large Apps.

Part 1 — Where Your Code Runs: Three Models, Not Two

Almost every argument about Server Components is really two people using the word "server" to mean different things. Pin the three models down before anything else, because the difference is not a preference — it is a difference in what bytes reach the browser.

  CSR — a plain SPA (Vite, CRA)

    GET /             ->  <div id="root"></div>        an empty shell
    GET bundle.js     ->  380 KB of JavaScript
    React boots, renders a skeleton, THEN starts fetching data
    Useful pixels appear after three sequential round trips.

  SSR — server-side rendering (Next.js Pages Router, Remix, renderToString)

    server:  runs YOUR components, produces HTML
    browser: paints that HTML fast — then downloads THE SAME COMPONENTS
             AGAIN as JavaScript and HYDRATES them: attaches listeners,
             re-runs render to rebuild the tree in memory
    The component code travels TWICE — once as HTML, once as JS.

  RSC — React Server Components

    server:  runs SERVER components, produces a SERIALISED UI TREE —
             not HTML; a description of elements, props and holes
    browser: receives that tree, plus JavaScript for the CLIENT
             components only
    A server component's own code is NEVER sent. Zero bytes, not
    "fewer bytes".
  THE SENTENCE THAT SEPARATES SSR FROM RSC

    SSR is about WHEN the first HTML is produced.
    RSC is about WHETHER THE COMPONENT'S CODE EXISTS ON THE CLIENT AT ALL.

  They are orthogonal, and in practice they are used together: on the
  first request a framework renders the server tree AND turns it into
  HTML, so the browser has something to paint immediately. But on a
  client-side navigation no HTML is involved — the browser fetches the
  RSC payload and patches the existing tree in place.

  One question settles which you are looking at:

    AFTER HYDRATION FINISHES, CAN THIS COMPONENT RE-RENDER IN THE BROWSER?

      SSR'd client component  -> YES. Its code is in the bundle, it holds
                                 state, it re-renders on every keystroke.
      server component        -> NO. There is no code for it in the
                                 browser. A new version requires a
                                 request to the server.

  "SSR means no JavaScript is sent" is the most common wrong sentence in
  this whole area. SSR sends ALL of it — it just sends HTML first.
CSR (SPA)SSR + hydrationRSC

First paint has contentNo — empty shellYesYes (when SSR'd, which is the norm)
Where data is fetchedIn an effect, after mountIn a route-level loader, then again on navigationInside the component, with await
Cost of a big dependency (markdown, syntax highlighter)ShippedShippedRuns on the server; not shipped

🔑 The measurable claim is about the bundle, not about speed. A page whose content is a markdown article rendered with remark plus a syntax highlighter ships roughly 120–200 KB of parser to every visitor in a CSR or SSR app. As a server component it ships zero — the parser runs once, on the server, and only its output crosses. If your page is mostly interactive widgets, RSC saves you very little, because those widgets have to be client components anyway. Know which kind of page you have before claiming a win.

Part 2 — The Boundary, and What 'use client' Actually Marks

In an RSC application every module is server-side by default. There is no directive at the top of your pages, and there does not need to be — the default is the server. The only directive that changes module placement is 'use client', and almost everyone reads it wrong on first contact.

  'use client' DOES NOT MEAN "THIS FILE IS A CLIENT COMPONENT".

  It marks a DOOR: the point where the module graph crosses from the
  server into the client bundle. Everything reachable through that door
  — every import, and every import of those imports — is compiled into
  the client bundle, whether or not it carries the directive itself.

    app/page.js              server, no directive
      imports Chart.js       'use client'   <-- THE DOOR
        imports d3                 no directive, but SHIPPED (~90 KB)
        imports lib/format.js      no directive, but SHIPPED
          imports date-fns         no directive, but SHIPPED (~20 KB)
        imports lib/db.js          no directive, and now your DB client
                                   is in the browser bundle — or the
                                   build fails, if you were lucky

  page.js ships 0 bytes. Everything below the door ships.

  This is why "I added 'use client' to lib/utils.ts to make the error go
  away" is a real incident and not a style nit. That file is imported by
  forty components; the directive does not annotate a component, it
  drags a transitive closure into the browser.
  PUSH THE BOUNDARY DOWN, NEVER UP

  BAD — one piece of state at the top turns the entire route client-side:

    // app/dashboard/page.js
    'use client';
    export default function Dashboard() {
      const [tab, setTab] = useState('sales');
      return (
        <>
          <Tabs value={tab} onChange={setTab} />
          <MarkdownReport />    {/* now a client component */}
          <RevenueTable />      {/* now a client component */}
        </>
      );
    }

    Consequences: the markdown parser ships; RevenueTable can no longer
    query the database, so it needs an API route and a fetch-in-effect;
    you have rebuilt the SPA you were trying to leave.

  GOOD — only the thing that owns state crosses:

    // app/dashboard/page.js         (server — no directive)
    export default async function Dashboard() {
      const rows = await db.revenue.findMany();
      return (
        <Tabs>                                {/* client: owns tab state */}
          <MarkdownReport />                  {/* server */}
          <RevenueTable rows={rows} />        {/* server */}
        </Tabs>
      );
    }

  Tabs is a client component whose CHILDREN are server components. That
  is legal, it is the composition rule that makes RSC usable, and Part 3
  explains exactly why it works.

⚠️ The directive must be the first statement in the file, before imports, and it applies to the whole module. There is no per-function version. Two consequences people trip on: a file cannot export one server and one client component, and the directive is not inherited downward — a client component's imports become client code automatically, so repeating 'use client' in every child file is noise, not safety.

Part 3 — Serialisation: What Can Cross the Boundary

A server component's output is serialised, written to a stream, and reconstructed in the browser. Every prop that crosses from server into client has to survive that trip. This single constraint generates most of RSC's error messages, and the rule underneath it is short: you can send a value, never a computation.

Passing this to a client componentWorks?Mechanism / what you see
Strings, numbers, booleans, null, undefinedYesWritten directly into the payload
Plain objects and arrays of serialisable valuesYesRecursively encoded. Note that the whole object crosses, including fields you never render
Date, Map, Set, BigInt, typed arraysYesThe RSC format is richer than JSON; these round-trip correctly
A PromiseYesSent as a pending hole and resolved by a later row; the client unwraps it with use()
JSX — including a rendered server componentYesWhat crosses is the already-rendered element tree, not the component function
A reference to a server actionYesEncoded as an ID, not as code. Calling it issues an HTTP POST — see Part 5
A plain function or arrow functionNo"Functions cannot be passed directly to Client Components." A closure has no wire representation
A class instance (an ORM model, a Decimal)NoFields might encode, but the prototype and its methods cannot be rebuilt. Convert to a plain object first
A render prop, renderItem={…}NoSame error as any function — and the reason is worth understanding, below
  WHY children WORKS AND A RENDER PROP DOES NOT

    <ClientTabs><ServerReport /></ClientTabs>        ✅
    <ClientTabs render={() => <ServerReport />} />   ❌

  In the first, the SERVER evaluates ServerReport while building the
  tree. What crosses the boundary is the RESULT — an already-rendered
  element tree sitting in the children prop. ClientTabs receives it as
  opaque data and drops it into a slot. It never calls anything.

  In the second, ClientTabs would have to CALL your function to obtain
  the element. That call would happen in the browser, so the function
  body would have to exist in the browser — and it closes over
  server-only scope: the db handle, the request, your secrets. There is
  nothing to serialise and nothing safe to send.

  THE GENERAL RULE:
    a VALUE can cross the boundary.   children is a value.
    a COMPUTATION cannot.             a render prop is a computation.

  Everything else follows. Event handlers are computations. Callbacks
  are computations. Server actions are the deliberate exception: they
  cross as an ID, and invoking one is a network request, not a call.
  THE COST PEOPLE FORGET: EVERY CROSSING PROP IS SENT TWICE

    <ProductCard product={product} />      // product = 4 KB of JSON

  On the first request that 4 KB appears in the streamed HTML — inlined
  so hydration can read it — AND in the RSC payload. If the card renders
  three fields, you paid roughly 8 KB to deliver about 80 bytes.

    ✅ Pass what is rendered, not what you fetched:
       <ProductCard name={p.name} price={p.price} id={p.id} />

  Across a list of 50 products this is the difference between a 60 KB
  document and a 400 KB one, and it is invisible in development where
  the fixture has three rows and no throttling.

Part 4 — Async Components, the Payload, and Streaming

A server component may be an async function. That is not a convenience — it is what makes the boundary worth crossing, because it removes the client-side request chain entirely.

  THE WATERFALL RSC DISSOLVES

  Fetch-in-effect, on the client:

    Page mounts        -> render (no data)
      useEffect        -> GET /api/user             180ms
        user arrives   -> render Posts userId=7
          useEffect    -> GET /api/posts?u=7        180ms
            posts      -> render Comments postId=12
              useEffect -> GET /api/comments?p=12   180ms
                                       ---------------------
                                       540ms of latency, plus TLS,
                                       plus auth on every hop

  Each request cannot START until the previous render finished, because
  the id it needs came from the previous response. That is a waterfall,
  and it is a property of the DEPENDENCY CHAIN — no amount of caching or
  HTTP/2 multiplexing removes it.

  The server component version:

    export default async function Page() {
      const user  = await db.user.find(7);                //  4ms
      const posts = await db.post.forUser(user.id);       //  6ms
      const cmts  = await db.comment.forPost(posts[0].id);//  5ms
      return <Feed user={user} posts={posts} comments={cmts} />;
    }

  Same three-step chain. Each hop is now a query inside one datacentre
  instead of a public round trip: ~15ms instead of 540ms.

  RSC DID NOT REMOVE THE WATERFALL. It moved it to where each step costs
  milliseconds. That distinction matters, because the sequential-await
  mistake is still a mistake:

    ❌ const a = await getA();   // independent of b
       const b = await getB();   // waits for A for no reason
    ✅ const [a, b] = await Promise.all([getA(), getB()]);
  THE PAYLOAD — the "flight" format, simplified

  A request for /dashboard with the RSC accept header returns a text
  stream of numbered rows, not HTML:

    1:I["./chunk-a1.js","Tabs"]
    0:["$","div",null,{"children":[
         ["$","$L1",null,{"label":"Sales"}],
         ["$","p",null,{"children":"Revenue: 42"}]]}]
    3:["$","table",null,{"children":[ ... 900 rows ... ]}]

  Three things to notice:

    - IT IS NOT HTML. It is a description of elements: type, props,
      children. The browser reconstructs React elements from it and
      reconciles them against the existing tree — which is why a
      navigation can update part of a page without a full reload and
      without destroying client state elsewhere in the tree.

    - "$L1" IS A HOLE pointing at row 1, which is a MODULE REFERENCE,
      not code: "load ./chunk-a1.js and use its Tabs export". Client
      component code is fetched separately by the normal bundler
      machinery, and cached like any other chunk.

    - ROWS ARRIVE OVER TIME. Row 3 can be written to the same response
      two seconds after row 0. That is all streaming is: one long
      response, filled in as data resolves.

  You rarely read this format by hand. You DO need its shape in your
  head to understand why props must serialise and why a 4 KB prop
  costs 4 KB.
  STREAMING WITH SUSPENSE

    export default async function Page() {
      const user = await getUser();        // 20ms — BLOCKS the response
      return (
        <>
          <Header user={user} />
          <Suspense fallback={<Skeleton />}>
            <SlowAnalytics />              // 900ms — does NOT block
          </Suspense>
        </>
      );
    }

  The response opens as soon as Header is ready, at roughly 20ms.
  SlowAnalytics becomes a hole; its row is appended 900ms later and
  React swaps the skeleton for real content with no flash and no layout
  shift, PROVIDED the skeleton reserves the same space.

    TTFB is set by the fastest awaited thing ABOVE the first Suspense
    boundary — not by the slowest thing on the page.

  THE COROLLARY MOST PEOPLE MISS: an await that is NOT inside a Suspense
  boundary blocks the entire document. One un-suspended 900ms call in a
  shared layout sets TTFB for every route beneath it, and it will not
  show up in a component-level profile — the layout looks innocent.
Where the slow await livesWhat the user seesEffect on TTFB
Directly in a layout, no boundaryA blank tab until it resolvesSets TTFB for every nested route. The worst placement, and the least visible
Directly in the page, no boundaryBlank until the whole page is readySets TTFB for that route only
In a child inside SuspenseShell immediately, then the section fills inNone. This is the placement you want for anything above ~100ms
Several siblings, each in its own boundarySections appear independently as they resolveNone — and the slowest no longer holds the others hostage

Awaited in a client component via use()Depends on the boundary above it; the promise must still be created on the serverNone, but the resolved data crosses the wire as a serialised value
🔑 A Suspense boundary is also the loading and error boundary for the region it wraps — see Error Boundaries and Concurrent React. Placing boundaries is therefore a UX decision, not a performance tweak: each one defines a chunk of the page that can fail, load, or arrive independently. Wrapping the whole app in one boundary at the root gives you streaming with none of the benefit.

Part 5 — Server Actions: Mutations, and a Public HTTP Endpoint

Server components read. Server actions write. The 'use server' directive marks a function as remotely callable — and that is the whole of it, which is exactly why the security consequences catch people out.

  // app/actions.js
  'use server';                 // FILE-LEVEL: every export in this file
                                // becomes a callable HTTP endpoint

  export async function deletePost(formData) {
    const id = formData.get('id');
    await db.post.delete({ where: { id } });
    revalidatePath('/posts');   // tell the framework the cache is stale
  }

  // Called from a SERVER component with zero client JavaScript:
  <form action={deletePost}>
    <input type="hidden" name="id" value={post.id} />
    <button>Delete</button>
  </form>

  This form works with JavaScript disabled: it is a real HTML form
  posting to a real endpoint, and React progressively enhances it once
  hydration completes.

  // Called from a CLIENT component, with pending state (React 19):
  const [state, action, pending] = useActionState(deletePost, null);
  <form action={action}>
    <button disabled={pending}>{pending ? 'Deleting…' : 'Delete'}</button>
  </form>
  THE SECURITY MODEL, STATED PLAINLY

  A server action compiles into a POST endpoint identified by a
  generated, stable ID. That ID is present in the client bundle.
  Therefore ANYONE CAN CALL IT:

    curl -X POST https://your.app/posts \
      -H 'Next-Action: 7f3a91c0e2b4…' \
      -F 'id=42'

  Four consequences that get people wrong:

  1. HIDING THE UI HIDES NOTHING.
     If the Delete button only renders for admins, the ACTION is still
     callable by anyone who read the bundle. Authorisation belongs
     INSIDE the action body, on every single invocation. A conditional
     in JSX is a UI affordance, not an access control.

  2. THE ARGUMENTS ARE ATTACKER-CONTROLLED.
     The formData you receive did not necessarily come from your form.
     Validate shape, type and range server-side with a schema, exactly
     as you would in a REST handler. "It came from my own UI" is not a
     property you can check.

  3. CLOSED-OVER VALUES TRAVEL TO THE BROWSER AND BACK.
       const del = deletePost.bind(null, post.id)
     The bound argument is serialised into the payload, sent to the
     client, and posted back on invocation. Next.js encrypts these so
     they are tamper-resistant, but they still LEAVE the server — never
     bind a value the client must not see, and never assume a bound
     argument arrived unmodified without checking authorisation anyway.

  4. 'use server' IS NOT THE OPPOSITE OF 'use client'.
     'use client' marks a BUNDLE ENTRY POINT.
     'use server' marks a REMOTE PROCEDURE — an endpoint.
     A file with neither directive is already server-only. Adding
     'use server' to an ordinary helper does not "make it more
     server-y"; it exposes it to the internet.

⚠️ Treat every server action review as an endpoint review. The mental shortcut that works: before merging, ask "if this function's name and arguments were published on the front page of the internet, what could someone do?" That is the actual threat model, because the ID and the argument shape are in the bundle. The same reasoning applies to route handlers — see JavaScript Security.

Part 6 — Caching, Revalidation, and Whether to Adopt This

  REACT ITSELF CACHES ALMOST NOTHING. THE FRAMEWORK DOES.

  React's own contribution is request-scoped deduplication:

    import { cache } from 'react';
    export const getUser = cache(async id => db.user.find(id));

  Two server components both calling getUser(7) during ONE request run
  ONE query. The memo lives for the duration of that render and is
  discarded afterwards.

  That is not a data cache — it is what lets you stop prop-drilling.
  Any component that needs the user calls getUser() directly instead of
  receiving it through six layers of props, and you pay for one query.

  Everything longer-lived belongs to the framework. Next.js layers a
  fetch cache, a full route cache and a client router cache on top,
  each with its own lifetime and its own way of being wrong.
LayerLives whereLifetimeHow it goes wrong
React cache()Server, per requestOne render passRarely. It is scoped so tightly that staleness is impossible
Framework data cache (fetch results, tagged queries)Server, shared across requests and usersUntil revalidated by time or tagCaching a per-user response. One user's data served to another — the highest-severity RSC bug there is
Full route cache (the prerendered payload)Server / CDNUntil the route is revalidated or redeployedA route silently prerendered at build time with data that has since changed
Client router cacheBrowser memorySeconds to minutes, per sessionBack-navigation shows the pre-mutation version; feels like the write was lost
CDN / Cache-ControlEdgeWhatever the header saysA personalised page cached publicly. Always private or no-store once a session is involved
  REVALIDATION — three tools, one rule

    revalidatePath('/posts')      // this route's cached output is stale
    revalidateTag('posts')        // every fetch tagged 'posts' is stale
    export const revalidate = 60  // time-based: recheck at most once a
                                  // minute (ISR)

  THE RULE: a write is not finished until the reads that depend on it
  have been invalidated. Every mutation path needs its matching
  revalidate call, and the commonest production bug in an RSC app is a
  server action that writes correctly and invalidates nothing.

  Tags scale better than paths. A path invalidation says "this URL";
  a tag says "everything derived from this data", which is what you
  actually mean when a post is edited and it appears on the home page,
  the author page and the tag listing.

  AND THE ONE THAT BITES HARDEST: never cache a response that depends on
  the current user unless the cache key includes the user. A shared
  cache plus a personalised response is a data-leak, not a performance
  problem.
  THE HONEST COST OF ADOPTING RSC

  ECOSYSTEM. A library that calls useState, useEffect or createContext,
  or touches window at module scope, cannot run in a server component.
  A great many do. The workaround — a one-line 'use client' wrapper file
  per library — works and is tedious, and it pulls the whole library
  into the bundle anyway. Chart libraries, most animation libraries and
  most component kits are client-only in practice, so the "zero JS"
  headline applies to your content, not to your widgets.

  DEBUGGING. A stack trace can now span two runtimes. "Functions cannot
  be passed directly to Client Components" tells you a boundary was
  violated but frequently not WHICH PROP in WHICH FILE. Hydration
  mismatches are harder to reason about than in plain SSR because the
  server tree and the client tree came from different code paths.

  MENTAL OVERHEAD. Every file now carries an invisible attribute: which
  runtime am I in? Engineers new to the model get this wrong constantly,
  and the failure is usually SILENT — a component that works perfectly
  and shipped 40 KB it did not need to. You need a bundle-size check in
  CI, or the boundary drifts upward one PR at a time.

  LOCK-IN. There is no production-grade standalone RSC runtime. Adopting
  RSC means adopting a framework that implements it: realistically
  Next.js, with React Router v7, Waku and Parcel's implementation as the
  smaller alternatives. Your build, your routing and your deployment
  target all become framework decisions.
SituationVerdict todayReasoning

🔑 The honest summary: RSC is a genuinely good answer to a specific problem — content-heavy pages carrying large render-time dependencies and a fetch waterfall — and an expensive answer to anything else. The React team's framing that it is "the future" and the critics' framing that it is "complexity for its own sake" are both marketing. Judge it against your own page: what fraction of your bundle exists only to render content that never changes after paint? If that fraction is large, RSC pays. If it is small, it does not.

Interview Questions

Beginner: What is a Server Component, and how is it different from server-side rendering?

A Server Component is a component that runs only on the server. Its output is a serialised description of UI — element types, props and children — which is streamed to the browser and turned back into React elements there. The component's own code is never sent to the client, so it contributes zero bytes to the JavaScript bundle.

SSR is a different thing. With SSR the server runs your components to produce HTML so the first paint has content, and then the browser downloads those same components as JavaScript and hydrates them — attaching event listeners and rebuilding the tree in memory. The component code travels twice.

The clean way to separate them: SSR is about when the first HTML appears; RSC is about whether the component's code exists on the client at all. They are orthogonal, and in practice they are used together — a framework will SSR the server tree on the first request so the browser has something to paint.

The practical test is: after hydration, can this component re-render in the browser? An SSR'd client component can, because it is in the bundle and holds state. A server component cannot — there is no code for it there.

Beginner: What does 'use client' do, and where should it go?

It marks a module as an entry point into the client bundle. It is not a label saying "this file is a client component" — it is the boundary crossing itself. Everything reachable from that module, its imports and their imports, is compiled into the browser bundle whether or not those files carry the directive.

That is why placement matters so much. A directive on a page turns the whole route into client code: you lose direct data access, the markdown parser or chart library you were rendering on the server now ships, and data fetching regresses to effects. A directive on a small leaf component costs you only that leaf.

So the rule is: push the boundary as far down the tree as it will go. Give the client component the interactive part, and pass server-rendered content into it as children.

Two mechanical details worth knowing: it must be the first statement in the file, before imports, and it applies to the entire module — you cannot mark one export client and another server, and you do not need to repeat it in files that a client component imports.

Mid: Why can you pass a server component as children to a client component, but not pass a function?

Because children is a value and a function is a computation, and only values can be serialised.

When you write a client component with a server component inside it, the server evaluates that server component while building the tree. What crosses the boundary is the result — an already-rendered element tree occupying the children prop. The client component treats it as opaque data and drops it into a slot. It never calls anything, so nothing about the server component's implementation needs to exist in the browser.

A render prop is the opposite. The client component would have to invoke your function in the browser to obtain an element. That requires the function body to be present there — and that body closes over server-only scope: a database handle, the request, secrets. There is nothing to serialise, and nothing safe to send if there were.

The same reasoning covers event handlers and callbacks: all computations, all rejected. The single deliberate exception is a server action, which crosses as an opaque ID rather than as code. Calling it is not a function call at all — it is an HTTP POST back to the server, which is why it is allowed and also why it needs its own authorisation.

Mid: How does streaming with Suspense change time-to-first-byte, and what silently blocks it?

Without streaming, the server must finish the entire tree before writing anything, so TTFB is set by the slowest data dependency on the page. With Suspense, the server writes the shell as soon as the content above the first boundary is ready, and each suspended subtree is appended to the same response as its data resolves. TTFB becomes a function of the fastest awaited work above the first boundary rather than the slowest work anywhere.

The mechanism is visible in the payload: a suspended subtree is emitted as a hole, and a later numbered row in the same response fills it in. Nothing about it requires a second request.

What silently blocks it is an await that is not underneath any boundary — and the dangerous version of that is in a shared layout. A single 900ms call in a layout sets TTFB for every route nested inside it, and it will not appear in a component-level profile because the layout looks trivial. I would check layouts first when TTFB is uniformly bad across unrelated routes.

Two further practicalities. Skeleton fallbacks must reserve the same space as the real content, or streaming trades a slow page for a janky one and you lose on CLS what you gained on TTFB. And boundary placement is a UX decision: each boundary defines a region that loads, fails and arrives independently, so one boundary at the root technically streams and delivers nothing useful.

Senior: A colleague says a server action is safe because the button that calls it only renders for admins. Walk through what is actually true, and how you would secure it.

The claim is wrong, and the reason is structural rather than a bug. A server action is compiled into a POST endpoint identified by a generated, stable ID, and that ID ships in the client bundle. Anyone can read it and issue the request with curl. Conditionally rendering the button controls what a browser displays; it does not control what the endpoint accepts. It is exactly the same fallacy as hiding a REST route from the navigation menu.

What I would require in the action body, on every invocation. First, authentication read from the session on the server — not from an argument, since arguments are caller-controlled. Second, authorisation against the specific resource, because ownership depends on the ID that was passed in; "is this user an admin" and "may this user delete this row" are different questions, and skipping the second is the classic insecure-direct-object-reference. Third, schema validation of every field, since FormData values are strings supplied by whoever made the request. Fourth, rate limiting, because this is an internet-facing POST like any other.

Then the things people forget. Bound arguments — action.bind(null, post.id) — are serialised to the browser and posted back; Next.js encrypts them so they are tamper-resistant, but they still left the server, so never bind a value the client must not see, and never treat a bound argument as trusted input in place of an authorisation check. Errors should be returned as serialisable values rather than thrown, so stack traces and internal paths do not reach the payload. And anything that costs money needs an idempotency key, because retries and double-clicks re-invoke.

The trade-off worth naming is that server actions blur the boundary that a REST layer made obvious. With an API route you know you are writing an endpoint and you reach for the endpoint checklist. With an action it looks like a local function call in the same file as your JSX, and the checklist does not come to mind. That ergonomic win is real and so is the risk it creates.

My recommendation: wrap actions in a small helper that takes a permission and a schema and returns the guarded function, so the checks are structurally impossible to forget, and add a lint rule that fails any exported action not created through it. Review every action as an endpoint review — ask what someone could do if its name and argument shape were published, because effectively they are.

Senior: Would you adopt RSC on a project today? Argue both sides and give a recommendation.

It depends on the shape of the page, and I would want that measured before deciding. The question I would ask is: what fraction of the bundle exists only to render content that never changes after paint? For a docs site, a commerce catalogue or a content-heavy marketing site that fraction is large — markdown parsers, syntax highlighters, date libraries, formatting code — and moving it to the server is a real, measurable win on bundle size and LCP, plus data access without an API layer in between. For an internal dashboard where almost everything is an interactive widget, that fraction is small, nearly every component has to be a client component anyway, and the win is close to zero.

The case against is not ideological, it is operational. The ecosystem still assumes client-side execution: anything calling useState or touching window at module scope needs a 'use client' wrapper, which works but is friction on every dependency and pulls the library into the bundle regardless. Debugging spans two runtimes, and the error messages frequently tell you a boundary was violated without telling you which prop in which file. The mental overhead is permanent: every file now has an invisible runtime attribute, and getting it wrong usually fails silently — the component works and shipped 40 KB it did not need to. Without a bundle-size check in CI, the boundary creeps upward one pull request at a time.

And there is lock-in worth stating plainly. There is no production-grade standalone RSC runtime, so adopting RSC means adopting a framework that implements it — realistically Next.js, with React Router v7 and Waku as smaller alternatives. Build, routing and deployment target all become framework decisions at once.

So my recommendation splits three ways. For a new content-heavy project where the team is already on Next.js: adopt, because there is no migration cost and starting on the Pages Router means migrating later anyway. For an existing large SPA with a working API and CDN: do not rewrite — the migration is measured in quarters and the same bundle win is available from code splitting at a fraction of the cost; adopt on new routes if at all. For anything offline-first or in a native shell: no, because the model assumes a reachable server on every navigation.

The framing I would push back on in either direction is that this is settled. It is not. The React team calls it the future and the critics call it complexity for its own sake, and both are positions rather than measurements. Measure your own page.

1 (easy): This page has 'use client' at the top because one button needs an onClick. Restructure it so the article stays on the server.
Solution 
  BEFORE — the whole route is client code

    'use client';
    import { renderMarkdown } from 'lib/markdown';   // 140 KB, now shipped
    export default function Article({ html, id }) {
      const [saved, setSaved] = useState(false);
      return (
        <article>
          <button onClick={() => setSaved(true)}>
            {saved ? 'Saved' : 'Save'}
          </button>
          <div dangerouslySetInnerHTML={{ __html: renderMarkdown(html) }} />
        </article>
      );
    }

  AFTER — two files, boundary at the leaf

    // SaveButton.jsx
    'use client';
    export function SaveButton({ id }) {
      const [saved, setSaved] = useState(false);
      return <button onClick={() => setSaved(true)}>
               {saved ? 'Saved' : 'Save'}
             </button>;
    }

    // page.jsx                                   (server — no directive)
    import { renderMarkdown } from 'lib/markdown';
    import { SaveButton } from './SaveButton';

    export default async function Article({ params }) {
      const post = await db.post.find(params.id);
      return (
        <article>
          <SaveButton id={post.id} />
          <div dangerouslySetInnerHTML={{ __html: renderMarkdown(post.body) }} />
        </article>
      );
    }

What the "before" version actually costs at runtime. The directive made page.jsx a client module, so its import of lib/markdown came with it: the parser is downloaded, parsed and executed in every visitor's browser to produce HTML that is identical for every visitor. It also had to receive html as a prop from somewhere, which means the raw markdown crossed the wire and the rendered output was produced client-side — you paid for the source twice over.

Why splitting the file is the whole fix. 'use client' applies to a module, not a function, so there is no way to mark one component in a shared file. Extracting the button is not a stylistic preference; it is the only mechanism the directive offers for controlling what ships.

The remaining risk. dangerouslySetInnerHTML is still dangerous — running on the server does not sanitise anything. If the markdown is user-supplied, sanitise it server-side before it reaches the payload.

2 (easy): A server component reads the user's saved theme from localStorage and the build crashes. Explain and fix.
Solution 
  BROKEN

    export default function Layout({ children }) {
      const theme = localStorage.getItem('theme') ?? 'light';   // ❌
      return <div className={theme}>{children}</div>;
    }

  ReferenceError: localStorage is not defined

  There is no browser here. Server components run in Node (or an edge
  runtime) where window, document and localStorage do not exist. Because
  this is a LAYOUT, the error takes down every route beneath it — not

  FIX A — a cookie, read on the server (best: no flash, no client JS)

    import { cookies } from 'next/headers';
    export default async function Layout({ children }) {
      const theme = (await cookies()).get('theme')?.value ?? 'light';
      return <div className={theme}>{children}</div>;
    }

  FIX B — a client island, if it must be localStorage

    'use client';
    export function ThemeShell({ children }) {
      const [theme, setTheme] = useState('light');
      useEffect(() => setTheme(localStorage.getItem('theme') ?? 'light'), []);
      return <div className={theme}>{children}</div>;
    }

The same call at the top level of a module breaks every route that transitively imports it, including ones that never render the component — which is why this failure so often looks disproportionate to the change that caused it.

3 (medium): This fails with "Functions cannot be passed directly to Client Components". Fix it without making Row a client component.
Solution 
  BROKEN

    // page.jsx  (server)
    <DataTable
      rows={rows}
      renderRow={row => <Row data={row} />}      // ❌ a function
    />

    // DataTable.jsx
    'use client';
    export function DataTable({ rows, renderRow }) {
      const [sort, setSort] = useState('asc');
      return <tbody>{sorted(rows, sort).map(renderRow)}</tbody>;
    }

  FIXED — pass rendered elements, not a way to render them

    // page.jsx  (server)
    <DataTable>
      {rows.map(row => <Row key={row.id} data={row} />)}
    </DataTable>

    // DataTable.jsx
    'use client';
    export function DataTable({ children }) {
      const [sort, setSort] = useState('asc');
      return <tbody>{sort === 'asc'
        ? children
        : [...children].reverse()}</tbody>;
    }

Why the broken version cannot work, mechanically. DataTable runs in the browser. To produce a row it must call renderRow there, which means renderRow's body — and therefore Row, and everything Row imports — has to be in the client bundle. The serialiser refuses before that can happen, because a closure has no wire representation at all.

Why the fix works. rows.map(…) is evaluated on the server. Each Row renders there, and what crosses is the finished element tree sitting in children. DataTable reorders that array — it manipulates elements as opaque values without ever calling a component.

CapabilityRender propchildren array
Rows rendered on the server, zero JS for RowImpossibleYes
Reorder, filter or slice on the clientYesYes — elements are values you can sort
Render a row that did not exist at server render timeYesNo — this is the real limitation
Pass per-row state down from the tableYesNo — the element's props were fixed on the server

Be honest about what you gave up. If the table paginates client-side over ten thousand rows, or generates rows from client state, children cannot express that and Row genuinely has to become a client component. The children trick is not universal — it covers the very common case where the set of rows is known on the server and the client only rearranges them.

Why "the form only shows the user's own orders" is not a defence. The action ID is in the client bundle and the endpoint accepts any well-formed POST. Rendering decisions constrain the browser; they do not constrain the network. Every check has to be inside the function body, on every invocation, with no exceptions for "the UI already checked".

The field that was silently dropped. total is gone from the schema entirely, not validated — it should be derived server-side from the line items. The general rule: do not validate a field the client has no business sending, remove it. A schema that accepts a field invites someone to relax the rule on it later.

Returning errors instead of throwing is deliberate. A thrown error can leak a stack trace and internal paths through the payload, and it forces the caller into an error boundary for what is an ordinary validation failure. A serialisable result object pairs naturally with useActionState, which gives you the message and a pending flag with no extra state.

The subtle one is the provider. A theme or query provider must be a client component, and wrapping the root layout in it is what every tutorial shows. That is fine as long as the provider itself only renders {children} — children passed from a server parent stay server-rendered, because they were already evaluated before crossing. It stops being fine the moment the provider imports and renders anything else, at which point that too is client code.

What I would tell the team afterwards. The regression was not any single bad decision — it was that the model makes the cost invisible. Nothing errors, nothing warns, the feature works. 🎯 Key Takeaways

  • A Server Component runs only on the server and ships zero JavaScript — its code never enters the bundle, and its output is a serialised description of UI, not HTML.
  • SSR and RSC are orthogonal, not competing. SSR is about when HTML appears; RSC is about whether the component's code exists on the client at all.
  • SSR sends every component twice — once as HTML, once as JavaScript to hydrate. "It is server-rendered so nothing is shipped" is false.
  • 'use client' marks an entry point into the client bundle, not a component. Everything it transitively imports ships with it.
  • Push the boundary down, never up. A directive on a page turns the whole route into client code and gives back every benefit.
  • Server components cannot use state, effects, event handlers, context or browser APIs — there is no instance, no DOM and no commit phase.
  • You can pass a value across the boundary, never a computation. children is a value; a render prop, callback or event handler is a computation.
  • A client component may render server components as children — but may never import one, since the import pulls it into the bundle.
  • Every prop crossing the boundary is serialised into both the payload and the inlined HTML — pass the fields you render, not the record you fetched.
  • Async components move the waterfall rather than removing it. Sequential awaits are still sequential; Promise.all still matters.
  • TTFB is set by the fastest work above the first Suspense boundary — and one un-suspended slow await in a layout sets it for every route beneath.
  • A server action is a public HTTP endpoint whose ID ships in the bundle. Authenticate, authorise and validate inside the function, on every invocation.
  • Hiding a button is not authorisation, and bound arguments travel to the browser and back — never treat either as a security boundary.
  • A write is unfinished until the reads it invalidates are revalidated, and caching a personalised response without the user in the key is a data leak, not a perf bug.
  • RSC pays on content-heavy pages with large render-time dependencies and pays very little on interaction-heavy dashboards — measure your own bundle before deciding.
  • The costs are real: ecosystem friction, two-runtime debugging, and silent bundle growth. Without a size budget in CI the boundary creeps upward one pull request at a time.
