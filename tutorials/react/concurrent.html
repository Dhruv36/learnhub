Concurrent Features Performance

What you'll master: why React 18's rewrite was necessary — before it, a render was one uninterruptible synchronous pass and input queued behind it; concurrent rendering means React can pause, abandon and restart a render, which is exactly why render must be pure and why StrictMode double-invokes in development; useTransition versus useDeferredValue and the real distinction — marking an update you trigger versus deferring a value you receive; automatic batching as a genuine behaviour change on upgrade, and flushSync as the escape hatch; useId and why Math.random() breaks hydration; streaming SSR with selective hydration; and tearing. Prerequisites: Code Splitting & Suspense, The Re-render Model.

Part 1 — The Blocking Render, and What "Concurrent" Actually Means

  BEFORE REACT 18, RENDERING WAS ONE SYNCHRONOUS PASS THAT COULD NOT BE
  INTERRUPTED. Once React started rendering a tree, it finished — no
  matter how long that took.

    User types "a" into a filter over 10,000 rows:

      t=0ms     keydown, setState("a")
      t=1ms     React begins rendering 10,000 rows
                >>> MAIN THREAD BLOCKED <<<
      t=180ms   render completes, commit, paint
      t=181ms   the "a" finally appears in the input

    The user typed "abc" quickly. Keystrokes 2 and 3 sat in the event
    queue behind a render they had nothing to do with. The input feels
    like it is lagging — because it is.

  THE FRAME BUDGET makes this concrete. 60fps means a frame every 16.7ms.
  Any single block of main-thread work longer than that drops frames; a
  180ms block drops about eleven in a row, which is what people describe
  as "janky" or "stuttery".

  CONCURRENT RENDERING IS NOT PARALLELISM. There is still ONE thread and
  no worker. What changed is that rendering became INTERRUPTIBLE:

    t=0ms     keydown, transition update begins rendering rows
    t=5ms     React has rendered ~400 rows, CHECKS whether anything more
              urgent is waiting
    t=5ms     keydown for "b" is queued -> React ABANDONS the in-progress
              render, handles the keystroke, paints the input
    t=7ms     React RESTARTS the row render with the value "ab"

  React yields roughly every 5ms, keeping each block well under the frame
  budget. The row list arrives slightly later; the INPUT never stalls.
  That trade — slightly slower background work for an always-responsive
  interface — is the entire feature.
  THIS IS WHY RENDER MUST BE PURE, AND IT IS NO LONGER JUST STYLE ADVICE.

  If React may abandon a render halfway and start over, then any render
  that did something on the way through has now done it twice — or done
  half of it and thrown the rest away:

    let requestCount = 0;

    function Row({ item }) {
      requestCount++;              // ran on the abandoned pass too
      analytics.track("row_seen"); // fired for rows never shown
      cache[item.id] = expensive(item);   // half-populated, then discarded
      return <li>{item.name}</li>;
    }

  In React 17 this was sloppy but survivable, because a render always ran
  exactly once and always committed. In 18 it is a correctness bug.

  STRICTMODE DOUBLE-INVOKES RENDERS AND EFFECTS IN DEVELOPMENT ONLY to
  surface exactly this. It is not a bug and it does not happen in
  production builds. If double-invoking breaks your component, concurrent
  rendering would have broken it too — StrictMode just made it fail on
  your machine instead of a user's.

    DEV, StrictMode on:   render, render, effect, cleanup, effect
    PRODUCTION:           render, effect

  Do not "fix" it with a ref guard to make effects run once. That hides
  the signal without fixing the impurity underneath.

Part 2 — useTransition: Marking an Update You Trigger

  useTransition SPLITS ONE EVENT INTO TWO UPDATES AT DIFFERENT
  PRIORITIES. The canonical case is a filter over a large list:

    function Search({ rows }) {          // rows.length === 10000
      const [query, setQuery] = useState("");
      const [results, setResults] = useState(rows);
      const [isPending, startTransition] = useTransition();

      function onChange(e) {
        const next = e.target.value;
        setQuery(next);                     // URGENT — the input echoes now
        startTransition(() => {
          setResults(rows.filter(r => r.name.includes(next)));  // INTERRUPTIBLE
        });
      }

      return (
        <>
          <input value={query} onChange={onChange} />
          <List rows={results} style={{ opacity: isPending ? 0.6 : 1 }} />
        </>
      );
    }

  WHAT THE USER PERCEIVES — this is the part worth being precise about:

    WITHOUT TRANSITION   Type "abc" fast. Each keystroke blocks ~180ms
                         re-rendering rows. Letters appear late and in
                         bursts. The input feels broken; people retype.

    WITH TRANSITION      Letters appear instantly, every time. The list
                         dims and updates a beat behind — and for "abc"
                         typed quickly, the intermediate lists for "a"
                         and "ab" are ABANDONED and never painted at all.
                         Less total work, and a responsive input.

  BOTH setState CALLS ARE IN THE SAME HANDLER. The difference is purely
  which one React is allowed to interrupt.

  isPending IS THE FEEDBACK CHANNEL. Dimming, a subtle spinner, or
  aria-busy — the user should know stale content is stale. Showing
  nothing at all is worse than a slightly late list.

  THE ONE HARD CONSTRAINT: THE CALLBACK MUST BE SYNCHRONOUS.

    // BROKEN — the update after await is NOT in the transition
    startTransition(async () => {
      const data = await fetch(url).then(r => r.json());
      setResults(data);              // treated as urgent again
    });

    // CORRECT — await outside, transition around the state update
    const data = await fetch(url).then(r => r.json());
    startTransition(() => setResults(data));

  React tracks transition context on the synchronous call stack. An await
  yields the stack, so anything after it has lost it — which is why
  people conclude "useTransition does nothing" and give up on it.

Part 3 — useDeferredValue: Deferring a Value You Receive

  useDeferredValue LOOKS INTERCHANGEABLE WITH useTransition AND IS NOT.
  The distinction is about WHAT YOU CONTROL.

    useTransition      you own the setState -> mark the UPDATE
    useDeferredValue   the value arrives as a prop -> defer the VALUE

  If a prop comes from a parent, a context or a store, there is no
  setState of yours to wrap. That is the case useDeferredValue exists for:

    function Results({ query }) {          // query is a PROP
      const deferred = useDeferredValue(query);
      const isStale = query !== deferred;

      // expensive, keyed off the DEFERRED value
      const rows = useMemo(() => filter(data, deferred), [deferred]);

      return <List rows={rows} style={{ opacity: isStale ? 0.6 : 1 }} />;
    }

  HOW IT BEHAVES: on the urgent render, deferred still holds the OLD
  value, so the expensive work is skipped and the frame is cheap. React
  then schedules a background re-render with the new value, at transition
  priority — interruptible, so fast typing abandons intermediate passes.

  isStale = query !== deferred IS THE isPending EQUIVALENT, and it comes
  for free with no extra state.

  THE MEMO IS NOT OPTIONAL. Deferring the value without memoising the
  work keyed on it accomplishes nothing — the expensive computation still
  runs on the urgent render, just with the old input:

    const deferred = useDeferredValue(query);
    const rows = filter(data, deferred);   // still runs every render

  Equally, the child receiving the deferred value must be memoised, or it
  re-renders on the urgent pass anyway.

Part 4 — Automatic Batching, and flushSync

  BATCHING MEANS SEVERAL setState CALLS PRODUCE ONE RE-RENDER. React 17
  did this ONLY inside React event handlers. Everywhere else, each call
  re-rendered:

    // REACT 17
    function handleClick() {           // React handler -> batched
      setCount(c => c + 1);
      setFlag(f => !f);                // ONE re-render
    }

    fetch(url).then(() => {            // promise -> NOT batched
      setCount(c => c + 1);            // re-render 1
      setFlag(f => !f);                // re-render 2
    });

    setTimeout(() => {                 // timeout -> NOT batched
      setCount(c => c + 1);            // re-render 1
      setFlag(f => !f);                // re-render 2
    }, 0);

  REACT 18 BATCHES ALL OF THEM. Promises, timeouts, native event
  listeners and intervals now behave like React handlers: one re-render.

  THIS WAS A REAL BEHAVIOUR CHANGE ON UPGRADE, and it broke a specific
  kind of code — anything that depended on a DOM read happening between
  two updates:

    // Worked in 17 by accident, breaks in 18
    setItems(next);
    const height = listRef.current.scrollHeight;  // 17: post-render value
    setScroll(height);                            // 18: PRE-render value

  In 17 the first setState flushed synchronously, so the DOM was already
  updated when you measured. In 18 both updates batch, so the measurement
  reads the OLD DOM.

  flushSync IS THE DELIBERATE ESCAPE HATCH:

    import { flushSync } from "react-dom";

    flushSync(() => { setItems(next); });     // commit NOW, synchronously
    const height = listRef.current.scrollHeight;   // correct value
    setScroll(height);

  USE IT SPARINGLY. It forces a synchronous render and commit, opting
  that update out of every concurrent benefit and blocking the main
  thread. Legitimate uses are narrow: measuring the DOM between updates,
  and integrating with imperative APIs that must observe a committed DOM
  (a third-party chart, a focus call that must land after a list grows).
  Reaching for it to "fix" ordering usually means the logic belongs in a
  layout effect instead.

Part 5 — useId, Hydration, and Streaming SSR

  HYDRATION REQUIRES THE CLIENT'S FIRST RENDER TO MATCH THE SERVER'S HTML
  EXACTLY. React walks the existing DOM and attaches handlers, assuming
  the structure is identical. Anything non-deterministic breaks it:

    const id = `input-${Math.random()}`;   // server: 0.7231, client: 0.1194
    <label htmlFor={id}>Email</label><input id={id} />

  Server HTML says input-0.7231; the client renders input-0.1194.
  React logs a hydration mismatch and, in React 18+, discards the server
  HTML for that subtree and re-renders it client-side — so you lose the
  performance benefit you did SSR for, silently, in production.

  THE SAME TRAP: Date.now(), new Date().toLocaleString(), crypto.randomUUID(),
  a global counter, and anything reading window or localStorage during
  render (the server has none).

  useId GENERATES IDS FROM THE COMPONENT'S POSITION IN THE TREE, so
  server and client agree by construction:

    function Field({ label }) {
      const id = useId();                 // e.g. ":r3:" — same both sides
      return (
        <>
          <label htmlFor={id}>{label}</label>
          <input id={id} aria-describedby={`${id}-hint`} />
          <span id={`${id}-hint`}>Required</span>
        </>
      );
    }

  ONE useId PER COMPONENT, SUFFIXED for multiple elements — do not call
  it in a loop to key a list. It is for ID ATTRIBUTES, never for React
  keys, which must come from your data.
  STREAMING SSR removes the all-or-nothing wait. Classic
  renderToString is blocking: the server builds the entire HTML string,
  and one slow data dependency delays every byte.

    CLASSIC SSR
      fetch everything (800ms) -> render all HTML -> send -> hydrate all
      user sees NOTHING for 800ms

    STREAMING SSR (renderToPipeableStream)
      send the shell immediately, stream sections as they resolve

      t=50ms    shell + header + nav arrive, browser paints
      t=60ms    fast sections stream in
      t=800ms   the slow section's HTML arrives and slots in

    <Layout>
      <Header />                          {/* in the shell */}
      <Suspense fallback={<FeedSkeleton />}>
        <SlowFeed />                      {/* streams in later */}
      </Suspense>
    </Layout>

  SELECTIVE HYDRATION is the other half. React hydrates each Suspense
  boundary independently and PRIORITISES WHATEVER THE USER INTERACTS
  WITH. Click a not-yet-hydrated button and React hydrates that boundary
  first, then replays the event — so the page becomes usable
  progressively rather than in one late step.

  THE SUSPENSE BOUNDARY IS THE UNIT OF BOTH. No boundary means no
  streaming and no independent hydration for that content, which is why
  boundary placement on the server is a performance decision as much as a
  loading-state one.

Part 6 — Tearing, and What You Should Actually Do

  TEARING IS ONE PAINTED FRAME SHOWING TWO VALUES OF THE SAME STATE. It
  is a direct consequence of interruptible rendering:

    External store value: 5

      t=0   ComponentA renders, reads store -> 5
      t=1   React YIELDS to handle urgent work
      t=2   something calls store.setState(6)
      t=3   React RESUMES THE SAME RENDER PASS
      t=4   ComponentB renders, reads store -> 6

      COMMITTED FRAME:  A shows 5, B shows 6.

  No error, no warning — an internally inconsistent UI, usually
  intermittent, usually under load. This was impossible in React 17
  because a render could not be interrupted.

  IT ONLY AFFECTS STATE OUTSIDE REACT. useState and useReducer are safe:
  React knows about them and keeps a consistent snapshot for the whole
  pass. The risk is external stores read directly during render.

    // UNSAFE in React 18
    function useStoreValue(store) {
      const [v, setV] = useState(store.getState());
      useEffect(() => store.subscribe(() => setV(store.getState())), [store]);
      return v;
    }

    // SAFE
    function useStoreValue(store) {
      return useSyncExternalStore(store.subscribe, store.getState,
                                  store.getServerSnapshot);
    }

  useSyncExternalStore forces a synchronous re-read and discards an
  in-progress render if the value moved. Redux, Zustand, Jotai and MobX
  all use it, so this matters mainly when you hand-roll a subscription —
  which, in React 18, you should not.
  THE HONEST GUIDANCE, WHICH IS MOST OF THE VALUE OF THIS TOPIC:

  MOST APPLICATIONS NEVER CALL ANY OF THESE HOOKS EXPLICITLY. The wins
  arrive through the framework:

    automatic batching     free on upgrade, no code
    streaming SSR          Next.js and Remix do it for you
    selective hydration    same
    tearing safety         your store library already handles it
    router transitions     React Router and Next wrap navigations in
                           transitions themselves

  WHEN YOU DO REACH FOR THEM — and the honest answer is rarely:

    useTransition       an expensive update YOU trigger: a filter or
                        sort over thousands of rows, a heavy tab switch
    useDeferredValue    an expensive child receiving a rapidly changing
                        PROP you do not own
    flushSync           you must measure the DOM between two updates
    useId               you generate ids and you server-render

  MEASURE FIRST. Concurrent features fix INTERACTION LATENCY — the delay
  between input and response. They do not make rendering faster; in fact
  they add scheduling overhead and can make total work slightly slower.
  If your list is slow because it renders 10,000 rows, VIRTUALISE IT —
  render 30. That is a 300x reduction in work, against which a transition
  is a consolation prize.

    THE ORDER THAT ACTUALLY HELPS:
      1. Render less        virtualise, paginate, split routes
      2. Render less often  fix state placement, then memo
      3. Render at the right priority   THEN concurrent features

  Reaching step 3 first is the common mistake, and it hides the real
  problem behind a smoother-feeling version of it.

Interview Questions

Beginner: What does "concurrent rendering" mean in React 18?

It means React can pause a render in progress, let more urgent work happen, and then resume or abandon and restart it. Before 18, once React began rendering a tree it ran to completion synchronously, so a long render blocked everything — including the keystroke that triggered it.

It is not multithreading. There is still one main thread and no worker; React simply yields to the browser roughly every five milliseconds and checks whether something more urgent is waiting. That keeps each block of work under the ~16.7ms frame budget, so the interface stays responsive even while a large update is being prepared.

The trade is that background work may take slightly longer overall, since yielding and restarting has a cost. In exchange, input never queues behind a render, which is almost always the better deal.

Beginner: Why does StrictMode render components twice, and should you stop it?

To surface impurity. Because concurrent rendering may abandon a render partway and start again, a render function that does something on the way through — incrementing a counter, firing analytics, mutating a cache or a module-level variable — is now a correctness bug rather than merely untidy. StrictMode double-invokes renders and effects in development so those bugs fail on your machine instead of intermittently on a user's.

It happens in development only. Production builds render once and run each effect once, so there is nothing to optimise away.

You should not suppress it, and the common workaround — a useRef guard so an effect only runs the first time — is the wrong fix. It hides the signal while leaving the impurity in place. The right response is to make the component tolerate being run twice: move side effects out of render, and give effects cleanups that genuinely undo what they did.

Mid: What is the difference between useTransition and useDeferredValue?

They achieve a similar result through opposite ends. useTransition marks an update you trigger as interruptible — you wrap your own setState in startTransition. useDeferredValue takes a value you already have and gives you back a version that lags behind, letting React render the urgent pass with the old one.

The deciding question is whether you own the setState. In a search input where you call setQuery and setResults yourself, useTransition is the natural fit and reads clearly. In a child receiving query as a prop from a parent, a context or a store, there is no update of yours to wrap — useDeferredValue is the only option.

One practical difference catches people: useDeferredValue does nothing on its own. The expensive work must be memoised on the deferred value, and the child receiving it memoised too, or the costly render still happens on the urgent pass with a stale input. useTransition needs no such pairing because the update itself is deprioritised. For pending feedback, useTransition gives you isPending, while with a deferred value you compare value !== deferred.

Mid: What changed with automatic batching, and when do you need flushSync?

React 17 batched multiple setState calls into one re-render only inside React's own event handlers. In promises, setTimeout callbacks, intervals and native event listeners, each call triggered its own render. React 18 batches all of them, which for most code is a free performance improvement requiring no changes.

It did break one pattern on upgrade: code that read the DOM between two updates. Previously the first setState outside a React handler flushed synchronously, so measuring immediately afterwards saw the updated DOM. With batching, both updates are deferred and the measurement reads the old DOM — producing a stale height or scroll position, usually in list or auto-scroll code.

flushSync is the intended escape hatch: it forces the wrapped update to render and commit synchronously, so a following DOM read is accurate. It should stay rare, because it blocks the main thread and opts that update out of every concurrent benefit. Legitimate uses are measuring between updates and integrating imperative third-party code that must observe a committed DOM. If you are using it for ordering rather than measurement, the logic usually belongs in useLayoutEffect.

Senior: A colleague says concurrent features will fix their slow table. How do you respond?

I would first separate two things that get conflated: render duration and interaction latency. Concurrent features address the second — the delay between an input and a visible response — by letting React yield and reprioritise. They do not make rendering faster. There is one thread and the same work, plus scheduling overhead, so total time to a settled UI can be slightly worse.

So the question is what "slow" means here. If typing lags but the table eventually appears at an acceptable speed, a transition genuinely helps: the input stays responsive and intermediate renders are abandoned rather than painted. If the table itself takes a second to appear, a transition only makes the wait smoother — the user is still waiting, now behind dimmed content.

For a slow table the real fix is nearly always to render less. Ten thousand rows into the DOM is the problem; virtualising to the ~30 visible ones is a hundredfold reduction in work, and it fixes both duration and latency. After that I would check state placement — a table re-rendering because unrelated state lives too high is a placement bug that memo only papers over. Only once the work is genuinely necessary does scheduling priority become the right lever.

My order is: render less, then render less often, then render at the right priority. Reaching for step three first is common and it hides the real problem behind a smoother-feeling version of it. I would also want a profile before and after, because concurrent features are easy to add and hard to attribute improvement to without one.

Senior: Explain tearing, and why React 18 required a new hook for external stores.

Tearing is a single committed frame displaying two different values of the same piece of state. It became possible because rendering is interruptible: React can render part of a tree, yield, and resume. If an external store changes during that yield, components rendered before the pause hold the old value and those rendered after hold the new one — and React commits both together. The result is an internally inconsistent screen, with no error and no warning, appearing intermittently and usually under load.

React's own state is immune. useState and useReducer values are managed by React, which keeps a consistent snapshot for the duration of a render pass. The exposure is state React does not know about — a store read directly during render through the old pattern of useState plus a useEffect subscription. That pattern was correct in React 17 purely because renders could not be interrupted, which is a good illustration of how a scheduling change can turn working code into buggy code without the code changing.

useSyncExternalStore is the fix: it takes a subscribe function and a getSnapshot, forces a synchronous re-read, and discards an in-progress render if the value moved mid-pass. You trade a little concurrency for consistency, which for external state is the right default. Two details matter if you implement it directly — getSnapshot must return a referentially stable value or you loop infinitely, and omitting getServerSnapshot throws under SSR. In practice Redux, Zustand, Jotai and MobX all sit on it, so the main lesson is not to hand-roll store subscriptions in React 18.

🏋️ Graded Exercises

1 (easy): The input still lags. Why did the transition not help?

  function onChange(e) {
    startTransition(() => {
      setQuery(e.target.value);
      setResults(rows.filter(r => r.name.includes(e.target.value)));
    });
  }
Solution 
  function onChange(e) {
    const next = e.target.value;
    setQuery(next);                                   // URGENT
    startTransition(() => {
      setResults(rows.filter(r => r.name.includes(next)));   // interruptible
    });
  }

Both updates were marked as transitions, including the one driving the input's own value. React is therefore free to delay and interrupt the input update too, so typed characters appear late — precisely the symptom the hook was meant to remove.

The point of useTransition is to split one event into two priorities. The update the user must see immediately stays outside; only the expensive one goes inside. Reading e.target.value into a local first is also necessary here, since the event object is pooled in older React and, more importantly, the deferred callback should close over a plain value rather than the event.

2 (easy): These ids differ between server and client and the console warns about hydration. Fix it.

  function Field({ label }) {
    const id = `field-${Math.random().toString(36).slice(2)}`;
    return <><label htmlFor={id}>{label}</label><input id={id} /></>;
  }
Solution 
  function Field({ label, hint }) {
    const id = useId();
    return (
      <>
        <label htmlFor={id}>{label}</label>
        <input id={id} aria-describedby={`${id}-hint`} />
        <span id={`${id}-hint`}>{hint}</span>
      </>
    );
  }

Hydration assumes the client's first render produces exactly the markup the server sent. Math.random() is non-deterministic, so the two never agree and React reports a mismatch — then, in React 18 and later, throws away the server HTML for that subtree and re-renders it on the client. The page still works, which is what makes it easy to miss, but you have quietly lost the benefit you did server rendering for.

useId derives the id from the component's position in the tree, so both sides produce the same string. Call it once per component and suffix for additional elements, as with the hint above. It is for ID attributes only — never for list keys, which must come from your data or reconciliation breaks.

3 (medium): This deferred value changed nothing — the app is exactly as slow. Explain and fix.

  function Results({ query, data }) {
    const deferred = useDeferredValue(query);
    const rows = data.filter(r => r.name.includes(deferred));
    return <ul>{rows.map(r => <Row key={r.id} row={r} />)}</ul>;
  }
Solution 
  const Row = memo(function Row({ row }) { /* ... */ });

  function Results({ query, data }) {
    const deferred = useDeferredValue(query);
    const isStale = query !== deferred;

    const rows = useMemo(
      () => data.filter(r => r.name.includes(deferred)),
      [data, deferred]
    );

    return (
      <ul style={{ opacity: isStale ? 0.6 : 1 }} aria-busy={isStale}>
        {rows.map(r => <Row key={r.id} row={r} />)}
      </ul>
    );
  }

useDeferredValue only gives you an older value. It does not make anything skip work by itself. Here the component still re-renders on the urgent pass — because query changed — and the filter runs on every one of those renders, just with the stale input. The expensive work was never actually deferred.

useMemo keyed on deferred is what does the deferring: on the urgent render deferred is unchanged, so the memo returns the previous result and the frame is cheap. React then schedules a background render at transition priority where deferred catches up and the filter runs once. Memoising Row matters for the same reason — without it every row re-renders on the urgent pass regardless.

isStale is the free equivalent of isPending, and worth surfacing so users know the list is a beat behind.

4 (medium): After upgrading to React 18, the chat window stopped auto-scrolling to the newest message. It worked in 17. Diagnose and fix.

  socket.on("message", (msg) => {
    setMessages(prev => [...prev, msg]);
    listRef.current.scrollTop = listRef.current.scrollHeight;
  });
Solution 
  // Option A — flushSync, when you must measure between updates
  socket.on("message", (msg) => {
    flushSync(() => setMessages(prev => [...prev, msg]));
    listRef.current.scrollTop = listRef.current.scrollHeight;   // post-commit
  });

  // Option B — usually better: react to the committed DOM
  useLayoutEffect(() => {
    listRef.current.scrollTop = listRef.current.scrollHeight;
  }, [messages]);

This is the automatic-batching behaviour change. In React 17, a setState inside a socket callback — not a React event handler — flushed synchronously, so by the time the next line ran the new message was in the DOM and scrollHeight included it. React 18 batches updates everywhere, so the state update is deferred and scrollHeight is measured against the DOM before the message was added. The scroll lands one message short, which reads as "it stopped scrolling".

flushSync restores the old timing explicitly and is the direct translation of the original intent. But Option B is usually the better structure: the scroll is a reaction to a committed change, which is exactly what useLayoutEffect is for. It runs after commit and before paint, so there is no visible jump, and it does not opt the update out of concurrent scheduling the way flushSync does.

5 (hard): A dashboard shows a filter input over 50,000 rows. Typing is unusable. A colleague proposes wrapping the filter update in startTransition. Evaluate that and design the real fix.

Solution 
  // The actual fix: render 30 rows, not 50,000
  import { useVirtualizer } from "@tanstack/react-virtual";

  function Table({ rows }) {
    const parentRef = useRef(null);
    const v = useVirtualizer({
      count: rows.length,
      getScrollElement: () => parentRef.current,
      estimateSize: () => 36,
      overscan: 8,
    });

    return (
      <div ref={parentRef} style={{ height: 600, overflow: "auto" }}>
        <div style={{ height: v.getTotalSize(), position: "relative" }}>
          {v.getVirtualItems().map(item => (
            <Row key={rows[item.index].id} row={rows[item.index]}
                 style={{ transform: `translateY(${item.start}px)` }} />
          ))}
        </div>
      </div>
    );
  }

  // THEN, if filtering 50k objects is still measurably slow:
  const [isPending, startTransition] = useTransition();
  setQuery(next);                                  // urgent
  startTransition(() => setFiltered(filter(rows, next)));

The transition is not wrong, but it treats the symptom. It would make the input responsive while React prepares the update, and abandoned intermediate renders would save some work. What it cannot do is reduce the work: fifty thousand DOM nodes still have to be created, laid out and painted, so the table still takes a long time to settle and the user still waits — now behind dimmed content.

Neither❌ Blocked per keystrokeSlow50,000

Virtualisation renders only the visible window plus a small overscan — roughly forty nodes regardless of dataset size. That is a three-orders-of-magnitude reduction in render work, and it fixes render duration and interaction latency together. Once it is in place, the remaining cost is the array filter itself, which for 50,000 plain objects is typically a few milliseconds and often needs nothing further.

The general principle: render less, then render less often, then render at the right priority. Concurrent features are step three, and reaching for them first hides the real problem behind a smoother-feeling version of it. I would also profile before and after, since a transition is easy to add and hard to attribute improvement to without measurement.

6 (hard): This store hook occasionally renders a screen where two components disagree about the same value. Explain the mechanism precisely and fix it.

  function useStore(store, selector) {
    const [value, setValue] = useState(() => selector(store.getState()));
    useEffect(() =>
      store.subscribe(() => setValue(selector(store.getState()))), [store]);
    return value;
  }
Solution 
  function useStore(store, selector) {
    const getSnapshot = useCallback(
      () => selector(store.getState()),
      [store, selector]
    );
    return useSyncExternalStore(store.subscribe, getSnapshot, getSnapshot);
  }

This is tearing. Concurrent rendering can interrupt a pass: React renders component A, which reads the store and gets 5; React yields to handle urgent work; something updates the store to 6; React resumes the same pass and renders component B, which reads 6. Both are committed in one frame, so the screen shows two values of one piece of state. There is no error, it is intermittent, and it appears under load — which makes it very hard to reproduce from a bug report.

The useState plus useEffect pattern cannot prevent this, because the value is read during render with no way to tell React it moved mid-pass. It was correct in React 17 only because renders could not be interrupted — the code did not change, the scheduler did.

useSyncExternalStore re-reads synchronously and discards an in-progress render if the snapshot changed, trading a little concurrency for consistency. Two details matter in this implementation. getSnapshot must be referentially stable and must return a stable value — an inline selector allocating a new object or array each call causes React's "getSnapshot should be cached" warning and an infinite loop, which is the same defect as a selector returning a new object. And passing getSnapshot as the server snapshot is only valid when server and client agree; a store hydrating from localStorage needs a separate one or it produces a hydration mismatch.

In practice you would not write this at all — Redux, Zustand, Jotai and MobX all sit on this hook already. The lesson is that hand-rolling store subscriptions stopped being safe in React 18.

🎯 Key Takeaways

  • Concurrent rendering is interruptible, not parallel — one thread still, but React can pause, abandon and restart a render.
  • React yields roughly every 5ms, keeping blocks under the ~16.7ms frame budget so input never queues behind a render.
  • Render purity became a correctness requirement, because an abandoned pass has already run whatever your render did on the way through.
  • StrictMode's double-invoke is development-only and exists to surface that impurity; ref-guarding effects hides the signal instead of fixing it.
  • useTransition marks an update you trigger; the urgent setState stays outside the callback or the input itself becomes laggy.
  • startTransition's callback must be synchronous — an await loses the transition with the call stack.
  • Intermediate transition renders are abandoned, never painted, so fast typing does less total work, not more.
  • useDeferredValue defers a value you receive — the option when the value is a prop and you own no setState.
  • A deferred value does nothing without useMemo and a memoised child; otherwise the expensive work still runs on the urgent pass.
  • value !== deferred is the free isPending, and stale content should always be visibly stale.
  • React 18 batches everywhere — promises, timeouts, intervals and native handlers — which was a real upgrade-time behaviour change.
  • Reading the DOM between two batched updates now sees the old DOM; flushSync fixes it, but useLayoutEffect is usually the better structure.
  • useId derives ids from tree position so server and client agree; Math.random() and Date.now() break hydration and silently discard the server HTML.
  • Streaming SSR sends the shell immediately and selective hydration prioritises whatever the user interacts with — the Suspense boundary is the unit of both.
  • Tearing is one frame showing two values of the same state, possible only because renders can now be interrupted, and it affects external stores rather than useState.
  • Most apps never call these hooks explicitly — batching, streaming, hydration and tearing safety arrive through the framework and your store library.
  • Render less, then less often, then at the right priority — virtualising 50,000 rows to 30 beats any amount of scheduling.
