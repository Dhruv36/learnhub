Code Splitting & Suspense Performance

What you'll master: why bundle size dominates first load — parse and execute cost on a mid-range phone, not download time; React.lazy and dynamic import(), and why the specifier must be statically analysable or no chunk is emitted; Suspense placement, where too coarse blanks the page and too fine gives you a spinner mosaic; route-based splitting as the highest-value split; useTransition to keep the old UI on screen instead of flashing a fallback; how Suspense actually works underneath; reading a bundle analysis; and what defeats tree-shaking — side effects, CommonJS and barrel files. Prerequisites: useMemo & useCallback, The Re-render Model.

Part 1 — The Cost Is Parse and Execute, Not Download

  EVERYONE OPTIMISES FOR DOWNLOAD TIME AND THEN WONDERS WHY A FAST
  CONNECTION STILL FEELS SLOW. JavaScript is the most expensive asset
  per byte on the web, because bytes must be downloaded, parsed,
  compiled AND executed — and only the first of those is helped by a
  fast network.

  1MB OF JAVASCRIPT (uncompressed; ~300KB over the wire gzipped):

    DEVICE                    DOWNLOAD   PARSE+COMPILE   EXECUTE   TOTAL
    ------------------------------------------------------------------
    Desktop, fibre               ~40ms          ~120ms    ~110ms   ~270ms
    iPhone 15, LTE              ~250ms          ~160ms    ~140ms   ~550ms
    Mid-range Android, 4G       ~700ms          ~900ms    ~800ms  ~2400ms
    Low-end Android, 3G        ~3000ms         ~1900ms   ~1700ms  ~6600ms

    Treat these as ORDERS OF MAGNITUDE, not measurements — they move with
    the device, the engine version, thermal state and what else is
    running. The SHAPE is the reliable part: on a cheap phone, CPU work
    costs MORE than the download, and it does not improve when the user
    finds better wifi.

  A 4-6x CPU GAP between a development laptop and a median phone is the
  normal case. This is why "it's fast on my machine" is not evidence, and
  why Chrome DevTools ships a 4x/6x CPU throttle — use it.

  DURING PARSE AND EXECUTE THE MAIN THREAD IS BLOCKED. Nothing renders,
  no click is handled, no input is echoed. The page is visibly there and
  completely dead — the interaction pattern users describe as "it froze".

  THE ONLY RELIABLE FIX IS TO SHIP LESS JAVASCRIPT. Splitting defers
  code; deleting removes it. Prefer deleting.

Part 2 — React.lazy, dynamic import, and Why the Specifier Must Be Static

  A DYNAMIC import() RETURNS A PROMISE FOR A MODULE. That is all it is —
  standard JavaScript, not a React feature. The bundler sees it and does
  something significant: it emits that module and its unique dependencies
  as a SEPARATE CHUNK, excluded from the main bundle.

    const Editor = lazy(() => import("./Editor"));

  React.lazy wraps that promise so React can suspend on it. The rules:

    - the module must have a DEFAULT EXPORT (or you map it yourself)
    - lazy() must be called at MODULE SCOPE, never inside a component
    - it must be rendered inside a <Suspense> boundary

  CALLING lazy() INSIDE A COMPONENT IS THE CLASSIC BUG:

    function Page() {
      const Editor = lazy(() => import("./Editor"));   // WRONG
      return <Suspense fallback={<S />}><Editor /></Suspense>;
    }

  Every render creates a NEW lazy component type. A new type means React
  unmounts the old subtree and mounts a fresh one — so the chunk is
  re-requested (served from cache, but re-executed), all component state
  is destroyed, and the fallback flashes on every parent render. It looks
  like a mysterious flicker and it is trivially avoided by hoisting.

  NAMED EXPORTS need a small adapter:

    const Chart = lazy(() =>
      import("./charts").then(m => ({ default: m.BarChart }))
    );
  THE SPECIFIER MUST BE STATICALLY ANALYSABLE. Bundling happens at BUILD
  time; the string is needed then, not at runtime.

    // NO CHUNK — the bundler cannot know what this is
    const name = getComponentName();
    const C = lazy(() => import(name));

    // NO CHUNK — same reason
    const C = lazy(() => import("./" + kind + "/View"));

    // WORKS — a literal prefix and suffix give the bundler a glob,
    // so it emits a chunk for EVERY file matching ./views/*/View.js
    const C = lazy(() => import(`./views/${kind}/View.js`));

    // BEST — an explicit map. Nothing to infer, and dead entries are
    // visible in review rather than silently bundling extra files
    const views = {
      chart: () => import("./views/chart/View.js"),
      table: () => import("./views/table/View.js"),
    };
    const C = lazy(views[kind]);

  THE TEMPLATE-LITERAL FORM IS A TRAP AT SCALE: a directory of forty
  views emits forty chunks, all reachable, none tree-shakeable, because
  the bundler must assume any of them might be requested.

  PRELOADING is just calling the importer early — the module cache
  deduplicates, so the later render finds it resolved:

    const load = () => import("./Editor");
    const Editor = lazy(load);

    <button onMouseEnter={load} onFocus={load} onClick={open}>Edit</button>

  Hover fires roughly 200-300ms before the click lands, which is often
  the entire chunk fetch. onFocus covers keyboard users — omitting it is
  a small accessibility regression that is easy to miss.

Part 3 — Suspense Placement: Blank Page vs Spinner Mosaic

  <Suspense> CATCHES A SUSPENDED CHILD ANYWHERE BELOW IT AND RENDERS THE
  FALLBACK INSTEAD OF THE WHOLE SUBTREE. Placement is therefore a design
  decision, not a technical one, and both extremes are bad:

  TOO COARSE — one boundary at the root:

    <Suspense fallback={<FullPageSpinner />}>
      <App />
    </Suspense>

    ANY lazy component anywhere blanks the ENTIRE application. Open a
    settings modal, and the header, sidebar and content you were reading
    all vanish for 300ms. The user loses their place.

  TOO FINE — a boundary per component:

    <Suspense><Header /></Suspense>
    <Suspense><Sidebar /></Suspense>
    <Suspense><Chart /></Suspense>
    <Suspense><Table /></Suspense>

    Six spinners resolving at six different times. The layout shifts on
    each one. This measures well and feels terrible — a "spinner mosaic".

  THE RULE: ONE BOUNDARY PER REGION THE USER PERCEIVES AS A UNIT, WITH A
  FALLBACK THE SAME SHAPE AND SIZE AS THE CONTENT.

    <Layout>                          <- never suspends; stays put
      <Sidebar />                     <- eager, cheap
      <Suspense fallback={<PageSkeleton />}>
        <Route />                     <- one region: the page
      </Suspense>
    </Layout>

  A SKELETON THAT MATCHES THE CONTENT'S DIMENSIONS ELIMINATES LAYOUT
  SHIFT. A centred spinner in a region that becomes a 600px table
  guarantees the page jumps when it resolves — that is a CLS regression
  you introduced yourself, and it is the single most common Suspense
  mistake after placement.

  KEEP THE SHELL OUTSIDE EVERY BOUNDARY. Header, nav and footer should
  never be inside a Suspense boundary that a page transition can trip,
  or navigation destroys the app frame.
Boundary atFallbackFeels like
Root, around everythingFull-page spinner❌ App disappears on any lazy load
Per route, inside the layoutPage-shaped skeleton✅ Shell persists, content swaps
Per heavy widgetWidget-shaped skeleton✅ Correct for an editor, chart or map

Part 4 — useTransition: Stop the Fallback From Flashing

  THE JANK NOBODY WARNS YOU ABOUT. You have a tab bar, each tab lazy:

    function Tabs() {
      const [tab, setTab] = useState("overview");
      return (
        <>
          <TabBar value={tab} onChange={setTab} />
          <Suspense fallback={<Skeleton />}>
            {tab === "overview" ? <Overview /> : <Reports />}
          </Suspense>
        </>
      );
    }

  Clicking "Reports" throws away perfectly good content you were already
  looking at and shows a skeleton for 200ms. The old UI was valid. The
  new one is not ready. React showed you neither.

  useTransition marks the update as NON-URGENT, which tells React to keep
  the OLD tree on screen while the new one prepares:

    const [isPending, startTransition] = useTransition();

    const select = (next) => {
      startTransition(() => setTab(next));    // old content STAYS
    };

    <div style={{ opacity: isPending ? 0.6 : 1 }}>
      <Suspense fallback={<Skeleton />}>
        {tab === "overview" ? <Overview /> : <Reports />}
      </Suspense>
    </div>

    WITHOUT TRANSITION:  content -> SKELETON -> new content
    WITH TRANSITION:     content -> content (dimmed) -> new content

  THE EXACT RULE: A SUSPENSE FALLBACK IS FOR CONTENT THAT HAS NEVER BEEN
  SHOWN. A TRANSITION IS FOR REPLACING CONTENT THAT IS ALREADY ON SCREEN.

  First paint of a route: fallback is right — there is nothing to keep.
  Switching tabs, filtering a list, paginating: transition is right.

  isPending is the honest affordance. Dim the region, disable the
  control, show a thin progress bar — anything that says "working"
  without destroying what the user is reading.

  ONE CONSTRAINT: startTransition's callback must be SYNCHRONOUS. An
  await inside it loses the transition context, and the update after the
  await is treated as urgent again — so the fallback flashes and it looks
  like useTransition simply does not work.

Part 5 — What Suspense Actually Does, and Why Data Waited

  THE MECHANISM IS DELIBERATELY CRUDE, AND KNOWING IT DEMYSTIFIES EVERY
  ODD BEHAVIOUR:

    1. A component renders and is not ready.
    2. Instead of returning JSX, it THROWS A PROMISE.
    3. React catches it while rendering — exactly like an error boundary
       catches an Error, except a thenable means "not an error, wait".
    4. React renders the nearest Suspense ancestor's fallback.
    5. When the promise resolves, React RETRIES the subtree from scratch.

  THREE CONSEQUENCES THAT EXPLAIN COMMON CONFUSION:

    RENDERS RUN TWICE (at least). The first attempt threw. Everything
    before the throw already ran, so a render with side effects — a
    counter increment, a log, a fetch — happens more than once. This is
    why render must be pure, stated in a way that finally has teeth.

    THE PROMISE MUST BE CACHED. Creating it during render means the retry
    creates a NEW promise, which throws again, which retries, forever:

      // INFINITE SUSPENSE LOOP
      function Profile({ id }) {
        const data = use(fetch(`/api/users/${id}`));   // new promise
        return <p>{data.name}</p>;                     // every attempt
      }

      // CORRECT — a stable, cached promise per key
      const cache = new Map();
      function getUser(id) {
        if (!cache.has(id)) cache.set(id, fetch(`/api/users/${id}`).then(r => r.json()));
        return cache.get(id);
      }
      function Profile({ id }) {
        const data = use(getUser(id));
        return <p>{data.name}</p>;
      }

    STATE IN A SUSPENDED SUBTREE IS PRESERVED, not destroyed — React
    hides the tree rather than unmounting it, which is what makes
    transitions back and forth cheap.

  WHY SUSPENSE FOR DATA TOOK YEARS. Code splitting was easy: the promise
  is import(), and the module cache makes it naturally stable and
  deduplicated. Data has none of that — WHO owns the cache, WHEN is it
  invalidated, HOW do you avoid refetching on every retry, and what
  happens on the server where there is no client cache at all? React
  shipped the primitive (use()) and left caching to libraries and to the
  server-component model, which is why "Suspense for data fetching" in a
  plain client app still means "use a library that supports it" —
  TanStack Query, Relay, or a framework's router.
Suspense for codeSuspense for data

Part 6 — Reading a Bundle, and What Defeats Tree-Shaking

  MEASURE BEFORE YOU SPLIT. Splitting the wrong thing adds round trips
  and buys nothing.

    npx source-map-explorer 'dist/assets/*.js'
    npx vite-bundle-visualizer
    # webpack: webpack-bundle-analyzer

  FOUR THINGS TO LOOK FOR, IN ORDER OF HOW OFTEN THEY ARE THE ANSWER:

    1. A DATE LIBRARY WITH ALL LOCALES.  moment ships ~230KB, most of it
       locales you never render. date-fns imports per function (~10KB
       used), and Intl.DateTimeFormat is built into the browser and costs
       ZERO bytes. This is a DELETE, not a split.

    2. AN ICON SET IMPORTED WHOLE.
         import { Search } from "react-icons/fa";     // pulls the set
         import Search from "react-icons/fa/FaSearch"; // pulls one icon
       Whole-set imports routinely account for 100KB+ of a bundle.

    3. THE SAME DEPENDENCY AT TWO VERSIONS. Two copies of lodash, or
       React itself duplicated by a mis-linked package. Check with
       `npm ls <pkg>`; fix with a resolution/override, not a split.

    4. A HEAVY WIDGET LIBRARY ON THE CRITICAL PATH. A charting library,
       a rich-text editor, a map, a PDF generator. THESE are what
       splitting is for.

  THE ORDER MATTERS: DELETE, THEN REPLACE, THEN SPLIT. Splitting a
  dependency you did not need just moves dead weight to a different file.
  TREE-SHAKING REMOVES UNUSED EXPORTS — but only when the bundler can
  PROVE removal is safe. Four things defeat that proof:

    SIDE EFFECTS AT MODULE SCOPE. If importing a module might do
    something (register a polyfill, mutate a global, inject CSS), the
    bundler must keep it. Declare honestly in package.json:

      "sideEffects": false                       // nothing has effects
      "sideEffects": ["*.css", "./src/polyfill.js"]   // these do

    Lying here is a real hazard: mark a module effect-free when it is not
    and it gets dropped, producing a bug that only appears in production
    builds.

    COMMONJS. require() is dynamic — resolvable only at runtime — so
    CJS modules are largely opaque to tree-shaking. ESM is a prerequisite,
    not an optimisation.

    BARREL FILES. index.ts re-exporting an entire directory means
    importing one symbol pulls the barrel, which references every module
    in it. Modern bundlers often recover, but not always, and it silently
    inflates dev-server work regardless:

      // components/index.ts
      export * from "./Button";
      export * from "./DataGrid";     // 180KB
      export * from "./Chart";        // 220KB

      import { Button } from "./components";   // may pull all three

      // Deep-import instead:
      import { Button } from "./components/Button";

    NAMESPACE IMPORTS. import * as _ from "lodash" defeats it outright;
    import { debounce } from "lodash-es" does not.

  A SPLIT IS NOT FREE. Each chunk is a request with latency, worse
  compression than one larger file, and a possible fallback flash. The
  threshold I use:

    SPLIT IF        the code is >30-50KB AND is not needed on first
                    paint AND a meaningful share of sessions never
                    reaches it
    DO NOT SPLIT    anything small, anything on the critical path, or
                    anything nearly every user hits immediately
    DELETE FIRST    if it can be removed or replaced with a platform
                    feature, that beats any split

  ROUTE BOUNDARIES SATISFY ALL THREE CONDITIONS ALMOST BY DEFINITION,
  which is why they are the highest-value split points in any app.

Interview Questions

Beginner: What does React.lazy do, and what must wrap it?

React.lazy takes a function returning a dynamic import() and gives back a component that React can suspend on. The bundler sees the import() at build time and emits that module and its unique dependencies as a separate chunk, so it is not in the main bundle. The chunk is fetched the first time the component renders.

It must be rendered inside a <Suspense> boundary, which supplies the fallback shown while the chunk loads. Without one, React throws. The module also needs a default export, though a named export is easy to adapt: lazy(() => import("./charts").then(m => ({ default: m.BarChart }))).

The most common mistake is calling lazy() inside a component. That creates a new component type on every render, so React unmounts the old subtree, state is lost and the fallback flashes. Always call it at module scope.

Beginner: Where should Suspense boundaries go?

One per region the user perceives as a unit, with the application shell outside every boundary. In practice that usually means a boundary just inside the layout wrapping the routed page, plus a boundary around any genuinely heavy widget such as an editor, chart or map.

Both extremes are bad. A single boundary at the root means any lazy component anywhere blanks the entire app — open a modal and the header and sidebar you were reading disappear. A boundary per component gives you a mosaic of spinners resolving at different times, with layout shifting on each one.

The fallback matters as much as the placement. A skeleton matching the content's shape and size prevents layout shift; a small centred spinner in a region that becomes a 600px table guarantees the page jumps when it resolves, which is a CLS regression you caused yourself.

Mid: Why does bundle size matter more on mobile than download speed suggests?

Because JavaScript has to be parsed, compiled and executed after it is downloaded, and all of that runs on the main thread. Download is the only part a fast network helps. On a mid-range phone the CPU work typically exceeds the download time for the same file, and it does not improve when the user finds better wifi.

Roughly, 1MB of JavaScript costs a few hundred milliseconds end to end on a desktop and can approach two to three seconds on a mid-range Android device — the exact figures move with the device and engine, but the shape holds. While that work happens the main thread is blocked: nothing renders, no click is handled, no keystroke echoes. Users describe it as the page freezing, and it happens after the content is visible, which makes it especially confusing.

The practical consequence is that a development machine is not evidence. There is commonly a four-to-six-times CPU gap between a developer laptop and a median phone, which is exactly why DevTools ships CPU throttling. And it reframes the goal: splitting defers the cost, deleting removes it, so deleting is always the stronger move.

Mid: When should you use useTransition instead of relying on a Suspense fallback?

The rule is about what is already on screen. A Suspense fallback is correct for content that has never been shown — the first paint of a route, opening a modal for the first time. A transition is correct when you are replacing content the user is already looking at: switching tabs, applying a filter, paginating.

Without a transition, React discards the valid old tree and shows the fallback, so the user's content vanishes for a few hundred milliseconds and comes back different. Wrapping the state update in startTransition marks it non-urgent, and React keeps the old tree on screen while preparing the new one. You then use isPending to signal work honestly — dim the region, disable the control, show a progress bar.

One constraint catches people: the callback passed to startTransition must be synchronous. Putting an await inside it loses the transition context, so the update after the await is treated as urgent, the fallback flashes, and it looks like useTransition does nothing. Kick off async work outside and start the transition when you set state.

Senior: Walk through how you would reduce a 1.2MB bundle. What is your order of operations?

I measure before touching anything, with source-map-explorer or the framework's analyzer, because splitting the wrong thing adds round trips and saves nothing. Then I work in a fixed order: delete, replace, split.

Delete first. Almost every large bundle contains something nobody needs: polyfills for browsers the product dropped, a dependency used in one removed feature, a duplicated package at two versions — which I check with npm ls and fix with an override rather than a split, since splitting a duplicate still ships both copies. Then replace: a date library with all its locales becomes Intl.DateTimeFormat at zero bytes or date-fns per function; a whole icon set becomes deep imports of the handful actually rendered. Those two passes routinely take a third off a bundle without any architectural change.

Only then do I split, and route boundaries first, because they match how the app is used — a user who never opens the admin section should never download it. After that, individually heavy widgets: an editor, a charting library, a map. I split at roughly 30-50KB and only for code that is off the first-paint path and genuinely skipped by a meaningful share of sessions; below that the extra request and worse compression cost more than they save. Alongside this I check tree-shaking is actually working — accurate sideEffects in package.json, ESM rather than CommonJS, and no barrel file pulling a whole directory through one import.

I verify with a real user metric, not bundle size alone. A smaller bundle that adds a round trip to the critical path is not a win, so I want LCP and INP on a CPU-throttled profile, ideally confirmed against field data.

Senior: Explain the Suspense mechanism, and why data fetching took so much longer to stabilise than code splitting.

Mechanically it is deliberately crude. A component that is not ready throws a promise instead of returning JSX. React catches it during render — the same machinery as an error boundary, except a thenable means "wait" rather than "fail" — renders the nearest Suspense ancestor's fallback, and retries the subtree when the promise resolves. State in the suspended tree is preserved rather than unmounted, because React hides it instead of destroying it.

Three consequences follow. Renders run more than once, since everything before the throw already executed on the failed attempt, which is where the purity requirement stops being advice and becomes load-bearing. The promise must be stable across attempts — create it during render and each retry produces a new promise that suspends again, an infinite loop. And because retries re-run the render, any caching has to live outside the component.

Code splitting satisfies all of that for free. The promise is import(), and the module system already caches and deduplicates it, so a retry finds the same resolved promise. Data has none of it. Someone must decide who owns the cache, what its key is, when it invalidates, how concurrent requests deduplicate, and what happens during server rendering where no client cache exists. Those are the hard problems in the field, and React reasonably declined to answer them in the core library — it shipped the primitive, use(), and left policy to server components and to libraries. That is why "Suspense for data" in a plain client app still means adopting TanStack Query, Relay or a framework router rather than writing it yourself, and I would not hand-roll a suspense cache in production.

🏋️ Graded Exercises

1 (easy): The modal's contents flash a spinner every time the parent re-renders, and the form inside loses its input. Fix it.

  function Page() {
    const [open, setOpen] = useState(false);
    const Settings = lazy(() => import("./Settings"));
    return open && (
      <Suspense fallback={<Spinner />}><Settings /></Suspense>
    );
  }
Solution 
  const Settings = lazy(() => import("./Settings"));   // module scope

  function Page() {
    const [open, setOpen] = useState(false);
    return open && (
      <Suspense fallback={<Spinner />}><Settings /></Suspense>
    );
  }

lazy() inside the component body runs on every render and returns a brand new component type each time. React compares types to decide whether to update or replace, so a new type means the old subtree is unmounted and a fresh one mounted — destroying the form's state and re-triggering the suspense fallback, even though the chunk is already in the module cache.

Hoisting to module scope means the type is created once and stays referentially stable, so React updates the existing subtree instead of replacing it.

2 (easy): This was supposed to split the views, but the bundle did not shrink at all. Why?

  const viewName = user.preferences.defaultView;
  const View = lazy(() => import(viewName));
Solution 
  const views = {
    chart: () => import("./views/Chart"),
    table: () => import("./views/Table"),
    board: () => import("./views/Board"),
  };
  const View = lazy(views[user.preferences.defaultView] ?? views.table);

Bundling happens at build time, so the bundler needs the module specifier then. A variable holding a value only known at runtime tells it nothing, so it cannot emit a chunk — and depending on the tool you get either a build warning or a silent no-op where the code still works but nothing was ever split.

An explicit map fixes it: every specifier is a literal, so each view becomes its own chunk, and only the selected one is fetched. A template literal such as import(\`./views/${name}\`) also works because the literal prefix gives the bundler a glob — but at scale that emits a chunk for every matching file in the directory, so an explicit map is safer and makes dead entries visible in review.

3 (medium): Switching dashboard tabs blanks the panel for ~300ms even though the user was reading valid content. Fix it, and say why a fallback is still right elsewhere.

  const [tab, setTab] = useState("overview");
  <TabBar onChange={setTab} />
  <Suspense fallback={<PanelSkeleton />}>
    {tab === "overview" ? <Overview /> : <Reports />}
  </Suspense>
Solution 
  const [tab, setTab] = useState("overview");
  const [isPending, startTransition] = useTransition();

  <TabBar onChange={(t) => startTransition(() => setTab(t))} />
  <div style={{ opacity: isPending ? 0.6 : 1 }} aria-busy={isPending}>
    <Suspense fallback={<PanelSkeleton />}>
      {tab === "overview" ? <Overview /> : <Reports />}
    </Suspense>
  </div>

Without a transition, changing tab is an urgent update: React must render it immediately, the new lazy component is not loaded, so it suspends and the boundary replaces perfectly good content with a skeleton. Marking the update non-urgent lets React keep the current tree on screen while the new one prepares, and swap only when it is ready.

The boundary is still correct and still necessary — it handles the case where there is nothing to keep. On the very first render of the panel there is no previous content, so the skeleton is what the user should see. aria-busy and the dimming communicate the pending state without destroying what is being read.

4 (medium): This component loops forever and the tab locks up. Explain precisely and fix.

  function Profile({ id }) {
    const user = use(fetch(`/api/users/${id}`).then(r => r.json()));
    return <h1>{user.name}</h1>;
  }
Solution 
  const cache = new Map();
  function getUser(id) {
    if (!cache.has(id)) {
      cache.set(id, fetch(`/api/users/${id}`).then(r => r.json()));
    }
    return cache.get(id);
  }

  function Profile({ id }) {
    const user = use(getUser(id));      // same promise on every retry
    return <h1>{user.name}</h1>;
  }

Suspense works by retrying the render once the thrown promise resolves. The original creates the promise during render, so the retry runs fetch again and produces a different promise, which is also pending, which suspends again. React retries, and so on — a loop that also fires an unbounded number of network requests, which is why the tab locks up rather than merely rendering oddly.

Caching by key makes the promise stable across attempts: the retry finds the resolved promise and renders. This is exactly why code splitting was easy and data was hard — the module cache gives import() this property for free, while for data someone has to own the cache.

Note the module-level Map here is a teaching device, not production code: it never invalidates, never refetches, and is shared across users on a server. Real applications use TanStack Query, Relay or a framework's router cache, which handle invalidation, deduplication and SSR.

Note that splitting moment or the icon set instead would have been the wrong instinct. Both are used across the app, so a split would either fail to help or push a fetch onto the critical path while still shipping every byte. The duplicate lodash is the clearest example: splitting either copy leaves both in the product.

Expected result is roughly 1.4MB down to ~450-500KB initial, with the charting chunk loading on demand. I would confirm with the analyzer again and then with a CPU-throttled LCP measurement, because on a mid-range phone the parse and execute saving is the part users actually feel.

6 (hard): After enabling "sideEffects": false, the production build loses all styling and a polyfill stops applying, though development is fine. Explain and fix, then describe how you would prevent this class of bug.

Solution 
  // package.json — declare what genuinely HAS side effects
  {
    "sideEffects": [
      "*.css",
      "*.scss",
      "./src/polyfills.js",
      "./src/registerServiceWorker.js"
    ]
  }

sideEffects: false is a promise to the bundler that importing any module in the package does nothing observable, so an import whose bindings are unused can be dropped entirely. That is exactly what happened. import "./styles.css" has no bindings at all, so with the promise in place it was removed. The same applies to import "./polyfills", which exists purely for its effect of mutating globals.

It only breaks in production because tree-shaking runs in the production build. Development serves modules largely untransformed, so the imports remain and everything appears fine — which is what makes this class of bug expensive: it ships.

Preventing it comes down to three habits. Declare sideEffects as an accurate allowlist rather than a blanket false, since the array form still lets everything else shake. Treat effect-only imports as suspicious in review — they are the ones this setting can silently delete. And run a production build in CI with at least a smoke test that loads the app and asserts something style- or polyfill-dependent, because no amount of development testing will surface it.

🎯 Key Takeaways

  • JavaScript's real cost is parse, compile and execute, all on the main thread — and unlike download, none of it improves on a faster network.
  • A mid-range phone is 4-6x slower than a development machine, so "fast on my laptop" is not evidence; throttle CPU and test on real hardware.
  • Deleting beats splitting — splitting defers a cost, deleting removes it. Order of operations is delete, replace, split.
  • lazy() must be called at module scope, or every render creates a new component type and destroys the subtree's state.
  • The import specifier must be statically analysable — a runtime variable emits no chunk at all, and the code silently stays bundled.
  • Template-literal imports emit a chunk per matching file; an explicit map of importers is safer and reviewable.
  • Preload by calling the importer on hover and focus — the module cache deduplicates, and hover leads the click by 200-300ms.
  • One Suspense boundary per perceived region, with the app shell outside every boundary.
  • The fallback must match the content's dimensions, or you have introduced a layout-shift regression yourself.
  • A fallback is for content never shown; a transition is for replacing content already on screen.
  • startTransition's callback must be synchronous — an await inside loses the transition and the fallback flashes anyway.
  • Suspense works by throwing a promise and retrying the subtree, so renders run more than once and purity is load-bearing.
  • The promise must be cached; creating it during render makes every retry suspend again — an infinite loop that also floods the network.
  • Code splitting was easy because the module cache is the promise cache; data needed ownership, invalidation and SSR answers, which is why it took until use() and server components.
  • Measure before splitting — the usual culprits are a date library with locales, a whole icon set, and a duplicated dependency, none of which splitting fixes.
  • Tree-shaking is defeated by side effects, CommonJS, barrel files and namespace imports, and an inaccurate sideEffects: false breaks only the production build.
  • Split above ~30-50KB, off the critical path, and genuinely skipped by many sessions — route boundaries satisfy all three almost by definition.
