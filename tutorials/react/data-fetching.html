Data Fetching Effects & Lifecycle

What you'll master: the four independent defects in useEffect + fetch — a race condition that resolves out of order, no cache so every mount refetches, waterfalls from nested components, and no sharing between two components that need the same data; why the ignore flag and AbortController are different tools; why isLoading + data + error as three independent variables admits states that cannot happen, and what a status union fixes; the caching vocabulary a library gives you — stale-while-revalidate, deduplication, invalidation; optimistic updates and the rollback path people forget; and why cursor pagination exists. Prerequisites: useEffect Mastery.

Part 1 — What Is Wrong With the Obvious Version

  THE CODE EVERY REACT TUTORIAL SHOWS:

    function UserProfile({ userId }) {
      const [user, setUser] = useState(null);
      const [loading, setLoading] = useState(true);

      useEffect(() => {
        setLoading(true);
        fetch(`/api/users/${userId}`)
          .then(r => r.json())
          .then(data => { setUser(data); setLoading(false); });
      }, [userId]);

      if (loading) return <Spinner />;
      return <h1>{user.name}</h1>;
    }

  IT HAS FOUR SEPARATE BUGS, NOT ONE.

  1. THE RACE. userId changes 1 -> 2 quickly. Two requests are in
     flight. If /users/1 resolves AFTER /users/2, the screen shows
     user 1 while the prop says 2. Nothing errors; the UI is simply
     wrong, and it correlates with network jitter so it reproduces
     on a train and never at your desk.

  2. NO ERROR HANDLING AT ALL. A rejected promise is unhandled,
     loading stays true forever, and the user watches a spinner.
     Note also that fetch does NOT reject on 404 or 500 — only on a
     network failure — so r.json() on an error page throws a syntax
     error instead.

  3. NO CACHE. Navigate away and back and the whole request runs
     again. Ten components needing the same user issue ten requests.

  4. IT RUNS AFTER RENDER, WHICH CREATES WATERFALLS. See Part 2.

  AND A FIFTH, SPECIFIC TO REACT 18: in StrictMode the effect runs
  twice in development, so you see two requests. That is not a bug
  being introduced — it is the missing cleanup being revealed.

  THE MINIMUM CORRECT VERSION IS ALREADY LONGER:

    useEffect(() => {
      let ignore = false;
      setStatus('loading');

      fetch(`/api/users/${userId}`)
        .then(r => {
          if (!r.ok) throw new Error(`HTTP ${r.status}`);
          return r.json();
        })
        .then(data => { if (!ignore) { setUser(data);
                                       setStatus('success'); } })
        .catch(e =>   { if (!ignore) { setError(e);
                                       setStatus('error'); } });

      return () => { ignore = true; };
    }, [userId]);

  That fixes bugs 1 and 2. It does nothing about 3 and 4, and you
  will write it again in every component.

Part 2 — Waterfalls

  AN EFFECT RUNS AFTER ITS COMPONENT COMMITS. So a child that fetches
  cannot start until its parent has rendered — which cannot happen
  until the parent's own data arrives.

    <Page>            fetch user        200ms
      <Profile>       fetch posts       200ms   (starts at t=200)
        <Comments>    fetch comments    200ms   (starts at t=400)

    SEQUENTIAL:  |--user--|--posts--|--comments--|   600ms
    PARALLEL:    |--user------|
                 |--posts-----|                      200ms
                 |--comments--|

  Three requests that could have taken 200ms take 600ms, and nothing
  in the code looks wrong. Each component is individually reasonable.

  THIS IS THE SINGLE LARGEST SOURCE OF PERCEIVED REACT SLOWNESS, and
  it is invisible in a component-by-component code review. You find
  it in the network waterfall view, where the requests appear as a
  staircase rather than a block.

  THE FIXES, IN ORDER OF HOW MUCH THEY CHANGE:

  1. HOIST THE FETCH. One component fetches everything it needs in
     parallel and passes data down:

       const [user, posts] = await Promise.all([
         getUser(id), getPosts(id)
       ]);

     Simple, and it couples the parent to its children's needs.

  2. START THE REQUEST AT NAVIGATION, NOT AT RENDER. A router loader
     begins fetching when the link is clicked, so the request
     overlaps with rendering rather than following it. This is the
     structural fix.

  3. RENDER-AS-YOU-FETCH WITH SUSPENSE. Kick off the request, render
     immediately, and let Suspense show fallbacks per boundary.

  4. SERVER COMPONENTS. The fetch happens on the server next to the
     data, so the round trip disappears entirely.

  WHAT DOES NOT FIX IT: making each individual request faster. A
  staircase of three 50ms requests is still a staircase.

  PARALLEL IS NOT ALWAYS RIGHT. If /posts needs the user's team id
  from /user, the dependency is real and the requests must be
  sequential — the fix there is a server endpoint that returns both.

Part 3 — ignore vs AbortController

  THEY SOLVE DIFFERENT PROBLEMS AND PEOPLE TREAT THEM AS
  INTERCHANGEABLE.

    ignore FLAG          the request completes; you DISCARD the
                         result. Network traffic still happens.
    AbortController      the request is CANCELLED. The browser
                         closes the connection; the promise rejects
                         with an AbortError.

  THE IGNORE FLAG:

    useEffect(() => {
      let ignore = false;
      getUser(id).then(u => { if (!ignore) setUser(u); });
      return () => { ignore = true; };
    }, [id]);

  Simple, always correct, works with any promise. Use it as the
  default.

  ABORTCONTROLLER:

    useEffect(() => {
      const controller = new AbortController();

      fetch(url, { signal: controller.signal })
        .then(r => r.json())
        .then(setData)
        .catch(e => {
          if (e.name === 'AbortError') return;   // EXPECTED
          setError(e);
        });

      return () => controller.abort();
    }, [url]);

  THE CATCH BLOCK IS MANDATORY. Aborting rejects the promise, so
  without that guard every cancellation is reported to the user as an
  error — and in StrictMode's development double-mount, that means an
  error on every single page load.

  WHEN TO ABORT RATHER THAN IGNORE:

    the request is expensive for the server
    the response is large and bandwidth matters
    it is a search-as-you-type endpoint firing constantly
    you are near a connection limit (6 per host on HTTP/1.1)

  WHEN NOT TO ABORT:

    a mutation. Aborting a POST does not undo it — the server may
    have already committed. You lose the response and keep the
    effect, which is the worst combination.

  BOTH ARE STILL NECESSARY EVEN WITH THE FLAG, because ignore alone
  leaves the connection open.
ignore flagAbortController
Network requestCompletesCancelled
Works with any promiseYesOnly APIs that accept a signal
Requires an error guardNoYes — AbortError
Frees a connection slotNoYes
Safe for mutationsYesNo — the server may have committed
Good defaultYesWhen the request is expensive

Part 4 — Four States, Not Two

  THE USUAL SHAPE ADMITS STATES THAT CANNOT HAPPEN:

    const [data, setData]       = useState(null);
    const [loading, setLoading] = useState(false);
    const [error, setError]     = useState(null);

  Three independent variables give 2 x 2 x 2 = 8 combinations. Only
  four are meaningful:

    loading  data   error    meaning
    -------  -----  -----    --------------------------------
    false    null   null     idle — not started
    true     null   null     loading
    false    set    null     success
    false    null   set      error

    true     set    null     ??? loading with stale data showing
    true     null   set      ??? loading and errored
    false    set    set      ??? both succeeded and failed
    true     set    set      ???

  Every component consuming this must decide what to render for the
  impossible ones, and the usual answer — a chain of ifs in some
  arbitrary order — silently picks a winner.

  A STATUS UNION MAKES THEM UNREPRESENTABLE:

    const [state, setState] = useState({ status: 'idle' });

    setState({ status: 'loading' });
    setState({ status: 'success', data });
    setState({ status: 'error', error });

    switch (state.status) {
      case 'idle':    return null;
      case 'loading': return <Spinner />;
      case 'error':   return <Error e={state.error} />;
      case 'success': return <List items={state.data} />;
    }

  In TypeScript a discriminated union means state.data does not
  EXIST outside the success branch — the compiler enforces the
  handling. Without TypeScript you still get an exhaustive switch
  instead of guessed precedence.

  THE FIFTH STATE PEOPLE FORGET IS EMPTY. A successful response with
  zero results is not a loading state and not an error, and rendering
  a bare empty list is a bad experience:

    case 'success':
      return state.data.length === 0
        ? <EmptyState />          // "No orders yet" + an action
        : <List items={state.data} />;

  AND ONE MORE FOR REAL APPS — REFRESHING. Showing a spinner over
  data you already have is worse than showing stale data with a
  subtle indicator. That is why libraries expose isLoading (no data
  yet) separately from isFetching (a request is in flight).

Part 5 — What a Library Actually Gives You

  THE SAME COMPONENT WITH TANSTACK QUERY:

    function UserProfile({ userId }) {
      const { data, isPending, error } = useQuery({
        queryKey: ['user', userId],
        queryFn: () => getUser(userId),
      });

      if (isPending) return <Spinner />;
      if (error)     return <Error e={error} />;
      return <h1>{data.name}</h1>;
    }

  Shorter — but that is not the point. The point is what it does that
  the hand-written version did not:

    DEDUPLICATION      ten components with the same key issue ONE
                       request
    CACHING            navigate back and the data is there instantly
    STALE-WHILE-       show cached data immediately, refetch in the
      REVALIDATE       background, update if it changed
    RACE SAFETY        results are keyed, so a stale response cannot
                       overwrite a newer one
    RETRY              with exponential backoff, configurable
    REFETCH ON FOCUS   returning to a tab shows fresh data
    INVALIDATION       after a mutation, mark keys stale and refetch
    GARBAGE COLLECTION unused cache entries are dropped

  THE MENTAL MODEL THAT MATTERS: SERVER DATA IS A CACHE, NOT STATE.
  You do not own it — the server does. Your copy is a possibly-stale
  replica, and every hard question (when to refetch, what to show
  while refetching, how to invalidate) follows from that.

  Treating server data as ordinary client state is the root cause of
  most React state-management complexity, and it is why teams end up
  putting API responses into Redux and then writing their own cache
  invalidation badly.

  THE CACHE KEY IS THE API:

    ['user', userId]                    one user
    ['users', { status: 'active' }]     a filtered list
    ['user', userId, 'posts']           nested

  Anything the query depends on belongs in the key. A missing
  dependency means two different queries share a cache entry — the
  same class of bug as a missing effect dependency.

  MUTATIONS AND OPTIMISTIC UPDATES:

    const mutation = useMutation({
      mutationFn: updateUser,

      onMutate: async (next) => {
        await qc.cancelQueries({ queryKey: ['user', next.id] });
        const previous = qc.getQueryData(['user', next.id]);
        qc.setQueryData(['user', next.id], next);    // optimistic
        return { previous };                          // for rollback
      },

      onError: (err, next, ctx) => {
        qc.setQueryData(['user', next.id], ctx.previous);  // ROLLBACK
      },

      onSettled: (data, err, next) => {
        qc.invalidateQueries({ queryKey: ['user', next.id] });
      },
    });

  THE ROLLBACK IS THE PART PEOPLE OMIT. An optimistic update without
  one leaves the UI showing a change that never happened, and the
  user only discovers it on refresh. cancelQueries matters too:
  without it an in-flight refetch can land after your optimistic
  write and undo it.

  WHEN OPTIMISTIC IS WRONG: when failure is likely, when the server
  computes something you cannot predict (an id, a total, a rank), or
  when being wrong is costly — a payment, a delete.

Part 6 — Pagination

  OFFSET PAGINATION IS WHAT EVERYONE WRITES FIRST:

    GET /items?limit=20&offset=40

  IT IS BROKEN WHEN THE DATA CHANGES UNDER YOU. Page 1 is items 1-20.
  Someone inserts a new item at the top. Page 2 with offset=20 now
  starts at what was item 19 — so the user sees item 20 twice and
  never sees item 41.

    before insert:  [1..20][21..40]
    after insert:   [N,1..19][20..39]    <- 20 repeats, 40 skipped

  It also gets slower as the offset grows, because the database must
  count and discard every skipped row.

  CURSOR PAGINATION FIXES BOTH:

    GET /items?limit=20&after=eyJpZCI6NDB9

  The cursor encodes a position in a stable sort order, so the query
  becomes "give me 20 rows after this one" — an index seek, at
  constant cost regardless of depth, with no duplicates or skips.

  ITS COST: you cannot jump to page 7. Cursor pagination gives
  next/previous, not numbered pages. That is a genuine product
  trade-off, not a purely technical one.

    numbered pages needed  -> offset, and accept the anomalies
    infinite scroll / feed -> cursor, always
    stable historical data -> offset is fine

  INFINITE SCROLL WITH useInfiniteQuery:

    const { data, fetchNextPage, hasNextPage, isFetchingNextPage } =
      useInfiniteQuery({
        queryKey: ['items'],
        queryFn: ({ pageParam }) => getItems(pageParam),
        initialPageParam: null,
        getNextPageParam: (last) => last.nextCursor ?? undefined,
      });

  Trigger fetchNextPage with an IntersectionObserver on a sentinel
  element rather than a scroll listener — it does not fire on every
  scroll frame and it handles the case where the list is shorter than
  the viewport.

  WHAT INFINITE SCROLL COSTS: no footer access, no reliable deep
  linking, a broken back button unless you restore scroll position,
  and unbounded DOM growth that needs virtualisation. A "load more"
  button avoids most of it.

  PREFETCH ON INTENT — the cheapest perceived-performance win there
  is:

    <Link
      onMouseEnter={() => qc.prefetchQuery({ queryKey: ['user', id],
                                             queryFn: … })}
    />

  The gap between hover and click is typically 100-300ms, which is
  often the entire request. Guard it on a fast connection
  (navigator.connection.saveData) so you do not spend a mobile user's
  data on pages they never open.

Interview Questions

Beginner: What is wrong with fetching in a useEffect with no cleanup?

It has a race condition. If the dependency changes quickly — a user id going from 1 to 2 — two requests are in flight, and responses are not guaranteed to arrive in the order they were sent. If the first resolves last, its setState runs last and the screen shows user 1 while the prop says 2.

Nothing throws. The UI is simply wrong, and because it depends on network timing it reproduces on a slow connection and never on your machine.

useEffect(() => {
  let ignore = false;
  getUser(id).then(u => { if (!ignore) setUser(u); });
  return () => { ignore = true; };
}, [id]);

The cleanup runs before the effect re-runs, so the previous request's callback finds ignore === true and does nothing.

A second, separate bug in the usual version: fetch does not reject on 404 or 500. You must check response.ok yourself, or r.json() will throw a confusing parse error on the error page.

Beginner: Why is isLoading plus data plus error a poor way to model a request?

Three independent booleans-ish variables give eight combinations, but only four are meaningful. The other four — loading and errored, both data and error set — cannot happen, yet every consumer has to decide what to render for them.

In practice that decision is an if chain whose order silently picks a winner, and different components in the same codebase pick differently.

const [state, setState] = useState({ status: 'idle' });
// 'idle' | 'loading' | { status:'success', data } | { status:'error', error }

A status union makes the impossible states unrepresentable. With TypeScript's discriminated unions, state.data does not exist outside the success branch, so the compiler enforces correct handling.

Two states people still miss: empty — a successful response with zero rows is neither loading nor an error, and a blank area reads as broken — and refreshing, where you have stale data and a request in flight and should show the data, not a spinner.

Mid: What is a request waterfall and how do you eliminate one?

An effect runs after its component commits, so a child that fetches cannot start until its parent has rendered — which requires the parent's data. Three nested components each fetching for 200ms take 600ms instead of 200ms.

It is invisible in code review because each component is individually reasonable. You find it in the network panel, where the requests form a staircase rather than a block.

FixEffectCost
Hoist and Promise.allParallel immediatelyParent knows children's data needs
Router loaderFetch starts at navigation, overlapping renderRequires a data router
Render-as-you-fetch + SuspenseParallel with per-boundary fallbacksMore machinery
Server componentsThe round trip disappearsA framework commitment

What does not help is making each request faster — a staircase of three 50ms requests is still a staircase.

And parallel is not always available: if /posts genuinely needs a value from /user, the dependency is real, and the right fix is a server endpoint that returns both.

Mid: When should you use AbortController rather than an ignore flag?

They solve different problems. An ignore flag lets the request complete and discards the result; AbortController cancels the request so the browser closes the connection.

Use the flag by default — it works with any promise and needs no error handling. Reach for AbortController when the request itself is worth stopping: an expensive server operation, a large response on a metered connection, a search-as-you-type endpoint firing constantly, or when you are near the six-connections-per-host limit on HTTP/1.1.

The mandatory detail is the error guard. Aborting rejects the promise, so without if (e.name === 'AbortError') return; every cancellation is reported to the user as a failure — and in StrictMode's development double-mount that means an error on every page load.

Never abort a mutation. Aborting a POST does not undo it — the server may already have committed — so you lose the response while keeping the effect, which is the worst outcome.

Senior: Why do teams end up with server data in Redux, and what is the better model?

Because it looks like state. It lives in the app, components read it, so it goes in the store next to everything else.

The better model is that server data is a cache, not state. You do not own it — the server does — and your copy is a possibly-stale replica. Every hard question follows from that framing: when is it stale, when do you refetch, what do you show while refetching, how do you invalidate after a write, what happens when two components want the same record.

Treating it as ordinary client state means answering all of those by hand, in application code, and the result is a home-grown cache with none of the deduplication, background revalidation or garbage collection a real one has. That is the actual source of most "React state management is complicated" complaints — the state library was never the problem.

A query library answers them once: queryKey identifies a cache entry, stale-while-revalidate defines the display policy, and invalidation after mutations defines coherence.

What is left for a client store is genuinely client-owned state — a wizard's current step, an unsaved draft, UI preferences — and there is usually far less of it than teams expect. My recommendation is a server-cache library plus useState and the URL, and to add a client store only when a concrete need appears.

Senior: Walk through implementing an optimistic update correctly.

Four steps, and the two people skip are the ones that matter.

onMutate: async (next) => {
  await qc.cancelQueries({ queryKey: ['user', next.id] });  // 1
  const previous = qc.getQueryData(['user', next.id]);      // 2
  qc.setQueryData(['user', next.id], next);                 // 3
  return { previous };
},
onError: (e, next, ctx) =>
  qc.setQueryData(['user', next.id], ctx.previous),         // 4
onSettled: (d, e, next) =>
  qc.invalidateQueries({ queryKey: ['user', next.id] }),

1 — cancel in-flight queries. Skipped, a refetch that was already running can land after your optimistic write and silently undo it. The bug is intermittent and looks like the update "sometimes doesn't stick".

2 and 4 — snapshot and roll back. Without the rollback, a failed mutation leaves the UI showing a change that never happened, and the user only finds out on refresh — which is worse than never having shown it, because they have moved on believing it succeeded.

The onSettled invalidation reconciles with the server on both paths, because the server's version can differ from your prediction even on success — a normalised field, an updated timestamp, a computed total.

When not to be optimistic: when failure is likely (a flaky third party, a conflict-prone resource), when the server computes something you cannot predict (an id, a rank, a price), or when being wrong is expensive — a payment or a destructive delete. There, a pending state is honest and cheap.

The general principle: an optimistic update is a prediction, so you owe the user a correction path when the prediction is wrong.

      old.map(m => m.id === id ? { ...m, read: true } : m));
  },
  onSettled: () => qc.invalidateQueries({ queryKey: ['messages'] }),
});
Solution

Two defects, and the intermittency points at the first.

1 — no cancelQueries. If a background refetch of ['messages'] is already in flight when you write optimistically, its response lands afterwards carrying the old read: false and overwrites your change. Whether a refetch happens to be in flight is timing-dependent — hence "intermittently".

2 — no rollback. If the mutation fails, nothing restores the previous value. The invalidation in onSettled usually masks this, but between the failure and the refetch the UI is lying, and if the refetch also fails it stays wrong.

onMutate: async (id) => {
  await qc.cancelQueries({ queryKey: ['messages'] });   // 1
  const previous = qc.getQueryData(['messages']);       // 2
  qc.setQueryData(['messages'], old =>
    old.map(m => m.id === id ? { ...m, read: true } : m));
  return { previous };
},
onError: (e, id, ctx) =>
  qc.setQueryData(['messages'], ctx.previous),          // 3
onSettled: () => qc.invalidateQueries({ queryKey: ['messages'] }),
StepPrevents
cancelQueriesAn in-flight refetch clobbering the optimistic write
Snapshot + onErrorA failed mutation leaving the UI wrong
onSettled invalidateDrift from the server's actual version

The snapshot must be taken after the cancel, or you may capture a value that the in-flight response is about to replace.

Rapid toggling is the remaining edge case: several mutations overlap and the last onSettled wins. A mutation key with a serial execution scope, or debouncing the toggle, handles it.

6 (hard): Users report seeing duplicate rows and missing rows in an activity feed as they scroll. The API is GET /activity?limit=20&offset=N. Explain and redesign.
Solution

Offset pagination over data that changes underneath the reader. The offset is a position in a result set that is recomputed on every request, so any insert or delete above the window shifts everything.

page 1 (offset 0):   [1..20]
  ← two new events arrive at the top
page 2 (offset 20):  [19, 20, 21 …]   ← 19 and 20 repeat, 39 and 40 skipped

An insert above the window causes duplicates; a delete causes skips. On an active feed both happen constantly.

There is a second, quieter problem: OFFSET 10000 forces the database to generate and discard ten thousand rows, so deep pages get progressively slower.

// cursor-based
GET /activity?limit=20&after=<cursor>
// cursor encodes the last row's position in a STABLE sort:
//   base64({ createdAt: '2026-09-08T10:00:00Z', id: 8412 })

SELECT * FROM activity
WHERE (created_at, id) < ($1, $2)    -- tuple comparison, index seek
ORDER BY created_at DESC, id DESC
LIMIT 20;

The id tie-breaker is not optional. Two rows with the same created_at make the ordering ambiguous, and the same duplicate/skip bug returns at that boundary.

What you give up is numbered pages — that is a product decision, not a technical one. For a feed it costs nothing; for a data table where users say "go to page 7" it may be unacceptable, and there offset with its anomalies is the honest trade.

Client side, useInfiniteQuery with getNextPageParam reading nextCursor, triggered by an IntersectionObserver on a sentinel — not a scroll listener, which fires every frame and misses the case where the list is shorter than the viewport. Add virtualisation once the accumulated list passes a few hundred rows.

🎯 Key Takeaways

  • A fetch effect without cleanup has a race — a slow earlier response can overwrite a newer one.
  • fetch does not reject on 404 or 500 — check response.ok yourself.
  • The ignore flag discards a result; AbortController cancels the request — different tools.
  • Aborting rejects the promise, so an AbortError guard is mandatory.
  • Never abort a mutation — the server may already have committed.
  • Effects run after commit, so nested fetching creates waterfalls — the largest source of perceived React slowness.
  • Fix waterfalls structurally — hoist, use a loader, or move the fetch to the server.
  • Three independent request variables admit impossible states; a status union removes them.
  • Empty and refreshing are states too — a blank area reads as broken, and a spinner over existing data is a regression.
  • Server data is a cache, not state — that reframing answers every hard question about it.
  • The query key is the API; a missing dependency makes two queries share one cache entry.
  • An optimistic update needs cancelQueries, a snapshot, and a rollback — the first prevents the intermittent revert.
  • Be optimistic only when failure is unlikely and cheap, and never for values the server computes.
  • Offset pagination duplicates and skips rows on live data and degrades with depth.
  • Cursor pagination fixes both, at the cost of numbered pages — and needs a unique tie-breaker in the sort.
  • Prefetch on hover — the 100–300ms before a click is often the whole request.
