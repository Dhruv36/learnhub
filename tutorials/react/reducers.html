useReducer & State Machines State Management

What you'll master: the three signals that useState has run out — several pieces moving together, the next state depending on the previous in non-trivial ways, and update logic duplicated across handlers; useReducer's mechanics and why the reducer must be pure when StrictMode calls it twice in development; actions as events that happened, not setters in disguise, and why that one naming decision removes whole categories of bug; dispatch's stable identity, which is the reason it never belongs in a dependency array; the lazy init argument; modelling status as an explicit machine so that isLoading && error becomes unrepresentable; reducer-plus-context and exactly where it stops scaling; and when a reducer is over-engineering for two useState calls. Prerequisites: State & useState (immutable updates) and Props (reference identity).

Part 1 — The Three Signals That useState Has Run Out

useReducer is not "the advanced useState". It is the same state cell with a different write interface: instead of handing React a value, you hand it a description of what happened and one function decides the value. That is worth doing only when the deciding is hard. Three symptoms say it is.

  THE SAME CART, BOTH WAYS.

  useState — the rules are smeared across handlers:

    function addItem(p) {
      setItems(is => {
        const found = is.find(i => i.id === p.id);
        if (found) return is.map(i =>
          i.id === p.id ? { ...i, qty: Math.min(i.qty + 1, p.stock) } : i);
        return [...is, { ...p, qty: 1 }];
      });
      setError(null);              // easy to forget
      setCoupon(c => revalidate(c, /* the NEW items… which we lack */));
    }

  Look at that last line. addItem needs the items AFTER the update, and
  it does not have them — the setter callback has them but cannot reach
  across to the coupon setter. The usual "fix" is to duplicate the merge
  logic above the setState. That is how signal 3 gets born.

  useReducer — one function sees the WHOLE state, so it is a non-issue:

    case "item_added": {
      const items = mergeItem(state.items, action.product);
      return { ...state, items, error: null,
               coupon: revalidate(state.coupon, items) };
    }

  Nothing clever happened. The state was ALREADY one thing with one
  transition rule; useState just had no place to write it down.

Part 2 — Mechanics, and Why the Reducer Must Be Pure

  const [state, dispatch] = useReducer(reducer, initialArg, init?);
                             ^         ^            ^
                             |         |            +-- lazy initialiser
                             |         +-- passed to init, or used as-is
                             +-- (state, action) => nextState

  WHAT HAPPENS ON dispatch(action):

    1. React appends the action to this hook's queue. It does NOT call
       your reducer yet — dispatch schedules, like setState. `state` is
       a const captured by this render's closure, so the next line
       still reads the CURRENT value.
    2. React schedules a re-render of the owning component.
    3. During that render React replays the queue:
         next = reducer(reducer(reducer(current, a1), a2), a3)
       The reducer runs in the RENDER PHASE — not in the handler, not
       after commit.
    4. If the result is Object.is-equal to the current state, React may
       bail out and skip re-rendering children. This is why
       `default: return state` matters, and why `return { ...state }`
       in the default arm is a performance bug.

  CONSEQUENCES PEOPLE GET WRONG:

    dispatch(a); console.log(state)   -> the OLD state. Always.
    dispatch(a); dispatch(b)          -> both applied, b sees a's result
    dispatch during render            -> infinite loop

Step 3 is where purity stops being a style preference. Your reducer runs in the render phase, and the render phase is territory React reserves the right to re-enter.

  WHY REACT MAY CALL YOUR REDUCER TWICE

  In DEVELOPMENT, under <StrictMode>, React double-invokes render
  functions, initialisers, and REDUCERS. It does NOT happen in a
  production build — it is a detector, surfacing impurity while you can
  still see it.

    case "logged":
      analytics.track("action", action);              // ❌ SIDE EFFECT
      state.log.push(action.msg);                     // ❌ MUTATION
      return { ...state, id: crypto.randomUUID() };   // ❌ NOT PURE

  In dev: two analytics events and two log entries per dispatch, and two
  different UUIDs — the second wins, so the id you see is never the one
  your handler thought it made. In production the double-invoke is off,
  so this "works", and dev is the only place the bug shows. People
  conclude StrictMode is broken and delete it. It was doing its job.

  THE DEEPER REASON, beyond StrictMode:

    - CONCURRENT RENDERING may abandon a render and restart at a higher
      priority. The abandoned render's side effects already happened;
      its state never shipped.
    - REPLAY. React re-derives state by replaying the queue from a base
      state. A reducer that reads the clock answers differently the
      second time.
    - TIME-TRAVEL DEBUGGING re-runs the reducer over a recorded action
      list. If it is not a pure function of (state, action), the
      replayed timeline diverges from what the user saw — which makes
      the tool worse than useless, because it lies confidently.

  THE RULE: everything the reducer needs arrives IN THE ACTION.

    dispatch({ type: "submitted", at: Date.now(), id: crypto.randomUUID() })

  Impurity moved into the handler: handlers run once per gesture,
  reducers run once per render attempt.
🔑 StrictMode's double-invoke is development-only. It never runs twice in a production build, and it is not a performance characteristic to optimise around. Treat a StrictMode symptom as a report about your code, not about React — the failures it surfaces are exactly the failures concurrent rendering can cause in production, only reproducible on demand.

Part 3 — Actions Are Events, Not Setters in Disguise

  THE MOST COMMON REDUCER MISTAKE IS NOT TECHNICAL. IT IS NAMING.

  Setter-shaped actions — a reducer that gained nothing:

    dispatch({ type: "setName",  value });
    dispatch({ type: "setError", value: null });

    case "setName": return { ...state, name: action.value };

  This is useState with ceremony and a bigger bundle. Every rule still
  lives in the component: the handler that clears the error is the one
  that must REMEMBER to clear it, in all four places it is typed.

  Event-shaped actions — the reducer owns the rules:

    dispatch({ type: "field_changed", field: "name", value });
    dispatch({ type: "submit_failed", errors });

    case "field_changed":
      return { ...state,
               values: { ...state.values, [action.field]: action.value },
               errors: omit(state.errors, action.field),  // the RULE:
               dirty:  true };                            // editing clears
                                                          // that field's error

  WHY THIS REDUCES BUGS:

    1. ONE PLACE TO ADD A RULE. "Editing any field also clears the
       banner error" is one line here. In the setter version it is a
       change in every handler, and you will miss one.
    2. THE ACTION LOG BECOMES A NARRATIVE. field_changed,
       field_blurred, submit_started, submit_failed tells you what the
       USER did. setName, setName, setError tells you what the code
       did — which you could already read in the code.
    3. ATOMICITY. One event that changes four fields is one dispatch
       and one render. Four setters are four chances to render a state
       where status is "error" and errors is still empty.
    4. THE ACTION TYPES BECOME A SPEC — the union of them tells a new
       engineer everything the feature can do.

  A USEFUL TEST: can you name the action without knowing the state
  shape? "item_added" — yes. "setItems" — no, it is named after a
  variable, so renaming the variable renames the action.

Part 4 — dispatch Identity and the Lazy init

  DISPATCH IS STABLE FOR THE LIFETIME OF THE COMPONENT — the same
  guarantee React makes for a useState setter. Documented, not inferred.

    useEffect(() => {
      const socket = connect(url);
      socket.on("tick", t => dispatch({ type: "ticked", t }));
      return () => socket.close();
    }, [url]);        // dispatch NOT in the deps — correct, and
                      // eslint-plugin-react-hooks does not ask for it.

  The callback version of the same effect:

    }, [url, onTick]);   // onTick is rebuilt every parent render, so
                         // the socket tears down and reopens on EVERY
                         // render unless the parent wraps it in
                         // useCallback with correct deps.

  That is the quiet argument for reducers in anything with
  subscriptions, timers or listeners: a stable callback for free,
  without a dependency array someone will get wrong. It also survives
  context — a context whose value is `dispatch` never changes identity,
  so its consumers never re-render. That is the basis of Part 6.

  ---------------------------------------------------------------

  THE THIRD ARGUMENT: LAZY INITIALISATION

  Without init, the expression producing initialArg runs on EVERY
  render, though only the first render uses the result:

    useReducer(reducer, expensiveParse(localStorage.getItem("cart")))
    //                  ^ runs every render, thrown away 99% of the
    //                    time. Same trap as useState(expensive()).

  With init, React calls init(initialArg) ONCE, on mount:

    useReducer(reducer, "cart", key => expensiveParse(localStorage.getItem(key)))

  TWO REASONS IT EXISTS; the second is the one people miss:

    1. Skip the work on every render after the first.
    2. RESET:  case "reset": return init(action.key);
       "Reset to initial" is one line and cannot drift from the real
       initial state, because there is only one copy of it.

  STRICTMODE NOTE: init is double-invoked in development too. Reading
  localStorage is fine; if it WRITES anything it is not an initialiser,
  it is an effect wearing a disguise.

Part 5 — Modelling It As an Explicit State Machine

The highest-value thing a reducer enables is not centralised updates. It is making illegal states impossible to represent. Independent booleans allow every combination; a status union allows only the ones you listed.

  BOOLEAN SOUP — four independent flags, sixteen combinations:

    const [isLoading, setLoading]   = useState(false);
    const [isError,   setError]     = useState(false);
    const [isSuccess, setSuccess]   = useState(false);
    const [isRetrying, setRetrying] = useState(false);

  How many are legal? Four, maybe five. The rest your UI will render:

    isLoading && isError    -> a spinner on top of an error message
    isSuccess && isError    -> "Saved!" next to "Save failed"
    !anything               -> a blank panel with no explanation
    isRetrying && !isError  -> retrying what?

  Every one is reachable by a real sequence: a slow request failing
  after a fast one succeeded, an unmount mid-flight, a double-clicked
  Save.

  A STATUS UNION — the illegal states stop existing:

    type State =
      | { status: "idle" }
      | { status: "loading"; startedAt: number }
      | { status: "success"; data: Item[] }
      | { status: "error";   message: string; retries: number };

  Note what moved: `data` exists ONLY in the success state, `message`
  ONLY in the error state. You cannot read state.data in the error
  branch — TypeScript knows it is not there, and in plain JS the
  discriminated render forces the same discipline:

    switch (state.status) {
      case "idle":    return <Empty />;
      case "loading": return <Spinner />;
      case "success": return <List items={state.data} />;
      case "error":   return <Retry msg={state.message} />;
    }

  isLoading && error is now UNREPRESENTABLE, not merely unlikely. The
  bug class was not fixed; it was deleted.

Once state is a union, the reducer is a transition table. Writing that table out — before the code — is the design tool: it makes you answer questions the boolean version let you avoid.

State ↓ / Action →fetch_startedfetch_succeededfetch_failedcancelled
idleloading———
loadingloading (ignore, or restart)successerroridle
successloading (keep old data)successerror—
errorloading (retries + 1)successerror (retries + 1)idle
  READ THE DASHES. Each is a decision you would otherwise have made by
  accident, at 3am, in whichever handler happened to run:

    - fetch_succeeded while idle: a response arrived for a request we
      cancelled. Ignoring it fixes the classic race where a slow first
      request overwrites a fast second one.
    - fetch_started while loading: does a second click restart the
      request or get swallowed? "Ignore" makes the button idempotent;
      "restart" is right for search-as-you-type. No universal answer —
      the table is where you write yours down.
    - fetch_started while success: staying on old data rather than
      dropping to a spinner is the difference between a list that
      refreshes and one that flashes empty. A product decision, living
      in one cell of this table.

  THE REDUCER IS THE TABLE:

    function reducer(state, action) {
      switch (state.status) {
        case "idle":
          if (action.type === "fetch_started")
            return { status: "loading", startedAt: action.at };
          return state;                       // everything else ignored

        case "loading":
          switch (action.type) {
            case "fetch_succeeded": return { status: "success", data: action.data };
            case "fetch_failed":    return { status: "error", message: action.message,
                                             retries: (state.retries ?? 0) + 1 };
            case "cancelled":       return { status: "idle" };
            default:                return state;
          }
        …
      }
    }

  SWITCHING ON STATE FIRST, ACTION SECOND is what makes a machine a
  machine. The usual action-only switch works, but cannot express
  "ignore this action in this state" without an `if` in every arm — and
  those ifs are exactly where races hide. XState formalises this with
  guards, entry/exit actions and a visualiser; you do not need the
  library to get most of the value, you need the table.

Part 6 — Reducer + Context, and Where It Stops Scaling

  THE "POOR MAN'S REDUX" — two contexts, one reducer:

    const StateCtx    = createContext(null);
    const DispatchCtx = createContext(null);

    export function CartProvider({ children }) {
      const [state, dispatch] = useReducer(cartReducer, null, init);
      return (
        <DispatchCtx.Provider value={dispatch}>
          <StateCtx.Provider value={state}>{children}</StateCtx.Provider>
        </DispatchCtx.Provider>
      );
    }

  WHY TWO CONTEXTS AND NOT ONE OBJECT:

    value={{ state, dispatch }}    // ❌ a NEW object every render, so
                                   //    every consumer re-renders even
                                   //    if it only needs dispatch

  Split, `dispatch` is stable forever, so an "Add to cart" button
  consuming only DispatchCtx NEVER re-renders when the cart changes. In
  a grid of 200 buttons that is smooth versus janky.

  WHERE IT STOPS. The ceiling is precise, and it is not about size:

    EVERY CONSUMER OF StateCtx RE-RENDERS ON EVERY STATE CHANGE,
    regardless of which field it reads.

  Context has NO change tracking. The value's identity changed, so React
  re-renders every component that called useContext(StateCtx) — one
  reading state.theme re-renders because state.cart.items changed.
  React.memo does not help: memo blocks updates arriving through PROPS,
  and context bypasses props entirely.

  THE NUMBERS. With N consumers and a state object updated per
  keystroke, each keystroke costs N renders. N=10 at 0.05ms is 0.5ms —
  invisible inside a 16ms frame. N=300 with a few rendering charts is
  tens of milliseconds and the input visibly lags. The threshold is not
  a component count, it is "does the p95 update fit in the frame
  budget?" — one Profiler recording answers it.

  MITIGATIONS, IN ORDER: split by DOMAIN (theme and cart update at
  totally different rates; one god-context couples them); push state
  DOWN (half the "global" state is read by one subtree); pass CHILDREN
  through (a consumer re-rendering is cheap, its subtree is not); then
  an external store with SELECTORS — the real fix, and the point at
  which context was the wrong tool.

  WHAT DOES NOT WORK: React.memo on consumers, useMemo around the value
  (fixes accidental identity churn, not per-field granularity), or ten
  contexts that all change together.

If the state is a boolean and a string, the transitions are obvious, and no handler touches both, a reducer adds an action vocabulary, a switch, and an indirection between the click and the change — for nothing. The honest heuristic: reach for a reducer when you can name three or more events the feature responds to, or when you have already written the same update in two handlers. Interview Questions

Beginner: What is useReducer and how is it different from useState?

Both create one piece of state in a component. The difference is the write interface. useState gives you a setter that takes the next value (or a function producing it), so each call site decides what the state becomes. useReducer gives you dispatch, which takes an action describing what happened, and a single reducer function decides what the state becomes.

Mechanically, useState is implemented in terms of useReducer inside React — with a trivial reducer that returns whatever you passed. So there is no capability useReducer has that you literally cannot achieve with useState; the difference is where the update logic lives, and therefore how many places it can be wrong.

The practical reason to prefer it is centralisation. When five handlers need the same three-step update, useState spreads that update across five places and useReducer keeps it in one. The secondary reason is testability: a reducer is a pure function, so you test "removing the last item empties the cart" by calling it, with no rendering involved.

Beginner: Why must a reducer be a pure function?

Because React calls it during rendering, and rendering is not a guaranteed once-per-update event. React may re-run a render, throw one away and restart it at a higher priority, or — in development under StrictMode — deliberately call your reducer twice to surface impurity.

So if the reducer sends an analytics event, you get two events per dispatch in development. If it calls Math.random() or Date.now(), replaying the same actions produces a different result the second time, which breaks the whole idea of deriving state from a log of actions — that is what makes time-travel debugging possible in the first place.

The rule that follows is simple: everything the reducer needs must arrive inside the action. If you need a timestamp or an ID, generate it in the event handler — which runs once per user gesture — and put it in the payload.

Worth being precise about the StrictMode part: the double-invoke is development-only and does not happen in a production build. It is a detector, not a behaviour to work around.

Mid: Why should actions be named after events rather than setters?

Because a setter-shaped action leaves the rules in the components. If your actions are setItems, setTotal and setError, then every handler still has to remember the sequence — remove the item, recompute the total, clear the error — and the reducer has become a switch full of one-line assignments. You paid the ceremony and got none of the benefit.

With item_removed, the reducer owns the consequences. Adding "and clear the coupon if it no longer applies" is one line in one arm, and it takes effect for every path that removes an item, including the one someone adds next month.

It changes what you can observe, too. An action log of filter_changed, page_requested, fetch_failed is a description of what the user did — you can replay it, attach it to a bug report, and reason about it. A log of setPage, setLoading, setError tells you what the code did, which you could already read in the code.

There is also an atomicity argument. One event that changes four fields is one dispatch and one render, and there is no intermediate state where three fields have updated and the fourth has not. Four setters give you four chances to render something inconsistent, particularly outside React's automatic batching.

The test I use: can you name the action without referring to the state shape? item_added passes. setItems fails — it is named after a variable, so renaming the variable renames the action, which tells you the coupling is wrong.

Mid: Does dispatch need to be in a dependency array, and why does the answer matter?

No. React guarantees that dispatch has a stable identity for the lifetime of the component, exactly like a useState setter. eslint-plugin-react-hooks knows this and will not ask you to add it.

Why it matters is the interesting half. Consider an effect that opens a WebSocket and needs to push messages into state. If it depends on a callback prop, that callback is a new function on every parent render, so the effect tears down and reconnects the socket on every render unless the parent wraps it in useCallback with a correct dependency array — and that array is a thing someone will eventually get wrong.

With a reducer, the effect depends only on the URL. The socket opens once. You get a stable callback for free, without a memoisation layer to maintain.

The same property is why the state/dispatch context split works. A context whose value is dispatch never changes identity, so components that only need to dispatch never re-render when state changes. In a grid of two hundred "add to cart" buttons, that is the whole difference between smooth and janky — and it falls out of a guarantee, not a trick.

Senior: When does useReducer plus context stop being enough, and what replaces it?

The ceiling is precise, and it is not about how much state you have. It is that context has no change tracking. When the provider's value identity changes, React re-renders every component that called useContext on it, regardless of which field that component reads. A component reading state.theme re-renders because state.cart changed, and React.memo cannot stop it, because memo blocks updates arriving through props and context bypasses props.

So the failure mode is a rate problem: high-frequency updates times many consumers. A keystroke in a search box updating a state object that three hundred components read costs three hundred renders per keystroke. Ten consumers at fifty microseconds each is invisible; three hundred, a few of them rendering charts, blows the 16ms frame budget and the input visibly lags. I would not guess at the threshold — I would record a Profiler session and look at the p95 commit duration.

The mitigations in order of cost: split by domain first, because a theme context and a cart context genuinely update at different rates and putting them together couples them for no reason. Then push providers down — a surprising amount of "global" state is read by one subtree. Then make sure the provider passes children through rather than rendering them, so the provider re-rendering does not re-render the whole subtree.

When those run out, the answer is an external store with selector-based subscriptions — Zustand, Redux Toolkit, Jotai. They are built on useSyncExternalStore, and the thing they buy you is exactly the thing context does not have: a component subscribes to a slice, and re-renders only when that slice changes.

My recommendation: start with useReducer plus split contexts, because it is zero dependencies and the reducer you write is portable to any of those libraries later. Move when the Profiler says so, not when the state "feels global". And check first whether the state in question is actually server data — most apps that reach for a store at this point needed a query library instead, and the two solve different problems.

Senior: How would you model an async flow as an explicit state machine, and what does that buy over booleans?

I would replace independent booleans with a discriminated union on a status field, and nest each state's data inside that state — { status: "success", data } and { status: "error", message, retries }, so data literally does not exist in the error state.

What that buys is the deletion of a bug class rather than the fixing of a bug. Four booleans are sixteen representable combinations of which perhaps four are legal, and the illegal ones are all reachable by real sequences — a slow request resolving after a fast one, a double-clicked save, a component unmounting mid-flight. That is where the spinner-on-top-of-an-error screenshot comes from. With a union, isLoading && error cannot be constructed.

Then I would write the transition table before the reducer: states down the side, actions across the top. The value is in the empty cells. "A response arrives while we are idle" — that is the cancelled request coming back, and ignoring it is the fix for the classic race where a slow first request overwrites a fast second one. "A fetch starts while we are already loading" — does the second click restart or get swallowed? For a submit button, swallow; for search-as-you-type, restart. There is no universal answer, and the table is where you record the one you chose instead of inheriting whatever the handler ordering happened to do.

Implementation detail worth arguing: I switch on state first and action second, not the usual action-only switch. That is what makes "ignore this action in this state" the default rather than something you express with an if in every arm — and those ifs are exactly where races hide.

On tooling: XState formalises this with guards, entry and exit actions, and a visualiser, and it is genuinely good for multi-step wizards, media players and checkout flows where the diagram is the spec and non-engineers need to read it. But it is a real dependency with a real learning curve, and most teams get eighty per cent of the value from a plain reducer plus the discipline of writing the table down first. I would start with the plain reducer and adopt XState when the flow has enough states that people are drawing it on whiteboards anyway.

1 (easy): Convert this counter to useReducer with increment, decrement and reset, where the count cannot go below zero: const [count, setCount] = useState(0);
Solution 
function counterReducer(count, action) {
  switch (action.type) {
    case "incremented": return count + 1;
    case "decremented": return Math.max(0, count - 1);
    case "reset":       return 0;
    default:            return count;
  }
}

function Counter() {
  const [count, dispatch] = useReducer(counterReducer, 0);
  return (
    <>
      <button onClick={() => dispatch({ type: "decremented" })}>−</button>
      <span>{count}</span>
      <button onClick={() => dispatch({ type: "incremented" })}>+</button>
    </>
  );
}

Two details that are not decoration. The state does not have to be an object — a reducer over a number is perfectly normal, and wrapping it in { count } just to look like Redux costs you an allocation and a spread on every action.

default: return count, not default: return { ...state }. Returning the identical value lets React compare with Object.is, find no change, and bail out of re-rendering the subtree. Returning a new object for an action you ignored means every stray dispatch re-renders everything below.

The clamp is the point of the exercise. In the useState version, "cannot go below zero" lives in whichever handler happens to decrement — and the second decrement button someone adds will not have it. Here the rule is in the transition, so it applies to every path that ever dispatches decremented.

2 (easy): This reducer looks right and the list never updates on screen. Why? case "added": state.items.push(action.item); return state;
Solution 
// WRONG — pushes into the existing array, returns the SAME state object.
case "added":
  state.items.push(action.item);
  return state;

// RIGHT
case "added":
  return { ...state, items: [...state.items, action.item] };
StepWhat happens
The pushSucceeds. The array genuinely contains the new item
The returnHands React the same object it already has
React's comparisonObject.is(prev, next) is true — "nothing changed"
The renderBailed out. No re-render is scheduled
What you seeThe data is correct in the console and stale on screen — and it "fixes itself" the next time anything unrelated re-renders the component

The intermittency is what makes this expensive. Add two items and click something else, and both appear at once — so the bug reproduces as "sometimes the list is one item behind", which is the shape of ticket that gets closed as not-reproducible and reopened twice.

The near-miss version is worse, not better. state.items.push(x); return { ...state }; renders correctly, because the outer object is new. But the previous state's array was mutated, so anything holding the old state — Redux DevTools' history, a useMemo keyed on the old array, an undo stack — now holds data that has silently changed underneath it. Time-travel replays a history that never happened.

If nested updates are getting painful, use Immer rather than deeper spreads. produce(state, draft => { draft.items.push(x) }) looks like mutation, tracks the writes on a proxy, and returns a new object — with structural sharing, so untouched branches keep their identity and stay memo-friendly. Redux Toolkit builds it into createSlice, which is why modern Redux code appears to mutate.

3 (medium): A search box does setQuery(q); setPage(1); setResults([]); setLoading(true); in one handler, and the same four lines appear in the "clear filters" handler with one of them missing. Rewrite with a reducer, and say what the bug in the second handler was.
Solution 
function searchReducer(state, action) {
  switch (action.type) {
    case "query_changed":
      return { ...state, query: action.query, page: 1,
               results: [], status: "loading" };

    case "filters_cleared":
      return { ...state, filters: {}, page: 1,
               results: [], status: "loading" };

    case "results_arrived":
      // Ignore a response for a query we have since moved on from.
      if (action.forQuery !== state.query) return state;
      return { ...state, results: action.results, status: "success" };

    default:
      return state;
  }
}

The bug in the second handler was the missing setPage(1). Clearing filters while on page 4 leaves page at 4, so the next fetch requests page 4 of a result set that now has one page — and the user gets an empty screen with no error. Nothing crashed; "no results" is a plausible-looking outcome, which is why this class of bug survives review.

What the reducer version preventsHow
Handlers drifting apart"Any change to the query set resets pagination" is written in the arms, not remembered at four call sites
Rendering an inconsistent intermediateOne dispatch, one state transition. Not four setters whose interleaving you have to reason about
The stale-response raceresults_arrived carries the query it was for, and the reducer discards it if the query moved on. Impossible to express cleanly with independent setters
An untestable ruleexpect(searchReducer({page: 4, …}, {type:"filters_cleared"}).page).toBe(1) — no rendering, no mocking

The race deserves its own note. Without the forQuery guard, typing "react" then "redux" can show results for "react" if the first request is slower — the classic out-of-order response bug. The reducer is a good place for the guard because it is the only code that sees both the response and the current query at the same instant.

What I would push back on in review: if this state is really "results for a query", it is server cache, and a query library gives you the race handling, deduplication and caching for free. The reducer here should own query, page and filters — the client state — and let the cache own results and status.

4 (medium): This provider makes every consumer re-render on every state change, including buttons that only dispatch. Fix it, and explain why React.memo on the buttons does not help. <Ctx.Provider value={{ state, dispatch }}>{children}</Ctx.Provider>
Solution 
const StateCtx    = createContext(null);

}

Problem in the originalEffectWhat the fix does
{{ state, dispatch }} is a fresh object each renderConsumers re-render even when the state is identical — a parent re-render is enoughTwo providers; each value is a single reference

Why React.memo on the buttons does not help. memo intercepts updates that arrive through props: it compares the new props with the old and skips the render if they match. A context update does not arrive through props. React tracks which fibers called useContext for a given context and schedules those fibers directly, walking straight past any memo between them and the provider. This is the single most common "memo doesn't work" report, and the answer is always the same — memo and context are orthogonal mechanisms.

useMemo on the combined value is the half-fix. useMemo(() => ({ state, dispatch }), [state, dispatch]) stops the identity churn from unrelated parent renders, but state is in the deps, so every real state change still produces a new value and still wakes every consumer. It fixes accidental re-renders, not the granularity problem. Splitting fixes both.

The remaining ceiling. Every consumer of StateCtx still re-renders on every state change, whichever field it reads. If that becomes the bottleneck, split StateCtx by domain, or move to a store with selectors — context has no per-field subscription and no amount of memoisation adds one.

5 (hard): Model a file upload as an explicit state machine. States: idle, selecting, uploading (with progress), success, error. Requirements: a retry must preserve the selected file; a response for a cancelled upload must be ignored; progress events must not be able to resurrect a cancelled upload.
Solution 
// State is a UNION. Progress exists only while uploading; the file
// exists in every state that could plausibly retry.
//
//   { status: "idle" }
//   { status: "selecting" }
//   { status: "uploading", file, progress, uploadId }
//   { status: "success",   file, url }
//   { status: "error",     file, message, attempts }

function uploadReducer(state, action) {
  switch (state.status) {

    case "idle":
    case "selecting":
      if (action.type === "file_selected")
        return { status: "uploading", file: action.file,
                 progress: 0, uploadId: action.uploadId };
      return state;

    case "uploading":
      // EVERY arm checks uploadId. This is the whole cancellation story.
      if (action.uploadId !== state.uploadId) return state;
      switch (action.type) {
        case "progress":  return { ...state, progress: action.pct };
        case "succeeded": return { status: "success", file: state.file,
                                   url: action.url };
        case "failed":    return { status: "error", file: state.file,
                                   message: action.message, attempts: 1 };
        case "cancelled": return { status: "idle" };
        default:          return state;
      }

    case "error":
      if (action.type === "retried")
        return { status: "uploading", file: state.file,   // FILE PRESERVED
                 progress: 0, uploadId: action.uploadId,
                 attempts: state.attempts };
      if (action.type === "file_selected")
        return { status: "uploading", file: action.file,
                 progress: 0, uploadId: action.uploadId };
      return state;

    case "success":
      if (action.type === "file_selected")
        return { status: "uploading", file: action.file,
                 progress: 0, uploadId: action.uploadId };
      return state;

    default:
      return state;
  }
}
RequirementHow the machine satisfies itWhat the boolean version would have done
Retry preserves the filefile lives in the error state, so retried reads state.fileKept the file in a separate useState that some reset path clears — retry uploads undefined
Cancelled uploads ignore their responsecancelled moves to idle; a late succeeded hits the idle arm and is ignoredSet isUploading=false, then the late response sets isSuccess=true — a cancelled upload reports success
Progress cannot resurrect a cancelled uploadProgress is only handled in the uploading arm, and only for a matching uploadIdsetProgress is callable from anywhere; the bar fills after cancel
No spinner-over-erroruploading and error are different values of one fieldisUploading && error both true after a failure that forgot one setter

The uploadId is the part that is easy to leave out and expensive to add later. Status alone is not enough: cancel, select a new file, and the first upload's progress events are still arriving. They match on status — we are uploading — so without an id they drive the second upload's progress bar with the first upload's numbers. Generate the id in the handler (not the reducer — that would be impurity) and stamp every event with it.

Switching on state before action is what makes the ignore-cases free. With the conventional action-first switch, "ignore succeeded unless we are uploading this particular id" becomes a guard clause at the top of the succeeded arm — and then the same guard at the top of failed, and progress, and whichever arm someone adds next without remembering. State-first, the guard is written once per state.

What the reducer deliberately does not do: abort the request. That is a side effect and belongs in an effect keyed on the transition, or in the handler that dispatched cancelled. The reducer's job is to make the late response harmless whether or not the abort succeeded — because AbortController races too, and a machine that only works when cancellation is instantaneous is a machine that fails under exactly the conditions you built it for.

6 (hard): A colleague has refactored a component with two useState calls — isOpen and selectedId — into a reducer with four action types, a separate reducer.js, and a context provider. Argue for or against, and say what evidence would change your mind.
Solution
What was addedWhat it costsWhat it prevents
An action vocabularyEvery change is now indirect: read the dispatch, find the arm, read the armNothing, if no rule spans both fields
A separate moduleA one-line change becomes a two-file change and a two-file reviewNothing at this size; helps only when the reducer is big enough to be worth reading alone
A context providerA provider component, two hooks, and a new re-render blast radiusProp drilling that, at two fields, probably was not happening
A switch statementA default arm and a stray-action policy to get rightNothing until there are states to make illegal

I would argue against, and I would be specific about why rather than appealing to simplicity. The three signals for a reducer are: several pieces moving together, a non-trivial dependence on previous state, and duplicated update logic. Two independent booleans that no handler sets in combination hit none of them. What has been bought is an abstraction whose entire value is centralising rules, applied to a case with no rules.

The context provider is the part I would push hardest on. It is a separate decision that got smuggled in with the reducer refactor, and it changes the re-render graph: every consumer now re-renders when either field changes, and the state has been promoted out of the component that owns it, so it can no longer be deleted by deleting that component. Colocation is the default for good reasons; breaking it needs its own justification.

What would change my mind, concretely. If selectedId and isOpen ever move together — "selecting an item opens the panel", "closing clears the selection" — then they are one state with transitions and the reducer is right, because that rule will otherwise be duplicated in the three places that can open the panel. If a third piece of state arrives, particularly a status. If the same open/close logic exists in two components. Or if the state needs to be driven from outside React — a keyboard shortcut handler, a router guard — where a stable dispatch is genuinely easier than threading callbacks.

The asymmetry that settles it. useState to useReducer is a mechanical refactor you can do in ten minutes on the day the third event appears. Guessing wrong in the other direction means every reader pays the indirection tax for months, and nobody ever removes a reducer because removing an abstraction looks like a regression in review. Wait for the third event, or for the second duplicated update. That is not laziness; it is buying the option at the point where you know its price.

🎯 Key Takeaways

  • Reach for a reducer on three signals — several pieces of state moving together, a non-trivial dependence on the previous state, or the same update written in two handlers. Not on "this feels complex".
  • dispatch schedules; it does not update. Reading state on the next line gives you the current render's value, because state is a const captured by that render's closure.
  • The reducer runs during render, not in the handler. That is why purity is a requirement and not a style rule.
  • StrictMode double-invokes reducers in development only. An analytics call that fires twice is a report about your reducer, not about React — and the same impurity breaks abandoned concurrent renders in production.
  • Everything the reducer needs must arrive in the action. Timestamps, IDs and random values are generated in the handler, which runs once per gesture.
  • Impure reducers break replay. Time-travel debugging re-derives state from the action log; a reducer that reads the clock produces a history the user never saw.
  • Name actions after events, not setters. item_removed puts the consequences in one arm; setItems leaves them in every handler.
  • The action log becomes a narrative of what the user did — replayable, attachable to a bug report, and far more useful than a log of which variables were assigned.
  • dispatch has a stable identity for the component's lifetime, so it never belongs in a dependency array — and an effect that dispatches does not reconnect its socket on every render.
  • The third argument is lazy init, and its underrated second use is case "reset": return init(...), so the initial state exists in exactly one place.
  • default: return state, never return { ...state } — the identical reference is what lets React bail out instead of re-rendering the subtree.
  • A status union makes isLoading && error unrepresentable. Four booleans are sixteen states, most illegal and all reachable.
  • Write the transition table before the reducer. The empty cells are the decisions — a late response, a double submit — that you would otherwise make by accident.
  • Switch on state first, action second for real machines: "ignore this action here" becomes the default rather than a guard clause repeated in every arm.
  • Split state and dispatch into two contexts. dispatch never changes identity, so dispatch-only consumers never re-render — and React.memo cannot give you that, because context bypasses props.
  • Reducer + context stops scaling at one precise point: every consumer re-renders on every state change, whichever field it reads. That is when a store with selectors earns its place — and a reducer for two useState calls never did.
