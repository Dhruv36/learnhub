State Architecture Patterns State Management

What you'll master: the five-way classification — server cache, client UI, form draft, URL, derived — that answers where does this value live before you reach for a library; why treating server data as client state is the root of most React state complexity; why derived state must be computed during render, never stored by an effect, and what the two-sources-of-truth bug looks like frame by frame; lifting to the lowest common ancestor and the re-render bill when that ancestor sits high; the URL as a first-class state container; controlled vs uncontrolled as a general component API including the defaultValue + onChange hybrid; and why an array of nested objects makes updates quadratic and shatters memoization. Prerequisites: State, Reducers, Context.

Part 1 — Five Kinds of State, Not One

  "STATE MANAGEMENT" IS THE WRONG QUESTION. There is no single thing
  called state whose management you pick a library for. There are
  five categories with different owners, lifetimes and correct
  storage. Most React pain is a value from one category living in
  another category's container.

  1. SERVER CACHE   — rows that exist in a database. Users, orders,
                      comments. You do not own the truth; you hold a
                      COPY that is stale the moment it arrives.
  2. CLIENT UI      — is the dropdown open, which tab is active,
                      hover index, "I dismissed this banner".
                      Nobody will ever ask the server for it.
  3. FORM DRAFT     — the half-typed value that is not yet a fact.
                      Owned by the user's keyboard until submit.
  4. URL            — filters, sort, page number, selected item.
                      Anything a shared link or a refresh must keep.
  5. DERIVED        — the filtered list, the total, isValid, the
                      object looked up by selectedId. NO storage.
                      It is a computation, not a value you hold.

  THE ROOT MISTAKE, IN THE FORM IT ALWAYS SHIPS:

    const [users, setUsers] = useState([]);
    useEffect(() => { fetch('/api/users')
      .then(r => r.json()).then(setUsers); }, []);

  You just declared yourself owner of data you do not own. Every
  hard part of caching is now YOUR job, hand-written, per component:

    - staleness      when is this copy too old to show?
    - invalidation   who tells this component a mutation happened?
    - deduplication  three components mounted, three identical GETs
    - lifetime       the copy dies with the component; two screens
                     showing the same list hold two divergent arrays
    - refetch policy on focus? on reconnect? on an interval?

  A query library is not a convenience. It is the admission that
  server data is a CACHE, and caches have a known set of problems
  you should not be re-deriving in each component.

  THE PLACEMENT DECISION TREE. Run it for EVERY new piece of state.
  Stop at the first yes.

    Does another user's action change this value?
      YES -> SERVER CACHE. Query library. Not useState.
      |
    Must a refresh or a pasted link preserve it?
      YES -> URL. Search params. Not useState.
      |
    Can it be computed from state you already have?
      YES -> DERIVE IT IN RENDER. No useState, no useEffect.
      |
    Does exactly one component read AND write it?
      YES -> useState right there. Colocate. Done.
      |
    Do two or more components need it?
      YES -> lift to their LOWEST common ancestor.
             Ancestor 4+ levels up AND the value changes rarely
               -> context.
             Changes on every keystroke
               -> do NOT use context. Restructure (Part 3), or use
                  a store with selectors.

  NOTICE WHAT IS MISSING: no branch reaches "global store" by
  default. In a typical CRUD app this tree routes roughly 70% of
  values to the server cache, 15% to the URL, 10% to local useState,
  and leaves a handful genuinely global.

Part 2 — Derived State: Compute, Never Store

  THE BUG:

    function Search({ items }) {
      const [query, setQuery] = useState('');
      const [filtered, setFiltered] = useState(items);   // COPY #2

      useEffect(() => {
        setFiltered(items.filter(i => i.name.includes(query)));
      }, [items, query]);

      return <List rows={filtered} />;
    }

  WHAT ACTUALLY HAPPENS WHEN THE USER TYPES "a":

    render 1   query='a'   filtered=[ALL ITEMS]
    commit + PAINT                     <- the user sees the
                                          UNFILTERED list for a frame
    effect     setFiltered([matches])  <- schedules another render
    render 2   query='a'   filtered=[matches]
    commit + PAINT                     <- finally correct

  TWO RENDERS AND TWO PAINTS PER KEYSTROKE, plus a visible flash of
  stale content. useEffect runs AFTER the browser paints, so this is
  not theoretical — on a 400-row list you can photograph it.

  AND IT IS NOT MERELY SLOW, IT IS INCORRECT. filtered is a SECOND
  SOURCE OF TRUTH. Any path that writes items without going through
  this effect leaves filtered describing rows that no longer exist.
  Delete a row optimistically and the list keeps showing it until
  the effect catches up. Add a second effect that also writes
  filtered and the two race, ordered by hook position rather than by
  anything you intended.

  THE FIX IS DELETING CODE:

    function Search({ items }) {
      const [query, setQuery] = useState('');
      const filtered = items.filter(i => i.name.includes(query));
      return <List rows={filtered} />;
    }

  One render. One paint. One source of truth. Impossible to desync
  because there is nothing to sync.

  "BUT FILTERING ON EVERY RENDER IS SLOW." Measure before believing
  it. Filtering 1,000 objects on a substring is ~0.02-0.05ms; your
  frame budget is 16.7ms. useMemo starts paying when the computation
  is genuinely expensive (sorting 10k+ rows, parsing, building a
  tree) or when the RESULT is a prop of a memo() child, where a new
  array identity would defeat the memo. Below that, useMemo costs a
  dependency comparison plus a cache slot and buys nothing.
ApproachRenders per input changeCan desync?Use when
Compute in the render body1No — there is no copyAlways, by default
useMemo around the computation1NoMeasured cost, or feeding a memo() child
useState + useEffect sync2, with a stale painted frame betweenYesNever, for derivation

  THE OTHER HALF OF THE SAME MISTAKE — PROPS COPIED INTO STATE:

    function Profile({ user }) {
      const [name, setName] = useState(user.name);  // initializer
      ...                                           // runs ONCE
    }

  useState's argument is an INITIAL value. React reads it on the
  first render of that component INSTANCE and ignores it forever
  after. Pass a different user and the field still shows the old
  name. People find this, then "fix" it with the effect above, which
  reintroduces the flash and the desync.

  THERE ARE ONLY THREE CORRECT ANSWERS:

  A. IT IS DERIVED -> compute it, do not store it.

  B. IT IS A DRAFT the user edits, and it must reset when the record
     changes -> give the component a key:

       <ProfileForm key={user.id} user={user} />

     Changing key makes React treat it as a DIFFERENT element type
     position: the old fiber is unmounted and a new one mounted, so
     ALL internal state resets — including scroll and focus inside
     it. That is exactly what you want when the identity changes.

  C. IT MUST RESET on something that is NOT identity -> adjust
     during render, the escape hatch React documents:

       const [prevId, setPrevId] = useState(user.id);
       if (user.id !== prevId) {
         setPrevId(user.id);
         setName(user.name);
       }

     Calling setState during render of the SAME component is legal
     and cheap: React throws away the in-progress output and re-runs
     the function body BEFORE committing. No extra paint, no effect
     round trip. Calling setState during render of a DIFFERENT
     component is an error and React will warn.

  PREFER B. It is one attribute and it cannot rot. Reach for C only
  when a remount would discard something you must keep.

Part 3 — Lifting, Colocation, and What a High Ancestor Costs

  TWO FORCES PULL IN OPPOSITE DIRECTIONS.

  COLOCATE (push state down): re-renders stay small, the component
  stays portable, deleting the feature deletes its state with it.
  LIFT (pull state up): the moment TWO components need the same
  truth, one owner is mandatory. "Keep two states in sync" has no
  correct implementation — only races that lose to whichever effect
  runs last.

  THE RULE: lift to the LOWEST common ancestor of everyone who reads
  or writes it. Lowest. Not the page, not the app.

  WHY "LOWEST" IS NOT PEDANTRY — THE COST IS MEASURABLE:

    App                     <- query lives here: EVERY keystroke
     ├─ Header                 re-renders Header, Sidebar, Footer
     ├─ Sidebar                and all 400 rows of Table
     ├─ Search  (writes)
     ├─ Table   (reads, 400 rows)
     └─ Footer

  setState marks the OWNING fiber dirty and React re-renders it and
  its subtree. Bailouts help only where props and element identity
  are unchanged — and every child of a re-rendering parent gets
  freshly created elements, so the bailout you are hoping for
  usually does not happen without memo().

  ROUGH NUMBERS FROM A REAL PROFILE (400-row table, mid-range
  laptop, development build):

    query at App    ~180 components render per keystroke   ~24ms
    query at Panel  ~410 components render per keystroke   ~31ms
                    (Panel wraps Search AND Table — correct, but
                     Table is the expensive part)
    query at Panel,
    Table memo'd    ~12 components render per keystroke    ~2ms

  16.7ms is the 60fps budget. At 24-31ms per keystroke a fast typist
  is permanently behind, and the input feels "sticky" — the classic
  complaint that gets misdiagnosed as "React is slow".
SymptomWhat it meansMove

A prop threaded through 4+ components untouchedComposition problem, not a context problemPass JSX as children (below)

  WHEN PROP DRILLING IS ACTUALLY FINE:

    Two or three levels, one or two props — FINE. It is explicit,
    greppable, type-checked, and it survives being moved. Context
    would add an indirection and a re-render surface for nothing.

    Five levels, six props, and intermediate components that only
    forward — NOT a context problem. It is a COMPOSITION problem,
    and context would only hide it.

  THE COMPOSITION FIX PEOPLE FORGET — pass the element, not data:

    // Before: Layout must know about user, and forwards it twice.
    function Layout({ user }) {
      return <Main><Sidebar user={user} /></Main>;
    }

    // After: Layout knows nothing. The owner of user renders it.
    function Layout({ sidebar, children }) {
      return <Main>{sidebar}{children}</Main>;
    }
    <Layout sidebar={<Sidebar user={user} />}>...</Layout>

  This also has a rendering benefit: children passed as props are
  created by the PARENT. When Layout re-renders for its own reasons,
  the children element objects are the same references it received,
  so React bails out of re-rendering that subtree without memo().
  Composition is the cheapest performance tool in React and nobody
  reaches for it first.

  THE COLOCATION REFACTOR, START TO FINISH:

    BEFORE: Dashboard holds 11 useState hooks — modal open, sort
    column, hovered row id, toast queue, sidebar collapsed, filter
    text, page number, selected ids, edit draft, tooltip anchor,
    scroll target. Every one of them re-renders the whole dashboard.
    Hovering a row re-rendered 380 components; the flame chart was a
    solid wall.

    THE MOVES, IN ORDER:
      hoveredRowId    -> into Row itself (or drop it: CSS :hover)
      tooltipAnchor   -> into the Tooltip trigger
      modalOpen       -> into the component that opens the modal
      sidebarCollapsed-> into Sidebar
      editDraft       -> into EditForm, keyed by record id
      filterText,
      sortColumn,
      pageNumber      -> into the URL (Part 4) — they were the ones
                         users kept asking to be able to share
      selectedIds     -> stays lifted; the toolbar and the table
                         both need it. This one was CORRECT.

    AFTER: Dashboard holds 1 useState. Hover re-renders 1 component.
    No memo() was added. The fix was placement, not optimization —
    which is the general lesson: reach for placement before memo,
    because memo is a patch over state that lives too high.

Part 4 — The URL Is State

  A FILTER IN useState IS A BUG REPORT WAITING TO HAPPEN:

    "I filtered to open tickets, hit refresh, lost it."
    "I sent Priya the link and she saw an unfiltered list."
    "I pressed back and it left the page instead of clearing the
     filter."
    "Two tabs, and the second one forgot everything."

  All four are one mistake: state that describes WHAT THE USER IS
  LOOKING AT was stored somewhere the browser cannot see. The URL is
  a state container that already gives you, free:

    - shareable      copy-paste reproduces the exact view
    - refresh-proof  survives F5, crash recovery, restore-tabs
    - back-button    history is state history, correctly ordered
    - server-usable  SSR/RSC can read searchParams and render the
                     right thing on the FIRST byte, no client
                     round-trip, no loading spinner
    - free undo      the back stack IS the undo stack

  THE SHAPE (React Router; Next's useSearchParams is close):

    const [params, setParams] = useSearchParams();
    const status = params.get('status') ?? 'all';   // DERIVED
    const page   = Number(params.get('page') ?? 1);

    function setStatus(next) {
      setParams(prev => {
        const p = new URLSearchParams(prev);
        next === 'all' ? p.delete('status') : p.set('status', next);
        p.delete('page');          // changing a filter resets paging
        return p;
      }, { replace: false });
    }

  NOTE THE THREE THINGS THAT ARE EASY TO GET WRONG:

  1. DERIVE, DO NOT MIRROR. Do not copy params into useState. The
     URL is the source of truth; reading it is a cheap synchronous
     call. Mirroring re-creates the Part 2 desync, and now the back
     button changes the URL while the mirror keeps the old value.

  2. DELETE DEFAULTS. Writing ?status=all bloats every link and
     makes two URLs that mean the same view. Absent = default.

  3. push VS replace IS A REAL DECISION.
       push    — a new history entry. Back returns to the previous
                 view. Correct for a filter the user chose.
       replace — overwrites. Correct for keystroke-level updates.
     Push on every keystroke of a search box and typing "invoice"
     puts SEVEN entries in history; the user presses back seven
     times to escape the page. Debounce ~300ms AND use replace
     while typing; push once when the value settles.
ValueURL?Why
Filters, sort, page, tab, selected record idYesDefines the view; must be shareable and refresh-proof
Search queryYes, debounced + replaceShareable, but one history entry per keystroke is hostile
Modal open/closedUsually yesBack should close it; deep links to "the edit dialog" work
Multi-step wizard stepYesBack means "previous step", which is what users expect
Half-typed form draftNoNot a view; it is user data, and URLs get logged
Anything secret (tokens, emails, ids you don't expose)NoURLs land in server logs, referrers, analytics and screenshots
Hover index, focus ring, dropdown openNoTransient; history entries would be noise
Large state (a whole draft object)NoPractical URL ceiling is ~2,000 chars in older browsers/proxies
Why this matters more in 2024+ than it did in 2018. With server components and server-side rendering, searchParams is available before any JavaScript runs — a filtered list can be rendered on the server and stream to the browser with no client fetch and no spinner. State kept in useState is invisible to the server by construction, so the same page must always render empty first, hydrate, then fetch. Putting view state in the URL is what makes the server rendering path possible at all. See Server Components.

Part 5 — Controlled, Uncontrolled, and the Hybrid Every Library Ships

  THIS IS NOT A FORMS TOPIC. It is the question "who owns this
  component's state" asked about ANY component: a tab set, an
  accordion, a date picker, a tree view, a modal.

  UNCONTROLLED — the component owns its state; you seed it and read
  it back through a callback:

    <Tabs defaultTab="billing" onTabChange={logIt} />

    Caller writes nothing. Cannot force a tab from outside.
    Fewest lines, fewest bugs, no re-render of the caller.

  CONTROLLED — the caller owns the state; the component is a pure
  function of props plus an event:

    <Tabs tab={tab} onTabChange={setTab} />

    Caller can force, reset, persist, sync to URL, validate before
    allowing the change. Costs a state hook and a re-render of the
    owner on every change.

  THE MECHANISM UNDER "why can't I just set value?":

    <input value={query} />      with no onChange

  React sets the DOM property on every commit. You type, the DOM
  value changes, React re-renders with the SAME query and writes the
  old value back. The character vanishes. It is not a lock — it is
  React continuously reasserting its value. React warns because the
  only two coherent options are value+onChange, or defaultValue.

  AND THE ONE THAT BURNS EVERYONE:

    const [name, setName] = useState();          // undefined!
    <input value={name} onChange={...} />

  value={undefined} means "uncontrolled" to React. The first
  keystroke makes it a string, and React logs "A component is
  changing an uncontrolled input to be controlled." Initialize to ''
  — or write value={name ?? ''}. Never let value be null/undefined.

  THE HYBRID, WHICH IS WHAT MUI, RADIX, HEADLESS UI AND REACT-SELECT
  ALL ACTUALLY DO. Support BOTH in one component:

    function useControllable({ value, defaultValue, onChange }) {
      const isControlled = value !== undefined;
      const [internal, setInternal] = useState(defaultValue);

      const current = isControlled ? value : internal;

      const set = useCallback((next) => {
        if (!isControlled) setInternal(next);   // uncontrolled:
                                                // keep it internally
        onChange?.(next);                       // ALWAYS notify
      }, [isControlled, onChange]);

      return [current, set];
    }

  THREE RULES THIS ENCODES, ALL OF WHICH GET BROKEN IN REVIEW:

  1. THE PROBE IS undefined, NOT falsy. value={0} and value=""
     are legitimate controlled values. if (value) is a bug.
  2. onChange FIRES IN BOTH MODES. An uncontrolled consumer still
     wants to know. Skipping it in uncontrolled mode is the most
     common bug in hand-rolled versions.
  3. THE MODE IS FIXED FOR THE COMPONENT'S LIFE. Flipping between
     them mid-life makes state appear or vanish; assert it in dev.

Design the uncontrolled path first. Ship defaultValue + onChange, then add the controlled prop when a consumer needs it — that ordering gives you the hybrid for free. The reverse (controlled-only) forces every consumer to hold state they may not want and is the reason so many component libraries feel heavy for simple cases.

Part 6 — Normalising Relational State

  THE SHAPE THE SERVER SENDS IS NOT THE SHAPE YOU SHOULD STORE.

    posts = [
      { id: 'p1', title: '...', comments: [
          { id: 'c1', text: '...', author: { id: 'u1', ... } },
          ...
      ]},
      ...
    ]

  UPDATING ONE COMMENT'S TEXT IN THIS SHAPE:

    setPosts(posts => posts.map(p =>
      p.id !== postId ? p : { ...p, comments: p.comments.map(c =>
        c.id !== commentId ? c : { ...c, text: next }
      )}
    ));

  WHAT THAT ACTUALLY COSTS, at 50 posts x 10 comments:

    - .map over 50 posts, and for the matching post .map over its
      10 comments: O(posts + comments) SCANNED for a single edit.
      Three levels deep it is O(n*m*k) and the code becomes
      genuinely unreadable.
    - IDENTITY CHURN: map ALWAYS returns a new outer array. So
      posts is a new reference, and the one edited post is a new
      object with a new comments array. Every memo() PostCard
      comparing props by reference sees a new array prop and
      re-renders — all 50 of them — for a one-character edit.
    - DUPLICATION: user u1 appears inside 40 comments. Rename them
      and you must find and rewrite 40 copies, or the UI shows two
      different names for one person on the same screen.

  NORMALISED — flat maps keyed by id, relationships by id:

    {
      posts:    { byId: { p1: {id:'p1', title, commentIds:['c1']} },
                  allIds: ['p1'] },
      comments: { byId: { c1: {id:'c1', text, authorId:'u1',
                               postId:'p1'} } },
      users:    { byId: { u1: {id:'u1', name:'Priya'} } }
    }

    THE SAME EDIT:

      setComments(cs => ({ ...cs,
        byId: { ...cs.byId,
                [commentId]: { ...cs.byId[commentId], text: next } }
      }));

    O(1) lookup. ONE new comment object. posts is untouched, so
    every PostCard bails out. A user rename is one write, and every
    place that renders users.byId[id].name updates at once, because
    there is only one copy.

  READING IT BACK IS A DERIVATION (Part 2), not storage:

    const post = posts.byId[postId];
    const comments = post.commentIds.map(id => comments.byId[id]);

  THE ORDER LIVES IN THE ARRAY OF IDS, THE DATA LIVES IN THE MAP.
  That separation is the whole trick: reordering touches only
  allIds; editing touches only byId; neither disturbs the other.

Do not normalise everything. Normalisation buys O(1) updates and stable identity; it costs a lookup step on every read and more code. It pays when the same entity appears in more than one place, when the list is long and edited in place, or when nesting is 3+ deep. A 20-row read-only table nested two levels does not need it. And if the data is server cache, your query library already keys entries by query — normalise inside the cache only when you have entity-level updates that must be reflected across queries.

Interview Questions

Beginner: Where should a piece of state live?

In the lowest component that contains every reader and every writer — their lowest common ancestor. If exactly one component uses it, it lives there and nowhere else. That is colocation, and it is the default because it keeps re-renders small, keeps the component portable, and makes deleting the feature delete its state too.

Lifting is not a preference, it is forced: the moment two components need the same truth, one of them has to own it, because keeping two copies in sync has no correct implementation. But lift only as far as the common ancestor. Lifting to the root because it is convenient means every change re-renders the whole tree.

The step before that question, though, is what kind of state it is. If the value comes from the server, it is a cache and belongs in a query library. If a refresh or a shared link must preserve it, it belongs in the URL. If it can be computed from state you already have, it should not be stored at all.

Beginner: What is derived state and why is storing it a bug?

Derived state is any value computable from state you already hold: a filtered list, a total, an isValid flag, the object found by selectedId. It should be a plain const in the render body, recomputed each render.

Storing it in a second useState and syncing with an effect breaks in two ways. First, timing: effects run after the browser paints, so React renders and paints with the stale derived value, then the effect sets state and a second render and paint follow. The user sees one frame of wrong content per change, and you pay two renders instead of one.

Second, and worse, correctness: you now have two sources of truth. Any code path that changes the source without going through that effect leaves the copy describing something that no longer exists. Deriving in render cannot desync because there is no copy to desync.

If the computation is genuinely expensive, useMemo is the answer — still one source of truth, still one render. An effect is never the answer for derivation.

Mid: When does state belong in the URL rather than in useState?

When it describes what the user is looking at rather than what they are doing. Filters, sort order, page number, active tab, the selected record, the current wizard step. The test is a sentence: "if I send you this link, should you see what I see?" If yes, it is URL state.

You get four things for free that are painful to build otherwise: shareable links, refresh and crash survival, a correct back button (history is your state history), and server readability — searchParams is available before any JavaScript runs, so an SSR or RSC page can render the filtered result in the first byte instead of rendering empty, hydrating and then fetching.

The limits are real: keep it small (assume a ~2,000-character practical ceiling), keep it non-sensitive, and do not put transient UI like hover index or dropdown-open in there — those would fill history with noise.

Mid: Explain controlled vs uncontrolled components and how a library supports both.

Uncontrolled means the component owns its own state; you seed it with defaultValue and observe it with onChange. Controlled means the caller owns the state; the component renders value and reports intent through onChange, and the caller decides whether to accept it. Controlled buys the ability to force, reset, validate before accepting, or mirror to the URL; it costs a state hook and a re-render of the owner on every change.

A library supports both with one probe: const isControlled = value !== undefined. It keeps an internal useState(defaultValue), reads isControlled ? value : internal, and on change writes internal state only when uncontrolled while always calling onChange.

Three details separate a working implementation from a broken one. The probe must be !== undefined, not truthiness, because 0 and '' are legitimate controlled values. onChange must fire in both modes — omitting it in uncontrolled mode is the classic hand-rolled bug. And the mode must be fixed for the component's lifetime; flipping makes state appear or vanish, which is precisely what React's "changing an uncontrolled input to be controlled" warning is about.

Design the uncontrolled path first and add the controlled prop when a consumer needs it. Controlled-only APIs force every consumer to hold state they may not want.

Senior: A dashboard lags while typing in its search box. Walk through your diagnosis.

I profile before I theorise. The React Profiler on a keystroke tells me how many components rendered and where the time went. The usual finding is that the search state lives at the page or app level, so a keystroke marks that fiber dirty and React re-renders the entire subtree — header, sidebar, and a table with hundreds of rows. On a mid-range laptop that is comfortably past the 16.7ms frame budget, which is why the input feels sticky.

The first fix is placement, not memoization. If only the search box and the results read the query, it belongs on their lowest common ancestor, not the page. That one move usually cuts the render count by an order of magnitude and costs nothing at runtime. If the query is genuinely also a filter that should be shareable, it goes in the URL with a debounce and replace, which also gets it out of the hot render path.

The second fix is composition. Children passed as element props are created by the outer parent, so their references are unchanged when the intermediate component re-renders and React bails out of that subtree without any memo call. Restructuring a layout to take a children slot is often a bigger win than a page of memoization.

Only then do I reach for memo/useMemo, and only on a component I have measured — typically the expensive table rows. Memo has a real cost: a props comparison on every render, and it goes stale the moment someone adds a prop that changes identity every render, so it needs useCallback discipline around it to keep working.

Recommendation: placement, then composition, then measured memoization — in that order. Memo applied first hides the real problem and leaves you maintaining it forever. If after all three the list is still slow, the honest answer is that the list is too long to render at all, and the fix is virtualization, not state architecture.

Senior: When do you normalise state, and when is a global store actually justified?

Normalisation — flat byId maps plus arrays of ids — pays when the same entity appears in more than one place, when lists are long and edited in place, or when nesting reaches three levels. The reason is not elegance, it is two measurable costs of the nested shape: updates scan and rebuild every parent container on the path, and every rebuild creates new object identities, so every memoized sibling re-renders for a one-field edit. Editing one comment in a 50-post tree creates about 53 new references and re-renders all 50 post cards; normalised, it creates three and re-renders one.

The costs are equally real: reads need a lookup or a selector, order has to be maintained separately in the id array, and the shape no longer matches what the API returns, so you own a transform. A short read-only list nested two levels should stay as it is.

SignalVerdict
Same entity rendered in several branchesNormalise
Long list edited in place, memoized rowsNormalise
Short, read-only, shallowLeave nested
Data is server cache with per-query entriesLet the query library own it; normalise only for cross-query entity updates

A global store is a separate question, and most teams answer it too early. If server data is in a query library and view state is in the URL, what remains is usually a theme, an auth object and a toast queue — which useState plus one or two contexts handles. A store earns its place when you have cross-cutting client state with real update logic, when you need subscriptions with selectors so a hot value does not re-render every consumer the way context does, or when you need state readable outside React.

Recommendation: normalise on the signals above rather than by default, and default to no store. Adopt one when you can name the specific thing context cannot do — usually selector-based subscription for high-frequency state — rather than because the app "got big".

2 (easy): The user picks a different customer from a list, but the form keeps showing the previous one's email. Why, and what are the two fixes? 
function CustomerForm({ customer }) {
  const [email, setEmail] = useState(customer.email);
  return <input value={email}
                onChange={e => setEmail(e.target.value)} />;
}
Solution

The argument to useState is an INITIAL value. React reads it once, when this component instance mounts, and stores it in the fiber's hook slot. Every later render reads the stored value and ignores the argument entirely. Selecting a different customer changes the prop but React re-renders the SAME fiber, so the hook slot — and the input — keeps the old email.

Fix A, and the one to prefer, is to tell React this is a different thing:

<CustomerForm key={customer.id} customer={customer} />

A changed key makes reconciliation unmount the old fiber and mount a new one, so every hook inside resets. Fix B, when a remount would throw away something you need to keep, is to adjust during render:

const [prevId, setPrevId] = useState(customer.id);
if (customer.id !== prevId) {
  setPrevId(customer.id);
  setEmail(customer.email);
}

Setting state during the render of the same component is supported: React discards the in-progress output and re-runs the body before committing, so nothing extra is painted. What you must not do is reach for useEffect — that reintroduces the stale painted frame from Exercise 1.

3 (medium): Users complain that refreshing loses their filter and that shared links "don't work". Fix it, and say what is wrong with the naive fix. 
function Tickets() {
  const [status, setStatus] = useState('all');
  const [page, setPage] = useState(1);
  const tickets = useTickets({ status, page });
  ...
}
Solution 
function Tickets() {
  const [params, setParams] = useSearchParams();
  const status = params.get('status') ?? 'all';     // DERIVED
  const page   = Number(params.get('page') ?? 1);

  function setStatus(next) {
    setParams(prev => {
      const p = new URLSearchParams(prev);
      next === 'all' ? p.delete('status') : p.set('status', next);
      p.delete('page');           // a new filter resets paging
      return p;
    });
  }
  const tickets = useTickets({ status, page });
}

The naive fix is to keep both — useState plus an effect that writes the URL, and another that reads it back. That is the Part 2 mistake wearing a hat. The browser can change the URL without telling your setter: press Back and the URL reverts while the mirrored state keeps the new value, so the list and the address bar disagree until something else re-renders. Read from the params; do not copy them.

DetailWhy it matters
p.delete('page') on filter changeOtherwise you land on page 7 of a 2-page result and see an empty list
Deleting the default instead of writing status=allKeeps links short and gives one canonical URL per view

Functional setParamsPreserves unrelated params other features own

The bonus is server-side: searchParams is readable before hydration, so this page can be rendered filtered on the server instead of rendering empty and fetching after mount.

4 (medium): This Rating works when uncontrolled but silently ignores the parent in controlled mode, and has a second bug. Find both. 
function Rating({ value, defaultValue = 0, onChange }) {
  const [internal, setInternal] = useState(defaultValue);
  const current = value ? value : internal;

  function pick(n) {
    setInternal(n);
    if (value) onChange?.(n);
  }
  ...
}
Solution 
function Rating({ value, defaultValue = 0, onChange }) {
  const isControlled = value !== undefined;
  const [internal, setInternal] = useState(defaultValue);
  const current = isControlled ? value : internal;

  function pick(n) {
    if (!isControlled) setInternal(n);   // only when we own it
    onChange?.(n);                       // ALWAYS notify
  }
  ...
}

Bug 1 — a truthiness probe. value ? value : internal means a controlled value={0} — a perfectly valid "no rating" — is falsy, so the component silently falls back to its internal state. The parent sets 0, the component keeps showing 3, and it looks like a React bug rather than a bad conditional. The probe for "did the caller pass this prop" is always !== undefined.

Bug 2 — the notification is backwards. onChange fires only in controlled mode, so a consumer who passed defaultValue and onChange — the whole point of the hybrid API — never hears about a click. The rule is the mirror image of what is written: the internal write is conditional, the callback is not.

There is also a latent third problem: in controlled mode the original still calls setInternal(n), so the ignored internal state drifts. If a consumer ever removes the value prop, the component snaps to a stale number. Writing internal state only when you own it removes that class of surprise.

5 (hard): A 50-post feed with ~10 comments each. Editing one comment's text re-renders all 50 memo()-wrapped PostCards. Explain precisely why, then restructure. 
setPosts(posts => posts.map(p =>
  p.id !== postId ? p : { ...p, comments: p.comments.map(c =>
    c.id !== commentId ? c : { ...c, text: next })}));
Solution

Why every card re-renders. memo compares props by reference. The outer .map always returns a NEW array, so posts is a new reference. The parent that renders the feed re-renders, and although 49 posts are the same object references, the parent is now creating new element objects for all of them with a new posts-derived prop somewhere in the chain — and the edited post is a new object with a new comments array. Anything reading the list identity, a computed commentCount, or an inline callback closing over posts gets a fresh identity too, and memo's shallow compare fails.

The update also SCANS: 50 posts, then 10 comments, to change one string. Nested one level deeper it is O(n·m·k), and the update expression stops being reviewable.

// state

setComments(cs => ({ ...cs,

The mechanism worth naming in an interview: immutable updates propagate new identities upward through every container on the path. That is exactly what React needs to detect a change — and exactly what destroys memoization when the path is long. 🎯 Key Takeaways

  • There are five kinds of state — server cache, client UI, form draft, URL, derived — and "where does it live" is answered by which one it is.
  • Server data is a cache, not state; putting it in useState makes staleness, invalidation, dedup and refetch your hand-written problem.
  • Derived state has no storage — compute it in the render body, never sync it with an effect.
  • An effect that derives state paints a stale frame first, because effects run after the browser paints: two renders and one visibly wrong frame per change.
  • Two states kept in sync is always a bug — there is no correct implementation, only races.
  • useState(props.x) reads the prop once; the initializer never runs again for that component instance.
  • A changed key remounts and resets all state in the subtree — the cleanest way to reset a draft when the record changes.
  • Setting state during render of the same component is legal: React re-runs the body before committing, with no extra paint.
  • Lift to the lowest common ancestor, not the root — an owner one level too high re-renders everything below it on every change.
  • Prop drilling two or three levels is fine; five levels of forwarding is a composition problem, and context would only hide it.
  • Children passed as element props keep their identity, so composition buys subtree bailouts without a single memo call.
  • Anything a shared link or a refresh must preserve belongs in the URL — and never mirror search params into useState.
  • Push per keystroke ruins the back button; debounce and replace while typing, push when the value settles.
  • Controlled vs uncontrolled is a general component API question, not a forms one; probe with value !== undefined and always fire onChange.
  • Nested state makes every edit rebuild its parents, creating new identities that defeat memo across all siblings.
  • Fix placement before reaching for memo — memoization is a patch over state that lives too high, and it rots at the next prop.
