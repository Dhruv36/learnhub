Lists, Keys & Conditional Rendering Foundations

What you'll master: what a key actually is — not a React rule but reconciliation identity, and the mechanism by which the wrong one attaches the right state to the wrong row silently; the proof that index keys corrupt state, where typing a meal choice for one guest and adding another moves the text to a different person; keys as a deliberate demolition order — one attribute that replaces a minefield of prop-syncing effects; the reconciliation rules beyond keys, including the one that warns you about nothing — flipping a wrapper from div to section remounts every stateful child beneath it; the measured cost of getting keys right (~1,000 re-renders and 48 ms versus ~0 and 6 ms on a 1,000-row re-sort); and why unmount-versus-hide is a real trade-off rather than a style preference. Prerequisites: State & useState — you need to care where state lives before keys make sense — and JS Arrays.

Part 1 — Lists Are Just Arrays of Elements

const USERS = [
  { id: "u1", name: "Ada",   role: "admin" },
  { id: "u2", name: "Linus", role: "dev" },
  { id: "u3", name: "Grace", role: "dev" },
];

function UserList() {
  return (
    <ul>
      {USERS.map(u => <UserRow key={u.id} user={u} />)}   {/* JSX renders arrays */}
    </ul>
  );
}

// Filter, sort and slice are DERIVED VIEWS computed in render — never
// stored in state (see the State lesson):
{USERS.filter(u => u.role === "dev")
      .toSorted((a, b) => a.name.localeCompare(b.name))
      .map(u => <UserRow key={u.id} user={u} />)}

There is no list primitive in React. JSX renders arrays of elements, so everything from Array Methods is the list API. The single new requirement is key — and note toSorted rather than sort, because sort would mutate the source array in place.

Part 2 — What Keys Are Actually For

When a list re-renders, React holds the old array of elements and the new one, and has to answer one question: which old item corresponds to which new item? That answer decides which fibers — and therefore which state, DOM nodes and effects — survive. Without keys, React matches by position. Keys replace position with identity:

  Render 1:  [A, B, C]          Render 2:  [X, A, B, C]   (X prepended)

  WITHOUT KEYS — positional matching:

    old[0] A  ↔  new[0] X   "A became X": keep A's fiber, DOM and state,
                             render X's props into it            ⚠️
    old[1] B  ↔  new[1] A   B's fiber now renders A              ⚠️
    old[2] C  ↔  new[2] B   C's fiber now renders B              ⚠️
    (none)    ↔  new[3] C   mount a NEW C with empty state       ⚠️

    Four rows re-rendered, and every row's state is attached to the
    wrong data.

  WITH STABLE KEYS:

    "a"↔"a", "b"↔"b", "c"↔"c"   matched regardless of position ->
                                 fibers untouched, no re-render
    "x"                          new -> one mount

    Correct AND minimal.
🔑 The one sentence to keep: a key tells React "this child is the same logical entity as the child with this key last render". State follows the key, not the data you passed alongside it. Get keys wrong and React's bookkeeping is internally consistent and externally wrong — which is why nothing errors.

Part 3 — Why Index-as-Key Corrupts State

function Guests() {
  const [guests, setGuests] = useState(["Ada", "Linus"]);
  return (
    <>
      <button onClick={() => setGuests(g => ["Grace", ...g])}>Add to top</button>
      {guests.map((name, i) => (
        <label key={i}>                                   {/* ❌ index */}
          {name}: <input placeholder="meal choice" />      {/* DOM state */}
        </label>
      ))}
    </>
  );
}

  REPRODUCE IT IN THREE STEPS:

  1. Type "vegan" into Ada's input.        (row key=0)
  2. Click "Add to top". Grace is now index 0.
  3. React matches new key=0 (Grace) to old key=0 (Ada's fiber and its
     DOM node) — so GRACE'S ROW NOW SHOWS "vegan", and Ada's row shows
     whatever Linus had typed.

  The data moved down. The state stayed at its position.

  WHAT IS AFFECTED — anything living on the fiber or its DOM:
    uncontrolled input values          checkbox and radio state
    component state (expanded rows)    scroll position within a row
    focus                              CSS transitions and animations
    effect cleanup order               third-party widgets mounted in a row

  NOTHING WARNS. Every key is present and unique, so the console is
  clean and the render is "successful".
Key choiceVerdictWhy
Entity id — u.idBestStable, unique, survives reorder, insert and delete
A stable natural key — email, slugFineSame properties, if genuinely unique and immutable. An email that can be edited is neither
Generated at creation time and stored on the itemFinecrypto.randomUUID() when the item is created is stable from then on — this is the answer for client-side items with no server id yet
Array indexLast resortOnly when the list never reorders, filters or inserts, and rows hold no state
Math.random() or a UUID in renderNeverA new key every render means unmount plus remount of every row, on every render — maximum work and total state loss

Part 4 — Keys as a Feature: Intentional Resets

Keys are not only for lists. Changing the key on any element tells React "this is a different entity — discard the old one". That is the idiomatic way to reset state:

// 1. Reset a whole form when switching records
<ProfileForm key={selectedUserId} userId={selectedUserId} />
//   New id -> new key -> old form unmounts with all its state, fresh
//   one mounts. This single attribute replaces the "sync props into
//   state" effects that would otherwise be needed per field — and
//   unlike an effect, there is no intermediate render showing the
//   previous record's data.

// 2. Replay an animation or an intro
<Confetti key={celebrationCount} />

// 3. Recover a crashed or poisoned third-party widget
<ChartWidget key={retryToken} data={data} />
🔑 The same prop, in both directions. The junior answer is "keys silence the console warning". The senior answer is that keys are reconciliation identity: inside a list a stable key preserves state across reorders, and outside a list a changed key is a deliberate demolition order. Being able to state both, and to pick which one a situation needs, is the whole topic.

Part 5 — Reconciliation Rules Beyond Keys

// RULE 1 — same position, same type: same fiber, state survives
{isSpecial ? <Panel tone="gold" /> : <Panel tone="gray" />}
//   ONE Panel. Props update, state kept.

// RULE 2 — type changes: old subtree unmounted, state destroyed
{isEditor ? <RichEditor /> : <PlainEditor />}

// RULE 3 — a HOST type change resets everything below it
{fancy ? <section><Form /></section> : <div><Form /></div>}
//   Form remounts on toggle. The Form element is identical; its
//   PARENT's type changed, and reconciliation stops at the mismatch.

// RULE 4 — conditional siblings do not shift their neighbours
{showBanner && <Banner />}   {/* false leaves a null slot */}
<Content />                   {/* so Content keeps its position */}

// RULE 5 — unmount vs hide is a real decision
{open && <HeavyPanel />}                        // frees memory, LOSES state
<div style={{ display: open ? "" : "none" }}>   // keeps state, pays memory
  <HeavyPanel />
</div>
Rule 5 — chooseWhenCost
Unmount — {open && …}Cheap content, or content that should reset each time it opensState, scroll and focus are discarded; mount effects re-run, including any fetch
Hide — display: noneA half-filled form, a scrolled list, a playing video, anything expensive to rebuildThe DOM stays in memory and in the accessibility tree unless you also manage hidden/aria-hidden
VirtualizeThousands of rows where neither answer scalesA library and more complexity — see the Performance section

Part 6 — Production List Patterns

// 1. Empty, loading and error states are part of EVERY list.
//    Design them at the same time as the happy path, not after QA.
function Results({ items, status }) {
  if (status === "loading") return <SkeletonRows count={5} />;
  if (status === "error")   return <RetryPanel />;
  if (items.length === 0)   return <p>No matches — try clearing filters.</p>;
  return <ul>{items.map(i => <Row key={i.id} item={i} />)}</ul>;
}
//    Note the empty state distinguishes "no results for this filter"
//    from "nothing exists yet" — they need different words and
//    different actions.

// 2. Grouped lists need keys at EVERY level
{Object.entries(byCategory).map(([cat, items]) => (
  <section key={cat}>
    <h3>{cat}</h3>
    {items.map(i => <Row key={i.id} item={i} />)}
  </section>
))}

// 3. Keys are unique among SIBLINGS only. Reusing the same id in a
//    different list elsewhere on the page is fine.

// 4. key is consumed by React and never reaches the component. If the
//    child needs the id, pass it twice:
<Row key={item.id} id={item.id} item={item} />

Part 7 — What Reconciliation Actually Costs

Keys are usually taught as a correctness rule. They are also a performance one, and the difference is measurable — which is worth knowing before reaching for memoization:

  Re-sorting a 1,000-row table by clicking a column header:

    index-as-key    every row's props change, because row 0 is now a
                    different record. React re-renders all 1,000 and
                    patches every cell.
                    ~1,000 re-renders, ~48 ms

    stable id key   React matches each element to its previous instance
                    and MOVES the DOM nodes instead of rewriting them.
                    ~0 re-renders, ~6 ms

  Prepending one row to a 1,000-row list:

    index-as-key    every index shifts by one -> 1,000 patched rows
    stable id key   999 matched and untouched, 1 inserted

  The correct key is an 8x improvement here that costs nothing and
  requires no memoization. This is worth trying before useMemo.
ComparisonReact's decision
Different element type at the same positionDestroy the old subtree entirely and build a new one — all state below is lost
Same type, same keyKeep the fiber, update props, recurse into children
Same type, different keyA different element: unmount, remount, fresh state
No key in a listPosition becomes the identity — the index-as-key behaviour, whether you wrote it or not
⚠️ The type rule bites in a way keys never warn you about. Conditionally rendering <div><Form /></div> versus <section><Form /></section> swaps the parent type, so Form unmounts and remounts and everything the user typed is discarded. There is no console message, because nothing is wrong — you asked for a different element. Keep the wrapper type stable and vary its className instead.

Interview Questions

Beginner: Why does React need keys on list items?

Because on a re-render React has two arrays of elements — the previous one and the new one — and has to decide which old child corresponds to which new child. That decision determines what is updated, moved, mounted or unmounted.

Without keys it matches by position, which is only correct if nothing ever moves. Keys give each child a stable identity so the matching follows the data instead of the index, which preserves each item's component state and DOM across reorders, insertions and deletions.

It is worth saying that this is a correctness mechanism first and a performance one second. The performance gain is real — on a 1,000-row re-sort I measured about 48 ms with index keys against 6 ms with stable ones — but the reason to care is that with the wrong key the right state ends up attached to the wrong row.

Beginner: When is index-as-key acceptable?

Only when all three of these hold: the list never reorders, filters or gets items inserted anywhere but the end; the rows hold no state of any kind — no inputs, no selection, no animation, no focus; and there is genuinely no stable id available.

Static footer links qualify. A rendered list of a fixed set of tabs qualifies. Anything a user can interact with does not.

In practice I use the id anyway even when the index would be safe today, because the condition is about the future rather than the present — someone adds sorting six months later, and the resulting bug appears nowhere near their change.

Mid: A row's input text jumps to a different row after deleting an item. Diagnose it.

Index keys, or no keys at all. Deleting item i shifts every later item down one index; React matches by key, and the keys are positions, so each later fiber — including the uncontrolled input's DOM node, which is where the typed text lives — is reused for the next item's data.

The precise framing is that the state stayed at its position and the data moved past it. Nothing errors because every key is present and unique; React's bookkeeping is internally consistent and externally wrong.

The fix is entity-id keys, so each fiber follows its item wherever it moves.

The follow-up I would raise unprompted is whether that text should be in the DOM at all. An uncontrolled input's value lives on the DOM node, so it is destroyed by any legitimate remount too — a filter change, a key-based reset. If the value matters, it belongs in state keyed by the item's id, and then even a remount cannot lose it.

Mid: How do you reset a child's state from the parent, without a callback or an effect?

Change its key. A new key means "different entity", so React unmounts the old instance — discarding its state, its DOM and its effects — and mounts a fresh one.

The canonical use is <ProfileForm key={recordId} />, so switching records can never leak the previous record's half-edited fields.

What makes it better than the alternative is not brevity. The usual approach is an effect that watches recordId and calls setters to reset each field — and that runs after a render in which the new record was displayed with the old record's values, so there is a visible frame of wrong data, and it has to be maintained as fields are added. The key does it as part of reconciliation, so no such frame exists.

The cost worth stating: a remount re-runs mount effects, so any fetch inside the child fires again, and scroll position and focus are lost. It is the right tool for "this is now a different thing", and the wrong one for "this thing changed".

Senior: Explain React's list diffing and the trade-off it makes.

A general minimal tree-edit-distance diff is O(n³), which is unusable for a UI tree. React trades optimality for linear time by making three heuristic assumptions.

It compares level by level and never matches a node against one at a different depth. So moving a component to a different level of the tree is always an unmount plus a mount, however identical it is.

Different types mean different subtrees. If the type at a position changes, React does not attempt to diff the children — it discards the whole subtree. This is what makes a div-to-section wrapper flip remount everything below it.

Keys identify children within a level, letting React build a map and match in linear time rather than searching.

The bargain is explicit: you supply identity, React supplies O(n) reconciliation. When you do not supply it, React falls back to position — which is a guess that happens to be right only when the list never changes shape.

The practical consequence I would draw out is that the wrong key is not a missed optimisation but a correctness bug, because these heuristics decide fiber lifetime, and fiber lifetime decides state.

Senior: Two concatenated lists (pinned, then recent) can contain the same entity. How do you key them?

Raw ids would collide, and duplicate keys among siblings mean state bleeds between them and updates apply to the first match. So they need namespacing per section: key={`pin-${id}`} and key={`rec-${id}`}.

The consequence worth stating out loud is that an item moving from recent to pinned now changes key, so it unmounts and remounts and loses any row-local state. That is usually fine — but if the row holds something that must survive, like a playing audio element or an open menu, it is a visible bug.

When that matters, the better structure is to stop concatenating. Render one keyed list where section membership is a field on the data, and let CSS place items into columns or groups. The fiber then follows the item's id regardless of which group it visually belongs to, so moving between sections preserves everything.

That reframing generalises: whenever "moving an item between two rendered lists" needs to preserve state, the answer is that it should be one list whose grouping is data rather than structure.

🏋️ Graded Exercises

1 (easy): Render [{id, city, temp}] as a list showing "City: temp°", keyed correctly.
Solution 
<ul>
  {reports.map(r => (
    <li key={r.id}>{r.city}: {r.temp}°</li>
  ))}
</ul>

The key goes on the <li> — the element the map returns, because that is the element React is matching against its siblings. A key on something inside the li would do nothing for this list, and the warning would persist.

Why r.id even though a weather list looks static: the moment someone adds "sort by temperature" or a city filter, index keys silently corrupt anything stateful in the row. The id costs nothing now and removes a bug that would otherwise appear far from the change that caused it.

If the data genuinely has no id — say it arrives as [["Pune", 31], ["Oslo", 4]] — the city name is a reasonable natural key here, since it is unique within the list and does not change. That is the test for a natural key: unique among siblings, and immutable.

2 (easy): What is wrong here, and where does the key go? {items.map(i => <div><Row key={i.id} item={i} /></div>)}
Solution 
// The key is on the wrong element. React matches the children of the
// mapped array — the <div>s — and those have no keys, so matching is
// positional and the warning stays.

{items.map(i => (
  <div key={i.id}>
    <Row item={i} />
  </div>
))}

Why the misplaced key does nothing: Row is an only child of its div. It has no siblings to be distinguished from, so a key there is meaningless. Keys only matter among siblings in the same array.

The symptom that makes this confusing: the console warning says "Each child in a list should have a unique key" while the code visibly contains a key — so people add a second one, or assume the warning is wrong.

The question worth asking next is whether the wrapper div is needed at all. If it exists only to have something to key, delete it and key the Row: {items.map(i => <Row key={i.id} item={i} />)}. If it exists for layout, keep it — but remember from Part 5 that a wrapper is never neutral inside a flex or grid parent.

3 (medium): Render products sorted by price, in-stock only, with a "Nothing in stock" empty state — and no extra state variables.
Solution 
function InStock({ products }) {
  const visible = products
    .filter(p => p.stock > 0)
    .toSorted((a, b) => a.price - b.price);        // derived, not state

  if (visible.length === 0) {
    return <p>Nothing in stock right now.</p>;
  }

  return (
    <ul>
      {visible.map(p => (
        <li key={p.id}>{p.name} — ${p.price}</li>
      ))}
    </ul>
  );
}
DecisionWhy
visible derived, not storedStoring it means every path that changes products must recompute it, and one will not — the list and the filter would disagree
toSorted, not sortsort mutates in place, so it would reorder the caller's products array as a side effect of rendering
Empty state before the mapA guard reads better than a ternary around the whole return, and it makes the empty case impossible to forget
key={p.id}The list is both filtered and sorted, so positions change constantly — the exact case index keys break

The filter is the reason the key matters here even though the rows look stateless. Filtering changes which item sits at each index, so with index keys React would patch every row's text on every stock change rather than moving the matched ones.

What is missing for production: this conflates "no products at all" with "none in stock". Those need different messages and different actions — one is empty inventory, the other suggests clearing a filter — and a user seeing the wrong one assumes the page is broken.

4 (medium): A tabbed editor keeps the draft when switching between Write and Preview, but should clear it when switching documents. Write the JSX for both.
Solution 
// TABS — same component, same position, SAME key: the fiber is reused,
// so the draft survives. Only the mode prop changes.
{tab === "write"
  ? <Editor doc={doc} mode="write" />
  : <Editor doc={doc} mode="preview" />}

// Better still, since the branches differ only in a prop:
<Editor doc={doc} mode={tab} />

// DOCUMENTS — key by document id: a new document is a new entity, so
// the old Editor unmounts with its draft and a clean one mounts.
<Editor key={doc.id} doc={doc} mode={tab} />

The same mechanism produces opposite outcomes, and that is the point of the exercise. A stable key preserves; a changing key resets. Nothing else about the component needs to know which behaviour it is in.

The ternary version is worth replacing with the prop version even though both work. Two branches rendering the same component type at the same position is exactly the situation Rule 1 describes, so the ternary adds nothing except an opportunity for someone to later change one branch's component type and accidentally destroy the draft.

The trap to avoid: reaching for a useEffect on doc.id that calls setDraft(""). It renders the new document with the previous draft first, then clears it — a visible flash of the wrong content, and it grows a line for every piece of state the editor accumulates.

The product question this raises: discarding a draft on document switch is a decision, not a default. If drafts should survive, the state belongs above the Editor keyed by document id — and then you deliberately do not key the Editor.

5 (medium): Predict the bug: a chat renders messages with key={i}, each row has a favourite star held in row state, and new messages are prepended.
Solution 
  Every new message shifts all existing indices by one. The row fibers
  stay bound to their index keys, so the state stays at its POSITION
  while the data moves down.

  Star message "Lunch?"  (currently index 0)
  A new message arrives  -> "Lunch?" is now index 1
  Row key=0 keeps the star, and now renders the NEW message.

  OBSERVED: every star appears on the message ABOVE the one you
  starred, and it moves again with each new message.

The fix for the reconciliation bug is key={message.id}, so each row's fiber follows its message.

But the deeper fix is that the star should not be row state at all. "Is this message favourited" is a property of the message, not of the row rendering it. Held in row state it is also lost whenever the row legitimately unmounts — a filter, a search, pagination, a virtualised list scrolling it out of view — and it cannot be persisted or synced to another device.

Where the star livesSurvives reorder?Survives unmount?Can be persisted?
Row state, index keyNoNoNo
Row state, id keyYesNoNo
On the message dataYesYesYes

The general lesson: when losing a piece of state on remount would be a bug, that state does not belong in the component being remounted. Keys fix identity; they do not make ephemeral state durable.

6 (hard): Build a TransferList — two columns, items move between them on click — such that a per-row note input survives the move. Explain why this needs one rendered list rather than two maps.
Solution 
// WHY TWO MAPS CANNOT WORK
// Two maps produce two separate sibling groups. Reconciliation matches
// children within a group; an item leaving group A and appearing in
// group B is an unmount in A and a mount in B. Different fiber, fresh
// state — the note is gone. No key can bridge two groups.

// ONE list; membership is DATA; CSS places the columns.
function TransferList({ items, onMove }) {     // [{ id, side: "L"|"R", label }]
  return (
    <div className="transfer">
      {items.map(it => (
        <div key={it.id}
             className={`cell side-${it.side}`}
             style={{ gridColumn: it.side === "L" ? 1 : 2 }}>
          <button type="button" onClick={() => onMove(it.id)}>
            {it.label} ⇄
          </button>
          <input placeholder="note" />    {/* same key -> same fiber -> survives */}
        </div>
      ))}
    </div>
  );
}

The fiber follows key={it.id} regardless of which column CSS paints it in, because side is only a prop and a style. Nothing about the item's position in the element array changed, so nothing unmounts.

The general principle, which is worth more than this component: if state must survive a visual regrouping, the grouping has to be data rather than structure. The same reframing solves the concatenated pinned/recent list, tabs that should keep their panes alive, and drag-and-drop between columns.

7 (hard): A widget crashes and stays broken until a page reload. Using only concepts from this lesson, add a "Try again" that guarantees a pristine widget — and say why re-rendering alone would not fix it.
Solution 
function WidgetSlot({ data }) {
  const [attempt, setAttempt] = useState(0);
  return (
    <>
      <Widget key={attempt} data={data} />
      <button type="button" onClick={() => setAttempt(a => a + 1)}>
        Try again
      </button>
    </>
  );
}

Why a re-render is not enough: re-rendering reuses the same fiber. The widget's internal state — the half-initialised chart instance, the failed connection object, the DOM a third-party library mutated — all live on that fiber and its DOM node, and a re-render only updates props. Whatever poisoned it is still there, so it fails again immediately.

Bumping the key changes its identity, so React unmounts it entirely — running effect cleanups, discarding state, removing the DOM — and mounts a fresh instance. That is the only way to guarantee "pristine" without reloading the page.

Consequence of the remountWhy it matters here
Mount effects re-runExactly what you want — the widget re-initialises from scratch
Any fetch inside re-firesUsually desirable on a retry, but it is a real request, so a rapid-clicking user sends several
Cleanup runs on the old instanceThis is what prevents a leak — if the widget's cleanup is buggy, remounting repeatedly accumulates listeners
Scroll position and focus are lostAcceptable on a crash recovery, unacceptable as a general "refresh" mechanism

This pairs with an error boundary rather than replacing it. A crash during render unmounts the subtree and shows the boundary's fallback; the boundary needs a way to try again, and bumping a key on the child is that mechanism — which is precisely how reset keys work. Without the boundary, a render-phase crash takes the whole tree down before any button can be clicked.

What I would add in production: a cap. Unlimited retries against a genuinely broken widget is a loop that hammers whatever it calls; after two or three attempts the honest answer is a permanent error state with a support link.

🎯 Key Takeaways

  • Lists are plain arrays of elements; filter, sort and group are derived views computed during render, never stored in state.
  • A key is reconciliation identity — React matches old to new children by key, or by position when there is none, and state follows the match.
  • Index keys corrupt state the moment order changes. The data moves and the state stays at its position, so the meal choice ends up on the wrong guest.
  • Nothing warns about the wrong key — every key is present and unique, so React is internally consistent and externally wrong.
  • Generate ids when the data is created, not during render. A key from Math.random() remounts every row on every render.
  • A changed key is a deliberate demolition order — <Form key={recordId}> replaces a pile of prop-syncing effects, with no intermediate frame of wrong data.
  • Same position and same type keeps the fiber; a changed type destroys the subtree and everything below it.
  • A wrapper flip from div to section remounts every stateful child — with no warning, because nothing is wrong.
  • Unmount versus hide is a real trade-off: unmounting frees memory and loses state; hiding keeps both, and keeps the DOM in the accessibility tree.
  • Correct keys are also a measurable optimisation — ~48 ms and 1,000 re-renders against ~6 ms and none, before any memoization.
  • Keys are unique among siblings only, live on the element the map returns, and never arrive as a prop.
  • Namespace keys when concatenating lists — and note that an item moving between them changes key, so it remounts.
  • If state must survive a visual regrouping, the grouping must be data, not structure — one keyed list, placed by CSS.
  • State that must not be lost on remount does not belong in the row. Keys fix identity; they do not make ephemeral state durable.
