The Re-render Model & memo Performance

What you'll master: what a re-render actually is — React calling your function and diffing the result, which is not a DOM update — and why an identical re-render costs a function call rather than layout; the three things that trigger one, and why "the props changed" is not among them; that a parent re-render re-renders every child regardless of props, which is the entire reason React.memo exists; how memo compares props shallowly and silently does nothing when the parent passes an inline object, array or arrow function; the composition fix that beats it; reading the Profiler against a 16ms budget; index keys corrupting row state on deletion; and the honest ordering — most React slowness is a fetch waterfall or a bundle, not a render. Prerequisites: The Render Cycle and Props.

Part 1 — A Re-render Is a Function Call and a Diff

The word does more damage than any other in React vocabulary. "Re-render" sounds like repainting the screen. It is not. A re-render is React calling your component function again, receiving a new tree of plain objects, and comparing it with the previous one. The DOM is touched only where that comparison finds a difference.

  WHAT ACTUALLY HAPPENS WHEN A COMPONENT RE-RENDERS

  1. RENDER PHASE  — React calls Profile(props). Hooks read their stored
                     values, the body runs, and it RETURNS element
                     objects, not DOM:

                       { type: "div", props: { children: [...] } }

                     React walks into those children and repeats. This is
                     the fiber work loop — beginWork down, completeWork
                     up. Pure JavaScript; it touches no DOM.

  2. DIFF          — per position, compare the new element with the old
                     fiber. Same type? Update in place and record which
                     ATTRIBUTES changed. Different type? Delete the old
                     subtree and build a new one.

  3. COMMIT PHASE  — apply ONLY the recorded mutations. If the diff found
                     nothing, this phase does nothing: no DOM write, no
                     style recalculation, no layout, no paint.

  A re-render producing identical output therefore costs
    (your function body) + (a per-element property comparison)
  and NOTHING ELSE. It does not repaint. It does not reflow.
CostRough scaleWhat makes it vary
Calling one small component functionSingle-digit microsecondsWhat is in the body — a sort, a toLocaleDateString, or a regex over a long string dwarfs the render itself
Diffing one element with unchanged propsWell under a microsecondNumber of props; React compares them one by one
Rendering a subtree of 1,000 simple elementsLow single-digit milliseconds on a laptopMultiply by 4–6× for a mid-range phone. Depth matters less than count
A DOM mutation React does commitCheap individually, expensive in aggregateWhether it invalidates layout. Writing textContent on 500 nodes forces one reflow; reading offsetHeight between the writes forces 500

🔑 "This component re-rendered 40 times" is not by itself a bug report. Forty renders of a component that returns eight elements and does no work is a fraction of a millisecond and commits nothing. Forty renders of a component that sorts 5,000 rows in its body is 40 sorts. The render count is the symptom; the body is the cost.

Part 2 — The Three Triggers, and the Props Myth

  A COMPONENT RE-RENDERS FOR EXACTLY THREE REASONS

  1. ITS OWN STATE CHANGED
     A useState or useReducer setter was called with a value that is
     Object.is-different from the current one.

  2. ITS PARENT RE-RENDERED
     No condition attached. The parent rendered, so React walked into its
     children and called them — WHETHER OR NOT THEIR PROPS CHANGED, and
     whether or not they have any props at all.

  3. A CONTEXT IT CONSUMES GOT A NEW VALUE
     useContext(Ctx) subscribes this component directly. A new Provider
     `value` re-renders every consumer even where memo would otherwise
     have stopped the parent walk.

  THAT IS THE COMPLETE LIST. "The props changed" is NOT on it.

The myth is worth killing because it is half true in effect and completely false in mechanism. Props do change when a parent re-renders, so the two are correlated, and a beginner concludes React watches props. It does not — there is no subscription on a prop. A child re-renders because its parent rendered, and the props are simply whatever the parent handed down on that pass.

BeliefRealityWhy it matters
"New props trigger a re-render"Nothing watches props. The parent rendering is the triggerExplains why a child with zero props still re-renders on every parent update
"Passing the same props avoids a re-render"It does not, unless the child is wrapped in memoThis is the single reason memo exists as an API
"Only the changed component re-renders"That component and its whole subtree re-renderState placement is the highest-leverage fix: push state down and the subtree shrinks

  THE STRUCTURAL CONSEQUENCE — and the fix that needs no memo

  function App() {
    const [text, setText] = useState("");        // state lives HERE
    return (
      <div>
        <input value={text} onChange={e => setText(e.target.value)} />
        <ExpensiveDashboard />      // no props at all — runs anyway
      </div>
    );
  }

  Every keystroke re-renders App, so React walks into
  ExpensiveDashboard and calls it. It has no props. It does not read
  `text`. Rule 2 has no exception.

  FIX — move the state into the component that uses it:

  function SearchBox() {
    const [text, setText] = useState("");
    return <input value={text} onChange={e => setText(e.target.value)} />;
  }
  // App now renders <SearchBox /> and <ExpensiveDashboard /> and never
  // re-renders itself, so neither does the dashboard.

  Zero memo, zero dependency arrays, and unlike a memo it cannot be
  silently broken from a distant call site. TRY THIS FIRST.

Part 3 — React.memo: One Shallow Comparison

  const Row = React.memo(function Row({ item, onSelect }) { ... });

  memo inserts a check at the top of rule 2:

    parent re-rendered
        |
        v
    memo-wrapped?  -- no -->  call the component
        |
       yes
        v
    same set of prop keys, and Object.is(prev[k], next[k]) for each?
        |                              |
       yes                             no
        |                              |
    SKIP the call, reuse the      call it, and walk its subtree
    entire previous subtree

  SHALLOW means one level: it compares REFERENCES for objects, arrays
  and functions, and never looks inside them.

  memo does NOT stop rule 1 (own state) or rule 3 (context). It only
  intercepts the parent walk.

Now the reason memo is the most-applied and least-effective optimisation in the ecosystem. Each of these props is a new value on every parent render, so the comparison fails every time and the wrapper adds cost without saving anything:

  <Row key={item.id}
       item={item}
       style={{ padding: 8 }}             // ❌ NEW OBJECT every render
       tags={["a", "b"]}                  // ❌ NEW ARRAY every render
       onSelect={() => select(item.id)} /> // ❌ NEW FUNCTION every render

  Object.is({padding:8}, {padding:8}) === false. Identical contents,
  different references. The comparison fails on the FIRST such prop and
  Row is called regardless.

  There is NO WARNING. The code looks optimised and is slower than no
  memo at all — you pay a failed comparison on top of the render.

  children IS THE SNEAKIEST CASE

    <MemoizedCard><Avatar user={u} /></MemoizedCard>

  `children` is a prop, and JSX creates a NEW element object for
  <Avatar /> on every parent render. memo around a component that
  receives JSX children from a re-rendering parent is dead weight.

⚠️ A memo is a claim that survives only as long as every caller keeps it true. It holds today; six months later somebody adds className={`row ${state}`} at the call site and it silently stops working. No test fails, and the wrapper stays in the file looking like an optimisation. That is why structural fixes are strictly better where they are available: they cannot be undone from a distance.

Part 4 — Composition: the Fix That Beats memo

React has a bail-out that predates memo and is more reliable than it. When React walks into a child and finds the element object is literally the same reference as last time, with no pending state update and no changed context on that fiber, it reuses the whole subtree without calling anything. You get it for free by creating the expensive element somewhere that is not re-rendering.

  BEFORE — the expensive tree is created inside the re-rendering component

  function Page() {
    const [count, setCount] = useState(0);
    return (
      <div>
        <button onClick={() => setCount(c => c + 1)}>{count}</button>
        <ExpensiveTree />          // JSX evaluated here, on every click
      </div>
    );
  }

  Each click re-runs Page's body, re-evaluating that JSX, which creates
  a NEW element for ExpensiveTree. New element -> no bail-out -> call.

  AFTER — the tree is created by the grandparent and passed in

  function Page({ children }) {          // does not know what it wraps
    const [count, setCount] = useState(0);
    return (
      <div>
        <button onClick={() => setCount(c => c + 1)}>{count}</button>
        {children}
      </div>
    );
  }

  function App() {
    return <Page><ExpensiveTree /></Page>;   // created HERE, in App
  }

  The click re-renders Page only. App did not run, so the
  <ExpensiveTree /> element is the SAME REFERENCE as before. React
  finds oldProps === newProps on that fiber with no pending work and
  bails out on the entire subtree.

  NO memo. NO useCallback. NO dependency array to get wrong.
React.memoComposition (children as a prop)
What it comparesEvery prop, shallowly, on every renderOne reference: the element object itself
Runtime costA comparison per prop per render, plus a wrapper fiberZero — it is the existing bail-out path

🔑 Reach for composition when the expensive subtree does not depend on the changing state, and for memo when it does. Most "we need to memoize the whole app" situations are the first case: a layout component holding a sidebar-open boolean, re-rendering a page of content that has nothing to do with the sidebar.

Part 5 — Measure First: the Profiler and the Frame Budget

  THE 16ms BUDGET, HONESTLY

    60 Hz display  -> 16.7 ms per frame
    120 Hz display ->  8.3 ms per frame

  That is the WHOLE frame, and the browser needs part of it for style
  recalculation, layout, paint and compositing. A realistic JavaScript
  budget at 60 Hz is roughly 8–10 ms, and less on a phone where every
  one of those steps is slower too.

  WHERE A FRAME GOES WHEN REACT UPDATES

    [ your component functions ][ diff ][ commit ][ layout effects ]
    |------- React's render phase ------|--- synchronous ---|
    [ browser: style -> layout -> paint -> composite ]
    [ passive effects (useEffect) ]

  useLayoutEffect runs inside the frame, BEFORE paint — which is what
  makes it useful for measuring the DOM and dangerous for anything
  slow. useEffect runs after paint, so the same work costs the user
  nothing visible.

  An update over ~50 ms is a long task, and that — not render count —
  is what the INP metric measures and what a user feels as sluggish.

Part 6 — Lists: Keys, Reconciliation, and Virtualisation

  HOW REACT MATCHES A LIST BETWEEN RENDERS

  Without keys it matches BY POSITION: old child 0 to new child 0.
  Insert at the front and every position shifts, so every row counts as
  changed and is re-rendered and re-committed.

  With keys it builds a map from key to old fiber and matches by key. A
  row whose key it finds is MOVED, not rebuilt — its DOM node, its
  component state and its uncontrolled input values come with it.

  A KEY IS AN IDENTITY CLAIM: "this is the same row as before."
  An index is a POSITION — and position is exactly what changes when a
  list is reordered, filtered, or has an item removed.
  WORKED EXAMPLE — index keys destroying user input

  {todos.map((todo, i) => <TodoRow key={i} todo={todo} />)}

  TodoRow holds internal state: a draft string the user is typing.

  BEFORE                            AFTER deleting "Milk"
    key  todo     draft               key  todo     draft
     0   Milk     ""                   0   Eggs     ""        <- typing LOST
     1   Eggs     "buy oat milk"       1   Bread    "buy oat milk"
     2   Bread    ""                                          <- MOVED here

  React's reasoning: key 0 existed before, so reuse that fiber with new
  props (Eggs). Key 1 existed, reuse with new props (Bread). Key 2 is
  gone, unmount it.

  The DATA moved up a position; the STATE stayed with the position.
  React did nothing wrong — you told it row 1 is still row 1. The
  checkbox version is worse: the wrong item silently looks ticked.

  With key={todo.id} React finds "eggs" and "bread" in the old map,
  keeps those exact fibers and their drafts, and unmounts only "milk".

Almost every "React is slow" report resolves to something that is not a re-render. Work the list in this order and you will spend your time where the milliseconds are.

Interview Questions

Beginner: What exactly happens when a component "re-renders"?

React calls the component function again. The function returns a tree of plain JavaScript element objects — { type, props, key } — not DOM nodes. React compares that tree against the one from the previous render, position by position, and records the differences.

Then it commits: it applies only the recorded differences to the real DOM. If the diff found nothing, the commit phase does nothing — no DOM write, no style recalculation, no layout, no paint.

So a re-render that produces identical output costs a function call plus a property comparison per element. It is not a repaint, which is the assumption behind most premature optimisation in React. The expensive parts are the work inside your function body and the browser work that follows an actual DOM mutation.

Beginner: Name the three things that cause a re-render — and say why "props changed" is not one.

A component re-renders when its own state changes, when its parent re-renders, or when a context it consumes gets a new value. That is the complete list.

Props are not a trigger because nothing subscribes to them. There is no watcher on a prop. When a parent re-renders, React walks into its children and calls them, and the props are simply whatever the parent passed on that pass. The correlation is why the myth survives: props usually do change when a parent renders.

The test that settles it: a child with no props at all still re-renders every time its parent does. And the practical consequence is that passing identical props does not prevent a re-render — which is precisely the gap React.memo exists to fill.

Mid: A colleague wrapped a list row in React.memo and the Profiler shows it still rendering on every parent update. Why?

Almost certainly because at least one prop is a new reference on every parent render. React.memo does a shallow comparison: same set of keys, and Object.is on each value. For objects, arrays and functions that compares references, not contents.

So style={{ padding: 8 }}, tags={[...]}, onSelect={() => select(id)}, data={items.filter(f)} and JSX children all produce a fresh value every render, and the comparison fails on the first one it reaches. Nothing warns you — the code looks optimised and is now marginally slower, because you pay for the failed comparison on top of the render.

Two other causes worth checking. If the row reads a context whose value changes, memo is bypassed entirely — context notifies consumers directly. And if the row has its own state that is updating, memo was never relevant; it only intercepts the parent walk.

The fix is to stabilise every prop — hoist constant objects to module scope, wrap handlers in useCallback with stable deps, memoize derived arrays — or to remove the memo. A partially-stabilised memo is worse than none, and it misleads the next reader into thinking the problem is solved.

Mid: Why do index keys corrupt state, and when is an index key acceptable?

A key is React's identity claim for a list item: "the element with this key is the same element as before." React builds a map from key to the previous fiber and reuses the matched fiber — including its component state, its DOM node, focus, scroll position and uncontrolled input values.

An index is a position, not an identity, and position is exactly what changes when an item is removed, inserted or reordered. Delete the first of three rows and the item formerly at index 1 is now at index 0, so React matches it to the fiber that belonged to the deleted row's neighbour — and the state attached to that fiber stays put while the data slides past it.

Concretely: a user types into row 1's draft field, deletes row 0, and their text is now sitting in a different row. With checkboxes the failure is quieter and worse, because the wrong item appears ticked and gets submitted. React is behaving exactly as instructed; the instruction was wrong.

Index keys are acceptable when the list is append-only and never reordered, filtered or deleted from, and the rows hold no state, no focus and no uncontrolled inputs. That is a narrow set of conditions, and none of them are enforced by anything — a later filter feature breaks it silently. So the default should be a stable id, generated where the data is created rather than in render.

Senior: A dashboard stutters while typing in a filter box. Walk through your diagnosis, and say when you would use memo versus a structural fix.

First, reproduce it on a production build with the CPU throttled 4–6×. Development timings include StrictMode's double-invocation and dev-only checks, so any number I take from a dev build is roughly double and not the user's device anyway.

Assuming it is rendering, I record a Profiler session with "why did this render" enabled, type a few characters, and read the commit list. The flame chart tells me which component is wide. There are usually two shapes. Either one component is expensive — it sorts or formats a few thousand rows in its body — or thousands of cheap components are re-rendering because state sits at the top of the tree. I check the Performance panel first regardless, because if typing fires a request per keystroke the stutter is network and parsing, and no amount of memoization touches it.

For the first shape the fix is useMemo around the computation, or moving it out of render entirely. For the second I try structure before memoization, in this order: push the state down into a FilterBox that owns it, so the dashboard stops re-rendering at all; or pass the expensive subtree as children so its element identity is stable and React bails out on it. Both are free at runtime and cannot be broken from a call site.

I reach for memo when the expensive child genuinely depends on the changing state — the filtered list itself. Then I memoize the row, stabilise every prop it receives, and verify in the Profiler that the rows actually went grey. If the list is in the thousands I would question the requirement first and virtualise second.

My recommendation: structural fixes first because they are permanent, memo second and always with a before/after profile in the PR, and virtualisation last because it costs real accessibility work. And I would not remove existing memos on the assumption that the React Compiler covers them unless I have confirmed it is enabled and inspected its output.

Senior: When is memo the wrong tool even though it would work, and what does the React Compiler change?

memo is wrong whenever a structural change gets the same result. If the expensive subtree does not read the state that is changing, the correct answer is to move the state down or to hand the subtree in as children from a component that is not re-rendering. Both use React's existing bail-out — same props reference, no pending state, no changed context — which is cheaper than a shallow comparison and, more importantly, cannot be silently defeated by a distant call site adding an inline prop.

It is also wrong when the render it saves is cheaper than the comparison it adds. A component returning six elements is not worth eight Object.is calls plus a wrapper fiber on every parent render, and blanket memoization makes the codebase harder to change: every prop becomes something that must stay referentially stable, forever.

The React Compiler, shipped as stable alongside React 19, changes the economics rather than the principles. It analyses components at build time and inserts memoization automatically — caching values and JSX so that a re-render with unchanged inputs skips the work — which removes most of the hand-written useMemo, useCallback and memo that exists purely for referential stability. It bails out on code it cannot prove safe, which means the discipline it rewards is exactly the one you already owe React: pure render functions and no mutation of props or state.

What it does not do is make renders free, fix a waterfall, or shrink a bundle, and it is opt-in — a build-tool plugin with an ESLint rule that reports what it had to skip. My recommendation: adopt it, keep the rule on, and stop hand-writing memoization for identity — but keep it where the cost is a genuinely expensive computation or where you have measured that it still matters.

🏋️ Graded Exercises

1 (easy): Explain why <Clock /> re-renders here, and fix it without memo. 
function App() {
  const [open, setOpen] = useState(false);
  return (
    <div>
      <button onClick={() => setOpen(o => !o)}>Toggle</button>
      {open && <Panel />}
      <Clock />          {/* no props — why does this re-render? */}
    </div>
  );
}
Solution 
  WHY: rule 2. App's state changed, so App re-runs; React walks into
  every child it returns and calls them. Clock has no props, which is
  irrelevant — nothing about props is consulted. It re-renders because
  its parent did.

  FIX — move the state to the component that uses it:

  function Toggler() {
    const [open, setOpen] = useState(false);
    return (
      <>
        <button onClick={() => setOpen(o => !o)}>Toggle</button>
        {open && <Panel />}
      </>
    );
  }

  function App() {
    return (
      <div>
        <Toggler />
        <Clock />      // App never re-renders now, so neither does this
      </div>
    );
  }

Why not memo(Clock)? It would also work — empty props always compare equal — but it leaves App re-rendering and stops the walk only one level down. Moving the state stops the render at its source, costs nothing at runtime, and keeps working when Clock acquires siblings later. State read by one small piece of the tree but held at the top is the most common performance bug in React, and the only one whose fix deletes code.

2 (easy): This memo never holds. Find every reason. 
const Row = React.memo(function Row({ item, style, onPick }) { ... });

function List({ items }) {

Solution

styleAn object literal is a new reference every renderHoist to module scope: const ROW_STYLE = { padding: 8 }; — free, no hook
onPickAn arrow function is a new reference every render, and it closes over item so it cannot simply be hoistedPass a stable handler and let the row supply the id: onPick={onPick} with onClick={() => onPick(item.id)} inside Row
itemFine if items holds the same object references. Breaks the moment a parent does items.map(i => ({ ...i }))Do not rebuild objects you did not change
  const ROW_STYLE = { padding: 8 };                 // module scope

  const Row = React.memo(function Row({ item, style, onPick }) {
    return <li style={style} onClick={() => onPick(item.id)}>{item.name}</li>;
  });

  function List({ items, onPick }) {                 // onPick from above
    return items.map(item => (
      <Row key={item.id} item={item} style={ROW_STYLE} onPick={onPick} />
    ));
  }

What the broken version does at runtime: on every List render, React calls the memo wrapper for each row, compares three props, fails on the first object, and calls Row anyway. You pay the full render plus a comparison per row per render. With 500 rows that is 1,500 wasted Object.is calls to achieve nothing.

Note the chain: onPick is only stable if List's own caller made it stable. Memoization is transitive — it holds end to end or not at all.

3 (medium): A sidebar toggle re-renders a heavy report. Fix it with composition rather than memo, and say when composition cannot work. 
function Layout() {
  const [open, setOpen] = useState(true);
  return (
    <div className={open ? "wide" : "narrow"}>
      <button onClick={() => setOpen(o => !o)}>Menu</button>
      <HeavyReport />       {/* 400ms render, unrelated to `open` */}
    </div>
  );
}
Solution 
  function Layout({ children }) {
    const [open, setOpen] = useState(true);
    return (
      <div className={open ? "wide" : "narrow"}>
        <button onClick={() => setOpen(o => !o)}>Menu</button>
        {children}
      </div>
    );
  }

  function App() {
    return (
      <Layout>
        <HeavyReport />      // element created HERE, in App
      </Layout>
    );
  }

  MECHANISM: clicking Menu re-renders Layout only. App did not run, so
  the <HeavyReport /> element object is byte-for-byte the same
  reference React saw last time. On that fiber React finds
  oldProps === newProps, no pending state update and no changed
  context, and takes the bail-out path — the 400ms never happens.
ApproachResultVerdict
Composition (above)Zero renders of the report; no hooks, no comparisonBest. Cannot be broken by a call site adding a prop
memo(HeavyReport)Also works today — it takes no propsFine, but fragile: the day it takes filters={{...}} it silently stops
CSS-only toggleNo React state at all; a class on <body>Worth asking for. If the state is purely presentational, React need not know about it

When composition cannot work: the moment HeavyReport needs a value that lives in Layout's state. Children are created by the grandparent, so they cannot read state held below them. If the report must know open, you are back to memo — or, better, to asking whether the report really needs that boolean or whether CSS can express the layout difference.

4 (medium): A todo list uses key={i}. Each row has a checkbox and an uncontrolled note field. The user reports "checking one item ticks the wrong one after I delete something." Explain precisely, then fix it.
Solution 
  WHAT HAPPENS, STEP BY STEP

  todos = [Milk, Eggs, Bread]   keys 0, 1, 2

  The user types "oat" into row 1's note (an uncontrolled input — the
  value lives in the DOM node) and ticks row 2's checkbox (component
  state inside TodoRow).

    key 0  Milk    note ""      checked false
    key 1  Eggs    note "oat"   checked false
    key 2  Bread   note ""      checked TRUE

  Delete Milk. todos = [Eggs, Bread], rendered with keys 0 and 1.

  React's key map from the previous render contains 0, 1, 2. It finds
  key 0 -> reuse that fiber and its DOM node, give it new props (Eggs).
  Finds key 1 -> reuse, new props (Bread). Key 2 is absent -> unmount.

    key 0  Eggs    note ""      checked false   <-- "oat" gone
    key 1  Bread   note "oat"   checked false   <-- tick gone, note wrong

  The DATA moved up one position; the STATE stayed with the position.
  That is exactly what an index key promises, so React honoured it.

  FIX

    {todos.map(todo => <TodoRow key={todo.id} todo={todo} />)}

  Now the map contains "milk", "eggs", "bread". React finds "eggs" and
  "bread" and keeps their exact fibers — note text and checkbox state
  travel with the item — and unmounts only "milk".
State that moves with the fiberWhy it is affected
useState inside the rowHook state is stored on the fiber, and the fiber is matched by key
Uncontrolled input valuesThey live on the reused DOM node, which React keeps rather than recreating
Focus and text selectionSame DOM node, so the caret stays where it was — now inside the wrong row
Scroll position, and mid-flight CSS transitionsBoth belong to the retained DOM node, so they continue on the wrong row

Why no error is ever thrown: nothing here is invalid. React cannot know that index 1 means a different logical item than it did last render — that is the information a key is supposed to carry. The bug is a lie in the data you gave the reconciler.

If the data has no id: generate one at creation time (crypto.randomUUID() when the todo is added), not in render. A key generated during render is new on every render, which unmounts and remounts every row — strictly worse than the index.

5 (hard): A table of 8,000 rows takes ~600ms to render and scrolls badly. Produce a plan, in the order you would actually do it, with the reasoning for each step.
Solution 
  STEP 0 — MEASURE, ON A THROTTLED PRODUCTION BUILD
    Profiler commit duration gives the render cost; the Performance
    panel says whether the scroll jank is React at all. A sticky header
    whose scroll listener reads offsetTop produces this exact symptom
    with zero React involvement.

  STEP 1 — ASK WHETHER 8,000 ROWS ARE NEEDED
    Nobody reads 8,000 rows. Server-side pagination or a better filter
    deletes the problem instead of engineering around it, and it also
    fixes the payload size and the JSON.parse cost nobody measured.
    This is the cheapest fix and the one usually skipped.

  STEP 2 — LOOK AT THE PER-ROW BODY BEFORE THE ROW COUNT
    8,000 rows x one new Intl.DateTimeFormat per row is 8,000 formatter
    constructions. Hoisting it to module scope has taken 600ms to under
    100ms in real cases. Same for per-row regexes and deep clones.

  STEP 3 — VIRTUALISE
    @tanstack/react-virtual or react-window: render ~25 rows plus
    overscan inside a spacer sized to 8,000 x rowHeight. Render cost
    becomes independent of dataset size, and the DOM drops from ~64,000
    nodes to a few hundred.

  STEP 4 — MEMOIZE THE ROW, LAST
    Only if the profile still shows row renders costing something. With
    virtualisation in place there are 25 rows, so memo saves 25 cheap
    calls — usually not worth the permanent prop-stability constraint.

The trap is that "8,000 rows" reads like a virtualisation problem, so that is what most people reach for first. But a per-row allocation is a constant multiplier on every row and it survives virtualisation — it just becomes 320× less visible while remaining wrong. Fixing the body first often makes step 3 unnecessary.

On accessibility: a screen-reader user needs aria-rowcount on the grid and aria-rowindex on each row, or the virtualised table announces "25 rows" when there are 8,000. Budget that rather than discovering it in an audit.

6 (hard): A team has added memo, useMemo and useCallback across 60 components. Load time is unchanged and typing is still slow. Diagnose the situation and write the recommendation you would give.
Solution 
  THE THREE THINGS TO CHECK, IN ORDER

  1. IS RENDERING THE BOTTLENECK AT ALL?
     Performance panel, throttled, production build. If the long tasks
     are JSON.parse or a third-party script, no memo could have helped.
     Load time being unchanged is a strong hint on its own: memoization
     affects UPDATE cost, never FIRST RENDER — every component runs on
     mount regardless.

  2. DO THE MEMOS ACTUALLY HOLD?
     Profiler with "why did this render" on. Expect to find most of
     them failing on an inline object, array, arrow or JSX children.
     A memo chain holds end to end or not at all: one unstable prop
     three levels up defeats everything below it.

  3. WHERE IS THE STATE?
     If a single state object at the root re-renders the tree on every
     keystroke, the answer was never memoization. Push the state down,
     or pass the stable subtree as children.

  AND THE COST NOBODY PRICED
     60 components x comparisons per render + 60 dependency arrays
     allocated and compared on every render + a wrapper fiber each.
     Small individually, permanent, and 60 new places for a stale
     dependency to hide.

The recommendation: stop adding memoization. Record one profile of the actual complaint on a throttled production build and fix the top item, whatever it is — my expectation is a fetch waterfall for the load time and state placement for the typing. Then delete the memos that the Profiler shows are not holding, because a failing memo is pure cost plus a false sense of safety. Keep the two or three that guard a genuinely expensive computation, and put the before/after numbers in the PR so the next person does not have to re-derive them.

On the React Compiler: for a codebase in this state it is the right medium-term answer — it inserts memoization automatically for the code it can prove pure, which is most of what these 60 components were hand-rolling badly. It will not fix the waterfall or the bundle, and it is not a reason to skip step 1.

🎯 Key Takeaways

  • A re-render is React calling your function and diffing the result — it is not a DOM update. An identical re-render commits nothing: no layout, no paint.
  • Exactly three things trigger a re-render: own state changed, parent re-rendered, or a consumed context value changed.
  • "The props changed" is not a trigger. Nothing subscribes to props; a child with no props re-renders whenever its parent does.
  • A parent re-render re-renders the entire subtree regardless of props — which is the only reason React.memo exists.
  • React.memo is one shallow props comparison — Object.is per key — and it intercepts only the parent walk, never own state or context.
  • An inline object, array, arrow function or JSX child silently defeats memo every render, with no warning — and memoization is transitive, so one unstable prop anywhere up the chain defeats everything below it.
  • Pushing state down is the cheapest fix in React and the only one that deletes code rather than adding it.
  • Passing the expensive subtree as children keeps its element identity stable, so React takes its built-in bail-out — no hooks, nothing a call site can break. It cannot work when the child needs state held by the re-rendering parent; that case is what memo is for.
  • Profile a production build with the CPU throttled 4–6×; dev renders are doubled by StrictMode and dev-only checks inflate every timing.
  • The frame budget is ~16ms at 60Hz, of which JavaScript gets roughly 8–10ms, and an update over 50ms is a long task the user feels.
  • A key is an identity claim, not a position — index keys attach row state, focus and uncontrolled input values to the wrong item after a deletion or reorder.
  • Keys generated in render (Math.random()) are worse than index keys: every row unmounts and remounts on every render.
  • Virtualise at thousands of rows, not dozens, and budget for the Ctrl-F, print and aria-rowindex work it costs you.
  • Most perceived React slowness is a fetch waterfall or a bundle, not a re-render — check the network waterfall and the main-thread flame chart before the React Profiler.
