useMemo & useCallback Performance

What you'll master: that useMemo caches a value and useCallback caches a function — and that useCallback(fn, d) is literally useMemo(() => fn, d); the cost nobody counts, because every memo allocates a closure and a dependency array and runs a comparison on every single render, so wrapping a cheap expression is a net loss; the three cases where a memo genuinely pays; why useCallback does nothing at all when the child is not memoized — the single most common misuse in real codebases; the same stale-closure traps as effect dependencies; that useMemo is a performance hint React is allowed to discard, so it can never carry correctness; memoized context values; React.memo's custom comparator; and what the React 19 compiler does to all of this. Prerequisites: The Re-render Model & memo.

Part 1 — Two Hooks, One Mechanism

Both hooks do exactly one thing: they store a value in the fiber's hook slot alongside the dependency array that produced it, and on the next render they compare the new dependency array with the stored one, element by element, using Object.is. Same array contents means hand back the stored value. Any difference means recompute and store again. That is the whole feature.

  WHAT LIVES IN THE HOOK SLOT

    fiber.memoizedState -> [ ... hook, hook, hook ... ]
                                        |
                                        +-- { value: <the cached thing>,
                                              deps:  [a, b, c] }

  ON EVERY RENDER, FOR EVERY MEMO:

    1. Evaluate the arguments. The arrow function you passed is
       ALLOCATED. The deps array literal is ALLOCATED. Both happen
       before React is even called — they are just JavaScript
       expression evaluation.
    2. React walks prev.deps and next.deps in parallel, calling
       Object.is on each pair.
    3. All equal   -> return the stored value. The arrow you just
                      allocated is thrown away.
       Any differ  -> call the arrow, store the result, store deps.

  THE TWO HOOKS ARE THE SAME HOOK:

    useCallback(fn, deps)  ===  useMemo(() => fn, deps)

  That is not an analogy. In React's own source useCallback is a
  near-copy of useMemo that skips the invocation step: useMemo calls
  what you gave it and caches the RESULT, useCallback caches what you
  gave it AS-IS.

    const handler = useCallback(() => save(id), [id]);
    const handler = useMemo(() => () => save(id), [id]);   // identical

  The second form is why people find useCallback confusing: the value
  being cached is itself a function, so there are two arrows and only
  the inner one is the thing you keep.

  A DETAIL THAT SURPRISES PEOPLE: DEPS ARE POSITIONAL, NOT NAMED.

    useMemo(() => f(a, b), [a, b])   and
    useMemo(() => f(a, b), [b, a])

  behave identically, because React only asks "is slot 0 the same as
  last slot 0". It does not know the names. It also does not check
  that your deps have anything to do with your function body — that
  is entirely the lint rule's job, and the lint rule is the only
  thing standing between you and a stale value.

  THE DEPS ARRAY MUST HAVE A CONSTANT LENGTH ACROSS RENDERS. React
  warns in development if it changes, because the positional walk has
  no meaning otherwise. Conditional deps are not a thing:

    useMemo(() => total(items), isAdmin ? [items, tax] : [items])
    // warns: "The final argument changed size between renders"

Part 2 — The Cost You Are Not Counting

The mental model most people carry is that a memo is free when it hits and expensive only when it misses. It is the opposite of free. A memo has a fixed per-render cost that you pay on every render, forever, in exchange for occasionally skipping some work. If the work you skip is small, you have made the component slower and harder to read at the same time.

  WHAT ONE useMemo COSTS ON A RENDER WHERE THE DEPS DID NOT CHANGE:

    - one closure allocation (the arrow you pass, every render)
    - one array allocation (the deps literal, every render)
    - a hook-slot advance and a bounds check
    - N Object.is calls
    - garbage: two objects per memo per render, which is minor on
      its own and is not minor when a list row has six of them and
      there are 500 rows

  Order of magnitude on a modern JIT: roughly 30-150 nanoseconds for
  a small memo, dominated by the allocations rather than the compare.
  Call it 0.0001ms. That number is the point: it is small, but it is
  not zero, and the thing you are protecting is frequently smaller.

  MEASURE WHAT YOU ARE ACTUALLY SKIPPING:

    const fullName = useMemo(
      () => `${first} ${last}`, [first, last]);

  A template literal on two short strings costs well under 100ns.
  You have wrapped a ~50ns operation in a ~100ns cache. You are now
  slower, you allocate more, and you have added a dependency array
  that can go stale. This is the most common useMemo in the wild.

  THE ROUGH THRESHOLD:

    computation cost   verdict
    ----------------   -----------------------------------------
    < 0.1ms            memo is a net loss, always
    0.1ms - 1ms        memo is noise; only matters if it runs in
                       a list of hundreds
    1ms - 5ms          worth memoizing if the deps are stable
    > 5ms              memo, or move the work off the render path
                       entirely (worker, server, precompute)

  5ms is a third of a 16.7ms frame at 60Hz, and most of an 8.3ms
  frame at 120Hz. That is the real reason the threshold sits there.
Operation on a mid-range laptopRough costMemo worth it?
String concat, arithmetic, property read< 0.001msNo — the memo costs more

Note the last row carefully, because it splits the whole topic in half. Memoizing an object literal is never about the cost of building the object. It is about the identity of the reference that comes out, and whether something downstream compares that identity. Those are two entirely different justifications, and confusing them is why so much memoization in real code accomplishes nothing.

Keep the two reasons apart when you review. For cost, the question is how many milliseconds. For identity, the question is who compares this reference, and are they memoized. If you cannot answer the question belonging to the reason you claimed, the memo is decoration — and identity is where nearly all wasted memos live, because the answer to "who compares it" is usually "nobody".

Part 3 — The Three Cases That Actually Pay

There are exactly three situations where a memo earns its keep. Everything else is speculation. Learn these three shapes and you can review memoization by pattern-matching rather than by argument.

  CASE 1 -- AN EXPENSIVE COMPUTATION, RE-RUN BY UNRELATED STATE.

    function Report({ rows }) {
      const [tab, setTab] = useState('summary');

      // 12ms sort over 20k rows. Without the memo it runs again
      // every time the user clicks a tab, which has nothing to do
      // with rows.
      const sorted = useMemo(
        () => [...rows].sort(byRevenue), [rows]);

      ...
    }

  The tell: the work depends on A, but the component re-renders
  because of B. Without the memo, B pays for A's work.

  If the component only ever re-renders when rows changes, the memo
  hits zero percent of the time and is pure overhead. MEASURE THE
  HIT RATE, not the cost.

  CASE 2 -- A REFERENTIAL PROP OF A MEMOIZED CHILD.

    const Row = memo(function Row({ item, onSelect }) { ... });

    function List({ items }) {
      const [q, setQ] = useState('');
      // Row is memo'd, so it compares onSelect by reference.
      // Without useCallback, typing in the search box gives every
      // Row a new function and all 500 rows re-render.
      const onSelect = useCallback(id => select(id), []);
      return items.map(i =>
        <Row key={i.id} item={i} onSelect={onSelect} />);
    }

  The tell: you can point at the memo() wrapper on the consumer.
  No wrapper, no case. See Part 4.

  CASE 3 -- A DEPENDENCY OF AN EFFECT, WHERE IDENTITY DRIVES RE-RUNS.

    function Search({ query }) {
      // Recreated every render -> the effect below re-runs every
      // render -> setState -> render -> infinite fetch loop.
      const fetchIt = useCallback(
        () => api.search(query), [query]);

      useEffect(() => { fetchIt().then(setHits); }, [fetchIt]);
    }

  The tell: the function appears in a dependency array. Here the
  memo is not a performance tweak at all -- without it the code is
  BROKEN, not slow. This is the only case where a memo is load
  bearing, and even then the better fix is usually to move the
  function INSIDE the effect and drop the hook entirely.

Case 3 deserves one more sentence because it is the case people invert. When identity drives an effect, the memo is not an optimisation — it is the difference between a working component and a render loop. But reaching for useCallback there is usually treating the symptom. The function only needs a stable identity because it escaped the effect that uses it. Put it back inside, and the dependency disappears along with the hook.

Part 4 — useCallback Without a Memoized Child Does Nothing

This is the single most common piece of wasted work in React codebases, and it survives review because it looks like diligence. A stable function reference has no effect unless something on the receiving end compares references. A plain component compares nothing — it re-renders because its parent re-rendered, and it would have done so if you had passed the same function object every time since the beginning of the universe.

  THE CODE THAT ACCOMPLISHES NOTHING:

    function Parent() {
      const [count, setCount] = useState(0);
      const handleClick = useCallback(() => doThing(), []);
      return (
        <>
          <button onClick={() => setCount(c => c + 1)}>{count}</button>
          <Child onClick={handleClick} />   {/* NOT memo'd */}
        </>
      );
    }

    function Child({ onClick }) { return <button onClick={onClick}/>; }

  Click the counter. Parent re-renders. React sees a Child element in
  the new tree and a Child element in the old tree at the same
  position, same type -- so it calls Child again. It does not look at
  props to decide that. PROPS ARE NOT A RE-RENDER TRIGGER.

  Child re-rendered. The useCallback changed nothing except:
    + one closure allocated per render (the arrow)
    + one array allocated per render (the [])
    + one hook slot, one comparison
    + a dependency array you now have to keep correct

  NET RESULT: strictly slower, plus a staleness risk, plus a reader
  who now believes something is being optimised.

  THE FIX IS ONE OF TWO THINGS, AND "ADD useCallback" IS NEITHER:

    A) memo the child, IF you have measured that its render matters:
         const Child = memo(function Child({ onClick }) {...});
       Now useCallback has a job. Both halves are required -- memo
       without useCallback is equally useless, because the inline
       arrow breaks the shallow compare every time.

    B) Delete the useCallback. This is the right answer far more
       often. A component that renders a button does not need
       protecting from re-rendering.

Memoization is all-or-nothing along a prop boundary: one unstable prop defeats the whole comparison, so a memo'd child with five stabilised props and one inline style={{ margin: 4 }} re-renders exactly as often as an unmemoized one, while costing more. And the moment you do get the comparison to succeed, a wrong dependency array stops being a performance detail and becomes a bug that shows the user stale data.

Part 5 — A Hint, Not a Guarantee, and the Staleness That Follows

React's documentation is explicit and people read past it: you may rely on useMemo as a performance optimization, not as a semantic guarantee. React reserves the right to throw away a cached value and recompute it — to free memory for offscreen content, for example. Today React 18 and 19 do not aggressively discard, but Activity/Offscreen trees are exactly the machinery that will, and code written against the guarantee breaks silently when it does.

  WHAT THIS FORBIDS.

  BROKEN -- identity used as a map key:

    const key = useMemo(() => ({}), []);   // "stable" object
    registry.set(key, subscription);        // WeakMap keyed on it

  If React recomputes, you get a new object, the WeakMap entry is
  orphaned, and the subscription leaks. Correct tool: useRef.

    const key = useRef({}).current;   // actually stable for the
                                      // life of the fiber

  BROKEN -- a memo that does work:

    const conn = useMemo(() => openSocket(url), [url]);

  Two problems. First, if React discards and recomputes you open a
  second socket and never close the first. Second, useMemo has no
  cleanup -- nothing runs on unmount, so the socket outlives the
  component either way. Effects exist for this. useMemo must be PURE:
  compute and return, no I/O, no subscriptions, no setState.

  BROKEN -- a memo standing in for an id:

    const id = useMemo(() => Math.random(), []);   // use useId()

  ALSO NOT GUARANTEED: that the memo survives a remount. The cache
  lives in the fiber's hook slot. Unmount the component -- a route
  change, a key change, a conditional -- and the fiber is discarded
  along with everything memoized in it. useMemo is a per-instance,
  per-lifetime cache of exactly one entry. It is not a cache in the
  sense you mean when you say "cache".

  ONE ENTRY. This catches people too:

    const heavy = useMemo(() => compute(tab), [tab]);
    // tab: 'a' -> 'b' -> 'a'  recomputes THREE times.

  There is no LRU. Alternating between two values gives you a 0%
  hit rate and pure overhead.

The staleness failure mode is identical to the one in effect dependencies, and worse in one respect: an effect with a missing dependency does the wrong thing eventually, while a memo with a missing dependency shows the wrong thing on screen, right now, and keeps showing it until something unrelated changes.

  THE STALE MEMO:

    function Cart({ items, taxRate }) {
      const total = useMemo(
        () => sum(items) * (1 + taxRate),
        [items]                       // taxRate MISSING
      );
      ...
    }

  The user changes country. taxRate goes 0.08 -> 0.20. Cart
  re-renders -- the prop changed, React has no reason not to. But
  items did not change, so the memo returns the cached number
  computed with the OLD closure, which captured taxRate = 0.08.

  The user sees a total that is wrong by 12%. Nothing throws. It
  will correct itself the next time items changes, which makes the
  bug report read "sometimes the tax is wrong", which is the worst
  kind of bug report.

  WHY THE CLOSURE IS THE MECHANISM: the arrow you passed on the
  render where taxRate was 0.08 is the one that ran. Its scope
  chain still points at that render's variables. Every render
  after allocates a NEW arrow closing over the NEW taxRate -- and
  React throws each one away, because the deps said nothing changed.

  eslint-plugin-react-hooks/exhaustive-deps catches this for
  useMemo and useCallback exactly as it does for useEffect. Turn it
  on as an error. The suppression comment is a bug in waiting:

    // eslint-disable-next-line react-hooks/exhaustive-deps

Part 6 — Context Values, Comparators, and the Compiler

Three loose ends, in ascending order of how much they change your defaults.

  (1) CONTEXT VALUES -- CASE 2 IN DISGUISE.

  Context does not shallow-compare anything. A consumer re-renders
  when the provider's value is not Object.is-equal to the previous
  value, and memo() on the consumer DOES NOT SAVE IT -- context
  updates bypass the memo bailout entirely.

    <AuthCtx.Provider value={{ user, login, logout }}>

  New object literal, every provider render, so every consumer in
  the tree re-renders even when user is identical. In an app where
  auth sits at the root, that is a full-tree render on any root
  state change.

    const value = useMemo(
      () => ({ user, login, logout }), [user, login, logout]);

  This is a real case-2 memo -- but only if login and logout are
  themselves stable. If login is defined inline in the provider, the
  memo recomputes every render and you are back where you started.
  Memoization is all-or-nothing down the whole chain.

  THE BETTER FIX IS USUALLY TO SPLIT THE CONTEXT:

    <AuthStateCtx.Provider value={user}>        // changes rarely
      <AuthActionsCtx.Provider value={actions}> // never changes

  Components that only dispatch subscribe to the actions context
  and never re-render at all. No memo needed on the value, because a
  bare user object IS the value. Two providers beat one useMemo.

  (2) memo's SECOND ARGUMENT.

    const Row = memo(RowImpl, (prev, next) =>
      prev.item.id === next.item.id &&
      prev.item.updatedAt === next.item.updatedAt);

  Returns TRUE to SKIP the render. Note the polarity: it is
  arePropsEqual, not shouldUpdate -- the inverse of the old
  shouldComponentUpdate, and people invert it constantly. An
  inverted comparator produces a component that never updates,
  which looks like a data-fetching bug for about an hour.

  TWO REASONS TO AVOID IT.

  a) IT IS A SILENT STALENESS MACHINE. The comparator lists the
     props it cares about. Add a prop next sprint, forget the
     comparator, and that prop is now permanently ignored. The
     default shallow compare has no such failure mode -- it
     automatically covers every prop, including ones added later.

  b) DEEP EQUALITY USUALLY COSTS MORE THAN THE RENDER IT SAVES.

       component render (10 DOM nodes, no children)   ~0.02-0.05ms
       shallow compare, 6 props                       ~0.0002ms
       deep compare, nested object, ~50 keys          ~0.02-0.10ms

     A deep compare on a moderately nested prop is in the same
     bracket as the render. You have replaced a render with a
     traversal and gained nothing -- and you pay the traversal on
     EVERY render, including the ones that end in a re-render
     anyway, where it is pure loss.

  THE COMPARATOR IS DEFENSIBLE IN EXACTLY ONE SHAPE: a huge prop
  object where one cheap scalar field (id, version, updatedAt) is
  known to determine the whole thing. That is a version check, not
  a deep compare, and it is O(1).

  ALSO: children DEFEATS IT. <Row>{something}</Row> passes a fresh
  element object as props.children on every parent render, so a
  shallow compare always fails. A memo'd component that takes
  children rarely bails out.
  (3) THE REACT COMPILER (React 19).

  babel-plugin-react-compiler reads your components, infers what
  depends on what, and emits the memoization for you. Roughly:

    function Row({ item, onSelect }) {          // you write
      const label = format(item);
      return <li onClick={onSelect}>{label}</li>;
    }

    function Row({ item, onSelect }) {          // it emits
      const $ = _c(4);                          // per-fiber cache
      let label;
      if ($[0] !== item) { label = format(item); $[0] = item;
                           $[1] = label; }
      else               { label = $[1]; }
      let el;
      if ($[2] !== label || $[3] !== onSelect) { el = ...; ... }
      else { el = $[...]; }
      return el;
    }

  It memoizes at a finer grain than you would by hand -- individual
  expressions and JSX elements, not just whole values -- and it
  never forgets a dependency, because it computes them from the
  code rather than from your memory.

  WHAT IT MEANS IN PRACTICE:

    - It only transforms components it can PROVE follow the Rules
      of React. Mutate a prop, read a ref during render, call a
      hook conditionally -- it bails out of that component silently
      and emits it unchanged. The eslint plugin tells you where.
    - It does not remove your existing useMemo/useCallback and it
      does not conflict with them. They just become redundant.
    - It cannot know that a computation is expensive. It memoizes
      for identity, broadly. Case 1 -- the genuinely expensive
      sort -- is still worth an explicit useMemo, and the compiler
      docs say so.
    - Adoption is not universal. It is stable in React 19 tooling
      and shipping at Meta scale, but plenty of codebases are on
      18, or on build setups where the Babel plugin is awkward.
      Do not write code that assumes it.

  THE HONEST SUMMARY: the compiler makes case 2 obsolete and leaves
  case 1 alone. Since case 2 is where nearly all hand-written memos
  live, most of what this lesson warns you about becomes the
  compiler's problem -- IF you are on 19 and IF your components are
  clean enough for it to transform.

Interview Questions

Beginner: What is the difference between useMemo and useCallback?

useMemo calls the function you give it and caches the return value. useCallback does not call anything — it caches the function itself. Both re-do that work only when one of the dependencies changes, compared with Object.is, positionally.

They are the same mechanism. useCallback(fn, deps) is exactly useMemo(() => fn, deps), and in React's source useCallback is a copy of useMemo with the invocation removed. If that equivalence is clear, you never have to remember which is which.

The reason they feel different in practice is what you use them for. useMemo is usually about skipping work — a sort, a filter, an index. useCallback is almost never about work, because allocating a closure is nearly free; it is about keeping the reference the same so a downstream shallow comparison succeeds.

One thing that catches beginners: useCallback does not stop the arrow function from being created. The arrow is a plain JavaScript expression that is evaluated on every render before React sees it. What useCallback does is throw the new one away and hand back the old one.

Beginner: Is useMemo free when the dependencies have not changed?

No. On every render, whether or not the deps changed, you pay: one closure allocation for the arrow you pass, one array allocation for the deps literal, a hook-slot advance, and one Object.is call per dependency. Roughly 30–150 nanoseconds and two garbage objects.

That is small in isolation, which is why people call it free. It is not small relative to what it often protects. A template literal on two strings costs well under 100ns, so wrapping it in a memo is a straight net loss — plus a dependency array that can now go stale and mislead a reader into thinking a measurement happened.

The practical threshold: below about 0.1ms of computation, a memo always loses. Between 0.1 and 1ms it is noise unless it happens hundreds of times in a list. Above a few milliseconds it starts to matter, because 5ms is a third of a 16.7ms frame at 60Hz.

The exception to all of this is when you memoize for identity rather than for cost — case 2. There the computation may be free and you still want the memo, because something downstream compares the reference. Those are different justifications and it is worth saying which one you mean.

Mid: A colleague wraps every handler in useCallback. What do you tell them?

That it does nothing unless the receiving component is wrapped in memo. A plain component re-renders because its parent re-rendered — props are not a re-render trigger. React sees the same element type at the same position and calls the function again without consulting props at all. A stable onClick changes nothing about that.

So the code pays two allocations, a comparison and a dependency array per handler per render, and receives nothing. Worse, it looks like an optimisation, so the next reader assumes someone measured and leaves it alone. And if a dependency is ever missed, the stable reference now closes over stale variables — a correctness bug that the unmemoized version could not have.

The fix is one of two things, and "add more useCallback" is neither. Either memo the child, having confirmed in the Profiler that its render actually costs something — and then stabilise every prop, because one inline object defeats the whole shallow compare — or delete the useCallback. The second is right far more often.

I would also point at composition first. If the problem is that a heavy subtree re-renders with its parent, passing it as children often solves it with no memo at all, because the element object is created in the grandparent and simply forwarded. That is cheaper and cannot go stale.

And on React 19 with the compiler on, I would tell them to stop writing these entirely. The compiler does the identity memoization at a finer grain and never forgets a dependency.

Mid: Why is memoizing a context value different from memoizing a prop?

Because consumers cannot defend themselves. A component reading context re-subscribes to the provider, and when the provider's value is not Object.is-equal to the previous one, every consumer in the subtree re-renders. Wrapping a consumer in memo does not help — a context update bypasses the memo bailout, by design, because the component's own read has changed.

So value={{ user, login, logout }} written inline creates a new object on every provider render, and if the provider sits near the root, any root state change re-renders the whole application. That is one of the few cases where a missing memo has an app-wide effect rather than a local one.

useMemo on the value fixes it, but only if the deps are themselves stable — if login is defined inline in the provider, the memo recomputes every render and you have gained nothing. Memoization is all-or-nothing along the chain.

My preference is to split the context instead: one provider for the state that changes, one for the action functions that never do. Components that only dispatch subscribe to the actions context and stop re-rendering entirely, with no memo anywhere, because the value is a bare object created once. Two providers are less code than one useMemo plus a dependency chain you have to keep honest — and the split survives someone adding a field later.

Senior: When would you use memo's custom comparator, and when would you refuse?

Rarely, and I would want a specific shape before agreeing. The default shallow compare has two properties that are hard to beat: it is O(number of props) with a pointer compare each, so on the order of 0.0002ms, and it automatically covers props that do not exist yet. A custom comparator gives up both.

The staleness risk is the one that actually bites. A comparator enumerates the props it cares about. Someone adds a prop next quarter, does not know the comparator exists, and that prop is now permanently ignored — the component silently never updates for it. That bug is invisible in review and reproduces as "the badge doesn't refresh sometimes". The default compare cannot fail that way.

The cost argument goes the same direction. A deep equality check on a nested object of ~50 keys lands around 0.02–0.10ms, which is the same bracket as rendering a small component. You have swapped a render for a traversal — and you pay the traversal on the renders where it returns false too, which is pure loss. Deep-comparing to avoid a render is usually a rounding error at best and a regression at worst.

The one shape I accept is a version check: a large prop object where a single cheap scalar — id, updatedAt, a revision counter — provably determines the whole thing. That is O(1), it reads clearly, and it is stable under prop additions as long as the version is maintained server-side. I would still write a comment saying why the default was not enough.

My recommendation: default shallow compare, and if it is not bailing out, fix the props rather than the comparator. Nine times out of ten the culprit is an inline object or a children prop in the parent, and the honest fix is upstream. And if the answer to "why is this memo'd at all" is not a Profiler measurement, remove the memo along with the comparator.

Senior: React 19 ships a compiler that inserts memoization automatically. Do you still write useMemo?

For identity, no. For measured cost, yes. The compiler infers dependencies from the code rather than from a hand-written array, memoizes at a finer grain than a human would — individual expressions and JSX elements, not just whole values — and cannot forget a dependency. Every case-2 memo I would have written by hand is strictly better done by the compiler, and since case 2 is where nearly all hand-written memos live, most of the manual work disappears.

What it cannot do is know that something is expensive. It memoizes for referential stability, broadly and uniformly; it has no profiler. So a 12ms sort over 20,000 rows that re-runs when an unrelated tab changes is still worth an explicit useMemo, and React's own documentation says as much. Those are the memos I keep, and they are the ones that had a measurement behind them anyway.

The condition attached to all of it is Rules of React compliance. The compiler only transforms components it can prove are safe — no prop mutation, no ref reads during render, no conditional hooks. When it cannot prove that, it silently emits the component unchanged, which means a codebase with sloppy components gets partial coverage and no error. The eslint plugin is not optional; it is how you find out which components opted themselves out.

There is also an honest adoption caveat. It is stable in React 19 tooling and runs at Meta scale, but plenty of production code is still on 18, or on build setups where adding a Babel plugin is a fight. I would not write code that assumes the compiler is present.

My recommendation for a team on 19: turn the compiler and its lint rule on, delete hand-written useCallbacks and identity useMemos in the same pass so nobody is left reading two competing strategies, and keep exactly the memos that have a profiler number in the commit message. For a team on 18: keep the three cases, delete everything else, and make exhaustive-deps an error — that is most of the compiler's benefit for none of the migration.

🏋️ Graded Exercises

1 (easy): What does this memo accomplish? 
function Greeting({ first, last }) {
  const name = useMemo(() => `${first} ${last}`, [first, last]);
  return <h1>Hello {name}</h1>;
}
Solution

Nothing, at a small cost. A template literal on two short strings is well under 100ns. The memo around it allocates an arrow, allocates a deps array, advances a hook slot and runs two Object.is calls — roughly the same order of magnitude, in the wrong direction.

function Greeting({ first, last }) {
  return <h1>Hello {first} {last}</h1>;
}

There is a second reason beyond cost. The memoized value is a string, and strings are compared by value everywhere in JavaScript, so no downstream consumer could ever benefit from its reference being stable. Memoizing a primitive for identity is meaningless by construction — only objects, arrays and functions have identity worth preserving.

The general rule this exercise encodes: if you cannot say either "this takes N milliseconds" or "this reference is compared by X", the memo is decoration.

2 (easy): Why does this useCallback not stop Toolbar from re-rendering? 
function Page() {
  const [n, setN] = useState(0);
  const onSave = useCallback(() => save(), []);
  return (
    <div>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <Toolbar onSave={onSave} />
    </div>
  );
}
function Toolbar({ onSave }) { return <button onClick={onSave}>Save</button>; }
Solution

Toolbar is not wrapped in memo, so nothing ever compares its props. When Page re-renders, React finds a Toolbar element of the same type at the same position and calls the function. Props are not consulted in that decision. Changed props are not what causes a re-render — a parent rendering is.

const Toolbar = memo(function Toolbar({ onSave }) {
  return <button onClick={onSave}>Save</button>;
});

But the honest answer to this exercise is delete the useCallback, not add the memo. Toolbar renders one button; its render costs perhaps 0.01ms. Adding memo to save that is the same category of mistake as the memo in exercise 1 — you have added machinery to protect a cost you never measured.

3 (medium): The rows still re-render on every keystroke even though everything looks memoized. Why? 
const Row = memo(function Row({ item, onPick, theme }) { ... });

function List({ items }) {
  const [q, setQ] = useState('');
  const onPick = useCallback(id => select(id), []);
  const shown  = useMemo(
    () => items.filter(i => i.name.includes(q)), [items, q]);

  return shown.map(i =>
    <Row key={i.id} item={i} onPick={onPick} theme={{ dark: true }} />);
}
Solution

theme={{ dark: true }} is a fresh object on every render. memo does a shallow compare across all props and bails out only if every one passes. item and onPick are stable; theme fails Object.is every single time; the comparison returns false and every row renders.

So the useCallback is doing real work and getting no benefit from it, and you are now paying the shallow comparison on top of the render you were trying to avoid. Memoization is all-or-nothing across a prop boundary.

const THEME = { dark: true };          // module scope: one object, ever

function List({ items }) {
  ...
  return shown.map(i =>
    <Row key={i.id} item={i} onPick={onPick} theme={THEME} />);
}

Hoisting to module scope is the cheapest fix and beats useMemo here — the object does not depend on anything, so it does not need a per-instance cache at all. If it did depend on state, useMemo would be right. Better still for a theme: put it in context and read it in Row, so it stops being a prop that can break the compare.

The DevTools Profiler names the culprit directly. With "record why each component rendered" enabled, Row reports "Props changed: theme".

4 (medium): A user reports the total is "sometimes wrong". Find the bug and explain what runtime state produces it. 
function Invoice({ lines, taxRate, discount }) {
  const total = useMemo(() => {
    const sub = lines.reduce((s, l) => s + l.qty * l.price, 0);
    return (sub - discount) * (1 + taxRate);
  }, [lines, discount]);

  return <Total value={total} />;
}
Solution

taxRate is read inside the memo and missing from the deps. When taxRate changes and lines and discount do not, Invoice re-renders — the prop changed — but React compares the deps, finds them equal, and returns the previously cached number.

The mechanism is closure capture, and it is worth stating precisely. The arrow that actually ran was allocated on a render where taxRate was 0.08; its scope chain still points at that render's bindings. Every subsequent render allocates a new arrow closing over the new taxRate, and React discards each one unread. The cached number was computed by the old closure and stays until lines or discount moves.

const total = useMemo(() => {
  const sub = lines.reduce((s, l) => s + l.qty * l.price, 0);
  return (sub - discount) * (1 + taxRate);
}, [lines, discount, taxRate]);

That is why the report reads "sometimes". Changing the country alone shows a wrong total; editing a line afterwards silently corrects it, so the reproduction depends on the order of two unrelated actions. Nothing throws and no console warning appears.

eslint-plugin-react-hooks/exhaustive-deps flags this — it lints useMemo and useCallback exactly as it lints useEffect. Run it as an error, not a warning.

Then ask whether the memo should exist. A reduce over an invoice's line items is perhaps twenty iterations — call it 0.001ms. This memo protected nothing and cost a money bug. Deleting it is a defensible answer to this exercise, and the better one.

5 (hard): This "stable id" works in development and leaks in production. Explain both halves. 
function Chart({ series }) {
  const id = useMemo(() => ({}), []);        // "stable identity"
  useEffect(() => {
    chartRegistry.set(id, series);           // a Map, not a WeakMap
  }, [id, series]);
  return <canvas />;
}
Solution

Two independent defects: useMemo is not a guaranteed cache, and the effect has no cleanup.

React documents useMemo as a performance hint, not a semantic guarantee — it reserves the right to discard a cached value and recompute, for instance to free memory for offscreen content. If it does, id becomes a different object, the effect re-runs because id changed, and a second entry appears in the registry while the first is orphaned. Nothing in the code is prepared for the identity to change, which is precisely the assumption the API refuses to make.

The second defect stands on its own: the effect writes into a module-level Map and nothing ever deletes. Every mount adds an entry that outlives the component, holding the series data alive. Mount and unmount the chart across a hundred route changes and you have a hundred live entries. This is a leak regardless of the memo.

function Chart({ series }) {
  const id = useRef({}).current;             // genuinely stable
  useEffect(() => {
    chartRegistry.set(id, series);
    return () => { chartRegistry.delete(id); };
  }, [id, series]);
  return <canvas />;
}

Note the third row: neither survives a remount, because both live in the fiber's hook slots. If the registry must span mounts, the key has to come from the data — a series id — not from the component instance.

One more thing worth saying about useRef({}): the object literal is re-evaluated and thrown away on every render, since arguments are evaluated before the call. That is negligible here, but for an expensive object use useState(() => new Thing()), whose lazy initialiser runs exactly once.

6 (hard): A team on React 18 wants to "memoize everything" before migrating to 19. Write the argument you would make, and say what you would actually do. 
PROPOSAL: wrap every component in memo(), every handler in
useCallback, every derived value in useMemo. "It can only help,
and it gets us ready for the compiler."
Solution

Both halves of the premise are wrong. It can hurt, and it does not prepare you for the compiler.

On cost: every memo allocates a closure and a deps array and runs a comparison on every render, forever. Around 100ns and two garbage objects each. Spread over six memos in a row component across 500 rows, that is roughly 0.3ms of pure overhead per render plus 6,000 short-lived objects per pass, and the GC pressure is the part that shows up as jank rather than as a slow render.

On effectiveness: universal memo is mostly inert. Any component taking children gets a fresh element object every parent render, so its shallow compare always fails. Any component receiving one inline object or array fails the same way. You end up paying the comparison and rendering anyway — strictly the worst outcome.

On correctness: every dependency array added is a place a stale value can hide. Before the change, a missing dependency was impossible because there were no dependencies. Exercise 4 is what that looks like in a money path.

ClaimReality
"It can only help"Fixed per-render cost and allocation pressure with a mostly-zero hit rate
"memo everywhere is safe"Inert wherever children or an inline prop is passed; you pay the compare regardless
"It prepares us for the compiler"The compiler needs Rules-of-React compliance, not existing memos; the memos become dead weight to delete
"Memos have no downside"Each dep array is a staleness surface that did not exist before

What I would actually do, in order. First, turn on eslint-plugin-react-hooks with exhaustive-deps as an error — that is the highest-value change and it costs nothing at runtime. Second, profile one real interaction with "record why each component rendered" enabled and fix only what it names, which is usually two or three components, not two hundred.

Third, prefer composition over memo where it applies: passing a heavy subtree as children so its element is created in the grandparent removes the re-render with no hooks and no staleness risk. Fourth, fix the context providers — an inline provider value is one of the few missing memos with an app-wide blast radius.

Then, for the migration itself: the compiler's actual prerequisite is Rules of React compliance — no prop mutation, no ref reads during render, no conditional hooks — because it silently skips any component it cannot prove safe. Adopting the compiler's eslint plugin now and fixing what it reports is genuine preparation. Adding memos is not; those memos are what you delete on the day the compiler lands.

Recommendation: lint rule on, profile-driven fixes only, composition before memo, and keep a Profiler number in the commit message for every memo that survives. If a memo cannot cite a measurement or name the consumer that compares its reference, it does not ship.

🎯 Key Takeaways

  • useCallback(fn, deps) is exactly useMemo(() => fn, deps) — one mechanism, and useCallback simply skips the call.
  • A memo is never free — a closure allocation, an array allocation and one Object.is per dep, on every render, hit or miss.
  • Below ~0.1ms of computation, memoizing is a net loss; above ~5ms it is a third of a 60Hz frame and clearly worth it.
  • There are two separate reasons to memo — cost and identity — and you should be able to say which one you mean.
  • useCallback does nothing if the child is not memo'd; props do not trigger re-renders, parents do.
  • memo is all-or-nothing across the prop boundary — one inline object or array defeats the whole shallow compare.
  • A memo'd component that takes children almost never bails out, because props.children is a fresh element each render.
  • Only three cases pay: a measured expensive computation, a referential prop of a memo'd child, and an identity that drives an effect's dependencies.
  • The effect-dependency case is correctness, not speed — and the better fix is usually to move the function inside the effect.
  • useMemo is a hint React may discard, so it can never carry correctness — no Map keys, no resource handles, no ids.
  • A memo holds one entry and dies with the fiber — no LRU, and nothing survives a remount or a key change.
  • A missing dep in a memo shows wrong data on screen immediately, and self-corrects later, which makes it report as "sometimes wrong".
  • An inline provider value re-renders every consumer, and memo on consumers cannot stop it — context bypasses the bailout.
  • Splitting a context into state and actions beats memoizing its value and cannot go stale.
  • memo's comparator returns true to skip, silently ignores props added later, and deep equality usually costs as much as the render it prevents.
  • The React 19 compiler makes identity memos obsolete but not cost memos — it cannot know what is expensive, and it silently skips components that break the Rules of React.
  • Measure first is the actual rule: if a memo cannot cite a Profiler number or name the consumer comparing its reference, delete it.
