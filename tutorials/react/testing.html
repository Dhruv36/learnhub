Testing React Patterns & Quality

What you'll master: why a test that asserts on state or props fails on every refactor and stays green through real bugs; Testing Library's query ladder and the fact that its priority order is an accessibility audit wearing a different hat; the exact split between getBy, queryBy and findBy; why userEvent catches bugs fireEvent.change cannot, because it fires the whole pointer/focus/key sequence; why a setTimeout in a test is always a defect; mocking the network at the boundary with MSW so a data-layer swap does not break the suite; renderHook; and what not to test at all. Prerequisites: Custom Hooks and Data Fetching.

Part 1 — Test What the User Experiences

  THE ONE RULE, FROM KENT C. DODDS, WHO WROTE TESTING LIBRARY:

    "The more your tests resemble the way your software is used,
     the more confidence they can give you."

  That sounds like a slogan. It has a hard, checkable consequence:

    A TEST MAY ONLY TOUCH WHAT A USER OR A SCREEN READER CAN TOUCH.
    Rendered text, roles, labels, focus, what happens on click, what
    goes over the network. NOT state, NOT props, NOT method names,
    NOT the number of renders, NOT the class name on a div.

  WHY THE DISTINCTION IS NOT PEDANTRY. Every assertion you write is
  a promise you have to keep. Assert on a rendered price and you have
  promised "this component shows a price" — a promise worth keeping.
  Assert on state.priceCents and you have promised "this component
  keeps its price in a state variable named priceCents in minor
  units" — a promise nobody asked for, which the next refactor
  breaks for no user-visible reason.

  THE TWO FAILURE MODES OF AN IMPLEMENTATION-COUPLED TEST:

    FALSE NEGATIVE (breaks with no bug). You move the counter from
    useState to useReducer. Behaviour identical. 40 tests red. The
    team learns that red means "someone refactored", and starts
    updating tests without reading them.

    FALSE POSITIVE (green with a bug). The test asserts
    setCount was called with 1. It was. But the button is disabled
    by CSS, or covered by an overlay, or the value never reaches the
    DOM. The user cannot increment anything. The suite is green.

  THE SECOND ONE IS WHY THIS MATTERS. A brittle test is annoying.
  A test that passes while the feature is broken is worse than no
  test, because it buys confidence that was never earned.
  A WORKED CONVERSION. HERE IS THE BRITTLE VERSION — THE SHAPE
  ENZYME TAUGHT A GENERATION OF REACT DEVELOPERS TO WRITE:

    // BAD - couples to internals
    it('increments', () => {
      const wrapper = shallow(<Counter />);
      expect(wrapper.state('count')).toBe(0);
      wrapper.instance().handleIncrement();
      expect(wrapper.state('count')).toBe(1);
      expect(wrapper.find('.count-display').text()).toBe('1');
    });

  COUNT THE PROMISES IT MADE: the component is a class; it has state;
  the state key is 'count'; there is a method named handleIncrement;
  a node carries the class 'count-display'. FIVE promises, ZERO of
  which a user can observe. Convert to a function component with
  useState and every line breaks, though nothing changed on screen.

  AND IT NEVER CLICKED THE BUTTON. handleIncrement was called
  directly. If the button's onClick was wired to the wrong handler,
  or the button never rendered, this test is still green.

  THE BEHAVIOURAL VERSION:

    // GOOD - couples to the contract
    it('increments the count when the user clicks', async () => {
      const user = userEvent.setup();
      render(<Counter />);

      expect(screen.getByText('Count: 0')).toBeInTheDocument();
      await user.click(screen.getByRole('button', { name: /increment/i }));
      expect(screen.getByText('Count: 1')).toBeInTheDocument();
    });

  WHAT IT NOW PROMISES: the count is visible, there is a control a
  user can identify as "increment", clicking it raises the number.
  Class to function, useState to useReducer, Redux, a signal library
  — all pass. Break the onClick wiring and it fails. That is the
  whole trade you are making, and it is the right one.

Test it if you must, but keep those tests in a separate file, few in number, and expect to rewrite them when React changes. See Memoization for what is actually worth asserting.

Part 2 — The Query Ladder Is an Accessibility Audit

  TESTING LIBRARY PUBLISHES A PRIORITY ORDER FOR FINDING ELEMENTS.
  PEOPLE READ IT AS STYLE ADVICE. IT IS NOT.

    1. getByRole            <-- start here, ~90% of queries
    2. getByLabelText       <-- form fields
    3. getByPlaceholderText <-- only if there is no label
    4. getByText            <-- non-interactive copy
    5. getByDisplayValue
    6. getByAltText
    7. getByTitle
    8. getByTestId          <-- escape hatch, last

  THE MECHANISM. getByRole reads the ACCESSIBILITY TREE — the same
  structure a screen reader consumes — not the DOM. It resolves an
  element's implicit or explicit role and its ACCESSIBLE NAME, which
  is computed by the W3C "accname" algorithm: aria-labelledby, then
  aria-label, then the associated <label>, then the element's own
  text content, then title.

  SO THIS QUERY:

    screen.getByRole('button', { name: /save draft/i })

  FAILS in exactly the cases where an assistive-technology user is
  also stuck:

    <div onClick={save}>Save draft</div>
        -> no role. Not a button. Not focusable. No Enter/Space
           handler. Fails the query AND fails a keyboard user.

    <button><SaveIcon /></button>
        -> role button, accessible name "". Fails the query AND
           is announced as "button" with no indication of what it
           does.

    <input placeholder="Email" />   (no label)
        -> getByLabelText fails. A screen reader may read the
           placeholder, but it vanishes on typing for everyone.

  YOU DID NOT INSTALL AN ACCESSIBILITY LINTER. YOU JUST CANNOT
  ADDRESS THE ELEMENT, FOR THE SAME REASON A USER CANNOT. That is
  why the order is a priority and not a preference — dropping to
  getByTestId to "make it work" is silencing the alarm.
QueryUse forNote
getByRoleButtons, links, headings, inputs, checkboxes, dialogs, listsAlways pass { name }; the role alone is rarely unique
getByLabelTextForm controlsMatches <label for>, wrapping label, aria-label, aria-labelledby
getByPlaceholderTextInputs with no labelFinding it necessary is itself a bug report
getByTextParagraphs, spans, error copyDefault matcher normalises whitespace; strings match exactly, regex loosely
getByDisplayValueAsserting a filled-in form's current valueUseful for edit screens pre-populated from a server
getByAltTextMeaningful imagesDecorative images should have alt="" and be unfindable
getByTestIdCanvas, charts, third-party widgets with no semanticsEscape hatch. Justify each one in review
  ROLE OPTIONS DO MOST OF THE WORK PEOPLE REACH FOR TEST IDS FOR:

    getByRole('button',   { name: 'Delete' })
    getByRole('checkbox', { checked: true })
    getByRole('heading',  { level: 2 })
    getByRole('textbox',  { name: /email/i })
    getByRole('button',   { name: 'Submit', disabled: true })
    getByRole('option',   { selected: true })
    getByRole('button',   { name: 'Menu', expanded: false })

  THE NAME OPTION TAKES A STRING (EXACT, AFTER WHITESPACE
  NORMALISATION) OR A REGEX (SUBSTRING, CASE-INSENSITIVE WITH /i).
  Prefer regex for copy that may gain punctuation:

    { name: 'Save' }        breaks when the label becomes "Save…"
    { name: /save/i }       survives it

  WHEN A QUERY FAILS, TESTING LIBRARY PRINTS THE WHOLE DOM. That is
  usually enough. When it is not:

    screen.debug()                   print the container
    screen.debug(element, 30000)     print one node, bigger limit
    screen.logTestingPlaygroundURL() open the DOM in a query builder
    logRoles(container)              list every role it can see

  logRoles IS THE ONE TO REMEMBER. "getByRole('button') found no
  elements" plus a logRoles dump showing role="generic" tells you
  instantly that someone shipped a clickable div.

Part 3 — getBy vs queryBy vs findBy

  THREE PREFIXES, THREE BEHAVIOURS ON FAILURE. THIS IS THE MOST
  COMMON THING PEOPLE GET WRONG IN THEIR FIRST MONTH.

    getBy*    synchronous. THROWS if not found (test fails with a
              DOM dump). Throws if MORE than one matches.
    queryBy*  synchronous. Returns NULL if not found. Throws on
              multiple.
    findBy*   returns a PROMISE. Retries until found or the timeout
              (1000ms default). Rejects if it never appears.

  THE RULE THAT FOLLOWS FROM THAT:

    ASSERTING PRESENCE, ALREADY THERE   -> getBy
    ASSERTING ABSENCE                   -> queryBy
    ASSERTING PRESENCE, ARRIVES LATER   -> await findBy

  THE ABSENCE CASE IS THE TRAP:

    // WRONG - getByText throws before expect() ever runs. The
    // test fails, and the failure message talks about a missing
    // element instead of an unexpected one. Confusing red.
    expect(screen.getByText('Error')).not.toBeInTheDocument();

    // RIGHT
    expect(screen.queryByText('Error')).not.toBeInTheDocument();

  THE ASYNC CASE IS THE OTHER TRAP:

    // WRONG - runs on the first paint, before the fetch resolves.
    render(<Profile />);
    expect(screen.getByText('Ada Lovelace')).toBeInTheDocument();

    // RIGHT - retries until it appears or 1s elapses.
    render(<Profile />);
    expect(await screen.findByText('Ada Lovelace')).toBeInTheDocument();

  ALL THREE HAVE ...All VARIANTS: getAllBy, queryAllBy, findAllBy.
  These return ARRAYS and do not throw on multiple matches. If you
  hit "Found multiple elements", the fix is a more specific query
  (add { name }, or scope with within()) far more often than it is
  getAllBy(...)[0], which silently depends on DOM order.

    // scoping beats indexing
    const row = screen.getByRole('row', { name: /invoice 42/i });
    await user.click(within(row).getByRole('button', { name: /void/i }));
Not foundFound oneFound manyAsync
getByThrowsElementThrowsNo
queryBynullElementThrowsNo
findByRejects after timeoutElementRejectsYes
getAllByThrowsArray of 1ArrayNo
queryAllBy[]Array of 1ArrayNo
findAllByRejects after timeoutArray of 1ArrayYes
  ASYNC, AND WHY setTimeout IN A TEST IS ALWAYS WRONG.

  THE BROKEN PATTERN, WHICH EVERY CODEBASE HAS SOMEWHERE:

    await new Promise(r => setTimeout(r, 500));
    expect(screen.getByText('Saved')).toBeInTheDocument();

  IT IS WRONG IN BOTH DIRECTIONS AT ONCE:

    TOO SHORT on a loaded CI box. A shared runner under 8 parallel
    workers is routinely 5-10x slower than your laptop. 500ms
    becomes not enough, the test flakes, someone bumps it to 2000,
    and the suite gets slower forever.

    TOO LONG in the normal case. The DOM was ready at 20ms. You
    burned 480ms of wall clock. Multiply by 200 tests: eight
    minutes of pure sleeping per run.

  waitFor AND findBy POLL INSTEAD (default: every 50ms, up to
  1000ms), so they return as soon as the condition holds — usually
  within one interval — and only spend the full budget when
  something is genuinely wrong.

    // correct, and typically ~20ms
    expect(await screen.findByText('Saved')).toBeInTheDocument();

  findBy IS waitFor + getBy. THESE ARE THE SAME:

    await screen.findByText('Saved');
    await waitFor(() => screen.getByText('Saved'));

  So reach for waitFor only when the condition is NOT "an element
  appeared" — a mock was called, a URL changed, a value updated:

    await waitFor(() => expect(onSave).toHaveBeenCalledWith(draft));

  RULES FOR waitFor CALLBACKS:

    - ONE assertion per callback. Several means you cannot tell
      which one was still failing when it timed out.
    - NO side effects inside. The callback runs repeatedly; a
      user.click() in there can fire five times.
    - NEVER await inside it for something unrelated.

  DISAPPEARANCE HAS ITS OWN HELPER:

    await waitForElementToBeRemoved(() => screen.queryByRole('status'));

  It THROWS if the element was never there to begin with, which is
  the bug it exists to catch: a spinner that already vanished means
  your test raced past the loading state and proves nothing.
  THE act() WARNING, DECODED.

    Warning: An update to Profile inside a test was not wrapped
    in act(...)

  WHAT IT MEANS: React applied a state update that your test never
  awaited. The assertions ran against a DOM that React was still in
  the middle of changing. It is NOT a lint rule to silence — it is
  React telling you your test has a race in it.

  YOU ALMOST NEVER WRITE act() YOURSELF. render, userEvent methods,
  waitFor and findBy are already wrapped. The warning nearly always
  means one of:

    1. A promise resolved after the test's last await. Fix: await
       findBy/waitFor for the state it produces.
    2. The component updates on a timer. Fix: fake timers, below.
    3. The test finished while a request was still in flight, and
       the update landed during teardown. Fix: assert on the
       settled state before the test ends.

  FAKE TIMERS, WHEN THE COMPONENT ITSELF USES setTimeout — a
  debounced search box, an auto-dismissing toast:

    beforeEach(() => vi.useFakeTimers());
    afterEach(()  => vi.useRealTimers());

    const user = userEvent.setup({
      advanceTimers: vi.advanceTimersByTime,   // REQUIRED
    });

    await user.type(screen.getByRole('textbox'), 'react');
    await act(async () => { vi.advanceTimersByTime(300); });
    expect(await screen.findByText(/3 results/)).toBeInTheDocument();

  THE advanceTimers OPTION IS NOT OPTIONAL. userEvent has its own
  internal delay between keystrokes; with fake timers installed and
  no bridge, that delay never elapses and user.type() HANGS until
  the test times out. This single line is the fix for the most
  baffling hang in the whole library.

Part 4 — userEvent, Not fireEvent

  fireEvent DISPATCHES ONE SYNTHETIC DOM EVENT. userEvent SIMULATES
  WHAT A HUMAN ACTUALLY DOES, WHICH IS NEVER ONE EVENT.

  WHAT fireEvent.click(button) DISPATCHES:

    click

  WHAT user.click(button) DISPATCHES:

    pointerover, pointerenter, pointermove, pointerdown,
    mousedown, focus, pointerup, mouseup, click

  ...and before any of it, it CHECKS THE ELEMENT IS ACTUALLY
  CLICKABLE: not disabled, not pointer-events: none, not covered.

  THE BUGS THAT DIFFERENCE CATCHES, ALL OF WHICH ARE REAL:

    - A button with pointer-events: none from a CSS state. fireEvent
      clicks it happily. Users cannot. userEvent throws.
    - A dropdown that opens on mousedown and closes on blur. With
      fireEvent.click there was no mousedown and no focus change,
      so the flow never runs.
    - A disabled submit button. fireEvent.click fires the handler
      anyway — disabled buttons do not dispatch click in a browser,
      but fireEvent does not care. Your test proves nothing.
    - A tooltip on pointerenter. fireEvent.click never triggers it.

  TYPING IS THE STARKEST CASE:

    fireEvent.change(input, { target: { value: 'hello' } });
      -> ONE change event. Value jumps from '' to 'hello'.
         No keydown. No keyup. No input events. No per-character
         onChange. Length-based validation that runs on keyup never
         runs. A maxLength of 3 is not enforced. An input mask that
         reformats per keystroke is never exercised.

    await user.type(input, 'hello');
      -> click to focus, then per character: keydown, keypress,
         input (React's onChange), keyup. FIVE onChange calls.
         Masks, counters, debounce and maxLength all behave as they
         do in a browser.

  SETUP MATTERS (userEvent v14+, the current API):

    // WRONG - v13 style, no setup, methods are not awaited
    userEvent.click(button);

    // RIGHT - v14
    const user = userEvent.setup();   // once, at the top of the test
    await user.click(button);         // every call is awaited

  EVERY v14 METHOD RETURNS A PROMISE. Forget the await and the
  assertion runs before the event finishes — the classic "works
  when I add a console.log" flake, because logging changes the
  microtask timing just enough to hide it.
InteractionuserEvent (v14)What fireEvent misses
Clickawait user.click(el)pointer/mouse/focus sequence, disabled and covered checks
Typeawait user.type(el, 'abc')Per-character key and input events; masks, counters, maxLength
Clear and retypeawait user.clear(el) then typeSelection state; leftover text silently concatenates
Tabawait user.tab()Focus order entirely — the only way to test keyboard nav
Select optionawait user.selectOptions(sel, 'b')Correct change semantics for multi-selects
Uploadawait user.upload(input, file)A real FileList; hand-built ones fail validation code
Hoverawait user.hover(el)Tooltips, hover menus, prefetch-on-hover
Keyboardawait user.keyboard('{Enter}')Modifier state, Escape-to-close, Enter-to-submit
Pasteawait user.paste('text')Paste handlers, which differ from typing in real apps

fireEvent still has narrow uses: dispatching events with no user gesture behind them (scroll, resize, a message from a worker), or firing something userEvent does not model. That is the whole list. Everything a person does with a mouse, a keyboard or a finger goes through userEvent.

Part 5 — Mock at the Network Boundary

  YOU HAVE THREE PLACES YOU COULD PUT A FAKE. ONLY ONE SURVIVES A
  REFACTOR.

    COMPONENT ---> useUsers() hook ---> fetch/axios ---> NETWORK
                        ^                    ^              ^
                    (A) mock            (B) mock       (C) intercept
                    the hook            fetch          the request

  (A) MOCK THE HOOK — vi.mock('./useUsers'). You have now deleted
      the thing you wanted to test. The hook's key, its error
      mapping, its loading transitions: none of it runs. If the
      hook returns { data } and the component reads { items }, the
      test passes and production is blank.

  (B) MOCK fetch — global.fetch = vi.fn().mockResolvedValue(...).
      Better, but you are hand-rolling a Response: ok, status,
      headers, json(). Miss one and you are testing your fake. And
      the day someone swaps fetch for axios, or the app starts
      using it through a query library, every mock in the suite is
      wrong even though behaviour is unchanged.

  (C) INTERCEPT THE REQUEST — MSW. A Service Worker in the browser,
      a request interceptor in Node. Your app calls fetch for real.
      MSW answers. EVERYTHING between the component and the socket
      runs exactly as in production: the hook, the cache, retries,
      error mapping, the query library.

  THE TEST BECOMES INDEPENDENT OF YOUR CLIENT LIBRARY, because HTTP
  is the boundary that does not move. Swap fetch for axios, add
  TanStack Query, restructure the hooks — the handlers are untouched.

  THE SETUP, ONCE, IN A GLOBAL SETUP FILE:

    // src/mocks/handlers.js
    import { http, HttpResponse } from 'msw';

    export const handlers = [
      http.get('/api/users', () => HttpResponse.json([
        { id: 1, name: 'Ada Lovelace' },
      ])),
      http.post('/api/users', async ({ request }) => {
        const body = await request.json();
        return HttpResponse.json({ id: 2, ...body }, { status: 201 });
      }),
    ];

    // src/setupTests.js
    export const server = setupServer(...handlers);
    beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
    afterEach(() => server.resetHandlers());
    afterAll(() => server.close());

  onUnhandledRequest: 'error' IS THE SETTING THAT EARNS ITS KEEP. A
  request you did not plan for fails loudly instead of hanging until
  the test times out with an unhelpful message. It also catches the
  typo'd URL — /api/user vs /api/users — immediately.

  resetHandlers() AFTER EVERY TEST IS NOT OPTIONAL. A per-test
  override that leaks into the next test produces the worst class of
  flake: passes alone, fails in the suite, order-dependent.

  PER-TEST OVERRIDES ARE HOW YOU TEST THE SAD PATHS:

    it('shows a message when the server fails', async () => {
      server.use(
        http.get('/api/users', () =>
          new HttpResponse(null, { status: 500 })),
      );
      render(<UserList />);
      expect(await screen.findByText(/could not load/i)).toBeInTheDocument();
    });

    it('shows a spinner while loading', async () => {
      server.use(
        http.get('/api/users', async () => {
          await delay(100);
          return HttpResponse.json([]);
        }),
      );
      render(<UserList />);
      expect(screen.getByRole('status')).toBeInTheDocument();
      await waitForElementToBeRemoved(() => screen.queryByRole('status'));
    });

  THE SAME HANDLERS RUN YOUR DEV SERVER AND YOUR CYPRESS/PLAYWRIGHT
  SUITE. One definition of "what the API does", not three.

  PROVIDERS: WRAP ONCE, NOT IN EVERY TEST.

  Almost every real component needs a router, a query client, a
  theme, maybe an auth context. Do not paste the pyramid into 200
  files — override render:

    // test-utils.jsx
    function AllProviders({ children }) {
      const queryClient = new QueryClient({
        defaultOptions: { queries: { retry: false } },  // SEE BELOW
      });
      return (
        <QueryClientProvider client={queryClient}>
          <MemoryRouter>{children}</MemoryRouter>
        </QueryClientProvider>
      );
    }

    const customRender = (ui, options) =>
      render(ui, { wrapper: AllProviders, ...options });

    export * from '@testing-library/react';
    export { customRender as render };   // shadows the real one

  Then every test imports render from './test-utils' and gets the
  providers for free.

  retry: false IS THE LINE PEOPLE OMIT AND THEN LOSE A DAY TO. With
  default retries, an error-path test waits through three backoff
  attempts — several seconds — before your error UI ever renders,
  so findByText times out at 1000ms and the test fails while the
  code is correct.

  A FRESH QueryClient PER RENDER, NOT A MODULE-LEVEL ONE. A shared
  client carries cached data between tests: test 3 passes because
  test 1 populated the cache, and fails when run alone.

  TESTING HOOKS DIRECTLY, WITH renderHook:

    const { result, rerender } = renderHook(
      ({ id }) => useUser(id),
      { initialProps: { id: 1 }, wrapper: AllProviders },
    );

    expect(result.current.status).toBe('loading');
    await waitFor(() => expect(result.current.status).toBe('success'));
    expect(result.current.data.name).toBe('Ada Lovelace');

    rerender({ id: 2 });                    // change the input
    act(() => { result.current.reset(); }); // call a returned fn

  TWO RULES. result.current IS A SNAPSHOT — destructure it early
  and you hold a stale value forever, the single most common
  renderHook bug. And any call that sets state goes inside act().

  WHEN IS renderHook RIGHT? For a genuinely reusable hook with
  branches a component would not naturally exercise — useDebounce,
  usePagination, a published package. For a hook used by exactly one
  component, test the component: same coverage, and it also proves
  the wiring. See <a>Custom Hooks</a> for what belongs in a hook
  at all.

Part 6 — What to Test, What to Skip, and Where

  THE PYRAMID, WITH THE NUMBERS THAT ACTUALLY MATTER FOR A REACT
  APP. Ignore the drawings; here is the real trade:

                    /\        E2E (Playwright/Cypress)
                   /  \       5-20 tests | 10-60s each | high value,
                  /    \      high maintenance, real browser
                 /------\
                /        \    INTEGRATION (RTL, whole route,
               /          \   MSW, real providers)
              /            \  50-200 tests | 50-500ms each
             /--------------\ <-- SPEND MOST OF YOUR TIME HERE
            /                \
           /    COMPONENT     \ 200-800 tests | 5-50ms each
          /   (RTL, one unit)  \
         /----------------------\
        /   STATIC: TS + ESLint  \ instant, catches typos and
       /__________________________\ shape errors for free

  THE REACT-SPECIFIC CORRECTION TO THE CLASSIC PYRAMID: the middle
  layer should be the FATTEST, not the component layer. Kent Dodds
  calls this the "testing trophy" and the reasoning is sound —
  most React defects are wiring defects. The button works, the form
  works, the request works, but the form does not pass the id, or
  the success handler navigates to the wrong route. Only a test that
  renders the whole route with MSW behind it catches that.

  BUDGET GUIDE FOR A REAL SUITE: if `npm test` takes more than ~90
  seconds locally, people stop running it before pushing, and the
  suite's value collapses. That budget, not a coverage number, is
  what should shape the mix.

  WHAT NOT TO TEST, AND WHY EACH ONE IS WASTE:

    THIRD-PARTY LIBRARIES. Do not test that react-router navigates
    or that date-fns formats. They have their own suites. Test that
    YOUR code calls them with the right arguments and renders the
    result.

    IMPLEMENTATION DETAILS. Covered in Part 1. State shape, method
    names, render counts, internal helper functions that are not
    exported.

    GENERATED OR TRIVIAL MARKUP. A component that returns
    <div className={cls}>{children}</div> has no behaviour. A test
    for it asserts that JSX works.

    STYLES. toHaveStyle on a computed CSS property is a
    reimplementation of the stylesheet in JS. Visual regression
    tooling covers this; unit tests do not. The exception is style
    that IS behaviour — a disabled state, a hidden element.

    TYPES. TypeScript already proved the prop is a string. Do not
    write a test for it.

    COVERAGE PERCENTAGE AS A GOAL. 100% coverage means every line
    ran, not that any behaviour was verified. A test that renders a
    component and asserts nothing scores full marks. Use coverage
    to FIND untested branches — the error path nobody wrote a test
    for — not as a number to hit.
  SNAPSHOT TESTS: ONE GOOD USE, ONE COMMON ABUSE.

    it('renders', () => {
      const { container } = render(<Dashboard />);
      expect(container).toMatchSnapshot();   // 800 lines of HTML
    });

  WHAT ACTUALLY HAPPENS ON THE TEAM. Someone changes a wrapper div.
  Nine snapshots fail. The diff is 800 lines. Nobody can tell a
  real regression from noise, so they run `vitest -u`, the snapshots
  update, the tests go green, and a genuine bug ships inside the
  same commit. The test now asserts "the output is whatever the
  output currently is" — a tautology with a maintenance cost.

  SNAPSHOTS ALSO FAIL THE PART 1 TEST: they assert on markup, which
  is implementation, so they break on every cosmetic refactor.

  WHERE THEY DO EARN THEIR PLACE — SMALL AND INLINE:

    expect(formatMoney(1234.5, 'de-DE')).toMatchInlineSnapshot(
      `"1.234,50 €"`
    );

  The value is small, the diff is readable in the pull request, and
  the assertion is about OUTPUT, not markup. Serialised errors,
  formatted strings, a reducer's next state, a GraphQL variables
  object: good. A rendered page: bad.

  IF YOU KEEP A COMPONENT SNAPSHOT, keep it under ~30 lines and
  snapshot a fragment, not the page.

  ACCESSIBILITY ASSERTIONS WITH jest-axe:

    import { axe, toHaveNoViolations } from 'jest-axe';
    expect.extend(toHaveNoViolations);

    it('has no obvious a11y violations', async () => {
      const { container } = render(<SignupForm />);
      expect(await axe(container)).toHaveNoViolations();
    });

  BE HONEST ABOUT WHAT THIS BUYS YOU. Automated tooling catches
  roughly 30-40% of WCAG issues — missing labels, colour contrast
  where colours are computable, bad ARIA, duplicate ids, missing
  alt. It CANNOT tell you the focus order is illogical, the error
  message is unhelpful, or the modal traps focus badly. Those need
  a keyboard and a screen reader.

  on computed colours are unreliable there. Run axe in a real
  browser (Playwright's @axe-core/playwright) for the full set, and
  keep the jsdom version as a cheap regression net.

  ONE axe TEST PER PAGE-LEVEL COMPONENT AND PER FORM is the right

Interview Questions

Beginner: What is the difference between getBy, queryBy and findBy?

They differ in what happens when the element is not there. getBy throws immediately, printing the DOM — so it is the right choice for asserting something is present right now, because the failure message is excellent. queryBy returns null, which is the only correct way to assert absence. findBy returns a promise that retries (every 50ms, up to 1000ms by default) until the element appears or the timeout expires.

The two errors that follow from this are almost universal in new suites. Writing expect(screen.getByText('Error')).not.toBeInTheDocument() can never pass or fail meaningfully: if the text is absent — the case you wanted — getByText throws before expect runs. And using getBy for content that arrives after a request means the query runs on the first paint, before the promise resolves.

findBy is exactly waitFor wrapped around getBy. So use findBy whenever the condition is "an element appeared", and save waitFor for conditions that are not about elements — a mock having been called, a URL having changed.

All three have All variants that return arrays and do not throw on multiple matches. If you hit "found multiple elements", prefer narrowing the query — add { name }, or scope with within(row) — over indexing into getAllBy(...)[0], which quietly depends on DOM order and breaks when the list is reordered.

Beginner: Why does Testing Library push you towards getByRole?

Because getByRole queries the accessibility tree rather than the DOM. It resolves an element's role and its accessible name using the same W3C algorithm a screen reader uses: aria-labelledby, then aria-label, then an associated <label>, then text content, then title.

The consequence is that the query fails in precisely the situations where an assistive-technology user is also blocked. A <div onClick> has no button role, is not focusable and has no keyboard handler — the query fails, and so does a keyboard user. An icon-only button has the button role but an empty accessible name — the query cannot address it, and a screen reader announces "button" with no idea what it does.

So the priority list is not a style preference. It is a cheap accessibility check that runs in your existing test suite. When a role query fails, the fix is nearly always in the component — add a real <button>, add an aria-label, associate the label with the input — not in the test.

Which is exactly why dropping to getByTestId when a role query fails is the wrong instinct. The test id will work, and the defect ships. Keep test ids for things with genuinely no semantics: a canvas, a chart, a third-party widget you do not control.

Mid: Why prefer userEvent over fireEvent, concretely?

fireEvent.click dispatches one click event. userEvent.click dispatches the sequence a browser produces — pointerover, pointerenter, pointermove, pointerdown, mousedown, focus, pointerup, mouseup, click — and first checks the element is actually interactable: not disabled, not pointer-events: none.

That difference is not academic. fireEvent.click will happily fire the handler on a disabled button, which a real browser never does — so the test proves something false. A dropdown that opens on mousedown and closes on blur never runs its flow under fireEvent. A tooltip bound to pointerenter never appears.

Typing is starker. fireEvent.change(input, {target:{value:'hello'}}) sets the value in one jump with no key events at all. Any per-keystroke logic — an input mask, a character counter, a debounce, maxLength — is skipped entirely, and your test asserts on a state the user can never reach. user.type fires keydown/keypress/input/keyup per character, so onChange runs five times for "hello", as it does in production.

Two practical notes on v14: call userEvent.setup() once at the top of the test and await every method, or assertions run mid-interaction and you get flakes that disappear when you add a console.log. And with fake timers, pass advanceTimers or user.type hangs forever. fireEvent remains correct for events with no user gesture behind them — scroll, resize, a worker message.

Mid: Why is an arbitrary setTimeout in a test always wrong?

Because you are guessing at a duration that is simultaneously too long and too short. On your laptop the DOM was ready at 20ms and you burned the remaining 480ms; across 200 tests that is eight minutes of the suite doing nothing. On a CI runner with eight workers competing for cores — routinely 5-10x slower — the same 500ms is not enough, the test flakes, and someone bumps it to 2000ms, which makes the first problem permanent.

waitFor and findBy poll instead: they re-run the condition on an interval (50ms by default) and return the moment it holds, spending the full 1000ms budget only when something is genuinely wrong. Fast in the good case, and the failure message tells you what was still failing.

There is a real case that looks like it needs a sleep: the component itself uses timers — a debounced search, an auto-dismissing toast. The answer there is fake timers, not a real sleep. Install vi.useFakeTimers(), wire userEvent.setup({ advanceTimers: vi.advanceTimersByTime }), then advance time explicitly inside act. That makes the debounce deterministic and instant.

A sleep also hides the act() warning rather than fixing it. The warning means React applied an update your test never awaited, so your assertions raced the render. Sleeping long enough usually makes it go away, which is why people do it — and why the race quietly comes back on a slow machine.

Senior: Where should you mock the network, and what does the choice cost you?

There are three candidate boundaries: your data hook, the HTTP client, or the request itself. The guiding question is how much of your own code still runs afterwards.

Mocking the hook (vi.mock('./useUsers')) deletes the thing worth testing. The hook's key construction, its error mapping, its loading transitions — none of it executes. Worse, the mock and the real hook can disagree about shape: the mock returns { data }, the real hook returns { items }, the test is green and production renders blank. That failure mode is the reason to avoid it, not the purity argument.

Mocking fetch is better but couples the suite to a client library. You hand-roll a Response — ok, status, headers, json() — and miss one field, so you end up testing your fake. And the day the app adopts axios or a query library, every mock is wrong even though nothing user-visible changed.

MSW intercepts at the request layer, so your app calls fetch for real and everything between component and socket runs: client, cache, retry policy, error mapping, hook. The boundary is HTTP, which does not move when you refactor — and the same handlers drive your dev server and your E2E suite, so there is one definition of what the API does instead of three.

The honest costs: an extra dependency and setup file; a small startup cost per suite; and handlers that can drift from the real API, because MSW does not know your backend changed. Mitigate the last one by generating handlers from an OpenAPI or GraphQL schema where you have one, and by keeping a handful of contract or E2E tests that hit a real environment.

Recommendation: MSW as the default, with onUnhandledRequest: 'error' so an unplanned request fails loudly instead of hanging, and resetHandlers() after every test so per-test overrides cannot leak. Mock a component only for heavy third-party widgets — maps, rich-text editors — that jsdom cannot render anyway.

Senior: How would you decide the test mix for a React app, and where does coverage fit?

Start from the defects you actually ship. In most React codebases they are wiring defects, not logic defects: the button works, the form works, the request works, but the form does not pass the id, or the success handler navigates to the wrong route. A pure unit test of each part passes; only a test that renders the whole route with a fake network behind it catches the seam.

So I invert the classic pyramid's middle: the fattest layer is integration — render a route with real providers and MSW, drive it with userEvent, assert on what the user sees. Component tests below it for genuinely reusable pieces with branchy behaviour. A small number of E2E tests, 5 to 20, covering the flows the business cannot afford to break — signup, checkout — because they are slow and the maintenance is real. TypeScript and ESLint underneath, catching shape errors for free.

The constraint I actually manage to is wall-clock time. Once npm test passes about 90 seconds locally, people stop running it before pushing and the suite's value collapses. That budget shapes the mix more honestly than any ratio: it is what pushes an expensive axe check to one per page rather than one per component.

Coverage is a diagnostic, not a goal. 100% means every line executed, not that any behaviour was verified — a test that renders a component and asserts nothing scores full marks. What coverage is genuinely good at is showing you the branch nobody thought about, which is nearly always the error path. I read the report to find untested branches; I do not gate merges on a percentage, because the cheapest way to move that number is to write worthless tests.

Where the ecosystem honestly disagrees: some teams get real value from a strict coverage gate on critical modules, and shallow rendering still has defenders for very large component trees. I would also concede that snapshot tests work fine on disciplined teams who read the diffs — the failure mode is social, not technical.

Recommendation: integration-heavy with MSW, a 90-second local budget as the real constraint, coverage as a report rather than a gate, and a hard rule that every production incident becomes a failing test before it is fixed. That last rule shapes the suite around what actually breaks better than any target.

});

Two things changed. The input is found by its accessible name, so the test also fails if the label is missing — a defect a screen-reader user would hit. And the error is asserted as rendered text, so the whole path from keystroke to visible message is covered. findByText rather than getByText because validation may be async.

3 (medium): A search box debounces at 300ms. This test hangs and fails after the 5s test timeout, with no useful message. Find the cause. 
beforeEach(() => vi.useFakeTimers());
afterEach(()  => vi.useRealTimers());

it('searches after the debounce', async () => {
  const user = userEvent.setup();
  render(<Search />);
  await user.type(screen.getByRole('textbox'), 'react');
  vi.advanceTimersByTime(300);
  expect(await screen.findByText(/3 results/)).toBeInTheDocument();
});
Solution

userEvent puts a small delay between keystrokes using the global timer functions. Fake timers replaced those, and nothing is advancing them, so the delay after the first character never elapses. user.type never resolves — the hang happens before advanceTimersByTime is ever reached.

const user = userEvent.setup({
  advanceTimers: vi.advanceTimersByTime,    // the fix
});

render(<Search />);
await user.type(screen.getByRole('textbox'), 'react');
await act(async () => { vi.advanceTimersByTime(300); });
expect(await screen.findByText(/3 results/)).toBeInTheDocument();

The advanceTimers option tells userEvent how to push the fake clock forward for its own waits. The second change matters as well: advancing timers triggers the debounced callback, which sets state, so it belongs inside act — otherwise you get the "not wrapped in act" warning and assertions that race the render.

Solution

Three separate defects, and the error message points at the least important one.

Stale snapshot. result.current is the value from the render that happened at that moment. Destructuring copies count as the number 0, taken before increment ran. State updates outside act. increment() and reset() set state. Called bare, React warns and the assertions may run before the re-render commits.

Nothing async here. The async keyword with no await is noise that suggests a timing problem the test does not have.

🎯 Key Takeaways

  • A test may only touch what a user or a screen reader can touch — rendered output, roles, focus, network. Not state, props, method names or render counts.
  • The dangerous failure of an implementation-coupled test is the false positive: it stays green while the button is disabled, covered, or wired to nothing.
  • getByRole's priority is an accessibility audit — the query fails in exactly the cases where an assistive-technology user is blocked.
  • Reaching for getByTestId when a role query fails silences a real defect; fix the semantics instead.
  • getBy throws, queryBy returns null, findBy awaits — absence assertions need queryBy or they can never pass.
  • findBy is waitFor + getBy; use bare waitFor only for conditions that are not "an element appeared".
  • A setTimeout in a test is too slow locally and too short on CI — polling returns in ~20ms and only spends its budget when something is wrong.
  • One assertion per waitFor callback, and no side effects inside it — the callback re-runs.
  • The act() warning is a race report, not lint noise: an update landed after your last await.
  • user.click fires nine events and checks the element is interactable; fireEvent.click fires one and will click a disabled button.
  • fireEvent.change skips every keystroke, so masks, counters, debounce and maxLength are never exercised.
  • Fake timers without advanceTimers make user.type hang until the test times out.
  • Mock at the HTTP boundary, because HTTP is the boundary that does not move — mocking your own hook deletes the code under test.
  • onUnhandledRequest: 'error' and resetHandlers() are what keep an MSW suite honest; leaked overrides are order-dependent flakes.
  • A fresh QueryClient per render with retry: false — a shared client leaks cache, and default retries time out your error tests.
  • result.current is a snapshot; destructure it early and you assert on a value that can never change.
  • Whole-page snapshots get rubber-stamped with -u — keep snapshots small, inline, and about values rather than markup.
  • Automated axe catches 30-40% of accessibility issues, and none of the ones about focus order or message quality.
  • Coverage finds untested branches; it does not measure verification — a test that asserts nothing scores 100%.
  • Integration is the fattest layer for React, because most React defects are wiring defects, and every production incident should become a failing test first.
