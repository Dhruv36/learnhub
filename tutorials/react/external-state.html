External Stores (Redux, Zustand) State Management

What you'll master: the one thing an external store gives you that context cannot — selective subscription, so a component re-renders only when the slice it reads actually changes; useSyncExternalStore as the primitive every store now sits on, and tearing as the reason React had to provide it; Redux Toolkit as it is actually written today rather than its 2016 reputation; why returning a new object from a selector loops forever, and the equality-function fix; Zustand, Jotai and MobX compared on subscription granularity rather than syntax; middleware and persistence; and the honest verdict that most apps need a server-cache library plus local state and reach for a client store far earlier than they should. Prerequisites: State Architecture, Context.

Part 1 — What a Store Is, and the One Thing Context Cannot Do

  AN EXTERNAL STORE IS TWO THINGS AND NOTHING MORE:

    1. STATE THAT LIVES OUTSIDE THE REACT TREE
    2. A SUBSCRIPTION LIST

  You can write one in fifteen lines, and doing so makes every library
  that follows obvious:

    function createStore(initial) {
      let state = initial;
      const listeners = new Set();
      return {
        getState: () => state,
        setState(fn) {
          state = fn(state);
          listeners.forEach(l => l());     // tell everyone something changed
        },
        subscribe(listener) {
          listeners.add(listener);
          return () => listeners.delete(listener);
        },
      };
    }

  Redux, Zustand and MobX are all elaborations on this. The interesting
  question is never "how is state stored" — it is WHO GETS NOTIFIED.
  THE CONTEXT PROBLEM. Context is a broadcast, not a subscription. Every
  consumer re-renders when the provider's value changes, no matter which
  part of it they read.

    const AppContext = createContext();
    <AppContext.Provider value={{ user, theme, notifications, cart }}>

    Header      reads value.user
    ThemeToggle reads value.theme
    Bell        reads value.notifications
    CartBadge   reads value.cart

  A notification arrives. notifications changes, so the object identity
  changes, so ALL FOUR RE-RENDER — including ThemeToggle, which cares
  about nothing that happened.

    CONTEXT                          STORE
    ---------------------------------------------------------------
    provider value changes           store state changes
    -> every consumer re-renders     -> each subscriber runs its selector
                                     -> re-renders ONLY if its slice changed

  THIS IS THE ENTIRE PITCH. Not "global state" — context is already
  global state. SELECTIVE SUBSCRIPTION.

  The usual workaround is splitting into many contexts — UserContext,
  ThemeContext, CartContext — and it genuinely works. It stops working
  when slices are numerous or dynamic: you cannot spin up a context per
  row in a 500-row table, but a store subscription per row is routine.

Part 2 — useSyncExternalStore, and the Tearing It Exists to Prevent

  BEFORE REACT 18, stores subscribed with useEffect + useState. That was
  fine while rendering was synchronous and uninterruptible. Concurrent
  rendering broke it, and the failure has a name: TEARING.

  TEARING IS ONE SCREEN SHOWING TWO DIFFERENT VALUES OF THE SAME STATE.

    Store value: 5

    React begins a concurrent render of a list of three components:

      t=0   ComponentA renders, reads store -> 5
      t=1   React YIELDS to the browser (concurrent rendering is
            interruptible — this is the whole point of it)
      t=2   an event handler or a timer calls store.setState -> 6
      t=3   React resumes the SAME render pass
      t=4   ComponentB renders, reads store -> 6
      t=5   ComponentC renders, reads store -> 6

      COMMITTED SCREEN:   A shows 5.   B and C show 6.

  One paint, two truths. No error, no warning — just a UI that is
  internally inconsistent, usually intermittently, usually under load.
  This was not possible in React 17 because a render could not be
  interrupted partway.

  useSyncExternalStore is React's answer:

    const value = useSyncExternalStore(
      store.subscribe,       // (cb) => unsubscribe
      store.getState,        // read the current value
      store.getServerState   // optional: SSR / hydration snapshot
    );

  It opts the component OUT of concurrent tearing by forcing a
  synchronous re-read and, if the value moved mid-render, discarding the
  in-progress render and starting again with the fresh value. You pay a
  little concurrency for consistency, which for external state is the
  right trade.

  YOU ALMOST NEVER CALL THIS YOURSELF. Redux, Zustand, Jotai and MobX all
  sit on it. It matters because it explains WHY you should not hand-roll
  a store subscription with useEffect in React 18 — the naive version has
  a real, subtle bug that only appears under concurrent features.
  THE THIRD ARGUMENT IS NOT OPTIONAL UNDER SSR. Without
  getServerSnapshot, server rendering throws outright. And the second
  argument has a trap of its own:

    // BROKEN — new array identity every call
    useSyncExternalStore(sub, () => store.getState().items.filter(i => i.done));

  getSnapshot must return a value that is REFERENTIALLY STABLE when
  nothing changed. React calls it during render and compares with
  Object.is; a fresh array every time means "changed" every time, which
  means an infinite loop and React's "getSnapshot should be cached"
  warning. This is the same defect as the selector loop in Part 4 — it is
  worth recognising that they are one bug wearing two hats.

Part 3 — Redux Toolkit as It Is Actually Written Today

  REDUX'S REPUTATION IS A DECADE OUT OF DATE. The boilerplate everyone
  remembers — action type constants, action creators, switch reducers,
  three files per feature, hand-written immutable spreads — is not how
  anyone writes it now. Redux Toolkit is the official API, and it is a
  different experience.

  2016 REDUX, one counter feature:

    const INCREMENT = "counter/INCREMENT";                 // constants file
    export const increment = () => ({ type: INCREMENT });  // actions file
    export default function reducer(state = { value: 0 }, action) {
      switch (action.type) {                                // reducer file
        case INCREMENT: return { ...state, value: state.value + 1 };
        default: return state;
      }
    }

  MODERN REDUX TOOLKIT, same feature, one file:

    const counter = createSlice({
      name: "counter",
      initialState: { value: 0 },
      reducers: {
        increment(state) { state.value += 1; },      // LOOKS like mutation
        addBy(state, action) { state.value += action.payload; },
      },
    });
    export const { increment, addBy } = counter.actions;   // generated
    export default counter.reducer;

  state.value += 1 is NOT mutation. createSlice wraps every reducer in
  Immer, which hands you a PROXY DRAFT. Immer records the writes you make
  against the draft and produces a new immutable state with structural
  sharing — untouched branches keep their identity, so memoised selectors
  and React.memo downstream still bail out correctly.

  THE ONE IMMER RULE THAT BITES: mutate the draft OR return a new value,
  never both in the same reducer.

    // WRONG — Immer cannot tell which you meant, and throws
    reducers: {
      reset(state) { state.value = 0; return { value: 0 }; }
    }
  RTK QUERY is the part people miss, and it is usually the strongest
  reason to pick Redux Toolkit at all:

    const api = createApi({
      baseQuery: fetchBaseQuery({ baseUrl: "/api" }),
      tagTypes: ["Project"],
      endpoints: (build) => ({
        getProjects: build.query({
          query: () => "/projects",
          providesTags: ["Project"],
        }),
        addProject: build.mutation({
          query: (body) => ({ url: "/projects", method: "POST", body }),
          invalidatesTags: ["Project"],       // refetch happens for you
        }),
      }),
    });

    const { data, isLoading, error } = api.useGetProjectsQuery();

  That is caching, deduplication, background refetch, and tag-based
  invalidation — the same job TanStack Query does, already integrated
  with the store and its devtools. If you are choosing Redux Toolkit
  today and NOT using RTK Query, ask yourself what you are getting that a
  200-line Zustand store would not give you.
  WHAT SURVIVES REDUX INDEPENDENT OF THE LIBRARY — these are ideas worth
  keeping even if you never install it:

    SINGLE SOURCE OF TRUTH   one state tree, so "what is the app's state
                             right now" has exactly one answer

    PURE REDUCERS            (state, action) => state, no I/O, no
                             randomness. Trivially unit-testable with no
                             mounting, no mocks, no React at all

    SERIALISABLE ACTIONS     every change is a plain object you can log,
                             replay, ship in a bug report, or diff

    UNIDIRECTIONAL FLOW      dispatch -> reducer -> new state -> render.
                             One direction, so "why did this change" is
                             answerable

  TIME-TRAVEL DEBUGGING FALLS OUT OF THOSE FOUR. If actions are
  serialisable and reducers are pure, replaying a user's action log
  reproduces their exact state. On a complex internal tool that is a
  genuinely decisive capability, and it is the one thing no other option
  on this page matches.

Part 4 — Selectors, and the New-Object Infinite Loop

  A SELECTOR IS A FUNCTION FROM STORE STATE TO THE SLICE A COMPONENT
  NEEDS. It is how selective subscription actually happens:

    const count = useSelector(state => state.cart.items.length);

  After every dispatch the store runs your selector and compares the
  result with the previous one using Object.is. Equal means no
  re-render. So a component reading items.length ignores every change
  that does not alter the count.

  NOW THE BUG EVERY TEAM HITS EXACTLY ONCE:

    // INFINITE LOOP
    const { user, theme } = useSelector(state => ({
      user: state.user,
      theme: state.theme,
    }));

  The selector allocates a NEW OBJECT on every call. Object.is compares
  identity, not contents, so:

    dispatch -> run selector -> new object -> !Object.is(prev, next)
      -> "changed!" -> re-render -> run selector -> new object -> ...

  React eventually bails out with "Maximum update depth exceeded", or in
  Redux with a "selector returned a different result" warning. The
  contents were identical every single time; only the wrapper was new.

  THE SAME BUG WITH ARRAYS, WHICH IS EVEN EASIER TO WRITE:

    const done = useSelector(state => state.todos.filter(t => t.done));
    //                                            ^ new array, always
  FOUR FIXES, IN THE ORDER YOU SHOULD REACH FOR THEM:

  1. SELECT PRIMITIVES SEPARATELY — no equality function needed, and
     usually the right answer:

       const user  = useSelector(s => s.user);
       const theme = useSelector(s => s.theme);

     Two subscriptions is not a performance problem. This is the boring
     fix and it is nearly always correct.

  2. SHALLOW EQUALITY when you genuinely want an object:

       // Zustand
       const { user, theme } = useStore(useShallow(s => ({
         user: s.user, theme: s.theme,
       })));

       // Redux
       import { shallowEqual } from "react-redux";
       const slice = useSelector(selectSlice, shallowEqual);

     Compares one level of keys by identity, so a new wrapper around
     unchanged values counts as equal.

  3. MEMOISE THE DERIVATION with createSelector (reselect, bundled with
     RTK) when the computation is expensive OR the result is a new
     collection:

       const selectDone = createSelector(
         [(s) => s.todos],
         (todos) => todos.filter(t => t.done)   // recomputed only if
       );                                        // todos changed identity

  4. DERIVE OUTSIDE THE SELECTOR when it is cheap:

       const todos = useSelector(s => s.todos);   // stable reference
       const done = todos.filter(t => t.done);    // recomputed per render,
                                                  // which is usually fine

  A NOTE ON createSelector: its default cache size is ONE. Two components
  calling the same memoised selector with different arguments thrash it —
  each call evicts the other's entry and nothing is ever cached. Use
  createSelector's cache options or a per-instance selector factory when
  a selector is parameterised.

Part 5 — Zustand, and Why Its API Is So Much Smaller

  ZUSTAND IS THE FIFTEEN-LINE STORE FROM PART 1 WITH A HOOK BOLTED ON.
  There is no provider, no dispatch, no action type, no context.

    import { create } from "zustand";

    const useCart = create((set, get) => ({
      items: [],
      addItem: (item) => set((s) => ({ items: [...s.items, item] })),
      removeItem: (id) =>
        set((s) => ({ items: s.items.filter(i => i.id !== id) })),
      clear: () => set({ items: [] }),
      total: () => get().items.reduce((n, i) => n + i.price, 0),
    }));

    function CartBadge() {
      const count = useCart(s => s.items.length);   // subscribes to length
      return <span>{count}</span>;
    }

  WHY THE API IS SMALL: Redux separates WHAT HAPPENED (the action) from
  HOW STATE CHANGES (the reducer), and that separation is what buys the
  serialisable log and time travel. Zustand collapses them — the updater
  function is both. You lose the action log; you delete most of the
  concepts.

  set MERGES AT THE TOP LEVEL, like this.setState in class components —
  it is a shallow merge, not a deep one. Nested updates are still your
  problem, which is why the immer middleware exists:

    import { immer } from "zustand/middleware/immer";
    const useStore = create(immer((set) => ({
      user: { profile: { name: "" } },
      setName: (name) => set((s) => { s.user.profile.name = name; }),
    })));

  OUTSIDE REACT, no hook required — useful in event handlers, websocket
  callbacks, tests, and anywhere else:

    useCart.getState().addItem(item);
    const unsub = useCart.subscribe((s) => console.log(s.items.length));

  THE SELECTOR RULE FROM PART 4 APPLIES UNCHANGED. Zustand's default
  equality is Object.is, so returning a fresh object loops in exactly the
  same way — which is what useShallow is for.

Part 6 — Middleware, Persistence, and When Not to Install Any of This

  MIDDLEWARE WRAPS THE UPDATE PATH, so cross-cutting concerns live in one
  place instead of in every action:

    // Zustand: middleware are function wrappers, composed outside-in
    const useStore = create(
      devtools(
        persist(
          immer((set) => ({ ... })),
          {
            name: "cart",                        // localStorage key
            partialize: (s) => ({ items: s.items }),   // never persist
                                                       // functions or
                                                       // ephemeral flags
            version: 2,
            migrate: (persisted, from) =>
              from === 1 ? upgradeV1(persisted) : persisted,
          }
        )
      )
    );

  THREE PERSISTENCE RULES THAT ARE LEARNED THE HARD WAY:

    PARTIALIZE ALWAYS.  Persisting the whole store writes transient flags
                        and stale server data to disk. Users then load a
                        month-old cart from localStorage and report it as
                        a backend bug.

    VERSION FROM DAY 1. Shipped state shapes live in your users' browsers
                        indefinitely. Without version + migrate, your
                        next refactor crashes on hydration for everyone
                        who used the old build — and they cannot clear it
                        for you.

    HYDRATION IS ASYNC-ISH. With SSR the server render has no
                        localStorage, so the first client render must
                        match the server's, then swap. Rendering
                        persisted state directly on the first pass is a
                        hydration mismatch.

  REDUX MIDDLEWARE IS THE SAME IDEA in the classic
  store => next => action => ... signature: logging, analytics,
  crash reporting, optimistic updates, and the serialisability check RTK
  turns on by default in development.
  THE HONEST VERDICT, AND IT IS THE MOST USEFUL THING ON THIS PAGE:

  MOST STATE IN MOST APPS IS SERVER STATE — data that lives in a
  database, arrives over HTTP, and can be stale. It needs caching,
  deduplication, background refetch, and invalidation. A client store
  provides NONE of that. Putting server data in Redux means you
  hand-write a cache, badly, and then maintain it.

    ORDER OF ADOPTION THAT ACTUALLY HOLDS UP:

      1. useState / useReducer          most things, most of the time
      2. Lift, or compose with children  before reaching for anything global
      3. URL                             filters, sort, page, open record
      4. Context                         theme, locale, current user
      5. TanStack Query / RTK Query      EVERYTHING from the server
      6. A client store                  what genuinely remains

    What remains at step 6 is smaller than teams expect: cross-cutting
    UI state (a command palette, multi-step wizard state, an undo stack,
    a canvas selection, a websocket connection status). Often a few
    hundred lines.

  TEAMS INSTALL A STORE AT STEP 1 AND THEN PUT SERVER DATA IN IT. That
  single sequence causes more state-management pain than any library's
  design flaw.

  WHEN A CLIENT STORE IS GENUINELY EARNED:
    - state read and written from many unrelated parts of the tree
    - updates frequent enough that context's broadcast is measurably slow
    - you need to read or write state OUTSIDE React
    - you need an action log for debugging or audit
    - the state has real invariants that belong in one reducer rather
      than scattered across components

Interview Questions

Beginner: What does an external store give you that context does not?

Selective subscription. Context is a broadcast: when the provider's value changes, every consumer re-renders regardless of which part of that value it actually reads. A store keeps a subscription list and runs each subscriber's selector, so a component re-renders only when its own slice changes.

The distinction is not "global state" — context is already global state, and it is genuinely the right tool for a theme or the current user. The difference shows up when the value changes frequently and consumers read different parts of it. A context holding { user, theme, notifications, cart } re-renders the theme toggle every time a notification arrives.

You can mitigate this by splitting into several contexts, and for a handful of values that is the better answer because it costs no dependency. It stops working when slices are numerous or dynamic — you cannot create a provider per row of a 500-row table, but a store subscription per row is ordinary.

Beginner: What is a selector, and why do people say to keep them cheap?

A selector is a function from the whole store state to the slice a component needs — state => state.cart.items.length. It is the mechanism of selective subscription: after every update the store runs the selector and compares its result with the previous one, re-rendering only if it differs.

They should be cheap because they run on every update to the store, for every subscribed component — not only the updates that concern them. A selector doing an expensive sort or reduce runs on unrelated dispatches too, so with many subscribers the cost multiplies quickly.

When a derivation genuinely is expensive, memoise it with createSelector so the work happens only when its inputs change identity. And prefer selecting a primitive where you can: s => s.items.length both avoids allocation and gives you a value that compares correctly by identity.

Mid: Why does returning a new object from a selector cause an infinite loop?

Because the change check is Object.is, which compares references rather than contents. A selector like s => ({ user: s.user, theme: s.theme }) allocates a fresh object on every call, so the comparison always reports a change even though nothing inside it moved.

That produces a cycle: an update runs the selector, the result is a new reference, the store concludes the slice changed and re-renders the component, the re-render runs the selector, and there is another new reference. React stops it with "Maximum update depth exceeded"; Redux usually warns first that a selector returned a different result with the same parameters. The array version, s => s.todos.filter(t => t.done), is the same bug and is much easier to write without noticing.

There are four fixes, and I reach for them in order. Select primitives separately — two subscriptions is not a performance problem and it needs no extra concept. Pass a shallow equality function (useShallow in Zustand, shallowEqual in Redux) when you really want an object. Memoise with createSelector when the result is a new collection or the computation is costly. Or select a stable reference and derive after, which is fine when the derivation is cheap. It is also worth noticing this is the same defect as an unstable getSnapshot in useSyncExternalStore — one bug, two hats.

Mid: What is tearing, and why did React 18 need useSyncExternalStore?

Tearing is a single committed frame showing two different values of the same state. It became possible in React 18 because concurrent rendering is interruptible: React can render part of a tree, yield to the browser, and resume. If an external store changes during that yield, components rendered before the pause hold the old value and those rendered after hold the new one — and both are committed together.

The pre-18 pattern of useEffect plus useState to subscribe cannot prevent this, because the component reads the store during render with no way to signal that the value moved mid-pass. In React 17 it was safe purely because rendering was synchronous and could not be interrupted.

useSyncExternalStore takes a subscribe function, a getSnapshot, and an optional getServerSnapshot. It forces a synchronous re-read and discards an in-progress render if the value changed, trading a little concurrency for consistency. In practice you rarely call it directly since Redux, Zustand, Jotai and MobX all sit on it — but it is exactly why you should not hand-roll store subscriptions today. Two details matter if you do: getSnapshot must be referentially stable or you loop, and omitting getServerSnapshot throws under SSR.

Senior: A team wants to add Redux to a growing app. How do you evaluate that?

My first question is what state they mean, because the answer is usually server state — lists, records, dashboards fetched over HTTP. That does not belong in a client store at all. It needs caching, deduplication, background refetch and invalidation, and Redux provides none of those; putting it there means hand-writing a cache and maintaining it. TanStack Query or RTK Query handles it directly. In my experience that reframing removes most of the perceived need.

If genuine client state remains, I check whether the cheaper rungs were tried: is it really global, or is it a component that should have been lifted or composed with children? Do filters and pagination belong in the URL, where they would also be shareable and refresh-safe? Would two or three focused contexts do, given theme and user change rarely? Skipping those and installing a store makes everything global by default, and global state is easy to add and very hard to remove.

When a store is genuinely earned, I would choose Redux Toolkit for a large team, complex flows, or where an action log matters — regulated domains, internal tools where "what did the user do" must be answerable, and anywhere time-travel debugging pays for itself. That capability is real and nothing else here matches it. For most product teams I would pick Zustand: ~1.2KB, no provider, and the same selector model, so the concept count is far lower. I would not migrate a working Redux app to Zustand for aesthetics — the churn is not worth it — but for a new store, Zustand plus a query library covers the ground with less to learn.

Senior: Compare subscription granularity across context, Redux/Zustand, Jotai and MobX, and say what the trade-off actually is.

They sit on a spectrum from manual to automatic. Context has no granularity at all — one value, all consumers re-render. Redux and Zustand are manual: you write a selector, and granularity is exactly as good as the selectors you write, which is both the flexibility and the failure mode, since a careless selector reintroduces the broadcast problem or loops outright. Jotai inverts it — state is decomposed into atoms up front, each atom is its own subscription, and granularity is structural rather than something you get right per call site. MobX is automatic at the property level: it tracks which observables were read during a render and re-runs only those reactions.

The trade-off is explicitness against magic. With selectors, what a component depends on is visible in its code — you can read the subscription. With MobX the dependency is inferred at runtime, which is wonderful when it works and genuinely hard when it does not: destructuring an observable outside a tracked context silently loses reactivity, and the resulting "component does not update" bug has no stack trace pointing at the cause. Jotai sits between them — the dependency is explicit in the atom graph, but decomposing an existing app into atoms is a real refactor rather than an incremental change.

My recommendation: selectors are the right default for most teams, because the failure mode — an accidental new object — is loud, well-documented, and fixed by a known pattern, whereas a lost-reactivity bug is silent. Jotai earns its place when the state is genuinely many small independent values, such as a form builder or a canvas editor where per-field or per-node subscription matters. MobX is a reasonable fit for an OO-shaped domain model or a team coming from Angular, but it is a paradigm commitment, not a library choice, and I would not introduce it into a codebase already written in the hooks idiom.

🏋️ Graded Exercises

1 (easy): This component re-renders on every keystroke anywhere in the app. Explain and fix.

  const state = useStore();                 // no selector
  return <span>{state.cart.items.length}</span>;
Solution 
  const count = useStore(s => s.cart.items.length);
  return <span>{count}</span>;

Calling the store hook with no selector subscribes to the entire store, so every update to any slice re-renders this component. It has thrown away the one thing a store offers over context.

Selecting items.length subscribes to a single number. Any change that leaves the count unchanged — editing an item's quantity, updating the user, a websocket message — now compares equal under Object.is and does not re-render. Selecting a primitive is the ideal case: it is cheap, and it compares correctly with no equality function.

2 (easy): This throws at runtime. Why?

  reducers: {
    reset(state) {
      state.items = [];
      return { items: [], total: 0 };
    },
  }
Solution 
  // Option A — mutate the draft only
  reset(state) { state.items = []; state.total = 0; },

  // Option B — return new state only
  reset() { return { items: [], total: 0 }; },

createSlice wraps reducers in Immer, which hands you a proxy draft. Immer supports two styles: record mutations against the draft and let it produce the next state, or ignore the draft and return a new value outright. Doing both in one reducer is ambiguous — Immer has a recorded set of changes and a returned value, cannot know which you intended, and throws rather than guessing.

Either style is fine. Mutation reads better for a deep update, since it avoids nested spreads; returning is clearer for a wholesale replacement like a reset. The rule is only that you pick one per reducer.

3 (medium): This crashes with "Maximum update depth exceeded". Fix it three different ways and say when each is right.

  const { user, theme, unread } = useStore(s => ({
    user: s.user, theme: s.theme, unread: s.notifications.filter(n => !n.read),
  }));
Solution 
  // A — separate primitives/stable refs, plus a memoised derivation
  const user   = useStore(s => s.user);
  const theme  = useStore(s => s.theme);
  const unread = useStore(selectUnread);        // createSelector

  // B — shallow equality on the wrapper, derivation still memoised
  const { user, theme } = useStore(useShallow(s => ({ user: s.user, theme: s.theme })));
  const unread = useStore(selectUnread);

  // C — select a stable reference, derive in the component
  const notifications = useStore(s => s.notifications);
  const unread = useMemo(() => notifications.filter(n => !n.read), [notifications]);

There are two independent bugs here. The object literal allocates a new wrapper on every call, and filter allocates a new array — either alone is enough to loop, because Object.is compares references and both are new every time.

Note that shallow equality alone does not fix this. It compares one level of keys by identity, and the unread key holds a fresh array each call, so the comparison still reports a change. That is why B still needs a memoised selector for the derivation.

FixUse when
A — separate selectorsDefault. Fewest concepts; extra subscriptions are not a real cost
B — useShallowYou genuinely want one object, e.g. spreading into a child's props
C — derive in the componentThe derivation is cheap and used in one place

4 (medium): After a release, returning users see a blank screen and a console error during hydration. The store persists to localStorage. What went wrong, and how do you prevent a repeat?

  const useStore = create(persist(
    (set) => ({ cart: { items: [] }, isModalOpen: false, fetchedAt: null }),
    { name: "app" }
  ));
  // this release renamed cart.items -> cart.lines
Solution 
  const useStore = create(persist(
    (set) => ({ cart: { lines: [] }, isModalOpen: false, fetchedAt: null }),
    {
      name: "app",
      version: 2,
      migrate: (persisted, from) => {
        if (from < 2 && persisted?.cart?.items) {
          persisted.cart.lines = persisted.cart.items;
          delete persisted.cart.items;
        }
        return persisted;
      },
      partialize: (s) => ({ cart: s.cart }),   // not isModalOpen, not fetchedAt
    }
  ));

Persisted state lives in your users' browsers indefinitely, so a shape change is a schema migration whether or not you treat it as one. Returning users hydrated a store whose cart.items no longer exists, code read cart.lines, got undefined, and rendering crashed. They cannot clear it for you, and to them it looks like the site is simply broken.

version plus migrate makes the upgrade explicit — set both from the very first release, because you cannot retrofit a version onto data already written without a version. partialize fixes the second problem visible in the original: it persisted isModalOpen and fetchedAt too, so users would reload into a modal that was open days ago and a timestamp implying fresh data. Persist an explicit allowlist, never the whole store.

Under SSR there is a third trap: the server has no localStorage, so the first client render must match the server's output and swap afterwards, or you get a hydration mismatch on top of everything else.

5 (hard): A dashboard keeps its projects list in Redux. Users complain data is stale until refresh, two components fetching the same list both trigger requests, and creating a project does not update the list. Diagnose the underlying mistake and restructure.

  // slice
  projectsLoading: false, projects: [], error: null
  // in each component
  useEffect(() => { dispatch(fetchProjects()); }, []);
Solution 
  const api = createApi({
    baseQuery: fetchBaseQuery({ baseUrl: "/api" }),
    tagTypes: ["Project"],
    endpoints: (build) => ({
      getProjects: build.query({
        query: () => "/projects",
        providesTags: ["Project"],
      }),
      addProject: build.mutation({
        query: (body) => ({ url: "/projects", method: "POST", body }),
        invalidatesTags: ["Project"],      // list refetches automatically
      }),
    }),
  });

  // any number of components, no coordination needed:
  const { data: projects, isLoading, error } = api.useGetProjectsQuery();
  const [addProject] = api.useAddProjectMutation();

All three complaints are one mistake: server state is being stored in a client store. Redux is a state container, not a cache — it has no concept of staleness, no request deduplication, and no invalidation, so each of those has to be hand-written, and this slice wrote none of them.

Specifically: data is stale until refresh because nothing refetches on focus or reconnect and nothing marks the data old. Two components fire two requests because each has its own useEffect with no shared in-flight registry to deduplicate against. And creating a project does not update the list because there is no link between the write and the read — someone must remember to dispatch a refetch, and eventually someone will not.

RTK Query supplies all three: one cache entry per endpoint means concurrent hooks share a single request; providesTags/invalidatesTags connects the mutation to the query so the refetch is structural rather than remembered; and staleness, refetch-on-focus and cache lifetime are configuration. TanStack Query is an equally good choice with the same model. The general rule stands regardless of library: server data belongs in a query cache, and what remains in a client store is genuinely client state — which is usually far less than a team expects.

6 (hard): Write a minimal store with useSyncExternalStore that supports selectors without infinite loops, then explain what the real libraries add.

Solution 
  function createStore(initial) {
    let state = initial;
    const listeners = new Set();
    return {
      getState: () => state,
      setState(fn) {
        const next = fn(state);
        if (Object.is(next, state)) return;    // no-op writes change nothing
        state = next;
        listeners.forEach(l => l());
      },
      subscribe(l) { listeners.add(l); return () => listeners.delete(l); },
    };
  }

  function useStore(store, selector = (s) => s, isEqual = Object.is) {
    // CACHE the selected value so getSnapshot is referentially stable
    const lastState = useRef(undefined);
    const lastSelected = useRef(undefined);

    const getSnapshot = useCallback(() => {
      const s = store.getState();
      if (Object.is(s, lastState.current)) return lastSelected.current;
      const selected = selector(s);
      if (lastSelected.current !== undefined &&
          isEqual(selected, lastSelected.current)) {
        lastState.current = s;
        return lastSelected.current;           // keep the OLD reference
      }
      lastState.current = s;
      lastSelected.current = selected;
      return selected;
    }, [store, selector, isEqual]);

    return useSyncExternalStore(store.subscribe, getSnapshot, getSnapshot);
  }

The whole difficulty is the caching. React calls getSnapshot during render and compares with Object.is, so a selector that allocates — s => s.items.filter(...) — must not be allowed to return a new reference when the contents are unchanged. Hence the two refs: one remembers the state object that produced the cached value so an unrelated update short-circuits immediately, and the other holds the selected value so an equal-but-new result is discarded in favour of the old reference. Return the fresh array and you loop, which is the same defect as the selector bug in Part 4.

getSnapshot is passed as getServerSnapshot too, which is only correct because this store's initial state is identical on server and client. A store hydrating from localStorage needs a separate server snapshot, or it produces a hydration mismatch.

The point of writing this is not to ship it. It is that once you have written it, Redux and Zustand stop being magic — they are this, plus devtools, plus the edge cases. That understanding is what lets you judge whether you need one at all.

🎯 Key Takeaways

  • A store is state outside the tree plus a subscription list — about fifteen lines; everything else a library ships is devtools, middleware and edge cases.
  • Selective subscription is the only thing a store gives you over context, which is already global state.
  • Context re-renders every consumer on any change, so a value holding several unrelated slices churns components that read none of them.
  • Splitting contexts is a legitimate fix until slices become numerous or dynamic — you cannot make a provider per table row.
  • Tearing is one paint showing two values of the same state, newly possible in React 18 because concurrent rendering can be interrupted mid-pass.
  • useSyncExternalStore exists to prevent tearing; every major store now sits on it, which is why hand-rolling a subscription with useEffect is a real bug today.
  • getSnapshot must be referentially stable or you get "getSnapshot should be cached" and an infinite loop — and omitting getServerSnapshot throws under SSR.
  • Returning a new object or array from a selector loops forever, because the change check is Object.is on references, not contents.
  • Selecting primitives separately is the default fix — extra subscriptions cost far less than people assume.
  • Shallow equality compares one level only, so it does not rescue a key whose value is a freshly allocated array.
  • createSelector's default cache size is one, so a parameterised selector shared across instances memoises nothing.
  • Immer drafts make state.x += 1 safe in RTK, but mutating and returning in the same reducer throws.
  • Redux's durable ideas are pure reducers, serialisable actions and one source of truth — time-travel debugging falls out of them, and nothing else here matches it.
  • Zustand's API is small because it collapses action and reducer into one updater — you trade the action log for far fewer concepts, and set merges shallowly.
  • Persist with partialize and version from day one; shipped state shapes live in users' browsers forever and they cannot migrate themselves.
  • Most state in most apps is server state and belongs in a query cache — putting it in a client store means hand-writing caching, deduplication and invalidation.
  • Reach for a store last: useState → lift or compose → URL → context → query library → store, and what remains is usually a few hundred lines.
