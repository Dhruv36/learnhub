The Render Cycle Effects & Lifecycle

What you'll master: the exact sequence React runs — trigger, render, reconcile, commit, effects — and the distinction that changes how you optimise: "it re-rendered" and "the DOM updated" are different claims, and most performance anxiety aims at the first while all the real cost lives in the second; why a child re-renders when its parent does even when no prop changed, and the structural trick that skips it without memo — passing content as children gives you memoization for free, because the element object is reference-equal; why render must be pure, stated as a consequence rather than a rule — React reserves the right to call your function and throw the result away; Strict Mode as a purity fuzzer, and why the didRun.current guard people reach for silences the alarm rather than the fire, since production remounts for its own reasons; the one-frame flicker that separates useLayoutEffect from useEffect; and how to read a Profiler flamegraph well enough to tell "too slow" from "too often", which have different fixes. Prerequisites: Components & JSX for elements versus fibers, and State for snapshots.

Part 1 — The Five Phases

1. TRIGGER     Something schedules a render:
               initial mount | setState | the parent re-rendered |
               a context value changed

2. RENDER      React calls your component functions, top-down from the
               scheduled fiber, collecting element trees.
               Pure computation. NO DOM is touched here.

3. RECONCILE   New elements are diffed against current fibers, using the
               position/type/key rules from Lists & Keys, producing a
               minimal list of DOM mutations.

4. COMMIT      Mutations are applied to the real DOM, synchronously.
               Refs are attached. useLayoutEffect runs — before paint.

5. PASSIVE     The browser paints. Then useEffect callbacks run.

  RENDERS CAN HAPPEN WITHOUT COMMITS.

  If reconciliation finds nothing changed, or a setState bails out
  because the value is identical, the DOM is never touched. The
  component function ran; the user saw nothing.
🔑 Vocabulary precision is what makes performance conversations productive. "Render" means React called your function — cheap, frequent, pure. "Commit" means the DOM was mutated — batched, minimal, and genuinely expensive. Most optimisation effort is aimed at renders, and a render that produces zero mutations costs some CPU and nothing else. Before optimising, find out which one you have: measure first.

Part 2 — What Re-renders, Exactly

function App() {                        // state lives here
  const [n, setN] = useState(0);
  return (
    <>
      <Counter n={n} onUp={() => setN(n + 1)} />
      <Sidebar />                       {/* no props related to n */}
    </>
  );
}

  setN triggers App to re-render. Then:

  • Counter re-renders — its props changed. Expected.

  • Sidebar ALSO re-renders. Not because its props changed, but because
    App ran again and produced a NEW <Sidebar /> element. React
    re-renders children by default; it does not compare props unless the
    child is wrapped in React.memo.

  • BUT: Sidebar's output is identical, so reconciliation produces ZERO
    mutations for it. Wasted CPU, invisible to the user. Usually fine.
  THE EXCEPTION WORTH KNOWING: CONTENT AS CHILDREN

  function Layout({ children }) {
    const [open, setOpen] = useState(false);   // state lives HERE
    return (
      <div>
        <button onClick={() => setOpen(o => !o)}>toggle</button>
        {children}
      </div>
    );
  }

  <Layout><ExpensiveTree /></Layout>

  When Layout re-renders from its OWN state, `children` is the same
  element object its parent created on the parent's last render —
  REFERENCE-EQUAL. Reconciliation sees an identical element and reuses
  the entire subtree without calling ExpensiveTree at all.

  This is structural memoization: no comparison function, no memo
  wrapper, no dependency array. The content is constructed ABOVE the
  component that churns, so the churn cannot reach it.

  "Move state down, push content up" is the first performance tool to
  reach for, before memo() — because it removes the work rather than
  paying to check whether the work is needed.
EventWhat re-renders
setState with a new valueThat component and its whole subtree — minus memo'd children whose props are equal, and reference-equal element children
setState with the same value (Object.is)Nothing. React may still render the component once more before bailing out
The parent re-renderedAll children, by default, regardless of props
A context value changedEvery consumer of that context — even through a memo wall
Props "changed" with no parent renderImpossible. Props only arrive via a parent render
A ref's .current was mutatedNothing — refs are invisible to rendering (Refs)
An event fired but no state changedNothing. Handlers do not schedule renders by existing

Part 3 — Render Purity, and Why It Is Enforced

function Bad({ items }) {
  items.sort(byPrice);                 // ❌ mutates a prop — visible outside
  document.title = "…";                // ❌ touches the outside world
  fetch("/api/log");                   // ❌ a side effect, per render
  const [s, setS] = useState(0);
  if (someCase) setS(1);               // ❌ unconditional-ish: render loop
  return <div>{Math.random()}</div>;   // ❌ nondeterministic output
}

  WHERE EACH OF THOSE BELONGS:

    mutating data              in the OWNER, via setState with copies
    document.title, listeners  useEffect, after commit
    network requests           useEffect, or an event handler
    responses to user actions  event handlers

  THE ONE SANCTIONED FORM of setting state during render is the
  derived-state reset:

    if (prevId !== id) {          // a condition that becomes false
      setPrevId(id);
      setDraft("");
    }

  React notices the update during render and RESTARTS the render
  immediately, before touching the DOM — so there is no extra paint.
  It is still cheaper than an effect, which would render once with the
  wrong value first.

  Even so, prefer key={id} to remount when you are resetting
  everything — see Lists & Keys.

Why the strictness is real rather than stylistic: React reserves the right to call your function and discard the result. Concurrent rendering can begin a low-priority render, abandon it when urgent input arrives, and start again. A render that logged, mutated or fetched has now done it twice — or an unbounded number of times. Purity is precisely what makes rendering interruptible and resumable.

Part 4 — Strict Mode: the Purity Fuzzer

<StrictMode><App /></StrictMode>   // development only; production untouched

  IN DEVELOPMENT IT DELIBERATELY:

  1. DOUBLE-INVOKES component functions, state initialisers and updater
     functions — so an impure render produces visibly wrong output, such
     as an array with everything in it twice.

  2. MOUNTS, UNMOUNTS AND REMOUNTS every component once, running the
     full effect cleanup cycle — so an effect with missing or wrong
     cleanup breaks loudly, with duplicate listeners or intervals.

  3. Warns about deprecated APIs.

  THE CLASSIC CONFUSION:

    useEffect(() => { console.log("mounted"); }, []);   // logs TWICE

  This is not a bug to suppress. It is the tool saying: your effect must
  be safe to run twice. Give it correct cleanup and both logs become
  harmless.
⚠️ The senior smell is a didRun.current guard. Code that "fixes" Strict Mode's double effect with if (didRun.current) return; silences the alarm and leaves the fire. The same mount-unmount-mount sequence happens in production for reasons you do not control: a key change, fast refresh in development, tab restoration, and offscreen rendering as it lands. An effect that cannot survive re-execution is broken — Strict Mode only decided when you find out.

Part 5 — Commit Timing: useLayoutEffect vs useEffect

  After React mutates the DOM, two effect queues run at different times:

  useLayoutEffect   SYNCHRONOUS, after mutation, BEFORE the browser
                    paints. For reading layout — measuring a tooltip,
                    a scroll position — and adjusting, so the user never
                    sees the intermediate frame.

  useEffect         After paint, asynchronously. For everything else:
                    data, subscriptions, logging. Does not block pixels.

function Tooltip({ anchorRef, children }) {
  const tipRef = useRef(null);
  const [pos, setPos] = useState(null);

  useLayoutEffect(() => {
    const a = anchorRef.current.getBoundingClientRect();
    const t = tipRef.current.getBoundingClientRect();
    setPos({ top: a.top - t.height - 8, left: a.left });
  }, [anchorRef]);

  return (
    <div ref={tipRef}
         style={pos ? { top: pos.top, left: pos.left }
                    : { visibility: "hidden" }}>
      {children}
    </div>
  );
}

  WITH useEffect INSTEAD: one painted frame with the tooltip at the
  wrong position, then a visible jump. That flicker is the entire
  difference between the two hooks.
useLayoutEffectuseEffect
RunsAfter DOM mutation, before paintAfter paint
Blocks pixelsYes — everything in it delays the frameNo
Right forMeasure-then-adjust: tooltips, popovers, scroll restorationData, subscriptions, logging, analytics — nearly everything
On the serverDoes not run, and warns during SSRDoes not run, no warning
Cost of choosing wrongJank on every commitA visible flicker at the wrong position

Part 6 — Reading the Cycle in DevTools

  React DevTools -> Profiler -> record an interaction.

  • FLAMEGRAPH per commit: which components rendered, and how long each
    took.
  • "WHY DID THIS RENDER?" (enable it in settings): props changed /
    hooks changed / parent rendered — the exact diagnosis for every
    mystery re-render, and it removes most guessing.
  • RANKED view: the most expensive components in this commit.

  INTERPRETING IT:

    grey   did not render this commit — skipped by memo, a bail-out, or
           reference-equal children
    wide   expensive. Now ask WHICH KIND of expensive, because the fixes
           are unrelated:

      TOO SLOW    one render takes real milliseconds
                  -> virtualize, split the component, memoize the
                     expensive computation inside it

      TOO OFTEN   each render is fast, but there are hundreds
                  -> fix identity and state placement (Props,
                     Memoization) — memoizing the component treats the
                     symptom

  A component rendering 200 times at 0.3ms and one rendering twice at
  30ms look similar in a total, and need opposite work.

Interview Questions

Beginner: Walk through what happens after a button's onClick calls setState.

React schedules a re-render, batching any other updates in the same event so they produce one render rather than several.

In the render phase the component function runs with the new state snapshot and returns new elements; children are called recursively. Nothing touches the DOM here. Reconciliation diffs those elements against the existing fibers to compute the minimal set of DOM changes. Commit applies them synchronously, attaches refs and runs layout effects. The browser then paints, and finally passive effects — useEffect — run.

The detail worth adding is that a render does not imply a DOM change. If the new elements produce the same output, reconciliation finds nothing to do and the commit is empty.

Beginner: Does a child re-render when its parent does, even with unchanged props?

Yes. By default React re-renders the whole subtree below the component whose state changed. It does not compare props — that comparison only happens for a component wrapped in React.memo, and it is opt-in precisely because comparing is not free.

There is one important exception: an element passed as a prop, typically children. If that element object is reference-equal to the previous render's — because it was created by a component further up that did not re-render — React reuses the subtree without calling the component.

And re-rendering with identical output costs CPU but produces no DOM mutations, so it is frequently not worth doing anything about.

Mid: Why does my useEffect(…, []) log twice in development?

Strict Mode deliberately mounts each component, unmounts it — running the effect's cleanup — and mounts it again, in development only. It is verifying that your effects are resilient to re-execution.

The reason that matters is that the same lifecycle happens in production, for reasons you do not control: a key change remounts a component, fast refresh does it during development, tab restoration and offscreen rendering do it as those features land. An effect that only works if it runs exactly once is already fragile; Strict Mode just decides when you discover that.

So the fix is never a didRun guard. It is correct cleanup — abort the fetch, clear the interval, unsubscribe the listener — so that running twice is harmless. If a double effect causes a visible problem, the effect has a real bug that a guard would hide rather than solve.

The one legitimate complaint is duplicated network requests in development, which is noise in the console. A request cancelled properly on cleanup makes even that harmless, and a data library deduplicates it entirely.

Mid: When is useLayoutEffect correct, and what does it cost?

When you must read the committed DOM and adjust before the user sees the frame — measuring a tooltip so it can be positioned above its anchor, restoring a scroll position, measuring text to decide whether to truncate.

It runs synchronously between DOM mutation and paint, which is exactly why it works: the state update it triggers is applied and re-rendered before any pixels appear, so the intermediate position is never visible. With useEffect the same code paints once at the wrong position and then jumps — that flicker is the whole difference.

The cost is that everything in it delays the frame. Heavy work there is jank by construction, and it is worse than it looks because it happens on every commit that triggers the effect, not just the first.

The other thing to know is that it does not run during server rendering and React warns about it, so a component relying on it needs to render something sensible before measurement — usually visibility: hidden until the position is known.

Default to useEffect. Reach for the layout variant only when you have observed the flicker.

Senior: Explain the children-as-props optimisation and why it works without memo.

If a stateful component receives its expensive content as children — for example <Layout><ExpensiveTree /></Layout> — the element for ExpensiveTree is created by the parent's render, not by Layout.

So when Layout re-renders because of its own state, props.children is the same element object it received last time. Reconciliation compares the element, finds it identical by reference, and reuses the whole subtree without calling ExpensiveTree at all.

It is structural memoization: no comparison function, no memo wrapper, no dependency array to maintain. The content is constructed above the component that churns, so the churn cannot reach it.

What makes it better than memo is that memo pays a comparison on every render and is defeated by any unstable prop — an inline object, an arrow function, JSX children. This approach removes the work instead of checking whether the work is needed, and it cannot be accidentally broken by adding a prop.

The general principle is "move state down, push content up", and it is the first thing I reach for before any memoization: state as low as possible so its re-renders are small, and expensive content constructed as high as possible so it sits outside them.

The honest limitation is that it only helps when the expensive content genuinely does not depend on the changing state. If ExpensiveTree needs the value that Layout owns, it has to re-render, and then you are back to memoizing or to splitting the state.

Senior: What does concurrent rendering change about these phases, and what stays guaranteed?

It makes the render phase interruptible. React can begin a low-priority render — one started inside startTransition, for instance — pause it when urgent input arrives, handle that input with a quick high-priority render, and then resume or abandon and restart the original work.

The consequence for your code is that a component function may run several times for a single visible update, and some of those runs are thrown away. That is precisely why the purity rules exist: an impure render that logged, fetched or mutated has now done it an unpredictable number of times. Purity is the price of interruptibility, not an aesthetic preference.

What stays guaranteed is what makes this safe to build on. Commit is synchronous and uninterruptible — the user never sees a half-applied DOM tree. Effects run only for renders that committed, so an abandoned render cannot fire an effect. And state updates keep their ordering, so the model of "state as a snapshot per render" still holds.

The practical implication I would draw out is that this changed the cost of impurity from "a bug in development" to "a bug that scales with how busy the app is". Code that mutated during render used to mostly work; under concurrency it misbehaves more often precisely when the app is under load, which is the worst possible debugging profile.

🏋️ Graded Exercises

1 (easy): In a tree of App → Header, Body (state here) → Row×3, Footer, Body's state updates. List what re-renders.
Solution 
  RE-RENDERS:  Body, Row, Row, Row
  DOES NOT:    App, Header, Footer

Renders propagate downward from the component that owns the changed state — never upward and never sideways. App did not re-render, so it did not produce new elements for Header or Footer, and their fibers are untouched.

This is the argument for keeping state as low as possible. Had the state lived in App, all five components would re-render for the same interaction — and the fix would be memoization, which costs comparisons, rather than simply putting the state where it belongs.

The follow-up worth answering: do the three Rows produce DOM changes? Only if their output differs. If the state change affects one row, reconciliation produces mutations for that row alone and the other two render to identical elements — CPU spent, no pixels touched.

2 (easy): Why does <div>{Math.random()}</div> violate the render rules, and where could a random value legally come from?
Solution

Renders must be deterministic — the same props and state must produce the same output. Math.random() returns something different on every call, so React calling the function twice (Strict Mode) or discarding and restarting a render (concurrency) produces different trees for the same inputs.

The visible symptoms are a value that changes when nothing changed, and — under server rendering — a hydration mismatch, because the server and the client generated different numbers for the same markup.

Where the value can legally come fromWhen
useState(() => Math.random())Generated once at mount and stable thereafter — the usual answer
An event handlerThe value is a response to a user action, so it belongs with the action
useEffectAfter commit, when the randomness is a side effect rather than part of the output
Generated with the data, upstreamBest of all for ids — created when the item is created, so it survives remounts

For generated ids specifically, useId is the right tool. It produces a stable identifier that matches between server and client, which is exactly what a random value cannot do — and its intended use, linking a label to an input, is the case people usually reach for randomness to solve.

3 (medium): A colleague wraps a component in React.memo and it still re-renders on every parent render. List the causes in the order you would check them.
Solution

The Profiler answers 1, 2 and 4 immediately — "why did this render?" names the prop that changed. That is why it comes before reading any code.

The question I would ask before fixing any of them: what is the re-render costing? If the component renders in under a millisecond and produces no DOM mutations, the correct action is to remove the memo, not to make it work. A defeated memo is pure overhead — a comparison paid on every render for nothing — plus the maintenance burden of keeping every prop stable.

And if it does need fixing, prefer restructuring over memoizing: moving state down, or passing the expensive part as children, removes the re-render entirely without a dependency array to keep correct.

4 (medium): A tooltip appears in the wrong place for one frame, then snaps into position. Diagnose and fix it.
Solution

The measurement is in useEffect, which runs after paint. So the sequence is: React commits the tooltip at its default position, the browser paints that frame, the effect then measures and sets state, and a second render moves it. The user sees both frames.

useLayoutEffect(() => {                 // not useEffect
  const a = anchorRef.current.getBoundingClientRect();
  const t = tipRef.current.getBoundingClientRect();
  setPos({ top: a.top - t.height - 8, left: a.left });
}, [anchorRef]);

// and render nothing measurable until the position is known:
style={pos ? { top: pos.top, left: pos.left } : { visibility: "hidden" }}

Why useLayoutEffect fixes it: it runs synchronously between the DOM mutation and the paint. The state update it triggers is processed and re-rendered before the browser gets a chance to draw, so the wrong position never reaches the screen.

DetailWhy it matters
visibility: hidden, not display: noneA hidden element still has dimensions to measure; a display: none element measures as zero
Measuring both rectsPositioning above the anchor needs the tooltip's own height, which is only knowable after it is in the DOM
It does not run during SSRReact warns; the pos ? … : hidden branch is what makes the server render valid

Keep it small. Layout effects delay pixels, and this one runs on every commit where its dependencies change. Measuring two elements is fine; fetching or looping over a list here is jank.

The modern alternative worth naming: CSS anchor positioning, and libraries like Floating UI, solve this without measuring in JavaScript at all — which is better when available, because it removes the render-measure-render cycle rather than hiding it.

5 (hard): A dashboard re-renders every component on each websocket tick, and the Profiler shows 40 components at roughly 0.2ms each. What do you do?
Solution

First, decide whether it matters. Forty components at 0.2ms is about 8ms per tick. At one tick a second that is irrelevant; at 30 ticks a second it is 240ms of every second spent rendering, and the app will feel unresponsive. The tick rate is the missing number, and I would get it before touching anything.

Then read which kind of expensive this is. This is the "too often" shape, not "too slow" — every individual render is fast. So the fix is structural, and memoizing components would be treating the symptom.

FixWhat it changesWhen it applies
Move the state downOnly the components that display the ticking value re-renderAlmost always the right first move — most of those 40 do not use the data
Push content up as childrenStatic sections become reference-equal elements and are skipped entirelyWhen a stateful wrapper contains expensive static content
Throttle at the sourceCoalesce ticks to animation frames before they reach stateWhen the feed is faster than the screen refreshes — 30 updates a second cannot be perceived anyway
Split the contextConsumers of rarely-changing values stop re-rendering with the fast-changing oneWhen the data arrives through context, which is the usual cause of a whole-tree render
Keep the value in a refNo render at all; the consumer reads it when it needs itWhen the value drives an imperative surface such as a canvas or chart

The one I would reach for first is throttling, because it is the only fix that reduces the number of updates rather than the cost of each. A dashboard that renders more often than the display refreshes is doing work nobody can see, and coalescing to a frame is a few lines with no architectural change.

What I would not do is wrap all 40 components in memo. If the data flows through context, memo does not block it at all; and if it flows through props, each memo pays a comparison per tick to save 0.2ms — plausibly a net loss, and certainly a large increase in the number of places that must keep their props stable.

6 (hard): Explain what breaks if a component mutates an array during render, and why concurrent rendering makes it worse.
Solution 
function Bad({ items }) {
  items.sort(byPrice);                    // mutates the OWNER's array
  return <ul>{items.map(…)}</ul>;
}

Three things break, in increasing order of how hard they are to diagnose.

The owner's data changes with no re-render. The array reference is unchanged, so nothing is scheduled — the parent's state and what is on screen disagree until something unrelated renders. That is the intermittent bug that gets closed as unreproducible.

Other consumers see it. Any sibling rendering the same array now shows a different order, at a time determined by whenever it next happens to render.

The render is not idempotent. Sorting an already-sorted array is stable, which is precisely why this survives testing — the second call produces the same result, so Strict Mode's double invocation reveals nothing. Replace sort with push or reverse and it breaks immediately and visibly.

Why concurrency makes it worse. Under the old model the function ran once per render, so an impure render was wrong but predictable. Concurrent rendering may start a render, abandon it part-way when urgent input arrives, and restart — so the mutation can happen an unpredictable number of times, and it happens during renders whose results were thrown away. Nothing in the committed output records that it occurred.

The failure rate therefore scales with how busy the application is, which means it appears under load and in production rather than on a developer's machine — the worst possible debugging profile.

// The fix, in the component:
const sorted = [...items].sort(byPrice);     // or items.toSorted(byPrice)
return <ul>{sorted.map(…)}</ul>;

// Better, if the order is a real product decision rather than a
// display detail: sort in the owner, and pass sorted data down.

The general rule worth extracting: a render may read anything and change nothing outside itself. Props and state are outside itself.

🎯 Key Takeaways

  • Five phases: trigger, render, reconcile, commit, passive effects. Render calls your functions; commit touches the DOM.
  • "It re-rendered" and "the DOM updated" are different claims. A render that produces no mutations costs CPU and nothing a user can see.
  • Children re-render with their parent by default — props are only compared for components wrapped in memo.
  • Content passed as children is reference-equal and gets skipped, giving structural memoization with no comparison and no dependency array.
  • "Move state down, push content up" is the first performance tool, before memo — it removes the work rather than checking whether the work is needed.
  • Context updates reach every consumer, straight through a memo wall.
  • Render must be pure because React may discard the result — concurrent rendering can start, abandon and restart a render.
  • The one sanctioned setState during render is the derived-state reset, guarded by a condition that becomes false — and a key remount is usually better.
  • Strict Mode double-invokes and remounts to expose impurity; it changes nothing in production.
  • A didRun.current guard silences the alarm, not the fire — production remounts for its own reasons.
  • useLayoutEffect runs before paint, so measure-then-adjust never shows the intermediate frame — and everything in it delays pixels.
  • Default to useEffect; reach for the layout variant only after seeing the flicker.
  • Effects run only for committed renders, which is what makes them the safe place for side effects.
  • "Too slow" and "too often" are different diagnoses with opposite fixes — read per-render time and render count separately.
  • Open the Profiler before optimising. "Why did this render?" removes almost all the guessing.
