Context State Management

What you'll master: context as dependency injection with no change tracking — not a state manager, and not a performance tool; the one mechanism that explains every context bug you will ever see — every consumer re-renders when the provider's value identity changes, regardless of which field it reads; the object-literal-in-JSX trap and why useMemo there is not premature optimization; splitting state from dispatch so action-only consumers never re-render; why a throwing useX hook beats a silent default value; use() in React 19 for reading context conditionally; why context is client-only in RSC; and composition via children, which removes most prop drilling with no context at all. Prerequisites: useReducer & State Machines.

Part 1 — What Context Solves, and What It Is Not

  THE PROBLEM: PROP DRILLING.

    App (theme) ──> Layout ──> Sidebar ──> NavList ──> NavItem (uses theme)

  Layout, Sidebar and NavList do not use `theme`. They accept it,
  forward it, and are now coupled to a value they do not care about.
  Change the shape of theme and four files change.

  CONTEXT MAKES THE VALUE AVAILABLE TO THE SUBTREE WITHOUT THE
  INTERMEDIATE HOPS:

    const ThemeContext = createContext(null);

    <ThemeContext.Provider value={theme}>
      <Layout />                       // knows nothing about theme
    </ThemeContext.Provider>

    function NavItem() {
      const theme = useContext(ThemeContext);   // reaches up the tree
    }

  In React 19 the Provider component is the context object itself —
  <ThemeContext value={theme}> — with `.Provider` still working.

  HOW THE LOOKUP ACTUALLY WORKS. This is not a global registry.
  useContext walks UP THE FIBER TREE from the calling component to
  the nearest provider of that exact context object; finding none,
  it returns createContext's default. Three consequences:

  - Two providers of the same context nest legally; the inner one
    wins for its subtree. That is a feature — a dark panel inside a
    light page — not an accident.
  - Position in the TREE matters, not in the file. A component
    passed as `children` is inside the provider wherever it was
    written.
  - The context OBJECT is the key. Two createContext() calls make
    two unrelated contexts, so a duplicated module (two copies in
    node_modules) silently yields the default forever — the classic
    "it's undefined and I definitely wrapped it" bug.

  WHAT CONTEXT IS NOT:

  NOT A STATE MANAGER. No store, no reducer, no subscription, no
  devtools, no middleware, no persistence. It holds nothing —
  whatever is in the value came from a useState or useReducer in
  some component, and context only TRANSPORTS it.

  NOT A PERFORMANCE OPTIMIZATION. Prop passing is a property
  assignment; it is free. Context often makes rendering SLOWER,
  converting a targeted update into a subtree-wide one (Part 2).

  NOT A REPLACEMENT FOR SERVER CACHE. "User data in context" is the
  most common misuse: server data needs caching, revalidation,
  deduplication and invalidation, and context gives you none.
ConcernContext gives youYou still need
Reaching a deep componentYes — that is the whole featureNothing
Holding stateNo — useState/useReducer holds itA state hook in the provider component
Selective subscriptionNo — all consumers re-render togetherSplitting, or an external store

The one-line framing that survives interviews: context is dependency injection for a React subtree, and dependency injection with no change tracking. It answers "how does this component get the value", never "how does the value change efficiently".

Part 2 — The Mechanism: Value Identity Drives Every Consumer

  THE ONE RULE. When a provider renders with a value that is not
  Object.is-equal to its previous value, React marks EVERY component
  in the subtree that reads that context as needing a re-render —
  regardless of which part of the value it reads, and regardless of
  React.memo boundaries in between.

  MEASURE IT:

    const AppContext = createContext(null);

    function App() {
      const [user, setUser] = useState({ name: 'Ada' });
      const [theme, setTheme] = useState('light');
      const [cart, setCart] = useState([]);

      return (
        <AppContext.Provider value={{ user, theme, cart, setCart }}>
          <Header />      // reads theme only
          <Profile />     // reads user only
          <CartBadge />   // reads cart only
        </AppContext.Provider>
      );
    }

  Add one item to the cart. Header re-renders. Profile re-renders.
  Neither reads cart. In a 40-consumer app that is 40 renders for a
  one-field change; at ~0.15ms of render + reconciliation per small
  component that is ~6ms of a 16.7ms frame spent on components whose
  output is byte-identical.

  WHY REACT CANNOT DO BETTER. Reading context is a function call
  inside a render, not a declaration. React cannot see that
  `const { theme } = useContext(AppContext)` only depends on
  `.theme` — by the time the destructure happens, the component is
  already rendering. The subscription unit is the context, not the
  field.

  MEMO DOES NOT HELP ACROSS A CONTEXT READ:

    const Header = React.memo(function Header() {
      const { theme } = useContext(AppContext);   // <-- reads context
      return <div className={theme} />;
    });

  memo compares PROPS. Header takes no props, so memo always says
  "props equal" — and React re-renders it anyway, because a context
  it consumes changed. memo is a prop gate; a context read is a
  second, independent input that bypasses that gate entirely.

  WHERE MEMO DOES HELP: on the CHILDREN of a consumer. If Header
  re-renders but returns a memoized <ExpensiveChart /> whose props
  did not change, the chart is skipped. So the damage is bounded to
  consumers and their non-memoized descendants, not the whole tree.

  THE PROPAGATION IS NOT A PARENT-TO-CHILD CASCADE. During the
  render phase React scans down from the changed provider for
  fibers carrying a matching dependency and schedules those; a
  subtree with no consumer beneath it is bailed out of and skipped.
  So <Provider>{children}</Provider> with a stable `children`
  element does NOT re-render the non-consuming parts — the basis
  for the composition fix in Part 6.

  ONE MORE CONSEQUENCE, OFTEN MISSED: a provider that re-renders
  for its OWN reasons re-runs the value expression. If that
  expression is an object literal, identity changes even when
  nothing inside it did. That is Part 3.

Part 3 — The Object-Literal Trap and the useMemo Fix

  THE BUG IS ONE CHARACTER WIDE AND COSTS WHOLE FRAMES.

    // BROKEN
    function AuthProvider({ children }) {
      const [user, setUser] = useState(null);
      return (
        <AuthContext.Provider value={{ user, setUser }}>
          {children}
        </AuthContext.Provider>
      );
    }

  `{{ user, setUser }}` allocates a NEW OBJECT on every render of
  AuthProvider. Object.is(prev, next) is false even when `user` is
  the same null it was a second ago. So every consumer re-renders
  every time AuthProvider renders — including when a completely
  unrelated parent re-rendered and pulled AuthProvider along.

  WHEN DOES THIS ACTUALLY BITE? Only when AuthProvider re-renders
  for reasons other than its own state changing. If the provider
  sits at the root and holds only its own state, then every render
  of it IS a state change, and memoizing changes nothing. Be honest
  about that: the useMemo is insurance against the provider being
  moved, or gaining a second piece of state, or a parent re-render.

  THE FIX:

    function AuthProvider({ children }) {
      const [user, setUser] = useState(null);

      const value = useMemo(() => ({ user, setUser }), [user]);
      //  setUser is omitted deliberately: useState setters are
      //  guaranteed stable for the life of the component. Including
      //  it is harmless and some lint configs demand it.

      return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
    }

  THIS IS ONE OF THE FEW PLACES useMemo IS NOT DEBATABLE. The usual
  argument against useMemo — "the comparison costs more than the
  work" — does not apply, because here the memo is not saving a
  computation. It is preserving an IDENTITY that the framework uses
  as a change signal. The cost saved is every consumer's render,
  which is unbounded.

  THE SAME TRAP, THREE MORE SHAPES:

    value={{ ...state, dispatch }}         // new object
    value={[user, setUser]}                // new array
    value={{ login: () => doLogin(x) }}    // new function, new object

  All three change identity every render. Functions must be wrapped
  in useCallback (or defined in the reducer/dispatch pattern of
  Part 4, which sidesteps it) before they go into a memoized value —
  otherwise the useMemo dependency array contains a value that is
  new every time and the memo never hits.

    // USELESS MEMO — login is new each render, so deps always differ
    const login = (email) => api.login(email).then(setUser);
    const value = useMemo(() => ({ user, login }), [user, login]);

    // CORRECT
    const login = useCallback(
      (email) => api.login(email).then(setUser), []);
    const value = useMemo(() => ({ user, login }), [user, login]);

  A memo whose dependency array is unstable is worse than no memo:
  all the cost, none of the benefit, and it reads as handled.

  WHEN CONSUMERS RE-RENDER "FOR NO REASON", CHECK IN THIS ORDER:
    1. Is value an inline literal?          -> Part 3.
    2. Does the provider hold unrelated     -> Part 4, split it.
       state that changes often?
    3. Is the provider high in the tree     -> Part 6, push it down
       and re-rendering from a parent?         or use children.
  The React DevTools Profiler says "Context changed" for exactly
  this case — enable "Record why each component rendered" first.

Part 4 — Splitting: State from Dispatch, and by Domain

  SPLIT 1 — STATE CONTEXT vs DISPATCH CONTEXT.

  A large fraction of consumers only WRITE. A "Add to cart" button
  never reads the cart; it only needs the action. In a single
  context it re-renders on every cart change anyway.

    const CartStateContext    = createContext(null);
    const CartDispatchContext = createContext(null);

    function CartProvider({ children }) {
      const [cart, dispatch] = useReducer(cartReducer, initial);
      return (
        <CartDispatchContext.Provider value={dispatch}>
          <CartStateContext.Provider value={cart}>
            {children}
          </CartStateContext.Provider>
        </CartDispatchContext.Provider>
      );
    }

  WHY THIS IS BETTER THAN IT LOOKS:

  - `dispatch` from useReducer is IDENTITY-STABLE for the lifetime
    of the component. React guarantees it. So CartDispatchContext's
    value NEVER changes, and its consumers NEVER re-render from
    context. Not "rarely" — never.
  - No useMemo is needed on either provider: `cart` is a state value
    and `dispatch` is stable, so neither is an object literal.
  - The nesting order matters for nothing functionally, but putting
    the never-changing provider OUTSIDE means it is not re-created
    when the inner one re-renders.

  MEASURED EFFECT on a checkout page with 60 components, of which
  22 read cart state and 18 are action-only buttons: adding an item
  went from 40 component renders to 22. The 18 buttons dropped out
  entirely. The remaining 22 genuinely display cart data.

  THE useCallback EQUIVALENT, FOR useState-BASED PROVIDERS:

    const actions = useMemo(() => ({
      add:    (id) => setCart(c => [...c, id]),
      remove: (id) => setCart(c => c.filter(x => x !== id)),
    }), []);          // [] is correct: the updaters are functional,
                      // so they never close over stale `cart`.

  The functional updater form is what makes the empty dependency
  array honest. Write `setCart([...cart, id])` instead and you MUST
  add `cart` to the deps, the actions object changes on every cart
  change, and the split has bought you nothing.

  SPLIT 2 — BY DOMAIN, NOT ONE GOD CONTEXT.

    // BAD: one context, four unrelated concerns
    <AppContext.Provider value={{ user, theme, cart, notifications }}>

  Notifications arrive every few seconds. Every arrival re-renders
  everything that reads user or theme. The concerns have completely
  different change frequencies, and the union changes at the sum of
  their rates.

    // GOOD: separate contexts, nested
    <AuthProvider>
      <ThemeProvider>
        <CartProvider>
          <NotificationProvider>{children}</NotificationProvider>

  Rule of thumb: PUT THINGS IN THE SAME CONTEXT WHEN THEY CHANGE
  TOGETHER, not when they feel related. Theme and locale often
  change together (both from a settings panel, both rarely) and can
  share. User and cart do not.

  The provider pyramid is a readability cost at five or six levels.
  Collect them in one Providers component — but do not build a
  reduce()-based abstraction for three of them.

Part 5 — The Provider Contract: Throw, Don't Default

  THE DEFAULT VALUE IS A TRAP FOR ANYTHING NON-TRIVIAL.

    const AuthContext = createContext({ user: null });

    function Profile() {
      const { user } = useContext(AuthContext);
      return <p>{user?.name ?? 'Guest'}</p>;
    }

  Forget the provider — move Profile into a modal that renders in a
  portal outside the provider, say — and there is no error. Every
  user is silently a Guest. The bug ships, and it looks like an auth
  problem, not a tree problem. You will debug the login flow for an
  hour.

  THE FIX IS FIVE LINES AND IT IS THE SINGLE HIGHEST-VALUE
  CONVENTION IN CONTEXT CODE:

    const AuthContext = createContext(undefined);

    export function useAuth() {
      const ctx = useContext(AuthContext);
      if (ctx === undefined) {
        throw new Error('useAuth must be used within <AuthProvider>');
      }
      return ctx;
    }

  WHY undefined AND NOT null: null is a value someone will
  legitimately want to provide ("no user is logged in"). undefined
  is the only value that cannot be confused with a real one — and
  createContext() with no argument gives you undefined for free.

  FOUR THINGS THE CUSTOM HOOK BUYS BEYOND THE ERROR:

  1. THE CONTEXT OBJECT NEVER LEAVES THE MODULE. Export useAuth and
     AuthProvider; do not export AuthContext. Now nobody can call
     useContext(AuthContext) directly and skip the guard, and you
     can change the internals — split it into two contexts, swap it
     for Zustand — without touching a single consumer.
  2. TYPES. In TypeScript the guard is a type narrowing:
     the hook's return type is the non-undefined type, so every
     consumer stops writing `auth?.user`.
  3. ONE PLACE FOR DERIVED VALUES. `const isAdmin = ctx.user?.role
     === 'admin'` belongs in the hook, not in fifteen components.
  4. THE ERROR MESSAGE NAMES THE FIX. "useAuth must be used within
     <AuthProvider>" is a complete bug report. "Cannot read
     properties of undefined (reading 'user')" is not.

  WHEN A REAL DEFAULT IS CORRECT: when the context is genuinely
  optional and the default is a WORKING implementation — a theme
  defaulting to 'light', a logger defaulting to a no-op, an
  analytics client defaulting to a stub. The test is: WOULD YOU
  SHIP THE DEFAULT? If it means "something is misconfigured", throw.

  TESTING NOTE: the throwing hook also makes tests honest. A test
  that forgets the provider fails loudly with a message naming what
  to wrap, instead of asserting against a silently-defaulted render.
  Export a helper that wraps in the REAL provider; never mock
  useContext.

Part 6 — Scale, use(), RSC, and the Composition Alternative

  A. THE SCALING CEILING, AND WHY use-context-selector EXISTS.

  Context has no selector API. The community package
  use-context-selector reimplements propagation on top of a
  subscription so that

    const theme = useContextSelector(AppContext, s => s.theme);

  re-renders only when `s.theme` changes. It works by having the
  provider push updates through its own subscriber list and calling
  useSyncExternalStore under the hood — i.e. it stops using React's
  context propagation for updates and uses it only for transport.

  React has repeatedly discussed a first-party selector API and it
  has not shipped as of React 19. Treat use-context-selector as a
  real option, not a hack, but understand what it implies: if you
  need per-field subscriptions, you have outgrown context, and an
  external store gives you the same thing plus devtools, middleware
  and a store you can read outside React.

  B. React 19's use() — READING CONTEXT CONDITIONALLY.

    function Panel({ compact }) {
      if (compact) {
        const theme = use(ThemeContext);   // LEGAL in React 19
        return <div className={theme.compact} />;
      }
      return <div />;
    }

  useContext must obey the Rules of Hooks: top level, unconditional,
  same order every render. `use` does not — it may be called inside
  a condition, a loop, or after an early return. React 19 only.

  WHAT use() DOES NOT CHANGE: the subscription is still per-context.
  A conditional read is still a read, and when the provider value
  changes this component re-renders. use() is an ergonomics fix, not
  a performance fix. It also reads promises (that is its other job,
  used with Suspense) — same function, two capabilities.

  C. CONTEXT IN RSC — CLIENT-ONLY. createContext and useContext
  throw in a Server Component: it renders once, has no state and no
  re-render, so there is nothing for a subscription to mean. The
  provider module needs 'use client'; the server layout can then
  import and render it normally. Exercise 6 works this through with
  the full file layout and the reachability rules.

  D. THE ALTERNATIVE THAT REMOVES MOST PROP DRILLING WITH NO
     CONTEXT AT ALL: COMPOSITION.

    // The problem, again
    function Page() {
      const [user] = useUser();
      return <Layout user={user} />;         // Layout doesn't use it
    }
    function Layout({ user }) {
      return <Sidebar user={user} />;        // nor does Sidebar
    }
    function Sidebar({ user }) {
      return <Avatar user={user} />;         // finally
    }

    // The fix: pass the ELEMENT, not the data
    function Page() {
      const [user] = useUser();
      return (
        <Layout sidebar={<Sidebar avatar={<Avatar user={user} />} />} />
      );
    }
    function Layout({ sidebar })  { return <aside>{sidebar}</aside>; }
    function Sidebar({ avatar })  { return <nav>{avatar}</nav>; }

  Layout and Sidebar no longer know that `user` exists — they accept
  a ReactNode. Change the user's shape and only Page and Avatar
  change. Strictly better than context for ONE OR TWO levels.

  IT ALSO FIXES A RENDER PROBLEM. Elements created in Page and
  passed down are the SAME element objects on a parent re-render, so
  React bails out of re-rendering them. That is why a provider
  written as <ThemeProvider>{children}</ThemeProvider> does not
  re-render `children` when its own state changes. Write
  <ThemeProvider><App /></ThemeProvider> inside the provider file
  instead and you lose that.

  HONEST LIMIT: composition stops helping when the value is read in
  MANY places at MANY depths — threading 50 elements through for a
  theme is worse than a provider. Composition for 1–3 consumers,
  context for a cross-cutting concern read everywhere.

Interview Questions

Beginner: What problem does context solve, and what does it not solve?

It solves prop drilling: passing a value through components that do not use it, purely to reach a descendant. Context lets a descendant read a value from an ancestor provider directly, so the intermediate components stop being coupled to data they do not care about.

What it does not solve is anything to do with how the value changes. Context has no store, no reducer, no subscription granularity, no caching, no devtools and no persistence. The state still lives in a useState or useReducer somewhere; context only transports it. The accurate description is "dependency injection for a React subtree".

It is also not a performance optimization, which surprises people. Passing props is a property assignment and costs nothing measurable. Context frequently makes an app slower, because it converts a targeted update into one that re-renders every consumer in the subtree.

The practical consequence: use it for cross-cutting values read at many depths that change rarely — theme, locale, the current user, a feature-flag set. For a value that changes many times a second, or one read by only two nearby components, something else is better.

Beginner: Why does value={{ user, setUser }} cause a performance problem?

The double braces are an object literal inside JSX, so a new object is allocated on every render of the provider component. React compares the provider's previous and next value with Object.is. Two structurally identical objects are not Object.is-equal, so React concludes the value changed and schedules a re-render for every consumer of that context.

The damage scales with consumer count, not with the size of the change. A hundred components reading the context means a hundred renders because the provider re-rendered — even if user is still the same null it was before.

const value = useMemo(() => ({ user, setUser }), [user]);
return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;

setUser is omitted from the dependency array because useState setters are guaranteed stable for the lifetime of the component. Including it is harmless.

One honest caveat worth saying out loud: if the provider only ever re-renders because its own state changed, the memo does nothing today — every render is a real change. It matters when the provider re-renders for another reason, which happens as soon as it gains a second piece of state or a parent re-renders it.

Mid: A consumer wrapped in React.memo still re-renders when the context changes. Why?

Because memo and context are two independent inputs. memo wraps a component with a props comparison: if the incoming props are shallow-equal to the previous ones, React skips the re-render. It says nothing about context.

A context read is a second subscription. During the render phase, when React encounters a provider whose value identity changed, it walks the subtree looking for fibers that registered a dependency on that context and marks each one for work. That marking happens regardless of the memo wrapper — in fact a memoized component with no props always passes the props check and is re-rendered purely because of the context.

What memo does still buy you is containment below the consumer. The consumer re-renders, but if it renders a memoized child whose props are unchanged, that child is skipped. So the blast radius is the consumers plus their non-memoized descendants.

The real fixes are structural: split the context so the consumer subscribes to something that changes less often; move the context read into the smallest component that needs it, so the expensive siblings are not consumers at all; or move to a store with selector-based subscriptions.

Mid: Explain the state/dispatch split and why it works without any memoization.

You publish two contexts instead of one: a state context holding the current value, and a dispatch context holding the updater. Consumers that only trigger actions — buttons, menu items, form submit handlers — read only the dispatch context.

<CartDispatchContext.Provider value={dispatch}>
  <CartStateContext.Provider value={cart}>
    {children}
  </CartStateContext.Provider>
</CartDispatchContext.Provider>

It works with no useMemo because of a guarantee: the dispatch function returned by useReducer is identity-stable for the lifetime of the component. Its context value therefore never changes, so its consumers are never scheduled from context. Not "rarely" — never. And the state context's value is the state itself, not a wrapper object, so it changes exactly when the state changes.

The measured payoff on a real checkout page: 60 components, 22 reading cart data, 18 action-only. Adding an item went from 40 renders to 22, because the 18 buttons stopped being state consumers.

The useState equivalent needs one extra step: wrap the action functions in useCallback with functional updaters (setCart(c => [...c, id])) and put them in a useMemo'd object with [] deps. If you write setCart([...cart, id]) instead, the actions object must depend on cart, it changes on every update, and the split has bought you nothing.

Senior: When do you move from context to an external store, and what do you lose?

The trigger is not app size, it is the product of update frequency and consumer count. Context re-renders every consumer on every value change. A theme read by 200 components and changed twice a session is fine. A cursor position read by 10 components and changed 60 times a second is not. When you find yourself splitting a context a third time to dodge re-renders, you have outgrown it.

The secondary triggers are capability, not performance: you need to read or write state outside React (a WebSocket handler, an interceptor); you need time-travel debugging or a middleware pipeline; you need persistence; or you need to subscribe to a computed slice rather than a whole object. Context offers none of these, and reimplementing them on top of it is how you end up with a worse Redux.

What you lose is real. A store is a second state model to learn and onboard people into. It lives outside the component tree, so a module-scoped store is shared across server requests during SSR unless you scope it per request — a genuine data-leak class of bug that context, being tree-scoped, cannot have. Testing needs store setup or resets between tests. And every store adds bundle weight (Zustand ~1KB, Redux Toolkit ~12KB gzipped) plus a devtools story to maintain.

My recommendation: reach for context by default for cross-cutting client concerns, split it by domain and by state/dispatch as a matter of course, and move to a store when you have a measured re-render problem the splits do not fix, or a concrete need for out-of-React access, devtools or middleware. And check first whether the state is actually server data — in most apps that "state management problem" is a cache problem, and a server-cache library removes 70% of what was in the store.

Senior: How does context behave in React Server Components, and what does that mean for architecture?

Context is client-only. createContext and useContext throw in a Server Component, because a Server Component renders once, has no state, no re-render and no hooks — there is nothing for a subscription to mean. In the Next.js app router, that means any provider module needs 'use client' at the top.

The part that trips people up is what happens next. Putting a client provider in the root layout does not make the app client-side. 'use client' marks a module boundary, not a subtree. Server children passed into the provider as children are rendered on the server and arrive as an already-rendered payload that the client provider slots in. So the wrapper is cheap. But those server children cannot call useContext — they never execute on the client — so context reaches client descendants only.

Architecturally this pushes you toward a cleaner split than most client-only apps have: server data is fetched in the server render or a cache library and passed as props, and context is reserved for genuinely client-side concerns — theme, modal state, a wizard's step. Worth noting alongside it that React 19's use(Context) lifts the Rules of Hooks for context reads only; the subscription is still per-context, so it is an ergonomics fix, not a selector.

My recommendation for a new app-router codebase: one thin client provider per client concern, mounted as low in the tree as the concern allows rather than at the root, and no server data in any of them. If a provider must be at the root, keep its value tiny and stable.

1 (easy): This provider makes every consumer re-render more often than it should. Fix it, and say when the fix actually matters. 
function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}
Solution 
function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light');
  const value = useMemo(() => ({ theme, setTheme }), [theme]);
  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}

What the wrong version does at runtime. Every time ThemeProvider renders, the JSX evaluates { theme, setTheme } and allocates a fresh object. React stores the previous value on the provider fiber and compares with Object.is; two distinct objects are never equal, so React marks every fiber with a dependency on ThemeContext as needing work.

When it matters — be precise. If ThemeProvider only ever re-renders because setTheme was called, the memo changes nothing: every render is a genuine change. It starts mattering the moment the provider re-renders for another reason — a parent re-renders it, or it gains a second piece of state such as a system-preference listener. Since that is a one-line change made by someone who will not re-audit the provider, the memo is worth writing up front.

Note the children prop is doing quiet work here too: because children is passed in from above, its element identity is unchanged when ThemeProvider re-renders, so React bails out of re-rendering the non-consuming parts of the subtree. Rendering <App /> directly inside the provider instead would lose that.

2 (easy): A teammate reports "context is undefined" in a component rendered inside a modal portal. The context is createContext({ user: null }). What do they actually see, and how would you make this class of bug impossible?
Solution

They do not see undefined — that is the tell. With a default of { user: null }, a component outside the provider reads that default and renders successfully with user === null. Every user appears logged out. The failure is silent and looks like an authentication bug, so the debugging goes to the login flow instead of the tree.

  if (ctx === undefined) {
    throw new Error('useAuth must be used within <AuthProvider>');

4 (medium): This "fix" was shipped after a profiler session and the profiler still says the consumers re-render on every keystroke. Explain why, and fix it properly. 
function SearchProvider({ children }) {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);

  const search = (q) => { setQuery(q); runSearch(q).then(setResults); };

  const value = useMemo(() => ({ query, results, search }),
                        [query, results, search]);
  return <SearchContext.Provider value={value}>{children}</SearchContext.Provider>;
}
Solution

The memo can never hit. search is a function expression re-created on every render, so it has a new identity every time and appears in the dependency array. React compares the deps, finds one differs, and recomputes the value — so the memo pays the comparison cost and returns a new object anyway. The code looks fixed, which is worse than no memo, because the next person profiling assumes this path is handled.

There is a second, larger problem: query changes on every keystroke and lives in the same context as results. Even with a perfect memo, everything reading results re-renders on each character typed.

const SearchStateContext  = createContext(undefined);
const SearchActionContext = createContext(undefined);

function SearchProvider({ children }) {
  const [state, dispatch] = useReducer(searchReducer,
                                       { query: '', results: [] });

  const actions = useMemo(() => ({
    search: (q) => {
      dispatch({ type: 'query', q });
      runSearch(q).then(r => dispatch({ type: 'results', r }));
    },
  }), []);        // [] is honest: only dispatch is captured, and it is stable

  return (
    <SearchActionContext.Provider value={actions}>
      <SearchStateContext.Provider value={state}>
        {children}
      </SearchStateContext.Provider>
    </SearchActionContext.Provider>
  );
}

The empty dependency array on actions is honest here precisely because the reducer moved the state transitions inside dispatch. Nothing in the closure captures query or results, so there is no stale-closure risk hiding behind the []. Reaching for a reducer is often less about complex state and more about getting a stable updater that lets dependency arrays be empty and mean it.

If the results list is still expensive, split further by change frequency: query into its own context read by the input, results into another. But measure first — the split above usually suffices.

5 (hard): A dashboard has one AppContext at the root holding { user, theme, notifications, sidebarOpen }. Notifications arrive over a WebSocket roughly every 3 seconds. The profiler shows a 22ms render every time one arrives, on a page with 140 components of which 90 are consumers. Design the fix and justify each step.
Solution

What is happening. A notification arriving replaces the notifications array, the root provider re-renders, the value object is rebuilt, and all 90 consumers are scheduled. At roughly 0.2ms of render plus reconciliation each, that is ~18ms of work plus commit — over the 16.7ms frame budget, so a dropped frame every 3 seconds, visible as a stutter while scrolling.

Step 1, split by domain, does almost all the work and is the one to do first. The four concerns have change rates differing by three orders of magnitude — user changes twice a session, notifications 1,200 times an hour — and merging them means everything updates at the sum of the rates. Group by change frequency, not by whether the values feel like they belong together.

Step 3 is the one people skip. The notification provider does not need to be at the root at all. If only the header bell and a toast container read it, mount the provider around those two and the chart grid stops being in the subtree entirely. Provider placement is a real lever, not boilerplate; the reflex to put every provider in main.jsx is what creates these problems.

What not to do. Do not wrap the 90 consumers in React.memo — memo gates props and a context read bypasses it, so it changes nothing here and costs a comparison per component. Do not reach for a store first: it is a larger change with a permanent maintenance cost, and after steps 1–3 you are at 6 renders, which needs no further work. Reach for the store only if profiling after the splits still shows a problem, or when you need devtools or out-of-React access for their own sake.

6 (hard): A Next.js app router build fails with "createContext is not a function" from the root layout. The team's proposed fix is to add 'use client' to app/layout.jsx. Evaluate that, give the correct fix, and state precisely what the context can and cannot reach afterwards.
Solution

The proposed fix works and is wrong. Marking the root layout as a Client Component makes the layout module client-side, and everything it imports and renders directly becomes part of the client bundle. You have traded a build error for shipping the whole shell to the browser and losing server rendering for it.

// theme-provider.jsx
'use client';

  const [theme, setTheme] = useState('light');

}
export function useTheme() { /* throwing guard */ }

    <html><body>

    </body></html>

Why the correct version does not make the app client-side. 'use client' marks a module boundary, not a subtree. children is rendered by the server layout before it is handed to ThemeProvider, so it arrives as an already-rendered payload that the client provider slots into its output — a thin client wrapper around server-rendered content.

The consequence to state clearly: context reaches client descendants only. A server component nested inside the provider cannot read the theme, because it never runs in the browser where the context exists. If a server component needs the value, it is not context state — read it from a cookie or header on the server and pass it as a prop.

🎯 Key Takeaways

  • Context is dependency injection for a subtree, with no change tracking — not a state manager and not a performance tool.
  • Every consumer re-renders when the provider's value identity changes, regardless of which field it reads.
  • React.memo does not stop a context re-render — it gates props, and a context read is a separate input.
  • An inline value={{...}} allocates a new object every render, so consumers re-render even when nothing changed.
  • useMemo on a provider value is not premature optimization — it preserves an identity the framework uses as a change signal.
  • A useMemo with an unstable dependency is worse than none — all the cost, none of the benefit, and it reads as fixed.
  • dispatch from useReducer is identity-stable for the component's lifetime, which is what makes the state/dispatch split free.
  • Split state from dispatch so action-only consumers never re-render — usually the single largest win.
  • Group values in one context by change frequency, not by topic; a merged context updates at the sum of its members' rates.
  • createContext(undefined) plus a throwing hook turns a silent wrong render into a named error at the first read.
  • Never export the raw context object — export the provider and the hook, and the internals stay replaceable.
  • Mutating the context value re-renders nothing; identity is unchanged, so the UI goes stale with no error.
  • Provider placement is a lever — mounting a provider around the smallest subtree that needs it beats any amount of memoization.
  • Accept children, never render <App /> inside a provider — a stable children element lets React bail out of non-consumers.
  • Composition removes most prop drilling with no context at all — pass the element, not the data, for 1–3 levels.
  • Context is client-only in RSC; 'use client' marks a module boundary, and server children inside a client provider still cannot read it.
