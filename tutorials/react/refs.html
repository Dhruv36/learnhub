Refs & the DOM Effects & Lifecycle

What you'll master: useRef as a mutable box that does not trigger a re-render, and the two unrelated jobs it does — DOM access and instance-like storage; why reading or writing a ref during render breaks concurrent rendering, and the exact rule that replaces "never touch a ref"; the callback ref form and the three cases where it beats the object form; ref as an ordinary prop in React 19 versus forwardRef before it; the narrow set of problems useImperativeHandle genuinely solves; the latest-value ref that escapes stale closures and why it is an escape hatch rather than a default; and integrating a non-React library where StrictMode's double-mount makes cleanup mandatory. Prerequisites: useEffect Mastery.

Part 1 — A Box That Does Not Re-render

  useRef RETURNS THE SAME OBJECT ON EVERY RENDER:

    const ref = useRef(initialValue);
    // ref === { current: initialValue }

  Two properties define it, and everything else follows:

    1. THE OBJECT IDENTITY IS STABLE for the component's lifetime.
       Not "usually stable" — the same object, always. That is why a
       ref never belongs in a dependency array.

    2. MUTATING .current DOES NOT TRIGGER A RE-RENDER. React does
       not know it happened and does not care.

  CONTRAST WITH STATE:

    const [count, setCount] = useState(0);   const ref = useRef(0);
    setCount(1);   -> re-render               ref.current = 1; -> nothing
    count is a SNAPSHOT of this render        ref.current is CURRENT,
                                              shared across renders

  THE DECISION RULE: IS IT RENDERED?

    displayed on screen               -> state
    used only in handlers/effects     -> ref
    both                              -> state (and read it from a
                                        ref only to defeat a stale
                                        closure)

  THE INITIALISER RUNS EVERY RENDER, unlike useState's lazy form:

    const ref = useRef(new Heavy());   // ❌ constructs on EVERY
                                       //    render, then discards
                                       //    all but the first

    const ref = useRef(null);          // ✓ lazy init
    if (ref.current === null) ref.current = new Heavy();

  useState(() => new Heavy()) has a lazy initialiser; useRef does
  not. The argument is evaluated every time and thrown away after the
  first render, which is invisible when the value is 0 and expensive
  when it is a media player or a websocket.

  THE TWO JOBS ARE UNRELATED, and it helps to keep them separate in
  your head:

    JOB 1  a handle on a DOM node       <input ref={inputRef} />
    JOB 2  a mutable value that must    intervalRef, latestPropsRef,
           survive renders              hasMountedRef

  Job 2 is what a class instance field used to be.

Part 2 — The Render Purity Rule

  THE RULE IS NOT "NEVER TOUCH A REF". It is:

    DO NOT READ OR WRITE ref.current DURING RENDER.
    Do it in event handlers, in effects, or in callback refs.

    function Bad() {
      const ref = useRef(0);
      ref.current++;                    // ❌ during render
      return <div>{ref.current}</div>;  // ❌ reading during render
    }

  WHY IT MATTERS AND IT IS NOT PEDANTRY. React 18's concurrent
  renderer may:

    render a component and THROW THE RESULT AWAY (a higher-priority
      update arrived)
    render the same component TWICE for one commit (StrictMode, in
      development)
    START a render, pause, and restart it from the top

  A render that mutates a ref therefore mutates it an unpredictable
  number of times. The counter above can be 1, 2, or 7 for a single
  visible update, and reading it during render makes the output
  depend on that.

  READING A REF DURING RENDER IS ALSO WRONG BECAUSE THE VALUE IS NOT
  A SNAPSHOT. State gives each render a consistent view; a ref gives
  whatever the latest mutation left. Two components reading the same
  ref during one render pass are not guaranteed to agree.

  THE ONE SANCTIONED EXCEPTION is lazy initialisation, because it is
  idempotent — it makes the ref's value a constant rather than
  varying with render count:

    if (ref.current === null) ref.current = expensiveThing();

  DURING RENDER THE DOM REF IS NULL ANYWAY:

    function Bad() {
      const inputRef = useRef(null);
      inputRef.current.focus();   // ❌ TypeError on first render
      return <input ref={inputRef} />;
    }

  React attaches the node AFTER the commit. There is no ordering in
  which the ref is populated during the render that creates the
  element.

    useEffect(() => { inputRef.current?.focus(); }, []);   // ✓

  ALWAYS USE OPTIONAL CHAINING. A ref can be null because the element
  is conditionally rendered, because it is inside a Suspense fallback,
  or because cleanup has already run.
WhereRead .current?Write .current?
During renderNoNo (lazy init excepted)
Event handlerYesYes
useEffectYesYes
useLayoutEffectYes — before paintYes
Callback ref body—Yes, the node is given to you
Effect cleanupYes, but capture it firstYes

Part 3 — Callback Refs

  A ref PROP ACCEPTS A FUNCTION AS WELL AS A REF OBJECT. React calls
  it with the node on mount and with null on unmount:

    <div ref={node => { if (node) measure(node); }} />

  THREE CASES WHERE THIS BEATS THE OBJECT FORM.

  1. YOU NEED TO REACT TO MOUNT, and an effect is too late or does
     not re-run. An object ref changing from null to a node does not
     trigger anything — React does not watch .current. A callback
     ref runs at exactly that moment:

       const [height, setHeight] = useState(0);
       const measuredRef = useCallback(node => {
         if (node) setHeight(node.getBoundingClientRect().height);
       }, []);
       <div ref={measuredRef}>…</div>

     With an object ref plus useEffect([]), a conditionally rendered
     node that appears later is never measured.

  2. A DYNAMIC LIST OF NODES:

       const nodes = useRef(new Map());
       {items.map(item => (
         <li key={item.id}
             ref={node => {
               if (node) nodes.current.set(item.id, node);
               else      nodes.current.delete(item.id);
             }}>
       ))}

     The else branch matters: without it the map retains detached
     DOM nodes forever, which is a real leak in a long-lived list.

  3. ATTACHING TO A NODE YOU DO NOT OWN THE LIFETIME OF — a portal
     target, or a node inside a third-party render.

  THE INLINE-FUNCTION GOTCHA: an inline arrow is a new function every
  render, so React calls it with null and then with the node on
  EVERY render. Usually harmless; not harmless if it does real work.
  useCallback with a stable dependency list fixes it.

  REACT 19 ALLOWS A CLEANUP RETURN, which removes the null branch:

    <li ref={node => {
      nodes.current.set(id, node);
      return () => nodes.current.delete(id);   // React 19+
    }} />

Part 4 — Forwarding a Ref

  A ref DOES NOT PASS THROUGH A COMPONENT LIKE AN ORDINARY PROP —
  in React 18 and earlier it was not a prop at all:

    function Input(props) { … }
    <Input ref={r} />    // ❌ warning; r stays null

  BEFORE REACT 19 — forwardRef:

    const Input = forwardRef(function Input(props, ref) {
      return <input ref={ref} {...props} />;
    });

  REACT 19 — ref IS AN ORDINARY PROP:

    function Input({ ref, ...props }) {
      return <input ref={ref} {...props} />;
    }

  forwardRef still works and is deprecated but not removed, so a
  codebase will contain both for a long time. If you write a
  component library today, check which React version your consumers
  are on before dropping forwardRef.

  WHY DESIGN SYSTEMS MUST FORWARD REFS. Without it, consumers cannot:

    focus a field after a validation error
    scroll an element into view
    attach a tooltip or popover positioner
    measure for layout
    integrate with focus-trap, drag-and-drop, or form libraries

  A component that swallows its ref is unusable in half the
  situations a real application produces — and the failure is silent
  (the ref is just null), so it is discovered late.

  useImperativeHandle CUSTOMISES WHAT THE REF EXPOSES:

    const Video = forwardRef(function Video(props, ref) {
      const el = useRef(null);
      useImperativeHandle(ref, () => ({
        play:  () => el.current.play(),
        pause: () => el.current.pause(),
        // deliberately NOT the raw element
      }), []);
      return <video ref={el} {...props} />;
    });

  THE JUSTIFIED USES ARE FEW, and they share a shape — a one-off
  ACTION at a moment in time, with no state to keep:

    focus() / blur()          scrollTo()
    play() / pause()          open() / close() on <dialog>
    a canvas or chart redraw  select() on text

  THE MUCH LARGER SET THAT IS A PROPS PROBLEM IN DISGUISE:

    ref.current.setValue(x)     -> a value prop
    ref.current.setLoading()    -> a loading prop
    ref.current.refresh()       -> a key prop, or lifted state
    ref.current.getData()       -> lift the state up

  THE TEST: if the parent would want to RE-APPLY it after a re-render,
  it is state and belongs in props. If it is a fire-and-forget action
  the DOM itself models imperatively, an imperative handle is honest.

Part 5 — Refs for Values, Not Nodes

  THE LATEST-VALUE REF ESCAPES A STALE CLOSURE:

    // ❌ the interval captures onTick from the first render
    useEffect(() => {
      const id = setInterval(() => onTick(count), 1000);
      return () => clearInterval(id);
    }, []);          // onTick and count are frozen at mount

    // ✓ the ref always holds the latest
    const latest = useRef(onTick);
    useLayoutEffect(() => { latest.current = onTick; });

    useEffect(() => {
      const id = setInterval(() => latest.current(), 1000);
      return () => clearInterval(id);
    }, []);           // the interval is created ONCE

  This is the standard useInterval / useEventListener pattern, and it
  is a deliberate escape hatch: it breaks the rule that an effect's
  behaviour follows from its dependencies, in exchange for not
  tearing down and recreating a long-lived subscription on every
  render.

  USE IT WHEN: the subscription is expensive or has visible side
  effects when recreated — a websocket, an interval whose phase
  matters, an observer.
  DO NOT USE IT WHEN: adding the dependency would simply work. A
  stale closure fixed by a correct dependency array is not a reason
  to reach for a ref.

  WHY useLayoutEffect FOR THE ASSIGNMENT: it runs before paint, so
  the ref is fresh before any event handler could fire in the same
  frame. With useEffect there is a window where a handler reads the
  previous value.

  OTHER LEGITIMATE VALUE REFS:

    timer/interval ids            clearTimeout(timerRef.current)
    a previous value              usePrevious
    "has this mounted yet"        skip an effect's first run
    an AbortController            abort on the next run
    a mutable third-party         a chart, an editor, a map instance
      instance

  usePrevious, WRITTEN OUT:

    function usePrevious(value) {
      const ref = useRef(undefined);
      useEffect(() => { ref.current = value; });
      return ref.current;          // the value from the PREVIOUS
    }                              //   committed render

  The assignment is in an effect precisely so it happens after
  render — writing it during render would break under a discarded
  render pass.

  THE COUNTER-CASE PEOPLE GET WRONG:

    const countRef = useRef(0);
    countRef.current++;                 // ❌ nothing re-renders
    return <div>{countRef.current}</div>;

  If it is on screen, it is state. A ref cannot make the UI update,
  and using one here produces a value that changes but is never
  shown.

Part 6 — Integrating Non-React Libraries

  THE PATTERN FOR ANY IMPERATIVE LIBRARY — a chart, a map, an editor,
  a video player:

    function Chart({ data }) {
      const containerRef = useRef(null);
      const chartRef     = useRef(null);

      // 1. CREATE ONCE
      useEffect(() => {
        chartRef.current = new ChartLib(containerRef.current);
        return () => {                    // 2. DESTROY — mandatory
          chartRef.current.destroy();
          chartRef.current = null;
        };
      }, []);

      // 3. SYNC on data change, do NOT recreate
      useEffect(() => {
        chartRef.current?.setData(data);
      }, [data]);

      return <div ref={containerRef} />;
    }

  THE THREE PARTS ARE SEPARATE EFFECTS ON PURPOSE. Merging creation
  and data-syncing into one effect with [data] destroys and rebuilds
  the chart on every data change — losing zoom, selection and
  animation state, and costing far more than an update.

  STRICTMODE MAKES CLEANUP NON-OPTIONAL. In development React mounts,
  unmounts and remounts every component. Without the destroy:

    two chart instances on one container
    two websockets
    duplicated event listeners
    a doubled animation loop

  People report this as "StrictMode broke my chart". StrictMode
  revealed that the code leaks an instance on every unmount — which
  in production shows up as a slow memory climb during navigation.

  CAPTURE THE REF VALUE FOR CLEANUP:

    useEffect(() => {
      const node = containerRef.current;      // capture NOW
      const obs = new ResizeObserver(…);
      obs.observe(node);
      return () => obs.unobserve(node);       // not ref.current
    }, []);

  By the time cleanup runs, ref.current may already be null or point
  at a different node. The lint rule that warns about this is
  correct.

  MEASURING LAYOUT — useLayoutEffect PLUS A REF:

    useLayoutEffect(() => {
      const { height } = ref.current.getBoundingClientRect();
      setHeight(height);           // before paint: no flicker
    }, [content]);

  With useEffect the user sees one frame at the wrong size, then a
  jump. The cost is that getBoundingClientRect forces a synchronous
  reflow and useLayoutEffect blocks painting — so batch reads, and do
  not put this in a component that renders hundreds of times.

  WHEN A REF IS THE WRONG TOOL ENTIRELY:

    resetting a child's internal state   -> change its key
    reading a form value on submit       -> FormData, or state
    animating                            -> CSS, or an animation lib
    storing rendered data                -> state

Interview Questions

Beginner: What is useRef and how does it differ from useState?

useRef returns the same object on every render, with a .current property you can mutate. Two properties define it: the object identity is stable for the component's lifetime, and mutating .current does not trigger a re-render.

useStateuseRef
Changing it re-rendersYesNo
Value in a renderA snapshot of that renderWhatever the latest mutation left
Identity across rendersNew value each renderSame object always

The decision rule is simply "is it rendered?" — if the value appears on screen it must be state, because a ref cannot make the UI update. If it is only read in handlers or effects — a timer id, a DOM node, a third-party instance — a ref is right.

One practical detail: useRef's argument is evaluated on every render and discarded after the first, so useRef(new Heavy()) constructs an object each time. Unlike useState, there is no lazy initialiser — guard it with if (ref.current === null).

Beginner: Why is a DOM ref null during render?

Because React attaches the node after the commit. During render your component is producing a description of the UI; the DOM node does not exist yet, so there is no ordering in which the ref could be populated.

function Bad() {
  const inputRef = useRef(null);
  inputRef.current.focus();          // TypeError on first render
  return <input ref={inputRef} />;
}

useEffect(() => { inputRef.current?.focus(); }, []);   // correct

Always use optional chaining even in effects. A ref can legitimately be null because the element is conditionally rendered, because it is inside a suspended boundary, or because cleanup already ran.

If you need to act at the moment a node appears — measuring a conditionally rendered element, for instance — a callback ref is the right tool, because an object ref changing from null to a node triggers nothing.

Mid: When is a callback ref better than an object ref?

When you need to react to the node appearing or disappearing. React does not watch .current, so an object ref going from null to a node notifies nobody; a callback ref runs at exactly that moment.

Case 1 — measuring. With an object ref plus useEffect([]), a conditionally rendered node that appears later is never measured. A callback ref handles it:

const measuredRef = useCallback(node => {
  if (node) setHeight(node.getBoundingClientRect().height);
}, []);

Case 2 — a dynamic list of nodes, collected into a Map keyed by item id. The null branch is essential; without it the Map retains detached DOM nodes, which is a real leak in a long-lived list.

Case 3 — nodes whose lifetime you do not control, such as a portal target.

The gotcha is that an inline arrow is a new function every render, so React calls it with null and then the node on every render. That is harmless for a Map write and not harmless if it does real work — useCallback fixes it. React 19 lets a callback ref return a cleanup function, which removes the null branch entirely.

Mid: Why must a design-system component forward its ref?

Because ref is not an ordinary prop that passes through — before React 19 it was not a prop at all. A component that ignores it leaves consumers with null, and the failure is silent, so it is discovered late.

Everything real applications do needs it: focusing a field after a validation error, scrolling an element into view, positioning a tooltip or popover, measuring for layout, and integrating with focus-trap, drag-and-drop or form libraries.

// React 18 and earlier
const Input = forwardRef((props, ref) => <input ref={ref} {...props} />);

// React 19 — ref is an ordinary prop
function Input({ ref, ...props }) { return <input ref={ref} {...props} />; }

forwardRef is deprecated in 19 but not removed, so codebases will contain both for years. If you publish a library, keep forwardRef until your consumers are on 19.

useImperativeHandle is the related tool for exposing a narrowed API instead of the raw node — play() and pause() rather than the whole <video> element.

Senior: When is useImperativeHandle justified, and when is it a props problem?

It is justified for a one-off action at a moment in time, with no state to keep — the same shape the DOM itself models imperatively.

JustifiedA props problem in disguise
focus(), blur(), select()setValue(x) → a value prop
scrollTo()setLoading() → a loading prop
play(), pause()getData() → lift the state up
open(), close() on a dialogrefresh() → a key change

The test: would the parent want to re-apply it after a re-render? If yes, it is state and belongs in props. Imperative setters desynchronise — the parent calls setValue('x'), the child re-renders from its own state, and now two sources disagree with no way to reconcile them.

The deeper reason is that React's model is a function from state to UI. An imperative handle punches a hole in it, so each one is a place where the UI can no longer be derived from the current state — and that is exactly the class of bug that is hard to reproduce.

My rule when reviewing: an imperative handle exposing a verb in the past or present imperative (focus, scroll, play) is usually fine; one exposing set, get or update is a design smell worth pushing back on.

Senior: How do you integrate an imperative library, and why does StrictMode break naive attempts?

Three separate concerns, deliberately in separate effects:

useEffect(() => {                              // create ONCE
  chartRef.current = new ChartLib(containerRef.current);
  return () => { chartRef.current.destroy();   // destroy — mandatory
                 chartRef.current = null; };
}, []);

useEffect(() => { chartRef.current?.setData(data); }, [data]);  // sync

Merging them is the common mistake. One effect with [data] destroys and rebuilds the chart on every data change, losing zoom, selection and animation state and costing far more than an update would.

StrictMode double-mounts in development — mount, unmount, remount — so a missing destroy() leaves two chart instances on one container, two websockets, or a doubled animation loop. Teams report this as "StrictMode broke my chart", but StrictMode only revealed that the code leaks an instance on every unmount. In production that appears as a slow memory climb as users navigate, which is much harder to attribute.

Capture the ref value for cleanup rather than reading ref.current inside it — by then it may be null or point at a different node. The lint rule that warns about this is correct.

The general principle: React owns the container element, the library owns everything inside it, and the boundary between them is a create-once effect plus prop-driven sync effects. Never let both write to the same DOM subtree.

🏋️ Graded Exercises

1 (easy): Why does the count not appear on screen? 
function Counter() {
  const count = useRef(0);
  return (
    <button onClick={() => count.current++}>
      Clicked {count.current} times
    </button>
  );
}
Solution

Mutating a ref does not trigger a re-render. The value increments correctly — React just never runs the component again, so the displayed text stays at 0 until something else causes a render.

That produces the worst symptom of all: if an unrelated state change re-renders the component, the count suddenly jumps to its true value, so it looks intermittent rather than broken.

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>
    Clicked {count} times
  </button>;
}
QuestionAnswer
Is it rendered?Yes → state
Only read in handlers/effects?→ ref

The code also reads count.current during render, which is the second violation — a ref's value is not a snapshot, so under concurrent rendering two components reading it in one pass are not guaranteed to agree.

2 (easy): What does this construct, and how many times? 
function Player({ src }) {
  const player = useRef(new VideoPlayer(src));
  …
}
Solution

A new VideoPlayer on every single render — all but the first immediately discarded. useRef's argument is an ordinary expression evaluated before the call; there is no lazy initialiser.

const player = useRef(null);
if (player.current === null) player.current = new VideoPlayer(src);
HookLazy init?
useState(expensive())No — evaluated every render
useState(() => expensive())Yes
useRef(expensive())No, and there is no lazy form

The guard is the sanctioned exception to the no-writes-during-render rule, because it is idempotent — the ref's value becomes a constant rather than varying with render count.

It is invisible when the value is 0 and serious when it is a media player, a websocket, or anything that allocates or connects on construction. Look for constructors and new inside a useRef call in review.

Better still for a real player: create it in a mount effect with a matching destroy() in cleanup, since it needs teardown anyway.

3 (medium): The height is always 0. Why? 
function Panel({ open }) {
  const ref = useRef(null);
  const [height, setHeight] = useState(0);

  useEffect(() => {
    if (ref.current) setHeight(ref.current.offsetHeight);
  }, []);

  return open ? <div ref={ref}>{content}</div> : null;
}
Solution

When open is false on mount, the div does not exist, so ref.current is null when the [] effect runs. It never runs again, so nothing measures the element when it later appears — React does not watch .current.

const measuredRef = useCallback(node => {
  if (node) setHeight(node.offsetHeight);      // runs the moment
}, []);                                        // the node attaches

return open ? <div ref={measuredRef}>{content}</div> : null;
ApproachFires when the node appears later?
Object ref + useEffect([])No
Object ref + useEffect([open])Yes, if you remember the dependency
Callback refYes, automatically
ResizeObserverYes, and on later size changes too

The callback ref is better than adding [open] because it does not depend on you correctly enumerating every condition that controls the element's presence — it fires on the actual event.

If the content can change size afterwards — a font loads, an image decodes, the window resizes — a single measurement goes stale, and a ResizeObserver attached in the callback ref is the durable answer.

Use useLayoutEffect if you render based on the height, or the user sees one frame at zero height and then a jump.

4 (medium): The parent's ref is always null. Fix it two ways. 
function TextField({ label, ...props }) {
  return (
    <label>{label}<input {...props} /></label>
  );
}

// parent
const inputRef = useRef(null);
<TextField ref={inputRef} label="Email" />

Solution

ref does not pass through as an ordinary prop in React 18 and earlier — it is intercepted by React, produces a warning, and the parent's ref stays null.

// React 18 and earlier
const TextField = forwardRef(function TextField({ label, ...props }, ref) {
  return <label>{label}<input ref={ref} {...props} /></label>;
});

// React 19 — ref is a normal prop
function TextField({ label, ref, ...props }) {
  return <label>{label}<input ref={ref} {...props} /></label>;
}

In React 19, {...props} would forward ref automatically — but destructure it explicitly anyway, so a reader can see where it goes.

Why this matters beyond focus: a field that swallows its ref cannot be scrolled into view on a validation error, cannot host a tooltip, and cannot be registered with React Hook Form. The failure is silent, which is why it survives until a real integration needs it.

Do not reach for useImperativeHandle here. The consumer wants a real input element; narrowing it to { focus() } only removes capability.

5 (hard): Two maps appear in development and memory grows during navigation. Diagnose. 
function MapView({ center, markers }) {
  const ref = useRef(null);
  const map = useRef(null);

  useEffect(() => {
    map.current = new MapLib(ref.current, { center });
    markers.forEach(m => map.current.addMarker(m));
  }, [center, markers]);

  return <div ref={ref} style={{ height: 400 }} />;
}
Solution

Three defects, and they compound.

1 — no cleanup. Every unmount leaks a map instance with its tile listeners and observers. StrictMode's development double-mount makes it immediately visible as two maps; in production it is a slow memory climb as users navigate.

2 — creation is in the data effect. Any change to center or markers builds a whole new map, discarding zoom, pan and tile cache.

3 — markers is a new array identity every render if the parent creates it inline, so the effect re-runs constantly.

useEffect(() => {                          // create once
  map.current = new MapLib(ref.current, { center: initialCenter });
  return () => { map.current.destroy(); map.current = null; };
}, []);

useEffect(() => { map.current?.setCenter(center); }, [center]);

useEffect(() => {
  map.current?.clearMarkers();
  markers.forEach(m => map.current.addMarker(m));
}, [markers]);
EffectDepsJob
Create[]Instantiate and destroy
Centre[center]Imperative update
Markers[markers]Diff and update

The identity problem still needs fixing at the source — memoise markers in the parent, or key the effect on a derived stable value such as a joined list of ids. Otherwise the marker effect runs on every parent render.

The general rule this illustrates: React owns the container div, the library owns its contents, and the boundary is a create-once effect plus prop-driven sync effects. Never let both write to the same subtree.

6 (hard): The interval fires with a stale callback. Fix it without recreating the interval every render, and say what the fix costs. 
function useInterval(callback, delay) {
  useEffect(() => {
    const id = setInterval(callback, delay);
    return () => clearInterval(id);
  }, []);          // callback frozen at mount
}
Solution

The empty array freezes callback at mount, so it forever sees the props and state of the first render. Adding [callback] would fix correctness but tears down and recreates the interval whenever the parent passes a new inline function — resetting its phase, so a one-second timer that re-renders every 800ms never fires.

function useInterval(callback, delay) {
  const latest = useRef(callback);

  useLayoutEffect(() => { latest.current = callback; });   // every render

  useEffect(() => {
    if (delay === null) return;                 // pause support
    const id = setInterval(() => latest.current(), delay);
    return () => clearInterval(id);
  }, [delay]);                                  // only the delay
}
ApproachStale?Interval recreated
[]YesNever
[callback, delay]NoEvery render — phase resets
Latest refNoOnly when delay changes

useLayoutEffect for the assignment runs before paint, so the ref is fresh before any handler could fire in the same frame. With useEffect there is a window where the previous callback is still reachable.

What the fix costs is real: it deliberately breaks the rule that an effect's behaviour follows from its dependencies. The interval no longer reacts to callback changing, which is exactly what you want here and would be a bug in a hook where the identity is meaningful.

So use it only when recreating the subscription is expensive or visibly wrong — an interval whose phase matters, a websocket, an observer. If simply adding the dependency works, add the dependency. React's useEffectEvent is the eventual first-class version of this pattern.

🎯 Key Takeaways

  • useRef returns the same object every render, and mutating .current does not re-render.
  • If it is on screen, it is state — a ref cannot update the UI.
  • Do not read or write a ref during render; concurrent rendering may render twice or discard the result.
  • Lazy initialisation is the one sanctioned render-time write, because it is idempotent.
  • useRef(new Heavy()) constructs on every render — there is no lazy initialiser.
  • A DOM ref is null during render; React attaches the node after commit.
  • Always use optional chaining on .current — conditional, suspended and unmounted elements all give null.
  • A ref never belongs in a dependency array — the identity is stable and mutation is invisible to React.
  • Callback refs fire when a node attaches, which object refs cannot do.
  • Handle the null branch in a callback ref or you retain detached DOM nodes.
  • Forward refs in any reusable component — swallowing one fails silently.
  • ref is an ordinary prop in React 19; forwardRef is deprecated but still works.
  • useImperativeHandle is for one-off actions — setters and getters are a props problem.
  • The latest-value ref escapes stale closures, at the cost of an effect that no longer follows its dependencies.
  • Separate create-once from prop-sync effects when wrapping an imperative library.
  • StrictMode reveals missing cleanup, it does not cause the leak — always destroy what you create.
  • Capture ref.current into a local for cleanup; by then it may be null or a different node.
