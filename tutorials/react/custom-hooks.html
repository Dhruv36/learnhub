Custom Hooks Effects & Lifecycle

What you'll master: what a custom hook actually is — a plain function that calls hooks, with no machinery behind it — and the misunderstanding that costs the most time: a custom hook shares logic, never state; every call site gets its own independent copy; the mechanistic reason the Rules of Hooks exist — hooks are matched by call order in a list on the fiber, so one conditional call shifts every hook after it; how to design a return value; the traps inside the hooks everyone writes (useLocalStorage's hydration mismatch, useDebounce's missing cleanup, useEventListener's stale handler); and useSyncExternalStore as the correct primitive for anything outside React. Prerequisites: useEffect Mastery and Refs.

Part 1 — There Is No Machinery

  A CUSTOM HOOK IS A FUNCTION WHOSE NAME STARTS WITH "use" AND WHICH
  CALLS OTHER HOOKS. That is the entire definition. React does not
  register it, wrap it, or treat it specially.

    function useToggle(initial = false) {
      const [on, setOn] = useState(initial);
      const toggle = useCallback(() => setOn(v => !v), []);
      return [on, toggle];
    }

  Calling it is exactly the same as inlining its body. That single
  fact answers most questions people have about hooks.

  THE MISUNDERSTANDING THAT COSTS THE MOST TIME:

    A CUSTOM HOOK SHARES LOGIC. IT DOES NOT SHARE STATE.

    function A() { const [on, toggle] = useToggle(); }
    function B() { const [on, toggle] = useToggle(); }

  A and B have COMPLETELY SEPARATE state. Toggling in A does nothing
  in B. This surprises people who expect a hook to behave like a
  store, and it produces bug reports of the form "my hook isn't
  syncing".

  Even calling the same hook twice in ONE component gives two
  independent states:

    const [a, toggleA] = useToggle();
    const [b, toggleB] = useToggle();   // unrelated to a

  IF YOU WANT SHARED STATE, YOU NEED SOMETHING OUTSIDE REACT:

    context             shared within a provider subtree
    an external store   shared app-wide (Zustand, Redux)
    a module variable   plus useSyncExternalStore

  A hook can READ from any of those, which is what makes
  useContext-wrapping hooks so common — but the sharing comes from
  the context, not from the hook.

  THE "use" PREFIX IS A LINT CONTRACT, NOT SYNTAX. React does not
  check it at runtime. But the ESLint plugin uses it to decide where
  the Rules of Hooks apply, so:

    function getWidth() { return useWindowWidth(); }   // ❌ no lint
                                                       //   coverage
    function useWidth() { return useWindowWidth(); }   // ✓

  Name it wrong and you silently lose every check the linter would
  have given you.

  AND A FUNCTION CONTAINING NO HOOKS IS NOT A HOOK:

    function useFormat(n) { return n.toFixed(2); }   // ❌ just a
                                                     //   function
    function formatMoney(n) { return n.toFixed(2); } // ✓

  Naming it "use" implies call-order constraints that do not exist,
  and prevents callers from using it in a loop or a condition where
  it would be perfectly fine.

Part 2 — Why the Rules Exist

  THE RULES:

    1. Only call hooks at the TOP LEVEL — not in conditions, loops,
       or nested functions.
    2. Only call hooks from a component or another hook.

  THE MECHANISM. React stores hooks as an ORDERED LIST on the fiber,
  and matches them BY POSITION across renders:

    function Profile() {
      const [name, setName] = useState('');       // hook 0
      const [age, setAge]   = useState(0);        // hook 1
      useEffect(…);                               // hook 2
    }

    fiber.memoizedState:  [ state:'' ] -> [ state:0 ] -> [ effect ]
                              0             1              2

  There is no name and no key. On the next render React walks the
  list in order and hands back slot 0, then slot 1, then slot 2.

  NOW MAKE ONE CONDITIONAL:

    if (isLoggedIn) {
      const [name, setName] = useState('');       // sometimes hook 0
    }
    const [age, setAge] = useState(0);            // hook 0 or 1!

    render 1 (logged in):   [name] [age]
    render 2 (logged out):  [age]
                             ^ React hands `age` the slot that held
                               `name` — so age becomes ''

  The state does not just reset. It gets the WRONG VALUE, and effects
  get the wrong cleanup functions. React detects the count change and
  throws "Rendered fewer hooks than expected", but if the counts
  happen to match, the corruption is silent.

  THIS IS ALSO WHY THE DEPENDENCY ARRAY LENGTH MUST BE CONSTANT —
  same positional-matching reason, one level down.

  THE FIX IS ALWAYS TO MOVE THE CONDITION INSIDE:

    const [name, setName] = useState('');     // always called
    useEffect(() => {
      if (!isLoggedIn) return;                // condition INSIDE
      …
    }, [isLoggedIn]);

  EARLY RETURNS ARE THE SAME BUG WEARING A DISGUISE:

    function Profile({ user }) {
      if (!user) return null;              // ❌ hooks below are
      const [name] = useState(user.name);  //    conditional
    }

  Put every hook above every return.
PatternLegal?Why
Hook at the top level of a componentYesCalled in the same order every render
Hook inside ifNoShifts every later hook's slot
Hook inside a loop with a varying countNoSame
Hook after an early returnNoConditional by another name
Hook inside an event handlerNoNot part of the render pass
Hook in a custom hookYesComposes into the caller's list
Condition inside a hook's callbackYesThe hook itself is unconditional
Hook in a loop with a fixed countTechnically yesFragile — avoid

Part 3 — When to Extract, and What to Return

  THE SIGNALS THAT IT IS TIME:

    the same three-line effect appears in two components
    a component body is 80% wiring and 20% markup
    a piece of logic has a clear name that is not a component's name
    you want to test the logic without rendering markup

  THE SIGNALS THAT IT IS NOT:

    one call site and no test need — extracting adds indirection for
      nothing
    the "hook" contains no hooks — it is a plain function
    you are extracting to make a component "look cleaner" while the
      hook takes eight arguments and returns eleven values

  THE RETURN SHAPE:

    TUPLE — exactly two values with an obvious order, mirroring
    useState so callers can rename freely:

      const [isOpen, toggle] = useToggle();
      const [value, setValue] = useLocalStorage('k', 0);

    OBJECT — three or more values, or any optional ones:

      const { data, error, isLoading, refetch } = useFetch(url);

    A tuple of five is unreadable at the call site and breaks whenever
    you insert a value in the middle.

  RETURN STABLE IDENTITIES for anything a caller might put in a
  dependency array:

    function useToggle(initial) {
      const [on, setOn] = useState(initial);
      const toggle = useCallback(() => setOn(v => !v), []);  // stable
      return [on, toggle];
    }

  Without useCallback, `toggle` is a new function every render, so a
  caller's useEffect([toggle]) re-runs forever. A hook that returns
  unstable functions pushes a memoisation problem onto every
  consumer, and they will not know why.

  The functional updater is what makes the empty dependency array
  correct here — setOn(v => !v) does not close over `on`.

  ARGUMENTS: keep them few and primitive. A hook taking an options
  OBJECT re-runs its effects on every render unless the caller
  memoises it:

    useThing({ url, retries: 3 })     // ❌ new object every render

    useThing(url, 3)                  // ✓ primitives compare by value

  If you need an options object, destructure it into primitive
  dependencies inside the hook rather than depending on the object.

  COMPOSITION — hooks calling hooks:

    function useUser(id)      { return useQuery(['user', id], …); }
    function useUserPosts(id) {
      const user = useUser(id);
      return useQuery(['posts', user.data?.teamId], …,
                      { enabled: !!user.data });
    }

  Keep the stack shallow. Three layers deep and a reader cannot tell
  which layer issued a request or owns a piece of state.

Part 4 — The Hooks Everyone Writes, and Their Traps

  useLocalStorage — THE ONE WITH THE MOST TRAPS.

    function useLocalStorage(key, initial) {
      const [value, setValue] = useState(() => {
        try {                                  // 1. LAZY + try/catch
          const raw = window.localStorage.getItem(key);
          return raw ? JSON.parse(raw) : initial;
        } catch { return initial; }            // 2. corrupt JSON,
      });                                      //    private mode

      useEffect(() => {
        try { window.localStorage.setItem(key, JSON.stringify(value)); }
        catch { /* quota exceeded — do not crash the app */ }
      }, [key, value]);

      return [value, setValue];
    }

  THE TRAPS, IN ORDER OF HOW OFTEN THEY BITE:

    SSR — window does not exist on the server. Reading it during the
      initial render crashes Next.js. And even guarded, the server
      renders `initial` while the client renders the stored value,
      which is a HYDRATION MISMATCH: React logs an error and, in
      React 18, may discard the server HTML for that subtree. The
      correct pattern is to render `initial` on the first client
      render too, then update in an effect.

    LAZY INITIALISER — useState(readFromStorage()) reads and parses
      on EVERY render. The function form runs once.

    JSON ROUND-TRIP LOSSES — Date becomes a string, undefined
      disappears, Map/Set become {}, NaN becomes null. A stored Date
      comes back as a string and .getTime() throws.

    QUOTA — 5MB, and Safari private mode throws on every write.
      An unguarded setItem crashes the app.

    CROSS-TAB — nothing syncs by default. Two tabs diverge silently.
      The `storage` event fires in OTHER tabs (never the writer),
      so add a listener if it matters.

  useDebounce:

    function useDebounce(value, delay) {
      const [debounced, setDebounced] = useState(value);
      useEffect(() => {
        const id = setTimeout(() => setDebounced(value), delay);
        return () => clearTimeout(id);      // WITHOUT THIS IT IS
      }, [value, delay]);                   // NOT A DEBOUNCE
      return debounced;
    }

  The cleanup IS the debounce. Omit it and every keystroke schedules
  a timer that all fire — you have added latency and changed nothing
  else.

  useEventListener — needs the latest-handler ref:

    function useEventListener(type, handler, target = window) {
      const saved = useRef(handler);
      useLayoutEffect(() => { saved.current = handler; });

      useEffect(() => {
        const listener = e => saved.current(e);
        target.addEventListener(type, listener);
        return () => target.removeEventListener(type, listener);
      }, [type, target]);        // NOT [handler]
    }

  Depending on `handler` would add and remove the listener on every
  render, since callers pass inline arrows.

  useMediaQuery — the SSR case again:

    function useMediaQuery(query) {
      return useSyncExternalStore(
        cb => { const m = window.matchMedia(query);
                m.addEventListener('change', cb);
                return () => m.removeEventListener('change', cb); },
        () => window.matchMedia(query).matches,   // client snapshot
        () => false                                // SERVER snapshot
      );
    }

  The third argument exists precisely for this. Without it, SSR
  crashes on `window`.

Part 5 — useSyncExternalStore

  THE PROBLEM IT SOLVES. Subscribing to something outside React with
  useState + useEffect has two bugs:

    1. A MISSED UPDATE. Between the first render and the effect
       running, the external value can change. You subscribed too
       late and never see it.

    2. TEARING under concurrent rendering. React can pause mid-render
       and resume after the external value changed, so two components
       in ONE commit read different values and the screen is
       internally inconsistent.

  useSyncExternalStore fixes both by making the read synchronous and
  consistent across a render pass:

    const value = useSyncExternalStore(
      subscribe,          // (callback) => unsubscribe
      getSnapshot,        // () => current value, SYNCHRONOUSLY
      getServerSnapshot   // optional, for SSR
    );

  A REAL EXAMPLE — online status:

    const subscribe = (cb) => {
      window.addEventListener('online', cb);
      window.addEventListener('offline', cb);
      return () => {
        window.removeEventListener('online', cb);
        window.removeEventListener('offline', cb);
      };
    };

    function useOnlineStatus() {
      return useSyncExternalStore(
        subscribe,
        () => navigator.onLine,
        () => true                 // assume online during SSR
      );
    }

  TWO REQUIREMENTS THAT CAUSE ALL THE BUGS:

    getSnapshot MUST RETURN A CACHED VALUE, not a fresh object:

      () => ({ x: store.x })     // ❌ new object every call
                                 //    -> infinite render loop
      () => store.state          // ✓ same reference until it changes

    React calls getSnapshot repeatedly and compares with Object.is.
    A new object every time means "always changed", and React throws
    "The result of getSnapshot should be cached".

    subscribe MUST BE STABLE. Defining it inline re-subscribes on
    every render. Hoist it to module scope, or useCallback it.

  WHEN TO USE IT:

    browser APIs        online status, media queries, geolocation
    a module-level      a store you wrote yourself
      store
    a non-React lib     a router, an editor, a game engine
      with events

  Every serious state library uses this internally — it is how Zustand
  and Redux stay correct under concurrent rendering.

  TESTING HOOKS:

    import { renderHook, act } from '@testing-library/react';

    test('toggles', () => {
      const { result } = renderHook(() => useToggle(false));
      expect(result.current[0]).toBe(false);
      act(() => { result.current[1](); });
      expect(result.current[0]).toBe(true);
    });

  Read result.current fresh after every act — destructuring it once
  captures a stale value from the previous render, which is the
  standard way these tests fail confusingly.

Part 6 — What Not to Extract

  A HOOK THAT TAKES EVERYTHING AND RETURNS EVERYTHING:

    const {
      values, errors, touched, isValid, isSubmitting, handleChange,
      handleBlur, handleSubmit, setFieldValue, resetForm, validate
    } = useMegaForm({ initialValues, validationSchema, onSubmit,
                      validateOnChange, validateOnBlur, enableReinit });

  This is a component's worth of responsibility with none of a
  component's structure. It cannot be understood in pieces, cannot be
  partially reused, and every consumer depends on all of it. Either
  use a form library or split it by concern.

  A HOOK WRAPPING A SINGLE HOOK CALL:

    function useUserState() { return useState(null); }   // ❌ nothing
                                                         //   gained

  A "HOOK" WITH NO HOOKS — covered in Part 1: it is a function, and
  naming it "use" imposes call-order rules that do not apply.

  LOGIC THAT IS REALLY A COMPONENT:

    useModal() returning { isOpen, open, close, Modal }

  A hook returning a component is a sign the abstraction is confused —
  now the component's identity depends on the hook's render, which
  remounts the subtree whenever the hook re-renders. Use composition:
  a <Modal> component plus useState for the flag.

  PREMATURE EXTRACTION. The rule of three applies here as elsewhere:
  two similar effects are a coincidence, three are a pattern.
  Extracting after the first duplication usually produces a hook with
  a parameter for every difference — which is harder to read than the
  duplication was.

  THE DIVIDING LINE WORTH REMEMBERING:

    CUSTOM HOOKS extract LOGIC     — state, effects, subscriptions
    COMPOSITION extracts STRUCTURE — markup, layout, slots

  Trying to solve a structure problem with a hook produces the
  useModal shape above; trying to solve a logic problem with
  composition produces render props nobody wants to read.

Interview Questions

Beginner: What is a custom hook, and does it share state?

It is a plain function whose name begins with use and which calls other hooks. React does not register or wrap it — calling it is identical to inlining its body.

It shares logic, never state. Two components calling useToggle() have completely separate state; toggling in one does nothing in the other. Even two calls in the same component are independent.

This is the single most common misunderstanding, and it produces bug reports like "my hook isn't syncing between components".

For genuinely shared state you need something outside React — context for a subtree, an external store for the whole app, or a module variable read through useSyncExternalStore. A hook can read from any of those, which is why context-wrapping hooks are so common, but the sharing comes from the context, not the hook.

Beginner: Why can't you call a hook inside an if?

Because React stores hooks as an ordered list on the fiber and matches them by position. There is no name and no key — on each render it walks the list handing back slot 0, then slot 1, and so on.

if (isLoggedIn) { const [name] = useState(''); }   // sometimes slot 0
const [age] = useState(0);                          // slot 0 or 1

When the condition flips, age is handed the slot that held name — so age becomes ''. The state does not reset, it takes the wrong value, and effects get the wrong cleanup functions.

React detects a changed hook count and throws "Rendered fewer hooks than expected", but if the counts happen to match, the corruption is silent.

The fix is always to keep the hook unconditional and move the condition inside its callback. Note that an early return is the same bug in disguise — every hook must be above every return.

Mid: How do you design a custom hook's signature?

Return a tuple for exactly two values with an obvious order, mirroring useState so callers can rename freely. Return an object past that, or when any value is optional — a five-element tuple is unreadable and breaks every caller when you insert a value in the middle.

Return stable identities for anything a caller might put in a dependency array:

const toggle = useCallback(() => setOn(v => !v), []);   // stable

Without this, toggle is new every render, so a consumer's useEffect([toggle]) runs forever. A hook returning unstable functions pushes a memoisation problem onto every consumer, and they will not know why their effect loops. The functional updater is what makes the empty dependency array correct.

Prefer primitive arguments. A hook taking an options object re-runs its effects every render unless the caller memoises it — so either take primitives, or destructure the object into primitive dependencies inside the hook.

Keep composition shallow. Hooks calling hooks is fine, but three layers deep and a reader cannot tell which layer issued a request or owns which state.

Mid: What is wrong with a naive useLocalStorage?

Five things, and SSR is the one that breaks builds.

TrapSymptom
window during renderCrashes on the server; even guarded, a hydration mismatch
Non-lazy initialiserReads and parses localStorage on every render
No try/catchCorrupt JSON, quota exceeded, or Safari private mode crashes the app
JSON round-tripDate → string, undefined vanishes, Map → {}
No cross-tab syncTwo tabs diverge silently

The hydration mismatch is the subtle one. The server renders the default while the client renders the stored value, so the markup differs. React logs an error and in React 18 may discard the server HTML for that subtree. The correct pattern is to render the default on the first client render too, then update in an effect — accepting one frame of the default in exchange for correctness.

For cross-tab sync, listen for the storage event — noting it fires in other tabs, never the writer.

Senior: Why does useSyncExternalStore exist?

Because subscribing to an external source with useState plus useEffect has two bugs, one of which only appears under concurrent rendering.

A missed update. Between the first render and the effect running, the external value can change. You subscribed too late and never observe it.

Tearing. React 18 can pause mid-render and resume after the external value changed, so two components in one commit read different values and the screen is internally inconsistent — a total shown next to items that no longer sum to it.

useSyncExternalStore makes the read synchronous and consistent across a render pass, which is why every serious state library uses it internally.

Two requirements cause all the bugs. getSnapshot must return a cached value — returning a fresh object each call means React's Object.is comparison always reports a change, producing an infinite loop and the "should be cached" warning. And subscribe must be stable, or you re-subscribe every render.

The third argument, getServerSnapshot, exists for SSR, and is what makes hooks like useMediaQuery safe on the server rather than crashing on window.

Senior: When should you not extract a custom hook?

Four cases, and premature extraction is the most common.

A single call site with no test need. Extraction adds indirection and buys nothing. The rule of three applies: two similar effects are a coincidence, three are a pattern. Extracting after the first duplication usually produces a hook with a parameter for every difference — harder to read than the duplication was.

A function with no hooks in it. That is a plain function, and naming it useX imposes call-order constraints that do not apply while preventing callers from using it in a loop or a condition.

A hook that takes everything and returns everything. A useMegaForm with six options and eleven return values is a component's worth of responsibility with none of a component's structure — it cannot be understood in pieces or partially reused.

Logic that is really a component. A hook returning a Modal component is confused abstraction: the component's identity now depends on the hook's render, so the subtree remounts whenever the hook re-renders.

The dividing line I use: custom hooks extract logic — state, effects, subscriptions. Composition extracts structure — markup, layout, slots. Solving a structure problem with a hook gives you the useModal shape; solving a logic problem with composition gives you render props nobody wants to read.

🏋️ Graded Exercises

1 (easy): Two components use this hook. Why doesn't the count sync? 
function useCounter() {
  const [count, setCount] = useState(0);
  return { count, increment: () => setCount(c => c + 1) };
}
Solution

Because a custom hook shares logic, not state. Calling it is identical to inlining its body, so each component gets its own useState call with its own independent slot on its own fiber.

WantUse
The same logic, separate stateA custom hook — this
Shared within a subtreeContext + a provider
Shared app-wideAn external store
const CounterContext = createContext(null);

export function CounterProvider({ children }) {
  const [count, setCount] = useState(0);
  const value = useMemo(
    () => ({ count, increment: () => setCount(c => c + 1) }), [count]);
  return <CounterContext.Provider value={value}>{children}</CounterContext.Provider>;
}

export function useCounter() {
  const ctx = useContext(CounterContext);
  if (!ctx) throw new Error('useCounter must be used within CounterProvider');
  return ctx;
}

The sharing comes from the context, not the hook — the hook is now just a typed, validated accessor. The throwing guard is worth including: without it, a component outside the provider silently reads null and fails somewhere far away.

The original also returns an unstable increment, which is its own bug — see exercise 3.

2 (easy): What breaks here, and what will the user actually see? 
function Profile({ user }) {
  if (!user) return <Spinner />;

  const [name, setName] = useState(user.name);
  const [bio, setBio]   = useState(user.bio);
  …
}
Solution

The hooks are conditional — when user is null the component returns before calling them, so it renders zero hooks; when the user arrives it renders two.

React compares the hook count with the previous render and throws:

Error: Rendered more hooks than during the previous render.

So the user sees an unmounted subtree or an error boundary — the error is loud, which is fortunate. The dangerous variant is when the counts happen to match across branches, because then the slots silently hold each other's values and nothing throws.

function Profile({ user }) {
  const [name, setName] = useState(user?.name ?? '');   // always
  const [bio,  setBio]  = useState(user?.bio  ?? '');

  if (!user) return <Spinner />;
  …
}
RuleReason
All hooks above all returnsSlots are matched by position
Conditions inside callbacks, not around hooksThe hook stays unconditional

A remaining subtlety: useState(user?.name) only reads the initial value once, so when user arrives later the state keeps ''. If the fields must reset when the user changes, the right tool is a key on the component, not an effect that syncs.

3 (medium): A consumer's effect runs on every render. Why? 
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = () => setOn(!on);
  return [on, toggle];
}

// consumer
const [isOpen, toggle] = useToggle();
useEffect(() => { analytics.track('panel', isOpen); }, [isOpen, toggle]);
Solution

toggle is a new function on every render, so the dependency array never matches and the effect runs every time.

There is a second bug hiding behind it: setOn(!on) closes over on, so two toggles in one event handler produce one net change.

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn(v => !v), []);   // stable
  return [on, toggle];
}
ChangeFixes
useCallback(..., [])Stable identity — consumers' deps and memo work
setOn(v => !v)No closure over on, which is what makes [] correct

The two changes are linked. useCallback(() => setOn(!on), []) would be worse than the original — a permanently stale closure. The functional updater is what allows the empty dependency array to be correct rather than merely quiet.

Why this is a hook-author responsibility: the consumer cannot fix it. They would have to omit toggle from their dependencies and suppress the lint rule — hiding a real problem because your hook has an unstable API.

4 (medium): Three bugs in this useDebounce. Find them. 
function useDebounce(value, delay) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    setTimeout(() => setDebounced(value), delay);
  });
  return debounced;
}
Solution

1 — no cleanup, so it is not a debounce at all. Every render schedules a timer and all of them fire. Typing five characters gives five updates, just delay milliseconds later. You have added latency and changed nothing else.

2 — no dependency array, so the effect runs after every render, including the ones caused by setDebounced itself.

3 — a timer leaks past unmount, calling setDebounced on an unmounted component.

function useDebounce(value, delay) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);          // THE debounce
  }, [value, delay]);

  return debounced;
}
MechanismEffect
Cleanup runs before the next effectCancels the pending timer — only the last one survives
Cleanup runs on unmountNo update after unmount
[value, delay]Reschedules only when the input actually changes

The insight worth carrying: the debounce is not implemented by the timeout — it is implemented by the cleanup. React's "cleanup runs before every re-run" rule is doing the whole job.

Note this debounces a value, not a callback. Debouncing an expensive function is a different hook, and it needs the latest-handler ref so the debounced call does not use a stale closure.

5 (hard): This crashes on the server and warns in the browser. Fix both. 
function useLocalStorage(key, initial) {
  const [value, setValue] = useState(
    JSON.parse(localStorage.getItem(key)) || initial
  );
  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);
  return [value, setValue];
}
Solution

Four defects. localStorage does not exist on the server, so it throws during SSR. The initialiser is not lazy, so it reads and parses on every render. There is no try/catch, so corrupt JSON or an exceeded quota crashes the app. And even with a guard, the server renders initial while the client renders the stored value — a hydration mismatch.

function useLocalStorage(key, initial) {
  const [value, setValue] = useState(initial);   // ALWAYS the default
  const [hydrated, setHydrated] = useState(false);

  useEffect(() => {                    // read AFTER hydration
    try {
      const raw = localStorage.getItem(key);
      if (raw !== null) setValue(JSON.parse(raw));
    } catch { /* corrupt or unavailable — keep the default */ }
    setHydrated(true);
  }, [key]);

  useEffect(() => {
    if (!hydrated) return;             // do not overwrite before reading
    try { localStorage.setItem(key, JSON.stringify(value)); }
    catch { /* quota exceeded — never crash the app */ }
  }, [key, value, hydrated]);

  return [value, setValue];
}

The hydrated flag is the non-obvious part. Without it, the write effect runs on mount with value === initial and destroys the stored value before the read effect has loaded it.

The cost is one frame showing the default before the stored value appears. That is the unavoidable trade for correct hydration — the server cannot know what is in the user's browser.

Still unhandled: JSON loses Date, undefined, Map and NaN, and nothing syncs across tabs. Both need explicit handling — a reviver function and a storage event listener.

function useWindowSize() {
  return useSyncExternalStore(
    (cb) => {
      window.addEventListener('resize', cb);
      return () => window.removeEventListener('resize', cb);
    },
    () => ({ width: window.innerWidth, height: window.innerHeight })
  );
}
Solution

getSnapshot returns a new object on every call. React invokes it repeatedly and compares results with Object.is; two different objects are never equal, so React concludes the store changed, re-renders, calls it again, and loops — with the warning "The result of getSnapshot should be cached to avoid an infinite loop".

A second bug: subscribe is defined inline, so it is a new function every render and React re-subscribes each time.

And a third: window is read with no server snapshot, so SSR crashes.

let cache = { width: 0, height: 0 };

function getSnapshot() {
  if (cache.width !== window.innerWidth ||
      cache.height !== window.innerHeight) {
    cache = { width: window.innerWidth, height: window.innerHeight };
  }
  return cache;                       // SAME reference until it changes
}

const SERVER = { width: 0, height: 0 };

function subscribe(cb) {              // module scope — stable
  window.addEventListener('resize', cb);
  return () => window.removeEventListener('resize', cb);
}

export function useWindowSize() {
  return useSyncExternalStore(subscribe, getSnapshot, () => SERVER);
}

subscribe is stableOtherwise it re-subscribes every render
getServerSnapshot returns a constantA new object there breaks hydration the same way

Returning two primitives instead avoids the problem entirely — two useSyncExternalStore calls returning numbers compare fine, since Object.is works on values. Prefer that when you can.

The general lesson: getSnapshot must be a pure read of already-existing state, not a computation that constructs something. Any derivation belongs in the store, or in a useMemo after the read.

🎯 Key Takeaways

  • A custom hook is just a function that calls hooks — calling it is identical to inlining its body.
  • Hooks share logic, never state; every call site gets its own independent copy.
  • Sharing requires context or an external store — the hook only reads from it.
  • Hooks are matched by call order in a list on the fiber, which is why conditional calls corrupt state rather than merely resetting it.
  • An early return makes every hook below it conditional.
  • The use prefix is a lint contract — miss it and you lose all checking.
  • A function with no hooks is not a hook; naming it useX imposes rules that do not apply.
  • Return stable identities, or you push a memoisation problem onto every consumer.
  • The functional updater is what makes an empty dependency array correct, not just quiet.
  • Tuple for two values, object beyond that.
  • Prefer primitive arguments — an options object re-runs effects every render.
  • Reading window during render causes a hydration mismatch, not only an SSR crash — render the default first.
  • The cleanup is the debounce — without it you have only added latency.
  • Listener hooks need a latest-handler ref, with deps on the target, not the handler.
  • useSyncExternalStore prevents missed updates and tearing; its getSnapshot must return a cached reference.
  • Extract logic with hooks and structure with composition — a hook returning a component is confused abstraction.
  • Wait for the third duplication; extracting at the first produces a parameter for every difference.
