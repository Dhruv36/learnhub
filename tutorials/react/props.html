Props & Component Contracts Foundations

What you'll master: props as a component's public API, and the two facts everything else depends on — one-way data flow, and reference identity, the concept behind most React performance questions and the reason a mutated prop produces a UI that silently disagrees with its own data while every test passes; why useState(props.value) freezes at mount and shows a stale value forever, and the two correct designs that replace it; how "data down, events up" decides who owns a piece of state, which is the real question behind most component design; the prop-API rules that survive thirty consuming teams — enums over boolean piles, sources over derivatives, slots over configuration flags; and why the honest answer to "should I wrap this in useCallback?" is "it depends who receives it" rather than yes. Prerequisites: Components & JSX and JS Objects — reference versus value semantics is the prerequisite that actually matters here.

Part 1 — Props Are Function Arguments With a Contract

A component's props are literally its parameter — one object per render. But they are more than arguments: props are the component's public API. Everything a parent can configure, and nothing else, flows through them.

RuleWhat it meansWhat it buys
One-way data flowData goes parent → child only. A child cannot reach upTo find where a value comes from you walk up the tree — one direction, no cycles, and no "who else writes this?"
Props are read-onlyNever assign to or mutate props inside a componentRenders stay pure and repeatable, so React can call them freely and compare results by reference
function PriceTag({ amount, currency = "USD" }) {   // default: plain JS syntax
  // amount = amount * 1.2;      ❌ never reassign
  const withTax = amount * 1.2;  // ✅ derive a new local value
  return <span>{withTax.toFixed(2)} {currency}</span>;
}
  "READ-ONLY" IS DEEPER THAN "DO NOT REASSIGN"

  Reassigning a prop is harmless-but-confusing: you shadow a local
  variable and the parent never sees it.

  MUTATING THROUGH a prop is a different category of bug:

    function TagList({ post }) {
      post.tags.push("new");        // ❌ the parent's object, changed
      return <ul>{post.tags.map(…)}</ul>;
    }

  The parent still holds THE SAME REFERENCE. So:

    parent's post === parent's post        -> true
    React's change detection               -> "nothing changed"
    re-render scheduled                    -> none
    memo(Child) comparison                 -> equal, skip
    useEffect([post]) dependency           -> unchanged, do not re-run

  THE DATA CHANGED AND NOBODY WAS NOTIFIED.

  What you observe: a value that is correct in the console and wrong on
  screen, which "fixes itself" when anything unrelated triggers a render.
  That intermittency is why these bugs get closed as "could not
  reproduce" and reopened a week later.

  The array methods that mutate, and their safe replacements:
    push/pop/shift/unshift  -> [...arr, x] / arr.slice(…)
    splice                  -> toSpliced   (or slice + spread)
    sort                    -> toSorted    (this one catches everyone)
    reverse                 -> toReversed
  sort() and reverse() are the dangerous pair, because they LOOK like
  they return a new array — they return the same one, reordered.
🔑 Reference identity is the axis the whole framework turns on. React answers "did this change?" with ===, not by inspecting contents — a deliberate trade, since deep comparison of every prop on every render would cost more than the re-render it saves. So a new object with identical contents counts as changed, and the same object with different contents counts as unchanged. Both halves of that surprise people, and both are covered here and in The Re-render Model.

Part 2 — Data Down, Events Up (and Who Owns the State)

Children cannot write to props, so how does anything change? The parent passes a callback prop; the child calls it with event data; the parent owns the state change. This is the fundamental loop of every React app:

function Parent() {
  const [cart, setCart] = useState([]);            // state lives HERE

  function handleAdd(productId) {                  // the parent decides WHAT happens
    setCart(c => [...c, productId]);
  }

  return <ProductRow id={7} name="Camera" onAdd={handleAdd} />;
}

function ProductRow({ id, name, onAdd }) {         // the child reports WHEN
  return (
    <li>
      {name}
      <button onClick={() => onAdd(id)}>Add to cart</button>
    </li>
  );
}

The naming convention has teeth: event props are onXxx and the functions that implement them are handleXxx. The child fires events in its own vocabulary — "a product was added" — and never presumes what the parent will do with that. That is precisely what lets ProductRow appear in a wishlist, a comparison page, or a search result without change.

  THE REAL DESIGN QUESTION: WHERE SHOULD THIS STATE LIVE?

  Put it in the LOWEST component that needs it — then lift it only when
  something else needs it too.

    Nobody else cares          -> local state in the component
                                  (an open/closed accordion, a hover)

    A sibling needs it         -> LIFT to the nearest common parent,
                                  pass value down + onChange up
                                  (a selected row highlighted in a
                                   list AND shown in a detail panel)

    Half the tree needs it     -> Context (see Context lesson) — but
                                  read that lesson's warnings first

    It outlives the page, or
    is really server data      -> URL, or a data-fetching cache.
                                  See Data Fetching: most "global
                                  state" is a cache of someone
                                  else's data wearing a disguise.

  THE COST OF GETTING IT WRONG, in each direction:

    Too low   the value is unreachable when a second component needs
              it, and you end up syncing two copies with an effect —
              the single most common source of state bugs in React.

    Too high  every keystroke in a text field re-renders the entire
              page, because state changes re-render the owner and its
              whole subtree.

  "Lift as far as necessary and no further" is the whole heuristic.

Part 4 — Evolving a Contract Without Breaking Callers

// v1 — a Rating display. The minimum contract.
function Rating({ value }) {                       // value: 0–5
  return <span>{"★".repeat(value)}{"☆".repeat(5 - value)}</span>;
}

// v2 — someone needs max=10. Extend with a DEFAULT: non-breaking,
//      because every existing call site keeps its old behaviour.
function Rating({ value, max = 5 }) {
  return <span>{"★".repeat(value)}{"☆".repeat(max - value)}</span>;
}

// v3 — make it interactive, but only when the parent opts in.
function Rating({ value, max = 5, onChange }) {
  const interactive = typeof onChange === "function";
  return (
    <span aria-label={`Rating: ${value} of ${max}`}>
      {Array.from({ length: max }, (_, i) => (
        <button
          key={i}
          type="button"
          disabled={!interactive}
          onClick={() => onChange?.(i + 1)}      // report the NEW value up
        >{i < value ? "★" : "☆"}</button>
      ))}
    </span>
  );
}

  WHAT WAS DELIBERATELY NOT ADDED: internal state.

  `value` stays parent-owned, which means:
    - two Ratings can be driven by one value
    - the parent can validate or veto a change before applying it
    - the displayed value can never disagree with the parent's data,
      because there is only one copy

  This is the CONTROLLED COMPONENT idea, and Forms is built on it.
ChangeBreaking?Why
Add an optional prop with a defaultNoExisting callers keep their behaviour exactly
Add a required propYesEvery call site must change at once — the same rule as an API request field
Rename a propYesA rename is a removal plus an addition, and the removal is the half that breaks
Widen an enum — add "warning" to toneNoNobody was passing it before
Narrow an enum, or tighten validationYesCalls that worked yesterday now fail
Change a default valueYes, silentlyThe worst kind: no call site changes, every rendered output does, and nothing warns

Part 5 — Reference Identity, the Prop Fact That Runs the Framework

function Parent() {
  const style  = { color: "red" };          // NEW object every render
  const items  = data.filter(d => d.ok);    // NEW array every render
  const onPick = () => select(id);          // NEW function every render
  return <Child style={style} items={items} onPick={onPick} />;
}

  Every one of those props is !== its previous value, even though
  nothing a user could perceive has changed.

  CONSEQUENCES, in increasing severity:

  1. React.memo(Child) NEVER SKIPS.
     The shallow comparison sees three changed props. The memo is
     pure overhead — you pay for the comparison and re-render anyway.

  2. useEffect(…, [items]) RE-RUNS EVERY RENDER.
     If that effect fetches, you now have a request per render. If it
     also sets state, you have an infinite loop, and the stack trace
     points at the effect rather than at the prop that caused it.

  3. A context value rebuilt per render RE-RENDERS EVERY CONSUMER,
     no matter how deep or how memoized. (Context lesson.)

  THIS IS NOT A BUG TO FIX EVERYWHERE.

  Creating objects during render is normal, idiomatic, and cheap. The
  allocation is not the problem — a re-render of a subtree that did not
  need it is, and only sometimes.

  The skill is KNOWING it is happening, so that when a memoized child
  re-renders or an effect loops, prop identity is the first thing you
  check rather than the last.
🔑 The question behind a large share of React interviews is "why does this memoized component still re-render?" The answer is nearly always that some prop is a fresh reference each render — an inline object, an array from map or filter, an arrow function, or JSX children. The fixes — useMemo, useCallback, hoisting constants, restructuring so the value is not rebuilt — live in useMemo & useCallback. The diagnosis lives here, and it is the more valuable half: applying the fixes without the diagnosis is how codebases end up with useCallback on everything and no measurable difference.

  WHAT TYPES BUY OVER RUNTIME CHECKS (legacy PropTypes):
    - errors at compile time, not console warnings nobody reads
    - autocomplete at every call site
    - refactors that cannot miss a caller
    - the ability to make illegal states unrepresentable:

  PropTypes survives in older codebases — recognise it, do not start

Interview Questions

Beginner: Why are props read-only, and how does anything ever change?

Read-only props are what make a render a pure function of its inputs. React needs to be able to call your component again at any time — because a parent re-rendered, because Strict Mode double-invokes, because a concurrent render was discarded and restarted — and get the same result. If children could write to their props, the same inputs would produce different outputs depending on call order.

Change happens through "data down, events up". The parent owns the value in state and passes it down; it also passes a callback; the child invokes the callback with what happened; the parent updates its state, and new props flow down on the next render.

The useful consequence is that data has exactly one owner. When a value is wrong, there is one place that writes it, and you find that place by walking up the tree — which is a very different debugging experience from a system where any component can write anywhere.

Beginner: How do you give a prop a default value?

Destructuring defaults in the signature: function Button({ variant = "primary" }). It is plain JavaScript, not a React feature.

The detail that matters is when it applies: only when the prop is undefined — either absent or explicitly passed as undefined. It does not apply to null, which passes straight through. So <Button variant={null} /> gives you null, not "primary", and that is a real bug source when the value comes from an API where "no value" is encoded as null.

Class components used a static defaultProps, and that has been removed for function components — recognise it in old code, do not write it.

Mid: What breaks when you mutate an object prop in place?

Everything that decides whether work is needed, because all of it compares by reference.

Concretely: React.memo's shallow comparison sees an equal prop and skips a render that was needed. A useEffect with that object in its dependency array does not re-run. If the object also lives in the parent's state, the parent will not re-render either, because setting state to the same reference is a no-op. The data changed and nothing was notified.

What you observe is a value that is correct in the console and wrong on screen, which appears to fix itself whenever something unrelated triggers a render. That intermittency is why these get closed as "could not reproduce".

The trap I would specifically call out is sort() and reverse(). They look like pure expressions because they return an array — but it is the same array, reordered, so const cheapest = items.sort(…)[0] quietly reorders the parent's data. The modern non-mutating versions are toSorted and toReversed, and a spread before sorting works everywhere.

Mid: Why is useState(props.value) usually a bug?

Because useState's argument is an initial value — it is read on the first render of that component instance and ignored on every subsequent one. So the copy captures whatever props.value was at mount and keeps it forever, and when the parent passes a new value the child keeps showing the old one.

It is a particularly nasty bug because it works in every test that mounts the component with fixed props, and only fails when the prop changes on an already-mounted instance — for example, an editor panel where the user selects a different record and the form still shows the previous one's values.

There are two correct designs and it is worth naming which you want. Fully controlled: render straight from the prop and report changes through a callback, so there is only one copy of the value and it cannot go stale. Explicitly initial: keep the local state, but name the prop defaultValue so callers know it is only a seed — and add key={recordId} at the call site so a different record remounts the component and re-seeds it.

The design I would push back on is the third option people reach for — syncing with a useEffect that calls setValue(props.value). It works, but it renders once with the wrong value before correcting itself, which is a visible flash, and it doubles the renders for every parent update.

Senior: Does passing an inline arrow function as a prop matter?

It depends entirely on who receives it, and the ability to say which case you are in is the actual senior signal here.

It does not matter for a plain DOM handler on an unmemoized child. That child re-renders with its parent regardless, so a stable function identity saves nothing — and the allocation itself is negligible.

It does matter in three cases. When the receiver is wrapped in React.memo, a fresh function defeats the comparison and the memo becomes pure overhead. When the function lands in a dependency array, the effect re-runs every render — and if that effect fetches or sets state, you have a request per render or an infinite loop. And when it is part of a context value, every consumer in the subtree re-renders no matter how well memoized they are.

So the answer is not "always useCallback". Premature memoization has a real cost: a dependency array to maintain, one more thing to get wrong, and noise that hides the places where memoization is load-bearing. I would reach for it when a consumer measurably needs it, and I would find that out from the DevTools Profiler rather than by inspection.

Worth adding that the React Compiler changes this calculus — it memoizes automatically, and the hand-written useCallback layer becomes largely unnecessary. That is a reason to be conservative about adding it by hand today.

Senior: How would you design the prop API for a component used by thirty teams?

I would treat it as a published API with the same discipline as an HTTP one, because the constraint is identical: you cannot change every caller at once, and some of them will not upgrade for months.

Keep the surface minimal. Every prop is permanent maintenance and a combination to test. The cheapest prop is the one not added — and content that varies belongs in children or an element slot rather than in a growing set of configuration flags, because slots accept requirements you have not thought of yet.

Make illegal states unrepresentable. Enums per axis rather than piles of booleans, so size cannot be both small and large. In TypeScript, a union that requires either children or an aria-label turns an accessibility rule into a compile error.

Name props for meaning, not markup. onSelect(id), never onTrClick — otherwise every caller depends on your internal structure and you can never change it.

Provide escape hatches. className and a ...rest spread to the root element, so a team with an unanticipated need can solve it without forking the component or filing a ticket that blocks them.

Additive changes only. New props are optional with defaults. A genuine breaking change gets a new name alongside the old, a deprecation period, and ideally a codemod — the same expand/contract shape as a database column or an API field.

The one I would emphasise because it is so often missed: changing a default value is a breaking change. No call site changes, so it passes review as a one-line diff, and every consumer's rendered output moves. It deserves the same process as removing a prop.

🏋️ Graded Exercises

1 (easy): Write Greeting taking name with a default of "friend", rendering "Hello, {name}!".
Solution 
function Greeting({ name = "friend" }) {
  return <p>Hello, {name}!</p>;
}

The detail being tested is when the default applies. It fires only for undefined — so <Greeting /> and <Greeting name={undefined} /> both say "friend", while <Greeting name={null} /> renders "Hello, !".

Why that matters in practice: APIs commonly encode "no value" as null, so <Greeting name={user.nickname} /> with a null nickname renders the broken string. If null is possible, coerce at the boundary — name={user.nickname ?? undefined} — or handle it in the component.

2 (easy): Spot the bug: function Total({ items }) { items.sort((a,b) => a.price - b.price); return <b>{items[0].price}</b>; }
Solution 
// sort() mutates IN PLACE and returns the SAME array. This component
// silently reorders its parent's data as a side effect of rendering.

// FIX — copy first
const cheapest = [...items].sort((a, b) => a.price - b.price)[0];

// or the non-mutating method (ES2023)
const cheapest = items.toSorted((a, b) => a.price - b.price)[0];

// or, since only the minimum is needed, skip the sort entirely:
const cheapest = items.reduce((lo, i) => (i.price < lo.price ? i : lo));
ConsequenceWhy it is hard to trace
The parent's array is reorderedThe reference is unchanged, so no re-render is scheduled — a sibling rendering the same array shows the new order only after some unrelated update
Render is no longer pureUnder Strict Mode it sorts twice; under concurrent rendering, an abandoned render has still mutated the data
Order depends on render countAlready-sorted input is idempotent, so it looks fine locally and misbehaves under load

The third fix is the one I would actually ship. Sorting to take the first element is O(n log n) for an O(n) question, and — more importantly — the bug only existed because the code reached for a sort it did not need. Removing the operation removes the whole class of error.

The general rule: a render must not change anything outside itself. A prop is outside itself.

3 (medium): Build Counter as a fully stateless component: props value, onIncrement, onDecrement, with the minus button disabled at 0.
Solution 
function Counter({ value, onIncrement, onDecrement, min = 0, max = Infinity }) {
  return (
    <div>
      <button type="button" onClick={onDecrement} disabled={value <= min}
              aria-label="Decrease">−</button>
      <span aria-live="polite">{value}</span>
      <button type="button" onClick={onIncrement} disabled={value >= max}
              aria-label="Increase">+</button>
    </div>
  );
}
DecisionReasoning
No internal state at allThe parent owns value, so the display can never disagree with the data, and the parent can clamp, validate or reject a change
min/max as props with defaultsThe rule "disabled at 0" was really "disabled at the minimum". Encoding the general rule costs nothing and is non-breaking
type="button"Buttons default to submit; inside a form these would submit it
aria-label on each button"−" and "+" are punctuation. A screen reader announces "minus button", which is not the intent
aria-live="polite" on the valueOtherwise a screen-reader user presses the button and hears nothing — the change is visual only

The disabled-button trade-off worth knowing: a disabled button is removed from the tab order, so a keyboard user tabbing through loses their place when it disables. An alternative is to keep it enabled with aria-disabled="true" and ignore the click, which preserves focus and still announces the state. For a counter, plain disabled is fine; for a form's submit button it usually is not.

Why stateless is the right default here: the moment two things need the count — this widget and a total elsewhere — a stateful version needs syncing, and syncing two copies of one value with an effect is the most common state bug in React. Starting stateless means that requirement costs nothing.

4 (medium): Refactor this prop API and justify each change: <Modal isSmall isLarge isDanger showCloseX titleText="Hi" bodyText="…" />
Solution 
<Modal size="sm" tone="danger" dismissible title="Hi">
  <p>…</p>
</Modal>
ChangeWhy
isSmall isLarge → size="sm"Both booleans could be true at once. What does the component do then? Whatever the if ordering happens to do — an undefined behaviour that a reviewer cannot check. An enum makes it unrepresentable
isDanger → tone="danger"Leaves room for warning and success without a new boolean each time — and without the same both-true problem
showCloseX → dismissibleNames the capability, not the pixel. If the design later uses a "Cancel" button instead of an X, the prop name is still accurate
bodyText → childrenA string prop caps the slot at plain text. The first request for a link or a list inside the modal forces a second prop or dangerouslySetInnerHTML
titleText → titleText describes the type, which the type system already states

Why title stays a string while body becomes children: the modal genuinely needs the title as a value — for aria-labelledby, for the document title, possibly for analytics. Body content is markup nobody needs to inspect. That is the test for string-versus-slot, and it is not "which is more flexible".

The counting argument for enums: four booleans are sixteen states, of which perhaps five are legal, and a test suite cannot tell the difference. Two enums with three and four values are twelve states, all legal.

What I would add that is not in the original: onClose. As written, dismissible says a close affordance exists but nothing says what it does — and a modal that cannot tell its parent it closed cannot be controlled by that parent.

5 (medium): A parent renders <Child config={{ theme: "dark" }} /> and Child is wrapped in React.memo. Why does it re-render every time, and what are the fixes?
Solution 
// The object literal is evaluated on every parent render, producing a NEW
// reference. memo does a SHALLOW comparison:
//
//   prevProps.config === nextProps.config   ->  false
//
// so it re-renders. The contents are identical; memo never looks at them.
FixWhen it is the right one
const CONFIG = { theme: "dark" }; at module scopeThe value never changes. Simplest, zero runtime cost, no dependency array — the correct answer here
useMemo(() => ({ theme }), [theme])The object is derived from props or state. Costs a dependency array you must keep correct
<Child theme="dark" />Flatten to scalars — strings compare by value, so the problem disappears. Usually the best fix when the object has one or two fields
Remove the memoGenuinely worth considering. If Child is cheap, memo plus a defeated comparison is slower than just rendering

The point I would make in review is that the memo was already useless before this bug. Someone added it for performance, and it never skipped a single render — so the codebase carries the maintenance cost of a memoized component and gets nothing. That is the usual outcome of memoizing by habit rather than from a profile.

The same trap with children, which is less obvious: <MemoChild><p>hi</p></MemoChild> also re-renders every time, because children is a fresh element object per render and is compared like any other prop.

6 (hard): Implement the v3 interactive Rating, then add a readOnly prop that wins even when onChange is passed. What should a screen reader user perceive?
Solution 
function Rating({ value, max = 5, onChange, readOnly = false, label = "Rating" }) {
  const interactive = !readOnly && typeof onChange === "function";

  if (!interactive) {
    // A display rating is not a control. Do not render buttons at all.
    return (
      <span role="img" aria-label={`${label}: ${value} of ${max}`}>
        {"★".repeat(value)}{"☆".repeat(max - value)}
      </span>
    );
  }

  return (
    <span role="radiogroup" aria-label={label}>
      {Array.from({ length: max }, (_, i) => (
        <button
          key={i}
          type="button"
          role="radio"
          aria-checked={i + 1 === value}
          aria-label={`${i + 1} of ${max}`}
          onClick={() => onChange(i + 1)}
        >{i < value ? "★" : "☆"}</button>
      ))}
    </span>
  );
}

readOnly beats onChange because explicit intent should beat inferred capability. The capability switch — "interactive if a callback was passed" — is convenient, but a parent may well pass a handler and still want a read-only view in a particular context. Without an explicit prop it has to pass undefined conditionally, which is the same information expressed worse.

DecisionWhy it differs from the naive version
Non-interactive renders no buttonsDisabled buttons are still announced as buttons and clutter the tab order. A display rating is an image with a label, and that is what a screen reader should hear
radiogroup / radio, not five buttonsIt is a single-choice control. Five unrelated buttons give no sense of "3 of 5 selected"; a radio group announces exactly that
aria-label per starThe accessible name of each option must be its value. "★" announces as nothing useful
aria-checked on the selected oneThis is the state the user is choosing. Without it the group has no current value

What a screen reader user should perceive: in read-only mode, a single labelled value — "Rating: 3 of 5" — and nothing focusable, because there is nothing to do. In interactive mode, a radio group named "Rating" with five options where the third is selected, navigable with arrow keys like any radio group.

The gap this still has: a real radio group supports arrow-key navigation with a single tab stop, which buttons do not give you for free — the honest options are to implement roving tabindex or to use actual <input type="radio"> elements with visually hidden inputs and styled labels. The second is less code and more robust, and is what I would ship.

Why the order matters: these are ranked by likelihood times cost-to-check, not by subtlety. The Profiler answers 1, 2 and 5 in one look, so the tool comes before the theory — and I would open it before reading any of the code.

The question worth asking before fixing any of them: what is the re-render actually costing? If Form renders in under a millisecond, the correct action is to delete the memo and its whole dependency-management burden. Memoization is a performance tool, and applying it without a measurement means paying its costs for an unknown benefit — which is exactly the situation this exercise describes.

🎯 Key Takeaways

  • Props are the component's public API — one-way, read-only, and the only sanctioned input besides context. Design them as if you will maintain them for years, because you will.
  • "Data down, events up": the parent owns state and passes onXxx callbacks; the child reports semantic events and never presumes what happens next.
  • Put state in the lowest component that needs it, and lift only when something else needs it. Too low forces two copies to be synced; too high re-renders the world on every keystroke.
  • Never mutate through a prop. The reference is unchanged, so React, memo and every dependency array conclude nothing happened — the data and the screen diverge.
  • sort() and reverse() mutate and return the same array; toSorted/toReversed or a spread are the safe forms.
  • React answers "did this change?" with === — so a new object with equal contents counts as changed, and a mutated object counts as unchanged.
  • Every render rebuilds inline objects, arrays and functions. Harmless by default; decisive when the consumer memoizes, depends on it, or provides it as context.
  • Diagnose identity before reaching for useCallback — memoizing by habit costs a dependency array and usually buys nothing.
  • useState(props.value) freezes at mount. Stay controlled, or name it defaultValue and reset with a key.
  • Syncing a prop into state with an effect renders the wrong value first — a visible flash, and double renders forever.
  • Enums over boolean piles — four booleans are sixteen states, most of them illegal.
  • Pass sources, not derivatives — items and count will drift.
  • Name events for meaning, not markup. onSelect survives the table becoming a list; onTrClick does not.
  • Changing a default value is a breaking change with an empty diff at every call site — the sneakiest one in a shared component.
  • An optional callback is a capability switch, but explicit intent (readOnly) should beat inferred capability.
  • Types are the contract: a union that demands children or an aria-label turns an accessibility rule into a compile error.
