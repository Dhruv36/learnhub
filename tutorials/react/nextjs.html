Next.js Essentials Full-Stack React

What you'll master: what a framework actually buys you over a Vite SPA — routing, SSR/SSG, bundling, image and font optimisation, an HTTP layer — and the coupling you pay for it; the App Router and the Pages Router as two live models with different defaults; the file conventions (page, layout, loading, error, not-found, template) and why a nested layout preserves state across navigation while a template does not; the four rendering strategies and what silently turns a static route dynamic; the four caching layers and how much of this reversed between Next 14 and 15; route handlers versus server actions; what middleware cannot do at the edge, and why it is not an auth boundary; the NEXT_PUBLIC_ build-time inlining trap; and an honest comparison with React Router v7, Astro, and staying on a plain SPA. Prerequisites: Server Components.

Part 1 — What Next.js Provides, and What It Costs

  START FROM THE HONEST BASELINE. A Vite React SPA is one HTML file,
  one JS bundle, and a client-side router. That is genuinely fine for
  a large class of apps. What a framework adds:

    1. FILE-BASED ROUTING. app/blog/[slug]/page.tsx IS the route
       /blog/:slug. No route table to keep in sync, and per-route
       code splitting for free — in a Vite SPA you get that only if
       you wrote React.lazy yourself.

    2. A SERVER. Not "SSR" as a checkbox — an actual request/response
       lifecycle you can put code in: route handlers, server actions,
       middleware, server components.

    3. RENDERING STRATEGY PER ROUTE. Static at build, dynamic per
       request, revalidated on an interval, or streamed — chosen per
       route, not per app. This one has no SPA equivalent at all.

    4. A BUILD YOU DID NOT CONFIGURE. Route chunking, tree shaking,
       CSS extraction, NODE_ENV set correctly. Worth more than people
       admit.

    5. next/image AND next/font. Both exist to solve one MEASURED
       problem — layout shift — plus format negotiation and font
       self-hosting. Part 7.

    6. AN HTTP LAYER. app/api/*/route.ts is a real endpoint in the
       same repo, same types, same deploy.

  THE COST, STATED PLAINLY:

    COUPLING. Your components now encode framework caching semantics.
    A component that calls cookies() cannot be rendered statically,
    and nothing in its signature says so.

    A BUILD YOU DO NOT CONTROL. "Why is this route dynamic" is a
    question a Vite app never has to ask, and it has no stack trace.

    VERSION CHURN. The App Router shipped stable in 13.4 (May 2023);
    caching defaults REVERSED in 15. Guides written 18 months apart
    contradict each other and both look authoritative. Part 5.

    HOSTING GRAVITY. Everything works off Vercel too — you just now
    own the pieces Vercel was quietly providing. Part 7.

  THE DECISION RULE THAT ACTUALLY HOLDS. Does an anonymous user, or a
  crawler, need meaningful HTML in the first response?

    YES -> you need a server. Marketing, docs, e-commerce, anything
           with SEO or paid traffic.
    NO  -> a SPA is still correct. An internal dashboard behind SSO
           renders after auth anyway; SSR buys it nothing and costs
           it a server to operate. Do not adopt a framework for a
           login wall.

Part 2 — Two Routers, and the File Conventions

  BOTH ROUTERS ARE SUPPORTED IN THE SAME APP AT THE SAME TIME. Not a
  hack — the documented incremental path. A request matches app/
  first, then pages/. Defining the same path in both is a build
  error, not a silent precedence rule.

  THEY DIFFER IN ONE FUNDAMENTAL WAY:

    PAGES ROUTER: a page is a CLIENT component. Data arrives from
    getServerSideProps / getStaticProps as a SERIALISED PROPS OBJECT.
    The server/client boundary is a function you can see.

    APP ROUTER: a page is a SERVER component by default. You await
    data in the component itself. The boundary is a directive at the
    top of a file — much easier to cross by accident.

  WHAT IS ACTUALLY DIFFERENT, NOT MARKETING:

    - LAYOUTS. Pages has _app.tsx — one global wrapper; per-page
      layouts are a userland getLayout pattern. App has real nested
      layouts. The biggest practical win.
    - STREAMING. Pages SSR is all-or-nothing: the response is sent
      when getServerSideProps resolves. App streams.
    - BUNDLE. A server component ships ZERO JS. In Pages, every page
      component is in the client bundle.

  FILE CONVENTIONS. Only these filenames are special — which is why
  you can colocate components, tests and CSS inside a route folder
  without every file becoming a URL.

    app/dashboard/
      page.tsx      the route's UI. WITHOUT THIS FILE THE SEGMENT IS
                    NOT ROUTABLE — a folder with only a layout 404s.
      layout.tsx    wraps page.tsx AND every nested route below.
                    Receives {children}. The root one renders
                    html/body.
      loading.tsx   sugar: wraps the segment in
                    <Suspense fallback={<Loading />}>. That is all.
      error.tsx     a segment error boundary. MUST be 'use client' —
                    error boundaries need componentDidCatch, which
                    only exists on the client.
      not-found.tsx rendered by notFound() and for unmatched paths.
      template.tsx  like layout, but REMOUNTS on every navigation.
      route.ts      an HTTP endpoint. Cannot coexist with page.tsx.

  THE ERROR-NESTING TRAP. error.tsx renders INSIDE its own segment's
  layout. So if app/dashboard/layout.tsx throws, app/dashboard/
  error.tsx cannot catch it — the boundary is below the thing that
  failed, and the PARENT segment's boundary handles it. The root
  layout has no parent, which is why global-error.tsx exists and why
  it must render its own <html> and <body>.

  WHY A NESTED LAYOUT PRESERVES STATE — THE ACTUAL MECHANISM:

  Navigating /dashboard/reports -> /dashboard/settings does not
  reload the page. The router diffs the segment path, keeps the
  common prefix mounted, and swaps only the differing subtree.
  Reconciliation sees the same component type at the same position,
  so the layout's FIBER survives — and every useState on that fiber
  with it.

    /dashboard/reports         /dashboard/settings
      RootLayout      keeps ->  RootLayout
        DashLayout    keeps ->    DashLayout   <- survives: sidebar
          Reports    UNMOUNT        Settings      scroll, open
                                                  accordion, nav

  That is why a sidebar scroll position survives a tab change, and
  why an expensive layout-level subscription is not re-established on
  every navigation.

  template.tsx IS THE OPT-OUT. Same shape, but the router gives it a
  NEW KEY per navigation, so React unmounts and remounts it: state
  resets, effects re-run, enter animations replay. Use it only when
  you want exactly that. Reach for layout by default — template
  throws away the benefit you adopted layouts for.

Part 3 — Server by Default, 'use client' as the Opt-Out

  The full mechanism is in the Server Components lesson. What matters
  HERE is what the framework does with it, because Next.js is where
  most people meet RSC and the DEFAULT is the surprise.

  EVERY FILE UNDER app/ IS A SERVER COMPONENT unless something marks
  it otherwise. No useState. No useEffect. No onClick. No window.
  These are not discouraged — they throw at build time.

    app/page.tsx                          -> server (default)
    app/ui/Chart.tsx  with 'use client'   -> client
    app/ui/Legend.tsx imported by Chart   -> CLIENT TOO

  THAT LAST LINE IS THE ONE PEOPLE MISS. 'use client' does not mark a
  file. It marks a BOUNDARY: that module and everything it imports,
  transitively, is compiled into the client bundle. One directive at
  the top of a shared layout drags half your tree across.

  SO THE DIRECTIVE GOES AS DEEP AS POSSIBLE, NOT AS HIGH:

    BAD                             GOOD
    'use client' on DashboardPage   server DashboardPage
      Header     -> client            Header    stays server
      Chart      -> client            Chart     'use client'
      DataTable  -> client            DataTable stays server
      Footer     -> client            Footer    stays server
    everything ships                only Chart ships

  CHILDREN PASS THROUGH THE BOUNDARY. A client component can RENDER
  server-rendered children — it just cannot IMPORT them.

    // Tabs.tsx  ('use client')
    export function Tabs({ panel }) {
      const [open, setOpen] = useState(false);
      return <div>{open && panel}</div>;   // panel is a prop
    }

    // page.tsx  (server)
    <Tabs panel={<ServerTable rows={await db.rows()} />} />

  The server already rendered ServerTable to a payload; Tabs only
  holds the resulting element. This is the composition trick that
  keeps the client boundary small, and it is under-taught.

  NEEDS 'use client': state and effects, event handlers, window /
  document / localStorage, context providers, most third-party UI
  libraries, and error.tsx always.

  DOES NOT, though people add it anyway: a component that only reads
  props and renders markup; one that awaits data; one that merely
  RENDERS a client component; a file importing only a type from a
  client module (types erase at compile time).

  THE HONEST STATE OF ADOPTION: RSC is stable and is the direction
  Next.js has chosen, but the ecosystem is uneven — libraries without
  'use client' in their published build have to be wrapped, and some
  state libraries needed rewrites. A team still shipping features on
  a 2022 Pages Router app is not wrong to wait. Adopt it for what it
  does — less JS on the client, no client/server data waterfall —
  not because it is newer.

Part 4 — Four Rendering Strategies, and Going Dynamic by Accident

  A ROUTE HAS ONE OF FOUR BEHAVIOURS, and you rarely pick explicitly
  — the framework INFERS it from what your code touched. That
  inference is the source of most Next.js confusion.

  1. STATIC. HTML + RSC payload generated once during `next build`,
     served from a CDN. TTFB ~20ms. The default when nothing dynamic
     is touched.

  2. DYNAMIC. Runs on every request; TTFB is your slowest await, paid
     by every user. Correct when the response genuinely differs per
     user.

  3. ISR. Serve the cached copy; after `revalidate` seconds the NEXT
     request triggers a background regeneration AND STILL GETS THE
     STALE COPY. The request that triggers regeneration is not the
     one that waits — that is the whole point, and the part people
     expect wrongly.

       export const revalidate = 60;

     Plus on-demand: revalidatePath('/blog/[slug]') or
     revalidateTag('posts') from an action or a CMS webhook. Use the
     on-demand form as the plan; time-based is a safety net.

  4. STREAMING. The shell is sent immediately; slow subtrees arrive
     later inside Suspense boundaries.

       <Suspense fallback={<Skeleton />}>
         <SlowRevenueChart />      {/* 800ms */}
       </Suspense>

     Without it a 60ms shell waits 800ms for the chart. With it the
     user sees nav and skeleton at 60ms. TOTAL time is identical.
     PERCEIVED time is not. Streaming re-orders bytes; it does not
     make anything faster.

  HOW A ROUTE SILENTLY BECOMES DYNAMIC. Calling ANY of these ANYWHERE
  in the route's server tree — including a utility three files deep —
  opts the WHOLE route out of static rendering, with no error and no
  warning:

    cookies()            <- the usual culprit
    headers()
    draftMode()
    searchParams (the prop; or useSearchParams in a child)
    connection()  /  the older noStore()
    fetch(..., { cache: 'no-store' })
    export const dynamic = 'force-dynamic'

  THE CLASSIC INCIDENT. Someone adds theming to the root layout:

    const theme = (await cookies()).get('theme')?.value ?? 'light';

  Every route in the app is now dynamic. The build output changes
  from circles to lambdas, sitewide TTFB goes from 20ms to 300ms, and
  the PR that caused it is three lines and looks harmless.

  HOW TO SEE IT — THIS IS THE ACTUAL SKILL. `next build` prints a
  legend per route, and you should read it on every deploy:

    Route (app)                    Size    First Load JS
    ┌ ○ /                          1.2 kB      98 kB
    ├ ● /blog/[slug]               2.1 kB     101 kB
    ├ ƒ /dashboard                 3.4 kB     140 kB
    └ ƒ /api/health                0 B          0 B

    ○ Static   ● SSG (generateStaticParams)   ƒ Dynamic

  A ƒ you did not intend is a bug. DIFF THIS OUTPUT BETWEEN BUILDS —
  the cheapest performance regression test you will ever add.

  THE FIX IS ALWAYS THE SAME SHAPE: push the dynamic read DOWN into a
  small leaf and wrap it in Suspense. The page stays static; the
  personalised sliver streams in.

    <Suspense fallback={<GenericHeader />}>
      <PersonalHeader />   {/* only this calls cookies() */}
    </Suspense>

  Next 15's Partial Prerendering (experimental) formalises exactly
  this: one route, static shell, dynamic holes. Do not ship an
  experimental flag, but understand the shape — it is the direction.

Part 5 — Data Fetching and the Four Caches

  In a server component you fetch by awaiting. No useEffect, no
  loading state, no race condition, no client/server waterfall.

    export default async function Page({ params }) {
      const { slug } = await params;          // async since Next 15
      const post = await db.post.find(slug);  // runs on the server
      return <Article post={post} />;
    }

  PARALLELISE SIBLINGS OR YOU HAVE REBUILT THE WATERFALL ON THE
  SERVER. Sequential awaits are sequential everywhere:

    const user  = await getUser();     // 200ms
    const posts = await getPosts();    // 200ms  -> 400ms

    const [user, posts] = await Promise.all([   // -> 200ms
      getUser(), getPosts(),
    ]);

  Sequence them only when the second genuinely needs the first.

  THE FOUR CACHES. Four layers, different scopes, different
  lifetimes, different invalidation — and one shared symptom, "my
  data is stale", which is why people fix the wrong one.

    1. REQUEST MEMOIZATION.  Scope: one render pass.  Life: ms.
       Duplicate fetch() calls to the same URL in one request return
       one response. This is what makes colocated fetching viable —
       a layout and three children can each ask for the user without
       three round trips.

    2. DATA CACHE.  Scope: the deployment.  Life: until revalidated.
       Persists ACROSS requests, users and deploys. Controlled by
       fetch(url, { next: { revalidate: 60, tags: ['posts'] } }),
       cleared by revalidateTag / revalidatePath.

    3. FULL ROUTE CACHE.  Scope: deployment.  Life: until revalidated.
       The rendered HTML + RSC payload of a static route. This is
       what makes a static route a CDN hit.

    4. ROUTER CACHE (client).  Scope: one tab.  Life: seconds.
       RSC payloads of visited routes, held in memory so Back is
       instant. THE ONE THAT BURNED EVERYONE: in Next 14 it held
       dynamic pages for 30 seconds with no per-route opt-out, so a
       user who submitted a form, navigated away and came back saw
       their OLD data.

  WHAT CHANGED, BECAUSE HALF THE INTERNET IS NOW WRONG:

    fetch() default        14: cached      15: NOT cached
    GET route handlers     14: cached      15: not cached
    Client router cache    14: 30s pages   15: 0s pages, 5min layouts
    cookies/headers/params 14: sync        15: ASYNC, must be awaited

  If an article disagrees with your behaviour, check the version
  before you check your code. Both are correct for their release. The
  direction is unambiguous: caching moved from implicit-on to
  explicit-opt-in, because implicit-on produced silent staleness
  nobody could trace.

  BEFORE YOU THEORISE, TURN ON THE LOG:

    // next.config.js
    logging: { fetches: { fullUrl: true } }

  It prints HIT or SKIP per fetch, and why.

  AND INVALIDATION IS DISTRIBUTED. revalidateTag reaches the INSTANCE
  that received the call. On one Vercel deployment that is invisible;
  on three self-hosted pods with the default filesystem cache it
  means content flips depending on which pod answered. Exercise 6.

  WHAT ABOUT REACT QUERY / SWR? Still correct for CLIENT-side,
  user-driven state: polling widgets, infinite lists, and optimistic
  mutations with rollback. The server cache serves the initial
  render; a client query cache serves interaction. They are not
  competitors, and they do not overlap. What you
  should NOT do is fetch your initial page data in a client effect
  inside a framework that could have fetched it on the server — you
  paid for the server and are still shipping a spinner.

Part 6 — Route Handlers, Server Actions, and Middleware

  THREE WAYS TO RUN SERVER CODE. Not interchangeable, and choosing
  wrongly is a common design mistake.

  ROUTE HANDLERS — app/api/things/route.ts

    export async function POST(req: Request) {
      const body = await req.json();
      return Response.json({ id: 1 }, { status: 201 });
    }

  Plain Web Request/Response, one export per verb. Use when the
  caller is NOT your own React tree: a mobile app, a Stripe webhook,
  a cron job, an OAuth callback, a file download — anything needing a
  status code or a custom content type.

  SERVER ACTIONS — an async function marked 'use server'

    async function createPost(formData: FormData) {
      'use server';
      const title = formData.get('title');
      if (typeof title !== 'string' || !title.trim())
        return { error: 'Title required' };
      await db.post.create({ title });
      revalidatePath('/posts');
      redirect('/posts');
    }

    <form action={createPost}>…</form>

  Use when the caller IS your React tree. You get progressive
  enhancement — the form submits before hydration, because it is a
  real form POST — plus typed arguments and cache revalidation in the
  same call.

  THE THING THAT MUST BE SAID LOUDLY:

    A SERVER ACTION IS A PUBLIC HTTP ENDPOINT.

  The framework generates an ID and posts to it. Anyone can call it
  with any payload. It is not "inside" your component in any security
  sense. So in EVERY action: AUTHENTICATE (re-check the session),
  AUTHORIZE (is this user allowed to touch THIS row — the hidden
  input carrying the id is attacker-controlled), VALIDATE (parse with
  a schema; FormData values are strings or Files, never the type you
  assumed).

  The failure mode is not theoretical. An action that deletes a
  postId, on a page that only renders your own posts, deletes
  ANYONE'S post. The gate was on the render; the render is not the
  endpoint.

  MIDDLEWARE — middleware.ts at the project root

    export function middleware(req: NextRequest) {
      if (!req.cookies.get('session'))
        return NextResponse.redirect(new URL('/login', req.url));
      return NextResponse.next();
    }
    export const config = { matcher: ['/dashboard/:path*'] };

  It runs BEFORE routing and before the cache, on every matched
  request, on the EDGE RUNTIME by default — a V8 isolate, not Node.

  WHAT IT CANNOT DO, the list that saves you a day:

    - No Node built-ins: fs, net, child_process, node:crypto.
    - No TCP, so most database drivers do not work: pg, mysql2,
      Prisma's standard client. HTTP-based drivers do.
    - No long work. Tens of milliseconds, not seconds.
    - A small bundle budget (~1MB on Vercel) — a big auth SDK
      blows it.
    - It cannot render. Rewrite, redirect, or set headers/cookies.
      That is the entire API surface.

  AND THE SECURITY POINT: MIDDLEWARE IS NOT AN AUTH BOUNDARY. It is a
  routing convenience. CVE-2025-29927 was exactly this — a crafted
  x-middleware-subrequest header let requests skip middleware
  entirely, and every app treating a middleware redirect as its only
  access control was exposed. Check the session AGAIN in the page,
  the route handler and the action. Middleware saves a render; it
  does not protect data.

  A GOOD MIDDLEWARE IS A CHEAP CHECK: does a session cookie EXIST
  (not: is it valid) -> if not, redirect. Locale detection. A/B
  bucket assignment. A request id. Everything else belongs deeper in.

Part 7 — Images, Fonts, Env Vars, and Where This Runs

  next/image AND next/font EXIST FOR ONE MEASURED REASON: Cumulative
  Layout Shift. CLS scores unexpected movement of visible content;
  "good" is under 0.1, and a hero image with no dimensions routinely
  scores 0.25 on its own.

  THE MECHANISM. A plain <img src> occupies ZERO height until the
  bytes arrive and the browser learns the intrinsic size. Everything
  below it then jumps. next/image requires width and height (or
  fill), emits them as an aspect-ratio box, and the space is reserved
  from first paint. Nothing moves.

    plain img            CLS ~0.25, 1.8MB PNG
    next/image           CLS 0,     ~180KB AVIF/WebP

  It also negotiates format from the Accept header, emits a srcset
  for device widths, and lazy-loads below the fold. `priority` turns
  lazy OFF and adds a preload — put it on your LCP image and ONLY
  that one. Marking everything priority preloads nothing.

  next/font DOES TWO THINGS:

    import { Inter } from 'next/font/google';
    const inter = Inter({ subsets: ['latin'], display: 'swap' });

    1. SELF-HOSTS. Downloaded at build, served from your origin — no
       DNS + TLS + RTT to fonts.gstatic.com on the critical path, and
       no third party in your privacy story.
    2. INJECTS AN ADJUSTED FALLBACK. It computes size-adjust,
       ascent-override and descent-override so the fallback occupies
       nearly the same box as the real font. The swap still happens;
       it just stops moving the layout. This is the part people do
       not know exists, and it is why next/font beats a hand-rolled
       @font-face.

  METADATA. export const metadata for static, generateMetadata for
  dynamic routes — and its fetches are deduped with the page's own
  (cache layer 1), so asking for the post twice costs one request.
  Two traps: metadata exports only work in SERVER components, so
  'use client' at the top of a page silently kills them with no
  warning; and without metadataBase your OG image URLs stay relative
  and no crawler resolves them.

  ENVIRONMENT VARIABLES — THE LEAK THAT KEEPS HAPPENING:

    DATABASE_URL=postgres://...      server only
    NEXT_PUBLIC_ANALYTICS_ID=abc     INLINED INTO THE BUNDLE

  NEXT_PUBLIC_ is not "shared". It is a TEXT SUBSTITUTION at BUILD
  time: process.env.NEXT_PUBLIC_X is replaced with the literal string
  in the JS your users download. It is as public as your logo.

    THE INCIDENT: someone needs a key in a client component. The
    unprefixed var reads as undefined there, so they add the prefix
    to "make it work". The key is now in a static chunk on a CDN, in
    every browser cache, and in any archive that crawled you —
    and rotating it needs a rebuild AND a purge.

    CHECK IT IN TEN SECONDS:  grep -r "sk_live" .next/static/

    THE GUARD: put `import 'server-only'` at the top of any module
    that touches a secret. If a client component ever imports it,
    even transitively, THE BUILD FAILS. A compile error instead of
    an incident.

    SECOND TRAP: because inlining happens at build time, you cannot
    promote one Docker image from staging to production if a
    NEXT_PUBLIC_ value differs. Build per environment, or fetch
    runtime config from an endpoint.

  DEPLOYING OFF VERCEL. It works — you are reimplementing services
  that were previously invisible. output: 'standalone' gives you a
  minimal server.js plus only the traced node_modules (~100MB image
  instead of ~1GB). What gets harder:

    IMAGE OPTIMISATION. /_next/image is served by your Node process.
    Install sharp and put a CDN in front, or you resize the same hero
    on every cold start.

    ISR ACROSS INSTANCES. The default cache is the local filesystem,
    so three pods are three independent caches. See Exercise 6.

    STREAMING. Anything that buffers the response — some reverse
    proxies, some serverless gateways — turns streaming back into
    all-or-nothing SSR. It does not error. Your Suspense boundaries
    simply stop doing anything.

    MIDDLEWARE. No edge network, so it runs in your Node process on
    every request, adding latency rather than removing it.

  THE ALTERNATIVES, FAIRLY:

    REACT ROUTER v7 (the merged Remix). Loaders and actions, close to
    web standards, one cache model instead of four. Easier to reason
    about and to self-host; smaller ecosystem, younger RSC story.

    ASTRO. Ships zero JS by default and hydrates islands on demand.
    For docs, blogs and marketing it beats Next.js on both bundle
    size and simplicity, and it renders your React components
    happily. Wrong choice for a highly interactive app.

Interview Questions

Beginner: What does Next.js give you that a plain React SPA does not?

Four things that a SPA structurally cannot have, and two it merely makes tedious. The structural ones: a server — an actual request/response lifecycle where route handlers, server actions and server components run; server rendering, so the first response contains real HTML rather than an empty root div; a per-route rendering strategy, so a marketing page can be static on a CDN while a dashboard is rendered per request in the same app; and streaming, where a fast shell is sent before slow sections finish.

The tedious ones: file-based routing with automatic per-route code splitting, and a production build configuration you did not write. Plus next/image and next/font, which exist to solve a specific measured problem — layout shift — rather than as convenience wrappers.

The cost is coupling. Your components now encode framework caching semantics: a component that calls cookies() makes its whole route dynamic, and nothing in its signature says so. You are also debugging a build system you do not own.

The test I would apply: does an anonymous user or a crawler need meaningful HTML on the first response? If no — an internal dashboard behind SSO, say — a Vite SPA is still the right answer and adopting a framework buys you a server to operate and nothing else.

Beginner: What is the difference between layout.tsx and template.tsx?

Both wrap a route segment and receive children. The difference is what happens on navigation. A layout persists: navigating between two sibling routes under it keeps the layout mounted, so its useState, scroll position, open accordions and subscriptions all survive. A template remounts: the router gives it a fresh key on every navigation, so React unmounts the old instance and mounts a new one. State resets and effects re-run.

The mechanism is ordinary reconciliation. The router diffs the segment path, keeps the common prefix mounted, and swaps only the differing subtree. Same component type at the same position means the same fiber, and the same fiber means the same hook state.

Default to layout. It is the reason nested layouts are the App Router's biggest practical win over _app.tsx. Reach for template only when you specifically want the remount: a per-route enter animation that must replay, or an analytics effect that must fire once per view.

Mid: A route you expected to be static is being rendered on every request. How do you find out why?

Start with next build. It prints a legend per route: ○ static, ● prerendered with generateStaticParams, ƒ dynamic. That tells you which routes flipped, which is usually more than the one you noticed — the cause is often in a shared layout, so the whole subtree went with it.

Then look for the opt-outs. Anywhere in that route's server tree, including a utility several files deep: cookies(), headers(), draftMode(), reading the searchParams prop, connection(), fetch with cache: 'no-store', or an explicit export const dynamic = 'force-dynamic'. Any one of them opts the entire route out of static rendering, silently.

The classic cause is three lines in the root layout — someone reading a theme cookie. Every route in the app becomes dynamic, TTFB goes from a 20ms CDN hit to a 300ms origin render sitewide, and the PR looks harmless.

The fix is always the same shape: push the dynamic read down into a small leaf component and wrap it in <Suspense>. The shell stays static and the personalised sliver streams in. Then make it a regression test — diff the build's route legend between deploys. It is the cheapest performance check you will ever add, and it catches this class of change before it ships.

Mid: When do you use a route handler and when a server action?

Decide by who calls it. If the caller is your own React tree — a form submission, a button that mutates data — use a server action. You get progressive enhancement, because a <form action={fn}> is a real form POST that works before hydration; type-safe arguments instead of hand-serialised JSON; and cache revalidation in the same call via revalidatePath/revalidateTag.

If the caller is anything else — a mobile client, a Stripe webhook, a cron job, an OAuth callback, a file download — use a route handler. You need control over the status code, headers and content type, and a server action gives you none of those; it returns a value, not a response.

NeedAnswer
Form mutation from your own UIServer action
Works with JS disabled / before hydrationServer action
Custom status code or headersRoute handler
Third-party webhook, signature verification on the raw bodyRoute handler
Streaming a file or a non-JSON content typeRoute handler

The point that matters more than the choice: both are public HTTP endpoints. A server action gets a generated ID and anyone can post to it. Authenticate, authorize and validate inside both — the gate you put on the page that rendered the form is not a gate on the endpoint.

Senior: Walk me through the caching layers, and why teams find them confusing.

There are four, with different scopes and lifetimes. Request memoization dedupes identical fetch calls within a single render pass — this is what makes colocated fetching viable, so a layout and three children can each ask for the user without three round trips. The data cache persists fetch results across requests, users and deploys until something revalidates it. The full route cache holds the rendered HTML and RSC payload for a static route, which is what makes it a CDN hit. The router cache lives in the browser and holds RSC payloads for visited routes so Back is instant.

The confusion has three sources. First, they compose: a stale page can be stale at any of the four layers and the symptom is identical, so people fix the wrong one — usually by reaching for force-dynamic, which disables static rendering to work around a cache problem.

Second, the defaults reversed between major versions. Next 14 cached fetch by default and held dynamic pages in the router cache for 30 seconds with no per-route opt-out — the notorious "I submitted a form, went back, and saw my old data" bug. Next 15 made fetch uncached by default and dropped page staleTime to 0. Every blog post is correct for its release and wrong for yours. Also in 15, cookies(), headers() and params became async, so code samples fail to compile across the boundary.

Third, invalidation is coarse and distributed. revalidateTag reaches the instance that received the call. On a single Vercel deployment that is invisible; on three self-hosted pods with the default filesystem cache it means content flips depending on which pod answers, until you wire a shared cache handler.

My recommendation for a new app: tag every fetch, revalidate on-demand from the CMS webhook rather than on a timer, turn on logging.fetches in development so you can see HIT/SKIP per request, and pin the Next version in docs and onboarding. Treat time-based revalidate as a safety net, not the plan. And resist force-dynamic — every use I have reviewed was a cache bug being papered over at the cost of every user's TTFB.

Senior: A team wants to move a working Vite SPA to Next.js. How do you evaluate that?

Start by asking what the migration is supposed to fix, and insist on a measurable answer. "Slow first paint on marketing pages" is measurable. "Google does not index our product pages" is measurable. "It is the modern way" is not, and neither is "we want server components".

Then apply the test: does an anonymous user or a crawler need meaningful HTML on the first response? For a public, content-heavy, SEO-dependent product the answer is yes and Next.js earns its cost. For an internal dashboard behind SSO the answer is no — the page renders after auth regardless, SSR buys nothing, and you have traded a static bundle on a CDN for a Node process to operate, patch and scale.

Price the real costs honestly. Every third-party UI library needs auditing for 'use client'. Anything touching window at module scope breaks. Your test setup changes. Your team learns four cache layers and a rendering model where a three-line PR can regress sitewide TTFB. If you are not on Vercel, add a shared ISR cache, sharp for image optimisation, and verification that your proxy does not buffer streamed responses.

Consider the cheaper options first, because they usually win. If the problem is only SEO on a handful of marketing and docs pages, put Astro or a static site in front of the SPA at those paths and leave the app alone — that is a week, not a quarter. If the problem is genuinely app-wide SSR, React Router v7 is a smaller step from an existing react-router SPA: loaders and actions, one cache model, host-agnostic.

My recommendation: do not do a big-bang rewrite. If Next.js is genuinely warranted, migrate incrementally — Next supports app/ and pages/ side by side, and you can put new routes under the App Router while the old app keeps shipping. If after two or three routes the team is not measurably better off, you have learned that cheaply and can stop. A migration that cannot be stopped halfway is the one to refuse.

🏋️ Graded Exercises

1 (easy): This route 404s. The files exist and the component renders fine in isolation. 
  app/
    reports/
      layout.tsx      exports ReportsLayout({ children })
      ReportsTable.tsx
      styles.css
Solution 
  app/
    reports/
      page.tsx        <- THIS was missing
      layout.tsx
      ReportsTable.tsx
      styles.css

Only page.tsx makes a segment publicly routable. A layout describes how a segment's children are wrapped; with no page and no routable child, /reports matches nothing and falls through to the 404. This is deliberate — it is what lets you colocate components, tests and CSS inside a route folder without every file accidentally becoming a URL. ReportsTable.tsx is just a module, and that is the point.

The same rule catches people in the other direction: a folder containing only route.ts is an API endpoint, not a page, and route.ts cannot sit beside page.tsx because both would claim the same path.

2 (easy): After this three-line change, the whole site's TTFB went from ~25ms to ~280ms. Nothing else changed. 
  // app/layout.tsx
  export default async function RootLayout({ children }) {
    const theme = (await cookies()).get('theme')?.value ?? 'light';
    return <html data-theme={theme}><body>{children}</body></html>;
  }
Solution 
  // app/layout.tsx  — stays static
  export default function RootLayout({ children }) {
    return (
      <html>
        <body>
          <Suspense fallback={null}>
            <ThemeAttribute />   {/* only THIS reads cookies */}
          </Suspense>
          {children}
        </body>
      </html>
    );
  }

  BETTER STILL: set the class in middleware, or accept a flash and
  read localStorage in a tiny inline script. Both keep every route
  prerenderable.

Calling cookies() is a dynamic-rendering opt-out. It is not scoped to the component that called it — it marks the whole route as dynamic, and because this is the root layout, "the whole route" means every route in the application. The build output flips from a page of ○ to a page of ƒ, the full route cache stops being populated, and every request now renders on the origin instead of hitting a CDN.

Where the cookie read livesEffect on the build
Root layoutEvery route dynamic — sitewide regression
One pageThat route dynamic; siblings unaffected
A leaf inside <Suspense>Route stays static; the sliver streams in
Middleware (sets a header/class)Route stays static; no server render at all

The reason this ships so often is that there is no error and no warning. The only visible signal is the route legend printed by next build, which nobody reads unless it is diffed in CI.

3 (medium): The dashboard takes 900ms to respond. Each query takes ~300ms and none depends on another. 
  export default async function Dashboard() {
    const user    = await getUser();
    const orders  = await getOrders();
    const revenue = await getRevenue();
    return <Grid user={user} orders={orders} revenue={revenue} />;
  }
Solution 
  // 900ms -> 300ms
  export default async function Dashboard() {
    const [user, orders, revenue] = await Promise.all([
      getUser(), getOrders(), getRevenue(),
    ]);
    return <Grid user={user} orders={orders} revenue={revenue} />;
  }

  // BETTER IF ONE IS SLOW: stream the slow one, ship the rest now
  export default async function Dashboard() {
    const [user, orders] = await Promise.all([getUser(), getOrders()]);
    return (
      <Grid user={user} orders={orders}>
        <Suspense fallback={<RevenueSkeleton />}>
          <Revenue />      {/* awaits getRevenue() itself */}
        </Suspense>
      </Grid>
    );
  }

Sequential await is sequential wherever it runs. Moving fetching to the server removed the client/server round trip but did nothing about ordering — the second request cannot start until the first promise settles, so three independent 300ms queries cost 900ms. This is the classic waterfall rebuilt on the server, and it is harder to spot there because the network tab shows one slow document request rather than a staircase.

ShapeWall clockUser sees the shell at
Three sequential awaits900ms900ms
Promise.all300ms300ms
Promise.all for two + Suspense for the slow one300ms total~60ms

Note what streaming does and does not do. It does not make getRevenue() faster. It changes when bytes reach the browser, so the nav and the tables paint immediately and the revenue panel fills in later. Only sequence awaits when the second genuinely needs a value from the first.

4 (medium): This action works in the UI. A security reviewer rejected it. 
  async function deletePost(formData) {
    'use server';
    await db.post.delete({ where: { id: formData.get('id') } });
    revalidatePath('/posts');
  }

  // rendered only on /my-posts, which is behind a middleware redirect
  <form action={deletePost}>
    <input type="hidden" name="id" value={post.id} />
    <button>Delete</button>
  </form>
Solution 
  async function deletePost(formData) {
    'use server';

    // 1. AUTHENTICATE — the endpoint is public
    const session = await auth();
    if (!session) return { error: 'Unauthorized' };

    // 2. VALIDATE — FormData gives strings or Files, nothing else
    const parsed = z.string().uuid().safeParse(formData.get('id'));
    if (!parsed.success) return { error: 'Bad id' };

    // 3. AUTHORIZE — ownership, checked in the write
    const result = await db.post.deleteMany({
      where: { id: parsed.data, authorId: session.userId },
    });
    if (result.count === 0) return { error: 'Not found' };

    revalidatePath('/posts');
    return { ok: true };
  }

A server action compiles to a public HTTP endpoint with a generated ID. The browser posts to it. So can curl, with any payload, from any session. The hidden input is not a secret — it is attacker-controlled input that happens to be pre-filled by your UI.

Each of the three original assumptions fails independently. The middleware redirect guards the render of /my-posts, not the endpoint, and middleware has been bypassable in practice (CVE-2025-29927) even for what it does guard. formData.get('id') is typed FormDataEntryValue — it can be a File, or a string that is not a UUID, and passing it straight to the query is how you get either a runtime error or something worse depending on the driver. And nothing ties the post to the caller, so a valid id belonging to another user deletes their post.

AssumptionWhy it fails
Only reachable from /my-postsIt is an HTTP endpoint; the page is irrelevant
Middleware already authenticatedMiddleware gates a render, and has been bypassable
The id is one of the user's ownIt came from the request body
formData.get returns a stringIt returns string | File | null

Putting the ownership condition in the where clause rather than in a preceding findFirst is deliberate: it makes the check and the write one atomic statement, so there is no window between "I verified you own it" and "I deleted it".

5 (hard): A rotated Stripe key leaked again. The developer says they only used it in one component. 
  // app/checkout/PriceWidget.tsx
  'use client';
  export function PriceWidget({ sku }) {
    const [price, setPrice] = useState(null);
    useEffect(() => {
      fetch('https://api.stripe.com/v1/prices/' + sku, {
        headers: { Authorization: `Bearer ${
                     process.env.NEXT_PUBLIC_STRIPE_SECRET }` },
      }).then(r => r.json()).then(setPrice);
    }, [sku]);
    return <span>{price?.amount}</span>;
  }
Solution 
  // lib/stripe.ts
  import 'server-only';              // build FAILS if a client imports this
  export const stripe = new Stripe(process.env.STRIPE_SECRET!);

  // app/checkout/PriceWidget.tsx   — now a SERVER component
  import { stripe } from '@/lib/stripe';
  export async function PriceWidget({ sku }) {
    const price = await stripe.prices.retrieve(sku);
    return <span>{price.unit_amount}</span>;
  }

  VERIFY, DO NOT ASSUME:
    next build && grep -r "sk_live" .next/static/   -> must be empty

NEXT_PUBLIC_ is not a scope or a permission. It is a build-time text substitution: the compiler replaces process.env.NEXT_PUBLIC_STRIPE_SECRET with the literal string in the JavaScript it emits. The key is in a static chunk served from a CDN, in every visitor's browser cache, in any archive that crawled the site, and in the source maps if those are published.

"Only used in one component" is exactly why it happened. The unprefixed variable read as undefined on the client, so adding the prefix made the code work. It made it work by making the secret public — and rotating the key now requires a rebuild and a cache purge, not just a dashboard click.

VariableServerClient bundleChangeable without rebuild
STRIPE_SECRETReal valueundefinedYes — restart the process
NEXT_PUBLIC_STRIPE_SECRETReal valueInlined literalNo — baked at build time

The structural fix is import 'server-only' at the top of the module holding the secret. If any client component imports it, directly or transitively, the build fails with a clear message. That converts an incident class into a compile error, which is the only version of this control that survives contact with a team.

The build-time inlining has a second consequence worth knowing: you cannot promote one Docker image from staging to production if any NEXT_PUBLIC_ value differs between them. It is compiled in. Either build per environment or fetch runtime configuration from an endpoint at startup.

6 (hard): Self-hosted on three Kubernetes pods. Editors publish in the CMS, the webhook returns 200, and the page updates — then reverts. Refreshing flips it back and forth. 
  // app/blog/[slug]/page.tsx
  export const revalidate = 3600;

  // app/api/revalidate/route.ts
  export async function POST(req) {
    const { slug } = await req.json();
    revalidatePath(`/blog/${slug}`);
    return Response.json({ revalidated: true });
  }
Solution 
  // next.config.js — one cache, shared by every pod
  module.exports = {
    output: 'standalone',
    cacheHandler: require.resolve('./cache-handler.js'),
    cacheMaxMemorySize: 0,        // disable the per-pod in-memory LRU
  };

  // cache-handler.js — get/set/revalidateTag backed by Redis

  // and tag the data so invalidation is precise
  const post = await fetch(url, { next: { tags: [`post:${slug}`] } });
  // webhook:
  revalidateTag(`post:${slug}`);

The default incremental cache is the pod's local filesystem plus an in-memory LRU. The webhook is a single HTTP request, so the load balancer routes it to exactly one pod. That pod regenerates the page. The other two still hold their old copies and will keep serving them for up to an hour. Which version a reader sees depends on which pod answered their request — hence the flip-flopping, and hence the "sometimes it works" reports that make this so hard to reproduce.

SetupWhat revalidatePath reachesResult
Single instanceThe only cacheCorrect — and why it worked in staging
VercelA managed shared cacheCorrect — and why the docs do not warn you
3 pods, default handler1 of 3 cachesContent flips per request
3 pods, shared handlerThe one shared cacheCorrect

Two details that matter beyond wiring Redis. Set cacheMaxMemorySize: 0 — otherwise each pod keeps an in-memory layer in front of the shared store and you have reintroduced a smaller version of the same bug. And prefer revalidateTag over revalidatePath: paths are fragile strings that must exactly match the route's shape, whereas a tag attached at the fetch site invalidates every page that consumed that data, including the index and the sitemap you forgot about.

This is the general shape of self-hosting Next.js. Nothing is impossible off Vercel; you are reimplementing services that were previously invisible. The same applies to image optimisation (sharp plus a CDN, or you resize on every cold start) and to streaming (a buffering proxy silently converts it back to all-or-nothing SSR, with no error).

🎯 Key Takeaways

  • A framework is worth it only if an anonymous user or a crawler needs HTML on the first response — behind a login wall, a SPA is still correct.
  • App Router and Pages Router coexist in one app, matched app/ first; that is the supported incremental migration path.
  • Only page.tsx makes a segment routable — a folder of components and a layout is a 404.
  • Nested layouts persist across navigation because the fiber persists; the router keeps the common prefix mounted and swaps only the differing subtree.
  • template.tsx is the opt-out that remounts — it throws away the state preservation you adopted layouts for.
  • error.tsx cannot catch its own layout's error, must be a client component, and needs global-error.tsx at the root.
  • 'use client' marks a boundary, not a file — everything it imports transitively joins the client bundle, so push it to the leaf.
  • A client component can render server children passed as props, even though it cannot import them — the composition trick that keeps the boundary small.
  • cookies(), headers(), searchParams or no-store anywhere in a route makes the whole route dynamic, with no warning; in a root layout that is the whole site.
  • The route legend in next build is your regression test — ○ static, ● prerendered, ƒ dynamic; diff it every deploy.
  • ISR serves stale and regenerates in the background: the request that triggers revalidation is not the one that waits.
  • Streaming re-orders bytes, it does not make anything faster — a fast shell plus one slow section, not a page of skeletons.
  • Sequential awaits rebuild the waterfall on the server — Promise.all independent fetches.
  • Four caches, and the defaults reversed between 14 and 15 — check the version before you trust an article, and turn on logging.fetches before you theorise.
  • A server action is a public HTTP endpoint: authenticate, authorize and validate inside every one of them.
  • Middleware is a routing convenience, never an auth boundary — no TCP, no Node built-ins, a small bundle budget, and it has been bypassable.
  • NEXT_PUBLIC_ is a build-time text substitution into a public chunk; guard secrets with import 'server-only' so a leak becomes a build failure.
  • Off Vercel you own ISR cache sharing, image optimisation and unbuffered streaming — all possible, none automatic.
