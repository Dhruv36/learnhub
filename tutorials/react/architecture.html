Architecture for Large Apps Patterns & Quality

What you'll master: why folder structure is a proxy for change cost and how to measure it instead of arguing about it; the feature folder and the module boundary rule — a feature exposes one index.ts and nothing imports its internals — enforced with an ESLint rule rather than a wiki page nobody reads; layering that survives contact with a deadline, and what a circular import actually does at runtime; why barrel files cost you bundle size, dev-server time and import cycles; the rule that a shared component earns its place only at three real consumers; TypeScript as the enforced contract and the four places any leaks back in; the strangler migration; and where all of this is over-engineering for a five-person team. Prerequisites: Composition Patterns and State Management.

Part 1 — Change Cost, Not Code Size

  ARCHITECTURE ARGUMENTS ARE UNWINNABLE IN THE ABSTRACT. "Feature folders
  are cleaner" is an aesthetic claim and the other person's aesthetics are
  as good as yours. Convert it to a measurement and the argument ends.

  THE METRIC: for a typical change, how many files must you open, how many
  code owners must approve, and how confident are you that nothing else
  broke? Call it BLAST RADIUS. Everything below is in service of shrinking
  it.

  Take one real ticket — "add a gift-note field to checkout" — and count.

    TYPE-BASED LAYOUT                     FEATURE-BASED LAYOUT
    src/                                  src/
      components/CheckoutForm.tsx           features/checkout/
      components/GiftNote.tsx                 components/CheckoutForm.tsx
      hooks/useCheckout.ts                    components/GiftNote.tsx
      api/checkout.ts                         useCheckout.ts
      types/checkout.ts                       api.ts
      utils/validation.ts                     types.ts
      store/checkoutSlice.ts                  checkoutReducer.ts
                                              index.ts
    7 files, 6 directories,               8 files, 1 directory,
    3 code owners triggered               1 code owner

  Same amount of code. The second one you can hold in your head, review in
  one diff, and hand to a new hire as "this folder is checkout".

  WHY TYPE-BASED ROTS — the mechanism, not the vibe:

  1. IT SORTS BY THE LEAST INTERESTING PROPERTY. "Is it a hook" is the
     thing you care least about at 3am. "Is it checkout" is the thing you
     always care about. Alphabetical order then interleaves domains, so
     useCart sits next to useCarousel and neither knows the other exists.

  2. NO FILE NAMES THE BOUNDARY. In components/ every file is equally
     importable by every other file. There is no place to write down "this
     is internal" because there is no unit for it to be internal TO.

  3. THE JUNK DRAWER IS LOAD-BEARING. utils/ starts as string helpers and
     within a year contains formatCurrency (locale rules), retry (network
     policy) and canEditOrder (a business rule). Those three belong to
     three different owners and now share a file that everything imports,
     so touching it triggers the whole test suite.

  4. DELETION BECOMES ARCHAEOLOGY. Sunsetting a feature means grepping six
     folders and guessing. So nobody deletes anything, and the codebase
     only ever grows. THE DELETION TEST is the sharpest architecture
     question there is: can you remove a feature by deleting one directory
     and one route entry? If not, you do not have modules — you have files.

  MEASURING IT ON YOUR OWN REPO. Files that change together should live
  together; version control already knows which do:

    git log --format=%H --name-only --since=1.year |    (run it yourself;
      ... group by commit, count co-occurring pairs     this lesson does
                                                        not run git)

  Pairs that co-change in 40%+ of commits and live in different top-level
  folders are your evidence. That number — not taste — is what you bring
  to the meeting. In a type-based app the top pairs are almost always
  components/X.tsx with hooks/useX.ts and api/x.ts: the same feature,
  scattered by a rule that never had a reason.

  THE THRESHOLD, HONESTLY. None of this hurts at 30 files. It starts
  hurting somewhere around 150-300 modules or the second team, whichever
  comes first, because that is where nobody holds the whole map any more.
  Below that, feature folders are still worth adopting — not because they
  relieve pain today, but because the migration cost rises with size and
  it is cheapest now.

Part 2 — The Feature Folder and Its Public API

  A FEATURE IS NOT A FOLDER OF RELATED FILES. It is a module with an
  inside and an outside. The folder is how you write that down; the
  index.ts is where the boundary actually lives.

    src/features/cart/
      index.ts             ← THE ONLY FILE THE REST OF THE APP MAY IMPORT
      CartProvider.tsx     ← wiring, internal
      useCart.ts           ← the capability, exported through index
      cartReducer.ts       ← business rules, pure, unit-tested directly
      api.ts               ← the cart's own request layer
      types.ts             ← its domain types
      components/
        CartDrawer.tsx     ← cart's OWN ui, not "shared"
        CartBadge.tsx
        LineItemRow.tsx    ← internal; nobody outside renders a line item
      __tests__/
      README.md            ← 20 lines: what it owns, what it exposes

    // features/cart/index.ts — the contract, and deliberately short
    export { CartProvider } from './CartProvider';
    export { useCart } from './useCart';
    export { CartBadge } from './components/CartBadge';
    export type { CartLine, CartTotals } from './types';
    // NOT exported: cartReducer, api, LineItemRow, CART_STORAGE_KEY

  WHY THE EXPORT LIST IS THE ARCHITECTURE. Everything in that file is a
  promise. Everything not in it is yours to rename at 4pm on a Friday. A
  feature with 30 exports has no boundary — it is a folder wearing a
  module costume. If your index.ts is longer than about 10 lines, ask
  which of those exports exist because a caller needed them and which
  exist because someone reached in and you legalised it after the fact.

  THE CONCRETE FAILURE THE RULE PREVENTS:

    // checkout/Summary.tsx
    import { cartReducer } from '../cart/cartReducer';   // deep import
    const totals = cartReducer(state, { type: 'recalc' }).totals;

  Now cart cannot change its reducer's shape without breaking checkout,
  and nothing anywhere records that dependency. Six months later the cart
  team splits the reducer, checkout's totals silently become NaN, and the
  bug surfaces as a support ticket about a £NaN charge. The import was
  legal, reviewed, and merged, because no mechanism said no.

  ENFORCE IT IN CI, NOT IN A WIKI. A rule that lives in a Notion page is
  a rule that new hires break in week one and nobody notices. The whole
  point is that the machine says no.

    // .eslintrc.cjs — zero new dependencies, uses core ESLint
    'no-restricted-imports': ['error', {
      patterns: [{
        group: ['@/features/*/*'],           // any path DEEPER than the feature
        message: 'Import from the feature index: @/features/cart',
      }, {
        group: ['../../features/*'],         // relative escapes out of a feature
        message: 'Use the @/features alias.',
      }],
    }]

  That single rule does most of the work. Note the glob: features/cart is
  allowed, features/cart/anything is not. Path aliases (tsconfig paths +
  the matching bundler alias) are what make the glob reliable — with
  relative imports the same file is '../cart/api' from one place and
  '../../features/cart/api' from another, and no pattern catches both.

  WHEN YOU NEED MORE, eslint-plugin-boundaries or dependency-cruiser let
  you declare element types and a full allow-matrix, including "shared may
  not import features" which no-restricted-imports expresses clumsily.
  Adopt one when the simple rule stops covering you — not before.

  THE THREE ESCAPE HATCHES PEOPLE ACTUALLY NEED, and what to do instead:

    "I need one type from inside."      → export the type from index.
    "I need it only in a test."         → tests may deep-import their OWN
                                          feature; add an eslint override
                                          scoped to that feature's folder.
    "Two features need the same code."  → it is not feature code. Move it
                                          down a layer (Part 3) or accept
                                          the duplication (Part 4).

  THE ONE THING THAT MAKES OR BREAKS ADOPTION: turn the rule on as a
  WARNING first, count the violations, fix them in batches, then flip to
  error. Turning it on as an error with 400 existing violations means
  someone adds an eslint-disable at the top of the config and the rule
  dies that afternoon.
ImportVerdictWhy
import { useCart } from '@/features/cart'AllowedThrough the declared contract
import { cartReducer } from '@/features/cart/cartReducer'BlockedCouples callers to an internal that is free to change
import { Button } from '@/shared/ui'AllowedDownward, into a lower layer
shared/ui/Button importing @/features/cartBlockedUpward dependency — makes the primitive undeployable elsewhere

Part 3 — Dependencies Point One Way

  FOUR LAYERS IS ENOUGH FOR ALMOST EVERY REACT APP. More is a taxonomy
  hobby; fewer and the boundary blurs.

    app/        composition root: providers, router, shell, env config
      ↓         may import anything
    features/   checkout, cart, search, auth — the product
      ↓         may import shared and lib; siblings only via their index
    shared/     domain-free UI and hooks: Button, Modal, useDebounce
      ↓         may import lib only
    lib/        api client, formatting, the design tokens, no React state
                imports nothing of ours

  THE RULE: an arrow may only point DOWN. That is the whole architecture.
  Two consequences worth stating plainly, because both get argued:

    • shared/ MUST NOT import features/. The moment shared/ui/Button
      imports useCart to show a badge, Button is no longer reusable, no
      longer testable in isolation, and pulls the cart's entire dependency
      graph into every bundle that renders a button. This is the single
      most common violation and it always arrives as a "small convenience".

    • FEATURE-TO-FEATURE is legal but is the coupling you must watch. If
      checkout imports cart's index, that is a real product dependency and
      fine. If cart also imports checkout, you have a cycle at the feature
      level, and no amount of index.ts hygiene saves you. Break it by
      inverting: the lower feature exposes data, the higher one composes.
      Or hoist the shared concept into its own feature that both depend on.

  WHAT A CIRCULAR IMPORT ACTUALLY DOES AT RUNTIME — this is worth knowing
  precisely, because the error message never mentions the cycle:

    // a.ts
    import { b } from './b';
    export const a = () => b();
    // b.ts
    import { a } from './a';
    export const B_LIST = [a];        // evaluated at module init!

  ESM hoists bindings but does not hoist VALUES. Whichever module the
  bundler evaluates second sees the other's exports in the temporal dead
  zone. You get one of three symptoms, none of which says "cycle":

    1. ReferenceError: Cannot access 'a' before initialization
    2. A value that is undefined at module scope but fine inside a
       function — so it works in dev and breaks only where the bundler
       ordered the graph differently.
    3. React: "Element type is invalid: expected a string or a class/
       function but got: undefined." That is a component that was
       undefined at import time. Nine times out of ten it is a cycle
       through a barrel file, and it took someone a full afternoon.

  Cycles inside a function body are harmless — by call time both modules
  are initialised. Cycles evaluated at module scope are the killer, and
  a React component reference in a const array is module scope.

  BARREL FILES: THE FEATURE INDEX IS GOOD, THE GLOBAL BARREL IS NOT.
  A barrel is any index.ts that re-exports. The difference:

    features/cart/index.ts        6 exports, one module, a real contract
    shared/index.ts               export * from every component in shared

  The second one costs you four separate things:

    • TREE SHAKING BECOMES CONDITIONAL. Rollup and esbuild can drop unused
      re-exports only if every module in the chain is side-effect free.
      One CSS import, one polyfill, one analytics call at module scope,
      or a missing "sideEffects": false in package.json, and importing
      one icon pulls the barrel's whole graph. Teams routinely find 100-
      300KB of a bundle this way — measure with rollup-plugin-visualizer
      before you believe any number, including this one.

    • DEV SERVER TIME. Vite serves unbundled ESM in dev; one barrel import
      becomes a request per re-exported module. A 200-module barrel that
      every page imports turns a cold page load into thousands of requests
      and seconds of waiting, every reload.

    • TEST TIME. Importing one component in a unit test drags in the graph.
      Suites go from 2s to 30s and nobody can point at the commit.

    • CYCLES. A imports the barrel, the barrel exports B, B imports the
      barrel. Half the "undefined component" bugs above trace to this.

  THE RULE THAT KEEPS THE GOOD HALF: barrels are for MODULE BOUNDARIES
  (one per feature, small, hand-written, curated). They are not for
  saving keystrokes across 200 files. Never let a module import its own
  barrel — inside shared/, import './Button' directly.

  DETECTING CYCLES: madge --circular src, or dependency-cruiser with
  no-circular, in CI. Run it once today; the count is usually not zero.
LayerMay importMust never importTest in isolation?
app/features, shared, lib—No — it is wiring; cover it with e2e
features/shared, lib, sibling feature indexesapp; another feature's internalsYes — the reducer and hooks directly

Part 4 — Shared Code Earns Its Place at Three Consumers

  THE RULE: duplicate it at two consumers. Extract at three.

  Not because three is magic, but because of what the second consumer
  teaches you and the first two cannot:

    ONE consumer   → you have an implementation, not an abstraction.
    TWO consumers  → you have a coincidence. Two things that look alike
                     today diverge for reasons neither of them knows yet.
    THREE consumers → you can finally see which parts VARY and which are
                     genuinely fixed. That is the only information an
                     abstraction is made of, and you cannot get it by
                     thinking harder about the first two.

  HOW THE PREMATURE VERSION FAILS, step by step. This is not hypothetical;
  it is the most reliably repeated mistake in front-end teams:

    Week 1  Two pages need a card. Extract shared/ui/Card.
    Week 3  Third page needs it without a border.   +prop borderless
    Week 5  Marketing needs a dark variant.         +prop dark
    Week 8  Checkout needs a header slot.           +prop header
    Week 12 One page needs it clickable-but-not-a-link.  +prop as, onClick
    Week 20 Card has 14 props, 9 booleans, an internal branch tree nobody
            can hold in their head, and 300 lines. Every product change
            is now a shared-component PR, reviewed by a different team,
            released and adopted separately.

  THE COST IS NOT THE PROPS. It is that the change cost of every consumer
  now routes through a queue owned by someone else. You optimised for
  "don't repeat yourself" and paid in "can't change anything alone".

  DUPLICATION IS CHEAPER THAN THE WRONG ABSTRACTION. Sandi Metz's line,
  and it is measurable: deleting three near-identical 40-line components
  and rewriting one good one costs an afternoon. Untangling a 14-prop
  component that 30 files depend on costs a sprint and a migration guide.
  The asymmetry is the whole argument.

  THE PROMOTION PATH — and note that every step is reversible:

    features/checkout/components/OrderCard.tsx     (local, week 1)
      ↓ a second feature needs something similar
    COPY IT. Add a comment naming the twin. Let them diverge.
      ↓ a third arrives AND all three have stayed the same shape
    shared/ui/Card.tsx  — extract what is provably identical, and
                          leave the differences in the callers.
      ↓ one consumer's needs diverge sharply
    DEMOTE: copy it back into that feature and simplify both. Deleting a
    shared component is a legitimate, healthy PR. Teams never do it,
    because promotion feels like progress and demotion feels like defeat.

  WHAT BELONGS IN shared/ ON DAY ONE, no rule of three required, because
  the variation is already known and it is genuinely domain-free:

    • Design tokens: colour, spacing, type scale, radii, z-index ladder.
    • Accessibility-hard primitives: Modal (focus trap, inert background,
      Escape, restore focus), Menu, Combobox, Tooltip. These are wrong in
      subtle ways when duplicated, and correctness is not a matter of
      taste. Better still: wrap a headless library and own the styling.
    • The api client, error normalisation, auth token refresh.

  WHAT NEVER BELONGS IN shared/: anything that knows a domain noun.
  shared/ui/OrderStatusBadge is a contradiction — the moment it knows
  what an order status is, it belongs to the orders feature.

  THE PREMATURE DESIGN SYSTEM, specifically. A design system is an
  internal product: it needs an owner, a release process, versioning,
  docs, a deprecation policy, and consumers who can upgrade. That is
  roughly a person's job. Before you have a settled visual language and
  more than one consuming app, you are paying a product's overhead to
  serve one customer who is sitting next to you. Start with tokens plus
  a handful of primitives in shared/, and let the system emerge from
  code that already works. The systems that succeed are almost always
  extracted, never designed up front.

Part 5 — Contracts at Scale: Types, and Where State Lives

  AT SCALE, THE PROPS TYPE IS THE CONTRACT and the compiler is the only
  reviewer that reads every call site every time. That is the argument
  for TypeScript in a large app — not fewer bugs in the abstract, but a
  boundary that is checked mechanically instead of remembered.

  DISCRIMINATED UNIONS FOR VARIANTS. The default way people type a
  component with modes admits states that cannot exist:

    // WEAK — 2^3 = 8 combinations, most of them meaningless
    type Props = {
      variant: 'link' | 'button';
      href?: string;
      onClick?: () => void;
      disabled?: boolean;
    };
    // A link with onClick and no href compiles. So does a button with
    // href. Both are bugs the type system was supposed to catch, and
    // both end up guarded at runtime inside the component.

    // STRONG — the impossible combinations do not typecheck
    type Props =
      | { variant: 'link';   href: string; onClick?: never }
      | { variant: 'button'; onClick: () => void; href?: never };

  Now the component body narrows on props.variant and TypeScript knows
  href exists in exactly one branch. The same shape is what makes request
  state safe (see Data Fetching's status union) and what makes a reducer's
  action type exhaustive: switch on action.type, return never in the
  default, and adding an action without handling it fails the build.

  WHERE any LEAKS BACK IN — four places, in rough order of damage:

    1. THE NETWORK BOUNDARY. res.json() is typed Promise<any>. Writing
       const u: User = await res.json() is a LIE the compiler cheerfully
       accepts: it is an assertion, not a check. Every downstream type is
       now fiction, and the failure surfaces as "cannot read property of
       undefined" three components away from the cause. Validate at the
       edge — zod, valibot, or a hand-written guard — and the parse error
       names the field and the endpoint.

    2. as CASTS. as User silences the compiler without checking anything.
       Treat every as in a PR as a question. The honest ones are narrow:
       as const, and casts where you genuinely know more than the checker
       (a DOM element type from a ref).

    3. CATCH CLAUSES. catch (e) gives you unknown under
       useUnknownInCatchVariables (on with strict). Anyone can throw
       anything; e.message may not exist. Narrow before you read.

    4. THIRD-PARTY TYPES. A stale @types package or a d.ts full of any
       poisons everything it touches, silently. Wrap the library in one
       adapter module of your own with types you control.

    Set noImplicitAny, strict, and noUncheckedIndexedAccess. The last one
    is the one teams skip: without it arr[0] is typed T rather than
    T | undefined, and every off-by-one becomes a runtime crash instead
    of a compile error.

  STATE ARCHITECTURE AT SCALE is the same split you learned in State
  Management, applied to a codebase rather than a component. The mistake
  is not choosing the wrong library — it is putting a piece of state in a
  home that cannot answer its questions.

    SERVER CACHE   Data the server owns; you hold a possibly-stale copy.
                   Home: a query library. Questions only it answers: when
                   is it stale, who refetches, what shows during refetch,
                   how does a mutation invalidate it.
    URL            Anything that must survive a refresh, a share, or the
                   back button: filters, tab, page, selected id.
    CLIENT GLOBAL  Genuinely app-wide and client-owned: theme, feature
                   flags, the auth session object. Far less than teams
                   expect — usually two or three things.
    LOCAL          Everything else. useState in the component that owns
                   it, hoisted only when a second component needs it.

  The architectural payoff: with server data in a cache and view state in
  the URL, most features need NO global store at all, so features stay
  independent and deletable. The moment a feature's state lives in a
  central store slice, that store is an upward dependency in disguise —
  app-level code now knows the feature's shape, and deleting the feature
  means editing the store. Keep feature state inside the feature, exported
  through a hook in its index.

  THE HONEST PART: the ecosystem does not agree here. Redux Toolkit with
  RTK Query is a coherent, well-documented answer that many large teams
  are productive in, and "Redux is dead" is fashion, not analysis. What is
  not defensible is a hand-rolled cache: server data in a store with
  manual invalidation written per-feature is the actual source of most
  "React state management is a nightmare" complaints.

Part 6 — Holding It in Place, Migrating, and Knowing When to Stop

  ARCHITECTURE DECAYS AT THE SPEED OF DEADLINES. Every rule above is one
  tired afternoon away from being broken, and the broken version is then
  precedent. Three mechanisms actually hold, in descending order of how
  well they work:

    1. AUTOMATED (works while everyone sleeps)
       import boundary rule, madge --circular, tsc --noEmit, a bundle
       size budget in CI, CODEOWNERS per feature folder.
    2. STRUCTURAL (works by making the wrong thing awkward)
       Path aliases, small feature indexes, a template folder to copy.
    3. SOCIAL (works only while the person who cares is still employed)
       Review checklists, ADRs, a wiki page. Necessary, never sufficient.

  IF A RULE MATTERS, IT GOES IN CI. If it cannot go in CI, expect it to be
  followed about 60% of the time and design for that. The review question
  that catches most of what lint cannot: "which layer does this file live
  in, and does every import point down?"

  BUNDLE BUDGET, since it is the one people skip and it is three lines:

    // CI: fail the build if the entry chunk grows past its budget
    size-limit / bundlesize / rollup-plugin-visualizer + a threshold
    Entry chunk 250KB gzip is a defensible ceiling for a product app;
    what matters is that a 40KB jump shows up in the PR that caused it,
    not six months later in a performance review.

  MONOREPOS — WHEN THEY ARE ACTUALLY WORTH IT. A monorepo solves exactly
  one problem: ATOMIC CHANGES ACROSS DEPLOYABLE UNITS. If you have one
  app, you do not have that problem, and feature folders already give you
  the module boundaries people think they are buying.

    WORTH IT WHEN:
      • 2+ deployable apps sharing real code (web + admin + marketing)
      • You want one PR to change a shared component AND every consumer
      • Shared config, lint, tsconfig genuinely drifting across repos
    NOT WORTH IT WHEN:
      • One app. This is most teams. The answer is folders.
      • You want it for "code sharing" you could get from one package.
      • Nobody owns build tooling. Turborepo/Nx caching, task graphs and
        CI-affected detection are real maintenance, and a badly wired
        monorepo makes every CI run slower for everyone.

    THE HIDDEN COST is that CI must learn which packages a change affects.
    Without that, every PR runs every test in every package and your
    feedback loop gets worse the more the repo succeeds.

  MIGRATING A LARGE EXISTING APP — NEVER A REWRITE. The rewrite fails for
  a reason that has nothing to do with skill: for its whole duration you
  ship no features while the old app keeps changing, so you are chasing a
  moving target with a team that is also maintaining the thing you are
  replacing. The strangler pattern instead:

    STEP 0  Add the structure with nothing in it: src/features/, src/shared/,
            path aliases, the lint rule as a WARNING. Zero behaviour change,
            merges in a day.
    STEP 1  Pick ONE feature — ideally one with active work, so the
            migration rides along with a ticket someone already owns.
    STEP 2  Move its files. Create index.ts. Fix imports. Do not refactor
            the code while moving it: a diff that is pure moves is
            reviewable in ten minutes; a diff that moves and rewrites is
            unreviewable and will be rubber-stamped.
    STEP 3  Delete what the move revealed as dead. Every migration finds
            some; it is the best part.
    STEP 4  Repeat. Old and new layouts coexist indefinitely and that is
            FINE. A half-migrated app where the active 20% is clean is
            strictly better than a fully consistent mess.
    STEP 5  When the remaining stragglers are only cold code, flip lint
            to error and stop thinking about it.

    Two rules that make the difference: NEVER BLOCK A FEATURE ON THE
    MIGRATION, and always leave the codebase working at every commit.

  DOCUMENTATION THAT STAYS TRUE. Docs rot in proportion to their distance
  from the code:

    features/cart/README.md   20 lines — what it owns, what index exports,
                              the one non-obvious decision. In the diff,
                              so review catches it when it goes stale.
    Storybook                 Only for shared/ui. It is the design system's
                              test surface and its docs at once; a11y and
                              visual-regression addons make it load-bearing
                              rather than decorative. Storybook for feature
                              components is usually maintenance for nobody.
    ADRs (docs/adr/000N.md)   One page: context, decision, consequences,
                              date. They exist to answer "why is it like
                              this" for someone who arrives in two years.
                              Write one when you rejected a real
                              alternative — never for the obvious.
    Types                     The docs that cannot go stale, because the
                              build fails. Prefer them to prose wherever
                              a choice exists.

  WHEN ALL OF THIS IS OVER-ENGINEERING. Be honest: most of this lesson is
  overhead for a five-person team on one app. The overhead is not the
  folders — it is the review load, the tooling, and the decisions you now
  have to make in advance.

    A 5-PERSON, ONE-APP TEAM SHOULD KEEP:
      • Feature folders and one index.ts per feature. Free, and it is
        what makes the rest possible later.
      • The one no-restricted-imports rule. Ten lines.
      • TypeScript strict. Not optional at any size.
      • Server cache vs client vs URL. A thinking tool, not tooling.

Interview Questions

Beginner: Why organise a React codebase by feature rather than by file type?

Because changes arrive by feature, not by file type. A ticket is "add a gift note to checkout", never "modify all the hooks". A type-based layout sorts files by the property you care least about while reading code, so a single change is scattered across components/, hooks/, api/, types/ and utils/.

The concrete costs are countable, which is what makes this more than taste: more files open per ticket, more code owners triggered per PR, and a longer answer to "am I sure nothing else broke". A feature folder collapses all of that to one directory and usually one owner.

The sharpest version of the question is the deletion test: can you remove a feature by deleting one folder and one route entry? Under a feature layout, yes. Under a type layout, sunsetting anything means grepping six folders and guessing — so nobody does it, and the codebase only grows.

A type-based layout also gives you nowhere to write down "this is internal". Every file in components/ is equally importable by every other file, so there is no unit for anything to be private to. Feature folders create that unit, which is what Part 2 builds on.

Honestly: none of this matters at 30 files. It starts to bite around 150–300 modules or the second team. The reason to adopt it early anyway is that the migration cost rises with the codebase size.

Beginner: What is a feature's public API and why does it matter?

It is the feature's index.ts: the short list of things the rest of the app is allowed to import. Everything else in the folder is internal and free to change without notice.

// features/cart/index.ts
export { CartProvider } from './CartProvider';
export { useCart } from './useCart';
export type { CartLine } from './types';
// internal: cartReducer, api.ts, LineItemRow, CART_STORAGE_KEY

It matters because every export is a promise. If checkout deep-imports cart/cartReducer, the cart team can no longer change its reducer shape without breaking a feature they may not know exists — and nothing in the codebase records that dependency. It fails silently and late, typically as wrong numbers on a screen rather than an error.

The corollary people miss: a 30-export index has no boundary at all. If the export list keeps growing, each addition is usually someone who reached inside and had it legalised after the fact. The fix is either to expose a proper capability (a hook that does the job) or to move the shared thing down a layer.

And the rule is only real if a machine enforces it — a wiki page gets broken in week one. Ten lines of no-restricted-imports banning @/features/*/* does it.

Mid: How do you enforce architectural boundaries so they survive a deadline?

By making the machine say no. Rules that live in review comments are followed while the person who cares is watching and forgotten the first tired afternoon — and the broken version then becomes precedent that the next person copies.

The rollout detail decides whether it works: turn the rule on as a warning, count the violations, fix in batches, then flip to error. Introducing it as an error with 400 existing violations guarantees someone adds a blanket disable and the rule dies that day.

Path aliases are what make the globs reliable. With relative imports the same module is '../cart/api' from one file and '../../features/cart/api' from another, and no single pattern catches both.

Leave the social layer in place for what lint genuinely cannot check — whether a shared component has earned its third consumer, whether a feature-to-feature dependency reflects real product coupling. Just do not expect it to hold anything on its own.

Mid: What is wrong with barrel files, given that a feature's index.ts is one?

Nothing is wrong with a barrel at a module boundary: small, hand-written, curated, one per feature. The problem is the global convenience barrel — shared/index.ts doing export * over 200 modules so people can write shorter imports.

That costs you four things. Tree shaking becomes conditional: bundlers can drop unused re-exports only if every module in the chain is side-effect free, so one CSS import or a missing "sideEffects": false means importing an icon pulls the whole graph. Dev server time: Vite serves unbundled ESM, so one barrel import becomes a request per re-exported module. Test time: a unit test drags in the graph and suites go from seconds to minutes. Cycles: A imports the barrel, the barrel exports B, B imports the barrel.

The cycle is the one that costs an afternoon, because the symptom never mentions imports. You get "Element type is invalid: expected a string or a class/function but got: undefined" — a component that was undefined at import time because ESM hoists bindings but not values, and the module evaluated second saw the other's exports in the temporal dead zone.

Two rules keep the good half: barrels only at boundaries, and never let a module import its own barrel — inside shared/, import './Button' directly. Add madge --circular to CI; the count on an existing codebase is rarely zero.

Senior: When does a component belong in a shared library, and what does getting it wrong cost?

My rule is three real consumers, with duplication until then. The reasoning is about information, not about the number: one consumer gives you an implementation; two gives you a coincidence, since things that look alike today diverge for reasons neither knows yet; three is the first point where you can see which parts genuinely vary. An abstraction is made of exactly that information, and you cannot get it by thinking harder about the first two.

The failure mode is stereotyped. Extract at two, then each new need arrives as a boolean — borderless, dark, header, as — and within a quarter you have a 14-prop component with a branch tree nobody can hold in their head. The real cost is not the props: it is that every product change now routes through a shared-component PR reviewed by another team, released and adopted separately. You optimised for "don't repeat yourself" and paid in "can't change anything alone".

That asymmetry is why duplication is the cheaper mistake. Deleting three near-identical 40-line components and writing one good one costs an afternoon. Untangling a 14-prop component that 30 files depend on costs a sprint and a migration guide.

There are exemptions where the variation is already known and the code is genuinely domain-free: design tokens, the api client, and accessibility-hard primitives — Modal with a focus trap, inert background, Escape handling and focus restoration; Menu; Combobox. Those are wrong in subtle ways when duplicated, and correctness there is not a matter of taste. Anything that knows a domain noun is not shared code: shared/ui/OrderStatusBadge is a contradiction.

On design systems specifically: a system is an internal product needing an owner, versioning, docs and a deprecation policy — roughly a person's job. Before a settled visual language and a second consuming app, that is a product's overhead for one customer sitting next to you.

My recommendation: tokens plus a handful of a11y-hard primitives on day one, the rule of three for everything else, and an explicit demotion path — copying a component back into a diverging feature is a healthy PR, and teams never do it because promotion feels like progress.

Senior: You inherit a 200k-line React app organised by file type. What do you do?

Not a rewrite. It fails for a reason unrelated to skill: for its whole duration you ship no features while the old app keeps changing, so you chase a moving target with a team that is also maintaining the thing you are replacing. Strangle it instead, feature by feature, with both layouts coexisting.

First I measure rather than assert, because I will need to justify the cost. Co-change coupling from version control history shows which files change together across folder boundaries; import cycles come from madge; bundle composition from a visualizer. That converts "the structure is bad" into "these six files co-change in 40% of commits and live in five directories".

StepActionRisk
0Empty features/, shared/, path aliases, lint rule as warningNone — no behaviour change, merges in a day
1Migrate one feature that has active workLow — rides along with a ticket someone owns
2Pure file moves + index.ts, no refactoringLow, and reviewable in ten minutes
3Delete what the move revealed as deadLow, and it is the best part
4Repeat; leave cold code where it isMixed layout — acceptable indefinitely
5Flip lint to error once stragglers are only cold codeNone by then

Two non-negotiables. Never block a feature on the migration — the moment product work waits on architecture work, the architecture work gets cancelled. And never move and refactor in the same commit: a pure-move diff is reviewable, a move-plus-rewrite diff is unreviewable and gets rubber-stamped, which is how migrations introduce the bugs that discredit them.

What I would deliberately not do early: adopt a monorepo, extract a design system package, or install a dependency-graph matrix tool. Those solve problems this app has not demonstrated yet, and each adds tooling maintenance during the period when the team's credibility depends on shipping.

Recommendation: structure in day one, one feature in week one, the boundary rule as a warning immediately and an error when the count reaches zero. Accept a permanently mixed codebase — a half-migrated app whose active 20% is clean beats a consistently bad one, and consistency was never the goal. Change cost was.

2 (easy): A junior asks why they cannot do this. Give the specific technical reason, not "it breaks the layering". 
// src/shared/ui/Button.tsx
import { useCart } from '@/features/cart';

export function Button({ children, showCartCount, ...rest }) {
  const { count } = useCart();

    <button {...rest}>

Solution

Three concrete consequences, all observable:

1. Every page that renders a button now bundles the cart. The import is static, so the bundler pulls cart's module graph — its reducer, its api layer, its types, and anything those import — into any chunk containing Button. A login page with one button ships the cart.

2. Button now throws outside a CartProvider. A primitive that works only inside one feature's provider is not a primitive. Storybook stories, unit tests, and the marketing page all break with "useCart must be used within a CartProvider".

3. The dependency is now circular in spirit and soon in fact. cart renders Button; Button imports cart. Once anything in that loop is evaluated at module scope you get the classic "Element type is invalid: got undefined".

// shared/ui/Button.tsx — knows nothing about any domain

      {children}
      {badge != null && <span className="badge">{badge}</span>}

  );
}

// features/cart/components/CartBadge.tsx — the feature composes

3 (medium): After adding a shared barrel, the dev server takes 9s per page load and one route crashes with "Element type is invalid: expected a string or a class/function but got: undefined". Explain both, and fix them. 
// src/shared/index.ts
export * from './ui/Button';
export * from './ui/Modal';
export * from './ui/Card';
// ...200 more

// src/shared/ui/Card.tsx
import { Button } from '@/shared';        // its own barrel
export const CARD_ACTIONS = [Button];     // module scope!
Solution

The 9s dev load is the barrel. Vite serves unbundled ES modules in development, so one import { Button } from '@/shared' makes the browser request the barrel, which requests all 200 re-exported modules, each of which requests its own imports. Every page that touches the barrel pays it, on every reload. In production the equivalent cost is bundle size: export * is tree-shakeable only if every module in the chain is side-effect free, and one CSS import or a missing "sideEffects": false defeats it silently.

The crash is a cycle through that barrel, and the message never says so. Card imports @/shared; the barrel exports Card. ESM hoists bindings but not values, so whichever module is evaluated second sees the other's exports in the temporal dead zone. Button is undefined when CARD_ACTIONS is built — at module scope, so there is no later chance to fix itself — and React reports the resulting element type as undefined.

// FIX 1 — never import your own barrel from inside the layer
import { Button } from './Button';

// FIX 2 — if the value is only needed at call time, the cycle is harmless
export const getCardActions = () => [Button];

// FIX 3 — the barrel is for consumers of shared/, not for shared/ itself.
// Better still: drop the global barrel and import files directly.
Cycle evaluated atSymptomHarmful?
Module scope (a const array, a decorator)undefined, or "cannot access before initialization"Yes — and order-dependent, so dev may pass
Inside a function bodyNone — both modules initialised by call timeNo

Why this bug eats an afternoon: it is order-dependent. Change an unrelated import elsewhere, the bundler orders the graph differently, and the crash moves to another component or vanishes — which is exactly the profile of a bug people call "flaky" and stop investigating.

The durable fix is a CI step, madge --circular src, plus the rule that barrels exist at module boundaries only. A feature's six-export index.ts is fine; a 200-line export * is a convenience you are paying for four times.

5 (hard): A "recently viewed products" list must appear in the header, on the product page, and in checkout. Three teams own those. Design the module boundaries, and say what you would deliberately not build.

Solution

Three real consumers, one genuinely shared concept, and a correctness bug already present — this is the case where extraction is right. But it is not shared UI: it is a feature that owns a piece of data, and it exposes a capability.

src/features/recently-viewed/

Why a feature and not shared/: it knows what a product is. The moment a module in shared/ understands a domain noun, it has an upward dependency and stops being reusable or testable in isolation. Features may import sibling indexes, so all three consumers are legal.

The bug the duplication was hiding: JSON.parse on corrupted localStorage throws during the state initialiser, which throws during render — so the page is blank, and only for the users whose storage is bad, which is why it never reproduced. Reading storage during render is also an SSR hazard: on the server there is no localStorage, and a value that differs between server and client produces a hydration mismatch. Both are fixed once, in one module.

// storage.ts
export function readRecent() {
  if (typeof window === 'undefined') return [];   // SSR-safe
  try {
    const raw = JSON.parse(localStorage.getItem(KEY) ?? '[]');
    return Array.isArray(raw) ? raw.slice(0, CAP) : [];
  } catch {
    localStorage.removeItem(KEY);                 // self-healing
    return [];
  }
}

🎯 Key Takeaways

  • Architecture is measured in change cost, not code size — files touched, owners triggered, and confidence that nothing else broke.
  • The deletion test is the sharpest question you can ask: if you cannot remove a feature by deleting one folder and one route entry, you have files rather than modules.
  • Type-based folders sort by the least interesting property — "is it a hook" is what you care least about at 3am; "is it checkout" is what you always care about.
  • A feature's index.ts is the architecture: every export is a promise, and everything absent from it is free to change on a Friday afternoon.
  • An import rule in a wiki is broken in week one — ten lines of no-restricted-imports banning @/features/*/* is what actually holds.
  • Roll boundary rules out as warnings first; an error with 400 existing violations gets disabled that afternoon.
  • Dependencies point down only: app → features → shared → lib, and shared/ importing a feature is the most common violation.
  • ESM hoists bindings but not values, so a cycle evaluated at module scope yields "Element type is invalid: got undefined" — a message that never mentions imports.
  • Barrels belong at module boundaries, not everywhere: a global export * costs tree shaking, dev-server time, test time and cycles.
  • A shared component earns its place at three real consumers — two is a coincidence, and the wrong abstraction costs a sprint where duplication costs an afternoon.
  • Anything that knows a domain noun does not belong in shared/; demotion — copying a component back into a diverging feature — is a healthy PR.
  • Discriminated unions make impossible prop combinations untypeable, moving guards from runtime to the compiler.
  • res.json() returns any, so annotating the result is an assertion, not a check — validate at the network boundary or every downstream type is fiction.
  • Feature state in a central store is an upward dependency in disguise — the feature stops being deletable the moment app-level code knows its shape.
  • Never rewrite; strangle — pure file moves, one feature at a time, never blocking a feature on the migration, with both layouts coexisting indefinitely.
  • Adopting a large team's architecture without a large team's problem is debt that is hard to argue against because it looks like maturity.
