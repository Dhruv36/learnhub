useEffect Mastery Effects & Lifecycle

What you'll master: what an effect is actually for — synchronising with a system outside React — and the much larger body of code that people put in effects and shouldn't: derived values, event-handler logic, and data transformation; the timing model, commit → paint → passive effect, and what useLayoutEffect costs you by running before paint; the dependency array as a shallow-compare list of reactive values, and why a lint suppression is nearly always a real bug wearing a comment; cleanup runs before every re-run, not only on unmount; StrictMode double-invoking effects in development only, why the team did that, and how to tell a real bug from the double-invoke; stale closures and the three genuine fixes; object and function dependencies changing identity every render; the race condition in every naive fetch effect; and effects that set state until the tab locks up. Prerequisites: State & useState and The Render Cycle — effect timing only makes sense once commit does.

Part 1 — An Effect Synchronises With Something Outside React

The name is misleading. useEffect is not "run this after render" and it is not a lifecycle hook with a new spelling. It exists for one job: keeping something that is not React in step with React state. A WebSocket, a browser API, a setInterval, a chart library that owns its own DOM node, the document title, a network request. Each of those lives outside the render tree and cannot be described by returning JSX, so you describe it as a synchronisation: given this state, this is what the outside system should look like.

  THE SHAPE OF EVERY CORRECT EFFECT

  useEffect(() => {
      START synchronising with the external system, using
      the current values of the reactive things it depends on

      return () => STOP synchronising
  }, [the reactive things it depends on]);

  Read it as a sentence, not a lifecycle:
    "While roomId is 'general', keep a connection to 'general' open."

  NOT "on mount, connect; on unmount, disconnect." That framing is
  what produces the bugs in Part 4 — because it has no answer for
  what happens when roomId changes while the component stays mounted.

That framing hands you both the dependency array — the values the sentence mentions — and the cleanup, which is whatever undoes the sentence.

The code that should not be an effect at all

Most useEffect calls in an average codebase are not synchronising with anything. They are computing a value, reacting to a click, or copying one piece of React state into another. Every one of those is slower, buggier and longer than the version without the effect.

  ❌  const [items, setItems]     = useState([]);

      paint     the user briefly sees the stale filter
      effect    setVisible(...)

  Two renders, one wrong frame, and two state variables that can
  disagree forever if any path sets one without the other.

🔑 The test: could this line have been written during render, or inside the event handler that caused it? If yes, it does not belong in an effect. An effect is for the things that cannot be expressed as "what should the screen look like" — and there are far fewer of those than the average codebase suggests.

Part 2 — Timing: Commit, Paint, and the Passive Effect Queue

Effects do not run "after render". Render is the pure phase that produces a description; nothing has touched the DOM yet. Effects are scheduled during commit, and when they actually run depends on which hook you used.

  ONE UPDATE, END TO END

  1. RENDER          your component runs, returns elements. Pure.
                     No DOM. May be thrown away or restarted.

  2. RECONCILE       React diffs the new tree against the old and
                     builds a list of DOM mutations.

  3. COMMIT          ─┬─ mutations applied to the real DOM
                      │  (correct now, but NOT drawn)
                      ├─ cleanup of previous useLayoutEffect
                      ├─ useLayoutEffect callbacks    ◄── SYNCHRONOUS,
                      └─ refs assigned                    blocks paint

  4. PAINT           the browser rasterises. The user sees it.

  5. PASSIVE FLUSH   ─┬─ cleanup of previous useEffect
                      └─ useEffect callbacks          ◄── after paint

  The gap between 4 and 5 is why a useEffect that measures a node and
  then repositions it flickers: the wrong position was already on
  screen for at least one frame.

"Asynchronously" is not "on a timer". React flushes passive effects on a scheduler callback shortly after paint, but flushes them early and synchronously if something forces the issue — a new update arriving first, or an update from a discrete input event such as a click. Rely only on the ordering, never on a delay.

  Fix for the third: BATCH. Read every measurement first, then write
  every style. Never interleave.

Part 3 — The Dependency Array Is a Shallow Compare Over Reactive Values

After every commit React compares the new dependency array with the previous one, element by element, using Object.is. If every element matches, the effect is skipped entirely — the previous cleanup does not run either. If any element differs, React runs the previous cleanup and then the new effect. That is the whole mechanism.

  THE THREE FORMS

  useEffect(fn)          no array — after EVERY commit. Rare and
                         usually accidental.

  useEffect(fn, [])      after the first commit only; cleanup at
                         unmount. Correct ONLY if the body reads
                         nothing reactive.

  useEffect(fn, [a, b])  after the first commit, and after any commit
                         where !Object.is(a, prevA) || !Object.is(b, prevB)

  Object.is, not ===. Two real differences:
      Object.is(NaN, NaN)   -> true    (=== says false)
      Object.is(0, -0)      -> false   (=== says true)
  A NaN dependency from a failed parseFloat would re-run forever
  under ===. It does not under Object.is.

  The array LENGTH must be constant across renders — React compares
  by index, so a conditionally-built array shifts the comparison.

A reactive value is anything that can differ between two renders of this component: props, state, context values, and any local variable computed from those during render. Everything else is not reactive and does not belong in the array — including things the linter will not put there for you and things people add "to be safe".

ValueReactive?Goes in the array?Why

Why suppressing the lint rule is almost always a bug

react-hooks/exhaustive-deps does not enforce a style. It enforces the invariant the whole hook rests on: the effect body may only read values that are in the array. Break that and the effect keeps running with values from an older render, indefinitely, with no error.

  ❌  useEffect(() => {
        const t = setInterval(() => sendHeartbeat(userId), 30_000);
        return () => clearInterval(t);
        // eslint-disable-next-line react-hooks/exhaustive-deps
      }, []);   //  "I only want this on mount"

  What you built: a heartbeat pinned to whichever userId was current
  at MOUNT. Log out, log in as someone else, and the app sends
  heartbeats for the previous user until a full remount. The screen is
  correct; the network tab is not. This reaches production constantly,
  because nothing looks wrong locally where you only ever log in as
  one user.

  ✅  }, [userId]);   // switching user tears down and restarts it

  WHEN THE WARNING IS TELLING YOU SOMETHING ELSE:

    "it re-runs too often"   -> the dep is an object or function
                                rebuilt every render. Fix the
                                identity (Part 6); keep the dep.
    "I only want the FIRST
     value, ever"            -> that is initial state, not an effect.
                                useState(() => initial) or a ref.
    "I want the latest value
     without re-running"     -> the ref-latest pattern (Part 5), with
                                a comment saying so.

  Each of those is a code change. None is a suppression comment.
🔑 React 19 ships an experimental useEffectEvent for exactly the "read the latest value without making it a dependency" case: you extract the non-reactive part into an event function that is deliberately excluded from the array. It is not stable API at the time of writing, and the ref pattern in Part 5 does the same job today with no experimental surface. Know it exists; do not build on it yet.

Part 4 — Cleanup Runs Before Every Re-run, Not Only on Unmount

This is the single most consequential misunderstanding in the hook. People read the returned function as "componentWillUnmount". It is not. React calls it before every subsequent run of the effect, and once more at unmount. If the effect runs eleven times, the cleanup runs eleven times.

  ACTUAL SEQUENCE — roomId goes "general" -> "random" -> unmount

    mount            effect("general")           connect general
    roomId="random"  cleanup("general")          disconnect general
                     effect("random")            connect random
    unrelated render deps unchanged              nothing happens
    unmount          cleanup("random")           disconnect random

  React NEVER leaves two synchronisations running at once, and never
  leaves one running past the state it belonged to. Cleanup-before-
  setup is what guarantees that.

  Note the closure: cleanup("general") closes over the roomId from
  the render that created it — "general", not "random". Not a bug,
  the point: a cleanup must undo what ITS OWN effect did.
  SUBSCRIPTION — the canonical case

  useEffect(() => {
    const conn = createConnection(serverUrl, roomId);
    conn.connect();
    conn.on("message", handleMessage);
    return () => conn.disconnect();          // undoes exactly this
  }, [serverUrl, roomId]);

  Drop the cleanup and switch rooms five times: five live sockets,
  five copies of every message rendered, a server that thinks five
  clients are present. Users report "messages are duplicated" —
  nobody reports "we leaked a socket".

  INTERVAL — same shape, cheaper to get wrong

  useEffect(() => {
    const id = setInterval(tick, 1000);
    return () => clearInterval(id);
  }, []);

  Without clearInterval, a component that mounts and unmounts as the
  user navigates leaves one timer per visit. Forty navigations, forty
  timers, all firing, all holding their closures alive so nothing
  they captured can be collected. The page gets slower the longer the
  session runs — the classic "it's fine until about twenty minutes
  in" report.

Part 5 — StrictMode's Double Invoke, and Stale Closures

Wrap your tree in <StrictMode> and React 18+ will, in development builds only, run every effect twice on mount: setup, cleanup, setup. It also double-invokes component function bodies and reducers. None of this happens in a production build — the code that does it is stripped.

  WHAT YOU OBSERVE ON MOUNT, DEV ONLY

    effect  ▸ "connect"
    cleanup ▸ "disconnect"      ◄── React does this deliberately
    effect  ▸ "connect"

  WHY THE TEAM DID IT

  A missing cleanup is invisible on the happy path. Everything works
  until the component remounts — and in a real app it remounts on
  navigation, on a key change, on a Fast Refresh. The double invoke
  MANUFACTURES that remount on every mount, so the bug shows up on
  your machine in the first minute instead of in production three
  weeks later. It is also forward-looking: React reserves the right
  to unmount and remount a subtree with its state preserved, and code
  that survives a double invoke survives that too.

  HOW TO TELL A REAL BUG FROM THE DOUBLE INVOKE

    Symptom in dev              Real bug?   What it means
    ───────────────────────────────────────────────────────────────
    Two sockets stay open       YES         cleanup missing
    Two intervals keep firing   YES         cleanup missing
    Two POSTs sent              YES         a mutation is in an
                                            effect; move it to the
                                            handler
    A counter starts at 2       YES         the effect mutates
                                            external state and is
                                            not idempotent
    Two fetches, ONE result
    rendered, no duplicates     NO          fired twice, the first
                                            discarded by cleanup.
                                            Wasteful, not broken.
    Two console.logs            NO          that is the whole bug

  THE TEST: after the first cleanup, does the second setup leave the
  system in the same state one setup would? If no, your cleanup is
  incomplete. "Disable StrictMode" is not on this list — it hides the
  failure, it does not remove it.
🔑 The double-invoke is not why your app fetches twice in production. It cannot be — the behaviour does not exist in a production build. Duplicate production requests mean a dependency churning, a structural double mount, or a router remount. Check against a production build before blaming StrictMode; a great deal of engineering time has gone into this misattribution.

Stale closures

Every render creates fresh local variables and fresh functions closing over them. An effect callback is one of those functions, so it sees the props and state from the render that created it — permanently. If the effect never re-runs, that snapshot never updates.

  ❌  const [count, setCount] = useState(0);

      useEffect(() => {
        const id = setInterval(() => {
          setCount(count + 1);        // count is captured HERE
        }, 1000);
        return () => clearInterval(id);
      }, []);                          // never re-runs

  The interval was created during the render where count === 0. Its
  closure holds 0 forever, so every tick computes 0 + 1 = 1.

    tick 1  setCount(0 + 1)  -> 1   (re-renders)
    tick 2  setCount(0 + 1)  -> 1   (same value, React bails out)

  The display freezes at 1 and nothing throws. The interval is
  running perfectly; it is reading a variable from a render that
  ended minutes ago.

Add the dependency}, [count]);The effect genuinely should restart when the value changes — a subscription to a changing roomTears down and rebuilds every time; for an interval that means a new timer each second
Functional updatersetCount(c => c + 1)You only need the previous value, not any other reactive value. The best fix for counters, queues, togglesNone. React passes the current value in, so the closure is irrelevant

  THE REF-LATEST PATTERN, WRITTEN OUT

  function useInterval(callback, delay) {
    const saved = useRef(callback);

    useEffect(() => { saved.current = callback; }, [callback]);
    //  ^ every render, point the ref at the newest function

    useEffect(() => {
      if (delay == null) return;                 // null pauses it
      const id = setInterval(() => saved.current(), delay);
      return () => clearInterval(id);
    }, [delay]);                                 // callback NOT a dep
  }

  The interval is rebuilt only when delay changes; the function it
  calls is always the freshest, because the ref is repointed every
  render.

  Why the assignment is in an EFFECT, not the render body: writing to
  a ref during render is a side effect in the pure phase. Under
  concurrent rendering React may render a component and throw the
  result away, and the ref would keep a value from a render that
  never committed. Assign in an effect, or in an event handler.

Part 6 — Unstable Deps, Fetch Races, and Effects That Set State

Three failure modes that share a root: React compares dependencies by identity, and JavaScript gives a fresh identity to every object, array and function literal you evaluate.

  ❌  function Chat({ roomId }) {
        const options = { serverUrl: "wss://x.io", roomId };  // NEW every render

        useEffect(() => {
          const c = createConnection(options);
          c.connect();
          return () => c.disconnect();
        }, [options]);      // linter is satisfied. Behaviour is a disaster.

  { } !== { } — always, regardless of contents. So:

    render -> new options object -> dep changed -> cleanup + effect
           -> effect connects, which sets state on open
           -> render -> new options object -> dep changed -> ...

  An infinite connect/disconnect loop that saturates the network tab
  and pegs a core. The same shape with fetch is the classic "why is
  my app making 4000 requests" screenshot.

  Which is why deps should be PRIMITIVES where possible: strings and
  numbers compare by value, so a re-render with the same roomId is a
  genuine no-op.
Fix, in order of preferenceHowWhen it is the right one
1. Move it inside the effectDeclare options in the effect body; depend on [roomId]Almost always. Nothing else uses the object, so nothing else needs to see it. Zero API surface, no memo to keep correct
2. Hoist it out of the componentModule-scope constThe value has no reactive inputs at all — a config constant, a formatter, a regex
3. Depend on the fields, not the object}, [options.serverUrl, options.roomId]);The object comes from a parent you cannot change, and you only need two primitives out of it
4. useMemo / useCallbackMemoize at the point of creation, with its own correct dep arrayLast. Only when the value must be shared across effects or passed to a memoized child. It moves the problem up a level rather than removing it, and adds a second dep array to keep correct

The race condition in every naive fetch effect

  ❌  useEffect(() => {
        fetch(`/api/user/${id}`)
          .then(r => r.json())
          .then(setUser);
      }, [id]);

  TIMELINE — the user clicks user 1, then quickly clicks user 2

    t=0ms     id=1  request A fired
    t=40ms    id=2  request B fired      (effect re-ran, A not cancelled)
    t=90ms          B resolves -> setUser(user 2)   screen: user 2 ✓
    t=310ms         A resolves -> setUser(user 1)   screen: user 1 ✗

  The screen shows user 1 while the URL, the highlight and every
  other piece of state say user 2. Responses arrive in network order,
  not request order, and a cold cache miss on the FIRST request is
  exactly how the slow one lands last.

  Invisible on localhost, where both take 3ms and never overlap.
  Routine on a real connection — and the reason "the wrong profile
  sometimes shows" is so hard to reproduce.
  FIX 1 — THE IGNORE FLAG (works with anything thenable)

  useEffect(() => {
    let ignore = false;
    fetch(`/api/user/${id}`)
      .then(r => r.json())
      .then(data => { if (!ignore) setUser(data); });
    return () => { ignore = true; };
  }, [id]);

  Cleanup runs before the re-run, so request A's closure sees its own
  ignore === true and drops the result. The request still completes
  and still costs bandwidth.

  FIX 2 — ABORTCONTROLLER (actually cancels)

  useEffect(() => {
    const ac = new AbortController();
    fetch(`/api/user/${id}`, { signal: ac.signal })
      .then(r => r.json())
      .then(setUser)
      .catch(e => { if (e.name !== "AbortError") setError(e); });
    return () => ac.abort();
  }, [id]);

  The socket is torn down and the server can stop work. Note the
  catch: aborting REJECTS the promise, so without that guard every
  navigation writes a spurious error into state.

  THE DIFFERENCE, PLAINLY:
    ignore flag       discards a result you already paid for
    AbortController   stops paying for it

  Use the flag when the response is cheap or the library has no
  cancellation. Use AbortController when the request is expensive, on
  a metered connection, or when the server does real work per
  request. Both together is fine, and is what most production hooks
  do.

Effects that set state

An effect that calls setState costs a second render for every one it participates in. That is sometimes unavoidable — you measured something, or data arrived. It becomes a loop the moment the state it sets feeds back into its own dependencies.

  ❌  const [items, setItems] = useState([]);
      useEffect(() => {
        setItems([...items, newOne]);   // reads items, writes items
      }, [items]);                       // items changed -> run again

  render -> effect -> setState -> render -> effect -> ...
  React gives up after 50 nested updates with
  "Maximum update depth exceeded" — a guard, not a fix.

  THE DIAGNOSTIC, when the cycle is not obvious:

    useEffect(() => { console.count("effect"); }, [dep]);

  If the count climbs with no user input while the dep's CONTENTS
  look unchanged, you have found it: a non-primitive dependency
  rebuilt every render. Go to the table above.

  Legitimate setState-in-effect, for contrast:
    - data arrived from the network      (no other way to know)
    - a measurement from the DOM         (use useLayoutEffect)
    - an external store pushed a value   (prefer useSyncExternalStore)
  In all three, what is being set is NOT what is being depended on.
  That asymmetry is what makes them terminate.

Interview Questions

Beginner: What is useEffect for, and when should you not use it?

It is for synchronising a component with something that lives outside React — a subscription, a timer, a browser API, a third-party widget, the network. The effect body describes how to start that synchronisation and the returned function describes how to stop it.

You should not use it for anything that can be expressed as a render or as an event handler. Deriving a value from props or state is a const during render. Reacting to a click is the onClick. Resetting state when a prop changes is a key. Initialising an expensive value once is a lazy useState initialiser.

The reason this matters is not purity, it is behaviour: an effect that computes derived state renders twice and commits the stale value in between, so there is a real frame where the screen is wrong. And two pieces of state that must be kept in step can drift, while a derived value cannot.

The one-line test I use: could this line have run during render, or inside the handler that caused it? If yes, it does not belong in an effect.

Beginner: What does the dependency array do, and what is the difference between omitting it and passing []?

After every commit React compares the new array with the previous one element by element using Object.is. If they all match, it skips the effect entirely — the cleanup does not run either. If any element differs, it runs the previous cleanup and then the effect.

Omitting the array means "no comparison is possible", so the effect runs after every single commit. Passing [] means "the comparison is trivially equal every time", so the effect runs once after the first commit and its cleanup runs at unmount.

[] is only correct if the effect body reads nothing reactive. If it reads a prop or a state variable, [] is a bug: the effect will keep using the value from the first render forever. That is the stale closure, and it is silent — no warning, no error, just an effect quietly acting on old data.

Worth adding: the array length must be constant across renders, because React compares by index. You cannot build it conditionally.

Mid: When does the cleanup function run? Walk through a component whose roomId prop changes.

Cleanup runs before every subsequent run of the effect, and once more at unmount. It is not an unmount hook.

With roomId going from "general" to "random" and then unmounting: on mount the effect runs and connects to "general". When roomId becomes "random", React first runs the cleanup created by the "general" effect, which disconnects "general", then runs the new effect, which connects to "random". A re-render that does not change roomId does nothing at all. At unmount the "random" cleanup runs and disconnects.

The important detail is which values the cleanup sees. It closes over the render that created it, so the "general" cleanup disconnects "general" even though the current render says "random". That is required for correctness — a cleanup must undo what its own effect did, not what the current state would do.

The invariant this buys you is that React never leaves two synchronisations alive at once. Without cleanup, switching rooms five times leaves five open sockets and every message rendered five times. Users report that as "duplicate messages", which is why the real cause takes a while to find.

Mid: Why does StrictMode run effects twice, and how do you tell a real bug from the double invoke?

In development only, React 18+ mounts the component, runs the effect, immediately runs the cleanup, then runs the effect again. The production build does not do this — the code is stripped.

The purpose is to surface missing or incomplete cleanup. A missing cleanup is invisible until the component actually remounts, which in a real app happens on navigation, on a key change, on Fast Refresh. The double invoke forces that remount to happen on every mount, so the bug appears on your machine immediately rather than in production later. It also prepares code for React's ability to unmount and remount a subtree while preserving state.

The test for whether you have a real bug: after the first cleanup, does the second setup leave the external system in the same state that a single setup would? Two sockets still open, two intervals still firing, two POSTs sent, a counter that lands on 2 — all real bugs, all cleanup or idempotence problems. Two console logs, or two fetches where the first result is discarded and one row renders — not bugs, just visible dev noise.

Turning StrictMode off is not a fix; it deletes the detector while leaving the defect. And if you see duplicated requests in a production build, StrictMode cannot be the cause — look for a dependency changing identity, or a router remounting the route.

Senior: A fetch inside useEffect sometimes renders the wrong record. Diagnose it, fix it, and say what you would actually ship.

That is a race. The effect re-runs when the id changes, but the in-flight request from the previous id is not cancelled and nothing discards its result. Responses arrive in network order, not request order, so if the first request is a cache miss and the second is a hit, the stale response lands last and wins the setState. The screen then disagrees with the URL and with every other piece of state.

It is invisible locally because both requests take a few milliseconds and never overlap. That is exactly why it reaches production.

The minimal correct fix is a closure-scoped ignore flag set to true in the cleanup, with the then checking it before setting state. Cleanup runs before the re-run, so the abandoned request's own closure knows to drop its result. Four lines, works with any promise. The stronger fix is an AbortController whose abort() is the cleanup, which actually tears down the socket so the browser and server stop spending on it — with a catch that filters AbortError, or every navigation writes a fake error into state.

The distinction is worth stating precisely: the flag discards a result you already paid for; the controller stops paying. On an expensive endpoint or a metered connection that difference is real.

What I would ship is neither, in most codebases. This bug is one of four that a hand-rolled fetch effect has — the others are no caching, so every mount refetches; waterfalls, because nested components each fetch in their own effect; and no sharing, so two components needing the same data issue two requests. Fixing all four by hand reconstructs a caching library badly. I would use TanStack Query, or a router loader that fetches before rendering, and keep the hand-rolled version only for a genuinely one-off request in a leaf component.

Senior: An effect must not re-run when a callback prop changes, but must always call the newest one. How, and what are you giving up?

The linter is right that the callback is a dependency: the effect body reads it. The problem is that parents rebuild inline functions every render, so honouring the dependency tears down and rebuilds the subscription on every parent render — for a socket or an interval that is unacceptable.

The correct fix in order of preference. First, ask the parent to stabilise the function with useCallback; if the parent is yours and the callback has few dependencies, this is the honest fix and keeps the reactivity real. Second, if you do not own the parent — a public hook, a library boundary — use the ref-latest pattern: hold the callback in a ref, repoint the ref in a small effect on every render, and have the subscription call ref.current(). The subscription then depends only on the things that should genuinely restart it.

What you give up is reactivity, deliberately and permanently. The effect will never respond to that value changing. If someone later changes the callback so that which function it is matters to the subscription — a different endpoint, a different channel — the ref silently does the wrong thing and there is no warning. That is why this needs a comment stating the intent, otherwise the next reader "fixes" it by adding the dependency back.

The assignment must happen in an effect, not in the render body. Writing to a ref during render is a side effect in the pure phase; under concurrent rendering React can render a component and discard the result, and the ref would keep a value from a render that never committed.

My recommendation: useCallback in the parent when I own it, because the reactivity stays truthful; the ref pattern at library boundaries where I cannot impose that discipline on callers. React 19's experimental useEffectEvent is designed to make this pattern first-class and lint-aware, and when it stabilises it becomes the right answer — but it is not stable API yet and I would not put it in a production codebase today.

🏋️ Graded Exercises

1 (easy): This effect syncs the document title. It has a bug that only shows up when the user navigates away. 
function Page({ title }) {
  useEffect(() => {
    document.title = title;
  }, [title]);
  return <h1>{title}</h1>;
}
Solution 
function Page({ title }) {
  useEffect(() => {
    const previous = document.title;
    document.title = title;
    return () => { document.title = previous; };
  }, [title]);
  return <h1>{title}</h1>;
}

What the original does at runtime: it sets the title correctly and never puts it back. Navigate from a product page to a route that does not set a title and the tab still reads "Wireless Mouse — Shop". The synchronisation was started and never stopped, which is the same defect as a missing removeEventListener, just with a harmless-looking global.

Why capturing previous inside the effect matters: each run captures the title as it was when that run started, and its own cleanup restores exactly that. Cleanup runs before every re-run, so a chain of title changes unwinds correctly in reverse. Capturing it outside the effect, or in a ref written during render, breaks that pairing.

The honest caveat: restoring a global like this is only safe while one component owns it. Two components both setting document.title will fight, and the last cleanup wins with a stale value. In a real app the title belongs to the router, set once per route.

3 (medium): A timer that should count up every second. It freezes at 1. Explain precisely why, then give two different correct fixes and say which you would ship. 
function Timer() {
  const [seconds, setSeconds] = useState(0);
  useEffect(() => {
    const id = setInterval(() => setSeconds(seconds + 1), 1000);
    return () => clearInterval(id);
  }, []);
  return <p>{seconds}s</p>;
}
Solution 
// FIX A — functional updater. Ship this one.
useEffect(() => {
  const id = setInterval(() => setSeconds(s => s + 1), 1000);
  return () => clearInterval(id);
}, []);

// FIX B — honour the dependency.
useEffect(() => {
  const id = setInterval(() => setSeconds(seconds + 1), 1000);
  return () => clearInterval(id);
}, [seconds]);

What the broken version does: the interval callback is created during the render where seconds === 0 and closes over that binding. [] means the effect never re-runs, so that one callback lives for the component's whole life computing 0 + 1. Tick one sets state to 1 and re-renders; tick two sets state to 1 again, React sees the same value and bails out without re-rendering. The interval is firing perfectly every second, reading a variable from a render that ended long ago.

Ship A. The functional updater is the right fix whenever the effect needs only the previous value: React passes the current state in, so the closure's staleness stops mattering and the effect genuinely has no reactive dependencies. Fix B is correct but rebuilds the timer sixty times a minute and compounds drift, because each new interval starts its 1000ms from after the render rather than from the last tick.

4 (medium): Under StrictMode the console shows "connected" twice. Decide whether there is a real bug, and fix whatever is actually wrong. 
function Chat({ roomId }) {
  const [messages, setMessages] = useState([]);
  const config = { url: "wss://chat.io", room: roomId };

  useEffect(() => {
    const conn = createConnection(config);
    conn.on("message", m => setMessages(prev => [...prev, m]));
    conn.connect();
    console.log("connected");
  }, [config]);

Solution 
function Chat({ roomId }) {
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    const config = { url: "wss://chat.io", room: roomId };  // INSIDE
    const conn = createConnection(config);
    conn.on("message", m => setMessages(prev => [...prev, m]));
    conn.connect();
    return () => conn.disconnect();                          // CLEANUP
  }, [roomId]);                                              // PRIMITIVE

  return <MessageList items={messages} />;
}

There are two real bugs, and the double log is a symptom of one of them. The double invoke did its job here: it exposed the missing cleanup in the first minute rather than in production.

Bug one — no cleanup. Nothing disconnects. In StrictMode you get two live sockets on mount. In production you get one per roomId change: switch rooms five times and five connections are open, all with live message listeners, so every message is appended five times. Users report duplicated messages; nobody reports a leaked socket.

Bug two — config is rebuilt every render. { } !== { }, so the dependency differs on every render. Each incoming message calls setMessages, which re-renders, which makes a new config, which re-runs the effect, which opens another connection. Combined with bug one this is a runaway loop: connections multiply with every message. Even with cleanup added, it would still disconnect and reconnect on every message.

Why move the object in rather than useMemo it: nothing outside the effect uses config. Moving it inside makes the dependency roomId, a string, which compares by value — so a re-render with the same room is a genuine no-op. useMemo would work but adds a second dependency array to keep correct and leaves the object visible in the component body inviting the same mistake later. Reach for memoization only when the value must be shared.

After the fix, StrictMode still logs twice — connect, disconnect, connect. That is now correct behaviour and not a bug: one connection remains open at the end.

5 (hard): Write useEventListener(target, event, handler) that attaches a listener, always calls the newest handler, and does not re-attach when the caller passes an inline arrow function. Handle a null target (a ref that has not attached yet).
Solution 
function useEventListener(target, event, handler, options) {
  const saved = useRef(handler);

  useEffect(() => { saved.current = handler; }, [handler]);

  useEffect(() => {
    const node = target && "current" in target ? target.current : target;
    if (!node?.addEventListener) return;      // null ref, or SSR

    const listener = e => saved.current(e);   // stable for this run
    node.addEventListener(event, listener, options);
    return () => node.removeEventListener(event, listener, options);
  }, [target, event, options]);
}

// usage — the inline arrow does NOT cause re-attachment
useEventListener(window, "resize", () => setWidth(window.innerWidth));

What the naive version does: putting handler in the dependency array is what the linter asks for and it is technically correct, but callers pass inline arrows, so the identity changes on every parent render. The effect then removes and re-adds the listener on every render — dozens of times a second during a resize. It works, and it is pure waste.

Why the ref is repointed in its own effect rather than assigned in the render body: writing to a ref during render is a side effect in the pure phase. Under concurrent rendering React can render a component and throw the result away, and the ref would then hold a handler from a render that never committed. The assignment effect has no cleanup because there is nothing to undo.

listener must be a local const, not saved.current directly. removeEventListener matches on reference identity; passing saved.current to both add and remove would fail the moment the ref was repointed between them, silently leaking the listener. Creating one stable wrapper per effect run guarantees the pair matches.

6 (hard): A search box fires a request per keystroke, sometimes shows results for a previous query, and floods the network tab. Fix all three problems in one hook.
Solution 
function useSearch(query) {
  const [state, setState] = useState({ status: "idle", data: null, error: null });

  // 1. DEBOUNCE — collapse a burst of keystrokes into one term
  const [term, setTerm] = useState(query);
  useEffect(() => {
    const t = setTimeout(() => setTerm(query), 300);
    return () => clearTimeout(t);      // cleanup on EVERY keystroke
  }, [query]);

  // 2. FETCH — cancelled and race-proof
  useEffect(() => {
    if (!term) { setState({ status: "idle", data: null, error: null }); return; }

    const ac = new AbortController();
    let ignore = false;
    setState(s => ({ ...s, status: "loading" }));

    fetch(`/api/search?q=${encodeURIComponent(term)}`, { signal: ac.signal })
      .then(r => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);   // fetch does NOT
        return r.json();                                  // reject on 404/500
      })
      .then(data => { if (!ignore) setState({ status: "success", data, error: null }); })
      .catch(err => {
        if (ignore || err.name === "AbortError") return;
        setState({ status: "error", data: null, error: err });
      });

    return () => { ignore = true; ac.abort(); };
  }, [term]);

  return state;
}

The debounce works because cleanup runs before every re-run. Each keystroke changes query, which runs the previous cleanup — cancelling the pending 300ms timeout — before scheduling a new one. Only a 300ms gap in typing lets a timeout survive to fire. This is the clearest demonstration in the language of why cleanup is not an unmount hook: here it never runs at unmount at all in the common case, and the whole mechanism depends on the re-run behaviour.

The race fix uses both guards, and they do different jobs. ac.abort() tears down the connection so the browser and server stop spending on an abandoned query. ignore covers the window where the response has already been received and the then is queued as a microtask — abort cannot un-deliver that, and without the flag a result that arrived microseconds before the cancellation still writes to state.

One state object, not three booleans. isLoading, data and error as separate variables admit combinations that cannot mean anything — loading and error at once, data alongside an error from a later query. A single status union makes those unrepresentable, and it means one setState per transition rather than three that can be interleaved by an out-of-order response.

The r.ok check is not optional. fetch only rejects on network failure; a 500 resolves normally, so without it you call .json() on an error page and report a JSON parse error instead of the actual server error.

Write it once to understand what the library is doing for you, then use the library. Note also that debouncing the term rather than the fetch call is deliberate: it keeps the fetch effect a pure function of a settled input, which is what makes the second effect easy to reason about.

🎯 Key Takeaways

  • An effect synchronises React with a system outside React. If the code could run during render or in an event handler, it is not an effect.
  • Derived state does not belong in an effect — it costs a second render and commits one visibly wrong frame in between.
  • Effects run after paint; useLayoutEffect runs before it and blocks the browser for its entire duration.
  • useLayoutEffect is for measure-then-adjust only. Reading getBoundingClientRect forces a synchronous reflow — roughly 0.5–3ms, and it compounds across a list.
  • Batch DOM reads before writes in any layout effect, or you get layout thrashing.
  • The dependency array is compared with Object.is, element by element, and its length must be constant across renders.
  • Reactive means props, state, context, and anything computed from them. Setters, dispatch and the ref object are stable; ref.current never belongs in the array.
  • useEffect cleanup runs before every re-run, not only on unmount — this is the fact that most effect bugs come from not knowing.
  • The cleanup closes over its own render's values, which is what lets it undo exactly what its effect did.
  • StrictMode double-invokes effects in development only — never in a production build, so it cannot be the cause of duplicate production requests.
  • If the double invoke breaks something, the cleanup is missing or the effect is not idempotent. Turning StrictMode off removes the detector, not the defect.
  • An effect sees the props and state from the render that created it. The three fixes are: add the dependency, use a functional updater, or hold the latest value in a ref.
  • Suppressing exhaustive-deps is almost always hiding a stale-closure bug that shows up as correct UI with wrong side effects.
  • Object and function dependencies get a new identity every render. Move them inside the effect first, hoist them out second, depend on primitive fields third, memoize last.
  • Every naive fetch effect has a race: guard with an ignore flag, which discards a result, or AbortController, which cancels the request.
  • An effect that depends on the state it sets is an infinite loop — React stops it at 50 nested updates, which is a guard, not a fix.
