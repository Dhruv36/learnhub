Error Boundaries & Resilience Patterns & Quality

What you'll master: exactly which errors a boundary catches — render, lifecycle, constructors below it — and the much longer list it does not: event handlers, async callbacks, promise rejections, SSR, and the boundary's own render; why a boundary is still the last thing in React that must be a class, and what react-error-boundary adds on top; why React 16 changed the default so an uncaught render error unmounts the entire tree, and why a blank page is the safer failure; boundary granularity as a product decision; why a reset that does not change the input immediately re-throws; reporting through componentDidCatch; and how boundaries interact with Suspense. Prerequisites: The Render Cycle, Composition Patterns.

Part 1 — What a Boundary Catches, and the Longer List It Does Not

  AN ERROR BOUNDARY IS A COMPONENT THAT CATCHES A THROWN ERROR FROM
  ANYWHERE IN THE TREE BELOW IT AND RENDERS A FALLBACK INSTEAD OF THAT
  SUBTREE. It is React's try/catch, and like try/catch it only wraps
  the code that runs INSIDE the call it is wrapping.

  That last sentence is the whole lesson. React calls your component
  functions during the render phase. A boundary wraps that call. So:

    CAUGHT:

      the render of any descendant           throw during the function body
      a descendant's constructor             class construction
      a descendant's lifecycle methods       componentDidMount, etc.
      a getDerivedStateFromProps below it
      a render triggered by a state update   whichever component throws
      a throw inside a useMemo               useMemo runs during render
      a lazy() chunk that fails to load      the throw is inside render

    NOT CAUGHT:

      event handlers                         onClick, onChange, onSubmit
      setTimeout / setInterval callbacks
      requestAnimationFrame callbacks
      .then / .catch / await after the first await
      any promise rejection at all
      server-side rendering                  renderToString, RSC
      the boundary's OWN render or fallback

  WHY THE SPLIT IS WHERE IT IS. React is on the call stack during
  render, so a throw propagates up through React's own frames and
  React can unwind the fiber tree to the nearest boundary.

    React.render()
      └─ Boundary            ← React holds a try/catch conceptually here
          └─ Sidebar
              └─ Widget      ← throws; the stack is still inside render

    browser click event
      └─ React's dispatch
          └─ your onClick    ← throws; render finished minutes ago

  An onClick fires from the BROWSER's event loop, long after render
  returned. There is nothing to unwind and no fiber to blame — and
  that is a JavaScript limitation, not a React one. You cannot catch a
  throw from a callback you did not call.

  THE PRACTICAL CONSEQUENCE PEOPLE MISS: MOST PRODUCTION ERRORS ARE IN
  THE UNCAUGHT CATEGORY. Render errors are usually reading a property
  of undefined, and they show up on the first load in development.
  Handler and async errors are failed requests, bad JSON, a permission
  denial — the things that only happen against a real backend. A
  boundary touches none of them, which is why teams who add one and
  see no change in their error dashboard conclude, wrongly, that it
  does not work.

  An uncaught handler error reaches window.onerror: the app stays
  mounted and the click silently does nothing, which the user reads as
  an unresponsive button. A rejected promise is quieter still — it
  reaches window.onunhandledrejection, which most apps never listen to
  unless a reporting SDK installed a handler for them.

  THE EFFECT ROW IS THE ONE PEOPLE GET WRONG IN BOTH DIRECTIONS.

    useEffect(() => {
      throw new Error('boom');          // CAUGHT — synchronous,
    }, []);                             // runs inside React's commit

    useEffect(() => {
      (async () => {
        const r = await fetch(url);     // everything AFTER this await
        if (!r.ok) throw new Error();   // is a separate task
      })();
    }, []);                             // NOT CAUGHT

  The rule is not "effects are caught" or "effects are not caught". It
  is: is React still on the stack? Everything up to the first await or
  .then is; nothing after it is.

Part 2 — Why This Is Still a Class, and What the Wrapper Adds

  THERE IS NO HOOK THAT MAKES AN ERROR BOUNDARY. Not in React 18, not
  in 19. This is the only remaining capability with no function-
  component equivalent, and it is deliberate rather than an oversight
  nobody got round to.

  THE MINIMAL BOUNDARY, IN FULL:

    class ErrorBoundary extends React.Component {
      state = { error: null };

      // PHASE 1: RENDER. Pure. Returns the next state.
      static getDerivedStateFromError(error) {
        return { error };
      }

      // PHASE 2: COMMIT. Side effects allowed.
      componentDidCatch(error, info) {
        report(error, info.componentStack);
      }

      render() {
        if (this.state.error) {
          return this.props.fallback(this.state.error);
        }
        return this.props.children;
      }
    }

  THE TWO METHODS ARE NOT INTERCHANGEABLE AND THE SPLIT IS THE POINT.

    getDerivedStateFromError   static, PURE, render phase. Its only
                               job is to flip state so the re-render
                               shows a fallback. It is static
                               precisely so you cannot reach `this`
                               and do something impure. A concurrent
                               render may call it, throw the work
                               away, and call it again — so it must be
                               safe to call twice.

    componentDidCatch          instance method, COMMIT phase, side
                               effects legal, runs ONCE per committed
                               error. This is where logging goes.

  WHY NO HOOK. A hook runs during the render of the component that
  owns it. To catch a child's throw you must be OUTSIDE that render.
  Class boundaries work because React special-cases the fiber type:
  when it unwinds from a throw it walks up looking for a fiber whose
  type declares one of those two methods. There is no analogous marker
  a function component could carry, and adding one would mean a
  second, parallel mechanism. The React team's position is that a
  declarative replacement should come as part of a broader Suspense-
  and-errors story, and that a half-measure would be worse than the
  class. Ten years in, the class is the API.

  IN PRACTICE YOU WRITE THIS ZERO TIMES. Install react-error-boundary
  (about 1.5KB gzipped) and use its component, because the four things
  it adds are things you would otherwise get wrong:

    <ErrorBoundary
      FallbackComponent={ErrorFallback}
      onError={(error, info) => report(error, info)}
      onReset={() => queryClient.clear()}
      resetKeys={[userId]}
    >
      <Profile userId={userId} />
    </ErrorBoundary>

    1. resetKeys       clears the error automatically when a value in
                       the array changes. This is the correct recovery
                       trigger — see Part 5.
    2. useErrorBoundary  a hook that lets a HANDLER or an async
                       callback deliberately throw INTO the nearest
                       boundary. This is the only sanctioned way to
                       route an uncatchable error to a boundary.
    3. onReset         a hook point to clear whatever caused the
                       failure before retrying.
    4. It re-throws correctly on repeated failure instead of looping.

  THE HOOK IS THE PART WORTH THE DEPENDENCY:

    const { showBoundary } = useErrorBoundary();

    async function onSubmit() {
      try {
        await placeOrder(cart);
      } catch (e) {
        showBoundary(e);      // schedules a state update that throws
      }                       // during the NEXT render, where React
    }                         // can see it

  It works by storing the error in state and re-throwing it during the
  component's next render — converting an uncatchable async error into
  a catchable render error. You can write this yourself in six lines;
  the value is that everyone on the team reaches for the same six.

Part 3 — Unmounting the Whole Tree Is the Deliberate Default

  BEFORE REACT 16, A RENDER ERROR LEFT THE COMPONENT IN A BROKEN
  HALF-STATE AND THE APP LIMPED ON. React 16 changed it: an error that
  reaches the root with no boundary in the way UNMOUNTS THE ENTIRE
  COMPONENT TREE. Your users get a white page.

  This is the single most complained-about default in React, and it is
  correct.

  THE ARGUMENT: A CORRUPTED UI IS MORE DANGEROUS THAN NO UI.

  When a render throws halfway through, the fiber tree is in a state
  React cannot reason about. Some children committed, some did not.
  The DOM reflects a partial render. Continuing means shipping a
  screen whose contents nobody — not React, not you — can describe.

  In a dashboard that is ugly. In these it is an incident:

    a banking screen showing the previous account's balance, because
      the account component threw and its old DOM remained

    a checkout showing the old total after the tax component threw, so
      the user consents to a price the server will not charge

    a permissions-gated admin panel whose guard component threw and
      whose children rendered anyway

  In each, a WHITE SCREEN IS THE CHEAPER FAILURE. A user who sees
  nothing knows something is wrong, reloads, and tells you. A user who
  sees a plausible wrong number acts on it. That is the same reasoning
  as a process aborting on a failed assertion rather than continuing.

  SO THE DEFAULT IS NOT "REACT IS FRAGILE" — it is "React refuses to
  guess". The blank page is a demand that YOU state what should happen
  instead, which is what a boundary is.

  WHAT ACTUALLY HAPPENS, STEP BY STEP:

    1. A component throws during render.
    2. React unwinds the fiber tree, walking up parent by parent.
    3. At each parent it asks: does this fiber's type define
       getDerivedStateFromError or componentDidCatch?
    4. First match wins. React re-renders THAT boundary with its new
       error state, so the fallback replaces the whole subtree.
    5. No match by the time it reaches the root: React unmounts
       everything and logs the error to the console.

  NOTE STEP 4 CAREFULLY: THE WHOLE SUBTREE UNDER THE BOUNDARY GOES,
  not just the component that threw. A boundary around a route
  replaces the route. There is no partial recovery, and any state held
  in that subtree is destroyed. That is what makes placement a design
  decision rather than a formality.

  IN DEVELOPMENT YOU ALSO GET THE ERROR OVERLAY, which is not React
  itself but your bundler's dev server. It appears on top of your
  fallback, so during development a working boundary can look like it
  did nothing. Dismiss the overlay to see the fallback. This costs
  people an hour roughly once per career.

Part 4 — Granularity Is a Product Decision

  "WHERE DO BOUNDARIES GO" IS NOT AN ENGINEERING QUESTION WITH ONE
  ANSWER. It is the question "which parts of this screen must keep
  working when another part fails", and only the product can answer it.

  THREE LEVELS, USED TOGETHER, NOT INSTEAD OF EACH OTHER:

    ROOT           one, at the top. Catches whatever slipped past
                   everything else; nothing inside the app survives.
                   Its job is to not be a white page: a branded screen
                   with a reload and a support reference.

    PER ROUTE      inside the layout, around the routed content. The
                   header, nav and router survive, so the user can
                   click somewhere else. This is the highest-value
                   single boundary in most apps, and the one most
                   teams skip.

    PER WIDGET     around anything independently failable — a chart, a
                   recommendations rail, a third-party embed. One card
                   fails; the rest of the page is untouched.

  THE SHAPE:

    <RootBoundary>
      <AppShell>                       ← survives a route error
        <Nav />
        <RouteBoundary key={pathname}>  ← key resets it on navigation
          <Routes>
            <Route path="/checkout" element={
              <Checkout>
                <OrderSummary />              ← NO boundary. If this
                                              fails, checkout MUST
                                              fail — see below.
                <WidgetBoundary>
                  <RecommendedItems />        ← boundary. Nice to have.
                </WidgetBoundary>
              </Checkout>
            } />
          </Routes>
        </RouteBoundary>
      </AppShell>
    </RootBoundary>

  DEGRADED RENDERING IS THE DESIGN GOAL: A FAILED SIDEBAR MUST NOT
  KILL CHECKOUT. Ask of every widget: if this cannot render, is the
  page still worth showing?

    recommendations fail      → hide the rail. Page is fine.
    the avatar image widget   → show initials. Page is fine.
    an analytics embed        → show nothing. Page is fine.
    the price total           → DO NOT hide it. Fail the page.
    a legal consent checkbox  → DO NOT hide it. Fail the page.

  THE LAST TWO ARE THE INTERESTING ONES. A boundary that hides a
  broken price is worse than no boundary, because it turns a visible
  crash into a silently incomplete checkout. Resilience is not "catch
  everything" — it is "fail at the right granularity". Wrapping a
  legally-required disclosure in a fallback that renders nothing is
  how you ship a compliance bug.

  A USEFUL RULE: PUT A BOUNDARY WHERE YOU WOULD ACCEPT THE FALLBACK AS
  A PERMANENT DESIGN. "We could not load recommendations" is a
  shippable screen. "Checkout with no total" is not.

  The easiest sell is third-party code — a chat widget, an ads slot, a
  map, a rich-text editor. You cannot fix its bugs and its release
  cadence is not yours.

  COST OF GRANULARITY: twenty boundaries means twenty fallback states
  someone draws and someone reviews. Teams that add them reflexively
  end up with "Something went wrong" everywhere, which is a white page
  with extra steps. Fewer boundaries with real fallbacks beat many
  with generic ones.

Part 5 — Recovery, and Why a Bare Reset Re-throws

  THE FALLBACK WITH A "TRY AGAIN" BUTTON IS THE MOST COMMON BROKEN
  ERROR BOUNDARY IN PRODUCTION.

    function Fallback({ resetErrorBoundary }) {
      return <button onClick={resetErrorBoundary}>Try again</button>;
    }

  Click it and the boundary clears its error state and re-renders its
  children. Its children re-render from EXACTLY THE SAME INPUTS that
  made them throw thirty seconds ago. So they throw again, instantly,
  and the user is back at the fallback having learned nothing.

    reset → render children → same props → same throw → fallback

  Worse, it can loop: if the throw happens synchronously and something
  auto-resets, you get a render/throw cycle that pins a CPU core.
  react-error-boundary guards this by refusing to reset repeatedly
  from the same error without a resetKey change.

  A RESET IS ONLY MEANINGFUL IF SOMETHING ABOUT THE INPUT CHANGED.
  There are exactly three ways to make that true:

  1. THE INPUT CHANGED BY ITSELF — the user navigated, picked a
     different id, changed a filter. Express this with resetKeys:

       <ErrorBoundary resetKeys={[userId, filter]} …>

     The boundary clears itself when any key changes. This is the
     honest version of "try again": the error is cleared because the
     thing that failed is no longer what you are asking for.

  2. YOU CLEARED THE STATE THAT CAUSED IT. If a component threw
     because a cached response was malformed, retrying is pointless
     until the cache entry is gone:

       <ErrorBoundary
         onReset={() => qc.resetQueries({ queryKey: ['user', id] })}
         resetKeys={[id]}
       />

     onReset runs BEFORE the children re-render, which is what makes
     this ordering work.

  3. THE FAILURE WAS TRANSIENT AND THE WORLD CHANGED. A chunk that
     failed to load because the network dropped will succeed on the
     second attempt. Here a plain retry IS legitimate — but bound it,
     and back it off, or a user on a train generates a request storm.

  THE HONEST FALLBACK MENU:

    error is a failed lazy chunk        → retry, then hard reload
    error is a bad server response      → clear the cache entry, retry
    error is a bug in your render code  → retry cannot help. Offer
                                          navigation away, and log it.
    error is a stale deployment         → window.location.reload()
                                          fetches the new bundle

  THE LAST ONE IS UNDER-USED. After a deploy, an old tab's lazy chunks
  404 because the filenames are content-hashed — a boundary-catchable
  render error with a genuinely correct automatic fix. Reload once,
  guarded by a sessionStorage flag so you never trap the user in a
  refresh loop. Exercise 3 builds it.

  ROUTING ASYNC AND HANDLER ERRORS TO A BOUNDARY. Part 1 established
  that a boundary cannot see them. If you want one to, you must
  convert them into a render error via an explicit state transition:

    const [error, setError] = useState(null);
    if (error) throw error;               // ← re-thrown DURING RENDER

    async function onSubmit() {
      try { await placeOrder(cart); }
      catch (e) { setError(e); }          // schedules the render above
    }

  That is precisely what useErrorBoundary().showBoundary does.

  BUT ASK WHETHER YOU WANT IT. Escalating a failed form submission to
  a boundary DESTROYS THE FORM — every field the user typed is gone,
  because the boundary unmounts the subtree. For a mutation, local
  error state next to the submit button is almost always the better
  product decision:

    escalate to a boundary   the component cannot meaningfully
                             continue: its core data is unusable
    handle locally           the user has a next action — retry the
                             save, fix a field, dismiss a toast

  A failed "load this page" is the first. A failed "save this form" is
  the second, and treating it as the first is how you get a support
  ticket that says "it deleted everything I typed".

Part 6 — Reporting, Suspense, and Proving It Works

  REPORTING GOES IN componentDidCatch, OR IN onError IF YOU USE THE
  LIBRARY. It runs in the commit phase, once per committed error, with
  a component stack you cannot get anywhere else.

    componentDidCatch(error, info) {
      Sentry.captureException(error, {
        contexts: { react: { componentStack: info.componentStack } },
        tags: {
          boundary: this.props.name,     // WHICH boundary caught it
          route:    location.pathname,
        },
        extra: {
          props: this.props.reportProps, // scrubbed, see below
          release: __BUILD_SHA__,
        },
      });
    }

  WHAT TO ATTACH, IN ORDER OF HOW OFTEN IT SOLVES THE TICKET:

    1. THE COMPONENT STACK. A JS stack in a minified bundle names
       minified functions. info.componentStack names your components:
       "in PriceTotal (at Checkout.jsx:42)". Most useful field, and it
       exists only here.

    2. WHICH BOUNDARY CAUGHT IT. "The route boundary caught it" and
       "the root boundary caught it" are different incidents — the
       second means every other boundary was bypassed. Name them.

    3. THE RELEASE / BUILD SHA, with source maps uploaded for that
       release. Without it every stack reads "a is not a function".

    4. THE ROUTE AND A BREADCRUMB TRAIL of what the user did.

    5. RELEVANT PROPS — DELIBERATELY, NOT WHOLESALE. Spreading props
       into a report is how tokens, emails and card details reach a
       third-party system. Pick fields, or scrub in beforeSend.

  IN REACT 19 THERE IS A BETTER FRONT DOOR for the errors no boundary
  sees. createRoot accepts onUncaughtError and onCaughtError, so you
  can report every render error centrally instead of relying on each
  boundary to log:

    createRoot(el, {
      onCaughtError:   (e, info) => report(e, info, 'caught'),
      onUncaughtError: (e, info) => report(e, info, 'uncaught'),
      onRecoverableError: (e) => report(e, null, 'hydration'),
    });

  onRecoverableError is the hydration-mismatch channel: React
  recovered by re-rendering on the client, the user saw nothing, and
  you would otherwise never know your SSR and client output disagree.

  YOU STILL NEED THE GLOBAL HANDLERS, because of Part 1:

    window.addEventListener('error', …);
    window.addEventListener('unhandledrejection', …);

  Reporting SDKs install both for you. If you are rolling your own,
  forgetting unhandledrejection means every async failure in your app
  is invisible.

  BOUNDARIES AND SUSPENSE ARE SIBLINGS, NOT ALTERNATIVES.

  Both work by a child throwing something during render and an
  ancestor catching it. Suspense catches a thrown PROMISE and shows a
  fallback until it resolves. An error boundary catches a thrown ERROR
  and shows a fallback permanently.

    throw promise  →  nearest <Suspense>      →  fallback, then retry
    throw error    →  nearest ErrorBoundary   →  fallback, stays

  So a lazy route needs BOTH, and the order matters:

    <ErrorBoundary fallback={<ChunkFailed />}>
      <Suspense fallback={<Skeleton />}>
        <LazyRoute />
      </Suspense>
    </ErrorBoundary>

  ERROR BOUNDARY OUTSIDE. If it were inside the Suspense boundary and
  the lazy import itself failed, the error would be thrown by the
  element Suspense is trying to render, and the boundary would never
  mount to catch it. Outside, it catches both the chunk failure and
  anything the loaded component throws afterwards.

  A CONSEQUENCE WORTH KNOWING: a component that suspends and then
  errors shows the Suspense fallback first and the error fallback
  second. Users see a skeleton flash before the error, which reads as
  slow rather than broken. If that matters, keep skeletons short.

  TESTING THAT A BOUNDARY WORKS. Untested boundaries are common and
  they fail in the worst possible way — silently, in production,
  during an incident.

  You need one throwing component and one console spy:

    function Bomb({ boom }) {
      if (boom) throw new Error('kaboom');
      return <span>fine</span>;
    }

    const spy = vi.spyOn(console, 'error')
                  .mockImplementation(() => {});

  THE console.error SPY IS NOT OPTIONAL. React logs every caught error
  to the console even when a boundary handles it, so without the mock
  your test output is unreadable and any "fail on console.error" rule
  in your setup turns a passing test red.

  TEST THE THREE THINGS THAT ACTUALLY BREAK:

    1. the fallback renders, and it is announced (role="alert")
    2. onError fired with the error — reporting is wired up
    3. RESET ACTUALLY RECOVERS — rerender with boom={false} and a
       changed resetKey, and assert the real content is back. This is
       the assertion that catches the Part 5 bug, and it is the one
       people omit.

Interview Questions

Beginner: What does an error boundary catch, and what does it not?

It catches errors thrown during rendering, in lifecycle methods, and in the constructors of any component below it in the tree. A failed React.lazy chunk counts, because that throw also happens during render.

It does not catch errors in event handlers, in setTimeout or requestAnimationFrame callbacks, in anything after an await, in promise rejections, during server-side rendering, or in the boundary's own render.

The dividing line is simple: is React still on the call stack? React calls your component function, so a throw there propagates up through React's frames and React can unwind to a boundary. An onClick is called by the browser's event loop long after render returned — there is nothing for React to unwind.

The practical consequence is that most production errors are in the uncaught category. Render errors are usually a property read on undefined and you find them in development. Handler and async errors are failed requests and bad responses, and those only appear against a real backend — which is why adding a boundary rarely changes your error dashboard.

Beginner: Why does React unmount the whole tree when nothing catches an error?

Because a corrupted UI is more dangerous than no UI. When a render throws part-way, some children have committed and some have not, and the DOM reflects a partial render that nobody — not React, not you — can describe.

Before React 16 the broken tree was left in place and the app limped on. The team changed it after seeing that limping produced worse bugs than crashing: a banking screen showing the previous account's balance, a checkout showing a total the tax component failed to update.

A blank page is a loud failure. The user knows something is wrong, reloads, and tells you. A plausible wrong number is a silent failure, and the user acts on it.

So the default is not fragility — it is React refusing to guess. The blank page is a demand that you state what should happen instead, and a boundary is that statement.

Mid: Why is an error boundary still a class in React 19, and how does react-error-boundary change your code?

There is no hook equivalent for getDerivedStateFromError or componentDidCatch. A hook runs during the render of the component that owns it; to catch a child's throw you must be outside that render. React finds boundaries by walking up the fiber tree looking for a fiber whose type declares one of those two methods — a class-only marker. There is no equivalent a function component could carry.

The two methods do different jobs and the split matters:

getDerivedStateFromErrorcomponentDidCatch
PhaseRender — must be pureCommit — side effects fine
May run twice per errorYes, under concurrent renderingNo
JobFlip state to show the fallbackReport the error

react-error-boundary is about 1.5KB and you use it because of four things you would otherwise get wrong: resetKeys for correct recovery, onReset to clear the state that caused the failure, loop protection on repeated resets, and useErrorBoundary.

That last one is the reason to take the dependency. showBoundary(e) stores the error in state and re-throws it during the next render, which is the only sanctioned way to convert an uncatchable async or handler error into a catchable render error. You can write it in six lines yourself; the value is that everyone reaches for the same six.

Mid: A user clicks "Try again" on your fallback and the error comes straight back. Why?

Because resetting the boundary clears its error state and re-renders the same children with exactly the same props that made them throw. Nothing about the input changed, so the render throws again immediately.

A reset is only meaningful if something changed. There are three ways to make that true: the input changed by itself (the user picked a different id — express this with resetKeys), you cleared the state that caused it (onReset resetting the bad cache entry, which runs before the children re-render), or the failure was genuinely transient — a chunk that failed on a dropped connection.

The looping case is worse than the annoying one. If the throw is synchronous and something auto-resets, you get a render/throw cycle that pins a CPU core. react-error-boundary guards this by refusing to reset repeatedly from the same error without a key change.

And some errors cannot be retried at all. A bug in your render code will throw on every attempt for as long as that build is deployed. The honest fallback there offers navigation away and a support reference, not a button that pretends to help.

Senior: How would you decide where boundaries go in a checkout flow?

Not by a rule about component depth. By asking, of every region: if this cannot render, is the page still worth showing? That is a product question, and the answer differs per region on the same screen.

My baseline is three layers. One root boundary whose only job is to not be a white page — branded, with a reload and a support reference. One route boundary inside the layout, so a failed page leaves the shell and navigation alive and the user can go somewhere else; this is the highest-value single boundary in most apps and the one teams most often skip. Then widget boundaries around independently failable content.

In checkout specifically, the recommendations rail, the promo-code widget and any third-party embed get boundaries — I did not write the third-party code and its release cadence is not mine. The order summary and the total do not. A boundary that hides a broken price converts a visible crash into a silently incomplete checkout that the user consents to, which is a commercial and possibly legal problem rather than a UX one. Same for a required consent checkbox.

My working rule: put a boundary where you would accept the fallback as a permanent design. If "we couldn't load recommendations" is a screen you would ship, boundary it. If "checkout with no total" is not, let the page fail and let the route boundary catch it.

The cost is real, and it is the reason not to go further. Every boundary is a fallback state someone designs and someone reviews. Teams that add them reflexively end up with "Something went wrong" in twenty places, which is a white page with extra steps. My recommendation is root plus route everywhere, and widget boundaries only where a specific fallback has been designed — then add more as incidents tell you where.

Senior: Design the error-reporting pipeline for a React app. What goes where?

The first thing to accept is that boundaries cover a minority of real errors, so a pipeline built only on componentDidCatch will look healthy while the app is failing. There are three channels and you need all of them.

ChannelCoversAttach
componentDidCatch / onErrorRender, lifecycle, constructorsComponent stack, boundary name, route
createRoot onCaughtError / onUncaughtError (React 19)Every render error, centrallySame, without per-boundary wiring
window.onerror + unhandledrejectionHandlers, timers, async — the majorityBreadcrumbs, route, release

What to attach, in order of how often it closes a ticket: the component stack, which exists only in componentDidCatch's second argument and names your components rather than minified functions; which boundary caught it, because "the root boundary caught it" means every other boundary was bypassed and is a different incident; the release SHA with source maps uploaded, without which every stack reads a is not a function; then route and breadcrumbs.

React 19's onRecoverableError is worth wiring separately. It reports hydration mismatches that React silently recovered from by re-rendering on the client. The user saw nothing, and you would otherwise never learn that your server and client output disagree — which is a correctness bug waiting to become a visible one.

The failure mode I actively guard against is PII. Spreading props into the report is how tokens, emails and card fragments end up in a third-party system with a different retention policy and a different jurisdiction. Name the fields explicitly, and run a beforeSend scrubber as a second line of defence.

My recommendation: global handlers plus onUncaughtError from day one — they are twenty lines and they cover the majority — then per-boundary onError with names, and source maps in CI before anything else. A pipeline you cannot read is the same as no pipeline.

🏋️ Graded Exercises

1 (easy): A developer reports that this boundary "doesn't work". What is happening? 
class Boundary extends React.Component {
  state = { error: null };
  static getDerivedStateFromError(e) { return { error: e }; }
  render() {
    if (this.state.error) return <p>Failed</p>;
    return this.props.children;
  }
}

<Boundary>
  <button onClick={() => { throw new Error('boom'); }}>Go</button>
</Boundary>
Solution

The boundary is correct; the error is simply not one it can see. The throw happens in an onClick, which the browser calls from the event loop after render has long finished. React is not on the stack, so there is nothing to unwind and no fiber to blame.

At runtime the error reaches window.onerror, the app stays mounted, and the button silently does nothing. To the user that reads as an unresponsive button, and they click again.

function Go() {
  const { showBoundary } = useErrorBoundary();
  return <button onClick={() => {
    try { doTheThing(); }
    catch (e) { showBoundary(e); }   // becomes a RENDER error
  }}>Go</button>;
}

showBoundary works by storing the error in state and re-throwing it during the next render — converting an uncatchable error into a catchable one. But ask whether you want that: if this button submitted a form, escalating destroys every field the user typed. Local error state next to the button is usually the better product decision.

2 (easy): The fallback appears, the user clicks Retry, and the fallback returns instantly. Fix it.

    <button onClick={resetErrorBoundary}>Retry</button>

>
  <UserProfile userId={userId} />
</ErrorBoundary>
Solution

Resetting clears the boundary's error state and re-renders the same children with the same props. UserProfile receives the identical userId that made it throw, does the identical work, and throws again in the same tick.

<ErrorBoundary
  resetKeys={[userId]}
  onReset={() => qc.resetQueries({ queryKey: ['user', userId] })}
  FallbackComponent={Fallback}
>
  <UserProfile userId={userId} />
</ErrorBoundary>

3 (medium): After a deploy, users with old tabs open see a white screen. Explain and build the fix. 
const Settings = React.lazy(() => import('./Settings'));

<Suspense fallback={<Skeleton />}>
  <Settings />
</Suspense>
Solution

Content-hashed chunk filenames. The old tab's bundle asks for Settings.a91f3c.js; the deploy replaced it with Settings.7d20b1.js and removed the old file. The import rejects, lazy re-throws that during render, and with no boundary above it React unmounts the entire tree.

Note this is a boundary-catchable error — the throw happens in render — which is exactly why the missing boundary is the bug.

function onChunkError() {
  if (sessionStorage.getItem('chunk-reloaded')) return;  // no loops
  sessionStorage.setItem('chunk-reloaded', '1');
  window.location.reload();
}

<ErrorBoundary
  onError={(e) => { if (isChunkError(e)) onChunkError(); }}
  FallbackComponent={ChunkFailed}
>
  <Suspense fallback={<Skeleton />}>
    <Settings />
  </Suspense>
</ErrorBoundary>
NestingResult
Boundary outside SuspenseCorrect — catches the chunk failure and anything the loaded component throws
Boundary inside SuspenseThe failed element is what Suspense was rendering; the boundary never mounts to catch it

The sessionStorage guard is the part people omit, and omitting it is worse than the original bug: if the reload also fails — a CDN purge, an offline user — you have built an infinite refresh loop the user cannot escape without closing the tab.

The structural fix is deployment-side: keep the previous build's chunks for a rollover window (a release or two, or 24 hours) so old tabs keep working. The boundary is then a safety net for the tab someone left open over a long weekend, not your primary strategy.

4 (medium): Review this placement in a checkout page. What is wrong? 
<Checkout>

    <OrderTotal items={items} tax={tax} />

The boundaries are on exactly the wrong components, in both directions.

If OrderTotal throws — a null tax rate, a currency the formatter does not know — the boundary renders null and checkout displays with no total at all. The user submits an order without seeing what they will be charged. A visible crash has been converted into a silent commercial defect, which is strictly worse.

ConsentCheckbox is the same failure with a legal edge: the boundary silently removes a required disclosure, and the flow proceeds without consent that the audit log will claim was given.

Meanwhile RecommendedItems — the one component nobody needs — is unprotected, so its failure takes down checkout.

<Checkout>

5 (hard): This boundary catches everything correctly and Sentry shows three reports per incident, all with unreadable stacks. Diagnose. 
class Boundary extends React.Component {
  static getDerivedStateFromError(error) {
    Sentry.captureException(error, { extra: { ...this.props } });
    return { error };
  }
  render() {
    if (this.state?.error) return <Fallback data={this.props.data} />;
    return this.props.children;
  }
}
Solution

Four defects, and they compound.

1 — reporting from a render-phase method. getDerivedStateFromError runs during render, and under concurrent rendering React may run it, discard the work and run it again. Every extra attempt is another captureException, which is the three-reports-per-incident symptom. Reporting belongs in componentDidCatch, which runs once per commit.

2 — this in a static method is not the instance. { ...this.props } spreads the constructor's own properties, so the report carries junk. The method is static precisely so you cannot do impure instance work in it.

3 — unreadable stacks. No info.componentStack (only componentDidCatch receives it) and no release tag, so a minified bundle yields a is not a function at bundle.js:1.

4 — the fallback reads this.props.data. If data is what was malformed, the fallback throws too. A boundary cannot catch its own fallback, so it escalates to the next boundary up — usually the root — and the user gets a white page from your error screen.

class Boundary extends React.Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };                 // PURE. That is all it does.
  }

  componentDidCatch(error, info) {    // commit phase, once
    Sentry.captureException(error, {
      contexts: { react: { componentStack: info.componentStack } },
      tags:  { boundary: this.props.name, route: location.pathname },
      extra: { release: __BUILD_SHA__, itemCount: this.props.count },
    });
  }

  render() {
    if (this.state.error) return <StaticFallback />;   // no props
    return this.props.children;
  }
}
DefectSymptomFix
Log in getDerivedStateFromErrorDuplicate reportsLog in componentDidCatch
this.props in a staticGarbage contextRead props on the instance
No component stack / releaseMinified, unreadableAttach both; upload source maps
Fallback depends on propsEscalates to the rootDependency-free fallback

The { ...this.props } spread is also a PII leak waiting to happen. Even from the instance, spreading props sends tokens, emails and card fragments to a third-party system with a different retention policy. Name fields explicitly and keep a beforeSend scrubber as a second line of defence.

Rule for fallbacks: they render from nothing. Static text, an icon, a reload button, a support reference. The moment a fallback touches data, formatting or context, it can fail for the same reason its children did.

6 (hard): Design and write the test suite for a route-level boundary that must survive a failing widget, report the failure, and recover on navigation.
Solution

Three assertions, and the third is the one teams omit. A boundary that catches but cannot recover is a boundary that works exactly once, and you discover that during an incident.

function Bomb({ boom }) {
  if (boom) throw new Error('kaboom');
  return <span>widget content</span>;
}

let spy;
beforeEach(() => {
  spy = vi.spyOn(console, 'error').mockImplementation(() => {});
});
afterEach(() => spy.mockRestore());

test('fallback renders, is announced, and reports', () => {
  const onError = vi.fn();
  render(
    <>
      <OrderTotal amount={42} />                 {/* sibling */}
      <ErrorBoundary FallbackComponent={Fallback} onError={onError}>
        <Bomb boom />
      </ErrorBoundary>
    </>
  );
  expect(screen.getByRole('alert')).toHaveTextContent(/couldn.t load/i);
  expect(onError).toHaveBeenCalledOnce();
  expect(screen.getByText('$42.00')).toBeInTheDocument();  // survived
});

test('recovers when the resetKey changes', async () => {
  const { rerender } = render(
    <ErrorBoundary resetKeys={['/a']} FallbackComponent={Fallback}>
      <Bomb boom />
    </ErrorBoundary>
  );
  expect(screen.getByRole('alert')).toBeInTheDocument();

  rerender(                                   // navigation: key CHANGES
    <ErrorBoundary resetKeys={['/b']} FallbackComponent={Fallback}>
      <Bomb boom={false} />
    </ErrorBoundary>
  );
  expect(screen.getByText('widget content')).toBeInTheDocument();
});
TestCatches the failure where…
Fallback renders with role="alert"The boundary is misplaced, or the fallback is silent to screen readers
onError called onceReporting is unwired, or logging sits in the render-phase method and fires twice
Sibling still rendersThe boundary is too high and takes the page with it
Recovers on a changed resetKeyReset does not actually recover — the Part 5 bug

The console.error spy is mandatory, not hygiene. React logs every caught error to the console even when a boundary handles it. Without the mock your output is unreadable, and any "fail the suite on console.error" rule in your setup turns a correct test red.

Why getByRole('alert') rather than getByText: it asserts the error is announced. A visually-obvious fallback that a screen reader never mentions leaves those users staring at a region that silently stopped updating.

What not to test: that getDerivedStateFromError was called, or the shape of the boundary's internal state. Those are React's contract, not yours, and asserting on them buys tests that break when you swap your hand-rolled class for react-error-boundary while the behaviour is unchanged.

🎯 Key Takeaways

  • A boundary catches render, lifecycle and constructor errors below it — and nothing else.
  • Event handlers, timers, promise rejections and everything after an await are not caught, because React is no longer on the call stack.
  • A synchronous useEffect body is caught; its async continuation is not — the line is the first await.
  • Most production errors are in the uncaught category, which is why adding a boundary rarely changes your error dashboard.
  • Boundaries are client-only — SSR errors must be handled by the server framework.
  • An unhandled render error unmounts the whole tree, deliberately — a corrupted UI is more dangerous than a blank one.
  • Boundaries are still classes in React 19; a hook runs inside the render it would need to be outside of.
  • getDerivedStateFromError is pure and may run twice; log in componentDidCatch, which runs once per commit.
  • info.componentStack exists only in componentDidCatch and is the field that most often closes the ticket.
  • Granularity is a product decision — root for last resort, route so navigation survives, widget for optional content.
  • Never boundary a price, total or consent control — hiding it turns a visible crash into a silent commercial or compliance defect.
  • Resetting without changing the input re-throws immediately; recovery needs resetKeys or an onReset that clears the bad state.
  • Escalating a failed form submit to a boundary destroys everything the user typed — handle mutation failures locally.
  • Error boundary outside, Suspense inside, or a failed lazy chunk throws before the boundary mounts.
  • A fallback must render from nothing — if it touches data it can fail the same way its children did, and escalate to the root.
  • Test that reset actually recovers, with a console.error spy and a changed key — a boundary that catches but cannot recover works exactly once.
