Forms: Controlled & Uncontrolled Foundations

What you'll master: the only question that decides a form's architecture — who owns the value, React or the DOM — and why "controlled everything" is dogma rather than engineering; the exact cause of "a component is changing an uncontrolled input to be controlled", which is one undefined and destroys what the user typed; why parsing a number input on every keystroke makes "1." and "-" impossible to type; validation as a timing problem rather than a regex problem — reward early, punish late — and why the error must be derived while only touched is state; why a failed submit that clears the form is the bug users actually rage about; the caret jumping to the end when you reformat while typing, and what production code does about it; and the hybrid architecture for a 40-field page where only three fields need to be live. Prerequisites: State, Events and the HTML Forms section — native validation attributes still do real work.

Part 1 — Two Sources of Truth; Pick One Per Field

A DOM input holds its own value natively — type into it and it changes, with no JavaScript involved. React state is a second place that value can live. The whole controlled/uncontrolled question is: who owns it?

// UNCONTROLLED — the DOM owns it; React reads it when it needs to
<input defaultValue="Ada" ref={nameRef} />      // defaultValue = initial only
// later: nameRef.current.value

// CONTROLLED — React state owns it; the DOM mirrors state
const [name, setName] = useState("Ada");
<input value={name} onChange={e => setName(e.target.value)} />
//      ^ every render forces the input to equal state
//                  ^ every keystroke updates state -> re-render -> input shows it
  WHY THE CONTROLLED LOOP IS NOT REDUNDANT

  It looks circular — state renders the input, the input updates state —
  and that circularity IS the guarantee: the input can never disagree
  with state, because the input has no independent value.

  What that buys, concretely:
    - anything can READ the value at any time, from anywhere in the tree
    - anything can TRANSFORM it: uppercase, strip spaces, mask a card
    - anything can REJECT a keystroke: refuse non-digits outright
    - anything can OVERWRITE it: "use my billing address" fills six fields

  What it costs:
    - one render per keystroke (usually irrelevant — measure before
      assuming otherwise)
    - state plus a handler per field, which is real ceremony at 40 fields

🔑 The deciding question is per field, not per codebase: does anything need to react to this value while it is being typed? If yes, controlled. If you only need the value at submit, uncontrolled is less code and fewer renders. A login form gains nothing from two setters and two handlers. It is worth knowing that React Hook Form — the library most teams reach for — is essentially industrial-grade uncontrolled: inputs registered by ref, with a subscription model so only the fields whose validation state changed re-render.

Part 2 — The Controlled API for Every Control

// TEXT, TEXTAREA, NUMBER — value + onChange
<textarea value={bio} onChange={e => setBio(e.target.value)} />

// CHECKBOX — `checked`, not `value`
<input type="checkbox" checked={agreed}
       onChange={e => setAgreed(e.target.checked)} />

// RADIO GROUP — one piece of state; `checked` computed per option

  <label key={size}>
    <input type="radio" name="size" value={size}
           checked={choice === size}
           onChange={e => setChoice(e.target.value)} />
    {size.toUpperCase()}
  </label>
))}

// SELECT — value goes on the <select>, NOT `selected` on an option
<select value={country} onChange={e => setCountry(e.target.value)}>
  <option value="">Choose…</option>
  <option value="in">India</option>
</select>

// MULTI-CHECKBOX — a Set beats parallel booleans
const [toppings, setToppings] = useState(new Set());
const toggle = t => setToppings(s => {
  const next = new Set(s);          // COPY — Sets mutate in place, and a
  next.has(t) ? next.delete(t)      // mutated Set is the same reference,
              : next.add(t);        // so React would bail out
  return next;
});

// FILE — always uncontrolled. `value` is read-only for security: a page
// cannot programmatically choose a file from your disk.
<input type="file" onChange={e => setFile(e.target.files[0])} />
  THE NUMBER INPUT TRAP

    <input type="number" value={qty}
           onChange={e => setQty(Number(e.target.value))} />   // ❌

  e.target.value is ALWAYS a string, and during typing it passes through
  states that are not yet numbers:

    ""      the user cleared it        -> Number("")  === 0
    "1."    mid-decimal                -> Number("1.") === 1, so the "." is
                                          erased as they type it
    "-"     starting a negative        -> Number("-")  === NaN
    "1e"    starting exponent notation -> NaN

  Every one of those is a keystroke the user cannot complete, because the
  parse round-trips through state and overwrites what they typed.

    ✅ KEEP THE STRING IN STATE. Parse once, at the boundary:
       await api.save({ ...form, qty: Number(form.qty) });

  The same rule covers currency, phone numbers and dates: store what the
  user typed, convert where the value leaves the UI.

Part 3 — Uncontrolled Done Right: FormData

function SignupForm({ onSubmit }) {
  function handleSubmit(e) {
    e.preventDefault();
    const data = Object.fromEntries(new FormData(e.currentTarget));
    // { email: "…", plan: "pro", newsletter: "on" } — keyed by `name`
    onSubmit(data);
  }

  return (
    <form onSubmit={handleSubmit}>
      <label>Email <input name="email" type="email" required /></label>
      <label>Plan
        <select name="plan" defaultValue="free">
          <option value="free">Free</option>
          <option value="pro">Pro</option>
        </select>
      </label>
      <label><input name="newsletter" type="checkbox" /> Newsletter</label>
      <button>Sign up</button>
    </form>
  );
}

  Zero state, zero onChange, and native `required` and `type="email"`
  validation still gate the submit.

  TWO SHARP EDGES OF Object.fromEntries:
    - an UNCHECKED checkbox is absent entirely, not false. So
      `data.newsletter` is undefined, and `"on"` when checked.
    - MULTIPLE fields with the same name collapse to the last one.
      Use formData.getAll("tag") for genuine multi-value fields.

  This shape is also what React 19 form actions build on —
  <form action={fn}> hands your function the FormData directly.

Part 4 — Validation: When Matters More Than What

Checking an email against a regex is trivial. The engineering is in when errors appear. The consensus that has emerged is reward early, punish late: validate on blur, then re-validate live once the field has been touched, and reveal everything on submit.

function useField(validate) {
  const [value, setValue]     = useState("");
  const [touched, setTouched] = useState(false);

  const error = validate(value);        // DERIVED every render — never stored

  return {
    error: touched ? error : null,      // exists always; SHOWN only after blur
    inputProps: {
      value,
      onChange: e => setValue(e.target.value),
      onBlur:   () => setTouched(true),
    },
    forceTouch: () => setTouched(true),
    isValid: !error,
  };
}

  WHY error IS DERIVED AND touched IS STATE:

    error   is a pure function of the value. Storing it in state means two
            sources of truth that drift — the classic bug being an error
            still displayed after the user fixed the field, because one
            code path forgot to clear it.

    touched is a record of something that HAPPENED — the user left the
            field. Nothing can compute that from the current value, so it
            is genuinely state.

  That distinction is the whole validation architecture. Get it right and
  the rest is a regex.

⚠️ Layer custom validation on top of native attributes; do not replace them. required, type="email", minLength and pattern work before your JavaScript has loaded, are announced correctly by assistive technology, and cost nothing. Custom validation adds better messages and cross-field rules. And regardless of either, the server revalidates everything — client validation is UX, not security, since anyone can post whatever they like with curl (see Security).

Part 5 — A Production Checkout Form

function CheckoutForm({ onComplete }) {
  const [form, setForm]       = useState({ name: "", email: "", qty: "1", agree: false });
  const [touched, setTouched] = useState({});
  const [status, setStatus]   = useState("idle");   // idle | submitting | error

  const set = e => {
    const { name, type, value, checked } = e.target;
    setForm(f => ({ ...f, [name]: type === "checkbox" ? checked : value }));
  };
  const blur = e => setTouched(t => ({ ...t, [e.target.name]: true }));

  // ALL validation derived, in one place, trivially unit-testable
  const errors = {
    name:  form.name.trim() ? null : "Name is required",
    email: /^\S+@\S+\.\S+$/.test(form.email) ? null : "Valid email required",
    qty:   Number.isInteger(+form.qty) && +form.qty >= 1
             ? null : "Quantity must be a whole number of at least 1",
    agree: form.agree ? null : "You must accept the terms",
  };
  const isValid = Object.values(errors).every(e => e === null);
  const show = k => (touched[k] ? errors[k] : null);   // visibility policy, one place

  async function submit(e) {
    e.preventDefault();
    setTouched({ name: true, email: true, qty: true, agree: true });
    if (!isValid) return;
    setStatus("submitting");
    try {
      await api.checkout({ ...form, qty: +form.qty });   // parse HERE, once
      onComplete();
    } catch {
      setStatus("error");            // keep every keystroke the user made
    }
  }

  return (
    <form onSubmit={submit} noValidate>
      <Field label="Name"  name="name"  value={form.name}  error={show("name")}
             onChange={set} onBlur={blur} />
      <Field label="Email" name="email" value={form.email} error={show("email")}
             onChange={set} onBlur={blur} type="email" />
      <Field label="Qty"   name="qty"   value={form.qty}   error={show("qty")}
             onChange={set} onBlur={blur} inputMode="numeric" />

      <label>
        <input type="checkbox" name="agree" checked={form.agree}
               onChange={set} onBlur={blur} />
        I accept the terms
      </label>
      {show("agree") && <p role="alert">{errors.agree}</p>}

      {status === "error" && <p role="alert">Payment failed — please try again.</p>}
      <button disabled={status === "submitting"}>
        {status === "submitting" ? "Processing…" : "Pay now"}
      </button>
    </form>
  );
}

Interview Questions

Beginner: Controlled versus uncontrolled — define both, and name the deciding question.

Controlled: React state is the source of truth. The input renders value from state and reports every change through onChange, so the DOM never holds a value React does not know about.

Uncontrolled: the DOM keeps the value. React sets at most a defaultValue and reads the result later through a ref or FormData.

The deciding question is whether anything needs to react to the value while it is being typed — a character counter, a live preview, a disabled submit button, input filtering. If yes, controlled. If the value is only needed at submit, uncontrolled is less code and does not re-render on keystrokes.

It is worth saying the choice is per field rather than per application. "Controlled everything" is a convention, not a requirement, and a login form gains nothing from it.

Beginner: Why defaultValue rather than value for an uncontrolled input?

Because value is an instruction React enforces on every render. Without an onChange to update state, each render sets the input back to the same value, so the field appears frozen — you type and nothing happens. React warns about exactly this.

defaultValue sets the initial DOM value once and then leaves ownership with the DOM, which is the entire uncontrolled contract.

The equivalents for other controls are worth knowing: defaultChecked for checkboxes and radios, and for a <select>, defaultValue on the select itself rather than selected on an option — React differs from plain HTML there.

Mid: What causes "a component is changing an uncontrolled input to be controlled"?

The value prop went from undefined to a string. React decides which mode an input is in by whether value is defined on the first render, so undefined means uncontrolled and a later string means it has switched.

The usual sources are useState() with no argument, useState(null), or reading from data that has not arrived — value={user?.name} while the fetch is in flight.

The warning matters because of what happens alongside it: anything the user typed into that field before the data landed is overwritten the moment React takes control. On a slow connection that is a real and confusing data-loss bug, not just console noise.

The minimal fix is value={user?.name ?? ""}. The better fixes express the intent: do not render the form until the data is there, or render it with key={user.id} so it mounts fresh with the loaded values — which also solves the related problem of switching records.

Mid: Design the error-display policy for a good form.

The principle is reward early, punish late. Errors should appear when they are useful and not while the user is mid-thought.

Concretely: track touched per field. Before the first blur, show nothing — "invalid email" after one character is the most common form UX failure. On blur, validate and show, because the user has signalled they are done with that field. Once touched, re-validate on every change so the error clears the instant they fix it. On submit, mark everything touched, reveal all errors, and move focus to the first invalid field.

The architectural half is that the error is derived and only touched is state. An error is a pure function of the value, so storing it creates a second source of truth that drifts — the familiar bug where a corrected field keeps its red message. Touched-ness is a record of something that happened and cannot be computed, so it is genuine state.

The accessibility requirements are not optional here: aria-invalid on the input, the message linked with aria-describedby, and role="alert" so it is announced. Focus moving to the first invalid field on submit is what stops a screen-reader user hunting for what went wrong.

Senior: A 60-field enterprise form is janky on every keystroke. Diagnose and fix it without a library, then say what a library would do.

The cause is almost always a single state object at the top of the form. Every keystroke replaces it, so the form component re-renders, and with it all sixty fields plus whatever else lives in that subtree. The work per keystroke scales with the size of the form rather than with the field being typed into.

The first thing I would check is the profiler, because there is a second common cause with the same symptom: an expensive derivation — a validation pass over every field, a big useMemo recomputing, a chart re-rendering — that is fine once and terrible sixty times a second.

Three fixes, in the order I would try them.

Go uncontrolled. If most of those fields need no live behaviour, name attributes plus one FormData read at submit gives zero renders while typing. It usually deletes more code than it adds.

Isolate state per field. If they must be controlled, move the state into each field component so a keystroke re-renders one field rather than sixty. The parent only learns about values at submit, or through a callback that does not re-render it.

Shrink the blast radius. If the parent genuinely must hold the state, memoize the field rows and pass stable, primitive props so only the edited field re-renders — which requires stable handlers, or it achieves nothing.

React Hook Form does the first and second together: inputs are registered by ref so they are uncontrolled and typing causes no React work at all, and a subscription model re-renders only the components whose validation state actually changed. That is the architecture I would land on for a form this size rather than hand-rolling the third option.

Senior: How do controlled inputs interact with reformatting while typing — credit-card spacing, for example?

Reformatting in onChange — setValue(format(raw)) — works for the value and breaks the caret. React re-renders the input with the formatted string, and because the DOM value was replaced wholesale, the browser puts the caret at the end. For appending that is invisible; for editing the middle of a number it makes the field unusable — every keystroke throws the user to the end.

The production answer is to compute where the caret should be after formatting and restore it with setSelectionRange in a layout effect, so it happens before paint and the user never sees the jump. The caret maths is genuinely fiddly, because inserted separator characters shift the offset and deletion has to handle the case where the character being deleted is a separator — which is why masking libraries exist and why I would use one rather than hand-roll it.

The alternative worth considering is to format on blur instead of on change. The user types freely, the value is normalised when they leave the field, and there is no caret problem at all. For most fields — phone numbers, currency, dates — that is the better trade, and it is a UX decision rather than a technical limitation.

Two related traps. Never reject keystrokes by refusing to update state, because fast typists and IME users will lose characters — filter the value, do not block the input. And keep the raw and formatted values separate if the API wants the raw one, rather than stripping the format again at submit and hoping the regex is symmetrical.

🏋️ Graded Exercises

1 (easy): A controlled textarea with a live character counter that styles differently past 100 characters.
Solution 
function Tweet() {
  const [text, setText] = useState("");
  const left = 100 - text.length;        // derived, not state
  const over = left < 0;

  return (
    <>
      <label htmlFor="tweet">Message</label>
      <textarea id="tweet" value={text}
                onChange={e => setText(e.target.value)}
                aria-describedby="tweet-count" />
      <small id="tweet-count" aria-live="polite"
             style={{ color: over ? "crimson" : "inherit" }}>
        {left} left
      </small>
    </>
  );
}

This is the textbook case for controlled: something outside the input reacts to the value on every keystroke, which is precisely what uncontrolled cannot do without poking at refs.

left is derived. Storing a charsLeft state beside the text would be the redundant-state bug — two values to keep in step, and one path that forgets.

Deliberately no maxLength: hard-truncating at 100 silently swallows the end of a paste, and the user cannot see what was lost. Letting them go over and showing a negative count — with submit disabled — is the friendlier design, and it is what Twitter itself settled on.

aria-live="polite" with a caveat: announcing on every keystroke is intolerable with a screen reader. A production version announces only at thresholds — say, at 20 remaining and when going over — by rendering the live region's text conditionally.

2 (easy): Convert a login form (email, password) to uncontrolled with FormData.
Solution 
function Login({ onLogin }) {
  function onSubmit(e) {
    e.preventDefault();
    const { email, password } = Object.fromEntries(new FormData(e.currentTarget));
    onLogin(email, password);
  }

  return (
    <form onSubmit={onSubmit}>
      <label>Email
        <input name="email" type="email" required autoComplete="username" />
      </label>
      <label>Password
        <input name="password" type="password" required
               autoComplete="current-password" />
      </label>
      <button>Log in</button>
    </form>
  );
}

3 (medium): A controlled radio group (standard / express / overnight) where choosing overnight reveals a required phone field.
Solution 
function Shipping() {
  const [method, setMethod] = useState("standard");
  const [phone, setPhone]   = useState("");

  return (
    <fieldset>
      <legend>Shipping</legend>

      {["standard", "express", "overnight"].map(m => (

      )}

  );
}

The conditional field is exactly why this group must be controlled: the UI reacts to the value as it changes. An uncontrolled radio group cannot reveal a field without reading the DOM.

5 (medium): Implement blur-then-live validation for a username field — required, at least 3 characters, lowercase only — with no library.
Solution 
function Username() {
  const [value, setValue]     = useState("");
  const [touched, setTouched] = useState(false);

  const error =
    !value                        ? "Required"
    : value.length < 3            ? "At least 3 characters"
    : value !== value.toLowerCase() ? "Lowercase only"
    : null;

  const visible = touched ? error : null;

  return (
    <>
      <label htmlFor="username">Username</label>
      <input id="username" value={value}
             onChange={e => setValue(e.target.value)}
             onBlur={() => setTouched(true)}
             aria-invalid={!!visible}
             aria-describedby={visible ? "username-err" : undefined} />
      {visible && <p id="username-err" role="alert">{visible}</p>}
    </>
  );
}
DecisionWhy
error derived, touched stateThe error is a function of the value; touched-ness is an event that happened. Storing the error is what makes stale messages possible
Ordered checks, most fundamental firstAn empty field should say "Required", not "At least 3 characters" — which would be true and unhelpful
aria-describedby conditionalPointing at an id that does not exist is a dangling reference some screen readers announce oddly
role="alert"Announces the message when it appears, without moving focus

What "lowercase only" should probably do instead: lowercase the input as they type rather than rejecting it. Telling a user their input is wrong when you could simply accept it is a worse experience — setValue(e.target.value.toLowerCase()), and the rule disappears. Reject only what you genuinely cannot interpret.

The scaling limitation: this is per-field state. For twenty fields it becomes twenty pairs of useState, which is where either the useField hook from Part 4 or a form library earns its place.

6 (hard): Build a confirm-password pair where the mismatch error appears on the confirm field only after it is touched, clears live, and submit is blocked until both are valid.
Solution 
function Passwords({ onValid }) {
  const [pw, setPw]   = useState("");
  const [pw2, setPw2] = useState("");
  const [touched2, setTouched2] = useState(false);

  const pwError   = pw.length >= 8 ? null : "At least 8 characters";
  const matchErr  = pw2 === pw ? null : "Passwords do not match";
  const showMatch = touched2 ? matchErr : null;
  const valid     = !pwError && !matchErr;

  function submit(e) {
    e.preventDefault();
    setTouched2(true);            // reveal on submit either way
    if (valid) onValid(pw);
  }

  return (
    <form onSubmit={submit}>
      <label>Password
        <input type="password" value={pw} autoComplete="new-password"
               onChange={e => setPw(e.target.value)} />
      </label>
      <label>Confirm
        <input type="password" value={pw2} autoComplete="new-password"
               onChange={e => setPw2(e.target.value)}
               onBlur={() => setTouched2(true)}
               aria-invalid={!!showMatch} />
      </label>
      {showMatch && <p role="alert">{showMatch}</p>}
      <button>Create account</button>
    </form>
  );
}

Cross-field validation is just derivation over more than one value — no extra machinery, no synchronising. Because matchErr recomputes from both fields on every render, correcting either field clears the error. An implementation that stored the mismatch in state when the confirm field blurred would leave the error on screen after the user fixed the first password.

DetailWhy
Only the confirm field tracks touchedThe mismatch is only meaningful once they have attempted the confirmation. Showing it while they type the second field for the first time is the "punish early" mistake
Submit reveals rather than blocking silentlyA disabled button with no explanation is the worst version of this form. The button stays enabled and the submit explains why nothing happened
autoComplete="new-password"Tells the password manager to offer generation rather than autofilling the existing password into both boxes

The design question underneath: confirm-password fields are increasingly considered an anti-pattern. They exist to catch typos in a masked field, and a "show password" toggle solves the same problem with less friction and better accessibility. If the requirement is negotiable, that is the change worth proposing.

7 (hard): A 40-field settings page needs live behaviour on exactly three fields — a slug preview, a password meter, a character counter. Design the architecture.
Solution 
  HYBRID: uncontrolled overall, with three controlled islands.

  1. THE FORM IS UNCONTROLLED.
     37 fields carry `name` attributes and nothing else. One onSubmit
     reads FormData. Zero state, zero renders while typing.

  2. THE THREE LIVE FIELDS ARE SELF-CONTAINED COMPONENTS that own their
     own state and render their own preview, meter or counter.

     function SlugField({ defaultValue }) {
       const [value, setValue] = useState(defaultValue ?? "");
       return (
         <>
           <input name="slug" value={value}
                  onChange={e => setValue(e.target.value)} />
           <small>example.com/{slugify(value)}</small>
         </>
       );
     }

     A keystroke re-renders THIS component and its few nodes. The other
     39 fields do not know it happened.

  3. STILL ONE <form>. The islands' inputs keep their `name`
     attributes, so FormData collects all 40 values uniformly at submit.
     The parent never needs to know which fields were controlled.

  4. VALIDATION: native attributes plus one submit-time pass over the
     FormData; the islands validate live with the touched pattern.
AlternativeWhy it loses
Fully controlled, one state objectEvery keystroke re-renders 40 fields. This is the version that gets reported as "the settings page is laggy"
Fully uncontrolledThe three live features become ref-poking and manual DOM updates — fighting the model to save state you actually need
A form library everywhereReasonable, and worth it if the page grows more live behaviour. For three fields it is a dependency and an API to learn for something the platform already does

The insight worth generalising: controlled versus uncontrolled is a per-field decision, and the component boundary is what lets those decisions coexist. An island owns its state, so the cost of being controlled is bounded by the island rather than paid by the page.

What I would verify before calling it done: that the islands' inputs really do appear in FormData. A controlled input still submits normally as long as it has a name and is inside the form — but if someone later moves an island into a portal for layout reasons, it leaves the form element and silently stops being submitted.

And the one thing I would not do: lift the three islands' values to the parent "for consistency". That reintroduces exactly the re-render problem the architecture exists to avoid, and it is the change a well-meaning reviewer asks for.

🎯 Key Takeaways

  • Controlled means React state owns the value; uncontrolled means the DOM does. Decide per field, on whether anything must react while typing.
  • The controlled loop's circularity is the guarantee — the input cannot hold a value React does not know about.
  • checked for checkboxes and radios, value on the <select>, and file inputs are always uncontrolled.
  • Keep number inputs as strings in state. Parsing per keystroke makes "1.", "-" and an empty field impossible to type.
  • FormData(e.currentTarget) reads a whole uncontrolled form in one line — and unchecked checkboxes are absent rather than false.
  • Never let value flip between undefined and a string — it switches the input's mode and overwrites what the user typed.
  • Errors are derived; only touched is state. Storing errors is what produces messages that outlive the problem.
  • Reward early, punish late: nothing before first blur, then live, and everything on submit with focus moved to the first invalid field.
  • Layer on native validation rather than replacing it — it works before your JS loads and is announced correctly.
  • Client validation is UX, never security. The server revalidates everything.
  • Never clear the form on a failed submit, and disable the button while submitting so a double-click cannot charge twice.
  • Reformatting while typing moves the caret to the end — restore the selection in a layout effect, or format on blur instead.
  • Filter values, never block keystrokes, or fast typists and IME users lose input.
  • The fix for a janky large form is architectural — go uncontrolled, or isolate state per field so a keystroke re-renders one field rather than sixty.
  • Forms are an accessibility hotspot: real labels, aria-invalid, errors linked by aria-describedby, and autoComplete tokens so password managers work.
