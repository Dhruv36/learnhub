JSX Deep Dive Foundations

What you'll master: everything JSX can express, and the handful of behaviours that produce real bugs — why props.children is undefined, a value, or an array depending on how many children you passed, so children.map crashes only when a caller passes exactly one; why onClick={fn()} can produce an infinite render loop and what it actually passes as the handler; how spread order silently decides whether a prop is a default or an override, which is the difference between a design-system component that can be themed and one that cannot; when the shorthand <> is a syntax error and <Fragment> is not; the three slot APIs — element-as-prop, component-as-prop and render prop — and the rule for picking the weakest one that works; and exactly where React's auto-escaping stops protecting you, including the URL props that still accept javascript:. Prerequisites: Components & JSX — you know JSX compiles to element objects; here we use that deliberately.

Part 1 — Children: the Prop With Special Syntax

Whatever sits between a tag's open and close becomes props.children. It can be text, elements, an array, an expression — any JavaScript value:

function Card({ title, children }) {         // children is just a prop
  return (
    <section className="card">
      <h3>{title}</h3>
      {children}                             {/* render whatever was nested */}
    </section>
  );
}

<Card title="Billing">
  <p>Next invoice: March 1.</p>           {/* this subtree is props.children */}
  <button>Update card</button>
</Card>

This is React's composition primitive — the equivalent of a slot. A component that renders children does not need to know what is inside it, which is what keeps cards, modals and layouts generic. The full pattern language is in Composition Patterns.

  THE SHAPE OF children IS NOT STABLE, AND THIS BITES

    <Card />                    children === undefined
    <Card>hi</Card>             children === "hi"              a string
    <Card><X /></Card>          children === {element}         NOT an array
    <Card><X /><Y /></Card>     children === [element, element] an array
    <Card>{list.map(…)}</Card>  children === [ … ]             an array

  So this component works in testing and crashes in production:

    function Tabs({ children }) {
      return children.map(child => <li>{child}</li>);   // ❌
    }

    <Tabs><Tab/><Tab/></Tabs>    works — array
    <Tabs><Tab/></Tabs>          TypeError: children.map is not a function

  THE FAILURE IS CONDITIONAL ON CALLER COUNT, which is why it survives
  review and every test that renders more than one child.

  TWO CORRECT ANSWERS:

    1. Do not iterate. Render {children} and let React handle any shape.
       Correct whenever you do not need to touch individual children.

    2. Normalise, when you genuinely must inspect them:
         import { Children } from "react";
         Children.toArray(children)     // always an array, flattens
                                        // fragments, drops null/undefined,
                                        // and assigns stable keys

  Prefer (1). Needing (2) usually means the API should have taken an
  array prop — <Tabs items={…}/> — rather than inspecting children.

Part 2 — Props Syntax, Fully

<Widget
  title="Plain string"              // string literal — the only unbraced form
  count={42}                        // ANY expression needs braces, numbers included
  user={{ name: "Ada" }}            // outer braces JSX, inner braces object literal
  onClick={handleClick}             // pass the FUNCTION, do not call it
  disabled                          // bare prop is shorthand for {true}
  data-testid="widget-1"            // data-* and aria-* pass through, dashes kept
  aria-label="Main widget"
/>

// SPREAD — forward every key of an object as individual props
const inputProps = { type: "email", required: true, placeholder: "you@example.com" };
<input {...inputProps} />
  SPREAD ORDER IS A SEMANTIC DECISION, NOT FORMATTING

  Props compile to an object built left to right, so later keys overwrite
  earlier ones. That single fact gives you two opposite behaviours:

    function TextInput(props) {
      return <input type="text" {...props} />;
      //            ^^^^^^^^^^^ BEFORE the spread
      //            = a DEFAULT. <TextInput type="password"/> overrides it.
    }

    function TextInput(props) {
      return <input {...props} type="text" />;
      //                       ^^^^^^^^^^^ AFTER the spread
      //            = ENFORCED. type="password" is silently ignored.
    }

  THE BUG THIS CAUSES, and it is always the same bug report:
    "I passed className to your Button and nothing happened."

    function Button({ ...rest }) {
      return <button {...rest} className="btn" />;   // ❌ eats className
    }

  The caller's className is overwritten by the component's. Nothing warns;
  the prop simply vanishes. The fix is to MERGE rather than pick a side:

    function Button({ className = "", ...rest }) {
      return <button {...rest} className={`btn ${className}`.trim()} />;
    }

  Pull out every prop you intend to combine, and let the spread carry only
  what you pass through untouched.
⚠️ Spread is a boundary tool, not a default. {...props} earns its keep in thin wrappers around host elements — design-system buttons and inputs, where forwarding every HTML attribute is the point. Between your own components, explicit props keep the data flow greppable: with a spread, "where does this prop come from?" has no answer short of running the app. Spreading everything everywhere is also how unknown-attribute warnings and leaked internals end up in the HTML.

Part 3 — Conditional Rendering: the Complete Idiom Set

function Inbox({ user, messages, error, loading }) {
  // 1. EARLY RETURN — whole-component branches
  if (error)   return <ErrorPanel error={error} />;
  if (loading) return <Spinner />;

  return (
    <div>
      {/* 2. TERNARY — exactly two inline branches */}
      {user ? <b>{user.name}</b> : <a href="/login">Sign in</a>}

      {/* 3. && — render-or-nothing, with a REAL boolean */}
      {messages.length > 0 && <Badge count={messages.length} />}

      {/* 4. VARIABLE — when the logic outgrows the markup */}
      {renderRows(messages)}
    </div>
  );
}

// 5. LOOKUP MAP — once you would nest ternaries
const STATUS_VIEW = {
  idle:    <p>Ready.</p>,
  running: <Spinner />,
  done:    <p>Complete</p>,
  failed:  <p>Failed — retry?</p>,
};
function Status({ state }) { return STATUS_VIEW[state] ?? null; }
IdiomUse whenWhy not the others
Early returnThe whole view differs — loading, error, empty, unauthorisedReads top-to-bottom as a list of guards, and keeps the happy path unindented
TernaryExactly two branches, both small, inline in markupA third branch means nesting, which is the most-flagged readability smell in React review
&&An optional extra — a badge, a warning rowOnly with a real boolean on the left; {count && …} renders 0
Extracted variableThe branch needs several statements to computeKeeps computation above the return, where statements are legal
Lookup objectThree or more states keyed by one valueAdding a state becomes one line, and an exhaustive TypeScript Record makes a missing case a compile error
⚠️ One caution on the lookup map as written above: those elements are created once, at module load, and shared by every render of every instance. That is fine for static content and wrong the moment a branch needs props or state — it will capture stale values. Store functions ({ idle: () => <p>Ready</p> }) or components ({ idle: IdleView }) as soon as the branches take arguments.

Part 4 — Fragments, Keys on Fragments & Returning Arrays

import { Fragment } from "react";

function Glossary({ terms }) {
  return (
    <dl>
      {terms.map(t => (
        <Fragment key={t.id}>        {/* <> cannot take props; Fragment can */}
          <dt>{t.word}</dt>
          <dd>{t.meaning}</dd>
        </Fragment>
      ))}
    </dl>
  );
}

  WHY THIS IS NOT STYLISTIC:
  <dl> may only contain <dt> and <dd> (and script-supporting
  elements). A wrapper <div> per pair produces invalid HTML — which
  browsers will render, and screen readers will stop treating as a
  definition list. The same constraint applies to:

    <table> / <tr> / <td>      a div between them breaks the table model
    <ul> / <li>                 and its list semantics
    flex and grid parents        a wrapper becomes the flex item, so every
                                 child's alignment silently changes

  That last one is the reason to reach for a Fragment by default rather
  than a div: an extra element is never visually neutral in a flex or
  grid container.

Part 5 — Dynamic Types & Elements as Values

// 1. THE TAG ITSELF CAN BE A VARIABLE — it is just the `type` field
function Heading({ level = 2, children }) {
  const Tag = `h${level}`;                 // Capitalized VARIABLE, or JSX
  return <Tag>{children}</Tag>;            // emits the string "h1", "h2", …
}
<Heading level={1}>Title</Heading>

// 2. POLYMORPHIC "as" PROP — the design-system staple
function Button({ as: Component = "button", ...props }) {
  return <Component className="btn" {...props} />;
}
<Button>Save</Button>                      // <button class="btn">
<Button as="a" href="/docs">Docs</Button>  // <a class="btn" href="/docs">

// 3. ELEMENTS ARE VALUES — store them, pass them, choose between them
const icon = active ? <StarFilled /> : <StarOutline />;
<Toolbar left={<Logo />} right={icon} />   // "element as prop": slots beyond children
Slot APIShapeWho controls the propsReach for it when
Element as propright={<Icon size={20}/>}The caller — the receiver only positions itThe content is fully known at the call site. The default, and the weakest tool
Component as propicon={Icon}, rendered <Icon />The receiver — it instantiates, so it can inject propsThe receiver knows something the caller cannot, such as the pixel size its own size maps to
Render proprenderRow={item => …}Both — the receiver passes data out, the caller returns markupThe caller's markup depends on data only the receiver has, such as each row of a virtualised list
🔑 Pick the weakest tool that works: element → component → render prop. Each step gives the receiver more power and costs the caller more indirection, and every step is harder to read in a stack trace. A render prop where an element would do is the component-API equivalent of making a field public because you might need it later — and it is the specific over-engineering that made pre-hooks React so hard to follow.

Part 7 — What JSX Actually Compiles To

Every rule in Parts 1–6 falls out of one fact: JSX is not a template language, it is syntax sugar over function calls. Once you have seen the output, the gotchas stop being arbitrary.

// what you write
<Card title="Hi" onSelect={fn}><p>body</p></Card>

// what the compiler emits (modern automatic runtime)
jsx(Card, { title: "Hi", onSelect: fn, children: jsx("p", { children: "body" }) })

// which evaluates to a plain object — a DESCRIPTION, not a DOM node
{ type: Card, props: { title: "Hi", onSelect: fn, children: {…} }, key: null }
RuleWhy it must be that way
Components must be capitalised<card /> compiles to jsx("card", …) — a string, so a DOM tag. <Card /> compiles to jsx(Card, …), the variable
No if statement inside JSXBraces hold an expression to pass as an argument. A statement has no value to pass — hence &&, ternaries and early returns
children is an ordinary propIt is one more key in the props object; nesting syntax is shorthand for setting it
Elements are cheapCreating one allocates a small object and touches no DOM. That happens later, at commit
key and ref never reach your componentThe runtime lifts them out of props, which is why props.key is undefined and React warns when you read it
Prop order decides overridesThe props object is built left to right, so later keys win — the whole of Part 2
🔑 An element is a description of what you want, produced by a function call. That is the entire model, and it is why the same JSX renders to the DOM in a browser, to a string on a server, and to native views on a phone — nothing in the syntax assumes any of them.

Interview Questions

Beginner: What is props.children and why is it useful?

It is the prop holding whatever was nested between a component's opening and closing tags — text, a single element, or several. The nesting syntax is just sugar for setting that prop; you could pass children={…} explicitly and get the same result.

Its value is that it inverts who decides the content. A Card that renders {children} does not need to know or care what is inside it, so one component serves every card in the product. The alternative — a content string prop, or a growing set of booleans like showFooter — makes the container responsible for every variation anyone will ever need. That is composition instead of configuration.

The detail worth adding is that its shape is not stable: undefined with no children, the value itself with one, and an array with several. Code that iterates children without normalising works until someone passes exactly one.

Beginner: What is the difference between onClick={fn} and onClick={fn()}?

The first passes the function itself, so React calls it when the click happens. The second calls it immediately, during render, and passes its return value — usually undefined — as the handler. So the click does nothing, and the work happened at the wrong time.

When fn sets state, it is worse than a no-op: setting state during render schedules another render, which calls it again, which schedules another. That is an infinite loop, and the symptom is a frozen tab or React's "Too many re-renders" error rather than anything pointing at the handler.

To pass arguments, wrap it: onClick={() => fn(id)}. That creates a new function on every render, which is fine — it only matters when the handler is passed to a memoized child, and that trade-off belongs in useMemo & useCallback rather than being pre-optimised here.

Mid: When do you need <Fragment key=…> instead of <>?

Whenever you map over a list and each item produces multiple sibling elements that must not be wrapped in a DOM node. Each item in a list needs a key, keys go on the outermost element per item, and the shorthand <> cannot take props at all — so the long form is the only option.

The canonical case is <dt>/<dd> pairs inside a <dl>. A wrapper <div> per pair would be invalid HTML, and the practical consequence is not pedantry — assistive technology stops treating it as a definition list. The same applies inside tables, where a div between <tr> and <td> breaks the table model.

There is a third case people miss: flex and grid containers. An extra wrapper becomes the flex item, so every child's alignment and sizing changes. That is why a Fragment, not a div, should be the reflex when grouping — a div is never visually neutral inside a layout container.

Mid: How does prop spread order interact with defaults and overrides?

JSX props compile to an object literal built left to right, so later keys overwrite earlier ones. That gives you two opposite behaviours from the same syntax, decided purely by position.

A prop placed before {...rest} is a default: the caller can override it. A prop placed after is enforced: the caller's value is silently discarded.

The bug this produces is one of the most common in design systems — a Button written as <button {...rest} className="btn" /> throws away every caller's className, so consumers report that styling "doesn't work" and nothing warns, because overwriting a key in an object literal is perfectly legal.

The fix is that anything you intend to combine rather than pick a winner for must be pulled out and merged explicitly: destructure className, then render className={`btn ${className}`}. Spread should carry only what passes through untouched.

In review I treat any prop written after a spread as a claim that the component owns it absolutely, and ask whether that was intended — half the time it was not.

Senior: Element-as-prop, component-as-prop, render prop — when does each earn its place?

They differ in one dimension: who supplies the props.

Element as prop — right={<Icon size={20}/>}. The caller builds the whole thing and the receiver only positions it. This is the default and the weakest tool, which is exactly why it should be the first choice.

Component as prop — icon={Icon}, rendered as <Icon />. The receiver instantiates it, so the receiver can inject props the caller could not know. The test is whether the receiver holds information the caller lacks: an IconButton whose own size="m" maps to 18 pixels cannot let the caller pre-size the icon, because only the button knows the mapping.

Render prop — renderRow={item => …}. Data flows out to the caller and markup comes back. Necessary when the caller's markup depends on values only the receiver has — each row of a virtualised list, or the result of a data-fetching component.

My rule is to pick the weakest tool that works, because each step gives the receiver more control and costs the caller more indirection. A render prop where an element would do is harder to read, harder to type, and shows up as an anonymous function in every stack trace and profile.

Worth noting that hooks removed most of the historical uses of render props. They were the only way to share stateful logic before hooks, which is why older codebases are full of them; today a render prop should be about rendering — the receiver controlling structure while the caller controls appearance — and anything that is really shared logic belongs in a custom hook.

Senior: How does JSX escaping prevent XSS, and where exactly does it stop?

Interpolated values are set through DOM APIs — as text nodes or attribute values — and never parsed as HTML. So a string containing <script> or an onerror handler renders as visible text rather than markup. Because that covers the overwhelming majority of injection points in a typical app, React is genuinely safe by default in a way that string-templating frameworks are not.

The limits are specific and worth being able to list.

dangerouslySetInnerHTML bypasses it completely — that is its entire purpose, and the name is a deliberate speed bump. Anything reaching it needs sanitizing with something like DOMPurify, ideally server-side so the client is not the only line of defence.

URL-bearing props are a different sink. href, src, action and formAction take strings that the browser may execute — javascript:alert(1) from a user-supplied profile link is not text, and escaping it as text does nothing. Modern React warns about and blocks some of these, but the reliable answer is to validate the protocol yourself against an allow-list.

Escaping only covers markup React produced. Anything assembled server-side and sent as HTML, or injected by a third-party script, was never in React's hands.

The framing I would give in an interview is that auto-escaping solves injection into content, which is the common case, and leaves you responsible for the sinks where a string is intended to be interpreted — HTML, URLs, and CSS. Knowing that boundary is the difference between "React prevents XSS" and actually being safe.

🏋️ Graded Exercises

1 (easy): Build an Alert component: renders its children in a div.alert, plus a tone prop ("info" | "error") that adds alert-info / alert-error.
Solution 
function Alert({ tone = "info", children }) {
  return <div className={`alert alert-${tone}`}>{children}</div>;
}

Why children rather than a message string prop: the moment someone needs a link or a bold word inside the alert, a string prop forces either dangerouslySetInnerHTML or a second prop. children accepts any subtree for free.

Why a tone enum rather than a color prop: it keeps the palette owned by the stylesheet. A free-text colour lets any call site bypass the design system, and a year later there are eleven reds and no way to theme them centrally.

What a reviewer would ask for next: the accessibility contract. An error alert should carry role="alert" so assistive technology announces it immediately, while an info alert usually should not — being interrupted for a non-urgent message is worse than missing it:

function Alert({ tone = "info", children }) {
  return (
    <div className={`alert alert-${tone}`}
         role={tone === "error" ? "alert" : "status"}>
      {children}
    </div>
  );
}
2 (easy): Why does <b>Save</b><i>now</i> on separate lines render "Savenow", and how do you fix it?
Solution 
// JSX collapses whitespace that SPANS LINES, exactly as HTML source
// formatting does — the newline and indentation between the tags are
// treated as insignificant and removed.

<b>Save</b>{" "}<i>now</i>      // explicit space as an expression
<b>Save</b> <i>now</i>         // also works — same line, space preserved

The rule precisely: whitespace on the same line between elements is kept; whitespace containing a newline is stripped. Both forms above are correct.

Why {" "} is the one to write anyway: the single-line version is at the mercy of your formatter. Prettier rewraps a line that grows past the print width, and the space disappears — a text bug introduced by a formatting commit, which is close to impossible to spot in a diff full of reindentation.

Where this actually shows up: inline links in sentences — <span>See <a>docs</a> for more</span> — where the words fuse into "Seedocsfor more" after a reformat. If you find yourself adding several {" "} in one sentence, that is a signal the whole sentence should be one text node with the element interpolated into it.

3 (medium): Refactor this into readable JSX: {a ? <X/> : b ? <Y/> : c ? <Z/> : <W/>}
Solution 
// OPTION A — early returns, when this is the whole component
if (a) return <X />;
if (b) return <Y />;
if (c) return <Z />;
return <W />;

// OPTION B — a lookup, when a/b/c are really one status value
const VIEWS = { loading: Spinner, error: ErrorPanel, empty: EmptyState };
const View = VIEWS[status] ?? ResultsList;
return <View {...props} />;
OptionChoose it whenCost
Early returnsThe branches are the whole render, and the conditions are genuinely independentOnly usable at the top of a component, not inline in markup
Lookup objectThe conditions are one variable in disguise — the usual caseNeeds a real status value; forcing one where none exists is worse than the ternaries
Extract a componentThe branching sits inside larger markupOne more file, one more name to invent

The diagnostic question is whether a, b and c can be true simultaneously. If they cannot, they are one state variable pretending to be three booleans, and the honest fix is upstream — replace them with status: "loading" | "error" | "empty" | "ready". Then the lookup is exhaustive, the impossible states are unrepresentable, and TypeScript can prove you handled every case.

Why nested ternaries get flagged so consistently: not aesthetics — reviewability. To check the third branch you must mentally evaluate the first two, and adding a state means editing in the middle of an expression, which produces diffs nobody can read.

4 (medium): Write a DefinitionList taking items = [{id, term, def}] that renders a valid <dl> with keyed term/definition pairs.
Solution 
import { Fragment } from "react";

function DefinitionList({ items }) {
  return (
    <dl>
      {items.map(({ id, term, def }) => (
        <Fragment key={id}>
          <dt>{term}</dt>
          <dd>{def}</dd>
        </Fragment>
      ))}
    </dl>
  );
}
DecisionWhy
Fragment, not <>The shorthand takes no props, and each list item needs a key
No wrapper <div><dl> permits only dt/dd children. A div renders, but assistive technology stops treating it as a definition list — a real accessibility regression, not a validator nit
key={id}, not the indexStable identity across insertion and reordering, which is the same fiber-identity question as everywhere else

The interesting constraint is that the key belongs on the Fragment, not on the <dt>. Keys identify one item among siblings, and here one item is a pair. Keying the dt and dd individually would work in the sense that React stops warning, but it models two independent lists that happen to interleave, and it breaks the moment a term has two definitions.

What I would ask before shipping: whether def can contain markup. If it is rich text from a CMS, this component needs a decision about sanitizing rather than a dangerouslySetInnerHTML added later under deadline.

5 (medium): Build a polymorphic Text component: as picks the tag (default p), size maps to a class, and all other props forward.
Solution 
function Text({ as: Tag = "p", size = "m", className = "", ...rest }) {
  return <Tag className={`text text-${size} ${className}`.trim()} {...rest} />;
}

// <Text as="span" size="s" id="hint">Small note</Text>
DetailWhy it is written that way
as: Tag renamed in the destructureA dynamic tag must be a capitalised identifier — lowercase as would compile to the literal string "as"
className destructured outSo it can be merged. Leaving it in rest means either the spread overwrites the component's classes or the component's overwrite the caller's — one of them is always lost
{...rest} lastLets callers pass id, onClick, aria-* and data attributes without the component enumerating them
.trim()Avoids a trailing space when no className is passed — cosmetic in the DOM, but it keeps snapshot tests stable

The sharp edge in this pattern is that as escapes your type system. <Text as="a"> without an href is a link to nowhere; as="button" without type defaults to submit and will post a surrounding form. Fully typing a polymorphic component in TypeScript is possible but genuinely awkward, and a common production compromise is to expose a small allow-list of tags instead of arbitrary ones.

The accessibility trap worth naming: as changes semantics, not just appearance. Using as="div" on something clickable to avoid button styling produces an element that is not focusable and not announced as interactive. If it behaves like a button it must be a button.

6 (hard): Design a SplitPane with left and right element props plus children as the main area — then explain why element props beat a leftContent="…" string API.
Solution 
function SplitPane({ left, right, children }) {
  return (
    <div className="split">
      {left && <aside className="split-left">{left}</aside>}
      <main className="split-main">{children}</main>
      {right && <aside className="split-right">{right}</aside>}
    </div>
  );
}

// <SplitPane left={<Nav />} right={<Ads />}><Article /></SplitPane>

Note the {left && …} guards. Without them an omitted pane still renders an empty <aside>, which in a grid or flex layout occupies a track and leaves a visible gap. These are safe && uses because the operands are elements or undefined, never numbers.

APIWhat the caller can put thereHow it ages
leftContent="Nav"Plain text onlyBadly — the first request for a link inside it forces a second prop, or dangerouslySetInnerHTML
left={<Nav />}Any subtree: components, interactive widgets, fragments, nullWell — new requirements are the caller's problem, not the component's

The general principle: a string prop is a slot with a ceiling. Every product request that exceeds it becomes a new configuration flag on the container, and containers accumulate them until nobody can tell which combinations are legal. An element prop has no ceiling, so the container stays a layout component forever.

When a string prop is right: when you genuinely need the value, not markup — an aria-label, a document title, something you will truncate, sort, or send to analytics. Those cannot accept an element, and reaching for one is the opposite mistake.

Why not just use children for all three? You can — <SplitPane.Left> compound components exist for exactly this. Element props are simpler, fully typed, and obviously optional; compound components read better when there are many slots and the caller expects to nest them like markup. For three slots, props win on simplicity.

7 (hard): A design-system IconButton takes icon={StarIcon} and renders it at a size derived from its own size prop. Implement it, and say why element-as-prop could not do this.
Solution 
const ICON_PX = { s: 14, m: 18, l: 24 };

function IconButton({ icon: Icon, size = "m", children, ...rest }) {
  return (
    <button type="button" className={`iconbtn iconbtn-${size}`} {...rest}>
      <Icon size={ICON_PX[size]} aria-hidden="true" />   {/* receiver injects */}
      {children}
    </button>
  );
}

Why element-as-prop cannot express this. With icon={<StarIcon />} the caller has already created the element, so its props are fixed before IconButton ever sees it. But the pixel size is derived from a mapping only IconButton owns — the caller passes size="m" and has no way to know that means 18. Passing the component defers instantiation to the party that holds the information.

DetailWhy
icon: Icon renamedIt must be capitalised to compile as a component reference rather than the string "icon"
type="button"A <button> defaults to type="submit", so inside a form this would submit it. One of the most common accidental-submit bugs
aria-hidden="true" on the iconThe icon is decorative; the accessible name comes from children. Without it a screen reader may announce the glyph twice or read a meaningless name
{...rest} after the classCallers can pass onClick, disabled, aria-* — but note this also lets them override type, which here is intended

The accessibility gap this implementation still has: an icon-only button, called with no children, has no accessible name at all — a screen reader announces "button". A real design-system component should require either children or an aria-label, and in TypeScript that constraint is expressible as a union type so the compiler enforces it.

Could you avoid the whole question? Yes — have the icon read its size from CSS (width: 1em) and let the button's font size drive it. That removes the need for component-as-prop entirely, and is usually the better answer when the only injected prop is sizing. Reach for component-as-prop when the receiver must inject something CSS cannot express, such as an isActive state.

🎯 Key Takeaways

  • children is an ordinary prop with nesting syntax — and its shape is undefined, a value, or an array depending on how many were passed.
  • children.map crashes for callers who pass exactly one child — render {children}, or normalise with Children.toArray.
  • Needing to inspect children is usually an API smell — an array prop is clearer than reflection over a subtree.
  • onClick={fn()} calls during render and passes the return value; with a state setter that is an infinite render loop.
  • Spread order decides defaults versus enforcement: before the spread the caller can override, after it the caller is silently ignored.
  • Anything you want to merge must be destructured out — the classic "your Button eats my className" bug.
  • Conditional idioms in order: early-return guards, one ternary, && with a real boolean, a lookup object. Never nested ternaries.
  • Three booleans that cannot be true together are one status value in disguise — fix it upstream and the rendering problem disappears.
  • A lookup map of elements is created once and shared, so it captures stale values the moment branches need props.
  • Keyed <Fragment> groups multi-element list items without emitting the wrapper that would be invalid inside dl or table.
  • A wrapper div is never neutral in flex or grid — it becomes the item and changes every child's alignment.
  • The tag is just a value: capitalised variables, as-prop polymorphism, and elements stored in variables are all the same fact.
  • as changes semantics, not just appearance — a clickable div is not focusable and is not announced as interactive.
  • Pick the weakest slot API that works: element → component → render prop, and use component-as-prop only when the receiver knows something the caller cannot.
  • Interpolation is auto-escaped, which covers injection into content — the common case, and genuinely safe by default.
  • It stops at dangerouslySetInnerHTML, URL props and server-built markup. Validate URL protocols against an allow-list yourself.
