Composition Patterns Patterns & Quality

What you'll master: why a component that has grown fifteen boolean props is telling you it wants elements instead of configuration; children as the one primitive everything else is built from, and the under-used move of passing several named element slots; the fact that children passed from a parent keep a stable element identity, so composition is a re-render tool as well as a design one; compound components sharing implicit state through context, and the API-surface and typing cost that buys; render props and HOCs framed honestly as mostly superseded — except where the component owns rendering position; and the rule that decides between a custom hook and a slot: hooks extract logic, composition extracts structure. Prerequisites: JSX Deep Dive, Context, Custom Hooks.

Part 1 — Configuration Collapses; Composition Does Not

Every shared component starts small and honest. Then a second team needs a footer, a third needs the header to be clickable, and someone needs a variant with no padding. Each request arrives as one more prop, and each one is individually reasonable. The failure is cumulative.

// MONTH 1 — reasonable
function Card({ title, body }) { … }

// MONTH 9 — the same component, after eleven reasonable requests
function Card({
  title, subtitle, body, footer,
  showHeader, showFooter, showDivider, showCloseButton,
  headerIcon, headerIconColor, headerAlign,
  footerAlign, footerButtons, onFooterButtonClick,
  compact, bordered, elevated, clickable, onClick,
  badge, badgeVariant, loading, error, errorRetry,
}) {
  // 340 lines, of which ~200 are conditional rendering
}
  WHY THIS SHAPE FAILS — and it is not "too many props" as an aesthetic

  1. STATE EXPLOSION. Sixteen booleans is 2^16 = 65,536 nominal
     combinations. Most are meaningless (showFooter=false with
     footerButtons set), and NOTHING in the type system says so. Every
     illegal combination is a bug someone will eventually ship.

  2. THE COMPONENT OWNS DECISIONS IT CANNOT SEE. headerAlign exists
     because one screen needed centre alignment. Card has no idea which
     screen, or why, and cannot be changed without auditing all callers.

  3. EVERY NEW REQUIREMENT IS A CHANGE TO SHARED CODE. Wanting a
     progress bar in the header means editing Card, re-reviewing Card,
     re-testing Card, and re-releasing it to every consumer.

  4. THE BUNDLE CARRIES ALL OF IT ALWAYS. The error-retry branch,
     the badge, the loading skeleton — every consumer downloads and
     parses the code for features it does not use.

  5. NOBODY CAN READ THE CALL SITE.
       <Card title="Users" showHeader showDivider compact bordered />
     What does this look like? You have to go read Card to find out.

Composition inverts the direction of control. Instead of the component deciding what to render from flags, the caller hands it rendered elements and the component decides only where they go.

// COMPOSITION — Card owns layout and nothing else
function Card({ header, children, footer, ...rest }) {
  return (
    <section className="card" {...rest}>
      {header  && <div className="card-head">{header}</div>}
      <div className="card-body">{children}</div>
      {footer  && <div className="card-foot">{footer}</div>}
    </section>
  );
}

// The call site now READS as what it renders
<Card
  header={<h2>Users <Badge tone="warn">3 pending</Badge></h2>}
  footer={<Button onClick={invite}>Invite</Button>}
>
  <UserTable rows={rows} />
</Card>

  showHeader          -> gone. Passing no header IS showHeader={false}.
  headerIcon          -> gone. Put the icon in the element you pass.
  headerAlign         -> gone. Style what you passed.
  footerButtons       -> gone. They are just children of the footer.
  badge/badgeVariant  -> gone. Badge is a component, not a Card feature.
  onFooterButtonClick -> gone, and with it the worst prop in the file:
                         a callback whose meaning depended on an index.
Symptom in reviewWhat it is really sayingComposition answer

Props that only style a sub-part — headerAlign, titleColorThe caller wants to control markup it is not allowed to passLet it pass the markup

🔑 The rule that catches this early: a prop should describe data or an axis of variation, never a piece of markup. size="sm" is an axis — genuinely enumerable, meaningful to the component, and testable. headerIconColor is markup the caller could not pass, smuggled in as a string. When you catch yourself adding the second one, add a slot instead. The escape hatch is not free — see Part 4 for what compound components cost — but a boolean you regret is permanent in a way an element prop is not.

Part 2 — children Is the Primitive; Named Slots Are the Under-used Half

children is not special syntax. It is a prop like any other, and JSX has a nesting shorthand for it. Understanding that literally is what unlocks the rest of this lesson.

// These two are the SAME element, byte for byte after compilation:
<Panel><p>hi</p></Panel>
<Panel children={<p>hi</p>} />

// Both compile to (React 17+ automatic runtime):
jsx(Panel, { children: jsx("p", { children: "hi" }) })

  So children can be: an element, an array of elements, a string, a
  number, null, false, undefined, a fragment — or a FUNCTION (Part 5).
  React renders strings and numbers, and ignores null/undefined/boolean,
  which is exactly why {cond && <X />} works and why {count && <X />}
  renders a bare 0 when count is 0.

The half most codebases skip: a component may take several element props. One is children by convention; the rest are named slots. This is how you keep a layout component both flexible and structurally opinionated.

function PageShell({ breadcrumbs, title, actions, aside, children }) {
  return (
    <div className="page">
      <nav aria-label="Breadcrumb">{breadcrumbs}</nav>
      <header className="page-head">
        <h1>{title}</h1>
        <div className="page-actions">{actions}</div>
      </header>
      <div className="page-cols">
        <main>{children}</main>
        {aside && <aside>{aside}</aside>}
      </div>
    </div>
  );
}

  WHAT THIS BUYS OVER ONE children BLOB:
    - PageShell still owns the grid, the landmarks and the spacing. A
      screen cannot accidentally put actions below the fold.
    - Slots are named, so the call site is self-documenting and the
      TypeScript signature is honest: actions?: ReactNode.
    - Omitting `aside` collapses the column. No showAside prop.
    - Each slot renders in ONE place, so there is no ambiguity about
      where a given element ends up.
TechniqueShapeUse whenCost

⚠️ Slots take elements, not components — and the difference is real. header={<Title />} passes an already-created element the caller fully configured. HeaderComponent={Title} passes the function, so the receiver decides the props. Take the element when the caller knows best (almost always). Take the component only when the receiver must inject props it owns — that is the legitimate case for as in Part 7, and the reason icon={Icon} beats icon={<Icon />} in a button that wants to force the icon's size.

Part 3 — Children Passed From a Parent Have Stable Identity

This is the part people meet as a performance trick and never connect back to composition. It is the same mechanism, seen from the reconciler's side.

  A component re-renders because ITS OWN state changed or because its
  parent re-rendered and produced a new element for it. Reconciliation
  compares the previous element to the new one at the same position:

    same type AND same reference  -> React can bail out of that subtree
    same type, different props    -> re-render the component
    different type                -> unmount old subtree, mount new one

  The reference check is the one composition affects. JSX written INSIDE
  a component body creates a new element object on every render of that
  component. JSX passed IN from a parent was created by the PARENT, and
  is the SAME object across the child's re-renders.
// ❌ SLOW — the expensive tree is created inside the re-rendering component
function Layout() {
  const [q, setQ] = useState("");             // changes on every keystroke
  return (
    <div>
      <input value={q} onChange={e => setQ(e.target.value)} />
      <ExpensiveChart data={data} />          // re-created + re-rendered
    </div>                                    // on EVERY keystroke
  );
}

// ✅ FAST — the expensive tree is created by the parent and passed through
function Layout({ children }) {
  const [q, setQ] = useState("");
  return (
    <div>
      <input value={q} onChange={e => setQ(e.target.value)} />
      {children}                              // SAME element object every
    </div>                                    // render of Layout
  );
}

function Page() {
  return (
    <Layout>
      <ExpensiveChart data={data} />          // created HERE, by Page,
    </Layout>                                 // which is not re-rendering
  );
}

  Typing a 20-character query:
    version 1 -> ExpensiveChart renders 20 times
    version 2 -> ExpensiveChart renders 0 additional times

  Nothing is memoized. No React.memo, no useMemo, no dependency array
  to get wrong. The state moved DOWN and the expensive tree moved UP,
  and the reconciler does the rest.
Element written whereNew object per render?Can React bail out of the subtree?
Inside the component whose state changedYesNo — different reference, so it re-renders
Passed in as children from a non-rendering parentNoYes — identical reference, subtree skipped
Passed in as a named slot prop (footer={…})NoYes — the same rule; children is not special
Inside a useMemo in the re-rendering componentNo, while deps holdYes, but you now maintain a dependency array
Created in a .map() over a prop arrayYes, every renderNo — memo on the child will never hit
🔑 This is also the reason React.memo "does not work" on components that take children. If the memoized component's parent renders JSX children inline, those children are a fresh object every time and memo's shallow compare fails on the children prop — every render, forever. Memo did not fail; it correctly detected a changed prop. Fix it by moving where the element is created, not by adding a custom comparator that lies about equality.

Part 4 — Compound Components: Shared Implicit State

Named slots run out when the regions are not fixed — a tab set has an arbitrary number of tabs, in an order the caller chooses, and each tab needs to know whether it is the selected one. Compound components solve that by letting the caller lay out the parts while a context carries the shared state between them.

const TabsCtx = createContext(null);

function useTabs(part) {
  const ctx = useContext(TabsCtx);
  // FAIL LOUDLY. Without this, a misplaced Tab throws
  // "cannot read property of null" from deep inside your own code.
  if (!ctx) throw new Error(`${part} must be used inside <Tabs>`);
  return ctx;
}

export function Tabs({ defaultValue, value, onChange, children }) {
  const [uncontrolled, setUncontrolled] = useState(defaultValue);
  const isControlled = value !== undefined;
  const active = isControlled ? value : uncontrolled;

  const select = useCallback(v => {
    if (!isControlled) setUncontrolled(v);
    onChange?.(v);
  }, [isControlled, onChange]);

  // useMemo matters HERE: without it every Tabs render gives every
  // consumer a new context value, defeating any memo below.
  const ctx = useMemo(() => ({ active, select }), [active, select]);

  return <TabsCtx.Provider value={ctx}>{children}</TabsCtx.Provider>;
}

Tabs.List = function TabList({ children }) {
  return <div role="tablist">{children}</div>;
};

Tabs.Tab = function Tab({ value, children }) {
  const { active, select } = useTabs("Tabs.Tab");
  const selected = active === value;
  return (
    <button role="tab" aria-selected={selected} id={`tab-${value}`}
            aria-controls={`panel-${value}`} tabIndex={selected ? 0 : -1}
            onClick={() => select(value)}>
      {children}
    </button>
  );
};

Tabs.Panel = function Panel({ value, children }) {
  const { active } = useTabs("Tabs.Panel");
  if (active !== value) return null;
  return (
    <div role="tabpanel" id={`panel-${value}`}
         aria-labelledby={`tab-${value}`}>{children}</div>
  );
};
// The call site: layout is the CALLER'S, state is implicit
<Tabs defaultValue="usage">
  <Tabs.List>
    <Tabs.Tab value="usage">Usage</Tabs.Tab>
    <Tabs.Tab value="billing">Billing <Badge>2</Badge></Tabs.Tab>
  </Tabs.List>
  <hr />                        // arbitrary markup between the parts
  <Tabs.Panel value="usage"><UsageChart /></Tabs.Panel>
  <Tabs.Panel value="billing"><Invoices /></Tabs.Panel>
</Tabs>

  Compare the configuration version this replaces:
    <Tabs items={[{id, label, badge, content, disabled, icon}]}
          renderLabel={…} renderPanel={…} listClassName={…} />
  — which needs a new prop for every visual idea anyone ever has.

Use context, not React.Children.map plus cloneElement. Cloning was the pre-hooks implementation and it breaks the moment a consumer wraps a part: with <Tooltip><Tabs.Tab /></Tooltip> the tooltip is the direct child, so the injected props land on the tooltip instead of the tab. Context reaches any depth and does not care about the shape of the tree.

Compound components give youAnd cost you
Callers control layout and arbitrary markup between partsA much larger public API — every part is a name you must support forever
No prop drilling; parts read shared state from contextTyping is genuinely harder: relating Tab value to Panel value needs generics, and static properties on a function fight forwardRef
New parts can be added without touching existing onesEvery part re-renders when the context value changes, unless you split contexts (state vs dispatch)
Accessibility wiring (role, aria-controls, roving tabIndex) lives in the parts, so callers cannot forget itYou now own that wiring — including keyboard arrow-key navigation, which the code above still lacks
Reads like the HTML it replaces (select/option, table/tr)Misuse fails at runtime, not compile time, unless you add the explicit context guard
⚠️ Do not build a compound component for two fixed regions. The pattern earns its complexity when the parts are variable in number or order and must share state. A dialog with a header, body and footer is three named slots, and a Dialog.Header that only ever appears once, first, is ceremony with a context attached. Reach for it at Tabs, Accordion, Menu, Select and Table — not at Card.

Part 5 — Render Props and HOCs: What They Were For, and What Replaced Them

Both patterns existed to solve one problem hooks did not yet solve: sharing stateful logic between components. Hooks solved it directly in 2019, and most render-prop and HOC code written since is inertia. Most — not all.

// RENDER PROP (2016-2018) — logic in a component, UI supplied by caller
<MouseTracker render={({ x, y }) => <Cursor x={x} y={y} />} />

// FUNCTION AS CHILDREN — identical mechanism, children happens to be a fn
<MouseTracker>{({ x, y }) => <Cursor x={x} y={y} />}</MouseTracker>

// THE HOOK THAT REPLACED BOTH
const { x, y } = useMouse();
return <Cursor x={x} y={y} />;

  WHAT THE HOOK FIXED:
    - No wrapper component in the tree, so no extra fiber and no
      extra element allocation per render.
    - No "wrapper hell": three render props nested four levels deep
      turn into three flat lines.
    - Values arrive as plain variables, so they participate in
      dependency arrays, early returns and destructuring normally.
    - Composing two of them is two calls, not a pyramid.
  WHERE A FUNCTION CHILD STILL WINS — and this is not nostalgia

  A hook can return VALUES. It cannot return a POSITION in the tree.
  When the component owns where, when and how many times something is
  rendered, the caller's markup must be a function the component calls.

    <VirtualList items={rows} height={600} rowHeight={32}>
      {(row, style) => <div style={style}>{row.name}</div>}
    </VirtualList>

  VirtualList decides that rows 40-58 are visible and calls the child
  function 19 times with a computed style. There is no hook shape that
  expresses "call this markup once per visible row, at a position I
  compute during my own render".

  Same category:
    - windowing / virtualisation (react-window, TanStack Virtual)
    - drag layers that render a preview at a measured position
    - measurement wrappers that render children with a known width
    - table and column builders where the library owns the cell loop
    - Suspense's fallback prop is this idea with the function removed

  RULE: hooks for values, function-children for POSITION.
// HIGHER-ORDER COMPONENT — a function taking a component, returning one
function withUser(Wrapped) {
  return function WithUser(props) {
    const user = useContext(UserCtx);
    return <Wrapped {...props} user={user} />;
  };
}
export default withUser(withTheme(withRouter(withAnalytics(Profile))));

  WHAT THAT LAST LINE COSTS:
    1. WRAPPER HELL. Four extra fibers per instance, and a DevTools
       tree reading WithAnalytics, WithRouter, WithTheme, WithUser and
       only then Profile — before you reach anything you wrote.
    2. PROP COLLISIONS, SILENT. If withUser and withRouter both inject
       `match`, the outer one wins and nothing warns you. The bug looks
       like "the route params are wrong on this one screen".
    3. UNCLEAR PROVENANCE. Profile reads props.user. Which HOC supplied
       it? You find out by reading the export chain bottom-up.
    4. REFS DO NOT PASS THROUGH. ref targets the wrapper, not Profile,
       so every HOC needs forwardRef plumbing to stay transparent.
    5. STATIC PROPERTIES ARE LOST unless you hoist them, which is why
       hoist-non-react-statics existed as a dependency.
    6. TYPES DEGRADE. Each layer must correctly subtract the props it
       injects; in practice one layer widens to any and the chain
       stops type-checking usefully.
What the HOC didWhat you write in React 18/19
withUser, withTheme — inject contextuseContext, usually behind a useUser() hook that throws outside its provider
withRouter — inject route datauseParams, useNavigate, useLocation
connect(mapState, mapDispatch)useSelector and useDispatch, or a store hook
withSubscription — external data sourceuseSyncExternalStore, or a query library's hook

Recognise HOCs in old code and understand them in interviews. Do not build new ones for application logic. The two survivors — memo and error-boundary wrappers — are both cases where the wrapper must exist as a real component in the tree, which is exactly when the pattern is correct.

Part 6 — Hooks Extract Logic; Composition Extracts Structure

Every duplication you find is one of two kinds, and getting the diagnosis right determines whether the abstraction helps or hurts.

  THE DIAGNOSTIC QUESTION:
  "If I delete the duplicated code, is what remains identical MARKUP
   or identical BEHAVIOUR?"

  IDENTICAL BEHAVIOUR, DIFFERENT MARKUP  -> CUSTOM HOOK
    Three screens each debounce a search box, call an endpoint, track
    loading and abort on unmount. The JSX differs entirely.
      const { data, loading } = useSearch(query);

  IDENTICAL MARKUP, DIFFERENT CONTENT    -> COMPOSITION
    Three screens each render a bordered panel with a title bar and a
    scrolling body. The logic differs entirely.
      <Panel title="…">{anything}</Panel>

  BOTH                                   -> BOTH, SEPARATELY
    A headless hook plus a presentational component that consumes it.
    This is the "headless UI" model: useCombobox() supplies behaviour
    and ARIA props; your markup supplies the look. Downshift, Radix
    primitives and TanStack Table all sell exactly this split.

  NEITHER                                -> LEAVE IT DUPLICATED
    Two components that merely LOOK similar today. Merging them creates
    a shared component with a boolean that forks its body — the
    prop-explosion seed from Part 1, planted deliberately.
Custom hookComposition (slots/children)
ExtractsStateful logic, effects, subscriptionsStructure, layout, wrapping
Appears in the React treeNo — it runs inside the caller's fiberYes — a real component boundary
Can own where markup rendersNoYes
Can bail out of re-rendering the callerNo — a state update in a hook re-renders its hostYes — a component boundary is what bounds a re-render (Part 3)
Testable in isolationYes, renderHook (see Testing)Yes, render it with fake children
Composes with othersTrivially — call bothBy nesting, which stays readable to about three levels
🔑 The performance corollary people miss: a custom hook cannot contain a re-render, but a component can. Moving useState into useDisclosure() changes nothing about what re-renders — the state still lives in the calling component, and the whole component still re-renders on every toggle. Moving it into a child component does, because a component boundary is where React can stop. When someone proposes "extract this to a hook for performance", the answer is that hooks are for readability; boundaries are for performance.

Part 7 — API Design: Controlled, Uncontrolled, Polymorphic — and Choosing

Two design decisions come up on nearly every reusable component, and both have a well-worn correct answer.

// A COMPONENT THAT SUPPORTS BOTH MODES — the platform's own convention
function Disclosure({ open, defaultOpen = false, onOpenChange, children }) {
  const [internal, setInternal] = useState(defaultOpen);

  // The mode is decided by whether `open` is undefined, and is fixed
  // for the component's lifetime — exactly like a DOM input.
  const isControlled = open !== undefined;
  const isOpen = isControlled ? open : internal;

  function set(next) {
    if (!isControlled) setInternal(next);   // ignored when controlled
    onOpenChange?.(next);                   // ALWAYS fired, both modes
  }

  return <section>{children(isOpen, () => set(!isOpen))}</section>;
}

  THE FOUR RULES THAT MAKE THIS CORRECT:

  1. `undefined` selects the mode. Not a separate `controlled` prop —
     that lets the two disagree.
  2. Fire onOpenChange in BOTH modes. Uncontrolled callers still want
     to know; omitting it forces them to control the component just to
     observe it.
  3. Never write to internal state while controlled. A useEffect that
     "syncs" open into internal produces a render with the old value
     then a second with the new one — a visible flicker, and a fight
     with the parent when it rejects the change.
  4. Warn in development if a component switches modes mid-life
     (open goes from undefined to a value). This is React's own
     "changing an uncontrolled input to be controlled" warning, and
     it is worth reproducing in your own components.
ModeWho owns the valueRight whenFailure if you pick wrong
Uncontrolled (defaultOpen)The componentNothing outside needs to read or set itThe parent cannot close it programmatically or read its state
Controlled (open + onOpenChange)The callerThe value is derived from, or must sync with, other state or the URLEvery caller writes the same three lines of boilerplate
Hybrid (both)Whichever the caller choseA library component, or anything with more than a handful of consumersNone — this is the default for shared components, and it is about six extra lines
Half-controlled (value, no change handler)Nobody, coherentlyNeverThe UI cannot respond to the user at all, and it looks broken
// POLYMORPHISM — one component, caller chooses the rendered element
function Text({ as: Tag = "span", ...props }) {
  return <Tag {...props} />;
}

<Text as="h1" className="title">Users</Text>
<Text as={Link} to="/users">Users</Text>

  WHY `as: Tag` IS RENAMED: JSX treats a lowercase name as a DOM tag
  and a Capitalised name as a component. A bare `as` would render a
  literal HTML element called "as", so destructuring to `Tag` is
  mandatory, not style.

  WHAT IT IS ACTUALLY FOR — and it is not "flexibility":
    - SEMANTICS. A styled heading must be able to be h1 on one page and
      h3 on another. Baking in h2 is an accessibility bug you cannot
      fix from the call site.
    - LINK vs BUTTON. The same visual button is an anchor when it
      navigates and a button when it acts. Keyboard behaviour, focus
      and the browser's context menu all differ, and users notice.

  WHAT IT COSTS:
    - Typing it properly needs generics plus
      ComponentPropsWithoutRef<T> and Omit of your own props; the
      naive version silently permits as="div" together with href.
    - Ref forwarding must be generic too, and generic forwardRef needs
      a cast or a wrapper type in TypeScript.
    - It is genuinely overkill below about three consumers. Two
      components beat one polymorphic component with one caller.

  ALTERNATIVE THAT IS OFTEN BETTER: asChild (Radix's approach) — merge
  your props onto the single child element the caller passed, instead
  of taking a component type. Composition again, one level down.

Interview Questions

Beginner: What is children, and what can it hold?

children is an ordinary prop. JSX gives it nesting syntax, so <Panel><p /></Panel> and <Panel children={<p />} /> compile to the same call. There is no special mechanism behind it — which is the point, because it means anything true of props is true of children.

It can hold an element, an array of elements, a string, a number, a fragment, null, undefined, a boolean, or a function. React renders strings and numbers as text and renders nothing for null, undefined and booleans. That last rule is why {isOpen && <Menu />} works, and also why {items.length && <List />} puts a literal 0 on the screen when the array is empty — 0 is a number, and numbers render.

A function child is the render-prop pattern: the component calls it and renders what comes back. That is not a separate feature either, just a component choosing to invoke a prop that happens to be a function.

Beginner: What is "composition over configuration" in a React component?

Configuration means the caller describes what it wants with data — booleans, enums, strings — and the component branches internally to produce markup. Composition means the caller hands over the markup itself and the component only decides where to put it.

The practical difference shows up in how each one grows. A configured component gains a prop per requirement, and those props multiply: sixteen booleans is sixty-five thousand nominal states, almost all of them meaningless and none of them prevented by the type system. A composed component gains nothing, because a new requirement is expressed in the element the caller passes.

The dividing line is what the prop describes. Props should describe data or a genuine axis of variation — size, variant, disabled. When a prop is really a piece of markup in disguise — headerIconColor, footerButtonLabel — that is the signal to open a slot instead.

Mid: Why does passing children from a parent help performance, and when does it not?

React decides whether to re-render a subtree by comparing the previous element at that position to the new one. JSX written inside a component body allocates a new element object on every render of that component, so the comparison always finds a difference and the subtree re-renders. JSX passed in as children was created by the parent, so while the parent is not re-rendering it is literally the same object, and React can skip the subtree.

The concrete pattern: a component owns fast-changing state (a search input) and also renders something expensive (a chart). Move the state into a small component and accept the chart as children. Twenty keystrokes then render the input twenty times and the chart zero extra times, with no memo, no useMemo and no dependency array.

It does not help when the parent itself re-renders — then it creates new children too, and everything is back to normal. It also does not help when the children depend on the fast-changing state, because then they genuinely must re-render; the pattern works precisely because the expensive subtree does not care about the state. And it is not a substitute for memo in a list, where each row's element is created fresh by the .map on every render.

The framing I would offer is that this is not a trick. It is the ordinary consequence of putting the state boundary in the right place, and the render saving is a side effect of a design that was already better.

Mid: When would you build a compound component instead of using props?

When the parts vary in number or order, and they need shared state. Tabs is the canonical case: a caller has an arbitrary number of tabs, wants to put a divider or a badge between them, and every tab needs to know whether it is the selected one. An items array cannot express arbitrary markup without accumulating renderLabel, renderPanel and a class name prop per region, which is Part 1's problem arriving by a different door.

The implementation is a context created by the parent and read by the parts, not Children.map with cloneElement. Cloning only reaches direct children, so it breaks the moment someone wraps a tab in a tooltip or a fragment — a real failure I have seen ship, because it works in the demo and fails in the application.

The costs are real and worth stating in an interview. The public API is much larger: every part is a name you support forever. Typing is harder — relating a tab's value to its panel's value needs generics, and attaching parts as static properties conflicts with forwardRef. Misuse fails at runtime, so you need an explicit context guard that throws a readable message. And every part re-renders when the context value changes unless you split state from dispatch.

So: Tabs, Accordion, Menu, Select, Table — yes. Card with a header and a footer — no, that is two element props, and the compound version is a context provider standing in for a slot.

Senior: Are render props and HOCs dead? Argue both sides.

For sharing stateful logic, effectively yes. Both existed because pre-2019 there was no way to reuse stateful behaviour without a component, and a component can only give you its output — so you either handed it a function to call (render prop) or wrapped the consumer (HOC). Hooks removed the constraint. A hook returns values as plain variables that destructure, feed dependency arrays and compose by being called twice, with no wrapper fiber and no nesting.

The HOC costs are not stylistic. Prop collisions are silent — two HOCs injecting match means the outer wins and nothing warns. Provenance is unclear: a component reads props.user and you find its source by reading the export chain backwards. Refs stop at the wrapper unless every layer forwards. Statics are lost without a hoisting library. And the types degrade, because each layer must subtract exactly the props it injects and in practice one layer widens.

But "dead" overstates it in two places. Function-as-children survives wherever the component owns rendering position rather than values — virtualisers calling the child once per visible row with a computed style, measurement wrappers, drag layers, table cell builders. No hook can express "render this markup at a position I compute during my own render", and every serious windowing library still uses the function-child form. And HOCs survive where the wrapper must genuinely exist in the tree: React.memo, forwardRef and error-boundary wrappers are all HOCs, and correctly so, because a boundary needs a real class component above the thing it protects.

My recommendation: default to hooks for logic and components with children for structure. Write a function child only when position is the thing being shared. Never write a new application-level HOC — a hook plus a wrapper component gets the same result without the ref, static and provenance problems. Do learn to read both, because a five-year-old codebase is full of them and the migration is usually mechanical.

Senior: Design the API for a Dialog used by forty teams. Walk through the trade-offs.

I would start by deciding what the component genuinely owns, because that is what determines what is a prop and what is a slot. A dialog owns focus trapping, the escape-key handler, scroll locking, the backdrop, portalling out of the layout, aria-modal, the labelling relationship, and restoring focus on close. It owns none of the content. So content is slots and the behaviours are props.

Shape: open, defaultOpen and onOpenChange as a hybrid controlled/uncontrolled trio, because at forty teams some dialogs are driven by a URL or a state machine and some are just a local toggle. undefined on open selects the mode, onOpenChange fires in both modes, and I warn in development if a dialog switches modes mid-life. Then title, children and footer as element slots. size as an enum, because that is a real axis with a small closed set.

What I would refuse: confirmLabel, onConfirm, cancelLabel, onCancel, showCancel, destructive. Those are one particular dialog — a confirmation — leaking into the general one. Instead I ship ConfirmDialog built on Dialog, with exactly those props. Teams get the convenient thing, and the primitive stays clean. This split is the single decision that keeps a shared component from becoming Part 1's sixteen booleans.

On compound versus slots: I would use slots. The regions are fixed at three, they always appear in the same order, and the compound version buys arbitrary ordering nobody wants at the cost of a context, a runtime failure mode and generic typing. I would reconsider only if a real need appeared for a fourth region or for nesting content between parts. The exception is Dialog.Close, which I would add as a compound part, because "close this dialog" is state a nested button genuinely needs and drilling a callback through the caller's markup is the exact prop-drilling that context exists for.

Two things I would insist on regardless. Every prop gets a documented default, and defaults are treated as breaking changes when they move — at forty consumers, changing a default is a change with an empty diff at every call site. And the component takes ...rest and a forwarded ref, so a team with an unanticipated need can reach the DOM node rather than filing a ticket. The escape hatch is what stops the prop list growing.

🏋️ Graded Exercises

1 (easy): Remove the flags. A component takes { title, showTitle, subtitle, showSubtitle, icon, iconColor, iconSize }. Redesign the API.
Solution 
// BEFORE — seven props, four illegal combinations, one render blob
<PanelHead title="Users" showTitle subtitle="12 active" showSubtitle
           icon="user" iconColor="blue" iconSize={16} />

// AFTER — one slot
function PanelHead({ children }) {
  return <div className="panel-head">{children}</div>;
}

<PanelHead>
  <UserIcon size={16} color="blue" />
  <h2>Users</h2>
  <small>12 active</small>
</PanelHead>

What the show* booleans actually were: a second encoding of information the data prop already carried. showTitle={false} with title="Users" is a representable state that renders nothing, and every bug report of the form "the title disappeared" is someone hitting it. Presence is the only signal you need.

Why iconColor and iconSize were the real smell: they are not axes of variation for PanelHead — it does not know what a colour means. They are props of UserIcon, forwarded through a component that has no opinion about them. Every forwarded prop like this is a maintenance obligation for a component that gains nothing from it.

What you give up, honestly: the component no longer guarantees a consistent header. If that guarantee matters — and in a design system it often does — the answer is named slots (icon, title, meta) rather than one children, so the layout stays owned while the content is free. Do not go back to booleans to get it.

2 (easy): This memo never skips a render. Explain why and fix it: const Card = memo(function Card({ children }) { … }), used as <Card><Row data={d} /></Card> inside a component with a counter.
Solution 
  WHY IT NEVER SKIPS

  memo does a shallow comparison of props. `children` is a prop. The
  parent's JSX creates a NEW element object for the Row on every one
  of its renders, so:

      prevProps.children === nextProps.children   ->  false

  every single time. memo is working correctly — it is detecting a
  changed prop, because the prop genuinely changed by identity.

// FIX A — hoist the element so the parent stops re-creating it
function Screen() {
  const [n, setN] = useState(0);
  const row = useMemo(() => <Row data={d} />, [d]);
  return <><button onClick={() => setN(n + 1)}>{n}</button>
           <Card>{row}</Card></>;
}

// FIX B (better) — move the state down so the parent stops re-rendering
function Screen() {
  return <><Counter /><Card><Row data={d} /></Card></>;
}
// Counter owns n. Screen never re-renders, so the Row element is
// never re-created, so Card is never asked to render at all — and the
// memo becomes unnecessary rather than merely working.
ApproachRenders savedOngoing cost
memo aloneNone — the compare fails every timeA comparison per render, for nothing
memo plus useMemo on the elementYesA dependency array to keep correct forever
Push state downYes, and the parent stops rendering entirelyNone — no memo, no deps

The general lesson: when memo "does not work", the answer is almost never a custom comparator. A comparator that ignores children is a lie about equality, and it will one day skip a render that mattered. Change where the element is created instead.

3 (medium): A search field re-renders a 5,000-point chart on every keystroke. The chart does not depend on the query. Fix it without memo or useMemo.
Solution 
// BEFORE — one component owns both the fast state and the slow tree
function Dashboard({ points }) {
  const [q, setQ] = useState("");
  return (
    <>
      <input value={q} onChange={e => setQ(e.target.value)} />
      <Results query={q} />
      <Chart points={points} />      // re-rendered per keystroke
    </>
  );
}

// AFTER — the state boundary moves inside; the slow tree moves outside
function SearchPane({ children }) {
  const [q, setQ] = useState("");
  return (
    <>
      <input value={q} onChange={e => setQ(e.target.value)} />
      <Results query={q} />
      {children}                     // element created by Dashboard
    </>
  );
}

function Dashboard({ points }) {
  return (
    <SearchPane>
      <Chart points={points} />      // created ONCE per Dashboard render
    </SearchPane>
  );
}

What happens at runtime: typing calls setQ, which schedules a render of SearchPane only. During that render children is the identical element object React already has from the previous commit, so reconciliation finds the same type and the same reference at that position and bails out of the subtree. Chart's function is never called. For a 20-character query that is 20 chart renders removed, and at 5,000 points those are the renders that were costing whole frames — anything over 16ms drops one at 60Hz.

Why this beats the memo version: memo(Chart) plus a stable points reference gets the same result, but it depends on two things staying true — the memo staying in place, and every future prop to Chart staying referentially stable. The composition version depends on nothing; a new prop cannot silently break it because there is no comparison to break.

The limitation to state honestly: this only works because Chart does not need q. If the chart must filter by the query, it has to re-render and the correct fix is a different one — useDeferredValue on the query so the chart lags the input by a frame instead of blocking it. Composition solves independence, not dependence.

4 (medium): Convert withAuth(Dashboard) — which redirects to /login when there is no user and injects user as a prop — away from the HOC.
Solution 
// BEFORE
function withAuth(Wrapped) {
  return function WithAuth(props) {

    const nav  = useNavigate();

function useUser() {
  const user = useContext(AuthCtx);
  if (user === undefined) throw new Error("useUser outside AuthProvider");
  return user;                       // null = signed out, object = signed in
}

  const user = useUser();
  const nav  = useNavigate();

  return children;
}

5 (hard): Build an Accordion as compound components: arbitrary items, one open at a time, and it must work both controlled and uncontrolled.
Solution 
const Ctx = createContext(null);
const use = part => {
  const c = useContext(Ctx);
  if (!c) throw new Error(`${part} must be used inside <Accordion>`);
  return c;
};

export function Accordion({ value, defaultValue = null,
                            onValueChange, children }) {
  const [internal, setInternal] = useState(defaultValue);
  const controlled = value !== undefined;
  const open = controlled ? value : internal;

  const toggle = useCallback(id => {
    const next = open === id ? null : id;      // click the open one to close
    if (!controlled) setInternal(next);
    onValueChange?.(next);
  }, [open, controlled, onValueChange]);

  const ctx = useMemo(() => ({ open, toggle }), [open, toggle]);
  return <Ctx.Provider value={ctx}>{children}</Ctx.Provider>;
}

Accordion.Item = function Item({ id, title, children }) {

What the uncontrolled path does at runtime when controlled: setInternal is never called, so internal stays at its initial value forever and is simply unread. What is still missing for production: arrow-key and Home/End navigation between headers, and an allowMultiple mode. 6 (hard): Three teams have each built a "table with sorting, selection and pagination" and all three want different markup. Design what you extract.
Solution 
  DIAGNOSIS FIRST (Part 6): what is actually duplicated?

    IDENTICAL BEHAVIOUR: sort comparator plus direction toggling, a
      selection Set with select-all and indeterminate logic, page
      maths, and keeping selection coherent across pages.
    DIFFERENT MARKUP: one is a data grid, one is a card list, one is a
      mobile stack that is not a table element at all.

  -> Logic duplication with no structural duplication. That is a HOOK,
     not a component. A shared DataTable would need markup props for
     every difference — the Part 1 failure, one year out.

// THE HEADLESS HOOK
function useDataTable({ rows, columns, pageSize = 25 }) {
  const [sort, setSort]       = useState(null);   // { key, dir }
  const [selected, setSelect] = useState(() => new Set());
  const [page, setPage]       = useState(0);

  const sorted = useMemo(() => {
    if (!sort) return rows;
    const col  = columns.find(c => c.key === sort.key);
    // toSorted, not sort — sort() mutates the caller's array in place
    const asc  = rows.toSorted(col.compare);
    return sort.dir === "asc" ? asc : asc.toReversed();
  }, [rows, sort, columns]);

  const pageRows = useMemo(
    () => sorted.slice(page * pageSize, (page + 1) * pageSize),
    [sorted, page, pageSize]);

  return {
    pageRows,
    pageCount: Math.ceil(sorted.length / pageSize),
    page, setPage, sort, selected,
    // Return PROP GETTERS, not raw handlers: the caller spreads them
    // onto whatever element it likes and cannot forget the ARIA.
    getHeaderProps: key => ({
      onClick: () => setSort(s =>
        s?.key === key ? { key, dir: s.dir === "asc" ? "desc" : "asc" }
                       : { key, dir: "asc" }),
      "aria-sort": sort?.key === key
        ? (sort.dir === "asc" ? "ascending" : "descending") : "none",
    }),
    getRowProps: id => ({
      "aria-selected": selected.has(id),
      onClick: () => setSelect(s => {
        const n = new Set(s);              // COPY — a mutated Set is the
        n.has(id) ? n.delete(id) : n.add(id);  // same reference, so React
        return n;                              // would bail out
      }),
    }),
    allOnPageSelected: pageRows.every(r => selected.has(r.id)),
  };
}

Why prop getters rather than raw values: returning sortKey and onSort makes every consumer wire up aria-sort themselves, and two of the three will forget. A getter bundles the handler with the ARIA attribute, so correct accessibility is the path of least resistance. This is the same reason Downshift and Radix return getters — the accessibility contract travels with the behaviour instead of living in a README.

Where the boundary should sit: the hook returns data and props, never elements. The moment it returns JSX it has an opinion about markup and the three teams start diverging again through a different prop. If two of the three later converge on identical markup, they can build a shared presentational component on top of the hook — that is the "both" case from Part 6, and it works because the two extractions are independent.

What I would actually do on a real team: adopt TanStack Table and spend the saved time on the shared presentational layer, because the hard part here is not the sorting maths — it is the selection semantics across pagination, filtering and refetch, which is where every hand-rolled version eventually grows a bug nobody can reproduce.

🎯 Key Takeaways

  • A prop should describe data or an axis of variation, never markup. When you are about to add headerIconColor, add a slot instead.
  • Sixteen booleans is 65,536 nominal states, most illegal and none prevented by the type system. Composition removes the states rather than documenting them.
  • children is an ordinary prop with JSX syntax sugar — <P>x</P> and <P children="x" /> compile identically.
  • Multiple named element slots are the under-used middle ground: the component keeps the layout opinion, the caller supplies every piece of content.
  • Pass an element when the caller configures it; pass a component when the receiver must inject props. icon={<Icon />} and icon={Icon} are different contracts.
  • Children created by a parent keep the same object identity across the child's re-renders, so React can skip the whole subtree with no memoization at all.
  • React.memo can never skip a component whose JSX children are written inline by its parent — the children prop changes identity every render, and memo is right to say so.
  • Push state down and lift expensive trees into children before reaching for useMemo — one is free forever, the other is a dependency array you maintain.
  • Compound components are for parts that vary in number or order and share state — Tabs, Menu, Select. Three fixed regions are three slots.
  • Build compound components on context, never cloneElement, which breaks the moment a consumer wraps a part in a tooltip or a fragment.
  • Memoize the context value and throw a named error when a part is used outside its parent — otherwise every consumer re-renders and misuse fails as "cannot read property of null".
  • Hooks share values; function-children share render position. That is why virtualisers still take a function child and almost nothing else does.
  • HOCs fell to silent prop collisions, lost refs and statics, unclear provenance and degrading types — memo, forwardRef and error boundaries are the legitimate survivors, because the wrapper must genuinely exist.
  • Custom hooks extract logic; components extract structure — and a hook cannot contain a re-render, because state in a hook still belongs to the calling component.
  • undefined selects controlled versus uncontrolled, and the change callback fires in both modes — never mirror a controlled prop into state with an effect.
  • The as prop exists for semantics, not flexibility — heading level and anchor-versus-button are accessibility decisions the call site owns, and it earns its typing cost at about three consumers.
