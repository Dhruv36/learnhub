SOLID & Clean Code Professional Java

What you'll master: SRP as "one actor to answer to" rather than "one method", and the shared private helper that makes a violation dangerous rather than merely untidy; OCP as polymorphism, with the honest counterpoint that a sealed type plus an exhaustive switch often beats it; LSP as behavioural substitutability — preconditions, postconditions, the history constraint, and the violation the JDK itself ships in Arrays.asList().add(); ISP and what default methods changed; DIP as a question of who owns the abstraction, which is what makes ports and adapters work; cohesion and coupling underneath all of it; the Clean Code heuristics and where that book overreaches; code smells with their refactorings; and when applying none of this is correct. Prerequisites: Interfaces.

Part 1 — SRP: One Reason to Change, One Actor

  THE DEFINITION EVERYONE MISQUOTES:

    "A class should do one thing."       ← unfalsifiable
    "A class should have one method."    ← not remotely
    "One reason to change."              ← Martin's original
    "Responsible to one, and only one,   ← Martin's own later
     ACTOR."                                clarification

  The last is the usable one, because "one reason to change" stays
  untestable until you ask WHO ASKS FOR THE CHANGE. Responsibility is
  a social fact, not a structural one.

  THE VIOLATION — one class, three bosses:

    class Payroll {
        BigDecimal computeNetPay(Employee e, Period p) {
            BigDecimal gross = e.rate().multiply(regularHours(e, p));
            return gross.subtract(tax(gross));
        }

        Report hoursReport(Employee e, Period p) {
            return new Report(regularHours(e, p), overtime(e, p));
        }

        void save(Employee e, BigDecimal net) throws SQLException {
            try (var st = conn.prepareStatement(
                    "INSERT INTO payslip(emp_id, net) VALUES (?,?)")) { ... }
        }

        private BigDecimal regularHours(Employee e, Period p) {
            return hoursWorked(e, p).min(new BigDecimal("40"));
        }
    }
MethodActor who requests changesChange trigger
computeNetPayFinance / the CFOTax rules, pension rates, overtime policy
hoursReportOperations / the COOWhat management wants to see this quarter
savePlatform / the DBASchema migrations, a store swap
regularHoursTwo of them, invisiblyEither — and neither knows about the other
  THE HARM IS NOT UNTIDINESS. IT IS THAT PRIVATE HELPER.

  Finance files "overtime now starts at 38 hours, not 40." You change
  the literal. Payroll is correct and its tests pass. THE COO'S HOURS
  REPORT ALSO CHANGED — untested, unreviewed, because the coupling was
  private and looked like an implementation detail.

  That is the real failure mode: a change one actor requested is
  DELIVERED TO A SECOND ACTOR who did not ask for it and will not
  notice until the numbers are wrong in a board pack. Merge conflicts
  and coupled deploys are the minor harms.

  THE FIX — SPLIT BY ACTOR, AND MAKE THE SHARED THING VISIBLE:

    Timesheet             the shared DATA — owns regular()/overtime()
    NetPayCalculator      finance owns the rules
    HoursReporter         operations owns the report shape
    PayslipRepository     platform owns the schema

  Moving regularHours onto a shared VALUE means changing it is now an
  explicit edit to a type both consumers reference, and both appear in
  its call hierarchy. That visibility is the whole refactoring.

  WHAT SRP DOES NOT MEAN:

  ❌ One public method per class — eight methods serving one actor
     over the same fields have ONE reason to change.
  ❌ A class per verb — six single-method classes sharing a mutable
     context are more coupled than the one they replaced.
  ❌ Splitting until nothing is left — the responsibilities move into
     the wiring, and the wiring becomes the file nobody understands.

  THE REVIEW TEST: name the human who files the ticket for each
  method. Two names with two budgets means two classes. One name
  means leave it alone, however long the class is.

Part 2 — OCP: Extension Without Modification, and When That Is Premature

  MEYER, 1988: "open for extension, closed for modification." Meyer
  meant inheritance. Martin's reading is the keeper: NEW BEHAVIOUR
  ARRIVES AS A NEW TYPE, NOT A NEW BRANCH IN AN OLD METHOD.

  THE VIOLATION — the switch that grows:

    BigDecimal fee(Payment p) {
        switch (p.type()) {
            case CARD: return p.amount().multiply(new BigDecimal("0.029"));
            case ACH:  return new BigDecimal("0.25");
            case WIRE: return new BigDecimal("15.00");
        }
        throw new IllegalArgumentException("unknown: " + p.type());
    }

  The switch is never alone. The same enum drives settlementDelay(p),
  refundable(p), reconciliationAccount(p) and the CSV exporter. Adding
  CRYPTO means finding all five — SHOTGUN SURGERY — and the one you
  miss throws in production, or falls into a default: branch and
  returns a plausible wrong number.

  THE POLYMORPHIC FORM — behaviour travels with the type:

    interface PaymentMethod {
        BigDecimal fee(Money amount);
        Duration   settlementDelay();
        boolean    refundable();
    }

    record Card(Brand brand) implements PaymentMethod {
        public BigDecimal fee(Money a)  { return a.times("0.029"); }
        public Duration settlementDelay() { return Duration.ofDays(2); }
        public boolean refundable()     { return true; }
    }

  Adding Crypto is one new file, zero edits to tested code, and the
  compiler makes you answer all three questions at once. Real payoff.
  Now the part most treatments omit.

  THE HONEST COUNTERPOINT

  1. OCP IS A BET ON THE AXIS OF VARIATION. You declared that payment
     TYPE varies. If the change that arrives is "every fee now needs a
     jurisdiction argument", you edit the interface and all N
     implementations — N files where the switch cost 1. An abstraction
     protects the axis you chose and makes every other axis worse.

  2. THE COST IS PAID NOW, THE BENEFIT MAYBE NEVER. Interface, N
     records, a factory to choose between them, wiring. Answering
     "what does a card cost?" now takes three files instead of a
     scroll to a case label.

  3. TWO CASES IS NOT EVIDENCE. Write the switch. On the THIRD case
     the shape of the variation is visible and the refactor is
     mechanical. Waiting is cheap; guessing wrong is not.

  MODERN JAVA INVERTS THE ADVICE FOR CLOSED SETS:

    sealed interface Payment permits Card, Ach, Wire { }

    BigDecimal fee(Payment p) {
        return switch (p) {                    // no default branch
            case Card c -> c.amount().multiply(RATE);
            case Ach  a -> FLAT_25;
            case Wire w -> FLAT_15;
        };
    }

  Add Crypto to the permits clause and EVERY exhaustive switch fails
  to compile until handled. That is not OCP — it is deliberately
  closed — but it turns shotgun surgery into a compiler-generated
  worklist.
Polymorphism (classic OCP)Sealed type + exhaustive switch
Adding a typeOne new file, no editsCompile error at every switch — a guided checklist
Adding an operationEdit the interface and every implementationOne method, one place
Missing a caseSilently inherits a default — ships wrongWill not compile
Who may extendAnyone, including code you never seeOnly the owning module
Choose it whenThe type set is open: plugins, third-party strategiesThe type set is closed and yours: order states, AST nodes

That is the expression problem, and it is the honest reason SOLID cannot be a checklist: OCP optimises one direction of growth at the direct expense of the other. Pick the direction your code actually grows in.

Part 3 — LSP: Behavioural Substitutability

  LISKOV, 1987, paraphrased: if S is a subtype of T, objects of type T
  may be replaced by objects of type S WITHOUT ALTERING ANY DESIRABLE
  PROPERTY OF THE PROGRAM.

  THE LOAD-BEARING WORD IS "PROPERTY", NOT "SIGNATURE". javac checks
  parameter types, return type and checked exceptions. NOTHING checks
  behaviour except your callers, at runtime. That gap is the subject.
RuleMeaningTypical violation
Preconditions may be weakened, never strengthenedThe subtype accepts everything the supertype accepted, possibly moreAn override that adds a null or range check
Postconditions may be strengthened, never weakenedThe subtype promises everything the supertype promised, possibly moreReturning unsorted where the base documented "sorted"
Invariants must be preservedWhat is always true of the supertype stays trueA subclass letting a balance go negative
History constraintNo state transitions the supertype forbidsSquare.setWidth also changing the height
Exceptions must not broadenNo new types outside the declared hierarchyUnsupportedOperationException from an implemented method
  THE CANONICAL CASE:

    class Rectangle {
        protected int w, h;
        void setWidth(int w)  { this.w = w; }
        void setHeight(int h) { this.h = h; }
        int  area()           { return w * h; }
    }

    class Square extends Rectangle {
        @Override void setWidth(int w)  { this.w = w; this.h = w; }
        @Override void setHeight(int h) { this.w = h; this.h = h; }
    }

  THE CLIENT THAT BREAKS NEVER MENTIONS Square:

    void stretch(Rectangle r) {
        r.setWidth(5);
        r.setHeight(4);
        assert r.area() == 20;          // 16 when r is a Square
    }

  GEOMETRY IS NOT THE PROBLEM — a square really is a rectangle. The
  problem is that MUTABLE Rectangle carries an invariant Square cannot
  honour: "setWidth does not change the height." That invariant is
  written nowhere; it lives in the head of every caller, which is
  exactly why the violation survives code review.

  Formally it is a HISTORY-CONSTRAINT violation. Make both immutable
  and it evaporates:

    record Rectangle(int w, int h) { int area() { return w * h; } }
    record Square(int side) { }

  MOST LSP VIOLATIONS IN THE WILD ARE MUTABILITY PROBLEMS WEARING AN
  INHERITANCE COSTUME.

  STRENGTHENED PRECONDITION — the subtype accepts LESS:

    class Validator {
        void check(String s) { if (s != null) validate(s); }   // null OK
    }
    class StrictValidator extends Validator {
        @Override void check(String s) {
            if (s == null) throw new IllegalArgumentException();   // ❌
            validate(s);
        }
    }

  A caller written against Validator legitimately passes null. Swap
  the implementation and it throws, and the stack trace blames the
  caller rather than the subclass that broke the deal.

  WEAKENED POSTCONDITION — the subtype promises LESS:

    /** @return orders, most recent first. */
    List<Order> findAll();                          // the contract

    class CachedOrderRepo extends OrderRepo {
        @Override List<Order> findAll() {
            return new ArrayList<>(cache.values());  // ❌ HashMap order
        }
    }

  Pagination built on "most recent first" now duplicates rows on page
  2 and silently drops others. POSTCONDITION VIOLATIONS ARE THE WORST
  CLASS: they do not throw, they return wrong answers that look right.

  THE VIOLATION THE JDK ITSELF SHIPS:

    List<String> l = Arrays.asList("a", "b");
    l.set(0, "z");     // works — writes THROUGH to the backing array
    l.add("c");        // UnsupportedOperationException
    List.of("a").set(0, "z");    // UnsupportedOperationException too

  add is declared on List. A method taking List<String> and calling
  add is type-correct and still explodes depending on who built the
  argument — a substitutability failure in the standard library, on
  the most-used interface in Java. The Javadoc legalises it with the
  words "optional operation": the contract weakened until the
  violation became permitted.

  TWO THINGS FOLLOW:

  1. PRACTICAL: never mutate a collection you did not construct. Copy
     with new ArrayList<>(incoming); return List.copyOf(x).
  2. DESIGN: THE ROOT CAUSE IS AN ISP FAILURE. Collection bundles read
     and write into one interface, so read-only implementations have
     nowhere to live except UnsupportedOperationException. A separate
     immutable type would have been LSP-clean; the JDK could not add
     one in 1998 without splitting the hierarchy, and cannot now
     without breaking every program ever written.

  THREE MORE JDK CASES WORTH RECOGNISING ON SIGHT:

    unmodifiableList(x)     a VIEW, not a copy — mutate x and the
                            "unmodifiable" list changes underneath
    Timestamp extends Date  equals is NOT symmetric, which breaks
                            List.contains and every hash collection
    Stack extends Vector    you can insert at index 3 of a stack

  Each is inheritance used for implementation reuse where composition
  was wanted. THAT is the pattern: if a subtype must disable, ignore
  or reinterpret something the supertype promised, it is not a
  subtype — it is a collaborator.

Part 4 — ISP: Fat Interfaces and What default Methods Changed

  "CLIENTS SHOULD NOT BE FORCED TO DEPEND ON METHODS THEY DO NOT USE."
  Note CLIENTS — ISP is stated from the caller's side. The cost of a
  fat interface is paid by everyone who compiles against it.

  THE FAT INTERFACE:

    interface PaymentGateway {
        Charge       charge(Money m, Card c);
        Refund       refund(ChargeId id, Money m);
        Subscription subscribe(Plan p, Card c);
        Token        tokenize(Card c);
        Payout       payout(BankAccount a, Money m);
    }

    class SimpleGateway implements PaymentGateway {
        public Charge charge(Money m, Card c) { ... }
        public Subscription subscribe(Plan p, Card c) {
            throw new UnsupportedOperationException();      // ❌
        }
        // ...three more of those
    }

  TWO DISTINCT FAILURES IN ONE PIECE OF CODE:

  - ISP: SimpleGateway compiles against, and appears to offer, four
    capabilities it does not have.
  - LSP: any holder of a PaymentGateway may call subscribe() and get
    an exception. UnsupportedOperationException IS ALMOST ALWAYS AN
    ISP VIOLATION ANNOUNCING ITSELF AS AN LSP FAILURE — when you write
    one, go looking for the interface that is too wide.

  THE SPLIT, BY CLIENT NEED:

    interface Charging    { Charge charge(Money m, Card c); }
    interface Refunding   { Refund refund(ChargeId id, Money m); }
    interface Subscribing { Subscription subscribe(Plan p, Card c); }

    class StripeGateway implements Charging, Refunding, Subscribing { }
    class SimpleGateway implements Charging { }

    class Checkout {
        Checkout(Charging gateway) { ... }     // declares what it needs
    }

  A missing capability is now a COMPILE ERROR AT THE WIRING, not a
  production exception. Checkout cannot start a subscription by
  accident, because the type it holds has no such method.

  ISP APPLIES TO PARAMETER TYPES, WHICH IS WHERE YOU USE IT DAILY:

    void render(ArrayList<Row> rows)    // demands a class
    void render(List<Row> rows)         // better
    void render(Iterable<Row> rows)     // exactly what a for-each needs

  Declare the narrowest type that supports what the body actually
  does. Costs nothing, widens what callers may pass, and documents the
  real requirement in the signature.

  WHAT default METHODS CHANGED

  BEFORE JAVA 8, adding a method to a published interface broke every
  implementation on earth at compile time. Interfaces stayed small
  partly for ISP and largely for BINARY COMPATIBILITY. The workaround
  was the adapter class, and the JDK is full of the evidence:

    interface MouseListener    5 abstract methods
    class MouseAdapter         all 5, implemented empty

  You extended the adapter and overrode the one you cared about — ISP
  solved by inheritance, at the cost of your one inheritance slot.

  JAVA 8 REMOVED THE COMPATIBILITY PRESSURE:

    Collection.stream()        default, via spliterator()
    Collection.removeIf(p)     default, via iterator().remove()
    Iterable.forEach(a)        default, via iterator()
    Comparator.reversed()      default, via compare()

  Collection gained four methods in one release and nothing on earth
  failed to compile.

  THE TRADE-OFF MOVED; IT DID NOT DISAPPEAR:

  ✓ A LEGITIMATE default has a CORRECT UNIVERSAL implementation
    written in terms of the interface's own abstract methods. forEach
    cannot be wrong for any Iterable. Override it for speed, never
    for correctness.

  ❌ default Subscription subscribe(Plan p, Card c) {
         throw new UnsupportedOperationException();
     }
    This does not fix the fat interface. It DELETES THE COMPILE ERROR
    THAT WAS REPORTING IT and reschedules the failure for runtime —
    strictly worse than before Java 8, when the implementer was at
    least forced to look.

  ❌ Worse: a default returning a plausible wrong value (empty list,
    false, null). Silence instead of a stack trace, in a money path.

  MODERN GUIDANCE: interfaces may be wider than 2008 dogma allowed,
  PROVIDED everything past the core few methods is a default written
  in terms of those few. THE ABSTRACT SURFACE — what an implementer is
  forced to write — is what ISP actually counts. Comparator has over
  twenty methods, one abstract, and nobody calls it fat.

Part 5 — DIP: Who Owns the Abstraction

  "HIGH-LEVEL MODULES SHOULD NOT DEPEND ON LOW-LEVEL MODULES. BOTH
  SHOULD DEPEND ON ABSTRACTIONS. ABSTRACTIONS SHOULD NOT DEPEND ON
  DETAILS; DETAILS SHOULD DEPEND ON ABSTRACTIONS."

  Everyone remembers the first sentence and implements it as "put an
  interface in front of it". THAT IS NOT DIP. The principle is about
  WHO OWNS THE ABSTRACTION, and the second sentence is where that
  lives.

  NOT INVERTED — an interface that changed nothing:

    package com.acme.persistence;

    public interface OrderDao {                 // lives WITH the detail
        ResultSet selectByCustomer(long id) throws SQLException;
        void      insert(Order o) throws SQLException;
        void      flush();
    }

    package com.acme.orders;
    class OrderService {
        private final OrderDao dao;             // "an abstraction!"
    }

  COUNT THE DEPENDENCIES HONESTLY:

  - com.acme.orders imports com.acme.persistence, so the high-level
    module still depends on the low-level one. Arrow unchanged.
  - The interface speaks SQL — ResultSet, SQLException, flush() — so
    the abstraction depends on the detail, which the second sentence
    explicitly forbids.
  - Swap to a document store and the interface changes, so
    OrderService changes. The indirection bought nothing.

  This is the most common "we follow SOLID" artefact in a Java
  codebase, and it is usually produced by the IDE's Extract Interface
  refactoring — which by construction mirrors the implementation.

  INVERTED — the CONSUMER declares the interface it needs:

    package com.acme.orders;                 // the HIGH-LEVEL module

    public interface OrderRepository {       // OWNED BY THE CONSUMER
        Optional<Order> findById(OrderId id);
        List<Order>     findOpenFor(CustomerId c);
        void            save(Order o);
    }

    package com.acme.orders.jdbc;            // the LOW-LEVEL module
    class JdbcOrderRepository implements OrderRepository {
        // knows DataSource and SQL; translates SQLException into
        // the domain's vocabulary at the boundary
    }

  NOW LOOK AT THE TWO ARROWS SEPARATELY:

    CALL DIRECTION      orders  ──────────▶  orders.jdbc
    SOURCE DEPENDENCY   orders  ◀──────────  orders.jdbc

  At runtime the service calls the adapter. At compile time the
  adapter depends on the service's package and the service depends on
  nothing. THAT OPPOSITION IS THE "INVERSION" IN THE NAME. Both arrows
  the same way means you have an interface, not DIP.

  THREE CHECKS THAT ARE HARD TO FAKE:

  1. VOCABULARY. Does the interface mention ResultSet, HttpResponse,
     ConsumerRecord or SQLException? If the domain must import the
     driver's types to compile, the abstraction leaks the detail.
  2. DELETION. Could you delete the adapter package and still compile
     the domain? In Maven this is enforceable rather than
     aspirational: the domain module does not declare the driver as a
     dependency, and the build fails if anyone imports it.
  3. ORIGIN. Designed from the CALL SITE, or extracted from the impl?
     The method set should be what the service needs — often three
     methods where the DAO had thirty.

  THIS IS WHAT MAKES PORTS AND ADAPTERS WORK:

    ┌────────────────────────────────────────────────┐
    │           com.acme.orders  (the core)          │
    │   Order, OrderId, PricingRules, OrderService   │
    │   interface OrderRepository   ← PORT (owned)   │
    │   interface PaymentGateway    ← PORT (owned)   │
    │   depends on: nothing outside the JDK          │
    └───────▲──────────────────────────▲─────────────┘
            │ implements               │ implements
    ┌───────┴─────────┐       ┌────────┴──────────┐
    │ orders.jdbc     │       │ orders.stripe     │
    │ DataSource, SQL │       │ HTTP, JSON        │
    └─────────────────┘       └───────────────────┘

  A "port" is just an interface the core owns and the outside world
  implements. Everything else in hexagonal architecture follows from
  the ownership rule.

  THE DIVIDEND IS MEASURABLE, AND IT IS TEST SPEED:

    class InMemoryOrderRepository implements OrderRepository {
        private final Map<OrderId, Order> store = new HashMap<>();
        public Optional<Order> findById(OrderId id) {
            return Optional.ofNullable(store.get(id));
        }
        public void save(Order o) { store.put(o.id(), o); }
        ...
    }

  Fifteen lines, no database. A domain suite running in ~400 ms
  instead of 40 s of context startup per test class is the difference
  between tests you run on every save and tests you run in CI and
  hope about.

  WHERE DIP IS NOT WORTH IT:

  - Types that do not vary and are trivially constructible:
    BigDecimal, LocalDate, your own value objects. Nobody needs IMoney.
  - Stable JDK abstractions that already exist. Inject Clock, Random
    or Path directly — Clock is already the seam for testing time.
  - A boundary you will never cross and cannot test faster for. The
    two things that justify a port are A REAL SECOND IMPLEMENTATION
    and A FAST TEST DOUBLE. Neither present means you have a naming
    convention, not an architecture.

Who designed the method set?Extract Interface on the implThe call site, before an impl existed
What vocabulary does it use?ResultSet, SQLException, flush()Order, OrderId, save

Part 6 — Cohesion, Coupling, and the Clean Code Heuristics

  SOLID IS NOT THE GOAL. It is five heuristics aimed at two properties
  named twenty years earlier by Constantine and Yourdon:

    HIGH COHESION   the things inside a module belong together
    LOW COUPLING    modules know as little about each other as possible

  WHEN A LETTER OF THE ACRONYM AND THESE TWO DISAGREE, FOLLOW THESE
  TWO. "Split it because SRP" that lowers cohesion and raises coupling
  is a worse design that passes the checklist — the exact failure mode
  of teaching SOLID as rules.
Cohesion (worst → best)What holds the module togetherJava smell
CoincidentalNothing — it accumulatedUtils, Helper, Common
LogicalSame category, selected by a flaghandle(int eventType) with a switch
TemporalThey run at the same timeStartupTasks, ShutdownHooks
ProceduralThey run in a fixed orderA pipeline class of unrelated steps
CommunicationalThey act on the same dataAcceptable — often a real entity
FunctionalAll serve one well-defined jobThe target: NetPayCalculator
Coupling (worst → best)What one module knowsJava example
ContentReaches into another's internalsReflection on private fields; a subclass mutating protected state
CommonShared global mutable statestatic mutable fields, a singleton registry
ControlPasses a flag that steers the calleerender(page, true)
StampPasses a whole object to use one fieldaudit(Order o) reading only o.id()
DataPasses exactly the values neededaudit(OrderId id)

Mapped back, the acronym stops being arbitrary: SRP and ISP are cohesion tools, DIP and OCP are coupling tools, and LSP is what stops the polymorphism both rely on from lying to you. Argue cohesion and coupling directly and you never need to cite a letter.

  NAMING:

    boolean flag;           →  boolean eligibleForRefund;
    List<Data> list2;       →  List<LineItem> unpricedItems;
    void process(Order o);  →  void submitForFulfilment(Order o);
    int d;  // elapsed days →  int elapsedDays;   (delete the comment)

  - NAME BY INTENTION, NOT IMPLEMENTATION. sortedByPrice is a promise;
    bubbleSorted leaks a decision you will change.
  - Booleans read as predicates: isEmpty, hasExpired, canRefund.
  - NO TYPE ENCODINGS: no strName, no m_count, no IUserService.
  - LENGTH SCALES WITH SCOPE. `i` is right in a three-line loop; a
    long-lived field earns a long name. The inverse reads badly.
  - IF YOU CANNOT NAME A CLASS YOU PROBABLY DO NOT KNOW WHAT IT IS.
    Manager, Processor, Handler and Data mean "I gave up".

  FUNCTION LENGTH — THE HEURISTIC, AND WHERE THE BOOK OVERREACHES.

  Clean Code says functions are "hardly ever 20 lines" and its own
  examples run to two to four. That goes too far, and the reason is
  reading cost, not taste:

    // ONE LINEAR FLOW, 35 lines, no branching, read top to bottom
    void settleBatch(Batch b) {
        ...load...  ...validate...  ...price...  ...post...  ...notify...
    }

    // "CLEANED UP" INTO ELEVEN 3-LINE METHODS
    void settleBatch(Batch b) {
        var loaded = load(b);
        var valid  = validate(loaded);
        post(price(valid));
    }

  The second is better ONLY IF the extracted names carry more
  information than the code they hide. When they do not, you replaced
  one page read top to bottom with a call graph you must navigate —
  and the state those steps shared gets smuggled through FIELDS
  because the extracted methods needed it. THAT SYMPTOM IS THE TELL: a
  class growing mutable fields to pass data between its own private
  methods has traded a long function for a thread-unsafe object.

  EXTRACT FOR A REASON, NOT A LINE COUNT:
    ✓ the fragment has a name more meaningful than its body
    ✓ it is reused, or you want to test it directly
    ✓ the function MIXES ABSTRACTION LEVELS — business rules beside
      string formatting beside JDBC (the strongest signal)
    ❌ "it is over 30 lines"

  ARGUMENT COUNT:

    0–2  fine        3  look hard at it        4+  a type is missing

  AND THE SPECIFIC JAVA HAZARD:

    void transfer(String from, String to, BigDecimal amount)
    transfer(to, from, amount);     // compiles. wires money backwards.

  Domain types fix the amount/account confusion but NOT this one —
  transfer(AccountId, AccountId, Money) still compiles transposed. So
  where correctness is expensive, make the call site name things:
  Transfer.from(a).to(b).amount(m). The goal is not fewer arguments;
  it is that ORDER STOPS BEING LOAD-BEARING.

  BOOLEAN FLAG PARAMETERS ARE ALWAYS TWO FUNCTIONS:

    render(page, true);        // true means what?
    →  renderForPrint(page);   renderForScreen(page);

  The body opens with an if whose branches share almost nothing, and
  no call site is readable without opening the signature.

  COMMENTS — WHY, NEVER WHAT:

    // ❌ restates the code; lies the moment the code moves
    i++;                         // increment i

    // ✓ unrecoverable from the code at any price
    // Retry three times: the gateway returns 502 for roughly a second
    // after their blue/green flip. Vendor-confirmed, INC-4471. Do not
    // lower without re-testing across a deploy.
    private static final int RETRIES = 3;

    // ✓ records a REJECTED alternative so nobody "fixes" it
    // Deliberately a List, not a Set: the audit export requires
    // duplicate line items to be preserved.

  "EVERY COMMENT IS A FAILURE TO EXPRESS YOURSELF IN CODE" is true of
  comments that RESTATE code, and gets misapplied to comments that
  record DECISIONS. A method name cannot hold a ticket number, a
  vendor bug, a spec citation, or the reason you did not do the
  obvious thing. Delete the noise; keep the archaeology.

  JAVADOC IS A DIFFERENT ARTEFACT. On a public API, @param / @return /
  @throws ARE the contract — the pre- and postconditions of Part 3.
  "Optional operation" in List.add's Javadoc is the only thing between
  a caller and an UnsupportedOperationException.
Heuristic as usually statedWhat is actually true
"Functions should be 2–4 lines"Extract when a fragment earns a better name, is reused, or mixes abstraction levels. Line count is a symptom, not a cause.
"Comments are always failures"Never restate code; always record decisions, constraints and rejected alternatives.
"No more than three arguments"Sound — and the fix is a missing type, not moving values into fields to lower the count.
"Don't repeat yourself"Two similar lines are not duplication; two copies of the same decision are.
"One level of abstraction per function"The most valuable rule in the book, and the least quoted.

  WHEN NOT TO APPLY ANY OF THIS

  1. SCRIPTS AND ONE-OFFS. A 60-line migration that runs once and is
     deleted next week. SOLID's payoff is amortised over FUTURE
     CHANGES, and there are none. A main method with four helpers is
     the correct design.

  2. PROTOTYPES AND SPIKES. The purpose is to answer a question, not
     to survive. The danger is not the design — it is that a
     well-structured prototype LOOKS shippable and gets shipped, with
     its unhandled errors and hardcoded credentials intact.

  3. THE ONE-IMPLEMENTATION INTERFACE.

       interface UserService { }
       class UserServiceImpl implements UserService { }

     Zero polymorphism, two files, and every "go to definition" lands
     on an empty method. Both defences are dead:
       "We might swap it."  You will not; and if you do, Extract
         Interface is a five-second refactor THEN, designed against a
         real second implementation instead of a guess.
       "We need it to mock."  Mockito has mocked concrete classes for
         over a decade, and the inline mock maker — default since
         Mockito 5 — handles final classes and methods too.

     KEEP IT WHEN: two or more implementations exist; it is a PORT
     owned by the consumer across a module boundary (Part 5); or it
     is published API where committing to a class is a compatibility
     decision you cannot reverse.

  4. THE FACTORY THAT MAKES ONE THING.

       class UserFactory { User create(String n) { return new User(n); } }

     `new` is already a factory, and every Java programmer can read
     it. A factory earns its place when construction is CONDITIONAL,
     EXPENSIVE and pooled, requires VALIDATION that must not be
     bypassed (use a static factory method on the type), or must
     return a subtype the caller must not name.

  5. THE COST OF THE WRONG ABSTRACTION. Metz's formulation is the most
     useful sentence here: DUPLICATION IS FAR CHEAPER THAN THE WRONG
     ABSTRACTION.

       duplication         visible, greppable, deletable; bounded cost
       wrong abstraction   fifteen call sites depend on it; case
                           sixteen does not fit, so someone adds a
                           boolean, then another, and within a year
                           it is a maze of flags nobody dares touch

     The asymmetry that matters is the EXIT COST: removing duplication
     is a refactor, while removing a wrong abstraction means inlining
     it at every call site first — which nobody schedules, so it
     stays. Write it, duplicate it, and on the THIRD occurrence look
     at all three and abstract what they genuinely share.

  6. THE READING TAX IS PAID DAILY; THE EXTENSION DIVIDEND MAY NEVER
     ARRIVE. Every layer of indirection costs every future reader a
     jump, forever — a recurring cost charged against a speculative
     one-off benefit. Priced that way, most speculative abstractions
     stop looking free.

Interview Questions

Beginner: What does the Single Responsibility Principle actually say, and what is the usual misreading?

The usual misreading is "a class should do one thing", which is unfalsifiable — a class that saves an order does one thing at some level of description, and so does an entire application. Martin's own clarification is the usable version: a module should be responsible to one, and only one, actor. A reason to change is a person who asks for the change.

So the test is social, not structural. Take each method and name the human who files the ticket. A payroll class where computeNetPay answers to finance, hoursReport answers to operations, and save answers to the DBA has three actors and should be three classes.

What makes it matter is the shared private helper. If both the pay calculation and the hours report call a private regularHours(), a change finance requested — "overtime starts at 38 hours now" — silently changes a report operations owns, and nobody tests it because nobody knew the coupling existed.

The inverse misreading costs just as much. SRP does not mean one method per class: eight methods serving the same actor over the same fields have exactly one reason to change. Splitting them yields single-method classes coordinating through shared mutable state, which is strictly more coupled than what you started with.

Beginner: What is the Liskov Substitution Principle, and can you give a real example?

If S is a subtype of T, code written against T must keep working when handed an S. The important word is behaviour — the compiler already checks signatures, so LSP is entirely about promises signatures cannot express.

The textbook case is Square extends Rectangle with setters: a client calls setWidth(5); setHeight(4); and expects area 20, and a square gives 16. Geometry is not the issue. The issue is that mutable Rectangle carries an unwritten invariant — "setting the width does not change the height" — that Square cannot honour. Make both immutable records and the problem disappears, which tells you the real culprit was mutability.

The example worth quoting is in the JDK. Arrays.asList("a","b").add("c") throws UnsupportedOperationException, and everything mutating on List.of(...) does too. add is declared on List, so a method taking a List and calling add is type-correct and still crashes depending on who built the argument. The Javadoc legalises it with the words "optional operation" — the contract weakened until the violation became permitted.

Two rules fall out: never mutate a collection you did not construct, and treat every UnsupportedOperationException you write as evidence that an interface is too wide.

Mid: You see interface UserService with exactly one implementation, UserServiceImpl. Is that a problem?

Usually yes, and it helps to be specific about the cost rather than just calling it unnecessary. You pay for two files instead of one, a name that had to be invented (Impl means "the one that does it", which is no information), and a permanent navigation tax: every "go to definition" lands on an empty method, so every reader takes two jumps to reach real code.

Both traditional defences are dead. "We might swap the implementation" is a guess made a year before the evidence; Extract Interface is a five-second refactor at the moment a real second implementation exists, and the interface you design then — with two concrete cases in front of you — will be better than the one you guess now. "We need it to mock" has been false since Mockito could subclass concrete classes, and the inline mock maker, default since Mockito 5, handles final classes and methods as well.

Keep the interface whenBecause
Two or more real implementations existThat is polymorphism, which is what interfaces are for
It is a port owned by the consumerIt inverts a module dependency and enables fast in-memory test doubles
It is published API for other teamsCommitting to a concrete class is a compatibility decision you cannot reverse

The second row is not "an interface" in the same sense at all, and the naming gives it away: the port lives in the consumer's package in the consumer's vocabulary. OrderRepository implemented by JdbcOrderRepository is a port; OrderService implemented by OrderServiceImpl is a habit.

Mid: Is Dependency Inversion the same thing as Dependency Injection?

No, and conflating them is why so many codebases have injection everywhere and inversion nowhere. Injection is a mechanism — a class receives its collaborators rather than constructing them. Inversion is a direction — which module owns the abstraction, and therefore which way the compile-time arrow points.

You can inject without inverting. If OrderService takes an OrderDao in its constructor, but OrderDao lives in the persistence package and its methods return ResultSet and throw SQLException, the high-level module still imports the low-level one and the abstraction still depends on the detail. That breaks both sentences of the principle while looking exactly like textbook DI.

You can also invert with no framework at all: declare OrderRepository in the domain package in domain vocabulary, implement it in orders.jdbc, and wire it with new in main. No container, full inversion.

The review test has nothing to do with annotations: could you delete the adapter package and still compile the domain? In Maven that is enforceable rather than aspirational — the domain module does not declare the JDBC driver, so the build fails if anyone imports it. A build file is a more reliable architecture reviewer than a human.

The payoff is concrete: domain tests needing no database and no application context. A suite that runs in a few hundred milliseconds gets run on every save; one that spends 40 seconds starting a context per class gets run in CI and hoped about.

Senior: Open/Closed via polymorphism, or a sealed interface with an exhaustive switch? Argue both and recommend.

This is the expression problem, and the honest answer is that the two optimise opposite directions of growth — so the question is empirical: which direction does this code actually grow in?

PolymorphismSealed + switch
New typeOne file, zero editsCompile error at every switch — a guided worklist
New operationEdit the interface and all N implementationsOne method, one place
Missing caseSilently inherits a defaultWill not compile
Who may extendAnyone, including code you never seeOnly the owning module

The case for polymorphism is that behaviour lives with data and adding a type touches nothing tested. Its real weakness is exhaustiveness: nothing tells you that Crypto forgot to override settlementDelay(), so it inherits a default that is wrong and ships silently — a much harder failure to find than a compile error.

The case for sealed types is that the compiler enumerates the work. Adding a payment method breaks the build at all five places you must update, converting shotgun surgery into a checklist. The price is that the set is closed to external modules, and that behaviour lives away from its data.

Recommendation: if you own the full set of types and it is genuinely closed — order states, payment methods, AST nodes, protocol messages — use a sealed interface with exhaustive switches. Compiler-enforced completeness is worth more than the ability to add a case without editing. Reserve polymorphic OCP for genuinely open sets: plugins, third-party strategies, anything other teams extend. In both cases wait for the third variation before abstracting at all — two cases tell you nothing about the axis of change, and an abstraction on the wrong axis makes the change you eventually get more expensive.

Senior: When would you deliberately not apply SOLID, and how do you defend that in review?

First I would reframe what is being defended. SOLID is five heuristics for two older properties: high cohesion and low coupling. If I can show a design has better cohesion and lower coupling than the "SOLID" alternative, I have won on the merits, and quoting a letter of the acronym back at me is the weaker position.

The uncontested cases are scripts and one-off migrations, where the payoff is amortised over future changes that will never happen, and prototypes, where the risk is not bad structure but that good structure makes throwaway code look shippable.

The contested cases need a rehearsed argument. A one-implementation interface costs two files and a permanent navigation tax and buys flexibility nobody has used — and since Mockito has mocked concrete classes for over a decade, the testing justification is gone. A factory that only calls new is a rename of a language feature. The asymmetry I lean on is that the reading cost is paid every day by every reader, while the extension benefit is speculative and may never arrive.

The argument that actually changes minds is Metz's: duplication is far cheaper than the wrong abstraction. Duplication is visible, greppable and deletable, and its cost is bounded. A wrong abstraction acquires fifteen call sites, then a boolean parameter when case sixteen does not fit, then another — and removing it means inlining it everywhere first, which nobody schedules. Wildly asymmetric exit costs are why waiting for the third occurrence is disciplined rather than lazy.

In review I make it concrete: "what change are we buying protection against, and what is the evidence it is coming?" A real answer — a second payment provider already on the roadmap — and I build it happily. "You never know" is the definition of speculative, and I would rather pay a five-second Extract Interface later than a navigation tax forever.

The one thing I never trade away is LSP. A cut corner on SRP costs maintainability, which is recoverable; a substitutability violation returns wrong answers with no exception, and those are found by customers rather than by tests.

What happens today is nothing, for months. interface Charging    { Charge charge(Money m, Card c); }
interface Refunding   { Refund refund(ChargeId id, Money m); }
interface Tokenizing  { Token  tokenize(Card c); }
interface Subscribing { Subscription subscribe(Plan p, Card c); }

class StripeGateway implements Charging, Refunding, Tokenizing, Subscribing { }
class SimpleGateway implements Charging, Refunding { }

class Checkout {
    Checkout(Charging gateway) { ... }      // declares exactly what it needs
}

The split buys a compile-time failure at the wiring instead of a runtime failure in production. Injecting SimpleGateway where a Tokenizing is required does not compile, and Checkout can no longer call subscribe by accident because the type it holds has no such method. The bug class is eliminated, not relocated.

Would a default method help? No — it makes it worse. A default subscribe() that throws deletes the compile error that was reporting the design problem and reschedules the failure for runtime; before, the implementer was at least forced to look at it. A default returning a plausible wrong value — an empty list, false, null — is worse still, trading a stack trace for silently wrong behaviour in a money path.

The rule that distinguishes the cases: a legitimate default has a correct universal implementation written in terms of the interface's own abstract methods. Iterable.forEach is defined by iterator() and cannot be wrong for any implementation. subscribe has no such definition — which is precisely the evidence that it does not belong on this interface.

The criterion, stated so it is not just "I disagree": every abstraction is an investment repaid in future changes. This code has a known, finite number of future changes — approximately zero — so each request has negative expected value. That argument is reviewable, which keeps the discussion off taste.

// WHAT I WOULD ACTUALLY CHANGE — and none of it is structure:
public static void main(String[] args) throws Exception {
    var rows = Files.readAllLines(Path.of(args[0]), UTF_8);    // explicit charset
    try (var conn = DriverManager.getConnection(args[1]);
         var st   = conn.prepareStatement(
             "INSERT INTO product(sku, price) VALUES (?,?)")) {
        conn.setAutoCommit(false);
        int line = 1;
        for (String row : rows.subList(1, rows.size())) {
            line++;
            String[] f = row.split(",", -1);                   // keep trailing empties
            if (f.length < 4) throw new IOException(
                    "line " + line + ": expected 4 columns, got " + f.length);
            st.setString(1, f[0]);
            st.setBigDecimal(2, new BigDecimal(f[3]));
            st.addBatch();
            if (line % 1000 == 0) st.executeBatch();
        }
        st.executeBatch();
        conn.commit();
    }
}
ChangeWhy it beats every structural request
Batching in one transaction40,000 autocommits against a remote database is minutes of round trips; batches of 1000 is seconds
Line number in the errorThe one thing you need at 2am when row 31,447 has a stray comma
split(",", -1)The default drops trailing empty fields, so a row ending in ,, silently becomes short
Explicit UTF_8The platform default differs between your laptop and the server — classic vendor-file corruption

The point: the reviewer optimised for changes that will never happen and missed every failure that will. What would change my answer: if this ran nightly, everything shifts — it has a future, failures repeat, and a ProductRepository port earns its cost by making the parsing testable without a database. The design question is never "is this SOLID" but "how many more changes will this code see, and who will make them?"

🎯 Key Takeaways

  • SRP means one actor, not one method — name the human who files the ticket; two names with two budgets means two classes.
  • The dangerous part of an SRP violation is the shared private helper, which delivers one actor's change to another actor untested.
  • OCP is a bet on the axis of variation; an abstraction on the wrong axis makes the change you actually get more expensive, not less.
  • A sealed type with an exhaustive switch often beats OCP when the type set is closed and you own it — the compiler enumerates every site to update.
  • LSP is about behaviour, and javac checks only signatures — that gap is where the bugs live.
  • Weaken preconditions, strengthen postconditions — never the reverse; a weakened postcondition returns wrong answers without throwing.
  • Square/Rectangle is a mutability problem, not a geometry one — immutable records have no history constraint to violate.
  • Arrays.asList(x).add(y) throws — the JDK ships an LSP violation and legalises it with the phrase "optional operation".
  • Never mutate a collection you did not construct; copy with new ArrayList<>(incoming) and return List.copyOf.
  • UnsupportedOperationException is an ISP violation announcing itself as an LSP failure — go find the interface that is too wide.
  • A default method is legitimate only with a correct universal implementation in terms of the interface's own abstract methods; one that throws just deletes the compile error.
  • DIP is about who owns the abstraction — the consumer declares the interface it needs, which is why the compile-time arrow points opposite to the call.
  • The test for DIP is a build-file question: can the domain compile with the adapter deleted and the driver off its classpath?
  • SOLID is a proxy for cohesion and coupling; when a letter and those two properties disagree, follow the properties.
  • Extract for a name, reuse, or a mixed abstraction level — never for a line count; fields invented to pass state between private methods mean you over-extracted.
  • Comment the why — a name cannot hold a ticket number, a vendor bug, or the reason you rejected the obvious approach.
  • Duplication is far cheaper than the wrong abstraction; the exit costs are wildly asymmetric, so wait for the third occurrence.
  • A one-implementation interface and a factory that only calls new are pure cost — the reading tax is paid daily, the extension dividend may never arrive.
