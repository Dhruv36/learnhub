SOLID & Clean Code Professional Java

What you'll master: SRP as "one actor to answer to" rather than "one method", and the shared private helper that makes a violation dangerous instead of merely untidy; OCP as polymorphism, with the honest counterpoint that a sealed type plus an exhaustive switch often beats it; LSP as behavioural substitutability — preconditions, postconditions, the history constraint, and the violation the JDK itself ships in Arrays.asList().add(); ISP and what default methods changed; DIP as a question of who owns the abstraction, which is what makes ports and adapters work; cohesion and coupling underneath all of it; the Clean Code heuristics and where that book overreaches; seven code smells with their refactorings; and when applying none of this is the right call. Prerequisites: Interfaces.

Part 1 — SRP: One Reason to Change, One Actor

  THE DEFINITION EVERYONE MISQUOTES:

    "A class should do one thing."         ← not the principle
    "A class should have one method."      ← not remotely
    "A class should have one reason to     ← Martin's original
     change."                                 phrasing
    "A module should be responsible to     ← Martin's own later
     one, and only one, ACTOR."                clarification

  The last one is the useful one, because "one reason to change" is
  untestable until you ask WHO ASKS FOR THE CHANGE. Responsibility is
  a social fact, not a structural one. Two methods belong in the same
  class when the same person would request a change to both.

  THE VIOLATION — one class, three bosses:

    class Payroll {
        BigDecimal computeNetPay(Employee e, Period p) {
            BigDecimal gross = e.rate().multiply(regularHours(e, p));
            return gross.subtract(tax(gross)).subtract(pension(gross));
        }

        Report monthlyHoursReport(Employee e, Period p) {
            return new Report(regularHours(e, p), overtime(e, p));
        }

        void save(Employee e, BigDecimal net) throws SQLException {
            try (var st = conn.prepareStatement(
                    "INSERT INTO payslip(emp_id, net, run_at) VALUES (?,?,?)")) {
                st.setLong(1, e.id());
                st.setBigDecimal(2, net);
                st.executeUpdate();
            }
        }

        private BigDecimal regularHours(Employee e, Period p) { ... }
    }
MethodActor who requests changesWhat triggers a change
computeNetPayFinance / the CFOTax rules, pension rates, overtime thresholds
monthlyHoursReportOperations / the COOWhat management wants to see this quarter
savePlatform / the DBASchema migrations, connection pooling, a store swap
regularHoursTwo of them, silentlyEither — and neither knows about the other
  THE HARM IS NOT UNTIDINESS. IT IS THAT SHARED PRIVATE HELPER.

  Finance files a ticket: "overtime now starts after 38 hours, not
  40." You edit regularHours. Payroll is correct and the payroll
  tests pass. THE COO'S HOURS REPORT ALSO CHANGED — nobody tested it,
  nobody reviewed it, and nobody knew the two shared a method,
  because it was private and looked like an implementation detail.

  That is the actual failure mode of an SRP violation: a change
  requested by one actor is DELIVERED to a second actor who did not
  ask for it and will not notice until the numbers are wrong in a
  board pack. The secondary harms are real but smaller — merge
  conflicts between two teams in one file, and a schema migration
  forcing a recompile and redeploy of tax arithmetic that did not
  change.

  THE FIX — SPLIT BY ACTOR, NOT BY NOUN:

    NetPayCalculator        finance owns the rules
    HoursReporter           operations owns the shape of the report
    PayslipRepository       platform owns the schema
    Timesheet               the shared DATA, owned by neither

  regularHours moves onto Timesheet — a value that both consumers
  read — so a change to it is now an obvious, reviewable change to a
  shared type rather than an invisible edit to someone's private
  helper. That is the real refactoring: EXTRACT THE THING THEY SHARE
  INTO SOMETHING VISIBLE.

  WHAT SRP DOES NOT MEAN:

  ❌ One public method per class. A class with eight methods that
     all serve the same actor and operate on the same fields has
     exactly ONE reason to change and is correct as it stands.
  ❌ A class per verb. Six single-method classes coordinating
     through a shared mutable context object have MORE reasons to
     change than the one class they replaced, plus a new one: the
     coordination.
  ❌ Splitting until nothing is left. When every class has one
     method, the responsibilities did not vanish — they moved into
     the wiring, and the wiring is now the file nobody understands.

  THE TEST YOU CAN APPLY IN A CODE REVIEW: name the human who would
  file the ticket for each method. Two names with two different
  budgets means two classes. One name means leave it alone, however
  long the class is.

Part 2 — OCP: Extension Without Modification, and When That Is Premature

  MEYER, 1988: "Software entities should be open for extension but
  closed for modification." Meyer meant INHERITANCE — freeze the base
  class, subclass to extend. Martin's later reading is the one worth
  keeping: NEW BEHAVIOUR ARRIVES AS A NEW TYPE, NOT AS A NEW BRANCH
  IN AN OLD METHOD.

  THE SHAPE OF A VIOLATION — the switch that grows:

    BigDecimal fee(Payment p) {
        switch (p.type()) {
            case CARD: return p.amount().multiply(new BigDecimal("0.029"));
            case ACH:  return new BigDecimal("0.25");
            case WIRE: return new BigDecimal("15.00");
        }
        throw new IllegalArgumentException("unknown: " + p.type());
    }

  Add CRYPTO and you edit a tested method and redeploy everything
  that links against it. The worse problem is that this switch is
  never alone. The same enum is switched on in settlementDelay(p),
  isRefundable(p), reconciliationAccount(p) and the CSV exporter.
  Adding a type means finding all five — SHOTGUN SURGERY — and the
  one you miss throws IllegalArgumentException in production, or
  worse, falls into a default branch and returns a plausible wrong
  number.

  THE POLYMORPHIC FORM — behaviour travels with the type:

    interface PaymentMethod {
        BigDecimal fee(Money amount);
        Duration   settlementDelay();
        boolean    refundable();
    }

    record Card(Brand brand) implements PaymentMethod {
        public BigDecimal fee(Money a) { return a.times("0.029"); }
        public Duration settlementDelay() { return Duration.ofDays(2); }
        public boolean refundable() { return true; }
    }

    record Wire(Bic bic) implements PaymentMethod { ... }

  Adding Crypto is ONE new file and ZERO edits to tested code, and
  the compiler forces you to answer all three questions at once. That
  payoff is real. Now the part most treatments omit.

  THE HONEST COUNTERPOINT

  1. OCP IS A BET ON THE AXIS OF VARIATION. You have declared that
     payment TYPE is what varies. If the change that actually arrives
     is "every method now needs a jurisdiction argument for tax", you
     edit the interface and all N implementations — N files instead
     of the 1 the switch would have cost. An abstraction protects the
     axis you chose and makes every other axis MORE expensive.

  2. THE COST IS PAID NOW, THE BENEFIT MAYBE NEVER. An interface, N
     record types, a registry or factory to build them, and wiring.
     Every future reader answering "what does a card cost?" now opens
     three files instead of scrolling to a case label.

  3. TWO CASES IS NOT EVIDENCE. Write the switch. When the THIRD
     case arrives on the same axis you have three data points, the
     shape of the variation is visible, and the refactor is
     mechanical and safe. The Rule of Three is not laziness; it is
     refusing to guess when waiting is cheap.

  THE MODERN JAVA TWIST — SEALED TYPES INVERT THE ADVICE:

    sealed interface Payment permits Card, Ach, Wire { }

    BigDecimal fee(Payment p) {
        return switch (p) {                 // no default branch
            case Card c -> c.amount().multiply(RATE);
            case Ach  a -> FLAT_25;
            case Wire w -> FLAT_15;
        };
    }

  Add a Crypto record to the permits clause and EVERY exhaustive
  switch in the codebase fails to compile until you handle it. That
  is not OCP — it is deliberately CLOSED for extension — but it
  converts shotgun surgery from a runtime bug into a compiler-checked
  worklist, which is strictly better when the set of types is closed
  and you own it.
Polymorphism (classic OCP)Sealed type + exhaustive switch
Adding a typeOne new file, no edits to existing codeCompile errors at every switch — a guided checklist
Adding an operationEdit the interface and every implementationOne new method in one place
ExhaustivenessNot checked — a missing override is a silent inherited defaultChecked by javac
Who may add typesAnyone, including code you have never seenOnly the module that owns the sealed type
Behaviour livesWith the data, in each typeWith the operation, away from the data
Choose it whenThe type set is open: plugins, third-party strategiesThe type set is closed and yours: order states, AST nodes, payment methods

This is the expression problem in one table, and it is the honest reason SOLID cannot be applied as a checklist: OCP optimises one direction of growth at the direct expense of the other. Pick the direction your code actually grows in.

Part 3 — LSP: Behavioural Substitutability

  LISKOV, 1987, paraphrased: if S is a subtype of T, objects of type
  T may be replaced by objects of type S WITHOUT ALTERING ANY
  DESIRABLE PROPERTY OF THE PROGRAM.

  THE LOAD-BEARING WORD IS "PROPERTY", NOT "SIGNATURE". javac checks
  the signature: parameter types, return type, checked exceptions.
  NOTHING checks the behaviour except your callers, at runtime, in
  production. That gap is the entire subject.
RuleWhat it meansTypical violation
Preconditions may be weakened, never strengthenedThe subtype must accept everything the supertype accepted, and may accept moreAn override that adds a null check or a narrower range check
Postconditions may be strengthened, never weakenedThe subtype must promise everything the supertype promised, and may promise moreReturning an unsorted list where the base documented "sorted"
Invariants must be preservedAnything true of the supertype for its whole lifetime stays trueA subclass that lets a balance go negative
History constraintThe subtype must not permit state transitions the supertype forbidsSquare.setWidth also changing the height
Exceptions must not broadenNo new exception types outside the declared hierarchyThrowing UnsupportedOperationException from an implemented method
  THE CANONICAL CASE — SQUARE AND RECTANGLE:

    class Rectangle {
        protected int w, h;
        void setWidth(int w)  { this.w = w; }
        void setHeight(int h) { this.h = h; }
        int  area()           { return w * h; }
    }

    class Square extends Rectangle {
        @Override void setWidth(int w)  { this.w = w; this.h = w; }
        @Override void setHeight(int h) { this.w = h; this.h = h; }
    }

  THE CLIENT THAT BREAKS — and notice it never mentions Square:

    void stretch(Rectangle r) {
        r.setWidth(5);
        r.setHeight(4);
        assert r.area() == 20;        // 16 when r is a Square
    }

  GEOMETRY IS NOT THE PROBLEM. A square really is a rectangle. The
  problem is that MUTABLE Rectangle's contract contains an invariant
  Square cannot honour: "setWidth does not change the height." That
  invariant appears nowhere in the source — it lives in the head of
  every caller — which is exactly why the violation survives review
  and why LSP needs stating at all.

  Formally this is a HISTORY-CONSTRAINT violation: Square permits a
  state transition (w and h moving together) that Rectangle forbids.

  MAKE THEM IMMUTABLE AND THE PROBLEM EVAPORATES:

    record Rectangle(int w, int h) { int area() { return w * h; } }
    record Square(int side) {
        Rectangle asRectangle() { return new Rectangle(side, side); }
    }

  With no setters there is no history to constrain. MOST LSP
  VIOLATIONS YOU MEET IN THE WILD ARE MUTABILITY PROBLEMS WEARING AN
  INHERITANCE COSTUME.

  STRENGTHENED PRECONDITION — the subtype accepts LESS:

    class Validator {
        void check(String s) { if (s != null) validate(s); }   // null OK
    }
    class StrictValidator extends Validator {
        @Override void check(String s) {
            if (s == null) throw new IllegalArgumentException();  // ❌
            validate(s);
        }
    }

  A caller written against Validator legitimately passes null. Swap
  the implementation and it throws. Nothing changed at compile time,
  and the stack trace points at the caller, not at the subclass that
  broke the deal.

  WEAKENED POSTCONDITION — the subtype promises LESS:

    /** @return orders, most recent first. */
    List<Order> findAll();                       // the contract

    class CachedOrderRepo extends OrderRepo {
        @Override List<Order> findAll() {
            return new ArrayList<>(cache.values());   // ❌ HashMap order
        }
    }

  Pagination built on "most recent first" now returns duplicate rows
  on page 2 and silently drops others. POSTCONDITION VIOLATIONS ARE
  THE WORST CLASS OF LSP BUG BECAUSE THEY DO NOT THROW — they return
  wrong answers that look right.

  THE VIOLATION THE JDK ITSELF SHIPS:

    List<String> l = Arrays.asList("a", "b");
    l.set(0, "z");     // works — writes THROUGH to the backing array
    l.add("c");        // UnsupportedOperationException
    l.remove(0);       // UnsupportedOperationException

    List<String> m = List.of("a", "b");
    m.set(0, "z");     // UnsupportedOperationException as well

  List.add is declared on the interface. A method that takes
  List<String> and calls add is type-correct and can still explode at
  runtime depending on who constructed the argument. That is the
  textbook definition of a substitutability failure, in the standard
  library, on the most-used interface in Java.

  THE JDK'S DEFENCE IS THE PHRASE "OPTIONAL OPERATION" IN THE JAVADOC
  — the contract was weakened until the violation became legal. Two
  things follow, and both matter:

  1. PRACTICAL: never mutate a List you did not construct. If you
     must, copy first: new ArrayList<>(incoming). Returning
     List.copyOf(x) from an accessor is good; calling add on
     something a caller handed you is a latent crash.
  2. DESIGN: THE ROOT CAUSE IS AN ISP FAILURE. Collection bundles
     reading and writing into one interface, so read-only
     implementations have nowhere to live except
     UnsupportedOperationException. A separate immutable type would
     have been LSP-clean; the JDK could not add one in 1998 without
     splitting the hierarchy, and cannot now without breaking every
     program ever written.

  OTHER JDK CASES WORTH RECOGNISING ON SIGHT:

    Collections.unmodifiableList(x)  a VIEW, not a copy — mutate x
                                     and the "unmodifiable" list
                                     changes underneath the holder
    Properties extends Hashtable     put(Object,Object) is inherited,
                                     so a non-String value makes
                                     getProperty return null for a
                                     key that demonstrably exists
    Timestamp extends Date           equals is NOT symmetric:
                                     d.equals(ts) and ts.equals(d)
                                     disagree, which breaks List
                                     .contains and every hash-based
                                     collection
    Stack extends Vector             you can insert at index 3 of a
                                     stack, and get(0) is the BOTTOM

  Every one is inheritance used for implementation reuse where
  composition was wanted. THAT is the pattern to recognise: if the
  subtype needs to disable, ignore or reinterpret something the
  supertype promised, it is not a subtype — it is a collaborator.

Part 4 — ISP: Fat Interfaces and What default Methods Changed

  "CLIENTS SHOULD NOT BE FORCED TO DEPEND ON METHODS THEY DO NOT
  USE." Note the word CLIENTS. ISP is stated from the CALLER's side,
  not the implementer's. The cost of a fat interface is paid by
  everyone who compiles against it, and only secondarily by the
  people implementing it.

  THE FAT INTERFACE:

    interface PaymentGateway {
        Charge       charge(Money m, Card c);
        Refund       refund(ChargeId id, Money m);
        Subscription subscribe(Plan p, Card c);
        void         cancelSubscription(SubscriptionId id);
        Token        tokenize(Card c);
        Payout       payout(BankAccount a, Money m);
    }

  Implement it for a gateway that only does one-off charges:

    class SimpleGateway implements PaymentGateway {
        public Charge charge(Money m, Card c) { ... }
        public Subscription subscribe(Plan p, Card c) {
            throw new UnsupportedOperationException();     // ❌
        }
        // ...four more of those
    }

  TWO DISTINCT FAILURES IN ONE PIECE OF CODE:

  - ISP: SimpleGateway must compile against, and appear to offer,
    five capabilities it does not have.
  - LSP: any client holding a PaymentGateway can call subscribe()
    and get an exception. UnsupportedOperationException IS ALMOST
    ALWAYS AN ISP VIOLATION ANNOUNCING ITSELF AS AN LSP VIOLATION —
    when you see it, look for the interface that is too wide.

  THE SPLIT, BY CLIENT NEED RATHER THAN BY THEME:

    interface Charging    { Charge charge(Money m, Card c); }
    interface Refunding   { Refund refund(ChargeId id, Money m); }
    interface Subscribing {
        Subscription subscribe(Plan p, Card c);
        void cancelSubscription(SubscriptionId id);
    }

    class StripeGateway implements Charging, Refunding, Subscribing { }
    class SimpleGateway implements Charging { }

    class Checkout {
        Checkout(Charging gateway) { ... }    // declares what it needs
    }

  A capability the gateway lacks is now a COMPILE ERROR AT THE
  WIRING, not a production exception on a Friday. Checkout also
  cannot accidentally start a subscription, because the type it holds
  has no such method.

  ISP APPLIES TO PARAMETER TYPES, AND THAT IS WHERE YOU WILL USE IT
  DAILY:

    void render(ArrayList<Row> rows)    // demands a specific class
    void render(List<Row> rows)         // better
    void render(Collection<Row> rows)   // better still
    void render(Iterable<Row> rows)     // exactly what it needs

  Ask what the method actually DOES with the argument — here, a
  for-each — and declare the narrowest type that supports it. This
  costs nothing, widens what callers may pass, and documents the
  method's real requirement in its signature.

  WHAT default METHODS CHANGED

  BEFORE JAVA 8, adding a method to a published interface broke every
  implementation on earth at compile time. Interfaces stayed small
  partly for ISP reasons and largely for BINARY COMPATIBILITY. The
  workaround was the ADAPTER CLASS, and the JDK is full of the
  evidence:

    interface MouseListener        5 abstract methods
    class MouseAdapter             all 5, implemented empty
    interface WindowListener       7 abstract methods
    class WindowAdapter            all 7, implemented empty

  You extended the adapter and overrode the one you cared about — ISP
  solved by inheritance, at the cost of your single inheritance slot.

  JAVA 8 REMOVED THE COMPATIBILITY PRESSURE:

    Collection.stream()           default, via spliterator()
    Collection.removeIf(pred)     default, via iterator().remove()
    Iterable.forEach(action)      default, via iterator()
    Comparator.reversed()         default, via compare()
    Map.computeIfAbsent(k, f)     default, via get() and put()

  Collection gained stream(), parallelStream(), removeIf() and
  spliterator() in one release, and not one implementation on earth
  failed to compile.

  THE TRADE-OFF MOVED; IT DID NOT DISAPPEAR:

  ✓ A LEGITIMATE default has a CORRECT UNIVERSAL implementation
    written in terms of the interface's own abstract methods.
    forEach cannot be wrong for any Iterable, because it is defined
    by iterator(). Implementers may override it for speed, never for
    correctness.

  ❌ AN ILLEGITIMATE default:
        default Subscription subscribe(Plan p, Card c) {
            throw new UnsupportedOperationException();
        }
    This does not fix the fat interface. It DELETES THE COMPILE ERROR
    THAT WAS TELLING YOU ABOUT IT and reschedules the failure for
    runtime. It is strictly worse than the pre-Java-8 situation,
    where at least the implementer was forced to look at it.

  ❌ WORSE STILL — a default that returns a plausible wrong value:
        default List<Refund> refunds() { return List.of(); }
    Silence instead of a stack trace. A reconciliation report that
    quietly shows zero refunds is more expensive than one that
    crashes.

  THE MODERN GUIDANCE: interfaces may be larger than 2008 dogma
  allowed, PROVIDED everything beyond the core few methods is a
  default written in terms of those few. THE ABSTRACT SURFACE — what
  an implementer is forced to write — is what ISP is really counting.
  Comparator has over twenty methods and one abstract one, and nobody
  calls it a fat interface.

Part 5 — DIP: Who Owns the Abstraction

  "HIGH-LEVEL MODULES SHOULD NOT DEPEND ON LOW-LEVEL MODULES. BOTH
  SHOULD DEPEND ON ABSTRACTIONS. ABSTRACTIONS SHOULD NOT DEPEND ON
  DETAILS; DETAILS SHOULD DEPEND ON ABSTRACTIONS."

  Everyone remembers the first sentence and implements it as "put an
  interface in front of it". THAT IS NOT DIP. The principle is about
  WHO OWNS THE ABSTRACTION, and the second sentence is where that
  lives.

  NOT INVERTED — an interface that changed nothing:

    package com.acme.persistence;

    public interface OrderDao {                    // lives WITH the detail
        ResultSet selectByCustomer(long id) throws SQLException;
        void      insert(Order o) throws SQLException;
        void      flush();
    }

    package com.acme.orders;

    class OrderService {
        private final OrderDao dao;                // "an abstraction!"
    }

  COUNT THE DEPENDENCIES HONESTLY:

  - OrderService imports com.acme.persistence, so the high-level
    module still depends on the low-level one. Arrow unchanged.
  - The interface speaks SQL: ResultSet, SQLException, flush(). The
    abstraction depends on the detail, which the second sentence of
    the principle explicitly forbids.
  - Swap to a document store and the interface must change, so
    OrderService changes. The indirection bought nothing.

  You added a file and a level of indirection and inverted NOTHING.
  This is the single most common "we follow SOLID" artefact in a Java
  codebase, and it is usually produced by the IDE's Extract Interface
  refactoring, which by construction mirrors the implementation.

  INVERTED — the CONSUMER declares the interface it needs:

    package com.acme.orders;                    // the HIGH-LEVEL module

    public interface OrderRepository {          // OWNED BY THE CONSUMER
        Optional<Order> findById(OrderId id);
        List<Order>     findOpenFor(CustomerId c);
        void            save(Order o);
    }

    package com.acme.orders.jdbc;               // the LOW-LEVEL module

    class JdbcOrderRepository implements OrderRepository {
        // knows about DataSource, SQL and SQLException;
        // translates all of it into the domain's vocabulary
    }

  NOW LOOK AT THE TWO ARROWS SEPARATELY:

    CALL DIRECTION      orders  ──────────▶  orders.jdbc
    SOURCE DEPENDENCY   orders  ◀──────────  orders.jdbc

  At RUNTIME the service calls the adapter. At COMPILE TIME the
  adapter depends on the service's package and the service depends on
  nothing. THAT OPPOSITION IS THE "INVERSION" IN THE NAME. If both
  arrows point the same way, you have an interface, not DIP.

  THREE CHECKS THAT ARE HARD TO FAKE:

  1. VOCABULARY. Does the interface mention ResultSet, HttpResponse,
     ConsumerRecord, SQLException, or an ORM entity? If the domain
     must import the driver's types to compile, the abstraction leaks
     the detail.
  2. DELETION. Could you delete the adapter package and still compile
     the domain? In Maven or Gradle this is enforceable rather than
     aspirational: the domain module simply does not declare the JDBC
     driver as a dependency, and the build fails if someone imports
     it. A compiler is a better architecture reviewer than a human.
  3. ORIGIN. Was the interface designed from the CALL SITE or
     extracted from the implementation? The method set should be what
     OrderService actually needs — frequently three methods where the
     DAO had thirty.

  THIS IS PRECISELY WHAT MAKES PORTS AND ADAPTERS WORK:

    ┌────────────────────────────────────────────────┐
    │           com.acme.orders  (the core)          │
    │                                                │
    │   Order, OrderId, PricingRules, OrderService   │
    │   interface OrderRepository   ← PORT (owned)   │
    │   interface PaymentGateway    ← PORT (owned)   │
    │                                                │
    │   depends on: nothing outside the JDK          │
    └───────▲──────────────────────────▲─────────────┘
            │ implements               │ implements
    ┌───────┴─────────┐       ┌────────┴──────────┐
    │ orders.jdbc     │       │ orders.stripe     │
    │ (ADAPTER)       │       │ (ADAPTER)         │
    │ DataSource, SQL │       │ HTTP, JSON        │
    └─────────────────┘       └───────────────────┘

  A "port" is just an interface the core owns and the outside world
  implements. Nothing more mystical than that, and everything in
  hexagonal architecture follows from the ownership rule.

  THE DIVIDEND IS MEASURABLE, AND IT IS TEST SPEED. The core's tests
  need no database, no HTTP, no Spring context. An in-memory
  Map-backed OrderRepository is about fifteen lines:

    class InMemoryOrderRepository implements OrderRepository {
        private final Map<OrderId, Order> store = new HashMap<>();
        public Optional<Order> findById(OrderId id) {
            return Optional.ofNullable(store.get(id));
        }
        public void save(Order o) { store.put(o.id(), o); }
        public List<Order> findOpenFor(CustomerId c) {
            return store.values().stream()
                        .filter(o -> o.customer().equals(c) && o.isOpen())
                        .toList();
        }
    }

  A domain suite that runs in ~400 ms instead of 40 s of Spring
  context startup per test class is the thing that actually changes
  how a team works: tests you run on every save versus tests you run
  in CI and hope.

  WHERE DIP IS NOT WORTH IT:

  - TYPES THAT DO NOT VARY and are trivially constructible:
    BigDecimal, LocalDate, your own value objects. Nobody needs an
    IMoney.
  - STABLE JDK ABSTRACTIONS THAT ALREADY EXIST. Do not wrap Clock,
    Random or Path in a port of your own — inject the JDK type. Clock
    is already the seam for testing time.
  - A BOUNDARY YOU WILL NEVER CROSS AND CANNOT TEST FASTER FOR.
    A port whose only implementation is a one-line delegation to a
    class in the same module is ceremony. The two things that justify
    a port are a REAL second implementation and a FAST test double —
    if neither is present, you have a naming convention, not an
    architecture.

Part 6 — Cohesion, Coupling, and the Clean Code Heuristics

  SOLID IS NOT THE GOAL. It is five heuristics aimed at two
  properties named twenty years earlier by Constantine and Yourdon:

    HIGH COHESION   the things inside a module belong together
    LOW COUPLING    modules know as little as possible about each
                    other

  WHEN A SOLID RULE AND THESE TWO PROPERTIES DISAGREE, FOLLOW THE
  PROPERTIES. "Split it because SRP" that lowers cohesion and raises
  coupling is a worse design that passes the review checklist — and
  that is the failure mode of teaching SOLID as rules.

Map the acronym back onto the properties and it stops being arbitrary: SRP and ISP are cohesion tools (what belongs in one place, what one client needs), DIP and OCP are coupling tools (which direction dependencies point, what a change touches), and LSP is what stops the polymorphism both rely on from lying to you. If you can argue cohesion and coupling directly, you never need to cite a letter.

  NAMING — the rules that survive contact with real code:

    boolean flag;              →  boolean eligibleForRefund;
    List<Data> list2;          →  List<LineItem> unpricedItems;
    void process(Order o);     →  void submitForFulfilment(Order o);
    int d;   // elapsed days   →  int elapsedDays;   (delete the comment)

  - NAME BY INTENTION, NOT IMPLEMENTATION. sortedByPrice is a promise
    to callers; bubbleSorted leaks a decision you will change.
  - Booleans read as predicates: isEmpty, hasExpired, canRefund.
  - NO TYPE ENCODINGS. No strName, no m_count, no IUserService. Java
    has types and packages; Hungarian notation is tooling debt from
    languages that had neither.
  - LENGTH SCALES WITH SCOPE. `i` is fine in a three-line loop; a
    field that lives as long as the object earns a long name. The
    inverse — `i` as a field, `theCurrentIndexValue` in a loop — is
    what actually reads badly.
  - IF YOU CANNOT NAME A CLASS, YOU PROBABLY DO NOT KNOW WHAT IT IS.
    That is design information, not a vocabulary problem. Manager,
    Processor, Handler and Data are the four words that mean "I gave
    up".

  FUNCTION LENGTH — the heuristic, and where the book overreaches.

  Clean Code says functions should be "hardly ever 20 lines" and its
  own examples run to two to four. That is too far, and the reason is
  a reading cost, not a matter of taste:

    // ONE LINEAR FLOW, 35 lines, no branching, read top to bottom:
    void settleBatch(Batch b) {
        ...load...  ...validate...  ...price...  ...post...  ...notify...
    }

    // "CLEANED UP" INTO ELEVEN 3-LINE METHODS:
    void settleBatch(Batch b) {
        var loaded = load(b);
        var valid  = validate(loaded);
        var priced = price(valid);
        post(priced);
        notify(priced);
    }

  The second version is better ONLY IF the extracted names carry more
  information than the code they hide. When they do not, you have
  replaced one page you read top to bottom with a call graph you must
  navigate — eleven jumps, eleven contexts to hold — and the state
  the steps shared gets smuggled through FIELDS because the extracted
  methods needed it. THAT LAST SYMPTOM IS THE TELL: a class growing
  mutable fields purely to pass data between its own private methods
  has been over-extracted, and it has traded a long function for a
  thread-unsafe object.

  EXTRACT FOR A REASON, NOT A LINE COUNT:

    ✓ the fragment has a name more meaningful than its body
    ✓ it is reused, or you want to test it directly
    ✓ the function mixes ABSTRACTION LEVELS — business rules next to
      string formatting next to JDBC — which is the strongest signal
    ✓ it is buried inside a deeply nested conditional
    ❌ "it is over 30 lines"

  ARGUMENT COUNT — the heuristic that is nearly always right:

    0–2   fine
    3     look hard at it
    4+    there is a missing type

  AND TWO SPECIFIC JAVA HAZARDS:

    void transfer(String from, String to, BigDecimal amount)
    transfer(to, from, amount);      // compiles. wires money backwards.

  Adjacent same-typed parameters are a silent-defect factory. Domain
  types fix the amount/account confusion but NOT this one:

    void transfer(AccountId from, AccountId to, Money amount)
    transfer(to, from, amount);      // still compiles — same type

  So where correctness is expensive, force the call site to name
  things: a Transfer record, or a staged builder —
  Transfer.from(a).to(b).amount(m). The point is not fewer arguments;
  it is that the argument ORDER stops being load-bearing.

  BOOLEAN FLAG PARAMETERS ARE ALWAYS TWO FUNCTIONS:

    render(page, true);          // true means what, exactly?
    →  renderForPrint(page);     renderForScreen(page);

  A boolean parameter means the body starts with an if whose branches
  share almost nothing, and every call site is unreadable without
  jumping to the signature.

  COMMENTS — WHY, NEVER WHAT:

    // ❌ restates the code, and lies the moment the code moves
    i++;                              // increment i
    // set the user's name
    user.setName(name);

    // ✓ cannot be recovered from the code at any price
    // Retry three times: the gateway returns 502 for roughly one
    // second after their blue/green flip. Confirmed with the vendor,
    // INC-4471. Do not lower this without re-testing across a deploy.
    private static final int RETRIES = 3;

    // ✓ warns about a footgun in call order
    // close() flushes, and flush() requires the lock still held —
    // do not move this out of the synchronized block.

    // ✓ records a REJECTED alternative, so nobody "fixes" it
    // Deliberately a List, not a Set: the audit export requires
    // duplicate line items to be preserved.

  WHERE CLEAN CODE OVERREACHES AGAIN: "every comment is a failure to
  express yourself in code" is true of comments that restate code,
  and it gets misapplied to comments that record DECISIONS. A method
  name cannot hold a ticket number, a vendor bug, a spec citation, a
  benchmark result, or the reason you did not do the obvious thing.
  Delete the noise; keep the archaeology.

  JAVADOC IS A DIFFERENT ARTEFACT ENTIRELY. On a public API,
  @param / @return / @throws ARE the contract — the preconditions and
  postconditions Part 3 is about. "Optional operation" in List.add's
  Javadoc is the only thing standing between a caller and an
  UnsupportedOperationException. Write it on anything other people
  call; skip it on private helpers whose name already says it.

  PRIMITIVE OBSESSION

    void register(String email, String country, int ageInYears)

  Every caller must know the validation rules, and nothing prevents
  register(country, email, age) — it compiles. The type says "String"
  where the domain says "an address with exactly one @, normalised to
  lower case".

    public record Email(String value) {
        private static final Pattern OK =
            Pattern.compile("[^@\\s]+@[^@\\s]+\\.[^@\\s]{2,}");
        public Email {
            Objects.requireNonNull(value);

                throw new IllegalArgumentException("bad email: " + value);
            value = value.toLowerCase(Locale.ROOT);   // normalise ONCE
        }

  place instead of in each controller, equals/hashCode come free and
  are correct, and register(Email, Country, Age) cannot have its

  WHEN NOT TO APPLY ANY OF THIS

  1. SCRIPTS AND ONE-OFFS. A 60-line data migration that runs once,
     is read by two people, and is deleted next week. SOLID's payoff
     is amortised across FUTURE CHANGES; there are none here. A main
     method with four helpers is the correct design, and adding an
     interface to it is a net loss with no offsetting benefit.

  2. PROTOTYPES AND SPIKES. The purpose is to answer a question, not
     to survive. The danger is not the prototype's design — it is
     that a well-structured prototype LOOKS shippable and therefore
     gets shipped, with its unhandled errors and hardcoded
     credentials intact. Make throwaway code look throwaway.

  3. THE ONE-IMPLEMENTATION INTERFACE.

       interface UserService { ... }
       class UserServiceImpl implements UserService { ... }

     Zero polymorphism, two files, and every "go to definition" lands
     on a method with no body. The two arguments for it are both
     dead:

       "We might swap the implementation."  You will not; and if you
         do, Extract Interface is a five-second refactor THEN — with
         the real second implementation in front of you to design
         against, rather than a guess made a year early.
       "We need it for mocking."  Mockito has mocked concrete classes
         via bytecode generation for over a decade, and the inline
         mock maker — the default since Mockito 5 — handles final
         classes and final methods too.

     KEEP THE INTERFACE WHEN: there are genuinely two or more
     implementations; it is a PORT owned by the consumer across a
     module boundary (Part 5); or it is published API where
     committing to a concrete class would be a compatibility
     mistake you cannot undo.

  4. THE FACTORY THAT MAKES ONE THING.

       class UserFactory {
           User create(String name) { return new User(name); }
       }

     `new` is already a factory, and it is one every Java programmer
     already knows how to read. A factory earns its place when
     construction is CONDITIONAL (the concrete type is chosen at
     runtime), EXPENSIVE and pooled or cached, must run VALIDATION
     that cannot be bypassed (then use a static factory method on the
     type itself), or must hand back a subtype the caller must not
     name.

  5. THE COST OF THE WRONG ABSTRACTION. Sandi Metz's formulation is
     the most useful sentence here: DUPLICATION IS FAR CHEAPER THAN
     THE WRONG ABSTRACTION.

       duplication          visible, greppable, deletable; the cost
                            is bounded and obvious
       wrong abstraction    fifteen call sites depend on it; case
                            sixteen does not fit, so someone adds a
                            boolean parameter, then another, and
                            within a year the method is a maze of
                            flags nobody dares touch

     The exit cost is the asymmetry that matters: removing
     duplication is a refactor, while removing a wrong abstraction
     means INLINING IT AT EVERY CALL SITE FIRST and then
     re-abstracting — which nobody has time for, so it stays.

     ORDER OF OPERATIONS: write it, duplicate it, and on the THIRD
     occurrence look at all three together and abstract what they
     genuinely share. Three data points beat one guess, every time.

  6. THE READING TAX IS PAID DAILY; THE EXTENSION DIVIDEND MAY NEVER
     ARRIVE. Every layer of indirection costs every future reader a
     jump, forever. That is a real recurring cost charged against a
     speculative one-off benefit. Price it that way and most
     speculative abstractions stop looking free.

Interview Questions

Beginner: What does the Single Responsibility Principle actually say, and what is the usual misreading?

The usual misreading is "a class should do one thing", which is unfalsifiable — a class that saves an order "does one thing" at some level of description, and so does an entire application. Martin's own clarification is the useful version: a module should be responsible to one, and only one, actor. A reason to change is a person who asks for the change.

So the test is social, not structural. Take each method and name the human who would file the ticket. A payroll class where computeNetPay answers to finance, monthlyHoursReport answers to operations, and save answers to the DBA has three actors and should be three classes.

The reason this matters is not tidiness. It is the shared private helper. If both the pay calculation and the hours report call a private regularHours(), then a change finance requested — "overtime starts at 38 hours now" — silently changes a report operations owns, and nobody tests it because nobody knew the coupling existed.

The inverse misreading is just as costly: SRP does not mean one method per class. A class with eight methods that all serve the same actor and share the same fields has exactly one reason to change and is correct as written. Splitting it produces single-method classes that coordinate through shared mutable state, which is strictly more coupled than what you started with.

Beginner: What is the Liskov Substitution Principle, and can you give a real example?

If S is a subtype of T, code written against T must keep working when handed an S. The important word is behaviour: the compiler already checks signatures, so LSP is entirely about the promises that signatures cannot express.

The textbook example is Square extends Rectangle with setters. A client does setWidth(5); setHeight(4); and expects an area of 20; a square gives 16. Geometry is not the issue — a square is a rectangle. The issue is that mutable Rectangle has an unwritten invariant, "setting the width does not change the height", which Square cannot honour. Make both immutable records and the problem disappears entirely, which tells you the real culprit was mutability.

The example worth quoting in an interview is in the JDK. Arrays.asList("a","b").add("c") throws UnsupportedOperationException, and so does everything on List.of(...). add is declared on List, so a method taking a List and calling add is type-correct and still crashes depending on who built the argument. The Javadoc legalises it with the phrase "optional operation", which is the contract being weakened until the violation is permitted.

Two practical rules come out of that: never mutate a collection you did not construct (copy with new ArrayList<>(incoming) if you must), and treat every UnsupportedOperationException you write as a signal that an interface is too wide.

Mid: You see interface UserService with exactly one implementation, UserServiceImpl. Is that a problem?

Usually yes, and it is worth being specific about the cost rather than just calling it unnecessary. You pay for two files instead of one, a name that had to be invented (Impl means "the one that does it", which is no information at all), and a permanent navigation tax: every "go to definition" lands on an empty method, so every reader takes two jumps to reach real code.

Both traditional defences are dead. "We might swap the implementation" is a guess made a year before the evidence; Extract Interface is a five-second IDE refactor at the moment a real second implementation exists, and the interface you design then — with two concrete cases in front of you — will be better than the one you guess now. "We need it to mock" has been false since Mockito could generate subclasses of concrete classes, and the inline mock maker (the default since Mockito 5) handles final classes and methods as well.

There are three cases where it is right, and it is worth naming them so the answer is not dogmatic:

Keep the interface whenBecause
Two or more real implementations existThat is polymorphism, which is what interfaces are for
It is a port owned by the consumerIt inverts a module dependency and makes fast in-memory test doubles possible
It is published API for other teamsCommitting to a concrete class is a compatibility decision you cannot reverse

Note that the second case is not "an interface" in the same sense at all. The port lives in the consumer's package and is named in the consumer's vocabulary, and the naming convention gives it away: OrderRepository implemented by JdbcOrderRepository is a port; OrderService implemented by OrderServiceImpl is a habit.

Mid: Is Dependency Inversion the same thing as Dependency Injection?

No, and conflating them is why so many codebases have injection everywhere and no inversion anywhere. Dependency injection is a mechanism — a class receives its collaborators instead of constructing them. Dependency inversion is a direction — a statement about which module owns the abstraction and therefore which way the compile-time arrow points.

You can inject without inverting. If OrderService takes an OrderDao in its constructor, but OrderDao lives in the persistence package and its methods return ResultSet and throw SQLException, then the high-level module still imports the low-level one and the abstraction still depends on the detail. That violates both sentences of the principle while looking exactly like textbook DI.

You can also invert without a framework. Declare OrderRepository in the domain package in domain vocabulary, implement it in orders.jdbc, and wire it with new in main. No container, full inversion.

The test I would give in a review has nothing to do with annotations: could you delete the adapter package and still compile the domain? In Maven that is enforceable rather than aspirational — the domain module simply does not declare the JDBC driver as a dependency, and the build fails if anyone imports it. A build file is a more reliable architecture reviewer than a human.

The payoff is concrete: domain tests that need no database and no application context. A suite that runs in a few hundred milliseconds gets run on every save; one that spends 40 seconds starting a context per test class gets run in CI and hoped about.

Senior: Open/Closed via polymorphism, or a sealed interface with an exhaustive switch? Argue both and give a recommendation.

This is the expression problem, and the honest answer is that the two options optimise opposite directions of growth, so the question is empirical: which direction does this code actually grow in?

PolymorphismSealed + switch
New typeOne file, zero editsCompile error at every switch — a guided worklist
New operationEdit the interface and all N implementationsOne method, one place
Missing caseSilently inherits a default, or a stale super callWill not compile
Who may extendAnyone, including code you never seeOnly the owning module

The case for polymorphism is that behaviour lives with data and adding a type touches nothing tested. Its real weakness is exhaustiveness: nothing tells you that Crypto forgot to override settlementDelay(), so it inherits a default that is wrong and ships silently. That failure is much harder to find than a compile error.

The case for sealed types is that the compiler enumerates the work. Adding a payment method fails the build at all five places you must update, which converts shotgun surgery from a production incident into a checklist. The price is that the type set is closed — no external module can add a case — and that behaviour lives away from the data it operates on.

My recommendation: if you own the full set of types and it is genuinely closed — order states, payment methods, AST nodes, protocol messages — use a sealed interface with exhaustive switches, because compiler-enforced completeness is worth more than the ability to add a case without editing. Reserve polymorphic OCP for sets that are genuinely open: plugins, third-party strategies, anything other teams extend. And in both cases, wait for the third variation before abstracting at all — two cases is not evidence about the axis of change, and an abstraction on the wrong axis makes the change you eventually get more expensive, not less.

Senior: When would you deliberately not apply SOLID, and how do you defend that in code review?

I would start by reframing what is being defended. SOLID is a set of heuristics for two older properties — high cohesion and low coupling. If I can argue that a design has better cohesion and lower coupling than the "SOLID" alternative, I have won the argument on the merits, and citing a letter of the acronym back at me is the weaker position.

The clear cases where I skip it outright: scripts and one-off migrations, where the payoff is amortised over future changes that will never happen; and prototypes, where the risk is not bad structure but that good structure makes throwaway code look shippable.

The contested cases are the ones worth having a rehearsed argument for. A one-implementation interface costs two files and a permanent navigation tax and buys flexibility nobody has used — and Mockito has mocked concrete classes for over a decade, so the testing justification is gone. A factory that only calls new is a rename of a language feature. Both are speculative generality, and the asymmetry I lean on is that the reading cost is paid every day by every reader, while the extension benefit is speculative and may never arrive at all.

The strongest argument, and the one that actually changes minds, is Metz's: duplication is far cheaper than the wrong abstraction. Duplication is visible, greppable and deletable, and its cost is bounded. A wrong abstraction acquires fifteen call sites, then a boolean parameter when case sixteen does not fit, then another — and removing it means inlining it everywhere first, which nobody schedules. So the exit costs are wildly asymmetric, which is why waiting for the third occurrence is the disciplined choice rather than the lazy one.

In review I try to make it concrete rather than philosophical: "what change are we buying protection against, and what is our evidence it is coming?" If there is a real answer — a second payment provider already in the roadmap, a database migration already scheduled — I build the abstraction happily. If the answer is "you never know", that is the definition of speculative, and I would rather pay a five-second Extract Interface later than a navigation tax forever.

The one place I never negotiate is LSP. Cutting corners on SRP costs maintainability, which is recoverable; a substitutability violation produces wrong answers with no exception, and those are found by customers rather than by tests.

    var out = new ArrayList<>(items);      // defensive copy
    out.add(new LineItem("DISCOUNT", discountFor(items)));
    return List.copyOf(out);               // hand back something safe
}

Why returning is better than mutating, beyond dodging the exception: the original signature took a List and secretly required a mutable one, a precondition that appears nowhere in the type. The new one takes any list at all and states its effect in its return type, so it is impossible to call incorrectly.

The testing lesson generalises well past collections: the test constructed the most permissive implementation available, so it verified the easiest case rather than the realistic one. Where an interface has behavioural variants, test against the awkward variant — that is the one production will hand you.

3 (medium): Refactor this to satisfy OCP — then argue the case for leaving it alone. 
BigDecimal fee(Payment p) {
    switch (p.type()) {
        case CARD: return p.amount().multiply(new BigDecimal("0.029"));
        case ACH:  return new BigDecimal("0.25");
    }
    throw new IllegalArgumentException();
}

Duration settlement(Payment p) { /* the same switch */ }
boolean  refundable(Payment p) { /* the same switch */ }
Solution 
// THE OCP REFACTOR — behaviour travels with the type:
interface PaymentMethod {
    BigDecimal fee(Money amount);
    Duration   settlement();
    boolean    refundable();
}

record Card(Brand brand) implements PaymentMethod {
    public BigDecimal fee(Money a) { return a.times("0.029"); }
    public Duration settlement()   { return Duration.ofDays(2); }
    public boolean refundable()    { return true; }
}

record Ach(Iban iban) implements PaymentMethod {
    public BigDecimal fee(Money a) { return new BigDecimal("0.25"); }
    public Duration settlement()   { return Duration.ofDays(3); }
    public boolean refundable()    { return false; }
}

What the original actually costs at runtime: not the switch itself, but the three of them. Adding WIRE means finding all three and any others that have appeared since — shotgun surgery. Miss one and you get either an IllegalArgumentException in the settlement path, or, if a helpful colleague added a default: branch, a plausible wrong number that reconciliation will find in a month.

Now the argument against. With exactly two cases, the refactor produces an interface, two record files and a construction site that must decide which record to build — the switch did not disappear, it moved into a factory. If the next change is not a new payment type but "fees now depend on the merchant's country", you edit the interface and every implementation: N files where the switch would have been one.

SituationDo this
Two cases, one axis, no third in sightLeave the switch; revisit on the third case
Types are closed and you own themsealed interface Payment + exhaustive switches
Third parties add payment typesPolymorphic PaymentMethod
Operations grow faster than typesKeep the switch — adding one is a single method
// THE OPTION MOST PEOPLE MISS — closed set, compiler-enforced:
sealed interface Payment permits Card, Ach { }

BigDecimal fee(Payment p) {
    return switch (p) {                       // no default branch
        case Card c -> c.amount().multiply(RATE);
        case Ach  a -> FLAT_25;
    };
}

Adding Wire to the permits clause now breaks the build at all three switches and does not compile until every one is handled. That is not OCP — it is deliberately closed — but it eliminates the failure mode the refactor was aimed at, with a fraction of the machinery. For a payment type set that only you can extend, this is the design I would ship.

package com.acme.persistence;

package com.acme.orders;

Solution

Injection is present; inversion is not. The interface was almost certainly produced by Extract Interface on the DAO, which by construction yields a mirror of the implementation. Because it is a mirror, it changes whenever the implementation does — swap to a document store and the interface changes, so OrderService changes, which is precisely what the principle exists to prevent.

package com.acme.orders;                 // the HIGH-LEVEL module OWNS this

public interface OrderRepository {
    Optional<Order> findById(OrderId id);
    List<Order>     findOpenFor(CustomerId customer);   // no SQLException
    void            save(Order order);
}

package com.acme.orders.jdbc;            // the adapter DEPENDS on the domain

class JdbcOrderRepository implements OrderRepository {
    public List<Order> findOpenFor(CustomerId c) {
        try (var st = ds.getConnection().prepareStatement(SQL)) {
            ...
        } catch (SQLException e) {
            throw new OrderLookupFailed(c, e);   // domain vocabulary
        }
    }
}

Three changes, and each is load-bearing. The interface moved into the consumer's package, so the compile-time arrow now points from the adapter to the domain — the inversion. ResultSet became List<Order>, so the abstraction no longer depends on the detail. SQLException — a checked exception that leaked JDBC into every caller's signature — is caught at the boundary and translated, so a caller no longer has to know a database exists.

The check that proves it worked is a build-file check, not a code-review opinion: the domain module does not declare the JDBC driver as a dependency. If someone re-introduces an import java.sql.* in the domain, the build fails. Architecture rules that a compiler enforces are the only kind that survive a year.

And the dividend is test speed. With the port owned by the domain, an in-memory Map-backed OrderRepository is about fifteen lines, and the domain suite runs in a few hundred milliseconds rather than spending tens of seconds per class starting an application context — which is the difference between tests you run on save and tests you run in CI.

5 (hard): Diagnose every principle violated here, then fix it. Say specifically whether a default method would help. 
interface PaymentGateway {
    Charge       charge(Money m, Card c);
    Refund       refund(ChargeId id, Money m);
    Subscription subscribe(Plan p, Card c);
    Token        tokenize(Card c);
    Payout       payout(BankAccount a, Money m);
}

class SimpleGateway implements PaymentGateway {
    public Charge charge(Money m, Card c) { ... }
    public Refund refund(ChargeId id, Money m) { ... }
    public Subscription subscribe(Plan p, Card c) {
        throw new UnsupportedOperationException();
    }
    public Token tokenize(Card c) { throw new UnsupportedOperationException(); }
    public Payout payout(BankAccount a, Money m) {
        throw new UnsupportedOperationException();
    }
}

class Checkout {
    Checkout(PaymentGateway gateway) { ... }   // only ever calls charge()
}
Solution
PrincipleHow it is violated
ISPSimpleGateway must compile against five capabilities it lacks; Checkout depends on four methods it never calls
LSPAny holder of a PaymentGateway may call subscribe and get an exception the interface never advertised
DIPThe interface was shaped by what gateways offer, not by what Checkout needs — the abstraction serves the detail
OCP (secondary)A gateway with one extra capability forces a change to the shared interface and therefore to every implementation

What happens at runtime today: nothing, for months. Checkout only calls charge, so SimpleGateway works fine — until someone adds a "save this card for next time" feature, calls tokenize on the injected gateway, tests it against Stripe in staging where it works, and ships it to the tenant configured with SimpleGateway. The failure lands in production, in a payment path, and the stack trace blames a caller that did nothing wrong.

// SPLIT BY CLIENT CAPABILITY:
interface Charging    { Charge charge(Money m, Card c); }
interface Refunding   { Refund refund(ChargeId id, Money m); }
interface Tokenizing  { Token  tokenize(Card c); }
interface Subscribing { Subscription subscribe(Plan p, Card c); }

class StripeGateway implements Charging, Refunding, Tokenizing, Subscribing { }
class SimpleGateway implements Charging, Refunding { }

class Checkout {
    Checkout(Charging gateway) { ... }     // declares exactly what it needs
}

What the split actually buys is a compile-time failure at the wiring instead of a runtime failure in production. Injecting SimpleGateway where a Tokenizing is required does not compile, and Checkout can no longer call subscribe by accident because the type it holds has no such method. The bug class is eliminated rather than relocated.

Would a default method help? No — it makes it worse.

interface PaymentGateway {
    Charge charge(Money m, Card c);
    default Subscription subscribe(Plan p, Card c) {
        throw new UnsupportedOperationException();      // ❌
    }
}

This deletes the compile error that was reporting the design problem and reschedules the failure for runtime. Before, an implementer was at least forced to look at subscribe and write something; now they never see it. A default that returned a plausible wrong value — an empty list, false, null — would be worse still, trading a stack trace for silently wrong behaviour in a money path.

The rule that distinguishes the two cases: a legitimate default has a correct universal implementation written in terms of the interface's own abstract methods. Iterable.forEach is defined by iterator() and cannot be wrong for any implementation. subscribe has no such definition, which is exactly the evidence that it does not belong on this interface.

// WHAT I WOULD ACTUALLY CHANGE — and none of it is structure:
public class ImportProducts {
    public static void main(String[] args) throws Exception {
        var rows = Files.readAllLines(Path.of(args[0]), UTF_8);   // explicit charset
        try (var conn = DriverManager.getConnection(args[1]);
             var st   = conn.prepareStatement(
                 "INSERT INTO product(sku, price) VALUES (?,?)")) {
            conn.setAutoCommit(false);                            // 40k autocommits
            int line = 1;
            for (String row : rows.subList(1, rows.size())) {
                line++;
                String[] f = row.split(",", -1);                  // keep trailing empties
                if (f.length < 4) throw new IOException(
                        "line " + line + ": expected 4 columns, got " + f.length);
                st.setString(1, f[0]);
                st.setBigDecimal(2, new BigDecimal(f[3]));
                st.addBatch();
                if (line % 1000 == 0) st.executeBatch();
            }
            st.executeBatch();
            conn.commit();
        }
    }
}
ChangeWhy it beats every structural request
setAutoCommit(false) + batching40,000 individual commits against a remote database is minutes of round trips; batches of 1000 in one transaction is seconds
Line number in the errorThe one thing you will actually need at 2am when row 31,447 has a stray comma
split(",", -1)The default drops trailing empty fields, so a row ending in ,, silently becomes short
Explicit UTF_8Platform default charset differs between your laptop and the server — a classic vendor-file corruption

The point of the exercise: the reviewer optimised for changes that will never happen and missed every failure that will. Correctness at the trust boundary, error messages that locate the problem, and not taking twenty minutes to run are what this code is judged on.

What would change my answer: if this script were scheduled nightly, everything shifts. Then it has a future, failures repeat, and a ProductRepository port earns its cost by making the parsing testable without a database. The design question is never "is this SOLID" — it is "how many more changes will this code see, and who will make them?"

🎯 Key Takeaways

  • SRP means one actor, not one method — name the human who files the ticket; two names with two budgets means two classes.
  • The dangerous part of an SRP violation is the shared private helper, which delivers one actor's change to another actor untested.
  • OCP is a bet on the axis of variation; an abstraction on the wrong axis makes the change you actually get more expensive, not less.
  • A sealed type with an exhaustive switch often beats OCP when the type set is closed and you own it — the compiler enumerates every site you must update.
  • LSP is about behaviour, and javac checks only signatures — the gap is where the bugs live.
  • Preconditions may be weakened, never strengthened; postconditions strengthened, never weakened — a weakened postcondition returns wrong answers without throwing.
  • Square/Rectangle is a mutability problem, not a geometry one; immutable records have no history constraint to violate.
  • Arrays.asList(x).add(y) throws — the JDK ships an LSP violation and legalises it with the phrase "optional operation".
  • Never mutate a collection you did not construct; copy with new ArrayList<>(incoming) and return List.copyOf.
  • UnsupportedOperationException is an ISP violation announcing itself as an LSP failure — go and find the interface that is too wide.
  • A default method is legitimate only with a correct universal implementation written in terms of the interface's own abstract methods; one that throws just deletes the compile error.
  • DIP is about who owns the abstraction — the consumer declares the interface it needs, which is why the compile-time arrow points opposite to the call.
  • The test for DIP is a build-file question: can the domain module compile with the adapter deleted and the driver not on its classpath?
  • SOLID is a proxy for cohesion and coupling; when a letter and those two properties disagree, follow the properties.
  • Extract for a name, reuse, or a mixed abstraction level — never for a line count; fields invented to pass state between private methods mean you over-extracted.
  • Comment the why: a name cannot hold a ticket number, a vendor bug, or the reason you rejected the obvious approach.
  • Duplication is far cheaper than the wrong abstraction — the exit costs are wildly asymmetric, so wait for the third occurrence.
  • A one-implementation interface and a factory that only calls new are pure cost; the reading tax is paid daily, the extension dividend may never arrive.
