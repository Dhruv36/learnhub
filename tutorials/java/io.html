Files & I/O Core Libraries

What you'll master: the distinction the whole API is built on — byte streams carry bytes and character streams carry text, and the boundary between them is where an encoding must be named or silently guessed; why Files.readAllLines on a large file is an OutOfMemoryError waiting to happen and what streaming replaces it with; why try-with-resources exists and what it fixed — the classic finally block that loses the original exception; why an unbuffered read of a million lines can be orders of magnitude slower than a buffered one, because each call is a syscall; why Files.lines must be closed even though it looks like a stream; and the path traversal check that string comparison does not give you. Prerequisites: Strings for encodings, and Exceptions.

Part 1 — Bytes or Characters

  TWO PARALLEL HIERARCHIES, AND CHOOSING THE WRONG ONE CORRUPTS DATA.

    BYTES        InputStream / OutputStream
                 images, PDFs, compressed data, network protocols,
                 anything you do not intend to interpret

    CHARACTERS   Reader / Writer
                 text — and text ALWAYS has an encoding

  THE BRIDGE BETWEEN THEM IS WHERE ENCODING IS DECIDED:

    new InputStreamReader(inputStream, StandardCharsets.UTF_8)
    new OutputStreamWriter(outputStream, StandardCharsets.UTF_8)

  OMIT THE CHARSET AND YOU GET THE PLATFORM DEFAULT. Since Java 18
  that is UTF-8 everywhere, which removed a large class of
  works-on-my-machine bugs — before that it varied by OS and locale,
  so the same code produced different bytes on a developer laptop and
  a Linux server.

  Name it anyway: it documents intent, and it is correct on older
  runtimes.

  READING A BINARY FILE AS TEXT IS THE CLASSIC CORRUPTION:

    String s = Files.readString(imagePath);   // bytes that are not
                                              // valid UTF-8 become
                                              // U+FFFD, irreversibly
    Files.writeString(copy, s);               // the image is now
                                              // destroyed

  Decoding is lossy for invalid sequences. Once a byte has become the
  replacement character, the original value is gone — so a
  read-as-text, write-as-text round trip does not preserve binary
  data.

Part 2 — The Modern API: Path and Files

Path path = Path.of("data", "orders.csv");     // NOT new File(...)

// SMALL FILES — the whole thing in memory
String content       = Files.readString(path);
List<String> lines   = Files.readAllLines(path);
byte[] bytes         = Files.readAllBytes(path);

// WRITING
Files.writeString(path, content);
Files.write(path, bytes);
Files.writeString(path, text, StandardOpenOption.APPEND);

// METADATA AND MANIPULATION
Files.exists(path);   Files.size(path);   Files.isDirectory(path);
Files.createDirectories(path.getParent());
Files.copy(src, dst, StandardCopyOption.REPLACE_EXISTING);
Files.move(src, dst, StandardCopyOption.ATOMIC_MOVE);
Files.delete(path);            // throws if absent
Files.deleteIfExists(path);    // returns false

  WHY Path RATHER THAN File

    File.delete()      returns false on failure — WHY it failed is
                       lost. Permissions? Missing? In use?
    Files.delete()     throws NoSuchFileException,
                       DirectoryNotEmptyException, AccessDeniedException

  The old API signalled failure with boolean returns that were
  routinely ignored, and gave no diagnostic when checked. That alone
  justifies the migration — plus symbolic links, file attributes,
  atomic moves and directory watching, none of which File supports.
⚠️ Files.readAllLines on a large file is an OutOfMemoryError. It materialises every line as a String in a List, so a 2 GB log file needs several gigabytes of heap — Java strings carry object overhead per line, so the in-memory form is considerably larger than the file. The methods that read everything at once are for configuration files and small documents. Anything whose size is determined by production data needs streaming.

Part 3 — try-with-resources

  THE PROBLEM IT SOLVED

    BufferedReader r = null;
    try {
        r = new BufferedReader(new FileReader(path));
        return r.readLine();                    // throws IOException
    } finally {
        if (r != null) r.close();               // ALSO throws
    }

  If both throw, the exception from close() REPLACES the original —
  so you lose the real failure and see a misleading one from cleanup.
  Getting this right by hand needs a nested try inside the finally,
  which almost nobody wrote.

  TRY-WITH-RESOURCES

    try (BufferedReader r = Files.newBufferedReader(path)) {
        return r.readLine();
    }                                  // close() is automatic

  Resources close in REVERSE order of declaration, and an exception
  from close() is SUPPRESSED rather than replacing the original —
  attached to it, and visible via getSuppressed() and in the printed
  stack trace.

  MULTIPLE RESOURCES, closed right to left:

    try (InputStream in = Files.newInputStream(src);
         OutputStream out = Files.newOutputStream(dst)) {
        in.transferTo(out);
    }

  ANY AutoCloseable WORKS — not just IO. ExecutorService (Java 19+),
  JDBC connections, locks wrapped in a closeable, and your own types.

Part 4 — Buffering

  AN UNBUFFERED READ IS ONE SYSCALL PER CALL.

    FileReader r = new FileReader(path);
    while ((c = r.read()) != -1) { … }        // a syscall per CHARACTER

  A system call costs on the order of a microsecond — a thousand times
  a memory access. Reading a 10 MB file character by character is
  roughly ten million syscalls.

  BUFFERING READS A BLOCK AT A TIME AND SERVES FROM MEMORY:

    try (BufferedReader r = Files.newBufferedReader(path)) {
        String line;
        while ((line = r.readLine()) != null) { … }
    }

  The default 8 KB buffer turns those ten million syscalls into about
  1,300. The difference is routinely two to three orders of magnitude
  on real files, which is why unbuffered IO is one of the few
  performance mistakes worth fixing on sight rather than after
  measurement.

  THE Files FACTORY METHODS ARE ALREADY BUFFERED:

    Files.newBufferedReader(path)      buffered
    Files.lines(path)                  buffered
    Files.readString(path)             reads in blocks

  So the mistake is mostly made by reaching for `new FileReader` out
  of habit.

  WRITING HAS AN EXTRA HAZARD: BUFFERED DATA IS NOT WRITTEN YET.

    Writer w = new BufferedWriter(...);
    w.write("important");
    // process exits without close() -> THE DATA IS LOST

  close() flushes. try-with-resources guarantees it. A buffered writer
  that is never closed silently discards whatever is still in the
  buffer — which is why a "missing last few lines" bug is nearly
  always a missing close.

Part 5 — Streaming Large Files

  THE STREAMING FORMS KEEP MEMORY FLAT REGARDLESS OF FILE SIZE:

    try (Stream<String> lines = Files.lines(path)) {     // MUST close
        long errors = lines.filter(l -> l.contains("ERROR")).count();
    }

    try (var reader = Files.newBufferedReader(path)) {
        String line;
        while ((line = reader.readLine()) != null) { … }
    }

  Files.lines READS LAZILY, one line at a time, so a 50 GB file uses
  constant memory.

  AND IT MUST BE CLOSED, WHICH LOOKS WRONG. Most streams need no
  cleanup — but this one holds an open file handle, so it implements
  AutoCloseable. Forgetting it leaks a descriptor per call, and the
  symptom is "Too many open files" much later, in unrelated code, once
  the process hits its limit.

  THAT IS WHY IT MUST BE IN try-with-resources, and why
  Files.lines(path).filter(...).count() as a one-liner is a leak.

  WALKING A DIRECTORY TREE — same rule:

    try (Stream<Path> paths = Files.walk(root)) {
        paths.filter(Files::isRegularFile).forEach(this::process);
    }

  Files.walk keeps directory handles open as it descends, so an
  unclosed walk leaks more than one.

  COPYING BETWEEN STREAMS

    in.transferTo(out);            // Java 9+, buffered internally
    Files.copy(src, dst);          // and it may use a zero-copy
                                   // system call where the OS
                                   // supports it

Part 6 — Path Traversal and Atomic Writes

  PATH TRAVERSAL — STRING CHECKS DO NOT WORK

    String name = request.getParameter("file");   // "../../etc/passwd"
    Path p = Path.of("/uploads", name);

    if (p.toString().startsWith("/uploads")) { … }   // ❌ TRUE, and
                                                     //    still escapes

  The string does start with /uploads. The path still resolves outside
  it, because ".." is only interpreted when the path is normalised.

  THE CORRECT CHECK — NORMALISE FIRST, THEN COMPARE PATHS:

    Path base = Path.of("/uploads").toAbsolutePath().normalize();
    Path target = base.resolve(name).normalize();

    if (!target.startsWith(base))
        throw new SecurityException("path traversal: " + name);

  Two things matter here. normalize() collapses ".." and "."; and
  Path.startsWith compares PATH ELEMENTS, not characters — so
  "/uploads-other" does not start with "/uploads", where the string
  version would say it does.

  For symlinks, toRealPath() resolves them and is stronger still —
  though it requires the file to exist.

  ATOMIC WRITES — DO NOT OVERWRITE IN PLACE

    Files.writeString(config, newContent);    // ❌ a crash mid-write
                                              //    leaves a truncated
                                              //    file, and the old
                                              //    content is gone

    Path tmp = config.resolveSibling(config.getFileName() + ".tmp");
    Files.writeString(tmp, newContent);
    Files.move(tmp, config, StandardCopyOption.ATOMIC_MOVE,
                            StandardCopyOption.REPLACE_EXISTING);

  A rename within the same filesystem is atomic: readers see either
  the old file or the new one, never a half-written one. ATOMIC_MOVE
  across filesystems throws rather than silently degrading to a copy,
  which is the behaviour you want — the temp file must be a sibling.

Interview Questions

Beginner: What is the difference between a stream and a reader?

InputStream and OutputStream carry bytes; Reader and Writer carry characters.

Use byte streams for anything you do not intend to interpret — images, PDFs, compressed data, network protocols. Use character streams for text.

The important part is the boundary: converting bytes to characters requires an encoding, and that is what InputStreamReader and OutputStreamWriter exist to specify. If you do not name a charset you get the platform default — which since Java 18 is UTF-8 everywhere, and before that varied by operating system and locale, producing the classic works-on-my-machine bug.

Choosing wrongly corrupts data. Reading an image with Files.readString turns every invalid byte sequence into the replacement character, irreversibly — so writing it back out destroys the file.

Beginner: Why is try-with-resources better than a finally block?

Because of what happens when both the body and the cleanup throw.

In a hand-written finally, calling close() can itself throw — and that exception replaces the one from the body. So you lose the real failure and see a misleading one from cleanup. Writing it correctly requires a nested try inside the finally, which almost nobody does.

try-with-resources suppresses the close exception instead: the original propagates, and the secondary is attached to it, visible through getSuppressed() and printed in the stack trace. Nothing is lost.

It also guarantees closure on every path — including returns and breaks — and closes multiple resources in reverse order of declaration, which is what you want when one wraps another.

It works for any AutoCloseable, not just IO: JDBC connections, ExecutorService since Java 19, and your own types.

Mid: Why does buffering matter so much?

Because an unbuffered read performs a system call per operation, and a syscall costs roughly a microsecond — about a thousand times a memory access.

Reading a 10 MB file one character at a time is around ten million syscalls. With an 8 KB buffer the same file needs about 1,300 — the buffer is filled in one call and subsequent reads are served from memory.

The difference is routinely two to three orders of magnitude, which makes it one of the few performance issues worth fixing on sight rather than after profiling.

The Files factory methods are already buffered, so the mistake is mostly made by reaching for new FileReader out of habit.

On the write side there is a second hazard: buffered data has not been written until the buffer is flushed. A writer that is never closed silently discards whatever is still buffered, which is why a "the last few lines are missing" bug is nearly always a missing close — and why try-with-resources matters as much for writing as for reading.

Mid: Why must Files.lines() be closed when most streams need no cleanup?

Because it holds an open file handle. Most streams are backed by an in-memory collection and need no cleanup, so Files.lines is the exception — it implements AutoCloseable precisely because it owns an OS resource.

Not closing it leaks a file descriptor per call. Descriptors are a per-process limit, so the failure is delayed and displaced: the process runs fine until it hits the ceiling, and then unrelated code fails with "Too many open files" — possibly a socket accept, or a log rotation.

That distance between cause and symptom is what makes it expensive. The leaking method is usually not in the stack trace at all.

So Files.lines(path).filter(...).count() written as a one-liner is a leak, and it looks perfectly idiomatic — which is the trap. It belongs in try-with-resources.

The same applies to Files.walk, Files.list and Files.find, and walk is worse because it holds a directory stream per level as it descends.

Senior: How do you prevent path traversal?

Not with string comparison, which is the common attempt and does not work.

Path p = Path.of("/uploads", userInput);        // "../../etc/passwd"
p.toString().startsWith("/uploads")             // TRUE — and it escapes

The string genuinely does begin with /uploads; the path still resolves outside it, because .. segments are only interpreted when the path is normalised.

Path base   = Path.of("/uploads").toAbsolutePath().normalize();
Path target = base.resolve(userInput).normalize();

if (!target.startsWith(base))
    throw new SecurityException("path traversal attempt");

Two things make this correct. normalize() collapses the .. and . segments, so the check sees where the path actually points. And Path.startsWith compares path elements rather than characters — so /uploads-other does not start with /uploads, where the string version would wrongly say it does.

For stronger guarantees, toRealPath() also resolves symbolic links, closing the case where an attacker-controlled symlink inside the upload directory points elsewhere. It requires the file to exist, so it suits reads rather than creates.

Defence in depth beyond the path check: validate the filename against an allow-list of characters, generate server-side names rather than trusting the client's, and store uploads outside the web root so that even a successful traversal does not yield an executable location.

Senior: How do you write a file so a crash cannot corrupt it?

Never overwrite in place. Write to a temporary file and rename it over the target.

Path tmp = target.resolveSibling(target.getFileName() + ".tmp");
Files.writeString(tmp, content);
Files.move(tmp, target, StandardCopyOption.ATOMIC_MOVE,
                        StandardCopyOption.REPLACE_EXISTING);

A rename within a single filesystem is atomic at the OS level: any reader sees either the complete old file or the complete new one, never a partial write. Writing directly means a crash or a full disk mid-write leaves a truncated file and the original is already gone.

The temp file must be a sibling, because atomicity only holds within a filesystem. Across a mount boundary the move degrades to copy-then-delete, which is not atomic — ATOMIC_MOVE throws in that case rather than silently doing the unsafe thing, which is the behaviour you want.

For durability rather than just atomicity, the rename is not sufficient on its own: the data may still be in the OS page cache. A FileChannel.force(true) on the temp file before the move, and ideally on the directory afterwards, is what survives a power loss. That is what databases do, and it is worth the cost only when the data genuinely must survive a crash.

The same pattern generalises beyond files — it is why a deploy writes a new directory and flips a symlink rather than editing in place.

🏋️ Graded Exercises

1 (easy): Why does this fail on a 3 GB log file, and what replaces it? 
List<String> lines = Files.readAllLines(logPath);
long errors = lines.stream().filter(l -> l.contains("ERROR")).count();
Solution

readAllLines materialises every line as a String in a List, so the whole file plus per-object overhead must fit in the heap. A 3 GB file typically needs well over 6 GB — Java strings carry an object header and a separate byte array per line.

try (Stream<String> lines = Files.lines(logPath)) {      // MUST close
    long errors = lines.filter(l -> l.contains("ERROR")).count();
}

Files.lines reads lazily — one line at a time, discarded after it passes through the pipeline — so memory stays flat regardless of file size.

The try-with-resources is not optional. Unlike most streams, this one holds an open file handle, so the one-liner version leaks a descriptor per call and eventually produces "Too many open files" somewhere unrelated.

MethodMemoryUse for
readAllLines / readStringO(file size)Config files, small documents
Files.linesO(1)Anything whose size is set by production data
BufferedReader loopO(1)The same, when you need checked exceptions or early exit

The rule worth extracting: any method whose name says "all" — readAllLines, readAllBytes, toList on an unbounded source — is a memory decision, and it is only safe when you control the size.

2 (easy): The last few lines are missing from the output file. Why? 
BufferedWriter w = Files.newBufferedWriter(out);
for (String line : lines) {
    w.write(line);
    w.newLine();
}
Solution

The writer is never closed, so whatever is still in the buffer is never flushed. A buffered writer accumulates up to 8 KB before writing to the OS — so the final partial buffer is lost when the process ends or the object is collected.

try (BufferedWriter w = Files.newBufferedWriter(out)) {
    for (String line : lines) {
        w.write(line);
        w.newLine();
    }
}                                    // close() flushes

The symptom is characteristic: the file is almost right. Most of the content is there and the tail is missing, which sends people looking for a loop bug rather than a resource one — and the amount missing varies with the buffer's fill level, so it changes between runs.

flush() alone is not enough — it pushes the buffer out but leaves the file handle open, so you have swapped lost data for a descriptor leak. close() does both.

The same failure with more consequence is a log file or an audit trail: the process crashes, and the last entries — precisely the ones describing the failure — are the ones lost.

3 (medium): Why is the original exception lost, and how does try-with-resources fix it? 
BufferedReader r = null;
try {
    r = Files.newBufferedReader(path);
    return parse(r);                    // throws ParseException
} finally {
    if (r != null) r.close();           // throws IOException
}
Solution

An exception thrown from a finally block replaces any exception in flight. So the IOException from close() propagates and the ParseException — the one that describes what actually went wrong — is discarded entirely.

try (BufferedReader r = Files.newBufferedReader(path)) {
    return parse(r);
}
// ParseException propagates.
// IOException from close() is SUPPRESSED and attached to it.

Suppression is the mechanism. The secondary exception is added to the primary's suppressed list, printed in the stack trace under "Suppressed:", and reachable through getSuppressed(). Nothing is lost, and the exception you see first is the one that matters.

Writing this correctly by hand is possible and nobody does it:

} finally {
    if (r != null) {
        try { r.close(); }
        catch (IOException e) { /* now what? log it? */ }
    }
}

Even that discards the close failure rather than attaching it, and it doubles the length of every resource block.

The wider lesson is that finally should not throw. Any exception from cleanup masks the real one, which is why cleanup code either must not fail or must handle its own failures — and why try-with-resources is the right default for anything closeable.

4 (medium): This check passes and the file still escapes. Fix it. 
String name = request.getParameter("file");
Path p = Path.of("/uploads", name);
if (p.toString().startsWith("/uploads")) {
    return Files.readAllBytes(p);
}
Solution

.. segments are not interpreted until the path is normalised, so the string genuinely starts with /uploads while pointing somewhere else entirely.

  name = "../../etc/passwd"
  p    = /uploads/../../etc/passwd        starts with "/uploads" ✓
  resolves to  /etc/passwd                                       ✗
Path base   = Path.of("/uploads").toAbsolutePath().normalize();
Path target = base.resolve(name).normalize();

if (!target.startsWith(base))
    throw new SecurityException("path traversal: " + name);

return Files.readAllBytes(target);

normalize()Collapses .. and ., so the check sees the real destination
Path.startsWith, not String.startsWithCompares path elements — so /uploads-other correctly does not match /uploads

The /uploads-other case is the one people miss. With string comparison it passes the check while being an entirely different directory — so the string version is wrong in both directions.

Symlinks need toRealPath(), which resolves them; an attacker who can create a symlink inside the upload directory defeats a normalise-only check. It requires the file to exist, so it fits reads rather than creates.

And in depth: generate server-side filenames rather than trusting the client's, and store uploads outside the web root so a successful traversal does not land somewhere executable.

5 (hard): A config file is occasionally found empty after a crash. Fix the write. 
Files.writeString(configPath, render(config));
Solution

Writing in place truncates the file first. There is a window — from truncation until the write completes — where the file exists and is empty or partial. A crash, a full disk, or a kill signal in that window destroys the configuration, and the previous content is already gone.

Path tmp = configPath.resolveSibling(configPath.getFileName() + ".tmp");

Files.writeString(tmp, render(config));
Files.move(tmp, configPath, StandardCopyOption.ATOMIC_MOVE,
                            StandardCopyOption.REPLACE_EXISTING);

A rename within one filesystem is atomic. Any reader sees the complete old file or the complete new one — the partial state is only ever visible in the temp file, which nothing reads.

DetailWhy
The temp file is a siblingAtomicity holds only within a filesystem; a temp directory may be a different mount
ATOMIC_MOVE throws across filesystemsCorrect behaviour — it refuses rather than silently degrading to a non-atomic copy
REPLACE_EXISTINGOtherwise the move fails when the target is present

For durability against power loss, the rename is not sufficient. The data may still sit in the OS page cache. Forcing it to disk before the move — and ideally forcing the directory entry afterwards — is what databases do:

try (FileChannel ch = FileChannel.open(tmp, WRITE)) {
    ch.force(true);          // flush data AND metadata to the device
}

That has a real cost — an fsync is milliseconds, not microseconds — so it is worth it for configuration and ledgers and not for a cache file. Deciding which one you have is the actual engineering judgement here.

6 (hard): A long-running service fails with "Too many open files" after several days. Diagnose.
Solution

A file descriptor leak — a resource opened per operation and never closed. Descriptors are a per-process limit, so the failure is delayed until the ceiling is reached and then appears in whatever code happens to open something next.

  DIAGNOSIS

    lsof -p <pid> | wc -l           how many, and growing?
    lsof -p <pid> | sort | uniq -c  WHICH resource repeats
    ulimit -n                       the limit being hit

  A repeated identical path in that output names the leak
  immediately.
Common sourceWhy it is missed
Files.lines(p).filter(...).count()Looks like an ordinary stream one-liner; it holds a file handle
Files.walk / list / findSame, and walk holds several while descending
A finally that can throw before closeThe close never runs on the exception path
Sockets and JDBC connectionsAlso descriptors — a connection pool leak looks identical
An exception between open and close()Correct on the happy path, leaks on every failure

The distance between cause and symptom is what makes it hard. The leaking code is not in the stack trace — the trace shows whichever unlucky call hit the limit, often a socket accept or a log rotation. So the failure points at innocent code.

The fix is try-with-resources everywhere, and the prevention is a static analyser rule for unclosed AutoCloseables. Modern IDEs flag most of these, including the Files.lines case, and enabling that check as an error is cheap.

What I would not do is raise ulimit. That converts a failure after three days into a failure after six, and it is the response that lets the actual leak survive to production twice.

🎯 Key Takeaways

  • Byte streams for data, character streams for text — and the bridge between them is where the encoding is decided.
  • Always name the charset. The platform default is UTF-8 only since Java 18.
  • Reading binary as text is irreversible — invalid sequences become the replacement character.
  • Path and Files over File, which signals failure with boolean returns that lose the reason.
  • readAllLines is a memory decision — safe for config, an OOM for production-sized data.
  • try-with-resources suppresses rather than replaces, so the real exception is never lost to a failing close.
  • Resources close in reverse order of declaration, and any AutoCloseable qualifies.
  • Unbuffered IO is one syscall per call — two to three orders of magnitude slower.
  • An unclosed writer silently loses its buffer, which is the "missing last lines" bug.
  • Files.lines and Files.walk hold file handles and must be closed, unlike most streams.
  • A descriptor leak fails later, in unrelated code — the trace never names the leak.
  • String checks do not prevent path traversal; normalise, then compare with Path.startsWith.
  • Path.startsWith compares elements, so /uploads-other does not match /uploads.
  • Write to a sibling temp file and ATOMIC_MOVE — overwriting in place can leave a truncated file with the original already gone.
  • Atomic is not durable; surviving power loss needs an explicit force.
