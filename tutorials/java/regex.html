Regular Expressions Core Libraries

What you'll master: the Java-specific mechanics that surround an otherwise portable syntax — Pattern.compile is expensive and String.matches recompiles on every call, which turns a validation in a loop into a measurable cost; the difference between matches and find that silently changes what your pattern means; greedy versus lazy quantifiers, and why the greedy one matches from the first opening tag to the last closing one; and the failure that takes production down — catastrophic backtracking, where a twenty-character input against an innocent-looking pattern runs for longer than the universe has existed, which is a denial-of-service vector whenever the input or the pattern comes from a user. Prerequisites: Strings — the split traps there are regex traps.

Part 1 — Pattern, Matcher, and the Cost of Compiling

  A regex must be COMPILED into a state machine before it can run.
  That is the expensive step, and Java makes it easy to do repeatedly
  by accident.

    // ❌ recompiles on EVERY call
    boolean valid(String s) {
        return s.matches("[a-z]+@[a-z]+\\\\.[a-z]{2,}");
    }

    // ✓ compiled ONCE, at class initialisation
    private static final Pattern EMAIL =
        Pattern.compile("[a-z]+@[a-z]+\\\\.[a-z]{2,}");

    boolean valid(String s) {
        return EMAIL.matcher(s).matches();
    }

  String.matches, String.split, String.replaceAll and
  String.replaceFirst ALL compile a fresh Pattern per call. For a
  one-off that is irrelevant; in a loop over ten thousand records it
  is ten thousand compilations of an identical pattern.

  THE DIVISION OF LABOUR:

    Pattern    the compiled pattern. IMMUTABLE and THREAD-SAFE, so a
               static final field is correct and shared freely.
    Matcher    the state of one matching operation. STATEFUL and NOT
               thread-safe — create one per use, never share it.

  That asymmetry is the whole API design, and sharing a Matcher
  across threads is a race that produces wrong results rather than an
  exception.

Part 2 — matches vs find

  matches()   the pattern must match the ENTIRE input
  find()      searches for the NEXT match anywhere in the input
  lookingAt() must match from the start, need not reach the end

    Pattern p = Pattern.compile("\\\\d+");

    p.matcher("abc123").matches()    // FALSE — the whole string is
                                     // not digits
    p.matcher("abc123").find()       // TRUE  — finds "123"

  THIS IS THE MOST COMMON JAVA-SPECIFIC REGEX BUG, because most other
  languages' default is search rather than full match. A pattern
  written for find() and used with matches() silently rejects
  everything.

  find() IS ITERATIVE — it resumes from where the last match ended:

    Matcher m = Pattern.compile("\\\\d+").matcher("a1b22c333");
    while (m.find()) {
        System.out.println(m.group());     // 1, then 22, then 333
    }

  ANCHORS MAKE THE INTENT EXPLICIT, which is better than relying on
  which method you called:

    ^  start of input        $  end of input
    \\\\b word boundary        \\\\B not a word boundary

    Pattern.compile("^\\\\d+$")     // explicit — behaves the same
                                  // under find() and matches()

Part 3 — Groups

Pattern p = Pattern.compile("(\\\\d{4})-(\\\\d{2})-(\\\\d{2})");
Matcher m = p.matcher("2026-09-03");

if (m.matches()) {
    m.group(0);      // "2026-09-03"  — group 0 is the WHOLE match
    m.group(1);      // "2026"
    m.group(2);      // "09"
}

  NAMED GROUPS ARE WORTH THE CHARACTERS:

    Pattern.compile("(?<year>\\\\d{4})-(?<month>\\\\d{2})");
    m.group("year");

  Positional groups break silently when someone inserts a group in
  the middle; named ones do not.

  NON-CAPTURING GROUPS — (?:...) — group without capturing:

    (?:https?|ftp)://(\\\\S+)      // group 1 is the address, not the
                                 // protocol

  Use them for alternation and grouping you do not need to extract.
  They also avoid renumbering every subsequent group.

  THE ORDER OF CALLS MATTERS, and this catches people:

    Matcher m = p.matcher(input);
    m.group(1);          // ❌ IllegalStateException: No match found

  group() is only valid AFTER a successful matches() or find(). The
  matcher has no result until you ask it to perform one.

Part 4 — Greedy, Lazy and Possessive

  GREEDY (the default) takes as much as possible, then backtracks
  until the rest of the pattern can match.

    "<a>text</a><b>more</b>"

    <.+>      matches the WHOLE string — from the first '<' to the
              LAST '>'
    <.+?>     matches "<a>" — lazy, takes as little as possible
    <[^>]+>   matches "<a>" — and is FASTER, because it cannot
              overshoot in the first place

  The third form is usually the right answer: rather than telling the
  engine to take less, describe what may not appear. A negated
  character class removes the backtracking entirely.

  POSSESSIVE quantifiers — ++ *+ ?+ — take as much as possible and
  REFUSE TO BACKTRACK:

    \\\\d++        matches digits, and never gives any back

  They can turn a catastrophic pattern into a linear one, at the cost
  of failing some matches a greedy version would find. They are the
  main defence in Part 5.

  QUANTIFIER REFERENCE:

    *   0 or more      +   1 or more      ?   0 or 1
    {n} exactly n      {n,} n or more     {n,m} between n and m

  each with a lazy form (*? +? ?? {n,m}?) and a possessive form
  (*+ ++ ?+ {n,m}+).

Part 5 — Catastrophic Backtracking

  THIS PATTERN IS A DENIAL OF SERVICE:

    Pattern.compile("(a+)+b").matcher("aaaaaaaaaaaaaaaaaaaaaaaaX")
           .matches();

  It does not return. Not slowly — the running time is EXPONENTIAL in
  the input length.

  WHY: the input has no 'b', so the match must fail. Before
  concluding that, the engine tries every way of splitting the a's
  between the inner a+ and the outer (...)+ :

      one group of 24
      23 + 1, 22 + 2, 22 + 1 + 1, …

  For n characters that is on the order of 2^n possibilities.

    20 a's    ~1 million steps      milliseconds
    30 a's    ~1 billion            seconds
    40 a's    ~1 trillion           ~20 minutes
    50 a's                          longer than a working day

  THE SIGNATURE: NESTED QUANTIFIERS OVER OVERLAPPING ALTERNATIVES.

    (a+)+          a quantifier inside a quantifier
    (a|aa)+        alternatives that can match the same text
    (\\\\s*\\\\w+)*      the classic real-world instance
    ^(\\\\w+\\\\s?)*$    an "input validation" pattern that ships often

  All of them share the property that the same input can be split
  many ways, and a failing match forces the engine to try all of them.

  WHY IT IS A SECURITY ISSUE — ReDoS

  If either the INPUT or the PATTERN comes from a user, an attacker
  chooses the worst case. One 30-character request pins a CPU core
  for seconds; a handful exhaust the thread pool. It is a
  denial-of-service with no payload and no exploit code.

  THE DEFENCES:

    avoid nested quantifiers      restructure so text can only split
                                  one way
    negated character classes     [^>]+ instead of .+?
    possessive quantifiers        \\\\d++ never backtracks
    bound the input length        reject before matching — the cheapest
                                  and most reliable guard
    a timeout                     Java has no built-in regex timeout;
                                  run it in a task you can cancel
    never compile user input      a user-supplied pattern is arbitrary
                                  code execution for the CPU
⚠️ Java's regex engine is backtracking, not automaton-based. That is what makes backreferences and lookahead possible, and it is what makes exponential behaviour possible — the two are the same design decision. Engines like RE2 (Go, and available for Java as RE2/J) guarantee linear time by forbidding backreferences. If you must run patterns you did not write, RE2/J is a genuine answer; within the JDK the only reliable protections are bounding the input and running the match somewhere you can time out.

Part 6 — When Not to Use a Regex

  A REGEX CANNOT PARSE NESTED STRUCTURE. HTML, XML and JSON are
  recursive, and a regular language cannot count nesting depth. Any
  pattern that appears to work is matching a subset and will fail on
  valid input — a comment, a CDATA section, an attribute containing
  the delimiter.

    Use a parser: Jackson, Jsoup, a real XML reader.

  EMAIL VALIDATION IS THE OTHER PERENNIAL. The RFC 5322 grammar
  permits quoted strings, comments and nested parentheses; the
  "correct" regex is thousands of characters and still cannot tell you
  whether the address exists.

    what to do instead:  check for exactly one '@' with something
                         either side, then SEND A CONFIRMATION EMAIL.
                         Deliverability is the only real validation.

  SIMPLER TOOLS WIN WHEN THEY APPLY:

    s.startsWith / endsWith / contains       clearer and far faster
    s.split(",", -1)                          for simple delimiters
    a real CSV parser                         once quoting is involved
    String.replace (not replaceAll)           literal replacement, no
                                              regex compilation at all

  AND WHEN YOU DO USE ONE, MAKE IT READABLE:

    Pattern.compile("""
        (?<year>\\\\d{4})-
        (?<month>\\\\d{2})
        """, Pattern.COMMENTS);      // whitespace and # comments
                                     // ignored

  A regex that needs a comment to explain it should have one.

Interview Questions

Beginner: What is the difference between matches() and find()?

matches() requires the entire input to match the pattern. find() searches for the next occurrence anywhere in the input.

So with the pattern \d+ and the input "abc123", matches() is false — the whole string is not digits — while find() is true and group() returns "123".

This is probably the most common Java-specific regex bug, because most other languages default to searching. A pattern written for a search and used with matches() silently rejects everything, and the pattern looks correct.

find() is also iterative — it resumes from the end of the previous match, so a while (m.find()) loop walks every occurrence.

My preference is to write explicit anchors — ^…$ — so the pattern states its intent regardless of which method the caller uses.

Beginner: Why should Pattern be a static final field?

Because compiling a regex is the expensive part, and String.matches, split, replaceAll and replaceFirst all compile a fresh Pattern on every call.

For a one-off that is irrelevant. In a loop over ten thousand records it is ten thousand compilations of an identical pattern — pure waste that a single static field removes.

It is safe to share because Pattern is immutable and thread-safe. The Matcher is not: it holds the state of one matching operation, so you create one per use and never share it. Sharing a matcher across threads produces wrong results rather than an exception, which is the worse failure mode.

The static field also has a secondary benefit — an invalid pattern fails at class initialisation rather than the first time that code path runs, which may be much later.

Mid: What is greedy versus lazy matching?

A greedy quantifier takes as much as it can and then backtracks until the rest of the pattern can match. A lazy one — written with a trailing ? — takes as little as possible and expands only as needed.

The classic demonstration is <.+> against "<a>text</a>": it matches the entire string, because .+ consumes everything and then gives back just enough to find a final >. <.+?> matches only "<a>".

The answer I would actually write is neither: <[^>]+>. Rather than telling the engine to take less, describe what cannot appear — a negated character class cannot overshoot, so there is no backtracking at all. It is both clearer and faster.

There is a third kind worth knowing: possessive quantifiers (++, *+) take as much as possible and refuse to give any back. They can convert an exponential pattern into a linear one, at the cost of failing some matches a greedy version would find.

Mid: Why can't you parse HTML with a regex?

Because HTML is recursive and regular expressions cannot count. Matching nested tags requires tracking arbitrary depth, and a regular language has no memory for that — it is a formal limitation, not a matter of writing a cleverer pattern.

Java's engine has backreferences and lookahead, so it is not strictly regular, but that does not rescue it: the constructs needed to approximate nesting are exactly the ones that backtrack catastrophically.

In practice any pattern that seems to work is matching a subset of the input, and it fails on things that are perfectly valid — an attribute containing >, a comment, a CDATA section, unquoted attributes, or a self-closing tag written differently.

The right tool is a parser — Jsoup for HTML, Jackson for JSON, a real XML reader — which handles the nesting, the entities and the malformed-input cases that a regex silently mishandles.

The same reasoning rules out regex for source code, for CSV once quoting is involved, and for anything with balanced delimiters. A regex is the right tool for tokens — a date, a postcode, an identifier — not for structure.

Senior: Explain catastrophic backtracking and how you would defend against it.

It is exponential blow-up in a backtracking engine when a match fails and the pattern permits the same input to be split many ways.

The minimal example is (a+)+b against a string of a's with no b. The match must fail, but before concluding that, the engine tries every partition of the a's between the inner a+ and the outer group — roughly 2ⁿ possibilities. Twenty characters is about a million steps and takes milliseconds; forty is a trillion and takes around twenty minutes; fifty is longer than a working day.

The signature is nested quantifiers over overlapping alternatives — (a+)+, (a|aa)+, (\s*\w+)*. The last is common in real validation patterns, which is why this ships.

It is a denial-of-service vector whenever the input or the pattern comes from outside. An attacker sends thirty characters, pins a CPU core for seconds, and a handful of requests exhaust the thread pool. There is no payload and nothing in the logs but slowness.

Defences, roughly in order of reliability. Bound the input length before matching — cheapest and most effective, since the blow-up is exponential in length. Restructure the pattern to remove nested quantifiers, usually with a negated character class. Use possessive quantifiers where backtracking is not wanted. Run the match in a task you can cancel, since Java has no regex timeout. And never compile a user-supplied pattern.

The structural answer is a non-backtracking engine: RE2/J guarantees linear time by forbidding backreferences. If you must run patterns you did not write — a rules engine, a user-defined filter — that is the correct choice rather than trying to sanitise regexes.

Senior: How would you validate an email address?

Loosely, and then by sending mail to it.

The RFC 5322 grammar permits quoted local parts, comments, nested parentheses and domain literals. A genuinely conformant regex runs to thousands of characters, is unmaintainable, and rejects addresses that work while accepting ones that do not.

More importantly, syntactic validity does not answer the question anyone cares about: whether the address exists and reaches the person. A perfectly formed address at a domain with no MX record is useless, and a slightly unusual one that delivers is fine.

So: check there is exactly one @ with something either side and a dot in the domain, bound the length, and then send a confirmation email. Deliverability is the only real validation, and it also proves the user controls the mailbox — which is usually the actual requirement.

An over-strict regex has a real cost, and it is worth naming in review: it rejects + tagging, which people use deliberately; newer TLDs, if the pattern hard-codes two to four letters; and non-ASCII addresses entirely. Those rejections are invisible to you and very visible to the user who cannot sign up.

If a library is available, jakarta.validation's @Email or Apache Commons EmailValidator is a better default than a hand-written pattern — not because it is complete, but because it is deliberately pragmatic and someone else maintains it.

🏋️ Graded Exercises

1 (easy): Why is the first version slower, and what else does the second gain? 
boolean isValid(String s) { return s.matches("\\\\d{3}-\\\\d{4}"); }

private static final Pattern P = Pattern.compile("\\\\d{3}-\\\\d{4}");
boolean isValid(String s) { return P.matcher(s).matches(); }
Solution

String.matches compiles the pattern on every call. Compiling builds a state machine and is far more expensive than running it, so validating ten thousand records performs ten thousand identical compilations.

The second version also fails earlier. An invalid pattern throws PatternSyntaxException at class initialisation rather than the first time that branch executes — which might be in production, months later.

MethodCompiles per call
String.matchesYes
String.splitYes — except for a single-character non-metacharacter, which is optimised
String.replaceAll / replaceFirstYes
String.replaceNo — literal, no regex at all

Sharing the Pattern is safe because it is immutable and thread-safe. The Matcher is not — it holds per-operation state — so it must be created per use. Hoisting a Matcher into a field is a race that yields wrong answers rather than an exception.

And String.replace is worth knowing for literal replacement: no compilation, and no surprises from $ or \ in the replacement text.

2 (easy): Why does this return false? 
Pattern p = Pattern.compile("\\\\d+");
boolean found = p.matcher("order 12345 shipped").matches();
Solution

matches() requires the entire input to match. The string contains digits but is not only digits, so the whole-input match fails.

p.matcher("order 12345 shipped").find()      // TRUE — finds "12345"
MethodRequires
matches()The whole input
find()A match anywhere; resumes on each call
lookingAt()A match from the start, need not reach the end

This trips people coming from other languages, where the default is search. In Python, JavaScript and grep, an unanchored pattern searches — so the same pattern behaves differently, and the Java version silently rejects valid input rather than erroring.

The habit that avoids it is to anchor explicitly. ^\d+$ means the same thing under both methods, so the pattern documents its own intent and stops depending on which call the reader chose.

To extract every number, find() in a loop is the idiom:

Matcher m = p.matcher(text);
while (m.find()) process(m.group());
3 (medium): Why does this match too much, and what are two fixes? 
Pattern.compile("<.+>").matcher("<a>text</a>").find();
// group() is "<a>text</a>"
Solution

.+ is greedy. It consumes to the end of the input, then backtracks just enough to find a final > — which is the last one in the string, not the first.

<.+>      "<a>text</a>"     greedy — to the LAST '>'
<.+?>     "<a>"              lazy — to the first
<[^>]+>   "<a>"              negated class — cannot overshoot
FixTrade-off
<.+?> lazyCorrect, and still backtracks — it expands one character at a time until the match succeeds
<[^>]+> negated classCorrect and faster — it can never consume past a >, so there is nothing to backtrack

The negated class is the better habit. Instead of telling the engine to take less, describe what may not appear. That removes the backtracking rather than compensating for it, which matters for both speed and for avoiding the pathological cases in Part 5.

The general shape: whenever a pattern uses . between delimiters, a negated class is nearly always more precise — "[^"]*" for a quoted string, [^,]+ for a CSV field.

And the caveat that applies to all three: none of them should be used on real HTML. This works for a fixed, known format; nesting, attributes containing >, and comments defeat every version.

4 (medium): This validation pattern hangs the server. Explain and fix. 
private static final Pattern P = Pattern.compile("^(\\\\w+\\\\s?)*$");
boolean valid(String input) { return P.matcher(input).matches(); }
Solution

Nested quantifiers with overlapping alternatives. \w+ inside a (...)* means the same run of characters can be divided between the inner and outer quantifiers in exponentially many ways.

  For input that FAILS to match — say 30 word characters followed
  by a '!' — the engine must try every partition before concluding
  failure:

     "aaaa"  as  (aaaa) / (aaa)(a) / (aa)(aa) / (aa)(a)(a) / …

     20 chars   ~1 million steps     milliseconds
     30 chars   ~1 billion           seconds
     40 chars   ~1 trillion          ~20 minutes

It only blows up on failure. Valid input matches quickly, so the pattern passes every test written with valid data — and an attacker supplies invalid data deliberately.

// FIX — remove the nesting entirely
Pattern.compile("^\\\\w+(\\\\s\\\\w+)*$");     // no quantifier inside a
                                          // quantifier over the same
                                          // characters

// Or possessive, if the structure must stay
Pattern.compile("^(\\\\w++\\\\s?)*+$");

// And regardless:
if (input.length() > 200) return false;   // bound BEFORE matching
DefenceStrength
Bound the input lengthMost reliable — the cost is exponential in length, so a cap makes the worst case finite and small
Restructure the patternRemoves the cause, and requires understanding it
Possessive quantifiersEffective, and can change which inputs match
Run with a timeoutJava has no regex timeout — needs a cancellable task

This is a ReDoS vulnerability, not just a performance bug. Thirty characters pin a core; a few concurrent requests exhaust the thread pool, with nothing in the logs but slowness.

5 (hard): A search feature lets users supply a pattern. Assess the risks. 
String userPattern = request.getParameter("q");
Pattern p = Pattern.compile(userPattern);
return documents.stream().filter(d -> p.matcher(d.body()).find()).toList();
Solution
RiskDetail
ReDoSThe user chooses the pattern, so they choose your CPU cost. (a+)+b against any document is exponential — no payload, no exploit code
AmplificationThe pattern runs against every document, so one request multiplies the cost by the corpus size
PatternSyntaxExceptionAn unbalanced bracket is a 500 rather than a validation message
MemoryPathological patterns can also consume heap through backtracking state

The first two combine badly. A single 30-character pattern applied to ten thousand documents is not one expensive match but ten thousand of them, so the amplification is the corpus size — a handful of requests take the service down.

// OPTION A — do not accept a regex at all (usually right)
String q = request.getParameter("q");
return documents.stream()
    .filter(d -> d.body().toLowerCase(Locale.ROOT)
                  .contains(q.toLowerCase(Locale.ROOT)))
    .toList();

// OPTION B — treat it as a literal, if the field looks like a regex
Pattern p = Pattern.compile(Pattern.quote(userPattern));

// OPTION C — a linear-time engine, if regex power is a requirement
//   com.google.re2j.Pattern — no backreferences, guaranteed linear

Option A is the answer most of the time, because "search" almost never requires regex semantics — users expect substring or token matching, and a search index is the real answer at scale.

If the feature genuinely is regex search — a log explorer, an admin tool — then RE2/J is the correct choice. It guarantees linear time by forbidding backreferences, which is precisely the trade you want when the pattern is untrusted. Sanitising regexes by inspection is not viable; the pathological forms are too varied.

Regardless of the option: cap the pattern length, run the search with a timeout on a bounded executor so exhaustion is contained, and catch PatternSyntaxException to return a 400 rather than a 500.

6 (hard): Extract dates from log lines, maintainably, and say what you would not use a regex for.
Solution 
private static final Pattern TIMESTAMP = Pattern.compile("""
    (?<year>\\\\d{4}) -          # ISO year
    (?<month>\\\\d{2}) -         # month
    (?<day>\\\\d{2})            # day
    """, Pattern.COMMENTS);

Matcher m = TIMESTAMP.matcher(line);
if (m.find()) {
    LocalDate date = LocalDate.of(
        Integer.parseInt(m.group("year")),
        Integer.parseInt(m.group("month")),
        Integer.parseInt(m.group("day")));    // real validation HERE
}
ChoiceWhy
Pattern.COMMENTS with a text blockWhitespace and # comments are ignored, so the pattern can be read and changed safely
Named groupsInserting a group later does not silently renumber every extraction
static finalCompiled once; an invalid pattern fails at startup
\d{2}, not a range checkDeliberate — see below

The important decision is not validating the date in the regex. A pattern that tries to reject month 13 becomes (0[1-9]|1[0-2]), and one that handles leap years is unreadable and still wrong. LocalDate.of throws DateTimeException for 2026-02-30 and knows about leap years — so the regex finds the shape and the parser decides validity.

That division generalises: use a regex to locate and tokenise, and a real parser to validate and convert. Trying to encode semantics in the pattern is what produces the unmaintainable thousand-character regexes.

What I would not use a regex for here: parsing the whole log line's structure. If the format is fixed, split on the delimiter is clearer; if it is JSON, use Jackson; if it is a known format, use its parser. A regex is right for extracting a token from otherwise unstructured text, which is exactly this case.

And for the timestamp specifically, if the whole line begins with a known format, DateTimeFormatter.ISO_LOCAL_DATE_TIME on a substring beats a regex entirely — fewer moving parts and better error messages.

🎯 Key Takeaways

  • Compiling is the expensive part, and String.matches, split and replaceAll recompile every call.
  • Pattern is immutable and thread-safe; Matcher is not — share the first, create the second per use.
  • matches() requires the whole input; find() searches — the most common Java-specific regex bug.
  • Anchor explicitly so the pattern means the same under either method.
  • group() before a successful match throws — the matcher has no result until asked.
  • Named groups survive edits; positional ones renumber silently.
  • Greedy runs to the last delimiter; a negated character class is better than lazy, because it cannot overshoot at all.
  • Possessive quantifiers refuse to backtrack, which can make a pathological pattern linear.
  • Nested quantifiers cause exponential backtracking — 40 characters can take twenty minutes.
  • It only blows up on failure, so valid test data never reveals it.
  • That is a denial-of-service vector whenever the input or the pattern is untrusted.
  • Bounding the input length is the cheapest reliable defence; Java has no regex timeout.
  • Never compile a user-supplied pattern — use RE2/J if you must run untrusted ones.
  • Regex cannot parse nested structure — HTML, XML, JSON need parsers.
  • Locate with a regex, validate with a parser — LocalDate.of knows about leap years and a pattern never will.
