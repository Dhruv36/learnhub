Immutability & Defensive Copying OOP

What you'll master: the five requirements for real immutability and why each one is there; the memory-model payoff that is the strongest argument — a correctly constructed object with final fields can be shared across threads with no synchronization at all; why the final guarantee is shallow, so a final List is still mutable; defensive copies on the way in and out, and the classic leak through a getter; List.copyOf versus Collections.unmodifiableList, which is a view over a still-mutable list; what records give you and what they conspicuously do not; the honest performance argument, including where immutability is genuinely wrong. Prerequisites: OOP and Collections.

Part 1 — What Immutability Actually Requires

  FIVE RULES. EACH ONE CLOSES A SPECIFIC HOLE, AND SKIPPING ANY OF
  THEM PRODUCES AN OBJECT THAT ONLY LOOKS IMMUTABLE.

  1. ALL FIELDS final
     Not just "no setters". final is what gives you the MEMORY
     MODEL guarantee in Part 2, and it makes the compiler prove
     that nothing reassigns them.

  2. NO MUTATORS
     No setters, and no method that changes state. A method that
     "changes" something returns a NEW instance.

  3. THE CLASS IS final (or all constructors are private)
     Otherwise a subclass can add mutable state and override
     methods, and callers holding your declared type cannot tell.

  4. `this` MUST NOT ESCAPE THE CONSTRUCTOR
     Registering a listener, starting a thread, or passing `this`
     to anything from the constructor publishes a half-built
     object — and VOIDS the final-field guarantee entirely.

  5. MUTABLE COMPONENTS ARE COPIED IN AND OUT
     A final reference to a mutable object protects the REFERENCE,
     not the contents. This is the rule people miss.

  ALL FIVE, APPLIED:

    public final class Period {                       // (3)
        private final Date start;                     // (1)
        private final Date end;

        public Period(Date start, Date end) {
            this.start = new Date(start.getTime());   // (5) copy IN
            this.end   = new Date(end.getTime());
            if (this.start.after(this.end))           // validate the
                throw new IllegalArgumentException(); // COPIES
        }

        public Date start() { return new Date(start.getTime()); }
        public Date end()   { return new Date(end.getTime()); }  // (5) out
    }

  *** NOTE THE ORDER IN THE CONSTRUCTOR ***
  Copy FIRST, then validate the copies. Validating the arguments
  and then copying leaves a TOCTOU window: another thread holding
  the original Date can change it between the check and the copy.
  This is a real attack, not a theoretical one.

  WHAT "IMMUTABLE" BUYS, ALL AT ONCE:

    thread safety      nothing can change, so nothing can race
    safe publication   share it with no synchronization (Part 2)
    safe as a Map key  its hashCode cannot drift
    cacheable          hashCode can be computed once
    no defensive copy  callers cannot break your invariants
    simple reasoning   the value at line 1 is the value at line 100

Part 2 — The Memory-Model Payoff

  THIS IS THE STRONGEST ARGUMENT AND THE LEAST KNOWN.

  THE final FIELD GUARANTEE:

    IF an object is correctly constructed — meaning `this` did not
    escape during construction — THEN any thread that sees a
    reference to it is guaranteed to see the correctly initialised
    values of its final fields, WITH NO SYNCHRONIZATION.

  COMPARE THE TWO:

    class Unsafe { int x;       Unsafe(int x) { this.x = x; } }
    class Safe   { final int x; Safe(int x)   { this.x = x; } }

    // publishing through a plain field, no synchronization
    holder = new Unsafe(42);      // another thread may read x == 0
    holder = new Safe(42);        // guaranteed to read x == 42

  WHY THE FIRST CAN FAIL: `holder = new Unsafe(42)` is roughly
  allocate, write the reference, run the constructor — and the last
  two MAY BE REORDERED. A reader can therefore see a non-null
  reference to an object whose field is still the default.

  final PREVENTS THAT with a FREEZE ACTION at the end of the
  constructor: no write to a final field may be reordered past
  constructor completion.

  THE CONSEQUENCE IS THE WHOLE VALUE PROPOSITION:

    an immutable object needs NO locks, NO volatile, NO copying
    when shared, and cannot be observed in an inconsistent state.

  It is the cheapest concurrency strategy that exists — cheaper
  than a lock, because there is nothing to coordinate.

  *** THE ESCAPE CLAUSE VOIDS IT COMPLETELY ***

    class Broken {
        final int x;
        Broken(int x) {
            Registry.register(this);   // ❌ ESCAPED
            this.x = x;                //    readers may see 0
        }
    }

  Any of these break it: registering a listener, starting a thread,
  passing `this` to a collection or a callback, or calling an
  OVERRIDABLE method (the subclass's override runs before the
  subclass's own fields are initialised).

  THE FIX IS A STATIC FACTORY — construct fully, then publish:

    static Broken create(int x) {
        Broken b = new Broken(x);      // fully constructed
        Registry.register(b);          // THEN published
        return b;
    }

Part 3 — Shallow vs Deep

  THE GUARANTEE IS ABOUT THE REFERENCE, NOT WHAT IT POINTS TO.

    public final class Order {
        private final List<Item> items;    // final reference
        public Order(List<Item> items) { this.items = items; }
        public List<Item> items() { return items; }
    }

    List<Item> list = new ArrayList<>(List.of(a, b));
    Order o = new Order(list);

    list.add(c);              // ❌ CALLER mutates it from outside
    o.items().clear();        // ❌ ANYONE mutates it through the
                              //    getter

  Both compile, both work, and the "immutable" order changed. The
  final only stopped `items` being REASSIGNED.

  YOU NEED THREE THINGS:

    1. COPY ON THE WAY IN     — sever the caller's reference
    2. COPY OR WRAP ON THE WAY OUT — sever the getter's reference
    3. IMMUTABLE ELEMENTS     — or the copy is pointless, since
                                each element is still mutable

    public Order(List<Item> items) {
        this.items = List.copyOf(items);       // copy IN
    }
    public List<Item> items() { return items; } // already immutable

  If Item itself is mutable, an unmodifiable list of it still lets
  a caller do items().get(0).setPrice(0). Immutability has to go all
  the way down — which is why immutable designs tend to spread.

  THE THREE "UNMODIFIABLE" THINGS ARE NOT THE SAME:

    List.copyOf(list)                  A COPY. Immutable. Later
                                       changes to `list` do not
                                       affect it. REJECTS NULLS.
    Collections.unmodifiableList(list) A VIEW. Read-only THROUGH
                                       THIS REFERENCE, but the
                                       backing list can still be
                                       changed by whoever holds it
                                       — and the view shows those
                                       changes.
    Arrays.asList(array)               A fixed-size VIEW over the
                                       array. set() WRITES THROUGH
                                       to the array.

  THE unmodifiableList TRAP IN FULL:

    List<String> backing = new ArrayList<>();
    List<String> view = Collections.unmodifiableList(backing);
    backing.add("surprise");
    view.size();          // 1 — the "unmodifiable" list changed

  It is only safe when NOBODY ELSE holds the backing list — which
  in practice means you built it locally and immediately forgot it.
  List.copyOf has no such precondition, which is why it is the
  better default.

Part 4 — Records: What You Get and What You Don't

  A RECORD GIVES YOU, FOR FREE:

    private final fields          (rule 1)
    no setters                    (rule 2)
    the class is implicitly final (rule 3)
    a canonical constructor, equals, hashCode, toString

    record Money(BigDecimal amount, Currency currency) { }

  Four of the five rules, in one line. That is genuinely most of the
  work.

  WHAT IT DOES NOT GIVE YOU: RULE 5. DEEP IMMUTABILITY.

    record Basket(String id, List<Item> items) { }

    var list = new ArrayList<Item>();
    var b = new Basket("b1", list);
    list.add(item);              // ❌ the record's list changed
    b.items().add(item2);        // ❌ so did this

  A record stores the reference it was given. Nothing copies.

  THE COMPACT CONSTRUCTOR IS WHERE YOU FIX IT:

    record Basket(String id, List<Item> items) {
        Basket {                                // compact form
            Objects.requireNonNull(id);
            items = List.copyOf(items);         // reassign the
        }                                       // PARAMETER
    }

  Note the shape: you assign to the PARAMETER, and the compiler
  emits the field assignment afterwards. Writing `this.items = …`
  in a compact constructor is a compile error.

  List.copyOf REJECTS NULL ELEMENTS, so this also validates. If
  nulls are legitimate, use
  Collections.unmodifiableList(new ArrayList<>(items)).

  THE GETTER IS THEN SAFE because the stored list is genuinely
  immutable — no second copy needed on the way out.

  RECORDS ALSO CANNOT:

    - extend a class (they extend Record)
    - have non-static mutable fields
    - hide the accessor names (they match the components)

  and they are a POOR FIT for JPA entities, which need a no-arg
  constructor, non-final fields for lazy loading, and identity based
  on a database key rather than all components.

  THE WITHER PATTERN — "changing" an immutable object:

    record Money(BigDecimal amount, Currency currency) {
        Money withAmount(BigDecimal a) { return new Money(a, currency); }
    }

  Fine for two or three components. At ten it becomes noise, and a
  builder (or a toBuilder() on the record) reads better.

Part 5 — The Performance Argument, Honestly

  THE OBJECTION IS ALWAYS "BUT ALL THAT COPYING". THE ANSWER IS
  NUANCED, NOT A DISMISSAL.

  WHY ALLOCATION IS CHEAPER THAN PEOPLE THINK:

    ALLOCATION IS A POINTER BUMP. Each thread has a Thread-Local
    Allocation Buffer; allocating is incrementing a pointer —
    roughly 10-15 CPU instructions, no lock, no free list.

    SHORT-LIVED GARBAGE IS NEARLY FREE. A copying young collector's
    cost is proportional to the SURVIVORS, not the garbage. An
    object that dies before the next young collection costs
    essentially nothing to collect — it is never even visited.

    ESCAPE ANALYSIS MAY REMOVE THE ALLOCATION. If the JIT proves an
    object never escapes its method, it can scalar-replace it: no
    heap object at all.

  SO THE "COST" OF creating a small short-lived immutable object is
  usually far smaller than the cost of the synchronization it lets
  you delete.

  WHERE THE COST IS REAL:

    LARGE OBJECTS COPIED FREQUENTLY. Copying a 10,000-element list
    to change one element is O(n) per change. In a loop that is
    O(n²), and no JIT optimisation saves you.

    HOT INNER LOOPS. Allocation in a tight numeric loop adds up,
    and escape analysis is not guaranteed — it fails when the object
    is stored, returned, or passed to a non-inlined method.

    LONG-LIVED CHURN. Objects that survive young collections get
    copied between survivor spaces and promoted, which is not free.

  THE ANSWER FOR LARGE STRUCTURES IS STRUCTURAL SHARING:

    A PERSISTENT data structure creates a new version that SHARES
    most of its internals with the old one. A persistent vector
    (as in Clojure, or Java libraries like Vavr) updates one element
    in O(log32 n) — effectively constant — copying only the path
    from root to leaf.

  WHERE IMMUTABILITY IS GENUINELY THE WRONG CHOICE:

    large mutable buffers   byte[], StringBuilder, image data
    hot paths with measured allocation pressure
    JPA entities            the framework requires mutability
    builders                mutable by design, then produce an
                            immutable result
    accumulators            a mutable local is simpler and faster
                            than folding new objects

  THE DEFAULT THAT SURVIVES REVIEW: make it immutable, and reach for
  mutability where you have MEASURED that it matters. That is the
  opposite of the usual instinct, and it is right because the
  correctness benefits are certain and the performance costs are
  usually hypothetical.

Part 6 — String as the Case Study

  String IS THE MOST-USED IMMUTABLE CLASS IN JAVA, AND ITS DESIGN
  SHOWS WHAT IMMUTABILITY ENABLES.

    public final class String {          // final — rule 3
        private final byte[] value;      // final — rule 1
        private int hash;                // ← NOT final. See below.
    }

  1. HASH CACHING. Because the contents cannot change, the hash can
     be computed once and cached:

       public int hashCode() {
           int h = hash;
           if (h == 0 && !hashIsZero) {
               h = computeHash();
               hash = h;                 // benign data race
           }
           return h;
       }

     `hash` is deliberately non-final and unsynchronized. Two
     threads may compute it simultaneously — but they compute the
     SAME value, so the race is harmless. This is one of the very
     few benign data races in the JDK, and it is only safe BECAUSE
     the string is immutable.

  2. THE STRING POOL. Literals are interned, so identical literals
     share one object:

       String a = "hello";
       String b = "hello";
       a == b;                 // true — the SAME object

     Sharing is only safe because nobody can modify it. If String
     were mutable, one class changing a literal would change it for
     every class in the JVM.

  3. SAFE AS A MAP KEY. A key whose hashCode changes after
     insertion is lost — you cannot find it, and it is not removed.
     Immutability makes String the safest possible key.

  4. SECURITY. A file path or a URL passed to a security check
     cannot be changed between the check and the use. If String were
     mutable, every such API would need a defensive copy.

  5. SUBSTRING — A CAUTIONARY TALE. Before Java 7u6, substring()
     SHARED the parent's char[] with an offset. That made substring
     O(1) — and meant a 2-character substring of a 10 MB string kept
     all 10 MB alive. It was changed to copy: substring is now O(n),
     and the leak is gone.

     The lesson generalises: sharing internals is a real
     optimisation with a real lifetime cost, and immutability is
     what made the sharing possible in the first place.

  THE COUNTERPART: StringBuilder EXISTS BECAUSE IMMUTABILITY IS THE
  WRONG DEFAULT FOR ACCUMULATION.

    for (…) s += item;              // O(n²) — a new String each time
    for (…) sb.append(item);        // O(n)

  That is the whole argument in one comparison: immutable values,
  mutable builders.

Interview Questions

Beginner: What makes a class immutable?

Five things, and each closes a specific hole:

  1. All fields final — not merely "no setters"; final is what gives the memory-model guarantee.
  2. No mutators — a "change" returns a new instance.
  3. The class is final, or all constructors are private, so a subclass cannot add mutable state.
  4. this does not escape the constructor — no registering listeners, no starting threads, no overridable calls.
  5. Mutable components are copied in and out.

Rule 5 is the one people miss. A final List field means the reference cannot be reassigned; the list itself is as mutable as ever, both by whoever passed it in and by anyone who gets it from a getter.

A record gives you rules 1–3 automatically, which is most of the work — but not rule 5, since it stores exactly the reference it was handed.

Beginner: Why is String immutable?

Four reasons, and each is a capability rather than a preference.

Hash caching. Because the contents cannot change, hashCode is computed once and cached in a field. That field is deliberately non-final and unsynchronized — two threads may compute it at the same time, but they compute the same value, so the race is benign. That trick is only sound because the string cannot change.

The string pool. Identical literals share one object, so "hello" == "hello" is true. Sharing is only safe when nobody can modify the shared thing.

Safe map keys. A key whose hashCode changes after insertion is lost — unfindable and unremovable. Immutability makes String the safest possible key.

Security. A path or URL validated by a security check cannot be swapped before use, so those APIs need no defensive copy.

The counterpart is StringBuilder: immutability is the wrong default for accumulation, because s += item in a loop is O(n²).

Mid: What is the difference between List.copyOf and Collections.unmodifiableList?
List.copyOfunmodifiableList
What it isA copyA view
Backing list changesNo effectVisible through the view
NullsRejectedAllowed
CostO(n) onceO(1), no copy
List<String> backing = new ArrayList<>();
List<String> view = Collections.unmodifiableList(backing);
backing.add("surprise");
view.size();          // 1 — the "unmodifiable" list changed

unmodifiableList only prevents modification through that reference. It is safe exactly when nobody else holds the backing list — which in practice means you built it locally and immediately dropped the reference.

List.copyOf has no such precondition, which makes it the correct default for a defensive copy. Its null rejection doubles as validation; when nulls are legitimate, use Collections.unmodifiableList(new ArrayList<>(items)) — copy first, then wrap.

Worth adding: Arrays.asList is neither. It is a fixed-size view over the array, and set writes straight through to it.

Mid: Are records immutable? What do you still have to do?

Shallowly, yes; deeply, no. A record gives you private final fields, no setters, an implicitly final class, and generated equals/hashCode/toString — four of the five requirements.

What it does not do is copy. It stores exactly the reference it was handed:

record Basket(String id, List<Item> items) { }

var list = new ArrayList<Item>();
var b = new Basket("b1", list);
list.add(item);            // the record's list changed
b.items().add(item2);      // so did this

The compact constructor is the fix, and note that you assign to the parameter — this.items = … there is a compile error:

record Basket(String id, List<Item> items) {
    Basket {
        Objects.requireNonNull(id);
        items = List.copyOf(items);        // parameter, not field
    }
}

The getter is then safe without a second copy, because the stored list is genuinely immutable.

And immutability still has to go all the way down: if Item is mutable, items().get(0).setPrice(0) works regardless of the copy.

Senior: What is the memory-model argument for immutability?

It is the strongest argument and the least known: a correctly constructed object with final fields can be shared across threads with no synchronization at all.

The guarantee is that if this did not escape during construction, any thread that sees the reference is guaranteed to see the correctly initialised values of the final fields. The JVM implements it with a freeze action at constructor completion: no write to a final field may be reordered past it.

Without final, publication through a plain field is a race — holder = new Unsafe(42) is roughly allocate, write the reference, run the constructor, and the last two may be reordered, so a reader can observe a non-null reference to an object whose field is still 0.

So immutability is not merely "safer" — it removes the need for locks, volatile and defensive copying when sharing. It is the cheapest concurrency strategy available, because there is nothing to coordinate.

Two caveats matter in practice. The escape clause is absolute: registering a listener, starting a thread, or calling an overridable method from a constructor voids the guarantee entirely — use a static factory that constructs and then publishes. And the guarantee is shallow, covering the reference rather than the contents, so a final field pointing at a mutable List gives you nothing.

Senior: When is immutability the wrong choice?

Less often than people assume, but the cases are real.

Large structures changed frequently. Copying a 10,000-element list to change one element is O(n) per change and O(n²) in a loop, and no JIT optimisation rescues that. The answer is usually a persistent structure with structural sharing — a persistent vector updates in O(log₃₂ n), copying only the root-to-leaf path — or a mutable building phase that produces an immutable result.

Buffers and accumulators. byte[], StringBuilder, image data. The String/StringBuilder pair is the canonical statement of the rule: immutable values, mutable builders.

Framework requirements. JPA entities need a no-arg constructor, non-final fields for lazy loading and proxying, and identity based on a database key rather than all components. Fighting that is not worth it — use a mutable entity and an immutable DTO at the boundary.

Measured hot paths. Allocation in a tight numeric loop adds up, and escape analysis is not guaranteed — it fails when the object is stored, returned, or passed to a method that does not inline.

But the default should still be immutable, because the usual objection is mis-calibrated. Allocation is a pointer bump in a TLAB — roughly ten instructions, no lock — and a copying young collector's cost is proportional to survivors, so an object that dies quickly is never even visited. The synchronization you delete typically costs more than the allocation you add.

My rule: immutable by default, mutable where profiling shows it matters, and mutable-builder-to-immutable-result whenever construction is incremental.

🏋️ Graded Exercises

1 (easy): Is this immutable? 
public final class Config {
    private final Map<String,String> settings;
    public Config(Map<String,String> s) { this.settings = s; }
    public Map<String,String> settings() { return settings; }
}
Solution

No — it is mutable through two separate doors.

var map = new HashMap<String,String>();
var c = new Config(map);
map.put("k", "v");            // door 1: the caller kept a reference
c.settings().put("x", "y");   // door 2: the getter handed one out

final stopped settings being reassigned. It did nothing about the map.

public final class Config {
    private final Map<String,String> settings;
    public Config(Map<String,String> s) {
        this.settings = Map.copyOf(s);          // copy IN
    }
    public Map<String,String> settings() {
        return settings;                        // already immutable
    }
}
FixNote
Map.copyOf in the constructorCorrect default; also rejects nulls, which doubles as validation
Copy in the getter insteadWorks but copies on every call, and the caller's original still leaks in
Collections.unmodifiableMap(s)Insufficient — a view; the caller's map still backs it

Copying once on the way in is the right shape — it fixes both doors, and the getter then needs no defensive copy at all.

2 (easy): Why does this record fail to protect its list, and what is the fix? 
record Order(String id, List<Item> items) { }
Solution

A record stores the reference it was given — nothing copies. It provides final fields, no setters and a final class, but not deep immutability.

record Order(String id, List<Item> items) {
    Order {                                     // compact constructor
        Objects.requireNonNull(id, "id");
        items = List.copyOf(items);             // assign the PARAMETER
    }
}
DetailWhy
Assign the parameter, not this.itemsthis.items = … in a compact constructor is a compile error — the compiler emits the field assignment after your block
List.copyOfA real copy, and it rejects nulls
No copy needed in the accessorThe stored list is already immutable

If null elements are legitimate, List.copyOf will throw — use Collections.unmodifiableList(new ArrayList<>(items)), which copies first and then wraps.

And this only goes as deep as Item. If Item is mutable, order.items().get(0).setPrice(0) still works — immutability has to be transitive, which is why immutable designs tend to propagate through a model.

3 (medium): Two bugs — one obvious, one subtle. 
public final class Period {
    private final Date start, end;

    public Period(Date start, Date end) {
        if (start.after(end))
            throw new IllegalArgumentException();
        this.start = start;
        this.end = end;
    }
    public Date start() { return start; }
}
Solution

Bug 1 — no defensive copies. Date is mutable, so the caller can change the period after construction, and start() hands out a reference anyone can mutate.

Bug 2 — validating before copying is a TOCTOU window. Even with copies, this order is exploitable: another thread holding the original Date can change it between the after() check and the copy, producing an object whose invariant was checked but no longer holds.

public Period(Date start, Date end) {
    this.start = new Date(start.getTime());     // COPY first
    this.end   = new Date(end.getTime());
    if (this.start.after(this.end))             // then validate
        throw new IllegalArgumentException();   // the COPIES
}
public Date start() { return new Date(start.getTime()); }   // copy OUT
RuleReason
Copy before validatingValidate what you will actually store, not what the caller can still change
Do not use clone() on a parameterA hostile subclass can override it and return a mutable alias
Copy on the way out tooOtherwise the getter reopens the hole

The real fix is to stop using Date:

public record Period(Instant start, Instant end) {
    public Period {
        if (start.isAfter(end)) throw new IllegalArgumentException();
    }
}

Instant is immutable, so no copies are needed anywhere and both bugs become unrepresentable. Choosing immutable component types removes the whole class of problem.

4 (medium): Why can a thread see x == 0 here, and what single keyword fixes it? 
class Holder { int x; Holder(int x) { this.x = x; } }

// thread A
shared = new Holder(42);        // plain field, no synchronization

// thread B
if (shared != null) print(shared.x);
Solution

Unsafe publication. shared = new Holder(42) is roughly: allocate, write the reference, run the constructor — and the last two may be reordered. Thread B can see a non-null reference to an object whose field is still the default.

class Holder { final int x; Holder(int x) { this.x = x; } }

final is the fix, and it is a memory-model guarantee rather than merely a reassignment restriction: the JVM inserts a freeze action at constructor completion, so no write to a final field may be reordered past it. Any thread seeing the reference then sees the initialised value, with no synchronization.

AlternativeMechanism
final fieldFreeze action — fixes it at the source, for every publisher
volatile Holder sharedOrders the construction before the publication — fixes this site only
Write and read under the same lockMonitor edge
A static initializerClass initialization is synchronized by the JVM

final is preferable to volatile here because it protects the object everywhere it is ever published, rather than fixing one publication site and leaving the next one broken.

The condition is "correctly constructed": if the constructor let this escape — registering a listener, starting a thread — the guarantee is void even with final.

5 (hard): This immutable design is a performance problem. Diagnose and fix. 
public record Grid(List<List<Cell>> rows) {   // 1000 x 1000
    public Grid set(int r, int c, Cell v) {
        var copy = new ArrayList<List<Cell>>(rows);
        var row  = new ArrayList<>(copy.get(r));
        row.set(c, v);
        copy.set(r, List.copyOf(row));
        return new Grid(List.copyOf(copy));
    }
}
// called in a loop, 1,000,000 times
Solution

Every single-cell update copies 1,000 row references plus a 1,000-element row — about 2,000 copies per set. Over a million updates that is ~2 billion reference copies, and the young generation churns constantly.

Full copy (as written)O(n + m)Rare updates only

public final class GridBuilder {
    private final Cell[][] cells;                    // mutable phase
    public GridBuilder(Grid g) { cells = g.toArray(); }
    public GridBuilder set(int r, int c, Cell v) {
        cells[r][c] = v; return this;                // O(1)
    }
    public Grid build() { return Grid.of(cells); }   // copy ONCE
}

var b = new GridBuilder(grid);
for (var u : updates) b.set(u.r(), u.c(), u.v());    // 1M O(1) ops
Grid result = b.build();                             // one copy

The builder pattern is the standard answer and it does not compromise the design: the mutable object is confined to one thread for the duration of the batch, and only the immutable result is ever shared. That is exactly the String/StringBuilder relationship.

Choose a persistent structure instead when every intermediate version must remain valid — undo history, or concurrent readers of older snapshots. Structural sharing gives O(log₃₂ n) updates, effectively constant, by copying only the root-to-leaf path.

The lesson is not "immutability is slow". It is that copy-on-write is the wrong strategy for large structures updated frequently, and there are two well-known alternatives.

6 (hard): Design an immutable domain model for an order with line items, a status and a total. State every decision.
Solution 
public record Money(BigDecimal amount, Currency currency) {
    public Money {
        Objects.requireNonNull(amount);
        Objects.requireNonNull(currency);
        amount = amount.setScale(currency.getDefaultFractionDigits(),
                                 RoundingMode.HALF_EVEN);   // normalise
    }
    public Money plus(Money o) {
        if (!currency.equals(o.currency))
            throw new IllegalArgumentException("currency mismatch");
        return new Money(amount.add(o.amount), currency);
    }
}

public record LineItem(String sku, int quantity, Money unitPrice) {
    public LineItem {
        if (quantity <= 0) throw new IllegalArgumentException("quantity");
    }
    public Money total() {
        return new Money(unitPrice.amount()
                .multiply(BigDecimal.valueOf(quantity)),
                unitPrice.currency());
    }
}

public sealed interface Status
        permits Draft, Placed, Shipped, Cancelled { }
public record Draft()                       implements Status { }
public record Placed(Instant at)            implements Status { }
public record Shipped(Instant at, String tracking) implements Status { }
public record Cancelled(Instant at, String reason) implements Status { }

public record Order(String id, List<LineItem> items, Status status) {
    public Order {
        Objects.requireNonNull(id);
        items = List.copyOf(items);            // DEFENSIVE COPY
        Objects.requireNonNull(status);
    }

    public Money total() {                     // DERIVED, not stored
        return items.stream().map(LineItem::total)
                .reduce(Money::plus)
                .orElseThrow(() -> new IllegalStateException("empty"));
    }

    public Order place() {                     // transition = new object
        if (!(status instanceof Draft))
            throw new IllegalStateException("not a draft");
        return new Order(id, items, new Placed(Instant.now()));
    }
}
DecisionWhy
List.copyOf in the compact constructorRecords do not copy — without it the caller retains a mutable reference
Total derived, not storedA stored total can disagree with the items; deriving makes that unrepresentable
Money as a type, not a BigDecimalCurrency travels with the amount, so mixed-currency addition fails loudly
Scale normalised in the constructorBigDecimal.equals compares scale — 1.5 and 1.50 would otherwise be unequal
Status as a sealed hierarchyEach state carries exactly its own data; a switch is exhaustive with no default
Transitions return a new OrderEvery version stays valid — natural audit history
Validation in compact constructorsAn invalid instance cannot exist at all

The sealed status is the strongest modelling choice. A Status enum plus nullable shippedAt, trackingNumber and cancelReason fields lets illegal combinations exist and forces every consumer to null-check. Here the wrong field does not exist.

Deriving the total is the second. Storing it creates an invariant you must maintain on every change; deriving it means the two can never disagree. Cache it only if profiling says so.

The trade-offs I would state: deriving the total is O(n) per call; a long transition chain allocates one object per step (cheap, since each dies immediately); and this model does not map cleanly onto JPA — persist with a mutable entity and convert at the boundary.

🎯 Key Takeaways

  • Immutability needs five things: final fields, no mutators, a final class, no escaping this, and copies in and out.
  • The memory-model payoff is the strongest argument — a correctly constructed object with final fields is safe to share with no synchronization.
  • The JVM implements that with a freeze action at constructor completion.
  • An escaping this voids the guarantee entirely — use a static factory that constructs, then publishes.
  • The guarantee is shallow: a final List field protects the reference, never the contents.
  • Copy on the way in and out, or a getter reopens the hole.
  • Copy before validating — validating the argument leaves a TOCTOU window.
  • List.copyOf is a copy; Collections.unmodifiableList is a view whose backing list can still change.
  • Arrays.asList is a fixed-size view whose set writes through.
  • Immutability must be transitive — an immutable list of mutable items protects nothing.
  • Records give you four of the five rules, never the copying — fix it in a compact constructor by assigning the parameter.
  • Allocation is a TLAB pointer bump and short-lived garbage is nearly free, so the usual performance objection is mis-calibrated.
  • The real cost is copying large structures frequently — use a builder phase or a persistent structure with structural sharing.
  • Immutable values, mutable builders — the String/StringBuilder relationship generalises.
  • String's design shows what immutability enables: cached hashes with a benign race, a shared literal pool, safe map keys and safe security checks.
  • Default to immutable; reach for mutability where you have measured that it matters.
