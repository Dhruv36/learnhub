Concurrent Collections & Atomics Concurrency

What you'll master: why Collections.synchronizedMap is not a thread-safe map in any useful sense — every compound operation is still a race and iteration still needs an external lock; how ConcurrentHashMap actually works (CAS on empty bins, per-bin locking, treeification) and why reads take no lock at all; its atomic compound methods and the self-deadlock inside computeIfAbsent that a recursive update causes; weakly consistent iterators and why size() is an estimate; why null keys are banned; CopyOnWriteArrayList's exact niche; the BlockingQueue family and the unbounded-queue OOM; CAS, the ABA problem, and why LongAdder beats AtomicLong under contention. Prerequisites: Synchronization and Collections.

Part 1 — Why a Synchronized Wrapper Is Not Enough

  Collections.synchronizedMap WRAPS EVERY METHOD IN A LOCK:

    Map<String,Integer> m = Collections.synchronizedMap(new HashMap<>());

  Each individual call is now atomic. That is all it gives you, and
  it is much less than people assume.

  PROBLEM 1 — COMPOUND OPERATIONS ARE STILL RACES:

    if (!m.containsKey(k)) {      // atomic
        m.put(k, compute(k));     // atomic
    }                             // THE SEQUENCE IS NOT

  Two threads can both see "absent" and both compute and put. If
  compute() is expensive, you paid twice; if it has a side effect,
  you did it twice.

  PROBLEM 2 — ITERATION STILL NEEDS AN EXTERNAL LOCK:

    for (String k : m.keySet()) { … }   // ConcurrentModificationException

  The wrapper does not lock across an iteration. The documented
  requirement is that YOU hold the wrapper's own monitor:

    synchronized (m) {
        for (String k : m.keySet()) { … }
    }

  Almost nobody does this, which is why synchronized-wrapper code
  throws CME in production and "works" in tests.

  PROBLEM 3 — ONE LOCK FOR THE WHOLE MAP.
  Every read and every write serialises through a single monitor. On
  a read-heavy map with 32 threads, 31 of them are blocked at any
  moment for data nobody is modifying.

  ConcurrentHashMap FIXES ALL THREE:

    m.computeIfAbsent(k, this::compute);   // atomic compound op
    for (String k : m.keySet()) { … }      // never throws CME
    // reads take NO LOCK; writes lock one bin

  THE RULE: if you find yourself writing synchronized around a
  collection, you almost certainly want a concurrent collection
  instead. The wrapper exists for legacy code and for the rare case
  where you must lock across several operations anyway.

Part 2 — How ConcurrentHashMap Works

  IT IS A HashMap WITH THREE CHANGES: volatile table slots, CAS for
  the empty case, and a lock on the FIRST NODE of a bin.

  WRITE PATH:

    hash the key  ->  find bin i
    if table[i] == null:
        CAS a new node in                  ← no lock at all
        succeeded? done.  lost the race? fall through
    else:
        synchronized (table[i]) {          ← lock ONE bin's head
            walk the chain (or tree), insert or update
        }

  So two writes to different bins never contend. With the default
  table size, contention is roughly (threads / bins) — negligible
  until the map is small or the hashes are terrible.

  READ PATH — NO LOCK, EVER:

    Node<K,V>[] tab = table;               // volatile read
    Node<K,V> e = tabAt(tab, i);           // volatile read
    walk the chain comparing keys

  Nodes' `val` and `next` are volatile, so a reader either sees the
  old node or the new one, never a half-linked chain. That is why
  reads scale perfectly with core count.

  RESIZE IS COOPERATIVE. When a write finds a resize in progress, it
  HELPS TRANSFER bins rather than blocking:

    ForwardingNode marks a bin already moved; a reader following it
    is redirected to the new table. Writers claim ranges of bins to
    transfer.

  This is why CHM has no "stop the world while we rehash" pause,
  unlike a synchronized HashMap.

  TREEIFICATION — the same as HashMap: a bin with more than 8 nodes
  (and a table of at least 64) converts to a red-black tree, making
  worst-case lookup O(log n) instead of O(n). It exists to blunt
  hash-collision denial-of-service.

  WHAT THIS BUYS AND COSTS:

    read throughput    scales linearly with cores
    write throughput   scales until bins collide
    memory             slightly higher per entry than HashMap
    ordering           none — and Map.of-style randomisation
                       does not apply, but you still must not
                       depend on iteration order

Part 3 — Atomic Compound Operations

  THESE ARE THE REASON TO USE CHM, MORE THAN THE LOCKING:

    putIfAbsent(k, v)          insert only if absent; returns the
                               EXISTING value or null
    computeIfAbsent(k, fn)     compute and insert atomically; fn
                               runs AT MOST ONCE per key
    computeIfPresent(k, fn)    update only if present
    compute(k, fn)             insert, update or remove in one step
    merge(k, v, fn)            the counter idiom
    remove(k, v)               remove only if it maps to v
    replace(k, old, new)       CAS on a map entry

  THE COUNTER, THREE WAYS:

    // ❌ race: get and put are separate
    map.put(k, map.getOrDefault(k, 0) + 1);

    // ✓ atomic
    map.merge(k, 1, Integer::sum);

    // ✓ better for hot keys — no boxing churn, no CAS retries
    map.computeIfAbsent(k, x -> new LongAdder()).increment();

  THE CACHE IDIOM:

    private final Map<K,V> cache = new ConcurrentHashMap<>();
    V get(K k) { return cache.computeIfAbsent(k, this::load); }

  load() runs exactly once per key even with 100 threads racing —
  the others block on that bin and then see the result.

  *** THE TRAP THAT DEADLOCKS *** — the mapping function must NOT
  modify the same map:

    cache.computeIfAbsent(k, key -> {
        cache.put(otherKey, …);     // ❌ may deadlock or corrupt
        return load(key);
    });

  You are inside a lock on that bin. Touching the map re-enters it,
  and if the two keys land in the same bin you self-deadlock; in
  other cases you can corrupt the table. Since Java 9 the map
  detects some of these and throws IllegalStateException
  ("Recursive update"), but not all of them.

  THE RULE: the mapping function must be SHORT, PURE and must not
  touch the map. A long-running load() also blocks every other
  writer to that bin — so for expensive loads, prefer a real cache
  (Caffeine) that handles this properly.

  ALSO ATOMIC, AND USEFUL:

    forEach, search, reduce           parallel bulk operations with
                                      a parallelism threshold
    keySet(true)                      a concurrent Set view backed
                                      by the map

Part 4 — Iteration, size() and Nulls

  WEAKLY CONSISTENT ITERATORS — the defining property:

    - they NEVER throw ConcurrentModificationException
    - they traverse elements as they existed at some point
    - they MAY or MAY NOT reflect updates made after creation
    - each element is returned exactly once

  So an iteration is not a snapshot and not live — it is somewhere
  between, and you cannot control which. That is the price of not
  locking the whole map.

  FAIL-FAST (HashMap) VS WEAKLY CONSISTENT (CHM):

    fail-fast    detects structural modification via a modCount and
                 throws CME. It is a BUG DETECTOR for single-threaded
                 misuse, not a safety mechanism — and it is
                 best-effort, so it can also miss.
    weakly consistent  never throws, never guarantees freshness.

  size() IS AN ESTIMATE under concurrent modification, and it is
  computed by summing striped counters rather than reading one field
  — which is why mappingCount() exists and returns a long:

    if (map.size() > MAX) reject();     // ❌ inherently racy

  Any decision based on size() is a check-then-act race. If you need
  a bound, use a Semaphore or a bounded queue, which enforce it.

  isEmpty() IS CHEAPER AND MORE RELIABLE than size() == 0.

  NULLS ARE BANNED — key AND value:

    map.put(k, null);        → NullPointerException
    map.get(k)               → null means WHAT?

  In a single-threaded HashMap you disambiguate with containsKey().
  Under concurrency that does not work: between get() returning null
  and containsKey() answering, another thread can insert or remove.
  The ambiguity is unresolvable, so the API forbids it.

  If absence must be representable as a value, use Optional or a
  sentinel object as the value.

Part 5 — Lists, Queues and Sets

  CopyOnWriteArrayList — EVERY MUTATION COPIES THE WHOLE ARRAY.

    add/remove/set    O(n), allocates a new array
    get/iterate       no lock, no CME, a true SNAPSHOT

  It is correct for exactly one shape: a small collection that is
  read constantly and written almost never. The canonical case is a
  LISTENER LIST — registered at startup, iterated on every event.

  It is catastrophic anywhere else: 1000 elements with 100 writes
  per second means 100 array copies of 1000 references per second,
  and every in-flight iterator holds its own old array alive.

  Its iterator is a snapshot, so remove() on it throws
  UnsupportedOperationException — there is nothing to remove from.

  THE BLOCKING QUEUES — the workhorses of producer/consumer:

    ArrayBlockingQueue      bounded, array-backed, ONE lock for
                            both ends, optional fairness
    LinkedBlockingQueue     optionally bounded (default
                            Integer.MAX_VALUE ← the trap), SEPARATE
                            head/tail locks so put and take do not
                            contend
    SynchronousQueue        capacity ZERO — every put waits for a
                            take. A handoff, not a buffer.
    PriorityBlockingQueue   unbounded, ordered by comparator
    DelayQueue              elements become available at a time
    LinkedTransferQueue     transfer() waits for a consumer

  THE DEFAULT-UNBOUNDED TRAP:

    new LinkedBlockingQueue<>()            // capacity 2^31-1
    Executors.newFixedThreadPool(10)       // uses exactly that

  A producer faster than the consumer never blocks; the queue grows
  until the heap is gone. An OutOfMemoryError instead of
  backpressure. ALWAYS pass a capacity.

  THE THREE WAYS TO OFFER, AND WHAT THEY SAY:

    add(e)              throws IllegalStateException when full
    offer(e)            returns false when full   ← lets the caller
                                                    decide
    put(e)              BLOCKS until space        ← backpressure
    offer(e, t, unit)   blocks up to a timeout

  SETS: ConcurrentHashMap.newKeySet() is the concurrent HashSet
  (there is no ConcurrentHashSet class).
  ConcurrentSkipListMap/Set are the concurrent SORTED structures —
  O(log n), lock-free, and the only concurrent option for range
  queries and navigation (headMap, ceiling, firstKey).

Part 6 — CAS, ABA and the Atomics

  COMPARE-AND-SWAP IS THE HARDWARE PRIMITIVE UNDER ALL OF THIS:

    boolean compareAndSet(expected, newValue)
      // atomically: if (value == expected) { value = newValue;
      //                                      return true; }
      //             else return false;

  One CPU instruction (LOCK CMPXCHG on x86). The classic loop:

    int old, next;
    do {
        old  = counter.get();
        next = old + 1;
    } while (!counter.compareAndSet(old, next));

  That is exactly what incrementAndGet does. It is LOCK-FREE — a
  thread that fails simply retries; it never blocks and cannot
  deadlock. But under heavy contention it BUSY-RETRIES, burning CPU.

  THE CONTENTION CLIFF:

    1 thread     ~5 ns per increment
    4 threads    ~30 ns   — retries plus cache-line ping-pong
    16 threads   ~100 ns+ — most CPU time is failed CAS

  All writers hammer ONE cache line, which must be exclusively owned
  by the writing core, so it bounces between cores.

  LongAdder SOLVES THIS BY NOT SHARING:

    internally: a base value plus an array of CELLS, padded so each
    lives on its own cache line. A thread hashes to a cell and
    increments THAT. sum() adds them up.

    16 threads: ~5 ns per increment (near single-threaded)
    sum():      O(cells), and NOT atomic with concurrent writes

  So: LongAdder for counters and metrics where you write constantly
  and read occasionally. AtomicLong when you need the exact current
  value on every operation (an id generator, a semaphore-like
  bound).

  THE ABA PROBLEM — CAS compares VALUES, not HISTORY:

    T1 reads A, is preempted
    T2 changes A -> B -> A
    T1's compareAndSet(A, C) SUCCEEDS

  The value matches, but the world changed underneath. For a simple
  counter this is harmless. For a lock-free stack it is fatal: the
  node you swapped in may point at a popped, recycled node.

  THE FIX IS A VERSION STAMP:

    AtomicStampedReference<Node> head;
    int[] stamp = new int[1];
    Node h = head.get(stamp);
    head.compareAndSet(h, newHead, stamp[0], stamp[0] + 1);

  AtomicMarkableReference carries a boolean instead, for
  logically-deleted nodes.

  THE ATOMIC FAMILY:

    AtomicInteger/Long/Boolean/Reference   single values
    AtomicIntegerArray etc.                element-wise atomics
    AtomicStampedReference                 ABA-safe
    LongAdder / DoubleAdder                write-heavy counters
    LongAccumulator                        any associative function
    AtomicIntegerFieldUpdater              atomics on an existing
                                           volatile field, no
                                           wrapper object
    VarHandle                              the modern low-level API

Interview Questions

Beginner: What is wrong with Collections.synchronizedMap?

It makes each individual method call atomic and nothing more, which is far less than the name suggests.

Compound operations are still races. if (!m.containsKey(k)) m.put(k, v); has two atomic calls with a gap between them, so two threads can both see "absent".

Iteration is not covered. The wrapper does not lock across a loop, so iterating throws ConcurrentModificationException unless you hold the wrapper's own monitor yourself — which the documentation requires and almost nobody does.

It is one lock for the whole map. Every read serialises behind every write, so a read-heavy map with many threads spends most of its time blocked.

ConcurrentHashMap fixes all three: atomic compound methods, weakly consistent iterators that never throw, and lock-free reads with per-bin write locking.

Beginner: Why does ConcurrentHashMap reject null keys and values?

Because get returning null would be ambiguous and the ambiguity would be unresolvable under concurrency.

In a single-threaded HashMap, null can mean "absent" or "present with a null value", and you disambiguate with containsKey. That works because nothing changes between the two calls.

Concurrently it does not: between get returning null and containsKey answering, another thread can insert or remove the key. There is no sequence of calls that gives you a reliable answer, so the API removes the question by banning nulls.

If absence needs to be a representable value, store a sentinel object or an Optional as the value.

Mid: How does ConcurrentHashMap achieve concurrency?

Three mechanisms, and the important one is that reads take no lock at all.

Writes: hash to a bin. If the bin is empty, insert with a single CAS — no lock. If it is occupied, synchronized on that bin's head node and walk the chain or tree. Two writes to different bins never contend, so write throughput scales until bins collide.

Reads: the table reference and each node's val and next are volatile, so a reader sees either the old node or the new one, never a half-linked chain. No lock is needed, which is why reads scale linearly with cores.

Resize is cooperative. A writer that finds a resize in progress helps transfer bins rather than blocking; a ForwardingNode redirects readers to the new table. That removes the stop-the-world rehash a synchronized HashMap would have.

Bins with more than 8 nodes treeify into red-black trees, bounding worst-case lookup at O(log n) — the same collision-DoS defence as HashMap.

Note this replaced the pre-Java-8 design of 16 fixed segment locks, which capped concurrency at the segment count regardless of table size.

Mid: What is the difference between fail-fast and weakly consistent iterators?
Fail-fast (HashMap, ArrayList)Weakly consistent (ConcurrentHashMap)
Concurrent modificationThrows ConcurrentModificationExceptionNever throws
FreshnessN/AMay or may not reflect later updates
Each elementOnceOnce
PurposeDetect a bugAllow safe traversal

Fail-fast is a bug detector, not a safety mechanism. It tracks a modCount and throws when it changes mid-iteration — and the documentation is explicit that this is best-effort, so you must not write code that depends on the exception being thrown.

Weakly consistent is a real guarantee, but a weak one. The traversal is neither a snapshot nor guaranteed live: elements added during iteration may or may not appear, and you cannot control which. That is the price of not locking the whole map.

If you genuinely need a snapshot, take an explicit copy — or use CopyOnWriteArrayList, whose iterator is a snapshot by construction.

Senior: When is LongAdder better than AtomicLong, and why?

Under write contention, which is most metrics and counters.

AtomicLong.incrementAndGet is a CAS retry loop. Every writer targets the same memory word, so two things degrade together: failed CAS attempts have to be retried, and the cache line holding the value must be exclusively owned by the writing core, so it ping-pongs between cores on every increment.

ThreadsAtomicLongLongAdder
1~5 ns~5 ns
4~30 ns~5 ns
16~100 ns+~5 ns

LongAdder avoids the sharing entirely: it keeps a base value plus an array of padded cells, each on its own cache line. A thread hashes to a cell and increments that one, so writers rarely touch the same line. sum() adds the cells up.

The trade-offs are real. Memory grows with contention (one cell per contending thread, roughly), and sum() is O(cells) and not atomic with concurrent writes — it can miss increments that land during the summation.

So the rule is: LongAdder when you write constantly and read occasionally — request counters, error counts, byte totals. AtomicLong when every operation needs the exact current value, such as an id generator or a bound you enforce with getAndIncrement.

Senior: What is the ABA problem and when does it matter?

CAS compares a value, not a history. If a location goes A → B → A between your read and your compare-and-set, the CAS succeeds even though the world changed underneath you.

T1 reads A, is preempted
T2 pops A, pushes B, pushes A again (a recycled node)
T1's compareAndSet(A, C) succeeds — on a different world

For a counter it is harmless — you only care that the arithmetic is right, and a value that returned to A means the intervening changes cancelled out.

For a lock-free linked structure it is fatal. In a Treiber stack, the A you re-observe may be a node that was popped, freed and recycled, whose next now points into the wrong part of the stack — so your CAS resurrects a lost or corrupted chain.

The fix is a version stamp. AtomicStampedReference pairs the reference with a counter you increment on every change, so a return to the same value still fails the comparison. AtomicMarkableReference carries a boolean instead, used for logically deleted nodes.

Why Java sees it less than C++ does: garbage collection. A node still referenced by T1 cannot be freed and reused, so the classic recycled-address form largely does not arise. It still occurs whenever you pool or reuse objects, or when the value itself is a reused key — so the risk tracks your own recycling, not the language.

Practical advice: unless you are writing a lock-free data structure, use the java.util.concurrent classes, which have already handled this. Hand-written lock-free code is one of the few places where being clever reliably loses.

🏋️ Graded Exercises

1 (easy): Why is this still racy, and what is the fix? 
Map<String,Integer> counts =
    Collections.synchronizedMap(new HashMap<>());

void record(String key) {
    counts.put(key, counts.getOrDefault(key, 0) + 1);
}
Solution

Two atomic calls do not make an atomic sequence. getOrDefault and put each hold the lock, but the lock is released between them — so two threads can both read 5 and both write 6, losing an increment.

private final Map<String,Integer> counts = new ConcurrentHashMap<>();

void record(String key) {
    counts.merge(key, 1, Integer::sum);     // one atomic operation
}
ApproachVerdict
merge(k, 1, Integer::sum)Correct and concise
computeIfAbsent(k, x -> new LongAdder()).increment()Better for hot keys — no boxing churn, no CAS retries
synchronized around both callsCorrect but serialises the whole map
AtomicInteger values with getAndIncrementWorks; merge reads better

Why this bug survives review: the collection is visibly "synchronized", so the line looks defended. The wrapper only ever protects one call at a time — and the moment you write two calls that depend on each other, you are back to a race.

The last one surprises people coming from HashMap, where this throws. ConcurrentHashMap's iterators are weakly consistent: they never throw, and removing through the map during iteration is explicitly supported.

3 (medium): This cache occasionally hangs. Why? 
private final Map<String,Node> cache = new ConcurrentHashMap<>();

Node get(String id) {
    return cache.computeIfAbsent(id, key -> {
        Node n = load(key);
        for (String childId : n.childIds()) {
            cache.computeIfAbsent(childId, this::loadChild);  // ❌
        }
        return n;
    });
}
Solution

The mapping function modifies the same map. You are executing inside a lock on id's bin; the nested computeIfAbsent tries to lock another bin — and if a child hashes to the same bin, the thread deadlocks against itself.

Since Java 9 the map detects some of these and throws IllegalStateException: Recursive update, but the detection is not complete — other cases corrupt the table or hang.

Node get(String id) {
    Node n = cache.get(id);
    if (n != null) return n;

    n = load(id);                          // load OUTSIDE the map lock
    List<Node> children = n.childIds().stream()
            .map(this::loadChild).toList();

    Node existing = cache.putIfAbsent(id, n);   // publish atomically
    if (existing != null) return existing;      // someone else won
    children.forEach(c -> cache.putIfAbsent(c.id(), c));
    return n;
}
Rule for computeIfAbsentWhy
Must not touch the same mapYou hold that bin's lock — re-entry deadlocks or corrupts
Must be shortIt blocks every other writer to that bin
Must be side-effect freeIt may run more than once across retries in some paths

The trade-off in the fix: load may now run more than once for the same key under a race, because the exactly-once guarantee came from holding the lock. That is usually the right trade — a duplicated load is cheaper than a deadlock — but if the load must be single-flighted, use a real cache library (Caffeine) whose loader handles exactly this.

4 (medium): Choose the right queue and say why. (a) 100k events/sec, one consumer, must not lose data. (b) A listener list read on every event, changed at startup only. (c) Tasks that should run at a specific future time. (d) A handoff where the producer must not proceed until a consumer takes the item.
Solution
ChoiceWhy
(a)LinkedBlockingQueue(capacity)Separate head and tail locks, so put and take do not contend — and a capacity gives backpressure
(b)CopyOnWriteArrayListLock-free snapshot iteration; the O(n) write cost is paid once at startup
(c)DelayQueue or ScheduledExecutorServiceElements become takeable only once their delay elapses
(d)SynchronousQueueCapacity zero — a put completes only when a take meets it

(a) is where "must not lose data" is the trap. The instinct is an unbounded queue so nothing is ever rejected — but that converts a throughput problem into an OutOfMemoryError, which loses everything. A bounded queue plus put pushes back on the producer, which is the only way to actually not lose data.

(b) fails badly if the list is large or written often — every mutation copies the whole array. It is right here precisely because writes happen once.

(d) requires an unbounded thread pool to be useful, which is exactly what newCachedThreadPool pairs it with: no queueing means a new thread for every task that arrives while all threads are busy.

5 (hard): This metrics counter is a bottleneck at high load. Diagnose and fix. 
public class Metrics {
    private final AtomicLong requests = new AtomicLong();
    private final AtomicLong errors   = new AtomicLong();

    public void recordRequest() { requests.incrementAndGet(); }
    public void recordError()   { errors.incrementAndGet(); }
    public long getRequests()   { return requests.get(); }
}
Solution

Every thread hammers the same cache line. incrementAndGet is a CAS retry loop, and the word holding the counter must be exclusively owned by the writing core — so it ping-pongs between cores while failed CAS attempts retry.

public class Metrics {
    private final LongAdder requests = new LongAdder();
    private final LongAdder errors   = new LongAdder();

    public void recordRequest() { requests.increment(); }
    public void recordError()   { errors.increment(); }
    public long getRequests()   { return requests.sum(); }
}
ThreadsAtomicLongLongAdder
1~5 ns~5 ns
4~30 ns~5 ns
16~100 ns+~5 ns

LongAdder wins by not sharing. It keeps a base plus an array of cells padded to separate cache lines; a thread hashes to a cell and increments that one, so writers rarely collide.

What you give up: sum() is O(cells) and not atomic with concurrent writes — it can miss increments landing during the summation. For a monitoring counter read once every 10 seconds, that is irrelevant; for a value you branch on, it is not.

A second problem worth catching: requests and errors are adjacent fields and may share a cache line even as AtomicLongs — false sharing between two unrelated counters. LongAdder's padding removes that too.

In production, use a metrics library. Micrometer's counters already do this, and add the tagging, aggregation and export you will want next.

6 (hard): Design a bounded LRU cache safe for concurrent use. State what you are giving up.
Solution

First: use Caffeine. A correct concurrent LRU is genuinely hard, and the library is faster than anything you will hand-roll. Write this to understand it, not to ship it.

// Simple, correct, and honest about its limits
public class LruCache<K,V> {
    private final int max;
    private final LinkedHashMap<K,V> map;

    public LruCache(int max) {
        this.max = max;
        this.map = new LinkedHashMap<>(16, 0.75f, true) {  // access order
            @Override protected boolean removeEldestEntry(Map.Entry<K,V> e) {
                return size() > LruCache.this.max;
            }
        };
    }

    public synchronized V get(K k)          { return map.get(k); }
    public synchronized void put(K k, V v)  { map.put(k, v); }
}
Why the obvious "better" versions failReason
ConcurrentHashMap + a size() checksize() is an estimate and check-then-act is racy — the cache overshoots
ConcurrentHashMap + a separate LRU listThe map and the list can no longer be updated atomically together
A ReadWriteLockA read reorders the LRU list, so it is a write — the read lock buys nothing
CopyOnWriteArrayList for orderO(n) per access

The third row is the insight. LRU makes every read mutate the recency order, so there are no true readers — which is why a naive concurrent LRU degenerates to a single lock anyway.

What the synchronized version gives up: throughput. All access serialises on one monitor, which is fine at thousands of ops/sec and not at millions.

How Caffeine avoids it: it does not maintain exact LRU order. Accesses are recorded in per-thread ring buffers and replayed in batches under a try-lock, so a read is nearly lock-free and eviction order is approximate — plus it uses a frequency sketch (TinyLFU) that gives a better hit rate than strict LRU anyway.

The lesson generalises: the way to make a concurrent data structure fast is usually to weaken a guarantee nobody actually needed, not to find a cleverer lock.

🎯 Key Takeaways

  • synchronizedMap makes single calls atomic and nothing else — compound operations remain races.
  • Iterating a synchronized wrapper requires holding its monitor yourself, which is why such code throws ConcurrentModificationException in production.
  • ConcurrentHashMap reads take no lock; writes CAS an empty bin or lock one bin's head node.
  • Resize is cooperative — writers help transfer bins, so there is no stop-the-world rehash.
  • The atomic compound methods are the real reason to use it: putIfAbsent, computeIfAbsent, merge.
  • The mapping function must not touch the map — recursive update deadlocks or corrupts, and detection is incomplete.
  • Keep mapping functions short; they block every other writer to that bin.
  • Nulls are banned because absent-versus-null cannot be disambiguated concurrently.
  • size() is an estimate, and any decision based on it is check-then-act anyway.
  • Weakly consistent iterators never throw and never promise freshness — they are not snapshots.
  • CopyOnWriteArrayList fits listener lists and almost nothing else — every write copies the array.
  • new LinkedBlockingQueue<>() is effectively unbounded, turning backpressure into an OutOfMemoryError.
  • offer lets the caller decide; put applies backpressure; add throws.
  • CAS is lock-free but busy-retries, and all writers contend on one cache line.
  • LongAdder beats AtomicLong for write-heavy counters by striping across padded cells — at the cost of a non-atomic sum().
  • ABA is harmless for counters and fatal for lock-free structures; use AtomicStampedReference.
