JVM Architecture & Class Loading JVM & Performance

What you'll master: the real pipeline from source to optimised machine code, and why javac deliberately optimises almost nothing; which runtime data areas are shared and which are per-thread, and the specific error each one throws when it fills; the three loading phases and what linking can throw long after startup; parent delegation — why it exists, and the two ecosystems that deliberately invert it; that class identity is name + defining loader, which is how you get a ClassCastException between a class and itself; NoClassDefFoundError vs ClassNotFoundException and why the first usually means a static initializer threw; and deoptimization — the JIT unwinding an optimisation whose assumption turned out false. Prerequisites: Classes, Objects & Encapsulation.

Part 1 — Source to Machine Code: the Whole Pipeline

  THERE ARE FIVE STAGES AND ONLY THE FIRST HAPPENS BEFORE YOU RUN:

    Account.java
        |
        |  javac — the only ahead-of-time step. Type-checks, resolves
        |  overloads, DESUGARS (lambda -> invokedynamic, enhanced for
        |  -> Iterator calls, generics -> erasure + checkcast,
        |  string concat -> invokedynamic/StringConcatFactory) and
        |  emits a stack-based instruction set.
        v
    Account.class   — bytecode + constant pool + metadata
        |
        |  CLASS LOADING — find the bytes, verify, prepare, resolve,
        |  run the static initializer. Happens LAZILY, at first use.
        v
    Class object in metaspace
        |
        |  INTERPRETER — starts executing immediately. Slow (roughly
        |  20-100x native) but zero startup cost. Counts invocations
        |  and loop back-edges as it goes.
        v
    C1 ("client") compiled code — fast to produce, ~5-10x interpreter
        |
        |  counters keep climbing; C1 code is instrumented with
        |  profile counters that C2 will consume
        v
    C2 ("server") compiled code — expensive to produce,
        aggressive, speculative, ~50-100x interpreter
        |
        |  a speculative assumption is VIOLATED
        v
    DEOPTIMIZE: discard the compiled frame, resume in the
    interpreter, re-profile, recompile with the new reality

  WHY javac IS DELIBERATELY DUMB

  javac performs almost no optimisation. No cross-method inlining,
  no loop unrolling, no constant propagation between methods, no
  dead-code elimination beyond `if (false)`. Compile this:

    int f(int a, int b, int c) { return a + b * c; }

  and javap -c shows exactly that, in order:

    iload_1
    iload_2
    iload_3
    imul
    iadd
    ireturn

  This is not laziness. The JVM has information javac cannot have:
  which branch actually runs, which receiver type actually shows up
  at a call site, whether an object ever escapes its method. A
  compiler that optimised early would only get in the way — and
  bake decisions into a .class file that must run on hardware that
  did not exist when it was compiled.

  BYTECODE IS AN UNTYPED STACK MACHINE, NOT A REGISTER MACHINE

  Every operation pops operands from an operand stack and pushes a
  result. There are no registers in the bytecode. The JIT is what
  allocates real registers. This is why bytecode is compact, and
  why reading it tells you about SEMANTICS, not about speed.

  THE PRACTICAL TAKEAWAY: reading bytecode answers "what did the
  language do here?" — did that string concat allocate, did that
  lambda capture, did that enhanced-for create an Iterator. It
  never answers "is this fast?". Only a profiler on running,
  warmed-up code answers that.

Part 2 — Runtime Data Areas: Shared vs Per-Thread

  THE JVM SPLITS MEMORY BY OWNERSHIP, AND THAT SPLIT IS THE ONE
  THAT MATTERS BOTH FOR CORRECTNESS AND FOR READING AN
  OutOfMemoryError CORRECTLY.

    +---------------------------- SHARED ----------------------------+
    |                                                                |
    |   HEAP                          METASPACE (native memory)      |
    |   all objects, all arrays       class metadata, method         |
    |   the GC's entire job           bytecode, field and method     |
    |                                 tables, the constant pool      |
    |                                                                |
    |   CODE CACHE (native)           Interned strings and static    |
    |   JIT-compiled machine code     fields live in the HEAP —      |
    |   plus stubs and adapters       they moved out of PermGen      |
    |                                 in Java 7 and 8                |
    +----------------------------------------------------------------+

    +------------------------- PER THREAD ---------------------------+
    |  JVM STACK      frames: locals, operand stack, frame data      |
    |  PC REGISTER    address of the current bytecode instruction    |
    |  NATIVE STACK   frames for JNI and native methods              |
    +----------------------------------------------------------------+

  WHY THE SPLIT MATTERS: anything per-thread needs no
  synchronization, ever. A local int cannot be raced on, because no
  other thread can name it. The moment a reference held in a stack
  frame is published to a field of a heap object, it becomes shared
  and every rule in the memory model applies to it.

  THE PC REGISTER IS PER-THREAD FOR AN OBVIOUS REASON: every thread
  is at a different instruction. It is undefined while a native
  method is executing — which is exactly why native frames appear
  in a stack trace without line numbers.

  READ THAT LAST ROW AGAIN. "unable to create native thread" is an
  OutOfMemoryError that has NOTHING TO DO WITH THE HEAP. Raising
  -Xmx makes it WORSE: heap and thread stacks compete for the same
  process address space and the same physical RAM, so a bigger heap
  leaves less room for stacks. The fix is fewer threads (a bounded
  pool) or a smaller -Xss — never a bigger heap.

  THE CODE CACHE IS THE ONE PEOPLE FORGET ENTIRELY. It is capped
  (240 MB on modern 64-bit JDKs; historically 48 MB, which large
  applications did hit). When it fills, the JVM logs:

    CodeCache is full. Compiler has been disabled.
    Try increasing the code cache size using -XX:ReservedCodeCacheSize=

  and from that moment everything runs INTERPRETED. Throughput
  falls off a cliff with no exception thrown, no GC pressure, and a
  heap that looks perfectly healthy in every dashboard you have.
  Applications with heavy runtime code generation — many proxies,
  many generated serialisers, a large Groovy or Kotlin surface —
  are the ones that get there.

Part 3 — Loading, Linking, Initialization

  A CLASS BECOMES USABLE IN THREE PHASES, AND THE MIDDLE ONE IS
  WHERE THE SURPRISES LIVE.

  1. LOADING
     A ClassLoader produces a byte[] from somewhere — a jar, a
     directory, a network stream, a generated proxy — and calls
     defineClass. The result is a java.lang.Class instance.
     Throws: ClassNotFoundException (a loader was asked and could
             not find it), NoClassDefFoundError (the VM needed it
             and it is not there).

  2. LINKING — three sub-phases:

     a. VERIFICATION
        The bytecode verifier proves the code is type-safe: the
        operand stack never underflows or overflows, every jump
        lands on an instruction boundary, no local is read before
        it is written, no aload appears where an iload belongs,
        every subclass relationship claimed is real. This is the
        JVM's security foundation — it is what makes it safe to
        run bytecode you did not compile yourself.
        Throws: VerifyError.

     b. PREPARATION
        Static fields are allocated and set to their DEFAULT
        values — 0, 0.0, false, null. NOT to their declared
        initializers. After preparation, `static int x = 5;` has
        x == 0. Nothing of yours has run yet.

     c. RESOLUTION
        Symbolic references in the constant pool ("the method
        named total with descriptor ()I on class Order") become
        direct references. The JVM spec explicitly PERMITS this to
        be lazy, and HotSpot is lazy: each reference is resolved
        the first time it is actually used.
        Throws: NoSuchMethodError, NoSuchFieldError,
                IllegalAccessError, NoClassDefFoundError.

  3. INITIALIZATION
     The JVM runs <clinit> — static field initializers and static
     blocks, concatenated in SOURCE ORDER. This is the only phase
     that runs code you wrote.
     Throws: ExceptionInInitializerError, wrapping whatever your
             static code threw.

  WHY LAZY RESOLUTION CAUSES SO MANY 3AM PAGES:

  You upgrade a library. A method signature changed. Your code
  compiled against the old jar, the service starts fine, serves
  traffic fine for six hours — and then the first request that
  reaches that one code path throws NoSuchMethodError. Nothing
  "broke at deploy": resolution simply had not happened yet.

  This is why a smoke test that only hits /health proves almost
  nothing about a dependency upgrade. The classes on the health
  path resolved; nothing else did.

  WHEN DOES INITIALIZATION ACTUALLY TRIGGER? The spec lists exactly
  these:
    - creating an instance of the class
    - reading or writing a static field (with the exception below)
    - invoking a static method
    - Class.forName(name) with initialize = true (the default)
    - initializing a subclass, which triggers its superclass first
    - the class is the main class of the program

  AND HERE IS THE ONE THAT SURPRISES EVERYONE:

    class Config { static { System.out.println("init!"); }
                   static final int MAX = 100; }

    System.out.println(Config.MAX);   // prints 100. NOT "init!".

  A static final field of primitive or String type, initialised
  with a COMPILE-TIME CONSTANT expression, is inlined into the
  caller's own constant pool by javac. The symbolic reference to
  Config disappears from the caller entirely, so the class is
  never loaded, let alone initialized.

  THREE CONSEQUENCES:
    - You can delete Config.class and the caller still runs.
    - Change the constant, recompile only Config, and every
      caller keeps the OLD value until IT is recompiled too. This
      is a real and recurring versioning bug in multi-module
      builds.
    - `static final int MAX = compute();` is NOT a compile-time
      constant, so it does trigger initialization. Neither is a
      boxed Integer, an array, or any object.

Part 4 — Class Loaders and Parent Delegation

  THE HIERARCHY ON JAVA 9 AND LATER (Java 8 called the middle one
  the "extension" loader; the bootstrap loader is unchanged):

    Bootstrap ClassLoader     — native code, represented as null
        |   loads java.base: java.lang, java.util, java.io
        |
    Platform ClassLoader
        |   loads the rest of the JDK: java.sql, java.xml, crypto
        |
    Application ClassLoader
        |   loads YOUR classes from the classpath / module path
        |
    (your own loaders: web app, plugin, script engine, agent)

  PARENT DELEGATION: asked to load a class, a loader FIRST asks its
  parent, which asks its parent, all the way to bootstrap. Only if
  every ancestor declines does the loader look for the class
  itself. In code, that is essentially ClassLoader.loadClass:

    protected Class<?> loadClass(String name, boolean resolve) {
        Class<?> c = findLoadedClass(name);       // already done?
        if (c == null) {
            try   { c = parent.loadClass(name, false); }  // ASK UP
            catch (ClassNotFoundException e) { /* keep going */ }
            if (c == null) c = findClass(name);   // then try me
        }
        return c;
    }

  WHY IT EXISTS — TYPE SAFETY AND SECURITY

  Put this on your classpath:

    package java.lang;
    public class String { public String() { exfiltrate(); } }

  Without delegation the application loader would find your
  java.lang.String first, and every string in the JVM would be
  yours. With delegation the bootstrap loader is asked first, it
  has a java.lang.String, and yours is never even looked at.

  Modern JDKs add a second guard: defining a class in a package
  beginning "java." from a non-bootstrap loader throws
  SecurityException outright. Delegation is the structural defence;
  the package check is belt and braces.

  A SECOND CONSEQUENCE, EQUALLY IMPORTANT: delegation guarantees
  that a class name resolves to ONE Class object across many
  loaders, as long as a common ancestor can supply it. That is
  what makes types interchangeable across a plugin boundary.

  WHERE DELEGATION IS DELIBERATELY INVERTED

  1. SERVLET CONTAINERS (Tomcat, Jetty). Each web application gets
     a loader that tries ITSELF FIRST for most packages and only
     then asks the parent. The reason: two applications in one
     container must be able to ship different versions of the same
     library. If WAR A needs Jackson 2.9 and WAR B needs 2.15,
     strict delegation would hand both whichever version the
     container loaded first. The container still delegates
     java.*, javax./jakarta. and the servlet API upward, so the
     types the container itself must understand stay shared.

  2. OSGi. Each bundle declares Import-Package and Export-Package,
     and the framework wires loaders into a GRAPH, not a tree. A
     bundle's loader delegates PER PACKAGE to whichever bundle
     exports it. This is the most complete answer to "several
     versions of one library in one JVM" and also by far the most
     complex; most teams now solve the same problem with separate
     processes, which is a legitimate trade.

  3. THREAD CONTEXT CLASSLOADER. A service-provider API loaded
     high in the tree (JDBC, JAXP, JNDI) needs to instantiate an
     IMPLEMENTATION that lives further down — which strict
     delegation forbids, since parents cannot see children.
     Thread.currentThread().getContextClassLoader() is the escape
     hatch: a mutable per-thread pointer to "the loader that
     should be used for lookups here". It causes endless framework
     bugs precisely because it is global mutable state that thread
     pools cheerfully carry from one unrelated task to the next.
  CLASS IDENTITY = FULLY-QUALIFIED NAME + DEFINING LOADER

  This is the single most surprising rule in the JVM, and it
  produces the stack trace that looks impossible:

    java.lang.ClassCastException: com.acme.Order
        cannot be cast to com.acme.Order

  It is not a JVM bug. Two loaders each defined a class named
  com.acme.Order. They are DIFFERENT RUNTIME TYPES that happen to
  share a name.

    ClassLoader a = new URLClassLoader(new URL[]{jar}, null);
    ClassLoader b = new URLClassLoader(new URL[]{jar}, null);
    // note: SAME jar

    Class<?> ca = a.loadClass("com.acme.Order");
    Class<?> cb = b.loadClass("com.acme.Order");

    ca == cb                            // false
    ca.getName().equals(cb.getName())   // true — same name
    ca.isAssignableFrom(cb)             // false — unrelated types

  This only happens when com.acme.Order is NOT reachable from a
  shared parent. If it is, delegation gives both loaders the same
  Class object and everything works. The bug appears when a jar
  sits BOTH on the parent classpath AND inside a child loader that
  loads child-first.

  HOW TO DIAGNOSE IT IN THIRTY SECONDS:

    System.out.println(obj.getClass().getClassLoader());
    System.out.println(Order.class.getClassLoader());

  Two different loaders printed means you have found it. The fix is
  structural: the shared TYPE must have exactly one definer,
  normally a thin parent-visible "api" jar, with implementations
  in the child loaders.

  WHY THE JVM IS DESIGNED THIS WAY: the alternative — global name
  uniqueness — would make it impossible to run two versions of a
  library in one JVM, and would let any loader shadow any type.
  Loader-scoped identity is exactly what makes app servers, plugin
  systems and hot redeploy possible at all.

Part 5 — When Loading Fails: Reading the Error Correctly

  THESE TWO ARE CONSTANTLY CONFUSED AND THEY MEAN DIFFERENT THINGS.

  ClassNotFoundException — a CHECKED EXCEPTION
    Someone asked for a class BY NAME at runtime and the loader
    could not find it:
      Class.forName("com.mysql.cj.jdbc.Driver")
      loader.loadClass("com.acme.Plugin")
      ServiceLoader / reflection inside a framework
    Cause: it genuinely is not on the classpath, the name is
    misspelled, or you used a source name ("Outer.Inner") where
    the BINARY name ("Outer$Inner") is required.

  NoClassDefFoundError — an ERROR, NOT AN EXCEPTION
    The class was present when the calling code was COMPILED, and
    the VM cannot supply it now. Two very different causes:

    (a) It really is absent at runtime — a dependency in the
        compile scope but not the runtime scope (Maven
        `provided`), or a shaded/minimised jar that stripped it,
        or a fat-jar merge that dropped it.

    (b) *** THE ONE PEOPLE MISS *** Its static initializer THREW.
        Initialization is attempted exactly ONCE. If <clinit>
        throws, the class is permanently marked ERRONEOUS. The
        FIRST use gets:

          ExceptionInInitializerError
            caused by: NullPointerException at Config.<clinit>

        and EVERY SUBSEQUENT use, in every thread, forever, gets:

          NoClassDefFoundError: Could not initialize class Config

        The message even tells you: "Could not INITIALIZE". Not
        "could not find".

  THE DEBUGGING RULE THAT SAVES HOURS:

    "Could not initialize class X"  ->  SCROLL BACK IN THE LOG.

  The real cause was logged once, possibly minutes or hours
  earlier, possibly on a different thread, possibly at a log level
  someone filtered out. The NoClassDefFoundError you are staring
  at is an echo with none of the diagnostic content.

  THE TYPICAL REAL CAUSE is a static field doing environment I/O:

    class Config {
        static final String URL =
            System.getenv("DB_URL").trim();   // NPE if unset
    }

  Works on every developer laptop. Fails in exactly one region's
  deployment. Produces thousands of misleading
  NoClassDefFoundErrors downstream, and sends the on-call engineer
  hunting a classpath problem that does not exist.
  STATIC INITIALIZER ORDERING — TOP TO BOTTOM, ALWAYS

    class Broken {
        static int a = compute();        // runs first
        static int b = 10;               // runs second
        static int compute() { return b * 2; }   // b is still 0
    }
    // a == 0, not 20.

  <clinit> is field initializers and static blocks WOVEN TOGETHER
  IN SOURCE ORDER. A method called from an early initializer sees
  later fields at their PREPARATION values: 0, 0.0, false, null.
  This compiles without a warning and is a genuine production bug.

  The rule: never call a method from a static initializer that
  reads other static fields of the same class. If you must, order
  the declarations so dependencies come first — but that is
  fragile, because it survives only until someone reformats the
  file. A holder class or a compile-time constant is better.

  CIRCULAR STATIC INITIALIZATION IS WORSE STILL

    class A { static final int X = B.Y + 1; }
    class B { static final int Y = A.X + 1; }

  Touch A first: A's <clinit> starts, triggers B's <clinit>,
  which reads A.X. A is already "in progress" ON THIS THREAD, so
  the JVM does NOT re-enter — it simply returns the current value,
  0. Result: B.Y == 1 and A.X == 2. Touch B first and you get the
  mirror image: A.X == 1, B.Y == 2.

  The answer depends on which class the program happened to touch
  first. No error, no warning, just different numbers on different
  runs of what looks like the same program.

  <clinit> DEADLOCK — TWO CLASSES, TWO THREADS

  Initialization is protected by a per-class lock, held for the
  ENTIRE duration of <clinit>.

    Thread 1: touches A -> holds lock(A) -> A's clinit needs B
    Thread 2: touches B -> holds lock(B) -> B's clinit needs A

  Classic lock-ordering deadlock — but a nasty variant, because it
  does NOT appear as a deadlock in a thread dump. jstack's
  deadlock detector understands object monitors and
  java.util.concurrent locks; class-initialization locks are
  internal. What you see is a process that starts, prints nothing
  further, and sits at 0% CPU forever, with threads parked in
  frames named <clinit>.

  REAL TRIGGERS: a logging framework whose static setup touches a
  config class whose static setup logs. Two enums referencing each
  other's constants. A DI container initialising two singletons
  concurrently. Keep static initialization SHALLOW, and if a cycle
  is unavoidable, force the order on one thread in main() before
  any worker starts.

Part 6 — The JIT: Tiering, OSR, Inlining, Deoptimization

  HOTSPOT RUNS FIVE TIERS, NOT TWO. THE DETAIL MATTERS BECAUSE IT
  EXPLAINS WHY BENCHMARKS AND STARTUP CURVES LOOK THE WAY THEY DO.

    Tier 0   Interpreter                     (profiling: counters)
    Tier 1   C1, fully optimised, NO profiling
             — used when C2 has decided this method will never be
               worth recompiling, e.g. trivial getters
    Tier 2   C1 with basic counters
    Tier 3   C1 with FULL profiling           (slower than tier 1)
    Tier 4   C2, fully optimised, consuming tier-3 profile data

  The usual path is 0 -> 3 -> 4. Tier 3 is INTENTIONALLY slower
  than tier 1 because it is collecting the type and branch profiles
  that C2 needs. A method that stalls at tier 3 — because the C2
  compile queue is long — runs slower than the same method would at
  tier 1. That is a real cause of "the service is slow for the
  first two minutes after deploy".

  ROUGH THRESHOLDS (tiered defaults; they scale with compile-queue
  length, so treat them as magnitudes, not constants):

    ~200 invocations                 -> C1
    ~5,000-10,000 invocations        -> C2
    loop back-edge counters trigger the same escalation

  ON-STACK REPLACEMENT (OSR)

  What about a method invoked ONCE that contains a ten-million-
  iteration loop? Invocation counters never fire. The back-edge
  counter does: the JVM compiles the loop and SWAPS THE RUNNING
  FRAME, mapping interpreter locals into compiled-code registers
  mid-execution. That is OSR.

  OSR code is generally WORSE than a normal compilation. Its entry
  point is the loop head rather than the method head, so some
  optimisations — particularly hoisting loop-invariant work above
  the entry — are unavailable. This is exactly why a hand-rolled
  benchmark consisting of one giant for-loop in main() measures
  the OSR version of your code and not the version production will
  actually run.

  INLINING IS THE MOTHER OF ALL OPTIMISATIONS

  Not because a call is expensive — a call is a couple of
  nanoseconds — but because inlining creates the LARGER SCOPE in
  which everything else becomes possible: constant propagation
  across the boundary, escape analysis proving an object never
  leaves, lock elision, dead-branch removal, vectorisation.

    -XX:MaxInlineSize=35       bytecode bytes; always try to inline
    -XX:FreqInlineSize=325     bytecode bytes; for HOT call sites
    -XX:MaxInlineLevel=15      maximum call-chain depth

  THE PRACTICAL RULE: keep hot methods SMALL. A 400-byte hot method
  will not be inlined into its caller, and that blocks a whole
  chain of downstream optimisations. This is the rare case where
  "extract method" makes code both clearer and faster.

  MONOMORPHIC, BIMORPHIC, MEGAMORPHIC

  At a virtual call site the JIT records which receiver types have
  actually turned up:

    1 type  (monomorphic) — inline directly, guarded by a single
                            class-pointer compare. Effectively free.
    2 types (bimorphic)   — inline both, guarded.
    3+      (megamorphic) — give up: emit a real vtable dispatch
                            and inline NOTHING past it.

  This is why a List field that only ever holds ArrayList is fast,
  and why the same code measurably slows down once a third
  implementation starts flowing through the same call site. It is
  also why adding a test double or a decorator in production code
  can cost more than the decorator itself does.
  DEOPTIMIZATION — THE MECHANISM THAT MAKES SPECULATION SAFE

  C2 optimises on things that are true SO FAR but are not
  guaranteed to stay true:

    - "this call site has only ever seen ArrayList"
    - "this branch has never been taken"
    - "this method is effectively final — no subclass overrides it"
    - "this reference has never been null here"
    - "this exception path is never entered"

  Each speculation is compiled with a cheap GUARD — a class-pointer
  compare, a branch to an "uncommon trap". When the guard fails —
  someone loads a subclass, the never-taken branch is finally taken
  — the JVM performs DEOPTIMIZATION:

    1. Stop the thread at a safepoint.
    2. Reconstruct interpreter frames from the compiled frame,
       using debug metadata the compiler recorded for exactly this
       purpose (this is why compiled code carries a description of
       the interpreter state at every safepoint).
    3. Resume execution in the interpreter, mid-method.
    4. Mark the compiled code "not entrant"; recompile later with
       the new information folded into the profile.

  THIS IS WHY LOADING A CLASS CAN SLOW DOWN CODE THAT NEVER
  MENTIONS IT. Class Hierarchy Analysis had proved a method had no
  overriding subclass and the JIT inlined it everywhere. Loading a
  subclass — via a plugin, a mock, a lazily created strategy —
  invalidates that proof and deoptimizes every call site that
  relied on it, all at once.

  You experience that as a latency spike several minutes into a
  load test, with no GC event and no lock contention to explain it.

  A DEOPTIMIZATION LOOP is the pathological case: the JIT
  recompiles, the guard fails again, it deoptimizes again.
  Symptoms: sustained CPU in the compiler threads and throughput
  that never settles.
    -XX:+UnlockDiagnosticVMOptions -XX:+PrintDeoptimization
  names the reason: unstable_if, class_check, null_check,
  bimorphic, unreached.

  WATCHING THE JIT WORK

    -XX:+PrintCompilation

  emits one line per compilation:

    1234  456       4       com.acme.Order::total (48 bytes)
    1240  456       4       com.acme.Order::total (48 bytes) made not entrant
    1301  501 %     4       com.acme.Order::sum @ 12 (95 bytes)

  Columns: milliseconds since start, compilation id, TIER, then
  the method and its bytecode size. The flag column carries the
  information:

    %                   OSR compilation — the benchmark smell
    s                   synchronized method
    !                   has exception handlers
    n                   native wrapper
    made not entrant    the code was DEOPTIMIZED
    made zombie         the old code is now unreachable and freed

  A steady stream of "made not entrant" for the same method in

Part 7 — Metaspace, PermGen, and Class Loader Leaks

  JAVA 8 REPLACED PERMGEN WITH METASPACE, AND THE CHANGE WAS NOT
  COSMETIC.

    PermGen (Java 7 and earlier)
      - part of the JAVA HEAP
      - fixed maximum (-XX:MaxPermSize, default ~64-82 MB)
      - collected only during a FULL GC
      - held class metadata, interned Strings and static fields
      - "OutOfMemoryError: PermGen space" was the single most
        common application-server error of that decade

    Metaspace (Java 8 and later)
      - NATIVE memory, outside the heap
      - UNBOUNDED by default: it grows until the machine says no
      - freed PER CLASS LOADER: when a loader becomes unreachable,
        all of its classes' metadata is released as one unit
      - interned Strings and static fields moved to the HEAP in
        Java 7 and 8

  THE UNBOUNDED DEFAULT IS A TRAP DRESSED AS A FIX. A class loader
  leak used to fail fast and loudly at 82 MB with a clear
  OutOfMemoryError and a heap dump. Now it grows quietly to
  gigabytes and the KERNEL OOM-KILLER terminates the container:
  exit code 137, no Java stack trace, no heap dump, nothing in the
  application log. In a container, ALWAYS set:

    -XX:MaxMetaspaceSize=256m

  so that the failure is a Java error you can catch, dump on, and
  diagnose.

  WHAT ACTUALLY FILLS METASPACE — IT IS RARELY "TOO MANY CLASSES"

  1. DYNAMIC PROXIES AND GENERATED CLASSES
     Every Spring AOP proxy, Hibernate-enhanced entity, Mockito
     mock, generated JSON serialiser and lambda call site defines a
     REAL CLASS. A lambda's implementation class is spun at runtime
     by LambdaMetafactory on FIRST EXECUTION of its invokedynamic
     call site — which is why the first call through a lambda is
     dramatically slower than the millionth, and why heavy lambda
     use pushes both startup time and metaspace up.

  2. CLASS LOADER LEAKS ON REDEPLOY — the classic
     Redeploy a WAR. The container drops its loader and expects
     everything to be collected. ONE reference from outside the
     application pins that loader — and a loader pins EVERY class
     it defined, each class pins its static fields, and those pin
     arbitrary object graphs. A single dangling reference retains
     tens of megabytes, and ten redeploys kill the process.

     THE USUAL SUSPECTS, roughly by frequency:

       A ThreadLocal set on a CONTAINER thread-pool thread and
         never removed. The pool outlives the application; the
         value's class pins the application loader.
       A THREAD started by the application and never stopped. A
         running thread is a GC root, and its context class loader
         is yours.
       DriverManager still holding a JDBC Driver that the
         application loader defined.
       A shutdown hook, a JMX MBean, or a logging appender
         registered in a container-level registry.
       java.beans.Introspector, or any JDK-level cache keyed by
         your Class objects.

  3. GENUINELY MANY LOADERS
     Script engines, rule engines, JSP recompilation, and test
     frameworks that build a fresh Spring context per test class
     each create loaders. One is fine; ten thousand are not.

  DIAGNOSING IT

    jcmd <pid> VM.classloader_stats
    jcmd <pid> GC.class_stats
    jcmd <pid> VM.native_memory summary   (needs NativeMemoryTracking)
    -Xlog:class+load=info   /   -Xlog:class+unload=info

  The signature is a class count climbing monotonically while the
  heap live set stays flat, and a class+load stream with an empty
  class+unload stream. In Eclipse MAT, open a heap dump and look
  for many instances of the SAME loader class, then run "path to
  GC roots, excluding weak references" on one of them. The single
  strong reference you find is the leak.

Interview Questions

Beginner: Walk me through what happens when you run java Main.

The launcher starts the JVM, which reserves the heap, creates the main thread, and sets up the class loader hierarchy — bootstrap (native, loads java.base), platform, then application.

The application loader is asked for Main. It delegates to its parent first, which delegates to bootstrap; nobody up the chain has it, so the application loader reads the bytes and calls defineClass. The class is then verified (proved type-safe), prepared (statics set to default values, not their initializers), and its references are resolved lazily. Finally <clinit> runs — static blocks and static field initializers in source order.

main is invoked and starts executing in the interpreter. Nothing is compiled yet. As methods are called and loops spin, invocation and back-edge counters climb; around a couple of hundred invocations the method is compiled by C1, and around several thousand by C2 using the profile C1 collected.

Every other class is loaded the same way — lazily, on first use. That laziness is why a missing dependency or a bad static initializer can surface hours into a run rather than at startup, and why a health-check smoke test proves very little about a dependency upgrade.

Beginner: What is the difference between ClassNotFoundException and NoClassDefFoundError?

ClassNotFoundException is a checked exception thrown when code explicitly asks for a class by name — Class.forName, loader.loadClass — and the loader cannot find it. The cause is nearly always a wrong name string or a genuinely absent jar.

NoClassDefFoundError is an Error: the class was present when the calling code was compiled, and the VM cannot supply it now. That has two causes, and people remember only the first.

The first is a real absence — a Maven provided dependency that never reached the runtime classpath, or a shaded jar that stripped the class out.

The second, and in production the more common one, is that the class exists but its static initializer threw. Initialization is attempted exactly once; if it fails, the class is marked erroneous permanently. The first thread gets ExceptionInInitializerError with the real cause attached; every subsequent use in every thread gets NoClassDefFoundError: Could not initialize class X. The message literally says "initialize", not "find" — so when I see it, my first action is to search backwards in the log for the original exception, which may be hours old and on a different thread.

Mid: Explain parent delegation and why it exists. Where is it deliberately broken?

When a loader is asked for a class it first asks its parent, recursively up to the bootstrap loader, and tries to find the class itself only if every ancestor declines.

The reason is type safety. Without delegation, putting a class named java.lang.String on the classpath would let it shadow the real one, and every string in the JVM would be attacker-controlled. With delegation, the bootstrap loader answers first and yours is never consulted. A secondary benefit is uniqueness: if a common ancestor can supply a type, everyone below it shares one Class object, which is what makes types interchangeable across a plugin boundary.

It is inverted in three well-known places. Servlet containers use child-first loading per web application so that two WARs can bundle different versions of the same library — while still delegating java.* and the servlet API upward so the container's own types stay shared. OSGi goes further and wires loaders into a graph, delegating per package according to declared imports and exports. And the thread context class loader exists for the opposite problem: a JDK-level SPI such as JDBC or JAXP, loaded high in the tree, must instantiate an implementation that lives below it, which delegation forbids since parents cannot see children.

All three trade safety for flexibility, and all three are a steady source of bugs — duplicate types, leaked loaders, and a context loader that a thread pool carried into an unrelated task. My recommendation is to reach for them last: if the versioning problem can be solved by running two processes instead of two loaders, that is almost always the cheaper answer in a containerised world.

Mid: How can a ClassCastException say a class cannot be cast to itself?

Because a runtime type is not just a name. Class identity is the fully-qualified name plus the defining class loader. Two loaders that each read the same bytes produce two distinct Class objects that are not assignable to one another, even though getName() returns the same string.

The usual setup is a jar that appears in two places: on the parent classpath, and again inside a child-first loader such as a web application or a plugin. Delegation would have prevented it, but child-first loading means the child defines its own copy. An object created on one side and passed to the other fails the cast.

Diagnosing it takes thirty seconds: print obj.getClass().getClassLoader() and Target.class.getClassLoader(). Different loaders confirm it. In a heap dump you will see two instances of the same class name with different loader fields.

Senior: A service is fast in steady state but has unexplained latency spikes minutes into a load test. No GC events, no lock contention. Where do you look?

With GC and locks excluded, my first hypothesis is the JIT — specifically deoptimization — and I would confirm it before theorising further.

C2 compiles speculatively: this call site has only seen one receiver type, this branch has never been taken, this method has no overriding subclass, this reference is never null here. Each speculation is cheap only because it is compiled behind a guard. When a guard fails, the JVM must stop at a safepoint, rebuild interpreter frames from debug metadata, resume interpreting mid-method, and later recompile. For a hot method that is a visible stall, and it lands minutes in — exactly when a rare code path, a new subclass, or the first null finally arrives.

The class-hierarchy case is the least intuitive and the one I check first, because it means loading a class can slow down code that never mentions it. If Class Hierarchy Analysis proved a method had no overrides, the JIT inlined it everywhere; loading a subclass — from a plugin, a lazily created strategy, a mock in a staging build — invalidates that proof and deoptimizes every dependent call site at once.

Confirmation is cheap. -XX:+PrintCompilation and look for repeated "made not entrant" on hot methods in steady state; -XX:+PrintDeoptimization names the reason (unstable_if, class_check, null_check). JFR's compilation events show the same thing with timestamps you can line up against the latency graph.

My recommendation is usually not a JVM flag. It is to make the speculation stable: warm the rare path during startup so its profile exists before traffic arrives, and avoid introducing a third implementation into a hot polymorphic call site. Reaching for -XX:PerMethodRecompilationCutoff treats the symptom and hides the cause.

Senior: A container is OOM-killed every few days. Heap usage is flat and healthy. What is your diagnosis?

A flat heap with a dying container points at native memory. Metaspace is the first place I look, followed by thread stacks and direct byte buffers.

Metaspace lives outside the heap and is unbounded by default. Under PermGen this class of bug failed fast at about 80 MB with a clear OutOfMemoryError. Now it grows quietly into gigabytes and the kernel kills the process: exit code 137, no stack trace, no heap dump, nothing in the application log. The first change I make is -XX:MaxMetaspaceSize, not to fix the leak but to make it diagnosable — a Java error I can dump on beats a silent kill.

Metaspace is freed per class loader: all of a loader's metadata is released together when that loader becomes unreachable. So growth means either genuinely more classes (dynamic proxies, generated serialisers, lambda call sites, a fresh Spring context per test class, a script engine) or — far more often — a class loader leak. One reference from outside the loader's intended lifetime pins it, and a loader retains every class it defined, which retains every static field, which retains arbitrary object graphs.

I confirm with jcmd VM.native_memory summary and jcmd VM.classloader_stats, and I compare -Xlog:class+load against -Xlog:class+unload. Loading without unloading is the signature. Then a heap dump in MAT, filtered to loader instances, with "path to GC roots excluding weak references" on one of them.

And stop treating redeploy-in-place as a supported operation: in a containerised deployment the honest answer to class loader leaks is to restart the process, which is a design decision worth making explicitly rather than discovering one dangling reference at a time.

2 (easy): Why does the second call report a different error than the first? 
class Registry {
    static final Map<String,String> MAP = load();

    static Map<String,String> load() {
        return Map.of("url", System.getenv("SERVICE_URL").trim());
    }
}
// SERVICE_URL is not set in this environment.
// First use:  Registry.MAP  -> ExceptionInInitializerError
// Later uses: Registry.MAP  -> NoClassDefFoundError
Solution

System.getenv returns null, .trim() throws NullPointerException inside <clinit>, and the JVM wraps it in ExceptionInInitializerError.

What happens next is the important part. A class is initialized at most once. When <clinit> throws, the class is permanently marked erroneous — there is no retry, no partial state, no second chance. Every later use, from any thread, gets NoClassDefFoundError: Could not initialize class Registry, which carries none of the original diagnostic information.

In production this is brutal. The one message naming the real problem is logged once, at startup, and then thousands of misleading "class not found" errors follow it. Engineers chase a classpath problem that does not exist.

// Fix 1 — fail loudly with a message that survives
static final Map<String,String> MAP = load();

static Map<String,String> load() {
    String url = System.getenv("SERVICE_URL");
    if (url == null)
        throw new IllegalStateException(
            "SERVICE_URL is not set; cannot initialize Registry");
    return Map.of("url", url.trim());
}

// Fix 2 — better: do no environment I/O in a static initializer at
// all. Read and validate configuration in main(), then pass it in.

3 (medium): Why is a zero? 
public class Broken {
    static int a = compute();
    static int b = 10;
    static int compute() { return b * 2; }

    public static void main(String[] args) {
        System.out.println(a);   // 0
        System.out.println(b);   // 10
    }
}
Solution

Because preparation and initialization are different phases. During preparation every static field is allocated and set to its default value, so b becomes 0. Only later, in <clinit>, do the declared initializers run — in source order.

So a = compute() executes first; compute() reads b, which is still at its preparation value of 0; a becomes 0. Then b = 10 executes. The compiler emits no warning, because nothing here is illegal.

// Fix A — declare dependencies before dependents
static int b = 10;
static int a = compute();          // a == 20

// Fix B — constants, folded at compile time, order-proof
static final int B = 10;
static final int A = B * 2;

// Fix C — compute lazily, order-independent by construction
private static int a = -1;
static int a() {
    if (a < 0) a = b * 2;
    return a;
}
Point in timeba

After a = compute()00
After b = 10100

The general rule: a static initializer must not call a method that reads other static fields of the same class. Fix A works but is fragile — it survives only until someone reorders the file, and no test will catch that. Fix B is what I would ship, because constant folding removes the ordering question entirely. The identical trap exists for instance fields when a constructor calls an overridable method: the subclass's fields have not been initialized yet, for exactly the same reason.

5 (hard): The application starts, prints nothing further, and hangs at 0% CPU. Explain and fix. 
class Settings {
    static final Settings INSTANCE = new Settings();
    static { Logger.init(); }
    Settings() { Logger.log("Settings created"); }
    void check() { }
}

class Logger {
    static final Logger LOG = new Logger();
    static { Settings.INSTANCE.check(); }
    static void init() { }
    static void log(String s) { System.out.println(s); }
}

// Thread A: new Settings();       Thread B: Logger.log("hi");
Solution

This is a <clinit> deadlock. Class initialization is guarded by a per-class lock that is held for the entire duration of <clinit>, and the two threads acquire the two locks in opposite orders.

Thread A                          Thread B
--------                          --------
touch Settings                    touch Logger
acquire init-lock(Settings)       acquire init-lock(Logger)
run Settings.<clinit>             run Logger.<clinit>
  -> Logger.init()                  -> Settings.INSTANCE
  -> needs init-lock(Logger)        -> needs init-lock(Settings)
     BLOCKED                           BLOCKED

What makes it vicious is the diagnosis. There is no "Found one Java-level deadlock" section in the thread dump, because these are internal class-initialization monitors, not the object monitors and j.u.c locks that jstack's deadlock detector understands. What you get is threads parked in frames named <clinit>, no obvious cycle, and a process at 0% CPU that never finishes starting.

Note also that single-threaded, this code does not deadlock at all. The JVM lets a thread re-enter a class it is already initializing, returning partially initialized values — so single-threaded you would get a silent null or 0 instead of a hang. That is precisely why this survives unit tests and appears in production under concurrent startup.

// Fix 1 — break the cycle. Logging must not depend on Settings.
class Logger {
    static void log(String s) { System.out.println(s); }
}

// Fix 2 — lazy holder: initialization happens on first USE, not
// inside another class's <clinit>.
class Settings {
    private static class Holder { static final Settings I = new Settings(); }
    static Settings get() { return Holder.I; }
}

// Fix 3 — if a cycle is genuinely unavoidable, force the order on
// ONE thread before any worker starts.
public static void main(String[] args) throws Exception {
    Class.forName("Logger");     // fully initialise, single-threaded
    Class.forName("Settings");
    startWorkers();
}

// The honest version — JMH, in its own module
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)

@State(Scope.Benchmark)
public class ComputeBench {
    private int x;                        // NOT final, NOT a constant

    @Setup
    public void setup() {
        x = ThreadLocalRandom.current().nextInt(1, 100);
    }

    @Benchmark
    public int compute() {                // returned -> consumed by JMH
        return x * x + x / 3 - 7;
    }
}

Three things do the work here. Returning the value (or feeding it to a Blackhole) defeats dead-code elimination. A non-final field assigned in @Setup defeats constant folding. @Fork runs each trial in a fresh JVM so profiles from other benchmarks cannot pollute this one, and JMH generates a real method-call loop rather than relying on OSR.

The remaining gap to 40 ns usually has a cause no microbenchmark can reproduce: in real code the call site is megamorphic, the data is not in L1, and the branch predictor has other work competing for it. That is the honest limit of microbenchmarking — it measures a method in isolation, and isolation is the one condition production never provides.

🎯 Key Takeaways

  • javac optimises almost nothing on purpose — the JIT has runtime information no static compiler can have.
  • Heap, metaspace and the code cache are shared; stacks, PC and native stacks are per-thread — which is why a local variable can never be raced on.
  • "unable to create native thread" is not a heap problem, and raising -Xmx makes it worse.
  • Class loading is lazy, so a missing dependency can surface hours into a run on a rarely executed path.
  • Preparation sets statics to defaults; initialization runs your code — that gap is why a method called from an early initializer reads zeros.
  • A static final primitive or String constant is inlined by javac, so callers keep stale values until they are recompiled.
  • Parent delegation exists so a fake java.lang.String is never consulted, and so one type has one Class object across loaders.
  • Servlet containers and OSGi invert delegation deliberately so two modules can use different versions of one library.
  • Class identity is fully-qualified name + defining loader — that is how X cannot be cast to X happens.
  • ClassNotFoundException is a lookup failure; NoClassDefFoundError usually means a static initializer threw.
  • A failed <clinit> marks the class erroneous for the life of the JVM — the real cause is logged once and never again.
  • <clinit> holds a per-class lock, so mutually initializing classes deadlock across threads and hang at 0% CPU, invisible to the deadlock detector.
  • Tiering runs 0 → 3 → 4, and tier 3 is deliberately slower because it is collecting the profile C2 needs.
  • OSR compiles a running loop mid-frame and is usually worse than a normal compilation — which is why hand-rolled benchmarks lie.
  • Inlining is the enabling optimisation: keep hot methods small, and expect a megamorphic call site to stop inlining altogether.
  • Deoptimization is the price of speculation — loading a subclass can slow down code that never mentions it.
  • Metaspace is native and unbounded by default; set -XX:MaxMetaspaceSize so a loader leak fails with a stack trace instead of exit 137.
