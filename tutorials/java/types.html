Syntax, Types & Variables Foundations

What you'll master: the single distinction that explains a dozen later gotchas — a primitive variable holds the value, a reference variable holds a pointer — and how it answers "why did modifying b change a?", "why does == fail on Strings?" and the interview question people get wrong more than any other; why Integer a = 1000, b = 1000; a == b is false while the same code with 100 is true, and why relying on that is a bug that appears only for large values; why integer overflow is silent — MAX_VALUE + 1 wraps to a large negative with no exception, which has taken down real systems; why unboxing a null wrapper throws a NullPointerException on a line with no visible method call; and the precise, provable reason Java is pass-by-value even though methods can clearly mutate your objects. Prerequisites: How Java Runs.

Part 1 — Java Is Statically Typed

Every variable has a type known at compile time, and the compiler enforces it. You cannot put a String into an int, and you are told the moment you try — before the program runs, rather than at 3am in production.

int count = 42;          // count is forever an int
count = "hello";         // ❌ COMPILE ERROR: incompatible types
String name = "Ada";
name = 42;               // ❌ COMPILE ERROR
🔑 The trade, stated honestly: static typing costs verbosity and buys a whole class of bugs caught for free, plus tooling that actually works — autocomplete and safe refactoring are possible because the IDE knows every type. Java bets that on a large, long-lived codebase this is overwhelmingly worth it. var later removes most of the verbosity without giving up any of the checking.

Part 2 — Primitives vs References: the Central Distinction

int x = 42;              // PRIMITIVE — the variable HOLDS 42
int y = x;               // copies the VALUE; independent from now on
y = 99;                  // x is still 42

int[] a = {1, 2, 3};     // REFERENCE — 'a' holds a pointer to a heap object
int[] b = a;             // copies the POINTER; both point at ONE array
b[0] = 99;               // a[0] is now 99 as well
  PICTURE IT PHYSICALLY

  PRIMITIVE:   x [ 42 ]      y [ 42 ]       two independent boxes

  REFERENCE:   a [ ---+                     +---------------+
                      +-------------------> | [99, 2, 3]    |   ONE array,
               b [ ---+                     +---------------+   two pointers

  A primitive variable is a labelled box with the number written inside.
  A reference variable is a labelled box with an ADDRESS written inside;
  the object itself lives on the heap, and any number of boxes can hold
  the same address.
Primitives (8, lowercase)References (everything else)
What the variable holdsThe value itselfA pointer to an object
Assignment and parameter passing copyThe value — an independent copyThe pointer — a shared object
Can be null?NoYes
Where the data livesTypically the stack, or inline in an objectThe object is on the heap, managed by GC
Equality with ==Compares values — what you wantCompares identity — almost never what you want
Examplesint, double, boolean, charString, arrays, every object, the wrapper classes
🔑 Internalise this and half of Java's "surprises" evaporate. "Why did modifying b change a?" — one object, two pointers. "Why does == fail on Strings?" — it compares pointers, not contents. "Is Java pass-by-reference?" — no, but the pointer's value is what gets copied. Every one of those is this part restated.

Part 4 — Casting and Numeric Promotion

  WIDENING IS IMPLICIT — no information can be lost

    byte -> short -> int -> long -> float -> double
                    char -> int

    int  i = 42;
    long l = i;        // fine, silent

  NARROWING IS EXPLICIT — you are asserting the loss is acceptable

    long l = 3_000_000_000L;
    int  i = (int) l;          // -1294967296. The cast SILENCES the
                               // compiler; it does not make it safe.

    double d = 9.99;
    int    n = (int) d;        // 9 — truncates toward zero, never rounds

  THE CAST IS A PROMISE YOU ARE MAKING, and Java takes you at your word.
  That is why (int) on a value that does not fit produces garbage rather
  than an exception: you told it to.
  NUMERIC PROMOTION — the rule behind several "impossible" errors

  In any binary numeric operation, both operands are promoted:
    if either is double -> double
    else if either is float -> float
    else if either is long -> long
    ELSE BOTH BECOME int          <-- the surprising one

  So arithmetic on small types produces an int:

    byte a = 10, b = 20;
    byte c = a + b;        // ❌ COMPILE ERROR: possible lossy conversion
                           //    from int to byte
    byte c = (byte)(a + b);   // ✓ explicit

  This baffles people because 30 obviously fits in a byte. The rule is
  about TYPES, not values — a + b is typed int before anything is
  evaluated.

  THE SAME RULE MAKES char ARITHMETIC WORK:

    char letter = 'A';
    int  code   = letter + 1;      // 66 — promoted to int
    char next   = (char)(letter + 1);   // 'B' — cast back

  AND IT EXPLAINS INTEGER DIVISION:

    int  half = 1 / 2;             // 0   — both int, so int division
    double h  = 1 / 2;             // 0.0 — the division happened FIRST
    double ok = 1.0 / 2;           // 0.5 — one operand is double

  The second line is the classic: widening the target does nothing,
  because the right-hand side is fully evaluated first. It is the same
  mistake as `long t = a * b` in Exercise 3, one type family over.

Reach for the cast when you know; reach for the exact method when you are hoping.

Part 5 — Wrappers and Autoboxing

Every primitive has a wrapper class — int→Integer, double→Double, boolean→Boolean. You need them because generics and collections hold objects only: List<int> is illegal, and it must be List<Integer>.

Integer boxed = 42;      // AUTOBOXING:   int -> Integer, implicitly
int prim = boxed;        // AUTO-UNBOXING: Integer -> int, implicitly

List<Integer> nums = new ArrayList<>();
nums.add(5);             // the int 5 is boxed on the way in
  TRAP 1 — == COMPARES REFERENCES

    Integer a = 1000, b = 1000;
    a == b        // FALSE — two distinct objects
    a.equals(b)   // true  — compares the value

    Integer c = 100, d = 100;
    c == d        // TRUE?! — the Integer CACHE

  Autoboxing routes through Integer.valueOf(), which caches instances
  for -128..127 and returns the SAME object for values in that range.
  Outside it, each boxing creates a new object.

  WHY THIS IS WORSE THAN A CURIOSITY: the same line of code is correct
  for small values and wrong for large ones. Code tested with 5 items
  passes; production with 500 does not, and the diff shows nothing.

  TRAP 2 — UNBOXING NULL THROWS

    Integer maybe = null;
    int val = maybe;       // NullPointerException

  The NPE lands on a line with no visible method call, which is what
  makes it confusing. There IS a call — the compiler inserted
  maybe.intValue().

  The same thing bites in arithmetic and in conditions:
    if (flags.get("on")) { … }    // Boolean from a map, null -> NPE
    int total = a + b;            // either Integer null -> NPE
SituationUseWhy

That asymmetry catches people: a field silently defaults to null and blows up later, while a local with the same mistake is a compile error. It is also why new String[3] hands you an array of nulls rather than empty strings.

var is not dynamic typing. var name = "Ada" makes name a String permanently — the compiler merely saved you writing the type. You cannot later assign an int to it. It is inference, not any.

Part 7 — Is Java Pass-by-Value or Pass-by-Reference?

The most misunderstood question in the language, and getting it exactly right is a genuine signal. Java is always pass-by-value. The work is in knowing what "value" means for each family.

// PRIMITIVE — the value copied is the number
void tryToChange(int n) { n = 99; }
int x = 5;
tryToChange(x);        // x is still 5

// REFERENCE — the value copied is the POINTER
void mutate(int[] arr)   { arr[0] = 99; }            // follows the pointer
void reassign(int[] arr) { arr = new int[]{7}; }     // repoints a LOCAL copy

int[] a = {1, 2, 3};
mutate(a);             // a[0] is now 99   — the shared object changed
reassign(a);           // a is UNCHANGED   — only the local copy moved
  THE RESOLUTION, AND THE PROOF

  A method receives a COPY of the pointer. Through that copy it can
  reach the same object the caller sees, so mutation is visible. But
  reassigning the parameter only changes the method's own copy — the
  caller's variable still points at the original.

  "Java can change what your object contains, but it cannot make your
   variable point somewhere else."

  THE PROOF IS reassign(). If Java were pass-by-reference, the caller's
  `a` would become {7} after that call. It does not. In C++ a
  reference parameter (int*&) genuinely can repoint the caller's
  variable; Java has no equivalent, and that is the precise,
  demonstrable difference.

  THE SAME FACT, WEARING A DISGUISE:

    void f(StringBuilder sb) { sb.append("x"); }   // caller SEES it
    void g(String s)         { s += "x"; }         // caller sees NOTHING

  Both are pass-by-value of a reference. The difference is mutability:
  StringBuilder is mutable, so append changes the shared object. String
  is immutable, so s += "x" compiles to s = s.concat("x") — a NEW
  object, assigned to the local copy of the pointer.

Interview Questions

Beginner: What is the difference between a primitive and a reference type?

A primitive variable holds the actual value — the number 42 itself. There are exactly eight, they can never be null, and assigning one copies the value, so the two variables are independent from then on.

A reference variable holds a pointer to an object that lives on the heap. It can be null, and assigning one copies the pointer, so both variables now refer to the same object.

The practical upshot is the part worth stating: mutating an object through one reference is visible through every reference to it, whereas primitives are always independent copies. That single fact is behind the shared-mutation surprises, the == confusion, and the pass-by-value question.

Beginner: Why is Integer a=1000, b=1000; a==b false, but true with 100?

== on objects compares identity, not value. Autoboxing goes through Integer.valueOf(), which keeps a cache of instances for −128 to 127 and returns the same object for values in that range. So at 100 both variables point at one cached object and == is true; at 1000 each boxing allocates a new object and it is false.

The lesson is not "remember the cache range". It is that == on wrappers is wrong even when it appears to work — the code is correct for small values and broken for large ones, so it passes a test with five items and fails in production with five hundred, with nothing in the diff to explain it.

Always .equals(), or Objects.equals() if either side might be null.

Mid: Is Java pass-by-value or pass-by-reference? Prove it.

Always pass-by-value. The subtlety is what gets copied.

For a primitive, the copied value is the number, so a method cannot affect the caller's variable at all. For an object, the copied value is the reference — the method gets its own pointer to the same object. So it can mutate that object, and the caller sees the change; but it cannot make the caller's variable point somewhere else.

The proof is a pair of methods. One that does list.add(x) affects the caller, because it mutated the shared object. One that does list = new ArrayList<>() does not, because it only reassigned its local copy of the pointer. If Java were pass-by-reference, the second would change the caller's variable too.

The reason the confusion is so persistent is that pass-by-value of a reference looks exactly like pass-by-reference as long as you only mutate. The difference only shows up on reassignment, which is why that is the experiment to run.

Mid: When would you choose Integer over int, and what does it cost?

Two legitimate reasons. Nullability, when the value genuinely may be absent — a database column, an optional API field — and 0 would be a wrong sentinel that quietly becomes real data. And generics, because collections hold objects, so List<Integer> is the only option.

The costs are real. Memory: an object header plus the value, rather than four bytes, and an array of a million Integers is dramatically larger than an int[]. A NullPointerException risk on every implicit unboxing, on lines that contain no visible method call. The == identity trap. And boxing overhead in hot loops, where an object is allocated per iteration.

So the default is the primitive, and the wrapper is what you reach for when nullability or generics demand it. In numeric stream code, IntStream over Stream<Integer> is the same decision.

Senior: Explain integer overflow, and how you would guard a counting or monetary calculation.

Java's integer types are fixed-width two's complement, and arithmetic is defined to wrap on overflow rather than to fail. Integer.MAX_VALUE + 1 is Integer.MIN_VALUE — no exception, no flag, nothing in the logs.

What makes it dangerous is that the failure is silent and the value is plausible-looking garbage, usually negative. Real incidents follow a pattern: a counter that grows past 2.1 billion, a duration in milliseconds that wraps after about 25 days, or a size computed as count * bytesPerItem that overflows before it is ever used as a length.

The guards, in the order I would reach for them. Use a wider type — long for anything that could plausibly grow, and note that the fix must be applied to the operands, not just the result: long total = a * b still overflows if a and b are int, because the multiplication happens in int before the widening. Use Math.addExact and multiplyExact, which throw ArithmeticException, converting silent corruption into a loud failure. BigInteger when there is no sensible bound.

For money, none of that applies, because the right answer is not to use binary floating point at all. double cannot represent 0.10 exactly, so sums accumulate error and never reconcile. Use BigDecimal with an explicit scale and rounding mode — constructed from a String, never from a double, or you have already lost the precision — or store integer minor units and format at the edges.

The instinct underneath all of it is to distrust silent numeric limits, and to choose types and operations that make overflow either impossible or loud.

Senior: A method appends to a StringBuilder and the caller sees it; another does s += "x" on a String and the caller sees nothing. Reconcile that with pass-by-value.

Both are pass-by-value of a reference. The difference is mutability, not passing semantics — and that is the whole point of the question.

StringBuilder is mutable. append modifies the object that the copied pointer refers to, and since the caller's pointer refers to the same object, the caller observes the change.

String is immutable. s += "x" compiles to something equivalent to s = s.concat("x") — it creates a new String and assigns it to the method's local copy of the pointer. The caller's pointer still refers to the original, unchanged object, so the caller sees nothing.

This is the cleanest illustration that "can the caller see my change?" depends on whether you mutated the shared object or reassigned your local reference. It never depends on pass-by-reference, which Java does not have.

It also explains why immutability is such a powerful design property: an immutable object can be passed anywhere, shared between threads, and used as a map key without any risk that a callee changes it underneath you. That is the argument the Immutability lesson develops.

🏋️ Graded Exercises

1 (easy): Predict the output, then explain each line. 
int[] a = {1, 2, 3};
int[] b = a;
b[0] = 99;
System.out.println(a[0]);

int x = 5;
int y = x;
y = 99;
System.out.println(x);
Solution 
99      // a and b point at the SAME array object
5       // x and y are independent copies of a value

Line by line: int[] b = a copies the pointer, so there is still exactly one array and two variables referring to it. b[0] = 99 follows the pointer and modifies that one array, which a also sees.

int y = x copies the value. There are two independent 32-bit boxes from that moment on, and assigning to y cannot reach x.

The test to apply to any Java assignment: is the type primitive or reference? That one question predicts the behaviour every time, and it is the same question behind the pass-by-value answer in Part 7.

If you wanted b to be independent, you must copy the array explicitly — int[] b = a.clone() or Arrays.copyOf(a, a.length). Note that for an array of objects even that is a shallow copy: you get a new array, but the elements are still the same shared objects.

2 (easy): Why does this throw, and on which line? 
Map<String, Integer> counts = new HashMap<>();
counts.put("a", 1);
int total = counts.get("a") + counts.get("b");
Solution

Line 3, with a NullPointerException. counts.get("b") returns null because the key is absent, and the + operator forces unboxing, so the compiler inserted a call to intValue() on null.

What makes this hard to read is that the line contains no visible method call on the null value. The stack trace points at an arithmetic expression, which is why people look for the bug in the wrong place.

FixWhen it is right
counts.getOrDefault("b", 0)Absent genuinely means zero — usually the case for counters
An explicit null checkAbsent means something different from zero and needs handling
Optional at the boundaryThe absence is meaningful and should propagate

The general shape: any implicit unboxing is a hidden method call, so any wrapper that might be null is a hidden NPE. Map lookups are the most common source, because get returning null for a missing key is the API's normal behaviour rather than an error.

Worth knowing the same trap in a condition: if (flags.get("enabled")) throws rather than being false when the key is missing — which is why a Map<String, Boolean> used for feature flags is a recurring source of production NPEs.

3 (medium): This computes a buffer size and gets a negative number. Find the bug. 
int itemCount = 3_000_000;
int bytesPerItem = 1_000;
long totalBytes = itemCount * bytesPerItem;
System.out.println(totalBytes);   // -1294967296
Solution

The multiplication happens in int, before the widening to long. Both operands are int, so Java performs 32-bit multiplication, overflows, and then widens the already-wrong result.

3_000_000 * 1_000 = 3_000_000_000   which exceeds Integer.MAX_VALUE
                                     (2_147_483_647), so it wraps

// FIX — widen an operand so the multiplication itself is 64-bit:
long totalBytes = (long) itemCount * bytesPerItem;

// or make the field a long in the first place:
long itemCount = 3_000_000;

The declared type of the target does nothing, and that is the whole trap. People add long on the left, see the type change, and assume the arithmetic followed — but Java evaluates the right-hand side entirely before assigning.

The safest habit is to widen the first operand, since the promotion then applies to the whole expression: (long) a * b * c is safe, while a * b * (long) c has already overflowed by the time the cast matters.

Where I would rather catch this is with Math.multiplyExact(itemCount, bytesPerItem), which throws instead of wrapping. A negative buffer size eventually surfaces as a confusing NegativeArraySizeException or a wrong allocation far from here; an ArithmeticException names the actual line.

4 (medium): A price total is drifting by a cent. Diagnose and fix. 
double total = 0;
for (int i = 0; i < 10; i++) total += 0.10;
System.out.println(total);            // 0.9999999999999999
System.out.println(total == 1.0);     // false
Solution

0.10 has no exact representation in binary floating point, in the same way that ⅓ has no exact decimal representation. Each addition stores the nearest representable double, and the tiny errors accumulate.

This is not a Java flaw — it is IEEE 754, and every language using binary floating point behaves the same way. What makes it a Java problem is that double is the default for decimal literals, so it is what you get unless you think about it.

// FIX A — BigDecimal, constructed from Strings
BigDecimal total = BigDecimal.ZERO;
for (int i = 0; i < 10; i++) total = total.add(new BigDecimal("0.10"));
total.compareTo(new BigDecimal("1.00"));   // 0 — equal

// FIX B — integer minor units; format only at the edges
long totalCents = 0;
for (int i = 0; i < 10; i++) totalCents += 10;
DetailWhy it matters
new BigDecimal("0.10"), never new BigDecimal(0.10)The double constructor captures the imprecision you were trying to escape — it produces 0.1000000000000000055511151231257827…
compareTo, not equalsequals compares scale too, so 2.0 and 2.00 are not equal — a genuinely surprising API
An explicit rounding mode on divisionNon-terminating division throws ArithmeticException without one

Which fix to choose: integer minor units are faster and simpler when every amount uses one currency with a fixed exponent. BigDecimal is right when you need varying scales, currencies with different minor units, or arithmetic where rounding policy is a business rule you must state explicitly.

And never compare floating-point values with == generally — for genuinely approximate quantities, compare within an epsilon.

5 (hard): Write a method that demonstrates Java is pass-by-value, using an object parameter, and explain why the demonstration is conclusive.
Solution 
static void mutate(List<String> list)   { list.add("added"); }
static void reassign(List<String> list) { list = new ArrayList<>(); }

public static void main(String[] args) {
    List<String> names = new ArrayList<>(List.of("a"));

    mutate(names);
    System.out.println(names);    // [a, added]   caller SEES it

    reassign(names);
    System.out.println(names);    // [a, added]   caller sees NOTHING
}

Why reassign is the conclusive half. mutate proves nothing on its own — it is exactly what both pass-by-value-of-a-reference and true pass-by-reference would do. The distinguishing experiment is reassignment.

Under true pass-by-reference the parameter would be an alias for the caller's variable, so assigning a new list to it would change what names refers to, and the second print would show []. It shows the unchanged list, so the parameter cannot be an alias — it must be a copy of the pointer.

LanguageCan a method repoint the caller's variable?
JavaNo — always a copy of the value, including when the value is a reference
C++ with T&Yes — the parameter is an alias for the caller's variable
C with T**Yes, but only because you passed a pointer to the variable — which is Java's model with an extra level

The framing I would give in an interview: "Java passes references by value." That single sentence contains both halves — you get the reference, and you get a copy of it — and it predicts both behaviours without any special cases.

If someone insists Java is pass-by-reference for objects, the productive move is not to argue about terminology but to run reassign. The disagreement is almost always about what "value" means, and the experiment settles it without either party conceding a definition.

6 (hard): A service stores per-user counts in a Map<String, Integer> and increments them under load. Identify every type-related hazard. 
Map<String, Integer> hits = new HashMap<>();

void record(String user) {
    hits.put(user, hits.get(user) + 1);
}
Solution
HazardWhat happens
NPE on the first callhits.get(user) is null for a new user, and + 1 unboxes it
Boxing per incrementEvery put allocates a new Integer above 127 — an object per event, purely for GC to collect
Not thread-safeGet-then-put is not atomic, so concurrent increments lose updates. HashMap itself can also corrupt under concurrent writes
Silent overflowA hot key passing 2.1 billion wraps to negative, with no error
== waiting to happenAny later hits.get(a) == hits.get(b) compares identity and is correct only below 128
// Single-threaded, minimal fix:
hits.merge(user, 1, Integer::sum);

// Concurrent, and the one I would ship:
ConcurrentHashMap<String, LongAdder> hits = new ConcurrentHashMap<>();

void record(String user) {
    hits.computeIfAbsent(user, k -> new LongAdder()).increment();
}

Why LongAdder rather than AtomicLong: under contention it spreads updates across internal cells instead of having every thread compare-and-swap the same memory, which is dramatically faster for a counter that is written far more often than it is read. Reading it is slightly more expensive, which is exactly the right trade for metrics.

Why long rather than int: the whole point of a hit counter is that it grows without bound, so int's 2.1 billion ceiling is a real deadline rather than a theoretical one.

The wider lesson: this is four separate hazards in two lines, and each traces to a different part of this lesson — null unboxing, boxing cost, fixed-width overflow, and reference identity. A Map<String, Integer> used as a counter is one of the most common shapes in Java code and one of the most reliably buggy.

🎯 Key Takeaways

  • A primitive variable holds the value; a reference variable holds a pointer. Half of Java's surprises are that sentence restated.
  • Assignment copies what the variable holds — the number, or the pointer. It never copies the object.
  • The eight primitives cannot be null; every reference type can.
  • int and double are the defaults — but never double for money.
  • Integer overflow is silent and wraps to a large negative; use long or Math.addExact.
  • Widen the operands, not the target. long t = a * b still overflows if both are int.
  • Autoboxing routes through a cache for −128…127, which makes == on wrappers right for small values and wrong for large ones.
  • Unboxing a null wrapper throws on a line with no visible call — map lookups are the usual source.
  • Prefer primitives unless you need nullability or generics; boxing in a hot loop allocates per iteration.
  • Locals must be definitely assigned; fields default silently to 0, false or null.
  • var is inference, not dynamic typing — the type is fixed and enforced forever.
  • Java is always pass-by-value; for objects the value copied is the reference.
  • A method can change what your object contains, but cannot repoint your variable — and reassignment is the experiment that proves it.
  • "Can the caller see it?" depends on mutability, not on passing semantics — StringBuilder versus String is the clean demonstration.
  • char is one UTF-16 code unit, not one character — an emoji is two.
