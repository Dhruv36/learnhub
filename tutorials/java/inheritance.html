Inheritance & Polymorphism OOP

What you'll master: dynamic dispatch as the mechanism that makes polymorphism work — one call site, the implementation chosen from the object rather than the variable, and why fields are not polymorphic, so a field with the same name in a subclass hides rather than overrides and which one you get depends on the declared type; the substitutability rule that decides whether inheritance is appropriate at all, and why Stack extends Vector in the JDK lets you insert into the middle of a stack — the standard cautionary tale, shipped in the standard library; why a subclass that overrides add and addAll can double-count, because whether addAll calls add is an undocumented implementation detail that can change between versions; the constructor chain and what super() actually does; and the honest comparison with composition, which is the default a modern codebase should reach for. Prerequisites: Classes & Encapsulation and Methods for overriding versus overloading.

Part 1 — extends and the "is-a" Test

class Animal {
    protected final String name;
    Animal(String name) { this.name = name; }
    void speak() { System.out.println("..."); }
}

class Dog extends Animal {
    Dog(String name) { super(name); }            // must call up
    @Override void speak() { System.out.println("Woof"); }
    void fetch() { … }                            // Dog-only
}

  Dog INHERITS every non-private member of Animal, may OVERRIDE the
  methods, and may ADD its own. Java has SINGLE inheritance of classes —
  one superclass — though a class may implement many interfaces.
  THE TEST IS NOT "SHARES CODE". IT IS SUBSTITUTABILITY.

  Every place that accepts an Animal must work correctly when handed a
  Dog — without knowing it is a Dog, and without any caller changing.

  Ask three questions before writing `extends`:

  1. Is a B genuinely an A, in every context A is used?
  2. Does B accept everything A accepts? (You cannot narrow inputs.)
  3. Does B promise everything A promises? (You cannot weaken
     guarantees.)

  A "no" to any of them means inheritance is the wrong tool, however
  convenient the code reuse.

  THE CLASSIC FAILURE — Square extends Rectangle

    class Rectangle { void setWidth(int w); void setHeight(int h); }
    class Square extends Rectangle { … }   // must keep w == h

    void stretch(Rectangle r) {
        r.setWidth(10);
        r.setHeight(5);
        assert r.area() == 50;      // fails for a Square
    }

  Square IS-A Rectangle in geometry and is NOT one here, because
  Rectangle's contract includes "width and height vary
  independently". Square cannot honour that, so it breaks callers that
  were written against Rectangle. The relationship in the domain does
  not settle the relationship in the code — the CONTRACT does.

Part 2 — super and the Constructor Chain

class Base    { Base()    { print("Base"); } }
class Middle  extends Base   { Middle()  { print("Middle"); } }
class Derived extends Middle { Derived() { print("Derived"); } }

new Derived();      // prints: Base, Middle, Derived

  CONSTRUCTION RUNS TOP-DOWN. Every constructor implicitly calls
  super() as its first statement unless you write this(…) or an
  explicit super(…).

  WHY TOP-DOWN: a subclass may depend on superclass state in its own
  constructor, so the superclass must be fully built first. The
  consequence is the trap from the previous lesson — the superclass
  constructor runs BEFORE the subclass's field initialisers, so an
  overridable method called from it sees uninitialised subclass
  fields.

  super HAS TWO USES:

    super(args)         call the superclass constructor — first
                        statement only
    super.method()      call the superclass's version of a method,
                        from an override

  super.method() is the standard way to EXTEND rather than replace
  behaviour:

    @Override void save() {
        validate();
        super.save();          // do what the parent did
        audit();
    }

  It is also the only way to reach a method you have overridden — and
  it works one level only. There is no super.super.

Part 3 — Dynamic Dispatch, and What Is Not Polymorphic

Animal a = new Dog("Rex");
a.speak();          // "Woof" — chosen from the OBJECT, not the variable

  THE MECHANISM: each class has a table of method implementations, and
  each object carries a pointer to its class. An interface or virtual
  call looks up the actual implementation through that pointer at
  invocation time. The compiler emits "call speak() on whatever this
  is"; the JVM resolves which one.

  This is what makes one call site serve every subtype, and it is the
  entire engine of polymorphism:

    for (Animal animal : animals) animal.speak();
      // adding a new Animal subclass requires NO change here

  THREE THINGS ARE NOT POLYMORPHIC, and each surprises people:

  1. FIELDS ARE NOT. They are resolved from the DECLARED type.

       class Animal { String type = "animal"; }
       class Dog extends Animal { String type = "dog"; }

       Animal a = new Dog();
       a.type          -> "animal"     !!
       ((Dog) a).type  -> "dog"

     The subclass field HIDES the superclass one; both exist in the
     object simultaneously. This is why fields should be private —
     hiding is almost never intended, and it produces two fields with
     one name.

  2. STATIC METHODS ARE NOT. They are also resolved from the declared
     type, so a "static override" is really static HIDING.

  3. PRIVATE METHODS ARE NOT. They are not inherited, so a subclass
     method with the same name is a new, unrelated method.

Part 4 — abstract Classes

abstract class Shape {
    abstract double area();                    // no body — subclasses
                                               // MUST implement

    void describe() {                          // shared concrete code
        System.out.printf("%s with area %.2f%n",
                          getClass().getSimpleName(), area());
    }
}

class Circle extends Shape {
    private final double r;
    Circle(double r) { this.r = r; }
    @Override double area() { return Math.PI * r * r; }
}

  Shape s = new Shape();     // ❌ cannot instantiate an abstract class

  An abstract class exists to be extended. It can hold state, define
  constructors, and mix abstract methods with concrete ones — which is
  exactly what distinguishes it from an interface.

🔑 Since default methods arrived, "can it have a body?" stopped being the distinction — state is. An interface cannot hold instance fields, so if your subtypes need to share data rather than just behaviour, an abstract class is the tool. The modern default is to define the type as an interface and, if several implementations genuinely share state, add an abstract base class implementing it — which keeps callers depending on the interface while still allowing reuse. That is the shape the JDK itself uses: List and AbstractList.

Part 5 — Casting, instanceof and final

Animal a = new Dog("Rex");

if (a instanceof Dog d) {        // pattern matching, Java 16+
    d.fetch();                   // no separate cast needed
}

Dog d2 = (Dog) a;                // unchecked cast: ClassCastException
                                 // at runtime if `a` is not a Dog

  UPCASTING (Dog -> Animal) is implicit and always safe.
  DOWNCASTING (Animal -> Dog) is explicit and checked at runtime.

  A CHAIN OF instanceof IS USUALLY A DESIGN SMELL:

    if      (s instanceof Circle c)    { … }
    else if (s instanceof Square sq)   { … }
    else if (s instanceof Triangle t)  { … }

  That is dynamic dispatch, hand-written. Adding a shape means editing
  every such chain, and missing one is a silent bug. A method on the
  type does it for free — that is what polymorphism is for.

  THE EXCEPTION: with SEALED types the chain is exhaustive and the
  compiler enforces it, which makes a switch over a closed hierarchy a
  legitimate alternative (see Pattern Matching).
  final HAS THREE MEANINGS, and they are unrelated

    final class      cannot be extended       (String, Integer)
    final method     cannot be overridden
    final field      cannot be REASSIGNED — not "immutable"

  final on a field of mutable type is the one people misread:

    private final List<String> items = new ArrayList<>();
    items.add("x");        // ✓ legal — the reference never changed
    items = new ArrayList<>();   // ❌ this is what final forbids

  DESIGN FOR INHERITANCE OR FORBID IT. A class that is neither
  documented for extension nor final is a class whose subclasses will
  break in ways you did not anticipate — because overriding one method
  can change how another behaves, and only the author knows which
  methods call which.

Part 6 — Composition Over Inheritance

  THE CAUTIONARY TALE IS IN THE STANDARD LIBRARY

    java.util.Stack extends Vector

  Vector is a random-access list. So every Stack inherits its entire
  API:

    Stack<String> s = new Stack<>();
    s.push("a"); s.push("b");
    s.add(0, "sneaky");        // INSERT AT THE BOTTOM of the stack
    s.remove(1);               // remove from the middle
    s.get(0);                  // read without popping

  A stack is defined by last-in-first-out access. This one cannot
  enforce it, because inheritance exposed operations that contradict
  the abstraction — and they can never be removed without breaking
  compatibility.

  THE FIX IS COMPOSITION:

    class Stack<E> {
        private final List<E> items = new ArrayList<>();   // HAS-A
        void push(E e) { items.add(e); }
        E pop() { … }
        // and NOTHING else is exposed
    }

  The list is an implementation detail. The class exposes exactly the
  operations that make sense, and it can swap ArrayList for an array
  later without any caller noticing.
  THE FRAGILE BASE CLASS PROBLEM — subtler, and worse

    class CountingSet<E> extends HashSet<E> {
        private int added = 0;

        @Override public boolean add(E e) {
            added++;
            return super.add(e);
        }
        @Override public boolean addAll(Collection<? extends E> c) {
            added += c.size();
            return super.addAll(c);
        }
        public int added() { return added; }
    }

    var s = new CountingSet<String>();
    s.addAll(List.of("a", "b", "c"));
    s.added();          // 6, not 3

  HashSet.addAll is implemented by calling add() for each element. So
  addAll counts three, then each add counts one more.

  THE REAL PROBLEM IS NOT THE DOUBLE COUNT. It is that the correct
  implementation depends on an UNDOCUMENTED INTERNAL DETAIL of the
  superclass — whether addAll delegates to add. That is not part of
  HashSet's contract, so it can change in any JDK release, and your
  subclass breaks without your code changing.

  Composition has no such coupling: you call the methods you chose to
  call, and a library update cannot silently redirect them.

Interview Questions

Beginner: What is polymorphism, and what makes it work?

Polymorphism is one call site behaving differently depending on the actual object. With Animal a = new Dog(), calling a.speak() runs Dog's version even though the variable is declared as Animal.

The mechanism is dynamic dispatch. Each class has a table of its method implementations, and every object carries a pointer to its class. The compiler emits "invoke speak() on this reference" and the JVM follows the object's class pointer at call time to find the right implementation.

Why it matters practically is that it removes conditionals. A loop calling speak() on every Animal needs no change when a new subclass appears — whereas the instanceof-chain equivalent must be edited everywhere, and missing one place is a silent bug.

The thing to be precise about is that this applies to instance methods only. Fields, static methods and private methods are all resolved from the declared type, not the object.

Beginner: What is the difference between an abstract class and an interface?

Since Java 8 gave interfaces default methods, "can it have a body?" is no longer the distinction. State is.

An abstract class can hold instance fields and define constructors; an interface cannot — its only fields are implicit public static final constants. So if the subtypes need to share data as well as behaviour, an abstract class is the tool.

The other structural difference is that a class has exactly one superclass but can implement many interfaces, which makes interfaces the right way to express capabilities that cut across a hierarchy.

The modern default is to declare the type as an interface, so callers depend on the contract, and add an abstract base class implementing it if several implementations genuinely share state. That is what the JDK does with List and AbstractList, and it keeps the freedom to implement the interface without inheriting the base.

Mid: Why is Stack extends Vector considered a design mistake?

Because inheritance exposes the superclass's entire public API, and Vector's API contradicts what a stack is.

A stack is defined by last-in-first-out access. Since Stack inherits from a random-access list, callers can do stack.add(0, x) to insert at the bottom, remove(3) to pull from the middle, or get(0) to read without popping. The class cannot enforce its own defining invariant.

And it is permanent. Those methods are part of Stack's public API now, so they can never be removed without breaking compatibility — which is why the JDK's own documentation steers people to Deque instead.

The fix is composition: hold a List in a private field and expose only push, pop and peek. The list becomes an implementation detail that can be swapped later, and no caller can reach past the abstraction.

The general lesson is that inheritance is a promise about substitutability, not a code-reuse mechanism. Asking "do I want everything the superclass exposes?" catches most of these before they are written — and the answer for Vector is plainly no.

Mid: What is the fragile base class problem?

It is when a subclass's correctness depends on how the superclass is implemented internally, so a change to the superclass — one that keeps its documented contract — silently breaks the subclass.

The canonical example is a HashSet subclass that counts additions by overriding both add and addAll. Adding three elements through addAll reports six, because HashSet.addAll happens to be implemented by calling add for each element, and both overrides count.

The double count is easy to fix once you know. The real problem is that you have to know — whether addAll delegates to add is not part of HashSet's documented contract. It is an implementation detail that can change in any JDK release, and when it does, your subclass breaks without a single line of your code changing.

That is the deep argument for composition. A wrapper holding a Set calls exactly the methods it chose to call, so no internal restructuring of the delegate can redirect them.

The other conclusion is for anyone writing a base class: if it is meant to be extended, its self-calls are part of its contract and must be documented — which is why @implSpec exists in the JDK's own docs. A class that is neither documented for extension nor final is a hazard, because only the author knows which methods call which.

Senior: Explain the substitutability rule and how it constrains overriding.

The rule — the Liskov substitution principle in practice — is that code written against a supertype must keep working when handed any subtype, without knowing which one it has.

Java enforces part of this at compile time, and the constraints all follow from that single requirement.

Parameters cannot be narrowed. If the supertype accepts any Object, the subtype must too — accepting only String would reject calls the supertype promised to handle. Attempting it produces an overload, not an override, which is precisely why @Override catches it.

Return types may be narrowed — covariant returns are safe, because anything expecting the supertype's return still gets something usable.

Access cannot be reduced, since a caller reaching the method through the supertype must still reach it.

Checked exceptions cannot be broadened, because a caller's catch blocks were written against the supertype's declaration.

What the compiler cannot check is the semantic half, which is where the real failures live. Square extends Rectangle satisfies every syntactic rule and still breaks a method that sets width and height independently — because Rectangle's contract includes that they vary independently, and Square cannot honour it. The domain relationship does not settle the code relationship; the contract does.

The practical version I use when reviewing an extends: can I hand this subtype to every existing caller of the supertype and be confident nothing changes? If I have to say "well, except when…", it is composition.

Senior: When would you actually choose inheritance today?

Rarely, and the cases are specific enough to name.

When the base class is designed for extension and says so. A framework's AbstractHandler with documented extension points and documented self-calls is inheritance used correctly — the contract includes how it may be extended.

A small closed hierarchy sharing state, especially with sealed, where I control every subclass and they change together. Sealed types make the set finite, which removes the fragile-base-class risk because I can see and update every subclass in one commit.

Template Method, where the base defines an algorithm's skeleton and subclasses fill in steps — and the steps are abstract or final, never both overridable and self-called.

Everywhere else I would compose. The default should be to declare an interface for the type and, if implementations share state, to provide an abstract base that implements the interface — callers depend on the interface, so nobody is forced into the hierarchy.

The two questions that decide it: do I want the entire public API of the supertype? and do I control the superclass? A no to either points at composition. The extra delegation methods are a real cost, and they are cheaper than the coupling — and modern Java softens even that, since records and interfaces with default methods cover many cases that once needed a base class.

Worth adding that inheritance and code reuse have largely been decoupled. Default methods reuse behaviour without a superclass, records remove the data-carrier case, and composition covers the rest — so "I want to reuse this code" is no longer a reason to reach for extends.

🏋️ Graded Exercises

1 (easy): What does this print, and why? 
class Animal { void speak() { print("animal"); } }
class Dog extends Animal { @Override void speak() { print("dog"); } }

Animal a = new Dog();
a.speak();
Solution

dog. Instance method calls are dispatched from the object, not the declared type of the variable. The compiler checks that Animal has a speak() and emits a virtual call; the JVM follows the object's class pointer at runtime and finds Dog's implementation.

The contrast worth holding onto is with overloading, which resolves from the declared type at compile time. The same variable behaves oppositely in the two cases:

a.speak();          // "dog"     — OVERRIDING follows the object
feed(a);            // "animal"  — OVERLOADING follows the declaration
                    //             (given feed(Animal) and feed(Dog))

This is what makes polymorphism useful: a loop over List<Animal> calling speak() works for every subclass that exists now and every one added later, without touching the loop.

The exceptions to remember: fields, static methods and private methods are all resolved from the declared type. Only instance methods dispatch dynamically.

2 (easy): Why does the second line print "animal"? 
class Animal { String type = "animal"; }
class Dog extends Animal { String type = "dog"; }

Animal a = new Dog();
System.out.println(a.type);
System.out.println(((Dog) a).type);
Solution 
a.type          -> "animal"
((Dog) a).type  -> "dog"

Fields are not polymorphic. They are resolved at compile time from the declared type of the expression, so a.type reads Animal's field and the cast version reads Dog's.

Both fields exist in the same object simultaneously. Dog does not override type — it hides it. The Dog instance carries two separate String fields with the same name, and which one you get depends on how you look at it.

MemberResolved fromSubclass version
Instance methodThe object, at runtimeOverrides
FieldThe declared type, at compile timeHides
static methodThe declared type, at compile timeHides
private methodNot inherited at allUnrelated new method

The practical rule is that this is why fields should be private. Hiding is almost never intentional, and it produces exactly this: a value that changes depending on the static type of the reference you happen to be holding. With private fields and a type() accessor, the accessor dispatches dynamically and the surprise disappears.

3 (medium): Why does this print 6, and what does that reveal? 
class CountingSet<E> extends HashSet<E> {
    private int added = 0;
    @Override public boolean add(E e) { added++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        added += c.size();
        return super.addAll(c);
    }
    int added() { return added; }
}

var s = new CountingSet<String>();
s.addAll(List.of("a", "b", "c"));
System.out.println(s.added());
Solution 
  addAll adds 3                        added = 3
  super.addAll(c) is HashSet's, which
    calls add(e) for EACH element      added = 6

  And the calls to add() dispatch DYNAMICALLY, so they reach the
  OVERRIDE, not HashSet's version.

The double count is the symptom. The disease is the dependency. To write this class correctly you must know whether HashSet.addAll delegates to add — and that is not in HashSet's documented contract. It is an implementation detail.

Which means a future JDK could reimplement addAll to insert directly, and this class would start reporting 3 instead of 6, with no change to your code. Either number is "correct" depending on an internal detail you were never told about.

"Fix"Why it is not one
Remove the addAll overrideCorrect today, and silently wrong the moment the delegation changes
Override addAll to loop and call addReimplements the superclass's method from guesswork about its behaviour
CompositionThe actual fix — no inheritance, no self-call coupling
class CountingSet<E> {
    private final Set<E> delegate = new HashSet<>();
    private int added = 0;

    public boolean add(E e)  { added++; return delegate.add(e); }
    public boolean addAll(Collection<? extends E> c) {
        int before = delegate.size();
        boolean changed = delegate.addAll(c);
        added += delegate.size() - before;     // count what ACTUALLY
        return changed;                        // went in
    }
    public int added() { return added; }
}

Note the composed version also fixes a bug the original had: a set ignores duplicates, so adding ["a","a","b"] should count 2, not 3. Counting the size delta measures what happened rather than what was requested — which the inheritance version could not do without knowing the delegate's internals either.

If you must subclass a class you do not own, the base class has to document its self-calls — which is what @implSpec is for in the JDK. Absent that documentation, subclassing is a guess about internals.

4 (medium): Why does Square extends Rectangle break, when a square genuinely is a rectangle?
Solution 
class Rectangle {
    void setWidth(int w);
    void setHeight(int h);
    int area();
}
class Square extends Rectangle { … }    // must keep width == height

void stretch(Rectangle r) {
    r.setWidth(10);
    r.setHeight(5);
    assert r.area() == 50;      // FAILS when r is a Square
}

The mathematics is not the point; the contract is. Rectangle's API promises that width and height can be set independently. Square cannot honour that — it must keep them equal — so it either breaks the invariant or breaks the caller's expectation.

Neither escape works. If setWidth also changes the height, stretch gets an area of 25 and its assertion fails. If setWidth throws, stretch fails differently. If it silently ignores the call, worse. The subtype cannot satisfy the supertype's promises, and callers of the supertype were written against those promises.

DesignVerdict
Square extends Rectangle, both mutableBroken — substitutability fails
Both immutable, with withWidth returning a new instanceWorks — there is no independent-mutation promise to break
Shape interface with area(), implemented separatelyWorks — they share a capability, not an implementation

The immutable row is the interesting one, because it shows the problem was never the geometry. Mutability introduced a promise ("these vary independently") that the subtype could not keep. Remove the setters and the relationship becomes sound.

The general test: can this subtype be handed to every existing caller of the supertype with nothing changing? Real-world taxonomy is a poor guide — the useful question is about the contract the code makes.

5 (hard): Redesign Stack extends Vector and explain what composition buys.
Solution 
  THE PROBLEM WITH THE JDK's VERSION

    Stack<String> s = new Stack<>();
    s.push("a"); s.push("b");
    s.add(0, "sneaky");     // insert at the BOTTOM of a stack
    s.remove(1);            // remove from the middle
    s.get(0);               // read without popping
    s.set(0, "x");          // overwrite in place

  Every one of those is legal, because Stack inherited Vector's whole
  random-access API. The class cannot enforce LIFO — the property that
  defines it.
public final class Stack<E> {
    private final Deque<E> items = new ArrayDeque<>();

    public void push(E e) { items.addFirst(e); }

    public E pop() {
        if (items.isEmpty()) throw new NoSuchElementException("empty stack");
        return items.removeFirst();
    }

    public E peek() {
        if (items.isEmpty()) throw new NoSuchElementException("empty stack");
        return items.peekFirst();
    }

    public boolean isEmpty() { return items.isEmpty(); }
    public int size()        { return items.size(); }
}
What composition buysConcretely
The invariant is enforceableThere is no API through which to reach the middle, so LIFO holds by construction
The representation is free to changeArrayDeque could become an array or a linked structure; no caller can tell
No inherited surprisesNothing arrives from a superclass you did not choose — and nothing new arrives when the JDK adds a method to Vector
Exactly the intended surfaceFive methods, all of which make sense for a stack

The cost is delegation — size() and isEmpty() are one-line forwards. That is the honest trade, and it is small next to permanently exposing operations that contradict the abstraction.

final on the class is deliberate. Having just argued that inheriting from something not designed for it is hazardous, leaving this open would invite the same mistake one level down.

The JDK cannot fix its own Stack, because those methods are public API and removing them breaks compatibility. That permanence is the real lesson: an inheritance relationship published in an API is essentially irreversible, which is why the documentation now steers people to Deque instead.

6 (hard): A colleague proposes class AuditedRepository extends JpaRepository to add audit logging. Evaluate it.
Solution

I would push back, and the reasoning is the fragile base class problem rather than taste.

ConcernWhy it applies here
Undocumented self-callsDoes saveAll call save per entity? Does save call persist or merge? If audit logic sits on both, entries are duplicated — and the answer is an implementation detail that varies by version
You do not own the baseA Spring Data upgrade can change delegation internally without breaking its own contract, and the subclass breaks silently
ProxiesSpring Data repositories are generated proxies. Extending the interface and expecting overrides to be invoked does not work the way inheritance suggests
You inherit the whole APIEvery method on JpaRepository becomes part of your audited repository, including ones that bypass auditing entirely
Cross-cutting concernAuditing is not a specialisation of "being a repository". It applies across many repositories, which is a strong signal it does not belong in the hierarchy
// COMPOSITION — a decorator, exposing exactly the audited operations
class AuditedOrderRepository {
    private final OrderRepository delegate;
    private final AuditLog audit;

    Order save(Order order) {
        Order saved = delegate.save(order);
        audit.record("order.saved", saved.id());
        return saved;
    }
}

What the decorator fixes: the delegate's internal restructuring cannot redirect your calls, the exposed surface is only the operations you audited, and there is no path that quietly bypasses the logging.

The better answer for this specific concern is probably neither. Auditing is cross-cutting, so the idiomatic solutions are JPA entity lifecycle callbacks (@PrePersist, @PreUpdate), Spring Data JPA auditing with @CreatedBy and @LastModifiedDate, or a domain event published on save. Each puts the concern where it belongs and covers every path, including the ones a wrapper would miss — such as a JPQL bulk update, or a cascade from another entity.

The question I would ask to settle it: must auditing happen when the entity is saved by a cascade, a bulk update, or another repository? If yes, no wrapper or subclass can guarantee it, and the answer has to be at the persistence layer.

🎯 Key Takeaways

  • Inheritance is a promise about substitutability, not a code-reuse mechanism.
  • The test is whether every caller of the supertype still works when handed the subtype, unchanged.
  • Dynamic dispatch selects the implementation from the object via its class pointer, which is the engine of polymorphism.
  • Fields are not polymorphic — they hide rather than override, and both exist in the object at once.
  • Static and private methods are not polymorphic either; only instance methods dispatch.
  • Constructors run top-down, so the superclass is fully built before the subclass initialises its fields.
  • Stack extends Vector permits inserting into the middle of a stack — the cautionary tale, shipped in the standard library and now unfixable.
  • The fragile base class problem is the deeper one: correctness depending on undocumented self-calls that can change in any release.
  • Composition has no self-call coupling — you call what you chose to call.
  • Parameters cannot be narrowed on an override; return types can, and access cannot be reduced — all from substitutability.
  • An instanceof chain is hand-written dispatch, except over a sealed hierarchy where the compiler checks exhaustiveness.
  • final means unassignable, not immutable — a final List is still mutable.
  • Design for inheritance and document the self-calls, or make the class final — anything else is a hazard for whoever extends it.
  • Prefer an interface for the type and an abstract base only for shared state, which is what List and AbstractList do.
  • Inheritance and reuse have been decoupled — default methods, records and composition cover what extends used to be reached for.
