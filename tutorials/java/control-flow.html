Control Flow & Loops Foundations

What you'll master: branching and looping written to be correct the first time — why a brace-less if disabled TLS certificate validation across Apple's entire platform in 2014, and why the fix costs two characters; the arrow switch, which removes the single most common switch bug by making fall-through impossible rather than merely discouraged, and which the compiler can check for exhaustiveness; the four loop forms and why for-each should be your default — it cannot be off by one, because there is no index to get wrong; why removing from a collection while iterating it throws ConcurrentModificationException even in a single thread, and the two correct ways to do it; the off-by-one error decomposed into the three questions that produce it; and how to write a loop whose termination you can actually argue for, since an infinite loop in production presents as 100% CPU on one core with no error at all. Prerequisites: Operators & Expressions.

Part 1 — Branching with if / else

int score = 82;
char grade;

if (score >= 90) {
    grade = 'A';
} else if (score >= 80) {        // checked ONLY if the first was false
    grade = 'B';
} else {
    grade = 'C';
}
  ALWAYS USE BRACES. THIS IS NOT A STYLE PREFERENCE.

  In February 2014 Apple shipped a TLS bug across iOS and macOS that
  disabled certificate validation entirely. The cause, reduced:

      if (somethingFailed)
          goto fail;
          goto fail;        <-- duplicated line, NOT in the if

  The second `goto fail` was outside the condition because there were no
  braces, so it ran unconditionally — jumping to a cleanup label that
  returned SUCCESS. Every certificate validated. The vulnerability was
  exploitable by anyone on the network.

  Braces cost two characters and make this class of bug impossible.
  The style argument is settled by the failure mode.

  WHAT JAVA PROTECTS YOU FROM, that C does not:

      if (x = 5) { … }      // ❌ COMPILE ERROR in Java

  In C this assigns 5 and tests it as truthy — the classic typo. Java's
  `if` requires a boolean, so the assignment version only compiles when
  x is itself boolean, which narrows the trap to one rare case:

      boolean done = false;
      if (done = true) { … }   // compiles! assigns, always true

Part 2 — The Modern switch

// THE CLASSIC FORM — fall-through is the default behaviour
switch (day) {
    case "SAT":
    case "SUN":
        type = "weekend";
        break;              // omit this and execution FALLS INTO default
    default:
        type = "weekday";
}

// THE ARROW FORM (Java 14+) — no fall-through, and it is an EXPRESSION
String type = switch (day) {
    case "SAT", "SUN" -> "weekend";     // multiple labels, comma-separated
    default           -> "weekday";
};                                       // semicolon: it produces a value

// Multi-statement arms use a block and `yield`
int len = switch (size) {
    case "S" -> 1;
    case "M" -> 2;
    case "L" -> { log.debug("large"); yield 3; }
    default  -> 0;
};
Classic case:Arrow ->
Fall-throughDefault behaviour — a missing break is a silent bugImpossible — each arm is independent
Produces a valueNo — assign inside each armYes — assign the whole expression
Exhaustiveness checkingNoYes, for enums and sealed types — a new constant becomes a compile error
Variable scopeShared across all arms, which permits genuinely confusing codePer arm
Use it whenMaintaining legacy code, or deliberately sharing behaviour between labelsEverywhere else
🔑 The exhaustiveness check is the underrated half. A switch expression over an enum with no default must cover every constant, so adding a constant later turns every incomplete switch into a build failure. That converts "find all the places that handle OrderStatus" from a grep into something the compiler guarantees — which is why the arrow form matters most in exactly the code that changes most. Add a default and you throw that away, so omit it deliberately when switching over a closed set.

Part 3 — The Four Loops

// 1. FOR — when you need the index, or a non-trivial step
for (int i = 0; i < 5; i++) { … }        // init; condition; step

// 2. FOR-EACH — iterate anything Iterable or an array. YOUR DEFAULT.
for (String name : names) { … }          // no index to get wrong

// 3. WHILE — when the count is unknown up front
while (scanner.hasNextLine()) { … }

// 4. DO-WHILE — when the body must run at least once
do { choice = prompt(); } while (!valid(choice));
FormReach for it whenCannot
for-eachYou need every element, in order — the overwhelming majority of loopsGive you the index, iterate backwards, or remove elements
forYou need the index, a step other than 1, or to iterate in reverseProtect you from off-by-one — three chances to get it wrong

  WHY FOR-EACH IS THE DEFAULT: IT CANNOT BE OFF BY ONE.

    for (int i = 0; i <= names.size(); i++)     // ❌ IndexOutOfBounds
    for (int i = 1; i < names.size(); i++)      // ❌ skips element 0
    for (int i = 0; i < names.size() - 1; i++)  // ❌ skips the last

  Three plausible-looking loops, three different bugs. The for-each
  version has no index, so none of them is expressible:

    for (String name : names) { … }

  It also works on anything Iterable, so the same loop reads a List, a
  Set, a Map's entrySet, or your own class — while an index-based loop
  only works on arrays and Lists.
  THE MODIFICATION TRAP — AND IT IS NOT ABOUT THREADS

    for (String s : list) {
        if (s.isBlank()) list.remove(s);      // ConcurrentModification
    }                                          // Exception, single thread

  The name is misleading. The iterator keeps a modCount snapshot and
  checks it on every next(); any structural change through the
  collection itself invalidates it. "Concurrent" here means "during
  iteration", not "from another thread".

  AND THE VERSION THAT IS WORSE — it does not throw:

    for (String s : list) {
        if (s.isBlank()) list.remove(s);
    }
    // With exactly TWO elements where the FIRST matches, removal
    // shifts the second into index 0, the cursor advances to 1, size
    // is now 1, so hasNext() is false. The loop exits having silently
    // SKIPPED an element. No exception.

  THE TWO CORRECT WAYS:

    list.removeIf(String::isBlank);            // ✓ clearest

    Iterator<String> it = list.iterator();     // ✓ when you need more
    while (it.hasNext()) {                     //   control
        if (it.next().isBlank()) it.remove();  //   remove via the ITERATOR
    }

Part 4 — break, continue and Labels

for (String row : rows) {
    if (row.isBlank()) continue;      // skip this iteration
    if (row.equals("END")) break;     // leave the loop entirely
    process(row);
}

// LABELS — for breaking out of NESTED loops
outer:
for (int i = 0; i < grid.length; i++) {
    for (int j = 0; j < grid[i].length; j++) {
        if (grid[i][j] == target) {
            found = true;
            break outer;              // leaves BOTH loops
        }
    }
}
// Without the label, `break` exits only the inner loop, and the outer
// one continues — a classic "why does it keep searching?" bug.
⚠️ A label is the honest option; a flag variable is usually worse. The common alternative — boolean found checked in both loop conditions — spreads the exit condition across three places and is easy to get subtly wrong. Labels have a bad reputation by association with goto, but a labelled break can only jump forwards, out of an enclosing construct; it cannot create arbitrary control flow. The better refactor when the nesting gets deep is to extract the search into a method and return — one exit, no label, and the intent is in the method name.

Part 5 — The Off-by-One Error, Decomposed

  IT IS ALWAYS ONE OF THREE QUESTIONS:

  1. Does the range START at 0 or 1?
  2. Is the END inclusive or exclusive?
  3. Is the LENGTH the last index, or one past it?

  Java's answer is consistent, and knowing it removes most of the risk:

    indices are ZERO-BASED               first element is [0]
    ranges are HALF-OPEN                 [start, end) — end excluded
    length is ONE PAST the last index    last element is [length - 1]

  So the canonical loop is:

    for (int i = 0; i < n; i++)          // ✓ i < n, never i <= n

  AND THE STANDARD LIBRARY FOLLOWS THE SAME CONVENTION:

    "hello".substring(1, 3)     -> "el"    3 is EXCLUSIVE
    list.subList(0, 2)          -> first two elements
    Arrays.copyOfRange(a, 0, 2) -> first two elements

  Half-open ranges are not arbitrary: the length is end - start, an
  empty range is [n, n), and adjacent ranges [0,k) and [k,n) tile the
  whole thing with no overlap and no gap. Every off-by-one you avoid
  comes from that arithmetic working out.
LoopBugSymptom

i < n - 1Skips the last elementSilent — a total that is short by one item
i = 1Skips the first elementSilent — and often looks like a data problem

Part 6 — Loops That Terminate

  AN INFINITE LOOP IN PRODUCTION HAS NO ERROR MESSAGE.

  It presents as one core pinned at 100%, a request that never returns,
  and a thread dump where the same stack frame appears every time you
  sample it. Nothing is thrown, nothing is logged, and the health check
  may well keep passing because the other threads are fine.

  THE FOUR WAYS THEY HAPPEN:

  1. THE VARIABLE IS NEVER UPDATED
       while (i < 10) { sum += i; }        // forgot i++

  2. THE UPDATE CANNOT REACH THE BOUND
       for (double d = 0.1; d != 1.0; d += 0.1)   // never EQUALS 1.0
     Floating point again: 0.1 cannot be represented exactly, so the
     accumulated value steps straight past 1.0. Use < with doubles,
     or better, count with an int.

  3. THE BOUND IS MOVED BY THE BODY
       for (int i = 0; i < list.size(); i++) {
           if (shouldDuplicate(list.get(i))) list.add(list.get(i));
       }
     size() grows every iteration, so the condition is never false.

  4. THE EXIT DEPENDS ON SOMETHING THAT NEVER CHANGES
       while (!queue.isEmpty()) { peek(); }    // never removes

  THE DISCIPLINE THAT PREVENTS ALL FOUR: for every loop, be able to
  state what decreases towards the bound on each iteration. If you
  cannot name it, the loop may not terminate.

  AND FOR DELIBERATE INFINITE LOOPS — a server accept loop, a consumer
  poll — make the exit explicit and bounded:

    while (running) { … }                  // a volatile flag someone
                                           // can actually set
    while (!Thread.currentThread().isInterrupted()) { … }   // ✓ better
                                           // cooperates with shutdown

Interview Questions

Beginner: What is fall-through in a switch, and how does the arrow form change it?

In the classic case: form, execution continues into the following case unless you write break. So a missing break runs two branches' worth of code, silently.

It is occasionally useful — stacking labels so several values share one body — but it is the default rather than opt-in, which means the common case requires remembering ceremony and the rare case gets it for free. That is the wrong way round, and it is the single most common switch bug.

The arrow form makes each arm independent, so fall-through is not expressible. It also produces a value, so you can assign the whole switch rather than assigning inside every arm — and it supports multiple labels with commas, which covers the legitimate use of stacking.

The part I would add is exhaustiveness: a switch expression over an enum with no default must handle every constant, so adding a constant later becomes a compile error at every incomplete site. That turns a grep into a guarantee.

Beginner: When would you use a for loop rather than for-each?

When you need the index itself, a step other than one, or to iterate in reverse. Removing elements while iterating is another case, though there the iterator or removeIf is usually better.

Otherwise for-each should be the default, and the reason is not brevity — it is that for-each cannot be off by one. There is no index expression, so i <= size(), i = 1 and i < size() - 1 are all inexpressible.

It also generalises: the same loop reads a List, a Set, a Map's entry set, or any class implementing Iterable, whereas an index-based loop only works on arrays and random-access lists — and on a LinkedList, indexing turns an O(n) traversal into O(n²).

Mid: Why does removing from a list inside a for-each throw ConcurrentModificationException in a single thread?

Because "concurrent" here means "during iteration", not "from another thread". The name is misleading and the question is really about fail-fast iterators.

The collection keeps a modCount that increments on every structural change. When you create an iterator it records that value, and every call to next() compares the two. If they differ, the iterator knows the collection changed underneath it and throws immediately rather than returning results that may be wrong.

That is a deliberate design choice: fail loudly at the point of the mistake instead of silently returning a corrupted traversal. It is best-effort rather than guaranteed, which is why the documentation says you must not rely on it for correctness.

The case worth knowing is the one where it does not throw. With exactly two elements where the first matches, removing it shifts the second down to index 0 while the cursor advances to 1 — and since the size is now 1, hasNext() returns false. The loop exits normally having skipped an element, with no exception at all. So the exception is not a reliable detector; the pattern is simply wrong.

The fixes are removeIf, which is clearest and is a single pass, or an explicit Iterator with it.remove(), which updates the modCount the iterator is tracking and so stays valid.

Mid: Why are Java's ranges half-open, and how does that prevent off-by-one errors?

Indices are zero-based, ranges exclude their end, and length is one past the last index. So the canonical loop is for (int i = 0; i < n; i++), and "hello".substring(1, 3) returns two characters.

The convention is not arbitrary — the arithmetic works out in three useful ways. The size of a range is simply end - start, with no adjustment. An empty range is expressible as [n, n) without a special case. And adjacent ranges [0, k) and [k, n) tile the whole sequence with no overlap and no gap, so splitting is exact.

Compare inclusive ranges, where the length is end - start + 1, an empty range needs end < start, and splitting requires deciding which half owns the boundary. Each of those adjustments is a place to be off by one.

So the practical discipline is to write i < n and never i <= n - 1, and to trust that every standard-library method takes the same convention. The errors that remain are the silent ones — i < n - 1 skipping the last element — which is why for-each is preferable wherever it applies.

Senior: How do you write a loop whose termination you can argue for, and how would you debug an infinite loop in production?

The discipline is to be able to name, for every loop, what decreases towards the bound on each iteration. In a counted loop it is the gap between the index and the limit; in a queue drain it is the queue's size; in a retry loop it is the remaining attempts. If I cannot state it, I do not yet know that the loop terminates.

That single question catches all four common causes: a variable that is never updated, an update that cannot reach the bound (comparing doubles with !=), a bound the body moves (adding to the collection being iterated), and an exit condition nothing changes.

Debugging one in production starts from the symptom, which is distinctive: one core pinned at 100%, a request that never completes, nothing thrown and nothing logged. Health checks often stay green because the other threads are healthy, so it can run for a long time.

The diagnosis is a thread dump — jstack, or three of them a few seconds apart. A thread stuck in a loop shows the same stack frame every time, and comparing dumps distinguishes "stuck" from "slow": slow code moves through frames, a spin does not. top -H to find the hot thread id, converted to hex, matches it to the dump.

For loops that are deliberately unbounded — a server accept loop, a consumer poll — I would make the exit explicit and cooperative: while (!Thread.currentThread().isInterrupted()) rather than while (true). That participates in shutdown properly, so the thread ends when the executor is stopped instead of keeping the JVM alive. A volatile boolean running is the alternative and is weaker, because it does not wake a thread that is blocked in a call.

The other guard worth having is a bound on anything driven by external input: a retry loop with a maximum attempt count, a parser with a maximum length. An unbounded loop over untrusted input is a denial-of-service vector, not just a bug.

Senior: When is a labelled break the right tool, and what is the better alternative?

It is the right tool when you must leave more than one enclosing loop at once — typically a search over a two-dimensional structure, where finding the target means you are done with both loops. A plain break exits only the innermost, and the outer loop carries on, which is a genuinely common bug.

The usual alternative — a boolean found flag tested in both loop conditions — is worse in my view. It spreads one exit condition across three locations, it still executes the remainder of the current inner iteration, and it is easy to get subtly wrong when the loops are edited later.

Labels carry a bad reputation by association with goto, and it is worth being precise about why that association is unfair: a labelled break can only jump forwards, out of a construct that encloses it. It cannot jump backwards, into a block, or between methods, so it cannot produce the arbitrary control flow that made goto notorious.

The better refactor, when it applies, is extraction. Move the nested search into its own method and return the result. Now there is one exit, no label, and the intent is documented by the method's name — findPosition(grid, target) reads better than any loop with a label on it. It is also individually testable.

So my order of preference is: extract to a method and return; a labelled break if extraction would be artificial; a flag only if neither is available. And if the nesting is three deep or more, the nesting itself is the thing to fix.

🏋️ Graded Exercises

1 (easy): Write FizzBuzz for 1–100 — "Fizz" for multiples of 3, "Buzz" for 5, "FizzBuzz" for both.
Solution 
for (int i = 1; i <= 100; i++) {
    if      (i % 15 == 0) System.out.println("FizzBuzz");
    else if (i % 3  == 0) System.out.println("Fizz");
    else if (i % 5  == 0) System.out.println("Buzz");
    else                  System.out.println(i);
}

The order is the whole exercise. Testing % 15 first is what makes the chain correct — put % 3 first and every multiple of fifteen prints "Fizz" and stops, because else if means the later tests never run.

Why % 15 rather than i % 3 == 0 && i % 5 == 0: both work. The explicit conjunction is arguably clearer about intent, and 15 relies on the reader spotting that it is 3 × 5. I would write the conjunction in real code and accept 15 in an interview where brevity is being watched.

Note i <= 100 is correct here, which looks like it contradicts the half-open rule from Part 5. It does not: this is a range of values from 1 to 100 inclusive, not a range of indices. The half-open convention applies to indexing, and blindly applying < here would stop at 99.

The variant worth knowing is building the string instead of branching, which extends cleanly to a fourth rule:

String out = (i % 3 == 0 ? "Fizz" : "") + (i % 5 == 0 ? "Buzz" : "");
System.out.println(out.isEmpty() ? String.valueOf(i) : out);

    case NEW:      label = "new";      break;
    case PAID:     label = "paid";     break;
    case SHIPPED:
    case DELIVERED: label = "closed";  break;
    default:       label = "unknown";
}
Solution 
String label = switch (status) {
    case NEW               -> "new";
    case PAID              -> "paid";

What changedWhy it matters
No breakFall-through is impossible, so the most common switch bug cannot occur
label is assigned once, as an expressionIt can be final, and there is no path where it is left unassigned

Keep a default when the input is genuinely open — a String or an int from outside your control — because there the unknown case is real and must be handled. For a closed enum, the exhaustiveness check is worth more.

3 (medium): Find the off-by-one bugs. 
int[] scores = {70, 80, 90};

int sum = 0;
for (int i = 1; i <= scores.length; i++) sum += scores[i];

int max = scores[0];
for (int i = 0; i < scores.length - 1; i++)
    if (scores[i] > max) max = scores[i];
Solution
LoopBugHow it presents
Firsti = 1 skips scores[0], and i <= length reads scores[3]ArrayIndexOutOfBoundsException: 3 — loud, so it gets fixed
Secondi < length - 1 never examines the last elementSilent. Returns 80 for this data. Correct-looking output, wrong answer

for (int score : scores) sum += score;         // no index to get wrong

    if (scores[i] > max) max = scores[i];

Note the second loop legitimately starts at 1, because element 0 was used to seed max. That is the case where i = 1 is right — which is exactly why an off-by-one cannot be spotted by pattern-matching the loop header. You have to know what the loop means.

The dangerous one is the silent bug. The first loop throws on the first run and gets fixed in minutes. The second returns a plausible number forever, and would only be caught by a test whose maximum happens to be the last element — which a hand-written fixture usually avoids by accident.

The stream versions remove the class of error entirely:

int sum = IntStream.of(scores).sum();
int max = IntStream.of(scores).max().orElseThrow();
4 (medium): This throws sometimes and silently skips an element other times. Explain both, and fix it. 
List<String> names = new ArrayList<>(List.of("", "bob"));
for (String n : names) {
    if (n.isBlank()) names.remove(n);
}
Solution 
  THE THROWING CASE (three or more elements)

  The iterator recorded modCount at creation and checks it in next().
  remove() incremented it, so the next next() throws
  ConcurrentModificationException — in a single thread. "Concurrent"
  means "during iteration".

  THE SILENT CASE — exactly two elements, first one matching

  index 0 = "", index 1 = "bob", cursor = 0
    next()  -> returns "", cursor = 1
    remove("") -> "bob" shifts to index 0, size becomes 1
    hasNext() -> cursor (1) < size (1)?  FALSE
    loop exits

  "bob" was never visited, and nothing was thrown. The loop reports
  success having processed half the list.
FixWhen to prefer it
names.removeIf(String::isBlank)Almost always. One pass, no iterator to manage, and it reads as the intent
Explicit Iterator + it.remove()When the body does more than test a predicate — logging each removal, or removing based on state accumulated as you go
Collect keepers into a new listWhen the original must not be mutated, or when it is a fixed-size or immutable list
Iterate a copy, remove from the originalWorks, and allocates a second list — acceptable for small collections, wasteful for large

The important lesson is that the exception is not a reliable detector. Because the two-element case passes silently, a test suite can be entirely green while the pattern is wrong. Fail-fast iteration is explicitly documented as best-effort — you cannot write code that depends on the exception being thrown.

And removeIf is not merely nicer syntax — it is implemented on the collection itself, so it manages modCount correctly and can be optimised per implementation. On an ArrayList it compacts in a single pass rather than shifting elements once per removal, which turns an O(n²) loop into O(n).

5 (hard): Search a 2D grid for a target and stop immediately. Show the label version and the version you would actually ship.
Solution 
// WITH A LABEL — correct, and fine
int foundRow = -1, foundCol = -1;
outer:
for (int r = 0; r < grid.length; r++) {
    for (int c = 0; c < grid[r].length; c++) {
        if (grid[r][c] == target) {
            foundRow = r; foundCol = c;
            break outer;                    // leaves BOTH loops
        }
    }
}

// WHAT I WOULD SHIP — extract and return
static Optional<Point> find(int[][] grid, int target) {
    for (int r = 0; r < grid.length; r++)
        for (int c = 0; c < grid[r].length; c++)
            if (grid[r][c] == target) return new Point(r, c);
    return Optional.empty();
}
ApproachVerdict
Labelled breakCorrect. Justified when the surrounding method genuinely needs to continue afterwards
Extract and returnPreferred. One exit, no label, the intent is in the name, and it is independently testable
A boolean found flag in both conditionsWorse than the label: the exit condition is in three places, and the current inner iteration still finishes
Plain breakWrong. Exits the inner loop only; the outer keeps scanning every remaining row

Why extraction wins beyond style: the sentinel values disappear. The label version leaves foundRow = -1 meaning "not found", which every caller must remember to check — a convention enforced by nothing. Returning Optional makes absence part of the type, so the compiler asks the caller to handle it.

Returning from inside nested loops is not a "multiple return" smell. An early return on success is the clearest possible expression of a search, and the alternative — a flag, a label, or a while condition combining both bounds — is strictly harder to verify.

Where the label genuinely earns its place is when the loops are doing work rather than searching, and you must stop early but continue in the same method — draining a queue until a budget is exhausted, for example. Then there is nothing to extract, and the label is the honest tool.

6 (hard): A service pins one CPU core at 100% and stops responding on one endpoint. No exception, no log line, health checks green. Diagnose it.
Solution

The symptom profile names it: an infinite loop. One core saturated rather than all of them, one endpoint affected rather than the whole service, nothing thrown, and health checks passing because the other request threads are unharmed.

  DIAGNOSIS, in order

  1. top -H -p <pid>        find the hot THREAD, note its id
  2. printf '%x\\n' <tid>    convert to hex — jstack uses hex nids
  3. jstack <pid>           find that nid; read the stack

  4. TAKE THREE DUMPS, a few seconds apart. This is the step that
     distinguishes the two possibilities:

       same frame every time      -> spinning. An infinite loop.
       frames moving              -> slow, not stuck. Different problem.

This degrades one endpoint while every automated signal says the service is fine, so it is typically found by a user complaint hours later. The thread also keeps its request's memory reachable, so a sustained loop can end as an OutOfMemoryError whose stack trace points somewhere unrelated.

What I would add after fixing it: a bound on the loop itself, so the failure is loud next time — a maximum iteration count that throws rather than spins. And if the loop is driven by external input, that bound is a correctness requirement rather than a diagnostic aid.

The prevention that generalises: for every loop, be able to name what decreases towards the bound each iteration. All four causes above are cases where nothing does, and the question catches them at review time rather than at 100% CPU.

🎯 Key Takeaways

  • Always use braces. The brace-less if is what disabled TLS validation across Apple's platforms; two characters make it impossible.
  • Prefer the arrow switch — fall-through is inexpressible, it produces a value, and it checks exhaustiveness.
  • Omit default for a closed enum so adding a constant becomes a compile error at every site rather than a silent fallthrough to "unknown".
  • For-each is the default because it cannot be off by one — there is no index to get wrong.
  • Ranges are half-open and indices zero-based, so the loop is i < n; the arithmetic of splitting and empty ranges is why.
  • i <= n throws; i < n - 1 is silent. The silent one is the expensive one.
  • ConcurrentModificationException is about iteration, not threads — a fail-fast modCount check.
  • With two elements it does not throw at all — it silently skips one, so the exception is not a reliable detector.
  • removeIf is the fix, and on an ArrayList it is O(n) rather than the O(n²) of repeated removal.
  • A plain break exits only the innermost loop; a label exits both, and extraction with return is usually better still.
  • A labelled break is not goto — it can only jump forwards out of an enclosing construct.
  • Never compare doubles with != for termination — accumulated 0.1 steps past 1.0 without equalling it.
  • Never move the bound from inside the loop — adding to the collection you iterate never terminates.
  • For every loop, name what decreases towards the bound. If you cannot, it may not terminate.
  • An infinite loop has no error message — one core at 100%, health checks green. Three thread dumps distinguish stuck from slow.
  • Use while (!Thread.currentThread().isInterrupted()) rather than while (true), so the loop participates in shutdown.
