Build Tools & the Ecosystem Professional

What you'll master: what a build tool does beyond compiling, and why dependency resolution is the part that actually matters; Maven's lifecycle/phase/goal model — which explains why mvn install runs your tests whether you wanted it to or not; the scopes, and what each means at packaging time; nearest-wins mediation, which is why the version you get is often not the version anyone requested, and dependency:tree as the tool that proves it; Gradle's implementation versus api and why the distinction determines your consumers' compile classpath; NoSuchMethodError as the signature of a version conflict that compiled cleanly; and why SNAPSHOT versions break reproducibility. Prerequisites: The Module System.

Part 1 — What a Build Tool Is For

  COMPILING IS THE EASY PART. javac does it in one command.

    javac -d target/classes $(find src -name '*.java')

  That stops working the moment you need a library. Then you need to
  find the jar, find the jars IT needs, resolve the version conflicts
  between them, and put the result on the classpath in the right
  order — by hand, correctly, for every developer and every CI run.

  WHAT A BUILD TOOL ACTUALLY PROVIDES:

    DEPENDENCY RESOLUTION   the whole transitive graph, downloaded,
                            versioned and cached. THIS IS THE
                            FEATURE. Everything else is convenience.
    A REPEATABLE LIFECYCLE  compile, test, package, verify, install,
                            deploy — the same on every machine
    TEST EXECUTION          discovery, reporting, failure gating
    PACKAGING               jar/war layout, manifests, shading
    PLUGIN INTEGRATION      annotation processors, code generation,
                            static analysis, coverage, containers
    REPRODUCIBILITY         the same inputs produce the same output,
                            which is what makes CI meaningful

  THE TWO THAT MATTER IN PRACTICE are dependency resolution and
  reproducibility. Everything else you could script; those two you
  could not.

  THE THREE TOOLS YOU WILL MEET:

    MAVEN     declarative XML, convention over configuration,
              overwhelmingly the most common in enterprise Java.
              Predictable, verbose, and hard to make weird.
    GRADLE    a Groovy/Kotlin DSL, incremental builds, a caching
              daemon. Faster and far more flexible — and the
              flexibility is the risk.
    ANT       imperative, no dependency management. Legacy only;
              you will read it, not write it.

  THE HONEST COMPARISON: Maven builds are boring, and that is
  mostly a compliment — any Maven developer can read any Maven POM.
  A Gradle build script is a PROGRAM, so it can do anything,
  including become an unmaintainable one that only its author
  understands.

Part 2 — Maven's Model

  COORDINATES IDENTIFY EVERY ARTIFACT:

    groupId:artifactId:version
    org.springframework:spring-core:6.1.3

  and the POM declares them:

    <dependency>
      <groupId>org.springframework</groupId>
      <artifactId>spring-core</artifactId>
      <version>6.1.3</version>
    </dependency>

  *** THE LIFECYCLE / PHASE / GOAL MODEL ***
  This is the concept that explains most Maven confusion.

    LIFECYCLE   an ordered sequence of phases (default, clean, site)
    PHASE       a named step in that sequence
    GOAL        a plugin's task, BOUND to a phase

  THE DEFAULT LIFECYCLE, IN ORDER:

    validate → compile → test → package → verify → install → deploy

  *** RUNNING A PHASE RUNS EVERY PHASE BEFORE IT. ***

    mvn package     runs validate, compile, test, THEN package
    mvn install     runs all of the above, then installs locally

  So `mvn install` running your tests is not a surprise once you know
  the model — and `-DskipTests` compiles them but does not run them,
  while `-Dmaven.test.skip=true` does not even compile them.

  A GOAL CAN BE RUN DIRECTLY, bypassing the lifecycle:

    mvn compiler:compile          plugin:goal
    mvn dependency:tree           the one you will use most

  SCOPES CONTROL WHERE A DEPENDENCY APPEARS:

    compile   (default) compile + test + runtime, and it is
              TRANSITIVE to your consumers
    provided  compile + test, NOT packaged — the container or
              platform supplies it at runtime (servlet-api,
              lombok)
    runtime   not needed to compile, needed to run (a JDBC driver)
    test      test compile and test run only
    import    only in dependencyManagement, for BOMs

  THE MOST COMMON SCOPE BUG: a library used only in tests declared
  with the default compile scope. It ships to production, enlarges
  the artifact and expands the attack surface — and nothing warns
  you.

  THE OTHER ONE: `provided` for something the runtime does NOT
  actually provide. It compiles perfectly and fails at startup with
  NoClassDefFoundError.

  THE STANDARD LAYOUT IS THE CONVENTION:

    src/main/java        src/test/java
    src/main/resources   src/test/resources
    target/              everything generated

  Deviating from it means configuring every plugin. Almost never
  worth it.
ScopeCompileTestRuntimePackagedExample
compile✓✓✓✓Spring, Jackson
provided✓✓✗✗servlet-api, Lombok
runtime✗✓✓✓JDBC driver, logging binding
test✗✓✗✗JUnit, Mockito
import————A BOM in dependencyManagement

Part 3 — Transitive Dependencies and Mediation

  YOU DECLARE 10 DEPENDENCIES AND GET 150. Each of yours brings its
  own, recursively.

    your-app
      ├── spring-boot-starter-web
      │     ├── spring-web  ──→ spring-core 6.1.3
      │     └── jackson-databind ──→ jackson-core 2.15.3
      └── some-library
            └── spring-core 5.3.20        ← CONFLICT

  *** MAVEN RESOLVES CONFLICTS BY "NEAREST WINS" ***
  NOT by highest version. NOT by newest. By SHORTEST PATH from
  your POM.

    your-app → spring-core 5.3.20        depth 1
    your-app → starter → ... → 6.1.3     depth 3

    → 5.3.20 WINS, even though it is older.

  If two paths are the same depth, the FIRST DECLARED wins — so
  reordering your POM can silently change which version you ship.

  THIS IS THE SINGLE MOST IMPORTANT MAVEN BEHAVIOUR TO INTERNALISE,
  because it means THE VERSION YOU GET IS OFTEN ONE NOBODY ASKED FOR.

  THE DIAGNOSTIC:

    mvn dependency:tree
    mvn dependency:tree -Dincludes=org.springframework:spring-core
    mvn dependency:tree -Dverbose        shows OMITTED versions and
                                         WHY each was omitted

  -Dverbose is the flag that actually answers "where did this
  version come from".

  THE THREE WAYS TO TAKE CONTROL:

  1. dependencyManagement — declare the version once; it applies
     wherever that artifact appears in the tree, at ANY depth. This
     OVERRIDES nearest-wins.

       <dependencyManagement>
         <dependencies>
           <dependency>…spring-core…<version>6.1.3</version></dependency>
         </dependencies>
       </dependencyManagement>

  2. A BOM — a POM that is nothing but dependencyManagement,
     published by a project to keep its own modules consistent:

       <dependency>
         <groupId>org.springframework.boot</groupId>
         <artifactId>spring-boot-dependencies</artifactId>
         <version>3.2.2</version>
         <type>pom</type>
         <scope>import</scope>
       </dependency>

     Then you omit versions entirely for anything the BOM manages,
     and every Spring artifact is guaranteed compatible.

  3. exclusions — remove one branch of the tree:

       <exclusions>
         <exclusion>
           <groupId>commons-logging</groupId>
           <artifactId>commons-logging</artifactId>
         </exclusion>
       </exclusions>

     Use it for a duplicate implementation (two logging bridges,
     two javax.annotation jars), not to "clean up" the tree.

  ENFORCE IT IN CI with the maven-enforcer-plugin's
  dependencyConvergence rule, which FAILS THE BUILD when two paths
  want different versions. That converts a runtime surprise into a
  build error.

Part 4 — Gradle

  A BUILD SCRIPT IS A PROGRAM, in Groovy or Kotlin:

    plugins { id 'java' }

    dependencies {
        implementation 'org.springframework:spring-core:6.1.3'
        api            'com.example:shared-model:1.0'
        compileOnly    'org.projectlombok:lombok:1.18.30'
        runtimeOnly    'org.postgresql:postgresql:42.7.1'
        testImplementation 'org.junit.jupiter:junit-jupiter:5.10.1'
    }

  *** implementation VS api IS THE DISTINCTION THAT MATTERS ***

    implementation   the dependency is on YOUR compile classpath
                     but NOT on your consumers'
    api              it is on both — it leaks into your public
                     contract

  USE api ONLY WHEN THE TYPE APPEARS IN YOUR PUBLIC SIGNATURES:

    public Order findOrder(long id)   ← Order comes from
                                        shared-model → api

    private final ObjectMapper m;     ← internal only →
                                        implementation

  WHY IT MATTERS: with everything as api (Maven's compile scope
  behaviour), any dependency change recompiles every consumer, and
  a consumer can accidentally start using a library you intended to
  swap out. Marking things implementation shrinks compile
  classpaths, speeds up incremental builds substantially on large
  projects, and keeps your dependency choices YOURS.

  TASKS AND THE TASK GRAPH — Gradle is not phase-based:

    ./gradlew build          runs the task and its DEPENDENCIES
    ./gradlew test --tests "OrderServiceTest"
    ./gradlew :api:build     one module

  Tasks declare inputs and outputs, which enables:

    INCREMENTAL BUILDS   a task whose inputs are unchanged is
                         skipped as UP-TO-DATE
    BUILD CACHE          outputs are reused across builds, and
                         across MACHINES with a remote cache — a CI
                         build can reuse what a developer built
    THE DAEMON           a warm JVM between builds, avoiding
                         startup and JIT warmup every time

  On a large multi-module project these are not marginal; a
  no-change build can go from minutes to seconds.

  VERSION CATALOGS centralise versions (the BOM equivalent):

    # gradle/libs.versions.toml
    [versions]
    spring = "6.1.3"
    [libraries]
    spring-core = { module = "org.springframework:spring-core",
                    version.ref = "spring" }

    dependencies { implementation libs.spring.core }

  MAVEN VS GRADLE, HONESTLY:

    Maven     predictable, uniform, any Java developer can read it.
              Slower. Verbose. Hard to express anything unusual —
              which is often a feature.
    Gradle    much faster on large builds, flexible, better
              multi-module support. But a build script is code, so
              it can rot into something only its author understands,
              and upgrades between major versions are real work.

  THE PRACTICAL RULE: a single-module service is fine either way, so
  follow your organisation. A large multi-module build where
  developers wait on compilation is where Gradle's caching earns its
  complexity.

Part 5 — Dependency Hell

  THE DIAMOND:

        your-app
        /      \
    lib-A      lib-B
       \        /
     guava 31 / guava 20

  Only ONE version ends up on the classpath. If lib-A calls a method
  added in 31 and you resolved to 20:

    java.lang.NoSuchMethodError:
      com.google.common.collect.ImmutableList.toImmutableList()

  *** NoSuchMethodError IS THE SIGNATURE OF A VERSION CONFLICT ***
  and its defining property is that IT COMPILED FINE. Compilation
  used one version; the runtime classpath has another. The same
  applies to NoSuchFieldError and some ClassNotFoundExceptions.

  When you see it, go straight to `mvn dependency:tree -Dverbose`
  for the class's artifact. It is almost never a code bug.

  SHADING (Maven Shade / Gradle Shadow) RELOCATES PACKAGES:

    com.google.common.*  →  com.myapp.shaded.com.google.common.*

  Now your Guava and the application's Guava cannot collide. This is
  the standard practice for LIBRARY authors who need a dependency
  their consumers might also use.

  WHAT SHADING COSTS:

    - a much larger artifact, with duplicated code
    - stack traces and debugging with relocated class names
    - security scanners cannot see the shaded versions, so
      vulnerabilities go unreported
    - if the shaded library uses reflection or resource lookups by
      package name, relocation can break it subtly

  So shade a library you PUBLISH; do not shade an application.

  SEMANTIC VERSIONING IS A PROMISE, NOT A GUARANTEE:

    MAJOR.MINOR.PATCH
    1.2.3 → 1.2.4   backward-compatible bug fix
          → 1.3.0   backward-compatible feature
          → 2.0.0   breaking change

  In practice, minor releases break things regularly — behaviour
  changes, added interface methods, tightened validation. Treat
  semver as a hint about INTENT, and let your test suite decide.

  REPRODUCIBILITY, AND WHY SNAPSHOTS BREAK IT:

    1.0.0-SNAPSHOT     re-resolved from the remote repository
                       periodically. "The same build" at two
                       different times can produce DIFFERENT
                       binaries.

  Never depend on a SNAPSHOT in anything you release. For internal
  development it is fine; for a reproducible build it is
  disqualifying. Version ranges ([1.0,2.0)) have the same problem
  and worse — avoid them entirely.

  SUPPLY CHAIN, THE MINIMUM RESPONSIBLE POSITION:

    pin exact versions          no ranges, no SNAPSHOTs in releases
    dependency-check / Snyk     scan for known CVEs, in CI
    an SBOM (CycloneDX)         so you can answer "are we affected?"
                                within minutes of a disclosure
    minimise the tree           every dependency is code you ship
                                and did not review
    a repository manager        Nexus/Artifactory — caching, and a
                                single place to block a bad artifact

  Log4Shell made the SBOM point concrete: the teams who recovered
  quickly were the ones who could answer "where is log4j-core in our
  estate" without a manual audit.

Part 6 — Multi-Module and the Wider Ecosystem

  A MULTI-MODULE BUILD SPLITS ONE PROJECT INTO ENFORCED PIECES:

    parent/pom.xml            packaging: pom
      ├── api/pom.xml
      ├── core/pom.xml        depends on api
      └── web/pom.xml         depends on core

    <modules>
      <module>api</module>
      <module>core</module>
      <module>web</module>
    </modules>

  THE PARENT POM CARRIES SHARED CONFIGURATION — plugin versions,
  compiler settings, and dependencyManagement — so every module
  agrees without repeating itself.

  WHAT THIS BUYS BEYOND ORGANISATION: the dependency direction is
  ENFORCED BY THE COMPILER. `api` cannot use `web`, because it does
  not depend on it. That is the cheapest form of architectural
  boundary available, and it works whether or not you use JPMS.

  BUILD ORDER IS DERIVED FROM THE GRAPH, not from the module
  listing order — and a cycle is a build error, which is exactly
  what you want.

  THE SURROUNDING ECOSYSTEM:

    ARTIFACT REPOSITORIES
      Maven Central       the default public repository
      Nexus/Artifactory   your own — caches Central (so a Central
                          outage does not stop your builds), hosts
                          internal artifacts, and gives you one
                          place to block a compromised version

    CI
      The build must run identically on a clean machine. If it only
      works on your laptop, something is coming from your
      ~/.m2/settings.xml or a locally installed artifact — the most
      common cause of "works for me".

    THE WRAPPER
      mvnw / gradlew commit the BUILD TOOL VERSION to the
      repository. Everyone and every CI agent uses the same one.
      Always use it; a build that depends on the developer's
      installed Maven version is not reproducible.

    RELEASE VERSIONING
      1.0.0-SNAPSHOT during development, 1.0.0 released and
      IMMUTABLE. A released version must never be republished with
      different content — that breaks every cache and every
      reproducible build downstream.

  THE PRACTICES THAT ACTUALLY PREVENT PAIN:

    ✓ commit the wrapper, use it everywhere
    ✓ pin every version; use a BOM for related artifacts
    ✓ run dependency:tree when anything is mysterious
    ✓ fail the build on dependency convergence errors
    ✓ scan for CVEs in CI, and keep an SBOM
    ✗ no SNAPSHOTs in releases, no version ranges
    ✗ no build logic that depends on the local machine

Interview Questions

Beginner: Why do you need a build tool at all?

Because dependency resolution is not something you want to do by hand. Compiling is one javac command; the moment you use a library you must find it, find everything it needs transitively, resolve the version conflicts between those, and reproduce that classpath identically on every machine and every CI run.

The other thing you cannot script cheaply is reproducibility — the same inputs producing the same output, which is what makes a CI result meaningful.

Everything else a build tool does — running tests, packaging, invoking plugins, generating code — you could approximate with scripts. Those two you could not.

A single declaration pulls in the whole graph:

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>
<!-- ~40 jars, versioned consistently, cached locally -->
Beginner: Why does mvn install run the tests?

Because of Maven's lifecycle model: phases run in a fixed order, and invoking a phase runs every phase before it.

validate → compile → test → package → verify → install → deploy

install comes after test, so tests run. Likewise mvn package runs validate, compile and test first.

Understanding this explains most Maven confusion — including why goals can also be invoked directly, bypassing the lifecycle entirely: mvn dependency:tree is plugin:goal and runs nothing else.

Two flags people confuse: -DskipTests compiles the tests but does not run them, while -Dmaven.test.skip=true does not even compile them — which can hide a test that no longer builds.

Mid: How does Maven resolve version conflicts?

Nearest wins — shortest path from your POM. Not the highest version, not the newest.

your-app → spring-core 5.3.20        depth 1  ← WINS
your-app → starter → web → 6.1.3     depth 3

If two paths are the same depth, the first declared wins — which means reordering your POM can silently change the version you ship.

The consequence worth internalising is that the version you get is often one nobody requested. That is exactly how a library compiled against a newer API ends up running against an older one.

ToolUse
dependency:treeSee the resolved graph
-DverboseShow omitted versions and why — the flag that answers the question
dependencyManagementPin a version at any depth, overriding nearest-wins
A BOM (import scope)Pin a whole family consistently
Enforcer dependencyConvergenceFail the build when paths disagree

Gradle differs here: it defaults to highest version wins, which surprises people moving between the two.

Mid: What is the difference between implementation and api in Gradle?

implementation puts the dependency on your compile classpath only. api puts it on your consumers' compile classpath too.

The rule for choosing is precise: use api only when the type appears in your public signatures.

public Order findOrder(long id)   // Order is in my API → api
private final ObjectMapper m;     // internal only → implementation

Why it matters practically: with everything as api — which is Maven's compile scope behaviour — any dependency change recompiles every consumer, incremental builds slow down markedly on large projects, and consumers can start depending on a library you intended to swap out.

Marking things implementation shrinks compile classpaths, keeps your dependency choices yours, and is one of the concrete reasons large Gradle builds are faster than the Maven equivalent.

The corresponding Maven concept is weaker — provided and runtime control packaging rather than the consumer's compile classpath — which is why Maven libraries leak their dependencies by default.

Senior: A service throws NoSuchMethodError in production but compiled fine. Diagnose it.

That combination is the signature of a dependency version conflict, and almost never a code bug. Compilation used one version of a jar; the runtime classpath has a different one that lacks the method.

NoSuchMethodError:
  com.google.common.collect.ImmutableList.toImmutableList()
  1. Identify the artifact owning the class in the message.
  2. mvn dependency:tree -Dverbose -Dincludes=com.google.guava — this shows which versions were requested and which were omitted, with the reason.
  3. Confirm what actually shipped — inspect the deployed artifact or the container's lib directory, since the built classpath and the deployed one can differ.
  4. Pin the version in dependencyManagement, or exclude the offending path.
  5. Verify the consumers still work — pinning to a newer version can break a library that wanted the older one, which is the real risk of the fix.

Why it reached production: nearest-wins picked a version nobody requested, and nothing checks that at build time by default.

The prevention is a CI gate: the enforcer plugin's dependencyConvergence rule fails the build whenever two paths want different versions. That converts a runtime error on a rare code path into a build failure, which is where it belongs.

Related errors with the same root cause: NoSuchFieldError, AbstractMethodError, and ClassNotFoundException for a class that clearly exists in one version of the library.

Senior: How do you keep a build reproducible and its dependencies safe?

Reproducibility first, because it is a precondition for everything else. A build whose output can change without a commit cannot be audited, bisected or trusted.

PracticePrevents
Exact versions — no ranges, no SNAPSHOTs in releasesThe same build producing different binaries at different times
Committed wrapper (mvnw/gradlew)Builds differing by each developer's installed tool version
A BOM or version catalogInconsistent versions across a family of artifacts
Enforcer dependencyConvergenceSilent nearest-wins resolution reaching production
Released versions are immutableRepublishing breaking every downstream cache
A clean-machine CI build"Works for me" from a local settings.xml or installed artifact

Then the supply chain. Every dependency is code you ship and did not review, and the transitive tree means most of it is code you never chose.

  • Scan for CVEs in CI (dependency-check, Snyk) and fail on high severity.
  • Generate an SBOM (CycloneDX). Log4Shell made this concrete: the teams that recovered in hours were the ones who could answer "where is log4j-core in our estate" without a manual audit.
  • Run a repository manager — Nexus or Artifactory caches Central so an outage does not stop your builds, and gives you one place to block a compromised artifact.
  • Minimise the tree. The cheapest security measure is not depending on something.

On upgrades: treat semver as a statement of intent rather than a guarantee — minor releases break behaviour regularly. Upgrade deliberately, one dependency at a time, and let the test suite decide. Automated dependency PRs (Dependabot, Renovate) work well precisely because they upgrade one thing at a time with a green build as the gate.

🏋️ Graded Exercises

1 (easy): Which scope for each, and why? (a) JUnit (b) a PostgreSQL JDBC driver (c) Lombok (d) Jackson used throughout your code
Solution
ScopeWhy
JUnittestNeeded only to compile and run tests; must never ship
PostgreSQL driverruntimeYou code against java.sql; the driver is loaded by name at runtime
LombokprovidedAn annotation processor — needed at compile time, irrelevant at runtime
Jacksoncompile (default)Used in your code and needed at runtime

The driver case is the instructive one. Using runtime scope makes the compiler prevent you from importing a PostgreSQL class by accident — so the database stays swappable. Declaring it compile works but removes that guardrail.

The most common real mistake is a test library left at the default scope. It ships to production, enlarges the artifact and expands the attack surface, and nothing warns you.

The second is provided for something the runtime does not actually provide — it compiles perfectly and fails at startup with NoClassDefFoundError.

2 (easy): Your POM asks for lib-x:2.0. The build uses 1.5. How is that possible and how do you confirm it?
Solution

Nearest wins. Another dependency brings lib-x:1.5 at a shorter path, or at the same depth but declared earlier — so Maven picks it over your explicit 2.0.

mvn dependency:tree -Dverbose -Dincludes=com.example:lib-x

[INFO] +- com.example:lib-x:jar:1.5:compile
[INFO] \- com.example:other:jar:3.0:compile
[INFO]    \- (com.example:lib-x:jar:2.0:compile - omitted for conflict with 1.5)

-Dverbose is the flag that matters — the plain tree shows only what won, not what was omitted or why.

FixEffect
dependencyManagement with 2.0Pins it at any depth, overriding nearest-wins — the standard fix
Exclude lib-x from the 1.5 pathWorks, but breaks if that path genuinely needs 1.5
Enforcer dependencyConvergencePrevents the next occurrence by failing the build

Note Gradle behaves differently — it defaults to highest-version-wins, so the same project would resolve to 2.0. That difference catches people moving between the two tools.

3 (medium): Fix this Gradle block and explain each change. 
dependencies {
    api 'org.springframework:spring-core:6.1.3'
    api 'com.fasterxml.jackson.core:jackson-databind:2.15.3'
    api 'org.projectlombok:lombok:1.18.30'
    api 'org.postgresql:postgresql:42.7.1'
    api 'org.junit.jupiter:junit-jupiter:5.10.1'
}
Solution 
dependencies {
    implementation     'org.springframework:spring-core:6.1.3'
    implementation     'com.fasterxml.jackson.core:jackson-databind:2.15.3'
    compileOnly        'org.projectlombok:lombok:1.18.30'
    annotationProcessor'org.projectlombok:lombok:1.18.30'
    runtimeOnly        'org.postgresql:postgresql:42.7.1'
    testImplementation 'org.junit.jupiter:junit-jupiter:5.10.1'
}
ChangeWhy
Spring, Jackson → implementationInternal use — no need to leak onto consumers' compile classpath
Lombok → compileOnly + annotationProcessorIt generates code at compile time and is not needed at runtime; both lines are required
PostgreSQL → runtimeOnlyLoaded by name; the compiler now stops you importing driver classes
JUnit → testImplementationIt was being shipped to production

The api-everywhere problem is real, not stylistic. Every consumer recompiles when any of these change, incremental builds slow down, and a consumer can start using Jackson through you — so swapping it later becomes a breaking change to your own API.

Keep api only for types in your public signatures — typically a shared model module whose types appear in your method parameters and return values.

The Lombok pair catches people out: compileOnly alone puts the annotations on the classpath but never runs the processor, so nothing is generated and compilation fails on the missing methods.

4 (medium): Two libraries need incompatible Guava versions. Options, with trade-offs.
Solution
OptionTrade-off
Upgrade both libraries to versions agreeing on GuavaCleanest; may not exist, and pulls in other changes
Pin the newer Guava in dependencyManagementUsually works — Guava is fairly backward-compatible — but the older library may call a removed method
Replace one libraryRemoves the conflict permanently; real migration cost
Shade one with a relocated GuavaBoth versions coexist; larger artifact, obscured traces, CVE scanners blind to the shaded copy
Separate class loadersTrue isolation; substantial complexity — an OSGi-shaped answer
Split into separate servicesTotal isolation; a large architectural change

Try pinning first — it is one line, and Guava specifically removes APIs slowly enough that the newer version usually satisfies both. Verify with the older library's test suite if you have one, and by exercising the paths that use it.

If pinning fails, the failure will be a NoSuchMethodError at runtime, so it must be caught by tests rather than by compilation — which is exactly why this is worth checking in CI rather than in production.

Shading is a legitimate answer but belongs to library authors. Shading inside your own application means your security scanner cannot see the relocated Guava, so a future CVE in it goes unreported — a real cost that outlives the conflict you were solving.

5 (hard): "It works on my machine, but CI fails with a compile error about a missing class." Diagnose.
Solution

Something on your machine is not in the repository. Your local build is resolving something CI cannot.

CauseCheck
A locally installed artifact (mvn install from another project)Delete it from ~/.m2/repository and rebuild locally

A SNAPSHOT resolved at different timesDifferent content locally versus on CI — the classic symptom
Uncommitted filesgit status; a fresh clone in a temp directory

Different build tool versionAre you using the wrapper on both?
Case-sensitive filesystemWindows/macOS are case-insensitive; Linux CI is not — a mis-cased import fails only on CI

The definitive test costs two minutes: clone fresh into a temp directory, run with an empty local repository, and see whether it builds.

git clone <repo> /tmp/verify && cd /tmp/verify
./mvnw -Dmaven.repo.local=/tmp/m2 clean verify

That reproduces CI's conditions exactly and tells you immediately whether the problem is your machine or the pipeline.

The case-sensitivity row surprises people and is worth remembering: a file named UserService.java imported as userservice compiles on a Mac and fails on Linux CI, with an error that looks nothing like a filesystem problem.

The prevention is structural: commit the wrapper, pin the JDK version in the build (toolchains or a CI image), never depend on SNAPSHOTs, and keep every repository your build needs in the committed configuration rather than in a personal settings.xml.

The architectural point is that module dependencies are compiler-enforced. common-model cannot use orders, because it does not depend on it — and a cycle is a build error. That is the cheapest architectural boundary available, and it works whether or not you adopt JPMS.

Gradle over Maven here if build times become the complaint: 12 modules with three teams waiting on compilation is exactly where incremental builds, the build cache and implementation-scoped classpaths pay for the added complexity.

The multi-team decision that matters most is release cadence. If the three teams must release independently, a single versioned multi-module build becomes a coordination bottleneck — at that point split the repositories and let the BOM be the contract between them. If they release together, one repository is simpler and the enforced boundaries are a benefit.

🎯 Key Takeaways

  • Dependency resolution and reproducibility are the real features; everything else you could script.
  • Maven runs every phase before the one you invoke, which explains why install runs your tests.
  • A goal can be invoked directly (mvn dependency:tree), bypassing the lifecycle.
  • Scope controls where a dependency appears — a test library at default scope ships to production.
  • Maven resolves conflicts by nearest-wins, not highest version, so the version you ship is often one nobody requested.
  • At equal depth, first declared wins — reordering a POM can change what you ship.
  • dependency:tree -Dverbose is the diagnostic; it shows omitted versions and why.
  • dependencyManagement and BOMs override mediation at any depth.
  • NoSuchMethodError means a version conflict, not a code bug — it compiled against a different jar.
  • Gradle's implementation keeps a dependency off consumers' compile classpath; api makes it part of your contract.
  • Gradle's incremental builds and build cache are why large multi-module projects choose it.
  • Shading is for published libraries — inside an application it blinds CVE scanners and obscures stack traces.
  • Semver is a statement of intent, not a guarantee — let the test suite decide.
  • SNAPSHOTs and version ranges destroy reproducibility; released versions must be immutable.
  • Commit the wrapper so the build tool version is not a per-developer variable.
  • Multi-module builds enforce dependency direction at compile time — the cheapest architectural boundary available.
