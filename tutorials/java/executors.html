Executors & Futures Concurrency

What you'll master: why a pool exists at all — amortised thread cost, and the more important one, bounded concurrency; why newFixedThreadPool and newCachedThreadPool are both traps (an unbounded queue versus unbounded threads); how to build a ThreadPoolExecutor by hand and the core → queue → max growth order that makes maximumPoolSize dead code behind an unbounded queue; the four rejection policies and which one is really backpressure; the submit exception-swallowing asymmetry; CompletableFuture composition and the common-pool trap; why a scheduled task that throws is cancelled forever; shutdown, sizing, and pool deadlock. Prerequisites: Threads.

Part 1 — Why a Pool Exists

  TWO REASONS, AND EVERYONE REMEMBERS THE LESS IMPORTANT ONE.

  REASON 1 (the one people quote): thread creation is expensive.

    creating a platform thread   ~50-100 µs — it is a syscall
    stack reservation            ~1 MB of address space each
    context switch               ~1-10 µs plus cache/TLB damage

  A pool creates N threads once and reuses them for millions of
  tasks. Real, but for a task taking 20 ms this is noise.

  REASON 2 (the one that actually saves you): a pool is a LIMIT.

    for (Request r : incoming) new Thread(() -> handle(r)).start();
    // 20k requests arrive in a burst → 20k OS threads →
    //   OutOfMemoryError: unable to create new native thread
    //   ...and the JVM dies holding every in-flight request.

  With a pool of 50, the 20,000th request WAITS. Your database sees
  at most 50 concurrent queries. Memory is bounded. Latency degrades
  instead of the process dying. That is the point: concurrency
  becomes a DECISION instead of a function of arrival rate.

  THE THIRD THING YOU GET IS DECOUPLING. The task says WHAT; the
  executor says WHERE, HOW MANY AT ONCE, and WHAT HAPPENS WHEN FULL.
  Those are deployment decisions, and burying them in business logic
  means you cannot tune them.

  THE INTERFACES, SMALLEST FIRST:

    Executor                  void execute(Runnable)
    ExecutorService           + submit / invokeAll / invokeAny
                              + shutdown and lifecycle
    ScheduledExecutorService  + schedule / scheduleAtFixedRate

    Runnable     void run()                 no result, no checked ex
    Callable<V>  V call() throws Exception  result AND checked ex

  Callable exists because Runnable can neither return a value nor
  throw a checked exception — which is what a submitted unit of work
  usually wants to do.

Part 2 — The Executors Factory Methods Are Traps

  EVERY TUTORIAL STARTS HERE, AND EVERY ONE OF THESE HAS AN
  UNBOUNDED DIMENSION. Read the actual constructor calls:

    newFixedThreadPool(n)
      → new ThreadPoolExecutor(n, n, 0L, MILLISECONDS,
                               new LinkedBlockingQueue<Runnable>())
                                    ↑ UNBOUNDED. Integer.MAX_VALUE.

    newCachedThreadPool()
      → new ThreadPoolExecutor(0, Integer.MAX_VALUE, 60L, SECONDS,
                               new SynchronousQueue<Runnable>())
                  ↑ UNBOUNDED THREADS. The queue holds nothing, so
                    every task that finds no idle thread MAKES one.

    newSingleThreadExecutor()
      → same unbounded LinkedBlockingQueue, one thread, and wrapped
        so you cannot cast it back and reconfigure it.

  WHAT THE UNBOUNDED QUEUE DOES TO YOU, WITH ARITHMETIC:

    Fixed pool of 10, tasks take 100 ms → service rate 100/s.
    Traffic arrives at 500/s. The backlog grows by 400 per second
    and never drains.

      after 1 minute    24,000 queued tasks
      after 10 minutes  240,000 queued tasks

    Each queued Runnable retains its captured request — headers,
    body, a user object. At 4 KB apiece that is ~1 GB of live heap,
    and the OOM lands in some UNRELATED allocation, so the stack
    trace points somewhere innocent.

    Worse, the tasks that DO run are answering requests whose
    clients gave up four minutes ago. You burn CPU on garbage while
    healthy traffic queues behind it. A bounded queue turns that
    into a fast, honest rejection.

  WHAT UNBOUNDED THREADS DO: newCachedThreadPool under a spike of
  30,000 slow tasks tries to make 30,000 threads. Native OOM, or a
  machine thrashing on context switches. It is fine for short,
  bursty, CPU-light work with a KNOWN ceiling, and dangerous for
  anything facing the internet.

  THE RULE: in server code, construct ThreadPoolExecutor yourself.
  The factories are demo code — Error Prone and SonarQube both flag
  them, and every serious framework configures its pools by hand.

Part 3 — Building a ThreadPoolExecutor Yourself

  new ThreadPoolExecutor(
      4,                              // corePoolSize
      16,                             // maximumPoolSize
      60L, TimeUnit.SECONDS,          // keepAlive for threads > core
      new ArrayBlockingQueue<>(200),  // BOUNDED work queue
      threadFactory,                  // naming, daemon, priority
      new ThreadPoolExecutor.CallerRunsPolicy());  // when full

  THE GROWTH ORDER IS THE MOST MISREAD PART OF THIS CLASS.
  On every execute(), the pool asks, IN THIS ORDER:

      task arrives
           │
           ├─ running threads < corePoolSize?
           │       YES → start a NEW thread (even if others are idle)
           │
           ├─ can the QUEUE accept it?
           │       YES → enqueue. DONE. No new thread.
           │
           ├─ running threads < maximumPoolSize?
           │       YES → start a new thread
           │
           └─ else → REJECT via the RejectedExecutionHandler

  READ THE MIDDLE BRANCH AGAIN. The pool prefers QUEUEING over
  growing past core. Therefore:

    new ThreadPoolExecutor(2, 100, 60, SECONDS,
                           new LinkedBlockingQueue<>())   // unbounded

    ...NEVER creates a third thread. The queue always accepts, so
    branch 3 is unreachable. maximumPoolSize is dead code and
    keepAliveTime with it. People write 100 and get 2.

    A BOUNDED QUEUE IS A PRECONDITION FOR maximumPoolSize TO MEAN
    ANYTHING. This is the difference between the pool you configured
    and the pool you got.

  SO THE QUEUE CHOOSES HOW FAST THE POOL REACTS TO LOAD:

    SynchronousQueue    grow to max immediately, then reject.
                        Fastest reaction; this is what
                        newCachedThreadPool uses.
    small bounded       absorb micro-bursts without paying thread
                        creation, then grow. Usually right.
    huge bounded        you built a fixed pool with a latency bomb.

  THE OTHER KNOBS:

    allowCoreThreadTimeOut(true)   core threads also die when idle —
                                   good for a usually-quiet pool,
                                   since each idle core thread still
                                   reserves ~1 MB of stack
    prestartAllCoreThreads()       pay creation cost at startup, not
                                   on the first user request
    setCorePoolSize(n)             tunable at runtime from JMX

  ALWAYS PASS A ThreadFactory. The default names threads
  "pool-3-thread-7", which tells you nothing in a 3am thread dump
  with six pools running:

    ThreadFactory tf = r -> {
        Thread t = new Thread(r, "http-worker-" + n.getAndIncrement());
        t.setDaemon(false);              // deliberate, not accidental
        t.setUncaughtExceptionHandler((th, e) -> log.error("died", e));
        return t;
    };

  A NAMED THREAD IS THE CHEAPEST OBSERVABILITY YOU WILL EVER BUY —
  every profiler, thread dump and flame graph groups by it.
Rejection policyBehaviourEffect on the callerUse when
AbortPolicy (default)Throws RejectedExecutionExceptionFails fast — but only if you catch itYou can map it to HTTP 503 and shed load
CallerRunsPolicyRuns the task on the submitting threadThe submitter blocks — real backpressureIngest pipelines, where slowing the producer is correct
DiscardPolicySilently drops the taskNothing. No exception, no logTruly optional work (metric samples), never orders
DiscardOldestPolicyDrops the queue head, retriesNothing; an old task vanishesLatest-value-wins feeds (quotes, sensor readings)

CallerRunsPolicy is the one people underuse. It converts overload into throughput loss instead of failure: while the caller runs a task it is not accepting new work, so the socket backlog fills and TCP itself pushes back on clients. It is wrong in exactly one common case — when the calling thread is an event loop or the acceptor thread, where blocking it stops everything.

Part 4 — submit vs execute, and the Swallowed Exception

  THIS ASYMMETRY HAS COST MORE PRODUCTION HOURS THAN ANYTHING ELSE
  ON THIS PAGE.

    executor.execute(() -> { throw new IllegalStateException("x"); });

      → the exception escapes run(), the worker thread DIES,
      → its UncaughtExceptionHandler fires (default: stack trace to
        System.err),
      → the pool notices and creates a REPLACEMENT thread.
      YOU SEE THE FAILURE. Noisy, but honest.

    Future<?> f = executor.submit(() -> { throw new IllegalStateException("x"); });

      → FutureTask.run() has catch (Throwable t) { setException(t); },
        so the exception becomes a RESULT stored in the Future. The
        thread does not die. Nothing is printed.
      → if you never call f.get(), the failure is INVISIBLE FOREVER.

  AN UNREAD FUTURE IS AN UNREAD FAILURE. This is why the nightly job
  "worked" for three weeks while producing wrong totals.

  THE FIXES, IN ORDER OF PREFERENCE:

    1. Consume the Future — get(), or exceptionally/whenComplete on
       a CompletableFuture.
    2. try/catch INSIDE the task and log there:
         executor.submit(() -> {
             try { doWork(); }
             catch (Throwable t) { log.error("task failed", t); throw t; }
         });
    3. Override afterExecute — it gets the Throwable for execute(),
       and for submit() you must unwrap the Future yourself:
         protected void afterExecute(Runnable r, Throwable t) {
             super.afterExecute(r, t);
             if (t == null && r instanceof Future<?> f && f.isDone()) {
                 try { f.get(); }
                 catch (CancellationException ce) { /* expected */ }
                 catch (ExecutionException ee) { t = ee.getCause(); }
                 catch (InterruptedException ie) { Thread.currentThread().interrupt(); }
             }
             if (t != null) log.error("task failed", t);
         }

  FUTURE ITSELF IS A BLOCKING, JOINLESS API:

    f.get()                    blocks FOREVER. In a request thread
                               this is how a service hangs.
    f.get(2, TimeUnit.SECONDS) throws TimeoutException — and DOES
                               NOT cancel the task. It is still
                               running and still holding a thread.
    f.cancel(true)             interrupts the running thread. A
                               REQUEST: a task that never checks
                               interruption and never blocks ignores
                               it completely.
    f.cancel(false)            only stops a not-yet-started task.
    ExecutionException         the real error is in getCause(). Log
                               the cause, or your stack trace
                               describes the framework, not the bug.

  THE CANONICAL TIMEOUT BLOCK:

    try {
        return f.get(2, TimeUnit.SECONDS);
    } catch (TimeoutException e) {
        f.cancel(true);                            // do not leak it
        return fallback();
    } catch (ExecutionException e) {
        throw new ServiceException(e.getCause());   // unwrap
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();         // restore the flag
        throw new ServiceException(e);
    }

  BATCH SUBMISSION:

    List<Future<Row>> all = ex.invokeAll(tasks, 3, SECONDS);

      Returns only when EVERY task is done or the timeout hits. On
      timeout, unfinished tasks are CANCELLED and their Futures
      throw CancellationException — every Future is "done", which is
      NOT the same as "succeeded". Inspect each one.

    Row first = ex.invokeAny(tasks, 1, SECONDS);

      First SUCCESSFUL result; cancels the rest. Use it for hedged
      requests — ask three replicas, take whoever answers first.

  invokeAll gives you nothing until the SLOWEST task finishes. For
  results as they arrive:

    var cs = new ExecutorCompletionService<Row>(ex);
    for (var t : tasks) cs.submit(t);
    for (int i = 0; i < tasks.size(); i++) render(cs.take().get());

  Total time is unchanged; TIME TO FIRST RESULT drops from max(t) to
  min(t), which is what a user perceives.

Part 5 — CompletableFuture: Composition Without Blocking

  Future.get() BLOCKS, so a thread sits idle holding a stack.
  CompletableFuture lets you say "when this finishes, do that" and
  hand the thread back.

  THE THREE COMPOSITION METHODS, AND THE ONE PEOPLE GET WRONG:

    thenApply(fn)      fn: T -> U       wraps  → CF<U>      (map)
    thenCompose(fn)    fn: T -> CF<U>   FLATTENS → CF<U>   (flatMap)
    thenCombine(o, fn) fn: (T,U) -> V   joins TWO independent CFs

    // ❌ nested — join() gives you a FUTURE, not a User
    CF<CF<User>> bad = findId(name).thenApply(id -> loadUser(id));

    // ✅ flattened
    CF<User> good = findId(name).thenCompose(id -> loadUser(id));

  If your lambda's return type is already async, COMPOSE.

  thenCombine RUNS THE TWO SOURCES IN PARALLEL:

    CF<Profile> p = supplyAsync(() -> loadProfile(id), pool);
    CF<Prefs>   q = supplyAsync(() -> loadPrefs(id),   pool);
    CF<Page> page = p.thenCombine(q, Page::new);
    // wall time = max(p, q), not p + q

  ═══════════ THE commonPool TRAP — THE BIG ONE ═══════════

    CompletableFuture.supplyAsync(() -> httpGet(url))
    // no executor argument → ForkJoinPool.commonPool()

    THE COMMON POOL IS:
      • sized to availableProcessors() - 1 threads
      • SHARED by every parallel stream, every unconfigured
        supplyAsync, and library code you did not write
      • made of DAEMON threads — pending work is abandoned at exit

    On an 8-core box that is SEVEN threads for the whole JVM. Put
    eight 200 ms HTTP calls on it and the ninth waits, your parallel
    streams stall, and an unrelated subsystem gets slow. The symptom
    is latency spikes with the CPU at 10%.

    WORSE IN A CONTAINER: with a 1-CPU limit, availableProcessors()
    reports 1, parallelism becomes 0, and tasks run on the CALLING
    thread. Your "async" pipeline is synchronous and nothing tells
    you. Check availableProcessors() inside the container, not on
    your laptop.

    RULE: pass an executor to every *Async call in application code.
    Reserve the common pool for short, non-blocking, CPU-bound work.

  NON-ASYNC VS ASYNC VARIANTS:

    thenApply(fn)             runs on WHICHEVER thread completed the
                              previous stage — or the CALLING thread
                              if that stage was already done.
    thenApplyAsync(fn)        the common pool.
    thenApplyAsync(fn, exec)  the only version whose execution
                              location you can state out loud.

    Non-async is fine for cheap pure transforms (parse a string, map
    a DTO). Anything that blocks on a non-async stage runs on a
    thread that belongs to someone else — often an HTTP client's I/O
    thread, which you must never block.

  ERROR HANDLING — THREE DIFFERENT SHAPES:

    .exceptionally(ex -> fallback)      only on failure; recovers
    .handle((v, ex) -> ...)             always; sees both; recovers
    .whenComplete((v, ex) -> log(...))  always; SIDE EFFECT ONLY —
                                        result and exception pass
                                        through unchanged

    Stage exceptions are wrapped in CompletionException. join()
    throws it unchecked; get() throws checked ExecutionException.
    Both hide the real error in getCause().

  COMBINING MANY:

    CompletableFuture<Void> all = CompletableFuture.allOf(
        futures.toArray(new CompletableFuture[0]));

    // allOf yields Void — re-gather results yourself:
    List<Row> rows = all.thenApply(v ->
        futures.stream().map(CompletableFuture::join).toList()).join();

    join() is safe THERE because allOf guarantees each is complete.
    Calling join() on an INCOMPLETE future from a pool thread is how
    you deadlock the pool (Part 7).

  TIMEOUTS (Java 9+):

    cf.orTimeout(2, SECONDS)                   fail with TimeoutException
    cf.completeOnTimeout(DEF, 2, SECONDS)      complete with a value

    Both bound how long you WAIT, not how long the task LIVES. The
    underlying call keeps running and keeps its connection, so set a
    real timeout on the client too.

Part 6 — Scheduling, and the Task That Silently Stops

  ses.schedule(task, 5, SECONDS);                    // once
  ses.scheduleAtFixedRate(task, 0, 10, SECONDS);     // every 10s
  ses.scheduleWithFixedDelay(task, 0, 10, SECONDS);  // 10s BETWEEN

  FIXED RATE vs FIXED DELAY, period 10 s:

    task takes 4 s   fixedRate   starts at 0, 10, 20, 30 …
                     fixedDelay  starts at 0, 14, 28, 42 …

    task takes 25 s  fixedRate   starts at 0, 25, 50 … BACK TO BACK.
                     Never overlapping (the scheduler serialises a
                     given periodic task) but with no gap at all —
                     it hammers a dependency exactly when that
                     dependency is already struggling.
                     fixedDelay  starts at 0, 35, 70 … gap preserved.

    USE fixedDelay FOR POLLING AND CLEANUP. Use fixedRate only when
    the schedule itself matters (a metric emitted on the minute) and
    the task is reliably faster than the period.

  ═══ THE TRAP: A PERIODIC TASK THAT THROWS IS CANCELLED FOREVER ═══

    ses.scheduleAtFixedRate(() -> {
        refreshCache();       // throws once, at 03:14, on one bad row
    }, 0, 60, SECONDS);

    That single exception ENDS the schedule. Not "skips this run" —
    ends it, permanently. And nothing is logged: the throwable goes
    into a ScheduledFuture you never kept, exactly like the submit()
    case in Part 4. Your cache silently stops refreshing and you
    learn about it days later from stale data.

    THE FIX IS A CATCH INSIDE THE TASK, AND IT MUST CATCH Throwable:

      ses.scheduleWithFixedDelay(() -> {
          try {
              refreshCache();
          } catch (Throwable t) {          // yes, Throwable
              log.error("refresh failed; retrying next period", t);
          }
      }, 0, 60, SECONDS);

    Catching Exception is not enough — a NoClassDefFoundError from a
    lazily loaded class kills the schedule just as dead. This is one
    of the very few places where catching Throwable and carrying on
    is the correct engineering decision.

    ADD A LIVENESS METRIC TOO: record the last successful run and
    alert when it is older than a few periods. A swallowed exception
    is invisible to monitoring; a stale timestamp is not.

  OTHER SHARP EDGES:

    • Scheduling is relative to nanoTime, so it is immune to wall
      clock changes and NTP steps. Do NOT build cron on it — "3am
      daily" across a DST boundary is not a duration.
    • A shared scheduler is a shared point of delay: one task that
      blocks for 30 s delays every other task on that thread. Keep
      scheduled tasks trivial — have them SUBMIT the real work to a
      separate worker pool.
    • ScheduledThreadPoolExecutor's queue is unbounded and its
      maximumPoolSize is meaningless (DelayedWorkQueue always
      accepts, so growth branch 3 from Part 3 never fires).

Part 7 — Shutdown, Sizing, and Pool Deadlock

  POOL THREADS ARE NON-DAEMON BY DEFAULT, SO A FORGOTTEN EXECUTOR
  KEEPS THE JVM ALIVE. main() returns, the process does not exit,
  and everyone blames the container.

  THE THREE METHODS DIFFER, AND ONLY ONE WAITS:

    shutdown()          reject new tasks; run everything already
                        submitted, queue included. Returns AT ONCE.
    shutdownNow()       reject new tasks, DRAIN the queue and return
                        the un-run tasks, INTERRUPT the running
                        ones. Returns AT ONCE. Interruption is a
                        request — a tight CPU loop that never checks
                        the flag keeps going.
    awaitTermination(t) the only blocking one. Returns false on
                        timeout. Without a prior shutdown it just
                        waits out the timeout and returns false.

  THE RECIPE (write it once, put it in a utility):

    void shutdown(ExecutorService ex) {
        ex.shutdown();                              // stop intake
        try {
            if (!ex.awaitTermination(30, SECONDS)) {
                List<Runnable> dropped = ex.shutdownNow();
                log.warn("forcing shutdown, {} dropped", dropped.size());
                if (!ex.awaitTermination(10, SECONDS))
                    log.error("pool did not terminate");
            }
        } catch (InterruptedException e) {
            ex.shutdownNow();
            Thread.currentThread().interrupt();      // restore the flag
        }
    }

    The grace period must exceed your slowest normal task, or every
    deploy kills healthy in-flight work.

  ══════════════════ SIZING ══════════════════

  CPU-BOUND: N = cores (some add +1 to cover a brief stall). More
  runnable threads than cores buys context switches, not throughput
  — measurably worse, not neutral.

  I/O-BOUND, THE UTILISATION FORMULA:

    N = cores × targetUtilisation × (1 + waitTime / computeTime)

    8 cores, target 0.9, task = 2 ms CPU + 48 ms waiting on a DB:
      N = 8 × 0.9 × (1 + 48/2) = 180

  LITTLE'S LAW GETS THERE FROM THE OTHER DIRECTION:

    L = λ × W          concurrency = arrival rate × time in system

    1,000 req/s at 50 ms each → L = 50 in flight. Fewer than 50
    threads and the queue grows without bound, full stop.

  NOW THE CORRECTION THE FORMULAS OMIT: 180 threads are useless if
  the JDBC pool has 20 connections. The other 160 block on
  connection acquisition instead of on the database — you moved the
  queue, you did not shorten it, and you spent 160 MB of stack doing
  it. SIZE TO THE NARROWEST DOWNSTREAM LIMIT, then verify by
  measurement: the formula assumes a constant W that real systems do
  not have.

  ONE POOL PER RESOURCE CLASS, NOT ONE PER APPLICATION. A slow
  third-party API sharing a pool with your database calls will
  eventually own every thread and take the database path down with
  it. That is the bulkhead pattern, and it is worth the config.

  ══════════════ THREAD POOL DEADLOCK ══════════════

    ExecutorService pool = Executors.newFixedThreadPool(4);

    Future<Report> f = pool.submit(() -> {            // PARENT
        Future<Part> a = pool.submit(() -> fetchA());  // CHILD
        Future<Part> b = pool.submit(() -> fetchB());  // CHILD
        return new Report(a.get(), b.get());          // BLOCKS HERE
    });

    Four parents occupy all four threads; each blocks on a child;
    the children sit in the queue behind them. No thread will ever
    free up. The pool is deadlocked with an IDLE CPU and a full
    queue, every worker parked in FutureTask.awaitDone.

    IT IS NOT A RACE. It is deterministic once nesting depth reaches
    the pool size, so it passes every low-load test and fails the
    moment production concurrency arrives.

    THE FIXES, BEST FIRST:
      1. DO NOT BLOCK — compose with thenCombine and return a
         CompletableFuture instead of calling get() inside a task.
      2. SEPARATE POOLS PER STAGE: parents in A, children in B. A
         blocked parent can no longer starve its own child.
      3. ForkJoinPool, whose join() lets a blocked worker STEAL and
         run other tasks — which is exactly why blocking I/O in it
         destroys that property.
      4. Virtual threads (Java 21), where threads are not scarce and
         this failure mode disappears entirely.

    "Just make the pool bigger" is not a fix: it moves the deadlock
    from depth 4 to depth 64, so the test goes green and production
    still falls over. The defect is structural, not numeric.

    THE RULE: NEVER call get()/join() on a task that runs in the
    same pool as the caller.

Interview Questions

Beginner: What does an ExecutorService give you that new Thread() does not?

Reuse, a bound, and a result type. Reuse matters because creating a platform thread is a syscall costing tens of microseconds plus about a megabyte of reserved stack; a pool pays that once per worker instead of once per task.

The bound matters more. new Thread() per request makes your concurrency equal to your arrival rate, so a traffic spike becomes thousands of threads and an OutOfMemoryError: unable to create new native thread. A pool of 50 makes the 51st request wait — the system degrades instead of dying, and your database never sees more than 50 concurrent queries.

The result type matters for correctness: Thread cannot return a value or report a checked exception, while submit(Callable) returns a Future carrying both, plus cancellation and timeouts.

Finally it separates concerns. The task says what; the executor decides how many at once, on which threads, and what happens when saturated. Those are deployment decisions, and code that hard-codes them cannot be tuned.

Beginner: What is the difference between execute and submit?

execute(Runnable) returns void; submit returns a Future. The important difference is exception handling, and it is counter-intuitive.

With execute, an exception escapes run(), kills the worker thread, and fires that thread's UncaughtExceptionHandler — by default printing a stack trace to System.err. The pool quietly creates a replacement, so the pool keeps working and you see the failure.

With submit, the task is wrapped in a FutureTask whose run() catches Throwable and stores it in the Future. The thread does not die and nothing is printed. If you never call get(), the failure is completely invisible — the classic "the nightly job stopped working and nobody noticed" bug.

So use submit when you need a result, a timeout or cancellation, and then actually consume the Future. Use execute for fire-and-forget work where you want failures to be loud. Either way, a try/catch with a log line inside the task is the cheapest insurance.

Mid: Why is Executors.newFixedThreadPool(10) dangerous in a web service?

Because of what it is underneath: new ThreadPoolExecutor(10, 10, 0L, MILLISECONDS, new LinkedBlockingQueue<>()), and that queue is unbounded — capacity Integer.MAX_VALUE.

Do the arithmetic. Tasks take 100 ms, so ten threads serve 100 tasks/second. If 500 requests/second arrive, the backlog grows by 400 every second and never shrinks. After ten minutes there are 240,000 queued Runnables, each retaining its captured request state; at 4 KB apiece that is about a gigabyte of live heap, and the OutOfMemoryError surfaces in whatever code allocates next, so the root cause looks like anything but the executor.

You are failing well before the OOM, though. The tasks currently executing belong to requests whose clients timed out minutes ago, so you burn CPU producing responses nobody will read while healthy traffic waits behind them. Nowhere in this design is there a backpressure signal — the queue happily accepts work the system cannot do.

The fix is an explicit ThreadPoolExecutor with a bounded queue and a deliberate rejection policy. CallerRunsPolicy pushes back on the submitter; AbortPolicy plus a handler returning HTTP 503 sheds load honestly. Both make the system's limit visible at the moment it is reached, which is the whole point.

The same reasoning condemns newCachedThreadPool from the other direction — unbounded threads rather than an unbounded queue, and native OOM rather than heap OOM.

Mid: How do you size a thread pool?

Start from the workload type, then correct with measurement.

WorkloadFormulaReasoning
CPU-boundN = cores (or cores + 1)More runnable threads than cores just adds context switches
I/O-boundN = cores × u × (1 + W/C)Threads are mostly waiting, so you need many per core
From measured loadL = λ × W (Little's Law)Gives the in-flight concurrency needed to sustain the arrival rate

Worked example: 8 cores, 90% target utilisation, a task spending 2 ms on CPU and 48 ms waiting on a database gives N = 8 × 0.9 × (1 + 48/2) = 180. From the other direction, 1,000 req/s at 50 ms gives L = 50 as a floor.

Then apply the correction the formulas omit: the pool cannot be more useful than the narrowest downstream limit. With a 20-connection JDBC pool, 180 threads means 160 of them block on connection acquisition — you moved the queue rather than shortening it, and spent 160 MB of stack to do so.

Use separate pools per resource class. One pool shared between fast local database calls and a slow third-party API means the slow dependency eventually owns every thread and takes the database path down with it. Finally, treat every number as a hypothesis: instrument queue depth, active count and task latency, then load-test. When throughput stops rising as you add threads, you have found the real limit and the formula was only a starting point.

Senior: A service built on CompletableFuture has p99 latency spikes, but CPU sits at 15%. Walk through the diagnosis.

Low CPU with high latency means threads are waiting, not working. Four candidates, in the order I would check them.

1. The common pool. Every supplyAsync or thenApplyAsync without an explicit executor runs on ForkJoinPool.commonPool(), which has availableProcessors() - 1 threads and is shared with every parallel stream in the JVM. Blocking HTTP calls there mean the eighth concurrent call waits for a thread while no CPU is busy. A thread dump showing ForkJoinPool.commonPool-worker-N threads parked in socket reads confirms it instantly.

2. Container CPU limits. With a 1-CPU limit, availableProcessors() reports 1, common-pool parallelism collapses to zero, and tasks run on the calling thread — the pipeline is silently synchronous. Check that value inside the running container.

3. Non-async stages on borrowed threads. A plain thenApply runs on whichever thread completed the previous stage. If that was an HTTP client's I/O thread, blocking work there stalls that client's event loop, and the latency appears in calls unrelated to your code.

4. The real bottleneck downstream. Threads blocked acquiring a connection look identical to threads blocked on the network, so read the connection pool's own metrics — pending acquisitions, acquisition time — before touching the executor.

Symptom in the thread dumpCauseFix
Common-pool workers in socket readBlocking work on the common poolA dedicated executor per dependency
Everything on the request threadParallelism 0 in a 1-CPU containerExplicit executor with an explicit size
Client I/O threads running business logicNon-async stage on a borrowed threadthenApplyAsync(fn, exec)
Workers parked in getConnectionThe connection pool is the real limitResize the connection pool, not the executor
Every worker in Future.get()Nested tasks in one pool — deadlockSplit the pools, or compose without blocking

Recommendation: make thread ownership explicit everywhere — a named executor per downstream dependency, an explicit executor argument on every async stage, and a metric for each pool's queue depth and active count. These bugs are invisible precisely because the default executor is implicit.

Senior: Design the executor configuration for an HTTP endpoint that calls three downstream services.

Say it calls a user service (fast, ~10 ms), a recommendation service (slow, ~200 ms, flaky) and a database (~5 ms). Two calls are independent; one depends on the user result.

Topology: one pool per dependency, not one shared. With a single pool, a recommendation-service outage fills it with threads blocked for the full timeout and requests needing only the database fail too. Bulkheads keep the blast radius to one dependency.

PoolSizeQueueRejectionWhy
user-iomin(formula, connection limit)Bounded, ~2× sizeAbortPolicy → 503Fast dependency; a backlog means it is down
reco-ioSmall — the call is optionalSmall boundedAbortPolicy → degradeRecommendations are droppable; keep the page working
db= JDBC pool sizeBoundedCallerRunsPolicyMore threads than connections is pure waste

Composition: the two independent calls with thenCombine, so wall time is max(10, 200) instead of 210; the dependent call with thenCompose; an explicit executor on every stage. The flaky dependency gets completeOnTimeout(EMPTY, 150, MILLISECONDS) and exceptionally(ex -> EMPTY), so a broken recommendation service degrades the response instead of failing it.

The rejected alternative: one large shared pool is simpler to configure and easier to reason about at low load, and if all three dependencies were equally fast and equally critical I would take it. Here the failure modes differ per dependency, which is exactly the condition that justifies separate pools.

What I would actually recommend on Java 21+: replace all three pools with Executors.newVirtualThreadPerTaskExecutor(), write plain blocking code, and keep a Semaphore per dependency to preserve the bulkhead. The pools existed to ration threads; virtual threads make threads cheap, so the only limit worth enforcing is the downstream one — and a semaphore states that limit far more directly than a pool size does. Straight-line code and readable stack traces are a real operational win on top.

Non-negotiable in either design: a timeout on every call, a bound on every queue, a named thread factory, metrics on queue depth and active count, and the shutdown recipe wired into the application lifecycle.

🏋️ Graded Exercises

1 (easy): This runs fine in staging and dies in production. Why? 
ExecutorService pool = Executors.newFixedThreadPool(10);

void onRequest(Request r) {
    pool.submit(() -> handle(r));    // handle() takes ~100 ms
}
Solution

The unbounded queue. newFixedThreadPool(10) is a ThreadPoolExecutor with a LinkedBlockingQueue of capacity Integer.MAX_VALUE. Ten threads at 100 ms each serve 100 requests/second. Staging sends 20/s and everything looks perfect; production sends 500/s, so the queue grows by 400 entries a second and never drains.

Each queued lambda captures r — headers, body, session. At 4 KB retained per task, ten minutes of overload is roughly a gigabyte of live heap, and the OutOfMemoryError lands in whatever allocates next, so the stack trace points somewhere innocent.

var pool = new ThreadPoolExecutor(
        10, 10, 0L, TimeUnit.MILLISECONDS,
        new ArrayBlockingQueue<>(100),          // BOUNDED
        namedFactory("req-worker"),
        new ThreadPoolExecutor.AbortPolicy());

void onRequest(Request r) {
    try {
        pool.submit(() -> handle(r));
    } catch (RejectedExecutionException e) {
        respond(503, "busy");                   // shed load honestly
    }
}

The queue length is a latency budget, not a round number. 100 slots at 100 tasks/second means a task at the back waits one second. Pick the capacity by asking how long a request may wait before the answer is worthless, then divide by the service rate.

For a request acceptor, AbortPolicy beats CallerRunsPolicy, because blocking the accepting thread stops you serving even cheap requests. In an ingest pipeline, where the producer reads from a file or a broker, CallerRunsPolicy is the better answer — there, slowing the producer is exactly what you want.

2 (easy): The nightly reconciliation stopped producing correct totals three weeks ago. No errors in the log. Find the bugs. 
ExecutorService pool = Executors.newFixedThreadPool(4);

for (Account a : accounts) {
    pool.submit(() -> reconcile(a));   // throws on one malformed account
}
pool.shutdown();
Solution

Bug 1 — submit swallows the exception. The task is wrapped in a FutureTask that catches Throwable and stores it in a Future nobody keeps. The worker survives, nothing prints, and the job reports success. Every later account still processes, so the total silently drifts — the worst kind of failure, because output keeps arriving and is wrong.

Bug 2 — shutdown() does not wait. It returns immediately. Non-daemon pool threads keep the JVM alive by accident rather than design, and in a container with a hard stop timeout the last tasks are killed mid-write.

var futures = new ArrayList<Future<?>>();
for (Account a : accounts) {
    futures.add(pool.submit(() -> {
        try {
            reconcile(a);
        } catch (Throwable t) {
            log.error("account {} failed", a.id(), t);
            throw t;                    // keep it in the Future too
        }
    }));
}
pool.shutdown();
if (!pool.awaitTermination(30, TimeUnit.MINUTES)) pool.shutdownNow();

int failed = 0;
for (Future<?> f : futures) {
    try { f.get(); }
    catch (ExecutionException e) { failed++; }
}
if (failed > 0) throw new JobFailedException(failed + " accounts failed");
ApproachFailure visible?Job exit status correct?
submit, ignore the FutureNoNo — always "success"
execute, no try/catchYes, on stderrNo — exit status still 0
try/catch + log inside the taskYes, in the logNot by itself
Collect and inspect every FutureYesYes

Do both. The log tells an operator which account broke; inspecting the futures makes the batch fail loudly so the scheduler and your alerts notice. A batch job that cannot fail is a batch job you cannot trust.

3 (medium): This pool is configured for up to 50 threads. Under sustained load a thread dump shows exactly 5. Explain, then fix. 
var pool = new ThreadPoolExecutor(
        5, 50, 60L, TimeUnit.SECONDS,
        new LinkedBlockingQueue<Runnable>());
Solution

The queue is unbounded, so the pool never reaches the branch that would create thread six. On every execute the pool asks three questions in a fixed order: below core, so start a thread? Can the queue take it, so enqueue and stop? Only if the queue refuses does it consider growing towards maximumPoolSize.

A LinkedBlockingQueue built with no capacity argument holds Integer.MAX_VALUE elements, so it never refuses and question two always answers yes. The 50 and the 60 seconds are dead configuration — this behaves exactly like newFixedThreadPool(5).

var pool = new ThreadPoolExecutor(
        5, 50, 60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<Runnable>(100),   // now it can refuse
        namedFactory("worker"),
        new ThreadPoolExecutor.CallerRunsPolicy());
QueueGrowth behaviourRejects when
LinkedBlockingQueue (unbounded)Stops at core, foreverNever — it OOMs instead
ArrayBlockingQueue(100)core → 100 queued → grow to max50 running and 100 queued
SynchronousQueuecore → grow to max immediately50 running and no idle thread

Choose the queue by how fast you want the pool to react. A SynchronousQueue hands off directly and grows on the first contended task — the fastest response to a burst, and what newCachedThreadPool uses. A modest bounded queue absorbs micro-bursts without paying thread creation, then grows. A large queue means you chose latency over parallelism, usually without realising it.

The reason for this order is that queueing is cheaper than thread creation, so the designers made it the default preference. Defensible — it is just not what the parameter names suggest, which is why this exact configuration is everywhere in production code.

4 (medium): A cache refresher stops running after a few days. The process is healthy and other scheduled jobs still fire. What happened, and what else is wrong? 
var ses = Executors.newSingleThreadScheduledExecutor();
ses.scheduleAtFixedRate(() -> {
    cache.putAll(loadFromDb());        // occasionally throws
}, 0, 30, TimeUnit.SECONDS);
Solution

An uncaught exception cancels a periodic task permanently. ScheduledThreadPoolExecutor treats a throwing periodic task as finished: the ScheduledFuture completes exceptionally and is never rescheduled. Nothing is logged, because — exactly as with submit — the throwable lives in a future you never kept. One transient database blip at 3am ends the refresh forever, and the cache serves stale data until someone notices.

Second problem: scheduleAtFixedRate is the wrong choice here. If loadFromDb() starts taking 45 seconds, fixed-rate runs it back to back with no gap, hammering the database precisely when it is already struggling. Fixed delay preserves the breather. Third: real work on the scheduler thread — a single-threaded scheduler running a slow query delays every other job on it.

ses.scheduleWithFixedDelay(() -> {
    try {
        worker.submit(() -> cache.putAll(loadFromDb()));   // off the scheduler
        lastOk.set(System.currentTimeMillis());            // liveness metric
    } catch (Throwable t) {                 // Throwable, not Exception
        log.error("cache refresh failed; retrying next period", t);
    }
}, 0, 30, TimeUnit.SECONDS);
Task duration (period 30 s)scheduleAtFixedRatescheduleWithFixedDelay
5 sStarts at 0, 30, 60Starts at 0, 35, 70
45 sStarts at 0, 45, 90 — back to back, no gapStarts at 0, 75, 150 — gap preserved
ThrowsCancelled foreverCancelled forever

Catch Throwable, not Exception. A NoClassDefFoundError from a lazily loaded class, or a StackOverflowError deep in a library, kills the schedule just as effectively. This is one of the few situations where catching Throwable and carrying on is right — the alternative is a silently dead subsystem.

The liveness metric is not optional. A swallowed exception is invisible to monitoring; "last successful refresh was 40 minutes ago" is an alert you can actually act on.

5 (hard): Load tests pass at 10 concurrent users and hang completely at 100. CPU is near zero. Diagnose and fix. 
ExecutorService pool = Executors.newFixedThreadPool(8);

Report buildReport(Id id) throws Exception {
    return pool.submit(() -> {
        Future<Header> h = pool.submit(() -> loadHeader(id));
        Future<Body>   b = pool.submit(() -> loadBody(id));
        return new Report(h.get(), b.get());
    }).get();
}
Solution

Thread pool deadlock from nested dependent tasks. Once eight report tasks are running, all eight pool threads are occupied and each is blocked in h.get(). Their child tasks sit in the queue behind them. No thread can finish, because finishing needs a child to run, and no child can run, because every thread is blocked. The pool is permanently stuck with an idle CPU and a full queue, every worker parked in FutureTask.awaitDone.

It is not a race — it is deterministic once concurrent depth reaches the pool size, which is exactly why it passed at 10 users and failed at 100.

// Fix 1 (best) — do not block at all
CompletableFuture<Report> buildReport(Id id) {
    var h = CompletableFuture.supplyAsync(() -> loadHeader(id), pool);
    var b = CompletableFuture.supplyAsync(() -> loadBody(id),   pool);
    return h.thenCombine(b, Report::new);
}

// Fix 2 — separate pools, if the caller really must block
ExecutorService parents  = Executors.newFixedThreadPool(8);
ExecutorService children = Executors.newFixedThreadPool(16);
// parents submit only to `children`; a blocked parent cannot starve it
FixWhy it worksCost
Compose with thenCombineNo thread ever blocks on a childThe API becomes async up the call stack
Separate parent and child poolsChild threads are never held by parentsTwo pools to size and monitor
ForkJoinPool + join()A joining worker steals and runs other tasksOnly valid for non-blocking work
Virtual threads (Java 21+)Threads are not scarce; blocking is cheapRequires Java 21; downstream limits still apply
"Make the pool bigger"It does not — it raises the depth at which it deadlocksA bigger pool and the same outage later

The general rule: never call get() or join() on a task that runs in the same pool as the caller. A blocked thread that owns the resource its own unblocking depends on is a deadlock by definition, and the pool makes that ownership invisible.

6 (hard): Review this pipeline. There are four defects — find them and rewrite it. 
CompletableFuture<Page> loadPage(long userId) {
    return CompletableFuture
        .supplyAsync(() -> userClient.fetch(userId))
        .thenApply(user -> ordersClient.fetchAsync(user.id()))
        .thenApply(ordersFuture -> ordersFuture.join())
        .thenApply(orders -> new Page(orders));
}
Solution

Defect 1 — no executor. supplyAsync without one runs on ForkJoinPool.commonPool(): cores - 1 threads shared with every parallel stream in the JVM. Blocking HTTP calls there starve unrelated code, and in a 1-CPU container parallelism can collapse to the point where work runs on the calling thread — an async pipeline that is silently synchronous.

Defect 2 — thenApply where thenCompose belongs. fetchAsync returns a future, so the stage type is CompletableFuture<CompletableFuture<Orders>>. The author papered over it with a third stage calling join(), which blocks a pool thread waiting for a future that may be completed by that very pool.

Defect 3 — no error handling: any failure propagates as a CompletionException to whoever eventually joins, with the real cause buried in getCause(), no fallback and nowhere that logs it. Defect 4 — no timeout: a downstream that accepts the connection and never responds holds the stage forever.

CompletableFuture<Page> loadPage(long userId) {
    return CompletableFuture
        .supplyAsync(() -> userClient.fetch(userId), ioPool)
        .thenCompose(user -> ordersClient.fetchAsync(user.id()))   // flatten
        .orTimeout(2, TimeUnit.SECONDS)
        .thenApply(Page::new)                  // cheap and pure: no Async needed
        .whenComplete((page, ex) -> { if (ex != null) log.warn("loadPage failed", unwrap(ex)); })
        .exceptionally(ex -> Page.degraded());
}

static Throwable unwrap(Throwable t) {
    return t instanceof CompletionException && t.getCause() != null ? t.getCause() : t;
}

Why whenComplete before exceptionally: whenComplete observes without altering the outcome, so the log sees the real failure; exceptionally then substitutes the degraded page. Reversed, the log would see nothing, because the exception is already handled by the time the observer runs.

What orTimeout does not do: it fails the stage after two seconds; the underlying HTTP call keeps running and keeps its connection. Set a real timeout on the HTTP client as well — orTimeout bounds your waiting, not the work.

Leaving thenApply for Page::new is deliberate. It is a cheap non-blocking transform, so running it inline on the completing thread avoids a pointless handoff. The rule is not "always async" — it is "async whenever the stage can block or take real time".

🎯 Key Takeaways

  • A pool's real value is the bound, not the reuse — it turns concurrency into a decision instead of a function of arrival rate.
  • Every Executors factory has an unbounded dimension: a queue, a thread count, or both. Build ThreadPoolExecutor yourself in server code.
  • The growth order is core → queue → max, so maximumPoolSize is dead code behind an unbounded queue.
  • An unbounded queue converts overload into an OutOfMemoryError in unrelated code, after a spell of answering requests nobody is waiting for.
  • CallerRunsPolicy is the only rejection policy that is real backpressure — and it is wrong on an event-loop or acceptor thread.
  • submit stores exceptions in the Future; execute prints them — an unread Future is an unread failure.
  • Future.get() with no timeout is how services hang, and TimeoutException cancels nothing.
  • Unwrap ExecutionException.getCause() before logging, or the stack trace describes the framework instead of the bug.
  • thenApply is map; thenCompose is flatMap — if the function returns a future, compose.
  • Never put blocking work on ForkJoinPool.commonPool(); it has cores - 1 threads and is shared with every parallel stream in the JVM.
  • A non-async stage runs on whichever thread completed the previous one, which may be a client's I/O thread you must not block.
  • A periodic task that throws is cancelled forever, silently — wrap every scheduled task in try/catch (Throwable) and alert on staleness.
  • Use scheduleWithFixedDelay for polling; fixed rate runs back-to-back once the task exceeds the period.
  • shutdown() does not wait — only awaitTermination blocks, and shutdownNow only interrupts.
  • Size to the narrowest downstream limit: 180 threads behind 20 connections only moves the queue.
  • Never get() a task running in your own pool — nested dependent tasks deadlock deterministically at depth = pool size.
