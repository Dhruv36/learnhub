Common Pitfalls & Gotchas Professional

What you'll master: the traps that survive code review because they compile cleanly and pass tests — the Integer cache that makes == work for 127 and fail for 128, so the bug appears only in production; equals without hashCode and the key mutated after insertion, both of which lose data silently; why 0.1 + 0.2 != 0.3 and why BigDecimal.equals is not compareTo; remove(int) versus remove(Object); finally silently discarding an exception; a Comparator that throws "Comparison method violates its general contract"; SimpleDateFormat's thread-unsafety; and the default-locale bug that only manifests in Turkey. Prerequisites: the rest of this track.

Part 1 — Equality and Identity

  THE Integer CACHE — THE MOST DANGEROUS BEHAVIOUR IN THE LANGUAGE,
  BECAUSE THE FAILURE IS INVISIBLE IN TESTS.

    Integer a = 127, b = 127;    a == b   →  TRUE
    Integer c = 128, d = 128;    c == d   →  FALSE

  Autoboxing does not call `new`. It calls Integer.valueOf, which the
  JLS REQUIRES to return a cached instance for -128..127. Outside
  that range you get distinct objects, and == compares references.

  YOUR TEST USES id = 1. PRODUCTION USES id = 90210.

    if (order.getUserId() == user.getId())      // ❌ Integer == Integer
    if (Objects.equals(order.getUserId(), user.getId()))   // ✓

  WHAT IS CACHED:
    Boolean  both       Byte  all 256      Short/Integer/Long -128..127
    Character 0..127    Float/Double  NOTHING — Double x=1.0, y=1.0
                                      gives x == y  ALWAYS false

  equals WITHOUT hashCode — SILENT DATA LOSS.

    class Point { int x, y;
        public boolean equals(Object o) { … } }   // no hashCode

    var set = new HashSet<Point>();
    set.add(new Point(1, 2));
    set.contains(new Point(1, 2));    // FALSE

  Object.hashCode is identity-based, so two equal points land in
  different buckets and are never compared. The contract is
  one-directional and absolute:

    a.equals(b)  ⟹  a.hashCode() == b.hashCode()

  The reverse is NOT required — unequal objects may share a hash.

  MUTATING A KEY AFTER INSERTION — THE SAME FAILURE, LATER.

    var key = new Point(1, 2);
    map.put(key, "v");
    key.x = 99;                   // hash changed
    map.get(key);                 // null — wrong bucket
    map.remove(key);              // does nothing
    // the entry is now UNREACHABLE and UNREMOVABLE — a leak

  USE IMMUTABLE KEYS. A record gives you correct equals/hashCode and
  final fields in one line.

  == VS equals FOR STRINGS:

    "hello" == "hello"                 true  — both interned literals
    new String("hello") == "hello"     false — a distinct object
    ("hel" + "lo") == "hello"          true  — folded at COMPILE time
    (prefix + "lo") == "hello"         false — computed at RUNTIME

  The compile-time/runtime distinction is why this "works" in a test
  with literals and fails with real input.

Part 2 — Numbers

  FLOATING POINT CANNOT REPRESENT 0.1.

    0.1 + 0.2 == 0.3        →  false
    0.1 + 0.2               →  0.30000000000000004

  Binary fractions cannot express tenths, exactly as decimal cannot
  express 1/3. This is IEEE 754 working correctly.

  NEVER USE double FOR MONEY:

    double total = 0;
    for (int i = 0; i < 10; i++) total += 0.1;
    total == 1.0;                 // FALSE — 0.9999999999999999

  Use BigDecimal, or long minor units (cents) with the scale kept in
  your head.

  BigDecimal HAS ITS OWN TRAPS:

    new BigDecimal(0.1)      → 0.1000000000000000055511151231257827…
                               it copies the double's ERROR
    BigDecimal.valueOf(0.1)  → 0.1   (goes via Double.toString)
    new BigDecimal("0.1")    → 0.1   ← always prefer the String form

    new BigDecimal("1.50").equals(new BigDecimal("1.5"))  → FALSE
    new BigDecimal("1.50").compareTo(new BigDecimal("1.5")) == 0

  equals compares VALUE AND SCALE; compareTo compares value only.
  This makes BigDecimal dangerous in a HashSet or as a map key, and
  it is why a Money type should normalise the scale in its
  constructor.

  BigDecimal IS IMMUTABLE — a.add(b) RETURNS the result:

    total.add(item);          // ❌ discarded
    total = total.add(item);  // ✓

  And divide() throws ArithmeticException on a non-terminating
  result unless you supply a scale and rounding mode:

    a.divide(b, 2, RoundingMode.HALF_EVEN)

  INTEGER DIVISION TRUNCATES:

    5 / 2          →  2        (not 2.5)
    5 / 2.0        →  2.5
    (a + b) / 2    →  truncated, and can OVERFLOW

  OVERFLOW IS SILENT — IT WRAPS:

    Integer.MAX_VALUE + 1  →  Integer.MIN_VALUE   (no exception)
    Math.addExact(a, b)    →  throws ArithmeticException  ✓

  Use the *Exact methods anywhere a wrap would be a correctness bug.

  THE ONE NOBODY EXPECTS:

    Math.abs(Integer.MIN_VALUE)  →  Integer.MIN_VALUE  (NEGATIVE)

  There is no positive counterpart to MIN_VALUE in two's complement,
  so abs returns the input. Any "take the absolute value then index"
  code can produce a negative index.

  NaN BREAKS EVERY COMPARISON:

    Double.NaN == Double.NaN            false
    Double.valueOf(NaN).equals(NaN)     TRUE  ← inconsistent!
    Double.compare(NaN, NaN)            0     ← also "equal"

  equals and compare treat NaN as equal to itself so that sorting
  and collections work; == follows IEEE 754. Use Double.isNaN().

  ALSO:  -0.0 == 0.0 is true, but
         Double.valueOf(-0.0).equals(0.0) is FALSE.

Part 3 — Collections

  remove(int) VS remove(Object) — OVERLOAD RESOLUTION BITES.

    List<Integer> list = new ArrayList<>(List.of(10, 20, 30));
    list.remove(1);                  // removes INDEX 1 → [10, 30]
    list.remove(Integer.valueOf(1)); // removes the VALUE 1

  An int argument matches remove(int) exactly, so no boxing happens
  and the index overload wins. Only for List<Integer> does this
  ambiguity exist — and it silently removes the wrong element.

  ConcurrentModificationException — NOT ONLY ABOUT CONCURRENCY.

    for (String s : list) {
        if (s.isEmpty()) list.remove(s);   // ❌ CME, single-threaded
    }

  The for-each loop uses an iterator, which checks a modCount. The
  fixes:

    list.removeIf(String::isEmpty);              // ✓ best
    var it = list.iterator();                    // ✓ explicit
    while (it.hasNext()) if (it.next().isEmpty()) it.remove();

  AND NOTE IT IS BEST-EFFORT — removing the SECOND-TO-LAST element
  can complete without throwing, because hasNext() returns false
  before the check runs. Never write logic that depends on the
  exception.

  Arrays.asList AND List.of ARE BOTH "IMMUTABLE", DIFFERENTLY:

    Arrays.asList(arr).add(x)     UnsupportedOperationException
    Arrays.asList(arr).set(0, x)  WORKS — and writes through to arr
    List.of(a, null)              NullPointerException
    List.of(a).contains(null)     NullPointerException, not false

  Arrays.asList IS A VIEW over the array. It is not a defensive copy.

  ARRAY COVARIANCE — A HOLE IN THE TYPE SYSTEM:

    Object[] objects = new String[10];    // legal: arrays are covariant
    objects[0] = 42;                      // compiles
                                          // → ArrayStoreException

  Generics are invariant precisely to avoid this: List<Object> is
  not a List<String>, so the same mistake will not compile.

  Iterating a HashMap:

    map.keySet() then map.get(k)     two lookups per entry
    map.entrySet()                   one — always prefer it

  AND THE ONE THAT COSTS PRODUCTION MEMORY:

    new ArrayList<>()  grows 1.5x, HashMap doubles at 0.75 load.
    Pre-size when you know the count:
      new HashMap<>(expected / 0.75f + 1)

Part 4 — Strings, Text and Locale

  CONCATENATION IN A LOOP IS O(n²):

    String s = "";
    for (String x : items) s += x;      // a new String each iteration

    var sb = new StringBuilder();       // O(n)
    for (String x : items) sb.append(x);

  Outside a loop, `a + b + c` compiles to efficient code
  (invokedynamic since Java 9), so the rule is specifically about
  loops.

  split() TAKES A REGEX, NOT A LITERAL:

    "a.b.c".split(".")     →  an EMPTY array — "." matches anything
    "a.b.c".split("\\.")   →  [a, b, c]
    "a|b".split("|")       →  splits between every character

  And it DROPS trailing empty strings unless you ask:

    "a,b,,".split(",")      →  [a, b]
    "a,b,,".split(",", -1)  →  [a, b, "", ""]

  That silently loses trailing empty CSV fields.

  *** THE TURKISH LOCALE BUG ***

    "TITLE".toLowerCase()          in Turkey → "tıtle"
                                   (dotless ı, U+0131)
    "i".toUpperCase()              in Turkey → "İ" (dotted capital)

  So this fails only for Turkish users:

    if (header.toLowerCase().equals("content-type"))   // ❌

    if (header.toLowerCase(Locale.ROOT).equals("content-type"))  // ✓
    if (header.equalsIgnoreCase("content-type"))                 // ✓

  ALWAYS PASS Locale.ROOT for case changes on identifiers, keys,
  protocol tokens and file paths. Use the user's locale only for
  text the user reads.

  THE SAME APPLIES TO EVERY DEFAULT:

    String.format("%.2f", 1.5)     "1,50" in German locale
    new String(bytes)              platform default charset
    new FileWriter(f)              platform default charset
    Charset.defaultCharset()       differs between your laptop and
                                   the container

  Since Java 18, file.encoding defaults to UTF-8 (JEP 400) — but
  earlier versions, and any code passing bytes around, still need it
  stated explicitly:

    new String(bytes, StandardCharsets.UTF_8)
    Files.readString(path)         // UTF-8 by definition

  SimpleDateFormat IS NOT THREAD-SAFE:

    static final SimpleDateFormat FMT = new SimpleDateFormat("yyyy-MM-dd");
    // shared across threads → silently WRONG dates, or exceptions

  It keeps mutable Calendar state internally. Use
  DateTimeFormatter, which is immutable and thread-safe.

  substring() COPIES since Java 7u6. Before that it shared the
  parent's array, so a 2-character substring kept a 10 MB string
  alive. Modern substring is O(n) and leak-free — but old advice
  about "substring leaks" still circulates.

Part 5 — Control Flow and Initialisation

  finally SILENTLY DISCARDS EXCEPTIONS AND RETURNS:

    try {
        throw new RuntimeException("real problem");
    } finally {
        return "ok";           // ❌ the exception VANISHES
    }

  A return, break or continue in finally overrides whatever the try
  block was doing, INCLUDING a thrown exception. Never put a control
  transfer in a finally block.

  THE SUBTLER VERSION — an exception thrown while closing:

    InputStream in = null;
    try { in = open(); read(in); }
    finally { in.close(); }     // if close() throws, it REPLACES the
                                // real exception from read()

  try-with-resources fixes this properly: the close exception is
  SUPPRESSED and attached to the primary one, retrievable via
  getSuppressed().

  RETURN VALUE VS finally MUTATION:

    int x = 1;
    try { return x; } finally { x = 2; }    // returns 1

  The return value is evaluated BEFORE finally runs.

  switch FALLTHROUGH — still real in the classic form:

    switch (day) {
        case MONDAY: doA();          // falls through to TUESDAY!
        case TUESDAY: doB(); break;
    }

  The arrow form has no fallthrough at all:

    case MONDAY -> doA();

  and a switch EXPRESSION must be exhaustive, so the compiler
  catches a missing case.

  STATIC INITIALISER ORDER IS TOP TO BOTTOM:

    class Config {
        static final String URL = build();      // runs first
        static final String HOST = "localhost"; // still null above!
        static String build() { return HOST + "/api"; }  // "null/api"
    }

  A static method called from an earlier initialiser sees later
  fields at their DEFAULTS. Declaration order is program order.

  CIRCULAR CLASS INITIALISATION produces the same shape across two
  classes, and can also DEADLOCK when two threads initialise A and B
  simultaneously — class init holds a per-class lock.

  AND THE ERROR IT PRODUCES IS MISLEADING:

    ExceptionInInitializerError    the FIRST time — with the cause
    NoClassDefFoundError:
      Could not initialize class X    EVERY time after, in every
                                      thread, forever

  If you see "Could not initialize class", the real exception was
  logged ONCE, possibly hours earlier. Scroll back.

  CALLING AN OVERRIDABLE METHOD FROM A CONSTRUCTOR:

    class Base { Base() { init(); } void init() { } }
    class Child extends Base {
        private final List<String> items = new ArrayList<>();
        @Override void init() { items.add("x"); }   // NPE — items
    }                                               // is still null

  The superclass constructor runs before the subclass's field
  initialisers. Make the class or the method final.

Part 6 — Contracts, Concurrency and Resources

  *** "Comparison method violates its general contract!" ***

    IllegalArgumentException from Arrays.sort / Collections.sort

  TimSort DETECTS an inconsistent comparator and refuses to
  continue, because an invalid ordering can make it read out of
  bounds. The usual causes:

    NOT TRANSITIVE
      a < b and b < c but not a < c
    NOT ANTISYMMETRIC
      compare(a,b) and compare(b,a) both return the same sign
    SUBTRACTION OVERFLOW
      (a, b) -> a.value - b.value      // ❌ overflows for large or
                                       //    negative values
      Comparator.comparingInt(X::value)  // ✓
    NULL HANDLING that returns 0 for "either is null"
    A MUTABLE FIELD changed during the sort

  It appears only on inputs large enough for TimSort to use its
  merge path — typically 32+ elements — which is why it reaches
  production after passing small tests.

  Objects.equals / Comparator.nullsFirst handle nulls properly.

  Optional MISUSE:

    Optional<String> field;               // ❌ not Serializable,
                                          //    adds an allocation
    void m(Optional<String> p)            // ❌ callers must wrap;
                                          //    and can pass null!
    opt.get()                             // ❌ NoSuchElementException
    if (opt.isPresent()) opt.get()        // ❌ just an if with extra
                                          //    steps

    opt.orElse(default) / orElseGet(sup) / orElseThrow()   // ✓
    opt.map(...).filter(...).ifPresent(...)                // ✓

  Optional was designed as a RETURN type. Note orElse always
  evaluates its argument; orElseGet defers it — which matters when
  the default is expensive.

  AUTOBOXING NPE ON UNBOXING:

    Map<String,Integer> m = new HashMap<>();
    int count = m.get("missing");    // NPE — null.intValue()

    int count = m.getOrDefault("missing", 0);      // ✓

  The stack trace points at the assignment, with no visible method
  call. Also:

    Integer i = null;
    if (i == 0)                      // NPE
    boolean b = someBooleanObject;   // NPE if null

  SWALLOWED InterruptedException:

    catch (InterruptedException e) { }   // ❌ the flag was ALREADY
                                         //    cleared by the throw

    catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // restore
        return;                               // AND stop
    }

  RESOURCE LEAKS — try-with-resources or nothing:

    var in = new FileInputStream(f);
    process(in);                // if this throws, the stream leaks
    in.close();

    try (var in = new FileInputStream(f)) { process(in); }   // ✓

  It closes in REVERSE declaration order, and suppressed close
  exceptions are attached rather than lost. Note that a Stream from
  Files.lines() also needs closing — most streams do not, that one
  does.

  DOUBLE LOGGING:

    catch (Exception e) {
        log.error("failed", e);
        throw e;                 // the caller logs it AGAIN
    }

  Log OR rethrow. Logging and rethrowing produces the same stack
  trace multiple times and makes the real origin harder to find.

Interview Questions

Beginner: Why does Integer a = 127, b = 127; a == b differ from the same code with 128?

Autoboxing calls Integer.valueOf, which the language specification requires to return a cached instance for −128..127. Inside that range both variables reference the same object, so == is true. Outside it, two distinct objects are created and == compares references.

The danger is entirely in the test/production split. Unit tests use small ids, so == appears to work; production uses real ids and the comparison silently starts returning false. Nothing throws and nothing logs — orders just stop matching users.

The fix is Objects.equals(a, b), which is also null-safe.

Worth knowing what else is cached: Boolean always, Byte entirely, Short/Integer/Long at −128..127, Character 0..127 — and Float/Double never, so Double x = 1.0, y = 1.0; x == y is always false, with no lucky small-value pass.

Beginner: Why must you override hashCode whenever you override equals?

Because hash-based collections locate an object by its hash before comparing with equals. Object.hashCode is identity-based, so two equal objects get different hashes, land in different buckets, and are never compared.

set.add(new Point(1, 2));
set.contains(new Point(1, 2));   // false — different bucket

The contract is one-directional and absolute: equal objects must have equal hash codes. The reverse is not required — unequal objects may collide, which is merely a performance concern.

The related trap is mutating a key after insertion: the hash changes, so the entry moves to a bucket nothing will look in. It becomes unreachable and unremovable, which is both a bug and a memory leak.

Both problems disappear if keys are immutable — and a record generates a correct equals/hashCode pair with final fields in one line.

Mid: Why does 0.1 + 0.2 != 0.3, and what do you use for money?

IEEE 754 binary floating point cannot represent tenths exactly, just as decimal cannot represent 1/3. 0.1 + 0.2 evaluates to 0.30000000000000004. This is the format working correctly, not a bug.

For money the errors compound: adding 0.1 ten times gives 0.9999999999999999. Across millions of transactions that becomes a reconciliation problem.

OptionNote
BigDecimal from a StringExact; the standard answer
long minor units (cents)Fast and exact; you track the scale yourself
doubleNever for money

BigDecimal has its own traps. new BigDecimal(0.1) copies the double's error, so always use the String constructor or valueOf. It is immutable, so total.add(x) without assignment does nothing. And equals compares scale as well as value, so 1.50 does not equal 1.5 — use compareTo(...) == 0, and normalise the scale in a Money type's constructor so the question stops arising.

Mid: What causes "Comparison method violates its general contract"?

An inconsistent Comparator. TimSort detects it and throws IllegalArgumentException rather than continuing, because an invalid ordering can make the merge read outside the array.

CauseExample
Subtraction overflow(a,b) -> a.value() - b.value() wraps for large or negative values
Not transitivea < b and b < c but not a < c
Not antisymmetriccompare(a,b) and compare(b,a) share a sign
Null handling returning 0Makes every null equal to everything
A mutable field changing mid-sortThe ordering is not stable during the sort

Subtraction is the usual culprit, and Comparator.comparingInt(X::value) fixes it — it compares rather than subtracts.

Why it reaches production: TimSort only uses the merge path that detects this on inputs of roughly 32 elements or more. Small test datasets sort with a simple insertion sort and never notice.

The error message is unhelpfully generic, so when you see it, go straight to the comparator and look for subtraction or a special-case return of 0.

Senior: Which of these bugs would survive code review, and why?

The dangerous ones share a property: they compile cleanly, pass tests, and fail on data the test suite does not contain.

BugWhy review misses it
== on boxed integersWorks for small values — the test data
Missing hashCodeThe equals is present and correct-looking
toLowerCase() without a localeOnly fails in Turkish, and nobody tests that locale
Comparator subtractionOnly throws above ~32 elements
Shared SimpleDateFormatFails only under concurrency, and silently
Default charsetLaptop and container differ
Static init orderReads as ordinary field declarations

The obvious ones are less dangerous — double for money, string concatenation in a loop and return in a finally all look wrong to a careful reader.

The defence is not more careful reading, it is tooling. ErrorProne and SpotBugs catch boxed ==, missing hashCode, locale-dependent calls and default-charset use mechanically, with no reviewer attention required. That is a much better use of the constraint than asking humans to notice.

The second defence is design. Records make equals/hashCode consistent by construction; a Money type makes double unrepresentable; DateTimeFormatter is immutable so the concurrency bug cannot occur. Removing the possibility beats detecting the instance.

Senior: A service works locally and mis-handles data in production. What locale and charset issues would you check?

Environment-dependent defaults, which is a category people forget exists until it costs them a day.

DefaultHow it bites
Charset.defaultCharset()UTF-8 on a Mac, possibly not in a minimal container — mojibake on non-ASCII
Locale.getDefault()String.format("%.2f", 1.5) gives "1,50" in German — breaking a generated CSV or JSON
toLowerCase() / toUpperCase()Turkish dotless ı breaks header, key and path comparison
TimeZone.getDefault()The container is UTC, the laptop is not — dates shift by hours
new String(bytes), new FileWriter(f)Decode and encode with whatever the platform decided

The fix is to state everything explicitly: StandardCharsets.UTF_8 on every conversion, Locale.ROOT for anything machine-readable, an explicit ZoneId, and Files.readString/writeString, which are UTF-8 by definition.

JEP 400 (Java 18) made file.encoding default to UTF-8, which removes a large part of the charset half — but only for code that relies on the default, and only on 18+. Any code passing bytes around still needs the charset stated.

How to catch it before production: run the test suite under a hostile configuration — -Duser.language=tr -Duser.country=TR -Dfile.encoding=ISO-8859-1 -Duser.timezone=Pacific/Auckland. If it passes there, these bugs are absent. That is a two-line CI job and it finds an entire class of defect that no amount of review will.

-XX:AutoBoxCacheMax=n raises the upper bound, which makes more broken code accidentally work — so it makes the bug harder to find rather than easier. Never rely on it.

2 (easy): What does each line do? 
List<Integer> list = new ArrayList<>(List.of(10, 20, 30));
list.remove(1);
list.remove(Integer.valueOf(30));
System.out.println(list);
Solution 
[10, 20, 30]
list.remove(1)                    → removes INDEX 1  → [10, 30]
list.remove(Integer.valueOf(30))  → removes VALUE 30 → [10]
prints: [10]

Overload resolution prefers an exact match without boxing. List has both remove(int index) and remove(Object o); an int literal matches the first exactly, so no autoboxing occurs and the index overload wins.

CallResolves to
remove(1)remove(int) — by index
remove(Integer.valueOf(1))remove(Object) — by value
remove((Integer) 1)remove(Object)

This ambiguity exists only for List<Integer>, which is what makes it so easy to miss — the same code on a List<String> behaves exactly as written.

And it fails silently. If the index happens to be valid, you remove the wrong element and no exception occurs; only an out-of-range index reveals the mistake.

4 (medium): What does this return, and why? 
public String process() {
    try {
        throw new IllegalStateException("failed");
    } finally {
        return "ok";
    }
}
Solution

It returns "ok", and the exception disappears completely. A control transfer in finally — return, break or continue — overrides whatever the try block was doing, including a propagating exception.

Nothing is logged. The caller sees a successful result from a method that failed.

CaseResult
return in finallyDiscards the exception silently
throw in finallyReplaces the original exception, losing the real cause
int x = 1; try { return x; } finally { x = 2; }Returns 1 — the value is evaluated before finally runs

The realistic version of this bug is close() in a finally. If the body throws and then close() also throws, the close exception replaces the real one:

try (var in = new FileInputStream(f)) { process(in); }

try-with-resources handles it correctly — the close exception is suppressed and attached to the primary one, retrievable through getSuppressed(). That is the concrete reason to prefer it over a manual finally, beyond the brevity.

The rule: never transfer control out of a finally block. Static analysis flags it, and it has no legitimate use.

5 (hard): This sorts fine in tests and throws in production. Why? 
orders.sort((a, b) -> (int) (a.getAmount() - b.getAmount()));
// java.lang.IllegalArgumentException:
//   Comparison method violates its general contract!
Solution

Subtraction overflow, plus a lossy cast. getAmount() returns a long; the difference can exceed int range, and the cast truncates — so a genuinely large positive difference can come out negative.

a = 3,000,000,000L   b = -3,000,000,000L
a - b = 6,000,000,000L
(int) 6,000,000,000L = 1,705,032,704     // truncated
// and other pairs truncate to the WRONG SIGN, breaking transitivity
orders.sort(Comparator.comparingLong(Order::getAmount));   // fix
Why it passes testsWhy it fails in production
Small amounts never overflowReal amounts do
Under ~32 elements, TimSort uses insertion sort and never checksLarger lists take the merge path, which validates

TimSort throws rather than returning a wrong order because an inconsistent comparator can make the merge read outside the array. The check is a safety measure, not a strictness preference.

The other causes of the same message are worth knowing: a comparator that returns 0 when either side is null (making every null equal to everything), one that is not antisymmetric, and a mutable field being changed while the sort runs.

Never write subtraction in a comparator. Comparator.comparingInt / comparingLong / comparingDouble compare rather than subtract, and read better.

public class Report {
    private static final String BASE = "/var/reports";      // FIRST
    private static final Path DIR = Path.of(BASE, "daily");

    public void write(List<Row> rows) throws IOException {
        try (var w = Files.newBufferedWriter(DIR.resolve("out.csv"),
                                             StandardCharsets.UTF_8)) {
            for (Row r : rows) {                       // stream, no
                w.write(escape(r.name()));             // accumulation
                w.write(',');
                w.write(String.format(Locale.ROOT, "%.2f", r.amount()));
                w.write('\n');
            }
        }
    }
}

The static-order bug is the one that hides in plain sight. Both fields are static final and look declarative, but declaration order is program order — a method called from an earlier initialiser sees later fields at their defaults. It produces "null/daily" with no error at all.

The locale bug is the one that reaches customers. A German-locale JVM formats 1.5 as "1,50", which inserts a delimiter into a comma-separated file. Locale.ROOT is mandatory for anything machine-readable.

Writing incrementally instead of accumulating fixes both the O(n²) concatenation and the memory ceiling — the original cannot handle a report larger than the heap.

🎯 Key Takeaways

  • == on boxed integers works for −128..127 and fails above — passes tests, fails in production.
  • Float and Double are never cached, so boxed == on them is always false.
  • Override hashCode whenever you override equals, or objects vanish from hash collections.
  • A key mutated after insertion becomes unreachable and unremovable — use immutable keys.
  • Never use double for money; and use new BigDecimal("0.1"), never the double constructor.
  • BigDecimal.equals compares scale — use compareTo(...) == 0 for value equality.
  • Integer overflow is silent, and Math.abs(Integer.MIN_VALUE) is negative.
  • list.remove(1) removes an index, not a value, on a List<Integer>.
  • ConcurrentModificationException is single-threaded and best-effort — never depend on it firing.
  • Arrays.asList is a view whose set writes through to the array.
  • split takes a regex and drops trailing empty strings unless you pass -1.
  • Pass Locale.ROOT for machine-readable case changes and formatting — the Turkish locale breaks identifier comparison.
  • State the charset explicitly; the platform default differs between your laptop and the container.
  • SimpleDateFormat is not thread-safe — use DateTimeFormatter.
  • A return in finally silently discards the exception; use try-with-resources, which suppresses rather than replaces.
  • Static initialisers run top to bottom, so an earlier one sees later fields at their defaults.
  • Never call an overridable method from a constructor — the override runs before the subclass's fields exist.
  • Never subtract in a Comparator; overflow breaks transitivity and TimSort throws above ~32 elements.
  • Unboxing a null throws with no visible method call in the stack trace.
  • Run your test suite under a hostile locale, charset and timezone — it finds a whole class of bug that review will not.
