Design Patterns in Java Professional Java

What you'll master: that a pattern is a name for a recurring solution and the vocabulary is most of its value — and that a pattern applied without its problem is just complexity with a respectable label; which patterns the language absorbed, so Strategy is now a lambda, Command a Runnable, Iterator a for-each, Template Method a default method; Builder against the telescoping constructor; Singleton done correctly and why DI usually replaces it; why clone() is broken; Decorator through java.io; the proxy self-invocation trap that silently disables @Transactional; and how sealed types plus pattern matching retire Visitor. Prerequisites: Interfaces.

Part 1 — What a Pattern Actually Is

  A PATTERN IS FOUR THINGS. MOST PEOPLE MEMORISE ONLY THE THIRD.

    1. A NAME         "that's a Strategy" ends a design discussion in
                      three words instead of three whiteboards.
    2. A PROBLEM      the situation, and the FORCES that make it hard.
    3. A SOLUTION     the arrangement of types and calls.
    4. CONSEQUENCES   what it costs. Never zero.

  THE NAME IS MOST OF THE VALUE. The Gang of Four book (1994) did not
  invent these arrangements — people were already writing them. What it
  did was give them shared names, so a reviewer could say "this wants to
  be a Decorator" and the author knew what was meant, including the
  drawbacks, without a diagram.

  That is why learning patterns is worth an afternoon and why treating
  them as a construction kit is worth a rewrite.

  THE STANDING WARNING:

    A pattern applied WITHOUT its problem is not design.
    It is complexity with a respectable name attached.

  Concretely — the four you will meet in real code review:

    AbstractRequestHandlerFactoryBuilder    one implementation, ever
    StrategyContext with one Strategy       an if statement, expanded
    SingletonConfigManager                  a global variable
    VisitorAcceptingNodeVisitor             a switch, spread over
                                            eleven files

  Each of these was a correct pattern. Each was applied to a problem
  the codebase did not have. The result is strictly worse than the
  naive code, because the naive code can be read top to bottom.

  HOW TO TELL WHETHER YOU HAVE THE PROBLEM

  A pattern responds to a FORCE — something that varies at runtime, or
  is going to change. So ask what varies. Nothing varies -> you do not
  have the problem; write the code. Everything varies -> you do not
  understand the domain yet, and no pattern rescues that.

  THE RULE OF THREE is the practical version: write it concretely,
  write it again for the second case, extract the abstraction on the
  THIRD — when you can finally SEE what varies instead of guessing.
  An abstraction extracted from three real cases fits. One designed
  from one real case and two imagined ones does not, and is much
  harder to remove than to have never written.

Part 2 — The Patterns the Language Absorbed

  HALF THE GoF CATALOGUE WAS A WORKAROUND FOR A LANGUAGE THAT HAD NO
  FIRST-CLASS FUNCTIONS. Java got them in 8. Those patterns did not
  become wrong — they became one-liners, and writing the 1994 class
  hierarchy for them is now the anti-pattern.

  STRATEGY, 1994:

    interface Discount { BigDecimal apply(BigDecimal p); }
    class TenPercentOff implements Discount { … }
    class NoDiscount    implements Discount { … }
    checkout(new TenPercentOff());

  STRATEGY, TODAY:

    checkout(p -> p.multiply(new BigDecimal("0.9")));

  Same pattern. The interface is still there — it is
  UnaryOperator<BigDecimal> or your own one-method interface — but the
  implementations stopped needing names and files.

  COMMAND, 1994: an interface with execute(), a concrete class per
  action, an invoker that holds a list of them.
  COMMAND, TODAY: Runnable. That is the entire pattern. The undo
  variant still needs a real type, because Runnable has one method:

    interface Command { void execute(); void undo(); }

  ITERATOR, 1994: hasNext()/next() written by hand.
  ITERATOR, TODAY: implement Iterable and use for-each. You write an
  Iterator only when you are the collection.

  OBSERVER, 1994: Subject, Observer, attach/detach/notify.
  OBSERVER, TODAY: a List<Consumer<Event>>, or an event bus, or a
  Flow.Publisher if you need backpressure. java.util.Observer was
  deprecated in Java 9 and removed later — it had no ordering
  guarantee, no thread-safety story, and no way to carry typed events.

  TEMPLATE METHOD, 1994: an abstract class with a final algorithm
  method calling abstract hooks.
  TEMPLATE METHOD, TODAY: often a default method, or better, a
  higher-order function that takes the varying step as a parameter:

    // inheritance version — subclass to vary one step
    abstract class Import {
        final void run() { open(); parse(); close(); }
        protected abstract void parse();
    }

    // function version — no subclass, no hierarchy
    void run(Consumer<Reader> parse) {
        try (Reader r = open()) { parse.accept(r); }
    }

  The function version composes; the inheritance version forces every
  variation into one hierarchy and gives the subclass access to your
  protected fields forever.

  HOW TO RECOGNISE THAT THE MODERN FORM IS ENOUGH:

    - The abstraction has exactly ONE method.
    - The implementations have NO STATE.
    - No implementation is referred to BY NAME anywhere else.
    - Nobody needs to enumerate the implementations.

  All four true -> a lambda. Any one false and a named type starts
  paying for itself: a stateful strategy needs fields, a user-selected
  strategy needs a name to map from, and an enumerable set of
  strategies wants an enum:

    enum Rounding implements UnaryOperator<BigDecimal> {
        UP   { public BigDecimal apply(BigDecimal v) { … } },
        DOWN { public BigDecimal apply(BigDecimal v) { … } };
    }

  An enum implementing a functional interface is the sweet spot people
  miss: named, enumerable, serialisable, switchable, exhaustive — and
  still one file.

Part 3 — Creational Patterns

  BUILDER — THE PROBLEM IT ACTUALLY SOLVES

  It is not "objects with many fields". It is the TELESCOPING
  CONSTRUCTOR:

    Pizza(int size)
    Pizza(int size, boolean cheese)
    Pizza(int size, boolean cheese, boolean pepperoni)
    Pizza(int size, boolean cheese, boolean pepperoni, boolean bacon)

  Two failures, both real:

    1. new Pizza(12, true, false, true)
       Unreadable at the call site. Which boolean is bacon?

    2. new Pizza(12, false, true, true)
       and
       new Pizza(12, true, false, true)
       Both compile. Only one is what you meant. The compiler cannot
       help because every parameter has the same type.

  THE JAVABEANS ALTERNATIVE IS WORSE:

    Pizza p = new Pizza();
    p.setSize(12);
    p.setCheese(true);      // and if you forget setSize?

  The object is now MUTABLE and can exist in a half-built,
  invariant-violating state between the calls. You have traded a
  readability problem for a correctness one.

  BUILDER FIXES BOTH:

    Pizza p = Pizza.builder()
                   .size(12)
                   .cheese(true)
                   .bacon(true)
                   .build();          // validation happens HERE

  Named parameters at the call site, and the object is constructed
  exactly once, fully, immutably. build() is the single place where
  invariants are checked — throw there, not in each setter.

  WHEN YOU DO NOT NEED ONE:

    - Three or fewer parameters of DIFFERENT types. A constructor is
      shorter and just as clear.
    - A record with all fields required. The canonical constructor
      already names them in order, and the compiler checks arity.

  MODERN SHORTCUTS:

    @Builder                Lombok, generates the whole thing. Costs
                            you an annotation processor and a class
                            you cannot read in the source.
    record + withers        for evolving an immutable value:

      record Pizza(int size, boolean cheese, boolean bacon) {
          Pizza withBacon(boolean b) {
              return new Pizza(size, cheese, b);
          }
      }

  Withers are hand-written today (a proposal exists to generate them).
  For 3-4 components they are fine; past that, a builder is less code
  and far less copy-paste risk — a wither that forgets to pass one
  component silently resets it to the default.
  FACTORY METHOD vs ABSTRACT FACTORY — THE DISTINCTION PEOPLE BLUR

  FACTORY METHOD: ONE product, and a SUBCLASS decides which concrete
  type to make.

    abstract class Dialog {
        abstract Button createButton();       // the factory method
        void render() { createButton().paint(); }
    }
    class WindowsDialog extends Dialog {
        Button createButton() { return new WindowsButton(); }
    }

  ABSTRACT FACTORY: a FAMILY of related products that must match each
  other, behind one interface.

    interface UiKit {
        Button   button();
        Checkbox checkbox();
        Menu     menu();
    }
    class MacKit implements UiKit { … }     // all Mac-styled

  The point of Abstract Factory is the CONSISTENCY CONSTRAINT: you
  must not end up with a Mac button next to a Windows checkbox. If
  there is no such constraint between your products, you do not have
  an Abstract Factory — you have several unrelated factories, and
  bundling them into one interface only couples them.

  AND THE THING PEOPLE ACTUALLY WANT MOST OF THE TIME:

  A STATIC FACTORY METHOD. Not a GoF pattern at all, and more useful
  than both:

    Optional.of(x)           List.of(a, b)
    Integer.valueOf(5)       EnumSet.noneOf(Color.class)
    Duration.ofSeconds(30)   BigDecimal.valueOf(0.1)

  What it buys over a constructor:

    - IT HAS A NAME. BigInteger.probablePrime(bits, rnd) versus a
      third BigInteger(int, int, Random) overload.
    - IT NEED NOT CREATE. Integer.valueOf hits a cache; Optional.empty
      returns a shared instance; Collections.emptyList allocates
      nothing.
    - IT CAN RETURN A SUBTYPE. List.of returns a different class for
      1, 2 and N elements, and callers never know.

  Cost: no subclassing (a class with only private constructors is
  effectively final), and it is not discoverable in the "new" list of
  an IDE.
  SINGLETON — DONE CORRECTLY, AND WHY YOU PROBABLY SHOULD NOT

  ❌ THE VERSION IN MOST TUTORIALS:

    class Config {
        private static Config instance;
        static Config getInstance() {
            if (instance == null) instance = new Config();  // race
            return instance;
        }
    }

  Two threads can both see null and both construct. Adding
  synchronized to the whole method fixes it but locks on every read.
  Double-checked locking fixes that but is silently broken without
  volatile — a second thread can see a non-null reference to a
  PARTIALLY CONSTRUCTED object.

  ✅ THE STATIC HOLDER — lazy, thread-safe, no synchronisation:

    class Config {
        private Config() { }
        private static class Holder {
            static final Config INSTANCE = new Config();
        }
        static Config getInstance() { return Holder.INSTANCE; }
    }

  It works because the JVM guarantees class initialisation happens
  exactly once, under a lock it manages, and Holder is not initialised
  until first touched. Zero cost after the first call.

  ✅ THE ENUM — the shortest correct one:

    enum Config {
        INSTANCE;
        private final Properties props = load();
    }

  Serialisation-safe and reflection-safe for free:
  Constructor.newInstance() on an enum throws
  IllegalArgumentException, and readResolve is handled by the runtime.
  Neither of the other forms survives a determined attacker or a
  careless deserialiser without extra code.

  NOW THE HONEST PART.

  A singleton is GLOBAL MUTABLE STATE with an approving name. What it
  costs you:

    TESTS       Every test shares one instance. Test A's mutation
                leaks into test B, and the failures depend on JUnit's
                execution order.
    SUBSTITUTION No way to swap in a fake. Your test now needs a real
                database because Config.getInstance() opened one.
    LIFECYCLE   No control over creation order or shutdown, and class
                initialisation failure surfaces as
                ExceptionInInitializerError — then NoClassDefFoundError
                on every subsequent access, which hides the real cause.
    CONCURRENCY If it holds mutable state, every field is shared
                across every thread in the process.

  WHAT TO DO INSTEAD: create ONE instance and pass it in.

    class OrderService {
        private final Config config;
        OrderService(Config config) { this.config = config; }
    }

  Spring's @Singleton scope is exactly this: one instance, injected,
  and trivially replaceable in a test. "One instance" is a LIFECYCLE
  decision that belongs to whoever wires the application — not a
  property the class should enforce on everyone.

  Legitimate uses remain: a stateless helper, a genuinely
  process-global resource (a logger backend, a metrics registry), and
  an enum used as a null object.
  PROTOTYPE, AND WHY clone() IS BROKEN

  The intent — "copy this object rather than construct one" — is
  reasonable. Java's implementation of it is not.

  FOUR THINGS WRONG WITH Object.clone():

  1. Cloneable HAS NO clone() METHOD. It is a marker interface that
     changes what the protected Object.clone() does. An interface that
     modifies the behaviour of a method it does not declare is a
     design mistake the JDK team has publicly acknowledged.

  2. THE COPY IS SHALLOW. Object.clone() copies fields bit by bit, so
     every reference field is SHARED with the original:

       class Stack implements Cloneable {
           private Object[] elements;
           public Stack clone() {
               return (Stack) super.clone();   // shares the array!
           }
       }

     Mutating the clone corrupts the original. You must deep-copy
     every mutable field by hand and remember to update clone() every
     time a field is added.

  3. IT FIGHTS final. A field you must reassign during cloning cannot
     be final — so making a class cloneable pushes you toward
     mutability.

  4. NO CONSTRUCTOR RUNS. Invariants established in the constructor
     are simply not established, and neither is anything a subclass
     needs.

  USE A COPY CONSTRUCTOR OR A STATIC COPY FACTORY:

    Stack(Stack other) {
        this.elements = other.elements.clone();   // arrays are fine
        this.size     = other.size;
    }

  Arrays are the exception: arr.clone() is the idiomatic, correct way
  to copy an array (still shallow for object arrays — the elements
  are shared).

  BEST OF ALL: MAKE THE OBJECT IMMUTABLE and copying disappears as a
  problem. A record needs no clone because nothing can mutate it, and
  "copy with one field changed" is a wither.

  ADAPTER vs DECORATOR — THE ONE-SENTENCE TEST

    Does the wrapper implement the SAME interface as the thing it
    wraps?

      Yes -> Decorator. It adds behaviour; it composes; it nests.
      No  -> Adapter. It converts; it does not nest.

  That is the whole distinction, and it is the question interviewers
  actually ask.

    // Adapter: byte world -> char world. Different interfaces.
    Reader r = new InputStreamReader(socket.getInputStream(), UTF_8);

    // Decorator: Reader -> Reader. Same interface, buffering added.
    Reader b = new BufferedReader(r);

  DECORATOR, WITH java.io AS THE WORKED EXAMPLE

  java.io is the most-cited Decorator in existence, and also the best
  argument about its cost.

    InputStream in =
        new GZIPInputStream(
            new BufferedInputStream(
                new FileInputStream("data.gz")));

    Composition, outermost first:

      GZIPInputStream        decompresses
        └── BufferedInputStream   reads 8 KB at a time
              └── FileInputStream    one syscall per read()

  Read one byte from the outermost and the call travels down the
  chain; the buffer means the file stream is touched roughly once per
  8192 bytes instead of once per byte. That is a measured 10-50x
  difference on a byte-at-a-time read loop, because each unbuffered
  read() is a syscall costing hundreds of nanoseconds to a few
  microseconds.

  WHY THIS BEATS INHERITANCE: the alternative is a class per
  combination — BufferedGzipFileInputStream,
  BufferedEncryptedFileInputStream — and the count multiplies. With
  decorators you get every combination from N classes, chosen at
  RUNTIME.

  WHAT IT COSTS — say this out loud in an interview:

    1. READABILITY. Three nested constructors to read a file is the
       standard complaint about java.io, and it is fair. Compare:

         Files.readAllLines(path)          // Facade, one call

    2. YOU MUST KNOW THE ORDER. Buffering outside decompression
       buffers compressed bytes; buffering inside buffers the file.
       Both "work", with different performance. Nothing warns you.

    3. DIAGNOSTICS DEGRADE. A stack trace through five decorators is
       five frames of plumbing before the frame you care about, and
       a debugger shows you a doll of wrappers.

    4. IDENTITY IS LOST. The decorated object is not the original;
       equals, instanceof and any type test now see the wrapper.
       This is why you can never unwrap a decorated stream to get at
       the FileInputStream's FileDescriptor.

  FACADE is the answer to complaint 1, and the JDK applies it to its
  own API: java.nio.file.Files is a facade over channels, buffers and
  charsets. Note that a facade does not REMOVE the subsystem — the
  decorators are still there when you need them. It adds the easy
  path without deleting the powerful one, which is exactly the right
  shape for a facade.
  PROXY — THE PATTERN YOUR FRAMEWORK ALREADY USES ON YOUR CODE

  Same interface as the target; controls access to it. Four flavours:

    VIRTUAL      delay expensive creation  -> Hibernate lazy loading
    PROTECTION   check permissions first   -> Spring Security
    REMOTE       local stand-in for remote -> RMI, gRPC stubs
    SMART        add behaviour on access   -> @Transactional, caching,
                                             metrics, retries

  HOW SPRING BUILDS ONE. When you write:

    @Service
    class OrderService {
        @Transactional
        public void placeOrder(Order o) { … }
    }

  the bean in the context is NOT an OrderService you wrote. It is
  either a JDK dynamic proxy (if OrderService implements an
  interface) or a CGLIB subclass, and it looks like:

    class OrderService$$Proxy extends OrderService {
        public void placeOrder(Order o) {
            tx.begin();
            try { super.placeOrder(o); tx.commit(); }
            catch (RuntimeException e) { tx.rollback(); throw e; }
        }
    }

  Hibernate does the same for a @ManyToOne: the field holds a proxy
  subclass whose first getter call fires the SELECT. That is why
  touching a lazy association outside a session throws
  LazyInitializationException — the proxy is alive, the session that
  could load it is gone.

  ⚠ THE SELF-INVOCATION TRAP — the single most common Spring bug:

    @Service
    class OrderService {
        public void process(List<Order> orders) {
            for (Order o : orders) save(o);     // ❌ no transaction
        }
        @Transactional
        public void save(Order o) { … }
    }

    CALL FROM OUTSIDE:            CALL FROM INSIDE:

      caller                        proxy.process()
        └─> proxy.save()              └─> this.save()   ← plain
              └─> tx.begin()                              field access
                    └─> real.save()                       on the REAL
                                                          object.
                                                    NO PROXY. NO TX.

  The proxy wraps the OBJECT, not the class. Once control is inside
  the real object, this.save() is an ordinary virtual call and the
  proxy is not in the path. The annotation is silently ignored — no
  warning, no exception, just no transaction, discovered when a
  partial failure leaves half the orders committed.

  THE SAME TRAP APPLIES TO @Cacheable, @Async, @Retryable, @PreAuthorize
  and every other proxy-based annotation.

  FIXES, best first:

    1. MOVE save() TO ANOTHER BEAN and inject it. The call is then a
       real proxy call. Also better design — the transaction boundary
       becomes visible in the type graph.
    2. INJECT THE BEAN INTO ITSELF (@Lazy self-reference) and call
       self.save(). Works, looks strange, needs a comment.
    3. AopContext.currentProxy() — requires exposeProxy=true and ties
       your code to Spring's AOP internals. Last resort.
    4. Switch to AspectJ load-time weaving, which rewrites the
       bytecode and has no proxy at all. Heavy for one method.

  TWO MORE CGLIB CONSEQUENCES worth knowing:
    - A final method cannot be overridden, so it cannot be advised.
      @Transactional on a final method does nothing, silently.
    - A private method is not overridable either. Same silent result.
  FLYWEIGHT — SHARING IMMUTABLE INSTANCES

  Intent: when a program would allocate millions of structurally
  identical immutable objects, share them instead. Requires
  immutability; otherwise one holder's mutation is everyone's.

  THE JDK DOES THIS TO YOU IN TWO PLACES, AND BOTH SURPRISE PEOPLE:

  1. THE Integer CACHE. Integer.valueOf caches -128..127, so:

       Integer a = 127, b = 127;   a == b   -> true
       Integer c = 128, d = 128;   c == d   -> false

     Autoboxing calls valueOf, so this applies to every boxed int in
     your code. The upper bound is tunable with
     -XX:AutoBoxCacheMax=<n>; the lower bound is fixed by the JLS,
     which REQUIRES caching in -128..127 and permits it elsewhere.
     Byte, Short, Long and Character have the same range; Boolean
     caches both values; Float and Double cache nothing.

  2. THE STRING POOL. Every string LITERAL is interned, so two
     identical literals are the same object. A string built at
     runtime is not:

       "hi" == "hi"                        true
       "h" + getI() == "hi"                false
       ("h" + getI()).intern() == "hi"     true

  Both are why == on boxed types and strings is a bug rather than a
  style choice: it works for small numbers and literals, which is
  exactly the range your unit test uses, and fails in production on
  128 or on a string that came from a request.

  WHEN TO BUILD ONE YOURSELF: rarely, and only with a measurement.
  The pattern trades allocation for a lookup (a map hit, ~20-50 ns)
  plus the cache's own memory, and the JVM's allocation is a pointer
  bump of a few nanoseconds. It pays when the object is large, lives
  long, and repeats enormously — interning a few thousand distinct
  status codes across 50 million rows, not caching Point objects.

Part 5 — Behavioural Patterns

  STATE vs STRATEGY — IDENTICAL SHAPE, OPPOSITE INTENT

  Structurally they are the same diagram: a context holding a
  reference to an interface with several implementations. Interviewers
  ask because the difference is entirely about intent and who does the
  switching.

    STRATEGY                        STATE
    ────────────────────────        ──────────────────────────────
    The CLIENT picks.               The OBJECT transitions itself.
    Implementations do not          Implementations know each other
    know each other.                (they name the next state).
    Interchangeable — any           Not interchangeable — a
    strategy is valid at any        transition to the wrong state is
    time.                           a bug.
    Varies an ALGORITHM.            Varies BEHAVIOUR OVER TIME.
    sort(list, comparator)          order: NEW -> PAID -> SHIPPED

  THE TELL: if an implementation ever sets the context's field to a
  different implementation, it is State. If nothing knows what comes
  next, it is Strategy.

  In Java, State is very often better as an enum with abstract
  methods:

    enum OrderState {
        NEW     { OrderState pay()  { return PAID; }     },
        PAID    { OrderState ship() { return SHIPPED; }  },
        SHIPPED { };

        OrderState pay()  { throw new IllegalStateException(this + " cannot pay");  }
        OrderState ship() { throw new IllegalStateException(this + " cannot ship"); }
    }

  You get an exhaustive, enumerable, switchable, serialisable state
  machine in one file, and illegal transitions fail loudly at the one
  place that defines them.

  CHAIN OF RESPONSIBILITY — PASS IT ALONG UNTIL SOMEONE HANDLES IT

  Every servlet filter chain, every Spring Security filter, every
  OkHttp interceptor, every Netty pipeline:

    request -> [auth] -> [rate limit] -> [logging] -> [gzip] -> handler
                  │            │
                  └── 401      └── 429      (short-circuit, chain
                                             stops here)

    class LoggingFilter implements Filter {
        public void doFilter(Req q, Res s, FilterChain chain) {
            long t0 = System.nanoTime();
            chain.doFilter(q, s);            // ← forward, or do not
            log(System.nanoTime() - t0);     // ← runs on the way back
        }
    }

  Two properties that make it worth the indirection:
    - ORDER IS CONFIGURATION, not code. Reordering filters changes
      behaviour without touching any of them.
    - A LINK CAN STOP THE CHAIN. Not forwarding is how auth rejects.

  Its cost is the flip side: the control flow is not visible in any
  one file. When a request mysteriously returns 403, the answer is in
  a registration list somewhere, not in a call stack you can read
  top-down. Log the chain order at startup and you take most of that
  cost back.

  OBSERVER — NOW JUST A LIST OF FUNCTIONS

    class Button {
        private final List<Consumer<Click>> listeners = new CopyOnWriteArrayList<>();
        void onClick(Consumer<Click> l) { listeners.add(l); }
        void click() { listeners.forEach(l -> l.accept(new Click())); }
    }

  Four things go wrong with every hand-rolled version, and exercise 4
  works through all of them: the subject strongly references each
  listener forever (the classic Swing/Android leak), a listener that
  unregisters itself during dispatch throws
  ConcurrentModificationException, one listener's exception silently
  cancels every later one, and notification runs on the NOTIFIER's
  thread — so a slow listener stalls the publisher.

  VISITOR — AND THE FEATURE THAT REPLACED IT

  Visitor exists to add operations to a fixed type hierarchy without
  editing every type, using double dispatch:

    interface Shape { <R> R accept(Visitor<R> v); }
    class Circle implements Shape {
        public <R> R accept(Visitor<R> v) { return v.visitCircle(this); }
    }
    interface Visitor<R> { R visitCircle(Circle c); R visitSquare(Square s); }

  That is a lot of ceremony. Java 21 gives you the same guarantee —
  including the exhaustiveness check that was Visitor's real
  attraction — for free:

    sealed interface Shape permits Circle, Square { }
    record Circle(double r)        implements Shape { }
    record Square(double side)     implements Shape { }

    double area(Shape s) {
        return switch (s) {
            case Circle(double r)    -> Math.PI * r * r;
            case Square(double side) -> side * side;
        };                    // no default: the compiler proves this
    }                         // covers every permitted subtype

  Add a Triangle to the permits clause and every such switch fails to
  compile until you handle it — exactly the safety Visitor bought,
  with none of the accept/visit plumbing and no visitor interface to
  change.

  VISITOR IS STILL RIGHT WHEN: the hierarchy is NOT sealed (a plugin
  API where third parties add types), or you must support Java 17 and
  earlier, or the traversal itself is complex and stateful (an AST
  walker accumulating scope as it descends).

  THE FOUR ANTI-PATTERNS YOU WILL SEE THIS QUARTER

  1. PATTERN-DRIVEN DESIGN — starting from the pattern.
     The symptom is a package named "patterns", or a design document
     that names patterns before it names the domain. Design responds
     to forces; patterns are a vocabulary for describing what you
     arrived at, not a menu to order from.

     TELL: you can describe the class by its pattern but not by what
     it does. "It's a facade over a factory" — over WHAT?

  2. A FACTORY THAT ONLY EVER MAKES ONE THING.

       class UserFactory {
           public static User create(String n) { return new User(n); }
       }

     This adds a file, an import and a level of indirection to hide
     the word "new". A factory earns its place when it CHOOSES among
     implementations, CACHES, VALIDATES, or gives a name to an
     overload. Choosing among one implementation is not choosing.

     A static factory method ON the class is different and often
     good — User.of(name) can validate and can later return a
     subtype. The problem is the separate class that does neither.

  3. AN INTERFACE WITH ONE IMPLEMENTATION.

       interface UserService { … }
       class UserServiceImpl implements UserService { … }

     The "Impl" suffix is the diagnostic: you could not think of a
     name for the difference because there is no difference. Costs:
     every navigation lands on the interface, every change touches
     two files, and the abstraction is shaped by its single
     implementation anyway, so it is not actually an abstraction.

     "For testing" is a weak defence — Mockito mocks concrete classes,
     and Spring proxies them with CGLIB. A MODULE OR PUBLISHED API
     BOUNDARY is a real one: there the interface is a contract you
     promise, and implementations may arrive from elsewhere.

     Otherwise, extract the interface when the SECOND implementation
     appears. That extraction is a one-keystroke IDE refactor; the
     interface designed for one implementation is not.

  4. A SINGLETON THAT SHOULD BE A DEPENDENCY.
     The tell is a test that fails only when run after another test,
     or a test that needs a real database. Every static getInstance()
     is an edge in your dependency graph that no tool can see and no
     test can cut.

  THE ONE SENTENCE TO KEEP:

    Patterns are a VOCABULARY for the design you arrived at,
    not a CATALOGUE to build from.

  Learn the names so you can read other people's code and defend
  yours in review. Reach for the simplest thing that solves the
  problem you can actually demonstrate you have.

Interview Questions

Beginner: What is a design pattern, and when should you not use one?

A design pattern is a named, reusable solution to a recurring design problem, described with four parts: a name, the problem and forces it addresses, the solution structure, and the consequences. The Gang of Four catalogued twenty-three of them in 1994 by observing what experienced designers already did.

The most valuable part is the name. "This wants to be a Decorator" communicates a structure, its benefits and its drawbacks in four words, which is the whole reason to learn the catalogue even if you never write a single one from the book.

You should not use one when you cannot state the problem it solves in your codebase. Every pattern adds indirection, and indirection is only worth it when something genuinely varies. A Strategy with one implementation is an if spread across three files; a factory that only calls one constructor hides the word new behind an import.

The practical guard is the rule of three: write it concretely, write it again when a second case arrives, and extract the abstraction on the third — when you can actually see what varies rather than guessing. Extracting an interface from two real implementations is a one-keystroke IDE refactor; removing an abstraction that was wrong is not.

Beginner: Adapter or Decorator — how do you tell them apart?

Ask one question: does the wrapper implement the same interface as the thing it wraps?

AdapterDecorator
Wrapper's interfaceDifferent from the wrapped typeSame as the wrapped type
PurposeConvert — make it fitAdd behaviour
Nests?No, one conversion is enoughYes, arbitrarily
JDK exampleInputStreamReader (bytes to chars)BufferedReader (Reader to Reader)

Both are wrappers, which is why they get confused. The consequence of the difference is composition: because a Decorator preserves the type, you can stack GZIPInputStream over BufferedInputStream over FileInputStream and get every combination of N behaviours from N classes, chosen at runtime. An Adapter has nothing to stack — once you are in the target interface, the conversion is done.

Arrays.asList is a good adapter to cite: it presents an array through the List interface without copying, which is also why the result is fixed-size and writes through to the array.

Mid: Implement a thread-safe Singleton, then argue against using it.

The two correct implementations:

// Static holder — lazy, no synchronisation on the hot path
class Config {
    private Config() { }
    private static class Holder { static final Config INSTANCE = new Config(); }
    static Config getInstance() { return Holder.INSTANCE; }
}

// Enum — the shortest thing that is correct
enum Config {
    INSTANCE;
    private final Properties props = load();
}

The holder works because the JVM guarantees class initialisation runs exactly once, under a lock the JVM owns, and Holder is not initialised until first referenced. The enum additionally survives serialisation and reflection: Constructor.newInstance on an enum throws, and the runtime handles readResolve.

The naive lazy version is a race — two threads can both see null. Double-checked locking fixes the race but is broken without volatile, because the reference can be published before the constructor's writes are visible, letting another thread use a partially constructed object.

Now the argument against it: a singleton is global mutable state. It makes tests order-dependent (every test shares one instance), it cannot be substituted with a fake, you have no control over creation order or shutdown, and initialisation failure surfaces as ExceptionInInitializerError followed by NoClassDefFoundError on every later access — which hides the original cause.

My recommendation: create one instance and inject it. Spring's singleton scope gives you exactly one instance with none of the costs, because "how many instances exist" is a lifecycle decision belonging to whoever wires the application, not a constraint the class should impose on everyone. I would write a real Singleton only for a stateless helper or a genuinely process-global resource, in a codebase with no container.

Mid: Which GoF patterns are obsolete in modern Java, and which are not?

Obsolete as class hierarchies, not as ideas. The patterns that existed to work around the absence of first-class functions collapsed into language features in Java 8, and sealed types plus pattern matching finished the job in Java 21.

PatternModern formStill write the classic version when
StrategyA lambda, or an enum implementing the interfaceThe strategy has state or must be selected by name
CommandRunnable / CallableYou need undo, serialisation, or a typed queue
IteratorIterable + for-each, StreamYou are the collection
ObserverA list of Consumer, or FlowBackpressure or lifecycle management matters
Template MethodA default method, or a function parameterMany steps vary together over shared state
Visitorsealed + switch patternsThe type set is open to third parties

What is not obsolete: Builder (the telescoping-constructor problem is a language limitation Java still has — no named or optional parameters), Decorator (composition of behaviour is not a function), Proxy (it is how every framework you use implements cross-cutting concerns), Facade, Adapter and Flyweight. These solve structural problems that no syntax removed.

The tell for "the lambda is enough" is four conditions together: the abstraction has one method, the implementations have no state, none is referenced by name elsewhere, and nobody needs to enumerate them. Break any one and a named type starts paying for itself.

Senior: A @Transactional method is not opening a transaction. Walk me through the diagnosis.

Spring implements @Transactional with a proxy. The bean in the context is not your class — it is a JDK dynamic proxy (if you implement an interface) or a CGLIB subclass, and it wraps begin/commit/rollback around the call before delegating to the real object. Everything that can go wrong follows from "the proxy wraps the object, not the class".

Check self-invocation first — it is the cause about eighty percent of the time. If another method on the same bean calls the annotated one through this, control is already inside the real object and the proxy is not in the call path. It is an ordinary virtual call; the annotation is silently ignored.

CauseWhy the advice never runsFix
Self-invocation (this.save())The proxy is not in the call pathMove to a separate bean; or inject a @Lazy self-reference
Method is finalCGLIB cannot override itRemove final
Method is private or package-privateNot overridable, so not advisableMake it public
The object was created with newIt never went through the container, so there is no proxyInject the bean
Checked exception thrownDefault rollback is on unchecked only — it commits@Transactional(rollbackFor = Exception.class)
The exception is caught inside the methodNothing propagates to the proxy, so nothing rolls backRethrow, or mark the transaction rollback-only
Called from a different thread (@Async, executor)The transaction context is thread-boundStart the transaction inside the new thread

How I would confirm it in five minutes: set logging.level.org.springframework.transaction=TRACE and look for "Creating new transaction" around the call. If it is absent, no advice ran — a proxy problem. If it is present but the data is missing, the transaction ran and rolled back — an exception or propagation problem. That single log line splits the search space in half.

The design lesson is that self-invocation is a symptom, not just a bug: a class calling its own transactional method usually has two responsibilities in it. Splitting the transactional unit into its own bean fixes the proxy issue and makes the transaction boundary visible in the type graph. I prefer that to AopContext.currentProxy(), which works but welds your business code to Spring's AOP internals for no design benefit.

Senior: A reviewer says your code "isn't using enough design patterns". How do you respond?

I would want to convert that into a specific question, because "more patterns" is never a goal. Patterns are a response to forces — something varying at runtime, something expected to change, a dependency that must be substitutable. If a pattern is missing, the right question is which force is currently unhandled.

So: which change is hard to make in this code as written? That is answerable and testable. If the answer is "adding a second payment provider means editing six files", we have a real Strategy or DIP problem and I will fix it. If the answer is "it doesn't look like the patterns book", we do not.

The cost of the opposite mistake is higher than people assume. Every speculative abstraction adds indirection to every read of the code, and a wrong abstraction is far more expensive than a missing one: adding an interface over two real implementations is a one-keystroke IDE refactor, whereas removing an interface whose shape was invented for a use case that never arrived means untangling every call site that adapted to it.

I would also point out the patterns that are present but unnamed, because this is often a vocabulary mismatch rather than a design disagreement. A Comparator parameter is a Strategy. A Consumer list is an Observer. A sealed interface with an exhaustive switch is a Visitor with the ceremony deleted. Code can be pattern-dense and contain zero classes named after a pattern.

Where I would concede: at module and published-API boundaries, where changing a signature later breaks other people's code, I will accept an abstraction on speculation, because the cost of being wrong is asymmetric. Inside a service that one team owns and can refactor in an afternoon, I would rather write the direct code, keep the rule of three, and extract when the second real case appears.

1 (easy): Replace this Strategy hierarchy with modern Java, and say when you would keep the classes. 
interface TaxCalculator { BigDecimal tax(BigDecimal amount); }

class ZeroTax implements TaxCalculator {
    public BigDecimal tax(BigDecimal a) { return BigDecimal.ZERO; }
}
class StandardTax implements TaxCalculator {
    public BigDecimal tax(BigDecimal a) { return a.multiply(new BigDecimal("0.20")); }
}

class Checkout {
    private final TaxCalculator calc;
    Checkout(TaxCalculator calc) { this.calc = calc; }
}
Solution

The interface has one method and the implementations have no state, so they are lambdas:

class Checkout {
    private final UnaryOperator<BigDecimal> tax;
    Checkout(UnaryOperator<BigDecimal> tax) { this.tax = tax; }
}

new Checkout(a -> BigDecimal.ZERO);
new Checkout(a -> a.multiply(new BigDecimal("0.20")));

Three files became zero. Keeping your own one-method interface instead of UnaryOperator is still worthwhile if the domain name matters — TaxCalculator reads better in a signature than UnaryOperator — but you still delete the two implementation classes.

ConditionLambda is enoughKeep a named type
Number of methodsOneTwo or more
State in the implementationNoneRate, locale, config
Referred to by name elsewhereNoYes — tests, config, logs
Must enumerate all of themNoYes — use an enum

Where the classes come back: the moment tax rates differ by country, the strategy has state and needs a name users can select. Then the best form is an enum:

enum TaxRegime implements UnaryOperator<BigDecimal> {
    NONE("0.00"), UK("0.20"), IE("0.23");
    private final BigDecimal rate;
    TaxRegime(String r) { this.rate = new BigDecimal(r); }
    public BigDecimal apply(BigDecimal a) { return a.multiply(rate); }
}

Named, enumerable, serialisable, switchable with exhaustiveness, and still one file. This is the form people skip past on the way from "class per strategy" to "lambda", and it is usually the right stop.

public class ConnectionPool {

Solution

The minimum correct version, keeping the singleton:

public final class ConnectionPool {
    private ConnectionPool() { }
    private static class Holder {
        static final ConnectionPool INSTANCE = new ConnectionPool();
    }
    public static ConnectionPool getInstance() { return Holder.INSTANCE; }

    private final BlockingQueue<Connection> free = new ArrayBlockingQueue<>(20);
}

The holder is lazy and thread-safe with no synchronisation on the hot path, because the JVM already initialises a class exactly once under its own lock, and Holder is not initialised until getInstance first touches it.

But a connection pool is the textbook case for not being a singleton. It owns an external resource with a lifecycle: it must be sized from configuration, health-checked, drained on shutdown, and replaced with a fake in tests. Every one of those is fought by a static accessor.

@Bean(destroyMethod = "close")
DataSource dataSource(DataSourceProperties props) { … }   // one instance, injected

What you actually want is one instance, and that is a wiring decision. Note also that the holder idiom hides initialisation failure badly: if the constructor throws, the first caller gets ExceptionInInitializerError and every subsequent caller gets NoClassDefFoundError with no trace of the original cause — a genuinely miserable production debug, and one more reason to let a container own construction.

3 (medium): Why does no transaction start, and what are three ways to fix it? 
@Service
public class ReportService {

    public void generateAll(List<Long> ids) {
        for (Long id : ids) {
            generateOne(id);
        }
    }

    @Transactional
    public void generateOne(Long id) {
        auditRepo.save(new Audit(id));
        reportRepo.save(buildReport(id));
    }
}
Solution

Self-invocation. The bean injected everywhere is a proxy that wraps ReportService. When a caller invokes generateAll, the proxy delegates to the real object — and from that point generateOne(id) is an implicit this.generateOne(id), an ordinary virtual call on the real object. The proxy is not in the path, so the transactional advice never runs.

caller  ->  proxy.generateAll()
              ->  real.generateAll()
                    ->  this.generateOne()      ← plain call, NO proxy
                          ->  two saves, each in its own auto-commit

The visible damage: each save commits independently, so a failure on the second leaves the Audit row committed with no report. The atomicity you annotated for does not exist.

FixHowTrade-off
Separate beanMove generateOne to ReportWriter and inject itBest design — the boundary becomes visible; one extra class
Self-injection@Lazy ReportService self; then self.generateOne(id)Smallest diff; looks odd and needs a comment
Annotate the callerPut @Transactional on generateAllOne transaction for the whole batch — changes the semantics
AopContext.currentProxy()Requires exposeProxy = trueCouples business code to Spring AOP internals

The third fix changes behaviour, and you must decide deliberately. With @Transactional on generateAll the whole batch is one transaction: an id-9,999 failure rolls back all 9,999 preceding reports, and the transaction holds locks for its entire duration. Per-item transactions mean a failure loses one item. Which is correct depends on the requirement — but nobody ever chose it here, which is the actual problem.

Two adjacent traps with the same cause: the annotation is also silently ignored on a final method (CGLIB cannot override it) and on a private method. All three fail the same way — no error, no log, no transaction.

4 (medium): Three bugs in this event bus. Find and fix them. 
public class EventBus {
    private final List<Consumer<Event>> listeners = new ArrayList<>();

    public void subscribe(Consumer<Event> l) { listeners.add(l); }

    public void publish(Event e) {
        for (Consumer<Event> l : listeners) {
            l.accept(e);
        }
    }
}
Solution
BugRuntime symptom
No way to unsubscribeThe bus strongly references every listener's captured scope forever — a steady heap leak
One listener throwsThe exception escapes publish; later listeners never run and the publisher fails
ArrayList iterated while listeners mutate itConcurrentModificationException when a listener subscribes or unsubscribes during dispatch
public class EventBus {
    private final List<Consumer<Event>> listeners = new CopyOnWriteArrayList<>();

    public AutoCloseable subscribe(Consumer<Event> l) {
        listeners.add(l);
        return () -> listeners.remove(l);      // caller can unsubscribe
    }

    public void publish(Event e) {
        for (Consumer<Event> l : listeners) {
            try { l.accept(e); }
            catch (RuntimeException ex) { log.error("listener failed", ex); }
        }
    }
}

Why CopyOnWriteArrayList: its iterator walks a snapshot taken at iterator(), so a mutation during dispatch cannot throw. Every write copies the whole array, which is exactly the right trade for a listener list — subscriptions are rare, publishes are frequent. It would be the wrong choice for a list written on every request.

Why return an AutoCloseable: a removeListener(l) method forces the caller to keep the reference, and a lambda-typed listener is not equals to any other object, so callers get it wrong. Handing back a subscription handle makes the caller's cleanup path obvious and works with try-with-resources.

The leak is the one that reaches production. A listener lambda captures its enclosing object — a controller, a session, a UI frame — and the bus keeps it reachable from a GC root for the process's lifetime. This is the classic Swing and Android leak. Weak references are the tempting fix and a bad one by default: nothing else holds the lambda, so it is collected immediately and events silently stop arriving. Explicit unsubscription tied to the owner's lifecycle is the correct answer.

One design point left open: publish runs on the caller's thread, so a slow listener stalls the publisher. That is a defensible default (it is what Spring's synchronous events do) but it must be a decision, and it needs documenting.

5 (hard): Replace this Visitor with modern Java, and state precisely what you gain and what you give up. 
interface Node { <R> R accept(Visitor<R> v); }

class Num implements Node {
    final double v;
    public <R> R accept(Visitor<R> vis) { return vis.visitNum(this); }
}
class Add implements Node {
    final Node l, r;
    public <R> R accept(Visitor<R> vis) { return vis.visitAdd(this); }
}

interface Visitor<R> { R visitNum(Num n); R visitAdd(Add a); }

class Eval implements Visitor<Double> {
    public Double visitNum(Num n) { return n.v; }
    public Double visitAdd(Add a) { return a.l.accept(this) + a.r.accept(this); }
}
Solution 
sealed interface Node permits Num, Add { }
record Num(double v)            implements Node { }
record Add(Node l, Node r)      implements Node { }

static double eval(Node n) {
    return switch (n) {
        case Num(double v)      -> v;
        case Add(Node l, Node r) -> eval(l) + eval(r);
    };                         // no default — the compiler proves it total
}

Five types and roughly forty lines became three declarations and a method. The record deconstruction patterns also remove the field access: case Add(Node l, Node r) binds the components directly, so there is no a.l/a.r and no cast anywhere.

PropertyVisitorSealed + switch
Exhaustiveness checkYes — adding a type breaks the visitor interfaceYes — adding a permit breaks every switch
Adding an operationNew visitor class, no existing type touchedNew method, no existing type touched
Adding a typeEdit the visitor interface + every implementationEdit the permits clause + every switch
Third parties can add typesYes, if they can extend NodeNo — sealed forbids it
Traversal with accumulated stateNatural — the visitor holds fieldsNeeds an explicit parameter or a helper class
Boilerplate per typeAn accept method eachNone

What you gain is the elimination of double dispatch. Visitor's whole mechanism exists because Java dispatches on the receiver only: accept gets you back to a statically-known type so the right visitX overload can be chosen. Pattern matching dispatches on the runtime type directly, so the mechanism becomes unnecessary rather than shorter.

What you give up is extension by third parties. sealed is a closed-world declaration: nobody outside your permits clause can add a Node. For an expression AST that is exactly what you want, and it is what makes the exhaustiveness proof possible. For a plugin API where others contribute node types, it is fatal — and there Visitor remains the right answer, along with any codebase that must run on Java 17 or earlier.

The honest caveat is deep, stateful traversal. A type checker threading a scope through the tree fits a visitor's fields naturally; with a switch you pass the scope as a parameter through every recursive call. That is not worse, but it is not obviously better either, and it is the one case where I would not automatically convert.

6 (hard): Review this design. It "uses patterns correctly". Say what you would cut and why. 
interface UserService { User find(Long id); }
class UserServiceImpl implements UserService { … }         // only impl

class UserServiceFactory {
    public static UserService create() { return new UserServiceImpl(); }
}

class UserServiceSingleton {
    private static UserService instance;
    public static UserService get() {
        if (instance == null) instance = UserServiceFactory.create();
        return instance;
    }
}

class UserFacade {
    public User find(Long id) { return UserServiceSingleton.get().find(id); }
}
Solution

Every one of these is a correctly implemented pattern, and all four should go. This is pattern-driven design: the structures were chosen from the catalogue rather than derived from a force in the code.

ElementForce it would needPresent here?Verdict
UserService interfaceTwo implementations, or a published API boundaryNo — the Impl suffix is the proofDelete
UserServiceFactoryA choice between implementations, caching, or validationNo — it calls one constructorDelete

class UserService {
    private final UserRepository repo;
    UserService(UserRepository repo) { this.repo = repo; }
    User find(Long id) { return repo.findById(id).orElseThrow(); }
}

Five types became one, and the surviving one is testable in a way the original was not.

What each removal actually buys. The interface: navigation lands on the code instead of a declaration, and a change touches one file instead of two. The factory: the call site says what it constructs. The singleton: this is the important one — it was a hidden edge in the dependency graph, invisible to every tool and uncuttable by any test. With constructor injection a test passes a stub repository and needs no database and no static reset between tests.

The singleton was also broken. The unsynchronised null check races: two threads can both construct. Nobody noticed because it happened to be harmless here, which is how this class of bug reaches production.

What I would concede in review. If UserService is exported from a module or published as an API others compile against, the interface is a real contract and I keep it — but I name it for what varies, not Impl. If a second implementation genuinely arrives, extracting the interface then is an IDE refactor measured in seconds. That asymmetry is the whole argument: adding an abstraction later is cheap; removing a wrong one is not.

🎯 Key Takeaways

  • A pattern is a name, a problem, a solution and a cost — and the name is most of the value.
  • A pattern applied without its problem is complexity with a respectable label. State the force before you reach for the structure.
  • The rule of three: write it concretely twice; extract the abstraction on the third real case, when you can see what actually varies.
  • Java 8 absorbed half the catalogue — Strategy is a lambda, Command is a Runnable, Iterator is for-each, Template Method is often a function parameter.
  • Keep a named type when the strategy has state, a name, or must be enumerated — and then an enum implementing the interface is usually the best form.
  • Builder solves the telescoping constructor, not "many fields"; setters trade a readability problem for a mutability one.
  • A static factory method beats a constructor when you need a name, a cache, or the freedom to return a subtype.
  • Abstract Factory is about a consistency constraint between products; without one, you have coupled unrelated factories.
  • The only correct singletons are the static holder and the enum; DCL without volatile can publish a partially constructed object.
  • A singleton is global mutable state — "one instance" is a wiring decision, so inject it instead.
  • clone() is broken: shallow, no constructor, fights final, and Cloneable declares nothing. Use a copy constructor, or immutability.
  • Adapter converts, Decorator adds — the test is whether the wrapper implements the same interface as what it wraps.
  • A proxy wraps the object, not the class, so this.method() bypasses @Transactional, @Cacheable and @Async silently.
  • Flyweight is why == lies: boxed integers are cached in −128..127 and string literals are interned.
  • State and Strategy have the same shape; the tell is whether an implementation ever chooses the next one.
  • Sealed types plus pattern matching replace Visitor and keep the exhaustiveness check — unless third parties must add types.
  • An interface with one implementation named Impl is not an abstraction — extract it when the second implementation appears.
