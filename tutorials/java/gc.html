Garbage Collection JVM & Performance

What you'll master: that GC works on reachability, not reference counting — which is why Java has no cycle problem and why a "leak" is always something still reachable; the weak generational hypothesis and the consequence that makes everything else make sense — a copying collector's cost is proportional to survivors, not to garbage, so allocating a million objects that die immediately is nearly free; why allocation is a pointer bump in a TLAB; what a card table buys and what it costs on every reference write; how G1, ZGC and Shenandoah actually differ and what you trade for a sub-millisecond pause; the four numbers worth reading in a GC log; and why most "GC problems" are allocation-rate or leak problems that no tuning flag will fix. Prerequisites: Memory: Stack, Heap & References.

Part 1 — Reachability, Not Counting

  THE JVM DOES NOT COUNT REFERENCES. It asks a different question:
  starting from a set of ROOTS, which objects can I reach?

  Anything unreachable is garbage — whether or not other garbage
  points at it.

  THE GC ROOTS:

    local variables and parameters in every live stack frame
    static fields of loaded classes
    JNI local and global references
    active Java threads (the Thread objects themselves)
    objects held by the JVM itself (system class loader, exception
      being thrown, monitors currently held)

  WHY THIS BEATS REFERENCE COUNTING — CYCLES COLLECT THEMSELVES:

    a.next = b;
    b.next = a;        // each has count 1
    a = null; b = null;

  A counting collector leaks this forever. A tracing collector simply
  never reaches the pair from a root, so both die. Python needs a
  separate cycle detector for exactly this reason; Java does not.

  THE CONSEQUENCE THAT MATTERS FOR DEBUGGING:

    A JAVA MEMORY LEAK IS ALWAYS SOMETHING STILL REACHABLE.

  There is no "forgot to free". If memory grows without bound, some
  root still reaches the objects — a static Map, a listener list, a
  ThreadLocal on a pooled thread, a cache with no eviction. The heap
  dump question is never "what leaked" but "WHAT PATH FROM A ROOT
  KEEPS THIS ALIVE", which is exactly what a dominator tree answers.

  MARK-SWEEP-COMPACT, THE BASELINE ALGORITHM:

    MARK     trace from roots, flag everything reachable
    SWEEP    reclaim the space of everything unmarked
    COMPACT  slide survivors together to remove fragmentation

  Compaction is what keeps allocation cheap — see Part 3 — but it
  MOVES OBJECTS, which means every reference to them must be updated,
  which is why naive collectors must stop the world to do it.

  FINALIZERS ARE DEAD. Object.finalize() is removed; it made objects
  survive an extra cycle, ran on an unbounded queue with no timing
  guarantee, and could resurrect the object. Use try-with-resources
  for deterministic cleanup, and java.lang.ref.Cleaner as the safety
  net — never as the primary mechanism.

Part 2 — The Generational Hypothesis

  THE WEAK GENERATIONAL HYPOTHESIS, measured across decades of real
  programs:

    MOST OBJECTS DIE YOUNG. Typically 90-98% of allocations are
    unreachable by the next collection.

  Think about what you actually allocate: a StringBuilder inside a
  method, boxed values in a stream pipeline, an iterator, a DTO for
  one request. Almost none of it outlives the call.

  THE HEAP IS SPLIT TO EXPLOIT THIS:

    ┌──────────── YOUNG GENERATION ────────────┬─── OLD GEN ───┐
    │   Eden          │  S0   │  S1            │               │
    │  (allocate)     │(from) │ (to)           │  (tenured)    │
    └─────────────────┴───────┴────────────────┴───────────────┘
         ~80%            10%     10%              typically 2/3
                                                  of total heap

  A YOUNG COLLECTION (a "minor GC"):

    1. Trace from roots, but only INTO the young generation.
    2. COPY every live object out of Eden and the in-use survivor
       space into the OTHER survivor space.
    3. Increment each survivor's age. At the TENURING THRESHOLD
       (default 15, adaptive) promote it to the old generation.
    4. Eden and the vacated survivor space are now entirely empty —
       reclaim them by resetting a pointer.

  HERE IS THE CRUCIAL CONSEQUENCE:

    A COPYING COLLECTOR TOUCHES ONLY THE SURVIVORS. Its cost is
    O(live), NOT O(heap) and NOT O(garbage).

  So a young GC that finds 2% survivors costs almost nothing no
  matter how much was allocated. ALLOCATING GARBAGE IS NEARLY FREE;
  KEEPING OBJECTS ALIVE IS WHAT COSTS.

  That single fact overturns the instinct to "reduce allocations".
  A million short-lived objects are cheaper than a hundred thousand
  that survive one collection.

  PREMATURE PROMOTION IS THE FAILURE MODE. If Eden is too small or
  survivor spaces overflow, objects that would have died young get
  copied into the old generation instead. They then require an
  expensive old-gen collection to remove. Symptoms: old gen growing
  steadily under a workload with no real long-lived state, and
  frequent full collections.

  WHY THE OLD GENERATION IS COLLECTED DIFFERENTLY: survival rates
  there are high, so copying would move almost everything. Old-gen
  algorithms therefore mark and either sweep or compact in place, and
  they are the expensive ones.

Part 3 — Allocation Is a Pointer Bump

  BECAUSE COMPACTION LEAVES EDEN CONTIGUOUS, ALLOCATION DOES NOT NEED
  A FREE LIST. It needs one pointer:

    top += size;          // that is genuinely most of it
    if (top > limit) slow_path();

  ~10 machine instructions. Faster than malloc, which must search a
  free list and handle fragmentation.

  BUT top IS SHARED, so a naive version needs an atomic increment per
  allocation — a contention point across every thread.

  THE FIX IS THE TLAB (THREAD-LOCAL ALLOCATION BUFFER). Each thread
  gets its own chunk of Eden:

    thread A: [==== TLAB ====][ ]
    thread B:                 [==== TLAB ====][ ]

  Inside its TLAB a thread bumps its own pointer with NO
  SYNCHRONISATION at all. Only when the TLAB is exhausted does it
  take a lock to claim another chunk.

  TLAB sizes adapt to each thread's allocation rate. A thread that
  allocates heavily gets bigger buffers; an idle one gets small ones.

  OBJECTS TOO LARGE FOR A TLAB go directly to the shared Eden or, if
  very large, straight into the old generation — bypassing the cheap
  path entirely. That is one reason huge arrays behave differently
  from many small objects.

  ESCAPE ANALYSIS CAN REMOVE THE ALLOCATION ENTIRELY. If C2 proves an
  object never escapes its method, it performs SCALAR REPLACEMENT —
  the fields become registers and no object is created:

    Point p = new Point(x, y);     // may never exist at runtime
    return p.x + p.y;

  This is why "object allocation is slow" is outdated advice and why
  micro-optimising allocation by hand can be counterproductive: you
  may defeat the analysis that was already eliminating it.

  THE ARITHMETIC YOU CAN ACTUALLY USE:

    young GC frequency = allocation rate ÷ Eden size

    500 MB/s allocation, 1 GB Eden  → a young GC every 2 s
    2 GB/s   allocation, 1 GB Eden  → a young GC every 0.5 s

  Each young GC costs roughly (survivors × copy cost). So there are
  exactly two levers: allocate less, or make Eden bigger so each
  collection is rarer and — because more objects have died by then —
  proportionally cheaper.

Part 4 — Cross-Generational References

  A YOUNG COLLECTION WANTS TO SCAN ONLY THE YOUNG GENERATION. But an
  old object may hold the only reference to a young one:

    static List<Order> cache;   // in OLD gen
    cache.add(new Order());     // the Order is in EDEN

  If the collector ignores the old generation, it will conclude the
  Order is unreachable and free a live object. Scanning the whole old
  generation to avoid that would cost exactly what generational GC
  was meant to save.

  THE CARD TABLE SOLVES IT. The old generation is divided into
  "cards" (512 bytes each), with a one-byte table entry per card:

    old gen:  [ card 0 ][ card 1 ][ card 2 ][ card 3 ] …
    table:       clean     DIRTY     clean     clean

  A WRITE BARRIER runs on every reference store to an object field:

    obj.field = ref;
    cardTable[address(obj) >> 9] = DIRTY;    // ~2 instructions

  At the next young GC, the collector scans only the dirty cards
  plus the young generation, and treats references found there as
  extra roots.

  YOU PAY FOR THIS ON EVERY REFERENCE WRITE IN YOUR PROGRAM — a
  couple of instructions, always, whether or not a GC ever happens.
  It is one of the few places where GC imposes a cost on ordinary
  execution rather than at collection time. It also explains why
  primitive writes are cheaper than reference writes.

  G1 GENERALISES THIS TO REMEMBERED SETS. Since G1 collects an
  arbitrary SET of regions, each region needs to know who points into
  it, so it keeps a per-region remembered set. That is far more
  bookkeeping than a flat card table, and it is precisely why G1 has
  higher overhead than Parallel on a throughput benchmark — you are
  buying pause predictability with CPU and footprint.

  THE PRACTICAL LESSON: holding young objects from long-lived
  structures is not free. A large mutable cache in the old generation
  dirties cards continuously and enlarges every young collection.

Part 5 — The Collectors

  SERIAL  (-XX:+UseSerialGC)
    One thread, stop-the-world, mark-copy young + mark-sweep-compact
    old. Lowest footprint and lowest overhead.
    USE IT: small heaps (< ~100 MB), single-core containers, CLI
    tools, and anywhere startup and footprint beat pause time. It is
    genuinely the right answer more often than its reputation
    suggests.

  PARALLEL  (-XX:+UseParallelGC)
    Same algorithms, many threads. Was the default through Java 8.
    HIGHEST THROUGHPUT of any collector — nothing runs concurrently
    with your application, so no CPU is spent on concurrent marking
    and no write barriers beyond the card table.
    USE IT: batch jobs, ETL, anything where total time matters and a
    one-second pause is irrelevant.
    COST: pauses scale with heap size. A 32 GB heap can pause for
    seconds.

  G1  (-XX:+UseG1GC)  — the default since Java 9
    The heap is divided into ~2048 equal REGIONS (1-32 MB), and a
    region is dynamically Eden, Survivor, Old, or Humongous:

      [E][O][S][E][O][O][H][H][E][O][S][E][O] …

    You state a PAUSE TARGET and G1 collects as many regions as it
    predicts will fit in it:

      -XX:MaxGCPauseMillis=200        (default)

    "Garbage First" is literal — it collects the regions with the
    most garbage per unit of work, which is why it is efficient
    without needing a contiguous young generation.
    MIXED COLLECTIONS clean young regions plus a few old ones each
    cycle, spreading old-gen work out instead of doing one big pause.
    HUMONGOUS ALLOCATIONS — objects larger than half a region — are
    allocated directly into contiguous old regions and are hard to
    reclaim. Many large arrays cause fragmentation and full GCs; the
    fix is usually a bigger -XX:G1HeapRegionSize.
    PAUSE TARGET IS A GOAL, NOT A GUARANTEE. Set it too low and G1
    collects too little per cycle, falls behind, and eventually does
    a full stop-the-world collection — worse than the pauses you were
    avoiding.

  ZGC  (-XX:+UseZGC)  and  SHENANDOAH  (-XX:+UseShenandoahGC)
    Concurrent collectors: marking AND relocation happen while the
    application runs, so pause time is essentially independent of
    heap size.
      pauses:  < 1 ms, on heaps from a few hundred MB to 16 TB
      how:     ZGC uses COLOURED POINTERS — metadata stored in unused
               pointer bits — plus load barriers that fix up a
               reference when the application reads one that has been
               relocated. Shenandoah uses a similar load-barrier
               approach with Brooks pointers historically.
      cost:    5-15% throughput, higher CPU (concurrent threads
               compete with yours), and more footprint.
    USE THEM: latency-sensitive services with large heaps where a
    200 ms G1 pause violates an SLA.
    DO NOT USE THEM: batch work, small heaps, or CPU-saturated
    services — you are paying throughput for a pause reduction nobody
    observes.

  EPSILON  (-XX:+UseEpsilonGC)
    Allocates and never collects; the JVM dies when the heap fills.
    Real uses: benchmarking allocation cost without GC noise, and
    extremely short-lived jobs that finish before exhausting memory.

Part 6 — Reading the Logs and Tuning Honestly

  ENABLE LOGGING. It is cheap and it is the only real evidence:

    -Xlog:gc*:file=gc.log:time,uptime,level,tags

  (The old -XX:+PrintGCDetails flags were removed in Java 9; unified
  logging replaced them.)

  A YOUNG COLLECTION LINE, DECODED:

    [12.345s][info][gc] GC(42) Pause Young (Normal)
                        (G1 Evacuation Pause)
                        512M->48M(1024M) 12.456ms
                         │     │    │      └ pause duration
                         │     │    └ total heap size
                         │     └ heap used AFTER
                         └ heap used BEFORE

  THE FOUR NUMBERS THAT MATTER — and none of them is "pause time on
  its own":

    1. ALLOCATION RATE = (heap used before GC n+1 − heap used after
       GC n) ÷ elapsed. This is the number that drives everything.
       Above ~1 GB/s, look at your code before your flags.
    2. PROMOTION RATE = growth of the old generation per second. If
       this is high in a service with no growing state, you have
       PREMATURE PROMOTION — Eden or the survivor spaces are too
       small.
    3. LIVE SET = heap used after a FULL collection. This is your
       real memory requirement. If it grows monotonically across
       full GCs, you have a leak, and no flag will help.
    4. GC OVERHEAD = time in GC ÷ wall time. Under ~5% is healthy;
       above 10% is a problem worth chasing.

  THE DIAGNOSTIC TABLE:

    growing live set across full GCs   → LEAK. Take a heap dump.
    high allocation rate, low survival → fine, or reduce allocation
    high promotion, low real lifetime  → premature promotion; raise
                                         -Xmn or the survivor ratio
    long young pauses                  → too many survivors; the
                                         young gen may be TOO BIG
    long full pauses on G1             → humongous fragmentation, or
                                         a pause target set too low
    "Allocation Failure" every second  → Eden too small for the rate

  TUNING, IN THE ORDER THAT ACTUALLY PAYS:

    1. FIX THE ALLOCATION RATE OR THE LEAK. Most "GC problems" are
       application problems. No collector makes a leak survivable.
    2. SET THE HEAP SIZE. -Xms == -Xmx to avoid resize pauses. Aim
       for a live set around 30-50% of the heap; a heap too small
       causes constant collection, and one too large lengthens full
       collections and wastes memory you paid for.
    3. CHOOSE THE COLLECTOR from the table above.
    4. SET A PAUSE GOAL if using G1 — and be realistic; too
       aggressive is worse than none.
    5. EVERYTHING ELSE. Survivor ratios, tenuring thresholds, region
       sizes. Change ONE flag, measure, keep or revert.

  NEVER CALL System.gc(). It requests a full stop-the-world
  collection at the worst possible moment and tells you nothing about
  your steady state. Disable it with -XX:+DisableExplicitGC when a
  library insists on calling it.

  CONTAINERS: modern JVMs are container-aware and read cgroup limits,
  but the default MaxRAMPercentage is only 25%. On a 4 GB container
  you get a 1 GB heap unless you say otherwise:

    -XX:MaxRAMPercentage=75.0

  Leave real headroom — metaspace, thread stacks, direct buffers and
  JIT code cache all live outside the heap, and the container OOM
  killer does not produce a heap dump.

Interview Questions

Beginner: How does the JVM decide an object is garbage?

By reachability, not reference counting. It traces outward from a set of GC roots — local variables in live stack frames, static fields, JNI references, active threads — and anything not reached is garbage.

The practical advantage is that cycles collect themselves. Two objects pointing at each other have non-zero reference counts but are unreachable from any root, so a tracing collector frees them. Python needs a separate cycle detector precisely because it counts.

The consequence for debugging is the one worth remembering: a Java memory leak is always something still reachable. There is no "forgot to free". If the heap grows without bound, some root still holds a path to the objects — a static collection, a listener list, a cache with no eviction, a ThreadLocal on a pooled thread. So the heap-dump question is never "what leaked" but "what keeps this alive", which is what a dominator tree answers.

Beginner: What is the generational hypothesis and why does the heap follow it?

The weak generational hypothesis is the observation that most objects die young — typically 90–98% of allocations are unreachable by the next collection. That matches what programs actually allocate: a StringBuilder inside a method, boxed values in a stream, an iterator, a per-request DTO.

The heap is split into a young generation (Eden plus two survivor spaces) and an old generation so the collector can exploit it. A young collection copies the survivors out and then reclaims Eden wholesale by resetting a pointer.

The key consequence is that a copying collector's cost is proportional to survivors, not to garbage. A collection that finds 2% live costs almost nothing regardless of how much was allocated — so allocating short-lived objects is nearly free, and keeping objects alive is what costs.

The old generation is collected differently because survival rates there are high; copying would move nearly everything, so those algorithms mark and sweep or compact in place, and they are the expensive ones.

Mid: Why is allocation in Java often faster than malloc?

Because compaction keeps Eden contiguous, so allocation needs no free list — it is a pointer bump:

top += size;
if (top > limit) slow_path();

That is roughly ten instructions. malloc must search a free list and cope with fragmentation.

The shared top pointer would be a contention point, so each thread gets a TLAB — a private chunk of Eden. Inside it a thread bumps its own pointer with no synchronisation at all, taking a lock only when the buffer is exhausted. TLAB sizes adapt to each thread's allocation rate.

On top of that, escape analysis may remove the allocation entirely: if C2 proves an object never escapes its method, scalar replacement turns its fields into registers and no object is created.

This is why "allocation is slow" is outdated, and why hand-optimising it can backfire — object pooling replaces a pointer bump with bookkeeping, keeps objects alive into the old generation, and can defeat the analysis that was already eliminating the allocation.

Mid: How does a young GC avoid scanning the old generation?

With a card table. An old-generation object can hold the only reference to a young one — staticCache.add(new Order()) — so ignoring the old generation would free a live object, while scanning all of it would cost exactly what generational GC was meant to save.

The old generation is divided into 512-byte cards with one table byte each. A write barrier runs on every reference store and marks the card dirty:

obj.field = ref;
cardTable[address(obj) >> 9] = DIRTY;   // ~2 instructions

At the next young collection, the collector scans the young generation plus only the dirty cards, and treats references found there as additional roots.

What makes this worth knowing is the cost model: you pay a couple of instructions on every reference write in your program, whether or not a GC happens. It is one of the few places GC taxes ordinary execution rather than collection time, and it is why reference writes are more expensive than primitive writes.

G1 generalises this to per-region remembered sets, since it collects an arbitrary set of regions. That bookkeeping is a large part of why G1 has lower throughput than Parallel — pause predictability is bought with CPU and footprint.

Senior: How do you choose a collector, and when is the default wrong?

Start from what you are actually optimising, because the collectors trade the same two things against each other.

SituationChoiceReason
Batch job, ETL, total time is the metricParallelHighest throughput; nothing runs concurrently with you
General server, 4–64 GBG1 (default)Predictable moderate pauses
Latency SLA, large heapZGC / ShenandoahSub-millisecond pauses independent of heap size
Small container, CLI toolSerialLowest footprint and overhead

Where the default is wrong. G1 on a batch job leaves throughput on the table — Parallel can be 10–20% faster in total time, and nobody measures its pauses. G1 in a small container is needlessly heavy; Serial is genuinely better there. And G1 on a strict latency SLA with a large heap cannot deliver what ZGC can.

ZGC is not a free upgrade. It costs 5–15% throughput and runs concurrent GC threads that compete with your application for CPU. On a CPU-saturated service, switching to it can make end-to-end latency worse even though the pause histogram improves.

The prior question is almost always more valuable: is this a collector problem at all? A growing live set is a leak, and a 2 GB/s allocation rate is an application problem. Neither is fixed by a flag. I would change the collector only after the allocation rate and live set are known to be reasonable and the pause profile is still unacceptable.

Senior: A service pauses for several seconds under load. Walk through the diagnosis.

Get evidence before touching flags. -Xlog:gc*:file=gc.log:time,uptime,level,tags is cheap and safe to enable in production.

Then read four numbers, not just the pause times:

  1. Live set — heap used after a full collection. If it climbs monotonically across full GCs, this is a leak and everything else is a symptom. Stop here and take a heap dump.
  2. Allocation rate — heap used before GC n+1 minus heap used after GC n, over elapsed time. Above roughly 1 GB/s, the fix is in the application.
  3. Promotion rate — old-generation growth per second. High promotion in a service with no growing state means premature promotion: Eden or the survivor spaces are too small, so objects that should have died young now require an old-gen collection.
  4. GC overhead — time in GC over wall time. Under 5% is healthy; above 10% needs action.

Map the pattern to a cause. Long full pauses on G1 usually mean humongous allocations fragmenting old regions, or a pause target set so low that G1 falls behind and is forced into a full collection. Long young pauses mean too many survivors — and counter-intuitively the young generation may be too big, since copying cost scales with survivors.

Rule out the impostors. Not every multi-second pause is GC: check for swapping (which makes any pause catastrophic), a long safepoint from something other than GC — biased-lock revocation historically, or a slow thread dump — and container CPU throttling, where a cgroup quota stalls the whole JVM. -Xlog:safepoint distinguishes these.

Then fix in order: the leak or the allocation rate first; heap sizing with -Xms equal to -Xmx; the collector; a realistic pause goal; and only then the fine-grained flags — one at a time, measuring each.

🏋️ Graded Exercises

1 (easy): Do these two objects ever get collected? 
class Node { Node next; }

Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;
a = null;
b = null;
Solution

Yes, both are collected. Each still has an incoming reference, but neither is reachable from a GC root once the locals are cleared — so a tracing collector never marks them.

ApproachResult
Reference countingBoth counts are 1 — leaked forever
Tracing (Java)Unreachable from roots — collected

This is the central advantage of tracing, and why Java never needed a cycle detector the way CPython does. Doubly-linked lists, parent/child trees and observer graphs all work without special care.

The flip side is the one that matters in production: if something is still reachable, no amount of nulling elsewhere helps. Adding a = null inside a method is almost always pointless — the frame dies at return anyway — while a static List holding the same node keeps it alive forever.

2 (easy): Which loop puts more pressure on the collector? 
// A
for (int i = 0; i < 10_000_000; i++) {
    String s = "item-" + i;
    process(s);
}

// B
List<String> all = new ArrayList<>();
for (int i = 0; i < 1_000_000; i++) {
    all.add("item-" + i);
}
process(all);
Solution

B, despite allocating ten times fewer objects.

AB
Objects allocated10,000,0001,000,000
Objects surviving a young GC≈ 0all of them
Copied between survivor spaces≈ 0Repeatedly, then promoted
Old-generation growthNone~60–80 MB

A copying collector's cost is O(survivors), not O(allocations). In A, every string is dead by the next collection, so Eden is reclaimed by resetting a pointer and the collection is nearly free. In B, everything is live, so each young GC copies the whole set, ages it, and eventually promotes it — after which removing it requires an old-generation collection.

The practical lesson is that "reduce allocations" is the wrong reflex. Reduce what survives. Streaming or batching B — processing a chunk and discarding it — converts expensive survivors into free garbage.

And in A the allocation may not happen at all: escape analysis can scalar-replace objects that never leave the method, so the loop can end up allocating nothing.

3 (medium): A young GC runs every 100 ms and each takes 50 ms. Diagnose it from these two lines. 
[10.000s] GC(50) Pause Young 2048M->1900M(4096M) 50.1ms
[10.100s] GC(51) Pause Young 2048M->1910M(4096M) 51.3ms
Solution

The survival rate is enormous and the old generation is growing. Each collection reclaims only 148 MB of 2048 MB — roughly 93% of objects survive, against the 2–10% a healthy young collection sees.

MetricValueVerdict
GC overhead50 ms per 100 ms = 50%Catastrophic (healthy < 5%)
Survival rate~93%Should be 2–10%
Allocation rate~1.5 GB/sVery high
Post-GC floor1900 → 1910 MBClimbing — a leak or unbounded cache

Two problems, and the order matters. The rising floor across collections points to a leak or an unbounded cache — that is the root cause and no flag fixes it. Take a heap dump and find what dominates the retained set.

The high survival rate is the mechanism by which it hurts. Because copying cost scales with survivors, 93% survival means every collection copies nearly the entire young generation and then promotes it, which is why 50 ms pauses are back-to-back.

What would be wrong here: enlarging the heap. It buys time before the OOM and makes each collection copy even more. Enlarging Eden only helps if the objects are genuinely short-lived and being collected too early — the climbing floor says they are not.

4 (medium): Allocation is 1 GB/s and Eden is 512 MB. How often does a young GC run, and what are your options?
Solution 
frequency = allocation rate ÷ Eden size
          = 1024 MB/s ÷ 512 MB
          = one young GC every 0.5 s

Whether that is a problem depends entirely on the pause length, which depends on survivors, not on the rate. At 5% survival each collection copies ~25 MB and takes a few milliseconds — two collections a second is completely fine.

The non-obvious one is that a bigger Eden usually lowers the survival rate, not just the frequency: more time passes before each collection, so more objects have already died. The saving is better than linear.

The limit is that Eden competes with the old generation for the same heap. Taking too much starves the old generation and triggers full collections — which is why -Xmn is a measure-and-adjust flag, not a set-and-forget one.

Where to start: measure the pause, not the frequency. Frequent cheap collections are a healthy profile, not a problem to fix.

5 (hard): A 32 GB service on G1 with MaxGCPauseMillis=50 sees occasional 8-second full GCs. Explain and fix.
Solution

The pause target is a goal, not a guarantee, and 50 ms on a 32 GB heap is unattainable. G1 responds by collecting fewer regions per cycle, which means it reclaims less than the application allocates. The old generation fills, concurrent marking cannot finish in time, and G1 falls back to a full, single-threaded, stop-the-world compaction — the 8 seconds.

The humongous case deserves attention because it is silent. Any object larger than half a region is allocated into contiguous old-generation regions and is not collected by ordinary young collections. With the default region size on a 32 GB heap, a 20 MB array qualifies — so a service handling large payloads fragments the old generation until only a full compaction can recover it.

If a 50 ms ceiling is a genuine requirement, G1 is the wrong collector at this heap size. ZGC delivers sub-millisecond pauses independent of heap size, at 5–15% throughput. That is the honest trade — you cannot get G1 to do it by tightening the target, and tightening it is what caused this.

Order of work: relax the target to 200 ms first and confirm the full GCs stop. That single change usually resolves it, and it tells you whether you are chasing a configuration problem or a real capacity problem before you change collectors.

6 (hard): Heap usage after every full GC rises steadily — 1.2 GB, 1.5 GB, 1.9 GB, 2.4 GB — until an OutOfMemoryError. Diagnose it.
Solution

This is a leak, and no GC tuning will help. Heap used after a full collection is the live set — memory that is genuinely still reachable. A rising live set means something holds references it should have released.

The diagnosis, in order:

  1. Capture a dump at a known-bad point: jcmd <pid> GC.heap_dump /tmp/heap.hprof, or arm -XX:+HeapDumpOnOutOfMemoryError in advance.
  2. Open it in Eclipse MAT and read the dominator tree, not the histogram. The histogram says "40 million char[]", which is never the answer; the dominator tree says what keeps them alive.
  3. Take the path to GC roots for the largest dominator, excluding weak and soft references. That path is the bug.
  4. Compare two dumps taken minutes apart to see what is growing rather than what is merely large.

What would waste the outage: raising -Xmx, changing collector, or adding System.gc(). The first two delay the failure; the third does nothing, because the objects are reachable and a full collection has already run at every one of those measurements.

🎯 Key Takeaways

  • GC traces reachability from roots, so cycles collect themselves and every leak is something still reachable.
  • Most objects die young — the hypothesis the whole generational design rests on.
  • A copying collector's cost is O(survivors), not O(garbage) — short-lived allocation is nearly free.
  • Reduce what survives, not what you allocate.
  • Allocation is a pointer bump in a per-thread TLAB, and escape analysis may remove it entirely.
  • A write barrier and card table let young GCs skip the old generation — paid for on every reference write.
  • Premature promotion is the common young-gen failure: objects that should die young need an old-gen collection instead.
  • Parallel has the best throughput; G1 the best general balance; ZGC the smallest pauses.
  • G1's pause target is a goal — set it too low and it falls behind into a full GC.
  • Humongous allocations bypass G1's young collections and fragment the old generation.
  • ZGC costs 5–15% throughput and extra CPU — wrong for batch work and saturated services.
  • Read four numbers: allocation rate, promotion rate, live set, GC overhead.
  • A live set rising across full GCs is a leak, and no flag fixes it.
  • Size the heap so the live set is 30–50% of it, with -Xms equal to -Xmx.
  • Containers default to 25% of RAM — set MaxRAMPercentage, leaving off-heap headroom.
  • Never call System.gc(), and change one flag at a time.
