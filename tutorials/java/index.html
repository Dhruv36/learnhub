How Java Runs: JVM, JDK & Bytecode Foundations

What you'll master: what actually happens between the source you type and a running program — and the one fact that explains most of Java's behaviour for the rest of the track: Java is compiled and interpreted and compiled again at runtime, which is why a Java process is slowest in its first seconds and fastest after a few thousand invocations; why timing the first run of a benchmark can be 10–50× off and report a conclusion that reverses once the JIT warms up; what the JVM is doing besides translating — verification, class loading, memory management and deoptimization; the JDK/JRE/JVM distinction stated precisely enough to survive a follow-up question; and the classpath as an ordered search where the first match wins, which is why two versions of the same library on the path produces a NoSuchMethodError at runtime rather than a build failure. No prerequisites — this is lesson one, and the model you build here is what makes performance, class loading and "why is my classpath broken" make sense later.

Part 1 — The Problem Java Was Built to Solve

In 1995, shipping software meant compiling your C or C++ separately for every target: one binary for Windows on Intel, another for Solaris on SPARC, another for a Mac. A pointer bug could take down the whole machine. Java's designers made a deliberate bet: compile once to a portable intermediate format, and let a small program on each machine execute that format. That program is the Java Virtual Machine, and the format is bytecode.

"Write Once, Run Anywhere" works because your code never talks to the operating system directly — it talks to the JVM, and a different JVM build for each platform does the translating. You write against one stable target.

🔑 The mental model that pays off all track long: Java is compiled (source → bytecode) and interpreted, and then JIT-compiled (bytecode → machine code, at runtime). It is not "compiled like C" and not "interpreted like Python" — it is a hybrid, and almost every Java performance characteristic falls out of that: slow startup, fast steady state, a warmup period, and benchmarks that lie if you time the first run.

Part 2 — The Journey of a Program

1. SOURCE          Hello.java — plain text.
                   public class Hello { public static void main(String[] a){…} }

2. COMPILE         javac Hello.java  ->  Hello.class
                   Type and syntax checking, then BYTECODE — not machine code.
                   Bytecode is the JVM's instruction set, identical on every
                   platform.

3. LAUNCH          java Hello  starts a JVM process and asks it to run the class.

4. CLASS LOADING   The loader finds Hello.class on the classpath, VERIFIES the
                   bytecode, and links it. Classes load LAZILY — on first use,
                   not up front.

5. INTERPRET       The JVM walks bytecode instruction by instruction. Correct,
                   and roughly an order of magnitude slower than native code.

6. JIT COMPILE     The JVM counts how often each method runs. Hot methods are
                   compiled to native code optimised for THIS CPU, using
                   profiling data an ahead-of-time compiler could never have.

7. EXECUTE + GC    The program runs while the garbage collector reclaims what
                   you no longer reference.
  WHAT VERIFICATION ACTUALLY DOES, AND WHY IT EXISTS

  Step 4 is not a formality. Before running a single instruction the JVM
  proves properties of the bytecode:

    - the operand stack never underflows or overflows
    - types match what each instruction expects
    - jumps land on real instruction boundaries
    - final fields are not reassigned, access modifiers are respected

  Because javac produced the bytecode, this looks redundant — until you
  remember the JVM has NO IDEA where a .class came from. It could be
  downloaded, generated at runtime by a framework, or hand-edited.

  Verification is what makes "running untrusted bytecode" a coherent idea,
  and it is why a corrupt or hand-mangled class fails with
  VerifyError at load time rather than crashing the process later.

  It is also why frameworks that GENERATE bytecode — Spring's proxies,
  Hibernate's entity enhancement, Mockito's mocks — produce load-time
  errors that look bizarre: the generator emitted something that does not
  verify.

Part 3 — JDK vs JRE vs JVM

Asked in interviews constantly, because the answer reveals whether you understand the platform. They nest:

TermStands forContainsYou need it to…
JVMJava Virtual MachineThe engine: class loader, verifier, interpreter, JIT, garbage collectorExecute bytecode. It is both a written specification and a concrete implementation
JREJava Runtime EnvironmentJVM + the standard class libraries (java.lang, java.util, …)Run Java programs
JDKJava Development KitJRE + tools: javac, javap, jar, jshell, jlink, the debuggerDevelop Java programs

One sentence for the interview: the JDK is what you develop with, the JRE is what you run with, and the JVM is the engine inside the JRE that executes the bytecode. Since Java 11 Oracle no longer ships a standalone JRE — you install a JDK, and produce a slimmed runtime with jlink if you need one for deployment.

🔧 Which JDK to install? A current LTS — Java 21 is the modern baseline, with 17 still widespread. Eclipse Temurin, Amazon Corretto and Azul Zulu are all builds of the same OpenJDK source, so the choice is about support and packaging rather than the language. The one thing worth checking is that your build tool, your IDE and your CI all use the same version: a project compiled on 21 will not run on a 17 JVM, and the error — UnsupportedClassVersionError — names class file versions rather than Java versions, which is its own small puzzle.

Part 4 — Write, Compile, Run

// Hello.java — the filename MUST match the public class name
public class Hello {
    public static void main(String[] args) {    // the JVM's entry point
        System.out.println("Hello, World!");
    }
}
javac Hello.java      # -> Hello.class (bytecode) in the same folder

java Hello            # name the CLASS, not the file — no .class extension
# -> Hello, World!

java Hello.java       # JDK 11+: compile in memory and run, one step.
                      # Ideal for experiments; not how you ship anything.

javap -c Hello        # disassemble the class back to JVM instructions
  WHAT javap SHOWS, AND WHY IT IS WORTH LOOKING ONCE

  public static void main(java.lang.String[]);
    Code:
       0: getstatic     #7   // Field java/lang/System.out:Ljava/io/PrintStream;
       3: ldc           #13  // String Hello, World!
       5: invokevirtual #15  // Method java/io/PrintStream.println:(…)V
       8: return

  Three things this makes concrete:

  1. THE JVM IS A STACK MACHINE. getstatic pushes System.out, ldc pushes
     the string, invokevirtual pops both and calls the method. There are
     no registers in the bytecode — the JIT assigns those later.

  2. THE #NUMBERS ARE CONSTANT POOL ENTRIES. Every class carries a table
     of its strings, method references and type names. This is why a
     .class file is larger than the code suggests, and how tools can
     inspect dependencies without running anything.

  3. THE METHOD SIGNATURE IS ENCODED IN THE DESCRIPTOR, which is why
     erasure works the way it does (Generics lesson) and why overloading
     resolves at COMPILE time while overriding resolves at RUNTIME
     (Inheritance lesson).

  You will rarely read bytecode in your career. Reading it once turns
  "Java compiles to bytecode" from a slogan into something you have seen.
🧪 Faster experiments: JShell. Run jshell and type System.out.println(2 + 2) — it evaluates immediately, with no class and no main. Throughout this track, when you want to check what a snippet actually does, JShell answers in seconds rather than minutes.

Part 5 — Interpreted, Compiled, or Both?

"Is Java compiled or interpreted?" is a trick question. The answer is both, and the reason it matters is that everything about Java's performance profile follows from it.

  THE THREE STAGES, AND WHAT EACH COSTS

  AHEAD OF TIME   javac, once. Source -> bytecode. Catches type errors and
                  produces the portable artifact. Does almost no
                  optimisation — that is deliberate, because the JIT can
                  do better with runtime information.

  INTERPRETED     Every method starts here. The JVM walks bytecode
                  instruction by instruction. Starts instantly, runs
                  roughly 10-50x slower than optimised native code.

  JIT COMPILED    The JVM counts invocations and loop iterations. Past a
                  threshold — thousands of calls — a method is compiled
                  natively. HotSpot uses TIERED compilation:

                    C1  compiles quickly, optimises lightly, and adds
                        profiling counters
                    C2  compiles slowly, optimises aggressively, using
                        the profile C1 collected

                  So a hot method is typically interpreted, then C1, then
                  C2 — each faster than the last.
  WHY THE JIT CAN BEAT AN AHEAD-OF-TIME COMPILER

  It knows things that are unknowable before the program runs:

    - WHICH BRANCHES ARE ACTUALLY TAKEN, so it lays out the common path
      contiguously and moves the rare one out of line
    - WHICH TYPES ACTUALLY APPEAR at a call site. An interface call with
      exactly one implementation seen becomes a direct call, then gets
      inlined — "monomorphic inlining", and it is the single biggest win
      in most Java code
    - WHAT IS ACTUALLY CONSTANT — a config flag read once and never
      changed folds away, taking the whole disabled branch with it

  AND WHAT HAPPENS WHEN IT GUESSED WRONG: DEOPTIMIZATION.

  If a second implementation of that interface finally appears, the
  compiled code's assumption is invalid. The JVM discards the native
  code, falls BACK to the interpreter mid-method, and recompiles later
  with the new profile.

  This is why a service can be fast for an hour and then briefly slower
  after a code path runs for the first time — and why "it got slow after
  we enabled that feature flag" is a real phenomenon rather than
  superstition.

🔑 The senior framing: the JVM is a specification, and HotSpot in OpenJDK is the dominant implementation but not the only one. Bytecode is also a target for other languages — Kotlin, Scala, Groovy and Clojure all compile to it and interoperate with Java. So "the JVM ecosystem" is genuinely larger than the Java language, and the portability of the bytecode format is what makes that possible.

Part 6 — The Classpath

When you run java Hello, how does the JVM find Hello.class — and the hundreds of library classes a real program needs? The classpath: an ordered list of folders and jars that the class loader searches.

# Folders and jars, separated by : on Unix and ; on Windows
java -cp .:lib/gson.jar com.example.App

# The package structure must exist as folders under a classpath entry:
#   com/example/App.class  found because "." is on the path
  THE PROPERTY THAT CAUSES THE HARD BUGS: FIRST MATCH WINS

  The classpath is searched IN ORDER, and the loader stops at the first
  entry containing the class. It does not check whether a second copy
  exists, and it does not warn you.

  So with two versions of the same library on the path:

    -cp lib/guava-19.jar:lib/guava-31.jar

  every class resolves from guava-19, INCLUDING classes that only make
  sense alongside 31. Nothing fails at build time, because the compiler
  saw only what your build tool put on the compile path.

  WHAT YOU GET AT RUNTIME:

    NoSuchMethodError      the class was found; the method was not
    NoClassDefFoundError   a class that loaded fine before now cannot
                           resolve something it references
    AbstractMethodError    an interface gained a method the loaded
                           implementation does not have

  These are the "jar hell" errors, and the tell is that they name a
  method or class that plainly exists in your IDE. That means the
  RUNTIME classpath differs from the COMPILE classpath — usually a
  transitive dependency pulled in twice at different versions.

  In real projects you never manage this by hand: Maven and Gradle
  compute it, and `mvn dependency:tree` / `gradle dependencies` is where
  you look when it goes wrong.

Part 7 — Java's Evolution, and Why the Version Matters

1995   Java 1.0        applets, WORA, automatic memory management
2004   Java 5          generics, enums, annotations, for-each
2014   Java 8          lambdas, Streams, the new Date/Time API
2017   Java 9          the module system; the 6-month release cadence begins
2021   Java 17 (LTS)   records, sealed types, pattern matching maturing
2023   Java 21 (LTS)   virtual threads, pattern matching for switch

Two things follow. Since Java 9 a release ships every six months, with an LTS every two to three years — 8, 11, 17, 21 — and those are what companies actually standardise on, so "what Java version?" nearly always means an LTS. And Java 8 is the dividing line: code before it is imperative and verbose, code after it (lambdas, streams, var, records, virtual threads) is dramatically more concise. This track teaches modern Java throughout, and flags the older idiom where you will still meet it.

Interview Questions

Beginner: What is the JVM and why does it exist?

The Java Virtual Machine is the runtime engine that executes bytecode. It exists to deliver "write once, run anywhere": source compiles to platform-independent bytecode, and a platform-specific JVM on each machine executes it, so the same .jar runs unchanged on Windows, Linux or macOS.

The part worth adding is that it is far more than a translator. It loads classes lazily, verifies bytecode before running it, manages memory and runs the garbage collector, and JIT-compiles hot methods to native code. Most of the engineering depth people associate with "Java" is really the JVM.

And it is a specification as well as an implementation — HotSpot is the common one, but the same bytecode is the target for Kotlin, Scala and Clojure, which is why the ecosystem is larger than the language.

Beginner: Explain the difference between JDK, JRE and JVM.

They nest. The JVM is the engine that executes bytecode. The JRE is the JVM plus the standard class libraries — everything needed to run a Java application. The JDK is the JRE plus development tools — javac, javap, jar, JShell, the debugger — everything needed to develop.

So: JDK to build, JRE to run, JVM inside the JRE doing the executing.

The detail that shows current knowledge is that since Java 11 there is no separate JRE download. You install a JDK, and if you need a minimal runtime for a container you build one with jlink containing only the modules your application uses.

Mid: Is Java compiled or interpreted? Defend your answer.

Both, and the sequence matters. javac compiles source to bytecode ahead of time — that is a real compile step, and it is where type errors are caught. At runtime the JVM starts by interpreting that bytecode, then the JIT compiler compiles hot methods to native machine code.

So a given method is typically interpreted first, then compiled by C1 with light optimisation and profiling counters, then recompiled by C2 with aggressive optimisation using that profile.

The reason this is worth understanding rather than reciting is that Java's whole performance profile follows from it. Startup is slow because everything begins interpreted. Steady state is fast because the hot paths end up native. Benchmarks that time the first run measure the interpreter and can be an order of magnitude off — sometimes reversing which of two options looks faster.

It also explains why the JIT can beat an ahead-of-time compiler: it knows which branches are actually taken and which types actually appear, so it can inline an interface call that has only ever seen one implementation. When that assumption is later violated it deoptimizes — discards the native code and falls back — which is the mechanism behind an occasional latency spike when a new code path runs for the first time.

Mid: What is the classpath, and why do classpath errors happen at runtime rather than at compile time?

The classpath is an ordered list of folders and jar files that the class loader searches when it needs a class. The key property is that it stops at the first match — it does not check whether another copy exists further along, and it does not warn.

These errors are runtime errors because compilation and execution use different lists. The compiler saw whatever your build tool put on the compile path; the JVM sees whatever is on the runtime path, which for a real application is assembled from transitive dependencies and can easily contain two versions of the same library.

That produces the "jar hell" family: NoSuchMethodError for a method that plainly exists in your IDE, AbstractMethodError when an interface gained a method the loaded implementation lacks, or NoClassDefFoundError for something that resolved a moment ago. The tell is always the same — the runtime classpath is not the compile classpath.

The other reason errors appear late is that class loading is lazy. A class is loaded the first time it is used, so a missing dependency on a rarely-taken branch surfaces the first time that branch runs, which may be in production weeks after the deploy.

In practice you diagnose it with mvn dependency:tree or gradle dependencies, then exclude or align the duplicate.

Senior: Why does the JVM verify bytecode, given that javac produced it?

Because the JVM has no idea where a .class file came from. javac is one producer among many: bytecode can be downloaded, hand-edited, or generated at runtime — and in a typical Spring or Hibernate application, a great deal of it is generated at runtime, for proxies, entity enhancement and mocks.

Verification proves structural properties before execution: the operand stack cannot underflow or overflow, types match what each instruction expects, jumps land on real instruction boundaries, and access control and final are respected.

What that buys is the ability to run untrusted or machine-generated bytecode without those defects becoming memory-safety bugs. In C, a malformed jump is undefined behaviour; on the JVM it is a VerifyError at load time.

The practical payoff for a working developer is diagnostic. When a bytecode-generating framework emits something invalid, you get a load-time VerifyError naming the generated class rather than a crash somewhere unrelated later — which is a much better failure mode, even though the error message is initially baffling.

There is a cost, which is startup time — verification is real work done for every class loaded. That is part of what Class Data Sharing addresses, by storing a pre-verified form of the class metadata.

Senior: A service is fast in steady state but its first requests are slow, and a colleague proposes a native image. How do you evaluate that?

First I would name the cause, because it determines whether the proposal helps. Slow first requests are the JIT warmup: every method starts interpreted, and only becomes fast after enough invocations to trigger C1 and then C2 compilation. Nothing is broken.

Then I would ask what the actual cost is. If it is a long-running service behind a load balancer, the fix may simply be a warmup period before it receives full traffic, or a health check that does not mark it ready until it has served some synthetic requests. That is cheap and changes no code.

A native image genuinely solves it — ahead-of-time compilation to a native binary, so startup is milliseconds and there is no warmup at all. But the trade-offs are substantial and worth stating plainly: peak throughput is lower, because there is no JIT and therefore no profile-guided optimisation or speculative inlining; builds take minutes rather than seconds; and the closed-world assumption means reflection, dynamic proxies and resource loading need explicit configuration, with failures appearing at runtime if a library lacks it.

So the question I would put back is what the service actually is. For a function or a CLI that runs briefly and exits, or anything that scales to zero, native is clearly right — those workloads pay all of the warmup cost and receive none of the benefit. For a service running twenty-four hours a day, trading 15–25% of steady-state throughput to fix the first few seconds is usually a bad deal.

The middle options are the ones I would try first: Class Data Sharing, which removes much of the class loading and verification cost, and framework-level AOT processing, which moves work from startup to build. Both keep the JIT, so steady state is unchanged, and neither changes the runtime you debug.

🏋️ Graded Exercises

1 (easy): Compile and run Hello.java, then rename the class to Greeter without renaming the file. Predict the error before running it.
Solution 
javac Hello.java
# Hello.java:1: error: class Greeter is public, should be declared
#                      in a file named Greeter.java

Why the rule exists: the class loader finds a class by turning its fully-qualified name into a path — com.example.Greeter becomes com/example/Greeter.class. If the file name did not match, the loader would have no way to locate it without scanning every file on the classpath.

The rule applies only to public classes. A non-public class can live in a file of any name, and one file can contain several — which is occasionally useful for a small helper and usually a bad idea, because nobody can find it.

Worth noticing: this is a compile-time error. The whole family of problems in this lesson divides into ones javac catches (this) and ones only the runtime can catch (the classpath errors), and knowing which is which tells you where to look.

2 (easy): Run javap -c on your Hello class. Identify which instruction pushes the string, and explain what the # numbers refer to.
Solution 
0: getstatic     #7   // Field java/lang/System.out:Ljava/io/PrintStream;
3: ldc           #13  // String Hello, World!
5: invokevirtual #15  // Method java/io/PrintStream.println:(…)V
8: return

ldc — "load constant" — pushes the string. The sequence is a stack machine at work: getstatic pushes System.out, ldc pushes the string, and invokevirtual pops both to make the call.

The # numbers are constant pool indices. Every class file carries a table of the strings, method references, field references and type names it uses, and the instructions refer to entries by index rather than embedding them. That is why the disassembly shows a comment with the resolved value — javap is looking it up for you.

What this explains laterHow
Why .class files are larger than the code suggestsThe constant pool is a substantial part of the file
How tools analyse dependencies without running anythingEvery type a class references is named in its constant pool
Why overloading resolves at compile timeThe descriptor in the instruction names the exact signature; the runtime does not choose

The bytecode is a stack machine with no registers, which surprises people who expect something resembling assembly. Register allocation is the JIT's job, and it happens per-CPU at runtime — which is precisely what makes the format portable.

3 (medium): A colleague benchmarks two sorting implementations by timing one run of each and concludes A is 3× faster than B. What is wrong, and what would you do?
Solution

They measured the interpreter, plus class loading, plus JIT compilation happening during the measurement. A single run of a Java method is dominated by costs that disappear entirely in steady state, so the number describes startup rather than the algorithm.

What contaminates a single runEffect
Interpretation before the JIT kicks inRoughly 10–50× slower than the eventual native code
Class loading and verification of everything touchedOne-off, and attributed to whichever ran first
Compilation happening during timingThe JIT's own CPU work lands inside the measurement
Dead-code eliminationA result that is never used can be optimised away entirely, "proving" an implementation takes zero time
Whichever ran first pays the shared warmupReordering the two tests can reverse the conclusion — the quickest way to demonstrate the problem

What I would actually do: ask them to swap the order and re-run. If the conclusion flips, the point is made without a lecture.

Then use JMH, which exists because doing this correctly by hand is genuinely hard. It runs warmup iterations until performance stabilises, forks fresh JVMs so profiles from one benchmark cannot pollute another, and consumes results through a Blackhole so the optimiser cannot delete the work. See Benchmarking & JMH.

The caveat worth keeping: steady-state numbers are the right measurement for a long-running server and the wrong one for a CLI that exits after a second. Benchmark the lifecycle you actually ship.

4 (medium): An application throws NoSuchMethodError for a method you can see in your IDE. Diagnose it.
Solution

The runtime classpath differs from the compile classpath. The method exists in the version you compiled against, and a different version of the same class was loaded at runtime — almost always two copies of a library on the path, where the first match won.

mvn dependency:tree -Dincludes=com.google.guava
# or
gradle dependencies --configuration runtimeClasspath

# transitively by two different dependencies.

The fix is to align the versions, with an exclusion or dependency management, rather than to reorder the classpath. Ordering is not stable across environments and it leaves the ambiguity in place.

The reason this cannot be caught at compile time is that the compiler only ever saw one version — the one your build tool resolved for compilation. The duplicate exists in the assembled runtime path. That is why "it works in my IDE" is a genuine and common report rather than carelessness.

What prevents recurrence: a dependency convergence check in the build — Maven's enforcer plugin or Gradle's resolution strategy — which fails the build when two versions of one artifact reach the runtime classpath. It is a one-line configuration that turns a production runtime error into a build error.

5 (hard): Explain why a Java service can be fast for an hour and then briefly slower after a rarely-used feature runs for the first time.
Solution

Two mechanisms, and both are the JVM working as designed.

Lazy class loading. Classes load on first use, so the first execution of that feature pays for loading, verifying and linking every class it touches — potentially dozens, including framework classes — plus any static initialisers.

Deoptimization. This is the interesting one. The JIT optimises speculatively: if a call site has only ever seen one implementation of an interface, it compiles a direct call and inlines it. That assumption is recorded as a guard. When the new feature introduces a second implementation, the guard fails, the JVM discards the compiled code, resumes in the interpreter mid-method, and later recompiles with the broader profile.

So a call site that was fully inlined becomes a megamorphic virtual call, and everything the inlining had enabled — constant folding, escape analysis, dead branch elimination — is lost with it. The slowdown is not confined to the new feature; it affects the shared code path both features use.

-XX:+PrintCompilation      # shows compilation, and "made not entrant"
                           # / "made zombie" lines when code is discarded

Why this is a good trade overall: speculative optimisation is exactly why Java's peak performance approaches C++. Optimising for what actually happens beats optimising for what might happen, and being able to undo the guess safely is what makes it possible at all.

What to do about it, if anything: usually nothing. If the spike matters — a latency SLO measured at p99.9 — the options are to exercise the path during warmup so the profile is broad before real traffic arrives, or to reduce polymorphism on the hot path so there is nothing to deoptimize. I would reach for the first; the second optimises for the compiler at the cost of the design.

6 (hard): Your team compiles on JDK 21 and deploys to a JDK 17 runtime. What breaks, when, and how do you prevent it?
Solution 
Exception in thread "main" java.lang.UnsupportedClassVersionError:
  com/example/App has been compiled by a more recent version of the
  Java Runtime (class file version 65.0), this version of the Java
  Runtime only recognizes class file versions up to 61.0

It breaks at class load time, immediately — the JVM refuses a class file format newer than it understands. Note the error speaks in class file versions, not Java versions: 61 is Java 17, 65 is Java 21, offset by 44.

Why -source and -target are not enough, and this is the part people get wrong: they control the language level and the emitted class version, but the code still compiles against JDK 21's libraries. So a method added to the standard library in 19 compiles cleanly and throws NoSuchMethodError on the 17 runtime — a failure that is deferred until that line executes.

ApproachCatches the class version?Catches new library APIs?
-source 17 -target 17YesNo — the dangerous gap
--release 17YesYes — it compiles against 17's API signatures
A build toolchain declarationYesYes, and it makes the JDK explicit for every developer and CI

--release is the correct answer, and a toolchain declaration in Maven or Gradle is better still, because it removes the assumption that whatever JDK happens to be on someone's PATH is the right one.

The organisational fix that matters more than any flag: compile and test on the JDK you deploy on, in CI. Every mechanism above narrows the gap between build and runtime; only actually running on the target closes it.

Worth knowing the reverse case is fine: a class compiled for 17 runs happily on 21. The JVM is backwards compatible, which is why upgrading a runtime is routine and downgrading is not.

🎯 Key Takeaways

  • Java is compiled to bytecode ahead of time, then interpreted, then JIT-compiled to native — a hybrid, and nearly every performance characteristic follows from it.
  • Bytecode is the real artifact. A .class is what you ship, and javap -c shows it as stack-machine instructions with constant pool references.
  • The JVM verifies bytecode before running it, because javac is only one of many producers — frameworks generate bytecode at runtime constantly.
  • Class loading is lazy, so a missing class or a failing static initialiser surfaces the first time that path runs, not at startup.
  • JDK ⊃ JRE ⊃ JVM: develop, run, execute. Since Java 11 there is no separate JRE — you install a JDK and use jlink for a minimal runtime.
  • HotSpot compiles in tiers — interpreted, then C1 with profiling, then C2 using that profile.
  • The JIT beats ahead-of-time compilation by knowing what actually happens — which branches are taken, which types appear, what is effectively constant.
  • Deoptimization is the price of that: when a speculative assumption is violated, the native code is discarded and execution falls back to the interpreter.
  • Warmup is real and measurable. Timing the first run measures the interpreter and can be 10–50× off, sometimes reversing the conclusion.
  • Benchmark the lifecycle you ship — steady state for a server, startup for a CLI.
  • The classpath is an ordered search where the first match wins, silently — which is the entire mechanism behind jar hell.
  • NoSuchMethodError for a method your IDE can see means the runtime classpath differs from the compile classpath. Start with the dependency tree.
  • Use --release, not -source/-target — the latter still compiles against the newer JDK's libraries and defers the failure to runtime.
  • An LTS every two to three years is what teams standardise on — 8, 11, 17, 21 — and Java 8 is the dividing line between the old idiom and the modern one.
  • The JVM is a specification with many languages targeting it; the ecosystem is larger than the language.
