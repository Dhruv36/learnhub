Threads & the Runnable Model Concurrency

What you'll master: what a platform thread actually costs — ~1 MB of reserved stack and a kernel scheduling entity, which is why "just make more threads" stops working around the low thousands; the difference between start() and run() that turns a concurrency bug into a silent single-threaded program; the six thread states and which method moves you between them; why Thread.stop() was removed and interruption is a cooperative request, not a kill; the interrupt-flag rule that gets destroyed by a careless catch (InterruptedException); daemon threads and what they mean for shutdown; and the uncaught-exception path that silently kills a worker. Prerequisites: Exceptions.

Part 1 — What a Thread Costs

  A JAVA PLATFORM THREAD IS A THIN WRAPPER OVER AN OS THREAD.
  Creating one is a system call; scheduling it is the kernel's job.

  THE COSTS, MEASURED:

    stack reservation     ~1 MB by default on 64-bit Linux
                          (-Xss changes it; 512 KB is common tuning)
    creation              ~50-100 µs — a syscall, not an allocation
    context switch        ~1-10 µs, plus cache and TLB pollution
                          that does not show up in the switch time
    practical ceiling     a few thousand before memory and scheduler
                          overhead dominate

  THE ARITHMETIC THAT MATTERS: 10,000 threads × 1 MB reserved stack
  = 10 GB of address space. It is RESERVED, not committed, so you may
  not touch 10 GB of RAM — but you will hit thread limits, scheduler
  overhead and GC root-scanning costs long before that.

  THIS IS THE ENTIRE MOTIVATION FOR THREAD POOLS AND, LATER, FOR
  VIRTUAL THREADS. A thread-per-request server on platform threads
  cannot serve 50,000 concurrent connections; the threads themselves
  are the bottleneck, not the work.

  WHERE THE COST BITES IS BLOCKING. A thread waiting on I/O holds its
  full stack and its scheduler slot while doing nothing. In a typical
  web request, 95%+ of wall time is waiting on a database or another
  service — so almost all of that reserved memory is idle.

  CREATING A THREAD PER TASK IS ALMOST ALWAYS WRONG:

    for (Request r : requests) new Thread(() -> handle(r)).start();
    // unbounded: 10k requests → 10k OS threads → OutOfMemoryError:
    //   unable to create new native thread

  Use an ExecutorService (see Executors & Futures) so the number of
  threads is a decision rather than an accident.

Part 2 — Creating and Starting

  THREE WAYS TO DEFINE THE WORK, ONE OF WHICH IS WRONG:

    // 1. Runnable — preferred: your class is free to extend
    //    something else, and the task is separable from the thread
    Thread t = new Thread(() -> System.out.println("work"));

    // 2. Extend Thread — couples the task to the mechanism, and
    //    burns your single inheritance slot
    class Worker extends Thread {
        @Override public void run() { … }
    }

    // 3. Callable + ExecutorService — when you need a RESULT or
    //    need exceptions to propagate. Runnable can do neither.
    Future<Integer> f = executor.submit(() -> compute());

  START() VERSUS RUN() — THE CLASSIC INTERVIEW QUESTION BECAUSE IT
  IS A REAL BUG:

    t.start();    // asks the JVM for a NEW thread, which calls run()
    t.run();      // an ordinary method call on the CURRENT thread

  t.run() compiles, executes the code, and produces no concurrency
  whatsoever. Nothing warns you. A program with a subtle race becomes
  a program that is simply sequential — and often that hides the bug
  in testing and exposes it in production.

  A THREAD CANNOT BE RESTARTED:

    t.start();
    t.start();    // IllegalThreadStateException

  The Thread object is a one-shot handle on an OS thread. Once
  terminated it stays terminated. This is why pools reuse threads by
  feeding them new TASKS, never by restarting them.

  NAME YOUR THREADS. The default is "Thread-0", which is useless in
  a stack trace or a thread dump at 3am:

    new Thread(task, "order-processor-1").start();

  In pools, supply a ThreadFactory that names them consistently.

  THREAD PRIORITY IS A HINT AND MOSTLY A NO-OP:

    t.setPriority(Thread.MAX_PRIORITY);   // 10

  The mapping to OS priorities is platform-specific; on Linux it does
  essentially nothing without privileges. Never build correctness on
  priority — that is what locks and queues are for.

Part 3 — The Six States

                    ┌─────┐
                    │ NEW │  created, start() not called
                    └──┬──┘
                       │ start()
                       ▼
                 ┌──────────┐
        ┌────────│ RUNNABLE │◄───────┐  running OR ready to run —
        │        └──────────┘        │  Java does not distinguish
        │             │              │
   wait()/join()  synchronized   sleep(n)/join(n)
   /park()        blocked on     /wait(n)
        │         a monitor           │
        ▼             ▼               │
  ┌─────────┐    ┌─────────┐    ┌────────────┐
  │ WAITING │    │ BLOCKED │    │TIMED_WAITING│
  └────┬────┘    └────┬────┘    └──────┬─────┘
       └──────────────┴────────────────┘
                       │ run() returns or throws
                       ▼
                 ┌────────────┐
                 │ TERMINATED │
                 └────────────┘

  THE DISTINCTION THAT MATTERS IN A THREAD DUMP:

    BLOCKED  waiting to ACQUIRE a monitor — someone else holds the
             lock. Many BLOCKED threads on one lock = contention.
    WAITING  waiting to be NOTIFIED — the thread gave up its lock
             voluntarily and is waiting for a condition.

  A dump full of BLOCKED on the same lock is a bottleneck. A dump
  full of WAITING on a queue is usually a healthy idle pool. Reading
  that difference correctly is most of what a thread dump is for.

  RUNNABLE INCLUDES "BLOCKED ON I/O", WHICH SURPRISES PEOPLE. A
  thread waiting on a socket read shows RUNNABLE because the JVM
  cannot see the OS-level block. So RUNNABLE does not mean "using
  CPU" — check the stack, not just the state.

  THE METHODS AND WHAT THEY DO TO LOCKS:

    Thread.sleep(ms)   TIMED_WAITING. KEEPS every lock it holds.
    obj.wait()         WAITING. RELEASES that object's monitor.
    t.join()           WAITING until t terminates.
    Thread.yield()     a hint to the scheduler; usually ignored.
    Thread.onSpinWait() a real CPU hint for spin loops (Java 9+)

  sleep() KEEPING ITS LOCKS is the one that causes outages. Sleeping
  inside a synchronized block holds up every other thread for the
  duration and buys nothing.

Part 4 — Interruption Is Cooperative

  THERE IS NO WAY TO KILL A THREAD IN JAVA. Thread.stop() existed,
  and was deprecated in 1.2 and REMOVED (it now throws
  UnsupportedOperationException) because it was unfixable:

    stop() threw a ThreadDeath at an arbitrary bytecode, releasing
    every lock the thread held — with shared data left half-updated
    and no way for anyone to know. An invariant broken by stop() is
    silently broken forever.

  INTERRUPTION IS A REQUEST THE TARGET MAY HONOUR:

    t.interrupt();          // sets a flag; may throw in the target
    t.isInterrupted();      // reads the flag, does NOT clear it
    Thread.interrupted();   // reads AND CLEARS — static, current
                            //   thread only

  TWO DIFFERENT THINGS HAPPEN DEPENDING ON WHAT THE TARGET IS DOING:

    blocked in sleep/wait/join/BlockingQueue.take
        → the flag is CLEARED and InterruptedException is thrown
    running normally
        → the flag is SET, and nothing else happens; code that never
          checks it runs to completion

  THAT FIRST RULE IS THE SOURCE OF THE MOST COMMON BUG:

    // ❌ swallows the interrupt entirely
    try { Thread.sleep(1000); }
    catch (InterruptedException e) { }        // flag already cleared,
                                              // and now discarded

  The thread is now uninterruptible. A shutdown that relies on
  interruption will hang, and you will blame the executor.

  THE TWO CORRECT RESPONSES:

    // A. propagate — best when you can
    void work() throws InterruptedException {
        Thread.sleep(1000);
    }

    // B. restore the flag and stop what you are doing
    try { Thread.sleep(1000); }
    catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // put it back
        return;                               // and actually exit
    }

  Restoring without returning is only half a fix: the flag is set but
  the loop continues, so the caller's cancellation still does not
  work.

  A CANCELLABLE LOOP, CORRECTLY:

    while (!Thread.currentThread().isInterrupted()) {
        Item item = queue.take();      // throws if interrupted
        process(item);                 // long work? check inside too
    }

  Use isInterrupted() rather than the static interrupted(), which
  clears the flag and makes the next check return false.

Part 5 — Daemons, Joining and Uncaught Exceptions

  DAEMON THREADS DO NOT KEEP THE JVM ALIVE.

    Thread t = new Thread(task);
    t.setDaemon(true);        // MUST be before start()
    t.start();

  The JVM exits when the last NON-daemon thread finishes. Daemon
  threads are then killed ABRUPTLY — no InterruptedException, no
  finally blocks, no chance to flush.

  THAT LAST PART IS THE TRAP. A daemon thread writing to a file or a
  database can be terminated mid-write at shutdown:

    setDaemon(true)  for: metrics reporters, heartbeats, cache
                          eviction, anything purely in-memory
    setDaemon(false) for: anything that must complete a unit of work

  MAIN IS NON-DAEMON, so a plain program stays alive while any
  non-daemon thread runs — which is why a forgotten worker keeps a
  CLI tool from exiting.

  JOIN WAITS FOR TERMINATION:

    t.start();
    t.join();          // block until t finishes (WAITING)
    t.join(5000);      // or until 5 s elapse

  join(timeout) DOES NOT TELL YOU WHETHER IT FINISHED. Check:

    t.join(5000);
    if (t.isAlive()) { /* timed out */ }

  join() itself throws InterruptedException, so the caller must
  handle its own cancellation too.

  AN UNCAUGHT EXCEPTION KILLS ONLY THAT THREAD — SILENTLY.

    new Thread(() -> { throw new RuntimeException("boom"); }).start();
    // main continues; a stack trace goes to stderr and nothing else
    // happens. No exit code, no alert, no retry.

  In production, a worker dies and throughput halves with no error in
  your logs — because the default handler writes to stderr, not to
  your logging framework.

    Thread.setDefaultUncaughtExceptionHandler((thread, ex) ->
        log.error("Thread {} died", thread.getName(), ex));

  Set that at startup, always. Per-thread handlers via
  t.setUncaughtExceptionHandler override it where needed.

  NOTE THE ASYMMETRY WITH EXECUTORS: a task submitted with
  submit() has its exception captured in the Future and is invisible
  until you call get(). Only execute() reaches the uncaught handler.
  That is a very common source of silent failure.

Part 6 — Shared State Is the Hard Part

  THREADS ARE EASY. SHARED MUTABLE STATE IS HARD.

    class Counter {
        private int count = 0;
        public void increment() { count++; }   // NOT atomic
    }

  count++ is three operations — read, add, write — and two threads
  can interleave between them:

    T1 reads 5        T2 reads 5
    T1 computes 6     T2 computes 6
    T1 writes 6       T2 writes 6      → 6, not 7

  Run 1000 increments on two threads and you reliably get less than
  2000.

  VISIBILITY IS A SEPARATE PROBLEM FROM ATOMICITY, and worse because
  it does not look like a bug:

    private boolean running = true;      // no volatile

    // thread A
    while (running) { work(); }

    // thread B
    running = false;                     // may NEVER be seen

  Thread A may loop forever. The JIT is allowed to hoist the read out
  of the loop, because within that thread nothing changes `running`.
  This is legal, it is not a JVM bug, and it is why volatile exists.

  THE TEST THAT FOOLS PEOPLE: this bug usually does NOT reproduce in
  a short test, because the loop finishes before the JIT compiles it.
  It appears in production, after the code has been running for
  seconds.

  THE THREE TOOLS, IN ORDER OF PREFERENCE:

    1. DON'T SHARE. Confine state to one thread, or make it
       immutable. Nothing to synchronize.
    2. USE A CONCURRENT CLASS. AtomicInteger, ConcurrentHashMap,
       BlockingQueue — someone has already got this right.
    3. SYNCHRONIZE. Correct, but you own the correctness.

  THE FIXES FOR THE TWO EXAMPLES ABOVE:

    private final AtomicInteger count = new AtomicInteger();
    count.incrementAndGet();             // atomic AND visible

    private volatile boolean running = true;   // visible

  volatile FIXES VISIBILITY ONLY — a volatile int++ is still a race,
  because volatile does not make the read-modify-write atomic. That
  distinction is the single most-tested concurrency fact.

  Full details in Synchronization & Locks and The Java Memory
  Model.

Interview Questions

Beginner: What is the difference between start() and run()?

start() asks the JVM to create a new OS thread, which then calls run(). run() called directly is an ordinary method call on the current thread — it executes the code with no concurrency at all.

It is a classic question because it is a real bug that compiles cleanly and produces no warning. A concurrent program silently becomes sequential, which often makes tests pass and hides a race until production.

Two related facts: a thread cannot be restarted — a second start() throws IllegalThreadStateException, because a Thread object is a one-shot handle — which is why pools reuse threads by feeding them new tasks rather than restarting them.

Beginner: What does a thread cost, and why does that matter?

A platform thread is a thin wrapper over an OS thread: roughly 1 MB of reserved stack, about 50–100 µs to create (a syscall), and 1–10 µs per context switch plus cache effects that do not show up in that number.

The consequence is a practical ceiling in the low thousands. Ten thousand threads reserve ten gigabytes of address space, and you hit thread limits, scheduler overhead and GC root-scanning costs well before memory becomes the binding constraint.

That single fact motivates most of the concurrency API. Thread pools exist because creation is too slow to do per task and the count must be bounded; virtual threads exist because thread-per-request is the model people actually want and platform threads cannot support it at scale.

The waste is concentrated in blocking: a thread waiting on a database holds its entire stack and scheduler slot while doing nothing, and in a typical web request that is 95% of wall time.

Mid: How does interruption work, and what is wrong with an empty catch block?

Interruption is cooperative. interrupt() sets a flag; it does not stop anything. What happens next depends on the target:

  • Blocked in sleep, wait, join or a BlockingQueue operation: the flag is cleared and InterruptedException is thrown.
  • Running: the flag is set and nothing else happens — code that never checks it runs to completion.

The empty catch is destructive because of that first rule: the flag has already been cleared, so swallowing the exception erases the only remaining evidence. The thread becomes uninterruptible, and a shutdown that relies on interruption hangs.

catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // restore
    return;                               // and actually stop
}

Restoring without returning is only half a fix — the flag is set but the loop keeps going, so cancellation still fails. And in loop conditions use isInterrupted(), not the static Thread.interrupted(), which clears the flag as it reads it.

Mid: Why was Thread.stop() removed?

Because it was unfixable. stop() threw a ThreadDeath at an arbitrary bytecode and released every lock the thread held.

A lock exists to protect an invariant during an update. Killing a thread halfway through a two-field update and then releasing the lock publishes the broken state to everyone else, with no exception and no indication anything is wrong. Unlike a crash, the program keeps running on corrupted data.

There is no safe version of this: only the code holding the lock knows what a consistent state looks like, so only that code can decide where it is safe to stop. That is precisely why interruption is a request — the target chooses the safe point.

It was deprecated in 1.2 and now throws UnsupportedOperationException. The practical consequence for a thread that will not respond to interruption is that you cannot kill it; the usual escape is to close the resource it is blocked on — a socket, a channel — which makes the blocking call throw.

Senior: You get a thread dump. How do you read it?

Start with the state distribution, because it tells you which kind of problem you have.

What you seeDiagnosis
Many BLOCKED on one lockContention — find the owner ("locked <0x…>") and shorten or split that critical section
Many WAITING on a queueUsually a healthy idle pool — or a starved producer
Many RUNNABLE in socket readsNot CPU-bound — waiting on a slow downstream. RUNNABLE covers blocking I/O
Many RUNNABLE in your own codeGenuinely CPU-bound; profile rather than dump
Pool threads all in one methodPool exhaustion — everything is stuck behind one dependency
"Found one Java-level deadlock"The JVM detected a monitor cycle and printed both sides

The most important interpretive fact is that RUNNABLE does not mean "using CPU". The JVM cannot see an OS-level block, so a thread waiting on a socket read looks runnable. Read the stack, not just the state — and correlate with CPU usage: high RUNNABLE with low CPU means waiting.

Take three dumps a few seconds apart. A single dump shows a moment; comparing them distinguishes "stuck" from "busy". Threads at the same stack across all three are stuck.

Thread names decide how fast this goes, which is the practical argument for naming every pool. "Thread-47" tells you nothing; "order-processor-3" tells you which subsystem is wedged.

Senior: A background worker silently stops processing. How do you diagnose and prevent it?

The likeliest cause is an uncaught exception. A thread that throws dies quietly: the default handler prints to stderr, not to your logging framework, so nothing appears in the logs, no alert fires, and throughput simply halves.

The variant that catches experienced people is the executor asymmetry: a task submitted with submit() has its exception captured in the Future and is invisible until someone calls get() — which for a fire-and-forget task is never. Only execute() reaches the uncaught-exception handler.

Prevention, in order of value:

  1. Thread.setDefaultUncaughtExceptionHandler at startup, routing to your logger.
  2. A try/catch around the loop body so one bad item does not kill the worker — catch, log, continue. Catch Exception, not Throwable, and let Error kill it.
  3. Either inspect every Future, or use execute() for fire-and-forget so failures surface.
  4. A liveness metric — a heartbeat or a "last processed" timestamp — with an alert. This is what actually detects the problem, because it does not depend on the failure being logged.

Diagnosis when it is already happening: a thread dump tells you whether the thread is gone (died) or present but stuck (blocked or waiting), and those have completely different fixes. Check stderr and the container logs separately from the application log — that is where the trace went.

The design conclusion is that a bare worker thread has no supervision. Executors give you a place to put it, and anything long-running should either report liveness or be restartable.

1 (easy): What does this print, and why? 
Thread t = new Thread(() ->
    System.out.println("in " + Thread.currentThread().getName()));
t.run();
t.start();
Solution 
in main        ← t.run() executed on the CURRENT thread
in Thread-0    ← t.start() created a new one

run() is just a method. Calling it invokes the code synchronously on whatever thread you are on; only start() asks the JVM for a new one.

Why it matters: nothing warns you. A program written for concurrency becomes sequential, which frequently makes the test suite pass — a race cannot occur with one thread — and exposes the bug in production instead.

The follow-up: add a third line, t.start() again, and you get IllegalThreadStateException. A Thread is a one-shot handle; once terminated it stays terminated. That is why pools recycle threads by giving them new tasks.

2 (easy): This shutdown hangs. Why? 
class Worker extends Thread {
    public void run() {
        while (true) {
            try { Thread.sleep(1000); process(); }
            catch (InterruptedException e) { }
        }

        try {
            Thread.sleep(1000);
            process();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();   // restore

        }
    }
}

3 (medium): This prints less than 20000, and sometimes hangs. Two separate bugs — name both. 
class Counter {
    private int count = 0;
    private boolean done = false;

    void increment() { count++; }
    void finish()    { done = true; }
    void await()     { while (!done) { } }
    int  get()       { return count; }
}
// 2 threads × 10000 increments
Solution

Bug 1 — atomicity. count++ is read, add, write. Two threads can read 5, both compute 6, both write 6 — one increment lost. Repeated thousands of times, the total is reliably short.

Bug 2 — visibility. await() may loop forever. Nothing in that thread modifies done, so the JIT is permitted to hoist the read out of the loop and test a register. This is legal, not a JVM bug.

class Counter {
    private final AtomicInteger count = new AtomicInteger();
    private volatile boolean done = false;

    void increment() { count.incrementAndGet(); }
    void finish()    { done = true; }
    void await()     { while (!done) Thread.onSpinWait(); }
    int  get()       { return count.get(); }
}

The visibility bug rarely reproduces in a short test, because the loop finishes before the JIT compiles it. It appears seconds into a production run — which is exactly the kind of bug that makes people distrust their own tests.

Thread.onSpinWait() is a genuine CPU hint (a PAUSE instruction on x86); it reduces the cost of the spin. A real design would use a CountDownLatch rather than spinning at all.

5 (hard): Review this worker for production. 
public class EventProcessor {
    private final Queue<Event> queue = new LinkedList<>();
    private Thread worker;
    private boolean running = true;

    public void start() {
        worker = new Thread(() -> {

    }

Solution

public class EventProcessor {
    private final BlockingQueue<Event> queue =
            new LinkedBlockingQueue<>(10_000);        // bounded
    private final ExecutorService exec =
            Executors.newSingleThreadExecutor(
                r -> new Thread(r, "event-processor")); // named

    public void start() {
        exec.submit(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                try {
                    process(queue.take());             // blocks, no spin
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return;
                } catch (Exception e) {
                    log.error("event failed", e);      // survive one bad event
                }
            }
        });
    }

    public boolean submit(Event e) {
        return queue.offer(e);            // false = backpressure, caller decides
    }

    public void stop() throws InterruptedException {
        exec.shutdownNow();
        if (!exec.awaitTermination(30, TimeUnit.SECONDS))
            log.warn("processor did not stop cleanly");
    }
}

take() replaces both the busy-wait and the stop flag. It blocks until an event arrives and throws InterruptedException on shutdownNow() — so cancellation and idling are the same mechanism.

Bounding the queue is the change people resist and need most. An unbounded queue converts a throughput problem into an out-of-memory crash; offer returning false pushes the decision to the caller, who is the only one who knows whether to drop, retry or reject.

Catch Exception per event, not around the loop, so one poison message does not end processing forever. Let Error propagate.

6 (hard): A service does new Thread(...).start() per request and fails at ~4000 concurrent users with OutOfMemoryError: unable to create new native thread. Heap is only 40% used. Explain and give options.
Solution

The heap is irrelevant — thread stacks live outside it. Each platform thread reserves about 1 MB of native stack, so 4000 threads is roughly 4 GB of address space plus per-thread kernel structures, and you hit the OS thread limit or native memory ceiling while the Java heap sits idle.

Why so many threads exist at once is the real point: if each request spends 200 ms waiting on a database, concurrency is not bounded by CPU, it is bounded by wait time. Little's Law gives the count directly — 2000 requests/second × 0.2 s = 400 in flight at steady state, and any downstream slowdown multiplies it.

The immediate fix is a bounded pool — it converts a crash into queueing and slower responses, which is a far better failure mode and can ship today.

The right long-term answer on Java 21 is virtual threads, because they preserve the simple blocking code while removing the per-thread stack cost. The caveat is pinning: a virtual thread blocked inside a synchronized block pins its carrier, so those sections need ReentrantLock.

Do not skip the last row. If the 200 ms downstream call becomes 20 ms, the in-flight count drops tenfold and the problem disappears without any concurrency change at all.

🎯 Key Takeaways

  • A platform thread costs ~1 MB of reserved stack and a syscall to create, giving a practical ceiling in the low thousands.
  • start() creates a thread; run() is a plain method call that silently removes all concurrency.
  • A thread cannot be restarted — pools reuse threads by feeding them new tasks.
  • Name every thread; "Thread-47" is useless in a 3am thread dump.
  • BLOCKED means contention on a lock; WAITING means a voluntary wait — the key distinction when reading a dump.
  • RUNNABLE includes blocking I/O, so it does not mean "using CPU".
  • sleep() keeps its locks; wait() releases the monitor.
  • Thread.stop() was removed because it released locks with invariants broken — silent corruption, not a crash.
  • Interruption is a cooperative request: blocked calls throw and clear the flag; running code must check it.
  • Never swallow InterruptedException — restore the flag and exit, or rethrow.
  • isInterrupted() reads; Thread.interrupted() reads and clears.
  • Blocking socket I/O is not interruptible — close the socket to unblock it.
  • Daemon threads are killed abruptly at exit — no finally, so never use one for durable work.
  • An uncaught exception kills only that thread, silently, to stderr — set a default handler at startup.
  • submit() hides exceptions in the Future; only execute() reaches the uncaught handler.
  • volatile fixes visibility, not atomicity — a volatile counter is still racy.
  • Prefer not sharing, then a concurrent class, then synchronization — in that order.
