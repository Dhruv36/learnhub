Pattern Matching Modern Java

What you'll master: pattern matching as test, cast and bind in one construct — removing the redundant cast that was always the compiler re-checking what instanceof had just proved; the scoping rule that makes a pattern variable available exactly where it is definitely assigned, including after an early return in the negated case; record deconstruction, which destructures nested data in the pattern itself; why case order matters and the compiler enforces it — an unreachable case is a build error rather than dead code; the null rule that changed, where a switch on a pattern throws unless you write case null; and when a chain of patterns is the right design and when it is polymorphism written by hand. Prerequisites: Records & Sealed Types and Inheritance.

Part 1 — instanceof Patterns

  THE OLD SHAPE — test, then cast the same thing again

    if (obj instanceof String) {
        String s = (String) obj;        // the compiler already KNOWS
        return s.length();              // this is a String
    }

  The cast is pure ceremony: instanceof established the type
  one line earlier, and the cast asks the compiler to re-verify it.
  Worse, the two can drift — change the instanceof and forget
  the cast, and you get a ClassCastException.

  THE PATTERN FORM (Java 16+)

    if (obj instanceof String s) {      // test, cast and BIND
        return s.length();
    }

  `s` is a PATTERN VARIABLE, in scope wherever the pattern has
  definitely matched. One construct, no cast, and they cannot
  disagree.

  IT COMBINES WITH && BECAUSE OF FLOW SCOPING:

    if (obj instanceof String s && s.length() > 5) { … }

  The right-hand side only evaluates when the left matched, so `s` is
  in scope there. The negation works too:

    if (!(obj instanceof String s)) return 0;
    return s.length();          // ✓ s IS in scope here

  That reads oddly the first time. The rule is that a pattern variable
  is in scope wherever the compiler can prove the pattern matched — and
  after an early return in the negated branch, the only way to reach
  the next line is if it did.

Part 2 — Patterns in switch

  Java 21 allows TYPE PATTERNS as case labels:

    String describe(Object o) {
        return switch (o) {
            case Integer i  -> "int " + i;
            case String s   -> "string of length " + s.length();
            case int[] arr  -> "array of " + arr.length;
            case null       -> "nothing";
            default         -> "unknown: " + o.getClass();
        };
    }

  GUARDS refine a case with a condition, using `when`:

    case Integer i when i < 0  -> "negative";
    case Integer i             -> "non-negative";

  The guard is part of the label, so the second case handles whatever
  the first rejected. Guarded cases must come BEFORE their unguarded
  counterpart, or the unguarded one would swallow everything.

  ORDER MATTERS, AND THE COMPILER ENFORCES IT:

    case Object o -> "any";        // ❌ then nothing after it is
    case String s -> "string";     //    reachable — COMPILE ERROR

  A case that can never match is an error rather than dead code, which
  is a genuine improvement over if-else chains where the same mistake
  is silent.

Part 3 — The null Rule Changed

  A CLASSIC switch THROWS ON null:

    switch (status) {           // status is null
        case ACTIVE: …          // NullPointerException before any
    }                           // case is considered

  That was a deliberate design decision in Java 1.0, and it forced
  every caller to null-check before switching.

  A PATTERN switch STILL THROWS BY DEFAULT — but you can now handle it:

    switch (obj) {
        case null      -> "nothing";      // explicit, and legal
        case String s  -> s;
        default        -> "other";
    }

  WITHOUT `case null`, a null selector throws NullPointerException
  even though `default` is present. That surprises people: default
  does NOT catch null.

  THE REASONING: making default absorb null silently would change the
  behaviour of every existing switch when patterns were added.
  Requiring an explicit case keeps null handling visible.

  THE COMBINED FORM IS OFTEN WHAT YOU WANT:

    case null, default -> "unknown";      // one arm for both

  AND A TYPE PATTERN NEVER MATCHES null — `case String s` does not
  match a null selector, because null is not an instance of anything.
  That is consistent with instanceof, and it is why the explicit case
  is needed.

Part 4 — Record Deconstruction

  A RECORD PATTERN destructures in the pattern itself:

    record Point(int x, int y) { }

    if (obj instanceof Point(int x, int y)) {
        return x + y;                    // x and y bound directly
    }

  No accessor calls, no intermediate variable. And it NESTS, which is
  where it earns its place:

    record Line(Point from, Point to) { }

    switch (shape) {
        case Line(Point(var x1, var y1), Point(var x2, var y2)) ->
            Math.hypot(x2 - x1, y2 - y1);
        …
    }

  Compare the accessor version:

    case Line l -> Math.hypot(l.to().x() - l.from().x(),
                              l.to().y() - l.from().y());

  The pattern version names the values once, in the position where
  they appear, and the shape of the data is visible in the shape of
  the code.

  `var` INFERS THE COMPONENT TYPE, which keeps deep patterns readable.
  A named type instead acts as a further test:

    case Line(Point(int x1, var y1), var to) -> …
      // matches only if the first component is an int Point

  COMBINING WITH GUARDS AND SEALED TYPES is where this becomes a
  complete tool:

    sealed interface Shape permits Circle, Rect { }
    record Circle(double r)                implements Shape { }
    record Rect(double w, double h)        implements Shape { }

    String classify(Shape s) {
        return switch (s) {
            case Circle(double r) when r > 100 -> "big circle";
            case Circle(double r)              -> "circle";
            case Rect(double w, double h) when w == h -> "square";
            case Rect r                        -> "rectangle";
        };                                  // exhaustive, no default
    }

Part 5 — Exhaustiveness

  A switch EXPRESSION must be exhaustive, and over a SEALED type the
  compiler can prove it from the permits clause:

    sealed interface Shape permits Circle, Square, Triangle { }

    double area(Shape s) {
        return switch (s) {
            case Circle c   -> …;
            case Square q   -> …;
            case Triangle t -> …;
        };                              // NO default — and none wanted
    }

  Add a Pentagon to the permits clause and EVERY such switch fails to
  compile, listing the sites that need a case.

  ADDING default THROWS THAT AWAY. It absorbs future subtypes
  silently, so the new shape falls into the default and produces a
  wrong answer rather than a build error. For a sealed hierarchy,
  omitting default is the whole point.

  WHEN default IS CORRECT: when the selector is genuinely open — an
  Object, a String, an int, or a type from a library that may gain
  subtypes outside your control. There the unknown case is real and
  must be handled.

  EXHAUSTIVENESS ALSO WORKS THROUGH RECORD PATTERNS:

    case Circle(double r) -> …          // still counts as covering
                                        // Circle

  though a GUARDED case never counts towards exhaustiveness, because
  the compiler cannot prove the guard is always true:

    case Circle c when c.r() > 0 -> …   // does NOT cover Circle
    // an unguarded case or a default is still required

Part 6 — When Not to Use It

  A CHAIN OF TYPE PATTERNS OVER YOUR OWN CLASSES IS USUALLY
  POLYMORPHISM WRITTEN BY HAND:

    // ❌ if you own Animal and its subtypes
    String sound(Animal a) {
        return switch (a) {
            case Dog d -> "woof";
            case Cat c -> "meow";
            default    -> "...";
        };
    }

    // ✓ the behaviour belongs on the type
    abstract class Animal { abstract String sound(); }

  Adding a subtype then requires nothing at the call sites — the
  compiler requires the method instead, and the logic lives with the
  data it describes.

  SO WHEN IS A PATTERN SWITCH RIGHT?

  1. THE BEHAVIOUR BELONGS TO THE CALLER, NOT THE TYPE.
     A UI colour for an order status does not belong on a domain
     class — putting it there makes the model depend on the view.

  2. THE TYPES ARE NOT YOURS.
     You cannot add a method to String, Integer or a library class,
     so dispatching externally is the only option.

  3. THE HIERARCHY IS SEALED AND THE OPERATIONS ARE MANY.
     An expression tree gains operations far more often than it gains
     node types, and a sealed switch adds an operation in one place
     rather than a method on every node. That is the visitor
     pattern's job, done by the language.

  4. THE MATCH DEPENDS ON STRUCTURE OR VALUES, NOT JUST TYPE.
     `case Rect(double w, double h) when w == h` is not expressible as
     a method on Rect without inventing an isSquare().

  THE HEURISTIC: if adding a new TYPE is more likely, put the
  behaviour on the type. If adding a new OPERATION is more likely,
  use a sealed hierarchy and switches.

Interview Questions

Beginner: What does an instanceof pattern give you?

It combines the type test, the cast and the variable binding into one construct. if (obj instanceof String s) tests the type and, when it matches, binds s as a String.

The old form required a redundant cast on the next line — asking the compiler to re-verify what instanceof had just established. Beyond the noise, the two could drift: change the instanceof and forget the cast, and you get a ClassCastException that the compiler could have prevented.

The scoping is flow-sensitive: the variable is in scope wherever the compiler can prove the pattern matched. That includes the right-hand side of &&, and — less obviously — the code after an early return in the negated branch, since the only way to reach it is if the pattern held.

Beginner: Why does a pattern switch throw on null even with a default?

Because default deliberately does not cover null. A pattern switch throws NullPointerException on a null selector unless you write case null.

The reasoning is compatibility. A classic switch has always thrown on null, and making default silently absorb it when patterns were introduced would have changed the behaviour of existing code. Requiring an explicit case keeps null handling visible at the site.

It is also consistent with type patterns: case String s does not match null, because null is not an instance of anything — the same rule instanceof has always had.

When you want one arm for both, case null, default -> … is the combined form.

Mid: What is a record pattern and when does it earn its place?

A record pattern destructures a record inside the pattern itself: if (obj instanceof Point(int x, int y)) binds the components directly, with no accessor calls and no intermediate variable.

For a single flat record the gain is modest. It earns its place when patterns nest, because the shape of the code then matches the shape of the data:

case Line(Point(var x1, var y1), Point(var x2, var y2)) ->
    Math.hypot(x2 - x1, y2 - y1);

// versus
case Line l -> Math.hypot(l.to().x() - l.from().x(),
                          l.to().y() - l.from().y());

The pattern version names each value once, in the position it occupies, rather than repeating a chain of accessors at each use.

var keeps deep patterns readable by inferring component types; naming a type instead makes it a further test, so Point(int x, var y) matches only when the first component is an int.

Combined with sealed hierarchies and guards, it covers the cases that previously needed a visitor — matching on structure and values rather than on type alone.

Mid: Why does case order matter, and what does the compiler check?

Cases are tried in order, so a broader pattern placed first swallows everything after it. The compiler treats that as an error rather than dead code — case Object o before case String s will not compile, because the second case can never match.

That is a genuine improvement over an if-else chain, where the same mistake is silent and the later branch simply never runs.

The same applies to guards: a guarded case must come before its unguarded counterpart, or the unguarded one matches first and the guard never runs.

The subtlety worth knowing is that a guarded case does not count towards exhaustiveness. The compiler cannot prove that when r > 0 is always true, so a sealed switch whose only Circle case is guarded still requires an unguarded case or a default. That catches people who expect the guard to cover the type.

Senior: When is a pattern switch better than polymorphism?

The general heuristic is about which axis changes more often — a restatement of the expression problem.

If new types are more likely, put the behaviour on the type. A method on Animal means adding a Dog requires no change at any call site, and the compiler demands the implementation. A pattern chain over your own hierarchy is dispatch written by hand, and every new subtype means finding every chain.

If new operations are more likely, a sealed hierarchy with switches is better. An expression tree gains operations — evaluate, print, simplify, optimise — far more often than it gains node types. Each operation is then one method with a switch, rather than a method added to every node class. That is what the visitor pattern was for, now done by the language with compiler-checked exhaustiveness.

Three other cases favour patterns regardless. The behaviour belongs to the caller — a UI colour for an order status does not belong on the domain type, because that would make the model depend on the view. The types are not yours — you cannot add a method to String or a library class. And the match depends on structure or values — case Rect(double w, double h) when w == h is not expressible as a method without inventing an isSquare().

What makes the modern version defensible where an instanceof chain was not is exhaustiveness: over a sealed type the compiler proves every case is handled and breaks the build when a subtype is added. That removes the failure mode that made the old pattern a smell.

Senior: How does pattern matching change how you model data?

It makes the algebraic-data-type style practical, and that changes what you reach for.

Before, a closed set of alternatives was expressed either with a flat class full of nullable fields and a discriminator — where illegal combinations are representable and every consumer checks — or with a visitor, which is verbose enough that people avoid it.

Now a sealed interface with record implementations gives each case exactly the data it needs, and a switch consumes it exhaustively with no default. Illegal states become unrepresentable rather than merely discouraged, and adding a case breaks the build at every consumer.

The practical consequence is that I model outcomes as types rather than as flags. A payment result becomes Approved, Declined, RequiresAction rather than a boolean plus three nullable fields — and the null checks disappear because there is no field to be null.

It also shifts where I put behaviour. With cheap exhaustive dispatch, keeping presentation logic out of domain types costs nothing — the switch lives in the UI layer and still fails to compile when a case is added.

The honest limit is that all of this requires a closed set. For anything third parties extend, sealing is wrong and ordinary polymorphism remains the answer — so this is a tool for domains you own, not a replacement for interfaces.

🏋️ Graded Exercises

1 (easy): Rewrite using a pattern, and say what the cast was costing. 
if (obj instanceof String) {
    String s = (String) obj;
    return s.trim().length();
}
return 0;
Solution 
if (obj instanceof String s) {
    return s.trim().length();
}
return 0;

// or, inverted:
if (!(obj instanceof String s)) return 0;
return s.trim().length();          // s IS in scope here

The cast was asking the compiler to re-verify what it had just proved one line earlier. That is noise, and it is a place the two can drift: change the instanceof to Integer and forget the cast, and you get a ClassCastException the compiler could have caught.

The inverted form surprises people. s is in scope after the early return because the compiler applies flow scoping — a pattern variable is available wherever it is definitely assigned, and the only way to reach the following line is if the pattern matched.

It combines with && for the same reason:

if (obj instanceof String s && !s.isBlank()) { … }

The right operand only evaluates when the left matched, so the binding is available there — while || would not work, since the right side can be reached without a match.

2 (easy): Why does this throw on null, and what are two fixes? 
String describe(Object o) {
    return switch (o) {
        case String s -> "string";
        case Integer i -> "int";
        default -> "other";
    };
}
Solution

default does not cover null. A pattern switch throws NullPointerException on a null selector unless there is an explicit case null.

// FIX A — handle null distinctly
case null      -> "nothing";
case String s  -> "string";
default        -> "other";

// FIX B — one arm for both
case String s      -> "string";
case Integer i     -> "int";
case null, default -> "other";
RuleReason
A type pattern never matches nullConsistent with instanceof — null is not an instance of anything
default does not catch nullMaking it do so would change the behaviour of every existing switch
case null is now legalClassic switches could not express it at all, forcing a null check before every switch

Which fix to choose depends on whether null means something. If it is a distinct outcome — "no value supplied" — give it its own arm. If it is simply unexpected input alongside everything else unrecognised, the combined form says so.

3 (medium): Why does this not compile, and what is the correct order? 
return switch (shape) {
    case Shape s            -> "a shape";
    case Circle c           -> "a circle";
    case Circle c when c.r() > 100 -> "a big circle";
};
Solution

Two unreachable cases. case Shape s matches everything, so nothing after it can ever run — and the unguarded Circle case precedes its guarded variant, so the guard would never be reached either.

return switch (shape) {
    case Circle c when c.r() > 100 -> "a big circle";   // guarded FIRST
    case Circle c                  -> "a circle";
    case Shape s                   -> "a shape";        // broadest LAST
};
RuleConsequence
Specific before generalA supertype case makes every later subtype case unreachable
Guarded before unguardedThe unguarded case matches first, so the guard never runs
Unreachable is a compile errorNot dead code — the build fails

That the compiler enforces this is the improvement over an if-else chain, where the identical mistake compiles and the later branch silently never executes.

The exhaustiveness subtlety: if Shape were sealed and the only Circle case were the guarded one, the switch would not be exhaustive — the compiler cannot prove r() > 100 always holds. A guarded case never counts towards covering its type.

4 (medium): Rewrite using record patterns. 
record Point(int x, int y) { }
record Line(Point from, Point to) { }

double length(Object o) {
    if (o instanceof Line l) {
        return Math.hypot(l.to().x() - l.from().x(),
                          l.to().y() - l.from().y());
    }
    return 0;
}
Solution 
double length(Object o) {
    if (o instanceof Line(Point(var x1, var y1), Point(var x2, var y2))) {
        return Math.hypot(x2 - x1, y2 - y1);
    }
    return 0;
}

Each value is named once, in the position it occupies, so the shape of the pattern mirrors the shape of the data. The accessor version repeats l.to() and l.from() at every use, and a reader has to reassemble the structure mentally.

ChoiceEffect
var for componentsKeeps deep patterns readable; the types are obvious from the record declarations
A named type insteadBecomes a further test — Point(int x, var y) matches only if the component is an int
NestingWhere the gain is; a single flat record barely benefits

The pattern also fails cleanly on partial matches. If from were somehow not a Point, the whole pattern simply does not match — whereas the accessor version would have compiled only because the types were already fixed.

Where this becomes genuinely powerful is combined with a sealed hierarchy, where the switch destructures and dispatches at once, and the compiler still proves exhaustiveness.

5 (hard): Evaluate this design. Animal and its subtypes are yours. 
String sound(Animal a) {
    return switch (a) {
        case Dog d -> "woof";
        case Cat c -> "meow";
        default    -> "...";
    };
}
Solution

This is polymorphism written by hand, and the default makes it worse. Since you own the hierarchy, the behaviour belongs on the type.

abstract class Animal {
    abstract String sound();
}
class Dog extends Animal { @Override String sound() { return "woof"; } }
class Cat extends Animal { @Override String sound() { return "meow"; } }

a.sound();          // dispatch, and no call site to update
ProblemConsequence
Dispatch at the call siteEvery new subtype means finding every such switch
default presentA new subtype compiles and silently returns "..." — no build error
Behaviour separated from dataA Dog's sound is defined somewhere other than Dog

If the hierarchy were sealed and default removed, the switch would at least be exhaustive and adding a subtype would break the build. That makes it defensible — but a method on the type is still better here, because the behaviour is intrinsic to the animal.

The switch becomes the right choice when the axis flips. If the behaviour belongs to the caller — a UI colour, a serialisation format — putting it on Animal would drag presentation into the domain, and an exhaustive switch in the appropriate layer is correct.

The heuristic: if new types are more likely, put behaviour on the type. If new operations are more likely over a closed set, use sealed types and switches.

6 (hard): Design a JSON value model with sealed types and pattern matching, and state what the compiler guarantees.
Solution 
sealed interface Json
    permits JsonNull, JsonBool, JsonNum, JsonStr, JsonArr, JsonObj { }

record JsonNull()                            implements Json { }
record JsonBool(boolean value)               implements Json { }
record JsonNum(double value)                 implements Json { }
record JsonStr(String value)                 implements Json { }
record JsonArr(List<Json> items)             implements Json { }
record JsonObj(Map<String, Json> fields)     implements Json { }

static String render(Json j) {
    return switch (j) {
        case JsonNull()        -> "null";
        case JsonBool(var b)   -> String.valueOf(b);
        case JsonNum(var n)    -> String.valueOf(n);
        case JsonStr(var s)    -> "\"" + escape(s) + "\"";
        case JsonArr(var items) -> items.stream()
                .map(Json::render)
                .collect(joining(",", "[", "]"));
        case JsonObj(var f)    -> f.entrySet().stream()
                .map(e -> "\"" + e.getKey() + "\":" + render(e.getValue()))
                .collect(joining(",", "{", "}"));
    };                                   // exhaustive — no default
}
The compiler guaranteesHow
Every JSON kind is handledThe sealed permits clause closes the set
Adding a kind updates every consumerEach exhaustive switch fails until the case is added
No null-kind confusionJsonNull is a value, distinct from a Java null
Structural equalityGenerated recursively, so two equal documents compare equal — which makes tests trivial

JsonNull as a record rather than a Java null is the important modelling choice. JSON null is a legitimate value distinct from "absent", and representing it as null would collapse that distinction and reintroduce null checks throughout.

The defensive-copy obligation still applies. JsonArr and JsonObj hold mutable collections, so their compact constructors need List.copyOf and Map.copyOf — otherwise the "immutable" document can be mutated through the list that was passed in.

What this replaces: a class with a type enum and six nullable fields, where every consumer checks the discriminator and trusts that the right field is populated. Here the wrong field does not exist.

The limit is the same as always: sealing means no third party can add a JSON kind — which for JSON is correct, since the set is fixed by the specification. For an extensible format it would be wrong.

🎯 Key Takeaways

  • An instanceof pattern tests, casts and binds in one construct, removing a cast that could drift from the test.
  • Flow scoping puts the pattern variable in scope wherever the compiler can prove the match — including after an early return in the negated branch.
  • Type patterns work as switch labels since Java 21, with when guards refining them.
  • A pattern switch throws on null unless case null is present — default does not cover it.
  • A type pattern never matches null, consistent with instanceof.
  • Case order matters and unreachable cases are compile errors — an improvement over silent dead branches in an if-else chain.
  • Guarded cases must precede their unguarded counterpart.
  • A guarded case does not count towards exhaustiveness, since the guard cannot be proven always true.
  • Record patterns destructure in the pattern, and nesting is where they earn their place.
  • var keeps deep patterns readable; a named type becomes a further test.
  • Over a sealed type the compiler proves exhaustiveness, so no default is needed — or wanted.
  • Adding default to a sealed switch discards the guarantee.
  • A pattern chain over types you own is hand-written dispatch — put the behaviour on the type instead.
  • Patterns win when the behaviour belongs to the caller, the types are not yours, or the match depends on structure and values.
  • New types favour polymorphism; new operations over a closed set favour sealed types and switches.
