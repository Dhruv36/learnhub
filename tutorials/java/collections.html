Collections Framework Core Libraries

What you'll master: choosing the right collection from the access pattern rather than from habit — why ArrayList beats LinkedList even for the operations LinkedList is supposed to win, because O(1) insertion still costs an O(n) traversal to reach the position, and pointer chasing defeats the cache; why List.of(), Arrays.asList() and new ArrayList<>() are three different things that all look like lists, and which operations throw on each; the contains difference that turns a working feature into a timeout — O(n) on a list, O(1) on a set; why Map.get returning null is ambiguous and what replaces it; and the modern factory methods, which are immutable, reject null, and are the right default. Prerequisites: equals & hashCode — hash-based collections depend entirely on that contract — and Arrays.

Part 2 — ArrayList vs LinkedList

  THE TEXTBOOK TABLE SAYS LinkedList WINS AT INSERTION.
  IN PRACTICE IT ALMOST NEVER DOES.

    ArrayList     get(i)          O(1)     one multiply-add
                  add(end)        O(1)*    amortised; occasional copy
                  add(0, x)       O(n)     shift everything right
                  remove(i)       O(n)     shift everything left

    LinkedList    get(i)          O(n)     walk the chain
                  add(end)        O(1)
                  add(0, x)       O(1)
                  remove(node)    O(1)     IF you already hold the node

  THE CATCH IS IN THAT LAST LINE. O(1) removal requires you to already
  have the node. Removing "the element at index 5000" costs an O(n)
  walk to find it, so the total is O(n) — the same as ArrayList, and
  slower in wall-clock terms.

  WHY SLOWER AT THE SAME COMPLEXITY: memory layout.

    ArrayList    one contiguous block. Iterating pulls ~16 elements
                 per cache line, so a scan is close to free after the
                 first miss.

    LinkedList   a separate node object per element, scattered across
                 the heap. Every step is a pointer dereference and a
                 likely cache miss — and each node carries an object
                 header plus two pointers, so it uses roughly 3-4x the
                 memory of the same data in an ArrayList.

  A cache miss is on the order of 100x slower than a hit. That
  constant factor dominates the asymptotic difference at every size
  you will actually meet.

  SO WHEN IS LinkedList RIGHT? Essentially: when you need a Deque and
  do not want ArrayDeque's resizing, or when you hold ListIterators
  and remove through them. Both are rare. The honest default is
  ArrayList, and ArrayDeque when you want a queue or stack.

Part 3 — The contains Cliff

  THE SAME METHOD NAME, WILDLY DIFFERENT COST

    list.contains(x)     O(n)   scans, calling equals on each element
    set.contains(x)      O(1)   one hash, one bucket, one comparison
    map.containsKey(x)   O(1)   the same

  This is the most common accidental quadratic in Java:

    for (Order order : orders) {              // n
        if (processedIds.contains(order.id()))  // O(n) if a List
            continue;
        …
    }

  With processedIds as a List this is O(n²). At 1,000 orders it is a
  million comparisons — fast enough that nobody notices. At 100,000
  it is ten billion, and the endpoint times out.

  The fix is one word:

    List<String> processedIds = …;      // O(n) lookups
    Set<String>  processedIds = …;      // O(1) lookups

  NOTHING ELSE CHANGES. Same interface for add and iterate, same
  code, and the algorithmic class of the whole loop changes.

  THE RULE: if you call contains() in a loop, the collection should be
  a Set — or a Map, if you need the associated value.

    List<String> list = List.of("a", "b");

  So a method returning List.of(...) hands callers something that
  looks modifiable and is not. That is usually what you want — the
  caller should not be modifying your return value — but it must be
  documented, because the compiler will not say so.

  list must not contain nulls" into an enforced rule rather than an
  assumption. It does mean List.of(mayBeNull) throws, so a nullable
  value needs handling first.

Part 5 — Maps, and the null Ambiguity

Map<String, Integer> counts = new HashMap<>();

counts.get("missing")            // null — but does that mean
                                 // "absent" or "mapped to null"?
counts.containsKey("missing")    // the unambiguous question

  HashMap PERMITS a null key and null values, so get() returning null
  genuinely cannot distinguish the two cases. That ambiguity is why
  the modern methods exist:

    getOrDefault(k, 0)                     absent -> a default
    putIfAbsent(k, v)                      only if not already there
    computeIfAbsent(k, k -> new ArrayList<>())   create on demand
    merge(k, 1, Integer::sum)              the counter idiom
    compute(k, (k, v) -> …)                update from the old value

  THE TWO THAT REPLACE MOST BOILERPLATE:

    counts.merge(word, 1, Integer::sum);

    // Multimap — replaces get, null-check, create, put
    index.computeIfAbsent(key, k -> new ArrayList<>()).add(value);

  Both are also atomic on ConcurrentHashMap, which the read-then-write
  version is not — so the idiom is correct in both settings, and the
  hand-rolled version is correct in neither.

Part 6 — Sizing, Views and Sorting

  PRE-SIZE WHEN YOU KNOW THE SIZE

    new ArrayList<>()            starts at 10, grows by ~1.5x with a
                                 copy each time
    new ArrayList<>(10_000)      one allocation, no copies

    new HashMap<>()              16 buckets, REHASHES at 12 entries,
                                 then at 24, 48, …
    new HashMap<>(1000)          fewer rehashes — though note the
                                 argument is capacity, not expected
                                 size, so it still resizes at 750

  Each resize reallocates and re-inserts everything. For a map built
  once and read many times, pre-sizing removes that entirely.

  VIEWS ARE WINDOWS, NOT COPIES

    list.subList(0, 5)           a VIEW — writes pass through, and
                                 structurally modifying the parent
                                 invalidates it
    map.keySet()                 a VIEW — removing from it removes
                                 the ENTRY from the map
    Arrays.asList(arr)           a VIEW over the array

  keySet().remove(k) removing the whole entry surprises people, and
  it is deliberate: the set is a window onto the map, not a snapshot.
  Take a copy — new HashSet<>(map.keySet()) — when you need
  independence.

  SORTING

    list.sort(Comparator.comparing(Order::total)
                        .thenComparing(Order::id));    // total order
    list.sort(null);                                   // natural order

  Sorting an immutable list throws; sorting a subList sorts that
  RANGE of the parent, in place. And a comparator used with TreeSet
  must be consistent with equals — see Equality.

Interview Questions

Beginner: When would you use a Set rather than a List?

When duplicates are meaningless and membership testing matters.

A List keeps insertion order and permits duplicates; a Set guarantees uniqueness and — for HashSet — gives no order at all.

The decisive practical difference is contains: O(n) on a list, because it scans calling equals, versus O(1) on a hash set. So any code that repeatedly asks "have I seen this?" should use a set, and that single change can move a loop from quadratic to linear.

The variants matter too: LinkedHashSet keeps insertion order, which is worth reaching for when output or test assertions depend on ordering, and TreeSet keeps them sorted at O(log n).

The requirement to remember is that a HashSet depends entirely on equals and hashCode being correct and stable — a mutable element makes its own entry unreachable.

Beginner: What is the difference between List.of(), Arrays.asList() and new ArrayList<>()?

Three different things that all satisfy the List interface.

new ArrayList<>() is a normal, growable, mutable list backed by its own array.

Arrays.asList(...) is a fixed-size view over an array. You can set elements — and that writes through to the underlying array — but add and remove throw, because there is no way to grow the array behind it.

List.of(...) is fully immutable: every mutating method throws, and it additionally rejects null elements.

The catch common to the last two is that the restriction is not in the type. All three are declared as List, so list.add(x) compiles and fails at runtime. Java has no ImmutableList type in the standard library, which means a method returning List.of(...) must document that the result is unmodifiable — the compiler will not.

Mid: Why is ArrayList usually faster than LinkedList, even for insertion?

Two reasons, and the second is the bigger one.

First, the complexity table is misleading about what you actually do. LinkedList insertion is O(1) only when you already hold the node. Inserting at "index 5000" requires walking 5000 links to find it, so the operation is O(n) overall — the same as ArrayList's shift, and with far worse constants.

Second, memory layout. An ArrayList is one contiguous block, so iterating pulls roughly sixteen elements per cache line and a scan is nearly free after the first miss. A LinkedList allocates a node object per element, scattered across the heap, so every step is a pointer dereference and a probable cache miss — and a miss costs on the order of a hundred times a hit.

It is also much larger: each node carries an object header and two pointers, so the same data uses roughly three to four times the memory, which pressures the collector as well.

So the constant factors dominate the asymptotic difference at every size you will meet in practice. The honest default is ArrayList, with ArrayDeque when you want a queue or a stack — LinkedList's remaining niche is holding a ListIterator and removing through it, which is rare.

Mid: Why does map.get(key) returning null not mean the key is absent?

Because HashMap permits null values, so null is a legitimate mapping. get returns null both when the key is missing and when it is present but mapped to null, and the two cases are indistinguishable from the return value.

containsKey answers the unambiguous question, but using both means two lookups.

That ambiguity is why the modern methods exist. getOrDefault(k, 0) covers the common "absent means a default" case in one call. computeIfAbsent covers "create it if it is not there". merge covers "combine with what is there, or start fresh".

Two of those replace most map boilerplate: counts.merge(word, 1, Integer::sum) is the counter idiom, and index.computeIfAbsent(k, k -> new ArrayList<>()).add(v) is the multimap idiom.

The reason to prefer them beyond brevity is that both are atomic on ConcurrentHashMap, where the hand-rolled get-check-put sequence is not. So the idiomatic version is correct in both single-threaded and concurrent settings, and the manual version is correct in neither without extra work.

Senior: An endpoint is fast in staging and times out in production. How do you find a collection-related cause?

The shape to look for is an accidental quadratic: something that scales with the square of the data, which is imperceptible at staging volumes and fatal at production ones.

The most common instance by far is contains on a List inside a loop. At a thousand elements that is a million comparisons and finishes instantly; at a hundred thousand it is ten billion, and the request never returns. Nothing about the code looks wrong — the fix is changing one declaration from List to Set.

Others in the same family: list.remove(object) in a loop, which is O(n) per call; indexOf in a loop; and building a string with +=, which is the same quadratic in a different guise.

How I would find it: a profiler or an async-profiler flame graph on the slow request, which shows the time concentrated in ArrayList.indexOf or String.concat rather than in anything that looks like business logic. Failing that, thread dumps taken a few seconds apart — a quadratic scan shows the same frame every time.

The check I would then add is a test that runs the endpoint with production-scale data. The reason these reach production is that fixtures are small by design, so the asymptotic difference never appears in CI — and it is cheap to generate ten thousand rows in a test.

The related non-collection cause worth ruling out at the same time is N+1 queries, which has an identical signature: fine in staging with ten rows, fatal with ten thousand.

Senior: How would you build an LRU cache with the standard library?

LinkedHashMap supports it directly, which surprises people who expect to need a library or a hand-rolled doubly-linked list plus map.

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruCache(int capacity) {
        super(16, 0.75f, true);          // true = ACCESS order
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}

Two pieces do the work. The three-argument constructor's accessOrder flag makes get move an entry to the end, so the head is always the least recently used. And removeEldestEntry is a hook the map calls after every insertion — returning true evicts the head.

The caveats matter for production use. It is not thread-safe, and it cannot simply be wrapped, because even get mutates the ordering — so concurrent reads need external synchronisation, which serialises them. There is no TTL, no weighting by entry size, and no statistics.

So for a real cache I would reach for Caffeine, which gives concurrency, expiry, size-based eviction, refresh-ahead and hit-rate metrics, and uses a better eviction policy than strict LRU. The LinkedHashMap version is right when the cache is small, single-threaded or already externally locked, and you do not want a dependency.

It is also worth noting this is one of the few places where extending a JDK collection is reasonable — removeEldestEntry is a documented extension point, which is exactly the "designed for inheritance" case from the Inheritance lesson.

The distinction is immutable versus fixed-size. List.of forbids all change; Arrays.asList forbids only structural change, because it is a view over an array whose length cannot change.

3 (medium): This is fine with 1,000 orders and times out with 100,000. Fix it. 
List<String> processed = loadProcessedIds();    // 100,000 ids

for (Order order : orders) {                    // 100,000 orders
    if (processed.contains(order.id())) continue;
    process(order);
}
Solution

List.contains is O(n) — it scans the list calling equals. Inside a loop over n orders that makes the whole thing O(n²).

  1,000 orders  x   1,000 ids  =        1,000,000 comparisons  (instant)
100,000 orders  x 100,000 ids  = 10,000,000,000 comparisons  (times out)

// THE FIX — one word
Set<String> processed = new HashSet<>(loadProcessedIds());
// contains is now O(1); the loop is O(n)

Nothing else changes. The loop body, the interface used for iteration, and the calling code are all identical — but the algorithmic class of the whole operation moves from quadratic to linear.

Why it survives review and testing
The code reads correctly — contains expresses exactly the right intent
Test fixtures are small by design, so the quadratic term never dominates in CI
It degrades gradually with data growth rather than failing on a specific input

The general rule: if contains appears inside a loop, the collection should be a Set. If you need the associated value rather than just membership, a Map.

The same shape in other disguises — list.remove(object) in a loop, indexOf in a loop, and string += in a loop — all quadratic, all invisible at small scale.

What I would add after fixing it is a test at production scale. These reach production precisely because fixtures are small, and generating ten thousand rows in a test is cheap next to a timeout in production.

The concurrency point is the substantive one. The hand-written versions are not merely verbose — they are wrong on a concurrent map, and wrong in a way that appears only under load and loses data silently. The idiomatic versions are correct in both settings, which is why they should be the default even in single-threaded code.

Two details worth knowing. merge removes the entry if the remapping function returns null, which is how you decrement-and-remove in one call. And the function passed to computeIfAbsent must not modify the map itself — doing so can corrupt a HashMap or deadlock a ConcurrentHashMap.

For the grouping case specifically, if you are building the whole index from a collection, Collectors.groupingBy expresses it in one expression — see Streams.

5 (hard): Explain each result. 
Map<String, Integer> map = new HashMap<>(Map.of("a", 1, "b", 2));

Set<String> keys = map.keySet();
keys.remove("a");
System.out.println(map);              // ?

List<Integer> nums = new ArrayList<>(List.of(1, 2, 3, 4, 5));
List<Integer> part = nums.subList(1, 3);
part.set(0, 99);
System.out.println(nums);             // ?
nums.add(6);
System.out.println(part.size());      // ?
Solution 
map    -> {b=2}              removing from keySet removed the ENTRY
nums   -> [1, 99, 3, 4, 5]   writing through the subList hit the parent
part.size() -> ConcurrentModificationException

Both are views, not copies. keySet() is a window onto the map's keys, and subList is a window onto a range of the list. Neither holds its own data, so every write passes through to the backing collection.

keySet().remove() removing the whole mapping is deliberate and documented, and it surprises people who expect a set of keys to be a snapshot. It also means keySet().removeIf(...) is a legitimate way to filter a map in place.

The third result is the sharpest. A subList is only valid while the parent is not structurally modified. Adding to nums increments its modCount, so the next operation on part detects the mismatch and throws — the same fail-fast mechanism as ConcurrentModificationException during iteration.

Take a copy when you need independence — new HashSet<>(map.keySet()) or new ArrayList<>(list.subList(1, 3)). The view is the efficient default and the copy is the safe one, and knowing which you have is the whole point.

The useful side of subList is that operations on it apply to that range of the parent — list.subList(0, 5).clear() removes the first five elements in one call.

6 (hard): A service holds a HashMap shared by request threads. Reads are frequent, writes rare. Someone proposes Collections.synchronizedMap. Evaluate.
Solution

It is correct for single operations and insufficient in two ways.

ProblemDetail
Compound operations still raceEach method is individually locked, but if (!map.containsKey(k)) map.put(k, v) is two operations with a gap between them
Iteration is not coveredYou must synchronise on the map manually around any iteration, or get ConcurrentModificationException
All reads serialiseOne lock for the whole map, so frequent reads block each other for no reason
ConcurrentHashMap<String, Config> map = new ConcurrentHashMap<>();

map.computeIfAbsent(key, this::load);       // ATOMIC, no external lock
map.merge(key, 1, Integer::sum);            // ATOMIC
map.forEach((k, v) -> …);                   // safe, no CME

ConcurrentHashMap is better on every axis here. Reads are essentially lock-free, writes lock only a single bin rather than the whole map, iteration is weakly consistent so it never throws, and the compound operations are genuinely atomic rather than needing a wrapper.

Given "reads frequent, writes rare", the alternative worth considering is CopyOnWriteArrayList's map equivalent — an immutable map swapped wholesale on each write, held in a volatile field. Reads then involve no synchronisation at all, and writes copy the whole map. That is the right trade when writes are genuinely rare — a configuration reloaded hourly — and terrible when they are not.

The caveat on ConcurrentHashMap is that atomicity is per operation, not across operations. Two computeIfAbsent calls are each atomic and the pair is not, so an invariant spanning several keys still needs explicit coordination.

And size() is approximate under concurrent modification — accurate at a quiescent moment, and a snapshot of a moving target otherwise. Code that branches on the exact size of a concurrent map is usually wrong for that reason.

🎯 Key Takeaways

  • Pick from the access pattern: duplicates, order, lookup by key, work at the ends.
  • Map is not a Collection — iterate entrySet(), not the map.
  • ArrayList beats LinkedList almost always — reaching a position is still O(n), and contiguity beats pointer chasing.
  • ArrayDeque for stacks and queues, not Stack or LinkedList.
  • contains on a List in a loop is the classic accidental quadratic — invisible at 1,000, a timeout at 100,000.
  • List.of is immutable and rejects nulls; Arrays.asList is a fixed-size view that writes through — and both compile before throwing.
  • get returning null is ambiguous; use containsKey or getOrDefault.
  • merge and computeIfAbsent replace most map boilerplate, and are atomic on a concurrent map where get-check-put is not.
  • Iterate entrySet() rather than keys plus get.
  • Views are windows, not copies — keySet().remove deletes the entry, and a structural change to a list invalidates its subList.
  • Pre-size when the size is known; every resize reallocates and re-inserts.
  • A mutable key makes its own entry unreachable — immutable keys, ideally records.
  • ConcurrentHashMap, not synchronizedMap — the wrapper serialises reads and still leaves compound operations racy.
  • LinkedHashMap with access order and removeEldestEntry is an LRU cache in a few lines — and Caffeine is the right answer for a real one.
  • Avoid Vector, Hashtable and Stack — legacy, synchronised on every call.
