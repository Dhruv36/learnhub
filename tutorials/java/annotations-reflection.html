Annotations & Reflection Core Libraries

What you'll master: annotations as metadata that does nothing by itself — something must read them, and RetentionPolicy decides who can; why @Override is SOURCE and @Autowired is RUNTIME, and what breaks when you get that wrong; reflection's real API — getDeclaredFields vs getFields, setAccessible, and the InvocationTargetException wrapper that hides your actual exception; the measured cost of reflection and why the first-call number is not the steady-state number; erasure's effect on what you can recover at runtime (and the one place generic types survive); and why annotation processors and compile-time generation have been displacing reflection. Prerequisites: Generics and OOP.

Part 1 — Annotations Are Inert

  AN ANNOTATION IS METADATA ATTACHED TO A DECLARATION. It has NO
  behaviour of its own. @Transactional does not start a transaction —
  Spring reads it and starts one. Delete Spring and the annotation is
  a comment the compiler happens to keep.

  This is the single most useful thing to understand about them:
  ALWAYS ASK "WHO READS THIS?"

    the COMPILER            @Override, @FunctionalInterface,
                            @SuppressWarnings, @Deprecated
    an ANNOTATION PROCESSOR @Entity (Hibernate metamodel), Lombok,
    at build time           MapStruct, Dagger
    a FRAMEWORK at runtime  @Autowired, @Test, @JsonProperty
    NOBODY                  your own @NotNull with no checker —
                            documentation with syntax

  THE THREE FORMS:

    @Override                          marker — no elements
    @SuppressWarnings("unchecked")     single element named `value`
    @Column(name="id", nullable=false) full

  `value` is special: if it is the only element you supply, the name
  may be omitted. That is why @SuppressWarnings("unchecked") works.

  THE BUILT-IN ONES EARN THEIR PLACE:

    @Override            compile error if it overrides nothing —
                         catches a typo'd method name or a changed
                         signature in the parent
    @FunctionalInterface compile error if the interface gains a
                         second abstract method
    @Deprecated          warning at use sites; pair with
                         @deprecated javadoc saying WHAT TO USE
    @SafeVarargs         suppresses the generic-varargs warning when
                         you have verified the array is not stored

  @Override IS THE ONE PEOPLE UNDER-USE. It costs nothing and turns a
  silent "this method is never called" bug into a build failure.

Part 2 — Retention Decides Who Can See It

  @Retention CONTROLS HOW FAR THE ANNOTATION SURVIVES:

    SOURCE    discarded by the compiler. Visible only to the compiler
              and to annotation PROCESSORS. @Override, Lombok.
    CLASS     written into the .class file, NOT loaded into memory.
              Visible to bytecode tools (ProGuard, ASM), not to
              reflection. This is the DEFAULT.
    RUNTIME   loaded and readable via reflection. Required by every
              framework that inspects your classes at run time.

  THE DEFAULT IS CLASS, AND THAT IS THE TRAP:

    public @interface MyAnnotation { }       // CLASS retention

    field.getAnnotation(MyAnnotation.class); // returns NULL, always

  No error, no warning — just null. You will look at the field, see
  the annotation on it, and conclude reflection is broken. It is not:
  the annotation was never loaded.

  ALWAYS WRITE THE RETENTION EXPLICITLY if anything reads it at
  runtime.

  @Target RESTRICTS WHERE IT MAY BE PLACED:

    TYPE  FIELD  METHOD  PARAMETER  CONSTRUCTOR
    LOCAL_VARIABLE  ANNOTATION_TYPE  PACKAGE
    TYPE_PARAMETER  TYPE_USE          (Java 8+)

  Omitting @Target means "anywhere", which produces annotations placed
  in nonsensical positions and no compiler help.

  TWO MORE META-ANNOTATIONS WORTH KNOWING:

    @Inherited   a subclass inherits the annotation from its
                 superclass — CLASSES ONLY, not methods or
                 interfaces, which surprises people
    @Repeatable  the same annotation may appear more than once on a
                 declaration; the compiler wraps them in a container

  THE JVM DOES NOT LOAD CLASS-RETENTION ANNOTATIONS at all, which is
  why CLASS is the default: it costs nothing at runtime. RUNTIME
  annotations occupy memory in the class metadata for the life of the
  class loader.
RetentionIn .class?Loaded?Read byExample
SOURCENoNoCompiler, annotation processors@Override, Lombok
CLASS (default)YesNoBytecode toolsProGuard hints
RUNTIMEYesYesReflection@Test, @Autowired

Part 3 — Writing and Reading Your Own

  A COMPLETE, WORKING EXAMPLE — a tiny validation annotation.

    @Retention(RetentionPolicy.RUNTIME)      // MUST be explicit
    @Target(ElementType.FIELD)
    public @interface MaxLength {
        int value();                          // required element
        String message() default "too long";  // optional element
    }

    public class User {
        @MaxLength(value = 50, message = "name too long")
        private String name;

        @MaxLength(10)                        // `value` name omitted
        private String code;
    }

  READING IT:

    List<String> validate(Object obj) {
        var errors = new ArrayList<String>();
        for (Field f : obj.getClass().getDeclaredFields()) {
            MaxLength ann = f.getAnnotation(MaxLength.class);
            if (ann == null) continue;
            f.setAccessible(true);            // private field
            Object v = f.get(obj);
            if (v instanceof String s && s.length() > ann.value()) {
                errors.add(f.getName() + ": " + ann.message());
            }
        }
        return errors;
    }

  THAT LOOP IS THE ENTIRE MECHANISM behind Bean Validation, Jackson,
  JPA and Spring's stereotype scanning. Everything else is caching,
  inheritance handling and error reporting.

  WHAT AN @interface MAY DECLARE — the rules are strict:

    - element types: primitives, String, Class, enum, another
      annotation, or a 1-D array of those. NOTHING ELSE.
    - no null defaults (use "" or a sentinel)
    - no parameters, no bodies, no inheritance between annotations
    - elements look like methods but are read like fields

  THE Class ELEMENT IS THE ESCAPE HATCH used by every framework:

    Class<? extends Validator> validatedBy();

  You cannot put behaviour in an annotation, so you name a class that
  has it. That is how @Constraint, @JsonSerialize and @Convert all
  work.

Part 4 — The Reflection API

  THE FOUR ENTRY POINTS TO A Class OBJECT:

    obj.getClass()             the runtime type of an instance
    String.class               a class literal
    Class.forName("com.X")     by name — the dynamic one
    ClassLoader.loadClass(n)   same, without running static init

  Class.forName RUNS STATIC INITIALIZERS by default. That matters:
  it is how the old JDBC Class.forName("com.mysql.jdbc.Driver")
  registered a driver — the side effect WAS the point.

  THE getX / getDeclaredX SPLIT CATCHES EVERYONE:

    getFields()           PUBLIC fields, INCLUDING inherited
    getDeclaredFields()   ALL fields declared HERE, including
                          private — but NOT inherited

  So neither one gives you "all fields including private and
  inherited". To get that you walk the hierarchy:

    for (Class<?> c = type; c != null; c = c.getSuperclass()) {
        for (Field f : c.getDeclaredFields()) { … }
    }

  This is why frameworks have a ReflectionUtils.doWithFields.

  INVOKING:

    Method m = obj.getClass().getMethod("process", String.class);
    Object result = m.invoke(obj, "input");

    Constructor<?> c = type.getDeclaredConstructor();
    c.setAccessible(true);
    Object instance = c.newInstance();

  InvocationTargetException IS THE ONE THAT WASTES AN AFTERNOON.
  If the invoked method throws, reflection WRAPS it:

    try {
        m.invoke(obj, arg);
    } catch (InvocationTargetException e) {
        throw e.getCause();       // ← YOUR actual exception
    }

  Log the exception itself and you get a stack trace pointing at
  Method.invoke, with your real NullPointerException hidden in the
  cause. Always unwrap.

  setAccessible(true) DEFEATS ACCESS CONTROL — but not
  unconditionally. Since Java 9 it fails for JDK internals unless the
  module opens the package:

    InaccessibleObjectException: Unable to make field
    private java.lang.String java.lang.String.value accessible

  and since 17 that is an error rather than a warning. It still works
  freely on classpath code, which is why most applications never
  notice until a library reaches into java.base.
CallReturnsIncludes private?Includes inherited?

getDeclaredFields()FieldsYesNo
getMethods()MethodsNoYes, plus Object's
getDeclaredMethods()MethodsYesNo

Part 5 — What Erasure Leaves Behind

  GENERIC TYPE ARGUMENTS ARE ERASED, so this is a dead end:

    List<String> list = new ArrayList<>();
    list.getClass();                 // class java.util.ArrayList
                                     // — no String anywhere

  BUT ERASURE APPLIES TO INSTANCES, NOT TO DECLARATIONS. Generic
  information in a class file's SIGNATURE attribute survives, and
  reflection can read it:

    class Repo { private List<String> names; }

    Field f = Repo.class.getDeclaredField("names");
    f.getType();            // interface java.util.List   (erased)
    f.getGenericType();     // java.util.List<java.lang.String>  ✓

    ParameterizedType pt = (ParameterizedType) f.getGenericType();
    pt.getActualTypeArguments()[0];  // class java.lang.String

  THE SAME WORKS FOR METHODS AND SUPERCLASSES:

    m.getGenericReturnType()
    m.getGenericParameterTypes()
    c.getGenericSuperclass()

  THIS IS HOW JACKSON DESERIALIZES List<User>. The instance cannot
  tell you, but the FIELD or the METHOD SIGNATURE can — which is why
  Jackson can populate a typed field but needs a TypeReference when
  you ask for a bare List<User> from a local variable:

    // no declaration for it to read — you supply it
    mapper.readValue(json, new TypeReference<List<User>>() {});

  The anonymous subclass exists purely so getGenericSuperclass() has
  something to read. That trick is the "super type token", and it is
  the standard workaround for erasure across the ecosystem.

  WHAT IS GENUINELY LOST: the type argument of an INSTANCE with no
  declaration behind it. new ArrayList<String>() passed as an Object
  cannot be interrogated, and no amount of reflection recovers it.

Part 6 — Cost, and the Compile-Time Alternative

  REFLECTION IS SLOWER, BUT THE HEADLINE NUMBERS MISLEAD.

  Rough order of magnitude on a modern JVM, per call, after warmup:

    direct call                    ~1 ns   (often inlined to zero)
    Method.invoke, cached Method   ~5-10 ns
    Method.invoke, getMethod each  ~1000 ns  ← the lookup dominates
    field.set with setAccessible   ~5 ns
    Class.forName + newInstance    ~microseconds

  TWO THINGS THE NUMBERS TELL YOU:

  1. THE LOOKUP, NOT THE INVOKE, IS THE COST. getMethod does a
     linear search and COPIES the Method object every call (so that
     setAccessible on your copy cannot affect anyone else's). Cache
     the Method and you remove ~99% of the overhead.

  2. THE FIRST CALLS ARE MUCH WORSE THAN THE STEADY STATE. The JVM
     generates a bytecode accessor after ~15 invocations (the
     inflation threshold); before that it uses a slow native path.
     A microbenchmark that measures 100 calls reports a number
     nothing in production will ever see.

  WHAT ACTUALLY HURTS IN PRODUCTION IS RARELY THE NANOSECONDS:

    - STARTUP TIME. Classpath scanning over thousands of classes is
      why a large Spring app takes seconds to boot.
    - NO INLINING across a reflective call, so surrounding
      optimisations are lost.
    - NO COMPILE-TIME CHECKING. A renamed method is a runtime
      failure, and refactoring tools cannot see string-based lookups.
    - GRAALVM NATIVE IMAGE needs every reflective target declared in
      configuration, because the closed-world analysis cannot see
      them.

  THE INDUSTRY RESPONSE: MOVE IT TO COMPILE TIME.

    ANNOTATION PROCESSORS (javax.annotation.processing) read
    SOURCE-retention annotations during compilation and GENERATE
    code. Lombok, MapStruct, Dagger, Micronaut and Quarkus all work
    this way. The output is ordinary Java: inlinable, checkable,
    native-image friendly, and visible in a debugger.

    METHODHANDLES (java.lang.invoke) are the runtime alternative.
    A MethodHandle bound to a static final field is JIT-visible and
    can reach direct-call speed, unlike Method.invoke. It is the
    mechanism behind lambdas and string concatenation.

  THE TRADE THAT MATTERS: reflection buys you a framework that works
  on classes it has never seen, at the cost of startup, checking and
  native-image compatibility. Compile-time generation gives all of
  that back, at the cost of a build-time dependency and generated
  code you have to look at. Spring chose reflection in 2003 for good
  reasons; Micronaut and Quarkus chose processors in 2018 for equally
  good ones, and the constraint that changed was containers.

Interview Questions

Beginner: What is an annotation, and does it change behaviour?

An annotation is metadata attached to a declaration. By itself it does nothing — @Transactional does not begin a transaction; Spring reads it and begins one.

So the useful question about any annotation is who reads it:

  • the compiler — @Override, @FunctionalInterface
  • an annotation processor at build time — Lombok, MapStruct, Dagger
  • a framework at runtime via reflection — @Test, @Autowired
  • nobody — a custom @NotNull with no checker is documentation with syntax

@Override is the one worth using everywhere: it costs nothing and turns "this method is silently never called" into a compile error.

Beginner: Why does getAnnotation return null for an annotation that is clearly on the field?

Almost always a missing @Retention(RetentionPolicy.RUNTIME). The default is CLASS, which writes the annotation into the .class file but never loads it into memory — so reflection cannot see it.

There is no error and no warning; you get null, and you conclude reflection is broken.

RetentionVisible to
SOURCECompiler and annotation processors only
CLASS (default)Bytecode tools; not reflection
RUNTIMEReflection

The default is CLASS because runtime annotations occupy class metadata for the life of the class loader — the JVM avoids paying for what nothing reads.

Mid: How do you read all fields of a class, including private and inherited ones?

Neither method does it alone, which is the point people miss:

  • getFields() — public only, but includes inherited
  • getDeclaredFields() — all modifiers, but only this class
for (Class<?> c = type; c != null && c != Object.class;
     c = c.getSuperclass()) {
    for (Field f : c.getDeclaredFields()) {
        if (f.isSynthetic() || Modifier.isStatic(f.getModifiers())) continue;
        f.setAccessible(true);
        …
    }
}

Two details worth including: skip synthetic fields — the compiler adds this$0 for inner classes and $jacocoData under coverage tools, and both will confuse a serialiser — and skip statics unless you specifically want them.

This loop is exactly why every framework ships a ReflectionUtils.doWithFields: the hierarchy walk, the synthetic filter and the Field cache are the same every time.

Mid: Generics are erased, so how does Jackson deserialize into List<User>?

Because erasure applies to instances, not to declarations. A class file keeps a Signature attribute holding the generic types of fields, methods and superclasses, and reflection reads it:

Field f = Repo.class.getDeclaredField("users");
f.getType();          // interface java.util.List        (erased)
f.getGenericType();   // java.util.List<com.example.User>  ✓

So when Jackson populates a field, it has a declaration to read and can construct the right elements.

When there is no declaration — you ask for a List<User> into a local variable — you must supply the type yourself:

mapper.readValue(json, new TypeReference<List<User>>() {});

That anonymous subclass exists solely so getGenericSuperclass() has something to read. It is the super type token idiom, and it appears across the ecosystem — Guice's TypeLiteral, Spring's ParameterizedTypeReference.

What is genuinely unrecoverable is an instance with no declaration behind it: a new ArrayList<String>() passed as Object cannot be interrogated at all.

Senior: How expensive is reflection really, and what actually costs you?

After warmup, with a cached Method, invoke costs roughly 5–10 ns against ~1 ns for a direct call. Uncached, getMethod on every call costs around 1000 ns — the lookup dominates by two orders of magnitude, because it does a linear search and returns a defensive copy so your setAccessible cannot affect other callers.

Two measurement traps. The JVM generates a bytecode accessor only after about 15 invocations (the inflation threshold), so a short benchmark measures the slow native path and reports a number production never sees. And reflective calls block inlining, so the real cost includes optimisations lost in the surrounding code, which a per-call microbenchmark cannot see at all.

In production the nanoseconds are rarely the problem. What costs is startup — classpath scanning over thousands of classes is why a large Spring application takes seconds to boot — the loss of compile-time checking, and GraalVM native image, whose closed-world analysis cannot see reflective targets without explicit configuration.

The practical rules: cache Method, Field and Constructor objects; never look up inside a loop; and where you need speed at runtime, a MethodHandle in a static final field is JIT-visible and can reach direct-call speed, unlike Method.invoke.

Senior: Why are new frameworks replacing reflection with annotation processing?

Because the constraints changed. Reflection buys a framework that works on classes it has never seen — which is exactly what you want for a long-running server started once and run for weeks. Spring chose it in 2003 and was right.

Containers and serverless inverted the trade. When a process starts thousands of times a day, or scales to zero, startup time is the performance metric — and reflective startup is dominated by classpath scanning and proxy generation. A 3-second boot that nobody noticed on a long-lived VM is unacceptable per-request.

GraalVM native image made it structural rather than merely slow. Closed-world analysis must see every reachable method at build time, and reflection is invisible to it. Every reflective target needs a configuration entry, which is fragile and often generated by running the app under a tracing agent — a poor foundation.

Annotation processors move the work to compile time. Micronaut, Quarkus, Dagger and MapStruct read SOURCE-retention annotations during compilation and emit ordinary Java. The result is inlinable, type-checked, debuggable, and visible to native image because it is just code.

What is given up is real: longer builds, generated code you must read when something is wrong, less runtime dynamism, and IDE support that depends on the processor running. Spring's model also allows behaviour that cannot be known at compile time, which is why Spring itself moved partway — AOT processing in Spring 6 generates at build time what it used to derive at startup.

The takeaway I would give a team: this is not "reflection is bad". It is that the cost of reflection is paid at startup and at the native-image boundary, and if neither matters to your deployment, the flexibility is still worth it.

🏋️ Graded Exercises

1 (easy): Why does this print null? 
@Target(ElementType.FIELD)
public @interface Audited { }

class Account { @Audited private String id; }

Field f = Account.class.getDeclaredField("id");
System.out.println(f.getAnnotation(Audited.class));
Solution

No @Retention, so it defaults to CLASS — written to the class file but never loaded, therefore invisible to reflection.

@Retention(RetentionPolicy.RUNTIME)   // ← the fix
@Target(ElementType.FIELD)
public @interface Audited { }

The failure mode is what makes this costly: no error, no warning, just null. You can stare at the annotation on the field and conclude reflection is broken.

Why CLASS is the default: runtime annotations live in class metadata for the lifetime of the class loader, so the JVM does not pay for what nothing reads. Most annotations historically were compiler or bytecode-tool hints.

Habit worth forming: write @Retention and @Target on every annotation you declare. @Target costs one line and turns a nonsensical placement into a compile error.

2 (easy): The invoked method throws NullPointerException, but the log shows a stack trace inside Method.invoke. Why, and what do you write? 
try {
    method.invoke(target, args);
} catch (Exception e) {
    log.error("call failed", e);
}
Solution

Reflection wraps any exception the target throws in an InvocationTargetException. You are logging the wrapper, whose stack trace ends at Method.invoke; the real exception is in getCause().

try {
    method.invoke(target, args);
} catch (InvocationTargetException e) {
    throw new ServiceException("call failed", e.getCause());   // unwrap
} catch (IllegalAccessException e) {
    throw new IllegalStateException("not accessible: " + method, e);
}
ExceptionMeans
InvocationTargetExceptionThe method threw — unwrap getCause()
IllegalAccessExceptionAccess denied — needs setAccessible(true)
IllegalArgumentExceptionWrong argument count or types
InaccessibleObjectExceptionModule encapsulation refused the access

Catching bare Exception is what hides the distinction. The four cases mean completely different things — one is a bug in the target, one is a missing setAccessible, one is a caller bug, one is a module configuration problem — and lumping them together loses that.

3 (medium): Write a method that copies matching fields from one object to another, including private and inherited ones. Note what you must skip.
Solution 
static void copy(Object src, Object dst) throws Exception {
    Map<String, Field> targets = new HashMap<>();
    for (Class<?> c = dst.getClass(); c != null && c != Object.class;
         c = c.getSuperclass()) {
        for (Field f : c.getDeclaredFields()) {
            if (skip(f)) continue;
            f.setAccessible(true);
            targets.putIfAbsent(f.getName(), f);   // subclass wins
        }
    }
    for (Class<?> c = src.getClass(); c != null && c != Object.class;
         c = c.getSuperclass()) {
        for (Field s : c.getDeclaredFields()) {
            if (skip(s)) continue;
            Field t = targets.get(s.getName());
            if (t == null || !t.getType().isAssignableFrom(s.getType()))
                continue;
            s.setAccessible(true);
            t.set(dst, s.get(src));
        }
    }
}

static boolean skip(Field f) {
    int m = f.getModifiers();
    return f.isSynthetic() || Modifier.isStatic(m) || Modifier.isFinal(m);
}
Must handleWhy
Walk getSuperclass()getDeclaredFields does not include inherited
isSynthetic()Compiler-added this$0, $jacocoData
Skip staticShared state, not instance data
Skip finalSetting one may appear to work but the JIT can have already folded the constant
isAssignableFromSame name, incompatible type → IllegalArgumentException
putIfAbsent walking down-upA shadowed field in a subclass should win

The final case is the one that produces ghost bugs. setAccessible lets you write a final field, but constant folding means readers may keep seeing the old value — the write "works" and nothing observes it.

In production, use a mapper. MapStruct generates this at compile time with type checking; hand-rolled reflective copiers silently skip mismatches and are hard to debug.

4 (medium): Recover the element type of this field at runtime. 
class Repo {
    private Map<String, List<User>> index;
}

f.getType();          // interface java.util.Map        ← erased

5 (hard): This runs in a request path. Find the performance problem and say how much it costs. 
public Object handle(Object target, String methodName, Object arg) {
    try {
        Method m = target.getClass().getMethod(methodName, String.class);
        return m.invoke(target, arg);
    } catch (Exception e) {
        throw new RuntimeException(e);
    }
}
Solution

getMethod is inside the hot path. The lookup does a linear search over the class hierarchy and returns a defensive copy of the Method — so your setAccessible cannot affect other callers — every single call.

OperationApprox. cost
Direct call~1 ns (often inlined away)
invoke, cached Method~5–10 ns
getMethod + invoke~1000 ns
private static final Map<String, Method> CACHE = new ConcurrentHashMap<>();

public Object handle(Object target, String methodName, Object arg) {
    Method m = CACHE.computeIfAbsent(
        target.getClass().getName() + "#" + methodName,
        k -> {
            try { return target.getClass().getMethod(methodName, String.class); }
            catch (NoSuchMethodException e) { throw new IllegalArgumentException(e); }
        });
    try {
        return m.invoke(target, arg);
    } catch (InvocationTargetException e) {
        throw new RuntimeException(e.getCause());     // unwrap!
    } catch (IllegalAccessException e) {
        throw new IllegalStateException(e);
    }
}

Two bugs, not one. The second is catch (Exception e) wrapping the InvocationTargetException — every real failure now presents as a stack trace inside Method.invoke.

Cache-key care: keying on the class name plus method is necessary because different target types must not share an entry. If methods are overloaded, the parameter types belong in the key too.

If this is genuinely hot, a MethodHandle held in a static final field is JIT-visible and can approach direct-call speed, which Method.invoke cannot. And the prior question is whether an interface would work — if the set of methods is known, reflection is buying nothing.

6 (hard): Design a minimal @Inject container. State what you would need to add for production, and what you would lose to a compile-time approach.
Solution 
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.FIELD, ElementType.CONSTRUCTOR})
public @interface Inject { }

public class Container {
    private final Map<Class<?>, Object> singletons = new ConcurrentHashMap<>();
    private final Set<Class<?>> inProgress =
            ConcurrentHashMap.newKeySet();

    @SuppressWarnings("unchecked")
    public <T> T get(Class<T> type) {
        Object existing = singletons.get(type);
        if (existing != null) return (T) existing;
        if (!inProgress.add(type))
            throw new IllegalStateException("Circular dependency: " + type);
        try {
            T instance = construct(type);
            injectFields(instance);
            singletons.put(type, instance);
            return instance;
        } finally {
            inProgress.remove(type);
        }
    }

    private <T> T construct(Class<T> type) throws Exception {
        Constructor<?> chosen = null;
        for (Constructor<?> c : type.getDeclaredConstructors())
            if (c.isAnnotationPresent(Inject.class)) chosen = c;
        if (chosen == null) chosen = type.getDeclaredConstructor();
        chosen.setAccessible(true);
        Object[] args = Arrays.stream(chosen.getParameterTypes())
                              .map(this::get)          // recursive
                              .toArray();
        return (T) chosen.newInstance(args);
    }

    private void injectFields(Object instance) throws Exception {
        for (Class<?> c = instance.getClass(); c != null && c != Object.class;
             c = c.getSuperclass()) {
            for (Field f : c.getDeclaredFields()) {
                if (!f.isAnnotationPresent(Inject.class)) continue;
                f.setAccessible(true);
                f.set(instance, get(f.getType()));
            }
        }
    }
}

Constructor injection is the better default, and this sketch shows why: with fields, the object exists in a half-built state between newInstance and injectFields, and a final field cannot be used at all. Constructor injection also makes the dependency visible to anyone reading the class.

Circular dependencies are detectable but not solvable for constructor injection — A needs a complete B which needs a complete A. Field injection can break the cycle only by handing out a partly built object, which is why Spring's cycle support is limited to setter and field injection.

What a compile-time container (Dagger, Micronaut) changes: the same graph is resolved by an annotation processor and emitted as plain Java. Missing bindings and cycles become compile errors, startup cost disappears, and native image works without configuration.

What you lose: runtime dynamism — no registering an implementation discovered from configuration, no classpath scanning for plugins, and generated code you have to read when the wiring is wrong. That is the whole reflection trade, in one component.

🎯 Key Takeaways

  • Annotations are inert metadata — always ask who reads them.
  • @Retention defaults to CLASS, so reflection silently sees nothing; write RUNTIME explicitly.
  • SOURCE is for processors, CLASS for bytecode tools, RUNTIME for reflection.
  • Annotation elements are limited to primitives, String, Class, enums, annotations and 1-D arrays — a Class element is the escape hatch frameworks use for behaviour.
  • @Inherited applies to class annotations only, not methods or interfaces.
  • getFields is public-plus-inherited; getDeclaredFields is all-modifiers but local — neither gives both, so walk the hierarchy.
  • Skip synthetic and static fields when reflecting over instance state.
  • Unwrap InvocationTargetException or your real exception is invisible.
  • The lookup, not the invoke, is the cost — getMethod searches and copies every call; cache it.
  • Reflection inflates to a generated accessor after ~15 calls, so short benchmarks report a number production never sees.
  • Erasure applies to instances, not declarations — getGenericType() recovers List<User> from a field.
  • The super type token (new TypeReference<…>() {}) supplies what erasure removed when there is no declaration.
  • setAccessible fails on JDK internals since 9, and errors since 17.
  • The real production costs are startup, lost inlining, lost compile-time checking, and native-image incompatibility — not the nanoseconds.
  • Annotation processors move the work to compile time, which is why Micronaut, Quarkus, Dagger and MapStruct exist — and why Spring 6 added AOT.
  • Reflection is not a security boundary; it defeats private by design.
