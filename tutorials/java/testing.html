Testing with JUnit & Mockito Professional Java

What you'll master: why JUnit 5 creates a new test instance per method and how that single decision prevents the most common source of flakiness; the assertion methods worth knowing and why assertThrows replaced an idiom that could pass without asserting anything; parameterised tests, and the point where six near-identical tests should become one; Mockito's actual vocabulary — mock, stub, spy and fake are four different things — the argument-matcher "all or none" rule, when doReturn is required rather than stylistic, and why UnnecessaryStubbingException is a feature; what not to mock, and why over-mocking produces tests that assert your implementation instead of your behaviour; and how to test time, randomness and concurrency without writing a test that lies. Prerequisites: Exceptions and SOLID.

Part 1 — JUnit 5's Architecture and Lifecycle

  JUNIT 5 IS THREE THINGS, NOT ONE. The split matters when a build
  breaks:

    PLATFORM   the engine API and launcher. Gradle, Maven and IDEs
               talk to this.
    JUPITER    the JUnit 5 programming model — @Test, assertions,
               extensions. What you write against.
    VINTAGE    an engine that runs JUnit 3 and 4 tests, so a
               migration can be incremental.

  So "JUnit 5 is on the classpath but no tests run" is almost always
  a missing engine, not a missing API: junit-jupiter-api compiles
  your tests, junit-jupiter-engine runs them.

  THE LIFECYCLE:

    @BeforeAll      once, before everything (must be static by
                    default — see below)
      @BeforeEach   before EACH test
        @Test       the test
      @AfterEach    after EACH test
    @AfterAll       once, at the end

  THE DECISION THAT PREVENTS MOST FLAKINESS:

    JUNIT CREATES A NEW INSTANCE OF THE TEST CLASS FOR EVERY TEST
    METHOD.

    class OrderTest {
        private List<Order> orders = new ArrayList<>();  // fresh
                                                          // every test
        @Test void a() { orders.add(o1); }   // sees []
        @Test void b() { orders.add(o2); }   // ALSO sees []
    }

  Fields cannot leak between tests, which is why @BeforeAll must be
  static — there is no single instance to hold it.

  @TestInstance(PER_CLASS) CHANGES THAT: one instance for the whole
  class, so @BeforeAll may be non-static and fields persist. It is
  convenient for an expensive shared fixture — and it reintroduces
  exactly the coupling the default prevents. Use it deliberately, and
  never for mutable state.

  ORDER IS DELIBERATELY UNSPECIFIED. JUnit runs methods in a stable
  but arbitrary order, precisely so you cannot depend on it. A test
  that only passes after another has run is a bug in the test, not a
  missing @Order.

  THE ANNOTATIONS THAT EARN THEIR PLACE:

    @DisplayName("rejects an order with no lines")
                        readable names in reports
    @Nested             group tests that share a context; inner
                        classes see the outer fixture
    @Tag("slow")        filter at run time: -Dgroups=fast
    @Disabled("...")    always with a reason
    @EnabledOnOs, @EnabledIfEnvironmentVariable
                        conditional execution instead of a commented
                        -out test

Part 2 — Assertions

  THE CORE SET:

    assertEquals(expected, actual)      // NOTE the argument order —
                                        // reversing it makes every
                                        // failure message backwards
    assertTrue / assertFalse
    assertNull / assertNotNull
    assertSame                          // identity, not equality
    assertArrayEquals
    assertIterableEquals

  ASSERTTHROWS REPLACED A GENUINELY BROKEN IDIOM. The JUnit 4 form:

    @Test(expected = IllegalArgumentException.class)
    public void rejectsNegative() {
        service.setup();          // if THIS throws it, the test
        service.withdraw(-1);     // passes for the wrong reason
    }

  The annotation cannot tell which line threw. assertThrows scopes it
  to the exact call and hands you the exception:

    var ex = assertThrows(IllegalArgumentException.class,
                          () -> service.withdraw(-1));
    assertEquals("amount must be positive", ex.getMessage());

  Asserting on the MESSAGE matters more than people think — otherwise
  a test for "rejects a negative amount" passes when the code throws
  for an unrelated reason.

  ASSERTALL REPORTS EVERY FAILURE, NOT THE FIRST:

    assertAll("user",
        () -> assertEquals("Ada", user.name()),
        () -> assertEquals(36, user.age()),
        () -> assertTrue(user.active()));

  Without it, a wrong name hides a wrong age and you fix one bug per
  test run.

  ASSERTTIMEOUT HAS TWO FORMS AND THEY DIFFER:

    assertTimeout(ofSeconds(1), task)          // runs to completion,
                                               // THEN fails if slow
    assertTimeoutPreemptively(ofSeconds(1), task)
                                               // aborts on another
                                               // thread

  The preemptive form can deadlock code using ThreadLocals or
  transactions, because the task runs on a different thread. Prefer
  the non-preemptive form unless the task can genuinely hang.

  ASSERTJ IS WORTH ADDING. Fluent assertions read as sentences and
  produce far better failure messages:

    assertThat(orders)
        .hasSize(3)
        .extracting(Order::status)
        .containsExactly(NEW, PAID, SHIPPED);

    assertThat(user.name()).isEqualTo("Ada");   // no argument-order
                                                // ambiguity

  On failure AssertJ prints the whole collection and the mismatch,
  where assertEquals prints two toString() blobs and leaves you to
  diff them.

Part 3 — Parameterised Tests

  SIX NEAR-IDENTICAL TESTS ARE ONE TEST WITH SIX INPUTS:

    @ParameterizedTest
    @ValueSource(strings = {"", " ", "\t", "\n"})
    void rejectsBlankNames(String name) {
        assertThrows(IllegalArgumentException.class,
                     () -> new User(name));
    }

  THE SOURCES, AND WHEN EACH FITS:

    @ValueSource       one primitive/String argument per case
    @CsvSource         several arguments, written inline
    @CsvFileSource     the same, from a resource file
    @MethodSource      arbitrary objects from a static method —
                       the general case
    @EnumSource        every enum constant, with include/exclude
    @NullAndEmptySource combine with @ValueSource for the classic
                       null/empty/blank trio

  CSVSOURCE FOR INPUT/EXPECTED PAIRS:

    @ParameterizedTest(name = "{0} + {1} = {2}")
    @CsvSource({ "1, 1, 2", "2, 3, 5", "-1, 1, 0" })
    void adds(int a, int b, int expected) {
        assertEquals(expected, calc.add(a, b));
    }

  The `name` attribute matters — without it the report says
  "adds(int, int, int)[2]" and you cannot tell which case failed.

  METHODSOURCE FOR REAL OBJECTS:

    static Stream<Arguments> orders() {
        return Stream.of(
            arguments(new Order(EMPTY),  false),
            arguments(new Order(PAID),   true));
    }

    @ParameterizedTest
    @MethodSource("orders")
    void shippable(Order o, boolean expected) { … }

  WHEN NOT TO PARAMETERISE: when the cases test DIFFERENT BEHAVIOURS
  rather than the same behaviour with different data. If the body
  needs an if-statement per case, you have merged two tests and made
  both harder to read. Parameterise data, never logic.

Part 4 — What a Mock Actually Is

  FOUR WORDS PEOPLE USE INTERCHANGEABLY AND SHOULD NOT:

    DUMMY   passed to satisfy a signature, never used.
    STUB    returns canned answers. No assertions about it.
    MOCK    a stub that ALSO records calls so you can VERIFY them.
            The distinguishing feature is verification.
    SPY     wraps a REAL object; calls pass through unless stubbed.
    FAKE    a working lightweight implementation — an in-memory
            repository, an H2 database. Real behaviour, not canned.

  The important line is between STUB and MOCK: a stub supports the
  test, a mock IS the assertion. Verifying calls asserts on HOW your
  code works; asserting on return values asserts on WHAT it does.
  Prefer the latter.

  BASIC MOCKITO:

    @ExtendWith(MockitoExtension.class)
    class OrderServiceTest {
        @Mock  PaymentGateway gateway;
        @Mock  OrderRepository repo;
        OrderService service;

        @BeforeEach void setUp() {
            service = new OrderService(gateway, repo);  // ← plain
        }                                               //   ctor
    }

  NOTE THE ABSENCE OF @InjectMocks. With constructor injection you
  simply call the constructor: it is explicit, refactor-safe, and
  fails to COMPILE when a dependency is added. @InjectMocks matches
  by type and name via reflection and silently leaves a field null
  when it cannot — producing a NullPointerException instead of a
  clear error. Constructor injection makes it unnecessary.

  STUBBING:

    when(repo.findById(1L)).thenReturn(Optional.of(order));
    when(gateway.charge(any())).thenThrow(new GatewayException());
    when(clock.instant()).thenReturn(FIXED, LATER);   // consecutive

  doReturn IS SOMETIMES REQUIRED, NOT A STYLE CHOICE:

    when(spy.method()).thenReturn(x);   // CALLS THE REAL METHOD
                                        // while setting up!
    doReturn(x).when(spy).method();     // does not

  Use the do* form for: spies, void methods (doThrow, doNothing,
  doAnswer), and any real method with side effects.

  ARGUMENT MATCHERS — THE ALL-OR-NONE RULE:

    when(repo.find(anyLong(), "ACTIVE"))   // ❌ InvalidUseOfMatchers
    when(repo.find(anyLong(), eq("ACTIVE"))) // ✓

  Matchers work by pushing onto a stack, not by inspecting values, so
  mixing raw values with matchers corrupts the positions. If ONE
  argument uses a matcher, ALL must.

  VERIFICATION, AND ARGUMENTCAPTOR:

    verify(gateway).charge(order);
    verify(gateway, times(2)).charge(any());
    verify(gateway, never()).refund(any());
    verifyNoMoreInteractions(gateway);      // brittle — use sparingly

    var captor = ArgumentCaptor.forClass(Email.class);
    verify(mailer).send(captor.capture());
    assertThat(captor.getValue().subject()).isEqualTo("Receipt");

  ArgumentCaptor is for asserting on an object your code CONSTRUCTED
  and handed to a collaborator — the one case where you cannot check
  it through a return value.

  STRICT STUBS ARE ON BY DEFAULT IN JUNIT 5, and
  UnnecessaryStubbingException is a FEATURE. An unused stub means
  either the test does not exercise the path you thought, or the
  production code changed and the test still passes for the wrong
  reason. Do not switch to lenient() to silence it; delete the
  stub.

MockCanned returns + verificationAsserting an interaction happenedCouples the test to implementation

Part 5 — What Not to Mock

  MOCKING IS A COST, NOT A DEFAULT. Every mock is an assertion that
  the real collaborator behaves the way you have described — and that
  assertion is never checked.

  DO NOT MOCK VALUE OBJECTS:

    Order order = mock(Order.class);
    when(order.total()).thenReturn(BigDecimal.TEN);   // ❌

    Order order = new Order(List.of(new Line(TEN)));  // ✓

  You have replaced arithmetic with a constant, so the test no longer
  covers the total calculation and will keep passing when it breaks.
  Constructing the real object is usually shorter anyway.

  DO NOT MOCK TYPES YOU DO NOT OWN. Mocking a third-party client
  encodes YOUR BELIEF about its API into the test. When the library
  changes its behaviour — not its signature — the mock keeps agreeing
  with the old behaviour and the test stays green while production
  breaks. Wrap it in your own interface and mock that; the wrapper
  gets an integration test.

  DO NOT MOCK THE CLASS UNDER TEST. A partial mock of the thing you
  are testing means you are testing the parts you did not replace.
  If you feel the need, the class is doing too much — extract the
  part you wanted to stub.

  DO NOT MOCK WHAT IS CHEAP AND REAL. A List, a Map, a String, a
  java.time value. Real ones are faster to write and always correct.

  THE OVER-MOCKING FAILURE, CONCRETELY:

    @Test void createsOrder() {
        when(validator.validate(any())).thenReturn(true);
        when(repo.save(any())).thenReturn(saved);
        when(mapper.toDto(any())).thenReturn(dto);

        service.create(request);

        verify(validator).validate(any());
        verify(repo).save(any());
        verify(mapper).toDto(any());
    }

  This test asserts that the method calls three collaborators in
  order. It would pass if every one of them returned nonsense, and it
  fails whenever you refactor the internals without changing the
  behaviour. It is a change detector, not a test.

  WHAT TO ASSERT INSTEAD: the observable outcome. Given this request,
  the returned DTO has this id and status, and the repository now
  contains an order with these lines. Use a FAKE in-memory repository
  and you can assert real state.

  THE HEURISTIC: MOCK AT ARCHITECTURAL BOUNDARIES — the network, the
  clock, the filesystem, a payment gateway, a message broker.
  Everything inside the boundary should be real.

  THE PYRAMID, WITH THE HONEST VERSION:

    many   unit tests        milliseconds, no I/O
    some   integration       Testcontainers: a REAL Postgres, Kafka,
                             Redis in Docker
    few    end-to-end        slow, flaky, but they test the wiring

  Testcontainers changed this trade-off. A test against a real
  Postgres catches what a mocked repository never will — constraint
  violations, transaction semantics, actual SQL — for a few seconds
  of startup. Many teams now write fewer mocked "integration" tests
  and more real ones.

Part 6 — Time, Randomness and Concurrency

  THE THREE THINGS THAT MAKE TESTS FLAKY ARE ALL THE SAME PROBLEM:
  HIDDEN NON-DETERMINISTIC INPUT. Make it an explicit dependency.

  TIME — INJECT A CLOCK:

    // ❌ untestable
    if (LocalDateTime.now().isAfter(order.expiry())) { … }

    // ✓ Clock is a dependency
    class ExpiryService {
        private final Clock clock;
        boolean expired(Order o) {
            return Instant.now(clock).isAfter(o.expiry());
        }
    }

    var clock = Clock.fixed(Instant.parse("2024-01-15T10:00:00Z"),
                            ZoneOffset.UTC);

  This also removes an entire class of production bug: code that
  calls now() several times in one operation and gets different
  answers, and code that behaves differently across midnight or a DST
  boundary. Test those explicitly with Clock.offset.

  RANDOMNESS — INJECT THE SOURCE OR THE SEED:

    new Random(42)        // reproducible in a test
    Random injected via the constructor

  A failing test with a random input you cannot reproduce is worse
  than no test.

  CONCURRENCY — A SLEEP-BASED TEST IS A LIE:

    // ❌ slow AND flaky: too short on a loaded CI machine,
    //    wasted time when it passes
    service.processAsync();
    Thread.sleep(1000);
    assertTrue(service.isDone());

    // ✓ wait for the CONDITION, with a generous ceiling
    assertTrue(latch.await(5, TimeUnit.SECONDS));

    // ✓ or Awaitility
    await().atMost(5, SECONDS).until(service::isDone);

  AND UNDERSTAND WHAT SUCH A TEST PROVES: almost nothing about
  correctness. Running two threads a thousand times does not explore
  the interleavings that matter, and a race that needs a specific JIT
  compilation state will not appear at all. For real memory-model
  claims the tool is jcstress; for everything else, DESIGN the
  concurrency out — confinement, immutability, a proven concurrent
  collection — and unit-test the sequential logic.

  DETERMINISTIC SEAMS BEAT TIMING. Testing a task submitted to an
  executor is far easier if the executor is injected:

    new OrderService(Runnable::run)   // synchronous in tests

  COVERAGE IS A DIAGNOSTIC, NOT A TARGET. It tells you what was
  EXECUTED, never what was VERIFIED — a test with no assertions gives
  full coverage. Low coverage on a critical path is a genuine signal;
  a mandated 80% produces assertion-free tests written to hit the
  number.

  WHAT MAKES A TEST WORTH KEEPING:

    ONE REASON TO FAIL     when it goes red you know what broke
    INDEPENDENT            passes alone and in any order
    FAST                   a slow suite stops being run
    NAMED FOR BEHAVIOUR    "rejectsOrderWithNoLines", not "test3"
    ASSERTS THE OUTCOME    not the sequence of internal calls

Interview Questions

Beginner: Why does JUnit create a new test instance for each method?

To make tests independent by construction. Fields are re-initialised for every test method, so nothing one test does can leak into another.

That single decision removes the most common source of flakiness — a test that passes alone and fails in the suite, or passes in one order and fails in another. And because JUnit deliberately leaves execution order unspecified, any accidental dependency surfaces quickly rather than lying dormant.

It also explains a rule that otherwise looks arbitrary: @BeforeAll must be static, because there is no single instance to hold it.

@TestInstance(PER_CLASS) switches to one instance per class, which allows a non-static @BeforeAll and persistent fields. It is reasonable for an expensive immutable fixture and a bad idea for mutable state, because it restores exactly the coupling the default prevents.

Beginner: What is the difference between a mock, a stub and a fake?
DoubleProvidesPurpose
StubCanned return valuesSteer the code down a path
MockCanned returns plus recorded callsAssert an interaction happened
FakeA real, lightweight implementationBehave like the real thing, cheaply
SpyA real object, selectively overriddenLegacy code you cannot restructure

The line that matters is between stub and mock. A stub supports the test; a mock is the assertion. Verifying that a collaborator was called asserts on how your code works; asserting on a returned value or resulting state asserts on what it does. The second survives refactoring, the first does not.

A fake — an in-memory repository, an embedded queue — is often the best of the three, because you can assert on real resulting state instead of on a call sequence.

Mid: Why must you not mix argument matchers with raw values?

Because matchers do not inspect values — they push onto a stack. When Mockito sees anyLong() it records a matcher and returns a dummy value; at the end of the stubbing call it pops one matcher per argument.

when(repo.find(anyLong(), "ACTIVE"))     // ❌ 1 matcher, 2 args
when(repo.find(anyLong(), eq("ACTIVE")))  // ✓ 2 matchers

With a raw value in one position, the count no longer matches the arity and Mockito cannot tell which argument the matcher belonged to. It throws InvalidUseOfMatchersException — and often on the next unrelated stubbing, since the stale matcher is still on the stack, which is why the error frequently points at the wrong line.

The rule is therefore all or none: wrap literals in eq() when any other argument uses a matcher.

The related trap is stubbing a spy with when(). Since a spy wraps a real object, when(spy.charge(order)) calls the real charge while setting up the stub. doReturn(x).when(spy).charge(order) avoids the invocation — and the same do* form is required for void methods.

Mid: What should you not mock, and why?

Every mock is an unverified assertion that the real collaborator behaves as you described. Four cases are reliably wrong.

Value objects. when(order.total()).thenReturn(TEN) replaces the total calculation with a constant, so the test no longer covers it and keeps passing when it breaks. Constructing the real object is usually shorter.

Types you do not own. Mocking a third-party client encodes your belief about its API. When the library changes its behaviour rather than its signature, the mock agrees with the old behaviour, the test stays green, and production breaks. Wrap it in your own interface, mock that, and integration-test the wrapper.

The class under test. A partial mock means you are testing only the parts you did not replace. Wanting to do it is a signal the class does too much.

Cheap real things — collections, strings, java.time values. Real ones are faster to write and always correct.

The heuristic: mock at architectural boundaries — network, clock, filesystem, payment gateway, broker. Inside the boundary, use real objects and fakes.

Senior: This test passes. What is wrong with it? 
@Test void createsOrder() {
    when(validator.validate(any())).thenReturn(true);
    when(repo.save(any())).thenReturn(saved);
    when(mapper.toDto(any())).thenReturn(dto);

    service.create(request);

    verify(validator).validate(any());
    verify(repo).save(any());
    verify(mapper).toDto(any());
}

It asserts that three methods were called, and nothing else. It is a change detector, not a test.

It would pass if the code were wrong. Every collaborator is stubbed with any(), so the order could be built from the wrong fields, the wrong amount could be saved, and the DTO could be mapped from a different entity — the test never looks at a value. It also never checks the return value of create at all.

It fails when the code is right. Split save into two calls, introduce a cache, or reorder the internals without changing behaviour, and it goes red. The test is coupled to the implementation, so refactoring costs test edits — which is exactly the tax that makes teams stop refactoring.

What to write instead: use a fake in-memory repository, pass a real request, and assert on the outcome — the returned DTO's fields, and the order now in the repository with the expected lines and status. If you must assert that the gateway was charged, use an ArgumentCaptor and check the amount, not merely that the call happened.

The general principle: assert on observable behaviour — return values and resulting state. Verification is for interactions with no other observable effect, such as sending an email or publishing an event, and even then assert on what was sent.

Senior: How do you make tests reliable around time, randomness and concurrency?

All three are the same problem — hidden non-deterministic input — and the same fix: make it an explicit dependency.

Time: inject a Clock. LocalDateTime.now() buried in business logic is untestable, and it hides a real bug too: code calling now() several times in one operation gets different answers. With Clock.fixed(...) you test the expiry boundary exactly, and with Clock.offset you test midnight and DST transitions on purpose rather than discovering them in October.

Randomness: inject the source or the seed. A failure you cannot reproduce is worth less than no test.

Concurrency: never sleep. A Thread.sleep(1000) is slow when it passes and flaky on a loaded CI machine. Wait for the condition — a CountDownLatch with a generous ceiling, or Awaitility.

But be honest about what a concurrent test proves: very little. Running two threads a thousand times does not explore the interleavings that matter, and a race that depends on a particular JIT state will not appear at all. For memory-model claims the tool is jcstress. For everything else, design the concurrency out — confinement, immutability, a proven concurrent collection — and unit-test the sequential logic.

The general move is a deterministic seam. Injecting the executor lets a test pass Runnable::run and make the whole thing synchronous, which converts an untestable asynchronous flow into an ordinary one.

🏋️ Graded Exercises

1 (easy): Why does this pass alone and fail in the suite? 
class CartTest {
    static List<Item> items = new ArrayList<>();

    @Test void addsItem()      { items.add(new Item("a"));
                                 assertEquals(1, items.size()); }
    @Test void addsTwoItems()  { items.add(new Item("b"));
                                 items.add(new Item("c"));
                                 assertEquals(2, items.size()); }
}
Solution

The field is static, so it survives between tests. JUnit's per-method instance protects instance fields; a static field is shared by every test in the JVM.

Whichever test runs second sees the other's items, and since execution order is unspecified, which one fails can change between machines.

class CartTest {
    private List<Item> items;              // instance field

    @BeforeEach void setUp() {
        items = new ArrayList<>();          // explicit and obvious
    }
    …
}
Field kindLifetime

Instance (default)One test method
Instance with PER_CLASSThe whole class

The wrong fix is @TestMethodOrder to force a passing sequence. That freezes the coupling in place, and the next test added breaks it again.

2 (easy): Rewrite these six tests as one. 
@Test void rejectsEmpty()      { assertThrows(IAE.class, () -> new User("")); }
@Test void rejectsSpace()      { assertThrows(IAE.class, () -> new User(" ")); }
@Test void rejectsTab()        { assertThrows(IAE.class, () -> new User("\t")); }
@Test void rejectsNewline()    { assertThrows(IAE.class, () -> new User("\n")); }
@Test void rejectsNull()       { assertThrows(IAE.class, () -> new User(null)); }
@Test void rejectsSpaces()     { assertThrows(IAE.class, () -> new User("   ")); }
Solution 
@ParameterizedTest(name = "rejects [{0}]")
@NullSource
@ValueSource(strings = {"", " ", "\t", "\n", "   "})
void rejectsBlankNames(String name) {
    assertThrows(IllegalArgumentException.class, () -> new User(name));
}

Same behaviour, different data — the exact case parameterisation is for. Adding a seventh input is one string rather than a new method, and the six copies cannot drift apart.

SourceFor
@ValueSourceOne primitive or String per case
@NullSource / @EmptySourceAdding null and empty to the set
@CsvSourceInput/expected pairs
@MethodSourceReal objects

The name attribute is not decoration. Without it the report reads rejectsBlankNames(String)[3] and you cannot tell which input failed — which is the main objection people raise to parameterised tests, and it is solved in one attribute.

When not to do this: if the cases test different behaviours and the body needs an if per case, you have merged two tests. Parameterise data, never logic.

3 (medium): Two Mockito bugs here. Find both. 
@Test void appliesDiscount() {
    OrderService spy = spy(new OrderService(repo));
    when(spy.lookupRate("GOLD")).thenReturn(0.1);
    when(repo.find(anyLong(), "GOLD")).thenReturn(order);

    assertEquals(90, spy.total(1L, "GOLD"));
}
Solution

Bug 1 — when() on a spy calls the real method. A spy wraps a real object, so when(spy.lookupRate("GOLD")) actually invokes lookupRate during setup. If it hits the database, throws, or has a side effect, the test fails before it starts.

Bug 2 — mixed matchers. anyLong() with the raw "GOLD" gives one matcher for two arguments, so Mockito throws InvalidUseOfMatchersException — often reported at a later, unrelated line, because the stale matcher stays on the stack.

OrderService spy = spy(new OrderService(repo));
doReturn(0.1).when(spy).lookupRate("GOLD");        // no real call
when(repo.find(anyLong(), eq("GOLD"))).thenReturn(order);  // all matchers
SituationRequired form
Stubbing a spydoReturn(...).when(spy).m()
Void methoddoNothing() / doThrow()
Any argument uses a matcherAll arguments must — wrap literals in eq()

The deeper problem is the spy itself. Stubbing a method on the class under test means part of the thing you are testing is fake. That lookupRate wants to be a separate collaborator you can substitute honestly.

4 (medium): Make this testable, and say what bug the fix also prevents. 
public class SubscriptionService {
    public boolean isExpired(Subscription s) {
        return LocalDateTime.now().isAfter(s.getExpiryDate());
    }
}
Solution 
public class SubscriptionService {
    private final Clock clock;

    public SubscriptionService(Clock clock) { this.clock = clock; }

    public boolean isExpired(Subscription s) {
        return LocalDateTime.now(clock).isAfter(s.getExpiryDate());
    }
}

// test
var clock = Clock.fixed(Instant.parse("2024-06-15T12:00:00Z"),
                        ZoneOffset.UTC);
var service = new SubscriptionService(clock);

// production
new SubscriptionService(Clock.systemUTC());

The original can only be tested by constructing a subscription relative to the real now — which cannot test the boundary precisely, and produces a test whose meaning changes as time passes.

The bug it also prevents is inconsistent time within one operation. Business logic that calls now() in several places gets different answers, so an operation can be evaluated as both expired and not expired — a real class of bug that appears under load, when the calls straddle a boundary.

Now testableHow
Exactly at expiryClock.fixed at the boundary instant
One second either sideClock.offset(clock, ofSeconds(±1))
Across midnightA fixed clock at 23:59:59
Across a DST changeA fixed clock plus a real ZoneId

Inject Clock, not a boolean or a timestamp. It is the JDK's designed seam, it works with every java.time type, and it keeps the production wiring a single Clock.systemUTC().

5 (hard): Rewrite this test so it survives refactoring. 
@Test void registersUser() {
    when(repo.existsByEmail("a@b.com")).thenReturn(false);
    when(hasher.hash("pw")).thenReturn("hashed");
    when(repo.save(any())).thenReturn(new User(1L, "a@b.com"));

    service.register("a@b.com", "pw");

    verify(repo).existsByEmail("a@b.com");
    verify(hasher).hash("pw");
    verify(repo).save(any());
    verify(mailer).sendWelcome(any());
}
Solution

It asserts a call sequence, so it fails on refactoring and passes on wrong values. Nothing checks the returned user, and save(any()) would accept a user with the wrong email or an unhashed password.

@Test void registersUserWithHashedPassword() {
    var repo   = new InMemoryUserRepository();          // fake
    var mailer = new RecordingMailer();                 // fake
    var service = new RegistrationService(repo, new Sha256Hasher(), mailer);

    User created = service.register("a@b.com", "pw");

    assertThat(created.email()).isEqualTo("a@b.com");
    assertThat(repo.findByEmail("a@b.com")).isPresent();
    assertThat(repo.findByEmail("a@b.com").get().passwordHash())
        .isNotEqualTo("pw");                            // actually hashed
    assertThat(mailer.sent()).extracting(Email::to)
        .containsExactly("a@b.com");
}

@Test void rejectsDuplicateEmail() {
    repo.save(new User("a@b.com"));
    assertThrows(DuplicateEmailException.class,
                 () -> service.register("a@b.com", "pw"));
}
ChangeWhy
Fake repository, not a mockLets you assert on real resulting state
Real hasherThe test now proves the password is not stored in plain text
Recording fake mailerAsserts what was sent, not that a method ran
Assert the return valueThe original ignored it entirely
A separate duplicate testOne reason to fail per test

Now internal refactoring is free. Reorder the calls, add a cache, split save — the tests stay green because they assert outcomes. And if the hashing is accidentally removed, they go red, which the original would not.

An ArgumentCaptor would be the middle ground if a real mailer is not practical: capture the email and assert its recipient and subject. Verifying that sendWelcome was called tells you nothing about what the user received.

6 (hard): Design the test strategy for an order service that validates, charges a payment gateway, persists, and publishes an event. Say what is mocked and what is real at each level.
Solution
LevelRealSubstitutedProves
Unit (many, ms)Domain objects, validation, pricingNothing — pure logicBusiness rules and edge cases

The gateway is the one thing mocked at every level, because it is a true architectural boundary — network, money, and not yours. Everything inside the boundary is real or a fake.

Fakes, not mocks, for the repository and publisher. An in-memory repository lets you assert that the order was persisted with the right lines and status; a recording publisher lets you assert the event's contents. Both survive refactoring, which verification does not.

The cases worth writing at the service level are the failure paths, which is where orchestration bugs live: the gateway times out after charging (do you retry? is the charge idempotent?), persistence fails after a successful charge (is there compensation?), and event publishing fails after commit (is it an outbox, or is the event lost?). These are the questions mocked happy-path tests never ask.

Testcontainers earns its seconds. A real Postgres catches unique-constraint violations, transaction-boundary mistakes and SQL that a mocked repository would happily accept — the failures that otherwise reach production.

The distribution follows from cost and confidence: hundreds of unit and service tests run in seconds on every commit; a dozen integration tests run per push; a handful of end-to-end tests run before deploy. Inverting that gives a slow, flaky suite people stop trusting.

🎯 Key Takeaways

  • JUnit creates a new instance per test method, which makes tests independent by construction — and is why @BeforeAll is static.
  • Execution order is deliberately unspecified; a test that needs an order is a broken test.
  • static fields defeat the per-method instance — the classic passes-alone-fails-in-suite bug.
  • assertThrows scopes the expectation to one call and gives you the exception — assert on its message.
  • assertAll reports every failure, not just the first.
  • assertTimeoutPreemptively runs on another thread and breaks ThreadLocals and transactions.
  • Parameterise data, never logic — and always set the name attribute.
  • Mock, stub, spy and fake are four different things; a stub supports the test, a mock is the assertion.
  • Matchers are all-or-none — mixing raw values corrupts the matcher stack.
  • when() on a spy calls the real method; use doReturn, and for void methods it is mandatory.
  • UnnecessaryStubbingException is a feature — delete the stub rather than silencing it.
  • Do not mock value objects, types you do not own, or the class under test.
  • Mock at architectural boundaries; use fakes and real objects inside them.
  • Verifying call sequences produces change detectors — assert on outcomes and state.
  • Inject a Clock; it makes time testable and prevents inconsistent now() within one operation.
  • Never Thread.sleep in a test — and remember a concurrent test proves very little.
  • Coverage measures execution, not verification — a diagnostic, never a target.
