Interfaces & Abstract Classes OOP

What you'll master: the interface as a contract that decouples callers from implementations, and the decision that actually separates it from an abstract class — since default methods arrived, "can it have a body?" is no longer the question; state is; why default methods were added to the language at all, which is the only reason List could gain stream() without breaking every implementation ever written; the diamond rules, where inheriting the same default from two interfaces is a compile error you must resolve explicitly with Interface.super.method(); functional interfaces and why a lambda is not an object of an anonymous class; and the habit that makes code testable — declare the parameter as the interface, not the implementation, so a List parameter accepts anything and an ArrayList parameter accepts one thing. Prerequisites: Inheritance.

Part 1 — An Interface Is a Contract

interface Payment {
    Receipt charge(Money amount);      // implicitly public abstract
    void refund(String receiptId);
}

class StripePayment implements Payment { … }
class PayPalPayment implements Payment { … }

  A class may implement MANY interfaces but extend ONE class, which is
  why capabilities that cut across a hierarchy belong in interfaces.

  WHAT AN INTERFACE MAY CONTAIN:

    abstract methods       the contract itself
    default methods        a body subclasses inherit       (Java 8+)
    static methods         utilities namespaced to the type (Java 8+)
    private methods        shared helpers for the defaults (Java 9+)
    constants              implicitly public static final

  WHAT IT MAY NOT CONTAIN:

    instance fields        no per-object state
    constructors           nothing to construct

  That single restriction — NO INSTANCE STATE — is the whole
  difference from an abstract class, and it is what makes multiple
  inheritance of interfaces safe: there is no state to inherit twice.

Part 2 — default and static Methods

interface Collection<E> {
    boolean add(E e);

    default boolean addAll(Collection<? extends E> c) {   // has a body
        boolean changed = false;
        for (E e : c) changed |= add(e);
        return changed;
    }

    static <E> Collection<E> empty() { … }     // not inherited
}
  WHY default EXISTS — INTERFACE EVOLUTION

  Before Java 8, adding a method to an interface broke EVERY
  implementation, everywhere, including ones in code you have never
  seen. That made published interfaces effectively frozen.

  Java 8 needed to add stream(), forEach() and removeIf() to
  Collection. Without default methods, every List implementation in
  every codebase on earth would have failed to compile.

  So default methods exist to let an interface GROW without breaking
  implementors. That is their purpose, and it is worth knowing because
  it explains their limitation:

    A DEFAULT METHOD CANNOT ACCESS STATE. It has no fields to read —
    only other interface methods. So it can define behaviour purely in
    terms of the contract, and nothing else.

  THE DESIGN CAUTION: a default method is inherited by implementors
  who never asked for it. If the default is wrong for one of them and
  they do not notice, it is silently wrong — which is why a default
  should be either obviously correct for every implementor, or absent.

Part 3 — Interface or Abstract Class?

ConstructorsNoYes

Non-public membersOnly private helpersAny access level
Adding a method laterSafe if you give it a defaultSafe if concrete
Reach for it whenExpressing a capability — and by default, for any type callers depend onImplementations share state and partial behaviour
🔑 The modern default is: declare the type as an interface, and add an abstract base class only if implementations genuinely share state. That keeps callers depending on the contract while still permitting reuse — and crucially, an implementor can choose to implement the interface directly rather than being forced into your hierarchy. It is exactly what the JDK does with List and AbstractList, and it means the single-inheritance slot stays free for whoever needs it.

Part 4 — Functional Interfaces and Lambdas

@FunctionalInterface                    // optional, and worth adding
interface Validator<T> {
    boolean test(T value);              // EXACTLY ONE abstract method
    default Validator<T> and(Validator<T> other) {   // defaults are fine
        return v -> this.test(v) && other.test(v);
    }
}

Validator<String> notBlank = s -> !s.isBlank();     // a lambda IS one

  A functional interface has exactly one abstract method, which is
  what lets a lambda stand in for it. Default and static methods do
  not count — only abstract ones.

  @FunctionalInterface is not required, but it makes the compiler
  enforce the single-abstract-method rule, so adding a second abstract
  method becomes a build error rather than silently breaking every
  lambda that implemented it.

  THE ONES YOU WILL ACTUALLY USE — java.util.function

    Function<T,R>     T -> R        map, transform
    Predicate<T>      T -> boolean  filter, test
    Consumer<T>       T -> void     forEach, side effects
    Supplier<T>       () -> T       lazy creation, defaults
    UnaryOperator<T>  T -> T        replaceAll
    BiFunction<T,U,R> (T,U) -> R    merge, combine

  Prefer these to inventing your own — every developer already knows
  them, and they compose with andThen, compose and negate.
  A LAMBDA IS NOT AN ANONYMOUS CLASS

    Runnable anon = new Runnable() {      // a real class file:
        public void run() { … }           // Outer$1.class
    };
    Runnable lambda = () -> { … };        // NO extra class file

  Lambdas compile to an invokedynamic instruction that the JVM links
  to a generated implementation at first execution. Practical
  differences:

    `this`        anonymous class -> the anonymous instance
                  lambda          -> the ENCLOSING instance
    class files   one per anonymous class; none per lambda
    capture       both capture effectively-final locals only

  The `this` difference is the one that bites: inside an anonymous
  Runnable, this.foo() calls the Runnable's method; inside a lambda it
  calls the enclosing class's. That also means a lambda holds a
  reference to its enclosing instance when it captures anything from
  it — which matters for the leak in Enums & Nested Classes.

Part 5 — The Diamond and Default Conflicts

interface A { default String hello() { return "A"; } }
interface B { default String hello() { return "B"; } }

class C implements A, B { }        // ❌ COMPILE ERROR
  // "class C inherits unrelated defaults for hello() from types A and B"

// You MUST resolve it explicitly:
class C implements A, B {
    @Override public String hello() {
        return A.super.hello();          // pick one, or combine
    }
}

  JAVA REFUSES TO GUESS. C++'s multiple inheritance of state produced
  the classic diamond problem — which copy of the shared field does an
  object have? Java avoids that entirely by forbidding instance state
  in interfaces, so only BEHAVIOUR can be inherited twice, and the
  compiler makes you choose.

  THE RESOLUTION RULES, in order:

  1. A CLASS WINS. A concrete method from a superclass beats any
     interface default. ("Class wins over interface.")
  2. THE MOST SPECIFIC INTERFACE WINS. If B extends A and both define
     hello(), B's is used — no ambiguity.
  3. OTHERWISE IT IS AN ERROR, and you override explicitly.

  Rule 1 has a sharp edge worth knowing: adding a default method to an
  interface can be SILENTLY SHADOWED by an inherited superclass method
  of the same signature, so implementors get the superclass behaviour
  rather than your new default.

Part 6 — Program to an Interface

  void process(ArrayList<Order> orders)   // ❌ accepts ONE type
  void process(List<Order> orders)        // ✓ accepts any List
  void process(Collection<Order> orders)  // ✓ if order does not matter
  void process(Iterable<Order> orders)    // ✓ if you only iterate

  DECLARE THE WEAKEST TYPE THAT DOES THE JOB. Each step widens what
  callers may pass and narrows what you may rely on — which is the
  right direction for both.

  THE SAME RULE ON THE INSIDE, AND ON RETURNS:

    private final List<Order> orders = new ArrayList<>();
    //            ^^^^ field type is the interface
    //                                  ^^^^^^^^^ implementation is a
    //                                  private decision you can change

    public List<Order> orders()      // ✓ callers see the contract
    public ArrayList<Order> orders() // ❌ now you can never switch

  WHY IT MATTERS BEYOND STYLE — TESTING.

    class OrderService {
        private final PaymentGateway gateway;      // an INTERFACE
        OrderService(PaymentGateway gateway) { … } // injected
    }

  A test passes a stub implementation. With a concrete StripeGateway
  as the field type, the test needs Stripe — a network call, an API
  key, and a failure mode you cannot trigger on demand.

  The interface is what makes the dependency substitutable, which is
  what makes the class testable. That is the practical payoff, and it
  is why "program to an interface" survived as advice.
⚠️ The counter-caution: do not create an interface with exactly one implementation that you invented at the same time. UserServiceImpl implements UserService, with no second implementation and no test double that could not be a mock of the class, is ceremony — two files, an extra indirection in every stack trace, and "go to implementation" landing on a declaration. Interfaces earn their place when there are genuinely multiple implementations, when the boundary is published to other modules, or when the seam is needed for testing. Creating one reflexively for every class is a pattern applied without its reason.

Interview Questions

Beginner: What is an interface, and how does it differ from a class?

An interface declares a contract — a set of methods a type promises to provide — without saying how they work. A class implementing it commits to supplying those behaviours.

The structural differences are that a class can implement many interfaces but extend only one class, and that an interface cannot hold instance state or constructors. Its members are implicitly public, and any fields are implicitly public static final constants.

Since Java 8 an interface can have method bodies — default and static methods — so "no implementation" is no longer the distinction. The remaining one is state: an interface has none.

The practical value is decoupling. A method taking a Payment works with Stripe, PayPal, or a test stub, without knowing or caring which — which is what makes the code both extensible and testable.

Beginner: What is a functional interface?

An interface with exactly one abstract method, which is what allows a lambda to be used wherever that interface is expected. Runnable, Comparator, Predicate and Function are all functional interfaces.

Default and static methods do not count towards the limit — only abstract ones — which is why Comparator can carry a dozen helper methods and still accept a lambda.

@FunctionalInterface is optional but worth adding: it makes the compiler enforce the single-abstract-method rule, so someone adding a second abstract method gets a build error at the interface rather than breaking every lambda that implemented it, possibly in other modules.

In practice I would reach for the standard interfaces in java.util.function before defining my own, because they are universally recognised and they compose — andThen, compose, negate — which a bespoke interface does not.

Mid: Why were default methods added, and what do they cost?

To allow interface evolution. Before Java 8, adding a method to an interface broke every implementing class everywhere, including implementations in code the interface's author had never seen. Published interfaces were effectively frozen.

Java 8 needed to add stream(), forEach() and removeIf() to Collection. Without defaults, every List implementation in the world would have failed to compile on upgrade. Default methods made that addition source-compatible.

The cost is that they are inherited by implementors who never asked for them. If a default is wrong for one implementation and the author does not notice, it is silently wrong — the class compiles and behaves incorrectly. So a default should be either obviously correct for every implementor, or not provided at all.

They also introduce the diamond case: implementing two interfaces that both define the same default is a compile error, and you must resolve it with A.super.method().

And there is a subtle one worth knowing — class wins over interface. If an implementing class inherits a method with the same signature from a superclass, that beats your new default silently, so implementors get the superclass behaviour rather than the one you added.

Mid: How does Java handle the diamond problem?

It avoids the hard version of it by forbidding instance state in interfaces. C++'s diamond problem is fundamentally about state — if two parents share a base with a field, does the object get one copy or two? Since a Java interface has no instance fields, only behaviour can be inherited more than once.

For behaviour, Java refuses to guess. Implementing two interfaces that define the same default method is a compile error, and you must override it and choose explicitly with A.super.hello() — or combine both.

There are two rules that resolve conflicts before it becomes an error. Class wins over interface: a concrete method inherited from a superclass beats any interface default. And the most specific interface wins: if B extends A and both define the method, B's is used, because it is more specific.

The reason this design is good is that it makes the ambiguity visible at compile time rather than resolving it by an ordering rule the reader has to know. The one sharp edge is the class-wins rule acting silently — that one you have to check for.

Senior: What does "program to an interface" mean, and when does it not apply?

It means depending on the weakest type that does the job — declaring parameters, fields and return types as the contract rather than the concrete class.

A method taking List rather than ArrayList accepts anything a caller has, including List.of(...) and Arrays.asList(...). A field typed as List lets you switch to LinkedList or an immutable list without touching callers. Returning List rather than ArrayList keeps the implementation from becoming part of your published API.

The payoff that matters most is testability. If a service holds a PaymentGateway interface, a test passes a stub. If it holds a concrete StripeGateway, the test needs a network call, an API key, and no way to trigger a decline on demand. The interface is the seam that makes the dependency substitutable.

Where it does not apply is the reflexive interface-per-class habit. UserServiceImpl implements UserService, with exactly one implementation invented at the same time and no second one in prospect, is ceremony: two files, an extra hop in every stack trace, and "go to implementation" landing on a declaration. Modern mocking libraries can stub concrete classes, so even the testing argument is weaker than it used to be.

My rule is that an interface earns its place when there are genuinely multiple implementations, when the boundary is published across a module, or when a real test seam is needed. Otherwise extract it when the second implementation appears — which is a mechanical refactor, and by then you know what the abstraction should actually be, rather than guessing before you have two examples.

Senior: A lambda and an anonymous class implementing the same interface — what actually differs?

Three things, and only one of them is usually visible.

Compilation. An anonymous class produces a real class file — Outer$1.class — loaded like any other. A lambda compiles to an invokedynamic instruction that the JVM links to a generated implementation on first execution. So a codebase with thousands of lambdas does not carry thousands of extra class files, which was a real concern for startup time and jar size.

this. Inside an anonymous class, this refers to the anonymous instance. Inside a lambda it refers to the enclosing instance. That is the difference that actually bites: a lambda has no way to refer to itself, so a self-referential callback needs an anonymous class or a named field.

Shadowing. An anonymous class body introduces a new scope, so it may declare a variable with the same name as one in the enclosing method. A lambda body shares the enclosing scope, so that is a compile error.

What is the same is capture: both may only capture effectively-final local variables, and both capture a reference to the enclosing instance when they use anything from it. That last point matters for leaks — a lambda stored in a long-lived listener list keeps its enclosing object alive exactly as an anonymous inner class would, which people sometimes assume lambdas avoid.

Performance is largely a wash after warm-up; the JIT inlines both. The genuine wins are the class-file count and the readability.

🏋️ Graded Exercises

1 (easy): Why does the second signature accept more callers? 
void process(ArrayList<Order> orders) { … }
void process(List<Order> orders)      { … }
Solution

The List version accepts any implementation — ArrayList, LinkedList, List.of(...), Arrays.asList(...), an unmodifiable view, or a caller's own implementation. The ArrayList version accepts exactly one class.

And it constrains you less on the inside. Declaring List means you only rely on List's contract, so the parameter type documents what you actually need.

Parameter typeAcceptsYou may rely on
ArrayListOne classRandom access, and ensureCapacity
ListAny listOrder, indexing, duplicates
CollectionAlso sets and queuesSize, iteration, contains
IterableAnything iterable, including a lazy sourceIteration only — not even size()

Take the weakest type that does the job. Each step down widens what callers can pass and narrows what you may depend on, and both directions are improvements.

The one legitimate reason to name a concrete type is when you genuinely need its guarantees — RandomAccess for an indexed loop, or ArrayDeque because you need both ends. Then say so, and prefer the interface that expresses it if one exists.

2 (easy): Why does this fail to compile, and how do you fix it? 
interface Walker { default String move() { return "walk"; } }
interface Swimmer { default String move() { return "swim"; } }

class Duck implements Walker, Swimmer { }
Solution

Duck inherits two unrelated defaults for move(), and Java refuses to pick one. The error names both interfaces explicitly.

class Duck implements Walker, Swimmer {
    @Override public String move() {
        return Walker.super.move();          // choose one
    }
}

// or combine them:
    @Override public String move() {
        return Walker.super.move() + " and " + Swimmer.super.move();
    }

Interface.super.method() is the syntax, and it works only for a direct superinterface — you cannot reach a grandparent interface that way.

SituationResolution
Two unrelated interfaces, same defaultCompile error — override explicitly
One interface extends the otherThe most specific wins, no error
A superclass has the same methodClass wins — silently, over any interface default

Why the compile error is the right design: the alternative is resolving by declaration order or some other rule the reader has to memorise, and then a silent behaviour change when someone reorders the implements clause. Forcing the choice makes the decision visible in the code.

The row to be wary of is the third. Class-wins operates silently, so adding a default to a published interface can be shadowed by an inherited superclass method in some implementor — they get the superclass behaviour and no warning that your default exists.

3 (medium): Java 8 added stream() to Collection. Why was that possible, and what would have happened before Java 8?
Solution

It was possible because stream() is a default method. Before Java 8, every method on an interface was abstract, so adding one meant every implementing class had to provide it — or fail to compile.

Collection is implemented by dozens of JDK classes and by an unbounded number of classes in other people's code. Adding an abstract stream() would have broken all of them on upgrade, which made the addition impossible in practice. Published interfaces were frozen.

interface Collection<E> {
    default Stream<E> stream() {
        return StreamSupport.stream(spliterator(), false);
    }
    default Spliterator<E> spliterator() {
        return Spliterators.spliterator(this, 0);
    }
}

Notice the default is written purely in terms of other interface methods — it has no fields to read, because interfaces have no instance state. That constraint is what makes defaults safe to inherit: a default can only use the contract, never an implementation's internals.

What implementors get is a working stream() for free, with the option to override for efficiency — which ArrayList does, providing a spliterator that knows the size and supports splitting.

The trade-off this introduced is that implementors inherit behaviour they never reviewed. A collection with unusual semantics might get a default that is subtly wrong for it and compile perfectly — which is why the guidance is to default only what is correct for every implementor.

4 (medium): Interface or abstract class for each, with reasoning? (a) Comparable; (b) a family of HTTP handlers sharing a request log and a timeout; (c) AutoCloseable; (d) an event-sourced aggregate holding a version and uncommitted events.
Solution
ChoiceWhy
(a) ComparableInterfaceA pure capability with no state. Any type may be comparable regardless of its hierarchy — which is exactly what a class's single-inheritance slot could not express
(b) HTTP handlersAbstract class (behind an interface)They share state — a logger and a timeout field. An interface cannot hold those
(c) AutoCloseableInterfaceOne method, no state, and it must apply to types that already extend something
(d) Event-sourced aggregateAbstract classThe version counter and pending-event list are genuine shared state with invariants to maintain

The deciding question is always state. Since default methods, "does it need a body?" no longer separates them — an interface can supply behaviour. Only an abstract class can supply fields.

For (b), the shape I would actually ship keeps both:

public interface HttpHandler {                    // callers depend on this
    Response handle(Request request);
}

public abstract class BaseHttpHandler implements HttpHandler {
    private final Logger log;                     // shared STATE
    private final Duration timeout;
    protected BaseHttpHandler(Logger log, Duration timeout) { … }
}

Why both: callers and tests depend on the interface, so nothing is forced into the hierarchy, and an implementor who does not want the shared state can implement HttpHandler directly. The abstract class is an optional convenience rather than a requirement — which is precisely how List and AbstractList relate.

The trap in (d) is that inheriting state pulls in the fragile-base-class risks from the previous lesson. It is justified here because the aggregate hierarchy is small, closed, and owned by one team — and sealed would make that explicit.

5 (hard): A colleague creates an interface for every service class. Evaluate the practice.
Solution

It is a pattern applied without its reason. "Program to an interface" is about depending on contracts where the implementation might vary — not about there being an interface for every class.

Cost of a reflexive interfaceConcretely
Two files per conceptUserService and UserServiceImpl, changed together forever
Navigation friction"Go to definition" lands on a declaration with no code; every stack trace gains a hop
A false abstractionAn interface extracted from one implementation just mirrors it — including the parts that should have been private
Deceptive flexibilityThe seam suggests implementations can be swapped, when nothing was ever designed for that
When it genuinely earns its place
There are two or more real implementations — or one and a clear second coming
The boundary is published across a module, so callers must not see the implementation
A test seam is needed that a mock of the concrete class cannot provide — an external system, a clock, a network
The implementation is chosen at runtime — a strategy, a plugin, a provider looked up by configuration

The testing argument is weaker than it used to be. Mockito can mock concrete classes, and Spring proxies them fine, so "we need it for tests" often does not survive scrutiny. Where it does survive is at genuine external boundaries — a payment gateway, an email sender — and that is exactly where you would want the interface anyway.

What I would propose instead: write the concrete class, and extract the interface when a second implementation actually appears. That is a mechanical, low-risk refactor with IDE support, and by then you know what the abstraction should be from two examples rather than guessing from one.

The nuance worth conceding: in a large codebase with enforced module boundaries, or a published library, the interface at the boundary is right even with one implementation today — because the cost of adding it later falls on consumers rather than on you.

6 (hard): Design a validation API using functional interfaces that composes and reports every failure rather than the first.
Solution 
@FunctionalInterface
public interface Validator<T> {

    List<String> validate(T value);        // EMPTY means valid

    default Validator<T> and(Validator<T> other) {
        return value -> {
            List<String> errors = new ArrayList<>(this.validate(value));
            errors.addAll(other.validate(value));    // BOTH always run
            return errors;
        };
    }

    static <T> Validator<T> check(Predicate<T> rule, String message) {
        return value -> rule.test(value) ? List.of() : List.of(message);
    }
}

// USE
Validator<User> validator =
    Validator.<User>check(u -> !u.name().isBlank(), "name is required")
        .and(check(u -> u.age() >= 18,        "must be 18 or older"))
        .and(check(u -> u.email().contains("@"), "invalid email"));

List<String> errors = validator.validate(user);   // ALL failures
DecisionWhy
Return List<String>, not booleanA boolean forces the caller to re-derive why. Accumulating messages is the whole requirement
and as a defaultComposition belongs on the type, and defaults let it live there without an abstract class
Both sides always evaluatedShort-circuiting would report only the first failure — the exact thing the requirement rules out
check as a static factoryAdapts a plain Predicate plus a message, so callers write predicates and not validators
@FunctionalInterfaceAdding a second abstract method would break every lambda; this makes that a build error here

The design point is that and deliberately does not short-circuit, which is the opposite of Predicate.and. A form should tell the user everything wrong at once, not make them resubmit five times — so the composition operator has to differ from the boolean one, and naming it and is arguably a small lie worth flagging.

What I would change for production: return a richer error type than String — a record carrying a field name, a code and arguments — so the UI can localise and highlight the offending field. Strings are fine for the shape and lose everything a real client needs.

The alternative worth knowing is Bean Validation (@NotBlank, @Min), which is declarative, integrates with Spring and JPA, and already accumulates violations. I would use it for standard field constraints and keep a composable Validator for cross-field and business rules that annotations express poorly.

  • A class implements many interfaces and extends one class, so capabilities that cut across a hierarchy belong in interfaces.
  • default methods exist for interface evolution — they are why Collection could gain stream() without breaking every implementation.
  • A default can only call other interface methods, having no fields to read.
  • Defaults are inherited by implementors who never reviewed them — default only what is correct for all of them.

  • Class wins over interface, silently — an inherited superclass method shadows your new default.
  • Most specific interface wins when one extends the other.
  • A functional interface has exactly one abstract method; defaults and statics do not count.
  • @FunctionalInterface moves the breakage to the definition instead of to every lambda.
  • Prefer the standard java.util.function types — they compose and everyone knows them.
  • this in a lambda is the enclosing instance, unlike in an anonymous class — and a lambda still captures its enclosing object.
  • Declare the weakest type that does the job for parameters, fields and returns.
  • The interface is the seam that makes a dependency substitutable, which is what makes the class testable.
  • Do not create an interface per class — extract it when a second implementation or a real boundary appears.
