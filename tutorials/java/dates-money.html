Dates, Time & Money Core Libraries

What you'll master: choosing the right temporal type, which is really the question "does this instant mean a moment in time, or a reading on a wall clock?" — and why storing a meeting as an Instant moves it when the timezone rules change; why LocalDateTime has no timezone and therefore does not identify a moment; the daylight-saving cases that break naive arithmetic — a day is not always 24 hours, and adding 24 hours across a DST boundary lands on the wrong wall time; why 0.1 + 0.2 != 0.3 makes double unusable for money, and the BigDecimal traps that catch people who switch — the double constructor recaptures the error, and equals compares scale so 2.0 is not 2.00; and why ZoneId beats a fixed offset for anything in the future. Prerequisites: Types for floating point.

Part 1 — Choosing the Type

TypeRepresentsHas a zone?Use for
InstantA point on the universal timelineUTC by definitionTimestamps — when something happened. Logs, audit, created-at
LocalDateA calendar date, no timeNoBirthdays, invoice dates, anything a calendar shows
LocalTimeA wall-clock time, no dateNoOpening hours, a daily alarm
LocalDateTimeA date and time, no zoneNoRarely alone — it does not identify a moment
ZonedDateTimeA moment in a named zoneZoneIdFuture events — meetings, schedules, reminders
OffsetDateTimeA moment at a fixed offsetOffset onlyWire formats, APIs, database columns
DurationA time-based amount — seconds—Timeouts, elapsed time
PeriodA date-based amount — years, months, days—Ages, subscription terms
  THE QUESTION THAT PICKS THE TYPE:

    "Is this a MOMENT, or a READING ON A CLOCK?"

    A moment              a log entry, a payment, an API call
                          -> Instant. It happened once, everywhere.

    A wall-clock reading  a meeting at 09:00 in Berlin, a shop
                          opening at 09:00 local
                          -> ZonedDateTime, or LocalDateTime + ZoneId

  THE DIFFERENCE MATTERS BECAUSE TIMEZONE RULES CHANGE. Governments
  move DST boundaries and shift offsets, several times a year
  somewhere in the world.

    A meeting stored as an Instant is pinned to a moment. If the zone
    rules change before it happens, the meeting MOVES on the
    participants' clocks — it was 09:00, now it is 10:00.

    A meeting stored as a local date-time plus a ZoneId stays at
    09:00. The moment moves instead, which is what the participants
    actually meant.

  SO: PAST EVENTS AS Instant. FUTURE EVENTS AS LOCAL TIME + ZONE.

Part 2 — LocalDateTime Is Not a Moment

  LocalDateTime.of(2026, 3, 29, 2, 30)     // does this exist?

  In Europe/Berlin, no. Clocks jump from 02:00 to 03:00 on that date,
  so 02:30 never occurs. In Europe/London it exists. In UTC it always
  exists.

  A LocalDateTime is a description, not a point in time. Converting
  one to a real moment requires a zone, and that conversion has two
  awkward cases:

    THE GAP (spring forward)
      02:30 does not exist. atZone() moves it FORWARD by the gap,
      silently, to 03:30.

    THE OVERLAP (autumn back)
      02:30 happens TWICE. atZone() picks the FIRST occurrence —
      the earlier offset — silently.

    ZonedDateTime z = local.atZone(ZoneId.of("Europe/Berlin"));
    // no exception either way

  If either case matters — billing, scheduling, legal timestamps — you
  must handle it explicitly:

    ZoneRules rules = zone.getRules();
    if (rules.getValidOffsets(local).isEmpty())      { /* gap */ }
    if (rules.getValidOffsets(local).size() > 1)     { /* overlap */ }

  THE PRACTICAL RULE: never store a LocalDateTime as if it were a
  timestamp. A "created_at" column of type LocalDateTime loses the
  information needed to know when it actually was — and the row is
  ambiguous for one hour every year.

Part 3 — Arithmetic, and Why a Day Is Not 24 Hours

  ZonedDateTime before = ZonedDateTime.of(
      LocalDate.of(2026, 3, 28), LocalTime.of(9, 0),
      ZoneId.of("Europe/Berlin"));

  before.plusDays(1)      -> 29 March, 09:00     ✓ same wall time
  before.plusHours(24)    -> 29 March, 10:00     ✗ clocks moved

  BOTH ARE CORRECT — they answer different questions.

    plusDays(1)    "the same time tomorrow"      — DATE-based
    plusHours(24)  "24 hours of elapsed time"    — TIME-based

  That is exactly the Duration/Period distinction:

    Duration   time-based: seconds and nanos. 24 hours is always
               86,400 seconds.
    Period     date-based: years, months, days. One day is whatever
               one day is in that zone on that date — 23, 24 or 25
               hours.

  ADDING A MONTH IS ALSO NOT ARITHMETIC:

    LocalDate.of(2026, 1, 31).plusMonths(1)     -> 28 February
    // clamped to the last valid day — NOT 3 March

  and it is not reversible:

    jan31.plusMonths(1).minusMonths(1)          -> 28 January

  which quietly breaks any code that computes a window by adding and
  subtracting. Compute both endpoints from the original date.

  THE MEASUREMENT MISTAKE:

    long start = System.currentTimeMillis();    // ❌ WALL CLOCK
    …
    long elapsed = System.currentTimeMillis() - start;

  currentTimeMillis can jump — NTP corrections, DST on some
  platforms, manual changes — so elapsed time can be negative or
  wrong. For durations use the monotonic clock:

    long start = System.nanoTime();             // ✓ monotonic
    Duration d = Duration.ofNanos(System.nanoTime() - start);

Part 4 — Why double Cannot Hold Money

  0.1 + 0.2 == 0.30000000000000004        // not 0.3
  1.03 - 0.42 == 0.6100000000000001       // not 0.61

  Binary floating point cannot represent 0.1 exactly, in the same way
  decimal cannot represent one third. Every arithmetic operation
  rounds to the nearest representable value, and the errors
  accumulate.

  IN MONEY TERMS: sum a million transactions and the total is wrong by
  a visible amount, ledgers do not reconcile, and no amount of
  formatting fixes it because the stored value is already wrong.

  It is not a Java flaw — it is IEEE 754, shared by every language.
  What makes it a Java trap is that `double` is the default type for a
  decimal literal, so you get it unless you think about it.

  THE TWO CORRECT REPRESENTATIONS:

  1. BigDecimal — arbitrary precision, explicit scale and rounding

     BigDecimal price = new BigDecimal("19.99");     // from a STRING
     BigDecimal tax = price.multiply(new BigDecimal("0.20"))
                           .setScale(2, RoundingMode.HALF_UP);

  2. INTEGER MINOR UNITS — cents as a long

     long priceCents = 1999;
     // fast, exact, and formatting happens only at the edges

  Minor units are simpler when every amount uses one currency with a
  fixed exponent. BigDecimal is right when scales vary, when
  currencies have different minor units, or when rounding policy is a
  business rule you must state.

Part 5 — The BigDecimal Traps

  TRAP 1 — THE double CONSTRUCTOR RECAPTURES THE ERROR

    new BigDecimal(0.1)
      -> 0.1000000000000000055511151231257827021181583404541015625

    new BigDecimal("0.1")      -> exactly 0.1        ✓

  Passing a double hands BigDecimal the imprecise value you were
  trying to escape. ALWAYS construct from a String — or from
  BigDecimal.valueOf(double), which routes through Double.toString and
  gives the short form.

  TRAP 2 — equals COMPARES SCALE

    new BigDecimal("2.0").equals(new BigDecimal("2.00"))   // FALSE
    new BigDecimal("2.0").compareTo(new BigDecimal("2.00")) // 0

  equals requires the same value AND the same scale. So a HashSet of
  BigDecimal treats 2.0 and 2.00 as different elements, while a
  TreeSet treats them as the same one — which is the
  compareTo-inconsistent-with-equals case from the Equality lesson,
  in the JDK itself.

  USE compareTo FOR VALUE COMPARISON. Always.

  TRAP 3 — DIVISION THROWS WITHOUT A ROUNDING MODE

    BigDecimal.ONE.divide(new BigDecimal("3"))
      -> ArithmeticException: Non-terminating decimal expansion

    ONE.divide(new BigDecimal("3"), 2, RoundingMode.HALF_UP)  // 0.33

  There is no default rounding because there is no safe default —
  the correct policy is a business decision.

  TRAP 4 — IT IS IMMUTABLE

    total.add(item);            // ❌ result discarded
    total = total.add(item);    // ✓

  Every operation returns a new instance, exactly like String.

  ROUNDING MODES WORTH KNOWING:

    HALF_UP      0.5 rounds away from zero — what people expect
    HALF_EVEN    0.5 rounds to the even neighbour — "banker's
                 rounding", which avoids the upward bias of HALF_UP
                 across many operations, and is the default in
                 financial standards
    UNNECESSARY  asserts no rounding is needed; throws if it is

Part 6 — Formatting, Parsing and Storage

  FORMATTING IS LOCALE-SENSITIVE, AND THAT IS A TRAP FOR MACHINE
  OUTPUT

    String.format("%.2f", 1234.5)
      -> "1234.50" in en-US
      -> "1234,50" in de-DE          — a COMMA

  Anything another program will parse must specify Locale.ROOT.
  Anything a human reads should use their locale. Mixing the two is
  how a CSV export becomes unparseable in one country.

    NumberFormat.getCurrencyInstance(Locale.GERMANY).format(amount)
      -> "1.234,50 €"               for DISPLAY

  DATE FORMATTING — DateTimeFormatter is IMMUTABLE and THREAD-SAFE,
  unlike the legacy SimpleDateFormat, which is not and has caused
  real corruption when shared as a static field.

    static final DateTimeFormatter ISO =
        DateTimeFormatter.ISO_LOCAL_DATE;              // safe to share

  STORAGE — the decisions that are hard to reverse:

    timestamps        UTC, as Instant / TIMESTAMP WITH TIME ZONE.
                      Convert to a zone only for display.
    future events     local date-time + the ZoneId, stored separately.
                      Not a UTC instant.
    money             DECIMAL(19,4) or an integer minor-unit column —
                      never FLOAT or DOUBLE.
    the currency      alongside every amount. A bare number is not
                      money.
    dates             DATE for a calendar date; do not store a
                      timestamp and hope.

  ZoneId, NOT ZoneOffset, FOR ANYTHING FUTURE:

    ZoneId.of("Europe/Berlin")     rules — knows when DST changes
    ZoneOffset.ofHours(2)          a fixed +02:00, forever

  An offset is correct for a past instant and wrong for a future
  event, because it cannot follow a rule change.

Interview Questions

Beginner: Why can't you use double for money?

Because binary floating point cannot represent most decimal fractions exactly. 0.1 has no finite binary expansion, in the same way one third has no finite decimal one — so 0.1 + 0.2 is 0.30000000000000004.

Each operation rounds to the nearest representable value, and those errors accumulate. Over a large number of transactions the total is visibly wrong, ledgers fail to reconcile, and no amount of formatting fixes it because the stored value is already incorrect.

It is not a Java flaw — it is IEEE 754, and every language using binary floating point behaves the same. What makes it a Java trap specifically is that double is the default type for a decimal literal, so you get it unless you actively choose otherwise.

The two correct representations are BigDecimal, with an explicit scale and rounding mode, or integer minor units — cents as a long — formatting only at the edges.

Beginner: What is the difference between Instant and LocalDateTime?

An Instant is a point on the universal timeline — a moment that happened once, everywhere, measured from the epoch in UTC.

A LocalDateTime is a date and a wall-clock time with no zone, so it does not identify a moment at all. "29 March 2026, 02:30" is a description; whether it corresponds to an instant, and which one, depends entirely on the zone you interpret it in — and in Europe/Berlin that particular value never occurs, because the clocks jump from 02:00 to 03:00.

So the practical rule is that a timestamp — created-at, a log entry, a payment — should be an Instant. A LocalDateTime stored as if it were a timestamp has lost the information needed to know when it actually was, and is ambiguous for one hour every autumn.

Where LocalDateTime genuinely fits is a wall-clock reading that is not tied to a moment — a shop opening at 09:00 local, whatever local means — usually paired with a ZoneId.

Mid: Why is plusDays(1) different from plusHours(24)?

Because a day is not always twenty-four hours. On a daylight-saving transition it is twenty-three or twenty-five.

plusDays(1) is date-based — it means "the same wall-clock time tomorrow", so 09:00 becomes 09:00 regardless of what happened to the clocks. plusHours(24) is time-based — exactly 86,400 seconds of elapsed time — so across a spring-forward boundary it lands at 10:00.

Both are correct; they answer different questions. The bug is using one when you meant the other, and it only appears twice a year, in one hemisphere at a time.

That is the same distinction as Period versus Duration: Period counts calendar units and Duration counts seconds.

The related surprise is that month arithmetic clamps and is not reversible: 31 January plus one month is 28 February, and subtracting a month gives 28 January. So a date window computed by adding then subtracting does not return to where it started — compute both endpoints from the original date.

Mid: What are the traps when switching from double to BigDecimal?

Four, and the first two are the ones that survive review.

The double constructor. new BigDecimal(0.1) produces 0.1000000000000000055511151231257827…, because it faithfully represents the imprecise double you were trying to escape. Always construct from a String, or use BigDecimal.valueOf, which routes through Double.toString.

equals compares scale. new BigDecimal("2.0") is not equals to new BigDecimal("2.00"), though compareTo returns zero. So a HashSet treats them as two elements and a TreeSet as one — the compareTo-inconsistent-with-equals case, in the JDK itself. Use compareTo for value comparison, always.

Division throws without a rounding mode. ONE.divide(THREE) raises ArithmeticException: Non-terminating decimal expansion, because there is no safe default — the rounding policy is a business decision and the API refuses to guess.

It is immutable. total.add(item) discards the result, exactly like String. It compiles and does nothing.

On rounding mode: HALF_UP matches what people expect, and HALF_EVEN — banker's rounding — avoids the systematic upward bias of always rounding halves away from zero, which is why financial standards prefer it across large volumes.

Senior: How would you store a future meeting time?

As a local date-time plus a ZoneId, stored as two fields — not as a UTC instant.

The reason is that timezone rules change. Governments move daylight-saving boundaries and shift offsets several times a year somewhere in the world, and the IANA database is updated accordingly.

If the meeting is stored as an Instant, it is pinned to a moment. When the rules change before the meeting happens, that moment now corresponds to a different wall-clock time — the meeting that was at 09:00 is now at 10:00 on the participants' calendars. Nobody asked for that.

If it is stored as 09:00 plus Europe/Berlin, the wall time stays 09:00 and the underlying instant moves instead — which is what "nine in the morning, Berlin time" always meant.

The corollary is that ZoneOffset is wrong for future events. A fixed +02:00 cannot follow a rule change, so it has the same defect as storing an instant. Use ZoneId, which carries rules rather than a number.

Past events are the opposite case: they happened at a specific moment, so an Instant is exactly right and a later rule change must not alter it.

The remaining detail is the DST gap and overlap. If a recurring meeting lands on 02:30 on a spring-forward date, that time does not exist — atZone will silently shift it, and for scheduling I would want to detect it with getValidOffsets and decide deliberately rather than accept the default.

Senior: What is wrong with using System.currentTimeMillis() to measure elapsed time?

It reads the wall clock, which can jump. NTP corrections adjust it forwards or backwards, an administrator can set it, virtual machines resynchronise after a pause, and on some platforms it is affected by timezone changes.

So a duration computed by subtracting two readings can be wrong, and can be negative — which typically surfaces as a nonsensical metric, a timeout that fires immediately, or a retry loop that never waits.

System.nanoTime() is monotonic: it comes from a counter that only increases and is unaffected by clock adjustments. It has no meaning as an absolute time — only differences between two readings are defined — which is exactly right for measuring elapsed time.

So the rule is currentTimeMillis or Instant.now() for "what time is it", and nanoTime for "how long did that take".

Two details worth adding. nanoTime's resolution is not guaranteed to be nanoseconds — it is platform-dependent, typically microseconds. And values are only comparable within one JVM, so they cannot be logged as timestamps or compared across processes.

🏋️ Graded Exercises

1 (easy): Why does this print false, and what should the code use? 
double total = 0.1 + 0.2;
System.out.println(total == 0.3);
Solution

0.1 and 0.2 have no exact binary representation, so each is stored as the nearest representable double and their sum is 0.30000000000000004.

// For money — BigDecimal from Strings
BigDecimal total = new BigDecimal("0.1").add(new BigDecimal("0.2"));
total.compareTo(new BigDecimal("0.3")) == 0;    // true

// Or integer minor units
long totalCents = 10 + 20;                       // exact, and fast
DetailWhy
new BigDecimal("0.1"), not new BigDecimal(0.1)The double constructor captures the imprecision you are escaping
compareTo, not equalsequals compares scale, so 0.30 is not equals to 0.3

For genuinely approximate quantities — a physical measurement, a ratio — comparing within an epsilon is the right approach, and double is fine. The rule is about money and anything else where exactness is part of the definition.

Which representation to choose: integer minor units when every amount is one currency with a fixed exponent — simpler and faster. BigDecimal when scales vary, currencies differ, or rounding policy is a business rule you must state explicitly.

2 (easy): Which type for each? (a) when a payment was processed; (b) a user's date of birth; (c) a meeting next March at 09:00 in Berlin; (d) a request timeout.
Solution
TypeWhy
(a) payment processedInstantA moment that happened once. Store UTC; convert to a zone only for display
(b) date of birthLocalDateA calendar date with no time and no zone — someone born on 3 September was born on 3 September everywhere
(c) meeting in BerlinLocalDateTime + ZoneIdA future wall-clock commitment. Storing an Instant moves it if the DST rules change
(d) timeoutDurationAn amount of elapsed time, not a point on any timeline

(b) is the one people get wrong by reaching for a timestamp. A birthday stored as an instant acquires a time and a zone it never had — and then someone born just after midnight in one zone appears to have been born the previous day in another.

(c) is the subtle one. "09:00 in Berlin next March" is a promise about a wall clock. If Germany changes its DST rules between now and then — which happens — an Instant keeps the moment and moves the meeting, while a local time plus zone keeps the meeting and moves the moment. The second is what everyone meant.

And (d) rather than Period: a timeout is seconds of elapsed time, so it is time-based. Period is for calendar amounts, where "one month" depends on which month.

3 (medium): A scheduler fires an hour early twice a year. Diagnose. 
ZonedDateTime next = last.plusHours(24);
Solution

plusHours is time-based arithmetic — exactly 86,400 seconds. Across a daylight-saving transition a calendar day is 23 or 25 hours, so adding 24 hours lands on the wrong wall-clock time.

  Berlin, spring forward (clocks 02:00 -> 03:00, so the day is 23h)

    last  = 28 March 09:00
    +24h  = 29 March 10:00      ✗ an hour late on the wall clock
    +1day = 29 March 09:00      ✓

  Autumn back (25-hour day) produces the mirror image — an hour early.
ZonedDateTime next = last.plusDays(1);      // date-based: same wall time
IntentUse
"Same time tomorrow"plusDays(1) — Period semantics
"24 hours from now"plusHours(24) — Duration semantics

Both are correct operations answering different questions, which is why this is not a bug in the API. A daily 09:00 job wants the wall clock; a "retry in 24 hours" wants elapsed time.

Why it survives testing: it is right for 363 days a year, and the two failures happen on dates nobody runs tests against — in one hemisphere at a time.

The related hazard for schedulers is a job scheduled at 02:30 in a zone that skips that hour: the time does not exist on that date, and atZone silently shifts it forward. For anything where the exact firing time matters, checking getValidOffsets is worth the lines.

The division exception is the API being deliberately unhelpful, and correctly so. There is no safe default rounding — half up, half even, floor and ceiling all give different money — so it refuses to guess and makes you state the policy.

Note the total is still not money, because it carries no currency. A bare amount cannot be safely compared or converted, so a Money type pairing the amount with a Currency is what production code wants.

5 (hard): A daily report's timestamps drift by an hour for some users, and an elapsed-time metric occasionally goes negative. Diagnose both.
Solution

Two separate defects with a common theme: using a wall clock where a different concept was needed.

The hour drift — LocalDateTime stored as a timestamp. A LocalDateTime has no zone, so it does not identify a moment. Written by a server in one zone and read in another, it is interpreted differently; and for one hour each autumn it is genuinely ambiguous, because that wall time occurs twice.

// store UTC, convert only for display
Instant createdAt = Instant.now();
createdAt.atZone(user.zone())        // at the presentation edge

The negative duration — currentTimeMillis for elapsed time. The wall clock can move backwards: an NTP correction, a VM resuming from a pause, or an administrator setting the time. Subtracting two readings across such a jump gives a negative result.

long start = System.nanoTime();                      // MONOTONIC
…
Duration took = Duration.ofNanos(System.nanoTime() - start);
QuestionClock
"What time is it?"Instant.now() / currentTimeMillis
"How long did that take?"System.nanoTime()

Why the negative duration is rare and therefore nasty: NTP corrections are usually small and infrequent, so the metric is right almost always. It appears as an occasional impossible value that nobody can reproduce, and it is often dismissed as a monitoring glitch.

The caveat on nanoTime is that it has no absolute meaning — only differences are defined, and only within one JVM. It cannot be logged as a timestamp or compared across processes.

6 (hard): Design the storage for an e-commerce order: when it was placed, when it ships, the total, and the customer's timezone.
Solution 
record Order(
    OrderId id,
    Instant placedAt,              // a MOMENT — past
    LocalDate shipDate,            // a calendar DATE, no time
    ZoneId customerZone,           // for display and for cut-offs
    Money total                    // amount + currency together
) { }

record Money(BigDecimal amount, Currency currency) {
    Money {
        amount = amount.setScale(currency.getDefaultFractionDigits(),
                                 RoundingMode.HALF_UP);
    }
}
FieldChoiceReason
placedAtInstant, stored UTCIt happened once. A later timezone rule change must not alter it
shipDateLocalDate"Ships on the 5th" is a calendar promise, not a moment — a timestamp would add a fictional time
customerZoneZoneId, not an offsetNeeded to render placedAt and to evaluate "order before 3pm" cut-offs. An offset cannot follow rule changes
totalBigDecimal + CurrencyA bare number is not money; comparison and conversion need the currency

The Money record normalising scale in its compact constructor means every instance is already at the currency's minor-unit precision — so JPY has zero decimals and USD has two, without each call site remembering.

What I would not do is store a single ZonedDateTime for placedAt. It conflates two things — the moment, and a zone for display — and databases store it inconsistently. Separate fields keep the moment immutable and the presentation zone changeable if the customer moves.

Database columns: TIMESTAMP WITH TIME ZONE for the instant, DATE for the ship date, VARCHAR for the zone id — never an offset — and DECIMAL(19,4) plus a currency code for the money. Never FLOAT.

The one thing this design still owes is a delivery window rather than a single date, since a ship date without a zone is ambiguous at the boundaries — "ships on the 5th" means the 5th in the warehouse's zone, which is worth making explicit if warehouses span regions.

🎯 Key Takeaways

  • Ask whether the value is a moment or a clock reading — that picks the type.
  • Instant for past events; local time plus ZoneId for future ones. Rule changes move a stored instant on the participants' clocks.
  • LocalDateTime has no zone and does not identify a moment — never store it as a timestamp.
  • DST gaps and overlaps are silent — atZone shifts a non-existent time and picks the first of an ambiguous one.
  • A day is not 24 hours. plusDays is date-based; plusHours(24) is elapsed time.
  • Month arithmetic clamps and is not reversible — 31 Jan + 1 month − 1 month is 28 Jan.
  • ZoneId, not ZoneOffset, for anything future — an offset cannot follow a rule change.
  • nanoTime for elapsed time; the wall clock can jump backwards.
  • double cannot hold money — 0.1 is inexact and errors accumulate.
  • Never new BigDecimal(double) — it captures the imprecision you were escaping.
  • BigDecimal.equals compares scale, so use compareTo for value.
  • divide needs a rounding mode, because there is no safe default.
  • BigDecimal is immutable — a discarded result is a silent no-op.
  • Store the currency with every amount; a bare number is not money.
  • DateTimeFormatter is thread-safe and SimpleDateFormat is not — a shared static formatter corrupts dates rather than throwing.
  • Use Locale.ROOT for machine-readable output, or a German locale writes a decimal comma into your CSV.
