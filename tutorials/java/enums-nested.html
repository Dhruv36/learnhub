Enums & Nested Classes OOP

What you'll master: enums as full classes rather than named integers — they carry fields, implement interfaces, and can give each constant its own behaviour, which replaces a switch that must be updated every time a constant is added; why an enum is the correct singleton, immune to reflection and to the serialisation attack that breaks every hand-written one; the ordering trap where ordinal() looks like a stable id and silently corrupts persisted data when someone reorders the constants; the four kinds of nested class and the distinction that matters — a non-static inner class holds a hidden reference to its enclosing instance, so a single cached listener can keep an entire object graph alive; and why EnumMap and EnumSet exist. Prerequisites: Equality and Interfaces.

Part 1 — An Enum Is a Class

enum Status { NEW, PAID, SHIPPED }

  This declares a CLASS with three public static final instances.
  Each constant is a singleton, created once at class initialisation.

  WHAT YOU GET FOR FREE:

    ==  works and is correct         constants are singletons
    switch support                   with exhaustiveness checking
    values()                         all constants, in declaration order
    valueOf("PAID")                  by name; throws if unknown
    name(), ordinal()                the identifier and its position
    Comparable                       by ordinal
    serialisable                     by NAME, not by field values

  WHY == IS RIGHT HERE, unlike everywhere else: there is exactly one
  instance per constant, guaranteed by the JVM. So identity IS value
  equality, and == additionally null-checks for free — status == PAID
  is false for null, where status.equals(PAID) would throw.

  THE TYPE SAFETY THAT MOTIVATED THEM:

    void ship(int status)      // ship(-4)? ship(999)? compiles
    void ship(Status status)   // only the three constants exist

Part 2 — Fields, Constructors and Methods

enum Planet {
    MERCURY(3.303e+23, 2.4397e6),
    EARTH  (5.976e+24, 6.37814e6);

    private final double mass, radius;      // per-constant state

    Planet(double mass, double radius) {    // implicitly private
        this.mass = mass;
        this.radius = radius;
    }

    double surfaceGravity() {
        return 6.67300E-11 * mass / (radius * radius);
    }
}

  Planet.EARTH.surfaceGravity();

  The constructor is called once per constant, at class
  initialisation. It cannot be public — you may not create new
  constants — and it must not reference static fields of the enum,
  because those are not yet initialised when the constants are built.

Part 3 — Per-Constant Behaviour

  THE SWITCH VERSION — must be edited whenever a constant is added

    double fee(Payment p, double amount) {
        switch (p) {
            case CARD:   return amount * 0.029;
            case BANK:   return 0.25;
            case CRYPTO: return amount * 0.01;
        }
    }

  Add a constant and this compiles fine — unless it is an exhaustive
  switch EXPRESSION over the enum with no default, which is the only
  form that turns the omission into a build error.

  THE ENUM VERSION — the behaviour lives with the constant

    enum Payment {
        CARD   { double fee(double a) { return a * 0.029; } },
        BANK   { double fee(double a) { return 0.25; } },
        CRYPTO { double fee(double a) { return a * 0.01; } };

        abstract double fee(double amount);
    }

    payment.fee(100);        // dispatches to the constant

  Now adding a constant WITHOUT a fee() is a compile error, because
  the abstract method is unimplemented. The compiler enforces
  completeness rather than a reviewer noticing.

  Each constant with a body is an anonymous subclass of the enum,
  which is why this works and why such an enum cannot be final.

  WHEN TO PREFER THE SWITCH: when the behaviour belongs to the CALLER
  rather than to the constant. A UI colour for an order status does
  not belong on the domain enum — that would drag presentation into
  the model. An exhaustive switch expression in the UI layer is the
  right home, and it still fails to compile when a constant is
  added.

Part 4 — The Enum Singleton

public enum Registry {
    INSTANCE;
    private final Map<String, Handler> handlers = new ConcurrentHashMap<>();
    public void register(String k, Handler h) { handlers.put(k, h); }
}

Registry.INSTANCE.register("x", handler);

🔑 The enum singleton is the only form that is correct without you doing anything. Every other approach requires remembering a defence — readResolve for serialisation, a throw in the constructor for reflection, volatile for the lazy holder. That said, the more useful question is usually whether you want a singleton at all: a single instance created once and injected gives the same sharing while remaining substitutable in tests, whereas Registry.INSTANCE is global state hardwired at every call site — the same objection as mutable static fields.

Part 5 — ordinal(), EnumMap and EnumSet

  NEVER PERSIST ordinal()

    enum Status { NEW, PAID, SHIPPED }        // NEW=0, PAID=1, SHIPPED=2

    // stored in the database as 0, 1, 2 …
    // then someone adds a constant alphabetically:

    enum Status { CANCELLED, NEW, PAID, SHIPPED }
                  // CANCELLED=0, NEW=1, PAID=2, SHIPPED=3

  EVERY EXISTING ROW NOW MEANS SOMETHING ELSE. Orders that were NEW
  read back as CANCELLED. No exception, no migration, no warning —
  the data was silently reinterpreted by a source edit.

  The same applies to @Enumerated(EnumType.ORDINAL) in JPA, which is
  the DEFAULT — so a JPA entity storing an enum is exposed to this
  unless you write @Enumerated(EnumType.STRING).

  PERSIST THE NAME, or an explicit code you control:

    enum Status {
        NEW("N"), PAID("P"), SHIPPED("S");
        private final String code;          // stable, chosen by you
    }

  ordinal() is for EnumMap and EnumSet internals. Treat it as an
  implementation detail of the JDK, not as an identifier.
  EnumMap AND EnumSet — specialised and dramatically faster

    Map<Status, Integer> counts = new EnumMap<>(Status.class);
    Set<Status> open = EnumSet.of(Status.NEW, Status.PAID);

  EnumMap is backed by an ARRAY indexed by ordinal — no hashing, no
  collisions, no boxing of the key, and iteration in declaration
  order.

  EnumSet is a BITMASK in a single long for enums of 64 or fewer
  constants. Membership tests, unions and intersections are single
  machine instructions.

  So the flags problem from the Operators lesson has a better answer
  than hand-rolled bit manipulation: EnumSet gives you the same
  performance with names, type safety and a readable toString.

Part 6 — The Four Nested Classes

  THE HIDDEN REFERENCE, AND WHY IT LEAKS

    class Screen {                       // holds a large bitmap
        private final byte[] pixels = new byte[50_000_000];

        class Listener implements EventListener {   // NOT static
            public void onEvent(Event e) { … }
        }
    }

    eventBus.register(new Screen().new Listener());

  The Listener holds an implicit `Screen.this` reference. The event bus
  holds the Listener. So the Screen — and its 50 MB array — cannot be
  collected for as long as the listener is registered, even though
  nothing else refers to the Screen and the listener never uses it.

  In a heap dump the retention path reads:

    EventBus -> Listener -> this$0 (Screen) -> byte[50000000]

  `this$0` is the compiler-generated field name, and seeing it in a
  dump is the signature of this leak.

  THE FIX IS ONE KEYWORD:

    static class Listener implements EventListener { … }

  With `static`, there is no outer reference, and the Screen is
  collectable as soon as nothing else holds it.

  MAKE NESTED CLASSES static BY DEFAULT. Drop the keyword only when
  the class genuinely needs the enclosing instance — and then know
  that you have tied their lifetimes together.

  THE SAME APPLIES TO LAMBDAS: a lambda that captures anything from
  the enclosing instance (including calling an instance method)
  captures `this`, so a long-lived registered lambda keeps its
  enclosing object alive exactly as an inner class would.

Interview Questions

Beginner: What advantages does an enum have over integer or string constants?

Type safety above all. A method taking an int status accepts -4 and 999; a method taking a Status accepts only the declared constants, so invalid values are unrepresentable rather than checked at runtime.

Namespacing and readability — Status.PAID rather than 2, so logs and debugger views are meaningful.

Compiler support — a switch expression over an enum can be checked for exhaustiveness, so adding a constant produces build errors at every site that needs updating.

And an enum is a real class: it can hold fields, implement interfaces, and define methods, so behaviour can live with the constant rather than in a switch elsewhere.

The one to mention is that == is correct for enums, unlike almost everywhere else, because each constant is a JVM-guaranteed singleton — and it null-checks for free, where status.equals(PAID) would throw.

Beginner: Why is an enum considered the best way to implement a singleton?

Because it is correct without any defensive code.

A hand-written singleton with a private constructor can be defeated by reflection — setAccessible(true) on the constructor creates a second instance. The JVM specifically forbids constructing enums reflectively, so that attack does not exist.

It can also be defeated by serialisation: deserialising produces a new object unless you implement readResolve(). Enums serialise by name and the runtime guarantees you get the same constant back.

And the lazy initialisation that hand-written versions need — double-checked locking with a volatile field, or a holder class — is handled by the JVM's class initialisation guarantees.

The caveat I would add is that the better question is often whether a singleton is wanted at all. Registry.INSTANCE is global state hardwired at every call site, which is the same objection as a mutable static field: it cannot be substituted in a test and has no lifecycle. A single instance created once and injected gives the same sharing while staying replaceable.

Mid: Why should you never persist ordinal()?

Because it encodes a constant's position in the source file, which is not a stable identifier and can be changed by an edit that looks entirely harmless.

With enum Status { NEW, PAID, SHIPPED } the stored values are 0, 1, 2. Someone adds CANCELLED at the top — alphabetically, or just because it read better — and every existing row now means something different. Orders stored as NEW read back as CANCELLED.

There is no error. No migration runs, nothing throws, and the data was silently reinterpreted by a source change with no database change at all. It is one of the few bugs that can corrupt historical data retroactively.

The trap that makes this common is that JPA's @Enumerated defaults to ORDINAL, so an entity with an enum field is exposed unless someone wrote @Enumerated(EnumType.STRING). That is a default worth checking in any codebase.

Persist name(), or better, an explicit code the enum owns — a short String field assigned in the constructor. That decouples the stored representation from both the position and the Java identifier, so a constant can be renamed without a migration.

ordinal() exists for EnumMap and EnumSet internals. Treat it as a JDK implementation detail.

Mid: When would you give each enum constant its own method body?

When the behaviour genuinely belongs to the constant and must exist for every one of them.

Declaring an abstract method on the enum and implementing it per constant means adding a constant without implementing it is a compile error. Compare a switch, which happily compiles when a new constant appears and falls through to whatever the default does — unless it is an exhaustive switch expression with no default, which is the one form that also fails.

So the choice is really about where completeness is enforced. Per-constant bodies enforce it at the enum; an exhaustive switch expression enforces it at the switch. Both are good; a switch statement with a default enforces nothing.

The case for the switch is when the behaviour belongs to the caller rather than the constant. A UI colour for an order status does not belong on a domain enum — putting it there drags presentation into the model and means the domain module depends on the UI's palette. An exhaustive switch in the UI layer keeps that dependency the right way round and still fails to compile when a status is added.

Worth knowing the mechanism: a constant with a body is an anonymous subclass of the enum, which is why the enum class is not final when any constant has one, and why they cannot be referenced as a distinct type.

Senior: Explain the inner-class memory leak.

A non-static nested class holds an implicit reference to its enclosing instance — the compiler adds a synthetic field called this$0. That is what lets it read the outer object's fields without qualification.

The leak is that anything holding the inner instance transitively holds the outer one. The classic shape is a listener:

class Screen {
    private final byte[] pixels = new byte[50_000_000];
    class Listener implements EventListener { … }   // not static
}
eventBus.register(new Screen().new Listener());

The event bus holds the listener, the listener holds the screen, and the screen holds fifty megabytes — for as long as the listener stays registered, even though nothing else references the screen and the listener never touches it.

In a heap dump the retention path shows this$0 explicitly, which is the recognisable signature.

The fix is the static keyword. A static nested class has no outer reference, so the screen becomes collectable as soon as nothing else holds it. The habit that prevents it entirely is to make nested classes static by default and drop the keyword only when the enclosing instance is genuinely needed.

The part people miss is that lambdas do the same thing. A lambda that references an instance field or calls an instance method captures this, so a long-lived registered lambda pins its enclosing object exactly as an inner class would. Capturing a local copy of just the value you need avoids it.

The same mechanism explains non-static inner classes in Android Activity leaks and in ThreadLocal values that outlive their thread — different framings of one hidden reference.

Senior: When would you use EnumMap and EnumSet over the general collections?

Whenever the keys or elements are enum constants — they are strictly better, not a micro-optimisation.

EnumMap is backed by an array indexed by ordinal(). So a lookup is an array access rather than a hash, there are no collisions, the key is not boxed, and iteration comes out in declaration order — which is usually the order you want for a status or a priority.

EnumSet is a bitmask, held in a single long for enums of 64 or fewer constants. Membership, union, intersection and complement become single machine instructions, and the memory footprint is one word regardless of how many constants are in the set.

The practical consequence I would highlight is that EnumSet replaces hand-rolled bit flags. The int flags with ADMIN = 0b0100 pattern — with its precedence traps and its unreadable debug output — gets the same performance from EnumSet, plus names, type safety, and a toString that says [READ, WRITE].

Two caveats. Neither permits null keys or elements, which is nearly always what you want but will throw if you were relying on it. And neither is synchronised, so concurrent use needs Collections.synchronizedMap or a different structure — there is no ConcurrentEnumMap.

🏋️ Graded Exercises

1 (easy): Give the enum a field so each constant carries a stable code, and say why the code is better than ordinal().
Solution 
enum Status {
    NEW("N"), PAID("P"), SHIPPED("S"), CANCELLED("X");

    private final String code;

    Status(String code) { this.code = code; }   // implicitly private

    public String code() { return code; }

    public static Status fromCode(String code) {
        for (Status s : values())
            if (s.code.equals(code)) return s;
        throw new IllegalArgumentException("unknown status code: " + code);
    }
}
IdentifierStable across…
ordinal()Nothing. Reordering or inserting a constant changes it
name()Reordering — but not renaming the constant
An explicit codeBoth. The constant can be renamed and reordered freely

The code decouples the stored representation from the Java identifier, which is what lets you rename SHIPPED to DISPATCHED without a database migration.

fromCode throwing on an unknown value is deliberate. Returning null would push the failure to a later NPE with no context; throwing here names the bad value at the boundary where it entered.

For a large enum the linear scan in fromCode would become a static Map<String, Status> built once — but note it must be initialised in a static block or holder, since a constructor cannot touch static fields that are not yet initialised.

2 (easy): Why does adding a constant break this silently, and what form would not? 
String label(Status s) {
    switch (s) {
        case NEW:     return "New";
        case PAID:    return "Paid";
        default:      return "Unknown";
    }
}
Solution

The default absorbs every future constant. Adding SHIPPED compiles cleanly and returns "Unknown" at runtime — a wrong label with no error, discovered by a user rather than by the build.

String label(Status s) {
    return switch (s) {                 // an EXPRESSION, no default
        case NEW     -> "New";
        case PAID    -> "Paid";
        case SHIPPED -> "Shipped";
    };
}

A switch expression over an enum with no default must be exhaustive. Adding a constant then fails the build at every such site, which turns "find everywhere that handles Status" from a grep into a compiler guarantee.

FormNew constant is…
Switch statement with defaultSilently absorbed
Switch statement without defaultSilently falls through — no value returned, or nothing happens
Switch expression without defaultA compile error
Abstract method on the enumA compile error, at the enum itself

Keep default only when the input is genuinely open — a value parsed from a string, or an enum from a library that may add constants outside your control. For an enum you own, exhaustiveness is worth more than the safety net.

Which of the last two rows to choose depends on where the behaviour belongs. A label is presentation, so it belongs in the UI layer as a switch — putting it on the domain enum would make the model depend on the view.

3 (medium): Replace this with per-constant behaviour and explain what the compiler now guarantees. 
double fee(Payment p, double amount) {
    if (p == Payment.CARD)   return amount * 0.029;
    if (p == Payment.BANK)   return 0.25;
    if (p == Payment.CRYPTO) return amount * 0.01;
    throw new IllegalStateException();
}
Solution 
enum Payment {
    CARD   { public double fee(double amount) { return amount * 0.029; } },
    BANK   { public double fee(double amount) { return 0.25; } },
    CRYPTO { public double fee(double amount) { return amount * 0.01; } };

    public abstract double fee(double amount);
}

payment.fee(100);       // dispatches to the constant's implementation

What the compiler now guarantees: adding a constant without a fee implementation does not compile. The abstract method must be implemented by every constant, so completeness is enforced at the enum rather than depending on someone finding every if chain.

The if chainPer-constant method
New constantCompiles; throws at runtimeCompile error
Where the rule livesScattered across every callerWith the constant it describes
Adding a second behaviourAnother chain to keep in syncAnother abstract method, enforced the same way
TestabilityTest the function with each inputSame, plus each constant is independently readable

The mechanism: each constant with a body is an anonymous subclass of the enum. That is why per-constant bodies work at all, and why such an enum is not final.

The caution: this is right when the behaviour is intrinsic to the constant. Fees are. A display colour or a translated label is not — putting those on the enum drags presentation into the domain, and the enum accumulates unrelated responsibilities. For those, an exhaustive switch in the relevant layer is better, and gives the same compile-time completeness.

If the behaviour needs collaborators — a fee that depends on a rates service — the per-constant method stops being a good fit, because an enum constant cannot be injected. A strategy resolved from a map keyed by the enum is then the right shape.

4 (medium): A database of orders is corrupted after a release that only touched Java source. Explain. 
// before
enum Status { NEW, PAID, SHIPPED }
// after
enum Status { CANCELLED, NEW, PAID, SHIPPED }

@Entity class Order {
    @Enumerated                        // note: no argument
    private Status status;
}
Solution

@Enumerated defaults to EnumType.ORDINAL, so the column holds the constant's position, not its name.

  BEFORE          stored        AFTER (constants reordered)
  NEW     = 0     0        ->   CANCELLED = 0
  PAID    = 1     1        ->   NEW       = 1
  SHIPPED = 2     2        ->   PAID      = 2

  Every existing row now reads as a DIFFERENT status. Orders that
  were NEW are now CANCELLED. Nothing threw, nothing migrated, and
  the schema did not change.

The release touched no SQL at all, which is what makes this so hard to attribute — the data "changed" because the code that interprets it changed, and the corruption is retroactive across the entire history.

@Enumerated(EnumType.STRING)      // stores "NEW", "PAID", …
private Status status;
StorageSurvives reorderingSurvives renamingColumn
ORDINAL (the default)NoYesCompact integer
STRINGYesNoReadable in the database
An explicit code via @ConverterYesYesShort and stable

STRING is the right default, and the column is also readable when someone queries the database directly — which matters more than the few bytes saved.

An AttributeConverter mapping to a short code is better still for a long-lived schema, because it survives renaming the Java constant too. The trade is one small class per enum.

Recovering from this requires knowing the old ordering and back-mapping every row — so the real defence is a test that asserts the stored representation, which fails the moment the mapping changes.

5 (hard): A heap dump shows 200 Screen objects retained by an EventBus, each holding a 50 MB array. Diagnose and fix. 
class Screen {
    private final byte[] pixels = new byte[50_000_000];

    class RefreshListener implements EventListener {
        public void onEvent(Event e) { repaint(); }
    }

    void attach(EventBus bus) { bus.register(new RefreshListener()); }
}
Solution

RefreshListener is a non-static inner class, so every instance holds a synthetic this$0 reference to its enclosing Screen.

  RETENTION PATH IN THE DUMP

    EventBus
      -> RefreshListener
        -> this$0 (Screen)
          -> byte[50000000]

  The bus holds the listener; the listener holds the screen; the
  screen holds 50 MB. Two hundred screens is 10 GB that cannot be
  collected, because the listeners were never unregistered.

Seeing this$0 in a retention path is the signature — it is the compiler-generated field name for the enclosing instance, and it appears in no source file.

FixEffect
static nested classRemoves this$0. The listener then needs whatever it uses passed explicitly
Unregister deterministicallyThe real fix for lifecycle — a detach() called when the screen closes
Weak references in the busHelps, and makes delivery non-deterministic — a listener can be collected mid-use
static class RefreshListener implements EventListener {
    private final Runnable onRefresh;                  // just what it needs
    RefreshListener(Runnable onRefresh) { this.onRefresh = onRefresh; }
    public void onEvent(Event e) { onRefresh.run(); }
}

Both fixes are needed, and they solve different problems. static stops the listener pinning the whole screen; unregistering stops the listener itself accumulating. With only the first, you leak 200 small listeners instead of 10 GB — better, and still a leak.

The lambda version has exactly the same defect: bus.register(e -> repaint()) calls an instance method, so the lambda captures this and pins the screen identically. People assume lambdas avoid this; they do not. Capturing a local copy of only what is needed is what breaks the chain.

The habit that prevents the class entirely: make every nested class static and remove the keyword only when the enclosing instance is genuinely required — at which point you have consciously tied their lifetimes together.

6 (hard): Replace this bit-flag permission system with an enum-based one, and justify the change. 
public static final int READ    = 0b0001;
public static final int WRITE   = 0b0010;
public static final int EXECUTE = 0b0100;

int perms = READ | WRITE;
if ((perms & WRITE) != 0) { … }
Solution 
enum Permission { READ, WRITE, EXECUTE }

EnumSet<Permission> perms = EnumSet.of(Permission.READ, Permission.WRITE);

if (perms.contains(Permission.WRITE)) { … }

perms.add(Permission.EXECUTE);
EnumSet<Permission> all = EnumSet.allOf(Permission.class);
EnumSet<Permission> none = EnumSet.noneOf(Permission.class);
EnumSet<Permission> readOnly = EnumSet.complementOf(
        EnumSet.of(Permission.WRITE, Permission.EXECUTE));
int flagsEnumSet
PerformanceBitmaskAlso a bitmask — a single long for ≤64 constants
Type safetyAny int compiles — perms | 64 is legal nonsenseOnly permissions
Debug output3[READ, WRITE]
Precedence trapperms & WRITE != 0 parses wrongly — bitwise binds looser than equalityNo operators involved
Adding a permissionHand-assign the next bit; exceeding 32 silently overflowsAdd a constant
Set operationsManual masksaddAll, retainAll, complementOf

The key point is that this costs nothing. EnumSet is implemented as a bitmask over the ordinals, so membership tests and unions compile down to the same machine operations. You are not trading performance for readability — you are getting the readability free.

The precedence row is a real bug source, and it is the one from the Operators lesson: & binds looser than !=, so perms & WRITE != 0 parses as perms & (WRITE != 0). In Java that fails to compile, which is the good outcome; in C it ships.

The caveats: EnumSet permits no nulls, and it is not synchronised — there is no concurrent variant, so shared mutable use needs wrapping or an immutable copy per read.

For persistence, do not store the EnumSet directly. Store the names, or a join table. Serialising it as a bitmask reintroduces the ordinal-stability problem from Part 5, with the same silent-corruption failure mode.

🎯 Key Takeaways

  • An enum is a class — fields, constructors, methods, interfaces — not a named integer.
  • == is correct for enums, because constants are JVM-guaranteed singletons, and it null-checks for free.
  • Per-constant method bodies make the compiler enforce completeness — a new constant without an implementation does not compile.
  • Keep presentation off domain enums; an exhaustive switch in the UI layer gives the same guarantee without the dependency.
  • A switch expression with no default is exhaustive; a statement with a default silently absorbs new constants.
  • Never persist ordinal() — reordering constants retroactively reinterprets every stored row, with no error.
  • JPA's @Enumerated defaults to ORDINAL, so always write EnumType.STRING.
  • An enum is the only singleton that is correct with no defensive code — immune to reflection, serialisation and lazy-init races.
  • But a singleton is still global state; an injected single instance is usually the better design.
  • EnumMap is an array indexed by ordinal — no hashing, no boxing, declaration-order iteration.
  • EnumSet is a bitmask, so it replaces hand-rolled int flags at no performance cost and with names.
  • A non-static nested class holds a hidden this$0 reference to its enclosing instance.
  • That is the classic listener leak — the bus holds the listener, which pins the whole enclosing object and everything it references.
  • Lambdas capture this too when they touch instance state, so they leak identically.
  • Make nested classes static by default, and drop the keyword only when the outer instance is genuinely needed.
