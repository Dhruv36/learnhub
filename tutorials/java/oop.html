Classes, Objects & Encapsulation OOP

What you'll master: encapsulation as an invariant-protection mechanism rather than a naming convention — why a private field with a public getter and setter is not encapsulated at all, and what the difference buys; the constructor rules that produce real bugs, including why adding one constructor silently removes the no-arg constructor and breaks every framework that reflects over your class; why calling an overridable method from a constructor sees uninitialised subclass fields — the initialisation-order trap that yields null for a field the subclass definitely assigned; why a getter returning a mutable collection hands callers a key to your internal state, so the private modifier is decoration; the four access levels and the one most people cannot name; and static's real meaning — one copy per class, which makes a mutable static field a data race by construction. Prerequisites: Methods and Types.

Part 1 — Class vs Object

  A CLASS is a blueprint: fields (state) and methods (behaviour).
  An OBJECT is one instance of it, with its own copy of the state.

    class Account {
        private final String id;      // state — per instance
        private BigDecimal balance;

        Account(String id, BigDecimal opening) {
            this.id = id;
            this.balance = opening;
        }

        void deposit(BigDecimal amount) { … }   // behaviour — shared
    }

    Account a = new Account("A-1", TEN);   // one object
    Account b = new Account("A-2", TEN);   // another, independent

  WHAT `new` ACTUALLY DOES, in order:

    1. allocate memory on the heap, zeroed
    2. run field initialisers and instance initialiser blocks,
       in source order
    3. run the constructor body
    4. return a reference to the object

  Step 2 happening BEFORE step 3 is why a field initialiser cannot see
  a constructor parameter, and step 2 running in SOURCE ORDER is why a
  field initialiser cannot reference a field declared below it.

Part 2 — Constructors

class Order {
    private final String id;
    private final List<Item> items;

    Order(String id, List<Item> items) {          // primary
        this.id = Objects.requireNonNull(id);
        this.items = List.copyOf(items);         // defensive copy
    }

    Order(String id) {                            // convenience
        this(id, List.of());                      // MUST be first
    }
}
  THE DEFAULT CONSTRUCTOR DISAPPEARS THE MOMENT YOU WRITE ONE

    class A { }                 // has an implicit A()
    class B { B(int x) { } }    // has NO B()  —  new B() fails

  This is the rule behind a class of framework failure. Jackson,
  Hibernate and many DI containers instantiate objects reflectively
  with the no-arg constructor. Adding a convenience constructor to a
  DTO removes it, and deserialisation fails at RUNTIME with a message
  about "no suitable constructor" — nowhere near the edit that caused
  it.

  this(...) vs super(...)

    this(...)   delegate to another constructor in THIS class
    super(...)  call the superclass constructor

  Either must be the FIRST statement, and you cannot use both — so a
  constructor delegates sideways or upwards, never both directly. If
  neither is written, the compiler inserts super() implicitly, which
  fails to compile when the superclass has no no-arg constructor.
⚠️ Never call an overridable method from a constructor. The superclass constructor runs before the subclass's field initialisers, so an overridden method invoked from it sees the subclass's fields at their defaults — null or 0 — even though the subclass assigns them at declaration. The result is a NullPointerException on a field that is visibly initialised in the source, which is one of the most confusing bugs in Java. Make such methods final, private, or static, or move the work out of the constructor entirely.

Part 3 — Encapsulation Is About Invariants

  THIS IS NOT ENCAPSULATION:

    class Account {
        private BigDecimal balance;
        public BigDecimal getBalance()          { return balance; }
        public void setBalance(BigDecimal b)    { balance = b; }
    }

  The field is private and every caller can still set it to anything,
  including a negative balance. The getter and setter are a public
  field with three extra lines. Nothing is protected.

  THIS IS:

    class Account {
        private BigDecimal balance;

        public BigDecimal balance() { return balance; }   // read-only

        public void deposit(BigDecimal amount) {
            requirePositive(amount);
            balance = balance.add(amount);
        }

        public void withdraw(BigDecimal amount) {
            requirePositive(amount);
            if (balance.compareTo(amount) < 0)
                throw new InsufficientFunds(id, balance, amount);
            balance = balance.subtract(amount);
        }
    }

  THE DIFFERENCE: the class now owns a RULE — the balance never goes
  negative — and enforces it on every path that can change the field.
  With a setter, that rule has to be re-checked by every caller, and
  it will be missed by one of them.

  THE TEST: name an invariant the class guarantees. If you cannot, the
  class is a data holder, and a record is probably the honest form.
  THE LEAK THAT MAKES `private` DECORATION

    class Order {
        private final List<Item> items = new ArrayList<>();
        public List<Item> getItems() { return items; }   // ❌
    }

    order.getItems().clear();       // legal. The field is private.

  Returning the internal collection hands the caller a reference to
  your state. Every rule the class enforces about `items` is now
  bypassable, and the compiler is satisfied because you never assigned
  to the field.

  THE SAME HOLE IN THE OTHER DIRECTION:

    Order(List<Item> items) { this.items = items; }   // ❌
                                     // the caller keeps a reference
                                     // and mutates it afterwards

  BOTH ENDS MUST COPY:

    Order(List<Item> items) { this.items = List.copyOf(items); }
    public List<Item> items() { return items; }   // already immutable

  Note List.copyOf is both the copy AND the immutability, which is why
  it is the right tool rather than new ArrayList<>(items).

  AND IT IS STILL SHALLOW: if Item is mutable, callers can reach
  through the unmodifiable list and change one. Immutable elements are
  what actually close this — see Immutability.

Part 4 — Access Modifiers

ModifierVisible toUse it for
privateThis class onlyThe default choice. Every field, and every method not part of the API
(none) — package-privateThe same packageCollaborating classes in one package; the modifier most people cannot name
protectedSubclasses, and the same packageExtension points designed for subclasses — and it is wider than people expect
publicEveryoneThe deliberate API surface, and nothing else
  TWO THINGS PEOPLE GET WRONG

  1. protected INCLUDES THE PACKAGE. It is not "subclasses only" — any
     class in the same package can access a protected member, subclass
     or not. So protected is wider than package-private, not
     narrower.

  2. private IS PER CLASS, NOT PER OBJECT.

       boolean sameBalance(Account other) {
           return this.balance.equals(other.balance);   // ✓ legal
       }

     A method can read another instance's private fields, as long as
     it is the same class. That is what makes equals() and copy
     constructors writable at all.

  START PRIVATE AND WIDEN ON DEMAND. Widening later is a
  source-compatible change; narrowing breaks every caller, so a
  member made public by default is public forever.

Part 5 — static vs Instance

class Counter {
    private static int totalCreated;    // ONE copy, shared by all
    private final int id;               // one per object

    Counter() { id = ++totalCreated; }

    static int totalCreated() { return totalCreated; }   // no object
    int id()                  { return id; }             // needs one
}

  A static member belongs to the CLASS. There is exactly one, it
  exists before any object does, and it lives until the class is
  unloaded — which for an application classloader is usually "forever".

  WHY A MUTABLE STATIC FIELD IS A DATA RACE BY CONSTRUCTION

  Every thread in the JVM shares that one copy. `++totalCreated` is
  read-modify-write, so two threads can read the same value and both
  write the same result — a lost update, silently.

  It is also global state: any code anywhere can change it, so a test
  that runs after another test sees whatever the first one left. That
  is the usual cause of tests that pass alone and fail in a suite.

  static IS RIGHT FOR: constants (static final, immutable), pure
  utility functions, and factory methods.
  static IS WRONG FOR: mutable state, and anything you might want to
  substitute in a test.

Part 6 — The Four Pillars, Honestly

🔑 Encapsulation is the pillar that survives every architectural fashion. Inheritance has narrowed to interfaces and sealed hierarchies; polymorphism competes with pattern matching; abstraction is contested by "just read the code". But "this class owns a rule and enforces it on every path" is as load-bearing in a functional style as an object-oriented one — it is why records have compact constructors that validate, and why an immutable value type is the strongest form of encapsulation available, not an exception to it.

Interview Questions

Beginner: What is the difference between a class and an object?

A class is the blueprint — it declares what state instances will have and what they can do. An object is one instance of that blueprint, with its own copy of the state.

Two Account objects share the class's methods but each has its own balance, so depositing into one does not affect the other.

The detail worth adding is what new actually does, because the order explains several later bugs: it allocates zeroed memory on the heap, runs the field initialisers and instance initialiser blocks in source order, runs the constructor body, and returns a reference. Field initialisers running before the constructor body is why they cannot see constructor parameters, and their running in source order is why one cannot reference a field declared below it.

Beginner: What happens if you write a constructor with arguments and nothing else?

The implicit no-arg constructor disappears. Java supplies a default constructor only when the class declares none at all, so as soon as you write B(int x), the expression new B() stops compiling.

Within your own code that is usually caught immediately by the compiler. Where it bites is reflection: Jackson, Hibernate, JAXB and many DI containers instantiate a class by calling its no-arg constructor. Adding a convenience constructor to a DTO removes it, and deserialisation then fails at runtime, with a message about no suitable constructor, in a completely different part of the system from the edit that caused it.

The fix is to add the no-arg constructor back explicitly, or to tell the framework which constructor to use — for Jackson, @JsonCreator, or the parameter-names module. And for a pure data carrier, a record avoids the question entirely, since modern versions of these libraries support them directly.

Mid: Is a class with a private field and public getters and setters encapsulated?

No. It is a public field with three extra lines of ceremony.

Encapsulation is about protecting invariants — rules the class guarantees. A setBalance that accepts anything means the class guarantees nothing: any caller can set a negative balance, and the rule "a balance is never negative" has to be re-checked by every caller instead. One of them will forget.

The encapsulated version has no setter. It exposes deposit and withdraw, each validating, so every path that can change the field enforces the rule. The class owns it, and a caller cannot get it wrong.

The test I would apply is to name an invariant the class guarantees. If nothing comes to mind, the class is a data holder — and then the honest form is a record, which says so in one line rather than pretending to encapsulate something.

The related hole is worth mentioning in the same breath: a getter that returns the internal List hands callers a reference to your state, so getItems().clear() is legal and the private modifier is decoration. Encapsulation has to cover what the accessors return, not just the field declarations.

Mid: Why should a constructor never call an overridable method?

Because of initialisation order. When you construct a subclass, the superclass constructor runs first — before the subclass's field initialisers and before its constructor body.

So if the superclass constructor calls a method that the subclass overrides, the overriding version runs while the subclass's own fields are still at their defaults: null for references, zero for numbers. A field the subclass visibly assigns at its declaration is null at that moment.

class Base { Base() { init(); } void init() { } }

class Sub extends Base {
    private final List<String> items = new ArrayList<>();
    @Override void init() { items.add("x"); }   // NPE — items is null
}

That is a particularly confusing failure, because the stack trace points at a line where the field is plainly initialised a few lines above.

The fixes are to make any method a constructor calls final, private or static, so it cannot be overridden; or to move the work out of construction entirely into an explicit initialisation step the caller invokes. The general principle is that a half-constructed object should never be visible to code that does not know it is half-constructed.

Senior: How do you decide what to make public, and why does it matter so much?

Start everything private and widen only when a concrete need appears. The asymmetry is the reason: widening access later is a source-compatible change, and narrowing it breaks every caller. So a member made public by default is public for the lifetime of the code.

For a library or a shared module that is a genuine commitment — you cannot remove or rename a public member without a deprecation cycle. Even within one application it is a commitment in practice, because anything reachable will eventually be reached, and then it is load-bearing.

The level people underuse is package-private, the default with no modifier. It lets collaborating classes in one package see each other while keeping them invisible outside, which is exactly what a cohesive package wants. It is also what makes tests in the same package able to reach internals without opening them to the world.

The level people misunderstand is protected. It is not "subclasses only" — it includes the entire package, so it is wider than package-private, not a narrowing of it. And a protected member is part of your API for subclasses, which means changing it breaks them as surely as changing a public one breaks callers.

My working rule is that public should describe a deliberate contract, and everything supporting it should be private. If the public surface of a class is most of its members, the class probably has no invariant to protect — which is a design question rather than an access one.

Senior: When is static the right choice, and what does it cost?

static means one copy per class rather than per object, existing before any instance and living until the class is unloaded — which for an application classloader is effectively forever.

It is right for three things: constants that are genuinely immutable, pure functions whose output depends only on their arguments, and factory methods, where the class is the natural namespace.

It is wrong for mutable state, and the reason is structural rather than stylistic. Every thread in the JVM shares that one copy, so ++count — a read-modify-write — loses updates under concurrency with no error. And every test shares it too, which is the usual cause of a suite that fails in one order and passes in another.

It is also wrong for anything with a side effect or a collaborator — a clock, a database, a random source. A static call hardwires the dependency at every call site, so it cannot be substituted in a test. That is not a testing inconvenience so much as evidence that the dependency was never made explicit.

The subtlety worth adding is that public static final does not mean immutable. final prevents reassignment of the reference, not mutation of the object, so a public static final List is globally writable by anything that can see it — List.of(...) is what actually closes that.

🏋️ Graded Exercises

1 (easy): Why does new Config() fail to compile? 
class Config {
    private final String path;
    Config(String path) { this.path = path; }
}

Config c = new Config();
Solution

Declaring any constructor removes the implicit no-arg one. Java supplies a default constructor only when a class declares none, so Config(String) is now the only way to construct one.

Config() { this("default.conf"); }      // add it back explicitly

Where this actually hurts is reflection, not your own code. Here the compiler catches it. But Jackson, Hibernate and most DI containers instantiate objects by calling the no-arg constructor, so adding a convenience constructor to an existing DTO removes it and deserialisation starts failing at runtime — with an error about no suitable constructor, raised far from the edit that caused it.

FixWhen
Add the no-arg constructor backThe framework needs it and the fields can be set afterwards
@JsonCreator on the real constructorFields are final and you want them set at construction — the better design
Use a recordIt is a data carrier with no invariant; modern Jackson and JPA support them

The design point behind it: a no-arg constructor plus setters means the object can exist in an invalid, half-populated state. Requiring the values at construction is what makes the final fields possible and the invariant enforceable — so the framework accommodation should be the annotation, not weakening the class.

2 (easy): Is this class encapsulated? Justify your answer. 
class User {
    private String email;
    public String getEmail()          { return email; }
    public void setEmail(String e)    { this.email = e; }
}
Solution

No. The field is private and any caller can still set it to anything — an empty string, a value with no @, or null. The accessors are a public field with three extra lines.

The question that settles it: what rule does this class guarantee? Nothing. So there is no invariant, and therefore nothing being encapsulated.

// EITHER enforce a rule, and the class earns its existence:
class User {
    private String email;

    public String email() { return email; }

    public void changeEmail(String candidate) {
        if (!EmailAddress.isValid(candidate))
            throw new IllegalArgumentException("invalid email");
        this.email = candidate;
    }
}

// OR admit it is data, and say so in one line:
record User(String email) { }
SignalWhat it suggests
A setter for every fieldNo invariant — probably a record
Validation duplicated in several callersThe rule belongs in the class
Methods named for operations, not fieldsGenuine encapsulation

The stronger version of this design makes the email itself a type — an EmailAddress record that validates in its compact constructor. Then an invalid email cannot be represented anywhere in the program, rather than being re-checked at each boundary, and the method signature documents what it accepts.

3 (medium): Find the encapsulation hole, and fix both ends. 
class Order {
    private final List<Item> items;
    Order(List<Item> items)     { this.items = items; }
    public List<Item> getItems() { return items; }
}
Solution

Both ends leak, and the field being private final hides neither.

List<Item> mine = new ArrayList<>(List.of(itemA));
Order order = new Order(mine);

mine.add(itemB);              // ❌ mutates the order from OUTSIDE
order.getItems().clear();     // ❌ mutates it from the getter

final prevents reassigning the reference, not mutating the object it points at. The constructor stored the caller's list, and the getter handed it back — so the "private" collection is reachable by anyone who has ever touched the class.

class Order {
    private final List<Item> items;

    Order(List<Item> items) {
        this.items = List.copyOf(items);    // copy AND make immutable
    }

    public List<Item> items() { return items; }   // already immutable
}
OptionNote
List.copyOf(items)Best. One call gives both the defensive copy and immutability, so the getter needs no wrapping
new ArrayList<>(items) + unmodifiableList in the getterWorks. Two things to remember instead of one, and the wrapper is a view — the class can still mutate the backing list
Return a copy from the getterSafe, and allocates on every call. Fine for small collections, wasteful in a loop

It is still shallow. If Item is mutable, a caller can iterate the unmodifiable list and change an item's fields. Defensive copying protects the structure, not the elements — immutable element types are what actually close it.

And List.copyOf rejects nulls, which is usually a feature: it turns "this collection must not contain nulls" into an enforced rule at the boundary rather than an assumption.

4 (medium): Why does this throw, when items is clearly initialised? 
class Base {
    Base() { init(); }
    void init() { }
}

class Sub extends Base {
    private final List<String> items = new ArrayList<>();
    @Override void init() { items.add("x"); }
}

new Sub();     // NullPointerException
Solution 
  CONSTRUCTION ORDER

  1. new Sub()  ->  Sub's constructor implicitly calls super()
  2. Base's constructor body runs        -> calls init()
  3. DYNAMIC DISPATCH selects Sub's override
  4. Sub.init() touches `items`... which has NOT been initialised yet
     -> NullPointerException
  5. (never reached) Sub's field initialisers would have run here
  6. (never reached) Sub's constructor body

The superclass constructor runs before the subclass's field initialisers. So an overridable method called from a constructor sees the subclass's fields at their defaults — null here — even though the source plainly assigns one at its declaration.

What makes it so confusing is that the stack trace points at items.add("x"), and the field is visibly initialised three lines above. Nothing in the subclass is wrong; the bug is in Base, which is often a different file and sometimes a different library.

FixEffect
Make init() finalIt can no longer be overridden, so the constructor calls a known implementation
Make it private or staticSame guarantee — neither participates in dynamic dispatch
Move the work out of the constructorAn explicit start() the caller invokes on a fully-built object. Best when the work is substantial
Pass the value in as a constructor argumentRemoves the need for the callback entirely

The general principle is that a half-constructed object must never escape to code that does not know it is half-constructed. The same rule forbids passing this out of a constructor — registering a listener, starting a thread, or putting it in a cache — because another thread can then observe the object before its fields are assigned. That is a genuine concurrency bug, not just a design preference.

5 (hard): A counter is wrong under load and a test suite fails only when run in full. Both trace to the same line. 
class Session {
    private static int active;
    Session()      { active++; }
    void close()   { active--; }
    static int activeCount() { return active; }
}
Solution

One mutable static field, two distinct failures.

Under load — lost updates. active++ is not atomic. It is a read, an increment and a write, so two threads can read the same value, both compute the same result, and both store it. One increment vanishes, silently and non-deterministically.

In the test suite — shared global state. There is one copy per class, and the class outlives every test. So a test asserting activeCount() == 1 sees whatever previous tests left behind. It passes alone and fails in the suite, and the failure moves when the order changes, which makes it look flaky rather than wrong.

FixSolvesNote
AtomicIntegerThe raceincrementAndGet() is a single atomic operation. Still global
LongAdderThe race, faster under contentionSpreads updates across cells; better when writes greatly outnumber reads
An injected instanceBothA SessionRegistry object passed in — each test gets a fresh one, and there is no global to race on
synchronizedThe raceCorrect and heavier than an atomic for a single counter
class SessionRegistry {
    private final AtomicInteger active = new AtomicInteger();
    void opened()  { active.incrementAndGet(); }
    void closed()  { active.decrementAndGet(); }
    int activeCount() { return active.get(); }
}

Making it an instance is the fix that addresses both symptoms, and it is the one people skip because AtomicInteger makes the visible bug go away. The test failure is not incidental — it is the design telling you that global mutable state has no owner and no lifecycle.

The remaining flaw even after this: close() must be called exactly once per session. A missed close on an exception path leaks the count upward forever, so the registry needs try/finally discipline or an AutoCloseable session. A counter that only counts correctly on the happy path is not a counter.

6 (hard): Design the class. A TemperatureReading has a sensor id, a Celsius value, and a timestamp. Values below absolute zero are invalid. Readings are compared, sorted, logged, and used as map keys.
Solution 
record TemperatureReading(String sensorId, double celsius, Instant at)
        implements Comparable<TemperatureReading> {

    private static final double ABSOLUTE_ZERO = -273.15;

    TemperatureReading {                         // compact constructor
        Objects.requireNonNull(sensorId, "sensorId");
        Objects.requireNonNull(at, "at");
        if (celsius < ABSOLUTE_ZERO)
            throw new IllegalArgumentException(
                "below absolute zero: " + celsius);
    }

    public double fahrenheit() { return celsius * 9 / 5 + 32; }

    @Override
    public int compareTo(TemperatureReading other) {
        return at.compareTo(other.at);
    }
}
RequirementHow a record satisfies it
Compared and used as map keysequals and hashCode are generated from all components and are consistent by construction — the contract in Equality cannot be got wrong
LoggedtoString is generated and includes every component
Invalid values rejectedThe compact constructor runs before the fields are assigned, so an invalid instance cannot exist
SortedComparable by timestamp — a deliberate choice, see below
ImmutableComponents are final, so it is thread-safe and safe to share

Why a record rather than a class: there is exactly one invariant, and it is enforceable at construction. Everything else the requirements ask for — equality, hashing, printing — is boilerplate that a record generates correctly. A hand-written class here is fifty lines with three opportunities to break the equals/hashCode contract.

The Comparable choice deserves a caveat, and I would raise it in review. Ordering by timestamp alone means two readings from different sensors at the same instant compare equal, so compareTo is inconsistent with equals. That breaks TreeSet and TreeMap, which use compareTo for identity and would silently drop one of the readings.

The safer design is not to implement Comparable at all and to pass an explicit Comparator at each sort site. There is no single natural order for a reading, and a comparator says which one is meant:

readings.sort(Comparator.comparing(TemperatureReading::at)
                        .thenComparing(TemperatureReading::sensorId));

One thing a record cannot give you is a unit-safe temperature. double celsius can still be passed a Fahrenheit value by a confused caller. A Celsius wrapper type would close that — the same argument as AccountId in the Methods lesson, and worth the extra type when unit confusion has consequences.

🎯 Key Takeaways

  • Encapsulation protects invariants, not fields. A getter-and-setter pair for every field is a public field with ceremony.
  • The test is whether you can name a rule the class guarantees. If not, it is data — use a record.
  • Returning an internal collection makes private decoration — getItems().clear() is legal.
  • Both ends must copy. Storing a caller's collection is the same hole in the other direction.
  • Defensive copying is shallow — immutable element types are what actually close it.
  • Declaring any constructor removes the implicit no-arg one, which breaks reflective frameworks at runtime, far from the edit.
  • this() or super() must be first, and you cannot use both — a constructor delegates sideways or upwards, never both.
  • Never call an overridable method from a constructor — it runs before subclass fields are initialised and sees null.
  • A half-constructed object must never escape, which also forbids publishing this from a constructor.
  • Field initialisers run in source order, before the constructor body.
  • protected includes the whole package — it is wider than package-private, not narrower.
  • private is per class, not per object, which is what makes equals and copy constructors writable.
  • Start private and widen on demand — widening is source-compatible, narrowing breaks every caller.
  • Mutable static state is a data race and a shared test fixture — count++ loses updates, and suites fail in ways single tests do not.
  • public static final is not immutable — final stops reassignment, not mutation.
  • Encapsulation is the pillar that survives every fashion, and an immutable value type is its strongest form rather than an exception to it.
