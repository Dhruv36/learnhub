Collections Internals Core Libraries

What you'll master: how HashMap actually works, and the consequences that only make sense once you know — why capacity is always a power of two, so the bucket index is a bitmask rather than a modulo; why the hash is spread before masking, because masking keeps only the low bits and a hash differing solely in its high bits would collide every time; why a bucket converts to a red-black tree at eight entries, which turned a denial-of-service attack into a logarithmic inconvenience; what resizing costs and why a map built once should be pre-sized; why ArrayList grows by 1.5× rather than doubling, and why remove(0) in a loop is quadratic; and how ConcurrentHashMap achieves lock-free reads. Prerequisites: Collections Framework and equals & hashCode.

Part 1 — The HashMap Structure

  A HashMap is an ARRAY OF BUCKETS. Each bucket holds either nothing,
  a short linked list of entries, or — past a threshold — a red-black
  tree.

    table[0] -> null
    table[1] -> (k1,v1) -> (k9,v9)          two keys collided here
    table[2] -> null
    table[3] -> (k4,v4)
    …

  PUT, STEP BY STEP:

    1. h = key.hashCode()
    2. h = h ^ (h >>> 16)              SPREAD — see Part 2
    3. index = h & (table.length - 1)   MASK  — see Part 2
    4. walk the bucket; if a key is equals(), REPLACE the value
    5. otherwise append, and treeify the bucket if it is long enough
    6. if size exceeds the threshold, RESIZE

  GET is steps 1-3, then a walk of that one bucket comparing with
  equals().

  WHICH IS WHY THE equals/hashCode CONTRACT IS LOAD-BEARING: step 3
  picks the bucket from the hash, and step 4 identifies the entry with
  equals. If two equal objects hash differently they land in different
  buckets, and the equals comparison never happens — the failure from
  the Equality lesson, seen from the inside.

Part 2 — Why Power-of-Two, and Why Spread

  CAPACITY IS ALWAYS A POWER OF TWO — 16, 32, 64, …

  Because then the modulo is a bitmask:

    h % 16          a division — tens of cycles
    h & 15          one AND    — a single instruction

  and (length - 1) for a power of two is all ones in binary:
    16 - 1 = 15 = 0b1111

  So the mask keeps the low four bits, which is the same answer as
  the modulo, far faster. It is also inherently non-negative, which
  the % operator is not — the negative-hash bug from the Operators
  lesson cannot occur here.

  Ask for new HashMap<>(1000) and you get a table of 1024. The
  constructor rounds UP to the next power of two.

  THE COST OF MASKING: IT ONLY LOOKS AT THE LOW BITS.

  Two hash codes differing only above bit 4 land in the SAME bucket:

    0000_0000_0000_0001    -> & 15 -> 1
    1111_1111_0001_0001    -> & 15 -> 1     collision

  Real hash codes do this constantly. Integer.hashCode() is the value
  itself, so 1, 17, 33, 49 all mask to bucket 1 — and a map keyed on
  ids that happen to be spaced by 16 degenerates to a single bucket.

  HENCE THE SPREAD:

    h = h ^ (h >>> 16);

  XOR the top 16 bits into the bottom 16. Now high-bit differences
  influence the low bits that the mask reads, so the distribution
  survives masking. One shift and one XOR, chosen because it is
  cheap — it is a mitigation, not a real hash function.

Part 3 — Treeification

  A bucket normally holds a linked list, so a lookup within it is
  O(k) for k entries. Fine when k is 1 or 2.

  BUT IF EVERY KEY COLLIDES, k = n AND LOOKUP BECOMES O(n).

  That was an exploitable denial of service. An attacker who knows the
  hash function can craft thousands of keys that all hash to one
  bucket — sent as JSON fields or form parameters — and a single
  request turns every map operation quadratic. It affected most web
  frameworks in 2011.

  THE FIX, IN JAVA 8: convert a long bucket to a RED-BLACK TREE.

    TREEIFY_THRESHOLD   = 8     list -> tree, at 8 entries in a bucket
    UNTREEIFY_THRESHOLD = 6     tree -> list, on removal (hysteresis,
                                so it does not flip back and forth)
    MIN_TREEIFY_CAPACITY = 64   below this, RESIZE instead of
                                treeifying — a small table with a long
                                bucket is under-sized, not attacked

  Worst-case lookup becomes O(log n) instead of O(n). The attack
  degrades performance rather than destroying it.

  TREEIFICATION NEEDS AN ORDERING. If the keys are Comparable it uses
  that; otherwise it falls back to comparing class names and identity
  hashes — which works and is slower.

  IN NORMAL CODE YOU WILL NEVER SEE A TREEIFIED BUCKET. Reaching 8
  collisions in one bucket with a decent hashCode is vanishingly
  unlikely. Seeing one means either an attack or a genuinely bad
  hashCode — a constant one, or a field with very few distinct
  values.

Part 4 — Load Factor and Resizing

  DEFAULT_LOAD_FACTOR = 0.75
  threshold = capacity × loadFactor

    capacity 16  -> resize at 12 entries
    capacity 32  -> resize at 24
    capacity 64  -> resize at 48

  RESIZING allocates a table of double the size and redistributes
  every entry. It is O(n), and it happens repeatedly while a map
  grows:

    inserting 1,000 entries into new HashMap<>()
      resizes at 12, 24, 48, 96, 192, 384, 768
      = 7 reallocations, and ~1,500 entry moves in total

    new HashMap<>(2048)
      = 0 resizes

  WHY 0.75: a space/time compromise. Higher means fewer, larger
  buckets — less memory, more collisions. Lower means more empty
  slots — more memory, fewer collisions. 0.75 was chosen empirically
  and is almost never worth changing.

  THE SIZING TRAP: THE ARGUMENT IS CAPACITY, NOT EXPECTED SIZE.

    new HashMap<>(1000)     -> capacity 1024, resizes at 768

  So sizing for 1,000 entries still resizes. To avoid it entirely you
  need capacity / 0.75:

    new HashMap<>((int)(1000 / 0.75f) + 1)     -> capacity 2048

  In Java 19+ there is a method that does the arithmetic for you:

    HashMap.newHashMap(1000)
🔑 Java 8 changed resize from a correctness hazard to merely a cost. The old implementation re-inserted entries at the head of each bucket, and under concurrent resizing two threads could link a bucket into a cycle — producing an infinite loop in get() that pinned a CPU at 100% forever. It was a famous production failure, and its cause was using a plain HashMap from multiple threads. Java 8 preserves relative order during resize so the cycle cannot form, but a HashMap is still not thread-safe — you now get lost updates and corrupted state instead of a hang, which is quieter rather than better.

Part 5 — ArrayList Growth

  DEFAULT_CAPACITY = 10, and growth is 1.5x — NOT doubling

    newCapacity = oldCapacity + (oldCapacity >> 1)

    10 -> 15 -> 22 -> 33 -> 49 -> 73 -> …

  Each growth allocates a new array and System.arraycopy's everything
  across. Appending is AMORTISED O(1): most appends are free, and the
  occasional copy averages out over the sequence.

  WHY 1.5x RATHER THAN 2x: it wastes less memory — at most 50% slack
  instead of 100% — and the reclaimed blocks are more likely to be
  reusable for the next allocation. The trade is slightly more
  frequent copies.

  THE OPERATIONS THAT ARE NOT O(1):

    add(0, x)        O(n)   shifts every element right
    remove(0)        O(n)   shifts every element left
    remove(Object)   O(n)   scans to find it, then shifts

  SO THIS IS QUADRATIC:

    while (!list.isEmpty()) process(list.remove(0));   // O(n^2)

  Each removal shifts the remaining elements. Draining 100,000
  elements from the front performs about 5 billion element moves.

    // Use a Deque, where both ends are O(1):
    Deque<T> queue = new ArrayDeque<>(list);
    while (!queue.isEmpty()) process(queue.poll());

  ArrayDeque is a CIRCULAR BUFFER — head and tail indices into an
  array — so adding or removing at either end is O(1) with no
  shifting. That is why it beats LinkedList for queues: same
  complexity, contiguous memory.

Part 6 — ConcurrentHashMap

  READS ARE LOCK-FREE. WRITES LOCK ONE BIN.

  The table is volatile and entries are read with volatile semantics,
  so get() takes no lock at all — it cannot block, and it cannot be
  blocked by a writer.

  A write synchronizes on the FIRST NODE of its bucket, so two writers
  to different buckets never contend. With a well-distributed hash and
  a table of thousands of bins, concurrent writes are effectively
  parallel.

  (Java 7 used fixed "segments" — typically 16 locks, so at most 16
  concurrent writers regardless of size. Java 8 replaced that with
  per-bin locking, which scales with the table.)

  WHAT THIS COSTS YOU IN GUARANTEES:

    size()            APPROXIMATE under concurrent modification —
                      a sum of per-cell counters, accurate only when
                      quiescent
    iteration         WEAKLY CONSISTENT — never throws
                      ConcurrentModificationException, and may or may
                      not reflect writes made during the traversal
    compound ops      atomic ONLY through the provided methods

  THE LAST POINT IS THE ONE THAT CAUSES BUGS:

    if (!map.containsKey(k)) map.put(k, v);    // ❌ RACES
    map.putIfAbsent(k, v);                     // ✓ atomic
    map.computeIfAbsent(k, this::load);        // ✓ atomic

  Each individual method is atomic; a sequence of them is not. And
  the function you pass to computeIfAbsent must not modify the map —
  doing so can deadlock, because the bin lock is already held.

  NULLS ARE FORBIDDEN, keys and values both. HashMap permits them; the
  concurrent version cannot, because get() returning null would be
  ambiguous between "absent" and "mapped to null" with no way to
  re-check atomically.

Interview Questions

Beginner: How does HashMap find a value?

It is an array of buckets. On get, the map takes the key's hashCode(), spreads it, masks it to an index within the table, and then walks that one bucket comparing keys with equals.

So the hash chooses where to look and equals decides which entry it is. That two-step process is exactly why both methods must agree: if two equal keys produce different hashes they are sent to different buckets, and the equals comparison never happens.

In the normal case a bucket holds zero or one entries, so a lookup is a hash, a mask, and one comparison — constant time. Collisions put several entries in one bucket, and the walk is what makes a bad hashCode expensive.

Beginner: Why is HashMap's capacity always a power of two?

So that the modulo can be a bitmask. For a power-of-two length, h & (length - 1) produces the same result as h % length, because length - 1 is all ones in binary — and a bitwise AND is a single instruction where a division is tens of cycles.

It also gives a non-negative result automatically, which % does not — the negative-index bug from the Operators lesson simply cannot happen here.

The consequence is that asking for new HashMap<>(1000) gives you a table of 1024; the constructor rounds up to the next power of two.

The cost is that masking only reads the low bits of the hash, which is why the hash is spread first — otherwise keys differing only in their high bits would all collide.

Mid: Why does HashMap spread the hash before masking?

Because the mask discards everything above the low bits. With a table of 16, only the bottom four bits of the hash affect the bucket, so any two keys differing solely above bit 4 collide.

That is not hypothetical. Integer.hashCode() returns the value itself, so 1, 17, 33 and 49 all mask to bucket 1. A map keyed on ids that happen to be spaced by a power of two degenerates to a single bucket while looking perfectly reasonable.

The spread is h ^ (h >>> 16) — XOR the top sixteen bits into the bottom sixteen. High-bit differences now influence the bits the mask reads, so the distribution survives.

It is deliberately cheap: one shift and one XOR. It is a mitigation for weak hash codes rather than a real hash function, and it cannot rescue a genuinely bad one — a constant hashCode stays constant after spreading. The map's job is to tolerate mediocre hashes, not to fix broken ones.

Mid: What is treeification and why was it added?

When a single bucket accumulates eight entries, HashMap converts that bucket from a linked list into a red-black tree, changing lookups within it from O(k) to O(log k). It converts back at six on removal, with the gap providing hysteresis so it does not oscillate.

It was added in Java 8 to blunt a hash collision denial-of-service attack. An attacker who knows the hash function can craft thousands of keys that all land in one bucket — submitted as JSON fields or form parameters, which frameworks put straight into a map. Every operation on that map then becomes O(n), so one modest request consumes enormous CPU. It affected most web frameworks around 2011.

Treeification does not prevent the collisions; it makes their cost logarithmic rather than linear, which turns an outage into a slowdown.

Two details worth knowing. Below a table capacity of 64 the map resizes instead of treeifying, on the reasoning that a small table with a long bucket is under-sized rather than under attack. And treeification needs an ordering — it uses Comparable if the keys implement it, and otherwise falls back to comparing class names and identity hashes.

In ordinary code you will never see a treeified bucket. Encountering one means either an attack or a hashCode with very few distinct outputs.

Senior: What happens on resize, and why did the pre-Java-8 version hang?

When the entry count exceeds capacity times the load factor — 0.75 by default — the map allocates a table of double the size and redistributes every entry. That is an O(n) operation, and it happens repeatedly as a map grows: inserting a thousand entries into a default map resizes seven times.

Because the capacity doubles and the index is a mask, an entry either stays at index i or moves to i + oldCapacity, decided by one additional bit. Java 8 exploits that to split each bucket into two lists cheaply.

The pre-Java-8 hang came from how the old implementation rehashed: it inserted each entry at the head of its new bucket, which reversed the list. If two threads resized the same map concurrently, one could be part-way through reversing a chain while the other traversed it, and the two could link nodes into a cycle.

After that, a get() that landed in the affected bucket would walk the cycle forever. The symptom was a thread pinned at 100% CPU with no exception and no progress — and it typically appeared under load, long after the unsafe sharing was introduced.

Java 8 preserves relative order during the split, so the cycle cannot form. But the important point is that this did not make HashMap thread-safe — it changed the failure mode from an obvious hang to silent lost updates and corrupted state, which is quieter and arguably worse to diagnose. Shared maps still need ConcurrentHashMap.

Senior: How does ConcurrentHashMap achieve lock-free reads?

The table reference and the entry fields are volatile, so get() reads them with volatile semantics and needs no lock at all. A reader cannot block, and cannot be blocked by a writer — which is what makes it scale for read-heavy workloads.

Writes synchronize on the first node of the target bin, so two writers touching different buckets never contend. With a well-distributed hash and a table of thousands of bins, concurrent writes are effectively parallel.

That is a change from Java 7, which used a fixed number of segments — typically sixteen locks — so at most sixteen threads could write concurrently regardless of map size. Per-bin locking scales with the table instead.

What you give up is worth stating precisely. size() is approximate under concurrent modification, because it sums per-cell counters. Iteration is weakly consistent: it never throws ConcurrentModificationException, and it may or may not observe writes made during the traversal. And atomicity is per operation — containsKey followed by put is two atomic operations with a race between them, which is why putIfAbsent and computeIfAbsent exist.

Nulls are forbidden for keys and values, unlike HashMap. The reason is specific to concurrency: with nulls permitted, a get returning null would be ambiguous between "absent" and "mapped to null", and unlike in a single-threaded map you could not resolve it with a follow-up containsKey, because the answer may change between the two calls.

The remaining trap is that the function passed to computeIfAbsent must not modify the map — the bin lock is already held, so doing so can deadlock.

🏋️ Graded Exercises

1 (easy): Why does new HashMap<>(1000) still resize when you insert 1,000 entries?
Solution

The argument is initial capacity, not expected size, and resizing is driven by capacity times the load factor.

  new HashMap<>(1000)
    -> capacity rounded up to 1024
    -> threshold = 1024 x 0.75 = 768
    -> the 769th insertion RESIZES to 2048
// To hold n entries without resizing, ask for n / 0.75:
new HashMap<>((int) (1000 / 0.75f) + 1);     // capacity 2048

// Java 19+ does the arithmetic for you:
HashMap.newHashMap(1000);

Why it matters for a map built once and read many times: each resize allocates a new table and redistributes every entry. Growing a default map to a thousand entries resizes seven times and moves roughly fifteen hundred entries in total — all avoidable with one constructor argument.

Do not adjust the load factor instead. Raising it to 1.0 avoids the resize and produces more collisions; lowering it wastes memory. 0.75 is an empirical compromise and is very rarely the right thing to tune — pre-sizing addresses the actual cost.

2 (easy): Why does this take minutes with 100,000 elements? 
while (!list.isEmpty()) {
    process(list.remove(0));
}
Solution

ArrayList.remove(0) is O(n) — removing the first element shifts every remaining element one position left, via System.arraycopy.

  100,000 removals x ~50,000 average shifts each
    = ~5,000,000,000 element moves
// FIX A — a deque, where both ends are O(1)
Deque<T> queue = new ArrayDeque<>(list);
while (!queue.isEmpty()) process(queue.poll());

// FIX B — if order permits, iterate rather than drain
for (T item : list) process(item);

// FIX C — remove from the END, which shifts nothing
for (int i = list.size() - 1; i >= 0; i--) process(list.remove(i));

ArrayDeque is a circular buffer — a head index and a tail index into an array — so adding or removing at either end moves nothing. That is why it beats LinkedList as a queue despite both being O(1): same complexity, contiguous memory, no per-element node object.

Fix B is usually the right one, because draining a list is often an unnecessary way to express iterating it. Removing as you go is only required when the list must be consumed destructively — for example when memory pressure means you need each element released as it is processed.

The mirror image is add(0, x) in a loop, which is quadratic for the same reason. Appending and reversing once at the end is linear.

3 (medium): A map keyed on this class performs like a list. Why? 
class UserId {
    private final long value;
    @Override public boolean equals(Object o) {
        return o instanceof UserId u && u.value == value;
    }
    @Override public int hashCode() { return 42; }
}
Solution

Every key hashes to the same bucket. A constant hashCode is technically legal — the contract only requires equal objects to have equal hashes, and this satisfies that trivially — but it destroys the map's entire mechanism.

  every key -> hash 42 -> spread -> the same bucket

    put:  walk the bucket, compare with equals, append
    get:  walk the bucket, compare with equals

  Every operation is O(n). The map has become a linked list with
  hashing overhead on top.

Java 8 softens it without fixing it. Once the bucket reaches eight entries it treeifies, so lookups become O(log n) rather than O(n) — but treeification needs an ordering, and UserId is not Comparable, so it falls back to comparing class names and identity hashes. Correct, and slower than a real tree.

@Override public int hashCode() { return Long.hashCode(value); }
// or, for several fields:
@Override public int hashCode() { return Objects.hash(a, b); }

4 (medium): Explain why keys 1, 17, 33 and 49 would collide without the spread, and what the spread does about it.
Solution

Integer.hashCode() returns the value itself, and the bucket index is h & (capacity - 1). With a default capacity of 16 the mask keeps only the low four bits.

   1  = 0000_0001   & 15 -> 1
  17  = 0001_0001   & 15 -> 1
  33  = 0010_0001   & 15 -> 1
  49  = 0011_0001   & 15 -> 1

  All four differ ONLY above bit 3, which the mask discards.

The spread mixes high bits down: h ^ (h >>> 16) XORs the top sixteen bits into the bottom sixteen, so differences above the mask now influence the bits the mask reads.

For these particular values it does not help much, and that is worth being honest about: the differing bits are at positions 4 and 5, which is below 16, so shifting right by 16 does not bring them into range. The spread targets hashes that differ in the upper half — which is the common case for composed hashes like Objects.hash or String.hashCode, where entropy is spread across all 32 bits.

What actually saves the sequential-integer case is resizing. As the table grows to 64, the mask widens to six bits, and 1, 17, 33, 49 separate. Sequential integer keys are in fact close to ideal for a HashMap once the table is large enough — they distribute perfectly with no collisions at all.

The keys that stay pathological are ones deliberately crafted to agree in the low bits at every capacity, which is exactly the collision-attack case that treeification exists to handle.

5 (hard): A service using a shared HashMap pins one CPU at 100% with no exception, on an old JDK. Explain, and say what changed in Java 8.
Solution

Two threads resized the map concurrently and linked a bucket into a cycle. A subsequent get() landing in that bucket walks the cycle forever.

  THE MECHANISM (Java 7 and earlier)

  Resizing rehashed each entry into the new table by inserting it at
  the HEAD of the target bucket — which REVERSES the chain.

  With two threads resizing at once, one could be part-way through
  reversing a chain while the other traversed it, leaving:

      A -> B -> A -> B -> …        a cycle

  get() then loops forever comparing keys that never match the end,
  because there is no end.
SymptomWhy it points here
One core at 100%A single thread spinning in a tight loop
No exception, nothing loggedIt is an infinite traversal, not a failure
Repeated thread dumps show the same frameHashMap.getEntry every time — spinning, not slow
Appears under load, long after deploymentRequires two concurrent resizes, which needs traffic

Java 8 changed the split so it preserves relative order. Because capacity doubles and the index is a mask, each entry either stays at i or moves to i + oldCapacity, decided by one bit — so the bucket is split into two ordered lists rather than reversed, and the cycle cannot form.

The crucial point is that this did not make HashMap thread-safe. The failure mode changed from an obvious, diagnosable hang to silent lost updates and corrupted state — a put that vanishes, a size that disagrees with the contents. That is quieter and considerably harder to attribute.

The fix is ConcurrentHashMap, and the lesson is that "it worked in testing" says nothing about a shared mutable HashMap: the bug needs concurrent resizes, which needs both load and growth at the same moment.

6 (hard): Design the map for a cache with 50,000 entries, read by 200 threads and written rarely. Justify each choice.
Solution 
ConcurrentHashMap<Key, Value> cache =
    new ConcurrentHashMap<>(
        (int) (50_000 / 0.75f) + 1,    // capacity: no resizing
        0.75f,                          // default load factor
        256);                           // concurrencyLevel hint

Value v = cache.computeIfAbsent(key, this::load);   // atomic
ChoiceReason
ConcurrentHashMapReads are lock-free, so 200 reading threads do not contend at all. synchronizedMap would serialise every read through one lock
Pre-sized to ~66,667Growing to 50,000 from the default resizes about twelve times, each redistributing every entry — and resizing under concurrent load is the most contended moment
Default load factor0.75 is an empirical compromise; the win here is pre-sizing, not tuning it
computeIfAbsentAtomic, so two threads missing the same key do not both load it. The get-check-put version races
Immutable keysA mutated key makes its own entry unreachable while still consuming memory — see Equality

The computeIfAbsent caveat matters for a cache specifically: the mapping function runs while the bin lock is held, so a slow load() blocks other writers to that bin — and it must not touch the map itself, or it can deadlock. For an expensive load, computing outside and using putIfAbsent trades a possible duplicate load for shorter lock hold.

What this design still lacks is eviction. A cache with no bound is a memory leak with a hit rate: 50,000 entries today, and nothing stops it reaching 500,000. It needs a size bound, a TTL, or both.

So the honest recommendation is Caffeine rather than a hand-built map — it provides size-based and time-based eviction, refresh-ahead, and hit-rate statistics, on top of the same concurrency properties. The hand-rolled version is right only when the key set is genuinely bounded and you do not want the dependency.

One note on the third constructor argument: concurrencyLevel is only a sizing hint in Java 8 and later — the per-bin locking scheme replaced the fixed segments it used to configure, so it no longer caps concurrent writers.

🎯 Key Takeaways

  • HashMap is an array of buckets; the hash picks the bucket and equals identifies the entry within it.
  • Capacity is a power of two so the modulo is a bitmask — one instruction, and inherently non-negative.
  • Masking reads only the low bits, so the hash is spread with h ^ (h >>> 16) to bring high-bit differences down.
  • The spread mitigates weak hashes; it cannot fix broken ones.
  • A bucket treeifies at 8 entries, turning the collision denial-of-service attack from O(n) into O(log n).
  • Below capacity 64 it resizes instead of treeifying — a small table with a long bucket is under-sized, not attacked.
  • Resize doubles the table and redistributes everything at 75% occupancy; a thousand entries costs seven resizes.
  • The constructor takes capacity, not expected size — use HashMap.newHashMap(n).
  • Pre-size rather than tuning the load factor; 0.75 is rarely worth changing.
  • Pre-Java-8 concurrent resize could form a cycle and hang get() at 100% CPU forever.
  • Java 8 removed the hang, not the thread-unsafety — now you get silent lost updates instead.
  • ArrayList grows by 1.5×, wasting at most 50% rather than 100%.
  • remove(0) and add(0, x) are O(n), so either in a loop is quadratic — use ArrayDeque.
  • ConcurrentHashMap reads are lock-free; writes lock one bin, so writers to different buckets never contend.
  • Its size() is approximate and iteration is weakly consistent, and atomicity is per operation — containsKey then put still races.
  • It forbids null keys and values, because an ambiguous get could not be resolved by a follow-up call.
