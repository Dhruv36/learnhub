Lambdas & Functional Interfaces Core Libraries

What you'll master: what a lambda actually compiles to — not an anonymous class, but an invokedynamic call site linked at first execution, which is why thousands of lambdas add no class files and why this means something different in each; the effectively final rule and the reason behind it — locals live on the stack and lambdas outlive the frame, so Java captures by value and requires the variable not to change; why that rule does not protect you from mutating a captured object, which is the loophole people use and then regret; the four core functional interfaces and their primitive variants, which exist to avoid boxing an object per element; method references and the four forms, including the one that looks ambiguous and is not; and why a lambda stored in a listener list keeps its enclosing object alive. Prerequisites: Interfaces for functional interfaces.

Part 1 — A Lambda Is an Implementation of an Interface

  A lambda is not a new kind of value. It is a compact way to
  implement a FUNCTIONAL INTERFACE — one with exactly one abstract
  method.

    Runnable r = () -> System.out.println("hi");
    Comparator<String> byLength = (a, b) -> a.length() - b.length();
    Predicate<String> notBlank = s -> !s.isBlank();

  THE TARGET TYPE DETERMINES WHAT THE LAMBDA IS. The same source text
  can implement different interfaces:

    Runnable  r = () -> doWork();      // no arguments, returns void
    Callable<Void> c = () -> { doWork(); return null; };

  So a lambda has no type of its own — it takes the type of the
  context it appears in, which is why you cannot write
  `var f = () -> 1;` (there is nothing to infer the target from).

  SYNTAX, from most to least explicit:

    (String s) -> { return s.length(); }    full
    (s) -> { return s.length(); }           types inferred
    s -> s.length()                          one parameter, one
                                             expression — the common
                                             form
    () -> 42                                 no parameters
    (a, b) -> a + b                          two parameters

Part 2 — Effectively Final

  A lambda may only capture a local variable that is EFFECTIVELY FINAL
  — assigned once and never reassigned.

    int count = 0;
    list.forEach(x -> count++);      // ❌ does not compile

    int total = list.size();          // assigned once
    list.forEach(x -> print(total));  // ✓ effectively final

  WHY: a local lives in the method's STACK FRAME, which disappears
  when the method returns. A lambda can outlive that — stored in a
  field, submitted to an executor, registered as a listener. So Java
  CAPTURES BY VALUE: the value is copied into the lambda at creation.

  If the variable could still change afterwards, the copy and the
  original would diverge, and there would be no sensible answer to
  which one the lambda should see. Requiring it not to change removes
  the question.

  (Inner classes have had this rule since Java 1.1, where it was
  spelled `final`; Java 8 relaxed the keyword, not the rule.)

  THE LOOPHOLE — AND WHY IT IS A TRAP

  The REFERENCE must be effectively final. The OBJECT it points at
  may still be mutated:

    int[] counter = {0};                    // the array ref never
    list.forEach(x -> counter[0]++);        // changes; contents do
    // counter[0] is now list.size()

    AtomicInteger count = new AtomicInteger();
    list.forEach(x -> count.incrementAndGet());

  Both compile. Both work single-threaded. Neither is a good idea in
  a STREAM, because a parallel stream will race on that shared
  mutable state — and the compiler cannot warn you, since the rule it
  enforces was never about mutation.

  The functional answer is not to accumulate into a captured variable
  at all:

    long count = list.stream().filter(...).count();
    int sum    = list.stream().mapToInt(X::value).sum();

Part 3 — The Core Functional Interfaces

InterfaceShapeMethodUsed by
Function<T,R>T → Rapplymap, computeIfAbsent
Predicate<T>T → booleantestfilter, removeIf
Consumer<T>T → voidacceptforEach, ifPresent
Supplier<T>() → TgetorElseGet, lazy defaults
UnaryOperator<T>T → TapplyreplaceAll
BiFunction<T,U,R>(T,U) → Rapplymerge, compute
BinaryOperator<T>(T,T) → Tapplyreduce, Collectors.toMap
  THEY COMPOSE, WHICH IS THE POINT

    Function<String,String> trim  = String::trim;
    Function<String,String> upper = String::toUpperCase;

    trim.andThen(upper)     // trim FIRST, then upper
    trim.compose(upper)     // upper first, then trim

    Predicate<String> notBlank = s -> !s.isBlank();
    Predicate<String> shortish = s -> s.length() < 20;

    notBlank.and(shortish)
    notBlank.or(shortish)
    notBlank.negate()
    Predicate.not(String::isBlank)      // static, reads better

  THE PRIMITIVE VARIANTS EXIST TO AVOID BOXING

    IntPredicate, IntFunction, IntUnaryOperator,
    ToIntFunction<T>, IntSupplier, IntConsumer   (and Long, Double)

    Function<Integer,Integer>    boxes on input AND output
    IntUnaryOperator             no boxing at all

  Over a million elements that is a million Integer allocations
  versus none — the difference between a warm cache and constant GC
  pressure. It is the same reason IntStream exists alongside
  Stream<Integer>.

Part 4 — Method References

  Four forms, and they cover most lambdas that just call one thing.

  1. STATIC METHOD
       Integer::parseInt              s -> Integer.parseInt(s)

  2. INSTANCE METHOD OF A PARTICULAR OBJECT
       System.out::println            x -> System.out.println(x)
       this::handle                   x -> this.handle(x)

  3. INSTANCE METHOD OF AN ARBITRARY OBJECT OF THE TYPE
       String::toUpperCase            s -> s.toUpperCase()
       // the RECEIVER becomes the first argument

  4. CONSTRUCTOR
       ArrayList::new                 () -> new ArrayList<>()
       User::new                      name -> new User(name)

  FORMS 2 AND 3 LOOK IDENTICAL AND ARE NOT:

    String::toUpperCase       arbitrary object — s -> s.toUpperCase()
    myString::toUpperCase     THIS object     — () -> myString.toUpperCase()

  The compiler distinguishes them by whether the left side is a TYPE
  or an EXPRESSION. It resolves the ambiguity from the target type,
  which is why an error here often reads as an unrelated inference
  failure.

  WHEN NOT TO USE ONE: when the lambda does anything more than call
  the method, and when the method reference is less readable than the
  lambda. `x -> x.getName()` and `X::getName` are equivalent; pick
  whichever the surrounding code makes clearer.

  ONE REAL SHARP EDGE:

    list.forEach(System.out::println);      // evaluates System.out
                                            // ONCE, at creation

  Form 2 captures the receiver eagerly. If System.out is
  later replaced, the reference still holds the old one — which
  matters when tests redirect it.

Part 5 — What a Lambda Compiles To

  NOT AN ANONYMOUS CLASS.

    Runnable anon = new Runnable() {      // -> Outer$1.class, a real
        public void run() { … }           //    class file, loaded
    };                                    //    normally

    Runnable lambda = () -> { … };        // -> an invokedynamic
                                          //    instruction; NO extra
                                          //    class file

  At first execution the JVM calls LambdaMetafactory, which spins an
  implementation and links the call site. Subsequent executions go
  straight to it.

  WHY IT WAS DONE THIS WAY: a codebase with ten thousand lambdas
  would otherwise ship ten thousand class files, which costs jar size
  and — more importantly — class-loading time at startup. The
  indirection also leaves room for the JVM to change the strategy
  later without recompiling anything.

  THE OBSERVABLE DIFFERENCES:

                        anonymous class        lambda
    class file          yes, one each          none
    `this`              the anonymous          the ENCLOSING
                        instance               instance
    shadowing a local   allowed (new scope)    compile error (same
                                               scope)
    self-reference      possible               impossible

  THE `this` DIFFERENCE IS THE ONE THAT BITES:

    class Handler {
        void register(Bus bus) {
            bus.on(new Runnable() {
                public void run() { this.cleanup(); }   // the RUNNABLE
            });
            bus.on(() -> this.cleanup());               // the HANDLER
        }
    }

  AND IT IS WHY LAMBDAS LEAK EXACTLY AS INNER CLASSES DO. A lambda
  that touches any instance state captures `this`, so a lambda stored
  in a long-lived listener list pins its enclosing object — the
  this$0 leak from Enums & Nested Classes, in a different syntax.

    bus.on(() -> this.repaint());     // captures the whole Screen
    int w = width;                     // capture only what you need
    bus.on(() -> resizeTo(w));         // still captures `this`
                                       // if resizeTo is an instance
                                       // method!

  Only a lambda that touches NO instance state avoids capturing.

Part 6 — Exceptions, and When Not to Use a Lambda

  CHECKED EXCEPTIONS DO NOT FIT THE FUNCTIONAL INTERFACES.

    list.forEach(f -> Files.delete(f));    // ❌ IOException is checked
                                           //    and Consumer.accept
                                           //    does not declare it

  None of Function, Predicate, Consumer or Supplier declares a checked
  exception, so any lambda that performs IO must handle it inline:

    list.forEach(f -> {
        try { Files.delete(f); }
        catch (IOException e) { throw new UncheckedIOException(e); }
    });

  which is verbose and loses the checked-ness. The alternatives:

    a plain for loop            handles checked exceptions naturally,
                                and is often clearer for IO
    a custom interface          ThrowingConsumer<T, E extends
                                Exception> — works, and does not
                                compose with the standard API
    a wrapper helper            unchecked(f -> …) — hides the
                                exception type from the signature

  MY DEFAULT: if a loop body does IO and must handle failures per
  element, write the loop. Streams and lambdas are for
  transformations, and error handling is where they are weakest.

  THE OTHER TIMES A LAMBDA IS THE WRONG CHOICE:

    it is longer than about three lines   -> extract a named method,
                                             then reference it
    it needs a name to be understood      -> a method reference IS the
                                             name
    it needs to refer to itself           -> recursion needs a field
                                             or an anonymous class
    the stack trace matters               -> lambdas appear as
                                             lambda$method$0, which is
                                             harder to read in a
                                             production trace

Interview Questions

Beginner: What is a lambda, and what is a functional interface?

A lambda is a compact way to implement an interface that has exactly one abstract method — a functional interface. It is not a new kind of value: at the point of use it becomes an instance of whatever interface the context expects.

That is why the same text can mean different things. () -> doWork() is a Runnable in one position and a Callable in another; the target type decides. It is also why var f = () -> 1; does not compile — there is no target to infer from.

Default and static methods do not count towards the single-abstract-method rule, which is how Comparator can carry a dozen helpers and still accept a lambda.

@FunctionalInterface is optional but worth adding: it makes the compiler enforce the rule, so someone adding a second abstract method gets an error at the interface rather than breaking every lambda that implemented it.

Beginner: What does "effectively final" mean, and why is it required?

A captured local must be assigned once and never reassigned — final in behaviour, whether or not the keyword is present.

The reason is lifetime. A local variable lives in the method's stack frame, which is destroyed when the method returns. A lambda can outlive that — stored in a field, submitted to an executor, registered as a callback. So Java captures by value: the value is copied into the lambda when it is created.

If the variable could still be reassigned afterwards, the copy and the original would diverge, and there would be no defensible answer to which one the lambda should see. Requiring it not to change makes the question disappear.

The rule is not new — inner classes required final since Java 1.1. Java 8 relaxed the keyword, not the constraint.

And the important caveat: only the reference must be effectively final. The object it points at can still be mutated, which is the loophole people use with a one-element array or an AtomicInteger — and which the compiler cannot warn about, because the rule was never about mutation.

Mid: How does a lambda differ from an anonymous class?

Three observable differences, and one of them causes real bugs.

Compilation. An anonymous class produces a class file — Outer$1.class — loaded like any other. A lambda compiles to an invokedynamic instruction that the JVM links, via LambdaMetafactory, on first execution. So ten thousand lambdas add no class files, which matters for jar size and class-loading time at startup.

this. Inside an anonymous class, this is the anonymous instance. Inside a lambda it is the enclosing instance. That means a lambda cannot refer to itself, so a self-referential callback needs an anonymous class or a field.

Scope. An anonymous class body is a new scope and may shadow a local; a lambda shares the enclosing scope, so redeclaring a name is a compile error.

What is the same is capture, and this is the part people get wrong: both capture only effectively-final locals, and both capture the enclosing this when they touch instance state. A lambda stored in a listener list pins its enclosing object exactly as an inner class does — lambdas do not avoid that leak.

Mid: Why do the primitive functional interfaces exist?

To avoid boxing. Function<Integer, Integer> takes and returns objects, so every application allocates an Integer on the way in and another on the way out — or hits the cache for small values, which only postpones the problem.

IntUnaryOperator takes an int and returns an int, with no allocation at all.

Over a million elements that is the difference between a million short-lived objects and none. The allocation itself is cheap; the cost is GC pressure and the loss of cache locality, which affects everything else running in the JVM at the time.

The full set follows a naming pattern worth recognising: IntPredicate, IntConsumer, IntSupplier, IntFunction<R> (int in, object out), and ToIntFunction<T> (object in, int out), with Long and Double equivalents.

It is the same reasoning as IntStream versus Stream<Integer>, and the same reason the JDK's own numeric code is full of these variants — it is a workaround for erasure not permitting primitive type arguments, which Valhalla may eventually remove.

Senior: Why is mutating a captured object a bad idea even though it compiles?

Because the compiler's rule is about the reference, not the object — so the check that stopped you reassigning a counter does nothing about mutating one.

int[] counter = {0};
list.forEach(x -> counter[0]++);        // compiles, works serially

Single-threaded and sequential, that is correct. It becomes wrong in two ways as soon as the context changes.

A parallel stream races on it. Multiple threads increment the same slot with no synchronisation, so updates are lost. Replacing it with an AtomicInteger fixes the race and leaves the deeper problem: the pipeline is now stateful, so its result depends on how the stream happens to be split and ordered.

It defeats the abstraction. Stream operations are specified as non-interfering and stateless precisely so the runtime is free to reorder, parallelise, short-circuit or skip them. Code that accumulates into captured state assumes an execution model the API does not promise.

The fix is nearly always to let the pipeline produce the value rather than to accumulate into a variable: count(), sum(), reduce, or a Collector. If the result genuinely cannot be expressed that way, that is a strong signal the operation is imperative and should be a for loop, where mutation is honest and the reader expects it.

Senior: When would you not use a lambda?

Four situations, and the first two come up constantly.

When it does IO or anything with checked exceptions. None of the standard functional interfaces declares a checked exception, so the lambda must catch and wrap inline — which is verbose, loses the exception type from the signature, and buries error handling inside a pipeline. A plain for loop handles it naturally, and I would write the loop.

When it is more than about three lines. A long lambda is unreadable at the call site, cannot be tested on its own, and appears in stack traces as lambda$process$0. Extracting it to a named method and passing a method reference fixes all three, and the name documents the intent.

When it needs to refer to itself. this in a lambda is the enclosing instance, so recursion needs a field or an anonymous class.

When the stack trace matters. Deeply chained lambdas produce traces that are genuinely hard to read, which is a real cost in production diagnosis and worth weighing against the concision.

The underlying judgement is that lambdas are for transformations — expressing what to compute. Where the code is fundamentally about sequencing side effects and handling failure per step, an imperative loop is not a step backwards; it is the honest shape.

🏋️ Graded Exercises

1 (easy): Why does this not compile, and what are two correct versions? 
int count = 0;
names.forEach(n -> { if (n.isBlank()) count++; });
Solution

count is not effectively final — the lambda reassigns it, so capture by value would leave the copy and the original disagreeing.

// ✓ let the pipeline produce the value
long count = names.stream().filter(String::isBlank).count();

// ✓ or an ordinary loop, where mutation is expected
int count = 0;
for (String n : names) if (n.isBlank()) count++;

The version to avoid, even though it compiles:

int[] count = {0};
names.forEach(n -> { if (n.isBlank()) count[0]++; });   // ❌

The array reference never changes, so the compiler is satisfied — but this races the moment the stream is parallel, and it makes the pipeline stateful in a way the Streams API explicitly does not guarantee to support.

Which of the two correct versions to prefer depends on what follows. If you need only the count, the stream states it directly. If the loop body grows to do several things, the for loop stays readable while a stream would not.

2 (easy): Rewrite each as a method reference, and name the form. 
s -> Integer.parseInt(s)
x -> System.out.println(x)
s -> s.toUpperCase()
() -> new ArrayList<String>()
Solution 
Integer::parseInt        form 1 — STATIC method
System.out::println      form 2 — instance method of a PARTICULAR object
String::toUpperCase      form 3 — instance method of an ARBITRARY object
ArrayList::new           form 4 — CONSTRUCTOR

Forms 2 and 3 look identical and differ in what is on the left. System.out is an expression, so the receiver is fixed. String is a type, so the receiver becomes the first argument — String::toUpperCase means s -> s.toUpperCase().

WrittenMeans
String::toUpperCases -> s.toUpperCase() — receiver supplied per call
myString::toUpperCase() -> myString.toUpperCase() — receiver fixed now

The sharp edge in form 2 is that the receiver is captured eagerly. list.forEach(System.out::println) resolves System.out once, when the reference is created — so if a test later replaces System.out, the reference still holds the original stream.

Use a method reference when the lambda does nothing but call the method. x -> x.getName() and X::getName are equivalent; anything more than a single call should stay a lambda or become a named method.

3 (medium): What does each print, and why do they differ? 
class Handler {
    String name = "handler";

    void run() {
        Runnable anon = new Runnable() {
            String name = "anon";
            public void run() { System.out.println(this.name); }
        };
        Runnable lambda = () -> System.out.println(this.name);
        anon.run();
        lambda.run();
    }
}
Solution 
anon.run()     -> "anon"      this = the anonymous instance
lambda.run()   -> "handler"   this = the ENCLOSING Handler

An anonymous class introduces a new this; a lambda does not. A lambda has no identity of its own to refer to, so this inside it resolves lexically, exactly as it would in the surrounding method.

The practical consequence is that a lambda cannot reference itself, which rules out recursive lambdas and any callback that needs to unregister itself:

// ❌ impossible as a lambda
bus.on(() -> { handle(); bus.off(/* this? */); });

// ✓ needs an anonymous class, or a field
Runnable r = new Runnable() {
    public void run() { handle(); bus.off(this); }
};

And the leak consequence. Because the lambda's this is the Handler, any lambda touching instance state captures the Handler. Stored in a long-lived listener list, it keeps the whole object alive — the same this$0 leak as a non-static inner class, in different syntax.

Only a lambda that touches no instance state avoids capturing, which includes calling an instance method. Copying the field into a local first is what actually breaks the reference.

4 (medium): This does not compile. Give three approaches and say which you would ship. 
paths.forEach(p -> Files.delete(p));
Solution

Files.delete throws IOException, which is checked, and Consumer.accept does not declare it. None of the standard functional interfaces does.

ApproachCost
A plain loopNone — and it can handle each failure individually
try/catch inside the lambda, wrapping in UncheckedIOExceptionVerbose, and the checked-ness is lost from the signature
A custom ThrowingConsumerWorks, and does not compose with the standard API — every caller needs the adapter
// WHAT I WOULD SHIP
for (Path p : paths) {
    try {
        Files.delete(p);
    } catch (IOException e) {
        log.warn("could not delete {}", p, e);     // per-element
    }                                              // handling
}

The loop is not a concession — it is the better shape here. Deleting files is a sequence of side effects where each can fail independently, and the interesting question is what to do about a failure: skip, retry, abort, collect. A loop expresses all of those naturally; a lambda expresses none of them without ceremony.

The wrapping version is defensible when failure genuinely should abort everything, and UncheckedIOException exists precisely for that bridge. But note it converts the first failure into an abort, which is a policy decision being made by the syntax rather than by the author.

The general rule: streams and lambdas are for transformations. Where the code is about sequencing effects and handling failure per step, a loop is the honest form.

5 (hard): A profiler shows heavy allocation in this pipeline. Fix it and explain the mechanism. 
Function<Integer, Integer> square = n -> n * n;
long total = 0;
for (int i = 0; i < 10_000_000; i++) {
    total += square.apply(i);
}
Solution

Function<Integer, Integer> boxes twice per call. The int is autoboxed to Integer on the way in; the result is boxed on the way out; and total += unboxes it again.

  10,000,000 iterations
    x 2 boxing operations
    = up to 20,000,000 Integer allocations

  (The cache covers -128..127 only, so beyond the first 128
   iterations every one allocates.)
IntUnaryOperator square = n -> n * n;      // int in, int out
long total = 0;
for (int i = 0; i < 10_000_000; i++) {
    total += square.applyAsInt(i);          // NO allocation
}
ShapeInterface
int → intIntUnaryOperator
int → booleanIntPredicate
T → intToIntFunction<T>
int → TIntFunction<T>

The allocation itself is cheap — a bump-pointer in the young generation. The cost is the consequences: twenty million short-lived objects mean frequent young collections, and the cache-line churn slows down everything else running in the JVM, not just this loop.

The stream equivalent has the same distinction: IntStream.range(0, n).map(i -> i * i).sum() allocates nothing, while Stream.iterate over Integer boxes every element.

The honest caveat: escape analysis can sometimes eliminate the boxing when the JIT proves the object does not escape, so the effect is not always as large as the arithmetic suggests. Measure rather than assume — but reaching for the primitive variant costs nothing and removes the question.

6 (hard): A dashboard leaks memory. Listeners are registered as lambdas. Explain and fix. 
class Chart {
    private final double[] data = new double[5_000_000];
    private int refreshCount;

    void attach(EventBus bus) {
        bus.onTick(() -> { refreshCount++; redraw(); });
    }
}
Solution

The lambda touches instance state, so it captures this — the whole Chart, including its forty-megabyte array.

  RETENTION PATH

    EventBus -> lambda -> captured Chart -> double[5000000]

  The bus outlives the chart, so every chart ever attached stays
  reachable. People assume lambdas avoid the inner-class leak; they
  do not.

Both refreshCount++ and redraw() capture it. A field access obviously does, and an unqualified instance method call is this.redraw() — so the second one captures just as surely as the first, which is the part that is easy to miss.

FixEffect
Unregister deterministicallyThe real fix for lifecycle — keep the subscription and cancel it when the chart closes
Capture only what is neededRemoves the reference to the large object, if the lambda can be expressed without instance state
A static nested class holding a narrow referenceExplicit about what is retained
Weak references in the busHelps, and makes delivery non-deterministic — a listener can vanish mid-use
class Chart implements AutoCloseable {
    private Subscription subscription;

    void attach(EventBus bus) {
        subscription = bus.onTick(this::onTick);   // still captures
    }                                              // this — but now
                                                   // it is cancellable
    @Override public void close() {
        if (subscription != null) subscription.cancel();
    }
}

Unregistering is the fix that matters, and capturing less is a mitigation. Even a lambda capturing nothing leaks the listener itself if it is never removed — the difference is whether you leak forty megabytes or forty bytes per chart.

Returning a Subscription rather than a bare register method is the API change that makes correct use possible. A bus with no way to unsubscribe forces every consumer to leak, and that is a design flaw in the bus rather than in the caller.

🎯 Key Takeaways

  • A lambda implements a functional interface — it has no type of its own and takes the target type from its context.
  • Captured locals must be effectively final, because capture is by value and the lambda outlives the stack frame.
  • The rule constrains the reference, not the object — mutating a captured array or AtomicInteger compiles and races in parallel.
  • Let the pipeline produce the value rather than accumulating into captured state.
  • A lambda is invokedynamic, not an anonymous class — no class file per lambda.
  • this in a lambda is the enclosing instance, so it cannot refer to itself.
  • Lambdas leak exactly as inner classes do — touching any instance state, including calling an instance method, captures this.
  • The four core shapes are Function, Predicate, Consumer, Supplier, and they compose.
  • Primitive variants exist to avoid boxing — millions of allocations in a hot loop.
  • Method references have four forms, and the arbitrary-object form turns the receiver into the first argument.
  • obj::method captures the receiver eagerly, at creation.
  • Checked exceptions do not fit the standard interfaces — write the loop.
  • Extract anything longer than a few lines; a method reference gives it a name and a readable stack frame.
  • No side effects in map or filter — the runtime is free to reorder, parallelise or skip them.
  • Lambdas are for transformations; sequencing effects with per-step failure handling is a loop's job.
