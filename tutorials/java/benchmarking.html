Benchmarking & JMH JVM & Performance

What you'll master: the five distinct ways a hand-written timing loop produces a number that means nothing — warmup, dead-code elimination, constant folding, loop unrolling and on-stack replacement — and why the last two make a "10× faster" result common and completely false; why nanoTime is monotonic and currentTimeMillis is not, and when that matters; JMH's model (separate process, forks, warmup and measurement iterations) and what each annotation is defending against; Blackhole and @State as the concrete defences; how to read the error bar and why a 3% difference is usually noise; the environment problems that silently invalidate a run; and when a microbenchmark is the wrong tool entirely. Prerequisites: JVM Architecture and Performance & Profiling.

Part 1 — Why Your Timing Loop Is Wrong

  EVERYONE WRITES THIS ONCE:

    long start = System.currentTimeMillis();
    for (int i = 0; i < 1_000_000; i++) {
        result = compute(i);
    }
    long end = System.currentTimeMillis();
    System.out.println((end - start) + " ms");

  IT IS WRONG IN AT LEAST FIVE INDEPENDENT WAYS, AND THE ERRORS DO
  NOT CANCEL.

  1. NO WARMUP.
     The first ~1,500 invocations run INTERPRETED, roughly 20-50×
     slower than compiled code. C1 compiles next, C2 later still.
     If your loop finishes before C2 gets there, you measured the
     interpreter. If it does not, you measured a MIXTURE of three
     execution modes in unknown proportion.

  2. DEAD CODE ELIMINATION.
     If nothing observes `result`, the JIT may delete the call
     entirely. The classic outcome is a benchmark reporting ~0.3 ns
     per operation — which is less than one CPU cycle for anything
     real. That number means "it did not run".

  3. CONSTANT FOLDING.
     If the input is a compile-time constant or a final field, the
     JIT computes the answer ONCE at compile time and the loop
     measures nothing.

       static final int N = 42;
       compute(N);            // may become a literal

  4. LOOP UNROLLING AND HOISTING.
     A loop whose body does not depend on the index can be hoisted
     out entirely — one execution instead of a million. Unrolling
     also changes the per-iteration cost in ways that do not
     transfer to real call sites.

  5. ON-STACK REPLACEMENT (OSR).
     A long-running loop gets compiled WHILE STILL EXECUTING, and
     OSR-compiled code is often optimised differently (and worse)
     than a normally compiled method. So you measure code shaped by
     the benchmark's own structure.

  PLUS THE NOISE YOU DID NOT CONTROL: a GC pause inside the timed
  region, CPU frequency scaling, another process on the machine,
  and the OS scheduler moving your thread between cores.

  THE RESULT IS NOT "SLIGHTLY OFF". Hand-rolled microbenchmarks
  routinely report differences of 10× in the WRONG DIRECTION. That
  is why JMH exists: not to make benchmarking convenient, but to
  make it not-wrong.

  currentTimeMillis VS nanoTime:

    currentTimeMillis   WALL CLOCK. Can jump backwards (NTP), and
                        has ~1-15 ms granularity on some platforms.
                        Use for timestamps, never for durations.
    nanoTime            MONOTONIC, high resolution. Meaningless as
                        an absolute value — only differences within
                        one JVM are valid.

  Measuring a duration with currentTimeMillis can literally produce
  a negative result when the clock is adjusted mid-measurement.

Part 2 — The JMH Model

  JMH IS AN ANNOTATION-DRIVEN HARNESS THAT GENERATES BENCHMARK CODE
  AT BUILD TIME AND RUNS IT IN A SEPARATE, CONTROLLED PROCESS.

  SET IT UP AS ITS OWN MODULE. This is not fussiness:

    - JMH needs an annotation processor to generate its harness
    - benchmark code must not ship in your application jar
    - the JVM flags a benchmark needs differ from production's

    <dependency>
      <groupId>org.openjdk.jmh</groupId>
      <artifactId>jmh-core</artifactId>
      <version>1.37</version>
    </dependency>
    <!-- plus jmh-generator-annprocess, provided scope -->

  A COMPLETE BENCHMARK:

    @BenchmarkMode(Mode.AverageTime)
    @OutputTimeUnit(TimeUnit.NANOSECONDS)
    @Warmup(iterations = 5, time = 1)
    @Measurement(iterations = 10, time = 1)
    @Fork(3)
    @State(Scope.Benchmark)
    public class StringConcatBenchmark {

        @Param({"10", "100", "1000"})
        private int size;

        private List<String> items;

        @Setup(Level.Trial)
        public void setup() {
            items = IntStream.range(0, size)
                    .mapToObj(i -> "item" + i).toList();
        }

        @Benchmark
        public String stringBuilder() {
            var sb = new StringBuilder();
            for (String s : items) sb.append(s);
            return sb.toString();          // RETURNED — not dead
        }

        @Benchmark
        public String joining() {
            return String.join("", items);
        }
    }

  WHAT EACH PIECE DEFENDS AGAINST:

    @Warmup       the interpreter and C1 — discard those iterations
    @Measurement  gives enough samples for a meaningful error bar
    @Fork(3)      THE ONE PEOPLE SKIP. Each fork is a FRESH JVM.
                  Without it, running benchmark A then B lets A's
                  profile pollute B's — the JIT specialises call
                  sites based on what it saw first, so ORDER
                  CHANGES RESULTS. Multiple forks also expose
                  run-to-run variance you would otherwise call a
                  real difference.
    @State        holds inputs outside the benchmark method so they
                  cannot be constant-folded
    @Param        runs the whole matrix across input sizes, which
                  is how you find the crossover point
    return        the result is consumed, defeating dead-code
                  elimination

  RUNNING IT:

    mvn clean package
    java -jar target/benchmarks.jar StringConcat -prof gc
AnnotationDefends againstTypical value
@WarmupInterpreted and C1 code5 iterations × 1 s
@MeasurementToo few samples for statistics10 iterations × 1 s
@ForkProfile pollution and run-to-run variance3 (never 0)
@StateConstant folding of inputsScope.Benchmark or Thread
@Setup/@TearDownSetup cost leaking into the measurementLevel.Trial or Invocation
@ParamA single input size hiding the crossoverA range spanning realistic sizes

@BenchmarkModeMeasuring the wrong thingAverageTime or Throughput
@CompilerControlUnwanted inlining of the method under testRarely — only with a reason

Part 3 — Defeating the Optimiser

  DEAD CODE ELIMINATION — the failure that produces impossible
  numbers.

    @Benchmark
    public void bad() {
        Math.log(42);              // ❌ result unused → deleted
    }
    // reports ~0.3 ns/op — less than a cycle. It did not run.

    @Benchmark
    public double good() {
        return Math.log(input);    // ✓ returned; JMH consumes it
    }

  JMH consumes returned values through a Blackhole. For MULTIPLE
  results, take one as a parameter:

    @Benchmark
    public void multiple(Blackhole bh) {
        bh.consume(compute(a));
        bh.consume(compute(b));
    }

  Blackhole is not free (roughly a nanosecond), which matters when
  the operation itself costs a nanosecond — another reason to be
  suspicious of sub-nanosecond results.

  CONSTANT FOLDING — the subtler failure.

    @Benchmark
    public double bad() {
        return Math.log(42);       // ❌ folded at compile time
    }

    @State(Scope.Benchmark)
    public static class Input {
        public double value = 42;  // NOT final, NOT a literal
    }
    @Benchmark
    public double good(Input in) {
        return Math.log(in.value); // ✓ opaque to the compiler
    }

  THE RULES: inputs live in a @State object, are not final, and are
  ideally set in @Setup so the compiler cannot see the value.

  LOOP OPTIMISATIONS — do not write the loop yourself.

    @Benchmark
    public int bad() {
        int sum = 0;
        for (int i = 0; i < 1000; i++) sum += compute(i);
        return sum;                // unrolled, maybe vectorised —
    }                              // you measured the LOOP, not
                                   // compute()

  Benchmark ONE operation and let JMH do the repetition. If the loop
  IS the thing under test, use @OperationsPerInvocation so the
  reported number is per element rather than per loop.

  THE MODES, AND WHEN EACH IS RIGHT:

    Throughput     ops/sec — best for comparing implementations
    AverageTime    time/op — best for small operations
    SampleTime     a DISTRIBUTION with percentiles — the only mode
                   that shows p99, and the right one when tail
                   latency matters
    SingleShotTime one invocation, no warmup — for measuring COLD
                   performance, e.g. startup or first-call cost
    All            all of the above

  Most people default to AverageTime and never learn SampleTime,
  which is the one that answers "is this occasionally very slow?"

Part 4 — Reading the Output

  Benchmark              (size)  Mode  Cnt   Score    Error  Units
  Bench.stringBuilder        10  avgt   30  45.231 ±  0.892  ns/op
  Bench.joining              10  avgt   30  52.104 ±  1.203  ns/op
  Bench.stringBuilder      1000  avgt   30  4231.5 ± 88.31  ns/op
  Bench.joining            1000  avgt   30  4102.7 ± 201.4  ns/op

  THE ERROR COLUMN IS THE MOST IMPORTANT ONE AND THE MOST IGNORED.
  It is a 99.9% confidence interval half-width.

    TWO RESULTS DIFFER MEANINGFULLY ONLY IF THEIR INTERVALS DO NOT
    OVERLAP.

    size 10:    45.231 ± 0.892  →  [44.34, 46.12]
                52.104 ± 1.203  →  [50.90, 53.31]
                DISJOINT → a real difference (~15%)

    size 1000:  4231.5 ± 88.3   →  [4143, 4320]
                4102.7 ± 201.4  →  [3901, 4304]
                OVERLAP → NOT a real difference

  So the honest reading of this table is: StringBuilder wins for
  small inputs, and at 1000 elements THERE IS NO MEASURED
  DIFFERENCE — not "joining is 3% faster".

  A GOOD RULE: ignore anything under about 5% unless the error bars
  are very tight and you have repeated the run.

  A LARGE ERROR IS ITSELF A FINDING. If the error is 20% of the
  score, something is unstable — GC during measurement, a noisy
  machine, frequency scaling, or a benchmark that is measuring
  different code on different iterations. Fix that before believing
  any score.

  PROFILERS ATTACHED TO A RUN:

    -prof gc         allocation rate and normalised bytes/op — often
                     MORE INFORMATIVE THAN THE TIME. "gc.alloc.rate.norm"
                     of 0 proves an allocation was eliminated.
    -prof perfasm    the generated assembly for the hottest region
                     (Linux). The ground truth when you need it.
    -prof perfnorm   CPU counters: cycles, instructions, cache
                     misses, branch mispredictions per op
    -prof stack      a sampling profile of the benchmark itself

  gc.alloc.rate.norm IS THE ONE TO LEARN FIRST. It reports bytes
  allocated per operation, deterministically, and it answers
  questions the time column cannot: did escape analysis remove that
  allocation? does this version box?

Part 5 — The Environment Will Betray You

  A PERFECT BENCHMARK ON A BAD MACHINE PRODUCES BAD NUMBERS.

  CPU FREQUENCY SCALING AND TURBO.
    A modern CPU boosts a single active core well above base clock,
    then drops as it heats or as other cores wake. Run the same
    benchmark for 30 seconds and the last iterations can be 20-30%
    slower than the first — with no code change involved.

      cpupower frequency-set -g performance    # Linux
      and disable turbo for stability, not for realism

  OTHER LOAD ON THE MACHINE.
    An IDE indexing, a browser, a container neighbour. Close what
    you can, and never benchmark on a laptop on battery — power
    management alone can halve clock speed.

  CONTAINERS AND CPU QUOTA.
    A CFS quota of 0.5 CPU does not slow you smoothly; it runs you
    at full speed and then STOPS you for the rest of the period.
    That produces multi-millisecond stalls inside a measurement
    window and enormous error bars.

  MEMORY AND NUMA.
    On a multi-socket machine, memory allocated on one node and read
    from another costs noticeably more. Pin with taskset/numactl
    when it matters.

  THE JVM ITSELF.
    Fix the heap (-Xms == -Xmx) so heap resizing does not appear as
    variance, and state the collector explicitly. Benchmarking with
    different collectors on different runs is a common accidental
    comparison.

  A REASONABLE BASELINE COMMAND:

    java -jar benchmarks.jar \
      -f 3 -wi 5 -i 10 \
      -jvmArgs "-Xms2g -Xmx2g -XX:+UseG1GC" \
      -prof gc

  AND THE CHECK THAT COSTS NOTHING: RUN IT TWICE. If two full runs
  disagree by more than the error bars, the environment is not
  stable and no conclusion is safe yet.

  CONCURRENCY BENCHMARKS ARE HARDER STILL:

    @Threads(4)              run the benchmark on N threads
    @Group / @GroupThreads   asymmetric roles (producer/consumer)
    @State(Scope.Thread)     per-thread state, no false sharing
                             between benchmark threads

  And they suffer COORDINATED OMISSION exactly as load tests do: if
  a thread stalls, it simply sends fewer operations, so the stall is
  under-represented in the results. SampleTime mode with percentiles
  is the mitigation.

Part 6 — When a Microbenchmark Is the Wrong Tool

  A MICROBENCHMARK MEASURES ONE OPERATION IN ISOLATION, WARM, WITH
  A HOT CACHE, NO CONTENTION AND NO GC PRESSURE. REAL SYSTEMS HAVE
  NONE OF THOSE PROPERTIES.

  WHAT IT LEGITIMATELY ANSWERS:

    - is implementation A faster than B for this exact operation?
    - does this change allocate less? (-prof gc)
    - where is the crossover between two algorithms? (@Param)
    - what does this library call actually cost?

  WHAT IT CANNOT ANSWER, AND IS ROUTINELY MISUSED FOR:

    - will my SERVICE get faster?
    - what is my p99 under load?
    - does this scale to 1,000 concurrent users?
    - is the cache hit rate good in production?
    - is this change worth making?

  THE WAYS A "FASTER" RESULT FAILS TO TRANSFER:

    CACHE EFFECTS      the benchmark's working set fits in L2; the
                       real one does not, and memory latency
                       dominates
    CONTENTION         the benchmark is single-threaded; production
                       has 200 threads on the same structure
    INLINING CONTEXT   a monomorphic call site in the benchmark is
                       megamorphic in production, so it does not
                       inline
    AMDAHL             a 2× win on 3% of runtime is 1.5% overall
    GC INTERACTION     lower per-op time with higher allocation can
                       be a net LOSS once GC frequency rises

  THE CORRECT ESCALATION:

    1. PROFILE production or a realistic load test — find the term
       that actually matters (see Performance & Profiling)
    2. MICROBENCHMARK the candidate fix in isolation — is the new
       version genuinely faster, and does it allocate less?
    3. LOAD TEST the whole system with the change — does the win
       survive contention, cache pressure and GC?
    4. MEASURE IN PRODUCTION — canary, compare p50/p99, watch
       allocation rate and error rate

  SKIPPING STEP 1 IS THE COMMON FAILURE. A carefully constructed
  benchmark proving a 40% improvement in a method that is 2% of
  runtime is rigorous work applied to the wrong question.

  SKIPPING STEP 3 IS THE EXPENSIVE ONE. It is entirely normal for a
  microbenchmark win to vanish — or reverse — under real
  conditions.

Interview Questions

Beginner: Why can't you just time a loop with System.currentTimeMillis()?

Several independent reasons, and the errors do not cancel out.

No warmup. The first ~1,500 invocations run interpreted, 20–50× slower than compiled code, then C1 compiles, then C2. A short loop measures the interpreter; a long one measures an unknown mixture of three execution modes.

Dead-code elimination. If nothing observes the result, the JIT may delete the call. The tell is a reported cost below one CPU cycle.

Constant folding. A literal or final input can be computed once at compile time.

The clock itself is wrong for the job. currentTimeMillis is wall-clock time — it can jump backwards when NTP adjusts, and has coarse granularity on some platforms, so a measured duration can literally come out negative. nanoTime is monotonic and high-resolution, which is what durations need.

The consequence is not a small error: hand-rolled microbenchmarks routinely report differences of 10× in the wrong direction.

Beginner: What is dead-code elimination in a benchmark, and how do you prevent it?

If a computation's result is never observed, the JIT is free to prove it has no effect and remove it entirely.

@Benchmark
public void bad() { Math.log(42); }        // deleted → ~0.3 ns/op

@Benchmark
public double good() { return Math.log(input); }   // consumed

The diagnostic is the number itself. Anything under about a nanosecond per operation is less than a few CPU cycles, which is impossible for real work — that result means the code did not run.

JMH consumes returned values through a Blackhole. When a benchmark produces several results, take one as a parameter and consume each:

@Benchmark
public void multiple(Blackhole bh) {
    bh.consume(compute(a));
    bh.consume(compute(b));
}

Note that Blackhole.consume itself costs roughly a nanosecond, which is another reason to distrust sub-nanosecond scores.

Mid: Why does @Fork matter, and why is @Fork(0) dangerous?

Each fork runs the benchmark in a fresh JVM. Without that, benchmarks in the same process contaminate each other.

Profile pollution is the concrete mechanism. The JIT specialises a call site based on the types it has seen. If benchmark A runs first with an ArrayList, the shared call site is monomorphic and inlines; when B then runs with a LinkedList, the site becomes bimorphic and B is measured on de-optimised code. Running order changes the results.

Multiple forks also expose run-to-run variance. JVM behaviour differs between runs — compilation decisions, heap layout, address randomisation. Three forks show that spread; one fork reports a single sample as if it were the truth, and its error bar only reflects within-run noise.

@Fork(0) runs in the harness's own JVM, which is worse still: JMH's own classes are loaded and compiled alongside yours. It exists only for debugging a benchmark, never for measurement.

Three forks is a reasonable default; more if the variance between them is large.

Mid: How do you read JMH output, and when is a difference real? 
Benchmark          Mode  Cnt   Score    Error  Units
Bench.a            avgt   30  4231.5 ±  88.3  ns/op
Bench.b            avgt   30  4102.7 ± 201.4  ns/op

The Error column is a 99.9% confidence interval half-width, and it decides everything. Two results differ meaningfully only if their intervals do not overlap.

a: [4143.2, 4319.8]
b: [3901.3, 4304.1]        OVERLAP → no measured difference

So the honest statement here is "no difference was measured", not "b is 3% faster". Reporting that 3% is the most common way benchmark results become misinformation.

A large error bar is itself a finding. If the error is 20% of the score, something is unstable — GC inside the measurement window, a noisy machine, frequency scaling, or a benchmark that is not measuring the same code each iteration. Fix that before believing any score.

Add -prof gc and read gc.alloc.rate.norm. Bytes allocated per operation is deterministic rather than statistical, so it often gives a clearer answer than the time column — including proving that escape analysis eliminated an allocation.

Senior: Your benchmark shows a 40% improvement but production is unchanged. What happened?

Several possibilities, and they are all common enough to check in order.

Amdahl's law. If the method is 3% of runtime, a 40% improvement is a 1.2% overall win — invisible in production noise. This is the most likely explanation and the cheapest to check: look at the profile before celebrating the benchmark.

Cache effects. The benchmark's working set fits in L2; production's does not, so memory latency dominates and swamps the difference you measured.

Inlining context. The benchmark's call site is monomorphic and inlines; production's is megamorphic and does not, so the optimised version never gets the treatment it got in isolation.

Contention. The benchmark is single-threaded; production has 200 threads on the same structure, where lock or cache-line contention dominates the per-operation cost entirely.

GC interaction. A version that is faster per operation but allocates more can be a net loss once young-collection frequency rises. -prof gc would have shown this.

The process that avoids this: profile first to find a term that actually matters, microbenchmark the candidate fix, load test the whole system, then canary in production and compare p50/p99 and allocation rate. Skipping the first step is rigorous work applied to the wrong question; skipping the third is how a microbenchmark win quietly fails to transfer.

Senior: When is a microbenchmark the wrong tool?

Whenever the question is about a system rather than an operation. A microbenchmark measures one operation warm, in isolation, with a hot cache, no contention and no GC pressure — and real systems have none of those properties.

QuestionRight tool
Is A faster than B for this operation?JMH
Does this change allocate less?JMH with -prof gc
Where do A and B cross over?JMH with @Param
Where is my service's time going?A profiler (async-profiler, JFR)
What is my p99 under load?A constant-rate load test
Does this scale to 1,000 users?A load test
Did this change help?A production canary

The trap is that a microbenchmark feels the most rigorous — precise numbers, confidence intervals, reproducible. That precision is real and local; it says nothing about whether the operation matters.

There is also a cost to writing one. A correct JMH benchmark takes real effort, and effort spent proving a 40% win on a 2% term is effort not spent finding the N+1 query that is 60% of the request.

My rule: a microbenchmark is justified once profiling has already identified the code as a dominant term, and I need to choose between two specific implementations. Before that point it is premature; after it, it is exactly the right tool.

🏋️ Graded Exercises

1 (easy): This benchmark reports 0.31 ns/op. What is wrong? 
@Benchmark
public void hashCode() {
    "some test string".hashCode();
}
Solution

Two problems, and the number gives it away. 0.31 ns is well under one CPU cycle at 3 GHz — no real work happens that fast.

ProblemEffect
Result unusedDead-code elimination removes the call
Constant string literalConstant folding could compute it at compile time
(Bonus) String caches its hashEven if it ran, you would measure a cached field read
@State(Scope.Benchmark)
public static class Input {
    public String s;              // not final
    @Setup public void setup() { s = "some test string" + System.nanoTime(); }
}

@Benchmark
public int hashCode(Input in) {
    return in.s.hashCode();       // consumed, and opaque
}

The generated string in @Setup matters. A literal is interned and the compiler can see it; building it at runtime makes the value opaque, so folding is impossible.

The third row is the interesting one. String caches its hash in a field after the first call, so even a correct-looking benchmark measures a field read on every iteration after the first — which is a benchmark of the cache, not of the hash function.

Solution

@State(Scope.Benchmark)
public static class Data {
    @Param({"10", "1000", "100000"})
    public int size;
    public List<Integer> list;

    @Setup(Level.Trial)
    public void setup() {
        var r = new Random(42);                       // seeded
        list = IntStream.range(0, size)
                .mapToObj(i -> r.nextInt(1000))       // opaque values
                .toList();
    }
}

@Benchmark
public long sumList(Data d) {
    long sum = 0;
    for (Integer n : d.list) sum += n;    // ONE operation
    return sum;                            // consumed
}

Letting JMH do the repetition is the key change. Your own loop invites hoisting, unrolling and on-stack replacement, all of which shape the measurement around the benchmark's structure rather than the operation.

@Param is what makes the result useful. At 10 elements the answer is dominated by call overhead; at 100,000 it is dominated by memory access and unboxing. A single size hides the crossover that would actually inform a decision.

Add -prof gc — unboxing a million Integers has an allocation story that the time column alone will not tell you.

Profile pollution is the most likely and the most surprising. The JIT specialises a call site by the types it has seen. If A runs first with one implementation, the site is monomorphic and inlines; B then runs on a bimorphic site that does not. Whichever runs first wins — and reversing the order reverses the result.

Forking is the structural fix because it gives each benchmark a fresh JVM with no inherited profile. Multiple forks also make run-to-run variance visible instead of letting one sample look like the truth.

Before doing any of this, check the last row. If the two implementations' intervals overlapped in both runs, there was never a difference to explain — the runs are not contradicting each other, they are both saying "no measured difference".

5 (hard): Write a benchmark comparing HashMap, TreeMap and ConcurrentHashMap lookups. What must you control?
Solution 
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 10, time = 1)
@Fork(3)
@State(Scope.Benchmark)
public class MapLookupBenchmark {

    @Param({"100", "10000", "1000000"})
    private int size;

    @Param({"HIT", "MISS"})
    private String outcome;

    private Map<String,Integer> hash, tree, concurrent;
    private String[] keys;
    private int idx;

    @Setup(Level.Trial)
    public void setup() {
        var r = new Random(42);                      // seeded
        hash = new HashMap<>(size * 2);              // pre-sized:
        tree = new TreeMap<>();                      // no resize
        concurrent = new ConcurrentHashMap<>(size * 2);
        for (int i = 0; i < size; i++) {
            String k = "key-" + r.nextLong();
            hash.put(k, i); tree.put(k, i); concurrent.put(k, i);
        }
        keys = "HIT".equals(outcome)
                ? hash.keySet().toArray(String[]::new)
                : IntStream.range(0, 1000)
                    .mapToObj(i -> "absent-" + i).toArray(String[]::new);
    }

    private String nextKey() {                       // vary the key
        return keys[(idx = (idx + 1) % keys.length)];
    }

    @Benchmark public Integer hashMap()   { return hash.get(nextKey()); }
    @Benchmark public Integer treeMap()   { return tree.get(nextKey()); }
    @Benchmark public Integer concurrent(){ return concurrent.get(nextKey()); }
}
ControlWhy
Vary the key per invocationA single key stays in L1 and its hash is cached — you would measure the cache
@Param on sizeO(1) vs O(log n) only diverges with scale; 100 entries hides it
Hit and missMiss paths differ sharply between implementations
Pre-size the mapsOtherwise resize behaviour differs between them
Seeded random keysReproducible, and avoids accidentally friendly hash distribution
Return the valueDefeats dead-code elimination
@Fork(3)Three Map implementations would otherwise pollute one call site

The polymorphism issue deserves care. Declaring the fields as Map means the get call site sees three implementations, so within one JVM it becomes megamorphic and stops inlining — penalising whichever runs later. Forking separates the runs; declaring the concrete types would be even safer.

What the result still will not tell you: how these behave under concurrent access. That needs @Threads and @State(Scope.Thread), and it is the only comparison in which ConcurrentHashMap is actually interesting.

6 (hard): A team benchmarks a JSON parser swap: 30% faster per parse. They ship it and see no change. What went wrong and what should they have done?
Solution
Likely causeHow to have known
Amdahl — parsing is 5% of the requestProfile first: a 30% win on 5% is 1.5% overall
The request is I/O-boundWall-clock profile — the time is in the network, not the CPU
Benchmark payloads unrepresentativeUse captured production payloads, with @Param across sizes
Warm cache in the benchmarkProduction parses different documents; nothing stays in L2
Higher allocation offsets the win-prof gc: gc.alloc.rate.norm per parse
The win is inside the noise of production p50Compare distributions in a canary, not a mean

The most likely answer is the first, and it was knowable before any benchmark was written. A profile of a real request would have shown parsing as a small term, and the whole exercise would have been redirected.

The correct sequence:

  1. Profile production (async-profiler or JFR) — how much of a request is actually parsing?
  2. If it is significant, microbenchmark with real payloads and -prof gc, not synthetic documents.
  3. Load test the whole system — does the win survive contention, cache pressure and GC?
  4. Canary in production, comparing p50 and p99 and allocation rate, not averages.

There is a real cost beyond the wasted effort. Swapping a parser changes edge-case behaviour — date formats, number precision, unknown-field handling, error messages — so the team took on genuine risk for a 1.5% ceiling.

The generalisable lesson: a rigorous benchmark of the wrong question is still the wrong question, and the precision of the number makes it more persuasive, not more relevant.

🎯 Key Takeaways

  • A hand-written timing loop is wrong in five independent ways — warmup, dead code, constant folding, loop optimisations and OSR.
  • Errors of 10× in the wrong direction are normal, which is why JMH exists.
  • nanoTime for durations, currentTimeMillis for timestamps — the wall clock can jump backwards.
  • A sub-nanosecond result means the code did not run.
  • Consume every result by returning it or using a Blackhole.
  • Keep inputs in a non-final @State field set in @Setup so they cannot be constant-folded.
  • Never write the repetition loop yourself — benchmark one operation and let JMH repeat it.
  • @Fork(3) is not optional: without fresh JVMs, benchmark order changes results through profile pollution.
  • Two results differ only if their error intervals are disjoint — under ~5% is usually noise.
  • A large error bar is a finding, not a nuisance; fix the instability before believing the score.
  • -prof gc and gc.alloc.rate.norm answer questions the time column cannot, deterministically.
  • Mode.SampleTime is the only mode that gives percentiles — use it when tail latency is the question.
  • @Param across sizes reveals the crossover that a single input hides.
  • The environment invalidates runs silently — frequency scaling, background load, CPU quota in containers, and laptops on battery.
  • Run it twice; disagreement beyond the error bars means no conclusion is safe yet.
  • A microbenchmark cannot tell you whether your service will get faster — profile first, load test after, canary last.
