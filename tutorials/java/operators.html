Operators & Expressions Foundations

What you'll master: the operators that look trivial and cause real bugs — integer division truncating an average to a whole number, the remainder of a negative that makes n % 2 == 1 fail for odd negatives, and + being two different operators whose meaning depends on evaluation order, so "total: " + a + b concatenates where you meant to add; short-circuiting as a correctness tool rather than an optimisation — the reason obj != null && obj.isValid() is safe and the reversed order is a guaranteed NullPointerException; why i++ and ++i differ only in what the expression yields, and why i = i++ leaves i unchanged; and the professional habit around precedence, which is not to memorise the table but to parenthesise anything non-obvious. Prerequisites: Syntax, Types & Variables — numeric promotion is defined there, and every arithmetic surprise here is an instance of it.

Part 1 — Arithmetic and the Integer Division Trap

int  sum  = 5 + 3;       // 8
int  quot = 7 / 2;       // 3   NOT 3.5 — integer division TRUNCATES
int  rem  = 7 % 2;       // 1   remainder
double d  = 7.0 / 2;     // 3.5 one operand is double, so both promote
  WHY THIS IS THE MOST EXPENSIVE ARITHMETIC BUG IN JAVA

  It is silent, it looks correct, and it produces a plausible number.

    int average = total / count;        // both int -> truncated
    int midpoint = (low + high) / 2;    // truncated AND can overflow
    int percent = part / whole * 100;   // 0, always: part/whole is 0 first

  The third one is the cruellest: part/whole is integer division, so it
  is 0 for any part smaller than whole, and 0 * 100 is 0. The code
  reads as a percentage and reports zero for every input under 100%.

  THE FIXES, and they differ:

    double average = (double) total / count;   // cast ONE operand
    double percent = 100.0 * part / whole;     // reorder so the double
                                               // participates first
    int midpoint = low + (high - low) / 2;     // avoids the overflow too

  Note `(double)(total / count)` does NOT work — the division has
  already truncated before the cast runs. The cast must apply to an
  OPERAND, not to the result.
  THE NEGATIVE REMAINDER SURPRISE

    -7 % 3    ==  -1        the result takes the sign of the DIVIDEND
     7 % -3   ==   1

  So the common oddness test is wrong:

    n % 2 == 1        // FALSE for -7, because -7 % 2 is -1
    n % 2 != 0        // ✓ correct for every int
    Math.floorMod(n, 2) == 1   // ✓ always non-negative

  WHERE THIS ACTUALLY BITES: hashing and bucketing.

    int bucket = key.hashCode() % numBuckets;   // can be NEGATIVE
    array[bucket]                               // ArrayIndexOutOfBounds

  hashCode() is frequently negative — Integer.MIN_VALUE is a real
  return value — so this is not a theoretical concern. Math.floorMod is
  the fix, and it is why HashMap uses a bitmask rather than %.

Part 2 — Promotion, Restated for Operators

The rules live in Types; what matters here is the order in which they apply, because that is what produces wrong answers rather than compile errors.

  THE OPERATION HAPPENS FIRST. THE ASSIGNMENT HAPPENS AFTER.

    long bad  = 1_000_000 * 1_000_000;    // int * int overflows, THEN
                                          // the wrong value widens
    long good = 1_000_000L * 1_000_000;   // 64-bit from the start

  Declaring the target as long does nothing, because Java evaluates the
  right-hand side completely before it looks at where the result is
  going. This is the same mistake as `double h = 1 / 2` giving 0.0.

  THE RULE THAT COVERS BOTH: widen an OPERAND, not the target.

⚠️ + is two operators wearing one symbol, and which one you get depends on the types encountered so far, left to right. That is why log.info("total: " + a + b) prints the two numbers side by side instead of their sum — the String on the left has already turned the expression into concatenation. The fix is "total: " + (a + b), and it is worth knowing because it produces a wrong log line rather than an exception, so it survives indefinitely.

Part 3 — Comparison, and the == Divide

int a = 5, b = 5;
a == b;                    // true — primitives compare by VALUE

String s1 = new String("hi"), s2 = new String("hi");
s1 == s2;                  // false — objects compare by IDENTITY
s1.equals(s2);             // true

String s3 = "hi", s4 = "hi";
s3 == s4;                  // TRUE — both are the same interned literal!
  WHY THE LITERAL CASE IS WORSE THAN THE new CASE

  String literals are INTERNED: the compiler puts one copy in the class
  file's constant pool, so every occurrence of "hi" in your code refers
  to the same object. So == works.

  Which means:

    String a = "hi", b = "hi";
    a == b                        // true

    String c = "h" + readInput();  // computed at RUNTIME
    c == "hi"                      // FALSE, even when c holds "hi"

  The same comparison is true for compile-time constants and false for
  computed values. So == on Strings passes every test written with
  literals and fails the moment real input arrives — which is precisely
  the shape of bug that reaches production.

  ALWAYS .equals(), and Objects.equals(a, b) when either side may be
  null.
Comparison== doesUse instead

Two IntegersCompares identity — right only inside the −128…127 cache.equals() or intValue()

Part 4 — Short-Circuiting Is a Correctness Tool

if (list != null && !list.isEmpty()) { … }   // safe
if (!list.isEmpty() && list != null) { … }   // ❌ NPE when null

  && stops at the first false; || stops at the first true. So the
  right-hand side MAY NEVER RUN, and that is the point — the guard on
  the left protects the expression on the right.

  THE ORDER IS PART OF THE LOGIC, not a style choice. Reversing it does
  not make the code slower; it makes it crash.

  THE NON-SHORT-CIRCUIT FORMS EXIST AND ARE ALMOST ALWAYS WRONG HERE:

    if (list != null & !list.isEmpty())      // & evaluates BOTH sides
                                             // -> NPE anyway

  Single & and | on booleans evaluate both operands unconditionally.
  They have legitimate uses — when both sides have side effects you
  want — but in a guard they defeat the guard.

  A SUBTLER CONSEQUENCE: SIDE EFFECTS MAY NOT HAPPEN.

    if (cheapCheck() || expensiveLog()) { … }

  If cheapCheck() is true, expensiveLog() never runs. Putting anything
  with a side effect on the right of && or || means it runs
  conditionally, which is a bug if you assumed otherwise.

Part 5 — Assignment, Increment and the Ternary

int n = 10;
n += 5;        // n = n + 5  -> 15. Also -= *= /= %= &= |= ^= <<= >>=

int i = 5;
int j = i++;   // j = 5, i = 6   post: yields the OLD value, then adds
int k = ++i;   // k = 7, i = 7   pre:  adds, then yields the NEW value

int max = (a > b) ? a : b;
String label = (n == 1) ? "item" : "items";
  COMPOUND ASSIGNMENT HIDES A CAST

    byte b = 10;
    b = b + 5;     // ❌ compile error: int cannot be converted to byte
    b += 5;        // ✓ compiles — and silently narrows

  += performs an implicit narrowing cast that plain + refuses. Usually
  convenient; occasionally it hides an overflow you would rather have
  been told about:

    byte b = 120;
    b += 10;       // 120 + 10 = 130, narrowed to -126. No warning.

  THE ONE TO NEVER WRITE

    i = i++;       // i is UNCHANGED

  The right-hand side evaluates to i's old value, i is incremented,
  and then the assignment overwrites i with the saved old value. It
  compiles, it does nothing, and it appears in interview questions
  precisely because the answer is counter-intuitive. In real code it is
  always a mistake — write i++ alone.
FormUse it forAvoid when
Ternary c ? a : bChoosing between two valuesChoosing between two actions — that is if/else
Nested ternaryEssentially neverTwo levels deep is already unreviewable; use if/else or switch
i++ as a statementIncrementing — identical to ++i here—
i++ inside a larger expressionRarely worth the ambiguityWhenever a reader must pause to work out which value was used
+= on byte/short/charConcise accumulationWhen silent narrowing could overflow — use int and check

Part 6 — Precedence, and When to Stop Memorising

  postfix          n++  n--
  unary            ++n  --n  !  ~  (cast)  -n
  multiplicative   *  /  %
  additive         +  -
  shift            <<  >>  >>>
  relational       <  >  <=  >=  instanceof
  equality         ==  !=
  bitwise          &  then  ^  then  |
  logical          &&  then  ||
  ternary          ?  :
  assignment       =  +=  -=  …

  So 2 + 3 * 4 is 14, and a && b || c means (a && b) || c.

  THE PROFESSIONAL HABIT IS NOT TO MEMORISE THIS.

  It is to parenthesise anything non-obvious. Code is read far more
  often than written, and `(a && b) || c` costs two characters and
  removes all doubt for every future reader — including you.

  Keep precedence knowledge for READING other people's code; write with
  parentheses.

  THE ONE PLACE THE TABLE GENUINELY MATTERS:

    if (flags & MASK == MASK)      // ❌ parses as flags & (MASK == MASK)
                                   //    because == binds TIGHTER than &
    if ((flags & MASK) == MASK)    // ✓ what you meant

  Bitwise operators binding LOOSER than equality is inherited from C and
  is the one precedence rule that regularly produces a compile error or
  a silently wrong condition.

Interview Questions

Beginner: What does 7 / 2 evaluate to, and why?

3, not 3.5. Both operands are int, so Java performs integer division, which truncates toward zero.

To get 3.5 at least one operand must be floating point — 7.0 / 2 or (double) 7 / 2. The cast has to apply to an operand: (double)(7 / 2) is 3.0, because the truncation already happened.

The reason this matters beyond the trivia is that it is silent and plausible. int average = sum / count quietly drops the fraction, and part / whole * 100 returns zero for every input below 100% — code that reads exactly like a percentage calculation and reports nothing but zero.

Beginner: What is the difference between i++ and ++i?

Both increment i by one. They differ in what the expression evaluates to.

i++ yields the old value and then increments, so int j = i++ gives j the value before the increment. ++i increments first and yields the new value, so int k = ++i gives the incremented value.

When the result is not used — a bare i++; statement, or the step of a for loop — they are interchangeable, and choosing between them is style.

The related question worth being ready for is i = i++, which leaves i unchanged: the right-hand side evaluates to the old value, the increment happens, and then the assignment overwrites i with the saved old value.

Mid: Explain short-circuit evaluation, and give a case where it is required for correctness rather than speed.

&& stops at the first false and || at the first true, so the right-hand operand may never be evaluated.

The correctness case is guarding: if (obj != null && obj.isValid()). When obj is null the left side is false, so isValid() is never called and there is no NullPointerException. Reversing the operands — obj.isValid() && obj != null — throws every time. The order is part of the logic, not a preference.

The non-short-circuiting & and | evaluate both sides unconditionally, which is exactly why they are wrong in a guard: obj != null & obj.isValid() throws despite looking almost identical.

The consequence people forget is the other direction: anything with a side effect on the right of && or || runs conditionally. If the right operand increments a counter or writes a log line, whether it happens depends on the left operand — which is a bug if you assumed both would run.

Mid: Why does long x = 1_000_000 * 1_000_000 give the wrong answer?

Because the multiplication is int * int, evaluated entirely in 32-bit arithmetic. The true product is a trillion, which exceeds Integer.MAX_VALUE, so it wraps — and only then is the already-wrong value widened to long.

The declared type of the target has no influence, and that is the whole trap. Java evaluates the right-hand side to completion before considering where the result is going.

The fix is to make an operand 64-bit: 1_000_000L * 1_000_000. And the safest habit is to widen the first operand, because promotion then applies to the whole expression — (long) a * b * c is safe, while a * b * (long) c has already overflowed by the time the cast matters.

It is the same structural mistake as double h = 1 / 2 giving 0.0, one type family over. In both cases the rule is: widen an operand, not the target.

Senior: Why is == on Strings especially dangerous, rather than merely wrong?

Because it works often enough to pass review and to pass tests.

String literals are interned — the compiler stores one copy per distinct literal in the constant pool, so every occurrence of "hi" in your source refers to the same object. So String a = "hi", b = "hi"; a == b is true. The same is true for concatenations of compile-time constants, which the compiler folds.

But a String built at runtime — read from a request, a file, a database, or concatenated with a variable — is a different object. So c == "hi" is false even when c contains exactly "hi".

The failure profile is what makes it dangerous: a unit test written with literals passes, and the same code fails the moment real input arrives. That is the worst possible signal, because the test suite actively certifies the bug.

Always .equals(), and Objects.equals(a, b) when either side might be null. I would also note the one place identity comparison is correct and idiomatic: enum constants, which are singletons by construction, so == is both safe and preferred there — and it null-checks for free.

String.intern() exists and can make == work, and I would treat any code relying on it as a red flag: it trades a clear .equals() for a subtle global invariant that one missed call breaks.

Senior: A hashing function uses hashCode() % buckets and throws ArrayIndexOutOfBoundsException in production. Explain and fix.

hashCode() returns a signed int, and the % operator gives a result with the sign of the dividend. So a negative hash code produces a negative index.

This is not a rare case. Hash codes are routinely negative — roughly half of the int range — so any object whose hash happens to be negative lands out of bounds. It appears in production and not in tests because test data is small and often happens to hash positive.

int bucket = Math.floorMod(key.hashCode(), buckets);   // always 0..buckets-1

Math.floorMod is the direct fix: it returns a non-negative result for a positive divisor, which is what "which bucket" means.

What Math.abs does not fix: Math.abs(Integer.MIN_VALUE) is still Integer.MIN_VALUE, because the positive range is one smaller than the negative. So the "obvious" fix leaves exactly one hash value broken, which is a genuinely nasty intermittent bug.

What real hash tables do is size the table to a power of two and use hash & (size - 1) — a bitmask, which is both non-negative and faster than a division. That is what HashMap does, and it also explains why it insists on power-of-two capacities and why it applies a spreading function to the hash first: masking only keeps the low bits, so poor hash codes that differ only in their high bits would all collide.

🏋️ Graded Exercises

1 (easy): Predict each result. 
System.out.println(7 / 2);
System.out.println(7 % 2);
System.out.println(-7 % 2);
System.out.println(7.0 / 2);
System.out.println(1 + 2 + "x");
System.out.println("x" + 1 + 2);
Solution 
3       integer division truncates
1       remainder
-1      the remainder takes the DIVIDEND's sign
3.5     one operand is double, so both promote
3x      left to right: 1+2 is 3, then concatenate
x12     the first + sees a String, so everything concatenates

The last two are the same operators in the same order — only the position of the String differs. + is resolved left to right, and once a String appears on the left every subsequent + is concatenation.

Why that matters in real code: log.info("total: " + a + b) prints the digits side by side rather than their sum, and it produces a wrong log line rather than an exception — so nothing surfaces it. Wrap the arithmetic: "total: " + (a + b).

And -7 % 2 being -1 is why n % 2 == 1 is the wrong oddness test. n % 2 != 0 is correct for every input.

2 (easy): This percentage always prints 0. Fix it, and explain why one obvious fix does not work. 
int part = 7, whole = 20;
double pct = (double)(part / whole * 100);
System.out.println(pct);   // 0.0
Solution 
  part / whole   -> 7 / 20 -> 0     (integer division, truncated)
  0 * 100        -> 0
  (double) 0     -> 0.0             the cast widens a value that is
                                    already wrong

// FIX — the double must participate in the DIVISION
double pct = 100.0 * part / whole;        // 35.0
double pct = (double) part / whole * 100; // 35.0 — also fine

Why the cast on the outside cannot work: a cast applies to the value it is given, and by the time it runs the division has already discarded the fraction. Casting can widen a number; it cannot recover information that was thrown away.

Why 100.0 * part / whole is my preference: the promotion happens at the leftmost operation and then applies to everything downstream, so there is no way to get the order wrong later. Putting the cast next to part works equally well but is easier to break when someone reorders the expression.

The general rule: in mixed arithmetic, make the widest type participate as early as possible. It is the same rule as widening the first operand to avoid integer overflow.

3 (medium): Why does this throw, and why did it pass every test? 
int bucket = key.hashCode() % buckets.length;
return buckets[bucket];
Solution

hashCode() returns a signed int, and % yields a result with the sign of the dividend. A negative hash gives a negative index, and buckets[-3] throws ArrayIndexOutOfBoundsException.

Why the tests passed: test fixtures are small and usually use short, tidy strings that happen to hash positive. Roughly half of the int range is negative, so the bug is a coin flip per key — reliable in production, invisible with five test values.

int bucket = Math.floorMod(key.hashCode(), buckets.length);

4 (medium): Find both bugs. 
if (user.isActive() && user != null) {
    total += user.getScore();
}
byte attempts = 120;
attempts += 10;
Solution

Bug 1 — the guard is on the wrong side. && evaluates left to right, so user.isActive() runs before the null check and throws a NullPointerException whenever user is null. The null check protects nothing where it is.

if (user != null && user.isActive()) { … }   // ✓

Bug 2 — += hides a narrowing cast. 120 + 10 is 130, which does not fit in a byte, so it silently becomes -126. Written as attempts = attempts + 10 it would not compile at all — the compound operator performs an implicit cast that plain + refuses.

int attempts = 120;
attempts += 10;              // 130, as intended
Why each survives review
The null check is present, so a reader skimming sees a guarded call and moves on. The order is the whole bug, and order is easy not to read
+= compiles, which readers reasonably take as evidence the types work. The narrowing is invisible in the source

What I would take from this pair: both bugs are about evaluation rather than about the operators themselves — what runs first, and what conversion was inserted for you. That is the recurring theme of this whole lesson.

The habit that prevents the second one: use int for counters unless you have a specific reason not to. byte and short save memory only in large arrays, and in a scalar they buy nothing while adding an overflow ceiling of 127.

5 (hard): Explain why i = i++ leaves i unchanged, using the evaluation order.
Solution 
  int i = 5;
  i = i++;
  // i is still 5

  STEP BY STEP:

  1. Java evaluates the right-hand side first: i++
  2. i++ yields i's CURRENT value, 5 — this value is saved
  3. As a side effect, i is incremented to 6
  4. The assignment now completes, writing the SAVED value 5 into i
  5. The increment has been overwritten. i == 5.

The mechanism is that the assignment's right-hand side is fully evaluated — including its side effects — before the assignment stores anything. The increment genuinely happened; it was then discarded by the very assignment that contained it.

ExpressionResult for i = 5Why
i = i++i == 5Old value written back over the increment
i = ++ii == 6Pre-increment yields the new value, which is then assigned — a no-op assignment
i++ alonei == 6No assignment to overwrite it
i = i++ + 1i == 6Yields 5, increments to 6, then assigns 5+1

Worth knowing this is well-defined in Java and not in C. The JLS specifies evaluation order precisely, so i = i++ reliably leaves i unchanged on every JVM. The equivalent C is undefined behaviour and may do anything. So it is a legitimate question about Java semantics rather than a trick with no answer.

And in real code it is always a mistake. There is no reading of i = i++ that expresses an intent — anyone who meant to increment writes i++. Its only value is as a probe for whether someone understands that side effects and assignment are separate steps.

6 (hard): A flag check compiles but the condition is never true. Find it, and give the rule. 
static final int ADMIN = 0b0100;
if (permissions & ADMIN == ADMIN) { grantAccess(); }
Solution 
  It parses as:

    permissions & (ADMIN == ADMIN)

  because == binds TIGHTER than &. So:

    ADMIN == ADMIN    -> true, a boolean
    permissions & true -> ❌ bad operand types for &
                           (int and boolean)

  In Java this is a COMPILE ERROR, which is the good outcome. The same
  code in C compiles and silently computes
  permissions & 1 — a condition that is true only when the lowest
  bit is set, unrelated to ADMIN.

// FIX
  if ((permissions & ADMIN) == ADMIN) { grantAccess(); }

The rule: the bitwise operators &, ^ and | bind looser than the equality and relational operators. It is inherited from C, where it is widely considered a design mistake, and it is the one precedence rule that regularly produces wrong code rather than merely surprising code.

WrittenParsed as
a & b == ca & (b == c)
a | b != ca | (b != c)
a & b > 0a & (b > 0)

Why Java's stricter typing saves you here: because & cannot mix an int and a boolean, the mistake is a build failure. In C the same expression is valid arithmetic and ships. That is a concrete instance of static typing converting a runtime defect into a compile-time one.

The habit rather than the rule: parenthesise every bitwise test. Even when precedence happens to work, (flags & MASK) != 0 states the intent, and no reader has to recall a table inherited from 1972.

A related readability point: for a single-bit flag, (p & ADMIN) != 0 is the idiomatic test. Comparing to ADMIN works and generalises to multi-bit masks, which is worth knowing when the mask has more than one bit set and you mean "all of these".

🎯 Key Takeaways

  • Integer division truncates, silently and plausibly — averages lose their fraction and part/whole*100 is always zero.
  • A cast must apply to an operand, not the result — (double)(a / b) widens a number that is already wrong.
  • Widen an operand, not the target. long x = int * int overflows before the assignment ever happens.
  • The remainder takes the dividend's sign, so n % 2 == 1 fails for negative odd numbers.
  • hashCode() % n can be negative — use Math.floorMod, and know that Math.abs is still broken for Integer.MIN_VALUE.
  • + is two operators, resolved left to right, which is why "total: " + a + b concatenates instead of adding.
  • == on Strings works for interned literals and fails for computed values — so tests certify the bug.
  • == on enum constants is correct and idiomatic, and null-safe as a bonus.
  • Short-circuit order is part of the logic. The guard goes on the left, or it guards nothing.
  • & and | evaluate both sides, which defeats a guard.
  • A side effect on the right of && runs conditionally — pull it out into its own statement.
  • i++ and ++i differ only in what the expression yields; as a statement they are identical.
  • i = i++ leaves i unchanged — the saved old value overwrites the increment, and this is well-defined in Java.
  • += hides a narrowing cast, so byte b = 120; b += 10; silently gives −126.
  • Bitwise operators bind looser than equality — always parenthesise a flag test.
  • Do not memorise the precedence table; parenthesise anything non-obvious. Keep the table for reading other people's code.
