Methods & Parameters Foundations

What you'll master: the method signature as a contract, and the distinction interviews return to constantly — overloading is resolved by the compiler from static types, overriding is resolved by the JVM from the runtime object, which is why adding an overload can silently change which method an existing call site invokes; why a single misspelled override becomes a new method that is never called, and the one annotation that turns that into a compile error; the varargs traps — passing null to a varargs method is ambiguous, and an overload plus varargs resolves in an order almost nobody predicts; why recursion is elegant and StackOverflowError arrives at around ten thousand frames, with no tail-call optimisation coming to save you; and what actually makes a method good — one level of abstraction, a name that says what rather than how, and parameters you cannot pass in the wrong order. Prerequisites: Types for pass-by-value, and Control Flow.

Part 1 — Anatomy of a Method

public    static    BigDecimal    total(List<Item> items)    throws PricingException
  │         │            │          │           │                      │
modifier  static    return type   name      parameters          checked exceptions
                                            (the SIGNATURE is name + parameter types)
  WHAT IS AND IS NOT PART OF THE SIGNATURE — this decides everything
  about overloading:

    PART OF IT       the method NAME
                     the parameter TYPES, in order

    NOT PART OF IT   the return type
                     parameter NAMES
                     the throws clause
                     access modifiers

  Which is why these two cannot coexist:

    int    parse(String s)
    double parse(String s)      // ❌ same signature, differing only
                                //    in return type

  The compiler resolves a call by signature alone, so it would have no
  way to choose. It is also why you cannot overload on a checked
  exception, and why renaming a parameter is never a breaking change
  for callers.

Part 2 — Parameters and Passing

Java is pass-by-value, always — the proof is in Types. The consequence for method design is what matters here:

void mutate(List<String> list)   { list.add("x"); }   // caller SEES this
void reassign(List<String> list) { list = new ArrayList<>(); }  // caller does not

  A method can change what your object CONTAINS, but cannot make your
  variable point elsewhere.

  THE DESIGN CONSEQUENCE: a method that mutates its argument is doing
  something invisible at the call site.

    processOrder(order);      // does this modify `order`? You cannot tell.

  Prefer returning a new value:

    Order processed = process(order);   // obvious, and testable

  Mutating parameters is not forbidden — collections are routinely
  filled that way — but it should be stated in the name:

    addAllTo(target, items)          // clear
    void collectInto(List<X> out)    // clear
    void process(List<X> items)      // unclear, and probably wrong

Part 3 — Overloading

void log(String msg)                  { … }
void log(String msg, Throwable t)     { … }
void log(String msg, Object... args)  { … }

  Same name, different parameter lists. The compiler picks one AT
  COMPILE TIME using the STATIC types of the arguments.

  THE RESOLUTION ORDER, and it surprises people:

  1. EXACT match, or widening primitive conversion   int -> long
  2. BOXING / UNBOXING                               int -> Integer
  3. VARARGS                                         int -> int...

  Varargs is LAST, which means:

    void f(long x)      { print("long"); }
    void f(Integer x)   { print("Integer"); }
    void f(int... x)    { print("varargs"); }

    f(42);              // prints "long"

  42 is an int. Widening to long (step 1) beats boxing to Integer
  (step 2), which beats varargs (step 3). Remove the long overload and
  it prints "Integer"; remove that too and it prints "varargs".

  So ADDING AN OVERLOAD CAN CHANGE WHICH METHOD AN EXISTING CALL SITE
  INVOKES, with no change at that call site and no warning.

  THE DIFFERENCE MADE CONCRETE

    class Animal { void speak() { print("..."); } }
    class Dog extends Animal { @Override void speak() { print("Woof"); } }

    Animal a = new Dog();
    a.speak();                  // "Woof" — OVERRIDING uses the OBJECT

    void feed(Animal x) { print("animal"); }
    void feed(Dog x)    { print("dog"); }

    feed(a);                    // "animal" — OVERLOADING uses the
                                //  DECLARED TYPE, which is Animal

  Same variable, same line, opposite rules. That pair is the reason
  this comes up in interviews: it is the cleanest demonstration that
  Java resolves these two things at different times.
  WHY @Override IS NOT DECORATION

    class Animal { void speak() { … } }

    class Dog extends Animal {
        void speek() { … }        // typo — a NEW method
    }

  This compiles. Dog now has two methods, speak() inherited and speek()
  never called by anything. The bug is silent and can survive for
  years.

  With @Override it is a compile error: "method does not override or
  implement a method from a supertype."

  IT CATCHES THREE THINGS:
    - misspelled names
    - wrong parameter types (an accidental OVERLOAD instead of an
      override — the subtlest of the three)
    - a superclass method that was later removed or renamed

  Put it on every override, including implementations of interface
  methods.

Part 5 — static, Varargs and Recursion

  STATIC — belongs to the CLASS, not an instance

    static int max(int a, int b) { … }      // Math.max style
    Math.max(3, 7);                         // no object needed

  Use static when the method needs no instance state. It is a signal to
  the reader: "this cannot touch a field".

  THE TESTABILITY CAVEAT: a static method cannot be overridden or
  mocked through an interface, so a static call to something with a
  side effect — a clock, a database, a random source — hardwires the
  dependency at every call site. Static is right for pure functions and
  wrong for collaborators.
  VARARGS — zero or more arguments, received as an array

    static int sum(int... nums) {           // nums is an int[]
        int t = 0;
        for (int n : nums) t += n;
        return t;
    }
    sum();  sum(1);  sum(1, 2, 3);  sum(existingArray);

  THREE RULES: at most one varargs parameter, it must be LAST, and it
  is genuinely an array inside the method.

  TRAP 1 — null is ambiguous

    sum(null);        // is this a null int[]? or one null element?
                      // For Object..., it is a NULL ARRAY -> NPE on
                      // the for-each, not a one-element array.

  TRAP 2 — an existing array plus a value does not append

    log("msg", args, extra);    // ❌ three args, not args + extra

  TRAP 3 — overload plus varargs resolves in an order few predict

    void f(Object o)     { … }
    void f(Object... o)  { … }
    f("x");              // calls f(Object) — varargs is a LAST resort
  RECURSION — and the ceiling that ends it

    static long factorial(int n) {
        if (n <= 1) return 1;         // BASE CASE — without it,
        return n * factorial(n - 1);  // StackOverflowError
    }

  EVERY CALL CONSUMES A STACK FRAME, and the stack is a fixed size
  (commonly around 512KB–1MB per thread). In practice you get roughly
  5,000–15,000 frames before StackOverflowError — the exact number
  depends on frame size and the -Xss setting, so it is not something to
  design against.

  JAVA HAS NO TAIL-CALL OPTIMISATION. Writing the recursion in tail
  position does NOT make it iterative — the JVM still pushes a frame.
  This is the crucial difference from Scala, Kotlin (with tailrec) or
  functional languages, and it means recursion in Java is bounded by
  DEPTH, not by elegance.

  SO: recursion is right when the depth is bounded by the STRUCTURE —
  a balanced tree is log(n) deep, a JSON document is nested by its
  schema. It is wrong when the depth is bounded by the DATA — never
  recurse once per element of a list.
Recursion is right whenUse iteration when
The structure is recursive — trees, directories, nested documentsThe depth scales with input size — a list, a file's lines
Depth is logarithmic or bounded by a schemaDepth could reach thousands
The recursive form is dramatically clearerThe iterative form is equally clear
You control the inputThe input is untrusted — deep nesting is a denial-of-service vector

Part 6 — What Makes a Method Good

  ONE LEVEL OF ABSTRACTION

  A method should read as a sequence of steps at the SAME conceptual
  level. Mixing levels is what makes a method hard to follow, more than
  its length:

    void placeOrder(Order o) {
        validate(o);                          // high level
        BigDecimal total = price(o);          // high level
        for (Item i : o.items())              // LOW level — dropping
            if (i.qty() < 0) throw …;         // into validation detail
        charge(o.customer(), total);          // back to high level
    }

  The loop belongs inside validate(). The test is whether the method
  reads like a summary or like an implementation.

  A NAME THAT SAYS WHAT, NOT HOW

    calculateTotalUsingLoop()     ❌ the how will change
    total()                        ✓
    getUserDataFromDatabase()      ❌ leaks the storage choice
    findUser(id)                   ✓

  PARAMETERS YOU CANNOT PASS WRONG

    transfer(long from, long to, BigDecimal amount)
    transfer(accountB, accountA, amount);     // compiles. Wrong.

  Two parameters of the same type in a row is a defect waiting to
  happen, and no test catches it because both orders are valid Java.

    transfer(AccountId from, AccountId to, Money amount)

  Distinct types make the mistake a compile error. This is the single
  highest-value habit in method design, and it is why records earn
  their place (see Records & Sealed Types).

  COMMAND OR QUERY, NOT BOTH

    boolean removeIfPresent(K key)     // changes state AND answers
                                       // — acceptable, and documented
    boolean isValid()                  // must not change anything

  A query with a hidden side effect is the hardest kind of bug to
  reason about, because callers assume they can call it freely, in any
  order, or not at all.

Interview Questions

Beginner: What is a method signature, and what is not part of it?

The signature is the method name plus the parameter types, in order. That is what the compiler uses to tell one method from another.

What is not part of it: the return type, the parameter names, the throws clause, and the access modifiers.

The consequences are worth stating because each one comes up. You cannot overload two methods that differ only in return type — the compiler would have no way to choose at a call site that discards the result. Renaming a parameter is never a breaking change for callers. And you cannot overload on the exceptions thrown.

The one that catches people is generics: List<String> and List<Integer> are the same type after erasure, so two methods differing only in type argument have the same signature and will not compile.

Beginner: What is the difference between overloading and overriding?

Overloading is several methods with the same name and different parameter lists, usually in one class. The compiler picks one at compile time based on the declared types of the arguments.

Overriding is a subclass replacing a superclass method with the same signature. The JVM picks one at run time based on the actual object.

The clean demonstration puts them side by side. With Animal a = new Dog(), calling a.speak() runs Dog's version, because overriding follows the object. But passing a to overloaded feed(Animal) and feed(Dog) selects the Animal one, because overloading follows the declared type. Same variable, opposite rules.

Overriding is what makes polymorphism work. Overloading is a naming convenience, and one that should be used sparingly when the parameter types are related.

Mid: Why is @Override important if it is optional?

Because without it, an override that does not actually override is legal code. Misspell speak as speek and you have not overridden anything — you have added a new method that nothing calls. It compiles, it runs, and the superclass behaviour silently remains in effect.

With the annotation the compiler checks your intent and rejects it: "method does not override or implement a method from a supertype."

It catches three distinct mistakes. A misspelled name. Wrong parameter types — which produces an accidental overload rather than an override, and is the subtlest of the three because the method does exist and does get called, just not where you expected. And a superclass method that was later renamed or removed, where the annotation turns a silently dead method into a build failure.

It also documents intent for readers, which matters in a class with many methods where "is this ours or inherited?" is otherwise a lookup. I would treat it as mandatory in review, including on interface implementations, where it has been legal since Java 6.

Mid: How does Java choose between overloads, and why can adding one break existing code?

The compiler tries three phases in order, and stops at the first that finds a match.

First, an exact match or a widening primitive conversion — int to long. Second, boxing or unboxing — int to Integer. Third, and only if neither worked, varargs.

So with overloads taking long, Integer and int..., the call f(42) selects the long version. Widening beats boxing, and boxing beats varargs. Most people guess Integer, because it looks like the closest match.

The reason this can break existing code is that resolution is redone on recompilation against the current set of overloads. Adding f(Integer) to a library where callers were binding to f(long) can move them to the new method without a single edit at any call site — and if the two behave differently, that is a behaviour change with an empty diff.

It is why I treat adding an overload to a published API as a change requiring thought rather than a free addition, and why overloading on related types — Object and String, or a class and its subclass — is worth avoiding entirely. Different names cost nothing and remove the whole question.

Senior: When is recursion appropriate in Java, given there is no tail-call optimisation?

The absence of tail-call optimisation is the constraint that decides it. Writing a recursion in tail position does not help — the JVM still pushes a frame per call, so recursion in Java is bounded by depth, full stop. Typical limits are five to fifteen thousand frames depending on frame size and -Xss, and StackOverflowError is an Error, so it is not something to catch and recover from.

That gives a clean rule: recursion is appropriate when the depth is bounded by the structure, and inappropriate when it is bounded by the data.

Walking a balanced tree is logarithmic — a million nodes is twenty frames. Traversing a directory tree or a nested document is bounded by how deep the schema realistically goes. Both are fine, and the recursive form is much clearer than the iterative one.

Recursing once per element of a list is not fine, however elegant, because the depth is the input size. Nor is recursing over a linked structure that could be a degenerate chain — an unbalanced tree is effectively a list.

The case I would flag in review is recursion over untrusted input. A parser that recurses per nesting level turns deeply nested JSON into a denial-of-service vector: the attacker controls the depth, so they control whether your thread dies. That needs an explicit depth limit, rejected before the stack runs out — and it is a security requirement rather than a robustness nicety.

Where the structure is recursive but the depth is unbounded, the answer is an explicit Deque as a work stack. It is less pretty, and it moves the growth to the heap where you can bound it and where failure is an OutOfMemoryError you can actually reason about.

Senior: What makes a method well-designed?

Four properties, roughly in order of how much trouble their absence causes.

One level of abstraction. The body should read as steps at a single conceptual level. A method that calls validate() and charge() and also contains a loop checking item quantities is mixing a summary with an implementation, and that — more than length — is what makes methods hard to follow.

Parameters you cannot pass in the wrong order. Two adjacent parameters of the same type is a latent defect: transfer(long from, long to, BigDecimal amount) accepts the accounts reversed, compiles, and no test finds it because both orders are valid Java. Distinct types — an AccountId rather than a long — make the mistake a compile error. This is the highest-value habit on the list, and it is most of the argument for wrapper records.

A name that describes what, not how. getUserFromDatabase leaks a storage decision into every call site and goes stale when a cache is added; findUser does not.

Command or query, not both. Callers assume a query is free, repeatable and safe to skip. A query that mutates breaks all three assumptions at once, and produces ordering bugs that are very hard to see.

What I deliberately would not put on the list is a line limit. Short methods are usually a consequence of the first property rather than a goal — and enforcing a number produces a different pathology, where a coherent forty-line method is split into six five-line ones that must be read together anyway, now scattered across a file.

🏋️ Graded Exercises

1 (easy): Which overload does f(42) call, and why? 
void f(long x)     { print("long"); }
void f(Integer x)  { print("Integer"); }
void f(int... x)   { print("varargs"); }
Solution

f(long). Resolution proceeds in three phases and stops at the first that matches:

PhaseConsidersResult for 42
1Exact match or widening primitiveint → long matches. Stops here
2Boxing / unboxingint → Integer would match, never reached
3VarargsWould match, never reached

Remove the long overload and it prints "Integer"; remove that too and it prints "varargs". So the answer depends entirely on which overloads exist, not on which looks closest.

Most people guess Integer, reasoning that int and Integer are "the same thing". They are not, and the phase order is why: widening is a cheaper conversion than boxing, so the language prefers it.

The design lesson is not to memorise the phases — it is that this set of overloads should not exist. Three overloads whose parameter types are mutually convertible make every call site ambiguous to a human reader, even when the compiler is certain. Different names would be clearer.

2 (easy): Write a varargs average, and handle the empty call.
Solution 
static OptionalDouble average(int... nums) {
    if (nums.length == 0) return OptionalDouble.empty();
    long sum = 0;                       // long: avoids overflow
    for (int n : nums) sum += n;
    return OptionalDouble.of((double) sum / nums.length);
}
DecisionWhy
OptionalDouble, not 0The average of nothing is undefined, and 0 is a wrong answer that looks like a right one. average() is a legal call, so the empty case is reachable
long sumSumming many ints overflows silently; accumulating in long costs nothing
(double) sum / nums.lengthCast an operand — sum / nums.length would do integer division first

The varargs detail worth knowing: nums is a real int[] inside the method, so nums.length works and you can pass an existing array directly at the call site.

What breaks if the parameter were Integer...: average(null) becomes ambiguous — Java reads it as a null array rather than a one-element array, so the for-each throws immediately. With primitive int... that particular trap is unavailable, which is a small argument for the primitive form.

The alternative worth naming: IntStream.of(nums).average() returns exactly this OptionalDouble, handles empty correctly, and is one line.

3 (medium): Convert this to iteration and explain when each form is right. 
static long sumList(List<Integer> list, int i) {
    if (i == list.size()) return 0;
    return list.get(i) + sumList(list, i + 1);
}
Solution 
static long sumList(List<Integer> list) {
    long sum = 0;
    for (int n : list) sum += n;
    return sum;
}

The recursion is wrong here because its depth is the input size. A list of 50,000 elements is 50,000 stack frames, which is a StackOverflowError. The limit is somewhere around 5,000–15,000 frames depending on frame size and -Xss, so the failure point is not even predictable across environments.

And tail position does not save it. Even rewritten with an accumulator, Java performs no tail-call optimisation — the JVM pushes a frame regardless. That is the difference from Scala or Kotlin's tailrec, and it is why "make it tail recursive" is not a fix in Java.

Recursion is right whenBecause
Walking a balanced treeDepth is log(n) — a million nodes is about twenty frames

The iterative version needs an explicit stack to imitate itYou would be hand-rolling what the call stack does, less clearly

The signature also improved. The recursive version leaked an index parameter that callers had to pass as 0 — an implementation detail in the public API, and a chance to pass the wrong value. If recursion were the right approach, the fix would be a public method with a clean signature delegating to a private recursive helper.

The security angle for untrusted input: where the depth is attacker-controlled — a JSON parser recursing per nesting level — this stops being a robustness concern and becomes a denial-of-service vector. Those need an explicit depth cap, rejected before the stack is exhausted.

4 (medium): Why does this print "animal" rather than "dog", and what would fix it? 
class Animal {}
class Dog extends Animal {}

void feed(Animal a) { print("animal"); }
void feed(Dog d)    { print("dog"); }

Animal pet = new Dog();
feed(pet);
Solution

Overload resolution happens at compile time, from the declared type. pet is declared Animal, so the compiler binds the call to feed(Animal) and bakes that choice into the bytecode. The fact that the object is a Dog at run time is never consulted — overloading is static dispatch.

Attempted fixWorks?
feed((Dog) pet)Yes — casting changes the compile-time type, which is what resolution reads
Declaring Dog pet = new Dog()Yes — same reason
Making Dog override somethingNo — there is nothing to override; these are unrelated methods that share a name
Adding @OverrideNo — it would not compile; overloads do not override

The real fix is not to write this at all. Overloading on a type and its subtype is a trap: the code reads as though it dispatches on the object, and it does not. A reader has to know the static type of every argument to predict behaviour.

// Polymorphism — resolved at RUN time, from the object
abstract class Animal { abstract void eat(); }
class Dog extends Animal { @Override void eat() { print("dog"); } }

pet.eat();      // "dog", regardless of the declared type

If the behaviour genuinely belongs to the feeder rather than the animal — so it cannot be a method on Animal — then the honest options are distinct method names, or a visitor. Both are more verbose and neither lies about when the decision is made.

6 (hard): Explain to a colleague why this compiles, runs, and is still broken. 
class Base    { void handle(Object o) { print("base"); } }
class Derived extends Base {
    void handle(String s) { print("derived"); }
}

Base b = new Derived();
b.handle("hello");
Solution

It prints "base". The author intended an override and wrote an overload.

  handle(Object)  in Base
  handle(String)  in Derived    -> DIFFERENT parameter type, so a
                                   DIFFERENT signature, so not an
                                   override at all.

  Derived now has TWO methods: the inherited handle(Object) and its own
  handle(String).

  The call is through a Base reference, so the compiler only knows
  about handle(Object) and binds to it. At run time, dynamic dispatch
  looks for an override of handle(Object) — Derived does not have one.
  So Base's version runs.

Why this is worse than a plain mistake: it is invisible in three ways at once. It compiles. It runs without error. And the "derived" method exists in the source, so a reader reasonably assumes it is being used — the bug is the absence of a call, which nothing shows you.

@Override would have caught it at compile time, which is the whole argument for the annotation: it is not documentation, it is a check on your intent. It fails here with "method does not override or implement a method from a supertype".

class Derived extends Base {
    @Override void handle(Object o) { print("derived"); }
}

And if the narrower type is genuinely wanted, the override must accept Object and narrow inside — Java does not permit an override to require a more specific parameter type, because that would break the substitutability the supertype promises:

@Override void handle(Object o) {
    if (o instanceof String s) { … }     // pattern matching, Java 16+
    else super.handle(o);
}

The general rule this illustrates: parameter types may not be narrowed on an override (that would be unsafe), return types may be narrowed (covariant returns are safe), and access may be widened but never restricted. All three follow from the same requirement — a Derived must be usable everywhere a Base is expected.

🎯 Key Takeaways

  • A signature is the name plus parameter types — not the return type, parameter names, or throws clause.
  • Overloading is resolved at compile time from declared types; overriding at run time from the object. Same variable, opposite rules.
  • Overload resolution is widening, then boxing, then varargs — so f(42) picks f(long) over f(Integer).
  • Adding an overload can silently rebind existing call sites on recompilation, with no edit at those sites.
  • Never overload on a type and its subtype — the code reads as if it dispatches on the object, and it does not.
  • @Override is a check, not decoration. It catches misspellings, wrong parameter types, and removed supertype methods.
  • An accidental overload instead of an override compiles, runs, and is never called — the bug is an absence, which nothing shows you.
  • Parameter types may not be narrowed on an override; return types may be, and access may be widened.
  • Varargs is a real array inside the method, resolved last, and f(null) means a null array rather than one null element.
  • Java has no tail-call optimisation, so recursion is bounded by depth — roughly 5,000–15,000 frames.
  • Recurse when depth is bounded by the structure, iterate when it is bounded by the data.
  • Recursion over untrusted nested input is a denial-of-service vector and needs an explicit depth cap.
  • Two adjacent parameters of the same type is a latent defect — distinct types make the mistake a compile error.
  • Name what, not how. findUser survives a caching change; getUserFromDatabase does not.
  • One level of abstraction per method — mixing a summary with implementation detail is what makes methods hard to read, more than length.
  • Command or query, not both. Callers assume queries are free and repeatable.
