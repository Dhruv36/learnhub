Virtual Threads (Project Loom) Concurrency

What you'll master: the problem Loom actually solves — blocking code was never the problem; blocking an OS thread was — and why async/reactive bought throughput by destroying stack traces, debuggers and profilers; what a virtual thread is (a continuation on the heap, mounted on a carrier thread) and what mount/unmount means at each blocking point; measured costs against platform threads; why you must never pool virtual threads and never size them; pinning — which constructs pin the carrier, how to detect it, and which JDK version fixed most of it; ThreadLocal's memory cost at a million threads and ScopedValue; structured concurrency; and the bottleneck virtual threads expose rather than fix. Prerequisites: Threads and Executors.

Part 1 — The Problem Loom Solves

  THREAD-PER-REQUEST IS THE MODEL EVERYONE WANTS TO WRITE:

    void handle(Request r) {
        User u    = userService.find(r.userId());   // blocks 50 ms
        Orders o  = orderService.list(u.id());      // blocks 80 ms
        respond(render(u, o));
    }

  Sequential, debuggable, a stack trace that names your business
  logic, a try/catch that works, a profiler that attributes time to
  the right method. Everything about it is good EXCEPT that each
  request holds an OS thread for 130 ms while doing no work.

  THE ARITHMETIC THAT KILLS IT (Little's Law):

    2,000 requests/sec × 0.13 s = 260 concurrent requests
    260 threads × 1 MB reserved stack = 260 MB — fine.

    20,000 requests/sec × 0.13 s = 2,600 concurrent
    ... and now you are at the practical platform-thread ceiling,
    with most of that memory holding stacks that are doing nothing
    but waiting for a socket.

  THE PRE-LOOM ANSWER WAS TO STOP BLOCKING:

    userService.findAsync(r.userId())
        .thenCompose(u -> orderService.listAsync(u.id())
            .thenApply(o -> render(u, o)))
        .exceptionally(this::handleError);

  This works and scales. It also costs you:

    STACK TRACES     the trace shows the executor internals, not
                     the call chain that led here
    DEBUGGING        you cannot step through a callback chain
    PROFILING        wall-clock time is spread across pool threads
    CONTROL FLOW     no try/catch across stages, no loops, no
                     early return
    COLOURED FNS     one async call forces every caller to become
                     async, all the way up

  THE INSIGHT: the problem was never blocking. It was blocking an
  OS THREAD, which is scarce. Make the thread cheap and the simple
  code becomes the scalable code.

  THAT IS ALL VIRTUAL THREADS ARE. Same Thread API, same blocking
  calls, same stack traces — a different implementation underneath.

Part 2 — What a Virtual Thread Is

  A VIRTUAL THREAD IS A CONTINUATION SCHEDULED BY THE JVM ONTO A
  SMALL POOL OF PLATFORM "CARRIER" THREADS.

    virtual threads   (millions)  ─┐
                                   ├─ scheduler: a ForkJoinPool,
    carrier threads   (≈ cores)   ─┘  parallelism = availableProcessors

  MOUNTING AND UNMOUNTING IS THE WHOLE MECHANISM:

    1. a virtual thread MOUNTS on a carrier and runs normally —
       its frames are on the carrier's real stack
    2. it hits a blocking call (socket read, sleep, lock, queue)
    3. the JVM COPIES its stack frames to the HEAP and UNMOUNTS it;
       the carrier is immediately free for another virtual thread
    4. when the operation completes, the thread is rescheduled and
       MOUNTS again — possibly on a DIFFERENT carrier
    5. its frames are copied back onto that carrier's stack

  So a blocking call blocks the VIRTUAL thread and releases the
  PLATFORM thread. That single sentence is the entire feature.

  WHAT WAS RETROFITTED TO UNMOUNT INSTEAD OF BLOCK:

    java.net sockets, java.nio channels, files (partly)
    Thread.sleep, Object.wait
    LockSupport.park — so ReentrantLock, BlockingQueue,
        CompletableFuture.get, Semaphore, CountDownLatch all work
    Selector, InputStream/OutputStream on sockets

  WHAT DOES NOT UNMOUNT — see Part 4 on pinning.

  MEASURED COSTS:

                       platform            virtual
    creation           ~50-100 µs          ~1 µs
    memory             ~1 MB reserved      ~200-800 bytes initially,
                                           stack grows on the heap
    context switch     ~1-10 µs (kernel)   ~100-200 ns (user space)
    practical count    a few thousand      MILLIONS

  THE APIS:

    Thread.ofVirtual().name("w-", 0).start(runnable);
    Thread.startVirtualThread(runnable);

    // the one you will actually use:
    try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
        for (Task t : tasks) exec.submit(() -> handle(t));
    }   // close() waits for all tasks — it is AutoCloseable

  Virtual threads are ALWAYS daemon threads and their priority is
  fixed; setDaemon(false) and setPriority are no-ops. They do not
  keep the JVM alive, so you must join or use the executor's
  close().

Part 3 — Do Not Pool Them, Do Not Size Them

  THIS IS THE MOST COMMON MISTAKE, AND IT IS A CATEGORY ERROR:

    // ❌ pointless and harmful
    ExecutorService e = Executors.newFixedThreadPool(200, virtualFactory);

  A POOL EXISTS TO AMORTISE AN EXPENSIVE RESOURCE. Virtual threads
  cost about a microsecond and a few hundred bytes. Pooling them
  reintroduces exactly the bottleneck you removed: 200 concurrent
  tasks maximum, and a queue behind it.

    // ✓ one virtual thread per task, unbounded
    Executors.newVirtualThreadPerTaskExecutor()

  THE SAME LOGIC KILLS SEVERAL OTHER HABITS:

    sizing by cores        meaningless — they are not CPU-bound
                           and do not occupy a carrier while blocked
    reusing a thread       nothing to reuse; create a new one
    thread-local caching   see Part 5 — now a memory problem
    "warm up the pool"     nothing to warm

  BUT UNBOUNDED THREADS DOES NOT MEAN UNBOUNDED EVERYTHING. The
  limit has to move somewhere real:

    // bound the thing that is ACTUALLY scarce
    private final Semaphore dbPermits = new Semaphore(50);

    void handle(Request r) {
        dbPermits.acquire();
        try { db.query(r); } finally { dbPermits.release(); }
    }

  THIS IS THE IMPORTANT SHIFT IN THINKING. With platform threads,
  the pool size was an accidental limiter on everything downstream.
  Remove it and you can open 10,000 concurrent database connections
  — which the database will refuse or, worse, accept and collapse
  under.

  So: bound each downstream resource explicitly, with a Semaphore or
  the connection pool's own limit, rather than relying on a thread
  pool to do it by accident. The bound is now visible and per-
  resource instead of global and implicit — which is better, but you
  have to write it.

  WHERE VIRTUAL THREADS DO NOT HELP AT ALL:

    CPU-BOUND WORK. You still have N cores. A million virtual
    threads doing matrix multiplication is slower than N platform
    threads, because you added scheduling overhead and cache
    pressure for nothing. Use a fixed pool sized to cores, or
    parallel streams, for computation.

Part 4 — Pinning

  A PINNED VIRTUAL THREAD CANNOT UNMOUNT, SO IT HOLDS ITS CARRIER
  WHILE BLOCKED. Enough pinned threads and you have starved the
  carrier pool back down to a platform-thread system.

  TWO CAUSES:

    1. BLOCKING INSIDE A synchronized BLOCK OR METHOD
       (in JDK 21-23 — see the version note below)
    2. A NATIVE FRAME on the stack (JNI, some Foreign Function
       calls)

  THE CLASSIC OFFENDER:

    synchronized void save(Order o) {
        db.write(o);          // blocks; carrier is PINNED
    }

  With 200 carriers and 200 threads in that method, throughput
  collapses to 200 concurrent operations — exactly the behaviour you
  adopted virtual threads to escape, but harder to see.

  THE FIX IS ReentrantLock, WHICH PARKS PROPERLY:

    private final ReentrantLock lock = new ReentrantLock();

    void save(Order o) {
        lock.lock();
        try { db.write(o); } finally { lock.unlock(); }
    }

  DETECTING IT:

    -Djdk.tracePinnedThreads=short     stack trace when pinned
    -Djdk.tracePinnedThreads=full      full trace

  or a JFR recording — jdk.VirtualThreadPinned events, which is the
  better option in production because the system property has real
  overhead.

  *** VERSION MATTERS A LOT HERE ***

    JDK 21-23   synchronized pins the carrier. Audit your code and
                your DEPENDENCIES (old JDBC drivers and connection
                pools are the usual culprits).
    JDK 24+     JEP 491 made object monitors unmount properly, so
                ordinary synchronized blocking no longer pins.
                Native frames still do.

  So advice written in 2023 about rewriting every synchronized block
  is obsolete on a current JDK. On 21 — the LTS most teams are
  actually on — it is still correct.

  THE PRACTICAL AUDIT, in priority order:
    1. synchronized methods that do I/O (on JDK < 24)
    2. JDBC drivers and connection pools — check versions
    3. any library doing JNI on a request path
    4. object pools generally, which often synchronize on checkout

Part 5 — ThreadLocal and ScopedValue

  ThreadLocal STILL WORKS. That is deliberate — a mountain of
  existing code (MDC logging, security contexts, transaction
  contexts) depends on it, and breaking it would have blocked
  adoption.

  BUT THE ECONOMICS CHANGED COMPLETELY:

    200 platform threads × 1 KB of thread-locals   =  200 KB
    1,000,000 virtual threads × 1 KB              =  1 GB

  With platform threads, a thread-local was implicitly shared across
  thousands of requests. With thread-per-request virtual threads,
  every request gets its own copy of everything.

  THREE PROBLEMS WITH ThreadLocal IN THIS WORLD:

    UNBOUNDED LIFETIME  it lives until the thread dies or you
                        remove() — and nobody remembers to remove()
    MUTABLE             any code can set() it, so you cannot reason
                        about its value
    UNCONSTRAINED COPY  InheritableThreadLocal copies the whole map
                        to every child thread

  ScopedValue (Java 21 preview, 25 final) IS THE REPLACEMENT:

    private static final ScopedValue<User> CURRENT =
        ScopedValue.newInstance();

    ScopedValue.where(CURRENT, user).run(() -> {
        handleRequest();          // CURRENT.get() works in here
    });                           // and is gone out here

  THE DIFFERENCES THAT MATTER:

    IMMUTABLE          bound once, cannot be reassigned by callee
    BOUNDED LIFETIME   automatically unbound when the block exits —
                       no leak, no remove()
    CHEAP INHERITANCE  child threads in a StructuredTaskScope share
                       the binding by reference, not by copying
    NO REMOVE NEEDED   which removes the classic pooled-thread leak

  THE POOLED-THREAD LEAK IT FIXES, for reference:

    executor.submit(() -> {
        CONTEXT.set(userSpecificData);
        // no remove() — the pooled thread keeps this ALIVE, and
        // the NEXT request on this thread SEES IT
    });

  That bug is both a memory leak and a security problem (one user's
  context visible to another). With ScopedValue it cannot happen,
  because the binding ends with the block.

Part 6 — Structured Concurrency and What Changes

  THE UNSTRUCTURED PROBLEM:

    Future<User>   u = exec.submit(() -> findUser(id));
    Future<Orders> o = exec.submit(() -> findOrders(id));
    return new Page(u.get(), o.get());

  If findUser throws, u.get() throws — and the ORDERS TASK KEEPS
  RUNNING, holding a connection, for nothing. If the caller is
  cancelled, neither task learns. Task lifetimes are unrelated to
  the code structure that created them.

  StructuredTaskScope TIES THEM TO A BLOCK:

    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        Subtask<User>   u = scope.fork(() -> findUser(id));
        Subtask<Orders> o = scope.fork(() -> findOrders(id));

        scope.join();                  // wait for both
        scope.throwIfFailed();         // propagate the first failure

        return new Page(u.get(), o.get());
    }   // close() GUARANTEES no subtask outlives the block

  WHAT THIS BUYS:

    ERROR PROPAGATION   one failure cancels the siblings
                        immediately — no orphaned work
    CANCELLATION        cancelling the parent interrupts children
    NO LEAKS            close() cannot return with a live subtask
    OBSERVABILITY       thread dumps show the parent/child tree, so
                        "what is this thread doing" has an answer

  ShutdownOnSuccess is the other policy — first result wins, the
  rest are cancelled. That is the hedged-request pattern in four
  lines.

  WHAT VIRTUAL THREADS DO NOT FIX — AND WHAT THEY EXPOSE:

    Removing the thread-pool limit removes an ACCIDENTAL rate
    limiter that was protecting everything downstream. Teams migrate
    and immediately see:

      - connection pool exhaustion (now 10,000 threads want a
        connection instead of 200)
      - downstream services rate-limiting or falling over
      - database connection limits hit
      - memory pressure from a million in-flight request objects

    None of these are virtual-thread bugs. They are pre-existing
    limits that the thread pool was hiding. The migration work is
    mostly making those limits EXPLICIT — a Semaphore per resource,
    a properly sized connection pool, a real rate limiter.

  THE HONEST SUMMARY: virtual threads make blocking code scale, and
  hand you back the responsibility for bounding concurrency that the
  pool was doing by accident.

Interview Questions

Beginner: What is a virtual thread?

A thread scheduled by the JVM rather than the OS. It runs on a small pool of platform "carrier" threads, and when it hits a blocking call the JVM copies its stack frames to the heap and unmounts it — freeing the carrier for another virtual thread immediately.

So a blocking call blocks the virtual thread and releases the platform thread. That one sentence is the whole feature.

PlatformVirtual
Memory~1 MB reserved~200–800 bytes, growing on the heap
Creation~50–100 µs~1 µs
Practical countThousandsMillions

The API is deliberately unchanged — Thread, Runnable, try/catch, real stack traces. Existing blocking code runs on them without modification, which is what makes adoption cheap.

Beginner: Why should you not pool virtual threads?

Because a pool exists to amortise an expensive resource, and virtual threads are not expensive — about a microsecond and a few hundred bytes each.

Pooling them reintroduces exactly the bottleneck you adopted them to remove: newFixedThreadPool(200, virtualFactory) caps you at 200 concurrent tasks with a queue behind it, which is what a platform-thread pool already did.

Executors.newVirtualThreadPerTaskExecutor()   // one per task

The same reasoning removes several other habits: sizing by core count is meaningless because a blocked virtual thread occupies no carrier; there is nothing to "warm up"; and reusing a thread saves nothing.

But unbounded threads is not unbounded everything. The limit has to move to whatever is actually scarce — a Semaphore around the database, or the connection pool's own cap — because a thread pool was previously doing that bounding by accident.

Mid: What is pinning and how do you deal with it?

A pinned virtual thread cannot unmount, so it holds its carrier platform thread while blocked. Enough of them and you are back to a platform-thread system with a carrier-count concurrency cap — but harder to see.

Two causes: blocking inside a synchronized block or method (on JDK 21–23), and a native frame on the stack from JNI or some Foreign Function calls.

synchronized void save(Order o) { db.write(o); }   // pins

// fix: ReentrantLock parks properly
void save(Order o) {
    lock.lock();
    try { db.write(o); } finally { lock.unlock(); }
}

Detection: -Djdk.tracePinnedThreads=short prints a stack trace when it happens; in production prefer JFR's jdk.VirtualThreadPinned events, since the system property has real overhead.

The version caveat matters more than the technique. JEP 491 in JDK 24 made object monitors unmount properly, so ordinary synchronized blocking no longer pins. Advice from 2023 about rewriting every synchronized block is obsolete on a current JDK — and still correct on 21, which is the LTS most teams are on.

When auditing, look first at synchronized methods doing I/O, then at JDBC drivers and connection pools, then at anything using JNI — dependencies are the usual culprits, not your own code.

Mid: How do virtual threads compare with reactive programming?

They target the same problem — not occupying an OS thread while waiting — and reach similar throughput. They differ entirely in what they cost you to write and operate.

ReactiveVirtual threads
Code shapeCallback/operator chainsOrdinary sequential code
Stack tracesExecutor internalsYour call chain
DebuggingCannot step throughNormal stepping
ProfilingTime spread across pool threadsAttributed correctly
Function colouringAsync infects every callerNone
BackpressureBuilt inYou must add it
Streaming operatorsRichNot the model

Virtual threads win for request/response services, which is most server code. You keep readable code and get the scalability, and the migration is often a configuration change.

Reactive still wins for genuine stream processing — data pipelines with backpressure, windowing, merging and complex operator composition. That is what the model was designed for, and virtual threads do not replace it.

The honest recommendation: do not start a new rewrite to reactive for throughput alone. If you already have a reactive codebase that works, migrating it back is rarely worth the churn.

Senior: You migrate a service to virtual threads and it gets worse. What happened?

Most likely one of four things, and only the first is a virtual-thread problem.

1. Pinning. On JDK 21–23, synchronized around I/O holds the carrier, so effective concurrency collapses to the carrier count. Check with jdk.tracePinnedThreads or JFR, and look at dependencies — old JDBC drivers and connection pools are the usual source.

2. You removed a rate limiter you did not know you had. This is the most common one. The old 200-thread pool was implicitly capping concurrency at every downstream service. Now 10,000 threads want a database connection, and the pool exhausts, the database refuses connections, or the downstream service starts rate-limiting. Nothing is broken — a hidden limit became visible.

3. The work is CPU-bound. Virtual threads add scheduling overhead and cache pressure while the core count is unchanged. Computation belongs on a fixed pool sized to cores.

4. ThreadLocal memory. What was 200 copies is now one per in-flight request. A 1 KB context across a million threads is a gigabyte.

How I would diagnose it: a thread dump first — pinned carriers versus threads waiting on a connection pool are visually different and point at (1) versus (2). Then JFR for pinning events and allocation. Then check whether CPU is saturated, which separates (3) from everything else.

The fix for the common case is to make the bounds explicit: a Semaphore per scarce downstream resource, a correctly sized connection pool, and a real rate limiter. That work is not overhead — it replaces an accidental global limit with intentional per-resource ones, which is strictly better once written.

Senior: What is structured concurrency and what problem does it solve?

It ties a subtask's lifetime to a lexical block, the way try/finally ties resource lifetime to a block. The problem it solves is that with a bare executor, task lifetimes have no relationship to the code that created them.

Future<User>   u = exec.submit(() -> findUser(id));
Future<Orders> o = exec.submit(() -> findOrders(id));
return new Page(u.get(), o.get());

If findUser throws, u.get() throws and the orders task keeps running — holding a connection to produce a result nobody will read. If the caller is cancelled, neither task learns.

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var u = scope.fork(() -> findUser(id));
    var o = scope.fork(() -> findOrders(id));
    scope.join();
    scope.throwIfFailed();
    return new Page(u.get(), o.get());
}   // close() cannot return with a live subtask

What it buys: a failure cancels the siblings immediately; cancelling the parent interrupts the children; no subtask can outlive the block; and thread dumps show the parent/child tree, so "what is this thread doing and who asked for it" has an answer.

ShutdownOnSuccess is the other policy — first result wins, the rest are cancelled — which makes the hedged-request pattern about four lines of code.

Why it needed virtual threads: forking a thread per subtask is only reasonable when a thread is nearly free. With platform threads you would be pooling, and pooling is what broke the lifetime relationship in the first place.

Status: still a preview API and it has been revised across releases, so check the shape for your JDK before depending on it.

1 (easy): What is wrong with this? 
ExecutorService exec = Executors.newFixedThreadPool(
    200, Thread.ofVirtual().factory());
Solution

It caps you at 200 concurrent tasks — the exact bottleneck virtual threads remove. A pool exists to amortise an expensive resource; a virtual thread costs about a microsecond and a few hundred bytes, so there is nothing to amortise.

try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Task t : tasks) exec.submit(() -> handle(t));
}   // close() waits for every task

Size the poolOne thread per task
Reuse threadsCreate a new one
Queue work behind the poolNo queue — every task starts immediately
Pool size limits downstream loadBound each resource explicitly

The last row is the one that bites. Removing the pool removes an accidental limiter on everything downstream, so add a Semaphore around the database or rely on the connection pool's own cap. The bound becomes visible and per-resource instead of global and implicit.

2 (easy): Why does this program print nothing? 
public static void main(String[] args) {
    Thread.startVirtualThread(() -> {
        System.out.println("working");
    });
}
Solution

Virtual threads are always daemon threads, so they do not keep the JVM alive. main returns immediately, the last non-daemon thread finishes, and the JVM exits — usually before the virtual thread has run.

// Option A — join it
Thread t = Thread.startVirtualThread(() -> System.out.println("working"));
t.join();

// Option B — the executor waits in close()
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    exec.submit(() -> System.out.println("working"));
}   // close() blocks until all tasks complete
PropertyVirtual thread
setDaemon(false)No-op — always daemon
setPriority(n)No-op
Keeps JVM aliveNo
NameEmpty by default — set one via Thread.ofVirtual().name(...)

Option B is the idiom to learn. ExecutorService is AutoCloseable from Java 19, and close() performs an orderly shutdown and waits — which makes try-with-resources the natural way to scope a batch of concurrent work.

3 (medium): This is slow on JDK 21 despite virtual threads. Why? 
public class OrderService {
    private final Connection conn;

    public synchronized void save(Order o) throws SQLException {
        try (var ps = conn.prepareStatement("INSERT ...")) {
            ps.setLong(1, o.id());
            ps.executeUpdate();        // blocks ~20 ms
        }
    }
}
Solution

Pinning. On JDK 21 a virtual thread blocked inside a synchronized method cannot unmount, so it holds its carrier for the full 20 ms. With carriers equal to core count, effective concurrency drops to the number of cores.

private final ReentrantLock lock = new ReentrantLock();

public void save(Order o) throws SQLException {
    lock.lock();                       // parks properly — unmounts
    try (var ps = conn.prepareStatement("INSERT ...")) {
        ps.setLong(1, o.id());
        ps.executeUpdate();
    } finally { lock.unlock(); }
}
StepFinding
Detect-Djdk.tracePinnedThreads=short, or JFR jdk.VirtualThreadPinned
Immediate fixReentrantLock instead of synchronized
On JDK 24+JEP 491 unmounts monitors — synchronized no longer pins
Better designWhy is there a lock at all?

The last row is the real answer. A single shared Connection guarded by a lock serialises every write regardless of threading model. A connection pool gives each thread its own connection and the lock disappears — which fixes throughput far more than the pinning fix does.

When auditing, start with dependencies. Old JDBC drivers and connection pools synchronize internally, and you cannot fix those with a code change — only by upgrading or moving to JDK 24+.

4 (medium): After migrating, the app throws CannotGetJdbcConnectionException under load. It never did before. Explain.
Solution

Nothing broke — a hidden limit became visible. The old 200-thread pool meant at most 200 requests ever wanted a connection at once, which happened to match the pool. With one virtual thread per request, 10,000 requests all ask simultaneously and the connection pool exhausts.

BeforeAfter
200 threads → ≤200 connection requests10,000 threads → 10,000 connection requests
Excess work queued at the thread poolExcess work fails at the connection pool
The bound was implicit and globalThe bound must be explicit and per-resource
private final Semaphore dbPermits = new Semaphore(50);

public Result query(Request r) throws InterruptedException {
    dbPermits.acquire();
    try { return jdbc.query(r); }
    finally { dbPermits.release(); }
}

Why a Semaphore rather than raising the pool size: the database has a hard connection limit and each connection costs it memory. Raising the pool moves the failure into the database, which is worse. The permit makes the wait happen in your process, where it is cheap and observable.

This is the central migration lesson. A thread pool was bounding every downstream resource by accident, with one number. Now each resource needs its own explicit bound — more code, but the limits are visible, tunable per dependency, and no longer coupled to each other.

Also worth adding: a timeout on acquire, so a saturated dependency produces a fast rejection instead of an unbounded queue of waiting requests.

5ThreadLocal usageMDC, security and transaction contexts now cost one copy per request
6CPU-bound pathsKeep them on a fixed pool sized to cores
7Object poolsOften synchronize on checkout — a pinning source, and usually unnecessary now

Steps 3 and 4 are where the work is. Add a Semaphore (with a timeout) around each scarce downstream resource so a saturated dependency produces fast rejections instead of an unbounded queue of waiting requests.

How to roll it out: staging first with the pinning trace on and a realistic load test — not a smoke test, since every problem here is load-dependent. Then a canary, watching connection-pool wait time, downstream error rates and heap. Keep the property as the rollback switch.

What to expect if it goes well: latency at high concurrency improves markedly because requests stop queueing for a thread; throughput at low concurrency is unchanged, since there was never a thread shortage there. If throughput does not move at all, you are probably CPU-bound or pinned — both of which the audit should have caught.

What not to do: rewrite blocking code "to take advantage of" virtual threads. Blocking code is the point. The only rewriting worth doing is replacing synchronized around I/O on JDK 21–23.

🎯 Key Takeaways

  • The problem was never blocking — it was blocking a scarce OS thread.
  • A virtual thread unmounts at a blocking call, freeing its carrier; that one sentence is the whole feature.
  • They cost ~1 µs and a few hundred bytes against ~50–100 µs and ~1 MB.
  • Never pool them — a pool amortises a cost that no longer exists and reimposes the cap you removed.
  • Never size them by cores; a blocked virtual thread occupies no carrier.
  • Unbounded threads is not unbounded everything — bound each scarce downstream resource with a Semaphore.
  • Pinning holds the carrier and collapses concurrency to the carrier count.
  • synchronized around I/O pins on JDK 21–23; JEP 491 fixed it in 24 — check your version before rewriting.
  • Native frames still pin regardless of version.
  • Detect pinning with JFR in production; the tracing system property has real overhead.
  • They do not help CPU-bound work — the core count is unchanged.
  • ThreadLocal still works but the economics changed: one copy per in-flight request instead of per pooled thread.
  • ScopedValue is immutable and automatically unbound, removing the pooled-thread context leak.
  • Virtual threads are always daemon and priority is a no-op — join, or use the executor's close().
  • Structured concurrency ties subtask lifetime to a block, cancelling siblings on failure and preventing orphaned work.
  • Migration mostly means making implicit limits explicit — the thread pool was rate limiting everything by accident.
