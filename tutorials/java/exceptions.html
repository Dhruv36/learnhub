Exceptions & Error Handling Core Libraries

What you'll master: what the Throwable hierarchy really encodes — not severity but who is expected to act; the honest case for and against checked exceptions, why no language since Java copied them, and why lambdas broke the model outright; the mechanics of catch/finally including finally silently eating a pending return or exception; try-with-resources and its getSuppressed channel; multi-catch and precise rethrow; what an exception costs (stack capture, not the throw) and why control-flow exceptions stay wrong once you make them free; helpful NPE messages in JDK 14+; and translating errors at layer boundaries. Prerequisites: Control Flow.

Part 1 — The Hierarchy, and Who Is Supposed to Handle What

  Throwable
  ├── Error                     THE JVM OR ENVIRONMENT IS BROKEN
  │   ├── VirtualMachineError
  │   │   ├── OutOfMemoryError
  │   │   └── StackOverflowError
  │   ├── LinkageError          NoClassDefFoundError, UnsatisfiedLinkError
  │   └── AssertionError
  └── Exception                 SOMETHING WENT WRONG IN YOUR PROGRAM
      ├── IOException                  ← CHECKED
      ├── SQLException                 ← CHECKED
      ├── InterruptedException         ← CHECKED
      └── RuntimeException             ← UNCHECKED, and all descendants
          ├── NullPointerException
          ├── IllegalArgumentException  (→ NumberFormatException)
          ├── IllegalStateException
          ├── IndexOutOfBoundsException
          ├── ClassCastException
          └── ConcurrentModificationException

  THE SPLIT IS NOT ABOUT SEVERITY. An OutOfMemoryError and a
  NullPointerException are both usually fatal to the request. What
  the hierarchy encodes is WHO IS EXPECTED TO ACT:

    Error              nobody — the assumptions your code runs on
                       are gone
    Checked Exception  the immediate caller — an anticipated
                       condition it could respond to
    RuntimeException   nobody at the point of failure. It means a
                       BUG, and the fix is a code change, not a
                       catch block

  TWO CATCH CLAUSES THAT ARE NOT THE SAME:

    catch (Exception e)   checked AND unchecked. NOT Error.
    catch (Throwable t)   Error too — including OutOfMemoryError.

  CATCHING Error IS ALMOST ALWAYS WRONG. The allocation that threw
  OutOfMemoryError may have been a tiny one while the real pressure
  is elsewhere; your handler probably needs to allocate (a log
  message, a string concat) and will throw again; and returning from
  the catch does not repair the heap. StackOverflowError is
  catchable in practice — recursive parsers do it — but the stack
  you return to is arbitrary.

  THE ONE DEFENSIBLE catch (Throwable) is the top of a worker loop
  or thread pool, where losing the thread silently stops all future
  work. It must LOG and RETHROW what it cannot classify.

Part 2 — Checked vs Unchecked: The Argument, Honestly

  JAVA RAN AN EXPERIMENT IN 1995 AND NOBODY REPEATED IT. Compiler-
  enforced checked exceptions shipped in exactly one mainstream
  language. What happened next is the evidence:

    C#      omitted them deliberately. Anders Hejlsberg's stated
            reasons were VERSIONING and SCALABILITY — the two below.
    C++     had exception specifications; deprecated in C++11,
            removed in C++17.
    Kotlin  runs on the JVM, sees the same exception objects, and
            treats every one of them as unchecked. So do Scala and
            Groovy.

  THE CASE FOR, AND IT IS REAL: the signature becomes documentation
  the compiler enforces. When Files.readAllBytes declares
  IOException, no caller can claim not to have known the disk can
  fail. Nobody has ever forgotten to consider file-not-found.

  THE CASE AGAINST — four failures, in order of damage:

  1. VERSIONING. Adding a checked exception to a published method
     breaks every caller at compile time. So library authors never
     add one; they pre-declare a broad type, which destroys the
     specificity the feature existed to provide.

  2. IT LEAKS THROUGH ABSTRACTION. A repository throwing
     SQLException forces its interface to declare SQLException,
     forcing every layer above to know a database exists. The escape
     hatch people take is `throws Exception`, which carries LESS
     information than no annotation at all.

  3. CALLERS SATISFY IT BY LYING. The demand is "handle or declare";
     the two cheapest ways to comply are

       catch (IOException e) { }                    // swallowed
       catch (IOException e) { throw new RuntimeException(e); }

     and both are in every large codebase. A rule routinely
     satisfied by a lie enforces nothing.

  4. LAMBDAS BROKE THE MODEL. No java.util.function interface
     declares a checked exception:

       interface Function<T, R> { R apply(T t); }      // no throws

     so this does not compile:

       paths.stream().map(Files::readAllBytes)      // ❌ IOException

     Workarounds: try/catch inside every lambda (unreadable); a
     parallel hierarchy of throwing functional interfaces (viral);
     or "sneaky throws" via an unchecked generic cast, which throws
     a checked exception the compiler cannot see. Lombok ships
     @SneakyThrows for exactly this. That a popular library exists
     to DEFEAT the feature is the clearest verdict available.

  THE HONEST POSITION: default new APIs to unchecked, document
  failures with Javadoc @throws, and use checked only where "the
  immediate caller must make a different decision" is a true
  statement about your design. The exception to that is
  InterruptedException, which should stay checked forever —
  ignoring it silently breaks cancellation across the whole
  program.
SituationChecked?Why

Object used in the wrong lifecycle stateNo — IllegalStateExceptionSame: fix the calling code

Part 3 — try/catch/finally and What finally Eats

  THE ORDERING RULES: the try body runs; the FIRST matching catch
  runs (source order, not specificity — a supertype before a subtype
  is a compile error, "already caught"); finally runs on EVERY path
  including return, break and continue; only then does the value or
  exception leave the method.

  TRAP 1 — A return IN finally DISCARDS A PENDING EXCEPTION.

    int f() {
        try { throw new IllegalStateException("boom"); }
        finally { return 42; }      // ❌ returns 42; "boom" is GONE
    }

  Not caught. Not logged. The exception object is abandoned when
  finally completes abruptly. break and continue out of a finally
  do the same. javac warns only under -Xlint:finally ("finally
  clause cannot complete normally"), which most builds never enable.

  TRAP 2 — THROWING IN finally REPLACES THE IN-FLIGHT EXCEPTION.

    try {
        parse(in);                 // throws ParseException("line 44")
    } finally {
        in.close();                // throws IOException("disk full")
    }
    // the caller sees IOException. ParseException never existed.

  This is the most common way a root cause disappears from a
  production log. The traditional "fix" is worse:

    } finally {
        try { in.close(); } catch (IOException ignored) { }   // ❌
    }

  Now close failures are invisible — which is how a BufferedWriter
  loses its last unflushed block and nobody notices for a month.
  try-with-resources exists to solve exactly this.

  TRAP 3 — THE RETURN VALUE IS CAPTURED BEFORE finally RUNS.

    int counter = 0;
    int f() {
        try { return counter; }    // the VALUE 0 is captured here
        finally { counter = 99; }
    }                              // f() returns 0

  But mutating what a returned reference POINTS AT is visible:

    List<String> f() {
        List<String> list = new ArrayList<>();
        try { return list; }
        finally { list.add("x"); }  // caller sees ["x"]
    }

  One rule covers both: the returned VALUE (for a reference, the
  pointer) is fixed at the return statement; the object it names is
  not.

  finally DOES NOT RUN when control never leaves the try:
  System.exit or Runtime.halt, a JVM crash or SIGKILL, an infinite
  loop or a blocking call that never returns, and a daemon thread
  when the last non-daemon thread exits. So it is right for
  releasing in-process resources and wrong as a durability
  guarantee.

Part 4 — try-with-resources and Suppressed Exceptions

  WHAT THE COMPILER GENERATES FOR try (InputStream in = open()) { … }
  is roughly:

    InputStream in = open();
    Throwable primary = null;
    try {
        …
    } catch (Throwable t) {
        primary = t;  throw t;
    } finally {
        if (primary != null) {
            try { in.close(); }
            catch (Throwable t2) { primary.addSuppressed(t2); }
        } else in.close();
    }

  FOUR GUARANTEES MANUAL CODE RARELY GETS RIGHT:

    1. close() runs on every path, including a return from inside.
    2. Resources close in REVERSE declaration order.
    3. They close BEFORE any catch or finally on the same try — so
       your handler sees a CLOSED resource. The manual version has
       this backwards.
    4. If the body threw AND close() threw, the BODY's exception is
       PRIMARY and close()'s is attached with addSuppressed().
       Neither is lost.

  REVERSE ORDER MATTERS BECAUSE RESOURCES DEPEND ON EACH OTHER:

    try (Connection c = ds.getConnection();
         PreparedStatement s = c.prepareStatement(SQL);
         ResultSet r = s.executeQuery()) { … }

    close order:  r, then s, then c
                  ^ the dependent dies first, so nothing closes a
                    statement out from under a live result set

  READING THE SUPPRESSED ONES — most people never do:

    catch (IOException e) {
        log.error("copy failed", e);
        for (Throwable s : e.getSuppressed())
            log.error("  ...and closing failed too", s);
    }

  printStackTrace already prints them indented under "Suppressed:".

  Since JAVA 9 an effectively final variable is enough:

    BufferedReader r = openReader();
    try (r) { … }                    // no redundant alias

  AutoCloseable VERSUS Closeable:

    Closeable extends AutoCloseable
      close() throws IOException     narrower, easier to catch
      contractually IDEMPOTENT       calling it twice is a no-op
    AutoCloseable
      close() throws Exception       any resource, not just I/O
      NOT required to be idempotent  — write yours idempotent anyway

  WHAT IT DOES NOT DO: it will not close what you did not declare.
  A resource created inside the block body is still on you, and
  lazy streams over files are the classic miss —

    Files.lines(path).forEach(…)      // ❌ leaks a file handle
    try (var lines = Files.lines(path)) { lines.forEach(…); }  // ✓
ConcernManual finally closetry-with-resources

Body exception vs close exceptionClose wins; the body's is lostBody wins; close is suppressed, not lost
Close failures visibleOnly if you do not swallow them — and everyone doesAlways, via getSuppressed()

Part 5 — Multi-catch, Precise Rethrow, and Never Losing the Cause

  MULTI-CATCH (Java 7) — one handler, several unrelated types:

    catch (IOException | SQLException e) {
        throw new ServiceException("loading order " + id, e);
    }

  THREE RULES PEOPLE TRIP OVER:
    a) e is IMPLICITLY FINAL — you cannot reassign it (a single-type
       catch parameter is not).
    b) The STATIC TYPE of e is the least upper bound of the
       alternatives, here Exception. Need getSQLState()? Separate
       catch.
    c) Alternatives may NOT be related by subclassing:
         catch (IOException | FileNotFoundException e)      // ❌

  MORE PRECISE RETHROW (Java 7) — the compiler analyses what the try
  block can ACTUALLY throw:

    void run() throws IOException, SQLException {   // ← not Exception
        try { doWork(); }                // declares IOE, SQLE
        catch (Exception e) {
            metrics.increment("failure");
            throw e;                     // compiler infers IOE | SQLE
        }
    }

  Before Java 7 this method had to declare `throws Exception`,
  poisoning every caller. The inference applies only while the catch
  parameter stays EFFECTIVELY FINAL.

  CHAINING — THE CAUSE IS THE ENTIRE DIAGNOSTIC:

    catch (SQLException e) {
        throw new OrderRepositoryException(
            "saving order " + orderId, e);          // ← pass e
    }

  Drop it and you lose the SQL state, the constraint name, the
  driver frame and the pool frame, leaving two words and a stack
  trace that starts in your own code:

    Caused by: java.sql.SQLIntegrityConstraintViolationException:
               Duplicate entry '88123' for key 'orders.PRIMARY'

  Every custom exception needs at minimum (String) and
  (String, Throwable). For a legacy type without a cause
  constructor, call initCause(e) once before throwing.

  MESSAGE QUALITY IS AN ENGINEERING DECISION:

    "An error occurred"                  useless
    "saving order 88123 to orders"       findable in a log search
    "connect to db-3:5432 timed out
     after 5000ms (pool 20/20 busy)"     diagnosable without a repro

  Include IDENTIFIERS and MEASUREMENTS, not adjectives — and never
  secrets or tokens, because an exception message ends up in a log
  an entire ops team can read.

Part 6 — What Exceptions Actually Cost

  "EXCEPTIONS ARE SLOW" IS TRUE OF ONE STEP, NOT THE MECHANISM.
  Allocating the object is ordinary (~10–20 ns) and throwing plus
  unwinding to the handler is comparable to a megamorphic virtual
  call (~20–50 ns). fillInStackTrace() is where the money goes:
  ~1–10 µs, roughly LINEAR IN STACK DEPTH. Formatting and printing
  the trace is worse still, ~10–100 µs plus a String per frame.

  WHAT MAKES IT VARY: depth dominates. The same throw at depth 8 and
  depth 300 differ by more than 10x, and a Spring/Hibernate request
  stack is routinely 80–150 frames — which is exactly why the
  microbenchmark said it was fine.

  REMOVING THE CAPTURE — the Java 7+ constructor is the clean way:

    class Signal extends RuntimeException {
        Signal(String m) { super(m, null, false, false); }
        //                            ^^^^^  ^^^^^
        //           enableSuppression ─┘        └─ writableStackTrace
    }

  The pre-7 idiom does the same:

    @Override
    public synchronized Throwable fillInStackTrace() { return this; }

  Pre-allocate a singleton on top of that and you are at ~20 ns with
  zero allocation. Netty, Jackson and Spring's internal flow-control
  exceptions all do this.

  THE JIT DOES IT FOR YOU, AND IT BITES: after the same implicit
  exception site has been hit thousands of times, HotSpot's
  FAST-THROW replaces it with a pre-allocated instance carrying NO
  message and NO stack trace. It applies to NullPointerException,
  ArrayIndexOutOfBoundsException, ArithmeticException,
  ClassCastException and ArrayStoreException. The symptom is a log
  full of a bare exception name with nothing under it, appearing
  precisely when the failure became frequent enough to matter. While
  diagnosing: -XX:-OmitStackTraceInFastThrow

  EXCEPTIONS FOR CONTROL FLOW STAY WRONG EVEN WHEN FREE:
    a) The jump is INVISIBLE at the call site.
    b) NOTHING forces a handler to exist — a missing catch is a
       runtime discovery, unlike a missing switch branch.
    c) It COMPETES WITH REAL ERRORS: once "not found" is an
       exception, the catch that handles it also catches the
       connection reset.
    d) BETTER TOOLS EXIST — Optional, a sealed result type, a
       boolean.
  THE TELL: if the "exceptional" branch fires on more than a few
  percent of calls, it is not exceptional. Parsing a CSV column with
  Integer.parseInt and catching NumberFormatException 40% of the
  time is the classic; return an OptionalInt instead.

  HELPFUL NPE MESSAGES — JEP 358, JDK 14, ON BY DEFAULT SINCE 15:

    a.b.getC().name = "x";

    JDK 13:  java.lang.NullPointerException
                     at Prog.main(Prog.java:5)
             // which of the three dereferences? unknowable

    JDK 15+: java.lang.NullPointerException: Cannot assign field
             "name" because the return value of "B.getC()" is null

  On throw, the JVM re-reads the bytecode at the failing index and
  reconstructs the expression that produced null. It costs NOTHING
  until an NPE is thrown. Two limits: LOCAL VARIABLE NAMES appear
  only if the class carries debug info (-g, the Maven/Gradle
  default) — otherwise you get "<local4>" — and it cannot help
  once fast-throw has stripped the exception.

Part 7 — Your Own Exceptions, and Handling at Boundaries

  WHEN A CUSTOM EXCEPTION EARNS ITS PLACE — it must pass at least
  one of these:
    1. Does some caller CATCH THIS SPECIFICALLY, and not its
       siblings? If every handler is `catch (Exception e) { log;
       return 500; }`, a new type adds a file and no information.
    2. Does it CARRY DATA the handler needs — an accountId, a
       retryAfter, a field name? A message the handler must parse is
       not carrying data.
    3. Does the NAME say something the message cannot? Types are
       greppable and switchable; messages are not.

  WHAT TO PUT IN IT — structured fields, not prose:

    public class InsufficientFundsException extends RuntimeException {
        private final String accountId;
        private final BigDecimal shortfall;

        public InsufficientFundsException(String id, BigDecimal s) {
            super("account " + id + " short by " + s);
            this.accountId = id;  this.shortfall = s;
        }
        public String accountId()      { return accountId; }
        public BigDecimal shortfall()  { return shortfall; }
    }

  The handler renders "you need £12.40 more" by calling shortfall(),
  not by parsing English out of getMessage().

  MAKING IT CHECKED IS A DESIGN STATEMENT, NOT A SAFETY MEASURE: it
  forces EVERY caller, forever, to write a catch or a throws. Choose
  it only when you can name two callers that would legitimately
  respond differently.

  TRANSLATE AT LAYER BOUNDARIES:

    ┌───────────────────────────────────────────────────────────┐
    │ HTTP / controller  maps DomainException → status codes;   │
    │                    everything else → 500. LOGS HERE.      │
    ├───────────────────────────────────────────────────────────┤
    │ Service            OrderNotFound, InsufficientFunds —     │
    │                    the domain's own vocabulary            │
    ├───────────────────────────────────────────────────────────┤
    │ Repository         catch SQLException →                   │
    │                    throw RepositoryException(msg, e)      │
    ├───────────────────────────────────────────────────────────┤
    │ JDBC driver        SQLException, vendor error codes       │
    └───────────────────────────────────────────────────────────┘

  Each layer converts to its own vocabulary AND KEEPS THE CAUSE. If
  SQLException reaches the controller, your HTTP contract now
  includes your database vendor.

  LOG IN EXACTLY ONE PLACE — the outermost handler. Everywhere else
  either HANDLES or RETHROWS, never both. Catch-log-rethrow produces
  the same failure four times at four levels, which makes error
  counts meaningless and alerts useless.

  FAIL FAST ON PROGRAMMING ERRORS:

    Objects.requireNonNull(config, "config");
    if (n <= 0) throw new IllegalArgumentException("n must be > 0: " + n);

  The value is a stack trace pointing at the CONSTRUCTION site
  rather than an NPE five minutes later where the null has lost all
  provenance.

  RETRY ONLY WHEN ALL THREE HOLD:
    1. THE OPERATION IS IDEMPOTENT, or carries an idempotency key
       the server honours. Retrying a non-idempotent POST charges
       the card twice.
    2. THE FAILURE IS TRANSIENT — timeout, connection reset, 429,
       503. NEVER 400, 401, 404, a constraint violation, or any
       RuntimeException: the same input fails identically, N times.
    3. ATTEMPTS ARE BOUNDED AND BACKED OFF WITH JITTER.

    no backoff          retries pile onto a struggling service and
                        guarantee it never recovers
    fixed backoff       every client retries in lockstep — a
                        synchronised thundering herd every 2s
    exponential+jitter  sleep = random(0, min(cap, base · 2^attempt))

  Above that, a CIRCUIT BREAKER: after N consecutive failures, fail
  immediately for a cooldown. Retries without one turn a single dead
  dependency into thread-pool exhaustion in your own service,
  because each request now holds a thread for attempts × timeout.

Interview Questions

Beginner: What is the difference between a checked exception, an unchecked exception, and an Error?

The split is not about severity — it is about who is expected to act.

Checked exceptions are everything under Exception except RuntimeException and its descendants: IOException, SQLException, InterruptedException. The compiler forces the caller to catch or declare them. They model an anticipated external condition the caller might respond to.

Unchecked exceptions are RuntimeException and below. No compiler ceremony, because they model a bug — the fix is a code change, not a catch block.

Error is a sibling of Exception, not a subclass: OutOfMemoryError, StackOverflowError, NoClassDefFoundError. The assumptions the program runs on are gone; nobody is supposed to catch these.

The consequence people get wrong: catch (Exception e) does not catch Error, but catch (Throwable t) does — so a Throwable catch makes a dying JVM look like a handled request.

Beginner: What does finally guarantee, and when does it not run?

finally runs on every path out of the try block — normal completion, an exception, return, break, continue. That is the whole contract, and it is narrower than people assume.

It does not run when control never leaves the block: System.exit() or Runtime.halt(), a JVM crash or SIGKILL, an infinite loop or a blocking call that never returns, and a daemon thread when the last non-daemon thread exits.

The dangerous part is what it can destroy. A return inside finally discards a pending exception entirely, with no log and no trace:

int f() {
    try { throw new IllegalStateException("boom"); }
    finally { return 42; }        // returns 42, "boom" vanishes
}

An exception thrown from finally likewise replaces the one in flight, which is why closing resources there is a bad habit: a failing close() overwrites the real cause with a disk error.

One more detail that shows up in puzzles: the returned value is captured before finally runs, so mutating the local afterwards changes nothing — but mutating the object the reference names is visible to the caller.

Mid: Explain try-with-resources and suppressed exceptions. What does it fix?

It fixes the fact that the manual pattern destroys the exception you cared about.

try {
    parse(in);          // throws ParseException("line 44")
} finally {
    in.close();         // throws IOException("disk full")
}
// the caller sees IOException. ParseException is gone forever.

try-with-resources makes the body's exception the primary and attaches the close() failure via addSuppressed(), reachable through getSuppressed() and printed under "Suppressed:" in a stack trace. Nothing is lost.

It also guarantees the things people write incorrectly by hand: close on every exit path including a return from inside the block; reverse declaration order, so a ResultSet dies before its Statement; and closing before any catch or finally on the same try, so your handler sees a closed resource.

The resource must implement AutoCloseable. Closeable is the narrower I/O subtype whose close() throws IOException and is contractually idempotent; AutoCloseable.close() throws Exception and is not required to be — write yours idempotent regardless.

Since Java 9 an effectively final variable works directly: try (r) { … }. The gap to know is a resource created inside the block instead of the header — the classic miss is Files.lines(path), which leaks a file handle per call.

Mid: A review shows catch (Exception e) { log.error("failed: " + e.getMessage()); }. How many things are wrong?

Four, and each independently makes an incident harder to resolve.

ProblemConsequence
Concatenating getMessage() instead of passing the throwableThe stack trace and every Caused by are discarded — a sentence and no location
Catching ExceptionSweeps up a NullPointerException from your own code as if it were expected
Logging and continuingThe method returns normally, so the caller proceeds on state that was never produced
No context in the message"failed: null" tells the on-call engineer nothing about which order, user or request

The getMessage() point is the sharpest: for a bare NullPointerException on an older JDK this logs the literal string "failed: null", which is the least useful line in the history of logging.

The rule being violated is "log once, at the outermost handler". Every layer that catches, logs and continues turns one failure into several lines at several levels, so error counts stop meaning anything and alerts fire on the wrong number.

If the method genuinely can recover — a cache miss falling back to the origin — log at WARN with the throwable and say what the fallback was. Recovery is a different act from hiding.

Senior: Are exceptions expensive? Explain what actually costs, and when you would remove it.

The throw is cheap; capturing the stack trace is not. "Exceptions are 100x slower" is a statement about fillInStackTrace(), not about the mechanism. Allocation is ~10–20 ns, throwing and unwinding ~20–50 ns, capture ~1–10 µs, and formatting the trace for a log ~10–100 µs plus a String per frame.

Depth is the variable that matters. The same throw costs an order of magnitude more inside a 150-frame Spring request stack than in a microbenchmark — which is exactly why the microbenchmark said it was fine.

Removing the capture is a constructor argument since Java 7: super(msg, null, false, false) disables suppression and a writable stack trace; the pre-7 idiom is overriding fillInStackTrace() to return this. Pre-allocate a singleton on top and you are at ~20 ns with zero allocation, which is what Netty and Jackson do for internal signals.

The JIT already does this, and it hurts: after thousands of hits at one site, HotSpot's fast-throw replaces implicit exceptions (NPE, array index, class cast, arithmetic, array store) with a pre-allocated instance carrying no message and no frames. The symptom is a log full of bare java.lang.NullPointerException lines appearing precisely when the problem became frequent. Use -XX:-OmitStackTraceInFastThrow while diagnosing.

My recommendation: do not optimise exception cost — remove the exception. If a path throws often enough for the microseconds to matter, it is not an exceptional path and should return Optional or a result type. Stack-trace-free exceptions belong in framework-internal signalling, and every one you create is a diagnostic you have permanently given up.

Senior: Would you design a new API with checked exceptions? Argue both sides and give a recommendation.

The evidence is that the experiment failed. Java is the only mainstream language that ever shipped compiler-enforced checked exceptions, and none has copied it since — C# omitted them deliberately, C++ removed exception specifications in C++17, and Kotlin runs on the same JVM, sees the same exception objects, and treats every one as unchecked.

The case for is genuine. The signature becomes documentation the compiler enforces. Files.readAllBytes declaring IOException is real information at the call site, and nobody has failed to consider file-not-found because the code would not compile.

Failure of the modelWhat it forces
VersioningAdding one to a published method breaks every caller — so nobody ever does
Abstraction leakageSQLException in an interface makes every layer above know about JDBC
Suppression is cheapestAn empty catch or a blanket RuntimeException wrap satisfies the compiler and nothing else
LambdasNo java.util.function type declares one, so a checked method cannot be a method reference

The lambda point is decisive for new code. paths.stream().map(Files::readAllBytes) does not compile, and every workaround is bad: try/catch inside each lambda, a parallel hierarchy of throwing functional interfaces, or sneaky-throws. That Lombok ships @SneakyThrows — a feature whose entire purpose is defeating checked exceptions — is the clearest verdict the ecosystem has given.

My recommendation: default to unchecked. Document failure modes with @throws, define a small domain hierarchy, translate at layer boundaries, and let one top-level handler map types to responses. Use a checked exception only when you can name two callers that would legitimately do different things — and never on a method likely to be referenced from a lambda. The one place I would change nothing is InterruptedException: cancellation is the case where forcing the developer to look is worth all the friction.

🏋️ Graded Exercises

1 (easy): What does this return, and what happened to the exception? 
static int compute() {
    int result = 0;
    try {
        result = 10;
        throw new IllegalStateException("bad state");
    } finally {
        result = 20;
        return result;
    }
}
Solution

It returns 20, and the IllegalStateException is silently destroyed. Not caught, not logged, not printed — the exception object is abandoned the moment the finally block completes abruptly with a return.

static int compute() {
    try { return 10; }
    finally { cleanup(); }      // side effects only: no return, no throw
}

This is worse than an ordinary bug because it leaves no evidence. A swallowed exception in an empty catch at least leaves a catch block a code search can find; a return in finally looks like ordinary cleanup.

Note the mirror-image trap. Written as try { return result; } finally { result = 20; } the method returns 10 — the value is captured at the return statement, before finally runs. Same rule, opposite-looking answer, which is why both appear in interviews.

Compile with -Xlint:finally and javac reports "finally clause cannot complete normally". It is off by default, which is why this survives in real codebases.

3 (medium): This copy method loses exceptions and can leak. Fix it, and say exactly which exception the original reports. 
public void copy(File src, File dst) throws IOException {
    InputStream in = new FileInputStream(src);
    OutputStream out = new FileOutputStream(dst);
    try {
        in.transferTo(out);
    } finally {
        in.close();
        out.close();
    }
}
Solution

Leak: if new FileOutputStream(dst) throws — no permission, no parent directory, disk full — the already-open in is never closed, because it is outside the try.

Lost exception: if transferTo throws and in.close() also throws, the caller sees the close failure and the transfer failure is gone. Worse, if in.close() throws then out.close() never runs at all, so the destination is left open and unflushed.

public void copy(File src, File dst) throws IOException {
    try (InputStream in = new FileInputStream(src);
         OutputStream out = new FileOutputStream(dst)) {
        in.transferTo(out);
    }
}

4 (medium): Why can this worker never be shut down? 
while (running) {
    try {
        Task t = queue.take();
        t.run();
    } catch (InterruptedException e) {
        log.warn("interrupted");
    }
}
Solution

Because throwing InterruptedException clears the interrupt flag, and this catch discards the only remaining evidence that someone asked the thread to stop.

The sequence: another thread calls worker.interrupt(); the flag is set; queue.take() notices, clears the flag, and throws. The catch logs a warning, the loop continues, running is still true, and the next take() blocks forever. Every subsequent interrupt does exactly the same thing.

while (running && !Thread.currentThread().isInterrupted()) {
    try {
        Task t = queue.take();
        t.run();
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // RESTORE the flag
        break;                                // and stop
    } catch (RuntimeException e) {
        log.error("task failed, continuing", e);   // one bad task must
    }                                              // not kill the worker
}

Why restore the flag even though you also break: code above you — a thread pool, a shutdown hook, a parent task — checks isInterrupted() to decide whether the exit was a cancellation or a normal completion. Leaving it cleared makes an aborted shutdown look clean.

The second catch is the other half of the bug. Without it, one task throwing a RuntimeException escapes the loop and kills the worker permanently while the queue fills silently. A worker loop must survive its tasks. And running must be volatile, or the loop may never observe another thread setting it false.

5 (hard): This retry helper made an outage worse. Find every reason. 
public <T> T retry(Callable<T> op) {
    for (int i = 0; i < 10; i++) {

            return op.call();

            log.error("attempt " + i + " failed", e);
        }
    }

}
Solution
DefectWhat it does during an outage
No backoff at allTen attempts land in microseconds, multiplying load on a service that is already failing — the retry storm is the outage
Retries every ExceptionA 400, a constraint violation and an NPE are each retried ten times, guaranteed to fail identically

public <T> T retry(Callable<T> op, Predicate<Exception> retryable)
        throws Exception {
    Exception last = null;
    for (int attempt = 0; attempt < MAX_ATTEMPTS; attempt++) {
        try {
            return op.call();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw e;                                  // never retry
        } catch (Exception e) {
            if (!retryable.test(e)) throw e;          // fail fast
            last = e;
            if (attempt == MAX_ATTEMPTS - 1) break;
            long delay = ThreadLocalRandom.current().nextLong(
                1 + Math.min(CAP_MS, BASE_MS << attempt));  // full jitter
            log.warn("attempt {} failed, retrying in {}ms", attempt, delay, e);
            Thread.sleep(delay);
        }
    }
    throw new RetryExhaustedException(MAX_ATTEMPTS + " attempts failed", last);
}

Jitter is the part people omit and the part that matters most. With fixed or plain exponential backoff, every client that failed at the same moment retries at the same moment: the recovering service takes a synchronised wave at 2s, 4s, 8s and never gets a quiet window to drain its queue. Randomising over the whole interval spreads the same number of retries into a flat load it can absorb.

The idempotency requirement is not optional. The dangerous case is a timeout, where the request may have been fully applied server-side before the response was lost. Retrying is safe only with a client-generated idempotency key the server deduplicates on; otherwise the correct behaviour on a timeout is to fail and let reconciliation decide.

Still missing: a circuit breaker. Retries alone turn one dead dependency into thread-pool exhaustion in your own service, because every request now holds a thread for MAX_ATTEMPTS × timeout instead of one timeout. Use Resilience4j rather than writing this; the value here is knowing what it does for you.

6 (hard): Design the exception strategy for a payment service with an HTTP layer, a service layer and a gateway client. Decide checked vs unchecked and justify it.
Solution 
// ─── domain vocabulary: unchecked, structured ───
public class InsufficientFundsException extends PaymentException {
    private final String accountId;
    private final BigDecimal shortfall;
    public InsufficientFundsException(String id, BigDecimal s) {
        super("account " + id + " short by " + s);
        this.accountId = id;  this.shortfall = s;
    }
    public String accountId()     { return accountId; }
    public BigDecimal shortfall() { return shortfall; }
}

// ─── the boundary type: CHECKED, because callers must decide ───
public class PaymentDeclinedException extends Exception {
    private final DeclineCode code;          // enum, knows retryability
    public PaymentDeclinedException(DeclineCode code, Throwable cause) {
        super("declined: " + code, cause);
        this.code = code;
    }
    public DeclineCode code()  { return code; }
    public boolean retryable() { return code.retryable(); }
}

// ─── gateway client: translate, keep the cause ───
try {
    return http.post(request);
} catch (SocketTimeoutException e) {
    throw new GatewayUnavailableException(
        "gateway timeout after " + timeoutMs + "ms", e);
} catch (IOException e) {
    throw new GatewayUnavailableException("gateway I/O failure", e);
}
TypeChecked?Reasoning
PaymentDeclinedExceptionCheckedTwo callers genuinely differ: checkout shows a retry-card screen, subscription billing schedules a dunning email. Forcing the decision is the point
InsufficientFundsExceptionUncheckedA decline subtype handled by the same code; checked would add ceremony and no new decision

The HTTP layer is the only place that logs. One handler maps types to statuses: declined → 402, insufficient funds → 402 with a structured body built from shortfall(), gateway unavailable → 503 with Retry-After, everything unmapped → 500 with a generated incident id in both the response and the log line.

Structured fields are what make this work. The handler renders "you need £12.40 more" by calling shortfall(), not by parsing getMessage(). Any design where a handler regex-matches a message will break the first time someone improves the wording.

The one checked exception is a deliberate cost. It cannot be used from a lambda without wrapping, and adding a second checked type later would break callers. That is acceptable precisely because a declined payment is the one outcome the business must never let a caller ignore by accident — the only argument for a checked exception that has ever held up.

What must never leak past the service layer: SocketTimeoutException, the gateway SDK's own types, and anything with a card number or token in its message. Translate at each boundary, always with the cause attached.

🎯 Key Takeaways

  • The hierarchy encodes who should act, not severity — Error: nobody; checked: the caller; RuntimeException: a bug.
  • catch (Exception) misses Error; catch (Throwable) does not — which makes a dying JVM look handled.
  • Checked exceptions are an experiment no language repeated — versioning, abstraction leakage and lambdas each broke them independently.
  • No java.util.function interface declares a checked exception, so a checked method cannot be a method reference in a stream.
  • InterruptedException is the one worth keeping checked — swallowing it clears the flag and makes the thread unstoppable.
  • A return in finally silently discards a pending exception — no log, no trace, no evidence.
  • An exception thrown from finally replaces the one in flight, which is why closing resources there destroys root causes.
  • The returned value is captured before finally runs — mutating the local changes nothing; mutating the object it names is visible.
  • try-with-resources closes in reverse order and before catch, turning a close failure into a suppressed exception instead of a lost one.
  • Read getSuppressed() — the close failure that truncated your file is in there.
  • Multi-catch's parameter is implicitly final and typed as the least upper bound, and its alternatives may not be subtypes of one another.
  • Always pass the cause — new X("saving order 88123", e), never new X("save failed").
  • Stack capture is the cost, not the throw — ~1–10 µs for fillInStackTrace against ~20–50 ns to throw and unwind.
  • Fast-throw strips traces from hot implicit exceptions — bare NullPointerException lines mean -XX:-OmitStackTraceInFastThrow.
  • Exceptions for control flow stay wrong even when free — the jump is invisible and nothing forces a handler to exist.
  • Translate at every boundary, log once at the outermost handler, and retry only idempotent operations on transient failures with exponential backoff plus jitter.
