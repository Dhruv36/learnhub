Generics Core Libraries

What you'll master: erasure, and the fact that every generics oddity follows from it — type arguments exist at compile time and are gone at runtime, which is why you cannot write new T[], why List<String> and List<Integer> are the same class, and why instanceof List<String> will not compile; why generics are invariant — List<String> is not a List<Object>, deliberately, because arrays made the opposite choice and defer type errors to runtime; wildcards and the rule that tells you which to use — PECS: producer extends, consumer super — and what each one forbids; why an unchecked warning is a promise you are making to the compiler rather than noise to suppress; and why List<Object> and List<?> mean entirely different things. Prerequisites: Collections and Inheritance.

Part 1 — What Generics Buy

  BEFORE GENERICS — every retrieval was a cast and an act of faith

    List names = new ArrayList();
    names.add("Ada");
    names.add(42);                        // compiles fine
    String s = (String) names.get(1);     // ClassCastException, at
                                          // runtime, far from the bug

  WITH GENERICS

    List<String> names = new ArrayList<>();
    names.add("Ada");
    names.add(42);                        // ❌ COMPILE ERROR
    String s = names.get(0);              // no cast needed

  Two gains: the error moves from runtime to compile time, and the
  casts disappear from your code. The second is not cosmetic — every
  cast you write is a place the compiler stopped helping.

  WRITING A GENERIC CLASS

    class Box<T> {                 // T is a TYPE PARAMETER
        private T value;
        void set(T value) { this.value = value; }
        T get()           { return value; }
    }

    Box<String> box = new Box<>();     // T is String HERE

  AND A GENERIC METHOD — the parameter goes before the return type

    static <T> List<T> listOf(T a, T b) { … }

  CONVENTIONS: T type, E element, K key, V value, R result, N number.

Part 2 — Erasure

  THE COMPILER CHECKS TYPES, THEN THROWS THEM AWAY.

    List<String>   ->  List          at runtime
    List<Integer>  ->  List          the SAME class
    Box<T>         ->  Box, with T replaced by Object
    Box<T extends Number> -> T replaced by Number (the bound)

  and the compiler inserts casts at every call site where a type
  argument was used. So generics are a compile-time discipline over a
  runtime representation that has never heard of them.

  WHY IT WAS DONE THIS WAY: MIGRATION COMPATIBILITY. Java 5 needed
  generic code and pre-generic code to interoperate, and existing
  .class files to keep running unchanged. Erasure achieved that at the
  cost of nearly every limitation below.

  WHAT ERASURE MAKES IMPOSSIBLE:

    new T()                    no constructor is known at runtime
    new T[10]                  the array type is unknown
    instanceof List<String>    the argument is gone — will not compile
    catch (MyException<T> e)   exceptions must be reifiable
    static T field             T is per-instance, statics are per-class

  AND THE OVERLOAD THAT LOOKS LEGAL AND IS NOT:

    void f(List<String> l)     both erase to f(List), so this is
    void f(List<Integer> l)    a duplicate method — a compile error

  THE ONE PLACE THE TYPE SURVIVES: it is recorded in the class file's
  signature attribute for the compiler and for reflection, which is
  how Jackson can deserialise into List<User> when the type is
  declared on a FIELD. It is the type ARGUMENT of a runtime object
  that is lost, not the declaration.

Part 3 — Invariance

  List<String> IS NOT A List<Object>. This is deliberate.

    List<String> strings = new ArrayList<>();
    List<Object> objects = strings;      // ❌ COMPILE ERROR

  If it were allowed:

    objects.add(42);                     // legal — an Integer IS an
                                         // Object
    String s = strings.get(0);           // ClassCastException

  So invariance is what keeps the guarantee that a successfully
  compiled program has no type errors at runtime.

  CONTRAST WITH ARRAYS, WHICH CHOSE THE OTHER WAY:

    Object[] objects = new String[3];    // ✓ compiles — COVARIANT
    objects[0] = 42;                     // ArrayStoreException at
                                         // RUNTIME

  Arrays are covariant and reified: the array knows its real type, so
  the JVM checks every store. Generics are invariant and erased: there
  is nothing to check at runtime, so the check has to happen at
  compile time.

  Both make the same trade in opposite directions, and generics made
  the better one — a compile error beats an exception in production.

  THE PRACTICAL CONSEQUENCE: you cannot mix them.

    List<String>[] arr = new List<String>[10];   // ❌ generic array
                                                  //   creation

Part 4 — Wildcards and PECS

  Invariance is safe and restrictive. Wildcards restore flexibility
  where it is provably safe.

  ? extends T   — an UPPER bound. "Some unknown subtype of T."
                  You can READ T. You cannot WRITE anything.

  ? super T     — a LOWER bound. "Some unknown supertype of T."
                  You can WRITE T. You can only read Object.

  PECS: PRODUCER extends, CONSUMER super.

    void copy(List<? extends T> src,     // src PRODUCES T -> extends
              List<? super T>   dst)     // dst CONSUMES T -> super

  WHY READING IS SAFE AND WRITING IS NOT, for `? extends`:

    List<? extends Number> nums = new ArrayList<Integer>();

    Number n = nums.get(0);      // ✓ whatever it holds IS a Number
    nums.add(1);                 // ❌ it might be a List<Double>
    nums.add(1.0);               // ❌ it might be a List<Integer>
    nums.add(null);              // ✓ the one legal write — null is
                                 //   a member of every type

  The compiler knows the element type is SOME subtype of Number and
  cannot know WHICH, so no value is provably safe to add.

  AND THE MIRROR IMAGE, for `? super`:

    List<? super Integer> sink = new ArrayList<Number>();

    sink.add(42);                // ✓ an Integer fits any supertype
    Integer i = sink.get(0);     // ❌ it might hold a Double
    Object  o = sink.get(0);     // ✓ everything is an Object
DeclarationRead asWriteUse for
List<T>TTYou need both, and the exact type is known
List<? extends T>TNothing but nullA source you only read from
List<? super T>ObjectT and its subtypesA sink you only write to
List<?>ObjectNothing but nullYou care about the list, not its element type — size(), clear()
List<Object>ObjectAnythingA genuinely heterogeneous list — not the same as List<?>
🔑 List<Object> and List<?> are frequently confused and are opposites in the way that matters. List<Object> is a concrete type you can add anything to — but a List<String> cannot be passed to it, because of invariance. List<?> accepts any list and lets you add nothing, because the element type is unknown. So one is maximally permissive about contents and restrictive about arguments; the other is the reverse.

Part 5 — Bounded Type Parameters

  <T extends Number>              T must be Number or a subtype
  <T extends Comparable<T>>       T must be comparable to itself
  <T extends Number & Comparable<T>>   multiple bounds, class first

  static <T extends Comparable<T>> T max(List<T> list) {
      T best = list.get(0);
      for (T item : list)
          if (item.compareTo(best) > 0) best = item;   // compareTo is
      return best;                                     // available
  }                                                    // BECAUSE of
                                                       // the bound

  Without the bound, T erases to Object and compareTo does not exist.
  The bound is what gives the method something to call, and it also
  changes what T erases TO — here, Comparable rather than Object.

  BOUNDS vs WILDCARDS — the rule of thumb:

    a TYPE PARAMETER when the type appears more than once and the
    relationship matters:
        <T> void copy(List<T> src, List<T> dst)   // same T both sides

    a WILDCARD when it appears once and you do not need to name it:
        void print(List<?> list)                  // any list

  If a method signature mentions a type parameter exactly once, it can
  almost always be a wildcard — and should be, because it is simpler
  for the caller.

Part 6 — Unchecked Warnings and Heap Pollution

  AN UNCHECKED WARNING IS A PROMISE YOU ARE MAKING.

    @SuppressWarnings("unchecked")
    List<String> list = (List<String>) someRawList;

  The compiler is saying: "I cannot verify this cast, because the type
  argument is erased. If you are wrong, the failure will surface
  somewhere else entirely."

  And it does — as a ClassCastException at a LATER line, when
  something reads the list and hits the compiler-inserted cast:

    List<String> strings = getStrings();   // unchecked, and wrong
    for (String s : strings) { … }         // ClassCastException HERE

  The stack trace points at the loop, not at the cast that lied. That
  distance is what makes heap pollution expensive to debug.

  SO: suppress narrowly — on the smallest possible declaration, never
  a whole method or class — and add a comment saying WHY the cast is
  actually safe.

  VARARGS + GENERICS = THE SAME PROBLEM

    static <T> List<T> listOf(T... items)   // creates a T[] — which
                                            // erases to Object[]

  The compiler warns because the caller's array can be aliased as
  Object[] and polluted. @SafeVarargs asserts that the method only
  READS the array, which is the condition that makes it safe.

  RAW TYPES EXIST ONLY FOR MIGRATION

    List list = new ArrayList();     // raw — every check disabled

  A raw type turns off generic checking for the WHOLE expression, not
  just the missing argument. Treat any raw type in modern code as a
  bug.

Interview Questions

Beginner: What problem do generics solve?

They move type errors from runtime to compile time, and remove casts from your code.

Before generics, a collection held Object. You could add anything to it, and every retrieval needed a cast that might fail — so putting an Integer into a list of names compiled cleanly and threw a ClassCastException later, at the point of reading, far from the mistake.

With List<String> the compiler rejects the bad add at the line that causes it, and get returns a String with no cast.

The second benefit matters more than it looks: every cast you write is a place the compiler has stopped checking, so removing casts removes opportunities for that class of failure entirely.

Beginner: What is type erasure?

The compiler checks generic types and then removes them. At runtime, List<String> and List<Integer> are both just List — the same class, with the same bytecode — and the compiler has inserted casts wherever a type argument was used.

An unbounded type parameter erases to Object; a bounded one erases to its bound, so T extends Number becomes Number.

It was done for migration compatibility: Java 5 needed new generic code to interoperate with existing non-generic code and to run on class files compiled before generics existed. Erasure achieved that, at the cost of most of the restrictions people run into.

The nuance worth adding is that the type is not erased everywhere: it is recorded in the class file's signature attribute, which is how reflection and libraries like Jackson can see that a field is declared as List<User>. What is lost is the type argument of a runtime object.

Mid: Why is List<String> not a List<Object>?

Because it would break type safety, and the example is short enough to give in full.

List<String> strings = new ArrayList<>();
List<Object> objects = strings;    // if this were allowed…
objects.add(42);                   // …this is legal, Integer IS Object
String s = strings.get(0);         // …and this throws

Generics are therefore invariant: no relationship between String and Object implies any relationship between List<String> and List<Object>.

The instructive comparison is arrays, which made the opposite choice. Object[] o = new String[3] compiles, and the bad store throws ArrayStoreException at runtime instead. Arrays can do that because they are reified — the array knows its real element type — so the JVM checks every write.

Generics are erased, so there is nothing at runtime to check against; the check has to happen at compile time, and that requires invariance. Both designs trade the same thing in opposite directions, and generics made the better trade: a compile error is cheaper than a production exception.

Where you genuinely need flexibility, wildcards provide it safely — List<? extends Object> accepts any list, and correspondingly forbids adding to it.

Mid: Explain PECS.

Producer extends, Consumer super — a rule for choosing a wildcard based on how the parameter is used.

If a parameter produces values you read, use ? extends T. You can read them as T, because whatever the actual element type is, it is a subtype of T. You cannot add anything, because the compiler knows the list is of some subtype and not which — a List<? extends Number> might be a List<Integer>, so adding a Double would corrupt it.

If a parameter consumes values you write, use ? super T. You can add a T, because it fits any supertype of T. Reading gives you only Object, since the actual type could be anything above T.

The canonical signature is copy(List<? extends T> src, List<? super T> dst), and the JDK uses it throughout — Collections.copy, and Collectors.toMap's merge function.

The practical payoff is at the call site: without wildcards, a method taking List<Number> rejects a List<Integer> that would be perfectly safe to read from. So PECS is about accepting the arguments callers actually have.

And the corollary: if a type parameter appears only once in a signature, it can usually be a wildcard instead — simpler for the caller and no less safe.

Senior: What is heap pollution, and how do you avoid it?

Heap pollution is when a variable of a parameterised type refers to an object that is not of that type — a List<String> reference actually pointing at a list containing an Integer. Erasure makes it possible, because at runtime there is nothing to enforce the type argument.

It arises through unchecked casts and raw types, and the compiler warns precisely because it cannot verify them. An unchecked warning is best read as a promise you are making: "I know this is a list of strings even though you cannot prove it."

The reason it is expensive is the distance between cause and symptom. The bad cast does not fail. It fails later, when something reads the collection and hits a compiler-inserted cast — so the ClassCastException points at a loop that is entirely innocent, with nothing in the trace connecting it to the cast that lied.

Avoiding it: never use raw types; suppress warnings at the narrowest possible scope with a comment justifying the safety; and where a boundary genuinely produces untyped data — deserialisation, reflection, a legacy API — validate the elements at that boundary rather than asserting the type and hoping.

The related case is generic varargs. A T... parameter creates a T[] that erases to Object[], so the method can alias and pollute the caller's array. @SafeVarargs asserts that the method only reads it — which is the condition that makes it safe, and is your responsibility to honour.

The type-safe alternative when you must hold a type at runtime is a type token: carrying a Class<T> and using cast(), which turns the unchecked cast into a checked one that fails at the boundary.

Senior: What can you not do because of erasure, and what would reification change?

The restrictions all follow from the type argument not existing at runtime.

You cannot new T(), because no constructor is known. You cannot new T[10], because the array type is unknown — and arrays, being reified, insist on knowing. You cannot write instanceof List<String>, because there is nothing to test. You cannot overload on List<String> versus List<Integer>, because both erase to the same signature. You cannot have a generic exception type, since catch needs a reifiable type. And a static field cannot use the class's type parameter, since it is per-instance while statics are per-class.

Reification would remove all of those, and C# is the demonstration: type arguments are available at runtime, so new T(), typeof(T) and List<int> without boxing all work.

The cost is that C# could do it because generics arrived with a CLR change, in a younger ecosystem. Java chose erasure for migration compatibility — generic and non-generic code had to interoperate, and existing class files had to keep running. That was a genuinely valuable property at the time, and it is the reason for essentially every complaint about Java generics.

The workarounds are worth knowing: a Class<T> token passed explicitly, the "super type token" idiom that reads the type from an anonymous subclass's signature attribute — which is how Jackson's TypeReference and Guice's TypeLiteral work — and simply using List instead of arrays.

Project Valhalla may eventually bring specialised generics for value types, which would address the performance half — List<int> without boxing — though not the general reification question.

🏋️ Graded Exercises

1 (easy): Why does each line fail? 
class Box<T> {
    private T value;
    T[] makeArray()          { return new T[10]; }
    boolean isList(Object o) { return o instanceof List<T>; }
    static T shared;
}
Solution
LineWhy it fails
new T[10]Arrays are reified — they store their element type and check every write. T is erased, so there is no type to store
instanceof List<T>The type argument does not exist at runtime, so there is nothing to test. instanceof List<?> is legal
static T sharedT is bound per instance, and a static field belongs to the class — which T would it be?
// The array workaround, with a narrow suppression:
@SuppressWarnings("unchecked")   // safe: the array never escapes, and
T[] makeArray() {                // only ever holds T
    return (T[]) new Object[10];
}

// Better still — use a List, which has no such problem:
List<T> makeList() { return new ArrayList<>(); }

The array workaround has a real sharp edge: the object is genuinely an Object[], so returning it where a caller expects a String[] throws ClassCastException. That is why ArrayList keeps its array private as Object[] and casts on read rather than exposing it.

The pattern behind all three is that generics are a compile-time construct laid over a runtime that knows nothing about them — so anything requiring the type at runtime is unavailable.

2 (easy): Which compile, and why? 
List<Integer> ints = new ArrayList<>();

List<Number> a = ints;
List<? extends Number> b = ints;
List<? super Integer> c = ints;

b.add(1);
Number n = b.get(0);
Solution 
List<Number> a = ints;              ❌ generics are INVARIANT
List<? extends Number> b = ints;    ✓ Integer IS a subtype of Number
List<? super Integer> c = ints;     ✓ Integer is a supertype of itself

b.add(1);                            ❌ cannot write to ? extends
Number n = b.get(0);                 ✓ reading as Number is safe

Line 1 fails because invariance is what preserves type safety — if it compiled, you could a.add(3.14) and then read a Double out of a List<Integer>.

b.add(1) fails for a reason worth stating carefully: not because adding an Integer to this particular list is unsafe — it would be fine — but because the compiler only knows b holds some subtype of Number. It could equally be a List<Double>, so no value can be proven safe.

The one legal write is null, which is a member of every reference type.

And the mirror image applies to c: c.add(42) compiles, because an Integer fits any supertype — but c.get(0) gives you only an Object, since the list could be a List<Number> or a List<Object>.

3 (medium): Fix this signature so it accepts the calls below. 
static double sum(List<Number> numbers) {
    double total = 0;
    for (Number n : numbers) total += n.doubleValue();
    return total;
}

sum(List.of(1, 2, 3));           // List<Integer>
sum(List.of(1.5, 2.5));          // List<Double>
Solution

Both calls fail on the original, because generics are invariant: List<Integer> is not a List<Number>, even though every Integer is a Number.

static double sum(List<? extends Number> numbers) {
    double total = 0;
    for (Number n : numbers) total += n.doubleValue();
    return total;
}

This is PECS applied: the parameter is a producer — the method only reads from it — so the bound is extends. Reading as Number is safe because whatever the element type is, it is a subtype of Number.

What the wildcard costs you is the ability to add, which this method does not need. If it did — say it appended a total to the list — the signature would be wrong and the design would need rethinking, because a method cannot both accept any subtype and add to it safely.

SignatureAcceptsCan add
List<Number>Only List<Number>Yes
List<? extends Number>Any list of a Number subtypeNo
Collection<? extends Number>Also sets and queuesNo

The third row is worth reaching for — the method only iterates, so it does not need list semantics at all. Taking the weakest type that does the job is the same rule as programming to an interface, applied to the type argument as well as the type.

4 (medium): Write copy so that it accepts copying a List<Integer> into a List<Number>.
Solution 
static <T> void copy(List<? extends T> src, List<? super T> dst) {
    for (T item : src) dst.add(item);
}

List<Integer> ints = List.of(1, 2, 3);
List<Number> nums = new ArrayList<>();
copy(ints, nums);            // T is inferred as Integer

This is the canonical PECS signature. src produces values, so ? extends T lets it be a list of any subtype. dst consumes them, so ? super T lets it be a list of any supertype.

Signaturecopy(List<Integer>, List<Number>)
copy(List<T>, List<T>)Fails — one T cannot be both
copy(List<? extends T>, List<T>)Works here, and rejects copying into a List<Object>
copy(List<? extends T>, List<? super T>)Works, and accepts the widest set of callers

Why T is still needed rather than two independent wildcards: the two parameters must be related. Declaring copy(List<?> src, List<?> dst) would let you copy a list of strings into a list of integers, because nothing ties the two unknowns together. The type parameter is what expresses that connection.

The rule this illustrates: use a type parameter when the type appears more than once and the relationship matters; use a wildcard when it appears once and you never need to name it.

The JDK's own Collections.copy has exactly this signature, as does Collections.addAll and most of the Collectors API — recognising the shape makes those signatures readable rather than intimidating.

5 (hard): This compiles with a warning and throws somewhere else. Explain the distance between cause and symptom. 
@SuppressWarnings("unchecked")
static <T> List<T> cast(List<?> list) { return (List<T>) list; }

List<Object> raw = new ArrayList<>(List.of("a", 42, "c"));
List<String> strings = cast(raw);

System.out.println(strings.size());      // 3 — fine
for (String s : strings) { … }           // ClassCastException
Solution

The cast itself cannot fail, because at runtime a List<String> and a List<Object> are the same class. Erasure means there is nothing to check, so the cast is a no-op and the compiler's warning is the only signal.

The reference is now polluted: a variable declared List<String> refers to a list containing an Integer.

  strings.size()            -> 3
      no element is touched, so nothing fails

  for (String s : strings)  -> ClassCastException
      the compiler inserted (String) on each element; the second
      element is an Integer

The stack trace points at the loop, which is entirely innocent. Nothing in it mentions cast, the suppression, or the fact that the list was built elsewhere with mixed contents. That distance is what makes heap pollution expensive — the failing line is not the wrong line.

Better approachWhy
Validate at the boundarylist.stream().allMatch(String.class::isInstance) before casting — fails where the data enters
A type token — Class<T> plus cast()Turns the unchecked cast into a checked one that throws at the boundary
Copy into a correctly typed listlist.stream().map(String.class::cast).toList() — fails immediately and produces a genuinely typed result

And suppress narrowly. @SuppressWarnings on a whole method hides every unchecked operation in it, including ones added later by someone else. Put it on the smallest declaration possible, with a comment stating why the cast is actually safe — if you cannot write that sentence, the suppression is not justified.

6 (hard): Design a type-safe heterogeneous container — a map holding values of different types, retrieved with the correct static type.
Solution 
public final class TypedMap {
    private final Map<Class<?>, Object> values = new HashMap<>();

    public <T> void put(Class<T> type, T value) {
        values.put(Objects.requireNonNull(type), type.cast(value));
    }

    public <T> T get(Class<T> type) {
        return type.cast(values.get(type));       // CHECKED cast
    }
}

TypedMap map = new TypedMap();
map.put(String.class, "hello");
map.put(Integer.class, 42);

String s = map.get(String.class);      // no cast at the call site
Integer i = map.get(Integer.class);
MechanismWhat it does
Class<T> as the keyA type token — carries the type at runtime, which erasure otherwise removes
type.cast(...) on readA checked cast, so a wrong entry throws here rather than polluting a reference
type.cast(...) on writeRejects a mismatched value at insertion, which is where the mistake was made
Generic methods, not a generic classEach call binds its own T, which is what allows different types in one map

The insight is that Class<T> is the type argument made concrete. Erasure removes T at runtime, so you pass the type explicitly and get back a checked cast — the unchecked cast, and the heap pollution it enables, disappears entirely.

The limitation is that it cannot hold parameterised types. There is no List<String>.class — only List.class — so List<String> and List<Integer> would collide on the same key.

The workaround is the super type token, which captures a full parameterised type from an anonymous subclass's signature attribute — the one place erasure does not discard the type. That is exactly how Jackson's TypeReference and Guice's TypeLiteral work:

new TypeReference<List<String>>() { }    // subclass records the type

Where this pattern belongs in practice: request or session attribute maps, dependency injection registries, and plugin configuration — anywhere a single container must hold values of unrelated types and hand each back with its real type. It is Effective Java's typesafe heterogeneous container, and the JDK uses it in AnnotatedElement.getAnnotation(Class<T>).

🎯 Key Takeaways

  • Generics move type errors to compile time and remove casts — and every cast removed is a place the compiler keeps checking.
  • Erasure removes type arguments at runtime, so List<String> and List<Integer> are the same class.
  • Erasure was chosen for migration compatibility, and nearly every generics limitation follows from it.
  • No new T(), new T[], instanceof List<String>, generic exceptions, or static T fields.
  • Generics are invariant — List<String> is not a List<Object>, and that is what preserves type safety.
  • Arrays are covariant and reified, so they defer the same error to runtime as ArrayStoreException.
  • PECS: producer extends, consumer super.
  • ? extends T can be read as T and written to only with null, because the element type is some unknown subtype.
  • ? super T accepts writes of T and reads back only Object.
  • List<?> and List<Object> are opposites — one accepts any list and takes nothing, the other takes anything and accepts only itself.
  • Use a type parameter when the type appears twice and must match; a wildcard when it appears once.
  • An unchecked warning is a promise you are making — suppress at the narrowest scope, with a reason.
  • Heap pollution fails far from its cause, at the compiler-inserted cast rather than at the cast that lied.
  • Raw types disable checking for the whole expression, not just the missing argument.
  • A Class<T> token restores the type at runtime and turns an unchecked cast into a checked one.
