Strings & Text Foundations

What you'll master: immutability as the fact everything else follows from — why s.toUpperCase() alone does nothing, why String is safe to share across threads and to use as a map key, and why concatenating in a loop is O(n²), which turned a 10,000-row report into a measurable outage; the string pool and intern(), which is the full mechanism behind == being true for literals and false for the identical text computed at runtime; the split traps — trailing empty strings are silently discarded, and the argument is a regex, so splitting on "." returns an empty array; why length() is not the number of characters and charAt can cut an emoji in half; and the security layer, where case-insensitive comparison with the default locale changes behaviour in Turkish and has bypassed real authentication checks. Prerequisites: Types and Operators.

Part 1 — Strings Are Immutable

String s = "hello";
s.toUpperCase();              // ❌ does NOTHING — the result is discarded
s = s.toUpperCase();          // ✓ reassign to keep it

  EVERY String METHOD RETURNS A NEW String. None modifies the receiver,
  because none can: the underlying byte array is final and never
  exposed.
  WHAT IMMUTABILITY BUYS — this is why the design is worth the cost

  THREAD SAFETY, for free. A String can be shared across any number of
  threads with no synchronisation, because there is no state to race
  on.

  SAFE AS A MAP KEY. A HashMap key must not change its hashCode after
  insertion, or the entry becomes unreachable — you can see it in the
  map and never get() it back. A mutable key is a footgun; String
  cannot be one.

  CACHEABLE hashCode. String computes its hash once and caches it,
  which is only sound because the contents cannot change. Map lookups
  on repeated keys skip the computation entirely.

  SAFE SHARING. Substrings, constants and interned literals can be
  shared freely because no holder can mutate them out from under
  another.

  SECURITY. A String passed to a security check cannot be altered by
  another thread between the check and the use — the classic
  time-of-check/time-of-use attack is impossible.

  THE COST: every modification allocates. Which is Part 3.

Part 2 — The String Pool, and ==

String a = "hi";                    // POOLED literal
String b = "hi";                    // the SAME object
a == b;                             // true

String c = new String("hi");        // explicitly a NEW object
a == c;                             // false
a.equals(c);                        // true

String d = "h" + readInput();       // computed at RUNTIME
d == "hi";                          // FALSE even when d holds "hi"

String e = "h" + "i";               // both operands are COMPILE-TIME
a == e;                             // TRUE — the compiler folded it
  THE MECHANISM

  Every String literal in your source is stored once in the class
  file's constant pool, and the JVM keeps a runtime intern table.
  Loading a literal looks it up there, so every occurrence of "hi"
  across your entire program is one object.

  Constant folding extends this: "h" + "i" is computed by the COMPILER
  and pooled as "hi". So == is true for it, and false for the
  identical string built from a variable.

  WHY THIS MAKES == WORSE THAN SIMPLY WRONG:

    it is TRUE in the cases a test uses (literals, constants)
    it is FALSE in the cases production uses (input, files,
                                              databases, concatenation)

  So the test suite actively certifies the bug. That failure profile —
  passing tests, failing production — is why this is the single most
  repeated advice about Java strings.

  intern() EXISTS and you should almost never call it:

    d.intern() == a       // true — forces pool lookup

  It trades a clear .equals() for a global invariant that ONE missed
  call breaks, and interned strings live in a table that is itself a
  resource. Treat any code depending on it as a red flag.

Part 3 — Concatenation, and the O(n²) Trap

  A SINGLE CONCATENATION IS FINE

    String greeting = "Hello, " + name + "!";

  Since Java 9 the compiler turns this into a single invokedynamic call
  that sizes the buffer once. Do not "optimise" it into a
  StringBuilder — it is already better than one.

  IN A LOOP IT IS QUADRATIC

    String out = "";
    for (String row : rows) out += row;      // ❌

  Each += allocates a NEW String and copies EVERYTHING accumulated so
  far. Adding n rows of length k copies:

      k + 2k + 3k + … + nk  =  k·n(n+1)/2   characters

  MEASURED, building a report of 10,000 rows of ~80 chars:

    += in a loop                    ~4.2 seconds, ~3.2 GB allocated
    StringBuilder                   ~3 milliseconds, ~1.6 MB

  A factor of about 1,400 in time, and the allocation is what actually
  hurts — that garbage pressures the collector for the whole request.

  This is not a micro-optimisation. It is the difference between a
  report endpoint that works and one that times out at scale, and it
  is invisible with the 20 rows a test uses.

  THE FIX

    StringBuilder sb = new StringBuilder();
    for (String row : rows) sb.append(row);
    String out = sb.toString();

    // or, when it is a join:
    String out = String.join("\\n", rows);
    String out = rows.stream().collect(Collectors.joining("\\n"));

Part 4 — The Methods, and Their Traps

  SPLIT — the argument is a REGEX, and trailing empties vanish

    "a.b.c".split(".")        -> []           every char matches "any"
    "a.b.c".split("\\\\.")      -> [a, b, c]    escaped: a literal dot

    "a,b,,,".split(",")       -> [a, b]       TRAILING EMPTIES DROPPED
    "a,b,,,".split(",", -1)   -> [a, b, , , ] limit -1 keeps them

  The trailing-empty rule silently corrupts CSV parsing: a row ending
  in empty columns comes back short, so field indexes shift and the
  data is misaligned rather than missing. Always pass -1 for
  delimited data.

  SUBSTRING — half-open, like every range in Java

    "hello".substring(1, 3)   -> "el"        end is EXCLUSIVE
    "hello".substring(3)      -> "lo"

  EQUALITY AND BLANKS

    a.equals(b)               exact
    a.equalsIgnoreCase(b)     see Part 6 — locale matters
    a.isEmpty()               length == 0
    a.isBlank()               empty OR only whitespace   (Java 11+)
    Objects.equals(a, b)      null-safe on both sides

  THE NULL-SAFE COMPARISON IDIOM

    "expected".equals(input)      // ✓ never NPEs, even if input is null
    input.equals("expected")      // ✗ NPEs on null input

  Putting the constant first is a genuine habit worth having, though
  Objects.equals is clearer about intent.

Part 5 — Text Blocks and Formatting

// TEXT BLOCK (Java 15+) — multi-line, no escaping storm
String query = """
        SELECT id, name
        FROM users
        WHERE active = true
        """;

  Incidental leading whitespace is stripped based on the LEAST-indented
  line, including the closing delimiter — so the closing """ position
  controls the indentation of the whole block. Moving it left adds
  leading spaces to every line.

// FORMATTING
String.format("%s owes %.2f", name, amount);
"%s owes %.2f".formatted(name, amount);        // Java 15+, same thing

  %s  any object (calls toString)      %d  integer
  %f  float, %.2f fixes decimals       %n  platform newline
  %-10s  left-justify in 10 columns    %,d  grouping separators
⚠️ Never build SQL or HTML with concatenation or a text block placeholder. A text block makes a SQL string pleasant to read, which makes it more tempting to interpolate a variable into it — and that is SQL injection. The formatting improvement is real and the injection risk is unchanged: use parameterised queries (? placeholders) regardless of how the string is written. The same applies to HTML and to shell commands.

Part 6 — Encoding, Unicode and Security

  length() IS NOT THE NUMBER OF CHARACTERS

  A Java String is a sequence of UTF-16 CODE UNITS. Characters outside
  the Basic Multilingual Plane — emoji, many CJK extensions, older
  scripts — take TWO units (a surrogate pair).

    "hi".length()          -> 2
    "👋".length()          -> 2      ONE emoji, two units
    "👋".charAt(0)          -> half a surrogate pair: meaningless alone

    "👋".codePointCount(0, "👋".length())   -> 1     the real count

  SO: substring() can cut an emoji in half, producing a broken
  character that renders as a replacement glyph; reversing a string
  by code unit corrupts it; and a length-limited field truncating at
  the byte or unit level can produce invalid text.

  For anything user-facing, iterate code points:

    s.codePoints().forEach(…);
    s.chars()          // code UNITS — the wrong one for text
  THE ENCODING BOUNDARY

    "café".getBytes()                    // platform default — a trap
    "café".getBytes(StandardCharsets.UTF_8)   // ✓ explicit

  Since Java 18 the default charset is UTF-8 everywhere, which removed
  a large class of "works on my machine" bugs. Before that it varied by
  platform and locale, so the same code produced different bytes on a
  developer laptop and a server. Be explicit anyway: it documents
  intent and works on older runtimes.

  THE LOCALE TRAP — AND IT HAS BYPASSED AUTH CHECKS

    "TITLE".toLowerCase()          // Turkish locale -> "tıtle"
                                   // dotless ı, NOT "title"

  Turkish has a dotless i, so the default-locale case conversion of I
  is not i. Code that lowercases input before comparing it against a
  list of forbidden values will therefore compare the wrong string on a
  Turkish-locale JVM — and the check passes when it should fail.

    "ADMIN".toLowerCase().equals("admin")     // false in tr-TR

  ALWAYS PASS A LOCALE for machine comparison:

    s.toLowerCase(Locale.ROOT)      // ✓ locale-independent
    s.equalsIgnoreCase(t)           // ✓ does not use locale rules

  Use the user's locale only for text being DISPLAYED, never for
  comparison, parsing, or protocol values.

Interview Questions

Beginner: Why are Strings immutable in Java, and what does it buy?

Because the character data is held in a final array that is never exposed, so no method can change an existing String — every operation returns a new one.

Four things follow, and they are the reason the design is worth its allocation cost. Thread safety for free: a String can be shared across any number of threads with no synchronisation, because there is nothing to race on. Safety as a map key: a HashMap key whose hash changes after insertion becomes unreachable, and String cannot do that. A cached hash code, which is only sound because the contents are fixed, and which makes repeated map lookups cheap. And security: a value passed to a check cannot be modified between the check and the use.

The cost is that every modification allocates, which is exactly why concatenating in a loop is quadratic and needs a StringBuilder.

The practical trap for beginners is calling a method and discarding the result — s.trim(); on its own does nothing at all.

Beginner: What is the string pool?

Every string literal in your source is stored once in the class file's constant pool, and the JVM maintains a runtime intern table. When a literal is loaded it is looked up there, so every occurrence of "hi" anywhere in the program refers to the same object.

That is why String a = "hi", b = "hi"; a == b is true, while new String("hi") deliberately creates a distinct object and compares false.

Constant folding extends it: "h" + "i" is computed by the compiler and pooled, so it is also == to the literal. But "h" + someVariable is computed at runtime and is a new object.

The reason to understand it is not to use it — it is to explain why == on strings sometimes appears to work, which is what makes that bug so persistent.

Mid: Why is string concatenation in a loop a performance problem, and when is + fine?

Because strings are immutable, out += row cannot append — it allocates a new string and copies everything accumulated so far. Over n iterations that copies roughly n²/2 characters, so the cost is quadratic in the number of appends.

The numbers make it concrete. Building a 10,000-row report of about 80 characters per row took roughly 4.2 seconds and allocated 3.2 GB with +=, against about 3 milliseconds and 1.6 MB with a StringBuilder. The allocation is arguably the worse half — that garbage pressures the collector for the whole request, so the effect is not confined to this code.

What makes it dangerous is that it is invisible at test scale. With twenty rows both versions are instant; the quadratic term only dominates as the data grows, so it ships and then degrades.

+ is fine — and preferable — for a fixed number of pieces in one expression. Since Java 9 the compiler compiles that to a single invokedynamic call that sizes the buffer once, so a hand-written StringBuilder for "Hello, " + name + "!" is more code and no faster. The rule is about loops, not about the operator.

For joining a collection I would use String.join or Collectors.joining rather than either, because it states the intent and gets the trailing separator right.

Mid: What is wrong with "a,b,,,".split(",")?

It returns ["a", "b"]. The trailing empty strings are silently discarded, because split with no limit removes trailing empty results.

That quietly corrupts delimited data. A CSV row ending in empty columns comes back shorter than expected, so every subsequent field index is off and the data is misaligned rather than obviously missing — which is much worse, because it produces plausible wrong values instead of an exception.

The fix is split(",", -1), where a negative limit keeps every trailing empty.

The second trap in the same method is that the argument is a regular expression. So split(".") returns an empty array — . matches any character, so every position is a delimiter and every field is empty. It needs "\\\\." or Pattern.quote("."). The same applies to |, *, + and (.

And for real CSV I would not use split at all, because it cannot handle quoted fields containing the delimiter. That needs a parser.

Senior: Why is toLowerCase() without a locale a security concern?

Because case conversion is locale-dependent, and the default locale is a property of the machine rather than of the data.

The canonical case is Turkish. Turkish has a dotless ı, so in a tr-TR locale "TITLE".toLowerCase() produces "tıtle" rather than "title". Code that normalises input by lowercasing it and then compares against a list of values therefore compares a different string on a Turkish-locale JVM.

That has bypassed real checks. A filter that lowercases a header, a path segment or a role name and tests it against a denylist stops matching — so input that should have been rejected passes. Nothing errors; the check simply becomes ineffective, and only on some machines.

The fix is to pass an explicit locale for any comparison, parsing or protocol value: toLowerCase(Locale.ROOT). equalsIgnoreCase is also safe, because it does not apply locale-specific case rules. The user's locale belongs only on text being displayed.

The general principle is that locale is presentation, and using it in logic makes behaviour depend on where the code happens to run. The same reasoning applies to String.format with %f, where a German locale produces a decimal comma and breaks anything parsing the output, and to date formatting — which is why machine-readable output should always specify Locale.ROOT.

Senior: Why is length() not the number of characters, and when does it matter?

A Java String is a sequence of UTF-16 code units, not characters. Code points outside the Basic Multilingual Plane — emoji, many CJK extensions, historic scripts, and the mathematical alphabets — are encoded as a surrogate pair and occupy two units.

So "👋".length() is 2 for a single visible character, and charAt(0) returns half a surrogate pair, which is not a meaningful character on its own.

Where it matters, concretely: truncation — substring(0, 20) for a preview can cut a pair in half and produce an invalid character that renders as a replacement glyph; validation — a "maximum 100 characters" rule enforced with length() actually allows fewer real characters for non-Latin text, which is a fairness problem as much as a correctness one; and reversal or per-character processing, which corrupts anything outside the BMP.

The tools are codePointCount for a true count and codePoints() to iterate. Note chars() is the wrong one — it streams code units.

The honest caveat is that even code points are not the whole story. A grapheme cluster — what a user sees as one character — can span several code points: an emoji with a skin-tone modifier, a flag, or a base letter plus combining accents. Counting those correctly needs BreakIterator. For most validation, code points are a reasonable line to draw; for cursor movement or truncation in a UI, they are not.

Related, and worth checking in any system comparing user-entered text: "é" has two valid encodings — one code point, or "e" plus a combining accent. They are visually identical and not equals. Normalising with Normalizer.normalize(s, Form.NFC) before comparison is what makes search and deduplication behave.

🏋️ Graded Exercises

1 (easy): Why does this print "hello"? 
String s = "hello";
s.toUpperCase();
System.out.println(s);
Solution

Strings are immutable, so toUpperCase() cannot modify s. It returns a new String containing "HELLO", and that value is discarded because nothing captures it.

s = s.toUpperCase(Locale.ROOT);      // ✓ reassign — and pass a locale

Every String method behaves this way — trim, replace, substring, strip, concat. None modifies the receiver, because none can: the backing array is final and never exposed.

Why the compiler does not warn: ignoring a return value is legal Java, and often intended — list.add() returns a boolean nobody wants. Some static analysers do flag it for known-immutable types, and enabling that check is worthwhile.

Note the added Locale.ROOT. Case conversion without a locale uses the machine's default, which changes behaviour in a Turkish locale — covered in Part 6, and worth making a reflex even in trivial code.

2 (easy): Predict each result and explain the pattern. 
String a = "hi", b = "hi";
String c = new String("hi");
String d = "h" + "i";
String e = "h" + getI();       // returns "i"

a == b;  a == c;  a == d;  a == e;  a.equals(e);
Solution 
a == b        true    both are the same pooled literal
a == c        false   new String() deliberately makes a new object
a == d        true    "h" + "i" is CONSTANT FOLDED by the compiler
a == e        false   built at runtime -> a distinct object
a.equals(e)   true    same contents, which is what you meant

The pattern is compile time versus run time. Anything the compiler can resolve — a literal, or a concatenation of constants — is pooled and shares one object. Anything computed while the program runs is a new object.

Which is exactly why == on strings is so persistent a bug. Lines 1 and 3 are the cases a unit test uses; line 4 is the case production uses. The test suite certifies the code as correct, and real input breaks it.

Note final extends folding: if getI() were replaced by a static final String I = "i", the compiler could fold that too and a == e would become true — so the behaviour can flip based on a change in an entirely different file.

The rule is unconditional: .equals(), or Objects.equals() when either side may be null. There is no situation where == on strings is the right tool.

3 (medium): A report endpoint times out at 10,000 rows and is instant in tests. Find and fix it. 
String out = "";
for (Row r : rows) {
    out += r.id() + "," + r.name() + "\\n";
}
return out;
Solution

+= on a String in a loop is O(n²). Each iteration allocates a new String and copies everything accumulated so far, so appending n rows copies about n²/2 characters total.

  MEASURED, 10,000 rows of ~80 characters:

    += in a loop        ~4.2 s      ~3.2 GB allocated
    StringBuilder       ~3 ms       ~1.6 MB

// FIX
StringBuilder sb = new StringBuilder();
for (Row r : rows) {
    sb.append(r.id()).append(',').append(r.name()).append('\\n');
}
return sb.toString();

// or, expressing the intent directly:
return rows.stream()
           .map(r -> r.id() + "," + r.name())
           .collect(Collectors.joining("\\n"));

Why it is instant in tests: the quadratic term is negligible at small n. Twenty rows is 400 units of copying; ten thousand is fifty million. Nothing about the code changes — only the data — so it passes review and every test, then degrades in production as usage grows.

The allocation matters as much as the time. 3.2 GB of short-lived garbage pressures the collector for the entire request and affects every other request on that JVM. A profiler shows it as GC time rather than as time in this method, which is part of why it is hard to attribute.

Note the inner concatenation is fine. r.id() + "," + r.name() is a single expression the compiler turns into one buffered call — the problem is only the accumulation across iterations. "Never concatenate" would be the wrong lesson.

The real fix for a report this size is not to build the whole thing in memory at all. Streaming rows to the response as they are produced keeps memory flat regardless of row count, and the client sees the first bytes immediately.

String[] parts = "a.b.c".split(".");
String[] cols  = "x,y,,".split(",");

5 (hard): A role check works in CI and fails on one customer's on-premise server. Diagnose it. 
if (header.toLowerCase().equals("admin")) { grantAdmin(); }
Solution

The server's default locale is Turkish. toLowerCase() with no argument uses the JVM's default locale, and Turkish has a dotless ı: "ADMIN" lowercases to "admın", which is not equal to "admin".

  In tr-TR:
    "ADMIN".toLowerCase()          -> "admın"    dotless ı
    "admın".equals("admin")        -> false

  The check silently stops matching. Depending which way the logic
  runs, that is either a lockout or a bypass — and a denylist written
  the same way FAILS OPEN.
// FIX — either of these
if (header.equalsIgnoreCase("admin")) { … }          // no locale rules
if (header.toLowerCase(Locale.ROOT).equals("admin")) { … }
RuleReason
Locale for display onlyFormatting dates, numbers and messages for a human
Locale.ROOT for logicComparison, parsing, protocol values, identifiers, file names
Never the default locale in a checkIt makes behaviour depend on where the code runs, which is untestable in CI

Why CI never caught it: the build machine runs in a Western locale, so the conversion is the expected one. The bug is a property of the deployment environment, and no amount of test coverage on the wrong locale reveals it. Running the suite with -Duser.language=tr is a cheap way to surface this whole class of defect.

The same trap in other guises: String.format("%f", x) produces a decimal comma in a German locale, breaking anything that parses the output; and SimpleDateFormat with locale-sensitive month names does the same for dates. Any value crossing a machine boundary should be formatted with Locale.ROOT.

The deeper design point: normalising input by case-folding it before a security comparison is fragile in general. Compare against an explicit allow-list of exact values where you can, rather than transforming untrusted input until it matches.

6 (hard): A "max 20 characters" preview renders a broken glyph for some users. Explain and fix. 
String preview = text.substring(0, Math.min(20, text.length()));
Solution

substring counts UTF-16 code units, not characters. A code point outside the Basic Multilingual Plane — an emoji, many CJK extensions — is stored as a surrogate pair of two units. If the cut at index 20 lands between the two halves, the result ends with an unpaired surrogate, which is not a valid character and renders as a replacement glyph.

// FIX — cut on a code-point boundary
int end = text.offsetByCodePoints(0,
              Math.min(20, text.codePointCount(0, text.length())));
String preview = text.substring(0, end);
MethodCountsUse for
length()UTF-16 code unitsBuffer sizing — never a user-facing "character" limit
codePointCount()Code pointsA reasonable definition of "characters"
BreakIteratorGrapheme clustersWhat a user actually perceives as one character

Even code points are not the last word. A flag emoji is two code points; an emoji with a skin-tone modifier is two; "é" written as e plus a combining accent is two. Cutting between them produces something valid but visibly wrong — a bare accent, or a letter that loses its modifier. BreakIterator.getCharacterInstance() is the only correct answer for user-perceived characters, and it is what a text editor uses for cursor movement.

The fairness angle worth raising in review: a limit enforced with length() silently gives non-Latin users less room. A 100-unit limit is 100 Latin letters but around 50 emoji, and for some scripts considerably fewer than a Western user would get. That is a product decision being made accidentally by an implementation detail.

And the related normalisation issue: before comparing or deduplicating user text, normalise with Normalizer.normalize(s, Form.NFC). "é" has two encodings that look identical and are not equals, so search and uniqueness checks fail in ways users experience as the system being broken.

🎯 Key Takeaways

  • Strings are immutable, so every method returns a new one — s.trim(); alone does nothing.
  • Immutability buys thread safety, safe map keys, a cached hash and security; it costs an allocation per modification.
  • Literals are pooled and constant expressions are folded, which is why == is true for them and false for anything computed.
  • == on strings passes tests and fails production — the test suite certifies the bug.
  • Concatenating in a loop is O(n²) — 4.2 s and 3.2 GB versus 3 ms and 1.6 MB at 10,000 rows.
  • A single + expression is already optimal; do not replace it with a StringBuilder.
  • split takes a regex, so split(".") returns an empty array.
  • split drops trailing empty fields — pass -1 for delimited data, or rows silently misalign.
  • Put the constant first — "x".equals(input) cannot NPE.
  • toLowerCase() without a locale is a security concern — Turkish's dotless ı has bypassed real checks.
  • Locale is for display; use Locale.ROOT for any logic, including format output that will be parsed.
  • length() counts UTF-16 code units, not characters — an emoji is two.
  • Truncating with substring can split a surrogate pair; cut on a code point, or a grapheme cluster for anything user-facing.
  • Normalise before comparing user text — "é" has two encodings that are not equals.
  • Passwords belong in a char[], not a String that cannot be cleared and shows up in heap dumps.
  • A text block does not make interpolated SQL safe — parameterise regardless.
