Streams API Core Libraries

What you'll master: laziness as the fact that explains the API — intermediate operations build a pipeline and do nothing until a terminal operation runs, which is why a stream with no terminal call executes zero times, why filter before map matters, and why elements flow through one at a time rather than stage by stage; why a stream is single-use and reusing one throws; why side effects in map or filter are unsafe rather than merely unfashionable; the collectors that replace most loops — and toMap's duplicate-key exception that only fires on certain data; and the honest position on parallelStream(), which is slower than sequential for most workloads and shares one thread pool across the entire JVM. Prerequisites: Lambdas and Collections.

Part 1 — Source, Intermediate, Terminal

list.stream()                    // SOURCE
    .filter(o -> o.total() > 100) // INTERMEDIATE — lazy, returns a
    .map(Order::customer)         //   stream, does nothing yet
    .distinct()
    .toList();                    // TERMINAL — runs the whole thing

  A pipeline with NO TERMINAL OPERATION NEVER EXECUTES:

    list.stream().map(this::expensiveCall);    // does nothing at all
                                               // — not one call

  That is the single most surprising property for newcomers, and it
  follows directly from laziness: intermediate operations only record
  what to do.

  ELEMENTS FLOW ONE AT A TIME, NOT STAGE BY STAGE.

    Stream.of("a", "b", "c")
          .filter(s -> { print("filter " + s); return true; })
          .map(s -> { print("map " + s); return s; })
          .toList();

    filter a, map a, filter b, map b, filter c, map c

  NOT "filter a, filter b, filter c, then map…". Each element is
  pushed through the entire pipeline before the next one starts, which
  is what allows short-circuiting and means no intermediate
  collections are ever materialised.

  THAT ALSO EXPLAINS WHY ORDER MATTERS:

    .map(expensive).filter(cheap)     // maps EVERY element
    .filter(cheap).map(expensive)     // maps only survivors

  Put the cheapest, most selective filter first.

Part 2 — Short-Circuiting and Infinite Streams

  Laziness makes infinite streams usable, because a short-circuiting
  terminal stops pulling.

    Stream.iterate(1, n -> n * 2)     // infinite
          .filter(n -> n > 1000)
          .findFirst();                // stops at the first match

    IntStream.range(0, 1_000_000)
             .filter(this::isPrime)
             .limit(10)                // stops after 10
             .boxed().toList();

  SHORT-CIRCUITING OPERATIONS:
    findFirst, findAny, anyMatch, allMatch, noneMatch, limit

  allMatch and noneMatch short-circuit on the first FAILURE, which is
  why they are cheaper than they look on large inputs.

  THE EMPTY-STREAM SUBTLETY WORTH KNOWING:

    Stream.of().allMatch(x -> false)     // TRUE — vacuous truth
    Stream.of().anyMatch(x -> true)      // false
    Stream.of().noneMatch(x -> true)     // true

  allMatch on an empty stream is true because there is no element that
  fails. That is mathematically correct and has produced real bugs in
  validation code — "all items are approved" is true for an order with
  no items.

Part 3 — The Operations That Matter

  So .sorted() on an infinite stream never terminates, and
  .sorted().findFirst() still sorts the entire input — the
  short-circuit cannot reach past the barrier. If you want the
  smallest element, use min() rather than sorting.

Part 4 — Collectors

  THE ONES THAT REPLACE MOST LOOPS

    .toList()                                  Java 16+, immutable
    .collect(Collectors.toSet())
    .collect(Collectors.joining(", "))
    .collect(Collectors.counting())

    .collect(groupingBy(Order::status))
        -> Map<Status, List<Order>>

    .collect(groupingBy(Order::status, counting()))
        -> Map<Status, Long>

    .collect(groupingBy(Order::customer,
                        summingDouble(Order::total)))
        -> Map<Customer, Double>

    .collect(partitioningBy(o -> o.total() > 100))
        -> Map<Boolean, List<Order>>   — ALWAYS has both keys

  groupingBy with a downstream collector is the one worth learning
  properly: the second argument decides what each group becomes, and
  it composes arbitrarily deep.

  toMap AND ITS TRAP

    .collect(toMap(User::email, u -> u))
        -> IllegalStateException: Duplicate key

  toMap throws on a duplicate key rather than overwriting. That is a
  deliberate choice — silently discarding data would be worse — but it
  means the failure depends on the DATA, so it passes every test with
  unique fixtures and throws in production.

    .collect(toMap(User::email, u -> u, (a, b) -> b))    // keep last
    .collect(toMap(User::email, u -> u, (a, b) -> a))    // keep first
    .collect(groupingBy(User::email))                     // keep both

  ALWAYS supply the merge function, and decide deliberately which
  duplicate wins.

  A SECOND toMap TRAP: it rejects null VALUES, throwing NPE — unlike
  HashMap, which permits them. A mapper returning null for a missing
  field fails at collection time.

Part 5 — reduce, and Purity

  reduce COMBINES ELEMENTS INTO ONE VALUE

    .reduce(0, Integer::sum)                    identity + accumulator
    .reduce(BinaryOperator.maxBy(comparator))   -> Optional

  THE ACCUMULATOR MUST BE ASSOCIATIVE — (a op b) op c == a op (b op c)
  — because a parallel stream splits the work arbitrarily and combines
  partial results in an unspecified order. Subtraction is not
  associative, so reduce(0, (a, b) -> a - b) gives different answers
  sequentially and in parallel.

  AND THE IDENTITY MUST GENUINELY BE ONE: identity op x == x. With
  reduce(1, Integer::sum) every parallel split adds another 1.

  WHY SIDE EFFECTS IN map/filter ARE UNSAFE, NOT JUST UNFASHIONABLE

    List<String> out = new ArrayList<>();
    stream.filter(...).map(x -> { out.add(x); return x; }).count();

  Three separate problems:

    1. count() may SKIP the pipeline entirely — if the source size is
       known and no operation changes it, the JDK can return the count
       without executing map at all. Your list stays empty.
    2. In parallel, ArrayList is not thread-safe: lost elements,
       or an ArrayIndexOutOfBoundsException from a torn resize.
    3. Order is unspecified.

  The API documents operations as non-interfering and stateless
  precisely so it is free to do (1). Collect instead:

    List<String> out = stream.filter(...).toList();

Part 6 — Parallel Streams

  .parallelStream() IS ONE METHOD CALL AND RARELY THE RIGHT ONE.

  IT IS USUALLY SLOWER. Splitting, task scheduling and merging cost
  real time, and they are paid before any speedup. For a few thousand
  elements of cheap work, sequential wins comfortably.

  IT NEEDS ALL OF THESE TO PAY OFF:

    a large N                    tens of thousands and up
    expensive per-element work   otherwise overhead dominates
    a splittable source          ArrayList and arrays split well;
                                 LinkedList and Stream.iterate do not
    no shared mutable state      or it races
    an associative reduction     or results differ from sequential

  THE PART THAT SURPRISES PEOPLE: THE POOL IS SHARED.

  Every parallel stream in the JVM uses the SAME common
  ForkJoinPool, sized to (cores - 1) by default. So one slow parallel
  stream — especially one doing blocking IO — starves every other
  parallel stream in the process, including ones inside libraries.

  NEVER DO BLOCKING IO IN A PARALLEL STREAM. The pool is sized for CPU
  work; a blocked thread occupies a core's worth of pool capacity
  doing nothing.

  If you need concurrency for IO, use an ExecutorService you control —
  see Executors — where the pool size matches the workload and the
  failure is contained.

  MEASURE, DO NOT ASSUME. The honest default is sequential; reach for
  parallel when a benchmark on realistic data shows it helps.

Interview Questions

Beginner: What is the difference between intermediate and terminal operations?

Intermediate operations — filter, map, sorted — return a stream and are lazy: they record what should happen and execute nothing. Terminal operations — collect, forEach, count, reduce — produce a result and are what actually drive the pipeline.

The consequence that catches people is that a pipeline with no terminal operation never runs. list.stream().map(this::expensiveCall); makes zero calls, and there is no warning.

Laziness is also what makes short-circuiting and infinite streams work: findFirst stops pulling as soon as it has an answer, so a stream over an infinite source can terminate.

And a stream is single-use. Once a terminal operation has run, the stream is consumed; reusing it throws IllegalStateException. If you need two results, create two streams from the source.

Beginner: Why does filter before map matter?

Because elements flow through the pipeline one at a time, and each stage runs for every element that reaches it. Filtering first means the expensive transformation only runs on the elements that survive.

With a thousand elements where fifty pass the filter, map then filter performs a thousand transformations; filter then map performs fifty.

The general rule is to put the cheapest and most selective operations earliest, which is the same reasoning as ordering conditions in a SQL WHERE clause.

It is worth knowing that the JDK does not reorder your pipeline — unlike a query planner, it executes the stages in the order you wrote them. The optimisation is yours to make.

Mid: Why are side effects in map and filter unsafe?

Because the API is specified so the runtime may reorder, parallelise, or entirely skip those operations — and code with side effects assumes an execution model it does not promise.

The most striking case is elision. If a terminal operation is count() and the source size is known, and no operation in the pipeline can change the count, the JDK is permitted to return the size without executing the pipeline at all. So a map that was quietly adding to a list runs zero times and the list stays empty — with no error.

Second, in parallel a shared ArrayList is not thread-safe, so concurrent adds lose elements or throw from a torn resize.

Third, ordering is unspecified, so even when it works the result may differ between runs.

The fix is to let the pipeline produce the value — collect, toList, reduce — rather than accumulating externally. If the operation genuinely is a sequence of side effects, that is a signal it should be a for loop, where mutation is expected and the reader can see it.

Mid: Why does Collectors.toMap throw on duplicate keys?

Because there is no safe default. Overwriting silently discards data, and keeping the first silently discards different data — so rather than guess, the two-argument form treats duplicates as a programming error and throws IllegalStateException.

The three-argument form takes a merge function and makes the choice explicit: (a, b) -> b keeps the last, (a, b) -> a keeps the first, and anything else combines them.

What makes it worth calling out is the failure profile. The exception depends entirely on the data, so a test fixture with unique emails passes and production throws the first time two users share one. It is a latent bug that ships.

So I would treat the two-argument toMap as a code smell: either duplicates are impossible — in which case say so with a merge function that throws a meaningful exception — or they are possible and you must decide what happens.

The related trap is that toMap rejects null values with an NPE, even though HashMap permits them. A value mapper returning null for a missing field fails at collection time, which is confusing because the map type would allow it.

Senior: When is parallelStream() actually worth using?

Rarely, and it needs several conditions together: a large number of elements, genuinely expensive per-element work, a source that splits evenly, no shared mutable state, and an associative reduction.

Miss any of those and it is slower. Splitting, scheduling and merging cost real time, paid up front, so for a few thousand elements of cheap work sequential wins comfortably. And the source matters more than people expect: an ArrayList or array splits in constant time, while a LinkedList or Stream.iterate must be traversed to split, which defeats the purpose.

The property that causes production incidents is that the pool is shared. Every parallel stream in the JVM uses the same common ForkJoinPool, sized to roughly the core count. So one long-running parallel stream starves every other one in the process — including ones inside libraries you did not write.

That makes blocking IO in a parallel stream a genuine hazard rather than a style issue: the pool is sized for CPU-bound work, and a thread blocked on a socket occupies a core's worth of capacity doing nothing. For concurrent IO, an ExecutorService you own is the right tool — sized for the workload, and its failures contained.

My default is sequential, with parallel reached for only after a benchmark on realistic data shows it helps. It is a one-word change to try and a one-word change to revert, which makes measuring cheap.

Senior: When would you use a loop rather than a stream?

They are not in competition, and I would pick per situation rather than by policy.

A loop when there are checked exceptions. No standard functional interface declares one, so IO inside a stream becomes try/catch within a lambda — verbose, and it loses the checked-ness. A loop handles it naturally and can decide per element whether to skip, retry or abort.

A loop when the operation is fundamentally imperative — sequencing side effects, mutating an accumulator with logic too involved for a collector, or needing to break out on a condition that takeWhile cannot express.

A loop when debugging matters. A stack trace through a stream is a wall of lambda$process$0 and internal pipeline frames; a loop gives line numbers you can breakpoint.

A stream when the code is a transformation — filter, map, group, reduce. There the stream states the intent and a loop states the mechanics, and groupingBy with a downstream collector replaces a dozen lines of map-of-list boilerplate that is easy to get subtly wrong.

The test I apply is whether the code reads as what or as how. A stream expressing "group orders by status and sum their totals" is clearer than the loop; a stream expressing "for each file, try to delete it and log failures" is worse than the loop.

And performance is rarely the deciding factor — for typical sizes they are close, and a stream's allocation of pipeline objects is offset by avoiding intermediate collections.

🏋️ Graded Exercises

1 (easy): Why does this print nothing? 
orders.stream()
      .filter(o -> o.total() > 100)
      .map(o -> { System.out.println(o.id()); return o; });
Solution

There is no terminal operation, so the pipeline never runs. filter and map are intermediate and lazy — they build a description of the work and return a stream. Nothing pulls elements through it.

orders.stream()
      .filter(o -> o.total() > 100)
      .forEach(o -> System.out.println(o.id()));    // terminal

There is no warning, because a stream is a legitimate value to discard — which is why this is such a common first surprise. Some static analysers flag an ignored stream result, and enabling that check is worthwhile.

The reason it works this way is that laziness is what makes short-circuiting and infinite streams possible. findFirst can stop pulling; an infinite Stream.iterate can terminate. Eager evaluation would forfeit both.

Note the original also puts a side effect in map, which is unsafe even with a terminal operation — forEach is the operation designed for side effects.

2 (easy): In what order do the print statements appear? 
Stream.of("a", "b")
      .filter(s -> { System.out.println("filter " + s); return true; })
      .map(s -> { System.out.println("map " + s); return s; })
      .toList();
Solution 
filter a
map a
filter b
map b

Each element traverses the entire pipeline before the next one starts. The intuitive guess — all the filters, then all the maps — would require materialising an intermediate collection between stages, which streams specifically avoid.

Two consequences follow from this. Short-circuiting works: findFirst can stop after the first element completes the pipeline, without touching the rest. And memory stays flat regardless of the source size, because no stage holds a collection.

The exception is stateful operations. sorted() cannot emit anything until it has seen everything, so it buffers the entire stream and breaks the one-at-a-time model:

.filter(...).sorted().map(...)
  // filter runs for every element, then sorted buffers, THEN map
  // begins — and .findFirst() after .sorted() still sorts it all

distinct() is similarly stateful, remembering everything it has seen — which is why distinct() on an infinite stream grows without bound.

3 (medium): This works in tests and throws in production. Diagnose and fix. 
Map<String, User> byEmail = users.stream()
    .collect(Collectors.toMap(User::email, u -> u));
Solution

toMap throws IllegalStateException: Duplicate key when two users share an email. The two-argument form has no way to combine them, and it refuses to guess.

The failure is data-dependent, which is why it survives testing: fixtures have unique emails by construction, and production eventually does not.

// Decide explicitly which one wins:
.collect(toMap(User::email, u -> u, (existing, replacement) -> replacement))
.collect(toMap(User::email, u -> u, (existing, replacement) -> existing))

// Or keep both, if duplicates are meaningful:
Map<String, List<User>> byEmail =
    users.stream().collect(groupingBy(User::email));

// Or fail with a message that says which key:
.collect(toMap(User::email, u -> u, (a, b) -> {
    throw new IllegalStateException("duplicate email: " + a.email());
}))
If duplicates are…Use
Impossible by invariantA merge function that throws with the offending key named
Expected, last wins(a, b) -> b
Expected, all mattergroupingBy

The second trap in the same method: toMap throws an NPE if the value mapper returns null, even though HashMap permits null values. A mapper reading an optional field fails at collection time, and the message does not make the cause obvious.

I treat the two-argument toMap as a smell. Supplying a merge function forces the author to think about duplicates once, at the point of writing, rather than discovering the question in production.

4 (medium): Replace this loop with a stream, and say what is gained. 
Map<Status, List<Order>> byStatus = new HashMap<>();
for (Order o : orders) {
    if (o.total() > 100) {
        byStatus.computeIfAbsent(o.status(), k -> new ArrayList<>()).add(o);
    }
}
Solution 
Map<Status, List<Order>> byStatus = orders.stream()
    .filter(o -> o.total() > 100)
    .collect(Collectors.groupingBy(Order::status));

What is gained: the intent is stated rather than assembled. There is no mutable accumulator, no computeIfAbsent boilerplate, and no opportunity to get the create-if-absent logic wrong.

And it extends cleanly in a way the loop does not — a downstream collector changes what each group becomes, without touching the grouping logic:

groupingBy(Order::status, counting())                  Map<Status, Long>
groupingBy(Order::status, summingDouble(Order::total)) Map<Status, Double>
groupingBy(Order::status, mapping(Order::id, toList()))
                                                        Map<Status, List<Id>>
groupingBy(Order::customer, groupingBy(Order::status)) nested

What is lost, and worth weighing: the loop can be stepped through in a debugger line by line, while the stream requires breakpoints inside lambdas. And a stack trace from inside a collector is considerably less readable.

Note the returned map type is unspecified — groupingBy gives you a HashMap and the lists are ArrayLists, but neither is guaranteed. If you need a TreeMap or immutability, use the three-argument form with an explicit map factory.

This is the case where a stream is clearly better, because the code is a transformation and the stream says what it is rather than how to build it.

5 (hard): This collects nothing. Explain all three defects. 
List<String> ids = new ArrayList<>();
long n = orders.parallelStream()
    .map(o -> { ids.add(o.id()); return o; })
    .count();
Solution
DefectConsequence
The pipeline may be elidedcount() can return the source size without running map at all, when the size is known and no operation changes it. ids stays empty
ArrayList is not thread-safeIn parallel, concurrent add calls lose elements or throw ArrayIndexOutOfBoundsException from a torn resize
Order is unspecifiedEven when it appears to work, the resulting order is not the source order
// Let the pipeline produce the value
List<String> ids = orders.stream()
    .map(Order::id)
    .toList();
long n = ids.size();

The elision is the interesting one, because it looks like a bug in the JDK and is specified behaviour. The API documents pipeline operations as non-interfering and stateless precisely so the implementation is free to make optimisations like this — code with side effects has relied on a guarantee that was never offered.

It also demonstrates why "it worked when I tested it" means little here. Whether the count is elided depends on the source type and the operations present, so adding a filter later can change whether your side effect runs at all.

Removing parallelStream fixes two of the three and leaves the elision. The real fix is not to have side effects in the pipeline — which is also why peek is documented as a debugging aid rather than a place to do work.

6 (hard): A team adds .parallel() to a pipeline that calls a REST API per element. Response times across the whole service degrade. Explain.
Solution

Every parallel stream in the JVM shares one common ForkJoinPool, sized to roughly the number of cores minus one. A parallel stream doing blocking IO occupies those threads while they wait on sockets.

  8-core machine  ->  common pool has ~7 threads

  A parallel stream over 1,000 elements, each a 200ms HTTP call,
  saturates all 7 for ~30 seconds.

  During that window EVERY other parallel stream in the process
  queues behind it — including ones inside libraries, and inside
  frameworks that use parallel streams internally.

That is why the impact is service-wide rather than local. The team changed one pipeline and degraded unrelated code paths, which makes the cause very hard to find from the symptom.

The pool is sized for CPU-bound work, where a thread per core is optimal because threads never idle. Blocking IO breaks that assumption completely: the right pool size for IO is determined by latency and target throughput, and is typically far larger than the core count.

// Use an executor you own, sized for the workload
ExecutorService pool = Executors.newFixedThreadPool(50);
List<CompletableFuture<Result>> futures = items.stream()
    .map(i -> CompletableFuture.supplyAsync(() -> call(i), pool))
    .toList();
List<Result> results = futures.stream().map(CompletableFuture::join).toList();

// Or, on Java 21+, virtual threads — ideal for blocking IO
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) { … }
WorkloadTool
CPU-bound, large N, splittable sourceA parallel stream — measure first
Blocking IOA dedicated ExecutorService, or virtual threads
Anything where failure must be containedA pool you own, so exhaustion affects one feature

The general principle is that the common pool is shared infrastructure. Using it for anything long-running or blocking makes your feature's behaviour everyone else's problem, and the resulting incident points at the wrong code.

🎯 Key Takeaways

  • Intermediate operations are lazy; a pipeline with no terminal operation never runs.
  • Elements flow one at a time through the whole pipeline, which is what enables short-circuiting and keeps memory flat.
  • Filter before map — the JDK does not reorder your pipeline.
  • sorted and distinct are stateful barriers; sorted().findFirst() still sorts everything, so use min.
  • A stream is single-use — reusing one throws.
  • Side effects in map or filter are unsafe, and count() may elide the pipeline entirely.
  • allMatch on an empty stream is true — vacuous truth has produced real validation bugs.
  • toMap throws on duplicate keys, and the failure is data-dependent, so it ships past tests. Always supply a merge function.
  • toMap also rejects null values, unlike HashMap.
  • groupingBy with a downstream collector replaces most map-of-list boilerplate and composes arbitrarily.
  • reduce needs an associative accumulator and a true identity, or parallel results differ.
  • Parallel streams are usually slower — they need large N, expensive work, and a splittable source.
  • All parallel streams share one JVM-wide pool, so one slow pipeline starves everything.
  • Never do blocking IO in a parallel stream — use an executor you own, or virtual threads.
  • Use a loop for checked exceptions and imperative sequencing; a stream for transformations.
