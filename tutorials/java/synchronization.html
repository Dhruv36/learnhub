Synchronization & Locks Concurrency

What you'll master: that synchronized provides two guarantees, not one — mutual exclusion and visibility — and why code that only needs the second should use volatile; which object a lock is actually on, and why synchronized on a method is a public lock anyone can hijack; reentrancy and why it exists; the four Coffman conditions for deadlock and the one you can practically break; why wait() must be in a while loop and never an if; what ReentrantLock buys that synchronized cannot (timeouts, interruptibility, multiple conditions, fairness) and what it costs; and where biased/lightweight locking means an uncontended lock is nearly free. Prerequisites: Threads.

Part 1 — Two Guarantees, Not One

  synchronized GIVES YOU BOTH OF THESE, AND PEOPLE ONLY REMEMBER THE
  FIRST:

  1. MUTUAL EXCLUSION — one thread at a time inside the block.
  2. VISIBILITY — everything written before releasing a monitor is
     visible to the next thread that acquires the SAME monitor.

  The second is what makes the following correct, and its absence is
  what makes an unsynchronized version silently broken:

    synchronized void set(int v) { this.value = v; }
    synchronized int  get()      { return this.value; }

  A common half-fix synchronizes the writer and not the reader:

    synchronized void set(int v) { this.value = v; }
    int get() { return this.value; }        // ❌ may read stale

  Mutual exclusion is pointless here — reads do not conflict with each
  other — but visibility is not. Without acquiring the same monitor,
  the reader has no guarantee of seeing the write, possibly forever.

  THE MECHANISM: every object has a MONITOR (a "intrinsic lock").
  Entering a synchronized block acquires it; leaving releases it,
  INCLUDING when an exception propagates. That last part is why you
  cannot leak an intrinsic lock the way you can leak a ReentrantLock.

  THE BYTECODE MAKES IT CONCRETE:

    monitorenter        // block form
    …
    monitorexit         // normal path
    monitorexit         // exception path — the compiler emits both

  A synchronized METHOD has no monitorenter at all: the ACC_SYNCHRONIZED
  flag tells the JVM to lock the receiver (or the Class object, for a
  static method) around the whole invocation. Same semantics,
  different encoding.

  IF YOU ONLY NEED VISIBILITY, USE volatile — it is far cheaper:

    private volatile boolean shutdown = false;

  volatile gives visibility and ordering but NOT atomicity, so it is
  right for a flag and wrong for a counter.

Part 2 — Which Object Are You Locking?

  THE FOUR FORMS AND THE OBJECT EACH LOCKS:

    synchronized void m() { }              locks `this`
    static synchronized void m() { }       locks MyClass.class
    synchronized (this) { }                locks `this`
    synchronized (lock) { }                locks `lock`

  TWO CONSEQUENCES PEOPLE MISS:

  1. AN INSTANCE LOCK AND A STATIC LOCK ARE DIFFERENT LOCKS.
     A synchronized instance method and a static synchronized method
     can run CONCURRENTLY. If both touch the same static field, that
     is a race.

  2. LOCKING `this` IS LOCKING A PUBLIC OBJECT.
     Anyone holding a reference to your object can do:

       synchronized (yourObject) { Thread.sleep(60_000); }

     and every synchronized method on it is blocked for a minute.
     That is not hypothetical — it happens accidentally when a
     caller synchronizes on a collection you also lock internally.

  THE FIX IS A PRIVATE LOCK OBJECT:

    private final Object lock = new Object();
    void m() { synchronized (lock) { … } }

  final matters: reassigning the lock reference means two threads can
  synchronize on DIFFERENT objects and both proceed.

  LOCK SPLITTING — one lock per independent piece of state:

    private final Object readLock  = new Object();
    private final Object writeLock = new Object();

  If two fields are never touched together, one lock for both is
  needless contention. If they ARE touched together, splitting them
  introduces a race — so split by invariant, not by field.

  NEVER LOCK ON THESE:

    String literals    interned and shared JVM-wide — you are
                       locking the same object as unrelated code
    Boxed primitives   Integer.valueOf caches -128..127, so
                       synchronized(Integer.valueOf(1)) is a global
                       lock
    Class objects      unless you mean a JVM-wide lock
    A mutable field    reassignment breaks exclusion entirely

  DOUBLE-CHECKED LOCKING NEEDS volatile:

    private volatile Singleton instance;    // ← REQUIRED

    Singleton get() {
        if (instance == null) {
            synchronized (lock) {
                if (instance == null) instance = new Singleton();
            }
        }
        return instance;
    }

  Without volatile, another thread can see a NON-NULL reference to a
  PARTIALLY CONSTRUCTED object, because the constructor's writes and
  the reference assignment may be reordered. It fails rarely and is
  nearly impossible to reproduce. Prefer a static holder class or an
  enum instead.

Part 3 — Reentrancy and Granularity

  INTRINSIC LOCKS ARE REENTRANT — a thread that holds a monitor can
  acquire it again:

    synchronized void outer() { inner(); }
    synchronized void inner() { }        // same lock, no deadlock

  Without reentrancy, that call would deadlock against itself, and
  any subclass calling a synchronized super method would too. The JVM
  keeps an owner and a HOLD COUNT per monitor; release only happens
  when the count reaches zero.

  GRANULARITY IS THE PERFORMANCE DECISION:

    // ❌ far too coarse — the network call holds the lock
    synchronized void process(Order o) {
        validate(o);
        String r = httpClient.post(o);     // 200 ms holding the lock
        save(o, r);
    }

    // ✓ hold it only around the shared state
    void process(Order o) {
        validate(o);
        String r = httpClient.post(o);     // no lock held
        synchronized (lock) { save(o, r); }
    }

  A lock held for 200 ms serialises everything: 100 requests take 20
  seconds. This is the single most common cause of a "slow under
  load" service with idle CPU.

  THE RULE: NEVER CALL UNKNOWN CODE WHILE HOLDING A LOCK. Network
  calls, disk I/O, callbacks, listeners, and anything overridable in
  a subclass. You cannot bound how long it runs and you cannot know
  what locks it takes — which is how deadlocks appear between two
  components that never referenced each other.

  BUT DO NOT OVER-SPLIT EITHER:

    synchronized (lock) { a++; }
    synchronized (lock) { b++; }        // two acquisitions, and
                                        // another thread can observe
                                        // a updated but not b

  If a and b share an invariant, they belong in ONE critical section.
  Correctness first, then granularity.

  THE ATOMICITY GAP IS THE CLASSIC BUG:

    if (!map.containsKey(k)) map.put(k, v);   // ❌ even on a
                                              // synchronized map

  Each call is atomic; the SEQUENCE is not. Two threads can both see
  "absent". Use an atomic compound operation instead:

    map.putIfAbsent(k, v);
    map.computeIfAbsent(k, key -> expensive(key));

Part 4 — Deadlock

  FOUR CONDITIONS MUST ALL HOLD (Coffman). Break any one and
  deadlock is impossible:

    1. MUTUAL EXCLUSION      a resource is held exclusively
    2. HOLD AND WAIT         a thread holds one while waiting for
                             another
    3. NO PREEMPTION         a lock cannot be taken away
    4. CIRCULAR WAIT         a cycle exists in the wait-for graph

  IN PRACTICE YOU BREAK #4 BY IMPOSING A GLOBAL LOCK ORDER.

  THE CANONICAL FAILURE — transfer between accounts:

    void transfer(Account from, Account to, BigDecimal amt) {
        synchronized (from) {
            synchronized (to) { … }
        }
    }

    transfer(A, B)  locks A then waits for B
    transfer(B, A)  locks B then waits for A       → deadlock

  THE FIX — ORDER BY A STABLE, UNIQUE KEY:

    void transfer(Account from, Account to, BigDecimal amt) {
        Account first  = from.id() < to.id() ? from : to;
        Account second = from.id() < to.id() ? to   : from;
        synchronized (first) {
            synchronized (second) { … }
        }
    }

  Now every thread takes locks in the same direction and no cycle can
  form. The key must be UNIQUE and STABLE — identityHashCode works as
  a fallback but can collide, so it needs a tie-breaker lock.

  BREAKING #2 INSTEAD — tryLock with a timeout:

    while (true) {
        if (fromLock.tryLock()) {
            try {
                if (toLock.tryLock(50, MILLISECONDS)) {
                    try { … return; } finally { toLock.unlock(); }
                }
            } finally { fromLock.unlock(); }
        }
        Thread.sleep(random.nextInt(50));    // back off, retry
    }

  This trades a guaranteed deadlock for possible LIVELOCK — threads
  repeatedly grabbing and releasing. Randomised backoff is what makes
  it terminate in practice.

  DETECTION: the JVM finds intrinsic-lock deadlocks itself.

    jstack <pid>   →  "Found one Java-level deadlock:"
                      with both stacks and both lock identities

  It does NOT detect deadlocks via ReentrantLock in older JDKs the
  same way, and it never detects a "logical" deadlock — everyone
  waiting on a queue nobody fills.

  RELATED FAILURES WORTH NAMING:

    LIVELOCK   threads are active but make no progress (mutual
               retry, mutual yielding)
    STARVATION a thread never gets the lock — often a fairness
               issue under sustained contention
    LOCK CONVOY many threads handing one lock back and forth, each
               switch costing a context switch

Part 5 — wait, notify and the while Rule

  wait/notify IS THE INTRINSIC CONDITION MECHANISM. Three rules, all
  enforced or required:

  1. YOU MUST HOLD THE MONITOR. Otherwise:
       IllegalMonitorStateException
  2. wait() RELEASES THE MONITOR while waiting, and REACQUIRES it
     before returning.
  3. YOU MUST WAIT IN A LOOP, NEVER AN if.

  THE CORRECT SHAPE:

    synchronized (lock) {
        while (!condition) {        // ← while, ALWAYS
            lock.wait();
        }
        // condition is true AND we hold the lock
        proceed();
    }

    synchronized (lock) {
        condition = true;
        lock.notifyAll();
    }

  WHY while AND NOT if — THREE INDEPENDENT REASONS:

    a) SPURIOUS WAKEUPS. wait() may return without any notify. This
       is permitted by the spec and does happen on real platforms.
    b) NOTIFYALL WAKES EVERYONE. Several waiters race to reacquire;
       the first may consume the condition, so the others must
       re-check.
    c) THE STATE CAN CHANGE between the notify and your reacquisition
       — you are not handed the lock atomically with the signal.

  With if, the thread proceeds on a condition that is no longer true.
  That is a correctness bug, not a performance one.

  notify() VERSUS notifyAll():

    notify()     wakes ONE arbitrary waiter. Safe only when all
                 waiters are interchangeable and wait for the same
                 condition. Otherwise it can wake a thread that
                 cannot proceed — and the one that could stays
                 asleep. That is a lost wakeup, and it looks like a
                 hang.
    notifyAll()  wakes all. Slightly wasteful, correct by default.

  USE notifyAll UNLESS YOU HAVE PROVEN THE WAITERS ARE UNIFORM.

  THE MODERN ANSWER IS USUALLY NOT TO WRITE THIS AT ALL:

    BlockingQueue   producer/consumer, already correct
    CountDownLatch  wait for N events (one-shot)
    CyclicBarrier   N threads meet repeatedly
    Semaphore       bound concurrent access to a resource
    Condition       when you genuinely need multiple wait sets

Part 6 — ReentrantLock and Friends

  THE SHAPE, AND WHY finally IS NOT OPTIONAL:

    private final ReentrantLock lock = new ReentrantLock();

    lock.lock();
    try { … } finally { lock.unlock(); }    // ALWAYS

  Unlike synchronized, nothing releases this for you. An exception
  before unlock leaks the lock permanently and every other thread
  hangs — the reason many teams still prefer synchronized by default.

  WHAT IT BUYS THAT synchronized CANNOT DO:

    tryLock()                        take it or move on — no blocking
    tryLock(t, unit)                 bounded wait, deadlock avoidance
    lockInterruptibly()              cancellable acquisition
    newCondition()                   MULTIPLE wait sets on one lock
    isLocked(), getHoldCount(),
    getQueueLength()                 introspection for diagnostics
    new ReentrantLock(true)          FAIR ordering

  MULTIPLE CONDITIONS IS THE FEATURE WITH NO EQUIVALENT — a bounded
  buffer wants two:

    final Condition notFull  = lock.newCondition();
    final Condition notEmpty = lock.newCondition();

    void put(E e) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();
            items[tail] = e; …; count++;
            notEmpty.signal();        // wake a CONSUMER specifically
        } finally { lock.unlock(); }
    }

  With one monitor you must notifyAll and wake producers to tell
  consumers something. With two conditions you signal exactly the
  right set — which is a real throughput difference under contention.

  FAIRNESS IS USUALLY THE WRONG CHOICE:

    new ReentrantLock(true)    grants in FIFO order

  It prevents starvation, but throughput can drop by an order of
  magnitude, because every handoff forces a context switch instead of
  letting a running thread barge in. Use it only when you have
  measured starvation.

  READWRITELOCK — many readers OR one writer:

    ReadWriteLock rw = new ReentrantReadWriteLock();
    rw.readLock().lock();  try { … } finally { rw.readLock().unlock(); }

  It only pays off when reads DOMINATE and are LONG. For short reads
  the extra bookkeeping loses to a plain lock. And a write lock
  starves under a constant read load unless fair mode is on — which
  brings back the throughput cost.

  StampedLock (Java 8) ADDS OPTIMISTIC READING:

    long stamp = sl.tryOptimisticRead();
    int x = this.x, y = this.y;                 // read without lock
    if (!sl.validate(stamp)) { /* retry under readLock */ }

  Very fast for read-heavy data — and NOT reentrant, which surprises
  people who treat it as a drop-in.

  PERFORMANCE, HONESTLY: an UNCONTENDED synchronized block is nearly
  free. The JVM uses lightweight (CAS-based) locking and only
  "inflates" to an OS monitor under real contention. Modern JITs also
  eliminate locks entirely when escape analysis proves an object is
  thread-local. So "synchronized is slow" is a statement about
  CONTENTION, not about the keyword — and the fix for contention is
  less shared state, not a different lock class.

Interview Questions

Beginner: What exactly does synchronized guarantee?

Two things, and people usually remember only the first.

Mutual exclusion — one thread at a time inside blocks guarded by the same monitor.

Visibility — everything written before releasing a monitor is visible to the next thread that acquires that same monitor. Without this, a thread could read a stale value indefinitely, because the JIT and the hardware are free to keep values in registers and caches.

The practical consequence is that synchronizing only the writer is broken. Reads do not conflict with each other, so exclusion is not the issue — but a reader that never acquires the monitor has no visibility guarantee at all.

If you need only the second guarantee, volatile is much cheaper. It gives visibility and ordering but not atomicity, which is why it is right for a flag and wrong for a counter.

Beginner: Why must wait() be inside a while loop?

Because wait() returning does not mean the condition is true. Three independent reasons:

  1. Spurious wakeups. wait() may return with no notify at all — permitted by the specification and observed on real platforms.
  2. notifyAll wakes everyone. Waiters race to reacquire the monitor; the first may consume the condition, so the rest must re-check.
  3. State can change between the signal and reacquisition. You are not handed the lock atomically with the notification.
synchronized (lock) {
    while (!condition) lock.wait();   // never `if`
    proceed();
}

With if, the thread proceeds on a condition that no longer holds — a correctness bug, and one that reproduces rarely enough to reach production.

Mid: How do you prevent deadlock?

Deadlock needs all four Coffman conditions: mutual exclusion, hold-and-wait, no preemption, and circular wait. Breaking any one prevents it, and circular wait is the practical target.

Impose a global lock order. The account-transfer case deadlocks because two callers disagree about direction:

Account first  = from.id() < to.id() ? from : to;
Account second = from.id() < to.id() ? to   : from;
synchronized (first) { synchronized (second) { … } }

The ordering key must be unique and stable. identityHashCode works as a fallback but can collide, so it needs a tie-breaker lock.

Other approaches: break hold-and-wait with tryLock(timeout) plus randomised backoff — which trades deadlock for possible livelock; avoid nested locks entirely by reducing granularity; or avoid locks by using immutable data or a concurrent collection.

The rule that prevents most real cases: never call unknown code while holding a lock. Callbacks and overridable methods can take locks you have never heard of, which is how two components that do not reference each other end up in a cycle.

Detection: jstack reports "Found one Java-level deadlock" with both stacks for intrinsic locks. It cannot detect a logical deadlock — everyone waiting on a queue nobody fills.

Mid: What does ReentrantLock give you over synchronized?

Multiple conditions is the feature with no equivalent. A bounded buffer wants notFull and notEmpty; with one monitor you must notifyAll and wake producers in order to reach consumers.

What it costs is that nothing releases it for you — a missing finally leaks the lock permanently — and you lose the JVM's deadlock reporting for intrinsic locks.

Performance is not the reason to switch. Uncontended synchronized is nearly free and benefits from lock elision; the two are comparable under contention. Choose ReentrantLock for a capability you actually need.

Senior: A service is slow under load but CPU is at 20%. How do you find the lock?

Idle CPU with poor throughput means threads are waiting, not computing. The question is what they wait on.

Take three thread dumps a few seconds apart. Threads at the same stack in all three are stuck; the state distribution names the problem:

PatternMeans
Many BLOCKED on one monitorLock contention — the dump names the owner
Many RUNNABLE in socket readsA slow downstream, not a lock
Pool threads all in one methodPool exhaustion behind one dependency
Many WAITING on a queueIdle pool — the bottleneck is upstream

The most common root cause is I/O inside a critical section. A 200 ms call under a lock serialises everything: 100 concurrent requests take 20 seconds while the CPU does nothing. The fix is to move the call out of the lock, not to make the lock faster.

Tools beyond dumps: async-profiler in lock mode, or JFR's jdk.JavaMonitorEnter events, attribute wait time to specific monitors and give you the total blocked time rather than a snapshot.

The fixes, in order of value: move I/O out of the critical section; split the lock by invariant; replace the structure with a concurrent one (ConcurrentHashMap instead of a synchronized map); or remove the sharing entirely with immutable data or thread confinement. Switching to ReentrantLock is almost never the answer — the contention is the problem, not the lock implementation.

Senior: Is synchronized slow? Explain what the JVM actually does.

Uncontended, it is nearly free. "Slow" is a statement about contention, not about the keyword.

The JVM uses lightweight locking: acquiring an uncontended monitor is a CAS on the object header, on the order of nanoseconds, with no OS involvement. Only when a second thread actually contends does the lock inflate into a heavyweight OS monitor with real parking and context switches. That inflation is the expensive part, and it is caused by contention.

The JIT can remove locks altogether. Escape analysis proves an object never leaves the thread and eliminates the lock entirely — which is why a StringBuffer in a local variable costs the same as a StringBuilder. Adjacent blocks on the same monitor can also be coarsened into one.

Biased locking, worth knowing historically: it optimised the repeated-single-thread case even further, but was deprecated in 15 and removed in 18 because the revocation cost hurt modern workloads. If you read older advice about it, it no longer applies.

What this means practically: do not replace synchronized with ReentrantLock for speed — measure them and they are comparable. Under contention, no lock implementation saves you; reduce the sharing. Under no contention, you are optimising something that already costs nanoseconds.

The one real cost of synchronized today is with virtual threads: a virtual thread blocked inside a synchronized block pins its carrier thread, while ReentrantLock does not. That, not performance, is the modern argument for switching.

🏋️ Graded Exercises

1 (easy): Is this thread-safe? 
class Config {
    private String value;
    public synchronized void set(String v) { this.value = v; }
    public String get() { return this.value; }
}
Solution

No. The reader never acquires the monitor, so it has no visibility guarantee — it may see a stale value indefinitely.

The instinct that "reads don't need locking because they don't modify anything" confuses the two guarantees. Mutual exclusion is indeed unnecessary between readers; visibility is not.

// Option A — symmetric synchronization
public synchronized void   set(String v) { this.value = v; }
public synchronized String get()         { return this.value; }

// Option B — cheaper, and enough here
private volatile String value;
public void   set(String v) { this.value = v; }
public String get()         { return this.value; }
ChoiceWhen
volatileSingle independent field, no compound operation
synchronized both sidesSeveral fields with an invariant between them
AtomicReferenceYou need compare-and-set

volatile is right here — one field, no read-modify-write. It would be wrong for a counter, where ++ is still three operations.

2 (easy): Why can these two run at the same time? 
class Registry {
    private static int total;
    public synchronized void addOne()        { total++; }
    public static synchronized void reset()  { total = 0; }
}
Solution

They lock different monitors. The instance method locks this; the static method locks Registry.class. Nothing prevents them running concurrently — and both mutate the same static field, so it is a straightforward race.

class Registry {
    private static int total;
    private static final Object LOCK = new Object();

    public void addOne()       { synchronized (LOCK) { total++; } }
    public static void reset() { synchronized (LOCK) { total = 0; } }
}
FormLocks
synchronized void m()this — one per instance
static synchronized void m()The Class object — one per class
synchronized (obj)Whatever obj is

The principle: one lock per piece of shared state. Static state needs a static lock, and mixing instance and static synchronization over the same data is a guaranteed bug regardless of how many methods carry the keyword.

A dedicated private lock is better than Registry.class, which is publicly reachable and can be locked by anyone.

3 (medium): Show how this deadlocks and fix it. 
void transfer(Account from, Account to, BigDecimal amt) {
    synchronized (from) {
        synchronized (to) {
            from.debit(amt);
            to.credit(amt);
        }
    }
}
Solution

The lock order depends on the arguments. Two concurrent opposite transfers form a cycle:

T1: transfer(A, B)   locks A, waits for B
T2: transfer(B, A)   locks B, waits for A     → deadlock
void transfer(Account from, Account to, BigDecimal amt) {
    Account first  = from.id() < to.id() ? from : to;
    Account second = from.id() < to.id() ? to   : from;
    synchronized (first) {
        synchronized (second) {
            from.debit(amt);
            to.credit(amt);
        }
    }
}
ApproachBreaks which conditionTrade-off
Global lock order by idCircular waitNeeds a unique stable key
tryLock + randomised backoffHold-and-waitPossible livelock; more code
One global lockCircular waitCorrect, but serialises all transfers
Single-threaded per account partitionMutual exclusionAn architectural change

The ordering key must be unique and stable. If ids can be equal — the self-transfer case — handle it explicitly, and if you fall back to System.identityHashCode, collisions require a third tie-breaker lock.

Also missing here: nothing checks sufficient funds, and the two accounts are updated with no transaction boundary. Both matter more than the deadlock in a real ledger.

4 (medium): Two bugs. 
synchronized (lock) {
    if (queue.isEmpty()) lock.wait();
    Item item = queue.remove();
    process(item);
}
// elsewhere:
synchronized (lock) { queue.add(item); lock.notify(); }
Solution

Bug 1 — if instead of while. After wait() returns, the queue may still be empty: a spurious wakeup, or another consumer took the item between the notify and this thread reacquiring the monitor. queue.remove() then throws.

Bug 2 — notify() with non-uniform waiters. It wakes one arbitrary thread. If producers also wait on this monitor when a bound is reached, the wakeup can go to a thread that cannot proceed, while the consumer that could stays asleep — a lost wakeup that presents as a hang.

synchronized (lock) {
    while (queue.isEmpty()) lock.wait();     // while
    Item item = queue.remove();
    lock.notifyAll();                        // notifyAll
}
process(item);                               // outside the lock

A third improvement: process(item) was inside the critical section, so every consumer serialises on unrelated work. Move it out.

What you would actually write:

Item item = queue.take();     // BlockingQueue — blocks, no lock code
process(item);

BlockingQueue gets all of this right, including the interruption semantics. Hand-rolled wait/notify is worth understanding and rarely worth writing.

5 (hard): Why is this slow under load, with the CPU nearly idle? 
public synchronized void processOrder(Order o) {
    validate(o);                              // 1 ms
    PaymentResult r = paymentGateway.charge(o); // 200 ms network
    inventory.reserve(o);                     // 5 ms
    repository.save(o, r);                    // 10 ms
}
Solution

The lock is held across a 200 ms network call, so every order serialises. Throughput is capped at about 4.6 orders per second regardless of how many cores or threads you have, and the CPU is idle because everyone is waiting.

public void processOrder(Order o) {
    validate(o);                                    // no shared state
    PaymentResult r = paymentGateway.charge(o);     // NO lock held

    synchronized (inventoryLock) {                  // only the shared part
        inventory.reserve(o);
    }
    repository.save(o, r);                          // DB has its own
}                                                   //   concurrency control
StepNeeds the lock?Why
validateNoOperates on the argument only
chargeNoExternal call — unbounded duration, and the gateway is not your state
reserveYesGenuinely shared mutable state
saveNoThe database enforces its own isolation

The rule: never hold a lock across a call you cannot bound. Beyond throughput, the gateway may take locks of its own, which is how deadlocks form between components that never reference each other.

The correctness caveat that must be handled is that removing the lock breaks atomicity between charging and reserving. A failed reservation after a successful charge needs compensation — releasing the reservation or refunding — and an idempotency key on the charge so a retry does not bill twice. That is a distributed-systems problem, and a lock never solved it anyway.

Better still, reserve inventory before charging: cancelling a reservation is cheap, and refunding a payment is not.

6 (hard): Implement a bounded buffer with ReentrantLock and explain why two conditions beat one monitor.
Solution 
public class BoundedBuffer<E> {
    private final Object[] items;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    public BoundedBuffer(int capacity) { items = new Object[capacity]; }

    public void put(E e) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();
            items[tail] = e;
            tail = (tail + 1) % items.length;
            count++;
            notEmpty.signal();          // wake ONE consumer
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    public E take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();
            E e = (E) items[head];
            items[head] = null;                  // let GC collect it
            head = (head + 1) % items.length;
            count--;
            notFull.signal();           // wake ONE producer
            return e;
        } finally { lock.unlock(); }
    }
}
DetailWhy
while, not ifSpurious wakeups and races after reacquisition
unlock() in finallyNothing releases it for you
items[head] = nullOtherwise the buffer retains a strong reference — a slow leak
signal, not signalAllSafe here because each condition has uniform waiters

The two-condition argument: with a single monitor, producers and consumers share one wait set, so notify() may wake a producer when a consumer needed waking — a lost wakeup. The safe fallback is notifyAll(), which wakes every waiter on every operation and wastes context switches under load.

Two conditions let put signal consumers specifically, so exactly one relevant thread wakes. That is what makes signal (rather than signalAll) safe here, and it is a measurable throughput difference under contention.

In production, use ArrayBlockingQueue — this is essentially its implementation, already tested, with interruption and timeout variants. Write this to understand it, not to ship it.

🎯 Key Takeaways

  • synchronized gives mutual exclusion and visibility — locking only the writer leaves readers seeing stale data.
  • Instance and static synchronization use different monitors, so both can run at once.
  • Locking this is a public lock — use a private final lock object.
  • Never lock on interned strings or boxed integers; the object is shared JVM-wide.
  • Double-checked locking requires volatile, or another thread can see a partially constructed object.
  • Intrinsic locks are reentrant, which is what makes nested synchronized calls work.
  • Never call unknown code — or do I/O — while holding a lock.
  • Individually atomic calls do not compose: use putIfAbsent / computeIfAbsent.
  • Deadlock needs all four Coffman conditions; break circular wait with a global lock order on a stable unique key.
  • tryLock(timeout) breaks hold-and-wait but can livelock without randomised backoff.
  • wait() belongs in a while loop — spurious wakeups are real, and state can change before reacquisition.
  • Prefer notifyAll() unless every waiter waits on the same condition.
  • ReentrantLock needs finally — a leaked lock hangs everything.
  • Multiple Conditions are its unique capability, letting you signal exactly the right waiters.
  • Fair locks prevent starvation at a large throughput cost — use only when measured.
  • Uncontended synchronized is nearly free (CAS-based, and elidable by escape analysis) — contention is the cost, not the keyword.
  • The modern reason to prefer ReentrantLock is virtual threads, since synchronized pins the carrier.
