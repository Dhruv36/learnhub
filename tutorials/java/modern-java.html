var, Text Blocks & Newer APIs Modern Java

What you'll master: var as compile-time inference, not dynamic typing — including the two cases where it infers something you did not intend (var x = null is illegal, var list = new ArrayList<>() silently becomes ArrayList<Object>); text blocks and the closing-delimiter rule that decides your indentation; why List.of is not Arrays.asList and neither is new ArrayList<>(); the Collectors.toList vs Stream.toList mutability difference that bites in production; and a version map keyed to what you can actually use on the LTS you target. Prerequisites: Collections and Streams.

Part 1 — var: Local Type Inference

  var IS STATIC TYPING WITH THE TYPE WRITTEN BY THE COMPILER.

    var count = 10;                   // int, forever
    var name  = "Ada";                // String
    var users = new ArrayList<User>();// ArrayList<User>

    var x = 10;
    x = "hello";                      // ❌ COMPILE ERROR

  The bytecode is identical to writing the type by hand. Nothing is
  deferred to runtime, nothing is boxed, nothing is slower. `var` is
  purely a source-level convenience.

  WHERE IT ACTUALLY EARNS ITS KEEP — when the type appears twice:

    Map<String, List<Order>> byCustomer = new HashMap<>();
    var byCustomer = new HashMap<String, List<Order>>();

  and when the type is unspeakably long but obvious:

    var entry = Map.entry("k", 42);   // Map.Entry<String,Integer>

  WHERE IT HURTS — when the initializer does not say the type:

    var result = service.process(input);   // ??? what IS this
    var flag   = compute();                // boolean? Boolean? int?

  The rule that survives review: THE READER MUST BE ABLE TO NAME THE
  TYPE FROM THE LINE ITSELF. A constructor call or a literal says it;
  a method call usually does not.

  THE RESTRICTIONS ARE ALL CONSEQUENCES OF "INFER FROM INITIALIZER":

    var y;                    // ❌ nothing to infer from
    var z = null;             // ❌ null has no type
    var f = () -> 42;         // ❌ lambdas need a target type
    var a = {1, 2, 3};        // ❌ array initializer has no type

  and it is LOCAL only — not fields, not parameters, not return types.
  Those are API surface, where an explicit type is documentation.

  THE ONE THAT SILENTLY DOES THE WRONG THING:

    var list = new ArrayList<>();     // ArrayList<Object> !
    list.add("a");
    list.add(42);                      // compiles fine — and now the
                                       // list is a bag of Objects

  With an explicit left-hand type the diamond has a target to infer
  from. With `var` there is none, so it infers Object and the type
  safety is gone with no warning.
DeclarationInferred typeVerdict
var n = 10;intFine — literal says it
var d = 10.0;double, not floatFine, but know the default
var c = 'x';charFine
var l = 10L;longFine — suffix required
var m = new HashMap<String,Integer>();HashMap<String,Integer>Good — removes the duplicate
var m = new HashMap<>();HashMap<Object,Object>Trap — silent loss of typing

The subtle one: var infers the concrete type, not an interface. var list = new ArrayList<String>() gives you an ArrayList, so you can call ensureCapacity on it — and if you later swap to LinkedList, calls that leaked into the concrete API break. With List<String> list = … that could not happen. Inside a short method it does not matter; over a long one it can.

Part 2 — Text Blocks

  THE PROBLEM THEY SOLVE — escaping and concatenation obscuring the
  content:

    String json = "{\n" +
                  "  \"name\": \"Ada\",\n" +
                  "  \"id\": 42\n" +
                  "}";

  THE TEXT BLOCK (Java 15+):

    String json = """
        {
          "name": "Ada",
          "id": 42
        }""";

  No escaping of quotes, no \n, no concatenation. The content reads
  as the content.

  THE INDENTATION RULE IS THE PART PEOPLE GET WRONG.

  The compiler finds the MINIMUM indentation across all non-blank
  lines AND the closing delimiter line, then strips that much from
  every line. So the closing """ position is a control:

    String a = """
        hello
        """;              // closing at col 8 → "hello\n"

    String b = """
        hello
    """;                  // closing at col 4 → "    hello\n"
                          //   ^ 4 extra spaces kept on every line!

  THE TRAILING NEWLINE IS ALSO CONTROLLED BY PLACEMENT:

    """
    line""";              // no trailing newline
    """
    line
    """;                  // trailing newline

  ESCAPES YOU STILL NEED:

    \n     an explicit newline (rarely wanted here)
    \"""   three literal quotes
    \s     a space that survives trailing-space stripping
    \      at end of line: JOIN this line to the next (no newline)

  The line-continuation backslash is the one worth remembering — it
  lets you wrap a long single-line string in the source:

    String q = """
        SELECT id, name FROM users \
        WHERE active = true""";
        // one line, no newline in the middle

  TRAILING SPACES ARE STRIPPED from every line, always. If you need
  one, write \s.

  INTERPOLATION DOES NOT EXIST. Use formatted():

    String msg = """
        Hello %s, you have %d messages""".formatted(name, count);

Part 3 — Collection and Stream Additions

  THE THREE "LISTS" THAT ARE NOT THE SAME THING:

    List.of("a","b")             immutable, rejects null, Java 9
    Arrays.asList("a","b")       FIXED SIZE, mutable elements, allows null
    new ArrayList<>(List.of(…))  fully mutable

    List.of(…).add(x)            → UnsupportedOperationException
    Arrays.asList(…).add(x)      → UnsupportedOperationException
    Arrays.asList(…).set(0, x)   → WORKS, and writes through to the
                                   backing array!

  Arrays.asList is a VIEW over the array. Setting an element mutates
  the array you passed in — a genuine source of surprise.

  List.of ALSO REJECTS NULL, at construction and in contains():

    List.of("a", null)           → NullPointerException
    List.of("a").contains(null)  → NullPointerException

  That is deliberate — these are meant to be honest immutable
  collections — but it breaks code that used to pass nulls through.

  Map.of IS LIMITED TO 10 PAIRS. Beyond that:

    Map.ofEntries(entry("a",1), entry("b",2), …);   // any size

  and Map.of has NO DEFINED ITERATION ORDER — it is deliberately
  randomised per JVM run so nobody depends on it.

  STREAM.TOLIST vs COLLECTORS.TOLIST — the difference that bites:

    stream.collect(Collectors.toList())   // usually ArrayList,
                                          // MUTABLE, allows null
    stream.toList()                       // UNMODIFIABLE, allows null

  Code that collected and then sorted in place breaks when switched to
  toList(). Note Collectors.toList() only "usually" gives ArrayList —
  the contract does not promise it, so mutating it was always a bet.

    stream.collect(Collectors.toUnmodifiableList())  // explicit, 10+

  OTHER ADDITIONS THAT CARRY THEIR WEIGHT:

    String:   isBlank(), strip(), stripLeading/Trailing(),
              repeat(n), lines(), formatted(), transform(fn)
    Optional: ifPresentOrElse, or, stream, isEmpty
    Stream:   takeWhile, dropWhile, iterate(seed, pred, next), mapMulti
    Files:    readString, writeString
    Objects:  requireNonNullElse, requireNonNullElseGet

  strip() vs trim() IS NOT COSMETIC: trim() removes chars <= U+0020,
  which predates Unicode. strip() is Unicode-aware and removes things
  like the non-breaking space that trim() leaves behind — a classic
  cause of "the validation says the field is not empty".

  HOW TO READ THIS TABLE IN PRACTICE:

  The features arrive as PREVIEWS one or two releases before they go
  final, and a preview feature needs --enable-preview at BOTH compile
  and run time, is not binary-compatible across releases, and can
  change. That is why "records are in 14" and "records are in 16" are
  both true statements about different things — 16 is when you can use
  them without a flag.

  THE LTS CADENCE: an LTS every two years since 17 (17, 21, 25),
  each supported for years; the releases between are supported for six
  months. Almost every production system targets an LTS, which is why
  the practical question is never "what is the newest Java" but "which
  LTS are we on".

  WHAT ACTUALLY DRIVES AN UPGRADE:
    8  → 11   the module-related removals (JAXB, CORBA) and the
              switch to the new release cadence
    11 → 17   strong encapsulation becomes the default — the illegal
              reflective access that only warned in 11 now fails
    17 → 21   virtual threads, which change how you write servers
              rather than merely how you write expressions

  So the 17→21 move is the one with a real payoff for throughput, and
  the 11→17 move is the one most likely to break something at runtime
  rather than at compile time.

Part 5 — Other Modern APIs Worth Knowing

  THE HTTP CLIENT (Java 11) replaces HttpURLConnection:

    HttpClient client = HttpClient.newHttpClient();
    HttpRequest req = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/users"))
        .header("Accept", "application/json")
        .timeout(Duration.ofSeconds(10))
        .GET()
        .build();

    HttpResponse<String> res =
        client.send(req, HttpResponse.BodyHandlers.ofString());

  It supports HTTP/2, async via sendAsync returning a
  CompletableFuture, and — the practical part — it has a TIMEOUT that
  is easy to set, which HttpURLConnection made awkward enough that
  people skipped it.

  SEQUENCED COLLECTIONS (Java 21) finally give a first/last API:

    list.getFirst();  list.getLast();
    list.addFirst(x); list.removeLast();
    list.reversed();                       // a VIEW, not a copy

  Before this, "get the last element" was list.get(list.size()-1) for
  a List, a different method for a Deque, and impossible for a
  LinkedHashSet. SequencedCollection unifies them.

  Note reversed() is a view: it costs nothing to create, and it
  reflects later changes to the underlying collection.

  HELPFUL NULLPOINTEREXCEPTIONS (Java 14) changed debugging:

    Cannot invoke "String.length()" because the return value of
    "java.util.Map.get(Object)" is null

  instead of "NullPointerException" and a line number with four
  possible culprits on it. It is on by default from 15.

  RECORD/SEALED/PATTERNS are covered in their own lessons — see
  Records & Sealed Types and Pattern Matching.

Part 6 — Concise vs Clear

  EVERY FEATURE HERE REMOVES CHARACTERS. THAT IS NOT THE POINT.
  The point is whether the reader reconstructs the intent faster.

  CASE 1 — var helps:

    Map<String, List<Order>> ordersByCustomer = new HashMap<>();
    var ordersByCustomer = new HashMap<String, List<Order>>();

  The type is stated once instead of twice, and it is still stated.

  CASE 2 — var hurts:

    var result = repository.findMatching(criteria);

  Nothing on this line says whether result is a List, a Stream, an
  Optional or a page object, and the next line probably depends on it.

  CASE 3 — the variable name can pay the debt:

    var userNamesSorted = svc.fetch();     // still vague
    List<String> names  = svc.fetch();     // says it

  CASE 4 — text blocks help when the content has structure:

    String sql = """
        SELECT id, name
        FROM users
        WHERE active = true
        ORDER BY name""";

  and hurt for a one-liner, where they add three lines of ceremony to
  a string that fit on one.

  THE TEST I APPLY: would a colleague reading this in a review need to
  open another file to know what a variable holds? If yes, write the
  type. The feature is not the goal; the reviewer's speed is.

Interview Questions

Beginner: Is var dynamic typing?

No. var is local variable type inference — the compiler works out the type from the initializer and writes it into the bytecode. The result is identical to declaring the type by hand: same type, same performance, no runtime cost.

The proof is that reassignment fails to compile. var x = 10; x = "hi"; is an error, because x is an int permanently.

The restrictions all follow from needing an initializer to infer from: no var without one, no var x = null, no bare lambda or array initializer. And it is limited to local variables — fields, parameters and return types are API surface, where the explicit type is documentation for callers.

Beginner: When does var make code worse?

When the line does not say what the type is. var result = service.process(input) forces a reader to open another file to learn whether they are holding a List, an Optional or a domain object.

The usable rule: use var when the initializer names the type — a constructor call, a literal, a cast — and write the type when it does not.

There is one case where it is not merely unclear but wrong:

var list = new ArrayList<>();   // ArrayList<Object>
list.add("a");
list.add(42);                    // compiles

The diamond infers from the left-hand type, and with var there is none, so it lands on Object with no warning and the type safety is gone.

A subtler one: var infers the concrete class, so var list = new ArrayList<String>() lets calls to ArrayList-specific methods leak in, and swapping the implementation later breaks them.

Mid: How does a text block decide indentation?

The compiler computes the minimum indentation across all non-blank lines and the closing delimiter line, then strips that amount from every line. Trailing spaces are stripped unconditionally.

The consequence people miss is that the closing """ participates in the calculation, which makes its position a control:

String a = """
    hello
    """;         // → "hello\n"

String b = """
    hello
""";             // → "    hello\n"  (delimiter at col 0 keeps 4 spaces)

Placement also decides the trailing newline: content ending immediately before """ has none; a delimiter on its own line adds one.

Two escapes remain useful — \s preserves a trailing space that would otherwise be stripped, and a backslash at end of line joins that line to the next, which lets you wrap a long single-line string in the source without introducing a newline.

And there is no interpolation: use .formatted(...), which chains neatly off the closing delimiter.

Mid: What is the difference between List.of, Arrays.asList and new ArrayList<>()?

The dangerous one is Arrays.asList: it is a fixed-size view over the array, so set writes through and mutates the caller's array. It is not immutable, despite being used as though it were.

List.of is genuinely immutable and rejects null aggressively — contains(null) throws, not returns false. That is deliberate but does break code that passed nulls through.

Related: Map.of caps at 10 pairs (use Map.ofEntries beyond that) and has deliberately randomised iteration order so nobody depends on it.

Senior: A team upgrades from 11 to 21 and replaces collect(toList()) with toList() everywhere. What breaks?

Anything that mutated the result. Stream.toList() returns an unmodifiable list, so Collections.sort(result), result.add(...) and result.removeIf(...) all start throwing UnsupportedOperationException.

The failure mode is what makes it expensive: it is a runtime exception, not a compile error, so a blanket find-and-replace passes review and CI unless the mutating path happens to be covered by a test. In practice it surfaces on an uncommon branch in production.

Worth being precise about the old behaviour: Collectors.toList() never promised an ArrayList — the contract says nothing about mutability. Code that relied on it was always betting on an implementation detail; the upgrade just collected the bet.

The fix is to say what you need: collect(toCollection(ArrayList::new)) where mutability is required, toList() where it is not, and preferably move the sort into the stream with .sorted() so no mutation is needed at all.

The general lesson for that upgrade: 11→17 breaks things at runtime through strong encapsulation of internals, and 17→21 mostly adds. This particular trap is self-inflicted — the mechanical rewrite, not the JDK.

Senior: How do you decide which Java version to target?

Target an LTS — 8, 11, 17 or 21 — because non-LTS releases get six months of support and then force a move. The real question is which LTS, and it is decided by constraints rather than by feature lists.

What actually blocks the move is usually the runtime environment: the base images, the build agents, the APM agent, and any framework with a hard floor. Spring Boot 3 requires 17, which has pulled more teams forward than any language feature.

The upgrade that hurts is 11→17, because strong encapsulation becomes the default. Reflective access into JDK internals that merely warned on 11 now throws, and the offenders are typically libraries you do not control — old mocking frameworks, serialisers, bytecode tools. Those failures are at runtime and often on a rare path.

The upgrade with the biggest payoff is 17→21, and it is virtual threads rather than syntax. A blocking-style server can hold hundreds of thousands of concurrent requests without a thread per request, which changes an architecture decision rather than a coding style. Pattern matching and record patterns are pleasant; virtual threads are the reason to move.

Preview features are not a target. They need --enable-preview at both compile and run time, are not binary-compatible across releases, and can change or be withdrawn. Building on one commits you to recompiling on every upgrade.

My default recommendation for a new service today is 21, and for an existing one, move to the LTS your framework requires and treat the reflective-access breakage as the real work.

Arrays.asList is a view, not a copy. It is fixed-size — add and remove throw — but set writes straight through to the backing array. Code that treats it as a defensive copy is handing out a mutable window into its own state.

List.of rejecting contains(null) surprises people. The collection cannot contain null, so the argument is treated as a programming error rather than answered. Migrating Arrays.asList to List.of in code that probes with nulls turns a false into an exception.

What to use: List.of for a fixed set of non-null values; new ArrayList<>(Arrays.asList(arr)) when you want a mutable independent copy.

4 (medium): This worked on Java 11 and throws on 21. Why, and how would you fix it? 
List<String> names = users.stream()
        .map(User::name)
        .toList();
Collections.sort(names);
return names;
Solution

Stream.toList() returns an unmodifiable list, so Collections.sort throws UnsupportedOperationException. On 11 the code would have used collect(Collectors.toList()), which happens to return a mutable ArrayList.

// BEST — sort inside the stream, no mutation at all
return users.stream()
        .map(User::name)
        .sorted()
        .toList();

// IF you genuinely need a mutable result
List<String> names = users.stream()
        .map(User::name)
        .collect(toCollection(ArrayList::new));
CollectorMutabilityNulls
Collectors.toList()Unspecified — currently ArrayListAllowed
Collectors.toUnmodifiableList()UnmodifiableRejected
Stream.toList()UnmodifiableAllowed

The reason this is expensive in practice is that it fails at runtime rather than at compile time, so a mechanical rewrite passes review and only breaks on whichever branch actually mutates.

The honest reading of the old code: Collectors.toList() never promised mutability. Relying on it was always a bet on an implementation detail — the upgrade only collected it. toCollection states the requirement instead of assuming it.

5 (hard): Review this method for modern-Java usage. 
public String buildQuery(Map<String,String> filters) {
    var sb = new StringBuilder();
    sb.append("SELECT * FROM orders WHERE 1=1");
    for (var e : filters.entrySet()) {
        sb.append(" AND ").append(e.getKey())
          .append(" = '").append(e.getValue()).append("'");
    }
    return sb.toString();
}
Solution

The modern-syntax question is the least important thing here — this is SQL injection. Values are concatenated straight into the statement, so a filter value of ' OR '1'='1 rewrites the query.

public PreparedStatement buildQuery(Connection c, Map<String,String> filters)
        throws SQLException {
    var allowed = Set.of("status", "customer_id", "region");   // whitelist
    var clauses = filters.keySet().stream()
            .filter(allowed::contains)
            .map(k -> " AND " + k + " = ?")
            .collect(joining());

    var sql = """
        SELECT * FROM orders
        WHERE 1=1%s""".formatted(clauses);

    var ps = c.prepareStatement(sql);
    int i = 1;
    for (var k : filters.keySet()) {
        if (allowed.contains(k)) ps.setString(i++, filters.get(k));
    }
    return ps;
}
IssueFix
Values concatenated into SQL? placeholders and setString
Column names concatenatedCannot be parameterised — whitelist them
Iteration order of the map decides the SQLFine for a prepared statement, but pair the clause and parameter loops so the order matches
Manual StringBuilderCollectors.joining() states the intent

Column names are the part people get wrong even after fixing the values. A placeholder can stand in for a value but never for an identifier, so the only safe treatment is an allow-list of known column names.

The var uses here are all fine — every initializer names its type. The text block earns its place because the SQL has structure, and formatted reads better than concatenation.

Order of review matters: modernising the syntax of an injectable query produces a prettier vulnerability. Security first, then style.

6 (hard): A team is on Java 8 and wants to move. Lay out the path and what will break.
Solution

Move in two hops, 8 → 11 → 17 (or 21), not one. Each hop has a distinct failure mode, and combining them makes the failures hard to attribute.

HopWhat breaksHow it shows up
8 → 11Removed Java EE modules (JAXB, JAX-WS, CORBA); sun.misc.Unsafe warnings; tools assuming the old version stringMostly compile/startup — missing classes
11 → 17Strong encapsulation by default — reflective access into JDK internals that only warned now throwsRuntime, often on a rare path
17 → 21Very little; mostly additiveRarely anything

The 11→17 hop is the dangerous one, and the offenders are usually dependencies rather than your code — old mocking frameworks, serialisers, bytecode manipulators reaching into java.base. Upgrade those libraries first; --add-opens is a temporary unblock, not a destination, because it is a per-module escape hatch you must maintain forever.

The sequencing that keeps it manageable:

  1. Upgrade build tooling and all dependencies while still on 8, so library problems are isolated from JDK problems.
  2. Run the existing test suite on 11 with --illegal-access=warn and fix every warning — those are exactly what fails at 17.
  3. Move source/target to 11, ship, and let it soak.
  4. Then 17, where the warnings you already cleared would have become errors.
  5. Then 21 if virtual threads matter to you.

What to expect in return: the 8→11 hop buys support and the new cadence; 11→17 buys the modern language (records, sealed types, switch expressions) and a framework floor that Spring Boot 3 already requires; 17→21 buys virtual threads, which is the only step that changes architecture rather than syntax.

What not to do: rewrite code to use new features during the upgrade. Keep the diff to "it runs on the new JDK", ship that, and modernise afterwards — otherwise a runtime failure could be the JDK or could be your rewrite, and you will not know which.

🎯 Key Takeaways

  • var is compile-time inference, not dynamic typing — same bytecode, same performance, type fixed forever.
  • Use it when the initializer names the type; write the type when a method call hides it.
  • var list = new ArrayList<>() silently infers ArrayList<Object> — the diamond has no target to infer from.
  • var infers the concrete class, so implementation-specific calls can leak in where an interface type would have prevented them.
  • A text block's indentation comes from the minimum indent including the closing delimiter, and its position also decides the trailing newline.
  • Trailing spaces are always stripped; \s keeps one, and a trailing backslash joins lines.
  • There is no string interpolation — use .formatted(...).
  • Arrays.asList is a fixed-size view whose set mutates the array you passed in.
  • List.of is genuinely immutable and rejects null, including in contains.
  • Stream.toList() is unmodifiable while Collectors.toList() happens to be mutable — a runtime break when you swap them.
  • Map.of caps at 10 pairs and randomises iteration order deliberately.
  • strip() is Unicode-aware, trim() is not — the difference shows up as "the field looks empty but validates as non-empty".
  • Target an LTS (8/11/17/21); preview features need a flag and are not binary-compatible across releases.
  • 11→17 is the hop that breaks things at runtime, via strong encapsulation of JDK internals.
  • 17→21 is the hop with the real payoff — virtual threads change architecture, not just syntax.
  • Judge every feature by reader speed, not by character count.
