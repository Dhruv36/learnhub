equals, hashCode & Object OOP

What you'll master: the contract that hash-based collections silently depend on, and the two ways to break it — overriding equals without hashCode makes every lookup fail, so an object you just put in a HashMap cannot be found; and mutating a key after insertion makes the entry unreachable while it remains visible in iteration, memory and size() — the vanishing-object bug, which is a genuine memory leak; why getClass() and instanceof in equals give different, both defensible answers, and why symmetry is impossible to preserve when a subclass adds a field; why compareTo being inconsistent with equals silently drops elements from a TreeSet; and why records exist — they generate all of this correctly and remove the whole category of bug. Prerequisites: Classes and Types for reference versus value.

Part 1 — What Every Object Inherits

  Every class extends Object, so every object has:

    equals(Object)   default: reference identity (==)
    hashCode()       default: derived from identity
    toString()       default: ClassName@hexHash
    getClass()       the runtime class
    clone()          protected, and broadly regarded as broken
    finalize()       deprecated for removal — never use it
    wait/notify      the intrinsic lock, covered in Synchronization

  THE DEFAULTS ARE CONSISTENT AND USUALLY NOT WHAT YOU WANT.

  Two Point objects with the same coordinates are different objects,
  so by default they are not equal and have different hash codes. For
  a VALUE — a point, a money amount, an id — that is wrong: equality
  should mean "same value", not "same object".

  Deciding which you want is the first question, and it is a design
  decision rather than a technical one:

    ENTITY     has an identity that outlives its state — a User with
               an id. Two rows with the same id are the same user even
               if the name differs. Compare by ID.

    VALUE      is defined entirely by its contents — Money, Point,
               LocalDate. Two instances with equal contents are
               interchangeable. Compare by ALL fields.

Part 2 — == vs equals

  ==        for primitives, compares VALUES     -> what you want
            for references, compares IDENTITY   -> same object?

  equals()  whatever the class defines. Object's default is ==, so a
            class that does not override it gets identity semantics.

    String a = new String("hi"), b = new String("hi");
    a == b          // false — two objects
    a.equals(b)     // true  — same contents

  THE NULL RULES, which are asymmetric and worth memorising:

    x.equals(null)     -> false, always (never throws)
    null.equals(x)     -> NullPointerException
    x == null          -> the correct null test
    Objects.equals(a, b) -> null-safe on BOTH sides

Part 3 — The Contract

RuleMeaningBroken by
Reflexivex.equals(x) is trueAlmost nothing — but a NaN field will do it
Symmetrica.equals(b) ⟺ b.equals(a)A subclass adding a field; comparing across types
Transitivea=b and b=c ⟹ a=cA subclass that ignores its own field to stay symmetric
ConsistentRepeated calls give the same resultComparing on mutable state, or on anything external
Null-safex.equals(null) is falseForgetting the null check — an NPE instead
hashCode agreesEqual objects must have equal hash codesOverriding one and not the other
  THE HASHCODE RULE IS THE ONE WITH TEETH

    equal objects        MUST have equal hash codes
    unequal objects      MAY have equal hash codes (a collision — fine)

  The asymmetry is because a HashMap uses the hash to pick a BUCKET,
  then equals to find the entry within it. If two equal objects hash
  differently they land in different buckets, and the lookup never
  reaches the comparison.

  So overriding equals WITHOUT hashCode does not produce a subtly
  wrong result — it produces a map that cannot find what you just put
  in it:

    Map<Point, String> map = new HashMap<>();
    map.put(new Point(1, 2), "origin-ish");
    map.get(new Point(1, 2));      // null  — different hash, wrong
                                   //         bucket, never compared

  ALWAYS OVERRIDE BOTH, TOGETHER. Every IDE generates them as a pair,
  and every static analyser flags one without the other.

Part 4 — The Vanishing Object

  MUTATING A KEY AFTER INSERTION MAKES THE ENTRY UNREACHABLE.

    class Tag { String name; }              // mutable, equals on name

    Tag tag = new Tag("java");
    Set<Tag> tags = new HashSet<>();
    tags.add(tag);                          // hashed on "java" -> bucket 7

    tag.name = "kotlin";                    // hash is now different

    tags.contains(tag);     // FALSE — looks in bucket 12, entry is in 7
    tags.remove(tag);       // fails silently — cannot find it
    tags.size();            // 1 — it is still there
    for (Tag t : tags) …    // yields it — iteration walks buckets

  THE OBJECT IS SIMULTANEOUSLY IN THE SET AND UNFINDABLE.

  It is visible in size(), in iteration, and in a heap dump. It cannot
  be retrieved, cannot be removed, and keeps whatever it references
  alive. That is a genuine MEMORY LEAK, and one that no amount of
  remove() calls will fix.

  WHY IT HAPPENS: the bucket is chosen at INSERTION TIME from the hash
  at that moment. The collection has no way to be notified that a key
  changed — there is no hook, and adding one would cost a listener per
  entry.

  THE FIXES, in order of preference:

  1. IMMUTABLE KEYS. If the key cannot change, the bug cannot exist.
     This is why String, Integer and LocalDate are ideal keys, and why
     records make excellent ones.

  2. Hash only on FIELDS THAT NEVER CHANGE — typically an id assigned
     at construction and final.

  3. Remove before mutating, mutate, then re-insert. Correct, easy to
     forget, and impossible to enforce.
⚠️ This is the strongest practical argument for immutable value types. The contract does not merely ask you to keep hashCode consistent — it assumes the object's equality-relevant state never changes while it is in a hash-based collection. Immutability makes that guarantee structural rather than a discipline someone has to remember, which is why records are the right default for anything used as a key.

Part 5 — Writing equals Correctly

public final class Point {
    private final int x, y;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                 // 1. fast path
        if (!(o instanceof Point p)) return false;  // 2. type + null
        return x == p.x && y == p.y;                // 3. fields
    }

    @Override
    public int hashCode() {
        return Objects.hash(x, y);                  // matches equals
    }
}

  STEP BY STEP:

  1. this == o          identity shortcut. Cheap, and matters when the
                        same object is compared often.
  2. instanceof         handles the null case for free — null is not
                        an instance of anything — and the pattern
                        variable removes the cast.
  3. compare the SAME FIELDS hashCode uses. Any divergence breaks the
     contract.

  FIELD COMPARISON, BY TYPE:

    primitives      ==                     but see float/double below
    objects         Objects.equals(a, b)   null-safe
    arrays          Arrays.equals(a, b)    NOT a.equals(b)
    float/double    Float.compare / Double.compare

  WHY float NEEDS compare: NaN != NaN, so == would make an object with
  a NaN field non-reflexive — x.equals(x) would be false. And +0.0 ==
  -0.0 is true while their bit patterns differ, which breaks the
  agreement with hashCode. Float.compare handles both.
  getClass() vs instanceof — BOTH DEFENSIBLE, PICK DELIBERATELY

    if (o == null || getClass() != o.getClass()) return false;
      -> STRICT. A subclass instance is never equal to a superclass
         one. Symmetry is guaranteed. Breaks Liskov: a Point and a
         ColouredPoint with the same coordinates are unequal even when
         the colour is irrelevant.

    if (!(o instanceof Point p)) return false;
      -> LENIENT. Permits subclass instances to be equal. Cannot be
         made symmetric once a subclass adds a field to the
         comparison.

  THE UNDERLYING PROBLEM IS UNSOLVABLE:

    Point p = new Point(1, 2);
    ColouredPoint c = new ColouredPoint(1, 2, RED);

    p.equals(c)     // true  — Point compares x and y only
    c.equals(p)     // false — ColouredPoint also compares colour
                    // SYMMETRY BROKEN

  Make ColouredPoint ignore colour to restore symmetry, and you break
  transitivity instead (two ColouredPoints of different colours become
  equal through a Point).

  THERE IS NO WAY TO EXTEND AN INSTANTIABLE CLASS AND ADD A VALUE
  COMPONENT WHILE PRESERVING THE CONTRACT. The practical answers are:
  make value classes final, or use composition instead of extension.
  Records enforce the first by being implicitly final.

Part 6 — toString, Comparable and Comparator

  toString — override it. The default, ClassName@1b6d3586, makes every
  log line and every debugger view useless. Include the fields that
  identify the object, and NEVER include secrets: toString output ends
  up in logs, exception messages and crash reports.

  Comparable — the type's ONE natural ordering

    class Version implements Comparable<Version> {
        public int compareTo(Version other) { … }   // negative/0/positive
    }
    Collections.sort(versions);      // uses it implicitly

  Comparator — any other ordering, supplied at the call site

    orders.sort(Comparator.comparing(Order::total)
                          .thenComparing(Order::createdAt)
                          .reversed());
  THE RULE PEOPLE MISS: compareTo SHOULD AGREE WITH equals.

  "Consistent with equals" means
      a.compareTo(b) == 0   if and only if   a.equals(b)

  It is strongly recommended rather than required — and violating it
  silently corrupts sorted collections, because TreeSet and TreeMap
  use compareTo for IDENTITY, not equals.

    record Reading(String sensor, Instant at) { }
    // compareTo compares `at` only

    TreeSet<Reading> set = new TreeSet<>(byTimestamp);
    set.add(new Reading("A", t));
    set.add(new Reading("B", t));    // SAME timestamp
    set.size();                      // 1 — the second was DISCARDED

  The set considers them duplicates because compareTo returned 0,
  even though equals says they differ. No exception, no warning — one
  reading silently vanishes.

  THE FIX: make the comparator total by adding a tie-breaker.

    Comparator.comparing(Reading::at).thenComparing(Reading::sensor)

Interview Questions

Beginner: What is the difference between == and equals?

For primitives, == compares values, which is what you want. For references it compares identity — whether both variables point at the same object.

equals is a method, so it does whatever the class defines. Object's default implementation is identity, so a class that does not override it behaves exactly like ==. String, the wrappers and records override it to compare contents.

So the practical rule is == for primitives and for enum constants, and equals for everything else — with Objects.equals(a, b) when either side might be null, since a.equals(b) throws if a is null while x.equals(null) is simply false.

Beginner: What happens if you override equals but not hashCode?

Hash-based collections stop working for that type, and they fail silently rather than throwing.

A HashMap finds an entry in two steps: it uses the hash code to choose a bucket, then uses equals to find the entry within that bucket. If two equal objects have different hash codes they land in different buckets, so the lookup goes to the wrong bucket and never performs the comparison at all.

The result is that you can put an object into a map and immediately fail to get it back with an equal key — map.get(new Point(1,2)) returns null having just put new Point(1,2) in. The same applies to HashSet, which will happily hold what look like duplicates.

That is why the contract requires equal objects to have equal hash codes. The reverse is not required — unequal objects may share a hash, which is just a collision and is handled by the equals comparison within the bucket.

Mid: What is the vanishing-object bug?

It is what happens when you mutate a key after putting it in a hash-based collection.

The bucket is chosen at insertion time from the hash code at that moment. Change a field that hashCode depends on, and the object's hash changes — but it is still physically in the old bucket. Lookups now compute the new hash, go to a different bucket, and find nothing.

What makes it striking is the contradiction. contains returns false and remove silently fails, while size() still counts it and iteration still yields it. The object is in the collection and unreachable through it at the same time.

That is a genuine memory leak: the entry cannot be removed by any normal means, and it keeps everything it references alive. In a long-lived cache keyed on mutable objects, it accumulates.

The collection cannot detect it — there is no notification when a key's fields change, and adding one would mean a listener per entry. So the fix has to be on your side: immutable keys, which is why String, Integer, LocalDate and records make good ones. Failing that, hash only on fields that are final and assigned at construction.

Mid: getClass() or instanceof in equals?

Both are defensible and they fail differently, so it is worth knowing which trade you are making.

getClass() is strict. A subclass instance is never equal to a superclass one, which guarantees symmetry and transitivity. The cost is that it breaks substitutability: a Point and a subclass that adds nothing to equality still compare unequal, so a collection of Point behaves differently depending on the exact runtime class.

instanceof is lenient. It permits a subclass instance to be equal to a superclass one, which respects substitutability. But it cannot stay symmetric once the subclass adds a field to the comparison: point.equals(colouredPoint) is true while colouredPoint.equals(point) is false.

And the escape people try — having the subclass ignore its extra field to restore symmetry — breaks transitivity instead, because two coloured points of different colours become equal by way of a plain point.

The honest answer is that there is no way to extend an instantiable class, add a value component, and preserve the contract. So the real fix is structural: make value classes final, or use composition — hold a Point rather than extending it. Records take the first option by being implicitly final, which is why the question does not arise for them.

Senior: Why must compareTo be consistent with equals?

Because the sorted collections use compareTo for identity, not just for ordering. TreeSet and TreeMap decide whether two elements are the same by asking whether compareTo returns zero — they never call equals.

So if compareTo returns zero for objects that equals considers different, a TreeSet treats them as duplicates and silently discards the second. Two readings with the same timestamp from different sensors: add both, size is one, and there is no exception or warning.

The failure is particularly nasty because the same data in a HashSet behaves correctly, so it looks like a collection bug rather than a comparator bug — and it depends on the data, so it can appear long after the code ships.

It is documented as "strongly recommended" rather than required, which is the specification acknowledging that inconsistent orderings are sometimes deliberate — BigDecimal is the famous case, where 2.0 and 2.00 compare equal but are not equals, so a TreeSet and a HashSet of the same values have different sizes.

The practical discipline is to make any ordering total by adding tie-breakers until it can only return zero for genuinely equal objects — comparing(Reading::at).thenComparing(Reading::sensor). And if there is no single natural order, do not implement Comparable at all; pass an explicit Comparator at each call site, where the intent is visible.

Senior: How do records change this, and when would you still write equals by hand?

A record generates equals, hashCode and toString from all its components, and generates them consistently — the same fields in both, correct null handling, Double.compare semantics for floating point. That removes the entire category of contract bugs, and it removes the getClass-versus-instanceof question because records are implicitly final.

They are also immutable, which addresses the vanishing-object problem structurally rather than by discipline. That combination — correct equality plus immutability — is what makes a record the right default for anything used as a map key or set element.

Where I would still write it by hand:

Entities with an identity. A JPA entity should compare on its id, not on all fields — two loads of the same row are the same user even if one is stale. Records are the wrong shape for entities anyway, since they are mutable by requirement.

When equality is a subset of the fields. A cached object with a lastAccessed timestamp should not have that participate in equality, and a record compares everything.

Normalisation before comparison. Case-insensitive identifiers, or Unicode normalisation for text, need work inside equals that a generated one will not do — though a better answer is usually to normalise on the way in, in the compact constructor, so the generated equality is then correct.

Performance in a very hot path, occasionally — comparing a cheap discriminator field first. I would want a profile before doing that, since it trades a real correctness risk for a marginal gain.

The wider point is that hand-writing this is a liability rather than a skill: three methods, six contract rules, and no compiler check that they agree. If the shape fits a record, use one.

🏋️ Graded Exercises

1 (easy): Why does the lookup return null? 
class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        return o instanceof Point p && p.x == x && p.y == y;
    }
}

Map<Point, String> map = new HashMap<>();
map.put(new Point(1, 2), "here");
System.out.println(map.get(new Point(1, 2)));   // null
Solution

hashCode was not overridden, so it is still Object's identity-based version. The two Point instances are equals and have different hash codes, which violates the contract.

  put:  hash of instance A -> bucket 7    entry stored in bucket 7
  get:  hash of instance B -> bucket 12   looks in bucket 12
                                          finds nothing, returns null

  equals is never even called — the lookup never reaches the right
  bucket to make the comparison.
@Override public int hashCode() { return Objects.hash(x, y); }

The fields in hashCode must match the fields in equals. Using a subset is safe but causes more collisions; using a superset breaks the contract exactly as omitting the method does.

This is why every IDE generates the pair together, and why static analysers flag one without the other. It is also the strongest argument for a record here — record Point(int x, int y) generates both correctly and this bug cannot be written.

2 (easy): Why is this an overload rather than an override, and what breaks? 
class User {
    private final String id;
    public boolean equals(User other) {       // note the parameter type
        return other != null && id.equals(other.id);
    }
}
Solution

The parameter is User, not Object, so this does not override Object.equals(Object) — it adds a second, unrelated method with the same name.

The class now has both: your equals(User) and the inherited equals(Object), which is still identity-based.

User a = new User("u1"), b = new User("u1");

a.equals(b)                   // true  — YOUR method, static type User
Object o = b;
a.equals(o)                   // false — Object.equals, identity

List.of(a).contains(b)        // false — collections call equals(Object)
map.put(a, x); map.get(b)     // null

Every collection calls equals(Object), because that is the signature declared on Object and collections hold Object references internally. So the class works when you call it directly and fails everywhere it matters.

@Override would have caught this at compile time — "method does not override or implement a method from a supertype." It is the exact case from the Methods lesson: a wrong parameter type produces a silent overload, and the annotation is the check.

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof User u)) return false;
    return id.equals(u.id);
}
@Override public int hashCode() { return id.hashCode(); }
3 (medium): The object is in the set and cannot be found. Explain and fix. 
class Tag { String name; /* equals + hashCode on name */ }

Tag t = new Tag("java");
Set<Tag> tags = new HashSet<>();
tags.add(t);
t.name = "kotlin";

tags.contains(t);   // false
tags.remove(t);     // false
tags.size();        // 1
Solution

The bucket was chosen at insertion time from the hash of "java". Changing the field changed the hash, so contains and remove now compute a different bucket and look in the wrong place. The entry is still physically where it was put.

OperationResultWhy
contains(t)falseHashes to a different bucket
remove(t)falseSame — it cannot find it to remove
size()1The count is not hash-based
IterationYields itWalks every bucket in order

This is a real memory leak, not just a lookup failure. The entry cannot be removed by any normal means and keeps whatever it references reachable. In a long-lived cache keyed on mutable objects it accumulates until something OOMs, and the heap dump shows objects that the code appears to have removed.

FixStrength
Immutable key — record Tag(String name)Structural. The bug becomes unwritable
Hash on a final id assigned at constructionStrong — mutable fields simply do not participate
Remove, mutate, re-insertCorrect and unenforceable; one forgotten call reintroduces it

The collection cannot help you. There is no notification when a key's fields change, and adding one would mean a listener per entry — so the guarantee has to come from the key's type. That is the practical reason String, Integer, LocalDate and records are the keys you see in well-written code.

4 (medium): Show why symmetry cannot be preserved here, and give two designs that avoid the problem. 
class Point          { int x, y; }              // equals on x, y
class ColouredPoint extends Point { Color c; }  // equals on x, y, c
Solution 
Point p        = new Point(1, 2);
ColouredPoint c = new ColouredPoint(1, 2, RED);

p.equals(c)     // TRUE  — Point's equals compares x and y only,
                //         and instanceof accepts the subclass
c.equals(p)     // FALSE — ColouredPoint also compares colour

  SYMMETRY BROKEN. And the consequences are not theoretical:

    List.of(p).contains(c)     // depends which is the argument
    set.remove(x)              // may or may not find it

The obvious repair breaks something else. Make ColouredPoint.equals ignore colour when comparing against a plain Point, and symmetry returns — but transitivity fails:

ColouredPoint red  = new ColouredPoint(1, 2, RED);
ColouredPoint blue = new ColouredPoint(1, 2, BLUE);
Point plain        = new Point(1, 2);

red.equals(plain)   // true
plain.equals(blue)  // true
red.equals(blue)    // FALSE — transitivity broken

There is no way to extend an instantiable class, add a value component, and preserve the contract. Not a limitation of any particular implementation — it follows from the definitions.

DesignHow it avoids the problem
Composition — ColouredPoint has a PointNo inheritance, so no cross-type comparison. Expose asPoint() when a plain point is wanted
Make the value class finalThe subclass cannot exist, so the question never arises. What records do implicitly
getClass() instead of instanceofRestores symmetry and transitivity, at the cost of substitutability — a different trade, not a fix

Composition is the one I would ship, and it is also the honest model: a coloured point is not a specialised point, it is a point plus a colour.

Worth noting the JDK's own java.sql.Timestamp extends java.util.Date has exactly this defect and documents it — its equals is explicitly not symmetric with Date's. It is a permanent warning about adding value components by extension.

5 (hard): A TreeSet silently loses readings. Diagnose and fix. 
record Reading(String sensor, Instant at, double value) { }

Comparator<Reading> byTime = Comparator.comparing(Reading::at);
TreeSet<Reading> set = new TreeSet<>(byTime);

set.add(new Reading("A", t, 20.0));
set.add(new Reading("B", t, 21.0));    // SAME instant
set.size();                            // 1
Solution

TreeSet uses the comparator for identity, not equals. Two elements are "the same" when compare returns zero. The comparator only looks at the timestamp, so two readings at the same instant are duplicates as far as the set is concerned, and the second is discarded.

The record's generated equals says they differ — sensor and value are different — but the set never calls it. There is no exception and no warning.

Comparator<Reading> byTime =
    Comparator.comparing(Reading::at)
              .thenComparing(Reading::sensor);      // TIE-BREAKER

set.size();     // 2
CollectionUses for identityResult here
HashSethashCode then equals2 — correct
TreeSetcompareTo / comparator only1 — silently loses one
ArrayListequals, for contains2

What makes it hard to diagnose is that the same data in a HashSet behaves correctly, so it presents as a collection bug rather than a comparator bug. And it is data-dependent: it only appears when two readings genuinely share a timestamp, which may be rare in test fixtures and routine in production at high sample rates.

The rule is that any comparator used for a sorted set or as map keys must be total — it may only return zero for objects that are genuinely equal. Add tie-breakers until that holds.

The related JDK case worth knowing is BigDecimal: 2.0 and 2.00 compare equal but are not equals, so a TreeSet of those values has a different size from a HashSet of them. It is a deliberate inconsistency, documented, and a reliable source of confusion.

6 (hard): Design equality for a JPA entity with a database-generated id, used in a HashSet before and after persisting.
Solution

This is the case where the generated record equality is wrong and the naive id-based version is also wrong, because the id is null until the entity is persisted.

  THE TRAP

    User u = new User("ada@example.com");      // id is null
    Set<User> set = new HashSet<>();
    set.add(u);                                // hashed on null id
    repository.save(u);                        // id assigned: 42
    set.contains(u);                           // FALSE — hash changed

  The vanishing-object bug, caused by the persistence layer rather
  than by application code.
@Entity
public class User {
    @Id @GeneratedValue private Long id;
    private String email;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        // Hibernate proxies are subclasses: getClass() would break
        if (!(o instanceof User other)) return false;
        return id != null && id.equals(other.id);   // null id -> never
    }                                               // equal to anything

    @Override
    public int hashCode() {
        return getClass().hashCode();    // CONSTANT for all instances
    }
}
DecisionReason
Constant hashCodeThe only value that cannot change when the id is assigned. Legal — the contract permits collisions — at the cost of linear lookup within the bucket
id != null guardA transient entity is equal only to itself, so two unsaved users are distinct
instanceof, not getClass()Hibernate hands you a proxy subclass, so getClass() would make an entity unequal to its own proxy
Compare id onlyAn entity's identity outlives its state — a stale load of row 42 is still user 42

The constant hash code is the part that looks wrong and is not. It means every entity of that type lands in one bucket, so a HashSet of them degrades to a linear scan. That is acceptable because entity sets are typically small — a user's orders, not a million rows — and it is the only way to keep the hash stable across the transient-to-persistent transition.

The alternative worth naming is a business key: a natural, immutable, assigned-at-construction identifier such as a UUID generated by the application rather than the database. Then the hash is stable from the moment of construction, entities are equal before and after persisting, and the hash distributes properly. That is the better design where the domain allows it — and it removes the database from the identity question entirely.

What I would not do is use all fields, as a record would. Two loads of row 42 with a stale name would be unequal, which contradicts what an entity is, and any field mutation would move it in a set.

🎯 Key Takeaways

  • Decide entity or value first — compare by id, or by all fields. It is a design decision, not a technical one.
  • Object.equals is identity, so a class that does not override it behaves exactly like ==.
  • Equal objects must have equal hash codes; unequal ones may collide, which is fine.
  • Overriding one without the other makes a HashMap unable to find what you just put in it — the lookup never reaches the comparison.
  • equals(MyType) is an overload, not an override, and collections call equals(Object).
  • Mutating a key after insertion makes the entry unreachable while still counted and still iterated — a real memory leak.
  • Immutable keys make that bug unwritable, which is the strongest argument for records as keys.
  • Use Double.compare for floating-point fields — NaN breaks reflexivity and signed zero breaks the hash agreement.
  • Use Arrays.equals for array fields; equals on an array is identity.
  • No class can be extended with a new value component while preserving the contract — symmetry and transitivity cannot both survive.
  • So make value classes final, or compose; records are implicitly final.
  • TreeSet and TreeMap use compareTo for identity, never equals — an inconsistent ordering silently drops elements.
  • Make comparators total with tie-breakers, or do not implement Comparable at all.
  • Override toString, and never put secrets in it — it reaches logs and crash reports.
  • Use a record unless you need entity semantics — hand-writing three methods against six contract rules with no compiler check is a liability.
