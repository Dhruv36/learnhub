The Module System (JPMS) Modern Java

What you'll master: what the classpath actually does wrong — no declared dependencies, no encapsulation above public, and silent first-match-wins shadowing; what module-info.java declares and what the JVM checks at launch rather than at first use; why public stopped meaning accessible and what opens exists for; the split-package rule that breaks more migrations than anything else; how the modular JDK affects you even when your own code is not modular; jlink and the image-size argument; and the honest answer to "should we modularize", which for most applications is no. Prerequisites: Build Tools and Annotations & Reflection.

Part 1 — What the Classpath Gets Wrong

  THE CLASSPATH IS A FLAT, ORDERED LIST OF PLACES TO LOOK.

    java -cp app.jar:lib/a.jar:lib/b.jar:lib/c.jar Main

  Everything is thrown into one namespace and searched in order.
  That produces four distinct failure modes.

  1. NO DECLARED DEPENDENCIES.
     A jar does not state what it needs. A missing jar is discovered
     at the moment some code path first touches the class:

       Exception in thread "main" java.lang.NoClassDefFoundError:
           org/apache/commons/lang3/StringUtils

     — possibly weeks into production, on a rare branch. Nothing
     checked at startup, because nothing declared anything.

  2. NO ENCAPSULATION BEYOND public.
     If a class is public, every jar on the classpath can use it.
     A library's "internal" package is only internal by convention:

       com.lib.internal.Cache      // public, therefore fair game

     So library authors cannot change internals without breaking
     users who reached in — which is why so many "internal" classes
     are frozen forever.

  3. FIRST MATCH WINS, SILENTLY.
     Two jars containing org/example/Util.class → the one earlier on
     the classpath wins. No warning. You may be running version 1.2
     of a class while every other class comes from 2.0, and the
     symptom is a NoSuchMethodError far from the cause.

  4. THE JDK ITSELF WAS ONE BLOB.
     rt.jar was ~60MB of everything — Swing, CORBA, XML, the lot —
     shipped to every device whether or not any of it was used.

  JPMS (JAVA 9) ADDRESSES ALL FOUR: modules declare dependencies,
  encapsulate packages, forbid duplicate packages across modules, and
  let the JDK be split into ~70 pieces.

Part 2 — module-info.java

  A MODULE IS A NAMED, SELF-DESCRIBING SET OF PACKAGES. The descriptor
  lives at the source root:

    src/main/java/module-info.java

    module com.example.orders {
        requires com.example.core;          // I need this
        requires java.sql;                  // and this JDK module
        requires transitive com.example.api;// and anyone who requires
                                            // ME also gets this

        exports com.example.orders.api;     // anyone may use this pkg
        exports com.example.orders.spi
            to com.example.admin;           // ONLY this module may

        opens com.example.orders.model;     // deep reflection allowed
                                            // (for Jackson, JPA, …)

        uses  com.example.orders.PricingRule;        // ServiceLoader
        provides com.example.orders.PricingRule
            with com.example.orders.StandardPricing;
    }

  THE FOUR DIRECTIVES THAT MATTER:

    requires             a hard dependency, checked at STARTUP
    requires transitive  callers inherit it — use when your API
                         SIGNATURES mention its types
    exports              compile-time AND runtime access to a package
    opens                runtime REFLECTIVE access, including private

  THE STARTUP CHECK IS THE HEADLINE BENEFIT. The module graph is
  resolved before main() runs, so a missing or cyclic dependency is:

    Error occurred during initialization of boot layer
    java.lang.module.FindException: Module com.example.core not found

  — at second zero, not on some rare code path months later.

  requires transitive IS AN API DECISION, NOT A CONVENIENCE.
  If a public method returns a type from another module, callers
  cannot use your API without that module. Use transitive there.
  If the type is only used internally, plain requires — otherwise
  you have made your dependency part of your public contract and
  cannot drop it without breaking callers.

  PACKAGES ARE NOT EXPORTED BY DEFAULT. That is the inversion: on
  the classpath everything public is open, in a module nothing is
  until you say so.

Part 3 — public Is No Longer Enough

  THE RULE CHANGED. For a class in a module to be usable, ALL of:

    1. the class is public
    2. its package is EXPORTED by the module
    3. the reading module REQUIRES the exporting module

  Miss any one and you get, at compile time:

    error: package com.lib.internal is not visible
      (package com.lib.internal is declared in module com.lib,
       which does not export it)

  This is the point of the whole system: a library can finally have
  internals that are actually internal, and change them.

  exports VERSUS opens IS THE DISTINCTION PEOPLE CONFLATE:

    exports P    compile against it; reflection sees only PUBLIC
                 members, and setAccessible(true) on a private one
                 still fails
    opens   P    no compile-time access granted; DEEP reflection
                 allowed, including private fields

  They are orthogonal, and you often want:

    exports com.example.api;       // the API, compiled against
    opens   com.example.model;     // the DTOs, for Jackson

  THE ERROR YOU WILL ACTUALLY SEE:

    InaccessibleObjectException: Unable to make field private
    java.lang.String com.example.User.name accessible: module
    com.example does not "opens com.example" to module
    com.fasterxml.jackson.databind

  The message names the fix. The reason frameworks need this is that
  they set private fields directly — which is exactly what strong
  encapsulation is designed to stop, so the module must consent.

  ESCAPE HATCHES FOR CODE YOU DO NOT CONTROL:

    --add-opens java.base/java.lang=ALL-UNNAMED
    --add-exports java.base/sun.nio.ch=ALL-UNNAMED
    --add-modules java.sql

  These are launch flags, and they are a maintenance liability: they
  must be repeated in every run configuration, test task, container
  entrypoint and IDE profile, forever. Treat them as a bridge while
  you upgrade the offending library, not a destination.

Part 4 — Split Packages and the Automatic Module

  THE SPLIT-PACKAGE RULE: NO TWO MODULES MAY CONTAIN THE SAME PACKAGE.

    module A  →  com.example.util.Strings
    module B  →  com.example.util.Numbers      ❌ ILLEGAL

  Even though the CLASSES differ, the PACKAGE is split, and the
  module system refuses to resolve:

    Error: Module A reads package com.example.util from both A and B

  This breaks more migrations than any other rule, because the
  classpath permitted it happily. Common real cases: a library and
  its "-compat" jar, javax.annotation shipped by three different
  dependencies, or an old jar that packaged classes into a JDK
  package.

  There is no flag to allow it. You must merge the packages, rename
  one, or shade.

  AUTOMATIC MODULES ARE THE MIGRATION BRIDGE.

  Put a plain non-modular jar on the MODULE PATH and it becomes an
  automatic module:

    - name derived from Automatic-Module-Name in its MANIFEST, or
      failing that from the FILE NAME (guava-31.1-jre.jar →
      "guava") — which is why relying on the filename is fragile
    - exports ALL its packages
    - requires ALL other modules (reads everything)

  So it participates in the graph without being modularized, letting
  you convert bottom-up. The catch: a module cannot require a jar
  that is still on the classpath, so your dependencies must move to
  the module path before you can modularize.

  THE UNNAMED MODULE is where classpath code lives. It reads every
  module, exports everything, and — critically — a NAMED module can
  never require it. That asymmetry is what makes migration one-way
  and why "just modularize the app" fails until the libraries move.

  IF YOU PUBLISH A LIBRARY, ADD ONE LINE TO YOUR MANIFEST:

    Automatic-Module-Name: com.example.mylib

  It costs nothing, requires no module-info, and stops your consumers
  depending on your filename. This is the single highest-value module
  action for most library authors.

Part 5 — The Modular JDK and jlink

  THE JDK ITSELF WAS SPLIT INTO ~70 MODULES:

    java.base        always implicitly required — lang, util, io, net
    java.sql         JDBC
    java.desktop     Swing/AWT
    java.logging     j.u.l
    jdk.unsupported  sun.misc.Unsafe, explicitly for those who must

  You never write "requires java.base" — it is automatic.

  THINGS WERE ALSO REMOVED. Java EE and CORBA modules were deprecated
  in 9 and DELETED in 11:

    java.xml.bind (JAXB), java.activation, java.xml.ws, java.corba

  So an 8→11 upgrade fails with NoClassDefFoundError on JAXB classes
  that had "always been there". The fix is to add the artifacts as
  ordinary dependencies — they now live on Maven Central.

  jlink BUILDS A CUSTOM RUNTIME CONTAINING ONLY WHAT YOU NEED:

    jlink --add-modules com.example.app \
          --output ./runtime \
          --compress=2 --no-header-files --no-man-pages \
          --strip-debug

    ./runtime/bin/java -m com.example.app/com.example.Main

  A hello-world image is ~35MB against a ~300MB JDK. For containers
  and desktop distribution that is a real win, and it is the most
  concrete payoff the module system delivers.

  BUT: jlink needs every module to be a real module. Automatic
  modules are NOT accepted, so one non-modular dependency blocks the
  whole thing. In practice that means most server applications cannot
  use jlink without jdeps/ModiTect gymnastics — which is why the
  benefit stays theoretical for many teams.

  THE PRACTICAL ALTERNATIVE most teams reach instead: a JRE-flavoured
  base image, or a native image via GraalVM. Both get the size win
  without requiring the dependency tree to be modular.

Part 6 — Should You Modularize?

  FOR MOST APPLICATIONS, NO. That is not cynicism; it is what the
  ecosystem settled on after several years.

  WHY THE COST IS HIGH:

    - every dependency must be a real module or an automatic one,
      and split packages have no workaround
    - reflective frameworks need opens declarations, discovered one
      InaccessibleObjectException at a time
    - build tooling, test runners and agents all need module-path
      configuration
    - the payoff (jlink, strong encapsulation) mostly matters at a
      boundary you SHIP ACROSS

  WHERE IT IS CLEARLY WORTH IT:

    1. YOU PUBLISH A LIBRARY. Real internals you can change, and
       consumers get a checked dependency graph. This is the case
       the system was designed for.
    2. YOU SHIP A DESKTOP OR CLI APP. jlink turns a 300MB JDK
       dependency into a 40MB bundle you can hand to a user.
    3. YOU HAVE A PLUGIN ARCHITECTURE. Module layers can load and
       unload plugin graphs at runtime with real isolation.
    4. A LARGE MONOLITH NEEDS ENFORCED INTERNAL BOUNDARIES, and
       "everyone agreed not to import that package" has stopped
       working.

  WHAT YOU GET FOR FREE EVEN IF YOU NEVER WRITE module-info:

    - the JDK is modular, so strong encapsulation applies to YOU
      from Java 17: reflection into java.base internals throws
      rather than warns
    - a smaller runtime and faster startup from the JDK's own split
    - your dependencies' Automatic-Module-Name entries do no harm

  THE MINIMUM RESPONSIBLE POSITION for an application team: do not
  modularize, but do fix the illegal reflective access that Java 17
  turns into errors, and do add Automatic-Module-Name if you publish
  anything.

  THE ENCAPSULATION IDEA OUTLIVES THE ADOPTION. Whether or not you
  use JPMS, the lesson holds: "public" was never a boundary, it was a
  visibility keyword, and every system needs a way to say "this is
  mine". Teams that skip modules get the same effect from
  package-private types, ArchUnit rules, or separate build modules.

Interview Questions

Beginner: What problems does JPMS solve that the classpath had?

Four, all consequences of the classpath being a flat ordered list with no declarations.

No declared dependencies. A missing jar surfaces as NoClassDefFoundError whenever some code path first touches the class — possibly long after deployment. A module graph is resolved before main runs, so it fails at startup.

No encapsulation beyond public. Any public class in any jar is usable by everything, so library "internals" are internal only by convention — and therefore frozen, because someone depends on them.

Silent shadowing. Two jars with the same class: first on the classpath wins, with no warning, producing a NoSuchMethodError far from the cause.

A monolithic JDK. rt.jar shipped everything to every device; the modular JDK made jlink possible.

Beginner: What is the difference between exports and opens?

exports grants compile-time and runtime access to public members of a package. opens grants runtime reflective access, including private members, and no compile-time access at all.

They are orthogonal, and a typical module uses both for different packages:

exports com.example.api;      // the API others compile against
opens   com.example.model;    // the DTOs Jackson reflects over

The error that teaches the distinction is InaccessibleObjectException: … module com.example does not "opens com.example" to module com.fasterxml.jackson.databind. Jackson sets private fields directly, which is exactly what strong encapsulation prevents — so the module has to consent explicitly.

Both take a qualified form (exports P to M) when only specific modules should have access.

Mid: What is a split package and why is it fatal?

A package that exists in more than one module. It is illegal even when the classes differ — module A having com.example.util.Strings and module B having com.example.util.Numbers fails resolution:

Error: Module A reads package com.example.util from both A and B

It is fatal because there is no flag to permit it. Unlike reflective access, which has --add-opens, split packages must be fixed structurally: merge the packages, rename one, or shade.

It breaks migrations more than anything else because the classpath allowed it silently — first match won. Real cases are common: javax.annotation shipped by three different dependencies, a library plus its compatibility jar, or an old artifact that put classes into a JDK package.

The module system forbids it because the whole design rests on a package belonging to exactly one module — that is what makes "who exports this?" answerable.

Mid: How do automatic modules make migration possible?

An automatic module is a plain non-modular jar placed on the module path. The system synthesises a descriptor for it: it exports all its packages and requires every other module.

Its name comes from Automatic-Module-Name in the manifest, or — failing that — from the file name, which is fragile: rename or re-version the jar and your requires breaks.

That lets you modularize bottom-up: your own module can requires a dependency that has not been modularized yet.

The constraint that shapes everything is the unnamed module — where classpath code lives. It reads everything and exports everything, but no named module can require it. So dependencies must move to the module path before you can modularize what uses them, which makes migration strictly bottom-up and is why "just add a module-info to the app" fails.

If you publish a library, adding Automatic-Module-Name to the manifest is a one-line, zero-risk change that stops your consumers depending on your filename. It is the highest-value module action most library authors can take.

Senior: Should a typical application modularize? Argue both sides.

Usually no, and that is the position the ecosystem settled on.

The costs are concrete. Every dependency must be a real or automatic module; split packages have no workaround and are common in older trees; every reflective framework needs opens, discovered one InaccessibleObjectException at a time; and build tooling, test runners and agents all need module-path configuration that most plugins handle imperfectly.

The benefits mostly apply at a boundary you ship across. Strong encapsulation protects you from other people's code reaching in — which matters for a published library and matters much less inside an application where you control every caller. And jlink, the most tangible payoff, refuses automatic modules, so one non-modular dependency blocks it entirely.

Where it is clearly worth it: published libraries (real internals you can change); shipped desktop or CLI apps (a 40MB bundle instead of a JDK dependency); plugin architectures, where module layers give genuine runtime isolation; and large monoliths where informal internal boundaries have stopped being respected.

What you get regardless: the JDK is modular, so from Java 17 strong encapsulation applies to your reflection into java.base whether you modularize or not. That is the part every team must deal with.

My default recommendation: do not modularize the application; do add Automatic-Module-Name to anything you publish; do fix illegal reflective access rather than papering it over with --add-opens; and get the deployment-size win from a slim base image or GraalVM instead of jlink.

Senior: What does JPMS teach about API design even if you never use it?

That public was never a boundary. It is a visibility keyword that says "reachable", and for twenty years Java had no way to say "reachable by my own code but not by yours". The consequence is visible across the ecosystem: sun.misc.Unsafe could never be removed, com.something.internal packages are permanently frozen, and library authors who changed internals broke users who were never supposed to be there.

The lesson generalises to three tiers, not two: what callers may use, what your own modules may use, and what only this component may touch. JPMS spells them exports, exports … to, and unexported. Every non-trivial system needs those distinctions whether or not the language provides them.

The second lesson is that dependencies should be declared and verified. The value of requires is not the syntax, it is that the graph is checked before anything runs. The classpath's "find out at first use" model is the same class of mistake as unchecked configuration.

How teams get the effect without modules: package-private types for real internals, separate build modules so a compile fails when the wrong direction is imported, and ArchUnit or similar tests that assert dependency rules. Those give the boundary without the migration cost.

The honest verdict on adoption: JPMS is a well-designed system that arrived after the ecosystem had already routed around the problem with shading, OSGi and build-tool boundaries — and its all-or-nothing migration made it hard to adopt incrementally. The design is worth learning even where the implementation is not worth deploying.

🏋️ Graded Exercises

1 (easy): Why does this fail to compile, and what are the two possible fixes? 
// module com.lib
module com.lib {
    // no exports
}
// package com.lib.util contains a public class Strings

// module com.app
module com.app {
    requires com.lib;
}
// com.app.Main: import com.lib.util.Strings;   ← error
Solution

public is not enough in a module. Three conditions must all hold: the class is public, its package is exported, and the reader requires the module. Only the first and third are satisfied here.

module com.lib {
    exports com.lib.util;              // open to everyone
    // or, restricted:
    exports com.lib.util to com.app;   // only com.app
}
ConditionHere
Class is public✓
Package is exported✗ — the failure
Reader requires the module✓

This inversion is the point of the system. On the classpath everything public is accessible by default; in a module nothing is until declared. That is what finally lets a library have internals it can change.

Choose the qualified form when the package is a "friend" API meant for your own other modules — it keeps the surface out of the public contract.

2 (easy): Jackson throws this at runtime. What is wrong, and what exactly do you add? 
InaccessibleObjectException: Unable to make field private
java.lang.String com.example.model.User.name accessible:
module com.example does not "opens com.example.model" to
module com.fasterxml.jackson.databind
Solution

The package is (probably) exported but not opened. exports grants access to public members; Jackson sets private fields via setAccessible(true), which requires opens.

module com.example {
    exports com.example.api;
    opens   com.example.model;   // to everyone
    // or, precisely:
    opens   com.example.model to com.fasterxml.jackson.databind;
}
OptionTrade-off
opens PSimple; any module may reflect into P
opens P to MPrecise, but breaks when another framework needs it too
open moduleEverything reflectable — fine mid-migration, poor as an end state
--add-opens at launchFor code you do not control; must be repeated everywhere forever

The qualified form is tempting and usually wrong for DTOs, because the next serialiser, validator or mapper needs the same access and you will chase this exception again.

Note the error message names the fix. That is deliberate — these messages were designed to be actionable, which is why they are unusually long.

3 (medium): Two of your modules both contain com.example.util, with different classes. Startup fails. Options?
Solution

A split package. There is no flag for this. The module system requires each package to belong to exactly one module, because that is what makes "which module exports this?" answerable.

FixWhen it fitsCost
Merge into one moduleThe two really are one concernLoses the boundary you wanted
Rename to com.example.util.a / .bUsually the right answerBreaks imports in callers
Move the shared package into a third module both requireThere is genuinely common codeAn extra artifact
Shade one of themA third-party jar you cannot changeDuplicated code, harder debugging

For your own code, renaming is normally correct — the package name should identify the module anyway, and a shared package across two modules usually indicates the boundary was drawn in the wrong place.

For third-party jars you cannot change, shading or a compatibility exclusion is the only option. The classic instance is javax.annotation, shipped by several artifacts, which is why so many builds carry an exclusion for it.

Why the classpath let you get away with it: first match won, silently — so you may have been running a mix of two versions for years without knowing.

4 (medium): When is requires transitive correct, and what does it commit you to? 
module com.example.orders {
    requires com.example.model;      // types appear in my public API
    requires com.google.gson;        // used only inside
}
Solution

The rule: transitive when your public signatures mention the module's types.

module com.example.orders {
    requires transitive com.example.model;   // Order appears in my API
    requires com.google.gson;                // internal only
}

If public Order findOrder(long id) is part of your API, callers cannot use it without com.example.model. Without transitive, every caller must add its own requires for a dependency they did not choose.

Type appears in…Directive
Public method parameters or return typesrequires transitive
Public field types, thrown checked exceptionsrequires transitive
Method bodies, private fields onlyrequires
Compile-time annotations, optional integrationsrequires static

What it commits you to: a transitive dependency becomes part of your public contract. Removing or replacing it is a breaking change for every consumer, exactly like changing a method signature. That is the argument against using it liberally "to be helpful".

Gson stays non-transitive precisely so you can swap it for Jackson without a major version bump — which is the version of encapsulation that pays off in practice.

5 (hard): A service with 40 dependencies wants jlink for a smaller container. Assess feasibility.
Solution

Almost certainly not feasible as-is. jlink requires every module in the graph to be a real module — it rejects automatic modules outright. With 40 dependencies, several will lack a module-info.

BlockerEffect
Any non-modular dependencyjlink refuses the whole image
Split packages in the treeResolution fails before jlink is even reached
Reflective frameworksNeed opens throughout; classpath scanning may not see modular code as expected
Agents (APM, profilers)Often need --add-opens, which the image must carry

What actually gets the size win, in order of effort:

  1. A slim base image — eclipse-temurin:21-jre-alpine instead of the full JDK. Nearly free, and gets most of the reduction.
  2. Layered jars (Spring Boot supports this directly) so dependency layers cache across builds — often a bigger real-world win than total size, because pushes and pulls get faster.
  3. jlink via jdeps + ModiTect, generating descriptors for non-modular jars. Possible, but it is ongoing maintenance every time a dependency changes.
  4. GraalVM native image — the largest reduction and fastest startup, at the cost of reflection configuration and a slow build.

The honest recommendation: take option 1, add option 2 if image pushes are slow, and consider option 4 only if startup time is a business requirement — serverless, or scale-to-zero. jlink is the option whose cost is furthest out of proportion to its benefit for a server-side service.

Where jlink does shine is a desktop or CLI application you hand to users, where "requires a JDK" is not an acceptable install instruction and the dependency tree is small enough to be modular.

6 (hard): Design module boundaries for an e-commerce system with api, orders, payments, shared model and persistence. State what each directive buys.
Solution 
module com.shop.model {                    // no dependencies at all
    exports com.shop.model;                //   pure domain types
    opens   com.shop.model;                //   for Jackson / JPA
}

module com.shop.persistence {
    requires transitive com.shop.model;    // repos return model types
    requires java.sql;
    exports com.shop.persistence.api;      // interfaces only
    // com.shop.persistence.impl NOT exported — swappable
}

module com.shop.orders {
    requires transitive com.shop.model;
    requires com.shop.persistence;
    exports com.shop.orders.api;
    exports com.shop.orders.spi to com.shop.payments;  // friend API
}

module com.shop.payments {
    requires com.shop.orders;
    requires transitive com.shop.model;
    exports com.shop.payments.api;
    uses com.shop.payments.spi.Gateway;    // pluggable providers
}

module com.shop.api {                      // the deployable
    requires com.shop.orders;
    requires com.shop.payments;
    // exports nothing — it is the top of the graph
}
DecisionWhat it buys
model has no dependenciesNothing in the graph can create a cycle through it — and the module system rejects cycles at startup, so this is enforced
persistence.impl unexportedThe implementation is genuinely swappable; nobody can import a repository class
exports … to com.shop.paymentsA cross-module API that is not public surface
requires transitive com.shop.modelCallers get the domain types automatically, since every API mentions them
opens com.shop.modelSerialisation works without opening the business modules
api exports nothingThe deployable is a leaf; nothing may depend on it

The cycle prohibition is doing real architectural work here. Modules cannot be mutually dependent, and that failure is at startup — so "orders needs a bit of payments" cannot be quietly added later, which is precisely how layered designs erode on a classpath.

The uses/provides pair on payments is where JPMS is genuinely better than the alternatives: gateway implementations can live in separate modules that the core never references, discovered by ServiceLoader.

The honest caveat: this only holds if every third-party dependency is modular. For a real system, most teams get 80% of this structure from separate Maven modules plus an ArchUnit test, at a fraction of the migration cost.

🎯 Key Takeaways

  • The classpath has no declared dependencies, no encapsulation beyond public, and silent first-match-wins shadowing.
  • A module graph is resolved at startup, so a missing dependency fails at second zero rather than on a rare code path.
  • Accessibility now needs three things: public class, exported package, and the caller's requires.
  • Packages are not exported by default — the inverse of the classpath.
  • exports is compile+runtime public access; opens is runtime deep reflection — orthogonal, and often both are needed.
  • requires transitive is an API commitment, correct exactly when your signatures mention the module's types.
  • Split packages are fatal and have no flag — merge, rename or shade.
  • Automatic modules bridge migration, taking their name from the manifest or, riskily, the filename.
  • No named module can require the unnamed module, which forces bottom-up migration.
  • Add Automatic-Module-Name if you publish a library — one line, no risk, protects your consumers.
  • --add-opens is a bridge, not a fix — it must be repeated in every launch configuration forever.
  • Java EE and CORBA modules were removed in 11, which is the classic 8→11 upgrade failure.
  • jlink rejects automatic modules, so one non-modular dependency blocks the image.
  • Most applications should not modularize; libraries, shipped apps and plugin architectures should.
  • Strong encapsulation of the JDK applies from 17 whether you modularize or not.
