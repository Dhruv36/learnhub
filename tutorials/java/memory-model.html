The Java Memory Model Concurrency

What you'll master: why the memory model is a contract about what the compiler and CPU may reorder, not a description of caches; the happens-before relation, which is the only thing that actually guarantees visibility; the eight rules that establish it and how they compose; why a data race is undefined behaviour in the practical sense — programs can observe values no sequential execution could produce; what volatile does and precisely where it stops; the final field guarantee that makes immutable objects safe to publish without synchronization — and the unsafe-publication bug it fixes; and why double-checked locking was broken for years. Prerequisites: Synchronization & Locks.

Part 1 — The Problem the JMM Solves

  THIS PROGRAM CAN PRINT (0, 0). Not "in theory" — on real hardware.

    int x = 0, y = 0;
    int a = 0, b = 0;

    Thread 1: x = 1; a = y;
    Thread 2: y = 1; b = x;

  No interleaving of the four statements produces a == 0 && b == 0.
  Yet it happens, because the statements do not execute in the order
  you wrote them.

  THREE LAYERS ARE ALLOWED TO REORDER YOUR CODE:

    1. THE COMPILER (javac and, mostly, the JIT) may reorder
       independent statements, hoist reads out of loops, and keep
       values in registers instead of re-reading memory.
    2. THE CPU may execute instructions out of order and complete
       them out of order.
    3. THE MEMORY SYSTEM may make writes visible to other cores in a
       different order than they were issued (store buffers).

  ALL OF THIS IS LEGAL, AND ALL OF IT IS INVISIBLE WITHIN ONE
  THREAD. The rule every layer obeys is "as-if-serial": a single
  thread always observes its own actions in program order. The
  reorderings only become visible to ANOTHER thread.

  SO THE JMM IS NOT A DESCRIPTION OF CACHES. It is a CONTRACT: it
  says which reorderings are forbidden, so that you can reason about
  multithreaded code without knowing whether you are on x86, ARM or
  something that does not exist yet.

  x86 IS RELATIVELY STRONG — it forbids most reorderings in hardware,
  which is why racy code often "works" on a laptop and fails on ARM
  (Apple silicon, Graviton). The bug was always there; the hardware
  was hiding it.

  THE PRACTICAL CONSEQUENCE: you cannot test your way to memory-model
  correctness. A race may be invisible for years and then appear when
  the JIT compiles a method differently, or when you change cloud
  instance type.

Part 2 — Happens-Before

  HAPPENS-BEFORE IS THE ONLY GUARANTEE THAT EXISTS.

  If action A happens-before action B, then everything A did is
  visible to B. If there is NO happens-before edge between a write
  and a read of the same variable, the read may see the old value,
  the new value, or — with non-atomic 64-bit types — a mixture.

  IT IS NOT ABOUT TIME. "Happens-before" does not mean "happened
  earlier on a wall clock". A write that occurred a millisecond ago
  with no edge is not guaranteed visible; a write with an edge is
  visible no matter how the scheduler ran.

  THE RULES THAT CREATE EDGES:

  1. PROGRAM ORDER
     Within one thread, each action happens-before every later one.

  2. MONITOR LOCK
     Releasing a monitor happens-before any subsequent acquisition
     OF THE SAME monitor. (Different monitors: no edge.)

  3. VOLATILE
     A write to a volatile field happens-before every subsequent
     read of THAT field.

  4. THREAD START
     Everything before t.start() happens-before anything in t.

  5. THREAD TERMINATION
     Everything in t happens-before t.join() returning, and before
     t.isAlive() returning false.

  6. INTERRUPTION
     interrupt() happens-before the interrupted thread detecting it.

  7. FINALIZER
     A constructor finishing happens-before finalize() starting.

  8. TRANSITIVITY
     A hb B and B hb C  ⟹  A hb C.

  TRANSITIVITY IS WHAT MAKES THE MODEL USABLE. It is why this works:

    // thread A
    data = compute();          // 1  plain write
    ready = true;              // 2  VOLATILE write

    // thread B
    if (ready) {               // 3  volatile read
        use(data);             // 4  sees the write from line 1 ✓
    }

  1 hb 2 (program order), 2 hb 3 (volatile rule), 3 hb 4 (program
  order) ⟹ 1 hb 4. The volatile write PUBLISHES everything written
  before it — not just the flag.

  THAT IS THE MOST USEFUL SINGLE FACT ABOUT volatile, and the one
  people do not know: it creates a memory barrier that carries
  ordinary writes with it.

  THE LIBRARY EDGES YOU RELY ON WITHOUT NOTICING:

    putting into a BlockingQueue hb taking it out
    submitting to an Executor hb the task running
    a task's actions hb Future.get() returning
    countDown() hb await() returning
    releasing a Semaphore permit hb acquiring it
    writing to a ConcurrentMap hb reading that key

Part 3 — What a Data Race Costs You

  A DATA RACE IS: two threads access the same variable, at least one
  writes, and there is no happens-before edge between them.

  A CORRECTLY SYNCHRONIZED PROGRAM — one with no data races — is
  guaranteed SEQUENTIALLY CONSISTENT: it behaves as some interleaving
  of the threads' statements. That is the deal the JMM offers.

  ONCE YOU HAVE A RACE, YOU LOSE THAT GUARANTEE ENTIRELY, and the
  results are not merely "stale values":

  1. INFINITE LOOPS FROM HOISTING

       private boolean stop = false;      // no volatile
       while (!stop) { work(); }          // may never exit

     The JIT sees nothing in the loop modifying `stop` and hoists the
     read out:  if (!stop) while (true) work();
     This is legal. It usually appears only after the method is
     JIT-compiled, i.e. seconds into a production run.

  2. WORD TEARING ON 64-BIT PRIMITIVES

       long counter;          // non-volatile

     A non-volatile long or double may be written as TWO 32-BIT
     HALVES. A reader can observe the high half of one value and the
     low half of another — a number that was never assigned. Making
     it volatile (or using AtomicLong) removes this.

  3. SEEING A PARTIALLY CONSTRUCTED OBJECT

       // unsafe publication
       public Holder holder;
       public void init() { holder = new Holder(42); }

     Another thread may see a non-null `holder` whose field is still
     0, because the constructor's write and the reference assignment
     can be reordered. The object exists but is not finished.

  4. IMPOSSIBLE INTERLEAVINGS
     The (0,0) example from Part 1.

  WHY THIS IS WORSE THAN A NORMAL BUG:

    - it does not reproduce under a debugger (which disables the
      optimisations that cause it)
    - it does not reproduce on x86 as often as on ARM
    - it does not reproduce in a short test, because the JIT has not
      compiled the code yet
    - and it can appear after an unrelated change, when a method
      crosses an inlining threshold

  TOOLS THAT ACTUALLY FIND THESE:

    jcstress   the JVM team's concurrency stress harness — the only
               reliable way to test memory-model claims
    ThreadSanitizer / Java Pathfinder for exhaustive exploration
    -XX:+StressLCM -XX:+StressGCM   randomised JIT scheduling

  Ordinary unit tests find approximately none of them.

Part 4 — volatile: What It Does and Does Not Do

  volatile GIVES YOU EXACTLY THREE THINGS:

    1. VISIBILITY — a write is immediately visible to subsequent
       reads by any thread.
    2. ORDERING — writes before the volatile write cannot be moved
       after it; reads after the volatile read cannot be moved
       before it. (A release-store / acquire-load pair.)
    3. ATOMICITY FOR 64-BIT — a volatile long/double is never torn.

  IT DOES NOT GIVE YOU ATOMICITY FOR COMPOUND OPERATIONS:

    volatile int count;
    count++;          // ❌ STILL A RACE — read, add, write

  Two threads can both read 5, both write 6. volatile made each read
  and each write visible; it did not make the trio indivisible.

  THE DECISION TABLE:

    one thread writes, others read a flag     → volatile ✓
    read-modify-write (++, --, +=)            → Atomic* ✓
    check-then-act (if (x == null) x = …)     → lock or Atomic ✓
    multiple fields with an invariant         → lock ✓

  THE CORRECT USE — a stop flag:

    private volatile boolean shutdown;
    public void stop()   { shutdown = true; }
    public void run()    { while (!shutdown) work(); }

  THE OTHER CORRECT USE — SAFE PUBLICATION, which is really the
  important one:

    private volatile Config config;              // whole object

    void reload() {
        Config c = new Config();
        c.load();                     // fully build it FIRST
        config = c;                   // publish atomically
    }

  Readers see either the old config or a fully initialised new one,
  never a half-built one — because the volatile write orders all the
  construction before it. Mutating the existing config in place would
  have no such guarantee.

  COST: a volatile write compiles to a store with a memory fence
  (on x86, typically a locked instruction, ~10-20 ns); a volatile
  read is nearly free on x86 but not on ARM. It also blocks
  optimisations — the JIT cannot hoist, cache in a register, or
  reorder around it — which is often the larger cost in a hot loop.

  WHAT REPLACED volatile FOR EXPERTS: VarHandle (Java 9+) exposes
  the individual modes:

    getAcquire/setRelease   ordering without full fences — cheaper
    getPlain/setPlain       no ordering at all
    getVolatile/setVolatile equivalent to a volatile field
    compareAndSet           the CAS primitive

  Use these only with a specific measured reason; a plain volatile
  field is right almost always.

Part 5 — The final Field Guarantee

  final IS NOT ONLY ABOUT REASSIGNMENT. It carries a MEMORY MODEL
  GUARANTEE that is the foundation of safe immutable objects:

    IF an object is correctly constructed — the reference does not
    escape during the constructor — THEN any thread that sees the
    reference is guaranteed to see the correctly initialised values
    of its final fields, WITH NO SYNCHRONIZATION AT ALL.

  THE PRACTICAL DIFFERENCE:

    class Unsafe  { int x;       Unsafe(int x)  { this.x = x; } }
    class Safe    { final int x; Safe(int x)    { this.x = x; } }

    // publishing without synchronization
    holder = new Unsafe(42);    // another thread may read x == 0 !
    holder = new Safe(42);      // guaranteed to read x == 42

  For the non-final version, the constructor's write and the
  reference assignment may be reordered, so a reader can see a
  non-null reference to an object whose field is still the default.

  final PREVENTS THAT with a freeze action at the end of the
  constructor: no write to a final field can be reordered past it.

  THE ESCAPE CLAUSE MATTERS — "correctly constructed" means `this`
  MUST NOT ESCAPE:

    class Broken {
        final int x;
        Broken(int x) {
            Registry.add(this);    // ❌ ESCAPED — other threads can
            this.x = x;            //    see x == 0 despite final
        }
    }

  Registering listeners, starting threads, or passing `this` to
  anything from a constructor all break the guarantee. Use a static
  factory that constructs first and publishes second.

  THE GUARANTEE IS SHALLOW. A final field pointing to a MUTABLE
  object protects the REFERENCE, not the contents:

    final List<String> items;    // the reference is safe
                                 // the list's contents are NOT

  So an immutable class needs final fields AND either immutable
  contents or defensive copies (List.copyOf).

  THIS IS WHY IMMUTABLE OBJECTS ARE THREAD-SAFE BY CONSTRUCTION:
  all-final fields plus no escape plus deeply immutable contents
  means there is no way to observe an inconsistent state, and no
  synchronization is required to share them. Records give you the
  final fields automatically.

Part 6 — Safe Publication and Double-Checked Locking

  "PUBLICATION" = making an object visible to another thread.
  UNSAFE publication is the most common memory-model bug in real code
  because it looks like ordinary assignment.

  THE FOUR SAFE WAYS TO PUBLISH A MUTABLE OBJECT:

    1. a static initializer          (the JVM synchronizes it)
    2. a volatile field or AtomicReference
    3. a final field of a correctly constructed object
    4. a field guarded by a lock, read under the same lock

  Anything else — a plain field, a non-thread-safe collection — is a
  race, even if it "works".

  DOUBLE-CHECKED LOCKING WAS BROKEN BEFORE JAVA 5:

    private static Singleton instance;              // NOT volatile

    static Singleton get() {
        if (instance == null) {                     // 1
            synchronized (Singleton.class) {
                if (instance == null)
                    instance = new Singleton();     // 2
            }
        }
        return instance;                            // 3
    }

  Line 2 is not one operation. It is roughly:

    allocate memory
    write the reference into `instance`      ← may happen FIRST
    run the constructor

  Another thread executing line 1 can see a non-null `instance`,
  skip the lock, and return an object whose constructor has not
  run — with fields at their defaults. It fails rarely and cannot be
  reproduced on demand.

  THE FIX IS ONE KEYWORD:

    private static volatile Singleton instance;

  The volatile write cannot be reordered before the constructor's
  writes, and the volatile read on line 1 pairs with it.

  BUT THE BETTER ANSWERS AVOID THE PROBLEM:

    // static holder — lazy, thread-safe, no volatile, no lock
    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }
    static Singleton get() { return Holder.INSTANCE; }

    // enum — also handles serialization and reflection attacks
    enum Singleton { INSTANCE; }

  The holder idiom works because CLASS INITIALIZATION IS ITSELF
  SYNCHRONIZED by the JVM, and Holder is not initialised until first
  referenced. You get laziness and thread safety with no explicit
  synchronization of your own — which is why it is preferred to
  double-checked locking in every case where it applies.

  THE ONE CASE DCL STILL EARNS ITS PLACE: a lazily initialised
  INSTANCE field (not static), where a holder class cannot be used.
  Even then, prefer a local variable to avoid re-reading the
  volatile:

    private volatile Config config;
    Config get() {
        Config c = config;                 // one volatile read
        if (c == null) {
            synchronized (this) {
                c = config;
                if (c == null) config = c = new Config();
            }
        }
        return c;
    }

Interview Questions

Beginner: What is the Java Memory Model?

It is a specification of which reorderings are permitted between threads — a contract between your program and the JVM, not a description of hardware.

Three layers are free to reorder your code: the compiler (hoisting reads, keeping values in registers), the CPU (out-of-order execution), and the memory system (store buffers making writes visible in a different order). All of it is invisible within a thread, because every layer preserves as-if-serial semantics for a single thread. It becomes visible to other threads.

The JMM defines the minimum guarantees so you can reason about concurrency without knowing whether you are running on x86 or ARM. The practical consequence is that racy code often works on an x86 laptop — that architecture forbids most reorderings in hardware — and fails on ARM. The bug was always there.

Beginner: What does volatile guarantee, and what does it not?

It guarantees three things: visibility (a write is immediately visible to subsequent reads on any thread), ordering (writes before a volatile write cannot move after it, reads after a volatile read cannot move before it), and atomicity for 64-bit primitives (a volatile long is never torn).

It does not give atomicity for compound operations. volatile int count; count++; is still a race — read, add and write are three steps, and two threads can both read 5 and both write 6.

The under-appreciated part is that a volatile write publishes everything written before it, not just the field itself — which is what makes it usable for safe publication.

Mid: Explain happens-before, and why this code is correct. 
// thread A
data = compute();        // plain field
ready = true;            // volatile

// thread B
if (ready) use(data);

Happens-before is the only visibility guarantee in Java. If A happens-before B, everything A did is visible to B. With no edge, a read may see the old value, the new one, or — for a non-volatile 64-bit type — a mixture.

The chain here uses three rules:

  1. data = compute() happens-before ready = true — program order.
  2. The volatile write happens-before the volatile read of ready — the volatile rule.
  3. The read happens-before use(data) — program order.

By transitivity, the write to data happens-before its use. So a plain field is safely published by a volatile write that follows it.

Crucially, happens-before is not about time. A write that occurred earlier on a wall clock with no edge is not guaranteed visible at all; a write with an edge is visible regardless of scheduling.

Remove volatile and the chain breaks at step 2 — thread B may see ready true and data stale, or may never see ready change.

Mid: What is unsafe publication, and what are the safe ways?

Publication is making an object visible to another thread. It is unsafe when there is no happens-before edge between constructing the object and reading the reference — in which case another thread can see a non-null reference to a partially constructed object, because the constructor's writes and the reference assignment may be reordered.

public Holder holder;
public void init() { holder = new Holder(42); }
// another thread: holder.x may read 0

The four safe ways:

  1. A static initializer — class initialization is synchronized by the JVM.
  2. A volatile field or AtomicReference.
  3. A final field of a correctly constructed object.
  4. A field guarded by a lock, read under the same lock.

This is why immutable objects are so valuable: with all-final fields and no escaping this, publication is safe automatically, and they can be shared with no synchronization at all.

Senior: Why was double-checked locking broken, and what would you write instead?

Because instance = new Singleton() is not one operation. It is approximately: allocate, write the reference, run the constructor — and the last two may be reordered. A second thread reaching the first null check can then see a non-null reference, skip the lock entirely, and return an object whose fields are still at their defaults.

It fails rarely, cannot be reproduced on demand, and disappears under a debugger — which is why it survived in textbooks for years. Java 5 did not "fix" the idiom; it strengthened volatile so that private static volatile Singleton instance makes it correct, since the volatile write cannot be reordered before the construction.

What I would actually write is the static holder:

private static class Holder {
    static final Singleton INSTANCE = new Singleton();
}
public static Singleton get() { return Holder.INSTANCE; }

It is lazy — Holder is not initialised until first referenced — and thread-safe because class initialization is itself synchronized by the JVM. No volatile, no lock, nothing to get wrong. An enum singleton is the other option, and additionally resists serialization and reflection attacks.

Where DCL still earns its place is a lazily initialised instance field, where a holder class does not apply. Even then, read the volatile into a local variable once rather than repeatedly, since each read blocks optimisation.

The deeper lesson is that this bug is unreachable by testing. It has to be prevented by reasoning about happens-before, which is the argument for preferring idioms whose correctness is structural.

Senior: What does final guarantee beyond immutability?

A memory-model guarantee: if an object is correctly constructed, any thread that sees the reference is guaranteed to see the correctly initialised values of its final fields — with no synchronization.

The JVM implements this with a freeze action at the end of the constructor: no write to a final field may be reordered past constructor completion. Without final, publishing an object through a plain field lets a reader observe default values.

"Correctly constructed" means this must not escape. This voids it:

Broken(int x) {
    Registry.add(this);    // escaped — the guarantee is gone
    this.x = x;
}

Registering listeners, starting threads, or passing this to anything from a constructor all break it. The fix is a static factory: construct fully, then publish.

The guarantee is shallow. A final field pointing to a mutable List protects the reference, not the contents — so an immutable class needs final fields and deeply immutable or defensively copied contents.

Why this matters in practice: it is what makes immutable objects thread-safe by construction and shareable with zero synchronization, which is the cheapest concurrency strategy there is. Records give you the final fields automatically, but not the deep immutability — that is still your job.

🏋️ Graded Exercises

1 (easy): Why might this never terminate? 
class Worker implements Runnable {
    private boolean running = true;
    public void run()  { while (running) doWork(); }
    public void stop() { running = false; }
}
Solution

There is no happens-before edge between stop() and the loop's read. Two legal behaviours follow: the write may never become visible, and — more likely — the JIT hoists the read out of the loop because nothing inside modifies it:

if (running) { while (true) doWork(); }   // a legal transformation
private volatile boolean running = true;   // the fix
AlternativeVerdict

AtomicBooleanWorks; more machinery than needed

InterruptionOften better — it also unblocks waiting calls

The reason this is dangerous is the failure timing. Interpreted code re-reads the field, so short tests pass; the hoisting only appears once the method is JIT-compiled, seconds into a production run.

For a worker that blocks — on a queue or on sleep — a flag alone is insufficient anyway, because the thread is parked and never re-tests it. Interruption handles both cases.

2 (easy): Is count correct? It is volatile. 
private volatile int count = 0;
public void increment() { count++; }
Solution

No. count++ is read, add, write — three operations. volatile makes each of them visible; it does not make the sequence indivisible.

T1 reads 5     T2 reads 5
T1 writes 6    T2 writes 6      → 6, not 7
private final AtomicInteger count = new AtomicInteger();
public void increment() { count.incrementAndGet(); }   // CAS loop
ToolVisibilityAtomic RMW
volatile intYesNo
AtomicIntegerYesYes
synchronizedYesYes
LongAdderYesYes — and far better under contention

The distinction to keep: visibility is about when a value is seen; atomicity is about whether an operation can be interleaved. volatile only addresses the first.

For a hot counter, use LongAdder. AtomicInteger's CAS loop degrades sharply under many writers because they all contend on one cache line; LongAdder spreads writes across cells and sums on read.

class Holder { int x; Holder(int x) { this.x = x; } }

// thread B
if (holder != null) System.out.println("x = " + holder.x);
Solution

Yes. This is unsafe publication. The assignment is roughly: allocate, write the reference, run the constructor — and the last two may be reordered. Thread B can see a non-null reference to an object whose field is still the default 0.

5 (hard): Explain how (0, 0) is possible, and how to prevent it. 
int x = 0, y = 0, a = 0, b = 0;
Thread 1: x = 1; a = y;
Thread 2: y = 1; b = x;
// observed: a == 0 && b == 0
Solution

No interleaving of the four statements produces (0,0) — whichever store happens first, the other thread's load should see it. It occurs anyway because the statements do not execute in program order as seen by the other thread.

LayerWhat it may do
Compiler / JITReorder the independent store and load
CPUExecute out of order and retire out of order
Store bufferHold x = 1 locally while the load of y proceeds

The store-buffer explanation is the concrete one, and it is why even x86 permits this particular case: x86 allows store-load reordering. Both writes sit in per-core store buffers while both reads go to memory and see the old values. This is Dekker's pattern, the canonical example.

volatile int x = 0, y = 0;    // the fix

A volatile write compiles to a store with a full fence, which drains the store buffer before the subsequent load — so the reordering is forbidden and (0,0) becomes impossible.

Why this matters beyond the puzzle: this exact shape is at the heart of lock-free mutual-exclusion algorithms and flag-based handshakes between threads. If you write one without volatile, it is broken on every architecture including x86.

And it is untestable by ordinary means. The frequency depends on the JIT, the core topology and the load. jcstress exists precisely because this class of bug cannot be found with unit tests.

6 (hard): Make this cache thread-safe with the least synchronization, and justify every choice. 
public class ConfigCache {
    private Map<String, String> config = new HashMap<>();
    public String get(String k)  { return config.get(k); }
    public void reload(Map<String,String> fresh) {
        config.clear();
        config.putAll(fresh);
    }
}
Solution

Two problems. Readers can observe the map mid-clear() — an empty or half-populated config — and HashMap is not thread-safe, so a concurrent resize can corrupt it or spin forever.

public class ConfigCache {
    private volatile Map<String, String> config = Map.of();

    public String get(String k) { return config.get(k); }

    public void reload(Map<String, String> fresh) {
        config = Map.copyOf(fresh);      // build new, publish once
    }
}
ChoiceWhy
Replace, never mutateReaders see the old map or the new one — never a partial state
volatile on the referenceThe single edge needed; the write publishes the fully built map
Map.copyOfImmutable, so no reader can be affected by later changes to fresh
No lock at allReads are a single volatile load — no contention between readers

Why not ConcurrentHashMap: it makes each operation safe but does not give you an atomic swap of the whole configuration. A clear plus putAll on a concurrent map still exposes an intermediate state — which is exactly the bug.

Why not a lock: every read would contend on a monitor for data that changes once an hour. Copy-on-write moves all the cost to the writer, where it belongs.

The one caveat: two reads in the same request may see different configuration versions if a reload lands between them. If a request must see one consistent snapshot, read the reference once into a local variable and use that throughout.

🎯 Key Takeaways

  • The JMM is a contract about permitted reorderings, not a description of caches.
  • Compiler, CPU and store buffers may all reorder — invisibly within a thread, visibly to others.
  • x86 hides most races; ARM does not — "works on my laptop" proves nothing.
  • Happens-before is the only visibility guarantee, and it is not about wall-clock time.
  • Transitivity is what makes it usable — a volatile write publishes everything written before it.
  • A race with no edge can produce impossible interleavings, hoisted loops, and torn 64-bit values.
  • A race-free program is sequentially consistent; that is the deal the JMM offers.
  • volatile gives visibility, ordering and 64-bit atomicity — never compound atomicity.
  • Safe publication has exactly four forms: static init, volatile, final, or a lock used on both sides.
  • final carries a freeze guarantee making correctly constructed objects safe to publish with no synchronization.
  • An escaping this voids that guarantee — use a static factory.
  • The final guarantee is shallow — the reference, not the contents.
  • Double-checked locking needs volatile; a static holder class or enum is better.
  • Class initialization is synchronized by the JVM, which is why the holder idiom works.
  • Different monitors give no edge — "synchronized somewhere" is not synchronization.
  • Ordinary tests cannot find these bugs; reason from the rules, and use jcstress when you must verify.
