Concurrency Patterns & Pitfalls Concurrency

What you'll master: the safety-versus-liveness split that classifies every concurrency bug and tells you which tool applies; the four strategies in strict preference order — don't share, make it immutable, confine it, then guard it — and why reaching for a lock first is usually a design failure; confinement forms and the ThreadLocal leak that makes a pooled thread serve one user's data to another; producer/consumer and why an unbounded queue converts a throughput problem into an OutOfMemoryError; the coordination utilities and which fits which shape; fork/join, work stealing and the common-pool blocking rule; false sharing; a graceful-shutdown recipe that actually terminates; and why unit tests find almost none of these. Prerequisites: Synchronization and Executors.

Part 1 — Safety vs Liveness

  EVERY CONCURRENCY BUG IS ONE OF TWO KINDS, AND THE DISTINCTION
  TELLS YOU WHICH TOOL YOU NEED.

  SAFETY — "nothing bad happens". Something wrong is COMPUTED.

    lost update     two increments, one result
    torn read       half of an old value, half of a new one
    partial object  a reference published before construction
                    finished
    broken invariant  two fields updated non-atomically

  Symptom: WRONG ANSWERS. The program keeps running and gives you
  bad data — which is why these are the dangerous ones. A crash gets
  investigated; a slightly wrong balance does not.

  LIVENESS — "something good eventually happens". Progress STOPS.

    deadlock     a cycle of threads each holding what another wants
    livelock     threads active, repeatedly retrying, no progress
    starvation   a thread never gets its turn
    lock convoy  many threads handing one lock around, each handoff
                 costing a context switch

  Symptom: A HANG OR A CRAWL. Unpleasant, but visible — and a thread
  dump usually names the culprit in a minute.

  THE TENSION IS REAL: more locking improves safety and hurts
  liveness. One global lock is perfectly safe and has no
  concurrency. The design work is finding the smallest amount of
  coordination that keeps the invariants.

  AND THE TWO HAVE DIFFERENT ECONOMICS:

    a liveness bug   is loud, reproducible-ish, and diagnosable
                     from a thread dump
    a safety bug     is silent, non-reproducible, and may be
                     discovered months later in a reconciliation
                     report

  So when you must choose, choose safety. A service that hangs gets
  restarted; a service that corrupts data does not get un-corrupted.

Part 2 — The Four Strategies, In Order

  TRY THESE IN ORDER. STOP AT THE FIRST ONE THAT WORKS.

  1. DON'T SHARE.
     If a value is computed and used within one task, nothing needs
     protecting. Most "concurrency problems" are really design
     problems where state was made a field that should have been a
     local variable or a parameter.

       // ❌ shared field for no reason
       class Parser { private StringBuilder buf; … }

       // ✓ local — inherently thread-safe
       String parse(String in) { var buf = new StringBuilder(); … }

  2. MAKE IT IMMUTABLE.
     An object that cannot change cannot be observed inconsistently.
     With all-final fields and no escaping `this`, it is also SAFE
     TO PUBLISH with no synchronization at all — that is the
     final-field guarantee.

       record Point(int x, int y) { }        // share freely

     "Changing" it means producing a new one, which is why copy-on-
     write configuration objects are so common.

  3. CONFINE IT.
     Mutable state owned by exactly one thread needs no locks.

       stack confinement    a local variable — the strongest form
       thread confinement   ThreadLocal, or a single-threaded
                            executor owning the state
       instance confinement encapsulate the state and the lock in
                            the same object, so callers cannot
                            touch it unguarded

  4. GUARD IT.
     Only now do you reach for synchronization — and you own the
     correctness. Document what each lock protects:

       // @GuardedBy("lock")
       private final Map<String,Order> orders = new HashMap<>();

  THE THREAD-LOCAL LEAK, WHICH IS BOTH A LEAK AND A SECURITY BUG:

    executor.submit(() -> {
        CONTEXT.set(currentUser);
        doWork();
        // no remove()
    });

  The pooled thread keeps that reference alive forever, AND THE NEXT
  REQUEST ON THIS THREAD SEES THE PREVIOUS USER'S CONTEXT. Always:

    try { CONTEXT.set(u); doWork(); } finally { CONTEXT.remove(); }

  The ScopedValue API (Java 21+) exists partly to make this
  impossible, since a binding is unbound when its block exits.
StrategyCostWhen it fails
Don't shareZeroState genuinely spans tasks
ImmutableAllocation per changeLarge objects changed frequently
Stack confinementZeroThe value must outlive the call
ThreadLocalMemory per thread; leak riskPooled threads without remove()
Single-threaded executorSerialises that stateThe one thread becomes a bottleneck
Concurrent collectionSmallYou need atomicity across collections
Explicit lockContention; deadlock riskHeld across I/O, or nested

Part 3 — Producer/Consumer

  THE MOST USEFUL CONCURRENCY PATTERN, AND THE ONE MOST OFTEN
  BUILT WRONG BY HAND.

    private final BlockingQueue<Task> queue =
        new LinkedBlockingQueue<>(1000);          // BOUNDED

    // producer
    if (!queue.offer(task, 100, MILLISECONDS)) {
        metrics.dropped();          // shed load — a real decision
    }

    // consumer
    while (!Thread.currentThread().isInterrupted()) {
        try {
            process(queue.take());               // blocks when empty
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return;
        } catch (Exception e) {
            log.error("task failed", e);         // survive one bad task
        }
    }

  WHY THE BOUND IS NOT OPTIONAL:

    unbounded queue + producer faster than consumer
      = the queue grows until the heap is gone
      = OutOfMemoryError, which loses EVERYTHING in the queue

  An unbounded queue does not prevent overload; it defers it and
  converts a manageable problem (some requests are slow or rejected)
  into an unrecoverable one. And latency degrades long before
  memory does: a 500,000-item backlog means every item waits.

  THE FOUR WAYS TO ENQUEUE SAY DIFFERENT THINGS:

    put(t)                 block the producer — TRUE BACKPRESSURE,
                           pushes the problem upstream where it can
                           be solved
    offer(t)               false when full — caller decides
    offer(t, time, unit)   bounded wait, then decide
    add(t)                 throws when full

  CHOOSING BETWEEN THEM IS A PRODUCT DECISION, not a technical one:
  should a burst slow the caller down (put), be dropped (offer +
  metric), or be rejected loudly (add)? Answer that before writing
  the code.

  THE POISON PILL, for shutting a consumer down through the queue:

    private static final Task STOP = new Task();
    queue.put(STOP);
    // consumer: if (t == STOP) { queue.put(STOP); return; }

  It re-inserts the pill so sibling consumers also stop. Useful when
  you need remaining work drained before exit; interruption is
  simpler when you do not.

  EXCEPTION HANDLING IS WHAT MAKES OR BREAKS THIS. Catch per task,
  not around the loop — otherwise one malformed message ends
  processing permanently, silently, and throughput just halves.

Part 4 — Coordination Utilities

  DO NOT HAND-ROLL THESE WITH wait/notify. Each encodes a specific
  shape.

  CountDownLatch — ONE-SHOT, "wait for N things"

    var latch = new CountDownLatch(services.size());
    services.forEach(s -> exec.submit(() -> {
        try { s.start(); } finally { latch.countDown(); }  // FINALLY
    }));
    latch.await(30, SECONDS);      // ALWAYS use the timeout form

  The count NEVER RESETS. countDown() in a finally, or a failing
  task hangs the waiter forever — the single most common misuse.

  CyclicBarrier — REUSABLE, "N threads meet here, repeatedly"

    var barrier = new CyclicBarrier(4, () -> mergeResults());

  Every party calls await(); when the last arrives, the optional
  barrier action runs and all are released. If one party dies, the
  others get BrokenBarrierException — the barrier is not
  fault-tolerant, which is why it suits fixed-size compute phases
  and not request handling.

  Semaphore — BOUND CONCURRENT ACCESS

    private final Semaphore permits = new Semaphore(10);
    if (!permits.tryAcquire(1, SECONDS)) return Response.busy();
    try { callDownstream(); } finally { permits.release(); }

  This is the tool for "at most N at a time" — the correct
  replacement for a thread pool used as an accidental rate limiter,
  and essential with virtual threads.

  Phaser — a barrier where parties JOIN AND LEAVE dynamically.
  More flexible, considerably harder to reason about; reach for it
  only when the party count genuinely changes.

  Exchanger — two threads swap objects at a rendezvous. Rare.

  CompletableFuture — composition rather than blocking:

    CompletableFuture.allOf(a, b, c).join();
    a.thenCombine(b, this::merge);

  CHOOSING:

    wait for N events, once            CountDownLatch
    N threads sync repeatedly          CyclicBarrier
    at most N concurrent               Semaphore
    dynamic party count                Phaser
    compose async results              CompletableFuture
    hand items between threads         BlockingQueue

Part 5 — Fork/Join, Parallel Streams and False Sharing

  FORK/JOIN IS FOR DIVIDE-AND-CONQUER CPU WORK, AND ITS TRICK IS
  WORK STEALING: each worker has its own deque, pushes and pops from
  its own head, and STEALS from the TAIL of a busy worker's deque
  when idle. Stealing from the opposite end minimises contention and
  takes the largest (least-divided) task.

    class SumTask extends RecursiveTask<Long> {
        protected Long compute() {
            if (hi - lo <= THRESHOLD) return sumDirectly();
            int mid = (lo + hi) / 2;
            var left = new SumTask(lo, mid);
            left.fork();                       // queue it
            long r = new SumTask(mid, hi).compute();  // do this one
            return r + left.join();
        }
    }

  Note the shape: fork ONE, compute the other yourself, then join.
  Forking both and joining both wastes a worker.

  THE THRESHOLD MATTERS: too small and coordination dominates; too
  large and you lose parallelism. Rough guidance is 1,000-10,000
  simple operations per leaf — but measure, because it depends
  entirely on the work.

  *** NEVER BLOCK IN THE COMMON POOL ***

    list.parallelStream().map(this::httpCall).toList();   // ❌

  parallelStream uses ForkJoinPool.commonPool, which is sized to
  (cores - 1) and SHARED BY THE WHOLE JVM. Blocking calls in it
  starve every other parallel operation in the process — including
  library code you did not write.

    // ✓ run it in your own pool
    var pool = new ForkJoinPool(32);
    pool.submit(() -> list.parallelStream().map(this::call).toList())
        .join();

    // ✓✓ or just use virtual threads for I/O

  WHEN parallelStream IS ACTUALLY WORTH IT — all four must hold:

    1. genuinely CPU-bound work
    2. a large enough N that splitting pays (typically 10k+)
    3. a cheaply splittable source (ArrayList and arrays split well;
       LinkedList and Stream.iterate do not)
    4. independent elements — no shared mutable state, no ordering
       dependence

  Miss any one and sequential is usually faster.

  FALSE SHARING — the invisible performance bug:

    class Counters { long a; long b; }     // 8 bytes apart

  Two threads incrementing a and b never touch the same variable,
  but both variables sit on the SAME 64-BYTE CACHE LINE. Every write
  invalidates the other core's copy, and throughput can drop by an
  order of magnitude for no visible reason.

  The fix is padding, which is what @Contended (with
  -XX:-RestrictContended) and LongAdder's Cell class do. Before
  hand-padding, check whether a LongAdder or a per-thread
  accumulator removes the sharing entirely — usually a better
  answer.

Part 6 — Shutdown, Timeouts and Testing

  THE SHUTDOWN RECIPE THAT ACTUALLY TERMINATES:

    void shutdown(ExecutorService exec) {
        exec.shutdown();                      // stop accepting work
        try {
            if (!exec.awaitTermination(30, SECONDS)) {
                exec.shutdownNow();           // interrupt running
                if (!exec.awaitTermination(10, SECONDS))
                    log.error("pool did not terminate");
            }
        } catch (InterruptedException e) {
            exec.shutdownNow();
            Thread.currentThread().interrupt();  // restore
        }
    }

  EVERY LINE EARNS ITS PLACE:

    shutdown()          existing tasks finish; new ones rejected
    awaitTermination    shutdown() does NOT wait — this is the
                        step people omit, and then wonder why work
                        was cut off
    shutdownNow()       interrupts running tasks and RETURNS the
                        queued ones, which you may want to log
    the second await    shutdownNow can fail too, and you should
                        say so rather than assume success
    restore the flag    the caller's own cancellation must survive

  AND IT ONLY WORKS IF TASKS COOPERATE. A task that swallows
  InterruptedException cannot be stopped by any of this — which is
  why the interrupt discipline is a shutdown concern, not a style
  preference.

  TIMEOUTS EVERYWHERE. Any operation that can block should have a
  bound:

    future.get(5, SECONDS)
    lock.tryLock(1, SECONDS)
    queue.offer(t, 100, MILLISECONDS)
    httpClient timeouts, JDBC query timeouts

  An unbounded wait converts one slow dependency into a total
  outage, because every thread ends up parked on it.

  TESTING CONCURRENT CODE — THE HONEST POSITION:

    ORDINARY UNIT TESTS FIND ALMOST NO RACES. A test runs
    interpreted, briefly, on an idle machine, with one interleaving
    out of billions. The JIT optimisations that CAUSE most memory-
    model bugs have not happened yet.

  WHAT ACTUALLY WORKS:

    jcstress          the JVM team's harness; the only reliable way
                      to test a memory-model claim
    stress + invariants  many threads, many iterations, then assert
                      an invariant (a total, a count) rather than a
                      timing
    deterministic seams  inject a scheduler or a latch so you can
                      force a specific interleaving in a test
    -XX:+StressLCM -XX:+StressGCM   randomised JIT scheduling
    static analysis   SpotBugs and ErrorProne find real classes of
                      bug (unsynchronized access, @GuardedBy
                      violations) cheaply
    production        JFR, thread dumps, and metrics that would
                      show an invariant breaking

  A TEST WITH Thread.sleep IN IT IS NOT A CONCURRENCY TEST. It
  is a slow test that passes for the wrong reason — sleeping creates
  no happens-before edge and proves nothing about visibility.

  DESIGN IT IN INSTEAD. Minimise shared mutable state, prefer
  immutability and confinement, use the concurrent library rather
  than hand-rolled locks, and keep critical sections small. Every
  one of those reduces the space of bugs that testing cannot
  find.

Interview Questions

Beginner: What is the difference between a safety and a liveness problem?

Safety is "nothing bad happens" — something wrong gets computed. Lost updates, torn reads, a partially constructed object being published, an invariant broken because two fields were updated non-atomically. The symptom is wrong answers while the program keeps running.

Liveness is "something good eventually happens" — progress stops. Deadlock, livelock, starvation, lock convoys. The symptom is a hang or a crawl.

The tension is that they pull in opposite directions: more locking improves safety and hurts liveness. One global lock is perfectly safe with no concurrency at all.

When forced to choose, choose safety. A liveness bug is loud and a thread dump usually names it in a minute; a safety bug is silent, non-reproducible, and may surface months later in a reconciliation report. A hung service gets restarted — corrupted data does not get un-corrupted.

Beginner: Why must a work queue be bounded?

Because an unbounded queue does not prevent overload, it defers it — and converts a manageable failure into an unrecoverable one.

If the producer is faster than the consumer, the queue grows until the heap is exhausted. The result is an OutOfMemoryError that loses everything already queued, which is far worse than having rejected some work at the door.

Latency degrades long before memory does. A 500,000-item backlog means every item waits, so the service is effectively down while appearing healthy.

A bound forces the decision to be explicit, and the four enqueue methods each state a different answer:

CallSays
putSlow the producer down — true backpressure
offerLet the caller decide (drop and count it)
offer(t, unit)Wait briefly, then decide
addFail loudly

Which one is right is a product decision, not a technical one — answer it before writing the code.

Mid: When is parallelStream() a good idea?

Rarely, and only when all four conditions hold together:

  1. Genuinely CPU-bound work. Blocking calls belong nowhere near it.
  2. Enough elements that splitting pays — typically tens of thousands, though it depends on the per-element cost.
  3. A cheaply splittable source. ArrayList and arrays split by index; LinkedList, Stream.iterate and I/O-backed sources do not.
  4. Independent elements — no shared mutable state, no ordering dependence.

The failure that hurts most is blocking in it. parallelStream uses ForkJoinPool.commonPool, which is sized to cores - 1 and shared by the entire JVM. Blocking calls there starve every other parallel operation in the process, including library code you did not write and cannot see.

// contain the damage
var pool = new ForkJoinPool(32);
pool.submit(() -> list.parallelStream().map(this::call).toList()).join();

For I/O the right answer today is virtual threads, not a bigger fork/join pool — one virtual thread per item, blocking freely.

And measure. Sequential is often faster than people expect, because the JIT vectorises simple loops and the splitting overhead is real.

Mid: Write a correct executor shutdown and explain each line. 
exec.shutdown();                          // 1
try {
    if (!exec.awaitTermination(30, SECONDS)) {   // 2
        exec.shutdownNow();                      // 3
        if (!exec.awaitTermination(10, SECONDS)) // 4
            log.error("pool did not terminate");
    }
} catch (InterruptedException e) {
    exec.shutdownNow();
    Thread.currentThread().interrupt();          // 5
}
StepWhy
1Stops accepting new work; existing tasks finish. It does not wait
2The waiting step people omit — without it, work is cut off at JVM exit
3Interrupts running tasks and returns the queued ones, which you may want to log
4shutdownNow can fail too; say so rather than assume
5Restore the flag so the caller's own cancellation survives

The whole recipe depends on the tasks cooperating. shutdownNow interrupts; a task with an empty catch (InterruptedException) has already discarded the flag and cannot be stopped by anything here.

That is why the interrupt discipline — rethrow, or restore the flag and return — is a shutdown concern rather than a style preference. The most common cause of "the pool did not terminate" is a swallowed interrupt somewhere in the task code.

Senior: How do you actually test concurrent code?

Start by accepting that ordinary unit tests find almost no races. A test runs briefly, interpreted, on an idle machine, exercising one interleaving out of billions — and the JIT optimisations that cause most memory-model bugs have not happened yet. A test that passes tells you very little.

TechniqueFinds
jcstressMemory-model violations — the only reliable way to test an ordering claim
Stress + invariantsLost updates: many threads, many iterations, then assert a total
Deterministic seamsA specific interleaving, by injecting a latch or a scheduler
SpotBugs / ErrorProneUnsynchronized access, @GuardedBy violations — cheap and static
-XX:+StressLCMRandomised JIT scheduling, surfacing reordering bugs
Production JFR and dumpsContention and pinning that only appear under real load

Assert invariants, not timings. "After 1000 threads each increment 1000 times, the total is exactly 1,000,000" is a real test. "It finishes within 2 seconds" is a flaky one.

A test containing Thread.sleep is not a concurrency test. Sleeping creates no happens-before edge, so it proves nothing about visibility — it just passes for the wrong reason and slows the suite.

The strategy that actually works is to design the bug space away: minimise shared mutable state, prefer immutability and confinement, use the concurrent library instead of hand-rolled locks, keep critical sections small, and never call unknown code under a lock. Each of those removes a class of bug that testing was never going to find.

Senior: A service is slow under load with the CPU at 20%. Walk through the diagnosis.

Idle CPU with poor throughput means threads are waiting rather than computing. The work is identifying what they wait on.

Three thread dumps, a few seconds apart. Threads at the same stack in all three are stuck, not busy. The state distribution then names the class of problem:

PatternDiagnosis
Many BLOCKED on one monitorLock contention — the dump names the owner
Many RUNNABLE in socket readsA slow downstream (RUNNABLE covers blocking I/O)
Pool threads all in one methodPool exhaustion behind a single dependency
Many WAITING on a queueIdle pool — the bottleneck is upstream
Threads waiting for a connectionConnection-pool exhaustion, often downstream latency

The most common root cause is I/O inside a critical section. A 200 ms call under a lock serialises everything — 100 concurrent requests take 20 seconds while the CPU does nothing.

Then narrow it with the right profiler. async-profiler in lock mode or JFR's jdk.JavaMonitorEnter events attribute total blocked time to specific monitors, which a snapshot cannot. Wall-clock profiling matters here — CPU profiling shows nothing when the problem is waiting.

The fixes in order of value: move I/O out of the critical section; split the lock by invariant; replace the structure with a concurrent one; remove the sharing entirely with immutability or confinement; or fix the slow dependency, which often makes the contention disappear because in-flight count drops proportionally.

What is almost never the answer is switching synchronized to ReentrantLock. Uncontended locking is already nearly free; contention is the problem, and no lock implementation fixes contention.

🏋️ Graded Exercises

1 (easy): Two bugs. Find both. 
private static final ThreadLocal<User> CTX = new ThreadLocal<>();

void handle(Request r) {
    CTX.set(r.user());
    process();
}   // submitted to a fixed thread pool
Solution

Bug 1 — a memory leak. The pooled thread lives for the life of the application and keeps the User reachable forever. With a large context object and a 200-thread pool, that is a permanent retention you will find in a heap dump.

Bug 2 — a security bug, and the worse one. The next request scheduled on this thread sees the previous user's context. If process() ever reads CTX without setting it first — an error path, a background continuation — one user's data is served to another.

void handle(Request r) {
    CTX.set(r.user());
    try { process(); }
    finally { CTX.remove(); }        // both bugs
}
AlternativeEffect
try/finally remove()Correct, but relies on discipline at every call site
ScopedValue (21+)Binding ends with the block — the bug is unrepresentable
Pass the user as a parameterBest when practical; nothing to leak

Why the ambient-context pattern persists is that threading a user through twenty call frames is tedious — which is exactly the pressure ScopedValue was designed to relieve without the leak.

2 (easy): Why might this hang forever? 
var latch = new CountDownLatch(services.size());
for (Service s : services) {
    exec.submit(() -> {
        s.start();
        latch.countDown();
    });
}
latch.await();
Solution

countDown() is not in a finally. If s.start() throws, the count is never decremented, and await() with no timeout blocks forever — with no error, because the exception was captured in the Future nobody inspects.

for (Service s : services) {
    exec.submit(() -> {
        try { s.start(); }
        catch (Exception e) { log.error("start failed: {}", s, e); }
        finally { latch.countDown(); }          // ALWAYS
    });
}
if (!latch.await(30, SECONDS))                  // ALWAYS a timeout
    throw new IllegalStateException("services did not start in 30s");
RuleWhy
countDown() in finallyA failing task must not hang the waiter
await with a timeoutTurns an invisible hang into a diagnosable error
Act on the false returnThe timeout is worthless if you ignore the result
Log inside the tasksubmit() hides exceptions in the Future

The double invisibility is what makes this expensive: the task failed silently and the waiter hangs silently. Neither produces a log line, so you get "the service does not start" with no evidence.

Remember a latch does not reset. If you need this repeatedly, use a CyclicBarrier or create a new latch each round.

3 (medium): What is wrong here, and how badly? 
List<Result> results = urls.parallelStream()
        .map(url -> httpClient.send(request(url), ofString()))
        .map(this::parse)
        .toList();
Solution

Blocking I/O in the common ForkJoinPool. parallelStream uses ForkJoinPool.commonPool, sized to cores - 1 and shared by the entire JVM.

ConsequenceDetail
Concurrency capped at ~coresOn 8 cores, 7 requests at a time regardless of list size
JVM-wide starvationEvery other parallelStream in the process stalls, including in libraries
Invisible couplingAn unrelated component slows down and nothing points here
No timeout or error isolationOne hung request occupies a common-pool worker indefinitely
// Best on Java 21+ — one virtual thread per request
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Result>> futures = urls.stream()
            .map(url -> exec.submit(() -> parse(
                    httpClient.send(request(url), ofString()))))
            .toList();
    return futures.stream().map(this::getQuietly).toList();
}

// Pre-21 — at least contain it in your own pool
var pool = new ForkJoinPool(32);
try { return pool.submit(() -> urls.parallelStream()…toList()).join(); }
finally { pool.shutdown(); }

The JVM-wide effect is the part that makes this severe. A local performance mistake becomes a global one, and the symptom appears in a component that has nothing to do with this code.

The general rule: parallelStream is for CPU-bound work over a large, cheaply splittable source. For I/O, use virtual threads.

4 (medium): Pick the right utility for each. (a) Wait for 5 caches to warm before serving traffic. (b) 4 worker threads process a matrix in phases, syncing after each phase. (c) At most 10 concurrent calls to a fragile downstream service. (d) Hand items from a reader thread to 3 processor threads.
Solution
ChoiceWhy
(a)CountDownLatch(5)One-shot "wait for N things"; a latch never resets, which suits startup exactly
(b)CyclicBarrier(4, mergeAction)Reusable rendezvous; the barrier action runs once per phase

(a) needs a timeout and a finally. await(30, SECONDS) plus countDown() in a finally, or a failing cache hangs startup with no diagnostic.

(b) is not fault-tolerant. If one party dies, the rest get BrokenBarrierException — which is why a barrier suits fixed-size compute phases and not request handling.

(c) is the important one in modern code. With virtual threads there is no thread pool limiting downstream load, so a Semaphore is how you express "at most 10 at a time". Use tryAcquire with a timeout so saturation produces fast rejection rather than an unbounded queue of waiters.

(d) must be bounded, and each consumer needs a per-item try/catch so one bad item does not kill a processor thread permanently.

5 (hard): Throughput drops 10× when a second thread is added. Neither counter is shared. Explain. 
public class Stats {
    private volatile long hits;      // thread A only
    private volatile long misses;    // thread B only

    public void hit()  { hits++; }
    public void miss() { misses++; }
}
Solution

False sharing. hits and misses are adjacent fields, 8 bytes apart, so they occupy the same 64-byte cache line. The threads never touch the same variable, but every write invalidates the other core's copy of the line, so it ping-pongs between cores on every increment.

volatile makes it worse: each write is a real store with a fence, so none of it can be cached in a register.

// Best — LongAdder's cells are already padded
public class Stats {
    private final LongAdder hits   = new LongAdder();
    private final LongAdder misses = new LongAdder();
    public void hit()  { hits.increment(); }
    public void miss() { misses.increment(); }
}
FixTrade-off
LongAdderPadded cells; sum() is not atomic with writes
@Contended on the fieldsNeeds -XX:-RestrictContended; wastes a cache line per field
Manual padding fieldsFragile — field layout is not guaranteed and the JIT may reorder
Per-thread counters, summed on readRemoves the sharing entirely; more code

There is also a correctness bug hiding here. volatile long hits; hits++; is still a read-modify-write race — safe only because exactly one thread writes each field, which is an undocumented invariant one refactor away from being false.

Why this is hard to find: nothing in the source suggests sharing, profilers show time in an increment that should cost a nanosecond, and it only appears with two or more threads. The signature is "adding a thread made it slower".

6 (hard): Design a bounded, cancellable job processor with graceful shutdown. State what each decision buys.
Solution 
public class JobProcessor implements AutoCloseable {
    private final BlockingQueue<Job> queue =
            new LinkedBlockingQueue<>(10_000);           // bounded
    private final Semaphore downstream = new Semaphore(50); // per-resource
    private final ExecutorService workers;
    private final LongAdder processed = new LongAdder();
    private final LongAdder failed    = new LongAdder();
    private volatile long lastProgressAt = System.nanoTime();

    public JobProcessor(int n) {
        workers = Executors.newFixedThreadPool(n,
                r -> new Thread(r, "job-worker"));         // named
        for (int i = 0; i < n; i++) workers.submit(this::loop);
    }

    public boolean submit(Job j) {
        return queue.offer(j);          // false = caller decides
    }

    private void loop() {
        while (!Thread.currentThread().isInterrupted()) {
            Job j;
            try { j = queue.take(); }                    // blocks
            catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            try {
                downstream.acquire();
                try { process(j); } finally { downstream.release(); }
                processed.increment();
                lastProgressAt = System.nanoTime();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            } catch (Exception e) {                      // per JOB
                failed.increment();
                log.error("job {} failed", j.id(), e);
            }
        }
    }

    @Override public void close() {
        workers.shutdown();
        try {
            if (!workers.awaitTermination(30, SECONDS)) {
                List<Runnable> dropped = workers.shutdownNow();
                log.warn("forced shutdown, {} queued", dropped.size());
                if (!workers.awaitTermination(10, SECONDS))
                    log.error("workers did not terminate");
            }
        } catch (InterruptedException e) {
            workers.shutdownNow();
            Thread.currentThread().interrupt();
        }
    }
}
DecisionWhat it buys
Bounded queueBackpressure instead of OutOfMemoryError
offer returning booleanThe caller decides to drop, retry or reject — only they know
take() rather than a flagBlocking and cancellation are the same mechanism; no busy-wait
Catch Exception per jobOne poison message does not end processing forever
Separate InterruptedException handlingCancellation must exit, not be logged and retried
Semaphore for downstreamBounds the scarce resource explicitly, not via worker count
Named threadsA thread dump becomes readable
lastProgressAtLiveness signal — detects a stall that logs never show
Four-step shutdownTerminates rather than assuming it did

The interrupt handling is what makes shutdown work. shutdownNow interrupts; catching InterruptedException together with the general Exception would log it and continue looping, and the pool would never terminate.

The liveness metric is the one people omit. A worker that dies or wedges produces no log line and no alert — throughput simply halves. A "last progress" timestamp with an alert detects it without depending on the failure being logged.

What I would still add: a retry policy with backoff for transient failures, a dead-letter destination for jobs that fail repeatedly, and idempotency so a retry after a partial success is safe. Those are business decisions the framework cannot make.

🎯 Key Takeaways

  • Safety bugs compute wrong answers; liveness bugs stop progress — and safety bugs are the dangerous ones because they are silent.
  • Try in order: don't share, make it immutable, confine it, then guard it.
  • Most "concurrency problems" are design problems where state became a field that should have been a local.
  • Immutable objects are safe to publish with no synchronization via the final-field guarantee.
  • A ThreadLocal without remove() on a pooled thread is a leak and a security bug — the next request sees the previous user's context.
  • An unbounded queue defers overload into an OutOfMemoryError that loses everything queued.
  • put, offer, timed offer and add each state a different overload policy — choose deliberately.
  • Catch exceptions per task, not around the loop, or one bad message silently ends processing.
  • countDown() belongs in a finally, and await always takes a timeout.
  • A CountDownLatch never resets; use a CyclicBarrier when you need to repeat.
  • A Semaphore is how you bound a scarce resource — essential once virtual threads remove the accidental pool limit.
  • Never block in ForkJoinPool.commonPool; it is shared by the whole JVM.
  • parallelStream needs CPU-bound work, a large splittable source and independent elements — all four, or go sequential.
  • False sharing puts unrelated hot fields on one cache line and costs an order of magnitude; LongAdder pads for you.
  • shutdown() does not wait — the four-step recipe with awaitTermination is the whole thing, and it fails if tasks swallow interrupts.
  • Unit tests find almost no races; assert invariants under stress, use jcstress for ordering claims, and design the bug space away.
