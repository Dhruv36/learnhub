Records & Sealed Types Modern Java

What you'll master: records as nominal tuples — a name, an ordered list of components, and generated equals, hashCode, toString and accessors that are correct by construction, which removes the entire category of contract bugs from the Equality lesson; the compact constructor, and why validation there makes an invalid instance unrepresentable; the shallow-immutability trap — a record holding a List is not immutable, and callers can mutate through it; sealed types, which let the compiler prove a switch is exhaustive so adding a subtype becomes a build error at every site; and how the two combine into algebraic data types, where the illegal states simply cannot be written. Prerequisites: Equality and Inheritance.

Part 1 — What a Record Generates

record Point(int x, int y) { }

  THAT ONE LINE GENERATES:

    private final int x;          a final field per component
    private final int y;
    Point(int x, int y)           the canonical constructor
    int x()                       an accessor per component — note the
    int y()                       name is x(), NOT getX()
    boolean equals(Object)        compares ALL components
    int hashCode()                derived from ALL components
    String toString()             "Point[x=1, y=2]"

  AND THE CLASS IS IMPLICITLY final, extending java.lang.Record.

  The equals and hashCode are the point. Hand-written, they are three
  methods against six contract rules with no compiler check that they
  agree — the failure modes from the Equality lesson. Generated, they
  cannot disagree, they handle null components, and they use
  Double.compare semantics for floating point so NaN and signed zero
  behave.

  THE ACCESSOR NAMING IS DELIBERATE. x() rather than getX() signals
  that a record is a transparent carrier of its state, not an object
  hiding one. It also matches the pattern-matching syntax in the next
  lesson.

  WHAT YOU CAN STILL ADD:

    record Point(int x, int y) {
        static Point origin() { return new Point(0, 0); }   // statics
        double distance() { … }                             // methods
        Point translated(int dx, int dy) {                  // "wither"
            return new Point(x + dx, y + dy);
        }
    }

  WHAT YOU CANNOT:

    extra instance fields         the components ARE the state
    extends anything              records are already final and extend
                                  Record
    non-final components          immutability is the contract

Part 2 — The Compact Constructor

record Range(int low, int high) {
    Range {                                  // COMPACT — no parameter
        if (low > high)                      // list, no assignments
            throw new IllegalArgumentException(low + " > " + high);
    }
}

  The compact form runs BEFORE the fields are assigned, and the
  parameters are implicitly assigned to the fields afterwards. So you
  validate — and may reassign the PARAMETERS to normalise — without
  writing this.low = low.

  NORMALISATION IS THE OTHER USE:

    record Email(String value) {
        Email {
            Objects.requireNonNull(value);
            value = value.trim().toLowerCase(Locale.ROOT);   // reassign
        }                                                    // the
    }                                                        // PARAMETER

  Now every Email in the program is trimmed and lower-cased, so
  equality behaves and no caller has to remember.

  WHY THIS MATTERS MORE THAN IT LOOKS: validating in the constructor
  makes an invalid instance UNREPRESENTABLE. A Range where low > high
  cannot exist anywhere in the program, so no downstream code needs to
  check — which is a much stronger guarantee than validating at each
  use.

  THE CANONICAL FORM IS ALSO AVAILABLE when you need full control:

    record Range(int low, int high) {
        Range(int low, int high) {           // canonical — explicit
            this.low = low;                  // assignments required
            this.high = high;
        }
    }

  Prefer the compact form; the canonical one is for the rare case
  where you must assign something different from the parameter.

Part 3 — Records Are Shallowly Immutable

  THE COMPONENTS ARE final. WHAT THEY POINT AT NEED NOT BE.

    record Team(String name, List<String> members) { }

    List<String> roster = new ArrayList<>(List.of("ada"));
    Team team = new Team("core", roster);

    roster.add("bob");            // ❌ MUTATES THE RECORD
    team.members().add("carol");  // ❌ so does this

  The reference cannot be reassigned; the list it points at is fully
  mutable, and the accessor hands it out.

  WHY THIS IS WORSE THAN AN ORDINARY CLASS HAVING THE SAME BUG: a
  record ADVERTISES immutability. Readers assume it, and the generated
  hashCode is computed from a mutable list — so a Team used as a map
  key becomes unreachable the moment someone adds a member. It is the
  vanishing-object bug, delivered by a type that looks like it cannot
  have it.

  THE FIX IS THE COMPACT CONSTRUCTOR:

    record Team(String name, List<String> members) {
        Team {
            members = List.copyOf(members);    // copy AND make
        }                                      // unmodifiable
    }

  List.copyOf does both jobs in one call, so the accessor needs no
  wrapping. Note it also rejects nulls, which turns "this list must
  not contain nulls" into an enforced rule.

  AND IT IS STILL SHALLOW: if the elements are mutable, callers reach
  through the unmodifiable list and change one. Immutable component
  types — records all the way down — are what actually close it.
⚠️ A record with a mutable component is the single most common record bug, and it is invisible. The class compiles, reads as a value type, and generates a hashCode over state that can change underneath it. The habit worth forming is: any record component that is a collection, an array, a Date, or a mutable class of your own gets a defensive copy in the compact constructor — and arrays are the worst case, because there is no Array.copyOf equivalent that also makes it unmodifiable, so an array component is nearly always the wrong choice.

Part 4 — Sealed Types

sealed interface Shape permits Circle, Square, Triangle { }

record Circle(double radius)          implements Shape { }
record Square(double side)            implements Shape { }
record Triangle(double b, double h)   implements Shape { }

  `sealed` declares a CLOSED set of subtypes. Nothing outside the
  permits clause may implement Shape — enforced by the compiler and by
  the JVM at class load.

  EVERY PERMITTED SUBTYPE MUST DECLARE ITS OWN INTENT:

    final       no further extension          (records are final)
    sealed      a further closed set
    non-sealed  deliberately reopened for extension

  There is no default; the compiler requires one of the three, which
  makes the decision explicit at every level of the hierarchy.

  WHAT IT BUYS: EXHAUSTIVENESS.

    double area(Shape s) {
        return switch (s) {
            case Circle c   -> Math.PI * c.radius() * c.radius();
            case Square q   -> q.side() * q.side();
            case Triangle t -> t.b() * t.h() / 2;
        };                       // NO default needed — and none wanted
    }

  Because the set is closed, the compiler can PROVE this covers every
  case. Add a Pentagon to the permits clause and every such switch
  fails to compile, naming the sites that need updating.

  That converts "find everywhere that handles Shape" from a grep into
  a compiler guarantee — the same argument as the exhaustive enum
  switch, extended to types that carry data.

  ADDING A default THROWS THAT AWAY. A default absorbs future
  subtypes silently, so omit it for a sealed hierarchy.

Part 5 — Algebraic Data Types

  RECORDS + SEALED = A CLOSED SET OF SHAPES, EACH CARRYING ITS OWN
  DATA. That is a sum of products — an algebraic data type — and it
  makes illegal states unrepresentable.

  THE PROBLEM IT SOLVES:

    class Result {                       // ❌ every field always
        boolean success;                 //    present
        String data;                     //    success + error set?
        String error;                    //    success with no data?
        int retryAfter;                  //    retryAfter when
    }                                    //    successful?

  Sixteen representable combinations, of which perhaps three are
  legal, and nothing enforces which.

    sealed interface Result<T> { }

    record Success<T>(T data)                    implements Result<T> { }
    record Failure<T>(String message)           implements Result<T> { }
    record Retry<T>(Duration after)             implements Result<T> { }

  Now each case carries EXACTLY the data it needs and nothing else.
  A Success has no error field to be inconsistent; a Retry has no data
  field to be null. The illegal combinations cannot be written.

  AND CONSUMING IT IS EXHAUSTIVE:

    String describe(Result<Order> r) {
        return switch (r) {
            case Success<Order> s -> "ok: " + s.data();
            case Failure<Order> f -> "failed: " + f.message();
            case Retry<Order> t   -> "retry in " + t.after();
        };
    }

  THE TRADE, HONESTLY: this is excellent for closed domains — a
  result, an expression tree, a protocol message, a state machine.
  It is wrong for an open set, where third parties must be able to add
  implementations. Sealing is a decision that the set of subtypes is
  YOURS, and reversing it later is a breaking change for anyone who
  wanted to extend it.

  A named tuple scoped to one method, with no file and no visibility

Interview Questions

Beginner: What does a record generate for you?

A private final field and an accessor for each component, a canonical constructor taking all components, and equals, hashCode and toString derived from all of them. The class is implicitly final and extends java.lang.Record.

The accessors are named after the component — x(), not getX() — which signals that a record is a transparent carrier of its state rather than an object hiding one.

The generated equals and hashCode are the substantive benefit. Written by hand they are three methods against six contract rules with no compiler check that they agree, and the failure modes are severe — a map that cannot find what you just put in it. Generated, they cannot disagree, and they handle nulls and floating-point edge cases correctly.

Beginner: What is a compact constructor for?

Validation and normalisation, without the ceremony of writing the field assignments.

It has no parameter list and no assignments — those are implicit. The body runs before the fields are set, and the parameters are assigned afterwards, so you can reassign a parameter to normalise it:

record Email(String value) {
    Email {
        Objects.requireNonNull(value);
        value = value.trim().toLowerCase(Locale.ROOT);
    }
}

The reason it matters more than it looks is that validating at construction makes an invalid instance unrepresentable. A Range where low exceeds high cannot exist anywhere in the program, so no downstream code needs to check — which is far stronger than validating at each point of use.

Writing this.value = value inside a compact constructor is a compile error, because the assignment is already implicit.

Mid: Are records immutable?

Shallowly. The components are final, so the references cannot be reassigned — but what they point at can be anything, including a mutable collection.

record Team(String name, List<String> members) { }

List<String> roster = new ArrayList<>();
Team t = new Team("core", roster);
roster.add("bob");            // mutates the record
t.members().add("carol");     // so does this

That is worse than the same bug in an ordinary class, because a record advertises immutability. Readers assume it, and the generated hashCode is computed over state that can now change — so a Team used as a map key becomes unreachable the moment someone adds a member. It is the vanishing-object problem, delivered by a type that looks incapable of it.

The fix is a defensive copy in the compact constructor, and List.copyOf is the right call because it copies and makes the result unmodifiable in one step, so the accessor needs no wrapping.

It is still shallow after that: if the elements are mutable, callers reach through and change one. Only immutable component types close it completely — which is an argument for records all the way down.

Arrays are the worst component type, because there is no copy that also makes them unmodifiable, and the generated equals compares array identity rather than contents.

Mid: What does sealed give you that abstract does not?

A closed set of subtypes, which the compiler can reason about.

An abstract class or interface can be extended by anyone, so the compiler can never know all the implementations. A sealed type lists them in its permits clause, and nothing outside that list may implement it — enforced at compile time and again by the JVM at class load.

The payoff is exhaustiveness checking. A switch over a sealed type with a case for every permitted subtype needs no default, and the compiler proves it is complete. Adding a subtype then breaks the build at every such switch, naming exactly the sites that need updating.

That converts "find everywhere that handles this type" from a grep into a guarantee — the same argument as an exhaustive enum switch, extended to types that carry data.

It also forces a decision at every level: each permitted subtype must declare itself final, sealed, or non-sealed. There is no default, so reopening a branch is deliberate and visible.

The cost is that sealing declares the subtypes are yours. If third parties should be able to extend the type, sealing is wrong — and unsealing later is a breaking change for anyone who wanted to.

Senior: How do records and sealed types combine into algebraic data types?

A sealed interface gives a closed set of alternatives; records give each alternative exactly the data it needs. Together that is a sum of products — and the practical effect is that illegal states become unrepresentable.

Compare the usual shape: a Result class with a success boolean, a data field, an error field and a retryAfter. Sixteen representable combinations, perhaps three of them legal, and nothing enforcing which — so every consumer defensively checks, and one of them gets it wrong.

sealed interface Result<T> { }
record Success<T>(T data)         implements Result<T> { }
record Failure<T>(String message) implements Result<T> { }
record Retry<T>(Duration after)   implements Result<T> { }

A Success has no error field to be inconsistent; a Retry has no data field to be null. The combinations that were illegal cannot be written at all, so the checks disappear rather than being duplicated.

And consumption is exhaustive: a switch covering the three cases needs no default, and adding a fourth outcome breaks every consumer at compile time.

This is the shape of an expression tree, a protocol message, a state machine, or a parse result — any closed domain where the set of cases is yours and the cases carry different data.

The honest limit is that it only fits closed domains. For anything third parties must extend, sealing is the wrong tool, and an ordinary interface with an open set of implementations is correct.

Senior: When would you not use a record?

Four cases, and the first is by far the most common.

JPA entities. An entity needs a no-arg constructor for reflective instantiation, mutable fields for dirty checking, and equality based on its identifier rather than all fields — a stale load of row 42 is still user 42. A record provides none of those. Use records for the DTOs at the boundary and classes for entities; keeping them separate is a feature, since the API contract and the persistence model should be free to differ.

When equality should use a subset of fields. The generated equals uses every component, so a cached object with a lastAccessed timestamp would compare unequal to itself a second later. Overriding equals on a record is legal and a strong signal that the type is not really a value.

When you need inheritance. Records are implicitly final. That is deliberate — it is what removes the equals-symmetry problem from the Equality lesson — but it rules out an abstract base with shared state.

When there are many components. The canonical constructor is positional, so eight components mean eight positional arguments and two of the same type adjacent is a transposition waiting to happen. Past about five, a builder or nested records that group related components read better.

And the general test: a record says "this type is its data". If the type has behaviour and invariants over mutable state, it is a class — records did not replace classes, they replaced the data-carrier ones.

🏋️ Graded Exercises

1 (easy): Write this class as a record, and list what disappears. 
public final class Point {
    private final int x, y;
    public Point(int x, int y) { this.x = x; this.y = y; }
    public int getX() { return x; }
    public int getY() { return y; }
    @Override public boolean equals(Object o) { … }
    @Override public int hashCode() { … }
    @Override public String toString() { … }
}
Solution 
record Point(int x, int y) { }
What disappearsWhat replaces it
Fields and constructorGenerated from the component list
getX() / getY()x() and y()
equals / hashCodeGenerated over all components — and correct
toStringPoint[x=1, y=2]
final on the classImplicit

The generated equality is the real gain, not the line count. Hand-written, those three methods must satisfy reflexivity, symmetry, transitivity, consistency, null-handling and the hashCode agreement — with nothing checking that they do. The generated versions also use Double.compare semantics for floating-point components, which hand-written ones usually get wrong for NaN and signed zero.

The accessor rename is not cosmetic. x() rather than getX() says the record is a transparent carrier of its state, and it is the form pattern matching uses when deconstructing.

If any caller depended on getX(), that is a source-incompatible change — worth knowing before converting a published type.

2 (easy): Make invalid instances impossible. 
record Percentage(int value) { }
// value must be 0..100
Solution 
record Percentage(int value) {
    Percentage {
        if (value < 0 || value > 100)
            throw new IllegalArgumentException(
                "percentage must be 0..100, was " + value);
    }
}

The compact constructor has no parameter list and no assignments — those are implicit. The body runs first, then the parameters are assigned to the fields.

The guarantee this creates is the point. A Percentage outside 0–100 cannot exist anywhere in the program, so no method receiving one needs to check. That is much stronger than validating at each use, where one caller eventually forgets.

Note the message includes the offending value. "Invalid percentage" costs a debugging session that "was 147" would have saved — the same argument as in the Exceptions lesson.

The stronger version of this idea is to use the type everywhere the concept appears. A method taking Percentage rather than int cannot be passed a raw 147, and cannot have its arguments transposed with an unrelated int — the parameter-type argument from the Methods lesson.

3 (medium): Why is this record not immutable, and what are the two levels of fix? 
record Team(String name, List<String> members) { }
Solution

The component is final; the list it refers to is not. Both the original reference and the accessor expose it.

List<String> roster = new ArrayList<>(List.of("ada"));
Team t = new Team("core", roster);

roster.add("bob");             // mutates through the ORIGINAL
t.members().add("carol");      // mutates through the ACCESSOR
// LEVEL 1 — defensive copy, in the compact constructor
record Team(String name, List<String> members) {
    Team {
        members = List.copyOf(members);     // copy AND unmodifiable
    }
}

List.copyOf does both jobs, so the accessor needs no wrapping — and it rejects nulls, turning "no null members" into an enforced rule.

// LEVEL 2 — immutable ELEMENTS, if they are not already
record Member(String name, String email) { }         // a record
record Team(String name, List<Member> members) { }   // now deep

Level 1 is still shallow. If the elements are mutable, a caller can iterate the unmodifiable list and change one — the list structure is protected, the contents are not.

Why this is worse in a record than in a class: the record advertises immutability, so readers stop checking. And the generated hashCode is computed over the mutable list, so a Team used as a map key becomes unreachable the moment a member is added — visible in size(), invisible to get().

4 (medium): Model a payment result so that illegal states cannot be represented.
Solution 
sealed interface PaymentResult
    permits Approved, Declined, RequiresAction { }

record Approved(String authCode, Money charged)   implements PaymentResult { }
record Declined(String reason, boolean retryable) implements PaymentResult { }
record RequiresAction(URI redirect)               implements PaymentResult { }
The flat-class version permitsThe sealed version
Approved with no auth codeCannot be constructed — the component is required
Declined with an auth codeThere is no such field on Declined
Approved and requiring actionThey are different types
retryable on a successDoes not exist there
String message(PaymentResult r) {
    return switch (r) {                       // no default — exhaustive
        case Approved a       -> "charged " + a.charged();
        case Declined d       -> "declined: " + d.reason();
        case RequiresAction x -> "redirect to " + x.redirect();
    };
}

Each case carries exactly the data it needs, so the defensive null checks that a flat class forces on every consumer simply disappear — there is no field to be null.

And adding a fourth outcome breaks the build at every switch, naming the sites to update. With a boolean-and-nullable-fields class, a new outcome compiles everywhere and misbehaves at runtime.

Omitting default is deliberate. Adding one would absorb future subtypes silently and discard the exhaustiveness guarantee — which is the whole reason to seal.

Where this would be wrong: if payment providers were plugins that could contribute their own result types, the set is not yours to close and sealing blocks them.

5 (hard): A team converts their JPA entities to records and everything breaks. Explain.
Solution
Requirement of an entityWhy a record cannot meet it
A no-arg constructorHibernate instantiates reflectively then populates fields; a record has only its canonical constructor
Mutable fieldsDirty checking compares the current state to a snapshot — final fields cannot change
Proxy subclassesLazy loading returns a generated subclass; records are implicitly final

The equality point is the deepest one. An entity has an identity that outlives its state — two loads of the same row are the same user even if one has a stale name. A record says the opposite: this object is its data. Those are different notions of sameness, and the record's is wrong for a persistent entity.

// The shape that works
@Entity
class User {                                   // a CLASS
    @Id @GeneratedValue private Long id;
    private String email;
    // equals/hashCode on id — see the Equality lesson
}

record UserDto(Long id, String email) { }      // a RECORD at the edge

UserDto toDto(User u) { return new UserDto(u.getId(), u.getEmail()); }

The separation is a feature rather than a workaround. The persistence model and the API contract are genuinely different things: a column rename should not break clients, and adding a field to the API should not require a migration. Sharing one type couples them permanently.

Where records fit in persistence is read-only projections — Spring Data can map a query result directly into a record, and JPA 3.2 supports record constructors in JPQL. That is querying, not entity mapping, and it is a good use.

6 (hard): Design an expression evaluator using sealed types and records, and say what the compiler now guarantees.
Solution 
sealed interface Expr permits Num, Add, Mul, Neg { }

record Num(double value)          implements Expr { }
record Add(Expr left, Expr right) implements Expr { }
record Mul(Expr left, Expr right) implements Expr { }
record Neg(Expr operand)          implements Expr { }

static double eval(Expr e) {
    return switch (e) {
        case Num n -> n.value();
        case Add a -> eval(a.left()) + eval(a.right());
        case Mul m -> eval(m.left()) * eval(m.right());
        case Neg n -> -eval(n.operand());
    };                                  // no default — exhaustive
}

// (2 + 3) * -4
Expr e = new Mul(new Add(new Num(2), new Num(3)), new Neg(new Num(4)));
The compiler guaranteesHow
Every case is handledThe permits clause closes the set, so the switch is provably exhaustive
Adding Div updates every consumerEach exhaustive switch fails to compile until the case is added
No malformed nodesAdd requires both operands; there is no partially-built state
Structural equality for freeGenerated equals compares recursively, so two structurally identical trees are equal — which makes testing trivial

The recursive toString is a free debugging aid too — printing the tree gives a readable nested form with no visitor to write.

What this replaces is the visitor pattern. Before sealed types, adding an operation over a closed hierarchy meant a visitor interface, an accept method on every node, and a new implementation per operation. Now an operation is one method with a switch, and the compiler still enforces completeness — which was the visitor's main benefit.

Where the visitor still wins is an open hierarchy that third parties extend, since sealing forbids exactly that. The trade is the same one as everywhere in this lesson: sealing buys exhaustiveness by giving up extensibility.

The natural next step is record deconstruction patterns — case Add(Expr l, Expr r) -> eval(l) + eval(r) — which removes the accessor calls entirely. That is the Pattern Matching lesson.

🎯 Key Takeaways

  • A record generates fields, accessors, constructor, equals, hashCode and toString — and the generated equality is correct by construction.
  • Accessors are x(), not getX(), signalling a transparent data carrier.
  • Records are implicitly final, which removes the equals-symmetry problem entirely.
  • The compact constructor validates and normalises before the fields are assigned — reassign the parameter.
  • Validating there makes invalid instances unrepresentable, so downstream code stops checking.
  • Records are only shallowly immutable — a mutable component is the most common record bug, and it is invisible.
  • List.copyOf in the compact constructor copies and makes unmodifiable in one call.
  • Array components are worse still — no unmodifiable copy, and generated equals compares identity.
  • sealed closes the set of subtypes, enforced by the compiler and the JVM.
  • Every permitted subtype must declare final, sealed or non-sealed — there is no default.
  • Exhaustiveness is the payoff: a switch needs no default, and adding a subtype breaks the build at every site.
  • Adding a default discards that guarantee.
  • Records plus sealed types make illegal states unrepresentable — each case carries exactly its own data.
  • Not for JPA entities — identity is the id, not all fields, and entities need mutability and a no-arg constructor.
  • Not when equality should use a subset of fields, or when the type has behaviour over mutable state.
  • Local records are underused — a named tuple scoped to one method.
