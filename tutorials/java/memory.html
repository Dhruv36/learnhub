Memory: Stack, Heap & References JVM & Performance

What you'll master: what actually lives on the stack versus the heap — the reference is in the frame, the object never is; why an empty object costs 16 bytes, and how the header, field packing and 8-byte padding produce that number; compressed oops and the 32GB cliff, where raising -Xmx can reduce the objects you can hold; what boxing really costs (20 bytes and a pointer chase instead of 4) and the Integer cache == trap that passes every test and fails in production; ArrayList growing 1.5× against HashMap doubling at load factor 0.75, and why new HashMap<>(n) does not hold n; the four reference strengths with a real job for each, including why soft references fight your GC settings; the six leak shapes that survive a collector; and shallow versus retained size — the one distinction that makes a heap dump readable. Prerequisites: JVM Architecture & Class Loading.

Part 1 — The Variable Is on the Stack, the Object Never Is

  ONE SENTENCE REMOVES MOST OF THE CONFUSION:

    THE VARIABLE LIVES IN THE STACK FRAME.
    THE OBJECT ALWAYS LIVES ON THE HEAP.

  void process() {
      int   count = 0;                // 4 bytes, IN THE FRAME
      Point p     = new Point(3, 4);  // 4-byte REFERENCE in the frame;
                                      // the Point is on the HEAP
      int[] data  = new int[1000];    // 4-byte REFERENCE in the frame;
                                      // a 4016-byte array on the HEAP
  }

  When process() returns, the frame is popped and count, p and data
  vanish in one stack-pointer adjustment — no GC involved. The Point
  and the int[] are still on the heap; they merely became UNREACHABLE,
  and are freed whenever the collector next runs. Two different
  reclamation mechanisms at two different times, and confusing them is
  the root of most "why is memory still high" questions.

  THE RULE FOR FIELDS IS THE OPPOSITE OF WHAT PEOPLE EXPECT:

    class Order {
        int    quantity;    // 4 bytes INSIDE the Order, on the heap
        String customer;    // 4-byte reference INSIDE the Order; the
                            // String is a separate heap object
    }

  A primitive LOCAL is on the stack. A primitive FIELD is on the heap.
  "Primitives live on the stack" is a half-truth that breaks the moment
  you write a class. The useful question is "local or field?", never
  "primitive or object?".

  WHY THE SPLIT EXISTS — LIFETIME, NOT SPEED. A local's lifetime is
  exactly the call, so the compiler can allocate by adding to a pointer
  and free by subtracting. An object can outlive its creator (returned,
  stored in a field, handed to a thread), so its lifetime is unknown at
  compile time — and that freedom is precisely what costs you a
  collector.

  PER-THREAD VS SHARED — WHY RACES ONLY HAPPEN ON ONE SIDE:

    Thread A stack     Thread B stack        SHARED HEAP
    ┌──────────────┐   ┌──────────────┐   ┌────────────────────┐
    │ frame: run() │   │ frame: run() │   │  Order@0x7f2a      │
    │   int i = 3  │   │   int i = 9  │   │    quantity = 5    │
    │   ref ───────┼───┼──────────────┼──▶│    customer ──┐    │
    └──────────────┘   │   ref ───────┼──▶│               │    │
                       └──────────────┘   │  String "ann" ◀┘   │
                                          └────────────────────┘

  No other thread can name your locals, so they cannot be raced on.
  Everything reachable through the heap can be. That picture is why the
  memory model is entirely about heap state and says nothing at all
  about locals.

  THE ESCAPE HATCH: the JIT runs ESCAPE ANALYSIS, and if it proves an
  object cannot be seen outside the compiled region it does not
  allocate at all — it explodes the object into registers:

    double dist(int x, int y) {
        Point p = new Point(x, y);       // never escapes
        return Math.sqrt(p.x*p.x + p.y*p.y);
    }
    // after C2: no allocation, no header, no GC pressure.

  Routinely worth 2-5x on allocation-heavy loops, and fragile: inlining
  must succeed first, and returning the object, storing it in a field,
  or passing it to an unresolved virtual call all kill it. Nothing here
  is in the language spec — "stack" and "heap" are HotSpot choices, and
  that is exactly what makes deleting the allocation legal.

Part 2 — Frames, -Xss, and StackOverflowError

  EVERY THREAD GETS ITS OWN STACK, SIZED ONCE AT CREATION. Each call
  pushes a FRAME:

    ┌─────────────────────────────────────┐  high addresses
    │ frame: main()                       │
    │   local variable array              │
    │   operand stack (the JVM is a stack │
    │     machine — iadd pops two)        │
    │   frame data: return address,       │
    │     constant-pool ref, exceptions   │
    ├─────────────────────────────────────┤
    │ frame: service()                    │
    ├─────────────────────────────────────┤
    │ frame: repository()   ◀── current   │
    └─────────────────────────────────────┘  grows downward
                        ▼ push past here → the guard page → SOE

  Frame size is fixed AT COMPILE TIME: javac records max_locals and
  max_stack in the method's Code attribute. Three ints and a small
  expression is 40-60 bytes; twenty locals with longs and a deep
  expression tree can be several hundred. That is why "how deep can I
  recurse" has no single answer.

  DEFAULT -Xss (HotSpot 64-bit): 1 MB on Linux and Windows.

    java -Xss512k App     # smaller: more threads fit
    java -Xss4m   App     # larger: deeper recursion survives

  MEASURED DEPTHS on a 1 MB stack, same machine and JDK:

    trivial recursion, one int arg  ...  ~20,000 - 60,000 frames
    method with ~10 locals          ...  ~ 8,000 - 15,000 frames
    a Jackson/JAXB parse chain      ...  ~ 1,500 -  4,000 frames
    interpreted (pre-JIT) frames    ...  roughly 2x a compiled one

  The spread is enormous, so never design around a depth number. It
  moves with -Xss, the JDK, the OS guard page, and whether C2 has
  inlined several logical frames into one physical frame.

  -Xss IS PER-THREAD AND OFF-HEAP. THIS BITES AT SCALE:

    2,000 platform threads x 1 MB = 2 GB RESERVED, entirely outside
    -Xmx.

  It is address space, committed lazily page by page, so RSS is usually
  far lower — but in a container with a hard limit the committed pages
  are real and the OOM killer does not care that your heap looked fine.
  (This is a large part of the argument for virtual threads, whose
  stacks are growable heap chunks measured in hundreds of bytes.) Note
  that -Xss does NOT resize the main thread on most platforms; if you
  need a deep stack, construct the thread yourself:

    new Thread(null, task, "deep", 16L * 1024 * 1024).start();

  THE FOUR WAYS TO HIT StackOverflowError:

  1. UNBOUNDED RECURSION — no base case, or an unreachable one:

       int fact(int n) { return n * fact(n - 1); }              // ❌
       int fact(int n) { return n <= 1 ? 1 : n * fact(n-1); }   // ✔

  2. ACCIDENTAL SELF-DELEGATION — the classic:

       public String toString() { return "Order" + this; }  // ❌
       // string concat calls toString() → forever

  3. CYCLES IN THE DATA, NOT THE CODE — a recursive walk over a graph
     containing a cycle. The code is correct; the data is not. Fix with
     a visited set (IdentityHashMap), not a bigger stack.

  4. LEGITIMATELY DEEP DATA — a 200,000-node list, deeply nested JSON.
     Here recursion is the wrong TOOL, because Java has NO TAIL-CALL
     ELIMINATION: even perfect tail recursion allocates a frame per
     call.

  THE FIX IS ALMOST NEVER A BIGGER -Xss. Move the frames from the 1 MB
  stack to the multi-GB heap with an explicit stack:

    void walk(Node root) {
        Deque<Node> todo = new ArrayDeque<>();
        if (root != null) todo.push(root);
        while (!todo.isEmpty()) {
            Node n = todo.pop();
            visit(n);
            if (n.right != null) todo.push(n.right);
            if (n.left  != null) todo.push(n.left);
        }
    }

  CATCHING SOE IS ALMOST ALWAYS WRONG — you have no idea which frame
  died, so an object may be half initialised or a lock half acquired.
  The one defensible use is a top-level server handler that abandons
  the whole request and unwinds to a known-clean state.

  READING THE TRACE: it is truncated at 1024 frames
  (-XX:MaxJavaStackTraceDepth=0 shows all). Ignore the top frame and
  look for the REPEATING CYCLE — two or three method names repeated
  over and over name your bug immediately.

Part 3 — Object Layout, and the 32GB Cliff

  A HOTSPOT OBJECT ON A 64-BIT JVM, HEAP UNDER 32 GB:

    offset  size  contents
    ──────  ────  ────────────────────────────────────────────────
       0      8   MARK WORD — identity hash, GC age bits, lock
                  state, or (during a copying GC) a FORWARDING
                  POINTER to the moved copy
       8      4   KLASS POINTER — which class this is
      12      ?   INSTANCE FIELDS, reordered by the JVM
       ?      ?   PADDING to a multiple of 8

  Header = 12 bytes. Alignment = 8 bytes. Therefore:

    new Object()  →  12 header + 0 fields = 12  →  PADDED TO 16.

  That is why "nothing" costs 16 bytes: a lock word you may never use,
  a type pointer, and four bytes of nothing.

  PADDING MAKES FIELD COSTS WILDLY NON-LINEAR:

    class A {}                   12 → 16   (4 bytes wasted)
    class B { int x; }           16 → 16   (the first int is FREE)
    class C { int x, y; }        20 → 24   (the second int costs 8)
    class D { int x,y,z; }       24 → 24   (the third is free again)
    class E { long a; int b,c; } 28 → 32

  "Adding one int made it 4 bytes bigger" is wrong half the time.

  FIELD REORDERING: the JVM does NOT use source order. It sorts by
  width (longs/doubles, ints/floats, shorts/chars, bytes/booleans,
  references) to close gaps, and superclass fields always precede
  subclass fields. So you cannot shrink an object by rearranging your
  source — only by removing fields, narrowing types, or replacing a
  boxed field with a primitive.

  ARRAYS CARRY AN EXTRA LENGTH WORD: header 12 + length 4 = 16.

    new int[0]     16 + 0    = 16
    new byte[1]    16 + 1    = 17 → 24     (7 bytes of padding!)
    new int[1000]  16 + 4000 = 4016

  A million byte[1] objects cost 24 MB to hold 1 MB of data. Small
  arrays are nearly pure overhead — which is why a pool of little
  arrays usually loses to one big array plus offsets.

  DO NOT GUESS. MEASURE WITH JOL (Java Object Layout):

    ClassLayout.parseInstance(new C()).toPrintable();  // offsets,
                                                       // gaps, padding
    GraphLayout.parseInstance(myMap).totalSize();      // deep size

  It is the only honest answer, because layout depends on the JDK, the
  flags, and the heap size. JDK 24/25's COMPACT OBJECT HEADERS
  (-XX:+UseCompactObjectHeaders) fold the mark word and klass pointer
  into 8 bytes, so the header drops 12 → 8: objects sitting just over
  an alignment boundary shrink by 8, others do not change at all.
  Re-run JOL rather than predicting it.

  ─────────────────── COMPRESSED OOPS AND THE 32 GB CLIFF ────────────

  A 64-bit pointer is 8 bytes, and references dominate a Java heap, so
  HotSpot stores them as 32-BIT values whenever it can:

    every object is 8-byte aligned → the low 3 bits of any address are
    always zero → store address >> 3 in 32 bits
    → 2^32 slots x 8 bytes = 34,359,738,368 = EXACTLY 32 GB

    decode: real = heap_base + (compressed << 3)
    (with a "zero-based" heap the base add disappears — one shift)

  Compressed oops are ON by default whenever -Xmx allows. Cross the
  limit and the JVM SILENTLY turns them off. Then every reference
  field, every reference array element, and every klass pointer goes
  from 4 bytes to 8.

  THE CLIFF, WITH ARITHMETIC:

    -Xmx31g   compressed oops ON,  ~31 GB of usable object space
    -Xmx33g   compressed oops OFF, references doubled

    A reference-dense heap (maps, linked structures, object graphs) is
    commonly 30-50% pointers. Doubling those costs 15-25% of the heap,
    so 33 GB with fat pointers HOLDS LESS LIVE DATA THAN 31 GB with
    thin ones. Raising -Xmx made you smaller. You need roughly
    40-48 GB before you are reliably ahead of 31 GB.

  VERIFY, DO NOT ASSUME:

    java -Xlog:gc+heap+coops=info -Xmx31g -version
    → "Compressed Oops mode: Zero based, Oop shift amount: 3"

  PRACTICAL RULES:
    • Stay at or below -Xmx31g. Highest-value heap decision on a big
      machine, and it costs nothing.
    • Need more? Run SEVERAL 31 GB JVMs, or move bulk data off-heap,
      before jumping to a 64 GB heap.
    • -XX:ObjectAlignmentInBytes=16 raises the ceiling to 64 GB by
      shifting 4 instead of 3 — but pads every object to 16 bytes,
      which usually wastes more than the pointers saved. Measure.

Part 4 — What Boxing Actually Costs

  int     → 4 bytes, stored INLINE, no indirection, no header.
  Integer → a 16-byte heap object PLUS the 4-byte reference pointing at
            it. TWENTY BYTES TO STORE FOUR.

  THE ARITHMETIC ON A MILLION VALUES:

    int[1_000_000]                 ~  4 MB
    Integer[1_000_000] (distinct)  ~ 20 MB    5x
      = 4 MB of refs + 16 MB of objects
    List<Integer>, 1,000,000       ~ 20-26 MB (plus up to 50% spare
                                               capacity if unsized)
    HashMap<Integer,Integer>       ~ 69 MB   17x
      per entry: 32 (Node) + ~5.3 (table slot at 0.75 load)
                 + 16 (key) + 16 (value)  ≈ 69 bytes

  THE MEMORY IS THE SMALL HALF OF THE COST. THE LAYOUT IS THE BIG HALF:

    int[] sum:      values are CONTIGUOUS. Sixteen per 64-byte cache
                    line, prefetcher-friendly, vectorisable. Runs at
                    memory bandwidth.
    Integer[] sum:  each element is a POINTER → a dependent load →
                    likely an L2/L3 or DRAM miss (~80-100 ns) → then
                    unbox. No vectorisation, and the objects are
                    scattered in ALLOCATION order, so locality depends
                    on how the list was built.

  Typical measured gap on a summation loop: 3-10x, widening as the data
  outgrows cache. That is why IntStream exists:

    IntStream.range(0, n).sum()                      // primitives
    list.stream().mapToInt(Integer::intValue).sum()  // unbox once
    list.stream().reduce(0, Integer::sum)            // ❌ boxes every
                                                     //    step

  ─────────────────── THE Integer CACHE AND THE == TRAP ──────────────

  Autoboxing does NOT call new. It calls Integer.valueOf, which the JLS
  REQUIRES to return a cached instance for -128..127:

    Integer a = 127, b = 127;   a == b  → TRUE   (same cached object)
    Integer c = 128, d = 128;   c == d  → FALSE  (two objects)

  This is the most dangerous behaviour in the language because the
  failure is INVISIBLE IN TESTS. Fixtures use id 1, 2, 3 — all cached,
  all passing. Production uses id 90210, the comparison silently starts
  returning false, and orders stop matching users. No exception, no log
  line.

    if (order.getUserId() == user.getId())            // ❌
    if (Objects.equals(order.getUserId(), user.getId()))  // ✔ and
                                                          //   null-safe

  WHAT IS AND IS NOT CACHED:

    Boolean    both values, always
    Byte       all 256 values, always
    Short      -128..127
    Integer    -128..127; upper bound raisable with
               -XX:AutoBoxCacheMax=n (the LOWER bound never moves)
    Character  0..127
    Long       -128..127
    Float      NOTHING
    Double     NOTHING → Double x = 1.0, y = 1.0; x == y is ALWAYS
                         false, with no lucky small-value pass

  Note the cruelty of AutoBoxCacheMax: raising it makes MORE broken
  code accidentally work, which makes the bug harder to find.

  UNBOXING THROWS NPE, AND THE LINE NUMBER LIES:

    Map<String,Integer> counts = new HashMap<>();
    int n = counts.get("missing");   // ❌ NPE from the implicit
                                     //    .intValue() on null

  Worse, in a conditional expression:

    Integer maybeNull = null;
    Integer r = flag ? 1 : maybeNull;   // ❌ NPE even when flag is
                                        //    TRUE and the null branch
                                        //    is never taken

  Because one arm is int and the other Integer, binary numeric
  promotion unboxes BOTH — the expression type becomes int, and the NPE
  happens on the branch you thought was dead. Fix by making both arms
  the same reference type.

  THE OVERLOAD TRAP:

    List<Integer> list = new ArrayList<>(List.of(10, 20, 30));
    list.remove(1);                   // removes INDEX 1 → 20 goes
    list.remove(Integer.valueOf(1));  // removes the VALUE 1 → nothing

  remove(int) and remove(Object) are different methods and Java prefers
  the non-boxing overload.

  WHEN TO CARE, HONESTLY: below a few thousand elements this is noise —
  write the clear code. Above a million, or in a per-request hot path,
  it dominates, and the fix is int[]/long[], IntStream, or a primitive
  collection library (fastutil, Eclipse Collections, HPPC), which
  typically takes a Map<Integer,Integer> from ~69 bytes per entry to
  ~9-16 with open addressing and no per-entry object at all.

Part 5 — Growth: ArrayList 1.5× vs HashMap 2×

  BOTH ARE ARRAYS UNDERNEATH, AND AN ARRAY CANNOT GROW. "Growing" means
  ALLOCATE A BIGGER ONE, COPY, ABANDON THE OLD. They differ in factor,
  and the difference is not arbitrary.

  ArrayList — 1.5x, AND THE FIRST add IS LAZY:

    int newCapacity = oldCapacity + (oldCapacity >> 1);   // 1.5x

    new ArrayList<>() allocates NO array. The first add() creates
    Object[10]. Then 10 → 15 → 22 → 33 → 49 → 73 → 109 → …

    Reaching 1,000,000 from the default: ~30 reallocations. A 1.5x
    geometric series sums to n/(1-1/1.5) = 3n, so ~3,000,000 slot
    copies and ~12 MB of dead Object[] to end up holding a 4 MB array.
    Peak transient footprint at the last resize: old + new = 2.5x.

    new ArrayList<>(1_000_000) → ONE allocation, zero copies, zero
    garbage. The highest-value one-word change in most loading code.

  Why 1.5 and not 2? Amortised O(1) only needs a CONSTANT factor above
  1. A 1.5 factor wastes at most 50% instead of at most 100%, and a
  sequence of 1.5x blocks can eventually REUSE previously freed blocks;
  with doubling, the new block is always larger than the sum of all
  freed ones.

  HashMap — 2x, AND THE POWER OF TWO IS LOAD-BEARING:

    capacity is ALWAYS a power of two, so bucket = hash & (cap-1) —
    one AND instead of a modulo (~20-40x cheaper). Doubling preserves
    that property; 1.5x would not.

    default capacity 16, load factor 0.75,
    threshold = capacity * loadFactor, resize when size > threshold:

      cap  16 → resize at 12 entries
      cap  32 → resize at 24
      cap  64 → resize at 48
      cap 128 → resize at 96 …

  ⚠ THE CONSTRUCTOR ARGUMENT IS NOT AN ENTRY COUNT. IT IS A TABLE SIZE.

    new HashMap<>(100)     → table 128, resizes at 96 entries.
                             Put 100 and YOU STILL RESIZE.
    new HashMap<>((int)(100/0.75f)+1)   → table 256, no resize.  ✔
    HashMap.newHashMap(100)            → JDK 19+, does it for you.
                             Also newLinkedHashMap, newHashSet.

  Nearly every "I pre-sized it" in the wild is wrong by exactly this
  factor. It is silent, and purely a performance bug.

  WHAT A RESIZE COSTS: a new Node[2n] plus a walk of EVERY entry.
  Java 8+ does not recompute hashes — an entry in bucket i moves to
  either i or i+oldCap, decided by one bit (hash & oldCap), so each
  bin splits into a "lo" and a "hi" list. Cheaper than a full rehash,
  still O(n), still a latency spike. On a 10M-entry map that is tens to
  hundreds of milliseconds, allocating an 80 MB table while the old one
  is still live.

  WHY 0.75: the javadoc notes that under uniform hashing, bucket
  occupancy is Poisson-distributed; at 0.75 the chance of a bucket
  reaching 8 entries is about 6 in 100,000,000. Drop to 0.5 and you
  spend 50% more table memory for a barely measurable gain; raise to
  1.0 and chains lengthen fast. Leave it alone unless you measured.

  TREEIFICATION: a bin with 8+ nodes becomes a red-black tree, but only
  once the table has 64+ slots (below that it resizes instead); it
  untreeifies at 6. That caps a pathological bucket at O(log n) — a
  hash-collision DoS defence, not a normal path. If you see treeified
  bins, your hashCode is bad.

  ⚠ NEITHER STRUCTURE EVER SHRINKS.

    A HashMap that peaked at 10,000,000 entries and now holds 3 still
    owns a 16,777,216-slot table — ~67 MB of Node[] that will never be
    released. clear() nulls the CONTENTS, not the TABLE.

    Fixes: list.trimToSize(), or rebuild the map at the right size.
    This "leak that is not a leak" is one of the most common heap-dump
    findings in long-lived caches.

  ALSO WORTH KNOWING:
    ArrayDeque            doubles, power-of-two, never shrinks
    StringBuilder         newCapacity = 2*old + 2 (default 16)
    CopyOnWriteArrayList  copies the ENTIRE array on EVERY write —
                          fine for 10 listeners, catastrophic for
                          10,000 rows

Part 6 — Four Reference Strengths, Four Different Jobs

  REACHABILITY IS A LADDER. The collector walks from the GC roots and
  labels each object with the STRONGEST chain that reaches it:

    strongly reachable  → never collected
    softly  reachable   → collected under heap pressure, before OOME
    weakly  reachable   → collected at the next collection
    phantom reachable   → already collected; you are told afterwards
    unreachable         → gone

  THE STRONGEST-CHAIN RULE IS THE WHOLE GAME: one strong reference
  anywhere defeats a thousand weak ones. That alone explains most
  "my weak cache isn't working" reports.

  ─── 1. STRONG — the default. Nothing to configure.

  ─── 2. WEAK — CANONICAL MAPS AND METADATA YOU DO NOT OWN

    WeakReference<Config> ref = new WeakReference<>(config);
    Config c = ref.get();      // may be null — ALWAYS check

  WeakHashMap holds its KEYS weakly, so an entry disappears when the
  key becomes otherwise unreachable. Its real job is ATTACHING DATA TO
  OBJECTS WHOSE LIFETIME YOU DO NOT CONTROL:

    Map<String,Currency> canonical = new WeakHashMap<>();  // one
                                     // instance per code
    Map<Connection,Stats> perConn  = new WeakHashMap<>();  // stats
                                     // on a third-party object

  TWO TRAPS THAT MAKE IT USELESS:

  (a) THE VALUE MUST NOT REFERENCE THE KEY. If it does, the map holds
      the value strongly, the value holds the key strongly, and the
      entry is immortal. Your weak map is a leak with extra steps.

  (b) IT IS NOT A CACHE. Entries vanish the moment nobody else holds
      the key — and with interned String keys, that is never. For
      caching use Caffeine/Guava with a size or time bound.

  ─── 3. SOFT — "MEMORY-SENSITIVE CACHE", AND WHY IT DISAPPOINTS

    SoftReference<byte[]> img = new SoftReference<>(decoded);

  Contract: cleared at the collector's discretion, but GUARANTEED to be
  cleared before an OutOfMemoryError. HotSpot's policy is
  time-and-space based:

    -XX:SoftRefLRUPolicyMSPerMB=1000     (default)

  A soft referent survives roughly ONE SECOND PER MEGABYTE OF FREE HEAP
  since its last access. On a 16 GB heap with 8 GB free that is ~8,000
  seconds — over two hours. Your "memory-sensitive cache" is
  effectively unbounded until the heap is nearly full.

  WHY THEY FIGHT YOUR GC SETTINGS — the part people miss:

    • They KEEP OBJECTS ALIVE THROUGH YOUNG COLLECTIONS, so cached
      objects are PROMOTED to the old generation. You converted cheap
      young garbage into expensive old-gen occupancy.
    • They are cleared aggressively only during a FULL GC, so the
      behaviour is: heap fills → full GC → the ENTIRE cache is dropped
      at once → every request misses → the app rebuilds everything →
      repeat. A sawtooth of full GCs and cold caches.
    • That fights a pause-time goal directly: G1/ZGC are tuned to
      AVOID full GCs, so the event that clears your soft refs is the
      one you configured the collector never to have.
    • They make the live set unpredictable, which breaks capacity
      planning and makes GC logs hard to read.

  VERDICT: soft references are a 2004 answer. Use a BOUNDED cache
  (Caffeine, maximumSize or expireAfterWrite). A cache whose size you
  chose is one you can reason about; one the GC empties at random
  is not.

  ─── 4. PHANTOM — POST-MORTEM CLEANUP, THE FINALIZER REPLACEMENT

    PhantomReference<Buf> p = new PhantomReference<>(buf, queue);
    p.get()    // ALWAYS returns null, by design

  You cannot resurrect the object — that is the point. What you get is
  a NOTIFICATION on a ReferenceQueue that the object is gone, so you
  can release something ELSE it owned (a native handle, an fd, an
  off-heap block):

    class Handle extends PhantomReference<Buf> {
        final long nativePtr;            // ⚠ a plain long — NOT a
        Handle(Buf b, long ptr) {        //   reference to Buf
            super(b, queue); this.nativePtr = ptr;
        }
    }
    while (true) {                       // reaper thread
        Handle h = (Handle) queue.remove();   // blocks until one dies
        free(h.nativePtr);
        h.clear();
    }

  THE ONE RULE: THE CLEANUP STATE MUST NOT REFERENCE THE OBJECT BEING
  CLEANED. If it does, the object stays strongly reachable from your
  reaper, never becomes phantom reachable, and the cleanup NEVER RUNS.
  That is why the example holds a long, not a Buf.

  In practice use java.lang.ref.Cleaner (JDK 9+), which is this with
  the thread and queue managed for you:

    private static final Cleaner CLEANER = Cleaner.create();
    // ⚠ the action must capture ptr, never `this`
    cleanable = CLEANER.register(this, () -> free(ptr));

  ─── WHY FINALIZERS WENT AWAY (JEP 421, deprecated for removal in
      JDK 18, which also shipped --finalization=disabled)

  Object.finalize() was broken in six independent ways:

    1. NO TIMING GUARANTEE. It may run in a second, in an hour, or
       never — the JVM may exit without running it. Any resource
       release that depends on it is a leak.
    2. ONE UNBOUNDED QUEUE, ONE THREAD. A slow finalizer stalls every
       other finalizer in the VM, and the queue grows until OOME.
    3. TWO GC CYCLES MINIMUM. A finalizable object survives the first
       collection in order to be queued, so it is PROMOTED — short-
       lived objects become old-gen garbage. Effective Java measured
       allocation of a finalizable class at ~400x a plain one.
    4. RESURRECTION. finalize() can store `this` and bring a dead
       object back, which every collector must defend against.
    5. SWALLOWED EXCEPTIONS. A throw aborts finalization for that
       object and is reported nowhere.
    6. THE FINALIZER ATTACK. A subclass finalizer, reached via a
       failed super() call, gets a half-built object that bypassed its
       invariant checks.

  THE REPLACEMENT IS NOT PHANTOM REFERENCES. It is try-with-resources:

    try (var in = Files.newInputStream(path)) { … }   // deterministic

  Cleaner/phantom refs are the SAFETY NET for a caller who forgot to
  close — and specifically for NATIVE memory, which no try-block can
  free once the object is already gone.

Part 7 — Leaks, Heap Dumps, and Memory Outside the Heap

  A "MEMORY LEAK" IN JAVA IS NOT A MISSING free(). IT IS AN
  UNINTENTIONAL STRONG REFERENCE. The collector is working perfectly —
  it is refusing to free objects YOUR CODE can still reach. Every
  investigation reduces to one question:

    WHAT PATH FROM A GC ROOT KEEPS THIS ALIVE?

  THE SIX SHAPES, ROUGHLY BY HOW OFTEN THEY ARE THE ANSWER:

  1. STATIC COLLECTIONS. A static field IS a GC root, so anything it
     reaches lives for the process lifetime.

       static final Map<String,Session> SESSIONS = new HashMap<>();

     Symptom: heap grows linearly with uptime and never recovers after
     a full GC. Fix: a bounded cache with eviction, and a removal path
     that also runs on the failure branches.

  2. UNCLOSED RESOURCES. A stream or connection holds native handles
     AND a chain of Java buffers. Leaking connections exhausts a pool,
     so the symptom is often "hangs" before it is "OOME". Fix:
     try-with-resources — and remember Files.lines() is itself
     closeable.

  3. LISTENERS REGISTERED AND NEVER REMOVED.

       bus.subscribe(this::onEvent);      // and no unsubscribe

     The bus is long-lived; the method reference holds `this`; `this`
     holds a whole page or service graph. Every navigation adds
     another. Fix: pair every add with a remove in a finally/dispose.

  4. ThreadLocal IN A POOLED THREAD — the subtle one.

       static final ThreadLocal<Context> CTX = new ThreadLocal<>();
       CTX.set(new Context(hugeRequest));      // never removed

     The value is attached to the THREAD, not the task, and pool
     threads live for the app's lifetime. ThreadLocalMap holds the
     ThreadLocal KEY weakly but the VALUE STRONGLY, and stale entries
     are swept only opportunistically when a later get/set/remove
     happens to probe that slot — so the value can survive
     indefinitely.

       try { CTX.set(ctx); handle(req); }
       finally { CTX.remove(); }               // ✔ non-negotiable

     In a container this is also a classloader leak: Context was
     loaded by the webapp loader and a container thread now pins it.

  5. INNER-CLASS this$0. A non-static inner class, an anonymous class,
     or a lambda touching an instance member holds a hidden reference
     to the ENCLOSING instance:

       class ReportPage {                   // holds 40 MB of rows
           byte[] data = new byte[40_000_000];
           void schedule() {
               scheduler.schedule(new Runnable() {    // ❌ inner
                   public void run() { ping(); }      //    → this$0
               }, 1, HOURS);
           }
       }

     One tiny Runnable pins 40 MB for an hour. Fix: a static nested
     class taking exactly the fields it needs, or a lambda capturing
     only locals — a lambda that touches NO instance state does not
     capture `this` at all.

  6. CLASSLOADER LEAKS ON REDEPLOY. Symptom: OutOfMemoryError:
     Metaspace after the third or fourth redeploy, heap fine. ONE
     reference from a JDK or container class into a webapp class pins
     the webapp ClassLoader, and a ClassLoader pins EVERY class it
     loaded plus every static field in them. Usual culprits:

       • a JDBC driver registered in java.sql.DriverManager
       • a ThreadLocal whose VALUE type is a webapp class
       • a Timer/ExecutorService thread the app never stopped
       • a log appender or JMX MBean still registered
       • a shutdown hook holding an app object

     Diagnosis: heap dump, then "path to GC roots" from the webapp
     ClassLoader. There is usually exactly one path; cure that.

  ALSO REAL, OFTEN MISDIAGNOSED:
    • A mutable object used as a HashMap key, then mutated. Its hash
      changed, so nothing can find it — but the map still holds it.
    • hashCode/equals inconsistency → duplicate keys accumulate.
    • Collections that never shrink (Part 5). Not a leak; looks
      exactly like one in a dump.

  ─────────────────── READING A HEAP DUMP ────────────────────────────

  GET ONE:
    -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps
    jcmd <pid> GC.heap_dump /tmp/app.hprof      (on demand)
    jcmd <pid> GC.class_histogram               (cheap first look)

  ⚠ A dump is roughly the size of the LIVE HEAP and STOPS THE WORLD for
  seconds to a minute. On a 30 GB heap, plan for a real outage and
  enough disk — take it from a canary out of the load balancer.

  THE ONE DISTINCTION THAT MAKES A DUMP READABLE:

    SHALLOW SIZE  — the bytes of the object ITSELF: header + fields.
                    References count as 4 or 8 bytes, not as what they
                    point to. A HashMap holding 10,000,000 entries has
                    a SHALLOW SIZE OF 48 BYTES.

    RETAINED SIZE — the bytes that would be FREED if this object were
                    collected: itself plus everything reachable ONLY
                    through it. The same HashMap: 700 MB.

  Sort a dump by shallow size and you get byte[] and String at the top
  — in every application, always, identifying nothing. Retained size is
  the number that answers "what is eating my heap".

  THE DOMINATOR TREE IS WHERE THE ANSWER IS:

    X DOMINATES Y ⟺ EVERY path from a GC root to Y passes through X.

    GC root ─▶ CacheHolder ─▶ HashMap ─▶ Node ─▶ Session ─▶ byte[]
                    │
                    └── dominates all of it, so its retained size is
                        the whole subtree

  MAT builds this tree and sorts by retained size; the top few rows ARE
  your leak. An object shared by two independent paths is dominated by
  neither — it floats up to their common dominator, which is exactly
  what you want: a shared cache shows up at the place that owns it.

  THE TWO-QUESTION WORKFLOW:

    "WHAT is big?"     → Dominator tree by retained size. Group by
                         class to see 3,000,000 Sessions instead of
                         3,000,000 rows.
    "WHY is it alive?" → Path to GC Roots, EXCLUDING ALL WEAK/SOFT/
                         PHANTOM REFERENCES. That exclusion is
                         essential: weak paths cannot keep anything
                         alive, and leaving them in buries the one
                         strong path that can.

  You need BOTH. The tree without the path says a HashMap is huge but
  not who owns it; the path without the tree tells you about an object
  too small to matter.

  THE SINGLE BEST TECHNIQUE IS TWO DUMPS: one at a steady state, run a
  known workload, another. Diff the histograms. Growth between two
  steady states is the leak by definition, and it removes the guesswork
  entirely. Also worth knowing: duplicate strings are commonly 10-30%
  of a large heap (-XX:+UseStringDeduplication), and MAT's Leak
  Suspects report is a decent first guess you should verify, not trust.

  ─────────────────── OFF-HEAP: DirectByteBuffer ─────────────────────

    ByteBuffer.allocate(8192);        // byte[] on the heap
    ByteBuffer.allocateDirect(8192);  // malloc'd, OUTSIDE -Xmx

  WHY THEY EXIST: the OS needs a stable address to DMA into, and a heap
  byte[] can be MOVED by the collector at any moment. So every I/O
  through a heap buffer is first copied into a temporary direct buffer.
  (HotSpot caches those temporaries PER THREAD, which is itself a
  native-memory surprise at a few hundred threads.) A direct buffer is
  handed to the kernel as-is: zero copy.

  THE COSTS, MEASURED:
    allocateDirect  ~10-100 µs   (malloc + mandatory zeroing)
    allocate        ~0.1-1 µs    (a TLAB pointer bump)
    → 10-100x. NEVER allocate a direct buffer per request. Allocate a
      pool at startup and reuse it. They pay off for long-lived, large,
      frequently reused I/O buffers and lose badly for small ones.

  THE LIFECYCLE IS THE DANGEROUS PART:

    The DirectByteBuffer OBJECT is ~64 bytes on the heap. The MEMORY is
    megabytes off-heap. The native block is freed only when that tiny
    Java object is collected and its Cleaner runs.

    → GC pressure is driven by the 64 bytes, not the megabytes.
    → A healthy, low-allocation app never collects them, so RSS climbs
      while the heap looks perfect.
    → You are killed by the container (exit 137) with NO Java OOME and
      NO heap dump, while your GC logs look clean.

  -XX:MaxDirectMemorySize IS THE GUARD RAIL. Unset, it DEFAULTS TO THE
  MAXIMUM HEAP SIZE — so a -Xmx4g service silently permits another 4 GB
  of direct memory and a 5 GB container dies. Set it explicitly and
  size the container as:

    -Xmx + MaxDirectMemorySize + metaspace + code cache
         + (threads x -Xss) + GC structures + native libs + headroom

  When the direct limit is reached, Bits.reserveMemory calls
  System.gc() and retries — so a service running with
  -XX:+DisableExplicitGC can throw "OutOfMemoryError: Direct buffer
  memory" while the memory is in fact reclaimable. One of the very few
  places where an explicit GC is load-bearing.

  DIAGNOSING NATIVE MEMORY:
    -XX:NativeMemoryTracking=summary + jcmd <pid> VM.native_memory
        → committed bytes per category: heap, class, thread, code, GC
    java.nio:type=BufferPool,name=direct MBean
        → Count, MemoryUsed, TotalCapacity — graph this
    MALLOC_ARENA_MAX=2
        → glibc creates up to 8 arenas per core; on a 32-core box that
          alone can inflate RSS by hundreds of MB

  THE MODERN ANSWER — JDK 22+ FOREIGN FUNCTION & MEMORY API gives
  off-heap memory the DETERMINISTIC lifetime DirectByteBuffer never
  had:

    try (Arena arena = Arena.ofConfined()) {
        MemorySegment seg = arena.allocate(1_000_000);
        …
    }   // freed HERE, at close. No Cleaner, no GC, no guessing.

  It also removes DirectByteBuffer's 2 GB int-indexing cap, and it is
  bounds-checked, unlike Unsafe.

Interview Questions

Beginner: What is the difference between the stack and the heap?

The stack is per-thread and holds one frame per active call — local variables, the operand stack, and bookkeeping. Frames are pushed on call and popped on return, so allocation and deallocation are a single pointer adjustment, no collector involved, and nothing on a stack can be shared between threads.

The heap is shared by all threads and holds every object and array. Objects outlive the method that created them, so their lifetime cannot be known at compile time — which is exactly why a garbage collector exists.

The sentence that resolves most confusion: the variable is on the stack, the object is on the heap. In Point p = new Point(), p is a 4-byte reference in the frame and the Point is on the heap. When the method returns p disappears instantly; the Point merely becomes unreachable and is freed later.

The common half-truth is "primitives go on the stack". That holds for local primitives only — a primitive field lives inside its object, on the heap. Ask "local or field?", not "primitive or reference?".

One refinement worth adding: neither region is defined by the language specification. They are HotSpot implementation details, which is precisely what lets the JIT's escape analysis prove an object never leaves a method and scalar-replace it into registers, with no heap allocation at all.

Beginner: Why does Integer a = 128, b = 128; a == b return false when 127 returns true?

Autoboxing does not call new. It calls Integer.valueOf, which the JLS requires to return a cached instance for −128 to 127. Two boxes of 127 are therefore the same object and == is true. Two boxes of 128 are two distinct objects, so == compares two different addresses.

What makes this the most dangerous behaviour in the language is that the failure is invisible in tests. Fixtures use id 1, 2, 3 — all cached, all passing. Production uses id 90210 and the comparison silently starts returning false. No exception, no log line; orders just stop matching users, and you find out months later.

The fix is to never use == on boxed types. Objects.equals(a, b) is correct and null-safe. If you genuinely have primitives, use primitives — and note that mixing Integer == int is fine, because the boxed side unboxes and the comparison becomes numeric.

Know the boundaries for the follow-up: Boolean always, Byte all values, Short/Integer/Long −128..127, Character 0..127, and Float and Double cache nothing — so Double x = 1.0, y = 1.0; x == y is false at every value, with no lucky small-number pass to hide it. -XX:AutoBoxCacheMax can widen the Integer range, which only makes broken code accidentally work over a wider span; never rely on it.

Mid: Explain the four reference strengths and give a real use for each.

The collector labels each object by the strongest chain that reaches it from a GC root. One strong reference anywhere defeats any number of weak ones — that rule alone explains most "my weak cache isn't working" reports.

StrengthClearedReal use
StrongNever while reachableEverything, by default
SoftUnder heap pressure, guaranteed before OOMELegacy memory-sensitive caches — mostly a mistake today
WeakNext GC once no strong/soft ref remainsWeakHashMap for canonicalisation and metadata on objects you do not own
PhantomEnqueued after collection; get() always nullFreeing native memory once the Java object is gone

Weak is for association, not caching. WeakHashMap holds keys weakly, so an entry disappears when the key becomes otherwise unreachable — right for "one canonical instance per code" tables, or for hanging statistics off a third-party Connection. Two traps: the value must not reference the key (or the entry is immortal), and it is not a cache, because entries vanish the instant nobody else holds the key.

Soft looks ideal for caching and is not. HotSpot keeps a softly reachable object for roughly SoftRefLRUPolicyMSPerMB (default 1000 ms) per megabyte of free heap, so on a large heap nothing is cleared for hours — then a full GC drops the entire cache at once. Meanwhile the cached objects survive young collections and get promoted to the old generation. Use a bounded cache instead.

Phantom exists to tell you an object is definitely gone. get() returns null by design so you cannot resurrect it; paired with a ReferenceQueue it lets you free a native block afterwards. In practice use java.lang.ref.Cleaner, which packages the queue and reaper thread — with the same non-negotiable rule that the cleanup state must not reference the object being cleaned, or it will never become phantom reachable and the cleanup will never run.

Mid: Why is an empty Object 16 bytes, and what is the 32GB heap cliff?

On a 64-bit HotSpot with compressed oops the header is 12 bytes: an 8-byte mark word (identity hash, GC age, lock state, or a forwarding pointer while a copying collector moves the object) and a 4-byte klass pointer. Objects align to 8 bytes, so 12 rounds up to 16. You pay for a lock word you may never use, a type pointer, and four bytes of nothing.

The alignment makes field costs non-linear: the first int is free (12 + 4 = 16), the second costs 8 (20 → 24), the third is free again. The JVM also reorders fields by width to close gaps, so you cannot shrink an object by rearranging source. Measure with JOL — and note -XX:+UseCompactObjectHeaders (JDK 24/25) folds the header to 8 bytes, shrinking some objects by 8 and others not at all.

Compressed oops: because every object is 8-byte aligned, the low three bits of any address are zero, so HotSpot stores a reference as a 32-bit value shifted right by 3. That addresses 232 × 8 bytes = exactly 32 GB. Below that limit every reference field, array element and klass pointer is 4 bytes instead of 8.

Cross the limit and the JVM silently disables it. Every reference doubles. A reference-dense heap is commonly 30–50% pointers, so you lose 15–25% of the heap to pointer width: a 33 GB heap can hold less live data than a 31 GB heap. Raising -Xmx made the application smaller, and you need roughly 40–48 GB before you are reliably ahead.

The practical rule is to cap at -Xmx31g and verify with -Xlog:gc+heap+coops=info. If you need more, run several JVMs or move bulk data off-heap before jumping to a 64 GB heap. -XX:ObjectAlignmentInBytes=16 raises the ceiling to 64 GB but pads every object to 16 bytes, which usually costs more than the pointers it saves.

The premise gives away the answer's shape: the memory is not in the heap, so no amount of heap tuning or heap-dump reading will find it. There is no Java OutOfMemoryError and no automatic heap dump because the JVM never noticed a problem — the kernel killed the process (exit 137).

It is one of the very few places where an explicit GC is load-bearing.

Senior: You have a 12GB heap dump from a service that OOMEs after four days. How do you find the leak?

The four-day timescale already tells me it is a slow accumulation, not a burst — so I am looking for something that grows monotonically with uptime or request count, and the answer will be a strong reference from a long-lived root.

Step 1 — open the dominator tree sorted by retained size, not the histogram. This is the distinction that decides whether the investigation takes ten minutes or a day. Shallow size is the object's own header and fields: a HashMap holding ten million entries has a shallow size of 48 bytes. Retained size is everything that would be freed if the object went away. Sorting by shallow size gives you byte[] and String at the top — in every application, always, identifying nothing. The dominator tree tells you which object owns those bytes, because X dominates Y when every path from a GC root to Y goes through X.

Step 2 — from the top retained entry, take "path to GC roots, excluding weak/soft/phantom". The exclusion matters: weak paths cannot keep anything alive, and including them buries the one strong path that can. The tree says what is big; the path says why it is alive. You need both answers, and they are different questions.

Step 3 — match the path to a known shape. A static Map, a ThreadLocal value on a pooled thread, a listener list on a long-lived bus, an inner class's this$0, an unclosed resource chain — or, if this were a metaspace OOME after redeploys, a classloader pinned by a JDBC driver or a container thread. Nine times in ten the path names the bug directly. Then rule out the impostor: collections never shrink, so a HashMap that peaked at ten million entries and now holds three still owns a 16-million-slot table, roughly 67 MB of Node[], forever. That looks exactly like a leak and is fixed by rebuilding the collection, not by hunting references.

If one dump is ambiguous, take two. One at a steady state, run a known workload, then another, and diff the histograms. Growth between two steady states is the leak by definition, and it removes all the judgement from step 3. That is worth the operational cost: a dump is roughly the size of the live heap and stops the world for seconds to a minute, so I take it from a canary out of the load balancer, with -XX:+HeapDumpOnOutOfMemoryError configured as the safety net.

My recommendation is prevention over diagnosis: run allocation profiling continuously (JFR's ObjectAllocationSample costs about 1%), alert on live-set size after full GC rather than on heap used, and treat every long-lived registry — caches, listener lists, ThreadLocals — as requiring a documented removal path before it merges. Those three habits catch nearly everything that would otherwise become a four-day OOME.

The boxed array is 5× and the map 17× the primitive array. Each Integer is a 16-byte object (12-byte header + 4-byte value) reached through a 4-byte reference: 20 bytes to store 4.

The memory is the smaller half of the cost. Summing int[] streams contiguous memory — sixteen values per 64-byte cache line, prefetcher-friendly, vectorisable, running at memory bandwidth. 3 (medium): Both collections are pre-sized. One of them is not. Which, and why? 
List<Row> rows = new ArrayList<>(100_000);
Map<String,Row> index = new HashMap<>(100_000);
for (Row r : source) { rows.add(r); index.put(r.id(), r); }
Solution

The HashMap is wrong. Its constructor argument is an initial table capacity, not an entry count. It rounds 100,000 up to the next power of two — 131,072 — and resizes when size > capacity × 0.75, i.e. at 98,304 entries. You wanted room for 100,000, so you still pay a full resize to 262,144 slots.

// correct, all JDKs
Map<String,Row> index = new HashMap<>((int) (100_000 / 0.75f) + 1);

// correct and readable, JDK 19+
Map<String,Row> index = HashMap.newHashMap(100_000);
// also LinkedHashMap.newLinkedHashMap, HashSet.newHashSet

What the wrong version actually does at runtime: at entry 98,304 the map allocates a new Node[262144] — about 1 MB — while the old 512 KB table is still live, then walks all 98,304 entries splitting each bin into a "lo" and a "hi" list using one bit of the stored hash. Java 8+ does not recompute hashes, so it is cheaper than a classic rehash, but it is still O(n), still touches every node, and still shows up as a latency spike. On a 10-million-entry map the same event is tens to hundreds of milliseconds and allocates an 80 MB table.

Pre-sizing is the cheapest performance change in most data-loading code, and the one most often written incorrectly. The ArrayList line is doing real work here: without it, growing to 100,000 from the default capacity of 10 costs roughly 25 reallocations and about 300,000 element copies, producing several hundred kilobytes of dead arrays on the way.

4 (medium): This handler leaks in a servlet container. Find both leaks. 
public class RequestHandler {
    private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();
    private final byte[] responseBuffer = new byte[10_000_000];

    public void handle(Request req) {
        CTX.set(new UserContext(req.user()));
        scheduler.schedule(new Runnable() {
            public void run() { audit(CTX.get()); }
        }, 1, TimeUnit.HOURS);
        render(req);
    }
}
Solution

Leak 1 — ThreadLocal set and never removed on a pooled thread. The value is attached to the thread, not the request, and container threads live for the application's lifetime, so every thread permanently holds the last UserContext it saw. ThreadLocalMap holds the ThreadLocal key weakly but the value strongly, and stale entries are swept only opportunistically when a later get/set/remove happens to probe that slot — so the value can survive indefinitely. In a container this is also a classloader leak, because UserContext was loaded by the webapp loader and a container thread now pins it.

Leak 2 — the anonymous Runnable's hidden this$0. An anonymous inner class captures its enclosing instance, so the scheduled task holds the RequestHandler, which holds a 10 MB byte[], for a full hour. Under load that is thousands of live handlers and gigabytes of pinned buffers.

public void handle(Request req) {
    UserContext ctx = new UserContext(req.user());
    CTX.set(ctx);
    try {
        // capture the VALUE — not `this`, not the ThreadLocal
        scheduler.schedule(() -> audit(ctx), 1, TimeUnit.HOURS);
        render(req);
    } finally {
        CTX.remove();                 // ✔ non-negotiable in a pool
    }
}

The subtle part of the fix is that the lambda captures ctx — a local — so it holds a 200-byte context instead of the handler. 5 (hard): A batch job on a 64GB machine had its heap raised from 31GB to 48GB and now OOMEs where it used to finish. Explain and fix. 
# before:  java -Xmx31g -jar batch.jar    → completes
# after:   java -Xmx48g -jar batch.jar    → OutOfMemoryError
Solution

Compressed oops turned off. Below 32 GB, HotSpot stores every reference as a 32-bit value: objects are 8-byte aligned, so the low three bits of an address are always zero and the JVM stores address >> 3, addressing 232 × 8 = exactly 32 GB. Above that limit the encoding cannot cover the heap, so the JVM silently disables it and every reference field, reference array element and klass pointer grows from 4 bytes to 8.

Item≤ 32 GB heap> 32 GB heap
Reference field4 bytes8 bytes
Object[] element4 bytes8 bytes
Klass pointer4 bytes8 bytes
HashMap.Node32 bytes48 bytes

The arithmetic: a reference-dense workload — maps, linked structures, object graphs — is commonly 30–50% pointers by volume, so doubling pointer width costs 15–25% of the heap. Data that needed 30 GB live at 31 GB with thin pointers now needs about 36–38 GB. 48 GB should just cover it, but you have also lost headroom for GC copying reserve and for the allocation burst, and G1 needs space to evacuate into. Hence the OOME — and note that at 33 GB it would have been strictly worse than the original 31 GB.

# verify what you actually got — do not assume
java -Xlog:gc+heap+coops=info -Xmx48g -version
java -XX:+PrintFlagsFinal -version | grep UseCompressedOops

The fix, in order of preference. First, go back to -Xmx31g and find out why 31 GB was not enough — a batch job needing more than 31 GB of live data usually has an accumulation it does not need, and streaming the input instead of materialising it is both cheaper and faster. Second, if the data genuinely is that big, run several 31 GB JVMs and partition the work: two 31 GB heaps hold far more than one 62 GB heap. Third, move the bulk data off-heap — a MemorySegment or a memory-mapped file has no pointers to widen. Only after those, consider a heap around 64 GB, where the extra space finally outweighs the doubled pointers.

-XX:ObjectAlignmentInBytes=16 extends the ceiling to 64 GB by shifting 4 bits instead of 3. It is real, and usually a trap: every object is then padded to a 16-byte boundary, so many 24-byte objects become 32. Measure before believing it.

The counter-intuitive headline worth remembering: on the JVM, more heap can mean less memory. It is the only common tuning knob where increasing the number makes the resource smaller.

6 (hard): This class wraps a native buffer. It leaks native memory and the cleanup never runs. Fix it. 
public class NativeBuffer {
    private final long ptr;

    public NativeBuffer(int size) {
        this.ptr = Native.malloc(size);
    }

    @Override
    protected void finalize() {
        Native.free(ptr);
    }
}
Solution

There are two problems: finalization is the wrong mechanism, and the obvious "modern" rewrite using a Cleaner that captures this would be broken in a way that is harder to see.

Why finalize fails here. It is deprecated for removal (JEP 421, JDK 18, which also shipped --finalization=disabled), and every one of its defects bites this class. There is no timing guarantee and the JVM may exit without running it, so native memory leaks on shutdown. All finalizers share one unbounded queue and one thread, so a slow one stalls every other finalizer in the VM. A finalizable object survives its first collection in order to be enqueued and is therefore promoted to the old generation — Effective Java measured allocation of a finalizable class at roughly 400× a plain one. And because the heap sees a small object while the native block is large, GC pressure never reflects the real memory use, so collection may not happen for hours.

public class NativeBuffer implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();

    // ⚠ a STATIC class holding only primitives — it must NOT be able
    //   to reach the NativeBuffer, or NativeBuffer never dies
    private static final class State implements Runnable {
        private final long ptr;
        State(long ptr) { this.ptr = ptr; }
        public void run() { Native.free(ptr); }
    }

    private final Cleaner.Cleanable cleanable;

    public NativeBuffer(int size) {
        this.cleanable = CLEANER.register(this,
                             new State(Native.malloc(size)));
    }

    @Override public void close() { cleanable.clean(); } // idempotent
}

// callers now get DETERMINISTIC release:
try (NativeBuffer buf = new NativeBuffer(1 << 20)) { … }

The trap in the rewrite: if the registered action were a lambda like () -> Native.free(this.ptr) it would capture this. The Cleaner holds the action strongly, so the NativeBuffer would stay strongly reachable forever, never become phantom reachable, and the cleanup would never run at all — strictly worse than the finalizer. That is why State is a static nested class holding only a long. The same rule governs hand-rolled phantom references.

The ordering that matters: close() is the real mechanism and the Cleaner is a backstop for callers who forgot. Getting that backwards — treating the Cleaner as the design and close() as optional — reproduces exactly the DirectByteBuffer problem, where releasing native memory depends on collecting a tiny Java object that may never be urgent enough to collect. For new code prefer try (Arena arena = Arena.ofConfined()), which frees at close() with no cleaner, no queue and no reachability reasoning at all.

🎯 Key Takeaways

  • The variable is on the stack; the object is always on the heap. A local reference is 4 bytes in the frame pointing at a heap object.
  • "Primitives live on the stack" is true only for locals — a primitive field lives inside its object, on the heap.
  • The split is about provable lifetime, not speed, which is why escape analysis can delete an allocation entirely.
  • Thread stacks are native memory outside -Xmx — 2,000 threads at -Xss1m reserve 2 GB the heap budget never sees.
  • A bigger -Xss never fixes a StackOverflowError — fix the recursion, or move the frames to the heap with an explicit Deque.
  • An empty object is 16 bytes: 8-byte mark word + 4-byte klass pointer, padded to an 8-byte boundary.
  • Padding makes field costs non-linear — the first int is free, the second costs 8. Measure with JOL; the JVM already reordered your fields.
  • Compressed oops end at 32GB, and crossing that line can shrink your app — every reference doubles, so 33 GB holds less live data than 31 GB.
  • An Integer costs 20 bytes to store 4 — a 16-byte object plus a 4-byte reference, and a pointer chase on every read.
  • Integer.valueOf caches −128..127, so == passes every test and fails in production. Use Objects.equals; Double caches nothing.
  • new HashMap<>(n) does not hold n entries — it resizes at 0.75n. Use HashMap.newHashMap(n).
  • ArrayList grows 1.5× and HashMap doubles; reaching n unsized costs ≈3n element copies, and neither structure ever shrinks.
  • The strongest reference chain wins — one strong reference defeats any number of weak ones, which is why most weak caches do not work.
  • Soft references fight your GC settings: nothing clears until a full GC, cached objects are promoted to old gen meanwhile, then the whole cache vanishes at once.
  • Finalizers are gone for six independent reasons; the replacement is try-with-resources, with Cleaner as a safety net whose action must never capture the object.
  • Java leaks are unintentional strong references — static collections, unclosed resources, unremoved listeners, ThreadLocal in a pool, inner-class this$0, and classloaders pinned on redeploy.
  • Shallow size answers nothing; retained size answers everything. Dominator tree for "what is big", path-to-GC-roots for "why is it alive".
  • Direct buffers are freed by a GC of a 64-byte object — set -XX:MaxDirectMemorySize explicitly, or use a JDK 22+ Arena for deterministic release.
