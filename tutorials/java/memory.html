Memory: Stack, Heap & References JVM & Performance

What you'll master: what actually lives on the stack versus the heap — the reference is in the frame, the object never is; why an empty object costs 16 bytes and how the header, field packing and 8-byte padding produce that number; compressed oops and the 32GB cliff, where raising -Xmx can reduce the objects you can hold; what boxing really costs (20 bytes and a pointer chase instead of 4) and the Integer cache == trap that passes every test and fails in production; ArrayList growing 1.5× against HashMap doubling at load factor 0.75, and why new HashMap<>(n) does not hold n; the four reference strengths with a real job for each, including why soft references fight your GC settings; the six leak shapes that survive a garbage collector; and shallow versus retained size — the one distinction that makes a heap dump readable. Prerequisites: JVM Architecture & Class Loading.

Part 1 — The Variable Is on the Stack, the Object Never Is

  ONE SENTENCE REMOVES MOST OF THE CONFUSION:

    THE VARIABLE LIVES IN THE STACK FRAME.
    THE OBJECT ALWAYS LIVES ON THE HEAP.

  void process() {
      int   count = 0;                // 4 bytes, IN THE FRAME
      Point p     = new Point(3, 4);  // 4-byte REFERENCE in the frame;
                                      // the Point is on the HEAP
      int[] data  = new int[1000];    // 4-byte REFERENCE in the frame;
                                      // a 4016-byte array on the HEAP
  }

  When process() returns, the frame is popped and count, p and data
  disappear in one stack-pointer adjustment. No GC is involved at all.
  The Point and the int[] are still sitting on the heap; they merely
  became UNREACHABLE, and they are freed whenever the collector next
  runs. Two different reclamation mechanisms, running at completely
  different times, and confusing them is the root of most "why is my
  memory still high" questions.

  THE RULE FOR FIELDS IS DIFFERENT AND PEOPLE GET IT BACKWARDS:

    class Order {
        int    quantity;        // 4 bytes INSIDE the Order, on the heap
        String customer;        // 4-byte reference INSIDE the Order;
                                // the String is a separate heap object
    }

  A primitive LOCAL is on the stack. A primitive FIELD is on the heap,
  embedded in its owning object. "Primitives are on the stack" is a
  half-truth that breaks the moment you write a class.

  WHY THE SPLIT EXISTS AT ALL — IT IS ABOUT LIFETIME, NOT SPEED:

    Stack:  lifetime is EXACTLY the method call. LIFO. The compiler
            knows every size at compile time, so allocation is
            "add N to the stack pointer" and freeing is subtraction.
            No bookkeeping, no fragmentation, no collector.
    Heap:   lifetime is UNKNOWN at compile time. An object can outlive
            the method that made it (return it, store it in a field,
            hand it to another thread). That freedom is exactly what
            costs you a garbage collector.

  So the question "stack or heap?" is really "can the compiler prove
  when this dies?" If yes, stack. If no, heap.

  PER-THREAD VS SHARED — THIS IS WHY DATA RACES ONLY HAPPEN ON ONE SIDE:

    Thread A stack     Thread B stack        SHARED HEAP
    ┌──────────────┐   ┌──────────────┐   ┌────────────────────┐
    │ frame: run() │   │ frame: run() │   │  Order@0x7f2a      │
    │   int i = 3  │   │   int i = 9  │   │    quantity = 5    │
    │   ref ───────┼───┼──────────────┼──▶│    customer ──┐    │
    └──────────────┘   │   ref ───────┼──▶│               │    │
                       └──────────────┘   │  String "ann" ◀┘   │
                                          └────────────────────┘

  Locals cannot be raced on: no other thread can name them. Everything
  reachable through the heap can be. That single picture explains why
  the memory model (happens-before, volatile, synchronized) is entirely
  about heap state and says nothing about locals.

  THE ESCAPE HATCH: SCALAR REPLACEMENT

  The JIT runs ESCAPE ANALYSIS. If it proves an object cannot be seen
  outside the compiled region, it does not allocate at all — it
  explodes the object into registers:

    double dist(int x, int y) {
        Point p = new Point(x, y);          // never escapes
        return Math.sqrt(p.x*p.x + p.y*p.y);
    }
    // after C2: no allocation, no header, no GC pressure.
    // p.x and p.y become two registers.

  This is real and routinely worth 2-5x on allocation-heavy hot loops.
  It is also fragile: inlining must succeed first, and storing the
  object in a field, returning it, passing it to an unresolved virtual
  call, or SYNCHRONIZING on something that escapes will kill it.
  Verify with -XX:+PrintEscapeAnalysis on a debug JVM, or just watch
  the allocation rate in GC logs before and after a change.

  NOTHING HERE IS SPECIFIED BY THE JLS. "Stack" and "heap" are HotSpot
  implementation choices; the spec only defines visibility and
  lifetime. That is precisely what lets the JIT delete allocations
  without breaking your program.

Part 2 — Frames, -Xss, and StackOverflowError

  EVERY THREAD GETS ITS OWN STACK, SIZED ONCE, AT CREATION.
  Each method call pushes a FRAME onto it:

    ┌─────────────────────────────────────┐  high addresses
    │ frame: main()                       │
    │   local variable array [this,args…] │
    │   operand stack (the JVM is a       │
    │     stack machine — iadd pops 2)    │
    │   frame data: return address,       │
    │     constant-pool ref, exception    │
    │     table pointer                   │
    ├─────────────────────────────────────┤
    │ frame: service()                    │
    ├─────────────────────────────────────┤
    │ frame: repository()   ◀── current   │
    └─────────────────────────────────────┘  grows downward
                        ▼ push a frame here and you hit the guard page

  Frame size is fixed AT COMPILE TIME: javac records max_locals and
  max_stack in the method's Code attribute. A method with three ints
  and a small expression needs maybe 40-60 bytes; one with twenty
  locals, longs and a deep expression tree can need several hundred.
  That is why "how deep can I recurse" has no single answer.

  DEFAULT STACK SIZE (HotSpot, 64-bit): 1 MB on Linux/Windows,
  512 KB on some 32-bit builds. Change it with -Xss:

    java -Xss512k  MyApp        # smaller: more threads fit
    java -Xss4m    MyApp        # larger: deeper recursion survives

  MEASURED DEPTHS on a 1 MB stack, same machine, same JDK:

    trivial recursion, one int arg  ......  ~ 20,000 - 60,000 frames
    method with ~10 locals          ......  ~  8,000 - 15,000 frames
    a Jackson/JAXB parse chain      ......  ~  1,500 -  4,000 frames
    an interpreted frame (pre-JIT)  ......  roughly 2x the cost of a
                                            compiled one

  The spread is enormous, so NEVER design around a depth number. The
  numbers move with -Xss, with the JDK version, with whether the method
  is interpreted or C2-compiled (inlining collapses several logical
  frames into one physical frame), and with the OS guard page size.

  -Xss IS PER-THREAD AND OFF-HEAP. THIS BITES AT SCALE:

    2,000 platform threads x 1 MB = 2 GB of stack RESERVED,
    entirely outside -Xmx.

  It is reserved address space, committed lazily page by page, so RSS
  is usually far lower than the reservation — but in a container with a
  hard memory limit the committed pages are real and the OOM killer
  does not care that your heap looked fine. This is one of the loudest
  arguments for virtual threads, whose stacks are heap-allocated,
  growable chunks measured in hundreds of bytes.

  Note that -Xss does NOT resize the main thread's stack on most
  platforms — the launcher/OS sets that one. If you need a deep stack
  reliably, run the work on a thread you construct yourself:

    new Thread(null, task, "deep", 16L * 1024 * 1024).start();

  WHAT StackOverflowError ACTUALLY MEANS: you pushed a frame past the
  guard page. The four ways to get there:

  1. UNBOUNDED RECURSION — no base case, or a base case that cannot be
     reached:

       int fact(int n) { return n * fact(n - 1); }   // ❌ n = 0 never
                                                     //    terminates it
       int fact(int n) { return n <= 1 ? 1 : n * fact(n - 1); }  // ✔

  2. MUTUAL RECURSION YOU DID NOT NOTICE — the classic is accidental
     self-delegation:

       @Override public String toString() {
           return "Order" + this;        // ❌ string concat calls
       }                                 //    toString() → forever

       @Override public boolean equals(Object o) {
           return this.equals(o);        // ❌ same shape
       }

  3. CYCLES IN DATA, NOT IN CODE — a recursive walk over a graph that
     contains a cycle. The code is correct; the data is not. Fix with a
     visited set (IdentityHashMap or Collections.newSetFromMap), not
     with a bigger stack.

  4. LEGITIMATELY DEEP DATA — a 200,000-element linked list, a deeply
     nested JSON document, a left-leaning parse tree. Here recursion is
     the wrong TOOL, because Java has NO TAIL-CALL ELIMINATION. Even a
     perfectly tail-recursive method allocates a frame per call.

  THE FIX IS ALMOST NEVER A BIGGER -Xss. Convert to iteration with an
  explicit stack — you move the frames from the 1 MB stack to the
  multi-GB heap:

    // recursive: SOE on a deep tree
    void walk(Node n) {
        if (n == null) return;
        visit(n); walk(n.left); walk(n.right);
    }

    // iterative: bounded only by the heap
    void walk(Node root) {
        Deque<Node> todo = new ArrayDeque<>();
        if (root != null) todo.push(root);
        while (!todo.isEmpty()) {
            Node n = todo.pop();
            visit(n);
            if (n.right != null) todo.push(n.right);
            if (n.left  != null) todo.push(n.left);
        }
    }

  CATCHING StackOverflowError IS ALMOST ALWAYS WRONG. It is an Error,
  and you have no idea which frame died — an object may be half
  initialised, a lock half acquired, an invariant half restored. The
  one defensible use is a top-level handler in a server that abandons
  the whole request and unwinds to a known-clean state, and even then
  you should be fixing the recursion.

  READING THE TRACE: a SOE stack trace is truncated (1024 frames by
  default; -XX:MaxJavaStackTraceDepth=0 shows all). Look for the
  REPEATING CYCLE, not the top frame. A cycle of two or three method
  names repeated over and over names your bug immediately.

Part 3 — Object Layout: Why Nothing Costs 16 Bytes

  A HOTSPOT OBJECT ON A 64-BIT JVM, HEAP UNDER 32 GB:

    offset  size  contents
    ──────  ────  ─────────────────────────────────────────────
       0      8   MARK WORD — identity hash code, GC age bits,
                  biased/lightweight lock state, or (during a
                  copying GC) a FORWARDING POINTER to the moved copy
       8      4   KLASS POINTER — which class this is
                  (compressed; 8 bytes without compressed class ptrs)
      12      ?   INSTANCE FIELDS, reordered by the JVM
       ?      ?   PADDING to a multiple of 8
    ──────────────────────────────────────────────────────────

  SO: header = 12 bytes. Alignment = 8 bytes.

    new Object()  → 12 header + 0 fields = 12 → PADDED TO 16.

  That is the answer to "why is an empty object 16 bytes". You are
  paying for a lock word you may never use, a type pointer, and 4 bytes
  of nothing.

  THE PADDING MAKES FIELD COSTS WILDLY NON-LINEAR:

    class A {}                    12 → 16   (4 bytes wasted)
    class B { int x; }            16 → 16   (the first int is FREE)
    class C { int x, y; }         20 → 24   (the second int costs 8)
    class D { int x,y,z; }        24 → 24   (the third is free again)
    class E { long a; int b; }    24 → 24
    class F { long a; int b,c; }  28 → 32

  "Adding one int made this 4 bytes bigger" is wrong half the time.
  Measure; do not compute in your head.

  FIELD REORDERING: the JVM does NOT lay fields out in source order.
  It sorts by width (longs/doubles, then ints/floats, then
  shorts/chars, then bytes/booleans, then references) to close gaps,
  and superclass fields always precede subclass fields. So you cannot
  reduce an object's size by rearranging your source — the JVM has
  already done it. You CAN reduce it by removing fields, narrowing
  types, or replacing a boxed field with a primitive.

  ARRAYS CARRY AN EXTRA LENGTH WORD:

    header 12 + length 4 = 16, then the elements.

    new int[0]     16 + 0     = 16
    new byte[1]    16 + 1     = 17 → 24    (7 bytes of padding!)
    new int[10]    16 + 40    = 56
    new long[10]   16 + 80    = 96

  A million tiny byte[1] objects cost 24 MB to hold 1 MB of data.
  Small arrays are almost pure overhead — this is why an object pool of
  little arrays usually loses to one big array plus offsets.

  DO NOT GUESS. MEASURE WITH JOL (Java Object Layout):

    System.out.println(
        ClassLayout.parseInstance(new C()).toPrintable());
    // prints every offset, every gap, the total, and the padding.

    GraphLayout.parseInstance(myMap).totalSize();   // deep size

  JOL is the only honest answer, because the layout depends on the JDK
  version, the flags, and the heap size.

  JDK 24/25 — COMPACT OBJECT HEADERS (-XX:+UseCompactObjectHeaders)
  fold the mark word and klass pointer into a single 8-byte header,
  so the header drops 12 → 8. Objects that were sitting just over an
  alignment boundary shrink by 8 bytes; objects that were not, do not
  change at all. Reported heap savings on object-heavy workloads run
  around 10-20%, but the distribution is entirely workload-specific.
  Re-run JOL rather than predicting it.

  ─────────────────── COMPRESSED OOPS AND THE 32 GB CLIFF ────────────

  A 64-bit pointer is 8 bytes. References dominate a typical Java heap,
  so HotSpot stores them as 32-BIT values whenever it can:

    every object is 8-byte aligned, so the low 3 bits of any object
    address are always zero → store address >> 3 in 32 bits
    → 2^32 slots x 8 bytes = 34,359,738,368 bytes = 32 GB reachable.

    decode: real_address = heap_base + (compressed << 3)
    (and with a "zero-based" heap the base add disappears entirely —
     one shift, effectively free)

  Compressed oops are ON by default whenever -Xmx allows. Cross the
  limit and the JVM SILENTLY turns them off. Then:

    every reference field   4 → 8 bytes
    every array element     4 → 8 bytes
    every klass pointer     4 → 8 bytes

  THE CLIFF, WITH ARITHMETIC:

    -Xmx31g   compressed oops ON,  ~31 GB of usable object space
    -Xmx33g   compressed oops OFF, references now double

    A reference-dense heap (linked structures, maps, object graphs) is
    commonly 30-50% pointers. Doubling those costs roughly 15-25% of
    the heap, so 33 GB with fat pointers holds LESS LIVE DATA than
    31 GB with thin ones. Raising -Xmx made you smaller.

    You need roughly 40-48 GB before you are reliably ahead of 31 GB.

  VERIFY, DO NOT ASSUME:

    java -Xlog:gc+heap+coops=info -Xmx31g -version
    → "Compressed Oops mode: Zero based, Oop shift amount: 3"

    java -XX:+PrintFlagsFinal -version | grep UseCompressedOops

  PRACTICAL RULES:
    • Stay at or below -Xmx31g. It is the single highest-value heap
      decision on a big machine and it costs nothing.
    • Need more than 31 GB? Run SEVERAL JVMs of 31 GB, or move the
      bulk data off-heap, before you jump to a 64 GB heap.
    • -XX:ObjectAlignmentInBytes=16 raises the ceiling to 64 GB by
      shifting 4 instead of 3 — but every object is then padded to 16
      bytes, which typically wastes more than the pointers saved.
      Measure before believing it.
    • Compressed CLASS pointers are a separate flag
      (-XX:+UseCompressedClassPointers) with its own
      -XX:CompressedClassSpaceSize region in metaspace.

Part 4 — What Boxing Actually Costs

  int    → 4 bytes, stored INLINE, no indirection, no header.
  Integer→ a 16-byte heap object, PLUS the 4-byte reference that points
           at it. 20 bytes to hold 4 bits of information's worth of int.

  THE ARITHMETIC ON A MILLION VALUES:

    int[1_000_000]                 4,000,016 B   ~   4 MB
    Integer[1_000_000] (distinct)  4 MB refs
                                 + 16 MB objects  ~  20 MB       5x
    List<Integer> of 1,000,000     + ArrayList overhead and up to
                                   50% spare capacity ~ 20-26 MB
    HashMap<Integer,Integer>       ~ 69 B/entry     ~  69 MB     17x
      = 32 (Node) + ~5.3 (table slot at 0.75 load)
      + 16 (key) + 16 (value)

  THE MEMORY IS THE SMALL HALF OF THE COST. THE LAYOUT IS THE BIG HALF:

    int[] sum:      values are CONTIGUOUS. The prefetcher streams them;
                    16 ints per 64-byte cache line; the loop vectorises.
                    Runs at memory bandwidth.
    Integer[] sum:  each element is a POINTER. Follow it → a dependent
                    load → likely an L2/L3 or DRAM miss (~80-100 ns
                    each) → then unbox. No vectorisation. Objects are
                    scattered in allocation order, so locality depends
                    on how the list was BUILT.

  Typical measured gap on a summation loop: 3-10x, and it widens as the
  array outgrows cache. This is why IntStream exists and why
  Stream<Integer> is not the same thing at all:

    IntStream.range(0, n).sum()           // primitives throughout
    list.stream().mapToInt(Integer::intValue).sum()   // unbox once
    list.stream().reduce(0, Integer::sum) // ❌ boxes on every step

  ─────────────────── THE Integer CACHE AND THE == TRAP ──────────────

  Autoboxing does NOT call new. It calls Integer.valueOf, which is
  required by the JLS to return a CACHED instance for -128..127:

    Integer a = 127, b = 127;   a == b   → TRUE   (same cached object)
    Integer c = 128, d = 128;   c == d   → FALSE  (two new objects)

  This is the most dangerous behaviour in the language, because the
  failure is INVISIBLE IN TESTS. Your unit test uses id = 1. Production
  uses id = 90210. The == comparison silently starts returning false
  and orders stop matching users.

    if (order.getUserId() == user.getId())   // ❌ Integer == Integer
    if (Objects.equals(order.getUserId(), user.getId()))  // ✔ and
                                                          //   null-safe

  WHAT IS AND IS NOT CACHED:

    Boolean    both values, always              (Boolean.valueOf)
    Byte       all 256 values, always
    Short      -128..127
    Integer    -128..127, upper bound RAISABLE with
               -XX:AutoBoxCacheMax=n  (the LOWER bound never moves)
    Character  0..127
    Long       -128..127
    Float      NOTHING
    Double     NOTHING  →  Double x = 1.0, y = 1.0;  x == y is
                           ALWAYS false. No lucky small-value pass.

  Note the cruelty of AutoBoxCacheMax: raising it makes MORE code
  accidentally work, which makes the bug harder to find, not easier.
  Never rely on it.

  UNBOXING THROWS NullPointerException, AND THE LINE NUMBER LIES:

    Map<String,Integer> counts = new HashMap<>();
    int n = counts.get("missing");   // ❌ NPE — the implicit
                                     //    .intValue() on null

  Worse, in a conditional expression:

    Integer maybeNull = null;
    Integer r = flag ? 1 : maybeNull;   // ❌ NPE even when flag is
                                        //    TRUE and the null branch
                                        //    is never taken

  Because the two arms are int and Integer, binary numeric promotion
  unboxes BOTH arms' type — the expression type becomes int, and the
  result is re-boxed. The NPE happens on the branch you thought was
  dead. Fix by making both arms the same reference type:

    Integer r = flag ? Integer.valueOf(1) : maybeNull;   // ✔

  THE OVERLOAD TRAP:

    List<Integer> list = new ArrayList<>(List.of(10, 20, 30));
    list.remove(1);                     // removes INDEX 1 → 20 goes
    list.remove(Integer.valueOf(1));    // removes the VALUE 1
                                        // → nothing here

  remove(int) and remove(Object) are different methods, and Java
  prefers the non-boxing overload. Same shape bites in any API that
  overloads on int and Object.

  WHEN TO CARE, HONESTLY: below a few thousand elements, boxing is
  noise — write the clear code. Above a million, or in a per-request
  hot path, it dominates. Then use int[]/long[], IntStream, or a
  primitive collection library (Eclipse Collections, fastutil, HPPC),
  which typically cut a Map<Integer,Integer> from ~69 B/entry to
  ~9-16 B/entry with open addressing and no per-entry object at all.

Part 5 — Growth: ArrayList 1.5× vs HashMap 2×

  BOTH ARE ARRAYS UNDERNEATH, AND AN ARRAY CANNOT GROW. "Growing" means
  ALLOCATE A BIGGER ONE, COPY, ABANDON THE OLD ONE. They differ in the
  growth factor, and the difference is not arbitrary.

  ArrayList — 1.5x, AND THE FIRST add IS LAZY:

    // java.util.ArrayList
    int newCapacity = oldCapacity + (oldCapacity >> 1);   // 1.5x

    new ArrayList<>()  allocates NO array. The first add() creates
    Object[10]. Then: 10 → 15 → 22 → 33 → 49 → 73 → 109 → …

    Growing to 1,000,000 from the default: ~30 reallocations.
    Total elements copied ≈ 3n (a 1.5x geometric series sums to
    n/(1-1/1.5) = 3n) → ~3,000,000 slot copies and ~12 MB of dead
    Object[] arrays produced to end up holding a 4 MB array.
    Peak transient footprint at the last resize: old + new = 2.5x.

    new ArrayList<>(1_000_000)  → ONE allocation, zero copies,
    zero garbage. This is the highest-value one-word change in most
    data-loading code.

  Why 1.5 and not 2? Amortised O(1) needs only a CONSTANT factor above
  1. A 1.5 factor wastes at most 50% instead of at most 100%, and —
  the subtler reason — a sequence of 1.5x blocks can reuse previously
  freed blocks, because 1+1.5 > 2.25 eventually fits; with doubling,
  the new block is always larger than the sum of all freed ones.

  HashMap — 2x, AND THE POWER OF TWO IS LOAD-BEARING:

    capacity is ALWAYS a power of two, so bucket = hash & (cap-1),
    a single AND instead of a modulo (~20-40x cheaper).
    Doubling preserves that property; 1.5x would not.

    default capacity 16, load factor 0.75
    threshold = capacity * loadFactor
    resize when size > threshold:

      cap  16 → resize at 12 entries
      cap  32 → resize at 24
      cap  64 → resize at 48
      cap 128 → resize at 96 …

  ⚠ THE CONSTRUCTOR ARGUMENT IS NOT AN ENTRY COUNT. IT IS A TABLE SIZE.

    new HashMap<>(100)      → table 128, resizes at 96 entries.
                              Put 100 entries and YOU STILL RESIZE.
    new HashMap<>((int)(100/0.75f)+1)  → table 256, no resize.  ✔
    HashMap.newHashMap(100)  → JDK 19+, does that arithmetic for you.
                              Also newLinkedHashMap, newHashSet.

  Nearly every "I pre-sized it" in the wild is wrong by exactly this
  factor. It is a silent, purely-performance bug.

  WHAT A RESIZE COSTS: a new Node[2n] plus a walk of EVERY entry.
  Java 8+ avoids recomputing hashes — an entry in bucket i moves to
  either i or i+oldCap, decided by one bit (hash & oldCap), so each
  bin splits into a "lo" and a "hi" list. Cheaper than a full rehash,
  still O(n), still touches every node, still a latency spike. On a
  10M-entry map a resize is tens to hundreds of milliseconds AND
  allocates an 80 MB table while the old one is still live.

  WHY 0.75 SPECIFICALLY: it is a collision/space trade. The javadoc
  notes that under uniform hashing, bucket occupancy follows a Poisson
  distribution; at 0.75 the probability of a bucket reaching 8 entries
  is about 6 in 100,000,000. Drop to 0.5 and you spend 50% more table
  memory for a barely measurable lookup gain; raise to 1.0 and chains
  lengthen fast. Leave it alone unless you have measured.

  TREEIFICATION: a bin with 8+ nodes turns into a red-black tree, but
  ONLY once the table has 64+ slots (below that it resizes instead).
  It untreeifies at 6. This caps a pathological bucket at O(log n)
  instead of O(n) — a hash-collision DoS defence, not a normal path.
  If you are seeing treeified bins, your hashCode is bad.

  ⚠ NEITHER STRUCTURE EVER SHRINKS.

    A HashMap that peaked at 10,000,000 entries and now holds 3 still

Part 6 — Four Reference Strengths, Four Different Jobs

  REACHABILITY IS A LADDER. The collector walks from the GC roots and
  labels every object with the STRONGEST reference chain that reaches
  it:

    strongly reachable  → never collected
    softly  reachable   → collected only when the heap is under
                          pressure (before an OOME)
    weakly  reachable   → collected at the NEXT collection cycle
    phantom reachable   → already finalized; you are told AFTER it dies
    unreachable         → collected

  Note the "strongest chain" rule: one strong reference anywhere
  defeats a thousand weak ones. This is the single most common reason a
  weak cache does not work.

  ─── 1. STRONG — the default. Nothing to configure, nothing to know.

  ─── 2. WEAK — CANONICALISING MAPS AND METADATA YOU DO NOT OWN

    WeakReference<Config> ref = new WeakReference<>(config);
    Config c = ref.get();          // may be null — ALWAYS check

  WeakHashMap holds its KEYS weakly. When a key becomes otherwise
  unreachable, the entry disappears on its own. Its real job is
  ATTACHING DATA TO OBJECTS WHOSE LIFETIME YOU DO NOT CONTROL:

    // canonical instances — one Currency object per code, and the
    // table does not keep a code alive on its own
    Map<String,Currency> canonical =
        Collections.synchronizedMap(new WeakHashMap<>());

    // metadata attached to third-party objects
    Map<Connection,Stats> perConn = new WeakHashMap<>();

  TWO TRAPS THAT MAKE WeakHashMap USELESS:

  (a) THE VALUE MUST NOT REFERENCE THE KEY. If it does, the value is
      strongly held by the map, the value strongly holds the key, and
      the entry lives forever. Your weak map is now a leak with extra
      steps. Wrap the value in a WeakReference if you must.

  (b) IT IS NOT A CACHE. Entries vanish only when nobody else holds the
      key. With String keys that came from literals or interning, that
      is never. For caching use Caffeine/Guava with a size or time
      bound; those give you eviction you can reason about.

  ─── 3. SOFT — "MEMORY-SENSITIVE CACHE", AND WHY IT DISAPPOINTS

    SoftReference<byte[]> img = new SoftReference<>(decoded);

  Contract: cleared at the collector's discretion, but GUARANTEED to be
  cleared before an OutOfMemoryError is thrown. HotSpot's policy is
  time-and-space based:

    -XX:SoftRefLRUPolicyMSPerMB=1000   (default)

  A soft referent survives roughly ONE SECOND PER MEGABYTE OF FREE
  HEAP since its last access. On a 16 GB heap with 8 GB free, that is
  ~8,000 seconds — well over two hours. Your "memory-sensitive cache"
  is effectively unbounded until the heap is nearly full.

  WHY THEY FIGHT YOUR GC SETTINGS — this is the part people miss:

    • Soft refs KEEP OBJECTS ALIVE THROUGH YOUNG COLLECTIONS, so cached
      objects get PROMOTED to the old generation. You converted cheap
      young garbage into expensive old-gen occupancy.
    • They are only cleared aggressively during a FULL GC, so the
      behaviour is: heap fills slowly → full GC → the entire cache is
      dropped at once → every request misses → the app re-decodes
      everything → the heap fills again. A sawtooth of full GCs and
      cold caches, which is the exact opposite of what a cache is for.
    • They interact badly with a pause-time goal: G1/ZGC are tuned to
      avoid full GCs, so the very event that clears your soft refs is
      the one you configured the collector to avoid.
    • They make the live set unpredictable, which breaks capacity
      planning and makes GC logs hard to read.

  VERDICT: soft references are a 2004 answer. Use a BOUNDED cache
  (Caffeine with maximumSize or expireAfterWrite). A cache whose size
  you chose is one you can reason about; a cache the GC empties at
  random is not.

  ─── 4. PHANTOM — POST-MORTEM CLEANUP, THE FINALIZER REPLACEMENT

    PhantomReference<Buf> p = new PhantomReference<>(buf, queue);
    p.get()   // ALWAYS returns null, by design

  You cannot resurrect the object — that is the entire point. What you
  get is a NOTIFICATION, on a ReferenceQueue, that the object is gone,
  so you can release something ELSE that it owned (a native handle, a
  file descriptor, an off-heap block).

    ReferenceQueue<Buf> q = new ReferenceQueue<>();

    class Handle extends PhantomReference<Buf> {
        final long nativePtr;                 // ⚠ a plain long — NOT
        Handle(Buf b, long ptr) {             //   a reference to Buf
            super(b, q); this.nativePtr = ptr;
        }
    }
    // reaper thread
    while (true) {
        Handle h = (Handle) q.remove();       // blocks until one dies
        free(h.nativePtr);
        h.clear();
    }

  THE ONE RULE: THE CLEANUP STATE MUST NOT REFERENCE THE OBJECT BEING
  CLEANED. If it does, the object is strongly reachable from your
  reaper, it never becomes phantom reachable, and the cleanup never
  runs. This is why the example holds a long, not a Buf.

  In practice use java.lang.ref.Cleaner (JDK 9+), which is exactly this
  with the thread and queue managed for you:

    private static final Cleaner CLEANER = Cleaner.create();

    class Resource implements AutoCloseable {
        private final Cleaner.Cleanable cleanable;
        Resource(long ptr) {
            // ⚠ the lambda must capture ptr, never `this`
            cleanable = CLEANER.register(this, () -> free(ptr));
        }
        public void close() { cleanable.clean(); }   // idempotent
    }

  ─── WHY FINALIZERS WENT AWAY (deprecated for removal, JEP 421,
      JDK 18, which also shipped --finalization=disabled)

  Object.finalize() was broken in six independent ways:

    1. NO TIMING GUARANTEE. It may run in a second, in an hour, or
       never — the JVM is allowed to exit without running it. Any
       resource-release logic that depends on it is a leak.
    2. ONE UNBOUNDED QUEUE, ONE THREAD. A slow finalizer stalls every
       other finalizer in the VM, and the queue grows without limit
       until OOME.
    3. TWO GC CYCLES MINIMUM. A finalizable object survives the first
       collection (to be queued), so it gets PROMOTED to the old
       generation — your short-lived objects become old-gen garbage.
       Measured allocation cost of a finalizable class: ~400x a plain
       one in Effective Java's benchmark.
    4. RESURRECTION. finalize() can store `this` somewhere and bring a
       dead object back, which every collector has to defend against.
    5. SWALLOWED EXCEPTIONS. A throw inside finalize() aborts
       finalization for that object and is not reported anywhere.
    6. THE FINALIZER ATTACK. A subclass with a finalizer, constructed
       from a partially-failed super() call, gets a reference to a
       half-built object that bypassed its invariant checks.

  THE REPLACEMENT IS NOT PHANTOM REFERENCES. It is try-with-resources:

    try (var in = Files.newInputStream(path)) { … }   // deterministic

  Cleaner/phantom refs are the SAFETY NET for the case where a caller
  forgot to close — and specifically for NATIVE memory, which no
  try-block can free after the object is gone.

Part 7 — Leaks, Heap Dumps, and the Memory Outside the Heap

  A "MEMORY LEAK" IN JAVA IS NOT A MISSING free(). It is an
  UNINTENTIONAL STRONG REFERENCE. The collector is working perfectly —
  it is refusing to free objects that YOUR CODE can still reach. Every
  leak investigation reduces to one question:

    WHAT PATH FROM A GC ROOT KEEPS THIS ALIVE?

  THE SIX SHAPES, IN ROUGH ORDER OF HOW OFTEN THEY ARE THE ANSWER:

  1. STATIC COLLECTIONS. A static field is a GC root, so anything it
     reaches lives for the process lifetime.

       static final Map<String,Session> SESSIONS = new HashMap<>();
       SESSIONS.put(id, session);      // ❌ removed... when?

     Symptom: heap grows linearly with uptime, never recovers after a
     full GC. Fix: a bounded cache with eviction, and an explicit
     removal path that runs on the failure branches too.

  2. UNCLOSED RESOURCES. A stream, connection, or channel holds native
     handles AND a chain of Java buffers. Leaking connections also
     exhausts a pool, so the symptom is often "hangs" before it is
     "OOME". Fix: try-with-resources, always — and remember that a
     Stream over a file (Files.lines) is itself closeable.

  3. LISTENERS REGISTERED AND NEVER REMOVED.

       bus.subscribe(this::onEvent);   // and no unsubscribe

     The bus is long-lived; the method reference holds `this`; `this`
     holds a whole page/service/graph. Every navigation adds another.
     Fix: pair every add with a remove in a finally/dispose, or make
     the registry hold weak references and document it.

  4. ThreadLocal IN A POOLED THREAD. This is the subtle one.

       static final ThreadLocal<Context> CTX = new ThreadLocal<>();
       CTX.set(new Context(hugeRequest));   // never removed

     The pool thread lives for the app's lifetime, and the value is
     attached to the THREAD, not the task. ThreadLocalMap holds the
     ThreadLocal KEY weakly but the VALUE STRONGLY, and stale entries
     are only swept opportunistically on a later get/set/remove that
     happens to probe that slot. So the value can survive indefinitely.

       try { CTX.set(ctx); handle(req); }
       finally { CTX.remove(); }            // ✔ non-negotiable

     In a container this is also a classloader leak: the Context class
     was loaded by the webapp loader, and a container thread now pins
     it. (Virtual threads sidestep this — each task gets a fresh
     thread — but ThreadLocal.remove() is still the correct habit.)

  5. INNER-CLASS this$0. A non-static inner class, an anonymous class,
     or a lambda that touches an instance member holds a hidden
     reference to the ENCLOSING instance:

       class ReportPage {                   // holds 40 MB of rows
           byte[] data = new byte[40_000_000];
           void schedule() {
               scheduler.schedule(new Runnable() {     // ❌ inner
                   public void run() { ping(); }       //    → this$0
               }, 1, HOURS);
           }
       }

     One tiny Runnable pins 40 MB for an hour. Fixes: a static nested
     class taking exactly the fields it needs; or a lambda that
     captures only locals (a lambda capturing NO instance state does
     NOT capture `this`, and HotSpot may even reuse a single instance
     of it).

  6. CLASSLOADER LEAKS ON REDEPLOY. Symptom:
     OutOfMemoryError: Metaspace after the third or fourth redeploy,
     while the heap is fine. One reference from a JDK or container
     class into a webapp class pins the webapp's ClassLoader, and a
     ClassLoader pins EVERY class it loaded and every static field in
     them. Usual culprits:

       • a JDBC driver registered in java.sql.DriverManager
       • a ThreadLocal whose VALUE type is a webapp class
       • a running Timer/ExecutorService thread the app never stopped
       • a log appender or JMX MBean still registered
       • a shutdown hook holding an app object
       • java.beans.Introspector / caches keyed by app Class objects

     Diagnosis: heap dump, then "path to GC roots" from the webapp
     ClassLoader instance. Cure the one path; there is usually exactly
     one.

  ALSO REAL, AND OFTEN MISDIAGNOSED:
     • A mutable object used as a HashMap key, then mutated. Its hash
       changed, so nothing can find it — but the map still holds it.
     • hashCode/equals inconsistency → duplicate keys accumulate.
     • Collections that never shrink (Part 5). Not a leak; looks
       exactly like one in a dump.

  ─────────────────── READING A HEAP DUMP ────────────────────────────

  GET ONE:
    -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps
        (free, and the only way to catch the state at the failure)
    jcmd <pid> GC.heap_dump /tmp/app.hprof     (on demand)
    jcmd <pid> GC.class_histogram              (cheap first look)

  ⚠ A dump is roughly the size of the LIVE HEAP and it STOPS THE WORLD
  for seconds to a minute. On a 30 GB heap plan for a real outage and
  enough disk. Take it from a canary instance if you can.

  THE ONE DISTINCTION THAT MAKES A DUMP READABLE:

    SHALLOW SIZE — the bytes of the object ITSELF: header + fields.
                   References count as 4 or 8 bytes, not as what they
                   point to. A HashMap holding 10,000,000 entries has
                   a shallow size of 48 BYTES.

    RETAINED SIZE — the bytes that would be FREED if this object were
                   collected: itself plus everything reachable ONLY
                   through it. The same HashMap: 700 MB.

  Shallow size answers almost nothing. Retained size answers "what is
  eating my heap". If you sort a dump by shallow size you get a list of
  byte[] and String — always, in every application, and it never
  identifies anything.

  THE DOMINATOR TREE IS WHERE THE ANSWER IS:

    X DOMINATES Y  ⟺  EVERY path from a GC root to Y passes through X.

    GC root ──▶ CacheHolder ──▶ HashMap ──▶ Node ──▶ Session ──▶ byte[]
                     │
                     └── dominates all of it, so its retained size
                         is the whole subtree

  MAT builds the dominator tree from the object graph and sorts by
  retained size. The top few rows ARE your leak, at the granularity
  that matters. An object shared by two independent paths is NOT
  dominated by either — it floats up to their common dominator, which
  is precisely the behaviour you want: shared caches show up at the
  place that actually owns them.

  THE TWO-QUESTION WORKFLOW:

    "WHAT is big?"        → Dominator tree, sorted by retained size.
                            Group by class to see 3,000,000 Session
                            objects instead of 3,000,000 rows.
    "WHY is it alive?"    → Right-click → Path to GC Roots →
                            EXCLUDE ALL PHANTOM/WEAK/SOFT REFERENCES.
                            That exclusion is essential: weak paths
                            cannot keep anything alive, and leaving
                            them in buries the one strong path that
                            can.

  You need BOTH. The dominator tree without the path tells you a
  HashMap is huge but not who owns it; the path without the tree tells
  you about an object too small to matter.

  OTHER MAT VIEWS THAT EARN THEIR KEEP:
    Leak Suspects report   — a decent first guess; verify it, do not
                             trust it
    Histogram + "retained  — how much do ALL instances of this class
      set"                   cost together
    Duplicate strings      — commonly 10-30% of a large heap; often
                             fixed by -XX:+UseStringDeduplication or
                             by interning at the parse boundary
    OQL                    — SELECT * FROM java.lang.String s WHERE
                             s.value.@length > 100000
    Compare two snapshots  — the single best leak technique: dump,
                             run the workload, dump again, diff the
                             histograms. Growth between two steady
                             states is the leak.

  ─────────────────── OFF-HEAP: DirectByteBuffer ─────────────────────

    ByteBuffer heap   = ByteBuffer.allocate(8192);       // byte[] on
                                                          // the heap
    ByteBuffer direct = ByteBuffer.allocateDirect(8192); // malloc'd,
                                                          // OUTSIDE -Xmx

  WHY DIRECT BUFFERS EXIST: the OS needs a stable address to DMA into.
  A heap byte[] can be MOVED by the collector at any moment, so every
  read/write through a heap buffer is copied into a temporary direct
  buffer first. (HotSpot caches those temporaries PER THREAD and they
  are not free — a few hundred threads doing large I/O with heap
  buffers is itself a native-memory surprise.) A direct buffer is
  handed to the kernel as-is: zero copy.

  THE COSTS, MEASURED:
    allocateDirect  ~ 10-100 µs   (malloc + mandatory zeroing)
    allocate        ~ 0.1-1 µs    (a TLAB pointer bump)
    → 10-100x. NEVER allocate a direct buffer per request. Allocate a
      pool at startup and reuse it. Direct buffers pay off for
      long-lived, large, frequently-reused I/O buffers, and lose badly
      for small short-lived ones.

  THE LIFECYCLE IS THE DANGEROUS PART:

    The DirectByteBuffer OBJECT is ~64 bytes on the heap. The MEMORY is
    megabytes off-heap. The native block is freed only when that tiny
    Java object is collected and its Cleaner runs.

    → GC pressure is driven by the 64 bytes, not the megabytes.
    → The heap looks healthy, young collections are rare, so the
      buffer objects are never collected, so RSS climbs and climbs.
    → You get killed by the container (exit 137) with NO Java OOME and
      NO heap dump, while your GC logs look perfect.

  -XX:MaxDirectMemorySize=<n> IS THE GUARD RAIL. If unset, the limit
  defaults to the maximum heap size — so a -Xmx4g service silently
  permits ANOTHER 4 GB of direct memory, and a 5 GB container dies. Set
  it explicitly, always, and size the container as:

    -Xmx  +  MaxDirectMemorySize  +  metaspace  +  code cache
          +  (threads x -Xss)  +  GC structures  +  native libs
          +  headroom

  When the direct limit is reached, Bits.reserveMemory calls
  System.gc() and retries — so a service that runs with
  -XX:+DisableExplicitGC can throw
  "OutOfMemoryError: Direct buffer memory" while memory is in fact
  reclaimable. That is one of the very few situations where an
  explicit GC is load-bearing.

  DIAGNOSING NATIVE MEMORY:
    -XX:NativeMemoryTracking=summary
    jcmd <pid> VM.native_memory summary
        → per-category committed bytes: heap, class, thread, code, GC,
          compiler, internal, other
    BufferPool MBean (java.nio:type=BufferPool,name=direct)
        → Count, MemoryUsed, TotalCapacity — graph this
    MALLOC_ARENA_MAX=2
        → glibc creates up to 8 arenas per core; on a 32-core box that
          alone can inflate RSS by hundreds of MB
    pmap -x <pid> / RSS minus heap = the gap you must explain

  ALSO OFF-HEAP AND ALSO NOT IN -Xmx: metaspace, the code cache,
  thread stacks, GC bookkeeping (G1 remembered sets can be several
  percent of heap), compiler arenas, and any JNI library.

  THE MODERN ANSWER — JDK 22+ FOREIGN FUNCTION & MEMORY API gives
  off-heap memory a DETERMINISTIC lifetime, which is what
  DirectByteBuffer never had:

    try (Arena arena = Arena.ofConfined()) {
        MemorySegment seg = arena.allocate(1_000_000);
        // … use it …
    }   // freed HERE, at close. No Cleaner, no GC, no guessing.

  It also fixes DirectByteBuffer's other limitation — a 2 GB cap from
  int indexing — and it is bounds-checked, unlike Unsafe.

Interview Questions

Beginner: What is the difference between the stack and the heap in Java?

The stack is per-thread and holds one frame per active method call. A frame holds the method's local variables, its operand stack and its bookkeeping. Frames are pushed on call and popped on return, so allocation and deallocation are a single pointer adjustment — no collector is involved, and nothing on a stack can be shared between threads.

The heap is shared by all threads and holds every object and array. Objects outlive the method that created them, so their lifetime cannot be known at compile time — which is exactly why a garbage collector exists.

The sentence that resolves most confusion: the variable is on the stack, the object is on the heap. In Point p = new Point(), p is a 4-byte reference in the frame and the Point is on the heap. When the method returns, p disappears instantly; the Point merely becomes unreachable and is freed later.

The common half-truth is "primitives go on the stack". That holds for local primitives only. A primitive field lives inside its object, on the heap. The right question is "local or field?", not "primitive or reference?".

One refinement worth mentioning: the JIT's escape analysis can prove an object never leaves a method and then scalar-replace it — no heap allocation at all. Neither region is defined by the language specification; they are HotSpot implementation details, which is precisely what makes that optimisation legal.

Beginner: Why does Integer a = 128, b = 128; a == b return false when the same code with 127 returns true?

Autoboxing does not call new. It calls Integer.valueOf, and the JLS requires that method to return a cached instance for values −128 to 127. Two boxes of 127 are therefore the same object and == is true. Two boxes of 128 are two distinct objects, so == compares two different addresses and is false.

What makes this the most dangerous behaviour in the language is that it is invisible in tests. Fixtures use id 1, id 2, id 3 — all cached, all passing. Production uses id 90210 and the comparison silently starts returning false. There is no exception and no log line; orders just stop matching users.

The fix is to never use == on boxed types. Objects.equals(a, b) is correct and null-safe. If you genuinely have primitives, use primitives — int == int is fine, and mixing Integer == int is also fine because the boxed side unboxes and the comparison becomes numeric.

Know the boundaries of the caches for follow-up questions: Boolean always, Byte all values, Short/Integer/Long −128..127, Character 0..127, and Float and Double cache nothing — so Double x = 1.0, y = 1.0; x == y is false at every value, with no lucky small-number pass to hide it.

-XX:AutoBoxCacheMax=n can raise the Integer upper bound. That makes broken code accidentally work over a wider range, which makes the bug harder to find — never rely on it.

Mid: Explain the four reference strengths and give a real use for each.

The collector labels each object by the strongest reference chain that reaches it from a GC root. One strong reference anywhere defeats any number of weak ones — that rule alone explains most "my weak cache isn't working" reports.

StrengthClearedReal use
StrongNever while reachableEverything, by default
SoftUnder heap pressure, guaranteed before OOMELegacy memory-sensitive caches — mostly a mistake today
WeakNext GC once no strong/soft ref remainsWeakHashMap for canonicalisation and for metadata attached to objects you do not own
PhantomEnqueued after collection; get() is always nullReleasing native memory after the Java object is gone

Weak is for association, not caching. WeakHashMap holds keys weakly, so an entry disappears when the key becomes otherwise unreachable — perfect for "one canonical instance per code" tables or for hanging statistics off a third-party Connection. Two traps: the value must not reference the key (or the entry is immortal), and it is not a cache, because entries vanish the instant nobody else holds the key.

Soft looks ideal for caching and is not. HotSpot keeps a softly reachable object for roughly SoftRefLRUPolicyMSPerMB (default 1000 ms) per megabyte of free heap, so on a large heap nothing is cleared for hours; then a full GC drops the entire cache at once. In the meantime the cached objects survive young collections and get promoted to the old generation. Use a bounded cache instead.

Phantom exists to tell you an object is definitely gone. get() returns null by design so you cannot resurrect it. Paired with a ReferenceQueue, it lets you free a native block afterwards. In practice use java.lang.ref.Cleaner, which packages the queue and reaper thread — with the same non-negotiable rule that the cleanup state must not reference the object being cleaned, or it will never become phantom reachable.

Mid: Why is an empty Object 16 bytes, and what is the 32GB heap cliff?

On a 64-bit HotSpot with compressed oops an object header is 12 bytes: an 8-byte mark word (identity hash, GC age, lock state, or a forwarding pointer while a copying collector is moving the object) and a 4-byte klass pointer. Objects are aligned to 8 bytes, so 12 rounds up to 16. You pay for a lock word you may never use, a type pointer, and four bytes of nothing.

The alignment makes field costs non-linear: the first int is free (12 + 4 = 16), the second costs 8 (20 → 24), the third is free again (24). The JVM also reorders fields by width to close gaps, so you cannot shrink an object by rearranging your source. Measure with JOL rather than reasoning about it — and note that -XX:+UseCompactObjectHeaders (JDK 24/25) folds the header to 8 bytes, which shrinks some objects by 8 and others not at all.

Compressed oops: because every object is 8-byte aligned, the low three bits of any address are zero, so HotSpot stores a reference as a 32-bit value shifted right by 3. That addresses 232 × 8 bytes = exactly 32 GB. Below that limit, every reference field, array element and klass pointer is 4 bytes instead of 8.

Cross the limit and the JVM silently disables the optimisation. Every reference doubles. A reference-dense heap is commonly 30–50% pointers, so you lose roughly 15–25% of the heap to pointer width. A 33 GB heap can hold less live data than a 31 GB heap — raising -Xmx made the application smaller. You need roughly 40–48 GB before you are reliably ahead.

The practical rule is to cap at -Xmx31g and verify with -Xlog:gc+heap+coops=info. If you need more memory than that, run several JVMs or move the bulk data off-heap before jumping to a 64 GB heap. -XX:ObjectAlignmentInBytes=16 raises the ceiling to 64 GB but pads every object to 16 bytes, which usually costs more than the pointers it saves.

The premise tells you the answer's shape: the memory is not in the heap, so no amount of heap tuning or heap-dump reading will find it. There is no Java OutOfMemoryError and no automatic heap dump because the JVM never noticed a problem — the kernel killed the process (exit 137).

In my experience the most common single cause is direct byte buffers, and the reason is a lifecycle mismatch. A DirectByteBuffer object is ~64 bytes on the heap while the block it owns is megabytes off-heap. GC pressure is driven by the 64 bytes, so a healthy, low-allocation application never collects them, and the native memory is never released. The heap genuinely does look fine; that is the symptom, not a contradiction. The default MaxDirectMemorySize equalling -Xmx makes it worse: a 4 GB heap silently permits another 4 GB.

My recommendation is to make the whole budget explicit rather than hunting for one culprit each time. Set -XX:MaxDirectMemorySize deliberately, size the container as heap + direct + metaspace + code cache + (threads × -Xss) + GC overhead + ~20% headroom, and prefer -XX:MaxRAMPercentage over a hard-coded -Xmx so the JVM tracks the cgroup limit. Then pool direct buffers instead of allocating them per request, and for new code use the JDK 22+ Arena API, which frees off-heap memory deterministically at close() instead of whenever a collector happens to run.

One caveat that trips people: if the service runs with -XX:+DisableExplicitGC, the JVM's internal System.gc() retry inside Bits.reserveMemory is disabled too, and you can get OutOfMemoryError: Direct buffer memory while the memory is in fact reclaimable. That is one of the very few places where an explicit GC is load-bearing.

Senior: You have a 12GB heap dump from a service that OOMEs after four days. How do you find the leak?

The four-day timescale already tells me it is a slow accumulation, not a burst — so I am looking for something that grows monotonically with uptime or with request count, and the answer will be a strong reference from a long-lived root.

Step 1 — open the dominator tree, sorted by retained size, not the histogram. This is the distinction that decides whether the investigation takes ten minutes or a day. Shallow size is the object's own header and fields; a HashMap holding ten million entries has a shallow size of 48 bytes. Retained size is everything that would be freed if the object went away. Sorting by shallow size gives you byte[] and String at the top — in every application, always, identifying nothing. The dominator tree tells you which object owns those bytes, because X dominates Y when every path from a GC root to Y goes through X.

Step 2 — from the top retained entry, take "path to GC roots, excluding weak/soft/phantom references". The exclusion matters: weak paths cannot keep anything alive, and including them buries the one strong path that can. This answers the second question — the dominator tree says what is big, the path says why it is still alive — and you need both answers.

Step 3 — match the path to a known leak shape. A static Map field, a ThreadLocal value on a pooled thread, a listener list on a long-lived bus, an inner class's this$0 pinning an object graph, an unclosed resource chain, or — if this were a metaspace OOME after redeploys — a classloader pinned by a JDBC driver or a container thread. Nine times in ten the path names the bug directly.

Step 4 — rule out the impostor. Collections never shrink. A HashMap that peaked at ten million entries and now holds three still owns a 16-million-slot table, roughly 67 MB of Node[], forever. That looks exactly like a leak in a dump and is fixed by rebuilding the collection, not by hunting references.

If one dump is ambiguous, the strongest technique is two dumps. Take one at a steady state, run a known workload, take another, and diff the histograms. Growth between two steady states is the leak by definition, and it removes all the judgement from step 3. This is worth the operational cost: a dump is roughly the size of the live heap and stops the world for seconds to a minute, so I take it from a canary instance out of the load balancer, with -XX:+HeapDumpOnOutOfMemoryError already configured as the safety net.

My recommendation for prevention rather than diagnosis: run allocation profiling continuously (JFR's ObjectAllocationSample costs about 1%), alert on live-set size after full GC rather than on heap used, and treat every long-lived registry — caches, listener lists, ThreadLocals — as requiring a documented removal path before it is merged. Those three habits catch nearly everything that would otherwise become a four-day OOME.

1 (easy): What does this print, and why is it a production bug? 
Integer a = 127, b = 127;

System.out.println(a == b);
System.out.println(c == d);
System.out.println(c.equals(d));
Solution

true, false, true.

Autoboxing calls Integer.valueOf, which the JLS requires to return a cached instance for −128..127. So a and b are literally the same object and == is true. 128 is outside the cache, so c and d are two distinct 16-byte objects at different addresses, and == compares those addresses.

The memory is the smaller half of the cost. Summing int[] streams contiguous memory — sixteen values per 64-byte cache line, prefetcher-friendly, vectorisable, running at memory bandwidth. 3 (medium): Both of these pre-size their collections. One of them does not work. Which, and why? 
List<Row> rows = new ArrayList<>(100_000);

The HashMap is wrong. Its constructor argument is an initial table capacity, not an entry count. It rounds 100,000 up to the next power of two — 131,072 — and resizes when size > capacity × 0.75, i.e. at 98,304 entries. You wanted room for 100,000, so you still pay a full resize to 262,144 slots.

// correct, all JDKs
Map<String,Row> index = new HashMap<>((int) (100_000 / 0.75f) + 1);

// correct and readable, JDK 19+
Map<String,Row> index = HashMap.newHashMap(100_000);
// also: LinkedHashMap.newLinkedHashMap, HashSet.newHashSet

What the wrong version actually does at runtime: at entry 98,304 the map allocates a new Node[262144] — about 1 MB — while the old 512 KB table is still live, then walks all 98,304 entries splitting each bin into a "lo" and a "hi" list using one bit of the stored hash. Java 8+ does not recompute hashes, so it is cheaper than a classic rehash, but it is still O(n), still touches every node, and still shows up as a latency spike. On a 10-million-entry map the same event is tens to hundreds of milliseconds and allocates an 80 MB table.

The general principle: pre-sizing is the cheapest performance change in most data-loading code, and it is the one most often written incorrectly. 4 (medium): This handler leaks in a servlet container. Find both leaks. 
public class RequestHandler {
    private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();
    private final byte[] responseBuffer = new byte[10_000_000];

    public void handle(Request req) {
        CTX.set(new UserContext(req.user()));
        scheduler.schedule(new Runnable() {
            public void run() { audit(CTX.get()); }
        }, 1, TimeUnit.HOURS);
        render(req);
    }
}
Solution

Leak 1 — ThreadLocal set and never removed on a pooled thread. The value is attached to the thread, not the request. Container threads live for the application's lifetime, so every thread ends up permanently holding the last UserContext it saw. ThreadLocalMap holds the ThreadLocal key weakly but the value strongly, and stale entries are only swept opportunistically when a later get/set/remove happens to probe that slot — so the value can survive indefinitely. In a container this is also a classloader leak, because UserContext was loaded by the webapp loader and a container thread now pins it.

Leak 2 — the anonymous Runnable's hidden this$0. An anonymous inner class captures its enclosing instance, so the scheduled task holds the RequestHandler, which holds a 10 MB byte[], for a full hour. Under load that is thousands of live handlers and gigabytes of pinned buffers.

public class RequestHandler {
    private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();
    private final byte[] responseBuffer = new byte[10_000_000];

    public void handle(Request req) {
        UserContext ctx = new UserContext(req.user());
        CTX.set(ctx);
        try {
            // capture the VALUE, not `this` and not the ThreadLocal
            scheduler.schedule(() -> audit(ctx), 1, TimeUnit.HOURS);
            render(req);
        } finally {
            CTX.remove();               // ✔ non-negotiable in a pool
        }
    }
}

The subtle part of the fix is that the lambda captures ctx — a local — so it holds a 200-byte context instead of the handler. 5 (hard): A batch job runs on a machine with 64GB of RAM. Someone raises the heap from 31GB to 48GB and it now OOMEs where it used to finish. Explain and fix. 
# before:  java -Xmx31g -jar batch.jar     → completes
# after:   java -Xmx48g -jar batch.jar     → OutOfMemoryError
Solution

Compressed oops turned off. Below 32 GB, HotSpot stores every reference as a 32-bit value: objects are 8-byte aligned, so the low three bits of an address are always zero and the JVM stores address >> 3, addressing 232 × 8 = exactly 32 GB. Above that limit the encoding cannot cover the heap, so the JVM silently disables it and every reference field, every reference array element, and every klass pointer grows from 4 bytes to 8.

Item≤ 32 GB heap> 32 GB heap
Reference field4 bytes8 bytes
Object[] element4 bytes8 bytes
Klass pointer4 bytes8 bytes
HashMap.Node32 bytes48 bytes
Empty Object16 bytes16 bytes (padding absorbs it)

The arithmetic: a reference-dense workload — maps, linked structures, object graphs — is commonly 30–50% pointers by volume, so doubling pointer width costs roughly 15–25% of the heap. If the job needed 30 GB of live data at 31 GB with thin pointers, the same data now needs about 36–38 GB. 48 GB should just cover it, but you have also lost headroom for GC copying reserve and for the allocation burst, and G1 needs space to evacuate into. Hence the OOME — and note that at 33 GB it would have been strictly worse than the original 31 GB configuration.

# verify what you actually got — do not assume

# → "Compressed Oops mode: Non-zero disjoint base" or nothing at all

java -XX:+PrintFlagsFinal -version | grep UseCompressedOops

The fix, in order of preference. First, go back to -Xmx31g and find out why 31 GB was not enough — a batch job that needs more than 31 GB of live data usually has an accumulation it does not need, and streaming the input instead of materialising it is both cheaper and faster. Second, if the data genuinely is that big, run several JVMs of 31 GB and partition the work; two 31 GB heaps hold far more than one 62 GB heap. Third, move the bulk data off-heap — a MemorySegment or a memory-mapped file has no pointers to widen. Only after those, consider a heap around 64 GB, where the extra space finally outweighs the doubled pointers.

-XX:ObjectAlignmentInBytes=16 extends the compressed-oop ceiling to 64 GB by shifting 4 bits instead of 3. It is real, and it is usually a trap: every object is then padded to a 16-byte boundary, so a 16-byte Integer stays 16 but many 24-byte objects become 32. Measure before believing it.

The counter-intuitive headline worth remembering: on the JVM, more heap can mean less memory. It is the only common tuning knob where increasing the number makes the resource smaller.

6 (hard): This class wraps a native buffer. It leaks native memory and the cleanup never runs. Fix it. 
public class NativeBuffer {
    private final long ptr;
    private final int  size;

    public NativeBuffer(int size) {
        this.size = size;
        this.ptr  = Native.malloc(size);
    }

    @Override
    protected void finalize() {
        Native.free(ptr);
    }
}
Solution

There are two separate problems: finalization is the wrong mechanism, and the obvious "modern" rewrite using a Cleaner that captures this would be broken in a way that is harder to see.

Why finalize fails here. It is deprecated for removal (JEP 421, JDK 18, which also shipped --finalization=disabled), and every one of its defects bites this class. There is no timing guarantee, and the JVM may exit without running it at all — so native memory leaks on shutdown. All finalizers share one unbounded queue and one thread, so a slow one stalls every other finalizer in the VM. A finalizable object survives its first collection in order to be enqueued, so it is promoted to the old generation — allocation of a finalizable class is roughly two orders of magnitude more expensive than a plain one. And because the heap sees a small object while the native block is large, GC pressure never reflects the real memory use, so collection may not happen for hours.

public class NativeBuffer implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();

    // ⚠ a STATIC class holding only primitives — it must NOT be able
    //   to reach the NativeBuffer, or NativeBuffer never dies
    private static final class State implements Runnable {
        private final long ptr;
        State(long ptr) { this.ptr = ptr; }
        public void run() { Native.free(ptr); }
    }

    private final State state;
    private final Cleaner.Cleanable cleanable;
    private final int size;

    public NativeBuffer(int size) {
        this.size      = size;
        this.state     = new State(Native.malloc(size));
        this.cleanable = CLEANER.register(this, state);
    }

    @Override public void close() { cleanable.clean(); }  // idempotent
}

// callers get DETERMINISTIC release:
try (NativeBuffer buf = new NativeBuffer(1 << 20)) { … }

The trap in the rewrite: if the registered action were a lambda like () -> Native.free(this.ptr), it would capture this. The Cleaner holds the action strongly, so the NativeBuffer would stay strongly reachable forever, never become phantom reachable, and the cleanup would never run at all — strictly worse than the finalizer. That is why State is a static nested class holding only a long. The same rule applies to hand-rolled phantom references: the cleanup state must never be able to reach the object being cleaned.

The ordering that matters: close() is the real mechanism and the Cleaner is a backstop for callers who forgot. Getting that backwards — treating the Cleaner as the design and close() as optional — reproduces exactly the DirectByteBuffer problem, where native memory release depends on a collection of a tiny Java object that may never be urgent enough to happen.

For new code, prefer the Foreign Function & Memory API: try (Arena arena = Arena.ofConfined()) { MemorySegment seg = arena.allocate(size); … } frees at close() with no cleaner, no queue and no reachability reasoning at all — and it is bounds-checked, unlike Unsafe.

🎯 Key Takeaways

  • The variable is on the stack; the object is always on the heap. A local reference is 4 bytes in the frame pointing at a heap object.
  • "Primitives live on the stack" is only true for locals — a primitive field lives inside its object, on the heap.
  • The stack/heap split is about provable lifetime, not speed, which is why escape analysis can delete an allocation entirely.
  • Thread stacks are native memory outside -Xmx — 2,000 threads at -Xss1m reserve 2 GB the heap budget never sees.
  • A bigger -Xss never fixes a StackOverflowError — fix the recursion, or move the frames to the heap with an explicit Deque.
  • An empty object is 16 bytes: 8-byte mark word + 4-byte klass pointer, padded to an 8-byte boundary.
  • Padding makes field costs non-linear — the first int is free, the second costs 8. Measure with JOL; the JVM already reordered your fields.
  • Compressed oops end at 32GB, and crossing that line can shrink your app — every reference doubles, so 33 GB holds less live data than 31 GB.
  • An Integer costs 20 bytes to store 4 — a 16-byte object plus a 4-byte reference, and a pointer chase on every read.
  • Integer.valueOf caches −128..127, so == passes every test and fails in production. Use Objects.equals. Double caches nothing.
  • new HashMap<>(n) does not hold n entries — it resizes at 0.75n. Use HashMap.newHashMap(n).
  • ArrayList grows 1.5× and HashMap doubles; reaching n unsized costs ≈3n element copies, and neither structure ever shrinks.
  • The strongest reference chain wins — one strong reference defeats any number of weak ones, which is why most weak caches do not work.
  • Soft references fight your GC settings: nothing is cleared until a full GC, cached objects get promoted to old gen meanwhile, and then the whole cache vanishes at once.
  • Finalizers are gone for six independent reasons; the replacement is try-with-resources, with Cleaner as a safety net whose action must never capture the object.
  • Java leaks are unintentional strong references — static collections, unclosed resources, unremoved listeners, ThreadLocal in a pool, inner-class this$0, and classloaders pinned on redeploy.
  • Shallow size answers nothing; retained size answers everything. Read the dominator tree for "what is big" and path-to-GC-roots for "why is it alive".
  • Direct buffers are freed by a GC of a 64-byte object — set -XX:MaxDirectMemorySize explicitly, or use a JDK 22+ Arena for deterministic release.
