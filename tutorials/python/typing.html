Type Hints & Typing Advanced

What you'll master: why annotations are erased at runtime and what that means for trusting them, the modern syntax that replaced typing.List, narrowing and why Optional forces you to handle None, Protocol as the static face of duck typing, generics with TypeVar and ParamSpec, why mutable containers are invariant, Literal, TypedDict and NewType, the difference between static checking and Pydantic validation, and how to add types to a large untyped codebase without stopping feature work. Prerequisites: OOP & Dataclasses and Decorators & Context Managers.

Part 1 — Annotations Do Not Run

def greet(name: str, times: int = 1) -> str:
    return f"Hi {name} " * times

greet(42, "lots")            # RUNS. No error from Python. Fails later,
                             # somewhere else, with a confusing traceback.

greet.__annotations__        # {'name': str, 'times': int, 'return': str}
# The annotations are stored and ignored. Python never checks them.

# ── SO WHAT ARE THEY FOR? ────────────────────────────────────────────────
# 1. STATIC CHECKERS   mypy / pyright, run in CI, find the bug above
#                      without executing anything
# 2. EDITORS           autocomplete, go-to-definition, inline errors
# 3. LIBRARIES that READ them at runtime:
#      pydantic   validates and coerces external data
#      dataclasses generates __init__ from them
#      FastAPI    builds routing, parsing and OpenAPI docs from them
#      attrs, SQLAlchemy 2.0, typer, cattrs
# 4. DOCUMENTATION that cannot drift, because CI checks it

# ── THE PRACTICAL CONSEQUENCE ────────────────────────────────────────────
def process(user_id: int) -> User: ...
process(request.json["user_id"])      # a str from JSON. Type-checks fine
                                      # if the JSON is typed as Any.
# Hints verify YOUR code's internal consistency. They guarantee NOTHING
# about data arriving from outside the program. That boundary needs
# runtime validation — see Part 6.

# ── MODERN SYNTAX (3.9+ / 3.10+) ─────────────────────────────────────────
names: list[str] = []                 # NOT typing.List — that is legacy
scores: dict[str, float] = {}
point: tuple[int, int] = (1, 2)       # exactly two ints
row: tuple[str, ...] = ()             # any number of strs
maybe: User | None = None             # NOT Optional[User] (3.10+)
value: int | str                      # a union

from typing import Optional           # still needed pre-3.10, and still
                                      # seen everywhere in existing code
# Optional[X] means X | None. It does NOT mean "optional argument" — that
# is a default value. A parameter can be required AND accept None:
def f(x: int | None) -> None: ...     # required, may be None
def g(x: int | None = None) -> None: ...   # optional AND may be None

# ── ANNOTATIONS AS STRINGS ───────────────────────────────────────────────
from __future__ import annotations    # all annotations become strings,
                                      # evaluated only by the checker
class Node:
    def child(self) -> Node: ...      # works without quotes; without the
                                      # future import you need "Node"
# This also solves most circular imports caused by type-only dependencies
# (see Modules, Packaging & Environments).

Part 2 — Narrowing

def find_user(uid: int) -> User | None: ...

user = find_user(1)
print(user.name)             # ✗ error: "None" has no attribute "name"
# The checker is right — find_user CAN return None and you did not handle
# it. This one rule catches a large share of real AttributeError crashes.

if user is not None:
    print(user.name)         # ✓ narrowed to User inside the branch

if user is None:
    return
print(user.name)             # ✓ narrowed after an early return

# ── WHAT NARROWS ─────────────────────────────────────────────────────────
if isinstance(x, str): ...        # x is str here
if x is None: ...                 # identity checks
if isinstance(x, (int, float)): ...
match x:
    case str(): ...               # structural pattern matching narrows too
assert isinstance(x, User)        # narrows, but ⚠ asserts vanish under -O

# ── TRUTHINESS IS NOT A NONE CHECK ───────────────────────────────────────
def f(items: list[int] | None):
    if items:                     # ✗ an EMPTY list takes the else branch
        process(items)
    else:
        handle_missing()          # runs for [] as well as for None —
                                  # almost never what you meant
    if items is not None:         # ✓ says exactly what it means
        process(items)

# ── EXHAUSTIVENESS: CATCHING A MISSED CASE AT CHECK TIME ─────────────────
from typing import Literal, assert_never

Status = Literal["pending", "active", "closed"]

def describe(s: Status) -> str:
    if s == "pending": return "waiting"
    if s == "active":  return "running"
    assert_never(s)               # ✗ mypy: "closed" is unhandled
# Add a fourth status to the Literal and every non-exhaustive match becomes
# a CI failure rather than a bug report. This is one of the highest-value
# patterns in the whole toolkit.

# ── TypeGuard: NARROWING THROUGH YOUR OWN FUNCTION ───────────────────────
from typing import TypeGuard

def is_str_list(v: list[object]) -> TypeGuard[list[str]]:
    return all(isinstance(x, str) for x in v)

if is_str_list(items):
    " ".join(items)               # ✓ the checker knows it is list[str]
# Without TypeGuard the helper returns plain bool and narrows nothing.

# ── cast(): LYING, DELIBERATELY ──────────────────────────────────────────
from typing import cast
user = cast(User, data)           # zero runtime effect. Pure assertion.
# Use ONLY when you genuinely know more than the checker — a deserialised
# object whose shape you already validated. Using it to silence an error
# you do not understand converts a check-time error into a production
# crash. Every cast deserves a comment saying why it is safe.

Part 3 — Protocols and Structural Typing

from typing import Protocol

class Sender(Protocol):
    def send(self, msg: str) -> None: ...

def notify(sender: Sender, msg: str) -> None:
    sender.send(msg)

class EmailSender:                # inherits NOTHING, imports nothing
    def send(self, msg: str) -> None: ...

notify(EmailSender(), "hi")       # ✓ it matches structurally

# ── NOMINAL vs STRUCTURAL ────────────────────────────────────────────────
# ABC (nominal):      you must inherit from it to qualify
# Protocol (structural): you qualify by having the right methods
#
# This is what lets a third-party class satisfy YOUR interface without
# either side knowing about the other — and it is how you type
# "composition over inheritance" statically without forcing every
# collaborator into your class tree.

# ── PROTOCOLS FOR ATTRIBUTES AND MORE ────────────────────────────────────
class HasId(Protocol):
    id: int                                    # attributes work too

class Closeable(Protocol):
    def close(self) -> None: ...

from typing import runtime_checkable
@runtime_checkable
class Sized(Protocol):
    def __len__(self) -> int: ...
isinstance(x, Sized)              # allowed — but ONLY checks that the
                                  # methods EXIST, not their signatures

# ── DEFINE THE PROTOCOL WHERE IT IS USED ─────────────────────────────────
# The consumer owns the interface, listing only what it actually needs:
class SupportsRead(Protocol):
    def read(self, n: int = -1) -> str: ...

def parse(f: SupportsRead) -> Config: ...
# Now parse() accepts a real file, an io.StringIO, a gzip handle, or a
# 5-line test fake — none of which had to import anything from you.
# Contrast with `def parse(f: TextIO)`, which is far more than parse needs
# and excludes anything that merely reads.

# ── USE THE ABSTRACT TYPES YOU ALREADY HAVE ──────────────────────────────
from collections.abc import Iterable, Sequence, Mapping, Callable

def total(xs: list[int]) -> int: ...        # ✗ rejects tuples, sets, gens
def total(xs: Iterable[int]) -> int: ...    # ✓ accepts all of them

# The rule: accept the MOST GENERAL type you can use, return the MOST
# SPECIFIC type you can promise.
def get_names(users: Iterable[User]) -> list[str]: ...
#              ^ general in            ^ specific out
# Iterable  — you only loop over it
# Sequence  — you also index or len() it (list, tuple, str)
# Mapping   — a read-only dict view
# Callable[[int, str], bool] — a function taking int and str, returning bool
Key insight: a type hint is a claim your code makes about itself, and a static checker is what turns that claim into something enforced. Nothing about it constrains the data arriving from a request body, a config file, or a database driver — at that boundary, the annotation is just documentation. So the two halves are not interchangeable: mypy verifies internal consistency across the whole codebase for free at check time, and Pydantic verifies external shape at runtime where the program meets the world. A codebase with one and not the other has a hole exactly where the other one would have been.

Part 4 — Generics and Variance

from typing import TypeVar

T = TypeVar("T")

def first(items: list[T]) -> T | None:
    return items[0] if items else None

first([1, 2, 3])          # the checker infers int | None
first(["a"])              # str | None
# Without the TypeVar you would write `list[Any] -> Any` and lose the
# connection between the argument and the return type entirely.

# ── BOUNDED AND CONSTRAINED ──────────────────────────────────────────────
from typing import Protocol
class Comparable(Protocol):
    def __lt__(self, other) -> bool: ...

C = TypeVar("C", bound=Comparable)      # T must SUPPORT <
def largest(items: list[C]) -> C: ...

S = TypeVar("S", str, bytes)            # EXACTLY str or bytes, no mixing
def join(items: list[S], sep: S) -> S: ...

# ── GENERIC CLASSES ──────────────────────────────────────────────────────
class Repository[T]:                    # 3.12+ syntax
    def get(self, id: int) -> T | None: ...
    def add(self, item: T) -> None: ...

repo: Repository[User] = Repository()
repo.get(1)                             # User | None

from typing import Generic              # pre-3.12 equivalent
class Repository(Generic[T]): ...

# ── VARIANCE: WHY list[Dog] IS NOT A list[Animal] ────────────────────────
def add_cat(animals: list[Animal]) -> None:
    animals.append(Cat())

dogs: list[Dog] = [Dog()]
add_cat(dogs)              # ✗ mypy rejects this — and it is RIGHT:
                           #   dogs would now contain a Cat, and the next
                           #   d.bark() crashes at runtime.
#
# MUTABLE containers are INVARIANT: list[Dog] is not a list[Animal] and
# not the reverse either. This is the single most common "why is mypy
# complaining, my code obviously works" moment, and the answer is that it
# obviously works only because nobody has appended to it yet.
#
# ✓ If you only READ, ask for a covariant type:
def count(animals: Sequence[Animal]) -> int:      # Sequence is covariant
    return len(animals)
count(dogs)                # ✓ fine — Sequence has no append
#
# Same fix for dicts: Mapping is covariant in its values, dict is not.
def show(cfg: Mapping[str, Animal]) -> None: ...

# ── ParamSpec: TYPING A DECORATOR ────────────────────────────────────────
from typing import ParamSpec, Callable
P = ParamSpec("P")
R = TypeVar("R")

def timed(fn: Callable[P, R]) -> Callable[P, R]:
    @functools.wraps(fn)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        return fn(*args, **kwargs)
    return wrapper
# Without ParamSpec the decorator returns Callable[..., R], so every
# decorated function accepts ANY arguments as far as the checker knows.
# One untyped decorator applied broadly silently disables checking at
# hundreds of call sites — a real and invisible loss.

# ── Self ─────────────────────────────────────────────────────────────────
from typing import Self
class Builder:
    def add(self, x: int) -> Self:      # subclasses return THEIR type,
        return self                      # not Builder

Part 5 — Literal, TypedDict, NewType, Any

from typing import Literal, TypedDict, NewType, Any, Final, overload

# ── Literal: EXACT VALUES ────────────────────────────────────────────────
def sort(order: Literal["asc", "desc"]) -> None: ...
sort("ascending")         # ✗ caught at check time, not by a runtime
                          #   ValueError in production
Mode = Literal["r", "w", "a"]
# Cheaper than an Enum for a small closed set of strings, and it composes
# with assert_never for exhaustiveness. Use an Enum when the values need
# methods, or when they must be iterated.

# ── TypedDict: A DICT WITH A KNOWN SHAPE ─────────────────────────────────
class UserDict(TypedDict):
    id: int
    name: str
    email: NotRequired[str]        # optional KEY (3.11+)

u: UserDict = {"id": 1, "name": "ada"}
u["nam"]                  # ✗ caught — a typo'd key, the classic dict bug
# For JSON-shaped data you cannot or will not convert to a class. It is
# still a plain dict at runtime, with NO validation — TypedDict describes,
# Pydantic enforces.

# ── NewType: DISTINCT TYPES WITH NO RUNTIME COST ─────────────────────────
UserId = NewType("UserId", int)
OrderId = NewType("OrderId", int)

def get_user(uid: UserId) -> User: ...
get_user(OrderId(5))      # ✗ caught, even though both are ints
get_user(5)               # ✗ caught — a bare int is not a UserId
# Prevents the entire family of "passed the wrong id" bugs, which are
# invisible to a checker when everything is `int`. Zero runtime overhead:
# UserId(5) is just 5.

# ── Any: THE ESCAPE HATCH THAT SPREADS ───────────────────────────────────
def load(path: str) -> Any: ...
config = load("cfg.json")
config.databse.host       # ✗ NOT caught — Any silences everything
                          #   downstream, including the typo
# Any is not "unknown", it is "stop checking". It propagates through every
# expression it touches, so one Any in a hot path can disable checking for
# a whole module without anyone noticing.
#
# ✓ object   — genuinely unknown; you must narrow before using it
# ✓ a union  — int | str | None
# ✓ a TypedDict or a Pydantic model for structured data
#
# mypy --disallow-any-explicit makes each one a deliberate decision.

# ── Final ────────────────────────────────────────────────────────────────
from typing import Final
MAX_RETRIES: Final = 3            # reassignment is a check-time error

# ── overload: DIFFERENT RETURN TYPE PER ARGUMENT TYPE ────────────────────
@overload
def get(key: str) -> str | None: ...
@overload
def get(key: str, default: str) -> str: ...
def get(key, default=None):                   # the real implementation
    return _store.get(key, default)
# Callers passing a default get a non-Optional str, so they are not forced
# to handle a None that cannot happen.

Part 6 — Static Checking vs Runtime Validation

# ── mypy IN CI ───────────────────────────────────────────────────────────
# pyproject.toml
[tool.mypy]
python_version = "3.12"
strict = true                     # the target
warn_unused_ignores = true        # stale `# type: ignore` becomes an error
warn_return_any = true

# strict turns on, among others:
#   disallow_untyped_defs         every function must be annotated
#   disallow_any_generics         no bare `list`, must be `list[str]`
#   no_implicit_optional          `x: int = None` is an error
#   warn_unreachable              dead code after a narrowing mistake

# ── ADOPTING IN A LARGE UNTYPED CODEBASE ─────────────────────────────────
# Never "annotate everything" as one PR — it will be unreviewable and will
# conflict with every branch in flight.
[tool.mypy]
strict = false                    # lenient baseline everywhere

[[tool.mypy.overrides]]           # strict ISLANDS, growing outward
module = ["myapp.core.*", "myapp.billing.*"]
strict = true
# Type new code and any module you are already editing. Start with the
# code where a bug is most expensive — money, auth, data integrity.
# Ratchet: the check must never get worse, and CI enforces that.

# ── mypy vs pyright ──────────────────────────────────────────────────────
# mypy     the reference implementation, plugin ecosystem (django, sqlalchemy)
# pyright  much faster, better inference, powers Pylance in VS Code
# Both are fine. Pick one for CI so there is a single source of truth —
# they disagree at the edges and chasing both wastes time.

# ── AND THE PART TYPES CANNOT DO ─────────────────────────────────────────
data = json.loads(request.body)   # Any. The checker is now blind.
user = User(**data)               # a dataclass does NOT validate:
                                  # User(id="abc") constructs happily

from pydantic import BaseModel, Field, field_validator

class UserIn(BaseModel):
    id: int
    name: str = Field(min_length=1, max_length=100)
    role: Literal["admin", "viewer"] = "viewer"
    email: str

    @field_validator("email")
    @classmethod
    def valid_email(cls, v: str) -> str:
        if "@" not in v:
            raise ValueError("invalid email")
        return v

user = UserIn.model_validate(data)     # RAISES on bad shape, with a
                                       # precise per-field error report
# From here on the object is genuinely what its annotations say, so the
# static types downstream are trustworthy rather than aspirational.

# ── THE DIVISION OF LABOUR ───────────────────────────────────────────────
#
#   mypy / pyright  →  YOUR code is internally consistent.
#                      Check time. Free. Whole codebase.
#
#   pydantic        →  DATA from outside matches its declared shape.
#                      Runtime. Costs cycles. Boundaries only.
#
# Validate once, at the edge — HTTP handlers, queue consumers, config
# loading, third-party API responses — and let static types carry the
# guarantee inward. Validating in the middle of the call stack is a sign
# the boundary is in the wrong place.

Interview Questions

Beginner: Do type hints change how Python runs?

No. The interpreter parses annotations and stores them in __annotations__, then ignores them entirely for execution, so def f(x: int) happily accepts f("hello") and whatever goes wrong goes wrong later, somewhere else. What makes them useful is everything outside the interpreter: static checkers like mypy and pyright analyse the code without running it and catch the mismatch in CI, editors use them for autocomplete and inline errors, and a whole category of libraries reads them at runtime — dataclasses to generate __init__, Pydantic to validate, FastAPI to build routing and OpenAPI documentation. So the value comes from the combination of hints plus a checker that runs on every commit; hints on their own are documentation that nothing verifies, which is why they eventually start lying if no checker is enforcing them.

Beginner: What is Optional[X] and why does the checker complain about using it?

Optional[X] means X | None — the modern spelling since 3.10 — and it does not mean an optional argument, which is a separate thing expressed by giving the parameter a default. When a function is annotated as returning User | None, the checker refuses to let you access .name on the result until you have handled the None case, because on the path where it is None that attribute access is an AttributeError. That single rule catches a large share of real production crashes, and it is usually the first thing people notice when they turn a checker on.

Handling it is called narrowing: an if x is not None: block, an early return when it is None, or an isinstance check all tell the checker which type it has inside that branch. The trap to avoid is narrowing with truthiness — if items: sends both an empty list and None down the same path, which is almost never what was meant, so is not None is the correct spelling.

Mid: What is a Protocol and when would you use one over an ABC?

A Protocol declares a structural interface: any object with matching methods and attributes satisfies it, with no inheritance and no registration. An ABC is nominal — a class only qualifies if it explicitly inherits from it. That difference matters most at boundaries you do not control: a third-party class can satisfy your Protocol without either side importing the other, which an ABC can never do.

It is also the honest way to type Python's existing duck-typing culture. A function that needs something with a read method can declare exactly that, and then accept a real file, a StringIO, a gzip handle or a five-line test fake — all statically checked, with no mocking framework and no shared base class. The convention that makes this work well is defining the protocol in the module that consumes it, listing only the methods actually used, so the interface describes a requirement rather than a class hierarchy.

I would still use an ABC when I want to provide shared implementation alongside the interface, or when instantiating an incomplete subclass should fail loudly at construction — an ABC raises TypeError for unimplemented abstract methods, which moves an error from the first call to startup. The two also compose: an ABC for a hierarchy I own, protocols for the seams where other people's code plugs in.

Mid: Why is list[Dog] not accepted where list[Animal] is expected?

Because mutable containers are invariant, and the rejection is protecting against a real bug. If list[Dog] were accepted as list[Animal], the callee would be free to do animals.append(Cat()) — which is perfectly valid for the type it was handed — and the caller's list, still typed list[Dog], would now contain a Cat. The next dog.bark() crashes. The checker cannot know the callee will not append, so it has to assume it might.

The fix follows from what the function actually does with the argument. If it only reads, ask for Sequence[Animal], which is covariant precisely because it has no mutating methods, and list[Dog] is then accepted. The same applies to dicts, where Mapping is the read-only counterpart to dict. This generalises into the rule I would state as: accept the most general type you can work with and return the most specific type you can promise — so parameters lean towards Iterable, Sequence and Mapping, and return types stay concrete like list[str]. Typing a parameter as list[X] when you only iterate over it rejects tuples, sets and generators for no benefit at all.

Senior: How do you guarantee that data from an external API actually matches its declared type?

You cannot do it with type hints, because they are erased — the guarantee has to come from runtime validation at the point where the data enters. json.loads returns Any, which makes the checker blind from that line onward, and a dataclass will not help either since it generates an __init__ that assigns whatever it is given: User(id="abc") constructs perfectly happily and fails much later, in code that had nothing to do with the mistake.

The tool for this is Pydantic. A BaseModel with the same annotations validates and coerces on construction, raising a structured per-field error listing exactly what was wrong, and supports field constraints and custom validators for rules the type system cannot express. Once model_validate returns, the object genuinely is what its annotations claim, so every static type downstream is trustworthy rather than aspirational. FastAPI builds on exactly this, which is why a typed handler signature there is real validation rather than documentation.

The architectural point is where to put it. Validate once, at the edges — HTTP handlers, queue consumers, config loading, third-party responses — and let the static types carry the guarantee inward so internal functions can trust their inputs. Validation appearing in the middle of a call stack usually means the boundary is in the wrong place. The division of labour is worth stating explicitly: mypy proves your code is internally consistent, for free, across the whole codebase at check time; Pydantic proves external data matches its shape, at runtime, at specific points. Neither substitutes for the other, and a codebase with only one has a hole exactly where the other belongs.

Senior: How would you introduce typing into a large untyped codebase?

Not as one big annotation PR. That produces thousands of changed lines nobody can review, conflicts with every branch in flight, and — because it is written to make the checker quiet rather than to describe reality — tends to be full of Any and type: ignore that make the result look checked while catching nothing.

What works is a lenient baseline plus strict islands. Turn mypy on across the repo with almost everything disabled so it passes immediately, then enable strict per module for the areas where a bug is most expensive — money, authentication, data integrity — and expand outward. New code is typed by policy, and any module someone is already editing gets typed as part of that work, so the coverage follows the code that is actually changing. The critical piece is the ratchet: CI enforces that the strict module list only ever grows and the error count never increases, because without that the effort quietly reverses within a quarter.

Some things pay off far above their cost and are worth doing early. Annotating function signatures alone — parameters and returns, leaving bodies inferred — captures most of the value for a fraction of the work. Third-party stubs from types-* packages remove a large class of spurious errors. --warn-unused-ignores stops suppressions outliving the problems they were added for, and ignores should always carry a specific error code so they do not silently swallow future errors on that line. And I would watch for two things that look like progress but are not: untyped decorators, which erase signatures at every call site unless written with ParamSpec, and blanket Any on deserialisation boundaries, which disables checking for everything downstream. The goal is not a percentage of annotated lines — it is that the checker catches a real bug often enough that the team stops seeing it as overhead.

# ✗ BEFORE
from typing import Any

def load_config(path: str) -> Any:
    return json.load(open(path))

cfg = load_config("app.json")
cfg.databse.host                   # NOT caught. Any silences everything
cfg["timeuot"]                     # NOT caught either
# Any is not "unknown" — it is "stop checking". It spreads through every

# ── OPTION A: TypedDict — describes the shape, no runtime cost ───────────
from typing import TypedDict, NotRequired

class DatabaseConfig(TypedDict):
    host: str
    port: int

class AppConfig(TypedDict):
    database: DatabaseConfig
    timeout: int
    debug: NotRequired[bool]       # optional KEY

def load_config(path: str) -> AppConfig:
    return json.load(open(path))   # ⚠ still unvalidated — a cast in
                                   #   effect. Typos in YOUR code are
                                   #   caught; a malformed FILE is not.

# ── OPTION B: PYDANTIC — describes AND enforces ──────────────────────────
from pydantic import BaseModel, Field

class DatabaseConfig(BaseModel):
    host: str
    port: int = Field(ge=1, le=65535)

class AppConfig(BaseModel):
    database: DatabaseConfig
    timeout: int = 30
    debug: bool = False

def load_config(path: str) -> AppConfig:
    return AppConfig.model_validate_json(Path(path).read_text())

#   database.port: Input should be less than or equal to 65535
# instead of a TypeError three hours into a batch job.

# ── WHICH ──────────────────────────────────────────────────────────────
# TypedDict — data you already trust, or a shape you must keep as a dict.
# Pydantic  — anything crossing INTO the program: config, request bodies,
#             queue messages, third-party responses.
# object    — genuinely unknown; the checker forces you to narrow first.
# Any       — a deliberate, commented escape hatch. Enable
#             --disallow-any-explicit so each one is a decision.
3 (medium): Type a plugin system so any conforming class works without inheriting from you.
Solution 
from typing import Protocol, runtime_checkable
from collections.abc import Iterable

class Exporter(Protocol):
    name: str                                        # attributes count too
    def supports(self, fmt: str) -> bool: ...
    def export(self, rows: Iterable[dict]) -> bytes: ...

def run_export(exporter: Exporter, rows: Iterable[dict]) -> bytes:
    return exporter.export(rows)

# ── A PLUGIN INHERITS NOTHING ────────────────────────────────────────────
class CsvExporter:                 # no base class, no import of ours
    name = "csv"
    def supports(self, fmt: str) -> bool: return fmt == "csv"
    def export(self, rows): ...

run_export(CsvExporter(), rows)    # ✓ structurally compatible

# This is the whole point: a plugin in someone else's package satisfies
# the interface without either side importing the other. An ABC cannot
# do that — it requires explicit inheritance.

# ── THE CHECKER CATCHES A NON-CONFORMING PLUGIN ──────────────────────────
class BadExporter:
    name = "bad"
    def export(self, rows) -> str:      # wrong return type, no supports()
        return "..."
run_export(BadExporter(), rows)
# ✗ error: Argument 1 has incompatible type "BadExporter";
#          expected "Exporter"
#   note: 'supports' is not present
#   note: 'export' has incompatible return type "str", expected "bytes"

# ── ASSERTING CONFORMANCE AT THE PLUGIN'S OWN SITE ───────────────────────
_: Exporter = CsvExporter()        # a one-line check in the plugin module,
                                   # so the error appears THERE rather
                                   # than at every call site

# ── RUNTIME CHECKS, WITH A CAVEAT ────────────────────────────────────────
@runtime_checkable
class Exporter(Protocol): ...
isinstance(plugin, Exporter)       # allowed, but ONLY verifies the
                                   # methods EXIST — not their signatures
                                   # or types. Use it for a registry
                                   # sanity check, not as validation.

# ── WHY NOT AN ABC ───────────────────────────────────────────────────────
class Exporter(ABC):
    @abstractmethod
    def export(self, rows) -> bytes: ...
# Forces every plugin author to import and inherit from your package, so
# a third-party class can never qualify and testing needs a real subclass
# rather than a 3-line fake.
#
# ✓ ABC when you also supply shared implementation, or when instantiating
#   an incomplete subclass should fail at construction.
# ✓ Protocol at the seams where other people's code plugs in.

# ✗ BEFORE — a typo is a runtime bug, and a new status silently falls
#            through every existing if/elif
def describe(status: str) -> str:
    if status == "pending": return "Waiting"
    if status == "active":  return "Running"
    return "Unknown"                          # swallows typos AND new cases

describe("actve")                             # "Unknown". No error.

# ✓ AFTER
from typing import Literal, assert_never

Status = Literal["pending", "active", "closed"]

def describe(status: Status) -> str:
    if status == "pending": return "Waiting"
    if status == "active":  return "Running"
    if status == "closed":  return "Finished"
    assert_never(status)           # unreachable IF all cases are covered

describe("actve")                  # ✗ caught at check time

# ── THE REAL PAYOFF: ADDING A STATUS ─────────────────────────────────────
Status = Literal["pending", "active", "closed", "cancelled"]
# mypy now FAILS every non-exhaustive function:
#   error: Argument 1 to "assert_never" has incompatible type
#          "Literal['cancelled']"; expected "NoReturn"
#
# CI hands you the complete list of places that need updating. Without
# assert_never, "cancelled" silently returns "Unknown" from a dozen
# functions and you find out from a bug report.

# ── WITH match ───────────────────────────────────────────────────────────
def describe(status: Status) -> str:
    match status:
        case "pending":   return "Waiting"
        case "active":    return "Running"
        case "closed":    return "Finished"
        case _ as unreachable:
            assert_never(unreachable)

# ── Literal vs Enum ──────────────────────────────────────────────────────
# Literal — a small closed set of strings that stay strings on the wire
#   (JSON, a DB column). No runtime object, no conversion at boundaries.
# Enum    — when the values need methods or metadata, must be iterated,
#   or the internal representation should differ from the wire format.
class Status(StrEnum):
    PENDING = "pending"
    @property
    def is_terminal(self) -> bool: return self is Status.CLOSED
# Exhaustiveness works the same way with both.

class Task(BaseModel):
    status: Status                 # Pydantic REJECTS "actve" at runtime

import json
from typing import Any, cast

def handle(request) -> Response:            # ← HOLE 1

# ── HOLE 1: AN UNANNOTATED PARAMETER ─────────────────────────────────────
# `request` is implicitly Any, so every attribute access on it is
# unchecked. Under strict mode disallow_untyped_defs catches this; without
# strict, mypy silently skips the whole function body of an unannotated
# function.
def handle(request: Request) -> Response:

# ── HOLE 2: json.loads RETURNS Any ───────────────────────────────────────
# Any does not mean unknown, it means STOP CHECKING — and it propagates.
# data["amount"] is Any, so passing it as a Decimal is not questioned.
# It arrives as a str or a float and Decimal arithmetic fails, or worse,
# float arithmetic silently produces the wrong amount of money.

# ── HOLE 3: cast() IS A LIE WITH NO RUNTIME EFFECT ───────────────────────
user = cast(User, data)          # data is still a plain dict
user.email                       # AttributeError at runtime; mypy is happy
# cast asserts something the checker cannot verify. Using it to silence an
# error converts a check-time failure into a production one.

# ── HOLE 4: NO VALIDATION AT THE BOUNDARY ────────────────────────────────
# Nothing has confirmed the payload has an "amount", that it is numeric,
# that it is positive, or that the user exists.

# ── HOLE 5: AN UNTYPED DECORATOR ERASES THE SIGNATURE ────────────────────
def log_calls(fn):                          # returns an untyped callable
    def wrapper(*args, **kwargs): ...
    return wrapper
# charge is now Callable[..., Any] to the checker. EVERY call site loses
# checking, silently. One such decorator applied broadly can disable
# typing across a service.
from typing import ParamSpec, TypeVar, Callable
P, R = ParamSpec("P"), TypeVar("R")
def log_calls(fn: Callable[P, R]) -> Callable[P, R]:
    @functools.wraps(fn)
    def wrapper(*a: P.args, **k: P.kwargs) -> R: return fn(*a, **k)
    return wrapper

# ── WHAT NOT TO DO ───────────────────────────────────────────────────────
# One PR annotating everything. It is unreviewable, conflicts with every
# open branch, and — because it is written to make the checker quiet
# rather than to describe reality — fills up with Any and type: ignore.
# The result LOOKS typed and catches nothing, and the next person
# concludes typing does not work here.

# ── PHASE 1: A GREEN BASELINE (day one) ──────────────────────────────────
[tool.mypy]
python_version = "3.12"
ignore_missing_imports = true     # temporarily; third-party stubs come later
# everything else off. The suite passes immediately, and CI has a gate
# that can now only tighten.

# ── PHASE 2: STOP THE BLEEDING (week one) ────────────────────────────────
[[tool.mypy.overrides]]
module = ["myapp.newfeature.*"]
disallow_untyped_defs = true
# Policy: new modules are typed. Any module you touch gets its signatures
# typed as part of that work. Coverage then follows the code that is
# actually changing, which is where bugs are.

# ── PHASE 3: STRICT ISLANDS, BY BLAST RADIUS ─────────────────────────────
[[tool.mypy.overrides]]
module = ["myapp.billing.*", "myapp.auth.*", "myapp.models.*"]
strict = true
# Order by what a bug COSTS: money, authentication, data integrity first.
# A typo in a reporting script is cheap; a typo in refund calculation is
# not. Do not order by what is easiest.

# ── PHASE 4: THE RATCHET (the part that makes it stick) ──────────────────
# CI fails if the error count INCREASES or a module leaves the strict list.
mypy --strict src/myapp/billing | tee current.txt
diff <(count current.txt) <(cat .mypy-baseline) || exit 1
# Without a ratchet, this effort reverses within two quarters. With one,
# it only ever improves, and nobody has to police it in review.

# ── PHASE 5: STRICT EVERYWHERE ───────────────────────────────────────────
[tool.mypy]
strict = true
[[tool.mypy.overrides]]
module = ["myapp.legacy.*"]       # the shrinking exception list
strict = false

# ── HIGHEST VALUE PER HOUR, IN ORDER ─────────────────────────────────────
# 1. SIGNATURES ONLY — parameters and returns, bodies inferred. Most of
#    the benefit for a fraction of the effort.
# 2. RETURN TYPES with | None — forces callers to handle the miss. This
#    alone eliminates a large share of AttributeError crashes.
# 3. types-* STUBS for third-party packages — removes a wall of spurious
#    errors that otherwise teaches people to ignore output.
# 4. PYDANTIC AT THE EDGES — without it, every handler starts from Any
#    and the internal types are aspirational.
# 5. ParamSpec ON SHARED DECORATORS — one untyped decorator applied
#    widely erases checking at hundreds of call sites, invisibly.

# ── THINGS THAT LOOK LIKE PROGRESS AND ARE NOT ───────────────────────────
# - "% of lines annotated" as a metric. Any counts as annotated.
# - Blanket `# type: ignore`. Always use a code: # type: ignore[arg-type]
#   Plus warn_unused_ignores = true, so suppressions cannot outlive the
#   problems they were added for.
# - Annotating dead code. Check `git log` before spending a day on a
#   module nobody has touched in three years.

# ── TOOLING ──────────────────────────────────────────────────────────────
# ONE checker in CI (mypy or pyright) as the source of truth — they
#   disagree at the edges and chasing both wastes days.
# pre-commit hook on changed files for a fast local signal.
# Pylance/Pyright in the editor regardless; instant feedback is what
#   actually changes how people write code.

# ── THE SUCCESS CRITERION ────────────────────────────────────────────────
# Not a coverage percentage. It is: does the checker catch a real bug
# often enough that the team stops experiencing it as overhead? Track
# "type errors caught in CI that would have shipped" for the first
# quarter — that number is what wins the argument, not coverage.

🎯 Key Takeaways

  • Annotations are stored and ignored at runtime — a checker in CI is what makes them mean anything.
  • Use modern syntax: list[str], X | None, not typing.List or Optional.
  • X | None forces callers to handle the miss; narrow with is not None, never with truthiness.
  • Protocol types duck typing structurally, so third-party classes and tiny test fakes qualify without inheriting anything.
  • Accept the most general type you can use (Iterable, Sequence), return the most specific you can promise.
  • Mutable containers are invariant — list[Dog] is not a list[Animal], because the callee could append.
  • Any means "stop checking" and spreads; prefer object, a union, or a TypedDict.
  • Decorators need ParamSpec or they silently disable checking at every call site.
  • Literal plus assert_never turns a missed case into a CI failure instead of a bug report.
  • mypy proves your code is internally consistent; Pydantic proves external data matches — validate once at the edge and trust the types inward.
