Syntax, Types & Variables Basics

Python favors readability: indentation IS the block structure, and "there should be one obvious way to do it". It's dynamically typed (types travel with values, not variables) but strongly typed (no silent "5" + 3). The deep idea underneath everything: variables are names bound to objects — get that and mutability, copying, and function arguments all click.

Almost every confusing Python bug a beginner hits — "why did my list change?", "why does my default argument remember things?", "why is a is b True here but False there?" — is the same misunderstanding wearing different hats. This lesson installs the correct mental model once so those bugs stop being mysterious.

Part 1 — Variables Are Names, Not Boxes

The single most useful correction to make early: a variable in Python is not a box that holds a value. It's a label stuck onto an object that lives somewhere in memory. Assignment moves the label. It never copies the object.

If you learned C or Java first, you likely picture x = 5 as "the box named x now contains 5". That picture predicts the wrong answer for mutable types, which is exactly where people get burned.

x = [1, 2, 3]        # x is a NAME bound to a list object
y = x                # y binds to the SAME object (no copy!)
y.append(4)          # x is now [1, 2, 3, 4] too — one object, two names
y = [9]              # rebinds y to a NEW object; x unaffected

print(x)             # [1, 2, 3, 4]   <-- surprised? that's the box model failing

Two different operations look similar but are fundamentally different:

OperationWhat it doesCaller sees change?
y = [9]Rebinding — moves the label y to a different objectNo
y.append(4)Mutation — changes the object itself, labels unmovedYes, through every name bound to it

Say it as a rule: = moves a label; a method call can change the thing. Everything below is a consequence.

Identity vs equality

a = [1]; b = [1]
a == b               # True  — equal VALUE (calls a.__eq__(b))
a is b               # False — different OBJECTS

id(a), id(b)         # different integers = different memory identities
c = a
c is a               # True — same object, two labels

== asks "do these look the same?"; is asks "are these literally the same object?". You want == almost always. Reserve is for the singletons None, True, False.

The interning trap: CPython caches small integers (−5 to 256) and some short strings, so a = 256; b = 256; a is b is True — but a = 257; b = 257; a is b is False. This is a private optimisation, not a language guarantee. Code that relies on it breaks between versions and between interpreters. Use == for values, always.

Why this matters for function arguments

Python's argument passing is often mis-taught as "pass by reference" or "pass by value". It's neither — it's pass by assignment. The parameter name is bound to the same object the caller passed. So the same rule applies: mutation is visible, rebinding is not.

def mutate(items):
    items.append(99)      # MUTATES the caller's object — visible outside

def rebind(items):
    items = [0]           # rebinds the LOCAL name only — invisible outside
    items.append(99)      # mutates the new local list, not the caller's

data = [1, 2]
mutate(data);  print(data)   # [1, 2, 99]   <-- changed
rebind(data);  print(data)   # [1, 2, 99]   <-- unchanged by rebind

This is why "does this function modify its arguments?" is a real design question in Python, and why functions that mutate should say so in their name (list.sort() mutates and returns None; sorted() returns a new list — the standard library is consistent about this signal).

The mutable/immutable split is the axis that matters. It determines whether an object can be a dict key, whether sharing it is safe, and whether = can surprise you.

Immutability is about the object, not the name

A common half-understanding: "tuples are immutable, so a tuple can't change." What's frozen is the tuple's set of bindings — not the objects those bindings point to.

t = ([1, 2], "hi")
t[0] = [9]           # TypeError — can't rebind a slot in a tuple
t[0].append(3)       # ✅ works! the LIST inside is still mutable
print(t)             # ([1, 2, 3], 'hi')

# Consequence: this tuple is NOT hashable, because a member isn't:
{t: "value"}         # TypeError: unhashable type: 'list'

The design consequence: "can I use this as a dict key?" is not answered by the outer type alone. It's hashable only if it's immutable all the way down.

Floats and money

0.1 + 0.2                     # 0.30000000000000004
0.1 + 0.2 == 0.3              # False  <-- classic bug

from decimal import Decimal
Decimal("0.1") + Decimal("0.2") == Decimal("0.3")   # True

import math
math.isclose(0.1 + 0.2, 0.3)  # True — the right float comparison

Floats are binary fractions; 0.1 has no exact binary representation, exactly as 1/3 has no exact decimal one. For money use Decimal (constructed from strings, not floats — Decimal(0.1) inherits the float's error) or integer cents. For measurements, compare with math.isclose rather than ==.

Part 3 — Strong + Dynamic Typing

These two words get conflated constantly. They're independent axes, and Python sits at a specific point on each.

"5" + 3          # ❌ TypeError — no implicit coercion (STRONG typing, unlike JS)
"5" * 3          # "555"  (str * int IS defined: repetition)
int("5") + 3     # 8      — convert explicitly

n = 5; n = "hi"  # ✅ allowed — names aren't typed (DYNAMIC typing)
AxisPythonMeaningContrast
Strong vs weakStrongNo implicit cross-type coercion; you convert on purposeJS: "5" + 3 === "53" silently
Static vs dynamicDynamicNames aren't typed; types are checked at runtimeJava/C#: types fixed at compile time

The practical consequence of "dynamic": type errors surface at runtime, in production, on the path you didn't test. That's the entire motivation for type hints plus mypy and for taking tests seriously — you're buying back the compile-time check the language declined to give you.

The practical consequence of "strong": you can trust that a value didn't quietly change type underneath you. A TypeError is a gift — it's the bug surfacing at the point of the mistake rather than three layers away as corrupted output.

Part 4 — Idiomatic Basics

Python code that reads as "written by a Python programmer" leans on a small set of constructs. Learn these five and your code stops looking translated from another language.

name = "Asha"; count = 3

# 1. f-strings — the modern formatting (3.6+)
f"Hi {name}, {count} new items ({count * 2} total)"
f"{value:.2f}"      # 2 decimal places
f"{n:>10}"          # right-align in width 10
f"{n:,}"            # thousands separators: 1,000,000
f"{x=}"             # debug form, prints "x=42" (3.8+)

# 2. Tuple packing/unpacking
a, b = b, a                      # swap, no temp variable
a, *rest = [1, 2, 3, 4]          # a=1, rest=[2, 3, 4]
first, *_, last = [1, 2, 3, 4]   # keep the ends, discard the middle

# 3. Conditional expressions (Python's ternary)
x = 10 if cond else 20

# 4. Chained comparisons — evaluates b once, reads like maths
if 0 <= index < len(items):  ...

# 5. Readability details
big = 1_000_000                  # digit separators
PI: float = 3.14159              # optional type hint

The a, b = b, a swap works because the right side is evaluated to a tuple first, then unpacked — so there's no intermediate clobbering. Same reason i, items[i] = i + 1, "new" behaves predictably.

PEP 8 and the culture

# snake_case for names, UPPER_CASE for constants, 4-space indent
user_count = 0
MAX_RETRIES = 3

# Tooling enforces it — nobody argues about style in review:
#   ruff format .     (formatter — the Prettier equivalent)
#   ruff check .      (linter — the ESLint equivalent)

PEP 8 is culturally mandatory in Python in a way style guides aren't in some other ecosystems. Deviating marks code as foreign. The upside is that you never spend review time on formatting: run the formatter, move on to the actual logic.

Part 5 — Deep Dive: The Mutable Default Argument

This is the canonical Python gotcha, and it's a direct consequence of Part 1. It appears in interviews constantly because understanding it proves you understand the object model.

def add_item(item, basket=[]):      # ❌ the bug
    basket.append(item)
    return basket

add_item("apple")     # ['apple']
add_item("banana")    # ['apple', 'banana']   <-- WHY?
add_item("cherry")    # ['apple', 'banana', 'cherry']

Why: default arguments are evaluated once, when the def statement executes — not on each call. That single list object is stored on the function and reused forever. Every call without an explicit basket mutates the same object.

add_item.__defaults__       # (['apple', 'banana', 'cherry'],) — you can see it hoarding

# ✅ The fix: use None as the sentinel, create fresh inside
def add_item(item, basket=None):
    if basket is None:
        basket = []
    basket.append(item)
    return basket

The rule: never use a mutable object ([], {}, set()) as a default argument. Immutable defaults (0, None, "" , tuples) are safe precisely because reusing them can't hurt — nothing can mutate them.

When it's deliberate: the same mechanism is occasionally used on purpose as a cheap cache or to bind a loop variable early (lambda x, n=n: x + n). That's a real technique, but it should carry a comment — a reader's default assumption will be that you made the mistake.

Part 6 — Deep Dive: Copying

Once you accept that = never copies, the natural question is how you do copy — and the answer has a depth dimension that catches people.

import copy

original = [[1, 2], [3, 4]]

alias    = original                  # NOT a copy — same object
shallow  = original.copy()           # new outer list, SAME inner lists
shallow2 = original[:]               # identical to .copy()
deep     = copy.deepcopy(original)   # new outer AND new inner objects

shallow[0].append(99)
print(original)    # [[1, 2, 99], [3, 4]]   <-- shallow copy shared the inner list!

deep[1].append(99)
print(original)    # [[1, 2, 99], [3, 4]]   <-- unaffected, fully independent
TechniqueCopiesCostUse when
b = aNothing — new name onlyFreeYou want shared state (or just reading)
a.copy() / a[:]Outer container onlyO(n) pointersFlat containers, or nested but immutable members
copy.deepcopy(a)Everything, recursivelyExpensive; handles cyclesNested mutable data you must isolate

When NOT to deepcopy: it's slow, it can choke on objects holding file handles or DB connections, and reaching for it is often a sign the design has mutation sprawl. The lazier fix is usually to stop mutating — build new values with comprehensions, or use immutable structures (tuples, frozen dataclasses) so copying never comes up.

Interview Questions

Q1 (🟢 Beginner): Explain Python's name/object model and how it affects function arguments.

Variables are names bound to objects; assignment binds a name, it doesn't copy the object. Arguments are passed by assignment (often called pass-by-object-reference): the parameter becomes another name for the same object the caller passed.

The consequence splits cleanly in two: mutating a mutable argument in place (items.append(x)) is visible to the caller, because both names point at the object you changed. Rebinding the parameter (items = [0]) is not visible, because you've only moved the local label.

So a function can append to a passed list but cannot reassign the caller's variable. This is why the standard library signals mutation in its API design: list.sort() mutates and returns None, while sorted() returns a new list.

Q2 (🟢 Beginner): is vs == — when does the difference bite?

== compares value via __eq__; is compares identity — whether two names point at the same object. Use is only for singletons: None, True, False.

Two ways it bites. First, false positives from interning: CPython caches small ints (−5..256) and short strings, so a is b can be True for equal values by accident. Test with 257 and it flips. That's an implementation detail, not a guarantee, so code depending on it breaks across versions or on PyPy.

Second, false negatives with == None: it usually works, but an object with a custom __eq__ (a NumPy array, an ORM field, a mock) can return something non-boolean or raise. is None can't be overridden, so it's unambiguous — which is precisely why PEP 8 mandates it.

Q3 (🟡 Mid): Why does this function accumulate state across calls, and what's the fix? 
def add_item(item, basket=[]):
    basket.append(item)
    return basket

Default arguments are evaluated once, at function definition time — when the def statement runs — not per call. The list object is created then and stored on the function (visible as add_item.__defaults__). Every call that omits basket binds the parameter to that same object and appends to it, so results accumulate.

The fix is the None sentinel: def add_item(item, basket=None), then if basket is None: basket = [] inside. The fresh list is created per call, in the function body, which does run every time.

The general rule is never to use a mutable default. Immutable defaults (0, None, "", tuples) are safe for exactly the reason the mutable ones aren't — sharing an object nobody can change is harmless.

Q4 (🟡 Mid): Shallow vs deep copy — show a case where a shallow copy is a bug, and one where deepcopy is the wrong choice.

Shallow copy as a bug: copy() and [:] build a new outer container holding the same inner objects. So for original = [[1, 2], [3, 4]], mutating shallow[0].append(99) also changes original[0] — you copied the list of pointers, not what they point at. Any nested mutable structure has this exposure.

Deepcopy as the wrong choice: it's expensive (full recursive traversal), and it breaks or behaves surprisingly on objects holding external resources — file handles, sockets, DB connections, thread locks. Deepcopying a config object that carries a live connection pool either raises or silently duplicates something that must not be duplicated.

The design-level answer: reaching for deepcopy is usually a symptom that mutation is sprawling through the code. The better fix is often to stop mutating — build new values with comprehensions, or use immutable structures (tuples, frozen dataclasses) so the question of copying never arises.

Q5 (🔴 Senior): Python is dynamically typed. What does that actually cost a large codebase, and how do you buy the safety back?

The cost is that type errors move from compile time to runtime — from a guaranteed, exhaustive check to one that only fires on code paths that actually execute. In a large codebase the practical effects are: refactors have no compiler to enumerate call sites for you; a rename or signature change surfaces as a production AttributeError on a rare branch; and IDE navigation degrades because the tooling can only guess at types.

You buy it back in layers. Type hints plus mypy or pyright in CI restores most of the static check — crucially, it's gradual, so you can annotate the core domain and public interfaces first and leave glue code untyped. Tests cover what types can't express (behaviour, not just shape) and are the only thing exercising the paths mypy proves nothing about. Validation at the boundaries — Pydantic/FastAPI at the edges of the system — turns untrusted external data into typed objects at one checkpoint, so interior code can trust its inputs.

The honest tradeoff: hints are not enforced at runtime (they're annotations, erased for execution), so they're a development-time tool, not a security boundary. That's why boundary validation is a separate layer rather than something hints give you free.

Q6 (🔴 Senior): You inherit code where a shared config dict is mutated across modules and causing intermittent bugs. Walk through your diagnosis and fix.

Diagnosis first. The signature of this bug class is order-dependence: behaviour changes with import order, test order, or which request arrived first. I'd confirm by checking whether tests pass alone but fail in suite, and by logging id(config) at each site to prove it's one shared object rather than several.

Why it happens: a module-level dict is a single object bound to a name in that module's namespace. Every importer gets a name for the same object, so any module's mutation is globally visible, with no ownership and no audit trail.

Fix, cheapest first. The lazy correct move is to make mutation impossible rather than to police it: load config into an immutable structure — a frozen dataclass or a NamedTuple — so a stray write raises at the offending line instead of corrupting state for everyone. Where per-component variation is genuinely needed, hand out derived copies (dataclasses.replace) rather than letting components edit the shared one.

If the config must stay a dict for compatibility, wrap it in types.MappingProxyType — a read-only view — and expose an explicit reload() that rebuilds it in one place. That's a small diff that converts a diffuse race into a single controlled write.

What I'd avoid: deepcopying the config at every use. It hides the design problem, costs on every access, and leaves the question of which copy is authoritative unanswered. The goal is one writer and many readers, not many private divergent copies.

🏋️ Exercises

1 (Easy): Demonstrate the aliasing bug: create a list, bind a second name to it, mutate through the second name, and show the first changed. Then fix it so the two are independent.
Solution
x = [1, 2, 3]
y = x                  # binds the SAME object — not a copy
y.append(4)
print(x)               # [1, 2, 3, 4]  <-- x changed too
print(x is y)          # True — one object, two names

# Fix: make an actual copy
x = [1, 2, 3]
y = x.copy()           # or list(x)  or  x[:]
y.append(4)
print(x, y)            # [1, 2, 3] [1, 2, 3, 4]  — independent
print(x is y)          # False

# Note this works here because the members (ints) are immutable.
# With nested lists you'd need copy.deepcopy — see exercise 5.
2 (Easy): Prove that a is b is False but a == b is True for two equal lists. Then find an integer where is gives True and one where it gives False, and explain.
Solution
a = [1]; b = [1]
print(a == b)          # True  — equal value
print(a is b)          # False — distinct objects
print(id(a), id(b))    # two different identities

# Integers: CPython caches -5..256
m = 256; n = 256
print(m is n)          # True  — both names point at the cached 256 object

m = 257; n = 257
print(m is n)          # False — each literal made a fresh object

# Why: CPython pre-allocates small integer objects at startup as an optimisation,
# so every reference to 256 reuses one object. 257 is outside that range.
# This is an IMPLEMENTATION DETAIL — not part of the language. It differs on PyPy
# and can change between CPython versions. Never write logic that depends on it.
# (In a REPL vs a script you may even see different results, because the compiler
#  also folds constants within a single code block.)
3 (Medium): Write a function that takes a list and returns a sorted version without modifying the caller's list. Then write the mutating variant. Show the difference at the call site.
Solution
def sorted_copy(items):
    return sorted(items)          # sorted() BUILDS A NEW list — caller untouched

def sort_in_place(items):
    items.sort()                  # .sort() MUTATES — caller sees it
    return None                   # returning None is the convention that signals mutation

data = [3, 1, 2]

result = sorted_copy(data)
print(data, result)               # [3, 1, 2] [1, 2, 3]   — original intact

sort_in_place(data)
print(data)                       # [1, 2, 3]             — original changed

# The standard library uses this naming convention deliberately:
#   sorted(x) / reversed(x)  -> new object
#   x.sort()  / x.reverse()  -> mutate, return None
# Returning None from a mutator is a FEATURE: it makes `y = x.sort()` obviously
# wrong (y is None) instead of silently giving you an alias you didn't want.
4 (Medium): Fix this function so each call starts with an empty log, and explain in a comment why the original failed. 
def record(msg, log=[]):
    log.append(msg)
    return log
Solution
# The bug: `log=[]` is evaluated ONCE, when `def` executes — not per call.
# That one list is stored on the function object and shared by every call
# that omits `log`, so entries accumulate forever.

def record(msg, log=None):
    if log is None:               # sentinel check — None is immutable, so safe as a default
        log = []                  # fresh list PER CALL (this line runs every call)
    log.append(msg)
    return log

print(record("a"))                # ['a']
print(record("b"))                # ['b']   — independent, as intended
print(record("c", ["existing"]))  # ['existing', 'c']  — caller can still pass one

# Verify the original was hoarding:
def buggy(msg, log=[]):
    log.append(msg); return log
buggy("x"); buggy("y")
print(buggy.__defaults__)         # (['x', 'y'],)  — the shared list, visible

# Why `None` and not, say, `False` or a sentinel object: None is the idiomatic
# "no value supplied" marker, and `is None` can't be fooled by a custom __eq__.
# Use a unique sentinel (_MISSING = object()) only when None is a VALID argument.
5 (Hard): You have config = {"db": {"host": "localhost", "port": 5432}, "debug": False}. Write make_variant that returns a copy with a different db.host, leaving the original completely unchanged. Show that the naive approaches fail.
Solution
import copy

config = {"db": {"host": "localhost", "port": 5432}, "debug": False}

# ❌ Attempt 1: assignment — not a copy at all
bad1 = config
bad1["db"]["host"] = "prod"
# config["db"]["host"] is now "prod" — same object

# ❌ Attempt 2: shallow copy — new OUTER dict, SAME inner dict
config = {"db": {"host": "localhost", "port": 5432}, "debug": False}
bad2 = config.copy()
bad2["db"]["host"] = "prod"
print(config["db"]["host"])       # 'prod'  <-- still leaked!
# The outer dict is new, so bad2["debug"] = True would be safe.
# But config["db"] and bad2["db"] are ONE object — nesting defeats shallow copy.

# ✅ Correct: deep copy
def make_variant(cfg, host):
    new = copy.deepcopy(cfg)      # recursively copies nested containers
    new["db"]["host"] = host
    return new

config = {"db": {"host": "localhost", "port": 5432}, "debug": False}
prod = make_variant(config, "prod.example.com")
print(config["db"]["host"])       # 'localhost'  — untouched
print(prod["db"]["host"])         # 'prod.example.com'

# ✅ Cheaper alternative when you know the shape — copy only the branch you change.
# deepcopy walks EVERYTHING; here only "db" needs isolating:
def make_variant_cheap(cfg, host):
    return {**cfg, "db": {**cfg["db"], "host": host}}
# One level of ** per nesting level you're modifying. O(size of that branch)
# instead of O(whole config), and it can't trip over unpicklable members
# (file handles, connections, locks) the way deepcopy can.
6 (Hard): A teammate proposes making all shared application state deeply immutable to eliminate mutation bugs. Evaluate the proposal: where does it genuinely help, where does it cost, and what would you actually do?
Solution
# Where immutability GENUINELY helps — take these:
#
# 1. Configuration. Read constantly, written once at startup. A frozen dataclass
#    turns "some module mutated config at import time" from a heisenbug into an
#    exception at the offending line. Near-zero cost, high payoff.
#
# 2. Anything crossing a thread boundary. Immutable objects need no lock — the
#    whole class of read-decide-write races disappears rather than being managed.
#
# 3. Dict keys / set members / cache keys. Not a style choice: mutable objects
#    are unhashable, so immutability is REQUIRED, not merely preferred.
#
# 4. Domain values — Money, Point, DateRange. If two instances with equal fields
#    are interchangeable, it's a value, and values should be frozen.

from dataclasses import dataclass, replace

@dataclass(frozen=True)
class DbConfig:
    host: str
    port: int = 5432

cfg = DbConfig("localhost")
# cfg.host = "prod"          # FrozenInstanceError — fails loudly, at the write
prod = replace(cfg, host="prod.example.com")   # derive instead of mutate

# Where it COSTS — push back here:
#
# 1. Accumulation in loops. Rebuilding a container per iteration turns O(n) into
#    O(n^2). Build with a local mutable list, freeze at the boundary:
#        rows = []                     # mutable, but LOCAL — no sharing, no risk
#        for r in source: rows.append(transform(r))
#        return tuple(rows)            # immutable at the edge
#
# 2. Genuinely mutable domain concepts. A connection pool, a running counter,
#    an LRU cache — these ARE state. Modelling them as immutable means threading
#    a "new world" object through every call, which is a real readability cost
#    Python's idioms don't support well (unlike Clojure/Haskell).
#
# 3. Large objects. Copy-on-write of a 100MB structure to change one field is a
#    memory and latency problem, not a safety win.

# WHAT I'D ACTUALLY DO — the distinction that matters is SHARED vs LOCAL,
# not mutable vs immutable:
#
#   - Freeze what is SHARED and long-lived (config, domain values, anything
#     crossing threads or module boundaries). This is where bugs actually come from.
#   - Leave LOCAL, short-lived mutation alone. A list built inside one function
#     and returned has no aliasing exposure — no other name can reach it.
#   - Freeze at the BOUNDARY: mutate freely inside a function, return an
#     immutable value. Best of both — no perf penalty, no shared-state bugs.
#
# So: adopt the proposal for shared state, reject it as a blanket rule.
# "All state immutable" is a solution aimed at the wrong variable — the bugs
# come from SHARING, and mutation is only dangerous because sharing makes it
# visible. Fix the sharing and most of the mutation stops mattering.

🎯 Key Takeaways

  • Variables are names bound to objects; = moves a label and never copies — this single model explains aliasing, argument passing, and copying.
  • Mutation is visible to every name bound to the object; rebinding is visible only locally. That's the whole of "pass by assignment".
  • is = identity, == = value. Use is only for None/True/False; small-int interning makes it a trap elsewhere.
  • Never use a mutable default argument — defaults evaluate once at def time. Use None as the sentinel.
  • Shallow copy duplicates the outer container only; nested mutables stay shared. deepcopy fixes it but is expensive — often the better fix is to stop mutating.
  • Strong + dynamic: no implicit coercion (convert explicitly), but type errors land at runtime — buy the check back with hints + mypy and tests.
  • Mutable (list/dict/set) vs immutable (int/str/tuple/frozenset); hashable requires immutable all the way down.
  • f-strings for formatting, Decimal or integer cents for money, math.isclose for float comparison, PEP 8 via ruff.
