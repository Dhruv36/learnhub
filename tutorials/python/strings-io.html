Strings, Files & I/O Basics

What you'll master: why string immutability turns an innocent loop into quadratic work, the format mini-language well enough to stop reaching for manual padding, the difference between str and bytes and where exactly the boundary sits, why every open() without encoding= is a latent production bug, streaming large files in constant memory, pathlib over string surgery, and the atomic-write pattern that keeps a crash from truncating a file to zero bytes. Prerequisites: Syntax, Types & Variables and Data Structures.

Part 1 — Strings Are Immutable Unicode

# A str is an immutable sequence of Unicode CODE POINTS. Every method that
# looks like it edits a string actually returns a new one.

s = "  Hello, World  "
s.strip()                 # "Hello, World"  — s itself is unchanged
s.upper()                 # "  HELLO, WORLD  "
s.replace("l", "L")       # a NEW string

s.strip()
print(s)                  # "  Hello, World  " — the result was thrown away
s = s.strip()             # ✓ rebind to keep it

# ── THE COST OF IMMUTABILITY ─────────────────────────────────────────────
# Because a str can never be edited in place, += must allocate a new buffer
# and copy everything accumulated so far.

out = ""
for piece in pieces:          # n pieces
    out += piece              # copies the whole accumulated string EACH time
# Total work: 1 + 2 + 3 + ... + n characters copied = O(n²)

out = "".join(pieces)         # ✓ measures the total, allocates ONCE, copies once
# O(n). For 100,000 short pieces this is the difference between ~4 seconds
# and ~5 milliseconds.

# When the pieces are produced incrementally rather than sitting in a list:
import io
buf = io.StringIO()
for piece in pieces:
    buf.write(piece)          # amortised O(1) — a growable buffer, like a list
out = buf.getvalue()

# CPython has an optimisation that sometimes makes += on strings look fast:
# if the string has a refcount of exactly 1 it may resize in place. Never
# rely on it — it disappears the moment anything else holds a reference, and
# it does not exist in PyPy or other implementations.

# ── SEARCHING AND SPLITTING ──────────────────────────────────────────────
"World" in s              # membership — the idiomatic test
s.find("o")               # index, or -1 if absent
s.index("o")              # index, or raises ValueError
s.count("l")              # non-overlapping occurrences

"a,b,c".split(",")        # ['a', 'b', 'c']
"a b  c".split()          # ['a', 'b', 'c'] — no argument splits on ANY run
                          # of whitespace and drops empties. Different rule!
"a,b,c".split(",", 1)     # ['a', 'b,c'] — maxsplit, useful for "key=value"
"k=v=w".partition("=")    # ('k', '=', 'v=w') — always a 3-tuple, no IndexError
text.splitlines()         # splits on \n, \r\n, and other Unicode line breaks

# ── REMOVING PREFIXES AND SUFFIXES ───────────────────────────────────────
name = "test_user_01"
name.lstrip("test_")      # "ser_01"  ← ✗ NOT what you wanted
# strip/lstrip/rstrip take a SET OF CHARACTERS, not a prefix. It removed
# every leading character that appears in "test_": t, e, s, _ ... including
# the 'u'? No — it stopped at 'u'. Here it ate "test_" then 's'? Read it as:
# strip characters from the set {t,e,s,_} until one is not in the set.

name.removeprefix("test_")   # "user_01"  ✓ exact prefix, Python 3.9+
name.removesuffix("_01")     # "test_user"

Part 2 — Formatting with the Mini-Language

name, pi, n, ratio = "Ada", 3.14159, 1234567, 0.4271

f"{name}"                 # 'Ada'                 — the default
f"{name!r}"               # "'Ada'"               — repr(), for debugging
f"{pi = }"                # 'pi = 3.14159'        — self-documenting, 3.8+

# ── ALIGNMENT: fill, align, width ────────────────────────────────────────
f"{name:>10}"             # '       Ada'   right
f"{name:<10}"             # 'Ada       '   left  (default for str)
f"{name:^10}"             # '   Ada    '   centre
f"{name:*^10}"            # '***Ada****'   fill character before the align

# ── NUMBERS ──────────────────────────────────────────────────────────────
f"{pi:.2f}"               # '3.14'         fixed point, 2 decimals
f"{n:,}"                  # '1,234,567'    thousands separator
f"{n:_}"                  # '1_234_567'
f"{ratio:.1%}"            # '42.7%'        multiplies by 100 and adds %
f"{pi:08.3f}"             # '0003.142'     zero-padded to width 8
f"{255:x}"  f"{255:#x}"   # 'ff'  '0xff'   hex; also b (binary), o (octal)
f"{n:.2e}"                # '1.23e+06'     scientific
f"{-5:+d}"  f"{5:+d}"     # '-5'  '+5'     always show the sign

# Right-align numbers, left-align text — that is what a column of figures
# needs, and it is the default for each type.
for item, qty, cost in rows:
    print(f"{item:<20}{qty:>5}{cost:>10.2f}")

# ── NESTED FIELDS: width and precision computed at runtime ───────────────
width = max(len(r.name) for r in rows)
for r in rows:
    print(f"{r.name:<{width}}  {r.value:.{places}f}")

# ── DATES ────────────────────────────────────────────────────────────────
from datetime import datetime
now = datetime.now()
f"{now:%Y-%m-%d %H:%M:%S}"     # the format spec is passed to __format__,
                               # which for datetime means strftime

# ── WHEN NOT TO USE AN F-STRING ──────────────────────────────────────────
logger.info(f"Processing {user_id}")   # ✗ formats even if INFO is disabled
logger.info("Processing %s", user_id)  # ✓ lazy — only formats if emitted

cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")   # ✗ SQL INJECTION
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))  # ✓ parameters
# The database driver escapes the value. String formatting never does.

Part 3 — str vs bytes, and the Encoding Boundary

# str   = TEXT.  A sequence of Unicode code points. What your program thinks in.
# bytes = DATA.  A sequence of 0-255 octets. What files, sockets and pipes carry.
#
# They do not mix. There is no implicit conversion. You cross the boundary
# explicitly, and you choose the encoding when you do.

"café".encode("utf-8")            # b'caf\xc3\xa9'   str → bytes
b"caf\xc3\xa9".decode("utf-8")    # 'café'           bytes → str

len("café")                       # 4   — four characters
len("café".encode("utf-8"))       # 5   — é needs two bytes in UTF-8

"café" + b"x"                     # ✗ TypeError — and that is a good thing

# ── THE MENTAL MODEL: DECODE AT THE EDGE, ENCODE AT THE EDGE ─────────────
#
#   [file / socket / stdin]  --bytes-->  decode  -->  [ str: your logic ]
#   [ str: your logic ]      --encode-->  bytes  -->  [file / socket / stdout]
#
# Everything in between is str. Programs that pass bytes deep into their
# logic end up with .decode() calls scattered through the codebase and
# TypeErrors in the paths nobody tested.

# ── WHY UnicodeDecodeError HAPPENS ───────────────────────────────────────
# Not every byte sequence is valid UTF-8. Decoding bytes that were encoded
# as something else (or that are not text at all) raises:
b"\xff\xfe".decode("utf-8")
# UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 0

# The error is almost always a WRONG ASSUMPTION about the encoding, not
# corrupt data. Find out what produced the bytes.

# Error handlers, when you genuinely cannot control the input:
data.decode("utf-8", errors="replace")   # bad bytes → U+FFFD  (lossy, visible)
data.decode("utf-8", errors="ignore")    # bad bytes dropped   (lossy, SILENT)
data.decode("utf-8", errors="strict")    # the default — raise
# Prefer "replace" over "ignore": you can see the damage in the output.

# ── MOJIBAKE ─────────────────────────────────────────────────────────────
# "café" written as UTF-8, then read back as cp1252, gives "cafÃ©".
# Two bytes were decoded as two separate Latin-1 characters. No error was
# raised, because those bytes are valid cp1252 — they just mean something
# else. This is why silence is worse than UnicodeDecodeError.

# ── LENGTH IS NOT WHAT USERS SEE ─────────────────────────────────────────
s = "é"                  # can be ONE code point (U+00E9) or TWO (e + U+0301)
len("café")              # 4 or 5 depending on how it was typed
import unicodedata
unicodedata.normalize("NFC", s)   # compose  — use before comparing or storing
unicodedata.normalize("NFD", s)   # decompose
# Two strings that look identical can compare unequal. Normalise user input
# (usernames, search terms, dedup keys) to NFC at the boundary.
Key insight: almost every text bug in production is the same bug — an encoding that was assumed instead of stated. open() without encoding= does not mean "UTF-8"; it means "whatever this machine's locale says", which is UTF-8 on the developer's Mac and cp1252 on a Windows server. The code passes review, passes tests, and fails on the first customer name containing an accent. Write the encoding down every single time, at every boundary, and this entire category of failure disappears.

Part 4 — Files: with, Modes, and Streaming

# ── ALWAYS `with` ────────────────────────────────────────────────────────
f = open("data.txt")
process(f)
f.close()               # ✗ never runs if process() raises → leaked handle,
                        #   and on write, buffered data is never flushed

with open("data.txt", encoding="utf-8") as f:
    process(f)          # ✓ closed on the way out, exception or not

# `with` calls f.__exit__() on any exit path. That is a context manager;
# the mechanism is covered in Decorators & Context Managers.

# ── MODES ────────────────────────────────────────────────────────────────
#   "r"   read           (default)  — FileNotFoundError if missing
#   "w"   write          — TRUNCATES an existing file to zero bytes IMMEDIATELY
#   "a"   append         — writes always go to the end
#   "x"   exclusive create — FileExistsError if it exists (no silent clobber)
#   "r+"  read and write, no truncation
#   add "b" for binary:  "rb", "wb" — no encoding, no newline translation
#
# open("out.txt", "w") truncates the file the moment it is called, before
# you have written anything. A crash between open and write leaves nothing.
# See the atomic-write pattern in Part 6.

# ── STREAMING: CONSTANT MEMORY ───────────────────────────────────────────
with open("huge.log", encoding="utf-8") as f:
    content = f.read()             # ✗ whole file into RAM — 8 GB log, 8 GB RSS
    lines = f.readlines()          # ✗ same, plus a list object per line

with open("huge.log", encoding="utf-8") as f:
    for line in f:                 # ✓ the file object IS an iterator
        if "ERROR" in line:        #   one buffered chunk at a time
            handle(line.rstrip("\n"))
# Memory stays flat regardless of file size. This works for a 4 KB file and
# a 400 GB file with identical code.

# Counting without building anything:
with open("huge.log", encoding="utf-8") as f:
    errors = sum(1 for line in f if "ERROR" in line)

# ── NEWLINES ─────────────────────────────────────────────────────────────
# In text mode Python translates \r\n to \n on read and \n to os.linesep on
# write. That is usually what you want — but for csv it is not:
import csv
with open("out.csv", "w", newline="", encoding="utf-8") as f:
    writer = csv.writer(f)         # newline="" disables translation so csv
    writer.writerow(["a", "b"])    # can control line endings itself.
# Without newline="" you get a blank line between every row on Windows.

# ── STRUCTURED FORMATS: USE THE STDLIB ───────────────────────────────────
import json
with open("config.json", encoding="utf-8") as f:
    config = json.load(f)                     # from a file object
config = json.loads(text)                     # from a str

with open("out.json", "w", encoding="utf-8") as f:
    json.dump(obj, f, indent=2, ensure_ascii=False)
# ensure_ascii=False keeps "café" as café instead of "café" — smaller
# and readable. The file is UTF-8, so it is safe.

with open("in.csv", encoding="utf-8", newline="") as f:
    for row in csv.DictReader(f):             # row is a dict keyed by header
        print(row["email"])
# Never split CSV by hand: values may contain commas, quotes and newlines
# inside quoted fields. line.split(",") is wrong on real data.

from pathlib import Path

# os.path is string surgery. pathlib is an object that knows it is a path.
p = Path("data") / "2026" / "users.csv"     # / joins, correctly per OS
p.exists()  p.is_file()  p.is_dir()
p.name        # 'users.csv'

text = p.read_text(encoding="utf-8")

raw  = p.read_bytes()
# Convenient for small files. For large ones, stream with `with p.open()`.

# Building a new name without string slicing:
p.with_suffix(".json")          # data/2026/users.json
p.with_stem("customers")        # data/2026/customers.csv   (3.9+)

# Directories:
Path("out/reports").mkdir(parents=True, exist_ok=True)
# parents=True creates intermediates; exist_ok=True makes it idempotent, so
# no race between "if not exists" and "mkdir".

for csv_file in Path("data").glob("*.csv"):        # this directory
    ...
for csv_file in Path("data").rglob("*.csv"):       # recursive
    ...

p.unlink(missing_ok=True)       # delete a file, no error if already gone
p.rename(target)                # atomic on the same filesystem

# ── TEMPORARY FILES ──────────────────────────────────────────────────────
import tempfile
with tempfile.TemporaryDirectory() as tmp:
    scratch = Path(tmp) / "work.json"
    scratch.write_text("{}", encoding="utf-8")

Part 6 — Writing Files Safely

# ── THE PROBLEM ──────────────────────────────────────────────────────────
with open("config.json", "w", encoding="utf-8") as f:
    json.dump(config, f, indent=2)
# "w" truncated config.json to zero bytes at open(). If the process is
# killed, the disk fills, or json.dump raises on a non-serialisable value,
# the file is now empty or half-written. The old good copy is gone.
#
# This is how a deploy takes out a service: the config file survives every
# test because nothing crashes in the middle during a test.

# ── THE FIX: WRITE ELSEWHERE, THEN RENAME ────────────────────────────────
import os, json, tempfile
from pathlib import Path

def write_atomic(path: Path, data: str) -> None:
    """Write data to path so readers see either the old file or the new one."""
    tmp = path.with_suffix(path.suffix + ".tmp")
    with open(tmp, "w", encoding="utf-8") as f:
        f.write(data)
        f.flush()                # push Python's buffer to the OS
        os.fsync(f.fileno())     # push the OS cache to the physical disk
    os.replace(tmp, path)        # ATOMIC on POSIX and Windows
# os.replace() either fully succeeds or does not happen. A reader at any
# instant sees a complete file — the old one or the new one, never a partial.
#
# Why the temp file must be in the SAME DIRECTORY: rename is only atomic
# within a filesystem. A temp in /tmp may be on a different mount, in which
# case os.replace copies, which is exactly the non-atomic operation you were
# avoiding.
#
# Why fsync: without it, os.replace can complete while the new file's
# CONTENTS are still in the OS write cache. A power loss then leaves an
# empty file with the right name. For durability that matters, fsync the
# containing directory too.

write_atomic(Path("config.json"), json.dumps(config, indent=2))

# ── DO NOT CLOBBER WHAT YOU DID NOT MEAN TO ──────────────────────────────
with open(dest, "x", encoding="utf-8") as f:      # exclusive create
    f.write(data)
# FileExistsError instead of silently destroying dest. Use "x" whenever the
# file is not supposed to exist yet — export jobs, generated artefacts.

# ── ENCODING ON WRITE ────────────────────────────────────────────────────
p.write_text(data)                        # ✗ locale encoding again
p.write_text(data, encoding="utf-8")      # ✓
# Python 3.15 makes UTF-8 the default. Until every environment you deploy to
# is on that version, state it explicitly — and keep stating it, because the
# code is clearer for it.

Interview Questions

Beginner: Why is with open(...) preferred over calling close() yourself?

A file object is a context manager: with guarantees its __exit__ runs on every exit path, including an exception, a return from inside the block, or a break. A manual close() on the following line is skipped entirely if anything in between raises, which leaks the file descriptor. On writes it is worse than a leak — Python buffers output, so data that was never flushed is simply lost, and the file on disk is truncated or incomplete. You could get the same guarantee with try/finally, and that is exactly what with compiles down to; it is the shorter, harder-to-forget spelling of the same thing. The pattern generalises to any resource with a lifetime — locks, database transactions, network connections — which is why learning it on files pays off everywhere else.

Beginner: Explain the difference between str and bytes.

str is text: a sequence of Unicode code points, which is what your program should reason about. bytes is data: a sequence of integers from 0 to 255, which is what files, sockets, and pipes actually carry. Converting between them requires an encoding — encode() turns text into bytes, decode() turns bytes back into text — and Python deliberately refuses to do it implicitly, so "a" + b"b" is a TypeError rather than a guess. The practical rule is to decode as early as possible when data enters the program and encode as late as possible when it leaves, keeping everything in between as str. A useful demonstration that they are genuinely different: len("café") is 4 characters, while len("café".encode("utf-8")) is 5 bytes, because é takes two bytes in UTF-8.

Mid: Why is repeated string concatenation slow, and what should you use instead?

Strings are immutable, so out += piece cannot extend the existing buffer — it must allocate a new string large enough for both parts and copy the whole accumulated result into it. Over n pieces that copies 1 + 2 + 3 + ... + n characters, which is O(n²). The fix is "".join(pieces): join walks the sequence once to compute the total length, allocates a single buffer, and copies each piece exactly once, giving O(n). When the pieces are produced incrementally rather than already collected, io.StringIO gives the same amortised behaviour with a write() interface. It is worth knowing that CPython has an optimisation that can resize a string in place when its reference count is exactly 1, which makes naive += loops look acceptable in a quick benchmark — but it silently stops applying the moment any other reference exists, and it does not exist in other Python implementations, so it is not something to design around. The scale of the difference is large: joining 100,000 short pieces is roughly milliseconds, while += is roughly seconds.

Mid: A file reads correctly on your laptop and raises UnicodeDecodeError in production. What happened?

The open() call almost certainly omitted encoding=, so Python fell back to locale.getpreferredencoding() — the platform default. On a modern macOS or Linux developer machine that is UTF-8, so the file decodes fine; on a Windows server, or a container with a C/POSIX locale, it can be cp1252 or ASCII, and any byte sequence that is not valid in that encoding raises. The fix is to pass encoding="utf-8" explicitly at every open(), which makes behaviour identical everywhere. It is worth stressing that the crash is the good outcome: the same mismatch in the other direction, where the bytes happen to be valid in the wrong encoding, produces mojibake such as cafÃ© with no error at all, and that corruption then gets written to a database where it is far more expensive to discover. If the input encoding genuinely cannot be controlled, decode with errors="replace" so the damage is visible in the output rather than errors="ignore", which deletes characters silently.

Senior: How do you write a file so that a crash mid-write cannot leave it corrupt?

Never write in place. Opening the destination with "w" truncates it to zero bytes at the moment of the call, before a single byte is written, so any failure after that — a crash, a full disk, an exception while serialising — leaves the file empty or half-written, and the previous good copy is already gone. The pattern is write-then-rename: serialise into a temporary file, then os.replace(tmp, path). On both POSIX and Windows os.replace is atomic, so a concurrent reader at any instant sees either the complete old file or the complete new one, never a partial state.

Two details decide whether this actually works. First, the temporary file must live in the same directory as the destination. Rename is only atomic within a single filesystem; if the temp file is in /tmp and that is a different mount, os.replace degrades to a copy followed by a delete, which is precisely the non-atomic operation you were trying to avoid. Second, atomicity of the rename is not the same as durability of the contents. After f.write() the data may sit in Python's buffer, and after f.flush() it may still sit in the OS page cache. If the machine loses power after the rename but before the cache is written back, you can end up with the new filename and empty contents. Calling f.flush() and then os.fsync(f.fileno()) before the replace closes that window; for full durability of the directory entry itself you would also fsync the containing directory.

The related habit is to use mode "x" — exclusive create — whenever a file is not supposed to exist yet, such as an export or a generated artefact. It raises FileExistsError instead of silently destroying whatever was there, turning a data-loss bug into an immediate, obvious failure.

Senior: You need to process a 50 GB CSV on a machine with 8 GB of RAM. How?

Stream it. A Python file object is already an iterator over lines, so for line in f reads one buffered chunk at a time and memory stays flat regardless of file size; the same applies to csv.reader(f) and csv.DictReader(f), which wrap the file object rather than consuming it. What must be avoided is anything that materialises the whole thing: f.read(), f.readlines(), list(reader), or a pandas read_csv without chunksize. The same discipline has to hold for the results — accumulating a Python object per row rebuilds the memory problem one step later, so aggregate as you go with a counter, a running total, or a heapq.nlargest for top-N rather than sorting everything.

If the work per row is genuinely independent and CPU-bound, the file can be split by byte offset and processed by a pool of worker processes, taking care to align the split points to line boundaries. But the honest first question is whether this belongs in Python at all: if the operation is a filter, an aggregation, or a join, loading the file into DuckDB or SQLite and expressing it as SQL is usually both faster and less code, because those engines already handle spilling to disk and parallel scans. Reaching for a database is not an admission of defeat here — it is the same reasoning that says use the csv module rather than split(","), one level up.

One practical detail that bites people at this scale: pass encoding="utf-8" and decide up front what to do about malformed rows. In a 50 GB file there will be some, and a job that dies on row 40 million after four hours because of one bad byte is far more expensive than one that logs the row and continues.

# ✗ BEFORE — the file is destroyed before anything is written:
def save(path, config):
    with open(path, "w", encoding="utf-8") as f:
        json.dump(config, f, indent=2)
# "w" truncates at open(). If json.dump raises on a non-serialisable value
# (a datetime, a set, a Decimal), the file is now zero bytes and the old
# config is gone.

# ✓ AFTER — serialise first, then write elsewhere, then rename:
import json, os
from pathlib import Path

def save(path: Path, config: dict) -> None:
    data = json.dumps(config, indent=2, ensure_ascii=False)   # may raise —
                                                              # before we
                                                              # touch the file
    tmp = path.with_suffix(path.suffix + ".tmp")
    with open(tmp, "w", encoding="utf-8") as f:
        f.write(data)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp, path)          # atomic

# Three separate protections, and each one covers a different failure:
#
# 1. json.dumps() BEFORE opening anything. A serialisation error now leaves
#    the original file completely untouched.
# 2. Writing to path + ".tmp" — in the SAME DIRECTORY, so os.replace is a
#    real rename and not a cross-filesystem copy.
# 3. flush + fsync before the replace, so the rename cannot complete while
#    the contents are still only in the OS cache.

# Leftover .tmp files after a hard kill are harmless and get overwritten on
# the next run. If that is untidy, tempfile.NamedTemporaryFile(dir=path.parent,
# delete=False) gives unique names, at the cost of needing cleanup.

6 (hard): Design the I/O for a job that reads a 30 GB gzipped JSON-lines export, filters it, and writes a report — restartable after a crash.
Solution 
import gzip, json, os
from pathlib import Path

# ── READING: STREAM, DECOMPRESSING AS YOU GO ─────────────────────────────
# gzip.open in text mode decompresses and decodes incrementally. Never
# decompress to a temp file first — that needs 30 GB of disk for nothing.

def records(path: Path):
    with gzip.open(path, "rt", encoding="utf-8") as f:   # "rt" = text mode
        for lineno, line in enumerate(f, 1):
            line = line.strip()
            if not line:
                continue
            try:
                yield lineno, json.loads(line)
            except json.JSONDecodeError as e:
                # A 30 GB export WILL contain malformed rows. Dying on row
                # 40,000,000 after three hours is the expensive outcome.
                log.warning("bad json at line %s: %s", lineno, e)

# A generator, so the caller drives it and nothing accumulates.

# ── WRITING: STREAM OUT TOO, AND MAKE IT ATOMIC ──────────────────────────
def run(src: Path, dest: Path, start_line: int = 0) -> None:
    tmp = dest.with_suffix(dest.suffix + ".partial")
    ckpt = dest.with_suffix(".checkpoint")

    mode = "a" if start_line else "w"
    with open(tmp, mode, encoding="utf-8", newline="") as out:
        for lineno, rec in records(src):
            if lineno <= start_line:      # already processed — skip
                continue
            if not keep(rec):
                continue
            out.write(json.dumps(transform(rec)) + "\n")

            if lineno % 100_000 == 0:
                out.flush()
                os.fsync(out.fileno())            # data is durable...
                ckpt.write_text(str(lineno))      # ...before the checkpoint
                                                  # records it. Order matters.
    os.replace(tmp, dest)
    ckpt.unlink(missing_ok=True)

# ── RESTART ──────────────────────────────────────────────────────────────
start = int(ckpt.read_text()) if ckpt.exists() else 0
run(src, dest, start_line=start)

# The design decisions, and why each one:
#
# STREAM BOTH ENDS      Peak memory is one record. The job runs the same on
#                       30 GB as on 30 MB, which also means it is testable
#                       on a small fixture.
#
# CHECKPOINT AFTER      fsync THEN write the checkpoint. Reversed, a crash
# FSYNC                 between the two makes the job skip records it never
#                       actually durably wrote — silent data loss.
#
# .partial + replace    A reader never sees a half-written report. The
#                       partial file surviving a crash is what makes resume
#                       possible, so it is deliberately not deleted.
#
# TOLERATE BAD ROWS     Log and continue. Count them, and fail the job at
#                       the end if the rate exceeds a threshold — that
#                       distinguishes "a few bad rows" from "wrong file".
#
# LINE NUMBERS AS       Works because the input is append-only and immutable.
# THE CURSOR            For a mutable source, checkpoint a record id instead.
#
# What this deliberately does NOT do: parallelise. Gzip cannot be split at
# arbitrary offsets, so parallel reads mean re-decompressing from the start.
# If the CPU is the bottleneck, re-export the source as multiple files or a
# splittable format (bgzip, parquet) and parallelise across files — a
# pipeline change, not a code change.

🎯 Key Takeaways

  • Strings are immutable, so += in a loop is O(n²) — use "".join() or io.StringIO.
  • str is text, bytes is data; decode at the edge on the way in, encode at the edge on the way out, keep str in between.
  • Pass encoding="utf-8" at every boundary; the platform default differs between your laptop and the server.
  • A UnicodeDecodeError is the good outcome — the same mismatch can silently produce mojibake instead.
  • Always use with: it closes and flushes on every exit path, including exceptions.
  • A file object is an iterator, so for line in f holds memory flat on a file of any size.
  • Mode "w" truncates at open(), before you write anything — write to a temp file in the same directory and os.replace.
  • os.replace gives atomicity; flush plus fsync before it gives durability. They are separate problems.
  • Use csv and json rather than splitting by hand, and pass newline="" when opening files for csv.
  • Normalise Unicode with NFC and compare with casefold() before using text as a key or a uniqueness check.
