OOP & Dataclasses Intermediate

What you'll master: how attribute lookup actually resolves and why a mutable class attribute is shared by every instance, the dunder protocols that wire a class into language syntax, @dataclass including slots and frozen and what each buys, super() and the MRO well enough to reason about a diamond, @property and descriptors, why __eq__ without __hash__ breaks sets, and the concrete point at which inheritance should become composition. Prerequisites: Data Structures and Control Flow & Functions.

Part 1 — Classes, Attributes, and Where They Live

class Account:
    interest_rate = 0.02              # CLASS attribute — ONE object, shared

    def __init__(self, owner, balance=0):
        self.owner = owner            # INSTANCE attributes — one per object
        self._balance = balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("amount must be positive")
        self._balance += amount

# ── ATTRIBUTE LOOKUP ORDER ───────────────────────────────────────────────
# a.x searches, in order:
#   1. the instance __dict__          a.__dict__
#   2. the class __dict__, then every class in the MRO
#   3. __getattr__ , if defined       (the fallback hook)
# Assignment ALWAYS writes to the instance, never to the class.

a = Account("ada")
a.interest_rate                  # 0.02 — not in a.__dict__, found on the class
a.interest_rate = 0.05           # creates an INSTANCE attribute that shadows it
Account.interest_rate            # still 0.02 — the class was not touched
Account.interest_rate = 0.03     # this changes it for every instance that
                                 # has not shadowed it

# ── THE MUTABLE CLASS ATTRIBUTE TRAP ─────────────────────────────────────
class Cart:
    items = []                   # ✗ ONE list, shared by every Cart ever made

    def add(self, item):
        self.items.append(item)  # MUTATES the shared class attribute —
                                 # no assignment happens, so no instance
                                 # attribute is created to shadow it

c1, c2 = Cart(), Cart()
c1.add("book")
c2.items                         # ['book']  ← c2 sees c1's item

class Cart:
    def __init__(self):
        self.items = []          # ✓ a fresh list per instance
# Same root cause as the mutable default argument: the class body runs ONCE,
# at import time. Anything created there is created once.

# ── self IS JUST THE FIRST ARGUMENT ──────────────────────────────────────
a.deposit(100)                   # is exactly:
Account.deposit(a, 100)          # Python passes the instance for you
# There is nothing magic about the name "self" — it is a convention that
# every reader relies on, so never rename it.

# ── PRIVACY IS A CONVENTION ──────────────────────────────────────────────
self._balance                    # "internal, do not touch" — enforced by
                                 # nothing but agreement and linters
self.__token                     # NAME MANGLING → self._Account__token
# The double underscore is not access control. Its actual purpose is to stop
# a subclass accidentally colliding with a base class's attribute. It is
# still reachable as a._Account__token, and choosing it for "security" is a
# misunderstanding.

Part 2 — Dunder Methods: Wiring Into the Language

# "Pythonic" mostly means: implement the protocol the syntax already uses,
# instead of inventing a method name of your own.

class Money:
    def __init__(self, cents, currency="USD"):
        self.cents, self.currency = cents, currency

    def __repr__(self):                     # for DEVELOPERS — unambiguous
        return f"Money({self.cents}, {self.currency!r})"

    def __str__(self):                      # for USERS — readable
        return f"${self.cents / 100:.2f}"

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented           # ← not False. Lets the OTHER
                                            #   operand try, and makes
                                            #   Money(1) == 1 return False
                                            #   rather than crash.
        return (self.cents, self.currency) == (other.cents, other.currency)

    def __hash__(self):                     # REQUIRED alongside __eq__ if
        return hash((self.cents, self.currency))   # the object goes in a set

    def __add__(self, other):
        if self.currency != other.currency:
            raise ValueError("currency mismatch")
        return Money(self.cents + other.cents, self.currency)

    def __lt__(self, other):                # < ; @total_ordering fills the rest
        return self.cents < other.cents

    def __bool__(self):                     # truthiness; falls back to __len__
        return self.cents != 0

# ── repr vs str ──────────────────────────────────────────────────────────
print(m)          # __str__   → $12.50
m                 # __repr__  → Money(1250, 'USD')     (REPL, logs, lists)
[m]               # containers ALWAYS use __repr__ of their elements
# If you define only one, define __repr__ — str falls back to it, not the
# other way round. A class with no __repr__ logs as <Money object at 0x7f…>,
# which makes production debugging materially harder.

# ── THE PROTOCOLS WORTH KNOWING ──────────────────────────────────────────
#   __len__               len(x)              also makes empty x falsy
#   __getitem__           x[k]                and legacy iteration
#   __setitem__ __delitem__   x[k] = v, del x[k]
#   __contains__          k in x              (falls back to __iter__)
#   __iter__ __next__     for                 → Comprehensions & Generators
#   __enter__ __exit__    with                → Decorators & Context Managers
#   __call__              x()                 makes an instance callable
#   __getattr__           fallback for MISSING attributes only
#   __format__            f"{x:spec}"

class Inventory:
    def __init__(self):
        self._items = {}
    def __len__(self):     return len(self._items)
    def __getitem__(self, k): return self._items[k]
    def __contains__(self, k): return k in self._items
    def __iter__(self):    return iter(self._items)

inv = Inventory()
len(inv);  inv["sku1"];  "sku1" in inv;  [k for k in inv]
if not inv:                # __len__ == 0 → falsy. No .is_empty() needed.
    ...

Part 3 — @dataclass

from dataclasses import dataclass, field, asdict, replace

@dataclass
class Point:
    x: float
    y: float
    label: str = "origin"           # defaults come last, as in any signature

# Generated for free: __init__, __repr__, __eq__.
Point(1.0, 2.0) == Point(1.0, 2.0)      # True — field-by-field comparison
# The equivalent hand-written class is about 15 lines, all of which are
# places to make a typo when a field is added.

# ── MUTABLE DEFAULTS ─────────────────────────────────────────────────────
@dataclass
class Order:
    items: list[str] = []                     # ✗ ValueError at CLASS
                                              #   DEFINITION time — dataclass
                                              #   catches this for you
    items: list[str] = field(default_factory=list)   # ✓ called per instance

# ── frozen=True ──────────────────────────────────────────────────────────
@dataclass(frozen=True)
class Config:
    host: str
    port: int

c = Config("db", 5432)
c.port = 5433                    # FrozenInstanceError
# frozen also generates __hash__, so the object works as a dict key or set
# member. That is the practical reason to reach for it: an immutable value
# object that is safe to cache, share between threads, and use as a key.

replace(c, port=5433)            # the way to "change" one: a NEW instance

# ── slots=True ───────────────────────────────────────────────────────────
@dataclass(slots=True)
class Row:
    id: int
    name: str
# No per-instance __dict__: attributes live in a fixed array. Roughly HALF
# the memory and faster attribute access, at the cost of not being able to
# add attributes that were not declared. For a million-row in-memory dataset
# that is the difference between fitting in RAM and not.
#
# Trade-off: no dynamic attributes, and multiple inheritance from two
# slotted classes needs care.

# ── FIELD CONTROL ────────────────────────────────────────────────────────
@dataclass(order=True)                # also generates < <= > >=
class Task:
    priority: int
    name: str = field(compare=False)               # ignored by __eq__/order
    token: str = field(repr=False, default="")     # kept out of __repr__ —
                                                   # use for secrets
    tags: set[str] = field(default_factory=set)
    _cache: dict = field(default_factory=dict, init=False)   # not a
                                                             # constructor arg

    def __post_init__(self):          # runs after the generated __init__ —
        if self.priority < 0:         # the place for validation or derived
            raise ValueError("priority must be >= 0")   # fields

asdict(task)                          # recursive dict, for serialisation

# ── WHEN NOT TO USE A DATACLASS ──────────────────────────────────────────
# Dataclasses do NOT validate types. The annotations are hints; nothing
# checks them at runtime:
Point("not a number", None)           # constructs happily

# At a trust boundary — an HTTP body, a config file, a message queue — that
# is not good enough. Use Pydantic, which validates and coerces at runtime
# (see FastAPI & Production APIs). Rule of thumb:
#   dataclass  → internal, already-trusted data
#   Pydantic   → anything crossing into the program from outside
#
# NamedTuple is the third option: immutable, tuple-compatible, iterable and
# indexable. Prefer a frozen dataclass unless you specifically need the
# tuple behaviour, because indexing a record by position ages badly.
Key insight: the class body executes once, at import time, exactly like a function's default arguments. Every confusing "shared state" bug in Python OOP — the mutable class attribute that leaks between instances, the mutable dataclass default that field(default_factory=...) exists to prevent — is the same fact viewed from a different angle. Instances get their own state only from what runs inside __init__, and reading self.x falls back to the class when the instance has no x of its own, while writing self.x always creates one on the instance.

Part 4 — Inheritance, super(), and the MRO

class Savings(Account):
    def __init__(self, owner, balance=0, rate=0.05):
        super().__init__(owner, balance)      # cooperative — never
                                              # Account.__init__(self, ...)
        self.rate = rate

    def deposit(self, amount):
        super().deposit(amount)               # extend rather than replace
        self._balance += amount * self.rate

# ── super() DOES NOT MEAN "THE PARENT" ───────────────────────────────────
# It means "the next class in the MRO of type(self)", which is not knowable
# from the class you are reading.

class Base:
    def go(self): print("Base")
class A(Base):
    def go(self): print("A"); super().go()
class B(Base):
    def go(self): print("B"); super().go()
class C(A, B):
    pass

C.__mro__      # (C, A, B, Base, object)
C().go()       # A, B, Base
# Inside A.go, super() resolved to B — NOT to Base, even though A's only
# declared base IS Base. The MRO belongs to the instance's class.
# This is what makes cooperative multiple inheritance work: Base.go runs
# exactly ONCE, no matter how many paths reach it in the diamond.

# The C3 linearisation guarantees:
#   - a class always precedes its bases
#   - the order bases were declared in is preserved
#   - each class appears exactly once
class D(B, A): ...     # (D, B, A, Base, object) — declaration order matters
class Bad(A, C): ...   # TypeError at class definition: no consistent MRO

# ── THE RULE FOR COOPERATIVE CLASSES ─────────────────────────────────────
# Every class in the hierarchy must call super() and accept **kwargs, or the
# chain breaks at the first one that does not:
class Mixin:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)      # pass the rest along
        self.extra = True

# ── isinstance, NOT type() ───────────────────────────────────────────────
type(x) == Account       # ✗ False for every subclass
isinstance(x, Account)   # ✓ respects the hierarchy
# The Liskov point in one line: code that special-cases type() is code a
# subclass cannot be substituted into.

# ── ABSTRACT BASE CLASSES ────────────────────────────────────────────────
from abc import ABC, abstractmethod

class Storage(ABC):
    @abstractmethod
    def save(self, key: str, data: bytes) -> None: ...

Storage()                # TypeError — abstract methods must be implemented
# ABCs fail at instantiation rather than at the first call to a missing
# method, which moves the error from production to startup.

Part 5 — Properties and Descriptors

class Temperature:
    def __init__(self, celsius=0.0):
        self._celsius = celsius

    @property
    def celsius(self):                 # read like a field: t.celsius
        return self._celsius

    @celsius.setter
    def celsius(self, value):          # written like a field: t.celsius = 30
        if value < -273.15:
            raise ValueError("below absolute zero")
        self._celsius = value

    @property
    def fahrenheit(self):              # DERIVED — no stored state, cannot
        return self._celsius * 9 / 5 + 32   # go stale

# ── WHY THIS MATTERS: NO PREEMPTIVE GETTERS ──────────────────────────────
# In Java you write getX/setX from the start because switching a public
# field to a method later breaks callers. In Python it does not:
class Circle:
    def __init__(self, r):
        self.radius = r          # start with a plain attribute

class Circle:                    # later, when validation is needed:
    @property
    def radius(self): return self._radius
    @radius.setter
    def radius(self, v):
        if v <= 0: raise ValueError("radius must be positive")
        self._radius = v
# Every c.radius and c.radius = 5 in existing code keeps working unchanged.
# So: expose plain attributes until there is a reason not to. Writing
# get_radius() in Python is importing a workaround for a problem the
# language does not have.

# ── CACHED PROPERTIES ────────────────────────────────────────────────────
from functools import cached_property

class Dataset:
    @cached_property
    def stats(self):                   # computed once, then stored in the
        return expensive_scan(self.rows)   # instance __dict__
# Needs a __dict__, so it does NOT work with slots=True.
# And it never invalidates — only use it when the underlying data is fixed
# for the object's lifetime.

# ── DESCRIPTORS: WHAT @property IS BUILT ON ──────────────────────────────
class Positive:
    def __set_name__(self, owner, name):     # told its own attribute name
        self.name = "_" + name
    def __get__(self, obj, objtype=None):
        if obj is None: return self
        return getattr(obj, self.name)
    def __set__(self, obj, value):
        if value <= 0:
            raise ValueError(f"{self.name} must be positive")
        setattr(obj, self.name, value)

class Product:
    price = Positive()        # the validation is written ONCE
    weight = Positive()       # and reused, unlike two @property pairs

# A descriptor is any object defining __get__/__set__/__delete__; the class
# hands attribute access over to it. Methods, classmethod, staticmethod and
# property are all descriptors. Write one when the SAME access logic repeats
# across several attributes or classes — otherwise @property is clearer.

Part 6 — Composition Over Inheritance

# ── WHERE INHERITANCE GOES WRONG ─────────────────────────────────────────
class Notifier:
    def send(self, msg): ...
class EmailNotifier(Notifier): ...
class RetryingEmailNotifier(EmailNotifier): ...
class RetryingThrottledEmailNotifier(RetryingEmailNotifier): ...
# Now add SMS with retry but not throttling. And Slack with throttling but
# not retry. The hierarchy has to be duplicated per combination — the class
# count grows multiplicatively with the number of orthogonal features.

# ── COMPOSITION: ASSEMBLE, DO NOT DESCEND ────────────────────────────────
class EmailSender:
    def send(self, msg): ...

class Retrying:
    def __init__(self, inner, attempts=3):
        self.inner, self.attempts = inner, attempts
    def send(self, msg):
        for i in range(self.attempts):
            try:
                return self.inner.send(msg)
            except TransientError:
                if i == self.attempts - 1: raise

notifier = Retrying(Throttled(EmailSender()))     # any combination, no new
notifier = Throttled(SmsSender())                 # classes required

# ── DUCK TYPING MAKES THIS FREE ──────────────────────────────────────────
class Order:
    def __init__(self, notifier):      # inject the capability
        self.notifier = notifier
    def place(self):
        self.notifier.send("order placed")

Order(FakeNotifier())      # tests need no mocking framework and no base
                           # class — anything with .send() is acceptable

# To DECLARE the shape without forcing a base class (see Type Hints):
from typing import Protocol
class Notifier(Protocol):
    def send(self, msg: str) -> None: ...
# Structural typing: EmailSender satisfies this without importing it. The
# type checker enforces the contract; runtime stays duck-typed.

# ── THE DECISION RULE ────────────────────────────────────────────────────
# Inherit when the subclass genuinely IS-A base and can substitute for it
# everywhere (Liskov). Compose when you are reaching for inheritance to
# REUSE CODE — that is the tell.
#
# Practical smells that inheritance was the wrong tool:
#   - a subclass overrides a method to raise NotImplementedError
#   - a subclass ignores constructor arguments it inherited
#   - you need a class per combination of two independent features
#   - the base class changes and unrelated subclasses break
#
# Mixins are the middle ground: small, single-purpose, stateless, always
# calling super(). Two or three is a pattern; eight is a hierarchy nobody
# can trace.

Interview Questions

Beginner: What is the difference between a class attribute and an instance attribute?

A class attribute is defined in the class body and exists once, on the class object itself, shared by every instance. An instance attribute is created by assignment on self, normally in __init__, and belongs to that one object. Reading obj.x checks the instance first and falls back to the class, but writing obj.x = 1 always creates or updates an attribute on the instance, which shadows the class one without changing it. The practical consequence is that a mutable class attribute is a bug waiting to happen: items = [] in the class body followed by self.items.append(x) mutates the single shared list rather than assigning, so every instance sees the change. Class attributes are appropriate for genuine constants and shared configuration; anything that represents per-object state belongs in __init__.

Beginner: What does @dataclass generate, and when would you not use one?

It reads the annotated class-level names as fields and generates __init__, __repr__ and __eq__ from them, with options for order=True to add comparisons, frozen=True for immutability plus a generated __hash__, and slots=True to drop the per-instance __dict__ and roughly halve memory usage. That removes the boilerplate where field lists drift out of sync — the classic bug of adding a field and forgetting to add it to __eq__. It is the right default for classes that mostly hold data.

The important limitation is that dataclasses do not validate anything: the annotations are hints and nothing checks them at runtime, so Point("abc", None) constructs perfectly happily and fails much later, somewhere unrelated. For data crossing a trust boundary — a request body, a config file, a queue message — Pydantic is the right tool because it validates and coerces at construction. A plain class is also better when construction or behaviour is genuinely complex, since at that point the generated methods are being overridden anyway and the decorator only obscures what is happening.

Mid: Explain the MRO and why super() depends on it.

The Method Resolution Order is the linearised sequence of classes Python searches for an attribute, computed by the C3 algorithm and visible as Class.__mro__. It guarantees that a class precedes its bases, that the order bases were declared in is preserved, and that each class appears exactly once; when no ordering can satisfy those constraints, the class definition itself raises TypeError.

super() does not mean "my parent" — it means "the next class after me in the MRO of type(self)". That distinction is invisible in single inheritance, where the next class always is the parent, and decisive in multiple inheritance. If A and B both inherit from Base and C inherits from both, then inside A.go the call to super().go() dispatches to B, not to Base, even though B is nowhere in A's declaration. This is exactly what makes cooperative multiple inheritance work: each class in the diamond runs once, in a defined order, and Base is not executed twice. It also explains why calling Base.__init__(self, ...) directly is a bug — it hard-codes a jump that skips whatever the MRO placed in between.

Mid: Why does defining __eq__ break using the object in a set?

Python sets __hash__ = None on any class that defines __eq__ without also defining __hash__, which makes instances unhashable and raises TypeError the moment one is added to a set or used as a dict key. That looks hostile but it protects an invariant: hash-based containers first bucket by hash and only then compare with ==, so objects that are equal must have equal hashes. If __eq__ were customised while __hash__ stayed the default identity-based one, two equal objects would land in different buckets and a lookup would report a miss for a key that is definitely present. Python would rather fail loudly than let that happen.

The fix is to define both, hashing exactly the fields that __eq__ compares — usually return hash((self.a, self.b)) — or to use @dataclass(frozen=True), which generates a consistent pair. The deeper requirement is that those fields must not change while the object is in a container; mutating a key after insertion moves its hash, and the entry becomes unreachable even though it is still there.

Senior: When should inheritance become composition? Give the concrete signals.

The test is substitutability, not vocabulary. Inheritance is correct when every instance of the subclass can be used anywhere the base is expected without the caller needing to know the difference — the Liskov substitution principle. That means the subclass may not narrow what it accepts, strengthen what it requires, or remove behaviour. When inheritance is instead being used because the base class happens to contain code you want, that is code reuse wearing an is-a costume, and composition is the honest expression of it.

The concrete smells are easy to spot in review. A subclass that overrides an inherited method to raise NotImplementedError has declared that it is not substitutable. A subclass that ignores constructor parameters it inherited is carrying state it does not want. Needing a class per combination of two independent features — RetryingThrottledEmailNotifier — is the clearest signal, because class count then grows multiplicatively with orthogonal concerns while composition grows additively. And a base class that cannot be changed without breaking unrelated subclasses is the fragile-base-class problem, which is inheritance's coupling cost coming due.

Composition in Python is unusually cheap because of duck typing: a collaborator is injected, and anything with the right method works, so tests can pass a five-line fake with no mocking framework and no shared base class. typing.Protocol lets that contract be declared and checked statically without forcing a runtime inheritance relationship. What inheritance still does well is expressing a genuinely stable is-a contract with shared invariants — abstract base classes defining an interface, or small stateless mixins that always call super(). The rule I apply is to inherit from things designed to be inherited from, and compose everything else.

Senior: Walk through what happens on obj.attr, including descriptors.

Attribute access goes through type(obj).__getattribute__, which runs a specific sequence. First it walks the MRO of type(obj) looking for the name. If it finds an entry that is a data descriptor — an object defining __set__ or __delete__ alongside __get__ — that descriptor wins immediately and its __get__ is called, taking priority over the instance. Otherwise the instance __dict__ is checked and returned if present. Failing that, a non-data descriptor found on the class (one with only __get__, which is what a plain function is) has its __get__ called — this is precisely the mechanism that turns a function into a bound method with self already applied. Then a plain class attribute is returned. Only if all of that fails does __getattr__ run, which is why __getattr__ is a fallback for missing attributes while __getattribute__ intercepts every access.

That priority order explains several behaviours that otherwise look arbitrary. @property is a data descriptor, so it cannot be shadowed by an instance attribute of the same name — assigning to it calls the setter, or raises if there is not one. cached_property is deliberately a non-data descriptor: it computes once, writes the result into the instance __dict__, and because instance __dict__ beats a non-data descriptor, every later access skips the descriptor entirely and costs a plain dict lookup. It also explains why cached_property is incompatible with slots=True: there is no instance __dict__ to write into.

Practically, this is worth knowing for two reasons. Writing a descriptor is the right move when the same access logic — validation, unit conversion, lazy loading, type coercion — repeats across several attributes or classes, because it is written once instead of as a @property pair per field. And when debugging an attribute that "isn't being set", the answer is almost always that a data descriptor is intercepting the write.

class Cart:

2 (easy): Convert this class to a dataclass and pick the right options.
Solution 
# ✗ BEFORE — 20 lines, three places to forget a field
class Point:
    def __init__(self, x, y, label="origin"):
        self.x, self.y, self.label = x, y, label
    def __repr__(self):
        return f"Point({self.x}, {self.y}, {self.label!r})"
    def __eq__(self, other):
        if not isinstance(other, Point): return NotImplemented
        return (self.x, self.y) == (other.x, other.y)   # ← label omitted;
                                                        # deliberate? a bug?
    def __hash__(self):
        return hash((self.x, self.y))

# ✓ AFTER
from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)
class Point:
    x: float
    y: float
    label: str = field(default="origin", compare=False)

# Every choice, and why:
#
# frozen=True   Generates __hash__, so Points work as dict keys and set
#               members — and a coordinate should not change identity
#               under you after it has been stored somewhere.
#
# slots=True    No per-instance __dict__: about half the memory and faster
#               attribute access. Worth it for a small record type that may
#               exist in large numbers. Cost: no dynamic attributes, and
#               no cached_property.
#
# compare=False Makes the original __eq__ behaviour EXPLICIT rather than
#               something a reader has to infer from an omission.

# What was NOT chosen:
# order=True    Only if sorting Points is meaningful. It compares fields in
#               declaration order, which is rarely the sort you actually
#               want — pass a key= to sorted() instead.
3 (medium): Objects inserted into a set cannot be found again. Diagnose.
Solution 
class Tag:
    def __init__(self, name):
        self.name = name
    def __eq__(self, other):
        return isinstance(other, Tag) and self.name == other.name
    def __hash__(self):
        return hash(self.name)

t = Tag("python")
tags = {t}
t.name = "py"            # ← the mutation
t in tags                # False
tags                     # {Tag('py')} — it IS in there

# WHY: a set puts each element in a bucket chosen from hash(element) at
# INSERTION time. Changing name changes hash(t), so the lookup computes a
# different bucket and finds nothing. The object is still stored, in the
# bucket for its old hash, permanently unreachable by lookup.
#
# Same failure with dict keys, and it is silent — no exception, just a
# cache that misses forever, or a dedup that stops deduplicating.

# ── FIX 1: MAKE THE KEY IMMUTABLE (preferred) ────────────────────────────
from dataclasses import dataclass

@dataclass(frozen=True)
class Tag:
    name: str
# Now t.name = "py" raises FrozenInstanceError at the point of the bug,
# instead of producing a wrong answer somewhere else later.

# ── FIX 2: HASH ONLY THE IMMUTABLE IDENTITY ──────────────────────────────
class User:
    def __init__(self, user_id, email):
        self.id = user_id            # never changes
        self.email = email           # may change
    def __eq__(self, other):
        return isinstance(other, User) and self.id == other.id
    def __hash__(self):
        return hash(self.id)         # only the stable field
# Legitimate when the object has a natural immutable key. The rule to
# preserve: the fields __hash__ uses must be a subset of the fields __eq__
# uses, and none of them may change while the object is in a container.

# ── THE RELATED FAILURE ──────────────────────────────────────────────────
class Tag:
    def __eq__(self, other): ...     # no __hash__
{Tag("x")}                           # TypeError: unhashable type
# Python sets __hash__ = None when you define __eq__ alone, specifically to
# stop the silent version of this bug. The loud failure is the kind one.
4 (medium): Replace a growing class hierarchy with composition.
Solution 
# ✗ BEFORE — a class per combination
class Notifier: ...
class EmailNotifier(Notifier): ...
class RetryingEmailNotifier(EmailNotifier): ...
class ThrottledEmailNotifier(EmailNotifier): ...
class RetryingThrottledEmailNotifier(RetryingEmailNotifier): ...
# Adding SMS doubles it. Adding a third feature triples that. The retry
# logic is also duplicated in every Retrying* class.

# ✓ AFTER — wrappers over a common shape
from typing import Protocol

class Sender(Protocol):
    def send(self, msg: str) -> None: ...

class EmailSender:
    def send(self, msg): smtp_send(msg)

class SmsSender:
    def send(self, msg): sms_send(msg)

class Retrying:                       # ONE implementation of retry
    def __init__(self, inner: Sender, attempts: int = 3):
        self.inner, self.attempts = inner, attempts
    def send(self, msg):
        for i in range(self.attempts):
            try:
                return self.inner.send(msg)
            except TransientError:
                if i == self.attempts - 1:
                    raise
                time.sleep(2 ** i)

class Throttled:                      # ONE implementation of throttling
    def __init__(self, inner: Sender, per_minute: int = 60):
        self.inner, self.per_minute = inner, per_minute
        self._sent = deque()
    def send(self, msg):
        self._wait_for_slot()
        return self.inner.send(msg)

# Any combination, no new classes:
notifier = Retrying(Throttled(EmailSender()))
notifier = Throttled(SmsSender(), per_minute=10)
notifier = EmailSender()                              # plain

# n features + m transports = n + m classes instead of n × m.
# Each wrapper is independently testable with a fake:
class Recording:
    def __init__(self): self.sent = []
    def send(self, msg): self.sent.append(msg)

fake = Recording()
Retrying(fake).send("hi")
assert fake.sent == ["hi"]
# No mocking framework, no base class — just an object with .send().

# Protocol declares the contract for the type checker without forcing a
# runtime inheritance relationship: EmailSender satisfies Sender without
# importing it. Structural typing, statically checked.
5 (hard): A mixin's __init__ is never called. Explain using the MRO.
Solution 
class LoggingMixin:
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        self.log = get_logger(type(self).__name__)

class Base:
    def __init__(self, name):
        self.name = name

class Service(LoggingMixin, Base):
    def __init__(self, name, url):
        Base.__init__(self, name)          # ← the bug
        self.url = url

s = Service("api", "http://x")
s.log            # AttributeError

# WHY: Service.__mro__ is (Service, LoggingMixin, Base, object). Calling
# Base.__init__ directly jumps straight past LoggingMixin, so its __init__
# never runs. The mixin is in the bases and is completely inert.

# ✓ FIX 1 — cooperative all the way down
class Service(LoggingMixin, Base):
    def __init__(self, name, url):
        super().__init__(name)     # → LoggingMixin.__init__ → Base.__init__
        self.url = url
# LoggingMixin passes *args through, so `name` reaches Base, and the mixin
# gets to run its own setup on the way back.

# ── THE SECOND HALF OF THE RULE ──────────────────────────────────────────
# Cooperative inheritance only works if EVERY class participates. One class
# that does not call super() silently truncates the chain:
class Base:
    def __init__(self, name):
        self.name = name
        # no super().__init__() — fine here, because object is next and
        # takes no arguments. But if a mixin were ordered AFTER Base, it
        # would never run.

# So a mixin designed to be composed should always be written as:
class Mixin:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)     # ALWAYS, even at the top
        ...

# ── VERIFYING, NOT GUESSING ──────────────────────────────────────────────
print(Service.__mro__)
# (Service, LoggingMixin, Base, object)
# Order comes from the DECLARATION: class Service(LoggingMixin, Base) puts
# the mixin BEFORE Base, which is what lets it wrap Base's behaviour.
# Reversed — class Service(Base, LoggingMixin) — Base.__init__ runs first
# and, since it does not call super(), the mixin never runs even with
# super() used correctly. Mixins go on the LEFT.

# ✓ FIX 2 — if the hierarchy cannot be made cooperative, do not use
# multiple inheritance for this at all. Logging is a capability, not an
# is-a relationship:
class Service:
    def __init__(self, name, url, logger=None):
        self.log = logger or get_logger("Service")
6 (hard): Design the class structure for a payments system with several providers, retries, idempotency and audit logging.
Solution 
from typing import Protocol
from dataclasses import dataclass
from decimal import Decimal

# ── 1. VALUE OBJECTS: frozen dataclasses ─────────────────────────────────
@dataclass(frozen=True, slots=True)
class Money:
    amount: Decimal          # NEVER float for money
    currency: str
    def __post_init__(self):
        if self.amount < 0:
            raise ValueError("negative amount")

@dataclass(frozen=True, slots=True)
class ChargeRequest:
    idempotency_key: str
    amount: Money
    customer_id: str

@dataclass(frozen=True, slots=True)
class ChargeResult:
    provider_ref: str
    status: str
# frozen: these cross thread and retry boundaries, and are used as cache
# keys. Immutability means a retry cannot observe a half-mutated request.

# ── 2. THE PORT: a Protocol, not a base class ────────────────────────────
class PaymentProvider(Protocol):
    def charge(self, req: ChargeRequest) -> ChargeResult: ...
    def refund(self, ref: str, amount: Money) -> None: ...

class StripeProvider:        # does NOT inherit from anything
    def charge(self, req): ...
class AdyenProvider:
    def charge(self, req): ...
# Structural typing: adding a provider means adding one class, with no
# import of ours and no hierarchy to fit into. Tests use a FakeProvider
# that is 10 lines.

# ── 3. CROSS-CUTTING CONCERNS: wrappers, one per concern ─────────────────
class Idempotent:
    """Same key → the original result, never a second charge."""
    def __init__(self, inner: PaymentProvider, store: ResultStore):
        self.inner, self.store = inner, store
    def charge(self, req):
        if cached := self.store.get(req.idempotency_key):
            return cached
        result = self.inner.charge(req)
        self.store.put(req.idempotency_key, result)
        return result

class Retrying:
    """Transient failures only. Ordered INSIDE Idempotent deliberately."""
    def __init__(self, inner: PaymentProvider, attempts: int = 3):
        self.inner, self.attempts = inner, attempts
    def charge(self, req): ...

class Audited:
    """Every attempt recorded, including failures."""
    def __init__(self, inner: PaymentProvider, log: AuditLog):
        self.inner, self.log = inner, log
    def charge(self, req):
        self.log.record("charge.start", req)
        try:
            result = self.inner.charge(req)
        except Exception as e:
            self.log.record("charge.failed", req, error=str(e))
            raise
        self.log.record("charge.ok", req, ref=result.provider_ref)
        return result

# ── 4. COMPOSITION — AND THE ORDER IS A DESIGN DECISION ──────────────────
provider = Audited(Idempotent(Retrying(StripeProvider()), store), audit_log)

# Read outside-in:
#   Audited     outermost  → sees the caller's intent, records ONE logical
#                            charge, not three retry attempts
#   Idempotent  next       → the dedup check happens BEFORE any retry, so a
#                            duplicate request never reaches the network
#   Retrying    innermost  → retries only the raw provider call
#
# Swap Retrying and Idempotent and you get a real bug: retries would each
# go through the idempotency check with the same key, and the FIRST
# transient failure could be cached as the result.

# ── 5. WHAT IS DELIBERATELY *NOT* HERE ───────────────────────────────────
#
# No PaymentProvider ABC to inherit from. A Protocol gives the same static
#   checking without coupling third-party adapters to our class tree.
#
# No RetryingAuditedStripeProvider. n concerns × m providers would be n × m
#   classes; this is n + m.
#
# No inheritance ANYWHERE except the value objects. Every relationship here
#   is has-a. The only thing shared is a method signature, which is exactly
#   what a Protocol expresses.
#
# No config objects for values that never change. Constructor arguments
#   with defaults cover it until they do not.

# ── 6. TESTING FALLS OUT ─────────────────────────────────────────────────
class FlakyProvider:
    def __init__(self, fail_times): self.calls, self.fail = 0, fail_times
    def charge(self, req):
        self.calls += 1
        if self.calls <= self.fail: raise TransientError
        return ChargeResult("ref-1", "ok")

flaky = FlakyProvider(fail_times=2)
p = Idempotent(Retrying(flaky), InMemoryStore())
p.charge(req); p.charge(req)
assert flaky.calls == 3          # 2 failures + 1 success, then cached
# Each layer is testable in isolation because each depends only on a
# method signature.

🎯 Key Takeaways

  • The class body runs once at import: a mutable class attribute is one object shared by every instance.
  • Reading an attribute falls back to the class; writing one always lands on the instance.
  • Define __repr__ on anything that reaches a log — <object at 0x…> is a debugging tax you pay later.
  • __eq__ without __hash__ makes the class unhashable, deliberately, to protect the hash/equality contract.
  • @dataclass generates the boilerplate; frozen=True adds immutability plus a hash, slots=True roughly halves memory.
  • Dataclasses do not validate — use Pydantic where data enters from outside the program.
  • super() means the next class in the MRO of type(self), not the parent; never call Base.__init__ directly.
  • Mixins go on the left of the base list, and every cooperative class must call super() or the chain truncates silently.
  • Start with plain attributes and add @property later — Python lets you change that without breaking callers, so pre-emptive getters are pure cost.
  • Inherit stable is-a contracts; compose capabilities. A class per feature combination is the signal you crossed the line.
