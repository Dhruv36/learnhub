FastAPI & Production APIs Ultra-Advanced

What you'll master: how type hints become validation, serialisation and OpenAPI docs at once, separate request and response models and the data leak they prevent, dependency injection with per-request caching and test overrides, why async def with a blocking driver is worse than plain def, authentication and the authorisation bug that tops the OWASP API list, error handling that does not leak internals, configuration and secrets, testing an API against a real database, and the deployment and observability decisions that separate a demo from a service. Prerequisites: Type Hints & Typing, Concurrency and Testing with pytest.

Part 1 — Types as the Contract

from fastapi import FastAPI, HTTPException, status
from pydantic import BaseModel, EmailStr, Field, field_validator
from datetime import datetime

app = FastAPI(title="Users API", version="1.0.0")

class UserCreate(BaseModel):                       # what the client SENDS
    name: str = Field(min_length=1, max_length=80)
    email: EmailStr
    password: str = Field(min_length=12)
    age: int = Field(ge=13, le=150)

    @field_validator("name")
    @classmethod
    def no_control_chars(cls, v: str) -> str:
        return v.strip()

class UserPublic(BaseModel):                       # what the client SEES
    id: int
    name: str
    email: EmailStr
    created_at: datetime
    model_config = {"from_attributes": True}       # build from an ORM object

@app.post("/users", response_model=UserPublic,
          status_code=status.HTTP_201_CREATED)
async def create_user(payload: UserCreate) -> UserPublic:
    row = await repo.insert(payload)
    return row

# ── WHAT THOSE ANNOTATIONS BOUGHT ────────────────────────────────────────
# 1. The body is parsed and VALIDATED into UserCreate. Bad data never
#    reaches your function — FastAPI returns 422 with per-field detail.
# 2. The response is serialised THROUGH UserPublic. Any field not listed
#    is dropped, whatever the handler returned.
# 3. An OpenAPI schema is generated, and /docs renders it interactively.
# One source of truth. No separate schema file to drift.

# ── SEPARATE MODELS ARE A SECURITY BOUNDARY, NOT STYLE ───────────────────
@app.get("/users/{user_id}")
async def get_user(user_id: int):
    return await repo.get(user_id)          # ✗ returns the ORM row:
                                            #   password_hash, internal
                                            #   flags, soft-delete columns,
                                            #   the whole table
@app.get("/users/{user_id}", response_model=UserPublic)     # ✓ filtered
#
# THREE models is the common shape, and each exists for a reason:
#   UserCreate    accepts `password`; must NOT accept `id` or `is_admin`
#                 (mass assignment — a client sending "is_admin": true)
#   UserUpdate    every field optional, for PATCH
#   UserPublic    exposes NO secret; this is your public API contract
#
# Pydantic ignores unknown fields by default. Make that explicit for
# request models so a typo'd field name is a 422 rather than silence:
model_config = {"extra": "forbid"}

# ── PATH, QUERY, HEADER, BODY — ALL TYPED ────────────────────────────────
from typing import Annotated
from fastapi import Query, Path, Header, Depends

@app.get("/users", response_model=list[UserPublic])
async def list_users(
    limit: Annotated[int, Query(ge=1, le=100)] = 20,       # BOUNDED
    offset: Annotated[int, Query(ge=0)] = 0,
    q: Annotated[str | None, Query(max_length=50)] = None,
    x_request_id: Annotated[str | None, Header()] = None,
):
    ...
# limit with no upper bound is a denial-of-service: ?limit=10000000.
# Bound every pagination parameter.

# ── ERRORS ───────────────────────────────────────────────────────────────
@app.get("/users/{user_id}", response_model=UserPublic)
async def get_user(user_id: int):
    user = await repo.get(user_id)
    if user is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "User not found")
    return user
# A path typed `int` gives 422 for /users/abc automatically — the handler
# never sees a non-integer.

Part 2 — Dependency Injection

from typing import Annotated
from fastapi import Depends

# ── A RESOURCE WITH TEARDOWN ─────────────────────────────────────────────
async def get_db() -> AsyncSession:
    async with async_session() as session:
        yield session                    # setup / teardown, like a context
                                         # manager — the session closes
                                         # after the response is sent
DB = Annotated[AsyncSession, Depends(get_db)]

# ── AUTHENTICATION AS A DEPENDENCY ───────────────────────────────────────
oauth2 = OAuth2PasswordBearer(tokenUrl="token")

async def current_user(
    token: Annotated[str, Depends(oauth2)], db: DB
) -> User:
    try:
        payload = jwt.decode(token, SECRET, algorithms=["HS256"])
    except jwt.PyJWTError:
        raise HTTPException(401, "Invalid token",
                            headers={"WWW-Authenticate": "Bearer"})
    user = await db.get(User, int(payload["sub"]))
    if user is None or not user.is_active:
        raise HTTPException(401, "Invalid token")     # same message for
                                                      # both — do not leak
                                                      # which accounts exist
    return user

CurrentUser = Annotated[User, Depends(current_user)]

@app.get("/me", response_model=UserPublic)
async def me(user: CurrentUser):
    return user
# The Annotated alias means every endpoint gets auth in one word, and the
# type is visible to mypy.

# ── DEPENDENCIES COMPOSE ─────────────────────────────────────────────────
def require_role(role: str):
    async def checker(user: CurrentUser) -> User:
        if role not in user.roles:
            raise HTTPException(403, "Insufficient permissions")
        return user
    return checker

@app.delete("/users/{user_id}", status_code=204)
async def delete_user(user_id: int,
                      admin: Annotated[User, Depends(require_role("admin"))],
                      db: DB):
    ...
# A dependency factory — the same three-layer closure pattern as a
# decorator with arguments (see Decorators & Context Managers).

# ── ROUTE-LEVEL, WHEN YOU DO NOT NEED THE VALUE ──────────────────────────
@app.post("/admin/reindex", dependencies=[Depends(require_role("admin"))])
async def reindex(): ...

# ── CACHED PER REQUEST ───────────────────────────────────────────────────
# If current_user is requested by three dependencies in one request, it
# runs ONCE — the result is cached for that request. That is why chaining
# auth dependencies does not multiply database queries.
Depends(expensive, use_cache=False)      # opt out when you need fresh

# ── AND THE REASON THIS MATTERS MOST: TESTS ──────────────────────────────
app.dependency_overrides[get_db] = lambda: test_session
app.dependency_overrides[current_user] = lambda: fake_admin
# Swap the database and the authenticated user without patching anything
# or touching a handler. This is the single strongest argument for
# expressing cross-cutting concerns as dependencies rather than as
# imports inside the function.

# ── LIFESPAN: STARTUP AND SHUTDOWN ───────────────────────────────────────
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.pool = await create_pool()        # once, at startup
    await app.state.pool.execute("SELECT 1")    # FAIL FAST on a bad config
    yield
    await app.state.pool.close()                # graceful shutdown

app = FastAPI(lifespan=lifespan)
# Connection pools, caches and background workers belong here — not at
# module import time, which would make the app unimportable in tests.

Part 3 — Async, Correctly

# ── THE MOST IMPORTANT RULE IN FASTAPI ───────────────────────────────────
#
#   async def  →  runs ON the event loop.        MUST NOT BLOCK.
#   def        →  runs in a THREAD POOL.         May block freely.
#
# FastAPI does the right thing with both. What it cannot do is rescue an
# `async def` that blocks.

@app.get("/users/{id}")
async def get_user(id: int):
    return db.query(User).get(id)         # ✗ WORST CASE: a sync driver
                                          #   inside async def blocks the
                                          #   loop. EVERY request stalls.

@app.get("/users/{id}")
def get_user(id: int):                    # ✓ plain def — FastAPI runs it
    return db.query(User).get(id)         #   in a thread; the loop stays
                                          #   free. Perfectly acceptable.

@app.get("/users/{id}")
async def get_user(id: int, db: DB):
    return await db.get(User, id)         # ✓ best: an async driver
                                          #   (asyncpg / SQLAlchemy async)

# Counter-intuitive but true: a sync endpoint with a sync driver
# outperforms an async endpoint with a sync driver, by a lot. `async def`
# is not a performance decoration — it is a promise you will not block.

# ── CONCURRENT I/O WITHIN ONE REQUEST ────────────────────────────────────
@app.get("/dashboard")
async def dashboard(user: CurrentUser):
    async with asyncio.TaskGroup() as tg:          # all three at once
        orders = tg.create_task(get_orders(user.id))
        stats  = tg.create_task(get_stats(user.id))
        feed   = tg.create_task(get_feed(user.id))
    return {"orders": orders.result(), "stats": stats.result(),
            "feed": feed.result()}
# Sequential awaits would be 150+120+200 = 470ms. Concurrent is 200ms.
# `await` alone is not concurrency (see Concurrency: GIL, Threads, Async).

# ── CPU WORK AND BLOCKING LIBRARIES ──────────────────────────────────────
@app.post("/reports")
async def make_report(data: ReportIn):
    pdf = generate_pdf(data)                  # ✗ 800ms of Python on the
                                              #   loop; everything stalls
    pdf = await asyncio.to_thread(generate_pdf, data)   # ~ok if it
                                              #   releases the GIL
    pdf = await loop.run_in_executor(process_pool, generate_pdf, data)
                                              # ✓ pure-Python CPU
# ⚠ Anything over a second or two does not belong in a request at all.
# Return 202 with a job id and process it on a queue.

# ── BACKGROUND TASKS: THE LIMIT ──────────────────────────────────────────
from fastapi import BackgroundTasks

@app.post("/orders", status_code=201)
async def create_order(order: OrderIn, bg: BackgroundTasks):
    saved = await repo.save(order)
    bg.add_task(send_confirmation_email, saved.email)   # after the response
    return saved
# Runs IN THIS PROCESS, with no retry and no durability. A restart during
# a deploy loses it silently. Fine for a best-effort email; wrong for
# anything that must happen. That needs a real queue (Celery, arq, SQS).

# ── EVERY OUTBOUND CALL NEEDS A TIMEOUT ──────────────────────────────────
client = httpx.AsyncClient(timeout=httpx.Timeout(5.0, connect=2.0))
# Without one, a slow dependency parks every worker and a partial outage
# upstream becomes a total outage here.
Key insight: FastAPI's real contribution is not speed — it is that the annotations you would write anyway become the enforced contract. The same UserCreate validates the request, documents the endpoint, and tells mypy what the handler receives, so those three things cannot drift apart. That is the pattern from the typing lesson taken to its conclusion: Pydantic converts untrusted input into a value that genuinely matches its type, and every static guarantee downstream rests on that one runtime check happening at the edge.

It also means the framework's failure modes are all about honouring the contract: returning a database row instead of a response model leaks columns, an async def that blocks breaks the concurrency promise, and an endpoint that checks authentication but not ownership passes every test while exposing everyone's data.

Part 4 — Security

# ── THE #1 API VULNERABILITY: BROKEN OBJECT-LEVEL AUTHORISATION ──────────
@app.get("/orders/{order_id}", response_model=OrderPublic)
async def get_order(order_id: int, user: CurrentUser, db: DB):
    return await db.get(Order, order_id)          # ✗ AUTHENTICATED but
                                                  #   NOT AUTHORISED
# Any logged-in user can read every order by incrementing the id. The
# endpoint has auth, passes review, and leaks the entire table. This is
# OWASP API Security #1 (BOLA), and it is the most common real API bug.

@app.get("/orders/{order_id}", response_model=OrderPublic)
async def get_order(order_id: int, user: CurrentUser, db: DB):
    order = await db.get(Order, order_id)
    if order is None or order.user_id != user.id:
        raise HTTPException(404, "Order not found")   # 404, NOT 403 —
                                                      # a 403 confirms the
                                                      # id exists
    return order
# ✓ Better still, make it structural so it cannot be forgotten:
order = await db.scalar(
    select(Order).where(Order.id == order_id, Order.user_id == user.id))
# Ownership in the QUERY. A missing filter is then a missing row, not a
# leak.

# ── MASS ASSIGNMENT ──────────────────────────────────────────────────────
@app.patch("/users/{user_id}")
async def update(user_id: int, data: dict):        # ✗ accepts ANYTHING
    await repo.update(user_id, **data)             #   including is_admin
class UserUpdate(BaseModel):
    name: str | None = None                        # ✓ an explicit
    email: EmailStr | None = None                  #   allow-list
    model_config = {"extra": "forbid"}

# ── PASSWORDS AND TOKENS ─────────────────────────────────────────────────
from passlib.context import CryptContext
pwd = CryptContext(schemes=["argon2"], deprecated="auto")
pwd.hash(password)                     # NEVER store or log a password
pwd.verify(attempt, stored_hash)       # constant-time comparison

jwt.encode({"sub": str(user.id), "exp": exp, "iat": now}, SECRET, "HS256")
# - short expiry (15 min) plus a refresh token, because a JWT cannot be
#   revoked before it expires
# - ALWAYS pass algorithms=[...] when decoding. Omitting it historically
#   allowed the "alg": "none" forgery.
# - never put anything secret in the payload; it is base64, not encrypted

# ── SQL INJECTION ────────────────────────────────────────────────────────
await db.execute(f"SELECT * FROM users WHERE email = '{email}'")   # ✗
await db.execute(text("SELECT * FROM users WHERE email = :e"),
                 {"e": email})                                     # ✓
# The ORM parameterises for you; raw SQL is where this reappears.

# ── THE REST OF THE BASELINE ─────────────────────────────────────────────
app.add_middleware(CORSMiddleware,
    allow_origins=["https://app.example.com"],     # NEVER ["*"] with
    allow_credentials=True)                        # credentials
# Rate limiting on auth endpoints — otherwise the login route is a free
#   password oracle
# HTTPS only, HSTS, and secure/httponly cookies if you use them
# Request body size limits (at the proxy) — a 2GB upload is a DoS

Part 5 — Errors, Config, Observability

# ── DO NOT LEAK INTERNALS ────────────────────────────────────────────────
@app.exception_handler(Exception)
async def unhandled(request: Request, exc: Exception):
    log.exception("unhandled", extra={"path": request.url.path,
                                      "request_id": get_request_id()})
    return JSONResponse(status_code=500, content={
        "error": "internal_error",
        "request_id": get_request_id(),       # the user quotes THIS; you
    })                                        # find the full trace in logs
# A stack trace in a 500 body tells an attacker your file layout, package
# versions and query structure. Log the detail, return the id.

# ── DOMAIN EXCEPTIONS, MAPPED ONCE ───────────────────────────────────────
class NotFound(Exception): ...
class Conflict(Exception): ...

@app.exception_handler(NotFound)
async def not_found(request, exc):
    return JSONResponse(404, {"error": "not_found", "detail": str(exc)})
# Service code raises domain errors and never imports HTTPException, so
# the same services work behind a CLI or a queue consumer.

# ── CONFIG: TYPED, VALIDATED, FROM THE ENVIRONMENT ───────────────────────
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: str
    secret_key: str
    environment: Literal["dev", "staging", "prod"] = "dev"
    log_level: str = "INFO"
    model_config = {"env_file": ".env"}

settings = Settings()        # a missing or malformed variable fails at
                             # STARTUP with a precise message — not on the
                             # first request that happens to need it
# Secrets come from the environment or a secret manager. Never in code,
# never in the image, never in git. Rotate on any suspicion.

# ── STRUCTURED LOGGING WITH A REQUEST ID ─────────────────────────────────
request_id: ContextVar[str] = ContextVar("request_id")

@app.middleware("http")
async def add_request_id(request: Request, call_next):
    rid = request.headers.get("x-request-id") or str(uuid4())
    token = request_id.set(rid)
    start = time.perf_counter()
    try:
        response = await call_next(request)
    finally:
        request_id.reset(token)               # a ContextVar MUST be reset
                                              # or it leaks across requests
    duration = time.perf_counter() - start
    log.info("request", extra={"request_id": rid, "path": request.url.path,
                               "status": response.status_code,
                               "duration_ms": duration * 1000})
    response.headers["x-request-id"] = rid
    return response
# JSON logs, one line per request, correlated end to end. Propagate the
# incoming header so a trace spans services.

# ── HEALTH CHECKS: TWO, NOT ONE ──────────────────────────────────────────
@app.get("/health/live")
async def live(): return {"status": "ok"}          # am I running?
                                                   # NO dependency checks

@app.get("/health/ready")
async def ready(db: DB):                           # can I serve traffic?
    await db.execute(text("SELECT 1"))
    return {"status": "ok"}
# Conflating them is a real outage: if liveness checks the database, a
# brief DB blip makes Kubernetes RESTART every pod, turning a recoverable
# problem into a full outage.

# ── WHAT TO MEASURE ──────────────────────────────────────────────────────
# RED: Rate, Errors, Duration — per endpoint, as PERCENTILES. An average
#   latency hides the p99 that is actually failing for users.
# Plus: DB pool utilisation, event loop lag, in-flight requests, upstream
#   dependency latency.
# OpenTelemetry for traces; alert on SLO burn rate, not on CPU.

Interview Questions

Beginner: How do type hints give FastAPI validation, serialisation and docs at once?

FastAPI inspects the annotations when the application starts. A parameter annotated with a Pydantic model means "parse the request body into this shape and validate it", so a mismatch returns a 422 with per-field detail before the handler runs. Path and query parameters annotated with primitive types are coerced and validated the same way, which is why /users/abc on an endpoint taking user_id: int never reaches your code. The response_model shapes and validates what goes out, dropping any field it does not declare. And from those same annotations FastAPI generates an OpenAPI schema, which is what renders the interactive documentation at /docs.

The value is that there is one source of truth. In a framework where the schema, the validation and the documentation are separate artifacts, they drift — the docs describe a field that was renamed three releases ago. Here they cannot, because they are all derived from the annotation the handler already needed. It is the point from the typing lesson taken to its conclusion: hints are erased by the interpreter, but libraries that read them at runtime can turn them into real enforcement.

Beginner: Why use separate request and response models?

Because they describe different things and have different security properties. The request model is an allow-list of what a client may send: it accepts a password, and critically it does not accept id, is_admin or created_at, so a client that includes those fields cannot set them — that is the mass assignment vulnerability, and the model is what prevents it. The response model is the opposite: it declares exactly what leaves the service, and because FastAPI serialises through it, any extra attribute on the object returned is dropped.

That second property matters more than it sounds. Returning an ORM row directly means every column goes out — the password hash, soft-delete flags, internal notes — and worse, it means adding a column to the table silently adds it to the public API. With a response model, a new column is invisible until someone chooses to expose it. So the usual shape is three models: one for create, one for update with every field optional, and one public model that is your actual API contract. It looks like duplication and it is a boundary.

Mid: When should an endpoint be async def and when plain def?

The rule is about what the handler does, not about which looks more modern. async def runs directly on the event loop, so it must never block; plain def is run by FastAPI in a thread pool, so it may block freely. Use async def when everything inside it is awaitable — an async database driver, httpx, an async cache client. Use plain def when you are stuck with a synchronous library, which is extremely common with older ORMs and third-party SDKs.

The failure people ship is the combination of the two: an async def handler calling a synchronous driver. That blocks the only thread running the loop, so every concurrent request stalls behind it, including the health check. Counter-intuitively, the sync endpoint with the sync driver performs far better than the async endpoint with the same driver, because the thread pool at least gives you real concurrency. async def is a promise not to block, not a performance decoration.

For the middle cases, a blocking call inside an async handler can be moved off the loop with asyncio.to_thread, and pure-Python CPU work needs a process pool because a thread still holds the GIL. Anything taking more than a second or two should not be in a request at all — return 202 with a job id and do it on a queue. Running with debug=True in development makes the loop warn about any callback that blocks, which finds these before production does.

Mid: What does Depends() give you beyond convenience?

Three things that are hard to get otherwise. First, resource lifecycle: a dependency that yields runs its teardown after the response is sent, so a database session is opened and closed per request with the guarantee a context manager gives, including when the handler raises. Second, composition — dependencies can request other dependencies, so authentication, then role checking, then a tenant-scoped database session form a graph that FastAPI resolves per request, and the result of each is cached within that request so requesting the current user from three places issues one query rather than three.

Third, and the one I would emphasise, is testability. app.dependency_overrides lets a test replace the database session with one bound to a rolled-back transaction, or replace the authenticated user with a fake admin, without patching anything and without any handler knowing. That avoids the whole patch-where-it-is-used problem from the testing lesson, because there is no import to patch — the dependency is injected. The one operational detail is clearing the overrides in fixture teardown, or they leak into every subsequent test.

Underneath it is the same argument as composition over inheritance: expressing cross-cutting concerns as injected collaborators rather than as imports inside the function makes them replaceable at the boundary, which is exactly what a test needs.

Senior: What is the most common serious security bug in an API like this?

Broken object-level authorisation — checking that the caller is authenticated but not that the resource belongs to them. An endpoint like GET /orders/{order_id} with a current_user dependency looks secure in review: there is authentication, there is a typed path parameter, there is a response model. But if the handler simply loads the order by id, any logged in user can read every order by incrementing the number. It is number one on the OWASP API Security list, and it is common precisely because the endpoint appears to have auth.

The tactical fix is an ownership check, and the structural fix is better: put the ownership into the query itself, selecting where the id matches and the owner is the current user. Then a forgotten check produces a missing row rather than a leak, and there is no separate line for someone to delete during a refactor. It should return 404 rather than 403, because a 403 confirms the id exists and lets an attacker enumerate valid identifiers. And it needs a test per ownership-scoped endpoint — one that authenticates as user A and asks for user B's resource, asserting 404 — because that is the only kind of test that catches a regression here.

The related bugs in the same family are mass assignment, where a PATCH endpoint accepting a raw dict or the full model lets a client set is_admin, fixed by an explicit update model with extra: "forbid"; and list endpoints that filter on a client-supplied user id rather than the authenticated one. All three share a root cause, which is trusting an identifier that came from the request instead of one derived from the token.

Senior: Walk through taking this service to production.

I would group it into correctness at the boundary, operational behaviour, and deployment safety.

At the boundary: a response model on every endpoint that returns data, so a new database column cannot silently become public; explicit request models with extra: "forbid"; bounded pagination everywhere, because an unbounded limit is a denial of service; ownership enforced in the query for every resource fetched by id; and configuration loaded through pydantic-settings so a missing or malformed environment variable fails at startup with a precise message rather than on the first request that touches it. Secrets come from the environment or a secret manager, never the image.

Operationally: structured JSON logs with a request id propagated from an incoming header and returned in the response, so a user can quote it and it correlates across services — and the ContextVar holding it must be reset, or it leaks into the next request on a reused worker. Errors are handled by a catch-all that logs the traceback and returns only an error code and the request id, since a stack trace in a response body is reconnaissance. Liveness and readiness must be separate probes: if liveness checks the database, a brief blip restarts every pod and converts a recoverable degradation into a full outage. Metrics are RED — rate, errors, duration as percentiles, not averages — plus connection pool utilisation and event loop lag, with alerting on SLO burn rate rather than on CPU. Every outbound call gets a timeout, because without one a slow dependency parks every worker.

For deployment: a multi-stage image with dependencies installed from the lockfile in a cached layer, running as a non-root user on a digest-pinned base. Gunicorn with uvicorn workers, though in Kubernetes I would run one or two workers per container and scale with replicas so that memory limits and metrics are attributable to a single process. Graceful shutdown must be honoured — on SIGTERM, stop accepting connections, drain in-flight requests, close pools — or every deploy drops live requests. Migrations run as a separate step before the rollout, never in the application's startup path where N pods would race, and they must be backward compatible so old and new code can coexist during a rolling deploy: add a nullable column and backfill in one release, make it NOT NULL in a later one. Dropping a column that the still-running version selects is an instant outage, and it is the mistake I have seen most often.

from typing import Annotated
from fastapi import Depends, HTTPException, status

oauth2 = OAuth2PasswordBearer(tokenUrl="/token")

async def current_user(token: Annotated[str, Depends(oauth2)],
                       db: DB) -> User:
    creds_error = HTTPException(
        status.HTTP_401_UNAUTHORIZED, "Could not validate credentials",
        headers={"WWW-Authenticate": "Bearer"})
    try:
        payload = jwt.decode(token, settings.secret_key,
                             algorithms=["HS256"])   # ← ALWAYS pass this.
    except jwt.PyJWTError:                           # Omitting it allowed
        raise creds_error                            # the "alg": "none"
    user = await db.get(User, int(payload["sub"]))   # forgery.
    if user is None or not user.is_active:
        raise creds_error                  # the SAME error for a bad
                                           # token and a missing user —
                                           # never reveal which accounts
                                           # exist
    return user

CurrentUser = Annotated[User, Depends(current_user)]

def require_role(*roles: str):             # a dependency FACTORY
    async def checker(user: CurrentUser) -> User:
        if not set(roles) & set(user.roles):
            raise HTTPException(403, "Insufficient permissions")
        return user
    return checker

@app.get("/me", response_model=UserPublic)
async def me(user: CurrentUser):
    return user

@app.delete("/users/{user_id}", status_code=204,
            dependencies=[Depends(require_role("admin"))])
async def delete_user(user_id: int, db: DB): ...

# the check.

# ── 1. CONFIG: FAIL AT STARTUP, NOT ON A REQUEST ─────────────────────────
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: str
    secret_key: str = Field(min_length=32)
    environment: Literal["dev", "staging", "prod"]
    partner_api_url: str
    model_config = {"env_file": ".env"}

settings = Settings()      # a missing var is a startup crash with a
                           # precise message, not a 500 at 3am on the one
                           # endpoint that reads it

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.pool = await create_pool(settings.database_url)
    await app.state.pool.execute("SELECT 1")     # prove it works NOW
    yield
    await app.state.pool.close()                 # graceful

# ── 2. OBSERVABILITY: CORRELATION FIRST ──────────────────────────────────
request_id: ContextVar[str] = ContextVar("request_id")

@app.middleware("http")
async def observability(request: Request, call_next):
    rid = request.headers.get("x-request-id") or str(uuid4())
    token = request_id.set(rid)
    start = time.perf_counter()
    try:
        response = await call_next(request)
    finally:
        request_id.reset(token)          # a ContextVar MUST be reset or
                                         # it leaks to the next request
                                         # on a reused worker
    dur = time.perf_counter() - start
    REQUEST_DURATION.labels(request.method, route_of(request),
                            response.status_code).observe(dur)
    log.info("request", extra={"request_id": rid, "duration_ms": dur*1000,
                               "status": response.status_code})
    response.headers["x-request-id"] = rid
    return response

# every id becomes a metric series and cardinality explodes.

🎯 Key Takeaways

  • The annotations are the contract: one Pydantic model drives validation, serialisation and the OpenAPI docs, so they cannot drift.
  • Separate request and response models are a security boundary — they block mass assignment on the way in and column leaks on the way out.
  • async def is a promise not to block; with a sync driver, plain def is genuinely better.
  • await is not concurrency — use TaskGroup for independent calls in one request.
  • Dependencies give per-request lifecycle, caching and composition, and dependency_overrides makes the whole app testable without patching.
  • Authentication is not authorisation: filter by owner in the query and return 404, or any user reads any record by id.
  • Bound every list endpoint and put a timeout on every outbound call, or one slow dependency takes the service down.
  • Validate configuration at startup and log a propagated request id — the two cheapest operational wins.
  • Keep liveness free of dependency checks, or a brief database blip restarts every pod.
  • Run migrations before the rollout and make them backward compatible, because old and new code run at the same time.
