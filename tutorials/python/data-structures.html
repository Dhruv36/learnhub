Data Structures Basics

What you'll master: the complexity of every core operation and why list is the wrong container more often than people think, how dicts and sets actually work and what hashability requires, the collections types that replace hand-rolled code, sorting with keys, and choosing a structure from access patterns rather than habit. Prerequisites: Syntax, Types & Variables and Control Flow & Functions.

Part 1 — Lists and the Cost of Each Operation

# A list is a DYNAMIC ARRAY: a contiguous block of pointers, over-allocated
# so most appends are free. That single fact explains every cost below.
#
#   OPERATION            COMPLEXITY   NOTE
#   items[i]             O(1)         direct index into the array
#   items[i] = x         O(1)
#   items.append(x)      O(1)*        amortised; occasionally reallocates
#   items.pop()          O(1)         from the END
#   items.pop(0)         O(n)         ← shifts EVERY remaining element
#   items.insert(0, x)   O(n)         ← same problem
#   items.remove(x)      O(n)         scans to find x, then shifts
#   x in items           O(n)         linear scan — see Part 2
#   len(items)           O(1)         stored, not counted
#   items[a:b]           O(b-a)       copies

# ── THE MOST COMMON PERFORMANCE BUG IN PYTHON ────────────────────────────
queue = []
while queue:
    item = queue.pop(0)        # ✗ O(n) EVERY time → O(n²) overall
    process(item)

from collections import deque
queue = deque()
while queue:
    item = queue.popleft()     # ✓ O(1)
    process(item)
# A deque is a doubly-linked list of blocks, so both ends are cheap. For
# 100,000 items the list version does ~5 billion pointer moves; the deque
# version does 100,000.

# ── SLICING COPIES ───────────────────────────────────────────────────────
first_ten = items[:10]         # a NEW list — the objects are shared
copy = items[:]                # a shallow copy of the whole list
items[:] = other               # replaces CONTENTS in place (aliases see it)

# The distinction matters when other names reference the same list:
a = [1, 2, 3]
b = a
a = [4, 5, 6]        # rebinds a; b still sees [1, 2, 3]
a[:] = [4, 5, 6]     # mutates the object; b sees [4, 5, 6]

# ── LIST MULTIPLICATION AND THE ALIASING TRAP ────────────────────────────
grid = [[0] * 3] * 3           # ✗ THREE REFERENCES to ONE inner list
grid[0][0] = 1
print(grid)                    # [[1,0,0], [1,0,0], [1,0,0]]

grid = [[0] * 3 for _ in range(3)]   # ✓ three independent lists
# `[0] * 3` is fine because ints are immutable — the aliasing only matters
# when the repeated element is mutable.

# ── SORTING ──────────────────────────────────────────────────────────────
items.sort()                   # in place, returns None
new = sorted(items)            # returns a new list, accepts any iterable

# sort() returning None is deliberate — it signals mutation. The classic
# mistake is `items = items.sort()`, which sets items to None.

# Python's sort is TIMSORT: O(n log n) worst case, and STABLE — equal
# elements keep their relative order. Stability is what makes multi-key
# sorting work by sorting repeatedly, least significant key first:
records.sort(key=lambda r: r.name)        # secondary
records.sort(key=lambda r: r.department)  # primary — ties keep name order

Part 2 — Dicts and Sets

# Both are HASH TABLES. Lookup is O(1) average because the hash jumps
# straight to a bucket rather than scanning.
#
#   OPERATION         dict/set     list
#   x in container    O(1)         O(n)
#   insert            O(1)         O(1) append / O(n) insert
#   delete            O(1)         O(n)

# ── THE SINGLE HIGHEST-VALUE OPTIMISATION IN PYTHON ──────────────────────
valid_ids = [1, 2, 3, ...]              # 10,000 entries
matches = [x for x in candidates if x in valid_ids]   # ✗ O(n×m)

valid_ids = {1, 2, 3, ...}              # a set
matches = [x for x in candidates if x in valid_ids]   # ✓ O(n)
# For 10,000 candidates against 10,000 ids that is 100 million comparisons
# versus 10,000 hash lookups. Changing one pair of brackets is often the
# entire fix for a slow script.

# ── DICTS PRESERVE INSERTION ORDER (3.7+, guaranteed) ────────────────────
config = {"host": "localhost", "port": 5432}
list(config)              # ['host', 'port'] — always this order
# Ordering is a language guarantee now, not an implementation detail. Equality
# still IGNORES order: {"a":1, "b":2} == {"b":2, "a":1} is True.

# ── ACCESS PATTERNS ──────────────────────────────────────────────────────
config["port"]                       # KeyError if absent
config.get("port")                   # None if absent
config.get("port", 5432)             # a default
config.setdefault("port", 5432)      # get, INSERTING the default if missing

# setdefault is for building nested structures, though defaultdict is
# usually clearer:
index = {}
for word in words:
    index.setdefault(word[0], []).append(word)

# ── MERGING AND COMPREHENSIONS ───────────────────────────────────────────
merged = base | overrides            # 3.9+, right wins
merged = {**base, **overrides}       # equivalent, works everywhere
base |= overrides                    # in place

squares = {n: n * n for n in range(5)}
by_id = {user.id: user for user in users}       # index a list by a key
inverted = {v: k for k, v in mapping.items()}   # careful: duplicates collide

# ── SET OPERATIONS express intent directly ───────────────────────────────
a | b        # union
a & b        # intersection
a - b        # difference
a ^ b        # symmetric difference — in exactly one
a <= b       # subset

# Finding what changed between two states, in one line each:
added   = new_keys - old_keys
removed = old_keys - new_keys
common  = old_keys & new_keys

# ── HASHABILITY: what can be a key ───────────────────────────────────────
# A key must be hashable: it needs __hash__ and its hash must never change.
# Immutable built-ins qualify; lists, dicts and sets do not.
d[(1, 2)] = "ok"        # ✓ tuple of immutables
d[[1, 2]] = "boom"      # ✗ TypeError: unhashable type: 'list'
d[frozenset({1, 2})]    # ✓ the immutable set

# THE RULE THAT CAUSES SUBTLE BUGS: if a key's hash changes after insertion,
# it becomes unreachable — the table looks in the wrong bucket:
class Point:
    def __init__(self, x): self.x = x
    def __hash__(self): return hash(self.x)     # ✗ mutable hash source
    def __eq__(self, other): return self.x == other.x

p = Point(1)
d = {p: "value"}
p.x = 2                 # the hash changed
d[p]                    # KeyError — the entry is still there, unreachable
# Only make a class hashable if it is genuinely immutable. Dataclasses get
# this right: @dataclass(frozen=True) generates __hash__, plain ones do not.
Key insight: most Python performance problems are a container chosen by habit rather than by access pattern, and the fix is usually a one-line change. A membership test against a list is O(n) and against a set is O(1); popping from the front of a list is O(n) and from a deque is O(1). Neither shows up in a code review because both versions are correct and read almost identically — they only diverge at scale. Before optimising anything else, check that each container matches how it is actually accessed.

Part 3 — Tuples, Named Tuples, and Immutability

# A tuple is an immutable sequence: fixed size, fixed contents.
point = (3, 4)
x, y = point                     # unpacking
first, *rest = [1, 2, 3, 4]      # star unpacking → 1, [2, 3, 4]
a, (b, c) = 1, (2, 3)            # nested

# ── WHEN TO USE A TUPLE RATHER THAN A LIST ───────────────────────────────
#   • a fixed-size record where position has meaning: (x, y), (host, port)
#   • a dict key or set member — lists are unhashable
#   • a return value of several related things
#   • a constant that must not be modified
#
# A list is for a variable number of HOMOGENEOUS items; a tuple is for a
# fixed number of HETEROGENEOUS ones. That is the semantic distinction, and
# it communicates more than the immutability does.

# ── IMMUTABLE DOES NOT MEAN DEEPLY IMMUTABLE ─────────────────────────────
config = ([1, 2], "fixed")
config[0].append(3)              # ✓ allowed — the LIST inside is mutable
config[0] = []                   # ✗ TypeError — rebinding the slot is not
# A tuple freezes its references, not the objects they point to. This is
# exactly why such a tuple is also unhashable:
hash(([1], 2))                   # TypeError — contains an unhashable list

# ── NAMEDTUPLE: a tuple with names ───────────────────────────────────────
from typing import NamedTuple

class Point(NamedTuple):
    x: float
    y: float
    label: str = ""              # defaults allowed, trailing only

p = Point(3, 4)
p.x                              # 3      — by name
p[0]                             # 3      — still a tuple
x, y, label = p                  # still unpacks
p._replace(x=10)                 # a NEW instance; tuples are immutable

# It IS a tuple, so it compares and hashes like one:
Point(3, 4) == (3, 4)            # True — useful, and occasionally surprising

# ── CHOOSING BETWEEN THE RECORD TYPES ────────────────────────────────────
#   tuple        throwaway, positional, 2-3 fields
#   NamedTuple   immutable record, needs to BE a tuple (hashable, unpackable)
#   @dataclass   mutable record, methods, validation in __post_init__
#   frozen dataclass  immutable with methods; hashable if eq=True
#   TypedDict    a dict with a known key schema — for JSON boundaries
#   Pydantic     when you need runtime VALIDATION of external input
#
# Reach for a dataclass by default; NamedTuple when tuple behaviour is
# genuinely wanted; a bare tuple only for two or three positional values.

Part 4 — The collections Module

from collections import defaultdict, Counter, deque, ChainMap

# ── defaultdict: no more setdefault ──────────────────────────────────────
groups = defaultdict(list)
for user in users:
    groups[user.department].append(user)     # key created automatically

counts = defaultdict(int)
for word in words:
    counts[word] += 1                        # starts at 0

# THE GOTCHA: merely READING a missing key CREATES it.
groups["nonexistent"]        # returns [] AND inserts the key
len(groups)                  # now one larger than expected
# Use .get() to check without inserting, or convert to a plain dict when you
# are finished building:
groups = dict(groups)

# ── Counter: counting, done ──────────────────────────────────────────────
counts = Counter(words)
counts.most_common(3)                    # top three (word, count) pairs
counts["missing"]                        # 0 — no KeyError, no insertion
counts.total()                           # 3.10+

Counter("hello") + Counter("world")      # combine
Counter(a) - Counter(b)                  # subtract, dropping non-positives
# Counter is the right tool for frequency analysis, histograms and finding
# duplicates — it replaces a dict plus a get-with-default loop.

# ── deque: O(1) at BOTH ends ─────────────────────────────────────────────
queue = deque([1, 2, 3])
queue.append(4)              # right
queue.appendleft(0)          # left  — O(1), unlike list.insert(0, x)
queue.pop(); queue.popleft()
queue.rotate(1)              # shift right

# A BOUNDED deque is a sliding window that maintains itself:
recent = deque(maxlen=100)
for event in stream:
    recent.append(event)     # automatically discards the oldest
# This is the cleanest implementation of "last N items" in the language —
# no manual trimming, no unbounded growth.

# ── ChainMap: layered lookups without merging ────────────────────────────
settings = ChainMap(cli_args, env_vars, config_file, defaults)
settings["timeout"]          # first match wins, searched left to right
# Unlike merging into a new dict, the underlying mappings stay live and
# separate — updating config_file is visible immediately, and you can still
# inspect which layer supplied a value.

# ── heapq: a priority queue on a plain list ──────────────────────────────
import heapq
heap = []
heapq.heappush(heap, (priority, task))
priority, task = heapq.heappop(heap)     # always the SMALLEST

heapq.nlargest(10, items, key=lambda x: x.score)
# nlargest is O(n log k) — far better than sorting everything for a top-N
# query. For a MAX-heap, negate the priority.

# ── bisect: binary search on a sorted list ───────────────────────────────
import bisect
index = bisect.bisect_left(sorted_items, target)   # O(log n)
bisect.insort(sorted_items, value)                 # insert, keeping order
# insort is O(n) because of the shift, but the SEARCH is O(log n) — worth it
# for read-heavy sorted data.

Part 5 — Sorting and Transforming

# ── KEY FUNCTIONS ────────────────────────────────────────────────────────
users.sort(key=lambda u: u.last_name)
users.sort(key=lambda u: (u.department, -u.salary))   # multi-key, mixed order
users.sort(key=str.lower)                             # case-insensitive

from operator import attrgetter, itemgetter
users.sort(key=attrgetter("last_name"))         # faster than a lambda
rows.sort(key=itemgetter(2))                    # by index/key
users.sort(key=attrgetter("department", "name"))

# The key function is called ONCE per element (the decorate-sort-undecorate
# pattern, built in), so an expensive key is computed n times, not n log n.

# ── STABILITY ENABLES MULTI-PASS SORTING ─────────────────────────────────
# Sort by the LEAST significant key first:
records.sort(key=attrgetter("name"))
records.sort(key=attrgetter("department"))
# Within a department, name order is preserved. This is often clearer than a
# single tuple key when the directions differ per field.

# Reversing descending order on a non-numeric field:
users.sort(key=attrgetter("name"))                  # ascending name
users.sort(key=attrgetter("score"), reverse=True)   # descending score
# `-x` only works for numbers; for strings, sort in passes.

# ── GROUPING ─────────────────────────────────────────────────────────────
from itertools import groupby
# groupby requires the input to be SORTED by the same key — it groups
# CONSECUTIVE runs, not all matching items.
users.sort(key=attrgetter("department"))
for department, members in groupby(users, key=attrgetter("department")):
    print(department, len(list(members)))
# Forgetting to sort first is the classic groupby bug: you get several small
# groups for the same key instead of one.

# For unsorted input, a defaultdict is simpler and O(n):
groups = defaultdict(list)
for user in users:
    groups[user.department].append(user)

# ── USEFUL itertools ─────────────────────────────────────────────────────
from itertools import chain, islice, pairwise, batched

chain(list_a, list_b)                # iterate several sequences as one
islice(iterable, 10)                 # first 10, works on any iterable
pairwise([1, 2, 3])                  # (1,2), (2,3)          — 3.10+
batched(items, 100)                  # chunks of 100         — 3.12+

# batched replaces the hand-rolled chunking loop everyone writes:
for chunk in batched(records, 500):
    bulk_insert(chunk)

# ── SORTING OBJECTS DIRECTLY ─────────────────────────────────────────────
from functools import total_ordering

@total_ordering
class Version:
    def __init__(self, major, minor): self.major, self.minor = major, minor
    def __eq__(self, other): return (self.major, self.minor) == (other.major, other.minor)
    def __lt__(self, other): return (self.major, self.minor) < (other.major, other.minor)
# total_ordering derives the other four comparisons from __eq__ and __lt__.
# Defining __eq__ WITHOUT __hash__ makes the class unhashable — set __hash__
# explicitly if instances need to go in a set.

Part 6 — Choosing a Structure

# Start from the ACCESS PATTERN, not from familiarity.
#
#   NEED                                  STRUCTURE
#   ordered, indexed, variable length     list
#   frequent add/remove at both ends      deque
#   membership testing                    set
#   key → value lookup                    dict
#   fixed-size record, positional         tuple / NamedTuple
#   record with methods or mutation       dataclass
#   counting occurrences                  Counter
#   grouping by key                       defaultdict(list)
#   "top N" or "next smallest"            heapq
#   sorted data with frequent lookup      list + bisect
#   layered configuration                 ChainMap
#   fixed-size sliding window             deque(maxlen=N)
#   unique AND ordered                    dict.fromkeys(items)

# ── DEDUPLICATING WHILE PRESERVING ORDER ─────────────────────────────────
unique = list(dict.fromkeys(items))       # ✓ order preserved, O(n)
unique = list(set(items))                 # ✗ order LOST
# dicts preserve insertion order, so this idiom is both correct and fast.

# ── MEMORY MATTERS AT SCALE ──────────────────────────────────────────────
import sys
sys.getsizeof([1, 2, 3])          # a list over-allocates
sys.getsizeof((1, 2, 3))          # a tuple is exact — smaller
# For millions of small records, the difference is real:
#   dict per record      ~200 bytes    flexible, slowest
#   NamedTuple           ~120 bytes
#   dataclass(slots=True) ~100 bytes   ← usually the right answer
#   array.array / numpy   ~8 bytes     for homogeneous NUMBERS only

@dataclass(slots=True)
class Point:
    x: float
    y: float
# slots removes the per-instance __dict__: less memory and faster attribute
# access, at the cost of not being able to add attributes dynamically.

# ── GENERATORS WHEN THE DATA DOES NOT FIT ────────────────────────────────
total = sum(int(line) for line in open("huge.txt"))   # constant memory
values = [int(line) for line in open("huge.txt")]     # loads EVERYTHING
# See Comprehensions, Iterators & Generators for the full treatment.

# ── MEASURE RATHER THAN ASSUME ───────────────────────────────────────────
import timeit
timeit.timeit("x in data", setup="data = list(range(10000)); x = 9999")
timeit.timeit("x in data", setup="data = set(range(10000)); x = 9999")
# Roughly 1000x apart on this input. Big-O predicts the shape; timeit tells
# you whether n is large enough for it to matter — and for small n, the
# "slower" structure is frequently faster because of constant factors.

Interview Questions

Beginner: When would you use a set instead of a list?

Whenever the main operation is membership testing or deduplication. A set is a hash table, so x in s is O(1) on average, while the same test against a list is O(n) because it scans every element. Inside a loop that difference turns linear work into quadratic work, which is the single most common performance problem in Python code. Sets also give you union, intersection and difference operations that express comparisons between collections in one line. The trade-offs are that sets are unordered, cannot contain unhashable items such as lists, and cannot hold duplicates — so when order matters or duplicates are meaningful, a list is still correct.

Beginner: What makes an object usable as a dictionary key?

It must be hashable, meaning it implements __hash__ and its hash value never changes for the lifetime of the object. Immutable built-in types qualify — numbers, strings, tuples of immutables, frozensets — while lists, dicts and sets do not, since mutating them would change their hash. The reason is mechanical: a dict stores an entry in a bucket determined by the hash, so if the hash changed afterwards the lookup would search the wrong bucket and the entry would become unreachable even though it is still in the table. That is also why defining a custom __hash__ over mutable attributes is dangerous, and why @dataclass(frozen=True) generates a hash while a plain dataclass does not.

Mid: Why is list.pop(0) slow, and what should you use instead?

A list is a contiguous array of pointers, so removing the first element requires shifting every remaining element one position left — O(n) work per call. Using it as a queue therefore costs O(n²) overall, which is imperceptible for a hundred items and catastrophic for a hundred thousand. collections.deque is implemented as a doubly-linked list of blocks, so popleft and appendleft are both O(1). The trade-off is that a deque has O(n) random indexing rather than O(1), so it is the wrong choice if you need arbitrary positional access — but for queue and sliding-window patterns it is strictly better, and deque(maxlen=n) also gives you a self-trimming fixed-size window for free.

Mid: How does itertools.groupby differ from grouping with a dict?

groupby groups consecutive elements sharing a key, so the input must already be sorted by that key or you get several separate groups for the same value — the most common bug with it. In exchange it is lazy and uses constant memory, which matters when streaming a large file. Grouping with a defaultdict(list) handles unsorted input in a single O(n) pass with no sort required, but materialises every group in memory. So the dict approach is the right default for in-memory collections, and groupby earns its place when the data is already sorted — for example rows coming back from a database with an ORDER BY — or when it is too large to hold at once. One further detail: the group iterator groupby yields is only valid until you advance to the next group, so it must be consumed or materialised immediately.

Senior: A script processing 100,000 records takes hours. Where do you look first?

Before profiling I would look for algorithmic problems in the container choices, because at that scale they dominate everything else and the fixes are one-liners. The first suspect is a membership test against a list inside a loop, which is O(n×m): with 100,000 records checked against a 100,000-entry list that is ten billion comparisons, and converting the inner container to a set makes it ten thousand hash lookups. The second is pop(0) or insert(0, ...) used as a queue, which is quadratic for the same reason. The third is repeated concatenation — building a string or list with += in a loop copies the whole accumulated result each time, so join or append is the fix. The fourth is an N+1 pattern against a database or API inside the loop, where the real cost is round-trip latency rather than Python at all. Only after those would I actually profile with cProfile, because guessing beyond that point is unreliable — and I would profile on realistic data volume, since these bugs are invisible on a small sample. If the profile shows the time genuinely spread across computation rather than concentrated in one call, then the answer is different: batching, generators to avoid materialising everything, or moving numeric work to NumPy.

Senior: How do you choose a data structure for ten million records in memory?

At that scale per-record overhead dominates, so the first question is whether they need to be in memory at all — a generator pipeline or a database query with server-side filtering often removes the problem entirely, and I would establish that before optimising the representation. If they genuinely must be resident, the representation choice is worth roughly a factor of two to twenty. A dict per record is the worst common option at around 200 bytes each, because every instance carries its own hash table. A NamedTuple is substantially smaller and a @dataclass(slots=True) smaller still, since slots removes the per-instance __dict__ and also speeds up attribute access; that is usually where I would land for heterogeneous records. If the fields are homogeneous numbers, NumPy arrays or array.array are a different order of magnitude — around eight bytes per value rather than a hundred — because they store raw values rather than pointers to boxed objects, and they bring vectorised operations with them. Beyond representation, I would think about access: if the workload is lookups by key, a dict of slotted objects is right; if it is scans and aggregations, columnar storage is far more cache-friendly than an array of records. And I would measure rather than assume, because sys.getsizeof does not count referenced objects and the intuition about Python memory is usually wrong by a large factor.

🏋️ Exercises

1 (easy): This function is O(n²). Make it O(n): [x for x in candidates if x in valid_ids] where valid_ids is a list.
Solution 
# ✗ BEFORE — valid_ids is a list, so each `in` scans it linearly:
valid_ids = [1, 2, 3, ...]          # 10,000 entries
matches = [x for x in candidates if x in valid_ids]
# 10,000 candidates × 10,000 average scan = up to 100,000,000 comparisons

# ✓ AFTER — one bracket change:
valid_ids = {1, 2, 3, ...}          # a SET
matches = [x for x in candidates if x in valid_ids]
# 10,000 hash lookups. Roughly 1000x faster on this input.

# If valid_ids arrives as a list you cannot change, convert ONCE outside the
# loop — never inside it:
valid_set = set(valid_ids)                          # O(n), done once
matches = [x for x in candidates if x in valid_set]

# ✗ THE MISTAKE THAT UNDOES THE FIX:
matches = [x for x in candidates if x in set(valid_ids)]
# This rebuilds the set on EVERY iteration — now O(n×m) again, plus the
# allocation cost. It looks correct and is slower than the original.

# WHY IT MATTERS: both versions are correct, read almost identically, and
# behave identically on the 50-element test fixture. They diverge only at
# production volume, which is why this survives code review.
2 (easy): Explain why grid = [[0] * 3] * 3; grid[0][0] = 1 changes three rows, and fix it.
Solution 
grid = [[0] * 3] * 3
grid[0][0] = 1
print(grid)          # [[1, 0, 0], [1, 0, 0], [1, 0, 0]]

# WHY: `* 3` on a list repeats the REFERENCE, not the object. The outer list
# holds three pointers to ONE inner list, so mutating through any of them is
# visible through all three.
print(grid[0] is grid[1])          # True — the same object

# ✓ FIX — a comprehension evaluates [0] * 3 fresh on each iteration:
grid = [[0] * 3 for _ in range(3)]
grid[0][0] = 1
print(grid)                        # [[1, 0, 0], [0, 0, 0], [0, 0, 0]]
print(grid[0] is grid[1])          # False — independent lists

# WHY `[0] * 3` IS STILL FINE: ints are immutable, so sharing references to
# the same 0 is harmless — nothing can mutate it. The aliasing only matters
# when the repeated element is MUTABLE.
#
# The same trap appears with dicts:
rows = [{}] * 3                    # ✗ three references to one dict
rows = [{} for _ in range(3)]      # ✓

# And it is the exact same mechanism as the mutable default argument: one
# object created once, then shared by everything that refers to it.
3 (medium): Group users by department and find the top 3 earners in each, efficiently.
Solution 
from collections import defaultdict
import heapq

def top_earners_by_department(users, n=3):
    # GROUP in one O(n) pass. defaultdict avoids the setdefault dance and
    # needs no pre-sorting — unlike itertools.groupby, which only groups
    # CONSECUTIVE items and would need a sort first.
    groups = defaultdict(list)
    for user in users:
        groups[user.department].append(user)

    # nlargest is O(m log n) per group rather than O(m log m) for a full
    # sort — a real saving when each department has thousands of members and
    # we only want three.
    return {
        department: heapq.nlargest(n, members, key=lambda u: u.salary)
        for department, members in groups.items()
    }

# ── WHY NOT SORT EVERYTHING ──────────────────────────────────────────────
# sorted(members, key=..., reverse=True)[:3] is correct and clearer for small
# groups, but it does O(m log m) work to discard all but three elements.
# For m = 10,000 that is ~130,000 comparisons versus ~40,000 for nlargest.
#
# For SMALL groups sorted() is actually faster — the constant factors favour
# it — so this optimisation is worth it only when groups are large. Measure.

# ── WHY NOT groupby ──────────────────────────────────────────────────────
users.sort(key=attrgetter("department"))        # a required O(n log n) sort
for dept, members in groupby(users, key=attrgetter("department")):
    ...
# Correct, but the mandatory sort makes it slower than the defaultdict pass
# unless the input is ALREADY sorted — for example rows from a database with
# ORDER BY department, where groupby then wins on memory because it streams.
4 (medium): Implement a fixed-size cache of the 100 most recent events with O(1) insertion, and a lookup by id.
Solution 
from collections import deque

class RecentEvents:
    """The last N events, in order, with O(1) lookup by id."""

    def __init__(self, maxlen=100):
        # deque(maxlen=...) discards from the LEFT automatically when full —
        # no manual trimming, no unbounded growth, O(1) append.
        self._events = deque(maxlen=maxlen)
        self._by_id = {}                    # id → event, for O(1) lookup

    def add(self, event):
        # Capture what will be evicted BEFORE appending, so the index stays
        # in sync. Once the deque is full, appending silently drops the
        # oldest item and we would otherwise leak that key forever.
        evicted = self._events[0] if len(self._events) == self._events.maxlen else None

        self._events.append(event)
        self._by_id[event.id] = event

        if evicted is not None and evicted.id != event.id:
            self._by_id.pop(evicted.id, None)

    def get(self, event_id):
        return self._by_id.get(event_id)     # O(1)

    def __iter__(self):
        return iter(self._events)            # oldest → newest

    def __len__(self):
        return len(self._events)

# ── THE DESIGN ───────────────────────────────────────────────────────────
# TWO structures because there are TWO access patterns:
#   deque  → ordered, bounded, O(1) append and eviction
#   dict   → O(1) lookup by id
# Using only the deque would make get() an O(n) scan; using only a dict would
# lose ordering and bounding.
#
# THE SUBTLE PART is keeping them consistent. The deque evicts silently, so
# the dict must be told what left — otherwise it grows without bound and the
# "fixed-size" cache is only fixed-size in one of its two structures. That
# leak is invisible until memory becomes a problem.

# ── IF YOU NEED LRU RATHER THAN INSERTION ORDER ──────────────────────────
from functools import lru_cache          # for function results
from collections import OrderedDict      # move_to_end for manual LRU
# A plain dict preserves insertion order but has no cheap "move to end", so
# OrderedDict.move_to_end is the right tool for true LRU eviction.
5 (hard): A dict-based cache keyed by a custom object intermittently returns misses for keys that were definitely inserted. Diagnose.
Solution 
# ✗ THE CAUSE — a MUTABLE object used as a key:
class CacheKey:
    def __init__(self, user_id, filters):
        self.user_id = user_id
        self.filters = filters              # a LIST — mutable

    def __hash__(self):
        return hash((self.user_id, tuple(self.filters)))

    def __eq__(self, other):
        return (self.user_id, self.filters) == (other.user_id, other.filters)

key = CacheKey(1, ["active"])
cache[key] = result                 # stored in bucket hash(...) = X

key.filters.append("verified")      # ← the hash CHANGES

cache[key]                          # KeyError: looks in bucket Y, not X
len(cache)                          # still 1 — the entry is there, orphaned

# WHY: a dict places an entry in a bucket derived from the hash AT INSERTION.
# It never rehashes existing entries. Mutating the key changes where lookups
# search, so the entry becomes permanently unreachable — and the memory is
# never reclaimed, so this is also a leak.
#
# It is INTERMITTENT because it only manifests when something mutates the key
# after insertion, which may happen on only one code path.

# ✓ FIX 1 — make the key genuinely immutable (best):
from dataclasses import dataclass

@dataclass(frozen=True)
class CacheKey:
    user_id: int
    filters: tuple[str, ...]        # a TUPLE, not a list

key = CacheKey(1, ("active",))
key.filters = (...)                 # FrozenInstanceError — cannot happen

# frozen=True generates __hash__ and __eq__ from the fields and blocks
# attribute assignment, so the bug is unrepresentable rather than avoided by
# discipline.

# ✓ FIX 2 — normalise to a plain tuple key:
cache[(user_id, tuple(sorted(filters)))] = result
# sorted() also makes the key ORDER-INDEPENDENT, so ["a","b"] and ["b","a"]
# hit the same entry — usually what a cache should do.

# ── THE GENERAL RULE ─────────────────────────────────────────────────────
# A dict key's hash must be stable for the object's entire lifetime.
# Therefore: only hashable-by-value, immutable objects belong as keys. If a
# class defines __eq__ without __hash__, Python makes it unhashable
# deliberately — that default is protecting you from exactly this.
6 (hard): Choose structures for a service holding 5 million records queried by id, by date range, and by tag.
Solution 
# THREE ACCESS PATTERNS → THREE INDEXES over ONE set of record objects.
# The records are stored once; every index holds references, not copies.

from dataclasses import dataclass
from collections import defaultdict
import bisect

@dataclass(slots=True)              # slots: ~100 bytes vs ~200 for a dict
class Record:
    id: int
    created_at: float               # a timestamp sorts and compares cheaply
    tags: frozenset[str]            # immutable → safe to share and hash
    payload: str

class RecordStore:
    def __init__(self):
        self._by_id = {}                        # id → Record       O(1)
        self._by_date = []                      # sorted [(ts, id)] O(log n)
        self._by_tag = defaultdict(set)         # tag → {ids}       O(1)

    def add(self, record):
        self._by_id[record.id] = record

        # Keep the date index sorted on insert. insort is O(n) because of the
        # memmove, but the SEARCH is O(log n) — the right trade for
        # read-heavy data. For write-heavy loads, append and sort in batches.
        bisect.insort(self._by_date, (record.created_at, record.id))

        for tag in record.tags:
            self._by_tag[tag].add(record.id)

    def get(self, record_id):
        return self._by_id.get(record_id)                    # O(1)

    def range(self, start, end):
        # Binary search both ends, then slice — O(log n + k), NOT a scan.
        left = bisect.bisect_left(self._by_date, (start, 0))
        right = bisect.bisect_right(self._by_date, (end, float("inf")))
        return [self._by_id[i] for _, i in self._by_date[left:right]]

    def by_tags(self, *tags):
        # Set INTERSECTION does the AND query in one operation. Starting from
        # the SMALLEST set keeps the intersection cheap.
        id_sets = sorted((self._by_tag[t] for t in tags), key=len)
        if not id_sets:
            return []
        matching = set.intersection(*id_sets)
        return [self._by_id[i] for i in matching]

# ── MEMORY, WHICH DOMINATES AT THIS SCALE ────────────────────────────────
#   5M slotted records          ~500 MB   (a dict per record would be ~1 GB)
#   _by_id                      ~300 MB   (dict overhead + pointers)
#   _by_date                    ~400 MB   (5M tuples)
#   _by_tag                     depends on tag cardinality
# Total is comfortably into gigabytes — which is the finding that matters.

# ── THE HONEST CONCLUSION ────────────────────────────────────────────────
# This is a database. Three indexes over five million records, kept
# consistent on every write, with range queries and set intersections, is
# precisely what SQLite or PostgreSQL already does — with persistence,
# crash safety, concurrent access and a query planner, none of which the
# code above has.
#
# I would build this in memory ONLY when: the dataset is genuinely bounded,
# it is derived and rebuildable from a source of truth, and the latency
# requirement rules out a database round trip. Otherwise the right answer is
# an index in the database and a cache in front of it.
#
# Recognising when a data-structure question is really a storage question is
# the senior judgement here — the implementation above is correct and is
# still usually the wrong thing to ship.

🎯 Key Takeaways

  • A list is a dynamic array: indexing and appending are O(1), but front insertion, removal and membership are O(n).
  • Membership testing against a set is O(1) versus O(n) for a list — the single most valuable one-line optimisation in Python.
  • Use deque for queues and sliding windows; maxlen gives self-trimming for free.
  • [[0] * 3] * 3 repeats the reference, not the object — use a comprehension for nested mutables.
  • Dict keys must be hashable and their hash must never change; mutating a key orphans the entry.
  • Dicts preserve insertion order, which makes list(dict.fromkeys(items)) the order-preserving dedup.
  • defaultdict creates keys on read, so checking with [] silently grows the dict.
  • groupby groups consecutive items and needs sorted input; a defaultdict handles unsorted data in one pass.
  • Sorting is stable, which lets multi-key sorts be done in passes, least significant key first.
  • At scale, choose by memory too: @dataclass(slots=True) roughly halves a dict-based record, and NumPy is an order of magnitude better for homogeneous numbers.
