Concurrency: GIL, Threads, Async Advanced

What you'll master: what the GIL actually locks and why it makes threads useless for CPU work but excellent for I/O, the decision table that picks the right tool from the workload, asyncio's event loop and the single blocking call that freezes it, why the GIL does not make += 1 safe, processes and the pickling boundary that decides whether they pay off, cancellation, timeouts and TaskGroups, and how to diagnose a concurrency problem rather than guess at it. Prerequisites: Decorators & Context Managers and Comprehensions, Iterators & Generators.

Part 1 — The GIL

# The Global Interpreter Lock is a mutex around the INTERPRETER. Only one
# thread executes Python bytecode at a time, in a given process.
#
# It exists because CPython's memory management uses reference counting,
# and making every refcount update atomic would cost more than the GIL
# does for single-threaded code — which is most code.

# ── WHAT IT MEANS IN PRACTICE ────────────────────────────────────────────
def cpu_work(n):
    return sum(i * i for i in range(n))

# 4 threads on a 4-core machine: NOT 4x faster. Roughly 1x, often slightly
# SLOWER, because the threads now also pay for lock contention and context
# switching while still executing one at a time.

# ── BUT THE GIL IS RELEASED ──────────────────────────────────────────────
# ...whenever a thread is not executing bytecode:
#
#   during BLOCKING I/O    socket reads, disk reads, subprocess waits,
#                          time.sleep — the thread releases the GIL while
#                          it waits and another thread runs
#   inside many C EXTENSIONS  numpy array ops, Pillow, lxml, hashlib,
#                          zlib — they release it around long computations
#   every ~5ms             sys.setswitchinterval() — so CPU-bound threads
#                          take turns rather than starving each other
#
# ⇒ Threads DO overlap I/O waits. 100 threads each waiting 200ms on HTTP
#   finish in about 200ms total, not 20 seconds.

# ── SO THE RULE IS ABOUT THE WORKLOAD, NOT THE TOOL ──────────────────────
#   I/O-BOUND   the program spends its time WAITING     → threads or async
#   CPU-BOUND   the program spends its time COMPUTING   → processes
#
# How to tell, without guessing:
#   top / htop shows one core at 100%      → CPU-bound
#   all cores idle while the program runs  → I/O-bound
#   py-spy top --pid PID                   → where the time actually goes

# ── THE FREE-THREADED BUILD ──────────────────────────────────────────────
# Python 3.13 ships an experimental no-GIL build (PEP 703), officially
# supported from 3.14. Threads then run bytecode in parallel — but every
# C extension must be rebuilt for it, single-threaded code is somewhat
# slower, and all the ordinary race conditions become much easier to hit
# because operations that were incidentally atomic no longer are.
#
# Worth knowing it exists and is coming. The model above is still what
# you deploy against today, and the workload-based decision does not
# change: processes still isolate memory, async still costs less per
# connection.

#

#   sequential                16.0s

#
# The two tables are mirror images. Picking the wrong one does not just
# fail to help — it actively costs.

# ── COST PER UNIT OF CONCURRENCY ─────────────────────────────────────────
#   asyncio task    ~KB      an object on the heap
#   thread          ~8MB     a real OS stack; ~10k is the practical ceiling
#   process         ~10MB+   plus interpreter startup and pickling
#
# This is why a web server handling 10,000 idle connections uses async:
# 10,000 threads is 80GB of stacks, and 10,000 tasks is a few hundred MB.

Part 3 — asyncio

import asyncio, httpx

async def fetch(client: httpx.AsyncClient, url: str) -> dict:
    r = await client.get(url)          # ← yields control at the await
    return r.json()

async def main(urls: list[str]) -> list[dict]:
    async with httpx.AsyncClient() as client:
        return await asyncio.gather(*(fetch(client, u) for u in urls))

asyncio.run(main(urls))                # ONE event loop, at the top

# ── THE MODEL ────────────────────────────────────────────────────────────
# A single thread runs an event loop. `await` marks a point where a
# coroutine can suspend, handing control back so the loop can run another.
# COOPERATIVE: nothing is preempted. A coroutine that never awaits holds
# the loop until it returns.
#
# This is the same machinery as generators — a suspended coroutine is a
# live stack frame the loop resumes when its I/O completes.

# ── await DOES NOT MEAN CONCURRENT ───────────────────────────────────────
async def slow():
    a = await fetch(client, url1)      # waits for a...
    b = await fetch(client, url2)      # ...THEN starts b. Sequential.
    return a, b                        # 400ms

async def fast():
    return await asyncio.gather(       # both start immediately
        fetch(client, url1),
        fetch(client, url2),
    )                                  # 200ms
# `await` means "suspend until this finishes". Concurrency comes from
# gather / TaskGroup / create_task, not from await itself. This is the
# most common async mistake in code review.

# ── TaskGroup: THE MODERN DEFAULT (3.11+) ────────────────────────────────
async def main(urls):
    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(fetch(client, u)) for u in urls]
    return [t.result() for t in tasks]
# If any task raises, the others are CANCELLED and the group re-raises.
# gather() by default leaves siblings running after one fails, which
# leaks work; gather(..., return_exceptions=True) collects errors instead
# of raising, which is right when partial results are acceptable.

# ── THE ONE BLOCKING CALL THAT FREEZES EVERYTHING ────────────────────────
async def handler():
    time.sleep(1)                      # ✗ blocks the LOOP for 1s. Every
                                       #   other connection stalls.
    requests.get(url)                  # ✗ blocking HTTP client
    data = heavy_parse(payload)        # ✗ 500ms of CPU, same effect
    conn.execute(sql)                  # ✗ blocking DB driver

# ✓ async-native libraries:
    await asyncio.sleep(1)
    await client.get(url)              # httpx / aiohttp
    await conn.fetch(sql)              # asyncpg

# ✓ or push it off the loop:
    data = await asyncio.to_thread(heavy_parse, payload)     # blocking I/O
                                                            # or a C ext
    loop = asyncio.get_running_loop()
    data = await loop.run_in_executor(process_pool, cpu_work, payload)
                                                            # pure-Python CPU
# to_thread uses a THREAD, so it helps blocking I/O and GIL-releasing C
# code — but NOT pure-Python CPU work, which still contends for the GIL
# and still stalls the loop. That needs a process pool.

# ── FORGETTING await ─────────────────────────────────────────────────────
result = fetch(client, url)            # a coroutine OBJECT. Nothing ran.
# RuntimeWarning: coroutine 'fetch' was never awaited
# It is a warning, not an error, so it is easy to ship. `if result:` is
# even true, because a coroutine object is always truthy.

# ── FIRE-AND-FORGET LOSES TASKS ──────────────────────────────────────────
asyncio.create_task(background_job())  # ✗ the loop holds only a WEAK
                                       #   reference — it can be garbage
                                       #   collected mid-flight
background = set()
task = asyncio.create_task(background_job())
background.add(task)                   # ✓ keep a strong reference
task.add_done_callback(background.discard)
Key insight: the question is never "should I use threads or async" — it is "is this program waiting, or computing?" A program that waits needs cheap concurrency and gets it from async or threads, because the GIL is released for the entire duration of the wait. A program that computes needs a second interpreter and gets it from processes, because the GIL is precisely what it is fighting over. Everything else — the pickling costs, the blocking-call trap, the lock discipline — follows from that one distinction, and measuring which side you are on takes less time than guessing wrong does.

Part 4 — Threads and Shared State

from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=20) as ex:
    results = list(ex.map(download, urls))         # ordered, raises on
                                                   # first exception seen

    futures = {ex.submit(download, u): u for u in urls}
    for fut in as_completed(futures):              # as they FINISH
        url = futures[fut]
        try:
            handle(fut.result())                   # ← exceptions surface
        except Exception as e:                     #   HERE, not at submit
            log.warning("%s failed: %s", url, e)

# ⚠ ex.map swallows nothing, but it also does not run your error handling
#   until you iterate. A submitted task whose result is never retrieved
#   fails SILENTLY — no traceback anywhere.

# ── SIZING THE POOL ──────────────────────────────────────────────────────
# I/O-bound: workers ≈ how many simultaneous waits the far side tolerates.
#   20-100 is typical. It is NOT bounded by core count — they are waiting.
#   But it IS bounded by the DB connection pool, the API's rate limit, and
#   ~8MB of stack each.
# CPU-bound: do not use threads at all.

# ── THE GIL DOES NOT MAKE YOUR CODE THREAD-SAFE ──────────────────────────
counter = 0
def increment():
    global counter
    for _ in range(100_000):
        counter += 1               # THREE bytecodes: LOAD, ADD, STORE.
                                   # A switch between them loses an update.

# 8 threads × 100,000 → expected 800,000, actual ~230,000.
# The GIL guarantees the INTERPRETER's internal state stays consistent.
# It guarantees nothing about YOUR invariants.

import threading
lock = threading.Lock()
def increment():
    global counter
    for _ in range(100_000):
        with lock:                 # ✓ 800,000, every time
            counter += 1

# ── WHAT IS ACTUALLY ATOMIC ──────────────────────────────────────────────
d[k] = v          # atomic (a single bytecode)
lst.append(x)     # atomic
d.get(k)          # atomic
counter += 1      # ✗ NOT atomic
if k not in d:    # ✗ NOT atomic as a PAIR — check-then-act is a race
    d[k] = v      #   even though each line is
# Relying on the atomic ones is a CPython implementation detail that the
# free-threaded build weakens. Use a lock and stop thinking about it.

# ── PREFER PASSING MESSAGES TO SHARING STATE ─────────────────────────────
from queue import Queue
q: Queue = Queue(maxsize=1000)     # maxsize gives BACKPRESSURE — a fast
                                   # producer blocks instead of consuming
                                   # all memory
def worker():
    while (item := q.get()) is not None:
        process(item)
        q.task_done()
# Queue is thread-safe internally, so there is no lock for you to forget.
# A design with no shared mutable state cannot have a data race.

# ── OTHER PRIMITIVES ─────────────────────────────────────────────────────
threading.RLock()            # re-entrant: the same thread can acquire twice
threading.Event()            # a one-shot flag to signal shutdown
threading.Semaphore(10)      # cap concurrent access to a scarce resource
threading.local()            # per-thread storage; no sharing at all

# ── DEADLOCK ─────────────────────────────────────────────────────────────
# Thread A holds lock1, wants lock2. Thread B holds lock2, wants lock1.
# Both wait forever. The program does not crash — it HANGS, which is
# harder to diagnose.
# Prevention: acquire locks in a consistent global order everywhere, hold
# them for the shortest possible time, and never call out to unknown code
# (a callback, a request) while holding one.
with lock.acquire(timeout=5):      # a timeout turns a hang into an error

Part 5 — Processes

from concurrent.futures import ProcessPoolExecutor

with ProcessPoolExecutor(max_workers=8) as ex:
    results = list(ex.map(cpu_heavy, chunks, chunksize=10))
# Each worker is a separate interpreter with its own GIL and its own
# memory. This is the only way to run pure-Python code on several cores.

# ── EVERYTHING CROSSES THE BOUNDARY BY PICKLING ──────────────────────────
# Arguments are pickled, sent through a pipe, and unpickled. Results come
# back the same way. Two consequences:
#
# 1. IT MUST BE PICKLABLE
with ProcessPoolExecutor() as ex:
    ex.submit(lambda x: x * 2, 5)          # ✗ PicklingError — no lambdas
    ex.submit(module_level_function, 5)    # ✓ must be importable by name
# Also unpicklable: open files, sockets, DB connections, local classes,
# anything holding a lock. Open resources INSIDE the worker.
#
# 2. THE TRANSFER CAN COST MORE THAN THE WORK
ex.map(process_row, million_rows)          # ✗ a pickle round-trip PER ROW
ex.map(process_chunk, chunks_of_10000)     # ✓ amortised
ex.map(f, items, chunksize=100)            # ✓ or let the pool batch them
# The rule: parallelise coarse-grained work. If a task takes less than
# ~10ms, the overhead dominates and the pool is slower than a loop.

# ── NO SHARED MEMORY ─────────────────────────────────────────────────────
counter = 0
def worker(): global counter; counter += 1     # ✗ increments a COPY
# Each process has its own address space. Use the return value, or
# multiprocessing.Queue / Value / Array / shared_memory when you must.
from multiprocessing import shared_memory      # zero-copy for big arrays

# ── START METHODS ────────────────────────────────────────────────────────
# fork    (Linux default before 3.14) fast, copy-on-write, but UNSAFE with
#         threads — a fork inherits locks held by threads that do not
#         exist in the child, which deadlocks. Classic symptom: a worker
#         that hangs only in production, where a logging or metrics thread
#         is running.
# spawn   (Windows, macOS, and Linux default from 3.14) a fresh
#         interpreter, re-imports your module — which is why the __main__
#         guard is MANDATORY:
if __name__ == "__main__":         # without it, spawn re-imports the
    main()                         # module and recursively creates pools
multiprocessing.set_start_method("spawn")      # be explicit

# ── BEFORE REACHING FOR PROCESSES ────────────────────────────────────────
# 1. Is it really CPU-bound?  Measure. py-spy top --pid PID
# 2. Is the algorithm the problem?  An O(n²) loop parallelised 8x is
#    still O(n²) — with more moving parts.
# 3. Can numpy/polars do it?  Vectorised C releases the GIL and often
#    beats 8 Python processes, in one line, with no pickling.
# 4. Only then: a process pool.
#
# And past one machine, this is a distributed-systems problem — Celery,
# Ray, Dask — not a bigger pool.

Part 6 — Cancellation, Timeouts, Diagnosis

# ── TIMEOUTS ARE NOT OPTIONAL ────────────────────────────────────────────
async with asyncio.timeout(5):             # 3.11+
    await fetch(url)                       # TimeoutError, and the task is
                                           # CANCELLED — not left running
result = await asyncio.wait_for(fetch(url), timeout=5)     # older form
# Without one, a hung connection holds a worker forever. In a service
# that is how one slow dependency takes down everything: every worker
# ends up parked on it and healthy requests have nowhere to run.
# Every network call needs a timeout. Every one.

# ── CANCELLATION IS AN EXCEPTION ─────────────────────────────────────────
async def worker():
    try:
        await long_operation()
    except asyncio.CancelledError:
        await cleanup()                    # release, roll back, log
        raise                              # ✗ NEVER swallow it — the loop
                                           #   needs it to finish cancelling
    finally:
        conn.release()                     # runs on cancellation too

# Cancellation only takes effect AT AN AWAIT. A coroutine in a long
# CPU loop cannot be cancelled until it yields — another reason CPU work
# does not belong on the loop.

# ── LIMITING CONCURRENCY ─────────────────────────────────────────────────
sem = asyncio.Semaphore(10)
async def fetch_limited(url):
    async with sem:                        # at most 10 in flight
        return await client.get(url)
await asyncio.gather(*(fetch_limited(u) for u in urls))
# gather() over 10,000 URLs starts 10,000 connections at once: the target
# rate-limits or falls over, and you exhaust local file descriptors. An
# unbounded gather over a user-supplied list is a denial-of-service on
# both ends.

# ── GRACEFUL SHUTDOWN ────────────────────────────────────────────────────
async def main():
    stop = asyncio.Event()
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGINT, signal.SIGTERM):
        loop.add_signal_handler(sig, stop.set)
    async with asyncio.TaskGroup() as tg:
        tg.create_task(server(stop))
    await drain_in_flight_requests()
# Killing a worker mid-transaction is how partial writes happen.

# ── DIAGNOSIS: MEASURE, DO NOT GUESS ─────────────────────────────────────
py-spy top --pid 1234              # live: where is time actually spent
py-spy dump --pid 1234             # every thread's stack — finds deadlocks
                                   # and the exact blocking call
asyncio.run(main(), debug=True)    # warns on coroutines that block the
                                   # loop for >100ms — the single best
                                   # tool for the freezing-loop bug
loop.slow_callback_duration = 0.05

import faulthandler; faulthandler.dump_traceback_later(30)   # hang → stacks

# ── THE DIAGNOSTIC LADDER ────────────────────────────────────────────────
# "It is not faster with threads"      → CPU-bound. Use processes.
# "The async service freezes"          → a blocking call. debug=True.
# "It hangs and never returns"         → deadlock. py-spy dump.
# "Results are wrong sometimes"        → a race. Lock, or use a queue.
# "Processes are slower than a loop"   → pickling. Increase chunk size.
# "Memory grows without limit"         → an unbounded queue. Set maxsize.

Interview Questions

Beginner: What is the GIL and how does it change your concurrency choice?

It is a mutex inside CPython that allows only one thread to execute Python bytecode at a time, so threads give no parallelism for pure-Python computation — four threads doing arithmetic on four cores run about as fast as one, sometimes slower once contention is added. It exists because CPython manages memory by reference counting, and making every refcount update atomic would slow down single-threaded code, which is the overwhelming majority of Python.

The part people miss is that the GIL is released whenever a thread is not running bytecode: during blocking I/O such as a socket or disk read, and inside many C extensions like numpy and hashlib during long operations. So threads do overlap waiting, and a hundred threads each blocked on a two-hundred-millisecond HTTP call finish in roughly two hundred milliseconds. That gives the rule: I/O-bound work goes to asyncio or threads, CPU-bound work goes to processes, because each process has its own interpreter and its own GIL. The classic surprise — "I added threads and my number crunching got no faster" — is exactly this, and the fix is a process pool.

Beginner: Why can one blocking call cripple an asyncio program?

asyncio is cooperative concurrency on a single thread. The event loop runs one coroutine until it hits an await, at which point that coroutine suspends and the loop is free to run another. Nothing preempts anything — so a call that does not yield, such as time.sleep, requests.get, a blocking database driver, or half a second of parsing, holds the only thread there is. Every other connection waits, including ones that were ready to make progress. A service that handles a thousand connections fine will show a latency spike on all of them from one slow synchronous call.

The fixes are to use async-native libraries — asyncio.sleep, httpx, asyncpg — or to move the blocking work off the loop with asyncio.to_thread. One nuance worth stating: to_thread uses a thread, which helps blocking I/O and GIL-releasing C code but not pure Python CPU work, since that still contends for the GIL and still starves the loop; that case needs a process pool via run_in_executor. Running with asyncio.run(main(), debug=True) makes the loop warn about any callback that blocks for more than a hundred milliseconds, which usually finds the culprit immediately.

Mid: Pick a tool for each: 1000 HTTP calls, resizing 10,000 images, a legacy blocking database driver.

The thousand HTTP calls are I/O-bound with async clients available, so asyncio with a TaskGroup — one thread handles all of them at roughly a kilobyte per task, and the total time approaches the slowest single request. I would add a Semaphore to cap in-flight requests at something the target tolerates, because an unbounded gather over a thousand URLs opens a thousand connections at once and gets you rate-limited or exhausts local file descriptors.

Image resizing is CPU-bound, so ProcessPoolExecutor with one worker per core, batching several images per task so pickling does not dominate. There is a caveat that makes this interesting: Pillow releases the GIL during the actual resize, so threads would also get some parallelism here — which is a good illustration that "CPU-bound" is really about whether the hot loop is Python bytecode or C. I would still start with processes and measure.

The legacy blocking driver is I/O-bound but cannot be awaited, so ThreadPoolExecutor: the driver blocks, but the GIL is released while it waits on the socket, so the waits overlap. The pool size should match the database's connection pool rather than the core count — more threads than connections just queues them somewhere less visible. If the surrounding application is already async, the same thing is spelled asyncio.to_thread, which keeps the loop responsive while the driver blocks in a worker thread.

Mid: Does the GIL make counter += 1 thread-safe?

No, and this is the most consequential misconception about it. counter += 1 compiles to three separate bytecodes — load the value, add one, store it back — and the interpreter can switch threads between any two of them. Two threads can both load 5, both compute 6, and both store 6, losing an update. Running eight threads incrementing a shared counter a hundred thousand times each gives something around 230,000 rather than 800,000, reliably enough to demonstrate in a few seconds.

What the GIL actually guarantees is that the interpreter's own internal state stays consistent — no corrupted reference counts, no torn object headers, no segfaults from concurrent access. It says nothing about your program's invariants. So shared mutable state needs a threading.Lock, and check-then-act sequences like if key not in d: d[key] = v need one even though each individual line happens to be atomic. Some single operations such as list.append are atomic in CPython, but that is an implementation detail that the free-threaded build weakens, so relying on it is a bet with no upside. The design that avoids the whole problem is passing messages through a queue.Queue rather than sharing state — a system with no shared mutable state cannot have a data race.

Senior: A service is slow under load. Walk through diagnosing whether it is a concurrency problem.

The first question is whether the machine is saturated or idle, because those point in opposite directions. One core pegged at 100% with the others idle means CPU-bound single-threaded work — the GIL, or simply a hot loop. All cores idle while latency climbs means the program is waiting on something, and the problem is a dependency or a concurrency limit rather than compute. Memory climbing steadily suggests an unbounded queue or buffer accepting work faster than it drains.

Then I would profile rather than reason. py-spy top --pid attaches to a running process without restarting it and shows where wall-clock time actually goes, and py-spy dump prints every thread's stack, which is how you find a deadlock or the exact blocking call sitting on an event loop. For an async service, running with debug=True and a low slow_callback_duration makes the loop itself report any coroutine that blocked for more than a threshold, which finds the freezing-loop bug directly instead of by inspection. If it hangs rather than being slow, faulthandler.dump_traceback_later gives stacks at the point of the hang.

The patterns those tools distinguish are the ones worth naming. A single synchronous call on an event loop serialises everything and shows up as uniform latency across all requests. A missing timeout means every worker eventually parks on one slow dependency, which presents as total failure caused by a partial outage — the classic cascading failure. A thread pool sized above the database connection pool just moves the queue somewhere with no metrics on it. And a pool of processes on fine-grained tasks can be slower than a plain loop because pickling dominates. What I would resist is changing the concurrency model first: the most common real answer is an N+1 query or a missing index, and parallelising that only multiplies the load on the database.

Senior: How would you design a pipeline that fetches 100,000 URLs and CPU-parses each response?

This is genuinely mixed, so it needs both models rather than a choice between them. The fetching is I/O-bound and belongs in asyncio with an async client and a semaphore bounding in-flight requests to something the targets and the local file descriptor limit tolerate — a hundred or so, not a hundred thousand. The parsing is CPU-bound pure Python, so it belongs in a ProcessPoolExecutor sized to the core count, driven from the loop with run_in_executor. Doing the parse inline in the coroutine would stall the loop and serialise the fetches behind it, which is the failure this design exists to avoid.

The connection between the two stages needs backpressure, or memory becomes the constraint: fetching is much faster than parsing, so an unbounded queue between them accumulates a hundred thousand response bodies. A bounded asyncio.Queue makes fetchers block once parsing falls behind, which is the correct behaviour. Results should be written out incrementally rather than accumulated, for the same reason — the pipeline should have a flat memory profile regardless of input size.

Operationally, several things are not optional at this scale. Every request needs a timeout, or a handful of hung connections permanently occupy semaphore slots. Failures need to be retried with exponential backoff and jitter, and then recorded and skipped rather than allowed to fail the run — with a hundred thousand URLs there will be failures, and a job that dies at ninety percent after two hours is far more expensive than one that logs them. Progress should be checkpointed so a restart resumes rather than refetches. And I would put a per-host rate limit in, because a hundred concurrent requests spread across many hosts is polite while a hundred against one host is an attack.

Before building any of it, though, I would check whether the parse is really CPU-bound in Python. If it is JSON, orjson may make the process pool unnecessary entirely; if it is HTML, lxml releases the GIL and threads would do. Removing a whole tier is worth more than tuning one. And past a single machine this stops being a concurrency problem and becomes a queue and workers problem — Celery or a similar system — because a hundred thousand URLs on one box has no recovery story when the box restarts.

# ✗ THE RACE
counter = 0
def increment():
    global counter
    for _ in range(100_000):
        counter += 1

threads = [threading.Thread(target=increment) for _ in range(8)]
[t.start() for t in threads]; [t.join() for t in threads]
print(counter)          # ~230,000, not 800,000. Different every run.

# WHY: counter += 1 is LOAD_FAST, ADD, STORE_FAST. A thread switch between
# LOAD and STORE loses the other thread's update. The GIL protects the
# INTERPRETER's state, never your invariants.

# ── FIX 1: A LOCK ────────────────────────────────────────────────────────
lock = threading.Lock()
def increment():
    global counter
    for _ in range(100_000):
        with lock:
            counter += 1
# ✓ 800,000 exactly. But ~10x slower than single-threaded here: the lock
# is acquired 800,000 times to protect an operation that takes
# nanoseconds. Correct, and a bad shape.

# ── FIX 2: BATCH LOCALLY, LOCK ONCE ──────────────────────────────────────
def increment():
    global counter
    local = 0
    for _ in range(100_000):
        local += 1              # no contention — a local variable
    with lock:
        counter += local        # ONE lock acquisition per thread
# ✓ 800,000, and fast. The general principle: do the work outside the
# critical section and hold the lock only for the merge.

# concurrent orders that is tens of thousands: the upstream rate-limits or

# generate_pdf is ~800ms of pure Python. During it, NOTHING else on the
# loop progresses — not other orders, not the health check. Under load
# this is the dominant term and it is invisible in per-request timings,
# because every request appears slow rather than one.
receipt = await loop.run_in_executor(process_pool, generate_pdf, results)
# A process pool, not to_thread: pure-Python CPU still holds the GIL in a

# If the payment provider hangs, this coroutine waits forever. Requests
# accumulate, each holding a connection and a DB handle, until the pool is
# exhausted and healthy requests cannot get one either. A PARTIAL outage
# upstream becomes a TOTAL outage here — cascading failure.
async with asyncio.timeout(5):

# Every network call. Not most of them.
# ⚠ And charge() is not idempotent — a timeout does not mean it failed.
#   It needs an idempotency key before any retry is safe.

# ── CAUSE 4: A FIRE-AND-FORGET TASK ──────────────────────────────────────

6 (hard): Design a pipeline fetching 100,000 URLs and CPU-parsing each response.
Solution 
import asyncio, httpx
from concurrent.futures import ProcessPoolExecutor

# ── THE SHAPE: TWO STAGES, TWO MODELS, BOUNDED BETWEEN ───────────────────
#   fetch   I/O-bound   → asyncio, semaphore-limited
#   parse   CPU-bound   → process pool, driven from the loop
#   queue   bounded     → backpressure, so memory stays flat

async def fetch_stage(urls, queue, client, sem):
    async def one(url):
        async with sem:                             # cap in-flight
            for attempt in range(3):
                try:
                    async with asyncio.timeout(10): # EVERY network call
                        r = await client.get(url)
                    await queue.put((url, r.text))  # BLOCKS when full
                    return
                except (httpx.HTTPError, TimeoutError):
                    if attempt == 2:
                        failures.append(url)        # log and CONTINUE
                        return
                    await asyncio.sleep(2 ** attempt * (0.5 + random()))
    async with asyncio.TaskGroup() as tg:
        for u in urls:
            tg.create_task(one(u))
    await queue.put(None)                           # sentinel

async def parse_stage(queue, pool, out):
    loop = asyncio.get_running_loop()
    batch = []
    while (item := await queue.get()) is not None:
        batch.append(item)
        if len(batch) >= 100:                       # BATCH — one pickle
            for rec in await loop.run_in_executor(  # round trip per 100,
                    pool, parse_batch, batch):      # not per item
                out.write(rec)                      # stream out; never
            batch.clear()                           # accumulate results

async def main(urls):
    queue = asyncio.Queue(maxsize=1000)             # ← THE KEY LINE
    sem = asyncio.Semaphore(100)
    with ProcessPoolExecutor() as pool, \
         open("out.jsonl", "w") as out:
        async with httpx.AsyncClient(http2=True) as client:
            async with asyncio.TaskGroup() as tg:
                tg.create_task(fetch_stage(urls, queue, client, sem))
                tg.create_task(parse_stage(queue, pool, out))

# ── EVERY DECISION, AND WHY ──────────────────────────────────────────────
#
# BOUNDED QUEUE     Fetching is ~10x faster than parsing. Unbounded, you
#                   buffer 100,000 response bodies — tens of GB. maxsize
#                   makes fetchers block when parsing falls behind, which
#                   is the correct behaviour, not a limitation.
#
# SEMAPHORE         gather over 100,000 URLs opens 100,000 sockets at
#                   once: upstream rate-limits, and you exhaust local file
#                   descriptors (OSError in unrelated code). Also add a
#                   PER-HOST limit — 100 requests spread over many hosts
#                   is polite; 100 against one host is an attack.
#
# TIMEOUT           Without it a few hung connections permanently occupy
#                   semaphore slots and throughput decays to zero.
#
# PROCESS POOL      Pure-Python parsing on the loop would serialise
#                   everything behind it. to_thread is not enough — the
#                   GIL. A pool is the only real fix.
#
# BATCH OF 100      Per-item run_in_executor pickles once per response;
#                   the overhead exceeds the parse for small documents.
#
# STREAM OUTPUT     Accumulating results rebuilds the memory problem one
#                   stage later. Peak memory must not depend on input size.
#
# TOLERATE FAILURE  With 100,000 URLs there WILL be failures. Retry with
#                   backoff and jitter, then record and skip. A job that
#                   dies at 90% after two hours is the expensive outcome.
#                   Fail the RUN at the end if the failure rate exceeds a
#                   threshold — that distinguishes "some bad URLs" from
#                   "the network is down".
#
# CHECKPOINT        Write completed URLs periodically so a restart resumes
#                   instead of refetching 90,000 URLs.

# ── WHAT I WOULD CHECK BEFORE BUILDING ANY OF IT ─────────────────────────
# Is the parse really CPU-bound in PYTHON?
#   JSON → orjson may remove the process pool entirely
#   HTML → lxml releases the GIL, so to_thread suffices
# Removing a whole tier beats tuning one.

# ── AND THE SCALING LIMIT ────────────────────────────────────────────────
# One machine, one process tree, no recovery if it restarts. Past this,
# it is a queue-and-workers problem (Celery, Ray, Arq) — durable state,
# retries across restarts, horizontal workers. A bigger pool is not the
# next step; a different architecture is.

🎯 Key Takeaways

  • The GIL lets one thread run bytecode at a time, but it is released during I/O and inside many C extensions.
  • Choose by workload: waiting → asyncio or threads; computing → processes. Measure which one you have.
  • Threads on CPU-bound work are not just useless, they are slower than sequential.
  • One blocking call freezes an entire event loop — use async libraries, to_thread, or a process pool for CPU.
  • await means "wait for this"; concurrency comes from TaskGroup or gather.
  • The GIL does not make += 1 atomic — lock shared state, or design so nothing is shared.
  • Every network call needs a timeout; without one, a slow dependency parks every worker.
  • Bound your concurrency with a semaphore and your queues with maxsize, or you fail on connections and memory.
  • Process pools pay off only on coarse-grained work — pickling per item can cost more than the work.
  • Before parallelising, check the algorithm and whether numpy or polars removes the need entirely.
