Modules, Packaging & Environments Intermediate

What you'll master: what actually happens on import and why modules execute exactly once, sys.path and the shadowing bug that makes import random fail, absolute versus relative imports and why ModuleNotFoundError depends on how you launched the process, circular imports and the three real fixes, virtual environments and the manifest/lockfile chain that makes an install reproducible, the src layout and why it exists, and building and publishing a package. Prerequisites: OOP & Dataclasses.

Part 1 — What import Actually Does

import math                       # bind the module object to the name `math`
from math import sqrt, pi         # bind two names from it
from utils import helper as h     # bind under a different name
import package.sub.module         # imports EVERY package on the way down

# ── THE FOUR STEPS ───────────────────────────────────────────────────────
# 1. Is it already in sys.modules? → return that object. Done.
# 2. Search sys.path for it.
# 3. EXECUTE the module top to bottom, in a fresh namespace.
# 4. Store it in sys.modules, then bind the name in the importer.

# Step 1 is the important one: a module's code runs EXACTLY ONCE per
# process, no matter how many files import it.

# config.py
print("loading config")
SETTINGS = load_from_disk()       # runs once, at FIRST import

# a.py: import config    → prints "loading config"
# b.py: import config    → prints nothing; same object

import sys
sys.modules["config"]             # the cache. `del` from it to force a
                                  # reload — almost always a mistake, since
                                  # existing references keep the old module.

# ── IMPORT-TIME SIDE EFFECTS ARE A DESIGN CHOICE ─────────────────────────
# db.py
connection = psycopg.connect(DATABASE_URL)   # ✗ runs on import
# Now importing db to read one constant opens a connection. Tests cannot
# import the module without a database. Documentation tools cannot import
# it. A CLI's --help takes 3 seconds.

# ✓ Defer the work:
_connection = None
def get_connection():
    global _connection
    if _connection is None:
        _connection = psycopg.connect(DATABASE_URL)
    return _connection

# Keep module top-level to: imports, constants, class and function
# definitions. Anything that touches the network, filesystem, or clock
# belongs in a function.

# ── THE __main__ GUARD ───────────────────────────────────────────────────
def main(): ...

if __name__ == "__main__":        # "__main__" when run directly;
    main()                        # the module's name when imported
# Without it, importing the module to test main() also RUNS it.

# ── from module import * ─────────────────────────────────────────────────
from utils import *               # ✗ binds every public name — you cannot
                                  #   tell where anything came from, and a
                                  #   new name upstream can shadow a local
__all__ = ["public_fn", "Widget"] # what * exports, and the module's
                                  # declared public API. Worth defining
                                  # even though you should not use *.

Part 2 — sys.path, and Why Imports Break

import sys
sys.path        # the search order:
#   1. the directory of the SCRIPT being run (or "" = cwd for -c / REPL)
#   2. PYTHONPATH entries
#   3. the standard library
#   4. site-packages (installed third-party code)

# ── THE SHADOWING BUG ────────────────────────────────────────────────────
# You write random.py in your project directory. Then:
import random
random.randint(1, 10)             # AttributeError: module 'random' has no
                                  # attribute 'randint'
# Your file came FIRST in sys.path. Every library that imports random now
# gets yours instead. The traceback points at library code, not at you.
#
# Names that catch people: random, email, string, types, test, code, json,
# logging, queue, select, signal, socket, token, copy, io, csv, secrets.
print(random.__file__)            # ← what actually got imported. First
                                  #   thing to check on a weird ImportError.

# Same failure with __pycache__: deleting a .py leaves a stale .pyc that
# can still import in some layouts. `find . -name __pycache__ -exec rm -rf`
# when an import makes no sense at all.

# ── ABSOLUTE vs RELATIVE ─────────────────────────────────────────────────
# myapp/
# ├── __init__.py
# ├── api.py
# └── services/
#     ├── __init__.py
#     └── billing.py

# In myapp/services/billing.py:
from myapp.api import Client          # ABSOLUTE — preferred
from ..api import Client              # relative — one dot = this package,
                                      # two = parent
from .helpers import fmt              # same package

# Absolute imports say where the code lives, survive a file being moved,
# and are unambiguous in a traceback. Use relative imports only for
# siblings inside one package, and never more than two dots — `from ...`
# is a signal the package is too deeply nested.

# ── THE ERROR EVERYONE HITS ──────────────────────────────────────────────
python myapp/services/billing.py
# ImportError: attempted relative import with no known parent package
#
# Running a file directly makes it __main__, with no package context, so
# relative imports have nothing to be relative TO. And sys.path[0] becomes
# myapp/services/, not the project root, so `from myapp.api import ...`
# fails too.
#
# ✓ Run it AS A MODULE, from the project root:
python -m myapp.services.billing
# Now sys.path[0] is the project root and the package context exists.
#
# ✓ Or give the package a real entry point:
[project.scripts]
myapp = "myapp.cli:main"          # in pyproject.toml → an `myapp` command

# ── NEVER DO THIS ────────────────────────────────────────────────────────
sys.path.append("../..")          # ✗ depends on the cwd, breaks in tests,
                                  #   in CI, and when the file moves
sys.path.insert(0, os.path.dirname(__file__))   # ✗ same
# The real fix is `pip install -e .` — the package becomes importable from
# anywhere, exactly as it will be in production.

Part 3 — Circular Imports

# models.py
from services import notify              # ← at import time
class User: ...

# services.py
from models import User                  # ← at import time
def notify(user: User): ...

# ImportError: cannot import name 'User' from partially initialized module
# 'models' (most likely due to a circular import)

# ── WHY, MECHANICALLY ────────────────────────────────────────────────────
# import models
#   → models is added to sys.modules, EMPTY, then starts executing
#   → line 1: from services import notify
#       → services is added to sys.modules, starts executing
#       → line 1: from models import User
#           → models IS in sys.modules → returns it immediately
#           → but it is empty: `class User` has not run yet
#           → ImportError
#
# The module is registered before it is executed — that is what stops
# infinite recursion, and it is why you get a HALF-BUILT module rather
# than a hang.

# ── FIX 1: EXTRACT THE SHARED PIECE (best) ───────────────────────────────
# models.py      — defines User, imports nothing from services
# services.py    — imports models
# A cycle means two modules each own part of one concept. Splitting it out
# usually reveals the missing abstraction.

# ── FIX 2: TYPE_CHECKING, WHEN THE IMPORT IS ONLY FOR ANNOTATIONS ────────
from typing import TYPE_CHECKING
if TYPE_CHECKING:                        # False at runtime; mypy still
    from models import User              # sees it

def notify(user: "User") -> None: ...    # a string, so no runtime lookup
# With `from __future__ import annotations` the quotes are unnecessary —
# all annotations become strings. This solves a large share of real
# cycles, because most of them are type-hint imports.

# ── FIX 3: IMPORT INSIDE THE FUNCTION (last resort) ──────────────────────
def notify(user):
    from services import send_email      # runs at CALL time, by which
    send_email(...)                      # point both modules are complete
# Works, and hides the dependency from anyone reading the imports. Also
# costs a sys.modules lookup per call. Acceptable for a genuinely
# optional or heavy dependency; a smell when used to paper over layering.

# ── FIX 4: DEPEND ON AN INTERFACE, NOT A MODULE ──────────────────────────
class UserService:
    def __init__(self, notifier):        # injected — no import at all
        self.notifier = notifier
# The cycle disappears because the dependency is passed in rather than
# imported. See the composition section of OOP & Dataclasses.

# ── AND ONE THAT LOOKS LIKE A FIX ────────────────────────────────────────
import services                          # module-level, no `from`
def notify(user):
    services.send_email(...)             # attribute looked up at CALL time
# This often works, because binding the MODULE only needs it to exist in
# sys.modules, not to be finished. It is fragile: it breaks the moment
# anything is needed at import time, and it depends on which module the
# process imported first.
Key insight: nearly every import problem is a question about time rather than about syntax. A module executes once, at first import, and everything at its top level happens then — which is why a circular import hands you a half-built module, why a connection opened at module scope makes the package untestable, and why a relative import fails when the file is run directly rather than as part of a package. Once you ask "what has finished running at this exact moment?", the errors stop being mysterious.

Part 4 — Virtual Environments and Reproducibility

# ── WHY ISOLATION IS NOT OPTIONAL ────────────────────────────────────────
# Project A needs django 4.2, project B needs django 5.1. Installed
# globally, one of them is broken at any moment. Worse, `pip install` into
# the system Python on Linux can break OS tooling that depends on it.

python -m venv .venv
source .venv/bin/activate         # Windows: .venv\Scripts\activate
pip install requests
deactivate

# A venv is a directory with its own interpreter symlink and site-packages,
# plus a pyvenv.cfg pointing at the base Python. Activation just puts its
# bin/ first on PATH. Nothing magic — which is why `.venv` is disposable
# and MUST be gitignored: it contains absolute paths and platform-specific
# binaries that are meaningless on another machine.

which python                      # ← confirm which interpreter you are on
python -c "import sys; print(sys.prefix)"

# ── THE REPRODUCIBILITY CHAIN ────────────────────────────────────────────
#
#   pyproject.toml   what you WANT      "fastapi>=0.110"
#   uv.lock          what you GOT       fastapi==0.115.6, plus all 34
#                                       transitive deps, with hashes
#   CI: uv sync      installs the LOCK, not the manifest
#
# Without the lockfile, two installs a week apart resolve differently and
# a transitive dependency you never chose changes under you. This is the
# same problem package-lock.json solves for npm.

# pip alone, the old way:
pip freeze > requirements.txt     # ⚠ dumps the whole env, including things
                                  #   you did not ask for, with no record
                                  #   of WHICH were direct dependencies
# Better with pip: requirements.in (direct) → pip-compile → requirements.txt
# (locked, hashed). Commit both.

# ── uv: THE CURRENT DEFAULT ──────────────────────────────────────────────
uv init myapp                     # pyproject.toml + .venv + git
uv add fastapi                    # resolves, installs, updates uv.lock
uv add --dev pytest ruff mypy     # dev-only group
uv sync                           # recreate the env EXACTLY from the lock
uv run pytest                     # run inside the env, no activation
uv lock --upgrade-package fastapi # deliberate, single-package bump
# 10-100x faster than pip, and it manages the venv, so there is no
# "did I activate it?" step. Poetry and PDM solve the same problem.

# ── PINNING: HOW TIGHT ───────────────────────────────────────────────────
dependencies = [
  "fastapi>=0.110,<0.116",        # APPLICATION: a range in the manifest,
  "pydantic>=2.0",                # exact versions in the LOCKFILE
]
# LIBRARY: keep ranges wide and do NOT commit a lockfile — you cannot know
#   what else your consumer installs, and a narrow pin makes your library
#   uninstallable alongside others.
# APPLICATION: commit the lockfile. You control the deployment; identical
#   bytes everywhere is the goal.

# ── COMMIT / IGNORE ──────────────────────────────────────────────────────
# ✓ commit:  pyproject.toml, uv.lock, .python-version
# ✗ ignore:  .venv/, __pycache__/, *.egg-info/, dist/, build/

├── pyproject.toml
├── uv.lock
├── README.md
├── src/
│   └── myapp/
│       ├── __init__.py
│       ├── __main__.py          # enables `python -m myapp`
│       ├── cli.py
│       ├── api.py
│       └── services/
│           ├── __init__.py
│           └── billing.py
└── tests/

# ── WHY src/ ─────────────────────────────────────────────────────────────
# Without it, the project root is on sys.path when you run pytest from
# there, so `import myapp` finds the SOURCE DIRECTORY — not the installed
# package. Consequences:
#   - tests pass against code that was never packaged
#   - a missing entry in pyproject.toml's package list is invisible until
#     a user pip-installs it and gets ModuleNotFoundError
#   - data files missing from the wheel are not caught
# With src/, the only way to import myapp is to install it, so tests
# exercise exactly what ships. This is the single highest-value layout
# decision in a Python project.

pip install -e .                  # editable: the installed package points
                                  # at your source, so edits take effect
                                  # without reinstalling

# ── pyproject.toml ───────────────────────────────────────────────────────
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "myapp"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27", "pydantic>=2"]

[project.scripts]
myapp = "myapp.cli:main"          # installs a `myapp` command on PATH

[dependency-groups]
dev = ["pytest>=8", "ruff", "mypy"]

[tool.ruff]
line-length = 100                 # tool config lives here too — one file
                                  # instead of setup.py + setup.cfg +
                                  # .flake8 + MANIFEST.in

# ── __init__.py ──────────────────────────────────────────────────────────
# src/myapp/__init__.py
from myapp.api import Client      # curate the public API
__all__ = ["Client"]
__version__ = "0.1.0"
# Keep it SMALL. Everything here runs on `import myapp`, so a heavy
# __init__ makes every import of any submodule slow. Never put logic in it.

# ── BUILD AND PUBLISH ────────────────────────────────────────────────────
uv build                          # → dist/myapp-0.1.0-py3-none-any.whl
                                  #   and dist/myapp-0.1.0.tar.gz
uv publish                        # to PyPI (twine upload also works)
# Test on TestPyPI first. A version number on PyPI can never be reused,
# even after deletion — so a bad release means bumping, not replacing.

Part 6 — Deploying and Debugging Imports

# ── WHEEL vs SOURCE DISTRIBUTION ─────────────────────────────────────────
# .whl  — pre-built, just unzipped into site-packages. Fast, no compiler.
# .tar.gz (sdist) — source; pip must BUILD it, which for C extensions
#   needs a toolchain the container may not have.
# A slow or failing install in CI is usually pip falling back to an sdist
# because no wheel matches the platform or Python version.

# ── DOCKER: LAYER CACHING ────────────────────────────────────────────────
FROM python:3.12-slim
WORKDIR /app
COPY pyproject.toml uv.lock ./          # ← dependencies FIRST
RUN uv sync --frozen --no-dev           # cached unless the lock changes
COPY src/ ./src/                        # ← code last, changes every commit
RUN uv sync --frozen --no-dev
CMD ["uv", "run", "myapp"]
# Copying the whole project before installing invalidates the dependency
# layer on every source edit — a 90-second rebuild instead of 2 seconds.
#
# --frozen fails if the lockfile does not match pyproject.toml, which is
# what you want in CI: no silent re-resolution during a build.

# ── DIAGNOSING AN IMPORT ─────────────────────────────────────────────────
python -c "import myapp; print(myapp.__file__)"    # WHICH copy loaded?
python -c "import sys; print(sys.path)"            # where it searched
python -X importtime -c "import myapp"             # what is slow
pip show myapp                                     # version and location
pip list | grep myapp
python -m site                                     # site-packages dirs

# The four causes of a confusing ImportError, in order of frequency:
#   1. the wrong interpreter — a global python, not the venv's
#   2. a local file shadowing a stdlib or installed module
#   3. running a file directly instead of `python -m package.module`
#   4. the package not installed at all (editable install forgotten)

# ── OPTIONAL DEPENDENCIES ────────────────────────────────────────────────
try:
    import orjson as json_impl
except ImportError:
    import json as json_impl          # graceful fallback

[project.optional-dependencies]
fast = ["orjson>=3"]                  # pip install myapp[fast]

# ── LAZY IMPORT FOR STARTUP TIME ─────────────────────────────────────────
def to_dataframe(rows):
    import pandas as pd               # 1.5s import, only if this is called
    return pd.DataFrame(rows)
# Legitimate for heavy optional dependencies in a CLI, where --help should
# not take two seconds. Not a general pattern — it hides dependencies.

Interview Questions

Beginner: What does if __name__ == "__main__": do, and why use it?

Python sets a module's __name__ to "__main__" when it is the file being run directly, and to the module's dotted name when it is imported. The guard therefore runs the entry-point code only in the first case. Without it, importing the module — to reuse one of its functions, or simply because a test collector imported it — also executes whatever is at the bottom of the file, so a script that starts a server or writes to a database does that as a side effect of the import. The same reasoning applies more broadly: module top level should hold imports, constants, and class and function definitions, and anything that touches the network, the filesystem or the clock belongs inside a function, because it will otherwise run at import time whether you wanted it to or not.

Beginner: Why are virtual environments necessary, and what does a lockfile add?

A virtual environment gives a project its own site-packages, so two projects needing different versions of the same library can coexist and neither can break the system Python that the OS may depend on. That solves conflict, but not reproducibility: a manifest usually declares ranges like fastapi>=0.110, so an install today and an install next month can legitimately resolve to different versions, and the same is true of every transitive dependency you never chose explicitly.

The lockfile closes that gap by recording the exact resolved version of every package in the tree, usually with hashes. The chain is that pyproject.toml declares intent, the lockfile records what was actually resolved, and CI and production install from the lockfile rather than re-resolving. It is the same relationship as package.json to package-lock.json. The one nuance is that this applies to applications: a library should keep its ranges wide and not ship a lockfile, because pinning exact versions makes it uninstallable alongside anything else.

Mid: How do you diagnose and fix a circular import?

The symptom is ImportError: cannot import name X from partially initialized module. The mechanism is that a module is registered in sys.modules before its body runs — which is what prevents infinite recursion — so when the cycle comes back around, the second import finds the entry, returns it immediately, and gets a module in which the name it wants has not been defined yet. Reading the traceback bottom-up shows the exact chain, and it always depends on which module was imported first, which is why the failure can look intermittent across different entry points.

There are three fixes worth knowing, in order of preference. The best is to extract the shared piece into a third module both can import, because a cycle almost always means two modules each own part of one concept and the abstraction is missing. Second, if the import exists only for type annotations — which covers a large share of real cycles — put it under if TYPE_CHECKING: and use a string annotation, or from __future__ import annotations; the import then does not exist at runtime at all while type checkers still see it. Third, and as a last resort, move the import inside the function that needs it, so it happens at call time when both modules are complete. That works but hides the dependency from anyone reading the import block, so I treat it as a signal that the layering is wrong rather than as a solution. The structural answer, where it applies, is dependency injection: pass the collaborator in instead of importing it, and the cycle stops existing.

Mid: Someone reports import random raising AttributeError: no attribute 'randint'. What happened?

There is a file called random.py in the directory the script was launched from. The first entry in sys.path is the script's own directory, which comes before the standard library, so their file wins and every subsequent import random in the process — including inside third-party libraries — gets it. The error surfaces as a missing attribute rather than a missing module, and the traceback usually points into library code that has nothing to do with the cause, which is why it is confusing out of proportion to how simple it is.

The diagnosis is one line: print(random.__file__) shows which file was actually loaded. The fix is to rename the local file, and to delete any stale __pycache__ directory, since a leftover .pyc can keep importing after the .py is gone. The names that catch people are the short, generic stdlib ones — email, string, types, test, code, json, logging, queue, socket, copy, io, secrets. Using a src/ layout with a proper package prefix largely prevents the whole class of problem, because your modules are then myapp.email rather than email.

Senior: Why use a src/ layout, and what does it prevent?

Without it, the project root sits on sys.path whenever you run anything from there, so import myapp resolves to the source directory rather than to the installed package. That means the test suite never exercises what actually ships, and a whole class of packaging bug becomes invisible: a subpackage missing from the package list in pyproject.toml, a data file or template not included in the wheel, an import that only worked because of a file sitting next to it in the repo. All of those pass CI and fail for the first person who runs pip install.

With src/, the package is simply not importable unless it has been installed, so pip install -e . becomes a required step and every test run goes through the real packaging path. It also removes the shadowing problem, because top-level module names in the repo can no longer collide with the standard library or with installed packages. The cost is one extra install step during setup, which an editable install makes a one-off — and in exchange, the difference between "works in the repo" and "works when installed" stops existing. It is the highest-value layout decision in a Python project and effectively free.

Senior: Design the dependency management for a service that must be reproducible and secure.

The foundation is a manifest declaring direct dependencies with deliberate ranges, plus a committed lockfile pinning the entire transitive tree with hashes. CI installs with something equivalent to uv sync --frozen, which fails if the lockfile and manifest disagree rather than silently re-resolving — that check is what makes "it built differently in CI" impossible. The same lockfile is what the Docker image installs from, so the artifact that passed tests contains identical bytes to the one that deploys. Hashes matter here beyond reproducibility: they defeat a compromised index serving different content for a version that already resolved.

Upgrades should be routine and small rather than rare and large. A scheduled job — Dependabot, Renovate, or a weekly uv lock --upgrade — opens a PR with the diff, the full test suite runs against it, and a human reviews it. The failure mode to avoid is a service that has not updated in eighteen months and now needs a forty-package jump to patch one CVE, which is when teams start shipping unreviewed upgrades under time pressure. Security scanning belongs in the same pipeline: pip-audit or uv pip audit against the lockfile catches known vulnerabilities, and because it reads the lock it sees the transitive packages nobody chose explicitly, which is where most advisories land.

Two more things I would insist on. Pin the Python version itself — in .python-version, in requires-python, and in the base image tag — because a minor version change alters resolution and behaviour as much as a dependency bump does. And build images in layers ordered by change frequency, copying the manifest and lock and installing before copying source, so a code change does not invalidate the dependency layer. That last one is a build time issue rather than a correctness one, but a ninety-second rebuild on every commit changes how often people are willing to run the pipeline, which does eventually become a correctness issue.

# Dumps everything installed, with no distinction between what you asked
# for and what came along transitively. Removing a package leaves its
# dependencies behind forever, and nobody can tell which lines are
# deliberate. If you must use pip:
#   requirements.in   → direct deps      (edit this)
#   pip-compile       → requirements.txt (locked + hashed, commit it)
#   pip-sync          → install exactly that

# ── VERIFY THE ISOLATION ─────────────────────────────────────────────────
uv run python -c "import sys; print(sys.prefix)"    # ends in .venv
uv run python -c "import fastapi; print(fastapi.__file__)"
3 (medium): Fix this circular import three different ways and say which you would ship.
Solution 
# ✗ THE CYCLE
# models.py
from services import send_welcome_email
class User:
    def register(self):
        send_welcome_email(self)

# services.py
from models import User
def send_welcome_email(user: User): ...

# ImportError: cannot import name 'User' from partially initialized module
# 'models'. models is in sys.modules but empty — `class User` has not run.

# ── FIX A: TYPE_CHECKING (if the import is only for annotations) ─────────
# services.py
from __future__ import annotations
from typing import TYPE_CHECKING
if TYPE_CHECKING:
    from models import User       # never executed at runtime

def send_welcome_email(user: User): ...    # a string annotation
# Zero runtime cost, mypy still checks it. Solves the majority of real
# cycles, because most of them ARE type-hint imports.
# ⚠ Does not help if you need User at runtime — isinstance, a default
#   argument, or a Pydantic model that resolves annotations.

# ── FIX B: EXTRACT THE SHARED PIECE ──────────────────────────────────────
# models.py      — defines User. Imports nothing from services.
# services.py    — imports models.
# events.py      — the shared event/protocol both need, if any.
#
# The cycle was telling you that models knows how registration notifies
# people, which is not a model's job. Splitting reveals the layering.

# ── FIX C: DEPENDENCY INJECTION ──────────────────────────────────────────
# models.py — no import of services AT ALL
class User:
    def register(self, notifier):
        notifier.send_welcome(self)

# wiring happens at the edge:
user.register(EmailNotifier())
# The dependency is passed in rather than imported, so there is nothing to
# cycle. Tests pass a fake with no patching.

# ── FIX D: FUNCTION-LEVEL IMPORT (last resort) ───────────────────────────
class User:
    def register(self):
        from services import send_welcome_email    # at CALL time
        send_welcome_email(self)
# Works. Hides the dependency from the import block, costs a sys.modules
# lookup per call, and papers over the layering problem rather than
# fixing it.

# ── WHAT I WOULD SHIP ────────────────────────────────────────────────────
# B or C. A cycle is a design signal: two modules each own part of one
# concept, or a low-level module is reaching up into a high-level one.
# A is the right answer when the import genuinely is annotation-only —
# it is not a workaround, it is correct. D only when a dependency is
# genuinely optional or very heavy.
4 (medium): A colleague's imports work locally and fail in CI. Walk through the diagnosis.
Solution 
# ModuleNotFoundError: No module named 'myapp'
# ...but it works on their laptop.

# ── STEP 1: WHICH INTERPRETER? ───────────────────────────────────────────
python -c "import sys; print(sys.executable, sys.prefix)"
# The most common answer: CI is on the system Python because the venv was
# created but never activated, or a step ran in a fresh shell.
# uv run / poetry run avoid this entirely — no activation state to lose.

# ── STEP 2: WAS IT INSTALLED? ────────────────────────────────────────────
pip list | grep myapp
# Absent → the local machine has an old `pip install -e .` from months ago
# that CI never performed. This is the classic "works on my machine": the
# laptop has state the repo does not describe.

# ── STEP 3: WHAT IS ON THE PATH? ─────────────────────────────────────────
python -c "import sys; print('\n'.join(sys.path))"
# Locally, sys.path[0] is the project root (they run from there), so a
# flat-layout `import myapp` finds the SOURCE FOLDER without any install.
# CI runs from a different directory and that accident does not happen.
#
# → the real bug is a flat layout. With src/, it fails identically in both
#   places, immediately, which is the point.

# ── STEP 4: WHICH FILE ACTUALLY LOADED? ──────────────────────────────────
python -c "import myapp; print(myapp.__file__)"
# Points at the repo → not installed, found via cwd.
# Points at site-packages → correctly installed.

# ── STEP 5: THE OTHER USUAL SUSPECTS ─────────────────────────────────────
# - a stale local file shadowing a stdlib name (check module.__file__)
# - `python pkg/mod.py` instead of `python -m pkg.mod` → relative imports
#   fail with "no known parent package"
# - case sensitivity: MyApp/ imports fine on macOS and Windows, fails on
#   the Linux CI runner. Silent locally, fatal in CI.
# - a __pycache__/*.pyc left behind after a .py was deleted

# ── THE STRUCTURAL FIX ───────────────────────────────────────────────────
# src/ layout          → importable only when installed, so dev == CI
# pip install -e .     → in the CI setup step AND in the README
# uv sync --frozen     → the environment is described by committed files,
#                        not by whatever accumulated on a laptop
# No sys.path.append() anywhere in the codebase.
5 (hard): Importing your package takes 4 seconds. Find and fix it.
Solution 
# ── MEASURE FIRST ────────────────────────────────────────────────────────
python -X importtime -c "import myapp" 2>&1 | sort -k2 -rn | head -20
# import time: self [us] | cumulative | imported package
#    1834521 |    1834521 | pandas
#     892341 |     892341 | tensorflow
#      45210 |      45210 | myapp.utils

# ── CAUSE 1: A HEAVY __init__.py ─────────────────────────────────────────
# src/myapp/__init__.py
from myapp.ml import Predictor        # → imports tensorflow
from myapp.reports import to_excel    # → imports pandas
from myapp.api import Client
# `import myapp.config` to read one constant now costs 4 seconds, because
# __init__ runs first and pulls in the entire dependency graph.

# ✓ FIX: keep __init__ to genuinely universal exports, or lazy-load:
def __getattr__(name):                # PEP 562: module-level __getattr__
    if name == "Predictor":
        from myapp.ml import Predictor
        return Predictor
    raise AttributeError(name)
# `from myapp import Predictor` still works, and pays for tensorflow only
# if someone actually asks for it.

# ── CAUSE 2: WORK AT MODULE SCOPE ────────────────────────────────────────
# config.py
SETTINGS = requests.get(CONFIG_URL).json()    # ✗ a NETWORK CALL on import
COUNTRIES = pd.read_csv("countries.csv")      # ✗ disk + pandas on import

# ✓ Defer it:
@functools.cache
def get_settings():
    return requests.get(CONFIG_URL).json()
# Now import is instant, the work happens once on first use, and the module
# can be imported by tests and doc tools with no network.

# ── CAUSE 3: A HEAVY OPTIONAL DEPENDENCY ─────────────────────────────────
import pandas as pd                   # top of the module

def to_dataframe(rows):               # ...used by ONE function
    return pd.DataFrame(rows)

# ✓ Import inside the function:
def to_dataframe(rows):
    import pandas as pd               # 1.5s, only for callers who need it
    return pd.DataFrame(rows)
# Legitimate for heavy, rarely-used dependencies — a CLI's --help should
# not take 4 seconds. Not a general pattern: it hides the dependency from
# the import block, so use it deliberately and comment why.

# ── WHY IT MATTERS BEYOND ANNOYANCE ──────────────────────────────────────
# - AWS Lambda / Cloud Run cold starts pay this on EVERY scale-up
# - a CLI feels broken at 4 seconds for --help
# - pytest pays it once per worker process
# - autocomplete and language servers import your package repeatedly

# ── VERIFY ───────────────────────────────────────────────────────────────
python -X importtime -c "import myapp" 2>&1 | tail -3
# and pin it so it does not regress:
def test_import_is_fast():
    t = timeit.timeit("import myapp", number=1)
    assert t < 0.3
6 (hard): Design the packaging and dependency policy for a team shipping both a library and a service.
Solution 
# ── THE CORE ASYMMETRY ───────────────────────────────────────────────────
# A LIBRARY is installed ALONGSIDE unknown other packages. It must be
#   flexible: wide ranges, no lockfile shipped, no opinions about the
#   consumer's environment.
# A SERVICE controls its own deployment. It must be exact: a committed
#   lockfile, pinned Python, identical bytes in CI and production.
# Applying either policy to the other is the mistake.

# ── LIBRARY: mylib/pyproject.toml ────────────────────────────────────────
[project]
name = "mylib"
requires-python = ">=3.10"            # as wide as you actually test
dependencies = [
  "httpx>=0.24,<1.0",                 # a range: floor = features you use,
  "pydantic>=2.0,<3.0",               # ceiling = next MAJOR only
]
[project.optional-dependencies]
fast = ["orjson>=3"]                  # pip install mylib[fast]

# uv.lock EXISTS in the repo for reproducible CI, but is NOT in the wheel
# and does not constrain consumers.
#
# ✗ dependencies = ["httpx==0.27.2"]
#   An exact pin makes mylib uninstallable next to anything else that
#   needs a different httpx. Libraries pinning exactly is how dependency
#   hell is manufactured.
#
# TEST THE RANGE, do not just declare it:
#   matrix: python 3.10-3.13 × [oldest pinned deps, newest]
#   The "oldest" leg is what catches a lower bound that was never true.

# ── SERVICE: myservice/pyproject.toml ────────────────────────────────────
[project]
requires-python = "==3.12.*"          # ONE version. You control the image.
dependencies = ["mylib>=2.1", "fastapi>=0.110,<0.116"]

# uv.lock COMMITTED. CI: uv sync --frozen  (fails on any drift)
# .python-version committed. Base image pinned by digest, not by tag.

# ── VERSIONING THE LIBRARY: SEMVER, ENFORCED ─────────────────────────────
# MAJOR  removing or renaming public API, changing a signature or a return
#        type, tightening validation
# MINOR  new API, new optional argument
# PATCH  bug fix with no signature change
#
# Deprecate before removing — one MINOR with a warning, remove in the next
# MAJOR:
warnings.warn("old_fn() is deprecated, use new_fn()",
              DeprecationWarning, stacklevel=2)

# ── THE MONOREPO QUESTION ────────────────────────────────────────────────
# Same repo, separate packages, with the service depending on the library
# via a workspace/path dependency in dev and a version in production:
[tool.uv.sources]
mylib = { workspace = true }          # dev: use the local source
# CI still builds and installs mylib as a WHEEL before testing the
# service, so the packaging path is exercised — otherwise you discover a
# missing file only after publishing.

# ── SUPPLY CHAIN ─────────────────────────────────────────────────────────
# - hashes in the lockfile (defeats a compromised index)
# - pip-audit against the LOCK (transitive deps are where CVEs live)
# - Dependabot/Renovate weekly: small reviewed PRs, full test suite
# - publish with a PyPI trusted publisher (OIDC), not a long-lived token
# - never reuse a version number — PyPI forbids it even after deletion

# ── WHY WEEKLY, SMALL UPGRADES ───────────────────────────────────────────
# The alternative is a service that has not updated in 18 months and now
# needs a 40-package jump to patch one CVE, under time pressure, with no
# way to tell which change broke the test that just went red. Routine
# small upgrades are a correctness practice, not hygiene theatre.

# ── LAYOUT, BOTH PROJECTS ────────────────────────────────────────────────
# src/ layout, so tests import the INSTALLED package and packaging bugs
# surface in CI rather than in the first bug report after release.

🎯 Key Takeaways

  • A module executes once per process, at first import — everything at its top level is an import-time side effect.
  • Keep module scope to imports, constants and definitions; anything touching the network, disk or clock goes in a function.
  • sys.path[0] is the script's own directory, so a local random.py shadows the stdlib for the whole process.
  • Prefer absolute imports; run modules with python -m pkg.mod, never python pkg/mod.py.
  • Never manipulate sys.path — pip install -e . is the real fix.
  • A circular import hands you a half-built module because registration happens before execution; extract the shared piece, or use TYPE_CHECKING.
  • A venv isolates; a lockfile makes the install reproducible. You need both, and CI must install from the lock.
  • Applications pin exactly via a committed lockfile; libraries keep ranges wide and ship no lockfile.
  • The src/ layout forces tests to import the installed package, so packaging bugs fail in CI instead of after release.
  • Keep __init__.py to re-exports — everything in it runs on every import of any submodule.
