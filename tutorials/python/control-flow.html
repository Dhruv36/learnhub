Control Flow & Functions Basics

What you'll master: truthiness and the comparison traps that follow from it, loops with else and why iterating while mutating breaks, the five kinds of function parameter and the rules governing their order, closures and the late-binding gotcha that catches everyone, and structural pattern matching. Prerequisites: Syntax, Types & Variables — particularly the name/object model, which explains most of what follows.

Part 1 — Truthiness and Conditionals

# Every object has a truth value. These are ALL falsy:
False, None, 0, 0.0, 0j, Decimal(0), Fraction(0, 1)
"", (), [], {}, set(), range(0)
# Everything else is truthy — including "0", "False", [0] and {} vs {"a": 1}.

if items:              # ✓ idiomatic: "if there are any items"
    process(items)

if len(items) > 0:     # ✗ works, but noisier and slower
if items != []:        # ✗ compares against a throwaway list

# HOW IT WORKS: Python calls __bool__(), then falls back to __len__() != 0,
# and defaults to True if neither exists.
class Basket:
    def __init__(self, items): self.items = items
    def __len__(self): return len(self.items)    # now truthiness works

if Basket([]):         # False — __len__ returned 0
    ...

# ── THE TRAP THAT CAUSES REAL BUGS ───────────────────────────────────────
def fetch(limit=None):
    if not limit:              # ✗ limit=0 is treated as "not supplied"
        limit = 100
    ...

def fetch(limit=None):
    if limit is None:          # ✓ only None means "not supplied"
        limit = 100
    ...
# 0, "" and [] are all legitimate values that `not x` silently discards. Use
# `is None` whenever None is the sentinel — this is the single most common
# source of "it works except when the value is zero".

# ── CHAINED COMPARISONS ──────────────────────────────────────────────────
if 0 <= index < len(items):    # ✓ reads like maths; evaluates index ONCE
if 0 <= index and index < len(items):    # equivalent, more typing

# Chaining works for any comparison operators, and each operand is evaluated
# at most once — which matters when the middle term is a function call:
if 0 < expensive() < 100:      # expensive() runs ONCE

# ── CONDITIONAL EXPRESSIONS ──────────────────────────────────────────────
status = "active" if user.is_enabled else "disabled"

# Note `x if cond else y` — Python puts the condition in the middle, unlike
# the ternary in most languages. Nesting them becomes unreadable fast; past
# two levels use a normal if/elif or a dict lookup.

# ── THE WALRUS OPERATOR ──────────────────────────────────────────────────
if (n := len(data)) > 100:
    print(f"Too many items: {n}")     # n is bound and reusable

while (line := file.readline()):      # assign and test in one step
    process(line)

# It earns its place when the value is needed in BOTH the test and the body.
# Using it purely to compress two lines makes code harder to scan.

Part 2 — Loops

# Python's for loop iterates over an ITERABLE, never an index counter.
for item in items:                    # ✓ idiomatic
for i in range(len(items)):           # ✗ almost always the wrong tool
    item = items[i]

# When you genuinely need the index:
for i, item in enumerate(items, start=1):
    print(f"{i}. {item}")

# Iterating two sequences together:
for name, score in zip(names, scores):
    ...
# zip STOPS at the shortest input, silently. If unequal lengths are a bug,
# say so explicitly:
for name, score in zip(names, scores, strict=True):   # 3.10+ → ValueError

# ── LOOP ELSE: runs if the loop was NOT broken out of ─────────────────────
for user in users:
    if user.is_admin:
        admin = user
        break
else:
    raise LookupError("No admin found.")   # only if break never ran

# Read `else` here as "no break". It is genuinely useful for search loops,
# and it is also one of Python's least-known features — a comment helps.

# ── MUTATING WHILE ITERATING: the classic bug ────────────────────────────
items = [1, 2, 3, 4, 5, 6]
for item in items:
    if item % 2 == 0:
        items.remove(item)     # ✗ skips elements
print(items)                   # [1, 3, 5] here, but the mechanism is worse
# The iterator holds an INDEX. Removing element 1 shifts everything left, so
# the next iteration reads index 2 — skipping what is now at index 1.

items = [x for x in items if x % 2]        # ✓ build a new list
items[:] = [x for x in items if x % 2]     # ✓ in place, if aliases exist

# The same applies to dicts and sets — mutating during iteration raises
# RuntimeError: dictionary changed size during iteration. That error is
# friendlier than the list behaviour, which corrupts silently.

# ── WHILE, AND WHEN IT IS THE RIGHT CHOICE ───────────────────────────────
# Use while when the number of iterations is not known in advance:
attempts = 0
while attempts < MAX_RETRIES:
    if try_connect():
        break
    attempts += 1
    time.sleep(2 ** attempts)
else:
    raise ConnectionError("All retries exhausted.")

# ALWAYS bound a while loop. `while True` without a break condition reachable
# on every path is an infinite loop waiting for the one input you did not
# consider.
Key insight: the mutable-default and late-binding closure traps share one root cause: function definition happens once, at import time. Default arguments are evaluated then and stored on the function object; closure variables are looked up later, when the function is called. Defaults bind too early, closures bind too late, and both surprise people who expect the intuitive timing. Once you internalise that def is an executable statement that builds an object rather than a declaration, both behaviours follow logically.

Part 3 — Function Parameters

# FIVE kinds of parameter, in the only order Python permits:
def f(pos_only, /, standard, *args, kw_only, **kwargs):
    ...
#     ^^^^^^^^  ^  ^^^^^^^^  ^^^^^  ^^^^^^^  ^^^^^^^^
#     1         2  3         4      5        6
#   1. positional-only (before /)
#   2. the / marker
#   3. standard: positional OR keyword
#   4. *args: extra positionals, as a tuple
#   5. keyword-only (anything after *args or a bare *)
#   6. **kwargs: extra keywords, as a dict

# ── KEYWORD-ONLY ARGUMENTS make call sites readable ──────────────────────
def create_user(name, *, admin=False, notify=True):
    ...

create_user("Ada", admin=True)      # ✓ clear
create_user("Ada", True)            # ✗ TypeError — and that is the point
# The bare * forces callers to name the flags. Without it,
# create_user("Ada", True, False) is unreadable at the call site and a
# silent bug if the argument order ever changes.

# ── POSITIONAL-ONLY (3.8+) ───────────────────────────────────────────────
def distance(x, y, /):
    ...
# Callers cannot write distance(x=1, y=2), which means you are free to rename
# the parameters later without breaking anyone. Useful for library APIs and
# for parameters whose names carry no meaning to the caller.

# ── DEFAULTS ARE EVALUATED ONCE, AT DEFINITION ───────────────────────────
def append_to(item, target=[]):        # ✗ ONE list, shared by every call
    target.append(item)
    return target

append_to(1)      # [1]
append_to(2)      # [1, 2]  ← the same list

def append_to(item, target=None):      # ✓ the standard fix
    if target is None:
        target = []
    target.append(item)
    return target

# The same applies to any mutable default — dicts, sets — and to anything
# computed at definition time:
def log(message, when=datetime.now()):   # ✗ frozen at IMPORT time forever
def log(message, when=None):             # ✓
    when = when or datetime.now()

# ── *args AND **kwargs, and forwarding ───────────────────────────────────
def wrapper(*args, **kwargs):
    return wrapped(*args, **kwargs)     # forward everything unchanged

# Unpacking at the call site is the mirror image:
point = (3, 4)
distance(*point)                        # distance(3, 4)

options = {"admin": True, "notify": False}
create_user("Ada", **options)           # create_user("Ada", admin=True, ...)

# ── RETURNING MULTIPLE VALUES is really returning a tuple ────────────────
def divide(a, b):
    return a // b, a % b                # a tuple

quotient, remainder = divide(17, 5)     # unpacked

# Past two or three values, a NamedTuple or dataclass beats a bare tuple —
# callers stop having to remember the order:
class Stats(NamedTuple):
    mean: float
    median: float
    stdev: float

Part 4 — Scope and Closures

# NAME RESOLUTION follows LEGB, checked in this order:
#   Local      → inside the current function
#   Enclosing  → any enclosing function
#   Global     → module level
#   Built-in   → len, print, range, ...

count = 0

def increment():
    count += 1          # ✗ UnboundLocalError
# Assigning to `count` ANYWHERE in the function makes it local for the WHOLE
# function — including the line that reads it before assignment. Python
# decides local-versus-global at COMPILE time, from the presence of an
# assignment, not at runtime.

def increment():
    global count        # ✓ explicit
    count += 1

# Prefer avoiding module-level mutable state entirely — return a new value
# and let the caller decide what to do with it.

# ── ENCLOSING SCOPE AND nonlocal ─────────────────────────────────────────
def make_counter():
    count = 0
    def increment():
        nonlocal count      # rebind in the ENCLOSING scope, not global
        count += 1
        return count
    return increment

counter = make_counter()
counter()    # 1
counter()    # 2
# The inner function keeps `count` alive after make_counter returns — that is
# a closure. Each call to make_counter creates an independent one.

# ── THE LATE-BINDING TRAP ────────────────────────────────────────────────
funcs = [lambda: i for i in range(3)]
[f() for f in funcs]        # [2, 2, 2] — NOT [0, 1, 2]
# Each lambda closes over the VARIABLE i, not its value. By the time any of
# them runs, the loop has finished and i is 2.

funcs = [lambda i=i: i for i in range(3)]    # ✓ bind at definition time
[f() for f in funcs]                          # [0, 1, 2]

funcs = [partial(lambda x: x, i) for i in range(3)]   # ✓ clearer intent

# This bites hardest with callbacks in loops — event handlers, retry
# wrappers, thread targets — where the symptom appears far from the cause.

# ── MUTABLE CLOSURES WITHOUT nonlocal ────────────────────────────────────
def make_accumulator():
    total = []                       # no rebinding, so no nonlocal needed
    def add(x):
        total.append(x)              # MUTATION, not assignment
        return sum(total)
    return add
# Mutating an object never requires nonlocal; only REBINDING the name does.

Part 5 — Structural Pattern Matching

# match/case (3.10+) destructures as well as compares — it is not a switch.
def handle(event):
    match event:
        case {"type": "click", "x": x, "y": y}:      # dict with these keys
            return f"Click at {x},{y}"

        case {"type": "key", "key": str(key)}:        # with a type check
            return f"Key {key}"

        case [first, *rest]:                          # non-empty sequence
            return f"{first} plus {len(rest)} more"

        case Point(x=0, y=0):                         # class pattern
            return "Origin"

        case str() | bytes():                         # alternatives
            return "Text"

        case _:                                       # the default
            return "Unknown"

# ── CAPTURE VS COMPARE: the rule that surprises people ───────────────────
CONSTANT = 5
match value:
    case CONSTANT:      # ✗ this CAPTURES into a new name, matching ANYTHING
        ...
# A bare name is a capture pattern, so this always matches and rebinds
# CONSTANT. To compare against a constant it must be DOTTED:
match value:
    case Config.MAX:    # ✓ a value pattern — compares
        ...
    case 5:             # ✓ a literal — compares
        ...

# ── GUARDS for conditions patterns cannot express ────────────────────────
match order:
    case {"total": total} if total > 1000:
        apply_discount(order)
    case {"total": total}:
        pass

# ── WHEN match EARNS ITS PLACE ───────────────────────────────────────────
# ✓ destructuring nested data — parsed JSON, ASTs, message envelopes
# ✓ matching on SHAPE rather than a single value
# ✗ a simple value-to-value mapping, where a dict is clearer AND faster:
handlers = {"click": on_click, "key": on_key}
handler = handlers.get(event["type"], on_unknown)
# match is a structural tool. Reaching for it to replace a two-branch if
# adds ceremony without adding clarity.

Part 6 — Exceptions as Control Flow

# EAFP — "easier to ask forgiveness than permission" — is the Python idiom,
# in contrast to LBYL, "look before you leap":
try:                                   # ✓ EAFP
    value = config["timeout"]
except KeyError:
    value = DEFAULT_TIMEOUT

if "timeout" in config:                # LBYL — two lookups, and a race if
    value = config["timeout"]          # config can change between them
else:
    value = DEFAULT_TIMEOUT

value = config.get("timeout", DEFAULT_TIMEOUT)   # ✓ clearest here

# EAFP is preferred when the failure is genuinely exceptional and when a
# check-then-act sequence would race. It is NOT free: raising and catching
# costs far more than a comparison, so it is the wrong choice inside a tight
# loop where failure is the common case.

# ── CATCH NARROWLY ───────────────────────────────────────────────────────
try:
    result = risky()
except Exception:          # ✗ swallows everything, including real bugs
    result = None

try:
    result = risky()
except (ValueError, KeyError) as exc:      # ✓ what you can actually handle
    logger.warning("Falling back: %s", exc)
    result = DEFAULT

# A bare `except:` also catches KeyboardInterrupt and SystemExit, so it makes
# a program impossible to stop with Ctrl-C. Never use it.

# ── else AND finally ─────────────────────────────────────────────────────
try:
    connection = connect()
except ConnectionError:
    logger.error("Could not connect.")
    raise
else:
    # Runs ONLY if no exception was raised. Keeping this out of the try block
    # means an exception raised HERE is not accidentally caught above.
    process(connection)
finally:
    # Always runs — cleanup belongs here, or better, in a context manager.
    connection.close()

# ── RAISING WELL ─────────────────────────────────────────────────────────
raise ValueError(f"Expected a positive quantity, got {quantity!r}")
# Include the offending VALUE. "Invalid input" costs a debugging session that
# the actual value would have saved.

# Preserve the cause when re-raising as a different type:
try:
    parse(raw)
except json.JSONDecodeError as exc:
    raise ConfigError("Malformed config file.") from exc   # keeps the chain

raise ConfigError("Malformed config file.") from None      # deliberately hides

# ── EXCEPTION GROUPS (3.11+) for concurrent failures ─────────────────────
try:
    async with asyncio.TaskGroup() as group:
        group.create_task(fetch(url1))
        group.create_task(fetch(url2))
except* ConnectionError as group:      # note except*
    for exc in group.exceptions:
        logger.warning("Fetch failed: %s", exc)
# Several tasks can fail simultaneously, so one exception cannot represent
# the outcome — see Concurrency for the full picture.

Interview Questions

Beginner: What values are falsy in Python?

False, None, numeric zero of any type, and every empty container — the empty string, tuple, list, dict, set and range(0). Everything else is truthy, including strings like "0" and "False" and containers holding falsy values such as [0]. Python determines this by calling __bool__, falling back to __len__() != 0, and defaulting to true when neither is defined — which is why a custom class implementing __len__ automatically works in an if. The practical consequence is that if not x and if x is None mean different things, and using the first when you meant the second is a common source of bugs where zero or an empty string is a legitimate value.

Beginner: Why is a mutable default argument dangerous?

Because default arguments are evaluated once, when the def statement executes at import time, and the resulting object is stored on the function. Every call that does not supply that argument therefore shares the same object, so a default of [] accumulates items across calls and appears to "remember" previous invocations. The standard fix is to default to None and create the container inside the function body, which produces a fresh object per call. The same reasoning applies to any default computed at definition time, such as datetime.now(), which would freeze a single timestamp for the process lifetime.

Mid: Explain the late-binding closure problem.

A closure captures the variable itself, not its value at the moment the closure was created. So [lambda: i for i in range(3)] produces three functions that all reference the same i, and because they are called after the loop completes, all three return 2 rather than 0, 1 and 2. The usual fix is to force evaluation at definition time with a default argument — lambda i=i: i — since defaults are evaluated when the function is created, or to use functools.partial, which states the intent more clearly. It matters most with callbacks registered in a loop, such as event handlers or thread targets, because the symptom appears far from the code that caused it and every callback appears to operate on the last item.

Mid: What is EAFP and when is it the wrong choice?

EAFP means "easier to ask forgiveness than permission" — attempt the operation and handle the exception, rather than checking preconditions first. It is the Python idiom because it avoids the race between checking and acting, which matters whenever the state can change in between, and because it keeps the common path free of guard clauses. It is the wrong choice in two situations. First, when the exceptional case is actually common: raising and catching is far more expensive than a comparison, so inside a tight loop where most lookups miss, a dict.get with a default or an in check is substantially faster. Second, when the check is cheap and clearer than the exception handling, which is why config.get("key", default) beats a three-line try/except for a simple lookup.

Senior: A function behaves correctly in tests but accumulates state in production. Diagnose.

The signature — correct in isolation, wrong over time — points at state shared across calls, and in Python the two usual culprits are a mutable default argument and a module-level mutable object. A default of [] or {} is created once when the module is imported and reused by every call that omits it, so items accumulate. Tests miss this precisely because they typically call the function once per test with fresh arguments, or because each test process starts clean; production runs the same function thousands of times in one process, so the accumulation becomes visible only after sustained use. Related variants worth checking are a default computed at import time such as a timestamp or a database connection, a class attribute used where an instance attribute was intended — since class attributes are shared across all instances — and a cached value on a module-level dict. I would confirm by inspecting function.__defaults__, which shows the actual stored objects, and by adding a test that calls the function twice and asserts the second call is unaffected by the first. That two-call test is the general defence: any state leaking between invocations shows up immediately, and it costs two lines.

Senior: How would you design a function's signature for an API used across a large codebase?

My main concern is that a signature is a contract that becomes expensive to change once there are many call sites, so I optimise for readability at the call site and for the freedom to evolve. I would keep required positional parameters to the very few whose meaning is obvious from the function name, and make everything else keyword-only using a bare * — that way a call reads create_user("Ada", admin=True, notify=False) rather than three unlabelled booleans, and I can add or reorder options later without breaking anyone. Boolean flags in particular should always be keyword-only, because a positional True is unreadable and silently changes meaning if the order shifts. For parameters whose names carry no information to the caller I would use positional-only with /, which leaves me free to rename them without a breaking change. Mutable defaults never appear; anything that needs a fresh container defaults to None. For return values I would avoid bare tuples beyond two elements and use a NamedTuple or dataclass, so callers do not have to remember the order and I can add a field without breaking unpacking. I would also think about what the function does when given nothing: raising is usually better than a silently permissive default, because a wrong default propagates quietly while an exception is found immediately. And I would accept a timeout or cancellation parameter on anything doing I/O, since retrofitting one across hundreds of call sites is far harder than including it from the start.

3 (medium): Write a retry decorator-free function that retries with exponential backoff, using loop else.
Solution 
import time
import random

def fetch_with_retry(url, *, max_attempts=5, base_delay=0.5, timeout=10):
    last_error = None

    for attempt in range(max_attempts):
        try:
            return http_get(url, timeout=timeout)

        except (ConnectionError, TimeoutError) as exc:
            last_error = exc

            # Do not sleep after the FINAL attempt — it delays the failure
            # for no benefit.
            if attempt < max_attempts - 1:
                # Exponential backoff with JITTER. Without jitter, many
                # clients retrying together stay synchronised and hammer the
                # server in waves.
                delay = base_delay * (2 ** attempt)
                time.sleep(delay + random.uniform(0, delay * 0.1))
    else:
        # `else` runs only if the loop was NOT broken out of — here, if every
        # attempt failed. `raise ... from last_error` preserves the original
        # traceback so the real cause is not lost.
        raise ConnectionError(
            f"Failed to fetch {url} after {max_attempts} attempts."
        ) from last_error

# NOTE the exception types are NARROW: catching Exception would also swallow
# a programming error such as a TypeError in http_get, retrying it five times
# and then reporting it as a connection problem.
#
# Only retry IDEMPOTENT operations. Retrying a POST that timed out may
# duplicate the request, since the server may have processed the first one.

5 (hard): A function removes expired items from a list and misses some. Diagnose and give three fixes with trade-offs.
Solution 
# ✗ THE BUG:
def purge_expired(sessions, now):
    for session in sessions:
        if session.expires_at < now:
            sessions.remove(session)      # mutating while iterating

# WHY IT SKIPS: the list iterator holds an integer INDEX, not a reference to
# the current element. Removing the item at index 1 shifts everything left, so
# the element that moved into index 1 is never examined — the iterator's next
# read is index 2.
#
#   [A✗, B✗, C, D]   i=0 → remove A → [B✗, C, D], iterator moves to i=1
#   [B✗, C, D]       i=1 → C (B was SKIPPED)
#
# Two adjacent expired items always leave the second one behind. And it fails
# SILENTLY — no exception, just a wrong answer that grows over time.

# ── FIX 1: build a new list (clearest) ───────────────────────────────────
def purge_expired(sessions, now):
    return [s for s in sessions if s.expires_at >= now]
# + simple, obviously correct, no mutation
# − the caller must rebind; any other reference to the old list still sees
#   the expired items

# ── FIX 2: slice assignment (in place, keeps aliases correct) ────────────
def purge_expired(sessions, now):
    sessions[:] = [s for s in sessions if s.expires_at >= now]
# + mutates the ORIGINAL object, so every alias sees the change
# + still builds the filtered list first, so iteration is safe
# − briefly holds both lists in memory
# Use this when other code holds a reference to the same list.

# ── FIX 3: iterate over a copy ───────────────────────────────────────────
def purge_expired(sessions, now):
    for session in list(sessions):        # iterate the COPY
        if session.expires_at < now:
            sessions.remove(session)      # mutate the original
# + minimal change to existing code
# − O(n²): list.remove scans from the start to find each element
# − still a full copy, so no memory saving over fix 2
# Acceptable for small lists; the worst option for large ones.

# ── RECOMMENDATION ───────────────────────────────────────────────────────
# Fix 2 for an in-place API, fix 1 if you can return a new list. Fix 3 only
# when the removal logic is too complex to express as a comprehension.
#
# NOTE: dicts and sets raise RuntimeError on mutation during iteration, which
# is friendlier than the list behaviour — an immediate error beats a silently
# wrong result.
6 (hard): Design the signature and error handling for a send_email function used across a large codebase.
Solution 
class EmailError(Exception):
    """Base for all email failures — callers can catch this one type."""

class EmailRejected(EmailError):
    """Permanent: the address is invalid or blocked. Do NOT retry."""

class EmailTransient(EmailError):
    """Temporary: provider outage or throttling. Retry with backoff."""


def send_email(
    to,                          # required, obvious from the function name
    subject,
    body,
    /,                           # positional-only: free to rename later
    *,                           # everything below is KEYWORD-ONLY
    cc=None,
    bcc=None,
    reply_to=None,
    attachments=None,
    html=False,
    priority="normal",
    timeout=30.0,
    dry_run=False,
):
    """Send an email. Raises EmailRejected or EmailTransient on failure."""

    # Mutable defaults are None and normalised here — never [] in the
    # signature, which would be shared across every call.
    cc = cc or []
    bcc = bcc or []
    attachments = attachments or []

    # Validate at the boundary, with the offending value in the message.
    if not to:
        raise ValueError("At least one recipient is required.")
    if priority not in {"low", "normal", "high"}:
        raise ValueError(f"Unknown priority: {priority!r}")

    if dry_run:
        logger.info("Dry run: would send %r to %s", subject, to)
        return None

    try:
        return provider.send(...)

    except provider.InvalidAddress as exc:
        # `from exc` preserves the original traceback.
        raise EmailRejected(f"Invalid recipient: {to!r}") from exc

    except (provider.Throttled, provider.Unavailable, TimeoutError) as exc:
        raise EmailTransient(f"Provider unavailable: {exc}") from exc

# ── THE DESIGN DECISIONS, AND WHY ────────────────────────────────────────
#
# KEYWORD-ONLY OPTIONS: send_email(to, subj, body, True, False) is
#   unreadable and silently changes meaning if the order ever shifts.
#   With `*`, callers must write html=True — and I can add or reorder
#   options later without breaking a single call site.
#
# POSITIONAL-ONLY CORE: `to`, `subject` and `body` are obvious from the
#   function name, and `/` leaves me free to rename the parameters.
#
# TWO EXCEPTION TYPES, not one: the caller's correct action differs
#   completely. A retry loop that cannot distinguish permanent from transient
#   failures will retry an invalid address five times and give up on a
#   provider blip. This distinction is the single most valuable thing in the
#   signature.
#
# A SHARED BASE CLASS: callers who do not care about the distinction catch
#   EmailError and get both.
#
# `from exc` EVERYWHERE: the provider's original traceback is what makes a
#   production failure diagnosable.
#
# dry_run: makes the function testable and safe to exercise in staging
#   without a mock, which matters for something with side effects.
#
# timeout WITH A DEFAULT: retrofitting a timeout across hundreds of call
#   sites is far harder than including it from the start, and a network call
#   with no timeout eventually hangs forever.

🎯 Key Takeaways

  • Every object has a truth value; empty containers and zero are falsy, so if not x and if x is None mean different things.
  • Default arguments are evaluated once at definition time — mutable defaults are shared across every call.
  • Closures capture variables, not values, so all closures created in a loop see the final value.
  • Mutating a list while iterating skips elements silently; dicts and sets at least raise an error.
  • Loop else runs when the loop was not broken out of — read it as "no break".
  • A bare * makes following parameters keyword-only, which is how boolean flags become readable at the call site.
  • Assigning to a name anywhere in a function makes it local throughout; use global or nonlocal deliberately.
  • In match, a bare name captures rather than compares — constants must be dotted or literal.
  • EAFP avoids check-then-act races but costs real time when failure is the common case.
  • Catch narrow exception types, always include the offending value in the message, and re-raise with from to preserve the cause.
