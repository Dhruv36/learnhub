Testing with pytest Advanced

What you'll master: pytest's assertion introspection and why plain assert is enough, parametrisation for table-driven edge cases, fixtures including scope, composition and conftest.py, the transaction-rollback pattern that makes database tests both real and fast, mocking at the right boundary and the patch-where-it-is-used rule that catches everyone, controlling time and randomness, diagnosing flaky tests, and deciding what is actually worth testing. Prerequisites: Decorators & Context Managers and Modules, Packaging & Environments.

Part 1 — Assertions and Discovery

# tests/test_pricing.py
from myapp.pricing import apply_discount

def test_applies_percentage():
    assert apply_discount(100, 10) == 90

# Plain assert. pytest rewrites the bytecode so a failure shows the values:
#
#   E       assert 91 == 90
#   E        +  where 91 = apply_discount(100, 10)
#
# No assertEqual, assertTrue, assertAlmostEqual family to memorise.

# ── DISCOVERY RULES ──────────────────────────────────────────────────────
# files:     test_*.py or *_test.py
# functions: test_*
# classes:   Test* with no __init__
# Rename a test function to something not starting with test_ and it stops
# running, silently — a real way to lose coverage in a refactor.

# ── EXCEPTIONS ───────────────────────────────────────────────────────────
import pytest

def test_rejects_negative():
    with pytest.raises(ValueError, match="must be positive"):
        apply_discount(-5, 10)
# match= is a REGEX searched against str(exception). Without it, the test
# passes on ANY ValueError — including one from a typo in the test setup.

def test_error_detail():
    with pytest.raises(ValidationError) as exc_info:
        parse(bad_input)
    assert exc_info.value.field == "email"       # inspect the exception

# ── FLOATS ───────────────────────────────────────────────────────────────
assert 0.1 + 0.2 == 0.3                          # ✗ False. Always.
assert 0.1 + 0.2 == pytest.approx(0.3)           # ✓
assert result == pytest.approx(expected, rel=1e-3)
# And for money, do not use floats at all — Decimal.

# ── WARNINGS AND OUTPUT ──────────────────────────────────────────────────
with pytest.warns(DeprecationWarning):
    old_api()

def test_prints(capsys):
    greet("ada")
    assert "Hi ada" in capsys.readouterr().out

def test_logs(caplog):
    with caplog.at_level(logging.WARNING):
        risky()
    assert "retrying" in caplog.text
# Assert on log LEVELS and key events, not exact message strings — those
# change for good reasons and the test then fails for no reason.

# ── RUNNING ──────────────────────────────────────────────────────────────
pytest                                # everything
pytest tests/test_pricing.py          # one file
pytest tests/test_pricing.py::test_applies_percentage
pytest -k "discount and not slow"     # by name expression
pytest -m integration                 # by marker
pytest -x                             # stop at the first failure
pytest --lf                           # ONLY last-failed — the tight loop
pytest --ff                           # failed first, then the rest
pytest -q                             # quiet
pytest -vv                            # full diffs on assertion failure
pytest --pdb                          # drop into a debugger at the failure
pytest -n auto                        # parallel (pytest-xdist)
pytest --durations=10                 # the 10 slowest tests

Part 2 — Parametrisation

@pytest.mark.parametrize("price,pct,expected", [
    (100, 10, 90),
    (100, 0, 100),          # no discount
    (100, 100, 0),          # full discount
    (0, 50, 0),             # zero price
    (0.01, 50, 0.005),      # smallest unit
])
def test_discount(price, pct, expected):
    assert apply_discount(price, pct) == pytest.approx(expected)

# Five SEPARATE reported tests. One failing case does not hide the others,
# and the failure names the exact input:
#   FAILED test_discount[100-100-0]

# ── NAMING THE CASES ─────────────────────────────────────────────────────
@pytest.mark.parametrize("value,expected", [
    pytest.param("", False, id="empty"),
    pytest.param("a@b.com", True, id="valid"),
    pytest.param("a@b", False, id="no-tld"),
    pytest.param("a b@c.com", False, id="space"),
])
def test_email(value, expected): ...
# FAILED test_email[no-tld] tells you what broke without opening the file.

# ── STACKING = CARTESIAN PRODUCT ─────────────────────────────────────────
@pytest.mark.parametrize("role", ["admin", "viewer"])
@pytest.mark.parametrize("method", ["GET", "POST"])
def test_access(role, method): ...        # 4 tests
# Useful for genuine matrices; a 5x5x5 stack is 125 tests that all break
# together and tell you nothing more than one would.

# ── EXPECTED FAILURES IN A TABLE ─────────────────────────────────────────
@pytest.mark.parametrize("price,pct", [
    (-1, 10),
    (100, -5),
    (100, 101),
])
def test_rejects_invalid(price, pct):
    with pytest.raises(ValueError):
        apply_discount(price, pct)

# ── WHAT TO PUT IN THE TABLE ─────────────────────────────────────────────
# Not five variations of the happy path — they exercise one branch five
# times. Cover the BOUNDARIES and the branches:
#   zero, one, many, empty
#   negative, the maximum, one past the maximum
#   None, empty string, whitespace
#   the exact boundary and both sides of it
#   duplicates, unicode, very long input
# One test per behaviour, not per input value that happens to differ.

Part 3 — Fixtures

@pytest.fixture
def user() -> User:
    return User(id=1, name="ada", role="admin")

def test_permissions(user):          # request by NAME — pytest injects it
    assert user.can("delete")

# ── SETUP AND TEARDOWN WITH yield ────────────────────────────────────────
@pytest.fixture
def temp_config(tmp_path):
    path = tmp_path / "config.json"
    path.write_text('{"debug": true}')
    yield path                       # ← the test runs here
    # teardown after the yield, and it runs EVEN IF THE TEST FAILS
    path.unlink(missing_ok=True)

# ── SCOPES ───────────────────────────────────────────────────────────────
@pytest.fixture(scope="function")    # default — fresh per test
@pytest.fixture(scope="class")
@pytest.fixture(scope="module")      # once per test file
@pytest.fixture(scope="session")     # once per pytest run

@pytest.fixture(scope="session")
def db_engine():                     # expensive: create ONCE
    engine = create_engine(TEST_DB_URL)
    Base.metadata.create_all(engine)
    yield engine
    Base.metadata.drop_all(engine)
# ⚠ THE SCOPE TRADE-OFF: anything mutable shared at session scope leaks
# state between tests and produces order-dependent failures. Share the
# expensive CONNECTION; give each test its own transaction (Part 4).

# ── FIXTURES COMPOSE ─────────────────────────────────────────────────────
@pytest.fixture
def repo(db_session):                # a fixture requesting another
    return UserRepo(db_session)

@pytest.fixture
def existing_user(repo):
    return repo.create(name="ada")

def test_rename(repo, existing_user):    # pytest resolves the whole graph
    repo.rename(existing_user.id, "grace")
    assert repo.get(existing_user.id).name == "grace"

# ── conftest.py: SHARED, AUTO-DISCOVERED ─────────────────────────────────
# tests/conftest.py           available to every test below it
# tests/api/conftest.py       available to tests/api/* only
# No import needed — pytest finds them by directory. Put fixtures at the
# narrowest level that works.

# ── autouse: APPLIED WITHOUT BEING REQUESTED ─────────────────────────────
@pytest.fixture(autouse=True)
def reset_registry():
    REGISTRY.clear()
    yield
    REGISTRY.clear()
# Good for global cleanup. Use sparingly — an autouse fixture is action
# at a distance, and a test that fails because of one three directories
# up is genuinely hard to debug.

# ── PARAMETRISED FIXTURES ────────────────────────────────────────────────
@pytest.fixture(params=["sqlite", "postgres"])
def db(request):
    yield connect(request.param)     # every test using `db` runs TWICE

# ── BUILT-IN FIXTURES WORTH KNOWING ──────────────────────────────────────
tmp_path        # a fresh Path directory per test, auto-cleaned
monkeypatch     # patch attributes, dict items, env vars; auto-undone
capsys          # captured stdout/stderr
caplog          # captured log records
request         # metadata about the running test

def test_reads_env(monkeypatch):
    monkeypatch.setenv("API_KEY", "test-key")
    monkeypatch.setattr(settings, "timeout", 1)
    monkeypatch.chdir(tmp_path)
    assert get_client().key == "test-key"
# All reverted automatically at the end of the test — which is the whole
# advantage over doing it by hand.

# ── FACTORY FIXTURES: WHEN ONE OBJECT IS NOT ENOUGH ──────────────────────
@pytest.fixture
def make_user(repo):
    created = []
    def _make(**kwargs):
        u = repo.create(**{"name": "test", "role": "viewer", **kwargs})
        created.append(u)
        return u
    yield _make
    for u in created:
        repo.delete(u.id)

def test_admin_sees_all(make_user):
    admin = make_user(role="admin")
    make_user(); make_user()
    assert len(admin.visible_users()) == 3
# Each test builds exactly the data it needs, and states the ONE field
# that matters — which is also the field the test is about.
Key insight: a test earns its keep by failing for exactly one reason and telling you what that reason is. Everything else in this lesson follows from that. Parametrised cases are separate tests so one failure does not mask four others. Fixtures give each test fresh state so a failure means the code broke and not that another test left something behind. Mocks belong only at the edges, because a test whose subject is a mock fails when you refactor and passes when the logic is wrong. And a test that asserts on wall-clock time or a random value fails for a reason that has nothing to do with your code at all.

Part 4 — Database Tests

# ── THE PROBLEM ──────────────────────────────────────────────────────────
# Real database tests are the ones that catch real bugs — constraints,
# cascades, transaction semantics, the query the ORM actually generates.
# But they are slow and they leak state into each other.

# ── THE TRANSACTION-ROLLBACK PATTERN ─────────────────────────────────────
@pytest.fixture(scope="session")
def engine():
    engine = create_engine(TEST_DATABASE_URL)
    Base.metadata.create_all(engine)          # schema ONCE per run
    yield engine
    Base.metadata.drop_all(engine)

@pytest.fixture
def db_session(engine):
    connection = engine.connect()
    transaction = connection.begin()          # OUTER transaction
    session = Session(bind=connection)
    yield session
    session.close()
    transaction.rollback()                    # ← everything undone
    connection.close()

# Every test gets a real database with real constraints, and every write
# vanishes at the end. No truncation, no fixture teardown to maintain, no
# order dependence. A rollback is far faster than DELETE across tables.
#
# ⚠ Code under test must not COMMIT — a commit ends the outer transaction
# and the rollback has nothing left to undo. For code that commits, use
# SAVEPOINTs (SQLAlchemy's join_transaction_mode="create_savepoint").

# ── DO NOT MOCK THE DATABASE ─────────────────────────────────────────────
def test_create_user():
    mock_db = Mock()
    repo = UserRepo(mock_db)
    repo.create("ada")
    mock_db.execute.assert_called_once()      # ✗ asserts on SQL you wrote
# This passes whether or not the SQL is valid, whether the unique
# constraint fires, whether the foreign key exists, or whether the column
# is even spelled correctly. It tests that your code called the method
# your code calls.

def test_duplicate_email_rejected(db_session):
    repo = UserRepo(db_session)
    repo.create(email="a@b.com")
    with pytest.raises(IntegrityError):       # ✓ the REAL constraint
        repo.create(email="a@b.com")

# ── THE TEST PYRAMID, PRACTICALLY ────────────────────────────────────────
# UNIT         pure logic, no I/O. Milliseconds. Hundreds of them.
# INTEGRATION  real DB, real queries, mocked third parties. Seconds.
# END-TO-END   the whole stack over HTTP. Minutes. A handful of the
#              critical paths only.
#
# Integration is where most real bugs live, and the rollback fixture is
# what makes that layer cheap enough to have a lot of.

@pytest.mark.integration                      # mark them
def test_order_flow(db_session): ...
# pytest -m "not integration"       fast loop
# pytest                            everything, in CI

# ── TESTCONTAINERS: THE REAL ENGINE, DISPOSABLE ──────────────────────────
from testcontainers.postgres import PostgresContainer

@pytest.fixture(scope="session")
def engine():
    with PostgresContainer("postgres:16") as pg:
        yield create_engine(pg.get_connection_url())
# SQLite in tests and Postgres in production is a classic source of bugs
# that only appear after deploy: different type coercion, different
# constraint timing, no JSONB, different concurrency behaviour.

Part 5 — Mocking, Time, and Randomness

# ── THE RULE THAT CATCHES EVERYONE ───────────────────────────────────────
# myapp/orders.py
from myapp.mailer import send_email          # ← a NEW reference is bound
                                             #   in orders' namespace
def place_order(order):
    send_email(order.email, "confirmed")

# ✗ patches the name in mailer — orders still holds its own reference
with patch("myapp.mailer.send_email") as m: ...        # the real email SENDS

# ✓ patch WHERE IT IS LOOKED UP
with patch("myapp.orders.send_email") as m:
    place_order(order)
    m.assert_called_once_with(order.email, "confirmed")

# `from x import y` copies the reference at import time. Patching the
# origin afterwards cannot reach the copy. (This is the same import-time
# binding covered in Modules, Packaging & Environments.)
#
# `import myapp.mailer` then `mailer.send_email(...)` looks the attribute
# up at CALL time, so patching the origin does work — which is one small
# argument for that import style.

# ── MOCK ONLY WHAT YOU DO NOT OWN ────────────────────────────────────────
# ✓ MOCK: third-party HTTP, email/SMS, payment providers, the clock,
#         randomness, the filesystem when it is incidental
# ✗ DO NOT MOCK: your own functions, your own classes, the database
#
# Mocking your own code tests that the code calls the code it calls. It
# passes when the logic is wrong and fails when you rename a method —
# exactly backwards.

# ── PREFER A FAKE TO A MOCK ──────────────────────────────────────────────
class FakeMailer:                            # 4 lines, no framework
    def __init__(self): self.sent = []
    def send(self, to, subject): self.sent.append((to, subject))

def test_confirmation(order):
    mailer = FakeMailer()
    place_order(order, mailer=mailer)        # INJECTED, not patched
    assert mailer.sent == [(order.email, "confirmed")]
# No patch target to get wrong, no assert_called_with signature coupling,
# and it asserts on the OUTCOME rather than on the interaction. If code
# is hard to test without patching, that is usually a design signal —
# see the composition section of OOP & Dataclasses.

# ── autospec: CATCH SIGNATURE DRIFT ──────────────────────────────────────
with patch("myapp.orders.send_email") as m:
    m(1, 2, 3, 4, 5)                         # ✗ a plain Mock accepts
                                             #   ANYTHING, forever
with patch("myapp.orders.send_email", autospec=True) as m:
    m(1, 2, 3, 4, 5)                         # ✓ TypeError — wrong signature
# Without autospec, a mocked function whose real signature changed keeps
# passing tests while production breaks. Always pass autospec=True.

# ── HTTP: INTERCEPT THE TRANSPORT ────────────────────────────────────────
import respx, httpx

@respx.mock
def test_fetch_user():
    respx.get("https://api.example.com/users/1").mock(
        return_value=httpx.Response(200, json={"id": 1, "name": "ada"}))
    assert fetch_user(1).name == "ada"
# Your real client code runs — real serialisation, real error handling,
# real timeout config — and only the socket is faked. Far better than
# patching your own fetch_user.

# ── TIME: INJECT IT ──────────────────────────────────────────────────────
def is_expired(token):
    return token.expires_at < datetime.now()     # ✗ untestable directly

def is_expired(token, now=None):                  # ✓ injectable
    return token.expires_at < (now or datetime.now())

def test_expiry():
    assert is_expired(token, now=datetime(2030, 1, 1))

from freezegun import freeze_time                 # for existing code
@freeze_time("2026-01-15 12:00:00")
def test_expiry(): ...
# A test that passes in the morning and fails at 23:59, or only on 29
# February, is this bug.

# ── RANDOMNESS AND IDS ───────────────────────────────────────────────────
def test_shuffle(monkeypatch):
    monkeypatch.setattr(random, "shuffle", lambda x: None)
def test_id(monkeypatch):
    monkeypatch.setattr(uuid, "uuid4", lambda: UUID(int=1))
# Or inject a seeded Random instance — the same injection argument.

Part 6 — What to Test, and Flakiness

# ── WORTH TESTING ────────────────────────────────────────────────────────
#   business logic branches, and every boundary condition
#   error paths — what happens on invalid input, on a failed dependency
#   integration through a REAL database
#   a REGRESSION TEST FOR EVERY BUG YOU FIX, written before the fix
#   public API contracts and serialisation shapes
#   security-relevant paths: authz, ownership checks, input validation
#
# ── NOT WORTH TESTING ────────────────────────────────────────────────────
#   third-party library internals (test YOUR use of them)
#   trivial getters, setters, pass-throughs
#   exact log message strings and formatting
#   private methods — test them through the public surface, or they
#     become impossible to refactor
#   framework behaviour (that a route decorator registers a route)

# ── COVERAGE ─────────────────────────────────────────────────────────────
pytest --cov=myapp --cov-report=term-missing --cov-branch
# --cov-branch matters: line coverage counts an `if` as covered when only
# the true side ever ran.
#
# Coverage finds UNTESTED code. It says nothing about whether the tests
# that exist assert anything meaningful:
def test_process():
    process(data)          # 100% coverage of process(). Zero assertions.
                           # Passes as long as it does not raise.
# Use it to find gaps, not as a target. A team chasing a percentage
# writes tests for trivial code because that is the cheapest way to move
# the number, which is the opposite of the intent.

# ── FLAKY TESTS ──────────────────────────────────────────────────────────
# A flaky test is worse than no test: it trains the team to re-run CI
# instead of reading failures, and then a real failure gets re-run too.
#
# THE CAUSES, in order of frequency:
#
# 1. SHARED STATE between tests
pytest -p no:randomly                 # passes
pytest -p randomly                    # fails → order dependence
# The fix is fixtures with the right scope, never a session-scoped
# mutable object.
#
# 2. TIME — freeze it, or inject it. Also: tests that assume a query
#    takes less than 100ms fail on a loaded CI runner.
#
# 3. UNORDERED COLLECTIONS
assert list(get_tags()) == ["a", "b"]      # ✗ a set has no order
assert sorted(get_tags()) == ["a", "b"]    # ✓
#
# 4. REAL NETWORK CALLS — an external API in a test suite means CI fails
#    when someone else has an outage. Intercept the transport.
#
# 5. CONCURRENCY — a test that sleeps to wait for a thread is a race with
#    a slow CI machine. Wait on an Event or poll a condition instead.
#
# ── DIAGNOSING ONE ───────────────────────────────────────────────────────
pytest --lf -x                        # reproduce quickly
pytest test_a.py test_b.py            # bisect the interaction
pytest -p randomly --randomly-seed=12345      # reproduce an ORDER
pytest --count=50 test_flaky.py       # pytest-repeat
#
# ⚠ Do NOT reach for @pytest.mark.flaky(reruns=3). It hides the bug, and
# the underlying race is usually real in production too — a test that
# fails one time in fifty is often reporting a genuine defect.

# ── CI CONFIGURATION ─────────────────────────────────────────────────────
[tool.pytest.ini_options]
addopts = "-ra --strict-markers --strict-config"
# --strict-markers  a typo'd @pytest.mark.integraton is an ERROR, not a
#                   marker silently doing nothing
testpaths = ["tests"]
markers = ["integration: needs a database", "slow: >1s"]
filterwarnings = ["error"]            # a DeprecationWarning fails the
                                      # build, so upgrades do not surprise
                                      # you six months later

Interview Questions

Beginner: How do pytest fixtures work, and why prefer them to setUp/tearDown?

A fixture is a function decorated with @pytest.fixture, and a test uses it by naming it as a parameter — pytest resolves the whole dependency graph, including fixtures that request other fixtures. When a fixture yields, everything before is setup and everything after is teardown, and the teardown runs even if the test fails, which is the same guarantee a context manager gives.

The advantages over setUp/tearDown are that dependencies are explicit per test rather than shared by every method on a class, so reading a test signature tells you exactly what it needs; reuse happens by composition instead of by inheriting from a base test class; and scope is controllable, so an expensive database engine can be created once per session while the data for each test stays function-scoped. conftest.py makes fixtures available to everything below it in the directory tree with no imports. In practice the highest-value one is the database session fixture that opens a transaction and rolls it back afterwards — real database, real constraints, and complete isolation without any cleanup code to maintain.

Beginner: You patched send_email but a real email still went out. Why?

You patched it where it is defined rather than where it is used. When the module under test does from myapp.mailer import send_email, that binds a new reference to the function in that module's namespace at import time. Patching myapp.mailer.send_email afterwards replaces the attribute on the mailer module, but the copy in the orders module still points at the original function, so the real one runs. The fix is patch("myapp.orders.send_email") — the place the name is looked up.

It follows directly from how imports bind names, and there are two things worth adding. If the code had used import myapp.mailer and called mailer.send_email(...), the attribute would be looked up at call time and patching the origin would have worked — which is a small argument for that import style in code you expect to patch. And I would rather avoid the question entirely by injecting the mailer as a dependency and passing a small fake in the test, because then there is no patch target to get wrong and the test asserts on the outcome rather than on which function was called.

Mid: How do you test code that touches a database, without the tests being slow or interfering?

Wrap each test in a transaction that is rolled back afterwards. A session-scoped fixture creates the engine and schema once per run, and a function-scoped fixture opens a connection, begins a transaction, hands the test a session bound to it, and rolls back at the end. Every test sees a real database with real constraints, and every write disappears — no truncation between tests, no cleanup code to maintain, and no ordering dependencies. A rollback is also much faster than deleting across tables.

The alternative people reach for is mocking the database, and it is a trap: asserting that execute was called with a particular string tests that your code calls the code you wrote. It passes when the SQL is invalid, when a unique constraint would have fired, when a foreign key is missing, and when a column name is misspelled — which is precisely the category of bug this layer is supposed to catch. There is one caveat with the rollback pattern: if the code under test commits, that ends the outer transaction and there is nothing left to roll back, so committing code needs savepoints. And the test database should be the same engine as production — SQLite standing in for Postgres differs in type coercion, constraint timing and concurrency, so testcontainers spinning up a real Postgres per run is worth the few seconds it costs.

Mid: What should you test, and is 100% coverage the goal?

Test behaviour at the boundaries: the branches of your business logic, edge cases like zero, empty, negative and one-past-the-limit, error paths including what happens when a dependency fails, integration through a real database, and a regression test for every bug you fix — written before the fix, so you know it actually reproduces the problem. Security-relevant paths such as authorisation and ownership checks deserve explicit tests because their failure mode is silent. What is not worth testing is third-party library internals, trivial getters and pass-throughs, exact log strings, and private methods, which should be exercised through the public surface or they make refactoring impossible.

Coverage is a gap-finder, not a target. It measures lines executed, not correctness, and a test that calls a function with no assertions at all reports full coverage of it while proving only that it did not raise. Branch coverage is more honest than line coverage, since an if counts as covered when only one side ever ran. The failure mode of a percentage target is predictable: the cheapest way to move the number is to test trivial code, so a team optimises for exactly the tests that catch nothing. I would rather see eighty percent with meaningful assertions on the paths that matter than a hundred percent that includes generated code and getters.

Senior: A test fails once in every fifty CI runs. How do you handle it?

First, I would not mark it as flaky and retry. That hides the failure and, worse, trains the team to re-run CI on any red build, so a genuine regression gets re-run too. A test failing one time in fifty is usually reporting a real race that also exists in production — it just needs a particular interleaving, and CI machines under load produce interleavings that a developer laptop does not.

The causes are a short list, in roughly this order. Shared state between tests, which pytest -p randomly flushes out by shuffling order — if the failure follows the ordering, something is leaking, usually a session-scoped mutable fixture or a module-level cache. Time dependence: a test that assumes an operation completes in under a hundred milliseconds, or that today is not the last day of a month. Unordered collections compared directly, where a set or dict happens to iterate in a different order. Real network calls, where the failure is actually someone else's outage. And concurrency, where the test sleeps to wait for a thread and eventually loses that race.

To reproduce it, --count from pytest-repeat runs the test many times in one session, -p randomly --randomly-seed=N pins a specific order that failed, and running a suspected pair of test files together isolates an interaction. Once identified, the fix is structural: correct fixture scoping, an injected clock, sorting before comparison, intercepting the transport, or waiting on an Event rather than sleeping. If the investigation genuinely cannot be done now, I would rather skip the test with a linked ticket than leave it failing intermittently — an honest gap is better than a signal nobody trusts.

Senior: Design the testing strategy for a payments service.

I would shape it as a pyramid weighted toward integration, because that is where the bugs in this kind of system actually live. The unit layer covers pure logic with no I/O — fee and tax calculation, currency handling, state machine transitions, refund eligibility — using Decimal throughout, never floats, and parametrised heavily over boundaries: zero, the smallest currency unit, the maximum, rounding at the half, negative inputs, and every currency the system accepts. These run in milliseconds and there should be a lot of them.

The integration layer runs against a real Postgres from testcontainers with the rollback fixture, and it is where the properties that matter get verified: that a duplicate idempotency key returns the original result instead of charging twice, that a failed capture rolls back cleanly and leaves no partial ledger entry, that concurrent refunds cannot exceed the original amount, and that the ledger balances after every operation. Payment providers are mocked at the transport layer with respx rather than by patching our own client, so our serialisation, error handling and timeout configuration all execute — and the mocked responses must include their real failure modes, not just the happy path: timeouts, 429s, 500s, and the ambiguous case where the request succeeded but the response was lost.

That ambiguous case is the one I would build the most tests around, because it is the defining hazard of payments. A timeout does not mean the charge failed, so every operation needs an idempotency key and the tests need to prove that replaying a request returns the original outcome rather than creating a second charge — including when the replay arrives concurrently with the original still in flight. I would also test reconciliation against the provider explicitly, since that is the safety net when our state and theirs diverge.

Above that, a handful of end-to-end tests over HTTP covering only the critical paths — charge, refund, dispute — plus contract tests against the provider's sandbox running on a schedule rather than per-commit, so an upstream API change is caught within a day without making every build depend on someone else's uptime. I would add property-based tests with Hypothesis for the money arithmetic, since rounding and currency conversion have edge cases nobody thinks to enumerate. And on process: every production incident gets a regression test written before the fix, warnings are errors so deprecations surface early, and the fast unit suite runs on every commit while the full integration suite gates merge.

🎯 Key Takeaways

  • pytest rewrites plain assert to show the values — no assertion method zoo to learn.
  • pytest.raises without match= passes on any exception of that type, including one from your setup.
  • Parametrise over branches and boundaries, not variations of the happy path; give each case an id.
  • Fixtures compose and are injected by name; yield teardown runs even when the test fails.
  • Session scope is for expensive immutable things; anything mutable at session scope leaks between tests.
  • Test against a real database in a transaction that rolls back — mocking it skips exactly the bugs that layer catches.
  • Patch where a name is looked up, not where it is defined, and always pass autospec=True.
  • Mock only what you do not own; a small injected fake beats a patch and asserts on outcomes rather than calls.
  • Inject the clock and any randomness — otherwise the suite fails at midnight, on leap days, or at random.
  • Coverage finds gaps but proves nothing; and never paper over a flaky test with reruns, since the race is usually real in production.
