Anti-Patterns at Scale Production

What you'll master: the capstone for this track — the designs that work perfectly in development, survive the first year, and then fail in ways that are expensive to reverse, each with the measurement that exposes it early. The unbounded array, which is the single most common MongoDB design failure: it does not degrade gradually, it works until a document crosses 16 MB and then fails completely, after 14 months of success. The relational schema in a document database, recognisable by $lookup in every query and a transaction on every write, and measurable as a count of transaction call sites. The collection-per-tenant explosion, where 40,000 collections consumed 18 GB of RAM in metadata before a single document was cached. The hot document, where one global counter produced 40% write conflicts and returned 503s from an idle database. Index sprawl — fourteen indexes accumulated through six months of individually-correct optimisations, ending slower than the start. Workload placement, where analytics on the primary cost unrelated queries 34 ms of p99 that nobody attributed to the dashboard. And the process anti-patterns that produce all of the above: no retention policy, no validators, configuration applied by hand, and a backup nobody has restored. Prerequisites: this is the last lesson of the track — everything before it feeds in.

Part 1 — The Unbounded Array

  { _id: "order_1",
    customerId: ...,
    events: [ { at: ..., type: "created" },
              { at: ..., type: "paid" },
              ... ] }        // grows forever

  It looks like good document modelling. It is the most common
  serious mistake in MongoDB, and it fails in four separate ways
  at once.
FailureMechanismMeasured
Hard 16 MB wallA document cannot exceed it. There is no warning as you approachOne order reached 312,000 events and every write to it began failing
Write amplificationA document is rewritten whole on every update, however smallAppending one 200-byte event to a 6 MB document writes 6 MB
Index explosionA multikey index stores one key per element41 documents with 4,000-element arrays produced 164,000 index keys
Cache wasteReading any field loads the whole documentAn endpoint needing 3 fields pulled 6 MB into cache per request
  THE FIXES, in order of preference

  1. BOUND IT. If only the recent N matter, keep N:
       $push: { events: { $each: [e], $slice: -50 } }
     One atomic operation, permanently bounded. If the product
     only ever shows "recent activity", this is the whole answer.

  2. SEPARATE COLLECTION with a reference:
       events { orderId, at, type }   index { orderId: 1, at: -1 }
     Unbounded growth becomes unbounded DOCUMENTS, which is what
     the database is designed for.

  3. BUCKET PATTERN, if the volume is high and reads are ranged:
       { orderId, bucket: "2026-08", events: [...], n: 412 }
     Bounded per bucket, far fewer documents than option 2.

  AND, regardless of which: maxItems in a validator, so the wall
  is a rejected write with a clear error rather than a 16 MB
  failure eighteen months later.
⚠️ The diagnostic that finds these before they fail: alert on document size, not on document count. $bsonSize: "$$ROOT" in an aggregation gives you the distribution; anything above about 1 MB is a design question, and anything growing monotonically is a future outage with a date attached. Unbounded arrays do not degrade — they work perfectly, then stop — so a gradual metric is the only warning you get.

Part 2 — The Relational Schema Wearing a Document Costume

  SYMPTOMS, any two of which are diagnostic

    - $lookup appears in most queries
    - a transaction wraps most writes
    - collections mirror what would have been tables, one to one
    - a "join table" collection exists: { userId, roleId }
    - reading one screen requires 4+ round trips
    - every write updates a parent's "updatedAt" separately

  COST, measured on one such system
    a single product page:   6 collections, 4 $lookup stages,
                             p99 780 ms
    after remodelling:       1 document, p99 6 ms

The reframe: in a relational database you model the entities and let the query engine assemble them. In a document database you model what one request needs. Those produce different schemas, and applying the first approach to the second engine gives you the costs of both models and the benefits of neither — no joins worth the name, and no atomicity across documents without paying for it.

Relational habitDocument equivalent
A child table joined on every readEmbed it, if it is bounded and owned by the parent
A join table for many-to-manyAn array of ids on whichever side is queried, or both if reads dominate
A transaction to keep two tables consistentOne document, or a conditional update, or a reconciler
A normalised lookup table joined for a labelThe extended reference pattern: store the id and the label
SELECT COUNT(*) on a pageA maintained counter, a capped count, or no total
  THE METRIC THAT CATCHES THIS DRIFTING

  Count the distinct transaction CALL SITES over time.

    one or two, stable      healthy
    steady growth           the model is being pushed relational

  It is a far better signal than any code review, because it is
  a number that trends, and the conversation is much cheaper at
  twenty sites than at two hundred.

Part 3 — Too Many Collections

  THE PATTERN
    orders_tenant_00001, orders_tenant_00002, ...
    or a database per tenant.

  The reasoning is usually sound-sounding: isolation, easier
  per-tenant deletion, "smaller indexes".

  THE COST, measured at 40,000 collections:
    - every collection and every index has an in-memory catalogue
      entry: 18 GB of RAM consumed before a single DOCUMENT was
      cached
    - startup time: 4 minutes, dominated by opening files
    - a schema change means 40,000 operations
    - the balancer and the config metadata grow accordingly
    - listCollections became unusable in tooling
    - each collection's indexes are separately paged, so cache
      hit rates collapse
Requirement behind itBetter answer
"Tenant isolation"A tenantId field on every document, enforced in a single data-access layer, plus per-tenant credentials if the isolation must be technical
"Delete a tenant easily"deleteMany({ tenantId }), batched — or per-tenant encryption keys that can be destroyed
"Smaller indexes per tenant"A compound index led by tenantId partitions the index anyway; scans are bounded to that tenant's keys
"Noisy-neighbour isolation"Zones pinning the largest tenants to dedicated shards — the real answer, and only needed for the few tenants that warrant it
Genuine regulatory separationSeparate clusters for those tenants. A legitimate case, and it should be the exception, priced accordingly

Part 4 — Hot Documents, Hot Keys, and Index Sprawl

  THE HOT DOCUMENT

  A single counter document written by every request:
    counters.updateOne({ _id: "global" }, { $inc: { n: 1 } })

  MEASURED at 900 writes/sec:
    write conflicts               40% of transactions
    withTransaction retries       up to its ~120s budget
    connection pool               exhausted by sleeping requests
    result                        API returned 503 while the
                                  database sat at 12% CPU

  No retry policy, pool size or index fixes this. The fixes are
  structural:
    - shard the counter across N documents, sum on read
    - move it out of the request path entirely (a rollup job)
    - or ask whether the number is needed at all -- in one case
      it was displayed and never acted upon
Hot-spot anti-patternConsequenceFix
Global counter document40% write conflicts, pool exhaustionShard the counter, or remove it
Monotonic shard keyAll inserts on one shard — 8 shards with the throughput of oneHash it, or lead with a non-monotonic field
Indexed updatedAt touched on every writeEvery update becomes an index delete-plus-insertOnly index it if a query needs it
One tenant at 40% of the dataAn unsplittable 340 GB jumbo chunkCompound shard key; zones for the largest tenants
A queue implemented as a collection scanEvery worker scans for the next itemAn indexed status field, ideally a partial index over the pending state
  INDEX SPRAWL -- the anti-pattern built from good intentions

  Six months of individually-correct optimisations:
    "this query is slow"  -> add an index    x14

  Result at 14 indexes on one collection:
    write throughput      14,200/s -> 7,400/s
    index size            1,480 MB, competing with documents for
                          a 31 GB cache
    net effect            SLOWER than before the optimisations
                          started

  After prefix-deduping to 6 indexes (mechanical, no judgement
  required): 4.1 GB of cache recovered, 22% write throughput back,
  no query regression.

  The process failure is that optimisation only ever ADDED. Every
  index change should be followed by an $indexStats review.

Part 5 — Workload Placement

Anti-patternMeasured costFix
Analytics and reports on the primaryUnrelated p99 34 ms → 4 ms once moved. Nobody had attributed that latency to the dashboardsecondaryPreferred, or a hidden tagged member
Heavy aggregations on the request path2.8 s per page load; 11 ms after pre-computing with $mergeMaterialised views on a schedule
Backups from the primaryReads the whole collection through cache, evicting the working setA hidden member
Exports streaming millions of documents on requestTimeouts for the biggest customers, cache churn for everyoneAn async job, on a secondary, paged and projected
No retention policyThe collection grows until indexes no longer fit in cache — a cliff, not a slopeTTL, or time-bucketed collections dropped wholesale
  THE UNBOUNDED-GROWTH ANTI-PATTERN, stated plainly

  Any collection with no retention policy is on a schedule to
  outgrow its cache. The date is calculable:

    (cache size - current working set) / (growth per day)

  That is a real number and almost nobody computes it. When it
  arrives, the symptom is a 180x latency change over a few weeks
  of growth, and the fix under pressure (buy RAM, shard) is far
  more expensive than the fix in advance (decide how long the
  data is useful).

  The question is not technical: "how long is this data worth
  keeping?" is a product decision, and asking it early is the
  single cheapest performance intervention available.

🔑 The common shape of every anti-pattern here: it works, until it does not, and the moment it stops is much more expensive than the moment it started. An unbounded array is free to bound on day one and a migration on day 500. A shard key is a decision on day one and a 26-hour operation later. A retention policy is a conversation early and a capacity emergency late. The most valuable thing this track can leave you with is the habit of asking, for each design, "what does this look like at 100× the data?" — because every measurement in these lessons is what happened to someone who did not.

Interview Questions

Beginner: What is the most common MongoDB design mistake?

The unbounded array — a field that accumulates entries as the entity is used: events on an order, comments on a post, readings on a device.

It is the most common because it looks like good document modelling, and because it does not warn you. It works perfectly until a document crosses the 16 MB limit and then every write to that document fails outright. In one case that was after fourteen months, when a single order reached 312,000 events.

Three other costs arrive earlier and quietly: the whole document is rewritten on every update, so appending 200 bytes to a 6 MB document writes 6 MB; a multikey index stores one key per element; and reading any field loads the entire document into cache.

The fix is to bound it — $push with $slice if only recent entries matter, or a separate collection if the history is genuinely needed — plus maxItems in a validator so the limit is a clear error rather than a surprise.

Beginner: Why is a collection per tenant a bad idea?

Because every collection and every index carries an in-memory catalogue entry. At 40,000 collections that was 18 GB of RAM consumed before a single document was cached, plus four-minute startup times and a schema change that meant 40,000 separate operations.

The requirements behind it are usually real but better served differently: isolation comes from a tenantId field enforced in one data-access layer, plus per-tenant credentials if it must be technical; per-tenant deletion is a batched deleteMany; and "smaller indexes" is already provided by a compound index led by tenantId, which partitions the index anyway.

The one legitimate case is genuine regulatory separation, and the right answer there is separate clusters for those specific tenants — priced as the exception it is, rather than applied to everyone.

Mid: How would you recognise a relational schema in a MongoDB codebase?

A few symptoms, any two of which are diagnostic: $lookup appears in most queries; a transaction wraps most writes; collections map one-to-one onto what would have been tables; there is a join-table collection holding nothing but two ids; and rendering one screen takes four or more round trips.

The underlying difference is that a relational model describes entities and lets the query engine assemble them, while a document model describes what one request needs. Applying the first to MongoDB gives you the costs of both and the benefits of neither — no real join capability, and no cross-document atomicity without paying about 5× per write.

The measurement I would use is the count of distinct transaction call sites over time. One or two, stable, is healthy; steady growth means the model is drifting relational. It is a better signal than code review because it trends, and the conversation is much cheaper at twenty sites than two hundred.

Mid: A team has added an index for every slow query for six months. What has happened?

Each individual decision was probably correct and the aggregate is negative. At fourteen indexes on one collection, write throughput had fallen from 14,200/sec to 7,400, the index set was 1,480 MB competing with documents for a 31 GB cache, and the system was slower overall than before the optimisation effort started.

The process failure is that optimisation only ever added. The corrective step is mechanical and needs no judgement: prefix-dedupe, since {a} is redundant when {a,b} exists and {a,b} is redundant when {a,b,c} does. Doing that took one team from fourteen indexes to six, recovering 4.1 GB of cache and 22% write throughput with no query regression.

Then $indexStats across a full business cycle for anything still unused — noting that the counters reset on restart and that month-end jobs matter — and hideIndex for a week before dropping, because hiding is instant to reverse and rebuilding a large index takes 22 minutes under load.

The durable fix is making the review part of the workflow: every index change closes with an $indexStats check for what it made redundant.

Senior: You are reviewing a design for a new service. What would make you push back?

I would ask one question of every collection — what does this look like at 100× the data? — and push back on the answers that only work at 1×.

Any array that grows with activity. Not because it is wrong, but because "bounded" must be a property someone has asserted. If the answer is "it will not get that big", I want the validator that guarantees it.

A $lookup or a transaction on a hot path. Both are legitimate and both are signals worth interrogating: is this genuinely two entities, or is it one document that has been split because the model was drawn relationally?

Any collection with no retention answer. "How long is this data useful?" is a product question with a calculable consequence — the date the working set exceeds cache — and asking it in design is the cheapest performance intervention available.

A single document written by every request. Counters, sequences, "current state" documents. No retry policy or pool size fixes contention.

Anything requiring a globally unique constraint if sharding is plausible, because a unique index must be prefixed by the shard key, and discovering that after sharding is very expensive.

What I would not push back on: a slightly denormalised schema with some duplication. That is usually the design working correctly, and reviewers coming from a relational background tend to flag it as the problem while missing the unbounded array two fields below.

Senior: You inherit a system with several of these anti-patterns. How do you prioritise?

By expected harm × reversibility cost, not by how offensive each one is to look at. The ones that get worse the longer you wait outrank the ones that are merely bad.

PriorityWhy
1. Cliff-edge failures — arrays approaching 16 MB, a working set approaching cache, a disk filling, a shard key that will need changingThese do not degrade, they stop. And each is dramatically cheaper to fix before the cliff: bounding an array today versus migrating 40M documents later; resharding 100 GB versus 900 GB
2. Missing safety nets — no restore drill, no maxTimeMS, no alerting on evictionsCheap, fast, and they change the severity of everything else. A day's work that turns future incidents into events
3. Contention and hot spotsActively costing availability now, and usually a bounded fix
4. Index sprawl and workload placementMechanical, low-risk, immediate measurable benefit
5. The relational schemaThe largest and most valuable change, and the slowest. It needs to be sequenced with product work, not attempted as a rewrite

The first week, though, is measurement, because the ranking above assumes I know which apply and how close each is to failing: the $bsonSize distribution, the eviction counter, index sizes against cache, the profiler ranked by total time, transaction call-site count, and the growth-per-day figure that dates the cache cliff.

What I would resist: a remediation project. These are best fixed as the surrounding code is touched, with the exception of category 1 and 2 which are genuinely urgent. A quarter-long "technical debt initiative" competes with product work, loses, and leaves the cliff-edge items unfixed — which are the only ones that were actually going to hurt.

And the thing I would insist on regardless: writing down the growth-per-day number and the date it crosses cache. It converts an argument about priorities into a deadline everyone can see, and it is the single most persuasive artefact I have found for getting this kind of work scheduled.

🏋️ Exercises

1 (easy): Identify every anti-pattern in this schema and rank them by urgency. 
  posts {
    _id, authorId, title, body,
    comments: [ { userId, text, at } ],       // unbounded
    viewCount: 0,
    tags: [ ... ]
  }
  comment_likes { commentId, userId }
  post_views    { postId, userId, at }        // no TTL
Solution
RankAnti-patternWhy this urgency
1Unbounded comments arrayA cliff-edge failure. A viral post accumulates comments until writes to that document fail at 16 MB — and it also means every comment write rewrites the whole post, and every post read loads every comment
2post_views with no retentionThe fastest-growing collection here and it grows forever. Compute the date it pushes the working set past cache; that is a real deadline
3viewCount on the post documentEvery view writes the post document — rewriting title, body and the whole comments array to increment an integer. Contention plus write amplification on the largest document
4comment_likes referencing an embedded subdocumentA join table pointing at something that has no independent identity — the relational habit. Also awkward: commentId must be generated by the application since embedded documents have no _id by default

The remodelled version:

  posts     { _id, authorId, title, body, tags,
              commentCount, recentComments: [ ...max 5 ] }
  comments  { _id, postId, userId, text, at, likeCount }
              index { postId: 1, at: -1 }
  likes     { _id: { commentId, userId } }   // natural unique key
  post_views { postId, userId, at }
              TTL index on at, 90 days
  view counts: a rollup job, or a sharded counter -- NOT an
              increment on the post document per view

The recentComments array is deliberate: the post page shows the first few comments, so keeping a bounded copy avoids a second query for the common case while the full list lives in its own collection. That is the subset pattern, and it is the document-model answer to "I need it embedded and unbounded".

Note likeCount on the comment rather than counting likes: the count is displayed constantly and an exact count of a filtered set is the most expensive thing on most pages.

2 (easy): Write the aggregation that finds documents at risk of the 16 MB limit, and say what you would do with the output.
Solution 
  db.posts.aggregate([
    { $project: {
        size: { $bsonSize: "$$ROOT" },
        comments: { $size: { $ifNull: ["$comments", []] } } } },
    { $match: { size: { $gt: 1048576 } } },        // over 1 MB
    { $sort: { size: -1 } },
    { $limit: 50 }
  ])

  // and the distribution, which is the more useful output:
  db.posts.aggregate([
    { $project: { size: { $bsonSize: "$$ROOT" } } },
    { $bucket: {
        groupBy: "$size",
        boundaries: [0, 16384, 262144, 1048576, 4194304, 8388608],
        default: "8MB+",
        output: { n: { $sum: 1 }, maxSize: { $max: "$size" } } } }
  ])

What I would do with it, in order:

  1. Anything above 8 MB is an incident in waiting. Those documents are one busy week from failing every write. Fix them specifically — truncate the array, migrate that entity — before doing anything structural.
  2. Anything above 1 MB is a design question. Not necessarily wrong, but it should be deliberate, and it means every read of that document pulls a megabyte into cache.
  3. Track maxSize as a metric over time. The trend is the warning — an unbounded array does not degrade, so the size trend is the only signal you get before total failure.
  4. Add maxItems to a validator at whatever the current maximum plus headroom is, so growth stops silently continuing while the redesign is scheduled.

Operational caution: this is a collection scan computing a size per document. Run it on a secondary, and on a very large collection consider $sample for the distribution and a targeted query for the outliers.

The related check worth running at the same time: average document size per collection from db.coll.stats().avgObjSize. A collection whose average is climbing is telling you the same story more cheaply, and it costs nothing to sample.

3 (medium): An API returns 503s under load. The database shows 12% CPU, no slow queries, and normal replication. Diagnose.
Solution

The database is not the problem, and every database metric correctly says so. This is client-side — almost always the connection pool.

The mechanism I would look for first: requests that hold a connection while doing nothing. The canonical case is a hot document causing write conflicts inside transactions; withTransaction retries for up to its ~120-second budget, each retrying request holds a pooled connection, and a pool of 100 fills with sleeping requests. New requests cannot check out a connection and the API returns 503 while the database sits idle.

  CONFIRM
    driver metrics: connection checkout wait time, pool
      utilisation, connection hold duration
    serverStatus().connections -- the same picture from the
      other end
    metrics.operation.writeConflicts -- and WHICH document;
      there is almost always exactly one
Other candidates with the same signatureDistinguishing check
Timeout inversion — the driver waits 30 s while the app gave up at 10Compare serverSelectionTimeoutMS against the application timeout
A client created per request instead of per processConnection count far above expectation; connection churn in the server log
Failover aftermath — stale DNS or a runtime DNS cacheRecent election in rs.status(); per-instance behaviour (some instances fine, some not)
A slow downstream service holding request threadsNot a database problem at all; check whether the 503s correlate with database calls

Immediate mitigation: bound the retry with an application-level timeout so a request fails fast instead of occupying a connection, and correct the timeout nesting. Both are configuration.

Durable fix: remove the contention. A single document written by every request cannot be rescued by pool size or retry policy — shard the counter across N documents and sum on read, move it off the request path into a rollup, or establish that nobody acts on the number and delete it.

The lesson for the monitoring: this class of incident is slow to diagnose precisely because teams instrument the database thoroughly and the driver not at all. Checkout wait time and pool utilisation are the two metrics that would have made this obvious in a minute.

4 (medium): A team proposes a database per tenant for a SaaS with 8,000 tenants. Write the response.
Solution

I would take the requirements seriously and reject the mechanism, because the costs are severe and the requirements have better answers.

The measured cost at scale: 40,000 collections consumed 18 GB of RAM in catalogue entries before a single document was cached; startup took four minutes, dominated by opening files; cache hit rates collapsed because each collection's indexes page separately. At 8,000 tenants with even five collections each, that is 40,000 — exactly the measured case. And every schema change, index build or validator update becomes 8,000 operations.

Their requirementBetter mechanism
Isolation — no tenant sees another's datatenantId on every document, enforced in one data-access layer so no query can omit it. If it must be technical, per-tenant credentials with a role scoped by a document filter
Delete a tenant on requestBatched deleteMany({ tenantId }). If the requirement includes backups, per-tenant encryption keys that can be destroyed — which a separate database does not give you either
"Smaller indexes"A compound index led by tenantId already partitions the index; a tenant's scan touches only its own keys
Noisy-neighbour isolationZones pinning the largest tenants to dedicated shards — needed for the few tenants that warrant it, not all 8,000
Per-tenant backup/restorePer-tenant logical export on a schedule. This one genuinely is easier with separate databases, and it is solvable without them

Where I would concede: if a small number of enterprise customers have contractual or regulatory requirements for physical separation, give those tenants their own cluster. That is a legitimate, priced exception — and it is a different thing from 8,000 databases in one deployment.

The design commitment I would ask for in exchange: tenantId on every document without exception, and a data-access layer that makes it impossible to write a query without it. The failure mode of shared-collection multi-tenancy is a query that forgets the filter, and the defence is structural, not a code-review habit. Getting that right also makes { tenantId: 1, ... } the natural shard key later, which is the key you want anyway.

5 (hard): Design a "MongoDB design review" that a team can apply to every new feature in under 30 minutes.
Solution

Constraints from watching reviews fail: it must fit in a normal design discussion, every question must have a concrete answer rather than a judgement, and it must be short enough that people run it rather than skip it.

  SIX QUESTIONS. Each has a right kind of answer.

  1. WHAT DOES ONE REQUEST NEED?
     Show the document a request returns. If assembling it takes
     more than one query, justify each extra one.
     (Catches: the relational schema, the N+1)

  2. WHAT GROWS WITHOUT BOUND?
     Name every array and every collection that grows with
     activity. For each: what caps it, or what retention applies?
     "It won't get big" is not an answer -- a validator is.
     (Catches: the 16MB wall, the cache cliff)

  3. WHAT DOCUMENT DOES EVERY REQUEST WRITE?
     If there is one, that is the contention point.
     (Catches: hot documents, counters, sequences)

  4. WHICH INDEXES, AND WHAT DID THEY REPLACE?
     Every proposed index, in ESR order, with the query shape it
     serves -- and which existing index it makes redundant.
     (Catches: index sprawl)

  5. WHERE DOES THIS RUN?
     Request path, or scheduled? Primary, or secondary? If a
     query cannot use an index to reduce its input, it is batch
     work whatever calls it.
     (Catches: analytics on the primary, aggregations on the hot
      path)

  6. AT 100x THE DATA, WHAT BREAKS FIRST?
     One sentence. If nobody can answer, that is the finding.
     (Catches: everything the first five missed)

Why these six: each maps to a failure that is cheap now and expensive later, and each has a verifiable answer — a document shape, a validator, a named document, an index list, a placement, a sentence. Questions like "is this well modelled?" produce opinions; these produce artefacts.

What I would explicitly leave out: anything about naming, formatting, or field-level style. Including them trains people to treat the whole review as taste, and then question 2 gets the same weight as a debate about camelCase.

How to make it stick: the answers go in the design document, not in a reviewer's head, so six months later the question "what was supposed to cap this array?" has an answer. And question 6's answer becomes a note in the ticket — when it turns out to be right, that note is what gets the follow-up work scheduled.

The honest limitation: this catches design problems, not operational ones. It will not find a missing restore drill, an untuned timeout, or an alert that does not exist — those belong in the readiness checklist, and the two together are what actually cover the ground.

  MONGODB: WHAT ACTUALLY MATTERS

  THE MODEL
  - The atomic single document is the primitive. Model what one
    request needs, not what the entities are.
  - Embed what is bounded and owned. Reference what is unbounded
    or shared. Duplicate deliberately, and decide snapshot vs
    live reference explicitly.
  - Nothing may grow without a bound. Every array needs a cap;
    every collection needs a retention answer.

  THE FIVE NUMBERS TO WATCH
  1. pages evicted by application threads    -- alert on > 0
  2. replication lag                          -- majority writes
                                                 stall
  3. oplog window (timeDiff)                  -- resync risk
  4. slow-query total time by queryHash       -- ranks real cost
  5. connection pool utilisation (driver side) -- 503s with a
                                                 healthy database

  INDEXES
  - ESR: Equality, Sort, Range.
  - Only prefixes of a compound index are usable.
  - keysExamined and docsExamined vs nReturned is the whole
    diagnosis.
  - Partial indexes are the highest-leverage technique available.
  - Every index costs ~6-8% of write throughput and shares the
    cache. Dedupe by prefix; hide before dropping.

  WRITES
  - w:"majority" is the default and almost always correct. w:1
    can be rolled back.
  - wtimeout means "unknown", never "did not happen". Make
    retries idempotent.
  - Put the precondition in the update filter; most transactions
    are unnecessary.
  - Backfills: batched on _id ranges, w:"majority", lag-aware,
    restartable.

  OPERATIONS
  - maxTimeMS on every query. Nest timeouts strictly.
  - Reports, backups and index builds go on a hidden member.
  - Upgrade binaries and set FCV as separate steps.
  - Validators, roles and indexes live in the repo, applied by
    migration.

  THE THINGS THAT END COMPANIES
  - A backup nobody has restored.
  - A shard key chosen without measuring the data distribution.
  - A database reachable from the internet without auth.
  - One credential with root, shared by five systems.

  THE HABIT
  - For every design: what does this look like at 100x?
  - For every incident: currentOp, evictions, concurrent work,
    replication, connections -- then the slow query log.
  - For every optimisation: what did it make redundant?

Why this selection: everything on it is either a number you can watch, a rule you can apply without judgement, or a failure that is disproportionately expensive to fix late. What is missing is deliberate — syntax, operator lists and API details are all one search away, while the judgement about what to watch and what to bound is what people actually lack when they take over a system.

The two lines I would most want them to internalise are "nothing may grow without a bound" and "a backup nobody has restored is a hypothesis". Between them they cover the majority of the genuinely severe incidents in this track — the cliff-edge failures and the unrecoverable ones.

🎯 Key Takeaways

  • The unbounded array is the most common serious mistake. It does not degrade — it works for 14 months and then every write to that document fails.
  • Monitor document size, not count. The size trend is the only warning an unbounded array gives you.
  • Bound arrays with $slice and enforce it with maxItems, or move the growth into its own collection.
  • A relational schema in MongoDB gives you the costs of both models and the benefits of neither — one page went from p99 780 ms to 6 ms when remodelled.
  • A growing count of transaction call sites is the signal that the model is drifting relational.
  • A collection per tenant consumed 18 GB of RAM in catalogue alone at 40,000 collections. Use a tenantId field; reserve separate clusters for genuine regulatory exceptions.
  • One document written by every request is a design problem no retry policy or pool size can fix — 40% write conflicts and 503s from a database at 12% CPU.
  • Index sprawl is built from individually-correct decisions. Fourteen indexes halved write throughput; prefix-deduping to six recovered 4.1 GB of cache with no regression.
  • Every optimisation should end with "what did this make redundant?"
  • Reports, backups and exports on the primary cost everyone else's p99 — 34 ms attributed to nothing until the workload moved.
  • A collection with no retention policy has a calculable date on which its working set exceeds cache. Compute it.
  • "How long is this data useful?" is the cheapest performance intervention available, and it is a product question.
  • Validators, roles and indexes belong in the repository, applied by migration — hand-applied configuration drifts and cannot be reviewed.
  • Rank slow queries by total time. The one people complain about is rarely the one consuming the cluster.
  • Test against production-like cardinality, not production-like schemas — the same code spills at 2.1M group keys and not at 40.
  • An untested backup and an uncalculated RTO are both guesses — 4 hours designed, 9h47m measured.
  • Ask of every design: what does this look like at 100× the data? Every measurement in this track is what happened to someone who did not.
