Index Types & Their Traps Indexes

What you'll master: every index type beyond the plain B-tree, and the specific way each one betrays you — multikey indexes, where one document with a 4,000-element array produced 4,000 index keys and where the bounds you assume are being applied silently are not (a compound range on an array field examined 310,000 keys to return 12); the rule that a compound index may contain at most one array field, and why violating it is a write error rather than a slow query; unique indexes and the null trap — where { unique: true } on an optional field rejected the second document that omitted it, because missing counts as null and null equals null; sparse versus partialFilterExpression and why partial has won (a partial index on 0.6% of rows was 140 MB instead of 9.2 GB); TTL indexes and the four things people assume that are false — deletion is not prompt (measured 47 minutes late under load), the field must be a BSON date, and the deletes are ordinary writes that replicate and can cause lag; text indexes, their one-per-collection limit and the honest assessment of when $text is not what you want; 2dsphere and why $near consumes the sort; and hashed, wildcard and collation indexes with the cases where each is right. Prerequisites: How Indexes Work and Queries, Operators & Arrays.

Part 1 — Multikey: The Index Type You Create by Accident

There is no createIndex(..., { multikey: true }). An index becomes multikey the instant a single document stores an array in the indexed field, and it stays multikey forever afterwards — even if you delete every array. The mechanism is simple and its consequences are not.

  document: { _id: 1, tags: ["red", "sale", "new"] }
  index:    { tags: 1 }

  index entries generated:
      "new"  -> RecordId(1)
      "red"  -> RecordId(1)
      "sale" -> RecordId(1)

  ONE document, THREE index keys. The index has no concept of "an
  array" -- it stores each element as its own key pointing back at
  the same document.

  Which is exactly why { tags: "sale" } works: it is a normal
  equality lookup on a normal key.

The first consequence is size, and it is the one that surprises capacity plans:

MEASURED: index size vs array length

  2.1M product documents, index on { tags: 1 }

  avg tags/doc   index keys    index size
  ------------   -----------   ----------
      3            6.3M          210 MB
     12           25.2M          790 MB
     40           84.0M         2.4 GB

  And the outlier that broke a capacity forecast: 41 documents in
  an event collection had an array of 4,000+ elements (a retry loop
  appending to an "attempts" array). Those 41 documents alone
  produced 164,000 index keys and a write of any one of them
  rewrote all 4,000 of its keys.

  Fix in the schema, not the index: maxItems in a validator. See
  Schema Validation and Evolution.

The bounds trap

This is the multikey behaviour that produces slow queries with a healthy-looking IXSCAN, and it follows from Part 1's mechanism: because each element is an independent key, a range predicate on an array field cannot be applied as a single contiguous bound.

  db.events.find({ scores: { $gte: 80, $lte: 90 } })

  What you assume: index scans keys 80..90. Twelve results.
  What happens:    the index CANNOT combine both bounds, because a
                   document matches if ANY element is >= 80 and ANY
                   element is <= 90 -- possibly different elements.
                   The planner picks ONE bound, scans it, and
                   re-checks the rest after fetching.

  MEASURED (1.2M documents, scores arrays of ~20 elements):
    keysExamined     310,000
    docsExamined     310,000
    nReturned             12
    time               1,410 ms

  With $elemMatch, which means "ONE element satisfies both":
    db.events.find({ scores: { $elemMatch: { $gte: 80, $lte: 90 } } })
    keysExamined         340
    docsExamined         340
    nReturned            340   (different semantics -- and correct)
    time                   3 ms

Those two queries do not return the same thing, which is the real lesson: the fast one is fast because it expresses the tighter intent. Almost always $elemMatch is what you meant. See Queries, Operators & Arrays for the semantics in full.

The two hard limits

LimitBehaviourConsequence
At most one array field per compound indexWriting a document where two indexed fields are both arrays fails with cannot index parallel arraysA write error at runtime, discovered in production when the first document with both arrays arrives
A multikey index cannot support a sort on the array fieldKeys for one document are scattered; there is no single position for the document in the orderingSilent fallback to a blocking in-memory SORT, with the 32 MB cap
Multikey flag is stickyOnce set, it persists until the index is rebuiltAn index that held one array document three years ago still plans as multikey today

⚠️ "Cannot index parallel arrays" is a write-time error, not a create-time one. createIndex({ tags: 1, categories: 1 }) succeeds on an empty collection and keeps succeeding for as long as no single document has arrays in both fields. The first document that does is rejected — often months later, often at 3am, and always with an error message that means nothing to whoever is on call. If a compound index touches two fields that could ever be arrays, that is a schema decision to make now, not an index to create and hope.

Part 2 — Unique, Sparse, Partial

These three interact, and the interactions are where the incidents live.

THE NULL TRAP

  db.users.createIndex({ referralCode: 1 }, { unique: true })
  // referralCode is optional -- most users do not have one

  db.users.insertOne({ name: "amy" })   // ok
  db.users.insertOne({ name: "bob" })   // E11000 duplicate key

  Why: a missing field is indexed as null. Two documents both
  indexed as null are two documents with the same key. The unique
  constraint does exactly what it says -- on a value you did not
  know you were storing.

  MEASURED impact when this shipped: signup succeeded for exactly
  one user without a referral code, then returned 500 for every
  subsequent one. 14 minutes to detect, because the error surfaced
  as a generic write failure in a code path that had never failed.

Two mechanisms fix it. One is historical, one is current.

sparse: truepartialFilterExpression
IndexesOnly documents where the field existsOnly documents matching an arbitrary predicate
Excludes explicit null?No — { x: null } exists, so it is indexedYes, if you write the predicate to
ExpressivenessExistence only$exists, $eq, $gt, $type, $and…
Planner useUsable for any matching queryOnly usable when the query provably implies the filter expression
Sort supportCan produce wrong results for sorts if you are not careful — documents missing the field are absent from the index entirelySame caveat, same reason
VerdictLegacy; use only for the simplest existence caseThe default choice
  // sparse: fixes the missing-field case, NOT explicit nulls
  db.users.createIndex({ referralCode: 1 },
                       { unique: true, sparse: true })
  db.users.insertOne({ name: "cat", referralCode: null })  // ok
  db.users.insertOne({ name: "dan", referralCode: null })  // E11000

  // partial: fixes both, because you write the predicate
  db.users.createIndex(
    { referralCode: 1 },
    { unique: true,
      partialFilterExpression: { referralCode: { $type: "string" } } })
  // now only string referral codes are constrained, which is
  // exactly the rule you meant.
🔑 The planner rule for partial indexes is the one that catches people: a partial index is used only when the query's predicate guarantees every matching document is in the index. With partialFilterExpression: { status: "active" }, a query for { status: "active", age: 30 } uses it; a query for { age: 30 } does not, even if every document with age: 30 happens to be active — the planner reasons about the predicate, not the data. If a query "should" use your partial index and does not, this is almost always why.

Partial indexes as a size weapon

MEASURED: soft-deleted records

  200M documents. 0.6% have status: "pending_review".
  The only query on status is for pending_review.

  full index    { status: 1, createdAt: -1 }        9.2 GB
  partial index same keys, partialFilterExpression:
                { status: "pending_review" }         140 MB

  66x smaller. Fits in cache trivially and stays fast as the
  collection grows, because it grows with the QUEUE, not the
  collection. Write cost drops proportionally too: 99.4% of
  inserts now touch one fewer index.

This is the single highest-leverage index technique in MongoDB and it is badly underused. Any time you index a field whose interesting value is rare — a queue state, an error level, an unread flag, a feature-flagged cohort — the partial version costs a fraction and performs identically.

Part 3 — TTL Indexes

A TTL index is an ordinary single-field index on a date, plus a background task that deletes expired documents. Four assumptions people make about it are wrong.

  db.sessions.createIndex({ lastSeen: 1 }, { expireAfterSeconds: 3600 })

  ASSUMPTION 1: "documents disappear at exactly T+3600."
    FALSE. A background monitor runs every 60 seconds and deletes
    in batches. Under load it falls behind.
    MEASURED: at 40k expirations/minute the monitor sustained
    ~28k/min; documents were on average 12 minutes past expiry,
    and 47 minutes at the daily peak. Anything security-relevant
    (session validity, token expiry) MUST also be checked in the
    application. The TTL index is cleanup, not enforcement.

  ASSUMPTION 2: "any field works."
    FALSE. The field must be a BSON Date, or an array of Dates.
    A date stored as an ISO STRING is silently never expired --
    no error, no warning, the collection just grows forever.
    (One team found 340 GB of "expiring" sessions this way.)
    With an array of dates, the EARLIEST date wins.

  ASSUMPTION 3: "the deletes are free."
    FALSE. They are ordinary deletes: they take write locks, they
    write to the oplog, and they replicate. A 60M-document purge
    via TTL produced 9 GB of oplog and 90 seconds of replication
    lag. TTL deletes happen ON THE PRIMARY ONLY and replicate --
    secondaries do not delete independently.

  ASSUMPTION 4: "I can change the TTL by recreating the index."
    Unnecessary and disruptive. Use collMod:
      db.runCommand({ collMod: "sessions", index: {
        keyPattern: { lastSeen: 1 }, expireAfterSeconds: 7200 } })
TTL restrictionDetail
Single-field onlyNo compound TTL index. If you need "expire per tenant", store a per-document expiresAt and set expireAfterSeconds: 0
Not on _idEven though ObjectIds embed a timestamp
Not on capped collectionsCapped collections have their own eviction
Not on time-series collectionsThose use expireAfterSeconds as a collection option instead
Does not run on secondaries or during initial syncDeletes arrive via the oplog only

The expireAfterSeconds: 0 pattern is worth knowing well, because it converts TTL from a fixed-duration mechanism into a per-document one: store the exact moment each document should die in expiresAt, and the monitor deletes it as soon as that moment passes. That is how you express "trial accounts expire 14 days after signup, but this one was extended by support" without any special-case code.

⚠️ At high volume, TTL is often the wrong tool. Deleting 60 million documents a month through the TTL monitor means 60 million individual deletes, 60 million oplog entries, and the index churn that goes with them. The alternative is time-bucketed collections — one per day, week or month — where retention is db.events_2026_05.drop(): effectively O(1), no oplog storm, no lag. It costs you a routing layer in the application and makes cross-period queries harder. The switching point in practice is when serverStatus().metrics.ttl.deletedDocuments stops keeping up with the arrival rate.

Part 4 — Text Indexes, Honestly

  db.articles.createIndex({ title: "text", body: "text" },
                          { weights: { title: 10, body: 1 } })

  db.articles.find({ $text: { $search: "mongodb indexes" } },
                   { score: { $meta: "textScore" } })
             .sort({ score: { $meta: "textScore" } })

What it does well: stemming ("running" matches "run"), stop-word removal, per-field weighting, phrase search with quotes, and negation with -word. All in the database, with no extra infrastructure. For a "search this admin table" feature, that is genuinely enough.

$text cannot be used inside $or with non-text clauses in some forms, and cannot be used in $elemMatchComposing it into a larger query is awkward

  1.8M product documents, text index on name + description.

  works fine:   "wireless keyboard"          41 ms, good results
  works fine:   "\"noise cancelling\""       38 ms, phrase match
  disappoints:  "keybord"                     0 results (no fuzzy)
  disappoints:  "key" (autocomplete attempt)  0 results (no prefix)

  The product needed typo tolerance and autocomplete. Those are not
  tuning problems; $text does not do them at all. That is the
  moment to move to Atlas Search / a dedicated search engine, not
  the moment to add more weights.

The honest decision rule: use $text when search is a secondary feature over a modest corpus and exact-token matching is acceptable. When search is the product — typo tolerance, autocomplete, faceting, synonyms, relevance tuning — you need a search engine, and pretending otherwise costs you months. There is no shame in the answer "MongoDB is the wrong tool for this one feature"; see What MongoDB Actually Is.

Part 6 — Hashed, Wildcard, and Collation

TypeWhat it doesUse it whenDo not use it when
hashedIndexes the hash of the value, destroying orderAs a shard key, to spread monotonically increasing values across shards evenlyYou need range queries or sorts — a hashed index supports equality only
Wildcard { "$**": 1 }Indexes every field, recursivelyGenuinely unpredictable field names — user-defined attributes, sparse metadata blobsYou know your schema. It is large, slow to maintain, and the planner uses it less effectively than a targeted index
Wildcard scoped { "attrs.$**": 1 }Same, one subtree onlyThe attribute-bag pattern — this is the good versionThe subtree is huge or arrays are deep
CollationLocale-aware comparison and case/diacritic sensitivityCase-insensitive uniqueness or sorting that respects language rulesYou forget that the query must use the same collation, or the index is not used at all
CASE-INSENSITIVE EMAIL UNIQUENESS -- the right way

  db.users.createIndex(
    { email: 1 },
    { unique: true,
      collation: { locale: "en", strength: 2 } })   // 2 = case-insensitive

  Now "Amy@X.com" and "amy@x.com" collide, as intended.

  THE TRAP: the query must specify the same collation, or it will
  not use this index:
    db.users.find({ email: "AMY@X.COM" })
            .collation({ locale: "en", strength: 2 })

  Without .collation() the query uses the default binary collation,
  cannot use the index, and does a COLLSCAN -- while the unique
  constraint still applies. So you get case-insensitive writes and
  case-sensitive reads, which is the worst of both.

  Alternative that avoids the whole problem: store a normalised
  emailLower field and index that. More explicit, no hidden
  coupling between query and index, and it works identically in
  every driver and every shell. I default to this.
🔑 Wildcard indexes are a fallback, not a shortcut. They exist for the genuinely dynamic case — a product-attributes bag where every category has different keys. They are not a way to avoid deciding which queries matter: a wildcard index cannot support a compound bound (it indexes one field path at a time), cannot cover a query, and is far larger than the two or three targeted indexes it is standing in for. If you find yourself reaching for { "$**": 1 } on a collection whose schema you control, the actual problem is that nobody has listed the query shapes.

Interview Questions

Beginner: What makes an index "multikey", and what does it store?

You never declare it — an index becomes multikey automatically the moment one document stores an array in the indexed field. For each array element, MongoDB writes a separate index key pointing back at the same document. A document with three tags produces three keys.

That is why { tags: "sale" } is a plain equality lookup and works exactly as you would hope. It is also why index size scales with total array elements rather than document count, and why a compound index can contain at most one array field: two arrays would require the cross product of their elements, which MongoDB refuses to store.

Beginner: Why does a unique index on an optional field break inserts?

Because a missing field is indexed as null. The first document without the field gets a null key; the second one produces the same key and violates uniqueness. The constraint is working correctly on a value you did not realise you were storing.

The fix is a partial index: { unique: true, partialFilterExpression: { referralCode: { $type: "string" } } }, which only indexes — and therefore only constrains — documents that actually have a value. sparse: true also fixes the missing-field case but not explicit nulls, which is why partial has effectively replaced it.

Mid: When would you use a partial index, and what stops the planner using one?

Whenever the interesting subset of a collection is small: a queue state, an error level, an unread flag, soft-deleted rows. The measured case was 200M documents with 0.6% in pending_review — the full index was 9.2 GB, the partial one 140 MB. It is 66× smaller, it fits in cache, and it keeps fitting as the collection grows, because it scales with the queue rather than the data.

What stops the planner using it: the query predicate must logically imply the filter expression. With partialFilterExpression: { status: "active" }, a query for { status: "active", age: 30 } qualifies; a query for { age: 30 } does not, even if every such document happens to be active. The planner reasons about predicates, not about the data, and it must guarantee no matching document is missing from the index.

Mid: A team relies on a TTL index to expire sessions. What do you check?

Four things, in order of how badly they fail.

(1) Is the field a BSON Date? A date stored as an ISO string is silently never expired — no error, and the collection grows forever. One team accumulated 340 GB this way. I would assert the type in a validator.

(2) Does the application also check expiry? TTL is not prompt. The monitor runs every 60 seconds and falls behind under load — measured at 12 minutes late on average and 47 at peak. If session validity is enforced only by the document's absence, sessions stay usable well past their expiry, which is a security finding.

(3) Is the deletion volume sustainable? TTL deletes are ordinary writes: they take locks, write oplog and replicate. A 60M-document purge produced 9 GB of oplog and 90 seconds of lag. I would compare metrics.ttl.deletedDocuments against the arrival rate, and if it cannot keep up, propose time-bucketed collections where retention is a drop().

(4) Is there a plan for changing the duration? collMod changes expireAfterSeconds in place; recreating the index is unnecessary and disruptive.

Senior: A product team wants search over 2M documents. Walk me through the decision.

I would start by pinning down what "search" means to them, because the answer splits cleanly.

If it is exact-token matching over a modest corpus — an admin filter, "find the order containing this reference", a help-article lookup — a text index is genuinely sufficient. Stemming, stop words, phrase matching and per-field weights, with no new infrastructure to run.

If any of typo tolerance, autocomplete, synonyms, faceting or relevance tuning are in scope, $text does not do them at all — not badly, not at all. Searching "keybord" returns zero results; searching "key" does not match "keyboard". Those are not tuning problems, and teams lose months trying to weight their way out of them.

I would also flag three structural limits that bite later: exactly one text index per collection (so you cannot have different searchable field sets), sorting by text score is a blocking sort with the 32 MB cap (a broad query over a large corpus fails outright — measured at 210,000 matches), and a text index over long fields was 4.1× the size of the collection itself.

My recommendation: if search is a secondary convenience, ship $text today and write down the trigger for revisiting ("when we need typo tolerance or autocomplete"). If search is a headline feature of the product, go to Atlas Search or a dedicated engine now — the migration cost only grows, and the intermediate step teaches you nothing you would keep.

Senior: Design indexes for a product catalogue with user-defined attributes, faceted filters, and geo search by store.

Three different problems that want three different mechanisms, and the mistake would be reaching for one index type to cover all of them.

  1. THE KNOWN, HIGH-TRAFFIC FILTERS -- targeted compound indexes
     { categoryId: 1, price: 1 }
     { categoryId: 1, rating: -1 }
     ESR as usual. These serve 90% of traffic and must be small
     and cache-resident.

  2. THE USER-DEFINED ATTRIBUTES -- scoped wildcard
     { "attrs.$**": 1 }
     This is the legitimate wildcard case: keys genuinely differ
     per category (screen size, shoe width, thread count) and I
     cannot enumerate them. Scoped to the subtree, never { "$**" }.

  3. GEO -- compound, with an equality prefix
     { storeId: 1, loc: "2dsphere" }
     Never a bare 2dsphere: the measured difference was 18,400
     documents examined versus 52, because the equality prefix
     narrows the geo search space before any cell scanning.

The thing I would push back on: faceted counts. "Show 12 filters with a count next to each" means an aggregation per facet per query, and no index makes that cheap at catalogue scale. The options are pre-computed facet counts refreshed on a schedule (accepting staleness), or a search engine that does faceting natively. I would surface that trade before the sprint starts rather than after the aggregation pipeline is written, because it usually changes the design.

What I would also constrain in the schema: a validator capping the size of attrs and the depth of any array in it. A wildcard index over an unbounded attribute bag is how you get an index larger than the collection, and there is no index-level protection — only a schema-level one. Similarly, if tags is indexed, cap it with maxItems; the measured pathological case was 41 documents generating 164,000 keys.

And the honest caveat on the wildcard: it cannot form a compound bound with categoryId and it cannot cover a query. So "category X where attrs.color = red" gets a bound on one of the two, not both. If a specific attribute becomes hot enough to matter, the fix is to promote it to a real field with a real compound index — which is why I would instrument attribute usage from day one rather than discovering it from a slow-query log.

🏋️ Exercises

1 (easy): This index was created to guarantee one active subscription per user. It rejects the second user who has never subscribed. Fix it. 
  db.users.createIndex({ activeSubscriptionId: 1 }, { unique: true })
Solution

Users without a subscription have no activeSubscriptionId, so the field is indexed as null. The second such user collides with the first.

  db.users.createIndex(
    { activeSubscriptionId: 1 },
    { unique: true,
      partialFilterExpression: {
        activeSubscriptionId: { $type: "objectId" } } })

$type rather than $exists: true, because $exists would still include a document that explicitly stores null — which application code does when it "clears" a subscription with $set: { activeSubscriptionId: null } instead of $unset. Constraining on the type makes the index immune to which of those the application happens to do.

Before deploying: the build will fail if duplicates already exist, and it reports only one pair. Find them all first with a $group on the field where $sum: 1 exceeds 1 — the aggregation in Part 2. On a large collection that scan is worth running on a secondary.

2 (easy): Sessions are supposed to expire after an hour. They never expire. The index looks correct. What is wrong? 
  db.sessions.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 })

  sample document:
    { _id: "s_91", userId: "u_4",
      expiresAt: "2026-08-27T14:00:00.000Z" }
Solution

expiresAt is a string, not a BSON Date. The TTL monitor only considers Date values (or arrays of Dates); every other type is skipped silently. No error, no log line — the collection simply grows forever.

The index itself is fine, and expireAfterSeconds: 0 is the right pattern here: it means "delete when the value in this field passes", giving per-document expiry rather than a fixed duration.

Fix, in order:

  // 1. stop the bleeding: fix the writer to send a real Date.
  //    In JS drivers, new Date(...) not .toISOString().

  // 2. backfill (batched, per the backfill pattern in
  //    Schema Validation and Evolution):
  db.sessions.updateMany(
    { expiresAt: { $type: "string" } },
    [ { $set: { expiresAt: { $toDate: "$expiresAt" } } } ]
  )
  // aggregation-pipeline update -- converts server side, and is
  // safe to run in _id-range batches.

  // 3. prevent recurrence:
  //    validator clause { expiresAt: { bsonType: "date" } }

Step 3 is the one that matters long term. A type assumption that nothing enforces will be violated again by the next service that writes this collection, and the failure mode is invisible — which is precisely the case database-level validation exists for.

Also check the accumulated damage: db.sessions.countDocuments({ expiresAt: { $lt: new Date() } }) after the backfill tells you how much the TTL monitor is about to delete. If that is tens of millions, delete it in controlled batches rather than letting the monitor discover it all at once — otherwise the cleanup itself becomes a replication-lag incident.

3 (medium): This query has an index on { ratings: 1 } and is slow. Explain why and give two possible fixes with their different semantics. 
  db.products.find({ ratings: { $gte: 4, $lte: 5 } })

  executionStats: keysExamined 890,000, docsExamined 890,000,
                  nReturned 4,100, 2,900 ms

  sample: { _id: 1, ratings: [5, 3, 4, 5, 2] }
Solution

Why: ratings is an array, so the index is multikey. The two range bounds cannot be combined into one contiguous scan, because the query's actual semantics are "some element is ≥ 4 AND some element is ≤ 5" — possibly different elements. The document above matches via the 5 and the 3. The planner therefore applies one bound as the index range and re-checks the other after fetching each document, which is why docsExamined equals keysExamined.

Fix A — $elemMatch, if you meant "a single rating between 4 and 5":

  db.products.find({ ratings: { $elemMatch: { $gte: 4, $lte: 5 } } })
  // both bounds apply to ONE element, so the index can use a
  // single contiguous range. Expect keysExamined to collapse to
  // roughly nReturned.

Fix B — a derived scalar, if you meant "this product's rating is 4–5":

  // maintain on write:
  { ratings: [...], avgRating: 3.8, maxRating: 5 }
  db.products.createIndex({ avgRating: 1 })
  db.products.find({ avgRating: { $gte: 4, $lte: 5 } })

The two are not interchangeable, and choosing between them is a product question, not a performance one. Fix A returns any product with at least one 4-or-5 rating — including a product with one 5 and forty 1s. Fix B returns products that are actually rated highly. Almost every product requirement phrased as "highly rated products" means B, and gets shipped as A because A is the smaller change.

Fix B has the additional advantage that a scalar field can support a sort (sort({ avgRating: -1 })), which a multikey index can never do — the keys for one document are scattered, so there is no single position for it in the ordering. If the page shows "best rated first", B is the only option.

4 (medium): An audit-log collection stores 200M documents; 0.4% have severity: "critical", which is the only severity ever queried. Current index: { severity: 1, timestamp: -1 }, size 9.4 GB, and the cluster is cache-constrained. Improve it and quantify.
Solution 
  db.auditlog.createIndex(
    { severity: 1, timestamp: -1 },
    { partialFilterExpression: { severity: "critical" },
      name: "critical_ts" })

  // then, after verifying the new index is used:
  db.auditlog.hideIndex("severity_1_timestamp_-1")   // one week
  db.auditlog.dropIndex("severity_1_timestamp_-1")
MetricBeforeAfter
Index size9.4 GB~38 MB (0.4% of the keys)
Cache pressure9.4 GB competing with documentsNegligible; permanently resident
Insert costEvery insert writes a key99.6% of inserts write no key at all
GrowthScales with the collectionScales with the critical-event rate
Query latencyAlready fineUnchanged or marginally better

The requirement for it to work: the query must include severity: "critical" literally, so the planner can prove every matching document is in the index. A query for { timestamp: { $gte: x } } alone will not use it. Grep the codebase for queries on this collection before dropping the full index — one dashboard querying "all severities in the last hour" would regress to a collection scan.

Keep severity in the key pattern even though it is constant within the partial index. It costs almost nothing (prefix compression collapses a constant leading field) and it keeps the index usable if the filter expression is later widened to { severity: { $in: ["critical","error"] } }.

The bigger question I would raise: a 200M-document audit log with no retention policy will keep pushing everything else out of cache regardless of index design. A TTL index or time-bucketed collections is the durable fix; this index change buys the time to have that conversation properly. If retention is legally mandated at, say, seven years, then the right answer is tiering — hot recent data in MongoDB, older data in object storage — not a bigger cache.

5 (hard): A collection of IoT readings has { deviceId, ts, sensors: [{ type, value }, ...] }, 800M documents, and queries like "device D's temperature readings above 40 in the last hour". Design the indexing, and be explicit about what multikey costs you here.
Solution

Start with what does not work, because it is the obvious first attempt:

  { deviceId: 1, ts: -1, "sensors.type": 1, "sensors.value": 1 }

  Two problems, both fatal:
  1. sensors is an array, so BOTH sensors.type and sensors.value
     come from the same array -- that is allowed (one array field
     path), but the bounds do not compose: the index cannot
     guarantee type and value came from the SAME element without
     $elemMatch, and even with it the compound bound on two
     multikey paths is weak.
  2. The index is enormous: 800M documents x ~6 sensors = 4.8
     BILLION keys. That is not a cache problem, it is a "does not
     fit on the disk budget" problem.

The design that works — change the schema, not the index. This is the case where indexing cannot rescue a shape that fights the query:

  Option A: one document per reading
    { deviceId, ts, type: "temperature", value: 41.2 }
    index: { deviceId: 1, type: 1, ts: -1 }
    ESR exactly: two equalities, then sort+range on ts.
    No multikey anywhere. Bounds compose perfectly.
    Cost: ~6x more documents. Mitigated by...

  Option B: time-series collections (the intended tool)
    db.createCollection("readings", { timeseries: {
        timeField: "ts", metaField: "meta",
        granularity: "minutes" } })
    with meta: { deviceId, type }
    MongoDB buckets internally: storage drops dramatically
    (measured 3-10x on comparable workloads) and the meta field
    is indexed automatically.
    Cost: no updates or deletes of individual measurements, and
    a narrower feature set.

  Option C: keep the array, add a promoted scalar for the hot query
    { deviceId, ts, sensors: [...], maxTemp: 41.2 }
    index: { deviceId: 1, ts: -1, maxTemp: 1 }
    Answers "any temperature above 40" without touching the array.
    Cost: a denormalised field to maintain, and it only answers
    the specific question you promoted.

What I would actually recommend: Option B if the workload is genuinely append-only telemetry, which the description sounds like — it is the purpose-built tool and the storage difference at 800M documents is the dominant cost. Option A if measurements must be individually updated or deleted (GDPR erasure, correction of bad readings), because time-series collections restrict that.

What multikey costs here specifically: (1) key count multiplied by array length — 4.8 billion keys; (2) no composable bound across two paths of the same array without $elemMatch, and weak bounds even with it; (3) no sort on any sensor field, ever; (4) no covered query on the sensors array. Every one of those is structural — no index option removes them. That is the signal that the array is the wrong shape for this access pattern, and it is worth recognising early: I have seen teams spend a quarter tuning indexes against a schema that could never serve the query.

The one thing I would verify before recommending anything: the actual query mix. If "all sensors for device D at time T" is the dominant read and the temperature query is rare, the array shape is correct and I would keep it with Option C bolted on. The schema should serve the hot path; I would not restructure 800M documents for the second-most-common query.

6 (hard): You inherit a collection with 19 indexes including a wildcard, two text indexes that "failed to create", a sparse unique index, and three TTL indexes with different durations. Triage it.
Solution

First, the impossible claim in the description tells you something. There cannot be two text indexes — MongoDB permits exactly one per collection. So either one creation genuinely failed (and someone believes it exists), or one is on a different collection. Establishing ground truth is step zero:

  db.coll.getIndexes()              // what actually exists
  db.coll.aggregate([{$indexStats:{}}])   // what is used
  db.stats().indexSizes             // what each costs

Then triage in four passes, cheapest and safest first:

PassActionRisk
1. Prefix dedupeDrop any index that is a strict prefix of another. Purely mechanicalNone — provably no capability lost
2. TTL auditThree TTLs with different durations is almost certainly a bug: the shortest one wins for any document with all three fields. Verify which field each targets and whether it is a DateLow, but the finding may be "we have been deleting data 6 days early"
3. Wildcard assessmentCheck whether it is scoped (attrs.$**) or global ($**). A global wildcard on a known schema is nearly always a shortcut someone took; measure its size and its $indexStats usageMedium — replacing it needs the query shapes first
4. Hide-then-drop everything else unusedhideIndex() for a full business cycleLow and reversible in milliseconds

The sparse unique index deserves individual attention, because it is both a performance object and a correctness constraint. Two questions: does the application depend on the uniqueness (almost certainly yes, and $indexStats will not tell you — a constraint can have zero query usage and still be load-bearing), and does sparse actually express the intended rule? If documents can store an explicit null, sparse does not exclude them and the constraint is subtly wrong. I would migrate it to a partial index with a $type filter — but as a deliberate change with a duplicate-check first, not as part of a cleanup sweep.

The three TTL indexes are the finding I would escalate first, ahead of any performance work. Nineteen indexes is a cost problem; three overlapping retention rules is a data-loss problem, and it may already have happened. The query that settles it is a count by age bucket against what the retention policy claims. Performance can wait a day; deleted data cannot be un-deleted.

What I would not do: drop anything in the first session. Every index here is load-bearing for someone until proven otherwise, and the reversibility gradient is steep — hiding costs milliseconds to undo, dropping a large index costs a multi-minute rebuild under load. The whole triage should be measurement, then hiding, then a week, then drops.

🎯 Key Takeaways

  • Multikey is not declared, it happens — one array in an indexed field, and each element becomes its own key pointing at the same document.
  • Index size scales with total array elements, not documents. 41 documents with 4,000-element arrays produced 164,000 keys.
  • Range bounds do not compose on an array field. Only one bound is applied — 310,000 keys examined for 12 results — until you use $elemMatch.
  • At most one array field per compound index, and the violation is a write error at runtime, not a create-time one.
  • A multikey index can never support a sort on the array field, and can never cover a query that projects it.
  • A missing field is indexed as null, so unique: true on an optional field rejects the second document that omits it.
  • sparse excludes missing fields; it does not exclude explicit null. Partial indexes replaced it.
  • Partial indexes are the highest-leverage index technique available — 9.2 GB → 140 MB on a 0.6% subset, with the write cost falling proportionally.
  • A partial index is used only when the query predicate implies its filter. The planner reasons about predicates, never about the data.
  • TTL is not prompt — measured 12 minutes late on average, 47 at peak. Never rely on it for security enforcement.
  • A TTL field must be a BSON Date. A date string is silently never expired; one collection reached 340 GB.
  • TTL deletes are ordinary writes: 60M of them produced 9 GB of oplog and 90 s of replication lag. At volume, prefer time-bucketed collections and drop().
  • One text index per collection, and $text does no typo tolerance and no autocomplete — zero results, not poor ones. That is the line where you need a real search engine.
  • GeoJSON is [longitude, latitude], and reversing it produces results that are wrong but plausible.
  • $near consumes the sort; $geoWithin does not. And an equality prefix on a geo index took 18,400 documents examined down to 52.
  • Wildcard indexes are for genuinely dynamic keys only — scoped to a subtree, never global on a schema you control.
  • A collation index requires the query to specify the same collation, or you get case-insensitive writes with case-sensitive reads. Normalising into a lowercase field is usually the better answer.
