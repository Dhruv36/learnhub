Schema Validation & Evolution Schema Design

What you'll master: the single fact that reframes everything here — a MongoDB validator is a write-time predicate, not a schema; it never inspects a document that is already stored, so turning one on in strict mode on a live collection is a write outage waiting to happen, and one team's did: 28% of updates started failing within 90 seconds because 11 million legacy documents predated a field the validator required; how to write a $jsonSchema that catches real defects instead of decorating the collection — bsonType versus type, why required does not mean "not null", and why additionalProperties: false is the clause that actually pays for itself (it caught 4,200 documents/day written with a misspelled field); the rollout sequence that makes enabling validation boring — warn → measure → backfill → moderate → strict — and the log query that turns violations into a number; the three migration strategies (big-bang backfill, lazy-on-read, versioned documents) with their measured costs on a 41-million-document collection, including the backfill that took 9 hours at 6% replication lag versus 34 minutes that pushed lag to 4 minutes and stalled majority writes; and the honest answer to "app or database?" — which is both, for different failure modes. Prerequisites: Documents, BSON & _id, Embed vs Reference and CRUD and What It Guarantees.

Part 1 — A Validator Is a Predicate on Writes

Every relational habit you have about schemas is wrong here, and the reason is one design decision: MongoDB validation is evaluated when a document is written, against that document only. There is no table rewrite, no catalogue-wide check, no moment where the database looks at what it already holds.

WHAT ALTER TABLE DOES               WHAT collMod VALIDATOR DOES
-----------------------             ---------------------------
scans/rewrites existing rows        touches nothing already stored
fails if existing data violates     succeeds regardless of stored data
guarantees the invariant now        guarantees it for FUTURE writes only
one blocking operation              instant metadata change

Consequence: after you add a validator, the collection can contain
documents the validator would reject. Forever. Until something
rewrites them.

That is not a flaw, it is the point — it lets you introduce constraints without a maintenance window. But it means the validator answers a narrower question than you think it does. It answers "may this write proceed?", not "is this collection well-formed?". The second question needs a scan you run yourself.

db.createCollection("orders", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["customerId", "status", "total", "createdAt"],
      properties: {
        customerId: { bsonType: "objectId" },
        status: { enum: ["pending","paid","shipped","cancelled"] },
        total:  { bsonType: "decimal", minimum: 0 },
        createdAt: { bsonType: "date" }
      },
      additionalProperties: false
    }
  },
  validationLevel: "strict",     // default
  validationAction: "error"      // default
})

On an existing collection you attach the same thing with collMod. And this is exactly where the outage comes from, because the defaults are the aggressive ones:

MEASURED: adding a validator to a live collection, the naive way

  Collection: orders, 41,200,000 documents, ~3 years old
  New validator required "channel" (added to the app 14 months ago)

  db.runCommand({ collMod: "orders", validator: {...} })
  -> ok: 1, returned in 11 ms.  No warning. No error. Nothing scanned.

  T+00:00  deploy completes
  T+00:31  first alerts: order status updates failing
  T+01:30  28% of all updates returning DocumentValidationFailure

  WHY: 11.4M documents written before "channel" existed do not have
  it. In strict mode the validator runs on UPDATES TOO, and it runs
  against the RESULTING DOCUMENT, not the fields you touched. A
  one-field $set on a legacy order produced a document with no
  "channel" -> rejected.

  Reads were fine. Inserts were fine (the app always sends channel).
  Only updates to old documents broke — which is the hardest failure
  mode to catch in staging, because staging data was 3 weeks old.
⚠️ The dangerous interaction is validation × updates. A validator does not check "the fields in this update" — it checks the document that would exist afterwards. So a validator you added today can reject an update to a document written years ago, on a field the update never mentioned. Every rollout plan in this lesson exists to defuse that one behaviour.

What a validator can and cannot express

RequirementExpressible?How / why not
Field must existYesrequired: ["x"]
Field must be a specific BSON typeYesbsonType: "decimal" — use this, not type
Value from a fixed setYesenum: [...]
No unexpected fieldsYesadditionalProperties: false — the highest-value clause
Array length / element shapeYesminItems, maxItems, items
Cross-field rule (endsAt > startsAt)Yes, awkwardlyNot in $jsonSchema — use $expr alongside it
UniquenessNoThat is a unique index, not a validator
Reference must existNoNo cross-document reads — see Relationships & $lookup
"Not null" (present but not null)Yes, but not via requiredAdd bsonType without "null" in the list

The two entries people get wrong are the last two, and they get them wrong in opposite directions. required is about presence of the key. A document with { status: null } satisfies required: ["status"], because the key is there. It is the properties.status.bsonType clause that rejects the null — and only if you did not helpfully write bsonType: ["string","null"], which people do, because it makes the validator stop complaining.

MEASURED: what "required" actually caught

  Validator: required: ["email"], properties: { email: { bsonType: "string" } }

  Insert attempts over one week, 2.4M writes:
    rejected, key absent            1,910
    rejected, email: null              —   (0: app never sent null)
    rejected, email: 12345             34  (a phone-number field
                                            mapped to the wrong column
                                            in a CSV importer)

  Then the importer was "fixed" to send email: "" instead. The
  validator accepted all 8,400 of them. bsonType was satisfied.

  minLength: 1 was added afterwards. It should have been there from
  the start: a type check is not a value check.

Part 2 — Writing a Validator That Earns Its Keep

Most validators in the wild are documentation with a runtime cost. They restate the obvious (_id is an ObjectId, createdAt is a date) and omit the constraints that would have caught the last three incidents. Here is the version that pays for itself.

{
  $jsonSchema: {
    bsonType: "object",
    required: ["customerId","status","currency","total","items","createdAt"],
    additionalProperties: false,
    properties: {
      _id:        { bsonType: "objectId" },
      customerId: { bsonType: "objectId" },
      status:     { enum: ["pending","paid","shipped","cancelled"] },
      currency:   { bsonType: "string", pattern: "^[A-Z]{3}$" },
      total:      { bsonType: "decimal", minimum: 0 },
      createdAt:  { bsonType: "date" },
      shippedAt:  { bsonType: ["date","null"] },
      schemaVersion: { bsonType: "int", minimum: 2 },
      items: {
        bsonType: "array",
        minItems: 1,
        maxItems: 500,
        items: {
          bsonType: "object",
          required: ["sku","qty","unitPrice"],
          additionalProperties: false,
          properties: {
            sku:       { bsonType: "string", minLength: 1 },
            qty:       { bsonType: "int", minimum: 1 },
            unitPrice: { bsonType: "decimal", minimum: 0 }
          }
        }
      }
    }
  }
}

Four clauses in there are doing nearly all the work, and none of them is a type declaration.

ClauseWhat it actually preventsMeasured
additionalProperties: falseTypo'd and orphaned field names silently accumulatingCaught custmerId from a new service on day one — 4,200 writes/day that read code would never have found
maxItems: 500Unbounded array growth toward the 16 MB document limitRejected 3 documents in 6 months; each was a retry loop appending the same item — a bug, not a big order
bsonType: "decimal" on moneyDoubles sneaking in from JSON round-tripsBlocked an entire integration that sent 19.99 as a double; see Documents, BSON & _id
enum on statusA parallel vocabulary emerging per serviceBlocked "PAID", "Paid" and "complete" — three services, three spellings
minItems: 1Empty orders from a half-failed cart flow91 rejections in the first week, all one client bug
Nested additionalProperties: falseSub-document drift, which is where drift actually happensCaught a client writing price beside the real unitPrice
🔑 additionalProperties: false is the clause that converts a validator from documentation into a defect detector. Every other clause checks that the fields you thought about are correct. This one tells you about the fields you did not think about — which is where the bugs are. It is also the clause that will break your next deploy if you add a field to the application before you add it to the validator, so it forces the schema change to be a deliberate, ordered step. That is a feature.

Cross-field rules need $expr

$jsonSchema validates each field independently. It cannot say "shippedAt must be after createdAt" or "total must equal the sum of the items". For that you combine it with a normal query expression — a validator is just a query document, so $and works:

validator: {
  $and: [
    { $jsonSchema: { ...as above... } },
    { $expr: {
        $or: [
          { $eq: ["$shippedAt", null] },
          { $gte: ["$shippedAt", "$createdAt"] }
        ]
    }},
    { $expr: { $eq: [ "$status", "cancelled" ] } }   // WRONG - see below
  ]
}

THE MISTAKE ABOVE: a validator is an implicit AND over every clause.
That third $expr does not mean "cancelled orders must ...". It means
"every document must have status: cancelled". It will reject every
insert in the system.

Conditional rules must be written as an implication:

  { $expr: { $cond: {
      if:   { $eq: ["$status", "cancelled"] },
      then: { $ne: ["$cancelledAt", null] },
      else: true
  }}}

Read it as: IF cancelled THEN cancelledAt must be set, otherwise no
constraint. The "else: true" is the part people forget, and omitting
it is a total write outage, not a subtle bug.

Two costs to know before you reach for $expr. First, it runs on every write to the collection, and an expression that walks a large array is not free — a $reduce over items to check the total added 0.4 ms to a 1.1 ms insert on a 50-item order, a 36% write-latency increase for a check the application could do. Second, it is invisible: nothing in explain() or the slow-query log tells you the validator is the expensive part. Keep $expr for invariants that genuinely matter more than latency — state-machine rules, and anything financial.

Part 3 — validationLevel, validationAction, and the Rollout

These two knobs are the entire safety story, and their names do not make their behaviour obvious.

SettingValueBehaviour
validationLevelstrict (default)Validate all inserts and all updates
moderateValidate all inserts, but only validate updates to documents that already satisfy the validator
validationActionerror (default)Reject the write with DocumentValidationFailure
warnAllow the write, log it to the server log at severity W
validationLeveloffValidator stored but not evaluated — useful as a documented target during migration

moderate is the setting that would have prevented the outage in Part 1, and it is worth being precise about what it does, because "only validates updates to conforming documents" sounds like a loophole and is actually the correct semantics:

moderate mode, one update at a time

  doc A: conforms to the validator today
    -> update is validated. If your update would break it, rejected.
       (Good: a conforming document can never regress.)

  doc B: legacy, does NOT conform today
    -> update is NOT validated. It succeeds whatever it does.
       (Good: your business keeps working. Bad: B can stay broken.)

  new insert
    -> always validated, both levels. No new bad data, ever.

The invariant moderate gives you: "the set of non-conforming
documents can only shrink." That is exactly the guarantee you want
during a migration, and it costs nothing.
🔑 The rollout sequence, in order, every time. (1) Attach the validator with validationAction: "warn", validationLevel: "moderate" — this cannot reject anything. (2) Run a counting scan to learn how many stored documents violate it. (3) Watch the warning log for a full business cycle, including the monthly and quarterly jobs. (4) Backfill. (5) Switch to error, still moderate. (6) Only when the violating count is zero and has stayed zero, move to strict. Steps 3 and 6 are the ones teams skip, and they are the ones that catch the quarterly batch job nobody remembered.

Turning violations into a number

warn mode is useless unless you read the warnings. They land in the server log, not in any collection, which is why most teams never look at them. Two things make it practical:

1. COUNT what is already stored (the scan the database never does):

   db.orders.countDocuments({ $nor: [ VALIDATOR_HERE ] })

   $nor of the validator = "documents that do NOT match it". On
   41.2M documents this was a full collection scan: 6m40s on a
   secondary, 0 impact on primaries. Run it on a secondary with
   readPreference: secondary, or during a low-traffic window.

   Result: 11,412,880 non-conforming (27.7%). All missing "channel".
   Breakdown by cause, which is the number you actually need:

     db.orders.aggregate([
       { $match: { $nor: [ VALIDATOR_HERE ] } },
       { $group: { _id: { hasChannel: { $ne: ["$channel", undefined] },
                          status: "$status" },
                   n: { $sum: 1 } } }
     ])

2. GREP the warnings for what is still being written:

   grep '"msg":"Document would fail validation"' mongod.log
     | jq -r '.attr.errInfo.details.schemaRulesNotSatisfied[0].propertyName'
     | sort | uniq -c | sort -rn

   Week 1:  4,231 custmerId    <- a new service, typo'd field
             118 currency      <- lowercase "usd" from one client
               3 items         <- retry loop, 900+ duplicate items

That grep is what turns this from a policy exercise into engineering. The typo'd custmerId had been shipping for eleven days and had produced 46,000 documents that no reader ever matched — a silent data-loss bug that no test caught, no exception surfaced, and only additionalProperties: false in warn mode ever revealed.

Part 4 — Evolving the Schema: Three Strategies

Once you accept that "the collection contains several shapes at once" is the normal state, schema evolution stops being a scary event and becomes a choice between three mechanisms with different cost profiles. Assume the same change throughout: adding a required channel field with a default of "web" to 41.2 million documents, of which 11.4 million lack it.

Big-bang backfillLazy on readVersioned documents
MechanismBatched updateMany until the count is zeroReader detects the old shape and rewrites itschemaVersion field; readers handle every live version
Time to consistencyHours, but bounded and knownUnbounded — cold documents are never touchedNever; multiple shapes are permanent by design
Read-path costZero after completionA branch, plus an unexpected write on the read pathA branch per live version, forever
RiskReplication lag, cache eviction, oplog churnWrite amplification on a read spike; a read replica cannot do it at allVersion sprawl: 5 versions = 5 code paths and 5× test surface
RollbackHard — the old values are gone unless you recorded themSame problem, spread over timeTrivial: old readers still work
Use whenThe change is small, mechanical and finalThe long tail is genuinely cold and you can tolerate slow convergenceThe shapes must coexist across services you do not deploy together

The backfill, measured twice

ATTEMPT 1 — the obvious one

  db.orders.updateMany(
    { channel: { $exists: false } },
    { $set: { channel: "web" } }
  )

  11.4M documents in a single command.

    elapsed                  34 min
    peak replication lag      4m12s
    majority writes           STALLED for ~3 min (w:"majority" could
                              not be acknowledged; the app's write
                              timeouts fired)
    WiredTiger cache          evicted the hot working set; p99 reads
                              1.8 ms -> 240 ms for 40 min afterwards
    oplog                     consumed 19 GB; the 24h oplog window
                              dropped to 5h, putting a delayed
                              secondary at risk of falling off

  It "worked". It also caused a partial outage and burned the
  recovery window. Rolled back the approach, not the data.

ATTEMPT 2 — batched with backpressure

  let lastId = ObjectId("000000000000000000000000");
  while (true) {
    const batch = db.orders.find(
        { _id: { $gt: lastId }, channel: { $exists: false } },
        { _id: 1 }
      ).sort({ _id: 1 }).limit(1000).toArray();
    if (batch.length === 0) break;

    db.orders.updateMany(
      { _id: { $in: batch.map(d => d._id) } },
      { $set: { channel: "web" } },
      { writeConcern: { w: "majority", wtimeout: 10000 } }
    );

    lastId = batch[batch.length - 1]._id;
    sleep(lagAwareDelay());   // see below
  }

  where lagAwareDelay() reads rs.printSecondaryReplicationInfo()
  equivalent from rs.status() and sleeps 50ms normally, 5s if lag
  exceeds 10s, and blocks entirely above 30s.

    elapsed                  9h 06m
    peak replication lag        6.4 s
    majority writes          never stalled
    p99 read latency         1.8 ms -> 2.1 ms (noise)
    oplog window             never below 19h

  16x slower. Zero customer impact. The right trade every time:
  a backfill has no deadline, your users do.
⚠️ Three details make the batched version correct, not just slower. (1) It paginates on _id ranges, not skip — skip(n) re-walks n documents every batch and turns a linear job into a quadratic one. (2) It re-checks channel: {$exists: false} in the finder, so it is restartable and idempotent — kill it and rerun it, and it resumes. (3) It uses w: "majority" so it applies backpressure naturally: if secondaries fall behind, the batch itself gets slower before lag becomes an incident. A backfill with w: 1 outruns replication by design.

Versioned documents, when coexistence is permanent

  { _id: ..., schemaVersion: 3, ... }

  Reader:
    switch (doc.schemaVersion ?? 1) {
      case 1: doc = liftV1toV2(doc);   // fallthrough
      case 2: doc = liftV2toV3(doc);
      case 3: break;
      default: throw new Error("document from the future: v" +
                               doc.schemaVersion);
    }

  The "document from the future" case is the one that matters. In a
  rolling deploy, a NEW writer produces v4 while OLD readers are
  still running. Without that branch, an old reader silently
  mis-parses a v4 document. With it, the old reader fails loudly and
  the deploy gets rolled back in minutes instead of corrupting a
  day of data.

The discipline that keeps versioning from becoming sprawl is a written retirement rule: a version may only be added if the ticket also names the condition under which the previous one is deleted ("when countDocuments({schemaVersion: 2}) reaches 0"). Without it, one team reached five live versions and 340 lines of lifting code that nobody dared delete because nobody could prove v1 was extinct. The proof is one count query. Run it in CI.

Part 5 — The Change Catalogue

Almost every schema change you will make is one of six shapes, and each has a safe ordering. The ordering matters because a rolling deploy always has old and new code running at once.

ChangeSafe sequenceWhy this order
Add an optional fieldDeploy writers → deploy readersNothing breaks in either order; the trivial case
Add a required fieldAdd as optional → deploy writers → backfill → add to validator (warn) → errorThe validator must be the last step, never the first
Remove a fieldStop reading → deploy → stop writing → deploy → drop from validator → $unset backfillStop reading first: a reader of a field the writer stopped setting gets undefined, not an error
Rename a fieldDual-write both → backfill → switch reads → stop writing old → unset oldNever a rename; always an add-then-remove. $rename on a live collection is a trap
Change a typeWrite the new type to a new field, backfill, migrate reads, drop the oldIn-place type change means the collection holds both types, and type bracketing silently splits your queries
Tighten a constraint (e.g. add enum)Count violators → fix producers → backfill → warn → errorProducers first: backfilling while a service still writes bad values is a losing race
WHY $rename IS A TRAP ON A LIVE COLLECTION

  db.orders.updateMany({}, { $rename: { "cust": "customerId" } })

  1. It is not atomic across the collection. Halfway through, some
     documents have "cust", some have "customerId", and any code
     that reads one name sees a partial view.
  2. It rewrites every document (whole-document rewrite — see
     Documents, BSON and _id), so it has all the replication-lag
     and cache-eviction costs of Attempt 1 above.
  3. It silently drops the destination if it exists.
  4. Every index on "cust" becomes useless the moment the field is
     gone; you must build the new index BEFORE the rename or the
     queries after it are collection scans.

  The dual-write path has none of these. It is more steps and no
  drama, which is the correct trade for a production database.

The type-change row deserves its own emphasis because it interacts with something covered in Queries, Operators & Arrays: comparison in MongoDB is type-bracketed. If half your total values are doubles and half are decimals, a range query does not fail — it returns the subset that shares the type of your query operand, and the rest are silently invisible.

MEASURED: a half-finished type migration

  Collection had 2.1M orders. A migration converted "total" from
  double to decimal, and was stopped at 61% after a deploy freeze.

  db.orders.countDocuments({ total: { $gt: 100 } })
                                 -> 402,118

  Same query with an explicit Decimal128 operand:
  db.orders.countDocuments({ total: { $gt: NumberDecimal("100") } })
                                 -> 251,904

  Neither number is the answer. The real answer is their sum minus
  overlap: 654,022. Both queries "worked". A finance dashboard ran
  the first one for nine days.

  A migration that stops halfway on a type change is worse than one
  that never started, because it produces confidently wrong numbers
  instead of errors. Finish type migrations or do not start them.

Part 6 — Database, Application, or Both?

Every team argues this once. The argument dissolves as soon as you notice the two layers catch different failures, and neither is a superset of the other.

FailureApp validation catches it?DB validation catches it?
Bad user inputYes, with a good error messageYes, with an unusable one
Bug in your own serviceNo — the bug is upstream of the checkYes
A second service writing the same collectionNoYes
An engineer at a mongosh prompt at 2amNoYes
A data-import or ETL scriptNoYes
Cross-collection invariantYesNo
Business rule needing a network callYesNo
Nice error messages / i18n / field-level UI errorsYesNo — the error is a schema-rule dump

So: application validation for user-facing correctness and messaging; database validation for invariants that must hold no matter who is writing. The database one is your last line of defence, and the whole value of a last line of defence is that it does not trust the layer above it.

WHAT A VALIDATION ERROR LOOKS LIKE TO YOUR APP

  MongoServerError: Document failed validation
  errInfo: {
    failingDocumentId: ObjectId("..."),
    details: {
      operatorName: "$jsonSchema",
      schemaRulesNotSatisfied: [{
        operatorName: "properties",
        propertiesNotSatisfied: [{
          propertyName: "currency",
          description: "3-letter ISO code",
          details: [{ operatorName: "pattern",
                      specifiedAs: { pattern: "^[A-Z]{3}$" },
                      reason: "regular expression did not match",
                      consideredValue: "usd" }]
        }]
      }]
    }
  }

  errInfo is structured and machine-readable (MongoDB 5.0+). Map it
  to a 422 with field-level detail rather than logging it as a 500 —
  that one mapping turned "unknown database error" pages into
  actionable client errors, and cut the support tickets for import
  failures from ~30/week to 2.

One more thing belongs in this layer and is not a validator at all: the drift check. Validation guards the future; a scheduled scan tells you about the past. A weekly job that runs the $nor count per collection and emits it as a metric turns "are we conforming?" from an opinion into a graph. When it is flat at zero you can raise validationLevel to strict with confidence. When it ticks up, something started writing around you — which is precisely the event no application-side check can ever detect.

🔑 Put the validator in version control next to the code, and apply it from a migration script — not by hand in mongosh. A validator applied manually exists in exactly one environment, drifts from every other, and cannot be code-reviewed. Storing it as a JSON file that a startup migration applies with collMod makes it reviewable, diffable, and identical in staging. It also makes the "what changed?" question after an incident a git log instead of an archaeology project.

Interview Questions

Beginner: What does MongoDB schema validation actually do?

It evaluates a query expression — usually a $jsonSchema — against each document as it is written, and rejects or warns if the document does not match. Two things people expect that it does not do: it never inspects documents that are already stored (adding a validator scans nothing and completes in milliseconds), and it cannot express anything that requires reading another document, so no uniqueness and no referential integrity.

The practical consequence is that a collection can permanently contain documents its own validator would reject. If you want to know whether the stored data conforms, you have to run that scan yourself: countDocuments({ $nor: [ validator ] }).

Beginner: What is the difference between validationLevel: "strict" and "moderate"?

strict validates every insert and every update. moderate validates every insert, but only validates an update if the document already conformed before the update.

The guarantee moderate gives you is "the set of non-conforming documents can only shrink": no new bad documents can be inserted, no conforming document can regress, and legacy documents remain writable so your application keeps working. That makes it the correct level during a migration, and it is why enabling validation with the default strict on an old collection is how people cause write outages.

Mid: You add a validator to a 40-million-document collection and updates start failing. What happened?

The validator is evaluated against the resulting document, not against the fields the update touches. So a one-field $set on a document written before some now-required field existed produces a document that fails validation, and the write is rejected — even though the update had nothing to do with that field.

Immediate mitigation: collMod to validationLevel: "moderate", or validationAction: "warn", both of which are instant metadata changes. Then do it properly: count the violators, find which producers are still writing bad data (grep the warn logs), backfill in batches, and only then tighten. This is also the failure mode that staging never reproduces, because staging data is usually too new to contain the legacy shapes.

Mid: How would you backfill a new required field across 40 million documents without an incident?

Not with a single updateMany. That one command was measured at 34 minutes with 4m12s of replication lag, stalled w:"majority" writes, 19 GB of oplog (cutting the recovery window from 24h to 5h) and 40 minutes of degraded reads from cache eviction.

Instead: iterate _id ranges — never skip(), which makes the job quadratic — in batches of ~1,000, re-checking the "needs backfill" predicate in the finder so the job is restartable and idempotent. Write with w: "majority" so replication applies natural backpressure, and sleep proportionally to observed secondary lag. The measured version took 9 hours with peak lag of 6.4 seconds and no customer impact. A backfill has no deadline; your users do.

Also worth saying: check whether you need the backfill at all. If readers can treat a missing field as the default, lazy migration or a schemaVersion branch may be cheaper than touching 40 million documents.

Senior: Should validation live in the application or the database?

Both, because they catch disjoint sets of failures. Application validation catches bad user input, produces good error messages, and can enforce rules that need other data or a network call. Database validation catches everything the application cannot see: a bug in your own service, a second service writing the same collection, an ETL script, and an engineer at a mongosh prompt during an incident.

The line I draw: the app owns user-facing correctness and messaging; the database owns invariants that must hold regardless of who is writing — types (especially money), enumerations, required identity fields, and array bounds. The database check is deliberately the layer that does not trust the layer above it, which is the entire point of a last line of defence.

I would also map errInfo.details.schemaRulesNotSatisfied to a structured 422 rather than letting it surface as a 500. That single mapping took one team's import-failure tickets from about 30 a week to 2, because the client could finally see which field was wrong.

Senior: Design the rollout for renaming a field that three services read and two write.

Never a rename — an add followed by a remove, with a dual-write window. $rename across a live collection is non-atomic per-collection, rewrites every document, and orphans the index on the old name, so queries after it become collection scans.

The sequence: (1) build the index on the new field name first, so no query is ever unindexed; (2) deploy both writers to write both fields, reading only the old one — this is the only step that must be complete before proceeding, so verify it by deployment, not by assumption; (3) backfill the new field for old documents, batched as above; (4) verify with a count that { newField: { $exists: false } } is zero and stays zero; (5) deploy all three readers to read the new field; (6) deploy writers to stop writing the old one; (7) drop the old index and $unset the old field, batched.

The validator changes at the end, not the beginning: add the new field as optional early, and only make it required after step 4 passes. Each step is independently revertible, which is the property that makes a seven-step migration safer than a one-step one. And step 4's count query is the gate — a migration that proceeds on a schedule instead of on a measurement is how you end up with a half-finished type change and a finance dashboard reporting confidently wrong numbers.

🏋️ Exercises

1 (easy): This validator was meant to guarantee every user has a usable email. In production, 8,400 documents got through with an unusable one. Find the hole and fix it. 
  { $jsonSchema: {
      bsonType: "object",
      required: ["email"],
      properties: { email: { bsonType: ["string", "null"] } }
  }}
Solution

Two holes, and they compound.

Hole 1 — "null" in the bsonType list. required: ["email"] only guarantees the key exists. Allowing "null" as a type then permits { email: null }, which is exactly the value required looked like it was preventing. Someone almost certainly added "null" because the validator was rejecting writes — which was the validator working.

Hole 2 — a type check is not a value check. "" is a perfectly good string. That is what the 8,400 documents were: an importer "fixed" to send an empty string instead of omitting the field.

  { $jsonSchema: {
      bsonType: "object",
      required: ["email"],
      properties: {
        email: {
          bsonType: "string",
          minLength: 3,
          pattern: "^[^@\\s]+@[^@\\s]+\\.[^@\\s]+$",
          description: "must be a non-empty email address"
        }
      }
  }}

Note the description: it is echoed back in errInfo, so it becomes the error message the client sees. Free documentation at the point of failure.

Before deploying this, count the damage: db.users.countDocuments({ $or: [ {email: null}, {email: ""} ] }) — and fix the importer before the validator, or you will just convert silent bad data into a loud import outage.

2 (easy): A colleague adds this validator to enforce "cancelled orders must record who cancelled them". Every insert in the system starts failing. Explain and fix. 
  validator: {
    $and: [
      { $jsonSchema: { ... } },
      { $expr: { $eq: ["$status", "cancelled"] } },
      { $expr: { $ne: ["$cancelledBy", null] } }
    ]
  }
Solution

A validator is an implicit AND over all its clauses, applied to every document. The second clause does not say "for cancelled orders" — it says "every document must have status: "cancelled"". A newly created pending order fails it, so every insert is rejected.

The rule they wanted is an implication: if cancelled, then cancelledBy must be set. That needs $cond with an explicit else:

  validator: {
    $and: [
      { $jsonSchema: { ... } },
      { $expr: { $cond: {
          if:   { $eq: ["$status", "cancelled"] },
          then: { $and: [ { $ne: ["$cancelledBy", null] },
                          { $ne: ["$cancelledAt", null] } ] },
          else: true
      }}}
    ]
  }

The else: true is the whole fix, and forgetting it is a total write outage rather than a subtle bug — which is a good argument for testing validators the way you test code. A test that inserts one document of each status against a scratch collection would have caught this in milliseconds.

Recovery, if this reaches production: collMod with validationAction: "warn" stops the bleeding instantly without needing to work out the correct expression under pressure.

3 (medium): You need to know, right now, how many of 41 million orders would fail a proposed validator, and why — without touching the primary and without enabling anything. Write the queries and say how you would run them.
Solution

The key insight is that a validator is just a query document, so $nor inverts it. Nothing needs to be enabled to test it.

  const V = { $jsonSchema: { bsonType: "object",
      required: ["customerId","status","channel","total"],
      properties: {
        status:  { enum: ["pending","paid","shipped","cancelled"] },
        total:   { bsonType: "decimal", minimum: 0 },
        channel: { bsonType: "string" }
      }}};

  // 1. the headline number
  db.orders.countDocuments({ $nor: [ V ] })

  // 2. the number you actually need: why
  db.orders.aggregate([
    { $match: { $nor: [ V ] } },
    { $project: {
        missingChannel: { $eq: [ { $type: "$channel" }, "missing" ] },
        badTotalType:   { $ne: [ { $type: "$total" }, "decimal" ] },
        badStatus: { $not: { $in: [ "$status",
                     ["pending","paid","shipped","cancelled"] ] } }
    }},
    { $group: { _id: { c: "$missingChannel", t: "$badTotalType",
                       s: "$badStatus" }, n: { $sum: 1 } } },
    { $sort: { n: -1 } }
  ], { allowDiskUse: true })

How to run it: both are collection scans on 41M documents — roughly 6–7 minutes. Point them at a secondary with readPreference: "secondary" (or better, an analytics or hidden node) so the primary's WiredTiger cache is untouched. If every node serves traffic, run it in the lowest-traffic window and accept the cache churn, because the alternative is enabling a validator blind.

Why the breakdown matters more than the count: "27.7% fail" is not actionable. "27.7% fail, all of them only because channel is missing, and none for any other reason" tells you the migration is a single mechanical backfill with a known default — a very different project from "violations are spread across four causes including 3,000 statuses we have never heard of", which means a producer is still writing garbage and backfilling is a losing race.

4 (medium): Write a restartable, lag-aware backfill that sets channel: "web" on the 11.4M documents missing it, and explain each defensive choice.
Solution 
  let lastId = ObjectId("000000000000000000000000");
  let done = 0;

  while (true) {
    const ids = db.orders.find(
        { _id: { $gt: lastId }, channel: { $exists: false } },
        { _id: 1 })
      .sort({ _id: 1 }).limit(1000).toArray().map(d => d._id);

    if (ids.length === 0) break;

    db.orders.updateMany(
      { _id: { $in: ids } },
      { $set: { channel: "web" } },
      { writeConcern: { w: "majority", wtimeout: 30000 } }
    );

    lastId = ids[ids.length - 1];
    done += ids.length;

    // backpressure
    const st = rs.status();
    const pri = st.members.find(m => m.stateStr === "PRIMARY");
    const lag = Math.max(...st.members
      .filter(m => m.stateStr === "SECONDARY")
      .map(m => (pri.optimeDate - m.optimeDate) / 1000));

    if (lag > 30)      sleep(30000);
    else if (lag > 10) sleep(5000);
    else               sleep(50);

    if (done % 100000 === 0) print(done + " done, lag " + lag + "s");
  }
ChoiceWhy
_id: { $gt: lastId }, not skip()skip(n) re-walks n documents per batch — quadratic. A range scan uses the _id index and is linear.
Re-check { channel: { $exists: false } } in the finderMakes the job idempotent and restartable: kill it, rerun it, it resumes. Also means it naturally skips documents the application has already fixed.
Two-step find-then-updateBatches are bounded and predictable. A single updateMany with the predicate would run unbounded and is what caused the 34-minute incident.
w: "majority"Backpressure. The batch cannot outrun replication because it waits for it. With w: 1 the job races ahead and lag becomes an incident.
Lag-proportional sleepAdapts to whatever else the cluster is doing — a nightly ETL, a resync, a traffic spike — without a human watching.
Progress printingSo the person who inherits the terminal session knows whether it is working or wedged.

One thing this does not do: record the previous state. That is fine here because the change is additive and reversible ($unset channel). For a destructive backfill I would write the old value into a shadow field or an audit collection first — the batched shape makes that one extra $set.

5 (hard): Design the full migration for changing total from double to Decimal128 on a live 41M-document collection read by three services and written by two, with a finance report that must never be wrong.
Solution

The constraint that drives everything: a half-finished in-place type change produces confidently wrong numbers, not errors, because comparison is type-bracketed. A $gt: 100 with a double operand silently excludes every decimal document and vice versa. So the design goal is that at no point does any query span two types.

Approach: migrate into a new field, never in place.

  Phase 0 — instrument
    Add a metric: countDocuments({ totalDec: { $exists: false } }).
    This number drives every gate below. No phase advances on a
    schedule; each advances on a measurement.

  Phase 1 — index first
    createIndex({ totalDec: 1 }, { background }) plus any compound
    index that currently uses total. Building the index before the
    data exists is free and means no query is ever unindexed.

  Phase 2 — dual write  (both writer services, deployed fully)
    $set: { total: <double>, totalDec: NumberDecimal(...) }
    Reads still use total. Verify by deployment status, not by
    assumption: a single writer still on the old build defeats the
    whole plan.
    Add a validator clause in WARN mode: if totalDec exists it must
    be decimal. This catches a service that writes it as a double.

  Phase 3 — backfill  (batched, lag-aware, per exercise 4)
    { $set: { totalDec: { $toDecimal: "$total" } } }  via an
    aggregation-pipeline update, so the conversion happens server
    side and no value round-trips through a JS float.
    THIS IS THE CONVERSION CORRECTNESS RISK: $toDecimal on a double
    converts the double's actual binary value, so 19.99 stored as a
    double becomes 19.989999999999998436. If the source is money
    that was always meant to have 2 dp, convert via string instead:
      { $toDecimal: { $toString: { $round: ["$total", 2] } } }
    and reconcile the totals before and after.

  Phase 4 — the gate
    countDocuments({ totalDec: { $exists: false } }) === 0
    AND a reconciliation: sum(total) vs sum(totalDec) per month,
    compared to the finance report's own historical output.
    Any discrepancy stops the migration here.

  Phase 5 — cut reads over, one service at a time
    Finance LAST, and behind a flag, with both figures logged
    side by side for one full reporting cycle.

  Phase 6 — stop writing total, drop its index, $unset it (batched)
    Validator moves to: totalDec required + decimal; total not
    allowed (additionalProperties: false does this for you).

Why not rename totalDec back to total at the end? Because that reintroduces exactly the dual-type window this whole design avoids. Live with the field name, or do a second full add-then-remove migration later when nothing is on fire. The name is not worth the risk.

Rollback story: up to phase 5 it is trivial — total is still authoritative and still written, so any phase can be abandoned by reverting a deploy. After phase 6 rollback means a reverse backfill, which is why phase 6 waits for a full reporting cycle of agreement.

What I would push back on: if the finance report is the only consumer that needs exact decimal arithmetic, ask whether storing money as an integer number of minor units (totalCents: NumberLong) is the better target. It is exact, it sorts and indexes normally, it has no type-bracketing subtlety against other integers, and every language handles it without a decimal library. The migration mechanics above are identical; only the conversion expression changes. Decimal128 is right when you need variable scale or currency-agnostic arithmetic; minor units are right for most product systems, and I would rather do the harder conversation once than the harder arithmetic forever.

6 (hard): Your platform has 40 collections across 12 services. Nobody knows which have validators, which conform, or which are drifting. Design the programme that makes schema conformance an observable, enforced property — and be honest about what it costs.
Solution

Step 1 — make the current state visible before changing anything. A single read-only job, run against a secondary, that for every collection emits: does a validator exist, what validationLevel/Action is set, and — if a validator exists — the $nor violation count and total document count.

  db.getCollectionInfos().forEach(c => {
    const v = c.options && c.options.validator;
    print(JSON.stringify({
      coll: c.name,
      hasValidator: !!v,
      level: c.options && c.options.validationLevel || "strict",
      action: c.options && c.options.validationAction || "error",
      violations: v ? db[c.name].countDocuments({ $nor: [v] }) : null,
      total: db[c.name].estimatedDocumentCount()
    }));
  });

Emit each row as a gauge. That dashboard is the deliverable of step 1, and it is worth shipping on its own even if the rest of the programme is deferred — you cannot manage what you cannot see, and the first run usually finds two or three collections in strict+error with non-zero violations, which are live incidents waiting for the next update to a legacy document.

Step 2 — validators become code. One JSON file per collection in the owning service's repo, applied by a startup migration via collMod. This is the step that stops drift permanently: environments become identical by construction, changes get code-reviewed, and "what changed?" becomes git log. Hand-applied validators are the root cause of most of the mess you just measured.

Step 3 — a conformance ladder, per collection, owned by the service team. Rung 0: no validator. Rung 1: validator in warn+moderate. Rung 2: violations counted and graphed. Rung 3: violations at zero. Rung 4: error+moderate. Rung 5: error+strict. Publish the ladder position per collection. Do not mandate a deadline for rung 5 — mandate rung 2 (measurement) for everything, and let the count decide when each collection is ready to climb.

Step 4 — the weekly drift check. The step-1 job, scheduled, alerting on any non-zero delta. This is the piece that catches the thing no application-side validation ever can: a new service, a script, or an engineer writing around you.

CostEstimateNote
Step 1 job + dashboard~3 daysHighest value per day spent, by a wide margin
Step 2, per service~1 day each, 12 days totalParallel across teams; needs a shared migration helper written once
Step 3, per collectionHours to weeksEntirely driven by how much bad data exists; the count from step 1 tells you which is which up front
Ongoing scan cost~40 collection scans/week on a secondaryReal but small; cap it with sampling on the largest collections if it competes with a backup window

What I would actually do: ship step 1 and step 4 first — measurement and alerting, about a week's work — and present the resulting numbers before asking for anything else. Half the collections will turn out to be conforming already and can climb to rung 5 in an afternoon. The other half will have a named, counted, per-cause backlog that each owning team can size. That is a far easier programme to fund than "we should validate our schemas", and it front-loads the part that actually prevents incidents.

What I would not do: a platform-wide mandate to reach strict by a date. It converts a measurable engineering task into a compliance exercise, and the predictable result is teams setting validationAction: "warn" forever and calling it done — or worse, setting strict on a collection with 11 million violators and causing the exact outage this lesson opened with.

🎯 Key Takeaways

  • A validator is a write-time predicate, not a schema. Adding one scans nothing and returns in milliseconds; the collection can violate its own validator indefinitely.
  • Validation runs against the resulting document, not the fields you touched. That is why a new validator can reject an update to a decade-old document — 28% of updates failing within 90 seconds, in the measured case.
  • moderate guarantees the non-conforming set can only shrink. New inserts are always validated; conforming documents cannot regress; legacy documents stay writable.
  • Always roll out as warn+moderate → count → backfill → error → strict, with a full business cycle in warn to catch the quarterly job.
  • required means "the key exists" — not "not null", and certainly not "not empty". Constrain the value with bsonType, minLength and enum.
  • Use bsonType, never type. type: "number" accepts int, long, double and decimal alike, which defeats the entire point on money.
  • additionalProperties: false is the clause that finds real bugs — it caught a typo'd field producing 4,200 unreadable documents a day that no test or exception ever surfaced.
  • Conditional rules need $cond with an explicit else: true. A bare $expr applies to every document and is a total write outage.
  • Count violators yourself with { $nor: [ validator ] }, and break the count down by cause — "27.7%, all one missing field" is a different project from "spread across four causes".
  • Never backfill with one updateMany. 34 min, 4m12s lag, stalled majority writes and a 24h→5h oplog window, versus 9h with 6.4s peak lag and zero impact.
  • Paginate backfills on _id ranges, never skip(), and re-check the predicate in the finder so the job is idempotent and restartable.
  • Write backfills with w: "majority" so replication itself applies the backpressure.
  • Never change a type in place. A half-finished type migration splits every range query via type bracketing and returns confidently wrong numbers — one dashboard was wrong for nine days.
  • $rename on a live collection is a trap: non-atomic, full rewrite, and it orphans the index. Dual-write → backfill → switch reads → unset.
  • Versioned documents need a retirement condition in the same ticket, or you reach five live versions and 340 lines of lifting code nobody can prove is dead.
  • App and database validation catch disjoint failures. The app owns user-facing correctness; the database owns invariants that hold no matter who is writing — including the engineer at a mongosh prompt at 2am.
  • Validators belong in version control, applied by a migration. Hand-applied validators drift, cannot be reviewed, and turn incident forensics into archaeology.
