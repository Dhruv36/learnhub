Transactions Distribution

What you'll master: the question that comes before the API — whether you need a transaction at all, because a single-document write is already atomic and most transactions in MongoDB codebases exist to compensate for a schema modelled as if it were relational; the correct way to use one, which is never a bare startTransaction/commit pair but withTransaction, whose retry loop handles two different error classes that hand-written code almost always gets wrong; what a transaction actually guarantees — snapshot isolation, all-or-nothing commit, and the specific anomaly it does not prevent (write skew, where two concurrent transfers each verified a sufficient balance and together overdrew the account); the costs, measured — a single-document update at 0.9 ms became 4.8 ms inside a transaction, the 60-second default limit, the 16 MB oplog entry that caps how much one transaction can change, and the cache pressure a long-running snapshot creates for every other query; the error handling that decides whether your system is correct under failure — TransientTransactionError versus UnknownTransactionCommitResult, which means the transaction may well have committed; why a distributed transaction across shards cost 31 ms versus 2 ms single-shard and what that does to a hot path; and the alternatives that are usually better — document redesign, the outbox pattern, and compensating actions. Prerequisites: CRUD and What It Guarantees, Embed vs Reference and Replica Sets & Read Concerns.

Part 1 — First, Do You Need One?

MongoDB has had atomicity since the beginning: a write to a single document is atomic, however many fields, arrays and nested subdocuments it touches. Transactions extend that guarantee across documents and collections. The design question is therefore whether your invariant genuinely spans documents, or whether it spans documents only because of how you modelled the data.

  THE SINGLE-DOCUMENT VERSION OF "CHECK THEN WRITE"

  // NOT atomic across two statements -- a classic race
  const acct = await accounts.findOne({ _id: id });
  if (acct.balance >= amount)
    await accounts.updateOne({ _id: id },
      { $inc: { balance: -amount } });

  // Atomic. The condition is part of the write.
  const r = await accounts.updateOne(
    { _id: id, balance: { $gte: amount } },
    { $inc: { balance: -amount } });
  if (r.matchedCount === 0) throw new InsufficientFunds();

  This is compare-and-swap, it is atomic on one document, and it
  needs no transaction. A great many "we need transactions"
  conversations end here.
🔑 A transaction on every write is a sign the schema is modelled like a relational one. That is a legitimate finding, not a criticism — but the fix is usually the document model, not the transaction API. Before adding one, ask: could these documents be one document? Could the condition be folded into the update filter? Could the second write be derived later by a reconciler? Transactions are a real and correct tool; they are the third answer, not the first.

Part 2 — The Only Correct Way to Write One

  const session = client.startSession();
  try {
    await session.withTransaction(async () => {
      await accounts.updateOne(
        { _id: from, balance: { $gte: amount } },
        { $inc: { balance: -amount } }, { session });

      await accounts.updateOne(
        { _id: to },
        { $inc: { balance: amount } }, { session });

      await ledger.insertOne(
        { from, to, amount, at: new Date() }, { session });
    }, {
      readConcern:    { level: "snapshot" },
      writeConcern:   { w: "majority" },
      readPreference: "primary"
    });
  } finally {
    await session.endSession();
  }
DetailWhy it is not optional
withTransaction, not manual begin/commitIt retries the whole callback on TransientTransactionError and retries the commit on UnknownTransactionCommitResult. Those are different failures with different remedies, and hand-written loops normally handle at most one
{ session } on every operationAn operation without it runs outside the transaction. It commits immediately and is not rolled back — the most common transaction bug, and it is silent
The callback must be idempotentIt can be re-executed several times. Anything with an external side effect (an email, a payment API call, a counter in Redis) must not be inside it
endSession() in finallyA leaked session holds a server-side snapshot open, which pins cache

  THE SILENT BUG, in full

  await session.withTransaction(async () => {
    await accounts.updateOne(f1, u1, { session });   // in
    await accounts.updateOne(f2, u2);                // OUT -- no session
    await ledger.insertOne(entry, { session });      // in
  });

  The middle write is a normal, immediately-committed operation.
  If the transaction aborts, writes 1 and 3 are undone and write 2
  REMAINS. No error is raised at any point.

  MEASURED: this shipped in a payment reconciliation job. Aborts
  were rare (0.3% write conflicts), so it produced roughly 40
  half-applied records per million, discovered five weeks later
  during an audit.

  Defence: a lint rule, or a repository wrapper that takes the
  session in its constructor so no call site can omit it.

⚠️ Transaction duration is a shared resource, not a private one. The cost of a long-running transaction is paid mostly by other queries, because an open snapshot prevents WiredTiger from evicting the page versions it might need. This is why "we raised transactionLifetimeLimitSeconds so the job would finish" is nearly always the wrong response to a timeout: it converts a failed job into a degraded cluster. Keep transactions short — ideally single-digit milliseconds — and never put a network call, a user interaction, or a large scan inside one.

Part 5 — Errors, and the One That Means "Maybe"

TransientTransactionErrorThe transaction as a whole failed and nothing was committed — a write conflict, a primary step-down mid-transactionRetry the entire transaction from the start. withTransaction does this

  WHY THE TWO CLASSES MUST BE HANDLED DIFFERENTLY

  TransientTransactionError -> nothing happened -> replaying the
    whole body is safe.

  UnknownTransactionCommitResult -> it MIGHT have happened.
    Replaying the BODY would double-apply. Only the COMMIT may be
    retried, because committing an already-committed transaction
    is a no-op.

  A hand-written "catch anything, run it again" loop treats both
  the same and double-applies on the second class. This is the
  single strongest argument for using withTransaction rather than
  writing the loop yourself.

  RETRY BUDGETS, which withTransaction does not give you

  withTransaction retries until a 120-second deadline. Under
  sustained contention that means a request can sit retrying for
  two minutes.

  MEASURED: a hot document (a global counter) reached 40%
  WriteConflict at 900 writes/sec. Requests retried for the full
  budget and the connection pool exhausted; the endpoint returned
  503s while the database was healthy.

  Two fixes, and the second is the real one:
    1. wrap withTransaction in your own timeout so a request fails
       fast rather than occupying a connection
    2. REMOVE THE CONTENTION. A global counter written by every
       request is a design problem no retry policy solves -- shard
       the counter across N documents and sum on read, or move it
       out of the transaction entirely.

Part 6 — Sharded Transactions, and the Alternatives

  A transaction touching ONE shard is coordinated locally.
  A transaction touching TWO OR MORE runs two-phase commit:

    mongos picks a COORDINATOR shard
      -> prepare on every participant  (each writes a prepare
         entry to its oplog and holds locks)
      -> coordinator decides commit/abort
      -> commit on every participant

  Measured 31 ms versus 2 ms single-shard. And during the prepare
  phase, participants hold locks on the affected documents --
  so a slow participant blocks the others.

  Design implication: choose a shard key that keeps
  transactionally-related documents on the SAME shard. Accounts
  belonging to one customer, orders for one tenant. See
  Sharding and Shard Keys.

  This is what you want whenever the second action is NOT a
  database write. Putting an email send inside a transaction is

🔑 Never put a non-database side effect inside a transaction callback. Two independent reasons: the transaction may abort after the side effect, leaving an email sent for an order that does not exist; and withTransaction may execute the callback several times, sending it twice. Both are real, both have shipped, and the outbox pattern solves both — the side effect becomes a durable, atomically-written intention that a separate idempotent worker carries out.

Interview Questions

Beginner: When do you need a transaction in MongoDB?

When an invariant genuinely spans more than one document and must hold at every instant. A single document write is already atomic — however many fields, arrays and nested subdocuments it changes — so anything expressible as one document needs no transaction.

The classic genuine case is moving money between two accounts owned by different parties: two documents, both must change or neither. The classic false case is "update an order and its line items", which is one document if the items are embedded.

There is also a middle case people miss: a check-then-write on one document does not need a transaction either, because the condition can go in the update filter — updateOne({ _id, balance: { $gte: amount } }, { $inc: { balance: -amount } }) is an atomic compare-and-swap.

Beginner: Why use withTransaction rather than start/commit manually?

Because it handles two different failure classes that need different responses. TransientTransactionError means nothing committed, so the whole body should be replayed. UnknownTransactionCommitResult means the commit outcome is unknown and it may have succeeded, so only the commit may be retried — replaying the body would double-apply.

A hand-written "catch and run it again" loop treats both the same and double-applies on the second. That is the strongest practical argument for the helper.

Two things it does not do for you: it does not make the callback idempotent (it can run several times, so no external side effects belong in it), and its retry budget is around two minutes, which under contention can occupy a connection far longer than a request should live.

Mid: What does snapshot isolation not protect against?

Write skew. Two transactions read the same consistent snapshot, each verifies an invariant that spans several documents, and each writes a different document. There is no write conflict, both commit, and the invariant is broken.

The canonical example is two accounts with a combined balance of 100 and a rule that the total must stay non-negative. Two concurrent transfers of 60, one from each account, each read total = 100, each pass the check, each write a different document. Result: −20, with both transactions individually correct.

The fixes all come down to making the concurrent transactions touch a shared document so one of them conflicts: hold the invariant's value on a parent document and update it in the same transaction, or bump a version field on a common document. Alternatively, encode the check into the update filter where the invariant is per-document, or accept it and reconcile — which is what real banking does with overdrafts.

Mid: What does a long-running transaction cost?

Mostly, it costs other queries. An open transaction holds a snapshot, and WiredTiger must retain every page version that snapshot might need, so eviction cannot reclaim them. In a measured case a 44-second transaction — well within the 60-second limit, so it "worked" — took unrelated p99 read latency from 2.1 ms to 180 ms and pushed tracked dirty bytes to 61% of cache.

That is why raising transactionLifetimeLimitSeconds to make a job fit is the wrong response to a timeout: it converts a failed job into a degraded cluster. The right response is to split the work into many short transactions, or to notice that the chunks were independent and needed no transaction at all.

The other limits worth knowing: 16 MB of total oplog changes per transaction (a size limit, not a document count), and on a sharded cluster a multi-shard transaction runs two-phase commit — measured 31 ms against 2 ms — holding locks on participants during the prepare phase.

Senior: A team wants a transaction that writes to the database and calls a payment API. How do you respond?

That cannot work, and it fails in both directions — so I would explain the mechanism rather than just saying no.

First, the transaction can abort after the payment API call succeeds, leaving money taken and no record of it. Second, withTransaction may execute the callback more than once on a transient error, so the payment could be charged twice. A database transaction has no authority over anything outside the database.

The outbox pattern is the answer. Atomically write the state change and an intention document — { type: "payment.capture", payload, status: "pending" } — in one transaction or, better, in one document if the model allows. A separate worker reads pending intentions, calls the payment API, and marks them done. That gives at-least-once delivery, which means the payment call must be idempotent — via the provider's idempotency key, which every serious payment API provides precisely for this.

What I would emphasise: at-least-once plus an idempotency key is not a compromise, it is the correct design. Exactly-once across two systems does not exist; what exists is an idempotent receiver. Teams that reject the outbox as "not atomic" usually end up with something that is at-most-once instead, which loses payments rather than duplicating them — a strictly worse failure mode.

I would also ask what the transaction was protecting. Often the real requirement is "the order must not appear as paid unless the payment succeeded", which is a state-machine question — the order starts as pending and the worker advances it — rather than an atomicity question.

Senior: Design the write path for a booking system: reserve a seat, charge a card, send a confirmation.

Three steps with three different consistency requirements, and the design mistake would be treating them as one unit of work.

  1. RESERVE -- must be atomic and contended
     One document per seat, or a seat array on the event document
     with a positional conditional update:

       seats.updateOne(
         { _id: seatId, status: "available" },
         { $set: { status: "held", holdBy: sessionId,
                   holdExpiresAt: now + 10min } })
       matchedCount === 0  ->  someone else got it

     Compare-and-swap on one document. No transaction. The TTL-ish
     hold field is what makes abandonment safe -- with a sweeper
     job rather than a TTL index, because TTL is not prompt.

  2. CHARGE -- external, cannot be transactional
     Outbox: the hold and a { type: "charge", idempotencyKey }
     intention written atomically. A worker calls the payment
     provider with that key, so a retry cannot double-charge.

  3. CONFIRM -- state transition on success
       seats.updateOne(
         { _id: seatId, status: "held", holdBy: sessionId },
         { $set: { status: "sold", orderId } })

     The filter re-asserts the hold, so an expired hold that has
     been re-sold cannot be silently overwritten.

  4. CONFIRMATION EMAIL -- a second outbox entry, written when
     the seat becomes "sold". Never inside any transaction.

Where a transaction earns its place: if a booking spans multiple seats that must be all-or-nothing ("four seats together or none"), that genuinely spans documents and I would use one — holding all four seats in a single transaction so a partial hold is impossible. That is a short, contended, same-shard transaction, which is exactly the shape transactions are good at.

The failure modes I would design for explicitly: the worker dies after charging and before confirming (the idempotency key makes the retry safe, and a reconciler compares provider charges against sold seats); the hold expires while the charge is in flight (the confirm's filter fails, and the compensating action is a refund — which is why the charge should be an authorisation captured later, if the provider supports it); and duplicate confirmation emails, which the consumer deduplicates on the outbox entry id.

What I would push back on: any request to make this "fully atomic end to end". It spans an external system, so it cannot be. What it can be is correct under every failure, via idempotent operations and a reconciler — and that is a stronger property than atomicity because it survives things atomicity does not, such as the payment provider timing out and succeeding anyway.

🏋️ Exercises

1 (easy): Rewrite this without a transaction. 
  await session.withTransaction(async () => {
    const p = await products.findOne({ _id: id }, { session });
    if (p.stock >= qty)
      await products.updateOne({ _id: id },
        { $inc: { stock: -qty } }, { session });
    else throw new OutOfStock();
  });
Solution

The invariant is entirely within one document, so the check belongs in the update filter:

  const r = await products.updateOne(
    { _id: id, stock: { $gte: qty } },
    { $inc: { stock: -qty } });

  if (r.matchedCount === 0) throw new OutOfStock();

Why this is not just shorter but better:

Transaction versionConditional update
Latency~4.8 ms (session, snapshot, two-phase commit)~0.9 ms
Round tripsStart, read, write, commitOne
Under contentionWrite conflicts and retriesThe filter simply does not match; no retry needed
CorrectnessCorrectEqually correct — the condition is evaluated atomically at write time

The subtle point: in the transaction version the check happens against a snapshot taken at the read, and the write happens later. It is correct because the transaction would detect a conflicting write and retry — but it is doing work to recover from a race that the conditional update never has.

When you would still need the transaction: if stock decrementing had to happen together with something in another collection — writing a reservation record, say — and both must be all-or-nothing. Then the conditional filter still belongs in the update; the transaction covers the second write.

2 (easy): Find the bug. 
  await session.withTransaction(async () => {
    await accounts.updateOne({ _id: from },
      { $inc: { balance: -amt } }, { session });
    await accounts.updateOne({ _id: to },
      { $inc: { balance: amt } });
    await audit.insertOne({ from, to, amt }, { session });
    await mailer.send(to, "You received a payment");
  });
Solution

Two bugs, and both are silent.

Bug 1 — the second updateOne has no { session }. It runs outside the transaction and commits immediately. If the transaction aborts, the debit and the audit entry are rolled back and the credit remains. Money is created. No error is raised at any point, so this is found by an auditor, not by a test — in one measured case, roughly 40 half-applied records per million, discovered five weeks later.

Bug 2 — the email send is inside the callback. Two separate problems: the transaction can abort after the email has gone out, and withTransaction can execute the callback multiple times on a transient error, sending the email twice.

  await session.withTransaction(async () => {
    const r = await accounts.updateOne(
      { _id: from, balance: { $gte: amt } },
      { $inc: { balance: -amt } }, { session });
    if (r.matchedCount === 0) throw new InsufficientFunds();

    await accounts.updateOne({ _id: to },
      { $inc: { balance: amt } }, { session });     // fixed
    await audit.insertOne({ from, to, amt }, { session });
    await outbox.insertOne({ type: "payment.received",
      to, amt, status: "pending" }, { session });   // not an email
  });
  // a worker reads the outbox and sends the mail, idempotently

I also added the balance guard to the debit filter — without it the transfer can overdraw the account, and a transaction alone does not prevent that.

Structural defence against bug 1: a repository object constructed with the session, so no call site can pass operations without it. Relying on every developer remembering an optional parameter, on a code path where forgetting is invisible, is not a control.

3 (medium): Under load, an endpoint using transactions returns 503s while the database reports healthy. Diagnose.
Solution

The combination — application 503s, healthy database — points at the connection pool, and transactions are a common cause.

The mechanism: withTransaction retries on write conflicts until an internal deadline of about 120 seconds. Each retrying request holds a connection for the whole time. With a pool of 100 and enough contention, every connection ends up occupied by a request that is retrying, and new requests are rejected — while the database itself is doing very little, because most of that time is backoff.

Confirming it:

  - driver metrics: connection checkout wait time, pool
    saturation, and how long requests hold a connection
  - server: serverStatus().metrics.operation.writeConflicts,
    and transactions.totalAborted vs totalCommitted
  - find the CONTENDED DOCUMENT: which _id appears in the
    conflicting writes. There is almost always exactly one

In a measured case a single global counter document at 900 writes/sec produced 40% write conflicts.

Two fixes, and only the second is a real one:

  1. Bound the retry. Wrap withTransaction in your own timeout — a few hundred milliseconds — so a request fails fast instead of occupying a connection for two minutes. This stops the 503s but does not stop the conflicts.
  2. Remove the contention. If a single document is written by every request, no retry policy fixes it. Options: shard the counter across N documents and sum on read; move the counter out of the transaction entirely and accept eventual accuracy; or aggregate it from the source data on a schedule instead of maintaining it inline.

The question I would ask before either: does this endpoint need a transaction at all? Contention on a single document usually means one write is the real work and the others are bookkeeping — and bookkeeping rarely needs to be atomic with the write it describes. Moving the counter to an outbox or a periodic rollup often removes both the transaction and the contention in one change.

4 (medium): Two transactions each check that a project has fewer than 10 members before adding one. Both pass, and the project ends with 11. Explain and fix three ways.
Solution

This is write skew. Both transactions read the same snapshot (9 members), both evaluate the rule as satisfied, and each inserts a different membership document. Different documents means no write conflict, so both commit. Snapshot isolation prevents concurrent writes to the same document; it does not prevent two transactions from deciding on the same data and writing elsewhere.

FixMechanismTrade-off
1. Counter on the project, updated in the same transactionBoth transactions $inc project.memberCount, so they write the same document and one gets a WriteConflict and retries — seeing 10 on the retry and failing correctlyMakes the project document a contention point. Fine at human rates, not at thousands per second
2. Embed the members in the project documentOne atomic conditional update: updateOne({ _id, $expr: { $lt: [{ $size: "$members" }, 10] } }, { $push: { members: m } }). No transaction at allOnly viable while the array stays small and bounded — which a 10-member cap guarantees. This is the best answer because of the cap
3. Unique index as the constraintStore a slot number on each membership with a unique index on { projectId, slot } and slots 0–9. The 11th insert fails on the indexAwkward to allocate slots and to reuse them after removals; the database enforces it absolutely

I would choose 2. A hard cap of 10 is exactly the condition that makes embedding safe — the array cannot grow unboundedly, so the usual objection to embedding does not apply. It removes the transaction, removes the race, and makes the invariant structurally impossible to violate rather than merely checked.

If memberships must stay separate documents (they carry roles, invitations, audit history), fix 1 is correct and is the general pattern for write skew: make the concurrent transactions touch a common document so one of them conflicts. The counter is not there to be read — it is there to create the conflict.

What I would also check: whether the existing data already violates the rule. Write skew that has been happening silently usually has a backlog, and shipping the fix without cleaning up leaves projects permanently over the limit and users confused about why they cannot remove and re-add someone.

5 (hard): A nightly job processes 2 million records inside a single transaction and now times out at 60 seconds. A colleague proposes raising transactionLifetimeLimitSeconds to 3600. Respond.
Solution

I would not do it, and the reason is that the cost of a long transaction is paid by everything else on the node, not by the job.

An open transaction holds a snapshot, and WiredTiger must retain every page version that snapshot might need — eviction cannot reclaim them. In a measured case a 44-second transaction took unrelated p99 read latency from 2.1 ms to 180 ms and pushed tracked dirty bytes to 61% of cache. Extending that to an hour does not make the job succeed quietly; it makes the cluster degraded for an hour. And the 16 MB oplog limit for a single transaction will very likely reject 2 million records anyway, so the change may not even work.

The question I would ask first: what invariant is the transaction protecting? Almost always the answer for a batch job is "none" — someone wrapped the loop in a transaction because it felt safer.

If the requirement is…Then
Each record is independentNo transaction. Batched writes with w: "majority", an _id-range cursor, and a resumable watermark. This is the usual case
Small groups must be atomic (a record and its children)One short transaction per group — thousands of 5 ms transactions, not one 3,600 s one
The whole job must be all-or-nothing as seen by readersNot a transaction: write to a new collection and swap, or write with a batch id and have readers filter on the committed batch. A 2-million-document atomic visibility change is a versioning problem, not a transaction problem

The recommended shape:

  iterate _id ranges in batches of ~1,000
    per batch: one short transaction (only if a group invariant
               needs it), w: "majority"
    record progress in a job_state document
    sleep proportionally to observed replication lag
  restartable: re-running resumes from the watermark

Slower in wall-clock terms and completely invisible to production — the same trade as the batched backfill in Schema Validation & Evolution, where 34 minutes with a 4-minute lag spike became 9 hours with no impact.

What I would concede: if the job genuinely needs a consistent read snapshot across 2 million records — a reconciliation comparing two collections, say — that is a real requirement. But the answer there is to run it on a secondary with a majority read concern and accept a slightly stale but consistent view, or to snapshot the data first, rather than holding a write transaction open on the primary for an hour.

6 (hard): Design a transaction policy for an engineering organisation: when transactions are allowed, how they are reviewed, and how they are monitored.
Solution

The goal is not to discourage transactions — they are a correct tool — but to make the alternatives visible, because the failure mode I see most is reaching for one reflexively and paying 5× write latency forever for an invariant a single document could have held.

1. A decision ladder in the engineering handbook, applied in order:

  a) Can these be ONE document?           -> no transaction
  b) Is the check per-document?           -> conditional update
  c) Is the second action outside the DB? -> outbox
  d) Must the invariant hold INSTANTLY,
     or would a reconciler do?            -> reconciler if not
  e) Otherwise: transaction, and document
     which invariant it protects

2. Guardrails encoded in a shared wrapper, not in review comments. One helper that every transaction goes through: it takes the session and hands it to a repository object (so { session } cannot be omitted), enforces a caller-supplied timeout shorter than the 120-second default, tags the transaction with a name for metrics, and refuses to run if the callback is not marked idempotent. Controls that live in a library survive turnover; controls that live in reviewers' heads do not.

3. Review checklist for anything in class (e): which invariant does this protect; could it be write skew (do concurrent instances write different documents?); is every operation sessioned; is the callback free of external side effects; is it bounded in size and duration; on a sharded cluster, does the shard key keep the documents co-located.

4. Monitoring, per named transaction:

MetricWhy
Commit / abort ratioRising aborts means growing contention before it becomes 503s
Retry count distributionThe leading indicator of pool exhaustion
Duration p99Long transactions degrade everything else on the node
writeConflicts by collectionLocalises the contended document
Count of distinct transaction sitesGrowth here is the signal that the schema is drifting relational

What I would deliberately not do: ban transactions or require an architecture review for each one. That produces workarounds that are less safe than the transaction would have been — hand-rolled two-phase writes, "we'll clean it up in a job that does not exist". The ladder plus a wrapper plus metrics gets the behaviour without the bureaucracy.

The metric I would actually watch as a leadership signal: the count of distinct transaction call sites over time. One or two, stable, is healthy. Steady growth means the document model is being pushed into a relational shape, and that is a design conversation to have at twenty sites rather than at two hundred.

🎯 Key Takeaways

  • A single-document write is already atomic, across every field, array and subdocument. Most transactions exist because of the schema, not the requirement.
  • A check-then-write on one document needs no transaction — put the condition in the update filter and it becomes an atomic compare-and-swap.
  • Always use withTransaction: it handles both TransientTransactionError (replay the body) and UnknownTransactionCommitResult (retry only the commit).
  • A hand-written retry loop double-applies, because it treats "maybe committed" like "definitely did not".
  • Every operation needs { session }. Omitting it on one write is silent and leaves that write committed after an abort.
  • The callback can run more than once. No emails, no payment calls, no external side effects inside it.
  • Snapshot isolation does not prevent write skew — two transactions verified the same invariant and each wrote a different document, with no conflict.
  • Fix write skew by making concurrent transactions touch a shared document so one of them conflicts.
  • Transactions cost about 5× on a single-document write (0.9 ms → 4.8 ms) and 15× across shards (2 ms → 31 ms).
  • A long transaction degrades every other query on the node by pinning page versions — 2.1 ms → 180 ms p99 during a 44-second transaction.
  • Never raise transactionLifetimeLimitSeconds to make a job fit. Split the work.
  • One transaction is capped at 16 MB of oplog changes — a size limit, not a document count.
  • withTransaction retries for about two minutes. Wrap it in your own timeout, and then remove the contention.
  • Contention on one document is a design problem no retry policy solves.
  • Cross-shard transactions run two-phase commit and hold locks during prepare. Choose a shard key that co-locates transactionally-related documents.
  • The outbox pattern is the answer whenever the second action is not a database write. At-least-once plus an idempotency key is the correct design, not a compromise.
  • Ask whether the invariant must hold instantly. Many cross-collection "consistency" requirements are satisfied by a reconciler at a fraction of the cost.
