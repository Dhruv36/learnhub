Embed vs Reference Schema Design

What you'll master: the decision that determines more about a MongoDB system's performance than every index and every query rewrite combined — and a framework for making it that does not reduce to "it depends". Why the question is not "what are my entities?" but "what does one request need?"; the measured case for embedding, where an order page went from 51 queries and 180 ms to one query and 1.2 ms; the three things that kill an embedded design — unbounded growth, cross-document duplication, and write contention on one hot document that capped throughput at 7,100 updates/sec with 12% of writes retrying on conflicts while a split design reached 61,000; what referencing actually costs, including a $lookup that took 47 seconds without an index and 2.1 seconds with one, and the N+1 pattern that quietly does the same thing in application code; the extended reference pattern that removed the join from 94% of reads; the question that resolves most duplication arguments — "is this value a snapshot or a live reference?"; and a cardinality-driven decision table you can apply in a design review. Prerequisites: Documents, BSON & _id and CRUD and What It Guarantees.

Part 1 — The Question Document Modelling Actually Asks

  RELATIONAL MODELLING asks:  "What are the entities and their
                               relationships?"
                              Then normalises, then adds indexes,
                              then joins at read time.

  DOCUMENT MODELLING asks:    "What does one request need, and how
                               often does each part change?"
                              Then stores that together.

  The relational question has ONE right answer for a given domain.
  The document question has a different answer for the same domain
  depending on what your application DOES with it. That is why two
  correct MongoDB schemas for "orders and customers" can look
  nothing alike.

Three inputs decide every embed-versus-reference call. Get these on the table before arguing about the shape:

InputWhat to establishWhich way it pushes
CardinalityOne-to-one, one-to-few (≤ dozens), one-to-many (hundreds), one-to-squillions (unbounded)Few → embed. Squillions → always reference
Access patternAre they read together, in the same request, most of the time?Read together → embed. Read separately → reference
Update patternHow large is the parent, and how often does the child change independently?Big parent + hot child → reference (write amplification)
Independent identityIs the child ever queried, linked to, or permissioned on its own?Yes → reference. No → embed
Consistency needMust a change be visible everywhere at once?Yes → reference (one copy). Tolerable lag → embed a copy
🔑 The single most useful sentence in a schema review: "show me the top five queries by volume." Not the domain model, not the ER diagram — the actual read paths and their rates. Almost every embed-versus-reference disagreement dissolves once those are on the table, because the argument was never about the data; it was about two people imagining different workloads.

Part 2 — The Case for Embedding, Measured

THE READ PATH: an order detail page

  REFERENCED - four collections
    orders(_id, customerId, status, createdAt)
    order_items(_id, orderId, sku, qty, priceCents)
    addresses(_id, customerId, line1, city, postcode)
    customers(_id, name, email)

  What the application does:
    1. findOne order                         1 query
    2. find items by orderId                 1 query
    3. findOne address                       1 query
    4. findOne customer                      1 query
                                             4 round trips, 4.8 ms

  And on the ORDER LIST page (50 rows), the naive version:
    1 query for the orders + 50 for the customers = 51 queries
                                             180 ms
    ^ this is the N+1 pattern, and it is the single most common
      performance bug written by developers arriving from an ORM.

  EMBEDDED - one collection
    { _id, status, createdAt,
      customer: { _id, name, email },
      shipTo:   { line1, city, postcode },
      items:    [ { sku, qty, priceCents }, ... ] }

    1. findOne order                         1 query, 1.2 ms
    List page: 1 query with a projection,    1 query, 6 ms

The difference is not really the query count — it is that the embedded version reads one contiguous, already-assembled record, while the referenced version pays a round trip and a random read per collection. Under load the gap widens, because each of those random reads is a chance to miss cache.

When embedding is clearly right

  ALL of these true -> embed, with no further discussion:

  [x] The child is meaningless without the parent
      (an order line item does not exist on its own)
  [x] They are almost always read together
  [x] The number of children is BOUNDED and small
      (order lines: a few dozen. Not "comments": unbounded)
  [x] The child is not queried independently across parents
      ("all line items for SKU X across all orders" is a
       reporting query, not an operational one - and $unwind
       or a warehouse handles it)
  [x] Updates to the child are updates to the parent anyway
💡 Embedding also buys you atomicity, for free. A single-document update is atomic (previous lesson), so an order and all its line items change together with no transaction, no coordination, and no partially-applied state. That is a real correctness advantage, not just a performance one, and it is the most under-rated argument for embedding.

Part 3 — The Three Things That Kill an Embedded Design

Killer 1: unbounded growth

  Every update rewrites the whole document (lesson 2). So an array
  that grows without limit turns a cheap write into an expensive
  one, GRADUALLY, with no code change to blame.

MEASURED: reviews embedded in product documents

  month 1     12 reviews   doc 31 KB    write p99   6 ms
  month 8    780 reviews   doc 1.4 MB   write p99  95 ms
  month 14  2,900 reviews  doc 3.4 MB   write p99 380 ms
                                        replication lag at peak: 40 s

  Nothing changed except time. There was no deploy to roll back and
  no query to blame, which is why this took eleven days to diagnose.

  THE TEST TO APPLY AT DESIGN TIME:
    "What is the 99th percentile count of this array after three
     years at our growth rate, and what does the parent document
     weigh then?"
  If you cannot answer, or the answer is "unbounded", do not embed.

Killer 2: duplication that must stay consistent

  Embedding a copy of shared data means N copies to update.

MEASURED: a customer's display name embedded in their orders

  Average orders per customer          9
  Worst case (a wholesale account) 41,000

  A name change fans out to every copy:
    db.orders.updateMany({ "customer._id": cid },
                         { $set: { "customer.name": newName } })
    41,000 documents, 9.1 s, and NOT atomic with the customer
    update - readers see a mix for those 9 seconds.

  Sometimes that is completely fine. Sometimes it is a compliance
  problem. Part 5 is about telling the difference.

Killer 3: write contention on one hot document

This one is the least known and bites hardest at scale. WiredTiger uses document-level optimistic concurrency: two concurrent writes to the same document conflict, and one is retried internally. That is invisible at low rates and becomes a throughput ceiling at high ones.

MEASURED: a per-campaign counter document, 800 concurrent clients

  ONE DOCUMENT   { _id: campaignId, clicks: N }
      throughput          7,100 updates/s  (ceiling - adding clients
                                            did not increase it)
      WriteConflict retries          12%
      p99 latency                   114 ms

  SHARDED COUNTER  { _id: {campaignId, bucket: 0..15}, clicks: N }
      write to a random bucket; read with a $group $sum
      throughput         61,000 updates/s
      WriteConflict retries         0.2%
      p99 latency                     9 ms

  The document was tiny. The index was perfect. The bottleneck was
  that everyone wanted to write to the SAME document, and no amount
  of hardware fixes that.
⚠️ A document is a unit of concurrency, not just a unit of storage. Embedding a frequently-updated field into a document that many writers touch converts independent writes into contending ones. When you see high WriteConflict counts in serverStatus, the answer is almost never a bigger machine — it is splitting the document.

Part 4 — What Referencing Actually Costs

  A reference is just a field holding another document's _id.
  There are no foreign keys, no cascades, no referential integrity.
  Nothing stops you deleting a customer with live orders - that is
  YOUR job, in application code or a background reconciler.

  Two ways to resolve one:

  1. APPLICATION-SIDE JOIN (usually better than its reputation)
     const orders = await orders.find(q).limit(50).toArray()
     const ids    = [...new Set(orders.map(o => o.customerId))]
     const custs  = await customers.find({ _id: { $in: ids } }).toArray()
     // stitch in memory

     TWO queries, regardless of row count. This is the correct fix
     for N+1, and it beat $lookup in most of the cases measured
     below because the $in is a batched point lookup.

  2. $lookup (a server-side left outer join)
     Convenient, and it keeps the work on the server - but see
     the numbers.

MEASURED: joining 200,000 orders to customers

  $lookup with NO index on the foreign field
      47,000 ms   - a nested loop: for each order, scan customers
  $lookup WITH an index on customers._id (the default)
       2,100 ms
  Application-side batched $in (50 orders per page, so 2 queries)
           7 ms per page

  The lesson is not "$lookup is bad". It is that $lookup is for
  ANALYTICAL work over sets, and paging UIs should batch instead.
  An unindexed $lookup is a nested loop and will find your
  production data.

The extended reference: the pattern that resolves most arguments

  Do not choose between "embed everything" and "embed nothing".
  Embed the two or three fields the read path needs, and keep the
  reference for the rest.

  {
    _id: ObjectId("..."),
    status: "paid",
    customer: {                    // <- EXTENDED REFERENCE
      _id: ObjectId("66a190..."),  //    the link
      name: "Ada Lovelace",        //    what the order page shows
      email: "ada@example.com"     //    what the receipt needs
    },
    items: [ ... ]
  }

  MEASURED on the real read mix:
    94% of order reads needed only name + email  -> no join at all
     6% needed the full customer (support tools, address book)
        -> one extra findOne, on the 6%

  Choose the embedded fields by two rules:
    1. They are needed by the HIGH-VOLUME read path
    2. They change RARELY (a name changes; a loyalty balance does
       not belong here)

Part 5 — Snapshot or Live Reference?

Most arguments about duplication are really an unasked question. Duplicated data is not automatically a bug — sometimes it is the requirement.

  ASK OF EVERY DUPLICATED FIELD:
  "Is this a SNAPSHOT of a value at a moment, or a LIVE REFERENCE
   to something that should always show current truth?"

  SNAPSHOT - duplication is CORRECT, and the alternative is a bug
    order.items[].priceCents
        The price when the order was placed. If a price change
        rewrote historical orders, your invoices would be wrong
        and your auditors would be unhappy. Referencing the
        product's current price here is a REAL BUG that teams
        ship regularly.
    invoice.customerAddress   - where it was actually shipped
    contract.termsVersion     - what they actually agreed to

  LIVE REFERENCE - keep ONE copy, or accept and bound the staleness
    user.currentEmail         - login must use the current value
    account.balance           - never duplicate; single source
    product.stockLevel        - never duplicate

  MIDDLE GROUND - a cached copy with a refresh mechanism
    order.customer.name       - stale for seconds is fine;
                                fan-out update, or refresh on read

Keeping duplicated values honest

MechanismHow it worksWhen to use it
Fan-out updateupdateMany on the source changeCopies are few (thousands); brief inconsistency acceptable
Change stream workerWatch the source collection, propagate asynchronouslyCopies are many, or the fan-out is too slow to do inline
Refresh on readStore copiedAt; re-fetch when older than a TTLLong-tail data where most copies are never read again
Version stampStore the source's version; a mismatch means "refresh me"You need to detect staleness, not just bound it
Accept it foreverNothing — the copy is a snapshotThe value is historical by definition. Write a comment saying so
🔑 Write the intent into the field name. priceAtOrderCents and customerNameCached tell the next engineer which rule applies; price and customerName invite them to "fix the inconsistency" and break your invoices. Naming is the cheapest documentation you will ever write, and in a schemaless database it is often the only documentation there is.

Part 6 — The Decision Table

One-to-one

One-to-few
order → line items (≤ ~50)		EmbedArray of sub-documentsChildren are queried independently across parents at high volume
One-to-many
product → reviews (hundreds+)		ReferenceChild collection with a productId index; embed a summary (reviewCount, avgRating) in the parentThe list is genuinely bounded and always shown in full → embed with a cap
One-to-squillions

Many-to-many
student ↔ course		Reference on the side you query fromArray of ids on one or both sides; a join collection only if the relationship has its own fields (enrolled date, grade)Both arrays are unbounded → a join collection
THE ONE-TO-MANY DEFAULT, CONCRETELY

  products: { _id, name, priceCents,
              reviewCount: 2900,        // summary, $inc'd on write
              avgRating: 4.3,           // summary, recomputed
              topReviews: [ {...}, {...}, {...} ] }   // capped at 3

  reviews:  { _id, productId, rating, body, createdAt }
            index { productId: 1, createdAt: -1 }

  The product page renders from ONE document (name, price, count,
  average, three featured reviews). "See all reviews" is a second,
  paginated query that most visitors never make.

  This is the shape most one-to-many relationships want: embed the
  SUMMARY, reference the DETAIL. It is neither "embed" nor
  "reference" - and it is usually the right answer.
💡 The schema is not permanent, but it is expensive. Changing a shape later means a migration over live data plus a dual-read/dual-write period — days of work, not hours. So it is worth an hour in a design review, and worth writing down why a choice was made. But do not gold-plate: model for the access patterns you have and the growth you can actually project, not for a hypothetical 100× that may never arrive.

Interview Questions

Beginner: When would you embed a sub-document rather than reference it?

When the child belongs to the parent and travels with it. My checklist:

  • The child is meaningless on its own — an order line item, a shipping address.
  • They are read together in the same request, nearly always.
  • The number of children is bounded and small.
  • The child is not queried independently across parents in the operational workload.

The payoff is one read instead of several — measured at 1.2 ms versus 4.8 ms for an order detail page — and, just as importantly, atomicity: a single-document update changes the parent and all its children together with no transaction.

The trigger to not embed is unbounded growth. If I cannot answer "how many of these will there be in three years?", I reference.

Beginner: What is the N+1 problem here, and how do you fix it?

Fetching a list of parents, then issuing one query per row to resolve a reference. A 50-row order list becomes 1 + 50 = 51 round trips — measured at 180 ms where the same page took 6 ms done properly. It is the most common performance bug developers bring from ORM habits, and it scales linearly with page size, so it looks fine in development with five rows.

Two fixes, in order:

  • Batch the second query. Collect the distinct ids and issue one find({_id: {$in: ids}}), then stitch in memory. Two queries at any row count. This is usually the right answer for a paginated UI, and measured at 7 ms per page.
  • Or remove the join entirely with an extended reference — embed the two or three fields the list renders. In one measured case that covered 94% of reads.

$lookup also works, but it is a heavier tool aimed at analytical work over whole sets; for a page of 50 rows the batched $in was 300× faster.

Mid: Write latency on a product collection has been climbing for months with no deploy to blame. Where do you look?

"Gradual, with no deploy" strongly suggests the documents themselves are growing, because every update rewrites the whole document — the cost of a write is proportional to document size, not to the size of the change.

I would confirm it with the distribution rather than the average, since the average hides a tail:

db.products.aggregate([
  { $project: { s: { $bsonSize: "$$ROOT" },
                n: { $size: { $ifNull: ["$reviews", []] } } } },
  { $group: { _id: null, avg: { $avg: "$s" }, max: { $max: "$s" },
              maxN: { $max: "$n" } } }
])

In the measured case an embedded reviews array had reached 2,900 elements and 3.4 MB, taking write p99 from 6 ms to 380 ms and pushing peak replication lag to 40 seconds — because every rewritten document also becomes an oplog entry the secondaries must apply.

The fix is structural: move reviews to their own collection indexed on {productId, createdAt}, and keep a summary in the product — reviewCount, avgRating, and the top three. The product page still renders from one document; "see all reviews" becomes a second, paginated query most visitors never make.

The preventable part: at design time, ask what the 99th-percentile array length will be in three years. "Unbounded" is a decision, not a detail.

Mid: A counter document is capped at about 7,000 updates/sec no matter how much hardware you add. Why?

Because a document is a unit of concurrency. WiredTiger uses optimistic concurrency control at document level: two concurrent writes to the same document conflict and one is retried internally. With 800 clients all incrementing one counter, measured throughput plateaued at 7,100/s with 12% of writes hitting WriteConflict retries and p99 at 114 ms. Adding clients did not increase throughput — it increased the conflict rate.

No amount of hardware fixes this, because the serialisation point is the document.

The fix is to shard the counter across N sub-documents:

// write to a random bucket
db.counters.updateOne({ _id: { campaignId, bucket: rand(0,15) } },
                      { $inc: { clicks: 1 } }, { upsert: true })
// read = one $group $sum over 16 documents

Measured: 61,000 updates/s, 0.2% conflicts, p99 9 ms. The trade-off is that reads now aggregate 16 documents instead of one, which is trivially cheap and is the correct place to pay the cost — reads of a click counter are rare, writes are constant.

The generalisable point: high WriteConflict counts in serverStatus are a modelling signal, not an infrastructure one.

Senior: How do you decide what to denormalise, and how do you keep the copies correct?

I ask one question of every candidate field: is this a snapshot of a value at a moment, or a live reference to something that must always show current truth?

  • Snapshot — the price on an order line, the address an order shipped to, the terms version a customer accepted. Here duplication is not a compromise, it is the requirement. Referencing the product's current price from a historical order line is a real bug that teams ship regularly, and it makes past invoices change retroactively.
  • Live reference — an account balance, stock level, current login email. Keep one copy. Two sources of truth for an authoritative value is not a performance trade-off, it is a correctness defect.
  • Cached copy — a customer's display name on an order. Duplicate it, but decide the refresh mechanism at the same moment you decide to duplicate: fan-out updateMany on change (fine for thousands of copies — 41,000 documents measured at 9.1 s), a change-stream worker for larger fan-outs, a TTL refresh-on-read for long-tail data, or a version stamp when you need to detect staleness rather than just bound it.

Two practices I insist on. Name the field for its semantics — priceAtOrderCents, customerNameCached — because in a schemaless database the field name is often the only documentation, and a field called price invites the next engineer to "fix the inconsistency". And never denormalise without naming the update mechanism in the same design discussion; a copy with no refresh plan is drift with a delay.

Senior: A team wants to embed everything to eliminate all joins. What is your response?

I would agree with the instinct and disagree with the absolute, then make it concrete rather than philosophical.

Where they are right: the read-path win is real and large, and the atomicity that comes with it removes whole classes of coordination bugs. "What does one request need?" is the right question.

Where the absolute breaks, with the three failure modes:

  • Unbounded growth. Every update rewrites the whole document. A measured embedded reviews array took write p99 from 6 ms to 380 ms over 14 months with no code change.
  • Write contention. A document is a unit of concurrency; embedding a hot field into a shared document capped throughput at 7,100/s with 12% conflict retries.
  • Consistency fan-out. One name change touching 41,000 documents, non-atomically.

What I would propose instead of a rule: the extended reference as the default. Embed the two or three fields the high-volume read path needs and that change rarely; keep the id for the rest. In the measured case that removed the join from 94% of reads while leaving the customer record as a single source of truth. Then the one-to-many default — embed the summary (reviewCount, avgRating, top three), reference the detail.

And I would reframe the goal. "Eliminate all joins" is a proxy for "make the hot paths fast". Measuring the top five queries turns an architectural argument into an engineering one — which is usually all a discussion like this needs, because both sides are picturing different workloads.

2 (easy): An order list page takes 180 ms for 50 rows. The profiler shows 51 queries. Show two fixes and say which you would ship.
Solution

Fix A — batch the lookup (ship this today):

const rows = await orders.find(q).sort({createdAt:-1}).limit(50).toArray()
const ids  = [...new Set(rows.map(o => o.customerId))]
const cust = await customers.find({ _id: { $in: ids } },
                       { projection: { name: 1, email: 1 } }).toArray()
const byId = new Map(cust.map(c => [String(c._id), c]))
rows.forEach(o => o.customer = byId.get(String(o.customerId)))

Two queries regardless of page size — measured 7 ms. Note the Set: 50 orders often have far fewer distinct customers, so the second query is usually smaller than the page.

Fix B — extended reference (the structural fix): store customer: {_id, name, email} on the order at write time. The list renders from one query with no join at all, and it is also more correct for a historical record: the order shows who placed it, which is arguably a snapshot anyway.

What I would ship: both, in that order. Fix A is a small, reversible change that removes the incident today and needs no migration. Fix B is the design I want, but it requires a backfill and a decision about the refresh mechanism for name changes — a fan-out updateMany on the customer's orders, measured at 9.1 s for the worst-case wholesale account with 41,000 orders.

What I would not do: reach for $lookup. It solves the round-trip count but on this data it measured 2.1 s per page against 7 ms for the batched form — it is a tool for analytical work over sets, not for paging.

3 (medium): Design the schema for a chat application: workspaces contain channels, channels contain messages, messages have reactions and threaded replies. State each decision and the query that drives it.
Solution

Start with the query list, because the shape falls out of it:

  1. Load the last 50 messages in a channel (constant, highest volume)
  2. Page backwards through history
  3. Post a message (write-heavy)
  4. Add/remove a reaction (very frequent, tiny)
  5. Open a thread (a minority of messages)
  6. List a user's channels on login

The schema:

workspaces: { _id, name, plan }
   Small, rarely changes.

channels:   { _id, workspaceId, name, topic,
              memberIds: [ ... ],       // embed: bounded, ~hundreds
              lastMessageAt, messageCount }
   memberIds embedded because "list my channels" is
   find({ memberIds: userId }) - one indexed query, no join.
   FLIP IT if channels can have 50,000 members: then a
   channel_members collection, indexed both ways.

messages:   { _id, channelId, userId,
              author: { name, avatarUrl },   // extended reference
              body, createdAt,
              reactions: { "thumbsup": [uid, uid], "tada": [uid] },
              threadCount: 4, threadLastAt: ISODate() }
   index { channelId: 1, _id: -1 }
   Referenced, never embedded in the channel: unbounded.

thread_replies: { _id, parentMessageId, userId, author, body, createdAt }
   index { parentMessageId: 1, _id: 1 }

The four decisions that matter, each with its reason:

  • Messages are their own collection. One-to-squillions. Query 1 becomes find({channelId}).sort({_id:-1}).limit(50) — served entirely by the index, with _id giving both ordering and range pagination for query 2.
  • author is an extended reference. Rendering 50 messages must not mean 50 user lookups (the N+1 from Part 4), and the display name at post time is arguably a snapshot anyway.
  • Reactions are embedded — bounded (a handful of emoji, tens of users), always read with the message, and $addToSet/$pull make add and remove atomic and idempotent. A popular message could grow this; if reactions ran to thousands of users I would store counts plus "did I react" separately.
  • Replies are a separate collection with a count on the parent. Threads are opened rarely, so embedding would make every message document carry weight that 90% of renders never use — and it would be unbounded. threadCount renders the "4 replies" affordance with no query.

The pressure point I would flag in review: lastMessageAt and messageCount on the channel mean every message posted also writes the channel document. In a busy channel that is a hot document and the contention ceiling from Part 3. If posting rates justify it, drop messageCount (compute it, or accept an approximation) and update lastMessageAt at most once every few seconds per channel.

4 (medium): A SaaS app embeds a full company sub-document (28 fields) into every user. There are 40,000 users across 900 companies. Company records are edited weekly. Diagnose and propose a migration.
Solution

Diagnosis — three separate costs:

  • Fan-out on every edit. A company with 4,000 users means 4,000 documents updated per edit, non-atomically. Readers see a mix during the update window.
  • Storage and cache. 28 fields plus their names, duplicated 40,000 times instead of 900. The names cost too — every field name is stored in every document (lesson 2), and cache does not get that back through compression.
  • Drift. Any write path that missed the fan-out has left stale copies, and nothing reports it. I would measure this before proposing anything, because the number is the argument.
// How much drift is already there?
db.users.aggregate([
  { $lookup: { from: "companies", localField: "company._id",
               foreignField: "_id", as: "c" } },
  { $unwind: "$c" },
  { $match: { $expr: { $ne: ["$company.name", "$c.name"] } } },
  { $count: "stale" }
])

Proposal — extended reference, keeping only what the hot path renders:

user: { _id, email, role,
        companyId: ObjectId("..."),
        company: { name: "Acme Ltd", plan: "enterprise" } }

Chosen by the two rules: needed on the high-volume path (the header shows the company name; the plan gates features on every request), and rarely changed. The other 26 fields — billing address, VAT number, support tier — are read on a settings page that one user in a thousand opens, so they become one findOne by companyId.

Migration, in reversible stages:

// 1. Add companyId while the old field still exists (additive, safe)
db.users.updateMany({ companyId: { $exists: false } },
  [ { $set: { companyId: "$company._id" } } ])
db.users.createIndex({ companyId: 1 })

// 2. Deploy readers that use companyId + the two embedded fields,
//    falling back to the old sub-document if absent
// 3. Shrink the embedded sub-document to {name, plan}
db.users.updateMany({}, [ { $set: { company: { name: "$company.name",
                                               plan: "$company.plan" } } } ])
// 4. Update the fan-out job to touch only those two fields

The judgement call worth stating: 40,000 users is small. This design is not currently hurting anyone, and "it is denormalised" is not by itself a reason to spend a sprint. What justifies the work is the drift count from the query above, plus the growth trajectory — at 400,000 users the weekly fan-out becomes an operational event. I would present it that way rather than as a purity argument, which is also how you get it prioritised.

5 (hard): Model an e-commerce order so that it is correct five years later when prices, product names, tax rates, and the customer's address have all changed. Be explicit about what is duplicated and why.
Solution

This is a snapshot-versus-live-reference exercise end to end. An order is a historical record, so the default flips: duplication is the requirement and referencing is the bug.

{
  _id: ObjectId("..."),
  orderNumber: "GB-2026-004192",     // natural business key, unique idx
  placedAt: ISODate("2026-08-21T10:14:07Z"),
  status: "delivered",

  // --- SNAPSHOTS: what was true at order time ---
  customer: {
    _id: ObjectId("66a190..."),      // link for "their other orders"
    nameAtOrder: "Ada Lovelace",     // who placed it, then
    emailAtOrder: "ada@example.com"  // where the receipt went
  },
  shipTo: { line1: "14 Bridge St", city: "Bristol",
            postcode: "BS1 4ND", country: "GB" },
  items: [ {
    productId: ObjectId("..."),      // link for "reorder" / reviews
    skuAtOrder: "ESP-250",
    nameAtOrder: "Espresso Beans 250g",   // the invoice line text
    unitPriceCents: NumberDecimal("18.99"),
    qty: 2,
    lineTotalCents: NumberDecimal("37.98")
  } ],
  tax: { scheme: "UK-VAT", ratePct: NumberDecimal("20.0"),
         rulesVersion: "2026-04", amountCents: NumberDecimal("7.60") },
  totals: { subtotal: ..., shipping: ..., tax: ..., grand: ... },
  termsVersion: "tc-2026-03",

  // --- LIVE: current operational state ---
  fulfilment: { carrier: "DPD", tracking: "...", deliveredAt: ... }
}

Why each duplication is correct, not sloppy:

FieldWhy it is a snapshot
unitPriceCentsReferencing the product's current price would silently rewrite historical invoices when prices change. This is the classic shipped bug
nameAtOrder (product)Products get renamed and rebranded; the invoice must say what the customer bought
shipToWhere it actually went, not where they live now
tax.ratePct + rulesVersionVAT rates change; a tax audit needs the rate that was applied and the ruleset that produced it
termsVersionWhich contract they actually accepted — a legal requirement, not an optimisation
totalsStored, not computed on read. Recomputing with today's rules would change history, and a rounding-rule change would silently alter past orders

Why the ids are still there: the links serve live questions — "show this customer's other orders", "reorder this item", "which orders contained the recalled batch". A snapshot plus a link gives you both, and that combination is exactly the extended reference pattern applied to historical data.

Two details that separate a good answer from a complete one:

  • Money is Decimal128, not double — the drift from lesson 2 is unacceptable in a financial record, and it appears only in aggregate, so spot-checking will not find it.
  • The field names carry the intent. nameAtOrder rather than name tells the next engineer this is deliberate. A field called name sitting next to a productId is an invitation to "fix the duplication" and break every historical invoice — and in a schemaless database the name is the only documentation they will see.

The one thing I would not snapshot: fulfilment. Delivery state is live operational data that changes after the order is placed, and it belongs in the order because it is read with it — but it is not a historical claim about the moment of purchase.

6 (hard): A social app embeds each user's follower list as an array of user ids. It works well until a celebrity signs up with 2.4M followers. Diagnose everything that breaks, then redesign — including the feed read path.
Solution

What breaks, in the order it will hurt:

  1. The 16 MB limit. 2.4M ObjectIds at 12 bytes plus array-key overhead is roughly 36 MB — the document literally cannot be written. Note that arrays are documents with numeric string keys (lesson 2), so the keys cost real bytes too.
  2. Write amplification, long before that. Every new follower rewrites the whole array. At a 4 MB document and a viral hour, this is the 380 ms-write scenario from Part 3.
  3. Write contention. Thousands of people following the same account concurrently all write one document — the 7,100/s ceiling with WriteConflict retries.
  4. Index explosion. A multikey index on the array creates one entry per element: 2.4M index entries for one document.
  5. Read cost. Loading the user for any purpose decompresses the whole array, even to render an avatar.

Redesign — the relationship becomes its own collection:

follows: { _id: { followerId, followeeId },   // compound _id =
           createdAt }                        //   free dedupe, no
                                              //   duplicate follows
  index { followeeId: 1, createdAt: -1 }   // "who follows X"
  index { followerId: 1, createdAt: -1 }   // "who does X follow"

users:   { _id, name, avatarUrl,
           followerCount: 2400000,   // $inc'd on follow/unfollow
           followingCount: 312 }

The compound _id makes a duplicate follow impossible rather than merely guarded — idempotency for free, per lesson 2. The counts are maintained with $inc so the profile page never counts rows; they are approximate under failure, which is universally acceptable for a follower count, and reconcilable by a nightly job.

The feed read path — and the reason this exercise is hard. The follow collection solves storage but not the timeline. Two strategies, and the right answer uses both:

Fan-out on WRITEFan-out on READ
MechanismOn post, insert into every follower's feed collectionOn read, query recent posts from everyone the user follows
ReadOne indexed query — very fast$in over followees + sort + merge
Write2.4M inserts for one celebrity postTrivial — one insert
Good forOrdinary users (a few hundred followers)Celebrities

The hybrid that production systems actually run: fan out on write for normal accounts, and mark accounts above a threshold (say 10,000 followers) as "pull". A user's feed is then their materialised feed rows merged at read time with recent posts from the handful of celebrity accounts they follow. That bounds both sides: no 2.4M-row write, and the read merges a small, capped number of pull sources.

What I would flag as the residual complexity: the merge makes exact chronological ordering and unread counts harder, and the threshold needs a backfill when an account crosses it. Those are real costs — but they are bounded and operational, whereas the embedded array has no version that works at all. Being able to say which problems are bounded and which are fatal is the actual skill this question tests.

🎯 Key Takeaways

  • Document modelling asks "what does one request need?", not "what are the entities?" — so two correct schemas for the same domain can look nothing alike.
  • Start every schema review with the top five queries by volume. Most embed-versus-reference arguments are two people imagining different workloads.
  • Embed when the child is bounded, meaningless alone, and read with the parent — measured 1.2 ms versus 4.8 ms per order page, and 6 ms versus 180 ms for a 50-row list.
  • Embedding also buys atomicity: parent and children change together with no transaction.
  • Killer 1 — unbounded growth. Embedded reviews took write p99 from 6 ms to 380 ms over 14 months with no deploy to blame. Ask for the 3-year p99 array length at design time.
  • Killer 2 — consistency fan-out. One name change touching 41,000 documents, non-atomically.
  • Killer 3 — write contention. A document is a unit of concurrency: 7,100 updates/s with 12% WriteConflict retries on one document, 61,000 across 16 buckets.
  • High WriteConflict counts are a modelling signal, not an infrastructure problem — no machine fixes a single-document serialisation point.
  • References have no referential integrity. Cascades and orphan cleanup are your job.
  • N+1 is the default failure of referencing: 51 queries and 180 ms for 50 rows. Fix it with one batched $in — two queries at any row count, 7 ms measured.
  • An unindexed $lookup is a nested loop — 47 s versus 2.1 s indexed; and even indexed it lost to a batched application join by 300× on a paginated view.
  • The extended reference is usually the right answer: embed the two or three fields the hot path needs and that change rarely — it removed the join from 94% of reads.
  • For one-to-many, embed the summary and reference the detail (reviewCount, avgRating, top three).
  • Ask of every duplicated field: snapshot or live reference? An order line's price is a snapshot and must be duplicated; a balance is live and must never be.
  • Never duplicate without naming the refresh mechanism in the same discussion: fan-out, change stream, TTL refresh, version stamp — or "never, it is a snapshot".
  • Name fields for their semantics (priceAtOrderCents, customerNameCached) — in a schemaless database that name is often the only documentation the next engineer gets.
