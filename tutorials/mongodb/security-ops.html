Security & Encryption Production

What you'll master: the layers that actually stop an incident, in the order they fail — starting with the one that caused MongoDB's reputational damage a decade ago and still causes breaches today: a database reachable from the internet with authentication not enforced, where the median time from exposure to an automated ransom note has been measured in hours, not days; authentication mechanisms and the account hygiene that matters more than the mechanism — one application credential with root is the single most common finding in a MongoDB security review, and it converts an application bug into a total compromise; RBAC done properly, including why readWrite on a database is not least privilege and what a custom role costs to maintain; the three encryption layers and the precise threat each one addresses — TLS for the network, storage encryption for a stolen disk, and client-side field-level encryption, the only one that protects data from a compromised database server or a curious DBA; operator injection, where an unvalidated JSON body turned { password: "x" } into { password: { $ne: null } } and logged an attacker in as any user; and the operational half — secrets that are not in environment variables forever, auditing that answers "who read this", and what you actually do in the first hour of a suspected compromise. Prerequisites: Operating MongoDB and CRUD and What It Guarantees.

Part 1 — Exposure Is the Whole Game

  THE BREACH PATTERN, unchanged for a decade

  1. A MongoDB instance is started for development with
     --bind_ip 0.0.0.0 and no authentication.
  2. It ends up on a network reachable from the internet -- a
     misconfigured security group, a forgotten test host, a
     container port published to the world.
  3. Automated scanners find it. Port 27017 is scanned
     continuously by many independent parties.
  4. The data is copied, the collections dropped, and a ransom
     document is inserted.

  Observed exposure-to-compromise times have been measured in
  HOURS. There is no window in which "we'll secure it next
  sprint" is safe.
ControlWhat it stopsEffort
Network isolation — private subnet, security group, no public IPEverything above, before authentication is even consultedConfiguration
--auth enforcedAnonymous access if the network control failsConfiguration + credentials
bindIp to specific interfacesAccidental exposure through an unexpected interfaceConfiguration
TLS requiredPassive interception and credential capture on the wireCertificate management
Non-default portEssentially nothing — scanners scan all portsDo not rely on it
⚠️ Defence in depth means every layer assumes the one outside it has already failed. Network isolation is the strongest control here and it is also the one most likely to be undone by someone else's change — a security-group edit, a new peering connection, a container platform publishing a port. So authentication must be enforced as though the database were public, and encryption must be configured as though the network were hostile. Every real breach in this class had two or three of these layers missing at once.

  THE FINDING THAT APPEARS IN ALMOST EVERY REVIEW

  A single credential, with the root role, used by:
    - the application
    - the migration scripts
    - the analytics job
    - three engineers' local tooling
    - CI

  Consequences:
    - an application bug (injection, SSRF, a leaked env var)
      becomes total compromise, not a scoped one
    - you cannot rotate it, because nobody knows every consumer
    - the audit log cannot attribute anything to anyone
    - you cannot revoke access for a departing engineer without
      breaking production

  systems nobody knew were using it, took 3 weeks, and was

Part 3 — Authorisation: Least Privilege in Practice

  db.createUser({
    user: "orders-service",
    pwd: passwordPrompt(),
    roles: [ { role: "readWrite", db: "shop" } ]
  })

  This is BETTER than root and is still not least privilege:
    - it can read and write EVERY collection in "shop",
      including collections belonging to other services
    - it can drop collections
    - it can create and drop indexes -- which means an
      application bug can drop an index and degrade the whole
      cluster

  A CUSTOM ROLE, scoped to what the service does

  db.createRole({
    role: "ordersServiceRole",
    privileges: [
      { resource: { db: "shop", collection: "orders" },
        actions: [ "find", "insert", "update" ] },
      { resource: { db: "shop", collection: "order_events" },
        actions: [ "find", "insert" ] },
      { resource: { db: "shop", collection: "customers" },
        actions: [ "find" ] }
    ],
    roles: []
  })

  Note what is ABSENT: no "remove" (this service never deletes),
  no "dropCollection", no "createIndex". If the service is
  compromised, the blast radius is bounded by this list.
Built-in roleGrantsWatch out for
readRead one databaseIncludes every collection in it
readWriteRead/write one databaseIncludes drop and index operations
dbAdminSchema and index administrationNot data access, which surprises people
clusterMonitorRead-only cluster metricsThe right role for monitoring agents
backup / restoreBackup operationsScope to the backup system only
rootEverythingBreak-glass only, with the credential in a vault and its use alerted on
🔑 The honest trade with custom roles is maintenance. A tightly scoped role must be updated whenever the service starts using a new collection, and a forgotten update is a production error. The way to make that sustainable is to define roles as code alongside the service and apply them from a migration — the same discipline as validators. A role edited by hand in mongosh drifts between environments and becomes the reason people give up and grant readWrite.

Part 4 — Three Encryption Layers, Three Different Threats

LayerProtects againstDoes not protect against
TLS (in transit)Network interception, credential capture, tampering on the wireAnything once the data is at the server
Encryption at rest (storage engine / volume)A stolen disk, a discarded drive, a copied snapshot volumeA running server, a compromised credential, a DBA reading the data — the database decrypts transparently for anyone authorised
Client-side field-level encryption (CSFLE / Queryable Encryption)The database server itself, its administrators, its backups, its logsA compromised application server, which holds the keys
  WHY AT-REST ENCRYPTION IS OFTEN MISUNDERSTOOD

  "Our data is encrypted at rest" is frequently offered as an
  answer to "what if the database is breached?".

  It is not an answer to that question. Encryption at rest
  protects the BYTES ON THE DISK. A running mongod decrypts
  transparently for any authenticated session. An attacker with a
  valid credential, or a DBA, sees plaintext.

  It answers exactly one question well: "what if someone obtains
  the physical or virtual disk?" -- a decommissioned drive, a
  copied snapshot, a seized machine. That is a real threat and
  worth addressing. It is just a different threat.

  CLIENT-SIDE FIELD-LEVEL ENCRYPTION

  The driver encrypts specific fields BEFORE sending them. The
  server stores and returns ciphertext and never has the key.

    { _id: 1,
      name: "Amy Chen",                    // plaintext
      ssn:  BinData(6, "AeI0...") }        // encrypted, always

  Deterministic encryption -> equality queries work (the same
    input produces the same ciphertext), at the cost of leaking
    equality: an observer can tell two records share a value.
  Randomised encryption -> stronger, but the field cannot be
    queried at all.
  Queryable Encryption (6.0+) -> supports equality and range
    queries on encrypted fields with a stronger scheme.

  What it costs, honestly:
    - key management becomes yours: a KMS, key rotation, and an
      application that cannot start without key access
    - encrypted fields cannot be used in most aggregations,
      cannot be indexed conventionally, and cannot be searched
      with regex
    - document size grows
    - ~10-25% overhead on operations touching encrypted fields

  Use it for the genuinely sensitive minority of fields --
  identifiers, health data, payment details -- not for whole
  documents.

Part 5 — Operator Injection

  THE VULNERABILITY

  // Express, JSON body parsed directly into a query
  app.post("/login", async (req, res) => {
    const user = await users.findOne({
      username: req.body.username,
      password: req.body.password        // <- attacker-controlled
    });
    ...
  });

  Normal body:   { "username": "amy", "password": "hunter2" }
  Attack body:   { "username": "amy",
                   "password": { "$ne": null } }

  The query becomes:
    { username: "amy", password: { $ne: null } }
  -- which matches Amy's document. Logged in as Amy, with no
  password.

  Variants: { "$gt": "" }, { "$regex": "^a" } to extract a
  password character by character, and { "$where": "..." } for
  arbitrary JavaScript where it is enabled.

  This is not a MongoDB flaw. It is trusting a JSON value to be a
  scalar when the client controls its TYPE.
DefenceHowStrength
Validate types at the boundaryA schema validator (zod, Joi, pydantic, a DTO) asserting username and password are stringsThe real fix. It also catches the next variant you have not thought of
Explicit castingString(req.body.password)Effective for this case, easy to forget on the next field
Strip $-prefixed keysSanitiser middlewareA useful net, but a blocklist — do not make it the only control
Never store retrievable passwordsCompare a hash, not the value; the query fetches by username onlyRemoves this specific attack by design
Disable server-side JavaScriptsecurity.javascriptEnabled: falseRemoves $where, $function, $accumulator — worth doing if unused
  THE SAME BUG IN A DIFFERENT SHAPE -- update injection

  await users.updateOne({ _id: id }, { $set: req.body });

  Attack body: { "role": "admin" }
  -> privilege escalation, and no operator was even needed.

  Fix: allowlist the fields that may be updated. Never spread a
  request body into an update document.

    const { displayName, timezone } = req.body;
    await users.updateOne({ _id: id },
      { $set: { displayName: String(displayName),
                timezone: String(timezone) } });
🔑 The general principle: never let a client control the structure of a query or an update, only its values. Both vulnerabilities above come from the same root — taking a parsed JSON object and handing it to the driver as if it were data, when the client chose its shape. Type validation at the boundary and field allowlists on updates address the whole class, where stripping $ characters addresses only the examples you thought of.

Part 6 — Secrets, Auditing, and the First Hour

Secrets practiceWhy
Never in the repository — including the git historyA rotated credential still in history is still a credential. Scan history, not just the working tree
Prefer workload identity to any stored secretNothing to leak, automatically rotated. Where available it removes the problem rather than managing it
Otherwise a secret manager with short-lived credentialsEnvironment variables are visible in process listings, crash dumps and container inspection output
Redact connection strings from logsThe password is in the URI, and the most common leak path is an error log with the full connection string
Rehearse rotationAn unrehearsed rotation takes weeks and gets abandoned — which is how credentials end up ten years old
  AUDITING -- what it answers that logs do not

  Enterprise/Atlas auditing records authentication attempts,
  authorisation failures, and (configurably) data access:

    auditLog:
      destination: file
      format: JSON
      filter: '{ atype: { $in: [ "authenticate",
                                 "authCheck",
                                 "createUser", "dropUser",
                                 "createRole", "grantRolesToUser",
                                 "dropCollection",
                                 "dropDatabase" ] } }'

  Filter deliberately. Auditing every read on a busy cluster
  produces unusable volume and measurable overhead; auditing
  authentication, privilege changes and destructive operations
  produces a log someone will actually read.

  The questions it answers:
    - who authenticated, from where, and when did it fail
    - who granted themselves a role
    - who dropped that collection
  None of which the ordinary log reliably tells you.

  THE FIRST HOUR OF A SUSPECTED COMPROMISE

  1. PRESERVE BEFORE YOU FIX
     Snapshot the current state. Capture logs, audit logs,
     currentOp, the user and role list, and the network
     configuration. Remediation destroys evidence, and you will
     need it to determine scope.

  2. CONTAIN
     Restrict network access first -- it is the fastest and
     least destructive control. Then rotate credentials, starting
     with any that are shared or privileged.

  3. DETERMINE SCOPE
     db.getUsers(), db.getRoles() -- any account you do not
     recognise, or any recently granted role?
     Audit log for authentications from unexpected sources.
     Collection list -- anything dropped, anything added
     (ransom notes are inserted as documents).

  4. ASSESS DATA EXPOSURE
     What could that credential read? This is where least
     privilege pays for itself: a scoped role turns "everything"
     into a specific, provable list.

  5. RECOVER
     Restore from an IMMUTABLE backup in a separate account --
     backups reachable with the compromised credentials must be
     treated as compromised too.

  6. Then the durable fixes, and a written timeline.

Interview Questions

Beginner: What are the first security controls you would put on a MongoDB deployment?

Network isolation and enforced authentication, in that order of effectiveness but both non-negotiable. The classic breach is a database reachable from the internet with authentication not enforced; automated scanners find port 27017 continuously, and observed exposure-to-compromise times are measured in hours.

Then TLS, so credentials and data are not readable on the network, and per-consumer credentials with scoped roles rather than one shared account.

The framing I would use: each layer assumes the one outside it has already failed. Network isolation is the strongest control and the one most likely to be undone by someone else's change — a security-group edit, a new peering connection — so authentication has to be configured as though the database were public.

Beginner: What is NoSQL operator injection?

Passing a client-controlled JSON value into a query without checking that it is a scalar. If the handler does findOne({ username, password: req.body.password }) and the attacker sends {"password": {"$ne": null}}, the query becomes "username = amy AND password is not null", which matches — and they are logged in without a password.

Variants include {"$gt": ""}, and {"$regex": "^a"} to extract a value one character at a time.

It is not a MongoDB flaw; it is trusting the client not to control the type of a value. The real fix is type validation at the API boundary — asserting these fields are strings — rather than stripping $ characters, which is a blocklist and only covers the cases you thought of.

Mid: What does encryption at rest actually protect against?

A stolen or improperly discarded disk, a copied snapshot volume, a seized machine. That is a real threat and worth addressing, and it is frequently a compliance requirement.

What it does not protect against is a breach of the running system. A running mongod decrypts transparently for any authenticated session, so an attacker with a valid credential — or a DBA — sees plaintext. "Our data is encrypted at rest" is often offered as an answer to "what if we are breached?", and it is an answer to a different question.

The layer that addresses that threat is client-side field-level encryption: the driver encrypts specific fields before sending them, so the server stores ciphertext and never holds the key. It costs you key management, the ability to index or aggregate on those fields, and 10–25% overhead — so it is for the genuinely sensitive minority of fields, not for whole documents.

Mid: Why is readWrite on a database not least privilege?

Because it grants access to every collection in that database, including collections owned by other services, and it includes destructive and administrative actions — dropping collections, and creating or dropping indexes. An application bug or a compromise can therefore drop an index and degrade the entire cluster, or read data the service has no business seeing.

Least privilege is a custom role naming the specific collections and the specific actions the service performs. If a service never deletes, it should not have remove. That list is also what lets you answer "what could this credential have accessed?" during an incident with a provable answer rather than "everything".

The honest cost is maintenance: the role must be updated when the service starts using a new collection, and a forgotten update is a production error. The way to make it sustainable is to define roles as code next to the service and apply them from a migration, exactly like schema validators — hand-edited roles drift between environments and are why teams give up and grant readWrite.

Senior: A developer says "we don't need auth, the database is in a private subnet". Respond.

I would agree that network isolation is the strongest single control here, and then explain why it cannot be the only one.

It is the layer most likely to be undone by someone else's change. A security-group edit, a new VPC peering, a load balancer misconfiguration, a container platform publishing a port, a VPN that grants broader access than intended — none of those are database changes, and none of them will be reviewed by the person who reasoned about this. The control is real and it is also outside our team's change control.

It does nothing against anything already inside the network. A compromised application server, a developer laptop on the VPN, a CI runner, another service with an SSRF vulnerability — all of these are inside the perimeter, and without authentication every one of them has full, unattributable access to all the data.

And without authentication there are no accounts, so there is no audit trail, no way to scope an incident, no way to revoke anything, and no way to give the analytics job read-only access. Those are operational capabilities, not just security ones.

The cost is genuinely low — enabling --auth, creating per-consumer users and connection strings — and I would offer to do it, because "it's on the backlog" is how this ends up permanent. The recurring pattern in this class of breach is that two or three layers were missing at once, and the one everyone was relying on turned out to have been changed months earlier by someone in a different team.

Senior: Design the security posture for a healthcare application storing patient records.

The requirement that shapes this is that the operator should not be able to read patient data casually, and that is a stronger requirement than "encrypted at rest" satisfies.

LayerDecision
NetworkPrivate subnets, no public endpoint, access only from the application tier. Administrative access via a bastion with its own audit trail
AuthenticationWorkload identity for services; LDAP/SSO for humans so revocation is central and immediate when someone leaves
AuthorisationCustom roles per service. No application credential with admin rights. A separate read-only role for analytics that cannot read the encrypted identifier fields
In transitTLS required, certificate validation enforced
At restStorage encryption with keys in a KMS — for the disk-theft and snapshot threat, and usually a compliance requirement
Field levelCSFLE / Queryable Encryption on direct identifiers and clinical detail. This is the control that addresses the actual requirement, because the server never holds the key
AuditingAuthentication, authorisation failures, privilege changes, and data access to patient collections — the one case where auditing reads is justified despite the volume
BackupsImmutable, separate account, encrypted. Note that CSFLE-encrypted fields stay encrypted in backups, which is a significant benefit

The design trade I would make explicit: encrypting a field removes the ability to index it conventionally, aggregate on it, or search it with regex. So the encrypted set must be chosen deliberately — direct identifiers and sensitive clinical fields, while pseudonymous keys and non-identifying attributes stay queryable. Getting that boundary right is a design conversation with clinical and legal stakeholders, not an engineering decision, and doing it late means re-encrypting data.

The operational commitments that come with it: key rotation with a rehearsed procedure; an application that cannot start without KMS access (so KMS availability becomes a dependency of your availability); and a documented answer to "what happens if we lose the keys", which is that the data is gone — permanently, by design.

What I would raise beyond the database: most healthcare data exposures are not database breaches. They are an over-broad API response, a log line containing a record, a support tool with no access control, or an export to a spreadsheet. The database posture above is necessary and it is not where I would expect the incident to come from, so I would push for the same rigour on logging redaction, API response shaping, and internal tooling access.

🏋️ Exercises

1 (easy): Find and fix the vulnerability. 
  app.post("/api/login", async (req, res) => {
    const u = await db.users.findOne({
      email:    req.body.email,
      password: hash(req.body.password)
    });
    if (u) res.json({ token: sign(u) });
    else res.status(401).end();
  });
Solution

The password is hashed, so the obvious injection on that field is blocked — hash() produces a string. But req.body.email is passed through untouched:

  { "email": { "$ne": null }, "password": "..." }

That matches the first user whose password hash happens to match — which is unlikely on its own, but combined with a known or leaked password it logs in as an arbitrary account rather than the intended one. And {"email": {"$regex": "^admin"}} narrows it to the account the attacker wants.

There is a second issue: hash(req.body.password) will throw or produce something unexpected if the password is an object rather than a string, depending on the hash implementation — an availability bug at best.

  // validate at the boundary -- the real fix
  const schema = z.object({
    email:    z.string().email(),
    password: z.string().min(1).max(200)
  });
  const { email, password } = schema.parse(req.body);

  const u = await db.users.findOne({ email });   // by email only
  if (!u || !(await verifyPassword(password, u.passwordHash)))
    return res.status(401).end();
  res.json({ token: sign(u) });

Three improvements, not one: types are validated so no field can be an object; the query fetches by email alone and the password is verified in application code with a constant-time comparison; and the response is identical for "no such user" and "wrong password", which avoids user enumeration.

The general rule: validate every client-supplied value's type at the boundary, not just the ones that look dangerous. The vulnerable field here was the one nobody was worried about.

2 (easy): An analytics service needs to read the orders and customers collections. Write the least-privilege role and explain each omission.
Solution 
  db.createRole({
    role: "analyticsReader",
    privileges: [
      { resource: { db: "shop", collection: "orders" },
        actions: [ "find" ] },
      { resource: { db: "shop", collection: "customers" },
        actions: [ "find" ] }
    ],
    roles: []
  })

  db.createUser({
    user: "analytics",
    pwd: passwordPrompt(),
    roles: [ { role: "analyticsReader", db: "shop" } ]
  })
OmittedWhy
read on the databaseWould grant every collection, including ones added later that analytics has no business reading — the failure is silent and grows over time
insert, update, removeAnalytics reads. The most common accidental-write vector in production is a reporting job, and this makes it impossible rather than unlikely
createIndexAn analyst adding an index to speed up their query can degrade production writes. Index changes should go through review
dropCollection, dropDatabaseNothing about this workload needs them
Only the two collections namedMakes "what could this credential have read?" answerable during an incident

Two things I would add beyond the role: the connection string should use readPreference=secondaryPreferred with maxStalenessSeconds so analytics does not churn the primary's cache, and ideally a tag pinning it to a hidden member. And maxTimeMS on the queries, since analytical queries are exactly the ones that run away.

The maintenance cost to acknowledge: when analytics needs a third collection, the role must be updated, and until it is the job fails with an authorisation error. That is the correct behaviour and it is also how these roles quietly get widened. Defining the role as code alongside the service, applied by a migration, keeps the change reviewable instead of someone granting read at 2am to unblock a report.

3 (medium): A compliance requirement says patient identifiers must not be readable by database administrators. Which controls satisfy it and which do not?
Solution
ControlSatisfies?Why
TLSNoProtects the network. The DBA reads the data at the server, not on the wire
Encryption at restNoA running mongod decrypts transparently for any authenticated session. This is the control most often cited for this requirement and it does not meet it
RBAC restricting the DBA's rolePartiallyA DBA who cannot find on that collection cannot read it through the normal path — but can typically grant themselves the role, restore a backup elsewhere, or read the files. It is a policy control, not a technical one
AuditingNo — but necessaryDetects and attributes access after the fact. Deterrence and evidence, not prevention
CSFLE / Queryable EncryptionYesThe driver encrypts before sending; the server stores ciphertext and never holds the key. A DBA sees BinData, in the collection, in the logs, and in backups

So the answer is CSFLE, with the others as supporting layers — and the key management is what makes it real: the KMS must be administered by a different team from the database, or the DBA can simply obtain the key and the control is theatre.

What it costs, which must be designed for up front: encrypted fields cannot be indexed conventionally, cannot be used in most aggregation expressions, and cannot be regex-searched. Deterministic encryption permits equality lookups but leaks equality — an observer can tell two records share a value, which for a small value domain can be enough to infer it. Queryable Encryption supports equality and range with a stronger scheme.

The design work is choosing the boundary: encrypt direct identifiers and sensitive clinical fields; keep pseudonymous keys and non-identifying attributes queryable so the application still functions. That decision needs clinical and legal input, and changing it later means re-encrypting data.

And the honest limitation: CSFLE protects against a compromised or curious database. It does not protect against a compromised application server, which holds the keys by necessity. If the threat model includes that, the controls belong at the application tier — and that is worth stating plainly rather than letting CSFLE be read as protection it does not provide.

4 (medium): You discover the application connects with a root credential shared by five systems. Plan the remediation.
Solution

The trap is rotating first. Rotating a shared credential before knowing every consumer breaks unknown systems — in one case four of them, taking three weeks and being abandoned twice. So discovery comes first, and it is the part that takes time.

  PHASE 1 -- discover every consumer (do not change anything)
    - audit log or connection log: source IPs and app names
      connecting with that user
    - grep the codebase, CI config, terraform, container specs,
      secret manager entries
    - ask, in a channel where the answer is not embarrassing:
      "who uses the shop-admin credential?"
    Expect to find consumers nobody remembered. That is the
    normal outcome and the reason for this phase.

  PHASE 2 -- profile what each consumer actually does
    For each: which collections, which operations. The profiler
    with the connection's appName is the fastest source.
    This produces the role definitions.

  PHASE 3 -- create scoped credentials, in parallel
    One user per consumer with a custom role. Roles defined as
    code, applied by migration.
    The old credential still works -- nothing has broken yet.

  PHASE 4 -- migrate consumers one at a time
    Deploy each with its new credential; verify; move on.
    Any authorisation error here is a role that was too narrow,
    and it is contained to one system.

  PHASE 5 -- verify the old credential is unused
    Monitor authentications for it across a FULL business cycle,
    including month-end jobs. This is the step people cut short,
    and month-end is exactly when the forgotten consumer runs.

  PHASE 6 -- disable, do not delete
    db.updateUser with a new random password first, so it can be
    restored in seconds if something surfaces. Delete after
    another cycle.

Why phase 6 is disable-then-delete: reversibility. If an unknown consumer appears, a password change is undone in seconds; a deleted user with a lost role definition is an incident.

The interim mitigation I would apply immediately, before any of this: if the application's credential has root, that is an active risk today. Creating one properly scoped credential for the application and switching it — the highest-value consumer, and the one most exposed to injection or SSRF — can usually be done in a day and removes most of the blast radius while the rest proceeds.

What to fix so it does not recur: credentials issued as code with a named owner, and a periodic review of accounts holding privileged roles. Shared credentials are not created deliberately; they accumulate because creating a new one is harder than reusing the one that works.

5 (hard): A monitoring alert shows an unfamiliar database named READ__ME_TO_RECOVER. Walk through your response.
Solution

This is the ransom pattern: data copied or destroyed, collections dropped, and a ransom document inserted. Treat it as a confirmed compromise, not a suspected one.

  HOUR 1 -- PRESERVE, then CONTAIN

  1. Do NOT delete the ransom database, and do not "clean up".
     It is evidence, and its contents indicate which automated
     campaign this is -- which sometimes tells you whether data
     was actually exfiltrated or merely dropped.

  2. Snapshot everything: volumes, logs, audit logs, currentOp,
     db.getUsers(), db.getRoles(), the network configuration,
     and the full list of databases and collections.

  3. CONTAIN via the network first -- it is fastest and least
     destructive. Restrict the security group to nothing, or to
     a single admin host. Do not stop mongod yet if the logs are
     not yet captured.

  4. Rotate every credential that could reach this cluster.
     Assume all are compromised.

  5. Declare an incident. Legal and privacy need to be involved
     early because disclosure obligations depend on scope, and
     scope determination has a clock on it.

  HOURS 2-4 -- SCOPE

  How did they get in? Almost always one of:
    - the instance was reachable from the internet
    - authentication was not enforced
    - a weak or leaked credential
    - an unpatched, known vulnerability
  The logs will usually show it within minutes of looking.

  What did they reach? This is where least privilege pays: a
  scoped role gives a provable list; a shared root credential
  gives "everything", and "everything" is what you must then
  disclose.

  Was data EXFILTRATED or only destroyed? Network egress volume
  around the event window is the strongest evidence. Absence of
  egress logging is itself a finding -- and it means you must
  assume exfiltration.

  RECOVERY

  Restore from an IMMUTABLE backup in a SEPARATE account. Backups
  reachable with the compromised credentials must be treated as
  compromised -- and deleting backups is the first thing these
  campaigns do when they can reach them.

  Rebuild the host rather than cleaning it. You cannot prove the
  absence of persistence on a compromised machine.

  Bring it back with auth enforced, network isolated, scoped
  credentials, and TLS -- all of which almost certainly means
  changing the configuration that allowed this.

The judgement call I would make explicitly: pay nothing, and do not expect the data back. These are automated campaigns; in many documented cases the data was never copied at all — the collections were simply dropped and a note left. Recovery comes from your backups, which is why the restore drill is a security control as much as an availability one.

The uncomfortable finding to prepare for: if there is no recent verified backup, the incident becomes an existential one rather than a bad day. That is the moment the value of the restore drill is settled, and it is far too late to start.

6 (hard): Design a security review checklist for MongoDB deployments that engineers will actually complete.
Solution

Design constraints, from watching checklists fail: it must be short enough to finish in an hour; every item must be verifiable by running something rather than by asserting it; and it must separate blocking items from recommendations, or everything becomes advisory.

#Blocking itemHow to verify
1Not reachable from the internetScan the public IP from outside; check security groups. Not "we believe it is private"
2Authentication enforcedAttempt an unauthenticated connection and confirm it fails
3TLS required, certificates validatedAttempt a non-TLS connection; confirm the client rejects a bad certificate
4No application credential with admin/rootdb.getUsers() — review every role assignment
5One credential per consumerMap credentials to consumers; any credential with two owners fails
6Secrets not in the repository, including historyRun a secret scanner over full git history
7Client input types validated at every query boundaryCode review of handlers passing request data into queries; one test asserting {"$ne": null} is rejected
8Backups exist, are immutable, in a separate account, and have been restoredThe restore drill record, with a date
Recommended (ticket, not blocking)
Custom roles rather than readWrite; auditing of auth and privilege changes; server-side JavaScript disabled if unused; field-level encryption for sensitive fields; rehearsed credential rotation; connection strings redacted from logs

Why item 7 is on the blocking list even though it is a code property rather than a configuration: operator injection is the most likely path from an application bug to a data breach, it is invisible in any infrastructure scan, and a single test asserting that a query field rejects an object is cheap enough that there is no excuse.

What makes engineers complete it: every item is a command whose output can be pasted into the review, so it takes an hour rather than a meeting; there are eight blocking items, not forty; and it runs at a defined moment — before a new deployment serves production data — rather than as a periodic sweep that competes with feature work.

What I would deliberately leave out: anything I cannot state a threat for. A checklist that includes "change the default port" teaches people that the list contains security theatre, and once they believe that they stop reading the items that matter.

And the meta-item: a date and an owner on each completed review. An undated checklist with no owner describes a system that existed once.

🎯 Key Takeaways

  • Exposure plus no authentication is still the dominant breach pattern, with exposure-to-compromise measured in hours.
  • Network isolation is the strongest control and the one most likely to be undone by someone else's change. Configure auth as though the database were public.
  • A non-default port is not a control.
  • One shared root credential is the most common finding — it turns an application bug into total compromise and makes rotation, revocation and attribution impossible.
  • readWrite is not least privilege: it covers every collection and includes drop and index operations.
  • Define roles as code and apply them by migration, or they drift and get widened.
  • TLS protects the wire; at-rest encryption protects a stolen disk. Neither protects data from an authenticated session.
  • Client-side field-level encryption is the only layer that protects data from the database server itself — at the cost of indexing, aggregation, and 10–25% overhead.
  • Encrypt the sensitive minority of fields, not whole documents.
  • Deterministic encryption enables equality queries and leaks equality.
  • Operator injection comes from letting a client control a value's type — { $ne: null } in a password field logs in as any user.
  • Never spread a request body into $set: {"role": "admin"} needs no operator at all.
  • Validate types at the boundary rather than stripping $ — a blocklist only covers what you thought of.
  • Prefer workload identity to any stored secret, and scan git history, not just the working tree.
  • Filter audit logs deliberately: authentication, privilege changes and destructive operations produce a log someone reads.
  • In an incident, preserve before you fix. Remediation destroys the evidence that determines scope — and scope determines your disclosure obligations.
  • Backups reachable with compromised credentials are compromised. Immutable, separate account, and restored recently enough that you know it works.
