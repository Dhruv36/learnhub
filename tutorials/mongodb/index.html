What MongoDB Actually Is Foundations

What you'll master: the model underneath the marketing — MongoDB's core primitive is the atomic single document, and almost every design rule in this track follows from that one fact; why schemaless is a claim about the database rather than about your data, demonstrated by the collection where one "user" document existed in six incompatible shapes and every reader carried defensive code for all six; how WiredTiger really stores and caches data, including the working-set arithmetic that turns a healthy database into a slow one overnight — p99 read latency went from 1.4 ms to 340 ms when the working set crossed the cache by 12%, with no change in query or data volume; what the database actually guarantees, since write concern and read concern are the two knobs that decide whether your data survives a failover and most applications never touch them; the query mental model, where there is no optimiser magic — a query either uses an index or examines every document, and a measured 41-second dashboard query became 9 ms with one compound index; and an honest fit assessment, including the three workloads where choosing MongoDB is a mistake you will pay for in year two. No prerequisites beyond basic programming — this is the entry point to the track.

Part 1 — The Document Model

THE SAME ORDER, TWO WAYS

  RELATIONAL — the data is normalised across tables
    orders        (id, customer_id, created_at, status, total_cents)
    order_items   (id, order_id, sku, qty, unit_price_cents)
    addresses     (id, customer_id, line1, city, postcode)
    -- reading one order for display: a 3-way join

  DOCUMENT — the data is stored the way it is read
    {
      _id: ObjectId("66c3f1..."),
      customerId: ObjectId("66a190..."),
      createdAt: ISODate("2026-08-21T10:14:07Z"),
      status: "paid",
      totalCents: 4599,

        { sku: "ESP-250", qty: 1, unitPriceCents: 1899 },
        { sku: "FLT-100", qty: 2, unitPriceCents: 1350 }

🔑 The design principle for the whole track: data that is read together should be stored together. Relational modelling asks "what are the entities?"; document modelling asks "what does one request need?" That is not a licence to embed everything — the limits are real and the next section is about where they bite — but it is the question you start from.

Part 2 — "Schemaless" Is a Statement About the Database, Not Your Data

MongoDB does not enforce a schema by default. Your application still has one — it is simply written in code, spread across every reader, and never validated.

WHAT THAT LOOKS LIKE AFTER THREE YEARS — ONE REAL `users` COLLECTION

Adopt it on day one; retrofitting it across 2.1M documents in six shapes is a project.

Part 3 — WiredTiger, Cache and the Working Set

THE STORAGE PICTURE

  ┌──────────────── mongod process ────────────────┐
  │  WiredTiger cache  (default: max(50% of        │
  │                     RAM−1GB, 256MB))           │
  │   ├─ uncompressed pages: documents + indexes   │
  │   └─ MVCC snapshots for concurrent readers     │
  └───────────────────┬────────────────────────────┘
                      │ evict / read
  ┌───────────────────▼────────────────────────────┐
  │  disk: collection files (snappy-compressed by  │
  │  default) + index files (prefix-compressed)    │
  │  + the journal (WAL)                           │
  └────────────────────────────────────────────────┘
  the OS page cache holds the COMPRESSED files, so RAM effectively
  serves twice — which is why "50% for WiredTiger" is a sensible default
  rather than a waste.

THE WORKING SET IS THE NUMBER THAT DECIDES YOUR LATENCY

  working set ≈ (indexes you actually use) + (documents you actually touch)

  MEASURED, one 240 GB collection on a 64 GB machine (31.5 GB cache):

    month   index size   hot docs   working set   cache   p99 read
    -------------------------------------------------------------

  nothing about the queries changed. Crossing the cache boundary turned
  index seeks that were memory reads into disk reads, and the eviction
  threads started competing with the workload.

Part 4 — What MongoDB Actually Guarantees

  GUARANTEE 1 — A SINGLE DOCUMENT WRITE IS ATOMIC

    db.orders.updateOne(
      { _id: id, status: "pending" },
      { $set: { status: "paid" }, $inc: { version: 1 },
        $push: { events: { type: "paid", at: new Date() } } }
    )
    -- all three modifications apply, or none do. No reader sees half.
    -- This is why embedding is powerful: a consistent unit of data is a
    -- consistent unit of WRITING.

  GUARANTEE 2 — WRITE CONCERN DECIDES WHAT "ACKNOWLEDGED" MEANS

    w: 1                the primary has it in memory (journal not
                        necessarily flushed)
    w: "majority"       a majority of replica-set members have it —
                        it will survive an election.  DEFAULT since 5.0
    j: true             flushed to the journal on those members
    wtimeout: 5000      how long to wait before returning an error
                        (NOTE: a timeout does NOT undo the write)

  GUARANTEE 3 — READ CONCERN DECIDES WHAT YOU MIGHT SEE

    "local"        whatever this node has, including writes that could
                   still be rolled back.  DEFAULT
    "majority"     only data acknowledged by a majority — cannot be
                   rolled back
    "linearizable" a real-time guarantee on a single document, at a
                   latency cost
    "snapshot"     a consistent point-in-time view (transactions)
🔑 The combination that surprises people: default write concern is majority (since 5.0) but default read concern is local. So a read on a secondary — or on a primary during an election — can return a write that later disappears. If your application reads back what it just wrote and acts on it, you want readConcern: "majority", or causally consistent sessions, both covered in replica sets & read concerns.

Part 5 — The Query Mental Model: Index or Scan

  THERE IS NO OPTIMISER MAGIC. A QUERY EITHER:
    (a) uses an index to go straight to candidate documents (IXSCAN), or
    (b) examines every document in the collection (COLLSCAN)

  and the only number that matters for (a) is how many documents it had
  to examine to return the ones you asked for.

MEASURED — THE SAME DASHBOARD QUERY, BEFORE AND AFTER ONE INDEX

  db.orders.find({ status: "paid", createdAt: { $gte: cutoff } })
           .sort({ createdAt: -1 }).limit(50)

  BEFORE — no useful index
    executionTimeMillis  41,208
    totalDocsExamined     8,412,006
    totalKeysExamined             0
    stage                 COLLSCAN + SORT (in memory, 87 MB)
    -- and the sort would have failed above the 32 MB find() limit if the
    -- match had been less selective

  AFTER — db.orders.createIndex({ status: 1, createdAt: -1 })
    executionTimeMillis          9
    totalDocsExamined           50
    totalKeysExamined           50
    stage                 IXSCAN (no SORT stage at all — the index
                          already provides the order)

  ratio docsExamined : docsReturned
    before  8,412,006 : 50   = 168,240 : 1
    after          50 : 50   =       1 : 1     ← the target

THE THREE QUESTIONS THAT DECIDE IT

  1. WHAT DOES ONE REQUEST NEED?
     If the answer is "one aggregate and its children" -> document model.
     If it is "five entities joined five ways, differently each time"
     -> relational.

  2. WHAT MUST BE CONSISTENT TOGETHER?
     If your invariants live inside one aggregate -> single-document
     atomicity covers you for free.
     If they span aggregates at high rate -> you are buying transactions,
     and you should compare honestly with a database whose primary
     primitive is the transaction.

  3. WHAT IS THE ACCESS PATTERN AT SCALE?
     Document databases reward knowing your queries in advance, because
     the schema is shaped for them. If your queries are genuinely
     unpredictable and analytical, that reward turns into a tax.

  A LEGITIMATE AND COMMON ANSWER: both. MongoDB for the operational,
  document-shaped workload; a relational store or warehouse for the
  reporting and the ledger. Choosing one database for every workload is
  how estates end up with the anti-patterns in the final lesson.

❌ Treating MongoDB as a schemaless JSON dump on a machine sized for the data rather than the working set, with default write and read concerns nobody has read, and queries written without checking whether an index exists. Three years later the users collection holds six incompatible document shapes across 2.1M records, and fourteen call sites carry defensive code to paper over renames and type changes that were never migrated. The machine has 64 GB of RAM for a 240 GB collection, which was fine until the working set crossed the cache by 12% and p99 reads went from 1.4 ms to 340 ms with no change in query or volume — and nobody was watching pages evicted by application threads. Reads use the default local concern, so an application that reads back what it just wrote occasionally acts on a write that a failover then discards. And the dashboard query examines 8.4 million documents to return 50, sorts 87 MB in memory, and takes 41 seconds — because no compound index exists and nobody has run explain.

✅ Model around what one request needs, manage the schema deliberately, size for the working set, and choose your concerns on purpose. Store data the way it is read, and let the atomic single document carry the invariants that belong to one aggregate — that is the primitive everything else in this track builds on. Version your documents from day one and add JSON Schema validation at moderate level, so old documents are tolerated and shape seven never appears. Size the machine so indexes plus hot documents fit in the WiredTiger cache, and alert on cache pressure before latency moves rather than after. Set writeConcern: majority deliberately and use readConcern: majority or a causally consistent session wherever you read back what you wrote. Then treat every query as index-or-scan: run explain, drive the examined-to-returned ratio toward 1:1, and let a compound index turn a 41-second scan into 9 milliseconds. And be honest about fit — ad-hoc joins across many entities, high-rate cross-document invariants, and star-schema reporting belong somewhere else.

Interview Questions

Beginner: What is the difference between a document database and a relational database?

A relational database normalises data into tables and reassembles it at read time with joins. A document database stores a whole aggregate — the thing your application reads and writes as a unit — in one document, including nested arrays and sub-documents.

The practical consequences:

  • Reads that need one aggregate become a single index seek rather than a multi-way join.
  • Writes to that aggregate are atomic for free, because a single-document write is atomic.
  • Schema is per-document and not enforced by default, which is flexibility you must manage rather than an absence of schema.
  • Joins exist ($lookup) but are not the primary tool — they are a left outer join inside an aggregation pipeline.

The framing I would offer: relational modelling asks "what are the entities?", document modelling asks "what does one request need?" Both are legitimate; the second is what MongoDB is optimised for.

Beginner: Is MongoDB schemaless?

The database does not enforce a schema by default. Your data still has one — it is written in your application code, duplicated across every reader, and never validated.

What that produces over time is measurable. In one real collection of 2.1M users there were six distinct field-sets: an original shape, a renamed shape (name → firstName/lastName), a snake_case shape from a different service, one where plan had become a sub-document instead of a string, and two partials. Every read path carried defensive code for all of them, in fourteen places.

So the accurate statement is that MongoDB has a flexible, per-document schema. Adding a field is genuinely free; renaming or retyping one is a migration with the same care you would take in SQL.

The practice that keeps the flexibility without the archaeology: put a schemaVersion in every document, add JSON Schema validation at moderate level (which tolerates existing documents while rejecting new bad ones), and migrate deliberately.

Mid: What is the "working set", and why does it decide your latency?

The working set is the data your workload actually touches: the parts of your indexes that get traversed, plus the documents that get read, over a representative window. It is almost never the size of your data.

It matters because MongoDB serves reads from the WiredTiger cache (by default about half of RAM minus a gigabyte). While the working set fits, index seeks and document reads are memory operations. When it does not, the same queries start faulting to disk and the eviction machinery starts competing with your workload — so the degradation is a cliff rather than a slope.

The measured example: a 240 GB collection on a 64 GB machine with a 31.5 GB cache. At a 27.5 GB working set, p99 reads were 1.4 ms. At 35.3 GB — 12% over cache — the same queries on the same data measured 340 ms.

The signals to alert on, all from serverStatus: pages read into cache per second rising, tracked dirty bytes approaching 5% of cache, and — the unambiguous one — pages evicted by application threads above zero, which means your queries are now doing the eviction work themselves.

Mid: A query returns 50 documents but takes 41 seconds. How do you approach it?

Start from the model: a query either uses an index or examines every document. So the first command is explain("executionStats"), and the first number I look at is the ratio of documents examined to documents returned.

In the measured case that ratio was 8,412,006 : 50 — a COLLSCAN, followed by an in-memory sort of 87 MB. Two problems in one plan: no index to select on, and no index to provide the sort order.

The fix was a single compound index matching the query's shape — equality field first, then the sort field — after which the plan was an IXSCAN with 50 documents examined for 50 returned and no SORT stage at all, in 9 milliseconds.

The general procedure: check the stage (IXSCAN vs COLLSCAN), check examined-to-returned, check whether a blocking SORT stage exists, and confirm the index key order matches Equality → Sort → Range. And I would add that a blocking sort in find() is limited to 32 MB, so this class of query often does not merely become slow — it starts failing under load while passing in testing.

Senior: When would you choose MongoDB, and when would you argue against it?

I would decide from three questions rather than from a feature list.

QuestionFavours MongoDBFavours relational
What does one request need?One aggregate and its childrenSeveral entities, joined differently each time
What must be consistent together?Invariants inside one aggregateInvariants spanning entities, at high rate
How predictable are the access patterns?Known in advance; the schema is shaped for themGenuinely ad-hoc and analytical

Strong fits: document-shaped aggregates (orders, profiles, catalogues, CMS content), evolving or per-tenant-variable schemas, high write throughput with a natural partition key, and event/telemetry data with bucketing or time-series collections.

Where I would argue against it: ad-hoc analytical joins across many entities ($lookup is a nested loop by default and this is what a warehouse is for); invariants that span many documents at a high rate, such as a double-entry ledger or seat inventory, where you end up buying multi-document transactions to emulate a primitive another engine gives you natively; and star-schema reporting, which is simply the wrong shape.

The answer I most often give in practice is both — MongoDB for the operational, document-shaped workload, and a relational store or warehouse for the ledger and the reporting. Insisting on one database for every workload is how estates arrive at the problems in the final lesson of this track.

Senior: What does MongoDB guarantee about a write, and what do most applications get wrong?

Three layers, and most applications only think about the first.

Atomicity is per document. A single updateOne that sets fields, increments a counter and pushes to an array applies entirely or not at all, and no reader sees a partial state. That is the primitive the whole data model is built around — it is why putting an aggregate in one document gives you consistency for free.

Write concern decides what acknowledgement means. w: 1 means the primary has it in memory; w: "majority" means a majority of members have it and it will survive an election; j: true adds journal durability. Since 5.0 the default is majority, which is the right default — but the detail people miss is that a wtimeout expiring does not undo the write. It reports that the durability level was not reached in time; the write may still be applied and later replicated.

Read concern decides what you might see, and its default is local — which can include writes that a rollback later discards. So the combination that catches people is majority writes with local reads: an application that writes, reads it back, and acts on the result can occasionally act on data that disappears after a failover.

What I would recommend: choose write concern explicitly per operation class, use readConcern: "majority" or causally consistent sessions for read-your-writes paths, and remember that none of these settings makes a multi-document invariant atomic — that requires a transaction, with the costs covered in its own lesson.

Solution

    JOIN addresses a ON a.id = o.ship_to_id

Solution 
STEP 1 — WHAT IS THE CACHE, AND HOW FULL IS IT?

  db.serverStatus().wiredTiger.cache["tracked dirty bytes in the cache"]

  // index size is the floor of the working set

  // (an overestimate: repeats are counted, so measure distinct _ids if
  //  you need precision)

STEP 3 — THE ALERT THAT FIRES BEFORE USERS NOTICE

  // sample serverStatus every 10s and alert on RATES, not levels
  alert: WiredTigerCacheChurn
    expr: rate(wt_cache_pages_read_into_cache[5m]) > 500
          and rate(wt_cache_pages_requested[5m]) > 0
          and (rate(wt_cache_pages_read_into_cache[5m])
               / rate(wt_cache_pages_requested[5m])) > 0.02
    // more than 2% of page requests are coming from disk

  alert: WiredTigerApplicationEviction        ← the unambiguous one
    expr: rate(wt_cache_pages_evicted_by_application_threads[5m]) > 0
    for: 5m
    annotation: "queries are doing eviction work; the working set no
                 longer fits. Expect a latency cliff."

  alert: WiredTigerDirtyBytes
    expr: wt_cache_tracked_dirty_bytes / wt_cache_maximum_bytes > 0.05

4 (medium): Prove single-document atomicity, and find where it stops protecting you.
Solution 
PART A — ONE DOCUMENT IS ATOMIC, INCLUDING MULTI-FIELD UPDATES

  // two concurrent workers, both trying to claim the same order
  db.orders.updateOne(
    { _id: id, status: "pending" },                  // the guard
    { $set:  { status: "processing", claimedBy: workerId },
      $inc:  { version: 1 },
      $push: { events: { type: "claimed", by: workerId, at: new Date() } } }
  )

  worker A: { matchedCount: 1, modifiedCount: 1 }    ← won
  worker B: { matchedCount: 0, modifiedCount: 0 }    ← lost, safely

  // the guard on `status` makes this a compare-and-swap. Without it,
  // both workers "succeed" and the second overwrites the first.

  // PROVE the events array never interleaves:
  for (let i = 0; i < 1000; i++) { /* 8 concurrent claimers */ }
  db.orders.aggregate([
    { $match: { _id: id } },
    { $project: { n: { $size: "$events" }, distinct:
        { $size: { $setUnion: "$events.by" } } } }
  ])
  { n: 1, distinct: 1 }        ← exactly one claim recorded

PART B — WHERE IT STOPS: TWO DOCUMENTS

  // move stock from one warehouse document to another
  db.stock.updateOne({ _id: "bristol", qty: { $gte: 5 } }, { $inc: { qty: -5 } })
  // ... process crashes here ...
  db.stock.updateOne({ _id: "leeds" },  { $inc: { qty:  5 } })

  RESULT: 5 units vanish. Each write was atomic; the PAIR was not.

  THREE WAYS OUT, IN ORDER OF PREFERENCE
   1. RESHAPE so the invariant lives in ONE document
      { _id: "sku-espresso-250",
        warehouses: { bristol: 40, leeds: 12, total: 52 } }
      db.stock.updateOne(
        { _id: sku, "warehouses.bristol": { $gte: 5 } },
        { $inc: { "warehouses.bristol": -5, "warehouses.leeds": 5 } })
      -- one document, one atomic write, invariant preserved

   2. MAKE IT IDEMPOTENT AND RETRYABLE
      record a transferId; each side is applied at most once:
      db.stock.updateOne(
        { _id: "leeds", appliedTransfers: { $ne: transferId } },
        { $inc: { qty: 5 }, $push: { appliedTransfers: transferId } })
      -- a crashed transfer can be replayed safely by a worker

   3. A MULTI-DOCUMENT TRANSACTION
      correct, and the most expensive option — see <transactions>
InvariantAtomic for free?Approach
Order total matches its line items✅ if both are in the order documentEmbed
Status transitions happen once✅ with a guard in the filterCompare-and-swap on status or version
Stock moves between warehouses❌ across documentsReshape into one document, or idempotent transfers
Debit one account, credit another❌Transaction — or a different database for the ledger
A counter shared by many writers✅ $inc is atomicBut it serialises on that document — see anti-patterns
🔑 The guard in the filter is what makes an update a compare-and-swap. updateOne({_id: id}, {$set: {status: "processing"}}) always "succeeds" — including when another worker already claimed it. Adding status: "pending" to the filter turns matchedCount: 0 into the signal you needed, and costs nothing.
5 (hard): Demonstrate what write concern and read concern actually change, including the read-your-writes trap.
Solution 
SETUP — A THREE-MEMBER REPLICA SET

  rs.status().members.map(m => ({ name: m.name, state: m.stateStr }))
  [ { name: "mongo1:27017", state: "PRIMARY" },
    { name: "mongo2:27017", state: "SECONDARY" },
    { name: "mongo3:27017", state: "SECONDARY" } ]

EXPERIMENT 1 — WHAT w:1 MEANS WHEN THE PRIMARY DIES

  // write with the weakest concern
  db.events.insertOne({ _id: 1, note: "w1" }, { writeConcern: { w: 1 } })
  { acknowledged: true, insertedId: 1 }          ← "success"

  // immediately partition the primary from the other two, forcing an
  // election before replication catches up:
  $ docker network disconnect testnet mongo1

  // after the new primary is elected:
  db.events.findOne({ _id: 1 })
  null                                           ← the write is GONE

  // and on the old primary when it rejoins:
  $ grep "rollback" /var/log/mongodb/mongod.log
  "Rolling back 1 operation" ... written to a rollback file, not applied

EXPERIMENT 2 — THE SAME WRITE WITH MAJORITY

  db.events.insertOne({ _id: 2, note: "wmajority" },
                      { writeConcern: { w: "majority", wtimeout: 5000 } })
  // this returns only once 2 of 3 members have it
  // partition the primary, force an election:
  db.events.findOne({ _id: 2 })
  { _id: 2, note: "wmajority" }                  ← survives ✅

EXPERIMENT 3 — THE READ-YOUR-WRITES TRAP (majority write, local read)

  db.orders.insertOne({ _id: 3, status: "paid" },
                      { writeConcern: { w: "majority" } })
  // application then reads from a SECONDARY for scale:
  db.getMongo().setReadPref("secondaryPreferred")
  db.orders.findOne({ _id: 3 })
  null                                           ← replication lag

  FIX A — read from the primary for read-your-writes paths
  FIX B — causally consistent session (works across nodes):
    const s = db.getMongo().startSession({ causalConsistency: true });
    const c = s.getDatabase("shop");
    c.orders.insertOne({ _id: 4 }, { writeConcern: { w: "majority" } });
    c.orders.findOne({ _id: 4 });          // guaranteed to see it,
                                           // even on a secondary
  FIX C — readConcern majority + causal session for the strongest
          practical guarantee

EXPERIMENT 4 — WHAT wtimeout DOES **NOT** DO

  db.events.insertOne({ _id: 5 },
    { writeConcern: { w: "majority", wtimeout: 1 } })   // 1 ms: too short
  WriteConcernError: waiting for replication timed out

  db.events.findOne({ _id: 5 })
  { _id: 5 }                     ← the write HAPPENED. The error means
                                   "not confirmed in time", NOT "rolled back".
  // applications that retry on this error must be idempotent, or they
  // create duplicates.
CombinationSurvives failover?Read-your-writes?Cost
w:1 + localNoOn the primary onlyLowest latency
w:majority + localYesNot on secondariesReplication round trip
w:majority + majorityYesYes on the primary+ read latency
w:majority + causal sessionYesYes, across nodesSmall; the practical default
w:majority + j:trueYes, through power loss—+ journal flush
⚠️ A wtimeout error is not a rollback. It says the durability level was not reached within the deadline; the write may still be applied and replicated moments later. Any retry path built on that error must be idempotent — an _id you control, or an upsert on a natural key — or you will manufacture duplicates during exactly the incident where you least want them.

STEP 3 — THE DECISION, WRITTEN DOWN

  ADR-014: Datastores for invoicing

  DECISION
    - MongoDB for invoices and customers (the operational aggregates)
    - PostgreSQL for the LEDGER only (double-entry, strict cross-row
      invariants, ~95 writes/s)
    - nightly export to the warehouse for analytics
    - Atlas Search / a search index for line-description search

  RATIONALE
    - 1,130 of 1,175 operations per second are single-aggregate reads and
      writes: exactly what the document model is for. Measured prototype:
      invoice detail 0.8 ms p50 with one index seek.
    - the ledger's invariant spans two rows and must hold under
      concurrency. Emulating it with multi-document transactions at
      95 writes/s is possible and measurably slower, and it buys a
      primitive Postgres provides natively.
    - the analytics pattern is ad hoc, multi-entity and low volume —
      the worst possible fit for a document store and a natural fit for
      the warehouse we already run.

  COSTS ACCEPTED
    - two operational datastores instead of one (runbooks, backups,
      on-call familiarity)
    - invoice-to-ledger consistency is eventual, reconciled by an
      idempotent worker with a transferId

  REVISIT WHEN
    - ledger write rate exceeds 1,000/s, or
    - analytics moves from ad hoc to a fixed set of known queries

"One database for everything" (all MongoDB)The ledger's cross-document invariant becomes transactions everywhere, and ad-hoc analytics becomes $lookup over large collections

🎯 Key Takeaways

  • The core primitive is the atomic single document. Almost every design rule in this track — embedding, guards in filters, why transactions are a last resort — follows from it.
  • Model around what one request needs, not around entities: relational asks "what are the entities?", document asks "what does one request need?"
  • Before calling duplication a problem, ask whether the value is a snapshot or a live reference — an order's prices and addresses are snapshots, and copying them is correct.
  • "Schemaless" describes the database, not your data. One measured collection held 2.1M users in six shapes, with defensive branches in fourteen call sites.
  • Adding a field is free; renaming or retyping one is a migration with the same care as SQL. Version documents and validate at moderate level from day one.
  • Mixed types fail silently: dates stored as strings are simply invisible to a date range query — 64,886 users missing from a report with no error anywhere.
  • Size for the working set, not the data. Indexes plus hot documents must fit the WiredTiger cache — measured p99 1.4 ms → 340 ms when the working set exceeded cache by 12%.
  • "Cache is full" is the design, not an alert. Watch rates: pages read into cache, dirty bytes, and above all pages evicted by application threads > 0.
  • Dropping two indexes that $indexStats showed unused for 30 days recovered 6.2 GB and restored latency without buying anything.
  • Documents are stored and rewritten whole: reading one field of a 2 MB document decompresses all of it, and every update rewrites it.
  • Write concern decides what "acknowledged" means: w:1 is lost in a failover; w:"majority" survives it and is the default since 5.0; j:true adds journal durability.
  • A wtimeout error is not a rollback — the write may still be applied, so any retry must be idempotent.
  • Default read concern is local, so majority writes plus local reads can still show you data that a rollback later discards.
  • For read-your-writes across nodes, use a causally consistent session — the practical default — rather than pinning everything to the primary.
  • Guards in the filter turn an update into a compare-and-swap. Without status: "pending" in the filter, two workers both "succeed" and one silently overwrites the other.
  • When an invariant spans documents, prefer reshaping it into one document, then idempotent replayable operations, and only then a transaction.
  • Every query is index-or-scan. A measured dashboard query examined 8.4M documents to return 50 in 41 seconds; one compound index made it 50 examined, 50 returned, 9 ms.
  • Drive the examined-to-returned ratio toward 1:1, and remember blocking sorts are capped (32 MB for find()) — they start failing under load while passing in testing.
  • Be honest about fit: excellent for document-shaped aggregates, evolving schemas and shardable write throughput; poor for ad-hoc analytical joins, high-rate cross-document invariants, and star-schema reporting.
  • "Both" is a normal answer — an operational document store plus a relational ledger and a warehouse — and an ADR with a dated revisit trigger is what stops the argument recurring.
