The Aggregation Pipeline Aggregation

What you'll master: the pipeline as a stream of documents passing through transforming stages, and why that model — rather than SQL's declarative one — explains everything about its performance and its limits; the stage catalogue with the property that actually matters for each one, whether it is streaming or blocking (a streaming stage emits as it reads; a blocking stage must consume its entire input before emitting anything, and that is where every memory failure comes from); $group in depth, including the accumulator that silently destroys pipelines — $push building an array that exceeded the 16 MB document limit on one group of 312,000 events; the expression language and its three sigils ($field, $$variable, literal), where confusing them matches nothing and raises no error; what the optimiser will and will not do for you — it moves $match toward the front, coalesces $sort+$limit into a bounded top-k (3.2 GB peak memory versus 40 MB), and gives up entirely the moment a stage references a computed field; the 100 MB per-stage memory limit, what allowDiskUse really buys you (a 19× slowdown instead of an error), and why it is usually the wrong answer; and the honest boundary — when a pipeline is the right tool and when you are writing a data warehouse inside your operational database. Prerequisites: Queries, Operators & Arrays and How Indexes Work.

Part 1 — Documents Flowing Through Stages

An aggregation pipeline is an ordered list of stages. Documents enter the first stage, each stage transforms or filters the stream, and whatever leaves the last stage is the result. That is the whole model, and it is worth holding onto because it makes the performance behaviour predictable.

  db.orders.aggregate([
    { $match: { status: "paid" } },        4.1M in  ->  310k out
    { $group: { _id: "$customerId",
                total: { $sum: "$amount" } } },
                                            310k in  ->   82k out
    { $sort:  { total: -1 } },              82k in   ->   82k out
    { $limit: 10 }                          82k in   ->     10 out
  ])

  Each stage's OUTPUT is the next stage's INPUT. Nothing else is
  shared. A stage cannot see the original documents once an earlier
  stage has reshaped them -- which is why $group destroying fields
  you later need is one of the most common pipeline bugs.

The difference from SQL is not cosmetic. SQL is declarative: you describe the result and the planner decides the order of operations. A pipeline is procedural: you specify the order, and the optimiser makes only a limited set of safe rewrites on top of it. That means a badly ordered pipeline stays badly ordered, and it means you can reason about cost by reading top to bottom.

The property that matters: streaming or blocking

StageDoesStreaming?
$matchFilters documentsStreaming — and uses indexes if it is first
$project / $set / $unset / $addFieldsReshapes each documentStreaming
$limit / $skipRow cutoffStreaming
$unwindOne document per array elementStreaming (but multiplies the stream)
$lookupLeft outer joinStreaming per input document
$sortOrders the streamBlocking — unless served by an index at the front
$groupAggregates by keyBlocking — must see every document
$bucket / $facet / $sortByCountGrouping variantsBlocking
$countCounts the streamBlocking, but O(1) memory
$out / $mergeWrites results to a collectionTerminal — must be last
🔑 Every aggregation memory problem is a blocking stage with too much input. A streaming stage handles a billion documents in constant memory. A blocking stage holds state proportional to its input — the whole sort buffer, or one entry per group key — and hits the 100 MB per-stage limit. So the entire craft of pipeline performance reduces to one instruction: reduce the stream before it reaches a blocking stage. Filter first, project away what you will not use, and limit early.

Part 2 — The Core Stages

  { $match: { status: "paid", createdAt: { $gte: cutoff } } }

  Identical syntax to find(). Two rules:
    1. Put it FIRST whenever possible -- as the first stage it
       becomes a normal indexed query with its own IXSCAN.
    2. A $match after $group can only reference the GROUPED
       fields (_id and the accumulators), because the original
       fields no longer exist in the stream.

  RESHAPING -- three stages, three different jobs

  { $project: { customer: 1, total: 1, _id: 0 } }
      Inclusive: keeps ONLY what you name. Everything else is gone.

  { $set: { margin: { $subtract: ["$total", "$cost"] } } }
      Adds or overwrites, keeps everything else. ($addFields is
      the same stage under an older name.)

  { $unset: ["internalNotes", "raw"] }
      Removes named fields, keeps everything else.

  Use $set/$unset by default. $project is the one that silently
  deletes the field a later stage needed -- it is the most common
  cause of "my $group returns null for everything".

  { $unwind: "$items" }

  { _id: 1, items: [a, b, c] }
       becomes
  { _id: 1, items: a }
  { _id: 1, items: b }
  { _id: 1, items: c }

  THE TRAP: a document with an EMPTY array, or no array at all,
  produces ZERO output documents. It silently disappears.

  { $unwind: { path: "$items",
               preserveNullAndEmptyArrays: true,
               includeArrayIndex: "idx" } }

  preserveNullAndEmptyArrays is what you almost always want. Its
  absence turns a left join into an inner join without saying so.

Part 3 — $group in Depth

  { $group: {
      _id: "$customerId",                     // the grouping key
      orders:  { $sum: 1 },                   // count
      revenue: { $sum: "$total" },
      avgValue:{ $avg: "$total" },
      first:   { $min: "$createdAt" },
      last:    { $max: "$createdAt" },
      statuses:{ $addToSet: "$status" },
      firstDoc:{ $first: "$$ROOT" }           // needs a prior $sort
  }}

  _id is the ONLY required field, and its value defines the groups:
    "$customerId"                    one group per customer
    { c: "$customerId", m: "$month" } compound key
    null                             ONE group: the whole stream
    "$$ROOT"                          one group per distinct document
AccumulatorReturnsMemory risk
$sum, $avg, $min, $max, $countA scalarNone — constant per group
$first, $lastOne value, in stream orderLow — but meaningless without a prior $sort
$addToSetArray of distinct valuesUnbounded — grows with cardinality
$pushArray of every valueUnbounded — grows with group size
$stdDevPop, $stdDevSampA scalarNone
$mergeObjectsMerged documentBounded by field count
$top, $bottom, $topN, $bottomNThe n best by a sort specBounded by n — the safe replacement for sort-then-$push
MEASURED: the $push that killed a pipeline

  { $group: { _id: "$orderId", events: { $push: "$$ROOT" } } }

  One order had 312,000 status events. Its group accumulated all
  of them into a single array -- and a $group output document is
  still a BSON document, subject to the 16 MB limit.

    BSONObjectTooLarge: the resulting document exceeded 16MB

  The whole pipeline failed. Not that group -- the pipeline. And
  it had run fine for 14 months, because no order had ever
  exceeded ~4,000 events before.

  THE FIX, if you need the top few:
    { $group: { _id: "$orderId",
                latest: { $topN: { n: 10, sortBy: { ts: -1 },
                                   output: "$$ROOT" } } } }
    Bounded by construction. Cannot fail this way.

  THE FIX, if you need them all: you do not want $group. You want
  to page through the events for one order at a time.

$first/$last need an order to be meaningful

  // WRONG -- "first" is whatever arrived first, which is
  // whatever order the scan happened to produce
  { $group: { _id: "$customerId", firstOrder: { $first: "$$ROOT" } } }

  // RIGHT -- establish the order, then take from it
  { $sort:  { customerId: 1, createdAt: 1 } },
  { $group: { _id: "$customerId", firstOrder: { $first: "$$ROOT" } } }

  // BETTER -- $topN says what it means and does not need the
  // preceding blocking sort of the WHOLE stream
  { $group: { _id: "$customerId",
              firstOrder: { $top: { sortBy: { createdAt: 1 },
                                    output: "$$ROOT" } } } }

The middle version is correct and expensive: it sorts the entire stream before grouping. The third sorts within each group, which is bounded and usually far cheaper. When you see $sort immediately followed by $group with $first, that is almost always a $top waiting to happen.

Part 4 — The Expression Language

Expressions appear inside $project, $set, $group accumulators and $expr. They have three distinct sigils, and confusing them is the single most common source of pipelines that return nothing without any error.

SyntaxMeansExample
"$field"The value of that field in the current document"$total" → 49.99
"$a.b"A nested path; on an array field it maps over elements"$items.sku" → array of skus
"$$var"A variable — from let, $map, or a system variable"$$NOW", "$$ROOT", "$$this"
"total"The literal string "total"Not a field reference at all
{ $literal: "$x" }The literal string "$x"The escape hatch when you need a leading $
  { $match: { $expr: { $eq: ["$status", "paid"] } } }   // field vs value
  { $match: { $expr: { $eq: ["status", "paid"] } } }    // "status" vs
                                                        // "paid" -- always
                                                        // false, no error

  The second one returns zero documents, every time, silently. If a
  pipeline returns nothing and you are sure the data is there,
  check your sigils first.

  CONDITIONALS

  { $set: { tier: { $switch: {
      branches: [
        { case: { $gte: ["$revenue", 10000] }, then: "platinum" },
        { case: { $gte: ["$revenue",  1000] }, then: "gold" }
      ],
      default: "standard"
  }}}}

  { $set: { name: { $ifNull: ["$displayName", "$username", "unknown"] } } }
  // first non-null wins -- the clean way to handle schema versions

  { $set: { safeRatio: { $cond: {
      if:   { $eq: ["$total", 0] },
      then: 0,
      else: { $divide: ["$profit", "$total"] }
  }}}}
  // $divide by zero is an ERROR that aborts the whole pipeline,
  // not a null. Guard every division whose denominator comes
  // from data.

  DATES -- the two things worth knowing

  { $set: { day: { $dateTrunc: { date: "$createdAt",
                                 unit: "day",
                                 timezone: "Europe/London" } } } }
  // $dateTrunc with an explicit timezone. The alternative --
  // { $dateToString: { format: "%Y-%m-%d", date: "$createdAt" } } --
  // produces a STRING that sorts correctly but is no longer a date,
  // and defaults to UTC, which silently shifts every daily rollup
  // for anyone not on UTC.

  { $set: { ageDays: { $dateDiff: { startDate: "$createdAt",
                                    endDate: "$$NOW",
                                    unit: "day" } } } }
⚠️ Timezone is a correctness bug, not a formatting preference. A daily revenue rollup grouped on UTC days assigns a 23:30 local order to the wrong day for anyone west of UTC — which one team discovered when their Monday revenue was consistently ~4% below the figure their finance system reported. Always pass an explicit timezone to $dateTrunc and $dateToString, and write down which timezone the report is defined in. "The server's" is not an answer that survives a region migration.

Part 5 — What the Optimiser Does For You

MongoDB rewrites your pipeline before executing it. The rewrites are conservative — it will only reorder when it can prove the result is identical — and knowing which ones exist tells you which pipelines you must order correctly yourself.

RewriteWhat happensWhen it is blocked
$match pushdownMoved toward the front, ideally becoming an indexed queryThe $match references a field created by an earlier stage
$sort + $limit coalescenceBecomes a bounded top-k sort holding only k documentsAny stage between them
$limit pushdownMoved earlier past stages that do not change document countPast $unwind, $group, or a filtering $match
$project pushdownUnused fields dropped early to shrink the streamRarely — this one is usually applied
$unwind + $lookup coalescenceExecuted together so the joined array is never fully materialisedAny stage between them
$sort + $groupNot coalesced — a preceding sort is executed in fullAlways; use $top/$topN instead
MEASURED: the blank line that cost 3.2 GB

  SLOW
    { $sort:  { score: -1 } },
    { $set:   { rank: "$score" } },     <- one harmless-looking stage
    { $limit: 100 }
      peak memory 3.2 GB, spilled to disk, 9.1 s

  FAST
    { $sort:  { score: -1 } },
    { $limit: 100 },
    { $set:   { rank: "$score" } }
      peak memory 40 MB, 2.4 s

  The stage between $sort and $limit blocked coalescence. Without
  it the sort holds only the top 100 documents at a time; with it,
  the sort must materialise all 4.1M.

  Rule: keep $sort and $limit ADJACENT. Do reshaping after.

  THE PUSHDOWN THE OPTIMISER CANNOT DO

  { $lookup: { from: "customers", localField: "customerId",
               foreignField: "_id", as: "cust" } },
  { $unwind: "$cust" },
  { $match: { "cust.region": "eu",
              createdAt: { $gte: cutoff } } }

  The createdAt predicate does NOT depend on the join -- but it is
  in the same $match as one that does, so the optimiser cannot
  split it and nothing moves. Every order is joined before
  anything is filtered.

  SPLIT IT YOURSELF:
    { $match: { createdAt: { $gte: cutoff } } },      // now first
    { $lookup: { ... } },
    { $unwind: "$cust" },
    { $match: { "cust.region": "eu" } }

  If August is 3% of orders, that removes 97% of the join work,
  and it is a two-line edit.

Verify all of this with db.coll.explain("executionStats").aggregate([...]), which shows the pipeline after rewriting. If a stage you expected to move is still where you put it, the explain output is where you find out — see Reading Explain Plans.

Part 6 — Memory Limits and the Boundary of the Tool

  Each blocking stage gets 100 MB by default.
  Exceed it and the pipeline FAILS:

    QueryFailedError: Exceeded memory limit for $group, but didn't
    allow external sort. Pass allowDiskUse:true to opt in.

  With { allowDiskUse: true } it spills to temporary files instead.

  MEASURED, same $group over 41M documents:
    within 100 MB                          2.1 s
    spilled to disk (allowDiskUse)        40.2 s     19x slower
    after adding a leading $match          1.4 s

  allowDiskUse converts a failure into something very slow. It is
  a safety net for genuine batch work, not a fix -- if a stage
  needs more than 100 MB on an interactive request, the pipeline
  is processing data it should have filtered out.
LimitValueWhat to do
Per blocking stage100 MBReduce the stream before it; allowDiskUse only for batch
Any single output document16 MBNever $push unbounded; use $topN
$facet sub-pipelinesEach blocking stage inside gets its own budget, but they run over the same inputPut a shared $match before the $facet, not inside each branch
$graphLookup100 MB regardless of allowDiskUseBound it with maxDepth and restrictSearchWithMatch
Result cursor16 MB per batchNormal cursor iteration handles this

When the pipeline is the wrong tool

SituationBetter answer
A dashboard runs the same rollup on every page loadPre-compute it into a summary collection with $merge on a schedule, and read that
The pipeline joins four collections and takes minutesEither denormalise what the read needs, or move the workload out of the operational database
You need a full outer join, a window over unbounded history, or complex multi-table SQLAn analytical store. Pipelines can express a lot, but expressing it is not the same as it being cheap
The result must be exact and instant on 100M+ documentsA maintained counter or rollup; no aggregation is instant at that scale

🔑 The pipeline is an excellent tool for shaping data you have already narrowed. It is a poor tool for scanning a large collection repeatedly on a user-facing request. The test I apply: if the first stage cannot use an index to reduce the input to something small, this pipeline does not belong on a request path — it belongs in a scheduled job writing to a collection that requests read directly. Interview Questions

Beginner: What is an aggregation pipeline?

An ordered list of stages. Documents flow in, each stage transforms or filters the stream, and the output of one stage is the input to the next. Nothing is shared between stages except that stream — which is why a $match after a $group can only reference the grouped fields, since the original fields no longer exist.

The important distinction from SQL is that a pipeline is procedural: you choose the order, and the optimiser only makes a limited set of provably safe rewrites. A badly ordered pipeline stays badly ordered, which is good news for reasoning about cost — you can read it top to bottom and estimate the stream size at each step.

Beginner: Why should $match come first?

Two reasons. As the first stage it becomes a normal query and can use an index — an IXSCAN instead of reading the collection. And every stage after it processes fewer documents, so the saving compounds through the whole pipeline.

The optimiser tries to move $match forward for you, but it gives up whenever the match references a field produced by an earlier stage — including when an independent predicate is bundled into the same $match as a dependent one. Splitting that $match so the independent half can lead is often a two-line change with a very large effect.

Mid: Which stages are blocking, and why does it matter?

$sort, $group, $bucket and $facet are blocking: they must consume their entire input before emitting anything. $match, $project, $set, $limit, $unwind and $lookup are streaming — they emit as they read.

It matters because every aggregation memory problem is a blocking stage with too much input. A streaming stage processes a billion documents in constant memory; a blocking stage holds state proportional to its input and hits the 100 MB per-stage limit. So the whole craft is reducing the stream before it reaches a blocking stage: filter first, project away unused fields, limit early.

The one exception worth knowing: a $sort that is first in the pipeline and served by an index is not blocking at all — the index already provides the order.

Mid: A pipeline fails with BSONObjectTooLarge after a $group. What happened?

An accumulator built an array bigger than 16 MB. A $group output document is still a BSON document and subject to the same limit as any other, so $push or $addToSet over a large group can exceed it. In the case I have seen, one order had 312,000 status events and $push: "$$ROOT" collected them all.

The failure characteristic worth noting: it had worked for 14 months, because no group had ever been that large. Unbounded accumulators do not degrade — they work perfectly until one day they fail completely.

If you need only the top few, $topN with a sortBy is bounded by construction and cannot fail this way. If you genuinely need every element of a huge group, $group is the wrong tool — page through that group's documents directly instead.

Senior: Should you use allowDiskUse: true?

Rarely, and almost never as a response to an error. It converts "this stage exceeded 100 MB" into "this stage spills to temporary files", which I have measured at 19× slower — 2.1 seconds becoming 40.2 on the same $group. Adding a leading $match instead took it to 1.4 seconds.

The reasoning: if a blocking stage needs more than 100 MB, the pipeline is processing data it should already have filtered out. The limit is doing its job as a warning. So my order of investigation is: can the first stage use an index; is there a $match that could move earlier; are we carrying fields we never use; is $sort adjacent to its $limit; and could a $topN replace an unbounded accumulator.

Where it is legitimate: a genuine batch job — a nightly rollup over a year of data — where the data volume is irreducible and slow is acceptable. There I would enable it deliberately, run it on a secondary or analytics node, and set a maxTimeMS. What I would not do is set it globally as a default, because that removes the signal that tells you a pipeline has gone wrong.

Senior: A dashboard runs six aggregations on every page load and the primary is struggling. Redesign it.

The framing I would start from: this is not an aggregation-tuning problem, it is a workload-placement problem. Interactive dashboards and operational writes want opposite things from a cache — one does large sequential scans, the other does small random reads — and no amount of pipeline tuning makes one node good at both.

First, measure what the six actually cost and how fresh they need to be. In my experience that question alone eliminates half of them: a "revenue this month" tile that recomputes on every page load almost never needs to be accurate to the second, and nobody has ever asked it to be.

Then, in order of leverage:

(1) Pre-compute. A scheduled job runs the rollups and $merges them into a summary collection; the dashboard reads single documents. This turns six aggregations per page load into six point reads, and the cost becomes proportional to the refresh interval rather than to traffic. For incremental rollups, key the merge on the period so each run only touches recent periods.

(2) Move the computation off the primary — secondaryPreferred at minimum, or a dedicated hidden/analytics member. This should be done regardless of (1), because the scheduled job itself should not churn the primary's cache.

(3) Combine what remains. If several tiles share a filter, one $facet with a common $match in front scans once instead of six times — but I would apply this after (1), because a $facet of six heavy branches is still heavy.

(4) Tune what is left: leading indexed $match, adjacent $sort/$limit, projections before joins.

The trade-off to state plainly: pre-computation buys latency with staleness, and the refresh interval is a product decision, not an engineering one. I would put the actual numbers in front of whoever owns the dashboard — "one-minute freshness costs roughly this; real-time costs a dedicated analytics node" — rather than choosing on their behalf. And I would add a visible "as of HH:MM" label, because a stale number without a timestamp is how you lose trust in a dashboard permanently.

🏋️ Exercises

1 (easy): This pipeline returns nothing. The data is definitely there. Find the bug. 
  db.orders.aggregate([
    { $match: { $expr: { $eq: ["status", "paid"] } } },
    { $group: { _id: "$customerId", n: { $sum: 1 } } }
  ])
Solution

"status" has no $, so it is the literal string "status", not a field reference. The expression compares the string "status" to the string "paid", which is false for every document. No error, no warning — just an empty result.

  { $match: { $expr: { $eq: ["$status", "paid"] } } }

But the better fix is not to use $expr at all here:

  { $match: { status: "paid" } }

$expr exists for comparing two fields of the same document ({ $gt: ["$spent", "$budget"] }) or for referencing let variables inside a $lookup. For a plain field-equals-value predicate, the query form is simpler and it can use an index — $expr comparisons are considerably weaker at index use, so using it unnecessarily costs performance as well as clarity.

The general debugging rule: if a pipeline returns empty and you are sure the data exists, check sigils before anything else, and bisect by running the pipeline one stage at a time with a $limit to see where the stream becomes empty.

2 (easy): Rewrite this to get the 5 most recent orders per customer, and explain why the obvious version is expensive. 
  db.orders.aggregate([
    { $sort: { createdAt: -1 } },
    { $group: { _id: "$customerId", orders: { $push: "$$ROOT" } } },
    { $set: { orders: { $slice: ["$orders", 5] } } }
  ])
Solution

Why the original is expensive and dangerous:

  • The $sort is a blocking sort over the entire collection before any grouping happens.
  • $push: "$$ROOT" accumulates every order for each customer into an array, complete documents included. A customer with 100,000 orders builds a 100,000-element array of full documents — likely blowing the 16 MB output-document limit, and certainly blowing the 100 MB stage limit across all groups.
  • The $slice discards 99.99% of what was just accumulated. All that work was done to throw it away.
  db.orders.aggregate([
    { $group: {
        _id: "$customerId",
        recent: { $topN: { n: 5,
                           sortBy: { createdAt: -1 },
                           output: "$$ROOT" } } } }
  ])

$topN maintains a bounded heap of 5 per group. No global sort, no unbounded array, and it cannot fail on the 16 MB limit no matter how many orders a customer has.

Two refinements worth making: add a leading $match if only some orders qualify (recent ones, non-cancelled ones), and replace output: "$$ROOT" with an explicit projection of the fields you actually display — carrying whole order documents through the heap is usually 10× more data than the page needs.

If $topN is not available (it needs MongoDB 5.2+), the pre-5.2 pattern is $sort + $group with $push + $slice — but restrict the input with a $match first so the accumulated arrays stay small. It is strictly worse; upgrading is the real answer.

3 (medium): Write a pipeline for monthly revenue by product category for 2026, in the Europe/London timezone, sorted highest first, with categories under £1,000 excluded. Orders look like { createdAt, status, items: [{ sku, categoryId, qty, unitPrice }] }.
Solution 
  db.orders.aggregate([
    // 1. reduce first -- indexed, and removes most of the collection
    { $match: {
        status: "paid",
        createdAt: { $gte: ISODate("2026-01-01T00:00:00Z"),
                     $lt:  ISODate("2027-01-01T00:00:00Z") } } },

    // 2. keep only what the rest of the pipeline needs
    { $project: { createdAt: 1, items: 1, _id: 0 } },

    // 3. one row per line item
    { $unwind: "$items" },

    // 4. bucket into local months
    { $set: {
        month: { $dateTrunc: { date: "$createdAt",
                               unit: "month",
                               timezone: "Europe/London" } },
        lineTotal: { $multiply: ["$items.qty", "$items.unitPrice"] } } },

    // 5. aggregate
    { $group: {
        _id: { month: "$month", category: "$items.categoryId" },
        revenue: { $sum: "$lineTotal" },
        units:   { $sum: "$items.qty" },
        orders:  { $sum: 1 } } },

    // 6. filter AFTER grouping -- this predicate needs the group
    { $match: { revenue: { $gte: 1000 } } },

    { $sort: { revenue: -1 } }
  ])

  index: { status: 1, createdAt: 1 }
DecisionWhy
$match first with a date rangeIndexable. { $expr: { $eq: [{ $year: "$createdAt" }, 2026] } } would compute per document and use no index
$project before $unwind$unwind multiplies the stream by the array length — carrying unused fields multiplies them too
Explicit timezoneWithout it, UTC boundaries misassign every late-evening UK order to the next month at month-end
$dateTrunc, not $dateToStringKeeps a real Date, so it sorts and formats correctly downstream. A string month sorts fine as YYYY-MM but is no longer a date
The £1,000 $match after $groupIt references revenue, which does not exist until grouping. It cannot be pushed forward and should not be
lineTotal computed before $group$sum takes one expression; computing the product in a $set keeps the group readable

The correctness question I would raise with whoever asked: does "revenue" include tax, shipping, and discounts? qty × unitPrice is a line subtotal, and it will not match the finance system's number. That mismatch surfaces two weeks after the dashboard ships, and it is cheaper to ask now.

And on money: if unitPrice is a double, $sum accumulates floating-point error across millions of rows. Store money as Decimal128 or as integer minor units — see Documents, BSON & _id.

4 (medium): This pipeline works but is slow and spills to disk. Reorder it, explaining each move. 
  db.events.aggregate([
    { $set:    { day: { $dateTrunc: { date: "$ts", unit: "day" } } } },
    { $lookup: { from: "users", localField: "userId",
                 foreignField: "_id", as: "u" } },
    { $unwind: "$u" },
    { $sort:   { ts: -1 } },
    { $set:    { label: { $concat: ["$type", " by ", "$u.name"] } } },
    { $limit:  100 },
    { $match:  { type: "purchase",
                 ts: { $gte: ISODate("2026-08-01") } } }
  ], { allowDiskUse: true })
Solution

What the original does: computes a day field for every event ever recorded, joins every one of them to a user, sorts all of them, builds a label for all of them, takes 100 — and then filters. The final $match is applied to 100 documents, so the result is also almost certainly wrong: it returns whichever of the 100 most recent events happen to be purchases, not the 100 most recent purchases.

  db.events.aggregate([
    // 1. filter FIRST -- indexable, and correct
    { $match: { type: "purchase",
                ts: { $gte: ISODate("2026-08-01") } } },

    // 2. sort + limit ADJACENT -> bounded top-k
    { $sort:  { ts: -1 } },
    { $limit: 100 },

    // 3. now join -- 100 lookups instead of millions
    { $lookup: { from: "users", localField: "userId",
                 foreignField: "_id", as: "u" } },
    { $unwind: { path: "$u", preserveNullAndEmptyArrays: true } },

    // 4. reshape last, on 100 documents
    { $set: { day:   { $dateTrunc: { date: "$ts", unit: "day",
                                     timezone: "Europe/London" } },
              label: { $concat: ["$type", " by ",
                                 { $ifNull: ["$u.name", "unknown"] }] } } }
  ])

  index: { type: 1, ts: -1 }
  // allowDiskUse no longer needed
MoveEffect
$match to the frontBecomes an indexed query. Also fixes the correctness bug
$sort+$limit made adjacentCoalesces into a bounded top-100 sort instead of materialising the whole stream — this is what was spilling
$lookup after the limit100 joins instead of millions
$set stages lastComputed on 100 documents instead of every event
preserveNullAndEmptyArrays addedThe original silently dropped events whose user had been deleted — an inner join nobody asked for
allowDiskUse removedIt was masking the ordering problem

The general lesson: reduce, then order, then enrich. Every stage that adds or computes should sit after every stage that removes. And when a filter appears last, check the semantics before optimising — a pipeline that is slow and wrong is usually slow because it is wrong.

5 (hard): Build a cohort retention report: for users who signed up in each month of 2026, what percentage were still active 1, 3 and 6 months later? Collections: users { _id, createdAt } and events { userId, ts } (400M documents).
Solution

The first thing to establish is that this should not be a live pipeline. 400M events joined against users, per dashboard load, on an operational cluster, is not a query — it is a batch job wearing a query's clothes. So the design has two parts: a nightly job that produces a small derived collection, and a trivial read against it.

  STEP 1 (nightly) -- collapse 400M events into monthly activity
  db.events.aggregate([
    { $match: { ts: { $gte: lastRunWatermark } } },   // INCREMENTAL
    { $project: {
        userId: 1,
        month: { $dateTrunc: { date: "$ts", unit: "month",
                               timezone: "UTC" } } } },
    { $group: { _id: { u: "$userId", m: "$month" } } },  // dedupe
    { $merge: { into: "user_active_months",
                on: "_id",
                whenMatched: "keepExisting",
                whenNotMatched: "insert" } }
  ], { allowDiskUse: true })

  // legitimate use of allowDiskUse: a batch job, on a secondary,
  // over irreducible data volume.
  // Incremental via the watermark: only new events each night, so
  // the nightly cost is proportional to NEW data, not to history.

  STEP 2 (nightly) -- build the cohort matrix
  db.users.aggregate([
    { $match: { createdAt: { $gte: ISODate("2026-01-01T00:00:00Z"),
                             $lt:  ISODate("2027-01-01T00:00:00Z") } } },
    { $set: { cohort: { $dateTrunc: { date: "$createdAt",
                                      unit: "month" } } } },
    { $lookup: {
        from: "user_active_months",
        let: { uid: "$_id", c: "$cohort" },
        pipeline: [
          { $match: { $expr: { $eq: ["$_id.u", "$$uid"] } } },
          { $project: { _id: 0,
              offset: { $dateDiff: { startDate: "$$c",
                                     endDate: "$_id.m",
                                     unit: "month" } } } },
          { $match: { offset: { $in: [1, 3, 6] } } }
        ],
        as: "act" } },
    { $group: {
        _id: "$cohort",
        size: { $sum: 1 },
        m1: { $sum: { $cond: [ { $in: [1, "$act.offset"] }, 1, 0 ] } },
        m3: { $sum: { $cond: [ { $in: [3, "$act.offset"] }, 1, 0 ] } },
        m6: { $sum: { $cond: [ { $in: [6, "$act.offset"] }, 1, 0 ] } } } },
    { $set: {
        r1: { $round: [ { $multiply: [ { $divide: ["$m1", "$size"] },
                                       100 ] }, 1 ] },
        r3: { $round: [ { $multiply: [ { $divide: ["$m3", "$size"] },
                                       100 ] }, 1 ] },
        r6: { $round: [ { $multiply: [ { $divide: ["$m6", "$size"] },
                                       100 ] }, 1 ] } } },
    { $sort: { _id: 1 } },
    { $merge: { into: "cohort_retention", on: "_id",
                whenMatched: "replace" } }
  ], { allowDiskUse: true })

  STEP 3 -- the dashboard
  db.cohort_retention.find().sort({ _id: 1 })      // 12 documents
DecisionWhy
Two-stage derivationStep 1 does the 400M-document work once and incrementally; step 2 operates on a collection roughly the size of users × active months
Watermark on step 1Nightly cost is proportional to new events, not to history. Without it the job grows unboundedly and eventually cannot finish overnight
whenMatched: "keepExisting"Makes step 1 idempotent — a re-run after a failure cannot double-count
Sub-pipeline $lookup with a $match insideFilters within the join rather than materialising every activity month per user
No division without a guardsize is $sum: 1 over a non-empty group, so it cannot be zero — worth stating explicitly, because a data-derived denominator would need a $cond

The definitional questions I would settle before writing any of it, because they change the numbers more than any optimisation: does "active" mean any event, or a meaningful one (a purchase, a session over 30 seconds)? Is month 1 "the calendar month after signup" or "days 30–60"? Are cohorts counted from signup or from first activity? Every retention report I have seen disagree with another one disagreed on exactly these, not on the SQL.

And the caveat on incomplete cohorts: the December 2026 cohort cannot have a 6-month number yet. The report must render that as blank, not as 0% — a zero there looks like catastrophic churn and will be escalated within a day.

6 (hard): A team has 40 aggregation pipelines across the codebase, several are slow, and nobody knows which run where. Design the programme to get this under control.
Solution

Step 1 — inventory, because you cannot triage what you cannot see. The profiler already records aggregations; group by queryHash to get shape, frequency, mean and total time, plus whether it spilled.

  db.system.profile.aggregate([
    { $match: { "command.aggregate": { $exists: true } } },
    { $group: { _id: { hash: "$queryHash", ns: "$ns" },
                n: { $sum: 1 }, total: { $sum: "$millis" },
                avg: { $avg: "$millis" },
                spilled: { $max: "$usedDisk" },
                sample: { $first: "$command.pipeline" } } },
    { $sort: { total: -1 } }
  ])

Step 2 — classify each one by what it is for, which determines the fix far more than its current shape does:

ClassSignalRight answer
Point transformLeading indexed $match, small inputLeave it alone. These are fine and most of the 40 will be here
Interactive rollupRuns per page load, scans a lotPre-compute with $merge; the dashboard reads documents
Batch/reportRuns on a schedule, large volumeMove to a secondary, set maxTimeMS, make it incremental with a watermark
Accidental analyticsJoins 3+ collections, minutes long, on the primaryThe real conversation: this workload does not belong here

Step 3 — a mechanical review checklist, applied to the slow ones. Every item is objective, so it can be delegated and does not need the original author: is the first stage an indexed $match; is any $match splittable so its independent half can lead; are $sort and $limit adjacent; is there a projection before any $unwind or $lookup; is every $push/$addToSet bounded; does every $unwind declare preserveNullAndEmptyArrays deliberately; does every date expression pass a timezone; is allowDiskUse masking a missing filter.

Step 4 — prevent recurrence. A CI check that runs each registered pipeline against a seeded dataset with explain and fails on a leading COLLSCAN or a spill; plus maxTimeMS as a required argument in a shared helper, so no pipeline can be written without one.

What I would deliver first and what I would resist. The inventory alone is a day's work and reorders everyone's priorities — in every case I have seen, the pipeline people were worried about was not in the top five by total cost. I would resist a "rewrite all 40" project: most will be in the first class and are fine, and a mass rewrite risks correctness bugs in pipelines that currently produce correct numbers. Fix the ranked top five, ship the checklist and the CI gate, and let the rest be reviewed as they are touched.

The one thing I would escalate rather than fix quietly: anything in the "accidental analytics" class. Those are not bugs — they are a signal that reporting has grown into the operational database without anyone deciding that it should. That is a capacity and architecture conversation with a cost attached, and it will only get more expensive to have later.

🎯 Key Takeaways

  • A pipeline is a stream through ordered stages. Each stage's output is the next stage's only input — which is why $match after $group can only see grouped fields.
  • Streaming versus blocking is the property that matters. Every memory failure is a blocking stage ($sort, $group, $facet) with too much input.
  • Reduce before you compute. Filter first, project away unused fields, limit early — in that order.
  • A $match that mixes an independent predicate with a dependent one cannot be pushed forward. Split it yourself; it is often a two-line change removing 97% of the work.
  • Keep $sort and $limit adjacent. One stage between them blocked coalescence and cost 3.2 GB peak memory versus 40 MB.
  • Prefer $set/$unset to $project — inclusive projection silently drops the field a later stage needed.
  • $unwind deletes documents with empty or missing arrays unless preserveNullAndEmptyArrays is set. It turns a left join into an inner join silently.
  • Unbounded $push/$addToSet will eventually hit the 16 MB output limit — one group of 312,000 events failed a pipeline that had worked for 14 months.
  • $topN/$top are bounded by construction and replace both the unbounded accumulator and the global sort before $group.
  • $first is meaningless without a defined order.
  • Three sigils: $field, $$variable, literal. Confusing them matches nothing and raises no error.
  • $divide by a data-derived zero aborts the whole pipeline. Guard it with $cond.
  • Always pass an explicit timezone to date expressions. UTC day boundaries made one rollup 4% low every Monday.
  • Blocking stages get 100 MB. allowDiskUse turns a failure into a 19× slowdown — it is for batch jobs, not a fix for a badly ordered pipeline.
  • $graphLookup ignores allowDiskUse and is capped at 100 MB regardless.
  • Verify with explain, which shows the pipeline after rewriting. If a stage did not move, that is where you find out.
  • If the first stage cannot use an index to shrink the input, the pipeline does not belong on a request path — it belongs in a scheduled job writing to a collection that requests read directly.
