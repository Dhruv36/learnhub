Sharding & Shard Keys Distribution

What you'll master: the decision before the mechanism — sharding is the most expensive change you can make to a MongoDB deployment, and a large majority of clusters that shard would have been better served by an index, a retention policy, or a bigger machine; how routing actually works, because every performance property of a sharded cluster follows from "mongos can only target a query that contains the shard key"; the three properties a shard key must have — cardinality, low frequency, and non-monotonicity — and what each one looks like when it is missing (a monotonically increasing key sent 100% of writes to one shard, so an 8-shard cluster had the write throughput of one); ranged versus hashed versus compound keys, and why the compound key is almost always the right answer; the measured difference between a targeted and a broadcast query (2 ms on one shard, 380 ms across twelve, and it gets worse as you add shards); chunks, the balancer, jumbo chunks and zones; resharding, what it costs and why "we can always change the key later" is a much weaker promise than it sounds; and the operational surprises — orphaned documents, the unique-index restriction that constrains the key choice itself, and why aggregation and transactions behave differently once the collection is split. Prerequisites: How Indexes Work, Replica Sets & Read Concerns and Embed vs Reference.

Part 1 — Should You Shard At All?

Sharding is horizontal scaling, and it is the correct answer to exactly two problems: a working set that cannot fit in one machine's RAM, and a write rate that exceeds one primary. Everything else it is proposed for has a cheaper answer.

Stated reasonUsually the real answer
"Queries are slow"Indexes. Sharding a badly-indexed collection makes every shard do the same bad scan
"The collection is huge"Size alone is fine. What matters is the working set. A 4 TB collection with a 20 GB hot set runs happily on one node
"We're running out of disk"A retention policy or archival tier. Sharding to store cold data is expensive storage
"Reads are overwhelming the primary"Secondary reads, or a hidden analytics member
"We might need it later"Then decide later — but design the schema so a good shard key exists
"The working set exceeds RAM on the largest instance we can buy"Shard. This is the real reason
"Write throughput exceeds one primary and the writes cannot be batched"Shard. The other real reason
  WHAT SHARDING COSTS, before you get any benefit

  Operationally
    - config server replica set (3 more nodes)
    - mongos routers (2+, and they are a component that fails)
    - every shard is itself a replica set: 12 shards = 36+ nodes
    - backup, monitoring and upgrade complexity multiplied

  In the data model
    - the shard key is IMMUTABLE per document (the value can be
      changed since 4.2, but the KEY DEFINITION requires
      resharding)
    - unique indexes must be prefixed by the shard key
    - queries without the shard key broadcast to every shard
    - transactions spanning shards cost ~15x

  MEASURED: a team sharded a 900 GB collection to fix p99 latency.
  The real cause was two unindexed queries. After sharding, the
  same queries broadcast to 6 shards; p99 got WORSE (240 ms ->
  410 ms). Adding the two indexes -- on the unsharded collection
  they had restored from backup -- gave p99 of 8 ms.
⚠️ Shard when you have measured that you must, not when the collection looks big. The diagnostic sequence is: is the working set larger than RAM (check wiredTiger.cache["pages evicted by application threads"] > 0); are the queries indexed; is there a retention policy; are reads on the primary that need not be. If all four are addressed and you still cannot fit, shard. Sharding a cluster with a query problem multiplies the query problem by the number of shards.

Part 2 — How Routing Works

  APPLICATION
      |
   mongos (router -- stateless, cached routing table)
      |
      +-- config servers (replica set): the CHUNK MAP
      |     "shard key range [a, b) lives on shard 2"
      |
      +-- shard 1 (replica set)   chunks: [minKey, 100), [400, 700)
      +-- shard 2 (replica set)   chunks: [100, 400)
      +-- shard 3 (replica set)   chunks: [700, maxKey)

  A collection is split into CHUNKS by shard key range (default
  128 MB). The config servers record which chunk lives where.
  mongos consults that map to decide where to send an operation.

  THE ONE RULE EVERYTHING FOLLOWS FROM

  query CONTAINS the shard key  ->  mongos knows the chunk
                                ->  TARGETED to one shard
  query LACKS the shard key     ->  mongos cannot know
                                ->  BROADCAST (scatter-gather) to
                                    EVERY shard, results merged

  MEASURED, 12 shards, orders sharded on { customerId: "hashed" }

    find({ customerId: c, status: "paid" })
      shardsTargeted 1     2 ms      total cluster work: 1 op
    find({ status: "paid", createdAt: { $gte: x } })
      shardsTargeted 12  380 ms      total cluster work: 12 ops

  At 200 requests/sec the second query occupies 2,400 shard
  operations per second. And adding a 13th shard makes each such
  query MORE expensive, not less -- the exact opposite of what
  sharding is for.

That last point is worth stating plainly: a workload dominated by broadcast queries does not scale with shard count. You pay the operational cost of sharding and get negative returns on the queries that matter. The shard key is therefore chosen by looking at your queries, not at your data distribution.

  WHY THE COMPOUND KEY WINS

  { tenantId: 1, createdAt: 1 }

  - WRITES distribute, because different tenants hash into
    different chunk ranges. Within one tenant writes are
    monotonic, but that only concentrates on that tenant's own
    chunks, not on the whole cluster.
  - QUERIES targeted, because every query in a multi-tenant app
    already filters by tenant.
  - RANGES work within a tenant: "this tenant's orders since
    August" hits one shard, in order.
  - JUMBO CHUNKS are avoidable, because createdAt gives the
    splitter something to divide a large tenant on. With
    { tenantId: 1 } alone, one huge tenant is one unsplittable
    chunk.

  That last point is the one people discover too late: a
  single-field key on a skewed field CANNOT be split further, and
  a jumbo chunk cannot be migrated.
🔑 Derive the shard key from your query patterns, in this order. (1) List the queries by frequency. (2) Find the field that appears in nearly all of them — in most products it is a tenant, customer or user id. (3) Check its skew; if one value dominates, hash it or add a second field. (4) Add a second field that gives the splitter somewhere to divide and supports your range queries. (5) Verify that every unique index you need can be prefixed by this key — because if it cannot, the key is not viable regardless of how good it looks.

Part 4 — Chunks, the Balancer, and Zones

    -> chunk counts per shard, per collection

  db.getSiblingDB("config").chunks.aggregate([
    { $group: { _id: "$shard", n: { $sum: 1 } } } ])

  The balancer moves chunks between shards to keep counts even.
  Since 6.0 it balances by DATA SIZE rather than chunk count,
  which is a meaningful improvement -- equal chunk counts with
  unequal chunk sizes was a common source of skew.

  A migration copies the chunk, then updates the config map. The
  source's copies become ORPHANS until the range deleter removes
  them.

Part 5 — Resharding, and Why "We Can Change It Later" Is Weak

  Before 5.0: changing the shard key meant dumping the collection,
  dropping it, re-sharding and restoring. An outage measured in
  hours or days.

  5.0+: db.adminCommand({ reshardCollection: "shop.orders",
                          key: { tenantId: 1, createdAt: 1 } })

  What it actually does: builds a complete new copy of the
  collection distributed by the new key, keeps it in sync from the
  oplog, then cuts over in a brief critical section.

  MEASURED, 900 GB collection, 6 shards:
    duration                       26 hours
    peak extra disk                +100% (both copies exist)
    CPU on every shard             +35% for the duration
    write latency during the run   p99 4 ms -> 21 ms
    critical section at cutover    ~2 s of blocked writes
    requirement                    enough free disk on EVERY
                                   shard for the new copy

So resharding is possible, and it is a real operation with a real cost — not a casual correction. The practical consequence is that the shard key deserves the care of a schema decision that will be expensive to revisit, even though it is no longer irreversible.

Before sharding, verifyWhy
Every unique index can be prefixed by the shard keyUniqueness cannot be enforced across shards. If you need { email: 1 } unique globally and shard on tenantId, you cannot have it
The key appears in >90% of query volumeOtherwise the workload broadcasts and does not scale
No value exceeds a few percent of documentsSkew becomes jumbo chunks
Transactionally-related documents share a key valueCross-shard transactions cost ~15×
You have measured the distribution on production dataSkew is invisible in staging
  THE UNIQUE INDEX CONSTRAINT, concretely

  Sharded on { tenantId: 1, orderId: 1 }

  db.orders.createIndex({ orderNumber: 1 }, { unique: true })
    -> ERROR. A unique index must be prefixed by the shard key.

  db.orders.createIndex({ tenantId: 1, orderNumber: 1 },
                        { unique: true })
    -> OK. Unique WITHIN a tenant. Often exactly what you wanted.

  If you need a GLOBALLY unique value on a sharded collection,
  the options are: make it the shard key itself, or enforce it in
  a separate small unsharded collection that acts as a registry.
  Neither is free, and discovering the need after sharding is
  much worse than before.

  THE MONITORING THAT MATTERS ON A SHARDED CLUSTER

  1. shardsTargeted distribution
       What fraction of queries are targeted vs broadcast? This is
       THE health metric for a sharded cluster and almost nobody
       tracks it. A rising broadcast fraction means the workload is
       drifting away from the shard key.

  2. per-shard data size and ops
       sh.status() plus per-shard opcounters. Divergence means
       skew, a jumbo chunk, or a hot tenant.

  3. balancer activity
       config.changelog for migration frequency and failures. A
       balancer that never runs and one that runs constantly are
       both problems.

  4. orphan counts
       Range deletions that never complete leave disk consumed and
       counts inflated.

  5. jumbo chunk count
       config.chunks with jumbo: true. Any non-zero value is a
       future incident.
🔑 The single number that tells you whether sharding is working is the fraction of queries targeted to one shard. If it is high, adding shards adds capacity. If it is low, you have built a distributed system that gets slower as it grows, and no amount of index tuning fixes it — only a different shard key, or moving that workload somewhere else. Track it from day one, because by the time it is obvious, resharding a large collection is a 26-hour operation.

Interview Questions

Beginner: What is a shard key and why does it matter so much?

It is the field or fields whose values determine which chunk — and therefore which shard — a document lives on. It matters because mongos can only route a query to a specific shard if the query contains the shard key. Without it, the query is broadcast to every shard and the results merged.

That single property drives everything: whether writes distribute or pile onto one shard, whether reads touch one machine or all of them, whether range queries work, and whether the cluster gets faster or slower as you add shards. A workload dominated by broadcast queries does not scale with shard count — it degrades.

Beginner: Why is sharding on _id usually a bad idea?

Because ObjectIds embed a timestamp and therefore increase monotonically. Every new document has a shard key larger than every existing one, so it belongs in the highest chunk, which lives on exactly one shard. All inserts go there.

In a measured case an 8-shard cluster offered 40,000 inserts/sec: one shard ran at 98% CPU handling all of them, and seven sat at 3%. The cluster's write throughput equalled a single shard's. Reads were fine because historical data was spread, which is why a read-only load test did not catch it.

If _id is the natural key, { _id: "hashed" } distributes writes — at the cost of losing range queries on _id.

Mid: Compare ranged, hashed and compound shard keys.

Ranged keeps documents with adjacent key values together, so range queries can be targeted. The risk is distribution: on a monotonic field it creates a write hotspot, and on a skewed field it creates jumbo chunks.

Hashed distributes writes evenly by hashing the value, which solves the hotspot completely. The cost is that hashing destroys ordering, so every range query broadcasts to every shard.

Compound is usually the right answer, and { tenantId: 1, createdAt: 1 } is the canonical shape. Different tenants land in different chunks so writes distribute; queries filter by tenant so they target one shard; range queries work within a tenant; and the second field gives the chunk splitter something to divide on, which is what prevents a large tenant from becoming an unsplittable jumbo chunk.

That last benefit is the one people discover too late. With { tenantId: 1 } alone, every document for one tenant has an identical shard key value, so they form one chunk that can never be split or migrated — I have seen that reach 340 GB.

Mid: What is a jumbo chunk and how do you avoid one?

A chunk that has grown beyond the chunk size but cannot be split, because every document in it has the same shard key value. There is no boundary to split on. Because it exceeds the size limit it also cannot be migrated, so the shard holding it stays permanently oversized — in one case 78% disk against 12% on its peers.

The cause is always skew on a low-cardinality or single-field key. Prevention is to include a second, high-cardinality field in the key so the splitter always has somewhere to divide — a timestamp, an order id, anything that varies within a heavy value.

Once you have one, the fix is resharding, which for a 900 GB collection took 26 hours and required double the disk on every shard while it ran. Which is a good argument for measuring the distribution of your candidate key on production data before sharding: skew is invisible in staging.

Senior: A team wants to shard because their collection is 2 TB. How do you respond?

Size alone is not a reason. What matters is the working set — the portion actually being read — and a 2 TB collection with a 20 GB hot set runs comfortably on one node. So I would ask for four measurements before discussing shard keys at all.

(1) Is the working set exceeding RAM? wiredTiger.cache["pages evicted by application threads"] > 0 is the definitive signal. If it is zero, this is not a capacity problem.

(2) Are the queries indexed? Sharding multiplies a query problem by the number of shards. In a case I have seen, a team sharded 900 GB to fix p99 latency; the real cause was two unindexed queries, sharding made p99 worse (240 → 410 ms because the queries then broadcast), and adding the two indexes gave 8 ms.

(3) Is there a retention policy? Much of a 2 TB collection is often data nobody queries. Archiving or time-bucketing is far cheaper than distributing it.

(4) Is read load on the primary that need not be? Reports and analytics on a hidden member is a config change, not an architecture change.

If all four are addressed and it still does not fit, then shard — and at that point the conversation is entirely about the shard key, because that is the decision that is expensive to revisit. I would want the query frequency distribution, the candidate key's value distribution on production data, and a list of every unique index the application depends on, since a globally unique constraint that cannot be prefixed by the key is a blocker discovered far too late otherwise.

What I would say about the cost: 12 shards is 36+ nodes plus config servers plus routers, and it multiplies backup, monitoring and upgrade complexity. That is a permanent operational commitment, and it should be made on evidence rather than on the size of a number.

Senior: Design the shard key for a multi-tenant SaaS where 5% of tenants hold 70% of the data.

The skew is the whole problem, and it rules out the obvious answer. { tenantId: 1 } gives perfect query targeting and creates jumbo chunks for the large tenants — one shard key value per tenant means one unsplittable chunk per tenant, and the biggest ones will be enormous.

My answer: { tenantId: 1, _id: 1 } (or { tenantId: 1, createdAt: 1 } if range-by-time within a tenant is a common query).

PropertyHow it is satisfied
Query targetingEvery query in a multi-tenant app filters by tenant, so nearly everything targets one shard
SplittabilityThe second field gives the splitter boundaries within a large tenant, so a big tenant becomes many chunks rather than one jumbo one
Write distributionAcross tenants, good. Within one large tenant, _id is monotonic — but that concentrates only on that tenant's own top chunk, not on the cluster
Range queriesWork within a tenant, which is the only scope that makes sense here

The residual problem, which I would name explicitly rather than let it surprise anyone: a single tenant that is genuinely larger than one shard can hold. The compound key spreads that tenant's chunks across shards, so capacity is fine — but its queries will then broadcast across those shards, and it is the customer most likely to complain. That is the case for zones: pin the largest tenants to dedicated shards so their load is isolated and their queries stay local, and let the long tail share the rest.

What I would verify before committing: the exact distribution on production data (not staging), whether any unique index needs to be global rather than per-tenant, and whether any transaction spans tenants — if one does, it will be a cross-shard transaction at 15× the cost, and it may be a modelling problem worth fixing first.

And the operational commitment: track the targeted-query fraction and the jumbo chunk count from day one. Both are leading indicators, and both are cheap to watch and expensive to discover late.

  a) { ts: 1 }
  b) { eventType: 1 }
  c) { _id: "hashed" }
  d) { userId: "hashed", ts: 1 }
Solution
VerdictWhy

b) { eventType: 1 }BadLow cardinality — perhaps 20 values, so at most 20 chunks, and event types are always skewed (page views dwarf everything). Guaranteed jumbo chunks

Hashing removes that. The cost is that cross-user range queries on userId broadcast — which no product actually needs.

The question I would ask before finalising (d): what fraction of queries filter by user? If a large share are "all events of type X in the last hour", none of these keys helps, and the honest answer may be that this workload belongs in a time-series collection or an analytics store rather than a sharded operational collection.

3 (medium): A sharded cluster's p99 got worse after adding two shards. Explain how that is possible and what you would check.
Solution

It is possible because broadcast queries get more expensive with every shard added. A query without the shard key is sent to every shard, and the response time is bounded by the slowest shard, not the average. With more shards there are more chances that one of them is momentarily slow — a compaction, a cache miss, an unlucky GC — so the tail latency of a scatter-gather query rises with fan-out even when every individual shard is healthy.

There is also a straightforward capacity effect: each broadcast query now occupies more shards, so total cluster work per query has gone up.

What I would check, in order:

  1. shardsTargeted distribution
     What fraction of queries hit one shard versus all? If the
     broadcast fraction is high, this is the explanation and no
     tuning fixes it -- only the shard key.

  2. per-shard latency during a slow request
     Is one shard consistently the straggler? That points at
     skew or hardware rather than fan-out.

  3. balancer activity
     Adding shards triggers a large migration wave. Migrations
     consume I/O and can cause replication lag on both source
     and destination -- p99 during a rebalance is not steady
     state. Check config.changelog for migration volume and
     whether it has settled.

  4. mergeType on aggregations
     If pipelines use $facet/$lookup/$graphLookup, the merge
     happens on one node and more shards means more data
     shipped to it.

The most likely answer is (3) if this is recent — a rebalance after adding shards runs for hours or days and degrades latency while it does. I would re-measure once config.changelog shows migrations have stopped before concluding anything.

If it persists, the finding is (1), and it is a serious one: the workload does not match the shard key, so the cluster gets slower as it grows. The remedies are resharding onto a key the queries actually contain, or moving the broadcast workload elsewhere — a materialised view, an analytics store — so it stops competing with the targeted traffic.

4 (medium): You must shard a collection that has a globally unique email field and is queried mostly by { accountId }. Resolve the conflict.
Solution

The conflict is real and structural: a unique index on a sharded collection must be prefixed by the shard key, because uniqueness cannot be checked across shards without a global lookup on every write. Sharding on accountId means the only unique indexes available are { accountId: 1, ... } — i.e. unique within an account, not globally.

OptionResultTrade-off
1. Shard on { email: 1 } (or hashed)Global uniqueness preserved by the shard key itselfEvery accountId query broadcasts — which is the dominant query. Wrong trade
2. Registry collection: a small unsharded emails { _id: email, userId } collection with the unique constraintGlobal uniqueness enforced; main collection shards on accountIdTwo writes to keep in step. Needs a transaction or an idempotent claim-then-write, plus a reconciler
3. Accept per-account uniqueness{ accountId: 1, email: 1 } uniqueOnly valid if the product genuinely allows the same email in different accounts — surprisingly often it does
4. Do not shard this collectionUsers are usually far smaller than the collection driving the sharding decisionNone, if it fits. Often overlooked

I would check option 4 first. Sharding is per-collection, and a users collection is typically orders of magnitude smaller than the events or orders collection that actually needs distributing. If users fits on one shard, the entire conflict disappears — and unsharded collections in a sharded cluster live on the primary shard and work normally.

If users genuinely must be sharded, I would take option 2, implemented as a claim: insert into the registry first (the unique index makes the claim atomic and a duplicate fails cleanly), then write the user document, then a reconciler sweeps registry entries with no corresponding user. That ordering means the failure mode is an orphaned claim — recoverable — rather than two users with the same email, which is not.

The decision I would escalate rather than make alone: option 3. "Can two accounts share an email address?" is a product question with real consequences for login, password reset and support, and engineers should not answer it silently because it makes the sharding easier.

5 (hard): Plan the migration of a 900 GB unsharded collection to a sharded cluster, with a 5-minute maximum write interruption.
Solution

The good news: converting an existing replica set into a sharded cluster does not require moving the data. The replica set becomes the first shard, and the collection is sharded in place. The risk is not the conversion — it is the rebalance that follows, and the shard key decision, which is the part that cannot be undone cheaply.

  PHASE 0 -- decide the key, on production data (days, not hours)
    - query frequency distribution: which field is in >90% of
      queries?
    - candidate key's value distribution: does any value exceed
      a few percent?
    - every unique index: can each be prefixed by the key?
    - do any transactions span key values?
    This phase is the whole project. Everything else is mechanics.

  PHASE 1 -- add infrastructure (no downtime)
    config server replica set, mongos routers.
    Existing replica set becomes shard 1.

  PHASE 2 -- point the application at mongos (the interruption)
    A rolling deploy of the connection string. Each instance
    reconnects; with retryable writes and a rolling restart this
    is seconds per instance, not a global outage.
    -- this is the only step that touches the application --

  PHASE 3 -- create the shard key index, unsharded
    Build it as a rolling index build BEFORE sharding, so
    shardCollection does not have to.

  PHASE 4 -- PRE-SPLIT, then shard
    shardCollection with presplitHashedZones (hashed keys), or
    manual split points derived from the distribution measured
    in phase 0.
    Without pre-splitting, everything starts in one chunk on
    shard 1 and the balancer spends days catching up while
    serving traffic.

  PHASE 5 -- add shards, one at a time
    Each addition triggers migrations. Restrict the balancer to
    off-peak windows; watch replication lag and p99 between
    additions. Expect degraded latency DURING migrations -- this
    is the long tail of the project, measured in days.

  PHASE 6 -- verify
    shardsTargeted fraction on real traffic. If it is low, the
    key was wrong and it is far better to know now, while the
    per-shard data is still small enough to reshard cheaply.

Meeting the 5-minute constraint: only phase 2 interrupts writes, and a rolling connection-string deploy keeps that to seconds per instance. What I would not promise is that latency is unaffected for the whole project — phase 5 degrades p99 for as long as migrations run, and conflating "no downtime" with "no impact" is how these projects lose trust.

What I would rehearse first: the whole sequence on a restored copy of production, at full size. The measurements that matter — how long the rebalance takes, what it does to p99, whether the key produces even distribution — cannot be obtained any other way, and getting them costs one restore.

Rollback: honest answer — there is no clean un-shard. Up to phase 3 everything is reversible by pointing the application back at the replica set. After shardCollection, reversal means a dump and restore. That asymmetry is why phase 0 deserves days.

6 (hard): Design the monitoring and review process that would catch a bad shard key before it becomes a 26-hour resharding operation.
Solution

The design constraint: every symptom of a bad shard key is visible early and cheap to fix early, and invisible-until-catastrophic if nobody looks. So the process is mostly about watching four leading indicators from day one.

MetricCatchesAlert on
Targeted-query fraction (shardsTargeted == 1 ÷ total)The workload drifting away from the key — the single most important signal, and almost nobody tracks itAny sustained decline; a hard floor (say 90%)
Per-shard write rate varianceA monotonic hotspot, immediately and unmistakablyAny shard above ~2× the mean
Jumbo chunk countSkew that has already become unfixable-by-balancerAny non-zero value. One jumbo chunk is a future incident
Per-shard data size spreadSkew before it reaches jumboMax/min ratio above ~1.5
Balancer migration volume and failuresA balancer fighting a hotspot, or unable to runSustained high migration rate; any repeated failure

The pre-sharding review, as a required checklist rather than a discussion — every item is a measurement, so it can be answered rather than debated:

  1. Query frequency table from the profiler. Which field
     appears in what fraction of query volume?
  2. Candidate key value distribution on PRODUCTION data.
     Top 10 values by document count, as a percentage.
  3. Monotonicity check: does the key's max value increase over
     time?
  4. Every unique index, and whether it can be prefixed by the
     key. This is a hard blocker, not a preference.
  5. Every transaction: does it span key values?
  6. Estimated chunk count at target size: key cardinality must
     exceed the planned shard count by a wide margin.

Plus a synthetic pre-check that costs nothing: before sharding, run the candidate key's distribution through a hash and bucket it into N buckets to simulate N shards. If the buckets are uneven on production data, the key is wrong — and you have learned it without touching the cluster.

What I would deliberately not rely on: a load test. Skew and monotonicity problems are properties of real data distributions and real query mixes, and synthetic tests reproduce neither. The 8-shard cluster with one-shard write throughput passed its load test, because the load test only measured reads.

The organisational half: a named owner for the sharded cluster's health dashboard, and a standing item to review the targeted-query fraction whenever a significant new query is added. Shard keys do not usually go bad on their own — they go bad because a new feature introduces a query pattern nobody checked against the key, and that is a review question, not a monitoring one.

🎯 Key Takeaways

  • Shard for working set or write throughput, nothing else. Sharding a query problem multiplies it — one team went 240 ms → 410 ms and fixed it with two indexes instead.
  • Collection size is not a reason. A 2 TB collection with a 20 GB working set runs on one node.
  • Everything follows from routing: a query containing the shard key targets one shard; one without it broadcasts to all.
  • Broadcast-heavy workloads get worse as you add shards — 2 ms targeted versus 380 ms across twelve.
  • A shard key needs cardinality, low skew, non-monotonicity, and presence in your queries.
  • A monotonic key sends every insert to one shard — 8 shards with the write throughput of one, and a read-only load test will not catch it.
  • Hashed keys distribute writes and destroy range queries.
  • A compound key like { tenantId: 1, createdAt: 1 } is usually right: it distributes, it targets, it ranges within a tenant, and it gives the splitter boundaries.
  • A single-field key on a skewed field creates jumbo chunks — unsplittable, unmigratable, 340 GB in one measured case.
  • Unique indexes must be prefixed by the shard key. Verify every one before sharding; a globally-unique requirement can make a key non-viable.
  • Resharding exists but is not casual: 26 hours, +100% disk on every shard, degraded write latency throughout, for 900 GB.
  • Co-locate transactionally-related documents — cross-shard transactions measured 31 ms against 2 ms, holding locks during prepare.
  • Per-shard backups are not a consistent cluster snapshot.
  • $facet, $graphLookup and most $lookup forms run on a single merging node, which becomes the bottleneck.
  • Track the targeted-query fraction from day one. It is the health metric for a sharded cluster and almost nobody has it.
  • Alert on any jumbo chunk. One is a future incident with no operational fix.
  • Measure the candidate key's distribution on production data. Skew is invisible in staging, and simulating N buckets costs nothing.
