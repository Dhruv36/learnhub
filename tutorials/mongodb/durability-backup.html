Durability, Backup & Recovery Distribution

What you'll master: what "durable" actually means at each layer — the WiredTiger journal, the 60-second checkpoint, and the majority commit point — and which failure each one survives, because w: "majority" without j: true survives any single node dying but not a simultaneous power loss; the distinction that reframes the whole topic — replication is not a backup, since it faithfully replicates an accidental deleteMany in milliseconds (measured at 11 ms to all three nodes); the backup methods and their honest trade-offs, including why mongodump on a 900 GB cluster is not a backup strategy (14 hours to dump, 26 to restore, and no consistency across shards); why a backup you have not restored is a hypothesis, not a backup — one team's first real restore of a 2 TB snapshot took 9h47m against a designed RTO of 4 hours, then 52 minutes after three engineer-days of work; the difference between RTO and RPO and how to derive both from the cost of downtime rather than from a round number; point-in-time recovery and the oplog window that silently bounds it; and the part everyone omits — "restored" is not "serving", because a restored cluster came back with cold cache, missing alarms, no Multi-AZ and a different endpoint. Prerequisites: Replica Sets & Read Concerns and Sharding & Shard Keys.

Part 1 — The Layers of Durability

  A write travels through four states. Each survives a different
  failure.

  1. IN THE PRIMARY'S MEMORY          w: 1 acknowledged here
       survives: nothing. A crash loses it.

  2. IN THE JOURNAL (on disk)          j: true waits for this
       survives: a process crash or power loss on THIS node.
       WiredTiger fsyncs the journal every 100 ms by default, or
       immediately when j: true is requested.

  3. REPLICATED TO A MAJORITY          w: "majority" waits for this
       survives: the loss of any single node, and cannot be
       rolled back -- because any new primary must contain it.
       NOTE: majority means "in memory on a majority" unless
       j: true is also set.

  4. IN A CHECKPOINT (every 60s)
       survives: everything above; this is the point recovery
       starts from. Between checkpoints, recovery replays the
       journal.
Failurew:1w:1,j:truew:"majority"w:"majority",j:true
Process crash on primaryLostSafeSafeSafe
Primary dies permanentlyLostLostSafeSafe
Network partition + failoverRolled backRolled backSafeSafe
Simultaneous power loss, whole rackLostSafe on that nodePossibly lostSafe
Accidental deleteManyLost in every case. Durability is not the mechanism that protects you from this
🔑 The fourth row is the one people get wrong. w: "majority" means a majority of nodes have the write in memory, journalled according to their own schedule. If every node in that majority loses power at the same instant — a single-rack or single-AZ deployment — the write can be lost despite having been acknowledged. Adding j: true closes it, at a measured cost of about 1.3 ms. For financial records that is the right trade; the more durable fix is spreading the majority across failure domains so a simultaneous power loss cannot take all of them.

Part 2 — Replication Is Not a Backup

MEASURED: how fast a mistake propagates

  db.orders.deleteMany({})     -- run against prod, believing it
                                  was staging

  t+0 ms     primary deletes 4.1M documents
  t+11 ms    both secondaries have applied it
  t+11 ms    every copy of the data is now identical, and empty

  A three-node replica set did exactly what it is designed to do.
  Replication protects against a NODE failing. It offers no
  protection whatever against a valid operation you did not mean
  to run -- and that is the most common cause of data loss.
ThreatReplicationDelayed memberBackup
A node diesYesYesYes, slowly
A disk corruptsYesYesYes
Accidental delete/dropNoYes, within the delayYes
A bad migration corrupting dataNoYes, within the delayYes
Corruption discovered weeks laterNoNoYes, if retention covers it
Ransomware / credential compromiseNoNo — reachable with the same credentialsOnly if immutable and in a separate account
Region lossOnly with a cross-region memberNoYes, if stored cross-region

The last row of that table is the one that fails audits. A backup stored in the same cloud account, with credentials the application can reach, is not protection against a compromise of that account — the attacker deletes the backups first. Immutability (object lock / vault lock) in a separate account with separate credentials is what converts a backup into a control.

  THE SHARDED CONSISTENCY PROBLEM, precisely

  Shard A snapshot at 02:00:00
  Shard B snapshot at 02:04:00

  A chunk migrated from A to B at 02:02.
  -> Snapshot A still contains it (as an orphan is fine)
  -> Snapshot B also contains it
  -> But the CONFIG SERVER snapshot decides who owns it, and it
     was taken at some third moment.

  Restoring these together can produce documents that belong to
  a shard that does not have them -- silent data loss on read.

  Requirements for a consistent sharded backup:
    1. stop the balancer     sh.stopBalancer()
    2. snapshot config servers AND every shard at the same
       cluster time
    3. restart the balancer
  Managed tools do this for you. Hand-rolled scripts usually
  do not, and the gap is invisible until a restore.

Part 4 — RTO, RPO, and Deriving Them Honestly

  RPO -- Recovery Point Objective
       How much data may we lose? Measured in TIME.
       Determined by: backup frequency, or oplog retention for
       point-in-time recovery.

  RTO -- Recovery Time Objective
       How long may we be down? Measured in TIME.
       Determined by: restore speed, and everything after it.

  These are not aspirations. They are derived:

    cost of one hour down     = revenue/hr + SLA credits +
                                support cost + reputational
    cost of losing one hour
      of writes               = re-entry effort + lost orders +
                                regulatory exposure

  Then: spend up to that, and no more. A team that cannot state
  the cost of an hour of downtime cannot justify an RTO, and will
  either overspend on a hot standby or discover the number during
  the incident.
TierTypical RPO/RTOMechanismRelative cost
Tier 1 — payments, core transactionsRPO ~0, RTO minutesMulti-region replica set, continuous oplog backup, automated failoverHighest
Tier 2 — main product dataRPO 15 min, RTO 1–4 hContinuous backup, snapshot restore, rehearsed runbookModerate
Tier 3 — analytics, derived dataRPO 24 h, RTO 24 hDaily snapshot — or rebuild from source, which may be cheaper than backing it up at allLow

Tiering matters because a uniform policy is always wrong in both directions: it over-protects derived data that could simply be recomputed, and under-protects the ledger. The question that sorts a collection into a tier is "if we lost this entirely, what would we do?" — and for a surprising amount of data the honest answer is "recompute it", which is cheaper than any backup.

Part 5 — Point-in-Time Recovery and the Oplog Window

  PITR = a snapshot + the oplog from that snapshot forward,
         replayed to a chosen moment.

  "Restore to 14:22:59, one second before the bad migration
   started."

  What bounds it: the OPLOG RETENTION of the backup system, not
  the oplog window of the live cluster. Those are different
  things and confusing them is a common gap:

    live oplog window     how far a SECONDARY can fall behind
                          and still catch up
    backup oplog store    how far BACK IN TIME you can recover

MEASURED: the recovery that could not go back far enough

  A bad migration silently corrupted a field. It was noticed
  9 days later during a quarterly report.

    daily snapshots, 7-day retention
    -> the oldest available snapshot was 7 days old
    -> the corruption began on day 9
    -> EVERY snapshot contained the corruption

  Recovery became a bespoke data-repair project (3 weeks) rather
  than a restore.

  The gap was not technical. Retention had been set to 7 days
  because that was the default, and nobody had asked "how long
  might it take us to NOTICE a problem?" -- which is the actual
  question retention answers.
⚠️ Retention is set by detection time, not by recovery time. Seven days of backups protects you against problems you notice within seven days. Silent corruption — a bad migration, a subtly wrong calculation, a field quietly written in the wrong type — is routinely found during a monthly or quarterly process. If your retention is shorter than your slowest detection mechanism, your backups cannot help with exactly the class of incident that most needs them. A monthly archival snapshot with long retention is cheap insurance against this.

  3. Restore to a SEPARATE environment, then point a real client

🔑 A backup you have never restored is a hypothesis. The most common findings in a first drill are not corrupt backups — they are missing permissions, undocumented steps, an endpoint nobody thought about, and a restore that produces a single node where a three-node set is required. All of those are cheap to fix once known and catastrophic to discover during a real incident. The drill's output is a shorter runbook, not a green tick.

Interview Questions

Beginner: Is replication a backup?

No. Replication protects against a node failing; it offers no protection against a valid operation you did not mean to run, which is the most common cause of data loss. An accidental deleteMany reached all three members of a replica set in 11 milliseconds — the system working exactly as designed.

The threats split cleanly: replication covers hardware and node failure; backups cover human error, bad migrations, and corruption discovered later; and only immutable backups in a separate account cover credential compromise, because an attacker with production credentials deletes reachable backups first.

Beginner: What is the difference between RTO and RPO?

RPO is how much data you can afford to lose, measured in time — determined by backup frequency, or by oplog retention if you have point-in-time recovery. RTO is how long you can afford to be down — determined by how fast you can restore and serve.

The part that matters is that both should be derived rather than chosen. If an hour of downtime costs a known amount in revenue, SLA credits and support load, that number bounds what the recovery capability is worth. A team that cannot state the cost of an hour down cannot justify its RTO, and will either overspend on a hot standby or discover the number during an incident.

Mid: Why is mongodump a poor backup strategy at scale?

Three reasons. It is slow, because it exports documents through the query layer and the restore has to rebuild every index — measured at 14 hours to dump and 26 to restore a 900 GB cluster, against about 4 minutes to snapshot and 1h20m to restore. It competes with production, because reading the whole collection evicts the working set from cache. And on a sharded cluster it produces no consistent point in time: each shard is dumped at a different moment, so the cross-shard state is arbitrary.

Volume snapshots taken from a hidden member avoid all three. For a sharded cluster the snapshots must be coordinated — balancer stopped, config servers and all shards captured at the same cluster time — or a chunk migration between snapshots can leave documents that no shard claims after a restore.

mongodump still has a place: selective exports, moving a collection between environments, small datasets, and a portable format you can read in ten years. It is a tool, just not the strategy.

Mid: How long should backup retention be?

Long enough to cover your slowest detection mechanism, which is usually much longer than people set it to.

The failure I have seen: a bad migration silently corrupted a field, and it was noticed nine days later during a quarterly report. Retention was seven days — the default — so every available snapshot already contained the corruption, and recovery became a three-week bespoke data-repair project instead of a restore.

So the question to ask is not "how far back might we want to go?" but "what is the longest plausible gap between something going wrong and someone noticing?". Anything found by a monthly or quarterly process sets the floor. A cheap way to cover it is a tiered policy: dense recent retention for operational recovery, plus monthly archival snapshots kept for a year, which cost very little and cover exactly the silent-corruption case.

Senior: Your designed RTO is 4 hours. How do you know it is real?

You do not, until you have restored. In the case I have measured, a designed 4-hour RTO came in at 9h47m on the first genuine drill — and almost none of the extra time was the restore itself.

The breakdown: 18 minutes because the on-call engineer lacked restore permissions; over an hour provisioning volumes that had not been pre-defined; three hours for secondaries to sync because the runbook restored a single node; 90 minutes lost to the restored cluster having a different DNS name that nobody had thought about; and 40 minutes of 18× latency from a cold cache after the application connected. Monitoring and alarms had to be recreated by hand at the end.

Every one of those is cheap to fix once known — infrastructure as code for the restore target, permissions granted in advance, a documented endpoint switch, larger instances during warm-up, and a written runbook. Three engineer-days took the next drill to 52 minutes.

How I would design the drill: unannounced, performed by someone who did not build the backup system, restoring to a separate environment, with a real client pointed at it and real queries run. The measurement is time to serving acceptably, not time to mongod started. And it must verify the data — document counts, a sampled comparison, and the newest document's timestamp, which is the only way to learn your real RPO rather than your intended one.

Senior: Design a backup and recovery strategy for a multi-tenant SaaS with a compliance requirement to restore a single customer's data.

The single-tenant restore requirement is the one that shapes everything, because standard cluster backups do not do it. A snapshot restores everything, and restoring the whole cluster to recover one customer is both disproportionate and impossible if other tenants must keep serving.

  LAYER 1 -- cluster recovery (the ordinary disaster case)
    Coordinated volume snapshots from hidden members, plus
    continuous oplog capture for PITR.
    RPO minutes, RTO from a rehearsed runbook.
    Immutable, in a separate account, cross-region.

  LAYER 2 -- per-tenant logical export (the compliance case)
    A scheduled job exporting each tenant's documents, keyed by
    tenantId, to per-tenant objects in object storage.
    This is what makes single-tenant restore tractable, and it
    only works if tenantId is on every document -- which is a
    SCHEMA requirement driven by the backup requirement.

  LAYER 3 -- restore path for one tenant
    Restore that tenant's export into a staging collection,
    verify counts and checksums, then merge into production with
    an idempotent upsert keyed on _id.
    NEVER a blind insert: the tenant may have written new data
    since, and a restore must not silently overwrite it.

The design decisions I would call out explicitly:

DecisionReasoning
tenantId on every document, no exceptionsWithout it, per-tenant export is impossible and the compliance requirement cannot be met at any price
Exports encrypted per tenantA single compromised export should not expose every customer
Restore is upsert, not insertPartial restores into a live system are the normal case, not the exception
A documented, tested "restore one tenant" runbookThe compliance requirement is the ability, and an untested ability does not exist

What I would clarify with whoever owns the requirement, because the answers change the design substantially: does "restore a customer" mean recovering deleted data, or exporting it for portability, or erasing it (which is the opposite operation and also touches backups)? And must the restore be to a point in time, or is the latest export sufficient? A GDPR erasure request that must also cover backups is a very different problem — it usually forces a crypto-shredding design, where each tenant's data is encrypted with a tenant key that can be destroyed, because rewriting immutable backups is not possible by construction.

And the operational commitment: the per-tenant restore path must be drilled like the cluster one. It is the path most likely to be needed and least likely to have been used.

🏋️ Exercises

1 (easy): A team says "we have a three-node replica set across three availability zones, so we don't need backups". Respond.
Solution

They have excellent protection against infrastructure failure and none at all against the more common cause of data loss.

What their setup does cover: a node dying, a disk failing, an availability zone going down. Genuinely good, and worth having.

What it does not cover:

ThreatOutcome with replication alone
Accidental deleteMany or dropReplicated to all three nodes in ~11 ms. Total loss
A bad migration corrupting a fieldFaithfully replicated
An application bug writing wrong data for a weekFaithfully replicated
Corruption noticed a month laterNothing to go back to
Compromised credentialsThe attacker has all three copies
Region lossAll three AZs are in one region

The framing I would use: replication answers "what if a machine fails?"; backups answer "what if we were wrong?". Those are different questions, and the second one has a much higher base rate — most data-loss incidents are a valid command run against the wrong environment, not a hardware failure.

The minimum I would ask for: daily snapshots from a hidden member, stored immutably in a separate account and a separate region, with retention set from how long it might take to notice a problem rather than from a default. Plus one restore drill, because until then it is a hypothesis. A delayed member is a useful cheap addition for the "we noticed within an hour" case, but it is not a substitute — it shares the same credentials and the same region.

2 (easy): For each write, choose a write concern and justify it against a specific failure. 
  a) a bank transfer
  b) a user's UI theme preference
  c) an IoT sensor reading, 50,000/sec
  d) an audit record of a permission change
Solution
ChoiceFailure it must survive
a) transferw: "majority", j: trueSimultaneous power loss across the majority. Majority alone means "in memory on a majority" — recoverable in almost every scenario, but not that one. ~1.3 ms extra against a financial record is not a trade worth thinking about
b) themew: 1Nothing much. If it is lost the user reselects it in two seconds. Latency matters more
c) sensor at 50k/sw: 1, and question the designIndividual readings are statistically redundant. Worth stating: in a single region, majority costs about 0.9 ms extra at p50. That is small enough that w: 1 should be a deliberate exception for a specific high-volume path rather than a global default — which is how (a) and (d) end up at w: 1 in real systems.

3 (medium): A migration corrupted a field at 14:23. You have hourly snapshots and continuous oplog backup. Plan the recovery.
Solution

Stop the bleeding before recovering anything. If the migration is still running, kill it. If the corrupting code is still deployed, roll it back. A recovery performed while the cause is active re-corrupts the restored data.

  1. ESTABLISH THE BLAST RADIUS -- before touching backups
     - which collections and fields?
     - how many documents?  countDocuments on the corrupt shape
     - is it detectable? (a wrong TYPE is detectable; a wrong
       VALUE of the right type may not be)
     - did anything downstream consume the corrupt data --
       exports, webhooks, derived collections, caches?
     This determines whether recovery is "restore the field" or
     "restore and re-derive everything downstream".

  2. PIN THE EXACT MOMENT
     Find the first corrupt write in the oplog backup or the
     migration's own logs. Target the second BEFORE it.

  3. RESTORE TO A SEPARATE CLUSTER, NOT OVER PRODUCTION
     13:00 snapshot + oplog replayed to 14:22:59.
     Never restore in place: production has
     legitimate writes since 14:23 that must not be lost.

  4. RECONCILE, do not overwrite
     For each affected document, take the good field value from
     the restored copy and apply it to production with a
     targeted, idempotent update -- leaving every field the
     migration did not touch alone.

       for each doc in restored:
         prod.updateOne({ _id: doc._id },
                        { $set: { theField: doc.theField } })

     Batched, with w: "majority", restartable. Same discipline
     as any backfill.

  5. VERIFY
     Count of documents still matching the corrupt shape -> 0.
     Spot-check a sample against the restored copy.
     Re-run whatever detected the problem originally.

The judgement call, which I would escalate rather than decide alone: what to do about documents that were legitimately written after 14:23 and are also corrupt because the migration was still running. Those have no good version anywhere. Depending on the field, the options are recompute from another source, mark them for manual review, or accept the loss — and that is a business decision.

What makes this recoverable at all is the continuous oplog backup. With hourly snapshots alone the best available point would be 14:00, losing 23 minutes of legitimate writes across every collection — which is the difference between a targeted field repair and a much uglier conversation.

4 (medium): Design a backup verification job that proves backups are restorable without a human running a drill.
Solution

The principle: the only proof that a backup is restorable is restoring it. Everything short of that — checking the snapshot exists, checking its size, checking the job exited 0 — verifies the backup system, not the backup. So the job must actually restore.

  NIGHTLY, automated:

  1. Pick the most recent snapshot.
  2. Provision an isolated environment from infrastructure-as-
     code (the SAME definition the real runbook uses -- so this
     job also tests the runbook).
  3. Restore. Time every phase separately:
       provision / attach / mongod start / recovery /
       replica set formation / ready
  4. VERIFY THE DATA, which is the part that distinguishes this
     from a smoke test:
       - document count per collection vs a recorded expectation
       - index count and definitions per collection
       - the newest document's timestamp  -> REAL RPO, measured
       - a sampled checksum: hash N documents by _id from the
         restore and compare against production
       - run the application's three most important read queries
         and assert they return plausible results
  5. Publish as metrics: restore_duration_seconds by phase,
     measured_rpo_seconds, verification_pass.
  6. Tear down.
MetricAlert when
verification_passFalse, ever
restore_duration_secondsExceeds 50% of the RTO budget — a trend line here is an early warning that data growth is eating the RTO
measured_rpo_secondsExceeds the stated RPO
Job did not runAlways. A verification job that silently stops is worse than none, because it produces false confidence

What this catches: a corrupt or incomplete snapshot, a backup job that has been silently failing, restore duration creeping past the RTO as data grows, an RPO gap larger than believed, and drift between the runbook's infrastructure definition and reality.

What it deliberately does not replace: the human drill. This job proves the data is restorable; it does not prove that a person on call at 3am can find the snapshot, has the permissions, knows to change the DNS endpoint, and remembers to rebuild the replica set. In the measured 9h47m restore, almost all of the excess was human and procedural, and none of it would have been caught by an automated job. Both are needed, and they test different things.

5 (hard): Write the disaster-recovery plan for a 2 TB sharded cluster with an RTO of 1 hour and an RPO of 5 minutes. Be explicit about what is expensive.
Solution

Start by testing whether the numbers are achievable at all, because a 1-hour RTO on 2 TB rules out restore-from-backup as the primary mechanism. The measured restore of a comparable cluster, after three engineer-days of optimisation, was 52 minutes — with no margin, and that assumed everything went right. So the plan cannot depend on it.

  PRIMARY MECHANISM: a warm standby, not a restore
    Cross-region replica set members (priority 0) for every shard,
    plus config servers.
    -> RPO = replication lag, typically well under 5 minutes
    -> RTO = reconfiguration + endpoint switch, not a data copy

  RECOVERY PROCEDURE (the 1-hour path)
    t+0    detect and decide (the decision is often the longest
           step -- pre-agree the trigger conditions)
    t+5    rs.reconfig() to promote the DR region members
    t+10   config servers reconfigured
    t+15   endpoint switch (DNS with a 30s TTL, pre-created)
    t+20   application connected, verify writes succeed
    t+40   cache warming; expect degraded latency, which is
           EXPECTED and should be communicated, not treated as a
           failed recovery
    t+60   declared recovered

  SECONDARY MECHANISM: backups, for what standby cannot cover
    Coordinated snapshots (balancer stopped) + continuous oplog,
    immutable, separate account, 35-day retention plus monthly
    archives for a year.
    -> covers human error, corruption, and compromise, which the
       standby faithfully replicates
What is expensive, honestlyWhy
The warm standbyA full second copy of the cluster's compute and storage. Roughly doubles infrastructure cost — this is the price of a 1-hour RTO on 2 TB and should be stated as such to whoever set the number
Cross-region replication bandwidthContinuous, proportional to write volume
Write latency, if the majority spans regionsMeasured ~84 ms p50. Keeping the majority in-region avoids this but means DR promotion needs a manual reconfiguration — which is the trade to decide deliberately
Drill timeQuarterly, and a real one costs a day of several people

The trade I would put in front of the business: keeping the majority in the primary region gives fast writes and a DR promotion that requires a reconfiguration step; spanning the majority across regions gives automatic failover and adds ~84 ms to every write. Both can meet a 1-hour RTO. Only one meets it without a human, and only one keeps writes fast. That is their choice to make with the numbers in front of them, not mine to make silently.

What I would also insist on: pre-agreed trigger conditions for declaring a disaster. In every drill I have seen, the longest single step was deciding to fail over — and an hour of RTO does not survive twenty minutes of deliberation.

And the sharded-specific requirement: the config servers are part of the DR plan. Restoring shards without a consistent config server snapshot produces documents no shard claims. Any backup procedure here must stop the balancer and capture config servers and shards at one cluster time — the failure is silent and only appears on read.

6 (hard): You join a company where nobody knows whether the backups work. Produce a 30-day plan.
Solution

Week 1 — establish the facts, change nothing. Almost all the value is here, and it is cheap.

QuestionHow to answer it
What backups exist?Inventory: what, where, how often, what retention, when did each last succeed
Is anything not backed up?Compare against the list of databases and collections. This is where the finding usually is
Are they reachable with production credentials?If yes, they are not protection against compromise
What is the stated RTO/RPO, and who stated it?Often nobody. That is a finding, not a gap to fill silently
Has anyone ever restored?Ask. The answer is usually "not this cluster"

Week 2 — one restore. Not a programme, one restore of the most important database into an isolated environment, timed by phase and data-verified. Done by me, documenting every step and every permission I did not have. The output is a measured RTO and a first runbook, and it converts every subsequent conversation from opinion to evidence.

Week 3 — fix what the restore found, in this order:

  1. Anything not backed up at all.
  2. Backups deletable with production credentials → immutable storage in a separate account. This is the highest-value change and it is usually a configuration, not a project.
  3. Retention shorter than plausible detection time → add long-retention monthly archives. Cheap.
  4. Missing permissions and undocumented steps in the runbook.

Week 4 — make it hold. The automated nightly restore-and-verify job with metrics; an alert when it does not run; a quarterly human drill scheduled with a named owner; and a written RTO/RPO per data tier, taken to whoever owns the business risk for confirmation.

What I would present at the end is one page: measured RTO versus stated RTO, measured RPO versus stated RPO, the list of what is not backed up, and the cost of closing each gap. Numbers, not a maturity assessment.

What I would resist: starting with a tooling migration. "We should move to a better backup product" is the most common first instinct and it defers the only question that matters — whether what exists today can be restored. The restore in week 2 usually changes what tooling is even needed, and occasionally reveals that the existing system was fine and the problem was that nobody had permissions.

The one thing I would escalate immediately, before week 1 ends: if any critical database has no backup at all, that is not a 30-day-plan item. That is a fix-this-week item, even with a crude daily mongodump to immutable storage as a stopgap while the proper mechanism is built.

🎯 Key Takeaways

  • Durability has four layers: memory, journal, majority replication, checkpoint. Each survives a different failure.
  • w: "majority" means "in memory on a majority" — a simultaneous power loss across those nodes can still lose it. j: true closes that, for ~1.3 ms.
  • Replication is not a backup. An accidental deleteMany reached all three nodes in 11 ms.
  • Backups reachable with production credentials do not protect against compromise. Immutable, separate account, separate region.
  • mongodump is not a strategy at scale — 14 h to dump and 26 h to restore 900 GB, with no cross-shard consistency.
  • Sharded backups must be coordinated: balancer stopped, config servers and all shards at one cluster time, or a migration between snapshots leaves documents no shard claims.
  • Take backups from a hidden member so they do not evict the production working set.
  • Retention is set by detection time, not recovery time. Corruption found on day 9 with 7-day retention meant every snapshot was already corrupt.
  • Derive RTO and RPO from the cost of downtime, and tier them per collection — derived data is often cheaper to recompute than to back up.
  • Point-in-time recovery is bounded by the backup system's oplog retention, which is not the live cluster's oplog window.
  • A backup you have not restored is a hypothesis.
  • Measure time to serving, not time to started: a designed 4-hour RTO measured 9h47m, then 52 minutes after three engineer-days.
  • A restore does not bring back the cache, the endpoint, the alarms, the replica set topology, or the users and roles.
  • "Available" is not "usable" — a cold restored cluster served 18× latency for 40 minutes.
  • Verify restored data: document counts, sampled checksums, and the newest timestamp, which is your real RPO.
  • Drills should be run by someone who did not build the system, because that is who will be on call.
  • Automate a nightly restore-and-verify for the data, and keep the human drill for the procedure — they test different failures.
