Query Tuning in Production Indexes

What you'll master: the tuning work that happens after the index is right — starting with the ranking mistake almost everyone makes, optimising the slowest query instead of the most expensive one (a 4-second report run twice a day costs 8 seconds; a 40 ms query run 100,000 times an hour costs 67 minutes, and only the first one gets reported by humans); why skip() pagination is quadratic and was measured at 4 ms on page 1 and 2,100 ms on page 5,000, and the keyset rewrite that makes every page cost the same; the counting problem — countDocuments on 41M documents took 6.4 seconds while estimatedDocumentCount took 1 ms, and the three honest ways to show a total; the predicate rewrites that turn an unindexable query into an indexed one — $ne, $nin, unanchored regex, $where, and the case-insensitive search that went from a 2.9-second collection scan to 3 ms; how projection, batchSize and cursor iteration cost you time that explain never reports (4 ms on the server, 900 ms in the application); what read preference and read concern actually cost, and the staleness you are accepting when you move reads to secondaries; and the guardrails that keep one bad query from taking the cluster down — maxTimeMS, killOp, pool sizing, and the closing-the-loop step teams skip. Prerequisites: Reading Explain Plans and How Indexes Work.

Part 1 — Find the Queries That Actually Cost You

Tuning starts with a ranking decision, and the intuitive ranking is wrong. Humans report the query that made them wait. The cluster is being consumed by something else entirely.

MEASURED: one hour of a real workload, ranked two ways

  BY WORST SINGLE EXECUTION (what gets reported)
    1. monthly revenue report        4,100 ms  x2      =    8 s
    2. admin export                  2,800 ms  x5      =   14 s
    3. customer order history          310 ms  x1,400  =  434 s
    4. session lookup                   41 ms  x98,000 = 4,018 s

  BY TOTAL TIME (what actually matters)
    1. session lookup                4,018 s   67 minutes of CPU
    2. customer order history          434 s
    3. admin export                     14 s
    4. monthly revenue report            8 s

  Taking the session lookup from 41 ms to 4 ms freed 60 minutes of
  database time per hour. Taking the report from 4.1 s to 0.4 s
  freed 7 seconds. Guess which one three engineers had been
  working on.

  db.setProfilingLevel(1, { slowms: 100 })

  db.system.profile.aggregate([
    { $group: {
        _id: { hash: "$queryHash", plan: "$planSummary", ns: "$ns" },
        n:     { $sum: 1 },
        total: { $sum: "$millis" },
        avg:   { $avg: "$millis" },
        p_keys:{ $avg: "$keysExamined" },
        p_docs:{ $avg: "$docsExamined" },
        p_ret: { $avg: "$nreturned" },

        sample:{ $first: "$command" } } },
    { $sort: { total: -1 } },
    { $limit: 20 }

FieldWhat it tells you
totalThe ranking. Everything else is diagnosis
planSummaryInstant triage: COLLSCAN or the index name, with no explain needed
p_docs vs p_retDocuments read per document returned. Above ~100× is a missing index field

⚠️ Profiling has a cost; size it deliberately. Level 1 with a threshold writes one document per slow operation to a capped system.profile collection. Level 2 records every operation and on a busy primary can measurably degrade it. Set the capped size before enabling (db.setProfilingLevel(0), drop, recreate with an explicit size), prefer a secondary where reads allow it, and put a reminder in the calendar to turn it off — a profiler left on at level 2 has caused more incidents than it has diagnosed.

Part 2 — Pagination and Counting

skip() is quadratic

  db.orders.find({ customerId: cid })
           .sort({ createdAt: -1 })
           .skip(page * 20).limit(20)

  What skip() does: walk the index from the beginning, DISCARDING
  the first N entries, then return 20. The discarded entries are
  read. They are just thrown away.

  MEASURED (a customer with 100,000 orders):
    page      1   skip      0    4 ms
    page     10   skip    180    5 ms
    page    100   skip  1,980   28 ms
    page  1,000   skip 19,980  310 ms
    page  5,000   skip 99,980 2,100 ms

  Cost grows linearly with page number, so the total cost of
  paging through everything is quadratic. And this is with a
  PERFECT index -- skip() is not an indexing problem.

  KEYSET (RANGE) PAGINATION -- every page costs the same

  // page 1
  db.orders.find({ customerId: cid })
           .sort({ createdAt: -1, _id: -1 })
           .limit(20)

  // page N+1: pass the last row's sort key back as a cursor
  db.orders.find({ customerId: cid,
                   $or: [
                     { createdAt: { $lt: lastCreatedAt } },
                     { createdAt: lastCreatedAt,
                       _id: { $lt: lastId } }   // tie-break
                   ]})
           .sort({ createdAt: -1, _id: -1 })
           .limit(20)

  index: { customerId: 1, createdAt: -1, _id: -1 }

  MEASURED: 4 ms on page 1, 4 ms on page 5,000.

The _id tie-break is not optional. Without it, two documents sharing a createdAt timestamp straddling a page boundary will either be shown twice or skipped entirely — a bug that appears only under load, only sometimes, and is nearly impossible to reproduce from a report. Any sort key used for keyset pagination must be made unique by appending _id.

skip/limitKeyset
Cost per pageGrows with page numberConstant
Jump to page 500Yes (slowly)No — only next/previous
Stable under concurrent writesNo — an insert shifts every later pageYes
Total page countNeeds a separate countSame problem
Right forSmall result sets, admin tables where deep paging is rareInfinite scroll, APIs, anything user-facing at scale

The counting problem

  db.orders.estimatedDocumentCount()       // 1 ms, metadata read
  db.orders.countDocuments({})             // 6,400 ms, full scan
  db.orders.countDocuments({ status: "paid" })   // index scan

  estimatedDocumentCount() reads collection metadata. It is fast,
  it takes NO filter, and after an unclean shutdown it can be
  wrong until the counts are corrected.

  countDocuments() runs a real aggregation. With an index it is a
  COUNT_SCAN over keys -- no documents fetched -- but it still
  walks every matching key. On 41M matching documents that is
  seconds, no matter how good the index is.

There is no fast exact count of a filtered set at scale. That is a real constraint, so the honest options are product decisions, not technical ones:

OptionHowTrade-off
Don't show a total"Load more" / infinite scrollFree, and what most modern UIs do. Propose this first
Bounded countcountDocuments(q, { limit: 1000 }) → "1,000+"Fast and honest. Stops counting at the cap
ApproximateestimatedDocumentCount() for unfiltered totalsInstant, but no filter and occasionally stale
Maintained counter$inc a counter document on every writeExact and instant to read, but it is a write hotspot and needs a reconciler; see Schema Design Patterns
🔑 An exact filtered count on a large collection is the most expensive thing on most pages, and it is usually decoration. One dashboard spent 6.4 seconds per load computing "41,203,881 orders" — a number no one had ever acted on. Deleting it was the entire optimisation. Ask what decision the number supports before you optimise it.

Part 3 — What Explain Does Not Charge You For

MEASURED: the query that was fast on the server and slow in the app

  explain: executionTimeMillis 4
  reality: 900 ms measured at the driver

  find({ tenantId: t }) with no projection and no limit
    nReturned       182,000
    responseLength  ~740 MB total across batches
    batchSize       101 (default first batch), then 16MB batches

  The server found the documents in 4 ms. The other 896 ms was
  BSON serialisation, network transfer, driver deserialisation,
  and 40 round trips to fetch subsequent batches.

  Fixes, in order of effect:
    1. limit()          -- do you need 182,000 documents?      -95%
    2. projection       -- 740 MB -> 31 MB by returning 6 fields
    3. batchSize        -- fewer round trips for a genuine bulk read
LeverEffectWatch out for
project()Cuts BSON size, network, driver CPU, and can enable a covered queryProjecting a large array field still materialises it; use $slice or restructure
limit()Bounds everything downstream — but only stops the scan early if the sort comes from the indexA blocking SORT reads everything regardless
batchSize()Fewer round trips on large readsLarger batches mean more memory held per cursor; the reply is capped at 16 MB per batch regardless
Cursor timeoutsIdle cursors are closed after 10 minutesA slow consumer that pauses mid-iteration gets CursorNotFound; process in bounded batches instead
allowDiskUseLets an aggregation stage spill past 100 MBIt converts a failure into something very slow. Usually a signal to reduce earlier, not to enable

The general principle: explain measures the database's work, and the database is often not where the time goes. When the server says 4 ms and the user waits 900, stop tuning indexes and start measuring responseLength and document counts.

Part 4 — Rewriting Predicates So They Can Use an Index

Some predicates cannot use an index no matter what you build, because they do not describe a contiguous key range. Each has a rewrite.

UnindexableWhyRewrite
{ status: { $ne: "cancelled" } }Two disjoint ranges spanning nearly the whole index{ status: { $in: ["pending","paid","shipped"] } } — each value is its own seek
{ type: { $nin: [...] } }SameEnumerate the positive set
{ name: /smith/ }Unanchored — matches could be anywhere in the key order/^smith/ if prefix matching is acceptable; otherwise a text index or a real search engine
{ name: /^smith/i }The i flag defeats the anchor: casing changes orderingStore and index a normalised nameLower
{ $where: "this.a > this.b" }Runs JavaScript per document; no index, and a security surface{ $expr: { $gt: ["$a","$b"] } } — still unindexed, but no JS; better, store a computed field and index that
{ $expr: { $gt: [{ $year: "$createdAt" }, 2025] } }A computed value cannot be indexed{ createdAt: { $gte: ISODate("2026-01-01") } } — express it as a range on the raw field
{ tags: { $size: 3 } }$size is not indexableMaintain a tagCount field and index it
$or with one unindexed branchThe whole $or falls back to a collection scanIndex every branch; check for a SUBPLAN stage with an IXSCAN under each
MEASURED: case-insensitive search

  db.users.find({ email: /^amy@example\.com$/i })
    COLLSCAN, 4.2M docs, 2,900 ms

  Option A -- normalised field (what I default to)
    { email: "Amy@Example.com", emailLower: "amy@example.com" }
    db.users.createIndex({ emailLower: 1 })
    db.users.find({ emailLower: q.toLowerCase() })
    IXSCAN, 1 key, 3 ms

  Option B -- collation index
    db.users.createIndex({ email: 1 },
                         { collation: { locale: "en", strength: 2 } })
    db.users.find({ email: q })
            .collation({ locale: "en", strength: 2 })
    IXSCAN, 3 ms -- but ONLY if the query specifies the collation.
    Omit it and you silently get a COLLSCAN.

  A is more code and no hidden coupling. B is less code and a trap
  that every new developer and every new driver call can fall into.

The $or rule

  db.orders.find({ $or: [
    { customerId: cid },        // indexed
    { email: someEmail }        // NOT indexed
  ]})

  The planner needs an indexed plan for EVERY branch. One
  unindexed branch means the whole query becomes a COLLSCAN --
  the indexed branch buys nothing.

  Check the plan for stage: "SUBPLAN" with an IXSCAN beneath each
  branch. If you see COLLSCAN at the top, find the branch that
  lacks an index.

  Also: $or over the SAME field is an $in, and $in is better --
  one index, one set of seeks, no deduplication step.
    { $or: [{s:"a"},{s:"b"}] }   ->   { s: { $in: ["a","b"] } }

Part 5 — Read Preference, Read Concern, and What They Cost

Read preferenceBehaviourCost
primary (default)All reads from the primaryNo staleness. Primary is the bottleneck
primaryPreferredPrimary, falling back to a secondarySilently becomes stale during a failover — usually the worst option, because the staleness appears exactly when things are already going wrong
secondarySecondaries onlyReplication lag, typically milliseconds but unbounded under load
secondaryPreferredSecondaries, falling back to primaryGood for analytics and reports
nearestLowest network latency, primary or secondaryGeographically fast, arbitrarily stale
  THE READ-YOUR-OWN-WRITE TRAP

  await orders.insertOne(doc)                       // primary
  const list = await orders.find({ customerId })     // secondary
                           .toArray()
  // the new order is often MISSING. Replication lag is real.

  Three ways out:
    1. Read from the primary on the path immediately after a write.
    2. Use causal consistency: one client session, with
       readConcern "majority" and writeConcern "majority" -- the
       session carries a cluster time so the read waits for it.
    3. Do not re-read: return the document you just wrote, or use
       findOneAndUpdate with returnDocument: "after".

  Option 3 is the cheapest and removes the round trip as well. It
  is also the one people forget exists.
Read concernGuaranteeLatency cost
local (default)Whatever this node has, possibly not yet replicated — and possibly rolled back laterLowest
majorityOnly data acknowledged by a majority; will never be rolled backWaits for the majority commit point — measured ~2–15 ms extra under normal lag, far more under stress
snapshotA consistent point-in-time view across the whole readHighest; used inside transactions
linearizableReflects all majority-acknowledged writes before the read beganVery high; primary only, single-document reads only, and requires maxTimeMS
⚠️ The default combination is the surprising one. Writes default to w: "majority" but reads default to readConcern: "local". So a write can be durably committed while a subsequent read on another node does not see it — and a read can return data that a rollback later removes. That mismatch is fine for most workloads and quietly wrong for money and for anything a user just did. See CRUD and What It Guarantees and Replica Sets & Read Concerns.

Part 6 — Guardrails and Closing the Loop

  1. maxTimeMS ON EVERY QUERY. Not most. Every one.

     db.orders.find({...}).maxTimeMS(2000)

     Without it, a single pathological query runs until it finishes
     or the client gives up -- and the client giving up does NOT
     stop the server. The operation keeps consuming CPU and cache
     with nobody waiting for the answer.

     MEASURED: an export endpoint whose client timed out at 30 s
     left 140 abandoned operations running after a traffic spike.
     Cluster CPU stayed at 100% for 20 minutes after the traffic
     had gone.

  2. KILL WHAT IS RUNNING AWAY.

     db.currentOp({ secs_running: { $gt: 5 },
                    op: { $in: ["query","command","getmore"] } })
     db.killOp(opid)

     killOp is cooperative: the operation stops at its next
     interrupt point. Fast for a scan, not instant for everything.

  3. SIZE THE CONNECTION POOL DELIBERATELY.

     Default maxPoolSize is 100 PER CLIENT INSTANCE. Forty app
     pods with one client each is 4,000 possible connections, and
     each costs ~1 MB of server RAM plus scheduling overhead.
     A pool larger than the server can usefully run in parallel
     does not add throughput -- it converts a queue you can see
     into contention you cannot.

  4. TIER YOUR TIMEOUTS.
     maxTimeMS  <  application timeout  <  load-balancer timeout
     Inverted, the client gives up while the server works on.

The loop that people leave open

  1. MEASURE     profiler, ranked by total time
  2. DIAGNOSE    explain("executionStats") on the top few
  3. CHANGE      one thing -- index, predicate, or projection
  4. VERIFY      re-run the SAME profiler aggregation, compare the
                 SAME queryHash. Not "it feels faster".
  5. CLEAN UP    $indexStats: did this change make an older index
                 redundant? An optimisation process that only ever
                 ADDS indexes eventually becomes a cache problem.

  Step 4 is skipped most often, and step 5 almost always. One team
  reached 19 indexes on a collection through six months of
  diligent, individually-correct optimisations, and the resulting
  cache pressure had made everything slower than when they started.
🔑 Before tuning any query, ask whether it should run at all. The fastest query is the one that is not executed: a cached result, a precomputed rollup, a total nobody reads, a page nobody scrolls to. The three largest wins in the measured examples in this lesson were deleting a count, adding an application-level cache in front of 98,000 session lookups an hour, and returning the document from the write instead of re-reading it. None of them were index changes.

Interview Questions

Beginner: Why is skip() slow for deep pagination?

Because skip(n) does not seek — it walks the index from the start and discards the first n entries. Those entries are read; they are just thrown away. So cost grows linearly with the page number, and paging through a whole result set is quadratic overall.

Measured on a customer with 100,000 orders and a perfect index: 4 ms on page 1, 310 ms on page 1,000, 2,100 ms on page 5,000. The index was not the problem, which is why this cannot be fixed by indexing.

Keyset pagination fixes it: instead of "skip 19,980", pass the last row's sort key and ask for "everything after this", which is a normal indexed seek. Every page then costs the same.

Beginner: What is the difference between countDocuments and estimatedDocumentCount?

estimatedDocumentCount() reads collection metadata — about 1 ms regardless of size — but takes no filter and can be briefly inaccurate after an unclean shutdown. countDocuments(filter) runs a real query. With a good index it is a COUNT_SCAN over keys with no document fetches, but it still walks every matching key, so on 41 million matches it took 6.4 seconds.

The practical consequence is that there is no fast exact count of a filtered set at scale. The options are a bounded count ({ limit: 1000 } → "1,000+"), a maintained counter, or not showing a total. I would ask what decision the number supports first — in the case I measured, the 6.4-second count was decoration and deleting it was the entire optimisation.

Mid: An explain says 4 ms but users wait 900 ms. Where is the time?

Outside the database. executionTimeMillis covers finding the documents; it excludes BSON serialisation, network transfer, driver deserialisation, and the round trips to fetch subsequent cursor batches.

In the case I measured, the query returned 182,000 documents with no projection — about 740 MB across roughly 40 batches. The server genuinely did its part in 4 ms.

The diagnosis is nReturned and responseLength in the profiler, not explain. The fixes in order of effect: a limit (does anything need 182,000 documents?), a projection (740 MB → 31 MB by returning six fields), and only then batchSize for a genuine bulk read. Adding an index would have changed nothing.

Mid: How do you make a case-insensitive search use an index?

A case-insensitive regex like /^amy@example\.com$/i cannot use an index even though it is anchored, because case folding changes the key ordering — measured at 2,900 ms as a collection scan over 4.2M users.

Two options. Store a normalised emailLower field, index it, and query it with a lowercased input: 3 ms, and completely explicit. Or create a collation index with strength: 2 and specify the same collation on every query — also 3 ms, but if any call site omits .collation() it silently falls back to a collection scan while the unique constraint still applies case-insensitively.

I default to the normalised field. It is a little more code and no hidden coupling between the query and the index, and it behaves identically in every driver and in the shell.

Senior: Design a systematic query-tuning process for a team, including the parts people skip.

Collect with the profiler at level 1 and a threshold matched to the workload — 100 ms is a starting point, but for a 5 ms API it should be far lower. Cap the collection first and prefer a secondary.

Rank by total time, grouped by queryHash. This is the step that changes outcomes: the queries humans report are the slowest ones, and the queries consuming the cluster are moderately slow ones running constantly. In one hour of real workload, the top-reported query cost 8 seconds and the unreported one cost 67 minutes.

Triage with planSummary, which is already in the profiler output — every COLLSCAN on a large namespace is a finding with no explain needed.

Diagnose the survivors with explain("executionStats"): the ratios of examined to returned, and indexBounds for compound fields contributing nothing.

Then the two steps teams skip. Verify by re-running the same profiler aggregation and comparing the same queryHash — not by impression. And clean up: check $indexStats for indexes the change made redundant, then hideIndex for a business cycle before dropping. A process that only ever adds indexes becomes a cache problem; I have seen a team reach 19 indexes through six months of individually-correct optimisations and end up slower than they started.

The organisational part: this should be a scheduled review with an owner, plus a CI check against production-shaped data that fails the build on a new COLLSCAN. The cheapest slow query to fix is the one that never ships.

And the question that comes before all of it: should this query run at all? The three biggest wins I have measured were deleting a count nobody read, caching 98,000 identical session lookups an hour, and returning the document from the write instead of re-reading it. None were index changes.

Senior: Your primary is at 100% CPU and the app is timing out. What do you do, in order?

Stabilise before diagnosing. db.currentOp({ secs_running: { $gt: 5 } }) to see what is actually running now. If one operation or one shape dominates, killOp it — that is triage, not optimisation, and it comes first. Note that killOp is cooperative: the operation stops at its next interrupt point, quickly for a scan and less so for other work.

Then check whether client timeouts are making it worse. A client giving up does not stop the server. If the application times out at 30 s and no query sets maxTimeMS, abandoned operations accumulate with nobody waiting for their results — I have seen 140 of them hold CPU at 100% for 20 minutes after the traffic had gone. If so, the immediate mitigation is shedding load at the application, and the follow-up is maxTimeMS everywhere.

Rule out the non-query causes, because they present identically and no index fixes them: an index build running, a backfill or migration, a backup, an initial sync from a new secondary, or the working set exceeding cache (check wiredTiger.cache["pages evicted by application threads"]).

Check the plan cache. A sudden step change with no deploy is its signature — one cached plan, chosen from a ~101-document trial, being applied to values it is wrong for. $planCacheStats and timeOfCreation near a restart make it likely.

Only then optimise. During an incident I would prefer reversible changes: a hint(), a query-side fix, or shedding a non-critical endpoint. I would not start an index build on a cluster at 100% CPU — the build consumes CPU and evicts cache, and it is not cheaply reversible. That goes on the list for a calm window, with the profiler evidence attached.

Afterwards: the guardrails that would have contained it — maxTimeMS on every query, tiered timeouts (maxTimeMS < app < load balancer), a sized connection pool, and an alert on currentOp long-runners. An incident that changes no defaults will recur.

🏋️ Exercises

1 (easy): An infinite-scroll feed uses .skip(page*20).limit(20) with the index { userId: 1, createdAt: -1 }. Users report that scrolling gets slower and that items occasionally appear twice. Fix both.
Solution

Both symptoms are skip(). It gets slower because skipped entries are read and discarded, so page cost grows with page number. Items appear twice because a new document inserted while the user scrolls shifts every subsequent page by one — an item that was at the top of page 4 moves to the bottom of page 3 and gets shown again.

  // first page
  db.feed.find({ userId })
         .sort({ createdAt: -1, _id: -1 })
         .limit(20)

  // subsequent pages: cursor = { createdAt, _id } of the last item
  db.feed.find({ userId,
    $or: [
      { createdAt: { $lt: cur.createdAt } },
      { createdAt: cur.createdAt, _id: { $lt: cur._id } }
    ]})
    .sort({ createdAt: -1, _id: -1 })
    .limit(20)

  index: { userId: 1, createdAt: -1, _id: -1 }

Why the $or is shaped that way: it means "strictly older, or the same instant but a lower _id". Without the tie-break, two items sharing a createdAt across a page boundary are either both shown or both skipped. That bug is load-dependent and effectively unreproducible from a user report, so it is worth writing correctly the first time.

What this costs you: no jumping to an arbitrary page. For an infinite-scroll feed that is not a loss — nobody jumps to page 400 of a feed. If the product genuinely needs page numbers, that is a different conversation, and the honest answer is that deep page numbers are expensive in every database.

Encode the cursor opaquely (base64 of the two values) so clients cannot construct one and you can change the sort key later without breaking them.

2 (easy): Rewrite these three predicates so they can use an index, and say what you gave up in each case. 
  a) { status: { $ne: "archived" } }
  b) { title: /report/i }
  c) { $expr: { $gt: [ { $year: "$createdAt" }, 2025 ] } }
Solution

(a) $ne describes everything except one value — two disjoint ranges that between them cover almost the whole index, so the scan is effectively unbounded.

  { status: { $in: ["draft","active","paused","completed"] } }

Given up: the enumeration must be maintained. Adding a new status without updating the query silently excludes it. Mitigate by generating the list from the same constant the validator's enum uses, so there is one source of truth.

(b) The i flag and the lack of an anchor both defeat the index — an unanchored regex has no contiguous key range, and case folding changes ordering.

  // if prefix search is acceptable:
  { titleLower: /^report/ }     with index { titleLower: 1 }
  // if substring search is required: a text index, or a real
  // search engine. There is no index that makes /report/ fast.

Given up: substring matching. This is the honest limit — "contains" is not an indexable operation in a B-tree, and pretending otherwise is how teams end up with a 3-second search box.

(c) $year computes a value per document, and computed values cannot be indexed. But the intent is a plain range.

  { createdAt: { $gte: ISODate("2026-01-01T00:00:00Z") } }

Given up: nothing, except that you now have to think about time zones explicitly. That is arguably a gain — $year silently used UTC, which was probably not what the report meant, and the bug was invisible.

The pattern across all three: express the predicate as a contiguous range over a stored value. Anything that negates, computes, or ignores ordering cannot bound an index scan.

Add it (ESR order) and the ratio should collapse toward 20/20. Also 210 KB per response for 20 documents suggests whole documents are being returned — a projection is likely a second, independent win.

2. A second. A collection scan over 4.1M documents returning 12 rows is a missing index, and 6.8 minutes/hour is real. Straightforward once the predicate is known.

3. D — not for its time, but as a risk. 18 seconds an hour is nothing, but it returns 380,000 documents and 740 MB per execution. That is a memory and network event on both the server and whatever client consumes it, and it will get worse as the collection grows. It also has no maxTimeMS protection implied. I would treat it as a correctness/guardrail item — add a limit or a projection, or move it to a secondary — rather than a latency optimisation.

4. C — leave alone. 1 document examined per 1 returned at 12 ms is already optimal. Any time spent here is wasted.

The observation worth raising beyond indexing: B runs 84,000 times an hour, which is 23 per second. Before optimising it from 38 ms to 4 ms, I would ask whether those calls are necessary — an N+1 pattern in the application, or a missing cache, would be a far larger win than a tenfold latency improvement. The profiler's n column is often the finding, not the avg column.

4 (medium): An endpoint shows a table of results with a total count and page numbers. It takes 6.8 seconds on a 41M-document collection. Give three options with their trade-offs and recommend one.
Solution

First, split the 6.8 seconds, because there are two independent costs and they need different fixes: the count (measured separately at ~6.4 s) and the page fetch (~0.4 s, and worse on deep pages if it uses skip). Optimising the wrong half wastes the effort.

OptionResultTrade-off
1. Drop the total, keyset pagination~5 ms per page, constantNo page numbers, no "of 41,203,881". Requires a UI change
2. Capped count + skip
countDocuments(q, {limit: 10000})		Count ~40 ms, shows "10,000+"; pages still degrade with depthSmallest change, keeps page numbers up to a bound. Deep pages remain slow
3. Maintained counterCount ~1 ms, exactOnly works for a fixed filter set; a write hotspot on the counter document; needs a reconciler because counters drift

Recommendation: option 1, and it is worth making the product argument rather than the technical one. In the case I measured, the exact total was 6.4 of the 6.8 seconds and no one had ever acted on the number — it was decoration on a page whose users only ever looked at the first two screens. Instrument it if there is doubt: log how often anyone requests a page beyond 3, and how often the total changes any behaviour.

If page numbers are genuinely required (an audit tool where "go to page 400" is a real workflow), option 2 is the pragmatic compromise: a capped count gives an honest "10,000+" quickly, and skip within a bounded range is acceptable. I would still cap the maximum reachable page rather than letting someone request page 500,000.

Option 3 only if the filter set is small and fixed (a handful of statuses, say). A counter per arbitrary filter combination does not scale, and the reconciler is not optional — counters drift through failed writes, retries and manual data fixes, and a total that is wrong is worse than one that is absent.

5 (hard): An export endpoint streams every order for a customer as JSON. It works for most customers and times out for the largest ones, and while it runs, unrelated queries slow down. Redesign it.
Solution

Three distinct problems are stacked here, and fixing only the visible one leaves the other two.

ProblemEvidence
Unbounded result setWorks for small customers, times out for large ones — the size scales with the customer, not with a limit
Cache eviction"Unrelated queries slow down" — the export pulls millions of documents through the WiredTiger cache, evicting everyone else's working set
No timeout containmentThe client giving up does not stop the server; the operation runs on

The redesign:

  1. MOVE IT OFF THE REQUEST PATH
     POST /exports -> 202 Accepted + job id
     worker processes it, writes to object storage
     GET /exports/{id} -> status, then a signed URL

     This alone fixes the timeout, because there is no longer an
     HTTP request waiting on it.

  2. READ FROM A SECONDARY
     readPreference: secondaryPreferred (or a dedicated
     analytics/hidden node)
     The export's cache eviction now damages a node that is not
     serving the hot path.

  3. PAGE THE READ, DO NOT STREAM ONE CURSOR
     Keyset iteration in batches of ~1,000 on { customerId, _id }.
     Bounded memory, restartable from the last _id, and immune to
     the 10-minute idle cursor timeout that a slow writer would
     otherwise hit with CursorNotFound.

  4. PROJECT
     An export needs specific columns, not whole order documents
     with their items arrays. In the measured case this was the
     difference between 740 MB and 31 MB.

  5. GUARDRAILS
     maxTimeMS per batch (not per export), a total-row cap with an
     explicit error rather than silent truncation, and one
     concurrent export per customer.

Why keyset batching rather than one cursor with a large batchSize: a single long-lived cursor holds a snapshot-ish position on the server, is vulnerable to the idle timeout if the consumer is slow (writing to object storage, for instance), and cannot be resumed after a worker restart. Batched keyset reads are individually short, restartable, and let you insert a deliberate pause between batches to limit cache impact.

What I would push back on: if exports are a core workflow rather than an occasional admin action, the durable answer is a separate analytics path — a hidden replica-set member, or periodic extraction to a warehouse — not a better-behaved export endpoint. Large sequential reads and low-latency point queries want opposite things from a cache, and no amount of tuning makes one node good at both. I would ship the redesign above now and open that conversation with the export volume numbers attached.

6 (hard): Design a query-performance regression gate for CI: it must catch a bad query before it ships, without a production database and without being so noisy that people disable it.
Solution

The two failure modes to design against are opposite, and most attempts die of the second: a gate that misses real regressions is useless, and a gate that fires on noise gets disabled within a month. So the design principle is assert on plan shape, not on timing. Timings on CI hardware are noise; plans are deterministic.

  1. A SEEDED DATASET WITH PRODUCTION-LIKE SHAPE
     Not production data. What matters is cardinality and skew:
     enough documents that the planner makes real choices (10k
     minimum, 100k better), a realistic tenant distribution
     including one large tenant, and realistic array lengths.
     A 500-document fixture makes every plan look identical --
     which is exactly why staging explains predict nothing.
     Seed it deterministically from a script in the repo.

  2. THE ASSERTIONS (plan shape, not milliseconds)
     For each registered query:
       - no COLLSCAN on a collection above N documents
       - docsExamined <= K * nReturned          (K ~ 10)
       - no blocking SORT stage
       - no [MinKey, MaxKey] on a field the query filters on
       - shardsTargeted == 1, where the collection is sharded

  3. HOW QUERIES GET REGISTERED
     The hard part is coverage, not assertions. Two options:
       a) explicit: a test file listing the queries that matter
       b) automatic: run the integration suite with the profiler
          on, then assert over the profiler output
     (b) has far better coverage and no maintenance, and it
     catches queries nobody remembered to register. It is the one
     I would build.

  4. FAILURE OUTPUT
     Print the explain, the failing assertion, and a suggested
     index. A gate that says "query performance regression" and
     nothing else gets bypassed.

What this catches: a new query with no index, a predicate rewritten into an unindexable form (someone changing $in to $ne), a dropped index, a sort added without an index to support it, and a new field filtered but not indexed. That is the large majority of real regressions.

What it cannot catch, and I would say so explicitly rather than implying coverage it does not have: plan-cache effects (they need production value distributions), cache-pressure cliffs (they need production data volume), lock contention and concurrency, replication lag, and anything where the fixture's skew differs from production. Those need production monitoring; the gate is a complement, not a replacement.

The anti-noise rules that keep it alive: never assert on wall-clock time; make the thresholds explicit constants that a reviewer can change with justification in the diff; allow an inline waiver with a required comment for the legitimate exceptions (a genuinely small collection, a deliberate scan in a batch job); and fail the build only on new violations, reporting existing ones as warnings, so the gate can be adopted on a legacy codebase without a flag day.

Effort estimate: roughly a week for the seeded dataset and the profiler-based harness, which is the honest cost — most of it in the dataset, not the assertions. I would ship it in warning-only mode first and turn on enforcement once the existing violations are triaged, because a gate introduced as a wall of red failures never survives its first sprint.

🎯 Key Takeaways

  • Rank by total time, not worst case. A 41 ms query at 98,000/hour costs 67 minutes; the 4-second report everyone complains about costs 8 seconds.
  • planSummary in the profiler is free triage — COLLSCAN findings need no explain at all.
  • Profiler level 2 on a busy primary is an incident risk. Level 1 with a threshold, capped, ideally on a secondary, and turned off afterwards.
  • skip() reads and discards. 4 ms on page 1, 2,100 ms on page 5,000 — with a perfect index.
  • Keyset pagination makes every page cost the same, and needs an _id tie-break or rows are duplicated and skipped at page boundaries.
  • There is no fast exact filtered count at scale. 6.4 s versus 1 ms for the estimate; prefer a cap, a counter, or no total.
  • Explain does not charge you for serialisation, network or cursor round trips — 4 ms on the server, 900 ms at the driver, 740 MB on the wire.
  • Projection is a performance feature, not just a tidiness one: 740 MB → 31 MB by returning six fields.
  • $ne and $nin are two disjoint ranges — enumerate the positive set with $in.
  • A case-insensitive regex cannot use an index, anchored or not. Index a normalised lowercase field: 2,900 ms → 3 ms.
  • One unindexed $or branch makes the whole query a collection scan.
  • Computed predicates ($year, $size, $where) cannot be indexed. Express them as ranges over stored values.
  • Writes default to majority, reads default to local — so a committed write can be invisible to the next read on another node.
  • Reading a secondary right after writing loses your own write. Read the primary, use causal consistency, or return the written document.
  • maxTimeMS on every query. A client timeout does not stop the server — 140 abandoned operations held CPU at 100% for 20 minutes.
  • Tier your timeouts: maxTimeMS < application < load balancer.
  • Close the loop. Re-measure the same queryHash, and audit $indexStats for newly redundant indexes — a process that only adds indexes becomes a cache problem.
  • The fastest query is the one that does not run. The three largest measured wins here were deleting a count, caching repeated lookups, and not re-reading after a write.
