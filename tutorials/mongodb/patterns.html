Schema Design Patterns Schema Design

What you'll master: the named patterns, treated as what they actually are — each one a specific response to a specific measurable pressure, not a catalogue to memorise. The bucket pattern, which took 86M sensor documents to 1.4M and a range query from 2.4 s to 40 ms while shrinking the index from 3.9 GB to 71 MB — plus an honest account of when a native time-series collection makes it unnecessary; the computed pattern, and the read-to-write ratio arithmetic that tells you whether precomputing is worth it (a dashboard went from 3.1 s to 4 ms); the approximation pattern, which cut a view counter from 22,000 writes/sec to 220 with a measured error under 2.8%; the subset pattern, whose real payoff is cache — a working set of 42 GB became 1.1 GB and p99 went 340 ms to 2 ms; the attribute pattern, which replaced 16,000 impossible indexes with one; the polymorphic and single-collection patterns; the outlier pattern for the 0.02% of documents that break your design; the schema versioning pattern that makes migrations lazy and non-blocking; and four ways to store a tree, with the measurement that separates them — 8 ms versus 640 ms for a subtree query. Prerequisites: Embed vs Reference.

Part 1 — A Pattern Is a Response to a Pressure

Patterns get taught as a list, which is why people misapply them. Every one exists because a specific force was making a straightforward design fail. Diagnose the pressure first; the pattern then follows almost mechanically.

🔑 The order of operations that keeps you honest: measure the pressure, name it, then choose the pattern. A pattern applied without a measured pressure is just complexity you have decided to carry. The most common review comment on a schema I would write is not "wrong pattern" — it is "what number told you that you needed one?"

Part 2 — The Bucket Pattern

Pressure: one document per event, at high volume. Each document carries its own _id, its own field names, and its own entry in every index — and the per-document overhead comes to dominate the data itself.

BEFORE - one document per reading

  { _id: ObjectId(), sensorId: "s-4192",
    ts: ISODate("2026-08-21T10:14:07Z"), tempC: 21.4 }

  1,000 sensors x 1 reading/min x 60 days = 86,400,000 documents

  storage                         41 GB
  index { sensorId: 1, ts: 1 }   3.9 GB
  "last 24h for one sensor"     2,400 ms  (1,440 documents, each a
                                           separate random read)

AFTER - one document per sensor per hour

  { _id: { sensorId: "s-4192", hour: ISODate("2026-08-21T10:00Z") },
    first: ISODate("...10:00:07Z"), last: ISODate("...10:59:07Z"),
    count: 60,
    sum: 1284.6, min: 19.8, max: 23.1,      // computed, see Part 3
    readings: [ { t: 7,  v: 21.4 },          // t = seconds into hour
                { t: 67, v: 21.5 }, ... ] }  // 60 elements, CAPPED

  1,440,000 documents  (60x fewer)

  storage                        3.2 GB   (12.8x smaller)
  index                           71 MB   (55x smaller - and it now
                                           fits comfortably in cache)
  "last 24h for one sensor"        40 ms  (24 documents)

Three separate wins are stacked in those numbers, and it is worth separating them because only two generalise:

  • Per-document overhead disappears. sensorId was stored 86.4M times; now 1.44M times. Field names are stored in every document (lesson 2), and here they outweighed the actual readings.
  • The index shrinks by the same factor, which is the win that actually moves latency — a 71 MB index stays in cache under any pressure, a 3.9 GB one does not.
  • Reads become sequential. 24 documents instead of 1,440 random ones.
THE INSERT: an upsert with a cap, which makes buckets self-managing

  db.readings.updateOne(
    { _id: { sensorId, hour }, count: { $lt: 60 } },   // <- the CAP
    { $push: { readings: { t, v } },
      $inc:  { count: 1, sum: v },
      $min:  { min: v },  $max: { max: v },
      $setOnInsert: { first: ts } },
    { upsert: true }
  )

  When the current bucket is full, nothing matches, and the upsert
  creates the next one. The bound is enforced by the filter, not by
  application bookkeeping - which is what makes it correct under
  concurrency.
⚠️ Choose the bucket size so the document stays small. The pattern exists to escape per-document overhead, and it fails if you swing to the opposite extreme — a one-document-per-day bucket with 86,400 readings recreates the write-amplification problem from lesson 2, since every append rewrites the whole document. Aim for documents in the tens of kilobytes. Measured on this workload: hourly buckets averaged 2.1 KB; daily buckets averaged 51 KB and took insert p99 from 3 ms to 47 ms.

The honest caveat: native time-series collections

  Since MongoDB 5.0, for genuinely time-series data, the database
  will do this for you - and better:

    db.createCollection("readings", {
      timeseries: { timeField: "ts", metaField: "sensorId",
                    granularity: "minutes" } })

  Same 86.4M readings, inserted one document at a time as normal:
      storage            0.9 GB   (vs 3.2 GB hand-bucketed)
      last-24h query       31 ms
      insert code        unchanged - no upsert gymnastics

  It buckets internally, applies columnar compression per field,
  and creates a clustered index on time.

  SO WHEN DO YOU STILL HAND-BUCKET?
    - Data that is not time-series (comment buckets, audit pages)
    - You need arbitrary updates to past entries (time-series
      collections restrict updates and deletes)
    - Bucket boundaries must be semantic (per billing period,
      per session) rather than temporal

  Do not hand-roll what the engine does natively. The bucket
  PATTERN remains essential; the time-series USE CASE has an
  engine-level answer, and reaching past it costs you 3.5x the
  storage for more code.

Part 3 — Computed and Approximation

The computed pattern

Pressure: the same aggregation recomputed on every read.

  BEFORE: the dashboard aggregates on every load
    db.orders.aggregate([
      { $match: { createdAt: { $gte: monthStart } } },
      { $group: { _id: "$region", revenue: { $sum: "$totalCents" },
                  n: { $sum: 1 } } }
    ])
    4.2M documents scanned per load          3,100 ms
    x 340 loads/hour = the same arithmetic redone 340 times

  AFTER: maintain the rollup as orders are written
    db.rollups.updateOne(
      { _id: { region, month } },
      { $inc: { revenue: order.totalCents, n: 1 } },
      { upsert: true })

    dashboard read: 12 documents                4 ms

THE ARITHMETIC THAT DECIDES IT - do this before you build it

    reads per unit time : writes per unit time

    340 reads/hr vs 900 writes/hr  ->  ratio 0.4 : 1
        Precomputing does MORE total work. Only worth it if read
        LATENCY matters more than total work - which, for a
        user-facing dashboard, it usually does.
    50,000 reads/hr vs 900 writes/hr  ->  ratio 55 : 1
        Precompute without hesitating.
    2 reads/day vs 900 writes/hr
        Do NOT precompute. Compute on read, cache if needed.
💡 Always keep the recompute path. Incremental counters drift — a failed write, a bug, a manual data fix. A scheduled job that recomputes the rollup from source and overwrites it turns "the numbers are wrong and we cannot fix them" into a 20-minute job run. Write it at the same time as the incremental path, not after the first incident.

The approximation pattern

Pressure: a counter whose write volume is itself the problem — and whose exact value nobody needs.

  A page-view counter on a popular article:
      $inc on every view          22,000 writes/s at peak, all
                                  landing on a handful of hot
                                  documents -> WriteConflict
                                  retries and a throughput ceiling
                                  (the contention killer from the
                                  previous lesson)

  APPROXIMATE: write 1 time in 100, and add 100

      if (Math.random() < 0.01)
        db.articles.updateOne({_id}, { $inc: { views: 100 } })

      220 writes/s   (100x fewer)

  MEASURED ERROR after 1M views: p50 0.4%, p95 2.8%, max 4.1%

  WHEN THIS IS FINE            WHEN IT IS NOT
    view counts                  anything billed
    "trending" scores            inventory
    non-billed API usage         audit trails
    progress bars                money, ever

  Two refinements worth knowing:
    - Scale the probability with popularity, so cold documents stay
      exact and only hot ones approximate.
    - Or batch in the application: accumulate in memory for 10s and
      flush one $inc. Exact totals, 100x fewer writes, at the cost
      of losing at most 10s of counts if the process dies.

Part 4 — Subset: The Pattern Whose Payoff Is Cache

Pressure: documents whose bulk is rarely read, evicting the parts that always are. This is lesson 1's working-set arithmetic showing up as a schema decision.

  BEFORE: product with all 2,900 reviews embedded
      avg document                    3.4 MB
      500,000 products
      working set (all hot products)   42 GB
      cache                            16 GB   -> constant eviction
      product page p99                340 ms

  AFTER: subset - keep only what the page renders
      products: { _id, name, priceCents,
                  reviewCount: 2900, avgRating: 4.3,
                  topReviews: [ {...}, {...}, {...} ] }   // 3 only
      reviews:  { _id, productId, rating, body, createdAt }
                index { productId: 1, createdAt: -1 }

      avg document                     34 KB   (100x smaller)
      working set                     1.1 GB   -> fits, permanently
      product page p99                   2 ms
      "see all reviews" (a minority)    18 ms, paginated
🔑 The subset pattern is not really about document size — it is about what fraction of your bytes are hot. The right question is never "is this document big?" but "what proportion of this document does the common read path actually use?" A 3.4 MB document where every byte is rendered is fine. A 3.4 MB document where 34 KB is rendered is a cache problem wearing a schema costume.

Keeping the subset correct is the only real work in the pattern:

  ON NEW REVIEW - one update maintains count, average and top-3
    db.products.updateOne({ _id: pid }, [
      { $set: {
          reviewCount: { $add: ["$reviewCount", 1] },
          avgRating: { $round: [ { $divide: [
              { $add: [ { $multiply: ["$avgRating", "$reviewCount"] },
                        newReview.rating ] },
              { $add: ["$reviewCount", 1] } ] }, 2 ] },
          topReviews: { $slice: [
              { $concatArrays: [[newReview], "$topReviews"] }, 3 ] }
      } }
    ])

  A pipeline update, so it is ONE atomic operation with no
  read-modify-write (see the CRUD lesson). And keep the nightly
  recompute job, per the note above.

Part 5 — Attribute, Polymorphic and Single-Collection

The attribute pattern

Pressure: fields that vary per document or per tenant, all of which must be queryable. You cannot index paths you do not know.

  THE PROBLEM: user-defined fields as field NAMES
    { custom: { "Renewal Date": ISODate(...), "ARR (USD)": 41000 } }
    2,000 tenants x 8 fields = 16,000 index paths needed.
    The limit is 64 indexes per collection. Impossible.

  THE PATTERN: values become data, names become a fixed small set
    { attrs: [ { k: "f_renewal", t: "date", d: ISODate(...) },
               { k: "f_arr",     t: "dec",  n: NumberDecimal(...) } ] }

    ONE index serves every tenant and every field:
      db.contacts.createIndex({ tenantId: 1, "attrs.k": 1, "attrs.d": 1 })

  THE COSTS, stated honestly:
    - Every query needs $elemMatch (two conditions on one element)
    - Sorting on a custom field is awkward - multikey index entries
      are per element, so it needs $unwind/$sort or a denormalised
      sort key for the two or three fields tenants actually sort by
    - Typed value slots (d/n/s) are needed to avoid the mixed-type
      bracketing bug; one polymorphic 'v' field reintroduces it

  Use it when fields are genuinely open-ended. Do NOT use it for a
  fixed schema with 20 known fields - you would be paying the
  ergonomic cost for nothing.

Polymorphic and single-collection

  POLYMORPHIC: similar entities, different shapes, one collection,
  because they are queried TOGETHER.

    { _id, type: "card",   last4: "4242", expiry: "09/28" }
    { _id, type: "bank",   sortCode: "..", accountLast4: "8891" }
    { _id, type: "wallet", provider: "applepay", token: "..." }

    One query lists a customer's payment methods regardless of type.
    A discriminator field (type) plus per-type validation via
    $jsonSchema oneOf keeps it honest - see schema validation.

  SINGLE-COLLECTION: a step further - different ENTITY TYPES in one
  collection, co-located by a shared key so one query returns a
  whole object graph.

    { _id: "order_4192",       type: "order",  customerId: ..., ... }
    { _id: "orderitem_88_1",   type: "item",   orderId: "order_4192" }
    { _id: "orderevent_88_9",  type: "event",  orderId: "order_4192" }

    index { orderId: 1, type: 1 }
    -> find({ orderId: "order_4192" }) returns the order, its items
       and its history in ONE indexed query, no $lookup, while each
       piece stays independently writable (no write amplification,
       no contention on one big document).

  This is the pattern for "I want embedding's read performance but
  the children are too numerous or too hot to embed". It costs you
  clarity: one collection now holds several shapes, so validation
  and tooling get harder. Reach for it when the read path demands
  it, not by default.

Part 6 — Outlier, Versioning, and Trees

The outlier pattern

  Pressure: the design is right for 99.98% of documents and
  catastrophic for the rest. (The celebrity with 2.4M followers;
  the wholesale account with 41,000 orders.)

  Do NOT redesign for the outlier - that makes every ordinary
  document pay for the exception. FLAG it and branch:

    { _id: userId, followers: [ ...up to 5,000... ],
      hasOverflow: true }                    // only on outliers
    { _id: ..., userId, page: 1, followers: [ ... ] }  // overflow docs

    Read path:
      if (!user.hasOverflow) return user.followers;   // 99.98%
      return [...user.followers, ...await overflow(userId)];

  The cost is two code paths, and the benefit is that the common
  case stays optimal. State the threshold explicitly and alert when
  the outlier PROPORTION grows - if 8% of documents become outliers,
  the design premise has expired and it is time to redesign.

The schema versioning pattern

  Pressure: the shape must change, on live data, without a
  maintenance window and without rewriting 40M documents in one go.

    { _id: ..., schemaVersion: 3, ... }

  Readers understand versions >= N and upgrade lazily:

    function toV3(doc) {
      if (doc.schemaVersion === 3) return doc
      if (doc.schemaVersion === 2) doc = upgrade2to3(doc)
      ...
      return doc
    }
    // optionally write it back on read ("migrate on touch")

  MEASURED after 6 months on a 40M-document collection:
      59% upgraded through normal traffic
      41% never touched, still v1 - and completely fine

  The dormant 41% is the POINT, not a failure: you paid nothing to
  migrate documents nobody reads. Run a background sweeper only
  when you actually want to retire the old reader code, and keep
  the version field forever - it is 4 bytes and it is the only
  thing that will tell you what you are looking at in three years.

Four ways to store a tree

ModelShapeGood atBad at
Parent reference{_id, parentId}Moves (one field), immediate parentSubtree queries — needs recursion or $graphLookup

MEASURED: a 6-level category tree, 240,000 nodes
"give me everything under Electronics" (18,000 descendants)

  parent reference + $graphLookup        640 ms
  ancestors array, index {ancestors: 1}    8 ms
      db.cats.find({ ancestors: electronicsId })
  materialised path, index {path: 1}       9 ms
      db.cats.find({ path: /^\/root\/electronics\// })
      ^ ANCHORED regex - unanchored would scan (queries lesson)

THE TRADE, stated plainly:
  moving a subtree with 18,000 descendants
      parent reference        1 document updated
      ancestors / path   18,000 documents updated (2.1 s bulk)

  Reads dominate in every catalogue, category tree and org chart
  I have seen, and moves are rare and human-initiated. So the
  ancestors array is the default - but store parentId ALONGSIDE it,
  because it is the cheap source of truth to rebuild from when a
  move goes wrong.
💡 Patterns compose, and real schemas use several at once. The sensor collection in Part 2 is bucket plus computed (the running sum/min/ max in each bucket). The product in Part 4 is subset plus computed (avgRating) plus extended reference. Do not look for the one right pattern — look for each pressure and answer it.

Interview Questions

Beginner: What is the bucket pattern and what problem does it solve?

Grouping many small related documents into one document holding an array of them — for example, one document per sensor per hour containing that hour's 60 readings, instead of 60 separate documents.

It solves per-document overhead. Every document carries its own _id, its own copies of all the field names, and its own entry in every index. At high event volume that overhead outweighs the data. Measured on 86.4M sensor readings: 41 GB of storage became 3.2 GB, the index went from 3.9 GB to 71 MB, and a "last 24 hours" query went from 2,400 ms to 40 ms — reading 24 documents instead of 1,440 random ones.

The index shrinking is the win that matters most, because a 71 MB index stays in cache and a 3.9 GB one does not.

The trap is over-correcting: a bucket that grows too large recreates write amplification, since every append rewrites the whole document. Cap the bucket in the upsert filter (count: {$lt: 60}) and aim for documents in the tens of kilobytes.

Beginner: When would you precompute a value rather than calculate it on read?

When reads dominate writes, or when read latency is the product. The deciding number is the read-to-write ratio for that value.

In a measured case a dashboard aggregated 4.2M orders on every load — 3,100 ms, 340 times an hour, recomputing identical arithmetic. Maintaining a rollup with $inc on each order made the dashboard read 12 documents in 4 ms.

The honest version of the rule: at 340 reads against 900 writes per hour, precomputing does more total work. It is still right here, because a user waits 3 seconds for the read and nobody waits for the write. But at two reads a day I would compute on read and cache if needed.

One thing I would always add: keep a scheduled job that recomputes the rollup from source. Incremental counters drift from failed writes and bugs, and without a recompute path "the numbers are wrong" becomes unfixable.

Mid: A product document is 3.4 MB and the page is slow. Walk me through the fix.

First I would establish what proportion of those bytes the page actually renders, because that decides whether size is the problem at all. In the measured case the page showed a name, a price, a rating average and three reviews — roughly 34 KB — while 2,900 embedded reviews made up the rest.

So this is a working-set problem, not a document-size problem per se. 500,000 products at 3.4 MB gave a 42 GB working set against a 16 GB cache, so the hot pages were constantly evicted and p99 sat at 340 ms.

The subset pattern: keep reviewCount, avgRating and the top three reviews in the product; move the rest to a reviews collection indexed on {productId, createdAt}. Measured result: documents 34 KB, working set 1.1 GB — fits permanently — and p99 of 2 ms. "See all reviews" becomes a second paginated query at 18 ms that most visitors never make.

Two details I would not skip: maintain the summary in a single pipeline update so there is no read-modify-write race, and add a nightly recompute so avgRating cannot drift silently.

And the secondary benefit worth naming: this also fixes write amplification. Every review previously rewrote a 3.4 MB document.

Mid: How would you store a category tree that needs fast subtree queries?

An ancestors array, with parentId stored alongside it.

{ _id: "cat_tv", name: "Televisions", parentId: "cat_electronics",
  ancestors: ["cat_root", "cat_electronics"] }
db.cats.createIndex({ ancestors: 1 })
db.cats.find({ ancestors: "cat_electronics" })   // whole subtree

Measured on a 240,000-node, six-level tree returning 18,000 descendants: 8 ms with the ancestors array against 640 ms for $graphLookup over parent references. A materialised path (/root/electronics/tv) with an anchored regex performs equivalently at 9 ms and is more human-readable; an unanchored regex would scan.

The trade-off I would state up front: moving a subtree means rewriting every descendant — 18,000 documents, 2.1 s as a bulk write — where a parent reference would be a one-field update. That is the right trade for catalogues, category trees and org charts, where reads vastly outnumber moves and moves are rare and human-initiated. If the workload were reorganisation- heavy, I would reconsider.

Keeping parentId as well costs almost nothing and gives you the authoritative structure to rebuild the denormalised ancestors from when a move is interrupted halfway.

Senior: How would you change a document shape across 40M live documents?

Not in one pass. A big-bang updateMany over 40M documents is hours of write storm, a replication-lag event, no partial rollback, and it needs a window nobody wants to give you.

The schema versioning pattern. Add schemaVersion to every document, teach readers to understand more than one version, and upgrade lazily:

function read(doc) {
  if (doc.schemaVersion === 2) return doc
  const up = upgrade1to2(doc)
  // optional: write it back on touch
  return up
}

Then the rollout is staged and each stage is reversible: deploy dual-capable readers → start writing v2 for new and touched documents → optionally sweep the remainder in throttled batches → retire the v1 reader path only once the sweep is complete.

The measured outcome worth quoting: after six months on a 40M-document collection, 59% had upgraded through ordinary traffic and 41% had never been touched. That dormant 41% is the point of the pattern, not a failure — you paid nothing to migrate documents nobody reads.

Three things I insist on: additive changes first (write the new field before removing the old, so every stage is reversible); a throttled sweeper that watches replication lag rather than running flat out; and keep the version field forever. It is four bytes, and it is the only thing that will tell you what you are looking at in three years.

Senior: A junior engineer proposes the attribute pattern for a new service. How do you evaluate it?

I would ask one question: are the field names known at design time? That single answer decides it, and it turns a stylistic debate into a factual one.

If the fields are open-ended — tenants define their own, or entities have hundreds of sparse attributes — the pattern is not just reasonable, it is the only thing that works. Field names cannot be indexed generically: 2,000 tenants with 8 custom fields each would need 16,000 index paths against a 64-index limit. The attribute pattern turns that into one index on {tenantId, "attrs.k", "attrs.d"}.

If the fields are a known, fixed set of twenty, it is over-engineering and I would push back with the specific costs rather than a general objection:

  • Every query needs $elemMatch, because two conditions must match the same array element — easy to get wrong, and wrong silently.
  • Sorting is awkward: multikey index entries are per element, so sorting on an attribute needs $unwind/$sort or a denormalised sort key.
  • $jsonSchema validation gets much weaker — you can no longer assert that price is a decimal, only that some element has a numeric slot.
  • Every developer and every BI tool now needs to understand the encoding.

If the answer is "mostly fixed, with some custom fields" — which it usually is — the right design is both: real fields for the known schema, plus an attrs array for the custom ones. That is the version I would propose, and I would also insist on typed value slots (d/n/s) rather than one polymorphic v, because a single mixed-type field reintroduces the type-bracketing bug deliberately.

}
Solution

Bug 1 — read-modify-write, so the cap is not enforced. Two concurrent writers both read a bucket with count: 59, both see room, and both push. The bucket ends at 61 elements. Worse, at the boundary both may take the insertOne branch and create two buckets for the same hour, so a later range query silently returns readings twice.

Bug 2 — no upsert, so the create path races. Two writers arriving for a new hour both find nothing and both insert. Same duplicate-bucket outcome as the upsert race in the CRUD lesson.

The fix is one operation with the cap in the filter:

await readings.updateOne(
  { sensorId, hour, count: { $lt: 60 } },        // cap enforced here
  { $push: { readings: r },
    $inc:  { count: 1, sum: r.v },
    $min:  { min: r.v }, $max: { max: r.v },
    $setOnInsert: { first: r.t } },
  { upsert: true }
)

The filter and the modification are evaluated atomically against the same document, so the cap cannot be exceeded. When the current bucket is full nothing matches and the upsert creates the next one — the buckets manage themselves.

And the piece that is still missing: a unique index, or the upsert has the race from Part 4 of the CRUD lesson.

db.readings.createIndex({ sensorId: 1, hour: 1, count: 1 })
// plus a uniqueness guarantee on the bucket identity, most simply
// by making _id the bucket key itself:
//   _id: { sensorId, hour, seq }

Making the bucket identity the _id is the cleanest version: the unique index already exists and cannot be forgotten.

3 (medium): Design the schema for an IoT platform: 40,000 devices, one reading every 10 seconds, 18 months retention, dashboards showing per-device hourly averages and a fleet-wide daily summary. Justify the pattern choices with arithmetic.
Solution

Start with the volume, because it decides everything:

40,000 devices x 6 readings/min x 60 x 24 = 345,600,000 readings/day
x 548 days retention = 189 BILLION readings

One document each is not a design, it is a bill.

Layer 1 — raw, in a native time-series collection. This is genuine time-series data with no need to update past readings, so I do not hand-bucket:

db.createCollection("readings", {
  timeseries: { timeField: "ts", metaField: "deviceId",
                granularity: "seconds" },
  expireAfterSeconds: 7776000            // 90 days of raw
})

It buckets internally and compresses per field columnar — measured at roughly 3.5× better than hand-rolled bucketing, with ordinary one-document-at-a-time inserts.

Layer 2 — hourly rollups (computed pattern), maintained on write:

hourly: { _id: { deviceId, hour },
          count, sum, min, max, sumSq }   // sumSq -> stddev later
db.hourly.createIndex({ "_id.deviceId": 1, "_id.hour": 1 })

The arithmetic that justifies it: a 30-day device chart from raw data means scanning 259,200 readings. From hourly rollups it is 720 documents — about 360× less work, on every dashboard load. Storing sum and count rather than a precomputed average is deliberate: averages do not compose, but sums and counts roll up into daily figures for free.

Layer 3 — daily fleet summary, one document per day built by a scheduled job from layer 2, not from raw. The fleet dashboard then reads a single document.

Retention, which is where the money is:

LayerRetentionVolumeWhy
Raw90 days (TTL)31B readingsDebugging and incident forensics only
Hourly18 months~526M docsServes every device chart
DailyForever~548 docsTrivial, and answers most questions

Keeping 18 months of raw data to serve charts that read hourly aggregates would be paying roughly six times over for data nobody queries.

Two things I would flag in review. First, TTL deletion of that volume is a real operational event — never shorten the retention window in one step (CRUD lesson), and consider dropping whole partitioned collections instead. Second, the rollup needs a recompute-from-source job; incremental counters over 345M writes/day will drift, and without a recompute path a drift incident is unfixable.

4 (medium): A "trending posts" score is recomputed by aggregating all likes and comments on every homepage load — 900 ms, 40,000 loads/hour. Design the fix, and say what you would do about the score being slightly stale.
Solution

The ratio decides it immediately: 40,000 reads/hour against maybe 2,000 engagement writes/hour is 20:1. Precompute without hesitating.

Maintain the score incrementally on each engagement:

db.posts.updateOne({ _id: postId },
  { $inc: { likes: 1, hotScore: 1.0 } })

But a trending score must decay, and decay is not incremental — this is the part that makes the exercise more than "add a counter". Two workable designs:

Periodic decay jobTime-anchored score
HowEvery 10 min: $mul: {hotScore: 0.9} over candidatesStore log(engagements) + createdAt/45000 — a Hacker-News-style score that never needs decaying
CostA recurring write over the candidate setZero — the score only ever goes up, and newer posts start higher
RiskThe job stops and trending silently freezesNeeds care with float precision over years

I would ship the time-anchored score: it needs no scheduled job, so it has no failure mode where trending quietly stops updating — which is the kind of outage nobody alerts on because nothing errors.

Then serve the homepage from a materialised list, not from a sort over all posts:

// one document, rebuilt every 60s
{ _id: "trending:global", updatedAt: ..., posts: [ {...20 items...} ] }

One findOne per homepage load — a few milliseconds, and it also removes the sort load from the posts collection entirely.

On staleness, which is the real question: a trending list is inherently a summary of the recent past. A 60-second lag is invisible to users and, unlike an account balance, being slightly behind is not a correctness defect. I would make the freshness explicit (updatedAt in the document), alert if it exceeds a few minutes — because a frozen trending list is the actual failure mode here — and let the requirement be a stated product decision rather than an accident.

5 (hard): A multi-tenant CRM stores contacts. Tenants add custom fields; some tenants have 200,000 contacts and others have 12. Some contacts have 400 activity records, one has 2.1M. Design the schema, applying every pattern that earns its place — and say which ones you deliberately rejected.
Solution

Four distinct pressures here, and each gets its own answer. The skill this tests is not knowing the patterns but refusing to apply the ones that do not earn their place.

Pressure 1: custom fields → attribute pattern, but hybrid.

contacts: {
  _id, tenantId,
  name, email, phone, ownerId, createdAt,   // fixed schema: REAL fields
  attrs: [ { k: "f_renewal", t: "date", d: ISODate(...) },
           { k: "f_arr",     t: "dec",  n: NumberDecimal(...) } ],
  activityCount: 412, lastActivityAt: ISODate(...),
  recentActivity: [ {...}, {...}, {...} ],   // subset: last 3
  hasActivityOverflow: false,
  schemaVersion: 2
}
db.contacts.createIndex({ tenantId: 1, "attrs.k": 1, "attrs.d": 1 })
db.contacts.createIndex({ tenantId: 1, email: 1 })

The known fields stay real fields — full validation, natural queries, ordinary indexes. Only the genuinely open-ended ones go into attrs. Applying the attribute pattern to email would be paying the $elemMatch tax for nothing.

Pressure 2: activity volume → reference, plus subset. Activities are their own collection indexed {contactId, createdAt: -1}; the contact carries a count, a last timestamp and the three most recent for rendering. The contact page needs one query.

Pressure 3: the 2.1M-activity contact → outlier, handled by the same design. Because activities are already referenced, the outlier costs nothing structurally — it is just a contact with more child rows. What it does break is any "count activities" query, so activityCount is maintained with $inc rather than counted, and any UI that would render an unbounded list is paginated. This is worth saying explicitly in a review: the outlier pattern's flag-and-branch machinery is unnecessary here precisely because the earlier reference decision already absorbed it.

Pressure 4: tenant size skew (12 to 200,000 contacts) → tenantId first in every index. Every query is tenant-scoped, so tenantId leads every compound index and every filter. For the small tenants this makes queries nearly free; for the large ones it keeps the scan bounded to their slice. If the platform later shards, tenantId is also the natural shard key prefix — though a single 200,000-contact tenant would make it a jumbo-chunk risk worth revisiting then.

What I deliberately rejected, and why:

PatternWhy not
Bucket (on activities)Activities are read individually and edited; bucketing would trade a real ergonomic cost for storage nobody is complaining about. Revisit if volume, not variety, becomes the pressure
Collection-per-tenant2,000 tenants × several collections is an operational disaster — index builds, migrations and backups multiply by tenant count
Approximation (on activityCount)Users see this number next to a list they can page through; an inconsistency is a visible bug, and the write rate does not justify it
Polymorphic contactsContacts are one entity type. The custom fields are variation within a type, which is what the attribute pattern is for

And schemaVersion from day one, because a multi-tenant CRM's shape will change and there will never be a maintenance window in which to change it.

6 (hard): You inherit a system where the computed pattern has drifted: orderCount on 1.2M customer documents disagrees with the orders collection for an unknown number of customers. Design the detection, the repair, and the prevention.
Solution

1. Quantify before touching anything. "An unknown number" is the actual problem — the size and shape of the drift determines whether this is a bug hunt or a one-off correction:

db.orders.aggregate([
  { $group: { _id: "$customerId", actual: { $sum: 1 } } },
  { $lookup: { from: "customers", localField: "_id",
               foreignField: "_id", as: "c" } },
  { $unwind: "$c" },
  { $project: { actual: 1, stored: "$c.orderCount",
                diff: { $subtract: ["$actual", "$c.orderCount"] } } },
  { $match: { diff: { $ne: 0 } } },
  { $group: { _id: null, n: { $sum: 1 },
              over:  { $sum: { $cond: [{ $gt: ["$diff", 0] }, 1, 0] } },
              under: { $sum: { $cond: [{ $lt: ["$diff", 0] }, 1, 0] } },
              worst: { $max: { $abs: "$diff" } } } }
])

Read the direction of the skew — it names the bug. If stored counts are uniformly low, some write path increments and some does not (an import script, a bulk tool). If they are high, deletions or cancellations decrement nowhere. If the drift correlates with a date, a deploy introduced it. That inference is the highest-value output of this step, and it is why quantifying comes before repairing.

2. Repair from source, in throttled batches — never one giant updateMany over 1.2M documents:

// batches of 1,000 customers, resumable by _id
const agg = await orders.aggregate([
  { $match: { customerId: { $in: batchIds } } },
  { $group: { _id: "$customerId", actual: { $sum: 1 } } }
]).toArray()
await customers.bulkWrite(agg.map(a => ({
  updateOne: { filter: { _id: a._id },
               update: { $set: { orderCount: a.actual,
                                 orderCountVerifiedAt: new Date() } } }
})), { ordered: false })

Customers with zero orders need explicit handling — they produce no aggregation group, so a separate pass must zero them, and that is exactly the case a naive repair silently misses.

3. Prevention, in three layers, because no single one is sufficient:

  • One write path. The drift exists because several places create orders and only some increment. Funnel order creation through one function; the count update belongs with the insert, not scattered across callers.
  • A scheduled reconciler — the same aggregation, run nightly over a rolling slice, correcting and reporting. This should have existed from the start; the computed pattern without a recompute path is drift with a delay.
  • An alert on the drift rate, not on drift itself. A handful of stale counters is normal in an eventually-consistent design. A step change in the count of drifted documents means a deploy broke a write path, and that is the signal worth waking someone for.

4. Then ask the question everyone skips: does orderCount need to be stored at all? If it is read on a page that already queries orders, a countDocuments({customerId}) against an existing index may be a few milliseconds and removes this entire class of bug permanently. The computed pattern is a performance optimisation, and an optimisation whose maintenance cost exceeds its benefit should be deleted rather than repaired. I would check the read path before rebuilding the machinery.

🎯 Key Takeaways

  • Every pattern answers a measured pressure. Name the pressure first; a pattern without one is just complexity you chose to carry.
  • Bucket beats per-document overhead: 86.4M docs → 1.44M, storage 41 GB → 3.2 GB, index 3.9 GB → 71 MB, query 2,400 ms → 40 ms.
  • Cap buckets in the upsert filter, not in application code — the database then enforces the bound under concurrency, and buckets roll over by themselves.
  • Do not hand-bucket genuine time-series data — a native time-series collection measured 0.9 GB against 3.2 GB, with no custom insert logic.
  • Computed trades staleness for latency: a dashboard went 3,100 ms → 4 ms. Check the read:write ratio first, and store sum+count rather than an average, because averages do not compose.
  • Every incremental rollup needs a recompute-from-source job, written at the same time — otherwise drift becomes unfixable.
  • Approximation cut 22,000 writes/s to 220 with p95 error 2.8% — correct for view counts, fraud for anything billed.
  • Subset is about hot fraction, not document size: 42 GB working set → 1.1 GB, p99 340 ms → 2 ms. Ask what proportion of the bytes the common read path uses.
  • Attribute replaces 16,000 impossible indexes with one — but costs $elemMatch everywhere and awkward sorts. Use it only for genuinely open-ended fields, and prefer the hybrid: real fields for the known schema.
  • Typed value slots in the attribute pattern; one polymorphic v field reintroduces type bracketing deliberately.
  • Polymorphic and single-collection co-locate different shapes so one indexed query returns a whole object graph — embedding's read performance without its write amplification.
  • Outlier: flag and branch. Never make the 99.98% pay for the exception — and alert when the outlier proportion grows, because that means the premise expired.
  • Schema versioning makes migrations lazy and reversible. After six months, 41% of documents were never touched — that is the payoff, not a failure. Keep the version field forever.
  • For trees, an ancestors array is the default: 8 ms versus 640 ms for $graphLookup. Keep parentId alongside it as the source of truth to rebuild from.
  • Anchor every materialised-path regex — unanchored means a collection scan.
  • Patterns compose. Real schemas are bucket + computed, or subset + computed + extended reference. Answer each pressure, rather than hunting for the one right pattern.
