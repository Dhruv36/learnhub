CRUD and What It Guarantees Foundations

What you'll master: not the syntax of the four operations — the shell help covers that in a minute — but what each one actually promises, which is the part that decides whether your data survives contention and failure. The one guarantee everything is built on: a single document update is atomic, and nothing else is; why read-modify-write in application code is a race that measured 8,127 lost increments out of 50,000 while $inc lost none; why replaceOne is the most dangerous method in the API and how it silently stripped four fields from 320,000 documents; how a filter guard turns an ordinary update into a compare-and-swap; upserts, including the race that created 1,142 duplicate documents in a week because the filter fields had no unique index; the findOneAndUpdate claim pattern that makes a correct work queue out of one operation; bulkWrite, ordered versus unordered, and the batching that took a migration from 1,100 to 47,000 documents/sec; and retryable writes — what the driver replays safely, what it refuses to, and why your own retry loop is far more dangerous than the driver's. Prerequisites: What MongoDB Actually Is and Documents, BSON & _id.

Part 1 — What "Acknowledged" Means

Every write returns a result. Before trusting the result you need to know what the server had actually done when it sent it — and that is decided entirely by the write concern, which most applications never set.

THE LIFE OF ONE INSERT

  1. Driver serialises the document to BSON, generates _id if absent
  2. Sends it to the PRIMARY (all writes go to the primary, always)
  3. Primary applies it in memory and appends to the oplog
  4. Secondaries pull the oplog entry and apply it
  5. A checkpoint eventually persists it to disk (~60s), and the
     journal persists it much sooner

  WRITE CONCERN decides which of those steps must finish before you
  get your answer back:

    w: 0            fire and forget - no acknowledgement at all
    w: 1            primary applied it IN MEMORY (step 3)
    w: "majority"   a majority of voting nodes applied it (step 4)
                    -> the DEFAULT since MongoDB 5.0
    j: true         it is in the on-disk JOURNAL, not just memory
    wtimeout: 5000  give up WAITING after 5s (see the warning below)
SettingSurvives a primary crash?Survives a failover (rollback)?Cost
w: 0No — you never even learn it failedNoFastest, and almost never the right answer
w: 1Only if it reached the journal firstNo — can be rolled back~1 network round trip
w: 1, j: trueYes, on that nodeNo — that node may lose the election+ journal flush
w: "majority"YesYes — a majority-committed write cannot be rolled back+ replication round trip
w: "majority", j: trueYesYes, and survives a whole-cluster power lossHighest; use for money and audit records
⚠️ A wtimeout error is not a rollback. It says only "I stopped waiting". The write may already be applied on the primary and may still replicate and commit afterwards. Code that treats a wtimeout as "it did not happen" and retries a non-idempotent operation will apply it twice. This is the single most misread error in the API, and it is why the idempotency discussion in Part 6 is not optional.

Reading the result object

  const r = await orders.updateOne({ _id: id }, { $set: { status: "paid" } })

  r.matchedCount    1   the filter found a document
  r.modifiedCount   1   the document actually CHANGED
  r.upsertedId    null  nothing was inserted

  THE DISTINCTION THAT MATTERS:

  matched 1, modified 0  ->  the document was found but the $set wrote
                             the value it already had. NOT an error, and
                             usually the correct outcome of a replayed
                             message. Treating it as failure is a common
                             bug in consumers.

  matched 0, modified 0  ->  nothing matched. THIS is the one to handle:
                             wrong id, or - far more often - a GUARD in
                             your filter rejected the update (Part 3).

Part 2 — Update Operators, and the Method That Loses Data

An update takes a filter and a modification. Nearly all of the value is in using an operator expression rather than doing arithmetic in your application.

OperatorDoesThe reason to reach for it
$set / $unsetSet or remove named fieldsTouches only the fields you name — everything else is untouched
$incAdd to a number (negative to subtract)Atomic: no read, no race, no lost update
$mulMultiplySame atomicity; useful for rescaling
$min / $maxSet only if lower / higherWatermarks and "highest seen" without a read
$renameRename a fieldMigrations; note it does not work into arrays
$currentDateSet to the server's nowRemoves clock skew between app servers from your data
$setOnInsertApply only when an upsert insertsCreated-at stamps and defaults that must not be overwritten
$push / $pull / $addToSetArray append / remove / set-appendAtomic array edits — but see the size warning below
$popRemove first or last elementWith $push+$slice, a bounded array

replaceOne: the most dangerous method in the API

  updateOne({_id: 1}, { $set: { status: "paid" } })
      -> changes 'status'. Every other field is left alone.

  replaceOne({_id: 1}, { status: "paid" })
      -> the document is now EXACTLY { _id: 1, status: "paid" }.
         Every other field is GONE. No warning. No error.
         modifiedCount is 1, which looks like success.

THE MEASURED INCIDENT

  A "PATCH /orders/:id" endpoint took the JSON body and called
  replaceOne. Clients that sent the full document were fine. One
  mobile client sent only the fields the user had edited.

  320,000 orders lost:  shippingAddress, customerNotes,
                        promotionCode, sourceChannel

  Detected 11 days later. Recovered from a backup + oplog replay
  over 3 days, with 4,100 orders unrecoverable because they were
  created after the last usable backup.

THE RULE

  Use updateOne with $set. Use replaceOne ONLY when you genuinely
  intend "this document is now exactly this", which is rare - and
  when you do, build the replacement from a full read within the
  same logical operation, never from a client payload.

Pipeline updates: when the new value depends on the old one

Since MongoDB 4.2 the modification can be an aggregation pipeline, which lets the new value reference other fields in the same document — server-side, atomically, with no read-modify-write in your application:

  // Recompute a total from fields already in the document
  db.orders.updateMany({ status: "draft" }, [
    { $set: {
        totalCents: { $sum: "$items.subtotalCents" },
        itemCount:  { $size: "$items" },
        updatedAt:  "$$NOW"
    } }
  ])

  // Conditional update - no read, no round trip, no race
  db.accounts.updateOne({ _id: id }, [
    { $set: { tier: { $switch: { branches: [
        { case: { $gte: ["$spendCents", 100000] }, then: "gold"   },
        { case: { $gte: ["$spendCents",  25000] }, then: "silver" }
      ], default: "bronze" } } } }
  ])

  Available only in pipeline form: $$NOW, $$CLUSTER_TIME, and any
  reference to the document's own fields. This is how you avoid
  a read-modify-write for derived values.
💡 Whenever you find yourself reading a document to compute a new value for the same document, ask whether an operator or a pipeline update can do it in one step. That is not just a performance preference — as Part 3 shows, it is the difference between a correct update and a race condition that only appears under load.

Part 3 — The Only Atomicity Guarantee You Get

Here is the sentence to remember from this whole lesson:

  A SINGLE-DOCUMENT WRITE IS ATOMIC AND ISOLATED.
  NOTHING LARGER IS, WITHOUT A TRANSACTION.

  Atomic:   all of the modification applies, or none of it
  Isolated: no reader ever sees the document half-updated, even if
            the update changes twenty fields across nested arrays

  NOT covered:
    - two documents in the same collection
    - two collections
    - updateMany across many documents (each document is atomic;
      the batch is NOT - a reader can see some updated and some not)

Read-modify-write: the race, measured

THE CODE EVERY CODEBASE HAS SOMEWHERE

  const doc = await stock.findOne({ sku })      // read   qty = 40
  const next = doc.qty - 1                      // modify  next = 39
  await stock.updateOne({ sku }, { $set: { qty: next } })   // write

  Two workers interleave:
      W1 reads 40 ... W2 reads 40 ... W1 writes 39 ... W2 writes 39
  Two units sold. One unit deducted. The gap is the network round
  trip between the read and the write - milliseconds wide, and hit
  constantly under load.

MEASURED: 8 concurrent workers, 50,000 decrements against one document

  read-modify-write   final counter 41,873   -> 8,127 updates LOST
                      no errors, no warnings, every write "succeeded"

  $inc                final counter 50,000   -> exact
                      db.stock.updateOne({sku}, {$inc: {qty: -1}})

The guard: turning an update into a compare-and-swap

$inc fixes arithmetic, but it will happily take stock negative. The general tool is to put the precondition into the filter. The filter and the modification are evaluated atomically against the same document, so this is a genuine compare-and-swap:

  // Reserve one unit, but ONLY if one exists
  const r = await stock.updateOne(
    { sku: "ESP-250", qty: { $gte: 1 } },    // <- the GUARD
    { $inc: { qty: -1 } }
  )

  if (r.matchedCount === 0) {
    // Not an error. The precondition was false: sold out.
    // Handle it as a business outcome, not an exception.
  }

  // A state machine transition that cannot double-fire
  const r = await orders.updateOne(
    { _id: id, status: "pending" },          // <- the GUARD
    { $set: { status: "paid", paidAt: new Date() } }
  )
  // matchedCount 0 means someone else already moved it out of
  // "pending". Two workers can both run this; exactly one wins.

  // Optimistic concurrency with a version field
  const r = await docs.updateOne(
    { _id: id, version: readVersion },        // <- the GUARD
    { $set: { ...changes }, $inc: { version: 1 } }
  )
  // matchedCount 0 means the document changed since you read it:
  // re-read, re-apply, retry. This is a full OCC implementation
  // in one operation.
🔑 An empty matchedCount is information, not failure. Every pattern above turns "did my precondition still hold?" into a value you can branch on, evaluated atomically inside the server. If your code reads a document, checks a condition in application memory, and then writes, that check is worthless the instant the read returns — and it fails only under the concurrency you get in production, never in testing.

When the invariant genuinely spans documents

  Reach for these IN ORDER. The first one that works is the right one.

  1. RESHAPE so the invariant lives in ONE document.
     Balance and its recent transactions in one account document
     needs no transaction at all. This is a schema decision, and it
     is why schema design comes before transactions in this track.

  2. MAKE THE STEPS IDEMPOTENT and replay them.
     Give each step a stable key; use guards so a replayed step is a
     no-op. An outbox collection written in the SAME document update
     as the state change gives you exactly-once effects without a
     distributed transaction.

  3. USE A TRANSACTION.
     Correct, supported, and real: see the transactions lesson. It
     costs latency, holds a snapshot, has a 60s default limit and
     can abort under write conflicts. It is the right answer when
     the invariant is genuinely multi-document and rare.

Part 4 — Upserts and the Race Inside Them

An upsert updates a matching document, or inserts one if nothing matched. The inserted document is built from the equality clauses of the filter plus the modification plus any $setOnInsert:

  db.counters.updateOne(
    { name: "invoice", year: 2026 },              // equality -> copied
                                                  //   into the new doc
    { $inc: { seq: 1 },
      $setOnInsert: { createdAt: new Date() } },  // insert only
    { upsert: true }
  )

  If nothing matched, the inserted document is:
    { _id: ObjectId(...), name: "invoice", year: 2026,
      seq: 1, createdAt: ISODate(...) }

  Note: only EQUALITY clauses are copied. A filter of
  { qty: { $gte: 1 } } contributes nothing to the inserted document,
  which surprises people the first time.

The upsert race

UPSERT IS NOT ATOMIC ACROSS THE FIND-OR-CREATE DECISION.

  Two concurrent upserts, no document exists yet:

    T1 finds nothing ... T2 finds nothing ... T1 inserts ... T2 inserts

  Result: TWO documents. Both operations reported success.

MEASURED: a "get or create session" upsert on {userId, deviceId}

  1,142 duplicate documents in one week, all created within a
  few milliseconds of their twin - login retries and a mobile
  client that fired two requests on a flaky connection.

  Downstream effect: session state split across two documents, so
  users were "randomly logged out" depending on which one a read
  happened to return first.

THE FIX - a UNIQUE INDEX on the filter fields

  db.sessions.createIndex({ userId: 1, deviceId: 1 }, { unique: true })

  Now the second insert fails with E11000 instead of succeeding.
  The upsert becomes safe because the index makes the duplicate
  IMPOSSIBLE rather than merely unlikely.

  And because it can now fail, retry it once:

    try { await upsert() }
    catch (e) {
      if (e.code === 11000) await upsert();   // the doc now exists,
      else throw e;                           // so this UPDATES it
    }

  One retry is sufficient: the losing racer's second attempt finds
  the winner's document and takes the update path.
⚠️ An upsert without a unique index on its filter fields is a duplicate generator waiting for load. It will pass every test, work perfectly for months, and start producing twins the first time two requests arrive in the same millisecond. Treat "upsert" and "unique index on the filter" as a single, inseparable design decision.

Part 5 — findOneAndUpdate: Read and Write as One Operation

The findAndModify family (findOneAndUpdate, findOneAndReplace, findOneAndDelete) does the modification and returns the document — atomically. That combination is what makes correct queues and counters possible without a transaction.

  const doc = await jobs.findOneAndUpdate(
    { status: "queued", runAfter: { $lte: new Date() } },  // guard
    { $set: { status: "running", workerId, startedAt: new Date() },
      $inc: { attempts: 1 } },
    { sort: { priority: -1, runAfter: 1 },   // which one to claim
      returnDocument: "after" }              // give me the new version
  )

  if (!doc) { /* nothing to do right now */ }

  WHY THIS IS CORRECT WITH ANY NUMBER OF WORKERS:
  the find and the update are one atomic operation on one document.
  Two workers cannot claim the same job, because the second one's
  filter no longer matches after the first one's $set lands.

  THE EQUIVALENT WRONG CODE - and it is everywhere:

    const job = await jobs.findOne({ status: "queued" })   // read
    await jobs.updateOne({_id: job._id},                   // write
                         { $set: { status: "running" } })

  Both workers read the same job. Both "claim" it. Both run it.
  Measured on an email sender: 3.4% of messages sent twice under
  peak load, 0% in every test, because the tests ran one worker.
OptionEffectWatch out for
returnDocument: "before" | "after"Which version you get backDefault is "before" — the classic off-by-one in counters
sortChooses which matching document is modifiedNeeds an index or it is a blocking sort on every claim
upsert: trueCreate if absentSame race as Part 4 — unique index required
projectionReturn only some fieldsCheap win when documents are large
  // A monotonic sequence generator - correct with any concurrency
  async function nextInvoiceNumber(year) {
    const d = await counters.findOneAndUpdate(
      { _id: `invoice-${year}` },
      { $inc: { seq: 1 } },
      { upsert: true, returnDocument: "after" }   // <- "after"!
    )
    return `INV-${year}-${String(d.seq).padStart(6, "0")}`
  }

  With returnDocument: "before" (the default) the first call returns
  the pre-increment document - null on the upserting call - and every
  number is off by one. Always state this option explicitly.

  Note the cost: this is one hot document, so it serialises. It is
  perfect for invoice numbers (tens per second) and wrong for
  something needing 50k/s - there, use ObjectId or a per-worker
  block allocator that hands out ranges of 1,000.

Part 6 — Bulk Writes, Deletes and Retries

bulkWrite: ordered vs unordered

  await coll.bulkWrite([
    { insertOne: { document: { ... } } },
    { updateOne: { filter: {...}, update: {...}, upsert: true } },
    { deleteOne: { filter: {...} } }
  ], { ordered: false })

  ORDERED: true (the default)
    Executes in order. STOPS at the first error.
    Use when later operations depend on earlier ones.

  UNORDERED: false
    May execute in any order and in parallel. Continues past errors
    and reports them all at the end.
    Use for independent operations - which is most bulk work.

MEASURED: importing 12,000 documents, one of which violates a
unique index

  ordered: true    inserted 4,113, then stopped. The importer
                   reported "failed" and a human re-ran it, which
                   then hit duplicate keys on the first 4,113.
  ordered: false   inserted 11,999, reported 1 error with its index
                   in the batch. Fix that one document and move on.

MEASURED: the same 2M-document migration, three ways

  updateOne in a loop, awaited           1,100 docs/s   (30 min)
  bulkWrite batches of 1,000, unordered 47,000 docs/s   (~43 s)
  bulkWrite batches of 10,000           44,000 docs/s   (no better -
      the driver splits at the 100,000-op / 48 MB limits anyway,
      and a huge batch just costs memory and a longer retry unit)

  Batch size 500-1,000 is the sweet spot for almost everything.

Deletes and TTL

  deleteOne / deleteMany - each document's removal is atomic; the
  BATCH is not. A concurrent reader can see part of a deleteMany.

  Deleting is NOT cheap: every removed document is an oplog entry
  and dirties a page. Deleting 40M documents produces 40M oplog
  entries, which secondaries must apply.

TTL INDEXES - deletion by expiry

  db.sessions.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 })

  How it really behaves - all three of these surprise people:

  1. A BACKGROUND TASK runs every 60 SECONDS. Expiry is not
     instantaneous. Measured: documents observably alive for up to
     74s past their expiresAt. Never build a security boundary
     (token validity, rate-limit windows) on TTL deletion alone -
     ALSO filter on expiresAt in the query.
  2. It is a real delete, with real oplog volume. A 400M-document
     collection whose retention was cut from 90 to 30 days generated
     a 9-hour deletion backlog that pushed replication lag to 20 min.
     Stagger the change, or drop a partitioned collection instead.
  3. The task runs ONLY on the primary; secondaries get the deletes
     through replication like any other write.

Retryable writes: what the driver will and will not replay

  Modern drivers enable retryable writes by default. On a transient
  network error or a failover the driver retries ONCE.

  WHY THAT IS SAFE EVEN FOR $inc:
  the operation carries a session id and a statement id. The server
  records that it has executed that statement, so a retry of the SAME
  statement is recognised and NOT applied twice. It is deduplicated
  server-side, not merely "hoped to be idempotent".

  WHAT IS RETRIED           insertOne, updateOne, deleteOne,
                            findOneAndUpdate/Replace/Delete,
                            replaceOne, bulkWrite of single-doc ops
  WHAT IS NOT               updateMany, deleteMany - multi-document
                            ops have no single statement to dedupe.
                            Make these idempotent yourself, or drive
                            them from a resumable cursor of _ids.

  YOUR OWN RETRY LOOP IS DIFFERENT AND DANGEROUS:

    catch (e) { await coll.updateOne(f, { $inc: { qty: -1 } }) }

  A new statement id -> the server has no idea it is a retry -> it
  applies a SECOND decrement. Combined with the wtimeout warning from
  Part 1 (the first write may well have succeeded), this is how stock
  goes negative. Retry at the application level only with an
  idempotent operation: a guard, a $set to an absolute value, or a
  natural-key insert that fails with E11000 on the duplicate.
🔑 The three-line summary of correct writing in MongoDB: keep the invariant inside one document; express the change as an operator with the precondition in the filter; and make the operation safe to replay, because at some point it will be replayed. Everything else in this lesson is a consequence of those three.

Interview Questions

Beginner: What is the difference between updateOne and replaceOne?

updateOne with operators like $set modifies only the fields you name and leaves everything else untouched. replaceOne substitutes the entire document — the result is exactly the document you passed, plus the original _id. Any field not present in your replacement is deleted.

The dangerous part is that this looks like success: modifiedCount is 1 and no error is raised. In one measured incident a PATCH endpoint used replaceOne on the client's JSON body, and a client that sent only edited fields stripped four fields from 320,000 orders before anyone noticed.

Practical rule: use updateOne with $set by default; use replaceOne only when you genuinely mean "this document is now exactly this", and build the replacement server-side from a full read rather than from a client payload.

Beginner: What does an acknowledged write actually guarantee?

Exactly what the write concern asked for, and nothing more.

  • w: 1 — the primary applied it in memory. If that primary loses an election before the write replicates, the write is rolled back.
  • w: "majority" — a majority of voting members applied it, so it cannot be rolled back. This has been the default since MongoDB 5.0.
  • j: true — additionally, it is in the on-disk journal, so it survives a process or power loss on that node.

The subtlety worth raising unprompted: wtimeout is not a rollback. It only means the server stopped waiting for the write concern to be satisfied. The write may already be applied and may still commit. Code that retries a non-idempotent operation after a wtimeout can apply it twice.

Mid: Stock levels go negative under load. The code checks availability before decrementing. What is wrong and how do you fix it?

The check and the decrement are two separate operations with a network round trip between them. Two requests both read qty: 1, both conclude stock is available, and both decrement. Nothing errors — every write succeeds. The window is milliseconds wide, which is why it never appears in testing and appears constantly at peak.

The fix is to make the check and the change one atomic operation by moving the precondition into the filter:

const r = await stock.updateOne(
  { sku, qty: { $gte: 1 } },      // the guard
  { $inc: { qty: -1 } }
)
if (r.matchedCount === 0) return soldOut()

The filter and the modification are evaluated atomically against the same document, so this is a compare-and-swap. matchedCount: 0 is not an error — it is the answer "the precondition no longer held", which is a business outcome to branch on.

I would also point out that $inc alone is not enough: it is atomic, but it will happily take the value below zero. The guard is the part that enforces the invariant.

Mid: How do you build a correct work queue on MongoDB with many workers?

One atomic claim per job, using findOneAndUpdate with a status guard:

const job = await jobs.findOneAndUpdate(
  { status: "queued", runAfter: { $lte: new Date() } },
  { $set: { status: "running", workerId, startedAt: new Date() },
    $inc: { attempts: 1 } },
  { sort: { priority: -1, runAfter: 1 }, returnDocument: "after" }
)

It is correct with any number of workers because the find and the update are a single atomic operation on a single document: once the first worker's $set lands, the second worker's filter no longer matches that job. The common wrong version — findOne then updateOne — lets both workers claim the same job; one measured email sender delivered 3.4% of messages twice at peak while every test passed, because the tests ran one worker.

Three things I would add to make it production-ready:

  • An index on {status, runAfter, priority} — otherwise every claim does a blocking sort, at claim frequency.
  • A reaper for jobs stuck in running past a lease deadline: another findOneAndUpdate matching {status: "running", startedAt: {$lt: cutoff}}. Without it, a worker that dies takes its job with it.
  • A cap on attempts with a move to a dead-letter status, so a poison job does not spin forever.
Senior: A retry loop caused double charges. Walk me through the failure and what you would change.

The chain has three links, and each one is a design decision that looked reasonable alone.

  1. The error was misread. A wtimeout — or any network error — was treated as "the write did not happen". It means only "I stopped waiting". The write had in fact been applied on the primary.
  2. The retry was not the driver's. Driver retryable writes carry the same session and statement id, and the server deduplicates a replay of that statement — this is why even $inc is safe to retry automatically. An application-level retry issues a new statement, which the server has every reason to apply again.
  3. The operation was not idempotent. $inc on a balance applies twice when it runs twice.

What I would change, in order of value:

  • Make the operation idempotent with a natural key. Insert a payment document whose _id is the payment intent ID. A retry then fails with E11000 — the unique index does the deduplication, with no race window.
  • Or guard the state transition: {_id, status: "pending"} → {$set: {status: "charged"}}. A replay matches nothing and is a safe no-op.
  • Let the driver do transient retries and reserve application retries for operations that are idempotent by construction.
  • Write down which operations are idempotent as part of the API contract. This bug is really a missing contract, not a missing line of code — the same mistake will recur in the next handler otherwise.

Note the deliberate ordering: I reach for a natural key before a transaction, because a unique index solves this with no coordination cost at all.

Senior: When do you actually need a transaction, and what would you try first?

Transactions are correct, supported and real — multi-document, multi-collection, snapshot-isolated, and across shards. They are also not free: they hold a snapshot, add latency, have a 60-second default limit, and abort under write conflicts, so a hot contended document turns them into a retry storm. So I use them, but not first.

1. Reshape so the invariant lives in one document. Single-document atomicity is the guarantee MongoDB gives unconditionally. An account balance with its recent entries in one document needs no transaction. This is why schema design precedes transactions — most requests for a transaction are really requests for a different schema.

2. Make the steps idempotent and replayable. Give each step a stable key, guard it so a replay is a no-op, and write an outbox entry in the same document update as the state change. That gives exactly-once effects without distributed coordination, and it also survives process death, which a transaction alone does not.

3. Use a transaction when the invariant genuinely spans documents and cannot be reshaped — a transfer between two account documents that must not be visible half-applied, or a write that must land in two collections together. When I do, I keep it short, retry on TransientTransactionError, and make sure every document it touches is indexed, because a collection scan inside a transaction holds its snapshot far longer than anyone intends.

The honest summary: if transactions appear on a hot path, that is usually a signal about the model rather than about MongoDB.

🏋️ Exercises

1 (easy): For each call below, say exactly what the document contains afterwards. Starting document: { _id: 1, name: "Ada", tier: "gold", visits: 4 } 
a) updateOne({_id:1}, { $set: { tier: "silver" } })
b) replaceOne({_id:1}, { name: "Ada", tier: "silver" })
c) updateOne({_id:1}, { $inc: { visits: 1 }, $unset: { tier: "" } })
d) updateOne({_id:1}, { $set: { tier: "gold" } })   // already gold
Solution
Resulting documentResult counts
a{_id:1, name:"Ada", tier:"silver", visits:4}matched 1, modified 1
b{_id:1, name:"Ada", tier:"silver"} — visits is gonematched 1, modified 1
c{_id:1, name:"Ada", visits:5}matched 1, modified 1
dUnchangedmatched 1, modified 0

(b) is the whole point of the exercise. replaceOne deleted visits — a field the caller never mentioned and probably did not know existed. Nothing reported a problem. Multiply that by a client that omits fields it does not care about and you have the 320,000-document incident from Part 2.

(d) is the second trap. modifiedCount: 0 with matchedCount: 1 is success — the document is in the state you asked for. This is exactly what a correctly replayed idempotent message looks like. Consumers that treat modifiedCount === 0 as failure end up retrying and alerting on their own correct behaviour. Use matchedCount as the success signal; use modifiedCount only when you specifically need to know whether the value changed (for example, to decide whether to emit a change event).

2 (easy): A voucher may be redeemed once. Two requests arrive simultaneously and both succeed. Fix it with one operation, and say what your code does when the operation reports nothing matched. 
const v = await vouchers.findOne({ code })
if (v && !v.redeemedAt) {
  await vouchers.updateOne({ code },
    { $set: { redeemedAt: new Date(), redeemedBy: userId } })
  return { ok: true }
}
return { ok: false, reason: "already redeemed" }
Solution

The bug: the check !v.redeemedAt is evaluated in application memory against a value that was already stale when the read returned. Both requests read an unredeemed voucher, both pass the check, both write. The second $set simply overwrites the first — so not only do both succeed, the audit trail of who redeemed it first is destroyed too.

The fix — move the precondition into the filter:

const r = await vouchers.updateOne(
  { code, redeemedAt: null },                    // guard: null OR missing
  { $set: { redeemedAt: new Date(), redeemedBy: userId } }
)
if (r.matchedCount === 0) return { ok: false, reason: "already redeemed" }
return { ok: true }

Exactly one request can match, because the filter and the modification are evaluated atomically against the same document. The loser gets matchedCount: 0.

What to do with matchedCount: 0: return the business outcome. It is not an exception, should not be logged as an error, and must not be retried — a retry will just report "already redeemed" again, correctly. Getting this wrong is how teams end up with alert fatigue from a system that is behaving perfectly.

One subtlety worth noticing: {redeemedAt: null} matches both an explicit null and an absent field — which is what you want here, since new vouchers may not carry the field at all. That is the null-versus-missing behaviour from the previous lesson, being useful for once rather than surprising.

If you also need to distinguish "no such voucher" from "already redeemed", use findOneAndUpdate with the guard and, on a null result, do one follow-up findOne({code}) — the extra read happens only on the failure path.

3 (medium): A "get or create device session" upsert on {userId, deviceId} is producing duplicate documents — 1,142 of them in a week, always in pairs milliseconds apart. Explain the mechanism precisely, fix it, and then explain what your fix does to the existing duplicates.
Solution

Mechanism. An upsert is not atomic across the find-or-create decision. Two concurrent upserts both evaluate the filter, both find nothing, and both proceed to insert. Both report success. The window is exactly the gap between the match phase and the insert, which is why the duplicates are always milliseconds apart — they are the pairs that raced.

Fix — make the duplicate impossible, not unlikely:

db.sessions.createIndex({ userId: 1, deviceId: 1 }, { unique: true })

Now the losing racer's insert fails with E11000 rather than succeeding. Handle it with a single retry:

async function getOrCreateSession(userId, deviceId) {
  const op = () => sessions.findOneAndUpdate(
    { userId, deviceId },
    { $set: { lastSeenAt: new Date() },
      $setOnInsert: { createdAt: new Date(), state: {} } },
    { upsert: true, returnDocument: "after" })
  try { return await op() }
  catch (e) { if (e.code === 11000) return await op(); throw e }
}

One retry is provably sufficient: by the time the loser retries, the winner's document exists, so the filter matches and the operation takes the update path.

The part the question is really asking about: the existing duplicates. createIndex with unique: true will fail while duplicates are present — the index build aborts and you have fixed nothing. So the order of work is:

// 1. Find them
db.sessions.aggregate([
  { $group: { _id: { u: "$userId", d: "$deviceId" },
              n: { $sum: 1 }, ids: { $push: "$_id" } } },
  { $match: { n: { $gt: 1 } } }
])

// 2. MERGE them - do not just delete. Each twin may hold real state
//    (one has the push token, the other the last-seen timestamp).
//    Decide the merge rule with the product owner, then apply it.

// 3. Delete the losers, then build the unique index.

Deciding the merge rule is the actual work; the index is one line. And note the failure was visible to users as "random logouts", because reads returned whichever twin came first — a good reminder that duplicate documents rarely announce themselves as duplicates.

4 (medium): A nightly migration backfills a normalisedEmail field on 2M documents. It currently takes 30 minutes, is not restartable, and last night it died at minute 24. Rewrite it, and justify each choice. 
const cursor = users.find({})
for await (const u of cursor) {
  await users.updateOne({ _id: u._id },
    { $set: { normalisedEmail: u.email.trim().toLowerCase() } })
}
Solution

Four things are wrong: it awaits one write at a time, it reprocesses everything on restart, it scans documents that are already done, and it pulls whole documents over the network to use one field.

Best answer first — it does not need application code at all. The transformation only references fields in the same document, so a pipeline update does it entirely server-side:

db.users.updateMany(
  { normalisedEmail: { $exists: false }, email: { $type: "string" } },
  [ { $set: { normalisedEmail: { $toLower: { $trim: { input: "$email" } } } } } ]
)

No documents cross the network at all. The filter makes it restartable by construction: re-running it processes only what remains.

When you do need client-side logic (a real normalisation library, say), batch it:

let lastId = null
while (true) {
  const filter = { normalisedEmail: { $exists: false },
                   ...(lastId ? { _id: { $gt: lastId } } : {}) }
  const batch = await users.find(filter, { projection: { email: 1 } })
                           .sort({ _id: 1 }).limit(1000).toArray()
  if (!batch.length) break
  await users.bulkWrite(batch.map(u => ({
    updateOne: { filter: { _id: u._id },
                 update: { $set: { normalisedEmail: normalise(u.email) } } }
  })), { ordered: false })
  lastId = batch[batch.length - 1]._id
}
ChoiceWhy
bulkWrite batches of 1,000Measured 1,100 → 47,000 docs/s. One round trip per 1,000 writes instead of per write
ordered: falseThe updates are independent; one failure must not stop the other 999
$exists: false in the filterMakes it restartable and idempotent — the crash at minute 24 costs you 24 minutes, not the job
_id: {$gt: lastId} pagingA stable cursor across batches; no skip (which is O(n)), and no long-lived cursor to time out
projection: {email: 1}Pulls one field, not whole documents
$type: "string" guardA null or missing email would throw mid-batch; the type audit habit from lesson 2

Two production notes I would add to the ticket: a backfill this size is a write storm, so throttle between batches if replication lag rises (watch it, do not guess); and if normalisedEmail is going to be indexed, build the index after the backfill, not before — otherwise every one of the 2M updates maintains the index as it goes.

5 (hard): Implement "transfer money between two accounts" three different ways — reshaped into one document, idempotent-and-replayable, and with a transaction. State which you would ship and under what circumstances your answer changes.
Solution

Approach 1 — reshape so the invariant lives in one document. Only possible when the two balances legitimately belong to one aggregate, e.g. two wallets inside one customer account:

db.customers.updateOne(
  { _id: cid, "wallets.gbp.balanceMinor": { $gte: amount } },
  { $inc: { "wallets.gbp.balanceMinor": -amount,
            "wallets.eur.balanceMinor":  converted },
    $push: { ledger: { $each: [entry], $slice: -100 } } }
)

Atomic, no coordination, and the guard prevents overdraft. When the model permits it, this is strictly the best answer — and $slice: -100 keeps the embedded ledger bounded, per lesson 2.

Approach 2 — idempotent, replayable steps. The general answer when the accounts are genuinely separate documents:

const tid = transferId   // stable, supplied by the caller

// Step 1: debit, guarded and idempotent
const r = await accounts.updateOne(
  { _id: from, balanceMinor: { $gte: amount },
    appliedTransfers: { $ne: tid } },        // <- replay protection
  { $inc: { balanceMinor: -amount },
    $push: { appliedTransfers: { $each: [tid], $slice: -1000 } },
    $push: { outbox: { tid, to, amount, at: new Date() } } }
)
if (r.matchedCount === 0) { /* insufficient funds OR already applied */ }

// Step 2: a worker drains the outbox
const c = await accounts.updateOne(
  { _id: to, appliedTransfers: { $ne: tid } },
  { $inc: { balanceMinor: amount },
    $push: { appliedTransfers: { $each: [tid], $slice: -1000 } } }
)
// Step 3: remove the outbox entry (safe to repeat)
await accounts.updateOne({ _id: from },
  { $pull: { outbox: { tid } } })

The debit and the intent to credit are written in one atomic update, so the outbox entry cannot be lost if the process dies. Every step is a no-op on replay. The trade-off, stated honestly: the credit is eventually consistent — there is a window where the money is in neither balance — and appliedTransfers is unbounded unless capped, which is why $slice is there (a dedicated transfers collection with _id: tid scales better).

Approach 3 — a transaction:

await session.withTransaction(async () => {
  const d = await accounts.updateOne(
    { _id: from, balanceMinor: { $gte: amount } },
    { $inc: { balanceMinor: -amount } }, { session })
  if (d.matchedCount === 0) throw new InsufficientFunds()   // aborts
  await accounts.updateOne({ _id: to },
    { $inc: { balanceMinor: amount } }, { session })
  await transfers.insertOne({ _id: tid, from, to, amount }, { session })
}, { readConcern: { level: "snapshot" },
     writeConcern: { w: "majority" } })

Note that the guard is still needed — a transaction gives isolation, not business rules — and that withTransaction handles TransientTransactionError retries for you.

What I would ship. Approach 3, for a system doing tens of transfers per second, with _id: tid on the transfers insert so a client retry of the whole transfer fails with E11000 rather than transferring twice — transactions give atomicity, not idempotency, and this is the detail most candidates miss.

When the answer changes: at thousands of transfers/sec against hot accounts, transaction write conflicts turn into a retry storm and Approach 2 wins on throughput. Across shards, the transaction still works but costs a two-phase commit. And if a business review says the two balances are really one aggregate, Approach 1 makes the entire question disappear — which is the outcome to push for.

6 (hard): A webhook consumer processes payment events. It is at-least-once (duplicates arrive), events can arrive out of order, and it currently double-charges under retries. Design the write path end to end.
Solution

Three distinct problems hide in that sentence — duplicates, ordering, and non-idempotent effects — and each needs its own mechanism. Solving only the first is why this bug usually survives one round of fixes.

1. Duplicates — a natural _id does the deduplication.

try {
  await events.insertOne({
    _id: evt.id,                    // the provider's event id
    type: evt.type, payload: evt, receivedAt: new Date(),
    processedAt: null
  })
} catch (e) {
  if (e.code === 11000) return ack()   // seen it - ack and stop
  throw e
}

The unique _id index is the dedupe store. No separate "seen events" service, no check-then-insert race — the check and the insert are the same operation.

2. Ordering — never trust arrival order; use the provider's sequence.

await payments.updateOne(
  { _id: evt.paymentId, lastEventSeq: { $lt: evt.seq } },   // guard
  { $set: { status: evt.status, lastEventSeq: evt.seq,
            updatedAt: new Date() } },
  { upsert: true }
)

An out-of-order stale event matches nothing and is correctly ignored. If the provider has no sequence, use its event timestamp with $max semantics — and if it has neither, model the state machine so only legal transitions match: {status: "pending"} → "charged".

3. Effects — separate "record the fact" from "do the thing". The double charge happens because the side effect is re-executed on replay. Write the intent atomically with the state change, then let a worker perform it:

// same atomic update as above, plus:
  $push: { outbox: { kind: "sendReceipt", key: evt.id } }

// worker: claim, perform, then clear - and make the CALL idempotent
// by passing an idempotency key the provider honours

4. Close the loop, and mark completion last:

await events.updateOne({ _id: evt.id, processedAt: null },
                       { $set: { processedAt: new Date() } })

The processedAt: null guard means a concurrent duplicate delivery cannot mark it twice, and a sweeper can find events inserted but never processed — the crash-in-the-middle case, which is otherwise invisible.

Two things I would deliberately not do: not use a transaction (each step is a single-document atomic write, so there is nothing multi-document to protect); and not ack the webhook until the event row is durably written with w: "majority" — acking on w: 1 means a failover can lose an event the provider believes was delivered, which is the one failure mode this design would otherwise still have.

🎯 Key Takeaways

  • A single-document write is atomic and isolated. Nothing larger is, without a transaction — updateMany included.
  • Write concern defines what "acknowledged" means. w: 1 can be rolled back by a failover; w: "majority" cannot, and is the default since 5.0.
  • wtimeout is not a rollback — it means "I stopped waiting". The write may still be applied and may still commit.
  • matchedCount is the success signal, not modifiedCount. Matched-but-not-modified is what a correctly replayed idempotent write looks like.
  • Never read-modify-write. Measured: 8,127 of 50,000 decrements silently lost with 8 workers; $inc lost none.
  • Put the precondition in the filter. That single move turns an update into a compare-and-swap, and matchedCount: 0 becomes a business outcome you branch on.
  • replaceOne deletes every field you did not send. 320,000 documents were silently stripped this way. Default to updateOne with $set.
  • Pipeline updates let the new value reference the document's own fields server-side, removing whole classes of read-modify-write.
  • An upsert without a unique index on its filter fields is a duplicate generator — 1,142 twins in a week. Add the index, retry once on E11000.
  • Only equality clauses in the filter seed an upserted document; use $setOnInsert for the rest.
  • findOneAndUpdate with a status guard is a correct multi-worker claim. findOne-then-updateOne is not — it delivered 3.4% of emails twice at peak while every test passed.
  • Always set returnDocument: "after" explicitly when you want the new version; the default is "before".
  • bulkWrite in unordered batches of ~1,000: 1,100 → 47,000 docs/s, and one bad document no longer stops the job at 4,113 of 12,000.
  • Deletes are writes. TTL runs as a background task every 60 s (documents observed alive 74 s past expiry), so filter on expiresAt too, and never shorten retention on a huge collection in one step.
  • Driver retryable writes are deduplicated server-side by statement id — which is why even $inc is safe. Your own retry loop is a new statement and will apply it twice.
  • Reach in order: reshape into one document → idempotent replayable steps → transaction. A transaction on a hot path is usually a message about the schema.
