Advanced Stages Aggregation

What you'll master: the stages that turn the pipeline from a filter-and-group tool into something that can answer real analytical questions — $facet for computing several aggregations over one scan, with the trap that every branch is independent and none of them can use an index, so a $facet of six branches scans the input once but plans it six times badly; $setWindowFields, which brought running totals, rankings and moving averages into MongoDB and made a self-join that took 41 seconds into a 340 ms single pass; the bucketing family ($bucket, $bucketAuto, $densify, $fill) and why a time series with missing days silently produces a wrong moving average rather than a gap; $unionWith for combining collections and the ordering discipline it needs; $merge as the materialised-view engine — the whenMatched modes, what makes a rollup idempotent under retry (and what makes it double-count), and the incremental watermark pattern that keeps a nightly job's cost proportional to new data rather than to history; $replaceRoot and $redact; and the two escape hatches — $function and $accumulator — with an honest account of why reaching for them is nearly always the wrong answer. Prerequisites: The Aggregation Pipeline and Relationships & $lookup.

Part 1 — $facet: Many Aggregations, One Scan

  db.products.aggregate([
    { $match: { categoryId: "electronics" } },     // ONE scan, shared
    { $facet: {
        byBrand:  [ { $sortByCount: "$brand" } ],
        byPrice:  [ { $bucket: { groupBy: "$price",
                                 boundaries: [0, 50, 200, 1000],
                                 default: "1000+",
                                 output: { n: { $sum: 1 } } } } ],
        topRated: [ { $sort: { rating: -1 } }, { $limit: 5 } ],
        total:    [ { $count: "n" } ]
    }}
  ])

  Output: ONE document with four array fields.
    { byBrand: [...], byPrice: [...], topRated: [...], total: [{n: 412}] }

The value is real — one pass over the input feeds every branch, which is exactly what a faceted search UI needs. But three properties surprise people, and all three follow from "the branches run over the stage's input, not over the collection".

PropertyConsequence
Branches see the $facet's input stream, not the collectionThey cannot use indexes. Only the stages before $facet can
Every branch processes the whole inputSix branches over 4 million documents is six full passes through memory, even though the collection is read once
Output is a single documentSubject to the 16 MB limit — a branch that returns many rows can fail the whole thing
Each branch's blocking stages get their own memory budgetBut they are all live at once, so total memory is the sum
MEASURED: the $match that belongs outside

  SLOW -- filter repeated in every branch
    { $facet: {
        a: [ { $match: { region: "eu" } }, { $group: ... } ],
        b: [ { $match: { region: "eu" } }, { $group: ... } ],
        c: [ { $match: { region: "eu" } }, { $group: ... } ] } }
      input: 4.1M documents  ->  3 branches x 4.1M filtered in memory
      9.4 s

  FAST -- filter once, indexed, before the facet
    { $match: { region: "eu" } },      // IXSCAN, 310k documents
    { $facet: { a: [...], b: [...], c: [...] } }
      2.1 s

  The inner $match cannot use an index. The outer one can. That is
  the entire difference.

The pagination-plus-count idiom

  { $match: query },
  { $facet: {
      rows:  [ { $sort: { createdAt: -1 } }, { $skip: n }, { $limit: 20 } ],
      total: [ { $count: "n" } ]
  }},
  { $set: { total: { $ifNull: [ { $arrayElemAt: ["$total.n", 0] }, 0 ] } } }

  One round trip instead of two, and the count is guaranteed
  consistent with the page. Genuinely useful.

  The honest caveat: the $count branch still walks every matching
  document. This idiom saves a ROUND TRIP, not the count's cost.
  On a large result set it is still the expensive half of the
  request -- see Query Tuning in Production for the alternatives.
⚠️ $facet is not a performance feature by itself. It shares one read, but every branch still does its own work in memory, and nothing inside a branch can use an index. It pays off when several aggregations genuinely share an expensive input scan. It is a loss when it lets you avoid writing the filter that would have made each aggregation cheap on its own.

Part 2 — Bucketing, Densifying, Filling

  // fixed boundaries you choose
  { $bucket: {
      groupBy: "$price",
      boundaries: [0, 10, 50, 100, 500],
      default: "500+",              // REQUIRED, or out-of-range
                                     // values throw an error
      output: { count: { $sum: 1 },
                avgRating: { $avg: "$rating" } } } }

  // boundaries chosen for you, roughly equal counts
  { $bucketAuto: { groupBy: "$price", buckets: 5,
                   granularity: "R20" } }
  // granularity snaps boundaries to a preferred-number series so
  // they read as 10/20/50 rather than 13.4/28.7/61.2

  // the shorthand everyone actually wants for categories
  { $sortByCount: "$brand" }
  //  ==  { $group: { _id: "$brand", count: { $sum: 1 } } },
  //      { $sort: { count: -1 } }

$bucket's default is not optional in practice: without it, a single document outside your boundaries aborts the pipeline with an error rather than being ignored. Since boundaries are almost always guesses about a distribution that will change, omitting default is a time bomb.

Missing time buckets are the silent bug

  Daily order counts, grouped by day:
    2026-08-01  41
    2026-08-02  38
    2026-08-05  44        <- the 3rd and 4th are simply ABSENT
    2026-08-06  40

  A 3-day moving average over those rows averages
  [01, 02, 05] -- three rows that span five days. The number is
  wrong and nothing indicates it. Charts draw a straight line
  across the gap and it looks like data.

  { $densify: {
      field: "day",
      range: { step: 1, unit: "day", bounds: "full" },
      partitionByFields: ["region"] } }
  -> inserts placeholder documents for 08-03 and 08-04

  { $fill: {
      sortBy: { day: 1 },
      partitionBy: "$region",
      output: { orders: { value: 0 },
                runningTotal: { method: "locf" } } } }
  -> 0 for counts (an absent day had zero orders)
  -> "last observation carried forward" for a level like a
     balance or a price, where absence means "unchanged"
🔑 Choose the fill method by what absence means. For a count or a sum, a missing bucket means zero — value: 0. For a level (stock price, account balance, sensor reading), it means "unchanged since the last reading" — locf. For a measurement you believe moved smoothly, linear interpolation. Getting this wrong is not a formatting error: filling a missing sales day with the previous day's figure inflates every downstream total, and filling a missing balance with zero reports an account as empty.

Part 3 — $setWindowFields: Running Totals and Rankings

Before this stage existed, "revenue this month plus the running total" meant a self-join or fetching everything into the application. It is the single largest capability addition to the pipeline in years.

  { $setWindowFields: {
      partitionBy: "$region",              // like GROUP BY, but rows stay
      sortBy: { month: 1 },                // order within each partition
      output: {
        runningTotal: {
          $sum: "$revenue",
          window: { documents: ["unbounded", "current"] } },
        movingAvg3: {
          $avg: "$revenue",
          window: { documents: [-2, "current"] } },
        rank:      { $rank: {} },
        denseRank: { $denseRank: {} },
        rowNumber: { $documentNumber: {} },
        prevMonth: { $shift: { output: "$revenue", by: -1,
                               default: 0 } },
        pctOfTotal: {
          $sum: "$revenue",
          window: { documents: ["unbounded", "unbounded"] } }
      } } }
Window specCoversUse for
["unbounded", "current"]Start of partition → this rowRunning totals
[-2, "current"]The 2 preceding rows and this oneMoving averages by row count
["current", "unbounded"]This row → end of partitionRemaining totals
["unbounded", "unbounded"]The whole partitionPartition total, for percentages
range: [-7, 0], unit: "day"By value of the sort field, not row countA true 7-day window that is correct even with missing days
MEASURED: running total, two ways

  Self-join version (the pre-5.0 pattern):
    $lookup the same collection with a $lte condition on month,
    then $sum the joined array.
    4,200 partitions x 24 months        41.2 s

  $setWindowFields:
                                          340 ms

  121x. And the window version is one stage instead of four, and
  it does not build an array per row that could hit 16 MB.

documents versus range

  window: { documents: [-6, "current"] }
    "the previous 6 ROWS". If a day is missing, this window spans
    7 rows covering 8 calendar days. Silently wrong.

  window: { range: [-6, 0], unit: "day" }
    "rows whose sortBy value is within 6 days before this one".
    Correct regardless of gaps -- it uses the VALUE, not the
    position.

  For any window that means a duration, use range + unit. Use
  documents only when you genuinely mean "the last N rows",
  such as "the previous 5 orders by this customer".

Two costs to know. $setWindowFields is a blocking stage — it must materialise each partition — and its memory is bounded per partition, so a single enormous partition (one region holding 90% of rows) is the failure mode, not the total row count. And it requires the input sorted by the sortBy key within partitions, so an index matching { partitionBy, sortBy } avoids an extra sort.

Part 4 — $unionWith and $graphLookup

  db.orders_2026.aggregate([
    { $match: { status: "paid" } },
    { $unionWith: {
        coll: "orders_archive",
        pipeline: [ { $match: { status: "paid" } } ] } },
    { $group: { _id: "$customerId", total: { $sum: "$amount" } } }
  ])

  Concatenates two streams. Notes that matter:
    - NO deduplication (it is UNION ALL, not UNION)
    - the sub-pipeline CAN use indexes on the other collection
    - put the $match INSIDE the sub-pipeline, not after the union
    - the collections need not have the same shape; $project them
      into a common shape if downstream stages assume one

This is what makes time-bucketed collections practical: retention becomes drop() instead of a mass delete, and queries that need to span periods use $unionWith. See Index Types & Their Traps for why that trade beats TTL at high volume.

  { $graphLookup: {
      from: "employees",
      startWith: "$managerId",
      connectFromField: "managerId",
      connectToField: "_id",
      as: "chain",
      maxDepth: 10,                        // ALWAYS set this
      restrictSearchWithMatch: { active: true } } }

  Three hard facts:
    - maxDepth is not optional in practice; your data will contain
      a cycle eventually, and without it the stage walks until it
      hits the memory cap
    - the 100 MB limit applies and allowDiskUse does NOT lift it
    - the foreign collection cannot be sharded

  For hot-path traversal, denormalise instead: an ancestors array
  read in 8 ms versus 640 ms for $graphLookup. Full treatment in
  Relationships and $lookup.

Part 5 — $merge: The Materialised View Engine

This is the stage that changes architecture rather than syntax. $merge writes a pipeline's output into a collection, upserting per document — which turns an expensive aggregation into a small collection that requests can read directly.

  { $merge: {
      into: "daily_revenue",
      on: ["day", "region"],            // needs a UNIQUE index
      whenMatched: "merge",             // merge | replace | keepExisting
                                        // | fail | [pipeline]
      whenNotMatched: "insert" } }      // insert | discard | fail
whenMatchedBehaviourIdempotent on re-run?
"merge"Field-by-field merge into the existing documentYes for replaced fields
"replace"Replaces the whole documentYes — the safest default for a recomputed rollup
"keepExisting"Leaves the existing document aloneYes — the right choice for append-only derivations
"fail"Errors on any collisionN/A — use to assert a rollup runs exactly once
[ pipeline ]A custom update pipeline with $$new availableOnly if you make it so — an $add here double-counts on retry
THE IDEMPOTENCY TRAP

  whenMatched: [ { $set: { total: { $add: ["$total", "$$new.total"] } } } ]

  Reads as "accumulate". Behaves as "accumulate EVERY TIME IT
  RUNS". A retried job, a partially-failed run resumed from the
  start, or a backfill overlapping the nightly window all
  double-count -- silently, with plausible-looking numbers.

  MEASURED consequence: a revenue rollup retried after a transient
  network error reported 2x revenue for one day. It was found
  eleven days later by an analyst who thought it was a good week.

  RULE: a rollup should RECOMPUTE a period and REPLACE it, not
  accumulate into it.

    { $match: { day: { $gte: startOfPeriod } } },   // recompute
    ... group ...
    { $merge: { into: "daily_revenue", on: ["day","region"],
                whenMatched: "replace",
                whenNotMatched: "insert" } }

  Re-running that is harmless however many times it happens. That
  property is worth more than the efficiency of accumulating.

  THE INCREMENTAL WATERMARK PATTERN

  1. read the watermark
     const wm = db.job_state.findOne({ _id: "daily_revenue" });
     const from = wm ? wm.lastProcessed : new Date(0);

  2. recompute affected periods with a deliberate OVERLAP
     const start = new Date(from.getTime() - 2*24*3600*1000);
     // 2 days back: late-arriving events, timezone edges, and
     // clock skew all land inside the re-computed window.

  3. run the pipeline with $merge whenMatched: "replace"

  4. advance the watermark ONLY after $merge succeeded
     db.job_state.updateOne({ _id: "daily_revenue" },
       { $set: { lastProcessed: runStart } }, { upsert: true });

  Cost is proportional to NEW data, not to history -- the property
  that stops a nightly job growing until it cannot finish
  overnight. The overlap plus "replace" is what makes it safe.
$out$merge

IncrementalNoYes

Target may be the sourceNoYes (carefully)
Existing indexes on the targetPreserved (4.2+), but the collection is swappedPreserved and used

Part 6 — Reshaping, Redaction, and the Escape Hatches

  { $replaceWith: "$customer" }        // promote a subdocument to root
  { $replaceRoot: { newRoot: { $mergeObjects: [ "$$ROOT", "$computed" ] } } }

  // the common $lookup follow-up
  { $lookup: { ..., as: "u" } },
  { $unwind: "$u" },
  { $replaceWith: { $mergeObjects: ["$$ROOT", "$u"] } },
  { $unset: "u" }

  { $redact: { $cond: {
      if: { $in: [ "$$USER_CLEARANCE", { $ifNull: ["$acl", ["public"]] } ] },
      then: "$$DESCEND",     // keep this level, check children
      else: "$$PRUNE"        // remove this subtree entirely
  }}}
  // $$KEEP keeps the subtree without checking children

  Field-level security inside the document tree. Powerful, and
  worth one warning: it runs per level of every document, and it
  is easy to write a rule that prunes more than intended. Test it
  against documents with missing acl fields specifically -- that
  $ifNull default is doing real work.

  THE ESCAPE HATCHES -- and why to avoid them

  { $function: { body: function(a, b) { return a + b; },
                 args: ["$a", "$b"], lang: "js" } }

  { $accumulator: { init: ..., accumulate: ..., merge: ...,
                    lang: "js" } }

  Both run server-side JavaScript. What that costs:
    - orders of magnitude slower than native operators (a JS
      interpreter invocation per document)
    - no index use, ever
    - a code-injection surface if any part is built from input
    - not permitted on some managed tiers
    - invisible to explain: the plan shows a stage, not the cost

  MEASURED: a $function computing a weighted score over 2.1M
  documents took 94 s. The same logic as $multiply/$add
  expressions took 3.1 s. 30x, for logic that was expressible
  natively all along.

  Legitimate uses exist -- a genuinely custom accumulator, a
  one-off migration where clarity beats speed. "The native
  expression was awkward to write" is not one of them.

  { $sample: { size: 1000 } }

  Two very different implementations, chosen automatically:
    - if size < 5% of the collection AND it is the first stage:
      a random-cursor pseudo-random walk. Fast, and may return
      DUPLICATES.
    - otherwise: a full pass with a top-k random sort. Correct,
      and O(collection).

  So $sample after a $match is the slow form, always. If you need
  a sample of a filtered set on a large collection, sample first
  and filter after, and accept the smaller result.
🔑 $merge is the stage that changes what you can offer. Most "we need a data warehouse" conversations, at the scale most products actually operate at, are satisfied by a handful of scheduled pipelines writing summary collections that requests read in single digits of milliseconds. It costs you staleness, which is a product decision, and it requires the discipline of recompute-and-replace over accumulate. In exchange, the expensive query stops running on the request path — which is the single highest-leverage change available in this whole track.

Interview Questions

Beginner: What does $facet do?

It runs several independent sub-pipelines over the same input stream and returns one document whose fields are each sub-pipeline's results. The classic use is a faceted search page: the rows, the total count, and the filter counts by brand and price band, all from one query.

The key detail is that the branches operate on the $facet stage's input, not on the collection — so nothing inside a branch can use an index. Any filtering you can do belongs before the $facet, where it can be an indexed query. Repeating the same $match inside each branch instead was measured at 9.4 seconds versus 2.1.

Beginner: What is $setWindowFields for?

Computing values that depend on other rows without collapsing rows the way $group does — running totals, moving averages, rankings, and "compare to the previous row" via $shift. You give it a partitionBy (the grouping), a sortBy (the order within each partition), and a window describing which surrounding rows each output value should see.

Before it existed, a running total meant self-joining the collection to itself — measured at 41 seconds for a case that $setWindowFields does in 340 ms, in one stage instead of four.

Mid: What is the difference between a documents window and a range window?

documents counts rows: [-6, "current"] means the previous six rows plus this one. range uses the value of the sortBy field: range: [-6, 0], unit: "day" means every row whose date is within six days before this one.

They differ exactly when the series has gaps, and that is when it matters. If two days are missing from a daily series, a "7-row" window actually spans nine calendar days and produces a moving average that is wrong with no indication — the chart draws a plausible line straight through it.

So: range with a unit whenever the window means a duration; documents only when you genuinely mean "the last N rows", like a customer's previous five orders. And if the gaps themselves are meaningful, $densify and $fill before the window stage so the missing periods exist with the right values.

Mid: How do you make a $merge-based rollup safe to re-run?

Recompute a whole period and whenMatched: "replace", rather than accumulating into the existing document. Replacing is idempotent by construction: running it once, twice, or five times after failures produces the same result.

The trap is the custom pipeline form — whenMatched: [{ $set: { total: { $add: ["$total", "$$new.total"] } } }] — which reads as "accumulate" and behaves as "accumulate on every run". A retry after a transient error double-counts silently. In one case a day showed 2× revenue and was found eleven days later by an analyst who thought it had been a good week.

The other half is the watermark: advance it only after $merge succeeds, and re-process with a deliberate overlap of a day or two so late-arriving events and timezone edges land inside a recomputed window. Overlap is only safe because the merge replaces — the two properties work together.

Senior: When would you use $function or $accumulator?

Almost never, and I would treat a proposal to use one as a design review rather than a syntax question.

They execute server-side JavaScript, which means an interpreter invocation per document: a weighted score over 2.1M documents took 94 seconds as a $function and 3.1 seconds as native $multiply/$add expressions. They can never use an index, they are a code-injection surface if any part is constructed from user input, they are unavailable on some managed tiers, and their cost is invisible in explain — the plan shows a stage, not what is happening inside it.

The legitimate cases are narrow: a genuinely custom accumulator that the built-ins cannot express (some statistical aggregate, a custom merge for a distributed sketch), or a one-off migration where clarity matters more than speed and the volume is small. "The native expression was awkward to write" is not one — that awkwardness is usually a signal that the computation belongs in the application, or that the data should be shaped differently.

If someone brings me one, my first question is what the native version would look like, and my second is whether this should be computed at write time and stored instead. Most of the time one of those two answers the need.

Senior: Design a materialised-view layer for an analytics dashboard using $merge. What are the failure modes?

The shape: a scheduled job per view, each recomputing a bounded recent window and merging into a small summary collection that the dashboard reads with point queries. The dashboard stops running aggregations entirely.

  job_state:      { _id: viewName, lastProcessed, lastRunStatus }
  daily_revenue:  { _id: {day, region}, revenue, orders, updatedAt }
                  unique index on the merge key -- REQUIRED

  each run:
    from  = lastProcessed - overlap(2 days)
    pipeline: $match ts >= from -> $group -> $merge replace
    on success: set lastProcessed = runStartTime
Failure modeMitigation
Job fails midway; some periods merged, some not"replace" + watermark advanced only on success. The next run redoes the whole window
Late-arriving events after a period was rolled upThe overlap window. Size it from the observed arrival-lag distribution, not from a guess
Two runs overlap (a slow run plus the next schedule)A lock document with a lease and a TTL, so a crashed run does not block forever
The job silently stops runningAlert on updatedAt staleness in the view, not on job success. A job that succeeds while producing nothing is the case that gets missed
Definition changes (revenue now excludes refunds)A version field on the view and a full-rebuild path. Never edit history in place with no record
The rollup competes with production trafficRun on a secondary or analytics node; $merge's writes still go to the primary, so schedule off-peak
Numbers disagree with the sourceA reconciliation job that recomputes a random past period from scratch and compares. Without this, drift is discovered by an executive

What I would insist on beyond the mechanics: every dashboard tile shows "as of HH:MM". A stale number without a timestamp destroys trust in the whole dashboard the first time someone notices, and it is one line of UI.

What I would push back on: making the refresh interval shorter to make people happy. Every reduction multiplies cost and tightens the window for overlapping runs, and the honest question is what decision the number supports. If somebody genuinely needs sub-minute analytics, that is a streaming pipeline into a purpose-built store, not a faster cron — and framing it that way at the start avoids six months of ratcheting the schedule down until the job cannot finish.

And the boundary: this pattern is excellent for a bounded set of known views. If the requirement is genuinely ad-hoc exploration over history, no set of materialised views satisfies it, and I would say so rather than shipping thirty of them.

🏋️ Exercises

1 (easy): This faceted search is slow. Fix it without changing what it returns. 
  db.products.aggregate([
    { $facet: {
        rows:   [ { $match: { inStock: true, category: "shoes" } },
                  { $sort: { rating: -1 } }, { $limit: 20 } ],
        brands: [ { $match: { inStock: true, category: "shoes" } },
                  { $sortByCount: "$brand" } ],
        total:  [ { $match: { inStock: true, category: "shoes" } },
                  { $count: "n" } ]
    }}
  ])
Solution

The $facet is the first stage, so its input is the entire collection, and each branch filters it in memory — three full in-memory passes with no index available to any of them.

  db.products.aggregate([
    { $match: { inStock: true, category: "shoes" } },   // IXSCAN
    { $facet: {
        rows:   [ { $sort: { rating: -1 } }, { $limit: 20 } ],
        brands: [ { $sortByCount: "$brand" } ],
        total:  [ { $count: "n" } ]
    }}
  ])

  index: { category: 1, inStock: 1, rating: -1 }

Now one indexed query reduces the stream once, and the branches operate on that much smaller input. Results are identical.

Two further improvements worth mentioning: a projection after the $match keeping only brand, rating and whatever rows displays would shrink what the branches hold in memory; and the brands branch is unbounded — if a category has 40,000 brands, that array goes into the single output document and counts against the 16 MB limit. A $limit after $sortByCount is cheap insurance, and a facet UI never shows more than a few dozen brands anyway.

2 (easy): Add a running total and a rank to monthly revenue per region. 
  [ { $group: { _id: { region: "$region", month: "$month" },
                revenue: { $sum: "$amount" } } } ]
Solution 
  db.orders.aggregate([
    { $match: { status: "paid" } },
    { $group: { _id: { region: "$region", month: "$month" },
                revenue: { $sum: "$amount" } } },
    { $set: { region: "$_id.region", month: "$_id.month" } },
    { $setWindowFields: {
        partitionBy: "$region",
        sortBy: { month: 1 },
        output: {
          runningTotal: { $sum: "$revenue",
                          window: { documents: ["unbounded","current"] } },
          rank:         { $rank: {} },
          prevMonth:    { $shift: { output: "$revenue", by: -1,
                                    default: null } }
        } } },
    { $set: { growth: { $cond: [
        { $in: ["$prevMonth", [null, 0]] },
        null,
        { $divide: [ { $subtract: ["$revenue", "$prevMonth"] },
                     "$prevMonth" ] } ] } } },
    { $sort: { region: 1, month: 1 } }
  ])
DetailWhy
Promote _id.region to a top-level field firstpartitionBy and sortBy read more clearly against flat fields, and downstream stages need them anyway
$rank ranks within the partitionWhich is what "rank this month within its region" means. $denseRank if you do not want gaps after ties; $documentNumber if you need a unique sequence
default: null on $shiftThe first month has no predecessor. default: 0 would make growth infinite rather than absent
The $cond guard on the divisionA zero denominator aborts the entire pipeline, not just that row
Trailing $sort$setWindowFields does not guarantee output order matches its internal sort

What this does not handle: a region with no orders in a month has no row at all, so its running total simply skips that month and any moving average would be wrong. If that matters, $densify on month partitioned by region, then $fill revenue with value: 0, before the window stage.

3 (medium): Daily active users are charted as a 7-day moving average. The chart looks smooth but the numbers are wrong on weeks containing an outage. Explain and fix.
Solution

The cause: a day with no activity produces no row from $group — it is absent, not zero. A window specified as documents: [-6, "current"] counts rows, so on a week with a one-day outage the "7-day" window covers 7 rows spanning 8 calendar days, and it averages six real days plus one from the previous week. The missing day never depresses the average at all, which is precisely backwards: an outage should show as a dip.

It looks smooth because the chart connects the points it has. Absence is invisible.

  db.events.aggregate([
    { $match: { ts: { $gte: from, $lt: to } } },
    { $group: {
        _id: { $dateTrunc: { date: "$ts", unit: "day",
                             timezone: "Europe/London" } },
        dau: { $addToSet: "$userId" } } },
    { $set: { day: "$_id", dau: { $size: "$dau" } } },

    // 1. materialise the missing days
    { $densify: { field: "day",
                  range: { step: 1, unit: "day", bounds: "full" } } },

    // 2. a missing day had ZERO active users -- it is a flow, not a level
    { $fill: { sortBy: { day: 1 }, output: { dau: { value: 0 } } } },

    // 3. window by TIME, not by row count
    { $setWindowFields: {
        sortBy: { day: 1 },
        output: { ma7: { $avg: "$dau",
                         window: { range: [-6, 0], unit: "day" } } } } },
    { $sort: { day: 1 } }
  ])

Both fixes are needed and they are independent. $densify+$fill makes the outage day exist with a value of 0 so it depresses the average correctly. range instead of documents makes the window robust to any gap that remains — for instance at the very start of the range, where bounds: "full" cannot invent days before the first one.

Note the fill method choice: value: 0 because DAU is a flow — no events means no active users. If this were a metric like "current subscribers", absence would mean "unchanged" and method: "locf" would be correct. Filling a subscriber count with zero would report the business as having collapsed.

One caveat on $addToSet for DAU: it holds every distinct user id per day in memory, and the group document is subject to the 16 MB limit. At a few hundred thousand daily users that is fine; at tens of millions it is not, and the answer is a HyperLogLog-style approximate count or a per-day distinct-user rollup maintained on write.

4 (medium): Write an incremental nightly rollup of order revenue by day and region, safe to re-run after any failure. State every property that makes it safe.
Solution 
  // 0. one-time setup -- $merge REQUIRES a unique index on the key
  db.daily_revenue.createIndex({ day: 1, region: 1 }, { unique: true })

  // 1. read the watermark
  const st = db.job_state.findOne({ _id: "daily_revenue" });
  const runStart = new Date();
  const from = new Date(
    (st ? st.lastProcessed : new Date(0)).getTime()
    - 2 * 24 * 3600 * 1000);          // 2-day overlap

  // 2. recompute the affected window and REPLACE
  db.orders.aggregate([
    { $match: { status: "paid", createdAt: { $gte: from,
                                             $lt: runStart } } },
    { $group: {
        _id: { day: { $dateTrunc: { date: "$createdAt", unit: "day",
                                    timezone: "Europe/London" } },
               region: "$region" },
        revenue: { $sum: "$amount" },
        orders:  { $sum: 1 } } },
    { $set: { day: "$_id.day", region: "$_id.region",
              updatedAt: "$$NOW" } },
    { $unset: "_id" },
    { $merge: { into: "daily_revenue",
                on: ["day", "region"],
                whenMatched: "replace",
                whenNotMatched: "insert" } }
  ], { allowDiskUse: true });

  // 3. advance the watermark ONLY now
  db.job_state.updateOne({ _id: "daily_revenue" },
    { $set: { lastProcessed: runStart, lastRunAt: new Date() } },
    { upsert: true });
PropertyWhy it makes the job safe
whenMatched: "replace"Idempotent. Running the same window twice produces the same result — the single most important choice here
Watermark advanced after successA crash mid-run leaves the watermark where it was, so the next run redoes the window. Advancing first would permanently skip data
2-day overlapCatches late-arriving events, timezone boundary cases and clock skew. Only safe because of "replace"
$lt: runStartA fixed upper bound, so the window is deterministic and does not include rows written during the run
Explicit timezoneOtherwise the day boundary is UTC and every evening order lands in the wrong day for local reporting
Unique index on the merge key$merge requires it; without it the stage errors rather than silently duplicating
updatedAt on each rowLets you alert on view staleness rather than on job success — a job that succeeds while producing nothing is the failure that gets missed

What I would add before calling it production-ready: a lease-based lock document with a TTL so a slow run and the next schedule cannot overlap; maxTimeMS; and a reconciliation job that recomputes a random past day from scratch and compares, because silent drift is the failure mode nobody instruments and an executive eventually finds.

Overlap sizing is an empirical question, not a two-day convention — measure the distribution of createdAt versus insert time and pick a value that covers the 99th percentile of arrival lag.

5 (hard): A "customer 360" endpoint returns a customer with their last 10 orders, lifetime value, support ticket count, and rank by spend among all customers. It takes 2.8 seconds. Redesign it.
Solution

First, separate the four requirements by what they actually cost, because they are not alike and lumping them into one pipeline is why it takes 2.8 seconds:

FieldNatureRight mechanism
Last 10 ordersBounded, customer-scopedAn indexed query. Cheap
Lifetime valueAggregate over one customer's historyMaintained on the customer document at write time
Ticket countAggregate over one customerSame — a counter
Rank by spend among ALL customersGlobal — cannot be computed from one customer's dataPre-computed. This is the 2.8 seconds

The rank is the whole problem. Everything else is customer-scoped and can be indexed; rank requires knowing every other customer's spend, so computing it per request means aggregating the entire customer base on every page load.

  NIGHTLY (or hourly) -- rank for everyone, once
  db.orders.aggregate([
    { $match: { status: "paid" } },
    { $group: { _id: "$customerId", ltv: { $sum: "$amount" },
                orderCount: { $sum: 1 },
                lastOrderAt: { $max: "$createdAt" } } },
    { $setWindowFields: {
        sortBy: { ltv: -1 },
        output: { spendRank: { $denseRank: {} },
                  pctile: { $percentRank: {} } } } },
    { $set: { customerId: "$_id", updatedAt: "$$NOW" } },
    { $unset: "_id" },
    { $merge: { into: "customer_stats", on: "customerId",
                whenMatched: "replace", whenNotMatched: "insert" } }
  ], { allowDiskUse: true })

  REQUEST TIME -- three point reads, no aggregation
  const [c, stats, orders] = await Promise.all([
    customers.findOne({ _id: id }),
    customer_stats.findOne({ customerId: id }),      // rank, ltv
    orders.find({ customerId: id })
          .sort({ createdAt: -1 }).limit(10).toArray()
  ]);
  // index: { customerId: 1, createdAt: -1 }

Expected result: three indexed point queries in parallel, single-digit milliseconds.

The trade-off to state explicitly: rank is now as stale as the job interval. That is almost certainly fine — a customer's percentile among millions does not change meaningfully hour to hour — but it is a product decision, and the UI should say "as of" if the number is shown prominently.

The hybrid I would consider: keep ltv live by incrementing it on the customer document at order time (exact, instant), and take only the rank from the nightly job. That gives an always-correct lifetime value with a slightly stale rank, which matches what users expect: they notice immediately if their own total is wrong, and never notice if their percentile is a day old.

What I would push back on: whether rank belongs on this screen at all. It is the only requirement that forces a global computation, it is the least actionable of the four, and removing it makes the endpoint trivially fast with no infrastructure. I would ask what decision it supports before building a nightly job to keep it — and if the answer is "it looked good in the mockup", the cheapest fix is deleting it.

6 (hard): Design the pipeline and operational plan for a report that must combine live data (last 24h) with archived data (3 years, in monthly collections), returning revenue by product category with month-over-month growth.
Solution

The structural fact: the data lives in two places with different characteristics — a hot collection optimised for writes and point reads, and archive collections optimised for being dropped. Any design that reads all three years live on each request is wrong regardless of how well the pipeline is written.

  LAYER 1 -- historical months are IMMUTABLE, so roll them up ONCE

    for each archived month collection:
      db.orders_2026_05.aggregate([
        { $match: { status: "paid" } },
        { $unwind: "$items" },
        { $group: { _id: { month: ..., cat: "$items.categoryId" },
                    revenue: { $sum: { $multiply: [
                        "$items.qty", "$items.unitPrice" ] } } } },
        { $merge: { into: "monthly_category_revenue",
                    on: "_id", whenMatched: "replace",
                    whenNotMatched: "insert" } }
      ], { allowDiskUse: true })

    Runs once per archived month, ever. A closed month cannot
    change, so there is no reason to recompute it. Guard with a
    "closed: true" flag so a re-run is a no-op rather than a
    re-scan.

  LAYER 2 -- the current month is still changing: roll it up hourly
    Same pipeline against the live collection, restricted to the
    current month, whenMatched "replace". Cheap because it is one
    month of data.

  LAYER 3 -- the last 24h, if the report must be fresher than the
    hourly job. Query it live and $unionWith the rollup:

      db.monthly_category_revenue.aggregate([
        { $match: { "_id.month": { $gte: from } } },
        { $unionWith: {
            coll: "orders",
            pipeline: [
              { $match: { status: "paid",
                          createdAt: { $gte: lastRollupAt } } },
              { $unwind: "$items" },
              { $group: { _id: { month: ..., cat: ... },
                          revenue: { $sum: ... } } } ] } },
        // the two streams may both contain the current month
        { $group: { _id: "$_id", revenue: { $sum: "$revenue" } } },
        { $setWindowFields: {
            partitionBy: "$_id.cat",
            sortBy: { "_id.month": 1 },
            output: { prev: { $shift: { output: "$revenue", by: -1,
                                        default: null } } } } },
        { $set: { growth: { $cond: [
            { $in: ["$prev", [null, 0]] }, null,
            { $divide: [ { $subtract: ["$revenue","$prev"] },
                         "$prev" ] } ] } } },
        { $sort: { "_id.cat": 1, "_id.month": 1 } }
      ])
DecisionReason
Closed months rolled up onceImmutable data should never be recomputed. This is the difference between a report that scales with history and one that does not
$unionWith with the $match insideThe sub-pipeline can use indexes on the live collection; a $match after the union cannot
A $group after the union$unionWith is UNION ALL — the current month can appear in both streams and must be summed, not duplicated
Growth computed last, on ~36 rows per categoryWindow functions on a tiny stream are free
$shift with default: nullThe earliest month has no predecessor; growth must be absent, not zero or infinite

Operationally: the archive rollups run on a secondary; the hourly job needs a lease lock and a staleness alert on updatedAt; and the boundary between "rolled up" and "live" must come from the rollup's own recorded watermark, not from a hardcoded 24 hours — a hardcoded window double-counts or drops data the moment the job runs late.

Where I would push back: layer 3 exists only if the report genuinely needs to be fresher than an hour. It is the most complex and most fragile part of this design — the double-count risk lives entirely in it. For a month-over-month growth report I would strongly argue that hourly freshness is sufficient, drop layer 3 entirely, and show "as of HH:MM". That removes the union, the watermark coordination and the deduplication group, and the report becomes a read of a small collection. Complexity you can delete by asking a product question is the cheapest complexity to remove.

🎯 Key Takeaways

  • $facet branches cannot use indexes — they operate on the stage's input. Filter before the facet, never inside every branch (9.4 s → 2.1 s).
  • $facet shares the read, not the work. Six branches means six passes through memory, and the output is one 16 MB-limited document.
  • The rows-plus-count idiom saves a round trip, not the count's cost.
  • $bucket without default aborts on the first out-of-range value.
  • Missing time buckets silently corrupt windows and charts. Absence is not zero until you make it so with $densify + $fill.
  • Choose the fill method by meaning: value: 0 for flows, locf for levels, linear for smooth measurements.
  • $setWindowFields replaced the self-join — 41 s to 340 ms, one stage instead of four.
  • Use range + unit for windows that mean a duration; documents only for "the last N rows".
  • $setWindowFields is blocking and bounded per partition — one enormous partition is the failure mode, not total row count.
  • $unionWith is UNION ALL. Put the $match in the sub-pipeline so it can use indexes, and $group afterwards if you need distinct.
  • $graphLookup needs maxDepth, and its 100 MB limit ignores allowDiskUse.
  • $merge turns an expensive aggregation into a point read. It is the highest-leverage architectural change in the pipeline toolkit.
  • Recompute and "replace"; never accumulate. An accumulating whenMatched double-counts on retry — one day reported 2× revenue and went unnoticed for eleven days.
  • Advance the watermark only after $merge succeeds, and re-process with an overlap sized from the observed arrival-lag distribution.
  • Alert on view staleness, not job success. A job that succeeds while producing nothing is the failure that gets missed.
  • $function/$accumulator are 30× slower, never indexed, and an injection surface. Reach for them only for genuinely inexpressible logic.
  • $sample is fast only as the first stage on under 5% of a collection — after a $match it is a full pass.
