Replica Sets & Read Concerns Distribution

What you'll master: the replica set as a mechanism rather than a feature — one primary, an oplog of idempotent operations, and secondaries that tail it, which explains every behaviour in this lesson including the ones that look like bugs; elections, and the arithmetic that decides whether your cluster survives a failure (a 3-node set survives one loss; a 4-node set also survives only one, which is why adding a node made one team's availability worse); what a failover actually costs end-to-end — a 90-second claim measured at 7m12s once DNS TTL, driver caches and connection pools were included, then tuned to 1m35s; write concern in depth, and the fact that wtimeout firing does not undo the write — it returns an error for an operation that is still applied and may still become durable, which is the single most misunderstood behaviour in MongoDB; rollback, where a write acknowledged with w: 1 was reverted on failover and 2,140 orders vanished into a rollback directory nobody knew existed; the read-concern and read-preference matrix, and the read-your-own-writes trap created by the default pairing of majority writes with local reads; replication lag — what causes it, what it actually breaks, and why flow control exists; and the topology decisions that matter, including why an arbiter is almost always the wrong answer and what a delayed member is really for. Prerequisites: CRUD and What It Guarantees and What MongoDB Actually Is.

Part 1 — One Primary, One Log, Many Tailers

  CLIENT
    |  all writes
    v
  PRIMARY  ---- writes to the OPLOG (a capped collection in local.oplog.rs)
    |             |
    |             +---- SECONDARY 1  tails the oplog, applies in order
    |             +---- SECONDARY 2  tails the oplog, applies in order
    |
    +-- reads, by default

  The oplog is the ONLY replication mechanism. There is no
  page-level or file-level shipping. A secondary is a node that
  reads the primary's operation log and replays it.

Two properties of oplog entries explain most of what follows.

PropertyWhy it matters
Entries are idempotent{ $inc: { n: 1 } } is recorded as { $set: { n: 5 } }. Applying an entry twice is safe, which is what makes crash recovery and resumable sync possible
Entries are per-documentAn updateMany touching 1M documents produces 1M oplog entries. A bulk operation is not bulk in the oplog — this is why backfills cause lag
The oplog is cappedIt has a fixed size and old entries are overwritten. A secondary that falls further behind than the oplog window cannot catch up and needs a full resync
Ordering is totalEvery entry has a timestamp and term; secondaries apply in exactly the primary's order (with batching, but never reordered across dependencies)
  db.getReplicationInfo()
    -> logSizeMB, usedMB, timeDiff (the OPLOG WINDOW in seconds),
       tFirst, tLast

  The oplog window is the single most important number in a
  replica set that nobody watches. It is how long a secondary can
  be down before it needs a full resync -- and it is not a
  configured duration, it is size / write rate.

  MEASURED: a 50 GB oplog gave a 26-hour window at normal load.
  During a 41M-document backfill it produced 19 GB in 34 minutes,
  and the window collapsed to 5 hours. A delayed member configured
  with an 8-hour delay silently became unable to keep its
  guarantee.
🔑 The oplog window is a duration, not a size, and it moves with your write rate. Alert on timeDiff falling below your worst-case maintenance duration — typically the time to reboot and patch a node, or the delay on your delayed member. A window that is comfortable at steady state can collapse during a migration, and you discover it when a secondary comes back from a reboot and needs an eight-hour full resync instead of a two-minute catch-up.

Part 2 — Elections and What a Failover Really Costs

  Members exchange heartbeats every 2 seconds.
  If a secondary hears nothing from the primary for
  electionTimeoutMillis (default 10,000 ms), it calls an election.

  To become primary a node needs votes from a MAJORITY of the
  configured voting members -- not of the reachable ones.

    3 members: majority 2  -> survives 1 failure
    4 members: majority 3  -> survives 1 failure   (no better)
    5 members: majority 3  -> survives 2 failures
    7 members: majority 4  -> survives 3 failures

  Even-numbered sets buy nothing. A 4-node set has the same
  fault tolerance as a 3-node set and costs 33% more.

MEASURED: "failover takes 10 seconds" versus the endpoint

  A team's runbook claimed 90 seconds. The measured
  time-to-recovered-service on an unannounced primary kill:

    t+0.0s   primary killed
    t+10.4s  secondary detects the missing heartbeats
    t+11.1s  election completes, new primary elected
    t+11.1s  ---- MongoDB's part is DONE ----
    t+38s    DNS TTL (60s record, cached ~27s remaining) expires
             on the app hosts using a seedlist that had gone stale
    t+95s    driver connection pools finish failing over; each
             pooled connection had to error once before being
             discarded
    t+150s   JVM-level DNS cache (networkaddress.cache.ttl
             unset = cache forever on some JVMs) still resolving
             to the dead host on 3 of 14 app instances
    t+7m12s  those 3 instances restarted by an operator; service
             fully recovered

  After tuning:
    SRV records with a 30s TTL, JVM DNS TTL set to 30s,
    serverSelectionTimeoutMS 5000, retryWrites enabled,
    heartbeatFrequencyMS 5000
                                        -> 1m35s, no restarts

The lesson is not that MongoDB is slow to fail over — it took 11 seconds. It is that failover is a client-side event as much as a server-side one, and every layer between the two has its own timeout and its own cache. A failover drill that measures only rs.status() proves nothing about whether your application recovers.

SettingEffectCaution
priorityHigher values are preferred as primary; 0 means never eligiblePriority differences cause extra elections — a recovered high-priority node forces a step-down
votes: 0Member replicates but does not voteRequired beyond 7 voting members
electionTimeoutMillisHow long before an election is calledLower = faster failover, more spurious elections on a flaky network

Part 3 — Write Concern, and the Two Things It Does Not Do

  { w: 1 }              primary acknowledged it (in memory)
  { w: "majority" }     a majority of voting members have it (DEFAULT
                        since 5.0)
  { w: 2 }              a specific count -- fragile, prefer "majority"
  { w: 0 }              fire and forget; you are not told about errors
  { j: true }           the acknowledging nodes wrote to the journal
                        (on disk), not just memory
  { wtimeout: 5000 }    give up WAITING after 5 seconds
⚠️ wtimeout is not a rollback and not a cancellation. If the timeout fires, you receive an error — and the write has already been applied on the primary. It will very likely replicate a moment later and become permanent. So a wtimeout error means "I do not know whether this became durable", never "this did not happen". Code that retries on wtimeout without an idempotency key will double-apply. One payment system created 340 duplicate charges this way during a 90-second lag spike.

Rollback: when an acknowledged write is undone

  1. Primary A accepts a write with w: 1 and acknowledges it.
  2. Before it replicates, A is partitioned from the set.
  3. B is elected primary. It never saw the write.
  4. Traffic continues on B for several minutes.
  5. A rejoins. Its extra operations conflict with the new
     history, so A ROLLS THEM BACK.

  The rolled-back documents are written to a rollback directory
  (or a local collection, 4.4+) as BSON files. They are NOT
  reapplied. Recovering them is a manual job.

  MEASURED: 2,140 orders acknowledged to customers, then rolled
  back. Order confirmation emails had already been sent. The
  rollback files were found four days later, by which time
  reconciling them against subsequent activity was a multi-day
  project.

  With w: "majority" this cannot happen: a majority-acknowledged
  write is by definition present on enough nodes that any new
  primary must contain it.
Write concernLatencyCan be rolled back?Use for
w: 0~0Yes, and you would not knowNothing that matters. Metrics at extreme volume, at most
w: 1Lowest meaningfulYesData you can regenerate — caches, derived state
w: "majority"+ one round trip to the nearest majorityNoThe default, and correct for almost everything
w: "majority", j: true+ fsync on those nodesNo, and survives simultaneous power lossFinancial records, anything legally material
MEASURED: what majority actually costs

  Single region, 3 nodes, same AZ group
    w: 1           p50 0.9 ms   p99  2.1 ms
    w: majority    p50 1.8 ms   p99  4.4 ms
    w: majority
       + j: true   p50 3.1 ms   p99 11.0 ms

  Multi-region, majority spanning an ocean
    w: majority    p50 84 ms    p99 210 ms
                   -- the physics of the round trip, unavoidable

  In a single region majority is nearly free and the argument for
  w: 1 is weak. Across regions it is a genuine architectural
  decision, and the answer is usually to keep the majority within
  one region and treat the far region as a read/DR replica.

Part 4 — Read Concern, Read Preference, and Reading Your Own Writes

Read concernGuaranteeCost
"local" (default)Whatever this node has — may not be replicated, may be rolled backLowest
"available"Like local, and on a sharded cluster skips the orphan filterLowest; can return orphaned documents
"majority"Only majority-committed data; will never be rolled backWaits for the commit point — a few ms normally, much more under lag
"snapshot"A single consistent point-in-time view for the whole operationHighest; used in transactions
"linearizable"Reflects every majority write that completed before this read beganVery high. Primary only, single document, requires maxTimeMS
  THE DEFAULT MISMATCH

    writes default to  w: "majority"
    reads  default to  readConcern: "local"

  So the default configuration is: durable writes, and reads that
  may show you data which has not committed and could vanish.

  For most workloads that is a good trade. For a screen that
  displays a value the user just changed, or anything financial,
  it is quietly wrong -- and it is wrong in a way that only
  appears during a failover, which is the worst possible time to
  discover it.

  READ-YOUR-OWN-WRITES, three ways

  BROKEN
    await orders.insertOne(doc);                    // primary
    const list = await orders.find({ customerId })  // secondary
                             .toArray();
    // the new order is often absent

  FIX 1 -- causal consistency (the general answer)
    const s = client.startSession();
    await orders.insertOne(doc, { session: s });
    const list = await orders.find({ customerId }, { session: s })
      .readConcern("majority").toArray();
    // the session carries a cluster time; the read WAITS for the
    // node to reach it. Requires majority read concern to work.

  FIX 2 -- read the primary on that path
    Simple, and it puts read load back on the primary.

  FIX 3 -- do not re-read at all
    Return the document you just wrote, or use findOneAndUpdate
    with returnDocument: "after".
    Cheapest, removes a round trip, and the one people forget.

primaryPreferredPrimary, else a secondaryUsually the worst choice — it silently becomes stale precisely during a failover, when things are already going wrong
secondarySecondaries onlyFails entirely if all secondaries are down

Part 5 — Replication Lag

  rs.printSecondaryReplicationInfo()
  // or, programmatically:
  rs.status().members.map(m => ({ name: m.name, state: m.stateStr,
      lagSec: (primaryOptimeDate - m.optimeDate) / 1000 }))

  Lag is: primary's latest optime MINUS this secondary's optime.
  It is a symptom, never a cause. The causes:
CauseSignalFix
Bulk write on the primaryLag rises during a migration or backfillBatch it with w: "majority" so replication applies backpressure — see Schema Validation & Evolution
Secondary underpowered or busyOne member lags, others do notMatch hardware; move analytics off that node
Long-running query on a secondaryOplog application blocked behind a readBound reports with maxTimeMS; use a dedicated analytics node
Index buildLag on all secondaries at onceRolling build
Network saturationLag correlates with throughput, not with a nodeCapacity; check cross-AZ/region bandwidth
Many single-document writesOplog entry count, not byte volumeBatching helps only if it reduces the number of documents touched
  WHAT LAG ACTUALLY BREAKS -- in order of how much it hurts

  1. w: "majority" writes STALL. This is the big one. If a
     majority cannot acknowledge, every majority write blocks
     until wtimeout. Lag becomes a WRITE OUTAGE, not just a stale
     read.
  2. Secondary reads become stale by the lag amount.
  3. The oplog window shrinks (the primary keeps producing).
  4. A failover to a lagging secondary loses more data / takes a
     longer catch-up.

  FLOW CONTROL (4.2+) exists for #1: the primary deliberately
  slows its own writes to keep the majority commit point within
  flowControlTargetLagSeconds (default 10). It converts a cliff
  into a slope -- so "writes got slower" during a heavy job is
  often flow control working correctly, not a fault.

Part 6 — Topology Decisions

Member typeWhat it isUse it for
Standard secondaryVotes, replicates, can be elected, serves readsThe default
priority: 0Replicates and votes but can never be primaryA member in a region you never want to serve writes
hidden: trueInvisible to drivers; priority: 0 impliedBackups, analytics, index builds — the right place for anything that churns cache
slaveDelay / secondaryDelaySecsApplies the oplog N seconds lateProtection against operator error, not against hardware failure
ArbiterVotes; holds no dataAlmost never. See below
  WHY AN ARBITER IS USUALLY WRONG

  P + S + A looks like a cheap 3-node set. It is not equivalent.

  If the one data-bearing secondary fails:
    - the set still has a majority (P + A), so P stays primary
    - but there is now only ONE copy of your data
    - and w: "majority" needs 2 of 3 acknowledgements... from
      nodes that HAVE the data. With one data node left, majority
      writes CANNOT be satisfied. Writes stall.

  So the failure it is supposed to survive is exactly the one
  where it degrades you to zero redundancy AND blocks majority
  writes. It also cannot serve reads, cannot be promoted, and
  cannot help a resync.

  MEASURED: a P+S+A set lost its secondary at 02:10. The primary
  remained primary, so no alert fired for "no primary". Majority
  writes began timing out. The team spent 40 minutes investigating
  an "application bug" before someone ran rs.status().

  The correct answer is a third data-bearing member. If the cost
  is the objection, use a smaller instance with priority: 0 --
  it still holds data, still votes, still satisfies majority.

  DELAYED MEMBER -- what it is actually for

  secondaryDelaySecs: 3600, hidden: true, priority: 0, votes: 0

  It protects against: a bad migration, an accidental
  db.collection.drop(), a buggy deploy deleting data. You have
  one hour to notice and recover from that member.

  It does NOT protect against: hardware failure (it has the same
  data), or anything you notice after the delay window.

  Two requirements people miss:
    - the oplog window must exceed the delay, or the member falls
      off and needs a resync
    - votes: 0 unless you have counted the majority arithmetic --
      a delayed voting member can be elected in a bad scenario
      and promote hour-old data
🔑 Test the failover, do not reason about it. Every claim in this lesson about timing came from killing a primary and watching a real application, not from documentation. The drill that matters is unannounced, includes the client stack, and measures time-to-recovered-service rather than time-to-new-primary — which in the measured case differed by a factor of 39. Run it quarterly, and run it after any change to DNS, driver version, or connection settings.

Interview Questions

Beginner: How does replication work in MongoDB?

The primary records every change as an entry in a capped collection called the oplog. Secondaries tail that oplog and replay the entries in order. That is the entire mechanism — there is no file-level or page-level shipping.

Two details matter downstream. Oplog entries are idempotent — { $inc: { n: 1 } } is stored as { $set: { n: 5 } } — which is what makes crash recovery and resumable sync safe. And they are per-document, so an updateMany touching a million documents produces a million oplog entries, which is why bulk operations cause replication lag.

Beginner: Why should a replica set have an odd number of members?

Because elections require a majority of the configured voting members, and adding an even member raises the majority threshold without raising fault tolerance. Three members need two votes and survive one failure. Four members need three votes and still survive only one failure — you have paid 33% more for nothing. Five members need three and survive two.

The same arithmetic is why arbiters are a trap: they add a vote without adding a data copy, so the set can retain a majority while having only one copy of the data left.

Mid: What does wtimeout do when it fires?

It stops waiting. It does not cancel or undo anything. The write has already been applied on the primary, and it will very likely replicate a moment later and become permanent.

So a wtimeout error means "I do not know whether this became durable" — never "this did not happen". Code that treats it as a failure and retries will double-apply. One payment system created 340 duplicate charges this way during a lag spike.

The correct handling is to make the operation idempotent — an idempotency key, a unique index on a business identifier, or a conditional update guarded by the state you expect — so that a retry under uncertainty is safe. That is a general principle for any distributed write, and wtimeout is just the case that makes it obvious.

Mid: What is a rollback and how do you prevent one?

If a primary accepts writes that have not reached a majority, is then partitioned, and a new primary is elected without those writes, the old primary must discard them when it rejoins. Those documents are written to rollback files and are not reapplied — recovering them is a manual reconciliation job.

The damage is not just data loss, it is that the client was told the write succeeded. In one incident 2,140 orders were acknowledged, confirmation emails sent, and then rolled back; the files were found four days later, by which time reconciling them against subsequent activity was a multi-day project.

Prevention is w: "majority", which is the default since 5.0. A majority-acknowledged write is present on enough nodes that any node capable of winning an election must already have it, so it cannot be rolled back. In a single region the cost is small — measured p50 0.9 ms versus 1.8 ms — which makes the argument for w: 1 on important data very weak.

Senior: A user updates their profile and immediately sees the old value. Diagnose and fix.

The classic cause is a read served by a secondary that has not yet applied the write. But I would confirm rather than assume, because there are three distinct causes with different fixes.

Cause 1 — secondary read. The write went to the primary; the subsequent read went to a secondary that is milliseconds behind. Check the read preference on that code path.

Cause 2 — read concern. Even on the primary, readConcern: "local" is fine here — the primary has the write. But in a sharded or session-less setup, a read routed elsewhere shows the same symptom.

Cause 3 — not the database at all. An application or CDN cache, or a stale value already held in the client. I would check this early because it is common and costs nothing to rule out.

The fixes, in the order I would prefer them: first, do not re-read — return the document from the write itself, or use findOneAndUpdate with returnDocument: "after". That removes a round trip and the entire class of bug. Second, causal consistency: perform both operations in one client session with majority read concern, so the read waits until the node has reached the session's cluster time. Third, pin that path to the primary — simple, but it moves read load back and does not generalise.

What I would push back on: "just read from the primary everywhere". It solves this symptom and gives up the read scaling that secondaries exist for, and it does not help in a sharded deployment or across sessions. Causal consistency is the mechanism designed for this, and it is a session parameter rather than an architectural retreat.

Senior: Design a replica set topology for a service in two regions with a 5-minute RTO.

The decision that drives everything: where does the majority live? Writes cannot commit without a majority, so majority placement determines both write latency and what a regional failure does to you.

  OPTION A -- majority in the primary region
    Region 1: 3 members (P, S, S)
    Region 2: 2 members (S, S) priority 0 or low

    write latency: local (majority satisfied in-region)
    lose region 2: no impact at all
    lose region 1: NO MAJORITY. Region 2 cannot elect a primary
                   without manual reconfiguration.
                   -> a documented, rehearsed procedure, roughly
                      5-15 minutes. Meets a 5-minute RTO only if
                      it is automated and drilled.

  OPTION B -- majority spanning regions
    Region 1: 2, Region 2: 2, Region 3 (or a cloud zone): 1

    write latency: EVERY write waits for a cross-region ack.
                   Measured p50 84 ms, p99 210 ms.
    lose either region: automatic failover, no human involved.

My recommendation depends on the write latency budget, and I would ask for it explicitly. If the application can absorb ~85 ms per write, option B genuinely meets a 5-minute RTO with no human in the loop, and that is worth a great deal. If it cannot — most interactive products cannot — then option A with a rehearsed and automated reconfiguration is the honest answer, and I would say plainly that an unrehearsed manual procedure does not meet a 5-minute RTO no matter what the runbook claims.

What I would specify regardless: the region-2 members as priority: 0 in option A so a network blip cannot elect a distant primary; a hidden tagged member for backups and analytics; maxStalenessSeconds on any secondary reads; and an oplog window sized to exceed the worst-case time a region is unreachable, or a returning region needs a full resync instead of a catch-up.

And the measurement that matters more than the topology: a quarterly unannounced drill measuring time to recovered service, not time to new primary. The two differed by a factor of 39 in the case I measured — 11 seconds of election, 7 minutes of DNS TTLs, JVM DNS caches and connection pools. An RTO that has only ever been calculated is a guess.

🏋️ Exercises

1 (easy): A team proposes P + S + A (two data members and an arbiter) to save on infrastructure. Explain what happens when the secondary fails.
Solution

Three things happen at once, and the third is the one that causes the incident:

  1. The set keeps a majority (primary + arbiter = 2 of 3), so the primary stays primary. Nothing fails over, and no "no primary" alert fires.
  2. Redundancy drops to zero. One copy of the data remains. Losing the primary now means data loss, not a failover.
  3. Every w: "majority" write stalls. Majority means acknowledgement from a majority of members that hold data, and only one such member is left. Writes block until wtimeout.

So the failure the arbiter was supposed to help with is precisely the one where it leaves you with no redundancy and a write outage — while suppressing the most obvious alarm.

In a measured case, a P+S+A set lost its secondary at 02:10, majority writes began timing out, and the team spent 40 minutes investigating an "application bug" before anyone ran rs.status().

The fix: a third data-bearing member. If cost is the objection, a smaller instance with priority: 0 still holds data, still votes, and still satisfies majority — which is everything the arbiter fails to do. An arbiter's only legitimate niche is a set where a data member is genuinely impossible to place, and even then it is a compromise to document rather than a design to choose.

2 (easy): Classify these operations by the write concern you would use, with reasoning. 
  a) recording a payment
  b) updating a "last seen" timestamp on a session
  c) writing an audit log entry for a permission change
  d) incrementing a page-view counter
  e) creating a user account
Solution
Write concernReasoning
a) paymentw: "majority", j: trueMust survive a failover and simultaneous power loss. The extra ~2 ms measured is irrelevant against a financial record
b) last seenw: 1Regenerated on the next request; losing one is invisible. High volume, so latency matters more than durability
c) audit logw: "majority", j: trueIts entire purpose is to be trustworthy after the fact. An audit log that can silently roll back is worse than none, because it is believed

The general rule: ask what happens if this write is silently reverted after being acknowledged. If the answer involves a person being told something untrue — a payment taken, an account created, a permission recorded — use majority. If the data regenerates itself, w: 1 is a legitimate optimisation.

Worth noting: in a single region majority costs about 0.9 ms extra at p50. That is small enough that w: 1 should be a deliberate choice for a specific high-volume path, not a global default. Across regions the cost is 84 ms and the decision becomes genuinely architectural.

3 (medium): After a failover, customers report that some orders they received confirmations for have disappeared. Investigate.
Solution

This is a rollback, and the pattern is diagnostic: orders acknowledged to the client, confirmation sent, then gone after a failover. That combination means writes were acknowledged before reaching a majority — w: 1 or lower.

Immediate investigation:

  1. Find the rollback data. 4.4+ writes rolled-back documents to
     a local collection; earlier versions write BSON files to
     <dbpath>/rollback/<db>.<collection>/. Do this FIRST -- the
     files can be cleaned up, and in one case they were found
     four days later when reconciliation had become far harder.

  2. Confirm the timeline:
     rs.status() -- the election time and the new primary's term
     the old primary's log -- "transition to ROLLBACK"
     Match against the order timestamps customers are reporting.

  3. Quantify: how many documents, which collections, what value.

Recovery: the rollback files are BSON and can be inspected with bsondump, but they must not be blindly reinserted — the same customers may have retried and created new orders, and inventory or payment state has moved on. Reconciliation is per-document: does this order already exist under another _id, was the payment captured, was stock allocated. That is why finding the files early matters so much.

The fix, and it is one line: w: "majority" on order writes — which is the default since 5.0, so the first thing I would check is whether something explicitly overrode it. A driver-level default set years ago for latency reasons is the usual culprit.

What I would also fix, because the rollback was not the only failure: the confirmation email was sent on the basis of an acknowledgement that did not guarantee durability. Any outward-facing side effect — email, payment capture, webhook — should be triggered from a majority-committed state, ideally via an outbox pattern read by a separate process, so that a rollback cannot leave a customer holding a receipt for something that never happened.

4 (medium): Replication lag spikes to 4 minutes every night at 02:00 and majority writes start timing out. Investigate and fix.
Solution

The timing says "scheduled job", so I would start with what runs at 02:00 rather than with the database. The strong candidates, in order:

CandidateHow to confirm
A bulk migration/backfill (updateMany, a data fix)Oplog entry rate; db.currentOp() during the window; per-document oplog volume
A backup taking a snapshot or running mongodump against a secondaryThe lagging member is the backup target; I/O saturation on it
An analytics aggregation on a secondary blocking oplog applicationLong-running getmore/aggregate on that member
An index buildAll secondaries lag together
A TTL purgemetrics.ttl.deletedDocuments spiking; per-document deletes are per-document oplog entries

The distinguishing question is whether one member lags or all of them. One member means something is wrong on that node (backup, analytics, hardware). All members means the primary is producing oplog faster than they can apply it, which points at a bulk write.

Why it becomes a write outage rather than a staleness problem: when a majority cannot acknowledge, every w: "majority" write blocks until wtimeout. This is the part people do not anticipate — lag is usually discussed as a read-freshness issue, and its most damaging effect is on writes.

Fixes, by cause:

  • Bulk write: batch it on _id ranges with w: "majority" and a lag-aware sleep. Majority acknowledgement makes replication itself apply the backpressure. The measured version of this took a job from 34 minutes with 4m12s lag to 9 hours with 6.4 s lag and no impact.
  • Backup/analytics on a secondary: move it to a hidden member so it neither serves reads nor is expected to keep pace with the others under load.
  • TTL purge: consider time-bucketed collections where retention is a drop() rather than millions of individual deletes.

Also check flow control. If flowControlTargetLagSeconds has been raised or flow control disabled, the primary is no longer throttling itself, which converts a slope into a cliff. Its default behaviour — writes getting slower during a heavy job — is the system working, not a fault to tune away.

5 (hard): Design and script a failover drill that would have caught the 7-minute recovery described in Part 2.
Solution

The design principle: measure time to recovered service, not time to new primary. The two differed by a factor of 39. A drill that watches rs.status() would have declared success at 11 seconds and proved nothing.

  BEFORE
    - a synthetic client running the real application's write and
      read paths, through the real driver, from a real app host --
      not a mongosh loop on the database host, which bypasses
      every layer that actually broke
    - continuous 1 rps of each, logging {timestamp, outcome,
      latency} to a file OUTSIDE the cluster
    - record the environment: DNS TTLs, driver version, JVM/runtime
      DNS cache settings, pool config, serverSelectionTimeoutMS

  THE DRILL
    1. Baseline for 5 minutes.
    2. Kill -9 the primary process (not stepDown -- a graceful
       step-down hands off cleanly and hides the DNS and pool
       problems entirely).
    3. Do not touch anything. Let it recover on its own.
    4. Stop when the synthetic client has had 60 consecutive
       seconds of success.

  MEASURE, from the client's log
    t_election      first successful write after the kill
    t_full          60s of clean operation
    error_count     and their TYPES -- distinguishing
                    "no primary available" from "connection reset"
                    from "server selection timeout" is what
                    localises the problem
    write_loss      compare acknowledged writes against what is
                    present afterwards
    p99 during and after

  ALSO CAPTURE
    - per-instance behaviour. In the measured case 11 of 14
      instances recovered and 3 did not -- an average would have
      hidden that entirely
    - DNS resolution from each app host during the event

What this specifically catches that a server-side drill cannot: DNS TTL and seedlist staleness, runtime-level DNS caching (a JVM with networkaddress.cache.ttl unset caches forever on some configurations), serverSelectionTimeoutMS exceeding the application's own request timeout, connection pools that only discard a stale connection after it errors once, and any instance that needs a restart to recover.

The rules that make it worth running: unannounced (an announced drill has everyone watching, which is not the failure mode); in production or in an environment that shares production's DNS and networking, because staging usually does not reproduce the layers that break; and repeated after every change to driver version, DNS, or connection settings, since those are exactly what regressed.

The output should be a number with a date attached — "time to recovered service: 1m35s, measured 2026-08-14" — because an RTO that has only ever been calculated is a guess, and the gap between the runbook's 90 seconds and the measured 7m12s is the entire point of the exercise.

6 (hard): A team wants to move all read traffic to secondaries to relieve the primary. Evaluate the proposal.
Solution

I would not reject it, but I would reframe it: "move reads to secondaries" is not one decision, it is a per-query-path decision, and applying it globally introduces correctness bugs to relieve a pressure that may not be where they think.

First, verify the premise. Is the primary actually read-bound? Check the read/write ratio in opcounters, the cache hit rate, and whether the load is really coming from a few unindexed queries or a reporting job. If two bad queries are the cause, fixing them is far cheaper than a topology change — and if the working set exceeds cache, secondary reads move the problem rather than solving it, because the secondaries have the same cache pressure.

Then classify the read paths:

PathSecondary-safe?
Reports, analytics, exports, admin dashboardsYes — and they should never have been on the primary. Best on a hidden tagged member
Read-only browsing of data the user did not just change (catalogue, search, feeds)Yes, with maxStalenessSeconds
Anything immediately after a write by the same userNo — this is the read-your-own-writes trap
Reads that feed a subsequent conditional write (read-modify-write)No — a stale read makes the guard meaningless
Financial balances, inventory checks, authorisation decisionsNo — staleness is a correctness failure, not a UX one

The specific things I would require if we proceed: maxStalenessSeconds on every secondary read so a badly lagging member cannot serve arbitrarily old data; causal-consistent sessions on any path that follows a write; and secondaryPreferred rather than secondary, so losing the secondaries degrades to the primary instead of to an outage.

The one option I would rule out: primaryPreferred. It sounds like the cautious middle ground and it is the worst of the set — it reads the primary in normal operation (so it relieves nothing) and silently switches to stale secondary reads exactly during a failover, when the system is already misbehaving and nobody will attribute the wrong data to a read preference.

What I would propose instead, as the first step: move only reports and analytics, onto a dedicated hidden member. In the case I measured, that alone took unrelated p99 from 34 ms to 4 ms by ending the cache churn on the primary — most of the benefit, none of the correctness risk, and it is reversible in a config change. Then re-measure before touching any user-facing read path.

🎯 Key Takeaways

  • Replication is oplog tailing. Entries are idempotent and per-document — a million-document update is a million oplog entries.
  • The oplog window is a duration that moves with your write rate. A backfill took one from 26 hours to 5, silently breaking a delayed member's guarantee.
  • Elections need a majority of configured voting members. 3 and 4 members both survive exactly one failure.
  • An arbiter adds a vote without a data copy. Losing the one data secondary leaves zero redundancy and stalls majority writes, with no "no primary" alert.
  • Failover is a client-side event. 11 seconds to elect, 7m12s to recovered service, because of DNS TTLs, JVM DNS caches and connection pools.
  • wtimeout does not undo the write. It means "unknown", and retrying without an idempotency key double-applies — 340 duplicate charges in one incident.
  • w: 1 writes can be rolled back. 2,140 acknowledged orders ended up in rollback files that were found four days later.
  • In a single region, majority costs about 0.9 ms. Across regions it costs ~84 ms and becomes an architectural decision.
  • Writes default to majority; reads default to local. That mismatch is the read-your-own-writes trap and it only shows up during a failover.
  • The cheapest fix for read-your-own-writes is not re-reading — return the written document, or use findOneAndUpdate with returnDocument: "after".
  • Causal consistency is the general mechanism: one session, majority read concern, and the read waits for the node to reach the session's cluster time.
  • primaryPreferred is usually the worst read preference — it relieves nothing normally and goes stale exactly during a failover.
  • Set maxStalenessSeconds on every secondary read. Minimum 90.
  • Lag's worst effect is on writes, not reads: majority writes stall, turning lag into a write outage. Flow control exists to make that a slope rather than a cliff.
  • Put backups, analytics and index builds on a hidden member — long queries on a normal secondary block oplog application.
  • A delayed member protects against operator error, not hardware failure, and needs votes: 0 plus an oplog window longer than its delay.
  • Drill failover unannounced, with a real client, measuring time to recovered service. An RTO that has only been calculated is a guess.
