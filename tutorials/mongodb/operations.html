Operating MongoDB Production

What you'll master: the small set of numbers that actually predict trouble, and the much larger set that does not — starting with the one most dashboards omit, pages evicted by application threads, which is the difference between a database that is fine and one that is about to fall off a cliff (p99 measured at 1.4 ms below the line and 340 ms just above it, with no gradual slope in between); how to size a cluster from the working set rather than the data size, and why a 4 TB collection can be perfectly happy on a 64 GB machine while a 200 GB one is not; the triage sequence for a live incident, in the order that eliminates the most possibilities per minute — and the check that takes 30 seconds and reframes the entire investigation; upgrades, where the mechanism people miss is feature compatibility version, the one-way-ish switch that decides whether you can roll back; the change-management discipline for the operations that have bitten every team in this track — index builds, backfills, validator changes, shard-key decisions; and the client side, which causes more production incidents than the server does: connection pools, and the timeout inversion where an application gave up at 10 s while serverSelectionTimeoutMS was still waiting 30. Prerequisites: Query Tuning in Production and Replica Sets & Read Concerns.

🔑 Alert on pages evicted by application threads > 0. In normal operation background eviction threads keep the cache clean and this counter stays at zero. Non-zero means a user's query had to evict pages before it could proceed — the storage engine telling you the working set no longer fits. It is the only MongoDB metric I know of where "any value above zero" is a meaningful alert, and it fires before latency does.

Part 2 — Sizing From the Working Set

  WiredTiger cache default = max(50% of (RAM - 1GB), 256MB)
  A 64 GB machine therefore gets ~31.5 GB of cache.

  The remaining RAM is NOT wasted -- the filesystem cache uses it
  for compressed data. WiredTiger cache holds UNCOMPRESSED pages;
  the OS cache holds compressed blocks. Both matter.

  WHAT MUST FIT IN CACHE:
    indexes you actually use          + hot documents
                                      + a little headroom

  NOT: the whole collection. A 4 TB collection whose queries only
  ever touch the last 30 days can be entirely comfortable on a
  64 GB machine. A 200 GB collection scanned randomly cannot.

  ESTIMATING THE WORKING SET, practically

  1. Total index size -- this is the floor, and it is the number
     people forget:
       db.stats().indexSize
       db.coll.stats().indexSizes    // per index

  2. Hot document estimate: the documents touched in a
     representative window. Derive it from the access pattern,
     not from the collection size --
       (documents read per day) x (avg doc size) x overlap factor

  3. Compare against cache. If indexes alone approach cache size,
     that is the finding: dedupe indexes by prefix before buying
     RAM. One team recovered 4.1 GB of cache by dropping eight
     redundant indexes -- cheaper and faster than a resize.

  4. Verify empirically: the eviction counter is the truth. Any
     model that says you fit while that counter is climbing is
     wrong.
ResourceRule of thumbFailure mode when short
RAMWorking set + indexes fit in cache, with headroom for growthThe cliff: 180× latency change over a small range
Disk IOPSProvision for the miss rate, not the request rateEverything slows once you are reading from disk
Disk spaceData + indexes + oplog + 20–30% for compaction and growthA full disk on a primary is an immediate outage
CPUUsually not the constraint; index builds, aggregation and compression are the exceptionsQueueing on tickets
Connections~1 MB each; total across all app instancesMemory pressure and scheduling overhead

Part 3 — Triage: The First Five Minutes

  ORDER MATTERS. Each step eliminates the most possibilities per
  second spent.

  1. WHAT IS RUNNING RIGHT NOW?            (10 seconds)
     db.currentOp({ secs_running: { $gt: 3 },
                    op: { $in: ["query","command","getmore",
                                "update","remove"] } })
     One runaway operation explains a surprising share of
     incidents. If you find it: killOp, then investigate.

  2. IS THE WORKING SET STILL FITTING?     (30 seconds)
     serverStatus().wiredTiger.cache
       ["pages evicted by application threads"]
     Non-zero and climbing REFRAMES EVERYTHING: every query is
     slow for one reason and no index change will fix it.

  3. IS ANYTHING ELSE RUNNING?             (30 seconds)
     An index build, a backfill, a backup, an initial sync, a
     balancer migration. These present exactly like a query
     problem and are not one.
       db.currentOp({ $or: [ { "command.createIndexes":
                                { $exists: true } } ] })
       sh.isBalancerRunning()      // sharded
       rs.status()                 // any member in STARTUP2?

  4. REPLICATION AND WRITE AVAILABILITY    (30 seconds)
     rs.status() lag. If a majority cannot acknowledge, majority
     writes are stalling -- which looks like an application bug.

  5. CONNECTIONS                            (30 seconds)
     serverStatus().connections
     Near the limit? Then the database may be healthy and the
     POOL is the problem.

  6. ONLY NOW: the slow query log.
SymptomMost likely causes, in order
Everything is slow at onceCache cliff · a concurrent operation (index build, backfill, backup) · disk saturation · CPU steal on a noisy neighbour
One endpoint is slowMissing index · plan-cache change · data growth on one tenant · a broadcast query on a sharded cluster

⚠️ During an incident, prefer reversible interventions. killOp on a runaway operation, a hint() deployed in the application, shedding a non-critical endpoint, or hideIndex — all reversible in seconds. What I would not do on a struggling cluster is start an index build: it consumes CPU, evicts cache, and cannot be cheaply undone. Optimisations belong in the calm window afterwards, with the evidence attached.

Part 4 — Upgrades and Feature Compatibility Version

  THE MECHANISM PEOPLE MISS

  Upgrading binaries and enabling new features are SEPARATE steps.

    1. Upgrade binaries, one node at a time (rolling).
       FCV stays at the old version. New on-disk formats and
       features are NOT used.
       -> you can still downgrade the binaries. This is the
          reversible window, and it is the whole point.

    2. Soak. Days, not minutes. Run a full business cycle.

    3. setFeatureCompatibilityVersion: "8.0"
       -> new features and formats become active
       -> downgrading now requires setting FCV back down FIRST,
          and that can fail if incompatible data or index types
          already exist

  Teams that upgrade binaries and set FCV in the same maintenance
  window have given up their rollback path for no benefit.

  ROLLING UPGRADE ORDER

  Replica set:  secondaries one at a time -> verify each has
                caught up -> rs.stepDown() the primary -> upgrade
                the former primary last

  Sharded:      1. mongos routers?  NO -- config servers first
                Order: config servers -> shards (each as a replica
                set, by the rule above) -> mongos LAST

  Always: check driver compatibility BEFORE the server upgrade.
  An old driver against a new server usually works; a new driver
  against an old server often does not, and the two are upgraded
  by different teams on different schedules.
StepVerify before proceeding
Before startingBackups exist and have been restored recently; oplog window exceeds the time a node will be out; driver versions checked
After each secondaryrs.status() shows SECONDARY and lag near zero
Before stepping downAll other members are upgraded and healthy; a step-down during peak is an unnecessary failover
Before setting FCVA full business cycle has passed, including month-end jobs
After FCVNothing — this is the point of no easy return. Which is why step 2 matters

Part 5 — Change Management for the Dangerous Operations

OperationRiskDiscipline
Index buildCPU, cache eviction, runs on all members simultaneously by defaultRolling build on large collections; before the code that needs it ships; never during an incident

Backfill / migrationReplication lag, oplog window collapse, cache evictionBatched on _id ranges, w: "majority" for backpressure, lag-aware sleep, restartable

  THE PRE-CHANGE CHECKLIST, which is short on purpose

  1. What is the blast radius? One collection, one node, or the
     cluster?
  2. What is the EXACT rollback command, and have I run it in a
     non-production environment?
  3. How will I know it is going wrong -- which metric, within
     how long?
  4. Is anything else changing at the same time? (Concurrent
     changes make attribution impossible)
  5. Is the oplog window long enough to survive this?
  6. Who else is awake?

  Items 2 and 3 are the ones that turn a bad change into a
  five-minute event instead of an outage.

Part 6 — The Client Side, Which Causes More Incidents Than the Server

  THE TIMEOUT INVERSION

  serverSelectionTimeoutMS   30000   (driver default)
  application request timeout 10000
  load balancer timeout        5000

  Read it from the bottom: the load balancer gives up at 5 s, the
  app at 10 s, and the driver is STILL waiting until 30 s -- for
  a request nobody is listening to any more. Meanwhile the
  connection is held and the server keeps working.

  CORRECT ORDERING, each layer strictly inside the one outside it:
    maxTimeMS (2s) < serverSelectionTimeoutMS (5s)
                   < app timeout (10s)
                   < load balancer (30s)

  And maxTimeMS on EVERY query, because a client giving up does
  not stop the server: 140 abandoned operations held CPU at 100%
  for 20 minutes after the traffic had gone.
SettingDefaultGuidance
maxPoolSize100 per client instanceMultiply by instance count: 40 pods = 4,000 possible connections at ~1 MB each. Size it to what the server can usefully run in parallel
minPoolSize0A small floor avoids connection-storm latency after an idle period
serverSelectionTimeoutMS30000Lower than the application timeout, always
retryWrites / retryReadstrueLeave on. They absorb a failover transparently for retryable operations
heartbeatFrequencyMS10000Lower speeds up failover detection at the cost of more chatter
One client instance per process—Creating a client per request is the most expensive mistake available: each brings its own pool and its own topology monitoring
MEASURED: pool exhaustion with a healthy database

  Symptom: 503s from the API. Database CPU 12%, no slow queries.

  Cause chain:
    a hot document caused write conflicts inside transactions
      -> withTransaction retried for up to its ~120s budget
      -> each retrying request held a pooled connection
      -> pool (100) fully occupied by requests that were sleeping
      -> new requests could not check out a connection
      -> API returned 503 while the database was nearly idle

  The database was never the problem, and every database metric
  said so.

  Two fixes: bound the retry with an application timeout so a
  request fails fast, and remove the contention -- which was a
  single global counter document written by every request.
🔑 Instrument the client, not just the server. The metrics that would have diagnosed the incident above are all driver-side: connection checkout wait time, pool utilisation, and how long a request holds a connection. Most teams monitor the database thoroughly and the driver not at all, which is why "the database looks fine but the app is down" is such a common and such a slow-to-diagnose class of incident.

Interview Questions

Beginner: Which single metric would you alert on first?

pages evicted by application threads from serverStatus().wiredTiger.cache. In normal operation background threads handle eviction and this counter is exactly zero. Any sustained non-zero value means user queries are being made to evict pages themselves — the working set no longer fits in cache.

It matters because the failure it predicts is a cliff, not a slope. Measured on the same workload: 97% of cache gave p99 of 1.9 ms with zero evictions; 112% gave p99 of 340 ms. By the time the latency graph moves you are already over, and this counter moves first.

It is also unusually easy to alert on, because the healthy value is zero rather than "some threshold we tuned".

Beginner: How much RAM does a MongoDB server need?

Enough for the working set — the indexes you actually use plus the documents actually being touched — not for the whole collection. A 4 TB collection whose queries only ever touch the last 30 days can run comfortably on a 64 GB machine; a 200 GB collection accessed randomly cannot.

The floor is total index size, which is the part people forget: db.stats().indexSize. If indexes alone approach the cache size, the finding is usually that there are redundant indexes — prefix-deduping is free and mechanical, and one team recovered 4.1 GB of cache that way instead of resizing.

WiredTiger's cache defaults to about half of RAM minus 1 GB; the rest is not wasted, because the OS filesystem cache holds compressed blocks. And whatever the model says, the eviction counter is the truth.

Mid: Walk me through the first five minutes of a "the database is slow" incident.

In an order chosen to eliminate the most possibilities per second.

(1) currentOp for operations running over a few seconds. One runaway query explains a surprising share of incidents, and if I find it I can kill it immediately — triage before diagnosis.

(2) The eviction counter. Thirty seconds, and if it is climbing the entire investigation changes: every query is slow for one reason, and no index change fixes it.

(3) Is anything else running? An index build, a backfill, a backup, an initial sync, a balancer migration. These present exactly like a query problem and are not one.

(4) Replication lag, because if a majority cannot acknowledge then majority writes are stalling, which reaches the application as write failures that look like a bug.

(5) Connections. If the pool is exhausted, the database may be entirely healthy and the problem is client-side.

Only then the slow-query log. Starting there is the common mistake: it is the right tool for a specific slow endpoint and the wrong one when everything is slow, because it shows you symptoms of a cause that is not in the log.

Mid: Why should binary upgrade and FCV be separate steps?

Because the gap between them is your rollback window. Upgrading binaries with FCV still at the old version means new on-disk formats and features are not used, so you can downgrade the binaries if something is wrong. Once you set the feature compatibility version, new formats become active, and downgrading requires setting FCV back down first — which can fail outright if data or index types that the old version cannot understand already exist.

So a team that upgrades binaries and sets FCV in the same maintenance window has given up the reversible path for no benefit at all. The soak between them should cover a full business cycle, including the monthly and quarterly jobs, because those exercise code paths that daily traffic does not.

The other ordering people get wrong is sharded clusters: config servers first, then shards, then mongos last. And driver compatibility should be checked before any of it, since a new driver against an old server often breaks and drivers are usually upgraded by a different team on a different schedule.

Senior: The application is returning 503s and every database metric looks healthy. What is happening?

Almost certainly the connection pool, and the reason it is hard to diagnose is that all the instrumentation people have is on the wrong side.

The mechanism I have seen: a hot document caused write conflicts inside transactions; withTransaction retried for up to its ~120-second budget; each retrying request held a pooled connection while mostly sleeping; the pool of 100 filled with requests that were doing nothing; new requests could not check out a connection and the API returned 503 — with the database at 12% CPU and no slow queries, because the database genuinely was not the problem.

How I would confirm it: driver-side metrics — connection checkout wait time, pool utilisation, and how long requests hold connections. Then serverStatus().connections to see it from the other end, and metrics.operation.writeConflicts to localise the contention.

The other candidates with the same signature: a timeout inversion where the driver waits longer than the application does, so connections are held for requests nobody is waiting on; and the aftermath of a failover, where stale DNS or a runtime DNS cache leaves some instances unable to reconnect.

The fixes are in two layers. Immediately, bound the retry with an application timeout so a request fails fast rather than occupying a connection, and check the timeout nesting. Durably, remove the contention — in that case a single global counter document written by every request, which no retry policy or pool size can rescue.

Senior: Design the operational readiness checklist for taking a MongoDB deployment to production.

I would organise it by the question each item answers, because a checklist people understand gets used and one they do not gets copied forward unread.

QuestionItems
Will we know?Alerts on application-thread evictions, replication lag, oplog window, disk space, connection saturation, long-running operations. Profiler enabled at level 1 with a sensible threshold. Driver-side pool metrics — the ones most teams lack
Can we recover?Backups exist, are immutable and in a separate account, retention set from detection time, and have been restored with a measured RTO. A failover drill measuring time to recovered service
Will one bad query take us down?maxTimeMS on every query, strictly nested timeouts, a sized connection pool, one client per process
Is the data correct?Validators on the collections that matter, with a drift count as a metric. Unique indexes for real constraints
Can we change things safely?A written change procedure for index builds, backfills and validator changes; rollback commands documented and tested
Is it secured?Authentication and TLS enforced, least-privilege roles, no application account with admin rights, auditing where required

The two items I would refuse to sign off without are a completed restore drill and maxTimeMS everywhere. Everything else can be added while running; those two are the difference between an incident and a catastrophe, and both are much harder to retrofit under pressure.

What I would deliberately keep off the list: anything aspirational. A checklist with forty items becomes a formality; one with fifteen that are all genuinely blocking stays real. And each item should name the command or dashboard that demonstrates it, so "done" is observable rather than asserted.

🏋️ Exercises

1 (easy): A dashboard shows WiredTiger cache at 82% and the team wants to add RAM. Advise them.
Solution

82% cache utilisation is normal and healthy, and on its own is not a reason for anything. WiredTiger fills the cache with useful pages and evicts as needed; a cache sitting at 30% just means you are paying for RAM you are not using.

The number that would justify the spend:

  serverStatus().wiredTiger.cache["pages evicted by application threads"]

Zero means background eviction is keeping up and the working set fits — no matter what the utilisation percentage says. Sustained non-zero means user queries are doing eviction work themselves, and that is the cliff: measured p99 of 1.9 ms at 97% of cache versus 340 ms at 112%.

What I would check before buying RAM, in order:

  1. Index size versus cache. db.stats().indexSize. If indexes are a large fraction of cache, prefix-dedupe them first — mechanical, free, and one team recovered 4.1 GB that way.
  2. Unused indexes. $indexStats across a full business cycle, then hideIndex for a week before dropping.
  3. Retention. Is cache being consumed by data nobody queries? A TTL or archival policy is cheaper than RAM and keeps being cheaper.
  4. Whether the load is one bad query doing a repeated collection scan and churning the cache for everyone.

If all four are addressed and the eviction counter is still climbing, then RAM is the right answer — and now it is justified by a measurement rather than a percentage that was always going to look like that.

2 (easy): Order these timeouts correctly and explain what goes wrong if they are inverted. 
  application request timeout
  load balancer timeout
  maxTimeMS
  serverSelectionTimeoutMS
Solution 
  maxTimeMS                 2s     innermost
  serverSelectionTimeoutMS  5s
  application timeout      10s
  load balancer timeout    30s     outermost

  Each layer strictly inside the one outside it.

What goes wrong when inverted:

InversionConsequence
Load balancer shorter than the appThe client sees a 504 while the application is still working and will eventually succeed. Work is done and thrown away, and retries multiply the load
serverSelectionTimeoutMS longer than the app timeoutThe driver waits 30 s for a server while the app gave up at 10 — holding a connection for a request nobody is waiting on. This is a common default, since 30 s is the driver's out-of-the-box value
No maxTimeMSThe worst one. A client giving up does not stop the server: in one case 140 abandoned operations held CPU at 100% for 20 minutes after the traffic had stopped

The principle: the innermost layer should always be the first to give up, so failures are attributed correctly and no layer keeps working on something the layer above has abandoned. When the outer layer times out first, you get work without a consumer — which under load becomes a feedback loop, because the retries arrive while the abandoned work is still running.

Note that maxTimeMS is per operation, not per request. A request making four database calls needs its budget divided among them, or the sum can exceed the application timeout even though each call is within its own limit.

3 (medium): Latency stepped up 4× at 03:00 with no deploy and no traffic change. Produce a differential diagnosis with the check for each.
Solution

"Step change, no deploy" narrows this considerably, and 03:00 strongly suggests something scheduled.

HypothesisCheckDistinguishing evidence
A scheduled job — backup, backfill, TTL purge, analyticscurrentOp; cron inventory; metrics.ttl.deletedDocumentsMost likely, given the time. Latency should recover when it ends
Crossed the cache thresholdEviction counter; cache statsEvictions went from 0 to non-zero at 03:00. If a job pulled a large volume through cache, this is the mechanism by which the job hurt

InfrastructureDisk I/O metrics, CPU steal, host eventsA noisy neighbour or a burst-credit exhaustion has exactly this shape

The order I would actually check: currentOp first (it covers the top four at once), then the eviction counter, then whether latency recovered on its own — because "it recovered at 04:10" identifies a job far faster than any metric does.

The trap: assuming the scheduled job is the problem when it is only the trigger. If the job pushed the working set past cache, the durable fix is not "move the job" — the cluster is one growth increment away from the same cliff during normal traffic. Moving the job buys time; capacity or index reduction fixes it.

What makes this diagnosable at all is having the eviction counter and currentOp sampled historically. Without history you can only observe the current state, and by morning the job has finished and the evidence is gone — which is why a low-frequency sampler writing these to a time series is worth more than most dashboards.

4 (medium): Plan a 6.0 → 7.0 upgrade for a 3-node replica set serving production traffic.
Solution 
  PRE-FLIGHT (days before)
    - read the release notes for BREAKING changes and removed
      features; grep the codebase for anything deprecated
    - driver compatibility matrix: does the current driver
      support 7.0? Upgrade the driver FIRST if not -- old driver
      against new server is usually fine, the reverse often is not
    - verify backups exist AND have been restored recently
    - check the oplog window exceeds the time one node will be

        { getParameter: 1, featureCompatibilityVersion: 1 })
      You cannot jump FCV versions; it must be at 6.0 to go to 7.0
    - rehearse the whole sequence on a restored copy

  EXECUTION -- one node at a time, off-peak

       VERIFY: rs.status() shows SECONDARY, lag ~0
    2. secondary B: same
       VERIFY: same

       retryWrites the application should barely notice)
       VERIFY: new primary elected, writes succeeding
    4. former primary: stop, upgrade, start
       VERIFY: rejoined, caught up

    Binaries are now 7.0. FCV is still 6.0 -- and this is the
    REVERSIBLE state.

  SOAK -- days, not minutes
    Run a full business cycle including month-end jobs. Watch
    latency, error rates, replication. If anything is wrong,
    downgrade the binaries the same way, in reverse.

    db.adminCommand({ setFeatureCompatibilityVersion: "7.0",
                      confirm: true })
    New features and on-disk formats become active. Downgrading
    now requires setting FCV back first, which can fail if
    incompatible data already exists.

The decision I would push back on is setting FCV in the same window "to be done with it". The soak is the entire value of the two-step design, and skipping it converts a reversible change into an irreversible one for no benefit.

5 (hard): Design the monitoring and alerting for a production MongoDB deployment. Be explicit about what you would not alert on.
Solution

Design principle: alert on things that are (a) actionable, (b) predictive rather than coincident, and (c) not already covered by a broader alert. The most common failure of database monitoring is not missing alerts — it is so many alerts that the meaningful ones are muted.

Page (wake someone)ThresholdWhy it earns a page
No primaryAny duration > 30 sWrites are failing
Disk space< 20% freeA full disk on a primary is an immediate outage and takes time to fix
App-thread evictions> 0 sustained 5 minThe cliff. Predictive — it fires before latency moves
Replication lag> 60 sMajority writes are at risk of stalling
Connection saturation> 80% of limitPredicts 5xx before they happen
Backup verification failedAnyThe recovery path is broken and nobody would otherwise know
Ticket (do not page)Why
Oplog window below the maintenance thresholdImportant, not urgent — hours of headroom
Any jumbo chunkA future incident, not a current one
Targeted-query fraction decliningArchitectural drift, addressed in a review
New COLLSCAN shape in the profilerBelongs in a weekly review, or better, in CI
Index unused for a full business cycleCleanup candidate

What I would deliberately not alert on:

  • Cache utilisation percentage. Healthy is ~80%. Alerting on it teaches people to ignore cache alerts, which is exactly what you cannot afford when the eviction alert fires.
  • CPU. Rarely the binding constraint, and high CPU during a legitimate index build or backup produces noise.
  • Raw query latency thresholds. A batch rollup legitimately takes minutes. Alert on properties (a spill, a collection scan, a broadcast) and let duration be a dashboard.
  • Connection count in absolute terms rather than against the limit — meaningless without the denominator.
  • Every slow query. That is a report, not an alert.

The gap most teams have, which I would fix first: driver-side metrics. Connection checkout wait time and pool utilisation are what diagnose the "database healthy, app returning 503s" class of incident, and almost nobody collects them. Server monitoring alone cannot see that failure.

And one meta-alert: alert when the monitoring itself stops reporting. A silent dashboard reads exactly like a healthy one.

6 (hard): You are handed a production cluster with no documentation. Produce a one-week plan to reach operational confidence.
Solution

Day 1–2 — inventory and read-only assessment. Change nothing.

  Topology       rs.status(), sh.status(), member types,
                 priorities, votes, hidden/delayed members
  Version        db.version(), FCV, driver versions in the apps
  Data           db.stats() per database; collection sizes;
                 index sizes vs cache
  Indexes        getIndexes() + $indexStats per large collection
  Config         cache size, flow control, profiling level,
                 balancer state and window
  Security       auth enabled? TLS? role assignments? any account
                 with root that an application uses?
  Backups        what exists, when it last succeeded, retention,
                 whether it is reachable with prod credentials
  Health now     eviction counter, lag, oplog window, connections

Day 3 — the workload. Profiler at level 1 with a conservative threshold, grouped by queryHash and ranked by total time. This produces the list of what the cluster actually spends its time on, which is almost never what people believe. On a sharded cluster, also the targeted-query fraction.

Day 4 — the two questions that matter most. Can we recover, and will we know? A restore of the most important database into an isolated environment, timed and data-verified; and an audit of what is alerted on today. In my experience these two produce the largest findings of the week — usually a backup nobody has restored and an alert set that omits the eviction counter.

Day 5 — write it down and rank it. A single document: topology diagram, versions, the top ten query shapes by cost, current known risks ranked by expected harm, and the measured RTO against whatever RTO anyone believes they have.

What I would fix during the week rather than waiting: only things that are both urgent and reversible — a missing maxTimeMS, an alert that does not exist, a backup that is not running at all. Everything else goes on the ranked list, because changing an unfamiliar production system before understanding it is how a handover becomes an incident.

What I would escalate immediately if found: no backups at all; backups deletable with production credentials; authentication disabled; an even-numbered replica set or a P+S+A topology; or a primary above 90% disk. Each of those is a fix-this-week item regardless of the plan.

What I would resist: starting with a tooling or version upgrade. It is the most satisfying-feeling first move and it defers every question that actually determines whether this cluster survives its next bad day.

🎯 Key Takeaways

  • Alert on pages evicted by application threads > 0 — the healthy value is exactly zero, and it moves before latency does.
  • The cache boundary is a cliff, not a slope: p99 1.9 ms at 97% of cache, 340 ms at 112%.
  • Cache utilisation percentage is not a signal. A healthy cache is always nearly full.
  • Size RAM from the working set — indexes plus hot documents — not from collection size.
  • Dedupe indexes before buying RAM. One team recovered 4.1 GB of cache mechanically.
  • Triage in order: currentOp → evictions → concurrent operations → replication → connections → then the slow-query log.
  • During an incident, prefer reversible interventions. Never start an index build on a struggling cluster.
  • Upgrade binaries and set FCV as separate steps. The gap between them is your rollback window.
  • Sharded upgrade order: config servers → shards → mongos.
  • Check driver compatibility first — a new driver against an old server frequently breaks.
  • One change at a time, with the rollback command known and tested before you start.
  • Nest timeouts strictly: maxTimeMS < server selection < application < load balancer.
  • A client giving up does not stop the server — 140 abandoned operations held CPU at 100% for 20 minutes.
  • maxPoolSize is per client instance. 40 pods × 100 = 4,000 connections at ~1 MB each.
  • Pool exhaustion presents as application 5xx with every database metric healthy.
  • Instrument the driver, not just the server — checkout wait time and pool utilisation are what diagnose that class of incident.
  • Alert on what is actionable and predictive, and put the rest in a weekly review. An alert set people mute is worse than a smaller one.
