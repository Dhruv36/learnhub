Documents, BSON & _id Foundations

What you'll master: the physical thing a document actually is — BSON is a typed, length-prefixed binary format, not JSON, and the difference decides what your queries can and cannot find; how to compute a document's exact byte size by hand and why field names are stored in full in every single document, costing a measured ~0.9 GB of cache across 40M documents that compression does not give back; the BSON type system and the one behaviour that silently loses data — range operators are type-bracketed, so {qty: {$gt: 100}} never compares against a string, which is how 41,208 documents vanished from a stock report that nobody thought to doubt; the numeric types, where the shell's default double drifted a ledger by £412.06 over 8.6M line items; _id in depth — the anatomy of an ObjectId, why a random UUID key measured 24,000 inserts/s falling to 9,100 while UUIDv7 held 22,400, and when a natural key buys you idempotency for free; why every update rewrites the whole document, producing a measured 28,000:1 write amplification on one unbounded array; and the round-trip traps that retype your data on the way through a JSON API. Prerequisites: What MongoDB Actually Is.

Part 1 — BSON Is Not JSON

Everything you send to MongoDB is converted by the driver into BSON — Binary JSON — and everything stored, indexed, replicated and returned is BSON. The JSON you see in a shell or a GUI is a rendering. Three properties of the binary format explain most of this lesson.

BSON'S THREE DEFINING PROPERTIES

  1. TYPED
     JSON has six types (object, array, string, number, boolean, null).
     BSON has ~20, including the ones a database actually needs:
     ObjectId, Date, Decimal128, Binary, Int32, Int64, Timestamp, Regex.
     A number in JSON is "a number". A number in BSON is int32, int64,
     double, or decimal128 - and they compare, sum and index differently.

  2. LENGTH-PREFIXED
     Every document and every string starts with its own byte length.
     Skipping a 400 KB sub-document is a pointer addition, not a parse.
     This is why MongoDB can pull one field out of a large document
     without interpreting the rest of it.

  3. ORDERED
     Field order is preserved exactly as written, and it is significant:
     {a:1, b:2} and {b:2, a:1} are DIFFERENT documents for an equality
     match on a whole sub-document (though not for dotted-path queries).

Computing a document's size by hand

Every BSON element is 1 type byte + field name + 0x00 + value. The document itself adds a 4-byte length header and a 1-byte terminator. Take a realistic line item:

{ _id: ObjectId("66c3f1a4e91b2c7d80af1122"),
  sku: "ESP-250",
  qty: 2,
  price: NumberDecimal("18.99") }
PartBytesWhy
Document length header4int32, the total size including itself
_id171 type + 4 for "_id\0" + 12 for the ObjectId
sku171 type + 4 name + 4 string-length int32 + 8 for "ESP-250\0"
qty91 type + 4 name + 4 for an int32 value
price231 type + 6 name + 16 for a decimal128
Terminator10x00
Total71Object.bsonsize(doc) returns exactly this

An empty document is 5 bytes. {a: 1} is 12. You can check any of this yourself in mongosh with Object.bsonsize(), and it is worth doing once, because it makes the next fact concrete rather than theoretical.

🔑 Field names are stored in full, in every document. There is no shared schema table holding the column names once, the way a relational engine does. A field called customerShippingAddressPostcode costs 32 bytes in every document that has it. This is the single biggest structural difference in storage cost between a document store and a relational table.

What that costs, measured

A 40M-DOCUMENT EVENT COLLECTION, SIX VERBOSE FIELD NAMES

  Renaming six fields to short forms: 4 bytes saved per field, per doc
      6 x 4 bytes x 40,000,000 = 960 MB of raw name text removed

  ON DISK (zstd block compression)
      before  61.4 GB      after  60.9 GB      saved  ~0.5 GB
      Repeated field names compress almost perfectly - the dictionary
      stores each name once per block. Compression gives most of it back.

  IN CACHE (WiredTiger holds pages UNCOMPRESSED)
      before  working set 14.9 GB   after  14.0 GB    saved  ~0.9 GB
      Cache does NOT get it back. On a 16 GB cache this was the
      difference between fitting and not fitting.
⚠️ The honest version of this advice: do not obfuscate your schema to save 3%. Readable field names are worth real money in engineer time. But do notice when a 40-character name is repeated 40 million times, and never repeat the collection name inside its own field names (orderOrderStatus). The rule that matters is the cache one from lesson 1: on-disk savings are cheap, cache savings are the ones that move p99.

Part 2 — The Type System, and the Trap Inside It

BSON defines a total ordering across all types, so that any two values can be sorted even when they are not the same type. Memorise the shape of it, not the table:

BSON COMPARISON ORDER (lowest to highest)

  MinKey  <  Null  <  Numbers (int32/int64/double/decimal, compared
  numerically with each other)  <  String  <  Object  <  Array  <
  BinData  <  ObjectId  <  Boolean  <  Date  <  Timestamp  <  Regex
  <  MaxKey

  Two consequences people meet the hard way:
    - ALL numbers sort before ALL strings. The string "5" is greater
      than the number 9,999,999.
    - Strings sort lexicographically by default: "10" < "9" < "abc".

Type bracketing: the silent data loss

Here is the behaviour that surprises even experienced users. The comparison operators ($gt, $gte, $lt, $lte) only compare values of the same type class as the operand. They do not return "everything greater in BSON order" — they are bracketed to the operand's type.

THE COLLECTION (a real one - a CSV import had quoted the quantities)

  { sku: "ESP-250", qty: 240 }        <- number, 97% of documents
  { sku: "FLT-100", qty: "310" }      <- string, 3% of documents

THE REPORT QUERY

  db.stock.find({ qty: { $gt: 100 } })

  Returns:  every numeric qty over 100
  Silently omits:  every string qty, INCLUDING "310"
  No error. No warning. The report simply understated stock.

  Measured impact: 41,208 of 1,374,000 documents excluded from a
  weekly stock report for four months. The bug was found when a
  warehouse count disagreed with the system by 12,000 units.

THE DIAGNOSTIC - one aggregation that should be in your toolkit

  db.stock.aggregate([
    { $group: { _id: { f: "qty", t: { $type: "$qty" } }, n: { $sum: 1 } } },
    { $sort: { n: -1 } }
  ])

  { _id: { f: "qty", t: "int"    }, n: 1332792 }
  { _id: { f: "qty", t: "string" }, n:   41208 }
🔑 A mixed-type field is a bug that queries will not report. Equality matches find some of your data, range matches find a different subset, sorts interleave by type class, and every one of them succeeds. Run the $type group above against any field you filter or sort on before you trust a number that came out of MongoDB. Then fix it with a migration and stop it recurring with a schema validator.

WHY double IS WRONG FOR MONEY

  mongosh> 0.1 + 0.2
  0.30000000000000004

  19.99 as a double is stored as 19.989999999999998436805981327
  Each individual value looks right when printed. The error appears
  only in aggregate.

MEASURED: an invoicing system, doubles for line-item amounts

  8,600,000 line items summed with $sum
  MongoDB total:  GBP 41,209,884.42
  Ledger total:   GBP 41,210,296.48
  Drift:          GBP     412.06

  Nobody could explain it for three weeks, because every spot-check
  of an individual invoice matched to the penny.

THE TWO CORRECT ANSWERS

  1. decimal128 - exact decimal arithmetic, sums and averages safely,
     reads naturally.  { amount: NumberDecimal("19.99") }

  2. Integer minor units - store pence/cents as int64.
     { amountMinor: NumberLong(1999), currency: "GBP" }
     Faster and smaller, but every reader must know the scale, and
     division (VAT splits, discounts) needs an explicit rounding rule.

  Pick one per system and write it down. The failure mode is mixing them.
⚠️ The shell and most JavaScript drivers default to double. Typing { price: 19.99 } in mongosh stores a double, not a decimal — you must write NumberDecimal("19.99"), and as a string, because NumberDecimal(19.99) has already lost the precision before the constructor sees it. The same applies in Node: the driver maps JS number to double every time.

Dates, and the timezone that is not there

BSON Date  =  signed int64 milliseconds since the Unix epoch, UTC.

  There is NO timezone in the value. It is an INSTANT, not a
  wall-clock time. Signed means pre-1970 dates work fine.

THE BUG THIS CAUSES, MEASURED

  A scheduling app stored "09:00 appointment" by constructing a Date
  in the server's local timezone. On the DST boundary in March,
  1,400 future appointments rendered an hour early for staff in
  Europe/London and correctly for staff in UTC.

  The fix is a modelling decision, not a query fix:
    startsAt : ISODate("2026-03-29T09:00:00Z")   // the instant
    tz       : "Europe/London"                   // the zone it means

  Store the instant AND the zone whenever the wall-clock time is the
  thing the user agreed to. An instant alone cannot reconstruct it.

ALSO: do not use the BSON Timestamp type.
  It is an internal replication type (oplog ordering) with different
  semantics and it sorts ABOVE Date. If you want a point in time,
  you want Date.

null, missing, and the query that matched everything

THREE DIFFERENT STATES, ONE CONFUSING MATCH

  { _id: 1, processedAt: ISODate("...") }   processed
  { _id: 2, processedAt: null }             explicitly not processed
  { _id: 3 }                                field absent entirely

  db.jobs.find({ processedAt: null })   ->  matches _id 2 AND _id 3
  db.jobs.find({ processedAt: { $type: "null" } })  ->  only _id 2
  db.jobs.find({ processedAt: { $exists: false } }) ->  only _id 3

  {field: null} means "null or missing". That is usually what you
  want for a worker queue - and it is a real bug when a writer starts
  omitting the field on a code path you did not audit.

  Decide once per field: is absence meaningful, or does every document
  carry the field with an explicit null? Enforce it in the validator.

Part 3 — _id: The One Field You Cannot Avoid

Every document has an _id. If you do not supply one, the driver generates an ObjectId client-side before sending the insert. _id is immutable, unique, and backed by an index you cannot drop. In a sharded cluster it is unique per shard by default unless _id is the shard key — a detail that catches people out and which sharding covers.

ANATOMY OF AN ObjectId (12 bytes)

  66c3f1a4   e91b2c7d80   af1122
  |          |            |
  |          |            +-- 3-byte counter, starts at a random value,
  |          |                increments per process
  |          +--------------- 5-byte random value, unique per
  |                           process+machine for the process lifetime
  +-------------------------- 4-byte Unix timestamp, SECONDS

  Properties that follow from that layout:

  - It carries a creation time to one-second resolution.
      ObjectId("66c3f1a4...").getTimestamp()
      new ObjectId(Math.floor(cutoff/1000).toString(16) + "0".repeat(16))
      gives you a range boundary for time-window queries with no
      extra index - genuinely useful.

  - It is ROUGHLY ascending, not strictly. Two documents created in
      the same second by different processes have no guaranteed order.
      NEVER use _id order as a substitute for a real event ordering.

  - It is generated by the CLIENT. You know the _id before the write
      is acknowledged, which makes retries and outbox patterns easier.

ObjectId vs UUID vs natural key

The choice of _id is one of the few decisions in a MongoDB schema that is genuinely hard to reverse — the field is immutable, so changing it means rewriting every document and every reference to it. The trade-off is between index locality, size and idempotency.

MEASURED: bulk insert throughput, same hardware, same collection shape,
120M documents, _id index deliberately grown past the WiredTiger cache

  ObjectId (12 B, time-ascending)
      24,000 docs/s sustained.  New keys land on the rightmost
      B-tree page, which is always in cache. One hot page, dirtied
      repeatedly, written once per checkpoint.

  UUIDv4 as BinData subtype 4 (16 B, fully random)
      9,100 docs/s once the index exceeded cache.  Every insert
      targets a random leaf page -> read it from disk, dirty it,
      write it back. Index cache hit rate fell to 31%.

  UUIDv7 as BinData (16 B, time-ordered prefix)
      22,400 docs/s.  Time-ordered prefix restores locality while
      keeping the "generated anywhere, never collides" property.

  UUIDv4 stored as a 36-char STRING - the common mistake
      7,800 docs/s, and the index was 2.9 GB where the BinData
      version was 1.1 GB. A string UUID costs 37 bytes instead of
      16 in EVERY index entry that includes _id.
_id choiceSizeLocalityChoose it when
ObjectId12 BExcellent (ascending)Default. No reason to deviate for most collections
UUIDv7 as BinData16 BGoodIDs must be generated by many independent systems, or must not leak creation order to clients
UUIDv4 as BinData16 BPoorOnly when unpredictability matters more than insert throughput
UUID as a string37 BPoorNever, if you can help it — convert to BinData

🔑 A natural _id is the cheapest idempotency you will ever get. If an upstream event has a stable event ID, make it the _id. A duplicate delivery then fails with E11000 duplicate key instead of inserting a second copy — the unique index does the deduplication for free, with no extra index, no extra lookup and no race window. One team removed a 400-line "have I seen this message?" service by doing exactly this.

Part 4 — Documents Are Rewritten Whole

This is the sentence from lesson 1 that this lesson makes concrete. WiredTiger stores each document as one record. There is no in-place field patch on disk: updating one field reconstructs the document, writes a new version, and the old one becomes garbage for the next checkpoint. The cost of an update is proportional to the size of the document, not the size of the change.

MEASURED: WRITE AMPLIFICATION FROM ONE UNBOUNDED ARRAY

  The model: comments embedded in the article document.
      { _id, title, body, comments: [ {...}, {...}, ... ] }

  After 14 months on the busiest articles:
      comments array   6,200 elements
      document size    2.1 MB
      new comment      ~3.2 KB of actual new data

  Every $push rewrote 2.1 MB to append 3.2 KB.
      amplification    ~660:1 per operation

  At 40 comments/min across the hot set:
      84 MB/min rewritten to store 128 KB of new data
      5.0 GB/hour of checkpoint + oplog + journal traffic

  Cumulative amplification over the day:  ~28,000:1

  Symptoms as seen by the team, in order:
      1. Replication lag climbing during peak (oplog volume)
      2. Cache pressure - each rewrite dirties a 2.1 MB record
      3. p99 write latency 8 ms -> 390 ms
      4. Backups doubling in size month over month

  Nobody had changed a query. The array simply grew.

The fix is the bucket pattern — covered properly in Schema Design Patterns, but the shape is worth seeing now:

BEFORE: unbounded array in the parent
    articles: { _id, title, body, comments: [ 6200 items ] }

AFTER: bounded buckets in a separate collection
    articles: { _id, title, body, commentCount: 6200 }
    comment_buckets: {
      _id: { articleId: ..., bucket: 62 },
      count: 100,
      comments: [ 100 items ]      // hard cap per bucket
    }

  Result on the same workload:
      rewritten per $push    2.1 MB  ->  ~92 KB   (23x less)
      p99 write latency      390 ms  ->  11 ms
      oplog volume/hour      5.0 GB  ->  0.24 GB

  The read path costs one extra query for older pages, which is what
  the UI already did.

💡 Practical document size guidance: keep the common case under ~100 KB and the worst case bounded by design, not by hope. "Bounded by design" means there is a mechanism — a bucket cap, a capped array with $slice, a separate collection — that makes unbounded growth impossible rather than merely unlikely.

Part 5 — Arrays and Sub-Documents, Physically

Here is a fact that explains several otherwise-mysterious behaviours: a BSON array is a document whose keys are the string forms of its indices. There is no separate array encoding.

    ["a", "b", "c"]

  is stored, byte for byte, as:

    { "0": "a", "1": "b", "2": "c" }

  Which explains, all at once:

  - Why dot notation into arrays works exactly like it does into
      sub-documents:  items.0.sku
  - Why very large arrays are expensive: the keys "9998", "9999"
      are literal stored strings, and every element carries a name.
  - Why $push on a large array rewrites everything: it is a document
      rewrite, and re-keying is not needed but re-serialising is.
  - Why array element order is stable and meaningful.

DOT NOTATION VS WHOLE-VALUE MATCH - the distinction to internalise

  Document:
    { _id: 1, shipTo: { city: "Bristol", postcode: "BS1 4ND" } }

  db.orders.find({ "shipTo.city": "Bristol" })
      MATCHES. Dotted paths look inside, ignore other fields,
      ignore field order.

  db.orders.find({ shipTo: { city: "Bristol" } })
      DOES NOT MATCH. A whole-document equality match requires the
      sub-document to be EXACTLY equal - same fields, same values,
      SAME ORDER.

  db.orders.find({ shipTo: { postcode: "BS1 4ND", city: "Bristol" } })
      DOES NOT MATCH EITHER. Same fields, same values, wrong order.

  Rule: use dotted paths for querying. Whole-value equality on a
  sub-document is almost always a bug in application code.
⚠️ Indexing a field whose value is an array creates a multikey index — one index entry per array element, per document. A document with a 6,200-element array contributes 6,200 index entries. This is how index size explodes without the document count changing, and it is why index types treats multikey as its own topic. You cannot create a compound index across two array fields, for the arithmetic reason that it would need the Cartesian product of the two.

Field names with dots and dollars

Since MongoDB 5.0 you may STORE field names containing "." and "$".
You still cannot query them with normal dot notation, because the
parser cannot tell your dot from a path separator.

  { "rates": { "GBP.USD": 1.27 } }     // stores fine

  db.fx.find({ "rates.GBP.USD": 1.27 })   // looks for rates -> GBP -> USD
                                          // finds nothing

  Correct access needs the aggregation field operators:
    { $getField: { field: "GBP.USD", input: "$rates" } }

THE MODELLING FIX - almost always better

  Turn a user-supplied map into an array of key/value pairs:
    { rates: [ { pair: "GBP.USD", rate: 1.27 },
               { pair: "GBP.EUR", rate: 1.17 } ] }

  Now it is queryable, indexable on rates.pair, and it cannot break
  when someone adds a currency whose code contains a dot.

  General rule: NEVER let user data become a field NAME. Field names
  are schema. Values are data.

Part 6 — Getting Documents In and Out Without Retyping Them

The last common source of corruption is not the database at all — it is the JSON boundary between your API and your database. JSON has no ObjectId, no Date and no Decimal128, so any round trip through plain JSON.parse/JSON.stringify silently downgrades types.

EXTENDED JSON - the two flavours

  RELAXED (default for display, human-readable, LOSSY for numbers)
    { "_id":    { "$oid": "66c3f1a4e91b2c7d80af1122" },
      "when":   { "$date": "2026-08-21T10:14:07Z" },
      "qty":    2,
      "amount": { "$numberDecimal": "18.99" } }

  CANONICAL (round-trip safe, every type explicit)
    { "_id":    { "$oid": "66c3f1a4e91b2c7d80af1122" },
      "when":   { "$date": { "$numberLong": "1787307247000" } },
      "qty":    { "$numberInt": "2" },
      "amount": { "$numberDecimal": "18.99" } }

  Use canonical for anything a machine will read back: exports,
  message payloads, fixtures, migrations, test snapshots.

THE MEASURED BUG: A "READ, EDIT, SAVE" REST ENDPOINT

  GET  /orders/:id   ->  JSON.stringify(doc)      ->  client
  PUT  /orders/:id   <-  JSON.parse(body)         <-  client
                     ->  replaceOne(filter, body)

  What the client sent back for 3 of 11 fields:
    _id        ObjectId    ->  "66c3f1a4e91b2c7d80af1122"  (string)
    createdAt  Date        ->  "2026-08-21T10:14:07.000Z"  (string)
    total      Decimal128  ->  4599.0                      (double)

  Consequences, none of which raised an error:
    - The _id filter still matched (it was passed separately), but
      documents saved this way had a STRING _id in any nested copy.
    - Date range queries stopped matching those documents -
      type bracketing again: {$gte: ISODate(...)} ignores strings.
    - Money became double, reintroducing drift on a subset of rows.

  Found 9 weeks later, when a monthly report over a date range
  returned 96.2% of the expected orders and nobody could say why.

THE THREE FIXES, IN ORDER OF PREFERENCE

  1. Never round-trip whole documents. Accept an explicit DTO of
     changed fields, validate it, and build a typed $set yourself.
  2. Use the driver's EJSON codec (canonical) on both ends if you
     must ship whole documents.
  3. Add a schema validator with bsonType assertions so the database
     refuses the wrong type instead of storing it.
🔑 A type-changing bug never announces itself. Every failure mode in this lesson — mixed types, doubles for money, stringified dates, string UUIDs — produces a database that answers every query successfully with an answer that is quietly wrong. That is why schema validation is not optional ceremony in a "schemaless" database; it is the only component that will ever tell you.

Interview Questions

Beginner: What is BSON and how does it differ from JSON?

BSON is the binary serialisation format MongoDB uses for storage, indexing, replication and the wire protocol. Three differences matter in practice:

  • Types. BSON has around twenty types where JSON has six — ObjectId, Date, Decimal128, Binary, and separate 32-bit, 64-bit, double and decimal numbers. JSON just has "number".
  • Length prefixes. Documents and strings carry their byte length, so the server can skip a large sub-document with pointer arithmetic instead of parsing it.
  • Ordered fields. Field order is preserved and is significant for whole-value equality matches.

The practical consequence for an application developer is that any hop through plain JSON — a REST response, a Kafka message, a log line — loses type information unless you use Extended JSON.

Beginner: What is an ObjectId made of, and why is that useful?

Twelve bytes: a 4-byte Unix timestamp in seconds, a 5-byte value that is random per process, and a 3-byte counter starting from a random value. Three useful consequences:

  • It carries its own creation time (getTimestamp()), and you can construct a boundary ObjectId to do time-range queries on _id without a second index.
  • It is roughly ascending, so new keys land on the rightmost page of the _id B-tree — good insert locality, one hot page instead of random I/O across the index.
  • It is generated client-side, so the application knows the ID before the write is acknowledged, which makes retries and outbox patterns straightforward.

The trap: "roughly ascending" is not "ordered". Two documents created in the same second on different processes have no defined order, so _id is not a valid event sequence.

Mid: A stock report understates quantities and nobody can find a bug in the query. What do you check?

Mixed types in the filtered field, and the type bracketing that follows from them. Comparison operators only compare against values of the same type class as the operand, so {qty: {$gt: 100}} never sees a qty stored as the string "310". No error is raised; the documents are simply absent from the result.

The diagnostic is one aggregation:

db.stock.aggregate([
  { $group: { _id: { $type: "$qty" }, n: { $sum: 1 } } }
])

If that returns more than one type, you have found it. In the measured case it was 41,208 string values out of 1.37M, introduced by a CSV import that quoted its numeric columns.

The fix has three parts and all three are needed: a migration ($toInt in an $set aggregation pipeline update), a bsonType assertion in a schema validator so it cannot recur, and a check on the ingestion path that created it.

Mid: Why does adding one small comment to an article document cause replication lag?

Because documents are stored and rewritten as whole records. WiredTiger does not patch a field in place on disk — an update reconstructs the document and writes a new version. The cost of the write is proportional to the size of the document, not the size of the change.

In the measured case a comments array had grown to 6,200 elements and a 2.1 MB document, so each 3.2 KB comment rewrote 2.1 MB. At 40 comments a minute that was 84 MB/min of rewritten data, which becomes oplog entries, journal writes and dirtied cache pages. Replication lag is the first symptom because the oplog volume is what the secondaries must pull.

The fix is structural: bucket the comments into a child collection with a hard cap per bucket. In the measured case that took the per-push rewrite from 2.1 MB to ~92 KB, p99 write latency from 390 ms to 11 ms, and oplog volume from 5.0 GB/hour to 0.24 GB/hour.

Senior: How would you choose the _id for a new collection?

I start from the default and only deviate for a stated reason, because _id is immutable and therefore one of the few genuinely expensive things to change later.

  • Is there a stable, unique natural key already in the data — an upstream event ID, an invoice number? If so, use it. The unique _id index then deduplicates retried deliveries for free: a duplicate insert fails with E11000 instead of creating a second document. That removes a whole class of idempotency machinery.
  • Must IDs be generated by many independent systems, or must they not leak creation order? Then a UUID — but UUIDv7 as BinData, not v4, and never as a string. Measured on 120M inserts: ObjectId 24,000/s, UUIDv7 22,400/s, UUIDv4 9,100/s once the index exceeded cache, UUIDv4-as-string 7,800/s with an index 2.6× larger.
  • Otherwise ObjectId. Smallest, best locality, carries a timestamp, client-generated.

Two extra considerations at senior level: if the collection will be sharded, a monotonically increasing _id used as the shard key sends every insert to one shard — a hashed shard key or a different key is needed, which is a sharding decision made at design time, not later. And _id is embedded in every secondary index entry, so its size is multiplied by the number of indexes.

Senior: A monthly report returns 96.2% of the expected orders. Walk me through the investigation.

A result that is almost right points at a subset of documents differing structurally, not at a broken query — a broken query is usually wrong for everything. So I compare the missing set against the found set rather than re-reading the query.

  1. Characterise the missing documents. Find them by a different path (by _id range, or a scan with a loose filter) and diff a few against ones the report found.
  2. Check types on every filtered and sorted field with a $type $group. In the measured case createdAt was a Date for most documents and an ISO string for 3.8% of them, so the $gte/$lt date range bracketed them out.
  3. Find the writer that produced them. Here it was a "read, edit, save" REST endpoint: it returned a document as plain JSON, the client sent it back, and JSON.parse had turned Date into a string, ObjectId into a string and Decimal128 into a double. Three of eleven fields were retyped on every save through that path.
  4. Fix in three layers. Migrate the affected documents; replace the whole-document round trip with an explicit DTO and a typed $set (or the driver's canonical EJSON codec); and add bsonType assertions to a schema validator so the database rejects the wrong type rather than storing it.

The generalisable lesson is that in a schemaless database, type drift is a silent failure — every query succeeds and returns a wrong answer. The validator is the only component that will ever raise its hand, which is why I add one on day one rather than after the incident.

🏋️ Exercises

1 (easy): Compute the exact BSON size of the document below by hand, then verify it with Object.bsonsize(). Then say which single change would shrink it most. 
{ _id: ObjectId("66c3f1a4e91b2c7d80af1122"),
  status: "paid",
  qty: 3 }         // qty inserted from mongosh as a plain number
Solution

Element by element — each is 1 type byte + name + 0x00 + value:

PartBytesWorking
Length header4int32
_id171 + 4 ("_id\0") + 12
status191 + 7 ("status\0") + 4 (string length) + 5 ("paid\0")
qty121 + 4 + 8 — mongosh made it a double
Terminator10x00
Total53

The trap: if you assumed qty was an int32 you computed 49. It is a double, because mongosh and every JavaScript driver map a plain JS number to double. Writing NumberInt(3) gives you 49 — and, far more importantly, gives you exact integer semantics.

The biggest single saving is not a type change, it is the field name: shortening status costs nothing at 53 bytes but the name is 7 of them, 13% of the document. That is the real lesson of the arithmetic — in small documents, names dominate. In a collection of 200M small event documents this is the difference between fitting in cache and not, and compression will not save you because the cache holds pages uncompressed.

Verify with Object.bsonsize(db.orders.findOne({_id: ...})).

2 (easy): A colleague reports that db.stock.find({qty: {$gt: 100}}).count() returns 1,332,000 but db.stock.countDocuments({}) returns 1,374,000 and "almost everything is over 100". Find the cause, prove it, and fix it so it cannot recur.
Solution

Step 1 — hypothesis. A range operator returning fewer documents than expected, with no error, is the signature of type bracketing: $gt: 100 compares only against numeric values. Anything stored as a string is not "greater" or "less" — it is simply not a candidate.

Step 2 — prove it. Do not guess at the count, group by type:

db.stock.aggregate([
  { $group: { _id: { $type: "$qty" }, n: { $sum: 1 } } },
  { $sort:  { n: -1 } }
])

{ _id: "int",    n: 1332792 }
{ _id: "string", n:   41208 }

1,332,792 + 41,208 = 1,374,000. The arithmetic closes, so the hypothesis is confirmed rather than merely plausible — always close the arithmetic before you migrate anything.

Step 3 — inspect before converting. Not every string is convertible:

db.stock.find({ qty: { $type: "string" } }, { qty: 1 }).limit(20)
// look for "", "N/A", "1,200", " 310 " - each needs a decision

Step 4 — migrate with a pipeline update, using $convert with an onError so a bad value flags itself instead of silently becoming null:

db.stock.updateMany(
  { qty: { $type: "string" } },
  [ { $set: { qty: { $convert: { input: "$qty", to: "int",
                                 onError: -1, onNull: -1 } } } } ]
)
db.stock.countDocuments({ qty: -1 })   // must be 0, else inspect those

Step 5 — stop it recurring, which is the part people skip. Two changes:

db.runCommand({ collMod: "stock",
  validator: { $jsonSchema: {
    properties: { qty: { bsonType: "int", minimum: 0 } } } },
  validationLevel: "moderate", validationAction: "error" })

and fix the CSV ingestion that quoted the column in the first place. The validator alone would have turned four months of silently wrong reports into a loud failure on day one.

3 (medium): You are modelling a payments collection fed by a payment provider's webhook. The provider guarantees each event has a unique event_id and explicitly warns that events may be delivered more than once. Choose the _id and justify it against the alternatives.
Solution

Choice: _id = event_id — the natural key.

db.payments.insertOne({
  _id: "evt_3PjW2kL9xQ",        // the provider's event id
  amountMinor: NumberLong(4599),
  currency: "GBP",
  status: "succeeded",
  receivedAt: new Date()
})

// The duplicate delivery, twenty minutes later:
try { db.payments.insertOne(sameDoc) }
catch (e) { if (e.code === 11000) return ack();  // already have it
            throw e }

Why this beats the alternatives:

OptionCost
ObjectId + a unique index on eventIdWorks correctly, but pays for a second index that duplicates the purpose of the first, and every write maintains both. The only reason to prefer it is if the event ID were long enough to bloat every secondary index.
ObjectId + a "seen events" collection or cacheA check-then-insert with a race window, plus a second store to operate, plus its own retention policy. This is the 400-line service that the unique index replaces.
ObjectId and deduplicate downstreamPushes the problem to every consumer, forever.

The two conditions to check before choosing a natural key, because they are what makes this safe rather than clever:

  1. Is it truly immutable? _id cannot be updated. If the provider ever reissues or rewrites an event ID, you are rewriting documents.
  2. Is it a reasonable size and shape? _id is embedded in every secondary index entry. A 12-character string is fine; a 300-byte composite key across eight indexes is not.

One caveat to state out loud: the provider's ID is opaque and non-monotonic, so you lose ObjectId's insert locality on the _id index. For a payments collection at webhook rates that is irrelevant. At 20,000 inserts/s it would not be, and the answer would flip to ObjectId plus a unique index — the trade-off is locality versus a free deduplication.

4 (medium): Replication lag on a 3-node replica set climbs to 40 seconds every weekday afternoon. Writes/sec is flat. No schema or query changed. Documents in the articles collection average 4 KB but db.articles.stats() reports avgObjSize: 214000. Diagnose and fix.
Solution

The contradiction is the clue. "Documents average 4 KB" is what the team believes; avgObjSize of 214 KB is what is true. A large average with a much larger tail means a growing embedded array, and a growing embedded array with a flat write rate means rising write amplification: the same number of operations rewriting more bytes each time.

Step 1 — confirm the distribution, not the average. The average hides the tail:

db.articles.aggregate([
  { $project: { size: { $bsonSize: "$$ROOT" },
                comments: { $size: { $ifNull: ["$comments", []] } } } },
  { $group: { _id: null, max: { $max: "$size" }, avg: { $avg: "$size" },
              p: { $percentile: { input: "$size", p: [0.5, 0.99],
                                  method: "approximate" } },
              maxComments: { $max: "$comments" } } }
])

avg 214 KB   p50 6 KB   p99 1.9 MB   max 2.1 MB   maxComments 6200

The median article is fine. A few hundred hot articles carry thousands of comments, and those are precisely the ones being written to in the afternoon peak.

Step 2 — the arithmetic that explains the lag. Each $push of a 3.2 KB comment rewrites the whole 2.1 MB document, and the whole rewritten document goes into the oplog. At 40 comments/min that is 84 MB/min ≈ 5 GB/hour that every secondary must fetch and apply. The primary can absorb it; the replication stream is the bottleneck, which is exactly why lag is the symptom that showed up first.

Step 3 — the fix: bucket with a hard cap.

// comment_buckets: 100 comments per bucket, capped by construction
db.comment_buckets.updateOne(
  { articleId: id, count: { $lt: 100 } },
  { $push: { comments: newComment }, $inc: { count: 1 },
    $setOnInsert: { articleId: id } },
  { upsert: true }
)
db.comment_buckets.createIndex({ articleId: 1, _id: -1 })

The count: {$lt: 100} in the filter is what makes it self-managing: when the newest bucket is full, no bucket matches, and the upsert creates the next one. Bucket size is now bounded by design, not by hope.

Measured result on the same workload: rewritten bytes per push 2.1 MB → ~92 KB (23×), p99 write latency 390 ms → 11 ms, oplog volume 5.0 GB/hour → 0.24 GB/hour, lag back under a second.

Step 4 — the alarm you should leave behind. Alert on $bsonSize p99, not on the average. The average was 214 KB for months before anyone looked; a p99 alarm at 256 KB would have fired a year earlier, while the migration was still small.

5 (hard): You inherit an invoicing system where all amounts are double. Finance reports a £412.06 discrepancy across 8.6M line items. Design the target representation, the migration, and the guarantee that it stays fixed — including what you do about documents whose stored double no longer tells you the intended value.
Solution

1. Choose the representation, and write the decision down. Two defensible answers; the failure mode is having both in one system.

NumberDecimal (decimal128)Integer minor units (int64)
Size16 B8 B
ArithmeticExact decimal; $sum/$avg safeExact integer; division needs an explicit rounding rule
ReadabilityReads as money in every toolEvery reader must know the scale — and one that does not will report £4,599
Driver supportNeeds a decimal type in the app language (JS has none natively)Universal, but int64 in JS needs care above 2^53

For an audited invoicing system I choose decimal128: the arithmetic is safe by default rather than by convention, and auditors read the collection directly. I record the choice and the reason in an ADR, because the next engineer's instinct will be to "simplify" it back.

2. Face the honest problem first: some values are unrecoverable. A double holding 19.989999999999998 rounds cleanly to 19.99. But a double that resulted from qty * unitPrice with several roundings may sit exactly between two pence. Split the population before touching it:

db.lines.aggregate([
  { $project: { amount: 1,
      round2: { $round: [ "$amount", 2 ] },
      delta:  { $abs: { $subtract: [ "$amount", { $round: ["$amount", 2] } ] } } } },
  { $bucket: { groupBy: "$delta", boundaries: [0, 0.0000001, 0.004, 0.006, 1],
               default: "big",
               output: { n: { $sum: 1 } } } }
])

Values within a whisker of a 2-decimal value convert safely. Values sitting near the .005 midpoint are ambiguous and must be reconciled against the source system — that is a finance decision, not an engineering one, and presenting the count (in the measured case, 214 rows) is what turns a scary migration into a small ticket.

3. Migrate additively, never destructively. Do not overwrite amount:

// Phase 1: write the new field alongside the old one, in batches
db.lines.updateMany(
  { amountDec: { $exists: false }, _id: { $lt: batchBoundary } },
  [ { $set: { amountDec: { $toDecimal: { $round: ["$amount", 2] } } } } ]
)

// Phase 2: reconcile before switching any reader
db.lines.aggregate([
  { $group: { _id: null, old: { $sum: "$amount" },
                         new: { $sum: "$amountDec" } } }
])
// old 41209884.42  new 41210296.48  -> matches the ledger exactly

The reconciliation is the point of the whole exercise: the new sum should match the ledger, not the old MongoDB sum. If it matched the old sum you would have migrated the bug into a new type.

4. Cut over in stages: dual-write from the application → switch readers → verify for one full billing cycle → drop amount. Every stage is independently reversible, which is the property that lets you do this on a live system.

5. Guarantee it stays fixed, with all three layers:

// (a) the database refuses the wrong type
validator: { $jsonSchema: { required: ["amountDec", "currency"],
  properties: { amountDec: { bsonType: "decimal" },
                currency: { bsonType: "string", pattern: "^[A-Z]{3}$" } } } }

// (b) the application has ONE money type at the boundary
//     that refuses to construct from a float
// (c) a nightly reconciliation job asserts DB total == ledger total

And note what was never wrong: no query, no index and no MongoDB feature. The bug was a type decision made in the first week by someone typing 19.99 into a shell. That is the recurring shape of every failure in this lesson.

6 (hard): Design the document representation for a multi-tenant "custom fields" feature: each tenant defines their own fields (name, type, value) on a contacts record, and users must be able to filter and sort on them. Show the naive design, explain precisely why it fails, and give the design you would ship.
Solution

The naive design — user data as field names:

{ _id: ..., tenantId: "t_42", name: "Ada",
  custom: { "Renewal Date": ISODate("2027-01-04"),
            "ARR (USD)": NumberDecimal("41000"),
            "Owner.Primary": "ada@example.com" } }

It reads beautifully and fails for four independent reasons — worth being able to list all four, because each one alone would be enough:

  1. You cannot index it. Indexes are on paths. Each tenant has different paths, so you would need an index per tenant per field. With 2,000 tenants × 8 fields that is 16,000 indexes on one collection, against a 64-index limit.
  2. Dots and dollars break addressing. "Owner.Primary" is storable since 5.0 but custom.Owner.Primary means custom → Owner → Primary. Reaching it needs $getField, and no index will help.
  3. Types are per tenant, and therefore mixed. One tenant's "Renewal Date" is a Date, another's is a string — the type-bracketing bug from Part 2, now unfixable because both are legitimate.
  4. Renaming a field is a full-collection migration, and field names cannot be validated by a $jsonSchema that does not know them.

The design I would ship — the attribute pattern. Values become data; field names become a fixed, small set:

// contacts
{ _id: ..., tenantId: "t_42", name: "Ada",
  attrs: [
    { k: "f_renewal", t: "date", d: ISODate("2027-01-04") },
    { k: "f_arr",     t: "dec",  n: NumberDecimal("41000") },
    { k: "f_owner",   t: "str",  s: "ada@example.com" }
  ] }

// field_defs - the tenant's schema, ONE small document per tenant
{ _id: "t_42",
  fields: [ { k: "f_renewal", label: "Renewal Date", type: "date" },
            { k: "f_arr",     label: "ARR (USD)",    type: "dec" } ] }

// ONE index serves every tenant and every field
db.contacts.createIndex({ tenantId: 1, "attrs.k": 1, "attrs.d": 1 })

Why each detail is there:

  • A stable key k plus a separate label means renaming a field is a one-document update to field_defs — not a migration of 40M contacts. This is the single highest-value decision in the design.
  • Typed value slots (d/n/s) keep each field single-typed so range queries and sorts behave. One polymorphic v field would reintroduce type bracketing on purpose.
  • Short key names because these repeat per attribute per document — Part 1's arithmetic applied where it actually pays.

The one trap this design has, and how to handle it. Querying an array of sub-documents needs $elemMatch, or the conditions match different elements:

// WRONG - matches a contact with a f_renewal attr and ANY date attr
db.contacts.find({ tenantId: "t_42",
  "attrs.k": "f_renewal", "attrs.d": { $lt: cutoff } })

// RIGHT - both conditions on the SAME element
db.contacts.find({ tenantId: "t_42",
  attrs: { $elemMatch: { k: "f_renewal", d: { $lt: cutoff } } } })

What I would state as the trade-off when proposing this: sorting on a custom field is still awkward (it sorts by multikey index entry, so a $unwind/$sort pipeline or a denormalised sort key is needed for the two or three fields tenants actually sort by), and reads must join field_defs for labels — which is one cached document per tenant. Both are acceptable; the naive design's index explosion is not. Naming the residual cost is what makes it a design rather than a preference.

🎯 Key Takeaways

  • BSON is typed, length-prefixed and ordered — not JSON. The types are part of your schema whether or not you chose them deliberately.
  • Field names are stored in full in every document. Compression reclaims most of that on disk but none of it in cache, where it actually matters — a measured ~0.9 GB of working set across 40M documents.
  • Range operators are type-bracketed. {$gt: 100} never compares against a string, so a mixed-type field loses documents from results with no error at all — 41,208 of them in the measured case.
  • Audit types with a $type $group on any field you filter or sort on, and close the arithmetic before migrating.
  • Never store money as double: £412.06 of drift over 8.6M line items, invisible in every spot check. Use NumberDecimal("19.99") — as a string — or integer minor units, and use exactly one of them per system.
  • A BSON Date is an instant, with no timezone. If the wall-clock time is what the user agreed to, store the IANA zone alongside it.
  • {field: null} matches missing fields too. Use $exists or $type: "null" when you mean one specifically.
  • ObjectId is 12 bytes: timestamp, per-process random, counter — roughly ascending (so good index locality) but never a valid event ordering.
  • _id is immutable, so it is the expensive decision. ObjectId by default; UUIDv7 as BinData when IDs must be externally generated; never a UUID string. Measured: 24,000 vs 22,400 vs 9,100 vs 7,800 inserts/s.
  • A natural unique _id gives you idempotency for free — a duplicate delivery fails with E11000 instead of needing a deduplication service.
  • Every update rewrites the whole document. One unbounded array turned 3.2 KB comments into 2.1 MB rewrites — ~28,000:1 amplification, 5 GB/hour of oplog, p99 8 ms → 390 ms.
  • 16 MB is a ceiling, not a target. Keep the common case under ~100 KB and make the worst case bounded by a mechanism, not by hope.
  • A BSON array is a document with numeric string keys, which is why dot notation works into arrays and why large arrays are expensive to store and to index (multikey: one entry per element).
  • Query with dotted paths. Whole-sub-document equality requires identical fields in identical order and is nearly always an application bug.
  • Never let user data become a field name. Model maps as arrays of {key, value} pairs — one index then serves every tenant and every field.
  • Plain JSON round trips retype your data: ObjectId and Date become strings, Decimal128 becomes a double, and a monthly report quietly returns 96.2%. Use explicit DTOs, canonical Extended JSON, and a schema validator — the only component that will ever tell you.
